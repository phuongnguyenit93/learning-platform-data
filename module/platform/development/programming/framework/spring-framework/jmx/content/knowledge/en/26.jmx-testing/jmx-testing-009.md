# Testing Remote Connectors in an Isolated Environment — Spring Framework JMX

## Learning Objectives

This lesson belongs to the **Testing** group of **Spring Framework JMX**, focusing on testing a remote JMX connection between a client JVM and a server JVM without relying on production infrastructure, exposing management ports on public networks, or polluting the registries of other tests.

After completing it, you will be able to:

- Distinguish \`MBeanServer\`, \`JMXConnectorServer\`, \`JMXConnector\`, \`MBeanServerConnection\`, and \`JMXServiceURL\`.
- Build a test environment allowing only loopback connections, using dynamic ports, with full teardown.
- Run server and client in the same JVM to test the JMX remote protocol or in two JVMs for stronger isolation.
- Test the end-to-end path: register MBean → start connector → connect client → read attribute → invoke operation → disconnect.
- Understand the difference between testing connector transport and testing the JVM's remote JMX management agent configuration.
- Control authentication, SSL/TLS, timeouts, and secrets appropriately for the environment.
- Diagnose RMI registry, advertised host, port, registration, lifecycle, and callback errors.
- Build tests reproducible in CI without relying on hardcoded IPs or pre-running servers.

## 1. What Is a Remote JMX Connector?

JMX provides a client/server model:

\`\`\`text
JVM client                              JVM server
-----------                             -------------------
JMXConnectorFactory.connect             JMXConnectorServer
        |                                       |
        v                                       v
JMXConnector                             MBeanServer
        |                                       |
        v                                       +-- ObjectName -> MBean
MBeanServerConnection                           |
        |                                       |
        +------ getAttribute/invoke ------------+
\`\`\`

In Spring Framework JMX, \`MBeanExporter\` typically exports Spring beans into an \`MBeanServer\`. However, **MBeanExporter does not automatically open a remote endpoint**. For an external JVM to access the registry, a suitable connector is needed, such as a JSR 160 RMI connector.

Each component has a distinct responsibility:

| Component | Responsibility |
| --- | --- |
| \`MBeanServer\` | Holds registered MBeans and executes JMX operations |
| \`MBeanExporter\` | Exports Spring beans into the server and manages lifecycle registration |
| \`JMXConnectorServer\` | Exposes the remote JMX endpoint for clients |
| \`JMXServiceURL\` | Describes the address/protocol used by clients |
| \`JMXConnector\` | Manages the client-side connection |
| \`MBeanServerConnection\` | Client API for calling \`getAttribute\`, \`invoke\`, \`queryNames\`, etc. |
| \`RMI Registry\` | In a common JMX/RMI setup, binds \`jmxrmi\` so clients can look up the stub |

A local API test calling \`server.getAttribute(...)\` **does not test the remote connector**. To verify transport, create a \`JMXConnector\` from a \`JMXServiceURL\`, obtain an \`MBeanServerConnection\`, and execute calls through that connection.

## 2. Why Must the Test Environment Be Isolated?

Remote JMX can inspect JVM details and invoke management operations, many of which can mutate application state. A careless test can:

- Bind a connector on all network interfaces instead of loopback only.
- Use a fixed port already occupied by another service.
- Accidentally connect to a real endpoint via URLs taken from the environment.
- Affect the test JVM's platform \`MBeanServer\` and pollute suite state.
- Leave an RMI registry or open socket lingering after the test.
- Configure unauthenticated access in an environment reachable by other hosts.
- Execute side-effecting JMX operations against a shared service.

**Isolation principle:** the test creates its own server, creates an endpoint used only within the fixture, registers only test MBeans, connects only to the address generated by the fixture, and closes all resources in \`finally\` or a teardown hook.

Prefer loopback \`127.0.0.1\` and dynamic ports; never use production addresses or another system's DNS. When real multi-host/TLS testing is required, use a test environment with isolated network policies and dedicated credentials.

## 3. Testing Levels to Distinguish

| Level | Client/Server | What It Verifies | Limitations |
| --- | --- | --- | --- |
| MBean unit test | Same Java object | Business behavior and manually built metadata | Does not test JMX registry/transport |
| Local JMX integration test | \`MBeanServer\` in same JVM | Registration, attributes, operations | Does not test connector |
| Remote connector integration test | \`JMXConnector\` + \`MBeanServerConnection\` | Protocol, serialization, lookup, remote invocation | Same-JVM setup does not cover process isolation |
| Two-JVM integration test | Client and server in separate JVMs | Network stack, lifecycle/process boundary, JVM properties | Requires strict orchestration/teardown |
| Security/production-like test | TLS, authentication, firewall/container networking | Real security configuration and routing | Heavy, environment-dependent |

This lesson starts with testing an RMI remote connector over loopback, then expands to a two-process client/server test. This balances test speed and confidence.

## 4. Preparing a Simple Standard MBean

Use an MBean that depends on no database, network, or external system.

**RemoteProbeMBean.java**

\`\`\`java
package com.example.jmx;

public interface RemoteProbeMBean {
    String getStatus();
    long getInvocationCount();
    String ping(String message);
}
\`\`\`

**RemoteProbe.java**

\`\`\`java
package com.example.jmx;

import java.util.concurrent.atomic.AtomicLong;

public final class RemoteProbe implements RemoteProbeMBean {
    private final AtomicLong invocations = new AtomicLong();

    @Override
    public String getStatus() {
        return "READY";
    }

    @Override
    public long getInvocationCount() {
        return invocations.get();
    }

    @Override
    public String ping(String message) {
        invocations.incrementAndGet();
        return "PONG:" + message;
    }
}
\`\`\`

This is a Standard MBean: implementation \`RemoteProbe\` implements interface \`RemoteProbeMBean\`, following JMX convention. Once registered, attributes \`Status\` and \`InvocationCount\` and operation \`ping(java.lang.String)\` can be invoked through \`MBeanServer\`.

In transport tests, \`ping\` is an operation with a small, controlled side effect: incrementing an in-memory counter. Never use methods that delete data, trigger external jobs, or call production APIs.

## 5. Minimal Fixture: Using JMXConnectorServer with a Direct RMI URL

RMI connectors support multiple service URL forms. One form used to start a connector and obtain a connectable address is:

\`\`\`java
new JMXServiceURL("service:jmx:rmi://127.0.0.1:0");
\`\`\`

However, how the server selects/binds sockets and which address is advertised to clients also depends on the RMI provider and \`java.rmi.server.hostname\`. For tests that must guarantee no non-loopback interface is opened, configure an \`RMIServerSocketFactory\` bound only to loopback or use a test-managed RMI registry with matching socket factories. **Merely writing a loopback host in the URL does not prove all RMI sockets bound to loopback.**

The Java fixture below illustrates a connector without an external RMI registry:

\`\`\`java
package com.example.jmx;

import java.net.InetAddress;
import java.net.ServerSocket;
import java.rmi.server.RMIClientSocketFactory;
import java.rmi.server.RMIServerSocketFactory;
import java.util.HashMap;
import java.util.Map;

import javax.management.MBeanServer;
import javax.management.MBeanServerFactory;
import javax.management.remote.JMXConnectorServer;
import javax.management.remote.JMXConnectorServerFactory;
import javax.management.remote.JMXServiceURL;
import javax.management.remote.rmi.RMIConnectorServer;

public final class IsolatedJmxServer implements AutoCloseable {

    private final MBeanServer mBeanServer;
    private final JMXConnectorServer connector;
    private final JMXServiceURL address;

    public IsolatedJmxServer() throws Exception {
        this.mBeanServer =
                MBeanServerFactory.createMBeanServer("test.remote");

        RMIServerSocketFactory serverFactory = (port) ->
                new ServerSocket(
                        port, 0,
                        InetAddress.getByName("127.0.0.1"));

        RMIClientSocketFactory clientFactory = null;

        Map<String, Object> env = new HashMap<>();
        env.put(RMIConnectorServer.RMI_SERVER_SOCKET_FACTORY_ATTRIBUTE,
                serverFactory);
        if (clientFactory != null) {
            env.put(RMIConnectorServer.RMI_CLIENT_SOCKET_FACTORY_ATTRIBUTE,
                    clientFactory);
        }

        JMXServiceURL requested =
                new JMXServiceURL("service:jmx:rmi://127.0.0.1:0");

        connector = JMXConnectorServerFactory.newJMXConnectorServer(
                requested, env, mBeanServer);
        connector.start();
        address = connector.getAddress();
    }

    public MBeanServer server() {
        return mBeanServer;
    }

    public JMXServiceURL address() {
        return address;
    }

    @Override
    public void close() throws Exception {
        try {
            connector.stop();
        } finally {
            MBeanServerFactory.releaseMBeanServer(mBeanServer);
        }
    }
}
\`\`\`

This skeleton illustrates creating an isolated server and connector. When implementing it, note that **RMI socket factories may require a serializable implementation** to work properly when stubs are sent to clients, and how the JDK/provider handles \`RMI_SERVER_SOCKET_FACTORY_ATTRIBUTE\` must be verified in your test environment. Capturing lambdas and custom socket factories should not be assumed portable across all JDKs. A \`Serializable\` factory class and explicit hostname configuration are generally more suitable for two-JVM tests.

For real CI tests, the easiest setup to control is a standard configuration verified on the target JDK, with fixture-scoped registry/connector ports allocated dynamically by orchestration rather than using "find free port, close socket, then rebind" if you need to avoid races.

## 6. A Practical Variant: RMI Registry on a Test Port

Common JMX/RMI URL:

\`\`\`text
service:jmx:rmi:///jndi/rmi://127.0.0.1:PORT/jmxrmi
\`\`\`

In this model:

1. The test creates an RMI registry on loopback and the chosen port.
2. The test creates a dedicated \`MBeanServer\`.
3. The test creates a \`JMXConnectorServer\` with a JNDI lookup URL via the registry.
4. The server binds the stub under \`jmxrmi\`.
5. The client uses the same URL to look up the stub and connect.

With RMI, there can be **two ports**: the registry port and the exported remote object port. Restricting only the registry port still lets the RMI server open a random second port. In CI environments with firewalls or container networks, this causes "lookup succeeds but invoke fails".

Tests should therefore design clear network boundaries, bind both host and port of the exported object, or use a direct connector URL from the server to eliminate the registry in minimal transport tests.

In Docker or Kubernetes, the address advertised by the RMI stub must be reachable from the client. \`127.0.0.1\` inside the server container is **not** the client container's loopback. For two-container tests, use an isolated network and appropriate reachable hostnames within the test network.

## 7. Registering the MBean and Executing the Remote Client Test

With \`IsolatedJmxServer\`, the test can register the MBean directly on the private server and then connect through the connector:

\`\`\`java
package com.example.jmx;

import javax.management.ObjectName;
import javax.management.remote.JMXConnector;
import javax.management.remote.JMXConnectorFactory;
import javax.management.MBeanServerConnection;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class RemoteConnectorIntegrationTest {

    @Test
    void remoteClientReadsAttributeAndInvokesOperation()
            throws Exception {

        try (IsolatedJmxServer fixture =
                new IsolatedJmxServer()) {

            ObjectName name = new ObjectName(
                    "test.remote:type=RemoteProbe,name=primary");

            fixture.server().registerMBean(
                    new RemoteProbe(), name);

            try (JMXConnector client =
                    JMXConnectorFactory.connect(
                            fixture.address())) {

                MBeanServerConnection connection =
                        client.getMBeanServerConnection();

                assertTrue(connection.isRegistered(name));
                assertEquals("READY",
                        connection.getAttribute(name, "Status"));

                Object result = connection.invoke(
                        name,
                        "ping",
                        new Object[]{"hello"},
                        new String[]{"java.lang.String"});

                assertEquals("PONG:hello", result);
                assertEquals(1L,
                        connection.getAttribute(
                                name, "InvocationCount"));
            }
        }
    }
}
\`\`\`

**Key check:** all client \`isRegistered\`, \`getAttribute\`, and \`invoke\` calls go through \`MBeanServerConnection\`, never touching \`fixture.server()\` directly (except during setup). That guarantees the test truly traverses the remote JMX transport.

For stability, the fixture must return a service URL connectable under the specific connector configuration. In the direct \`service:jmx:rmi://...\` form, the URL returned by \`getAddress()\` may contain an encoded stub; use it rather than guessing ports/URLs after \`start()\`.

## 8. Wiring Spring MBeanExporter into the Remote Connector Test

If the goal is testing the full path **Spring bean → MBeanExporter → MBeanServer → JMXConnectorServer → remote client**, replace manual \`registerMBean\` with a Spring-managed \`MBeanExporter\`.

**SpringJmxTestConfiguration.java**

\`\`\`java
package com.example.jmx;

import java.util.Map;
import javax.management.MBeanServer;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jmx.export.MBeanExporter;

@Configuration
public class SpringJmxTestConfiguration {

    @Bean
    public RemoteProbe remoteProbe() {
        return new RemoteProbe();
    }

    @Bean
    public MBeanExporter testExporter(
            RemoteProbe remoteProbe,
            MBeanServer testMBeanServer) {

        MBeanExporter exporter = new MBeanExporter();
        exporter.setServer(testMBeanServer);
        exporter.setBeans(Map.of(
                "test.remote:type=RemoteProbe,name=primary",
                remoteProbe));
        return exporter;
    }
}
\`\`\`

The test must provide the fixture-created \`testMBeanServer\` to the context before refresh, for example:

\`\`\`java
try (IsolatedJmxServer fixture = new IsolatedJmxServer()) {
    var context = new AnnotationConfigApplicationContext();
    context.registerBean(
            "testMBeanServer",
            MBeanServer.class,
            fixture::server);
    context.register(SpringJmxTestConfiguration.class);
    context.refresh();

    try {
        // Connect client via fixture.address() and run assertions.
    } finally {
        context.close();
    }
}
\`\`\`

With this design:

- \`MBeanExporter\` registers only into the test-supplied \`testMBeanServer\`.
- \`JMXConnectorServer\` attaches to that exact same server.
- There is no reason to touch the JUnit process's platform MBeanServer.
- When the context closes, the exporter unregisters its MBeans.
- When the fixture closes, the connector stops and the server is released.

The teardown order should match: **close client → close Spring context/exporter → stop connector → release MBeanServer**.

## 9. Assertions on Lifecycle and Cleanup

A thorough test verifies not only successful connection, but also that resources are cleaned up:

\`\`\`text
Before:
  server created
  connector started
  MBean registered
  client connected

During:
  remote read/invoke returns expected result

After:
  client.close()
  ApplicationContext.close() -> exporter unregister
  connector.stop()
  MBeanServerFactory.releaseMBeanServer()
\`\`\`

You can hold a reference to the server to confirm the MBean was unregistered after \`context.close()\` before the fixture releases the server:

\`\`\`java
ObjectName name = new ObjectName(
        "test.remote:type=RemoteProbe,name=primary");

assertTrue(fixture.server().isRegistered(name));

context.close();

assertFalse(fixture.server().isRegistered(name));
\`\`\`

Do not use \`Thread.sleep\` to "wait for cleanup" if closing is synchronous and directly assertable. In cases with asynchronous connector start/stop or connection retries, use polling with a finite deadline and a clear failure message.

Tests should not try reconnecting after stopping the connector merely to prove the port closed if another service could immediately reuse that port. Inspect connector state or lifecycle contracts instead, and rely on subsequent tests to catch leaks.

## 10. Using Two JVMs for Stronger Isolation

Same-JVM tests exercise the JMX remote connector layer, yet still have limitations:

- Java static state could accidentally be shared.
- Classloaders and system properties are shared.
- Same-process clients do not reproduce full firewall/network behavior.
- A miswritten test could look up the server directly.

When you need certainty across a process boundary, run the server in a child JVM:

\`\`\`text
JUnit JVM (parent)
     |
     +-- starts ProcessBuilder
     |      |
     |      +-- Child JVM
     |              +-- isolated MBeanServer
     |              +-- JMXConnectorServer
     |              +-- RemoteProbe MBean
     |              +-- prints READY + service URL
     |
     +-- JMXConnectorFactory.connect(service URL)
     +-- remote assertions
     +-- requests child shutdown
     +-- waits for exit with timeout
     +-- destroyForcibly if needed
\`\`\`

With \`ProcessBuilder\`, never pass passwords or secrets via command-line arguments if a safer channel exists, as process lists or logs may expose them. Tests should capture stdout/stderr for diagnostics while bounding output and avoiding logging secrets.

A reliable workflow:

1. Start the child JVM with a deterministic classpath and test fixture.
2. Child binds the connector to loopback and picks an available port.
3. Child prints a machine-readable readiness record, e.g. \`READY|serviceUrl\`.
4. Parent reads readiness with a finite timeout.
5. Parent connects and runs assertions.
6. Parent sends a shutdown signal over stdin or a dedicated test channel.
7. Parent waits for process exit with a deadline; if exceeded, destroys the process.
8. Clean up temporary files/directories and test artifacts.

Important: \`ProcessBuilder\` does not enforce a startup timeout automatically. Waiting indefinitely on \`readLine()\` can hang the entire CI job. Use an asynchronous stream reader or an explicit deadline.

## 11. Authentication Configuration: Test vs. Production

An unauthenticated remote JMX connector on loopback can be fine for a **short-lived test fixture**, but is unsuitable as a default on broader networks.

In production or dedicated security tests, consider:

- Authentication via credentials or an appropriate provider mechanism.
- Authorization/role restrictions limiting administrative operations.
- TLS/SSL to protect the transport.
- Restricting bind interfaces and network ingress.
- Credential lifetimes and rotation.
- Auditing side-effecting administrative invocations.

With an RMI connector, authentication can be configured via environment/server provider attributes such as \`jmx.remote.authenticator\`, though exact behavior and setup depend on the JDK/provider. When testing authentication, use dummy credentials in an isolated environment—never embed real credentials in source code or CI logs.

If using the Java management agent via JVM flags such as \`com.sun.management.jmxremote.*\`, that is a different configuration path from creating a \`JMXConnectorServer\` in code. Flags and port behaviors can vary by JDK version. Do not mix the two paths without clearly identifying which endpoint is being tested.

## 12. Negative Tests for Authentication and Authorization

A security suite may include:

| Case | Expected Outcome |
| --- | --- |
| Valid credentials | Connects and reads \`Status\` successfully |
| Wrong credentials | Connection/authentication rejected |
| Missing credentials when required by server | Connection fails |
| Read-only user | Reads attributes successfully; invoke rejected if disallowed |
| TLS client missing proper trust material | Handshake fails |
| Loopback-bound endpoint | External host cannot connect directly |

These assertions are meaningful only when the fixture actually enables the corresponding security mechanism. You cannot test "missing credentials are rejected" on a connector whose test config does not require authentication.

For TLS and role-based access, create a dedicated fixture with securely managed test certificates/keystores—never production material. Avoid logging passwords, private keys, or the full authentication environment.

## 13. Testing Timeouts and Connection Failures

Remote calls can stall or drop. Test cases should cover:

1. Server not started yet: client connect fails cleanly.
2. Server still starting: bounded readiness timeout.
3. Server stops mid-request: client reports exception and cleans up.
4. Client closes connector: subsequent calls on the connection must not be assumed valid.
5. RMI registry reachable but remote object port unreachable: lookup may succeed while invocation fails.
6. Network or serialization error: corresponding exception received.
7. Long-running server-side operation: client must not blindly retry without knowing the outcome.

**Transport timeout does not equal operation execution timeout.** Even when the client stops waiting, the server-side operation may keep running. For operations with side effects, design request IDs, idempotency keys, or queryable state to avoid unsafe retries.

There is no single portable timeout property across all \`JMXConnector\` implementations. Some RMI transport settings are provider- or JDK-specific. Tests should explicitly target the project's provider and version rather than relying on an unguaranteed property key.

## 14. Standardizing Service URLs and Advertised Hostnames

JMX over RMI commonly trips people up at two layers:

**Layer 1 — registry lookup.** The client connects to \`rmi://host:port/jmxrmi\` to obtain the stub.

**Layer 2 — remote object invocation.** The stub may point to a different host/port. If that address is an unresolvable hostname or unreachable interface, lookup succeeds while MBean operations fail.

For example, a container might declare:

\`\`\`text
JMX URL:
  service:jmx:rmi:///jndi/rmi://test-jmx:9010/jmxrmi
\`\`\`

yet the RMI stub advertises \`127.0.0.1\` or the server container's internal hostname. A client in another container cannot reach the remote object.

In two-JVM tests on the same host, loopback and advertised host \`127.0.0.1\` are usually fine. With two containers on a test network, use a hostname/IP reachable from the client container and configure an isolated network; do not set \`127.0.0.1\` in a way that causes the client to point at itself.

Each test should log **secret-free** diagnostics: service URL, advertised hostname, registry port, connector port, and JVM identity.

## 15. Common Errors and How to Handle Them

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| \`ConnectException: Connection refused\` | Server not started, wrong port, or socket closed | Check readiness and bind |
| \`NameNotFoundException: jmxrmi\` | Registry has not bound the expected name | Check JNDI URL and lifecycle |
| Lookup succeeds but invoke fails | Stub advertises unreachable host/port | Check RMI remote object endpoint |
| \`InstanceNotFoundException\` | Wrong \`ObjectName\`, exporter did not register MBean | Check registry on the right server |
| \`NotCompliantMBeanException\` | Class/interface violates JMX Standard MBean rules | Check \`RemoteProbeMBean\` |
| \`SecurityException\` | Invalid credentials or permissions | Check fixture auth and roles |
| SSL handshake error | Mismatched truststore/keystore or protocol | Use aligned test certificates and config |
| Passes locally, fails in CI | Port collision, firewall, or hostname | Use isolated test ports and readiness timeout |
| Fails when run in parallel | Fixtures share port or \`ObjectName\` on shared server | Give each fixture its own server and endpoint |
| Test JVM hangs on exit | Unclosed RMI thread, connector, registry, or executor | Close client/connector and manage registry lifecycle |
| Client sees wrong data | Connected to wrong JVM or stale MBean | Check URL, PID, identity attribute |
| Operation never returns | Server-side method blocked | Design business deadline/timeout, avoid blind retries |

Diagnose errors in order: **endpoint → connection → registry → ObjectName → metadata → method invocation**, rather than immediately tweaking Spring annotations.

## 16. Testing Serialization and Parameter Types

Remote JMX transfers data across the connector. Primitives, wrappers, \`String\`, and standard JMX types are generally more reliable than custom POJOs with classpath dependencies.

An operation test:

\`\`\`java
Object result = connection.invoke(
        name,
        "ping",
        new Object[]{"hello"},
        new String[]{"java.lang.String"});
\`\`\`

The signature must match the parameter types declared in the MBean management interface. For \`ping(String)\`, use \`"java.lang.String"\`.

If a Standard MBean returns a custom object, the remote client may need that class on its classpath and the object must satisfy transport serialization rules. With MXBeans, Java defines Open Type mappings such as \`CompositeData\` and \`TabularData\`; therefore remote management interfaces often favor MXBean-compatible or simple types.

Do not assume an arbitrary \`Map\` or DTO always crosses JMX/RMI cleanly. Tests should cover the actual data shapes external clients will use.

## 17. Testing Remote Notifications

Beyond reads and invokes, JMX supports notification listeners:

\`\`\`java
connection.addNotificationListener(
        name,
        listener,
        filter,
        handback);
\`\`\`

If the MBean implements \`NotificationBroadcaster\`, a remote client can register a listener and receive callbacks. This is a deeper end-to-end check because it exercises the server-to-client notification path and subscription state management.

Tests should:

1. Register the listener.
2. Trigger a test notification.
3. Await the callback via \`CountDownLatch\` with a finite deadline.
4. Assert matching notification type/sequence/userData.
5. Remove the listener via \`removeNotificationListener\`.
6. Close the connector.
7. Trigger another event if the broadcaster survives, and verify the listener was removed per the test contract.

Never use \`Thread.sleep\` as proof that a callback definitely arrived or did not arrive. When testing **no further notifications received**, use proper synchronization and reasonable bounds, avoiding timing-only negative tests when registry/listener lifecycle can be verified directly.

## 18. Spring Configuration for a Remote Connector with Explicit Lifecycle

If the Spring context owns the connector, you can declare a \`@Bean\` with init/destroy lifecycle:

\`\`\`java
@Configuration
public class RemoteConnectorConfiguration {

    @Bean(destroyMethod = "stop")
    public JMXConnectorServer remoteConnectorServer(
            MBeanServer mBeanServer) throws Exception {

        Map<String, Object> env = /* test-only environment */ Map.of();
        JMXServiceURL url = new JMXServiceURL(
                "service:jmx:rmi://127.0.0.1:0");

        JMXConnectorServer connector =
                JMXConnectorServerFactory.newJMXConnectorServer(
                        url, env, mBeanServer);

        connector.start();
        return connector;
    }
}
\`\`\`

This is a conceptual configuration example; real usage requires a verified loopback RMI setup like in the fixture. Because the connector starts inside the factory method, if \`start()\` throws, Spring will not invoke destroy on an unreturned bean; ensure cleanup inside catch/finally of the factory method if resources were partially created.

Another design is using \`SmartLifecycle\` for the connector so it starts only once dependencies and exporters are ready. On context shutdown, stop the connector before releasing \`MBeanServer\`, and prevent new remote invocations from hitting already-unregistered MBeans.

The test goal is proving a **deterministically closable** lifecycle that leaves no uncontrolled sockets or threads behind.

## 19. CI Pipelines and Reproducibility

To keep remote connector tests stable in CI:

- Never hardcode a shared port across builds.
- Never depend on a JMX server outside the fixture.
- Never assume the CI runner shares the developer machine's DNS or firewall rules.
- Set finite timeouts on startup, connection, invocation, and shutdown.
- Separate networked tests from pure unit tests when appropriate.
- Log enough to reproduce failures without leaking secrets.
- Clean up processes, sockets, and connectors even when assertions fail.
- Avoid running tests in parallel if they share JVM properties or a global RMI registry.
- Never use unbounded \`Thread.sleep\` or deadline-free polling.
- If tests require TLS/authorization, inject test-only certificates and credentials securely in the pipeline.

A clean organizational pattern is tagging with \`@Tag("integration-jmx-remote")\` in JUnit Jupiter so remote tests can run separately:

\`\`\`java
@Tag("integration-jmx-remote")
@Test
void remoteConnectorIsReachable() throws Exception {
    // Fixture creates server and connector within the test.
}
\`\`\`

Do not turn a remote integration test into a health check against a production endpoint. An isolated environment must control its own inputs and outputs so results stay repeatable.

## 20. Checklist Before Considering a Remote Connector Test Complete

| Area | Verification Question |
| --- | --- |
| Server identity | Did the client connect to the intended JVM/test fixture? |
| Isolation | Is the MBeanServer unshared with other tests? |
| Network | Bound to loopback/isolated network, not exposed publicly? |
| Port | Allocated and managed within the test scope? |
| RMI | Do registry and remote object advertised host/port match? |
| Connector | Did \`JMXConnectorServer.start()\` succeed? |
| Registration | Was the MBean present under the right \`ObjectName\` before client connect? |
| Remote read | Did \`getAttribute\` via connection return the expected value? |
| Remote invoke | Did \`invoke\` execute the right method and return the expected result? |
| Metadata | Did \`getMBeanInfo\` return the expected contract? |
| Security | Are authentication/TLS actually enabled when tested? |

## 21. Practice Exercises

**Exercise 1 — Remote loopback:** create a dedicated \`MBeanServer\`, register \`RemoteProbe\`, start \`JMXConnectorServer\`, and connect with \`JMXConnectorFactory\`. Read \`Status\` and invoke \`ping\`.

**Exercise 2 — Spring exporter:** put \`RemoteProbe\` into \`ApplicationContext\` and use \`MBeanExporter\` instead of manual registration. After closing the context, confirm the MBean is gone from the server before stopping the connector.

**Exercise 3 — Two JVMs:** run the server fixture in a child process and the client from the JUnit JVM; pass the service URL via readiness output. Add a startup timeout and child process cleanup.

**Exercise 4 — Wrong ObjectName:** connect remotely with success, then call \`getAttribute\` on a non-existent MBean name. Explain the difference between a transport error and \`InstanceNotFoundException\`.

**Exercise 5 — RMI hostname:** build an isolated two-container test environment and observe what happens when the stub advertises \`127.0.0.1\` instead of a hostname reachable by the client container. Do not expose endpoints to public networks.

**Exercise 6 — Authentication:** enable a JMX authenticator in a dedicated fixture and test valid/invalid credentials. Confirm tests never log passwords and use TLS when testing over untrusted remote networks.

**Exercise 7 — Notifications:** register a remote \`NotificationListener\`, emit an event, await with \`CountDownLatch\`, then remove the listener and close the connector.

**Exercise 8 — Resource cleanup:** intentionally fail an assertion and verify \`finally\` still stops the connector and releases the server. Re-run the test to confirm no leftover port/registry blocks it.

## Conclusion

Testing **remote connectors in an isolated environment** verifies the real path through \`JMXConnector\` and \`MBeanServerConnection\`, not merely an internal \`MBeanServer\`. With Spring Framework JMX, ensure \`MBeanExporter\` and \`JMXConnectorServer\` use the same server, \`ObjectName\` stays consistent, loopback/test network endpoints remain isolated, authentication/TLS are never assumed without configuration, and teardown is complete. When tests enforce readiness checks, timeouts, attribute/operation assertions, RMI port/hostname management, and clean teardown, you catch remote JMX defects before they cause incidents in operations.
