# Sending Forms and Multipart with BodyInserters and MultipartBodyBuilder

**Module:** Spring Framework – reactive  
**Parent topic:** Sending WebClient Requests

## Learning Objectives

After this lesson, you will be able to:

1. Distinguish URL-encoded forms from multipart/form-data and choose the right format for outgoing data.
2. Use `BodyInserters.fromFormData` to send forms with single or multiple values for the same key.
3. Use `BodyInserters.fromMultipartData` and `MultipartBodyBuilder` to build multipart requests containing text, JSON metadata, and files.
4. Set content type, filename, and custom headers per part; understand why the multipart boundary must be generated by the writer.
5. Choose an appropriate `Resource` for file uploads, recognizing repeatable resources versus single-read publishers.
6. Send parts asynchronously, preserve streaming, and avoid buffering large files on the heap.
7. Handle WebClient responses, 4xx/5xx errors, timeouts, and retries according to request body semantics.
8. Test form and multipart requests using a WebFlux receiver with `WebTestClient`.

## 1. Two Common Form Submission Formats

An HTML form or HTTP client can send data in two common formats:

| Format | Content-Type | Representation | When to use |
| --- | --- | --- | --- |
| URL-encoded form | `application/x-www-form-urlencoded` | Key/value pairs encoded in the body | Forms consisting mostly of simple text, numbers, and selections. |
| Multipart form | `multipart/form-data; boundary=...` | Body split into multiple parts, each with its own headers and content | Forms containing files, JSON metadata, or mixed payload types. |

### 1.1. URL-Encoded Form

Example data:

```text
name=Lan&city=Ha+Noi&tag=java&tag=reactive
```

Each key/value pair is encoded according to URL-encoded form rules. Spaces are typically represented as `+`; special characters are percent-encoded. A key can appear multiple times, such as `tag` in the example above having two values.

This format is compact, easy to process, and fits text-only forms. It does not provide an independent part structure to attach filenames or individual content types per file.

### 1.2. Multipart Form

Multipart splits the body into parts. Each part has its own headers such as `Content-Disposition` and optionally `Content-Type`:

```text
--boundary
Content-Disposition: form-data; name="description"

Monthly report
--boundary
Content-Disposition: form-data; name="metadata"
Content-Type: application/json

{"category":"finance","confidential":true}
--boundary
Content-Disposition: form-data; name="file"; filename="report.txt"
Content-Type: text/plain

...file bytes...
--boundary--
```

`boundary` is the delimiter string generated by the multipart writer and placed in the Content-Type of the overall request. Each part can contain text, JSON, a byte array, or a Resource. Multipart is suitable when an operation needs to send both structured metadata and files.

Do not manually concatenate boundary strings or build a multipart body as a string. Spring's writer is responsible for escaping headers, encoding parts, adding boundaries, and terminating the body properly.

## 2. Where Does BodyInserters Fit in WebClient?

`WebClient` builds requests with a fluent API. When a body is needed, `RequestBodySpec` can accept an object via `bodyValue` or a `BodyInserter` via `body`.

`BodyInserters` provides factory methods to create inserters by body format:

- `fromValue(object)`: serializes a regular object using the appropriate codec.
- `fromPublisher(publisher, elementClass)`: writes data from a publisher.
- `fromFormData(key, value)` or `fromFormData(multiValueMap)`: creates a URL-encoded form.
- `fromMultipartData(key, value)` or `fromMultipartData(multiValueMap)`: creates a multipart body.

Example of a URL-encoded request:

```java
webClient.post()
        .uri("/registrations")
        .body(BodyInserters.fromFormData("name", "Lan")
                .with("city", "Ha Noi"))
        .retrieve()
        .bodyToMono(RegistrationResult.class);
```

`BodyInserters.fromFormData` returns a form inserter. Call `with` to add another field; call `with` multiple times with the same key to send multiple values for that key.

There is no need to manually serialize the form into a string and pass it to `bodyValue`. The form inserter selects the corresponding writer and sets the appropriate media type.

## 3. Sending URL-Encoded Forms with BodyInserters

### 3.1. Form with a Few Fields

Example:

```java
Mono<RegistrationResult> result = webClient.post()
        .uri("/registrations")
        .contentType(MediaType.APPLICATION_FORM_URLENCODED)
        .body(BodyInserters.fromFormData("name", "Lan")
                .with("email", "lan@example.com")
                .with("city", "Ha Noi"))
        .retrieve()
        .bodyToMono(RegistrationResult.class);
```

`contentType` can explicitly declare the desired format. The form inserter also knows how to write URL-encoded forms. When using a form inserter, do not call `URLEncoder` manually per field; the writer handles encoding.

### 3.2. Sending Multiple Values for the Same Key

HTML checkboxes, multi-selects, or certain APIs can accept one key with multiple values. Call `with` multiple times:

```java
BodyInserters.FormInserter<String> form =
        BodyInserters.fromFormData("name", "Lan")
                .with("tag", "java")
                .with("tag", "spring")
                .with("tag", "reactive");

Mono<RegistrationResult> result = webClient.post()
        .uri("/registrations")
        .body(form)
        .retrieve()
        .bodyToMono(RegistrationResult.class);
```

The server receives three values for the `tag` key. Do not join them into a comma-separated string if the server contract expects repeated values; commas can be valid data inside a value.

### 3.3. Using MultiValueMap

When form fields are already in a data structure, use `MultiValueMap<String, String>`:

```java
MultiValueMap<String, String> fields = new LinkedMultiValueMap<>();
fields.add("name", "Lan");
fields.add("tag", "java");
fields.add("tag", "reactive");

Mono<RegistrationResult> result = webClient.post()
        .uri("/registrations")
        .body(BodyInserters.fromFormData(fields))
        .retrieve()
        .bodyToMono(RegistrationResult.class);
```

`LinkedMultiValueMap` holds multiple values per key. The `add` method appends a value; `set` replaces existing values with a single value.

### 3.4. When Not to Use URL-Encoded?

Do not choose URL-encoded if you need to send binary files or each field needs its own content type. While a file could be Base64-encoded in a text field, doing so inflates the payload, adds encode/decode overhead, and often forces the server to hold a large string in memory. For file uploads, multipart or a dedicated streaming protocol is more appropriate.

## 4. Sending Multipart with BodyInserters.fromMultipartData

A multipart inserter can be created directly from key/value pairs:

```java
Mono<UploadReceipt> result = webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData("description", "Monthly report")
                .with("category", "finance")
                .with("file", resource))
        .retrieve()
        .bodyToMono(UploadReceipt.class);
```

This works well for simple multipart payloads. When more per-part configuration is needed—such as JSON metadata, filenames, or custom content types—`MultipartBodyBuilder` is easier to read and extend.

## 5. MultipartBodyBuilder: Building Each Part

`MultipartBodyBuilder` produces a `MultiValueMap<String, HttpEntity<?>>`. Each part can have its own body and headers.

Example:

```java
MultipartBodyBuilder builder = new MultipartBodyBuilder();

builder.part("description", "Monthly report");

builder.part("metadata", new UploadMetadata("finance", true))
        .contentType(MediaType.APPLICATION_JSON);

builder.part("file", resource)
        .filename("report.txt")
        .contentType(MediaType.TEXT_PLAIN);

MultiValueMap<String, HttpEntity<?>> parts = builder.build();

Mono<UploadReceipt> result = webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData(parts))
        .retrieve()
        .bodyToMono(UploadReceipt.class);
```

Here:

- `description` is a text part.
- `metadata` is an object serialized to JSON because the part has content type `application/json`.
- `file` is a Resource; the part has its own filename and media type.
- `build()` creates the map used as input for the multipart inserter.

Each part can be configured using methods on the builder returned by `part`:

| Method | Meaning |
| --- | --- |
| `contentType(MediaType)` | Sets the Content-Type for the part. |
| `filename(String)` | Sets the filename in Content-Disposition. |
| `header(name, value)` | Adds a custom header to the part. |
| `headers(Consumer<HttpHeaders>)` | Modifies the part's headers. |

Field names must match the server contract. For example, if the server expects `@RequestPart("metadata")`, the client must send a part named `metadata`; changing it to `meta` causes the server not to find the part.

### 5.1. JSON Part

When sending a metadata object, declare the content type explicitly:

```java
builder.part("metadata", new UploadMetadata("finance", true))
        .contentType(MediaType.APPLICATION_JSON);
```

The JSON codec will serialize the object into a JSON part. If the server expects a plain text string instead of a JSON object, send a string with the corresponding content type. Do not assume all parts default to text/plain.

If a part needs custom headers or disposition control, use `headers`/`header` on PartBuilder. Only add headers that the server contract actually requires.

### 5.2. Filename and Content-Disposition

A file part typically has headers like:

```http
Content-Disposition: form-data; name="file"; filename="report.txt"
Content-Type: text/plain
```

Filename is client-supplied metadata. The server must never treat the filename as a trusted file-saving path. When storing files, generate a server-controlled destination name, sanitize or strip path components, check permissions, and enforce size limits. Never concatenate a client-supplied filename directly into a filesystem path.

### 5.3. Writer-Generated Boundary

A multipart request has a request-level Content-Type such as:

```text
Content-Type: multipart/form-data; boundary=generated-boundary
```

Each part is separated by that boundary. With `BodyInserters.fromMultipartData` and `MultipartBodyBuilder`, Spring's multipart writer is responsible for generating the boundary and writing the appropriate header.

Do not set one boundary in the header while writing the body with another boundary. Do not manually set `Content-Length` if the exact serialized byte count is unknown. With a Resource or streaming publisher, the length may be unknown beforehand and the transport can use an appropriate transfer mechanism.

Normally, let the multipart writer set Content-Type and the boundary automatically. If there is a reason to set the media type, set only `MediaType.MULTIPART_FORM_DATA` and let the writer append the boundary; do not invent boundary values yourself.

## 6. Choosing a Resource for File Uploads

`Resource` is Spring's abstraction for data such as files, classpath resources, or byte arrays. Common choices:

| Resource | Data source | Notes |
| --- | --- | --- |
| `FileSystemResource` | File on the filesystem | Suitable for re-openable files; usually knows filename and may know content length. |
| `ClassPathResource` | File on the classpath | Suitable for sample files/assets bundled with the application. |
| `ByteArrayResource` | In-memory byte array | Easy to test and repeatable; entire payload already resides on the heap. |
| `InputStreamResource` | InputStream | Usually single-read only; retries or re-writing the body may fail. |

Filesystem file example:

```java
Resource file = new FileSystemResource("/data/reports/report.pdf");

MultipartBodyBuilder builder = new MultipartBodyBuilder();
builder.part("file", file)
        .filename("report.pdf")
        .contentType(MediaType.APPLICATION_PDF);
```

Byte array example in tests:

```java
Resource file = new ByteArrayResource(
        "hello multipart".getBytes(StandardCharsets.UTF_8)) {
    @Override
    public String getFilename() {
        return "hello.txt";
    }
};
```

`ByteArrayResource` does not necessarily have a suitable filename by default for uploads. You can override `getFilename()` or call `filename` on the part builder.

### 6.1. Repeatability and Retries

WebClient can retry requests on transient failures, but the upload body must be capable of being recreated. `FileSystemResource` can usually reopen the file. `ByteArrayResource` can be re-read because the data lives in a byte array. `InputStreamResource` is typically backed by an already-consumed stream and cannot be replayed.

Do not blindly retry a multipart upload. Consider:

- Can the body publisher be resubscribed to?
- Can the Resource be reopened from the beginning?
- Did the server already receive and process the request before the connection dropped?
- Does the endpoint support an idempotency key or duplicate-upload detection?

A client-side timeout does not prove the server did not save the file. For resource-creating operations, retries can create duplicate records or files if the API lacks an idempotency mechanism.

## 7. Sending Parts Asynchronously and Streaming

`MultipartBodyBuilder` also supports `asyncPart` to send content from a Publisher. This is the option when part data comes from a stream rather than an existing object:

```java
Flux<DataBuffer> fileContent = dataBufferPublisher;

MultipartBodyBuilder builder = new MultipartBodyBuilder();
builder.part("description", "Streaming upload");

builder.asyncPart("file", fileContent, DataBuffer.class)
        .filename("stream.bin")
        .contentType(MediaType.APPLICATION_OCTET_STREAM);

Mono<UploadReceipt> result = webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData(builder.build()))
        .retrieve()
        .bodyToMono(UploadReceipt.class);
```

This is an **illustrative snippet**; `dataBufferPublisher` must supply buffers with a valid lifecycle. The publisher should only be consumed by the subscription managed by WebClient. Do not call `subscribe()` separately to push the file into the request.

When working directly with `DataBuffer`:

- Do not retain pooled buffers after the publisher has transferred ownership.
- Do not release a buffer before the writer finishes reading it.
- If creating replacement buffers, clarify which component releases the old and new buffers.
- Propagate errors and cancellation from the data source to the request.
- Bound the source's rate and memory; do not collect the entire stream into a `byte[]` just to build a multipart request.

For large files, use a Resource or appropriate streaming publisher and test with files near realistic limits. Never use `ByteArrayResource` for multi-gigabyte files because it requires the payload to live on the heap.

## 8. Receiving Multipart on the WebFlux Server Side

Client multipart requests succeed only if the server recognizes the part names and corresponding types. An annotated controller can use `@RequestPart` for regular fields, JSON parts, and file parts:

```java
@PostMapping(
        value = "/uploads",
        consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public Mono<UploadReceipt> upload(
        @RequestPart("description") String description,
        @RequestPart("metadata") UploadMetadata metadata,
        @RequestPart("file") FilePart file) {

    return Mono.just(new UploadReceipt(
            description,
            metadata.category(),
            file.filename(),
            0L));
}
```

`@RequestPart` uses the appropriate message reader to decode each part. JSON parts need a matching content type so the JSON codec selects the right reader. File parts are represented by `FilePart`, which exposes filename, headers, and a content publisher.

If you want to save the file, use `FilePart.transferTo(destination)` or stream to a storage service. Construct the destination path from a server-generated ID/name; do not trust the client-sent path. Conceptual example:

```java
Path destination = uploadDirectory.resolve(serverGeneratedName);

return file.transferTo(destination)
        .thenReturn(new UploadReceipt(
                description,
                metadata.category(),
                serverGeneratedName,
                knownSize));
```

This is an **illustrative snippet**; `uploadDirectory` must be a configured directory, `serverGeneratedName` must be safely generated, and `knownSize` must be determined appropriately. In practice, validate size, permissions, file type, filename, antivirus/scanning where appropriate, and clean up partial files if transfer fails.

### 8.1. Receiving URL-Encoded Forms

For text forms, a controller can accept `MultiValueMap<String, String>`:

```java
@PostMapping(
        value = "/registrations",
        consumes = MediaType.APPLICATION_FORM_URLENCODED_VALUE)
public Mono<RegistrationResult> register(
        @RequestBody MultiValueMap<String, String> form) {

    return Mono.just(new RegistrationResult(
            form.getFirst("name"),
            form.getOrDefault("tag", List.of())));
}
```

`getFirst` retrieves the first value; `get("tag")` can hold multiple values. Check required fields and validate data on the server. Clients can send arbitrary payloads, so never treat a properly serialized form as proof of valid data.

## 9. Handling Responses and Errors from WebClient

Successfully sending a body does not mean the server accepted the business operation. Read the status and response body according to the contract.

### 9.1. retrieve() and 4xx/5xx Errors

`retrieve()` converts 4xx/5xx responses into `WebClientResponseException` by default if no status handler is configured:

```java
Mono<UploadReceipt> result = webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData(builder.build()))
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError, response ->
                response.bodyToMono(String.class)
                        .defaultIfEmpty("Upload rejected")
                        .map(UploadRejectedException::new))
        .onStatus(HttpStatusCode::is5xxServerError, response ->
                Mono.error(new UploadServiceException(
                        "Upload service failed")))
        .bodyToMono(UploadReceipt.class);
```

This is an **illustrative snippet**; exception constructors and error DTOs are application-defined. The 4xx handler can read the response body to construct a business exception; the 5xx handler can mask internal details behind a stable error. If custom mapping is not needed, keep the default and handle `WebClientResponseException` at the calling layer.

### 9.2. exchangeToMono() When Full Response Control Is Needed

`exchangeToMono` fits when branching on status or headers is needed:

```java
Mono<UploadReceipt> result = webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData(builder.build()))
        .exchangeToMono(response -> {
            if (response.statusCode().is2xxSuccessful()) {
                return response.bodyToMono(UploadReceipt.class);
            }
            return response.createError();
        });
```

After the callback, WebClient manages releasing the response body per the API contract. If reading the body manually, do not overlook error status cases. Only use `exchangeToMono` when full response control is needed; for simple mappings, `retrieve` is shorter.

### 9.3. Timeouts and Retries

You can apply a timeout to the overall operation:

```java
webClient.post()
        .uri("/uploads")
        .body(BodyInserters.fromMultipartData(builder.build()))
        .retrieve()
        .bodyToMono(UploadReceipt.class)
        .timeout(Duration.ofSeconds(30));
```

Timeouts must fit the file size and network speed. A large upload may require a longer timeout or a dedicated idle timeout policy. Do not retry every exception: a 400 validation error will not resolve itself on retry, and a connection error after the server saved the file can cause duplicate uploads. Use bounded retries, backoff, and idempotency when supported by the contract.

### 10.6. UploadController.java

```java
package demo;

import java.util.List;
import org.springframework.core.io.buffer.DataBuffer;
import org.springframework.core.io.buffer.DataBufferUtils;
import org.springframework.http.MediaType;
import org.springframework.http.codec.multipart.FilePart;
import org.springframework.util.MultiValueMap;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestPart;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Mono;

@RestController
public class UploadController {

    @PostMapping(
            value = "/receive/form",
            consumes = MediaType.APPLICATION_FORM_URLENCODED_VALUE)
    public Mono<FormReceipt> receiveForm(
            @RequestBody MultiValueMap<String, String> form) {

        return Mono.just(new FormReceipt(
                form.getFirst("name"),
                form.getOrDefault("tag", List.of())));
    }

    @PostMapping(
            value = "/receive/multipart",
            consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public Mono<UploadReceipt> receiveMultipart(
            @RequestPart("description") String description,
            @RequestPart("metadata") UploadMetadata metadata,
            @RequestPart("file") FilePart file) {

        return file.content()
                .map(buffer -> {
                    long size = buffer.readableByteCount();
                    DataBufferUtils.release(buffer);
                    return size;
                })
                .doOnDiscard(DataBuffer.class, DataBufferUtils::release)
                .reduce(0L, Long::sum)
                .map(bytes -> new UploadReceipt(
                        description,
                        metadata.category(),
                        file.filename(),
                        bytes));
    }
}
```

The receiver reads the form into a MultiValueMap. The multipart endpoint decodes JSON metadata and receives the file as a FilePart. The example counts bytes of the file stream without collecting the entire file into an array; each DataBuffer is released after reading its size metadata. Real file-saving applications should use controlled storage transfer/streaming rather than just counting bytes.

### 10.7. UploadClient.java

```java
package demo;

import java.util.List;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.core.io.ByteArrayResource;
import org.springframework.core.io.Resource;
import org.springframework.http.MediaType;
import org.springframework.http.client.MultipartBodyBuilder;
import org.springframework.stereotype.Component;
import org.springframework.web.reactive.function.BodyInserters;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

@Component
public class UploadClient {
    private final WebClient client;

    public UploadClient(
            WebClient.Builder builder,
            @Value("http://localhost:8080") String receiverBaseUrl) {
        this.client = builder.baseUrl(receiverBaseUrl).build();
    }

    public Mono<FormReceipt> sendForm(String name, List<String> tags) {
        BodyInserters.FormInserter<String> form =
                BodyInserters.fromFormData("name", name);

        tags.forEach(tag -> form.with("tag", tag));

        return client.post()
                .uri("/receive/form")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .body(form)
                .retrieve()
                .bodyToMono(FormReceipt.class);
    }

    public Mono<UploadReceipt> sendMultipart(
            String description,
            UploadMetadata metadata,
            Resource file) {

        MultipartBodyBuilder builder = new MultipartBodyBuilder();

        builder.part("description", description);

        builder.part("metadata", metadata)
                .contentType(MediaType.APPLICATION_JSON);

        builder.part("file", file)
                .filename(file.getFilename() == null
                        ? "upload.bin"
                        : file.getFilename())
                .contentType(MediaType.APPLICATION_OCTET_STREAM);

        return client.post()
                .uri("/receive/multipart")
                .body(BodyInserters.fromMultipartData(builder.build()))
                .retrieve()
                .bodyToMono(UploadReceipt.class);
    }

    public Mono<UploadReceipt> sendSampleMultipart() {
        Resource file = new ByteArrayResource(
                "hello multipart".getBytes(java.nio.charset.StandardCharsets.UTF_8)) {
            @Override
            public String getFilename() {
                return "hello.txt";
            }
        };

        return sendMultipart(
                "Monthly report",
                new UploadMetadata("finance", true),
                file);
    }
}
```

`UploadClient` illustrates both sending approaches. The base URL is configured in the constructor; the example defaults to running the receiver on port 8080. In real environments, load the URL from application configuration and use a Spring-managed WebClient.Builder to preserve connector, filter, TLS, and timeout settings.

```java
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.core.io.ByteArrayResource;
import org.springframework.core.io.Resource;
import org.springframework.web.reactive.function.client.WebClient;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class UploadClientIntegrationTest {
    @LocalServerPort
    int port;

    private UploadClient client;

    @BeforeEach
    void setUp() {
        client = new UploadClient(
                WebClient.builder(),
                "http://localhost:" + port);
    }

    @Test
    void sendsUrlEncodedFormWithRepeatedKeys() {
        FormReceipt result = client.sendForm(
                        "Lan",
                        List.of("java", "reactive"))
                .block(Duration.ofSeconds(5));

        assertThat(result.name()).isEqualTo("Lan");
        assertThat(result.tags()).containsExactly("java", "reactive");
    }

    @Test
    void sendsMultipartTextJsonAndFileParts() {
        Resource file = new ByteArrayResource(
                "hello multipart".getBytes(StandardCharsets.UTF_8)) {
            @Override
            public String getFilename() {
                return "hello.txt";
            }
        };

        UploadReceipt result = client.sendMultipart(
                        "Monthly report",
                        new UploadMetadata("finance", true),
                        file)
                .block(Duration.ofSeconds(5));

        assertThat(result.description()).isEqualTo("Monthly report");
        assertThat(result.category()).isEqualTo("finance");
        assertThat(result.filename()).isEqualTo("hello.txt");
        assertThat(result.bytes()).isEqualTo(15);
    }
}
```

In tests, `block` is only used to wait for the result in the test method. Application code still returns publishers and does not block the event loop. The test starts the server on a random port and creates UploadClient pointing to that port, avoiding dependence on port 8080 being free.

## 11. Size Limits and Protecting File Uploads

Multipart makes it possible to send mixed data types in a single request, but it does not automatically make uploads safe. The server must enforce limits and checks according to contract:

- Limit total request bytes, part count, per-part size, and part headers.
- Configure the multipart reader to decide whether small payloads stay in memory or large payloads spill to disk; monitor disk quota and clean up temporary files.
- Authenticate and authorize before accepting large uploads whenever possible.
- Never trust client-supplied filenames, extensions, or Content-Type. Verify actual content according to business needs.
- Generate storage filenames on the server; prevent path traversal, overwriting other files, and escaping the target directory.
- Consider virus/malware scanning, checksums, per-user/tenant quotas, and retention.
- Use streaming to avoid loading entire files onto the heap; limit concurrent uploads to control disk, memory, and connections.

`spring.codec.max-in-memory-size` can tune buffer limits for certain codecs, but should not be treated as an overall quota for all multipart uploads or every byte passing through the server. Configure multipart readers and transport/proxy limits according to the Spring version in use.

## 12. Common Mistakes and How to Handle Them

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Sending files as URL-encoded text | Payload bloats and streaming becomes difficult | Use multipart or a dedicated upload protocol. |
| Using `bodyValue` with manually concatenated multipart strings | Boundary/headers easily break and data corrupts | Use BodyInserters and MultipartBodyBuilder. |
| Forgetting to match field names with the server | `@RequestPart` fails to find the part | Synchronize part names between client and receiver. |
| Sending metadata object without JSON content type | Server may select the wrong reader | Set `contentType(APPLICATION_JSON)` on the part. |
| Manually setting boundary in Content-Type | Header boundary and body may mismatch | Let the multipart writer generate the boundary. |
| Joining multiple form values into one string | Server does not receive repeated keys per contract | Call `with` multiple times or use MultiValueMap. |
| Using `InputStreamResource` then retrying upload | Stream already consumed; retry has no data | Use a repeatable Resource or create a fresh publisher. |
| Using ByteArrayResource for very large files | Holds the entire file on the heap | Use FileSystemResource or a streaming publisher. |
| Manually subscribing to the file publisher | Body detaches from WebClient request lifecycle | Pass publisher to asyncPart and let WebClient subscribe. |
| Forgetting filename | Server receives part without filename or default name | Set an explicit filename when the contract requires it. |
| Manually setting a wrong Content-Length | Server may under-read or hang waiting for more bytes | Let the writer/transport compute length whenever possible. |
| Retrying uploads without idempotency | Can create duplicate files/records | Use an idempotency key and bounded retries. |
| Ignoring error responses | Loses useful 4xx/5xx diagnostics | Use retrieve/onStatus or exchangeToMono. |
| Using block in reactive services | Blocks the event loop and lowers throughput | Return Mono/Flux; block only at imperative/test boundaries. |
| Trusting client filename or MIME type | Risk of writing dangerous files or wrong locations | Verify content, generate server-side storage names, and enforce upload limits. |
| Collecting entire file into byte array just to count | Memory spikes with file size | Count/stream DataBuffer by DataBuffer or use storage transfer. |

## 13. Self-Check Questions

**Question 1.** When should you use a URL-encoded form?  
**Answer:** When the body consists mainly of simple text fields and does not need per-part metadata or binary files.

**Question 2.** When should you use multipart/form-data?  
**Answer:** When a request requires multiple independent parts, especially files, JSON metadata, and text fields.

**Question 3.** What does `BodyInserters.fromFormData` handle?  
**Answer:** Creates a URL-encoded form inserter, encodes key/value pairs, and supports multiple values for the same key via `with`.

**Question 4.** What is the role of `MultipartBodyBuilder`?  
**Answer:** Builds each part with its own body and headers, then produces a MultiValueMap for the multipart inserter.

**Question 5.** Who generates the multipart boundary?  
**Answer:** Spring's multipart writer when writing the request; never craft boundaries or concatenate multipart bodies manually.

**Question 6.** How do you send a metadata object as a JSON part?  
**Answer:** Use `builder.part("metadata", object).contentType(MediaType.APPLICATION_JSON)`.

**Question 7.** Why can `InputStreamResource` cause issues on retry?  
**Answer:** An InputStream is typically single-read. A retried request body may fail to regenerate the already-consumed data.

**Question 8.** What does `FilePart` on the server represent?  
**Answer:** A file part decoded by the multipart reader, with filename, headers, and a content publisher; it can be moved to storage via transferTo or streaming.

**Question 9.** Does `limitRate` or backpressure replace upload size limits?  
**Answer:** No. Demand counts elements; the server still needs limits on bytes, part count, disk usage, and concurrent uploads.

**Question 10.** Why should you not unconditionally retry uploads after a timeout?  
**Answer:** The server may have already received and saved the file before the client timed out. Retrying can create duplicate records/files if the API lacks idempotency.

## Key Takeaways

- Use `BodyInserters.fromFormData` for URL-encoded text forms; use `fromMultipartData` or `MultipartBodyBuilder` for multipart with multiple parts and files.
- Use `MultipartBodyBuilder.part` to set per-part content type, filename, and headers. JSON metadata requires a JSON content type so the server picks the right codec.
- Let Spring's multipart writer generate the boundary and handle encoding; do not manually assemble bodies or set boundaries.
- Choose `Resource` based on the data source and repeatability. Large files should stream; `InputStreamResource` is generally unsuitable for retries.
- WebClient keeps requests within the reactive lifecycle. Never manually subscribe or block in application code; handle error responses and retries according to the idempotency contract.
- Servers must limit size, part count, and concurrent uploads; never trust client-supplied filenames, extensions, or MIME types.
