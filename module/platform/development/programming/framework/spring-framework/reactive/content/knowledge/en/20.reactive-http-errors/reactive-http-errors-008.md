# Sanitizing Sensitive Information and Preserving Correlation IDs in HTTP Errors with Spring WebFlux

**Module:** Spring Framework - reactive. **Group:** HTTP Errors.

When an API fails, the caller needs a response that is **stable, actionable, and informative enough to request support**; operations needs a trail that can be followed across logs, traces, and services. Those two goals do not mean sending stack traces, hostnames, SQL, tokens, request bodies, or internal exception messages to the client.

This lesson presents the boundary between **public** and **internal** information, how to generate and propagate correlation IDs in WebFlux, how to handle different response timings, and how to test the safety of the error contract. The small examples in sections 1–9 illustrate individual principles; from section 10 onward, we cover selecting error boundaries, a sample project, testing, and operational runbooks.

## 1. Goals and Threat Model

Expected outcomes: select the right HTTP status/error code, construct a safe public error body, attach a searchable correlation ID to responses and logs, preserve context across scheduler switches, verify that no secrets leak, and handle cases where the response has already begun sending.

Treat the following data sources as **untrusted and potentially sensitive**: path/query, cookies, `Authorization`, API keys, usernames, emails, JSON payloads, validation rejected values, exception messages, SQL, JDBC/R2DBC diagnostics, stack traces, raw response bodies from upstreams, and inbound correlation headers sent by clients. Exceptions thrown by libraries can contain this data even when controllers never intentionally log it.

**Invariant rule:** never expose internal information over HTTP merely because it makes debugging convenient. Logging also requires protection policies; logs are not a safe default place to copy entire requests.

## 2. External Error Contract: Status, Code, Detail, Correlation ID

A REST error should include at least: (1) an HTTP status matching the contract; (2) a stable error `code` for machine processing; (3) vetted, localizable `title`/`detail`; (4) a `correlationId` revealing no user information; (5) a consistent media type, such as `application/problem+json` for RFC 9457 Problem Details.

Example public response (illustrative ID value):

~~~http
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json
X-Correlation-ID: 5eafc70a-84e9-46d8-bcc0-034aa5f1f2c4

{"type":"https://api.example.test/problems/internal-error","title":"Internal server error","status":500,"detail":"An unexpected error occurred. Provide the correlation ID to support.","code":"INTERNAL_ERROR","correlationId":"5eafc70a-84e9-46d8-bcc0-034aa5f1f2c4"}
~~~

This example contains **no** exception class name, hostname, SQL, file path, session token, customer information, or raw input. The user provides the correlation ID to support; support uses controlled log/trace access to look up the cause. Do not treat the ID as a password, identity proof, or authorization mechanism.

For 400/422, indicate only allowlisted fields and public rules; do not echo raw rejected values if they might contain secrets. For 401/403, do not reveal whether an internal user or resource exists if anti-enumeration policies require it. For 429/503, `Retry-After` may be used per contract; do not turn infrastructure details into client messages.

## 3. Classification of Allowed Data

| Component | Can Be Returned to Client | Kept Internally Under Control Only |
| --- | --- | --- |
| HTTP status, business error code, safe message | Yes | Yes |
| System-generated correlation ID without PII | Yes | Yes |
| Stack trace, Java package/class, topology, hostname | No | Store only if needed and access-controlled |
| SQL, connection URL, token, cookie, API key | No | Must mask by default; do not log secrets |
| Allowlisted validation field | Conditionally | Yes |
| Rejected value, request body, downstream error body | Not by default | Requires separate policy, data filtering, retention |

**Allowlist beats denylist:** build `ProblemDetail` from a vetted set of fields instead of taking an exception and trying to search-and-replace password strings. Regex redaction is only a supplementary defense layer; it cannot catch every secret pattern.

## 4. Correlation ID Lifecycle and Trust Boundaries

A UUID-formatted `X-Correlation-ID` can be used independently of `traceId`/`spanId` generated by a tracing system. Both IDs can coexist: correlation ID for users/support to reference requests, trace ID for exploring relationships across spans. Never use user IDs, emails, or secret material as a correlation ID.

Logical flow:

~~~text
HTTP request -> gateway (trusted boundary)
             -> WebFilter picks/generates ID
             -> exchange attribute + Reactor Context
             -> handler/service/WebClient
             -> logs/traces with ID
             -> safe response header + error body
~~~

If accepting an external header, establish a clear policy: a trusted gateway can verify format/length and forward it; where no gateway exists, the safest approach is **generating a new UUID in the application**. Never log arbitrary client headers verbatim; attackers can inject newlines, supply oversized IDs, or forge trails.

When propagating across multiple services, configure consistent header transmission and ID replacement policies at trust boundaries. In systems with OpenTelemetry/W3C Trace Context, let tracing instrumentation manage `traceparent`; custom correlation IDs do not replace tracing protocols.

## 5. Passing IDs into WebFlux Without Thread Affinity

`ServerWebExchange` holds the request/response of an HTTP exchange and provides `attributes` suited for middleware data sharing; Reactor `Context` holds metadata per **subscription**, not as a global variable. The same ID can be placed in both locations so appropriate layers can retrieve it.

Illustrative example of a `WebFilter` generating a new ID at the start of a request (standalone snippet, do **not** register alongside `CorrelationIdFilter` in the complete project in section 11):

~~~java
import java.util.UUID;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebFilter;
import org.springframework.web.server.WebFilterChain;
import reactor.core.publisher.Mono;

@Component
public class ExampleCorrelationFilter implements WebFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        String id = UUID.randomUUID().toString();
        exchange.getAttributes().put("correlationId", id);
        exchange.getResponse().getHeaders().set("X-Correlation-ID", id);
        return chain.filter(exchange)
            .contextWrite(ctx -> ctx.put("correlationId", id));
    }
}
~~~

`Mono<Void>` is **returned** to WebFlux without manually calling `subscribe()`. Setting the response header here occurs before the chain executes/commits. Any filter that needs to modify the response later must check `isCommitted()` or use a pre-commit callback; do not try to write headers after bytes have been sent.

In services, you can read `Mono.deferContextual(ctx -> Mono.just(ctx.getOrDefault("correlationId", "unavailable")))` within the same reactive chain. `Context` is not automatically propagated into a detached execution flow spawned by manual `subscribe()` or across every library; check where subscriptions are created and integrate propagators when needed.

## 6. Logging and Redaction in Reactive Environments

Structured logs should include `event`, `correlationId`, `errorCode`, `status`, `exceptionType` (if policy permits), `service`, `durationMs`, and `traceId` when tracing is active. Never include raw bodies, tokens, cookies, JDBC URLs, or unvetted exception messages as default fields. Statements like `log.error("request {}", request)` can accidentally serialize private data.

Example of a safely designed log message:

~~~text
event=http_request_failed correlationId=5eafc70a-84e9-46d8-bcc0-034aa5f1f2c4 errorCode=INTERNAL_ERROR status=500 exceptionType=IllegalStateException
~~~

In the centralized log collector, enforce role-based access, bounded retention, export controls, and secret/PII detection scans. Never allow correlation IDs to bypass log access permissions. If internal stack traces must be recorded, store them in an appropriately protected sink and review contents before writing.

**Note on MDC:** Common MDC relies on `ThreadLocal`; Reactor can switch schedulers or event loops between signals. Do not set MDC once and assume it stays accurate; use Reactor Context and configured context propagation/observability mechanisms, or log `correlationId` explicitly where the data is available. Do not rely on `ThreadLocal` as the sole source of the ID.

## 7. Across WebClient, Gateways, and Dependent Services

Every outbound request must clearly separate request ID/correlation ID from authentication data. When using Spring Boot's managed `WebClient.Builder` alongside Micrometer Observation, tracing propagation can be configured automatically; do not assume `WebClient.create()` carries all application trace headers.

When propagating custom IDs, send the header only to **allowlisted trusted destinations** and preserve the ID of the request being processed. Do not send tokens or user metadata alongside the ID for debugging convenience. When an upstream returns 500 with a detailed body, map it to `DEPENDENCY_UNAVAILABLE` or `INTERNAL_ERROR` and log the code/status in a controlled manner—**never proxy the raw error body** to the client.

If downstream calls use retries, keep one correlation ID for the logical request and use separate span/attempt indices to distinguish individual attempts; verify idempotency before retrying side-effecting requests. An ID helps tracing; it does not guarantee exactly-once execution.

## 8. Distinguishing Errors Before and After Response Commit

**Before commit:** the framework can still choose the status, headers, and response body. `@ExceptionHandler`, `@RestControllerAdvice`, `WebExceptionHandler`, or an appropriate error handler produces a public `ProblemDetail` and logs once. Choosing the error-catching layer depends on whether the error arises in a controller, functional handler, or WebFilter.

**After commit:** status/headers may have already been sent to the client, especially with SSE, NDJSON, chunked responses, or downloads. You cannot reliably turn an in-flight response into a new error JSON or change 200 to 500. You can only terminate the stream, send an *in-band* error frame if protocol and state allow, log/record metrics with the correlation ID, or let the client reconnect per contract.

Do not handle `onErrorResume` by returning a second response after output has already committed; that can cause protocol corruption or lose error context. See section 15 for detailed scenarios.

## 9. QA for the Error Contract and Runbooks

Test at least these paths: 400/422 validation errors; 401/403 unauthorized/forbidden; 404/409 business errors; 500 unclassified exceptions; WebFilter errors before the handler; upstream 5xx; client stream cancellation; errors when the response has already committed.

For each case, assert `HTTP status`, `Content-Type`, allowlisted `code`, `detail`, `X-Correlation-ID`, consistency between header and body, and assert the absence of markers such as dummy passwords, DB names, stack traces, `Authorization`, and raw exception messages. Use `WebTestClient` to verify the HTTP contract; verify logs/traces via an appender or instrumentation test with controlled log capture.

Operational checklist: error-rate/latency dashboards, alerts by status group and upstream, correlation ID lookup path, log redaction policy, support access permissions, customer documentation on reporting error codes without sending secrets, and replayable tests with dummy markers to detect leaks.

**Incident handling example:** client reports 500 and a correlation ID → support searches logs by ID → identifies exception type, service/trace span, and timestamp → investigates in internal systems → replies to the customer with a safe message. Never ask customers to send tokens, full cookies, or database credentials.

## 10. Choosing the Right Exception Boundary in Spring WebFlux

Spring WebFlux has multiple error-handling layers. Using the right layer ensures responses are sanitized whether an error occurs in a controller, a filter, or outer HTTP processing.

| Mechanism | Scope | Use When |
| --- | --- | --- |
| `@ExceptionHandler` | Exceptions tied to controller/handler methods | Specific business errors, mapping to status/error code |
| `@RestControllerAdvice` | Multiple annotated controllers | Shared error contract for REST APIs |
| `ResponseEntityExceptionHandler` | Built-in Spring WebFlux exceptions and `ErrorResponseException` | Standardizing binding, method, media type, and framework errors |
| `WebExceptionHandler` | WebFilter chain and target WebHandler | Errors arising outside annotated controllers, such as filter errors |
| `WebFilter` | Wraps request/response chain | Attaching correlation ID, timing, and request context |
| `WebClient` filter / `onStatus` | Outbound HTTP client | Normalizing errors from dependent services without forwarding raw downstream bodies |

`@RestControllerAdvice` does not replace `WebExceptionHandler` for errors occurring before or outside controller invocation. For instance, a `WebFilter` throwing an exception may not pass through controller advice.

### 10.1. Using ResponseEntityExceptionHandler to Sanitize Framework Errors

Spring WebFlux provides `ResponseEntityExceptionHandler` as a base class for `@ControllerAdvice`. You can override `handleExceptionInternal` to replace the default body with a safe `ProblemDetail`. This is especially useful because built-in exceptions may carry technical details or input that should not be echoed verbatim.

~~~java
@RestControllerAdvice
public class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    public Mono<ResponseEntity<Object>> handleNotFound(
            OrderNotFoundException exception,
            ServerWebExchange exchange) {

        String id = CorrelationIdFilter.from(exchange);
        ProblemDetail problem = ApiProblems.create(
            HttpStatus.NOT_FOUND,
            "ORDER_NOT_FOUND",
            "Order not found",
            "The requested order was not found.",
            id
        );

        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_PROBLEM_JSON);

        return super.handleExceptionInternal(
            exception, problem, headers, HttpStatus.NOT_FOUND, exchange);
    }

    @Override
    protected Mono<ResponseEntity<Object>> handleExceptionInternal(
            Exception exception,
            Object body,
            HttpHeaders headers,
            HttpStatusCode status,
            ServerWebExchange exchange) {

        String id = CorrelationIdFilter.from(exchange);
        ProblemDetail safeBody = ApiProblems.forStatus(status, id);

        HttpHeaders safeHeaders = headers == null
            ? new HttpHeaders()
            : new HttpHeaders(headers);

        safeHeaders.setContentType(MediaType.APPLICATION_PROBLEM_JSON);

        return super.handleExceptionInternal(
            exception, safeBody, safeHeaders, status, exchange);
    }
}
~~~

Here:
- `OrderNotFoundException` has a clear business error code and safe detail.
- Built-in WebFlux exceptions pass through `handleExceptionInternal`; the original body is replaced by a `ProblemDetail` built from the status.
- `correlationId` is read from the exchange attribute, matching the value the filter wrote to the response header.
- `instance` uses an opaque URN so raw paths are not echoed.
- If the response has already committed, Spring cannot overwrite the response; log the error with the correlation ID and handle per streaming protocol if applicable.

Do not pass `exception.getMessage()` into `ApiProblems`. When more client-facing information is needed, map the exception to an approved error code and wording.

### 10.2. WebExceptionHandler for Out-of-Controller Errors

Use `WebExceptionHandler` as a fallback for errors from the WebFilter chain or target WebHandler. The example below preserves `ResponseStatusException` statuses, while returning 500 for unclassified errors. It always builds a safe public detail.

~~~java
@Component
@Order(-2)
public class SanitizingWebExceptionHandler implements WebExceptionHandler {

    private static final Logger log =
        LoggerFactory.getLogger(SanitizingWebExceptionHandler.class);

    private static final HandlerStrategies STRATEGIES =
        HandlerStrategies.withDefaults();

    private static final ServerResponse.Context RESPONSE_CONTEXT =
        new ServerResponse.Context() {
            @Override
            public List<HttpMessageWriter<?>> messageWriters() {
                return STRATEGIES.messageWriters();
            }

            @Override
            public List<ViewResolver> viewResolvers() {
                return STRATEGIES.viewResolvers();
            }
        };

    @Override
    public Mono<Void> handle(
            ServerWebExchange exchange, Throwable exception) {

        if (exchange.getResponse().isCommitted()) {
            return Mono.error(exception);
        }

        String id = CorrelationIdFilter.from(exchange);

        HttpStatusCode status =
            exception instanceof ResponseStatusException responseStatus
                ? responseStatus.getStatusCode()
                : HttpStatus.INTERNAL_SERVER_ERROR;

        log.error(
            "web_pipeline_failed correlationId={} exceptionType={}",
            id,
            exception.getClass().getName()
        );

        ProblemDetail problem = ApiProblems.forStatus(status, id);

        return ServerResponse.status(status)
            .contentType(MediaType.APPLICATION_PROBLEM_JSON)
            .bodyValue(problem)
            .flatMap(response ->
                response.writeTo(exchange, RESPONSE_CONTEXT));
    }
}
~~~

`ServerResponse.writeTo` requires `ServerResponse.Context` to obtain message writers and view resolvers. The example uses default `HandlerStrategies`; if the application customizes codecs, use the server's same writer configuration so error bodies serialize consistently.

`@Order(-2)` places this handler before the lower-priority default status handler. Check the order of every `WebExceptionHandler` in the application, especially when Spring Security or custom error handlers are also present. Do not register multiple catch-all handlers without explicit ordering.

### 10.3. Mapping Statuses to Public Details

A centralized factory ensures all boundaries return the same schema:

~~~java
final class ApiProblems {

    private ApiProblems() {}

    static ProblemDetail create(
            HttpStatusCode status,
            String code,
            String title,
            String detail,
            String correlationId) {

        ProblemDetail problem =
            ProblemDetail.forStatusAndDetail(status, detail);

        String slug = code.toLowerCase(Locale.ROOT)
            .replace('_', '-');

        problem.setType(URI.create(
            "https://api.example.test/problems/" + slug));
        problem.setTitle(title);

        // Opaque instance: do not echo path/query that may contain PII.
        problem.setInstance(URI.create("urn:uuid:" + correlationId));

        problem.setProperty("code", code);
        problem.setProperty("correlationId", correlationId);

        return problem;
    }

    static ProblemDetail forStatus(
            HttpStatusCode status, String correlationId) {

        int value = status.value();

        String code = switch (value) {
            case 400 -> "INVALID_REQUEST";
            case 401 -> "UNAUTHENTICATED";
            case 403 -> "FORBIDDEN";
            case 404 -> "NOT_FOUND";
            case 405 -> "METHOD_NOT_ALLOWED";
            case 406 -> "NOT_ACCEPTABLE";
            case 409 -> "CONFLICT";
            case 413 -> "PAYLOAD_TOO_LARGE";
            case 415 -> "UNSUPPORTED_MEDIA_TYPE";
            case 429 -> "RATE_LIMITED";
            default -> status.is5xxServerError()
                ? "INTERNAL_ERROR"
                : "HTTP_ERROR";
        };

        String title = status.is5xxServerError()
            ? "Internal server error"
            : "Request failed";

        String detail = status.is5xxServerError()
            ? "An unexpected error occurred. Provide the correlation ID to support."
            : "The request could not be processed. Check the request and try again.";

        return create(status, code, title, detail, correlationId);
    }
}
~~~

In production, replace the `type` URI and wording with your organization's API documentation. Never put hostnames, stack traces, or exception messages into the URI. Keep `code` stable so clients can handle errors without depending on localized wording.

### 11.4. CorrelationIdFilter.java

~~~java
package com.example.errors;

import java.util.UUID;

import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebFilter;
import org.springframework.web.server.WebFilterChain;

import reactor.core.publisher.Mono;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class CorrelationIdFilter implements WebFilter {

    public static final String HEADER = "X-Correlation-ID";
    public static final String ATTRIBUTE =
        CorrelationIdFilter.class.getName() + ".id";
    public static final String CONTEXT_KEY = "app.correlationId";

    @Override
    public Mono<Void> filter(
            ServerWebExchange exchange, WebFilterChain chain) {

        String id = UUID.randomUUID().toString();

        exchange.getAttributes().put(ATTRIBUTE, id);
        exchange.getResponse().getHeaders().set(HEADER, id);

        return chain.filter(exchange)
            .contextWrite(context -> context.put(CONTEXT_KEY, id));
    }

    public static String from(ServerWebExchange exchange) {
        String id = exchange.getAttribute(ATTRIBUTE);
        return id != null ? id : "unavailable";
    }
}
~~~

The example always generates a new ID at the service boundary. If a trusted gateway assigns the ID, replace this policy with logic that accepts only gateway-authenticated values validated against an allowlist; never read and echo raw headers straight from the Internet.

### 11.8. SanitizingWebExceptionHandler.java

~~~java
package com.example.errors;

import java.util.List;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMessageWriter;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.MediaType;
import org.springframework.stereotype.Component;
import org.springframework.web.reactive.function.server.HandlerStrategies;
import org.springframework.web.reactive.function.server.ServerResponse;
import org.springframework.web.reactive.result.view.ViewResolver;
import org.springframework.web.server.ResponseStatusException;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebExceptionHandler;

import reactor.core.publisher.Mono;

@Component
@Order(-2)
public class SanitizingWebExceptionHandler
        implements WebExceptionHandler {

    private static final Logger log =
        LoggerFactory.getLogger(SanitizingWebExceptionHandler.class);

    private static final HandlerStrategies STRATEGIES =
        HandlerStrategies.withDefaults();

    private static final ServerResponse.Context RESPONSE_CONTEXT =
        new ServerResponse.Context() {
            @Override
            public List<HttpMessageWriter<?>> messageWriters() {
                return STRATEGIES.messageWriters();
            }

            @Override
            public List<ViewResolver> viewResolvers() {
                return STRATEGIES.viewResolvers();
            }
        };

    @Override
    public Mono<Void> handle(
            ServerWebExchange exchange, Throwable exception) {

        if (exchange.getResponse().isCommitted()) {
            return Mono.error(exception);
        }

        String id = CorrelationIdFilter.from(exchange);

        HttpStatusCode status =
            exception instanceof ResponseStatusException responseStatus
                ? responseStatus.getStatusCode()
                : HttpStatus.INTERNAL_SERVER_ERROR;

        log.error(
            "web_pipeline_failed correlationId={} exceptionType={}",
            id,
            exception.getClass().getName()
        );

        return ServerResponse.status(status)
            .contentType(MediaType.APPLICATION_PROBLEM_JSON)
            .bodyValue(ApiProblems.forStatus(status, id))
            .flatMap(response ->
                response.writeTo(exchange, RESPONSE_CONTEXT));
    }
}
~~~

This handler serves as a fallback for errors not handled by controller advice, such as errors from WebFilters or the target WebHandler. If the response has already committed, it re-emits the error signal because already-sent status/body cannot be changed. The log records only the correlation ID and exception type, not the raw message.

### 11.9. DownstreamWebClientConfiguration.java

~~~java
package com.example.errors;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.reactive.function.client.ClientRequest;
import org.springframework.web.reactive.function.client.WebClient;

import reactor.core.publisher.Mono;

@Configuration
public class DownstreamWebClientConfiguration {

    @Bean
    WebClient internalWebClient(WebClient.Builder builder) {
        return builder
            .filter((request, next) ->
                Mono.deferContextual(context -> {
                    if (!context.hasKey(
                            CorrelationIdFilter.CONTEXT_KEY)) {
                        return next.exchange(request);
                    }

                    String id = context.get(
                        CorrelationIdFilter.CONTEXT_KEY);

                    ClientRequest forwarded = ClientRequest.from(request)
                        .headers(headers -> headers.set(
                            CorrelationIdFilter.HEADER, id))
                        .build();

                    return next.exchange(forwarded);
                }))
            .build();
    }
}
~~~

Use this bean for allowlisted internal destinations. Boot supplies `WebClient.Builder`; keep the auto-configured builder so observability/tracing configuration is not lost. Do not apply this filter to arbitrary third-party hosts without a policy governing outbound correlation headers.

## 13. Micrometer Tracing: When Multiple Services Must Be Connected

Custom correlation IDs are useful for a single request or workflow, but when observing a distributed call graph, use tracing instead of building an ad-hoc trace system out of custom headers.

Spring Boot supports Micrometer Tracing with tracers such as OpenTelemetry or Brave. When tracing is active:
- Trace ID connects spans within the same distributed trace.
- Span ID identifies each operation/span.
- Default log correlation IDs are generated from trace ID and span ID.
- Auto-configured client builders can automatically propagate trace context.
- Context propagation keeps traces/spans properly linked across reactive execution.

A custom log pattern might look like:

~~~properties
logging.pattern.correlation=[${spring.application.name:},%X{traceId:-},%X{spanId:-}]
logging.include-application-name=false
~~~

Boot uses a trailing space in the pattern to separate the correlation prefix from the logger name in output. If changing the format, verify the MDC keys used by your tracer.

**Distinguish the two IDs:**
- `X-Correlation-ID` in the example is an application-generated ID returned to the client.
- `traceId` is the distributed trace ID managed by the tracing system.
- `spanId` changes per operation/span.
- Do not overwrite `traceparent` with a custom correlation ID.
- Do not accept arbitrary client-sent trace IDs and trust them as valid traces; the tracing library must parse/validate per W3C Trace Context.

When using `WebClient`, prefer the builder provided by Spring Boot so trace propagation is enabled. If creating clients with a standalone builder or `WebClient.create()` bypassing auto-configuration, trace propagation may not work as intended.

### 13.1. Reactor Context and MDC

Reactor Context is the right place for custom request metadata in reactive pipelines. Since MDC relies on ThreadLocal, context propagation integration is needed if log patterns read values from MDC across thread switches.

Do not:
- Set MDC at the start of a request and assume callbacks always execute on the same thread.
- Clear MDC in an arbitrary `doFinally` without understanding thread scope.
- Use `ThreadLocal` as a substitute for Reactor Context.
- Put raw user objects, request bodies, or credentials into Reactor Context.

You can use Micrometer Context Propagation or built-in mechanisms supported by Spring Boot/Reactor to bridge context when MDC is genuinely needed. For custom IDs, explicit log fields from `deferContextual` are often easier to control.

## 14. WebClient Error Handling: Do Not Forward Raw Errors from Other Services

A downstream service may return bodies containing hostnames, stack traces, SQL, tokens, or internal info. Never forward `WebClientResponseException.getResponseBodyAsString()` verbatim to the current client.

~~~java
WebClient client = internalWebClient;

Mono<Inventory> inventory =
    client.get()
        .uri("/api/inventory/{id}", itemId)
        .retrieve()
        .onStatus(
            status -> status.isError(),
            response -> response.releaseBody()
                .thenReturn(new InventoryUnavailableException())
        )
        .bodyToMono(Inventory.class);
~~~

This is an illustrative fragment. `InventoryUnavailableException` is an internal business/technical exception defined by the application; the current API's error mapper converts it into `DEPENDENCY_UNAVAILABLE` or `INTERNAL_ERROR` with a safe detail. If downstream statuses must be logged, log only the status and allowlisted destination service; do not log raw bodies or full headers.

For retries:
- Retry only transient errors and idempotent operations or those with an idempotency key.
- Keep the correlation ID across retry attempts of the same request.
- Log the retry count as a separate field rather than generating a new ID per attempt.
- Configure timeouts and retry limits; never turn a downstream error into an infinite retry loop.

## 15. Committed Responses: Cannot Replace with a New ProblemDetail

When a response has not committed, the exception handler can choose the status and write ProblemDetail. Once headers/body have been sent, the server cannot go back to change 200 to 500 or write a fresh error JSON from the start.

This commonly occurs with:
- `Flux<T>` streaming.
- Server-Sent Events.
- NDJSON.
- File downloads.
- Response bodies written directly via `ServerHttpResponse`.

When an error appears after commit:
1. Keep the correlation ID in internal logs/events.
2. Record that the stream ended abnormally along with the exception category.
3. Terminate the connection/Publisher per contract.
4. If the protocol supports error events, emit a safe event following a dedicated schema.
5. Never attempt to write a JSON ProblemDetail in the middle of an NDJSON/SSE stream.

With SSE, you can define an `error` event containing `code` and `correlationId` if the client contract allows it. Never send exception messages or stack traces in the event.

## 16. Production Security and Operations

### 16.1. Controlling Inbound Correlation IDs

If a trusted gateway supplies the ID:
- Authenticate the gateway using network boundaries, mTLS, or service identity mechanisms.
- Accept the header only from authenticated gateways.
- Validate charset/length, e.g., `[A-Za-z0-9._-]{1,64}`.
- Reject CR/LF, control characters, and overly long values.
- Never use the ID as an authorization token.
- Never put raw IDs into SQL or unescaped log statements.

If no clear trust boundary exists, generate a new ID in the service. You can store a validated inbound ID in a separate field if needed for auditing, but never let it overwrite the internal ID.

### 16.2. Limiting Where the ID Appears

A correlation ID is not an authentication secret, yet it can still correlate a user's activity. Expose it only to:
- The response header and error body of that request.
- Internal log/trace backends.
- Internal services authorized to receive correlation metadata.
- Authenticated support tooling.

Do not place the ID in URLs, query strings, public analytics, or unrelated third-party logs. Never use correlation ID as a metric tag because every request can generate a new value, causing cardinality explosion.

### 16.3. Log Access Control and Retention

- Restrict who can view stack traces and diagnostic payloads.
- Separate operational logs from audit logs if retention/access policies differ.
- Encrypt logs in transit and at rest per organizational policy.
- Enforce clear retention and disposal schedules.
- Audit who accesses or exports logs containing sensitive data.
- Check app logs, proxies, gateways, APM, tracing backends, and crash reports alike.
- Periodically scan test/staging logs to detect accidentally logged secrets.

### 16.4. Error Codes and Statuses Must Be Stable

Do not use `detail` prose as a machine-readable contract. Use codes such as:
- `ORDER_NOT_FOUND`
- `INVALID_REQUEST`
- `UNAUTHENTICATED`
- `FORBIDDEN`
- `DEPENDENCY_UNAVAILABLE`
- `INTERNAL_ERROR`

Clients can translate messages or drive UX by error code. When wording changes or is internationalized, client logic stays intact.

## 17. Common Mistakes and Fixes

| Mistake | Consequence | Right Approach |
| --- | --- | --- |
| Returning `exception.getMessage()` | Leaks SQL, hostnames, tokens, or input | Map exceptions to safe ProblemDetail |
| Serializing the entire `Throwable` | Leaks stack traces/causes/internal classes | Return only status, stable code, safe detail, and ID |
| Logging entire requests/responses | Credentials, cookies, and PII enter logs | Allowlist fields, never log full bodies/headers |
| Masking tokens with `****` in responses | Partial secrets can still be sensitive | Remove them completely from public errors |
| Generating correlation IDs inside individual service methods | IDs mismatch across layers | Generate at the request boundary, propagate via context |
| Generating a new ID on retry | Cannot correlate one request across attempts | Keep the same ID, add a retry count |
| Trusting arbitrary `X-Correlation-ID` from clients | Log forging, ID spoofing, and header injection | Generate fresh or trust only authenticated gateways + validate |
| Using correlation ID as trace ID | Wrong semantics, breaks trace propagation | Keep app correlation ID separate from W3C trace/span |
| Using ThreadLocal/MDC directly in reactive code | Loses context across thread switches or leaks to other requests | Reactor Context and Micrometer Context Propagation |
| Expecting `@ControllerAdvice` to catch all filter errors | Out-of-controller errors lack a unified error contract | Add a WebExceptionHandler for the WebHandler chain |
| WebExceptionHandler writing a body after commit | Corrupts the response or writes a second error | Check `isCommitted()` and terminate the stream safely |
| Forwarding raw downstream error bodies | Leaks topology and dependent service info | Map to the current API's error code |
| Putting correlation ID into metric labels | High cardinality, inflates metric cost | Keep IDs in logs/traces; use low-cardinality metric tags |
| Logging raw URL paths/queries | May contain emails, tokens, account IDs | Log route templates and allowlisted fields |
| Enabling public stack traces when debugging | Leaks implementation and secrets | Use protected internal diagnostic logs |

## 18. Debugging Workflow When Clients Report Errors

1. Retrieve `X-Correlation-ID` from the response header or `correlationId` in ProblemDetail.
2. Search logs by ID on the service that received the request.
3. Identify the route template, method, status, error code, and timestamp.
4. Locate the corresponding trace ID/span ID if Micrometer Tracing is enabled.
5. Follow the trace across services and identify the first failing span.
6. Inspect the exception type and sanitized internal diagnostic records.
7. If the error came from downstream, check status/duration/retry count of that service.
8. Verify whether the response had already committed to understand why the error body might not have changed.
9. After remediation, verify the client receives the expected status/error code and that the correlation ID still matches.

Never ask users to send passwords, cookies, Authorization headers, or raw request bodies in support tickets. The correlation ID is sufficient to locate the request in controlled systems.

## 19. Production Checklist

- [ ] Error responses use RFC 9457 `ProblemDetail` or an equivalent error contract.
- [ ] Every error category has a status and stable error code.
- [ ] `detail` is built from approved messages, never taken directly from `Throwable.getMessage()`.
- [ ] No stack traces, SQL, connection strings, hostnames, or secrets appear in responses.
- [ ] `instance` does not echo paths/queries that may contain PII or tokens.
- [ ] Correlation ID is generated at the boundary and preserved across response headers, bodies, and logs.
- [ ] Correlation ID is never used as a credential or metric label.
- [ ] Client-supplied headers are trusted only through authenticated gateways and after validation.
- [ ] Reactor Context is used for custom metadata in reactive pipelines.
- [ ] MDC/ThreadLocal is used only when context propagation is properly configured.
- [ ] WebClient propagates trace context via the auto-configured builder and custom IDs only to necessary internal services.
- [ ] `@RestControllerAdvice` handles controller errors; `WebExceptionHandler` handles WebHandler chain errors.
- [ ] WebExceptionHandler checks whether the response has committed before writing.
- [ ] Logs use an allowlist; raw credentials, cookies, bodies, and unsanitized exception messages are not logged.
- [ ] Tests prove secrets do not appear in responses/logs.
- [ ] Tests verify that correlation IDs in headers match bodies and logs.
- [ ] CORS exposes the correlation header if browser clients need to read it.
- [ ] Downstream errors are mapped to the current service's contract.
- [ ] Support has a workflow for looking up by correlation ID with appropriate log access controls.
