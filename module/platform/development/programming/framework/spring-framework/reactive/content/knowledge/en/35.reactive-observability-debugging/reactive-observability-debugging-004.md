# Correlation ID, Reactor Context, and MDC Integration in Spring WebFlux

## 1. Goal and Problem to Solve

A WebFlux application typically handles many concurrent requests with few threads. A single request may start on a Netty event-loop, continue through **flatMap**, switch to another Scheduler via **publishOn**, call WebClient or a reactive database, and return to write the HTTP response. When analyzing logs, lines belonging to the same request can appear interleaved among logs from hundreds of other requests.

A **Correlation ID** helps link logs and events belonging to the same logical operation. **Reactor Context** carries metadata through a reactive pipeline per subscription. **MDC (Mapped Diagnostic Context)** puts metadata into log lines via SLF4J/Logback. These three concepts are related, but **they are not the same mechanism**.

This lesson covers:

1. Why ThreadLocal MDC does not automatically follow WebFlux execution.
2. How Context and ContextView attach to a subscriber/subscription.
3. contextWrite, deferContextual, transformDeferredContextual, and key visibility scope.
4. How to generate/receive/validate X-Correlation-ID using a WebFilter.
5. Manual MDC integration using a scope with finally so data does not leak across threads.
6. Micrometer Context Propagation, ThreadLocalAccessor, ContextRegistry, and automatic mode.
7. Spring Boot Observability/Micrometer Tracing, traceId, spanId, and W3C traceparent.
8. Propagating correlation IDs to WebClient, message brokers, and asynchronous boundaries.
9. A Java 17, Spring Boot 4.1.2, WebFlux, logging, and WebTestClient example.
10. Testing concurrent requests, errors, timeouts, cancellation, and context loss.

## 2. What Is a Correlation ID?

A Correlation ID is a string that identifies a **request or logical operation** so operators can group related logs together.

Example of a request crossing three services:

~~~text
Client
  |
  | GET /checkout
  | X-Correlation-ID: req-8f42
  v
API Gateway
  | log: correlationId=req-8f42
  v
Order Service
  | log: correlationId=req-8f42
  v
Inventory Service
    log: correlationId=req-8f42
~~~

When searching for correlationId=req-8f42 in a centralized logging system, an engineer can view all events tagged with the same identifier.

### 2.1. Where Should the Correlation ID Appear?

- Request header when a contract uses X-Correlation-ID.
- Response header so the caller can report that ID when troubleshooting errors.
- Reactor Context of the server pipeline.
- Log events or MDC when writing logs.
- Headers of downstream HTTP calls if the inter-service contract requires it.
- Metadata of message events, jobs, or callbacks when tracking across time is needed.
- Error responses or diagnostic metadata when aligned with security policy.

The **X-Correlation-ID** header is common, but it is not a uniformly standardized distributed tracing mechanism across all systems. Clearly define its scope and management rules in the API contract.

### 2.2. One ID for a Request or a Business Operation?

If a user performs a checkout across multiple requests, you may need:

- a separate **requestId** for each HTTP request;
- a shared **correlationId** for a workflow;
- a **traceId** generated by the tracing system to link spans;
- a durable **business operation ID** (for example, orderId) for business logic.

Do not reuse a single identifier type for every purpose without considering cardinality, access control, reusability, and lifecycle.

## 3. Why Is Traditional MDC Easily Lost in Reactor?

MDC in popular Java logging frameworks usually relies on **ThreadLocal**. In a traditional servlet stack, a request is usually processed on one request thread for most of its synchronous lifecycle.

In WebFlux:

~~~text
Request A -> reactor-http-nio-1
Request B -> reactor-http-nio-1
Request A -> parallel-2
Request C -> reactor-http-nio-1
Request A -> boundedElastic-3
~~~

One thread can serve multiple requests at different times, and one request can hop across multiple threads.

If code uses:

~~~java
MDC.put("correlationId", "req-A");

return Mono.delay(Duration.ofMillis(20))
    .doOnNext(value -> log.info("processed"));
~~~

the log line inside doOnNext may run on a different thread and not see the value set on the initial thread. Worse, if MDC is not cleared, request A's value can appear in request B's logs on a reused thread.

**Never treat ThreadLocal or MDC as a reliable source of correlation data in a reactive pipeline without a context propagation mechanism.**

### 3.1. What Does Reactor Context Solve?

Reactor Context is a key-value collection attached to the **Subscriber** that travels with the subscription. It does not rely on operators always executing on the same thread.

~~~text
Subscription A
  Context {correlationId=req-A}
  -> map -> publishOn -> flatMap -> WebClient

Subscription B
  Context {correlationId=req-B}
  -> map -> publishOn -> flatMap -> database
~~~

As a result, A and B can run on the same thread while each subscription still keeps its own data. That is the foundation for carrying correlation IDs in Reactor.

## 4. Context and ContextView

Reactor provides:

- **reactor.util.context.Context**: an immutable API with operations that produce new instances such as put, delete, putAll.
- **reactor.util.context.ContextView**: a read-only interface via get, getOrDefault, getOrEmpty, hasKey.

A Context is a key-value structure with Object keys and values. Choose a stable key to avoid collisions with other libraries.

Example:

~~~java
public final class CorrelationId {
    public static final String KEY =
        "demo.correlationId";

    private CorrelationId() {}
}
~~~

Use the same key when writing and reading. In large applications, you can use a dedicated key object or a clear constant namespace instead of short strings like "id".

### 4.1. Writing Context with contextWrite

~~~java
Mono<String> pipeline =
    Mono.deferContextual(view ->
        Mono.just(view.get(CorrelationId.KEY))
    )
    .contextWrite(ctx ->
        ctx.put(CorrelationId.KEY, "req-123")
    );
~~~

Here contextWrite creates a **new Context** with the correlation key rather than mutating a global variable.

### 4.2. Reading Context with deferContextual

~~~java
Mono<String> currentId = Mono.deferContextual(view -> {
    String value = view.getOrDefault(
        CorrelationId.KEY,
        "missing"
    );
    return Mono.just(value);
});
~~~

deferContextual obtains ContextView **at subscription time**. It is suitable for source Mono/Flux pipelines that need to inspect subscriber metadata.

### 4.3. Context Is Not a Mutable Map

~~~java
Context c1 = Context.of("cid", "A");
Context c2 = c1.put("cid", "B");
~~~

c1 still holds A; c2 is a new Context holding B. Do not rely on writing in one branch to mutate a Context held elsewhere.

### 4.4. contextWrite Propagates from Downstream to Upstream

A common point of confusion is that data signals flow from publisher to subscriber, whereas Context is supplied from the subscriber side and seen by operators **upstream** of contextWrite.

Example:

~~~java
Mono<String> value =
    Mono.deferContextual(view ->
        Mono.just(view.get("cid"))
    )
    .contextWrite(ctx -> ctx.put("cid", "req-456"));
~~~

The deferContextual source is upstream of contextWrite, so it reads req-456.

If contextWrite is placed on a branch that is not downstream of the operator reading it, the key will not be visible there. Check its position in the chain rather than merely checking whether contextWrite is called somewhere in the file.

### 4.5. transformDeferredContextual

When an intermediate operator needs to inspect ContextView and transform the pipeline:

~~~java
Flux<String> enriched = source
    .transformDeferredContextual(
        (flux, view) -> flux.map(value ->
            view.getOrDefault("cid", "missing")
                + ":" + value
        )
    );
~~~

This is an illustrative snippet: source is an application Flux<String>. transformDeferredContextual lets the transformation receive the ContextView for each subscription.

### 4.6. Do Not Manually Subscribe Mid-Chain

Wrong:

~~~java
Mono.deferContextual(ctx -> {
    auditService.logAsync(ctx.get("cid")).subscribe();
    return nextStep();
});
~~~

A separate subscribe() has a separate lifecycle, can lose Reactor Context, detaches error/cancellation handling, and becomes an unawaited side effect.

Better via composition:

~~~java
Mono.deferContextual(ctx ->
    auditService.logAsync(ctx.get("cid"))
        .then(nextStep())
);
~~~

This snippet requires an appropriate auditService and nextStep. In this form, the main subscription coordinates both logging and the next step.

## 5. Correlation ID at the HTTP Boundary

A WebFlux **WebFilter** can:

1. Read the X-Correlation-ID header from the request.
2. Check trust policy, format, and size.
3. Keep a valid ID or generate a new one.
4. Attach the ID to the response header.
5. Write the ID into Reactor Context using contextWrite for the downstream pipeline.

Diagram:

~~~text
Request
  |
  v
WebFilter reads X-Correlation-ID
  |
  +-- valid --> reuse ID per trust policy
  |
  +-- missing/invalid --> generate new UUID
  |
  v
Response header X-Correlation-ID
  |
  v
chain.filter(exchange)
  |
  v
contextWrite(correlationId)
  |
  v
Controller -> Service -> Reactor operators
~~~

### 5.1. Do Not Trust Arbitrary Headers

An external client can send any arbitrary string. Never log raw values that are megabytes long or contain CR/LF, tokens, URLs with secrets, or control characters.

A starting policy:

- Accept only ASCII alphanumeric characters, dots, underscores, and hyphens.
- Limit length to 64 characters.
- When missing or invalid, generate a new UUID.
- Do not use correlation IDs as proof of authentication or authorization.
- Handle duplicate headers and trust boundaries at the gateway.
- If strictly system-generated IDs are required, always generate a new one and only record the incoming ID in sanitized metadata.

### 5.2. Returning the ID in the Response

The response header lets users send the correlation ID to support teams to locate logs, especially on 4xx/5xx errors. Do not include stack traces or internal details in error responses.

If JavaScript clients need to read custom response headers in CORS requests, the server may need to configure Access-Control-Expose-Headers according to its CORS policy.

### 5.3. WebFilter Must Not Block

Do not call blocking databases, Thread.sleep, or block() to obtain a correlation ID. Generating a UUID and running a regex check are lightweight operations. If an asynchronous session/identity lookup is required, compose a Mono into the WebFilter chain instead of blocking the event loop.

## 6. Logging with Short-Scoped MDC

MDC is a utility layer for logging patterns to pull variables such as correlationId, traceId, and spanId.

Example Logback pattern configuration:

~~~properties
logging.pattern.level=%5p [cid:%X{correlationId:-}]
~~~

If MDC contains correlationId when log.info executes, the log line can look like:

~~~text
INFO [cid:req-123] processed record
~~~

If the key is absent, the fallback displays an empty value or dash depending on configuration.

### 6.1. Manual Scope

When inside a callback that has a ContextView, you can temporarily attach MDC:

~~~java
Mono.deferContextual(view -> {
    String cid = view.get(CorrelationId.KEY);

    String previous = MDC.get("correlationId");
    try {
        MDC.put("correlationId", cid);
        log.info("handling request");
    }
    finally {
        if (previous == null) {
            MDC.remove("correlationId");
        }
        else {
            MDC.put("correlationId", previous);
        }
    }

    return Mono.just(cid);
});
~~~

This approach does not assume ThreadLocal travels across Schedulers automatically. It **restores the previous MDC value** after the log call on the exact same thread.

MDC.putCloseable can also help remove the key when closing the scope:

~~~java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("correlationId", cid)) {
    log.info("handling request");
}
~~~

However, MDC.putCloseable usually removes the key on close; if the thread already held the same key beforehand, do not assume it automatically restores the old value. Use a save/restore helper when state preservation is required.

### 6.2. doOnEach for Signal-Based Logging

The Reactor FAQ recommends a pattern using doOnEach combined with ContextView on the signal:

~~~java
Flux<Event> logged = events
    .doOnEach(signal -> {
        if (!signal.isOnNext()) {
            return;
        }

        String cid = signal.getContextView()
            .getOrDefault(
                CorrelationId.KEY,
                "missing"
            );

        try (MDC.MDCCloseable ignored =
                 MDC.putCloseable("correlationId", cid)) {
            log.debug("event={}", signal.get());
        }
    });
~~~

This snippet requires the application's Event, events, and logger. The hook reads ContextView from the Signal rather than blindly reading ThreadLocal. The scope is opened only around the log callback and should never be held across an asynchronous Publisher.

### 6.3. doFinally Does Not Have Direct Access to ContextView

doFinally receives SignalType, not a Signal containing ContextView. If you need to log the correlation ID on cancel/error/complete, capture the ID inside deferContextual and pass it into doFinally:

~~~java
Mono.deferContextual(view -> {
    String cid = view.get(CorrelationId.KEY);

    return process()
        .doFinally(signal ->
            ScopedMdc.run(cid, () ->
                log.info("finished: {}", signal)
            )
        );
});
~~~

This snippet requires process(), ScopedMdc, and logger. Do not try to read Reactor Context via ThreadLocal from doFinally without a bridge.

## 7. Automatic Integration via Micrometer Context Propagation

Micrometer Context Propagation is a library that bridges different context mechanisms, such as:

- Reactor Context / ContextView.
- ThreadLocal from imperative libraries.
- MDC or tracing context when an appropriate ThreadLocalAccessor is present.
- Tasks running on other Executors when properly captured/restored.

Key APIs:

| Component | Role |
| --- | --- |
| ThreadLocalAccessor | Reads/writes/clears a ThreadLocal value |
| ContextAccessor | Accesses a key-value structured context |
| ContextRegistry | Holds the registry of accessors |
| ContextSnapshot | Snapshots a set of contextual values |
| ContextSnapshot.Scope | Temporarily restores context into ThreadLocal |
| contextCapture() | Captures registered ThreadLocals into Reactor Context |
| Hooks.enableAutomaticContextPropagation() | Enables automatic propagation mode for new subscriptions |

**ReactorContextAccessor** is provided by Reactor and loaded via ServiceLoader when the Micrometer Context Propagation dependency is present. You do not need to write a custom ReactorContextAccessor just to use Reactor Context.

### 7.1. Limited vs Automatic Mode

According to Reactor 3.8 and Spring Boot 4.1 documentation:

- **Limited**: propagation to ThreadLocal is supported at appropriate operators/points such as handle and tap. Do not expect every operator callback to restore ThreadLocal automatically.
- **Automatic**: Reactor attempts to restore ThreadLocal for registered accessors across more operator/Scheduler boundaries. The hook must be enabled at startup before new subscriptions.
- Automatic mode does not turn every non-Reactor library into reactive code or automatically cover arbitrary raw Threads, CompletableFutures, and uninstrumented executors.

Spring Boot provides the property:

~~~properties
spring.reactor.context-propagation=auto
~~~

The default is typically limited. Enable auto when the application has the appropriate context-propagation dependency and you have verified performance/correctness impact.

### 7.2. Registering an MDC ThreadLocalAccessor

To bridge a key in Reactor Context to MDC, you can register an accessor:

~~~java
ContextRegistry.getInstance()
    .registerThreadLocalAccessor(
        CorrelationId.KEY,
        () -> MDC.get("correlationId"),
        (String value) ->
            MDC.put("correlationId", value),
        () -> MDC.remove("correlationId")
    );
~~~

Required dependency:

~~~xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>context-propagation</artifactId>
</dependency>
~~~

When using an appropriate Spring Boot parent/BOM, there is no need to hardcode a separate version.

After registering the accessor and enabling auto, Reactor can restore the MDC correlationId while executing operator callbacks with the corresponding Context:

~~~java
Mono.deferContextual(view -> {
    log.info("MDC can be restored here with auto mode");
    return Mono.just(view.get(CorrelationId.KEY));
});
~~~

There is no guarantee the log line above will see CID if the dependency is missing, the accessor is missing, context keys do not match, the hook is not enabled, the subscription was created before enabling the hook, or the code executes outside Reactor.

### 7.3. Registration and Cleanup

Register accessors **once at application startup**, not on every request. Do not accidentally let multiple beans register the same key.

Automatic propagation must ensure ThreadLocal is cleared when Context lacks the corresponding key to prevent leaking the previous request's value on a reused thread. The accessor must implement reset/remove properly.

If the application is already instrumented by Micrometer Tracing, **do not manually register duplicate accessors for traceId/spanId**; let the tracing library manage the context it owns.

### 7.4. contextCapture vs contextWrite

- **contextWrite**: writes values directly into Reactor Context without reading from ThreadLocal.
- **contextCapture**: reads registered ThreadLocals at an appropriate point (usually at subscribe time) and puts them into Reactor Context.
- **ContextSnapshot.captureAll**: captures values according to the registry within a specific scope.
- **ContextSnapshot.Scope**: restores values inside an imperative scope and cleans up when the scope ends.

For new WebFlux requests, prefer generating/sanitizing the ID in a WebFilter and calling **contextWrite**. There is no need to detour through MDC -> contextCapture when you already have the ID at the HTTP boundary.

### 7.5. @Async and Executors

When transitioning from Reactor to @Async or an arbitrary Executor, Reactor Context may not automatically propagate across non-Reactor mechanisms.

Spring Boot 4.1 supports:

~~~properties
spring.task.execution.propagate-context=true
~~~

for the auto-configured AsyncTaskExecutor in applicable cases; for custom-configured executors, you can use ContextPropagatingTaskDecorator.

Do not use thread inheritance or static ThreadLocals to replace capture/restore mechanisms. For background jobs completely decoupled from a request, create a separate context rather than extending the context of an already-finished HTTP subscription indefinitely.

## 8. Correlation ID, Request ID, and Distributed Tracing

Three concepts are often conflated:

| Property | Correlation ID | Trace ID | Span ID |
| --- | --- | --- | --- |
| Purpose | Group logs of an operation | Identify a distributed trace | Identify a unit of work within a trace |
| Origin | Gateway or application | Tracing SDK/propagator | Tracing SDK per span |
| Standardization | Contract-based; X-Correlation-ID has no universal standard | W3C Trace Context supports trace-id | W3C Trace Context supports parent-id/span |
| Scope | Request/workflow per design | Distributed trace journey | A specific span |
| Propagation | Custom-defined header | traceparent/tracestate | Via tracing context |

**traceparent** is the W3C Trace Context standard header. Do not replace traceparent with X-Correlation-ID or manually assemble traceId from arbitrary UUIDs if you are already using a tracing SDK.

### 8.1. Micrometer Tracing in Spring Boot

When Micrometer Tracing is configured, Spring Boot can populate traceId and spanId in MDC and include correlation info per the logging pattern. For example:

~~~text
[803B448A0489F84084905D3093480352-3425F23BB2432450]
~~~

That is an illustrative format from traceId/spanId, not necessarily identical to an application's custom X-Correlation-ID value.

If tracing is available and satisfies log-lookup needs, **prefer framework-managed traceId/spanId** instead of building a parallel ID propagation system that is hard to maintain.

### 8.2. Tracing Dependency

Spring Boot 4.1 supports Micrometer Tracing and OpenTelemetry. Depending on the exporter, you can use the appropriate OpenTelemetry starter:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
~~~

You must configure an exporter/collector, sampling, and privacy appropriate for the real environment. Merely adding the starter does not mean a collector capable of receiving spans is configured.

### 8.3. Auto-Configured WebClient.Builder

When tracing is enabled, inject the WebClient.Builder managed by Spring Boot:

~~~java
@Bean
WebClient downstreamWebClient(
    WebClient.Builder builder
) {
    return builder
        .baseUrl("https://inventory.example")
        .build();
}
~~~

Spring Boot recommends using the auto-configured WebClient.Builder so tracing propagation interceptors/customizers are applied. If you create a WebClient via WebClient.create() in an arbitrary place, propagation customizers may be bypassed.

### 8.4. Cardinality: Do Not Put correlationId in Metric Tags

Correlation IDs have huge numbers of unique values. Never add them as Prometheus labels or **low-cardinality metric tags**, because doing so creates unbounded time series.

High-precision identifiers belong in logs, span attributes under appropriate data policies, or high-cardinality metadata—not as dimensions on every metric.

## 9. Propagating X-Correlation-ID Downstream to WebClient

If a downstream API requires the same correlation header, you can create an ExchangeFilterFunction for WebClient.

~~~java
@Bean
WebClient inventoryWebClient(
    WebClient.Builder builder
) {
    return builder
        .baseUrl("https://inventory.example")
        .filter((request, next) ->
            Mono.deferContextual(view -> {
                String cid = view.getOrDefault(
                    CorrelationId.KEY,
                    "unavailable"
                );

                ClientRequest outgoing =
                    ClientRequest.from(request)
                        .headers(headers ->
                            headers.set(
                                "X-Correlation-ID",
                                cid
                            )
                        )
                        .build();

                return next.exchange(outgoing);
            })
        )
        .build();
}
~~~

Typical imports:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.web.reactive.function.client.ClientRequest;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;
~~~

This is a standalone propagation snippet and is not part of the runnable demo project in section 12.

Key points to understand:

- This is a **client-side filter** on WebClient, distinct from the **WebFilter** receiving inbound requests.
- Mono.deferContextual reads context upon subscription of the **outbound request**.
- Do not read MDC directly in the interceptor unless propagation is guaranteed.
- If context lacks CID, production policy must be explicit: generate a new ID, omit the header, or error. Do not use a string like "unavailable" in real systems as a shared ID.
- Tracing frameworks may propagate traceparent automatically, but do not propagate custom X-Correlation-ID by default; you need a dedicated filter or baggage propagation per contract.

### 9.1. Do Not Manually Subscribe Inside WebFilter or WebClient Filters

If you invoke downstream with a separate subscribe() and then return Mono.empty(), context and cancellation may not follow the main pipeline. Return the corresponding Mono<ClientResponse>, Mono<Response>, or Flux so Reactor coordinates execution.

### 9.2. Baggage and Tracing

If you want business metadata to traverse distributed tracing, you can consider baggage according to your tracing standard and library. However, baggage can be sent over the network, so never put tokens, PII, secrets, or sensitive payloads in it.

## 10. Logging on Errors, Retries, and Cancellation

### 10.1. doOnError

~~~java
Mono.deferContextual(view -> {
    String cid = view.getOrDefault(
        CorrelationId.KEY,
        "missing"
    );

    return repositoryCall()
        .doOnError(error ->
            ScopedMdc.run(cid, () ->
                log.error("repository failed", error)
            )
        );
});
~~~

This snippet requires the application's repositoryCall(), ScopedMdc, and logger.

Do not log the same stack trace at every layer, causing one failure to produce hundreds of records. Choose the right boundary and keep intermediate layer logs concise.

### 10.2. doFinally and Cancellation

doFinally is invoked with SignalType.CANCEL if downstream cancels the pipeline at that position. If you want to log CID on cancel, capture it inside deferContextual:

~~~java
Mono.deferContextual(view -> {
    String cid = view.get(CorrelationId.KEY);

    return longRunningWork()
        .doFinally(signal ->
            ScopedMdc.run(cid, () ->
                log.info("lifecycle={}", signal)
            )
        );
});
~~~

Cancellation does not guarantee remote side effects were rolled back, so do not log "operation rolled back" merely because of SignalType.CANCEL.

### 10.3. Retries and New Subscriptions

Retries can resubscribe upstream. Context written outside the retry or at the request boundary should remain stable for **one logical operation** if policy requires the same correlation ID across attempts.

Example:

~~~java
Mono.deferContextual(view ->
    retryableCall()
        .retryWhen(retryPolicy)
);
~~~

This snippet requires retryableCall and retryPolicy. If each retry attempt generates a different UUID inside defer, logs become hard to stitch back to the same operation; keep one correlation ID at the outer boundary. If you want to distinguish attempts, add a separate attempt number.

### 10.4. Context Loss with Thread/CompletableFuture

Reactor Context does not jump across boundaries outside Reactor automatically. If the application uses:

- new Thread(...).
- CompletableFuture.supplyAsync(...).
- An uninstrumented ExecutorService.
- Callbacks from legacy libraries.
- Standalone message broker listeners.

then you must pass the ID explicitly or capture/restore via Micrometer ContextSnapshot. Do not run a hidden subscribe() inside a callback and expect the same Reactor Context.

## 11. Designing Production Logging

### 11.1. Log Enough, Without Logging Sensitive Data

An event should typically include:

- Timestamp, log level.
- Service, environment, instance.
- Correlation ID and/or traceId/spanId.
- Route template instead of raw paths containing personal data where possible.
- Method, status, duration.
- Error code and exception type when an error occurs.

Never log Authorization, Cookie, passwords, access tokens, refresh tokens, card numbers, health data, or sensitive request contents. Correlation IDs must also be validated to prevent log injection.

### 11.2. Structured JSON Format

When using structured logging, put correlationId in its own JSON field rather than only concatenating it into the message string. A record might look like:

~~~json
{
  "service": "checkout",
  "level": "INFO",
  "correlationId": "req-abc",
  "event": "inventory_reserved",
  "durationMs": 14
}
~~~

The JSON above is illustrative, not the stdout of the demo application. Logging implementation depends on Spring Boot/Logback and the logging pipeline.

### 11.3. Do Not Confuse Context with Logging Verbosity

Reactor Context is metadata storage; it does not write logs by itself. MDC holds values for the logging framework; it does not generate traces by itself. Micrometer tracing is a separate system that creates/propagates spans.

All three can be used together if ownership is clear: Context as the source of truth for custom IDs, MDC only as an adapter for the logger, and Tracer owning traceId/spanId.

## 12. Complete Java 17 / Spring Boot 4.1.2 Example

The following WebFlux project demonstrates:

- Generating or validating X-Correlation-ID in a **WebFilter**.
- Writing the same ID to the response header.
- Putting the ID into Reactor Context via contextWrite.
- Reading the ID via Mono.deferContextual after an async boundary.
- Logging through an MDC scope with finally so values do not leak on shared threads.
- Using WebTestClient to verify the ID is preserved over HTTP and across concurrent requests.
- Not requiring automatic Micrometer Context Propagation, helping you understand the manual approach before introducing a bridge.

### 12.5. CorrelationIdWebFilter.java

~~~java
package com.example.correlation;

import java.util.UUID;
import java.util.regex.Pattern;

import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.server.ServerWebExchange;
import org.springframework.web.server.WebFilter;
import org.springframework.web.server.WebFilterChain;

import reactor.core.publisher.Mono;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public final class CorrelationIdWebFilter
        implements WebFilter {

    private static final Pattern SAFE_ID = Pattern.compile(
        "[A-Za-z0-9][A-Za-z0-9._-]{0,63}"
    );

    @Override
    public Mono<Void> filter(
        ServerWebExchange exchange,
        WebFilterChain chain
    ) {
        return Mono.defer(() -> {
            String incoming = exchange.getRequest()
                .getHeaders()
                .getFirst(CorrelationId.HEADER);

            String id =
                incoming != null
                    && SAFE_ID.matcher(incoming).matches()
                    ? incoming
                    : UUID.randomUUID().toString();

            // Must be set before response gets committed.
            exchange.getResponse().getHeaders().set(
                CorrelationId.HEADER,
                id
            );

            // Context is applied to the upstream subscription
            // represented by chain.filter(exchange).
            return chain.filter(exchange)
                .contextWrite(context ->
                    context.put(CorrelationId.KEY, id)
                );
        });
    }
}
~~~

Meaning:

1. The filter is placed early in the outer WebFilterChain.
2. One ID is chosen per request/subscription.
3. Valid IDs consist of at most 64 characters matching SAFE_ID.
4. Missing/invalid IDs are replaced with a UUID.
5. The response header is set before the response is committed.
6. contextWrite puts the ID into Reactor Context for downstream controllers/services.
7. No static ThreadLocal, no block(), and no manual subscribe().

**Production note:** check duplicate X-Correlation-ID headers, total header length, and reverse proxy trust boundaries. If only the gateway is allowed to pick the ID, services should trust headers coming from an authenticated gateway and regenerate IDs for requests bypassing the gateway.

### 12.6. ScopedMdc.java

~~~java
package com.example.correlation;

import org.slf4j.MDC;

public final class ScopedMdc {

    private ScopedMdc() {}

    public static void run(
        String correlationId,
        Runnable action
    ) {
        String previous = MDC.get(CorrelationId.MDC_KEY);

        try {
            MDC.put(CorrelationId.MDC_KEY, correlationId);
            action.run();
        }
        finally {
            if (previous == null) {
                MDC.remove(CorrelationId.MDC_KEY);
            }
            else {
                MDC.put(
                    CorrelationId.MDC_KEY,
                    previous
                );
            }
        }
    }
}
~~~

Unlike setting MDC at the beginning of an HTTP request and hoping it follows across threads, this helper opens an MDC scope **right at the logging site**. It saves and restores the previous value even if the action throws an exception.

### 12.7. CorrelationService.java

~~~java
package com.example.correlation;

import java.time.Duration;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import reactor.core.publisher.Mono;

@Service
public final class CorrelationService {

    private static final Logger log =
        LoggerFactory.getLogger(
            CorrelationService.class
        );

    public Mono<String> readAfterAsyncHop() {
        return Mono.delay(Duration.ofMillis(15))
            .flatMap(ignored ->
                Mono.deferContextual(context -> {
                    String id = context.get(
                        CorrelationId.KEY
                    );

                    ScopedMdc.run(id, () ->
                        log.info(
                            "Service step after async hop"
                        )
                    );

                    return Mono.just(id);
                })
            );
    }
}
~~~

Mono.delay usually emits on a Reactor Scheduler rather than assuming it stays on the Netty event-loop. deferContextual still reads the correct ID from the subscription. ScopedMdc exists only during the log call and is cleaned up in finally.

If you add a doOnNext(log.info) after Mono.delay without a bridge, MDC may be empty; that is why the example proactively opens the scope at the log point.

### 12.11. CorrelationIntegrationTest.java

~~~java
package com.example.correlation;

import java.time.Duration;
import java.util.UUID;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.http.ResponseEntity;
import org.springframework.test.web.reactive.server.EntityExchangeResult;
import org.springframework.test.web.reactive.server.WebTestClient;
import org.springframework.web.reactive.function.client.WebClient;

import reactor.core.publisher.Flux;
import reactor.test.StepVerifier;

import static org.junit.jupiter.api.Assertions.*;

@SpringBootTest(
    webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT
)
class CorrelationIntegrationTest {

    @LocalServerPort
    int port;

    WebTestClient client;

    @BeforeEach
    void setUp() {
        client = WebTestClient.bindToServer()
            .baseUrl("http://localhost:" + port)
            .build();
    }

    @Test
    void preservesValidIncomingIdAcrossAsyncHop() {
        EntityExchangeResult<String> result =
            client.get()
                .uri("/api/correlation")
                .header(
                    CorrelationId.HEADER,
                    "req-123"
                )
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class)
                .returnResult();

        assertEquals(
            "req-123",
            result.getResponseHeaders().getFirst(
                CorrelationId.HEADER
            )
        );
        assertEquals(
            "req-123",
            result.getResponseBody()
        );
    }

    @Test
    void generatesUuidWhenHeaderIsMissing() {
        EntityExchangeResult<String> result =
            client.get()
                .uri("/api/correlation")
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class)
                .returnResult();

        String id = result.getResponseHeaders()
            .getFirst(CorrelationId.HEADER);

        assertNotNull(id);
        assertEquals(
            id,
            result.getResponseBody()
        );

        UUID.fromString(id);
    }

    @Test
    void rejectsUntrustedHeaderValue() {
        EntityExchangeResult<String> result =
            client.get()
                .uri("/api/correlation")
                .header(
                    CorrelationId.HEADER,
                    "value with spaces"
                )
                .exchange()
                .expectStatus().isOk()
                .expectBody(String.class)
                .returnResult();

        String id = result.getResponseHeaders()
            .getFirst(CorrelationId.HEADER);

        assertNotNull(id);
        assertNotEquals(
            "value with spaces",
            id
        );
        UUID.fromString(id);
        assertEquals(id, result.getResponseBody());
    }

    @Test
    void concurrentRequestsDoNotMixContext() {
        WebClient webClient = WebClient.builder()
            .baseUrl(
                "http://localhost:" + port
            )
            .build();

        Flux<Integer> checked = Flux.range(1, 24)
            .flatMap(index -> {
                String id = "req-" + index;

                return webClient.get()
                    .uri("/api/correlation")
                    .header(CorrelationId.HEADER, id)
                    .retrieve()
                    .toEntity(String.class)
                    .map((ResponseEntity<String> response) -> {
                        assertEquals(
                            id,
                            response.getHeaders().getFirst(
                                CorrelationId.HEADER
                            )
                        );
                        assertEquals(
                            id,
                            response.getBody()
                        );

                        return index;
                    });
            }, 8);

        StepVerifier.create(checked)
            .expectNextCount(24)
            .verifyComplete();
    }
}
~~~

The four integration tests prove:

1. A valid ID is preserved across the inbound header, response header, and Reactor Context after an async hop.
2. When the header is missing, the server generates a UUID and the same value flows through the pipeline.
3. Invalid headers are replaced with a UUID.
4. Concurrent requests keep independent IDs without sharing ThreadLocal.

Note: The tests verify **response and context values**, not the exact formatting of each actual log line. ScopedMdcTest verifies the helper's behavior; to verify logging events, you can add a suitable Logback test appender.

## 13. Extending the Demo to an Automatic MDC Bridge

The manual-mode example helps clarify how Context and MDC work. When many log statements across different operators are needed without opening a scope manually at each site, propagation can be enabled.

### 13.1. Adding the Dependency

In pom.xml, add:

~~~xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>context-propagation</artifactId>
</dependency>
~~~

In application.properties:

~~~properties
spring.reactor.context-propagation=auto
~~~

### 13.2. Configuring the Accessor

Add an illustrative configuration class:

~~~java
package com.example.correlation;

import io.micrometer.context.ContextRegistry;
import jakarta.annotation.PostConstruct;

import org.slf4j.MDC;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MdcPropagationConfiguration {

    @PostConstruct
    void registerAccessor() {
        ContextRegistry.getInstance()
            .registerThreadLocalAccessor(
                CorrelationId.KEY,
                () -> MDC.get(
                    CorrelationId.MDC_KEY
                ),
                (String value) -> MDC.put(
                    CorrelationId.MDC_KEY,
                    value
                ),
                () -> MDC.remove(
                    CorrelationId.MDC_KEY
                )
            );
    }
}
~~~

This is an **optional extension**; it is not required for the base project to compile/run. After adding the dependency and configuration, Spring Boot can enable automatic mode early while the accessor is registered at startup before serving requests.

### 13.3. Reading Logs Inside Operators

Once the bridge is active, Reactor callbacks can read the MDC value corresponding to the value in Context:

~~~java
Mono.delay(Duration.ofMillis(10))
    .doOnNext(value ->
        log.info("MDC auto-propagated")
    );
~~~

There is no guarantee correlationId is present if this snippet is called **outside** a subscription that carries the Context key. Do not turn a standalone log call into a request-bound context.

### 13.4. Testing Automatic Mode

Add tests in an application booted with the auto property:

- Header req-A is reflected in MDC inside Reactor callbacks.
- Concurrent header req-B does not appear in A's logs.
- Callbacks after leaving the scope do not retain MDC from a finished request.
- When Context lacks the key, accessor reset removes MDC instead of retaining an old value.
- No exceptions or deadlocks occur during retry, cancel, or publishOn.

Do not just enable the property and assume all ThreadLocals are propagated: accessors, key mappings, and subscription boundaries still determine the result.

## 14. Unit-Testing Reactor Context

If you do not want to start an HTTP server, you can use StepVerifier directly:

~~~java
Mono<String> pipeline =
    Mono.deferContextual(view ->
        Mono.just(view.get(CorrelationId.KEY))
    )
    .publishOn(Schedulers.boundedElastic())
    .contextWrite(ctx ->
        ctx.put(CorrelationId.KEY, "unit-1")
    );

StepVerifier.create(pipeline)
    .expectNext("unit-1")
    .verifyComplete();
~~~

The snippet requires Reactor Test, Schedulers, and CorrelationId. publishOn switches downstream execution; Context still belongs to the subscription.

### 14.1. Testing Isolation

~~~java
Mono<String> template =
    Mono.deferContextual(view ->
        Mono.just(view.get(CorrelationId.KEY))
    );

Mono<String> a = template.contextWrite(
    Context.of(CorrelationId.KEY, "A")
);

Mono<String> b = template.contextWrite(
    Context.of(CorrelationId.KEY, "B")
);
~~~

A and B are two pipelines with separate Contexts. Test each pipeline or zip/flatMap concurrently to verify they do not mix.

### 14.2. Testing Missing Keys

If a context key must always be present, use view.get(key) to fail fast instead of silently returning "missing". For optional IDs, getOrDefault may be appropriate. Do not use a shared fallback for every request in production, as that causes logs from many requests to be grouped under the same ID.

### 14.3. Testing contextWrite Order

Design tests placing contextWrite before and after an operator that reads context, to distinguish upstream visibility effects. When pipelines are composed using transform, flatMap, publishOn, defer, and contextWrite, you must know the exact subscription boundaries.

## 15. Understanding Context-Loss Boundaries

### 15.1. Manual subscribe()

~~~java
public Mono<Void> handle() {
    service.call().subscribe();
    return Mono.empty();
}
~~~

This is an **anti-pattern** in WebFlux request handlers: the new subscription is not composed with the request lifecycle; context propagation, errors, and cancellation can be lost.

Replace with:

~~~java
public Mono<Void> handle() {
    return service.call().then();
}
~~~

### 15.2. CompletableFuture and Raw Threads

A Runnable inside CompletableFuture.supplyAsync or ExecutorService does not see Reactor Context by default. You can pass the correlation ID as an argument:

~~~java
Mono.deferContextual(view -> {
    String id = view.get(CorrelationId.KEY);

    return Mono.fromCallable(
        () -> blockingLegacyCall(id)
    ).subscribeOn(Schedulers.boundedElastic());
});
~~~

This snippet requires blockingLegacyCall; at minimum it passes the ID explicitly and isolates blocking work. For multiple contextual values, see Micrometer ContextSnapshot and ContextPropagatingTaskDecorator.

### 15.3. Message Brokers and Asynchronous Jobs

An event may be processed minutes later or in another process where the original HTTP Reactor Context no longer exists. If the business contract requires correlation, add structured metadata to message headers. The receiving listener creates a new Context based on validated metadata.

Do not capture the entire request object or a SecurityContext containing secrets into a message just to keep log correlation.

### 15.4. Reactor Context and Spring Security

ReactiveSecurityContextHolder also uses Reactor Context to store SecurityContext. Do not overwrite the entire Context with a new Context containing only the correlation ID if doing so drops keys managed by Spring Security, tracing, and other libraries.

Safer is:

~~~java
.contextWrite(context ->
    context.put(CorrelationId.KEY, id)
)
~~~

rather than replacing the whole Context or using a custom mechanism that does not merge metadata. This is one reason to use contextWrite(Function).

## 16. Log Querying and Observability

With a correlation ID returned to the client:

1. The user sends the ID from the error response or response header.
2. Search in the logging system by the correlationId field.
3. Sort by timestamp and group by service.
4. Combine with traceId/spanId if distributed tracing is available.
5. Cross-reference HTTP status, latency, exceptions, and downstream dependencies.
6. Look for timeouts, retries, or cancelled requests.
7. Do not confuse duplicate/retry events with new requests if a workflow shares one ID.

### 16.1. Which Metrics Should Be Measured as Well?

- Request count by route template and status.
- Latency p50/p95/p99.
- Error rate by dependency and exception category.
- Retry count, timeout count, cancellation count.
- Tracing sampling rate and exporter queue health.
- Log ingestion delay or dropped log count.

**Never add correlation ID to metric labels** because cardinality becomes uncontrollable.

### 16.2. Log Correlation When a Trace Is Not Sampled

A tracing system may sample only a fraction of requests. When a trace is not exported, internal correlation IDs remain useful for log search if log retention policies permit. However, do not increase log volume uncontrollably for every request just to compensate for an underconfigured tracing setup.

## 17. Common Errors and Troubleshooting

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| MDC empty after publishOn | ThreadLocal does not propagate automatically across Schedulers | Read Reactor Context and open an MDC scope or configure propagation |
| Request A shows B's CID | ThreadLocal not cleared on shared thread | try/finally restore, accessor reset, or proper automatic mode |
| ContextView cannot find key | contextWrite placed in the wrong position | Check upstream/downstream positions in the chain |
| ID present in controller, lost in service | Service runs in a separate subscribe | Return Mono/Flux composition; do not manually subscribe |
| Logs lack CID despite response header having it | Header does not automatically populate MDC | Scoped MDC logging or a bridge |
| Auto enabled, yet MDC still empty | Missing context-propagation or ThreadLocalAccessor/key | Check dependencies, registry, and startup order |
| Auto propagation still lost on raw Thread | Non-Reactor threads are not instrumented | Pass ID explicitly or use ContextSnapshot |
| Many requests share the same CID "missing" | Using a shared fallback as a real ID | Generate UUID at the inbound boundary |
| Header contains overly long string | Trusting input without validation | Limit size/charset and handle duplicate headers |
| Log injection | Allowing CR/LF and control chars | Validate ID and sanitize logs |
| Tracing has traceId, but downstream lacks it | WebClient created outside Boot builder | Inject auto-configured WebClient.Builder |
| X-Correlation-ID does not reach other services | W3C tracing does not carry custom headers automatically | Client filter or baggage contract |
| MDC traceId overwritten incorrectly | Manually registered duplicate accessor | Let Micrometer Tracing own tracing context |
| Prometheus metrics cardinality explosion | Putting CID in a label | Use only low-cardinality labels |
| doFinally lacks context | Hook receives SignalType, not ContextView | Capture ID in deferContextual |
| CORS client cannot read header | Header not exposed | Expose X-Correlation-ID per CORS policy |
| CID missing in async job | Job decoupled from HTTP subscription | Pass metadata and initialize a new context |
| Source not subscribed | Code uses cache/side effects at assembly | Check lazy assembly and subscription |
| MDC scope does not restore previous value | Only calls remove on close | Save previous and restore in finally |
| Rare failures in concurrent tests | Using static ThreadLocal as request context | Use Reactor Context and concurrency tests |

## 18. Implementation Checklist

Before taking correlation logging to production:

1. Clarify how correlation ID differs from requestId/traceId.
2. Is there a policy for ID generation source and trust boundary?
3. Are IDs validated for charset and length?
4. Is the response header set before commit?
5. Does the WebFilter write the right key to Reactor Context?
6. Is ContextView read at subscription time?
7. Is contextWrite placed properly for upstream visibility?
8. Is MDC ThreadLocal avoided as the source of truth in WebFlux?
9. Does the MDC scope restore the old value in finally?
10. Are manual MDC and automatic bridging clearly distinguished?
11. Is ThreadLocalAccessor registered once with proper reset?
12. Is Spring Boot auto context propagation enabled only when dependencies exist and are tested?
13. Are tracing exporter and sampling properly configured?
14. Does outbound WebClient use Boot's builder when trace propagation is needed?
15. Is custom X-Correlation-ID propagated explicitly?
16. Are secrets/PII, tokens, and raw credentials excluded from logs?
17. Is CID never used as a metric label?
18. Are there tests for concurrent requests and across thread hops?
19. Are there tests for missing/invalid headers and preserving context on errors?
20. Are cancellation, timeouts, and necessary asynchronous boundaries tested?

## 20. Key Takeaways

**Correlation ID** links logs of a request or logical operation. **Reactor Context** stores and propagates metadata per subscription, surviving thread switches across the pipeline. **MDC** is a ThreadLocal adapter for loggers and is not inherently safe in WebFlux.

Generate or validate the ID at the HTTP boundary, store it in Context with **contextWrite**, read it with **deferContextual**, and either open a short MDC scope at log statements or use **Micrometer Context Propagation** with a registered ThreadLocalAccessor. Clean up ThreadLocals properly so IDs do not leak between requests.

In Spring Boot, **spring.reactor.context-propagation=auto** enables automatic mode for Reactor when appropriate dependencies and configuration are present. If the application already uses Micrometer Tracing, prefer framework-managed traceId/spanId; they are distinct from a custom X-Correlation-ID. Use the auto-configured WebClient.Builder so instrumentation and tracing propagation are not bypassed.
