# ETag, Last-Modified, and conditional requests

**Context:** Spring Framework Reactive → **HTTP Contracts**.

An HTTP response can carry data along with validators describing the version of the representation. When a client stores a copy, it sends the validator back on a subsequent request to ask the server whether the copy is still usable. When a client updates a resource, it can send a validator as a condition to avoid overwriting someone else's changes.

Three concepts to grasp:

- `ETag` is an entity tag identifying a version of a representation. The server usually generates it from a content hash or a stable version of the resource.
- `Last-Modified` is the time the representation was last modified, sent as an HTTP-date.
- **Conditional request** is a request with a condition such as `If-None-Match`, `If-Modified-Since`, or `If-Match`. The server evaluates the condition before sending the representation or performing a change.

With GET/HEAD, a validator lets the server return `304 Not Modified` and skip the body when the client's copy is still valid. With write operations, `If-Match` helps detect that the resource has changed and can prevent stale updates with `412 Precondition Failed`.

## 1. Why does HTTP need validators?

Suppose an application reads a book record via `GET /books/42`. The first time, the server returns:

```http
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "book-v17"
Last-Modified: Tue, 15 Apr 2025 10:15:30 GMT
Cache-Control: private, max-age=60

{"id":42,"title":"Reactive HTTP"}
```

The client can store this representation along with the headers. If later the client needs to check whether the data has changed, it does not need to download the entire JSON right away. It sends the validator:

```http
GET /books/42 HTTP/1.1
If-None-Match: "book-v17"
```

If the current representation still has the matching ETag, the server returns:

```http
HTTP/1.1 304 Not Modified
ETag: "book-v17"
Last-Modified: Tue, 15 Apr 2025 10:15:30 GMT
Cache-Control: private, max-age=60
```

`304` is not an error and has no response body. The client uses the previously stored representation as if it had just received a successful response. As a result, the request can still reach the server to verify validity, while the server does not need to resend the entire payload.

If the resource has changed, the server returns `200 OK` with the new representation and the new validator, for example `ETag: "book-v18"`.

**Freshness and validation are two related but different mechanisms:**

- When a response is still fresh per `Cache-Control: max-age`, the cache can reuse the response without asking the origin.
- When a response is stale, the cache can send a conditional request with `ETag` or `Last-Modified`.
- `no-cache` allows storing, but requires revalidation before reuse.
- `no-store` instructs not to store the response in a cache.
- `private` restricts caching to a private cache such as a browser; `public` allows shared caches to store it if other conditions allow.

Validators do not themselves decide how long a cache is used. `Cache-Control` specifies the freshness policy; validators support checking when revalidation is needed.

## 2. What is an ETag?

`ETag` (entity tag) is an opaque value generated by the server to identify a version of a representation. The client does not need to understand the tag content; it only sends that value back to the server for comparison.

Example:

```http
ETag: "book-v17"
```

An ETag can be generated from:

- **A database version:** for example, an optimistic-lock version column that increments after each update.
- **A content hash:** for example, the SHA-256 of the chosen representation bytes.
- **A revision ID:** a version identifier issued by the storage system or content management system.

### 2.1. Strong ETag and weak ETag

A strong ETag has the form:

```http
ETag: "book-v17"
```

A weak ETag has the `W/` prefix:

```http
ETag: W/"book-v17"
```

The two kinds have different semantics:

| Type | Meaning | Appropriate use |
|---|---|---|
| **Strong validator** | Represents identical representation data under strong comparison requirements | Exact cache checks, ranges, and preventing lost updates with `If-Match` |
| **Weak validator** | Two representations are considered semantically equivalent even though the bytes may differ | Cache validation when minor differences do not alter the meaning of the content |

A strong ETag is appropriate when the server can guarantee that any change to the representation bytes produces a different tag. Hashing the encoded bytes themselves is a common approach. A database version can also be used as a strong validator if every change affecting the representation increments the version and the same version always produces a consistent representation.

A weak ETag is useful when the server only wants to say that two representations are equivalent in content, such as formatting differences or minor details unimportant to the client. A weak ETag cannot be used for the strong comparison of `If-Match`.

### 2.2. An ETag must identify the chosen representation

A resource can have multiple representations:

- JSON and XML.
- Vietnamese and English languages.
- Gzip-compressed data and uncompressed data.
- Responses that differ by user permissions or configuration.

If representations differ in bytes yet are assigned the same strong ETag, the validator may falsely assert that they are identical. Generate tags per chosen representation, or use a weak validator if you only want to confirm semantic equivalence.

When a response depends on headers such as `Accept` or `Accept-Language`, use `Vary` appropriately so caches know about the different variants. For personal data, an appropriate cache policy such as `private` or `no-store` is needed; ETag does not replace authorization.

### 2.3. Do not confuse ETag with a security checksum

An ETag is primarily an HTTP validator, not a digital signature or a data authentication mechanism. Clients must not treat an ETag as proof that a response came from a trusted server. If integrity or authenticity is needed, use appropriate cryptographic mechanisms such as TLS and signatures under a separate contract.

## 3. What is Last-Modified?

`Last-Modified` indicates when the representation was last modified:

```http
Last-Modified: Tue, 15 Apr 2025 10:15:30 GMT
```

The value is an HTTP-date in UTC/GMT. The server usually derives it from the resource's updated field, normalized to HTTP-date precision.

The client sends back:

```http
If-Modified-Since: Tue, 15 Apr 2025 10:15:30 GMT
```

If the representation is no newer than this point in time, the server can return `304 Not Modified`.

### 3.1. One-second resolution limitation

HTTP-date has one-second resolution. If a resource is modified twice within the same second, the two versions can have the same `Last-Modified`. Therefore, Last-Modified may not be accurate enough to distinguish every version.

Example:

- Version A was modified at 10:15:30.100.
- Version B was modified at 10:15:30.800.
- Both can be represented as `10:15:30 GMT`.

A client may hold version A yet send `If-Modified-Since: 10:15:30 GMT`; comparing only timestamps is not enough to detect change B within the same second.

Other issues include clock skew across servers, incorrectly updated timestamps, low-precision storage systems, and representations assembled from multiple data sources.

**Good practice:** send both ETag and Last-Modified if possible. ETag is usually the more accurate validator; Last-Modified is useful for clients or caches that do not store ETags and is easy to read when diagnosing.

## 4. Important conditional request headers

### 4.1. If-None-Match: checking whether a representation has not changed

`If-None-Match` contains one or more entity tags, or the character `*`:

```http
If-None-Match: "book-v17"
If-None-Match: "book-v16", "book-v17"
If-None-Match: *
```

With GET/HEAD:

- If a tag matches the current representation, the server returns `304 Not Modified`.
- If no tag matches, the server processes the request normally and can return `200` along with the representation.

`If-None-Match` uses **weak comparison**. Therefore `W/"book-v17"` can match `"book-v17"` in the context of cache validation.

With unsafe methods such as PUT, POST, or DELETE, if the `If-None-Match` condition fails, the server returns `412 Precondition Failed` and performs no change. The `If-None-Match: *` case is often used to create a resource only if the resource does not already exist.

### 4.2. If-Modified-Since: checking by time

`If-Modified-Since` is used with GET/HEAD:

```http
If-Modified-Since: Tue, 15 Apr 2025 10:15:30 GMT
```

If the current representation's Last-Modified is earlier than or equal to the date sent, the server can return `304`. If the resource is newer, the server returns the representation normally.

If the request has both `If-None-Match` and `If-Modified-Since`, the server **ignores If-Modified-Since**. ETag is the more accurate validator and has higher precedence.

### 4.3. If-Match: execute only if the current version matches

`If-Match` is often used when updating or deleting a resource:

```http
PUT /books/42 HTTP/1.1
If-Match: "book-v17"
Content-Type: application/json

{"title":"Reactive HTTP in Practice"}
```

The server performs the change only if the current representation has a strong ETag matching one of the tags in the header. If it does not match, the server returns `412 Precondition Failed`.

`If-Match: *` means continue only if the resource currently exists. This is useful when the client wants to update an existing resource and does not want to create a new one by accident.

`If-Match` uses **strong comparison**. A weak ETag is not suitable for preventing lost updates because it does not guarantee identical representation data.

### 4.4. If-Unmodified-Since: date-based update condition

This is a timestamp-based option when the client does not have an ETag:

```http
If-Unmodified-Since: Tue, 15 Apr 2025 10:15:30 GMT
```

If the resource was modified after that point in time, the server should not perform the operation and can return `412`. If there are no newer changes, the request proceeds.

If the request has `If-Match`, the server ignores `If-Unmodified-Since` because ETag is the more accurate condition.

### 4.5. If-Range

`If-Range` is combined with `Range` when downloading part of a resource. The client sends the validator it has stored; if the representation still matches, the server returns `206 Partial Content` for the requested byte range. If the validator no longer matches, the server ignores Range and returns the whole representation as `200 OK`.

This is a useful mechanism for resumable downloads. A strong ETag is usually more appropriate to confirm that the content of the byte ranges has not changed.

## 5. How do 304 and 412 differ?

| Status | Meaning | Typical case |
|---|---|---|
| **200 OK** | The request was processed and the representation is sent | The resource is newer or there is no condition preventing sending |
| **304 Not Modified** | GET/HEAD where the cached representation is still valid | `If-None-Match` matches or `If-Modified-Since` indicates no change |
| **412 Precondition Failed** | A request condition was not met; the operation is not performed | `If-Match` does not match or `If-None-Match` fails with an unsafe method |
| **428 Precondition Required** | The server requires the client to send a precondition | The API mandates `If-Match` to prevent lost updates |

`304` is a cache validation response and carries no body. The client keeps its existing representation. The server should send the relevant metadata for caches to update or identify the representation, such as ETag, Vary, Cache-Control, or Expires where appropriate.

`412` is the result of a failed precondition. The client usually needs to re-read the resource, resolve the conflict, and then send a new request with the new validator. The server must not perform the side effects of the rejected operation.

`428` is not emitted automatically by every Spring configuration. It is an API choice when the server wants to require clients to supply a condition such as `If-Match`.

## 6. Precedence order when multiple conditions are present

HTTP does not evaluate conditional headers in an arbitrary order. RFC 9110 defines an order so preconditions do not conflict:

1. If `If-Match` is present, evaluate it first. If it fails, return `412` (unless the server determines the change has already been applied).
2. If `If-Match` is absent but `If-Unmodified-Since` is present, evaluate this condition. If it fails, return `412`.
3. If `If-None-Match` is present, evaluate it. If it fails for GET/HEAD, return `304`; for other methods, return `412`.
4. If the method is GET/HEAD, `If-None-Match` is absent, and `If-Modified-Since` is present, evaluate the date. If the representation has not changed, return `304`.
5. If GET has `Range` and `If-Range`, evaluate whether partial content can be returned or the full representation must be resent.
6. If no precondition prevents the request, process the method normally.

Practical point to remember: **If-None-Match has higher precedence than If-Modified-Since; If-Match has higher precedence than If-Unmodified-Since.** Do not write a chain of if/else statements in an arbitrary order because it can return the wrong status or perform an update even though a precondition failed.

## 7. Spring WebFlux: creating responses with validators

In a functional endpoint, `ServerResponse` has builders to add ETag, Last-Modified, and cache policy.

Example of returning a resource:

```java
public Mono<ServerResponse> getBook(ServerRequest request) {
    int id = Integer.parseInt(request.pathVariable("id"));

    return repository.findById(id)
            .flatMap(book -> {
                String etag = "\"" + book.version() + "\"";
                Instant modified = book.updatedAt()
                        .truncatedTo(ChronoUnit.SECONDS);

                return ServerResponse.ok()
                        .eTag(etag)
                        .lastModified(modified)
                        .cacheControl(CacheControl.maxAge(
                                60, TimeUnit.SECONDS).cachePrivate())
                        .contentType(MediaType.APPLICATION_JSON)
                        .bodyValue(book);
            })
            .switchIfEmpty(ServerResponse.notFound().build());
}
```

This snippet requires `Book`, the repository, imports, and the corresponding route. `version()` must change whenever the corresponding representation changes. `updatedAt()` is a meaningful timestamp for the representation; the code normalizes to seconds to match HTTP-date.

`eTag` and `lastModified` on the response builder **set the validator headers**. To perform conditional evaluation, the handler must still use an appropriate helper or let a supported framework mechanism perform the comparison.

### 7.1. Using ServerWebExchange.checkNotModified

Spring WebFlux provides `ServerWebExchange.checkNotModified` to compare a resource's validators against the request's conditional headers. This method has overloads taking ETag, Last-Modified, or both. It prepares the status and response headers when the condition indicates there is no need to continue.

In WebFlux.fn, `ServerRequest.exchange()` provides the exchange bound to the request:

```java
public Mono<ServerResponse> getBook(ServerRequest request) {
    int id = Integer.parseInt(request.pathVariable("id"));

    return repository.findById(id)
            .flatMap(book -> {
                String etag = "\"" + book.version() + "\"";
                Instant modified = book.updatedAt()
                        .truncatedTo(ChronoUnit.SECONDS);

                if (request.exchange()
                        .checkNotModified(etag, modified)) {
                    return ServerResponse
                            .status(HttpStatus.NOT_MODIFIED)
                            .eTag(etag)
                            .lastModified(modified)
                            .build();
                }

                return ServerResponse.ok()
                        .eTag(etag)
                        .lastModified(modified)
                        .cacheControl(CacheControl.maxAge(
                                60, TimeUnit.SECONDS).cachePrivate())
                        .contentType(MediaType.APPLICATION_JSON)
                        .bodyValue(book);
            })
            .switchIfEmpty(ServerResponse.notFound().build());
}
```

This is an example for GET. When the cache condition is met, the helper returns true and the handler builds a 304 response with no body. If the not-modified condition is not met, the handler builds a 200 response with a body.

`ServerRequest.exchange()` is a low-level access path; the Javadoc warns that manipulating the exchange directly outside the normal request/response APIs can create inconsistent behavior. Here it only uses the conditional helper provided by Spring, without modifying the request/response itself or writing the body directly through the exchange.

### 7.2. Conditional update to prevent lost updates

Suppose two clients both read `book-v17`:

- Client A updates first; the resource moves to `book-v18`.
- Client B still holds `book-v17` and sends a PUT with `If-Match: "book-v17"`.
- The server compares against the current version and rejects B's request with `412`.

In WebFlux, the `checkNotModified` helper also supports preconditions for POST/PUT/DELETE. Conceptual example:

```java
public Mono<ServerResponse> updateBook(ServerRequest request) {
    int id = Integer.parseInt(request.pathVariable("id"));

    return repository.findById(id)
            .flatMap(current -> {
                String currentTag = "\"" + current.version() + "\"";
                Instant modified = current.updatedAt()
                        .truncatedTo(ChronoUnit.SECONDS);

                if (request.exchange()
                        .checkNotModified(currentTag, modified)) {
                    return ServerResponse
                            .status(HttpStatus.PRECONDITION_FAILED)
                            .build();
                }

                return request.bodyToMono(UpdateBook.class)
                        .flatMap(command ->
                                repository.updateIfVersion(
                                        id, current.version(), command))
                        .flatMap(updated ->
                                ServerResponse.ok()
                                        .eTag("\"" + updated.version() + "\"")
                                        .lastModified(updated.updatedAt()
                                                .truncatedTo(ChronoUnit.SECONDS))
                                        .bodyValue(updated));
            })
            .switchIfEmpty(ServerResponse.notFound().build());
}
```

This snippet requires the repository, DTO, and imports. `updateIfVersion` is the key part: the save operation must check the version in the same update statement or atomic transaction. Merely reading the version, checking the ETag in Java, and then updating afterward **is not enough** if another request can interleave between the two steps.

Example SQL for optimistic locking:

```sql
UPDATE books
SET title = ?, version = version + 1, updated_at = CURRENT_TIMESTAMP
WHERE id = ? AND version = ?;
```

If the number of updated rows is 0, either the version changed or the resource no longer exists. The repository needs to distinguish the two cases according to the application contract and return the appropriate error/status. ETag protects the HTTP protocol; the version condition at the database protects actual atomicity.

## 8. How should an ETag be generated?

### 8.1. Based on revision/version

If the database has a version column that increments every time the representation changes:

```java
static String etagFor(Book book) {
    return "\"" + book.version() + "\"";
}
```

This approach is cheap because it does not need to serialize and hash the entire body. However, it is only correct if the version changes for every change that can affect the chosen representation. If a DTO combines data from multiple tables, the version of one separate table may not be enough.

### 8.2. Based on hashing the representation

If a tag tied to the actual bytes is needed, you can hash the serialized representation:

```java
static String strongEtag(byte[] representation)
        throws NoSuchAlgorithmException {
    byte[] digest = MessageDigest.getInstance("SHA-256")
            .digest(representation);

    return "\"" + HexFormat.of().formatHex(digest) + "\"";
}
```

This is a Java 17+ snippet that requires imports. The hash must be computed on the exact representation the server chooses to send. If the response is compressed or transformed after computing the hash, ensure the validator still remains correct per the definition of a strong validator and content coding.

Hashing the body can be CPU-intensive and requires serializing before deciding 304. If a version or metadata is available, checking the validator with metadata can save work. However, the server still needs to retrieve enough state to know what the current representation is; 304 does not mean the request incurs no processing cost at all.

### 8.3. When to use a weak ETag?

If the server may change how it serializes or orders fields while the content remains equivalent at the application level, you can consider a weak ETag:

```http
ETag: W/"catalog-revision-17"
```

A weak tag is suitable for cache validation with `If-None-Match`, but do not use it to guarantee optimistic locking with `If-Match`. When you need to prevent lost updates, use a strong ETag or a version token with strong semantics.

## 9. Standalone Java 17+ program: precision of the two validators

The following example does not start an HTTP server. It illustrates how to build an ETag from a stable version and normalize Last-Modified to seconds. Actual conditional comparisons should be delegated to the HTTP framework or an RFC 9110-compliant implementation.

Structure:

```text
http-validator-demo/
└── src/demo/ValidatorDemo.java
```

File `src/demo/ValidatorDemo.java`:

```java
package demo;

import java.time.Instant;
import java.time.ZoneOffset;
import java.time.format.DateTimeFormatter;
import java.time.temporal.ChronoUnit;

public class ValidatorDemo {

    private static String etagForVersion(long version) {
        return "\"book-v" + version + "\"";
    }

    public static void main(String[] args) {
        Instant firstUpdate =
                Instant.parse("2025-04-15T10:15:30.100Z");
        Instant secondUpdate =
                Instant.parse("2025-04-15T10:15:30.800Z");

        Instant firstHttpDate =
                firstUpdate.truncatedTo(ChronoUnit.SECONDS);
        Instant secondHttpDate =
                secondUpdate.truncatedTo(ChronoUnit.SECONDS);

        String lastModified = DateTimeFormatter.RFC_1123_DATE_TIME
                .format(firstHttpDate.atZone(ZoneOffset.UTC));

        String oldTag = etagForVersion(17);
        String newTag = etagForVersion(18);

        System.out.println("old ETag: " + oldTag);
        System.out.println("new ETag: " + newTag);
        System.out.println("Last-Modified: " + lastModified);
        System.out.println("same-second dates equal: "
                + firstHttpDate.equals(secondHttpDate));
        System.out.println("version tags differ: "
                + !oldTag.equals(newTag));
    }
}
```

Compile and run with JDK 17+ from the directory containing `src`:

```bash
javac -d out src/demo/ValidatorDemo.java
java -cp out demo.ValidatorDemo
```

**Exact standard output:**

```text
old ETag: "book-v17"
new ETag: "book-v18"
Last-Modified: Tue, 15 Apr 2025 10:15:30 GMT
same-second dates equal: true
version tags differ: true
```

Explanation:

1. Two updates occurred at two different times within the same second.
2. When converted to HTTP-date, both timestamps become `10:15:30 GMT`.
3. The version-based ETag changes from 17 to 18, so the two versions can still be distinguished.
4. The program only illustrates validator generation; it does not parse `If-None-Match` or implement the precondition algorithm itself. Do not use a simple string comparison in a demo to replace RFC logic.

## 10. Testing conditional requests

An endpoint with validators should be tested on both the initial response and conditional requests.

### 10.1. Initial GET

Use `curl`:

```bash
curl -i http://localhost:8080/books/42
```

Check:

- Status `200 OK`.
- `ETag` and/or `Last-Modified` is present.
- `Content-Type` is correct.
- `Cache-Control` fits public or private data.
- Body is the expected representation.

### 10.2. GET with the current ETag

```bash
curl -i \
  -H 'If-None-Match: "book-v17"' \
  http://localhost:8080/books/42
```

If the ETag is still `"book-v17"`, expect `304 Not Modified` and no body. If the resource has moved to version 18, expect `200` with the new representation and ETag.

### 10.3. GET with Last-Modified

```bash
curl -i \
  -H 'If-Modified-Since: Tue, 15 Apr 2025 10:15:30 GMT' \
  http://localhost:8080/books/42
```

If there is no change newer than that point in time and the request does not contain If-None-Match, the server can return 304. Remember the one-second precision.

### 10.4. PUT with If-Match

```bash
curl -i -X PUT \
  -H 'If-Match: "book-v17"' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Reactive HTTP in Practice"}' \
  http://localhost:8080/books/42
```

If the current version is 17 and the update is valid, the request can succeed and the resource advances its version. If the current version is already 18, expect `412 Precondition Failed` and no overwrite of newer data.

### 10.5. WebTestClient

In Spring WebFlux tests, `WebTestClient` can verify status and headers:

```java
webTestClient.get()
        .uri("/books/42")
        .exchange()
        .expectStatus().isOk()
        .expectHeader().exists("ETag")
        .expectHeader().exists("Last-Modified");

webTestClient.get()
        .uri("/books/42")
        .header("If-None-Match", "\"book-v17\"")
        .exchange()
        .expectStatus().isNotModified()
        .expectBody().isEmpty();
```

This snippet requires a `WebTestClient` bound to the router/controller and a fixture with the corresponding version. In real tests, obtain the ETag from the first response and reuse it, rather than hardcoding the tag if the fixture changes.

Test additionally:

- A non-matching ETag must return the new body and status 200.
- If-Modified-Since is ignored when If-None-Match is present.
- A non-matching If-Match returns 412 and does not call repository update.
- A weak ETag does not satisfy the strong comparison of If-Match.
- Concurrent updates cannot bypass optimistic locking in the database.
- 304 has no body but still has the necessary metadata.
- Variant representations have the right ETag and Vary.
- Responses containing personal data are not unintentionally stored by shared caches.

## 11. Common mistakes

1. **Treating ETag as the resource ID.** ETag represents a version of a representation, not necessarily the record's ID.
2. **Using the same strong ETag for different representations.** If JSON, XML, language, or content coding produces different bytes, the tag must match the representation or a semantic weak validator must be used.
3. **Using a weak ETag for If-Match.** If-Match requires strong comparison; a weak tag does not protect against lost updates.
4. **Comparing ETags yourself with equals.** If-None-Match supports lists, wildcards, and weak comparison. Use framework helpers or an RFC-compliant implementation.
5. **Sending only Last-Modified even though the resource changes multiple times per second.** HTTP-date has one-second resolution; consider ETag.
6. **Not normalizing timestamps.** Comparing sub-second timestamps directly against HTTP-date can produce wrong results; normalize to seconds when generating the validator.
7. **Not updating the ETag when the representation changes.** Clients may receive a wrong 304 and keep using stale data.
8. **Building an ETag from a single version column that does not cover the entire representation.** A DTO may combine data from multiple sources; any change affecting the body must change the validator.
9. **Treating 304 as a 200-style response with an empty body.** 304 has its own semantics; the client reuses its stored representation.
10. **Returning 304 for PUT when If-Match fails.** An unsafe method with a failed precondition usually receives 412.
11. **Ignoring precedence between If-None-Match and If-Modified-Since.** When If-None-Match is present, ignore If-Modified-Since.
12. **Checking version then updating non-atomically.** Another request may interleave an update in between; use optimistic locking or a version-conditioned update statement.
13. **Using ETag as authorization.** Knowing a tag does not prove the caller has permission to read or modify a resource.
14. **Using a max-age that is too long for rapidly changing data.** Caches may use a fresh response without revalidating; choose freshness based on business requirements.
15. **Confusing no-cache and no-store.** no-cache allows storing but requires revalidation; no-store instructs not to store.
16. **Setting public cache for personal responses.** Per-user/tenant data needs an appropriate cache policy and Vary.
17. **Computing an expensive body hash on every request.** If reliable version metadata exists, use metadata to avoid re-serializing/hashing the entire payload.
18. **Assuming Spring automatically generates an ETag for every response.** The application needs to provide a validator or configure an appropriate mechanism; do not assume every WebFlux endpoint already has an ETag.
19. **Using a file's Last-Modified while forgetting the content is assembled from multiple files.** One file's timestamp does not adequately represent a composite representation.
20. **Ignoring clock errors and timestamp sources.** Clock skew or wrong timestamps can cause caches to serve stale data; ETag is usually more stable when an accurate version exists.

## 12. Checklist review API

Before enabling conditional requests for a resource, confirm:

- **Representation:** Which exact variant does the ETag represent? Is there content negotiation, compression, or user-specific content?
- **Validator strength:** Is strong or weak needed? Is it guaranteed that the same strong tag means identical representation data?
- **ETag generation:** Is the tag derived from a version, revision, or hash? Does every change affecting the body change the tag?
- **Last-Modified:** Is the timestamp from a reliable source? Is it normalized to one-second resolution?
- **Cache policy:** Do max-age, private/public, and no-cache/no-store match the data requirements?
- **GET/HEAD:** Do If-None-Match and If-Modified-Since return 304 properly?
- **Update/delete:** Do If-Match and If-Unmodified-Since prevent lost updates?
- **Precedence:** Does If-None-Match take precedence over If-Modified-Since? Does If-Match take precedence over If-Unmodified-Since?
- **Atomicity:** Does the database update check the version atomically?
- **Status:** Are 304, 412, and 428 properly distinguished according to the API contract?
- **Headers:** Does 304 have appropriate metadata? Does the response have Vary when needed?
- **Security:** Could caches inadvertently share private data across users or tenants?
- **Tests:** Have matching/non-matching tags, weak/strong, same-second updates, concurrent updates, and representation variants been tested?
- **Observability:** Can 304/412 statuses and cache revalidation rates be logged without leaking data?

**Key takeaway:** `ETag` identifies a representation version; `Last-Modified` describes the modification time with one-second precision. `If-None-Match` and `If-Modified-Since` help caches avoid re-downloading the body; `If-Match` and `If-Unmodified-Since` help clients protect updates against overwriting newer changes. Use strong/weak comparison properly, follow precondition precedence, and use atomic optimistic locking in the database. In Spring WebFlux, you can set validators with `ServerResponse`/`ResponseEntity` and use `ServerWebExchange.checkNotModified` to handle conditional requests according to HTTP semantics.
