# Bridge Methods, Interface Methods, and Implementation Methods in Spring AOP

## 1. Lesson goal

A Spring bean may be accessed through an **interface**, implement logic in an **implementation class**, and use **generic types**. When using Spring AOP, a simple call like `processor.process("spring")` can involve three different `java.lang.reflect.Method` objects:

1. **The interface method** exposed by a JDK dynamic proxy.
2. **The concrete method on the implementation** executing the business logic.
3. **The synthetic bridge method** generated by the Java compiler to preserve overriding after generic type erasure.

They can share the same name yet differ in **declaring class**, **parameter types**, **return type**, **annotations**, and the `isBridge()` flag. If advice reads only `MethodSignature.getMethod()` and assumes it is always the implementation method, annotation lookup or metadata selection easily breaks.

After this lesson, you can:

- Clearly distinguish **interface method**, **implementation method**, and **bridge method** in the context of Spring AOP.
- Explain why the Java compiler generates a bridge for `Processor<T>` and `TextProcessor implements Processor<String>`.
- Understand how JDK dynamic proxies differ from CGLIB in exposing methods and what can appear in `MethodSignature`.
- Use **`AopUtils.getMostSpecificMethod(Method, Class<?>)`** to locate the corresponding method on the target class, and **`BridgeMethodResolver.findBridgedMethod(Method)`** when unwrapping a bridge is needed.
- Build an **`@Around` Spring aspect** that records method information accurately without assuming reflection signatures always come from the implementation.
- Inspect annotations placed on interfaces vs. implementations without falsely claiming every proxy style returns identical metadata.
- Spot risks of duplicate logging/advice, incorrect pointcut matches, type erasure, self-invocation, and methods missing from the proxy interface.

**Scope:** Focuses on **proxy-based Spring Framework AOP** and how Spring handles method metadata at a method-execution join point. It does not go into Java generics or standalone AspectJ weaving beyond what is needed to understand Spring Aspects.

## 2. Three commonly encountered signature layers

Java example:

~~~java
public interface Processor<T> {
    T process(T input);
}

public class TextProcessor implements Processor<String> {
    @Override
    public String process(String input) {
        return input.trim();
    }
}
~~~

These are **two top-level types, placed in two separate Java files** to compile, and are not yet the full Spring AOP application from section 7.

In source code, we see:

- Interface: `T process(T input)`.
- Implementation: `String process(String input)`.

Due to **type erasure**, however, the runtime signature of the generic interface corresponds to the erased type:

~~~text
Processor.process(Object) : Object
~~~

In the implementation there is the real method:

~~~text
TextProcessor.process(String) : String
~~~

So that a call through the erased interface still dispatches properly to the overridden method, the compiler may generate an additional bridge equivalent to:

~~~java
// Pseudocode representing compiler-generated bytecode;
// do not insert this directly into TextProcessor.java.
public Object process(Object input) {
    return process((String) input);
}
~~~

A bridge method is a **synthetic method in the class file**, not an application-authored method. For instance, it can be reflected as `Method.isBridge() == true` and `Method.isSynthetic() == true`. The real implementation method `process(String)` does not carry the bridge flag.

Diagram:

~~~text
Processor<String> proxy (JDK interface)
      |
      +-- process(Object) on interface after erasure
      |
      v
Spring AOP invocation
      |
      v
TextProcessor target
      |
      +-- bridge process(Object) (generated by javac)
      |       |
      |       +-- casts String argument and calls
      |           process(String)
      |
      +-- process(String) (actual business method)
~~~

This diagram is a **mental model of signatures**, not a requirement that every Spring invocation invokes both methods through reflection in that exact sequence. Spring AOP can **resolve the specific/bridge method** before selecting advisors and invoking the target. Do not infer that two advice executions happen just because a bridge method exists.

## 3. Why do bridge methods exist?

Java generics are largely implemented via **type erasure**. Before erasure, `Processor<String>.process(String)` looks like a method taking and returning `String`. After erasure, the interface bytecode must support `process(Object)`, while the implementation declares `process(String)`.

If the compiler did not maintain a call path compatible with the erased interface method, Java polymorphism would break when callers hold a generic interface reference. Bridges solve that.

Distinction:

| Property | Interface method | Implementation method | Bridge method |
| --- | --- | --- | --- |
| Example | `Processor.process(Object)` | `TextProcessor.process(String)` | `TextProcessor.process(Object)` |
| Origin | Generic interface definition | Written by developer | Generated by compiler |
| `getDeclaringClass()` | `Processor.class` | `TextProcessor.class` | `TextProcessor.class` |
| Runtime parameter | `Object` | `String` | `Object` |
| Runtime return | `Object` | `String` | `Object` |
| `isBridge()` | `false` | `false` | **`true`** |
| `isSynthetic()` | Usually `false` | Usually `false` | **`true`** in `javac` examples |
| Annotation on implementation | Does not automatically carry it | Present if declared | Do not treat bridge annotations as source of truth |

Do not copy/match only method names and guess generic parameters. When a method has overloads or a hierarchy, `getName()` alone cannot distinguish:

~~~java
String process(String input);
String process(String input, int limit);
~~~

The key is using **type + signature + target class** to resolve the exact method.

## 4. Spring AOP works via proxies, not bytecode weaving

Spring AOP wraps a Spring-managed target with a proxy:

~~~text
Caller
  |
  v
JDK proxy or CGLIB proxy
  |
  +-- Advisor / pointcut
  +-- matching @Before, @Around, @After...
  |
  v
Target method
~~~

Two main proxy kinds:

### 4.1. JDK dynamic proxy

When the target has an interface and configuration selects a JDK proxy, the object received by callers implements the proxied interfaces. Callers typically write:

~~~java
Processor<String> processor = /* Spring-injected proxy */;
processor.process("hello");
~~~

The proxy **is not an instance of `TextProcessor`**. Never cast a JDK proxy to the concrete class:

~~~java
// May throw ClassCastException if the bean is a JDK dynamic proxy.
TextProcessor concrete = (TextProcessor) processor;
~~~

The method returned by `MethodSignature.getMethod()` during a JDK proxy invocation **may be the method on the interface**, not the method annotated by the application in the implementation. Consequently, interface metadata can differ from target metadata.

### 4.2. Class-based CGLIB proxy

When `@EnableAspectJAutoProxy(proxyTargetClass = true)` is configured or the target lacks a suitable interface, Spring can use a CGLIB class-based proxy.

The proxy subclasses the target and can override eligible methods. However:

- `final` classes cannot be proxied by subclassing.
- `private`/`final` methods cannot be advised by overriding.
- Methods not visible for subclass overriding, such as package-private methods in a superclass from another package, may not be advised.
- Self-invocation on the target still bypasses the Spring proxy.
- Bridge/synthetic methods may exist in the target class, but a bridge should not be treated as a separate business operation to advise a second time.

**Enabling CGLIB does not eliminate compiler-generated bridge methods**, nor does it guarantee `MethodSignature.getMethod()` always carries the annotation you need. When reading metadata, the durable solution is resolving the target method explicitly.

### 4.3. Distinguishing JDK proxy and target

Useful helpers:

~~~java
AopUtils.isAopProxy(bean);
AopUtils.isJdkDynamicProxy(bean);
AopUtils.isCglibProxy(bean);
AopUtils.getTargetClass(bean);
~~~

Here `getTargetClass(bean)` returns the real target class when the framework can determine it. It does **not** mean unwrapping every custom proxy across all systems. `pjp.getTarget()` inside advice points to the current target, while `pjp.getThis()` represents the Spring AOP proxy.

## 5. `MethodSignature` and limitations to understand

In `@Around` advice, you can retrieve metadata:

~~~java
MethodSignature signature =
        (MethodSignature) pjp.getSignature();

Method invokedMethod = signature.getMethod();
~~~

`MethodSignature` belongs to `org.aspectj.lang.reflect`; Spring AOP supplies join point information under that contract. With a JDK proxy, `invokedMethod` typically describes the interface method; with CGLIB or other generic cases, declaring class and bridge status may differ.

**Never assume**:

~~~java
// Wrong assumption: method from signature is always the method declared
// directly in TextProcessor and always carries the implementation's annotation.
Method method = ((MethodSignature) pjp.getSignature()).getMethod();
boolean marked = method.isAnnotationPresent(TrackedOperation.class);
~~~

If the annotation appears only on `TextProcessor.process(String)`, checking `Processor.process(Object)` can return `false`.

Two distinct objects:

- **Invoked method**: the method exposed by the AOP invocation/signature at the proxy boundary.
- **Most-specific target method**: the corresponding implementing method on the target class, suitable for finding implementation metadata.

Do not conclude that `getMethod().getDeclaringClass()` alone gives you the concrete implementation type.

## 6. Two important Spring APIs

### 6.1. `AopUtils.getMostSpecificMethod`

~~~java
Method resolved = AopUtils.getMostSpecificMethod(
        invokedMethod,
        targetClass
);
~~~

This API belongs to `org.springframework.aop.support.AopUtils`. It finds the method on the target class corresponding to the supplied method, such as resolving `Processor.process(Object)` to `TextProcessor.process(String)` when generic bridges are resolved.

It is especially helpful when looking up:

- Custom annotations placed on the implementation method.
- The exact target method signature for auditing/metrics.
- The specific method whose generic return/parameter types are bound.
- Where business logic is actually defined in a class hierarchy.

In Spring Framework 6.2.x, this helper handles **bridge resolution**; thus you do not need to assume it returns a bridge. If you want to be explicit for readers, calling `BridgeMethodResolver.findBridgedMethod(...)` on the result is still safe.

### 6.2. `BridgeMethodResolver.findBridgedMethod`

~~~java
Method bridged =
        BridgeMethodResolver.findBridgedMethod(candidate);
~~~

This API belongs to `org.springframework.core.BridgeMethodResolver`. If `candidate` is a bridge method, Spring tries to find the **corresponding original method**. If it is not a bridge, the API returns the input method; calling `isBridge()` beforehand is unnecessary.

**Limitation:** `findBridgedMethod` resolves only within the class declaring `candidate`; it **cannot infer the full implementation** from an interface method alone without the target class. Therefore you normally need:

~~~java
Method declared =
        ((MethodSignature) pjp.getSignature()).getMethod();

Class<?> targetClass = pjp.getTarget().getClass();

Method specific =
        AopUtils.getMostSpecificMethod(declared, targetClass);

Method original =
        BridgeMethodResolver.findBridgedMethod(specific);
~~~

This pattern handles cases where the proxy method is an interface/generic bridge and you need annotations on the implementation. It does not automatically solve every problem of **annotation inheritance, interface annotation composition, or meta-annotations**; those cases require pairing with an appropriate Spring merged-annotation strategy.

### 6.3. Why not call `getDeclaredMethod` directly?

The following snippet is error-prone:

~~~java
targetClass.getDeclaredMethod(
    invokedMethod.getName(),
    invokedMethod.getParameterTypes()
);
~~~

If `invokedMethod` is `Processor.process(Object)` while the business implementation declares `process(String)`, the call above can return the bridge `process(Object)` or fail, depending on class/compiler/hierarchy. When the annotation sits on `process(String)`, reading directly from the bridge misses the goal.

`AopUtils.getMostSpecificMethod` and `BridgeMethodResolver` were designed by Spring specifically for these cases.

### 7.3. `Processor.java`

~~~java
package demo;

public interface Processor<T> {
    T process(T input);
}
~~~

At runtime, `Processor<T>.process(T)` is erased to a method taking and returning `Object`. The source-level generic type parameter does not force the Java reflection method to have a `String` parameter.

### 7.4. `TrackedOperation.java`

~~~java
package demo;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface TrackedOperation {
}
~~~

The marker annotation is declared with runtime retention and method target. In this example it is placed **only on the implementation method**; it is deliberately omitted from the interface to distinguish metadata from the two places.

### 7.5. `TextProcessor.java`

~~~java
package demo;

import java.util.Locale;
import org.springframework.stereotype.Service;

@Service
public class TextProcessor implements Processor<String> {

    @TrackedOperation
    @Override
    public String process(String input) {
        System.out.println("TARGET process(String)");
        return input.trim().toUpperCase(Locale.ROOT);
    }
}
~~~

Two points:

1. `@Service` registers the implementation as a Spring bean via component scanning.
2. `@TrackedOperation` sits on `process(String)`, not on the generic interface `process(Object)`.

With `javac`, the Java compiler generates a bridge so the implementation satisfies the erased interface contract. You do not need to write any bridge manually in source.

### 7.6. `TraceAspect.java`

~~~java
package demo;

import java.lang.reflect.Method;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.reflect.MethodSignature;
import org.springframework.aop.support.AopUtils;
import org.springframework.core.BridgeMethodResolver;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class TraceAspect {

    @Around("execution(* demo.Processor+.process(..))")
    public Object trace(ProceedingJoinPoint pjp) throws Throwable {
        MethodSignature signature =
                (MethodSignature) pjp.getSignature();

        Method interfaceOrProxyMethod = signature.getMethod();

        Method specific = AopUtils.getMostSpecificMethod(
                interfaceOrProxyMethod,
                pjp.getTarget().getClass()
        );

        Method original = BridgeMethodResolver.findBridgedMethod(specific);

        boolean annotationOnImplementation =
                original.isAnnotationPresent(TrackedOperation.class);

        System.out.println(
                "ADVICE process annotationOnImpl=" +
                annotationOnImplementation);

        return pjp.proceed();
    }
}
~~~

How to read this:

- `@Aspect` declares the advice; `@Component` registers the aspect bean.
- The pointcut `execution(* demo.Processor+.process(..))` selects matching method executions belonging to `Processor` or its subtypes/implementations, within Spring AOP boundaries.
- `signature.getMethod()` yields the method exposed by the AOP invocation. **Do not jump to the conclusion that it is always the implementation method.**
- `AopUtils.getMostSpecificMethod` uses the **target class** to find the concrete method.
- `BridgeMethodResolver.findBridgedMethod` ensures that if the candidate is a bridge, we get the original method.
- `original.isAnnotationPresent` checks annotations **placed directly** on the original method. For custom composed/meta-annotations or annotations on interfaces, use a lookup approach matching your requirements.
- `pjp.proceed()` is called exactly once, returning the original result and letting the target execute. The advice **does not invoke** `TextProcessor.process` directly, so it does not break the interceptor chain.

`@Around` is one convenient advice type for inspecting signatures; with `@Before`, you can use `JoinPoint` and cast the signature similarly, without `proceed()`.

### 7.8. `App.java`: inspecting interface, bridge, and target methods

~~~java
package demo;

import java.lang.reflect.Method;
import java.util.Arrays;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.core.BridgeMethodResolver;

public class App {

    private static String describe(Method method) {
        return method.getDeclaringClass().getSimpleName()
                + "." + method.getName()
                + "("
                + Arrays.stream(method.getParameterTypes())
                        .map(Class::getSimpleName)
                        .reduce((a, b) -> a + "," + b)
                        .orElse("")
                + ")";
    }

    public static void main(String[] args) throws Exception {
        try (var context =
                     new AnnotationConfigApplicationContext(AppConfig.class)) {

            @SuppressWarnings("unchecked")
            Processor<String> processor =
                    (Processor<String>) context.getBean(Processor.class);

            System.out.println(
                    "IS_PROXY " + AopUtils.isAopProxy(processor));
            System.out.println(
                    "IS_JDK_PROXY " +
                    AopUtils.isJdkDynamicProxy(processor));

            Method interfaceMethod =
                    Processor.class.getMethod("process", Object.class);

            Method bridge = Arrays.stream(
                        TextProcessor.class.getDeclaredMethods())
                    .filter(Method::isBridge)
                    .filter(m -> m.getName().equals("process"))
                    .findFirst()
                    .orElseThrow();

            Method specific = AopUtils.getMostSpecificMethod(
                    interfaceMethod,
                    TextProcessor.class
            );

            Method bridged = BridgeMethodResolver.findBridgedMethod(bridge);

            System.out.println(
                    "INTERFACE_METHOD " + describe(interfaceMethod));
            System.out.println("BRIDGE_PRESENT " + bridge.isBridge());
            System.out.println("SPECIFIC_METHOD " + describe(specific));
            System.out.println(
                    "BRIDGED_METHOD " + describe(bridged));

            System.out.println(
                    "ANNOTATION_ON_INTERFACE " +
                    interfaceMethod.isAnnotationPresent(
                            TrackedOperation.class));
            System.out.println(
                    "ANNOTATION_ON_IMPL " +
                    bridged.isAnnotationPresent(
                            TrackedOperation.class));

            String result = processor.process("  spring  ");
            System.out.println("RESULT " + result);
        }
    }
}
~~~

Here:

- `Processor.class.getMethod("process", Object.class)` retrieves the erased method on the generic interface.
- `TextProcessor.class.getDeclaredMethods()` finds the compiler-generated bridge; **filter by `isBridge()` instead of trusting reflection order**.
- `AopUtils.getMostSpecificMethod` takes the interface method and concrete target class; here it resolves to `TextProcessor.process(String)`.
- `BridgeMethodResolver.findBridgedMethod(bridge)` traces back to the original method backed by the bridge.
- `describe` prints a concise signature without random proxy class names, keeping output stable.
- The caller uses the `Processor<String>` interface bean, **without casting the JDK proxy to `TextProcessor`**.

Run in the directory containing `pom.xml`:

~~~bash
mvn -q clean compile exec:java
~~~

## 8. Experiment: switching `proxyTargetClass` to CGLIB

In `AppConfig.java`, replace:

~~~java
@EnableAspectJAutoProxy(proxyTargetClass = false)
~~~

with:

~~~java
@EnableAspectJAutoProxy(proxyTargetClass = true)
~~~

This is a **one-line configuration experiment**, without creating a second `AppConfig`.

When starting the new context:

- Spring can use a **CGLIB class-based proxy** for `TextProcessor`.
- `AopUtils.isAopProxy(processor)` is still expected to be `true`.
- `AopUtils.isJdkDynamicProxy(processor)` is expected to be `false`.
- `AopUtils.isCglibProxy(processor)` will be `true` if CGLIB is actually used.
- The class-based proxy can still expose the `Processor` interface for callers invoking via the interface.
- The bridge method in the class file still exists; changing proxy mode does not remove type erasure from Java generics.
- The `Method` represented by `MethodSignature.getMethod()` may differ in declaring-class details compared to a JDK proxy; **most-specific method resolution logic is still needed**.

Avoid claiming that `proxyTargetClass = true` makes Spring advise `private`, `final`, or self-invoked methods. Proxy limitations still apply.

## 9. Annotations on interface vs. implementation: where to decide?

With `Processor<T>` and `TextProcessor implements Processor<String>`, a marker placed on the interface method may **not be directly present** on the implementation method; the reverse is also true. Java's `@Inherited` does not make method annotations inherited across overrides. When using raw reflection, you must know whether you hold the `Method` of the interface, the implementation, or a bridge.

This affects `@annotation(...)` pointcuts: Spring can resolve methods during matching, whereas calling `isAnnotationPresent(...)` on `MethodSignature.getMethod()` does not automatically replicate all framework semantics. When an annotation involves a generic interface, test both JDK/CGLIB proxies and especially **the method resolved past any bridge**. Never treat a bytecode bridge as an independent business method just because reflection exposes it.

## 10. When merged annotation metadata is needed

The ordered path for reading metadata is: take the method from `MethodSignature`, find the **most-specific target method** with `AopUtils.getMostSpecificMethod`, resolve any bridge with `BridgeMethodResolver.findBridgedMethod`, and then choose a **raw annotation** or **merged/meta-annotation** policy using the appropriate Spring APIs. Finding the method and finding the annotation serve different purposes; `@annotation(...)` pointcuts must also be verified with real advice invocations.

The lesson **Reading Annotations on the Right Method When the Target Is a Proxy** thoroughly covers lookup across interfaces, implementations, superclasses, and composed annotations. The focus here is compiler bridges and identifying **one logical method** per proxy call.

## 11. Bridge methods are not business overloads

Java source code lets developers write overloads:

~~~java
String process(String input);
String process(String input, int limit);
~~~

However, bridge methods are compiler-generated artifacts to support overriding/generics or covariant returns, not overloads intentionally added by the team.

| Concept | Created by | Why does it exist? | Should it be treated as a separate business operation? |
| --- | --- | --- | --- |
| Overload `process(String,int)` | Developer | Multiple API variants with different parameter lists | Yes, if business logic distinguishes them |
| Override `process(String)` | Developer | Implements generic interface contract | Yes, it is the target logic |
| Bridge `process(Object)` | Compiler | Preserves overriding after type erasure | Typically **no** |
| JDK proxy method `Processor.process(Object)` | Interface/proxy contract | Provides the proxy's invocation entry point | Same logical operation as the target |

Do not log audits twice just because reflection returns both `process(String)` and `process(Object)`. When scanning methods to build metadata yourself, filter out bridge/synthetic methods purposefully or resolve to the bridged method and deduplicate by logical signature. Avoid blindly filtering out all synthetic methods if the framework relies on other special methods.

In **Spring AOP**, a call `processor.process("x")` through a proxy is in principle one logical proxy invocation; the compiler generating a bridge does not by itself cause two advice calls for the same pointcut. If you observe two logs, first check for **multiple matching advisors**, actual double invocations, or multiple proxy layers.

## 12. Generics, erasure, and pointcut expressions

An expression such as:

~~~text
execution(* demo.Processor+.process(..))
~~~

is well suited for selecting a method family by name/type without depending on erased generic parameter details.

If writing an expression binding a specific parameter, understand:

- `Processor<T>` undergoes erasure; the interface method has runtime parameter `Object`.
- The implementation `TextProcessor.process(String)` has its own signature.
- Spring's AspectJ pointcut matcher can resolve target/bridged methods.
- An expression inspecting an interface/generic hierarchy should not be evaluated merely by matching `Method.toString()` strings.

If you need to select "every implementation of `Processor<String>` but not `Processor<Integer>`", Java erasure makes matching **generic type arguments** by simple method patterns unreliable. Consider explicit bean types, custom annotations, a dedicated contract, or inspecting type metadata with Spring `ResolvableType`; write integration tests proving match behavior.

**Do not use `args(java.lang.String)` as if it were an overload selector on declared parameter types**: `args` checks the runtime argument type, whereas `execution` checks the method execution signature. A target declaring `process(Object)` can still receive a `String` instance at runtime.

## 13. Passing `JoinPoint` parameters and reading `MethodSignature` safely

Inside advice, beyond `getMethod()` you can observe:

~~~java
Object[] arguments = pjp.getArgs();
Object proxy = pjp.getThis();
Object target = pjp.getTarget();

MethodSignature signature =
        (MethodSignature) pjp.getSignature();

String methodName = signature.getName();
Class<?> declaringType = signature.getDeclaringType();
~~~

This is a **fragment inside `@Around`**, without full imports and context. Understand:

- `getArgs()` describes the invocation's arguments; runtime argument types can differ from the declared signature due to inheritance.
- `getThis()` is the proxy providing the AOP invocation.
- `getTarget()` is the target object.
- `getDeclaringType()` is not automatically `target.getClass()` with a JDK proxy.
- `getName()` is only the name; it does not distinguish overloads or generic bridges.
- `MethodSignature.getMethod()` is the entry point for resolving the exact target method, not proof that an annotation exists on the implementation.
- If an aspect matches other join point types in an AspectJ weaving environment, do not unconditionally cast every signature to `MethodSignature`; Spring AOP itself handles only method-execution join points.

When altering arguments via `pjp.proceed(Object[])`, match the exact count and types; never use generic erasure as an excuse to pass an incompatible runtime type. A bridge can cast `Object` to `String`, so passing the wrong type can cause a `ClassCastException` along the execution path.

## 14. Pointcut matches interface, yet method exists only on implementation

Consider a service:

~~~java
public interface OrderApi {
    void place();
}

public class OrderService implements OrderApi {
    @Override
    public void place() {
    }

    public void internalReport() {
    }
}
~~~

These two types must be in **two separate Java files** if both are public. This is a boundary-illustrating fragment, not the main runnable project.

If the bean is proxied by a **JDK dynamic proxy** for `OrderApi`, callers cannot invoke `internalReport()` through `OrderApi` because the method is not in the proxy contract. The expression:

~~~text
execution(* demo.OrderService.internalReport(..))
~~~

cannot make that method appear on the JDK proxy interface. If you truly need to advise that method:

- Consider adding the method to an appropriate public interface.
- Or use a **CGLIB class-based proxy** if the class/method can be overridden.
- Or refactor into another Spring bean with an explicit API.

Bridge resolution is a **method metadata** concern; it cannot overcome a proxy's method-exposure limits.

## 15. Self-invocation still bypasses Spring AOP

If `TextProcessor.process(String)` calls another method on the same target via `this.helper()`, that internal call does not go back through the proxy, so advice on `helper()` does not apply along that path.

~~~java
public String process(String input) {
    return this.normalize(input);
}

public String normalize(String input) {
    return input.trim();
}
~~~

This is an **illustrative fragment**, not a replacement for the example's `TextProcessor.java` since annotations and imports are omitted. Even though `normalize` has a clear signature and Spring can resolve the method, `this.normalize` inside the target creates no new invocation passing through the proxy.

Do not confuse two questions:

1. **Can Spring resolve the right method?** Involves bridges, interfaces, target methods, and pointcuts.
2. **Does the call pass through the proxy?** Involves self-invocation, JDK/CGLIB, and bean lifecycle.

Resolving the method properly **does not guarantee advice will run** if the caller bypasses the proxy.

## 16. Common errors and resolutions

| Symptom | Common cause | How to check |
| --- | --- | --- |
| `getMethod().getAnnotation(...)` returns null | `getMethod()` is the interface method | Resolve target method with `AopUtils.getMostSpecificMethod` |
| Got `process(Object)` instead of `process(String)` | Method from generic interface or compiler bridge | Use `BridgeMethodResolver` and target class |
| Reflection scan sees two same-named methods | Both implementation method and compiler-generated bridge exist | Check `isBridge()`, `isSynthetic()`, and parameter types |
| Advice logs twice | Multiple advisors/calls/proxy layers, not necessarily the bridge | Count proxy invocations; inspect advisor chain |
| Casting Spring proxy to concrete implementation fails | Proxy is a JDK dynamic proxy | Inject/use the interface; consider CGLIB when needed |
| `@annotation` does not match under one proxy config | Annotation placement or method resolution differs | Test interface/implementation metadata in a real context |
| Interface method lacks annotation while implementation has it | Raw reflection checked the wrong place | Resolve the most-specific target method |
| Generic type is `String` yet reflection returns `Object` | Type erasure on the generic interface | Inspect `getGenericParameterTypes()` and `ResolvableType` when needed |
| Spring does not advise implementation-only method | JDK proxy does not expose that method | Add API to interface or adjust architecture/proxy |
| Spring does not advise `private`/`final` method | Class-based proxy cannot override it | Change entrypoint / interceptable design |
| Advice does not run when target calls method internally | Self-invocation bypasses proxy | Extract bean / call through Spring-managed dependency |
| `getDeclaredMethod` fails | Used erased interface parameter types against implementation | Use `AopUtils.getMostSpecificMethod` |
| `ClassCastException` when calling generic bridge | Runtime argument incompatible with `String` | Ensure typed caller/proceed arguments match |
| Annotation scan misses meta-annotations | Raw reflection does not search composed annotations | Consider `AnnotatedElementUtils` / merged metadata |
| Spring context creates no AOP proxy | Aspect is not a bean, AOP is off, or no matching advisor | Check `@Component`, `@Aspect`, `@EnableAspectJAutoProxy` |

## 17. Checklist for implementing a Spring Aspect on a generic interface

1. Identify whether the advised method sits on the **interface**, implementation, or both.
2. Is the bean registered in the Spring `ApplicationContext`?
3. Is the aspect a Spring bean and is AOP infrastructure enabled?
4. Is the actual proxy JDK or CGLIB? Use `AopUtils.isJdkDynamicProxy`/`isCglibProxy`.
5. On which class is the `Method` from `MethodSignature.getMethod()` declared?
6. Is there a bridge method? Check with `Method.isBridge()`.
7. If implementation annotations are needed, did you resolve `AopUtils.getMostSpecificMethod` with the target class?
8. If the candidate is a bridge, did you find the bridged method?
9. Are meta-annotations/hierarchies required? If so, use Spring annotation utilities matching your policy.
10. Does the pointcut match **one logical business operation** as intended?
11. Could another advisor, overload, interface default method, or inherited method change the advice count?
12. Is the method exposed on the JDK proxy interface or interceptable by CGLIB?
13. Does the caller go through the proxy instead of `new`/`this.method()`?
14. Are there integration tests covering JDK proxy, CGLIB (if supported), and key annotation placements?
15. Did you verify output under the runtime and compiler your application deploys on, rather than guessing reflection order?

## 18. Self-assessment questions

**1. Why can `Processor<String>.process(String)` appear as `process(Object)` in bytecode?**

Because type erasure turns the generic interface method into an erased signature, and the compiler may generate a bridge to preserve overriding.

**2. What does `Method.isBridge()` indicate?**

It indicates the method is marked as a compiler-generated bridge; it does not mean it is a separate business operation.

**3. With a JDK proxy, is `MethodSignature.getMethod()` always the implementation method?**

No. It may be the method declared on the interface. Resolve the target method when you need implementation metadata.

**4. Which Spring API is commonly used to find the implementation method from an interface `Method`?**

`AopUtils.getMostSpecificMethod(method, targetClass)`.

**5. Which API is used to find the original method when given a bridge?**

`BridgeMethodResolver.findBridgedMethod(bridgeMethod)`.

**6. Must you check `isBridge()` before calling `findBridgedMethod`?**

No; the Spring API accepts non-bridge methods and returns them as-is.

**7. If an annotation is only on the implementation, does raw reflection on the interface method see it?**

No. You must inspect the concrete method or use an appropriate Spring annotation lookup strategy.

**8. Why does switching from JDK proxy to CGLIB not make bridge methods disappear?**

A bridge is an artifact of the Java compiler in the class file, not an object created solely by JDK proxies.

**9. Does having a bridge method make Spring AOP run `@Around` twice?**

No. A bridge does not by itself constitute two client proxy invocations. If advice runs twice, investigate the call path and advisors.

**10. If a method exists only on the implementation, can a JDK proxy client call it directly?**

No, if the method does not belong to an interface exposed by the JDK proxy.

**11. Is `@annotation` identical to `MethodSignature.getMethod().isAnnotationPresent` in every case?**

No. Spring method matching and annotation resolution can consider target/bridge hierarchies, whereas raw reflection reads annotations only on that exact `Method`.

**12. Does resolving bridges properly fix self-invocation bypassing the proxy?**

No. Method metadata resolution and proxy invocation boundaries are two independent concerns.

**Conclusion:** With generic interfaces in Spring AOP, the **interface method, concrete implementation method, and compiler bridge method** can represent the same logical operation while carrying different metadata. Whenever advice needs to inspect implementation annotations or signatures, start from `MethodSignature`, identify the **target class**, and use **`AopUtils.getMostSpecificMethod`** and **`BridgeMethodResolver.findBridgedMethod`** where appropriate. Always remember as well: Spring AOP is **proxy-based**; even when the method is resolved accurately, advice runs only when the invocation actually passes through the proxy and an advisor matches.
