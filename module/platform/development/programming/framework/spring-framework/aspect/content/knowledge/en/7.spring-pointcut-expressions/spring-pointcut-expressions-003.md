# `this` and `target` in Spring AOP's Proxy Model

## 1. The Core Problem

In **Spring AOP**, a client call enters Spring's **proxy**. The proxy selects the matching interceptors/advice and ultimately, if the advice chain proceeds, delegates the call to the **target object** executing the business logic. Because the proxy and the target play two different roles, Spring pointcuts distinguish:

- **`this(Type)`:** a condition on the **Spring AOP proxy object** receiving the call. The join point matches when the proxy can be considered an instance of `Type`.
- **`target(Type)`:** a condition on the **target object** standing behind the proxy. The join point matches when the target is an instance of `Type`.

This is the meaning of these two **pointcut designators** in Spring AOP, not a general explanation of the Java `this` keyword. In pure AspectJ weaving, the two designators can have different semantics because there is no Spring AOP proxy layer sitting in between. This lesson focuses only on **Spring Framework and Spring AOP**.

Picture this:

```text
Caller bean
    |
    | Spring injects a bean reference
    v
+-------------------------+
| Spring AOP proxy        | <-- this(Type)
|  - JDK proxy or CGLIB   |
|  - advisor chain        |
+-------------------------+
    |
    | proceed() / delegate
    v
+-------------------------+
| Target object           | <-- target(Type)
| PaymentServiceImpl      |
| business method()       |
+-------------------------+
    |
    v
Result / exception returns to proxy and caller
```

The very same `pay()` call can satisfy `target(PaymentServiceImpl)` yet **not satisfy** `this(PaymentServiceImpl)` if the proxy is a JDK dynamic proxy. This is the most important difference when using `this` and `target` in Spring pointcuts.

## 2. Distinguishing Proxy, Target, Interface, and Implementation

Consider an interface and implementation:

```java
package demo;

public interface PaymentService {
    String pay(String id);
}

public class PaymentServiceImpl implements PaymentService {
    @Override
    public String pay(String id) {
        return "PAID:" + id;
    }
}
```

The two declarations above are illustrative code and must be placed into their corresponding Java files if run standalone. We assume Spring creates an AOP proxy for `PaymentServiceImpl` because matching advice exists.

### Case A: JDK Dynamic Proxy

A JDK proxy implements `PaymentService`, but is **not a subclass of `PaymentServiceImpl`**:

```text
JDK-generated proxy  -- implements --> PaymentService
        |
        | dispatch advice + delegate
        v
PaymentServiceImpl target  -- implements --> PaymentService
```

In a call through a JDK AOP proxy:

- `this(PaymentService)`: **matches**, because the proxy implements the interface.
- `this(PaymentServiceImpl)`: **does not match**, because the JDK proxy does not extend the implementation.
- `target(PaymentService)`: **matches**, because the target implements the interface.
- `target(PaymentServiceImpl)`: **matches**, because the actual object belongs to the implementation class.

### Case B: CGLIB Class-Based Proxy

A CGLIB proxy generated by Spring is a **runtime subclass of the target class**:

```text
CGLIB-generated subclass  -- extends --> PaymentServiceImpl
        |
        | dispatch advice + delegate
        v
PaymentServiceImpl target -- implements --> PaymentService
```

With a valid target/proxy as above:

- `this(PaymentService)`: **matches**, because the subclass also implements the interface.
- `this(PaymentServiceImpl)`: **matches**, because the proxy is a subtype of the implementation.
- `target(PaymentService)`: **matches**, because the target implements the interface.
- `target(PaymentServiceImpl)`: **matches**, because the target belongs to the implementation.

| Pointcut on method `pay()` | JDK Spring AOP proxy | CGLIB Spring AOP proxy |
| --- | --- | --- |
| `this(demo.PaymentService)` | Matches | Matches |
| `this(demo.PaymentServiceImpl)` | Does not match | Matches |
| `target(demo.PaymentService)` | Matches | Matches |
| `target(demo.PaymentServiceImpl)` | Matches | Matches |

The table assumes a single `PaymentServiceImpl` target, an interceptable public method, a matching advisor, and a caller **calling through the Spring proxy**. With other targets, proxies exposing additional interfaces, nested proxies, or special mechanisms, verify at runtime.

## 3. `this` in a Spring Pointcut DIFFERS from the Java `this` Keyword

These two lines do not carry the same meaning:

```java
// Java: reference to the instance currently executing this method
this.otherMethod();

// Pointcut: selects method execution where the AOP proxy is an instance of PaymentService
@Before("execution(* demo..*.pay(..)) && this(demo.PaymentService)")
public void before() {
    System.out.println("advice");
}
```

The block above is an **illustration**, combining syntax from two different places; the `@Before` method must reside in a Spring-managed `@Aspect` bean with proper imports.

- **Java `this` inside a target method:** is the target instance executing the business method. A `this.otherMethod()` call from here **usually does not go back through the proxy**, so it does not trigger advice on `otherMethod()` via Spring AOP.
- **Spring AOP `this(Type)` designator:** constrains/inspects the **proxy object** at a method execution join point intercepted by Spring.
- **`JoinPoint.getThis()`:** provides the proxy object corresponding to the Spring AOP meaning of `this` in a pointcut.
- **`JoinPoint.getTarget()`:** provides the target object corresponding to the meaning of `target`.

In a normal call through a proxy, `joinPoint.getThis() == joinPoint.getTarget()` returns `false`. The Spring AOP model separates the proxy object and the target even when a CGLIB proxy extends the target class.

With Spring AOP, **self-invocation** still bypasses the proxy, even when using CGLIB; switching `proxyTargetClass=true` does not automatically turn `this.otherMethod()` inside the target into a new proxy call.

## 4. At Which Step Are `this(Type)` / `target(Type)` Applied?

A pointcut such as:

```java
@Around("execution(* demo..*.pay(..)) && target(demo.PaymentServiceImpl)")
public Object around(ProceedingJoinPoint pjp) throws Throwable {
    return pjp.proceed();
}
```

is used by Spring to identify matching **method execution join points** in calls **going through the proxy**. `execution(...)` checks the method signature and scope; `target(...)` constrains the target object type. They act as two logical conditions combined with `&&`.

A corresponding expression using `this`:

```java
@Around("execution(* demo..*.pay(..)) && this(demo.PaymentServiceImpl)")
public Object aroundImplProxy(ProceedingJoinPoint pjp) throws Throwable {
    return pjp.proceed();
}
```

When the bean is AOP-proxied by JDK, the `this(demo.PaymentServiceImpl)` condition is not satisfied, even though target `PaymentServiceImpl` has method `pay()` and the client calls it through the interface. When the same bean uses a CGLIB proxy, the condition can be satisfied because the proxy subclasses `PaymentServiceImpl`.

**Important:** a pointcut that only matches a type without a call going through a proxy will not make Spring "remotely intercept" a manually `new`-ed object or a `this.foo()` call inside the target. The two designators are **conditions on join points that Spring AOP can already intercept**, not mechanisms that replace proxies.

### Do Not Use `target(...)` Like `execution(...)`

`target(Type)` only states that the target instance satisfies the type; it does not state which methods you want to advise. Combine it with a specific method condition and package scope:

```java
@Before("execution(public * demo.service..*.*(..)) && target(demo.service.PaymentService)")
public void auditPaymentCall() {
    // record matching service calls
}
```

This is a **snippet** requiring classes in the `demo.service` package, an `@Aspect` bean, and a matching Spring context. The pointcut is scoped more clearly than applying `target(...)` to every method on the target.

The aspect uses **one `@Around` advice** matching `perform()`, then directly observes `ProceedingJoinPoint.getThis()` and `getTarget()`. Because there is only one advice and one target method execution, stdout has a clear order.

```java
package demo;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;
import org.springframework.context.annotation.Import;

public class ThisTargetDemo {

    public interface TaskApi {
        String perform(String input);
    }

    public static class TaskService implements TaskApi {
        @Override
        public String perform(String input) {
            System.out.println("TARGET perform " + input);
            return "DONE:" + input;
        }
    }

    @Aspect
    public static class TraceAspect {
        @Around("execution(* demo..*.perform(..))")
        public Object trace(ProceedingJoinPoint pjp) throws Throwable {
            Object proxy = pjp.getThis();
            Object target = pjp.getTarget();

            System.out.println("THIS_IS_API=" + (proxy instanceof TaskApi));
            System.out.println("THIS_IS_IMPL=" + (proxy instanceof TaskService));
            System.out.println("TARGET_IS_API=" + (target instanceof TaskApi));
            System.out.println("TARGET_IS_IMPL=" + (target instanceof TaskService));
            System.out.println("SAME_OBJECT=" + (proxy == target));

            return pjp.proceed();
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class SharedBeans {
        @Bean
        public TaskApi taskApi() {
            return new TaskService();
        }

        @Bean
        public TraceAspect traceAspect() {
            return new TraceAspect();
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy(proxyTargetClass = false)
    @Import(SharedBeans.class)
    public static class JdkConfig {
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy(proxyTargetClass = true)
    @Import(SharedBeans.class)
    public static class CglibConfig {
    }

    private static void inspect(String label, TaskApi bean) {
        System.out.println(label + "_AOP=" + AopUtils.isAopProxy(bean));
        System.out.println(label + "_JDK=" + AopUtils.isJdkDynamicProxy(bean));
        System.out.println(label + "_CGLIB=" + AopUtils.isCglibProxy(bean));
    }

    public static void main(String[] args) {
        try (var context =
                new AnnotationConfigApplicationContext(JdkConfig.class)) {
            TaskApi bean = context.getBean(TaskApi.class);
            System.out.println("=== JDK ===");
            inspect("JDK", bean);
            System.out.println("RESULT=" + bean.perform("A"));
        }

        try (var context =
                new AnnotationConfigApplicationContext(CglibConfig.class)) {
            TaskApi bean = context.getBean(TaskApi.class);
            System.out.println("=== CGLIB ===");
            inspect("CGLIB", bean);
            System.out.println("RESULT=" + bean.perform("B"));
        }
    }
}
```

Run from the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

```text

JDK_AOP=true
JDK_JDK=true
JDK_CGLIB=false
THIS_IS_API=true
THIS_IS_IMPL=false
TARGET_IS_API=true
TARGET_IS_IMPL=true
SAME_OBJECT=false
TARGET perform A
RESULT=DONE:A
=== CGLIB ===
CGLIB_AOP=true
CGLIB_JDK=false
CGLIB_CGLIB=true
THIS_IS_API=true
THIS_IS_IMPL=true

```

In both contexts, `SharedBeans.taskApi()` still returns `TaskApi` and constructs `new TaskService()`. Only the proxy creation strategy changes:

- In the JDK context, `pjp.getThis()` is a JDK proxy, so `THIS_IS_IMPL=false`.
- In the CGLIB context, `pjp.getThis()` is a subclass proxy, so `THIS_IS_IMPL=true`.
- In both contexts, `pjp.getTarget()` is `TaskService`, so `TARGET_IS_IMPL=true`.
- `SAME_OBJECT=false` illustrates that the proxy and target are two different objects under the standard Spring AOP setup in the example.

Although the two proxy types differ, calls through the proxy are still intercepted by the `@Around` advice and `pjp.proceed()` forwards the call to the target method. The program does not need to know the runtime-generated proxy class name.

## 6. Using `this(...)` and `target(...)` Directly in Pointcuts

Below are **standalone pointcut illustrations**; do not add them simultaneously to one aspect if you want to keep section 5's stdout intact.

### 6.1. Filtering by the Interface Exposed by the Proxy

```java
@Before("execution(* demo..*.perform(..)) && this(demo.TaskApi)")
public void onlyApiProxyCalls() {
    System.out.println("THIS(TaskApi)");
}
```

In an application with a top-level interface `demo.TaskApi`, this matches under both JDK and CGLIB if the proxy exposes `TaskApi`. If using an interface nested inside a class like the section 5 example, the nested type name syntax in the AspectJ expression must be adjusted to valid Java/AspectJ naming; do not copy this top-level snippet verbatim and assume that type already exists.

### 6.2. Filtering by the Target's Implementation Class

```java
@Before("execution(* demo..*.perform(..)) && target(demo.TaskService)")
public void onlyTaskTargetCalls() {
    System.out.println("TARGET(TaskService)");
}
```

This condition matches under both proxy strategies if the target is actually `demo.TaskService`. The class name here is an **illustrative top-level type**; the runnable project in section 5 defines nested type `ThisTargetDemo.TaskService`.

### 6.3. Condition Where JDK and CGLIB Produce Different Results

```java
@Before("execution(* demo..*.perform(..)) && this(demo.TaskService)")
public void onlyImplSubtypeProxyCalls() {
    System.out.println("THIS(TaskService)");
}
```

With target `TaskService implements TaskApi` and the proxy strategies described, the advice is satisfied only when **the proxy is a subtype of `TaskService`**, i.e., the CGLIB case. In JDK dynamic proxy mode, the client can call `perform()` via the interface, yet the `this(TaskService)` pointcut does not match.

**Do not generalize mechanically:** if a Spring proxy exposes other interfaces, the target is a different subclass, or scoped proxies or stacked proxy layers are used, verify the actual runtime and target types before concluding.

## 7. Binding Proxy and Target to Advice Parameters

Spring supports a **binding form** of both designators using parameter names, allowing advice to receive the matching object:

```java
@Aspect
@Component
public class BindingAspect {

    @Before(
        value = "execution(* demo..*.perform(..)) && this(proxy)",
        argNames = "proxy"
    )
    public void beforeProxy(TaskApi proxy) {
        // proxy is the bound Spring AOP proxy reference.
    }

    @Before(
        value = "execution(* demo..*.perform(..)) && target(service)",
        argNames = "service"
    )
    public void beforeTarget(TaskService service) {
        // service is the bound target object.
    }
}
```

This is an **illustrative sample requiring appropriate top-level types and imports/scanning**, not a standalone runnable class. Meaning:

- `this(proxy)` paired with parameter `TaskApi proxy` binds proxies compatible with `TaskApi`.
- `target(service)` paired with parameter `TaskService service` binds targets compatible with `TaskService`.
- Names in the expression must match the parameter names recognized by Spring; `argNames` avoids relying on whether the compiler preserved parameter names.
- The parameter received by the advice is the **actual object** supplied by Spring AOP; it is not a copy of the target's state.

If you only need to inspect type info or arguments at the join point, you can use `ProceedingJoinPoint.getThis()` and `getTarget()` as in section 5. If you want to express the constraint clearly at the pointcut level, use `this(Type)` and `target(Type)`.

### Note on JDK Proxies and Injection Types

If an advice uses `this(proxy)` while declaring a concrete implementation parameter type, a JDK proxy is **not** an instance of the implementation and the condition will not match. Conversely, `target(service)` with an implementation parameter type can match because the target object has that exact type.

Do not cast `pjp.getThis()` to an implementation class when the program allows JDK dynamic proxies. Use interfaces for callers and binding parameters that must work across both strategies.

## 8. Distinguishing `this`/`target` from Other Designators

In Spring AOP, the expressions below have different meanings:

| Designator | Match basis | Usage example |
| --- | --- | --- |
| `this(Type)` | **Type of the proxy object** | Advise only when the proxy is an instance of an interface |
| `target(Type)` | **Type of the target object** | Advise beans whose target belongs to an implementation/base type |
| `execution(...)` | **Method execution signature** | Advise only `pay(..)` methods in the service package |
| `within(TypePattern)` | **Declaring type falls within pattern scope** | Restrict method execution by package/class |
| `args(Type)` | **Runtime type of passed arguments** | Select invocations whose arguments belong to a type |
| `@annotation(Annotation)` | **Annotation on matching method execution** | Select methods annotated with a specific annotation |
| `@target(Annotation)` | **Annotation on the target class per matcher** | Select targets whose class carries an annotation |
| `@within(Annotation)` | **Annotation on the declaring type of matching method execution** | Select executions within types carrying an annotation |

Two easily confused pairs:

- **`target(Type)` and `@target(Annotation)`:** the former checks the Java type relationship of the target object; the latter checks annotations.
- **`this(Type)` and `within(TypePattern)`:** the former inspects the proxy instance; the latter restricts the declaring-type location used by the pointcut matcher.

Expressions like `call(...)`, `get(...)`, and `set(...)` belong to broader AspectJ pointcuts, but **are not supported by Spring AOP proxies to intercept method call sites or field reads/writes**. Spring AOP focuses on *method execution join points* invoked through proxies.

A practical expression combining the responsibilities of each designator:

```java
@Around(
    "execution(public * demo..service..*Service.*(..)) " +
    "&& target(demo.service.PaymentService)"
)
public Object profile(ProceedingJoinPoint pjp) throws Throwable {
    long start = System.nanoTime();
    try {
        return pjp.proceed();
    } finally {
        System.out.println("elapsedNs=" + (System.nanoTime() - start));
    }
}
```

This is a **sample method**, not a standalone runnable program. It uses `execution` to restrict the method and `target` to restrict the target type; returns/exceptions from `proceed()` propagate back to the caller. Timing values depend on the environment, so there is no fixed stdout.

## 9. Self-Invocation and Two Different Concepts of `this`

Suppose Spring has created a proxy for the bean:

```java
public class PaymentServiceImpl implements PaymentService {

    @Override
    public String pay(String id) {
        return save(id);
    }

    public String save(String id) {
        System.out.println("TARGET save " + id);
        return "OK:" + id;
    }
}
```

This illustrates one method calling another method **on the same target object**. If a client calls `proxy.pay("A")`, advice for `pay()` can run. However, when target `pay()` runs, the call `save(id)`—equivalent to `this.save(id)`—is a Java call inside the target and does not return to the Spring AOP proxy. Advice matching only `save()` will not run along this internal call path.

```text
Client --> proxy.pay()
              |
              v
          advice(pay)
              |
              v
          target.pay()
              |
              | Java this.save()
              v
          target.save()
       (does not go through proxy a second time)
```

Here:

- **Pointcut `this(Type)`** is evaluated when Spring AOP processes a join point passing through the proxy.
- **Java `this`** inside `target.pay()` is the target instance executing the method.
- Even if the target's subtypes/types overlap with proxy class-related types, the `this.save()` call path does not automatically add a proxy boundary.

If an interceptor is needed for `save()` when called from `pay()`, the straightforward approach is to **extract `save()` into another Spring bean and inject that bean**; the caller then invokes a separate Spring proxy. Techniques exist for calling back into the proxy via self-reference or `AopContext.currentProxy()` with `exposeProxy=true`, but they couple code to Spring AOP and require careful design consideration.

## 10. When Should You Choose `this`, and When `target`?

**Choose `this(Type)` when the condition genuinely depends on the type of object Spring provided to the client.** For example, restricting advice to a proxy implementing an `ExternalApi` interface. This fits thinking in terms of the **proxy contract**. Note that changing configuration from JDK → CGLIB can alter the match result of a pointcut bound to an implementation class via `this(Implementation)`.

**Choose `target(Type)` when the condition should follow the class/type of the business object.** For example, advising only Spring beans whose target implements `PaymentService` or belongs to `PaymentServiceImpl`, regardless of proxy strategy. Even so, advice still runs only at method executions that the proxy can intercept.

**Do not use them interchangeably just because they look alike on CGLIB.** On a CGLIB proxy, many `this(Type)` and `target(Type)` conditions both return true, but when configuration switches to JDK proxies, differences can surface and stop advice from running.

For a service layer, pointcuts are generally easier to maintain when combining **method execution scope** with an appropriate **target type or interface contract**. If the intent is simply "methods in a set of packages", `execution(...)` or `within(...)` can express it more directly than overusing `this(...)`.

## 11. Special Cases and Limitations

### 11.1. Non-Proxied Beans

Not every Spring bean has an AOP proxy. Simply declaring `@Aspect` or `@EnableAspectJAutoProxy` is not enough to turn **every bean** into a proxy. Spring must detect a matching advisor and create the proxy. If a client holds the target directly without going through AOP, there is no Spring AOP interception on that call path.

### 11.2. CGLIB Cannot Intercept Every Method

CGLIB generates a subclass, so it cannot override `final` or `private` methods, and cannot subclass a `final class`. Do not assume that because `this(Implementation)` matches, every method on the implementation can be advised.

### 11.3. JDK Proxies Do Not Expose Methods Outside Interfaces

A JDK proxy implements configured/exposed interfaces. A public method present only on the implementation and not on the proxied interface generally cannot be called by clients through the JDK proxy's implementation type. `target(Implementation)` matching the real object **does not expand the JDK proxy API**.

### 11.4. Scoped Proxies, Nested Proxies, and Dynamic TargetSource

The lesson example uses a simple singleton target auto-proxied once. Spring can also use scoped proxies, nested proxies, or dynamic target sources; in those cases, **the target object may change per invocation**, proxy layers may differ, and you must verify which proxy you are inspecting.

Helpers like `AopUtils.getTargetClass(bean)` help identify the target class of a Spring AOP proxy in normal scenarios, but `bean.getClass()` alone should not be used to infer all proxy/target relationships in complex setups.

### 11.5. `@Aspect` Beans Advising Themselves

A Spring `@Aspect` bean is managed by the container to supply pointcuts/advice, but Spring AOP auto-proxying normally excludes aspect beans from target auto-proxying. Therefore, do not expect `this(AspectClass)` or `target(AspectClass)` to cause another aspect to intercept methods on that `@Aspect` bean itself.

### 11.6. Type Names in Pointcuts Can Differ from Java Nested-Type Syntax

In the sample project, `TaskApi` and `TaskService` are declared as nested types of `ThisTargetDemo`. When writing pointcut expressions using **qualified type names**, follow AspectJ's type-pattern syntax for nested types. The `demo.TaskApi` / `demo.TaskService` snippets in sections 6–7 intentionally illustrate two **top-level** types to avoid attaching a non-existent name to the runnable project. If you want to test directly with the section 5 project, move the types into top-level files or use the exact type names and test with the pointcut parser.

## 12. Workflow for Debugging a `this` / `target` Pointcut That Does Not Run

1. **Obtain the bean from the Spring context**, do not manually `new` an object to compare results.
2. **Confirm it is an AOP proxy** using `AopUtils.isAopProxy(bean)`.
3. **Identify the proxy kind** using `AopUtils.isJdkDynamicProxy(bean)` and `isCglibProxy(bean)`.
4. **Check the runtime object** using `bean instanceof Api`, `bean instanceof Impl`, or `type.isInstance(bean)`.
5. **Find the target class** using `AopUtils.getTargetClass(bean)`. The proxy class and target class may differ.
6. **Check the pointcut** to ensure `execution(...)` matches method/visibility/package before evaluating `this/target`.
7. **Check the `this(Type)` condition**: is `Type` actually an interface/subtype of the **proxy**?
8. **Check the `target(Type)` condition**: is the target object behind the proxy actually an instance of `Type`?
9. **Check the call path**: self-invocation, objects outside Spring, and non-interceptable methods cannot be rescued by changing designators.
10. **Check the effective context/proxy strategy**: plain Spring Framework defaults and Spring Boot auto-configuration can use different strategies; rely on runtime checks, not just a single property.

A helpful log inside an `@Around` advice:

```java
Object proxy = pjp.getThis();
Object target = pjp.getTarget();

System.out.println("proxyClass=" + proxy.getClass().getName());
System.out.println("targetClass=" + target.getClass().getName());
System.out.println("sameReference=" + (proxy == target));
```

This is an **additional snippet**, requiring `pjp` from an advice. Class names depend on runtime; in automated programs, assert with `instanceof` and `AopUtils` rather than hardcoding generated proxy names.

## 13. Self-Check

**Question 1.** Target `InvoiceServiceImpl implements InvoiceService`, Spring AOP uses a JDK proxy. Does `this(InvoiceServiceImpl)` match a public method already intercepted by the proxy?  
**Answer:** No, because the proxy object is not a subtype of the implementation. `target(InvoiceServiceImpl)` matches when the target has that type.

**Question 2.** The same bean is switched to a CGLIB proxy. Can `this(InvoiceServiceImpl)` match?  
**Answer:** Yes, because the CGLIB proxy subclasses the implementation class, provided the method and pointcut are eligible.

**Question 3.** Are `pjp.getThis()` and `pjp.getTarget()` the same object in a standard Spring AOP example?  
**Answer:** No. `getThis()` is the AOP proxy; `getTarget()` is the target object behind the proxy.

**Question 4.** Can self-invocation be fixed by writing `target(Implementation)` instead of `this(Implementation)`?  
**Answer:** No. Self-invocation does not enter the Spring proxy for the pointcut to be evaluated on the internal call.

**Question 5.** The target implements interface `PaymentApi` and the JDK proxy implements `PaymentApi`. Do `this(PaymentApi)` and `target(PaymentApi)` differ in meaning?  
**Answer:** Yes. Although both may match, `this` inspects the proxy, while `target` inspects the target.

**Question 6.** Is `@target(Audited)` the same as `target(Audited)`?  
**Answer:** No. `@target` inspects an annotation on the target class; `target` inspects Java type relationships.

**Question 7.** A Spring bean has no AOP proxy; calling a method directly where the target class matches `target(MyType)`. Does Spring AOP automatically run advice?  
**Answer:** No. There must be a call that Spring AOP actually intercepts through an eligible proxy.

**Question 8.** A `final` class has a business interface and is proxied with JDK; can `target(FinalImplementation)` match?  
**Answer:** Possibly, because the target still belongs to that class while the proxy is a JDK object implementing the interface. Do not assume a final target class makes JDK proxying completely impossible.
