# Distinguishing Proxy Class, Target Class, and Declared Bean Type in Spring AOP

## 1. Why Distinguish All Three Types?

In a Spring application, a bean may be declared with an interface, instantiated from a concrete class, yet the object clients receive from `ApplicationContext` belongs to **a proxy class generated at runtime**. These concepts serve different roles:

1. **Declared bean type:** the type appearing in the bean definition, such as the `PaymentService` return type of a `@Bean` method. Spring uses this declared information for type prediction, determining injection candidates, and processing before the bean is instantiated.
2. **Target class:** the class of the real object that executes business logic after Spring AOP lets interceptors proceed with the call, such as `PaymentServiceImpl`.
3. **Proxy class:** the runtime class of the object returned by Spring to clients when the bean is AOP-proxied, such as a JDK dynamic proxy class or a CGLIB subclass generated at runtime.

Do not assume these three types are the same merely because they represent the same bean name. **The declared type does not choose the proxy mechanism by itself; the runtime proxy class is not necessarily the target class; and the client's injection type is also a separate concept.**

This lesson focuses on **Spring AOP proxy-based interception**, the container, `@Bean`, and Java dependency injection. It does not expand into general Aspect principles or AspectJ weaving.

## 2. Example of One Bean Having Three Types

Suppose there is an interface and an implementation:

```java
public interface PaymentService {
    String pay(String orderId);
}

public class PaymentServiceImpl implements PaymentService {
    @Override
    public String pay(String orderId) {
        return "PAID:" + orderId;
    }
}
```

Registering the Spring bean:

```java
@Configuration
public class PaymentConfig {
    @Bean
    public PaymentService paymentService() {
        return new PaymentServiceImpl();
    }
}
```

These are illustrative declaration snippets; section 5 has a runnable project. From the two snippets above:

- `PaymentService` is **the declared type** in the `@Bean` signature.
- `PaymentServiceImpl` is **the target class** created by the `@Bean` method.
- If Spring AOP applies advice to the bean, the reference consumers receive will be **a proxy**: that reference's runtime class may differ from both types above.

```text
@Bean PaymentService paymentService()
           |
           | declared bean type: PaymentService
           v
    Spring BeanFactory
           |
           | invokes factory method
           v
  new PaymentServiceImpl()
           |
           | target class: PaymentServiceImpl
           v
   Spring AOP auto-proxy
          / \
         /   \
        v     v
   JDK proxy   CGLIB proxy
   implements  extends
   interface   implementation
        \       /
         \     /
          v   v
  Client receives bean reference,
  calls pay() via proxy then to target
```

**Important note:** Spring can run a `BeanPostProcessor` after creating the object from `@Bean` to replace the object supplied to consumers with a proxy. Thus, the `@Bean` method may actually return the implementation while `context.getBean(...)` returns a proxy.

## 3. Comparison by Proxy Type

Same target `PaymentServiceImpl implements PaymentService` with a matching Spring AOP advisor:

| Property | JDK dynamic proxy | CGLIB class-based proxy |
| --- | --- | --- |
| Runtime proxy class | Class generated by JDK, implementing exposed interfaces | Runtime subclass of the target class |
| Target class | `PaymentServiceImpl` | `PaymentServiceImpl` |
| Example `@Bean` return type | `PaymentService` | `PaymentService` |
| `bean instanceof PaymentService` | `true` | `true` |
| `bean instanceof PaymentServiceImpl` | `false` | `true` |
| `bean.getClass() == PaymentServiceImpl.class` | `false` | `false` |
| `AopUtils.isJdkDynamicProxy(bean)` | `true` | `false` |
| `AopUtils.isCglibProxy(bean)` | `false` | `true` |
| `AopUtils.getTargetClass(bean)` | `PaymentServiceImpl.class` | `PaymentServiceImpl.class` |

In the table, the bean **has already been proxied by Spring AOP**. If no advisor matches, the bean may be returned directly as `PaymentServiceImpl`, in which case proxy-related outcomes change.

### 3.1. JDK Proxy Has the Interface, Not the Implementation

With a JDK dynamic proxy, Spring creates an object implementing the exposed interfaces. Therefore:

```java
PaymentService service = context.getBean(PaymentService.class);
// Compatible with the JDK proxy's interface.

// Never assume the following cast is always valid:
PaymentServiceImpl impl = (PaymentServiceImpl) service;
```

When `service` is an actual JDK proxy, the cast line typically throws `ClassCastException`. The fact that the target behind the proxy is `PaymentServiceImpl` **does not make the proxy a subtype of the implementation**.

### 3.2. CGLIB Proxy Extends the Target Class

With CGLIB, Spring creates a subclass to intercept overridable methods:

```text
PaymentServiceImpl             <- target class
        ^
        | extends
        |
Generated CGLIB proxy class    <- proxy runtime class
        |
        +-- intercepts call via advisor chain
        |
        +-- delegates to target PaymentServiceImpl instance
```

For a CGLIB proxy, `instanceof PaymentServiceImpl` is `true`, yet `proxy.getClass() == PaymentServiceImpl.class` is still `false`. These two checks answer **two different questions**: inheritance relationship vs. exact runtime class.

A Spring AOP proxy holds a separate target object in standard configurations. Therefore, once the target executes a method and calls `this.otherMethod()`, the internal call does not return to the proxy, even when the proxy is a CGLIB subclass.

## 4. Declared Bean Type Differs from Injection Point Type

Look again at a factory method:

```java
@Bean
PaymentService paymentService() {
    return new PaymentServiceImpl();
}
```

At least two things are easily confused:

- **Return type `PaymentService`:** information in the bean definition. Before the singleton is instantiated, Spring typically uses this type to predict candidates for `@Autowired` or `getBeanNamesForType(...)`.
- **Actual object `new PaymentServiceImpl()`:** fully known only when the factory method runs. Afterwards, Spring can apply an AOP proxy.

For the client:

```java
@Service
class CheckoutService {
    private final PaymentService paymentService;

    CheckoutService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

This is an illustrative Spring DI snippet requiring corresponding imports. The constructor parameter here is **the injection point type**. When the injection type is an interface, both matching JDK and CGLIB AOP proxies can be injected.

If the constructor instead requests `PaymentServiceImpl`, two **separate** conditions must be considered:

1. Does BeanFactory recognize this bean as a candidate for the implementation type at dependency resolution time? A `@Bean` return type declaring an interface can limit type prediction before the singleton exists.
2. Is **the final object** assignable to the implementation? A JDK proxy **is not** a `PaymentServiceImpl`; a CGLIB proxy is a subclass of `PaymentServiceImpl` when created successfully.

Declaring `@Bean PaymentServiceImpl paymentService()` provides more specific type prediction info, **but does not force AOP to pick CGLIB**. If AOP still selects a JDK proxy, the final bean reference cannot be cast to `PaymentServiceImpl`.

## 5. Complete Program: Same Target, Two Proxy Types

The example uses **Java 17+, Maven, Spring Framework 6.2.19**. Two contexts are created sequentially and completely independently:

- `JdkConfig` enables `@EnableAspectJAutoProxy(proxyTargetClass=false)`.
- `CglibConfig` enables `@EnableAspectJAutoProxy(proxyTargetClass=true)`.
- Both contexts import the same `SharedBeans`; the `@Bean` method returns the interface type, while the implementation is a concrete class.
- `TraceAspect` advises before `deliver()` so Spring actually needs to create an AOP proxy.

### 5.2. File src/main/java/demo/BeanTypeDemo.java

```java
package demo;

import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;
import org.springframework.context.annotation.Import;

public class BeanTypeDemo {

    public interface MessageService {
        String deliver(String id);
    }

    public static class MessageServiceImpl implements MessageService {
        @Override
        public String deliver(String id) {
            System.out.println("TARGET deliver " + id);
            return "ACK:" + id;
        }
    }

    @Aspect
    public static class TraceAspect {
        @Before("execution(* demo..*.deliver(..))")
        public void beforeCall() {
            System.out.println("ADVICE deliver");
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class SharedBeans {
        @Bean
        public MessageService messageService() {
            return new MessageServiceImpl();
        }

        @Bean
        public TraceAspect traceAspect() {
            return new TraceAspect();
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy(proxyTargetClass = false)
    @Import(SharedBeans.class)
    public static class JdkConfig {
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy(proxyTargetClass = true)
    @Import(SharedBeans.class)
    public static class CglibConfig {
    }

    static void inspect(String label, Object bean) {
        System.out.println(label + " aop=" + AopUtils.isAopProxy(bean));
        System.out.println(label + " jdk="
                + AopUtils.isJdkDynamicProxy(bean));
        System.out.println(label + " cglib="
                + AopUtils.isCglibProxy(bean));
        System.out.println(label + " proxy-is-impl="
                + (bean instanceof MessageServiceImpl));
        System.out.println(label + " target="
                + AopUtils.getTargetClass(bean).getSimpleName());
    }

    public static void main(String[] args) {
        try (var jdk =
                new AnnotationConfigApplicationContext(JdkConfig.class)) {
            MessageService bean = jdk.getBean(MessageService.class);
            inspect("JDK", bean);
            System.out.println("JDK result=" + bean.deliver("A"));
        }

        try (var cglib =
                new AnnotationConfigApplicationContext(CglibConfig.class)) {
            MessageService bean = cglib.getBean(MessageService.class);
            inspect("CGLIB", bean);
            System.out.println("CGLIB result=" + bean.deliver("B"));
        }
    }
}
```

Run in the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

```text

JDK cglib=false
JDK proxy-is-impl=false
JDK target=MessageServiceImpl
ADVICE deliver
TARGET deliver A
JDK result=ACK:A
CGLIB aop=true
CGLIB jdk=false
CGLIB cglib=true
CGLIB proxy-is-impl=true
CGLIB target=MessageServiceImpl
ADVICE deliver
```

### 5.3. Reading the Results

In **both contexts**, `SharedBeans.messageService()` declares return type `MessageService` and creates target `MessageServiceImpl`. Yet:

- **JDK context:** `isJdkDynamicProxy=true`, the proxy object is not an instance of `MessageServiceImpl`; calling the method through the interface still runs advice.
- **CGLIB context:** `isCglibProxy=true`, the proxy is a subclass of `MessageServiceImpl`; the proxy object is an instance of the implementation in Java's type system.
- **Both:** `getTargetClass(bean)` returns `MessageServiceImpl` and advice runs on `deliver()`.

The proxy selection mechanism changes without changing the `@Bean` signature at all. At the same time, a proxy using an interface does not mean the target class turned into an interface.

### 5.4. Experiment Changing the Declared Type

Change just one method in `SharedBeans`:

```java
@Bean
public MessageServiceImpl messageService() {
    return new MessageServiceImpl();
}
```

This is a **replacement version**, not declared alongside the old one in the same context. The declared type becomes more specific, helping type prediction by implementation. However, if `JdkConfig` still uses a JDK proxy, `MessageServiceImpl` is still not the runtime proxy's type. If the application injects the implementation, it can fail after post-processing. You must inspect both the bean declaration **and** the effective proxy type.

## 6. At Which Points Does Spring Infer a Bean's Type?

In real applications, the question “which type does Spring know the bean has?” depends on **timing**:

| Stage | Key information |
| --- | --- |
| Java compilation | `@Bean` signature and variable types at the client |
| Bean definition registration | Declared return type, class metadata, and registration conditions |
| Injection candidate prediction | Type inferable from bean definition, factory method, and certain `BeanPostProcessor`s |
| Target instance creation | Actual runtime type created by `@Bean` or constructor |
| Spring AOP proxy creation | Proxy strategy; type exposed to clients |
| Client method call | Actual object reference; method execution passes through proxy/interceptors if applicable |

For example, `@Bean PaymentService service()` tells Spring the interface before the singleton is instantiated. Spring may only discover the implementation after the method is called to create the instance. Spring documentation warns that type prediction for an undeclared implementation type can depend on when the singleton is created.

Consequently, **querying bean names by implementation class** at startup can differ from after initialization. This requires analyzing the actual context; do not rely on a single `getBeanNamesForType(Implementation.class)` call as an absolute conclusion.

Choose declared return types based on need: interface when consumers only need the contract, concrete type when the container needs type prediction for a specific injection point; however, if you want to inject the implementation when Spring AOP is active, you must also ensure the final proxy is type-compatible.

## 7. Which Spring Tools Identify the Right Class?

### 7.1. Runtime Class

```java
Object bean = context.getBean("messageService");
Class<?> runtimeClass = bean.getClass();
```

This is the actual class of the reference clients receive. If the bean has been AOP-proxied, this is typically a class dynamically generated by the JVM/Spring, **not the target implementation class**. Generated class names are not a stable API; do not write logic depending on prefixes like `$Proxy` or `$$SpringCGLIB$$`.

### 7.2. Checking Spring AOP Proxies and Target Class

```java
boolean aop = AopUtils.isAopProxy(bean);
boolean jdk = AopUtils.isJdkDynamicProxy(bean);
boolean cglib = AopUtils.isCglibProxy(bean);
Class<?> targetClass = AopUtils.getTargetClass(bean);
```

This is an **additional illustrative snippet** for the section 5 example, requiring `import org.springframework.aop.support.AopUtils;`. Each answers something different:

- `isAopProxy` asks whether the object is a Spring AOP proxy.
- `isJdkDynamicProxy` and `isCglibProxy` distinguish the proxy creation strategy.
- `getTargetClass` returns the target class known to Spring AOP; for an ordinary object, it returns that object's class.

`AopProxyUtils.ultimateTargetClass(bean)` can be useful when nested proxies with static target sources exist, but is unnecessary to diagnose a typical single-proxy example. Also do not confuse it with unwrapping a target object to bypass AOP.

### 7.3. When Not to Use `ClassUtils.getUserClass`

The `ClassUtils.getUserClass(...)` utility is useful for identifying the original class when an object has been CGLIB-enhanced. However, for a **JDK dynamic proxy**, do not assume it always infers the business implementation sitting behind the proxy. To find the target class of a Spring AOP proxy, use `AopUtils.getTargetClass(bean)`.

### 7.4. `BeanFactory.getType` Does Not Necessarily Equal `bean.getClass`

`applicationContext.getType("messageService")` asks Spring for the bean's type from `BeanFactory`'s perspective at query time. `context.getBean("messageService").getClass()` asks for the current object's runtime class. Returning different values can relate to `@Bean` declarations, lifecycle, proxying, `FactoryBean`, and type prediction.

When diagnosing injection failing to find a candidate, inspect both the bean definition and the final object. When diagnosing advice, inspect the proxy and target class using Spring AOP utilities.

## 8. Common Consequences in Spring AOP

### 8.1. JDK Proxies Cause Concrete Implementation Injection to Fail

The following consumer snippet:

```java
@Service
public class BillingFacade {
    private final PaymentServiceImpl paymentService;

    public BillingFacade(PaymentServiceImpl paymentService) {
        this.paymentService = paymentService;
    }
}
```

is **a pattern requiring imports/scanning**, not a standalone file. If the final bean is a JDK proxy, the constructor requesting `PaymentServiceImpl` is Java type-incompatible. Depending on the check stage and bean declaration style, the error may surface during candidate selection or after Spring creates the proxy.

Usually you should inject the interface the client actually uses:

```java
public BillingFacade(PaymentService paymentService) {
    this.paymentService = paymentService;
}
```

Do not switch to CGLIB merely to avoid a cast if the interface already serves the business need.

### 8.2. CGLIB Preserves Subtyping Yet Still Has Interception Limits

`proxy instanceof Implementation` being `true` does not prove every method on the implementation is advised. CGLIB cannot override `final` or `private` methods; it cannot subclass a `final class`. Furthermore, `this.inner()` inside the target does not go through the proxy again.

### 8.3. Targets Without a Business Interface

A target class without an interface usually needs CGLIB if Spring AOP creates a proxy. `proxyTargetClass=false` only means “do not force class proxies where an interface proxy is feasible,” not “forbid CGLIB.”

### 8.4. Spring Framework Differs from Spring Boot on Defaults

In plain Spring Framework, AOP defaults to choosing JDK proxies if the target has interfaces. Spring Boot can enable class-based proxies by default via AOP auto-configuration; in common configurations, the property is `spring.aop.proxy-target-class=true`. To return to an interface-based strategy when appropriate, use:

```properties
spring.aop.proxy-target-class=false
```

However, if multiple auto-proxy configurations coexist, a target-class proxy choice from elsewhere may govern. Hence **verifying on the runtime bean** is more reliable than reading a single property.

### 8.5. `@Configuration`'s CGLIB Is Not Necessarily an AOP Proxy

A `@Configuration(proxyBeanMethods=true)` class can be enhanced by Spring with a subclass to coordinate calls to `@Bean` methods. That is different from a proxy created by Spring AOP to run advisors. Do not infer `AopUtils.isAopProxy(bean) == true` solely because the class name contains `CGLIB`.

## 9. Workflow for Diagnosing Type and Proxy Errors

When an application fails after adding `@Aspect` or changing proxy strategy:

1. **Identify the bean name and declaration**: what is the `@Bean` return type or `@Component` class?
2. **Identify the actual class created by the factory**: `new ...Impl()` or which component class?
3. **Check whether an advisor actually applies**: does any aspect bean/pointcut select a method on the bean?
4. **Retrieve the bean from the ApplicationContext itself**: do not use an object created manually with `new` to draw conclusions about Spring proxies.
5. **Measure the proxy type**: `AopUtils.isAopProxy/isJdkDynamicProxy/isCglibProxy`.
6. **Measure the target class**: `AopUtils.getTargetClass(bean)`.
7. **Compare the injection point type**: interface or implementation? Does `type.isInstance(bean)` return true?
8. **Check type prediction**: is the `@Bean` return type too broad for specific injection points?
9. **Check proxy configuration**: `@EnableAspectJAutoProxy(proxyTargetClass=...)`, Boot properties, and other auto-proxy creators.
10. **Check the call path**: does it go through the proxy, or is there self-invocation or a `final`/`private` method?

Briefly note five facts when debugging: declared type, target class, runtime proxy kind, requested injection type, and method invocation path. They resolve most confusion without relying on Spring/JVM-generated proxy names.

## 10. Self-Check Questions

**1.** `@Bean PaymentService paymentService()` returns `new PaymentServiceImpl()`; a JDK AOP proxy is created. Is `bean.getClass() == PaymentServiceImpl.class` true?  
**Answer:** No. `getClass()` returns the runtime proxy class.

**2.** The same bean above uses CGLIB. What is `bean instanceof PaymentServiceImpl`?  
**Answer:** `true`, because the CGLIB proxy extends the target implementation.

**3.** A JDK proxy does not extend the implementation. Does `AopUtils.getTargetClass(bean)` always return only the interface?  
**Answer:** No. In the example, Spring AOP knows the target implementation is `PaymentServiceImpl`.

**4.** Does changing the return type to `@Bean PaymentServiceImpl paymentService()` force Spring to use CGLIB?  
**Answer:** No. Declared return types and proxy strategy are decided by separate mechanisms.

**5.** A dependency injects `PaymentServiceImpl`, and the AOP bean uses a JDK proxy. What is the primary issue?  
**Answer:** A JDK proxy is not assignable to the implementation class; additionally, the declared return type affects candidate lookup during the type prediction phase.

**6.** A bean uses CGLIB and `proxy instanceof PaymentServiceImpl` returns `true`. Is `private void audit()` guaranteed to run advice?  
**Answer:** No; private methods cannot be overridden by a subclass.

**7.** Should you rely on class name prefixes to identify JDK/CGLIB proxies?  
**Answer:** No. Prefer `AopUtils` utilities and Java type assignability checks.
