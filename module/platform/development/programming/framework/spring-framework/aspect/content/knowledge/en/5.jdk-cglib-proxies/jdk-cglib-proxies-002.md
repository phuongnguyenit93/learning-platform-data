# Subclass-Based CGLIB Proxies of the Target Class in Spring AOP

## 1. What Is a Spring AOP CGLIB Proxy?

In Spring AOP, an advised bean can be returned to the client as a **proxy**. When Spring chooses **CGLIB (class-based proxy)**, the proxy is a class **generated at runtime that extends the target class**, rather than only implementing interfaces like a JDK dynamic proxy.

Example of a bean of type `OrderService`:

```java
public class OrderService {
    public String submit(String id) {
        return "OK:" + id;
    }
}
```

If Spring AOP applies advice to `submit()` using CGLIB, the structure can be visualized as:

```text
        Spring ApplicationContext
                  |
                  | provides bean reference
                  v
       OrderService$$SpringCGLIB$$...
             (proxy subclass)
                  |
                  | extends
                  v
             OrderService
              (target type)

Client --> proxy.submit("A01")
              |
              +--> runs matching interceptor/advice
              |
              +--> delegates to target OrderService.submit(...)
              |
              +--> returns value / throws exception to client
```

The actual proxy class name generated by Spring is **not a stable API**; do not detect proxies by matching class name strings. Use `AopUtils.isCglibProxy(bean)` to inspect it.

Core point: **the proxy has an inheritance relationship with the target type, yet Spring AOP still separates the concept of the proxy from the target object**. When an interceptor proceeds with the call, it typically delegates business execution to the target object managed by Spring. Do not assume every statement inside a target method executes on the proxy object itself just because the proxy's type is a subclass.

**Scope:** explains Spring AOP class-based proxies, how Spring generates and uses subclasses, when to configure CGLIB, which methods are intercepted, and practical limitations. It does not expand into bytecode weaving technologies or general Aspect theory.

## 2. Why Does Spring Need Subclass-Based Proxies?

Spring AOP typically uses one of two proxy types:

| Criterion | JDK dynamic proxy | CGLIB class-based proxy |
| --- | --- | --- |
| Foundation | JDK proxy API | Subclass generator used by Spring via `spring-core` |
| Type relationship | Implements exposed interfaces | Extends the target class (if subclassable) |
| Target without a business interface | Not enough interfaces to expose the business API via JDK proxy | Usually the necessary choice |
| Callable through an implementation-typed variable? | Usually no, because the proxy is not the implementation | Yes, because the proxy is a subtype of the implementation |
| Method not declared on an interface | Not callable through the JDK proxy's interface | Can be intercepted if the method is eligible for proxying and the pointcut matches |
| Characteristic limitation | Caller can only use the proxy's interfaces | Cannot subclass a `final class`; cannot override `final`/`private` methods |

If the target **does not implement an interface**, Spring AOP can create a CGLIB proxy so clients can still inject/invoke the bean by its concrete class. If the target has an interface, plain Spring Framework typically prefers a JDK proxy unless a target-class proxy is requested. However, an application can **force CGLIB** even when interfaces exist.

Do not view CGLIB as a mechanism that automatically “intercepts every call in a class.” The scope of **Spring AOP remains method execution passing through a Spring proxy**.

## 3. How Does Spring Create the Subclass and Delegate Calls?

A class diagram helps distinguish the **proxy class** from the **target instance**:

```text
   OrderService (the Java class you write)
      ^
      | extends
      |
   OrderService$$SpringCGLIB$$... (runtime-generated class)
      ^
      |
   bean reference the client receives from Spring

   Proxy -- intercepts public overridable method -->
        MethodInterceptor / advisor chain
                |
                +-- proceed --> target instance of OrderService
                |
                +-- result / exception --> client
```

CGLIB generates a subclass to override the methods it can intercept. Inside the generated overriding method, Spring embeds routing logic to the AOP interceptor chain. If an advisor/pointcut matches the current method execution, advice executes at that boundary; if the advice proceeds, the call is forwarded to the target.

This is only a **conceptual model**, not the actual generated subclass source code. Spring uses internal components, callbacks, and dedicated optimizations to generate code; clients do not write subclasses or interceptors manually.

An illustrative `@Around` advice:

```java
@Around("execution(* com.example.app.service..*.save(..))")
public Object trace(ProceedingJoinPoint pjp) throws Throwable {
    System.out.println("BEFORE " + pjp.getSignature().getName());
    Object result = pjp.proceed();
    System.out.println("AFTER " + pjp.getSignature().getName());
    return result;
}
```

This is an **illustrative method** that must be placed inside a `@Aspect` Spring bean with the necessary imports. `pjp.proceed()` means **continue through the rest of the interceptor chain**, eventually reaching the target if not short-circuited. It does not mean “call the target directly and skip all other advice.”

If the method throws an exception, the exception propagates back up through the chain; outer advice can observe, rethrow, or handle it according to their contracts. CGLIB does not change these fundamental semantics compared to JDK proxies.

## 4. When Does Spring Choose a CGLIB Proxy?

### 4.1. Target Class Has No Interface

A Spring bean declared as follows:

```java
@Service
public class InvoiceService {
    public String createInvoice(String id) {
        return "INV:" + id;
    }
}
```

If an advisor applies to `createInvoice()` and Spring AOP needs to create a proxy, **without a business interface**, Spring can use a CGLIB class-based proxy. This class snippet is **illustrative code**, not a standalone program, because it requires Spring imports and a context containing the bean.

### 4.2. Explicitly Forcing Class-Based Proxies

In plain Spring Framework, enable `@AspectJ` auto-proxying and request target-class proxies:

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class AopConfig {
}
```

In XML:

```xml
<aop:aspectj-autoproxy proxy-target-class="true"/>
```

In Spring Boot when AOP auto-configuration is active, the property commonly used is:

```properties
spring.aop.proxy-target-class=true
```

Boot 3.x uses class-based proxies as the default choice for Spring AOP auto-configuration; you can set `false` to revert to the interface-based strategy when beans have interfaces. **`false` alone does not prohibit CGLIB** for beans without interfaces.

Spring can merge multiple auto-proxy creator configurations. A `proxyTargetClass=true` setting elsewhere can govern the entire context; do not conclude the proxy type from a single isolated annotation/property.

### 4.3. Not Every Bean Receives a Proxy

CGLIB is used only in **contexts where a proxy is actually created**. A bean with no matching advisor can remain a plain object. The presence of the `spring-aop` dependency or `@EnableAspectJAutoProxy` **does not prove** every bean is a proxy.

You should also separate **Spring AOP CGLIB proxies** from the enhancement mechanism of `@Configuration(proxyBeanMethods=true)` configuration classes. Both can involve subclass generation, but their purposes differ: one intercepts method executions per advisors, while the other coordinates calls between `@Bean` methods. Do not equate them when using `AopUtils.isAopProxy(...)`.

## 5. Runnable Experiment: CGLIB Subclass, Advice, and Self-Invocation

The example uses **Java 17+, Maven, Spring Framework 6.2.19**. There is a service **declaring no interfaces**, two normal business methods, and one `final` method. An aspect advises both `quote()` and `finalStatus()`, but CGLIB can only intercept calls to overridable methods.

The output demonstrates:

1. The bean provided by Spring is indeed a Spring AOP CGLIB proxy.
2. Clients can hold the bean by its **concrete class type** `PricingService`.
3. Client → proxy → `quote()` runs advice before the target.
4. `process()` on the target calls `this.quote("INNER")`; the call **does not go back through the proxy**, so `quote()` advice does not run a second time.
5. `finalStatus()` is not overridden by the subclass, so there is no advice even though the pointcut explicitly names that method. This is not a general guarantee for other proxy technologies.

**File `src/main/java/demo/CglibProxyDemo.java`:**

```java
package demo;

import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;

public class CglibProxyDemo {
    public static class PricingService {
        public String quote(String code) {
            System.out.println("TARGET quote " + code);
            return "PRICE:" + code;
        }

        public void process() {
            System.out.println("TARGET process");
            this.quote("INNER");
        }

        public final void finalStatus() {
            System.out.println("FINAL status");
        }
    }

    @Aspect
    public static class TraceAspect {
        @Before(
            "execution(* demo..*.quote(..)) || " +
            "execution(* demo..*.finalStatus(..))"
        )
        public void beforeCall(JoinPoint joinPoint) {
            System.out.println("ADVICE " + joinPoint.getSignature().getName());
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAspectJAutoProxy(proxyTargetClass = true)
    public static class Config {
        @Bean
        public PricingService pricingService() {
            return new PricingService();
        }

        @Bean
        public TraceAspect traceAspect() {
            return new TraceAspect();
        }
    }

    public static void main(String[] args) {
        try (var context =
                 new AnnotationConfigApplicationContext(Config.class)) {
            PricingService service = context.getBean(PricingService.class);

            System.out.println("AOP_PROXY=" + AopUtils.isAopProxy(service));
            System.out.println("CGLIB_PROXY=" + AopUtils.isCglibProxy(service));
            System.out.println("IS_PRICING_SERVICE="
                    + (service instanceof PricingService));

            System.out.println("=== OUTSIDE CALL ===");
            System.out.println("RESULT=" + service.quote("OUTER"));

            System.out.println("=== SELF INVOCATION ===");
            service.process();

            System.out.println("=== FINAL METHOD ===");
            service.finalStatus();
        }
    }
}
```

Run in the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

**Stdout lines printed by the program itself in order** (Maven/Spring may emit their own logging):

```text
AOP_PROXY=true
CGLIB_PROXY=true
IS_PRICING_SERVICE=true
=== OUTSIDE CALL ===
ADVICE quote
TARGET quote OUTER
RESULT=PRICE:OUTER
=== SELF INVOCATION ===
TARGET process
TARGET quote INNER
=== FINAL METHOD ===
FINAL status
```

Trace explanation:

- `@EnableAspectJAutoProxy(proxyTargetClass=true)` requests target-class proxies for advised beans.
- `@Bean TraceAspect` makes the aspect an actual Spring bean; `@Aspect` alone is not enough for the container to register the class automatically.
- The proxy of `PricingService` is a subclass, so the object returned by `getBean(PricingService.class)` is an instance of `PricingService`.
- When the client calls `quote("OUTER")` on the proxy, `@Before` runs before the target method, and then the target's return value is printed at the client.
- When the target executes `process()` and calls `this.quote("INNER")`, the direct call on the target **bypasses the proxy**, so there is no `ADVICE quote` line for `INNER`.
- The `finalStatus()` method is declared `final` and cannot be overridden by the CGLIB subclass; it runs directly and **no** `ADVICE finalStatus` appears. This method intentionally **avoids using instance fields** to avoid an important issue with final methods on proxies discussed in a later section.

The CGLIB limitation mechanism here is a property of **Spring AOP proxy-based interception**, not of pointcut syntax. Even if a pointcut matches the method declaration, there is no interceptor hook on an un-overridable method.

## 6. Which Methods Can a CGLIB Proxy Intercept?

| Member in target class | Can be advised by Spring AOP CGLIB? | Reason |
| --- | --- | --- |
| Non-`final` `public` method | Yes, if the call goes through the proxy and the pointcut matches | The proxy subclass can override it |
| Non-`final` `protected` method | Possibly, depending on call site and pointcut | The proxy is able to override visible methods |
| Package-private method | Possibly if the method is visible to the subclass and supported by the framework | Visibility can restrict overriding |
| `final` instance method | **No** | Subclass cannot override |
| `private` method | **No** | Private methods are not inherited/overridden |
| Method in a `final class` | **Cannot build a CGLIB subclass** | A `final` class cannot be extended |
| `static` method | Not an instance-proxy-intercepted method execution | Static calls do not dispatch via instance overriding |
| Constructor | No | Spring AOP does not advise constructor execution with proxies |
| Method the target calls on itself via `this` | **No new interception** | The call does not enter the proxy |
| Method called on an object created with `new` outside the container | Not automatically advised by Spring AOP | No Spring proxy is involved |

For non-public methods, you must verify **actual visibility, the pointcut expression, the proxy type, and the Spring version**. Spring can handle some protected/package-visible calls through CGLIB, but conventional service design should place external interception points on clear public methods.

### 6.1. Why Is a `final class` a Problem?

Example:

```java
public final class FinalReportService {
    public void generate() {
        System.out.println("generated");
    }
}
```

Java forbids another class from `extends FinalReportService`, so Spring **cannot create a CGLIB subclass** for that bean. If the bean must be proxied using a class-based proxy, proxy creation can fail right during context initialization. Only removing `final` from the class, changing the bean design, or using an appropriate interface-based strategy resolves the root cause.

**Do not assume a class with an interface will automatically get a JDK proxy if configuration is forcing CGLIB.** Check the effective proxy mode.

### 6.2. Why Is a `final method` Particularly Dangerous with Instance State?

A CGLIB AOP proxy typically holds a **separate target object**. For overridable methods, the proxy routes execution through interceptors to the target. For a `final` method, the subclass cannot override it, so the client invokes that method **directly on the proxy instance**.

This can create discrepancies in **instance fields** if the `final` method accesses state initialized in the target's constructor: do not assume a `final` method on the proxy sees the same state as a method delegated to the target. Common pattern:

```java
class StatefulService {
    private String token;

    StatefulService() {
        token = "READY";
    }

    public final String token() {
        return token;
    }
}
```

This is **risk-analysis code, not a standalone program**. Spring typically instantiates the proxy via **Objenesis** so it does not have to run the target's constructor a second time. Consequently, instance field data on the proxy inside a `final` method may not be the target's data. Do not treat calling `final` methods on a CGLIB proxy as a reliable contract.

Safer approaches are keeping methods that Spring AOP needs to intercept overridable, avoiding `final` classes for targets requiring proxying, or placing the intercepted behavior on another interface/service with an appropriate proxy strategy.

### 6.3. `private` and `static` Methods

`private` methods belong directly to the class's own scope and are not overridden; Spring AOP CGLIB has no way to replace them with a proxy's overriding method. `static` methods bind to the class rather than dispatching through an instance; placing an annotation on a static method also does not make it a Spring AOP join point intercepted by a proxy.

To have advice at a business boundary, place the behavior to intercept on an appropriate method of a Spring-managed bean and call that method through the proxy.

## 7. Proxy Subclasses Still Have Self-Invocation

This is an easy source of confusion when hearing that CGLIB “extends the target class.”

```text
Client ------------------> CGLIB proxy
                              |
                           intercept
                              |
                              v
                         target.outer()
                              |
                              | this.inner()
                              v
                         target.inner()
                     (does not return to proxy)
```

Once the target is executing `outer()`, the `this` reference inside the target points to the target; the `this.inner()` call proceeds directly via normal dispatch on that object and does not return to the proxy entry point.

Setting `proxyTargetClass=true` **does not automatically solve** self-invocation, even if `inner()` is public and has a matching pointcut. This directly affects mechanisms built on Spring AOP such as `@Transactional`, `@Cacheable`, and application advice.

### Designing Calls to Go Through the Proxy

Usually, you should extract the method needing advice into a dedicated Spring bean and inject that bean:

```java
@Service
public class PriceCalculator {
    @Transactional
    public void calculateAndSave() {
        // logic with transaction applied when called through the proxy
    }
}

@Service
public class OrderProcessor {
    private final PriceCalculator calculator;

    public OrderProcessor(PriceCalculator calculator) {
        this.calculator = calculator;
    }

    public void processOrder() {
        calculator.calculateAndSave(); // called via the Spring-injected bean reference
    }
}
```

This is an **illustrative design pattern**, requiring imports, a context with transaction management, and an appropriate database/transaction manager to apply in practice. The key is that `OrderProcessor` uses a Spring-supplied bean reference, allowing the call to pass through the `PriceCalculator` proxy.

Self-injection or `AopContext.currentProxy()` with `exposeProxy=true` exist, but they couple code to Spring AOP internals; generally use them only when refactoring bean boundaries is not possible.

## 8. Constructors: Does a CGLIB Proxy Call the Constructor Twice?

Modern Spring Framework typically uses **Objenesis** to instantiate proxy objects without calling the target's constructor a second time. Therefore, in normal cases **the target constructor does not run twice** merely because a CGLIB AOP proxy is created.

A commonly observed misconception:

```java
public class DocumentService {
    public DocumentService() {
        System.out.println("CONSTRUCTOR");
    }

    public void generate() {
        System.out.println("GENERATE");
    }
}
```

Do not assume the output always prints two `CONSTRUCTOR` lines when Spring creates a CGLIB proxy. In some JVM environments that restrict constructor bypassing, Spring may fall back and produce an extra constructor call along with a debug log; this is an exception noted in the Spring documentation.

**Practical consequence:** constructors should perform pure initialization work, avoiding dependencies on proxies or advice existing at constructor execution time. Spring AOP does not use proxies to advise methods called inside a constructor before the bean proxy is ready.

## 9. Module System and Class Subclassability

CGLIB needs to generate a subclass and access the target's methods/classes. Therefore, with the Java Platform Module System (JPMS), Java access rules can prevent proxying certain classes or packages.

An example frequently mentioned by Spring: creating a class-based proxy for a class in the `java.lang` package when deployed on the module path has strong restrictions; opening a package with a flag such as:

```text
--add-opens=java.base/java.lang=ALL-UNNAMED
```

is only meaningful in appropriate JVM configurations and cannot arbitrarily open packages for a named module in the same way. Do not add JVM flags indiscriminately without a specific error and without identifying the target package, module boundary, and deployment mode.

For application service classes, check whether the class is `final`, whether methods are overridable, package/module access visibility, and classloader types if Spring reports an error creating a CGLIB subclass.

## 10. CGLIB Proxies and Bean Types Upon Injection

An easily observed advantage of class-based proxies is that beans can be injected by their **concrete class**:

```java
@Service
public class CustomerService {
    public String find(String id) {
        return "CUSTOMER:" + id;
    }
}

@RestController
public class CustomerController {
    private final CustomerService customerService;

    public CustomerController(CustomerService customerService) {
        this.customerService = customerService;
    }
}
```

This is **illustrative code requiring Spring Boot Web imports and appropriate handler methods**. If Spring AOP creates a CGLIB proxy for `CustomerService`, the proxy is a subclass of `CustomerService`, so type-wise it can be supplied to a `CustomerService` field/constructor parameter.

When switching to a JDK dynamic proxy, beans usually expose only interfaces, and injections requiring the implementation class can fail. To reduce coupling to the proxy type, design clear business interfaces where appropriate; however, if the application genuinely needs class-based proxies, ensure the class can be validly subclassed.

Note: **being able to inject by concrete class is not proof that the bean is advised**. Ordinary unproxied beans also have the concrete type; verify with `AopUtils.isCglibProxy(bean)`.

## 11. How to Verify the Actual Proxy Type at Runtime

Assuming you have an `ApplicationContext` and an appropriate service class:

```java
Object bean = context.getBean(PricingService.class);

System.out.println(AopUtils.isAopProxy(bean));
System.out.println(AopUtils.isCglibProxy(bean));
System.out.println(AopUtils.isJdkDynamicProxy(bean));
System.out.println(bean instanceof PricingService);
```

This is an **add-on snippet** for the runnable example in section 5. With the CGLIB configuration and advised target bean in that example, the output lines are:

```text
true
true
false
true
```

Do not use `bean.getClass() == PricingService.class` to check the target type: the proxy class is a dynamically generated subclass, so exact class comparison can return `false`. When you need the target class, Spring provides utilities such as `AopUtils.getTargetClass(bean)`. Even so, extracting the real target from a proxy or manipulating it directly is rarely needed in business code.

In applications with multiple auto-proxy creators or special proxies, **runtime output is the primary evidence**. Do not infer the proxy type from starter names or a single property without knowing the effective configuration.

## 12. Common Misconceptions

| Misconception | Reality in Spring AOP |
| --- | --- |
| “CGLIB creates an object like the target with no type relationship.” | The proxy is a subclass of the target class (when valid subclassing applies). |
| “CGLIB can intercept every method in a class.” | No: `final`, `private`, `static`, and ineligible methods all have limitations. |
| “Switching from JDK to CGLIB makes `this.inner()` get advised.” | No: self-invocation still bypasses the proxy. |
| “Using CGLIB causes the target constructor to run twice.” | Spring typically uses Objenesis to avoid a second constructor call; fallback cases are exceptions. |
| “A CGLIB proxy is no different from the target instance.” | You must distinguish the proxy object from the target object; state in `final` methods can be particularly dangerous. |
| “A `final` class is fine if the pointcut only matches public methods.” | CGLIB cannot subclass a `final class`. |
| “Having the Spring AOP dependency means every service is a CGLIB proxy.” | Only beans that need proxying and are eligible get auto-proxied. |
| “Checking whether the class name contains `CGLIB` is reliable.” | Use `AopUtils.isCglibProxy(bean)`; runtime class names are not a contract. |
| “CGLIB requires adding a separate external dependency.” | CGLIB is already repackaged by Spring in `spring-core` for this proxy mechanism. |
| “Every subclass generated by Spring is a Spring AOP CGLIB proxy.” | Subclasses for `@Configuration` and class-based AOP proxies serve different purposes. |

## 13. Troubleshooting Checklist

1. **Is the bean actually managed by Spring?** Ensure callers use the bean injected/retrieved from the context instead of creating objects directly with `new`.
2. **Is there a matching advisor?** Without an advisor, an ordinary bean will not necessarily be proxied.
3. **Is target-class proxy configuration in effect?** Check `@EnableAspectJAutoProxy(proxyTargetClass=true)`, `spring.aop.proxy-target-class`, and other AOP/transaction configurations.
4. **Is the class `final`?** If so, Spring cannot create a CGLIB subclass for that class.
5. **Is the method `final`/`private`/`static`?** If so, do not expect Spring AOP to advise the method via overriding.
6. **Is there self-invocation?** Check for `this.method()` calls inside the target; that is not a fresh call entering through the proxy.
7. **Are Java visibility and module permissions valid?** Check package access, inherited package-private methods, module path, and subclass creation exceptions.
8. **Is instance state accessed in a `final` method?** If so, check the risk of proxy object state differing from target state; prefer redesigning the boundary.
9. **What is the proxy type at runtime?** Use `AopUtils.isAopProxy` / `isCglibProxy` / `isJdkDynamicProxy` and inspect the actual call site.
10. **Is the aspect registered?** The `@Aspect` class must be a Spring bean, and `@AspectJ` auto-proxying must be enabled appropriately.

## 14. Self-Check Questions

**Question 1.** Target `InventoryService` implements no interfaces, has a public `reserve()` method, and has a Spring AOP advisor matching that method. What proxy type is expected?  
**Answer:** A CGLIB class-based proxy, because there is no suitable business interface for a JDK proxy.

**Question 2.** The target implements an interface, but `proxyTargetClass=true` is set. What proxy is expected?  
**Answer:** CGLIB, provided the target class is eligible for subclassing and no other configuration/exception changes the outcome.

**Question 3.** Why does calling `this.reserve()` inside `InventoryService` not run advice on `reserve()`, even though Spring is using CGLIB?  
**Answer:** The internal call executes directly on the target without returning to the proxy. CGLIB does not weave advice into the target's bytecode.

**Question 4.** Why is `final void status()` not advised by CGLIB?  
**Answer:** The runtime-generated subclass cannot override a `final` method.

**Question 5.** Can `AopUtils.isCglibProxy(bean)` be used to verify that a bean is proxied by Spring AOP with CGLIB?  
**Answer:** Yes. However, you still need to check the specific method and call path to know whether advice will run.

**Question 6.** A constructor prints one line and the bean is CGLIB-proxied. Will it always print two lines?  
**Answer:** No. Modern Spring typically uses Objenesis, so the target constructor is not called twice under normal conditions.

**Question 7.** A `final` method reads an instance field assigned in the constructor; should you trust that it always reads the same target data on a CGLIB AOP proxy?  
**Answer:** No. A `final` method is not delegated through an interceptor like an overridable method; the proxy and target can have different instance state.
