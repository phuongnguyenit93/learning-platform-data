# Distinguishing Spring-Side Named Parameters from JDBC Driver Support

> **Context:** Spring Framework Data Access → Stored procedures and functions. When passing `Map<String, Object>` or `MapSqlParameterSource` into `SimpleJdbcCall`, we are using **names at the Spring layer**. This **does not prove** that the JDBC driver can call `CallableStatement.setXxx(String parameterName, ...)` or `getXxx(String parameterName)`. Understanding the layers properly prevents misconfigurations when calling procedures/functions, especially when changing database management systems (DBMS).

## 1. Goals and core issue

After this lesson, you will be able to:

1. Distinguish three concepts: **named placeholders in Spring-side SQL**, **`SimpleJdbcCall` `IN`/`OUT` parameter name matching**, and **JDBC driver/DBMS named parameter support**.
2. Explain why `SimpleJdbcCall.execute(Map)` can work even when the underlying driver only binds positionally at 1, 2, 3.
3. Choose the right `SqlParameter`, `SqlOutParameter`, `SqlInOutParameter`, and handle metadata and declaration order.
4. Know when to use `withNamedBinding()`, why it differs from passing a `Map`, and how to verify compatibility.
5. Run a real Java 17 + Spring JDBC + MySQL example, verifying both Spring and direct JDBC results.

One sentence to remember:

**Names in Spring APIs serve data mapping; the positional indices or call syntax generated by Spring and what the driver/DBMS supports are what determine the actual call.**

## 2. Four layers often lumped together as "named parameters"

| Layer | Example API/syntax | Who resolves the names? | Requires driver support for JDBC binding by name? |
| --- | --- | --- | --- |
| Ordinary SQL statements in Spring | `NamedParameterJdbcTemplate`: `SELECT :amount - :discount` | Spring parses `:amount`, `:discount`, generates `?` placeholders, and arranges values positionally | **No** |
| Inputs for stored procedures/functions in Spring | `SimpleJdbcCall.execute(Map.of("p_amount", 80, "p_discount", 15))` | Spring matches Map keys against declared `SqlParameter`s or metadata | **No**, when the default call path uses positional binding |
| Named argument syntax in DBMS call string | `withNamedBinding()` may generate fragments like `p_amount => ?` or DB-specific syntax | Spring builds the **SQL call string**; the DBMS/driver must understand that call syntax | Depends on DBMS/driver; distinct from JDBC `setInt(String,...)` |
| True named API in JDBC | `CallableStatement.setInt("p_amount", 80)`; `registerOutParameter("p_net", Types.INTEGER)` | The JDBC driver itself must resolve the names | **Yes**; requires testing the actual implementation |

In particular, `:amount` notation is a **Spring `NamedParameterJdbcTemplate`** convention, not a required `PreparedStatement` placeholder form in standard JDBC. In ordinary JDBC, calls are still executed with `?` and **1-based** indices.

### 2.1. Same meaning, two paths

```text
SQL SELECT :amount - :discount
    └─ NamedParameterJdbcTemplate
          └─ Spring parses SQL, replaces :name with ?
                └─ PreparedStatement: SELECT ? - ?
                      └─ setInt(1, 80); setInt(2, 15)

Stored procedure calc_net
    └─ SimpleJdbcCall.execute(MapSqlParameterSource)
          ├─ matches "p_amount" / "p_discount" against declared parameters
          ├─ by default builds {call calc_net(?, ?, ?)}
          └─ CallableStatement: position 1 = 80, 2 = 15, OUT position 3
                └─ JDBC driver → DBMS
```

**Key difference:** `NamedParameterJdbcTemplate` fits SQL queries/updates; `SimpleJdbcCall` additionally handles **procedure/function signatures, `OUT`/`INOUT` parameters, return values, and metadata**. Do not treat `NamedParameterJdbcTemplate.update("CALL ...")` as a general replacement for `SimpleJdbcCall`'s `OUT` parameter mechanism.

## 3. How does Spring turn a Map into a procedure call?

Suppose we have a MySQL procedure:

```sql
CREATE PROCEDURE calc_net(
    IN p_amount INT,
    IN p_discount INT,
    OUT p_net INT
)
BEGIN
    SET p_net = p_amount - p_discount;
END;
```

The exact signature order in the DB is **IN amount → IN discount → OUT net**. Inputs `80` and `15` yield output `65`.

Explicit `SimpleJdbcCall` declaration:

```java
SimpleJdbcCall call = new SimpleJdbcCall(dataSource)
        .withProcedureName("calc_net")
        .withoutProcedureColumnMetaDataAccess()
        .declareParameters(
                new SqlParameter("p_amount", Types.INTEGER),
                new SqlParameter("p_discount", Types.INTEGER),
                new SqlOutParameter("p_net", Types.INTEGER)
        );

MapSqlParameterSource in = new MapSqlParameterSource()
        .addValue("p_discount", 15) // intentionally reversed key order
        .addValue("p_amount", 80);

Map<String, Object> out = call.execute(in);
int net = ((Number) out.get("p_net")).intValue(); // 65
```

In this example:

- Spring looks up values by name `p_amount` and `p_discount`; **the order in which keys are added to the Map does not matter**.
- When metadata lookup is disabled via `withoutProcedureColumnMetaDataAccess()`, **the order of `declareParameters(...)` must match the actual DB signature**. Swapping `p_amount` and `p_discount` in the declarations causes wrong positional binding. With subtraction, this bug is easy to spot: it can turn `80 - 15` into `15 - 80`.
- `SqlOutParameter("p_net", Types.INTEGER)` tells Spring the `OUT` position and JDBC type to register before `execute()`. Spring places the `OUT` value into the returned Map under the parameter name.
- You **do not need** `withNamedBinding()` to pass a Map with named keys. Under default settings, `SimpleJdbcCall` can use `{call calc_net(?, ?, ?)}` and operate by **index** on `CallableStatement`.

If relying on metadata, Spring queries `DatabaseMetaData` from the driver to determine the procedure/function signature. Reliable metadata saves manual declarations, though effectiveness depends on **DBMS, version, driver, schema, overloads, and parameter types**. The fact that a driver can read names from metadata does not mean it supports all named `CallableStatement` overloads.

### 3.1. Declaring IN, OUT, and INOUT

| Spring declaration | Meaning | Effect at execution time |
| --- | --- | --- |
| `new SqlParameter("p_in", Types.INTEGER)` | Value only goes into the procedure | Read from Map/`SqlParameterSource` and bound at the corresponding position |
| `new SqlOutParameter("p_out", Types.INTEGER)` | Value returned from the procedure | Registered as `OUT`, retrieved, and placed in the output Map |
| `new SqlInOutParameter("p_both", Types.INTEGER)` | Same parameter is both `IN` and `OUT` | Input value bound, registered, and output value retrieved |
| `new SqlReturnResultSet("rows", rowMapper)` | Direct `ResultSet` output | Maps returned list of rows; not always equivalent to a cursor `OUT` parameter |

For a function returning a single value, use `withFunctionName("...")` and `executeFunction(ReturnType.class, args)` when supported by the driver/DBMS. Standard escape syntax typically looks like `{? = call function_name(?)}`: the first `?` is reserved for the **return value**, not the first `IN` argument. Do not apply procedure indices blindly to functions.

Note that a plain `SqlOutParameter` is **not** where `IN` values are supplied. For a bidirectional parameter, use `SqlInOutParameter` as intended. When encountering `NULL`, an explicit JDBC type declaration helps the driver handle it consistently.

## 4. `withNamedBinding()`: names in the **SQL call string** and compatibility limits

In `SimpleJdbcCall`, the following two setups have different meanings:

```java
// A. Spring API accepting a named Map, using default positional binding:
new SimpleJdbcCall(dataSource).withProcedureName("calc_net");

// B. Changes how Spring formats parameter syntax in the call string:
new SimpleJdbcCall(dataSource).withProcedureName("calc_net")
        .withNamedBinding();
```

According to Spring JDBC source code, `AbstractJdbcCall` defaults to `namedBinding=false`. When `withNamedBinding()` is enabled, Spring asks `CallMetaDataProvider` to generate **named parameter syntax fragments inside the call string**. Common forms are `parameterName => ?` (with generic providers) or `parameterName = ?` (with providers specific to certain DBMSs). For instance, **strictly to illustrate the mechanism**, a string might look like:

```sql
{call calc_net(p_amount => ?, p_discount => ?, p_net => ?)}
```

**Do not assume** the illustrative syntax above runs on every DB, and specifically **do not enable it in the MySQL example** in section 5. The DBMS must understand the corresponding named argument syntax and the JDBC driver must translate/forward the call properly. Spring inserting names into the SQL call string also **does not mean** Spring calls `CallableStatement.setInt("p_amount", 80)` underneath; on the standard execution path, `CallableStatementCreatorFactory` may still bind placeholders by **index**.

There are three independent decisions:

1. **Want to call Spring with a named Map?** Use `SimpleJdbcCall.execute(Map)` or `execute(SqlParameterSource)`; no need to enable named binding.
2. **Want Spring to determine `IN`/`OUT` order/names from the DB?** Use metadata if trustworthy; otherwise disable metadata and manually declare exact order and types.
3. **Want parameter names to appear in the actual call syntax sent to the DB?** Only consider `withNamedBinding()` after verifying the specific DBMS + JDBC driver, especially for overloaded procedures, default parameters, or vendor-specific syntax.

### 4.1. Direct named binding on `CallableStatement` is a separate matter

JDBC defines two groups of operations (example):

```java
// By position: common approach, 1-based index.
cs.setInt(1, 80);
cs.setInt(2, 15);
cs.registerOutParameter(3, Types.INTEGER);
cs.execute();
int net = cs.getInt(3);

// By name: use only when the specific driver/DBMS supports it.
cs.setInt("p_amount", 80);
cs.setInt("p_discount", 15);
cs.registerOutParameter("p_net", Types.INTEGER);
cs.execute();
int netByName = cs.getInt("p_net");
```

The two snippets are **two alternative approaches**, not executed sequentially on the same already-executed statement. The second approach must be verified via driver documentation and real integration tests; you may encounter `SQLFeatureNotSupportedException`, `SQLException`, or mismatched DB signature behavior if names are normalized or types differ. Do not treat `SimpleJdbcCall.execute(Map)` succeeding as proof that these named JDBC methods work.

**Metadata trap:** `PreparedStatement`'s `ParameterMetaData` describes **count, type, precision, IN/OUT mode, etc.**, and has no standard `getParameterName()` method. For procedure parameter names, Spring relies on `DatabaseMetaData` APIs for procedures/functions along with specialized providers; actual results still depend on the driver.

## 5. Complete, runnable example: Spring JDBC and MySQL 8.4

This example intentionally uses **both approaches** on the same procedure:

- Spring `SimpleJdbcCall.execute(MapSqlParameterSource)`: input keys are inserted in reverse order to demonstrate Spring's name-matching mechanism.
- JDBC `CallableStatement`: binds all three parameters by index, registers `OUT`, and reads the result.

Both call styles must produce `65` even though `SimpleJdbcCall` **does not** use `withNamedBinding()`. Requires JDK 17+, Maven 3.9+, Docker, and permission to run containers. Run in a dedicated practice directory structured as:

```text
named-call-demo/
├── pom.xml
└── src/main/java/CallDemo.java
```

### 5.3. File `src/main/java/CallDemo.java`

```java
import java.sql.CallableStatement;
import java.sql.Connection;
import java.sql.DatabaseMetaData;
import java.sql.Statement;
import java.sql.Types;
import java.util.Map;

import org.springframework.jdbc.core.SqlOutParameter;
import org.springframework.jdbc.core.SqlParameter;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.core.simple.SimpleJdbcCall;
import org.springframework.jdbc.datasource.DriverManagerDataSource;

public class CallDemo {

    public static void main(String[] args) throws Exception {
        DriverManagerDataSource ds = new DriverManagerDataSource();
        ds.setDriverClassName("com.mysql.cj.jdbc.Driver");
        ds.setUrl(System.getenv().getOrDefault(
                "DB_URL",
                "jdbc:mysql://127.0.0.1:33079/proc_lab"
                + "?sslMode=DISABLED&allowPublicKeyRetrieval=true"));
        ds.setUsername(System.getenv().getOrDefault("DB_USER", "lab"));
        ds.setPassword(System.getenv().getOrDefault("DB_PASSWORD", "labpass"));

        // Prepare procedure in the practice DB; no production data is used.
        try (Connection con = ds.getConnection();
             Statement statement = con.createStatement()) {
            statement.execute("DROP PROCEDURE IF EXISTS calc_net");
            // JDBC sends CREATE PROCEDURE as one SQL statement: do not use DELIMITER
            // because DELIMITER is a MySQL CLI-only command.
            statement.execute("""
                CREATE PROCEDURE calc_net(
                    IN p_amount INT,
                    IN p_discount INT,
                    OUT p_net INT
                )
                BEGIN
                    SET p_net = p_amount - p_discount;
                END
                """);

            DatabaseMetaData md = con.getMetaData();
            System.out.println("Driver: " + md.getDriverName());
        }

        // A. SQL query with :name: Spring converts to ? before sending to JDBC.
        NamedParameterJdbcTemplate named = new NamedParameterJdbcTemplate(ds);
        MapSqlParameterSource sqlArgs = new MapSqlParameterSource()
                .addValue("discount", 15)
                .addValue("amount", 80);
        Integer queryResult = named.queryForObject(
                "SELECT :amount - :discount", sqlArgs, Integer.class);
        System.out.println("Named SQL result: " + queryResult);

        // B. Stored procedure: Map keys are matched by Spring to
        // SqlParameter; declared in the DB procedure's ORDER.
        SimpleJdbcCall springCall = new SimpleJdbcCall(ds)
                .withProcedureName("calc_net")
                .withoutProcedureColumnMetaDataAccess()
                .declareParameters(
                        new SqlParameter("p_amount", Types.INTEGER),
                        new SqlParameter("p_discount", Types.INTEGER),
                        new SqlOutParameter("p_net", Types.INTEGER));

        MapSqlParameterSource procedureArgs = new MapSqlParameterSource()
                .addValue("p_discount", 15)
                .addValue("p_amount", 80); // intentionally reversed key order
        Map<String, Object> out = springCall.execute(procedureArgs);
        Number springNet = (Number) out.get("p_net");
        System.out.println("Spring procedure result: " + springNet.intValue());

        // C. Plain JDBC: binds by ordinal index, not by name.
        try (Connection con = ds.getConnection();
             CallableStatement cs =
                     con.prepareCall("{call calc_net(?, ?, ?)}")) {
            cs.setInt(1, 80);
            cs.setInt(2, 15);
            cs.registerOutParameter(3, Types.INTEGER);
            cs.execute();
            int jdbcNet = cs.getInt(3);
            if (cs.wasNull()) {
                throw new IllegalStateException("Unexpected SQL NULL");
            }
            System.out.println("JDBC indexed result: " + jdbcNet);

            if (queryResult == null || queryResult != 65
                    || springNet.intValue() != 65 || jdbcNet != 65) {
                throw new IllegalStateException("Results differ");
            }
        }
    }
}
```

Writing `CREATE PROCEDURE` inside `Statement.execute(...)` sends a single SQL statement over JDBC, so **do not include** the MySQL CLI utility's `DELIMITER //`. The procedure name `calc_net`, parameter types, and order must always match between SQL and Spring declarations.

## 6. Metadata and portability when calling procedures/functions

### 6.1. Enabling metadata when appropriate

```java
SimpleJdbcCall call = new SimpleJdbcCall(dataSource)
        .withProcedureName("calc_net");
Map<String, Object> result = call.execute(
        Map.of("p_amount", 80, "p_discount", 15));
```

In this form, `SimpleJdbcCall` can infer `IN`/`OUT`/types and order from driver-provided metadata. This reduces configuration code when the DBMS and driver expose **reliable metadata**. However, some cases can get complicated: same procedure name across multiple schemas, uppercase/lowercase/quoted identifiers, overloads, parameters with unsupported type mappings, cursor-returning procedures, or inconsistent function/procedure info between driver and DB.

Therefore, **measure against your actual deployment system**: check DBMS/version, driver/version, actual schema/procedure, and `IN`/`OUT` types before assuming Spring will always infer them accurately.

### 6.2. Disabling metadata when signatures need strict control

```java
new SimpleJdbcCall(dataSource)
        .withProcedureName("calc_net")
        .withoutProcedureColumnMetaDataAccess()
        .declareParameters(
                new SqlParameter("p_amount", Types.INTEGER),
                new SqlParameter("p_discount", Types.INTEGER),
                new SqlOutParameter("p_net", Types.INTEGER)
        );
```

This is the clear option when metadata is missing/wrong, routines are overloaded, you want control over `Types`, or you use a driver not fully supported by Spring. **The consequence** is that you own keeping the signature synchronized with the DB; changing parameter order or SQL types in the procedure requires updating the declarations accordingly.

`useInParameterNames(...)` can restrict the `IN` names considered during metadata processing, such as when disambiguating signatures; this method **does not fix** a wrong signature, replace `OUT` declarations, or grant named-binding capability to a driver.

### 6.3. Mind `OUT` names and `NULL` values

Key names returned in the `Map` can follow metadata and the DBMS's letter-casing rules. You can configure `JdbcTemplate.setResultsMapCaseInsensitive(true)` and pass that `JdbcTemplate` into `SimpleJdbcCall` if the application needs case-insensitive `OUT` key lookups.

```java
JdbcTemplate jdbc = new JdbcTemplate(dataSource);
jdbc.setResultsMapCaseInsensitive(true);
SimpleJdbcCall call = new SimpleJdbcCall(jdbc)
        .withProcedureName("calc_net");
```

This is a configuration example, not a replacement for metadata/type declarations when the driver returns incomplete info. `OUT` types must fit the returned values: use `Number` and convert appropriately, and check for `NULL` rather than blindly casting or auto-unboxing. For `NULL` inputs, use `addValue("p_amount", null, Types.INTEGER)` to supply an explicit JDBC type.

## 7. Verifying each capability independently, not inferring from a single successful run

| What you want to know | Verification test | Allowed conclusion |
| --- | --- | --- |
| Spring understands `:name` in `SELECT` | Use `NamedParameterJdbcTemplate` with two keys in reversed order | Proves Spring maps names → positions properly for ordinary SQL |
| Spring understands Map keys in procedures | `SimpleJdbcCall.execute(MapSqlParameterSource)` as in the demo | Proves name matching at the Spring API and standard positional calls work |
| Driver metadata is sufficient | Remove `withoutProcedureColumnMetaDataAccess()`, cross-check signature/`OUT` against DB | Proves metadata **for that specific routine** suffices, not that every routine is compatible |
| JDBC driver supports true named API | Create `CallableStatement`, try `setInt("p_amount", ...)`, `registerOutParameter("p_net", ...)`, `getInt("p_net")` | Only if it works on the target driver/version is the named API confirmed |
| DB supports named arguments in call string | Test `withNamedBinding()` in an isolated environment, inspect generated SQL and results | Confirms call syntax compatibility for that signature, not for every DB |
| Declarations are in the right order | Intentionally swap two `IN` declarations **in a test** and compare `65` vs `-65` | Clarifies why Map order and declared parameter order are distinct concepts |

In test reports, record `DatabaseMetaData.getDatabaseProductName()`, `getDatabaseProductVersion()`, `getDriverName()`, `getDriverVersion()`, Spring JDBC version, SQL signature, and `OUT` results. For driver named API methods, catch `SQLException`/`SQLFeatureNotSupportedException` and inspect `SQLState` and vendor error codes. Errors can stem from **lack of name support**, **name mismatch**, **type mismatch**, **routine not found**, or **invalid SQL syntax** — do not blame everything on "Spring did not recognize the name".

## 8. Common errors and how to handle them

| Symptom | Common cause | Resolution |
| --- | --- | --- |
| `MapSqlParameterSource` has the right keys, yet results are wrong | `SqlParameter` declarations are out of order with metadata disabled | Check each `IN`/`OUT` ordinal index against the DB signature; add tests using non-commutative operations |
| `Required input parameter ... is missing` | Spring key does not match declared/metadata `IN` parameter, or casing/spelling mismatch | Match keys, DB names, and `declareParameters`; log names **without logging sensitive values** |
| `CallableStatement.setXxx("name")` throws an exception | Driver does not support named access or name is invalid | Check driver/version docs; prefer positional binding when appropriate |
| Calling `withNamedBinding()` causes SQL syntax errors | DBMS rejects the provider's named-argument syntax | Remove `withNamedBinding()`, use Map in Spring + positional JDBC |
| `OUT` missing from Map | Missing `SqlOutParameter`, wrong `OUT` position, missing metadata, or different `OUT` key casing | Declare `OUT` with the exact `Types`, position, and inspect actual returned keys |
| Function returns value at the wrong position | Forgetting the return slot of `{? = call ...}` | Use `withFunctionName` and `executeFunction`; check signature and driver |
| Driver metadata is wrong with overloads | DBMS returns multiple signatures or incomplete names/types | Specify exact schema/signature, declare parameters manually, and integration test |
| `null` inferred with the wrong type | Driver cannot infer JDBC type from null | Specify `Types` in `MapSqlParameterSource`/`SqlParameter` |
| Procedure signature changed, Spring code did not | New order/parameters differ from current declarations | Manage migrations and test procedures together with client code |

**Security pitfalls to avoid:** procedure names, schema names, and column names are **SQL identifiers**, never replace them with value placeholders `?` or `:name`. If a routine name comes from user input, map it through an allowlist; never concatenate strings directly. Parameter names are also not an authorization check for calling procedures. The DB user still needs `EXECUTE` privileges and transactions must be coordinated properly.

**Performance pitfalls to avoid:** creating a `SimpleJdbcCall` and introspecting metadata on every request. Configure it once as a reusable DAO/service field so Spring compiles metadata/call strings as needed. When benchmarking with vs. without metadata, measure initialization cost separately from per-call cost; do not conflate the two metrics.

## 9. Rules of choice in a Spring project

- If only running ordinary SQL queries/updates and wanting `:name`, use `NamedParameterJdbcTemplate` or `JdbcClient`. These are Spring name-mapping utilities and do not require driver named APIs.
- If calling stored procedures/functions with `IN`/`OUT`/return values, use `SimpleJdbcCall` with `Map`/`SqlParameterSource`. By default, Spring can bind JDBC positionally; you **do not need** to call `withNamedBinding()` just because inputs are in a Map.
- If driver metadata is accurate and signatures are simple, leverage metadata. If metadata is unreliable or routines are complex, use `withoutProcedureColumnMetaDataAccess()` + full parameter declarations **in exact order**.
- If you want `CallableStatement` to access parameters by name or enable `withNamedBinding()`, verify separately on the **exact DBMS + driver + version + procedure/function signature**.
- When switching DBs or drivers, keep integration tests checking **`IN`, `OUT`, `INOUT`, `NULL`, overloads, errors, and ordering**; a "Spring context starts successfully" test is not enough.

### Self-check questions

1. Why can `SimpleJdbcCall.execute(Map.of("b", ..., "a", ...))` succeed even when `CallableStatement.setInt("a", ...)` is unsupported by the driver?
2. With metadata disabled, if `SqlParameter("p_discount")` is declared before `SqlParameter("p_amount")`, what happens if the real procedure expects amount before discount?
3. Does `withNamedBinding()` change the **SQL syntax** or change key order in the Map? Should it be enabled by default across all DBs?
4. What evidence do you need before claiming a driver supports `registerOutParameter(String,...)`?
