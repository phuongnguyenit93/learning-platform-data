# Multiple Generated Keys or Multiple Key Columns and How to Read Them Properly

When inserting data with JDBC or Spring JDBC, the simple case is a table with one auto-generated `id` column where each `INSERT` creates one row and the code only needs a single numeric value. However, real applications may encounter **multiple columns forming a key**, **multiple database-generated values**, or **multiple rows inserted in one operation**. Always calling `getKey()` or reading the first cell of a `ResultSet` easily loses identifying data, misinterprets results, or throws exceptions.

This lesson explains how to read generated keys according to the actual *shape* of the result: **rows × columns**, distinguish composite primary keys from multiple columns returned by the database, and choose the right API among `Statement.getGeneratedKeys()`, `Spring KeyHolder`, `NamedParameterJdbcTemplate`, and DBMS-specific `RETURNING/OUTPUT` syntax.

## 1. Learning objectives

After this lesson, you will be able to:

1. Distinguish **a single numeric key**, **a multi-column composite primary key**, **multiple generated value columns**, and **multiple rows of generated keys**.
2. Understand why `getGeneratedKeys()` returns a `ResultSet` and why **both rows and columns** must be read once leaving the simple case.
3. Properly use `Connection.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` or the overload requesting returned column names.
4. Read `ResultSetMetaData`, `getColumnLabel(index)`, and `getObject(index)` using **1-based** column indexes.
5. Choose the right `KeyHolder.getKey()`, `getKeyAs(Class)`, `getKeys()`, or `getKeyList()` method in Spring Framework.
6. Write safe Java 17+ code when part of a composite key is already known in the application and the remainder is generated by the database.
7. Know the limitations regarding JDBC drivers, `Long/BigDecimal/UUID` key types, batch ordering, and multi-column retrieval support.
8. Test outcomes with 0/1/many rows, 1/many columns, and transaction rollback scenarios.

## 2. First, distinguish four concepts

Several uses of the phrase “multiple generated keys” may refer to **different** phenomena:

| Concept | Example | What must be read |
| --- | --- | --- |
| **Single auto-generated key** | `shipment_no` generated by identity/sequence | One row × one column; usually returns `Number` |
| **Composite primary key** | `(tenant_id, shipment_no)` | One identifier with **two components**; maybe only one component is auto-generated |
| **Multiple columns returned by database** | `shipment_no` and `created_at` | One row × multiple columns; not every returned column is a “primary key” |
| **Multiple keys for multiple rows** | Insert 3 shipments, receive 3 shipment numbers | Multiple rows × one or multiple columns; must read all results |

**A composite primary key does not mean multiple auto-generated columns.** For instance, `tenant_id` is supplied by the authorization layer while `shipment_no` is generated by a sequence; the `(tenant_id, shipment_no)` pair forms the primary key, yet the database only needs to generate `shipment_no`. Conversely, the database might generate extra columns like `created_at` or `public_id` in a table with only **one** primary key.

Classifying before picking an API prevents two kinds of bugs: dropping part of the identity and forcing a tabular result into a single number.

### Rows × columns model

Picture the results a driver can produce via `getGeneratedKeys()`:

~~~text
1 row × 1 column               1 row × 2 columns
+-------------+                +-----------+-------------+
| shipment_no |                | tenant_id | shipment_no |
+-------------+                +-----------+-------------+
|         301 |                |         7 |         301 |
+-------------+                +-----------+-------------+

2 rows × 1 column              2 rows × 2 columns
+-------------+                +-----------+-------------+
| shipment_no |                | tenant_id | shipment_no |
+-------------+                +-----------+-------------+
|         301 |                |         7 |         301 |
|         302 |                |         7 |         302 |
+-------------+                +-----------+-------------+
~~~

These tables are **structural patterns**, not a guarantee that every driver can return each exact shape from every `INSERT`. Which columns a driver returns, whether it returns multiple rows after a batch, and column names/types are **capabilities that must be verified**.

## 3. Schema example: composite key with only one auto-generated column

Using PostgreSQL to illustrate a concrete schema:

~~~sql
CREATE TABLE shipment (
    tenant_id BIGINT NOT NULL,
    shipment_no BIGINT GENERATED ALWAYS AS IDENTITY,
    state VARCHAR(30) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, shipment_no)
);
~~~

Here:

- `tenant_id` is determined by the application from the authorized tenant.
- `shipment_no` is assigned by PostgreSQL using identity.
- The primary key is **two columns** `(tenant_id, shipment_no)`.
- `created_at` also has a database default, yet **is not part of the primary key**.
- The identity sequence in the example is a database-wide value-allocation mechanism; do not assume it starts at 1 separately per tenant.

An insert statement:

~~~sql
INSERT INTO shipment (tenant_id, state)
VALUES (7, 'NEW');
~~~

After insertion, the application wants `ShipmentKey(tenantId=7, shipmentNo=...)` to reference the newly created row. `tenantId=7` is already known **before INSERT**; we only need to retrieve the database-generated `shipment_no`.

### Do not confuse “composite key” with asking the driver to generate two keys

If code tries to fetch both `tenant_id` and `shipment_no` through the generated-keys API, ask: will the driver treat application-bound `tenant_id` as an *auto-generated column* to return? Being part of the primary key does not guarantee that. A more portable approach is to **keep `tenantId` in Java and only request the generated column**, or use database-specific `RETURNING` syntax to return both columns.

The schema and `GENERATED ALWAYS AS IDENTITY` syntax above are a **PostgreSQL** example, not automatically representative of MySQL/SQL Server/Oracle/H2 DDL. Real systems differ in datatypes, multiple identity columns, and triggers.

## 4. JDBC: how to request generated keys

A `PreparedStatement` can be created with generated-key retrieval enabled.

### 4.1. Generic RETURN_GENERATED_KEYS mode

~~~java
String sql = "INSERT INTO shipment (tenant_id, state) VALUES (?, ?)";
try (PreparedStatement ps = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS)) {
    ps.setLong(1, 7L);
    ps.setString(2, "NEW");
    int affected = ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        while (keys.next()) {
            // Read one generated-keys row returned by the driver.
        }
    }
}
~~~

This is an **integrated JDBC** snippet requiring imports, a `Connection connection`, and a matching database. `Statement.RETURN_GENERATED_KEYS` tells the driver the application wants generated keys. Per the JDBC API, when no specific columns are named, **the driver decides** which columns are appropriate to return.

This is crucial: never assume the driver always returns **only the single id column**, or returns **all defaulted columns**, or returns **the exact two columns of a composite PK**. Such assumptions may hold on one driver and fail on another.

### 4.2. Requesting specific column names

JDBC provides an overload:

~~~java
String sql = "INSERT INTO shipment (tenant_id, state) VALUES (?, ?)";
try (PreparedStatement ps = connection.prepareStatement(
        sql, new String[]{"shipment_no"})) {
    ps.setLong(1, 7L);
    ps.setString(2, "NEW");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            Object shipmentNo = keys.getObject(1);
            // Verify type, row count, and store the identifier.
        }
    }
}
~~~

The `new String[]{"shipment_no"}` argument **requests** the driver to return the generated value in column `shipment_no`. Specifying a column list reduces ambiguity compared to letting the driver choose. Still, column-name handling and returning the exact requested columns depend on the JDBC driver/database; verify with integration tests.

When multiple columns are desired, you can request:

~~~java
connection.prepareStatement(
        sql, new String[]{"shipment_no", "created_at"});
~~~

This is merely an **API capability**: some drivers allow returning `created_at` even though it is a default value, while others only return generated keys in the narrow sense or reject the request. Do not treat passing a two-name array as a portable promise that the result contains two columns.

### 4.3. Not a single number returned directly

`Statement.getGeneratedKeys()` returns a **`ResultSet`**, even when there is only one key. If no keys were generated, the API specifies an empty result set; if the driver does not support it, `SQLFeatureNotSupportedException` or an equivalent error may be thrown depending on the API/driver. You can check `connection.getMetaData().supportsGetGeneratedKeys()` as a metadata-level signal, though testing against the actual SQL and real driver remains necessary.

`executeUpdate()` returns the **affected row count or a code per method contract**, not the generated key value. For instance, an `INSERT` affecting one row and generating `shipment_no=301` produces `affected=1`, completely distinct from `shipment_no=301`. Never use `int affected` as the ID.

## 5. Reading all rows and columns from getGeneratedKeys()

When unsure how many columns/rows a driver returns, use `ResultSetMetaData` to inspect rather than assuming `rs.getLong(1)`.

Java 17+ method template **usable in a JDBC class that already has a valid `ResultSet`**:

~~~java
import java.sql.ResultSet;
import java.sql.ResultSetMetaData;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public final class GeneratedKeyReader {
    private GeneratedKeyReader() {}

    public static List<Map<String, Object>> readAll(ResultSet rs)
            throws SQLException {
        ResultSetMetaData meta = rs.getMetaData();
        int columnCount = meta.getColumnCount();
        List<Map<String, Object>> rows = new ArrayList<>();

        while (rs.next()) {
            Map<String, Object> row = new LinkedHashMap<>();
            for (int column = 1; column <= columnCount; column++) {
                String label = meta.getColumnLabel(column);
                if (row.containsKey(label)) {
                    throw new SQLException(
                            "Duplicate generated-key column label: " + label);
                }
                row.put(label, rs.getObject(column));
            }
            rows.add(row);
        }
        return rows;
    }
}
~~~

**Why read it this way?**

- `while (rs.next())` iterates over **every result row**, not assuming only one row.
- `getColumnCount()` determines the actual column count of the result set.
- JDBC column indexes in `getColumnLabel(column)` and `getObject(column)` are **1-based**.
- `getColumnLabel()` prefers the label/alias exposed by the result set; this can differ from DDL naming.
- `getObject()` preserves the driver's Java type and returns Java `null` for SQL NULL.
- `LinkedHashMap` preserves **read** order of columns for convenient inspection; column order is not the logical identity of a composite key.
- Checking duplicate labels prevents silently overwriting columns if the result set has two identical names/aliases. In production, choose unique labels from the query.

This method **does not produce generated keys**; it only reads a driver-supplied `ResultSet`. Therefore, invoke it after an update statement run with key retrieval enabled, and close the result set properly within its lifecycle.

### Do not read a column by name if the driver returns a different name

Code like:

~~~java
long shipmentNo = keys.getLong("shipment_no");
~~~

only works when the result set has the matching **column label**. Drivers may return different labels or alter casing; verify via `ResultSetMetaData` or specify explicit column names where the driver supports it. Calling `getObject(1)` can be suitable when **you have verified there is only one column**; reading index 1 and assuming it is `shipment_no` when multiple columns exist is unsafe.

### Do not infer type from column name

If `getObject(...)` returns `BigDecimal`, `BigInteger`, `Long`, `Integer`, `UUID`, or a driver-specific type, convert according to the schema and contract. `getLong("shipment_no")` handles SQL numerics, yet can lose SQL NULL information without `wasNull()`. For truly `NOT NULL` keys, null is a data-error signal to handle, not a default ID of 0.

## 6. Complete Java JDBC for a composite key with one generated column

This is a **Java 17 class compilable standalone with the JDK**, though it requires a configured `DataSource` with a JDBC driver, the `shipment` schema, and a compatible PostgreSQL database to execute the insert. It has no `main` and produces no assumed stdout.

~~~java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import javax.sql.DataSource;

public final class ShipmentJdbcDao {
    public record ShipmentKey(long tenantId, long shipmentNo) {}

    private final DataSource dataSource;

    public ShipmentJdbcDao(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public ShipmentKey insert(long authorizedTenantId, String state)
            throws SQLException {
        String sql =
                "INSERT INTO shipment (tenant_id, state) VALUES (?, ?)";

        try (Connection connection = dataSource.getConnection();
             PreparedStatement ps = connection.prepareStatement(
                     sql, new String[]{"shipment_no"})) {

            ps.setLong(1, authorizedTenantId);
            ps.setString(2, state);

            int affected = ps.executeUpdate();
            if (affected != 1) {
                throw new SQLException(
                        "Expected one inserted row, got " + affected);
            }

            try (ResultSet keys = ps.getGeneratedKeys()) {
                if (!keys.next()) {
                    throw new SQLException("No generated shipment_no returned");
                }

                Object raw = keys.getObject(1);
                if (!(raw instanceof Number number)) {
                    throw new SQLException(
                            "shipment_no is not a numeric generated key");
                }

                long shipmentNo = number.longValue();
                if (keys.next()) {
                    throw new SQLException(
                            "Expected one generated-key row");
                }

                return new ShipmentKey(authorizedTenantId, shipmentNo);
            }
        }
    }
}
~~~

Details matching the goal:

- Requests only `shipment_no` because `tenantId` is **already known in Java**.
- JDBC binding indexes: `1 = tenant_id`, `2 = state`.
- Verifies `affected==1`, exactly one generated-key row, and that the value is a `Number`.
- `try-with-resources` closes `ResultSet`, `PreparedStatement`, and `Connection` in proper order, avoiding resource leaks.
- `ShipmentKey` holds **both primary key components** for the application layer to use in subsequent queries/relations.

**Numeric conversion note:** `Number.longValue()` can drop fractional parts or overflow if the source falls outside `long` range. This pattern assumes `shipment_no BIGINT` in the schema and a driver returning an appropriate integer representation. In systems requiring exact verification, validate type/range or use exact conversion methods (such as `BigDecimal.longValueExact()`), rather than forcing every generated value to `long`.

If the method is invoked inside a Spring-managed transaction, use `JdbcTemplate`/`DataSourceUtils` via the transaction manager so you do not accidentally acquire a connection outside the open transaction. The plain JDBC class here is a standalone ownership exercise; the Spring examples in later sections fit Spring applications better.

## 7. Spring KeyHolder represents **List<Map<String, Object>>**

Spring `org.springframework.jdbc.support.KeyHolder` (with common implementation `GeneratedKeyHolder`) stores generated keys in the general structure:

~~~java
List<Map<String, Object>>
~~~

Each **element in the List** corresponds to **one generated-keys row**, and each **entry in the Map** corresponds to **one column/label returned for that row**.

Some illustrations:

~~~text
One row, one column:
[
  {shipment_no=301}
]

One row, two columns:
[
  {tenant_id=7, shipment_no=301}
]

Two rows, one column each:
[
  {shipment_no=301},
  {shipment_no=302}
]

Two rows, two columns each:
[
  {tenant_id=7, shipment_no=301},
  {tenant_id=7, shipment_no=302}
]
~~~

These are **illustrative representations**, not JSON or actual log output; actual maps depend on the columns returned by the driver. Simply looking at the structure makes it clear why an API that “gets one `Number`” cannot represent every case.

### 7.1. getKey(): one row, one column, Number type

`KeyHolder.getKey()` fits the most common scenario: **one** generated-key row, **one** numeric generated-key column.

~~~java
Number value = keyHolder.getKey();
if (value == null) {
    throw new IllegalStateException("No generated key");
}
long id = value.longValue();
~~~

This snippet assumes `keyHolder` came from an INSERT operation. If there are **multiple rows** or a single row contains **multiple columns**, `getKey()` **does not arbitrarily grab the first column**: per Spring's contract, it throws `InvalidDataAccessApiUsageException` when the key count is no longer one. If the value is not a `Number`, use an appropriate reading API/type instead of casting blindly.

### 7.2. getKeyAs(Class<T>): a single value, not necessarily Number

In supporting Spring versions, `getKeyAs(Class<T>)` retrieves a single key of the matching type:

~~~java
UUID id = keyHolder.getKeyAs(UUID.class);
~~~

Use only when the actual result is **one row × one column** and the JDBC driver returns an object whose runtime type is compatible with `UUID`. Do not assume every driver maps SQL UUID to `java.util.UUID`; some drivers return `String` or a custom type. If incompatible, the API can raise a type error; check actual behavior or convert explicitly from an appropriate object.

`getKeyAs(...)` does not turn a multi-column composite key into a single object: it still requires **one** value in **one** row.

### 7.3. getKeys(): one row, possibly multiple columns

When the driver returns one row with multiple columns, use:

~~~java
Map<String, Object> columns = keyHolder.getKeys();
if (columns == null || columns.isEmpty()) {
    throw new IllegalStateException("No generated-key columns");
}

for (Map.Entry<String, Object> entry : columns.entrySet()) {
    System.out.println(entry.getKey() + "=" + entry.getValue());
}
~~~

Here `getKeys()` is only valid when there is **one generated-keys row**. If KeyHolder contains multiple rows, Spring throws `InvalidDataAccessApiUsageException` to avoid losing information. As for how many columns the Map contains, the application handles them itself.

**Do not** do `columns.values().iterator().next()` and assume it is the ID when the Map has multiple entries: Map iteration order is not an identity contract. Read by **confirmed column name**:

~~~java
Object tenant = columns.get("tenant_id");
Object shipment = columns.get("shipment_no");
~~~

This example is **only valid when the actual key labels are `tenant_id`/`shipment_no`**. Drivers may change casing or return different columns; verify the key set via metadata/integration tests. If `tenant_id` is already known from input, there is no need to ask the DB to return it.

### 7.4. getKeyList(): multiple rows, each possibly having multiple columns

When all generated keys across multiple rows are needed:

~~~java
List<Map<String, Object>> keyRows = keyHolder.getKeyList();

for (Map<String, Object> row : keyRows) {
    Object raw = row.get("shipment_no");
    // Verify type and presence of the column in each row.
}
~~~

This is the API for **multiple rows**; if a row contains multiple columns, each Map also has multiple entries. Never call `getKeys()` or `getKey()` on a batch that returned multiple key rows. `getKeyList()` can be empty if the driver returned no keys; check **row count**, column structure, and data types rather than assuming success just because INSERT threw no exception.

### API selection table

| Actual generated-keys shape | Suitable Spring API | What to avoid |
| --- | --- | --- |
| 1 row × 1 numeric column | `getKey()` | Casting to a specific type without checking |
| 1 row × 1 UUID/String column | `getKeyAs(T.class)` if driver returns T | `getKey()` assuming Number |
| 1 row × N columns | `getKeys()` or `getKeyList()` | `getKey()` |
| N rows × 1 column | `getKeyList()` | `getKeys()` and `getKey()` |
| N rows × M columns | `getKeyList()` | Arbitrarily taking first map/row |
| No key rows | Check empty/null and operation contract | Silently returning ID 0 |

## 8. Standalone Java 17 example: distinguishing key shapes

This snippet **does not connect to a database or use Spring**, instead simulating the exact `List<Map<String,Object>>` structure so you can practice “one row × one column” and “multiple rows/columns” before integrating. Uses pure JDK 17 with no external dependencies.

Save file **`GeneratedKeysShapeDemo.java`**:

~~~java
import java.util.List;
import java.util.Map;

public class GeneratedKeysShapeDemo {
    record ShipmentKey(long tenantId, long shipmentNo) {}

    static long onlyNumericKey(List<Map<String, Object>> keyRows) {
        if (keyRows.size() != 1 || keyRows.get(0).size() != 1) {
            throw new IllegalArgumentException("Expected exactly one row and one column");
        }
        Object value = keyRows.get(0).values().iterator().next();
        if (!(value instanceof Number n)) {
            throw new IllegalArgumentException("Expected numeric key");
        }
        return n.longValue();
    }

    static ShipmentKey compositeKey(Map<String, Object> row) {
        Object tenant = row.get("tenant_id");
        Object shipment = row.get("shipment_no");
        if (!(tenant instanceof Number t) || !(shipment instanceof Number s)) {
            throw new IllegalArgumentException("Missing or nonnumeric composite key");
        }
        return new ShipmentKey(t.longValue(), s.longValue());
    }

    public static void main(String[] args) {
        var single = List.<Map<String, Object>>of(
                Map.of("shipment_no", 301L));
        var twoColumns = List.<Map<String, Object>>of(
                Map.of("tenant_id", 7L, "shipment_no", 301L));
        var twoRows = List.<Map<String, Object>>of(
                Map.of("shipment_no", 301L),
                Map.of("shipment_no", 302L));

        System.out.println("Single key: " + onlyNumericKey(single));
        System.out.println("Composite: " + compositeKey(twoColumns.get(0)));
        System.out.println("Rows of generated keys: " + twoRows.size());
        try {
            onlyNumericKey(twoColumns);
        } catch (IllegalArgumentException expected) {
            System.out.println("Cannot flatten two columns into one key");
        }
        try {
            onlyNumericKey(twoRows);
        } catch (IllegalArgumentException expected) {
            System.out.println("Cannot flatten two rows into one key");
        }
    }
}
~~~

Compile and run:

~~~bash
javac --release 17 GeneratedKeysShapeDemo.java
java GeneratedKeysShapeDemo
~~~

Exact stdout:

~~~text
Single key: 301
Composite: ShipmentKey[tenantId=7, shipmentNo=301]
Rows of generated keys: 2
Cannot flatten two columns into one key
Cannot flatten two rows into one key
~~~

**Meaning:** The simulation proves that a function accepting only “one row, one column” must reject multi-column/multi-row cases rather than silently picking the first element. It **does not simulate driver key-generation behavior**, so JDBC/Spring integration tests are still needed to verify actual types/result metadata.

## 9. Spring NamedParameterJdbcTemplate: retrieving one generated key column

In a Spring application that already has a `NamedParameterJdbcTemplate jdbc` bean, you can request a specific key column:

~~~java
import java.util.Map;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public record ShipmentKey(long tenantId, long shipmentNo) {}

public ShipmentKey createShipment(
        NamedParameterJdbcTemplate jdbc,
        long authorizedTenantId,
        String state) {

    String sql = """
            INSERT INTO shipment (tenant_id, state)
            VALUES (:tenantId, :state)
            """;

    var params = new MapSqlParameterSource()
            .addValue("tenantId", authorizedTenantId)
            .addValue("state", state);

    KeyHolder holder = new GeneratedKeyHolder();
    int affected = jdbc.update(
            sql, params, holder, new String[]{"shipment_no"});

    if (affected != 1) {
        throw new IllegalStateException("Expected one inserted row");
    }

    Map<String, Object> row = holder.getKeys();
    if (row == null || row.size() != 1) {
        throw new IllegalStateException(
                "Expected one generated-key column");
    }
    Object raw = row.values().iterator().next();
    if (!(raw instanceof Number n)) {
        throw new IllegalStateException(
                "Generated shipment_no is not numeric");
    }
    return new ShipmentKey(authorizedTenantId, n.longValue());
}
~~~

This is **code illustrating the method and record at class level inside a Spring application**; it cannot be pasted verbatim into a file with a top-level method in Java. For real use, place the record and method inside a valid repository/service class, pass/inject `NamedParameterJdbcTemplate`, and ensure a DataSource bean, JDBC driver, and schema exist. The scenario **requests exactly one key column** and validates the Map has exactly one entry before reading its value. The code does not assume the driver automatically returns `tenant_id`.

**Why use `getKeys()` instead of `getKey()`?** Either can work when the driver returns one numeric key; here `getKeys()` helps enforce the **column count**, aligning with the lesson on result shapes. If the driver returns only one numeric key and the contract is verified, `Number number = holder.getKey()` followed by a null check can be used.

**Mind the snippet's source layout:** Java does not allow top-level methods outside a class; when integrating, write a full repository class and choose where to declare the record properly. The SQL text block closes **before** being passed to `jdbc.update`, avoiding text-block concatenation whitespace issues.

### Compilable Spring class structure example

More complete template (still requires Spring libraries and a database to run):

~~~java
import java.util.Map;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public final class ShipmentRepository {
    public record ShipmentKey(long tenantId, long shipmentNo) {}

    private final NamedParameterJdbcTemplate jdbc;

    public ShipmentRepository(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public ShipmentKey create(long tenantId, String state) {
        String sql = """
                INSERT INTO shipment (tenant_id, state)
                VALUES (:tenantId, :state)
                """;

        var params = new MapSqlParameterSource()
                .addValue("tenantId", tenantId)
                .addValue("state", state);

        KeyHolder holder = new GeneratedKeyHolder();
        int count = jdbc.update(
                sql, params, holder, new String[]{"shipment_no"});
        if (count != 1) {
            throw new IllegalStateException("Expected one inserted row");
        }

        Map<String, Object> columns = holder.getKeys();
        if (columns == null || columns.size() != 1) {
            throw new IllegalStateException(
                    "Expected one generated-key column");
        }
        Object value = columns.values().iterator().next();
        if (!(value instanceof Number number)) {
            throw new IllegalStateException("Generated key is not numeric");
        }
        return new ShipmentKey(tenantId, number.longValue());
    }
}
~~~

For production code, the caller must supply an **authorized `tenantId`**; avoid accepting unauthenticated tenant IDs directly from requests. For consistency when saving multiple tables depending on the new key, call the repository inside an appropriate Spring-managed transaction. Reading the key after `INSERT` occurs **before commit**, so “received an ID” does not mean the transaction committed successfully.

## 10. One row containing multiple returned columns: reading by column name

If the driver supports returning two columns via `keyColumnNames`, Spring can receive a single-row result containing multiple entries:

~~~java
KeyHolder holder = new GeneratedKeyHolder();

int count = namedJdbc.update(
        insertSql,
        params,
        holder,
        new String[]{"shipment_no", "created_at"}
);

Map<String, Object> columns = holder.getKeys();
if (count != 1 || columns == null) {
    throw new IllegalStateException("No single-row key result");
}
Object number = columns.get("shipment_no");
Object createdAt = columns.get("created_at");
~~~

This is an **integration example conditional on driver support**. `created_at` may be a database default rather than a key component; it is simply a **value returned alongside by the database**. Do not call `getKey()` if two columns were actually returned, because `getKey()` requires exactly one column.

**Important:** passing two column names **does not guarantee** both are returned. Check `columns.keySet()`, nullability, and runtime JDBC types. If the DBMS must provide all columns deterministically, consider database-specific `RETURNING/OUTPUT` syntax.

### Reading a composite key from a Map

A hypothetical result:

~~~text
columns = {tenant_id=7, shipment_no=301}
~~~

Can be mapped as:

~~~java
Object tenantRaw = columns.get("tenant_id");
Object shipmentRaw = columns.get("shipment_no");

if (!(tenantRaw instanceof Number t)
        || !(shipmentRaw instanceof Number s)) {
    throw new IllegalStateException("Composite key columns missing");
}
ShipmentRepository.ShipmentKey key =
        new ShipmentRepository.ShipmentKey(
                t.longValue(), s.longValue());
~~~

This illustrative snippet requires `ShipmentRepository` from earlier and a Map with matching labels. Never rely on Map value iteration order to build a composite key: `(tenant_id, shipment_no)` has meaning **by field name**. If column labels differ from expected names, handle via verified metadata/aliases rather than silently swapping two numeric values.

## 11. When to use SQL RETURNING or OUTPUT?

Not every database/driver returns multiple generated columns via `getGeneratedKeys()` conveniently. Some DBMSs allow write statements to **directly return the columns you request**.

### PostgreSQL: INSERT ... RETURNING

With the `shipment` schema from section 3:

~~~sql
INSERT INTO shipment (tenant_id, state)
VALUES (:tenantId, :state)
RETURNING tenant_id, shipment_no, created_at;
~~~

In PostgreSQL, `RETURNING` specifies the three columns to retrieve. A Java record representing the **composite primary key** can be constructed from the first two columns; `created_at` is metadata generated with the row rather than part of the key.

With `NamedParameterJdbcTemplate` and a PostgreSQL JDBC driver supporting results from `RETURNING`, a query-style approach is:

~~~java
String sql = """
        INSERT INTO shipment (tenant_id, state)
        VALUES (:tenantId, :state)
        RETURNING tenant_id, shipment_no
        """;

var params = new MapSqlParameterSource()
        .addValue("tenantId", authorizedTenantId)
        .addValue("state", state);

ShipmentRepository.ShipmentKey key = namedJdbc.queryForObject(
        sql,
        params,
        (rs, rowNum) -> new ShipmentRepository.ShipmentKey(
                rs.getLong("tenant_id"),
                rs.getLong("shipment_no"))
);
~~~

This is a **PostgreSQL integration example**, not portable SQL. When using `INSERT ... RETURNING`, you are reading a ResultSet from the write statement, so pick an API capable of reading results instead of expecting `int updateCount` to be the key. If 0/multiple rows violate `queryForObject`'s contract, Spring applies the corresponding cardinality rules; handle errors per business logic.

If code needs newly generated defaults like `created_at`, add the column to `RETURNING` and map an appropriate record/DTO. Correctness and data structure depend on PostgreSQL, the query, and the driver in use.

### SQL Server: OUTPUT INSERTED

SQL Server has a semantically similar feature with **different syntax**:

~~~sql
INSERT INTO shipment (tenant_id, state)
OUTPUT INSERTED.tenant_id, INSERTED.shipment_no
VALUES (@tenantId, @state);
~~~

This is a **T-SQL syntax template**; do not use `@tenantId` directly in `NamedParameterJdbcTemplate` as if it were Spring syntax. When implementing in Java, choose valid parameter markers for your driver/framework and adapt for SQL Server. `OUTPUT` results can contain multiple rows/columns, so they must still be read according to the actual shape.

Other systems like Oracle support `RETURNING ... INTO` with different mechanisms/binding; MySQL has its own auto-increment ID retrieval mechanism and constraints. **Do not copy syntax verbatim across databases.** Pick the API according to the driver + dialect verified in tests.

## 12. Multiple rows inserted: generated keys can have multiple rows

Example of business expectation:

~~~text
Input 1 -> INSERT row A -> generated shipment_no 301
Input 2 -> INSERT row B -> generated shipment_no 302
Input 3 -> INSERT row C -> generated shipment_no 303
~~~

Some drivers can return multiple generated-key rows during a **multi-row INSERT** or **JDBC batch**. However, this is error-prone:

1. The generated-key row count may not match the input row count when the driver lacks support or uses specialized SQL.
2. The order of generated-key rows is **not a portable guarantee** that they always match input/batch order.
3. Batch update counts are not generated IDs.
4. One rejected record can fail the whole batch or yield partial results depending on driver/transaction policy.
5. When each row returns multiple columns, you must map each row before using it.

### Spring NamedParameterJdbcTemplate.batchUpdate and KeyHolder

Spring has an overload accepting `KeyHolder`:

~~~java
String sql = """
        INSERT INTO shipment (tenant_id, state)
        VALUES (:tenantId, :state)
        """;

SqlParameterSource[] batch = {
        new MapSqlParameterSource()
                .addValue("tenantId", 7L)
                .addValue("state", "NEW"),
        new MapSqlParameterSource()
                .addValue("tenantId", 7L)
                .addValue("state", "PENDING")
};

KeyHolder keys = new GeneratedKeyHolder();

int[] counts = namedJdbc.batchUpdate(
        sql, batch, keys, new String[]{"shipment_no"});

List<Map<String, Object>> keyRows = keys.getKeyList();
~~~

This is **integration code** with appropriate Spring imports. This overload requires **driver support for generated keys in batches**. Do not assume `keyRows.size()==batch.length` or that element `i` is the ID of input `i` without specific driver/schema evidence. `counts` may also contain JDBC values such as `SUCCESS_NO_INFO` or `EXECUTE_FAILED`, which cannot be used as IDs.

### How to map keys back to inputs safely?

If a reliable mapping between input rows and generated rows is needed:

- When feasible, process **each INSERT individually** (within a transaction) and retrieve the key right after its statement. This is simple, though potentially less efficient than batching.
- Or use a unique application-generated **correlation token**/business key included in each row; query/return **both the token and generated key** via a dialect-appropriate mechanism, then match by token.
- With PostgreSQL, `RETURNING` can return row columns, yet still avoid inferring a fixed order without an explicit contract. Token-based correlation is more reliable than positional ordering.
- If a driver has a documented guarantee on key ordering and count for a specific operation, you can rely on it and guard it with integration tests on driver upgrades.

**Do not assume** three IDs are sequentially 301, 302, 303 from one insert call. Sequences/identities can have gaps, jump values, experience concurrency, or roll back; contiguity is not a generated-key contract.

## 13. A composite primary key may have zero auto-generated columns

Not every composite primary key needs `getGeneratedKeys()`. For example:

~~~sql
CREATE TABLE enrollment (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    enrolled_at TIMESTAMP NOT NULL,
    PRIMARY KEY (student_id, course_id)
);
~~~

If Java already has `studentId` and `courseId`, the entire key is known before INSERT. Simply bind and execute:

~~~java
String sql = """
        INSERT INTO enrollment (student_id, course_id, enrolled_at)
        VALUES (:studentId, :courseId, :enrolledAt)
        """;
var params = new MapSqlParameterSource()
        .addValue("studentId", studentId)
        .addValue("courseId", courseId)
        .addValue("enrolledAt", enrolledAt);
int affected = namedJdbc.update(sql, params);
~~~

**Do not use the generated-key API merely because the primary key has multiple columns.** Distinguish “composite” (multiple fields forming identity) from “generated” (values created by the database). An `EnrollmentKey(studentId, courseId)` record can be built directly from the two known inputs.

If business logic wants a composite key with a **per-tenant** sequential component, do not compute `MAX(shipment_no)+1` and insert: concurrent transactions can see the same old MAX. Use properly synchronized sequences/counters, unique constraints, and appropriate database transaction isolation/locking.

## 14. Non-integer generated key types

`getKey()` is designed for a **single numeric value**. In modern systems, generated identifiers can be:

- BIGINT/INTEGER identity or sequence → may map to `Long`, `Integer`, `BigDecimal`, or another `Number`.
- Database-generated UUID → may be `UUID`, `String`, or a driver-specific object.
- String code or trigger/procedure-generated token → usually needs reading via matching type/string mapping.
- Composite value → requires a multi-component record/DTO, not cramming into a `Long`.

### Checking type/range instead of casting `(Long) getKey()`

Anti-pattern:

~~~java
Long id = (Long) keyHolder.getKey();
~~~

If the driver returns `BigDecimal` even for an integer value, casting throws `ClassCastException`. Better approach for numeric IDs:

~~~java
Number raw = keyHolder.getKey();
if (raw == null) {
    throw new IllegalStateException("No generated numeric key");
}
long id = raw.longValue();
~~~

This avoids a rigid cast, yet still requires **checking range/precision** if the database can allocate numbers outside Java `long` range. For `BigDecimal`:

~~~java
BigDecimal raw = (BigDecimal) value;
long exact = raw.longValueExact();
~~~

This illustrates the case when `value`'s runtime type is *already verified* as `BigDecimal`. `longValueExact()` throws `ArithmeticException` if there is a fractional part or overflow, which is better than silently rounding/truncating. `BigInteger` has a corresponding `longValueExact()` method.

### Java-generated UUIDs do not need the database to generate IDs

If the application is permitted to choose the ID before insertion:

~~~java
UUID id = UUID.randomUUID();
String sql = "INSERT INTO document (id, title) VALUES (:id, :title)";
var params = new MapSqlParameterSource()
        .addValue("id", id)
        .addValue("title", title);
namedJdbc.update(sql, params);
~~~

This is an **app-generated key**, not a database-generated key. You already have `id` before INSERT; no `getGeneratedKeys()` is needed just to fetch it back. The database still needs a uniqueness constraint and UUID mapping tests for the actual dialect/driver.

## 15. Transactions: obtaining a key does not mean data committed

JDBC generated keys are usually read after a statement succeeds, yet **before the transaction commits** (when a transaction is open). Example:

~~~text
BEGIN TRANSACTION
    INSERT shipment -> receives shipment_no = 301
    INSERT shipment_item referencing (tenant_id=7, shipment_no=301)
    ...
ROLLBACK (due to a business error)
~~~

The application may have received `301`, yet the row no longer exists after rollback. Therefore:

- Do not announce “permanently saved” just because `getGeneratedKeys()` had data.
- Never use identity/sequence numbers to infer committed row counts or contiguous ranges.
- Never run `SELECT MAX(id)` after insert to determine the key: concurrent transactions and multiple connections can yield wrong results.
- When creating parent/child records in one business flow, use the retrieved key **within the same transaction** to write child rows, then commit/roll back all together via the proper transaction manager.
- Events emitted externally before commit can expose the ID of a rolled-back row to consumers; use an outbox or post-commit event mechanism when consistency is needed.

In Spring, use `@Transactional` with the transaction manager matching the DataSource. Do not accidentally open a separate connection and assume all updates share one transaction.

## 16. Common mistakes when reading multiple generated keys

| Mistake | Why it is wrong | Fix |
| --- | --- | --- |
| Calling `getKey()` on a two-column Map | API only accepts exactly one key | Use `getKeys()` and read each column by name |
| Calling `getKeys()` when multiple rows exist | API is for a single row only | Use `getKeyList()` |
| Calling `rs.next()` once when batch produces multiple keys | Skips remaining rows | Loop with `while(rs.next())` |
| `rs.getLong(1)` on multi-column result set without checking metadata | Unknown what column 1 is | Specify columns, inspect metadata, read by label |
| `(Long) holder.getKey()` | Driver may return another Number type | Read `Number`, validate range/precision |
| Two-column composite key keeping only the generated identity | Loses the other identity component | Build record containing both, combining known part with DB-generated part |
| Assuming `RETURN_GENERATED_KEYS` always returns all default columns | Driver decides when unspecified | Request `keyColumnNames` or DB-specific `RETURNING` |
| Assuming `affected == generatedId` | Update count is row count, not key | Read `getGeneratedKeys()`/`KeyHolder` |
| Unverified mapping batch index i ↔ returned key row i | No portable ordering guarantee | Correlation token or row-by-row insert |
| `MAX(id)+1` to self-generate IDs | Concurrency race condition | Use identity/sequence and unique constraints |
| Assuming reading a key means row committed | Transaction may roll back | Manage transactions, confirm commit |
| Map key name differs in casing | JDBC drivers can alter labels | Inspect metadata/keySet, test on real driver |
| Ignoring empty `getGeneratedKeys()` | Missing key to construct domain identity | Fail explicitly or use alternative return mechanism |
| Failing to close ResultSet/Statement/Connection | Resource/pool leak | `try-with-resources` or Spring JDBC resource management |

### Distinguishing unsupported feature errors from missing keys

An empty `ResultSet` can mean the statement generates no keys, no row was actually inserted, or the driver mechanism does not return keys in that scenario. Meanwhile, `SQLFeatureNotSupportedException`/related JDBC errors typically indicate the driver does not implement the requested capability. Never return ID 0 in either case; record the SQL template, update count, driver, schema, statement preparation method, and contract.

## 17. Diagnostic workflow when KeyHolder unexpectedly contains multiple keys

Suppose existing code:

~~~java
Number id = holder.getKey();
~~~

starts throwing `InvalidDataAccessApiUsageException` after changing a JDBC driver or schema.

Follow these steps:

1. Confirm whether the SQL actually inserts **one or multiple rows**, and whether batching/triggers/dialect extensions are involved.
2. Confirm whether `RETURN_GENERATED_KEYS` or specific `keyColumnNames` were requested.
3. Inspect `holder.getKeyList().size()` (row count) and the number of key columns in each Map in a **secured test environment**. Do not log sensitive raw data.
4. Compare against the contract: do you need only one numeric ID, a composite key, default metadata, or multiple IDs?
5. If one row with multiple columns, switch to `getKeys()` and map by name; if multiple rows, use `getKeyList()`.
6. Check the runtime type and label of each value; do not force-cast Long or assume column names.
7. Re-verify transactions and how keys link back to input rows; for batches, do not pair by position if the driver makes no guarantee.
8. If driver support is unstable, consider dialect-specific `RETURNING/OUTPUT` or application-side ID generation.

An effective review question: **How many rows are in the result? How many columns are in each row? Which columns actually constitute the business key?** Answering all three usually points straight to the right API.

## 18. Testing result shapes

Set up integration tests on the project's real database/driver and verify:

| Case | Condition | Expected outcome |
| --- | --- | --- |
| One row × one numeric key | INSERT one shipment, request `shipment_no` | One numeric value in valid range |
| One row × multiple columns | Driver supports returning `shipment_no` and `created_at` | One Map with expected columns/types per contract |
| Partially known composite key | Tenant ID from request context, shipment_no DB-generated | Record has accurate tenantId and shipmentNo |
| Fully pre-supplied composite key | Enrollment (student_id, course_id) | No generated keys needed |
| Multi-row batch | Two or more INSERTs in batch | Check how many rows, labels, order/association driver returns |
| No generated key | Driver/schema does not generate or return | Handle empty intentionally; never fake ID=0 |
| UUID/String key | DB generates non-numeric ID if supported | Read proper type; do not call numeric getKey |
| Metadata differs from expected label | Driver returns different alias/case | Code does not silently swap columns |
| Rollback after key retrieval | Insert in transaction, get key, then roll back | Row does not exist after rollback |
| Concurrent inserts | Multiple transactions insert in parallel | Never determine ID via MAX/id+1; keys truly unique |
| Driver upgrade | Compare generated-key metadata across versions | Detect if shape, labels, or types change |

In Java 17 unit tests, you can separately test mappers over `List<Map<...>>` like `GeneratedKeysShapeDemo` in section 8. However, **that test does not verify the driver**: integration tests against the actual schema and database are still required.

### Suggested assertions

- For one numeric key: `assertEquals(1, keyRows.size())` and `assertEquals(1, keyRows.get(0).size())` before converting.
- For one row with multiple columns: assert Map contains expected key column labels with valid types/nullability.
- For multiple rows: assert row count **only when the driver has a clear contract**; verify correlation if pairing back to inputs.
- For rollback: query by composite key after transaction rollback and confirm no row exists, rather than trusting an ID held in a Java variable.
- Never assert that identity sequences are always contiguous or gap-free.

## 19. Strategy selection checklist

Before writing a repository to persist an object:

1. **How many components does the identifying key have?** If composite, identify every component.
2. **Which components are application-supplied and which are DB-generated?**
3. **How many rows can a single call insert?** If multiple, what generated result shape is expected?
4. **Do the driver and database support `getGeneratedKeys()` and requesting `keyColumnNames`?**
5. **Does the result need extra default/trigger values beyond the PK?** If yes, is `RETURNING/OUTPUT` more suitable?
6. **Is the result numeric, UUID, or string?** Check runtime mapping before type conversion.
7. **Must IDs be mapped back to each input in a batch?** If yes, reliable correlation is needed.
8. **Is there a multi-step transaction depending on the newly generated key?** Ensure the same transaction/connection context.
9. **Does the API check 0/1/many rows and columns?** Never silently grab the first element.
10. **Are there integration tests for the deployed JDBC driver and schema?**

For simple cases, `getKey()` is very convenient. For complex cases, **preserving the true data structure** and mapping it into a domain record is far more robust than forcing everything into a single `Long`.

## 20. Review questions

**Question 1.** A table has primary key `(tenant_id, shipment_no)`; only `shipment_no` is auto-generated. Must the DB return both columns via `getGeneratedKeys()`?  
**Answer:** Not mandatory. The application already knows tenantId, so it can request only shipmentNo and construct a record containing both. Or use `RETURNING` to return the full set if suitable for the DB.

**Question 2.** Can `KeyHolder.getKey()` be used when the result contains one row and two columns?  
**Answer:** No. Its contract requires one row × one numeric key; when multiple columns exist, use `getKeys()` or `getKeyList()`.

**Question 3.** With a KeyHolder having three rows, one column each, what should you call?  
**Answer:** `getKeyList()` and process each Map according to the ordering/association verified by the driver/tests.

**Question 4.** `executeUpdate()` returns 1. Does the row's generated key have to equal 1?  
**Answer:** No. 1 is typically the update count, not the generated ID.

**Question 5.** You use `Statement.RETURN_GENERATED_KEYS` without naming columns; are you guaranteed to receive every defaulted column?  
**Answer:** No. The driver decides which columns are appropriate; specify key columns if supported or use dialect-specific SQL RETURNING.

**Question 6.** You obtain `shipment_no=301` and then the transaction rolls back. Does the newly inserted row still exist?  
**Answer:** No, if the transaction actually rolled back successfully. Having an ID in Java does not mean the data committed.

**Question 7.** The driver returns `BigDecimal` for a DB ID; is `(Long)holder.getKey()` safe?  
**Answer:** No. Use `Number` and convert with range/precision checks; direct casting can throw ClassCastException.

**Question 8.** A batch inserts 3 rows and getKeyList contains 3 rows. Can you always pair them by index 0, 1, 2 with inputs?  
**Answer:** There is no portable guarantee. You need an explicit driver contract or a correlation token; otherwise insert row-by-row.

**Question 9.** A table has a composite PK where the caller knows both components. Is `getGeneratedKeys()` needed?  
**Answer:** No. The components are already known before INSERT; just write the proper keys and constraints.

**Question 10.** Why should `getColumnLabel(1)` and `getObject(1)` be placed in a column loop starting from 1?  
**Answer:** JDBC column indexes are 1-based; reading via result set metadata identifies every column returned by the driver.

## 21. Summary

**Generated keys are tabular results, not automatically a single number.** A well-written application clearly identifies the returned rows × columns shape, which key components are already known, which components the database generates, and the JDBC driver's contract.

- Use `Statement.getGeneratedKeys()` with `ResultSet.next()` and `ResultSetMetaData` to read all rows/columns when needed.
- Use `KeyHolder.getKey()` only for **one numeric key**, `getKeyAs(...)` for a single typed key, `getKeys()` for **one row with multiple columns**, and `getKeyList()` for **multiple rows**.
- Use key column names when supported by the driver; choose `RETURNING/OUTPUT` when an explicit set of returned columns is needed and supported by the DBMS.
- For composite keys, assemble fields by **name and meaning**, not by Map iteration order.
- For batches and transactions, be careful about correlation, rollback, driver support, and sequence gaps.
