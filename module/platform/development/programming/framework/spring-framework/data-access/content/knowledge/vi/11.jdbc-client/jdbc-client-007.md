# Chạy update() và lấy khóa sinh theo API phiên bản — Spring JdbcClient

Trong Spring JDBC, **JdbcClient.update()** là thao tác thực thi INSERT, UPDATE hoặc DELETE và **trả về số hàng ảnh hưởng** (kiểu int). Nếu INSERT vào bảng có cột ID do database sinh, con số ấy **không phải khóa mới**. Để thu thập generated key, Spring Framework 6.1+ cung cấp overload **update(KeyHolder)** và **update(KeyHolder, String... keyColumnNames)**; còn các phiên bản Spring cũ dùng **JdbcTemplate**, **NamedParameterJdbcTemplate** hoặc **SimpleJdbcInsert**.

Đây là bài thuộc nhóm **JdbcClient** trong module **Spring Framework - data-access**. Bài tập trung vào việc chọn API theo phiên bản Spring, phân biệt affected row count với generated ID, sử dụng **GeneratedKeyHolder** đúng cách, tình huống driver không trả key, cú pháp **RETURNING** của PostgreSQL, giao dịch và kiểm thử bằng ví dụ Java 17+.

## 1. Hai kết quả khác nhau khi INSERT

Giả sử bảng có ID do database sinh:

~~~sql
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(80) NOT NULL UNIQUE
);
~~~

H2 hỗ trợ cú pháp trên; PostgreSQL có cú pháp identity tương tự. Một INSERT:

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
~~~

có thể cho biết hai thông tin:

| Thông tin | Ví dụ | Ý nghĩa |
| --- | --- | --- |
| **Affected row count** | 1 | INSERT đã tác động một hàng |
| **Generated key** | 42 | ID do database gán cho hàng mới |
| **SQL RETURNING result** | Một dòng gồm id=42 | Dữ liệu DB trả về khi statement có RETURNING |
| **Transaction commit status** | Chưa biết | INSERT có thể chưa được commit ở thời điểm nhận key |

Hãy nhìn ví dụ JdbcClient:

~~~java
int rows = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (:name)")
    .param("name", "Lan")
    .update();
~~~

**rows == 1 không đồng nghĩa ID vừa sinh bằng 1.** Khi sequence đã tạo hàng thứ 1000, update() vẫn có thể trả 1, còn ID là 1000 hoặc một giá trị khác. Trả int này thuộc ngữ nghĩa JDBC **executeUpdate()**, không phải cơ chế trả khóa.

Một nhầm lẫn nguy hiểm:

~~~java
// SAI: newId thực chất là số hàng ảnh hưởng.
long newId = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Lan")
    .update();
~~~

Java cho phép tự mở rộng int thành long, nên ví dụ trên **biên dịch được** nhưng newId là **row count**, không phải primary key. Unit test chỉ chèn hàng đầu tiên có ID 1 có thể vô tình qua; khi chạy lâu dài sẽ dùng sai ID.

## 2. Cách dùng update() cho các câu lệnh ghi

Phương thức JdbcClient.StatementSpec.update() không chỉ dùng cho keyword SQL UPDATE; nó thường dùng với INSERT, UPDATE và DELETE.

~~~java
// INSERT với tham số theo vị trí.
int inserted = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Minh")
    .update();

// UPDATE với tham số có tên.
int renamed = jdbcClient
    .sql("""
         UPDATE members
         SET display_name = :name
         WHERE id = :id
         """)
    .param("name", "Minh Anh")
    .param("id", 10L)
    .update();

// DELETE theo khóa chính.
int deleted = jdbcClient
    .sql("DELETE FROM members WHERE id = :id")
    .param("id", 999L)
    .update();
~~~

Đây là **đoạn minh họa nằm trong repository đã có JdbcClient và bảng members**, không phải class độc lập. Kết quả thường là:

- INSERT một hàng thành công: affected = 1.
- UPDATE hoặc DELETE với ID không tồn tại: affected = 0.
- UPDATE/DELETE làm thay đổi nhiều hàng: affected có thể >1.
- SQL/constraint/connection lỗi: Spring có thể ném **DataAccessException** thích hợp, không trả một ID đặc biệt.

**Phân biệt “0 hàng” với “lỗi”.** Nếu một repository cần đổi tên đúng một member đã tồn tại, affected == 0 có thể là tín hiệu không tìm thấy. Nếu cùng phương thức có câu WHERE không đủ chặt và affected >1, đó có thể là vi phạm hợp đồng. Không tùy tiện coi mọi affected >0 là “đã cập nhật đúng một người”.

Một số DBMS/driver khác nhau về cách tính số hàng “matched” và “changed” khi UPDATE một giá trị giống trước đó. Cần đo trên DBMS thực tế nếu ứng dụng dựa vào chi tiết này.

### 2.1. Bind tham số không phải dựng SQL động

JdbcClient hỗ trợ:

~~~java
jdbcClient.sql("DELETE FROM members WHERE id = ?")
    .param(5L)
    .update();

jdbcClient.sql("DELETE FROM members WHERE id = :id")
    .param("id", 5L)
    .update();
~~~

Cả hai đều bind **giá trị ID**. Tên bảng members, tên cột id và cú pháp DELETE là cấu trúc SQL cố định. Không lấy tên bảng/cột từ request rồi nối thẳng vào SQL. Parameter binding giúp ngăn SQL injection ở những vị trí giá trị được bind nhưng **không tự bảo vệ** phần SQL nối chuỗi từ input chưa kiểm soát.

## 3. Bảng so sánh API theo phiên bản Spring

**JdbcClient được giới thiệu trong Spring Framework 6.1**. Tài liệu Javadoc của **Spring 6.1.8** đã liệt kê đầy đủ ba overload update trong JdbcClient.StatementSpec:

~~~java
int update();
int update(KeyHolder generatedKeyHolder);
int update(KeyHolder generatedKeyHolder, String... keyColumnNames);
~~~

| Phiên bản Framework | Có JdbcClient? | Cách trả generated key |
| --- | --- | --- |
| Spring 5.x | **Không** | JdbcTemplate, NamedParameterJdbcTemplate, SimpleJdbcInsert |
| Spring 6.0.x | **Không** | Các API JDBC truyền thống |
| Spring 6.1.x | **Có** | JdbcClient.update(holder), update(holder, "id") |
| Spring 6.2.x | **Có** | Cùng overload KeyHolder, kiểm tra version cụ thể |
| Spring 7.0.x | **Có** | Các overload trên tiếp tục tồn tại |
| Spring 7.1 và các bản phát triển mới hơn | Có thể có thêm API như batch() | Đọc đúng Javadoc của dependency trước khi dùng |

**Không nhầm rằng update(KeyHolder) mới xuất hiện trong Spring 6.2**; nó đã có từ thế hệ JdbcClient 6.1. Ngược lại, các bài viết dùng JdbcClient không thể copy nguyên xi vào dự án Spring 6.0 vì **lớp JdbcClient chưa tồn tại**.

### 3.2. Không suy diễn tên method giữa các lớp

| Class | API | Giá trị trả trực tiếp |
| --- | --- | --- |
| JdbcClient.StatementSpec | **update()** | int affected |
| JdbcClient.StatementSpec | **update(KeyHolder)** | int affected, key nằm trong holder |
| JdbcClient.StatementSpec | **update(KeyHolder, String...)** | int affected, key nằm trong holder |
| JdbcTemplate | **update(PreparedStatementCreator, KeyHolder)** | int affected, key nằm trong holder |
| NamedParameterJdbcTemplate | **update(sql, SqlParameterSource, KeyHolder, String[])** | int affected, key nằm trong holder |
| SimpleJdbcInsert | **executeAndReturnKey(...)** | Number generated key |
| SimpleJdbcInsert | **executeAndReturnKeyHolder(...)** | KeyHolder chứa key |

JdbcClient **không** có một API chung tên executeAndReturnKey() chỉ vì SimpleJdbcInsert có method đó. Mỗi class có chữ ký và vai trò khác nhau.

## 4. Lấy generated ID với JdbcClient và GeneratedKeyHolder

**KeyHolder** là interface thuộc package **org.springframework.jdbc.support**; **GeneratedKeyHolder** là implementation chuẩn, lưu các key do JDBC driver trả về.

Cách được khuyến nghị khi biết tên cột khóa cần thu thập:

~~~java
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long createMember(String displayName) {
    GeneratedKeyHolder holder = new GeneratedKeyHolder();

    int affected = jdbcClient
        .sql("""
             INSERT INTO members (display_name)
             VALUES (:name)
             """)
        .param("name", displayName)
        .update(holder, "id");

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, actual=" + affected
        );
    }

    Number key = holder.getKey();
    if (key == null) {
        throw new IllegalStateException(
            "JDBC driver did not return the generated id"
        );
    }
    return key.longValue();
}
~~~

Đây là **method trong một repository đã có trường jdbcClient**. Bảng members và cột identity id phải tồn tại. Đoạn mã không tự chạy bằng javac vì không có main và không khai báo toàn bộ class.

Quy trình:

1. **new GeneratedKeyHolder()** riêng cho một INSERT.
2. Đặt SQL và bind **giá trị**.
3. Gọi **update(holder, "id")**, trả int affected và yêu cầu JDBC trả generated key của cột id.
4. Kiểm tra affected == 1 theo hợp đồng “một insert”.
5. Gọi **getKey()** lấy Number, kiểm tra khác null.
6. Chuyển Number sang long **chỉ khi schema dùng kiểu ID tương thích BIGINT**.

**Cực kỳ quan trọng:** returned int và key đọc từ holder là hai kết quả độc lập. Không đọc nhầm int affected làm key, và không coi có key là bằng chứng transaction đã commit.

### 4.1. Vì sao nên chỉ định tên cột "id"?

Nếu gọi:

~~~java
GeneratedKeyHolder holder = new GeneratedKeyHolder();

int affected = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Lan")
    .update(holder);
~~~

driver phải tự chọn các cột generated key cần trả. Với nhiều driver điều này hoạt động, nhưng có thể nhận **nhiều cột**, cột ngoài ý muốn, giá trị non-numeric, ROWID hoặc không nhận được key. Cách **update(holder, "id")** cung cấp thông tin rõ hơn cho driver.

Tên **"id"** ở đây là tên identifier SQL cố định, không phải một giá trị bind. Tính hỗ trợ column name selection vẫn phụ thuộc DBMS/driver. Đặc biệt với một số driver Oracle, gọi update(holder) không chỉ định key column có thể nhận ROWID thay vì khóa số, khiến getKey() thất bại.

Không được giả định rằng KeyHolder tự phân tích schema và tìm cột PRIMARY KEY chính xác trong mọi DBMS.

### 4.2. getKey(), getKeys(), getKeyList() và getKeyAs()

Một KeyHolder có thể chứa **một hay nhiều hàng**, mỗi hàng có **một hay nhiều cột** generated values.

| API | Dùng cho | Lưu ý |
| --- | --- | --- |
| **getKey()** | Một hàng, một cột key kiểu Number | Có thể null nếu không có key; lỗi khi nhiều key |
| **getKeyAs(Class<T>)** | Một hàng, một key có kiểu cụ thể | Driver phải trả kiểu tương thích T |
| **getKeys()** | Một hàng, nhiều cột key | Map cột/giá trị; không dùng nếu nhiều hàng |
| **getKeyList()** | Nhiều hàng hoặc cần xem raw key records | List<Map<String,Object>> |

Ví dụ API:

~~~java
Number numericKey = holder.getKey();

java.util.Map<String, Object> keyMap = holder.getKeys();

java.util.List<java.util.Map<String, Object>> keyRows =
    holder.getKeyList();
~~~

Đây là snippet đọc từ cùng holder, **không phải yêu cầu phải gọi tất cả method để lấy key**. Nếu getKey() gặp nhiều cột hoặc nhiều hàng, nó có thể ném **InvalidDataAccessApiUsageException** thay vì tự chọn một.

Với key không phải số (ví dụ UUID), không gọi getKey().longValue(). Khi driver trả đúng kiểu UUID, có thể dùng getKeyAs(UUID.class); nếu trả kiểu khác phải map rõ ràng hoặc dùng PostgreSQL RETURNING. Tên cột trong Map có thể khác chữ hoa/chữ thường theo JDBC driver, đặc biệt ở H2/Oracle.

### 4.3. Mỗi INSERT phải có holder riêng

~~~java
// KHÔNG đặt trường này vào singleton repository:
private final GeneratedKeyHolder sharedHolder =
    new GeneratedKeyHolder();
~~~

GeneratedKeyHolder là container **mutable**; nếu dùng chung giữa nhiều request/threads, key có thể trộn lẫn. Tạo holder **local** cho từng thao tác. JdbcClient có thể dùng chung dưới dạng bean đã cấu hình, còn trạng thái key từng lượt phải độc lập.

## 5. Generated keys phụ thuộc schema, JDBC driver và cách prepare

Một API có đúng chữ ký vẫn không tự biến một ID chưa tồn tại thành generated key. Cần đồng thời xác minh:

1. **Schema thực sự sinh giá trị**: identity, sequence/default, trigger hoặc tính năng phù hợp.
2. **Driver hỗ trợ generated keys**, liên quan DatabaseMetaData.supportsGetGeneratedKeys().
3. **Statement được tạo ở chế độ yêu cầu generated keys** — overload KeyHolder của Spring hỗ trợ việc đó.
4. **Tên cột khóa chính xác** nếu chỉ định keyColumnNames.
5. **Số hàng/số cột returned keys** phù hợp cách đọc getKey hoặc getKeyList.
6. **Kiểu dữ liệu** returned value tương thích Number/UUID/String theo hợp đồng.

Chỉ khai PRIMARY KEY **không đủ** để DB tự sinh ID. Ví dụ:

~~~sql
-- Có IDENTITY: DB có thể sinh id.
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(80) NOT NULL
);
~~~

Ngược lại, nếu cột id là BIGINT PRIMARY KEY **không có DEFAULT/IDENTITY** và ứng dụng không truyền ID, INSERT có thể thất bại. Nếu ứng dụng dùng UUID.randomUUID() rồi truyền vào INSERT, ID do **Java tạo**; không cần KeyHolder để biết giá trị ấy.

### 5.1. Một inserted row chưa chắc sinh một key duy nhất

Một DB có thể sinh cả ID lẫn timestamp, computed column hoặc giá trị default. Một số driver khi được yêu cầu RETURN_GENERATED_KEYS có thể trả hơn một cột. getKey() chỉ hợp lý khi **một hàng có đúng một khóa số**; với nhiều cột dùng getKeys() hoặc yêu cầu cột id cụ thể.

Một batch insert có thể trả nhiều hàng key; khi đó getKeyList() là cấu trúc thích hợp hơn. Nhưng không mặc định số lượng/độ sắp xếp của keyRows luôn giống affected trên mọi driver; phải kiểm tra nền tảng cụ thể.

### 5.2. Không đoán generated ID từ thứ tự INSERT

Một sequence có thể cache, bỏ số, gặp rollback hoặc bị ứng dụng khác dùng. Không viết logic “hàng đầu ID 1, hàng sau ID 2” trừ khi đang nói đến demo database mới và không có concurrent writers. Trong code production phải **dùng ID được driver/DB trả lại**.

**Tuyệt đối không sử dụng SELECT MAX(id)** để tìm “ID vừa chèn”:

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
SELECT MAX(id) FROM members;
~~~

Giữa hai lệnh, giao dịch khác có thể chèn bản ghi lớn hơn, hoặc sequence có cách cấp số riêng. MAX(id) không gắn key với **chính statement INSERT vừa chạy**. Dùng KeyHolder hoặc cú pháp RETURNING có hỗ trợ; các session-specific key functions cũng cần đúng connection/DBMS nên không thể gọi tùy tiện trên connection khác trong pool.

## 6. Ví dụ Java 17+ chạy được với H2

Ví dụ sau được thiết kế cho **Spring JDBC 6.2.7**, **H2 2.3.232**, **JDK 17+** và Gradle. Nó minh họa **INSERT có sinh ID**, **UPDATE trả affected count**, và việc **SELECT theo generated ID**. Cơ sở dữ liệu H2 là in-memory và được tạo mới khi chương trình khởi chạy.

Cấu trúc:

~~~text
jdbc-generated-keys/
  build.gradle
  src/main/java/example/JdbcClientKeysDemo.java
~~~

Tệp **build.gradle**:

~~~groovy
plugins {
    id 'java'
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-jdbc:6.2.7'
    runtimeOnly 'com.h2database:h2:2.3.232'
}

application {
    mainClass = 'example.JdbcClientKeysDemo'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}
~~~

Tệp **src/main/java/example/JdbcClientKeysDemo.java**:

~~~java
package example;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public final class JdbcClientKeysDemo {

    record InsertResult(long id, int rowCount) {}

    static InsertResult insert(JdbcClient jdbc, String name) {
        GeneratedKeyHolder keys = new GeneratedKeyHolder();

        int affected = jdbc
            .sql("""
                 INSERT INTO members (display_name)
                 VALUES (:name)
                 """)
            .param("name", name)
            .update(keys, "id");

        if (affected != 1) {
            throw new IllegalStateException(
                "Expected one row, got " + affected
            );
        }
        Number key = keys.getKey();
        if (key == null) {
            throw new IllegalStateException("Missing generated id");
        }
        return new InsertResult(key.longValue(), affected);
    }

    public static void main(String[] args) {
        DriverManagerDataSource dataSource =
            new DriverManagerDataSource(
                "jdbc:h2:mem:keydemo;DB_CLOSE_DELAY=-1",
                "sa",
                ""
            );

        JdbcTemplate template = new JdbcTemplate(dataSource);
        template.execute("""
            CREATE TABLE members (
                id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                display_name VARCHAR(80) NOT NULL UNIQUE
            )
            """);

        JdbcClient jdbc = JdbcClient.create(dataSource);

        InsertResult lan = insert(jdbc, "Lan");
        InsertResult minh = insert(jdbc, "Minh");

        System.out.println(
            "Lan: id=" + lan.id() + ", rows=" + lan.rowCount()
        );
        System.out.println(
            "Minh: id=" + minh.id() + ", rows=" + minh.rowCount()
        );

        int renamed = jdbc
            .sql("""
                 UPDATE members SET display_name = :name
                 WHERE id = :id
                 """)
            .param("name", "Lan Anh")
            .param("id", lan.id())
            .update();

        int missing = jdbc
            .sql("UPDATE members SET display_name = ? WHERE id = ?")
            .param("Nobody")
            .param(999L)
            .update();

        System.out.println("updated rows: " + renamed);
        System.out.println("missing rows: " + missing);

        String persistedName = jdbc
            .sql("SELECT display_name FROM members WHERE id = :id")
            .param("id", lan.id())
            .query(String.class)
            .single();
        System.out.println("selected name: " + persistedName);
    }
}
~~~

**Phân tích mã:** JdbcTemplate.execute tạo bảng; JdbcClient.create(DataSource) tạo fluent client; insert tạo holder mới, gọi update(holder, "id"), kiểm tra affected, đọc Number key và trả record InsertResult. UPDATE sau đó **chỉ** dùng update() vì không cần key. SELECT qua query(String.class).single() đọc kết quả cuối.

~~~

Vì cơ sở dữ liệu mới và identity mặc định bắt đầu từ 1, hai insert theo thứ tự sẽ nhận id 1 và 2 trong ví dụ này. Chương trình **không hard-code** ID: nó đọc đúng giá trị từ KeyHolder, nên vẫn đúng nếu ID bắt đầu ở một số khác. UPDATE id không tồn tại trả count 0; đó không phải một generated ID.

**Phạm vi demo:** DriverManagerDataSource được dùng cho ví dụ dễ học, không phải pool hiệu năng production. Trong Spring Boot ứng dụng thực tế, thường dùng HikariCP, transaction manager, migration schema và DataSource được cấu hình qua application properties.

### 6.1. Vì sao update(keys, "id") thường dễ đoán hơn update(keys)?

Khi chỉ định key column, ứng dụng nói rõ muốn **id**. Không chỉ định, driver có thể trả một tập key mặc định rộng hơn. Nếu thử đổi thành:

~~~java
GeneratedKeyHolder keys = new GeneratedKeyHolder();

int affected = jdbc
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Hà")
    .update(keys);
~~~

thì cách đọc getKey() vẫn chỉ hợp lệ khi driver trả đúng **một key số**. Đây là **một biến thể thử nghiệm riêng**, không cần chạy thêm để hoàn tất demo gốc. Trong sản phẩm thực tế nên kiểm tra driver trước khi chọn cách không chỉ rõ cột.

## 7. Dự án Spring 6.0 hoặc cũ hơn: dùng JdbcTemplate

Khi **không có JdbcClient**, vẫn lấy generated key được bằng API lâu đời:

~~~java
import java.sql.PreparedStatement;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long insertWithJdbcTemplate(
        JdbcTemplate jdbc, String name) {

    GeneratedKeyHolder keys = new GeneratedKeyHolder();
    String sql =
        "INSERT INTO members (display_name) VALUES (?)";

    int affected = jdbc.update(connection -> {
        PreparedStatement ps = connection.prepareStatement(
            sql, new String[] {"id"}
        );
        ps.setString(1, name);
        return ps;
    }, keys);

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, got " + affected
        );
    }

    Number key = keys.getKey();
    if (key == null) {
        throw new IllegalStateException("No generated key");
    }
    return key.longValue();
}
~~~

Đây là **một method trong class có JdbcTemplate**, không phải chương trình Java độc lập. Điểm rất quan trọng là **PreparedStatementCreator phải bật việc trả generated keys**, ví dụ dùng connection.prepareStatement(sql, new String[] {"id"}). Nếu tạo statement bằng prepareStatement(sql) mà không bật chế độ đó, KeyHolder có thể trống dù INSERT thực sự thành công.

Có thể dùng Statement.RETURN_GENERATED_KEYS ở driver hỗ trợ, nhưng chỉ định column names thường rõ ràng hơn nếu database và JDBC driver có khả năng đó.

## 8. Dự án dùng NamedParameterJdbcTemplate

Đối với SQL tham số theo tên, có overload:

~~~java
int update(
    String sql,
    SqlParameterSource paramSource,
    KeyHolder generatedKeyHolder,
    String[] keyColumnNames
);
~~~

Ví dụ:

~~~java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long insertWithNamedJdbc(
        NamedParameterJdbcTemplate namedJdbc, String name) {

    MapSqlParameterSource params =
        new MapSqlParameterSource("name", name);
    GeneratedKeyHolder keys = new GeneratedKeyHolder();

    int affected = namedJdbc.update(
        "INSERT INTO members (display_name) VALUES (:name)",
        params,
        keys,
        new String[] {"id"}
    );

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, got " + affected
        );
    }
    Number key = keys.getKey();
    if (key == null) {
        throw new IllegalStateException("No generated id");
    }
    return key.longValue();
}
~~~

So sánh chữ ký:

- **JdbcClient**: `.update(keys, "id")`, với String... là **varargs**.
- **NamedParameterJdbcTemplate**: `.update(sql, params, keys, new String[] {"id"})`, tham số key columns là mảng String[].

Cả hai trả int affected. Generated ID nằm ở keys. Không sao chép chữ ký từ class này sang class khác.

## 9. SimpleJdbcInsert: API trả thẳng một khóa số

Nếu chỉ cần INSERT vào một bảng có cấu trúc khá đơn giản, **SimpleJdbcInsert** cung cấp phương thức **executeAndReturnKey(...)**. Đây là API **khác** JdbcClient.

~~~java
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public long insertWithSimpleJdbcInsert(
        DataSource dataSource, String name) {

    SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("members")
        .usingColumns("display_name")
        .usingGeneratedKeyColumns("id");

    Number generated = insert.executeAndReturnKey(
        Map.of("display_name", name)
    );
    if (generated == null) {
        throw new IllegalStateException("No generated id");
    }
    return generated.longValue();
}
~~~

Trong ứng dụng thực tế, nên **khởi tạo SimpleJdbcInsert một lần** trong bean repository rồi tái sử dụng. Ví dụ method tạo mới mỗi lần chỉ để trình bày API. Class này có khả năng dùng DatabaseMetaData từ driver để hỗ trợ dựng SQL; nếu metadata không đầy đủ, cần chỉ định bảng/cột/schema phù hợp.

Nếu nhiều cột key hoặc nhiều giá trị generated được trả, dùng **executeAndReturnKeyHolder(...)** và kiểm tra map/list. **Không** gọi executeAndReturnKey() trên JdbcClient, vì method này thuộc SimpleJdbcInsert.

## 10. PostgreSQL: INSERT ... RETURNING và JdbcClient.query()

PostgreSQL hỗ trợ **RETURNING** trên INSERT, UPDATE và DELETE, trả dữ liệu của các hàng được xử lý. Ví dụ:

~~~sql
INSERT INTO members (display_name)
VALUES ('Lan')
RETURNING id;
~~~

Với PostgreSQL JDBC driver, SQL này trả ResultSet. Một cách rõ ràng để lấy ID là dùng **JdbcClient.query(...)**, không phải update(KeyHolder):

~~~java
public long insertPostgres(JdbcClient jdbc, String name) {
    return jdbc
        .sql("""
             INSERT INTO members (display_name)
             VALUES (:name)
             RETURNING id
             """)
        .param("name", name)
        .query(Long.class)
        .single();
}
~~~

Đây là **method theo PostgreSQL dialect**, không phải mã portable sang mọi DBMS. Câu SQL trả một giá trị ID, nên .single() thích hợp khi chắc chắn INSERT tạo **đúng một hàng**. Nếu dùng ON CONFLICT DO NOTHING và không có hàng nào được chèn, RETURNING có thể trả **0 hàng**; .single() sẽ báo lỗi cardinality, không tự trả ID 0.

| Tiêu chí | update(keys, "id") | INSERT ... RETURNING id |
| --- | --- | --- |
| API Spring | JdbcClient.update với KeyHolder | JdbcClient.query(...).single() |
| Giá trị trực tiếp | int affected | Giá trị ID từ ResultSet |
| Đường trả ID | holder.getKey() | .single() |
| Khả năng chuyển DB | Phụ thuộc JDBC generated keys | Phụ thuộc SQL dialect |
| Hỗ trợ nhiều cột | getKeys/getKeyList | query map/record |
| Trường hợp 0 hàng | Xem affected và keys | Query không có kết quả, xử lý cardinality |

Không tự nghĩ mọi database đều có RETURNING theo cú pháp PostgreSQL. Nếu cần tính portable, chọn JDBC generated keys hoặc abstraction riêng theo dialect, rồi integration test ở DBMS mục tiêu.

## 11. Tình huống nhiều key và batch update

### 11.1. Multiple generated columns

Giả sử driver trả id cùng một cột generated khác. Khi đó getKey() có thể báo **InvalidDataAccessApiUsageException** vì nó chỉ dùng khi có đúng một entry số. Đọc getKeys() để lấy map của **một hàng**, hoặc chỉ định key column `"id"` trong update(holder, "id") nếu driver hỗ trợ.

~~~java
java.util.Map<String, Object> rowKeys = keys.getKeys();
if (rowKeys == null || rowKeys.isEmpty()) {
    throw new IllegalStateException("Key result is empty");
}
~~~

Tên cột trong map có thể là ID hoặc id tùy cách driver xử lý identifier. Không hard-code assumption về chữ hoa/thường mà chưa kiểm tra. Với composite key hoặc non-numeric key, hợp đồng repository cũng phải mô tả kiểu dữ liệu đầy đủ, không ép mọi kết quả về long.

### 11.2. Multiple generated rows

Với batch INSERT, driver có thể trả các key của nhiều hàng. Khi đó:

~~~java
java.util.List<java.util.Map<String, Object>> rows =
    keys.getKeyList();
~~~

mang nhiều map key; **getKey()** không dành cho trường hợp này. Phải kiểm tra đúng số lượng key, thứ tự liên kết với input và các hạn chế của DBMS/driver. Không xem mảng **int[]** từ batch update là mảng generated IDs; nó thường là update counts hoặc mã trạng thái JDBC.

### 11.3. Khác biệt phiên bản cho batch

Các bản Spring JDBC 6.x có **JdbcTemplate.batchUpdate** và **NamedParameterJdbcTemplate.batchUpdate**. Tài liệu cho **Spring 7.1** còn mô tả các convenience API dạng **JdbcClient.batch()**. Đừng sử dụng .batch() trong mã đang chạy Spring 6.1/6.2/7.0 chỉ vì đọc ví dụ từ một bản tài liệu mới hơn; hãy xem **Javadoc của dependency thực tế**.

Ngay cả khi API batch đã hỗ trợ generated keys, không nên giả định mọi driver trả tất cả ID hoặc bảo toàn thứ tự key một cách thống nhất. Đối với nghiệp vụ cần ID từng hàng, kiểm thử bản DB/driver đang chạy, hoặc cân nhắc INSERT ... RETURNING ở dialect phù hợp.

## 12. Giao dịch: có ID chưa chắc đã commit

Một service có thể dùng:

~~~java
@Transactional
public long createMember(String name) {
    return repository.insertAndReturnId(name);
}
~~~

Đoạn trên là **snippet của Spring service** đã có @Transactional và repository, không phải chương trình độc lập. Bên trong transaction, câu INSERT có thể tạo ID và trả về cho service **trước khi commit**. Nếu xảy ra exception sau đó và transaction rollback, hàng vừa chèn có thể **không tồn tại** trong database sau giao dịch, dù KeyHolder đã nhận ID.

Sequence/identity thường có gaps do rollback, concurrency, caching hoặc vận hành DB. Không viết logic yêu cầu ID liên tục không có khoảng trống. ID chỉ là identifier, không phải thước đo số lần INSERT thành công hay thứ tự giao dịch commit.

Nếu ứng dụng cần gửi event chứa ID của bản ghi mới, nên thiết kế thời điểm phát sự kiện phù hợp transaction (ví dụ outbox/after-commit theo nhu cầu) để không công bố ID của dữ liệu sẽ rollback.

### 12.1. Vì sao SELECT MAX(id) sai khi tìm key?

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
SELECT MAX(id) FROM members;
~~~

Câu SELECT không gắn với **statement INSERT vừa chạy**, và có thể nhìn thấy giá trị của hàng khác tùy isolation/concurrency. Không giải quyết bằng việc “chờ vài mili giây”. Dùng generated keys của chính statement hoặc RETURNING. Tương tự, các session-specific last-id functions chỉ đúng khi hiểu phạm vi connection/DBMS; không chạy tùy tiện trên một connection khác từ pool.

### 12.2. Retry có thể chèn trùng

Nếu server INSERT xong nhưng kết nối mạng mất trước khi client nhận generated key, retry mù quáng có thể tạo **hai bản ghi**. Cần thiết kế idempotency/unique business key khi nghiệp vụ yêu cầu, không mặc định “không có ID nghĩa là chưa hề INSERT”.

## 13. Chẩn đoán lỗi generated keys

| Hiện tượng | Nguyên nhân khả dĩ | Điều cần kiểm tra |
| --- | --- | --- |
| update() trả 1, nhưng code coi đó là ID | Đọc nhầm affected count | Dùng holder hoặc RETURNING |
| holder.getKey() == null | Driver không trả key, sai key column, DB không sinh ID | Schema identity/default, JDBC metadata, affected |
| getKey() báo nhiều key | Driver trả nhiều cột/hàng | update(holder, "id"), getKeys/getKeyList |
| getKey() báo kiểu không phải Number | ROWID/UUID/kiểu driver đặc thù | keyColumnNames, getKeyAs/map, dialect |
| INSERT lỗi unique constraint | Giá trị trùng hoặc vi phạm index | Xử lý DataAccessException, không giả ID 0 |
| affected = 0 sau UPDATE | Không có hàng khớp hoặc cơ chế count của DBMS | Điều kiện WHERE, driver semantics |
| ID không theo thứ tự mong chờ | Sequence/identity có gaps | Không hard-code ID hay dùng MAX |
| Key trả nhưng SELECT sau đó không thấy | Transaction rollback, replication lag, khác tenant/DB | Transaction, connection, datasource |
| Mã JdbcClient không compile ở Spring 6.0 | API chưa tồn tại | Dùng JdbcTemplate/NamedParameterJdbcTemplate |
| update(KeyHolder) trả ROWID | Driver tự chọn generated keys không đúng | update(holder, "id"), metadata |
| UUID key bị cast sang Long | Sai kiểu dữ liệu | Dùng getKeyAs/RETURNING mapping phù hợp |
| Batch không trả đủ keys | Hạn chế JDBC driver và API version | Integration test driver, keyList |

Một số lỗi được Spring dịch thành **DataAccessException**. Không catch(Exception) rồi trả ID = -1 hoặc Optional.empty() cho mọi tình huống; như vậy database outage hoặc vi phạm constraint sẽ bị diễn giải sai là “chưa có dữ liệu”.

## 14. Kiểm thử theo phiên bản và database

Một bộ test có giá trị cần kiểm tra cả **count** lẫn **key**:

1. **Spring API compatibility:** phiên bản đang chạy có đúng JdbcClient.StatementSpec.update() và overload KeyHolder không?
2. **INSERT một hàng:** affected = 1, key khác null, key đọc lại bản ghi đúng.
3. **ID không bắt đầu ở 1:** code lấy từ holder, không dựa vào row count.
4. **UPDATE ID không tồn tại:** affected = 0, không coi đó là generated ID.
5. **Unique violation:** có exception phù hợp, không trả key giả.
6. **Driver không trả keys:** repository báo lỗi rõ ràng thay vì tự tính MAX(id).
7. **Nhiều generated columns:** getKey() không được dùng thiếu kiểm tra.
8. **Bảng có UUID:** conversion không ép long sai.
9. **Transaction rollback:** key có thể đã sinh nhưng hàng không commit.
10. **PostgreSQL RETURNING:** xử lý 0/1/n rows theo hợp đồng.
11. **Batch:** số keys và thứ tự có được driver bảo đảm hay không?
12. **Concurrency:** hai request INSERT không lấy nhầm key của nhau.

H2 là lựa chọn tiện để học API; với Oracle, PostgreSQL, MySQL, SQL Server hoặc các cách sinh khóa đặc thù, nên integration-test bằng DBMS tương ứng hoặc Testcontainers. Không mặc định một test H2 chứng minh mọi driver khác nhau đều trả key giống nhau.

## 15. Bài tập có đáp án

**Câu 1.** JdbcClient.update() trả 1 sau INSERT. Có thể kết luận generated ID là 1?

**Đáp án:** Không. Đó là số hàng ảnh hưởng, không phải khóa.

**Câu 2.** Spring Framework 6.1.8 có overload update(KeyHolder, String...) không?

**Đáp án:** Có. Javadoc 6.1.8 đã liệt kê update(), update(KeyHolder) và update(KeyHolder, String...).

**Câu 3.** Một dự án Spring 6.0 muốn lấy identity ID phải làm sao?

**Đáp án:** Dùng JdbcTemplate.update(PreparedStatementCreator, KeyHolder), NamedParameterJdbcTemplate.update(...KeyHolder...) hoặc SimpleJdbcInsert.executeAndReturnKey.

**Câu 4.** Vì sao update(holder, "id") thường tốt hơn update(holder) khi cần ID?

**Đáp án:** Nó nêu rõ key column mong muốn, tránh để driver tự chọn một cột/tập cột không đúng. Tuy nhiên vẫn phải kiểm tra driver hỗ trợ.

**Câu 5.** getKey() có thể xử lý generated keys cho ba hàng không?

**Đáp án:** Không. getKey() dành cho một hàng, một khóa số. Dùng getKeyList cho nhiều hàng khi driver hỗ trợ trả keys.

**Câu 6.** Key là UUID thì getKey().longValue() có đúng?

**Đáp án:** Không. Phải dùng mapping đúng kiểu UUID/String theo driver hoặc query RETURNING tương ứng.

**Câu 7.** INSERT lấy được ID nhưng sau đó transaction rollback. ID có bảo đảm bản ghi vẫn tồn tại không?

**Đáp án:** Không. Số identity/sequence có thể đã tiêu thụ và hàng có thể không được commit.

**Câu 8.** Vì sao SELECT MAX(id) sau INSERT không đáng tin?

**Đáp án:** Nó không gắn với statement vừa INSERT và có thể bị ảnh hưởng bởi concurrency/dãy sinh ID.

**Câu 9.** PostgreSQL INSERT ... RETURNING id dùng JdbcClient API nào?

**Đáp án:** Có thể dùng **query(Long.class).single()** vì statement trả ResultSet; cú pháp RETURNING không portable sang mọi DBMS.

**Câu 10.** .update(holder) trả đúng affected = 1 nhưng holder không có key; nên trả ID = 0 để tránh lỗi?

**Đáp án:** Không. Phải xác định schema/driver/keyColumnNames, rồi báo lỗi rõ ràng nếu contract yêu cầu ID mà DB không trả.

## 16. Ghi nhớ trước khi triển khai production

- **JdbcClient.update() trả int số hàng ảnh hưởng**, không trả ID sinh tự động.
- **Spring 6.1+** có overload **update(KeyHolder)** và **update(KeyHolder, String...)**; phải kiểm tra bản Javadoc tương ứng.
- **GeneratedKeyHolder** giữ key sau INSERT, không phải giá trị trả trực tiếp từ update(holder).
- **getKey()** dành cho một khóa kiểu Number; nhiều key dùng getKeys/getKeyList, non-numeric key cần mapping đúng kiểu.
- **Chỉ định tên cột ID** khi phù hợp để giảm phụ thuộc cách driver tự nhận diện.
- **Spring <=6.0** dùng JdbcTemplate/NamedParameterJdbcTemplate/SimpleJdbcInsert; không có JdbcClient.
- **PostgreSQL RETURNING** là hướng khác dựa trên ResultSet; không coi nó portable.
- **Không dùng SELECT MAX(id)**, không suy luận ID từ affected count, không chia sẻ mutable KeyHolder giữa requests.
- **Khóa được sinh trước commit** và sequence có thể bỏ số khi rollback.
- **Kiểm thử driver/database thực tế**, nhất là key kiểu UUID, nhiều cột, batch, Oracle và multi-tenant.
