# SimpleJdbcInsert: Configuring Table, Schema, and Column List in Spring JDBC

## 1. Problem and Goal

When writing a record to a database with JDBC, developers typically have to write `INSERT INTO ... VALUES (...)` manually, keep columns and `?` placeholders in the right order, and bind the corresponding parameters. When INSERT operations repeat across the data access layer, Spring JDBC's `SimpleJdbcInsert` consolidates that configuration into a reusable object.

This lesson focuses on three configuration decisions:

1. **Which table is the target?** — `withTableName(...)`.
2. **Which schema/catalog does the table belong to?** — `withSchemaName(...)` and, when supported by the DBMS, `withCatalogName(...)`.
3. **Which columns are actually included in the INSERT statement?** — `usingColumns(...)`, combined with `usingGeneratedKeyColumns(...)` to retrieve database-generated keys.

In addition, you need to understand when Spring relies on JDBC metadata, when columns must be declared explicitly, how to handle case-sensitive identifiers, default values, schema errors, and reusing the object after configuration.

`SimpleJdbcInsert` belongs to the `org.springframework.jdbc.core.simple` package in the `spring-jdbc` library. It generates and executes INSERTs based on configuration and parameters; it **does not create tables, schemas, or migrations**, is not an ORM, and does not replace a transaction manager.

## 2. APIs to Remember

Typical configuration example:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingColumns("SKU", "NAME", "PRICE")
        .usingGeneratedKeyColumns("ID");
```

The snippet above assumes `dataSource` is already provided and the table exists; this is a **configuration pattern**, not a standalone Java program.

| API | Role | Things to Watch Out For |
|---|---|---|
| `new SimpleJdbcInsert(dataSource)` | Creates an instance operating against a `DataSource`. | Can use the constructor taking `JdbcTemplate` if an appropriate template already exists. |
| `withTableName("PRODUCTS")` | Specifies the target table name. | The table name is a SQL identifier, not a value bound via `?`. |
| `withSchemaName("SALES")` | Specifies the schema containing the table. | Must exist and the connection account needs access permissions. |
| `withCatalogName("...")` | Specifies the catalog when used by the database/driver. | Catalog and schema have different meanings depending on the DBMS. |
| `usingColumns("SKU", "NAME", "PRICE")` | Limits and defines the list of columns appearing in the INSERT. | Does not alter the table structure itself. |
| `usingGeneratedKeyColumns("ID")` | Specifies the key column to request reading auto-generated values. | Use `executeAndReturnKey(...)` or `executeAndReturnKeyHolder(...)` to receive the key. |
| `withoutTableColumnMetaDataAccess()` | Disables reading table column metadata. | Must declare all columns to INSERT via `usingColumns(...)`. |
| `usingQuotedIdentifiers()` | Requests quoting schema, table, and column names per database rules. | Must declare `usingColumns(...)` explicitly and use the exact casing of identifiers. |
| `compile()` | Finalizes configuration and prepares SQL/metadata. | Not required to call manually; the first execution compiles automatically if not yet compiled. |

The `with...` and `using...` methods follow a *fluent* style, returning the object itself so calls can be chained. You should build a complete configuration in the constructor or repository initialization phase and reuse it, rather than instantiating and inspecting metadata for every record.

## 3. Table, Schema, Catalog: How Do They Differ?

Consider the illustrative table:

```sql
CREATE SCHEMA SALES;

CREATE TABLE SALES.PRODUCTS (
    ID BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    SKU VARCHAR(30) NOT NULL UNIQUE,
    NAME VARCHAR(100) NOT NULL,
    PRICE DECIMAL(12, 2) NOT NULL,
    CREATED_AT TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

The SQL above is compatible with H2 used in the standalone runnable example below. In this database, unquoted identifiers like `SALES` and `PRODUCTS` are stored in uppercase.

- `PRODUCTS` is the **table name**.
- `SALES` is the **schema name**, not part of the table name string passed to `withTableName`.
- `ID` is assigned a value by the database; `CREATED_AT` has a default value.
- `SKU`, `NAME`, and `PRICE` are the three columns the application needs to send when creating a normal product.

Clean configuration with an explicit target:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingColumns("SKU", "NAME", "PRICE")
        .usingGeneratedKeyColumns("ID");
```

Conceptual SQL generated by this configuration:

```sql
INSERT INTO SALES.PRODUCTS (SKU, NAME, PRICE)
VALUES (?, ?, ?);
```

The `?` placeholders are bound via JDBC; the names `SALES`, `PRODUCTS`, `SKU`, `NAME`, and `PRICE` are trusted configuration defined by the application.

**If you only use `withTableName("PRODUCTS")`:** the database/driver resolves the table based on the connection context and default schema, so the application might write to a different table of the same name or fail to find the table when switching accounts or default schemas. Use `withSchemaName` when you need to lock down the exact table address.

**If you use `withCatalogName`:** only add it when required by the specific DBMS and you understand the driver's catalog/schema mapping. For example, PostgreSQL uses schemas within the current database, whereas other DBMSs may distinguish catalogs differently. Do not treat `withCatalogName` as a generic way to switch databases across products.

**Important:** `withSchemaName("SALES")` does not execute `CREATE SCHEMA` or `SET SCHEMA`, nor does it grant access permissions. Schemas and tables must already exist via migrations or database administration tools.

## 4. usingColumns: Controlling Exactly What Gets INSERTed

The `usingColumns(...)` method accepts the column names **to include in the SQL**, in the declared order. For table `SALES.PRODUCTS`:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingColumns("SKU", "NAME", "PRICE");
```

When executing:

```java
int affected = insert.execute(Map.of(
        "SKU", "P-001",
        "NAME", "Pencil",
        "PRICE", new java.math.BigDecimal("12.50")
));
```

This is an example **inside a method that already has the `insert` variable**, not a standalone program. `execute(Map<String, ?>)` returns the affected row count reported by the driver, typically `1` for a successful single INSERT.

Key mechanics:

1. **The column list determines the SQL.** `usingColumns("SKU", "NAME", "PRICE")` produces an INSERT statement with only those three columns, regardless of whether the table also has `ID` or `CREATED_AT`.
2. **Key names in the `Map` match values to columns.** Keys should match column names consistently; do not rely on `Map` iteration order. The number of `?` placeholders and bind order are determined by the configured column list.
3. **Not every table column has to be passed.** The auto-generated `ID` column and `CREATED_AT` with a default will be handled by the database as long as they genuinely **do not appear in the SQL INSERT**.
4. **Extra data does not expand the SQL.** Adding `"CREATED_AT"` to the `Map` will not make it appear in the INSERT when `usingColumns` restricts it to three columns. Treat extra keys as a sign to review input data; do not rely on them being ignored as business validation.
5. **Missing columns remain an issue.** If the list requires `NAME` and no valid value is provided, the INSERT may bind `NULL` and violate `NOT NULL`; the application must validate inputs.

### Omitting a Column vs. Passing NULL

These two operations are **different**:

```sql
-- The database can apply CREATED_AT's DEFAULT:
INSERT INTO SALES.PRODUCTS (SKU, NAME, PRICE)
VALUES ('P-001', 'Pencil', 12.50);

-- A NULL value is explicitly sent; NOT NULL may reject it:
INSERT INTO SALES.PRODUCTS (SKU, NAME, PRICE, CREATED_AT)
VALUES ('P-002', 'Ruler', 18.00, NULL);
```

Therefore, to let the database populate a timestamp/default, you must **exclude the column from the INSERT list**, not just pass a key with `null`. `usingColumns` is very effective for this requirement.

A new `NOT NULL` column **without a DEFAULT** added to the table later can break existing code because that column is still omitted from the INSERT. Migrations and application configuration must stay in sync.

## 5. Generated Keys: Configuring the ID Column Without Putting ID in the Insert List

If `ID` is generated by the database, combine:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingColumns("SKU", "NAME", "PRICE")
        .usingGeneratedKeyColumns("ID");

Number id = insert.executeAndReturnKey(Map.of(
        "SKU", "P-003",
        "NAME", "Notebook",
        "PRICE", new java.math.BigDecimal("35.00")
));
long productId = id.longValue();
```

Key distinction:

- `usingColumns` describes the **list of parameters to INSERT**: `SKU`, `NAME`, `PRICE`.
- `usingGeneratedKeyColumns` describes the **column to retrieve back from the driver**: `ID`.
- `executeAndReturnKey` returns `Number`, without guaranteeing a fixed type like `Long` or `Integer`; convert via `longValue()` if the value fits the application's data range.
- If the database generates multiple keys or you need a non-numeric type, consider `executeAndReturnKeyHolder(...)` and inspect the `KeyHolder` contents. Retrieval capability depends on the driver and database.
- If IDs are assigned by the application itself, declare the ID in `usingColumns`, pass the ID value in the `Map`, and use `execute(...)` according to that contract.

Declaring a generated key **does not create** an identity/sequence column in the database; the DDL determines how keys are generated. Likewise, do not both rely on DB-generated IDs and require the application to supply IDs without a clearly designed rule.

## 6. Complete Java 17+ Example: Schema and Column List

The following example uses **Spring JDBC 6.2.12** and **H2 2.3.232** to demonstrate everything from creating the table to calling `SimpleJdbcInsert`. No Spring Boot or external database server is needed. Requires JDK 17+ and Maven.

Project directory structure:

```text
simple-jdbc-insert-demo/
├── pom.xml
└── src/main/java/demo/InsertConfigurationDemo.java
```

**`pom.xml`**:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>demo</groupId>
    <artifactId>simple-jdbc-insert-demo</artifactId>
    <version>1.0.0</version>
    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-jdbc</artifactId>
            <version>6.2.12</version>
        </dependency>
        <dependency>
            <groupId>com.h2database</groupId>
            <artifactId>h2</artifactId>
            <version>2.3.232</version>
        </dependency>
    </dependencies>
    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>

            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>

                    <mainClass>demo.InsertConfigurationDemo</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

**`src/main/java/demo/InsertConfigurationDemo.java`**:

```java
package demo;

import java.math.BigDecimal;
import java.util.Map;

import org.h2.jdbcx.JdbcDataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public final class InsertConfigurationDemo {

    public static void main(String[] args) {
        JdbcDataSource dataSource = new JdbcDataSource();
        dataSource.setURL("jdbc:h2:mem:insert_configuration;DB_CLOSE_DELAY=-1");
        dataSource.setUser("sa");
        dataSource.setPassword("");

        JdbcTemplate jdbc = new JdbcTemplate(dataSource);
        jdbc.execute("CREATE SCHEMA SALES");
        jdbc.execute("""
            CREATE TABLE SALES.PRODUCTS (
                ID BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                SKU VARCHAR(30) NOT NULL UNIQUE,
                NAME VARCHAR(100) NOT NULL,
                PRICE DECIMAL(12, 2) NOT NULL,
                CREATED_AT TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
            )
            """);

        // 1. Configure schema name, table, outgoing columns, and generated key.
        SimpleJdbcInsert productInsert = new SimpleJdbcInsert(dataSource)
                .withSchemaName("SALES")
                .withTableName("PRODUCTS")
                .usingColumns("SKU", "NAME", "PRICE")
                .usingGeneratedKeyColumns("ID");

        // This line is optional: the first execute also compiles automatically.
        productInsert.compile();

        // 2. ID and CREATED_AT are omitted: assigned by the database.
        Number firstId = productInsert.executeAndReturnKey(Map.of(
                "SKU", "P-001",
                "NAME", "Pencil",
                "PRICE", new BigDecimal("12.50")
        ));

        // 3. Reuse the same configured instance.
        int secondCount = productInsert.execute(Map.of(
                "SKU", "P-002",
                "NAME", "Notebook",
                "PRICE", new BigDecimal("35.00")
        ));

        Integer rowCount = jdbc.queryForObject(
                "SELECT COUNT(*) FROM SALES.PRODUCTS", Integer.class
        );
        Integer rowsWithTimestamp = jdbc.queryForObject(
                "SELECT COUNT(*) FROM SALES.PRODUCTS " +
                "WHERE CREATED_AT IS NOT NULL", Integer.class
        );

        System.out.println("First ID: " + firstId.longValue());
        System.out.println("Second insert count: " + secondCount);
        System.out.println("Rows: " + rowCount);
        System.out.println("Default timestamps: " + rowsWithTimestamp);
    }
}
```

Command to run from the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

Expected output of the program above with a fresh in-memory H2 database:

```text
First ID: 1
Second insert count: 1
Rows: 2
Default timestamps: 2
```

Explanation:

1. `CREATE SCHEMA SALES` and `CREATE TABLE SALES.PRODUCTS` set up the structure for the example. In real projects, this step usually belongs to Flyway, Liquibase, or dedicated migrations.
2. `withSchemaName("SALES")` together with `withTableName("PRODUCTS")` points to the exact table; do not put `"SALES.PRODUCTS"` inside `withTableName`.
3. `usingColumns("SKU", "NAME", "PRICE")` restricts the INSERT to three parameters. `ID` and `CREATED_AT` **are not in the INSERT statement**, so H2 generates the key and default timestamp.
4. `usingGeneratedKeyColumns("ID")` together with `executeAndReturnKey(...)` asks the driver to return the key from the first INSERT.
5. `productInsert.compile()` prepares the SQL once; the object can be reused for subsequent INSERT statements with different parameter sets.
6. The two `SELECT COUNT(*)` queries verify the **actual record count** and that the default timestamp was applied. This is stronger evidence than merely checking the return value of `execute`.

Note: the key value `1` depends on using a fresh in-memory H2 instance and default identity configuration. In a database with existing data or a custom sequence, the key value does not necessarily start at 1.

## 7. Automatic Metadata vs. Explicit Column Declaration

`SimpleJdbcInsert` can query the JDBC driver's `DatabaseMetaData` to discover table columns. That is why a minimal configuration can just be:

```java
SimpleJdbcInsert insertFromMetadata = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingGeneratedKeyColumns("ID");
```

This snippet **illustrates the metadata strategy**, not a choice tested against the default constraints of the example table. When `usingColumns` is omitted, the column list inferred from metadata may include columns you want the database to populate with defaults, such as `CREATED_AT`. If they appear in the SQL and the application supplies no value, the INSERT may fail or fail to apply `DEFAULT` as expected.

Comparison:

| Configuration Approach | How Does Spring Know Which Columns to INSERT? | Best When |
|---|---|---|
| Only `withTableName`/`withSchemaName` | Discovers columns via JDBC metadata. | Simple tables, complete metadata, minimal configuration desired. |
| Adding `usingColumns(...)` | Column list is specified by the application; Spring may still use metadata for other JDBC details. | You want a fixed INSERT contract and intentionally omit ID/default/computed columns. |
| Adding `withoutTableColumnMetaDataAccess()` and `usingColumns(...)` | Does not read table-column metadata; relies on declared column names. | Driver returns incomplete metadata, metadata is hard to access, or stricter configuration control is needed. |

Example of declaring without table-column metadata:

```java
SimpleJdbcInsert explicitInsert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("SALES")
        .withTableName("PRODUCTS")
        .usingColumns("SKU", "NAME", "PRICE")
        .usingGeneratedKeyColumns("ID")
        .withoutTableColumnMetaDataAccess();
```

**Condition:** column, schema, and table names must be exact; if the DDL changes, the code must be updated accordingly. Disabling *table-column metadata* does not mean Spring and the driver never read any database metadata at all, as building SQL and reading generated keys still have database-dependent behaviors.

When should you prefer `usingColumns`? When the table has DB-generated columns, defaults, triggers, or computed columns; when permissions or driver metadata are inconsistent; or when you want to strictly constrain which data may be inserted from the repository layer.

## 8. Quoted Table/Column Names and Case Sensitivity

Databases have different rules for unquoted identifiers. For example, H2 folds unquoted names to uppercase by default, while PostgreSQL typically folds them to lowercase. Quoted names can be stored verbatim and be case-sensitive.

For a table intentionally using mixed-case names:

```sql
CREATE SCHEMA "salesApp";

CREATE TABLE "salesApp"."OrderItem" (
    "itemId" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "skuCode" VARCHAR(30) NOT NULL,
    "quantity" INTEGER NOT NULL
);
```

Corresponding configuration:

```java
SimpleJdbcInsert insertQuoted = new SimpleJdbcInsert(dataSource)
        .withSchemaName("salesApp")
        .withTableName("OrderItem")
        .usingColumns("skuCode", "quantity")
        .usingGeneratedKeyColumns("itemId")
        .usingQuotedIdentifiers();
```

This is an **illustrative configuration snippet**, assuming the DDL has been executed on an appropriate `dataSource`.

- `usingQuotedIdentifiers()` uses the quote characters provided by the driver/database for schema, table, and column names; do not hardcode `"` across all databases yourself.
- When quoted identifiers are enabled, **you must declare the column list with `usingColumns(...)`**, and schema/table/column names must match exactly how they exist in the database, including uppercase/lowercase.
- Do not embed quotes inside the strings passed to `withTableName` or `usingColumns` when using the quoting mechanism; pass plain identifier names to the API.
- Quoting is not always desirable. If your project uses standard case-insensitive naming, leaving the default is simpler and more portable across environments.

If you encounter "table not found" or "column not found", besides checking permissions/schema, compare how the database stores identifier names against actual metadata.

## 9. Input Data, Binding, and SQL Types

`execute(Map<String, ?>)` requires keys describing columns. `MapSqlParameterSource` is useful when you need to declare the SQL type for special values or `null`:

```java
MapSqlParameterSource values = new MapSqlParameterSource()
        .addValue("SKU", "P-004")
        .addValue("NAME", "Binder")
        .addValue("PRICE", new BigDecimal("15.00"), java.sql.Types.DECIMAL);

int affected = productInsert.execute(values);
```

This is **illustrative code inside a method with `productInsert` available**; it requires importing `org.springframework.jdbc.core.namedparam.MapSqlParameterSource` and `java.math.BigDecimal`.

Things to distinguish:

- `Map.of(...)` does not allow `null` values. If a table has nullable columns where `null` must be sent, use `HashMap` or `MapSqlParameterSource` and declare `java.sql.Types` when the driver needs it.
- Java types, JDBC types, and database column types must be compatible; for instance, `BigDecimal` is more suitable than `double` for monetary prices.
- `usingColumns(...)` and Map parameters must reflect **table column names**. They are not arbitrary Java property names; if an entity uses `productName` while the column is `NAME`, the repository layer must map explicitly.
- Parameter binding separates **values** from SQL. However, schema, table, and column names are still **identifiers interpolated into the framework-generated SQL**; they must come from trusted configuration, never using raw user-supplied strings as table/schema names.
- Constraints such as `NOT NULL`, `UNIQUE`, `CHECK`, and foreign keys are still validated by the database. `SimpleJdbcInsert` does not act as a business data validator.

## 10. Configuration Lifecycle, Reusability, and Transactions

A repository typically creates `SimpleJdbcInsert` once at initialization and reuses it:

```java
public final class ProductWriter {
    private final SimpleJdbcInsert insert;

    public ProductWriter(javax.sql.DataSource dataSource) {
        this.insert = new SimpleJdbcInsert(dataSource)
                .withSchemaName("SALES")
                .withTableName("PRODUCTS")
                .usingColumns("SKU", "NAME", "PRICE")
                .usingGeneratedKeyColumns("ID");
        this.insert.compile();
    }

    public long add(String sku, String name, java.math.BigDecimal price) {
        Number id = insert.executeAndReturnKey(Map.of(
                "SKU", sku,
                "NAME", name,
                "PRICE", price
        ));
        return id.longValue();
    }
}
```

This is an **illustrative repository class** using the same table and `DataSource` as the example, not a full application initializing the database. Once compiled (explicitly or implicitly on the first execute), configuration is locked: do not call `withTableName`, `withSchemaName`, or `usingColumns` to mutate that same instance's configuration. If you need to write to another schema/table, create a separate instance within your configuration scope.

`SimpleJdbcInsert` can be reused across calls and across threads once configured; per-INSERT values are passed via a separate `Map`/`SqlParameterSource`. Never share mutable parameter objects across concurrent requests.

**Transactions** are governed by Spring's transaction manager and `DataSource`. `SimpleJdbcInsert` does not automatically ensure multiple `execute` calls commit or roll back together as one unit. In a Spring service, you can define appropriate transaction boundaries with `@Transactional` when a transaction manager is properly configured and calls go through Spring's proxy mechanism. On a failed INSERT, the underlying `JdbcTemplate` typically translates `SQLException` into a `DataAccessException`.

In addition to single rows, `SimpleJdbcInsert` also supports `executeBatch(Map<String, ?>...)` or `executeBatch(SqlParameterSource...)`, returning `int[]` per the JDBC batch contract; if you need multiple rows with the same table/column configuration, this is the right choice. Even then, **schema and column selection** is still determined by the same configured object.

## 11. Common Errors and How to Diagnose Them

| Symptom | Possible Cause | What to Check |
|---|---|---|
| `Table not found` | Wrong table name, wrong default schema, `withSchemaName` omitted, quote/case mismatch. | Check the connection session's schema, DDL, permissions, and actual identifier names. |
| `Column not found` | Wrong name in `usingColumns`, DDL changed without updating code, or incorrect quoting. | Compare metadata and migrations, especially case-sensitive names. |
| `NULL not allowed` | Missing value for a `NOT NULL` column, or a default column included in the INSERT with `NULL`. | Inspect the generated INSERT and column list; exclude columns meant to use DEFAULT from INSERT. |
| `Duplicate key` | Duplicate unique `SKU` value or duplicate application-assigned ID. | Verify key generation rules and idempotency; do not blindly retry to fix data errors. |
| Generated key not received | `usingGeneratedKeyColumns` omitted, driver does not support requested key retrieval, or DDL does not actually generate keys. | Check IDENTITY/sequence, `executeAndReturnKey` API, driver, and `KeyHolder`. |
| Metadata error on compile | Table/schema does not exist yet, driver provides limited metadata, metadata access permissions, or column name mismatch. | Check DDL/permissions, consider `usingColumns` with `withoutTableColumnMetaDataAccess`. |
| Cannot modify configuration | Object was already compiled at initialization or on first execution. | Create a new configuration before compiling; avoid reconfiguring per request. |
| Writing to the wrong place across environments | Relying on default schema when tables share names across locations. | Specify `withSchemaName` explicitly and control environment configuration. |

When investigating errors, you need to know the **actual SQL** and the **database/schema the connection uses**. Enable appropriate logging in development, or inspect the column list/metadata via database tools. Avoid logging sensitive values.

## 12. Design Decisions to Finalize Before Writing a Repository

1. **Identify the actual table:** table and schema/catalog names must match migrations and connection permissions.
2. **Lock down the columns to send:** distinguish required, default, computed, generated columns, and columns the application should not modify directly.
3. **Decide the metadata source:** whether automatic metadata is stable enough or explicit `usingColumns(...)` is needed; only disable column metadata after declaring all column names.
4. **Standardize naming:** uppercase/lowercase conventions and whether `usingQuotedIdentifiers()` is needed.
5. **Design primary keys:** DB-assigned or application-assigned ID; if DB-assigned, whether reading the key back is needed and how well the driver supports it.
6. **Create and compile once:** keep repository configuration immutable while handling multiple requests.
7. **Verify actual data:** execute test INSERTs, read back the ID/default columns and stored values; test missing required fields, duplicate keys, and wrong schemas.
8. **Define transaction rules:** if a business operation writes to multiple tables, clearly decide commit/rollback boundaries and error handling.

## 13. Self-Check Knowledge Quiz

**Question 1.** Why might `withTableName("PRODUCTS")` work on machine A but fail on machine B?  
**Answer:** Because the table may reside in a schema different from the connection's default schema; you should specify the right schema or configure `withSchemaName("SALES")`.

**Question 2.** A table has `CREATED_AT DEFAULT CURRENT_TIMESTAMP`. To let the DB set the timestamp, is `Map.put("CREATED_AT", null)` enough?  
**Answer:** No. That column must **not appear in the SQL INSERT** at all; `usingColumns` helps specify which columns to include.

**Question 3.** How does `usingColumns("SKU", "NAME", "PRICE")` differ from `usingGeneratedKeyColumns("ID")`?  
**Answer:** The first specifies the three columns sent in the INSERT; the second requests retrieving the DB-generated `ID` key back.

**Question 4.** If the driver does not return reliable column info, what should you configure?  
**Answer:** Declare `usingColumns(...)` explicitly and consider `withoutTableColumnMetaDataAccess()`, while verifying table/schema/column names and generated key retrieval capability.

**Question 5.** When `usingQuotedIdentifiers()` is enabled, can you let Spring auto-discover all column names and freely write `"products"` instead of `"PRODUCTS"`?  
**Answer:** No. You must declare `usingColumns(...)` and match identifier names exactly, especially uppercase/lowercase casing.

**Question 6.** Can you change `withSchemaName` on the same object after the first `execute` call?  
**Answer:** You should not, and the API prevents changing configuration after compile. Create an object with the right configuration from the start.
