# GeneratedKeyHolder and KeyHolder in Spring JDBC

## 1. The problem: after INSERT, retrieve the database-generated key

Suppose the `orders` table has an `id` column generated automatically by the database (identity/auto-increment). When creating an order, the application needs the new ID to return to the API, assign to a domain object, or use as a foreign key in subsequent operations.

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);
```

The statement `INSERT INTO orders (customer_name) VALUES (?)` does not pass `id`. The database assigns the ID value when executing the statement. However, `JdbcTemplate.update(sql, args...)` normally returns the **number of affected rows** (e.g., `1`), **not the generated ID**. Spring JDBC provides `KeyHolder` to hold the key data returned by the JDBC driver after statement execution.

Distinguish three responsibilities:
- **Key generation**: handled by the database (identity, sequence, default expression, trigger...) according to the schema design.
- **Requesting key return**: handled by the `PreparedStatement`/JDBC driver configured to retrieve generated keys.
- **Holding and reading the key**: handled by `KeyHolder` and the `GeneratedKeyHolder` object.

`KeyHolder` does not invent IDs and does not lock tables or records. If the driver/database does not return keys, merely instantiating `GeneratedKeyHolder` will not make an ID appear.

## 2. Roles of KeyHolder and GeneratedKeyHolder

Both are in the `org.springframework.jdbc.support` package:

- `KeyHolder` is an **interface** defining how returned keys are accessed.
- `GeneratedKeyHolder` is the **default implementation** of `KeyHolder`, holding a list of key maps that Spring populates from the `ResultSet` of `PreparedStatement.getGeneratedKeys()`.

Common declaration:

```java
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

KeyHolder keyHolder = new GeneratedKeyHolder();
```

Typical execution flow:

```text
Application
   │ creates KeyHolder and PreparedStatementCreator
   ▼
JdbcTemplate.update(creator, keyHolder)
   │ obtains Connection, creates PreparedStatement with key return enabled
   │ binds parameters, executes INSERT
   ▼
JDBC PreparedStatement.getGeneratedKeys()
   │ ResultSet containing columns/rows returned by the driver
   ▼
JdbcTemplate copies ResultSet into KeyHolder
   │
   ▼
Application reads getKey() / getKeys() / getKeyList()
```

**Ways to read the result:**

| Method | Return type | Use case and constraints |
| --- | --- | --- |
| `getKey()` | `Number` or `null` | Exactly **one key row, one numeric key column**; throws if multiple rows/columns exist. |
| `getKeyAs(Class<T>)` | `T` or `null` | Exactly one row/column, when the value is of the requested type (e.g., `UUID.class` if the driver actually returns `UUID`); not an arbitrary type converter. |
| `getKeys()` | `Map<String, Object>` or `null` | Retrieves **all key columns of one row**; throws if multiple key rows exist. |
| `getKeyList()` | `List<Map<String, Object>>` | Inspects multiple key rows; each map corresponds to one row of the returned keys `ResultSet`. |

`getKey()` and `getKeyAs(...)` can throw `InvalidDataAccessApiUsageException` if the column/row count does not match expectations, or a type retrieval error if the value is incompatible. `getKeyList()` can be an empty list if no keys were retrieved. A successful `JdbcTemplate.update(...)` call does not guarantee keys were returned: that also depends on the SQL, schema, and driver.

**Selection rule:** one numeric key → `getKey()`; one non-numeric key → `getKeyAs(type)` when the type is known; multiple columns returned in one row → `getKeys()`; multiple key rows → `getKeyList()`.

## 3. Runnable example with Java 17, Spring Boot 3.5.7, and H2

The example below pins versions for easy reproduction. In an existing Spring Boot project, you only need the `spring-boot-starter-jdbc` dependency, an appropriate JDBC driver, and the repository code. For this standalone example, create the following files:

```text

├── pom.xml
└── src/main/
    ├── java/com/example/keyholder/
    │   ├── KeyholderDemoApplication.java
    │   └── OrderRepository.java
    └── resources/
        ├── application.properties
        └── schema.sql
```


**`src/main/resources/schema.sql`**:

```sql

    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);
```

**`src/main/resources/application.properties`**:

```properties

spring.datasource.driver-class-name=org.h2.Driver

```

**`src/main/java/com/example/keyholder/OrderRepository.java`**:

```java
package com.example.keyholder;

import java.sql.PreparedStatement;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class OrderRepository {
    private static final String INSERT_SQL =
            "INSERT INTO orders (customer_name) VALUES (?)";

    private final JdbcTemplate jdbcTemplate;

    public OrderRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public long create(String customerName) {
        KeyHolder keyHolder = new GeneratedKeyHolder();

        int affectedRows = jdbcTemplate.update(connection -> {
            // Request the driver to return the id column generated after INSERT.
            PreparedStatement statement =
                    connection.prepareStatement(INSERT_SQL, new String[] {"id"});
            statement.setString(1, customerName);
            return statement;
        }, keyHolder);

        if (affectedRows != 1) {
            throw new IllegalStateException(
                    "Expected one inserted row, got " + affectedRows);
        }

        Number generatedId = keyHolder.getKey();
        if (generatedId == null) {
            throw new IllegalStateException("Database did not return an id");
        }

        return generatedId.longValue();
    }
}
```

**`src/main/java/com/example/keyholder/KeyholderDemoApplication.java`**:

```java
package com.example.keyholder;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class KeyholderDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(KeyholderDemoApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(OrderRepository repository) {
        return args -> {
            long id = repository.create("An");
            System.out.println("Created order with id=" + id);
        };
    }
}
```

Requires JDK 17+ and Maven. From inside the `keyholder-demo` directory:

```bash
mvn -q spring-boot:run
```

In a run against a **fresh H2 database with an empty table**, the line printed by the program is:

```text
Created order with id=1
```

ID `1` is the result of the fresh initialization setup in the example; on a database with existing data, the key can differ and should not be assumed sequential. With `logging.level.root=ERROR`, normal logs are suppressed; library/tool output may vary by environment.

**Why does the example work?** `connection.prepareStatement(INSERT_SQL, new String[]{"id"})` both creates the statement with the `?` placeholder and asks the JDBC driver to return the `id` column; `JdbcTemplate.update(creator, keyHolder)` executes it and populates the key into the holder. Only after `update` completes is `getKey()` read. The `customerName` parameter is bound with `setString` to preserve the proper type and avoid dangerous SQL string concatenation.

## 4. Two ways to request the driver to return generated keys

Use a **column-name array** when you need control over the returned key column and the driver supports it:

```java
PreparedStatement ps =
        connection.prepareStatement(INSERT_SQL, new String[] {"id"});
ps.setString(1, customerName);
```

Or request generated keys using the general JDBC flag:

```java
import java.sql.Statement;

// Inside the PreparedStatementCreator callback:
PreparedStatement ps =
        connection.prepareStatement(INSERT_SQL, Statement.RETURN_GENERATED_KEYS);
ps.setString(1, customerName);
```

Both are overloads of `Connection.prepareStatement(...)`; **do not use both in the same statement creation call**. `RETURN_GENERATED_KEYS` is often convenient for a single numeric ID. Depending on the database/driver, it may return extra columns, use different column names, or not support it fully; in that case `getKey()` may fail because the map contains multiple columns. Specifying `new String[]{"id"}` can be more precise, though it also depends on the driver's capabilities and column-naming rules. Always test against the project's actual database system.

**Do not** call `jdbcTemplate.update(INSERT_SQL, customerName)` and then `getKey()` on a separate holder: that `update(sql, args...)` overload does not accept a `KeyHolder` and does not populate keys into it. You must use `update(PreparedStatementCreator, KeyHolder)` or another API that supports returning keys.

## 5. Single key, multiple key columns, multiple key rows

### Single numeric key

```java
Number key = keyHolder.getKey();
if (key == null) {
    throw new IllegalStateException("No generated key returned");
}
long id = key.longValue();
```

Use `Number` because drivers may return `Long`, `Integer`, `BigDecimal`, etc., depending on the database. If the value can exceed the `long` range, check the type and range before converting; `longValue()` does not preserve all large numeric values.

### Single row, multiple returned columns

When the driver provides additional default-computed columns, calling `getKey()` may be invalid. Use:

```java
Map<String, Object> generated = keyHolder.getKeys();
if (generated == null || generated.isEmpty()) {
    throw new IllegalStateException("No generated columns returned");
}
System.out.println(generated);
```

Example **illustrative data shape**, not a guaranteed result across every driver: `{ID=42, PUBLIC_CODE=ORD-0042}`. The map contains **column name → value**; the name may be `id`, `ID`, or an alias depending on the driver. Inspect the actual keys or specify the column list to return before calling `generated.get("id")`. If **multiple rows** are returned, `getKeys()` is not the right choice either.

### Multiple rows returned by JDBC

```java
List<Map<String, Object>> rowsOfKeys = keyHolder.getKeyList();
for (Map<String, Object> keysForRow : rowsOfKeys) {
    System.out.println(keysForRow);
}
```

Each element is a map for one row of the generated-keys `ResultSet`. It is suitable when the statement/driver returns multiple key rows. **Do not assume** a standard `JdbcTemplate.batchUpdate(...)` API will populate a shared `KeyHolder`: common batch overloads do not take a holder like `update(PreparedStatementCreator, KeyHolder)`. When doing batch inserts, check driver characteristics, the chosen API, the number/order of returned keys, and the strategy for mapping back to each record. For non-numeric keys such as database-generated UUIDs, `getKeyAs(UUID.class)` should only be used when the driver actually returns an object of type `UUID`.

## 6. Comparison with SimpleJdbcInsert and SQL RETURNING

| Approach | When to use | Points to watch |
| --- | --- | --- |
| `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` | Need control over SQL, parameters, statement, and returned keys | Write callback to enable generated keys; depends on JDBC driver |
| `SimpleJdbcInsert.executeAndReturnKey(...)` | Simple INSERT, single numeric generated key | Declare table/key columns; API leverages database metadata |
| `SimpleJdbcInsert.executeAndReturnKeyHolder(...)` | Need multiple columns or non-numeric keys | Handle holder according to actual result structure |
| SQL `INSERT ... RETURNING` via appropriate query API | DB supports `RETURNING` and complex returned results are needed | Syntax and handling are DBMS-specific; do not assume parity across all JDBC drivers |

Example using `SimpleJdbcInsert` inside a DAO that already has `DataSource`:

```java
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

SimpleJdbcInsert insertOrder = new SimpleJdbcInsert(dataSource)
        .withTableName("orders")
        .usingColumns("customer_name")
        .usingGeneratedKeyColumns("id");

Number newId = insertOrder.executeAndReturnKey(
        Map.of("customer_name", "An"));
long id = newId.longValue();
```

This is an **illustrative snippet inside a method/class that has a `dataSource` variable**, not a standalone Java file. In a real application, configure the `SimpleJdbcInsert` object at the repository level and reuse it rather than creating a new one on every call. `executeAndReturnKey(...)` is for a single numeric key; use `executeAndReturnKeyHolder(...)` if a richer structure is needed.

For PostgreSQL, a specific option is `INSERT ... RETURNING id` combined with a JDBC API capable of reading a `ResultSet` such as `queryForObject`; this is PostgreSQL syntax and should not be copied verbatim to every DBMS or assumed supported by every driver under the same `update` overload.

## 7. Transactions, correctness, and performance

- `KeyHolder` **does not manage transactions itself**. If the INSERT runs inside a `@Transactional` method, obtaining an ID only means the statement generated/returned the key; the transaction can still be rolled back afterward.
- Identity/sequence generators may have already consumed a value even if the transaction fails; **gaps between IDs are normal**, do not indicate lost data, and IDs cannot be used as contiguous sequence numbers.
- When creating a parent record and then child records using the generated key, run both statements in the same service/transaction when atomicity is needed. For example: create `orders`, get `orderId`, then insert `order_items(order_id, ...)`.
- Create a **`new GeneratedKeyHolder()` for every INSERT**; it is a mutable container holding per-call results. Never share a singleton/shared holder across multiple requests or threads.
- `JdbcTemplate` manages connection/statement/result set lifecycles and translates `SQLException` into Spring's `DataAccessException` hierarchy. Do not manually close `PreparedStatement` inside the callback before `update` executes.
- Bind values using `?` parameters. Table/column names are SQL structure, not bindable values; if dynamic structure is needed, allow-list from a predefined list rather than concatenating user input directly.
- You can use `update`'s returned affected row count and `KeyHolder` together; **the two pieces of data serve different purposes**. Checking `affectedRows == 1` only makes sense if the use case requires exactly one inserted record.

## 8. Common errors and diagnosis

| Symptom | Common cause | Check or fix |
| --- | --- | --- |
| `getKey() == null`, `getKeyList()` empty | Column not DB-generated, statement did not enable key return, driver lacks support or returned nothing | Check schema, `prepareStatement` overload, driver, SQL, and key names |
| `InvalidDataAccessApiUsageException` when calling `getKey()` | Driver returned multiple key columns or multiple key rows | Use `getKeys()`/`getKeyList()`, or restrict returned columns |
| `DataRetrievalFailureException` or type error reading key | Called `getKey()` on a non-`Number` key, or `getKeyAs(...)` with wrong runtime type | Inspect `getKeyList()`/map structure, pick the matching type |
| Got an ID, but querying immediately afterward finds no row | Transaction rolled back, read from another uncommitted transaction/connection, or read from a different DB | Check transaction boundaries, isolation, and datasource |
| Returned key data differs between H2 and real DB | Drivers and dialects differ in columns, labels, numeric types, and generated-keys behavior | Run integration tests on the real production database/driver |
| Wrong ID under concurrent execution | Shared holder, concatenated SQL, or inferring key via `MAX(id)` | Create per-call holder, use generated-keys API, strictly avoid `SELECT MAX(id)` to get the newly inserted key |

**Never use `SELECT MAX(id)` or `SELECT COUNT(*)` to guess the newly created key**: multiple requests can insert concurrently, the count/max value is inconsistent with the ID and causes race conditions. `KeyHolder` receives the key bound to the executed statement itself.

## 9. How to test a repository using KeyHolder

1. **Success case**: on a fresh database, call `create("An")`, receive a positive ID; run `JdbcTemplate.queryForObject("SELECT customer_name FROM orders WHERE id = ?", String.class, id)` and verify the value equals `"An"`.
2. **Real schema/driver**: run at least one integration test against the production DBMS or a compatible container, because key-returning behavior and data types differ from H2.
3. **Do not assume ID ordering**: test row existence and uniqueness; avoid asserting that two consecutive IDs differ by exactly `1`.
4. **Rollback**: inside a `@Transactional` service, intentionally throw an exception to verify the inserted data is gone after rollback; do not expect the identity/sequence counter to rewind.
5. **Abnormal cases**: driver returns no key or returns multiple columns; confirm the code handles `null`/exceptions transparently instead of returning a fake ID.

## 10. Takeaways and self-check

- `KeyHolder` is the contract for reading keys; `GeneratedKeyHolder` is the container implementing that contract.
- Spring does not allocate IDs itself; the database generates the key and the driver must return it, after which `JdbcTemplate` places it into the holder.
- Use the right `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` overload and enable key return when creating the statement.
- `getKey()` is only suitable for **one numeric key from one row**. The general structure resides in `List<Map<String, Object>>`.
- Key values may differ in Java type, column name, column count, or row count depending on the database/driver; test with the real system.
- Having a new ID does not mean the transaction has committed; nor are IDs guaranteed to be contiguous.

**Ask yourself:** (1) Why does `jdbcTemplate.update("INSERT ...", ...)` return `1` but not the ID? (2) If `getKey()` throws because two columns were returned, which structure should you read? (3) When a transaction rolls back, is the sequence/identity value guaranteed to be rolled back too? If you can answer all three, you have grasped the core mechanism and limitations of `KeyHolder`.
