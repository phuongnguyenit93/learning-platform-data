# Declaring Database-Generated Key Columns with SimpleJdbcInsert

When inserting a record, the application typically supplies attributes such as name and email, while **the database generates the primary key** (`id`). With Spring JDBC, `SimpleJdbcInsert` lets you declare this key column via `usingGeneratedKeyColumns("id")` and retrieve the generated key using `executeAndReturnKey(...)` or `executeAndReturnKeyHolder(...)`.

The goal of this lesson is to understand **declaring auto-generated key columns**, how the table definition and Spring work together, how to receive returned keys, multi-key or non-numeric key cases, and common pitfalls.

## 1. Two Distinct Responsibilities: The Database Generates the Key, Spring Declares How to Read It

Suppose we have a `customers` table:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL
);
```

In this H2 example, `GENERATED BY DEFAULT AS IDENTITY` specifies that **the database itself** generates the value for `id` when an `INSERT` statement omits `id`.

On the Java side, declare:

```java
SimpleJdbcInsert insertCustomer = new SimpleJdbcInsert(dataSource)
    .withTableName("customers")
    .usingColumns("full_name", "email")
    .usingGeneratedKeyColumns("id");
```

Keep these responsibilities distinct:

- `withTableName("customers")`: specifies the target table receiving the record.
- `usingColumns("full_name", "email")`: specifies **the columns that will receive values** in the `INSERT` statement.
- `usingGeneratedKeyColumns("id")`: tells Spring **the name of the auto-generated column to retrieve via JDBC**.
- `executeAndReturnKey(...)`: executes a single-row insert and reads the key returned by the database.

**Core point:** `usingGeneratedKeyColumns` **does not create a column**, does not turn `id` into `IDENTITY`, and does not generate ID numbers in Java. If the schema lacks a key-generation mechanism (identity, sequence/default, appropriate trigger, etc.), calling this method alone will not make the database generate values. Likewise, having the database generate a key **does not guarantee** your code will receive it if you pick the wrong API or the driver does not support key retrieval.

## 2. Syntax and How It Works

Most common declaration:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
    .withTableName("customers")
    .usingColumns("full_name", "email")
    .usingGeneratedKeyColumns("id");

Number id = insert.executeAndReturnKey(
    Map.of("full_name", "Lan", "email", "lan@example.test")
);
long customerId = id.longValue();
```

The snippet above **is only an API usage example**, assuming the table already exists and a valid `dataSource` is available; section 4 provides a standalone runnable program.

Related methods:

| API | Purpose | Return Type |
| --- | --- | --- |
| `withTableName(String)` | Selects the target table name to insert into | `SimpleJdbcInsert` for chaining |
| `withSchemaName(String)` | Specifies the schema if needed | `SimpleJdbcInsert` |
| `usingColumns(String...)` | Restricts the columns included in `INSERT` | `SimpleJdbcInsert` |
| `usingGeneratedKeyColumns(String...)` | Declares **one or more** auto-generated key columns to retrieve | `SimpleJdbcInsert` |
| `execute(Map<String, ?>)` | Inserts the record, returns the affected row count | `int` |
| `executeAndReturnKey(Map<String, ?>)` | Inserts and returns **a single numeric key** | `Number` |
| `executeAndReturnKeyHolder(Map<String, ?>)` | Inserts and returns key values via `KeyHolder` | `KeyHolder` |

The `execute...` overloads also accept `SqlParameterSource` (e.g., `MapSqlParameterSource`). Two common overloads:

```java
Number generated = insert.executeAndReturnKey(
    Map.of("full_name", "Lan", "email", "lan@example.test")
);
```

```java
MapSqlParameterSource params = new MapSqlParameterSource()
    .addValue("full_name", "Lan")
    .addValue("email", "lan@example.test");

Number generated = insert.executeAndReturnKey(params);
```

`MapSqlParameterSource` is useful when you need to pass `null` or declare a specific SQL type with `addValue(name, value, sqlType)`. If using `Map.of(...)`, remember that `Map.of` **does not allow null values**.

### How Does Spring Build SQL and Retrieve the Key?

Conceptually, Spring prepares a statement equivalent to:

```sql
INSERT INTO customers (full_name, email) VALUES (?, ?)
```

Main steps:

1. `SimpleJdbcInsert` uses its declared configuration and, by default, JDBC metadata to determine how to insert. It can compile the configuration at startup or automatically on first execution.
2. Spring binds the `full_name` and `email` parameters using `PreparedStatement`.
3. The database executes `INSERT`, generating `id` according to the table definition.
4. Spring requests and reads the key returned by the JDBC driver, based on the declared column.
5. `executeAndReturnKey` returns `Number`, or `executeAndReturnKeyHolder` returns a container holding the keys.

This is **a single record insert with key retrieval**. There is no need to run `SELECT MAX(id)` or query for the "highest ID" after inserting: those approaches are unsafe when multiple transactions insert concurrently. Spring uses JDBC's generated-key retrieval capability, with execution details varying across databases and drivers.

## 3. Declaring Key Columns Correctly

### 3.1. Do Not Pass the Auto-Generated Key in Input When Expecting the Database to Generate It

Correct:

```java
Map<String, Object> params = Map.of(
    "full_name", "Lan",
    "email", "lan@example.test"
);
Number newId = insert.executeAndReturnKey(params);
```

Wrong in intent:

```java
// If you expect the database to generate id, do not manually set id = 0 or null.
Map<String, Object> params = new HashMap<>();
params.put("id", 0L);
params.put("full_name", "Lan");
params.put("email", "lan@example.test");
```

If `usingColumns("full_name", "email")` already excludes `id` from the insert column list, an extra `id` value in the Map may be ignored; however, it still makes code confusing and error-prone if configuration changes. The clearest approach is **not passing `id` when the database is responsible for generating `id`**.

### 3.2. `usingColumns` and `usingGeneratedKeyColumns` Are Not Synonymous

```java
new SimpleJdbcInsert(dataSource)
    .withTableName("customers")
    .usingColumns("full_name", "email")
    .usingGeneratedKeyColumns("id");
```

`usingColumns` states which columns **receive values during INSERT**, whereas `usingGeneratedKeyColumns` states which columns **should be returned after INSERT**. These are two opposite data directions.

You can call only `withTableName(...).usingGeneratedKeyColumns("id")` and let Spring infer the column list from database metadata; however, `usingColumns` makes intent explicit and avoids unnecessary reliance on inferring unrelated columns. It is especially helpful when a table has many default/computed columns, or when the key must remain strictly in the generated-keys list.

### 3.3. Column Names Must Match the Database

Use the **actual SQL column name**, such as `customer_id`, rather than assuming the Java field name `customerId` works by default:

```java
// If the DDL defines column customer_id:
.usingGeneratedKeyColumns("customer_id");
```

For a different schema, declare `withSchemaName("...")` when needed. Quoted and case-sensitive identifiers can behave differently from unquoted names. The `usingQuotedIdentifiers()` API quotes identifiers using driver syntax, but when using it you must supply `usingColumns(...)` explicitly and ensure casing matches DB metadata. Do not use `usingQuotedIdentifiers()` merely as trial-and-error for random errors; compare the DDL and actual metadata first.

### 3.4. Key Type Must Match the Result Retrieval Method

For a single numeric key (`BIGINT`, `INTEGER`, etc.), use:

```java
Number generatedId = insert.executeAndReturnKey(params);
long id = generatedId.longValue();
```

`Number` may be `Long`, `Integer`, `BigDecimal`, or another subclass depending on the database/driver. Do not cast directly with `(Long) generatedId` unless you are certain of the concrete type. `longValue()` fits when your domain uses `long` and values stay within the `long` range; for large numeric types or lossless requirements, verify value ranges and convert accurately.

If the database returns multiple generated columns or a non-numeric key (such as UUID), use `executeAndReturnKeyHolder` instead of forcing it into `Number`.

## 4. Complete Runnable Example with Java 17+, Spring JDBC, and H2

The following program creates a table with an `IDENTITY` key, inserts two records with `SimpleJdbcInsert`, prints the newly generated IDs, and verifies the table contents. It uses in-memory H2 so no database server installation is required.

Structure:

```text
simple-insert-demo/
├── build.gradle
└── src/main/java/GeneratedKeyDemo.java
```

Contents of `build.gradle`:

```groovy
plugins {
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-jdbc:6.2.12'
    runtimeOnly 'com.h2database:h2:2.3.232'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

application {
    mainClass = 'GeneratedKeyDemo'
}
```

Contents of `src/main/java/GeneratedKeyDemo.java`:

```java
import java.util.Map;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.datasource.DriverManagerDataSource;

public class GeneratedKeyDemo {

    public static void main(String[] args) {
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:generated_keys;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");

        JdbcTemplate jdbc = new JdbcTemplate(dataSource);
        jdbc.execute("""
            CREATE TABLE customers (
                id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                full_name VARCHAR(100) NOT NULL,
                email VARCHAR(150) NOT NULL
            )
            """);

        SimpleJdbcInsert insertCustomer = new SimpleJdbcInsert(dataSource)
            .withTableName("customers")
            .usingColumns("full_name", "email")
            .usingGeneratedKeyColumns("id");

        // Lock configuration and check metadata before reusing.
        insertCustomer.compile();

        Number id1 = insertCustomer.executeAndReturnKey(
            Map.of("full_name", "An", "email", "an@example.test")
        );
        Number id2 = insertCustomer.executeAndReturnKey(
            Map.of("full_name", "Binh", "email", "binh@example.test")
        );

        System.out.println("First generated id: " + id1.longValue());
        System.out.println("Second generated id: " + id2.longValue());

        Integer count = jdbc.queryForObject(
            "SELECT COUNT(*) FROM customers", Integer.class
        );
        System.out.println("Rows in database: " + count);
    }
}
```

Run in the `simple-insert-demo` directory using an installed Gradle (if the project has a Gradle Wrapper, use `./gradlew --quiet run`):

```bash
gradle --quiet run
```

Lines printed by the program when run with in-memory H2 and the freshly created table above:

```text
First generated id: 1
Second generated id: 2
Rows in database: 2
```

Result explanation:

- H2 generates identity values starting at 1 in a fresh table; the two inserts receive `id=1` and `id=2` respectively.
- The input to `executeAndReturnKey` **contains only `full_name` and `email`**, without manually passing `id`.
- `usingGeneratedKeyColumns("id")` instructs Spring to retrieve the `id` value generated by H2.
- `COUNT(*)` proves two rows were stored; the `id` values are obtained from the JDBC result, not inferred from `COUNT(*)`.
- `compile()` is optional: Spring can auto-compile on the first call. Pre-compiling catches some configuration errors early and prepares one configured instance for subsequent inserts.

**Note:** The output `1, 2` comes from an H2 environment with a fresh table and no other operations. In real systems, IDs can have gaps due to rollbacks, sequence allocation, errors, or concurrent operations. Never guarantee that IDs are always contiguous, start at 1, or reflect exact chronological ordering across transactions.

## 5. When You Need Multiple Keys or Non-Numeric Keys: KeyHolder

`executeAndReturnKey(...)` targets the common case of retrieving **a single numeric key**. For more flexible result retrieval:

```java
import java.util.Map;
import org.springframework.jdbc.support.KeyHolder;

// Extension snippet, assuming insertCustomer is already configured
// and the customers table exists as in the example above.
KeyHolder holder = insertCustomer.executeAndReturnKeyHolder(
    Map.of("full_name", "Chi", "email", "chi@example.test")
);

Map<String, Object> generated = holder.getKeys();
if (generated == null || generated.isEmpty()) {
    throw new IllegalStateException("Database did not return generated keys");
}

System.out.println(generated);
```

`getKeys()` returns a `Map<String, Object>` for the key result row; **map key names and casing depend on the driver and metadata**. Do not assume every database returns a Map whose key is the exact string `"id"`. If you only need a single numeric key, `executeAndReturnKey(...)` remains the simplest approach.

If a table genuinely generates two values and the driver supports retrieving both, you can configure:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
    .withTableName("documents")
    .usingColumns("title")
    .usingGeneratedKeyColumns("id", "tracking_code");

KeyHolder holder = insert.executeAndReturnKeyHolder(
    Map.of("title", "Spring JDBC guide")
);
Map<String, Object> keys = holder.getKeys();
```

This snippet **illustrates the API**, not a standalone program; it requires a `documents` DDL capable of auto-generating both `id` and `tracking_code` along with a supporting driver. Declaring column names does not force the DB to return all of them. When results have multiple columns, calling `holder.getKey()` or `executeAndReturnKey(...)` may fail because those APIs expect **a single numeric key**.

If the driver returns multiple rows of generated keys, `KeyHolder` also provides `getKeyList()` to represent the list of key rows. `getKeys()` is only appropriate when expecting a single row; do not treat a `KeyHolder` as guaranteeing exactly one row and all columns returned.

## 6. DAO Design in Spring Boot

In a Spring Boot application, `DataSource` is usually configured by Spring. You can instantiate `SimpleJdbcInsert` once in a DAO or bean and reuse it:

```java
import java.util.Map;
import javax.sql.DataSource;

import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.stereotype.Repository;

@Repository
public class CustomerJdbcRepository {

    private final SimpleJdbcInsert insert;

    public CustomerJdbcRepository(DataSource dataSource) {
        this.insert = new SimpleJdbcInsert(dataSource)
            .withTableName("customers")
            .usingColumns("full_name", "email")
            .usingGeneratedKeyColumns("id");
    }

    public long create(String fullName, String email) {
        Number id = insert.executeAndReturnKey(
            Map.of("full_name", fullName, "email", email)
        );
        return id.longValue();
    }
}
```

This is a **DAO snippet for integration** (without DDL, Spring Boot configuration, or a standalone entry point). Use the Spring JDBC version managed by your project; there is no need to create `DriverManagerDataSource` manually in production applications.

Configure `SimpleJdbcInsert` in the constructor or during initialization, before handling concurrent calls. Once the instance is compiled, do not try to mutate `withTableName`, `usingColumns`, or `usingGeneratedKeyColumns` per request; create a separate instance if a different configuration is needed.

If a business operation inserts into `customers` and a secondary table and both must succeed together, use an appropriate transaction boundary, such as `@Transactional` on the service. Obtaining a generated ID **does not prove the transaction committed**. On rollback, the record will not exist even though the application previously observed an ID. Many databases also do not reclaim allocated sequence/identity numbers on rollback, so IDs can skip numbers.

## 7. Differences Between Generated Keys, Other Auto-Generated Values, and Application-Level Keys

| Case | Who Generates the Value? | Is `usingGeneratedKeyColumns` Suitable? |
| --- | --- | --- |
| `BIGINT IDENTITY` / auto-increment | Database | Yes, if the driver supports key retrieval. |
| Value drawn from a sequence via SQL default | Database | Possibly, depending on whether the database and driver return that column as a generated key. |
| UUID generated by DB via default/trigger | Database | Can use `executeAndReturnKeyHolder` if the driver can return this value. |
| UUID created via `UUID.randomUUID()` in Java | Java application | Not required; usually passed as an input parameter. |
| Manually entered client key | Client/application | No generated-key mechanism needed; `execute(...)` may suffice. |
| Computed/default value of another column | Database | Only readable via generated keys when supported by driver/database; otherwise query back by the known key. |

Also distinguish **Spring JDBC's `SimpleJdbcInsert`** from **JPA/Hibernate's `@GeneratedValue`**. They belong to two different data-access approaches. Configuring an ID generation strategy on a JPA entity does not alter how `SimpleJdbcInsert` works; for JDBC, the source of truth remains the schema and the driver's generated-key mechanism.

## 8. Common Errors and How to Verify

### 8.1. Forgetting `usingGeneratedKeyColumns("id")`

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
    .withTableName("customers")
    .usingColumns("full_name", "email");

// Generated key column not declared:
Number id = insert.executeAndReturnKey(params);
```

Calling key-retrieval methods requires the generated key column to be declared; missing configuration can throw `InvalidDataAccessApiUsageException`. Add the exact column name to `usingGeneratedKeyColumns` before compiling/running.

### 8.2. The Table Does Not Actually Generate Values

```sql
-- id is just a regular primary key, not declared as auto-generated:
CREATE TABLE wrong_customers (
    id BIGINT PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL
);
```

`.usingGeneratedKeyColumns("id")` cannot fix this DDL. You must define `IDENTITY` or an appropriate DB mechanism, or supply `id` from the application by design.

### 8.3. Declaring the Wrong Column Name, Schema, or Case

"Column not found", missing metadata, invalid insert SQL, or empty returned keys can happen when code uses `id` while the actual schema uses `customer_id`, the table lives in another schema, or identifiers are quoted with different casing. Verify table/column names via DDL and JDBC metadata; declare `withSchemaName(...)` when needed. Do not guess name variants on real data.

### 8.4. Expecting a `Long` Key Across Every DB

```java
// Unsafe across all JDBC drivers:
Long id = (Long) insert.executeAndReturnKey(params);
```

Use `Number` and convert according to your value range and key type. If the database generates non-numeric keys, use `executeAndReturnKeyHolder`. If there are multiple generated columns, never try to cast a `Map` to `Number`.

### 8.5. Calling Only `execute(...)` and Expecting an ID

`execute(...)` returns the **affected row count** (usually `1` for a single-row insert), **not the ID**. On the 100th record, returning `1` does not mean the generated key is `1`. When you need the ID, use `executeAndReturnKey` or `executeAndReturnKeyHolder`.

### 8.6. Relying on Generated Keys Unsupported by the Driver

The database and JDBC driver decide which keys can be returned and through which API. Some DBs/drivers only return the identity column; some drivers support UUID/default/computed columns; and some omit column names or return unexpected extra columns. Test with the **exact production driver and DB version**, especially in multi-vendor systems. Do not assume that having a trigger guarantees the driver will return trigger-populated values.

### 8.7. Trying to Retrieve Generated IDs from Batch Insert via Another API

`SimpleJdbcInsert.executeBatch(...)` returns an `int[]` of update counts, **not a list of generated IDs**. If business logic requires mapping each exact ID after a batch, examine driver-specific JDBC APIs, single-record inserts, or DB-supported result mechanisms separately. Never derive IDs from update counts.

### 8.8. Using IDs to Infer Transactions and Contiguity

IDs can be allocated and then the transaction rolled back; sequences/identities can skip numbers and concurrent requests can interleave. Never compute new IDs as "previous ID + 1", never use `MAX(id)` to look up the record you just created, and never depend on contiguous keys in business logic.

## 9. Recommended Test Scenarios

1. **Standard case:** `IDENTITY` table created, input includes only business columns, `executeAndReturnKey` returns a valid key; querying by ID finds the exact row.
2. **Multiple inserts:** IDs are unique; row counts increase accordingly. Do not rigidly assert contiguous IDs in multi-transaction environments.
3. **Constraint violation:** e.g., duplicate `UNIQUE(email)`; confirm an appropriate `DataAccessException` is thrown, update counts are not mistaken for IDs, and transactions handle it properly.
4. **Misnamed key column:** test that configuration/driver errors yield clear messages rather than "guessing" IDs with `MAX(id)`.
5. **UUID key or multiple generated columns:** use `KeyHolder` and verify whether the driver actually returns the expected columns.
6. **Rollback:** create a record in a transaction and force a rollback; the record no longer exists even though an ID was previously returned.
7. **Production DB integration:** confirm value types (`Long`, `BigDecimal`, UUID, etc.), column names returned in `KeyHolder`, schema/casing, and default/trigger behavior.

In particular, a good test should **query back by the received ID** and compare business fields. That proves the ID maps to the exact row just inserted, rather than only checking `id != null`.

## 10. Self-Assessment Questions

**Question 1.** A table has `id BIGINT GENERATED BY DEFAULT AS IDENTITY`. To insert `name` and receive the ID, what should you call?

- Configure `withTableName(...).usingColumns("name").usingGeneratedKeyColumns("id")`, then call `executeAndReturnKey(...)` with the `name` input.

**Question 2.** Why is adding `usingGeneratedKeyColumns("id")` not enough if the DDL has a plain `id BIGINT PRIMARY KEY`?

- Because Spring only **declares which column to read the key from**; the value-generation mechanism must be provided by the database or the application.

**Question 3.** `execute(...)` returns `1`. Can you conclude the generated ID is `1`?

- No. `1` is the number of affected rows; the ID must be obtained via generated keys.

**Question 4.** A table has an auto-generated UUID key or returns two columns. Can you cast `executeAndReturnKey(...)` to `Long`?

- No. Use `executeAndReturnKeyHolder(...)` and inspect key contents according to the actual type returned by the driver.

**Question 5.** You just received an ID, but then the transaction rolled back. Can you consider the record durably saved?

- No. Receiving the ID happens during the insert step and does not prove the transaction committed.

## 11. Summary

- The database creates keys via DDL/defaults/sequences/triggers; **`SimpleJdbcInsert.usingGeneratedKeyColumns(...)` declares the column to retrieve**, rather than generating keys on the DB's behalf.
- Use `usingColumns(...)` to specify input columns, omitting `id` when the database should assign the key.
- Use `executeAndReturnKey(...)` for **a single numeric key**, handling the result as `Number`. Use `executeAndReturnKeyHolder(...)` for multiple keys or non-numeric types when supported by the DB/driver.
- Do not confuse `execute(...)` (update count) with a generated ID; never query `MAX(id)` to guess a new ID.
- Column/schema/case naming, JDBC driver generated-key support, transactions, and rollbacks must be verified through integration tests against the real DB.
