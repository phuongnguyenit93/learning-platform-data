# GeneratedKeyHolder và KeyHolder trong Spring JDBC

## 1. Bài toán: INSERT xong, lấy khóa do cơ sở dữ liệu sinh

Giả sử bảng `orders` có cột `id` được cơ sở dữ liệu tự sinh (identity/auto-increment). Khi tạo một đơn hàng, ứng dụng cần ID mới để trả về cho API, gán cho đối tượng domain hoặc dùng làm khóa ngoại trong thao tác tiếp theo.

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);
```

Câu lệnh `INSERT INTO orders (customer_name) VALUES (?)` không truyền `id`. Cơ sở dữ liệu sẽ cấp giá trị ID khi thực thi lệnh. Tuy nhiên, `JdbcTemplate.update(sql, args...)` thông thường trả về **số dòng bị tác động** (ví dụ `1`), **không phải ID vừa sinh**. Spring JDBC cung cấp `KeyHolder` để giữ dữ liệu khóa mà JDBC driver trả về sau khi thực thi câu lệnh.

Cần phân biệt ba việc:
- **Sinh khóa**: do cơ sở dữ liệu (identity, sequence, default expression, trigger...) đảm nhiệm theo thiết kế schema.
- **Yêu cầu trả khóa**: do `PreparedStatement`/JDBC driver được cấu hình để truy xuất generated keys.
- **Giữ và đọc khóa**: do `KeyHolder` và đối tượng `GeneratedKeyHolder` đảm nhiệm.

`KeyHolder` không phát minh ID và không tự khóa bảng hay bản ghi. Nếu driver/cơ sở dữ liệu không trả khóa, việc tạo `GeneratedKeyHolder` đơn thuần không khiến ID xuất hiện.

## 2. Vai trò của KeyHolder và GeneratedKeyHolder

Cả hai ở package `org.springframework.jdbc.support`:

- `KeyHolder` là **interface**, định nghĩa cách truy xuất các khóa được trả về.
- `GeneratedKeyHolder` là **implementation mặc định** của `KeyHolder`, chứa danh sách các map khóa do Spring nạp từ `ResultSet` của `PreparedStatement.getGeneratedKeys()`.

Khai báo thông dụng:

```java
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

KeyHolder keyHolder = new GeneratedKeyHolder();
```

Luồng thực thi điển hình:

```text
Ứng dụng
   │ tạo KeyHolder và PreparedStatementCreator
   ▼
JdbcTemplate.update(creator, keyHolder)
   │ lấy Connection, tạo PreparedStatement có bật trả khóa
   │ bind các tham số, thực thi INSERT
   ▼
JDBC PreparedStatement.getGeneratedKeys()
   │ ResultSet chứa những cột/dòng mà driver trả về
   ▼
JdbcTemplate chép ResultSet vào KeyHolder
   │
   ▼
Ứng dụng đọc getKey() / getKeys() / getKeyList()
```

**Các cách đọc kết quả:**

| Phương thức | Kiểu trả về | Trường hợp dùng và ràng buộc |
| --- | --- | --- |
| `getKey()` | `Number` hoặc `null` | Đúng **một dòng khóa, một cột khóa kiểu số**; ném lỗi nếu có nhiều dòng/cột. |
| `getKeyAs(Class<T>)` | `T` hoặc `null` | Đúng một dòng/cột, khi giá trị là kiểu yêu cầu (ví dụ `UUID.class` nếu driver thực sự trả `UUID`); không phải bộ chuyển đổi kiểu tùy ý. |
| `getKeys()` | `Map<String, Object>` hoặc `null` | Lấy **toàn bộ các cột khóa của một dòng**; lỗi nếu có nhiều dòng khóa. |
| `getKeyList()` | `List<Map<String, Object>>` | Xem nhiều dòng khóa; mỗi map ứng với một dòng của `ResultSet` returned keys. |

`getKey()` và `getKeyAs(...)` có thể ném `InvalidDataAccessApiUsageException` nếu số cột/dòng không đúng kỳ vọng, hoặc lỗi truy xuất kiểu dữ liệu nếu giá trị không tương thích. `getKeyList()` có thể là danh sách rỗng nếu không lấy được khóa. Một lần gọi `JdbcTemplate.update(...)` thành công không đảm bảo key được trả về: đó còn phụ thuộc SQL, schema và driver.

**Quy tắc chọn:** một khóa số → `getKey()`; một khóa không phải số → `getKeyAs(type)` khi kiểu đã rõ; nhiều cột trả về trong một dòng → `getKeys()`; nhiều dòng khóa → `getKeyList()`.

**`src/main/java/com/example/keyholder/OrderRepository.java`**:

```java
package com.example.keyholder;

import java.sql.PreparedStatement;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class OrderRepository {
    private static final String INSERT_SQL =
            "INSERT INTO orders (customer_name) VALUES (?)";

    private final JdbcTemplate jdbcTemplate;

    public OrderRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public long create(String customerName) {
        KeyHolder keyHolder = new GeneratedKeyHolder();

        int affectedRows = jdbcTemplate.update(connection -> {
            // Yêu cầu driver trả cột id được sinh sau INSERT.
            PreparedStatement statement =
                    connection.prepareStatement(INSERT_SQL, new String[] {"id"});
            statement.setString(1, customerName);
            return statement;
        }, keyHolder);

        if (affectedRows != 1) {
            throw new IllegalStateException(
                    "Expected one inserted row, got " + affectedRows);
        }

        Number generatedId = keyHolder.getKey();
        if (generatedId == null) {
            throw new IllegalStateException("Database did not return an id");
        }

        return generatedId.longValue();
    }
}
```

**`src/main/java/com/example/keyholder/KeyholderDemoApplication.java`**:

```java
package com.example.keyholder;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;

@SpringBootApplication
public class KeyholderDemoApplication {

        SpringApplication.run(KeyholderDemoApplication.class, args);
    }

```

Yêu cầu JDK 17+ và Maven. Đứng trong thư mục `keyholder-demo`:

```bash
mvn -q spring-boot:run
```

Trong một lần chạy với **cơ sở dữ liệu H2 mới, bảng trống**, dòng do chương trình in ra là:

```text
Created order with id=1
```

ID `1` là kết quả của cấu hình khởi tạo mới trong ví dụ; trên database có sẵn dữ liệu, khóa có thể khác và không nên được giả định liên tiếp. Trong cấu hình `logging.level.root=ERROR`, các log thông thường được giảm bớt; đầu ra của thư viện/tool có thể khác tùy môi trường.

**Tại sao ví dụ hoạt động?** `connection.prepareStatement(INSERT_SQL, new String[]{"id"})` vừa tạo câu lệnh với placeholder `?`, vừa yêu cầu JDBC driver trả lại cột `id`; `JdbcTemplate.update(creator, keyHolder)` thực thi và nạp khóa cho holder. Chỉ sau khi `update` hoàn tất mới đọc `getKey()`. Tham số `customerName` được bind bằng `setString` để giữ đúng kiểu và tránh ghép chuỗi SQL nguy hiểm.

## 4. Hai cách yêu cầu driver trả generated key

Dùng **danh sách tên cột** khi cần kiểm soát cột khóa trả về và driver hỗ trợ:

```java
PreparedStatement ps =
        connection.prepareStatement(INSERT_SQL, new String[] {"id"});
ps.setString(1, customerName);
```

Hoặc yêu cầu generated keys theo chế độ JDBC tổng quát:

```java
import java.sql.Statement;

// Bên trong callback PreparedStatementCreator:
PreparedStatement ps =
        connection.prepareStatement(INSERT_SQL, Statement.RETURN_GENERATED_KEYS);
ps.setString(1, customerName);
```

Cả hai là các overload của `Connection.prepareStatement(...)`; **không dùng cả hai trong cùng một lần tạo statement**. Cách `RETURN_GENERATED_KEYS` thường tiện cho ID số đơn lẻ. Tùy database/driver, nó có thể trả thêm cột khác, đặt tên cột khác, hoặc không hỗ trợ hoàn toàn; khi đó `getKey()` có thể lỗi vì map chứa nhiều cột. Cách chỉ định `new String[]{"id"}` có thể chính xác hơn nhưng cũng phụ thuộc khả năng và quy tắc đặt tên cột của driver. Luôn kiểm tra với hệ quản trị cơ sở dữ liệu thật của dự án.

**Không dùng** `jdbcTemplate.update(INSERT_SQL, customerName)` rồi gọi `getKey()` trên một holder riêng: overload `update(sql, args...)` đó không nhận `KeyHolder` và không nạp key cho nó. Cần overload `update(PreparedStatementCreator, KeyHolder)` hoặc API khác hỗ trợ trả khóa.

## 5. Một khóa, nhiều cột khóa, nhiều dòng khóa

### Một khóa số

```java
Number key = keyHolder.getKey();
if (key == null) {
    throw new IllegalStateException("No generated key returned");
}
long id = key.longValue();
```

Dùng `Number` vì driver có thể trả `Long`, `Integer`, `BigDecimal`... tùy database. Nếu giá trị có thể vượt phạm vi `long`, phải kiểm tra kiểu và phạm vi trước khi chuyển; `longValue()` không bảo toàn mọi giá trị số lớn.

### Một dòng, nhiều cột được trả về

Khi driver cung cấp thêm các cột được tính mặc định, việc đọc `getKey()` có thể không hợp lệ. Dùng:

```java
Map<String, Object> generated = keyHolder.getKeys();
if (generated == null || generated.isEmpty()) {
    throw new IllegalStateException("No generated columns returned");
}
System.out.println(generated);
```

Ví dụ **hình dạng dữ liệu minh họa**, không phải kết quả bảo đảm của mọi driver: `{ID=42, PUBLIC_CODE=ORD-0042}`. Map chứa **tên cột → giá trị**; tên có thể là `id`, `ID` hoặc alias tùy driver. Kiểm tra các key thực tế hoặc chỉ định danh sách cột cần trả trước khi dùng `generated.get("id")`. Nếu có **nhiều dòng** được trả về, `getKeys()` cũng không phải lựa chọn đúng.

### Nhiều dòng được JDBC trả về

```java
List<Map<String, Object>> rowsOfKeys = keyHolder.getKeyList();
for (Map<String, Object> keysForRow : rowsOfKeys) {
    System.out.println(keysForRow);
}
```

Mỗi phần tử là một map cho một dòng của generated-keys `ResultSet`. Nó phù hợp khi câu lệnh/driver trả nhiều dòng khóa. **Không mặc định** một API `JdbcTemplate.batchUpdate(...)` thông thường sẽ điền chung một `KeyHolder`: các overload batch thông dụng không nhận holder như overload `update(PreparedStatementCreator, KeyHolder)`. Khi làm batch insert, kiểm tra đặc tính driver, API được chọn, số lượng/ thứ tự khóa trả về, và chiến lược ánh xạ lại từng bản ghi. Với khóa không phải số như UUID do database sinh, `getKeyAs(UUID.class)` chỉ nên dùng khi thực tế driver trả về đối tượng `UUID` đúng kiểu.

## 6. So sánh với SimpleJdbcInsert và SQL RETURNING

| Cách làm | Khi nên dùng | Điểm cần chú ý |
| --- | --- | --- |
| `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` | Cần kiểm soát SQL, tham số, statement và returned keys | Viết callback để bật generated keys; phụ thuộc JDBC driver |
| `SimpleJdbcInsert.executeAndReturnKey(...)` | INSERT đơn giản, một generated key số | Khai báo bảng/cột khóa; API tận dụng metadata của database |
| `SimpleJdbcInsert.executeAndReturnKeyHolder(...)` | Cần nhiều cột hoặc khóa không phải số | Xử lý holder theo cấu trúc kết quả thật |
| SQL `INSERT ... RETURNING` qua API query phù hợp | DB hỗ trợ `RETURNING` và cần kết quả trả về phức tạp | Cú pháp và cách xử lý là đặc thù hệ quản trị; không giả định tương đương mọi JDBC driver |

Ví dụ dùng `SimpleJdbcInsert` trong một DAO đã có `DataSource`:

```java
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

SimpleJdbcInsert insertOrder = new SimpleJdbcInsert(dataSource)
        .withTableName("orders")
        .usingColumns("customer_name")
        .usingGeneratedKeyColumns("id");

Number newId = insertOrder.executeAndReturnKey(
        Map.of("customer_name", "An"));
long id = newId.longValue();
```

Đây là **đoạn minh họa bên trong phương thức/lớp có biến `dataSource`**, không phải một file Java độc lập. Trong ứng dụng thật, nên cấu hình đối tượng `SimpleJdbcInsert` ở tầng repository rồi tái sử dụng, thay vì tạo mới cho mỗi lần gọi. `executeAndReturnKey(...)` dành cho khóa số đơn; dùng `executeAndReturnKeyHolder(...)` nếu cần cấu trúc phong phú hơn.

Đối với PostgreSQL, một lựa chọn riêng là `INSERT ... RETURNING id` kết hợp một API JDBC có thể đọc `ResultSet` như `queryForObject`; đây là cú pháp PostgreSQL, không nên sao chép nguyên sang mọi hệ CSDL hoặc tự giả định mọi driver hỗ trợ dưới cùng một overload `update`.

## 7. Transaction, tính đúng đắn và hiệu năng

- `KeyHolder` **không tự quản lý transaction**. Nếu thao tác INSERT nằm trong phương thức `@Transactional`, việc lấy được ID chỉ có nghĩa statement đã tạo/trả khóa; transaction vẫn có thể bị rollback sau đó.
- Identity/sequence có thể đã tiêu thụ một giá trị ngay cả khi transaction thất bại; **khoảng trống giữa các ID là bình thường**, không chứng tỏ mất dữ liệu và không thể dùng ID như số thứ tự liên tục.
- Khi tạo bản ghi cha rồi tạo con dùng khóa vừa sinh, thực hiện hai lệnh trong cùng service/transaction khi cần tính nguyên tử. Ví dụ: tạo `orders`, lấy `orderId`, rồi chèn `order_items(order_id, ...)`.
- Tạo **`new GeneratedKeyHolder()` cho mỗi lần INSERT**; đó là container mutable chứa kết quả theo lượt gọi. Đừng dùng một holder singleton/shared giữa nhiều request hoặc luồng.
- `JdbcTemplate` quản lý vòng đời connection/statement/result set và dịch `SQLException` sang hệ `DataAccessException` của Spring. Không đóng thủ công `PreparedStatement` ngay bên trong callback trước khi `update` thực thi.
- Bind giá trị bằng tham số `?`. Tên bảng/tên cột là cấu trúc SQL, không bind như giá trị; nếu cần cấu trúc động phải cho phép từ danh sách định nghĩa sẵn, không ghép trực tiếp dữ liệu người dùng.
- Có thể dùng `update` trả về số dòng bị tác động và `KeyHolder` cùng lúc; **hai dữ kiện phục vụ mục đích khác nhau**. Kiểm tra `affectedRows == 1` chỉ có ý nghĩa nếu use case đòi đúng một bản ghi được chèn.

## 8. Lỗi thường gặp và cách chẩn đoán

| Triệu chứng | Nguyên nhân thường gặp | Kiểm tra hoặc xử lý |
| --- | --- | --- |
| `getKey() == null`, `getKeyList()` rỗng | Cột không do DB sinh, câu lệnh không bật trả khóa, driver không hỗ trợ hoặc không trả kết quả | Kiểm tra schema, overload `prepareStatement`, driver, SQL và key names |
| `InvalidDataAccessApiUsageException` khi gọi `getKey()` | Driver trả nhiều cột khóa hoặc nhiều dòng khóa | Dùng `getKeys()`/`getKeyList()`, hoặc giới hạn cột cần trả |
| `DataRetrievalFailureException` hoặc lỗi type khi đọc khóa | Gọi `getKey()` với key không phải `Number`, hoặc `getKeyAs(...)` sai kiểu runtime | Xem cấu trúc `getKeyList()`/map, chọn kiểu phù hợp |
| Có ID nhưng truy vấn ngay sau đó không thấy hàng | Transaction đã rollback, đọc bằng transaction/connection khác chưa thấy commit hoặc thao tác đọc không cùng DB | Kiểm tra transaction boundary, isolation, datasource |
| Dữ liệu khóa trả về khác giữa H2 và DB thật | Driver và dialect có khác biệt về columns, labels, kiểu số và hành vi generated keys | Integration test trên đúng database/driver production |
| Có ID sai sau chạy đồng thời | Dùng holder chung, ghép SQL, hoặc tự suy diễn khóa bằng `MAX(id)` | Tạo holder riêng, dùng generated-keys API, tuyệt đối tránh `SELECT MAX(id)` để lấy khóa vừa chèn |

**Không dùng `SELECT MAX(id)` hoặc `SELECT COUNT(*)` để đoán khóa vừa tạo**: nhiều request có thể chèn cùng lúc, giá trị đếm không đồng nhất với ID và gây race condition. `KeyHolder` nhận khóa gắn với chính statement thực thi.

## 9. Cách kiểm thử một repository dùng KeyHolder

1. **Trường hợp thành công**: với database mới, gọi `create("An")`, nhận ID dương; dùng `JdbcTemplate.queryForObject("SELECT customer_name FROM orders WHERE id = ?", String.class, id)` và xác nhận giá trị bằng `"An"`.
2. **Schema/driver thật**: chạy ít nhất một integration test trên hệ CSDL production hoặc container tương thích, vì khả năng trả khóa và kiểu dữ liệu khác H2.
3. **Không giả định thứ tự ID**: test sự tồn tại của hàng và tính duy nhất, tránh khẳng định hai ID liên tiếp chênh lệch đúng `1`.
4. **Rollback**: trong một service `@Transactional`, cố tình ném exception để xác minh dữ liệu chèn không còn sau rollback; không kỳ vọng bộ đếm identity/sequence quay lại.
5. **Trường hợp bất thường**: driver không trả key hoặc trả nhiều cột; xác nhận code xử lý `null`/exception minh bạch thay vì trả ID giả.

## 10. Ghi nhớ và tự kiểm tra

- `KeyHolder` là hợp đồng đọc khóa; `GeneratedKeyHolder` là container triển khai hợp đồng đó.
- Spring không tự cấp ID; database sinh khóa và driver phải trả khóa, sau đó `JdbcTemplate` đưa vào holder.
- Dùng đúng overload `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` và bật trả khóa khi tạo statement.
- `getKey()` chỉ thích hợp với **một khóa số của một dòng**. Cấu trúc tổng quát nằm ở `List<Map<String, Object>>`.
- Giá trị khóa có thể khác kiểu Java, tên cột, số cột hoặc số dòng tùy database/driver; kiểm thử với hệ thật.
- Có ID mới không đồng nghĩa transaction đã commit; ID cũng không đảm bảo liên tục.

**Tự hỏi:** (1) Vì sao `jdbcTemplate.update("INSERT ...", ...)` trả `1` nhưng không trả ID? (2) Nếu `getKey()` ném lỗi do trả hai cột, nên đọc cấu trúc nào? (3) Khi transaction rollback, có chắc giá trị sequence/identity được hoàn lại? Nếu trả lời được ba câu này, bạn đã nắm cơ chế và giới hạn quan trọng nhất của `KeyHolder`.
