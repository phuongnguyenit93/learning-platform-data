# Translating SQLException While Preserving the Original Cause in Spring Framework

> **Context:** Spring Framework – Data Access, **Data Exceptions** group. This lesson focuses on how to translate JDBC `SQLException` errors into Spring's `DataAccessException` classification **without losing the original `SQLException`**, cause chain, SQLState, and database vendor error code.

## 1. Why Translate Exceptions While Preserving the Cause?

When executing SQL directly with JDBC, the driver can throw `SQLException` or one of its subclasses. The error typically contains specific details: `SQLState`, `vendorCode`, the original message, and sometimes an additional `SQLException` chain. If the service layer has to handle individual codes from PostgreSQL, MySQL, Oracle, SQL Server, or H2 separately, application code becomes tied to the database.

Spring JDBC uses `SQLExceptionTranslator` to convert such technical errors into **unchecked** subclasses of `org.springframework.dao.DataAccessException`, such as `DataIntegrityViolationException` or `BadSqlGrammarException`. This allows upper layers to handle errors based on **the nature of the failure** rather than the driver name.

However, the translation process **must not erase the original information**. Two layers of information need to coexist:

```text
Service layer
    |
    +-- DataIntegrityViolationException (Spring classification)
            |
            +-- getCause() -> SQLException from JDBC driver
                    |
                    +-- getSQLState(): "23505"
                    +-- getErrorCode(): DB/driver-specific code
                    +-- getMessage(): technical description
                    +-- getNextException(): additional SQLException (if any)
```

For a unique-key violation, the service usually only needs to know this is a **data integrity** error; the operations team needs to know *which constraint* was violated, the driver version, SQLState, and raw details for diagnostics. **Translating the error type and preserving the original cause serve two complementary goals.**

### Goals to Achieve

- Retain the original exception in `cause` when creating a new exception; original details remain accessible.
- Use Spring exception types for business logic and transaction boundaries.
- Read `SQLState`/vendor code when investigating; do not rely on `getMessage()` for classification.
- Understand the limits of `getRootCause()`: not every `DataAccessException` originates from JDBC.
- Avoid losing the `getNextException()` chain, especially when the driver returns a `BatchUpdateException`.
- Never let SQL details, passwords, or sensitive data values leak into API responses.

## 2. Reading Data Properly from SQLException

An `SQLException` can provide:

| Property | API | What to understand |
| --- | --- | --- |
| Message | `getMessage()` | String generated by the driver; useful for debugging, may contain SQL/table names/data; unstable for string matching. |
| SQLState | `getSQLState()` | Usually a 5-character code per SQL standard or X/Open; may be `null`; exact meaning varies by database. |
| Vendor code | `getErrorCode()` | Integer defined by the DB/driver; may be `0` or differ across DBMSs. |
| Java cause | `getCause()` | Standard `Throwable` link, used for stack traces and wrapped exceptions. |
| Next SQLException | `getNextException()` | A **separate** JDBC chain, not synonymous with `getCause()`; may contain subsequent SQL errors or a more specific underlying error. |
| Suppressed errors | `getSuppressed()` | For example, resource-closing errors in `try-with-resources`; not identical to `getNextException()`. |
| Batch results | `BatchUpdateException.getUpdateCounts()` | Counts or status codes for statements in a batch; must be interpreted per driver and transaction. |

The first two characters of `SQLState` can hint at the error category: `23` typically relates to integrity constraints; `42` typically relates to SQL syntax or resource access; `08` typically relates to connections; `40` relates to transaction rollback. However, you cannot always deduce the **exact Spring exception type** from just those two characters. For example, `23505` is usually a duplicate key, but the driver and Spring version determine the final mapping.

**Rule:** use the *Spring type* for application decisions; record *SQLState + vendor code + exception class* to find the root cause. When nested `SQLException`s exist, retain the exact caught object rather than constructing a new `SQLException` from only its message.

## 3. How Does Spring Classify SQLException?

### 3.1. The DataAccessException Hierarchy

`DataAccessException` is a `RuntimeException`, belonging to an exception hierarchy that does not depend directly on JDBC. Common classes include:

| Spring class | Typical meaning | Handling direction |
| --- | --- | --- |
| `DataIntegrityViolationException` | Data constraint violation: keys, `NOT NULL`, foreign keys... | Validate data and constraints; do not retry unconditionally. |
| `DuplicateKeyException` | A specific case of `DataIntegrityViolationException`: unique-key conflict | Handle duplicate-data rules; prefer catching the parent class for multi-DB compatibility. |
| `BadSqlGrammarException` | Invalid SQL syntax, wrong table/column name... | Fix the SQL or schema; do not auto-retry. |
| `CannotAcquireLockException` | Unable to acquire lock or equivalent concurrency error per translation | May consider retrying the **entire transaction**, depending on the situation. |
| `QueryTimeoutException` | Query exceeded allowed time when recognized by the driver | Investigate slowness, adjust timeout/load; retry only with controls. |
| `DataAccessResourceFailureException` | Serious failure in data resources/connectivity | Check DB, network, pool, and blast radius. |
| `UncategorizedSQLException` | Could not be classified into a specific group | Still retains `SQLException`, related SQL, and task; inspect code/driver. |

Class names in the table are **classification examples**, not a fixed lookup table for every DBMS. `DuplicateKeyException` extends `DataIntegrityViolationException`; catching the parent class is generally more stable when changing vendors. `TransientDataAccessException` indicates an error that might succeed if retried *under appropriate conditions*, which does not mean you may retry non-idempotent operations.

Beyond JDBC, Spring can also produce `DataAccessException` from other data access technologies. Therefore, a `DataAccessException` **does not always have an `SQLException` deep inside its cause**.

### 3.2. SQLExceptionTranslator and the Default Choice

`org.springframework.jdbc.support.SQLExceptionTranslator` has the signature:

```java
DataAccessException translate(String task, String sql, SQLException ex);
```

In this API, the return value may be `null` if the translator finds no match. `task` is a description of the operation; `sql` is the SQL statement if known (may be `null`); `ex` must be the original JDBC error. Once translated, the returned Spring exception **must preserve `ex` as its cause**.

In Spring Framework **6.x**:

1. `JdbcTemplate` catches `SQLException` during JDBC execution and uses a translator to convert it into a `DataAccessException`.
2. Since Spring 6.0, the usual JDBC default is `SQLExceptionSubclassTranslator`: it inspects JDBC 4 subclasses (such as `SQLIntegrityConstraintViolationException`), then falls back to `SQLStateSQLExceptionTranslator` if needed.
3. `SQLStateSQLExceptionTranslator` relies on `SQLState` and common cases. This is a fallback mechanism that does not require checking the vendor name.
4. `SQLErrorCodeSQLExceptionTranslator` relies on database error-code tables in `sql-error-codes.xml`, determined via `DataSource` metadata; it can classify more granularly. With an application-provided `sql-error-codes.xml` file at the **root of the classpath**, the error-code strategy may be selected by default.
5. If none of the translators recognize the error, `JdbcTemplate` can throw `UncategorizedSQLException`, **still containing the original SQLException**. Failure to identify the category does not mean the error may be dropped.

These details describe the 6.x branch; when using Spring 7.x or another framework configuration, verify the API and actual behavior in the deployed version. If using Spring Boot, prefer letting Boot's dependency management control the Spring version.

### 3.3. Why Is the Initial SQLException Still Needed?

`DataAccessException.getCause()` directly returns the exception stored as its cause. Spring also provides:

- `getRootCause()`: finds the *deepest* cause, which may return `null` if there is no nested cause.
- `getMostSpecificCause()`: the deepest cause if present, otherwise the current exception itself.
- `contains(SQLException.class)`: checks whether the cause chain contains this type.

Do not blindly cast `(SQLException) ex.getCause()` in every application layer: a service might have wrapped it in another `RuntimeException`, and data could come from a non-JDBC source. When certain JDBC is used, walk `Throwable.getCause()` or use dedicated accessors like `UncategorizedSQLException.getSQLException()`; when reading code details, check `instanceof SQLException` first.

## 4. Runnable Example: Spring JDBC + H2 Preserving Real SQLException

This example uses **Java 17**, **Spring JDBC 6.2.19**, and **H2 2.5.252**. We create a table with a `UNIQUE` constraint, intentionally insert a duplicate email, and catch `DataIntegrityViolationException`. Spring performs the exception translation; the program proves that the original `SQLException` remains accessible. The example also demonstrates a custom translator that preserves the **exact cause instance**, not merely the same message.

Project structure:

```text

├── pom.xml
└── src/main/java/SqlExceptionDemo.java
```

### 4.2. src/main/java/SqlExceptionDemo.java

```java
import java.sql.SQLException;
import java.sql.SQLSyntaxErrorException;

import org.springframework.dao.DataAccessException;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.BadSqlGrammarException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.jdbc.support.SQLExceptionSubclassTranslator;

public final class SqlExceptionDemo {

    public static void main(String[] args) {
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:sqlerrors;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");

        JdbcTemplate jdbc = new JdbcTemplate(dataSource);

        jdbc.execute("CREATE TABLE person (" +
                "id BIGINT PRIMARY KEY, " +
                "email VARCHAR(120) NOT NULL UNIQUE)");

        jdbc.update("INSERT INTO person (id, email) VALUES (?, ?)",
                1L, "same@example.test");

        try {
            // Violates UNIQUE(email); H2 throws SQLException with SQLState 23505.
            jdbc.update("INSERT INTO person (id, email) VALUES (?, ?)",
                    2L, "same@example.test");
            throw new AssertionError("Expected a duplicate-key failure");
        } catch (DataIntegrityViolationException ex) {
            SQLException sqlCause = firstSqlCause(ex);
            if (sqlCause == null) {
                throw new IllegalStateException(
                        "Original SQLException is missing", ex);
            }

            System.out.println("Caught integrity violation: true");
            System.out.println("SQLException preserved: " +
                    ex.contains(SQLException.class));
            System.out.println("SQLState: " + sqlCause.getSQLState());
            System.out.println("Vendor code: " + sqlCause.getErrorCode());
        }

        // Custom rule: simulated vendor code 70001.
        // All other errors continue to be classified by Spring.
        SQLExceptionSubclassTranslator translator =
                new SQLExceptionSubclassTranslator();

        translator.setCustomTranslator((task, sql, original) -> {
            if (original.getErrorCode() == 70001) {
                return new DataIntegrityViolationException(
                        "Custom integrity rule failed during " + task,
                        original); // IMPORTANT: keep the exact original object
            }
            return null; // delegate handling back to the default translator
        });

        SQLException original =
                new SQLException("Synthetic database rule", "HY000", 70001);
        DataAccessException custom =
                translator.translate("save person", null, original);

        System.out.println("Custom translation: " +
                (custom instanceof DataIntegrityViolationException));
        System.out.println("Same original cause: " +
                (custom != null && custom.getCause() == original));

        SQLException syntaxError =
                new SQLSyntaxErrorException("Invalid SQL", "42000", 0);
        DataAccessException fallback =
                translator.translate("query", "SELECT bad", syntaxError);

        System.out.println("Fallback recognized: " +
                (fallback instanceof BadSqlGrammarException));
    }

    private static SQLException firstSqlCause(Throwable failure) {
        for (Throwable current = failure;
             current != null;
             current = current.getCause()) {
            if (current instanceof SQLException sql) {
                return sql;
            }
        }
        return null;
    }
}
```

In the directory containing `pom.xml`, run (requires JDK 17+ and Maven; on the first run Maven must download dependencies):

```bash
mvn -q compile exec:java
```

Expected output with the exact declared dependencies:

```text
Caught integrity violation: true
SQLException preserved: true
SQLState: 23505
Vendor code: 23505
Custom translation: true
Same original cause: true
Fallback recognized: true
```

**Reading the output:**

1. `JdbcTemplate.update(...)` throws an exception of type `DataIntegrityViolationException` (which may be the `DuplicateKeyException` subclass); the code catches only the parent class to avoid depending on the granularity of the translation.
2. `ex.contains(SQLException.class)` proves the original JDBC error remains in the `cause chain`; `firstSqlCause(...)` lets you read `SQLState` and `vendorCode` without guessing nesting depth.
3. In the custom section, `original` is passed as the **exact object** into the `DataIntegrityViolationException(message, original)` constructor; the reference comparison `custom.getCause() == original` proves the initial error was not lost.
4. `SQLSyntaxErrorException` does not match the custom code; returning `null` lets the base translator map it to `BadSqlGrammarException`. Returning an arbitrary exception instead of `null` would block the fallback.
5. Do not search the exception's `getMessage()` for the word "duplicate"; messages from H2 and other versions can change.

> This example executes real SQL on in-memory H2, unlike manually instantiating `new SQLException(...)` and claiming JDBC ran. Only the synthetic portion tests the database-independent **custom translation** path. `DriverManagerDataSource` is suitable for an example; in a real application, use a connection pool and proper transaction configuration.

## 5. Translating Errors Properly When Not Using JdbcTemplate

`JdbcTemplate` usually already performs exception translation. Only when using raw JDBC, custom callbacks, or a custom data access layer do you need to invoke a translator directly:

```java
// Illustrative code inside an existing method:
// task/sql provide context, caught is the just-caught SQLException.
SQLExceptionTranslator translator = new SQLExceptionSubclassTranslator();

DataAccessException mapped =
        translator.translate("update customer", sql, caught);

throw mapped != null
        ? mapped
        : new UncategorizedSQLException("update customer", sql, caught);
```

Required imports: `org.springframework.jdbc.support.SQLExceptionTranslator`, `SQLExceptionSubclassTranslator`, `org.springframework.dao.DataAccessException`, `org.springframework.jdbc.UncategorizedSQLException`. This is an **integration fragment**, not a standalone class: the variables `sql` and `caught` must be declared at the JDBC handling site.

**Why is the `mapped == null` branch needed?** The `SQLExceptionTranslator.translate(...)` contract allows returning `null` when no mapping is found. You must not treat `null` as "no error" and continue writing data; `UncategorizedSQLException` indicates an uncategorized error and retains the original cause via its constructor.

**Note on context:** `task` should be a short operation name, and `sql` only the relevant statement if known. Do not concatenate secrets or user data into exception messages for logging; use parameterized SQL and log only permitted fields.

### When Should You Configure a Custom Translator?

If a driver returns a custom code that the default does not recognize properly, create a custom translator and install it on the exact `JdbcTemplate` instance in use:

```java
// Configuration fragment integrated into DataSource/JdbcTemplate setup.
JdbcTemplate jdbcTemplate = new JdbcTemplate(dataSource);
SQLExceptionSubclassTranslator translator =
        new SQLExceptionSubclassTranslator();

translator.setCustomTranslator((task, sql, ex) -> {
    if (ex.getErrorCode() == 70001) {
        return new DataIntegrityViolationException(
                "Vendor integrity rule in " + task, ex);
    }
    return null;
});

jdbcTemplate.setExceptionTranslator(translator);
```

Using `setCustomTranslator(...)` on `AbstractFallbackSQLExceptionTranslator` has been available since Spring 6.1. If using `SQLErrorCodeSQLExceptionTranslator`, you can set the `DataSource` to look up codes by database name and customize the translator; you should not rely on code tables copied from a different DB. `SQLErrorCodeSQLExceptionTranslator.customTranslate(...)` in older docs has been marked deprecated since Spring 6.1, so avoid choosing it as a new extension API when `setCustomTranslator(...)` is available.

**Invariant to maintain in every implementation:** the returned Spring exception must always keep `ex` as its `cause`. A custom mapper should handle only **codes it truly understands**; for other errors, return `null` for the fallback step. Do not turn every `SQLException` into `DataIntegrityViolationException`, as that can cause retry logic, metrics, and HTTP mapping to make wrong decisions.

## 6. Why Is getRootCause() Not Enough to Diagnose All Errors?

Suppose the service layer wraps additional business context:

```java
// Illustrative fragment in a service, not a standalone application.
try {
    repository.saveCustomer(customer);
} catch (DataAccessException ex) {
    throw new CustomerWriteException(
            "Could not save customer " + customer.id(), ex);
}
```

Here `CustomerWriteException` is designed with a constructor taking `Throwable cause`; thus the entire chain:

```text
CustomerWriteException
    -> DataIntegrityViolationException
        -> SQLException (driver)
```

remains intact. But if you write:

```java
// Wrong: loses the original object, stack trace, and vendor information.
throw new CustomerWriteException(ex.getMessage());

// Right: preserves the original cause along with business context.
throw new CustomerWriteException("Could not save customer", ex);
```

then the two cases differ in diagnostic quality. A single message-only constructor may be convenient, but it **does not automatically store `ex`** as the cause.

If you only need to know whether an error originated from JDBC, you can check:

```java
// Used on a caught DataAccessException:
boolean fromJdbc = ex.contains(SQLException.class);
Throwable deepest = ex.getRootCause();        // may be null
Throwable specific = ex.getMostSpecificCause(); // non-null
```

Do not assume `deepest` is always an `SQLException`: `SQLException` itself might have a deeper `Throwable.getCause()`, or the cause may reside at another layer. `UncategorizedSQLException` provides `getSQLException()` to retrieve the directly wrapped SQLException, and `getSql()` to get the SQL statement if available. For a `DataAccessException` originating from JPA or other data access, there may be no `SQLException` at all.

One way to locate `SQLException` along the cause chain in a JDBC system is the `firstSqlCause(...)` method in the complete example. It intentionally returns `null` if not found, forcing callers to handle non-JDBC cases rather than casting and causing a `ClassCastException`.

## 7. BatchUpdateException: Multiple Errors and Multiple Results

During batch updates, the driver may throw `java.sql.BatchUpdateException`. In addition to `SQLException.getSQLState()` and `getErrorCode()` on the batch object, detailed errors may reside in the `getNextException()` chain. `BatchUpdateException.getUpdateCounts()` also reflects the status of statements the driver processed. If you only log `e.getMessage()`, you may miss **SQL errors belonging to specific batch items**.

Illustrative example of walking the JDBC chain (not a standalone program):

```java
import java.sql.SQLException;

static void inspectSqlChain(SQLException first) {
    for (SQLException current = first;
         current != null;
         current = current.getNextException()) {

        System.out.println("SQLState=" + current.getSQLState()
                + " vendor=" + current.getErrorCode()
                + " type=" + current.getClass().getSimpleName());
    }
}
```

This is the **`nextException` chain**, which is different from `Throwable.getCause()`. For full coverage, first walk the cause chain to find any `SQLException`, then read `getNextException()` elements for each relevant SQLException; production logging systems should cap the element count and avoid sensitive data so logs do not grow unbounded or become too large.

For a batch exception:

```java
// Illustration: "batch" is the just-caught BatchUpdateException.
int[] counts = batch.getUpdateCounts();
for (int i = 0; i < counts.length; i++) {
    int count = counts[i];
    if (count == java.sql.Statement.EXECUTE_FAILED) {
        // Driver indicates the statement at index i failed.
    } else if (count == java.sql.Statement.SUCCESS_NO_INFO) {
        // Succeeded, but the driver does not know the affected row count.
    } else {
        // count >= 0: affected row count reported by the driver.
    }
}
```

**Do not conclude** that all records outside `counts` were rolled back or never ran. Depending on the database, driver, and whether a transaction is active, some statements that succeeded may still require rollback. Transaction boundaries must be clearly defined. Some Spring translator versions (e.g., Spring 6.2.12+) additionally inspect `BatchUpdateException.getNextException()` for more accurate classification, but **the original cause and SQLException chain must still be preserved** for analysis.

If you need to translate a batch exception into a Spring type, set **the entire original `BatchUpdateException` object** as the cause, rather than picking one `getNextException()` and discarding the batch object containing `updateCounts`. When a custom translator returns null, let the default/fallback translator handle it.

## 8. Handling at Repository, Service, and HTTP API Layers

### Repository / DAO

- Use `JdbcTemplate` or `NamedParameterJdbcTemplate` to leverage Spring's resource management and exception translation.
- Do not catch `DataAccessException` just to wrap it into `new RuntimeException(ex.getMessage())`.
- If you need to add business context, create an exception with a `(String message, Throwable cause)` constructor and pass **the full cause**.
- Do not use English database message strings as branching conditions. Rely on the `DataAccessException` type, SQLState, or verified vendor code.

### Service and Transactions

`DataAccessException` is an unchecked exception. With standard Spring declarative transactions, an unchecked exception escaping a `@Transactional` method triggers rollback by default. If you catch the exception and return a "success" value or ignore the error, the transaction may commit depending on configuration. Therefore, if handling errors in the service, explicitly decide whether to **rethrow**, roll back, or recover.

Retry only when you determine the error is genuinely transient, the transaction has finished rolling back, and the operation can be safely re-executed. For example, lock contention handling may require retrying the **entire transaction**; a unique-key violation usually requires fixing data and should not be blindly retried.

### API

You can convert a constraint error **confirmed to be a business duplicate key** into an HTTP `409 Conflict` response; other integrity errors may require `400`, `422`, or `500` depending on the API contract. Never return `SQLState`, table names, raw SQL, or vendor messages directly in a public API. Diagnostic details can be recorded in access-controlled logs/tracing along with a `correlationId` for reconciliation.

A user-friendly response might only include a business code such as `CUSTOMER_EMAIL_ALREADY_EXISTS` and a request ID; the initial exception chain still exists in server-side logs. You do not need to modify or strip the cause to produce a safe response.

### Logging

When using a logging framework, log the **exception object** to retain the stack trace and cause chain:

```java
// Application fragment: logger is a configured SLF4J Logger.
logger.error("Save customer failed: requestId={}", requestId, ex);
```

Avoid:

```java
// Message only; drops stack trace/cause and may contain sensitive SQL.
logger.error(ex.getMessage());
```

Do not log the same exception redundantly at every layer when it adds no value; structured logs should retain type, trace, and permitted metadata without logging raw sensitive parameters. That Spring preserves `cause` **does not** mean the application should expose cause details to end users.

## 9. Common Practical Mistakes

| Wrong practice | Problem | Right practice |
| --- | --- | --- |
| `throw new RuntimeException(e.getMessage())` | Loses `SQLException`, stack trace, and chain | `throw new RuntimeException("context", e)` |
| `throw new DataIntegrityViolationException("error")` | Drops original cause; easily masks wrong category | Use constructor `(message, SQLException)` when truly in that group |
| `catch (SQLException e)` around `JdbcTemplate.update` | The API already translated it into `DataAccessException`, so this catch does not handle the expected error path | Catch the appropriate Spring type |
| `((SQLException) dae.getCause()).getSQLState()` without checking | Cause may not be a direct SQLException | Use `instanceof` or walk the cause chain |
| Classifying errors via `message.contains("duplicate")` | Messages vary by driver, locale, and version | Use Spring class / SQLState / vendor code |
| Custom translator always returns one error type | Every failure is misclassified, fallback never runs | Map only confirmed cases; otherwise `return null` |
| Translator returns `null` and error is ignored | Failure is unreported and work may continue erroneously | Create `UncategorizedSQLException` or let `JdbcTemplate` handle it |
| Inspecting only `getCause()` on `BatchUpdateException` | Can miss `getNextException()` and update counts | Keep the original batch object; inspect the JDBC chain separately |
| Swallowing exceptions inside `@Transactional` | May commit instead of rolling back | Rethrow or mark rollback-only by design |
| Putting `SQLException.getMessage()` in HTTP responses | Leaks system details or data | Return a business error code; log restricted details on server |
| Retrying every `TransientDataAccessException` right in the DAO | May retry individual statements after a failed transaction | Recover/roll back first, then retry at the proper business scope |

## 10. Testing Translation and Cause Preservation

**Testing translators with simulated errors:**

1. Create an `SQLException` with a known `SQLState` and `vendorCode`.
2. Call the translator with a clear task/sql; assert the expected `DataAccessException` type.
3. For custom mappers, use `assertSame(original, translated.getCause())` to prove the **exact original** SQLException object is preserved.
4. For codes not in the custom mapping, verify fallback still runs (or returns `null` when no translator matches).
5. Create an `SQLException` with `setNextException(...)` and ensure the wrapped exception still allows reading that chain.
6. Create a `BatchUpdateException` and verify `getUpdateCounts()`, detailed errors, and transaction rollback behavior are preserved.

**Integration testing with a real database:**

- Trigger one `UNIQUE` error and one `FOREIGN KEY` error; the Spring exception class may match at the parent level, while SQLState/vendor code differ.
- Trigger an SQL syntax error and a connection failure to verify how the translator/driver classifies them.
- Cross-check the actual Spring and driver versions, especially when changing databases.
- Create a multi-operation transaction: trigger an error mid-way and verify actual rollback, not just the exception class.
- Inspect logs to confirm stack traces/causes are present while sensitive data does not appear in HTTP responses.

**Production readiness checklist:**

- [ ] Use the right `DataAccessException`/subclasses to accurately represent error categories.
- [ ] When creating wrappers, constructors must accept and store `Throwable cause`.
- [ ] Do not depend on message strings; use verified exception types/error codes.
- [ ] When JDBC diagnostics are needed, safely traverse the cause chain for `SQLException`.
- [ ] For batches, preserve the full `BatchUpdateException`, `nextException`, and update counts.
- [ ] Custom translators handle recognized codes and return `null` for remaining errors.
- [ ] Have a plan for uncategorized errors (`UncategorizedSQLException`).
- [ ] Transaction/rollback/retry boundaries are explicit, with no swallowed exceptions.
- [ ] Logging includes stack traces and correlation IDs; public APIs never expose SQL/secrets.

**Remember:** translated exceptions are valuable because **they let the business layer understand the right kind of failure**. Preserved original exceptions are valuable because **they let you pinpoint the exact technical root cause**. Constructing `DataAccessException` with the original `SQLException` as its cause, combined with proper traversal of `cause` and `nextException`, preserves both capabilities.
