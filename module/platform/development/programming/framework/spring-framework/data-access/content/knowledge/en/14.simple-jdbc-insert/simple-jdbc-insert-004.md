# SimpleJdbcInsert: Passing Values with Map or SqlParameterSource

`SimpleJdbcInsert` is a **Spring JDBC** utility that builds and executes `INSERT` statements based on a table name, column configuration, and metadata provided by the JDBC driver. Instead of manually aligning `?` placeholders and calling `PreparedStatement.setXxx(...)`, developers pass input data to `SimpleJdbcInsert` using one of two primary forms:

- **`Map<String, ?>`**: each key is a column name to supply, and each value is the Java value to write.
- **`SqlParameterSource`**: an interface representing name–value pairs that can also supply the **SQL type** for each parameter. Two common implementations are `MapSqlParameterSource` and `BeanPropertySqlParameterSource`.

Both forms use the **same insert configuration**, the same JDBC connection, and the same parameter-binding mechanism; they differ in how values and type metadata are obtained. Choosing the right one helps prevent column mismatches, handle `NULL` cleanly, and keep DAOs maintainable.

## 1. How SimpleJdbcInsert Processes Parameters

Suppose we have an order table:

~~~sql
-- DDL used in the H2 2.x hands-on example below.
CREATE TABLE purchase_order (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL,
    amount_cents BIGINT NOT NULL,
    note         VARCHAR(255),
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
~~~

In a Spring application that already has a `DataSource`:

~~~java
SimpleJdbcInsert insertOrder = new SimpleJdbcInsert(dataSource)
        .withTableName("purchase_order")
        .usingColumns("customer_name", "amount_cents", "note")
        .usingGeneratedKeyColumns("id");
~~~

This is a **configuration snippet inside a repository**, assuming `dataSource` is already available; section 5 provides a complete runnable program. Role of each call:

1. `withTableName("purchase_order")` selects the target table.
2. `usingColumns(...)` defines the exact columns included in the `INSERT` and their order. This example excludes `id` and `created_at` from the values sent to the database.
3. `usingGeneratedKeyColumns("id")` requests retrieving the generated key column after the insert, if supported by the database and JDBC driver.
4. `execute(...)` or `executeAndReturnKey(...)` accepts a `Map` **or** `SqlParameterSource`, and Spring matches parameter names against the column list and binds each value using JDBC parameter binding.

The actual SQL Spring builds looks conceptually like:

~~~sql
INSERT INTO purchase_order (customer_name, amount_cents, note)
VALUES (?, ?, ?);
~~~

The three `?` placeholders receive values from the corresponding three keys/columns. **The insertion order of keys in a `HashMap` does not determine the SQL column order**: Spring uses the configured/metadata column list to match by name. The SQL shown here illustrates the fixed configuration, not a guarantee of how every JDBC driver quotes identifiers.

`SimpleJdbcInsert` leverages column metadata when needed; for explicit control, use `usingColumns(...)` and test against the target DB. It **does not require** writing `:customer_name` syntax manually like `NamedParameterJdbcTemplate`.

## 2. Option A: Passing a `Map<String, ?>`

A simple `Map` is enough to insert standard columns:

~~~java
Map<String, Object> values = new HashMap<>();
values.put("customer_name", "An");
values.put("amount_cents", 120_000L);
values.put("note", "Morning delivery");

int affectedRows = insertOrder.execute(values);
System.out.println("inserted=" + affectedRows);
~~~

This is a **code snippet inside a repository** after creating `insertOrder` in section 1; it requires importing `java.util.Map` and `java.util.HashMap`. With a fresh database and no constraint errors, the expected output is:

~~~text
inserted=1
~~~

`execute(Map<String, ?>)` returns the **affected row count reported by the JDBC driver**, not the generated `id` key value. To retrieve the generated numeric key:

~~~java
Number generatedId = insertOrder.executeAndReturnKey(values);
long id = generatedId.longValue();
~~~

The calls `execute(...)` and `executeAndReturnKey(...)` in the two illustrations are **two separate choices**. If you run both consecutively with the same `values`, you will insert **two records**, rather than inserting one and reading the key of the previous record.

### Matching Keys to Column Names and Using Proper Value Types

With `usingColumns("customer_name", "amount_cents", "note")`, supply keys such as `"customer_name"`, `"amount_cents"`, and `"note"`. Do not assume that variations in underscores, casing, or Java types will be accepted identically across every schema and driver.

~~~java
Map<String, Object> order = new HashMap<>();
order.put("customer_name", "Binh");    // VARCHAR
order.put("amount_cents", 250_000L);   // BIGINT
order.put("note", null);               // SQL NULL, if bound properly
~~~

A `HashMap` allows `null` values. Conversely, Java's `Map.of(...)` is suited for **non-null** values and a small number of entries:

~~~java
Map<String, Object> nonNullValues = Map.of(
        "customer_name", "Chi",
        "amount_cents", 90_000L,
        "note", "Store pickup");
~~~

**Note:** `Map.of("note", null)` throws `NullPointerException` immediately when creating the map; the failure happens in Java, **before JDBC is called**. If a column can be null, use `HashMap`, `LinkedHashMap`, or `MapSqlParameterSource`.

`Map<String, ?>` is convenient when data is already in a key–value structure and the database/driver can infer parameter types. Its limitation is that a `Map` itself **does not directly supply SQL type metadata** such as `Types.VARCHAR` for a null parameter or a specialized type.

## 3. Option B: `SqlParameterSource` and `MapSqlParameterSource`

`SqlParameterSource` belongs to the `org.springframework.jdbc.core.namedparam` package. It is an **interface**; it is neither a SQL statement nor a `DataSource`/connection. The interface provides these main methods:

| Method | Meaning |
| --- | --- |
| `hasValue(String name)` | Whether a value has been supplied for that parameter name |
| `getValue(String name)` | Retrieves the Java value; may be `null` if the parameter exists with a null value |
| `getSqlType(String name)` | SQL type code, e.g., `Types.VARCHAR` or `Types.BIGINT`; defaults to `TYPE_UNKNOWN` |
| `getTypeName(String name)` | SQL type name if needed, such as a database-defined type |
| `getParameterNames()` | Lists parameter names when supported by the implementation; useful for column matching |

`MapSqlParameterSource` is the closest implementation to a `Map`, adding fluent `addValue(...)` methods and SQL type registration:

~~~java
import java.sql.Types;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;

SqlParameterSource params = new MapSqlParameterSource()
        .addValue("customer_name", "Dung", Types.VARCHAR)
        .addValue("amount_cents", 125_000L, Types.BIGINT)
        .addValue("note", null, Types.VARCHAR);

Number generatedId = insertOrder.executeAndReturnKey(params);
System.out.println("id=" + generatedId.longValue());
~~~

This snippet **depends on `insertOrder`** from section 1. `Types.VARCHAR` explicitly states that the `note` parameter should be bound as a SQL character type, even when the current value is `null`. The `addValue(name, value, sqlType)` signature fits cases where the driver struggles to infer types from `null` or specialized types.

You can also write:

~~~java
MapSqlParameterSource params = new MapSqlParameterSource()
        .addValue("customer_name", "Mai")
        .addValue("amount_cents", 50_000L)
        .addValue("note", null);

params.registerSqlType("note", Types.VARCHAR);
~~~

`registerSqlType(...)` is inherited from `AbstractSqlParameterSource`. For simple non-null values, registering the type may be unnecessary; for `null` and database-specific types like JSON/array/UUID, check the driver documentation and register the appropriate type. **Do not blindly assign `Types.VARCHAR` to every field just to avoid errors**, as binding the wrong type can cause SQL rejection or unintended value conversions.

`MapSqlParameterSource` can be initialized from an existing map:

~~~java
Map<String, Object> supplied = new HashMap<>();
supplied.put("customer_name", "Lan");
supplied.put("amount_cents", 180_000L);
supplied.put("note", null);

MapSqlParameterSource typed = new MapSqlParameterSource(supplied);
typed.registerSqlType("note", Types.VARCHAR);
insertOrder.execute(typed);
~~~

This is an **independent** insert operation; if run alongside the previous examples, each `execute` creates an additional record. `MapSqlParameterSource` is **mutable**; create a fresh instance per DAO call rather than sharing one instance and calling `addValue` concurrently across requests.

### NULL, Missing Key, and Database `DEFAULT`

The following three states are distinct:

- **Concrete value:** `note = "Note"`, Spring binds the string.
- **Parameter present, `null` value:** `note = null`, Spring binds SQL `NULL` using the parameter source/driver's type resolution.
- **Column omitted from the SQL insert:** for example, excluding `"note"` from `usingColumns(...)` on a separate `SimpleJdbcInsert` configuration. The database can then apply `DEFAULT` for the column (or use `NULL` if allowed by the table design).

**Do not equate "Map missing a key" with "omitting a column from INSERT".** If `SimpleJdbcInsert` still configures `note` as a column to bind while the input lacks `note`, Spring may bind null and/or throw an execution error depending on the situation. To let the database apply a default intentionally, configure the SQL columns so the column is **not sent**. In the illustrative DDL, `created_at` does not appear in `usingColumns`, allowing `DEFAULT CURRENT_TIMESTAMP` to take effect.

## 4. Option C: `BeanPropertySqlParameterSource` — Supplying Data from a JavaBean

When input data is already a JavaBean with getters, there is no need to copy each property into a `Map` manually. Example input object:

~~~java
public final class OrderInput {
    private final String customerName;
    private final long amountCents;
    private final String note;

    public OrderInput(String customerName, long amountCents, String note) {
        this.customerName = customerName;
        this.amountCents = amountCents;
        this.note = note;
    }

    public String getCustomerName() {
        return customerName;
    }

    public long getAmountCents() {
        return amountCents;
    }

    public String getNote() {
        return note;
    }
}
~~~

Save as `OrderInput.java` if used standalone; this class is valid in Java 17+. Once `insertOrder` is configured:

~~~java
OrderInput input = new OrderInput("Ha", 300_000L, "Send invoice");

SqlParameterSource beanParams =
        new BeanPropertySqlParameterSource(input);

long id = insertOrder.executeAndReturnKey(beanParams).longValue();
~~~

`BeanPropertySqlParameterSource` reads values from **JavaBean properties with readable getters**, rather than arbitrarily inspecting every private field. With `SimpleJdbcInsert`, Spring supports matching column names like `customer_name`/`amount_cents` with Java property names like `customerName`/`amountCents` according to its mapping rules. That is why the JavaBean example uses camelCase while the table uses snake_case.

Keep in mind:

1. **Names must genuinely match per Spring's rules**; `BeanPropertySqlParameterSource` is not an arbitrary ORM mapper and does not read JPA annotations as a column-renaming contract.
2. The bean class must have readable getters. A class with only private fields and no matching getters does not meet the JavaBean requirement of this example.
3. This source can infer some SQL types from the Java property types, but inference is no substitute for testing against database-specific types.
4. If DB names and property names differ significantly, write a `MapSqlParameterSource` with exact keys or implement a custom `SqlParameterSource`; do not rely on unpredictable implicit mapping.
5. A property with a `null` value differs from a missing property. A bean lacking a getter for an insert column may cause Spring to bind missing/`NULL` or trigger data errors; test table constraints.

Spring supports standard JavaBeans across many versions. Some newer versions also support records or other property sources; for projects requiring compatibility across Spring versions, stick to mapping approaches verified on the actual version in use.

## 5. Runnable Java 17+ Example: One Insert, Three Parameter Sources

This example uses **Spring JDBC 6.1.14**, **H2 2.2.224**, and Gradle, without requiring Spring Boot. The goal is to compare three data-passing calls on the same table:

- `Map<String, Object>`, including `note = null`;
- `MapSqlParameterSource` with explicitly declared SQL types;
- `BeanPropertySqlParameterSource` from a JavaBean with getters.

Create the directory structure:

~~~text
simple-insert-demo/
├── build.gradle
└── src/
    └── main/
        └── java/
            └── demo/
                └── SimpleJdbcInsertInputsDemo.java
~~~

File `build.gradle` (Groovy DSL):

~~~groovy
plugins {
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-jdbc:6.1.14'
    runtimeOnly 'com.h2database:h2:2.2.224'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

application {
    mainClass = 'demo.SimpleJdbcInsertInputsDemo'
}
~~~

File `src/main/java/demo/SimpleJdbcInsertInputsDemo.java`:

~~~java
package demo;

import java.sql.Types;
import java.util.HashMap;
import java.util.Map;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.BeanPropertySqlParameterSource;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.datasource.DriverManagerDataSource;

public final class SimpleJdbcInsertInputsDemo {
    public static void main(String[] args) {
        DriverManagerDataSource dataSource =
                new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl(
                "jdbc:h2:mem:input_demo;DB_CLOSE_DELAY=-1");
        dataSource.setUsername("sa");
        dataSource.setPassword("");

        JdbcTemplate jdbc = new JdbcTemplate(dataSource);
        jdbc.execute("""
                CREATE TABLE purchase_order (
                    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                    customer_name VARCHAR(100) NOT NULL,
                    amount_cents BIGINT NOT NULL,
                    note VARCHAR(255),
                    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
                )
                """);

        SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
                .withTableName("purchase_order")
                .usingColumns("customer_name", "amount_cents", "note")
                .usingGeneratedKeyColumns("id");

        // 1) Map: HashMap allows null values.
        Map<String, Object> byMap = new HashMap<>();
        byMap.put("customer_name", "An");
        byMap.put("amount_cents", 120_000L);
        byMap.put("note", null);
        long mapId = insert.executeAndReturnKey(byMap).longValue();

        // 2) SqlParameterSource: explicitly declare SQL types as well.
        SqlParameterSource bySource = new MapSqlParameterSource()
                .addValue("customer_name", "Binh", Types.VARCHAR)
                .addValue("amount_cents", 250_000L, Types.BIGINT)
                .addValue("note", null, Types.VARCHAR);
        long sourceId = insert.executeAndReturnKey(bySource).longValue();

        // 3) BeanPropertySqlParameterSource: read values from getters.
        OrderInput orderInput =
                new OrderInput("Chi", 90_000L, "Counter pickup");
        SqlParameterSource byBean =
                new BeanPropertySqlParameterSource(orderInput);
        long beanId = insert.executeAndReturnKey(byBean).longValue();

        Long rows = jdbc.queryForObject(
                "SELECT COUNT(*) FROM purchase_order", Long.class);
        System.out.printf(
                "map=%d, source=%d, bean=%d, rows=%d%n",
                mapId, sourceId, beanId, rows);
    }

    // JavaBean class supporting camelCase -> DB column name mapping.
    public static final class OrderInput {
        private final String customerName;
        private final long amountCents;
        private final String note;

        public OrderInput(
                String customerName, long amountCents, String note) {
            this.customerName = customerName;
            this.amountCents = amountCents;
            this.note = note;
        }

        public String getCustomerName() {
            return customerName;
        }

        public long getAmountCents() {
            return amountCents;
        }

        public String getNote() {
            return note;
        }
    }
}
~~~

Run in the directory containing `build.gradle` with Gradle installed:

~~~bash
gradle run
~~~

If the project has the Gradle Wrapper, you can use `./gradlew run` (Linux/macOS) or `gradlew.bat run` (Windows). Gradle downloads dependencies if not already cached. **Stdout line from the program** with a fresh H2 database:

~~~text
map=1, source=2, bean=3, rows=3
~~~

Gradle also prints its own build logs. The numbers `1`, `2`, `3` are the result of a **fresh H2 table in this run**; production applications must never assume specific values or continuity of generated keys. All three insert calls share the same `SimpleJdbcInsert` configuration, changing only the **parameter container type**. `note = null` in the first two calls; the third reads `note` from the bean getter.

**Why does the code work?** `DriverManagerDataSource` supplies the JDBC connection, `JdbcTemplate` creates the table in the in-memory H2 database, and `SimpleJdbcInsert` builds the SQL and matches column names with the parameter source. The `spring-jdbc` dependency pulls in the required Spring libraries; the H2 driver is loaded at runtime. This example is for learning purposes; do not use `DriverManagerDataSource` as a production connection pool.

## 6. Name and Column Matching Rules — More Important Than Choosing the Parameter Container Type

`SimpleJdbcInsert` does not "dump" every key in the map into the database. It determines **which columns to insert** (from `usingColumns` or metadata) and then pulls matching values by name from the parameter source.

| Scenario | Practical Effect |
| --- | --- |
| Configured `usingColumns("customer_name")`, key `customer_name` present | The value is bound to the corresponding parameter position |
| `Map` has key `unused_field` not in the column list | Do not expect this column to be added to the SQL automatically |
| Insert configuration includes `amount_cents` but input omits the value | Do not assume it defaults to 0; it may bind `NULL` or fail depending on parameter resolution and DB constraints |
| Configuration excludes `created_at` | Column is omitted from `INSERT`; the DB can apply `DEFAULT CURRENT_TIMESTAMP` |
| Bean has getter `getCustomerName()`, column is `customer_name` | Supported by Spring's property-name matching rules in `SimpleJdbcInsert` |
| Map has `customerName` instead of `customer_name` | Do not treat implicit renaming as an arbitrary contract; exact column keys are safer and clearer |

For tables with special column names, custom schemas, or quoted/case-sensitive identifiers, you may need `withSchemaName(...)`/table name configuration and DB-appropriate quoting. Inspect the generated SQL and run integration tests rather than guessing just because a JavaBean has a similarly named property.

### Do Not Confuse Column Names with `NamedParameterJdbcTemplate` Placeholders

The following two calls serve **different roles**:

~~~java
// SimpleJdbcInsert generates SQL based on configured columns.
insertOrder.execute(Map.of(
        "customer_name", "An",
        "amount_cents", 100L,
        "note", "Note"));

// NamedParameterJdbcTemplate requires explicit SQL with :param.
// This is an illustrative example inside a DAO with a namedJdbc field.
namedJdbc.update(
        "INSERT INTO purchase_order "
        + "(customer_name, amount_cents, note) "
        + "VALUES (:name, :amount, :description)",
        Map.of("name", "An", "amount", 100L,
               "description", "Note"));
~~~

The `namedJdbc` snippet assumes a `NamedParameterJdbcTemplate` has already been created; the two statements illustrate **two separate inserts**, so do not run both consecutively when you only want one record. With `NamedParameterJdbcTemplate`, keys must match placeholders such as `:name`; with `SimpleJdbcInsert`, keys normally match the insert column names recognized by Spring. Both use parameter binding rather than concatenating user values directly into SQL strings.

## 7. Choosing the Right Execution Overload

`SimpleJdbcInsertOperations` declares overloads accepting `Map<String, ?>` and `SqlParameterSource`:

| Need | Call with `Map` | Call with `SqlParameterSource` |
| --- | --- | --- |
| Insert and get affected row count | `execute(map)` | `execute(source)` |
| Insert and get **a single numeric generated key** | `executeAndReturnKey(map)` | `executeAndReturnKey(source)` |
| Insert and get general generated keys | `executeAndReturnKeyHolder(map)` | `executeAndReturnKeyHolder(source)` |
| Insert multiple records | `executeBatch(map1, map2, ...)` | `executeBatch(source1, source2, ...)` |

`execute(...)` returns `int`; `executeAndReturnKey(...)` returns `Number`; `executeAndReturnKeyHolder(...)` returns `KeyHolder`, which is useful for multiple key columns or non-numeric key values. `executeBatch(...)` returns `int[]` of update counts; do not assume this array is a list of generated IDs.

Example using the same configuration with two calling styles:

~~~java
Map<String, Object> map = new HashMap<>();
map.put("customer_name", "Quan");
map.put("amount_cents", 10_000L);
map.put("note", null);

SqlParameterSource source = new MapSqlParameterSource()
        .addValue("customer_name", "Quan")
        .addValue("amount_cents", 10_000L)
        .addValue("note", null, Types.VARCHAR);

// Choose ONE of the two options, do not call both for a single order:
int countByMap = insertOrder.execute(map);
// or:
// int countBySource = insertOrder.execute(source);
~~~

If using `executeAndReturnKey(...)`, you must configure `usingGeneratedKeyColumns(...)` and verify the driver returns numeric keys as expected. Choosing `Map` vs. `SqlParameterSource` **does not fix** a JDBC driver that lacks generated-key retrieval support.

## 8. Handling SQL Types, NULL, and Special Types

For `String`, `long`/`Long`, `int`/`Integer`, and simple fields, Spring/JDBC usually infers a reasonable type from Java and metadata. However, some drivers require explicit type information, especially when values are `null` or the database uses vendor-specific types.

Example of a `DECIMAL(12, 2)` amount column in **another table**:

~~~java
import java.math.BigDecimal;
import java.sql.Types;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;

MapSqlParameterSource params = new MapSqlParameterSource()
        .addValue("customer_name", "Nga", Types.VARCHAR)
        .addValue("amount", new BigDecimal("149.90"), Types.DECIMAL)
        .addValue("description", null, Types.VARCHAR);
~~~

This is a **parameter-type illustration snippet**, not executable against the `purchase_order` table in the H2 example because that table uses `amount_cents` and `note`. Adjust SQL/schema accordingly before using. For monetary amounts, prefer `BigDecimal` for decimal numbers over `double` whenever precision matters.

Some guiding principles:

- For SQL `VARCHAR`/`TEXT`, a Java `String` is appropriate; when binding `null`, try `Types.VARCHAR` if the driver requires it.
- For `BIGINT`, use `Long`/`long` matching the value range; avoid careless casting or overflow.
- For `TIMESTAMP`, `DATE`, `UUID`, JSON, or arrays, cross-check the Java types supported by the driver and the actual SQL type; not every driver binds these the same way.
- `SqlParameterSource.getSqlType(name)` may return `TYPE_UNKNOWN`. In that case Spring/the driver still needs to infer the type; do not interpret it as a valid SQL type value.
- `registerTypeName(...)` is only for when the database/driver needs a **specific SQL type name**; do not add arbitrary type names.
- Nullability is a schema rule. `MapSqlParameterSource` lets you bind `NULL` cleanly, but **cannot make a `NOT NULL` column accept null**.

## 9. Separating Insert Configuration from Per-Call Data

`SimpleJdbcInsert` is normally **configured once when initializing a DAO** and reused for many executions. Each call's input data is a fresh object:

~~~java
import javax.sql.DataSource;
import java.sql.Types;
import java.util.Map;

import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;

public final class PurchaseOrderDao {
    private final SimpleJdbcInsert insertOrder;

    public PurchaseOrderDao(DataSource dataSource) {
        this.insertOrder = new SimpleJdbcInsert(dataSource)
                .withTableName("purchase_order")
                .usingColumns("customer_name", "amount_cents", "note")
                .usingGeneratedKeyColumns("id");
    }

    public long insertWithMap(String name, long cents, String note) {
        Map<String, Object> map = new java.util.HashMap<>();
        map.put("customer_name", name);
        map.put("amount_cents", cents);
        map.put("note", note);
        return insertOrder.executeAndReturnKey(map).longValue();
    }

    public long insertWithTypedSource(String name, long cents, String note) {
        MapSqlParameterSource source = new MapSqlParameterSource()
                .addValue("customer_name", name, Types.VARCHAR)
                .addValue("amount_cents", cents, Types.BIGINT)
                .addValue("note", note, Types.VARCHAR);
        return insertOrder.executeAndReturnKey(source).longValue();
    }
}
~~~

Save as `PurchaseOrderDao.java` in an appropriate package and configure `DataSource`, tables, and dependencies as in section 5. Each method here performs **one insert**; they are **two alternative calling styles** to accomplish the same task. Returning `long` assumes the generated key fits within the `long` range.

Do not alter `withTableName`/`usingColumns` on the same instance while serving requests: finish configuration before the first execution and reuse the configured `SimpleJdbcInsert`. Conversely, `MapSqlParameterSource` is a **mutable** value source: create a dedicated instance per call, especially in multi-threaded systems.

## 10. Common Errors and How to Diagnose Them

| Symptom | Common Reason | How to Check / Fix |
| --- | --- | --- |
| `Map.of(...)` throws `NullPointerException` | A key or value is `null` | Use `HashMap` or `MapSqlParameterSource`, validate values before calling |
| `NOT NULL constraint violated` | Missing value, `null` passed, or wrong column key | Cross-check `usingColumns`, keys/source, DDL, and data |
| `BadSqlGrammarException` | Wrong table/column name, schema/quoting issue, or metadata mismatch | Check the actual SQL, identifier names, and schema |
| `DataAccessException` when binding values | Java type incompatible with SQL type, driver error, or constraint | Inspect root cause SQLState/vendor code, register the proper SQL type |
| Bean fails to supply values | Missing getter, property does not match DB name, or incompatible getter type | Check `hasValue`/`getValue`, snake_case–camelCase rules, or use an explicit source |
| Default column does not receive its default | Column is still in the insert list and receives `NULL` | Exclude the column from the SQL insert if the database should apply its default |
| `execute(...)` returns `1` but there is no `id` | `execute` returns row count, not a generated key API | Use `executeAndReturnKey` and configure generated key column |
| Generated key retrieval fails | Driver/DB does not return keys as requested | Check `usingGeneratedKeyColumns` and driver generated-keys support |

When diagnosing issues, log table/column names and parameter types **without sensitive data**. Avoid directly logging customer names, notes, or payloads containing personal information. Never turn input data into table/column names via `withTableName`/`usingColumns`: `Map`/`SqlParameterSource` parameters only bind **values**, not SQL identifiers.

### Distinguishing Java, Spring, and Database Errors

- Creating `Map.of` with `null` is a **Java** API error.
- Wrong column lists, `SimpleJdbcInsert` configuration errors, or mismatches between properties and column names are **Spring JDBC / binding-layer** issues.
- `NOT NULL`, foreign key, unique constraint violations, incompatible column types, or unsupported operations are errors returned by the **database/driver**, usually translated by Spring into the appropriate `DataAccessException`.

Using parameter binding avoids literal concatenation errors and improves data safety, but does not replace input validation, constraint checks, or transactions.

## 11. Testing and Self-Practice Exercises

Integration tests should verify both **input values and actual stored data**, not just assert that `execute(...) == 1`.

1. **Map with all keys:** insert a record, read it back by `id`, and verify `customer_name`, `amount_cents`, and `note` match.
2. **Null values:** pass `note = null` via `HashMap`, then via `MapSqlParameterSource` with `Types.VARCHAR`; verify the database stores SQL `NULL`.
3. **JavaBean:** use `BeanPropertySqlParameterSource` with `customerName`/`amountCents` and verify Spring maps them to snake_case columns.
4. **Default column:** insert with a `usingColumns` configuration omitting `created_at` and verify `created_at` is populated by the database.
5. **Missing key:** omit `amount_cents` (a `NOT NULL` column), observe the exception/null handling per DB; fix with validation and complete input.
6. **Extra key:** include `unknown_field` in the Map while keeping a fixed `usingColumns` list; do not assume it becomes a SQL column.
7. **Real driver:** repeat the main cases on the target deployment DB and driver, especially when using `UUID`, JSON, or temporal types.

## 12. Choosing `Map` or `SqlParameterSource`?

| Option | When to Use | Things to Remember |
| --- | --- | --- |
| `Map<String, ?>` | Few columns, simple data, keys already match column names, driver infers types | `Map.of` rejects `null`; keys must be verified |
| `MapSqlParameterSource` | Chaining `addValue`, explicit SQL types needed, nullable/special types | Mutable object; create a new instance per operation |
| `BeanPropertySqlParameterSource` | Input is a JavaBean with matching getters, want to avoid manual mapping | Relies on property/column naming rules; test the mapping |
| Custom `SqlParameterSource` | Need custom parameter-resolution rules not covered by the two implementations above | Only implement when truly required, as it adds complexity |

**Rule of thumb:** use `Map` for simple inserts; use `MapSqlParameterSource` when you want explicit SQL types or null handling; use `BeanPropertySqlParameterSource` when you already have a JavaBean with getters and schema-compatible names. Regardless of the choice, the `SimpleJdbcInsert` configuration and database constraints determine the SQL, target columns, and whether the insert succeeds.
