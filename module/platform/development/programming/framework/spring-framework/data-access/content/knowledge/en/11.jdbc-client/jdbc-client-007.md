# Running update() and Retrieving Generated Keys by API Version — Spring JdbcClient

In Spring JDBC, **JdbcClient.update()** executes an INSERT, UPDATE, or DELETE statement and **returns the affected row count** (`int`). When inserting into a table with a database-generated ID column, that number **is not the new key**. To collect generated keys, Spring Framework 6.1+ provides the **update(KeyHolder)** and **update(KeyHolder, String... keyColumnNames)** overloads; older Spring versions use **JdbcTemplate**, **NamedParameterJdbcTemplate**, or **SimpleJdbcInsert**.

This lesson belongs to the **JdbcClient** group in the **Spring Framework - data-access** module. It focuses on choosing the API by Spring version, distinguishing affected row counts from generated IDs, using **GeneratedKeyHolder** properly, handling drivers that do not return keys, PostgreSQL's **RETURNING** syntax, transactions, and testing with a Java 17+ example.

## 1. Two Different Results on INSERT

Suppose a table has a database-generated ID:

~~~sql
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(80) NOT NULL UNIQUE
);
~~~

H2 supports the syntax above; PostgreSQL has similar identity syntax. An INSERT:

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
~~~

can provide two pieces of information:

| Information | Example | Meaning |
| --- | --- | --- |
| **Affected row count** | 1 | INSERT affected one row |
| **Generated key** | 42 | ID assigned by the database to the new row |
| **SQL RETURNING result** | One row containing id=42 | Data returned by the DB when the statement uses RETURNING |
| **Transaction commit status** | Unknown yet | INSERT may not yet be committed when the key is received |

Look at a JdbcClient example:

~~~java
int rows = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (:name)")
    .param("name", "Lan")
    .update();
~~~

**rows == 1 does not mean the newly generated ID is 1.** When a sequence has already created the 1000th row, `update()` still returns 1, while the ID is 1000 or another value. Returning `int` follows JDBC **executeUpdate()** semantics, not a key-retrieval mechanism.

A dangerous mistake:

~~~java
// WRONG: newId is actually the affected row count.
long newId = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Lan")
    .update();
~~~

Java widens `int` to `long` implicitly, so the snippet above **compiles** yet `newId` is the **row count**, not the primary key. A unit test inserting only the first row with ID 1 can accidentally pass; over time in real runs it will use the wrong ID.

## 2. Using update() for Write Statements

`JdbcClient.StatementSpec.update()` is not only for the SQL UPDATE keyword; it is commonly used for INSERT, UPDATE, and DELETE.

~~~java
// INSERT with positional parameter.
int inserted = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Minh")
    .update();

// UPDATE with named parameters.
int renamed = jdbcClient
    .sql("""
         UPDATE members
         SET display_name = :name
         WHERE id = :id
         """)
    .param("name", "Minh Anh")
    .param("id", 10L)
    .update();

// DELETE by primary key.
int deleted = jdbcClient
    .sql("DELETE FROM members WHERE id = :id")
    .param("id", 999L)
    .update();
~~~

This is an **illustrative snippet inside a repository that already has JdbcClient and the `members` table**, not a standalone class. Typical outcomes are:

- Single-row INSERT succeeds: affected = 1.
- UPDATE or DELETE with non-existent ID: affected = 0.
- UPDATE/DELETE modifying multiple rows: affected may be >1.
- SQL/constraint/connection error: Spring throws the appropriate **DataAccessException** rather than returning a special ID.

**Distinguish "0 rows" from "error".** If a repository needs to rename exactly one existing member, `affected == 0` can signal not-found. If the same method has a loose WHERE clause and `affected > 1`, that may violate the contract. Do not arbitrarily treat any `affected > 0` as "updated exactly one person".

Some DBMSs/drivers differ in whether they count "matched" vs. "changed" rows when updating a column to the same value it already holds. Measure on your actual DBMS if your application relies on that detail.

### 2.1. Parameter Binding Is Not Dynamic SQL Construction

JdbcClient supports:

~~~java
jdbcClient.sql("DELETE FROM members WHERE id = ?")
    .param(5L)
    .update();

jdbcClient.sql("DELETE FROM members WHERE id = :id")
    .param("id", 5L)
    .update();
~~~

Both bind the **ID value**. The table name `members`, column name `id`, and DELETE syntax are fixed SQL structure. Never take table/column names from a request and concatenate them directly into SQL. Parameter binding prevents SQL injection at bound value positions, but **does not automatically protect** SQL fragments concatenated from untrusted input.

## 3. API Comparison by Spring Version

**JdbcClient was introduced in Spring Framework 6.1.** The Javadoc for **Spring 6.1.8** already lists all three `update` overloads on `JdbcClient.StatementSpec`:

~~~java
int update();
int update(KeyHolder generatedKeyHolder);
int update(KeyHolder generatedKeyHolder, String... keyColumnNames);
~~~

| Framework Version | Has JdbcClient? | How to return generated keys |
| --- | --- | --- |
| Spring 5.x | **No** | JdbcTemplate, NamedParameterJdbcTemplate, SimpleJdbcInsert |
| Spring 6.0.x | **No** | Traditional JDBC APIs |
| Spring 6.1.x | **Yes** | JdbcClient.update(holder), update(holder, "id") |
| Spring 6.2.x | **Yes** | Same KeyHolder overloads; check exact version |
| Spring 7.0.x | **Yes** | Above overloads continue to exist |
| Spring 7.1 and newer releases | May include additions like `batch()` | Check exact Javadoc of your dependency before using |

**Do not mistakenly think `update(KeyHolder)` first appeared in Spring 6.2**; it has existed since the 6.1 generation of JdbcClient. Conversely, examples using JdbcClient cannot be copied verbatim into a Spring 6.0 project because **the JdbcClient class does not exist there yet**.

### 3.1. Determining the Actual Resolved spring-jdbc Version

A project may use Spring Boot for dependency management or apply overrides. Check the **`org.springframework:spring-jdbc` version**, not just the Boot version name.

Gradle with wrapper:

~~~bash
./gradlew dependencyInsight --dependency spring-jdbc --configuration runtimeClasspath
~~~

System-installed Gradle:

~~~bash
gradle dependencyInsight --dependency spring-jdbc --configuration runtimeClasspath
~~~

Maven:

~~~bash
mvn dependency:tree -Dincludes=org.springframework:spring-jdbc
~~~

These commands are for **a project with `build.gradle`/`pom.xml`**, not standalone Java programs. When upgrading major/minor versions, verify `JdbcClient.StatementSpec` signatures and driver behaviors rather than relying on unversioned snippets.

### 3.2. Do Not Guess Method Names Across Classes

| Class | API | Direct return value |
| --- | --- | --- |
| JdbcClient.StatementSpec | **update()** | int affected |
| JdbcClient.StatementSpec | **update(KeyHolder)** | int affected, key placed in holder |
| JdbcClient.StatementSpec | **update(KeyHolder, String...)** | int affected, key placed in holder |
| JdbcTemplate | **update(PreparedStatementCreator, KeyHolder)** | int affected, key placed in holder |
| NamedParameterJdbcTemplate | **update(sql, SqlParameterSource, KeyHolder, String[])** | int affected, key placed in holder |
| SimpleJdbcInsert | **executeAndReturnKey(...)** | Number generated key |
| SimpleJdbcInsert | **executeAndReturnKeyHolder(...)** | KeyHolder containing key |

JdbcClient does **not** have a generic `executeAndReturnKey()` API just because `SimpleJdbcInsert` has that method. Each class has its own signatures and role.

## 4. Retrieving Generated IDs with JdbcClient and GeneratedKeyHolder

**KeyHolder** is an interface in **org.springframework.jdbc.support**; **GeneratedKeyHolder** is the standard implementation holding keys returned by the JDBC driver.

Recommended approach when you know the key column name to collect:

~~~java
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long createMember(String displayName) {
    GeneratedKeyHolder holder = new GeneratedKeyHolder();

    int affected = jdbcClient
        .sql("""
             INSERT INTO members (display_name)
             VALUES (:name)
             """)
        .param("name", displayName)
        .update(holder, "id");

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, actual=" + affected
        );
    }

    Number key = holder.getKey();
    if (key == null) {
        throw new IllegalStateException(
            "JDBC driver did not return the generated id"
        );
    }
    return key.longValue();
}
~~~

This is a **method inside a repository that already has a `jdbcClient` field**. The `members` table and identity column `id` must exist. The snippet will not compile/run standalone with `javac` because it lacks `main` and the enclosing class declaration.

Workflow:

1. Create a fresh **new GeneratedKeyHolder()** per INSERT.
2. Specify the SQL and bind **values**.
3. Call **update(holder, "id")**, returning `int affected` and requesting JDBC to return the generated key for column `id`.
4. Verify `affected == 1` per the "single insert" contract.
5. Call **getKey()** to obtain a `Number`, checking for non-null.
6. Convert `Number` to `long` **only when the schema uses a BIGINT-compatible ID type**.

**Crucial:** the returned `int` and the key read from the holder are two independent results. Never mistake `int affected` for the key, and never treat receiving a key as proof that the transaction has committed.

### 4.1. Why Should You Specify the Column Name `"id"`?

If you call:

~~~java
GeneratedKeyHolder holder = new GeneratedKeyHolder();

int affected = jdbcClient
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Lan")
    .update(holder);
~~~

the driver must pick which generated key columns to return on its own. With many drivers this works, yet it may return **multiple columns**, unintended columns, non-numeric values, `ROWID`, or no key at all. **`update(holder, "id")`** gives clearer guidance to the driver.

Here `"id"` is a fixed SQL identifier name, not a bound value. Column-name selection support still depends on the DBMS/driver. Specifically with some Oracle drivers, calling `update(holder)` without specifying key columns can return a `ROWID` instead of the numeric key, causing `getKey()` to fail.

Never assume `KeyHolder` automatically inspects the schema and picks the exact PRIMARY KEY column across every DBMS.

### 4.2. getKey(), getKeys(), getKeyList(), and getKeyAs()

A `KeyHolder` can contain **one or more rows**, each with **one or more columns** of generated values.

| API | Used for | Notes |
| --- | --- | --- |
| **getKey()** | One row, one numeric key column (`Number`) | May be null if no key; errors on multiple keys |
| **getKeyAs(Class<T>)** | One row, one key of a specific type | Driver must return a type compatible with `T` |
| **getKeys()** | One row, multiple key columns | Column/value Map; do not use for multiple rows |
| **getKeyList()** | Multiple rows or inspecting raw key records | `List<Map<String,Object>>` |

API examples:

~~~java
Number numericKey = holder.getKey();

java.util.Map<String, Object> keyMap = holder.getKeys();

java.util.List<java.util.Map<String, Object>> keyRows =
    holder.getKeyList();
~~~

These snippets read from the same holder; **they do not mean you must call every method to retrieve a key**. If `getKey()` encounters multiple columns or multiple rows, it can throw **InvalidDataAccessApiUsageException** instead of picking one arbitrarily.

For non-numeric keys (such as UUIDs), never call `getKey().longValue()`. When the driver returns an actual `UUID` type, you can use `getKeyAs(UUID.class)`; if it returns another type, map explicitly or use PostgreSQL `RETURNING`. Column names in the Map may differ in casing depending on the JDBC driver, especially in H2/Oracle.

### 4.3. Every INSERT Must Have Its Own Holder

~~~java
// DO NOT place this field on a singleton repository:
private final GeneratedKeyHolder sharedHolder =
    new GeneratedKeyHolder();
~~~

`GeneratedKeyHolder` is a **mutable** container; if shared across requests/threads, keys can get mixed up. Create a **local** holder per operation. `JdbcClient` can be shared as a configured bean, while each operation's key state must stay isolated.

## 5. Generated Keys Depend on Schema, JDBC Driver, and Statement Preparation

Even an API with the right signature cannot turn a non-existent generated ID into a key. You must simultaneously verify:

1. **Schema actually generates values**: identity, sequence/default, trigger, or equivalent feature.
2. **Driver supports generated keys**, related to `DatabaseMetaData.supportsGetGeneratedKeys()`.
3. **Statement is prepared in generated-keys mode** — Spring's `KeyHolder` overloads handle this.
4. **Exact key column names** if `keyColumnNames` is specified.
5. **Row/column count of returned keys** matches how you read via `getKey` or `getKeyList`.
6. **Data type** of returned value is compatible with `Number`/`UUID`/`String` per contract.

Declaring `PRIMARY KEY` alone is **not enough** for the DB to auto-generate IDs. For example:

~~~sql
-- With IDENTITY: the DB can generate id.
CREATE TABLE members (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(80) NOT NULL
);
~~~

Conversely, if `id` is `BIGINT PRIMARY KEY` **without DEFAULT/IDENTITY** and the application does not pass an ID, INSERT will fail. If the application generates `UUID.randomUUID()` and passes it into INSERT, the ID is **Java-generated**; no `KeyHolder` is needed to know that value.

### 5.1. One Inserted Row May Generate More Than One Key

A DB can generate both an ID and a timestamp, computed column, or default values. Some drivers asked for `RETURN_GENERATED_KEYS` may return more than one column. `getKey()` is only valid when **one row has exactly one numeric key**; with multiple columns, use `getKeys()` or request the specific `id` column.

A batch insert can return multiple key rows; in that case `getKeyList()` is the appropriate structure. However, do not assume the count or ordering of `keyRows` always matches `affected` across every driver; verify on your target platform.

### 5.2. Do Not Guess Generated IDs from INSERT Order

A sequence can cache, skip numbers, suffer rollbacks, or be consumed by other applications. Never write logic assuming "first row gets ID 1, next gets ID 2" unless talking about a fresh demo database with no concurrent writers. In production code, always **use the ID returned by the driver/DB**.

**Never use `SELECT MAX(id)`** to find "the ID just inserted":

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
SELECT MAX(id) FROM members;
~~~

Between the two statements, another transaction may insert a larger record, or a sequence may allocate numbers differently. `MAX(id)` does not tie the key to **the exact INSERT statement just executed**. Use `KeyHolder` or supported `RETURNING` syntax; session-specific key functions also require the exact same connection/DBMS and cannot be called arbitrarily on another pooled connection.

## 6. Runnable Java 17+ Example with H2

The following example is built for **Spring JDBC 6.2.7**, **H2 2.3.232**, **JDK 17+**, and Gradle. It demonstrates **INSERT with ID generation**, **UPDATE returning affected count**, and **SELECT by generated ID**. The H2 database is in-memory and initialized fresh when the program starts.

Structure:

~~~text
jdbc-generated-keys/
  build.gradle
  src/main/java/example/JdbcClientKeysDemo.java
~~~

File **build.gradle**:

~~~groovy
plugins {
    id 'java'
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-jdbc:6.2.7'
    runtimeOnly 'com.h2database:h2:2.3.232'
}

application {
    mainClass = 'example.JdbcClientKeysDemo'
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}
~~~

File **src/main/java/example/JdbcClientKeysDemo.java**:

~~~java
package example;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public final class JdbcClientKeysDemo {

    record InsertResult(long id, int rowCount) {}

    static InsertResult insert(JdbcClient jdbc, String name) {
        GeneratedKeyHolder keys = new GeneratedKeyHolder();

        int affected = jdbc
            .sql("""
                 INSERT INTO members (display_name)
                 VALUES (:name)
                 """)
            .param("name", name)
            .update(keys, "id");

        if (affected != 1) {
            throw new IllegalStateException(
                "Expected one row, got " + affected
            );
        }
        Number key = keys.getKey();
        if (key == null) {
            throw new IllegalStateException("Missing generated id");
        }
        return new InsertResult(key.longValue(), affected);
    }

    public static void main(String[] args) {
        DriverManagerDataSource dataSource =
            new DriverManagerDataSource(
                "jdbc:h2:mem:keydemo;DB_CLOSE_DELAY=-1",
                "sa",
                ""
            );

        JdbcTemplate template = new JdbcTemplate(dataSource);
        template.execute("""
            CREATE TABLE members (
                id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                display_name VARCHAR(80) NOT NULL UNIQUE
            )
            """);

        JdbcClient jdbc = JdbcClient.create(dataSource);

        InsertResult lan = insert(jdbc, "Lan");
        InsertResult minh = insert(jdbc, "Minh");

        System.out.println(
            "Lan: id=" + lan.id() + ", rows=" + lan.rowCount()
        );
        System.out.println(
            "Minh: id=" + minh.id() + ", rows=" + minh.rowCount()
        );

        int renamed = jdbc
            .sql("""
                 UPDATE members SET display_name = :name
                 WHERE id = :id
                 """)
            .param("name", "Lan Anh")
            .param("id", lan.id())
            .update();

        int missing = jdbc
            .sql("UPDATE members SET display_name = ? WHERE id = ?")
            .param("Nobody")
            .param(999L)
            .update();

        System.out.println("updated rows: " + renamed);
        System.out.println("missing rows: " + missing);

        String persistedName = jdbc
            .sql("SELECT display_name FROM members WHERE id = :id")
            .param("id", lan.id())
            .query(String.class)
            .single();
        System.out.println("selected name: " + persistedName);
    }
}
~~~

**Code walkthrough:** `JdbcTemplate.execute` creates the table; `JdbcClient.create(DataSource)` creates the fluent client; `insert` creates a new holder, calls `update(holder, "id")`, checks `affected`, reads `Number key`, and returns an `InsertResult` record. Subsequent UPDATEs **only** call `update()` because no key is needed. SELECT via `query(String.class).single()` reads the final result.

Run with an installed Gradle:

~~~bash
gradle run
~~~

Or Gradle Wrapper if present in the project:

~~~bash
./gradlew run
~~~

On Windows PowerShell with wrapper:

~~~powershell
.\gradlew.bat run
~~~

Do not invoke `javac` directly without specifying a classpath; Spring JDBC and H2 classes are resolved by Gradle. If dependencies are not cached yet, Gradle will download them before running.

**Expected stdout from `main` on a fresh H2 database**, excluding Gradle logs:

~~~text
Lan: id=1, rows=1
Minh: id=2, rows=1
updated rows: 1
missing rows: 0
selected name: Lan Anh
~~~

Because the database is fresh and identity defaults start at 1, the two sequential inserts receive IDs 1 and 2 in this example. The program **does not hard-code** IDs: it reads the actual values from `KeyHolder`, so it stays valid even if IDs start at a different number. Updating a non-existent ID returns count 0; that is not a generated ID.

**Demo scope:** `DriverManagerDataSource` is used for simplicity, not as a production connection pool. In real Spring Boot applications, typically use HikariCP, a transaction manager, schema migrations, and a `DataSource` configured via application properties.

### 6.1. Why Is `update(keys, "id")` Usually More Predictable Than `update(keys)`?

Specifying the key column tells the driver explicitly that you want **`id`**. Without specifying it, the driver may return a broader default set of keys. If you change it to:

~~~java
GeneratedKeyHolder keys = new GeneratedKeyHolder();

int affected = jdbc
    .sql("INSERT INTO members (display_name) VALUES (?)")
    .param("Ha")
    .update(keys);
~~~

reading `getKey()` is still only valid when the driver returns **a single numeric key**. This is **a separate experimental variant**, not needed to finish the base demo. In production code, verify driver behavior before omitting key column names.

## 7. Spring 6.0 or Older Projects: Use JdbcTemplate

When **JdbcClient is unavailable**, you can still retrieve generated keys using the long-standing API:

~~~java
import java.sql.PreparedStatement;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long insertWithJdbcTemplate(
        JdbcTemplate jdbc, String name) {

    GeneratedKeyHolder keys = new GeneratedKeyHolder();
    String sql =
        "INSERT INTO members (display_name) VALUES (?)";

    int affected = jdbc.update(connection -> {
        PreparedStatement ps = connection.prepareStatement(
            sql, new String[] {"id"}
        );
        ps.setString(1, name);
        return ps;
    }, keys);

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, got " + affected
        );
    }

    Number key = keys.getKey();
    if (key == null) {
        throw new IllegalStateException("No generated key");
    }
    return key.longValue();
}
~~~

This is **a method in a class that has a JdbcTemplate**, not a standalone Java program. Crucially, the **`PreparedStatementCreator` must enable returning generated keys**, e.g., via `connection.prepareStatement(sql, new String[] {"id"})`. If you create a statement with `prepareStatement(sql)` without enabling that mode, `KeyHolder` may stay empty even when the INSERT succeeds.

You can use `Statement.RETURN_GENERATED_KEYS` on drivers that support it, though specifying column names is usually clearer when supported by the database and JDBC driver.

## 8. Projects Using NamedParameterJdbcTemplate

For SQL with named parameters, there is an overload:

~~~java
int update(
    String sql,
    SqlParameterSource paramSource,
    KeyHolder generatedKeyHolder,
    String[] keyColumnNames
);
~~~

Example:

~~~java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;

public long insertWithNamedJdbc(
        NamedParameterJdbcTemplate namedJdbc, String name) {

    MapSqlParameterSource params =
        new MapSqlParameterSource("name", name);
    GeneratedKeyHolder keys = new GeneratedKeyHolder();

    int affected = namedJdbc.update(
        "INSERT INTO members (display_name) VALUES (:name)",
        params,
        keys,
        new String[] {"id"}
    );

    if (affected != 1) {
        throw new IllegalStateException(
            "Expected one inserted row, got " + affected
        );
    }
    Number key = keys.getKey();
    if (key == null) {
        throw new IllegalStateException("No generated id");
    }
    return key.longValue();
}
~~~

Signature comparison:

- **JdbcClient**: `.update(keys, "id")`, where `String...` is **varargs**.
- **NamedParameterJdbcTemplate**: `.update(sql, params, keys, new String[] {"id"})`, where key columns is a `String[]` array.

Both return `int affected`. The generated ID is placed inside `keys`. Do not copy signatures across classes without checking.

## 9. SimpleJdbcInsert: API Returning a Numeric Key Directly

If you only need to INSERT into a fairly simple table, **SimpleJdbcInsert** provides **`executeAndReturnKey(...)`**. This is a **different** API from JdbcClient.

~~~java
import java.util.Map;
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public long insertWithSimpleJdbcInsert(
        DataSource dataSource, String name) {

    SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("members")
        .usingColumns("display_name")
        .usingGeneratedKeyColumns("id");

    Number generated = insert.executeAndReturnKey(
        Map.of("display_name", name)
    );
    if (generated == null) {
        throw new IllegalStateException("No generated id");
    }
    return generated.longValue();
}
~~~

In real applications, **initialize `SimpleJdbcInsert` once** inside the repository bean and reuse it. The example method creates one per call solely to illustrate the API. This class can use `DatabaseMetaData` from the driver to help build SQL; if metadata is incomplete, specify table/column/schema explicitly.

If multiple key columns or multiple generated values are returned, use **`executeAndReturnKeyHolder(...)`** and inspect the map/list. **Do not** call `executeAndReturnKey()` on `JdbcClient`, as that method belongs to `SimpleJdbcInsert`.

## 10. PostgreSQL: INSERT ... RETURNING and JdbcClient.query()

PostgreSQL supports **RETURNING** on INSERT, UPDATE, and DELETE, returning data from the affected rows. For example:

~~~sql
INSERT INTO members (display_name)
VALUES ('Lan')
RETURNING id;
~~~

With the PostgreSQL JDBC driver, this SQL returns a `ResultSet`. A clean way to retrieve the ID is **`JdbcClient.query(...)`**, not `update(KeyHolder)`:

~~~java
public long insertPostgres(JdbcClient jdbc, String name) {
    return jdbc
        .sql("""
             INSERT INTO members (display_name)
             VALUES (:name)
             RETURNING id
             """)
        .param("name", name)
        .query(Long.class)
        .single();
}
~~~

This is a **PostgreSQL-dialect method**, not portable across every DBMS. The SQL returns one ID value, so `.single()` fits when the INSERT is guaranteed to create **exactly one row**. If using `ON CONFLICT DO NOTHING` and no row is inserted, `RETURNING` can return **0 rows**; `.single()` will throw a cardinality error rather than returning ID 0.

| Criterion | `update(keys, "id")` | `INSERT ... RETURNING id` |
| --- | --- | --- |
| Spring API | `JdbcClient.update` with `KeyHolder` | `JdbcClient.query(...).single()` |
| Direct value | `int affected` | ID value from `ResultSet` |
| How ID is read | `holder.getKey()` | `.single()` |
| DB portability | Depends on JDBC generated keys | Depends on SQL dialect |
| Multi-column support | `getKeys`/`getKeyList` | query map/record |
| 0-row case | Inspect affected and keys | Query has no result, handle cardinality |

Never assume every database supports `RETURNING` with PostgreSQL syntax. If portability is required, choose JDBC generated keys or a dialect-specific abstraction, then integration-test against the target DBMS.

## 11. Multiple Keys and Batch Update Scenarios

### 11.1. Multiple Generated Columns

Suppose the driver returns `id` along with another generated column. In that case `getKey()` can throw **InvalidDataAccessApiUsageException** because it requires a single numeric entry. Read `getKeys()` to get a map for **one row**, or specify the key column `"id"` in `update(holder, "id")` if supported by the driver.

~~~java
java.util.Map<String, Object> rowKeys = keys.getKeys();
if (rowKeys == null || rowKeys.isEmpty()) {
    throw new IllegalStateException("Key result is empty");
}
~~~

Column names in the map may be `ID` or `id` depending on how the driver handles identifiers. Never hard-code casing assumptions without testing. With composite keys or non-numeric keys, the repository contract must also represent the full key type rather than forcing everything into `long`.

### 11.2. Multiple Generated Rows

With a batch INSERT, a driver may return keys for multiple rows. In that case:

~~~java
java.util.List<java.util.Map<String, Object>> rows =
    keys.getKeyList();
~~~

holds multiple key maps; **`getKey()`** is not meant for this scenario. Verify the exact key count, alignment with input order, and DBMS/driver limitations. Do not mistake the **`int[]`** array returned by batch updates for generated IDs; those are update counts or JDBC status codes.

### 11.3. Version Differences for Batching

Spring JDBC 6.x releases provide **JdbcTemplate.batchUpdate** and **NamedParameterJdbcTemplate.batchUpdate**. Documentation for **Spring 7.1** also describes convenience APIs like **JdbcClient.batch()**. Do not use `.batch()` in code running on Spring 6.1/6.2/7.0 just because you read a newer documentation version; inspect the **Javadoc of your actual dependency**.

Even when a batch API supports generated keys, never assume every driver returns all IDs or preserves key order uniformly. For workflows needing per-row IDs, test the running DB/driver version, or consider `INSERT ... RETURNING` in a compatible dialect.

## 12. Transactions: Having an ID Does Not Mean Committed

A service might write:

~~~java
@Transactional
public long createMember(String name) {
    return repository.insertAndReturnId(name);
}
~~~

The snippet above is a **Spring service snippet** with `@Transactional` and a repository, not a standalone program. Inside a transaction, an INSERT can generate an ID and return it to the service **before commit**. If an exception occurs later and the transaction rolls back, the inserted row **will not exist** in the database afterward, even though `KeyHolder` received an ID.

Sequences/identities routinely have gaps due to rollbacks, concurrency, caching, or DB operations. Never write logic requiring contiguous, gap-free IDs. An ID is merely an identifier, not a measure of successful INSERT count or transaction commit order.

If the application needs to publish an event containing the new record's ID, design the event emission timing to match the transaction (such as outbox or after-commit hooks as needed) so you do not broadcast IDs of data that ends up rolled back.

### 12.1. Why Is SELECT MAX(id) Wrong for Finding Keys?

~~~sql
INSERT INTO members (display_name) VALUES ('Lan');
SELECT MAX(id) FROM members;
~~~

The SELECT is not bound to **the INSERT statement just executed**, and can observe rows from other transactions depending on isolation/concurrency. Do not "fix" this by waiting a few milliseconds. Use generated keys from the statement itself or `RETURNING`. Similarly, session-specific last-id functions only work when you understand connection/DBMS scoping; never invoke them arbitrarily on a different pooled connection.

### 12.2. Retries Can Insert Duplicates

If the server completes the INSERT but the network drops before the client receives the generated key, blind retries can create **two records**. Design idempotency/unique business keys when required rather than assuming "no ID received means no INSERT occurred".

## 13. Diagnosing Generated Key Errors

| Symptom | Possible cause | What to check |
| --- | --- | --- |
| `update()` returns 1, yet code treats it as ID | Confusing affected row count with ID | Use holder or `RETURNING` |
| `holder.getKey() == null` | Driver did not return key, wrong key column, DB did not generate ID | Schema identity/default, JDBC metadata, affected |
| `getKey()` reports multiple keys | Driver returned multiple columns/rows | `update(holder, "id")`, `getKeys`/`getKeyList` |
| `getKey()` reports non-Number type | `ROWID`/UUID/driver-specific type | `keyColumnNames`, `getKeyAs`/map, dialect |
| INSERT fails on unique constraint | Duplicate value or index violation | Handle `DataAccessException`, never fake ID 0 |
| `affected = 0` after UPDATE | No matching row or DBMS count behavior | `WHERE` condition, driver semantics |
| IDs not in expected sequence | Sequence/identity gaps | Do not hard-code IDs or use `MAX` |
| Key returned yet subsequent SELECT finds nothing | Transaction rollback, replication lag, different tenant/DB | Transaction, connection, datasource |
| `JdbcClient` code fails to compile on Spring 6.0 | API does not exist yet | Use `JdbcTemplate`/`NamedParameterJdbcTemplate` |
| `update(KeyHolder)` returns `ROWID` | Driver auto-selected generated keys inaccurately | `update(holder, "id")`, metadata |
| UUID key cast to `Long` | Wrong data type | Use `getKeyAs`/`RETURNING` with matching mapping |
| Batch does not return all keys | JDBC driver and API version limitations | Driver integration test, `keyList` |

Some errors are translated by Spring into **DataAccessException**. Never `catch (Exception)` and return `ID = -1` or `Optional.empty()` for every case; doing so misrepresents a database outage or constraint violation as "no data".

## 14. Testing Across Versions and Databases

A valuable test suite checks both **count** and **key**:

1. **Spring API compatibility:** does the runtime version actually have `JdbcClient.StatementSpec.update()` and the `KeyHolder` overloads?
2. **Single-row INSERT:** `affected = 1`, key non-null, key reads back the exact record.
3. **ID not starting at 1:** code reads from holder, not from row count.
4. **UPDATE non-existent ID:** `affected = 0`, not treated as a generated ID.
5. **Unique violation:** raises the expected exception, does not return a fake key.
6. **Driver returns no keys:** repository raises a clear error rather than computing `MAX(id)`.
7. **Multiple generated columns:** `getKey()` is not called without safeguards.
8. **Table with UUID:** conversion does not erroneously cast to `long`.
9. **Transaction rollback:** a key may have been generated even though the row did not commit.
10. **PostgreSQL RETURNING:** handles 0/1/n rows per contract.
11. **Batch:** are key counts and order guaranteed by the driver?
12. **Concurrency:** two concurrent INSERT requests never mix up each other's keys.

H2 is convenient for learning the API; for Oracle, PostgreSQL, MySQL, SQL Server, or specialized key-generation schemes, integration-test with the target DBMS or Testcontainers. Never assume a passing H2 test proves every driver returns keys identically.

## 15. Exercises with Answers

**Question 1.** `JdbcClient.update()` returns 1 after an INSERT. Can you conclude the generated ID is 1?

**Answer:** No. That is the affected row count, not the key.

**Question 2.** Does Spring Framework 6.1.8 include the `update(KeyHolder, String...)` overload?

**Answer:** Yes. The 6.1.8 Javadoc lists `update()`, `update(KeyHolder)`, and `update(KeyHolder, String...)`.

**Question 3.** How should a Spring 6.0 project retrieve an identity ID?

**Answer:** Use `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)`, `NamedParameterJdbcTemplate.update(...KeyHolder...)`, or `SimpleJdbcInsert.executeAndReturnKey`.

**Question 4.** Why is `update(holder, "id")` usually better than `update(holder)` when you need the ID?

**Answer:** It explicitly states the desired key column, avoiding letting the driver pick an unintended column or set of columns. You should still verify driver support.

**Question 5.** Can `getKey()` handle generated keys for three rows?

**Answer:** No. `getKey()` is for one row and one numeric key. Use `getKeyList` for multiple rows when the driver supports returning keys.

**Question 6.** If the key is a UUID, is `getKey().longValue()` valid?

**Answer:** No. Use proper UUID/String mapping per driver or a corresponding `RETURNING` query.

**Question 7.** An INSERT obtained an ID, but the transaction later rolled back. Is the ID guaranteed to still exist as a row?

**Answer:** No. Identity/sequence numbers can be consumed even when the row is not committed.

**Question 8.** Why is `SELECT MAX(id)` after an INSERT unreliable?

**Answer:** It is not tied to the INSERT statement just run and can be affected by concurrency and ID generation behavior.

**Question 9.** Which JdbcClient API does PostgreSQL `INSERT ... RETURNING id` use?

**Answer:** You can use **`query(Long.class).single()`** because the statement returns a `ResultSet`; `RETURNING` syntax is not portable across all DBMSs.

**Question 10.** `.update(holder)` returns `affected = 1`, yet the holder has no key; should you return `ID = 0` to avoid an error?

**Answer:** No. Inspect the schema/driver/`keyColumnNames`, and fail clearly if the contract requires an ID that the DB did not return.

## 16. Pre-Production Checklist

- **`JdbcClient.update()` returns an `int` affected row count**, not an auto-generated ID.
- **Spring 6.1+** provides **`update(KeyHolder)`** and **`update(KeyHolder, String...)`**; check the matching Javadoc.
- **`GeneratedKeyHolder`** holds keys after INSERT, rather than being the direct return value of `update(holder)`.
- **`getKey()`** is for a single `Number` key; multiple keys use `getKeys`/`getKeyList`, and non-numeric keys require proper typed mapping.
- **Specify the ID column name** where appropriate to reduce reliance on driver auto-detection.
- **Spring <=6.0** uses `JdbcTemplate`/`NamedParameterJdbcTemplate`/`SimpleJdbcInsert`; `JdbcClient` does not exist there.
- **PostgreSQL `RETURNING`** is an alternative based on `ResultSet`; do not treat it as portable.
- **Never use `SELECT MAX(id)`**, never infer IDs from affected counts, and never share a mutable `KeyHolder` across requests.
- **Keys are generated before commit** and sequences can have gaps upon rollback.
- **Test on the actual driver/database**, especially for UUID keys, multi-column keys, batching, Oracle, and multi-tenant setups.
