# SimpleJdbcInsert Simplifies Generating Insert Statements

## 1. The Problem: Inserting Data Without Repeatedly Writing INSERT Statements

When working directly with JDBC, creating a record typically requires writing SQL `INSERT INTO ...`, creating a `PreparedStatement`, setting each parameter in the right position, executing the statement, and handling resources. Spring's `JdbcTemplate` reduces the boilerplate of managing connections, statements, and errors, yet developers still often have to write SQL strings manually for each table.

**`SimpleJdbcInsert`** in Spring JDBC simplifies the case of **inserting one or more rows into a relational table**: you configure the table name, the columns to write, and (if needed) the database-generated key column; Spring uses table metadata provided by the JDBC driver and/or the declared column list to generate the `INSERT` statement along with parameter placeholders. Each time you use it, you provide **column name → value** pairs instead of concatenating SQL and counting `?` positions.

For example, suppose you want to create a customer in a table:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(200) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

This DDL uses `IDENTITY` syntax compatible with H2 (and some other DBMSs); auto-increment key syntax may differ in other databases. When creating a customer, the application only needs to write `full_name` and `email`. The database will generate `id`, and the default value of `created_at` takes effect if that column is **not included in the insert list**.

Traditional SQL looks like this:

```sql
INSERT INTO customer (full_name, email) VALUES (?, ?);
```

With `SimpleJdbcInsert`, instead of keeping that SQL string in the repository, you can write:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("customer")
        .usingColumns("full_name", "email");

int affectedRows = insert.execute(
        Map.of("full_name", "An", "email", "an@example.test"));
```

This is an **illustrative snippet** placed inside a class that has a `dataSource` field of type `javax.sql.DataSource` and imports `SimpleJdbcInsert` and `Map`. The snippet is not yet a standalone program with a `main` method; section 5 provides a complete runnable project.

The `affectedRows` result is the **number of affected rows returned by the JDBC driver**, which for a successful single-row insert is typically `1`. It is not the newly generated `id`. How to retrieve the `id` is explained in section 6.

## 2. How Does `SimpleJdbcInsert` Work?

`SimpleJdbcInsert` belongs to the `org.springframework.jdbc.core.simple` package, extends `AbstractJdbcInsert`, and uses the `JdbcTemplate` infrastructure underneath. It can be created from a `DataSource` or a `JdbcTemplate`:

```java
SimpleJdbcInsert viaDataSource = new SimpleJdbcInsert(dataSource);
SimpleJdbcInsert viaTemplate = new SimpleJdbcInsert(jdbcTemplate);
```

These two lines show two alternative ways to instantiate it; use whichever fits your existing repository.

Processing flow:

```text
Configure once: DataSource/JdbcTemplate + table + columns
                     |
                     v
  SimpleJdbcInsert prepares/compiles the INSERT configuration
      (may read DatabaseMetaData from the JDBC driver)
                     |
                     v
Each invocation: Map or SqlParameterSource containing values
                     |
                     v
          Build/bind parameters for the SQL INSERT
                     |
                     v
             JdbcTemplate executes JDBC
                     |
                     v
     Affected row count / generated key (if requested)
```

Important distinctions to keep in mind:

- **Table names and column names** are configuration used to build the SQL **structure**. They must be identifiers controlled by application code, never taken arbitrarily from user input.
- **Column values** go into parameters bound via JDBC, separating data from SQL syntax rather than concatenating values into the statement.
- `DatabaseMetaData` helps Spring discover columns, table names, and properties as supported by the driver. If the driver provides inaccurate metadata, you can declare columns explicitly or disable column metadata discovery.
- `SimpleJdbcInsert` is not an ORM: it does not manage object relationships, does not perform dirty checking, does not reload the entire entity after inserting, and does not replace transaction management.

### Instantiation, Configuration, and Reuse

Typically, you create and configure `SimpleJdbcInsert` **once** in the constructor or during repository initialization:

```java
private final SimpleJdbcInsert insert;

public CustomerRepository(DataSource dataSource) {
    this.insert = new SimpleJdbcInsert(dataSource)
            .withTableName("customer")
            .usingColumns("full_name", "email");
}
```

Once configuration is complete, the object is designed to be **reused across calls**, even from multiple threads. Avoid recreating it on every insert because that can cause unnecessary repeated preparation and metadata lookups. Avoid modifying the configuration after the object has been compiled or started executing.

By default, if `compile()` has not been called explicitly, configuration compilation occurs on demand during the first execution. You can call `insert.compile()` **after configuration is complete and the schema already exists** to catch certain configuration errors early. This compiles the SQL operation configuration, not Java source code.

## 3. Configuration Methods to Remember

| API | Purpose | Notes |
| --- | --- | --- |
| `withTableName("customer")` | Specifies the target table. | Usually required configuration. |
| `withSchemaName("sales")` | Specifies the schema when the table is not in the default schema. | Depends on schema organization and the JDBC driver. |
| `withCatalogName("...")` | Specifies the catalog if needed. | Not all DBMSs use catalogs in the same way. |
| `usingColumns("full_name", "email")` | Declares **exactly which columns** are included in `INSERT`. | Very useful for omitting `id`, default timestamps, and columns that should not be written. |
| `usingGeneratedKeyColumns("id")` | Requests retrieval of the DB-generated key in the `id` column. | Used together with `executeAndReturnKey` or `executeAndReturnKeyHolder`. |
| `withoutTableColumnMetaDataAccess()` | Disables table column metadata lookup. | Requires explicitly declaring the insert columns with `usingColumns(...)`. |
| `usingQuotedIdentifiers()` | Uses the identifier quote characters provided by the database. | Requires declaring `usingColumns(...)` and matching exact casing from metadata. |

### Default Metadata or Explicit Column Specification?

Minimal configuration:

```java
new SimpleJdbcInsert(dataSource).withTableName("customer");
```

In this case, Spring can use metadata returned by the driver to determine the column list. This is convenient for simple schemas, but it **does not mean that if your input only has two columns, Spring will always omit all other columns as you expect**. Default-valued, nullable, auto-generated, and required columns depend on specific configuration and metadata.

For the example table, a clearer and more predictable approach is:

```java
new SimpleJdbcInsert(dataSource)
        .withTableName("customer")
        .usingColumns("full_name", "email")
        .usingGeneratedKeyColumns("id");
```

The `usingColumns` list determines which columns are included in the `INSERT` statement; `created_at` is omitted so the DB applies `DEFAULT CURRENT_TIMESTAMP`. `usingGeneratedKeyColumns("id")` requests reading the generated key; it **does not replace `usingColumns`**, and the `id` column does not need to be passed in the insert data.

If column metadata from the driver is missing or problematic, you can explicitly declare both:

```java
new SimpleJdbcInsert(dataSource)
        .withTableName("customer")
        .usingColumns("full_name", "email")
        .usingGeneratedKeyColumns("id")
        .withoutTableColumnMetaDataAccess();
```

`withoutTableColumnMetaDataAccess()` does not mean the JDBC driver is no longer involved in execution; Spring still needs a connection and the corresponding JDBC capabilities to insert rows and retrieve keys. Test this configuration with your actual database and driver, especially with special SQL column types or generated keys.

### When You Need a Schema or Quoted Column Names

If the table resides in a separate schema:

```java
new SimpleJdbcInsert(dataSource)
        .withSchemaName("sales")
        .withTableName("customer")
        .usingColumns("full_name", "email");
```

If table/column names are defined as case-sensitive or collide with SQL keywords, you may need `usingQuotedIdentifiers()`. When enabled, you must declare columns explicitly and use the exact identifier spelling from metadata. Do not enable quoting mechanically, because quoting and case rules differ across PostgreSQL, H2, Oracle, SQL Server, MySQL, and others.

## 4. Passing Data to Insert: `Map` and `SqlParameterSource`

### Option A — `Map<String, ?>`

```java
Map<String, Object> values = new HashMap<>();
values.put("full_name", "An");
values.put("email", "an@example.test");

int affected = insert.execute(values);
```

The keys `"full_name"` and `"email"` are **column names**, not `1`, `2` positional indices as in `PreparedStatement.setString`. Do not use the Java property name `"fullName"` if the SQL column is named `full_name` without an appropriate mapping step.

`Map.of(...)` is concise for data without `null`. It does not allow `null` keys or values. If a column allows `null`, use `HashMap` or `MapSqlParameterSource` and register the SQL type when needed.

### Option B — `MapSqlParameterSource`

```java
import java.sql.Types;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;

MapSqlParameterSource params = new MapSqlParameterSource()
        .addValue("full_name", "An")
        .addValue("email", null, Types.VARCHAR);

int affected = insert.execute(params);
```

This example **only works if the schema allows `email` to accept NULL**; the illustrative table above declares `email NOT NULL`, so using it with that table will be rejected. The goal is to demonstrate how to declare `Types.VARCHAR` for a `null` value so the driver knows the SQL type when binding the parameter. `MapSqlParameterSource` is suitable when you need to add parameters and declare types explicitly.

### Option C — `BeanPropertySqlParameterSource`

If you have a JavaBean with getters matching the SQL parameter/column names, you can write:

```java
SqlParameterSource params = new BeanPropertySqlParameterSource(customerBean);
int affected = insert.execute(params);
```

This is an **API illustration**; `customerBean` must be a valid JavaBean and its properties must have getters whose names are compatible with the column names used. Do not assume `BeanPropertySqlParameterSource` automatically converts `fullName` to `full_name`. When the database uses `snake_case` naming while Java DTOs use `camelCase`, `MapSqlParameterSource` or an explicitly mapped `Map` is usually easier to control.

### Name Matching and Data Type Rules

Assuming `usingColumns("full_name", "email")` is configured, each call must supply the corresponding values. If a key name is wrong, Spring cannot bind the parameters in the `INSERT` statement properly and will typically throw an exception. Do not mistakenly think the entry order in a `HashMap` determines the bind order; the column order is already fixed by Spring in the SQL configuration, and values are looked up by **column name**.

Java types must match SQL types: `String` with `VARCHAR`, `BigDecimal` with `DECIMAL`, `LocalDate` with `DATE`, etc.; `null` or vendor-specific types may require declaring `java.sql.Types`. Inspect logs and `DataAccessException` errors when diagnosing issues.

## 5. Runnable Demo: Spring JDBC + H2 + Java 17+

This example provides a **standalone** program that creates a table in in-memory H2, inserts rows with `SimpleJdbcInsert`, retrieves the generated ID, and verifies the data with `JdbcTemplate`. Neither Spring Boot nor a Spring context is needed just to try this class.

Project structure:

```text
simple-jdbc-insert-demo/
├── build.gradle
└── src/
    └── main/
        └── java/
            └── Demo.java
```

`build.gradle` (Gradle using Groovy DSL):

```groovy
plugins {
    id 'application'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-jdbc:6.2.12'
    runtimeOnly 'com.h2database:h2:2.3.232'
}

application {
    mainClass = 'Demo'
}
```

`src/main/java/Demo.java`:

```java
import java.util.Map;

import javax.sql.DataSource;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.datasource.DriverManagerDataSource;

public class Demo {

    public static void main(String[] args) {
        // H2 in-memory; DriverManagerDataSource is for demo only, without pooling.
        DataSource ds = new DriverManagerDataSource(
                "jdbc:h2:mem:simple_insert;DB_CLOSE_DELAY=-1", "sa", "");

        JdbcTemplate jdbc = new JdbcTemplate(ds);

        jdbc.execute("""
                CREATE TABLE customer (
                    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                    full_name VARCHAR(100) NOT NULL,
                    email VARCHAR(200) NOT NULL,
                    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
                )
                """);

        // Configure once. No need to write INSERT INTO ... VALUES (?, ?) manually.
        SimpleJdbcInsert insert = new SimpleJdbcInsert(ds)
                .withTableName("customer")
                .usingColumns("full_name", "email")
                .usingGeneratedKeyColumns("id");

        Number newId = insert.executeAndReturnKey(
                Map.of("full_name", "An", "email", "an@example.test"));

        if (newId == null) {
            throw new IllegalStateException("Database did not return an ID key");
        }

        String storedName = jdbc.queryForObject(
                "SELECT full_name FROM customer WHERE id = ?",
                String.class,
                newId.longValue());

        // execute(...) returns the affected row count, not the generated key.
        int affected = insert.execute(
                Map.of("full_name", "Binh", "email", "binh@example.test"));

        Integer totalRows = jdbc.queryForObject(
                "SELECT COUNT(*) FROM customer", Integer.class);

        System.out.println("storedName=" + storedName);
        System.out.println("affectedRows=" + affected);
        System.out.println("totalRows=" + totalRows);
    }
}
```

Requirements: JDK 17+, a compatible Gradle version (e.g., Gradle 8.x), and network access to download dependencies from Maven Central on the first run. From the project directory, run:

```bash
gradle run
```

If the project has the Gradle Wrapper, you can use `./gradlew run` on Linux/macOS or `.\gradlew.bat run` in Windows PowerShell. Without the Wrapper, `gradle run` requires Gradle to be installed.

**Output from `main`** (ignoring Gradle and library logs):

```text
storedName=An
affectedRows=1
totalRows=2
```

No specific ID value is printed because the ID is DB-generated, and tests should not hardcode expectations that the ID equals `1`. The program still verifies that the ID works via `SELECT ... WHERE id = ?`. After the first `executeAndReturnKey`, the second `execute` inserts one more row, bringing the total row count to `2`.

In the demo, `DriverManagerDataSource` creates a new connection on every request; it is convenient for quick tests but **has no connection pooling**. Real applications typically use a `DataSource` configured by Spring Boot/a pool along with proper transaction management.

### Breaking Down the 4 Essential Steps of the Demo

**Step 1 — Specify the table:** `withTableName("customer")` designates the insert target.

**Step 2 — Specify the insert columns:** `usingColumns("full_name", "email")` ensures `id` and `created_at` are excluded from `INSERT`, allowing the DB to apply identity/default values.

**Step 3 — Bind values by name:** `Map.of(...)` supplies values to bind to the two columns; no manual SQL string concatenation from user content.

**Step 4 — Choose the result API:** `executeAndReturnKey(...)` returns a numeric key; `execute(...)` returns the number of affected rows.

## 6. Retrieving Generated Keys: `executeAndReturnKey` and `KeyHolder`

To obtain a DB-generated key, you must specify the generated key column during configuration:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("customer")
        .usingColumns("full_name", "email")
        .usingGeneratedKeyColumns("id");

Number generatedId = insert.executeAndReturnKey(
        Map.of("full_name", "An", "email", "an@example.test"));
```

This is an **illustration separate from the demo in section 5**, and assumes a `dataSource` variable is available. Do not run it consecutively in the demo program unless you intend to insert another row.

Key differences to remember:

| Call | Result | When to use |
| --- | --- | --- |
| `execute(Map)` or `execute(SqlParameterSource)` | `int` — number of affected rows reported by JDBC. | When you need to know how many rows were successfully inserted. |
| `executeAndReturnKey(Map)` or `SqlParameterSource` overload | `Number` — single numeric key from the DB. | When the table has a single numeric generated key and the driver supports it. |
| `executeAndReturnKeyHolder(Map)` or `SqlParameterSource` overload | `KeyHolder` containing returned generated keys. | When you need to inspect key columns or non-numeric keys. |
| `executeBatch(Map...)/executeBatch(SqlParameterSource...)` | `int[]` — affected row count per batch element. | When inserting multiple rows with a single configuration. |

Never treat `execute(...)` as returning an ID. Likewise, `executeAndReturnKey(...)` is only reliable when the driver supports returning keys and the `id` column is actually generated by the database. `Number` is a general supertype: the driver might return `Long`, `Integer`, `BigDecimal`, etc. Only convert via `longValue()` if your domain uses `long` and the value fits the representation range; check for `null`/errors when no key is returned.

If the key is non-numeric or there are multiple key columns, use `KeyHolder`:

```java
KeyHolder holder = insert.executeAndReturnKeyHolder(
        Map.of("full_name", "An", "email", "an@example.test"));

// Example: inspect all key maps instead of assuming a single Number.
List<Map<String, Object>> keyRows = holder.getKeyList();
for (Map<String, Object> keyRow : keyRows) {
    System.out.println(keyRow);
}
```

The snippet above requires importing `org.springframework.jdbc.support.KeyHolder`, `java.util.List`, and `java.util.Map`. The actual map structure and row/column counts depend on the database, JDBC driver, and supported statement behavior. Do not assume the key name is always lowercase `id`; inspect what the driver returns. `KeyHolder.getKey()` is only convenient when there is genuinely **a single numeric key value**; multiple key columns or rows do not fit that call.

**Do not confuse `SimpleJdbcInsert` with `SimpleJdbcCall`:** the latter is for stored procedures/functions. The scope of this lesson is standard `INSERT` generation.

## 7. Inserting Multiple Rows with `executeBatch`

When you need to insert multiple records with the same structure, `SimpleJdbcInsert` also provides a batch API:

```java
int[] updateCounts = insert.executeBatch(
        Map.of("full_name", "An", "email", "an@example.test"),
        Map.of("full_name", "Binh", "email", "binh@example.test"),
        Map.of("full_name", "Chi", "email", "chi@example.test"));
```

This is an **alternative scenario** to the single inserts in the demo; avoid running both if you want exactly three rows. `updateCounts` holds the per-element update counts reported by the driver, not the list of generated `id`s. Some drivers may return JDBC codes such as `Statement.SUCCESS_NO_INFO` instead of `1`; test against the actual DB if you need to interpret individual elements. Never guess subsequent IDs from the record count.

Batching is useful for reducing round-trips and statement dispatch overhead; actual optimization, batch size, and error handling depend on the driver, transaction, and DB limits. A batch does not automatically make the entire operation atomic; use a transaction if you need all-or-nothing commit/rollback semantics.

## 8. Comparison with `JdbcTemplate.update` and Plain JDBC

Consider the same task of inserting two values into the `customer` table:

**Plain JDBC:**

```java
try (PreparedStatement ps = connection.prepareStatement(
        "INSERT INTO customer (full_name, email) VALUES (?, ?)")) {
    ps.setString(1, fullName);
    ps.setString(2, email);
    int rows = ps.executeUpdate();
}
```

The snippet above requires importing `java.sql.PreparedStatement` and having `connection`, `fullName`, and `email` available. The author must write the SQL, set parameters in order, manage the statement (and manage the connection externally).

**`JdbcTemplate.update`:**

```java
int rows = jdbcTemplate.update(
        "INSERT INTO customer (full_name, email) VALUES (?, ?)",
        fullName, email);
```

Spring handles JDBC resource lifecycles and translates `SQLException` into its data access exception hierarchy; the developer still maintains the SQL string and argument order.

**`SimpleJdbcInsert.execute`:**

```java
int rows = insert.execute(
        Map.of("full_name", fullName, "email", email));
```

Once `insert` is pre-configured, the insert code only needs a **column → value** mapping. This reduces SQL boilerplate and prevents parameter-order mismatches when tables have many columns; on the flip side, it ties into metadata and the constraints of generated statements.

Selection table:

| Case | Suitable choice |
| --- | --- |
| Simple single-table `INSERT`, stable columns, repeated calls | `SimpleJdbcInsert` is a concise choice. |
| Special SQL needed: `INSERT ... SELECT`, UPSERT/`ON CONFLICT`, vendor hints, DB-specific `RETURNING`, CTEs... | Write explicit SQL via `JdbcTemplate` or an appropriate API. |
| Fine-grained control over SQL, batching, or vendor-specific features needed | `JdbcTemplate` or direct JDBC. |
| Complex object/relationship mapping and entity lifecycle management needed | Consider an ORM such as JPA/Hibernate if it fits the architecture. |

`SimpleJdbcInsert` **has no built-in record update mechanism** like `UPDATE`, does not perform UPSERT automatically, and does not turn records into managed entities.

## 9. Transactions, Security, and Performance

### Participating in Spring Transactions

`SimpleJdbcInsert` executes through Spring JDBC and can participate in Spring-managed transactions when using the same `DataSource` and an appropriate transaction manager. Example of a service method using `@Transactional`:

```java
@Transactional
public long createCustomerAndAudit(CustomerInput input) {
    long customerId = customerRepository.insert(input);
    auditRepository.insertCreatedEvent(customerId);
    return customerId;
}
```

This is an **architectural illustration**, not a standalone program: `CustomerInput`, `customerRepository`, `auditRepository`, `@Transactional` configuration, and the transaction manager must be provided by the application. When sharing the same resource and transaction, an error can roll back both operations according to the configured rollback rules. Having received an `id` before commit **does not prove** the transaction has committed; sequences/identities can still have gaps if a transaction rolls back.

### Input Handling Security

Values from `Map`/`SqlParameterSource` are bound as JDBC parameters. However, **SQL identifiers** in `withTableName(...)`, `usingColumns(...)`, or `withSchemaName(...)` are not data placeholders. Only use fixed table/column names or an application-level whitelist; never pass arbitrary request input as a table name.

### Optimizing in the Right Places

- Instantiate a single `SimpleJdbcInsert` per repository, finish configuration before using it, and then reuse it.
- Explicitly choose `usingColumns(...)` when you want to avoid inserting columns with defaults or generated values and want the code to reflect the schema.
- Use `executeBatch(...)` when you genuinely need multiple rows and have verified batch semantics on the driver.
- Choose a pooling `DataSource` in real applications where appropriate; `SimpleJdbcInsert` does not create a connection pool itself.
- Do not assume auto-generated SQL is always faster than handwritten SQL: actual costs lie in network/driver/database, indexing, transactions, locks, and batch sizes. Measure on your specific workload.

## 10. Common Errors, Causes, and Fixes

| Issue | Common Cause | How to Fix |
| --- | --- | --- |
| Spring cannot find the table/column or reports a metadata error | Wrong table name, schema, metadata permissions, or insufficient metadata from the driver. | Check `withTableName`, `withSchemaName`, permissions/schema, and casing rules; use `usingColumns` or consider disabling column metadata. |
| Table has a `created_at` column with a default, but insert fails due to `NULL` | The generated insert statement may be passing `NULL` into the column instead of omitting it from the statement. | Choose `usingColumns` with only the columns the application actively writes, letting the DB apply the default. |
| Passing `Map.of("fullName", ...)`, while the column is named `full_name` | Parameter key does not match the column name. | Use `"full_name"` or map explicitly from the Java property. |
| Using `Map.of` with a `null` value | Java immutable map factory does not allow `null`. | Use `HashMap` or `MapSqlParameterSource`; declare `Types` as needed. |
| `execute(...)` returns `1` and it is treated as `id=1` | Confusing affected row count with generated key. | Configure `usingGeneratedKeyColumns("id")` and call `executeAndReturnKey(...)`. |
| `executeAndReturnKey(...)` does not return a key or throws an error | Generated key column not specified, schema does not generate keys, driver lacks support, or multiple/non-numeric keys returned. | Check schema, `usingGeneratedKeyColumns`, and driver; for multiple or non-numeric keys use `executeAndReturnKeyHolder`. |
| Some drivers generate invalid SQL for names with uppercase letters, spaces, or keywords | Identifier quoting/casing rules differ. | Consider `usingQuotedIdentifiers()` with `usingColumns(...)` matching metadata exactly; test on the target DB. |
| Intermittent configuration errors after application startup | Configuration was modified after first compile/use or schema changed. | Create the instance and configure it completely once; if structure changes, create a separate appropriately configured instance. |
| Expecting `executeBatch` to return each row's ID | Batch API returns update counts. | Do not interpret `int[]` as a list of IDs; choose a key-retrieval approach verified to be supported by the driver. |
| Data appears inserted but disappears when the transaction rolls back | IDs can be generated before commit, while the transaction can still roll back. | Inspect transaction boundaries, limit side effects, and test rollback behavior. |

### Notable Detail About Default Values

The following two SQL statements behave **differently** if `created_at` has `DEFAULT CURRENT_TIMESTAMP`:

```sql
-- Column omitted: DB applies DEFAULT.
INSERT INTO customer (full_name, email)
VALUES ('An', 'an@example.test');

-- NULL passed: DB may reject due to NOT NULL; DEFAULT is not applied automatically.
INSERT INTO customer (full_name, email, created_at)
VALUES ('An', 'an@example.test', NULL);
```

Therefore, `usingColumns` both shortens the SQL statement and helps control default value semantics. Similarly, for an auto-generated ID column, do not pass the ID if the database is responsible for assigning it.

## 11. Recommended Tests

In an integration test environment using the same target database type and driver, verify:

1. **Successful insert:** call `execute(...)` with `full_name` and `email`, then query back the record; verify the affected row count matches.
2. **Generated key:** configure `usingGeneratedKeyColumns("id")`, call `executeAndReturnKey(...)`, and use the returned ID to read the record; do not assume the first ID equals `1`.
3. **Default column:** after inserting, confirm `created_at` was populated by the DB instead of being written as `NULL`.
4. **Wrong column name:** intentionally change to `usingColumns("missing_column")` in a dedicated test; ensure a clear error is raised rather than silently dropping data and appearing to succeed.
5. **NULL and constraint cases:** verify NOT NULL, unique, and other integrity errors are reported properly; do not expect Spring to bypass DB constraints.
6. **Transaction:** when executing multiple inserts in the same transaction and triggering a rollback error, verify data is not committed.
7. **Real database:** if using a different schema, quoted identifiers, special drivers, or batching, run integration tests on a DB as close to production as possible; H2 is only a convenient demo and does not guarantee identical metadata/SQL behavior across all RDBMSs.

You can use `JdbcTemplate.queryForObject` to check row counts or contents after inserting. Mocking `SimpleJdbcInsertOperations` helps test business logic, but **does not prove the generated SQL is valid** on a real database.

## 12. Self-Check Questions

**Question 1. Why can `SimpleJdbcInsert` insert rows without manually writing SQL?**

Because it knows the target table, the column list configured or discovered via metadata, and receives data keyed by column name; from this, it prepares `INSERT ... VALUES (...)` SQL and uses `JdbcTemplate` infrastructure to execute it.

**Question 2. How does `usingColumns` differ from `usingGeneratedKeyColumns`?**

`usingColumns` specifies **which columns receive values in the insert statement**. `usingGeneratedKeyColumns` declares **which auto-generated key columns should be retrieved as results**. Usually, the auto-generated `id` column is not included in `usingColumns`.

**Question 3. Why should a table with `created_at DEFAULT CURRENT_TIMESTAMP` usually omit `created_at` from `usingColumns`?**

So the SQL does not pass `NULL` or another value for that column, allowing the DB to apply the schema default.

**Question 4. Which method is right for getting the new ID: `execute(...)` or `executeAndReturnKey(...)`?**

`execute(...)` returns the number of affected rows. When `usingGeneratedKeyColumns("id")` is configured and the key is numeric, `executeAndReturnKey(...)` returns a `Number` representing the ID provided by the driver.

**Question 5. If the driver does not provide good column metadata, can `SimpleJdbcInsert` still be used?**

You can try declaring `usingColumns(...)` explicitly and, when appropriate, calling `withoutTableColumnMetaDataAccess()` to skip column metadata lookup. You still must test the actual driver, schema, and generated key retrieval.

## 13. Key Takeaways

```text
new SimpleJdbcInsert(dataSource)
    .withTableName("customer")                   // target table
    .usingColumns("full_name", "email")           // columns included in INSERT
    .usingGeneratedKeyColumns("id");              // key to retrieve (if needed)

insert.execute(params)                            // int: affected row count
insert.executeAndReturnKey(params)                // Number: 1 numeric key
insert.executeAndReturnKeyHolder(params)          // KeyHolder: key results
insert.executeBatch(params1, params2, ...)        // int[]: update counts
```

The core idea is: **declare table/column information once, and pass data by column name on each insert**, letting Spring build and execute the `INSERT`. `SimpleJdbcInsert` fits simple, readable, reusable inserts; for complex SQL, `JdbcTemplate` with explicit SQL statements remains a strong choice.
