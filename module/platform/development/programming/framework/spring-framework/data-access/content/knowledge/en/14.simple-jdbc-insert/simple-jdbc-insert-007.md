# Inserting Multiple Rows in Batches with `SimpleJdbcInsert`

> **Topic:** Spring Framework Data Access → `SimpleJdbcInsert` → Inserting Multiple Rows in Batches. Goal: configure one `SimpleJdbcInsert`, prepare multiple parameter sets, call `executeBatch(...)`, evaluate update counts, use transactions, and handle errors when only part of a batch succeeds.

## 1. What Problem Does Batch Insert Solve?

When importing a file with many items, writing line items of an order, or ingesting a list of records, you often need to create multiple rows in **the same table**. Looping `execute(...)` for each element causes many round-trips to JDBC and the database. Batch insert lets you supply **multiple parameter sets for the same `INSERT` structure** so the JDBC driver can process them more efficiently.

`SimpleJdbcInsert` (package `org.springframework.jdbc.core.simple`) uses a `DataSource` or `JdbcTemplate` and database metadata to build an `INSERT` statement with bound parameters. It provides APIs for single-row and multi-row inserts:

```java
// Inserts one row and returns the number of affected rows.
int execute(Map<String, ?> args);

// Inserts multiple rows and returns per-element update counts.
int[] executeBatch(Map<String, ?>... batch);
int[] executeBatch(SqlParameterSource... batch);
```

`SqlParameterSource` resides in `org.springframework.jdbc.core.namedparam`. Both `executeBatch` overloads accept records targeting the same table and column set, returning an `int[]` ordered to match the submitted elements.

**Do not confuse three concepts:**
- **JDBC batch:** one prepared SQL `INSERT` with multiple value sets; the driver may execute them individually or optimize by grouping commands.
- **Multi-row SQL:** a single statement such as `INSERT INTO t(a,b) VALUES (?,?),(?,?)`. `SimpleJdbcInsert.executeBatch` does not promise to always generate this SQL form.
- **Bulk load:** DB-specific mechanisms (such as `COPY` or `LOAD DATA`) may fit very large datasets better, but are outside the `SimpleJdbcInsert` API.

Batch inserts typically reduce overhead, though actual speedup depends on the driver, DB, indexes, triggers, batch size, and connection configuration. There is no guarantee a batch will be N times faster than N individual statements.

## 2. Example Table and `SimpleJdbcInsert` Configuration

Suppose we are inserting line items from an import session. Consider an H2-compatible illustrative schema:

```sql
CREATE TABLE order_item (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    import_id VARCHAR(64) NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    CONSTRAINT uq_import_line UNIQUE (import_id, line_no)
);
```

The `id` column is DB-generated. The remaining four columns hold data from each input row. The `UNIQUE(import_id, line_no)` constraint prevents duplicate line numbers within an import.

In a repository/writer class provided with a `DataSource`, configure:

```java
import javax.sql.DataSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public final class OrderItemWriter {
    private final SimpleJdbcInsert insert;

    public OrderItemWriter(DataSource dataSource) {
        this.insert = new SimpleJdbcInsert(dataSource)
            .withTableName("order_item")
            .usingColumns("import_id", "line_no", "sku", "quantity");
    }
}
```

This is an **integration snippet**; a complete class also needs a write method. `withTableName` selects the target table; `usingColumns` explicitly lists the columns appearing in the `INSERT` statement and excludes the DB-generated `id` column. Only use table/column names from trusted configuration; never pass user-submitted table names directly.

If the table resides in a separate schema, add `withSchemaName(...)`. Normally `SimpleJdbcInsert` reads `DatabaseMetaData` from the JDBC driver to build the statement. When metadata is incomplete, declare columns explicitly and consider `withoutTableColumnMetaDataAccess()` based on the actual DB and driver. Configure the instance **once** in the data access layer and reuse it; do not create a new instance per row.

Before calling the API, validate business-meaningful constraints: valid `import_id`, valid `sku` format, `quantity > 0`, and no duplicate `line_no` in the import payload. DB constraints are still necessary because concurrent errors or invalid data can slip past the application layer.

## 3. Option A — `executeBatch(Map<String, ?>...)`

Each `Map` holds column names and values for **one row**. Inside a method with the `insert` field available:

```java
import java.util.Map;

int[] counts = insert.executeBatch(
    Map.of(
        "import_id", "IMPORT-001",
        "line_no", 1,
        "sku", "BOOK-01",
        "quantity", 2
    ),
    Map.of(
        "import_id", "IMPORT-001",
        "line_no", 2,
        "sku", "PEN-05",
        "quantity", 4
    )
);
```

With H2 and straightforward valid inserts, the result is typically `[1, 1]`: two inputs, each reporting one inserted row. This is **reported by the driver**, not a constant fixed by Spring. In JDBC, an element may also carry the special value `Statement.SUCCESS_NO_INFO` (i.e., `-2`).

Notes:
- Keys must match the column names used by `SimpleJdbcInsert`; do not arbitrarily change to `importId` if the actual column is `import_id`.
- `Map.of(...)` disallows `null` values. If there are nullable columns, use `HashMap` or `MapSqlParameterSource`.
- Parameter values are bound via a prepared statement; there is no need to escape or concatenate values into SQL.
- Do not mix record types with different column structures into one `executeBatch`, because the API uses a single fixed-structure `INSERT` statement.

## 4. Option B — `executeBatch(SqlParameterSource...)`

`MapSqlParameterSource` is very useful when building parameters from DTOs, handling nulls, or declaring SQL types. Example inside a writer method:

```java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;

SqlParameterSource[] rows = {
    new MapSqlParameterSource()
        .addValue("import_id", "IMPORT-002")
        .addValue("line_no", 1)
        .addValue("sku", "MOUSE-01")
        .addValue("quantity", 3),

    new MapSqlParameterSource()
        .addValue("import_id", "IMPORT-002")
        .addValue("line_no", 2)
        .addValue("sku", "PAD-02")
        .addValue("quantity", 1)
};

int[] counts = insert.executeBatch(rows);
```

You can use `addValue("optional_note", null, java.sql.Types.VARCHAR)` when a nullable column needs an explicit SQL type. `BeanPropertySqlParameterSource` is another option when objects have JavaBean properties matching parameter names; pay close attention to camelCase property names vs. snake_case column names.

**Which option to choose?** `Map` is convenient when data is already in column-name → value form; `MapSqlParameterSource` gives better control over SQL types and nulls. Both invoke the same batch capability of `SimpleJdbcInsert`; there is no rule that "Option B is always faster".

## 5. Standalone Java 17 Example with Maven, Spring JDBC, and H2

The following example creates a table in in-memory H2, inserts three valid rows, and attempts another batch with a duplicate business key. The goal is to observe **counts**, post-commit data, and **rollback** when a batch fails.

Requirements: JDK 17+, Maven; uses `spring-jdbc:6.2.19` and `h2:2.3.232`. Structure:

```text
simplejdbc-batch/
├── pom.xml
└── src/main/java/demo/BatchInsertDemo.java
```


Create `src/main/java/demo/BatchInsertDemo.java`:

```java
package demo;

import java.util.Arrays;
import javax.sql.DataSource;

import org.springframework.dao.DataAccessException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.transaction.support.TransactionTemplate;

public final class BatchInsertDemo {
    private BatchInsertDemo() {
    }

    public static void main(String[] args) {
        DataSource ds = new DriverManagerDataSource(
            "jdbc:h2:mem:simplejdbc_batch;DB_CLOSE_DELAY=-1", "sa", ""
        );
        JdbcTemplate jdbc = new JdbcTemplate(ds);

        jdbc.execute(
            "CREATE TABLE order_item (" +
            "id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, " +
            "import_id VARCHAR(64) NOT NULL, " +
            "line_no INTEGER NOT NULL, " +
            "sku VARCHAR(64) NOT NULL, " +
            "quantity INTEGER NOT NULL CHECK (quantity > 0), " +
            "CONSTRAINT uq_import_line UNIQUE (import_id, line_no))"
        );

        SimpleJdbcInsert insert = new SimpleJdbcInsert(ds)
            .withTableName("order_item")
            .usingColumns("import_id", "line_no", "sku", "quantity");

        TransactionTemplate tx = new TransactionTemplate(
            new DataSourceTransactionManager(ds)
        );

        SqlParameterSource[] valid = {
            item("IMPORT-OK", 1, "BOOK-01", 2),
            item("IMPORT-OK", 2, "PEN-05", 4),
            item("IMPORT-OK", 3, "PAD-02", 1)
        };

        int[] counts = tx.execute(status -> {
            int[] result = insert.executeBatch(valid);
            requireExactlyOnePerItem(result, valid.length);
            return result;
        });

        System.out.println("validCounts=" + Arrays.toString(counts));
        System.out.println(
            "validRows=" + countRows(jdbc, "IMPORT-OK")
        );

        SqlParameterSource[] invalid = {
            item("IMPORT-BAD", 1, "MOUSE-01", 1),
            item("IMPORT-BAD", 1, "USB-02", 2)
        };

        try {
            tx.execute(status -> {
                int[] result = insert.executeBatch(invalid);
                requireExactlyOnePerItem(result, invalid.length);
                return result;
            });
        } catch (DataAccessException ex) {
            System.out.println("invalidBatch=ROLLED_BACK");
        }

        System.out.println(
            "invalidRows=" + countRows(jdbc, "IMPORT-BAD")
        );
    }

    private static SqlParameterSource item(
            String importId, int lineNo, String sku, int quantity) {
        return new MapSqlParameterSource()
            .addValue("import_id", importId)
            .addValue("line_no", lineNo)
            .addValue("sku", sku)
            .addValue("quantity", quantity);
    }

    private static void requireExactlyOnePerItem(
            int[] counts, int expectedSize) {
        if (counts.length != expectedSize) {
            throw new IllegalStateException(
                "Expected " + expectedSize + " counts, got " + counts.length
            );
        }

        for (int i = 0; i < counts.length; i++) {
            if (counts[i] != 1) {
                throw new IllegalStateException(
                    "Item " + i + " affected rows: " + counts[i]
                );
            }
        }
    }

    private static int countRows(JdbcTemplate jdbc, String importId) {
        Integer value = jdbc.queryForObject(
            "SELECT COUNT(*) FROM order_item WHERE import_id = ?",
            Integer.class,
            importId
        );
        if (value == null) {
            throw new IllegalStateException("COUNT(*) returned null");
        }
        return value;
    }
}
```

In the `simplejdbc-batch` directory, run:

```bash
mvn -q compile exec:java -Dexec.mainClass=demo.BatchInsertDemo
```

Program output lines (excluding Maven logs/messages if any):

```text
validCounts=[1, 1, 1]
validRows=3
invalidBatch=ROLLED_BACK
invalidRows=0
```

**Why does this output occur?** The three valid items create three rows. With H2, each item's count is `1`. `TransactionTemplate` only commits after both the batch and count verification complete. In the `IMPORT-BAD` batch, two rows share `(import_id, line_no)`, violating the unique constraint. Spring translates the JDBC error into an appropriate `DataAccessException` that exits `TransactionTemplate`, rolling back the entire batch; subsequently `COUNT(*)` for `IMPORT-BAD` is `0`.

**Key takeaway:** just because `executeBatch` throws an error does not mean the DB processed zero items. The driver may have executed part of the batch before reporting an error. In this example, **transaction rollback** is what enforces all-or-nothing atomicity. With other DBs/drivers, re-verify identity syntax, batch rules, exception translation, and update counts.

## 6. Interpreting the `int[]` Array Properly per JDBC

`executeBatch` returns counts as reported by the JDBC driver. `java.sql.Statement` defines special constants:

| Count | Meaning | Suggested Handling if Each Input Must Insert Exactly One Row |
| --- | --- | --- |
| `1` | Driver reports one row affected | Meets expectations for that item, provided the transaction succeeds |
| `0` | Driver reports zero rows affected | Must be explained by SQL/driver behavior and business rules |
| `> 1` | Driver reports multiple rows affected | Unusual for a normal single-row `INSERT`; investigate |
| `Statement.SUCCESS_NO_INFO` = `-2` | Command succeeded, row count **unknown** | Never treat as "-2 rows"; verify further depending on your contract |
| `Statement.EXECUTE_FAILED` = `-3` | Driver reports command failure inside the update-count array | Error must be handled/rolled back per requirements |

**Two different checking styles:**
1. Strict requirement *each input creates exactly one row*: verify `counts.length == input.length` and `count == 1` for every element. The example code uses this policy; `-2` does not prove the row count and is rejected.
2. Requirement *driver confirms successful execution even without knowing row counts*: `-2` can be accepted once semantics and reconciliation checks are agreed upon. You must still catch `DataAccessException` and manage transactions.

Never infer success solely from `counts.length`; never add `-2` into a row total; never assume `counts.length == N` means N rows committed. Some drivers throw `BatchUpdateException` (translated by Spring into `DataAccessException`) when a statement fails, instead of returning an array containing `-3`. Do not design code around only one error-reporting path.

## 7. Transactions Determine Whole-Batch vs. Partial Success

Clearly define your import contract:

- **All-or-nothing:** all rows commit together, or none commit. Wrap the entire `executeBatch` and count check inside **one transaction**.
- **Partial success:** each chunk commits separately so you do not have to redo the entire file. Persist which chunks/items have committed and design retries to avoid creating duplicates.
- **Multiple related tables:** you can use different writers/`SimpleJdbcInsert` instances in the **same transaction** for different tables, though write order must respect foreign keys; these remain separate batches.

In a Spring application with a transaction manager, a service can use:

```java
import org.springframework.transaction.annotation.Transactional;

@Transactional
public void importItems(SqlParameterSource[] rows) {
    if (rows.length == 0) {
        return;
    }

    int[] counts = insert.executeBatch(rows);
    requireExactlyOnePerItem(counts, rows.length);
}
```

**This is an integration snippet**, using the `insert` field and count-checking helper declared in the service/repository, not a standalone program. Under Spring's default rollback rules, an unchecked exception escaping a transaction-managed method triggers a rollback. For checked exceptions, configure `rollbackFor` if required by business logic. In standard proxy mode, calling a `@Transactional` method **from another method on the same instance** normally bypasses the interceptor; verify that transactions actually activate.

If you catch and swallow an exception **inside** the transactional method and return normally, the DB may commit the already-written steps. Place error handling outside the transaction boundary, or explicitly mark the transaction for rollback when appropriate.

## 8. Splitting Large Batches into Chunks

`SimpleJdbcInsert.executeBatch(...)` takes an array of elements and **has no separate batch size parameter** on the method. For large imports, split the array into reasonably sized chunks and benchmark them (for example, start with 200–1,000 rows/chunk; no single optimal size fits all DBs).

Assuming `all` is a prepared `SqlParameterSource[]` and `insert`, `tx`, and `requireExactlyOnePerItem` are the components from the example above, the following **additional illustration** executes all chunks in one transaction:

```java
import java.util.Arrays;

int chunkSize = 500;

tx.executeWithoutResult(status -> {
    for (int from = 0; from < all.length; from += chunkSize) {
        int to = Math.min(from + chunkSize, all.length);
        SqlParameterSource[] chunk = Arrays.copyOfRange(all, from, to);

        int[] counts = insert.executeBatch(chunk);
        requireExactlyOnePerItem(counts, chunk.length);
    }
});
```

If the final chunk fails, the overall transaction rolls back all earlier chunks as well. The trade-off is that long transactions can hold locks and generate large WAL/undo logs; for millions of rows, consider committing per chunk and explicitly modeling partial success.

Control your application's own memory usage: if you already loaded the entire file into a giant array, chunking at the API call **does not** eliminate the memory overhead of holding every row. For large datasets, read and validate in batches from the source and pick appropriate commit boundaries.

Even when chunking, you must still handle the same risks as small batches: mid-batch failures, `-2` counts, duplicates, timeouts, and retry behavior. Chunk size is also constrained by bind parameter limits, packet size, timeouts, and driver capabilities.

## 9. Can `executeBatch` Retrieve Generated IDs for Each Row?

**No.** `SimpleJdbcInsert.executeBatch(...)` returns `int[]` counts, with no overload returning `KeyHolder[]`. For a single row, another API is available:

```java
SimpleJdbcInsert singleInsert = new SimpleJdbcInsert(dataSource)
    .withTableName("order_item")
    .usingColumns("import_id", "line_no", "sku", "quantity")
    .usingGeneratedKeyColumns("id");

Number id = singleInsert.executeAndReturnKey(
    new MapSqlParameterSource()
        .addValue("import_id", "ONE-ROW")
        .addValue("line_no", 1)
        .addValue("sku", "BOOK-01")
        .addValue("quantity", 1)
);
```

This is an illustrative integration snippet; `dataSource` must be provided by the application. If you only need to insert many rows, you can **omit** `usingGeneratedKeyColumns` and let the DB generate `id` during `executeBatch`. If you strictly need the ID for **every** row, choose an approach verified on your DB/driver:
- Call `executeAndReturnKey` per row within a transaction (trading simplicity for multiple round-trips).
- Use DB-specific SQL such as `INSERT ... RETURNING` or the driver's JDBC batch generated-keys mechanism, and verify returned ID mapping.
- Use application-assigned keys (UUID, business key), or a staging table with correlation keys, avoiding sequential ID guessing.

Never rely on `MAX(id)`, and never assume IDs are contiguous or increase in batch order: sequences/identities, transaction rollbacks, and concurrency all create gaps.

## 10. Idempotency, Duplicate Data, and Retries

A batch insert can be resent due to client timeouts or lost network responses. If the DB committed before the connection dropped, retrying the entire batch can create duplicates. If the previous attempt rolled back, retrying may be the right move. **Never infer commit status merely from the client failing to receive a response.**

Safe designs typically include:
- A request key `import_id` and per-row key such as `(import_id, line_no)` backed by a `UNIQUE` constraint.
- An import status tracking table (e.g., `IN_PROGRESS`, `COMPLETED`, `FAILED`) or verification query by business key.
- A clear duplicate policy: reject, skip with reconciliation, or upsert.
- Reconciliation queries before retrying under your chosen consistency boundary; do not rely solely on "`SELECT` sees nothing so `INSERT`" because two concurrent requests can both see nothing.
- Retry only transient errors when impact, timeouts, and idempotency are understood; avoid infinite retries on constraint violations that cannot heal themselves.

`SimpleJdbcInsert` builds standard `INSERT` statements. If you need `ON CONFLICT DO NOTHING`, `ON DUPLICATE KEY UPDATE`, `MERGE`, or `RETURNING`, switch to DB-specific SQL with `JdbcTemplate`/`NamedParameterJdbcTemplate` and verify count semantics separately.

## 11. Performance and Choosing the Right Tool

| Scenario | Appropriate API |
| --- | --- |
| Insert one row without needing a key | `SimpleJdbcInsert.execute` |
| Insert one row and retrieve a generated key | `executeAndReturnKey` or `executeAndReturnKeyHolder` |
| Insert many rows into the same table with stable columns | `SimpleJdbcInsert.executeBatch` |
| Batches needing complex SQL, custom SQL, or `batchSize` control | `JdbcTemplate.batchUpdate`/`NamedParameterJdbcTemplate.batchUpdate` |
| Multi-key retrieval, upserts, conflict handling, or specialized bulk loads | DB/driver-specific SQL or tools, requiring benchmarking and integration tests |

Measure throughput, latency, CPU, commit time, lock waits, connection count, and memory with the **production driver**. A proper connection pool must be configured in real applications; `DriverManagerDataSource` in the demo only simplifies quick execution. Drivers may have options to rewrite batches into multi-row SQL, which alters update counts: measure and test instead of assuming.

Making chunks too large can hit packet limits, parameter limits, lock contention, and transaction log limits. Start with a moderate size and measure based on row width, indexes/triggers, and system concurrency.

## 12. Common Mistakes and How to Avoid Them

**A. Looping `execute` and calling it a batch.**

```java
for (Map<String, ?> row : rows) {
    insert.execute(row);
}
```

This performs multiple individual inserts; for a JDBC batch, build an array of `Map` or `SqlParameterSource[]` and call `executeBatch` once per chunk. However, a single-row loop is still useful when you need a generated key immediately per row and data volume is small.

**B. Creating a new `SimpleJdbcInsert` for each record.** It has to initialize/inspect metadata repeatedly, adding overhead and losing reusability benefits. Configure once per table and reuse it afterward.

**C. Wrong keys/columns, missing `NOT NULL`, confusing camelCase with snake_case.** Set `usingColumns` explicitly, verify key names and type mappings, and run integration tests against the real schema.

**D. Misreading counts.** `-2` means row count unknown, not an error of minus two rows; `-3` is `EXECUTE_FAILED` if returned in counts by the driver; array length alone does not prove commit succeeded. Validate according to business requirements.

**E. Omitting a transaction and assuming a batch rolls everything back automatically.** JDBC may succeed partially before reporting an error. Transaction boundaries and exception handling determine what data persists.

**F. Treating `executeBatch` as a generated-key retrieval API.** It returns `int[]`, not a list of IDs. Choose a different strategy if keys are needed.

**G. Retrying an entire batch after a timeout without an idempotency key.** This can create duplicates if the transaction already committed. Unique constraints and import state provide the foundation for safe retries.

**H. Splitting into chunks while still holding every row in RAM.** Also split **how you read from the source** if files are very large; keep transaction strategy independent from memory strategy.

## 13. Testing Checklist

| Test Case | What to Verify |
| --- | --- |
| Valid 3-row batch | Exactly 3 rows inserted; `[1,1,1]` in H2 demo |
| Empty batch | Caller handles early, avoiding unnecessary DB calls |
| Missing `NOT NULL` column | Exception raised; no bad commit |
| `quantity <= 0` | Constraint or validation rejects it |
| Two rows with same `import_id + line_no` | Unique violation; shared transaction rolls back |
| Driver returns `SUCCESS_NO_INFO` | Policy handles `-2` with accurate semantics |
| Large batch split into 2–3 chunks, last chunk fails | Shared transaction rolls back all; per-chunk transactions record partial success |
| Two concurrent requests with same business key | Constraint protects data; verify retry behavior |
| Timeout after DB may have committed | Mechanism exists to check state before retrying |
| Rows needing auto-generated IDs | IDs are not inferred from `int[]` |
| Non-H2 DB | Verify SQL types, metadata, batch counts, exception translation, and rollback on the real driver |

Integration tests on the exact target DB/driver are essential, especially when exact counts are required or mid-batch element failures must be handled. You can use testcontainers and transaction isolation matching production.

## 14. Key Takeaways

Standard workflow: **identify columns and business keys → configure a reusable `SimpleJdbcInsert` → convert each row to `Map`/`SqlParameterSource` → call `executeBatch` → verify each count → commit/rollback in a transaction → manage retries/idempotency**. Before optimizing with large chunks, get constraints, per-row results, and transaction boundaries right.
