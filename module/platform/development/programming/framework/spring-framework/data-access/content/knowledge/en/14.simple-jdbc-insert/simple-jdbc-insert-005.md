# SimpleJdbcInsert: `executeAndReturnKey()` and `executeAndReturnKeyHolder()`

## 1. The Problem: Inserting and Retrieving a Database-Generated Value Together

In many tables, the primary key is not sent by the application when adding a record, but is generated automatically by the database—for example, an `id BIGINT GENERATED ... AS IDENTITY` or `AUTO_INCREMENT` column. After inserting a customer, the application needs the exact `id` of the newly created record to create relationships, return an API response, or emit a business event.

`SimpleJdbcInsert` in Spring JDBC helps perform `INSERT`s without writing the full SQL or managing `PreparedStatement` boilerplate. It uses table information via JDBC metadata (or explicit column configuration) to construct the statement. The two core methods are:

- **`executeAndReturnKey(...)`:** inserts **one** record and retrieves **a single auto-generated numeric key** via the `Number` return type.
- **`executeAndReturnKeyHolder(...)`:** inserts **one** record and returns a `KeyHolder` object, giving access to the structure of values returned by the database/driver, including multi-column or non-numeric keys.

The concept of a "generated key" refers to values created/returned by the database through the JDBC generated keys mechanism. It **does not automatically mean every `DEFAULT` column, every trigger-generated field, or the entire row after INSERT**. Which columns are actually returned depends on the database, driver, and `usingGeneratedKeyColumns(...)` configuration.

Business example:

~~~sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(160) NOT NULL
);
~~~

When adding a customer, only `full_name` and `email` are sent; the database generates `id`. The value you need is the `id` of the **exact INSERT operation just executed**, not `MAX(id)` in the table (which is wrong under concurrent transactions).

## 2. Configuration Requirements and Mechanism

A typical `SimpleJdbcInsert` is created as follows:

~~~java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("customer")
        .usingColumns("full_name", "email")
        .usingGeneratedKeyColumns("id");
~~~

Explanation of each part:

1. `new SimpleJdbcInsert(dataSource)`: uses the persistence layer's `DataSource`; Spring manages connections and translates JDBC errors into the `DataAccessException` hierarchy.
2. `withTableName("customer")`: target table name. If needed, you can configure `withSchemaName(...)` or `withCatalogName(...)` to pinpoint the table.
3. `usingColumns("full_name", "email")`: specifies **the input columns receiving values** in the INSERT. Do not include the auto-generated `id` in this list.
4. `usingGeneratedKeyColumns("id")`: requests retrieval of the database-generated key in column `id`. This step is required when using either method that returns generated keys.

Conceptually, Spring prepares SQL equivalent to:

~~~sql
INSERT INTO customer (full_name, email) VALUES (?, ?);
~~~

After execution, Spring asks the JDBC driver to provide generated keys (typically via `Statement.getGeneratedKeys()`, or a database-metadata-appropriate path), and returns `Number` or `KeyHolder`. The application does not need to run `SELECT MAX(id)` or guess IDs from a global sequence.

**Note on metadata:** `usingColumns(...)` is not always mandatory because Spring can read table columns; however, declaring them explicitly avoids accidentally pulling unwanted columns into INSERT when the schema evolves. If using `withoutTableColumnMetaDataAccess()`, you must declare the appropriate input columns and generated keys, and test against the real driver. All configuration methods should be called **before** the object is compiled/first used. A configured instance can be reused across many calls.

## 3. Method Signatures and How to Choose

Overloads to remember on `SimpleJdbcInsert`:

~~~java
Number executeAndReturnKey(Map<String, ?> args);
Number executeAndReturnKey(SqlParameterSource parameterSource);

KeyHolder executeAndReturnKeyHolder(Map<String, ?> args);
KeyHolder executeAndReturnKeyHolder(SqlParameterSource parameterSource);
~~~

| Criterion | `executeAndReturnKey(...)` | `executeAndReturnKeyHolder(...)` |
|---|---|---|
| Return type | `java.lang.Number` | `org.springframework.jdbc.support.KeyHolder` |
| Best suited for | A single numeric auto-generated key, e.g., an identity ID | Inspecting returned key sets, multiple generated columns, or non-numeric keys |
| Accessing the result | `Number.longValue()` / `intValue()` per schema | `getKey()`, `getKeyAs(Class<T>)`, `getKeys()`, `getKeyList()` |
| Input | `Map<String, ?>` or `SqlParameterSource` | `Map<String, ?>` or `SqlParameterSource` |
| Records per call | One INSERT | One INSERT |
| Guaranteed to have a key? | Depends on database/driver/configuration support | Returns a `KeyHolder` to inspect; it may contain no data |

Both can accept a `Map` if data is already in column-name → value pairs, or a `SqlParameterSource` if you want to leverage `MapSqlParameterSource`, `BeanPropertySqlParameterSource`, and SQL type declarations. Parameter names must match input column names; `Map.of(...)` disallows null keys/values, so when passing nulls use `MapSqlParameterSource.addValue("column", null, Types.VARCHAR)` or a null-tolerant `Map`.

**Important boundary:** calling `executeAndReturnKey(...)` followed by `executeAndReturnKeyHolder(...)` on the same data will create **two separate records**, because each call executes an independent INSERT. Choose one method per record you want to add.

## 4. Standalone Java 17+ Example: All Four Overloads

This example uses Spring JDBC 6.2.12, H2 2.3.232, Maven, and Java 17. The program creates a fresh in-memory database on each run, inserts four customers—demonstrating each overload once—and then verifies the data.

**`src/main/java/demo/GeneratedKeysDemo.java`**

~~~java
package demo;

import java.util.List;
import java.util.Map;
import java.util.Objects;

import org.h2.jdbcx.JdbcDataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;
import org.springframework.jdbc.support.KeyHolder;

public class GeneratedKeysDemo {
    public static void main(String[] args) {
        JdbcDataSource dataSource = new JdbcDataSource();
        dataSource.setURL(
                "jdbc:h2:mem:generated_keys_demo;DB_CLOSE_DELAY=-1");
        dataSource.setUser("sa");

        JdbcTemplate jdbc = new JdbcTemplate(dataSource);
        jdbc.execute("""
                CREATE TABLE customer (
                    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
                    full_name VARCHAR(100) NOT NULL,
                    email VARCHAR(160) NOT NULL
                )
                """);

        SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
                .withTableName("customer")
                .usingColumns("full_name", "email")
                .usingGeneratedKeyColumns("id");

        // 1) executeAndReturnKey(Map): returns a Number.
        Number keyFromMap = Objects.requireNonNull(
                insert.executeAndReturnKey(Map.of(
                        "full_name", "An",
                        "email", "an@example.test")),
                "Database did not return the generated key");
        System.out.println("KEY_MAP=" + keyFromMap.longValue());

        // 2) executeAndReturnKey(SqlParameterSource).
        SqlParameterSource binh = new MapSqlParameterSource()
                .addValue("full_name", "Binh")
                .addValue("email", "binh@example.test");
        Number keyFromSource = Objects.requireNonNull(
                insert.executeAndReturnKey(binh),
                "Database did not return the generated key");
        System.out.println("KEY_SOURCE=" + keyFromSource.longValue());

        // 3) executeAndReturnKeyHolder(Map): KeyHolder.
        KeyHolder holderFromMap = insert.executeAndReturnKeyHolder(
                Map.of("full_name", "Chi",
                       "email", "chi@example.test"));
        Number keyFromHolderMap = Objects.requireNonNull(
                holderFromMap.getKey(), "KeyHolder contains no single key");
        System.out.println("HOLDER_MAP=" + keyFromHolderMap.longValue());

        // 4) executeAndReturnKeyHolder(SqlParameterSource).
        SqlParameterSource dung = new MapSqlParameterSource()
                .addValue("full_name", "Dung")
                .addValue("email", "dung@example.test");
        KeyHolder holderFromSource =
                insert.executeAndReturnKeyHolder(dung);

        Number keyFromHolderSource = Objects.requireNonNull(
                holderFromSource.getKey(), "KeyHolder contains no single key");
        Map<String, Object> keyColumns = Objects.requireNonNull(
                holderFromSource.getKeys(), "No generated-key row");

        System.out.println(
                "HOLDER_SOURCE=" + keyFromHolderSource.longValue());
        System.out.println(
                "HOLDER_ROWS=" + holderFromSource.getKeyList().size());
        System.out.println("HOLDER_FIELDS=" + keyColumns.size());

        List<String> names = jdbc.queryForList(
                "SELECT full_name FROM customer ORDER BY id", String.class);
        System.out.println("NAMES=" + names);
    }
}
~~~

**Run from the directory containing `pom.xml`:**

~~~bash
mvn -q compile exec:java "-Dexec.mainClass=demo.GeneratedKeysDemo"
~~~

**Program output on a fresh in-memory H2 database:**

~~~text
KEY_MAP=1
KEY_SOURCE=2
HOLDER_MAP=3
HOLDER_SOURCE=4
HOLDER_ROWS=1
HOLDER_FIELDS=1
NAMES=[An, Binh, Chi, Dung]
~~~

Explanation: H2 generates identity values starting at 1 in a fresh table. Each call inserts one row; all four IDs are read from the corresponding INSERT result. With `usingGeneratedKeyColumns("id")`, H2 returns one generated key column per INSERT, so `getKeyList()` on the last call contains one map with one column. Key names (e.g., `ID` vs. `id`) and sometimes specific numeric types **do not follow a single rule across drivers**, so the example prints only the field count rather than hardcoding column name casing.

In the code, `Objects.requireNonNull(...)` catches cases where the driver does not return a key early. If the driver returns multiple keys for a row, `holder.getKey()` is not the right API; use `getKeys()` as shown in the next section.

## 5. Reading `KeyHolder` Correctly

`KeyHolder` models generated key results using a **`List<Map<String, Object>>`** structure: each list element is a set of columns returned for a row.

| Method | Key Characteristics to Remember |
|---|---|
| `holder.getKey()` | Reads a single **numeric** value when the result has only **one key row and one key column**; returns `Number` (possibly null if no key); throws `InvalidDataAccessApiUsageException` if multiple values exist |
| `holder.getKeyAs(MyType.class)` | Similar to `getKey()` but requires the value to match `MyType` (e.g., `UUID.class` if the driver actually returns a `UUID`); does not convert strings to that type |
| `holder.getKeys()` | Returns a `Map<String, Object>` containing the key columns of **a single row**; allows multiple columns in the map; may return null if empty, and errors if the list has multiple rows |
| `holder.getKeyList()` | Returns `List<Map<String, Object>>` to inspect all key rows returned by the driver; normally a single `SimpleJdbcInsert` call inserts one row |

If a table has two DB-generated fields, such as `id` and `public_token`, and the driver supports returning both when configured with `usingGeneratedKeyColumns("id", "public_token")`, inspect the map:

~~~java
// Illustration: "holder" comes from executeAndReturnKeyHolder(...).
Map<String, Object> generated = holder.getKeys();
if (generated == null || generated.isEmpty()) {
    throw new IllegalStateException("Driver did not return generated keys");
}

for (Map.Entry<String, Object> item : generated.entrySet()) {
    System.out.println(item.getKey() + " = " + item.getValue());
}
~~~

This is an **illustrative snippet assuming a `holder` variable exists in context**, not a standalone Java program. Do not assume map keys always follow one casing, do not assume map iteration order matches column order, and do not assume the driver will definitely return every column populated by DEFAULT or triggers. Verify metadata and actual results on each DB system.

**Commonly confused cases:**

- If `getKeys()` contains multiple entries (multiple columns), `getKey()` will throw an error even if a desired `id` column is present; look up the exact entry from the map after confirming the column name.
- If `getKeyList()` has multiple maps (multiple rows), `getKeys()` may throw `InvalidDataAccessApiUsageException` because it only serves a single row. Multi-row results are not the default behavior of a normal `SimpleJdbcInsert.executeAndReturnKeyHolder(...)` call.
- For non-numeric keys like UUID, prefer `getKeyAs(UUID.class)` **only if** the driver returns an actual `UUID` instance; otherwise, read `getKeys()` and convert according to the actual runtime type.
- `getKeyAs(Long.class)` does not automatically convert `BigDecimal` or `BigInteger` into `Long`; for standard numeric IDs, read `Number` and convert per your schema after checking value bounds.

## 6. Usage in DAOs/Services and Transactions

In a Spring application, configure `SimpleJdbcInsert` once in the repository/DAO layer (constructor or bean initialization), and reuse it:

~~~java
// Illustrative snippet in CustomerRepository; DataSource is injected.
private final SimpleJdbcInsert insertCustomer;

public CustomerRepository(DataSource dataSource) {
    this.insertCustomer = new SimpleJdbcInsert(dataSource)
            .withTableName("customer")
            .usingColumns("full_name", "email")
            .usingGeneratedKeyColumns("id");
}

public long create(String name, String email) {
    Number key = insertCustomer.executeAndReturnKey(
            new MapSqlParameterSource()
                    .addValue("full_name", name)
                    .addValue("email", email));
    if (key == null) {
        throw new IllegalStateException(
                "Insert succeeded without a generated id");
    }
    return key.longValue();
}
~~~

These are **components of a class** that need to be placed in a full class with appropriate imports, not a standalone runnable file. Service call:

~~~java
// Illustrative snippet in a Spring-managed service.
@Transactional
public long registerCustomer(String name, String email) {
    long newId = customerRepository.create(name, email);
    auditRepository.writeRegistration(newId);
    return newId;
}
~~~

`@Transactional` requires a properly configured transaction manager and calls routed through a Spring proxy; self-invocation on the same object normally bypasses the transaction proxy. Transactions govern the scope of data changes per rollback configuration; **generated IDs may not be reused after a rollback**, because sequences/identities do not necessarily roll back. Returning an ID does not prove the transaction ultimately committed.

The returned key is the result of the exact INSERT just executed via JDBC, allowing accurate relationship building even when multiple requests create records concurrently. Avoid `SELECT MAX(id)` or assuming an `execute(...)` call returning an affected row count can substitute for a generated key.

## 7. When Not to Use It or When Further Checks Are Needed

**Application-generated keys:** if the application generates a UUID/ULID before inserting and passes it straight into the table, you can use `execute(...)` (returning the affected row count) without necessarily using generated key retrieval. The two methods in this lesson are for values that need to be returned by the database/driver.

**Multiple generated columns:** `executeAndReturnKeyHolder(...)` is the right structural choice, but it does not guarantee the driver returns every column. Some DBs only return the identity column; others support `RETURNING` or differ in retrieval behavior. Run integration tests on the **production database** and verify the returned column list.

**Table/column names and DB permissions:** configured table/column names must match the actual schema. Identifiers are not bound via `?`, so never pass untrusted input strings into table/column configuration. For case-sensitive or keyword-colliding identifiers, consider `usingQuotedIdentifiers()` and ensure exact identifier spelling.

**Nulls and data types:** when passing null values, `MapSqlParameterSource.addValue("email", null, Types.VARCHAR)` passes explicit type metadata; meanwhile, the DB will reject it if the column is `NOT NULL`. Input errors or constraint violations are INSERT failures, not evidence that generated keys are broken.

**Batch insert:** `SimpleJdbcInsert.executeBatch(...)` returns affected row counts (`int[]`), **not a `KeyHolder` per element** via the two APIs discussed here. Do not assume batch execution yields a corresponding list of IDs. When you must retrieve IDs for multiple records, choose an API/design supported by the driver and verify ordering, transactions, and performance.

**Performance:** retrieving generated keys may introduce extra work at the driver/DB layer. Optimize after measuring on the real system; driver support for key retrieval matters more than extrapolating performance from an H2 example.

## 8. Common Errors, Causes, and Fixes

| Symptom | Possible Cause | What to Check |
|---|---|---|
| No key received / `null` returned | Forgot `usingGeneratedKeyColumns(...)`, table does not generate keys, driver lacks support or returns empty | Check identity/default DDL, column configuration, JDBC driver, and `KeyHolder.getKeyList()` |
| `InvalidDataAccessApiUsageException` when calling `getKey()` | `KeyHolder` contains multiple columns/rows or configuration returns multiple keys | Use `getKeys()` (single row) or `getKeyList()` (multiple rows), pick key by name |
| Type error when retrieving UUID/string | Used `executeAndReturnKey()` or `getKey()`, which expect a `Number` | Use `executeAndReturnKeyHolder()` and `getKeyAs(...)` when types match, or extract from `getKeys()` |
| Map missing parameters or INSERT reports null column | Missing `full_name`/`email`, wrong column name, `usingColumns` mismatch | Log and verify configuration metadata, input, and table constraints |
| Non-contiguous IDs despite inserts/rollbacks | Identity/sequence already allocated numbers, transaction rolled back, or concurrent transactions | Treat IDs as unique identifiers, do not require sequential continuity |
| Same data appears twice | Called both methods on the same input | Each method executes an INSERT; choose only one |
| Works on H2 but fails on real DB | Differences in schema, generated key types, or `getGeneratedKeys` support | Write integration tests using the production driver and DB |
| Mistaking `getKeys()` for returning the entire record | JDBC only returns the generated columns provided by the driver | Use `SELECT ... WHERE id = ?` when you need full record data after inserting |

Spring JDBC translates `SQLException` into the `DataAccessException` hierarchy; the application must handle duplicate keys, constraint violations, connection issues, or missing permissions like any other DB operation. For multi-table workflows, set proper transaction boundaries so related data commits or rolls back consistently.

## 9. Checklist and Practice Exercises

**Checklist when inserting a record and retrieving its ID:**

1. The real table has a key-generation mechanism and the driver supports reading generated keys.
2. `withTableName`, `usingColumns`, and `usingGeneratedKeyColumns` match the schema; input does not supply the identity column itself.
3. Does the business logic need **one numeric key** or **a set of generated values**? Choose the right method.
4. For `Number`/`KeyHolder`, check for null or key count before casting/converting; use data types compatible with the schema.
5. Define transaction boundaries and test failed inserts, rollbacks, null inputs, and concurrency.
6. Run integration tests with the real DB and JDBC driver to confirm returned columns, value types, and casing.

**Practice exercises:**

1. Remove `usingGeneratedKeyColumns("id")` from the H2 example; observe the error/behavior change and explain the configuration requirement.
2. Rewrite the `Chi` insert to read the generated key using `holder.getKeys()`; inspect the key column map returned by H2.
3. Create a table with a database-generated `UUID` key (depending on the DBMS), test `getKeyAs(UUID.class)` and `getKeys()`; note the exact type the driver returns.
4. Place customer creation and audit logging inside the same transaction; deliberately fail the audit step to verify rollback even after an identity value was allocated.
5. Insert two customers concurrently; explain why `SELECT MAX(id)` cannot substitute for the key returned by each individual INSERT.
