# @Repository and Component Registration in the Spring IoC Container

## 1. What Problem Does This Lesson Solve?

In a Spring application, the data layer usually contains classes responsible for accessing the database: executing SQL with Spring JDBC, calling a JPA `EntityManager`, or using a repository generated by Spring Data. Writing query logic correctly in a class is still **not enough** for the application to use it automatically: Spring must know the class needs to be managed, create the bean, and provide that bean to dependent components.

For example, `CustomerService` needs `CustomerRepository` to find customers:

~~~text
CustomerService
      │ depends on CustomerRepository
      ▼
CustomerRepository (interface)
      ▲
      │ implements
JdbcCustomerRepository ----> JdbcTemplate ----> DataSource ----> Database
      ^
      │ @Repository + component scanning
Spring IoC Container creates, manages, and injects bean
~~~

Two key questions:

1. **What is the role of `@Repository`?** This annotation denotes a data access layer component, is a specialization of `@Component`, and can serve as an identification point for persistence exception translation.
2. **How does that object actually become a Spring bean?** A bean registration mechanism is required, typically component scanning or explicit declaration with `@Bean`. Writing `@Repository` on a class that Spring does not scan/register **does not automatically create a bean**.

After this lesson, you should be able to distinguish annotation metadata, bean definition, bean instance, dependency injection, exception translation, and Spring Data-generated repositories.

## 2. What Is `@Repository` and How Does It Differ from `@Component`?

`@Repository` belongs to the `org.springframework.stereotype` package. It is typically placed on a **data access implementation class** (DAO/repository), for example:

~~~java
@Repository
public class JdbcCustomerRepository implements CustomerRepository {
    // Methods using JdbcTemplate to access data
}
~~~

As a stereotype, `@Repository` is meta-annotated with `@Component`. Because of this, the default component scanner can detect classes annotated with `@Repository` just like classes annotated with `@Component`. However, the annotation name also expresses an **architectural responsibility**: this is a component in the persistence/data access layer.

| Annotation | Typically used for | Relation to bean registration |
| --- | --- | --- |
| `@Component` | General Spring component not belonging to a specialized stereotype | Can be discovered by component scanning |
| `@Repository` | Data access layer, DAO, persistence adapter | Specialized `@Component`; plays a role in exception translation |
| `@Service` | Business logic, use case orchestration | Specialized `@Component` |
| `@Controller` / `@RestController` | Web/controller layer | Recognized by Spring with additional web semantics |
| `@Bean` | Factory method providing a bean | Registered through the configuration containing that method |
| `@Entity` (JPA) | Entity data type mapped by ORM | **Does not** turn the entity into a component bean like `@Repository` |

Do not use `@Repository` merely so "Spring finds the class" when it holds business logic. Using the right stereotype helps readers and tools/AOP distinguish roles. By itself, `@Repository` **does not** implement SQL, connect to a database, open transactions, create tables, auto-build CRUD, or guarantee thread-safe methods.

**Three distinct layers of meaning:**

- **Annotation on source code:** metadata describing the class's role.
- **Bean definition in the container:** information Spring stores on how to create the bean, its scope, name, and dependencies.
- **Bean instance:** the actual object instantiated/managed by Spring, which may be wrapped in a proxy depending on configuration.

Adding an annotation is a common condition for discovery; having a bean definition is the condition for the container to manage the object. Do not conclude "annotation present = already injected everywhere".

## 3. Registering `@Repository` in the Container via Component Scanning

### 3.1. Mechanism from Class to Bean

When `@ComponentScan` includes the package containing the repository class, Spring scans the classpath for matching classes, applies default filters, registers bean definitions, and then creates beans when needed according to lifecycle/scope.

~~~java
@Configuration
@ComponentScan(basePackages = "com.example.shop")
public class AppConfig {
}
~~~

If `JdbcCustomerRepository` lives under `com.example.shop.data`, it is a scan candidate. If it lives outside the scanned packages, merely adding `@Repository` will not let Spring find the class automatically.

A way to configure scanning that relies less on raw package strings is to use a marker class:

~~~java
@Configuration
@ComponentScan(basePackageClasses = JdbcCustomerRepository.class)
class AppConfig {
}
~~~

Here Spring takes the package of `JdbcCustomerRepository` as the scan root. If services live in a different package not beneath this one, you must widen the scan scope or register the service separately. Choose the root package deliberately to avoid scanning unrelated classes.

**Logical flow:**

~~~text
Application initializes ApplicationContext
    │
    ├─ reads @Configuration / configuration sources
    │
    ├─ processes @ComponentScan
    │      └─ discovers @Repository class (via @Component meta-annotation)
    │
    ├─ registers BeanDefinition, e.g., "jdbcCustomerRepository"
    │
    ├─ resolves constructor dependencies (JdbcTemplate, ...)
    │
    └─ instantiates/completes bean, applies post-processors/proxies when present
           └─ CustomerService receives a CustomerRepository bean
~~~

This is a conceptual model; actual bean instantiation timing can vary due to lazy initialization, scope, or specific configuration.

### 3.2. In Spring Boot

`@SpringBootApplication` includes component scanning. By default, the application class's package and its subpackages form the natural scan area.

~~~text
com.example.shop
├── ShopApplication.java        // @SpringBootApplication
├── service
│   └── CustomerService.java    // @Service
└── data
    └── JdbcCustomerRepository.java // @Repository
~~~

This layout usually works without writing an explicit `@ComponentScan`. If `ShopApplication` is placed in `com.example.shop.web` while the repository is in `com.example.shop.data` (a sibling package), default scanning may miss the repository. The proper fix is usually to place the application in a common root package or explicitly declare the scan scope, rather than adding redundant annotations to the repository.

`@ComponentScan` only determines which component candidates are discovered; it **does not** automatically configure a `DataSource`, create schemas, or enable JPA. In Boot, providing `DataSource`, `JdbcTemplate`, entity managers, etc., depends on the corresponding starters, auto-configuration, and properties.

### 3.3. Bean Names and Lifecycle Scope

Given the class:

~~~java
@Repository
public class JdbcCustomerRepository {
}
~~~

the default bean name is typically `jdbcCustomerRepository` when using the standard bean-name generator. You can assign an explicit name:

~~~java
@Repository("customerSqlRepository")
public class JdbcCustomerRepository {
}
~~~

The name is only a bean identifier; data access capability is determined by the code and its collaborators. The default scope of stereotype components is `singleton` **per Spring container**, which does not mean one shared instance across all JVMs or all deployments.

A singleton repository should hold stable dependencies (such as `final JdbcTemplate`) rather than storing per-request state in mutable fields. `JdbcTemplate` is designed to be shared once configured; `Connection` or a JPA `EntityManager` has different lifecycle requirements and should not be arbitrarily held in a field of a singleton repository.

`@Scope("prototype")` can be applied when genuinely necessary, but it is not a default solution for data access or concurrency. Changing scope also changes how lifecycle and dependencies are managed.

## 4. Explicit Bean Registration Using `@Bean`

Component scanning is not the only path. A repository class can omit `@Repository` and still become a bean if a `@Bean` method returns it and the configuration is loaded:

~~~java
public final class JdbcCustomerRepository implements CustomerRepository {
    private final JdbcTemplate jdbc;

    public JdbcCustomerRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    // Implement CustomerRepository methods...
}
~~~

~~~java
@Configuration
public class RepositoryConfig {
    @Bean
    public CustomerRepository customerRepository(JdbcTemplate jdbc) {
        return new JdbcCustomerRepository(jdbc);
    }
}
~~~

**The two snippets above illustrate explicit registration; a complete runnable class is in Section 7.** Spring invokes the factory method to create the `customerRepository` bean and supplies `JdbcTemplate` automatically if a matching bean exists. Note: when the implementation class **does not have** `@Repository` and is registered only via `@Bean`, the bean does not automatically carry the `@Repository` stereotype for mechanisms targeting that annotation. If you want stereotype-based exception translation, appropriate configuration and annotation are required.

When to prefer `@Bean`: creating objects from third-party libraries whose annotations you cannot edit, creating adapters requiring special configuration, or wanting explicit factory control. There is no need to force every component through scanning.

**Avoid duplicate registration:** if you both scan `@Repository JdbcCustomerRepository` and declare a `@Bean` method creating another `JdbcCustomerRepository`, the container may hold **two beans of the same type**. When injecting a `CustomerRepository` without disambiguation criteria, Spring may fail because it cannot determine a unique candidate. Register beans using one clear strategy per implementation, or disambiguate explicitly when multiple implementations are intentional.

Other registration mechanisms such as `@Import`, XML configuration, bean definition registration APIs, or programmatic registration also exist. All of them must be integrated into the proper `ApplicationContext`; do not confuse them with instantiating objects via `new` in business code.

## 5. Dependency Injection: Why Does the Service Receive the Repository?

Suppose there is an interface:

~~~java
public interface CustomerRepository {
    Customer findById(long id);
}
~~~

and an implementation registered via `@Repository` or `@Bean`. The service should depend on the abstraction:

~~~java
@Service
public class CustomerService {
    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Customer load(long id) {
        return repository.findById(id);
    }
}
~~~

Spring inspects the constructor parameter and selects a bean compatible with `CustomerRepository`. With **a single constructor**, Spring does not require `@Autowired` on the constructor. Constructor injection has key advantages: required dependencies are explicit, fields can be `final`, and it is easy to instantiate the service in unit tests with a fake repository.

If you do:

~~~java
CustomerService service = new CustomerService(new JdbcCustomerRepository(...));
~~~

then an object created with `new` sits outside Spring's management pipeline (unless you explicitly register/insert it into the container). It remains a normal Java object, but Spring does not automatically apply bean post-processing or proxying to that instance.

### Multiple Beans for the Same Interface

Suppose both `JdbcCustomerRepository` and `CachedCustomerRepository` are Spring beans implementing `CustomerRepository`. If Spring cannot pick a single candidate, injection by type alone is insufficient.

**Select with a qualifier:**

~~~java
@Service
public class CustomerService {
    private final CustomerRepository repository;

    public CustomerService(
            @Qualifier("jdbcCustomerRepository") CustomerRepository repository) {
        this.repository = repository;
    }
}
~~~

This snippet is illustrative and assumes the actual bean name is `jdbcCustomerRepository`. Besides `@Qualifier`, you can mark one implementation with `@Primary` if it is a sensible default. Avoid relying on scan order; do not use bean names as a workaround for ambiguous dependency architecture.

**Distinguish common errors:**

- `NoSuchBeanDefinitionException`: no matching bean found at a direct lookup point, or no candidate for a dependency.
- `UnsatisfiedDependencyException`: a bean being initialized cannot have its dependency satisfied; the root cause may be that the repository was not scanned or `JdbcTemplate` was not provided.
- `NoUniqueBeanDefinitionException`: multiple beans of the same type, with insufficient information to choose one.
- Bean creation failure due to SQL/DB during initialization: the repository may already be registered properly, yet a dependency or initialization logic failed; do not blame component scanning for every startup error.

When debugging, check the scanned packages, bean names/types, any other `@Bean` definitions, available dependencies, and the root stack trace before changing annotations.

## 6. `@Repository` and Data Access Exception Translation

An architectural benefit of `@Repository` is that it serves as a **marker** allowing Spring to apply exception translation from storage technologies into the `DataAccessException` hierarchy.

For example, an ORM provider may throw provider-specific exceptions. If the service layer always has to catch each provider's exception types, the service becomes directly coupled to the persistence technology. Spring provides the `DataAccessException` abstraction, including types such as `DataIntegrityViolationException`, `DuplicateKeyException`, `DataAccessResourceFailureException`, and others.

However, it is important to understand **the exact conditions for it to apply**, rather than claiming `@Repository` does everything by itself:

1. A Spring-managed repository bean exists.
2. Appropriate exception translation infrastructure exists, such as `PersistenceExceptionTranslationPostProcessor`.
3. One or more suitable `PersistenceExceptionTranslator` instances exist that understand the exceptions thrown by the provider.
4. Calls pass through the bean/proxy processed by that infrastructure, not an object created manually with `new` outside the container.
5. Only translatable exceptions are converted to `DataAccessException`. An arbitrary business `IllegalArgumentException` will not automatically turn into a database error.

With Java config, the post-processor can be declared as follows when the infrastructure is not already present:

~~~java
@Configuration
class PersistenceConfig {
    @Bean
    static PersistenceExceptionTranslationPostProcessor translationPostProcessor() {
        return new PersistenceExceptionTranslationPostProcessor();
    }
}
~~~

*This is a standalone configuration snippet using `org.springframework.dao.annotation.PersistenceExceptionTranslationPostProcessor`; it only produces the desired effect when an appropriate translator exists. Do not add duplicate configuration if the framework/starter already configures this mechanism.*

**Distinguish the Spring JDBC case:** `JdbcTemplate` already translates `SQLException` to `DataAccessException` during JDBC execution itself, **even when the class calling it does not carry `@Repository`**. Therefore, seeing a translated exception in a JDBC demo does not prove `@Repository` performed the translation. In the demo, `@Repository` primarily clarifies the role and allows component scanning to discover the class.

**Distinguish from transactions:** being registered with `@Repository` does not automatically create a transaction wrapping an entire use case. `@Transactional` and a transaction manager handle commit/rollback boundaries; whether an exception is checked/unchecked or caught can also affect rollback rules. A database exception may be translated, yet data modifications still require an appropriate transaction boundary.

### 7.3. `AppConfig.java`: Providing Infrastructure Beans and Enabling Scanning

~~~java
package demo;

import javax.sql.DataSource;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DriverManagerDataSource;

@Configuration
@ComponentScan(basePackageClasses = JdbcCustomerRepository.class)
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        DriverManagerDataSource source = new DriverManagerDataSource();
        source.setDriverClassName("org.h2.Driver");
        source.setUrl("jdbc:h2:mem:repository_demo;DB_CLOSE_DELAY=-1");
        source.setUsername("sa");
        source.setPassword("");
        return source;
    }

    @Bean
    public JdbcTemplate jdbcTemplate(DataSource source) {
        return new JdbcTemplate(source);
    }
}
~~~

The two `@Bean` methods create `DataSource` and `JdbcTemplate`. `@ComponentScan` takes package `demo` (from `JdbcCustomerRepository.class`) and discovers `@Repository`/`@Service` within it. `DriverManagerDataSource` is suitable only for demos because it does not pool connections; real applications usually require a connection pool.

### 7.4. `Customer.java`: Java Model

~~~java
package demo;

public record Customer(long id, String name) {
}
~~~

`Customer` here is a simple Java record. It is not annotated with `@Repository` or `@Entity`; the repository is responsible for constructing this object from queried data.

### 7.5. `CustomerRepository.java`: Data Layer Abstraction

~~~java
package demo;

import java.util.Optional;

public interface CustomerRepository {
    void save(Customer customer);
    Optional<Customer> findById(long id);
    int count();
}
~~~

This interface **does not** automatically become a Spring bean just because it is named `CustomerRepository`. The demo registers the **implementation** via `@Repository`. This differs from an interface extending `JpaRepository`/`CrudRepository`, for which specialized Spring Data infrastructure generates a proxy.

### 7.6. `JdbcCustomerRepository.java`: Implementation Scanned by Spring

~~~java
package demo;

import java.util.List;
import java.util.Optional;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class JdbcCustomerRepository implements CustomerRepository {

    private final JdbcTemplate jdbc;

    public JdbcCustomerRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public void save(Customer customer) {
        jdbc.update(
                "INSERT INTO customer(id, full_name) VALUES (?, ?)",
                customer.id(),
                customer.name());
    }

    @Override
    public Optional<Customer> findById(long id) {
        List<Customer> customers = jdbc.query(
                "SELECT id, full_name FROM customer WHERE id = ?",
                (rs, rowNum) -> new Customer(
                        rs.getLong("id"),
                        rs.getString("full_name")),
                id);
        return customers.stream().findFirst();
    }

    @Override
    public int count() {
        return jdbc.queryForObject(
                "SELECT COUNT(*) FROM customer", Integer.class);
    }
}
~~~

Points to observe:

- `@Repository` lets Spring scan and register the class under the data access stereotype.
- The constructor receives the `JdbcTemplate` bean instead of calling `new JdbcTemplate`.
- `JdbcTemplate` manages the JDBC lifecycle and translates SQL exceptions; repository code only writes SQL/mapping.
- `RowMapper` converts a row into `Customer`; mapping is a separate responsibility from bean registration.
- `?` parameters bind values instead of concatenating SQL strings.

### 7.7. `CustomerService.java`: Injecting the Repository by Interface

~~~java
package demo;

import org.springframework.stereotype.Service;

@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    public String customerName(long id) {
        return repository.findById(id)
                .orElseThrow()
                .name();
    }
}
~~~

No `@Autowired` is needed on the single constructor. The service does not depend directly on `JdbcCustomerRepository` or `JdbcTemplate`, making it easier to swap implementations and write isolated unit tests.

### 7.8. `RepositoryDemo.java`: Starting the Spring Container and Observing

~~~java
package demo;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.dao.DataAccessException;
import org.springframework.jdbc.core.JdbcTemplate;

public class RepositoryDemo {

    public static void main(String[] args) {
        try (AnnotationConfigApplicationContext context =
                     new AnnotationConfigApplicationContext(AppConfig.class)) {

            JdbcTemplate jdbc = context.getBean(JdbcTemplate.class);
            jdbc.execute(
                    "CREATE TABLE customer (" +
                    "id BIGINT PRIMARY KEY, " +
                    "full_name VARCHAR(100) NOT NULL)");

            CustomerRepository repository = context.getBean(CustomerRepository.class);
            CustomerService service = context.getBean(CustomerService.class);

            repository.save(new Customer(1L, "An"));
            System.out.println("Repository bean: " +
                    String.join(", ",
                            context.getBeanNamesForType(CustomerRepository.class)));
            System.out.println("Customer: " + service.customerName(1L));

            try {
                repository.save(new Customer(1L, "Duplicate"));
            } catch (DataAccessException expected) {
                System.out.println("Duplicate key: caught DataAccessException");
            }

            System.out.println("Count: " + repository.count());
        }
    }
}
~~~

In the directory containing `pom.xml`, run:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.RepositoryDemo
~~~

**Lines printed by the application:**

~~~text
Repository bean: jdbcCustomerRepository
Customer: An
Duplicate key: caught DataAccessException
Count: 1
~~~

H2 rejects the duplicate primary-key `INSERT`. `JdbcTemplate` translates the SQL error into an exception in the `DataAccessException` hierarchy, so the `catch` branch prints the message and the program continues. The table has only one row.

Explanation in exact execution order:

1. `AnnotationConfigApplicationContext(AppConfig.class)` loads the configuration.
2. `@ComponentScan` finds `JdbcCustomerRepository` and `CustomerService`; Spring creates the `jdbcCustomerRepository` bean (default name).
3. Spring creates `DataSource` and `JdbcTemplate` from `@Bean` methods and injects `JdbcTemplate` into the repository.
4. Spring injects the repository (via the `CustomerRepository` interface) into the service.
5. `RepositoryDemo` retrieves beans from the context, creates the table, and calls the service/repository. `getBeanNamesForType` confirms the implementation is registered, and `Count: 1` shows no duplicate record was inserted.
6. `try-with-resources` closes the Spring context when finished. This manual context-bootstrapping pattern is for learning; Spring Boot applications are normally started and lifecycle-managed by `SpringApplication.run(...)`.

**Nature of the example:** this demo does not set up transactions across multiple business operations, does not handle concurrency, and is not intended to model a production architecture. It specifically illustrates repository scanning/registration/injection and how `JdbcTemplate` raises `DataAccessException`.

## 8. Experiments: Changing Configuration to Understand the Mechanics

### Experiment A: Removing `@Repository`

Remove the annotation from `JdbcCustomerRepository`, keep `@ComponentScan`, and add no replacement `@Bean`. The plain class is no longer recognized as a component by default; `CustomerService` still requires `CustomerRepository`. On context startup, Spring fails to satisfy that dependency and reports a bean creation error (typically `UnsatisfiedDependencyException`, with the root cause being a missing `CustomerRepository` candidate).

**Takeaway:** the annotation provides discovery **when scanning is used**. Having a valid constructor is not enough for Spring to create a bean.

### Experiment B: Using `@Bean` Instead of Scanning the Implementation

Suppose you want explicit configuration. Remove `@Repository` from the implementation and replace implementation registration with a method in `@Configuration`:

~~~java
@Bean
public CustomerRepository customerRepository(JdbcTemplate jdbc) {
    return new JdbcCustomerRepository(jdbc);
}
~~~

Also make sure `CustomerService` is still scanned or registered another way. In this configuration, the `customerRepository` bean is created by the factory method even though the implementation no longer has a stereotype annotation. Do not leave both scanning of the old annotated implementation and the `@Bean` registration active if you only want one bean.

**Takeaway:** **bean registration** is the end goal; `@Repository` is one way to help the scanner recognize the implementation and convey data-layer semantics.

### Experiment C: Placing the Implementation Outside the Scanned Package

Move the repository to `com.example.external.data` while scanning only `demo`. Even with `@Repository` still present, the scanner does not inspect packages outside its scope. Fix this by configuring the right packages or using `@Import`/`@Bean`/explicit registration. Do not fix it by blindly widening the scan scope to the entire classpath.

**Takeaway:** **scan scope** is an input to component discovery; the annotation does not change the scan scope.

### Experiment D: Adding a Second Implementation

Add another bean implementing `CustomerRepository`. The `CustomerService(CustomerRepository)` constructor may now fail to resolve a unique candidate. Explicitly decide which implementation is the default with `@Primary`, or specify `@Qualifier` at the injection point. If you genuinely want both, inject `List<CustomerRepository>` or `Map<String, CustomerRepository>` and write explicit selection logic.

**Takeaway:** injection by type requires an unambiguous candidate; Spring does not automatically guess the right bean by class name when two exist.

### Experiment E: Persistence Exceptions and Annotations

If repository code uses `JdbcTemplate`, removing `@Repository` while registering the repository via `@Bean` still produces `DataAccessException` on duplicate SQL keys: that is `JdbcTemplate`'s own mechanism. Conversely, a repository throwing an arbitrary `RuntimeException` will not have it automatically translated simply because you added `@Repository`. An appropriate post-processor and translator must be present, and the translator only handles exception types it recognizes.

**Takeaway:** do not test exception translation merely by counting annotations; inspect the infrastructure and the origin of the exception.

## 9. `@Repository` Is Often Confused with Spring Data Repositories

In Spring Data, you can declare:

~~~java
public interface CustomerJpaRepository
        extends JpaRepository<CustomerEntity, Long> {
}
~~~

This is **illustrative code**; it requires `spring-data-jpa`, a valid `CustomerEntity`, an entity manager, transaction/persistence configuration, and infrastructure enabling repository scanning. Spring Data's mechanism finds repository interfaces and generates a proxy bean implementing the interface. That differs from component scanning a hand-written implementation like `JdbcCustomerRepository` in the demo.

| Case | What gets discovered/registered | Who provides the implementation? |
| --- | --- | --- |
| `@Repository JdbcCustomerRepository` class | Concrete component via `@ComponentScan` | The class written by the developer |
| `@Bean CustomerRepository ...` method | Bean definition supplied by a factory method | The developer instantiates the object |
| Interface extending `JpaRepository` | Spring Data repository infrastructure recognizes the interface | Spring Data generates a repository proxy |
| JPA `@Entity CustomerEntity` | ORM mapping metadata | Managed by the JPA provider, not automatically a Spring component bean |
| Writing only an interface named `CustomerRepository` | Not enough to create a bean | No mechanism provides it yet |

`@EnableJpaRepositories` (or equivalent setup from Spring Boot auto-configuration) enables/customizes Spring Data JPA repository creation; it is not a required annotation for every `@Repository` class using JDBC or manual DAOs.

Do not assume that merely naming a class or interface with a `Repository` suffix makes Spring Data generate `save`, `findAll`, or create tables. Those methods come from Spring Data interfaces and their supporting infrastructure, or from code you write yourself.

## 10. Common Errors and How to Fix Them

| Symptom | Diagnostic question | How to fix |
| --- | --- | --- |
| `CustomerService` fails to start due to missing repository | Does the implementation have `@Repository` or `@Bean`? Is it within the scan base package? | Register the bean via the proper mechanism, fix the scan scope |
| `@Repository` is present but `getBean(...)` cannot find it | Is the class on the runtime classpath? Is the queried context the one that registered it? | Verify packaging, configuration, and active context |
| Multiple beans of type `CustomerRepository` | Both scanned and declared as `@Bean`, or multiple implementations? | Remove unintended duplicate registration, or use `@Qualifier`/`@Primary` if intentional |
| `@Autowired` field in a manually `new`-ed object is null | Was the object created by the container or directly by application code? | Use constructor injection and obtain beans via context/DI |
| Native persistence exception is thrown | Are `PersistenceExceptionTranslationPostProcessor` and a suitable translator present? Did the call go through the Spring bean? | Configure translation for the active persistence technology |
| `JdbcTemplate` throws `DataAccessException` without `@Repository` | Was the exception translated by `JdbcTemplate` itself? | Distinguish the source of exception translation |
| Queries run, yet data commits with the wrong scope | Are there a business transaction boundary and the right transaction manager? | Design transactions on the service; `@Repository` does not replace transactions |
| Bean is created, yet DB connection fails | Are `DataSource`, credentials, URL, schema, and migrations valid? | Diagnose database configuration instead of changing stereotypes |
| Singleton repository causes concurrency bugs | Does it hold request data/`Connection` in mutable fields? | Keep dependencies thread-safe, handle state with proper scope |
| Injection depends on a concrete implementation and is hard to test | Can the service depend on an interface instead? | Extract an interface, inject via constructor, use fakes in unit tests |

**Design principles for the data layer:**

- Place repositories in scannable packages with clear data-access responsibilities.
- Use `@Repository` for persistence adapter classes; use `@Service` for use case/transaction orchestration.
- Prefer constructor injection; let services depend on meaningful abstractions.
- Register infrastructure objects (`DataSource`, `JdbcTemplate`, JPA-related beans) explicitly; do not assume `@Repository` creates them.
- Minimize mutable state in singleton repositories; keep connection/session lifecycles aligned with the underlying technology.
- Do not conflate exception translation, rollback, validation, and mapping. Each mechanism solves a separate responsibility.
- Test that the application actually boots and the service invokes the repository; do not merely verify annotations exist in source code.

## 11. Self-Check Questions

**1. `@Repository` was added, yet Spring fails to inject it. Where should you look first?**  
Check scanning/bean registration, packages, and required dependencies. `@Repository` does not register a bean if no mechanism brings the class into the context.

**2. Is `@Repository` mandatory for Spring to inject a data access class?**  
No. A bean created via `@Bean` is injected normally. However, the `@Repository` stereotype carries architectural meaning and marks the bean for exception translation when configured.

**3. Will Spring automatically generate an implementation for a custom `CustomerRepository` interface just like `JpaRepository`?**  
No. You must provide a concrete implementation/`@Bean`, or use a supported Spring Data interface and infrastructure.

**4. Does `@Repository` automatically convert every exception in a class into `DataAccessException`?**  
No. Appropriate post-processor and translator infrastructure is required; only exceptions recognized by a translator can be converted. `JdbcTemplate` has its own exception translation mechanism.

**5. Why is constructor injection usually a good fit for repositories?**  
It makes required dependencies explicit, supports `final` fields, reduces container coupling in unit tests, and surfaces missing-bean errors at startup.

**6. What is the default bean scope of a `@Repository` class?**  
Typically `singleton` per context. That does not make every connection object or state used by the repository thread-safe.

**7. If two implementations of `CustomerRepository` exist, will Spring automatically choose the JDBC implementation?**  
Not necessarily. Check dependency resolution rules and use `@Primary` or `@Qualifier` when explicit selection is needed.

**8. If `@Transactional` is added to the service, can `@Repository` be removed?**  
These are two separate responsibilities. Transactions manage commit/rollback boundaries; the repository bean still must be registered via one of the valid mechanisms.
