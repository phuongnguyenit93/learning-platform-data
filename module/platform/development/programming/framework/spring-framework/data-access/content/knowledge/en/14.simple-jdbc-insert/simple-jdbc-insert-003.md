# SimpleJdbcInsert: Using Database Metadata vs. Declaring Columns Explicitly

## 1. Lesson Objectives

In Spring JDBC, `SimpleJdbcInsert` helps perform `INSERT` operations without writing SQL strings or managing `PreparedStatement` manually for straightforward cases. A key configuration decision is: **let Spring infer columns from database metadata**, or **explicitly declare the columns the application wants to insert**.

After this lesson, you should be able to:
- Understand how metadata comes from the JDBC driver and is used by `SimpleJdbcInsert` to build SQL.
- Distinguish three configuration modes: auto-detecting columns, specifying `usingColumns(...)`, and disabling column metadata lookup with `withoutTableColumnMetaDataAccess()`.
- Know when to declare `usingGeneratedKeyColumns(...)`, `withSchemaName(...)`, and `withCatalogName(...)`.
- Avoid common pitfalls with `DEFAULT` columns, keys missing from input, duplicate table names across schemas, uppercase/lowercase identifiers, and drivers returning inaccurate metadata.
- Choose the appropriate configuration approach, verifiable with Java 17+ code and integration tests.

**Scope:** this lesson focuses on **the source of column information and configuring the `SimpleJdbcInsert` INSERT statement**. Retrieving generated keys, transactions, and batch inserts are covered only as they relate to metadata and column selection.

## 2. What Is Metadata, and How Does SimpleJdbcInsert Use It?

*Database metadata* is information describing the structure and capabilities of a database returned by the JDBC driver through APIs such as `Connection.getMetaData()` and `DatabaseMetaData`. To identify a table's columns, Spring can look up information corresponding to `DatabaseMetaData.getColumns(...)`: column names, SQL types, table/schema/catalog, and related supporting details.

Minimal configuration for a table whose IDs are **supplied by the application**:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("customer");

int affected = insert.execute(Map.of(
        "id", 10L,
        "full_name", "Lan"
));
```

This is an **illustrative code snippet** placed inside a class or method with a `dataSource` variable of type `javax.sql.DataSource`. `Map` holds column names and values; `execute(...)` returns the affected row count, not the ID.

High-level flow:

```text
DataSource / JDBC Connection
        │
        ▼
SimpleJdbcInsert is configured (table, schema, columns, generated key)
        │
        ▼
At compile time, Spring reads column metadata if enabled
        │
        ▼
Builds/fixes the INSERT statement and parameter list in column order
        │
        ▼
execute(Map or SqlParameterSource) → bind parameters → JDBC INSERT
```

`SimpleJdbcInsert` performs the *compile* step implicitly when first needed at runtime; you can also call `compile()` after configuration to catch some errors early. The SQL is finalized at compile time and reused across subsequent executions. **Do not treat metadata as a mechanism that automatically detects schema changes on every `execute` call.**

Common misconceptions:
- Metadata **does not fetch data values** from the table; it provides column names, types, and structure so Spring can generate the statement.
- `SimpleJdbcInsert` **does not automatically validate that every Map value satisfies business rules**. `NOT NULL`, `UNIQUE`, foreign key, and other constraints are still enforced by the database.
- Just because a column exists in the database does not mean it should be written in every case. Many columns rely on DB `DEFAULT` values or are managed by triggers or other applications.
- `SimpleJdbcInsert` is reusable across multiple inserts; create and configure it at repository initialization rather than instantiating it inside a data-writing loop.

## 3. Three Configuration Modes to Distinguish

Suppose we have the table:

```sql
CREATE TABLE catalog_item (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(30) NOT NULL UNIQUE,
    name VARCHAR(100) NOT NULL
);
```

The application wants to insert `sku` and `name`; the `id` column is generated by the DB.

### Mode A — Auto-Detect Columns via Metadata (Default)

```java
SimpleJdbcInsert auto = new SimpleJdbcInsert(dataSource)
        .withTableName("catalog_item")
        .usingGeneratedKeyColumns("id");

Number id = auto.executeAndReturnKey(Map.of(
        "sku", "AUTO-001",
        "name", "Notebook"
));
```

`withTableName(...)` identifies the table. Because `usingColumns(...)` is omitted, Spring relies on table metadata to build the insert column list, excluding the column declared as a generated key. `usingGeneratedKeyColumns("id")` indicates which column to retrieve after the DB generates it; **it does not replace `usingColumns(...)`** and **does not create an identity column in the database**.

With this schema, the logical SQL is equivalent to:

```sql
INSERT INTO catalog_item (sku, name) VALUES (?, ?);
```

Column display order and identifier quoting in the actual SQL may vary by driver/dialect. Values are bound as JDBC parameters, not concatenated directly into the SQL string.

**Best when:** the table is simple, driver metadata is complete, all non-DB-generated columns genuinely have input values, and relying on the metadata column list is acceptable.

### Mode B — Specify Write Columns with `usingColumns`, Metadata Still Available

```java
SimpleJdbcInsert explicitColumns = new SimpleJdbcInsert(dataSource)
        .withTableName("catalog_item")
        .usingColumns("sku", "name")
        .usingGeneratedKeyColumns("id");

Number id = explicitColumns.executeAndReturnKey(Map.of(
        "sku", "EXPLICIT-001",
        "name", "Fountain pen"
));
```

`usingColumns("sku", "name")` acts as an **allowlist of columns appearing in `INSERT`**. It proactively excludes other columns from the SQL, even if new columns are added to the table later. Spring can still use metadata to inspect SQL types and driver capabilities because column metadata lookup has **not been disabled**.

This is a practical choice for many DAOs: the code clearly states its write intent, keeps the convenience of Spring JDBC, and avoids accidentally pulling DB-managed columns into the statement.

**Best when:** you only want to write a subset of columns, the table has `DEFAULT`/trigger columns, you want to control the impact of schema migrations, or you want an explicit repository write contract.

### Mode C — Disable Column Metadata Lookup, Declare All Insert Columns Manually

```java
SimpleJdbcInsert noColumnMetadata = new SimpleJdbcInsert(dataSource)
        .withTableName("catalog_item")
        .withoutTableColumnMetaDataAccess()
        .usingColumns("sku", "name")
        .usingGeneratedKeyColumns("id");

Number id = noColumnMetadata.executeAndReturnKey(Map.of(
        "sku", "NO-META-001",
        "name", "Ruler"
));
```

`withoutTableColumnMetaDataAccess()` disables processing of **table column metadata**. Because Spring cannot determine columns automatically, you must provide an appropriate `usingColumns(...)` list and take responsibility for keeping it aligned with the schema.

**Important distinction:** disabling *table-column metadata* does not mean Spring will never call any `DatabaseMetaData` method; other features, such as checking generated-key support or identifier quoting, may still query information from the driver.

**Best when:** the JDBC driver provides incomplete or inaccurate column metadata, tables/views/synonyms make column discovery unreliable, the environment restricts metadata permissions, or you want a column contract strictly controlled by code.

### Quick Comparison Table

| Criterion | A. Auto-detected Metadata | B. `usingColumns` | C. Disable Column Metadata + `usingColumns` |
| --- | --- | --- | --- |
| Spring auto-discovers columns from the table | Yes | Not needed to determine insert column list | No |
| `INSERT` column list explicitly chosen by code | No | Yes | Yes |
| JDBC column metadata still processed | Yes | Yes (default) | No |
| Works well with `DEFAULT` columns omitted from input | Error-prone if column enters SQL | Good, if column is excluded from `usingColumns` | Good, if column is excluded from `usingColumns` |
| Dependency on column name/type metadata quality | High | Medium | Lower |
| Code update required if mandatory write columns change | Depends on how metadata sees the schema | Yes | Yes |

**Remember:** `usingColumns(...)` and `withoutTableColumnMetaDataAccess()` are **two separate switches**: the first chooses **which columns to write**, while the second chooses **whether column metadata is used to assist processing**. You can use `usingColumns(...)` without disabling metadata; that is usually a good starting point.

## 4. Critical Pitfall: `DEFAULT` Columns and Keys Missing from `Map`

Suppose the table evolves with an additional column:

```sql
CREATE TABLE audited_item (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    description VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
```

The application only supplies `description`. If you let `SimpleJdbcInsert` auto-discover every column via metadata without declaring the write columns, it **may generate an INSERT that includes `created_at` and binds `NULL` for the missing Map value**. The database will not apply `DEFAULT CURRENT_TIMESTAMP` as it would when the column is truly omitted from the INSERT list; the result may be a `NOT NULL` error or unexpected data.

SQL example showing the difference:

```sql
-- Column omitted completely from INSERT: database applies DEFAULT.
INSERT INTO audited_item (description) VALUES ('Created');

-- Passing NULL for the column: not equivalent to requesting DEFAULT.
INSERT INTO audited_item (description, created_at)
VALUES ('Created', NULL);
```

With the schema above, the second statement violates `NOT NULL` in H2. The proactive way to avoid this risk is:

```java
SimpleJdbcInsert insertAudit = new SimpleJdbcInsert(dataSource)
        .withTableName("audited_item")
        .usingColumns("description")
        .usingGeneratedKeyColumns("id");

insertAudit.executeAndReturnKey(
        Map.of("description", "Created")
);
```

After inserting, `created_at` receives the DB timestamp because it **does not appear in the INSERT statement**.

**Do not confuse three states:** (1) column not in `usingColumns` → omitted from SQL; (2) column in write list, input value is `null` → may bind SQL `NULL`; (3) key missing from Map while metadata mode still selects the column → Spring may bind `NULL`. These do not mean the same thing, especially with `DEFAULT` or required columns.

Schema migrations also have consequences: if a new `created_at` column with `DEFAULT` is added, an already-compiled instance may keep using its prepared SQL, whereas a newly compiled instance using fresh metadata may add the column to the list. Therefore, always integration-test insert behavior after migrations and prefer explicit `usingColumns` when tables have DB-managed columns.


**`src/main/java/com/example/insertmeta/InsertMetadataApplication.java`**:

```java
package com.example.insertmeta;

import java.util.Map;
import javax.sql.DataSource;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

@SpringBootApplication
public class InsertMetadataApplication {

    public static void main(String[] args) {
        SpringApplication.run(InsertMetadataApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(DataSource dataSource, JdbcTemplate jdbc) {
        return args -> {
            // A: metadata auto-detects columns; id is generated by the database.
            SimpleJdbcInsert auto = new SimpleJdbcInsert(dataSource)
                    .withTableName("catalog_item")
                    .usingGeneratedKeyColumns("id");

            // B: only these two columns are included in INSERT; metadata remains enabled.
            SimpleJdbcInsert explicit = new SimpleJdbcInsert(dataSource)
                    .withTableName("catalog_item")
                    .usingColumns("sku", "name")
                    .usingGeneratedKeyColumns("id");

            // C: skip column metadata lookup, explicitly specify columns in code.
            SimpleJdbcInsert noColumnMeta = new SimpleJdbcInsert(dataSource)
                    .withTableName("catalog_item")
                    .withoutTableColumnMetaDataAccess()
                    .usingColumns("sku", "name")
                    .usingGeneratedKeyColumns("id");

            Number autoId = auto.executeAndReturnKey(
                    Map.of("sku", "AUTO-001", "name", "Notebook"));
            Number explicitId = explicit.executeAndReturnKey(
                    Map.of("sku", "EXPLICIT-001", "name", "Pen"));
            Number noMetaId = noColumnMeta.executeAndReturnKey(
                    Map.of("sku", "NO-META-001", "name", "Ruler"));

            // Write description only, letting created_at receive DB DEFAULT.
            SimpleJdbcInsert audit = new SimpleJdbcInsert(dataSource)
                    .withTableName("audited_item")
                    .usingColumns("description")
                    .usingGeneratedKeyColumns("id");
            audit.executeAndReturnKey(
                    Map.of("description", "Created"));

            int total = jdbc.queryForObject(
                    "SELECT COUNT(*) FROM catalog_item", Integer.class);
            int timestamps = jdbc.queryForObject(
                    "SELECT COUNT(*) FROM audited_item "
                            + "WHERE created_at IS NOT NULL", Integer.class);

            System.out.println("Catalog rows: " + total);
            System.out.println("Generated IDs returned: "
                    + (autoId.longValue() > 0
                    && explicitId.longValue() > 0
                    && noMetaId.longValue() > 0));
            System.out.println("Default timestamp applied: "
                    + (timestamps == 1));
        };
    }
}
```

From the `simplejdbc-metadata-demo` directory:

```bash
mvn -q spring-boot:run
```

**Three lines printed by the program** when run against a fresh H2 database:

```text
Catalog rows: 3
Generated IDs returned: true
Default timestamp applied: true
```

Other logs (if any) depend on the runtime environment. The example uses three distinct SKUs and a freshly initialized in-memory database for deterministic results; **do not assume auto-generated IDs must be 1, 2, 3, or sequential**. In Mode A, `catalog_item` has no extra default columns, so column auto-detection is safe within this sample's scope. For `audited_item`, `usingColumns("description")` ensures `created_at`'s default is not overwritten with `NULL`.

### Where in the Program Is Metadata Usage Decided?

- `auto` omits `usingColumns`, so Spring uses column names read from metadata and excludes `id` because of `usingGeneratedKeyColumns`.
- `explicit` selects strictly `sku` and `name` for the SQL insert; column metadata stays enabled.
- `noColumnMeta` selects strictly `sku` and `name` **and** skips table-column metadata discovery. This illustrates the fully explicit declaration mode.
- `audit` shows the benefit of a column allowlist: when the SQL omits `created_at`, the database applies `DEFAULT CURRENT_TIMESTAMP`.

If you only need the inserted row count, you can call `execute(Map)` instead of `executeAndReturnKey(Map)`; to obtain a numeric ID, configure `usingGeneratedKeyColumns("id")` and use the overload returning `Number`. Both key-retrieval approaches still depend on the driver/DB.

## 6. When to Explicitly Declare Schema, Catalog, or Quoted Identifiers

### Same Table Name Across Multiple Schemas

If a connection has access to multiple schemas containing tables with the same name, calling `withTableName("catalog_item")` may not resolve the intended table, or metadata may fail to find the table along the search path/default schema.

Explicit configuration:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withSchemaName("inventory")
        .withTableName("catalog_item")
        .usingColumns("sku", "name")
        .usingGeneratedKeyColumns("id");
```

This is an **illustrative configuration snippet**: schema `inventory` only exists if you created it; do not use this literal name in the H2 sample project above. `withCatalogName(...)` is also available when the DBMS/JDBC driver distinguishes catalogs. Choose the actual database/schema explicitly instead of guessing based on matching names.

### Quoted Identifiers and Case-Sensitivity Rules

Some DBMSs fold the case of unquoted names; quoted names can be case-sensitive. With Spring Framework 6.1+, `usingQuotedIdentifiers()` instructs Spring to quote table, schema, and column identifiers in the generated SQL according to database rules.

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("CatalogItem")
        .usingColumns("SkuCode", "DisplayName")
        .usingQuotedIdentifiers();
```

This is an **illustrative example** for a real table whose names are quoted exactly like that. Column/table names must match the casing in DB metadata; **when using `usingQuotedIdentifiers()`, you must provide `usingColumns(...)`** per Spring's Javadoc. Do not turn on quoted identifiers as a blanket fix for every missing-column error: check the DDL, actual names, driver, and schema first.

### Views, Synonyms, and Driver Limitations

Some drivers do not return a stable column list for views, synonyms, or tables behind a proxy/gateway. If using Oracle synonyms, `includeSynonymsForTableColumnMetaData()` may be needed to include synonyms in metadata lookup. If table metadata remains unreliable, you can use `withoutTableColumnMetaDataAccess()` together with a verified `usingColumns(...)` list. However, **this does not mean every view is insertable**; that is governed by the database.

## 7. SQL Types, NULL, and SqlParameterSource When Metadata Is Disabled

When relying on metadata, Spring can know the JDBC types of columns. Disabling column metadata reduces inferred type information; for `null` values or special database types, the driver may require explicit type declarations.

Example **illustrative snippet inside a DAO that already has `insert`**:

```java
import java.sql.Types;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;

MapSqlParameterSource params = new MapSqlParameterSource()
        .addValue("sku", "PEN-009", Types.VARCHAR)
        .addValue("name", null, Types.VARCHAR);

insert.execute(params);
```

Here `insert` must be a `SimpleJdbcInsert` configured with matching columns; **this snippet is not standalone**. For the `catalog_item` table in the main example, `name` is `NOT NULL`, so this statement **will fail due to the DB constraint** even though `Types.VARCHAR` is supplied. The purpose of the code is to show how to specify a JDBC type, **not a way to make NULL valid**. In practice, test with a nullable column.

Distinguish clearly:
- `usingColumns(...)` determines **which columns go into the SQL**.
- `Map` / `SqlParameterSource` provides **the values to bind**.
- `MapSqlParameterSource.addValue(name, value, sqlType)` can provide the **SQL type** when the driver cannot easily infer it, especially when `value == null`.
- Database DDL still enforces `NULL`, `DEFAULT`, constraints, identity, and triggers.

## 8. Common Errors and How to Handle Them

| Symptom | Common Cause | Check / Resolution |
| --- | --- | --- |
| Metadata not found for table | Wrong schema/catalog, case sensitivity, incomplete driver support, or table not created yet | Check DDL, permissions, schema; use `withSchemaName` or declare columns with `usingColumns` |
| Generated SQL contains unwanted columns | Letting auto metadata pick all non-generated-key columns | Use `usingColumns(...)` to narrow down explicitly |
| `NOT NULL` error on a column with `DEFAULT` | SQL includes the column and binds `NULL`, preventing the DB from applying default | Remove that column from `usingColumns`; re-verify with an integration test |
| Disabled metadata and Spring does not know which columns to insert | Calling `withoutTableColumnMetaDataAccess()` without providing a column list | Explicitly declare all valued columns with `usingColumns(...)` |
| Insert fails after a schema change | New required column, default column bound as NULL, or stale configuration mismatching schema | Review migrations; update `usingColumns`/mappings as needed and recreate compiled instances |
| Generated key returns `null` or throws an error | `usingGeneratedKeyColumns` not configured, DB does not generate key, or driver does not return key | Check DDL and driver generated-keys support; distinguish generated key from insert columns |
| Quoted/case-sensitive column name mismatch | Case normalized differently, or DB name has special quoting | Inspect actual names in metadata; use `usingQuotedIdentifiers` with `usingColumns` and exact casing when needed |
| Wrong table hit across multiple schemas | Search path or metadata picks a different schema | Specify `withSchemaName`/`withCatalogName` explicitly and verify the connection |
| `null` value handled with wrong type by driver | Missing JDBC type info, especially when metadata is disabled | Use `MapSqlParameterSource` with appropriate `Types.*` |
| Slow execution from repeated `SimpleJdbcInsert` creation | Configuring and compiling on every record | Reuse a single configured instance; do not instantiate inside write loops |

### Systematic Diagnostic Steps

1. Re-read the table's **actual DDL**: schema, name, column types, `DEFAULT`, identity/generated, `NOT NULL`.
2. List the **business columns that the INSERT must populate**; DB-managed columns should be omitted if defaults or triggers are desired.
3. If relying on metadata, verify the JDBC driver actually sees the right table and columns in the current schema.
4. Enable Spring JDBC logging at an appropriate level in development to inspect the SQL statement and parameter binding; avoid logging sensitive data in production.
5. If the SQL includes extra columns, try `usingColumns` first. If metadata is genuinely broken or the driver lacks info, add `withoutTableColumnMetaDataAccess` and declare types explicitly as needed.
6. Run integration tests against the actual production DB/driver or a compatible environment; H2 only proves behavior for H2.

## 9. Design Choices and Testing

### Rules for Choosing Configuration

- **Very simple table, full inputs provided, reliable metadata:** start with `withTableName` and `usingGeneratedKeyColumns` when an ID is needed.
- **Tables with default, audit, trigger columns, or frequent migrations:** prefer `usingColumns(...)` to lock down the SQL contract; keep metadata enabled if it works well.
- **Problematic table metadata or restricted permissions:** use `withoutTableColumnMetaDataAccess()` **along with** `usingColumns(...)`; verify generated keys and specific data types.
- **Non-unique table names across schemas:** specify schema/catalog explicitly before considering disabling metadata.
- **Tables with quoted/case-sensitive identifiers:** use the exact database names; consider `usingQuotedIdentifiers()` + `usingColumns(...)`.

### Recommended Test Suite

1. **Metadata mode:** insert into a simple table, verify row count, and confirm no required field values are lost.
2. **`usingColumns`:** add an optional column in a migration, confirm the repository only inserts the declared columns.
3. **DB default:** insert a record without supplying `created_at`, read it back, and confirm the DB populated the timestamp.
4. **No-metadata mode:** run against the real schema/driver; confirm `usingColumns` is sufficient and generated keys work if needed.
5. **Case/schema:** test against the actual schema if using quoted identifiers or multiple schemas.
6. **NULL and data types:** test nullable fields with explicit types if required by the driver; never send NULL to `NOT NULL` columns.
7. **Migration:** re-run tests after adding/removing/renaming columns; verify compiled instances still produce valid SQL.

**A practical exercise:** You have a table `orders(id, amount, created_at DEFAULT CURRENT_TIMESTAMP)`, the application only supplies `amount`, and wants `id` back. A safe, clear configuration is:

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("orders")
        .usingColumns("amount")
        .usingGeneratedKeyColumns("id");
```

The statement will not overwrite `created_at` because of `usingColumns("amount")`, and `id` is requested back after DB generation. If the driver cannot provide column metadata reliably, add `withoutTableColumnMetaDataAccess()`; the write column list remains `amount`. This snippet illustrates configuration inside a class with `dataSource`, not a standalone Java program.

## 10. Key Takeaways to Remember

- `SimpleJdbcInsert` relies on JDBC `DatabaseMetaData` to simplify building `INSERT` statements.
- **Auto-detecting metadata** reduces configuration, but the column list returned by the driver may be broader than the dataset you actually intend to write.
- **`usingColumns(...)`** explicitly controls which columns appear in `INSERT` while allowing metadata to remain enabled.
- **`withoutTableColumnMetaDataAccess()`** disables column metadata processing; requires declaring `usingColumns(...)`, especially when metadata is unreliable.
- **`usingGeneratedKeyColumns(...)`** specifies the generated key to retrieve, distinct from the write column list.
- Only omitting a column entirely from `INSERT` lets the DB apply `DEFAULT`; binding `NULL` is not equivalent.
- Reuse compiled configurations, consider schema/case/driver specifics, and verify against the real database.
