# Requesting Generated Keys When Creating PreparedStatement in Spring JDBC

## 1. Goal and use case

After inserting a record with `INSERT`, the database often auto-generates the primary key, such as an `id` column with `IDENTITY` or `AUTO_INCREMENT`. The application may need the newly generated key to return to an API, create related records, or continue processing within the same transaction.

The core point of this lesson: **you must instruct the JDBC driver to allow returning generated keys right when creating the `PreparedStatement`**. Only then do you execute the `INSERT` statement and read the key from the JDBC `ResultSet` or Spring's `KeyHolder`. Requesting generated keys does not itself generate a key; key generation belongs to the database.

Suppose a `customer` table has a database-generated `id` column and two application-supplied columns:

```sql
-- Standard SQL IDENTITY syntax example, compatible with H2/PostgreSQL;
-- syntax for auto-generated columns in other DBMSs may differ.
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(200) NOT NULL
);
```

We insert data with `INSERT INTO customer (name, email) VALUES (?, ?)` and want to get `id` back. The two `?` placeholders are `PreparedStatement` parameters; they do not represent the database-assigned `id` key.

## 2. Where is the generated-key request declared?

In JDBC, `Connection` provides the following ways to create a `PreparedStatement`:

```java
// (1) Only prepares SQL; does not explicitly request generated keys.
PreparedStatement plain = connection.prepareStatement(sql);

// (2) Enables requesting keys generated by the database.
PreparedStatement withKeys = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS);

// (3) Explicitly specifies the key column to retrieve by name.
PreparedStatement withId = connection.prepareStatement(
        sql, new String[] {"id"});
```

The three lines are illustrative alternatives, not three statements to create simultaneously. In real usage, pick one option and close the statement properly.

| Call | Meaning | When to use |
| --- | --- | --- |
| `prepareStatement(sql)` | Prepares statement and parameters; does not explicitly request generated keys. | Only need the updated row count or queried data. |
| `prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)` | Instructs the driver to make generated keys retrievable after execution. | Want the driver to decide which key columns to return. |
| `prepareStatement(sql, new String[] {"id"})` | Requests the key from the column named `id`. | Know the exact column name to return; often useful to avoid differences in columns auto-selected by drivers. |

`Statement.NO_GENERATED_KEYS` is the opposite flag to `RETURN_GENERATED_KEYS`. The `String[]` array contains **table column names**, not Java parameter names, and must match the naming/case rules of the database and driver. JDBC also has an overload taking `int[] columnIndexes`, but column indexes depend on table layout, so column names are usually more readable.

**Important:** The `RETURN_GENERATED_KEYS` flag is passed to **`Connection.prepareStatement(...)`**, not to `PreparedStatement.executeUpdate(...)`. Overloads like `executeUpdate(sql, Statement.RETURN_GENERATED_KEYS)` belong to `Statement`; do not call those overloads on an already-prepared `PreparedStatement`.

## 3. Pure JDBC flow: create, bind parameters, execute, read key

This is a syntactically complete Java 17+ class depending only on JDBC in the JDK. It accepts an open `Connection`; the caller is responsible for managing `Connection`/transaction lifecycles and configuring the JDBC driver.

```java
// File: GeneratedKeyJdbcExample.java
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;

public final class GeneratedKeyJdbcExample {

    private static final String INSERT_SQL =
            "INSERT INTO customer (name, email) VALUES (?, ?)";

    public static long insertCustomer(
            Connection connection, String name, String email)
            throws SQLException {

        // Request generated keys when creating the PreparedStatement.
        try (PreparedStatement ps = connection.prepareStatement(
                INSERT_SQL, Statement.RETURN_GENERATED_KEYS)) {

            ps.setString(1, name);
            ps.setString(2, email);

            int affectedRows = ps.executeUpdate();
            if (affectedRows != 1) {
                throw new SQLException(
                        "Expected one inserted row, got " + affectedRows);
            }

            // Read generated keys only after executing INSERT.
            try (ResultSet keys = ps.getGeneratedKeys()) {
                if (!keys.next()) {
                    throw new SQLException(
                            "INSERT succeeded but no generated key returned");
                }
                long id = keys.getLong(1);
                if (keys.wasNull()) {
                    throw new SQLException("Generated id is SQL NULL");
                }
                return id;
            }
        }
    }
}
```

You can verify **compiling the class** with JDK 17 or later:

```bash
javac GeneratedKeyJdbcExample.java
```

The class has no `main`, so it cannot run standalone via `java GeneratedKeyJdbcExample`. To run it for real, the application needs a `Connection` from an appropriate JDBC driver, the `customer` table created, and a call to the method above. There is no fixed stdout because the generated key depends on data and the database.

Processing flow:

1. `prepareStatement(INSERT_SQL, RETURN_GENERATED_KEYS)` informs the driver ahead of time that keys need to be retrieved.
2. `setString(1, ...)` and `setString(2, ...)` bind values to the `?` placeholders; never concatenate data directly into SQL.
3. `executeUpdate()` runs the `INSERT` and returns the affected row count, **not the ID value**.
4. `getGeneratedKeys()` opens a separate `ResultSet` containing the keys returned by the driver.
5. `keys.next()` checks whether a key row exists; `keys.getLong(1)` reads the first column if the key is an appropriate numeric type.
6. `try-with-resources` closes `ResultSet` and `PreparedStatement` even when errors occur. The example does not close `Connection` because the caller manages it.

If you need to make sure you read the exact `id` column, replace the statement creation line with:

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, new String[] {"id"});
```

This is just a replacement line **inside the same `try-with-resources` block** of the example; do not create a second statement.

## 4. Main Spring approach: PreparedStatementCreator + KeyHolder

In Spring JDBC, `JdbcTemplate.update(PreparedStatementCreator, KeyHolder)` provides this exact capability:

- `PreparedStatementCreator` is a callback receiving a `Connection` managed by `JdbcTemplate`; the callback must create a `PreparedStatement` **with generated-key return enabled** and bind parameters.
- `GeneratedKeyHolder` is where Spring places returned keys after running `INSERT`.
- `JdbcTemplate` manages JDBC resource lifecycles, participates in configured Spring transactions, and translates `SQLException` into appropriate `DataAccessException` subclasses.

The example below is a repository class usable in a Spring Framework 6.x application on Java 17+. The application must provide a `JdbcTemplate` configured from a `DataSource` and have the table from section 1.

```java
// File: CustomerRepository.java
import java.sql.PreparedStatement;
import java.util.Objects;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public final class CustomerRepository {

    private static final String INSERT_SQL =
            "INSERT INTO customer (name, email) VALUES (?, ?)";

    private final JdbcTemplate jdbcTemplate;

    public CustomerRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = Objects.requireNonNull(jdbcTemplate);
    }

    public long create(String name, String email) {
        KeyHolder keyHolder = new GeneratedKeyHolder();

        int affectedRows = jdbcTemplate.update(connection -> {
            // Specify the key column to return RIGHT WHEN creating PreparedStatement.
            PreparedStatement ps = connection.prepareStatement(
                    INSERT_SQL, new String[] {"id"});
            ps.setString(1, name);
            ps.setString(2, email);
            return ps;
        }, keyHolder);

        if (affectedRows != 1) {
            throw new IllegalStateException(
                    "Expected one inserted row, got " + affectedRows);
        }

        Number key = keyHolder.getKey();
        if (key == null) {
            throw new IllegalStateException(
                    "Database did not return a generated id");
        }
        return key.longValue();
    }
}
```

In this example, `connection.prepareStatement(INSERT_SQL, new String[] {"id"})` is called right inside the `PreparedStatementCreator` lambda. This is the decisive detail: merely passing a `KeyHolder` into `update` **cannot fix a statement that did not request generated keys**. You can use `Statement.RETURN_GENERATED_KEYS` instead of the column-name array if the driver supports it well.

`keyHolder.getKey()` is appropriate when the operation returns **one key row with one numeric key value**. Note that the result has type `Number` (e.g., `Integer`, `Long`, or `BigDecimal` depending on the driver); use `longValue()` when the domain truly needs `long` and the value fits within its range. For UUIDs or non-numeric keys, or when multiple key columns/rows are needed, do not call `getKey()` as if there is always a single `long`: read `getKeys()`/`getKeyList()` according to the actual structure. Spring may throw an exception if `getKey()` is called when multiple key values are present.

The `CustomerRepository` class above has no `main` and depends on Spring JDBC libraries. It cannot be compiled with the JDK alone: it needs compatible Spring JARs (and at runtime a JDBC driver/DataSource). In Spring Boot, configuring a DataSource and `spring-boot-starter-jdbc` usually provides the needed components; fundamentally, requesting keys remains a JDBC concern.

### Distinguishing from standard `update` overloads

```java
// Counts inserted rows; does not receive generated keys via KeyHolder.
int count = jdbcTemplate.update(
        "INSERT INTO customer (name, email) VALUES (?, ?)",
        "An", "an@example.test");

// Receives generated keys; callback creates a statement with key-return enabled.
KeyHolder holder = new GeneratedKeyHolder();
jdbcTemplate.update(con -> {
    PreparedStatement ps = con.prepareStatement(
            "INSERT INTO customer (name, email) VALUES (?, ?)",
            Statement.RETURN_GENERATED_KEYS);
    ps.setString(1, "An");
    ps.setString(2, "an@example.test");
    return ps;
}, holder);
```

The two snippets are **two independent INSERT operations to compare APIs**, not meant to be run back-to-back with the same data when only inserting one row. The second snippet needs `import java.sql.Statement;` and the corresponding Spring imports as in the repository example. When you need generated keys, use the overload with `KeyHolder`. Do not confuse the `int` returned by `update(...)` (affected row count) with the key value inside `KeyHolder`.

## 5. How to choose the right key-return mode?

### Option A — `Statement.RETURN_GENERATED_KEYS`

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, Statement.RETURN_GENERATED_KEYS);
```

This is a general request for the driver to return database-generated keys. However, when columns are not specified, the driver decides which columns are appropriate to return. Results and column ordering may vary by driver/DBMS.

### Option B — requesting the `id` column by name

```java
PreparedStatement ps = connection.prepareStatement(
        INSERT_SQL, new String[] {"id"});
```

This states the intent that the key from the `id` column is needed. The name must match a column supported by the table/driver; some drivers enforce case sensitivity or only support certain key types. If you want to read one exact column, verify against the real database rather than assuming every driver behaves identically.

### The mechanism does not replace database key generation

If the table does not auto-generate keys, or the `INSERT` already supplies `id` manually, enabling `RETURN_GENERATED_KEYS` will not force the database to create an extra ID. Understand the schema, `INSERT` statement, and driver capabilities clearly. JDBC provides `DatabaseMetaData.supportsGetGeneratedKeys()` to query feature support, though you must still test the exact statement/schema type on the target DBMS.

For DBMS-specific SQL like `INSERT ... RETURNING id` (e.g., PostgreSQL), that is a mechanism returning data via SQL results that must be handled per the semantics of the chosen driver and API; do not arbitrarily mix `RETURNING` with `getGeneratedKeys()`/`KeyHolder` without testing.

## 6. Common pitfalls and how to handle them

| Symptom/pitfall | Possible cause | Fix |
| --- | --- | --- |
| `INSERT` succeeds but `getGeneratedKeys()` is empty | Statement was created with `prepareStatement(sql)` without requesting keys, or driver/SQL lacks support. | Recreate statement using `RETURN_GENERATED_KEYS` or column-name array overload; check driver and schema. |
| Calling `ps.executeUpdate(sql, Statement.RETURN_GENERATED_KEYS)` | This overload is for `Statement`, not for re-supplying SQL/flags on a `PreparedStatement`. | Move the flag to `connection.prepareStatement(...)`, then call parameterless `ps.executeUpdate()`. |
| Using `affectedRows` as the ID | `executeUpdate`/`JdbcTemplate.update` returns the affected row count. | Read the `ResultSet` from `getGeneratedKeys` or `KeyHolder`. |
| `keyHolder.getKey()` returns `null` | No key was populated into the holder. | Check statement creation, driver, `INSERT` type, and keys actually returned. |
| `getKey()` reports multiple keys | Driver returned multiple key columns or multiple rows; `getKey()` is for a single numeric key value. | Use `getKeys()`/`getKeyList()` and inspect the returned map/rows. |
| Key is a UUID but `getLong(1)`/`getKey()` is called | Assumed keys are always numeric. | Read the matching type, such as `ResultSet.getObject(...)` or the key map; check the driver. |
| Test code assumes IDs always increase sequentially with no gaps | Sequences/identities can skip numbers on rollback, retry, concurrent transactions, or allocation mechanisms. | Treat IDs as DB-assigned identifiers, not as commit order or record counts. |
| Storing `KeyHolder` as a shared field | `GeneratedKeyHolder` is a mutable result container, not meant to be shared across concurrent inserts. | Create `new GeneratedKeyHolder()` per insert call. |

A retrieved key **does not mean the transaction has committed**. When Spring manages transactions with `@Transactional`, inserting and retrieving the key can occur before commit; the transaction can still roll back. Do not emit external events solely based on having obtained a key when commit consistency is required.

## 7. Testing according to the lesson's goals

Against a test database with an auto-generated `id` column, verify the following cases:

1. **Standard case:** call `create("An", "an@example.test")`, receive an ID; query by ID and confirm `name` and `email` match. Do not hard-code ID starting at `1`.
2. **Verify configuration at preparation time:** verify the implementation uses `Connection.prepareStatement(INSERT_SQL, RETURN_GENERATED_KEYS)` or the column-name overload inside `PreparedStatementCreator`; merely passing `KeyHolder` is insufficient.
3. **Failure path:** if the driver does not support it or returns no key, the method must fail explicitly rather than returning a dummy ID like `0`.
4. **Transaction rollback:** if the insert occurs inside a transaction that then rolls back, verify the record does not exist even though the program may have observed the generated ID.
5. **Compatibility:** run integration tests against the same DBMS/JDBC driver used in production; returned key results and column naming are driver-dependent.

When testing, use a real database or equivalent environment to verify key-return behavior. Mocks only confirm the callback called the right overload, not that the driver actually supplies keys.

## 8. Self-check questions

**Question 1.** Why is `jdbcTemplate.update(sql, args...)` insufficient if you need to return the newly generated ID?  
Because this overload returns the affected row count and does not populate keys into a `KeyHolder`. You need `update(PreparedStatementCreator, KeyHolder)` with a statement created in key-return-enabled mode.

**Question 2.** How do `Statement.RETURN_GENERATED_KEYS` and `new String[] {"id"}` differ?  
The first requests generated keys in general and lets the driver pick the appropriate columns; the second explicitly specifies the `id` column to retrieve. Both are passed when **creating** the `PreparedStatement`.

**Question 3.** If `executeUpdate()` returns `1`, does that guarantee `getGeneratedKeys()` contains `id = 1`?  
No. `1` is the updated row count; the generated key depends on the database/driver and must be read and checked separately.

## 9. Takeaways

```text
Connection / JdbcTemplate
        |
        v
prepareStatement(sql, RETURN_GENERATED_KEYS or ["id"])
        |
        v
setXxx(...) -> executeUpdate()
        |
        +--> affected row count (int)
        |
        v
getGeneratedKeys() / Spring KeyHolder
        |
        v
check key presence, column count, and key type before use
```

**Practical rule:** Request generated keys **when creating the `PreparedStatement`**; executing `INSERT` and reading the key result are the two subsequent steps. In Spring JDBC, `PreparedStatementCreator` determines whether the statement is configured properly, while `KeyHolder` only receives the result.
