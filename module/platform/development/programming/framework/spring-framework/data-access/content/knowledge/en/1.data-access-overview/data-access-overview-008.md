# End-to-End Example: Saving, Finding, and Updating an Order

## 1. Problem Statement and Learning Goals

Suppose a sales system needs three familiar operations: **saving** a new order with multiple product line items, **finding** an order by ID, and **updating** an order's status from NEW to PAID. This serves as an end-to-end example for the *Spring Framework Data Access* overview: a business workflow with relational data, multiple SQL statements, and consistency requirements.

After this lesson, you should be able to explain the data path from service to database; distinguish the roles of DataSource, repository, JDBC template, and transaction manager; understand why saving an order and its line items must share a transaction; handle not-found results; and prevent lost updates under concurrent modifications. The example uses **Spring JDBC** so SQL is directly visible. Spring Data JDBC and JPA can swap the access mechanism without changing the core business questions.

**Business rules:**

- Customer 42 buys 2 copies of BOOK-01 (120.00 each) and 1 PEN-01 (10.00). Total amount is 250.00.
- Upon creation, the order has status NEW and version = 0. After valid payment, status becomes PAID and version increments to 1.
- An order consists of a parent record in `orders` and multiple child records in `order_items`. A parent order must never exist if saving any child item fails.
- The example only simulates payment confirmation; it does **not** integrate a payment gateway or build an HTTP API. In a real system, verify reliable payment confirmation before marking PAID.

## 2. Data Flow Map

| Component | Responsibility in the Example |
| --- | --- |
| Application/runner | Sends requests to create, read, and pay for an order; in a web app, a controller would receive requests. |
| OrderService | Validates inputs, computes totals, orchestrates multiple operations, sets transaction boundaries, and enforces state-transition rules. |
| OrderRepository | Executes INSERT, SELECT, UPDATE; converts ResultSet rows into Java objects; does not decide payment business rules itself. |
| NamedParameterJdbcTemplate | Binds SQL parameters, handles repetitive JDBC mechanics, translates SQLException into Spring's DataAccessException hierarchy. |
| DataSource | Provides database connections; the connection is bound to the active transaction by the transaction manager. |
| Transaction manager | Begins, commits, or rolls back operations sharing a transaction. |
| Database | Durably stores data; enforces primary keys, foreign keys, data types, and update predicates. |

Create flow: caller → OrderService.create → compute total → OrderRepository.insertOrder → obtain generated key → insert each order_item → commit. If an unhandled error occurs midway, the transaction rolls back both the parent and any inserted child rows.

Find flow: caller → OrderService.find → repository SELECTs parent order → SELECTs line items → assembles OrderView. If the ID is not found, returns Optional.empty() without silently creating a new order.

Update flow: caller passes ID and previously read version → service issues conditional UPDATE checking status NEW and matching version → database reports affected row count. One row means success; zero rows means the record does not exist, already changed status, or was updated by another concurrent operation.

## 3. Sample Data and Table Schema

We use a compact model sufficient to illustrate a one-to-many relationship:

- **orders**: id, customer_id, status, total_amount, version.
- **order_items**: id, order_id, sku, quantity, unit_price.
- total_amount is computed in the service from quantity × unit_price and stored as DECIMAL; money in Java uses BigDecimal, never double.
- version is an integer for controlling concurrent updates. Each successful state transition increments version by 1.

Here is the H2 SQL for the example; place it in src/main/resources/schema.sql:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(16) NOT NULL,
    total_amount DECIMAL(19, 2) NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE order_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    sku VARCHAR(64) NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    unit_price DECIMAL(19, 2) NOT NULL CHECK (unit_price >= 0)
);
~~~

The foreign key prevents line items from referencing a nonexistent order. CHECK constraints protect data directly at the database, even if another application accesses it. These constraints alone do not recompute total_amount or enforce every state transition; the service and production data policies must still handle those.

### 4.1. Java Models

Place in src/main/java/example/orders/OrderModels.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;

record ItemInput(String sku, int quantity, BigDecimal unitPrice) {}

record OrderHeader(
        long id,
        long customerId,
        String status,
        BigDecimal totalAmount,
        long version) {}

record OrderLine(String sku, int quantity, BigDecimal unitPrice) {}

record OrderView(
        long id,
        long customerId,
        String status,
        BigDecimal totalAmount,
        long version,
        List<OrderLine> items) {}
~~~

ItemInput represents input data passed by the caller to the service. OrderHeader and OrderLine hold the results of two relational queries; OrderView combines them into a single business response. These records live in the same package as the service/repository and are intentionally package-private to keep the example concise.

### 4.2. Repository: SQL and Result Mapping

Place in src/main/java/example/orders/OrderRepository.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;
import java.util.Map;
import java.util.Optional;

import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class OrderRepository {
    private final NamedParameterJdbcTemplate jdbc;

    public OrderRepository(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public long insertOrder(long customerId, BigDecimal totalAmount) {
        KeyHolder keys = new GeneratedKeyHolder();
        int changed = jdbc.update("""
                INSERT INTO orders (customer_id, status, total_amount, version)
                VALUES (:customerId, 'NEW', :totalAmount, 0)
                """,
                new MapSqlParameterSource()
                        .addValue("customerId", customerId)
                        .addValue("totalAmount", totalAmount),
                keys,
                new String[] {"ID"});

        if (changed != 1 || keys.getKey() == null) {
            throw new IllegalStateException("Failed to retrieve order id");
        }
        return keys.getKey().longValue();
    }

    public void insertLine(long orderId, ItemInput item) {
        int changed = jdbc.update("""
                INSERT INTO order_items (order_id, sku, quantity, unit_price)
                VALUES (:orderId, :sku, :quantity, :unitPrice)
                """,
                new MapSqlParameterSource()
                        .addValue("orderId", orderId)
                        .addValue("sku", item.sku())
                        .addValue("quantity", item.quantity())
                        .addValue("unitPrice", item.unitPrice()));

        if (changed != 1) {
            throw new IllegalStateException("Failed to insert order item");
        }
    }

    public Optional<OrderHeader> findHeader(long id) {
        List<OrderHeader> rows = jdbc.query("""
                SELECT id, customer_id, status, total_amount, version
                FROM orders
                WHERE id = :id
                """,
                Map.of("id", id),
                (rs, rowNum) -> new OrderHeader(
                        rs.getLong("id"),
                        rs.getLong("customer_id"),
                        rs.getString("status"),
                        rs.getBigDecimal("total_amount"),
                        rs.getLong("version")));

        return rows.stream().findFirst();
    }

    public List<OrderLine> findLines(long orderId) {
        return jdbc.query("""
                SELECT sku, quantity, unit_price
                FROM order_items
                WHERE order_id = :id
                ORDER BY id
                """,
                Map.of("id", orderId),
                (rs, rowNum) -> new OrderLine(
                        rs.getString("sku"),
                        rs.getInt("quantity"),
                        rs.getBigDecimal("unit_price")));
    }

    public int markPaidIfUnchanged(long id, long expectedVersion) {
        return jdbc.update("""
                UPDATE orders
                SET status = 'PAID', version = version + 1
                WHERE id = :id
                  AND status = 'NEW'
                  AND version = :version
                """,
                Map.of("id", id, "version", expectedVersion));
    }
}
~~~

Points to examine closely:

1. Parameters `:customerId`, `:totalAmount`, `:id`… are bound via a prepared statement. Never concatenate input data into SQL strings, as that is both type-error-prone and opens the door to SQL injection.
2. `GeneratedKeyHolder` receives the database-generated `id` key. In H2, the auto-generated key column is requested by name `ID`. Another database/driver may require adjusting the column name or generated-key retrieval style.
3. `query` uses a `RowMapper` to convert each `ResultSet` row into a record. A `SELECT` can return an empty list; here `Optional` explicitly expresses "order not found."
4. `UPDATE` returns the affected row count; this count matters more than merely checking whether the SQL threw an exception. No exception does not mean a record was updated.
5. The Repository does not manually open/close `Connection`s or commit itself. The templates participate in the transaction Spring has bound to the current execution flow.

### 4.3. Service: Business Logic and Transaction Boundaries

Place in src/main/java/example/orders/OrderService.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long create(long customerId, List<ItemInput> items) {
        if (customerId <= 0 || items == null || items.isEmpty()) {
            throw new IllegalArgumentException("Invalid customer or items");
        }

        BigDecimal total = BigDecimal.ZERO;
        for (ItemInput item : items) {
            if (item == null
                    || item.sku() == null
                    || item.sku().isBlank()
                    || item.quantity() <= 0
                    || item.unitPrice() == null
                    || item.unitPrice().signum() < 0) {
                throw new IllegalArgumentException("Invalid order item");
            }
            total = total.add(
                    item.unitPrice().multiply(BigDecimal.valueOf(item.quantity())));
        }

        long orderId = repository.insertOrder(customerId, total);
        for (ItemInput item : items) {
            repository.insertLine(orderId, item);
        }
        return orderId;
    }

    @Transactional(readOnly = true)
    public Optional<OrderView> find(long id) {
        return repository.findHeader(id)
                .map(header -> new OrderView(
                        header.id(),
                        header.customerId(),
                        header.status(),
                        header.totalAmount(),
                        header.version(),
                        repository.findLines(header.id())));
    }

    @Transactional
    public void pay(long id, long expectedVersion) {
        int changed = repository.markPaidIfUnchanged(id, expectedVersion);
        if (changed != 1) {
            throw new IllegalStateException(
                    "Order does not exist, is no longer NEW, or version has changed");
        }
    }
}
~~~

In `create`, all `INSERT`s run inside the same transaction. By default, Spring rolls back when an unchecked exception (`RuntimeException`) or `Error` exits a transactional method. Constraint errors from JDBC are translated into `DataAccessException` (also a `RuntimeException`), so one failing line item rolls back the whole order. Never catch and swallow the exception midway, or the service could commit partial data.

In `find`, `readOnly = true` is an optimization hint expressing read-only intent; do not treat it as a security mechanism or a guarantee every database will reject writes. In `pay`, the version predicate prevents two concurrent requests from both assuming they are updating the same `NEW` state.

### 4.4. Running the Three Operations in Order

Place in src/main/java/example/orders/OrderDemoApplication.java:

~~~java
package example.orders;

import java.math.BigDecimal;
import java.util.List;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class OrderDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(OrderDemoApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(OrderService service) {
        return args -> {
            long id = service.create(42L, List.of(
                    new ItemInput("BOOK-01", 2, new BigDecimal("120.00")),
                    new ItemInput("PEN-01", 1, new BigDecimal("10.00"))));

            OrderView before = service.find(id).orElseThrow();
            System.out.printf(
                    "Created order #%d: %s, total %s, %d items, version=%d%n",
                    before.id(), before.status(), before.totalAmount(),
                    before.items().size(), before.version());

            service.pay(id, before.version());

            OrderView after = service.find(id).orElseThrow();
            System.out.printf(
                    "Reloaded order #%d: %s, total %s, version=%d%n",
                    after.id(), after.status(), after.totalAmount(),
                    after.version());
        };
    }
}
~~~

Using JDK 21 and a compatible Gradle (such as Gradle 8.5), run from the project directory:

~~~bash
gradle bootRun
~~~

With a fresh H2 database and the logging configuration above, the two lines printed by the program are:

~~~text
Created order #1: NEW, total 250.00, 2 items, version=0
Reloaded order #1: PAID, total 250.00, version=1
~~~

Order ID `#1` assumes the H2 database starts empty when the app launches. If switched to a database with existing rows, the ID may differ. The total remains `250.00` and a valid update still advances version from `0` to `1`.

## 5. Anatomy of Each Operation

### 5.1. Saving an Order: Consistency Between Parent and Child Tables

The Service computes the total 2 × 120.00 + 1 × 10.00 = 250.00, then inserts into `orders` to obtain the ID. Inserts into `order_items` use that ID as a foreign key. Because everything runs inside one transaction, **atomicity** applies: either the whole order persists successfully, or all effects of the transaction roll back.

Suppose inserting the second line violates the `VARCHAR(64)` length of the `sku` column. The database raises an error, and Spring translates it into `DataIntegrityViolationException` in the `DataAccessException` family. When the exception propagates out of `create`, the transaction rolls back both `orders` and any `order_items` written in that transaction. That is why the transaction belongs on the service—which understands the entire order as one unit of work—rather than on each individual `INSERT`.

Do not treat foreign keys as a substitute for transactions: a foreign key preserves referential validity, yet by itself does not guarantee "both the order and all its line items exist together." Similarly, `@Transactional` does not replace database constraints protecting data integrity.

### 5.2. Finding an Order: Data Mapping and Not-Found Handling

The first `SELECT` retrieves `id`, `customer_id`, `status`, `total_amount`, `version`; the second `SELECT` retrieves rows with matching `order_id`. The repository returns `OrderHeader` and `List<OrderLine>`; the service builds `OrderView`. If no parent row exists, `Optional.empty()` is returned without querying child lines.

Two queries serve a single order cleanly. When loading hundreds of orders, querying each order's line items separately creates an **N+1 query** problem. In that case, consider a JOIN, a batch query over the set of IDs, pagination, or a tailored projection. Reading one order in this example is intentional to highlight repository responsibilities.

### 5.3. Updating: Status Predicates and Optimistic Locking

The SQL transitions `NEW → PAID` only when `id`, `status`, and `version` all match. Consider two tasks that both read `version = 0`:

1. Task A updates first: the database sets status to `PAID`, version to `1`, and returns updated row count = `1`.
2. Task B still sends `expectedVersion = 0`: the `WHERE` predicate no longer matches, updated row count = `0`, and the service reports a business conflict.

This is SQL-level **optimistic locking**; there is no need to hold database locks while a user views and processes the order. However, a conditional `UPDATE` is not enough for every concurrency problem: adjusting inventory quantities, debiting/crediting balances, or mutating multiple records may require proper isolation, explicit locking, or a different transaction design. Never assume a pre-update read check is safe if the final `UPDATE` lacks a condition.

## 6. Scenarios to Verify Yourself

| Scenario | Expected Outcome | Governing Mechanism |
| --- | --- | --- |
| Create order with two valid items | One `orders` row and two `order_items` rows committed; total 250.00 | `@Transactional` and generated id |
| Find nonexistent ID | `Optional.empty()` | `SELECT` + `Optional` mapping |
| A line item violates a constraint after parent order `INSERT` | No partial data from the transaction remains | Rollback triggered by `DataAccessException` |
| Pay `NEW` order with matching version | One row updated, status `PAID`, version +1 | Conditional `UPDATE` |
| Resend stale version or pay a second time | Zero rows updated; service throws error | `status`/`version` in `WHERE` |
| Database unreachable | Operation fails with a data access exception | `DataSource` and `DataAccessException` |

To verify rollback, try passing an `sku` longer than 64 characters (after noting the baseline row counts), catch the exception in the caller outside the transaction, and check `orders`/`order_items` counts before and after via count queries. Do not catch the exception inside `create` and return normally. To verify conflict detection, retain the version read before a successful `pay` call and attempt to `pay` again with that stale version.

## 7. Real-World Choices and Common Mistakes

**Choosing the data access mechanism.** Plain JDBC requires managing `Connection`, `PreparedStatement`, `ResultSet`, and transactions manually. Spring JDBC still uses developer-written SQL while reducing boilerplate, managing `DataSource`, and unifying exceptions. Spring Data JDBC/JPA provide higher-level repository/aggregate or entity mapping; whichever tool you choose, you must still define business boundaries, transactions, constraints, queries, and concurrent updates.

**Never misplacing transactions.** `@Transactional` normally works via a Spring proxy. Calling a transactional method from another bean—like `runner → service` in this example—is the proper case. A method in the same object directly calling another `@Transactional` method (self-invocation) can bypass the proxy, so never assume the annotation will apply. Moreover, transactions do not span network calls or wrap external systems.

**Never using `double` for money.** Use `BigDecimal` and decimal columns, with explicit currency, scale, and rounding rules. The sample uses two decimal places; production systems should normalize input prices and guard against numeric overflow/limits.

**Never conflating technical errors with business errors.** Not finding an order is an expected business outcome. Losing a database connection, duplicate keys, or constraint violations are data access errors. An `UPDATE` returning `0` could mean a wrong ID, disallowed status, or stale version; if an API needs distinct error codes, the service must distinguish them via appropriate logic or follow-up queries while preserving concurrency safety. Never return raw SQL or connection details to end users.

**Never building SQL from raw input.** Named parameters safely bind values; dynamic table/column names or `ORDER BY` clauses are not protected by placeholders. If dynamic SQL is needed, use an allowlist of verified identifiers.

**Never treating H2 as proof of compatibility across all databases.** H2 is handy for learning, yet dialects, generated keys, isolation, numeric precision, and constraints can differ from PostgreSQL, MySQL, or other DBMSs. Production requires versioned migrations (e.g., Flyway/Liquibase), indexes, tests against the target database, connection pool policies, and transaction monitoring. Real payment systems also need idempotency, provider confirmation, and consistent event handling.

## 8. Self-Check Questions

1. If you remove `@Transactional` from `create`, what can happen when inserting the second line item fails?
2. Why must the service compute `totalAmount` before saving, while the database still needs `CHECK` and foreign keys?
3. How does finding a nonexistent ID differ from a lost database connection error?
4. Why does updating status by `id` alone risk lost updates when two requests arrive nearly simultaneously?
5. Why is `@Transactional(readOnly = true)` not a mechanism for enforcing `SELECT` permissions?
6. If you switch the repository to JPA, which service and database responsibilities stay the same?

**Key takeaway:** Data problems do not stop at "making the SQL run." A correct order operation needs valid data, clear mapping, transaction boundaries covering the business unit of work, explicit not-found handling, and concurrency control. Spring Data Access provides the infrastructure to enforce these consistently; designing the business rules remains the application's responsibility.
