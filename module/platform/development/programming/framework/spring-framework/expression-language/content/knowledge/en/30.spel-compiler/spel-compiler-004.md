# Conditions for an expression to be compilable in SpEL

## 1. What is SpEL compilation?

Spring Expression Language (SpEL) usually evaluates expressions using an interpreter. The interpreter performs each operation on objects and data at runtime. This approach is flexible because SpEL does not require static type declarations for every part of an expression, but it can incur overhead when the same expression is evaluated very many times.

The SpEL compiler can generate a Java class containing the expression's behavior and use that class in subsequent evaluations. The goal is to reduce repeated overhead in paths where an expression is used frequently.

The compiler cannot compile every expression. To generate bytecode, it needs enough information about the nodes in the expression, especially property types, method results, and operands. Because SpEL is dynamic, part of the type information is often known only after the expression has run through the interpreter.

Expressions suitable for compilation typically have these characteristics:

- Evaluated repeatedly enough for compilation cost to be worthwhile.
- Object structures and data types are stable across evaluations.
- Accessed properties and methods have clear types.
- Do not depend on syntax or resolvers not yet supported by the compiler.
- Do not change input data types in ways that make the generated bytecode unsuitable.

Compilation is a performance optimization. The expression still needs to be correct when run in interpreted mode; do not rely on the compiler to fix data errors or change semantics.

## 2. Where does the compiler get type information from?

SpEL does not have a full static type system like Java. With the expression:

~~~text
payload.customer.name
~~~

The parser knows the property names, but does not necessarily know the runtime types of payload, customer, and name from the expression string alone.

When the interpreter evaluates the expression against a real root object, it observes the types of intermediate values and access results. The compiler can use this collected information to generate corresponding bytecode.

Example:

~~~java
public class Customer {
    private final String name;

    public Customer(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

public class Payload {
    private final Customer customer;

    public Payload(Customer customer) {
        this.customer = customer;
    }

    public Customer getCustomer() {
        return customer;
    }
}

public class Message {
    private final Payload payload;

    public Message(Payload payload) {
        this.payload = payload;
    }

    public Payload getPayload() {
        return payload;
    }
}
~~~

Evaluating the expression:

~~~java
Expression expression = parser.parseExpression("payload.customer.name");

Message message = new Message(
        new Payload(new Customer("Lan")));

String name = expression.getValue(message, String.class);
~~~

After the interpreted evaluation, SpEL has additional runtime information about the properties along the path. If those types remain stable, the expression may be suitable for the compiler to generate bytecode.

If one evaluation uses Customer while on another call the customer property returns a different object type, the information used for compilation may no longer be accurate. This is why type stability is an important condition.

## 3. Expression forms that are usually suitable

The compiler targets common expressions on high-performance execution paths. Cases that are usually suitable when data types are stable include:

- Reading properties from a root object or nested objects.
- Accessing array elements by index in supported forms.
- Performing arithmetic and comparison operations on known types.
- Evaluating logical conditions or simple conditional expressions.
- Invoking methods that can be clearly resolved with stable target and argument types.
- Using values and types that the compiler can determine from interpreted evaluations.

Example of an expression with property access, index access, and arithmetic:

~~~java
Expression expression = parser.parseExpression(
        "measurements[0].value * 1.8 + 32");

Double fahrenheit = expression.getValue(
        sensorReading,
        Double.class);
~~~

If measurements is always an array or collection with a stable element type, the first element always has a value property of a compatible type, and the operations always receive known types, the expression can be a candidate for compilation.

There is no simple rule such as "the shorter the expression, the easier it is to compile." What decides it is whether the compiler can generate bytecode from the nodes and collected type information.

## 4. Expressions not supported by the compiler

The SpEL compiler currently does not support compiling the following forms:

- Expressions with assignment.
- Expressions relying on ConversionService.
- Expressions using custom resolvers.
- Expressions using overloaded operators.
- Expressions using Optional together with the null-safe operator or Elvis operator.
- Expressions using array creation syntax.
- Expressions using selection or projection.
- Expressions using bean references.

Examples of forms that must continue to be evaluated by the interpreter:

~~~text
quantity = 10
items.?[active]
items.![name]
@pricingService.calculate(amount)
~~~

If an expression contains an unsupported operation, the compiler cannot create a compiled form for that expression. Enabling compiler mode does not mean every expression is automatically optimized.

Expressions relying on ConversionService or custom resolvers need to keep the interpreter's conversion/resolution mechanism. Check the limitation list for the Spring Framework version the application uses, as support scope can change across versions.

## 5. Data types must be stable across evaluations

The compiler uses types observed from interpreted evaluations. If input data changes types, the compiled expression may no longer be compatible.

For example, the same property may return different types:

~~~java
public class DynamicMessage {
    private Object payload;

    public Object getPayload() {
        return payload;
    }

    public void setPayload(Object payload) {
        this.payload = payload;
    }
}
~~~

Expression:

~~~text
payload.toString()
~~~

The first time payload may be a String, and the next time it may be a different object. For expressions dependent on runtime types, the compiler may generate bytecode based on the type from a previous evaluation and fail when the type changes.

Cases to watch out for:

- A property declared as Object that returns unrelated types at runtime.
- A method returning different types depending on branches or data state.
- A collection containing elements of multiple different types.
- A root object changing structure or type across evaluations.
- A value that can be null on some calls and an object of a concrete type on others.
- A runtime proxy or implementation changing across environments.

If data types are unstable, keep the compiler OFF or consider MIXED after testing behavior and side effects. Do not use IMMEDIATE based solely on a single representative data sample.

## 6. Nulls and property paths

Nulls need separate consideration when assessing compilability. One interpreted evaluation may observe a concrete object type, while on the next call an intermediate property may be null or return different data.

Example:

~~~text
customer.address.city
~~~

If customer or address can be null, a regular expression may throw an evaluation error. Null-safe navigation:

~~~text
customer?.address?.city
~~~

can help the expression handle null points according to business intent. However, using the null-safe operator does not by itself guarantee the expression is supported by the compiler. The compiler has its own limitation list; check the specific syntax and framework version.

At minimum, test these cases:

- Root object with all properties populated.
- Intermediate property is null.
- Final property is null.
- Same expression evaluated with root objects of different actual types.

If data has many null states and frequently changing types, the interpreter may be a more predictable choice. Do not enable compilation just to work around null handling in the model.

## 7. Configuring SpelCompilerMode

The compiler has three modes in the SpelCompilerMode enum:

| Mode | Behavior |
|---|---|
| OFF | Disables the compiler; every expression is evaluated by the interpreter. This is the default. |
| IMMEDIATE | Compiles expressions as soon as possible, usually after the first interpreted evaluation. Errors when running the compiled form are returned to the caller. |
| MIXED | After a number of successful interpreted evaluations, the expression is compiled. If the compiled form fails, SpEL switches back to the interpreter and may attempt to recompile later. |

OFF is appropriate when expressions are evaluated infrequently, data types change, or the compiler brings no significant benefit.

IMMEDIATE is better suited for expressions with stable, verified types and without hard-to-repeat side effects. If the compiled form fails, the exception is surfaced to the caller.

MIXED allows switching between interpreted and compiled during execution. It can be suitable when gradual optimization is desired while keeping the ability to fall back to the interpreter if the compiled form runs into problems. However, fallback can re-evaluate the expression after partial execution; be cautious with side effects.

## 8. Configuring the compiler with SpelParserConfiguration

The mode and class loader can be configured when creating the parser:

~~~java
import org.springframework.expression.spel.SpelCompilerMode;
import org.springframework.expression.spel.SpelParserConfiguration;
import org.springframework.expression.spel.standard.SpelExpressionParser;

SpelParserConfiguration configuration =
        new SpelParserConfiguration(
                SpelCompilerMode.MIXED,
                MyApplication.class.getClassLoader());

SpelExpressionParser parser =
        new SpelExpressionParser(configuration);

Expression expression =
        parser.parseExpression("payload.customer.name");
~~~

This configuration applies to expressions created by the corresponding parser. A parser does not automatically alter any other parsers in the application.

OFF, IMMEDIATE, or MIXED can be used depending on requirements. If no mode is specified, the compiler is disabled by default.

Recent Spring Framework versions provide a builder API for SpelParserConfiguration. Use the API appropriate for the actual dependency version; the constructor above is a configuration pattern common across many versions.

## 9. Choosing a ClassLoader for compiled expressions

Compiled expressions are defined in a child ClassLoader. The child loader is created on top of the class loader supplied by the application; it needs to see all types involved in evaluating the expression.

The application's class loader can be passed in:

~~~java
SpelParserConfiguration configuration =
        new SpelParserConfiguration(
                SpelCompilerMode.IMMEDIATE,
                MyApplication.class.getClassLoader());
~~~

If no class loader is passed, SpEL uses a default class loader, typically the context ClassLoader of the thread evaluating the expression.

The class loader is especially important when the application runs in:

- An application server with multiple class loaders.
- A plugin system or modules with separate class loaders.
- A runtime environment with proxies or dynamically generated classes.
- An application with domain types residing in a module not visible from the thread context class loader.

If the compiled expression cannot see the class of the root object or properties, compilation or class loading may fail. Choose a class loader that can access all involved types and test in the real runtime environment.

## 10. Enabling the compiler via system property

When SpEL is used inside another module and it is not easy to configure the parser directly, a property can be set:

~~~text
spring.expression.compiler.mode=off
spring.expression.compiler.mode=immediate
spring.expression.compiler.mode=mixed
~~~

JVM configuration example:

~~~text
-Dspring.expression.compiler.mode=mixed
~~~

Spring also supports the SpringProperties mechanism for this property. Valid values correspond to the OFF, IMMEDIATE, and MIXED modes.

This configuration affects how integrated parsers obtain the default compiler mode. Consider the scope of impact before enabling it at the JVM or SpringProperties level, especially when the application has multiple modules using SpEL with different kinds of EvaluationContext.

If only one expression path needs compilation, configuring a specific parser is usually easier to scope and control than enabling it globally.

## 11. Explicitly requesting compilation for an expression

With SpelExpression, compilation of an expression can be requested after it has been evaluated in interpreted mode and has sufficient type information:

~~~java
SpelExpressionParser parser = new SpelExpressionParser();

SpelExpression expression = (SpelExpression) parser.parseExpression(
        "payload.customer.name");

Message message = TestData.message("Lan");

// Collect type information via interpreted evaluation.
String firstResult = expression.getValue(message, String.class);

// Request the compiler to generate the compiled form.
boolean compiled = expression.compileExpression();

if (compiled) {
    String nextResult = expression.getValue(message, String.class);
}
~~~

compileExpression returns true if the expression already has or just created a compiled form. It can return false if the compiler lacks enough information or the expression contains an unsupported node.

An expression can be returned to interpreted mode:

~~~java
expression.revertToInterpreted();
~~~

This API is useful for testing or when the application manages compilation explicitly. In most cases, configuring compiler mode on the parser is sufficient; there is no need to manually manage compile/revert without a clear reason.

## 12. IMMEDIATE and MIXED have different error behaviors

These two modes differ in how they handle errors from a compiled expression.

In IMMEDIATE:

- The expression is compiled early.
- If the compiled form fails during evaluation, the exception is returned to the caller.
- The caller sees the error and can handle it according to application policy.

In MIXED:

- The expression is evaluated in interpreted mode a number of times before compiling.
- If the compiled form fails, the error is handled internally and the expression returns to interpreted mode.
- Afterward, the compiler may try again; if it keeps failing enough times, the expression may be kept in interpreted mode.

MIXED can hide the fact that the compiled form no longer matches the data types. Therefore, monitor performance and runtime errors instead of just enabling the mode and assuming every expression compiled successfully.

## 13. Why does MIXED require caution with side effects?

MIXED can fall back to the interpreter after a compiled expression encounters an error. If the expression already performed part of an operation with side effects before the error, the subsequent interpreted evaluation may re-execute part of the logic.

For example, an expression calling a state-mutating method:

~~~text
counter.incrementAndGet()
~~~

If the compiled form performs part of the operation and then fails, fallback may cause the method to be called an additional time. That can change counters or state more than expected.

For expressions with side effects:

- Prefer pure expressions that only read data and compute results.
- Avoid calling methods that write data, send messages, or perform transactions from within an expression.
- If side effects cannot be eliminated, understand MIXED's fallback risk.
- Consider OFF or IMMEDIATE depending on the contract and error-handling strategy.

IMMEDIATE exists in part because callers may want to receive a clear exception rather than letting MIXED silently re-run the expression using the interpreter.

## 14. How to determine whether an expression can compile

Do not infer compilability from visible syntax alone. The compileExpression API can be used after an evaluation to check the actual result:

~~~java
SpelExpression expression = (SpelExpression) parser.parseExpression(
        "payload.customer.name");

Message message = TestData.message("Lan");
expression.getValue(message);

boolean compilable = expression.compileExpression();
~~~

If compilable is false, keep the expression in interpreted mode. Do not alter logic just to force the compiler to accept an expression that inherently depends on custom resolvers or a conversion service.

In tests, record:

- Expression source.
- Parser configuration and compiler mode.
- Root object and runtime types.
- Result of interpreted evaluation.
- Result of compileExpression.
- Evaluation result after compilation.
- Behavior when data changes type or contains null.

This check is a technical test of the compiler, not a guarantee that the expression will always compile in every runtime environment.

## 15. Measuring performance before and after compilation

The compiler targets expressions evaluated frequently. For an expression that runs only once, the cost of parsing, context creation, and compilation may outweigh the time saved.

The measurement workflow should include:

1. Identify expressions on hot paths using profiling.
2. Use representative data with stable types.
3. Measure the interpreter after the JVM has warmed up.
4. Measure compiled mode with the same data and workload.
5. Compare throughput, latency, and memory/class-loading overhead.
6. Check behavior when data contains null or types different from warm-up data.

Do not use a single microbenchmark as proof that the compiler improves the entire application. Measure on realistic workloads and include startup, compilation, and class-loading costs.

## 16. Testing boundary conditions

An expression may compile with warm-up data yet fail when real-world data changes. Tests should cover the types and states that can appear:

| Case | What to verify |
|---|---|
| Standard root object | Interpreted and compiled results are equivalent |
| Null intermediate property | Null/error behavior matches the expression |
| Empty collection | Result and index errors match the contract |
| Changing runtime type | Compiled mode may fail; MIXED falls back per policy |
| Custom resolver or ConversionService | Confirm the expression needs the interpreter if unsupported by the compiler |
| Bean reference | Do not assume a compiled form is created |
| Selection/projection | Keep interpreter because the compiler does not support these nodes |
| Expression with side effects | Avoid fallback that could repeat operations |

Test both warm-up data and data appearing after the expression has compiled. Testing only the first call will not catch errors caused by type assumptions.

## 17. Compiler limitations and mode selection

| Scenario | Handling approach |
|---|---|
| Simple expression, runs rarely | OFF |
| Expression reading properties and computing repeatedly, stable types | Try MIXED or IMMEDIATE after benchmarking |
| Expression with changing runtime types | OFF or MIXED after testing |
| Expression using selection/projection | Interpreter |
| Expression relying on custom resolver or ConversionService | Interpreter |
| Expression with bean reference | Interpreter |
| Expression with side effects | Prefer OFF or choose mode after analyzing re-execution possibility |
| Expression lacking enough type info to compile | Keep interpreted mode |

There is no need to enable the compiler for the entire application to optimize one expression. Limit compilation to the parsers and paths that genuinely need that performance.

## 18. Security note with SimpleEvaluationContext

SimpleEvaluationContext is designed to restrict SpEL capabilities, typically used for controlled data binding or property access. Do not assume that enabling the compiler for a restricted context always preserves all interpreter safety guards.

Spring published CVE-2026-59283 on August 20, 2026 regarding potential safety guard bypass when the SpEL compiler operates with SimpleEvaluationContext. The advisory describes cases where an application uses SimpleEvaluationContext while enabling compiler mode IMMEDIATE or MIXED, via parser configuration or a global property. Compiled expressions could bypass safety guards enforced during interpreted evaluation; the advisory also notes the risk of unbounded class-loading growth when many distinct expressions are compiled.

Affected versions listed by the advisory include:

- Spring Framework 7.0.0 to 7.0.8.
- Spring Framework 6.2.0 to 6.2.19.
- Spring Framework 6.1.0 to 6.1.28.
- Spring Framework 6.0.0 to 6.0.30.
- Spring Framework 5.3.0 to 5.3.49.
- Spring Framework 5.2.25.RELEASE and older versions.

Fixed versions mentioned by the advisory include 7.0.9, 6.2.20, 6.1.29, 6.0.31, 5.3.50, and 5.2.26; some branches have Enterprise Support releases only. Check the official advisory to confirm the support branch and patch appropriate for the application.

In the fixed versions, SimpleEvaluationContext does not support expression compilation by default, regardless of where compiler mode is configured. Applications should only explicitly call withCompilationSupported() on the builder if expressions are trusted and the removal of safety guards in compiled evaluation has been clearly assessed.

Do not enable compilation for SimpleEvaluationContext when evaluating untrusted expressions. Upgrading to a patched version is the primary remediation if the application uses an affected configuration.

## 19. Common mistakes

**Assuming every expression can be compiled**

The compiler only supports a subset of SpEL. Expressions using assignment, selection, projection, bean references, custom resolvers, or a conversion service do not belong to the currently supported set.

**Compiling before type information is available**

The compiler may not yet know enough runtime types to generate bytecode. Evaluate in interpreted mode first and check the compileExpression result.

**Using a single data sample to conclude types are always stable**

Production data can have nulls, subclasses, proxies, or other types. Test real-world variants before enabling the compiler.

**Enabling IMMEDIATE for expressions with side effects**

A compiled failure will be returned to the caller; however, side effects that already occurred before the error may still remain. Design expressions to be pure and predictable.

**Enabling MIXED without understanding fallback**

MIXED can fall back to the interpreter after a compiled-form error and may retry compilation. If the expression has side effects, re-evaluation must be examined carefully.

**Just enabling the system property without checking modules**

A global property can affect parsers created inside other modules. Identify which modules use SpEL and which contexts will be affected.

**Ignoring the ClassLoader**

The compiled class needs to see all types used in the expression. An unsuitable ClassLoader can cause compilation or loading errors.

**Ignoring security advisories**

SimpleEvaluationContext has its own safety guards. Check the Spring Framework version and CVE-2026-59283 advisory before enabling the compiler in this context.

## 20. Comprehensive example

The example below creates a parser in MIXED mode, evaluates an expression on an object with stable types, and checks compilability:

~~~java
import org.springframework.expression.spel.SpelCompilerMode;
import org.springframework.expression.spel.SpelParserConfiguration;
import org.springframework.expression.spel.standard.SpelExpression;
import org.springframework.expression.spel.standard.SpelExpressionParser;

SpelParserConfiguration configuration =
        new SpelParserConfiguration(
                SpelCompilerMode.MIXED,
                MyApplication.class.getClassLoader());

SpelExpressionParser parser =
        new SpelExpressionParser(configuration);

SpelExpression expression =
        (SpelExpression) parser.parseExpression(
                "payload.customer.name");

Message message = TestData.message("Lan");

// First run with the interpreter to collect type information.
String interpretedResult =
        expression.getValue(message, String.class);

// Compilation can be requested explicitly after type information is available.
boolean compiled = expression.compileExpression();

String nextResult =
        expression.getValue(message, String.class);

System.out.println(interpretedResult); // Lan
System.out.println(nextResult);        // Lan
System.out.println(compiled);          // true if compilation succeeds
~~~

In real applications, there is no need to call compileExpression manually when parser mode already manages compilation. This example illustrates how to observe compilability and compare results on the same root object type.

If the expression is unsupported or lacks type information, compileExpression may return false. Continue using the interpreter and preserve the expression's behavior.

## 21. Takeaways

- The SpEL compiler generates bytecode to speed up repeatedly evaluated expressions.
- The compiler uses type information gathered from interpreted evaluation; runtime types need to be stable.
- The compiler does not support all syntax; assignment, selection, projection, bean references, custom resolvers, and ConversionService-dependent expressions are among those that cannot be compiled.
- OFF is the default; IMMEDIATE returns compiled evaluation errors to the caller; MIXED can fall back to the interpreter and attempt to recompile.
- MIXED requires caution with side effects because fallback can cause the expression to be evaluated again.
- Configure the parser via SpelParserConfiguration and choose a ClassLoader that sees all involved types.
- compileExpression and revertToInterpreted can be used when explicit compilation management is needed.
- Benchmark on real workloads before enabling the compiler.
- Test changing data types, nulls, empty collections, and unsupported expressions.
- Do not enable compilation with SimpleEvaluationContext on versions affected by CVE-2026-59283; upgrade to a patched version and only opt in when expressions are trusted.
- Separate performance optimization from security design and EvaluationContext permissions.
