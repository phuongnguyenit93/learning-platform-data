# Reading the expression string and expression tree when diagnosing errors

When a Spring Expression Language (SpEL) expression behaves incorrectly, looking only at the final exception is often not enough to find the root cause. It is necessary to identify the exact source expression that was parsed, the structure that the parser created, the object and variables used during evaluation, and the position where the error occurred.

SpEL provides two useful perspectives:

- **Expression string**: the input expression string that the application sends to the parser.
- **Expression tree (AST)**: the abstract syntax tree that the parser builds to represent operators, property accesses, method calls, literals, and subcomponents.

Reading these two perspectives helps distinguish syntax errors from runtime data errors, determine how a complex expression was broken down into parts, and narrow down the location to inspect. The AST serves diagnostics; you should not rely on the internal class name of each node to build business logic because the implementation structure may change across Spring versions.

## 1. Two things to observe when debugging

### 1.1. Expression string

The expression string is the source that the application passes to ExpressionParser:

~~~java
String source =
        "orders.?[total >= #minimum].![id]";
~~~

This string represents the syntax written by a developer or generated by a system. When debugging, preserve the exact source used in the failed evaluation, including:

- Whitespace and parentheses/brackets.
- Property and method names.
- Literals and literal types.
- Variable names starting with #.
- Bean references starting with @ if allowed.
- Indexes, selections, projections, and nested operators.

Do not only log a string that has been reformatted or reconstructed from data after the error occurred. If the source is dynamically generated, save the exact version passed to the parser so the error can be reproduced.

### 1.2. Expression tree (AST)

The parser parses the source into a node structure. Each node represents a syntactic component or an operation.

For example:

~~~java
orders.?[total >= #minimum].![id]
~~~

At a conceptual level, the expression has:

- Accessing the orders property.
- A selection operation on the collection.
- A comparison of total with the #minimum variable.
- A projection operation to extract id.

The AST shows the parent/child relationships among those components. When traversing the tree, you can see the root node, child nodes, source positions, and the AST representation of each node.

The AST is useful when the source is long or automatically generated, because it shows the structure into which the parser interpreted the expression. However, the AST does not contain the full runtime state such as the actual value of each property, which bean was resolved, or the data returned by a method.

### 1.3. Source and AST serve different purposes

| Perspective | Answers the question | Use when |
|---|---|---|
| Expression string | What exact string did the parser receive? | Checking the source, special characters, dynamically concatenated data |
| AST | What components did the parser interpret the string into? | Analyzing operators, structural order, and child nodes |
| EvaluationContext | On which object and variables is the expression evaluated? | Finding data, accessor, resolver, and converter errors |
| Exception | Which operation failed and at what position? | Narrowing down the runtime or parse cause |

Do not use the AST in place of the original source. An AST may provide a normalized representation, but it does not necessarily preserve the original whitespace or writing style.

## 2. Getting the expression string from Expression

### 2.1. Keep the source before parsing

When the application receives or builds an expression, you should keep the source in a separate variable:

~~~java
String source = "total >= #minimum";

ExpressionParser parser = new SpelExpressionParser();
Expression expression = parser.parseExpression(source);
~~~

This approach helps log the exact parsed string and makes it convenient when reproducing errors.

If the source is fetched from a database or configuration, you should also store the identifier and configuration version. Two expressions with the same rule name but different sources can produce different results.

### 2.2. Using getExpressionString()

The Expression interface provides the getExpressionString() method:

~~~java
String expressionString = expression.getExpressionString();
~~~

You can log the source together with the rule identifier:

~~~java
logger.debug(
        "Evaluating ruleId={}, expression={}",
        ruleId,
        expression.getExpressionString()
);
~~~

For an expression created by a standard parser, this method returns the expression string associated with the Expression object. Keep the input source separately if you need to guarantee an exact record of the initial payload or if the application uses a parser context/template.

### 2.3. Expression template

SpEL also supports template expressions, in which regular text is interleaved with delimited expression sections:

~~~java
String template =
        "Hello #{customer.name}, order total is #{order.total}";
~~~

Parsing a template:

~~~java
ExpressionParser parser = new SpelExpressionParser();

Expression expression = parser.parseExpression(
        template,
        new TemplateParserContext()
);
~~~

When debugging a template, record both the template source and the parser context. An error may lie inside an embedded expression segment, while the plain text portion remains valid.

Do not assume a template's AST has the same structure as a pure expression's AST. The template parser may produce a structure combining literal and expression segments.

## 3. Getting the AST from SpelExpression

### 3.1. ExpressionParser returns the Expression interface

Typically an application parses using the interface:

~~~java
Expression expression =
        parser.parseExpression("total >= #minimum");
~~~

The Expression interface provides operations to evaluate, get the result type, and get the expression string. To access SpEL's specific node tree, you can check whether the implementation is SpelExpression.

~~~java
if (expression instanceof SpelExpression spelExpression) {
    SpelNode ast = spelExpression.getAST();
}
~~~

SpelExpression belongs to package:

~~~java
org.springframework.expression.spel.standard.SpelExpression
~~~

SpelNode belongs to package:

~~~java
org.springframework.expression.spel.SpelNode
~~~

### 3.2. Using getAST()

Example of getting the root node:

~~~java
SpelExpression spelExpression =
        (SpelExpression) parser.parseExpression(
                "total >= #minimum"
        );

SpelNode ast = spelExpression.getAST();
~~~

The root node represents the parsed expression structure. From this node, you can read the AST representation, the number of child nodes, and traverse child nodes via the SpelNode API.

Casting is only appropriate when you know the parser being used returns SpelExpression. If the application receives an Expression from another implementation or a wrapper, check the type before accessing SpelExpression-specific APIs.

### 3.3. Using toStringAST()

SpelNode provides the toStringAST() method:

~~~java
String astText = ast.toStringAST();
~~~

Example:

~~~java
SpelExpression spelExpression =
        (SpelExpression) parser.parseExpression(
                "total >= #minimum"
        );

String astText =
        spelExpression.getAST().toStringAST();
~~~

toStringAST() returns the syntactic representation of the node or subtree. It is useful for seeing how the parser represented the expression.

This is not a byte-for-byte copy of the source. Whitespace, unnecessary parentheses, or certain formatting details may not be preserved. When you need to reproduce the exact input, use getExpressionString() or the saved source.

## 4. Traversing the expression tree

### 4.1. Methods of SpelNode

SpelNode provides the main methods for traversing and inspecting the tree:

- **getChildCount()**: number of direct child nodes.
- **getChild(index)**: gets the child node at the given index.
- **getStartPosition()**: start position of the node in the source.
- **getEndPosition()**: end position as provided by the node information.
- **toStringAST()**: AST representation of the node.

You can use these methods to build a text-based debug tree without depending on the class name of each node implementation.

### 4.2. Recursive tree-printing function

Example of an AST traversal function:

~~~java
static void printTree(SpelNode node, int depth) {
    String indent = "  ".repeat(depth);

    System.out.printf(
            "%s%s [%d, %d] %s%n",
            indent,
            node.getClass().getSimpleName(),
            node.getStartPosition(),
            node.getEndPosition(),
            node.toStringAST()
    );

    for (int i = 0; i < node.getChildCount(); i++) {
        printTree(node.getChild(i), depth + 1);
    }
}
~~~

Usage:

~~~java
SpelExpression expression =
        (SpelExpression) parser.parseExpression(
                "orders.?[total >= #minimum].![id]"
        );

printTree(expression.getAST(), 0);
~~~

The code snippet illustrates printing the node class name, source positions, and AST representation of each node. Specific node class names and how the parser organizes child nodes are implementation details; you should not write tests that depend on the exact entire tree across Spring versions unless that is the goal of the test.

If the application runs on a Java version prior to String.repeat() support, you can replace the indent creation with a compatible helper.

### 4.3. Traversing the tree without assuming depth

Do not read only the root node and one level of child nodes. Expressions can be nested many levels deep:

~~~java
orders.?[
    customer != null
    && customer.active
    && total >= #minimum
].![id]
~~~

Traverse recursively or use a stack to process the entire tree. Each node may have a different number of child nodes; do not assume all node types have the same structure.

### 4.4. Using a stack instead of deep recursion

If the source is system-generated and may be deeply nested, recursive traversal can increase call stack depth. You can use a Deque:

~~~java
Deque<SpelNode> pending = new ArrayDeque<>();
pending.push(root);

while (!pending.isEmpty()) {
    SpelNode node = pending.pop();

    System.out.println(node.toStringAST());

    for (int i = node.getChildCount() - 1; i >= 0; i--) {
        pending.push(node.getChild(i));
    }
}
~~~

The example above performs depth-first traversal and preserves left-to-right child node order by pushing in reverse. If you need to store depth or parent, put the node along with metadata in a separate record or object on the stack.

## 5. Understanding nodes in an expression

### 5.1. Literal

Expression:

~~~java
'Spring'
~~~

or:

~~~java
42
~~~

contains a node representing a literal. A literal provides a fixed value recognized by the parser.

When debugging, inspecting literals helps detect issues such as:

- Improperly opened/closed string quotes.
- Numeric values with unexpected formatting.
- Literal type incompatible with the target method or property.
- Source generator escaping characters incorrectly.

### 5.2. Property access

Expression:

~~~java
customer.address.city
~~~

has chained property access components. During evaluation, SpEL must resolve each step through an appropriate PropertyAccessor.

If an error occurs at city, check:

- Whether customer is null.
- Whether address is null.
- The actual types of customer and address.
- Whether the city property exists and the accessor can read it.
- Whether the getter throws an exception or performs backend access.

The AST shows the property path that the parser recognized. It does not show the runtime value of each step.

### 5.3. Method call

Expression:

~~~java
customer.findAddress('HOME')
~~~

has nodes representing the target, method name, and argument. During evaluation, MethodResolver finds a matching executor and the arguments are evaluated/converted.

If method resolution fails, check the method name, number of arguments, argument types, and configured resolvers. If the method is invoked but throws an exception, inspect the cause from the Java logic inside.

### 5.4. Operator

Expression:

~~~java
total >= #minimum && active
~~~

combines comparison and logical operator nodes. The AST helps show how the parser groups operators and operands.

Use parentheses when you want to express precedence explicitly:

~~~java
(total >= #minimum) && active
~~~

Do not rely on readers memorizing every precedence level when an expression has multiple operators. A readable expression speeds up debugging and reduces the risk of logic differing from intent.

### 5.5. Selection and projection

Selection:

~~~java
orders.?[total >= #minimum]
~~~

Projection:

~~~java
orders.![id]
~~~

The AST represents the selection/projection along with the predicate or expression applied to each element. During evaluation, #this changes to the current element while #root remains the context's root object.

If selection returns empty or projection yields unexpected results, inspect both the source collection node and the predicate/projection. The syntax tree cannot tell what elements the runtime collection contains.

### 5.6. Ternary and Elvis operator

Example:

~~~java
active ? 'enabled' : 'disabled'
~~~

and:

~~~java
nickname ?: 'anonymous'
~~~

The AST helps see the condition node and the branches. When debugging, check which branch is actually evaluated. Do not assume both ternary branches run; typically only the selected branch is evaluated.

With the Elvis operator, check the runtime value of the left-hand side to know whether the fallback is used.

## 6. Distinguishing parse errors from evaluation errors

### 6.1. Parse error

A parse error occurs when the source does not conform to SpEL syntax:

~~~java
total >= && active
~~~

Example:

~~~java
try {
    parser.parseExpression("total >= && active");
} catch (SpelParseException ex) {
    logger.error(
            "Could not parse expression at position {}",
            ex.getPosition(),
            ex
    );
}
~~~

SpelParseException is the dedicated exception for SpEL parse errors. It can provide the position, message code, and error-related data according to the API of the version in use.

When encountering a parse error, check the source and error position first. There is no need to inspect the root object or runtime values if the parser could not create an expression yet.

### 6.2. Evaluation error

An evaluation error occurs after parsing succeeds, when SpEL needs to access data or execute a node:

~~~java
try {
    Object result = expression.getValue(context);
} catch (SpelEvaluationException ex) {
    logger.error(
            "Expression evaluation failed at position {}",
            ex.getPosition(),
            ex
    );
}
~~~

Causes can include:

- Property does not exist or receiver is null.
- Method has no matching overload.
- Constructor cannot be invoked.
- Bean reference cannot be resolved.
- TypeConverter cannot convert an argument.
- Getter, method, or constructor throws an exception.
- Index out of bounds or write operation is unsupported.

When encountering an evaluation error, inspect the context and runtime target along with the reported node/position.

### 6.3. Do not conflate the two error types

Parse errors and evaluation errors need to be recorded separately:

| Phase | Common exception | Investigation direction |
|---|---|---|
| Parse | SpelParseException | Source, syntax, position, and parser configuration |
| Evaluate | SpelEvaluationException | AST, root object, variables, accessor, resolver, converter, and data |
| Code inside method/getter | Original or wrapped exception | Java logic, backend, and cause chain |

Do not catch every exception and report "invalid expression". That message does not distinguish a syntactically invalid source from missing runtime data or a failing internal service.

## 7. Using node positions to isolate errors

### 7.1. Source position

SpelNode provides start and end positions for a node. This information can help locate the source segment corresponding to the node.

When printing the tree, preserve the position of each node:

~~~java
System.out.printf(
        "%s [%d, %d]%n",
        node.toStringAST(),
        node.getStartPosition(),
        node.getEndPosition()
);
~~~

Positions are calculated as provided by the Spring version's parser. When displaying to users, match against the exact parsed source string; do not apply positions from a reformatted expression onto the original source.

### 7.2. Position in exceptions

ExpressionException and related SpEL exceptions can provide the error position. With SpelEvaluationException, record:

- getPosition().
- getMessageCode() if categorization by error code is needed.
- getInserts() when parameters describing the error are needed.
- The cause chain to find the root error.

Specific APIs and details may vary across Spring versions. When writing a shared diagnostic helper, compile and test it against the project's actual dependency version.

### 7.3. Position does not always identify the ultimate cause

A node may invoke a getter, method, or resolver. An exception may be reported at the node performing the operation, while the root cause lies deep in Java code.

For example, an error at customer.address may be due to getter getAddress() calling a repository and the repository failing. The AST helps identify the point SpEL is accessing; the cause chain helps identify the error inside the getter.

Combine the position with the target type and stack trace, rather than concluding from a single offset number.

## 8. A repeatable debugging workflow

### 8.1. Record the source and expression identifier

Before parsing, record the rule identifier, configuration version, and controlled source:

~~~java
logger.debug(
        "Parsing expressionId={}, version={}, source={}",
        expressionId,
        version,
        source
);
~~~

If the source may contain sensitive information, do not log it verbatim in production logs. You can log the expression ID, hash, length, and a redacted version according to policy.

### 8.2. Parse separately and catch parse errors

~~~java
Expression expression;

try {
    expression = parser.parseExpression(source);
} catch (SpelParseException ex) {
    logger.error(
            "SpEL parse failed: position={}, code={}",
            ex.getPosition(),
            ex.getMessageCode(),
            ex
    );
    throw ex;
}
~~~

Separating the parse step tells you whether the error occurred before the context was involved.

### 8.3. Print the AST when needed

If the parser returns a SpelExpression, get the AST and print the structure:

~~~java
if (expression instanceof SpelExpression spelExpression) {
    printTree(spelExpression.getAST(), 0);
}
~~~

Only enable AST logging when needed for diagnostics. A large expression can produce many log lines; avoid logging it continuously in production if unnecessary.

### 8.4. Evaluate with a defined context

When evaluating, record the root object type and required variable types:

~~~java
logger.debug(
        "Evaluating expressionId={}, rootType={}",
        expressionId,
        rootObject == null
                ? "null"
                : rootObject.getClass().getName()
);
~~~

Do not log entire objects or variables if they may contain personal information, tokens, secrets, or customer data.

To reproduce an error, use the exact:

- Source expression.
- Parser version and SpelParserConfiguration.
- Root object type and relevant data state.
- Context variables and their types.
- PropertyAccessor, MethodResolver, BeanResolver, and ConstructorResolver.
- TypeConverter/ConversionService.
- Parser context if using templates.

### 8.5. Catch evaluation errors and preserve the cause

~~~java
try {
    Object result = expression.getValue(context);
    return result;
} catch (SpelEvaluationException ex) {
    logger.error(
            "SpEL evaluation failed: position={}, code={}",
            ex.getPosition(),
            ex.getMessageCode(),
            ex
    );
    throw ex;
}
~~~

Do not turn every error into null or false. Doing so can cause the application to continue with incorrect results and lose investigation information.

## 9. Complete example: printing source and AST

The following example parses an expression, prints the source, prints the AST, and then evaluates:

~~~java
ExpressionParser parser = new SpelExpressionParser();

String source =
        "orders.?[total >= #minimum].![id]";

Expression expression = parser.parseExpression(source);

System.out.println(
        "Expression: " + expression.getExpressionString()
);

if (expression instanceof SpelExpression spelExpression) {
    SpelNode ast = spelExpression.getAST();

    System.out.println(
            "AST: " + ast.toStringAST()
    );

    printTree(ast, 0);
}

StandardEvaluationContext context =
        new StandardEvaluationContext(report);

context.setVariable(
        "minimum",
        new BigDecimal("100")
);

List<?> ids = expression.getValue(context, List.class);
~~~

In the example:

1. The source is stored in the source variable.
2. The parser creates an Expression.
3. getExpressionString() provides the string attached to the Expression.
4. getAST() retrieves the root node of the SpelExpression.
5. toStringAST() displays the AST representation.
6. printTree() traverses the node structure.
7. EvaluationContext provides the root object and the minimum variable.
8. getValue() performs evaluation on runtime data.

If an error occurs at step 7 or 8, the AST can still be completely valid. In that case, inspect the data and resolvers/accessors rather than modifying the source by guesswork.

## 10. AST and the SpEL compiler

### 10.1. AST belongs to the parse phase

The AST is the syntax structure created when the parser processes the source. SpEL can use this structure to evaluate the expression and, in some modes, compile the expression into a more optimized executable form.

The AST helps understand what syntax the parser recognized. It is not compiled bytecode and does not display the full state of the compiler or generated classes.

### 10.2. Differences between interpreted and compiled modes

If the application enables the SpEL compiler, an expression may execute along the compiled path once eligible. When debugging an error that only appears in one mode, reproduce it using the application's exact compiler mode.

You can compare interpreted and compiled modes in a separate test with the corresponding configuration of the Spring version in use. Do not conclude the AST is wrong just because runtime behavior differs between the two modes.

### 10.3. AST nodes are implementation details

You should not write business code like:

~~~java
if (node.getClass().getSimpleName().equals("SomeInternalNode")) {
    // business permission decision
}
~~~

Class names and how nodes are split can change when Spring updates the parser. If you need to control expressions, use a syntax allowlist or explicitly designed validation, without relying on internal AST class names as a security boundary.

AST traversal is suitable for logging, diagnostics, and analysis tools. Allowing or rejecting expressions requires a separate policy tested per version.

## 11. Common pitfalls when reading source and AST

| Symptom | Possible cause | Resolution |
|---|---|---|
| Expression string differs from entered source | Source was normalized or loaded from a different config version | Store original source and version |
| Cannot cast to SpelExpression | Parser returned a different implementation or wrapper | Check instanceof before calling getAST() |
| Whitespace missing in AST | toStringAST() is a syntactic representation, not verbatim source | Use getExpressionString() to view source |
| AST is right but evaluation fails | Error lies in runtime data or resolvers | Inspect EvaluationContext and cause |
| Unknown which node caused the error | Only exception message was logged | Log position, message code, and traverse AST |
| Position does not match displayed source | Using reformatted source or different template context | Match against the exact parsed string |
| AST log is too large | Expression has many nodes or deep nesting | Limit log level and enable only when needed |
| Debug code depends on node names | Using implementation classes as stable API | Rely on SpelNode interface and avoid business logic |
| Error only appears when compiler is enabled | Difference between interpreted and compiled execution | Reproduce with the exact compiler mode |
| Logs expose sensitive data | Logging entire expressions or variables | Redact, log ID/hash and safe metadata |

## 12. Safe logging guidelines

Expression sources can contain bean names, internal properties, user data, or sensitive literals. The AST can also display those literals again.

When logging:

- Prefer expression ID, version, hash, and length.
- Only log source or AST in development environments or after redaction.
- Do not log passwords, tokens, emails, account numbers, or personal data.
- Do not log entire root objects or large collections.
- Record the root object class and variable types instead of sensitive values.
- Limit log length to prevent a large expression from bloating logs.
- Keep exception causes in internal logs, but do not return stack traces to clients.
- Distinguish parse failures from evaluation failures using separate events or error codes.

If you need to store sources for reproduction, use a diagnostic store with appropriate access controls and retention periods.

## 13. Expression diagnostic checklist

When investigating a failing expression, verify:

- The exact source was saved before parsing.
- The correct parser and SpelParserConfiguration are used.
- Whether expression parsing succeeded or failed.
- If parsing succeeded, whether the Expression implementation is SpelExpression.
- The AST is retrieved via getAST() and represented with toStringAST().
- Child nodes and source positions are recorded when needed.
- The right root object, variables, and runtime data types.
- Accessors, resolvers, and TypeConverter match production configuration.
- Exceptions are categorized by parse/evaluate and preserve the cause.
- Source/AST/logs have been redacted if containing sensitive data.
- If compiler mode is enabled, the error has been reproduced in the exact mode.

There is no need to print the entire AST for every request. Enable diagnostics selectively by expression ID or on error to avoid excessive logging and data exposure.

## 14. Summary

Reading the expression string and expression tree helps separate source errors from errors occurring during evaluation:

- **getExpressionString()** provides the expression string attached to the Expression.
- **SpelExpression.getAST()** retrieves the root node when the parser returns a SpelExpression.
- **SpelNode.toStringAST()** provides the syntactic representation of a node.
- **getChildCount()** and **getChild(index)** allow traversing the tree.
- **getStartPosition()** and **getEndPosition()** help isolate the source segment.
- **SpelParseException** helps investigate syntax errors; **SpelEvaluationException** helps investigate runtime errors.
- The AST does not contain runtime data state and should not be used as a stable internal API for authorization.
- Logging must protect the source, literals, and data inside EvaluationContext.

An effective workflow is to save the exact source, parse separately, inspect the AST when needed, evaluate with a reproducible context, and read the cause chain along with the error position. This helps pinpoint whether the error lies in syntax, expression structure, runtime data, or extension points without guessing from the final exception.
