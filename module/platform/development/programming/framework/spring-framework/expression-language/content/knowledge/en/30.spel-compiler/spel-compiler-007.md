# Runtime type changes affecting compiled expressions

## Objectives

SpEL can evaluate expressions using an interpreter or compile expressions into bytecode for faster execution. The compiler collects type information from earlier interpreted evaluations and uses this information to generate code. Therefore, a compiled expression generally works best when the data types it observes remain stable across evaluations.

If the same expression is used with multiple root objects, properties, or values of different runtime types, the type assumptions used during compilation may no longer hold. When that happens, the compiled expression may fail even though the expression can still be evaluated successfully by the interpreter with the new data.

After this lesson, you will be able to:

- Understand why the SpEL compiler relies on type information gathered from interpreted evaluation.
- Identify runtime type changes that can cause a compiled expression to fail.
- Distinguish the behavior of OFF, IMMEDIATE, and MIXED compiler modes.
- Choose a mode suited to data stability and expression side effects.
- Configure the compiler via SpelParserConfiguration.
- Check class loader and compiler limitations.
- Design tests with multiple runtime data types and monitor fallback.

## 1. Interpreter and compiler in SpEL

By default, SpEL evaluates expressions using an interpreter. The interpreter executes nodes in the expression tree when the application calls getValue() or setValue(). This approach is flexible because SpEL can handle multiple object types and resolve property, method, or operator access at runtime.

The SpEL compiler can generate a Java class containing the expression logic as bytecode. Once the expression is compiled, subsequent evaluations can run faster because they do not have to interpret the entire expression tree in the same way.

The compiler does not know all runtime types in advance from the expression string alone. For example, an expression with a property reference may receive objects of different actual types. SpEL uses interpreted evaluations to observe the types of expression elements before generating bytecode based on the collected information.

This creates an important assumption: data types in subsequent evaluations will be compatible with the types observed at compile time. If that assumption does not hold, the compiled expression may no longer be suitable for the new data.

## 2. Why do runtime type changes cause errors?

An expression can be evaluated with multiple root objects or multiple input values. If a property, method result, or data element changes type between calls, the interpreter can re-resolve the operation for the new type, whereas the compiled bytecode may be based on the old type.

Common sources of variation:

- The same expression is used across multiple classes implementing a common interface while returning different property types.
- A property is declared with a broad type such as Object or Number, while actual values change across evaluations.
- A method returns different implementations or subtypes depending on data.
- A variable in EvaluationContext receives values of different types across requests.
- The root object changes across messages or event types.
- Collection data contains heterogeneous elements.
- A value is initially null and later has a concrete runtime type, or vice versa.

For example, an expression reading the payload property:

~~~text
payload
~~~

The first time, payload may contain a String. Next time, the same expression is evaluated with another object and payload contains a different type. The interpreter can return the value according to the current object, while the compiled form may have been created with the type assumption from the first time.

Example with a numeric expression:

~~~text
#root.value + 1
~~~

If value varies among Integer, Long, BigDecimal, or another numeric type, numeric handling and result types can change. A compiled form generated based on a previously observed type may not handle every variant.

Not every type change is guaranteed to fail. Problems appear when the new type is no longer compatible with the assumptions or bytecode generated by the compiler. Test with the application's actual set of runtime types.

## 3. The compiler learns types from interpreted evaluation

Typical flow:

1. The application parses the expression into an Expression.
2. An interpreted evaluation runs and nodes collect runtime type information.
3. When compiler mode allows and the expression qualifies, SpEL attempts to compile the expression.
4. Bytecode is generated based on the expression structure and observed type information.
5. Subsequent evaluations can use the compiled form.
6. If runtime types change and become incompatible, compiled evaluation may fail.

The key point is that the compiler does not exhaustively infer every data type that might appear in the future. It optimizes for the types observed during evaluation.

Therefore, compiled expressions are better suited to data streams with stable schemas and types. For rule engines receiving multiple object kinds, heterogeneous messages, or variables with frequently changing types, interpreted mode may be the safer and more predictable choice.

## 4. Three compiler modes

SpEL defines three modes in the SpelCompilerMode enum:

| Mode | Behavior |
|---|---|
| OFF | Disables the compiler; all expressions are evaluated by the interpreter. This is the default. |
| IMMEDIATE | Compiles as early as possible, usually after the first interpreted evaluation. Errors from compiled evaluation are returned to the caller. |
| MIXED | Switches between interpreted and compiled over time. If compiled evaluation fails, the error is handled internally and the expression returns to interpreted mode. |

### OFF

OFF is appropriate when data types change frequently, the expression is not on a critical performance path, or the application prioritizes flexibility.

Since there is no compiled form, there are no errors from bytecode type assumptions. The interpreter can still raise normal business errors or property access errors; OFF does not make expressions immune to data errors.

### IMMEDIATE

IMMEDIATE instructs SpEL to compile expressions as soon as possible, usually after the first interpreted evaluation.

If the compiled expression fails, for instance because runtime types changed, the exception is returned to the caller. The application can detect the error immediately on that evaluation and decide how to handle it according to its own policy.

Choose IMMEDIATE when:

- Runtime types are stable and controlled.
- Compiled evaluation errors should be surfaced clearly to the caller.
- The expression should not be automatically re-executed in another mode after an error.
- Silent fallback must be avoided for expressions with side effects.

IMMEDIATE does not fix or stabilize data types on its own. It only determines how compiled evaluation errors are propagated outward.

### MIXED

MIXED allows SpEL to switch between interpreted and compiled at runtime. After a number of successful interpreted evaluations, the expression can be compiled. If the compiled form fails, the error is caught internally and the expression falls back to interpreted mode. Later, the compiler may try creating another compiled form.

This cycle may continue until SpEL determines it should stop attempting compilation, such as after reaching a failure threshold. At that point, the expression continues in interpreted mode.

MIXED is useful when you want to leverage compilation while retaining the ability to fall back to the interpreter if runtime types change. However, fallback is not always safe for expressions with side effects.

## 5. Why can MIXED execute an expression multiple times?

Spring documentation warns that MIXED can cause problems for expressions with side effects. If a compiled expression has already performed part of an operation before failing, SpEL may fall back to interpreted mode and re-evaluate the expression.

For example, do not place sending notifications or updating state into an expression that may run under MIXED:

~~~text
#service.sendNotification(#root)
~~~

If the compiled evaluation partially executed a side effect before failing, falling back and re-running could cause the operation to execute a second time.

Therefore:

- Prefer pure expressions that only read data and compute results.
- Do not place data writes, message sending, payments, or API calls with side effects into repeatedly evaluated expressions.
- If side effects cannot be eliminated, do not rely on MIXED for automatic fallback.
- Put actions with side effects in a Java service with proper idempotency, transactions, and error handling.

IMMEDIATE ensures the exception is returned instead of automatically switching back to interpreted mode, but it cannot undo side effects that already occurred before the compiled evaluation failed. The best design remains separating expression evaluation from state-mutating actions.

## 6. Configuring the compiler via SpelParserConfiguration

The compiler is disabled by default. Mode can be configured when creating the parser using SpelParserConfiguration.

Example with IMMEDIATE:

~~~java
SpelParserConfiguration configuration =
    SpelParserConfiguration.builder()
        .compilerMode(SpelCompilerMode.IMMEDIATE)
        .compilerClassLoader(getClass().getClassLoader())
        .build();

SpelExpressionParser parser =
    new SpelExpressionParser(configuration);

Expression expression = parser.parseExpression("payload");
~~~

Example using MIXED:

~~~java
SpelParserConfiguration configuration =
    SpelParserConfiguration.builder()
        .compilerMode(SpelCompilerMode.MIXED)
        .build();

SpelExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

With OFF, the default can be used or configured explicitly:

~~~java
SpelParserConfiguration configuration =
    SpelParserConfiguration.builder()
        .compilerMode(SpelCompilerMode.OFF)
        .build();
~~~

The builder API can vary across Spring versions. Check the Javadoc of the version in use if the project uses a different constructor or builder API.

Besides parser configuration, when SpEL is embedded inside another component and the parser cannot be configured directly, a JVM or SpringProperties property can be set:

~~~text
spring.expression.compiler.mode=off
spring.expression.compiler.mode=immediate
spring.expression.compiler.mode=mixed
~~~

The property name accepts one of the three corresponding values. Identify the application's actual configuration source and avoid setting conflicting modes in multiple places without convention.

## 7. ClassLoader of a compiled expression

Compiled expressions are defined in a child ClassLoader. SpelParserConfiguration allows specifying compilerClassLoader as the parent class loader for this process.

The supplied ClassLoader must be able to see all data types participating in expression evaluation, including:

- The type of the root object.
- Property or method result types.
- Method argument and return types.
- Business classes referenced by the expression.
- Types loaded by module, plugin, or application class loaders.

If the class loader cannot see a type, creating or running the compiled expression can fail even though the interpreter could access that type through another configuration.

When no class loader is specified, Spring uses a default class loader, usually the context class loader of the thread evaluating the expression.

In applications using plugins, application servers, module layers, or multiple class loaders, inspect class visibility more carefully. Do not choose a class loader merely because it can load SpelExpressionParser; it needs to see all types involved in the expression.

## 8. Limitations of the SpEL compiler

Not every expression can be compiled. The compiler focuses on common constructs likely to yield performance gains.

According to Spring documentation, the following expression categories are not supported for compilation:

- Expressions with assignment.
- Expressions relying on ConversionService.
- Expressions using custom resolvers.
- Expressions using overloaded operators.
- Expressions using Optional together with the null-safe operator or Elvis operator.
- Expressions using array creation syntax.
- Expressions using selection or projection.
- Expressions using bean references.

If an expression cannot be compiled, SpEL continues using the interpreter according to the mode and framework version mechanism. Do not assume that enabling compiler mode means every expression is converted into bytecode.

When evaluating performance, confirm that the expression can actually compile. Otherwise, compiler mode optimization will bring no benefit to that expression.

## 9. Designing type-stable expressions

For compiled expressions to operate stably:

- Use a consistent root object type for the expression.
- Keep property types and method return types stable across evaluations.
- Normalize input data before placing it into EvaluationContext.
- Avoid the same property sometimes returning String and other times returning Number or an unrelated object.
- Do not mix multiple implementations with incompatible runtime contracts if the expression requires compilation.
- Split expressions by data type group when input groups differ significantly.
- Use concretely typed DTOs instead of Map or Object when the schema is known.
- Validate nulls and input types before evaluating when business rules require it.

For example, if an expression always needs a monetary amount, normalize amount to BigDecimal before placing it in the root object or variable. Do not pass the same amount variable sometimes as String, sometimes as Double, and sometimes as BigDecimal and expect the compiled expression to handle every case like the interpreter.

If the application needs to handle multiple message kinds, a separate expression can be used for each message kind or messages normalized into a common, clearly typed model before evaluation.

## 10. Distinguishing type-change errors from business errors

A failing compiled expression does not necessarily mean the business data is wrong. The expression may still be valid while the current runtime type differs from the type the compiler used when generating bytecode.

When investigating, check:

1. Which compiler mode was used to parse the expression?
2. Was the expression compiled or is it still interpreted?
3. Do runtime types on the first evaluation and the failing evaluation differ?
4. Which root object, property, or method result changed type?
5. Is the error a ClassCastException, a method/property access error, or a compile/evaluation exception?
6. Is the expression on the list of constructs unsupported for compilation?
7. Can the ClassLoader see the new type?

Do not handle every error by immediately disabling the compiler. First determine whether the expression needs the compiler and whether runtime types can be normalized.

If data is inherently polymorphic and requires flexible handling, OFF or MIXED may be better suited than IMMEDIATE. If a type change indicates a data contract violation, fix it at the model or validation layer.

## 11. Testing when runtime types change

A test using only one data type is insufficient to catch retained type assumptions. Test the same expression with multiple root objects and different property types.

Example model with a broadly declared property:

~~~java
public class PayloadMessage {
    private final Object payload;

    public PayloadMessage(Object payload) {
        this.payload = payload;
    }

    public Object getPayload() {
        return this.payload;
    }
}
~~~

Simple expression reading payload:

~~~java
Expression expression = parser.parseExpression("payload");
~~~

Evaluate sequentially with multiple values:

~~~java
Object first = expression.getValue(
    new PayloadMessage("hello"));

Object second = expression.getValue(
    new PayloadMessage(42));
~~~

In interpreted mode, the expression reads the property from each root object according to the current data. When the compiler is enabled, re-test the same sequence of types and verify behavior when a type differs from the type observed in the initial phase.

For expressions with operators or method calls, select runtime types that can actually occur in production and test both success and failure cases. Do not test only two compatible types; also cover incompatible types and nulls if permitted by the contract.

Cases to include:

- The same runtime type across all evaluations.
- Two different subtypes of the same interface.
- A property declared as Object whose runtime value changes.
- A method result changing type depending on input.
- A null value before and after a concretely typed value.
- A type change after the expression has compiled.
- A class loaded from a different class loader.
- An expression not supported for compilation.
- Compiled evaluation failing in IMMEDIATE.
- Falling back to interpreted mode in MIXED.
- An expression with side effects to verify it is not executed repeatedly by accident.

## 12. Diagnosing and observing compiler behavior

When an expression only fails after multiple evaluations, record enough data to compare calls:

- ID or versioned content of the expression.
- Compiler mode in use.
- Type of the root object.
- Runtime types of important properties and method results.
- Exception type and cause chain.
- Configured ClassLoader.
- Whether the expression supports compilation.

Appropriate logging for the SpEL package can be enabled to observe compilation in test environments. Avoid overly verbose logging in production if it exposes expression data or generates high log volume.

Do not infer that an expression is running compiled solely because compiler mode is not OFF. The expression might not belong to the supported set of constructs, or the compiler might lack enough information to generate bytecode.

To measure performance, benchmark with the same data, same context setup, and same evaluation count. Compare OFF with the target mode; also include context creation, conversion, and external data access costs if they lie on the real path.

## 13. Common errors and troubleshooting

| Symptom | Possible cause | Resolution |
|---|---|---|
| Compiled expression fails after the first run | Runtime type differs from the type used when compiling | Normalize types, split expressions, or choose a suitable mode |
| IMMEDIATE throws an exception | Compiled evaluation failed and the exception was propagated to the caller | Check type changes, class visibility, and the expression |
| MIXED falls back to interpreter | Compiled evaluation failed | Check data types and monitor subsequent compile attempts |
| Expression does not compile | Construct is outside compiler limits or lacks type information | Use the interpreter or rewrite the expression if reasonable |
| ClassCastException error | Bytecode uses a type assumption that no longer holds | Compare runtime types before and after compilation |
| Error occurs only in plugin/runtime container | Compiler class loader cannot see the involved types | Configure an appropriate class loader |
| Side effects happen twice | MIXED fell back after the compiled form already executed part of the operation | Remove side effects from the expression and handle them in Java |
| Performance does not improve | Expression did not compile or other costs dominate | Re-measure and check compiler eligibility |
| Expression works in OFF but not in IMMEDIATE | Runtime types change or bytecode assumptions are unsuitable | Keep OFF/MIXED or normalize input per contract |

## 14. Workflow for selecting compiler mode

1. **Assess type stability.** Check root object, properties, and method results across evaluations.
2. **Check compiler eligibility.** Confirm the expression does not use restricted constructs.
3. **Measure performance first.** Determine whether the expression is genuinely on a critical performance path.
4. **Choose OFF when flexibility is needed.** Use the interpreter when types change frequently or compilation brings no clear benefit.
5. **Choose IMMEDIATE when types are stable.** Use when compiled evaluation errors should be returned directly to the caller.
6. **Choose MIXED when fallback is acceptable.** Use only when the expression has no side effects or re-evaluation is controlled.
7. **Verify the ClassLoader.** Ensure generated classes can see all participating types.
8. **Test type changes.** Run multiple times with realistic types, including new types appearing after compilation.
9. **Monitor production.** Record exceptions, mode, and runtime types without logging sensitive data.

## 15. Best practices

- Only enable the compiler when benchmarks show a significant benefit.
- Keep runtime types stable when using compiled expressions.
- Normalize data and use concretely typed models.
- Use OFF when expressions need flexibility across multiple types.
- Use IMMEDIATE when compiled evaluation errors should be visible to the caller.
- Use MIXED when fallback is safe and expressions have no side effects.
- Do not place writes or service calls with side effects in expressions that MIXED can re-evaluate.
- Configure the compiler via SpelParserConfiguration and choose a ClassLoader that can see involved types.
- Check compiler limitations before optimizing expressions.
- Test the same expression with multiple root objects and runtime types.
- Monitor type changes and exceptions after deployment.
- Separate business logic with side effects into Java services.

## 16. Review checklist

Before enabling the SpEL compiler, verify:

- [ ] Runtime types of the root object and key properties have been identified.
- [ ] Property and method result types are stable across evaluations.
- [ ] Inputs are normalized according to the data contract.
- [ ] The expression belongs to a compiler-supported category.
- [ ] Compiler mode is explicitly chosen.
- [ ] OFF, IMMEDIATE, and MIXED behave appropriately for error requirements.
- [ ] MIXED cannot inadvertently re-run side effects.
- [ ] The ClassLoader can see all involved types.
- [ ] Tests exist for both stable types and types changing after compilation.
- [ ] Tests exist for nulls and multiple implementations if permitted.
- [ ] Performance has been measured with realistic workloads.
- [ ] Sufficient logging/diagnostics exist to recognize type-change errors.

## Conclusion

The SpEL compiler generates bytecode based on type information collected from interpreted evaluation. If the runtime type of the root object, a property, or a method result changes after the expression is compiled, the bytecode may no longer be suitable. OFF always uses the interpreter; IMMEDIATE returns compiled evaluation errors to the caller; MIXED can fall back to the interpreter and attempt to recompile later. Because MIXED can re-evaluate an expression after an error, do not put side effects into expressions handled under this mode. Enable the compiler only when data types are stable, the expression is supported, the class loader is appropriate, and benchmarks confirm the benefit.
