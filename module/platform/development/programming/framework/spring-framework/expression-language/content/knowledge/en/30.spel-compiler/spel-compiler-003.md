# ParserConfiguration and compiler modes in Spring Expression Language

Spring Expression Language (SpEL) can execute an expression in interpreted mode or compile the expression into bytecode to speed up cases that are evaluated repeatedly. In addition, the parser can be configured to automatically expand certain null properties or collections when an expression accesses them.

These options are configured using the \`SpelParserConfiguration\` class and passed into \`SpelExpressionParser\`. In documentation or discussions, this topic is sometimes referred to briefly as parser configuration; the specific Spring API name is \`SpelParserConfiguration\`.

Two configuration groups should be distinguished:

- **Parser configuration:** determines how the parser handles expressions, such as auto-grow and compiler mode.
- **EvaluationContext:** supplies the root object, variables, property accessors, method resolvers, type converter, and evaluation-time services.

Compiler mode does not replace EvaluationContext. It only changes how an expression is executed after the parser creates the Expression object.

## 1. What is SpelParserConfiguration?

\`SpelParserConfiguration\` belongs to the \`org.springframework.expression.spel\` package. This class groups options that affect the parser and how expressions are prepared for evaluation.

A parser can be created with the default configuration:

~~~java
ExpressionParser parser =
    new SpelExpressionParser();
~~~

Or receive an explicit configuration:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration();

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

When compiler mode or auto-grow is needed, create an appropriate \`SpelParserConfiguration\` and pass it into the \`SpelExpressionParser\` constructor.

Parser configuration is chosen when creating the parser. If two groups of expressions require different policies, separate parsers can be created for each group so behavior stays clear and controllable.

## 2. Parser configuration vs EvaluationContext

The two components participate at different stages:

| Component | Responsibility | Example |
|---|---|---|
| SpelParserConfiguration | Configures how the parser prepares and processes expressions | Compiler mode, auto-grow |
| ExpressionParser | Parses a SpEL string into an Expression | parseExpression("price * 2") |
| EvaluationContext | Provides data and services at evaluation time | Root object, variables, resolvers |
| Expression | Represents the parsed expression | getValue(context) |

Example:

~~~java
SpelParserConfiguration parserConfiguration =
    new SpelParserConfiguration();

ExpressionParser parser =
    new SpelExpressionParser(parserConfiguration);

Expression expression =
    parser.parseExpression("price * #quantity");

StandardEvaluationContext context =
    new StandardEvaluationContext(product);

context.setVariable("quantity", 2);

BigDecimal total =
    expression.getValue(context, BigDecimal.class);
~~~

Parser configuration does not hold product or quantity. The root object and variables are supplied via EvaluationContext when getValue is called.

## 3. Main option groups

Common options in SpelParserConfiguration include:

- **Auto-grow null references:** allows SpEL to instantiate certain null references along a property path when deeper access is needed.
- **Auto-grow collections:** allows expanding a collection when an expression accesses an index beyond its current size, within configured limits.
- **Maximum auto-grow size:** limits the maximum size when auto-expanding collections.
- **Compiler mode:** selects whether expressions execute in interpreted mode or via the compiler.
- **Compiler classloader:** specifies the classloader used for bytecode classes generated by the SpEL compiler.

Not every application needs all of them enabled. Choose each option based on actual data structures and expression characteristics.

## 4. Auto-grow null references

When an expression accesses nested properties, an intermediate object may be null.

Example:

~~~spel
customer.address.city
~~~

If customer exists but address is null, reading city normally cannot proceed. When auto-grow null references is enabled, SpEL can instantiate the null intermediate object if that type can be created through a mechanism supported by the framework.

Configuration:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        true,   // autoGrowNullReferences
        false   // autoGrowCollections
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

The two Boolean parameters enable auto-grow null references and auto-grow collections, respectively.

Auto-grow does not mean SpEL can create any object type. The intermediate type must satisfy appropriate instantiation requirements, such as having a constructor or instantiation mechanism SpEL can use. If the object cannot be created, evaluation can still fail.

### Auto-grow does not replace data model validation

Automatic object instantiation can be useful for data binding, but it can also mutate object state simply because an expression accesses a deep property.

For example, an expression expected to be read-only could cause an intermediate object to be created if auto-grow is enabled and the path is accessed in a way that triggers this feature.

Therefore, consider enabling this feature when the goal is binding or updating data. For read-only expressions, disabling auto-grow by default is usually more predictable.

## 5. Auto-grow collections

Auto-grow collections allows SpEL to expand a collection when an expression accesses an index greater than the existing indices, within a configured limit.

For example, with an initially empty list:

~~~java
public class FormData {
    private List<String> labels = new ArrayList<>();

    public List<String> getLabels() {
        return labels;
    }

    public void setLabels(List<String> labels) {
        this.labels = labels;
    }
}
~~~

It can be configured as:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        false,
        true,
        100
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

In the example, auto-grow null references is disabled, auto-grow collections is enabled, and maximum auto-grow size is 100.

If an expression writes to an index beyond the current size, SpEL can expand the list up to the required position. The values created for the new positions depend on the element type and corresponding instantiation/conversion capabilities.

### Maximum auto-grow size

The size limit prevents an expression from requesting a collection expansion to an excessively large number of elements.

For example, if maximum auto-grow size is 100, do not assume an expression can auto-expand a collection to thousands of elements. Requests exceeding the limit can cause evaluation to fail.

This limit is especially important when the index comes from runtime data. Do not allow an uncontrolled index value to trigger large memory allocations.

Auto-grow collections does not make any arbitrary index valid. It only supports expansion according to configured rules and limits.

## 6. Combining auto-grow null references and collections

Both options can be enabled together:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        true,
        true,
        100
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

This configuration is useful in certain data-binding flows with nested objects and collections that need to be created/expanded when users input data.

Example path:

~~~spel
customer.addresses[2].city
~~~

Depending on object state and data types, SpEL may need to:

1. Instantiate a null intermediate address or collection if auto-grow null references is enabled.
2. Expand the collection so that index 2 exists if auto-grow collections is enabled.
3. Instantiate the new element if the element type supports it.
4. Set or read the city property according to the expression.

Not every path can be completed automatically. Non-instantiable types, non-writable properties, collections that do not support modification, or out-of-bounds indices can still cause errors.

## 7. What is compiler mode?

SpEL normally evaluates expressions in interpreted mode. When an expression is evaluated repeatedly, compiling the expression into bytecode can reduce execution overhead.

Compiler mode is controlled by the \`SpelCompilerMode\` enum:

- \`OFF\`: does not use the compiler.
- \`IMMEDIATE\`: requests early expression compilation when possible.
- \`MIXED\`: combines interpreted and compiled execution, with the ability to fall back to interpreted mode when compiled execution is no longer suitable.

The compiler does not change the logical meaning described by an expression. The goal is to improve execution performance for expressions that can be compiled and have suitable runtime characteristics.

Compiler mode is set in SpelParserConfiguration when creating the parser.

## 8. OFF mode

\`SpelCompilerMode.OFF\` disables the SpEL compiler. Expressions are evaluated by the interpreter mechanism.

Example:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.OFF
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);

Expression expression =
    parser.parseExpression("price * #quantity");
~~~

This is the default mode when no compiler is requested.

OFF is suitable when:

- Expressions are only evaluated occasionally.
- Runtime type flexibility matters more than compile optimization.
- Expressions use constructs not supported by the compiler.
- The application wants stable and easy-to-diagnose interpreted behavior.

Disabling the compiler does not mean expressions are not parsed or optimized in other application layers. It only means SpEL does not compile expressions into bytecode via compiler mode.

## 9. IMMEDIATE mode

\`SpelCompilerMode.IMMEDIATE\` instructs SpEL to compile expressions as early as possible once the required information is available.

Example:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.IMMEDIATE,
        MyService.class.getClassLoader()
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

In this mode, if an expression cannot be compiled or compiled execution encounters an issue, the error can be surfaced directly rather than silently relying on an interpreted fallback like MIXED mode.

IMMEDIATE is suitable when:

- Expressions are evaluated repeatedly with stable structure and data types.
- The application knows clearly which expressions need to be compiled.
- The types of the root object and important values are relatively stable.
- Compile errors can be controlled and tested before deploying to the runtime environment.

Do not enable IMMEDIATE broadly for dynamic expressions or ones with heavily changing runtime types. An expression valid in interpreted mode is not guaranteed to belong to the syntax subset the compiler can handle.

## 10. MIXED mode

\`SpelCompilerMode.MIXED\` allows an expression to be evaluated in interpreted mode first, then switch to compiled execution once the compiler has sufficient information and suitable conditions.

If compiled execution encounters problems due to changing runtime characteristics, MIXED mode can fall back to interpreted mode to continue evaluation.

Configuration example:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED,
        MyService.class.getClassLoader()
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

MIXED is often suitable when:

- Expressions are reused many times.
- Runtime types are generally stable but may vary on some evaluations.
- The application wants to take advantage of the compiler while still retaining the ability to fall back to interpreted execution.
- Expressions are supplied by configuration or a rule engine and not every case can be compiled.

Fallback does not mean all logic errors are automatically fixed. If an expression has invalid data, calls a nonexistent method, or performs an invalid operation, interpreted execution can still raise the corresponding error.

## 11. Comparing the three compiler modes

| Mode | Behavior | When suitable |
|---|---|---|
| OFF | Always interpreted, not compiled by the SpEL compiler | Infrequently used expressions or when flexibility is needed |
| IMMEDIATE | Compiles early when possible; compile/runtime errors are not handled by MIXED's fallback mechanism | Stable expressions that can be controlled and tested |
| MIXED | Starts interpreted, may switch to compiled; can fall back to interpreted if compiled execution is unsuitable | Repeatedly used expressions with runtime variation |

No mode is always the fastest in every situation. Performance depends on expression complexity, evaluation count, data types, compilability, and startup cost.

For an expression that runs only once, the cost of preparing compilation may bring no benefit. For an expression evaluated thousands of times on data with stable types, the compiler can make a significant difference.

## 12. Compiler classloader

The SpEL compiler generates bytecode for expressions. The classloader used to define or access compiled classes needs to see the types used by the expression.

The compiler classloader can be specified when creating SpelParserConfiguration:

~~~java
ClassLoader compilerClassLoader =
    MyService.class.getClassLoader();

SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED,
        compilerClassLoader
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

Choosing the right classloader is especially important in applications with:

- Multiple modules or classloaders.
- Dynamically loaded plugins.
- Application servers or containers.
- Domain types residing in a separate classloader.
- Proxy classes or generated classes.

If the compiler classloader cannot see a required type, compiling or loading the compiled expression class may fail.

Choose a classloader that can access the types used by the expression's root object, properties, and methods. Do not assume the thread context classloader is always the right choice for every application.

## 13. The compiler needs runtime type information

Compiled expressions work better when SpEL can determine the types of values in the expression.

Example:

~~~java
public class Product {
    private BigDecimal price;

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Expression:

~~~spel
price * 2
~~~

can be optimized when the types of the root object and the price property are stable.

If the same expression is evaluated with multiple root objects of different types or a property returns unstable types, the compiler may be unable to produce a single execution path suitable for all cases.

This explains why an expression that runs well in interpreted mode cannot necessarily be compiled or run stably when compiled.

When using compiler mode, keep the type contracts of the root object, variables, and properties consistent whenever possible.

## 14. Not every expression can be compiled

The SpEL compiler only supports a certain set of expression constructs. Compilability depends on the Spring version and expression content.

Factors that can affect this:

- Whether the expression structure is supported by the compiler.
- Whether the runtime types of properties and methods can be determined.
- Whether a custom PropertyAccessor or dynamic access mechanism is used.
- Whether operations are used whose types or behaviors cannot be represented in compiled form.
- Whether parameter types and return values are stable across evaluations.

Therefore, do not conclude an expression is definitely compilable just because it parses and evaluates successfully in interpreted mode.

If the compiler does not support an expression, OFF still works in interpreted mode. With MIXED, the framework can continue with interpreted execution when the compiled form cannot be used. With IMMEDIATE, test early to detect expressions incompatible with the chosen mode.

## 15. Parser configuration for auto-grow and compiler mode are independent groups

One parser may need auto-grow for data binding without needing the compiler. Another parser may need the compiler for repeated calculation expressions without needing auto-grow.

Example enabling only auto-grow:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        true,
        true,
        100
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

Example selecting only compiler mode:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);
~~~

Choose the constructor matching the needed option group and the project's Spring version. Do not enable auto-grow just because the compiler is being used; the two features have no mandatory dependency on each other.

## 16. Parse once and reuse the Expression

Compiler mode makes more sense when an expression is reused. Applications should typically parse an expression once and evaluate it many times rather than repeatedly creating parsers and re-parsing the same string.

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);

Expression expression =
    parser.parseExpression("price * #quantity");

for (Product product : products) {
    StandardEvaluationContext context =
        new StandardEvaluationContext(product);

    context.setVariable("quantity", 2);

    BigDecimal total =
        expression.getValue(context, BigDecimal.class);

    // Use total.
}
~~~

The Expression holds the parsed structure. On each evaluation, the context supplies the corresponding root object and variables.

If an expression needs to be evaluated concurrently, consider reusing the Expression and managing a separate EvaluationContext per unit of work. Avoid mutating variables on a shared context across multiple threads without an appropriate synchronization mechanism.

## 17. Measuring performance before choosing a compiler mode

Compiler mode is an optimization option, not a guarantee that every expression will be faster.

When measuring, distinguish:

- **Parsing cost:** cost of creating an Expression from a string.
- **Warm-up cost:** initial interpreted evaluations and compiler preparation.
- **Steady-state cost:** time once the expression reaches a stable running state.
- **Fallback cost:** cost if compiled execution is no longer suitable and must fall back to interpreted mode.

A meaningful benchmark should:

1. Use the same expressions and data representative of production.
2. Measure parse time and evaluate time separately.
3. Run enough iterations to observe warm-up.
4. Compare OFF, IMMEDIATE, and MIXED.
5. Use multiple realistic data types if the application has variation.
6. Verify that computation results are identical across modes.
7. Measure both throughput and latency under near-realistic load conditions.

Do not enable the compiler just because a simple microbenchmark shows one case is faster. Measure with the application's real expressions and data.

## 18. Diagnosing errors related to parser configuration and compiler

Some common error categories:

### Parser does not recognize configuration or constructor

Check the Spring Framework version and the SpelParserConfiguration API present in the actual dependencies. A constructor or option may differ across versions.

### Auto-grow cannot create an object

Check the intermediate property type, constructor, setter, collection implementation, and maximum auto-grow size. Auto-grow cannot instantiate every type or modify a non-writable property.

### Compiler cannot compile the expression

Check the compiler mode, runtime types, expression structure, and compiler classloader. An expression may be valid in interpreted mode yet not belong to the subset supported by the compiler.

### Compiled execution fails when runtime types change

Check whether evaluations use root objects or properties with different types. If the expression needs flexibility, MIXED may be more suitable than IMMEDIATE.

### Classloader cannot see types

Check whether the compiler classloader can access domain classes, proxies, and dependencies used by the expression.

When investigating, distinguish parsing errors, evaluation errors in interpreted mode, and errors during compilation or compiled expression execution.

## 19. Complete example: configuring MIXED and reusing an expression

Suppose an application needs to calculate order values many times:

~~~java
public class Product {
    private final BigDecimal price;

    public Product(BigDecimal price) {
        this.price = price;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Create a parser in MIXED mode:

~~~java
SpelParserConfiguration configuration =
    new SpelParserConfiguration(
        SpelCompilerMode.MIXED,
        Product.class.getClassLoader()
    );

ExpressionParser parser =
    new SpelExpressionParser(configuration);

Expression expression =
    parser.parseExpression("price * #quantity");
~~~

Evaluate with each product:

~~~java
Product first =
    new Product(new BigDecimal("250000"));

Product second =
    new Product(new BigDecimal("400000"));

StandardEvaluationContext firstContext =
    new StandardEvaluationContext(first);

firstContext.setVariable("quantity", 2);

StandardEvaluationContext secondContext =
    new StandardEvaluationContext(second);

secondContext.setVariable("quantity", 3);

BigDecimal firstTotal =
    expression.getValue(firstContext, BigDecimal.class);

BigDecimal secondTotal =
    expression.getValue(secondContext, BigDecimal.class);
~~~

Result:

~~~text
firstTotal = 500000
secondTotal = 1200000
~~~

The example illustrates using the same parsed Expression with multiple EvaluationContexts. Compiler mode can optimize evaluation when the expression and runtime types are suitable; the business result must still remain identical between interpreted and compiled execution.

## 20. Common misconceptions

**Misconception 1: ParserConfiguration is EvaluationContext.**  
SpelParserConfiguration sets up parser and compiler behavior. EvaluationContext supplies the root object, variables, and evaluation-time services.

**Misconception 2: IMMEDIATE and MIXED are the same.**  
IMMEDIATE requests early compiled execution and has no fallback mechanism like MIXED. MIXED can fall back to interpreted mode if compiled execution is no longer suitable.

**Misconception 3: Enabling the compiler makes every expression faster.**  
Only suitable expressions evaluated frequently enough can benefit. Parsing, warm-up, and compilation also have costs.

**Misconception 4: A parseable expression is definitely compilable.**  
The compiler only supports a certain set of constructs and needs appropriate runtime type information.

**Misconception 5: Auto-grow is just a performance optimization.**  
Auto-grow can instantiate objects or change collection sizes. It is data-affecting behavior, not a compiler optimization.

**Misconception 6: The compiler classloader does not matter.**  
The compiler needs to access types used in the expression. An unsuitable classloader can cause compilation or loading compiled classes to fail.

**Misconception 7: Auto-grow and compiler must be enabled together.**  
These are two independent option groups. Only enable the features the application needs.

## 21. Takeaways

- SpEL's parser configuration API is \`SpelParserConfiguration\`, passed into \`SpelExpressionParser\`.
- Parser configuration differs from EvaluationContext: one configures the parser, the other provides data and services at evaluation time.
- Auto-grow null references can instantiate null intermediate objects if the type supports it.
- Auto-grow collections can expand a collection when an index requires it, within the maximum auto-grow size limit.
- Auto-grow can mutate objects and collections; enable intentionally, especially for read-only expressions.
- SpelCompilerMode has three modes: OFF, IMMEDIATE, and MIXED.
- OFF uses interpreted execution; IMMEDIATE requests early compilation; MIXED can switch between compiled and interpreted execution.
- The compiler needs appropriate runtime type information and only supports a certain set of expressions.
- The compiler classloader must be able to see the types used by the expression.
- Parse once, reuse the Expression, and manage EvaluationContext per unit of work.
- Measure warm-up and steady-state on realistic workloads before choosing a compiler mode.

When configuring SpEL, separate data-binding requirements from execution optimization requirements. Choose auto-grow according to the data model and an appropriate size limit; choose compiler mode according to type stability and evaluation count; then test expressions on the application's actual Spring version and classloader.
