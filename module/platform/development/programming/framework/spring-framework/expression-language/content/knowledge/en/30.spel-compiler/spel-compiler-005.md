# Compiler-unsupported expressions and fallback mechanisms

Spring Expression Language (SpEL) has two ways to execute expressions: **interpreted mode** and **compiled mode**. Interpreted mode is flexible because on each evaluation SpEL processes the expression structure using the interpreter. Compiled mode generates Java bytecode for the expression to reduce processing overhead when the expression is evaluated frequently.

Not every expression can be compiled. Some syntax and extension capabilities depend on the runtime context, so the compiler cannot generate corresponding bytecode. In those cases, the expression can still run using the interpreter. Therefore, **being uncompilable does not mean the expression is invalid or cannot be evaluated**.

In addition, when an expression has been compiled but fails at runtime, how it is handled depends on **SpelCompilerMode**:

- **OFF:** always interpret.
- **IMMEDIATE:** use the compiled expression when possible; errors from compiled evaluation are returned to the caller.
- **MIXED:** switch back and forth between interpreted and compiled; if compiled evaluation fails, SpEL catches the error internally and falls back to the interpreter.

Understanding these limitations and modes helps choose the right execution strategy, avoiding the expectation that enabling the compiler will automatically make every expression run faster or always fall back safely.

## 1. Interpreted mode and compiled mode

### 1.1. Interpreted mode

In interpreted mode, SpEL parses the expression into an internal structure and the interpreter evaluates that structure when getValue() or setValue() is called.

Example:

~~~java
ExpressionParser parser = new SpelExpressionParser();

Expression expression =
        parser.parseExpression("customer.address.city");

String city = expression.getValue(order, String.class);
~~~

The interpreter reads the customer property, then reads address, and then retrieves city. Property access and data types are handled during evaluation.

Interpreted mode is suitable when:

- The expression is only evaluated occasionally.
- Input data types may change between calls.
- The expression uses features not yet supported by the compiler.
- The application needs the flexibility of custom resolvers or a conversion service.
- Correctness and compatibility matter more than small evaluation overhead.

### 1.2. Compiled mode

The SpEL compiler can generate a Java class representing the expression's behavior at runtime. Once a compiled form exists, subsequent evaluations can run faster because they do not need to perform the full interpretation process.

Example expression with a chain of property accesses and arithmetic:

~~~text
#order.items[0].price * #quantity
~~~

If the expression and involved data types are suitable for the compiler, SpEL can generate bytecode to perform those operations.

The compiler needs to know the types of elements in the expression. Some types can only be inferred after interpreted evaluations. Therefore, a compiled expression typically relies on type information observed while running the interpreter.

This is also an important limitation: if data types change between evaluations, the compiled form may no longer be suitable.

### 1.3. The compiler is not a different parser

Both modes use the same SpEL syntax and expression model. The compiler only changes how an expression is executed after parsing.

An expression may:

- Parse successfully and run via the interpreter.
- Parse successfully, but fail to compile.
- Parse and compile, yet fail compiled evaluation on a different dataset.
- Run stably in both modes.

Therefore, separate three phases: parsing the expression, determining compilability, and evaluating the expression with real data.

## 2. Expression types not supported by the compiler

Current Spring documentation lists the following expression categories as non-compilable. The list can change across Spring Framework versions, so verify against the documentation of the exact version the application uses.

| Expression category | Example or indicator | Why the interpreter is needed |
| --- | --- | --- |
| Assignment | name = 'Linh' | Involves writing a value to a property or variable |
| Relies on ConversionService | Converting a String to a domain type via a converter | Depends on the context's runtime conversion mechanism |
| Custom resolver | Uses an application-supplied resolver | Behavior does not have bytecode generated by the default compiler |
| Overloaded operators | Operators handled via an operator overloader | Execution depends on a custom resolver |
| Optional with null-safe or Elvis | #value?.name or #value ?: 'default' when value is Optional | Some of these Optional operations are not yet supported by the compiler |
| Array construction | new int[] {1, 2, 3} | Creates an array using special constructor syntax |
| Selection or projection | #orders.?[total > 100], #orders.![id] | Iterates and transforms collections using specialized operators |
| Bean reference | @priceService.calculate(#order) | Needs a BeanResolver to look up beans in the context |

Note a few easily confused points:

- **Array construction** does not mean all array operations are uncompilable. Element access like #scores[0] is a different operation from creating an array with new int[] {...}.
- **Selection and projection** are two different operators, but both belong to the group not supported by the compiler.
- **Bean reference** can work normally in interpreted mode if the EvaluationContext has a BeanResolver. The limitation here is that the compiler cannot compile that expression.
- **ConversionService** is the context's type conversion mechanism. An expression requiring a conversion service can still run properly when interpreted.
- **Custom resolver** is an extension capability of EvaluationContext; do not expect the compiler to understand custom application-defined behavior.

If an expression contains one of these features, let the interpreter handle it or split the compilable portion into a simpler expression if that fits the design.

## 3. Why can changing data types make a compiled expression fail?

SpEL cannot know all runtime types just by reading the expression string. Example:

~~~text
#payload.amount
~~~

On the first evaluation, payload may be an Invoice. The compiler records that amount has type BigDecimal and generates bytecode based on that information.

If a later evaluation passes payload as a different object, such as a Quote whose amount is a String, the compiled expression may no longer be able to perform the generated operation.

Similar situations occur when:

- A property returns different types depending on state or implementation.
- A collection changes element types across evaluations.
- The passed root object does not have the same structure or type as in previous calls.
- Custom conversion or a resolver changes behavior per request.
- A class is loaded through a different classloader than the one used during compilation.

Compiled mode is best suited for expressions with stable structure and data types across many evaluations. If one expression is used with multiple root object types, consider keeping interpreted mode or creating separate expressions/parsers per data type.

## 4. Configuring compiler mode

The compiler is not enabled by default. The mode is controlled by the **SpelCompilerMode** enum in the org.springframework.expression.spel package.

There are three modes:

| Mode | Behavior |
| --- | --- |
| OFF | Disables the compiler; every expression is evaluated by the interpreter. This is the default. |
| IMMEDIATE | The compiler attempts to compile expressions early, usually after the first interpreted evaluation. If compiled evaluation fails, the exception is returned to the caller. |
| MIXED | After a number of successful interpreted evaluations, the expression can be compiled. If compiled evaluation fails, SpEL catches the error internally and falls back to the interpreter. |

### 4.1. Configuring with SpelParserConfiguration

The compiler mode and classloader can be passed into SpelParserConfiguration when creating the parser:

~~~java
SpelParserConfiguration configuration =
        SpelParserConfiguration.builder()
                .compilerMode(SpelCompilerMode.MIXED)
                .compilerClassLoader(getClass().getClassLoader())
                .build();

ExpressionParser parser =
        new SpelExpressionParser(configuration);

Expression expression =
        parser.parseExpression("payload.amount * 1.08");
~~~

Here the parser uses MIXED mode. The supplied classloader serves as the parent for the classloader that defines the compiled expression.

If a specific classloader does not need to be specified, compilerClassLoader can be omitted to use the default classloader chosen by Spring.

For older Spring versions that do not yet have the builder API, use the SpelParserConfiguration constructor provided in that version. Always check the Javadoc of the actual dependency rather than copying APIs from a different version.

### 4.2. Configuring via system property

When SpEL is used inside a module or integration point where the application does not create the parser directly, the compiler mode can be configured via a property:

~~~text
spring.expression.compiler.mode
~~~

The property accepts one of these values:

~~~text
off
immediate
mixed
~~~

It can be set via a JVM system property or the SpringProperties mechanism. This is a broader configuration approach, so consider the impact on other expressions in the same application.

If the application manages the parser itself, configuring directly with SpelParserConfiguration usually helps scope the mode to that parser.

## 5. Fallback mechanisms in each mode

Two situations must be distinguished:

1. The expression is not within the feature set supported by the compiler, so a compiled form cannot be created.
2. The expression was compiled, but one run of the compiled form fails, for example due to changing runtime types.

Fallback mainly refers to the second situation. An expression that does not support compilation can still run via the interpreter; that is not a runtime error requiring MIXED mode recovery.

### 5.1. OFF: always use the interpreter

With OFF, the compiler is disabled:

~~~java
SpelParserConfiguration configuration =
        SpelParserConfiguration.builder()
                .compilerMode(SpelCompilerMode.OFF)
                .build();
~~~

Every evaluation uses the interpreter. Since there is no compiled form, there is also no fallback from compiled to interpreted.

Choose OFF when expressions use selection, projection, bean references, assignment, or other unsupported compilation features; when data types change frequently; or when predictable execution behavior is desired.

### 5.2. IMMEDIATE: compiled evaluation errors are returned

In IMMEDIATE mode, SpEL tries to compile the expression early, usually after the first interpreted run to gather type information.

If the compiled expression fails to run, the caller receives the exception. SpEL does not silently re-run the expression using the interpreter like MIXED mode does.

Example:

~~~java
SpelParserConfiguration configuration =
        SpelParserConfiguration.builder()
                .compilerMode(SpelCompilerMode.IMMEDIATE)
                .build();

SpelExpressionParser parser =
        new SpelExpressionParser(configuration);
~~~

IMMEDIATE is suitable when data types are stable and the application wants a clear error if the compiled form is no longer suitable.

Do not choose IMMEDIATE just for high speed. First verify that the expression falls within compiler support and that data has stable types.

### 5.3. MIXED: automatically fall back to the interpreter

MIXED mode allows an expression to switch between interpreted and compiled during usage:

1. The expression is evaluated by the interpreter during initial runs.
2. After a number of successful runs, the compiler may create a compiled form.
3. Subsequent calls can use the compiled form.
4. If compiled evaluation fails, the error is caught internally and the expression falls back to the interpreter.
5. Later, the compiler may attempt to create a new compiled form.
6. If compilation continues failing enough times, SpEL may stop trying and keep the expression in interpreted mode.

This mechanism lets the application keep running when inferred type information is no longer suitable. However, fallback does not mean all business errors are ignored. Errors from invalid data, unhandled nulls, or methods throwing exceptions must still be handled according to the expression's semantics.

### 5.4. MIXED may re-run part of an expression

MIXED mode carries an important risk for expressions with side effects.

If a compiled expression executes part of an action and then fails, SpEL may fall back to the interpreter and re-evaluate the expression. The portion that already ran before the error may be executed a second time.

Example that should not be used in MIXED:

~~~text
@paymentService.charge(#account, #amount)
~~~

If the charge operation already created a transaction before another node failed, the interpreted retry could create an additional transaction.

Therefore:

- Prefer pure expressions that only read data or compute values.
- Do not place payments, sending emails, writing data, or state changes inside expressions that could be automatically re-run.
- If an expression has side effects and needs compiled mode, consider IMMEDIATE so errors are returned to the caller, while also designing operations to be idempotent with clear error handling.
- If the compiler is not needed, OFF is the most predictable choice.

## 6. ClassLoader and compiled expressions

A compiled expression is generated as a Java class in a child ClassLoader. If the application specifies a classloader for the compiler, that classloader must be able to see all types involved in expression evaluation.

Example:

~~~java
ClassLoader expressionClassLoader =
        MyApplication.class.getClassLoader();

SpelParserConfiguration configuration =
        SpelParserConfiguration.builder()
                .compilerMode(SpelCompilerMode.MIXED)
                .compilerClassLoader(expressionClassLoader)
                .build();
~~~

Class visibility errors can appear in applications with plugins, module loaders, application servers, or separate classloaders per component.

When encountering errors that only appear in compiled mode, check:

- The root object and property types accessed by the expression.
- Argument and return types of invoked methods.
- Whether the classloader can see the relevant classes.
- Whether classes are loaded from multiple different classloaders.
- Whether runtime types remain stable across evaluations.

If there is no special reason to specify a classloader, Spring can be left to use the default classloader. For modular applications, configure a classloader that can access all types related to the expression.

## 7. Checking whether an expression is compilable

When needing to check compilability in tests or diagnostic tools, SpEL provides an API on **SpelExpression**.

The expression can be evaluated first to gather type information, then compilation requested:

~~~java
SpelExpressionParser parser =
        new SpelExpressionParser();

SpelExpression expression = (SpelExpression)
        parser.parseExpression("payload.amount * 1.08");

Object firstResult = expression.getValue(message);

boolean compiled = expression.compileExpression();
~~~

compileExpression() returns true if the expression compiled successfully and false if it could not yet be compiled. Compilation only succeeds when the nodes have sufficient required type information.

This API is useful in testing or diagnostics. For normal applications, configuring SpelCompilerMode on the parser is usually the more appropriate way to manage the compiler.

If an expression already uses a compiled form and needs to return to the interpreter explicitly, SpelExpression has the revertToInterpreted() method:

~~~java
expression.revertToInterpreted();
~~~

This operation removes the current compiled form and puts the expression into interpreted mode. Depending on the compiler mode, SpEL may try compiling again later.

Do not use compileExpression() as a mandatory step before every getValue() call. The compiler needs sufficient runtime information, and some expressions are inherently uncompilable.

## 8. Splitting expressions to avoid compiler limitations

If a large expression contains both a compilable part and an uncompilable part, consider splitting the logic into smaller steps.

Original example:

~~~text
#orders.?[total >= #minimumTotal].![total * #taxRate]
~~~

This expression uses selection and projection, so the compiler does not support it.

If the architecture allows, collection filtering can be done in Java and a simple expression used to calculate the value per Order:

~~~text
total * #taxRate
~~~

Another option is to move the entire filtering and mapping to a Java Stream:

~~~java
List<BigDecimal> totals = orders.stream()
        .filter(order -> order.getTotal().compareTo(minimumTotal) >= 0)
        .map(order -> order.getTotal().multiply(taxRate))
        .toList();
~~~

Do not split an expression just to force the compiler to work if the result makes logic harder to read or adds data conversion overhead. Keep SpEL for short configurable expression parts and use Java for complex collection logic or when strict type control is needed.

## 9. Diagnosing when an expression does not compile or falls back

When performance is below expectations or compiled evaluation throws errors, identify the specific case.

### 9.1. Expression runs but is not compiled

Symptoms:

- The expression evaluates successfully.
- There are no syntax or runtime errors.
- The compiler cannot create a compiled form or the expression belongs to an unsupported category.

Resolution:

1. Check the expression against the limitation list for the Spring version in use.
2. Check whether there is assignment, selection, projection, bean reference, custom resolver, or conversion service.
3. Accept interpreted mode if the expression only runs occasionally.
4. If performance is needed, move unsupported processing to Java or rewrite as a simpler expression when appropriate.

This is not a parse error and is not a reason to alter input data.

### 9.2. Compiled expression fails in IMMEDIATE

Symptoms:

- The expression already ran in interpreted mode.
- After compiling, an evaluation with different data throws an exception.
- The error may relate to property types, method arguments, class visibility, or runtime structure.

Resolution:

1. Check the types of the root object and properties on the first successful run.
2. Compare against the types on the failing run.
3. Check the classloader and involved method types.
4. If types genuinely change, use OFF or MIXED depending on side-effect and error requirements.
5. If types should be stable, normalize data before evaluating.

IMMEDIATE does not automatically switch to the interpreter when compiled evaluation fails.

### 9.3. MIXED falls back to the interpreter

Symptoms:

- The expression still runs even though compiled evaluation failed at some point.
- Performance may vary between evaluations.
- The expression may be recompiled later or eventually remain in interpreted mode.

Resolution:

1. Determine why runtime types are changing.
2. Check whether the expression has side effects.
3. If there are side effects, assess the risk of part of the expression being re-executed.
4. If type changes are normal, consider OFF to avoid repeated failed compilation attempts.
5. If types ought to be stable, fix the data source or split expressions by type.

Do not view MIXED as a general exception-ignoring mechanism. It handles compiled-form failures by falling back to the interpreter; business errors during interpretation can still be returned.

## 10. Choosing a mode by expression characteristics

| Scenario | Mode to consider | Reason |
| --- | --- | --- |
| Expression uses selection/projection or bean reference | OFF | These forms do not support compilation in current documentation |
| Expression needs a custom resolver or ConversionService | OFF | The compiler cannot compile such extended behavior |
| Expression has stable types, no side effects, and needs performance | IMMEDIATE or MIXED | Can benefit from compiled form |
| Data types may change between evaluations | OFF or MIXED | OFF avoids compiled form; MIXED has an interpreter fallback mechanism |
| Compiled failures must be visible to the caller | IMMEDIATE | Compiled evaluation errors are returned directly |
| Expression has side effects and cannot be re-run | OFF or IMMEDIATE | Avoids MIXED's silent automatic retry |
| Expression only runs a few times | OFF | Compilation cost may bring no significant benefit |

These are selection guidelines, not rigid rules. Measure performance on real workloads and verify the actual data types the application uses.

## 11. Testing interpreted, compiled, and fallback behavior

Separate tests should exist for the following scenarios:

- Expression runs in OFF.
- Stable expression can compile.
- Expression belongs to an uncompilable group yet still runs via the interpreter.
- Runtime types change after compilation.
- MIXED switches back to the interpreter when the compiled form fails.
- IMMEDIATE returns an error when compiled evaluation fails.
- Expressions with side effects are not unintentionally re-executed.

Example checking a selection expression:

~~~java
SpelExpressionParser parser =
        new SpelExpressionParser();

SpelExpression expression = (SpelExpression)
        parser.parseExpression("#orders.?[total > 100]");

StandardEvaluationContext context =
        new StandardEvaluationContext();

context.setVariable("orders", orders);

Object result = expression.getValue(context);

// Selection is supported in interpreted mode.
// In current Spring Framework, selection is not supported by the compiler.
boolean compiled = expression.compileExpression();
~~~

In tests tied to a specific Spring version, you can assert that compileExpression() returns false for selection expressions. When upgrading Spring versions, recheck limitations because the compiler may add support for new syntax.

For compilable expressions, run tests with objects of stable types as well as type-changing cases. Do not test just one evaluation and conclude the compiled form is safe for the entire application lifecycle.

## 12. Performance notes

The compiler can improve the speed of expressions evaluated repeatedly many times, though it is not always faster overall.

Consider:

1. **Evaluation frequency:** an expression that runs only once may not be worth compiling.
2. **Compilation cost:** the compiler needs to generate classes and gather type information.
3. **Type stability:** the compiled form relies on observed types.
4. **Syntax limitations:** unsupported expressions still run via the interpreter.
5. **Cost inside methods:** if an expression calls a service or queries a database, that time can dwarf interpreter overhead.
6. **Classloader and memory:** compiled expressions create classes in a child ClassLoader.
7. **Side effects:** MIXED can fall back to the interpreter after a compiled expression has partially run.

Run benchmarks with the same data, evaluation counts, and EvaluationContext similar to production. Do not enable the compiler globally based solely on a single microbenchmark.

## 13. Quick takeaways

- SpEL has interpreted mode and compiled mode.
- The compiler is not enabled by default; the default mode is OFF.
- Expressions not supported for compilation can still run normally via the interpreter.
- Current limitations include assignment, ConversionService, custom resolvers, overloaded operators, certain Optional operations, array construction, selection/projection, and bean references.
- The compiler infers types from interpreted evaluations; changing types can cause the compiled form to fail.
- OFF always uses the interpreter.
- IMMEDIATE returns exceptions to the caller if compiled evaluation fails.
- MIXED catches compiled evaluation errors and falls back to the interpreter; it may attempt to recompile later.
- MIXED risks re-executing side effects if a compiled expression partially ran before failing.
- Configure the parser using SpelParserConfiguration or the spring.expression.compiler.mode property when the parser is managed by another integration point.
- The classloader used for the compiler must see all types involved in the expression.
- Use compileExpression() to check compilability during diagnostics; use revertToInterpreted() to discard the compiled form.
- Measure actual performance before choosing a mode for production.
