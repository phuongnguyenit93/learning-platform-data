# Size Limits and User-Supplied Data

SpEL can create lists, maps, and arrays, access objects, and invoke methods during expression evaluation. These capabilities are useful when expressions are controlled by the application, but must be carefully restricted if the expression string or input data comes from users.

A short expression can still request allocating a very large array, iterating over a large collection, or calling an expensive method. Conversely, a long expression is not necessarily dangerous, yet it increases parsing, storage, logging, and inspection costs. Therefore, you need to control expression size, data size, EvaluationContext permissions, and execution cost separately.

**Size limits are part of input design; they do not replace restricting what an expression is allowed to do.**

## 1. Identify data sources and trust levels

Before evaluating an expression, distinguish which data is generated by the application and which data is controlled by users:

| Component | Example | How to manage |
|---|---|---|
| Expression string | Condition entered by user | Limit length, validate syntax, and restrict expression permissions |
| Input values | Name, code, quantity, list | Validate type, length, element count, and value domain |
| Root object | Order, Customer, Report | Provide only necessary objects; avoid exposing the entire domain |
| Context variables | #limit, #selectedIds | Assign validated and properly typed values |
| Objects allowing method calls | Service or policy | Provide only necessary methods; limit side effects |
| Expression result | List, Map, Array, Boolean | Validate type, size, and content before using |

An expression string written beforehand by the development team can be trusted under the application's review process. Expressions entered by users, stored in a database, or received from an API must be treated as untrusted input until they pass validation policies.

Do not equate "parsed successfully" with "safe". The parser only confirms that the syntax can be turned into an Expression; it does not confirm that the expression has appropriate access permissions or reasonable execution cost.

## 2. Limiting expression length before parsing

### 2.1. Validate at the input boundary

Expression length should be limited as soon as data is received, before calling the parser. Example:

~~~java
private static final int MAX_EXPRESSION_LENGTH = 10_000;

static Expression parseUserExpression(
        String source,
        ExpressionParser parser) {

    if (source == null) {
        throw new IllegalArgumentException(
                "Expression must not be null"
        );
    }

    if (source.length() > MAX_EXPRESSION_LENGTH) {
        throw new IllegalArgumentException(
                "Expression is too long"
        );
    }

    if (source.isBlank()) {
        throw new IllegalArgumentException(
                "Expression must not be blank"
        );
    }

    return parser.parseExpression(source);
}
~~~

The 10,000-character limit in the example is only an illustrative policy. Applications need to pick a number based on functionality, expression complexity, resources, and user experience. Do not copy a threshold without measuring against real data.

In Java, **String.length()** counts UTF-16 code units, not the number of UTF-8 bytes or visible characters. If a limit is enforced at an HTTP/API gateway in bytes, also check payload size in bytes at the transport boundary. If the limit is by user-visible characters, align Unicode counting rules with the UI.

### 2.2. Do not rely solely on parser limits

Some versions of Spring Framework provide configuration for expression length limits in SpelParserConfiguration. If the version in use supports it, configure an appropriate limit and verify the actual behavior of that version.

Even if the parser has its own limit, the application should still validate input at the API or service layer. Reasons:

- Oversized payloads can be rejected before creating processing objects.
- Error messages can be returned consistently with the API contract.
- Different limits can be applied per expression type.
- Accompanying input data can be limited as well, not just the SpEL string.
- Metrics can be recorded and abnormal expression sources detected.

Do not increase parser limits just so an oversized expression can run. Review whether the expression contains data or logic that should be moved to Java instead.

## 3. Limiting the size of lists, maps, and arrays

### 3.1. Short expressions can still create large data

Example:

~~~java
new int[100000000]
~~~

This string is very short yet requests allocating an array of one hundred million elements. Depending on the environment, it can cause heavy memory consumption or crash the application due to insufficient heap.

Another expression might create a collection with many literal elements or nest many collections. Therefore, limiting string length alone is not enough to bound memory and evaluation cost.

### 3.2. Validate sizes before evaluation

If an array size or element count comes from user data, validate it in Java before putting it into the context:

~~~java
private static final int MAX_ARRAY_SIZE = 256;

static int validateArraySize(Integer requestedSize) {
    if (requestedSize == null) {
        throw new IllegalArgumentException(
                "Array size is required"
        );
    }

    if (requestedSize < 0 || requestedSize > MAX_ARRAY_SIZE) {
        throw new IllegalArgumentException(
                "Array size is outside the allowed range"
        );
    }

    return requestedSize;
}
~~~

Only after validation, put the value into the context:

~~~java
int size = validateArraySize(requestedSize);

StandardEvaluationContext context =
        new StandardEvaluationContext();

context.setVariable("size", size);
~~~

If an expression is permitted to allocate arrays using a variable, the size must be bounded before calling **getValue**. Do not only check the size after the array has been created because the allocation cost has already occurred by then.

For inline lists or maps whose elements are written directly in the expression, restrict complexity and the allowed element count. For collection data passed from outside, check the element count before putting it into the context.

### 3.3. Limiting multiple dimensions and nested structures

A multidimensional array can consume far more memory than each dimension's size appears individually:

~~~java
new int[100][100][100]
~~~

The total number of elements is the product of the dimensions. If multiple dimensions are permitted, check:

- Maximum number of dimensions.
- Maximum size of each dimension.
- Total number of elements after multiplying dimensions.
- Expected memory limit.
- Element type and actual object size.

When computing the total number of elements, use a sufficiently wide numeric type and check for overflow before allocation. Do not multiply int values and assume the result is always accurate.

For nested lists/maps, limit both depth and total node count, not just the number of elements at the outermost level. A collection with few top-level elements can still hold a huge data tree at child levels.

### 3.4. SpEL's auto-grow

SpelParserConfiguration has options that control automatically expanding null references and collections when accessing out-of-bounds indices. Example of configuring auto-grow limits:

~~~java
SpelParserConfiguration configuration =
        new SpelParserConfiguration(
                false,
                false,
                256
        );

ExpressionParser parser =
        new SpelExpressionParser(configuration);
~~~

The three parameters in the example constructor respectively disable auto-growing null references, disable auto-growing collections, and set the maximum auto-grow size limit.

Auto-grow can be useful when the application intentionally wants SpEL to expand data structures during certain write operations. However, for untrusted expressions or read-only data access, disable this feature so that out-of-bounds access does not accidentally grow collections.

**maximumAutoGrowSize** only limits the corresponding auto-grow behavior. It must not be treated as a general limit for all array construction, inline lists, inline maps, or pre-existing collections passed into the context. Those data sources must be checked separately.

## 4. Limiting input data size

### 4.1. Limiting strings

Large strings can increase storage, comparison, normalization, parsing, and logging costs. Set per-field limits:

~~~java
private static final int MAX_NAME_LENGTH = 200;
private static final int MAX_TEXT_LENGTH = 4_000;

static String validateText(String value, int maxLength) {
    if (value == null) {
        return null;
    }

    if (value.length() > maxLength) {
        throw new IllegalArgumentException(
                "Text exceeds the allowed length"
        );
    }

    return value;
}
~~~

Do not use the same limit for every field. Display names, identifiers, notes, and search contents have different needs.

If a byte limit is needed to match storage or protocols, measure the size after encoding with the charset in use, typically UTF-8.

### 4.2. Limiting collection element counts

Example of checking a list before putting it into the context:

~~~java
private static final int MAX_ITEMS = 500;

static <T> List<T> validateItems(List<T> items) {
    if (items == null) {
        return List.of();
    }

    if (items.size() > MAX_ITEMS) {
        throw new IllegalArgumentException(
                "Too many items"
        );
    }

    return List.copyOf(items);
}
~~~

This example returns an immutable list and rejects null elements because **List.copyOf** does not allow null. If null is valid data in the domain, use another copy approach and define a clear null policy.

For Maps, limit entry count, key length, value size, and allowed data types. Do not only check how many entries the map has if each value is itself a nested list or map.

### 4.3. Checking data types

Do not put arbitrary objects from a request into the context. Convert data into simple types or DTOs containing only the necessary fields:

~~~java
public record ExpressionInput(
        String customerCode,
        int quantity,
        List<String> tags
) {
}
~~~

After validating, create a context containing only the needed values:

~~~java
StandardEvaluationContext context =
        new StandardEvaluationContext();

context.setVariable("customerCode", input.customerCode());
context.setVariable("quantity", input.quantity());
context.setVariable("tags", List.copyOf(input.tags()));
~~~

This limits what the expression can observe and reduces the risk of accidentally granting access to internal services, entities, or objects.

## 5. Do not concatenate user data directly into SpEL strings

### 5.1. Risk of altering expression structure

Do not build expressions by directly concatenating user data:

~~~java
String source =
        "customer.name == '" + userInput + "'";

Expression expression =
        parser.parseExpression(source);
~~~

If userInput contains quotes or SpEL syntax, the expression structure can change unexpectedly. This is a bug caused by mixing data with expression code.

### 5.2. Using variables in EvaluationContext

Keep the expression fixed and pass data via variables:

~~~java
String source = "#customerName == #expectedName";

StandardEvaluationContext context =
        new StandardEvaluationContext();

context.setVariable("customerName", customerName);
context.setVariable("expectedName", userInput);

Boolean matches = parser
        .parseExpression(source)
        .getValue(context, Boolean.class);
~~~

User values are now data passed into the context, not re-parsed as SpEL syntax.

If you need to pass a list or map, place the validated collection into a variable:

~~~java
context.setVariable("allowedCodes", validatedCodes);
context.setVariable("settings", validatedSettings);
~~~

Then the expression accesses only the values provided:

~~~java
#allowedCodes.contains(#customerCode)
~~~

Using variables does not automatically make an expression safe if users are still allowed to control the entire expression string. It only prevents concatenating data values into code. Expression permissions still need to be restricted separately.

## 6. Restricting EvaluationContext permissions

### 6.1. Do not expose the entire application to the context

StandardEvaluationContext can support property, method, constructor, type, and bean access depending on configuration. If the root object is a large service or an entity with many relationships, the expression can reach far more data than needed.

Provide a small, clearly scoped object:

~~~java
public record CustomerExpressionView(
        String code,
        String displayName,
        boolean active
) {
}
~~~

Create the context from the prepared view:

~~~java
CustomerExpressionView view =
        new CustomerExpressionView(
                customer.getCode(),
                customer.getDisplayName(),
                customer.isActive()
        );

StandardEvaluationContext context =
        new StandardEvaluationContext(view);
~~~

The expression can only access properties exposed by the view and other capabilities allowed by the context.

### 6.2. Consider SimpleEvaluationContext

When only a subset of SpEL features is needed, use SimpleEvaluationContext. This context is designed to restrict permissions compared to StandardEvaluationContext.

Example of creating a read-only context:

~~~java
SimpleEvaluationContext context =
        SimpleEvaluationContext.forReadOnlyDataBinding()
                .build();
~~~

SimpleEvaluationContext does not provide full capabilities such as type references, constructors, and bean references. Method invocation support also depends on the builder configuration and permitted resolvers.

Choose the specific configuration matching the expressions that actually need to run. Do not enable method resolvers or extra access permissions just to make an arbitrary expression work.

SimpleEvaluationContext is also not a general resource limiter. The application still needs to limit expression length, data, and evaluation cost.

### 6.3. Restrict methods with side effects

If an expression can invoke methods, provide only the required methods. Avoid placing into the context methods that can:

- Send network requests or access the file system.
- Write to a database or mutate business state.
- Launch background tasks.
- Access sensitive data.
- Create large collections or arrays.
- Perform unbounded loops or queries.

Methods called from SpEL should have clear names and contracts, preferably with no side effects. Successful type conversion or successful method resolution is not an authorization check.

## 7. Limiting evaluation cost

### 7.1. Restrict complex expressions

An expression can contain many nesting levels, many operations, many method calls, or collection accesses. Length does not fully reflect execution cost.

Set appropriate limits for:

- Expression string length.
- Number and depth of nested structures.
- Array/list/map sizes.
- Number of elements iterated.
- Number of method invocations.
- Time and resources that methods are allowed to consume.

SpEL is not a sandbox environment for running arbitrary code. Do not allow untrusted users to author expressions that can invoke unrestricted methods and expect the parser to prevent every resource-heavy case automatically.

### 7.2. Do not rely on a single timeout

A timeout at the caller layer cannot automatically stop a running Java method. If a method has a loop that does not check interrupts or is performing unbounded I/O, timing out does not guarantee the underlying work has stopped.

A better approach is to:

- Disallow arbitrary method calls.
- Limit data and element counts before evaluation.
- Use time-bounded APIs for I/O operations.
- Design methods that finish quickly and controllably.
- For high-risk cases where untrusted expressions must be executed, consider isolating in a separate process or environment with CPU, memory, and time limits.

Do not use thread interruption as an enforcement safety mechanism for arbitrary code.

### 7.3. Compiler mode is not a security boundary

SpEL has a compiled mode to improve performance in some cases. Compiler mode is an execution and performance decision; it does not replace controlling types, methods, data, or EvaluationContext permissions.

Do not enable compiler mode merely to make untrusted expressions safer. Determine configuration based on actual usage, testing, and the Spring version in use.

## 8. Input validation and error handling

Distinguish errors occurring at each step:

| Stage | Error example | How to handle |
|---|---|---|
| Receive request | Payload too large | Reject before parsing |
| Validate data | Collection has too many elements | Return validation error |
| Parse | Invalid SpEL syntax | Catch ParseException |
| Permission resolution | Type or method not allowed | Reject according to context policy |
| Evaluate | Invalid property/method | Handle EvaluationException |
| Allocation/collection | Size exceeds limit or out of memory | Prevent upfront with resource limits |
| Consume result | Result has unexpected type or size | Check before passing to downstream business logic |

Example of validating input before parsing:

~~~java
public Object evaluate(
        String source,
        ExpressionInput input) {

    if (source == null || source.length() > 10_000) {
        throw new IllegalArgumentException(
                "Expression is missing or too long"
        );
    }

    if (input.tags() != null && input.tags().size() > 500) {
        throw new IllegalArgumentException(
                "Too many tags"
        );
    }

    ExpressionParser parser =
            new SpelExpressionParser(
                    new SpelParserConfiguration(false, false, 256)
            );

    Expression expression = parser.parseExpression(source);

    StandardEvaluationContext context =
            new StandardEvaluationContext();

    context.setVariable("customerCode", input.customerCode());
    context.setVariable("quantity", input.quantity());
    context.setVariable(
            "tags",
            input.tags() == null ? List.of() : List.copyOf(input.tags())
    );

    return expression.getValue(context);
}
~~~

This is an example illustrating validation checkpoints, not a complete sandbox for untrusted expressions. If users are allowed to author source directly, restrict syntax and access permissions via an allowlist before evaluation.

Messages returned to users should state the violated field or rule without exposing stack traces, internal class names, paths, or sensitive data.

## 9. Input limits checklist

Before introducing SpEL into an API or feature that lets users enter expressions, check:

- Expression length is limited before parsing.
- Payload is limited in bytes at the transport layer if needed.
- Strings, numbers, lists, maps, and arrays each have separate limits.
- Nested collections have depth and total element count limits.
- Array sizes are validated before evaluation.
- Auto-grow is disabled if not needed; if enabled, it has a specific limit.
- Root object contains only necessary data.
- Context variables hold validated and properly typed data.
- User data is passed via variables, not concatenated into SpEL strings.
- Method, type, constructor, and bean access are restricted as needed.
- Permitted methods have controlled cost and side effects.
- Parse errors and evaluation errors are handled separately.
- Results are checked for type and size before use.
- Tests exist for boundary inputs, large collections, and malformed data.

## 10. Summary

When expressions or data are supplied by users, multiple independent limits must be managed:

- Limit expression length before parsing.
- Limit string size, collection size, element count, nesting depth, and array size.
- Disable auto-grow if unnecessary and understand that auto-grow limits do not bound every way of creating collections.
- Pass data via EvaluationContext variables instead of concatenating directly into the expression string.
- Provide only necessary root objects and methods; consider SimpleEvaluationContext for a restricted feature set.
- Do not treat the parser, compiler mode, or a single timeout as a sandbox.
- Validate results and handle errors at the right stage.

SpEL is suitable for expressing clearly scoped rules. When users are allowed to control expressions, the application must control data, syntax, access permissions, and execution cost before using the result in business logic.
