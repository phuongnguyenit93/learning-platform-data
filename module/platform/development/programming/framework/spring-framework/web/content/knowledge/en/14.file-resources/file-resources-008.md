# Preventing Path Traversal and Enforcing File Access Control in Spring MVC

> **Scope:** Spring Web MVC (Servlet stack), Java 17+, and Spring Boot 3.x / Spring Framework 6.x. This lesson focuses on how APIs that **upload, download, view, modify, and delete files** prevent access outside the storage area, prevent users from reading other users' files, and protect the system against malicious paths, symbolic links, race conditions, oversized files, and dangerous contents. The most important defense is **never letting the client choose the physical path** and **enforcing server-side authorization for every operation on every resource**.

## 1. The Problem: One Filename Can Lead to Unintended Data

Suppose an application exposes:

```http
GET /api/download?name=invoice.pdf
```

Unsafe code:

```java
// ANTI-PATTERN — never use in a real application.
@GetMapping("/download")
public byte[] download(@RequestParam String name) throws IOException {
    return Files.readAllBytes(
            Path.of("/srv/app/uploads/" + name));
}
```

A client can replace `name` with path segments walking up to parent directories. If the application concatenates input directly into a path, sensitive files outside the upload directory can be read (if the process has filesystem permissions), for example:

```text
/srv/app/uploads/../../private/config.yml
```

This is **path traversal / directory traversal**, a form of unauthorized filesystem access caused by client-controlled paths. Operating systems, web servers, and URL decoders can represent paths in many ways, so merely checking whether a string contains `../` is **not enough**.

Alongside traversal sits **IDOR/BOLA (Broken Object Level Authorization)**: a client simply swaps a file ID for another user's valid ID. The physical path may stay completely inside the permitted folder, yet access is still unauthorized.

**Two independent barriers:**

1. **Filesystem isolation:** the opened file must belong inside the storage area, with proper symlink handling and OS permissions.
2. **Object-level authorization:** the current user must be authorized to **read/create/update/delete that specific file**, regardless of whether they can guess the ID.

Failing either one still leaves the endpoint vulnerable.

## 2. Untrusted Input Sources

Paths can enter the application from many places:

- `@PathVariable("filename")` and `@RequestParam("path")`.
- The `Content-Disposition` header of a multipart upload, via `MultipartFile.getOriginalFilename()`.
- JSON `{"path":"..." }` or form fields containing file/directory names.
- Metadata stored in a database if previously written from an unvalidated client.
- URLs from callbacks, archive entry names when extracting ZIP/TAR files, or URIs pointing to remote files.

Data already stored in the DB **does not automatically become trustworthy**. If a user was once able to modify `storedPath`, reading `storedPath` from a repository and passing it to `Files.readAllBytes` can still cause traversal.

**Do not confuse:**
- Client filename (display name): a value for presentation, must be restricted/escaped.
- Server storage key (internal filename): **generated by the server**, never taken from the client name.
- Opaque file ID (API ID): used by clients to reference a resource; the server maps the ID to metadata.
- Owner/tenant/ACL: permission data from identity and resource management systems, **never** trusting a client-sent `ownerId` field.

## 3. Path Traversal Variants

| Variant | Risk | How to reason about it |
| --- | --- | --- |
| `../` on Unix systems | Climbs to parent directories | Never pass client paths directly to the filesystem |
| `..\\` on Windows | Uses Windows separator | Never check only for `/` |
| `/etc/...` or `C:\\...` | Absolute path / drive root | Never let input choose the root |
| UNC paths like `\\\\server\\share` | Network share access via Windows path | Distinguish platform roots and UNC paths |
| `%2e%2e%2f`, `%252e%252e%252f` | URL encoding / multi-layer decoding | Standardize one decode pass, avoid repeated decoding |
| `foo/../secret` | `..` in the middle | Use `Path.normalize()`, though insufficient against symlinks |
| Symlink `uploads/link -> /etc` | Escapes root even when lexical path stays inside | Check real path/NOFOLLOW, keep root private |
| Hard link or bind mount | Filesystem data referenced in multiple ways | Use OS isolation and restrict who can alter contents |
| ZIP entry `../../x` | Zip Slip during extraction | Validate every archive entry before creating files |
| Filename `..`, separators, NUL, special names | Parser/OS/display context differences | Generate storage keys independently on the server |

These examples are **test/diagnostic inputs**, not a claim that every framework/container lets those strings reach the handler. Earlier layers may return 400/404; that **never replaces** securely designed endpoints and storage services.

### 3.1. Why String Prefix Comparison Is Unsafe?

Example:

```java
// WRONG: plain text comparison ignores path component boundaries.
if (target.toString().startsWith("/srv/files")) {
    // Can mistakenly allow /srv/files-evil/...
}
```

`Path.startsWith(Path)` operates on path-component boundaries, making it better than `String.startsWith`:

```java
Path root = Path.of("/srv/files").toAbsolutePath().normalize();
Path target = root.resolve(relativeName).normalize();

if (!target.startsWith(root)) {
    throw new SecurityException("Outside storage root");
}
```

Yet the snippet above only checks **the lexical path**. If `/srv/files/link` is a symbolic link to a directory outside root, `target.startsWith(root)` can still return true even though the real file lives elsewhere. See section 5 on `toRealPath` and TOCTOU.

### 3.2. Never Use a Blocklist Regex for a Few Strings as Primary Defense

```java
// WRONG: neither an allowlist nor hard isolation.
if (input.contains("../")) {
    throw new IllegalArgumentException("Bad path");
}
```

Windows also uses `..\\`; data may or may not already be URL-decoded; paths have special segments; symbolic links never appear in input strings. Prefer **ID -> metadata -> server-generated key** over trying to turn an arbitrary client path into a "safe filename" by stripping `../`.

## 4. Recommended Design: Use IDs Instead of Physical Filenames

Replace an API like:

```http
GET /api/files?path=../../private/secret.txt
```

with:

```http
GET /api/files/11111111-1111-4111-8111-111111111111
```

Server holds metadata:

```text
fileId                 -> 11111111-1111-4111-8111-111111111111
owner                  -> alice
storageKey             -> 86a6c5d8-...-generated.bin
displayFilename        -> invoice.txt
mediaType              -> text/plain
size                   -> 1234
status                 -> AVAILABLE
tenantId               -> tenant-a
```

Notes:
- `fileId` is a **resource reference**; a user can still submit someone else's `fileId`, so **authorization is mandatory**.
- `storageKey` is generated by the server using a strong random UUID or internal system key, **never** derived from `getOriginalFilename()`.
- `displayFilename` is presentation metadata; it never decides where the file is stored.
- Files live outside `resources/static`, `public`, or the servlet webroot; never let Spring serve private assets through a static handler.
- Every upload/download/delete operation must look up metadata and verify `user/tenant/action/resource`.

Flow:

```text
GET /api/files/{opaqueId}
     |
Spring Security authenticates principal
     |
FileService.findById(opaqueId)
     |
Authorization: can principal READ this file?
     |
Metadata: server-generated storage key
     |
Private storage root + path/file-type verification
     |
Open file -> stream via ResponseEntity<Resource>
```

**Never use an unguessable UUID as proof of authorization.** UUIDs reduce bulk guessing, yet never replace authorization. A leaked link, misdirected log, or client-swapped ID must still pass permission checks.

## 5. Path Controls in Java NIO

### 5.1. `normalize()` Is a Lexical Operation

```java
Path root = Path.of("/srv/app/private-files")
        .toAbsolutePath()
        .normalize();

Path p = root.resolve("drafts/../file.txt").normalize();
// p has the form /srv/app/private-files/file.txt
```

`Path.normalize()` eliminates syntactically redundant `.` and `..` segments; it **does not touch the filesystem** and **does not know where symlinks point**. Nor does it verify access permissions or prove the file exists.

### 5.2. `toRealPath()` Checks the Real Filesystem

```java
Path configuredRoot = Path.of("/srv/app/private-files");
Path rootReal = configuredRoot.toRealPath(); // Root must exist.
Path realFile = rootReal.resolve(serverGeneratedName).toRealPath();

if (!realFile.startsWith(rootReal)) {
    throw new SecurityException("Outside permitted root");
}
```

This is an illustrative snippet. `toRealPath()` (without `NOFOLLOW_LINKS`) resolves symlinks and requires the file to exist. If a symlink points outside, the real path may no longer sit under root, allowing `startsWith` to detect it **at check time**.

However, this snippet still carries a **TOCTOU** risk if another process can swap a symlink or directory after the check and before the file is opened. Never treat `toRealPath() + startsWith() + open()` as an absolute defense against race conditions.

### 5.3. `NOFOLLOW_LINKS` and Its Limits

When you do not want to follow a symlink on the **final path component**:

```java
try (InputStream input = Files.newInputStream(
        candidate,
        StandardOpenOption.READ,
        LinkOption.NOFOLLOW_LINKS)) {
    // Read/stream within the applicable policy.
}
```

`LinkOption.NOFOLLOW_LINKS` asks Java not to follow symbolic links where supported. However, if `candidate` has **parent directories** controlled by an adversary, intermediate components still need protection. Therefore combine:

1. Storage root managed exclusively by the service user; untrusted parties have no permission to create/modify symlinks or hard links inside it.
2. Server generates a **single flat filename**, avoiding arbitrary nested paths.
3. Never give clients direct path control.
4. In strongly adversarial environments, use `SecureDirectoryStream` / directory-handle-relative opens when supported by the filesystem provider, or object storage APIs with proper permission boundaries.
5. Restrict OS privileges and container mounts of the application process.

`NOFOLLOW_LINKS` is a specialized safeguard and **does not** replace ACL/owner checks or application authorization.

### 5.4. Creating Files Without Overwriting Existing Ones

For uploads, avoid:

```java
// Bad: client filename may collide and overwrite.
Files.copy(upload.getInputStream(), root.resolve(upload.getOriginalFilename()));
```

Generate a server-side key and use an **atomic create**:

```java
String storageName = UUID.randomUUID() + ".bin";
Path destination = root.resolve(storageName);

try (InputStream in = upload.getInputStream();
     OutputStream out = Files.newOutputStream(
             destination,
             StandardOpenOption.CREATE_NEW,
             StandardOpenOption.WRITE)) {
    in.transferTo(out);
}
```

This is an **upload fragment**; `root` must be a protected directory, the file must already have passed permission/size/type checks, and metadata must be saved to the database with a cleanup policy on failure. `CREATE_NEW` ensures creation fails if the target already exists (including a symbolic link), making the existence check + creation atomic under supporting filesystems. Never write `if (!Files.exists(path)) Files.write(...)` assuming there is no race. On ACL-enabled filesystems, apply restrictive initial permissions on private file creation.

## 6. Restricting Client Filenames: Display Only, Never a Storage Key

`MultipartFile.getOriginalFilename()` is **client-supplied input**. Spring Javadoc warns that this value may contain path information, `..`, or dangerous characters; never use it directly as a storage path.

Wrong:

```java
@PostMapping("/upload")
void upload(@RequestParam MultipartFile file) throws IOException {
    file.transferTo(Path.of("/data/files/", file.getOriginalFilename()));
}
```

This is an **anti-pattern**: beyond compilation/overload quirks with `Path.of(...)`, the core flaw is trusting the client filename and risking traversal/overwrite. **Never use** this pattern; real file APIs should use `@RequestParam("file")`, enforce size limits, and save under a server-generated name.

Good rules:
- Read the original filename only for display, auditing, or populating response `Content-Disposition` after filtering/normalization.
- Bound the length and allowed characters of display names; strip control characters, path separators, and special sequences.
- For downloads, use `ContentDisposition.attachment().filename(safeName, StandardCharsets.UTF_8)` to build properly escaped/encoded headers, and test on target clients/browsers.
- Even if the display name is `../secret.txt`, it must **never** be used to construct real read/write paths.

**Never treat `Paths.get(original).getFileName()` as an absolute guarantee:** on Linux, `\\` is not a path separator as on Windows, special characters can still cause header/UX issues, and attackers can still cause collisions. The clean approach is filtering display names with an allowlist while assigning storage names completely independently.

## 7. Authorization: Preventing IDOR/BOLA Per File

### 7.1. Authentication Differs From Authorization

- **Authentication:** verifies identity, e.g., principal `alice`.
- **Authorization:** verifies whether `alice` is permitted to **READ/WRITE/DELETE file X** in the matching tenant.

An API marked `.authenticated()` still lets any logged-in user read anyone else's files if record-level checks are missing:

```java
// ANTI-PATTERN: only checks that the user is logged in, not ownership.
@GetMapping("/api/files/{id}")
public Resource download(@PathVariable String id) {
    FileRecord file = repository.findById(id);
    return new FileSystemResource(storageRoot.resolve(file.storageKey()));
}
```

This code may have a safe path yet still suffer from IDOR. Better:

```java
FileRecord file = repository.findById(id)
        .orElseThrow(() -> new ResponseStatusException(
                HttpStatus.NOT_FOUND));

authorizationService.requireCanRead(currentUser, file);

Path filePath = storageService.resolveServerKey(file.storageKey());
Resource body = storageService.open(filePath);
```

This is a business-logic snippet; in the runnable demo in section 9, the minimal policy compares `authenticated principal name` with `owner` in metadata. Production systems also handle team sharing, tenant scoping, ACLs, suspended accounts, retention, and auditing.

### 7.2. 403 or 404?

For a resource belonging to someone else:
- **403 Forbidden:** user is authenticated but not permitted; clear for debugging and administration.
- **404 Not Found:** API intentionally avoids revealing whether the resource exists, commonly used to reduce enumeration.

Both options are valid if applied consistently. Never return 200 with an error message. The demo in section 9 uses **403** so you can observe authorization clearly; apps requiring resource-existence secrecy can return **404** after running the same authorization policy.

### 7.3. Never Take Ownership From the Request

```json
{
  "fileId": "11111111-1111-4111-8111-111111111111",
  "owner": "alice"
}
```

A client sending the body above **does not become alice**. Owner and tenant must come from the authenticated identity and server metadata, never from a self-declared `X-User` header or an `ownerId` form field.

### 7.4. Spring Security: Layers of Control

- **HTTP layer:** `SecurityFilterChain` requires authentication for `/api/files/**` and enforces coarse method/path rules.
- **Domain layer:** the service checks the specific file record (owner, tenant, sharing ACL, action) rather than relying solely on URL patterns.
- **OS/storage layer:** file/directory permissions, container isolation, and storage credentials limit blast radius if application code has a bug.

Across multiple instances or object storage, metadata/ACL checks and object opens must align with the permission model; if immediate revocation is required, avoid caching permissions too long or issuing unrevocable public links.

## 8. File Operations Requiring Dedicated Controls

| Operation | Risk | Must verify |
| --- | --- | --- |
| GET/download | Traversal, IDOR, secret disclosure | AuthN/AuthZ, server storage key, canonical containment, and file type |
| POST/upload | Escape outside root, overwrite, malware, DoS | AuthN/AuthZ, server key, `CREATE_NEW`, size/type/quota/scanning |
| PUT/replace | Overwriting wrong file/owner, lost updates | WRITE permission, ID ownership, version/concurrency |
| DELETE | Deleting another user's file, link tricks | DELETE permission, metadata state, safe deletion, and audit |
| List/search | Leaking filenames/IDs/accounts | Tenant/owner scoping inside the query, pagination |
| Preview/thumbnail | Parser exploits, XXE/image bombs | Sandboxing/isolation, format validation, resource caps |
| ZIP/TAR extract | Zip Slip, archive symlinks, zip bombs | Per-entry containment, symlink policy, total expanded quota |

**Never store uploads in** `src/main/resources/static`, `src/main/webapp`, or directories served automatically by the servlet container if files are private. An authorized `@GetMapping` is pointless if users can also fetch the same file via a public static URL.

## 9. Complete Runnable Example: File Download by ID With Authorization

The example below uses **Spring Boot 3.x, Java 17+, Spring Web, and Spring Security**. To demonstrate real authorization, it configures **two demo accounts** via HTTP Basic: `alice` and `bob`. Each user can download only their own file. A private temp directory is created by the server at startup, with server-defined metadata.

**Intentional boundaries:** this is a **GET/download-only** demo without uploads, database, email, external storage, or complex ACLs. `{noop}` passwords are for local learning only, never production. CSRF is not disabled; because the demo exposes only GET endpoints, no state-changing HTTP requests are needed. Demo files are tiny and filenames are fully server-controlled.

### 9.1. Preparing the Maven Project

Create a Spring Boot 3.x Maven project at [Spring Initializr](https://start.spring.io/) with Java 17+, **Spring Web**, and **Spring Security**:

### 9.2. Complete Java Code

```java
package com.example.demo;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.LinkOption;
import java.nio.file.NoSuchFileException;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.Map;
import java.util.Optional;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.InputStreamResource;
import org.springframework.core.io.Resource;
import org.springframework.http.ContentDisposition;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configurers.AbstractHttpConfigurer;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.stereotype.Service;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@Configuration
class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http)
            throws Exception {
        return http
                .authorizeHttpRequests(auth -> auth
                        .anyRequest().authenticated())
                .httpBasic(Customizer.withDefaults())
                .formLogin(AbstractHttpConfigurer::disable)
                .sessionManagement(session -> session
                        .sessionCreationPolicy(
                                SessionCreationPolicy.STATELESS))
                .build();
    }

    @Bean
    UserDetailsService userDetailsService() {
        // DEMO ONLY: {noop} and static passwords are never for production.
        return new InMemoryUserDetailsManager(
                User.withUsername("alice")
                        .password("{noop}alice-password")
                        .roles("USER")
                        .build(),
                User.withUsername("bob")
                        .password("{noop}bob-password")
                        .roles("USER")
                        .build());
    }
}

record FileRecord(
        String id,
        String owner,
        String storageKey,
        String displayName,
        long size) {
}

@Service
class PrivateFileStore {

    static final String ALICE_ID =
            "11111111-1111-4111-8111-111111111111";

    static final String BOB_ID =
            "22222222-2222-4222-8222-222222222222";

    private final Path root;
    private final Map<String, FileRecord> records;

    PrivateFileStore() throws IOException {
        // Server-created directory, no client path in its name.
        root = Files.createTempDirectory("private-file-demo-")
                .toRealPath();

        Path aliceFile = root.resolve("alice-note.txt");
        Path bobFile = root.resolve("bob-note.txt");

        Files.writeString(
                aliceFile, "Hello Alice\n",
                StandardCharsets.UTF_8,
                StandardOpenOption.CREATE_NEW,
                StandardOpenOption.WRITE);

        Files.writeString(
                bobFile, "Hello Bob\n",
                StandardCharsets.UTF_8,
                StandardOpenOption.CREATE_NEW,
                StandardOpenOption.WRITE);

        records = Map.of(
                ALICE_ID,
                new FileRecord(
                        ALICE_ID, "alice", "alice-note.txt",
                        "alice.txt", Files.size(aliceFile)),
                BOB_ID,
                new FileRecord(
                        BOB_ID, "bob", "bob-note.txt",
                        "bob.txt", Files.size(bobFile)));
    }

    Optional<FileRecord> find(String id) {
        return Optional.ofNullable(records.get(id));
    }

    InputStream open(FileRecord record) throws IOException {
        // Internally generated metadata. Pattern prevents accidentally
        // using paths with segments/separators from DB later.
        if (!record.storageKey().matches("[a-z0-9-]+\\.txt")) {
            throw new IOException("Invalid internal storage key");
        }

        Path path = root.resolve(record.storageKey()).normalize();
        if (!path.startsWith(root)) {
            throw new IOException("Outside storage root");
        }

        if (!Files.isRegularFile(path, LinkOption.NOFOLLOW_LINKS)) {
            throw new NoSuchFileException("Stored file is unavailable");
        }

        // Do not follow symlinks on the final file component.
        // Root is app-owned: users cannot create nested paths.
        return Files.newInputStream(
                path,
                StandardOpenOption.READ,
                LinkOption.NOFOLLOW_LINKS);
    }
}

@RestController
@RequestMapping("/api/files")
class FileController {

    private final PrivateFileStore store;

    FileController(PrivateFileStore store) {
        this.store = store;
    }

    @GetMapping("/{id}")
    ResponseEntity<Resource> download(
            @PathVariable("id") String id,
            Authentication authentication) throws IOException {

        FileRecord record = store.find(id)
                .orElseThrow(() ->
                        new ResponseStatusException(
                                HttpStatus.NOT_FOUND, "File not found"));

        // Object-level authorization: DO NOT only check logged-in status.
        if (!record.owner().equals(authentication.getName())) {
            throw new ResponseStatusException(
                    HttpStatus.FORBIDDEN, "Access denied");
        }

        // Stream is opened only after verifying principal + owner.
        InputStream stream = store.open(record);
        Resource body = new InputStreamResource(stream);

        String contentDisposition = ContentDisposition.attachment()
                .filename(record.displayName(), StandardCharsets.UTF_8)
                .build()
                .toString();

        return ResponseEntity.ok()
                .contentType(MediaType.TEXT_PLAIN)
                .contentLength(record.size())
                .header(HttpHeaders.CONTENT_DISPOSITION,
                        contentDisposition)
                .header("X-Content-Type-Options", "nosniff")
                .header(HttpHeaders.CACHE_CONTROL, "no-store")
                .body(body);
    }
}
```

### 9.3. Security Explanation of the Program

- `SecurityFilterChain` requires authentication; `Authentication#getName()` is supplied by Spring Security from the HTTP Basic identity, never from a client-fabricated `X-User` header.
- `PrivateFileStore.find(id)` returns only **server-created** metadata. The controller never uses `id` as a filesystem path.
- Comparing `record.owner()` with `authentication.getName()` is minimal object authorization. If `bob` submits Alice's valid ID, the API returns 403. Real apps need services/ACLs enforcing dynamic permissions and tenants.
- `root` is created via `Files.createTempDirectory(...)` and resolved with `toRealPath()` at startup; file keys are fixed internal strings without subdirectories or client paths. Production storage directories must live in a dedicated location with explicit ACLs/ownership; do not assume identical permissions across platforms.
- `Files.isRegularFile(...NOFOLLOW_LINKS)` verifies the final file is not a symlink at check time; `Files.newInputStream(...NOFOLLOW_LINKS)` avoids following a symlink on the final file when opening. The private root directory must still be protected from malicious processes altering structure between the two operations.
- `InputStreamResource` lets the response converter stream from the input. Because the stream is one-shot, the response sets `contentLength(record.size())` ahead of time from the demo metadata. When metadata is untrusted or file sizes can mutate, design a consistent mechanism and dedicated error/streaming handling.
- `ContentDisposition.attachment()` constructs the download header rather than letting users control raw headers. Display names in metadata should also be sanitized when users can upload files.
- `Cache-Control: no-store` and `nosniff` reduce caching and content-sniffing risks. They do not replace authorization or content scanning.
- Because the example uses a temp directory root and in-memory metadata, **restarting recreates new files**; never use this setup for durable file storage.

### 9.5. Testing HTTP by Identity

**Alice downloads Alice's file:**

```bash
curl -i -u alice:alice-password \
  http://localhost:8080/api/files/11111111-1111-4111-8111-111111111111
```

Key parts of the response:

```http
HTTP/1.1 200
Content-Type: text/plain
Cache-Control: no-store
X-Content-Type-Options: nosniff

Hello Alice
```

In the real response, `Content-Disposition: attachment` with Spring-encoded filename and `Content-Length: 12` are also present. The body is **12 bytes**: `Hello` (5) + space (1) + `Alice` (5) + newline (1). Browsers will tend to download instead of rendering text because of the attachment header.

**Bob tries to access Alice's file:**

```bash
curl -i -u bob:bob-password \
  http://localhost:8080/api/files/11111111-1111-4111-8111-111111111111
```

Expected **403 Forbidden**; the file is never opened by the controller because the owner check failed. The exact error body depends on Spring Boot/Security error configuration, so do not assert an exact JSON output.

**Alice uses a nonexistent ID:**

```bash
curl -i -u alice:alice-password \
  http://localhost:8080/api/files/99999999-9999-4999-8999-999999999999
```

Expected **404 Not Found**.

**Sending no credentials:**

```bash
curl -i \
  http://localhost:8080/api/files/11111111-1111-4111-8111-111111111111
```

Expected **401 Unauthorized** with the `WWW-Authenticate` challenge for HTTP Basic, handled by Spring Security before the controller.

**Alice tries injecting a traversal string into the URL:**

```bash
curl -i -u alice:alice-password \
  'http://localhost:8080/api/files/..%2F..%2Fprivate%2Fsecret.txt'
```

The request may be rejected by the servlet container, Spring Security firewall, or MVC mapping before the handler as 400/404. Even if the handler receives an ID not in the map, it never constructs a filesystem path from the ID, so no file outside root can be opened. **Never promise an exact status across all encodings/environments**; guarantee instead that the design never maps such input to a path.

In PowerShell, use `curl.exe` on a single line to avoid the `curl` alias and Bash line continuations.

## 10. Safe Uploads: Recommended Pipeline

The demo in section 9 only performs GET. To add `POST multipart` in a real application, `@RequestParam MultipartFile` alone is not enough; you need a clearly bounded pipeline:

```text
Authenticated user
   |
Authorization: canUploadTo(targetFolder/tenant)?
   |
Multipart size limits + quotas + rate limiting
   |
Validate filename display + allowlisted extension
   |
Validate actual file type/signature + parse/sandbox policy
   |
Server generates opaque storage key
   |
Private root (outside webroot) + CREATE_NEW
   |
Copy as stream; compute hash/scan if needed
   |
Persist metadata: owner/tenant/ACL/size/status
   |
Return 201 Created + opaque file ID
```

### 10.1. Spring Boot Multipart Limits

Example in `application.properties`:

```properties
spring.servlet.multipart.max-file-size=5MB
spring.servlet.multipart.max-request-size=6MB
spring.servlet.multipart.file-size-threshold=0B
```

- `max-file-size` limits a single file.
- `max-request-size` limits the entire multipart request.
- `file-size-threshold=0B` governs the container/Servlet disk-spill threshold for multipart parts; it **does not** replace disk quotas, timeouts, part counts, and cleanup.
- These settings are not a universal hard cap for all JSON/binary requests. Also configure reverse-proxy/container limits or byte-counting limits per data path.

### 10.2. Never Use `getBytes()` for Large Uploads

```java
// Bad: loads the entire byte array onto the heap.
byte[] full = upload.getBytes();
```

Instead, after authorization/limits and generating a storage key:

```java
// Illustrative fragment inside the storage service.
String storageKey = UUID.randomUUID().toString() + ".bin";
Path destination = storageRoot.resolve(storageKey);

try (InputStream input = upload.getInputStream();
     OutputStream output = Files.newOutputStream(
             destination,
             StandardOpenOption.CREATE_NEW,
             StandardOpenOption.WRITE)) {
    input.transferTo(output);
}
```

This snippet requires `java.util.UUID`, `java.io.InputStream`, `java.io.OutputStream`, and `java.nio.file.*`; `storageRoot` must be a server-controlled private directory and `upload` a validated multipart object. Never use `originalFilename` to build `destination`. Roll back/clean up if copying fails, and never publish file metadata before upload and scanning complete.

### 10.3. MIME Types and Extensions Are Untrusted

`MultipartFile.getContentType()` is client-sent metadata. A file named `photo.png` or claiming `image/png` does not guarantee the bytes are actually PNG. Based on business requirements:
- Allow only strictly required file types.
- Rely on file signatures + trusted parsing libraries, not extensions or headers alone.
- Block executables/scripts when unnecessary.
- Perform malware scanning/CDR if required by the environment.
- Avoid processing images/XML/PDF/ZIP without post-decode or post-decompression size bounds.
- Never serve untrusted user-uploaded files on an origin capable of executing HTML/JavaScript; consider a dedicated download domain and `Content-Disposition: attachment`.

**Zip Slip:** inside archives, every entry name is an untrusted path. Normalize and check containment for each entry, block symbolic links and absolute paths, and cap total expanded size and entry count. Checking only the uploaded ZIP's filename is **not enough**.

## 11. Downloads and Content-Disposition

For a private file authorized for reading, a typical response is:

```java
return ResponseEntity.ok()
        .contentType(MediaType.APPLICATION_OCTET_STREAM)
        .header(HttpHeaders.CONTENT_DISPOSITION,
                ContentDisposition.attachment()
                        .filename(safeDisplayName, StandardCharsets.UTF_8)
                        .build()
                        .toString())
        .header("X-Content-Type-Options", "nosniff")
        .cacheControl(CacheControl.noStore())
        .body(resource);
```

This is a standalone snippet requiring a sanitized `safeDisplayName` and a streamable `resource`. Never use raw strings:

```java
// ANTI-PATTERN: client-derived name can cause header/display issues.
response.setHeader("Content-Disposition",
        "attachment; filename=" + userSuppliedName);
```

Never let the client submit a content disposition value to alter the file path opened. The header filename controls only the **suggested download name**, never the storage key.

If the endpoint supports HTTP Range/partial content, cache validators, CDNs, or signed links:
- Proceed only after ACL checks pass.
- Ensure every downloaded byte slice belongs to the same authorized file.
- For redirects to object storage, signed URLs must be scoped to the exact object with a short TTL and expose no shared credentials.
- Never cache private responses in a public CDN cache without an explicit cache-key/auth isolation design.

## 12. Symlinks, TOCTOU, and Limits of Path Validation

### 12.1. What Does TOCTOU Mean?

**Time of Check to Time of Use**: the system checks a path/file at time T1, then opens/acts on it at time T2. If an adversary can swap a symlink or directory between those two moments, a valid check at T1 does not necessarily protect the operation at T2.

```text
T1: Files.isRegularFile("/private/root/a.txt")
        |
Attacker replaces entry a.txt with symlink
        |
T2: Files.newInputStream("/private/root/a.txt")
        |
Unexpected target
```

If an attacker has permission to modify the storage directory, `normalize()` or `toRealPath()` alone cannot solve the problem completely. The primary defense is **OS directory ownership and ACLs** preventing attackers from altering the root structure.

### 12.2. What Provides Stronger Protection?

- Use a **flat private storage root** and storage keys containing no `/`, `\\`, or nested segments.
- Never grant untrusted shell/local users write access to root or parent directories.
- Use `CREATE_NEW` on creation, `NOFOLLOW_LINKS` on open where supported, and a root directory immutable to other actors.
- When race resistance is required in shared/adversarial filesystems, consider `SecureDirectoryStream` (directory-handle-relative operations) if supported by the provider, or dedicated object storage APIs.
- Apply least-privilege file permissions/ACLs: the app user only reads/writes necessary files; never run the process as root or mount broad directories containing secrets.
- If the storage setup allows hardlinks or bind mounts from other actors, enforce appropriate OS/container mount policies; checking symlinks alone is insufficient.

**Note:** `SecureDirectoryStream` is not always supported by every filesystem provider; any fallback must be security-reviewed, never silently "falling back" to unguarded path access when high security is required.

### 12.3. Keep Path Validation and Authorization Separate

Even when:
```text
Path is inside /srv/app/private-files
```
the file can still belong to another tenant. And even if the database record says `owner=alice`, a `storageKey=../../secret` could still escape the filesystem. You need **both** layers of control.

Additional tests needed for upload/path operations (outside the GET demo):
- `../`, `..\\`, absolute paths, encoded traversal, and double-decoding at the appropriate layer.

## 14. Common Mistakes and Fixes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| `root + userPath` | Traversal / reading outside root | Use opaque ID → metadata → server-generated storage key |
| Only checking `contains("../")` | Misses Windows, encoding, symlinks | Allowlist storage keys + Path checks + OS isolation |
| Using `String.startsWith(root)` | Accepts sibling dirs like `root-evil` | Use `Path.startsWith(root)` |
| Trusting `normalize()` as real path | Symlinks can escape root | Use `toRealPath`/`NOFOLLOW` and private storage |
| Check then open in shared writable dir | TOCTOU symlink swap | Deny attacker writes in dir; use handle-relative APIs if needed |
| Saving with `getOriginalFilename()` | Traversal, overwrites, malicious names | UUID/random server key; separate `displayName` |
| Overwriting with `Files.write(...)` | Data loss / races | Use `CREATE_NEW` for new uploads |
| Checking login without checking owner | IDOR/BOLA | Enforce ACLs per record and action |
| Trusting client-sent `ownerId`, `tenantId` | Cross-user/cross-tenant access | Derive identity/tenant from server auth context |
| Storing private files under `static/` | Bypasses controller auth | Store outside webroot; serve via authorized endpoint |
| Trusting upload `Content-Type`/extension | Spoofed files, XSS, parser exploits | Validate bytes/format, allowlist, scan |
| Using `MultipartFile.getBytes()` | Loads large files onto heap | Stream to storage, enforce quotas |
| `readAllBytes()` on download | OOM on large files | Use `Resource`/streams and download limits |
| Returning raw file paths in errors | Leaks server layout | Generic error bodies and secure logging |
| Allowing inline untrusted HTML file responses | Stored XSS | Use `attachment`, `nosniff`, isolated download domain |
| Publicly caching private files | User data exposure | Use `no-store` or partitioned/authorized cache model |
| Using UUIDs instead of authorization | Anyone holding an ID can access it | Check principal + record ACL |
| Checking ZIP filename without checking entries | Zip Slip | Per-entry safe extraction + quotas |

## 15. Production Deployment Checklist

1. Are resources requested by **opaque file ID**, or can clients supply filesystem paths?
2. Are storage keys **server-generated** without any client-supplied path segments?
3. Is the root directory **outside the webroot**, with minimal OS permissions and container mounts?
4. Are **authentication + authorization enforced per file, action, and tenant**?
5. For symlinks, are root/parent permissions, `NOFOLLOW_LINKS`, and TOCTOU addressed?
6. Do uploads enforce `max-file-size`, `max-request-size`, quotas, content validation/scanning, and failure cleanup?
7. Are uploaded files created using an atomic non-overwriting operation such as `CREATE_NEW`?
8. Do downloads use proper statuses/headers, leak no storage paths, and avoid loading whole files onto the heap?
9. Are `Content-Disposition` filenames sanitized/encoded, paired with `nosniff` and safe cache policies?
10. Could private files be accessed directly through a static handler or CDN URL?
11. Does deletion or permission revocation invalidate signed URLs and cached copies per contract?
12. Have you tested user A vs B, traversal, encoded inputs, symlinks, parsers, concurrency, large files, and audit logs?

## 16. Self-Check

**Question 1.** Does `Path.resolve(input).normalize().startsWith(root)` completely block traversal?

**Answer:** No. It catches many lexical escapes, yet does not guarantee the real path when symbolic links exist and can still suffer from TOCTOU. The best defense is avoiding client paths, using a private root, and generating keys on the server.

**Question 2.** If Alice knows Bob's file UUID and both are logged in, can Alice download Bob's file?

**Answer:** No. A UUID is not a permission; the service must check object-level authorization, owner, tenant, and ACLs.

**Question 3.** May `MultipartFile.getOriginalFilename()` be used as the server filename?

**Answer:** No. It is client data and may contain paths or `..`; use it only as sanitized display metadata while generating the storage key on the server.

**Question 4.** Why is `CREATE_NEW` better than "check file does not exist, then write"?

**Answer:** `CREATE_NEW` performs an atomic creation operation, avoiding check-then-write races and refusing to overwrite existing files or symlinks.

**Question 5.** Should you return 403 or 404 when a file belongs to another tenant?

**Answer:** It depends on your resource-existence disclosure policy. 403 indicates forbidden access; 404 helps reduce enumeration. Neither may leak unauthorized data.

**Question 6.** Are `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff` enough for arbitrary file uploads?

**Answer:** No. You also need type/size limits, scanning or safe processing, storage isolation, and authorization; those headers only mitigate certain client-side risks.

**Question 7.** Why can a file inside the allowed directory still be accessed without authorization?

**Answer:** Because path containment differs from **object-level permissions**. Another user's file can sit in the same root; you must verify ACL/owner/tenant.
