# HttpSession: Creating, Invalidating Sessions, and Multi-Server Limitations

## 1. Why Does a Web Application Need Sessions?

HTTP inherently processes independent requests: one request does not carry memory from the previous request. Still, applications sometimes need to maintain **short-term state for a browser** across multiple calls, such as a shopping cart, multi-step form progress, UI preferences, or login session information. In the Java Servlet stack, `jakarta.servlet.http.HttpSession` is the API for associating server-side data with a session identifier carried by the client.

Example sequence:

~~~text
Client                         Load balancer               Server
  | GET /catalog                    |                          |
  |-------------------------------->|------------------------->|
  |<------------------------------- HTTP 200, no session needed|
  |
  | POST /api/demo-session/start     |                          |
  |-------------------------------->|------------------------->| getSession(true)
  |                                  |                          | setAttribute(...)
  |<------------------------------- Set-Cookie: JSESSIONID=... |
  |
  | GET /api/demo-session + Cookie   |                          |
  |-------------------------------->|------------------------->| getSession(false)
  |<------------------------------- stored data ---------------|
  |
  | DELETE /api/demo-session         |                          |
  |-------------------------------->|------------------------->| invalidate()
  |<------------------------------- HTTP 204 ------------------|
~~~

The name `JSESSIONID` in the diagram is the common Servlet container session cookie. When using Spring Session, the default name may be `SESSION`; the final name can be customized. **The cookie normally carries an ID for lookup; session attributes are kept on the server/store, not embedded automatically in the cookie.** Do not confuse `HttpSession` with a self-contained JWT carrying claims or a cookie storing the entire payload.

This lesson helps you:
- Understand the session lifecycle: non-existent, created, reading/writing attributes, timeout, invalidation, and creating a new session.
- Distinguish `getSession()` / `getSession(true)` from `getSession(false)`, and how to avoid unintended session creation.
- Understand session IDs/cookies, inactivity timeout, logout, session fixation, and security policies.
- Practice Java 17+ Spring Boot MVC with a controller/tests and two requests sharing one session.
- Evaluate local sessions under multi-node load balancing, sticky sessions, and shared session stores via Spring Session + Redis.
- Distinguish a shared session store from a business database, durability/consistency trade-offs, and scaling limits.

**Version scope:** examples target the Servlet stack `jakarta.servlet`, Java 17+, and Spring Boot 3.3.x / Spring Framework 6.1.x. Servlet API semantics apply across modern versions. When using Spring Security or Spring Session, verify dependencies/configuration against your running version.

## 2. What Is `HttpSession` and What Is It Not?

`HttpSession` represents a logical session between a web application and a client over a finite duration. The server/container generates a session ID, stores attributes under String keys, and may use cookies or URL rewriting to link subsequent requests to the same session.

| Component | Where is it stored? | Role |
| --- | --- | --- |
| `HttpSession` and attributes | Servlet container or replacement session store | State tied to the session |
| Session ID | Generated by server, typically sent by browser via cookie | Lookup key for the session |
| `JSESSIONID` | Common cookie in Servlet containers | Carries the container session ID |
| `SESSION` | Common cookie when Spring Session uses default cookie resolver | Carries the Spring Session ID |
| `HttpServletRequest` | A specific request | Allows looking up/creating the session and inspecting cookies |
| `SecurityContext` | Authentication context managed by Spring Security | Not equivalent to the whole session; storage depends on auth/security configuration |

**A session is not an automatic authentication mechanism.** Merely calling `getSession()` does not log a user in or authorize them. A session can be anonymous, and arbitrary attributes placed in the session do not replace authentication, CSRF protection, or authorization.

A browser can also hold many cookies. The server selects the matching cookie by domain, path, secure flags, and configuration. Never put session IDs in URLs or query strings in normal APIs; URLs routinely enter logs, browser history, and referrers, increasing the risk of exposing the session identifier.

### 2.1. Overall Lifecycle

~~~text
                   HTTP request without a valid session
                                  |
                         getSession(false)?
                          /             \
                       null         getSession(true)
                                       |
                                       v
                            NEW session + generated ID
                                       |
                               setAttribute(...)
                                       |
                                       v
                            ACTIVE, client sends cookie
                                 /              \
                       Inactive beyond         invalidate()
                           timeout                 |
                            |                      v
                            v                    INVALID
                          EXPIRED             do not reuse
                              \                    /
                               \                  /
                             Next request:
                       cannot find old session
                    creates new session only if requested
~~~

Timeout is normally based on the **inactivity interval** between client accesses, not an absolute deadline from login time. The server may run cleanup asynchronously, so "expiring to the exact second" is not a guarantee to rely on in the UI. In distributed session stores, the time a key is evicted and the time the next read detects expiration may differ.

## 3. Important Servlet Methods

| Method | Meaning | Notes |
| --- | --- | --- |
| `request.getSession()` | Returns current session, or **creates a new one** if absent | Can generate unintended state/cookies |
| `request.getSession(true)` | Equivalent creation-if-missing behavior | Use when you genuinely want to start a session |
| `request.getSession(false)` | Returns current session if present/valid, **does not auto-create** | Use in read-only or logout endpoints |
| `session.setAttribute(key,value)` | Stores or replaces an attribute | Keep data small, stable, and serializer-friendly |
| `session.getAttribute(key)` | Reads attribute or returns null | Cast/check type and handle absence |
| `session.removeAttribute(key)` | Removes a single attribute | Does not destroy the entire session |
| `session.invalidate()` | Destroys the session and unbinds attributes | Do not use that session object after invalidation |
| `session.getId()` | Reads the session ID | Avoid logging or returning to clients as ordinary data |
| `session.getCreationTime()` | Creation timestamp | Not the authentication timestamp |
| `session.getLastAccessedTime()` | Last request access timestamp | Not the last time `setAttribute` was called |
| `session.setMaxInactiveInterval(seconds)` | Changes inactivity timeout for this session | Values `<= 0` normally mean no timeout; avoid in production |
| `session.getMaxInactiveInterval()` | Reads current timeout | Unit is **seconds**, unlike Duration strings in application config |
| `request.changeSessionId()` | Rotates ID of current session, keeping attributes | Use upon successful authentication when preventing fixation |
| `request.isRequestedSessionIdValid()` | Checks whether request ID identifies a valid session | Does not mean the user is authenticated |

`request.getSession(false)` is crucial. A status endpoint reporting "no cart/session yet" should not create a session just because the controller declared `HttpSession` and triggered another API. Injecting `HttpSession` directly as a handler parameter often causes Spring MVC/Servlet to create a session if missing; to avoid this strictly, accept `HttpServletRequest` and call `getSession(false)` explicitly.

After `invalidate()`, many operations on the old `HttpSession` object throw `IllegalStateException`. Never retain a session reference in a singleton service or background thread; retrieve the session from the request context when needed.

### 3.1. Difference Between Removing an Attribute and Invalidating a Session

~~~java
HttpSession session = request.getSession(true);
session.setAttribute("theme", "dark");
session.setAttribute("cartId", 42L);

// Remove a single key, the session can still exist:
session.removeAttribute("theme");

// Destroy all attributes and the session:
session.invalidate();
~~~

This is a **fragment** to place inside a method having `HttpServletRequest request`. Do not use `removeAttribute("user")` as a default logout when Spring Security stores authentication state elsewhere; logout should use the configured security/logout flow.

### 3.2. Do Not Use `HttpSession` as Global Memory

A singleton `@Service` serves many users; mutable instance fields on a service are shared data inconsistent with session scope. `HttpSession` holds one client's state, yet **it does not automatically guarantee thread safety either**: two concurrent requests from the same browser can read/write the same session attributes.

Wrong example:

~~~java
// WRONG ILLUSTRATION: a singleton service must not store per-client carts.
@Service
class WrongCartService {
    private final List<String> items = new ArrayList<>();
    public void add(String item) { items.add(item); }
}
~~~

The snippet above lacks imports and is not meant to be copied and run independently. It illustrates the global-state mistake, **not the main example of this lesson**.

Even if `items` were replaced with `session.getAttribute("cart")` and items added to a mutable `ArrayList`, race conditions and risks in distributed session stores would still exist. For a real shopping cart, consider storing it in a database keyed by user/cart ID or performing transactional/atomic updates on the backend.

## 4. Session ID, Cookies, and Security Attributes

The HTTP response that first creates a session typically includes `Set-Cookie`, and subsequent requests include the corresponding `Cookie`. The browser stores and sends the cookie automatically when domain/path/security conditions match.

~~~http
HTTP/1.1 200 OK
Set-Cookie: JSESSIONID=<opaque-id>; Path=/; HttpOnly; Secure; SameSite=Lax
~~~

This is an **example of a security-configured cookie over HTTPS**, not the default header in every environment. `<opaque-id>` must be randomly generated by the server, never derived from a username or predictable timestamp.

- **`HttpOnly`:** JavaScript in the browser cannot read the cookie directly, reducing certain script-based theft paths; does not replace XSS prevention.
- **`Secure`:** the cookie is sent only over HTTPS; if `Secure` is enabled while testing `http://localhost` with a browser/curl, clients may not send the cookie back depending on client behavior.
- **`SameSite=Lax/Strict/None`:** helps restrict certain cross-site contexts; `SameSite=None` requires `Secure` in modern browsers. Do not treat SameSite as a complete replacement for CSRF protection.
- **`Path`, `Domain`:** determine where the cookie is sent; misconfiguration can prevent the cookie from reaching another endpoint.
- **Cookie `Max-Age` / `Expires`:** describes client-side cookie lifetime; **distinct** from server-side `HttpSession` inactivity timeout. A surviving cookie does not guarantee the server session is still valid.

Never return the session ID in debug bodies or access logs. Reverse proxies must forward HTTPS/forwarded headers accurately and be trusted in a controlled manner, especially when deciding `Secure` cookies, URLs/redirects, and origin validation.

### 4.1. Session Fixation: Rotating the ID After Authentication

If an attacker controls or knows a session ID before login, and the victim logs in while the system keeps using that same ID, the attacker can exploit it (*session fixation*). Servlet 3.1+ provides `request.changeSessionId()` to assign a new ID to the **current session** while retaining needed attributes.

~~~java
// ILLUSTRATIVE in an application-owned custom authentication flow:
HttpSession existing = request.getSession(false);
if (existing != null && authenticationSucceeded) {
    request.changeSessionId();
}
~~~

This is not a standalone snippet: `authenticationSucceeded` is a result verified by the auth service, never supplied by the client. If the application uses **Spring Security**, avoid manually rotating the ID or clearing the security context arbitrarily: Spring Security normally applies session fixation protection upon login. In modern Servlet containers, the default strategy is typically `changeSessionId`, with `newSession`/`migrateSession` available for specific needs. Verify actual policy with integration tests.

Rotating the ID does not automatically revoke all other credentials; logout and revocation of tokens, remember-me cookies, refresh tokens, and SSO follow separate logic. Rely on Spring Security's `SecurityFilterChain` and configured logout handlers for that.

## 5. Timeout and Session Invalidation: Key Distinctions

### 5.1. Inactivity Timeout

`session.setMaxInactiveInterval(1800)` means an inactivity limit of about **1800 seconds (30 minutes)**. Each request associated with the session observed by the container/store can refresh the access timestamp per its rules. `getLastAccessedTime()` is not simply the last time a developer called `setAttribute()`.

In a Spring Boot Servlet app you can set:

~~~properties
server.servlet.session.timeout=30m
~~~

When Spring Session is present, `spring.session.timeout=30m` can control repository timeout; when unset, Spring Boot's Servlet auto-configuration falls back to `server.servlet.session.timeout`. Do not set both and guess precedence by name; check your dependency-managed version and verify the runtime value via `getMaxInactiveInterval()`.

**Do not use a negative timeout as a way to "keep users logged in forever."** It increases the risk of hijacked sessions and unbounded data retention. If your product needs "remember me," use an appropriate authentication mechanism (token/cookie lifecycle, rotation, revocation), not an infinite session.

### 5.2. Logout and Session Invalidation

~~~java
HttpSession existing = request.getSession(false);
if (existing != null) {
    existing.invalidate();
}
~~~

Using `getSession(false)` avoids creating a new session just to destroy it. Subsequent requests carrying the old cookie will not find the old session once invalidation is persisted in the session store. However, for **concurrent requests already in flight**, invalidation does not guarantee immediate cancellation of ongoing work; enforce authorization at business boundaries and choose appropriate semantics.

In applications with Spring Security, use the logout endpoint/handler managed by Spring Security: it can clear the security context, invalidate `HttpSession`, and clean up cookies as configured. The demo below omits Spring Security to show raw Servlet operations, and **must not be treated as a secure login/logout implementation**.

### 5.3. Session Events and Cleanup

Servlets offer `HttpSessionListener`, `HttpSessionAttributeListener`, and `HttpSessionIdListener` for observing session creation/destruction or ID changes. With Spring Session Redis, `SessionCreatedEvent`/`SessionDeletedEvent`/`SessionExpiredEvent` depend on repository configuration and Redis keyspace notifications; **do not rely on expiration callbacks firing to the exact second or reliably across every failover**.

Never tie critical business logic such as refunds, order cancellations, or ticket locking **solely** to a session-expired event. Those workflows need transactions, scheduled jobs/reconciliation, and durable data sources independent of session lifecycles.

### 6.2. Controller: Actively Create, Read Only When Present, and Invalidate

`src/main/java/com/example/sessiondemo/web/DemoSessionController.java`:

~~~java
package com.example.sessiondemo.web;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/demo-session")
public class DemoSessionController {

    public record StartRequest(String nickname) {}
    public record DemoState(String nickname, int timeoutSeconds) {}

    @PostMapping(path = "/start", consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<DemoState> start(
            @RequestBody StartRequest input,
            HttpServletRequest request) {

        if (input.nickname() == null || input.nickname().isBlank()) {
            return ResponseEntity.badRequest().build();
        }

        HttpSession session = request.getSession(true);
        String nickname = input.nickname().trim();
        session.setAttribute("nickname", nickname);

        return ResponseEntity.ok(
                new DemoState(nickname, session.getMaxInactiveInterval()));
    }

    @GetMapping
    public ResponseEntity<DemoState> read(HttpServletRequest request) {
        // Do not create a session for someone merely checking state.
        HttpSession session = request.getSession(false);
        if (session == null) {
            return ResponseEntity.noContent().build();
        }

        Object value = session.getAttribute("nickname");
        if (!(value instanceof String nickname)) {
            return ResponseEntity.noContent().build();
        }

        return ResponseEntity.ok(
                new DemoState(nickname, session.getMaxInactiveInterval()));
    }

    @DeleteMapping
    public ResponseEntity<Void> end(HttpServletRequest request) {
        HttpSession session = request.getSession(false);
        if (session != null) {
            session.invalidate();
        }
        return ResponseEntity.noContent().build();
    }
}
~~~

**Analysis:**
1. `POST /start` validates `nickname`, then calls `getSession(true)` to create a session if absent; if one already exists, it **reuses the current session**. The stored value is a small string, avoiding complex serialization later when moving to a shared store.
2. `GET /api/demo-session` calls `getSession(false)`, returning `204 No Content` when no session or nickname exists, without accidentally creating a new session. This is a **demo policy**, not a mandatory Servlet status.
3. `DELETE /api/demo-session` invalidates the session if present and always returns 204. With the old cookie, a GET after logout will no longer read the destroyed session's attribute.
4. `session.getId()` is not returned in JSON; the ID must remain confidential like a session credential.
5. `timeoutSeconds` comes from `getMaxInactiveInterval()` (in seconds), which does not necessarily equal "seconds remaining."
6. The demo has no auth; anyone holding the cookie can access the demo session's nickname. Never use this endpoint to authorize access to real resources.

If the controller accepted `HttpSession` directly instead of `HttpServletRequest` in `read`, the framework might create a session on GET. This design intentionally avoids doing so.

### 6.3. Running and Observing Cookies with curl

In the project with Gradle wrapper:

~~~bash
./gradlew bootRun
~~~

On Windows you can use `.\gradlew.bat bootRun`. Use `curl.exe` in PowerShell when you want standard curl option parsing.

First, GET with no session:

~~~bash
curl -i 'http://localhost:8080/api/demo-session'
~~~

Expected result is **204 No Content**, normally with no new session cookie created by this controller. External filters (if added later) may create their own session, so never claim the entire app never emits a cookie.

Start a session, saving the cookie to a jar:

~~~bash
curl -i -c cookies.txt -X POST \
  'http://localhost:8080/api/demo-session/start' \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Lan"}'
~~~

Expected **200 OK**, JSON containing nickname `Lan` and `timeoutSeconds` matching config (e.g., 1800). The `Set-Cookie` header is normally named `JSESSIONID` when using container sessions. The cookie jar is strictly for testing; **do not commit or publish cookie files**.

Read back using the same cookie:

~~~bash
curl -i -b cookies.txt 'http://localhost:8080/api/demo-session'
~~~

Expected **200 OK** and `nickname="Lan"`. Without sending the cookie:

~~~bash
curl -i 'http://localhost:8080/api/demo-session'
~~~

Expected **204 No Content** because the request is not linked to the old session. This proves state is linked by session ID, not by IP address.

Invalidate:

~~~bash
curl -i -b cookies.txt -X DELETE \
  'http://localhost:8080/api/demo-session'
curl -i -b cookies.txt 'http://localhost:8080/api/demo-session'
~~~

The DELETE request is expected to return **204**; the GET with the old cookie is expected to return **204**. The container may or may not send an expired cookie depending on config, but the server has invalidated the session. After invalidation, sending `POST /start` with the old cookie can create **a new session** with a new ID; it does not resurrect the old session.

### 6.4. MockMvc Testing of the Session Lifecycle

`src/test/java/com/example/sessiondemo/web/DemoSessionControllerTest.java`:

~~~java
package com.example.sessiondemo.web;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.MediaType;
import org.springframework.mock.web.MockHttpSession;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.delete;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class DemoSessionControllerTest {

    @Autowired
    MockMvc mvc;

    @Test
    void getWithoutSessionDoesNotCreateOne() throws Exception {
        MvcResult result = mvc.perform(get("/api/demo-session"))
                .andExpect(status().isNoContent())
                .andReturn();
        assertEquals(null, result.getRequest().getSession(false));
    }

    @Test
    void sameSessionKeepsAttributeUntilInvalidation() throws Exception {
        MvcResult created = mvc.perform(post("/api/demo-session/start")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"nickname\":\"Lan\"}"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.nickname").value("Lan"))
                .andReturn();

        MockHttpSession session =
                (MockHttpSession) created.getRequest().getSession(false);
        assertNotNull(session);
        assertEquals("Lan", session.getAttribute("nickname"));

        mvc.perform(get("/api/demo-session").session(session))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.nickname").value("Lan"));

        mvc.perform(delete("/api/demo-session").session(session))
                .andExpect(status().isNoContent());

        assertTrue(session.isInvalid());

        // New request without providing the invalidated session:
        mvc.perform(get("/api/demo-session"))
                .andExpect(status().isNoContent());
    }

    @Test
    void blankNicknameIsRejectedWithoutSessionCreation() throws Exception {
        MvcResult result = mvc.perform(post("/api/demo-session/start")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("{\"nickname\":\"  \"}"))
                .andExpect(status().isBadRequest())
                .andReturn();
        assertEquals(null, result.getRequest().getSession(false));
    }
}
~~~

Run `./gradlew test`. The tests confirm `getSession(false)`, attributes, and `invalidate()` in MockMvc **within a single application**. They do not prove Redis TTL, real browser cookies, two-node load balancing, concurrent session writes, or Redis downtime handling; those tests require real servers/containers, Redis, and a load balancer.

Suggested additional tests for production: short timeout with real cookie clients; session invalidation on logout; `HttpOnly/Secure/SameSite` cookie flags; Spring Security authentication/CSRF tests; two concurrent requests; testing across two nodes with a shared session store.

## 7. Multi-Server: Why Do Default Single-Node Sessions Fail?

Suppose a load balancer forwards requests to two independent application instances running the same version:

~~~text
                  ┌───────────────┐
Browser ──LB─────┤ App node A    │  Local session memory A
                  └───────────────┘
                  ┌───────────────┐
             └────┤ App node B    │  Local session memory B
                  └───────────────┘
~~~

If the initial `POST /start` hits node A, container A creates a session ID and stores `nickname` in A's memory. The next request reaches node B carrying the same cookie, yet B **does not have that local session entry**. `getSession(false)` on B can return null; the client sees state "lost" or must log in again. During rolling deployments or node restarts, memory-local sessions can also disappear.

This problem is not solved merely by:
- Deploying the same JAR file onto two nodes.
- Sharing the same business database while still keeping sessions in memory.
- Enabling HTTPS or sharing a cookie domain.
- Passing the session ID in a header.
- Keeping a static or singleton user object in each JVM.

You need an appropriate routing mechanism or **shared session persistence**.

### 7.1. Sticky Sessions at the Load Balancer

The load balancer can keep a browser pinned to node A (*session affinity/sticky routing*). This reduces "node hopping" while sessions remain in each JVM's memory.

Pros: simple, fewer round trips to a session store; suitable for some small, short-lived systems.

Limitations:
- If node A dies or is replaced during deployment, in-memory data can be lost.
- Uneven load distribution when heavy sessions accumulate.
- May require separate LB affinity cookies; those cookies differ from application cookies.
- Scaling nodes up/down and draining connections require careful strategy.
- Sticky routing **does not provide session failover on its own**; container replication or a shared store is needed if sessions must survive node loss.

Do not declare sticky sessions always wrong: it is a valid trade-off, provided failures are tested and user impact on node loss is clearly communicated.

### 7.2. Sharing `HttpSession` via Spring Session

Spring Session replaces container-managed session storage with a `SessionRepository`, typically via `springSessionRepositoryFilter` wrapping `HttpServletRequest/HttpSession`. Redis, JDBC, or another supported store holds shared session attributes and metadata across nodes.

~~~text
 Browser (SESSION cookie or equivalent configuration)
                   |
            Load balancer
             /          \
            v            v
      App node A      App node B
      Spring Session  Spring Session
            \          /
             \        /
           Shared Redis
       session attributes + TTL
~~~

By sharing Redis, requests with a valid ID can read the same session on either A or B, provided both nodes use compatible namespace, serializer, timeout, and session cookie configurations. Spring Session **does not make the whole application stateless**; it moves session state from each JVM into a shared store.

Limitations:
- Redis/network can be slow or down: session reads/writes fail and impact availability.
- Serialization of session attributes must stay compatible across deployed versions.
- Concurrent updates to the same session from multiple nodes can suffer lost updates; there is no automatic per-attribute transaction/locking.
- Session cache/flush modes, TTLs, and library versions affect when changes are persisted.
- Redis replication/failover involves durability trade-offs; a single ACK does not guarantee every replica across all regions has received the data.
- A shared session store does not automatically share singleton/local caches, WebSocket state, temporary files, or in-flight transactions.

This **replaces the `dependencies` block** in `build.gradle` from Section 6—do not blindly add a second `dependencies` block. For Boot 3.3, `spring-session-data-redis` plus the Redis starter is the right choice per Spring Session 3.x/Boot 3.3 docs. Latest Spring Session 4.x docs may reference `spring-boot-starter-session-data-redis` for newer Boot generations; do not copy latest starter names into Boot 3.3 without checking versions.

Example Redis configuration in **development**:

~~~properties
server.servlet.session.timeout=30m
spring.session.timeout=30m
spring.session.redis.namespace=demo:session
spring.session.redis.flush-mode=on_save
spring.data.redis.host=localhost
spring.data.redis.port=6379
~~~

For production:
- Supply Redis host/port via environment variables/secrets/managed Redis, securing connections with TLS, network policies, credentials, and failover.
- Application nodes must share **an appropriate session repository** and compatible serializer/schema.
- Separate Redis namespaces by environment/application; never share a namespace between staging and production.
- Configure request timeouts, connection pools, monitoring, max memory, and eviction policies appropriately. If Redis deletes keys due to eviction/TTL, sessions disappear.
- Cookie name/path/domain and secure flags must stay consistent across nodes and reverse proxies.
- Measure session read/write latency; avoid storing bulky objects or mutating them continuously.

Spring Boot auto-configuration can create the repository filter automatically when the right dependencies are on the classpath. Do not combine auto-configuration with `@EnableRedisHttpSession` unless intentionally overriding; if configuring manually, understand what auto-configuration backs off. Once enabled, the default cookie may become `SESSION` instead of `JSESSIONID`.

**About serialization:** Redis session repositories must serialize attributes, and many default configurations use JDK serialization; storing custom objects may require `Serializable` and version/class compatibility. Using simple immutable primitives/Strings/IDs reduces risk; if switching to a JSON serializer, establish type metadata rules and defenses against deserialization gadgets. Never treat any serialized Java object from a store as inherently harmless simply because it came from Redis.

### 7.4. Two-Node, One-Redis Experiment

Start an appropriate Redis instance at `localhost:6379` (or point both nodes to an authorized store). Run **two application processes** with the same source and Redis config on different ports:

~~~bash
./gradlew bootRun --args='--server.port=8081'
./gradlew bootRun --args='--server.port=8082'
~~~

Run each command in a separate terminal/process. Both processes must use the same Redis session namespace and cookie/serialization config. When multiple apps share hostname `localhost` on different ports, HTTP cookies **are not isolated by port**; this makes multi-node testing possible, though it can cause interference if other apps run on the same hostname. Use a dedicated cookie jar for testing.

Send POST to create a session on A, then GET on B using the same cookie jar:

~~~bash
curl -i -c shared-cookies.txt -X POST \
  'http://localhost:8081/api/demo-session/start' \
  -H 'Content-Type: application/json' \
  -d '{"nickname":"Lan"}'

curl -i -b shared-cookies.txt \
  'http://localhost:8082/api/demo-session'
~~~

If Spring Session Redis is working and both nodes share the store, the GET on B is expected to return **200** with nickname `Lan`. Try DELETE on B followed by GET on A:

~~~bash
curl -i -b shared-cookies.txt -X DELETE \
  'http://localhost:8082/api/demo-session'

curl -i -b shared-cookies.txt \
  'http://localhost:8081/api/demo-session'
~~~

The final GET is expected to return **204**, proving invalidation was observed through the shared repository (assuming sequential requests and a healthy backend). Seeing 204 before Redis is actually shared proves nothing: verify that the first request created a session, the response carried a cookie, cookie name/path match, and the next request sent that cookie.

### 7.5. When the Session Store Fails

If Redis becomes unavailable, the outcome depends on configuration and timing:
- Creating/reading/writing sessions can fail; never silently treat the user as anonymous and continue granting sensitive privileges.
- The load balancer may see many simultaneous request failures.
- Switching nodes will not help if both depend on the same broken store.
- Adding Redis HA/replication improves availability, yet **does not provide absolute consistency/durability**.
- When a session is lost due to eviction/TTL, the user may need to recreate the session/log in again; the system should define clear UX behavior.

Monitor session lookup failures, Redis latency, error rates, key eviction, stale serialization, and rolling deploy compatibility. Never log raw session IDs for debugging; use request tracing and aggregated metrics.

## 8. Concurrency: A Shared Session Store Does Not Solve Race Conditions

Two concurrent requests can read the same attribute and overwrite each other:

~~~text
Initially counter=0
Request A reads counter=0
Request B reads counter=0
Request A writes counter=1
Request B writes counter=1
Result is counter=1 instead of 2
~~~

This can happen with both local `HttpSession` and shared Redis. `setAttribute` is not an atomic "increment counter," and containers/stores may have different copy-on-read/write or flush modes. A `synchronized(session)` block on node A **does not synchronize with node B**.

For critical operations (payments, inventory, quotas, monetized carts), use business transactions, optimistic locking/versioning, atomic Redis commands/Lua scripts, or properly designed queueing/distributed mechanisms. `HttpSession` fits small, temporary UI state; never use it as the source of truth for assets or orders.

In particular, avoid putting a mutable object like `ArrayList` into the session and mutating its contents without calling `setAttribute` again: depending on the session repository and flush mode, internal mutations may not be marked "dirty" or saved reliably. For distributed sessions, prefer immutable values, re-assign attributes after changes, and design race-safe updates.

## 9. How `HttpSession`, Spring MVC Model Session, and Spring Security Differ

### 9.1. `@SessionAttribute` and `@SessionAttributes`

| API | Placement | Purpose |
| --- | --- | --- |
| `HttpSession` | Servlet request/controller | Actively create, read, write, and invalidate sessions |
| `@SessionAttribute("key")` | Handler **parameter** | Read an existing attribute; supports `required` |
| `@SessionAttributes("form")` | **Controller class level** | Temporarily keep model attributes across a multi-step controller flow |
| `SessionStatus#setComplete()` | Within `@SessionAttributes` flow | Ends management of the controller's model session attributes |
| `@RequestAttribute` | Handler parameter | Reads an attribute of **a single request**, not the session |

`@SessionAttributes` is not an arbitrary session-creation statement for any data. It fits multi-request model flows within the same controller; `SessionStatus.setComplete()` finishes the conversational model and cleans up related attributes, and **does not invalidate the entire `HttpSession`** or log out an account.

`@SessionAttribute` is suitable when a filter/middleware has already populated the data to read; to avoid accidentally creating a session or to control the entire lifecycle explicitly, `HttpServletRequest.getSession(false)` can be clearer.

### 9.2. Spring Security Session Management

Spring Security may use `HttpSession` to persist `SecurityContext`/authenticated principals across requests depending on authentication setup. Yet not every Spring Security app is stateful: bearer token resource servers or `SessionCreationPolicy.STATELESS` configurations may avoid sessions for auth. The phrase "REST API" also **does not strictly mandate** statelessness, even though stateless is a common choice for many architectures.

For cookie/session-authenticated web apps:
- Verify credentials in a trusted auth provider/filter.
- Enforce session fixation protection on login; modern Servlet setups normally rotate the session ID.
- Configure CSRF protection for state-changing requests when browsers attach cookies automatically.
- Log out through Spring Security to clear the security context and invalidate the session as configured.
- Optionally enforce concurrent session limits and session-expiration strategies.
- Remember-me tokens and SSO differ from sessions; invalidating `HttpSession` does not revoke every token type.

For instance, `SessionCreationPolicy.STATELESS` avoids using `HttpSession` for `SecurityContext`, yet **it is not a ban preventing application code from calling `getSession(true)`**. If you want zero server sessions, every component must be designed in alignment with that goal.

## 10. Choosing a Session Architecture as Node Count Grows

| Criterion | Local container `HttpSession` | Sticky LB + local session | Spring Session + shared Redis/JDBC |
| --- | --- | --- | --- |
| Simplicity on one node | Good | Requires LB | Requires external store |
| Preserving state across any two nodes | No | No, unless affinity stays on the same node | Yes, if store and config are healthy |
| Node A fails mid-session | Session usually lost | Usually lost/disrupts sessions pinned to A | Node B can continue via shared store |
| Attribute access latency | Usually in-process | Usually in-process | Incurs I/O/serialization cost |
| Concurrency issues | Yes | Yes | Yes, even cross-node |
| Serialization/deployment issues | Container-specific | Container-specific | More prominent; needs schema/serializer compatibility |
| Session store as new dependency | No | No | Yes; needs HA/observability |
| Best suited for | Dev, single node, tolerable session loss | Acceptable affinity, planned fallback | Multi-node setups needing session continuity across nodes |

If the business **does not need server-side sessions**, a stateless API with proper token authentication can scale more easily since nodes need not share `HttpSession`. Still, tokens carry expiration, rotation, revocation, replay, and security trade-offs; never claim switching to JWT automatically solves all distributed systems problems.

Some apps use Redis for caching/rate limiting without Spring Session; merely adding a Redis dependency does not automatically move `HttpSession` to Redis. You must have Spring Session integration/repository filters and proper configuration.

## 11. Security and Production Operations

### 11.1. Risks and Mitigations

| Risk | Action |
| --- | --- |
| Session ID read from JavaScript | Use `HttpOnly` cookies and prevent XSS |
| Cookie sent over plain HTTP | Enable HTTPS and `Secure` cookies in production |
| Session fixation after login | Rotate ID via Spring Security/container strategy |
| CSRF on cookie-authenticated POST/DELETE | Use Spring Security CSRF tokens and proper `SameSite` policy |
| Sessions live too long | Set reasonable timeout, plus absolute lifetime if business requires |
| Session leaked in logs | Never log IDs/cookies; use a separate correlation ID |
| Redis outage/eviction | Monitor availability, memory policy, TTL, and recovery |
| Serialization of large objects | Store only small data, immutable IDs, versioned serializers/schemas |
| Concurrent writes losing updates | Use atomic/transactional updates in a domain store |
| Cross-environment session namespace | Separate prefixes by environment, credentials, and network isolation |
| Logout only deletes client cookie | Must invalidate/revoke server-side state or auth layer |
| Using session to hold money/quotas | Move source of truth to a transactional datastore |

### 11.2. Data Durability and Session Stores

A session is **not** a long-term transactional database. If Redis is configured as an evicting cache, session keys can be evicted before the expected inactivity timeout under memory pressure. Redis replication/HA does not mean zero data loss across every partition/failover. JDBC-backed Spring Session trades off durability, latency, cleanup, and locking differently, while still requiring schema migrations, indexing, transactions, and security.

During rolling deployments, two app versions may run concurrently. If a session contains a serialized class from the new version that the old version cannot deserialize, users hit errors when routed to old nodes. Mitigation: use simple data records, explicit schemas, compatible or versioned serialization strategies, and real canary/blue-green testing.

### 11.3. What to Measure in Production

Track: active session count, unusual session creation rates, mid-flow session loss, login failures due to timeouts, Redis/session-store latency and errors, memory usage/key evictions, serialization failures, cookies with mismatched domain/path, session fixation/auth anomalies, logout processing duration, and concurrent requests on the same session.

For diagnostics, use trusted generated trace IDs and route templates. Never expose raw `Cookie`, `Set-Cookie`, session IDs, passwords, or private attributes in developer-wide dashboards/logs.

## 12. Common Issues and Root-Cause Analysis

| Symptom | Cause | What to check |
| --- | --- | --- |
| GET endpoint unexpectedly creates `JSESSIONID` | `getSession()`/injected `HttpSession`, or filter/security creates session | Controlled logging on `getSession(true)` call sites, inspect filter chain |
| Every request gets a new session ID | Client omits cookie, wrong cookie path/domain/secure | Use curl cookie jar and inspect `Set-Cookie`/`Cookie` |
| Using HTTPS yet cookie is not returned | Reverse proxy/forwarded headers, `SameSite`/`Path`/`Domain` | Test browser/devtools and ingress config |
| Session lost when switching nodes | JVM-local container state | Test A→B requests, check Spring Session/shared store |
| Sticky routing still loses sessions on deploy | Old pod/node replaced, local memory unreplicated | Plan connection draining and shared repository, or accept reset |
| Redis has data yet app cannot read session | Mismatched namespace/cookie name/serializer, expired session | Compare per-node configs, TTL, versions |
| Updated attribute yet other node sees old value | Flush/save behavior or concurrent updates | Prefer immutable values, re-set attribute, check transaction/last-writer |
| `IllegalStateException` after logout | Code keeps using invalidated session object | Stop all access to old session after `invalidate()` |
| Logout does not truly log out | Only cleared custom attr/cookie; security context/token remains | Use Spring Security logout/revocation flow |
| Session created for all API requests | Framework config or default `getSession()` calls | Review session creation policy and filters |
| Session expiry event does not fire on time | Repository/event config, Redis keyspace notifications | Do not rely on expiry events for critical business logic |
| Memory leak / oversized sessions | Storing entity graphs/huge carts, infinite timeouts | Store only IDs/small data, set timeouts and instrumentation |
| Counter/cart overwritten | Two requests modifying session concurrently | DB transactions, optimistic locking, or atomic Redis operations |
| MockMvc tests pass, multi-node fails | Mock session does not validate cookies/network/store | Write two-server + Redis/LB integration tests |

## 13. Step-by-Step Diagnostic Workflow

1. **Inspect `Set-Cookie`** on the session-creating response and **`Cookie`** on the next request. Check name and Path/Domain/Secure/SameSite; never copy real values into public tickets/logs.
2. Use `request.getSession(false)` on read endpoints to observe whether a session truly exists without altering state during debugging.
3. Check `getMaxInactiveInterval()` and `server.servlet.session.timeout` / `spring.session.timeout` for your version.
4. Compare requests hitting node A then node B with the same cookie. If only A reads it, determine whether local memory is in use or Spring Session configs mismatch.
5. Check Redis connectivity, namespace, TTL, serialization, flush mode, memory eviction, and latency.
6. For concurrent updates, audit who writes attributes, whether read-modify-write occurs, and whether transactions/locking exist.
7. Check Spring Security: session creation policy, fixation, login/logout, CSRF, `SecurityContextRepository`, and remember-me if used.
8. Try shutting down one node and verify clients keep their session via the shared store; when the shared store is down, verify fail-closed behavior, metrics, and user messaging.
9. Verify cookie flags and TLS/forwarded-header configuration in a real environment.
10. Separate user/business data that must never be lost from recreatable session state; move long-lived data to proper persistence.

## 14. Self-Check Questions

**1.** How does `request.getSession(false)` differ from `request.getSession()`?

**Answer:** `false` does not create a new session and returns null if no valid session exists; `getSession()` can create a session when missing.

**2.** Does `session.invalidate()` delete one attribute or the entire session?

**Answer:** It invalidates the session and unbinds its attributes; that session object must not be used afterward.

**3.** The browser still has a `JSESSIONID` cookie; does that guarantee the server session still exists?

**Answer:** No. The server may have invalidated it, timed it out, or lost in-memory state.

**4.** Why does a sticky LB not guarantee session survival if node A dies?

**Answer:** Affinity only routes requests to A while A is healthy; A's local state is typically lost if A is replaced without replication.

**5.** Does Spring Session Redis automatically create global transactions for all session attributes?

**Answer:** No. It shares persistence; you still must design for concurrency, serialization, failure handling, and consistency.

**6.** When Spring Security uses the session to store auth, is calling `session.removeAttribute("user")` a safe logout?

**Answer:** No. Auth state may reside in the security context or elsewhere. Use the Security-configured logout flow.

**7.** Can `@SessionAttributes` be used as an alias for `HttpSession.invalidate()`?

**Answer:** No. `@SessionAttributes` is for model attributes in a controller workflow; `SessionStatus.setComplete()` cleans up flow data and neither destroys the whole session nor guarantees logout.
