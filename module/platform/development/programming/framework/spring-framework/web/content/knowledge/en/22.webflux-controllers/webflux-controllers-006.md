# Spring WebFlux — @ExceptionHandler, @RestControllerAdvice, and ProblemDetail

## 1. Objectives

Spring WebFlux needs a consistent HTTP error contract even when an exception originates from a `Mono`, `Flux`, request binding, validation, business service, or framework handler. A good API communicates errors to clients via **HTTP status + error code + safe body**, rather than returning stack traces or returning 200 for failures.

This lesson focuses on annotated WebFlux controllers:

- Handling exceptions for a single controller with `@ExceptionHandler`.
- Reusing error-handling policies across controllers with `@RestControllerAdvice`.
- Using `ProblemDetail` per **RFC 9457 — Problem Details for HTTP APIs** and the `application/problem+json` media type.
- Understanding `ErrorResponse`, `ErrorResponseException`, `ResponseStatusException`, and `ResponseEntityExceptionHandler`.
- Distinguishing `WebExchangeBindException` from `HandlerMethodValidationException`; preserving HTTP 400, 404, 405, 409, 415, 500, and 504.
- Understanding precedence among local exception methods, multiple advice classes, `@Order`, and root/cause matches.
- Knowing the boundaries of controller advice with respect to `WebFilter`, WebExceptionHandler, Spring Security, reverse proxies, and already-committed responses.
- Building a standalone runnable example in **Java 17 / Spring Boot 3.5.0 / Spring Framework 6.2 / Maven**, verified with `WebTestClient`.
- Designing error contracts, i18n, requestId/traceId, logging, and protection of sensitive information.

This topic belongs to **WebFlux Controllers**. Spring MVC also has annotations with the same names, yet uses Servlet `DispatcherServlet`; WebFlux uses reactive `DispatcherHandler` and its corresponding types. Never copy WebMVC-specific exception-handler signatures into WebFlux without checking the Javadoc.

## 2. Which Processing Layers Does a Request Pass Through?

Overview diagram:

~~~text
Browser / API client
        |
        v
Reactor Netty / HTTP server
        |
        v
WebHttpHandlerAdapter + WebFilter chain
        |
        v
DispatcherHandler
        |
        +--> HandlerMapping (selects route)
        |
        +--> HandlerAdapter (invokes controller)
        |
        +--> Mono / Flux / return value
        |
        +--> @ExceptionHandler on controller
        |             or @RestControllerAdvice
        |
        +--> HandlerResultHandler / codecs
        |
        v
HTTP status, headers, response body
~~~

Beyond annotated controller resolution, there are `WebExceptionHandler` instances in the WebHandler chain, Spring Boot's default error handling, responses generated by reactive Spring Security, and gateway/proxy failures. They are **not synonymous** with controller advice.

| Scope | Mechanism | Suitable for |
| --- | --- | --- |
| Single annotated controller | `@ExceptionHandler` | Errors with a controller-specific contract |
| Multiple annotated controllers | `@RestControllerAdvice` | Domain errors, validation, API error schema |
| Built-in WebFlux exceptions | `ResponseEntityExceptionHandler` | Standardizing Spring `ErrorResponse` |
| Web handler/filter chain | `WebExceptionHandler` | Errors outside annotated controller processing |
| Boot reactive fallback | `ErrorWebExceptionHandler` | Errors not handled by higher layers |
| Reactive Spring Security | `SecurityWebFilterChain`, entry point/access denied handler | 401/403 related to authentication/authorization |
| Edge/gateway | Envoy/Nginx/CDN | May independently return 502/504/429 |

**Do not assume** a `@RestControllerAdvice` will catch all exceptions from a `WebFilter`. WebFilters typically execute outside `DispatcherHandler`, so errors may be handled by WebExceptionHandler or Boot's error layer. And if a proxy returns 504 on its own, the request never even reached the controller.

### 2.1. Exceptions and Reactor Error Signals

~~~java
@GetMapping("/api/items/{id}")
Mono<Item> get(@PathVariable long id) {
    return service.find(id);
}
~~~

If `service.find(id)` returns a `Mono.error(new ItemNotFoundException(...))` before the response has committed, Spring WebFlux can route the error to the appropriate controller-local or global exception handler.

Both a **synchronously thrown** exception during handler invocation and an **onError signal** from a publisher within the request lifecycle can participate in WebFlux exception handling, though details and timing depend on response state.

Avoid calling `subscribe()` directly inside a controller just to kick off a task and return `Mono.just("ok")`: fire-and-forget tasks escape the request lifecycle, and their errors/cancellations are no longer managed naturally by the HTTP handler.

## 3. @ExceptionHandler Inside a Controller

Example:

~~~java
@RestController
@RequestMapping("/api/orders")
class OrderController {

    private final OrderService orders;

    OrderController(OrderService orders) {
        this.orders = orders;
    }

    @GetMapping("/{id}")
    Mono<OrderDto> get(@PathVariable long id) {
        return orders.find(id);
    }

    @ExceptionHandler(OrderNotFoundException.class)
    ResponseEntity<ProblemDetail> missing(
            OrderNotFoundException exception) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, "Order not found");
        p.setProperty("code", "ORDER_NOT_FOUND");
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(p);
    }
}
~~~

This is a **fragment**: `OrderService`, `OrderDto`, the exception, and imports are undefined; the standalone project is in section 13.

### 3.1. Annotation Matching

You can declare the exception type in the annotation:

~~~java
@ExceptionHandler(OrderNotFoundException.class)
ProblemDetail handle(OrderNotFoundException error) { ... }
~~~

Or let the framework infer it from the method parameter:

~~~java
@ExceptionHandler
ProblemDetail handle(OrderNotFoundException error) { ... }
~~~

Prefer an explicit exception type and a specific signature; avoid catching all `RuntimeException` when you only mean to handle one domain error.

Spring can match either the root exception or a cause within a wrapper exception. A wrapped exception does not guarantee the handler always receives the wrapper class; test nested causes and pick the appropriate exception type explicitly.

### 3.2. Parameters and Return Types

WebFlux exception handlers can accept the matching `Throwable`, `ServerWebExchange`, request/response interfaces, and certain context arguments. They can return:

- `ProblemDetail`.
- `ResponseEntity<ProblemDetail>`.
- `Mono<ProblemDetail>` or `Mono<ResponseEntity<ProblemDetail>>`.
- `ErrorResponse` or another codec-supported error DTO.

Asynchronous return example:

~~~java
@ExceptionHandler(InventoryUnavailableException.class)
Mono<ResponseEntity<ProblemDetail>> unavailable(
        InventoryUnavailableException exception) {
    ProblemDetail p = ProblemDetail.forStatusAndDetail(
            HttpStatus.SERVICE_UNAVAILABLE,
            "Inventory check service is busy");
    p.setProperty("code", "INVENTORY_UNAVAILABLE");
    return Mono.just(ResponseEntity
            .status(HttpStatus.SERVICE_UNAVAILABLE).body(p));
}
~~~

This is a fragment. Unless you genuinely need to compose non-blocking operations, returning `ProblemDetail`/`ResponseEntity` directly is simpler. Never perform blocking network or database calls in an exception handler just to embellish error content.

`@ExceptionHandler` methods do not support all `@RequestMapping` arguments—especially request-body and `@ModelAttribute`-related arguments; do not treat them as a second input-binding handler method.

## 4. @RestControllerAdvice and Scope

`@RestControllerAdvice` combines `@ControllerAdvice` with `@ResponseBody` so handler method bodies are serialized via HttpMessageWriter. It suits a system-wide unified API error format.

~~~java
@RestControllerAdvice
class ApiErrors {

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail missing(OrderNotFoundException ex) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND,
                "Resource not found");
        p.setProperty("code", "ORDER_NOT_FOUND");
        return p;
    }
}
~~~

**Difference:** `@ControllerAdvice` can also be used with `@ExceptionHandler`, whereas `@RestControllerAdvice` explicitly expresses intent to return a response body rather than a view template.

### 4.1. Local Handlers Before Global Handlers

If a controller defines an `@ExceptionHandler(OrderNotFoundException.class)` method and a global advice also catches that type, the controller-local method is typically evaluated before the global advice for errors raised by that controller.

This helps for exceptions requiring highly specific handling. However, overusing local handlers can cause the same error code to return different schemas/statuses across endpoints. Standardize a domain error catalog and override locally only when a genuinely different contract applies.

### 4.2. Restricting Advice with Selectors

You can scope advice to a package:

~~~java
@RestControllerAdvice(basePackages = "com.example.api")
class PublicApiErrors {
}
~~~

Or by controller annotation:

~~~java
@RestControllerAdvice(annotations = RestController.class)
class RestOnlyErrors {
}
~~~

You can use `basePackageClasses` instead of package strings for safer refactoring. Selectors carry runtime matching cost, so avoid complex selectors when a single global advice suffices.

### 4.3. Multiple Advice Classes and @Order

Example:

~~~java
@Order(-1)
@RestControllerAdvice
class DomainErrors {
}

@Order(100)
@RestControllerAdvice
class OptionalFallbackErrors {
}
~~~

These are fragments. Advice classes are ordered via `Ordered`/`@Order`. Within one advice, a root match takes precedence over a cause match, yet **a cause match in a higher-precedence advice** can beat a root match in a lower-precedence advice.

Common risk: a high-precedence advice has:

~~~java
@ExceptionHandler(Exception.class)
ProblemDetail everything(Exception ex) {
    return ProblemDetail.forStatus(
            HttpStatus.INTERNAL_SERVER_ERROR);
}
~~~

This can accidentally convert legitimate framework 400/405/415 errors into 500. In Spring Boot, it can also interfere with the auto-configured ProblemDetails handler. Only write a catch-all if you truly manage **all** HTTP error semantics and maintain thorough regression tests.

## 5. RFC 9457 — Problem Details

RFC 9457 defines a human- and machine-readable error response format.

~~~http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Resource not found",
  "instance": "/api/widgets/42"
}
~~~

### 5.1. The Five Standard Fields

| Field | Meaning | Best practice |
| --- | --- | --- |
| `type` | URI identifying the problem type | Stable URI, optionally linking to docs; defaults to `about:blank` |
| `title` | Short summary of the error type | Keep stable per type; may be localized |
| `status` | HTTP status | Must match the actual HTTP status line |
| `detail` | Readable explanation for this occurrence | Must not contain SQL, secrets, stack traces, or PII |
| `instance` | URI reference to this occurrence | May be the request path; avoid leaking sensitive tokens/queries |

Extension properties can be added per the API contract: `code`, `requestId`, `invalidFields`, and others. The RFC does not require all clients to consume extension fields.

### 5.2. Creating ProblemDetail in Spring

~~~java
ProblemDetail p = ProblemDetail.forStatusAndDetail(
        HttpStatus.CONFLICT,
        "Order state does not allow this operation");
p.setTitle("Conflict");
p.setProperty("code", "ORDER_CONFLICT");
~~~

When returning `ProblemDetail` directly, Spring uses `status` to set the HTTP status and prefers `application/problem+json`. With `ResponseEntity`, ensure the status line never contradicts the body:

~~~java
return ResponseEntity.status(HttpStatus.CONFLICT).body(p);
~~~

Never return HTTP 200 with a body containing `status=409`. HTTP clients, proxies, and metrics inspect the status line first.

### 5.3. type URI

When a stable machine-readable distinction is needed:

~~~java
p.setType(URI.create(
        "https://api.example.com/problems/order-conflict"));
p.setTitle("Order conflict");
p.setProperty("code", "ORDER_CONFLICT");
~~~

The URL is illustrative only. If using real type URIs, document them for clients, keep URIs stable over time, and never construct them from an untrusted request `Host`.

### 5.4. Extension Properties Serialized as Top-Level JSON

~~~java
p.setProperty("code", "WIDGET_NOT_FOUND");
p.setProperty("requestId", "example-7ab...");
~~~

Spring integrates Jackson's `ProblemDetailJacksonMixin`, allowing map properties to be unwrapped into top-level JSON fields:

~~~json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "Resource not found",
  "instance": "/api/widgets/42",
  "code": "WIDGET_NOT_FOUND",
  "requestId": "example-7ab..."
}
~~~

`requestId` in the example is not a real value. Never reuse a singleton `ProblemDetail` and mutate it across requests: it is a mutable stateful object, which causes data races and cross-client metadata leaks.

### 5.5. Keep the Meanings of status and code Distinct

- HTTP status 404: protocol-level problem category.
- `code=WIDGET_NOT_FOUND`: application-level problem category.
- `requestId`: locates a specific request in logs; do not use as an error type.
- `traceId`: correlates multiple service spans.
- `detail/title`: display text, which may be translated.

Clients must branch on status/code/type rather than parsing natural-language strings in `detail` to make business decisions.

## 6. ErrorResponse and ErrorResponseException

Spring Framework 6.2 provides:

- `ProblemDetail`: model representing the response body.
- `ErrorResponse`: contract holding status, headers, body, and message codes/arguments.
- `ErrorResponseException`: exception capable of carrying an error response.
- `ResponseStatusException`: used when a request handler wants to express an HTTP status and optional reason.
- `ResponseEntityExceptionHandler`: base class for global advice handling built-in WebFlux exceptions per RFC 9457.

Example `ResponseStatusException`:

~~~java
return repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ResponseStatusException(
                        HttpStatus.NOT_FOUND, "Item not found")));
~~~

This is a fragment. In an application with many use cases, domain services should usually throw `WidgetNotFoundException` without embedding HTTP statuses, letting the WebFlux advice layer decide 404 + code.

### 6.1. ErrorResponseException When an Exception Carries Metadata

~~~java
ProblemDetail p = ProblemDetail.forStatusAndDetail(
        HttpStatus.CONFLICT, "Version mismatch");

throw new ErrorResponseException(
        HttpStatus.CONFLICT, p, null);
~~~

This is a fragment using Spring 6.2 APIs. Stay consistent with your error catalog, avoiding mixing multiple exception styles for the same business failure without a clear policy.

### 6.2. WebFlux ResponseEntityExceptionHandler

WebFlux import (different from Servlet MVC):

~~~java
import org.springframework.web.reactive.result.method.annotation.ResponseEntityExceptionHandler;
~~~

One implementation style:

~~~java
@RestControllerAdvice
class FrameworkErrorAdvice extends ResponseEntityExceptionHandler {
}
~~~

The Spring base class handles `ErrorResponse` exceptions and supports i18n/message code resolution. When overriding protected methods, use the exact **WebFlux 6.2 signatures**—never copy methods from MVC's `org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler`.

Do not both extend the base class yourself and let Boot create a duplicate handler without defining precedence.

### 6.3. Spring Boot Problem Details

With Spring Boot 3.5 WebFlux:

~~~properties
spring.webflux.problemdetails.enabled=true
~~~

Boot can auto-configure a `ResponseEntityExceptionHandler` handling built-in WebFlux errors as ProblemDetail. This fits a clean division:

1. Boot handles framework errors such as malformed bodies, unsupported media types, and method not allowed.
2. A custom `@RestControllerAdvice` handles only specific domain errors.
3. When customizing validation body formats, give the advice an appropriate `@Order` and test its interaction with Boot's handler.

Spring docs note that Boot's advice for this has order 0; custom advice can use `@Order(-1)` to be selected first for specific exceptions.

**There is no guarantee** this property unifies responses from Security filters, reverse proxies, raw WebFilters, or streaming transport failures. Those belong to different layers.

## 7. Validation in WebFlux: Two Exception Types

Spring WebFlux 6.2 distinguishes per-argument validation from method validation.

### 7.1. WebExchangeBindException

Typically with `@Valid @RequestBody` on a DTO:

~~~java
record CreateWidgetRequest(
        @NotBlank @Size(max = 80) String name) {
}

@PostMapping("/widgets")
Mono<Widget> create(
        @Valid @RequestBody CreateWidgetRequest request) {
    return service.create(request);
}
~~~

When the body fails Bean Validation, WebFlux can throw `WebExchangeBindException`. For this to run, the classpath needs a Jakarta Bean Validation provider such as `spring-boot-starter-validation`.

The exception exposes field/global errors so the app can map them to an appropriate ProblemDetail. Never return rejected values for passwords, tokens, or raw bodies to the client.

### 7.2. HandlerMethodValidationException

When constraint annotations are placed **directly** on method parameters:

~~~java
@GetMapping("/widgets/{id}")
Mono<Widget> get(@PathVariable @Min(1) long id) {
    return service.find(id);
}
~~~

Spring WebFlux built-in method validation can throw `HandlerMethodValidationException` if `id=0`. This exception can also arise when return-value constraints fail.

**Do not collapse every HandlerMethodValidationException into 400.** For return-value validation violations, the status may be 500 because the bug is on the server side; use `ex.getStatusCode()`/validation source to preserve semantics.

If a controller class has class-level `@Validated`, method validation may take the AOP path instead of built-in support. In Spring 6.2, do not add class-level `@Validated` solely to activate constraints without verifying the mechanism.

### 7.3. Safe Validation Error Body Example

~~~json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invalid input data",
  "code": "VALIDATION_FAILED",
  "invalidFields": ["email", "name"]
}
~~~

`invalidFields` should use safe field names/violation codes, sorted/deduplicated and bounded. Never return:

~~~json
{
  "field": "password",
  "rejectedValue": "plain-text-user-password"
}
~~~

If localized field messages are needed, use `MessageSource` and allowlisted message codes. Raw validation messages may include interpolated input; review them before exposing publicly.

### 7.4. Other Input Errors Remain with the Framework

| Error | Typical HTTP status |
| --- | --- |
| Missing body or malformed JSON | 400 |
| Bean validation on input | 400 |
| Method parameter constraint | 400 |
| Method return constraint | 500 |
| Unsupported Content-Type | 415 |
| Unacceptable Accept header | 406 |
| Unsupported HTTP method | 405 |
| Missing required query/header | 400 |

Do not let an `@ExceptionHandler(Exception.class)` swallow these statuses and return a generic 500.

## 8. Error Statuses and Domain Codes

| Condition | Status | Example code |
| --- | --- | --- |
| Validation/invalid input | 400 | `VALIDATION_FAILED` |
| Unauthenticated | 401 | `AUTH_REQUIRED` |
| Unauthorized | 403 | `ACCESS_DENIED` |
| Resource missing | 404 | `WIDGET_NOT_FOUND` |
| Method not allowed | 405 | Built-in handling |
| Accept not acceptable | 406 | Built-in handling |
| Business conflict | 409 | `WIDGET_CONFLICT` |
| ETag precondition failed | 412 | `PRECONDITION_FAILED` |
| Unsupported Content-Type | 415 | Built-in handling |
| Rate limited | 429 | `RATE_LIMITED` |
| Internal error | 500 | `INTERNAL_ERROR` |
| Auxiliary service unavailable | 503 | `UPSTREAM_UNAVAILABLE` |
| Upstream timeout (gateway role) | 504 | `UPSTREAM_TIMEOUT` |
| Client closes socket/cancels | No new standard HTTP status | Cleanup/cancel, send no further body |

Nginx may log 499 for client-closed requests in access logs; that is a **non-standard proxy log status**, not a standard status WebFlux should attempt to send to a disconnected client.

Status/code mappings must match API semantics. Do not auto-map every timeout to 504 if the service is not acting as a gateway/upstream proxy; in other use cases, 503 or a dedicated contract may fit better.

## 9. Reactive Exception Flow

### 9.1. Throw and Mono.error

In a reactive service:

~~~java
return repository.findById(id)
        .switchIfEmpty(Mono.error(
                new WidgetNotFoundException()));
~~~

`Mono.error` propagates the error to the subscriber; WebFlux can process it in controller exception resolution as long as the request has not committed.

Never write:

~~~java
remoteOperation().subscribe(
        value -> log.info("done"),
        ex -> log.warn("error", ex));
return Mono.just("started");
~~~

inside a controller for request-scoped work. A manually created subscription has its own lifecycle; `@ExceptionHandler` can no longer handle its result or error as an HTTP response.

### 9.2. Service Recovery vs HTTP Error Rendering

~~~java
return primary.fetch(id)
        .onErrorResume(TransientUpstreamException.class,
                error -> cache.find(id));
~~~

If recovery succeeds, the advice does not need to run. `onErrorResume` **does not** "resume the same source Flux" at the point of failure; it switches to a fallback publisher. Use fallbacks only when the API contract permits cached/stale data.

### 9.3. Translating Technical Errors

~~~java
return remote.fetch(id)
        .timeout(Duration.ofSeconds(2))
        .onErrorMap(TimeoutException.class,
                UpstreamTimeoutException::new);
~~~

An advice can map `UpstreamTimeoutException` to `504 UPSTREAM_TIMEOUT`. Do not make services decide `ResponseEntity` directly if you want reusable domain code.

### 9.4. Cancellation Differs from onError

A browser closing an SSE stream or a subscriber calling `cancel()` does not necessarily emit `onError`. Manage cleanup with `using/usingWhen/doFinally` per publisher lifecycle; do not attempt to send HTTP 500 simply because downstream no longer wants data.

## 10. Error Boundaries Outside ControllerAdvice

### 10.1. WebFilter

In WebFlux, `WebFilter` runs in the web handler chain, potentially before annotated controller resolution:

~~~java
@Component
class ExampleFilter implements WebFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange,
                             WebFilterChain chain) {
        return chain.filter(exchange);
    }
}
~~~

This is an illustrative fragment. If a filter emits an exception, controller advice is not guaranteed to receive it. Evaluate `WebExceptionHandler` or Boot's ErrorWebExceptionHandler when managing filter-level errors. Custom handlers must account for ordering, cancellation, and committed status.

### 10.2. Spring Security

Reactive Security generates 401/403 via `SecurityWebFilterChain`, `ServerHttpSecurity`, authentication entry points, and access denied handlers. Auth checks can execute **before any controller runs**, so do not rely solely on domain advice to standardize Security errors.

Never weaken authentication just to make CORS preflight "stop failing"; design Reactive CORS and security properly across layers.

### 10.3. WebClient Upstream Errors

`WebClient.retrieve()` can emit `WebClientResponseException` for upstream 4xx/5xx responses. An upstream HTTP 404 **does not automatically mean** your API client should receive 404. Translate by domain:

- Authoritative upstream catalog lacks the item → may be 404.
- Optional upstream service lacks cache → may fall back.
- Upstream 503/network timeout → may be 503/504.
- Upstream 401 due to broken backend credentials → never leak body or credential details.

Never echo raw upstream bodies or query URLs containing tokens into public ProblemDetails.

### 10.4. Gateway/Proxy

A CDN, gateway, or ingress can generate 502/504 outside Spring. Controller advice cannot apply to such responses. When a unified cross-service error contract is needed, align schemas/statuses across services and gateways and test at the external ingress.

## 11. Already-Committed HTTP Responses: An Unavoidable Limit

With Server-Sent Events:

~~~http
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: progress
data: {"percent":20}
~~~

Once status/headers are sent, a `Flux` error **cannot change the same response into**:

~~~http
HTTP/1.1 500 Internal Server Error
Content-Type: application/problem+json

{"status":500,"detail":"Internal server error"}
~~~

If the stream is still usable and the failure is business-level, you can emit an **SSE application error event**:

~~~text
event: app-error
data: {"code":"JOB_FAILED","message":"Cannot continue"}

~~~

The HTTP status remains 200. The frontend must distinguish transport success from application event outcomes.

When a transport write fails or the client has disconnected, **do not try to write ProblemDetail JSON or a second SSE error event**. Stop the publisher, clean up resources, and log/record metrics appropriately. An exception handler cannot recall bytes already sent; this is an HTTP protocol constraint.

## 12. Secure Design, i18n, and Correlation

### 12.1. Suggested Contract

~~~json
{
  "type": "https://api.example.com/problems/widget-not-found",
  "title": "Widget not found",
  "status": 404,
  "detail": "Requested resource not found",
  "instance": "/api/widgets/123",
  "code": "WIDGET_NOT_FOUND",
  "requestId": "example-2b7..."
}
~~~

HTTP status and `code/type` are the machine-readable source of truth; `detail/title` may be translated or refined.

### 12.2. Redact Sensitive Data

Never return:

- Exception stack traces / exception classes and internal Java packages.
- SQL queries, database URLs, usernames/passwords, access tokens/cookies.
- Filesystem paths, internal DNS names, private IPs/ports.
- Raw upstream response bodies that might contain customer records.
- Validation rejected values for passwords, API keys, or personal data.

Avoid:

~~~java
problem.setDetail(exception.getMessage());
~~~

for generic unexpected errors. Replace it with a safe public message constant and log useful details **server-side**. Logs must also protect secrets and follow retention/access policies.

### 12.3. Request ID and Trace ID

- Request ID distinguishes a specific request.
- Trace ID correlates multiple downstream spans in distributed tracing.
- Error code describes a stable error category.

For a cross-origin SPA reading an `X-Request-ID` response header, configure CORS `exposedHeaders` appropriately. Never trust raw client-sent headers as authoritative for log correlation without validation/normalization.

### 12.4. ErrorMessage Internationalization

Spring `ErrorResponse` supports message codes/arguments for `type/title/detail`, resolved by `ResponseEntityExceptionHandler` via `MessageSource`. You can translate title/detail by locale while keeping `code` and HTTP status unchanged.

An i18n-enabled application must define locale resolution, fallback language, and safe interpolation. Never let locale-dependent error details become branching conditions in frontend SDKs.

package demo;

import java.net.URI;
import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.atomic.AtomicLong;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.MediaType;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.bind.support.WebExchangeBindException;
import org.springframework.web.method.annotation.HandlerMethodValidationException;

import reactor.core.publisher.Mono;

@SpringBootApplication
public class WebFluxProblemApplication {
    public static void main(String[] args) {
        SpringApplication.run(WebFluxProblemApplication.class, args);
    }
}

record CreateWidgetRequest(
        @NotBlank @Size(max = 80) String name) {
}

record Widget(long id, String name) {
}

class WidgetNotFoundException extends RuntimeException {
}

class WidgetConflictException extends RuntimeException {
}

class UpstreamTimeoutException extends RuntimeException {
    UpstreamTimeoutException(Throwable cause) {
        super("Upstream timeout", cause);
    }
}

class SystemFaultException extends RuntimeException {
    SystemFaultException(String privateDetail) {
        super(privateDetail);
    }
}

@RestController
@RequestMapping("/api")
class WidgetController {
    private final AtomicLong ids = new AtomicLong(100);
    private final Map<Long, Widget> widgets = new ConcurrentHashMap<>();

    @GetMapping(path = "/widgets/{id}",
            produces = MediaType.APPLICATION_JSON_VALUE)
    Mono<Widget> get(@PathVariable @Min(1) long id) {
        return Mono.defer(() -> {
            Widget widget = widgets.get(id);
            return widget != null
                    ? Mono.just(widget)
                    : Mono.error(new WidgetNotFoundException());
        });
    }

    @PostMapping(path = "/widgets",
            consumes = MediaType.APPLICATION_JSON_VALUE,
            produces = MediaType.APPLICATION_JSON_VALUE)
    Mono<ResponseEntity<Widget>> create(
            @Valid @RequestBody CreateWidgetRequest request) {
        return Mono.fromSupplier(() -> {
            long id = ids.incrementAndGet();
            Widget widget = new Widget(id, request.name());
            widgets.put(id, widget);
            URI location = URI.create("/api/widgets/" + id);
            return ResponseEntity.created(location).body(widget);
        });
    }

    @GetMapping("/demo/conflict")
    Mono<String> conflict() {
        return Mono.error(new WidgetConflictException());
    }

    @GetMapping("/demo/timeout")
    Mono<String> timeout() {
        return Mono.delay(Duration.ofMillis(300))
                .map(tick -> "late")
                .timeout(Duration.ofMillis(40))
                .onErrorMap(TimeoutException.class,
                        UpstreamTimeoutException::new);
    }

    @GetMapping("/demo/crash")
    Mono<String> crash() {
        return Mono.error(new SystemFaultException(
                "jdbc-password=super-secret-value"));
    }
}

@Order(-1)
@RestControllerAdvice
class WidgetApiErrors {

    @ExceptionHandler(WidgetNotFoundException.class)
    ProblemDetail missing(WidgetNotFoundException ex) {
        return problem(HttpStatus.NOT_FOUND,
                "WIDGET_NOT_FOUND", "Resource not found");
    }

    @ExceptionHandler(WidgetConflictException.class)
    ProblemDetail conflict(WidgetConflictException ex) {
        return problem(HttpStatus.CONFLICT,
                "WIDGET_CONFLICT",
                "Resource is not in a valid state");
    }

    @ExceptionHandler(UpstreamTimeoutException.class)
    ProblemDetail timeout(UpstreamTimeoutException ex) {
        return problem(HttpStatus.GATEWAY_TIMEOUT,
                "UPSTREAM_TIMEOUT",
                "Upstream service did not respond in time");
    }

    @ExceptionHandler(SystemFaultException.class)
    ProblemDetail internal(SystemFaultException ex) {
        // Do not return ex.getMessage() to the HTTP client.
        return problem(HttpStatus.INTERNAL_SERVER_ERROR,
                "INTERNAL_ERROR", "An internal system error occurred");
    }

    @ExceptionHandler(WebExchangeBindException.class)
    ProblemDetail invalidBody(WebExchangeBindException ex) {
        ProblemDetail p = problem(HttpStatus.BAD_REQUEST,
                "VALIDATION_FAILED", "Invalid input data");
        p.setProperty("invalidFields",
                ex.getFieldErrors().stream()
                        .map(error -> error.getField())
                        .distinct()
                        .sorted()
                        .toList());
        return p;
    }

    @ExceptionHandler(HandlerMethodValidationException.class)
    ProblemDetail invalidMethod(
            HandlerMethodValidationException ex) {
        HttpStatusCode status = ex.getStatusCode();
        ProblemDetail p = ProblemDetail.forStatusAndDetail(
                status,
                status.is4xxClientError()
                        ? "Invalid input data"
                        : "An internal system error occurred");
        p.setProperty("code", status.is4xxClientError()
                ? "VALIDATION_FAILED" : "INTERNAL_ERROR");
        return p;
    }

    private ProblemDetail problem(
            HttpStatusCode status, String code, String detail) {
        ProblemDetail p = ProblemDetail.forStatusAndDetail(
                status, detail);
        p.setProperty("code", code);
        return p;
    }
}
~~~

### 13.5. Code Explanation

- `@Valid @RequestBody CreateWidgetRequest` produces validation errors via WebFlux argument binding.
- `@Min(1)` on the path parameter is a method-level constraint that can produce `HandlerMethodValidationException`.
- Advice has `@Order(-1)` to take precedence over Boot's order-0 RFC 9457 handler for specific exceptions.
- There is no `@ExceptionHandler(Exception.class)`, allowing framework 405/415/406 handling to continue working.
- `ProblemDetail.forStatusAndDetail` preserves the exact HTTP status when returned directly from a handler.
- `setProperty("code")` creates an extension property serialized top-level by Jackson in a standard Spring environment.
- `invalidFields` includes only safe field names, returning no rejectedValue.
- `SystemFaultException` illustrates an exception message containing a secret while the public body exposes only a generic detail.
- `HandlerMethodValidationException.getStatusCode()` prevents turning return-value validation failures into client 400s.
- `Mono.defer` and `Mono.fromSupplier` compute results at subscription time, though the in-memory map here does not replace a database/transaction.
- `URI.create("/api/widgets/" + id)` is a relative Location without hardcoding an internal hostname.
- `Duration.ofMillis(40)` is a very short demo-only timeout, unsuitable for production SLAs.
- The demo lacks authentication/authorization, quotas, or persistence; this is an error-handling infrastructure example.

import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.test.web.reactive.server.WebTestClient;

import static org.junit.jupiter.api.Assertions.assertNotNull;

        webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)

    @Autowired
    WebTestClient http;

    @Test
    void createReturns201AndLocation() {
        http.post().uri("/api/widgets")
                .contentType(MediaType.APPLICATION_JSON)
                .bodyValue(new CreateWidgetRequest("Reactive"))
                .exchange()
                .expectStatus().isCreated()
                .expectHeader().valueMatches(
                        HttpHeaders.LOCATION,
                        "/api/widgets/[0-9]+")
                .expectBody()
                .jsonPath("$.name").isEqualTo("Reactive");

    @Test
    void missingReturnsProblem404() {
        http.get().uri("/api/widgets/999999").exchange()
                .expectStatus().isNotFound()
                .expectHeader().contentTypeCompatibleWith(
                        MediaType.APPLICATION_PROBLEM_JSON)
                .expectBody()
                .jsonPath("$.status").isEqualTo(404)
                .jsonPath("$.code").isEqualTo("WIDGET_NOT_FOUND");
    }

    @Test
    void invalidJsonBodyReturnsSafe400() {
        http.post().uri("/api/widgets")
                .contentType(MediaType.APPLICATION_JSON)
                .bodyValue(new CreateWidgetRequest(""))
                .exchange()
                .expectStatus().isBadRequest()
                .expectBody()
                .jsonPath("$.code").isEqualTo("VALIDATION_FAILED")
                .jsonPath("$.invalidFields[0]").isEqualTo("name");
    }

    @Test
    void pathConstraintIs400() {
        http.get().uri("/api/widgets/0").exchange()
                .expectStatus().isBadRequest()
                .expectBody()
                .jsonPath("$.code").isEqualTo("VALIDATION_FAILED");
    }

    @Test
    void domainConflictIs409() {
        http.get().uri("/api/demo/conflict").exchange()
                .expectStatus().isEqualTo(409)
                .expectBody()
                .jsonPath("$.code").isEqualTo("WIDGET_CONFLICT");
    }

    @Test
    void timeoutIs504() {
        http.get().uri("/api/demo/timeout").exchange()
                .expectStatus().isEqualTo(504)
                .expectBody()
                .jsonPath("$.code").isEqualTo("UPSTREAM_TIMEOUT");
    }

    @Test
    void serverErrorDoesNotLeakSecret() {
        http.get().uri("/api/demo/crash").exchange()
                .expectStatus().is5xxServerError()
                .expectBody(String.class)
                .value(body -> {
                    assertNotNull(body);
                    assertFalse(body.contains("jdbc-password"));
                    assertFalse(body.contains("super-secret-value"));
                });
    }

    @Test
    void frameworkMethodErrorStill405() {
        http.delete().uri("/api/widgets/42").exchange()
                .expectStatus().isEqualTo(405);

    void unsupportedMediaTypeStill415() {
        http.post().uri("/api/widgets")
                .contentType(MediaType.TEXT_PLAIN)

                .expectStatus().isEqualTo(415);

    @Test

        http.post().uri("/api/widgets")
                .contentType(MediaType.APPLICATION_JSON)

                .exchange()
                .expectStatus().isBadRequest();
    }

## 15. ResponseEntityExceptionHandler vs Boot-First

Two common approaches exist:

**Boot-first:**

~~~properties
spring.webflux.problemdetails.enabled=true
~~~

Combined with a `@RestControllerAdvice` declaring specific domain/validation handlers while retaining Boot's built-in 400/405/415 behavior.

**Framework-first:** an advice extending WebFlux `ResponseEntityExceptionHandler` and customizing framework-specific protected hooks per Spring Framework 6.2 Javadoc.

Do not add both "just in case" without designing ordering, as that can cause duplicate handling and differing message codes.

### 15.1. i18n with MessageSource

`ErrorResponse`/`ResponseEntityExceptionHandler` supports message codes for type/title/detail resolved via `MessageSource`. You can translate `detail` for Vietnamese/English while keeping `code=VALIDATION_FAILED` unchanged.

Avoid using unsanitized exception messages as translation keys. For validation, interpolated values must be checked for privacy.

### 15.2. ErrorResponse Interceptor

Spring Framework 6.2 WebFlux documentation notes the ability to register `ErrorResponse` interceptors via WebFlux Configurer to augment or record RFC 9457 responses. When attaching a common requestId/correlation, consider official extension points; you do not always need to write a low-level `WebExceptionHandler`.

## 16. Common Mistakes

1. Using a generic catch-all `Exception.class` in high-precedence advice and turning every 400/405/415 into 500.
2. Returning ProblemDetail.status 404 while the HTTP response status line is 200.
3. Passing `ex.getMessage()` for 500 errors, accidentally leaking SQL/credentials.
4. Catching only WebExchangeBindException while overlooking HandlerMethodValidationException.
5. Forcing every method validation exception to 400 despite return-value validation.
6. Using Servlet MVC exception handler signatures in WebFlux.
7. Assuming `@RestControllerAdvice` catches every error from WebFilter/Spring Security/gateways.
8. Assuming advice can alter the status after an SSE response has committed.
9. Treating client cancellation as `onError` in every case.
10. Putting too much domain logic/HTTP status directly into `ResponseStatusException` inside services.
11. Reusing a shared mutable ProblemDetail instance across requests.
12. Returning rejected password/token values in validation errors.
13. Building problem `type`/`instance` from raw query strings or Host headers.
14. Adding `@EnableWebFlux` in Boot just to "enable WebFlux," accidentally disabling ProblemDetails auto-config.
15. Not testing built-in 405/406/415 after adding global advice.
16. Using blocking I/O inside an error handler on the Reactor Netty event loop.
17. Calling `subscribe()` inside a controller, causing errors to escape the HTTP lifecycle.
18. Swallowing all errors with `onErrorResume`/`onErrorComplete` and returning 200 success.
19. Overusing `@Order` to mask conflicts instead of designing distinct exception types.
20. Treating proxy HTTP 499 as a standard status WebFlux must send.
21. Treating `detail` as a stable error code for frontends.
22. Adding requestId to metric labels, causing high cardinality.
23. Assuming enabling Boot ProblemDetails customizes all 401/403/Security errors.
24. Neglecting sensitive data in logs even after redacting public payloads.
25. Lacking integration tests for JSON codecs, content negotiation, and handler ordering.

## 17. Debugging by Symptom

| Symptom | Likely cause | Check |
| --- | --- | --- |
| Invalid DTO returns 500 | Catch-all or wrong mapping | WebExchangeBindException, advice ordering |
| @Min does not run | Method validation inactive / different signature | Jakarta provider, Boot/Framework, annotations |
| Returns 400 for invalid return value | Catching HandlerMethodValidationException and hardcoding 400 | ex.getStatusCode |
| @RestControllerAdvice does not run | Wrong component scan/scope or error in filter | basePackages, order, WebFilter |
| 404 body differs from domain errors | Route not found via Boot fallback | ControllerAdvice vs error handler |
| POST text/plain returns 500 | Generic handler swallows UnsupportedMediaType | 415 defaults |
| code is not top-level | Altered Jackson ProblemDetail mixin | Codecs, content type |
| ProblemDetails property has no effect | Boot WebFlux auto-config disabled | @EnableWebFlux, app type, property |
| CORS/Security 401/403 differs | Security filter layer | ServerHttpSecurity / gateway policy |
| WebClient error body leaks hostname | Raw upstream error echoed | Domain translation, redaction |
| SSE error after 200 lacks ProblemDetail 500 | Response already committed | In-band error or cleanup |
| Timeout returns 500 instead of 504 | TimeoutException unmapped | onErrorMap/domain advice |
| Controller unit tests pass yet HTTP fails | Bypassed codec/validation/error resolver | WebTestClient HTTP integration |

**Exercise 8.** Use `onErrorMap` to convert `TimeoutException` into `UpstreamTimeoutException`; map it to ProblemDetail 504 with an error code.

**Exercise 9.** A `WebFilter` raises an error. Why might controller advice fail to handle it? Which layer is appropriate?

## 19. Production Checklist

- [ ] RFC 9457 ProblemDetail contract is consistent and documented.
- [ ] Status line, ProblemDetail.status, and domain code never contradict each other.
- [ ] Local/global advice responsibilities are clear and ordering is tested.
- [ ] No high-precedence catch-all breaks Spring built-in errors.
- [ ] Boot ProblemDetails config does not conflict with custom ResponseEntityExceptionHandler.
- [ ] Both validation exception types are handled properly by the app or Boot.
- [ ] Method return validation errors are never returned as client 400s.
- [ ] Secrets, stack traces, and raw rejected values are never exposed publicly.
- [ ] Logs include correlation IDs and privacy controls; metrics avoid high cardinality.
- [ ] Security 401/403 behavior is verified at the reactive filter layer.
- [ ] 404/405/406/415/429/500/503/504 semantics are verified.
- [ ] Post-commit streaming errors use SSE events/cancellation without attempting a new HTTP response.
- [ ] Client cancellation and Reactor `onError` are distinguished.
- [ ] Errors from WebFilter/WebClient/gateway have explicit contracts.
- [ ] Code/type remain stable across locales and versions; extensions are additive.
- [ ] `WebTestClient` integration tests run in CI, including negative cases.
- [ ] No blocking on the Netty event loop inside exception handlers.
- [ ] Production authentication, authorization, CSRF, CORS, and deployment proxy policies are verified.

## 20. Summary

- `@ExceptionHandler` handles errors in an annotated controller; `@RestControllerAdvice` shares handling across controllers.
- `ProblemDetail` per RFC 9457 provides type/title/status/detail/instance fields and can be extended with code/requestId.
- `ResponseEntityExceptionHandler` supports framework ErrorResponse; Spring Boot WebFlux offers a property to enable Problem Details.
- `WebExchangeBindException` and `HandlerMethodValidationException` serve two distinct validation scopes; never hardcode all method validations to 400.
- Local advice, global advice, `@Order`, and root/cause matching determine which handler is selected.
- WebFilter, Security, gateways, and already-committed responses lie outside the promise that "every error goes through `@RestControllerAdvice`."
- Reactor cancellation is not `onError`; business errors after a stream has committed require in-band error protocols or cleanup.
- Error APIs must return proper statuses, safe messages, stable codes, and have regression tests; never leak internal exception messages.
