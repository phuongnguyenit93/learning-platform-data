# Contract Testing HTTP Service Clients and WebSocket/STOMP

## 1. Goal: testing the contract that actually crosses the wire

A Java interface with `@HttpExchange` can compile cleanly while its proxy still sends the wrong HTTP method, URL, query, header, or JSON. A STOMP `@MessageMapping` can likewise pass a direct-method unit test while real clients fail to CONNECT, SUBSCRIBE, or receive MESSAGE frames.

**Contract testing** means verifying what both sides of a communication channel agree upon: request/destination, payload data, message types, status/error semantics, and compatibility rules. The contract must be verified at the layer where bugs can occur, rather than mocking a Java method and assuming the protocol works.

This lesson covers two communication paths:

- **HTTP Service Client:** the application consumes a REST API. Spring creates the interface proxy via `HttpServiceProxyFactory` and `RestClientAdapter` or `WebClientAdapter`. Verify the actual HTTP requests generated by the proxy and the responses decoded by the adapter.
- **WebSocket/STOMP:** the client completes a WebSocket handshake and then uses STOMP `CONNECT`, `SUBSCRIBE`, `SEND`, `MESSAGE`, `ERROR`, and `DISCONNECT`. Verify Spring's `@MessageMapping` routing, broker behavior, and data flow across the asynchronous session.

The lesson uses Java 17+, Spring Framework 6.1, and Spring Boot 3.3.x. The runnable example builds an HTTP interface proxy and a local STOMP endpoint. No external API provider or separate message broker is required; the Spring simple broker in the demo runs inside one JVM.

After this lesson, you will be able to:
1. Choose unit, mock HTTP, mock socket, integration, or consumer-driven contract tests matched to the risk.
2. Test `@HttpExchange`: method, URI template, path/query encoding, request headers/body, JSON responses, and error statuses; verify proxy configuration.
3. Test STOMP from a real client: handshake, subscribe, send, receiving payloads, and timeouts; separate destination tests from transport tests.
4. Use `RECEIPT` to synchronize on when the broker has processed a subscription, avoiding test races caused by `Thread.sleep`.
5. Build a matrix covering version evolution, auth/CSRF/Origin failures, reconnects, SockJS fallback, and delivery semantics, while recognizing each test type's limits.

## 2. A “contract” is more than a Java interface signature

In an HTTP Service Client, the signature:

~~~java
@GetExchange("/{id}")
Item findById(@PathVariable("id") long id);
~~~

describes only **part** of the contract. To verify it completely, you must know the base URL, `@HttpExchange` endpoint prefix, GET method, success/error HTTP codes, `Accept`, JSON shape, required fields, auth headers, and versioning policy. For instance, if the server only accepts `/v2/items/7` while the proxy calls `/v1/items/7`, Java still compiles and a Mockito unit test mocking the interface will still pass.

A STOMP contract also spans more than one method:

~~~java
@MessageMapping("/echo")
@SendTo("/topic/echo")
public EchoReply echo(EchoRequest request) { /* ... */ }
~~~

You must know the WebSocket HTTP endpoint (e.g., `/events`), application destination prefix (`/app`), client sending to `/app/echo`, server broadcasting to `/topic/echo`, JSON payload, STOMP headers, authentication/authorization rules, and reconnect behavior. HTTP URL `/events` **differs** from STOMP destination `/app/echo`: clients issue `SEND` after connecting, and HTTP proxies do not route `/app/echo` as an HTTP path.

| Layer | What to protect | Recommended test |
| --- | --- | --- |
| Facade/business | Orchestration, calculations, fallback selection | Unit test with fake/mock interface |
| HTTP proxy mapping | URL, method, path/query/headers, JSON, status | `MockRestServiceServer` bound to `RestClient.Builder` |
| HTTP transport | DNS/TLS, redirects, connection timeouts, HTTP encoders, proxies | WireMock/MockWebServer over a real network port |
| Provider HTTP contract | Server still accepts requests and returns promised schema/status | Provider verification/consumer-driven contracts |
| STOMP handler | `@MessageMapping`, conversion, validation, broker routing | Test with Spring messaging infrastructure |
| STOMP end to end | Handshake, `CONNECTED`, `SUBSCRIBE`, `SEND`, `MESSAGE` | `WebSocketStompClient` over local/random port |
| Deployment | LB, TLS termination, Origin, CSRF, SockJS fallback, broker relay | Integration/E2E across deployment network path |

**Each level only proves what it actually exercises.** A unit test mocking CatalogClient does not prove the HTTP proxy. A `MockRestServiceServer` test does not prove real TLS. A single-JVM `WebSocketStompClient` test does not prove sticky sessions across a cluster or message recovery after network drops.

## 3. Designing a testable HTTP contract

Suppose the catalog service provides:
- `GET /api/items/{id}` returns 200 JSON `{"id":7,"name":"Pen"}`; requires header `X-Tenant`.
- `POST /api/items` accepts JSON `{"name":"Pen"}` and returns 201 with the DTO.
- When the item is missing, GET returns 404.
- Responses are JSON; endpoints may also be versioned or switched by host configuration.

Target interface:

~~~java
@HttpExchange(url = "/api/items", accept = MediaType.APPLICATION_JSON_VALUE)
public interface CatalogClient {
    @GetExchange("/{id}")
    Item findById(@PathVariable("id") long id,
                  @RequestHeader("X-Tenant") String tenant);

    @PostExchange(contentType = MediaType.APPLICATION_JSON_VALUE)
    Item create(@RequestBody CreateItem body);

    record Item(long id, String name) {}
    record CreateItem(String name) {}
}
~~~

Tests must create the **real proxy** with `HttpServiceProxyFactory` over a `RestClient` configured similarly to production. Then inspect what the proxy actually sends, instead of stubbing `CatalogClient.findById()` with Mockito.

### 3.1. MockRestServiceServer

In Spring Framework 6.1, `MockRestServiceServer` can be bound to `RestClient.Builder`:

~~~java
RestClient.Builder builder = RestClient.builder()
    .baseUrl("https://catalog.example.test");

MockRestServiceServer server =
    MockRestServiceServer.bindTo(builder).build();

RestClient restClient = builder.build();
CatalogClient catalog = HttpServiceProxyFactory
    .builderFor(RestClientAdapter.create(restClient))
    .build()
    .createClient(CatalogClient.class);
~~~

**Order matters:** bind the mock server **before** `builder.build()`, so RestClient uses the request factory installed by Spring Test. The mock server checks method, URI, headers, and body without opening a TCP socket or contacting `https://catalog.example.test`. The `.test` domain is solely for verifying routing.

Assertions to make explicit:
- Full URL matches base URL + declared path; path variables and query parameters are encoded properly.
- Exact HTTP method GET/POST/PUT/DELETE, not just status checks.
- Request body encodes JSON with the right Content-Type. On POSTs with bodies, check field names, types, and values.
- Auth/tenant/correlation-ID headers appear accurately without leaking headers meant for other services.
- Response JSON decodes into the DTO type; test nullable/required fields and extra fields when schema allows them.
- 404/429/500 and contract-defined errors translate into the expected exceptions/statuses.
- Retries occur only when intentionally configured; request counts and idempotency keys must be verified if retries exist.

### 3.2. WebClient interfaces also need reactive semantics checked

With WebClientAdapter, interfaces typically return `Mono<Item>` or `Flux<Item>`. HTTP requests execute when the publisher is subscribed; calling the method without subscribing **does not prove a request was sent**. Tests should use `StepVerifier` from reactor-test against a mock HTTP server.

Illustrative integration snippet:

~~~java
Mono<Item> result = reactiveCatalog.findById(7L);

StepVerifier.create(result)
    .expectNextMatches(item ->
        item.id() == 7L && "Pen".equals(item.name()))
    .verifyComplete();
~~~

This snippet is **not standalone**: `reactiveCatalog` is an already-constructed WebClientAdapter proxy, `Item` is the DTO, and the test needs `reactor-test`, a mock HTTP server, and imports. Beyond success, test error signals, timeouts, cancellation, retry/resubscription, and request counts. Stubbing `Mono.just(...)` on the interface instead of running the WebClient proxy misses URI, header, codec, and HTTP status bugs.

Checking the `Publisher` with `StepVerifier` and checking requests on a mock HTTP server provide two complementary layers of evidence: StepVerifier checks reactive signals, while the mock HTTP server checks the wire protocol.

## 4. WebSocket and STOMP contracts

Spring STOMP over WebSocket typically follows this flow:

~~~mermaid
sequenceDiagram
    participant Client as STOMP client
    participant Server as Spring WebSocket endpoint
    participant Handler as @MessageMapping
    participant Broker as STOMP simple broker
    Client->>Server: HTTP GET /events + Upgrade
    Server-->>Client: 101 Switching Protocols
    Client->>Server: STOMP CONNECT
    Server-->>Client: STOMP CONNECTED
    Client->>Server: STOMP SUBSCRIBE /topic/echo
    Client->>Server: STOMP SEND /app/echo + JSON
    Server->>Handler: Resolve @MessageMapping("/echo")
    Handler->>Broker: Publish to /topic/echo
    Broker-->>Client: STOMP MESSAGE + JSON
~~~

Different risks at each step:
- **Handshake:** wrong endpoint, proxy not forwarding WebSocket Upgrade, TLS/WSS, origin policy, or authentication preventing the connection from opening.
- **CONNECT:** WebSocket opens yet STOMP CONNECT fails due to headers, CSRF, or auth; `101` does not prove STOMP reached `CONNECTED`.
- **SUBSCRIBE:** wrong destination, permissions, or broker routing. Subscribers not yet registered by the broker when a message arrives may miss it.
- **SEND:** client sends the wrong `/app` prefix, Content-Type mismatches converter, malformed JSON, or Bean Validation rejects the message.
- **MESSAGE:** payload has a different schema, wrong destination, or fails to broadcast to expected subscribers.
- **ERROR/close/reconnect:** old session is lost; client must reconnect and resubscribe; messages sent during disconnects require business-level replay when the contract demands it.

**Never treat a direct call to a `@MessageMapping` method as a complete STOMP contract test.** Direct calls only check Java logic; they bypass STOMP frame decoding, channel dispatching, message conversion, and broker subscriptions.

### 4.1. Avoiding race conditions in integration tests

Tests often write:

~~~java
session.subscribe("/topic/echo", handler);
session.send("/app/echo", new EchoRequest("ping"));
~~~

Both actions fire rapidly on the client side. Even though the SUBSCRIBE frame is sent before SEND, asynchronous processing on the server or broker can deliver the message before the subscription is registered. `Thread.sleep(500)` merely guesses timing and becomes flaky on CI.

STOMP supports the `receipt` header: the client asks the server to return a `RECEIPT` once a frame is processed. In Spring's `StompSession`, call `setAutoReceipt(true)` before `subscribe`, then use `Subscription.addReceiptTask(...)`. For receipt tracking to work, `WebSocketStompClient` needs a `TaskScheduler`; tests should enforce finite timeouts and handle lost receipts. Depending on the broker/server, **RECEIPT must be supported**; if production uses a different broker, verify receipt support before choosing this test strategy.

Do not assert global delivery order across multiple connections: STOMP ordering depends on individual channels, brokers, and Spring configuration. If business rules require strict ordering or at-least-once delivery, define explicit sequence/ack contracts and test them accordingly.

## 5. Standalone example: HTTP Service Client proxy + STOMP over a real socket

The example below uses **Java 17+**, **Maven**, and Spring Boot **3.3.13** (Spring Framework 6.1). One project contains:
- Interface `CatalogClient` to test URI, headers, JSON, and 404 with `MockRestServiceServer`.
- WebSocket STOMP endpoint `/events`, destinations `/app/echo` and `/topic/echo`.
- Integration test `@SpringBootTest(webEnvironment = RANDOM_PORT)` creating a STOMP client, awaiting the SUBSCRIBE receipt, sending JSON, and receiving MESSAGE.

The demo server uses a **simple broker** in a single JVM; it does not simulate clustering or a broker relay. The catalog URL in HTTP tests uses `.test` with no outbound network calls. The WebSocket test opens a **localhost** socket on a random port chosen by Spring Boot.

### 5.4. CatalogClient.java

~~~java
package demo;

import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.HttpExchange;
import org.springframework.web.service.annotation.PostExchange;

@HttpExchange(url = "/api/items", accept = MediaType.APPLICATION_JSON_VALUE)
public interface CatalogClient {

    @GetExchange("/{id}")
    Item findById(@PathVariable("id") long id,
                  @RequestHeader("X-Tenant") String tenant);

    Item create(@RequestBody CreateItem input);

    record CreateItem(String name) {}

~~~

This is the proxy client interface; the demo does not implement a REST server for `/api/items` because MockRestServiceServer acts as the provider in the HTTP tests.

### 5.5. SocketConfiguration.java

~~~java
package demo;

import org.springframework.context.annotation.Configuration;
import org.springframework.messaging.handler.annotation.MessageMapping;
import org.springframework.messaging.handler.annotation.SendTo;
import org.springframework.messaging.simp.config.MessageBrokerRegistry;
import org.springframework.stereotype.Controller;
import org.springframework.web.socket.config.annotation.EnableWebSocketMessageBroker;
import org.springframework.web.socket.config.annotation.StompEndpointRegistry;
import org.springframework.web.socket.config.annotation.WebSocketMessageBrokerConfigurer;

@Configuration
@EnableWebSocketMessageBroker
public class SocketConfiguration implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/events");
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.setApplicationDestinationPrefixes("/app");
        registry.enableSimpleBroker("/topic");
    }

    public record EchoRequest(String text) {}
    public record EchoReply(String text) {}

    @Controller
    public static class EchoController {
        @MessageMapping("/echo")
        @SendTo("/topic/echo")
        public EchoReply echo(EchoRequest request) {
            return new EchoReply("echo:" + request.text());
        }
    }
}
~~~

The `/events` WebSocket endpoint uses native WebSocket without SockJS enabled. The sample configuration intentionally omits authentication to test the basic contract. Real systems must authenticate/authorize STOMP destinations, validate payloads, and enforce Origin/CSRF protection per security policy.

### 5.6. HttpProxyContractTest.java

~~~java
package demo;

import org.junit.jupiter.api.Test;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.test.web.client.MockRestServiceServer;
import org.springframework.web.client.HttpClientErrorException;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.content;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.header;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.method;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.requestTo;
import static org.springframework.test.web.client.response.MockRestResponseCreators.withStatus;
import static org.springframework.test.web.client.response.MockRestResponseCreators.withSuccess;

class HttpProxyContractTest {

    private CatalogClient proxy(RestClient.Builder builder) {
        return HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(builder.build()))
            .build()
            .createClient(CatalogClient.class);
    }

    @Test
    void getUsesAnnotatedPathMethodHeaderAndJson() {
        RestClient.Builder builder = RestClient.builder()
            .baseUrl("https://catalog.example.test");
        MockRestServiceServer server =
            MockRestServiceServer.bindTo(builder).build();
        CatalogClient client = proxy(builder);

        server.expect(requestTo(
                "https://catalog.example.test/api/items/7"))
            .andExpect(method(HttpMethod.GET))
            .andExpect(header("X-Tenant", "tenant-1"))
            .andRespond(withSuccess(
                "{\"id\":7,\"name\":\"Pen\"}",
                MediaType.APPLICATION_JSON));

        assertEquals(
            new CatalogClient.Item(7L, "Pen"),
            client.findById(7L, "tenant-1"));
        server.verify();
    }

    @Test
    void postSerializesBodyAndUsesExpectedEndpoint() {
        RestClient.Builder builder = RestClient.builder()
            .baseUrl("https://catalog.example.test");
        MockRestServiceServer server =
            MockRestServiceServer.bindTo(builder).build();
        CatalogClient client = proxy(builder);

        server.expect(requestTo(
                "https://catalog.example.test/api/items"))
            .andExpect(method(HttpMethod.POST))
            .andExpect(content().contentTypeCompatibleWith(
                MediaType.APPLICATION_JSON))
            .andExpect(content().json("{\"name\":\"Pen\"}"))
            .andRespond(withStatus(HttpStatus.CREATED)
                .contentType(MediaType.APPLICATION_JSON)
                .body("{\"id\":8,\"name\":\"Pen\"}"));

        assertEquals(
            new CatalogClient.Item(8L, "Pen"),
            client.create(new CatalogClient.CreateItem("Pen")));
        server.verify();
    }

    @Test
    void missingResourceIsReportedAsHttp404() {
        RestClient.Builder builder = RestClient.builder()
            .baseUrl("https://catalog.example.test");
        MockRestServiceServer server =
            MockRestServiceServer.bindTo(builder).build();
        CatalogClient client = proxy(builder);

        server.expect(requestTo(
                "https://catalog.example.test/api/items/999"))
            .andRespond(withStatus(HttpStatus.NOT_FOUND));

        assertThrows(HttpClientErrorException.NotFound.class,
            () -> client.findById(999L, "tenant-1"));
        server.verify();
    }
}
~~~

Explanation:
- `proxy(builder)` creates a real proxy on the RestClient adapter. `bindTo(builder)` is called beforehand to swap in the test request factory.
- The GET test checks URL, method, header, and DTO; if the annotation path changes or a header disappears, the mock expectation fails.
- The POST test checks Content-Type, request JSON, and response body, catching cases where the interface is type-safe yet the wire format is wrong.
- The 404 test protects error semantics: RestClient's `retrieve` reports 4xx via exceptions by default. If an app installs a custom status handler, update assertions to match the **published contract**, not an implicit default.
- `server.verify()` confirms expected requests actually ran; the test makes no external TCP connections.

### 5.7. StompContractTest.java

~~~java
package demo;

import java.lang.reflect.Type;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.messaging.converter.MappingJackson2MessageConverter;
import org.springframework.messaging.simp.stomp.StompFrameHandler;
import org.springframework.messaging.simp.stomp.StompHeaders;
import org.springframework.messaging.simp.stomp.StompSession;
import org.springframework.messaging.simp.stomp.StompSessionHandlerAdapter;
import org.springframework.scheduling.concurrent.ThreadPoolTaskScheduler;
import org.springframework.web.socket.client.standard.StandardWebSocketClient;
import org.springframework.web.socket.messaging.WebSocketStompClient;

import static org.junit.jupiter.api.Assertions.assertEquals;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class StompContractTest {

    @LocalServerPort
    int port;

    private WebSocketStompClient stompClient;
    private ThreadPoolTaskScheduler scheduler;

    @BeforeEach
    void setUp() {
        scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(1);
        scheduler.initialize();

        stompClient = new WebSocketStompClient(
            new StandardWebSocketClient());
        stompClient.setTaskScheduler(scheduler);
        stompClient.setMessageConverter(
            new MappingJackson2MessageConverter());
    }

    @AfterEach
    void tearDown() {
        if (stompClient != null) {
            stompClient.stop();
        }
        if (scheduler != null) {
            scheduler.shutdown();
        }
    }

    @Test
    void clientCanConnectSubscribeSendAndReceiveJson() throws Exception {
        CompletableFuture<SocketConfiguration.EchoReply> received =
            new CompletableFuture<>();
        CompletableFuture<Void> subscribed =
            new CompletableFuture<>();

        StompSession session = stompClient.connectAsync(
                "ws://127.0.0.1:" + port + "/events",
                new StompSessionHandlerAdapter() {})
            .get(10, TimeUnit.SECONDS);

        try {
            // Request broker ACK for SUBSCRIBE handling via RECEIPT.
            session.setAutoReceipt(true);
            StompSession.Subscription subscription =
                session.subscribe("/topic/echo", new StompFrameHandler() {
                    @Override
                    public Type getPayloadType(StompHeaders headers) {
                        return SocketConfiguration.EchoReply.class;
                    }

                    @Override
                    public void handleFrame(
                            StompHeaders headers, Object payload) {
                        received.complete(
                            (SocketConfiguration.EchoReply) payload);
                    }
                });

            subscription.addReceiptTask(() ->
                subscribed.complete(null));
            subscription.addReceiptLostTask(() ->
                subscribed.completeExceptionally(
                    new IllegalStateException("SUBSCRIBE receipt timeout")));

            subscribed.get(10, TimeUnit.SECONDS);
            session.send("/app/echo",
                new SocketConfiguration.EchoRequest("ping"));

            SocketConfiguration.EchoReply reply =
                received.get(10, TimeUnit.SECONDS);
            assertEquals(
                new SocketConfiguration.EchoReply("echo:ping"), reply);
        } finally {
            session.disconnect();
        }
    }
}
~~~

The test uses `connectAsync` (returning a CompletableFuture, the Spring 6.1 API), replacing deprecated `connect(...)` overloads. `@LocalServerPort` injects the real port assigned by Boot. `StandardWebSocketClient` opens a WebSocket TCP connection on localhost, the STOMP handshake passes through the Spring server, SUBSCRIBE registers on the simple broker, SEND goes to the controller, and the test awaits the JSON MESSAGE.

**Why wait for RECEIPT?** If the test sends a message too soon after SUBSCRIBE, the broker may not have registered the subscription yet. Awaiting the receipt callback provides a protocol-level synchronization point. `ThreadPoolTaskScheduler` enables receipt and timeout tracking; `CompletableFuture.get(10, TimeUnit.SECONDS)` ensures the test fails clearly if CONNECT, RECEIPT, or MESSAGE never arrives. Never use `Thread.sleep` to guess readiness.

**Limitations:** receiving one MESSAGE proves the basic localhost flow works, without proving auth/Origin/CORS, loss/replay, network proxies, or scale-out. The real server/broker must support STOMP receipts; if the broker's policy does not provide receipts, use a separately verified synchronization mechanism instead of sleep.

### 5.8. Running and expectations

Place files in the structure above, install JDK 17+ and Maven, and run from the project directory:

~~~bash
mvn -q test
~~~

There are **4 `@Test` methods** across two classes: 3 HTTP proxy tests and 1 STOMP integration test. Expected exit status when environment and code match is Maven exit code **0**. Detailed reports are generated under `target/surefire-reports/`; `-q` may suppress test totals on stdout. This lesson provides code for the reader to execute and **does not claim the tests were executed in the authoring environment**.

If the STOMP test times out, check in order:
1. Did the server bind a port; is the endpoint `/events` and URL `ws://`?
2. Was a `CONNECTED` frame received?
3. Does the `SUBSCRIBE` destination match the `/topic` prefix? Did the broker send `RECEIPT`?
4. Did `SEND` to `/app/echo` map to `@MessageMapping("/echo")`?
5. Did the converter serialize/deserialize JSON for the records properly? Any STOMP ERROR, conversion exception, or unexpected close?
6. Does the test use finite timeouts and shut down session/client/scheduler to avoid resource leaks?

When an HTTP proxy test fails, enable request status/URL logging in the test environment and inspect the mismatch from MockRestServiceServer; determine whether the bug is in URI/template, method, headers, body converter, or status mapping. Never change expected URLs just to turn tests green if the provider contract still requires the original URL.

## 6. Clarifying HTTP contracts across multiple services and versions

When an app calls Inventory Service v1 and Pricing Service v2, each proxy needs its own baseUrl, credentials, timeouts, and error policy. Tests should not merely build standalone interfaces—retrieve the **production-configured beans** from the Spring context and verify they route properly.

Example matrix:

| Check | Inventory Client | Pricing Client |
| --- | --- | --- |
| Base URL | inventory.example.test | pricing.example.test |
| HTTP path | /v1/stock/A-1 | /v2/prices/A-1 |
| Authentication | Audience inventory | Audience pricing |
| Response | Stock DTO | Price DTO |
| Error | OUT_OF_STOCK/404 per contract | PRICE_UNAVAILABLE/503 per contract |
| Schema evolution | Field available or quantity | amountMinorUnits + currency |
| Negative security test | Rejects pricing token | Rejects inventory token |

Do not merge both into one mock server when the goal is proving **host and token isolation**: use two separate mock servers or two distinct local mock HTTP ports. Ensure factories are built from the real production `RestClient.Builder` or equivalent configuration; testing an interface on a different builder than production can miss baseUrl misconfigurations.

### 6.1. Provider contracts, not only consumer-stubbed expectations

Mock HTTP tests confirm “the client sends what the consumer thinks the API expects.” They do not guarantee the real service returns that JSON. Contracts should be agreed, versioned, and verified on the provider via:
- OpenAPI/schemas + provider contract tests, or consumer-driven contracts (Pact, Spring Cloud Contract where suited to the stack).
- JSON fixture sets: required fields, new fields, missing/null values, numeric boundaries, timezone/currency, status codes, and error bodies.
- Provider verification in CI against all still-active consumer versions.
- Pre-deployment compatibility checks: new providers must satisfy published contracts or expose a new API version.
- Integration tests against provider sandboxes/staging to catch risks beyond schema contracts such as auth, redirects, certificates, and rate limits.

Adding an optional response field is usually compatible when consumers ignore unknown fields; **renaming/removing a required field or changing currency units** can be a breaking change even when JSON still parses. Clients can selectively use `@JsonIgnoreProperties(ignoreUnknown = true)`, while still validating required semantics.

### 6.2. Retries and side effects

Tests for HTTP proxies with retries must verify **actual request counts** and `maxRetries` policies. Raising retries without idempotency on order/payment-creating POSTs can duplicate side effects. Test by scenario:
- GET 503 → 200 up to the max attempt count; 400 errors do not retry.
- POST response lost after server commit: retry only when the server supports deduplication with the same Idempotency-Key.
- Do not generate a fresh key on each resubscription/retry attempt.
- Once retries are exhausted, return the final or contract-defined domain error rather than faking success.
- End-to-end retry timeouts must fit the caller's SLA so CI never hangs indefinitely.

With MockRestServiceServer you can declare expected requests in order, but to verify dropped connections, read timeouts/TLS, and transport-level retries, use a socket-based mock web server instead of a mock request factory.

## 7. Designing STOMP contracts compatible across versions

A STOMP contract encompasses:
- **Endpoint URL:** e.g., `/events` to open transport; changing paths breaks handshakes.
- **Application destinations:** `SEND /app/echo`; changing prefixes or method mappings breaks routing.
- **Subscribe destinations:** `SUBSCRIBE /topic/echo`; changing topics stops subscribers from receiving MESSAGE frames.
- **Payload schema:** field names, types, nullability, defaults, enums, and timestamp/monetary semantics.
- **Error semantics:** STOMP ERROR frames, application-level error messages, or agreed protocol close codes.
- **Security:** WebSocket origin, STOMP CONNECT token/CSRF, per-destination SEND/SUBSCRIBE permissions; not just HTTP handshake auth.
- **Delivery:** how many times does a client receive messages? Does the broker buffer while offline? Are ACK/redelivery or sequence-ID replays used?
- **Reconnect/resubscribe:** users/clients can drop connections; new session IDs and subscriptions must be restored.

Changes such as renaming `/topic/echo` to `/topic/messages` break clients subscribed to the old topic. Adding optional JSON fields can stay compatible when client decoders tolerate them. Changing String `text` into a complex object is a contract change worth testing on both producer and consumer.

**Spring's simple broker** fits single-JVM demos/tests; subscriptions live in the node's memory. Running multiple instances may require a broker relay/external STOMP broker and SockJS session affinity, yet passing single-node tests does not prove clustering works. Never claim STOMP provides exactly-once delivery; that requires dedicated application/protocol logic.

## 8. What should socket tests cover beyond the happy path?

| Scenario | Suitable test approach | What is verified |
| --- | --- | --- |
| Wrong WebSocket endpoint | WebSocketStompClient to non-existent URI | Handshake fails within bounded time |
| Disallowed Origin | Test handshake with real Origin header | Request blocked by allowed-origin policy |
| CONNECT without auth/CSRF when Security enabled | Connect with missing/extra STOMP headers | Rejected promptly, preventing unauthorized subscribe |
| Wrong SUBSCRIBE destination | Subscribe to non-existent/unauthorized topic | Receives no messages or rejected per contract |
| Malformed JSON SEND | Client sends invalid raw payload or wrong content-type | Error behavior/conversion observed |
| Valid SEND | Subscription then SEND, wait for MESSAGE | End-to-end mapping/JSON/broker |
| Multiple subscribers | Two sessions SUBSCRIBE to topic | Broadcast reaches authorized subscribers properly |
| Unsubscribe | UNSUBSCRIBE, then SEND | Unsubscribed session receives nothing further |
| Heartbeat/idle timeout | Test with shortened scheduler/timeouts | Disconnect/reconnect matches policy |
| Reconnect | Close socket then open new session | Re-CONNECT, re-SUBSCRIBE, clear missing-message policy |
| SockJS HTTP fallback | SockJsClient/Browser forcing xhr-polling | HTTP transports work, not only 101 Upgrade |
| LB + two nodes | Integration through a real load balancer | Sticky sessions/broker relay/routing |
| Broker unavailable | Stop broker relay in staging test | App/client reports errors and recovers cleanly |

**Layer separation:** server-side tests can use `ChannelInterceptor` or `TestChannelInterceptor` to observe messages sent/received on Spring channels without opening a WebSocket. This is fast for verifying `@MessageMapping` and conversion, yet requires wiring `clientInboundChannel`/`clientOutboundChannel` properly and handling async executors; it does not replace handshake tests. When using `@SendToUser`, tests must include a session/principal and user-destination routing rather than merely checking message content.

### SockJS behind a proxy

A native WebSocket STOMP test **does not** test SockJS fallback. When an endpoint uses `registry.addEndpoint("/events").withSockJS()`, SockJS clients typically hit HTTP base URL `http://host/events`, call `/events/info`, and then pick WebSocket or XHR transports. Proxies must permit GET/POST/OPTIONS appropriately, forward session paths, and handle buffering/timeouts and CORS/CSRF.

In production-like verification, add browser tests or transport-restricted SockJsClient tests:
- WebSocket transport: observe 101 handshake, CONNECT/SUBSCRIBE/SEND/MESSAGE.
- XHR polling: no 101; uses `/info`, `/xhr`, `/xhr_send`; still receives MESSAGE.
- XHR streaming: verify data reaches the client before proxies buffer it.
- With multiple backends: the same SockJS session must route consistently, and clients must resubscribe after reconnecting.

Never apply `"Access-Control-Allow-Origin: *"` with credentialed requests or disable all CSRF just to pass tests. When Spring Security is present, test STOMP CONNECT CSRF, Origin, session cookies, and destination permissions in a production-like environment.

## 9. Reducing flaky tests and proving negative paths

Network and messaging tests are inherently asynchronous; **never use sleep as the primary synchronization mechanism**. Use `CompletableFuture`, `BlockingQueue.poll(timeout)`, `CountDownLatch.await(timeout)`, or STOMP RECEIPT and proper instrumentation. Every wait must have a finite timeout; ensure tests close sessions, schedulers, and sockets.

When testing “did not receive MESSAGE” or “unauthorized user cannot SUBSCRIBE,” waiting briefly and seeing nothing is **not strong evidence** that the server blocked it. Observe explicit rejection signals: STOMP ERROR, close frames/authorization exceptions, broker receipts, or test-observable server logs/metrics. For notification streams, compare message counts and IDs to avoid picking up stale messages from prior tests.

Quality-improving practices:
1. Isolate tests: use distinct sessions/destinations or correlation IDs per test; avoid shared broker state across cached contexts.
2. Mock HTTP providers at the protocol boundary, not interfaces when testing proxy mappings.
3. For STOMP tests, subscribe after CONNECTED and await broker acknowledgement if supported; send only after a real synchronization point.
4. Assert both payloads **and** status/headers/destinations; `notNull` alone can miss contract breaks.
5. Verify exact HTTP attempt counts and STOMP message counts during retries/reconnects.
6. Keep `maxWait` reasonable for CI; diagnose transport/broker/serializers on timeouts instead of raising timeouts endlessly.
7. Use dynamic ports (`RANDOM_PORT`) and close clients; avoid hard-coded ports or thread leaks across suites.
8. Test sensitive flows only with harmless dummy data; never log or assert real tokens or sensitive business data.
9. When testing HTTPS/WSS through edge proxies, verify certificates, forwarded headers, Origin, query/path rewriting, and no mixed content.
10. Ensure tests only hit mock/local servers or approved sandboxes, never accidentally running mutating calls against production.

## 10. Combined HTTP + STOMP test matrix

A feature like “place an order and receive status updates” combines an HTTP POST to create the order with a STOMP topic broadcasting updates. Separate the contracts:

| Case | HTTP Service Client | STOMP |
| --- | --- | --- |
| Happy path | POST sends right body/status/ID | After subscribing, receives event matching order ID |
| Invalid input | 400/422 ProblemDetail per contract | Invalid SEND payload handled per policy |
| Missing resource | Accurate 404 JSON/ProblemDetail | Topic/destination or “not found” event per contract |
| Unauthorized | HTTP 401/403, no order created | Unauthorized CONNECT/SUBSCRIBE/SEND blocked |
| Retry | Bounded; POST uses idempotency key if server supports it | Reconnect must not recreate the order |
| New schema | New optional fields do not break old DTOs | Event versioning, unknown fields, enum values |
| Network interruption | Timeout then query operation state | Reconnect + resubscribe + reconcile missing events |
| Duplicate data | Server deduplicates by operation key | Consumer deduplicates by eventId if required by contract |
| Scale out | Accurate host/auth/timeout config | Broker relay/affinity/sessions and multi-node broadcast |

A passing “green unit test” on a facade is insufficient to prove this system. Beyond the two separate contract test suites, add a few **end-to-end business scenarios**: the same order ID returned by HTTP appears in the event, status updates do not arrive before expected conditions, and duplicates/replays obey the idempotency contract.

## 11. Common mistakes

- **Mocking an @HttpExchange interface and concluding URLs are right:** bypasses the proxy; add MockRestServiceServer or a socket-based mock HTTP server.
- **Binding MockRestServiceServer after building RestClient:** RestClient keeps the old request factory and mocks miss requests; bind before building.
- **Asserting only HTTP status:** requests may carry wrong paths/headers/bodies while stubs still return data; check outbound requests against the contract.
- **Using WebClient yet forgetting to subscribe:** the publisher never runs and no HTTP call occurs; use StepVerifier and a mock server.
- **Not testing custom status handlers:** 404/409/429 get mapped into unexpected fallbacks or wrong exceptions.
- **Testing @MessageMapping solely via direct Java calls:** skips STOMP frames, converters, and broker/destination routing.
- **Treating WebSocket 101 as STOMP CONNECTED:** handshake success can still be rejected at STOMP CONNECT.
- **Sending immediately after SUBSCRIBE and adding sleep when flaky:** leaves the race unresolved; use RECEIPT/real synchronization points.
- **Forgetting a task scheduler for STOMP receipts:** receipt callbacks and timeout tracking fail to operate as intended.
- **Switching native WebSocket to SockJS while keeping ws:// URLs:** SockJS expects HTTP base URLs; test clients with the right protocol.
- **Ignoring Origin/CSRF/auth:** localhost tests without security do not represent production.
- **Relying on the simple broker when scaling clusters:** single-node tests do not prove cross-node fan-out.
- **Assuming reconnect replays missed messages:** new STOMP sessions have no history; design replay explicitly.
- **Catching timeouts without closing sessions:** leaks sockets/threads and causes random failures in later CI tests.
- **Changing test expectations to stay green when a real provider introduced a breaking change:** version contracts, alert teams, and coordinate rollout/rollback.

## 12. Checklist when adding a new endpoint

**HTTP Service Client**
- Interface and proxy specify accurate method, base URL, URI template, query/header/body, and Accept/Content-Type.
- Clear contract for 2xx statuses, 4xx/5xx errors, media types, and DTO nullable/required fields.
- Mock HTTP tests protect request and JSON; integration/contract verification targets real providers or sandboxes when needed.
- Matching negative auth/rate-limit/timeout and retry/idempotency tests are included.
- When adding an API version, test old/new consumers side by side and verify rollback safety.

**WebSocket/STOMP**
- Handshake URL, CONNECT headers, SEND/SUBSCRIBE destinations, and payload versions are clearly documented.
- Real STOMP client test verifies `MESSAGE` after subscription, not just opening a socket.
- Tests cover ERROR/authorization, reconnect/resubscribe, and duplicate/delivery policies where applicable.
- SockJS fallback, CORS/CSRF/cookies, and proxy/LB behavior are tested in environments that include them.
- Timeouts/receipts/lifecycles are bounded; resources are released after tests.

## 13. Conclusion

Both HTTP Service Clients and WebSocket/STOMP carry **hidden contracts behind interfaces and annotations**: HTTP requires accurate requests and responses; STOMP requires proper connections, destinations, frames, and delivery. Protecting contracts requires placing assertions at protocol boundaries and adding provider verification; mocking Java methods cannot replace that.

For HTTP, use `MockRestServiceServer` for fast `RestClient` proxy tests, socket-based mock HTTP servers for transport, and provider contracts for compatibility. For WebSocket/STOMP, combine Spring messaging infrastructure tests with `WebSocketStompClient` integration tests verifying CONNECT → SUBSCRIBE → SEND → MESSAGE. When production includes authentication, SockJS, reverse proxies, broker relays, or multiple nodes, test those layers separately matching production topology.
