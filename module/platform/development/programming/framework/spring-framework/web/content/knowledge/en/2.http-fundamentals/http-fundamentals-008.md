# Distinguishing REST, HTML Pages, HTTP Streaming, and WebSocket

## 1. Four Concepts Operating at Different Layers

Within a single Spring application, the same server can return JSON to mobile apps, serve HTML pages to browsers, stream continuous events over HTTP, and open WebSocket connections. These are **not four directly competing frameworks**:

- **REST** is an *architectural style* for resource-oriented APIs: identifying resources by URI, operating through HTTP semantics, exchanging representations, stateless communication, and other REST constraints. JSON is common, yet **not mandatory**. An API returning JSON is not necessarily fully RESTful.
- **An HTML page** is a *document/UI representation* received and rendered by a browser. Pages can be generated on the server (server-side rendering), served as static files, or use JavaScript to fetch data and update the UI.
- **HTTP streaming** is a *way of delivering a response incrementally over time*: the server sends chunks within a single HTTP response as data becomes available. **Server-Sent Events (SSE)** and **NDJSON** are two common ways to structure streaming data.
- **WebSocket** is a *bidirectional, persistent communication protocol* established after a handshake. Client and server can proactively push messages to each other; traffic is no longer discrete per-request HTTP responses.

Two questions help distinguish them: **(1) What is the API/document representing?** and **(2) How does data flow over the connection?** A REST endpoint can perfectly well serve an HTML representation or a stream; an HTML app can call REST APIs and open a WebSocket. Thus, these concepts **can be combined**.

## 2. Quick Comparison by Observable Behavior

| Characteristic | Typical REST API | HTML Page | HTTP Streaming (SSE/NDJSON) | WebSocket |
| --- | --- | --- | --- | --- |
| Nature | API/resource architecture | Document/UI format | Progressively emitted HTTP response | Full-duplex message exchange protocol |
| How it opens | HTTP request (GET/POST/PUT/DELETE...) | Usually HTTP GET | Usually HTTP GET for streams; varies by use case | HTTP handshake; usually HTTP/1.1 Upgrade or equivalent setup on HTTP/2 |
| After opening | One response per request | One HTML response, fetching extra CSS/JS/APIs if needed | One long-lived HTTP response, multiple chunks/events | Connection stays open; many messages in both directions |
| Typical data flow | Client requests → server replies | Server sends HTML to browser | Usually server → client within response; client can send separate requests | Client ↔ server proactively |
| Payload format | JSON, XML, HTML, binary... | `text/html` | `text/event-stream` (SSE), `application/x-ndjson`, or bytes | Text/binary WebSocket frames; schema defined by application |
| Browser client | `fetch()` | Navigation/browser renderer | `EventSource` (SSE), `fetch()` streams | `WebSocket` API |
| HTTP status & caching | Yes, per endpoint semantics | Yes, supports document/asset caching | Status/headers at start; streams usually not cached like finite documents | HTTP status covers handshake; subsequent messages carry no per-message HTTP status |
| Typical use cases | CRUD, resource APIs, business actions | Landing pages, dashboards, forms | Progress updates, logs, tickers, live feeds | Chat, games, collaborative editing, real-time bidirectional interaction |

**Note:** "REST" does not mean "GET + JSON", "streaming" does not mean "WebSocket", and "WebSocket" does not mean every HTTP request in the app should be replaced.

## 3. Timeline Diagrams: Differences in Connection Lifecycle

### A. REST API: finite request and response

~~~text
Browser / Mobile            Server
    |  GET /api/items/7        |
    |------------------------->|
    |  200 application/json    |
    |<-------------------------|
    |  {"id":7,"name":"Keyboard"} |
    |  response completed      |
~~~

A subsequent request may reuse the TCP connection via HTTP keep-alive, yet it remains a **new HTTP request/response**. Do not equate TCP connection reuse with a still-streaming HTTP response.

### B. HTML page: browser renders a document

~~~text
Browser                       Server
    | GET /page                   |
    |---------------------------->|
    | 200 text/html               |
    |<----------------------------|
    | parse HTML, render DOM      |
    | load CSS / JS / images if any |
    | JS may call REST or WS      |
~~~

HTML can be static or generated by a template engine. In modern applications, a single HTML load can trigger dozens of asset/API requests; that is still normal HTTP behavior.

### C. HTTP streaming: one response with multiple incremental parts

~~~text
Client                        Server
    | GET /events                |
    |--------------------------->|
    | 200 text/event-stream      |
    |<---------------------------|
    | event #1                  <|
    | event #2 (after a moment) <|
    | event #3 (after a moment) <|
    | response ends/closes       |
~~~

The server sends headers upfront, then continues flushing the body as data arrives. Streaming data can produce one or multiple transport chunks; **network chunk boundaries are not automatically application message boundaries**.

### D. WebSocket: a bidirectional message-exchange session

~~~text
Browser / App                Server
    | request handshake         |
    |--------------------------->|
    | handshake succeeds         |
    |<---------------------------|
    |--- "hello" -------------->|
    |<------------ "welcome" ---|
    |<--------------- "update" -|
    |--- "ack" ---------------->|
    |        ...                |
    | close / connection drops   |
~~~

After the handshake, WebSocket messages **are not separate JSON HTTP responses**. To model business operations such as "join room", "send message", "ACK", or "error notification", the application must define a message schema or adopt a suitable subprotocol.

## 4. REST: Understanding Resources, Methods, and Representations

REST emphasizes resources with stable URIs and operations conforming to HTTP contracts. Examples:

| Request | Example Meaning | Illustrative Response |
| --- | --- | --- |
| `GET /api/orders/42` | Retrieve representation of order 42 | `200 OK` + JSON |
| `POST /api/orders` | Request creating an order per API convention | `201 Created` + `Location` when created |
| `PUT /api/orders/42` | Replace resource state per contract representation | `200 OK` or `204 No Content` |
| `PATCH /api/orders/42` | Apply partial update per patch document/contract | `200 OK` or `204 No Content` |
| `DELETE /api/orders/42` | Request deleting the resource | `204 No Content` commonly used |

Semantics to remember:

- `GET` is **safe** in that it intends no client-requested state changes; `GET` is also idempotent. Server-side logs and metrics can still be recorded.
- `PUT` and `DELETE` carry **idempotent** semantics: repeating the same intended request must have the same desired effect as once, though **each response/status is not required to be identical**.
- `POST` is not idempotent by default. Order/payment creation transactions may need an application-designed **idempotency key** for safe retries.
- `PATCH` is not inherently idempotent; this depends on patch semantics.
- **Stateless** in REST means each request carries sufficient context for the server to process it, without relying on application session state stored server-side to interpret the request. This does not forbid persisting data in a database.
- `Accept` expresses the representation type the client wants; `Content-Type` indicates the payload type being sent. `Accept: application/json` and response `Content-Type: application/json` are examples, not the definition of REST.

JSON representation example:

~~~http
GET /api/orders/42 HTTP/1.1
Host: localhost:8080
Accept: application/json
~~~

~~~http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":42,"status":"PAID"}
~~~

REST does not mandate JSON or "one URI returns only one format". A resource can have multiple representations; HTML can also be a representation of a resource.

## 5. HTML: When the Server Returns a Document for Browsers

An endpoint returning HTML:

~~~http
GET /page HTTP/1.1
Host: localhost:8080
Accept: text/html
~~~

~~~http
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8

<!doctype html>
<html lang="en">
  <head><meta charset="UTF-8"><title>Sample Page</title></head>
  <body><h1>Welcome</h1></body>
</html>
~~~

Three common approaches:

1. **Static HTML:** the server delivers `.html` files and assets; suitable for static pages, documentation, or SPA entry points.
2. **Server-side rendered HTML (SSR):** controllers pass a model to a template engine like Thymeleaf; the server renders HTML and returns it to the browser. Suited to content needing complete HTML on initial load, traditional forms, and SEO where relevant.
3. **Client-rendered UI (SPA):** the server returns an HTML shell; application JavaScript uses `fetch()` to retrieve REST/HTTP API data and render the UI.

In Spring MVC, a `@Controller` method returning a view name such as `"product-detail"` can be resolved by a template resolver; `@RestController` or `@ResponseBody` methods normally return the **body** directly. Returning raw HTML strings from `@RestController` is only for demos; real applications should use proper views/templates or static resources and escape user-supplied content.

**HTML is not a rival to REST:** the same website can serve HTML at `/products` and JSON at `/api/products`. Using CSS/JS or loading data asynchronously does not turn an HTML page into a WebSocket.

## 6. HTTP Streaming: Emitting Data Gradually in One Response

In a typical HTTP response, the server knows the finite payload upfront and the client processes it after receiving the full body or reads it as it arrives. With streaming, the server intentionally keeps the response open over time and sends new content in waves.

Common forms:

- **Streaming bytes/files:** large file downloads, proxied streams, video/file chunks; the client reads bytes progressively, possibly without message-level framing.
- **SSE:** standard text format `text/event-stream`, each event carrying fields like `data:`, `event:`, `id:`; browsers offer the convenient `EventSource` API.
- **NDJSON (Newline-Delimited JSON):** each line is an independent JSON value, e.g., telemetry/logs/items; clients split by line separator to parse each record.
- **Long polling:** the client holds a request waiting for an event, the response completes, and the client opens a new request. This differs from a multi-event response stream and from WebSocket.

With **HTTP/1.1**, a streaming response without a known `Content-Length` may use `Transfer-Encoding: chunked` depending on the server and case. With **HTTP/2**, data travels in DATA frames, **not HTTP/1.1 chunked transfer encoding**. Clients must never treat TCP/HTTP frame boundaries as business message boundaries.

### 6.1 SSE: server-pushed events to browsers

Key response headers:

~~~http
Content-Type: text/event-stream
Cache-Control: no-cache
~~~

An SSE body might look like:

~~~text
id: 101
event: status
data: {"orderId":42,"state":"PACKING"}

id: 102
event: status
data: {"orderId":42,"state":"SHIPPING"}

~~~

A **blank line** terminates an event. `data:` can appear multiple times within one event and is concatenated per SSE rules. `id:` lets the browser record the last event ID; when reconnecting, the client can send `Last-Event-ID` so the server knows the last marker, **but replaying missed events is the application/server's responsibility**, not automatic just from using SSE.

Browser client:

~~~javascript
const source = new EventSource("/events");
source.addEventListener("status", (event) => {
  console.log(event.lastEventId, JSON.parse(event.data));
});
source.onerror = () => console.log("SSE disconnected or error");
~~~

`EventSource` typically uses GET and reconnects automatically when needed; applications should provide a way to close it via `source.close()`. Native `EventSource` does not support arbitrary custom request headers like `fetch()`; when auth is required, design cookies/credentials or another suitable streaming client while accounting for CORS.

**Choose SSE when:** clients need to receive order status updates, dashboards, job progress, monitoring, or live feeds; client-initiated commands still use separate HTTP POST/PUT requests. If continuous two-way messaging is needed, consider WebSocket.

### 6.2 NDJSON: multiple JSON documents in one HTTP response

Example body with three independent lines:

~~~ndjson
{"id":1,"name":"Pen"}
{"id":2,"name":"Notebook"}
{"id":3,"name":"Ruler"}
~~~

Common content type: `application/x-ndjson`. Clients **do not** parse the whole body as a JSON array; instead they read line by line, buffering byte fragments as needed and parsing each JSON object. In JavaScript, `fetch()` exposes `Response.body` as a `ReadableStream` in supporting browsers; when decoding UTF-8 streams with `TextDecoder`, handle characters and lines split across network chunks.

Distinction: SSE defines event syntax and has `EventSource` auto-reconnect; NDJSON is simply a one-JSON-per-line convention with no built-in `id`, replay, or auto-reconnect.

### 6.3 Operational limits of HTTP streaming

- **Status and headers are sent upfront.** Once the response is committed, you cannot normally change the status to `500` if the stream fails midway; you need an in-stream error signaling mechanism or to close the connection.
- **Proxies/CDNs/load balancers** may buffer, idle-timeout, or drop connections. Measure latency from server write to client receipt; test actual buffering and flushing behavior.
- **Slow consumers/backpressure:** slow-reading clients put pressure on buffers and memory; reactive backpressure helps in supporting publishers, yet does not automatically throttle all traffic or external upstreams.
- **Reconnects, retries, duplicates:** streams can break mid-flight. Reliability requires cursors/event IDs, replay stores, deduplication, and resume rules.
- **Timeouts/heartbeats:** long-lived connections may need keep-alive events or heartbeats and tuned timeouts. SSE supports comment lines starting with `:`.
- **Security:** streams still require authentication/authorization, connection limits, and scoping of data sent per subscriber.

## 7. WebSocket: Bidirectional Session for Independent Messages

WebSocket fits when **both server and client need to push data proactively with low latency**. Example chat: client sends `SEND_MESSAGE`, server replies `ACK`, and server pushes `NEW_MESSAGE` to multiple clients when new messages arrive. One connection can carry many messages without creating a new HTTP request per message.

Over HTTP/1.1, browsers typically initiate via a handshake with headers:

~~~http
GET /ws/echo HTTP/1.1
Host: localhost:8080
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: [client-generated value]
Sec-WebSocket-Version: 13
~~~

On success, the server responds with `101 Switching Protocols` and required WebSocket headers. Over HTTP/2, the standard also permits an alternate setup (extended CONNECT) when supported by client and server; do not assume every WebSocket uses the exact HTTP/1.1 handshake. With TLS, browsers use `wss://` instead of `ws://`; on HTTPS pages, use WSS.

**After the handshake:**

- Transport consists of WebSocket frames/messages (text or binary), not per-message JSON HTTP responses with status codes and headers.
- WebSocket **does not prescribe** whether business messages are JSON, protobuf, topic names, or event structures; that is an application contract.
- **STOMP over WebSocket** is an optional subprotocol/messaging layer when applications need destinations and subscriptions; STOMP is not required for WebSocket.
- WebSocket provides protocol-level ping/pong, yet application-level heartbeats, timeouts, and reconnect strategies still need evaluation.
- WebSocket **does not automatically guarantee** message persistence, exactly-once delivery, replay after reconnect, or cross-instance distribution.

### When does WebSocket shine?

- Two-way chat, presence, and typing indicators.
- Collaborative editing with frequent client ↔ server edits.
- Multiplayer games / interactive controls or dense command-and-push streams.
- Bidirectional telemetry needing a continuous message channel.

If clients only need a one-way event stream, SSE can be simpler. For infrequent updates without real-time demands, periodic polling or REST APIs may suffice.

### What must be designed for production

- Authenticate on connect and authorize **every message type/destination**; never treat an established connection as full permission.
- Validate `Origin` for browsers, cookie/session policies, CSRF where applicable, and never trust client payloads.
- Enforce limits on message size, rate, connection count, outbound queues, and idle time.
- Detect disconnects, reconnect with backoff, and resynchronize state/cursors after reconnecting.
- Across multiple instances, design how to broadcast to the right subscribers (broker/pub-sub/shared state) and configure WebSocket-aware load balancers; sticky sessions alone do not replace a message distribution system.
- Monitor active connections, send queues, ping/pong, handshake failures, event-loop latency, and downstream saturation.

## 8. What Options Do Spring MVC and Spring WebFlux Provide?

| Need | Spring MVC / Servlet stack | Spring WebFlux / reactive stack |
| --- | --- | --- |
| JSON REST API | `@RestController` + `@GetMapping`, `ResponseEntity` | Similar `@RestController`, can return `Mono<T>` / `Flux<T>` |
| HTML pages | `@Controller` + view resolver/Thymeleaf, static resources | Supports view rendering/static resources and annotated or functional endpoints |
| SSE | `SseEmitter`, `ResponseBodyEmitter`, Servlet async handling | `Flux<ServerSentEvent<T>>` or `Flux<T>` with `text/event-stream` |
| Raw/file streaming | `StreamingResponseBody`, async support where applicable | `Flux<DataBuffer>` and reactive codecs |
| NDJSON stream | Possible via emitters/custom streaming | `Flux<T>` with `application/x-ndjson` |
| WebSocket | Spring WebSocket Servlet API, `WebSocketHandler`, optional STOMP broker | Reactive `org.springframework.web.reactive.socket.WebSocketHandler` |
| Evaluation point | Sync/JPA libraries, Servlet async/virtual threads when suitable | End-to-end non-blocking downstream chain, Reactor semantics, and flow control |

Do not choose WebFlux **solely** because you want SSE or WebSocket. Spring MVC also supports streaming and WebSocket. Choosing between MVC and WebFlux is an architectural decision about execution models and the I/O chain beyond the scope of this lesson.

## 9. Runnable Example: One WebFlux App with All Four Exchange Styles

This example uses **Java 17+**, **Spring Boot 3.3.x / Spring Framework 6.1+**, as a standalone app providing:

- `GET /api/items/7` → a standard JSON response;
- `GET /page` → an HTML document;
- `GET /events` → three SSE events emitted over time;
- `GET /stream/items` → three NDJSON records emitted over time;
- `/ws/echo` → an echo WebSocket endpoint where clients can send messages.

WebFlux is chosen **to demonstrate all response styles in one unified example**; it does not imply MVC cannot handle these styles.

### 9.1 Gradle configuration

Create a new project directory with `settings.gradle`:

~~~groovy
rootProject.name = 'protocol-demo'
~~~

Create `build.gradle`:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.5'
    id 'io.spring.dependency-management' version '1.1.6'
}

group = 'example'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-webflux'
}
~~~

Requires JDK 17+ and a Gradle version compatible with the Spring Boot version used (e.g., Gradle 8.x). If you have a Gradle Wrapper, use the wrapper; otherwise you need Gradle installed to run `gradle bootRun` or generate the wrapper.

### 9.2 Java source

Create `src/main/java/example/protocols/ProtocolDemoApplication.java`:

~~~java
package example.protocols;

import java.time.Duration;
import java.util.Map;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;
import org.springframework.http.MediaType;
import org.springframework.http.codec.ServerSentEvent;
import org.springframework.stereotype.Component;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.reactive.HandlerMapping;
import org.springframework.web.reactive.handler.SimpleUrlHandlerMapping;
import org.springframework.web.reactive.socket.WebSocketHandler;
import org.springframework.web.reactive.socket.WebSocketSession;

import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@SpringBootApplication
public class ProtocolDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(ProtocolDemoApplication.class, args);
    }

    public record Item(long id, String name) {}

    @RestController
    static class HttpController {

        @GetMapping(value = "/api/items/{id}",
                    produces = MediaType.APPLICATION_JSON_VALUE)
        public Item item(@PathVariable long id) {
            return new Item(id, "Keyboard");
        }

        @GetMapping(value = "/page",
                    produces = MediaType.TEXT_HTML_VALUE)
        public String page() {
            return "<!doctype html><html lang=\"en\">"
                    + "<head><meta charset=\"UTF-8\">"
                    + "<title>HTML demo</title></head>"
                    + "<body><h1>HTML Page from Spring</h1></body></html>";
        }

        @GetMapping(value = "/events",
                    produces = MediaType.TEXT_EVENT_STREAM_VALUE)
        public Flux<ServerSentEvent<String>> events() {
            return Flux.interval(Duration.ZERO, Duration.ofSeconds(1))
                    .take(3)
                    .map(index -> ServerSentEvent.<String>builder()
                            .id(Long.toString(index))
                            .event("tick")
                            .data("Notification " + index)
                            .build());
        }

        @GetMapping(value = "/stream/items",
                    produces = MediaType.APPLICATION_NDJSON_VALUE)
        public Flux<Item> ndjson() {
            return Flux.interval(Duration.ZERO, Duration.ofSeconds(1))
                    .take(3)
                    .map(index -> new Item(index + 1,
                            "Item " + (index + 1)));
        }
    }

    @Component
    static class EchoSocket implements WebSocketHandler {

        @Override
        public Mono<Void> handle(WebSocketSession session) {
            return session.send(session.receive()
                    .map(message -> session.textMessage(
                            "echo: " + message.getPayloadAsText())));
        }
    }

    @Bean
    public HandlerMapping socketMapping(EchoSocket echoSocket) {
        Map<String, WebSocketHandler> endpoints =
                Map.of("/ws/echo", echoSocket);
        return new SimpleUrlHandlerMapping(endpoints, -1);
    }
}
~~~

In a standard Boot-configured Spring Boot WebFlux app, the WebSocket handler adapter is set up by the framework. `SimpleUrlHandlerMapping` registers `/ws/echo` with order `-1` so handshake requests route to the WebSocket handler. When the client closes the connection, the receive stream completes and the session is released. This is a plain text echo demo, not a full chat protocol.

### 9.3 Running and verifying HTTP behavior

From the project directory, run:

~~~bash
./gradlew bootRun
~~~

On Windows:

~~~powershell
.\gradlew.bat bootRun
~~~

Without a wrapper, use `gradle bootRun` with a compatible installed Gradle. Once the server runs on default port 8080:

**A. JSON REST-style GET**

~~~bash
curl -i http://localhost:8080/api/items/7
~~~

Expected status: `200 OK`; `Content-Type` is `application/json`. Body:

~~~json
{"id":7,"name":"Keyboard"}
~~~

**B. HTML document**

~~~bash
curl -i http://localhost:8080/page
~~~

Expected status: `200 OK`; `Content-Type` is `text/html`. The body contains `<h1>HTML Page from Spring</h1>`, which browsers render as a page heading.

**C. SSE streaming**

~~~bash
curl -N -H "Accept: text/event-stream" http://localhost:8080/events
~~~

As the connection emits events on the example's schedule, the body contains three events equivalent in content:

~~~text
id:0
event:tick
data:Notification 0

id:1
event:tick
data:Notification 1

id:2
event:tick
data:Notification 2

~~~

Whitespace after colons depends on valid SSE serialization; **do not rely on exact spacing**. `-N` disables curl stdout buffering; events arrive roughly one second apart, while actual timing depends on the scheduler and load.

**D. NDJSON streaming**

~~~bash
curl -N -H "Accept: application/x-ndjson" http://localhost:8080/stream/items
~~~

Expected body lines, each an independent JSON object:

~~~ndjson
{"id":1,"name":"Item 1"}
{"id":2,"name":"Item 2"}
{"id":3,"name":"Item 3"}
~~~

Lines arrive progressively over time; there are no outer `[ ]` brackets wrapping all lines like a JSON array.

**E. WebSocket client from browser DevTools**

Open a page in the browser and run:

~~~javascript
const ws = new WebSocket("ws://localhost:8080/ws/echo");
ws.onopen = () => ws.send("hello");
ws.onmessage = (event) => console.log(event.data);
ws.onerror = (event) => console.error("WebSocket error", event);
ws.onclose = (event) => console.log("closed", event.code);
~~~

Expected console output upon a successful connection:

~~~text
echo: hello
~~~

To close the connection once testing is complete, call `ws.close()`. If the page is served over HTTPS, the WebSocket URL must use `wss://` in an environment deployed with proper TLS.

**F. SSE client from browser**

If opened on the same origin as the demo app:

~~~javascript
const es = new EventSource("/events");
let received = 0;

es.addEventListener("tick", (event) => {
  console.log("SSE", event.lastEventId, event.data);
  received++;
  if (received === 3) es.close();
});
~~~

The example closes after three events because `EventSource` may automatically reconnect when a stream closes; `Flux.take(3)` on the server only ends **one connection's** response and does not disable client-side reconnection.

### 9.4 What makes this example work?

- `@RestController` and `produces` distinguish content types for JSON, HTML, SSE, and NDJSON.
- `Flux.interval(...).take(3)` is a publisher simulating gradually produced data. In real apps, it can be replaced by event sources from application services.
- `ServerSentEvent<T>` produces SSE syntax with event names and IDs.
- `Flux<Item>` with `application/x-ndjson` encodes each item as a JSON line rather than bundling into one JSON array when preserving the streaming media type.
- `WebSocketHandler` consumes incoming messages and transforms them into outgoing messages on the same session.
- Having one application serve all five endpoints proves **the same web stack can implement multiple communication styles**.

**Demo limitations:** the program lacks authentication/authorization, rate limiting, persistence, resume cursors, or error/retry handling for distributed environments. In production, never expose an unbounded broadcaster or arbitrary echo to untrusted clients.

## 10. How to Choose for Real-World Scenarios

### Scenario 1 — Product / order management

Users click "Place Order" and view purchase history. Clients need clear request outcomes, proper HTTP status codes, and easy caching of GET data when allowed. **Use a resource/REST-style HTTP API**, returning JSON for apps or SSR HTML for traditional pages. There is no need for WebSocket to replace POST actions.

### Scenario 2 — Informational website / forms

Pages have complete content on initial load, templates render data, and forms submit via POST. **Serve HTML**; certain interactions can still call JSON APIs. WebSocket brings no benefit merely because a browser has the page open.

### Scenario 3 — Tracking a 2-minute file processing job

The client sends `POST /jobs` to create a job, receives `202 Accepted` and a `jobId`, then watches `GET /jobs/{id}/events` via SSE or polling. **SSE** makes sense when the server needs to push multiple one-way updates over a single open request; for simpler needs, periodic polling also works. Reconnect/replay mechanisms are needed if progress updates cannot be missed.

### Scenario 4 — Continuous log/telemetry dashboard

Sequential records arrive as JSON. **NDJSON streaming** fits clients capable of line-by-line parsing that want one-way machine-readable data; **SSE** fits if the target is a browser using `EventSource` and wanting convenient event IDs and reconnect semantics.

### Scenario 5 — Multi-user live chat

Clients simultaneously send messages and receive new messages and typing indicators. **WebSocket** fits because of frequent bidirectional messages over a persistent connection. You can still use REST APIs for login, history loading, file uploads, and room management, while WebSocket handles the real-time interaction channel.

### Scenario 6 — Prices updated once every 10 minutes

A GET API with caching/periodic refresh is usually far simpler than keeping streaming/WebSocket connections open. "Real-time" is a business requirement that should be quantified, not a goal for its own sake.

## 11. Key Differences in Design, Debugging, and Deployment

### 11.1 Latency and buffering

An application may call `flush()`, yet a reverse proxy still buffers the body. To test streams, use `curl -N`, inspect browser Network timings, and test through the actual production ingress/CDN. Separate business processing time from server write time and client receipt time. Streaming does not guarantee instant rendering if proxies or clients delay delivery.

### 11.2 Caching and CDNs

GET JSON/HTML can be cached via `Cache-Control` and `ETag`/`Last-Modified` when permitted by the contract. SSE and long-lived streams usually require disabling caching and proxy buffering. WebSocket does not use HTTP response caching per message. Avoid marking personal data with `Cache-Control: public`.

### 11.3 Backpressure, fan-out, and load

Multiple subscribers to the same broadcast read at different speeds; the server needs policies for buffering, dropping/coalescing, disconnecting slow clients, or bounding queues. WebFlux supports Reactive Streams, yet upstream sources or brokers do not necessarily propagate backpressure all the way to the origin. Measure memory, connection counts, queue lengths, and send rates.

### 11.4 Error semantics

Standard HTTP APIs express errors via HTTP status codes and error bodies. With SSE/NDJSON, if an error occurs after headers have been committed, you cannot change the status code as with an unstarted response; you need protocol-level error events/records or to close the stream so clients can resume. WebSocket requires defining error messages or close codes; you cannot expect HTTP 500 on individual frames.

### 11.5 Connection drops and message ordering

SSE supports last event IDs in browsers, yet the server must store history to replay it. NDJSON requires custom cursor/reconnect logic if needed. WebSocket preserves message order within **a single connection** at the protocol level, yet across reconnects, failovers, or multiple services, you must design ACKs, offsets, idempotency, and deduplication at the application layer.

### 11.6 Authentication and security

HTTP, SSE, and WebSocket all require data-appropriate authentication. `EventSource` has header limitations in browsers. For browser WebSockets, evaluate `Origin`, cookies, handshake auth, and **per-message authorization**. Use TLS (`https://`, `wss://`), validate payloads, enforce size/rate limits, and check permissions before publishing data to rooms or topics.

### 11.7 Observability and testing

- REST: status codes, response schemas, cache headers, idempotent retries, p95/p99 latency.
- HTML: accurate rendering, escaping/XSS, asset loading, SEO/SSR if required.
- SSE: multiple events arriving over time, reconnects, Last-Event-ID/replay, proxy idle timeouts.
- NDJSON: every line parses cleanly, chunks splitting mid-line or mid-UTF-8 character, stream cancellation, and slow consumers.
- WebSocket: handshake, message schema, ping/pong, reconnects, per-message auth, multi-client/multi-instance behavior, and close codes.

## 12. Common Misconceptions

| Misconception | Correction |
| --- | --- |
| “REST is JSON” | REST is an architectural style; JSON is only one representation format; a JSON API may not be RESTful |
| “HTML is backend, REST is frontend” | Both HTML and REST APIs can be served by the backend and consumed by browsers or mobile clients |
| “Streaming requires WebSocket” | HTTP streaming (SSE, NDJSON, files) works inside an HTTP response |
| “SSE is bidirectional like WebSocket” | An SSE stream is inherently server → client; to send commands, the client uses separate HTTP requests |
| “`Transfer-Encoding: chunked` is the SSE standard” | SSE is an event format; chunked is merely an HTTP/1.1 body transfer mechanism |
| “One TCP chunk corresponds to one JSON record” | The network can split or coalesce bytes arbitrarily; parse according to SSE/NDJSON framing |
| “WebSocket has built-in topics, rooms, ACKs, persistence” | WebSocket only provides message transport; the application or a subprotocol designs those features |
| “HTTP status codes apply to every WebSocket frame” | HTTP status applies to the handshake; subsequent messages need their own error schema |
| “Having `id` in SSE automatically replays everything” | The server must store and replay events by ID when the client reconnects |
| “You must switch to WebFlux to use WebSocket/SSE” | Spring MVC also supports SSE, WebSocket, and async HTTP |
| “Streaming means zero latency immediately” | Proxy buffering, schedulers, backpressure, and client read speed still affect latency |
| “Keeping a long-lived connection open is always better than polling” | Connections, memory, broker fan-out, and operations all carry costs; choose based on update frequency |

## 13. Applied Exercises

Choose the appropriate communication mechanism and explain why:

1. A frontend needs to fetch details of one product by ID; once loaded, it is done.
2. The server needs to render an article list page for browsers, complete with links and forms.
3. A browser needs to receive data-sync status every second for one minute, without sending interactive messages over the same channel.
4. A CLI needs to read thousands of growing JSON records, processing each line immediately.
5. Two users are editing the same document simultaneously and exchanging frequent changes back and forth.
6. A service updates product prices roughly once per hour.

**Suggested answers:** (1) HTTP GET REST-style/JSON. (2) HTML from the server (static or SSR). (3) SSE, or polling if requirements are simple. (4) NDJSON HTTP streaming. (5) WebSocket, plus a message schema and state synchronization. (6) GET with caching or scheduled polling; no need to hold long-lived connections.

## 14. Endpoint Design Checklist

- [ ] Clarify the goal: resource API, HTML document, one-way feed, or two-way interaction.
- [ ] Define HTTP method, URI, status codes, `Content-Type`, `Accept`, and cache policy.
- [ ] For REST APIs: understand safe/idempotent semantics, transactions, and retries.
- [ ] For HTML: decide server vs. client rendering, escape dynamic data, and manage assets.
- [ ] For SSE/NDJSON: define framing, stream bounds, timeouts, heartbeats, backpressure, and post-commit errors.
- [ ] For SSE: decide whether event IDs, replay, and browser-compatible auth are needed.
- [ ] For WebSocket: define message schemas, per-message auth, close/reconnect behavior, capacity, and multi-instance broadcasting.
- [ ] Verify streaming through a real proxy/load balancer; measure when clients actually receive data.
- [ ] Test slow-reading clients, mid-stream disconnects, and reconnects.
- [ ] Choose MVC vs. WebFlux only after evaluating the **entire I/O chain** and libraries in use.

**Practical conclusion:** REST organizes resource APIs; HTML delivers documents/UIs; HTTP streaming delivers incremental responses inside HTTP; WebSocket provides a long-lived bidirectional message channel. A healthy Spring system can combine all four across different business flows.
