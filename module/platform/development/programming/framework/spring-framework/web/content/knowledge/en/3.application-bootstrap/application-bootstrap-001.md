# Setting Up Dependencies and Minimal Spring Web Application Structure

## Objectives

After this lesson, you can build a small HTTP application using Spring Web MVC on your own, understand why each dependency is present, place classes into the proper package structure, and test an endpoint. You can also distinguish between two common initialization approaches:

1. **Plain Spring Framework Web MVC**: manually declare `spring-webmvc`, configure `DispatcherServlet`, and deploy onto a Servlet container.
2. **Spring Boot + Spring Web MVC**: use a starter and auto-configuration to get a standalone application with an embedded server. This is the runnable example approach in the main section.

Both approaches are based on the Spring MVC/Servlet stack. Spring Boot is a layer that assists with configuring and bootstrapping the application, **not an alternate name for Spring MVC**.

## 1. The Minimal Picture: Where Does an HTTP Request Go?

```text
HTTP client
    |
    | GET /api/hello?name=Ada
    v
Servlet container (embedded Tomcat or external container)
    |
    v
Spring MVC DispatcherServlet
    |
    +--> HandlerMapping finds a handler matching GET /api/hello
    +--> HandlerAdapter invokes the controller method
    +--> HttpMessageConverter writes the JSON/text body
    |
    v
HTTP response
```

The roles:

| Component | Responsibility in a Minimal Application |
|---|---|
| Java/JDK | Compiles and runs application code. |
| Gradle/Maven | Downloads dependencies, compiles, tests, and packages. |
| `spring-web` | Supports HTTP, request/response, and various web abstractions and utilities. |
| `spring-webmvc` | Adds Spring MVC, `DispatcherServlet`, handler mapping, and request processing on the Servlet stack; has a transitive dependency on `spring-web`. |
| Servlet container | Accepts HTTP connections/requests and runs Servlets; for example, Tomcat. |
| `@Controller` / `@RestController` | Endpoint handler class managed by Spring. |
| JSON library / converter | Converts Java data to JSON and back when an endpoint needs JSON. |
| Spring Boot starter/auto-configuration | Bundles compatible dependencies, configures common parts, and starts an embedded server. |

**Key distinction:** merely adding `spring-webmvc` to a Java project does not automatically start an HTTP server listening on port 8080. With plain Spring MVC, you still have to configure and deploy the Servlet; with the Spring Boot web starter, Boot creates and configures an embedded Servlet container by convention.

## 2. Prerequisites and Consistent Version Selection

The main example uses **Java 17**, **Gradle 8.5**, **Spring Boot 3.5.16**, and the Spring MVC version from Spring Framework 6.2.x managed by Boot. This is a combination supported by the system requirements documentation for the Boot 3.5 line: Java 17+, Gradle 8.4+ in the 8.x line. Do not mix Spring Boot 4.x with an older dependency/Gradle set without verifying the new version requirements.

Check tools:

```bash
java -version
javac -version
gradle -version
```

If the project already has a **Gradle Wrapper** (`gradlew` / `gradlew.bat`), use the wrapper instead of a globally installed Gradle. The wrapper locks the Gradle version so that different machines build the same project consistently. A JDK, not just a JRE, is required for compilation.

To create a new project, you can create the files presented below manually or use https://start.spring.io/ with:
- Project: Gradle - Groovy or Maven
- Language: Java
- Spring Boot: a release in the **3.5.x** line compatible with Java and the build tool
- Packaging: Jar
- Java: 17
- Dependency: **Spring Web**

This example explicitly specifies `3.5.16` to make the configuration reproducible; in a real project, update to a currently supported patch release in your chosen line and align the plugin/BOM according to the official documentation.

## 3. Directory Structure of a Minimal Gradle Application

```text
spring-web-minimal/
├── settings.gradle
├── build.gradle
├── gradlew                     # Gradle Wrapper on Unix/macOS
├── gradlew.bat                 # Gradle Wrapper on Windows
├── gradle/wrapper/
│   ├── gradle-wrapper.jar
│   └── gradle-wrapper.properties
└── src/
    ├── main/
    │   ├── java/
    │   │   └── com/example/webapp/
    │   │       ├── WebApplication.java
    │   │       └── controller/
    │   │           └── HelloController.java
    │   └── resources/
    │       └── application.properties
    └── test/
        └── java/
            └── com/example/webapp/
                └── HelloControllerTest.java
```

The `gradlew`, `gradlew.bat`, and `gradle/wrapper/*` files are generated by the Gradle Wrapper or Spring Initializr; you do not need to manually write the binary contents of `gradle-wrapper.jar`. For a minimal initial try, the test file can be added later. If creating manually and a suitable Gradle is installed on the machine, the command `gradle wrapper --gradle-version 8.5` will generate the wrapper; afterward, prefer invoking the wrapper.

Explanation:

- `settings.gradle` sets the project name.
- `build.gradle` describes plugins, repositories, dependencies, the Java toolchain, and build tasks.
- `src/main/java` holds the program source; Java package names match the directory structure.
- `src/main/resources` holds configuration placed on the classpath at runtime.
- `src/test/java` separates tests from production code.
- `WebApplication` is placed in the root package `com.example.webapp`; the controller goes under `com.example.webapp.controller` so that Boot's **default component scan** finds it.
- In a real project, add `service`, `repository`, and `config` packages **when corresponding responsibilities exist**; there is no need to create dummy classes just to fill out the diagram.

## 4. Declaring Dependencies with Gradle (Groovy DSL)

File `settings.gradle`:

```groovy
rootProject.name = 'spring-web-minimal'
```

File `build.gradle`:

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.5.16'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
```

**Why declare it this way?**

- `java` enables Java compilation and the standard source set structure.
- `org.springframework.boot` provides Boot tasks such as `bootRun` and `bootJar`, supporting executable JAR packaging.
- `io.spring.dependency-management` enables library version management via Spring Boot's dependency management; in this configuration, no separate version is written for the starters.
- `mavenCentral()` is the repository for downloading published libraries.
- `spring-boot-starter-web` pulls in Spring MVC, the components needed for servlet web development, Jackson for JSON, and embedded Tomcat by default in the 3.5 line.
- `spring-boot-starter-test` brings in commonly used testing libraries (JUnit Jupiter, Spring Test, assertion/mocking libraries depending on the starter).
- `useJUnitPlatform()` configures the `test` task to run the JUnit Platform test suite.
- The Java toolchain standardizes the compilation JDK; the machine needs the corresponding toolchain installed or an auto-download mechanism configured.

Do not simultaneously add an arbitrary `spring-webmvc` version when already using the starter: Spring Boot dependency management has already selected a compatible Spring Framework set. If you must override a dependency, check compatibility, because updating a single Spring module in isolation can cause binary conflicts.

### If Using Maven Instead of Gradle

The two build tools are **alternative options**; there is no need to place both `pom.xml` and `build.gradle` in the same example. The basic equivalent `pom.xml` file:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.16</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>spring-web-minimal</artifactId>
    <version>0.0.1-SNAPSHOT</version>

    <properties>
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

Maven gets dependency versions from the `spring-boot-starter-parent` parent; with a typical Maven project, run `./mvnw spring-boot:run`, or `mvn spring-boot:run` if Maven is already installed. Choose Gradle or Maven according to the project's build system; the Java-side Spring Web logic remains the same.

## 5. Application Entry-Point Class

File `src/main/java/com/example/webapp/WebApplication.java`:

```java
package com.example.webapp;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class WebApplication {
    public static void main(String[] args) {
        SpringApplication.run(WebApplication.class, args);
    }
}
```

This is a syntactically standalone Java class, yet it **must be built with Spring Boot dependencies** to compile. `SpringApplication.run` creates the Spring `ApplicationContext`, applies auto-configuration, discovers beans, and starts the embedded server based on the dependencies on the classpath.

`@SpringBootApplication` combines application configuration, auto-configuration, and component scanning roles. Because this class is in `com.example.webapp`, Spring by default discovers beans under that package, including `com.example.webapp.controller.HelloController`.

If you move the entry-point class down into `com.example.webapp.bootstrap` while the controller stays in a sibling package, default scanning may miss the controller. The simple approach is to keep the entry-point class in the common parent package.

## 6. Minimal HTTP Controller

File `src/main/java/com/example/webapp/controller/HelloController.java`:

```java
package com.example.webapp.controller;

import java.util.Map;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public Map<String, String> hello(
            @RequestParam(defaultValue = "friend") String name) {
        return Map.of("message", "Hello, " + name + "!");
    }
}
```

Explanation of execution flow:

1. `@RestController` marks a web controller bean; the return value is typically written to the HTTP response body via `HttpMessageConverter` rather than interpreted as a view name.
2. `@GetMapping("/api/hello")` maps HTTP GET to the path `/api/hello`. Without a controller bean, this mapping does not exist.
3. `@RequestParam` reads the `name` query parameter; when omitted, `defaultValue = "friend"` is used. If parameter names are not retained by the compiler, you must explicitly declare `@RequestParam(name = "name", defaultValue = "friend")` to avoid depending on parameter-name metadata. To keep the example robust across build configurations, use the explicit declaration shown below.
4. `Map<String, String>` is a Java object; Jackson and the starter's HTTP message converter convert it to JSON when the response is handled.
5. A single JSON key keeps the demonstration output stable; with multiple keys, do not rely on JSON property order unless explicitly configured.

To avoid depending on whether compilation retains parameter names, you can replace the parameter declaration above with:

```java
@RequestParam(name = "name", defaultValue = "friend") String name
```

In both cases, clients can call `/api/hello?name=Ada` to receive personalized data.

File `src/main/resources/application.properties`:

```properties
spring.application.name=spring-web-minimal
server.port=8080
```

`server.port` is a **Spring Boot** configuration for the embedded web server; it has no effect on its own if you run plain Spring Framework MVC inside an external Tomcat. If no port is declared, a Boot web app usually defaults to 8080. There is no need to create `web.xml`, a manual `DispatcherServlet` bean, or Java-based Tomcat configuration for this Boot example.

### Fully Explicit Controller Version to Copy and Use Directly

So that the exercise does not depend on parameter-name metadata, here is the full controller chosen for the runnable example:

```java
package com.example.webapp.controller;

import java.util.Map;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public Map<String, String> hello(
            @RequestParam(name = "name", defaultValue = "friend") String name) {
        return Map.of("message", "Hello, " + name + "!");
    }
}
```

The two controller blocks in this section illustrate the same endpoint; in the project **create only one `HelloController.java` file**, using the final explicit version.

## 7. Running and Verifying Request/Response

In the Gradle project root directory (where `build.gradle` is located):

**Windows PowerShell:**

```powershell
.\gradlew.bat clean test
.\gradlew.bat bootRun
```

**Linux/macOS:**

```bash
./gradlew clean test
./gradlew bootRun
```

`bootRun` keeps the application running in the terminal; open a second terminal to send requests. On the first run, Gradle may need Internet access to download plugins/dependencies. Wait until the application actually starts up successfully and the server listens on port 8080 before testing HTTP.

Use `curl.exe` on Windows, or `curl` on macOS/Linux:

```powershell
curl.exe -i "http://localhost:8080/api/hello?name=Ada"
```

Example JSON response body:

```json
{"message":"Hello, Ada!"}
```

Typical headers include `HTTP/1.1 200` and `Content-Type: application/json` (exact header/status line details may vary by server). When omitting the query:

```powershell
curl.exe "http://localhost:8080/api/hello"
```

Expected body:

```json
{"message":"Hello, friend!"}
```

When calling `http://localhost:8080/api/missing` and there is no handler for this path, the application returns HTTP 404 by default, though the detailed error structure/JSON depends on version and configuration.

Packaging and running as an executable JAR:

```powershell
.\gradlew.bat bootJar
java -jar build/libs/spring-web-minimal-0.0.1-SNAPSHOT.jar
```

If you change `rootProject.name` or `version`, the JAR name may change according to the build configuration. `bootJar` contains the runtime dependencies and startup mechanism needed for Spring Boot, unlike a standard Java library JAR.

## 8. Testing the Endpoint with Spring Boot + MockMvc

You can verify routing and JSON without opening a real HTTP server on a fixed port. File `src/test/java/com/example/webapp/HelloControllerTest.java`:

```java
package com.example.webapp;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

@SpringBootTest
@AutoConfigureMockMvc
class HelloControllerTest {

    @Autowired
    MockMvc mockMvc;

    @Test
    void helloUsesQueryParameter() throws Exception {
        mockMvc.perform(get("/api/hello").param("name", "Ada"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.message").value("Hello, Ada!"));
    }

    @Test
    void helloUsesDefaultName() throws Exception {
        mockMvc.perform(get("/api/hello"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.message").value("Hello, friend!"));
    }
}
```

`@SpringBootTest` loads the application context; `@AutoConfigureMockMvc` creates a mock Servlet request layer to test mappings and responses. `mockMvc.perform(...)` does not need to bind port 8080. The two assertions verify endpoint semantics without depending on logs or JSON key order.

Run:

```powershell
.\gradlew.bat test
```

When successful, the Gradle `test` task completes with success; if run again immediately without changes, Gradle may report `UP-TO-DATE`. Do not assume a fixed stdout for the entire Gradle run because logs depend on plugin version, JDK, and environment.

## 9. How Is Plain Spring Framework Different? Manual Servlet Configuration

This is a **separate deployment option**, shown so you can see what Spring Boot automates for you. When using plain Spring Framework MVC, you need at minimum:

- `org.springframework:spring-webmvc` and Spring's transitive dependencies.
- The corresponding Servlet API on the compile classpath.
- A `@Configuration` class with `@EnableWebMvc` + `@ComponentScan`.
- Registration of `DispatcherServlet` with the Servlet container via `WebApplicationInitializer` or `web.xml`.
- Building a WAR and deploying it to a compatible container (for example, Tomcat 10.1 for Jakarta Servlet 6.0). The external container must be running to accept HTTP requests.

Example of a **different project**, using Gradle + Spring Framework 6.2.19 and Tomcat 10.1:

```text
spring-mvc-war/
├── settings.gradle
├── build.gradle
└── src/main/java/com/example/plainweb/
    ├── WebConfig.java
    ├── WebInitializer.java
    └── HelloController.java
```

`settings.gradle`:

```groovy
rootProject.name = 'spring-mvc-war'
```

`build.gradle`:

```groovy
plugins {
    id 'java'
    id 'war'
}

group = 'com.example'
version = '0.0.1'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework:spring-webmvc:6.2.19'
    compileOnly 'jakarta.servlet:jakarta.servlet-api:6.0.0'
}
```

In the non-Spring Boot WAR example: the Gradle `war` plugin produces a WAR file; `compileOnly` means compiled code needs the Servlet API, while the external server will provide the Servlet API at runtime. Do not directly mix legacy `javax.servlet.*` classes with Spring Framework 6.x, which uses `jakarta.servlet.*`.

`WebConfig.java`:

```java
package com.example.plainweb;

import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.EnableWebMvc;

@Configuration
@EnableWebMvc
@ComponentScan(basePackageClasses = WebConfig.class)
public class WebConfig {
}
```

`WebInitializer.java`:

```java
package com.example.plainweb;

import org.springframework.web.servlet.support.AbstractAnnotationConfigDispatcherServletInitializer;

public class WebInitializer
        extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Class<?>[] getRootConfigClasses() {
        return null;
    }

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[] {WebConfig.class};
    }

    @Override
    protected String[] getServletMappings() {
        return new String[] {"/"};
    }
}
```

`HelloController.java` in the WAR project:

```java
package com.example.plainweb;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/api/hello")
    public String hello() {
        return "Hello from Spring MVC";
    }
}
```

When Tomcat detects `WebApplicationInitializer` via the Servlet startup mechanism, the initializer creates `DispatcherServlet`, uses `WebConfig` to enable MVC configurations, and scans for controller beans. `@RestController` + returning a string in this example produces a **text response**; Jackson is not required.

Build with Gradle:

```bash
./gradlew war
```

Then deploy `build/libs/spring-mvc-war-0.0.1.war` to a standalone Tomcat 10.1 instance. When deployed under the default context path derived from the WAR name, the request is typically:

```text
GET http://localhost:8080/spring-mvc-war-0.0.1/api/hello
```

The actual path depends on the deployment name/context path configured on the server; you can change the context to `/` so the endpoint becomes `/api/hello`. Do not use `java -jar` to run this WAR like a Boot JAR, because there is no embedded server/Boot launcher.

### Comparing Initialization Approaches

| Criterion | Plain Spring Framework MVC | Spring Boot + Spring MVC |
|---|---|---|
| Primary dependency | `spring-webmvc` | `spring-boot-starter-web` in Boot 3.5 |
| HTTP server | Usually requires an external Servlet container | Embedded Tomcat by default |
| DispatcherServlet configuration | Declare an initializer or `web.xml` | Boot auto-configuration |
| Startup | Deploy WAR to a container | `main()` + `SpringApplication.run` |
| MVC config | `@EnableWebMvc` in plain Java config | Convention + auto-configuration; usually no `@EnableWebMvc` needed |
| Deployment | Traditional WAR | Executable JAR commonly used; WAR can be configured separately |
| When useful | Understanding fundamentals, integrating legacy Servlet systems | Fast web service bootstrap, reducing configuration boilerplate |

**Note on `@EnableWebMvc`:** this annotation makes sense when configuring plain Spring MVC manually. With Spring Boot, adding `@EnableWebMvc` to a configuration can hand control of most MVC config back to you and override Boot's default customizations. When you only need to add an interceptor, formatter, CORS rule, or resource handler in Boot, first consider `WebMvcConfigurer` without enabling `@EnableWebMvc`.

## 10. Application Organization Rules When Scaling Up

A two-layer structure is sufficient for a minimal endpoint. As business requirements grow, keep responsibilities clear:

```text
com.example.webapp/
├── WebApplication.java
├── controller/
│   └── ProductController.java   # HTTP, request/response, status
├── service/
│   └── ProductService.java      # Business rules
├── repository/
│   └── ProductRepository.java   # Data access if present
├── dto/
│   └── ProductResponse.java     # HTTP data contract
└── config/
    └── WebConfig.java           # Add only when custom MVC is needed
```

This is a suggested layout, **not a set of mandatory classes** required for a Spring Web application to run. The Spring container manages objects annotated with `@Component`, `@Service`, `@Repository`, and `@Controller`/`@RestController` when scanned. Dependencies should be passed via constructors; controllers should only handle HTTP communication, while complex business logic moves into services for easier testing.

### When to Use Other Web Dependencies?

- `spring-web` alone provides many web/HTTP APIs but is **not equivalent** to the full Spring MVC servlet framework.
- `spring-webmvc` is the foundation for `DispatcherServlet`, handler mappings, and annotated controllers in Servlet MVC.
- `spring-boot-starter-web` (Boot 3.5 line) bundles MVC and a server for standalone Servlet applications.
- `spring-boot-starter-webflux` serves the reactive stack with a different processing model; do not add it just to create simple REST endpoints.
- Jackson is primarily needed when working with JSON; Spring MVC can return plain text without Jackson.
- Spring Boot 4.x reorganized web starter names (for example, `spring-boot-starter-webmvc`). Do not copy a Boot 3.5 build file into Boot 4 expecting all versions/dependencies to remain unchanged.

**Minimal dependencies** depend on the deployment style: plain servlet MVC and Boot MVC do not require the exact same list of directly declared libraries.

## 11. Common Issues and How to Check Them

| Symptom | Common Cause | Troubleshooting Step |
|---|---|---|
| Build cannot download `spring-boot-starter-web` | Missing `mavenCentral()`, wrong coordinates, network/proxy, repository credentials. | Check `repositories`, internet, `./gradlew dependencies`, and the actual resolution error. |
| `Unsupported class file major version` or toolchain failure | Incompatible JDK/Gradle/plugin, Gradle running on a different JDK. | Check `java -version` and `./gradlew --version`; choose a supported version set. |
| `Port 8080 was already in use` | Another application holds port 8080. | Stop the process occupying the port or set `server.port=8081` and test the new port. |
| HTTP 404 for `/api/hello` | Wrong path, wrong HTTP method, controller outside scan scope, app not running, or different context path. | Check `WebApplication`'s package, annotations, mapping, and actual URL. |
| HTTP 405 | Route exists but does not support the sent HTTP method. | Match GET/POST with the annotation. |
| Body returns JSON conversion error | Missing JSON converter or type/serialization error. | Check the starter, Jackson, and response data type. |
| Spring bean not found | Package scan does not cover the bean or missing stereotype/config annotation. | Place the app in the root package and check bean declarations. |
| `ClassNotFoundException: jakarta.servlet...` | Servlet API absent when running a WAR on a container or incompatible version combination. | Run the WAR on a suitable Servlet/Jakarta container; avoid `javax.servlet` in Spring 6.x. |
| Built a plain WAR yet running `java -jar` | Plain WAR lacks Boot launcher/embedded container. | Deploy to Tomcat or change design to a Spring Boot executable JAR. |
| Added `@EnableWebMvc` in Boot and static resource/MVC behavior changed | Overrode default MVC auto-configuration. | Remove the annotation if full MVC control isn't needed; use `WebMvcConfigurer` to extend. |

Some useful commands in a Gradle project:

```bash
./gradlew --version
./gradlew dependencies --configuration runtimeClasspath
./gradlew clean test
./gradlew bootRun
```

The last command only exists if the project applies the Spring Boot Gradle plugin. Do not infer the root cause from the HTTP status code alone without checking logs, mappings, port, context path, and runtime environment.

### Self-Check

**Q:** Is adding `spring-webmvc` to a Java project enough to have an HTTP server?  
**A:** Not yet. Spring MVC requires a Servlet container and registration of `DispatcherServlet`; the Spring Boot web starter handles automatically initializing an embedded container.

**Q:** Why is a controller placed in `com.example.webapp.controller` easily discovered?  
**A:** `@SpringBootApplication` on `com.example.webapp.WebApplication` triggers component scanning from the entry-point class's package down into subpackages.

**Q:** Should `@EnableWebMvc` be added so that a Boot endpoint can run?  
**A:** Not needed in typical Boot MVC examples. Boot already auto-configures MVC; adding that annotation can alter the default configuration.

**Q:** How do you ensure every machine uses the same Gradle version?  
**A:** Commit the Gradle Wrapper and run `./gradlew` or `.\gradlew.bat`; also control the Java toolchain and plugin/dependency versions.
