# Structure of Header, Properties, and Body of a JMS Message in Spring Framework

## 1. Big Picture

In Jakarta Messaging (JMS), a **message** is the unit of data sent by a producer to a **Destination** (Queue or Topic) and read by a consumer from a broker. A JMS message has **three parts with distinct roles**:

1. **Header**: standard JMS fields used for identification, routing, delivery coordination, and message tracking.
2. **Properties**: typed name–value pairs used as extensible metadata for the application, the JMS standard, or the provider; the broker can use some of these fields for filtering.
3. **Body**: the primary business data, such as a JSON string, plain text, a byte array, or map-structured data.

~~~text
Producer / Spring JmsTemplate
        |
        v
+------------------ JMS Message ------------------+
| HEADER        JMSMessageID, JMSCorrelationID,    |
|               JMSDestination, JMSType, ...       |
+-------------------------------------------------+
| PROPERTIES    tenant="VN", schemaVersion=1,      |
|               requiresAudit=true, ...            |
+-------------------------------------------------+
| BODY          {"orderId":"O-42","total":125000}  |
+-------------------------------------------------+
        |
        v
      Broker  --- selector on supported header/property
        |
        v
Consumer / @JmsListener  ---> process body + metadata
~~~

Suppose an order system sends an order-creation event:

- **Body** carries `{"orderId":"O-42","total":125000}` for business processing.
- **Property** `tenant="VN"` lets a consumer receive messages for only one data domain; `schemaVersion=1` helps select how to decode the payload.
- **Header** `JMSCorrelationID="checkout-O-42"` helps correlate with a request flow or trace; `JMSMessageID` is generated by the provider upon sending.

All three parts belong to **one JMS message**. Header/property values are not JSON fields inside the body, and the broker does not implicitly understand JSON content.

## 2. Header: Standard Fields Supported by Every JMS Message

Header fields are defined in `jakarta.jms.Message`; corresponding getters look like `getJMSMessageID()`, `getJMSTimestamp()`, etc. In the following table, "provider" means the JMS implementation library/broker, while "application" means the producer/consumer code.

| Header | Role | Who sets it per the JMS contract? |
| --- | --- | --- |
| `JMSDestination` | Target Queue or Topic of the message | Provider on send |
| `JMSMessageID` | Technical identifier of the message, normally generated by the provider | Provider on send |
| `JMSTimestamp` | Send timestamp in milliseconds since Unix epoch UTC | Provider on send |
| `JMSDeliveryMode` | `PERSISTENT` or `NON_PERSISTENT` | Provider reflecting the choice on send |
| `JMSExpiration` | Message expiration timestamp; `0` means no expiration by TTL | Provider computed from TTL on send |
| `JMSDeliveryTime` | Earliest timestamp the provider is allowed to deliver the message; related to delivery delay | Provider on send |
| `JMSPriority` | Priority level from `0` to `9`, default `4` | Provider reflecting the choice on send |
| `JMSCorrelationID` | Identifier linking messages in an exchange or processing flow | Application may set before send |
| `JMSReplyTo` | Suggested `Destination` where replies for a request message should be sent | Application may set before send |
| `JMSType` | Message type label per application/provider convention | Application may set before send |
| `JMSRedelivered` | Indicator that the message is being redelivered, not the first delivery | Provider before delivery |

### 2.1. Identification and Correlation Group

**`JMSMessageID`** is the technical ID of a JMS message instance. The provider normally assigns it when the send operation completes; its format and prefix such as `ID:...` depend on the provider. Applications should not set it themselves via `setJMSMessageID` before sending because the provider will ignore/overwrite it. ID generation can be disabled in some configurations for optimization; therefore, do not build business logic on the assumption that this ID always has a value.

**`JMSCorrelationID`** is proactively attached by the producer and passed through to the consumer. Two common usage patterns:

- Assign a business correlation ID, for example `checkout-O-42`, to messages belonging to the same transaction.
- In a request/reply pattern, the reply has `JMSCorrelationID` pointing to the request identifier; some systems use a business ID and some systems use the request's `JMSMessageID`. Both sides must agree on the same rule.

**`JMSReplyTo`** only provides a reply address; it **does not automatically generate a reply**. The receiving application still has to create/send the reply, or use the reply-handling feature of a listener framework.

**`JMSType`** is a classification label, for example `order.created.v1`. It is **not required** to be a Java class name, MIME type, or a schema automatically decoded by the broker. If you need to record `application/json`, a separate property (for example `contentType`) or an explicit system contract is typically used.

### 2.2. Timing, Priority, and Delivery Reliability Group

- **`JMSTimestamp`**: send time, **not** consumer processing time. The provider can be configured to omit the timestamp when appropriate; do not use it as the sole business timestamp.
- **`JMSExpiration`**: lifetime limit resulting from time-to-live (TTL). TTL = 0 means it does not expire automatically due to TTL; it does not mean permanent storage regardless of broker quota/retention.
- **`JMSDeliveryTime`**: constraint meaning *must not be delivered before this time* when delivery delay is used; it does not guarantee delivery at that exact millisecond.
- **`JMSPriority`**: 0 is lowest, 9 is highest, default value is 4; the broker may prioritize messages, but JMS does not guarantee strict ordering of all messages by priority.
- **`JMSDeliveryMode`**: `PERSISTENT` provides better message protection across provider failures than `NON_PERSISTENT`; the actual outcome still depends on broker configuration, transactions, and subscription state.
- **`JMSRedelivered`**: `true` means the message has been/is being redelivered according to the provider, useful for detecting errors and implementing duplicate-handling logic.

Do not use `message.setJMSPriority(...)`, `setJMSExpiration(...)`, or `setJMSDeliveryMode(...)` to dictate QoS before sending. According to JMS, the provider sets these headers from **send/producer options**. With `JmsTemplate`, `explicitQosEnabled` must be enabled when you want explicit priority, TTL, or delivery mode settings to take effect on send.

### 2.3. Headers Are Not "Everything Named JMS..."

A message also has **JMSX properties** such as `JMSXDeliveryCount`. They are **properties**, not part of the 11 standard headers above. In Jakarta Messaging 3.1, the provider must include `JMSXDeliveryCount` on a received message; the first delivery is `1`, and `2` or higher indicates redelivery. When a broker suffers a severe failure, the count value may not be strictly exact. Other JMSX properties may be supported to varying degrees depending on the provider.

## 3. Properties: Typed Extensible Metadata

Properties are a set of `name -> value` pairs attached to a message **outside the body**. They are commonly used for business routing, message selection, recording schema versions, or observability.

~~~text
Properties of an example message
tenant         : String  = "VN"
schemaVersion  : int     = 1
requiresAudit  : boolean = true
sourceSystem   : String  = "checkout"
~~~

JMS allows property values to belong to a strict set of types:

| JMS property type | Setter | Example getter |
| --- | --- | --- |
| `boolean` | `setBooleanProperty("requiresAudit", true)` | `getBooleanProperty("requiresAudit")` |
| `byte` | `setByteProperty(...)` | `getByteProperty(...)` |
| `short` | `setShortProperty(...)` | `getShortProperty(...)` |
| `int` | `setIntProperty("schemaVersion", 1)` | `getIntProperty("schemaVersion")` |
| `long` | `setLongProperty(...)` | `getLongProperty(...)` |
| `float` | `setFloatProperty(...)` | `getFloatProperty(...)` |
| `double` | `setDoubleProperty(...)` | `getDoubleProperty(...)` |
| `String` | `setStringProperty("tenant", "VN")` | `getStringProperty("tenant")` |

The `setObjectProperty` method also exists, but it only accepts the valid property type group, **not an arbitrary POJO**. Do not put a `Map`, `List`, or DTO object into a property. Large structured business data belongs in the **body**.

### 3.1. Property Names and Namespace Groups

- **Application-specific**: for example `tenant`, `schemaVersion`, `eventType`. Use readable, stable names that are valid under JMS selector identifier syntax.
- **JMS-defined**: the `JMSX` prefix is reserved by the JMS specification for standard properties, such as `JMSXDeliveryCount`, `JMSXGroupID`. Do not invent application names starting with `JMSX`.
- **Provider-specific**: the `JMS_<vendor>` prefix is reserved for providers. Do not rely on broker-specific fields if portability is a goal.

Property names are **case-sensitive**: `tenant` and `Tenant` are two different names. Set values with consistent types across producers; if producer A sends `schemaVersion` as an `int` while producer B sends it as a `String`, selector comparisons and getters may not behave as expected.

### 3.2. Message Selectors Only Filter Permitted Metadata

JMS selectors use expressions similar to a subset of SQL-92 syntax, but **are not full SQL**. Example:

~~~sql
tenant = 'VN' AND schemaVersion >= 1
~~~

The broker uses the selector to decide whether a consumer/subscription receives a message. Conditions can read application properties and **a subset of JMS headers supported in selectors**: `JMSDeliveryMode`, `JMSPriority`, `JMSMessageID`, `JMSTimestamp`, `JMSCorrelationID`, `JMSType`. Do not arbitrarily put the remaining headers into a selector; for instance, `JMSRedelivered` is not part of the standard selector header set.

Rules to remember:

1. Selectors **do not inspect a JSON body**. You cannot write `payload.orderId = 'O-42'` when `payload` only lives inside a `TextMessage`.
2. String comparisons use single quotes: `tenant = 'VN'`. Numeric comparisons use numeric literals: `schemaVersion >= 1`.
3. If a property is missing or the expression evaluates to **UNKNOWN** under three-valued logic, the selector does not match.
4. Filtering on properties assigned by the provider only **at receive time** (for example `JMSXDeliveryCount`) has undefined results per the specification; do not use such properties to build a reliable selector.
5. Changing property names/types after consumers have already been deployed can prevent messages from being delivered; manage them like an API contract.

### 3.3. When Should Information Go into Properties?

Choose a property if the broker/consumer needs to access metadata **without decoding the body**. For example, `tenant` for filtering; `schemaVersion` for selecting a decoder; `eventId` for tracking processing.

Do not turn an entire business JSON payload into dozens of properties: there is transfer/read overhead, provider dependency, and the risk of exposing metadata when logging. The body remains the primary source of data.

## 4. Body: Application-Defined Content

JMS defines message body types through interfaces extending `jakarta.jms.Message`:

| Type | Body content | When to use |
| --- | --- | --- |
| `TextMessage` | A `String` | Plain text, JSON, XML; suitable for cross-language integration |
| `BytesMessage` | Sequentially read/written byte stream | Protobuf, Avro, binary payloads with their own schema |
| `MapMessage` | Set of name–value fields of JMS-supported types | Small key/value data following the JMS contract |
| `StreamMessage` | Ordered sequence of primitive/string values | Sequential stream payloads, rarely used |
| `ObjectMessage` | Java `Serializable` object | Only consider in systems with full control over object types and security |
| `Message` | No body | Signal/control messages where business content is in metadata |

Notes:

- `TextMessage` holds a **string**, and does not inherently understand JSON. Producer and consumer must agree on encoding, schema, null handling, and versioning.
- `BytesMessage` suits binary formats; the consumer needs the matching schema/decoder. Endianness, versioning, and payload size are governed by the data contract.
- `MapMessage` is **different from** message properties: fields in the map belong to the body and are not implicitly accessible in a selector.
- `ObjectMessage` relies on Java serialization; it carries deserialization risks, classpath compatibility issues, and class sharing between services. In distributed systems, prefer JSON/Avro/Protobuf with controlled decoders.
- `Message#getBody(String.class)` reads a body assignable to `String` (typically `TextMessage`). If the body has a different type, the call may fail because it cannot be converted.

In Spring, `MessageConverter` decides which JMS message type a Java object turns into. A simple converter typically maps `String -> TextMessage`, `byte[] -> BytesMessage`, `Map -> MapMessage`, and `Serializable` objects `-> ObjectMessage`. For DTOs, configure an explicit JSON converter rather than relying on Java serialization.

## 5. Creation, Sending, Receiving, and Mutability Mechanics

A typical lifecycle:

1. **Producer creates a message** with a body; it may set `JMSCorrelationID`, `JMSReplyTo`, `JMSType`, and valid properties.
2. **Application sends** via `JmsTemplate` / `MessageProducer`; delivery mode, priority, TTL, and delay are taken from the send options. The provider sets related headers such as `JMSMessageID`, `JMSTimestamp`, `JMSDestination`.
3. **Broker routes** to a Queue/Topic, taking into account selectors, expiration, subscription state, and delivery policies.
4. **Consumer reads** headers, properties, and body; the provider attaches receive-time information such as `JMSRedelivered`, `JMSXDeliveryCount`.
5. **ACK/transaction** confirms consumption; if an error occurs before confirmation, the message may be redelivered.

**Read-only state:** the properties and body of a **newly received message** are in read-only mode. Calling setters to modify them directly can throw `MessageNotWriteableException`. `clearProperties()` or `clearBody()` can switch the corresponding part to writable, but during business processing you should usually create a **new message** to reply or forward, avoiding accidental corruption of the received message's metadata.

Headers have a different setter contract from properties: provider-managed header setters are not an API for forcing send outcomes.

## 6. Hands-On Example: Spring Boot 3.x + ActiveMQ Artemis (Java 17)

This hands-on example sends **a TextMessage containing JSON** to Queue `orders.demo`. The producer sets application-controlled headers and three typed properties; the listener uses a selector and reads **all three parts** to show clearly where each piece of information lives.

### 6.1. Run the Broker

Docker and Java 17+ are required. Use the official Apache Artemis image:

~~~bash
docker run --detach --rm --name jms-message-demo -p 61616:61616 -p 8161:8161 -e ARTEMIS_USER=demo -e ARTEMIS_PASSWORD=demo apache/artemis:latest-alpine
~~~

The broker accepts JMS connections on `localhost:61616`; the management console is at `localhost:8161`. The example uses demo credentials **for learning environments only**. Container data is lost after the container is removed unless a volume is mounted; do not use this sample configuration as a production operating standard.

If the broker does not auto-create destinations, create the Queue `orders.demo` with appropriate JMS routing on the broker before running the application. Auto-create behavior depends on broker configuration.

### 6.2. Gradle Project

`settings.gradle`:

~~~groovy

~~~

`build.gradle`:

~~~groovy

}
~~~

`src/main/resources/application.properties`:

~~~

`pub-sub-domain=false` configures routing by **Queue**. This lesson focuses on JMS message structure so a Topic is unnecessary; both Queue and Topic use the same header/properties/body model.

### 6.3. Entry Point

`src/main/java/demo/jms/DemoApplication.java`:

~~~java
package demo.jms;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.jms.annotation.EnableJms;

@SpringBootApplication
@EnableJms
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
~~~

### 6.4. Producer Setting Headers and Properties Correctly

`src/main/java/demo/jms/MessagePublisher.java`:

~~~java
package demo.jms;

import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Component;

@Component
public class MessagePublisher implements ApplicationRunner {

    private final JmsTemplate jmsTemplate;

    public MessagePublisher(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    @Override
    public void run(ApplicationArguments args) {
        String json = "{\"orderId\":\"O-42\",\"total\":125000}";

        jmsTemplate.convertAndSend("orders.demo", json, message -> {
            // HEADERS the application is allowed to set:
            message.setJMSCorrelationID("checkout-O-42");
            message.setJMSType("order.created.v1");

            // Typed PROPERTIES:
            message.setStringProperty("tenant", "VN");
            message.setIntProperty("schemaVersion", 1);
            message.setBooleanProperty("requiresAudit", true);
            return message;
        });

        System.out.println("SENT order O-42");
    }
}
~~~

Explanation:

- `convertAndSend` uses `MessageConverter` to turn `String json` into a JMS `TextMessage`.
- `MessagePostProcessor` receives the message after the convert step but **before the send step**, so it can set application headers and properties.
- The producer does **not** manually assign `JMSMessageID` / `JMSTimestamp`. The provider generates those values upon sending.
- `tenant="VN"` and `schemaVersion=1` have real types (String and int), allowing the selector to filter accurately.

### 6.5. Consumer Reading the Native JMS Message

`src/main/java/demo/jms/MessageInspector.java`:

~~~java
package demo.jms;

import jakarta.jms.JMSException;
import jakarta.jms.Message;
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class MessageInspector {

    @JmsListener(
        destination = "orders.demo",
        selector = "tenant = 'VN' AND schemaVersion = 1"
    )
    public void inspect(Message message) throws JMSException {
        // BODY: TextMessage is read as String
        String body = message.getBody(String.class);

        // HEADERS:
        String messageId = message.getJMSMessageID();
        String correlationId = message.getJMSCorrelationID();
        String type = message.getJMSType();

        // PROPERTIES:
        String tenant = message.getStringProperty("tenant");
        int version = message.getIntProperty("schemaVersion");
        boolean audit = message.getBooleanProperty("requiresAudit");

        System.out.println("BODY=" + body);
        System.out.println("JMSType=" + type);
        System.out.println("JMSCorrelationID=" + correlationId);
        System.out.println("tenant=" + tenant);
        System.out.println("schemaVersion=" + version);
        System.out.println("requiresAudit=" + audit);
        System.out.println("JMSMessageID present=" + (messageId != null));
        System.out.println("JMSXDeliveryCount=" +
                message.getIntProperty("JMSXDeliveryCount"));
    }
}
~~~

Because Spring supports the **native `jakarta.jms.Message`** parameter in `@JmsListener`, you can read all JMS headers, properties, and body without having to guess field names after mapping to `org.springframework.messaging.Message<?>`.

When the consumer receives the message, the 6 lines with deterministic values are:

~~~text
BODY={"orderId":"O-42","total":125000}
JMSType=order.created.v1
JMSCorrelationID=checkout-O-42
tenant=VN
schemaVersion=1
requiresAudit=true
~~~

The remaining two lines depend on the provider/delivery state: under normal configuration `JMSMessageID present=true` and `JMSXDeliveryCount=1` on the first delivery. The broker generates its own ID; the ID string cannot be predicted beforehand. The `SENT order O-42` line and the consumer lines may interleave depending on thread scheduling.

## 7. How Do Send Options Affect Headers?

With Spring `JmsTemplate`, an illustrative example configuring QoS on the template **before sending**:

~~~java
// Set once during JmsTemplate initialization configuration,
// do not call again across threads sharing the template.
jmsTemplate.setExplicitQosEnabled(true);
jmsTemplate.setTimeToLive(60_000L);   // 60 seconds
jmsTemplate.setPriority(7);            // Higher priority than default
jmsTemplate.setDeliveryPersistent(true);
~~~

This is an **illustrative supplementary configuration snippet**, not a standalone Java file. `setExplicitQosEnabled(true)` forces `JmsTemplate` to apply the configured QoS options on send. The broker reflects them in `JMSExpiration`, `JMSPriority`, and `JMSDeliveryMode`; the provider/administrator may still apply override rules per policy. Do not set `setJMSExpiration` directly on a `TextMessage` to achieve TTL.

In pure JMS API, the corresponding configuration lives on `MessageProducer` / `JMSProducer` or in the send parameters. Delivery delay is another send option, not an arbitrary custom property you set hoping the broker will defer delivery.

## 8. Request/Reply Example: Three Headers Often Confused

In a `checkout` request sent to check status:

~~~text
Request:
  JMSMessageID      = ID assigned by broker, e.g. ID:request-...
  JMSCorrelationID  = checkout-O-42
  JMSReplyTo        = queue:checkout.replies
  JMSType           = checkout.status.request

Reply:
  JMSMessageID      = New ID of reply
  JMSCorrelationID  = checkout-O-42 (per example contract)
  JMSDestination    = queue:checkout.replies
  JMSType           = checkout.status.reply
~~~

Code setting `JMSReplyTo` when creating a request with Spring:

~~~java
// Illustration inside a bean with an injected JmsTemplate:
jmsTemplate.send("checkout.requests", session -> {
    var request = session.createTextMessage("{\"orderId\":\"O-42\"}");
    request.setJMSCorrelationID("checkout-O-42");
    request.setJMSReplyTo(session.createQueue("checkout.replies"));
    request.setJMSType("checkout.status.request");
    request.setStringProperty("tenant", "VN");
    return request;
});
~~~

This code only **sends the request**. The server-side consumer needs to create a new reply and send it to the destination from `request.getJMSReplyTo()`. Some Spring features such as `@JmsListener` return values support sending replies, but you must not assume a request automatically generates a reply.

Key distinctions:

- `JMSMessageID`: ID of **each individual** JMS message, typically different between request and reply.
- `JMSCorrelationID`: identifier **linking multiple messages** in the same processing flow, per the convention agreed by both sides.
- `JMSReplyTo`: destination address where the **reply should be sent**, not a correlation ID.

## 9. Inspecting All Properties and Distinguishing from Body

When the set of properties is not known in advance, you can enumerate them:

~~~java
// Illustration inside a method that received jakarta.jms.Message message:
var names = message.getPropertyNames();
while (names.hasMoreElements()) {
    String name = names.nextElement().toString();
    Object value = message.getObjectProperty(name);
    System.out.println(name + "=" + value);
}
~~~

`getPropertyNames()` and `getObjectProperty()` only iterate over **properties**; they do not automatically include all 11 JMS headers and do not decode the body. To read `JMSType`, you must call `getJMSType()`; to read a JSON `TextMessage`, call `getText()` or `getBody(String.class)`.

A consumer can check `propertyExists("schemaVersion")` before calling a typed getter. For optional metadata, clearly distinguish **missing property**, **property with wrong type**, and **valid value**. Do not use `0` or `false` as the sole signal for "property does not exist".

## 10. Practical Notes: Security, Schema, and Reprocessing

**Data contract:** document all 3 layers clearly across services, for example:

~~~yaml
destination: orders.demo
messageType: TextMessage
headers:
  JMSType: order.created.v1
  JMSCorrelationID: checkout-O-42
properties:
  tenant: VN               # String
  schemaVersion: 1         # int
  requiresAudit: true      # boolean
body: '{"orderId":"O-42","total":125000}'
~~~

This is an **illustrative YAML contract document**, not a Spring configuration file for the application to load automatically. In a real system, you should standardize required fields, data types, access permissions, schema evolution, and backward-compatibility policies.

**Security:** headers/properties often appear in broker management UIs, traces, or logs. Do not put passwords, access tokens, or sensitive personal data into properties merely for easy filtering. If carrying sensitive data is unavoidable, appropriate encryption, authorization, and log-redaction policies are required.

**Redelivery:** on processing errors or rollbacks, the same message may be redelivered with `JMSRedelivered=true` and `JMSXDeliveryCount>=2`. This is a diagnostic signal, **not a substitute for idempotent processing**. If business logic must prevent duplicate processing, store a stable business `eventId` in the body/property and guard side effects using that key; do not rely solely on `JMSMessageID`.

**Transaction:** "message delivered to listener" differs from "message ACKed/committed after processing". If you update a DB and the process crashes before ACK, redelivery can occur; a local JMS transaction does not automatically synchronize with an external DB transaction outside the broker.

**Compatibility:** renaming the `tenant` property to `region` while forgetting to update the selector can stop consumers from receiving messages. Likewise, changing the body from JSON text to a Java serialized object without publishing a contract change can prevent consumers from decoding it or introduce security risks.

## 11. Common Pitfalls and How to Check

| Symptom | Hypothesis to check | Resolution |
| --- | --- | --- |
| Listener runs but receives no messages | Wrong destination, Queue/Topic mode, or selector mismatch | Re-check destination, `pub-sub-domain`, and property value/type |
| `schemaVersion >= 1` does not match | Producer sends version as String or uses wrong name | Set `int` consistently; inspect actual properties via broker/consumer |
| `JMSMessageID` differs from business ID | Confusing technical ID with `eventId` | Attach a separate business ID; do not force `JMSMessageID` via setter |
| TTL set but message does not expire | Only set header, forgot explicit QoS or broker override | Configure producer/template QoS and observe `JMSExpiration` |
| `JMSReplyTo` set but no reply arrives | No handler sending reply; response destination does not exist | Create request/reply handler, verify reply is sent and correlation matches |
| Body cannot be read as String | Message is not TextMessage or converter differs from contract | Check message type, use matching converter/decoder |
| Java DTO causes deserialization error | Using ObjectMessage with mismatched classpath or allowlist | Prefer TextMessage JSON/BytesMessage with controlled schema and decoder |
| `MessageNotWriteableException` error | Modifying properties/body of a received message | Create a new message or understand `clearProperties` / `clearBody` |
| One message processed twice | Rollback, crash before ACK, or retry | Idempotency, retry/DLQ, and observe `JMSXDeliveryCount` |

## 12. Self-Check Questions

1. When a producer sends a JSON string via `convertAndSend`, is the JSON a property or the body? **Body**, usually in a `TextMessage`; it does not automatically become a set of properties.
2. Can `message.setJMSExpiration(now+60000)` be used before sending to set TTL? **No**; configure TTL through the producer/send options, using explicit QoS with `JmsTemplate`.
3. Can you write selector `tenant = 'VN'` if `tenant` is inside the JSON body with no corresponding property? **No**.
4. Does `JMSXDeliveryCount` belong to headers or properties? **JMS-defined property**; on a received message, the first delivery is 1.
5. In request/reply, must the reply's ID equal the request's ID? **No**; each message has its own `JMSMessageID`, while `JMSCorrelationID` carries the agreed pairing mechanism.
6. Are `MapMessage` and message properties the same thing? **No**; map fields reside in the body, whereas properties are separate metadata usable in selectors.
7. Why use a business `eventId` instead of relying only on `JMSMessageID` for idempotency? Because retries/re-publishing can create a new transport message for the same business event.
8. Should a consumer read `JMSType` via `getStringProperty("JMSType")` like any custom property? **No**; `JMSType` is a standard header, so use `getJMSType()`.
