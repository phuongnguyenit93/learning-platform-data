# Determining Compatible Spring, Java, and Jakarta Validation Versions

When building **validation** and **data binding** features in Spring, you must choose a complete **compatible version stack**, rather than just picking a recent version of the `jakarta.validation-api` library. An application may compile yet still fail to run properly if Spring Framework, Java, the Jakarta Validation API, and the actual validation implementation are from mismatched generations.

This lesson guides you through identifying the version layers, choosing an appropriate configuration for new or maintained projects, verifying actual dependencies, and troubleshooting common errors. The illustrated versions are checked against official release documentation **as of November 2, 2026**; for projects using releases after that date, cross-check the corresponding documentation.

## 1. Which Components Need to Be Checked?

| Component | Role in the application | What to check |
| --- | --- | --- |
| **Java / JDK** | Compiles and runs the application | Minimum version, JDK used to build, generated bytecode level, and JDK used to run |
| **Spring Framework** | IoC, data binding, Spring MVC, Bean Validation support | Major/minor version compatible with the Jakarta API and the Spring version's ecosystem |
| **Spring Boot** (if used) | Auto-configuration and dependency stack management via BOM | Which Spring Framework and Hibernate Validator versions the chosen Boot line manages |
| **Jakarta Validation API** | Defines `@Valid`, `@NotNull`, `@Size`, `Validator`, `ConstraintViolation`… | Correct API generation and `jakarta.validation.*` or `javax.validation.*` namespace |
| **Validation provider** | Executes constraint checks at runtime | Hibernate Validator (or another provider) implementing the matching Jakarta Validation API version |
| **Build tool / deployment environment** | Maven, Gradle, CI runners, server/container | Supports the chosen Spring Boot and JDK; creates no mismatch between build and run environments |

**Key point:** The API is only a contract. For example, `jakarta.validation-api` contains the `@NotBlank` definition, but by itself it does not provide the engine that executes all constraints. A provider such as **Hibernate Validator** performs that work.

### How Do Spring Framework and Spring Boot Differ?

**Spring Framework** is the foundation providing features such as `DataBinder`, `ConversionService`, `org.springframework.validation.Validator`, and integration with Jakarta Validation. **Spring Boot** builds on Spring Framework and defines a set of libraries tested together. Therefore, if your project uses Boot, **choose the Boot version first**, and let Boot's BOM/parent manage Spring Framework, Jakarta Validation API, and Hibernate Validator.

Do not manually upgrade `spring-core` alone to a new major version or force a Hibernate Validator version from a different generation just because the version number looks higher.

## 2. Generation Comparison Table

The "API" and "provider" columns below represent the stack that Spring Boot **manages**, and do not imply that any release of those libraries can be freely interchanged.

| Reference version stack | Java | Spring Framework | Jakarta Validation API | Default provider via starter | Namespace |
| --- | --- | --- | --- | --- | --- |
| **Spring Boot 4.1.2** (stable at reference date) | Minimum **17**; Boot states compatibility up to Java **27** | **7.0.10+** in the corresponding line | **3.1.1** (Jakarta Validation 3.1 specification) | Hibernate Validator **9.1.5.Final** | `jakarta.validation.*` |
| **Spring Boot 3.5.16** | Minimum **17**; Boot states compatibility up to Java **25** | **6.2.19+** in the corresponding line | **3.0.2** (Jakarta Bean Validation 3.0 specification) | Hibernate Validator **8.0.3.Final** | `jakarta.validation.*` |
| **Spring Boot 2.7.x** (legacy line, for identification/migration) | Starts at Java **8** | **5.3.x** | Bean Validation **2.0** | Hibernate Validator **6.2.x** | `javax.validation.*` |

Verification sources: [Spring Boot 4.1 system requirements](https://docs.spring.io/spring-boot/4.1/system-requirements.html), [Spring Boot 3.5 system requirements](https://docs.spring.io/spring-boot/3.5/system-requirements.html), [Boot 4.1 managed dependencies](https://docs.spring.io/spring-boot/4.1/appendix/dependency-versions/coordinates.html), [Boot 3.5 managed dependencies](https://docs.spring.io/spring-boot/3.5/appendix/dependency-versions/coordinates.html), [Hibernate Validator compatibility matrix](https://hibernate.org/validator/releases/).

**Notes on reading the table:**

1. **Minimum Java** is the baseline requirement to run; **maximum Java claimed compatible by Boot** is not a guarantee that every third-party library has also been tested on every JDK in that range. Hibernate Validator 9.1, for instance, publishes its own list of supported Java versions; if prioritizing widely adopted environments, choose **JDK 21 or 25** within the Boot 4.1 stack.
2. "Spring Framework **7.0.10+**" and "**6.2.19+**" are threshold requirements stated in the respective Boot guides, **not** a suggestion to arbitrarily mix a newer Spring Framework line into an older Boot release. Let the BOM choose the actual patch version.
3. "Jakarta Validation **3.1**" is the **specification version**; "`jakarta.validation-api:3.1.1`" is the **artifact version** managed by the BOM. Likewise, API `3.0.2` implements the contract of specification `3.0`.
4. Boot 2.7 is included to recognize legacy systems, not as a default choice for new projects. Upgrading from Boot 2 to Boot 3 entails changing the namespace from `javax.validation.*` to `jakarta.validation.*`.
5. RC, milestone, and snapshot releases (for example, an unreleased new Boot branch before GA) must be distinguished from stable releases. Avoid using preview releases when the task simply calls for an officially released stack.

## 3. Which Java Version Should You Use?

**Java 17** is the baseline for Spring Framework 6 and 7, as well as Spring Boot 3 and 4. For new projects choosing Boot 4.1 or Boot 3.5, **Java 21** is a practical, widely adopted LTS choice; Java 25 is also an LTS line to consider if all dependencies, tooling, and production environments support it.

Before configuring the project, check:

~~~bash
java -version
javac -version
mvn -version
~~~

`java -version` displays the invoked Java Runtime; `javac -version` displays the JDK compiler; `mvn -version` shows which Java Maven actually uses. For Gradle:

~~~bash
./gradlew --version
~~~

On Windows, you can replace `./gradlew` with `gradlew.bat` or use `mvnw.cmd` if the project provides Maven Wrapper.

If `java -version` is 21 while `mvn -version` uses 17, the build may fail when `--release 21` is declared. Adjust `JAVA_HOME`, IDE/CI settings, and Java toolchains so they match. Do not rely solely on the "Project SDK" displayed in the IDE.

### Distinguishing Three Java Version Concepts

- **Build JDK:** the JDK used by Maven/Gradle and build plugins.
- **Target/release bytecode:** the class file version produced by the compiler, such as Java 21.
- **Runtime JDK:** the actual JVM on the server or in the container. It must be able to read the bytecode and meet the framework/provider requirements.

For example, an application compiled with `--release 21` cannot run on JVM 17; the typical error is `UnsupportedClassVersionError`. If there is no need for newer features, set the release target to the lowest deployment JDK confirmed to be compatible.

## 4. Choosing Jakarta Validation 3.0 or 3.1?

### Jakarta Bean Validation 3.0

This is the generation that changed packages from `javax.validation.*` to `jakarta.validation.*`, used in the Jakarta EE 9/10 stack and Hibernate Validator 7/8. The actual stack of Spring Boot **3.5.16** uses **Jakarta Validation API 3.0.2 + Hibernate Validator 8.0.3.Final**. The Java runtime must still meet Spring Boot 3.5's **Java 17+** requirement.

### Jakarta Validation 3.1

The Jakarta Validation **3.1** specification belongs to Jakarta EE **11**, uses Java **17+**, and clarifies support for **Java records**. Spring Framework 7 and Spring Boot 4 belong to the Jakarta EE 11 generation; Boot **4.1.2** manages **Jakarta Validation API 3.1.1 + Hibernate Validator 9.1.5.Final**.

Do not conclude that merely swapping the API artifact from `3.0.2` to `3.1.1` upgrades the entire application to the new generation. The provider, Spring integration, and dependent libraries must all align. Likewise, adding API `3.1` to Boot 3.5 does not automatically upgrade Spring Framework 6 to 7.

### API, Provider, and Spring Validator

Three common imports in source code:

~~~java
import jakarta.validation.Valid;
import jakarta.validation.Validator;
import jakarta.validation.constraints.NotBlank;

import org.springframework.validation.BindingResult;
~~~

- `jakarta.validation.Valid` and `jakarta.validation.Validator` belong to the **Jakarta Validation API**.
- `org.hibernate.validator.*` belongs to **Hibernate Validator**, the provider executing Jakarta Validation.
- `org.springframework.validation.Validator` is **Spring's validation interface**, distinct from `jakarta.validation.Validator` even though Spring has an adapter integrating the two APIs; `BindingResult` also belongs to Spring.

Choose imports based on the specific need, rather than mechanically swapping the two `Validator` interfaces.

**Namespace rule:** Spring Boot 3/4 code uses `jakarta.validation.constraints.NotNull`, not `javax.validation.constraints.NotNull` from Boot 2 projects. Besides Java source files, you must audit constraint XML, custom validators, extension libraries, and legacy dependencies during migration.

## 5. Working Maven Configuration: Spring Boot 4.1.2 + Java 21

This example selects **Spring Boot 4.1.2**, **Java 21**, Jakarta Validation **3.1**, and Hibernate Validator **9.1** managed by Boot's BOM. It is a small Java application to self-verify the validation provider; no HTTP server is required.

Create `pom.xml`:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>4.1.2</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>validation-compatibility</artifactId>
    <version>0.0.1-SNAPSHOT</version>

    <properties>
        <java.version>21</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-validation</artifactId>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

**No `<version>` is needed for starters, `jakarta.validation-api`, or `hibernate-validator`:** the Spring Boot parent imports the appropriate dependency management. When Spring MVC is needed for forms/data binding, add `org.springframework.boot:spring-boot-starter-webmvc` (Boot 4), whereas the pure API check example below does not require web.

Create `src/main/java/com/example/demo/ValidationCompatibilityApplication.java`:

~~~java
package com.example.demo;

import java.util.Set;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validator;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.SpringBootVersion;
import org.springframework.context.annotation.Bean;
import org.springframework.core.SpringVersion;

@SpringBootApplication
public class ValidationCompatibilityApplication {

    public static void main(String[] args) {
        SpringApplication.run(ValidationCompatibilityApplication.class, args);
    }

    public record Registration(
            @NotBlank String name,
            @Min(18) int age) {
    }

    @Bean
    ApplicationRunner checkVersions(Validator validator) {
        return args -> {
            Registration invalid = new Registration("", 16);
            Set<ConstraintViolation<Registration>> errors =
                    validator.validate(invalid);

            System.out.println("validationErrors=" + errors.size());
            System.out.println("java=" + Runtime.version().feature());
            System.out.println("springBoot=" + SpringBootVersion.getVersion());
            System.out.println("springFramework=" + SpringVersion.getVersion());
        };
    }
}
~~~

With JDK 21, a compatible Maven version, and downloaded artifacts, run:

~~~bash
mvn spring-boot:run
~~~

In the logs, the program will print **the lines worth checking**:

~~~text
validationErrors=2
java=21
springBoot=4.1.2
~~~

The `springFramework=...` value is the actual Spring Framework version selected by dependency management, so **read the printed value** rather than assuming every future build will always pick the same patch. If a different JDK is used, `java=...` will change accordingly. Spring Boot startup logs should not be treated as a fixed part of the illustrated output.

Why are there **2** errors? `name=""` violates `@NotBlank` and `age=16` violates `@Min(18)`. Without an active provider, the program will not produce the expected validation results; this step verifies the API, the provider, and Spring Boot's integration.

File structure:

~~~text
validation-compatibility/
├── pom.xml
└── src/
    └── main/
        └── java/
            └── com/
                └── example/
                    └── demo/
                        └── ValidationCompatibilityApplication.java
~~~

This is a complete example inside a Maven project; it cannot be run with just `javac ValidationCompatibilityApplication.java` because it requires Spring and Jakarta Validation on the classpath.

## 6. Gradle Equivalent

With **Gradle Groovy DSL** and JDK 21, you can declare:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '4.1.2'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
}
~~~

Save the file as `build.gradle`. This Spring Boot plugin version applies alongside `io.spring.dependency-management` to use the corresponding BOM; starters still omit manual version numbers. Verify that the Gradle Wrapper is **8.14+** (in Gradle 8) or a Gradle 9 version supported by Boot 4.1. Run:

~~~bash
./gradlew bootRun
./gradlew dependencyInsight --dependency hibernate-validator --configuration runtimeClasspath
./gradlew dependencyInsight --dependency jakarta.validation-api --configuration runtimeClasspath
~~~

If the project environment uses **Spring Boot 3.5**, substitute a Gradle version compatible with Boot 3.5 and use JDK 17 or 21; keep the same principle of **letting Boot manage the API/provider**. Do not copy Boot 4 plugin/starter configurations verbatim into a Boot 3 build without checking compatibility.

## 7. How to Verify Actual Versions Using the Dependency Tree

Do not just read `pom.xml` or `build.gradle`: dependencies can arrive transitively through starters, BOMs, parents, or other libraries.

With Maven:

~~~bash
mvn -version
mvn dependency:tree -Dincludes=org.springframework:spring-core,jakarta.validation:jakarta.validation-api,org.hibernate.validator:hibernate-validator
~~~

You can view the entire tree with:

~~~bash
mvn dependency:tree
~~~

With Gradle:

~~~bash
./gradlew --version
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency spring-core --configuration runtimeClasspath
./gradlew dependencyInsight --dependency hibernate-validator --configuration runtimeClasspath
~~~

Compare the **final selected** artifacts against the running Boot line. For example, with Boot 4.1.2, expect Java 21 (if configured as in the example), Spring Framework 7.0.x, Jakarta Validation API 3.1.1, and Hibernate Validator 9.1.5.Final; whereas Boot 3.5.16 corresponds to Spring 6.2, Validation API 3.0.2, and Hibernate Validator 8.0.3.Final.

If the dependency tree shows two versions of the same API or a provider forced by another dependency, trace the **transitive path** leading to the conflict. In Maven, `dependencyManagement` determines the selected version; in Gradle, resolution strategies, platforms/BOMs, or constraints can affect the outcome. Analyzing **runtimeClasspath** is especially important because the application must run with the exact dependencies that were tested.

### A Quick Checklist Before Concluding a Stack Is Compatible

1. Read the **System Requirements** documentation of the exact Boot version in use to determine JDK and build tool requirements.
2. Check the **Managed Dependency Coordinates** of that exact Boot version to find `spring-core`, `jakarta.validation-api`, and `hibernate-validator`.
3. Cross-check the **Hibernate Validator Compatibility Matrix** to know the Jakarta Validation specification and Java versions supported by the provider.
4. Run Maven/Gradle dependency tree or `dependencyInsight` to confirm the actual resolved artifacts.
5. Run the application and a constraint smoke test, rather than relying only on source code compilation.
6. Document the JDK/toolchain and lock the Boot version using Wrapper/BOM in CI so development machines and build machines use the exact same configuration.

## 8. Compatibility at the Spring MVC and Data Binding Layer

A Spring MVC controller might use:

~~~java
@PostMapping("/users")
public String create(
        @Valid @ModelAttribute UserForm form,
        BindingResult errors) {
    if (errors.hasErrors()) {
        return "users/form";
    }
    return "users/saved";
}
~~~

This is an **illustrative snippet**, not a standalone Java class. In addition to the appropriate imports, the application needs the controller and `UserForm` defined, along with the MVC and validation starters.

- `@ModelAttribute` uses Spring MVC's data binding system to instantiate/populate form properties.
- `@Valid` triggers validation of the object using the compatible provider when configured.
- `BindingResult` receives binding/validation errors and must be placed **immediately after** the parameter to be validated so the controller can handle errors.
- With Spring Boot 4, the starter for MVC is `spring-boot-starter-webmvc`; the old name `spring-boot-starter-web` is marked deprecated. With Spring Boot 3, `spring-boot-starter-web` remains the standard MVC starter.

If `spring-boot-starter-validation` is missing, the application may still receive forms via Spring MVC, but constraint annotations may not be enforced as expected. Therefore, "binding succeeded" **is not the same as** "validation ran and returned errors properly".

Jakarta EE and Servlet levels also need attention when deploying WARs/to external containers. For instance, the Boot 3.5 line uses the Servlet 6.0/Tomcat 10.1 generation, while Boot 4.1 uses Servlet 6.1/Tomcat 11. An outdated runtime/container can cause errors even when validation code is written correctly.

## 9. Common Version Errors and How to Find the Root Cause

| Symptom | Common cause | Resolution |
| --- | --- | --- |
| `package javax.validation does not exist` after upgrading to Boot 3/4 | Source code still imports the old namespace | Switch to `jakarta.validation.*`; check related libraries/custom constraints |
| `NoProviderFoundException` when calling `Validation.buildDefaultValidatorFactory()` | Jakarta Validation API is present but a compatible provider is missing on the runtime classpath | Add `spring-boot-starter-validation` in Boot; if not using Boot, declare a provider and its dependencies per the provider's guide |
| `NoClassDefFoundError: jakarta/validation/...` | Missing API or a dependency was excluded/omitted from packaging | Inspect the runtime dependency tree, fix dependencies and packaging |
| `NoSuchMethodError`, `ClassNotFoundException` after upgrading versions | Spring, provider, API, or transitive libraries are mixed incompatibly | Remove manually pinned versions, use consistent BOM alignment, trace the failing artifact's path |
| `UnsupportedClassVersionError` | Runtime JDK does not support the compiled bytecode | Align target release with the runtime/CI JDK |
| `UnexpectedTypeException` | Annotation does not match the data type, e.g. `@NotBlank` on `Integer` | Use type-appropriate constraints such as `@NotNull` and `@Min` |
| `@Valid` does not produce errors as expected | Validation was not triggered, missing provider, wrong integration path, or constraints placed in the wrong location | Check starter/provider, validation trigger, DTO model, and `BindingResult` output |
| Both `javax.validation` and `jakarta.validation` appear in dependencies | A legacy dependency pulls in the old API or code mixes imports | Locate the root dependency, upgrade/migrate the corresponding module, do not arbitrarily rewrite packages by forcing versions |

**Do not try to fix `NoSuchMethodError` by randomly updating individual artifacts.** Look at the **resolved** versions and select a consistent set via the BOM. When an external library still requires `javax.validation`, evaluate upgrading/migrating that library itself first.

## 10. Choosing a Version Stack by Scenario

**New Spring Boot project:** start from a current stable release, such as Boot **4.1.2** at the time this lesson was written; pick JDK **21** or **25** if dependencies and infrastructure are compatible. Declare the validation starter and let Boot manage Jakarta Validation 3.1/provider 9.1.

**Existing Spring Boot 3.5 project:** stay on the **Spring Framework 6.2 + Jakarta Validation 3.0 + Hibernate Validator 8** line, applying compatible patch updates per project policy. There is no need to upgrade the entire stack just to use `@NotNull`, `@Valid`, or basic data binding.

**Plain Spring Framework project without Boot:** consult the system requirements of the exact Spring line, select a provider matching the Jakarta Validation API version, and directly manage required dependencies (which may include an implementation for message interpolation). On this path, there is no Boot BOM to automatically guarantee all libraries align in version.

**Spring Boot 2 / Spring Framework 5 system:** recognize the `javax.validation` namespace and plan a full migration to `jakarta.validation` when upgrading to Boot 3/4. This is a package and ecosystem shift, not merely changing a version number in a build file.

### Quick Decision Examples

- **Java 11 + Boot 4.1?** Incompatible because Boot 4.1 requires **Java 17+**. You must upgrade the JDK or choose an older Spring generation suited to legacy constraints while considering support lifecycles.
- **Java 21 + Boot 3.5 + Hibernate Validator 8?** A combination aligned with the published requirements of this line when using Boot's BOM.
- **Java 21 + Boot 4.1 + manually pinned Jakarta Validation API 3.0.2?** Not recommended: Boot 4.1 manages API **3.1.1** and provider **9.1**. Remove the version override, restore dependency management, and re-run tests.
- **Only the `jakarta.validation-api` dependency?** Sufficient to compile annotations, but not enough to execute constraints; a provider or a container environment supplying an appropriate provider is required.

## 11. Self-Practice Questions

1. Why is looking at the `jakarta.validation` package name alone not enough to tell whether it is API 3.0 or 3.1?
2. A Boot 3.5 project has Java 21 and the `@NotNull` annotation, yet at runtime it reports no violations at all. Which dependencies and integration points should be checked?
3. If Gradle selects Hibernate Validator 9.x in a Boot 3.5 project using the default BOM, which command should you run to find the dependency forcing that version?
4. When upgrading from Boot 2 to Boot 3, which namespace change affects constraint annotations and custom validators?
5. Why is "Spring Boot supports Java X" still not sufficient to guarantee that every provider, JDBC driver, and build tool in the project supports Java X?

**Remember:** choose **Spring Boot → Java/JDK → BOM-managed Spring Framework, Jakarta Validation API, and provider**, then inspect the dependency tree and run actual validation. Compatibility is a property of **the entire library stack and runtime environment**, not just a single line in `pom.xml`.
