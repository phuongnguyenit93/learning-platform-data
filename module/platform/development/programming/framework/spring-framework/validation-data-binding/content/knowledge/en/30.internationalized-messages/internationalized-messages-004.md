# Error Codes by Object Name, Field, and Data Type in Spring: Designing Multilingual Messages

## 1. The Problem to Solve

When Spring Framework binds HTTP data into a Java object or validates a form/DTO, the same kind of error may require **different messages depending on the context**:

- User leaves `name` blank on the registration form: “Please enter your full name”.
- User leaves `name` blank on the supplier form: “Please enter the supplier name”.
- User sends `age=abc`: “Age must be a whole number”.
- User sends `quantity=abc`: “Quantity must be a number”.
- An object has inconsistent fields: “Profile data is invalid”.

You should not hardcode every message inside validators and write dozens of `if/else` branches. Spring provides an **ordered error code** mechanism through `MessageCodesResolver`, whose default implementation is **`DefaultMessageCodesResolver`**, combined with **`MessageSource`** to look up messages by `Locale`.

**Key takeaway:** an error has a **base code** such as `typeMismatch`, while Spring can attach multiple **candidate codes** from specific to general:

~~~text
typeMismatch.profileForm.age
typeMismatch.age
typeMismatch.java.lang.Integer
typeMismatch
~~~

When resolving a message, Spring picks **the first code that has a translation** in the appropriate message bundle. This lets us customize messages for a specific form, a field across multiple forms, all fields of the same data type, or the entire system — **without changing binding or validation logic**.

This lesson belongs to the **internationalized messages in Spring validation and data binding** series, focusing on how error codes are generated by **object name**, **field name**, and **Java type**, how messages are selected, how to test them, and common pitfalls.

## 2. Related Concepts and APIs

| Component | Typical Package/Interface | Responsibility |
| --- | --- | --- |
| `Errors` | `org.springframework.validation.Errors` | Records object-level or field-level errors via `reject(...)`, `rejectValue(...)`. |
| `BindingResult` | `org.springframework.validation.BindingResult` | Holds errors after binding/validation, including `FieldError` and `ObjectError`. |
| `FieldError` | `org.springframework.validation.FieldError` | Describes an error on a property: field name, rejected value, codes, arguments, default message. |
| `ObjectError` | `org.springframework.validation.ObjectError` | Describes an object-level error, not necessarily tied to a single field. |
| `MessageCodesResolver` | `org.springframework.validation.MessageCodesResolver` | Generates a list of error codes from context (object, field, type). |
| `DefaultMessageCodesResolver` | `org.springframework.validation.DefaultMessageCodesResolver` | Default algorithm generating codes **from specific to general**. |
| `MessageSource` | `org.springframework.context.MessageSource` | Resolves messages by code, arguments, and `Locale`. |
| `MessageSourceResolvable` | `org.springframework.context.MessageSourceResolvable` | A message resolution request carrying candidate codes, arguments, and a default. |
| `DataBinder`/`WebDataBinder` | `org.springframework.validation`/`org.springframework.web.bind` | Binds form/query values, converts types, and records binding errors. |
| `@Valid`/`@Validated` | Jakarta/Spring | Triggers the corresponding validation; errors can be adapted into `BindingResult` by Spring. |

Two concepts must be kept separate:

1. **What is the error?** For example `typeMismatch` (string cannot be converted to `Integer`), `NotBlank` (constraint failing on missing text), `reserved` (custom validator code), `profile.invalid` (object-level error).
2. **How should it be displayed?** For example in Vietnamese “Tuổi phải là số nguyên” or in English “Age must be an integer”. `MessageSource` selects the wording using **candidate codes + Locale**.

An error code is not necessarily the translated message itself. `FieldError#getCode()` is usually the base code such as `typeMismatch`, while `FieldError#getCodes()` returns **the entire candidate list** shown in the priority table in the next section.

## 3. Default Algorithm for Field-Level Errors

### 3.1. Four Levels of Error Codes

With `DefaultMessageCodesResolver`, a field error typically generates four categories of codes in order:

| Priority | Pattern | Meaning |
| --- | --- | --- |
| 1 — most specific | `errorCode.objectName.fieldName` | Only this field on one specific object. |
| 2 | `errorCode.fieldName` | Any object with the same field name. |
| 3 | `errorCode.fieldType` | Any field with the same Java type. |
| 4 — most general | `errorCode` | Fallback for every case sharing the same base code. |

Suppose:

- Base code: `typeMismatch`.
- Object name: `profileForm`.
- Property: `age`.
- Java type of `age`: `java.lang.Integer`.

The order is:

~~~text
1. typeMismatch.profileForm.age
2. typeMismatch.age
3. typeMismatch.java.lang.Integer
4. typeMismatch
~~~

If the message bundle has all four keys, key **1** is used. If key 1 is absent, Spring tries key **2**, then **3**, and finally **4**. **There is no mechanism that picks based on “which translation sounds better”**; the candidate code order solely determines precedence.

Note the distinction between primitives and wrappers:

~~~text
int.class       -> typeMismatch.int
Integer.class   -> typeMismatch.java.lang.Integer
String.class    -> typeMismatch.java.lang.String
LocalDate.class -> typeMismatch.java.time.LocalDate
~~~

These lines illustrate the **`fieldType` segment** for different Java types. A Java property declared as `int` does not produce the same type-code sequence as an `Integer` property. Always inspect the **actual type** in `FieldError#getCodes()`/`BindingResult` rather than guessing from JSON types or old examples.

### 3.2. Direct Code Generation Without a Web Server

~~~java
DefaultMessageCodesResolver resolver =
        new DefaultMessageCodesResolver();

String[] codes = resolver.resolveMessageCodes(
        "typeMismatch",
        "profileForm",
        "age",
        Integer.class);

System.out.println(Arrays.toString(codes));
~~~

This is a snippet requiring imports for `DefaultMessageCodesResolver` and `Arrays`. Expected output:

~~~text
[typeMismatch.profileForm.age, typeMismatch.age, typeMismatch.java.lang.Integer, typeMismatch]
~~~

To check `int`, pass `int.class` to `resolveMessageCodes`. The official Javadoc illustrates the same four codes with object name `user`, field `age`, and type `int`. The difference in the type token is **exact and intentional**.

### 3.3. Why Does the Object Name Matter?

An application may have:

~~~java
@ModelAttribute("profileForm") ProfileForm profileForm
@ModelAttribute("supplierForm") SupplierForm supplierForm
~~~

These two lines are **illustrative parameter declarations**, not a complete handler. If both have a `name` field and both produce base code `NotBlank` or `required`, configuring:

~~~properties
required.profileForm.name=Please enter the user's name.
required.supplierForm.name=Please enter the supplier's name.
required.name=Please enter a name.
required=A value is required.
~~~

lets you display different wording while the validator simply calls `rejectValue("name", "required")`. If the object name at runtime is `profile` instead of `profileForm`, the key `required.profileForm.name` **will not match**. You can inspect the actual name via `BindingResult#getObjectName()`.

The object name may be explicitly specified by `@ModelAttribute("...")`, supplied via `DataBinder(target, "name")` in unit tests, or inferred by the framework from the argument/bean. **Do not hardcode messages against an unverified object name.**

## 4. Object-Level Errors Without a Field Name

Not every error belongs to a single field. For example, a profile may have a start date after its end date—both fields are individually valid, yet the **object-wide relationship is invalid**.

Spring `Errors#reject("profile.invalid")` creates an object/global error. `DefaultMessageCodesResolver` generates **two** candidate codes:

~~~text
profile.invalid.profileForm
profile.invalid
~~~

There is no `fieldName` or `fieldType` here. Translations can be configured as:

~~~properties
profile.invalid.profileForm=Profile data is inconsistent.
profile.invalid=Invalid data.
~~~

In a controller, call `BindingResult#getGlobalErrors()` for object-level errors, `getFieldErrors()` for field-level errors, and `getAllErrors()` when you need both.

Snippet:

~~~java
BeanPropertyBindingResult result =
        new BeanPropertyBindingResult(
                new ProfileForm(), "profileForm");

result.reject("profile.invalid");

ObjectError error = result.getGlobalError();
System.out.println(Arrays.toString(error.getCodes()));
~~~

Example output:

~~~text
[profile.invalid.profileForm, profile.invalid]
~~~

The snippet requires Spring imports and `ProfileForm`. If a class-level Bean Validation constraint produces a global error, the same code-priority rules apply once Spring adapts the constraint violation into `BindingResult`.

**Key distinction:** `FieldError#getField()` tells you which property failed, whereas `ObjectError` has no property name of its own. Do not coerce an object error into a synthetic `"global"` field and treat it like an actual DTO property.

## 5. Collections, Arrays, and Maps: Spring Also Generates Unindexed Codes

When a property path contains an index, Spring by default supports both **element-specific** codes and **unindexed** codes so a bundle can be shared across the whole collection.

Given:

~~~text
errorCode = typeMismatch
objectName = profileForm
field = contacts[0].email
fieldType = java.lang.String
~~~

The typical codes, in order (for an indexed path like the one above), are:

~~~text
typeMismatch.profileForm.contacts[0].email
typeMismatch.profileForm.contacts.email
typeMismatch.contacts[0].email
typeMismatch.contacts.email
typeMismatch.email
typeMismatch.java.lang.String
typeMismatch
~~~

Meaning:

- `typeMismatch.profileForm.contacts[0].email`: specifically element `[0]` on object `profileForm`.
- `typeMismatch.profileForm.contacts.email`: any element in `contacts` on that form.
- `typeMismatch.contacts[0].email`: the same element path regardless of object name.
- `typeMismatch.contacts.email`: any element with the same nested path.
- `typeMismatch.email`: any field named `email`.
- `typeMismatch.java.lang.String`: any `String` fields with that error.
- `typeMismatch`: all errors with the same base code.

Path syntax can become more complex with `items[3].price`, map keys, or nested collections. **Do not hardcode a fixed “always 4 codes” assumption for every field path**; indexed paths can produce extra codes. Test the actual list generated by `DefaultMessageCodesResolver` for your property.

Example bundle entry for the entire list:

~~~properties
typeMismatch.profileForm.contacts.email=An email in the contact list is invalid.
typeMismatch.email=Invalid email.
~~~

If a form has 10 contacts, you do not need to create 10 separate translations for `[0]`, `[1]`, ... just to reuse one message.

## 6. How Does `MessageSource` Choose a Sentence by Locale?

`MessageSource` is Spring's abstraction for retrieving internationalized messages. Common overloads:

~~~java
String getMessage(String code, Object[] args,
                  String defaultMessage, Locale locale);

String getMessage(String code, Object[] args, Locale locale);

String getMessage(MessageSourceResolvable resolvable,
                  Locale locale);
~~~

`FieldError`/`ObjectError` implements `MessageSourceResolvable`, so the most concise call is:

~~~java
String message = messageSource.getMessage(
        fieldError, Locale.forLanguageTag("vi"));
~~~

Spring tries each entry of `fieldError.getCodes()` in order to find a key with a translation in the requested locale. You can replace `Locale.forLanguageTag("vi")` with `Locale.ENGLISH` or the locale provided by the HTTP request's resolver.

**Do not do the following** if you want to preserve object/field/type priority:

~~~java
// Not ideal: uses only the base code, losing precedence information.
String text = messageSource.getMessage(
        fieldError.getCode(),
        null,
        fieldError.getDefaultMessage(),
        locale);
~~~

This call can be used if the application **intentionally** wants only the general code, but it ignores `getCodes()`. In standard cases, pass **the whole `FieldError`** (a `MessageSourceResolvable`) to preserve the fallback chain.

### 6.1. Message Arguments

Some constraints carry parameters: `@Size(min=3,max=20)`, `@Min(18)`. Spring errors/`MessageSource` can supply arguments to message templates. Inspect `getArguments()` and interpolation rules so placeholders like `{0}`, `{1}` are used with the right meaning. **Do not assume argument 0 is always `min` or the field name** across all validators; `arguments` may include a resolvable representing the field label.

Example message with application-controlled arguments:

~~~java
errors.rejectValue(
        "age",
        "age.minimum",
        new Object[] {18},
        "Invalid age");
~~~

With bundle:

~~~properties
age.minimum.profileForm.age=Age must be at least {0}.
age.minimum=Value must be at least {0}.
~~~

`MessageSource` substitutes `{0}` with `18`, while the locale determines the rest of the text. This is a **snippet inside a validator/controller** that has an `Errors errors` variable; not a standalone compilable function.

### 6.2. When No Code Is Found: Default Message and Fallback

A `MessageSourceResolvable` may carry a `defaultMessage`. When no matching key is found, Spring can return that default if provided. If you call an overload **without a default** and no message is found, `NoSuchMessageException` can be thrown.

Therefore, maintain **general fallback keys** in your bundles and define a policy for untranslated errors. Never return raw exception text or Java stack traces to clients when a message key is missing. Also, do not assume every `FieldError#getDefaultMessage()` already uses the HTTP request's locale: especially with Bean Validation, the default message may already have been interpolated in the validator's environment.

## 7. Sources of Error Codes: Binding, Spring Validator, and Bean Validation

Three common paths can populate `BindingResult`, each with potentially different **base codes**.

### 7.1. Binding/Conversion Errors: `typeMismatch`, `required`

When the binder receives `age=abc` for a Java `Integer age` property, conversion can fail and create a `FieldError` whose `getCode()` is typically `typeMismatch`.

~~~java
ProfileForm form = new ProfileForm();
DataBinder binder = new DataBinder(form, "profileForm");

binder.bind(new MutablePropertyValues(
        Map.of("age", "abc")));

FieldError ageError =
        binder.getBindingResult().getFieldError("age");

System.out.println(ageError.getCode());
System.out.println(Arrays.toString(ageError.getCodes()));
~~~

This snippet requires imports for `DataBinder`, `MutablePropertyValues`, `FieldError`, `Arrays`, `Map`, and the `ProfileForm` DTO. Main output for type `Integer`:

~~~text
typeMismatch
[typeMismatch.profileForm.age, typeMismatch.age, typeMismatch.java.lang.Integer, typeMismatch]
~~~

`setRequiredFields("age")` is another `DataBinder` configuration; it can produce the `required` code when a required input field is absent. Do not confuse binding's `required` with Jakarta Bean Validation's `@NotNull` — both may represent “missing data”, yet they come from **two different mechanisms**.

### 7.2. Errors from a Custom Spring `Validator`

A custom Spring `Validator` can do:

~~~java
@Override
public void validate(Object target, Errors errors) {
    ProfileForm form = (ProfileForm) target;

    if ("admin".equalsIgnoreCase(form.getName())) {
        errors.rejectValue("name", "reserved");
    }
}
~~~

This is a method snippet inside a class implementing `org.springframework.validation.Validator`. The base code `reserved` expands to:

~~~text
reserved.profileForm.name
reserved.name
reserved.java.lang.String
reserved
~~~

Simply define the corresponding keys in `messages_vi.properties`/`messages_en.properties`. The Spring `Validator` checks the condition; the message bundle determines the wording. You can also pass a `defaultMessage` to `rejectValue` if you want a display fallback.

### 7.3. Jakarta Bean Validation Errors: `NotBlank`, `NotNull`, `Min`

Given:

~~~java
public class ProfileForm {
    @NotBlank
    private String name;

    @NotNull
    private Integer age;
}
~~~

This snippet only illustrates annotations; the full file with getters/setters is in Section 9. When Spring MVC triggers Bean Validation via `@Valid @ModelAttribute` or `@Valid @RequestBody`, `ConstraintViolation`s are adapted into Spring errors inside `BindingResult`. Typical candidate codes:

~~~text
NotBlank.profileForm.name
NotBlank.name
NotBlank.java.lang.String
NotBlank

NotNull.profileForm.age
NotNull.age
NotNull.java.lang.Integer
NotNull
~~~

**Important distinction:** `@NotBlank(message = "{profile.name.required}")` uses **Jakarta Bean Validation's message interpolation mechanism**; this is conceptually different from `DefaultMessageCodesResolver`'s four-code strategy. Spring can integrate message sources with the validator depending on configuration, yet there are **two stages**: creating/interpolating the constraint message and resolving errors from `BindingResult` for the UI/API.

If you want to rely consistently on Spring's message code priority, provide keys like `NotBlank.profileForm.name` in `messages_vi.properties` and resolve via `MessageSource.getMessage(fieldError, locale)`. If you want custom constraint templates like `{profile.name.required}`, ensure Bean Validation's message interpolation is configured with the appropriate bundle/provider. Do not assume that having `messages_vi.properties` automatically configures Jakarta's `ValidationMessages` without integration testing.

## 8. Organizing Vietnamese/English Bundles

With Spring Boot's `MessageSource` auto-configuration, create these files under `src/main/resources/`:

~~~text
src/main/resources/
  application.properties
  messages.properties
  messages_vi.properties
  messages_en.properties
~~~

`messages.properties` is the **default bundle**. Spring Boot normally auto-configures a message source from the basename only when a default bundle exists; therefore, do not create only `messages_vi.properties` and `messages_en.properties` and expect every Boot app to detect them automatically.

### 8.1. `application.properties`

~~~properties
spring.messages.basename=messages
spring.messages.encoding=UTF-8
spring.messages.fallback-to-system-locale=false
~~~

Meaning:

- `basename` specifies the bundle Spring uses.
- `encoding=UTF-8` preserves Vietnamese diacritics.
- `fallback-to-system-locale=false` avoids falling back unpredictably to the server host's locale. The **request** locale is still determined by the MVC `LocaleResolver` or handler.

**Note on keys:** Spring message resolution is **exact-code and case-sensitive**. `NotBlank` differs from `notBlank`, `profileForm` differs from `ProfileForm`, and `java.lang.Integer` differs from `int`. A single mismatched character causes the resolver to try another candidate—easily causing the app to display an overly generic sentence.

In `.properties` files, save using true UTF-8. If an older build tool or IDE re-encodes files automatically, verify Vietnamese characters after the application reads them. When exposing messages to UI/API, do not blindly concatenate internal property names; design user-friendly, contextual sentences.

## 9. Complete Example: Java 17+, Spring Boot 3.x, Form Error i18n

Create a **Spring Boot 3.x**, **Java 17+** Maven project using Servlet Spring MVC. Every Java file uses package `com.example.errormessages`.

### 9.1. Dependencies

In a project with the Spring Boot parent/BOM, add:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-validation</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
~~~

The bundles in Section 8 belong to **this exact project**. No database or view/template controller is needed: responses are JSON.

### 9.2. `ErrorMessagesApplication.java`

File `src/main/java/com/example/errormessages/ErrorMessagesApplication.java`:

~~~java
package com.example.errormessages;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ErrorMessagesApplication {

    public static void main(String[] args) {
        SpringApplication.run(ErrorMessagesApplication.class, args);
    }
}
~~~

### 9.3. `ProfileForm.java`

File `src/main/java/com/example/errormessages/ProfileForm.java`:

~~~java
package com.example.errormessages;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

public class ProfileForm {

    @NotBlank
    private String name;

    @NotNull
    private Integer age;

    public ProfileForm() {
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public Integer getAge() {
        return age;
    }

    public void setAge(Integer age) {
        this.age = age;
    }
}
~~~

The DTO has two fields:

- `name` has `@NotBlank`, producing base code `NotBlank` when the user submits a blank string.
- `age` has type `Integer`; `age=abc` is a **conversion** error with code `typeMismatch`, while omitting `age` can trigger a `@NotNull` error with code `NotNull`.
- There are no sensitive fields such as `role` or `balance`. Production still needs dedicated DTOs and proper authorization rather than binding entities directly.

### 9.4. `ProfileController.java`

File `src/main/java/com/example/errormessages/ProfileController.java`:

~~~java
package com.example.errormessages;

import jakarta.validation.Valid;
import org.springframework.context.MessageSource;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.BindingResult;
import org.springframework.validation.FieldError;
import org.springframework.validation.ObjectError;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.util.List;
import java.util.Locale;
import java.util.Map;

@RestController
@RequestMapping("/api/profiles")
public class ProfileController {

    private final MessageSource messages;

    public ProfileController(MessageSource messages) {
        this.messages = messages;
    }

    @PostMapping(
            path = "/register",
            consumes = MediaType.APPLICATION_FORM_URLENCODED_VALUE)
    public ResponseEntity<?> register(
            @Valid @ModelAttribute("profileForm") ProfileForm form,
            BindingResult errors,
            Locale locale) {

        if ("admin".equalsIgnoreCase(form.getName())) {
            // Example custom rule using base code "reserved".
            errors.rejectValue("name", "reserved");
        }

        if (!errors.hasErrors()) {
            return ResponseEntity.ok(Map.of(
                    "status", "accepted"));
        }

        List<Issue> issues = errors.getAllErrors().stream()
                .map(error -> new Issue(
                        error instanceof FieldError fieldError
                                ? fieldError.getField()
                                : "",
                        error.getCode(),
                        messages.getMessage(error, locale)))
                .toList();

        return ResponseEntity.badRequest()
                .body(new ValidationResponse(issues));
    }

    public record Issue(
            String field, String code, String message) {
    }

    public record ValidationResponse(List<Issue> errors) {
    }
}
~~~

Design rationale:

1. `@ModelAttribute("profileForm")` sets an **explicit object name**. Bundle keys such as `NotBlank.profileForm.name` and `typeMismatch.profileForm.age` therefore have a clear target.
2. `@Valid` activates Bean Validation after binding, backed by the validation starter's provider.
3. `BindingResult errors` sits **immediately after** the form object so the controller receives field/object errors.
4. The `admin` rule avoids literal text: `errors.rejectValue("name", "reserved")` lets Spring generate `reserved.profileForm.name`, `reserved.name`, `reserved.java.lang.String`, `reserved`.
5. `messages.getMessage(error, locale)` accepts **the whole `ObjectError`**, since `ObjectError` implements `MessageSourceResolvable`; Spring tries all `getCodes()` in order.
6. `Locale locale` is resolved by Spring MVC via configured locale resolution (by default, `Accept-Language` can be used), allowing the API to return messages in the desired language.
7. The response includes the field, a **stable base code**, and the display sentence. It intentionally **omits `FieldError#getRejectedValue()`** to avoid exposing potentially sensitive input.

Example user form submission:

~~~http
POST /api/profiles/register
Content-Type: application/x-www-form-urlencoded
Accept-Language: vi

name=&age=24
~~~

The object binds successfully, but `@NotBlank` fails. With the bundles from Section 8, the expected response is:

~~~json
{
  "errors": [
    {
      "field": "name",
      "code": "NotBlank",
      "message": "Vui lòng nhập tên."
    }
  ]
}
~~~

The same request with `Accept-Language: en` returns `"Please enter a name."`. Sending `name=admin&age=24` causes the controller to add the `reserved` error and return `"Tên này không được sử dụng."` for locale `vi`.

**Note:** The HTTP status here is explicitly chosen as **400** by the controller, rather than a rule that every validation error in every app is handled inside a controller. If an adjacent `BindingResult` is omitted, Spring MVC may throw `MethodArgumentNotValidException` for `@ControllerAdvice` to handle.

## 10. Unit Tests: Verifying Code Order and Field-Type Lookup

Create file `src/test/java/com/example/errormessages/ErrorCodeResolutionTest.java`:

~~~java
package com.example.errormessages;

import org.junit.jupiter.api.Test;
import org.springframework.beans.MutablePropertyValues;
import org.springframework.context.support.ResourceBundleMessageSource;
import org.springframework.validation.BeanPropertyBindingResult;
import org.springframework.validation.DataBinder;
import org.springframework.validation.DefaultMessageCodesResolver;
import org.springframework.validation.FieldError;

import java.util.Arrays;
import java.util.Locale;
import java.util.Map;

import static org.junit.jupiter.api.Assertions.*;

class ErrorCodeResolutionTest {

    private ResourceBundleMessageSource messageSource() {
        var source = new ResourceBundleMessageSource();
        source.setBasename("messages");
        source.setDefaultEncoding("UTF-8");
        source.setFallbackToSystemLocale(false);
        return source;
    }

    @Test
    void fieldCodesAreOrderedFromSpecificToGeneral() {
        var resolver = new DefaultMessageCodesResolver();

        String[] actual = resolver.resolveMessageCodes(
                "typeMismatch", "profileForm", "age",
                Integer.class);

        assertArrayEquals(new String[] {
                "typeMismatch.profileForm.age",
                "typeMismatch.age",
                "typeMismatch.java.lang.Integer",
                "typeMismatch"
        }, actual);
    }

    @Test
    void primitiveFieldTypeProducesDifferentCode() {
        var resolver = new DefaultMessageCodesResolver();

        assertArrayEquals(new String[] {
                "typeMismatch.profileForm.age",
                "typeMismatch.age",
                "typeMismatch.int",
                "typeMismatch"
        }, resolver.resolveMessageCodes(
                "typeMismatch", "profileForm", "age",
                int.class));
    }

    @Test
    void globalErrorHasTwoCandidateCodes() {
        var binding = new BeanPropertyBindingResult(
                new ProfileForm(), "profileForm");

        binding.reject("profile.invalid");

        assertArrayEquals(new String[] {
                "profile.invalid.profileForm",
                "profile.invalid"
        }, binding.getGlobalError().getCodes());

        assertEquals("Thông tin hồ sơ không nhất quán.",
                messageSource().getMessage(
                        binding.getGlobalError(),
                        Locale.forLanguageTag("vi")));
    }

    @Test
    void fieldErrorUsesMostSpecificVietnameseCode() {
        var binding = new BeanPropertyBindingResult(
                new ProfileForm(), "profileForm");

        binding.rejectValue("name", "required");

        FieldError error = binding.getFieldError("name");
        assertNotNull(error);

        assertArrayEquals(new String[] {
                "required.profileForm.name",
                "required.name",
                "required.java.lang.String",
                "required"
        }, error.getCodes());

        assertEquals("Tên là bắt buộc cho biểu mẫu này.",
                messageSource().getMessage(
                        error, Locale.forLanguageTag("vi")));
    }

    @Test
    void fallbackUsesFieldNameWhenObjectSpecificCodeMissing() {
        var binding = new BeanPropertyBindingResult(
                new ProfileForm(), "otherForm");

        binding.rejectValue("name", "required");

        assertEquals("Cần cung cấp tên.",
                messageSource().getMessage(
                        binding.getFieldError("name"),
                        Locale.forLanguageTag("vi")));
    }

    @Test
    void actualDataBinderCreatesTypeMismatchForInteger() {
        var target = new ProfileForm();
        var binder = new DataBinder(target, "profileForm");

        binder.bind(new MutablePropertyValues(
                Map.of("age", "abc")));

        FieldError error = binder.getBindingResult()
                .getFieldError("age");

        assertNotNull(error);
        assertEquals("typeMismatch", error.getCode());

        assertTrue(Arrays.asList(error.getCodes())
                .contains("typeMismatch.java.lang.Integer"));

        assertEquals("Tuổi phải là số nguyên.",
                messageSource().getMessage(
                        error, Locale.forLanguageTag("vi")));
    }

    @Test
    void prefixCanNamespaceGeneratedCodes() {
        var resolver = new DefaultMessageCodesResolver();
        resolver.setPrefix("validation.");

        assertArrayEquals(new String[] {
                "validation.typeMismatch.profileForm.age",
                "validation.typeMismatch.age",
                "validation.typeMismatch.java.lang.Integer",
                "validation.typeMismatch"
        }, resolver.resolveMessageCodes(
                "typeMismatch", "profileForm", "age",
                Integer.class));
    }

    @Test
    void indexedFieldProducesIndexSpecificAndGenericCodes() {
        var resolver = new DefaultMessageCodesResolver();

        String[] codes = resolver.resolveMessageCodes(
                "typeMismatch", "profileForm",
                "contacts[0].email", String.class);

        assertArrayEquals(new String[] {
                "typeMismatch.profileForm.contacts[0].email",
                "typeMismatch.profileForm.contacts.email",
                "typeMismatch.contacts[0].email",
                "typeMismatch.contacts.email",
                "typeMismatch.email",
                "typeMismatch.java.lang.String",
                "typeMismatch"
        }, codes);
    }
}
~~~

The **8 unit tests** demonstrate:

- Order **object + field → field → field type → general**.
- Wrapper `Integer.class` and primitive `int.class` produce different type tokens.
- Object-level errors have only two candidate codes.
- `MessageSource` picks the Vietnamese translation via the **highest-priority code found**.
- When changing the object name to `otherForm` without `required.otherForm.name`, lookup falls back to `required.name`.
- `DataBinder` actually produces a `typeMismatch` error when `age=abc`.
- `setPrefix("validation.")` changes the generated code names without changing the validator's base business code.
- Indexed paths support both element-specific and unindexed codes.

The `DataBinder` test here only verifies **binding/conversion**; it does not run `@Valid`. The MVC tests below verify **Bean Validation** and request locale handling.

## 12. Customizing the Error Code Strategy

### 12.1. Using a Prefix to Avoid Code Collisions

A large project may use multiple bundles containing `required`, `invalid`, `typeMismatch`. You can group codes with a prefix:

~~~java
DefaultMessageCodesResolver resolver =
        new DefaultMessageCodesResolver();

resolver.setPrefix("validation.");

String[] codes = resolver.resolveMessageCodes(
        "typeMismatch", "profileForm", "age",
        Integer.class);
~~~

Result:

~~~text
validation.typeMismatch.profileForm.age
validation.typeMismatch.age
validation.typeMismatch.java.lang.Integer
validation.typeMismatch
~~~

When using a prefix, `messages*.properties` files must also use that prefix. Enabling the prefix in code without updating the bundles will prevent `MessageSource` from finding the old keys.

To apply this **to MVC argument binding application-wide**, provide a `MessageCodesResolver` via `WebMvcConfigurer#getMessageCodesResolver()`:

~~~java
@Configuration
public class ErrorCodeMvcConfig implements WebMvcConfigurer {

    @Override
    public MessageCodesResolver getMessageCodesResolver() {
        var resolver = new DefaultMessageCodesResolver();
        resolver.setPrefix("validation.");
        return resolver;
    }
}
~~~

This is an **alternative configuration snippet** requiring Spring imports. Do not add this class to the Section 9 example while the bundles still use **unprefixed** keys. In a real setup, test both binding and validation errors to ensure existing i18n keys are not broken.

### 12.2. Customizing Code Formatting

`DefaultMessageCodesResolver` also supports `setMessageCodeFormatter(...)` and the `DefaultMessageCodesResolver.Format` enum. By default, the base code comes first, e.g., `typeMismatch.profileForm.age`. Changing the formatter alters **how codes are assembled** according to policy; the team must align conventions with whoever maintains the bundles.

Do not arbitrarily write a custom `MessageCodesResolver` just to change one sentence; adding a key at `errorCode.object.field` is usually enough. Changing code rules broadly can make existing translations unreachable and affect many screens.

### 12.3. Local Configuration in DataBinder

When invoking `DataBinder` manually in a unit test or a service outside MVC, the binder also provides `setMessageCodesResolver(...)` to choose a strategy. Consequently, binder test results can differ if you configure a resolver different from MVC's. To debug, inspect `bindingResult.getFieldError(field).getCodes()` from the **actual binder** that processed the request.

## 13. Relationship to `@ControllerAdvice` and REST Error Contracts

If a handler does not declare `BindingResult` immediately after `@Valid @ModelAttribute` or `@Valid @RequestBody`, Spring MVC may throw `MethodArgumentNotValidException`. A `@RestControllerAdvice` can read `ex.getBindingResult()` and use the same `MessageSource`.

Snippet:

~~~java
@RestControllerAdvice
public class GlobalValidationAdvice {

    private final MessageSource source;

    public GlobalValidationAdvice(MessageSource source) {
        this.source = source;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<?> handle(
            MethodArgumentNotValidException ex,
            Locale locale) {

        List<String> messages =
                ex.getBindingResult().getAllErrors()
                        .stream()
                        .map(error -> source.getMessage(
                                error, locale))
                        .toList();

        return ResponseEntity.badRequest()
                .body(Map.of("messages", messages));
    }
}
~~~

This is an **optional illustrative class** requiring imports; it is not part of the runnable source above. Note that Spring MVC's method-level validation may throw `HandlerMethodValidationException`, and malformed JSON bodies may throw `HttpMessageNotReadableException`. Do not lump every exception into `MethodArgumentNotValidException`.

**Some API designs** return only stable codes like `NAME_REQUIRED` and leave message translation to the frontend. That is also a valid design, especially when multiple clients need multilingual or versioned error contracts. When the server translates messages, obtain `Locale` from the right source and avoid letting a cache/CDN mix `vi` and `en` responses.

## 14. Security and Translation Maintainability

### 14.1. Never Expose Rejected Input

`FieldError#getRejectedValue()` may contain passwords, tokens, email addresses, ID numbers, or user-submitted data. Even when using message codes for translation, **do not append raw rejected values to messages or error responses** without a redaction policy.

Unsafe example:

~~~java
// Should not return rejectedValue directly to the client.
String message = "Invalid: "
        + fieldError.getRejectedValue();
~~~

Better: return an approved field identifier, error code, and controlled text; do not expose exception stack traces or internal class names in the API. Property names in error responses should also match **public API fields** rather than leaking internal entity paths.

### 14.2. Avoid Excessive Specialized Codes

If every screen defines its own dedicated key, bundles bloat and translations become hard to synchronize. Good precedence guidelines:

1. Use `errorCode.object.field` **only when there is truly a special message** for that context.
2. Use `errorCode.field` for a field appearing across multiple forms with the same meaning.
3. Use `errorCode.fieldType` for uniform type-conversion wording, such as all `Integer` fields.
4. Always provide `errorCode` as a fallback so technical text is never shown when a key is missing.

In the example, `typeMismatch.profileForm.age` is specific because it mentions “Age”; `typeMismatch.java.lang.Integer` is the fallback “Please enter a whole number”; and `typeMismatch` is the final fallback “Invalid input type”.

### 14.3. Testing Fallbacks and Locales

For multilingual data, include tests covering:

- Most specific key present.
- Object-level key absent while field-level key is present.
- Field-level key absent while type-level or generic key is present.
- `Locale.forLanguageTag("vi")` and `Locale.ENGLISH` for the same error.
- Global (object-level) codes, indexed (collection) codes, and primitive/wrapper types.
- Unicode and Vietnamese diacritics in `.properties` files.
- Message arguments `{0}` for limits like age/size.
- An intentionally missing key to ensure the fallback policy does not leak stack traces.
- Object name or field renaming after refactoring.

Do not rely on the ordering of `getAllErrors()` when multiple validators can record errors simultaneously; sort the output if a deterministic contract is required. Also, never treat translated text as the sole key for frontend business branching: use error codes with distinct semantics.

### 14.4. Distinguishing Request Locale from Server Default Locale

Spring MVC can determine `Locale` from HTTP `Accept-Language` with default configuration, though an application may use a custom `LocaleResolver`, cookie/session preferences, or user settings. `MessageSource#getMessage(...)` always uses **the passed-in `Locale`**, so direct test results do not depend on an HTTP request when calling `Locale.forLanguageTag("vi")` explicitly.

The `spring.messages.fallback-to-system-locale=false` option controls **resource bundle** fallback; it does not mean “every request automatically becomes Vietnamese”. When a backend serves multiple regions, decide on the Locale source, default locale, and the `Vary: Accept-Language` header if caching depends on that header.

## 15. Common Errors and How to Fix Them

| Symptom | Possible Cause | Diagnosis/Fix |
| --- | --- | --- |
| Always shows “Invalid value” despite custom keys | Mismatched object name, field name, or letter casing. | Safely log `getObjectName()`, `getField()`, `getCodes()`; compare against bundle. |
| `typeMismatch.int` does not apply | The actual property is `Integer`, not primitive `int`. | Inspect `getCodes()`; use `typeMismatch.java.lang.Integer`. |
| Error code is `NotBlank` but bundle has `notblank` | Message keys are case-sensitive. | Use `NotBlank.profileForm.name` or keys matching `codes`. |
| `messages_vi.properties` exists but Boot ignores it | Missing `messages.properties` or wrong basename config. | Add default bundle; check `spring.messages.basename`. |
| Renaming `@ModelAttribute("profileForm")` to `("profile")` breaks specific translation | Key references the old object name. | Update keys or keep contract names stable; test locales. |
| Array item fails but only `[0]` key was written | Other elements lack specific translations. | Add unindexed path key or field/type fallbacks. |
| Calling `getMessage(error.getCode(), ...)` only shows generic text | Bypassed `getCodes()`. | Pass `ObjectError`/`FieldError` directly to `getMessage(error, locale)`. |
| Sending malformed JSON expecting `typeMismatch.profileForm.age` | JSON decoder failed before Spring `WebDataBinder`. | Distinguish `HttpMessageNotReadableException` from form binding errors. |
| Confusing `@NotNull` with `required` error | Bean Validation and `DataBinder` required fields are separate mechanisms. | Inspect `getCode()` and know its origin. |
| `ValidationMessages_vi.properties` exists but Spring keys do not apply | Confusing Bean Validation interpolation with Spring error-code resolution. | Separate both stages; configure validator/`MessageSource` intentionally. |
| Client receives English despite `Accept-Language: vi` | `LocaleResolver`/bundle fallback or custom handler ignores locale. | Test controller locale; pass proper `Locale` to `MessageSource`. |
| Message contains submitted password | Handler echoes `rejectedValue` or logs full exception. | Redact input; return stable codes and text. |
| Codes are prefixed while bundle uses old keys | `setPrefix("validation.")` enabled without updating keys. | Synchronize resolver and bundles; add integration tests. |

## 16. Implementation Checklist

- [ ] Distinguish base codes (`typeMismatch`, `required`, `NotBlank`, custom codes) from candidate code lists.
- [ ] Understand the precedence **object.field → field → type → general** for field errors.
- [ ] Understand that global errors only have **object → general**.
- [ ] Verify the binder/`@ModelAttribute` object name, exact field name, and Java type.
- [ ] For lists/maps/arrays, inspect the extra codes generated for indexed and unindexed paths.
- [ ] Use `MessageSource#getMessage(ObjectError, Locale)` to leverage all fallback codes.
- [ ] Provide `messages.properties` along with `messages_vi.properties`/`messages_en.properties` in UTF-8.
- [ ] Verify which `MessageSource`/locale resolution the framework actually uses.
- [ ] Provide general fallbacks and a missing-message policy that never leaks Java stack traces.
- [ ] Place `BindingResult` immediately after the validated object to handle errors locally in MVC.
- [ ] Do not confuse binding `typeMismatch` with JSON decoding errors or Jakarta Bean Validation interpolation.
- [ ] Run unit tests for `DefaultMessageCodesResolver` and MockMvc tests for request locales.
- [ ] Never return rejected values or PII; keep a clear versioning strategy for public error codes and wording.

**Conclusion:** Spring does not force every validation error to have only one code string. `DefaultMessageCodesResolver` generates **multiple candidates ordered by specificity**, and `MessageSource` chooses **the message by Locale**. Designing object names, field names, and Java types carefully lets you localize messages accurately while reusing validators and binders, and keeping fallbacks broad enough so translations do not break when adding forms or refactoring.
