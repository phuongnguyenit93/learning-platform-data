# Validation Does Not Replace Database Constraints or Business Rules

## 1. The Problem: Why Can `@Valid` Pass While Data Is Still Wrong?

In Spring MVC, `@Valid`, `@Validated`, and Jakarta Bean Validation catch requests with missing fields, invalid formats, or out-of-range values. For instance, `@Email` validates email format, `@NotBlank` validates non-empty strings, and `@Min(1)` checks minimum numbers. This is an essential input-defense layer, yet **passing validation does not guarantee the action is authorized, the data is unique, or the database can commit**.

Consider account registration:

- Request A submits `lan@example.org` and passes `@Email`.
- Service A checks that the email is not yet in the database.
- Almost simultaneously, Request B also checks that this email does not exist yet.
- Both requests try to insert a new row. If the database lacks `UNIQUE`, both can be saved.
- If the account has not verified its email, the service must also reject an activation request even though the email format is valid.

These are **three distinct problem categories**: input data validation, business rules grounded in trusted state, and database-level data constraints.

**Goal:** know what each layer must enforce, prevent TOCTOU (time-of-check to time-of-use) flaws, use `@Transactional` and constraints appropriately, handle exceptions safely, and write tests providing evidence for all three layers.

This article uses Java 17, Spring Framework 6.x, Spring Boot 3.x, Spring MVC, Jakarta Validation, Spring Data JPA, and a relational database. Illustrative fragments lacking full types/imports are explicitly noted; the Maven example in section 6 is a standalone deployable and testable project.

## 2. Three Control Layers with Distinct Responsibilities

| Layer | Question | Example | What it does NOT guarantee on its own |
| --- | --- | --- | --- |
| **Input validation** | Does the request value match format/shape/range? | `@NotBlank`, `@Email`, `@Size`, `@Min` | Access rights, uniqueness, concurrency |
| **Business/domain checks** | Is the action valid given state, actor, and resource? | Activate only when email is verified; never overbook seats; only owner may edit | DB atomicity without transaction design |
| **Database constraints** | Does post-INSERT/UPDATE/COMMIT state satisfy data invariants? | `UNIQUE`, `NOT NULL`, `FOREIGN KEY`, `CHECK`, primary key | Actor/permission logic, full business workflow |

A sufficiently secure API does not pick **one of the three**—it combines them:

```text
Client sends untrusted data
           |
           v
  DTO + input validation
           |
           v
  Service/domain + authorization
           |
           v
  Transaction / concurrency control
           |
           v
  Database: PK, UNIQUE, FK, NOT NULL, CHECK
           |
           v
  Commit succeeds -> success response
           |
           +--> Failure -> rollback and safe error mapping
```

### 2.1. `@Valid` knows only the constraints you give it

```java
public record RegisterRequest(
        @NotBlank @Email String email,
        @NotBlank @Size(max = 80) String displayName) {
}
```

This is a DTO fragment (requiring `jakarta.validation.constraints.*` imports). Spring MVC can use `@Valid @RequestBody RegisterRequest` to reject malformed emails. Yet `@Email` cannot tell you whether the email is verified, still unclaimed in the database, owned by the caller, or eligible under registration rules.

### 2.2. Business invariants usually require stored state

For example: an account has state `PENDING` or `ACTIVE`; activation is allowed only once verified. That condition must never come from a client-asserted field:

```java
// Fragment inside domain/service:
if (!account.isEmailVerified()) {
    throw new BusinessRuleException("EMAIL_NOT_VERIFIED");
}
if (account.getState() != AccountState.PENDING) {
    throw new BusinessRuleException("INVALID_STATE_TRANSITION");
}
```

The `emailVerified` flag must be updated by a **trusted verification workflow**, never by `"verified":true` in a request. Whether an account may be activated also requires **authorization** based on actor and resource.

### 2.3. The database protects write paths beyond HTTP

Beyond controllers, systems have scheduled jobs, message consumers, import scripts, admin tools, other services, and direct SQL. Placing `@Valid` only on controllers leaves those paths unguarded. A **UNIQUE constraint** in the database protects every writer sharing that table, provided the constraint actually exists and is enforced.

Illustrative DDL with foundational protections:

```sql
CREATE TABLE accounts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email_normalized VARCHAR(254) NOT NULL,
    display_name VARCHAR(80) NOT NULL,
    state VARCHAR(16) NOT NULL,
    email_verified BOOLEAN NOT NULL,
    version BIGINT NOT NULL,
    CONSTRAINT uk_accounts_email UNIQUE (email_normalized),
    CONSTRAINT ck_accounts_state
      CHECK (state IN ('PENDING', 'ACTIVE'))
);
```

**This is illustrative SQL**, not the migration for the project below; syntax and DDL must be adapted to your DBMS. It distinguishes `NOT NULL`, `UNIQUE`, and `CHECK` from DTO constraints. `CHECK` guarantees `state` belongs to the permitted set, yet knows nothing about whether the actor has permission to activate or how the email was verified.

## 3. Why Does Check-Then-Insert Still Have a Race Condition?

Code pattern:

```java
if (repository.existsByEmailNormalized(email)) {
    throw new DuplicateEmailException();
}
repository.save(account);
```

This is a **fragment**. It is useful as a friendly precheck, yet **insufficient to prevent duplicates**.

```text
Time             Transaction A                 Transaction B
----------------------------------------------------------------
T1               exists(email) -> false
T2                                             exists(email) -> false
T3               INSERT same email
T4                                             INSERT same email
T5               COMMIT
T6                                             COMMIT / CONFLICT

Without UNIQUE: both can commit two rows.
With UNIQUE: the database blocks one of the two writes/commits.
```

Between time-of-check and time-of-use, data can change. This is a **TOCTOU** flaw. `@Transactional` does not automatically turn `SELECT exists` + `INSERT` into an atomic check-and-write under default isolation in databases.

**Better handling:**

1. Canonicalize the email per policy (e.g., `strip + lowercase`) consistently.
2. Precheck `existsBy...` if you want early feedback.
3. Put **UNIQUE on the exact column/expression representing business identity**.
4. Let the database be the final arbiter under concurrency.
5. Translate **known constraint failures** into safe API codes after transaction failure; never expose SQL/driver messages.

If business rules treat `LAN@EXAMPLE.ORG` and `lan@example.org` as the same email, a case-sensitive unique constraint on raw values is insufficient. The demo stores `emailNormalized`. Normalization policies in real products must be specified clearly; never assume every email system or collation treats Unicode/casing identically.

### When do DB exceptions surface?

JPA has a persistence context and flush lifecycle:

- `save(...)` may not have sent all SQL to the database yet.
- `saveAndFlush(...)` forces an early flush so many DB errors surface before the method returns.
- **Flush does not equal commit.** A constraint can be evaluated at commit depending on the database and constraint deferrability.
- Transaction rollback can occur when the transactional proxy exits the method, not solely at the `save()` line.

Therefore, never send confirmation emails, message-queue events, or "successfully persisted" responses on the assumption that calling `save()` guarantees commit. For external side effects, consider transactional outboxes, post-commit listeners, and idempotency.

## 4. Distinguishing Validation Annotations, JPA Metadata, and Real Constraints

| Tool | Primary role | Limitation |
| --- | --- | --- |
| `@Email` | Input format | Does not verify ownership or uniqueness |
| `@NotBlank` | String value must have non-whitespace content | Does not create `NOT NULL` across all DB paths |
| `@Min(1)` | Number meets lower bound | Does not protect stock/balances under concurrency |
| `@Valid` | Requests cascading/object validation | Not authorization |
| `@Column(nullable=false)` | JPA/DDL metadata generated when configured | Does not replace real migrations if schema already exists |
| `@Table(uniqueConstraints=...)` | JPA metadata for schema generation | Must verify real `UNIQUE` in prod DB |
| `@Version` | JPA optimistic locking | Does not protect multi-row invariants |
| `@Transactional` | Transaction scope/rollback | Does not generate `CHECK`, `UNIQUE`, `FK`, or locking strategies |

A Hibernate/JPA provider can also trigger Bean Validation before entity insert/update in its lifecycle, yet **never treat this as a replacement for DB constraints**. A SQL client or another service writing to the same table will not run your Java process's Jakarta Validator.

In production, use migrations like Flyway/Liquibase, verify the schema was applied, and never enable `spring.jpa.hibernate.ddl-auto=create-drop` on real data.

## 5. Which Rule Should Be Enforced at Which Layer?

| Rule | DTO/HTTP | Service/domain | Database |
| --- | --- | --- | --- |
| Display name is 1–80 chars | `@NotBlank`, `@Size` | Trim/normalize | `NOT NULL`, length, and `CHECK` if needed |
| Email is well-formed | `@Email` | Canonicalize, internal policy | Sufficient column length |
| Email is unique | No guarantee | Friendly precheck | **UNIQUE** |
| Order has valid customer | Check ID shape | Verify association + authorization | **FOREIGN KEY** |
| Never oversell stock | Positive request quantity | Reservation logic/transaction | Atomic conditional `UPDATE`, `CHECK`/locking |
| Non-negative balance | Positive spend amount | Business balance rule | **CHECK** and atomic update |
| Only owner can edit | No | **Authorization** | Row-level security if designed |
| Activate only if verified | Never trust client | **State machine** | `CHECK`/triggers can assist |
| Prevent lost updates | No | Retry/conflict policy | **`@Version` / locking** |

Do not try to encode every domain rule as a Jakarta custom constraint hitting the database. If a custom validator calls `exists()`, race conditions remain—and validation acquires unpredictable I/O side effects. Business logic belongs at a properly transacted boundary.

## 6. Runnable Project: Spring Boot MVC + JPA + H2

The example below implements an account registration and activation flow:

- `POST /accounts`: validates JSON, normalizes email, prechecks duplicates, and persists `AccountEntity`.
- `GET /accounts/{id}`: reads current state.
- `POST /accounts/{id}/activate`: allows activating only a `PENDING` account verified by a trusted source.
- The entity defines `UNIQUE` on normalized email, `NOT NULL` columns, and `@Version`.
- The exception handler separates input errors, business conflicts, and persistence conflicts.
- Tests exercise both MockMvc and direct repository writes to prove `UNIQUE` still holds when the controller/precheck is bypassed.

**Security note:** this demo **does not implement login, a real email verification workflow, or per-`accountId` authorization**; never expose it directly to the Internet. It intentionally isolates validation, business rules, and DB constraints for learning.

### 6.6. src/main/java/demo/AccountEntity.java

```java
package demo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;
import jakarta.persistence.Version;

enum AccountState {
    PENDING, ACTIVE
}

@Entity
@Table(
    name = "accounts",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_account_email_normalized",
        columnNames = "email_normalized"
    )
)
public class AccountEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email_normalized",
            nullable = false, length = 254)
    private String emailNormalized;

    @Column(nullable = false, length = 80)
    private String displayName;

    @Column(nullable = false)
    private boolean emailVerified;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 16)
    private AccountState state;

    @Version
    private Long version;

    protected AccountEntity() {
        // Constructor for JPA.
    }

    private AccountEntity(String email, String name) {
        this.emailNormalized = email;
        this.displayName = name;
        this.emailVerified = false;
        this.state = AccountState.PENDING;
    }

    public static AccountEntity pending(
            String normalizedEmail, String displayName) {
        return new AccountEntity(normalizedEmail, displayName);
    }

    // Only a trusted verification workflow may call this.
    // Package-private so tests in package demo can simulate it.
    void markEmailVerified() {
        this.emailVerified = true;
    }

    void activate() {
        this.state = AccountState.ACTIVE;
    }

    public Long getId() {
        return id;
    }

    public String getEmailNormalized() {
        return emailNormalized;
    }

    public String getDisplayName() {
        return displayName;
    }

    public boolean isEmailVerified() {
        return emailVerified;
    }

    public AccountState getState() {
        return state;
    }

    public Long getVersion() {
        return version;
    }
}
```

Analysis:

- `@Table(uniqueConstraints=...)` lets Hibernate create the DB `UNIQUE` constraint under demo DDL settings.
- `nullable=false` declares DB `NOT NULL` for email, displayName, verified flag, and state.
- `@Version` enables optimistic locking for updates through the JPA provider.
- Domain state initializes to `PENDING` and `emailVerified=false`, with **no public setters** letting HTTP clients pick state.
- `markEmailVerified()` exists solely to simulate trusted verification in tests; the project exposes no arbitrary email-verification endpoint.
- Never put `@Email` on an entity and treat it as `UNIQUE`; they are different protections.
- When deploying via migrations, verify the real unique index/constraint exists rather than inferring from source annotations.

### 6.10. src/main/java/demo/AccountService.java

```java
package demo;

import java.util.Locale;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AccountService {

    private final AccountRepository repository;

    public AccountService(AccountRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public AccountView register(SignupRequest request) {
        String normalized = request.email()
                .strip()
                .toLowerCase(Locale.ROOT);

        if (repository.existsByEmailNormalized(normalized)) {
            throw new DuplicateEmailException();
        }

        AccountEntity account = repository.saveAndFlush(
                AccountEntity.pending(
                        normalized,
                        request.displayName().strip()
                )
        );

        return AccountView.from(account);
    }

    @Transactional(readOnly = true)
    public AccountView find(long id) {
        AccountEntity entity = repository.findById(id)
                .orElseThrow(AccountNotFoundException::new);

        return AccountView.from(entity);
    }

    @Transactional
    public AccountView activate(long id) {
        AccountEntity entity = repository.findById(id)
                .orElseThrow(AccountNotFoundException::new);

        if (entity.getState() != AccountState.PENDING) {
            throw new BusinessRuleException("ALREADY_ACTIVE");
        }

        if (!entity.isEmailVerified()) {
            throw new BusinessRuleException("EMAIL_NOT_VERIFIED");
        }

        entity.activate();
        repository.flush();
        return AccountView.from(entity);
    }
}
```

Reading the code layer by layer:

1. `SignupRequest` enters the service after HTTP validation, though the service needs additional input defense if called from jobs, consumers, or unit tests; the example builds a single HTTP path.
2. `strip().toLowerCase(Locale.ROOT)` defines a canonicalization policy. For `UNIQUE` to hold, **every write path** must apply this policy or the database must enforce the canonicalized identity.
3. `existsByEmailNormalized` lets ordinary duplicates return a clear code, though a race still exists.
4. `saveAndFlush` flushes to the DB before the method returns; `UNIQUE` is the final line if two requests both pass the precheck. **Flush is not yet commit.**
5. `activate` checks **trusted stored state**, never accepting `verified=true` from clients.
6. `@Transactional` wraps the use case in a transaction; throwing a runtime exception rolls back by default.
7. `repository.flush()` in `activate` surfaces optimistic-lock/DB errors earlier on many providers, though commit-time failures must still be handled.

**Never treat `@Version` as a universal concurrency solution:** it supports lost-update detection on a versioned entity, yet does not prevent cross-row overselling or enforce uniqueness on insert.

### 6.11. src/main/java/demo/AccountController.java

```java
package demo;

import java.net.URI;

import jakarta.validation.Valid;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/accounts")
public class AccountController {

    private final AccountService accounts;

    public AccountController(AccountService accounts) {
        this.accounts = accounts;
    }

    @PostMapping
    public ResponseEntity<AccountView> register(
            @Valid @RequestBody SignupRequest request) {

        AccountView view = accounts.register(request);
        return ResponseEntity.status(HttpStatus.CREATED)
                .location(URI.create("/accounts/" + view.id()))
                .body(view);
    }

    @GetMapping("/{id}")
    public AccountView find(@PathVariable long id) {
        return accounts.find(id);
    }

    @PostMapping("/{id}/activate")
    public AccountView activate(@PathVariable long id) {
        return accounts.activate(id);
    }
}
```

The `@Valid @RequestBody SignupRequest` signature triggers individual object validation on the DTO, so constraint failures typically raise `MethodArgumentNotValidException`. When direct constraints appear on method parameters such as `@Min(1) @RequestParam int page`, Spring MVC 6.1+ can raise `HandlerMethodValidationException`; handle both branches in systems mixing the two styles.

A syntactically invalid JSON body is not a Bean Validation failure, but a converter error such as `HttpMessageNotReadableException`. When an API needs a consistent error schema, handle it separately and never misattribute it to `@Email`.

### 6.12. src/main/java/demo/ErrorAdvice.java

```java
package demo;

import java.util.List;

import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

@RestControllerAdvice
public class ErrorAdvice extends ResponseEntityExceptionHandler {

    public record ApiError(
            String code,
            String message,
            List<String> fields) {
    }

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        List<String> fields = ex.getBindingResult()
                .getFieldErrors().stream()
                .map(FieldError::getField)
                .distinct().sorted().toList();

        return new ResponseEntity<>(
                new ApiError(
                        "INPUT_INVALID",
                        "Submitted data is invalid",
                        fields),
                headers, status);
    }

    @ExceptionHandler(DuplicateEmailException.class)
    public ResponseEntity<ApiError> duplicate() {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "EMAIL_ALREADY_EXISTS",
                        "Email already registered",
                        List.of("email")));
    }

    @ExceptionHandler(AccountNotFoundException.class)
    public ResponseEntity<ApiError> missing() {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError(
                        "ACCOUNT_NOT_FOUND",
                        "Account does not exist",
                        List.of()));
    }

    @ExceptionHandler(BusinessRuleException.class)
    public ResponseEntity<ApiError> business(
            BusinessRuleException ex) {

        String msg = switch (ex.code()) {
            case "EMAIL_NOT_VERIFIED" ->
                    "Email must be verified before activation";
            case "ALREADY_ACTIVE" ->
                    "Account is already active";
            default -> "Transition is not allowed";
        };

        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        ex.code(), msg, List.of()));
    }

    @ExceptionHandler(OptimisticLockingFailureException.class)
    public ResponseEntity<ApiError> stale() {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "CONCURRENT_MODIFICATION",
                        "Resource changed; reload and retry",
                        List.of()));
    }

    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<ApiError> integrity() {
        // Illustrative fallback; never assume every DB error is
        // a duplicate email or a client input error.
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "DATA_CONFLICT",
                        "Write violates a data constraint",
                        List.of()));
    }
}
```

**Critical in real deployments:** `DataIntegrityViolationException` can represent `UNIQUE`, `NOT NULL`, `FK`, `CHECK`, or other errors. Never lump them all into `EMAIL_ALREADY_EXISTS`. The demo returns `DATA_CONFLICT` with 409 for simplicity; production should map **known unique constraints** to matching business conflicts, while unexpected persistence faults may warrant **5xx** and redacted internal logs. Exactly which exception surfaces at flush/commit also depends on the provider and transaction manager.

Never serialize `ex.getMessage()` directly, as it can leak SQL, table names, key values, or PII. Public errors use stable codes; user-facing messages can be localized via `MessageSource`.

## 7. Layer-by-Layer Testing with MockMvc and the Database

### 7.1. src/test/java/demo/AccountLifecycleTest.java

```java
package demo;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class AccountLifecycleTest {

    @Autowired MockMvc mvc;
    @Autowired ObjectMapper objectMapper;
    @Autowired AccountRepository repository;

    @BeforeEach
    void clean() {
        repository.deleteAll();
    }

    private long create(String email) throws Exception {
        String json = objectMapper.writeValueAsString(
                new SignupRequest(email, "Lan")
        );
        MvcResult result = mvc.perform(post("/accounts")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content(json))
                .andExpect(status().isCreated())
                .andReturn();

        JsonNode body = objectMapper.readTree(
                result.getResponse().getContentAsString()
        );
        return body.get("id").asLong();
    }

    @Test
    void validInputCreatesPendingAccount() throws Exception {
        mvc.perform(post("/accounts")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                            {"email":"LAN@EXAMPLE.ORG",
                             "displayName":"Lan"}
                            """))
                .andExpect(status().isCreated())
                .andExpect(jsonPath("$.email")
                        .value("lan@example.org"))
                .andExpect(jsonPath("$.state").value("PENDING"))
                .andExpect(jsonPath("$.emailVerified")
                        .value(false));

        assertEquals(1, repository.count());
    }

    @Test
    void beanValidationRejectsBadEmail() throws Exception {
        mvc.perform(post("/accounts")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                            {"email":"not-an-email",
                             "displayName":"Lan"}
                            """))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.code")
                        .value("INPUT_INVALID"))
                .andExpect(jsonPath("$.fields[0]")
                        .value("email"));

        assertEquals(0, repository.count());
    }

    @Test
    void blankNameRejectedBeforePersistence() throws Exception {
        mvc.perform(post("/accounts")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                            {"email":"lan@example.org",
                             "displayName":" "}
                            """))
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("$.fields[0]")
                        .value("displayName"));

        assertEquals(0, repository.count());
    }

    @Test
    void servicePrecheckRejectsNormalizedDuplicate()
            throws Exception {
        create("LAN@EXAMPLE.ORG");

        mvc.perform(post("/accounts")
                        .contentType(MediaType.APPLICATION_JSON)
                        .content("""
                            {"email":"lan@example.org",
                             "displayName":"Mai"}
                            """))
                .andExpect(status().isConflict())
                .andExpect(jsonPath("$.code")
                        .value("EMAIL_ALREADY_EXISTS"));

        assertEquals(1, repository.count());
    }

    @Test
    void unverifiedAccountCannotActivate()
            throws Exception {
        long id = create("lan@example.org");

        mvc.perform(post("/accounts/" + id + "/activate"))
                .andExpect(status().isConflict())
                .andExpect(jsonPath("$.code")
                        .value("EMAIL_NOT_VERIFIED"));

        mvc.perform(get("/accounts/" + id))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.state")
                        .value("PENDING"));
    }

    @Test
    void verifiedAccountCanActivate() throws Exception {
        long id = create("lan@example.org");

        // Only tests simulate trusted email verification.
        AccountEntity entity = repository.findById(id)
                .orElseThrow();
        entity.markEmailVerified();
        repository.saveAndFlush(entity);

        mvc.perform(post("/accounts/" + id + "/activate"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.state")
                        .value("ACTIVE"))
                .andExpect(jsonPath("$.emailVerified")
                        .value(true));
    }

    @Test
    void cannotActivateTwice() throws Exception {
        long id = create("lan@example.org");

        AccountEntity entity = repository.findById(id)
                .orElseThrow();
        entity.markEmailVerified();
        repository.saveAndFlush(entity);

        mvc.perform(post("/accounts/" + id + "/activate"))
                .andExpect(status().isOk());

        mvc.perform(post("/accounts/" + id + "/activate"))
                .andExpect(status().isConflict())
                .andExpect(jsonPath("$.code")
                        .value("ALREADY_ACTIVE"));
    }

    @Test
    void uniqueConstraintSurvivesBypassOfService()
            throws Exception {
        repository.saveAndFlush(AccountEntity.pending(
                "same@example.org", "First"
        ));

        assertThrows(
                DataIntegrityViolationException.class,
                () -> repository.saveAndFlush(
                        AccountEntity.pending(
                                "same@example.org", "Second")
                )
        );
    }

    @Test
    void missingAccountIsNotValidationError()
            throws Exception {
        mvc.perform(get("/accounts/999999"))
                .andExpect(status().isNotFound())
                .andExpect(jsonPath("$.code")
                        .value("ACCOUNT_NOT_FOUND"));
    }
}
```

**These tests verify different layers:**

- `beanValidationRejectsBadEmail` and `blankNameRejectedBeforePersistence`: invalid input is rejected before writing.
- `servicePrecheckRejectsNormalizedDuplicate`: users receive a friendly code when a duplicate already exists.
- `unverifiedAccountCannotActivate` and `verifiedAccountCanActivate`: service/business state transitions inspect trusted state.
- `cannotActivateTwice`: prevents repeating an action invalid for the current state.
- `uniqueConstraintSurvivesBypassOfService`: **writes straight through the repository**, bypassing the service precheck, yet the DB still rejects duplicate emails.
- `missingAccountIsNotValidationError`: a missing resource is distinct from a malformed field.

**What the DB UNIQUE test does not prove:** those are two sequential writes, not a race where two transactions both pass the precheck. Testing races requires two real transactions, a barrier after `exists()==false`, and checking final state; never rely on `Thread.sleep(...)` as deterministic proof.

## 8. Business Validation Requires Transactions and Authorization

A business rule typically depends on state at the moment of the action:

- Ship an order only when its status is paid.
- Activate an account only after email verification.
- Never transfer more than the current balance.
- Never sell more than remaining seats.
- Allow only the account owner or an admin to edit specific data.

Never slap annotations onto a request DTO and assume they cover these conditions. The service/domain must identify the actor/resource and inspect state at the right moment.

### 8.1. `@Transactional` does not replace database constraints

Spring `@Transactional` establishes a transaction boundary; by default it rolls back on `RuntimeException` and `Error`, not on checked exceptions unless configured with `rollbackFor`. It never generates `UNIQUE`, `FOREIGN KEY`, or `CHECK` on its own, and the default isolation level depends on the transaction manager and database.

**Self-invocation caveat:** a Spring bean method calling `this.anotherTransactionalMethod()` bypasses the AOP proxy in default proxy mode, so transactional annotations on the inner method may not take effect the same way as external bean calls.

### 8.2. Never catch a database error and pretend success

An anti-pattern fragment:

```java
try {
    repository.saveAndFlush(entity);
} catch (DataIntegrityViolationException ex) {
    return successResponse();
}
```

This is not a standalone program. After a constraint failure, the transaction or persistence context may be marked rollback-only. Never keep writing inside the same transaction or return success; roll back and map the error at an appropriate boundary.

### 8.3. External side effects need dedicated design

If a transaction records an order and then sends an email or calls a payment API, rolling back the database **cannot undo** the email or payment. Avoid external side effects before commit whenever possible. Use transactional outboxes, idempotency keys, post-commit events, or sagas depending on business complexity.

## 9. Multi-Row Constraints: Stock, Balances, FK, and CHECK

### 9.1. Never oversell inventory

`@Positive int quantity` checks only that the request asks for a positive amount. If stock is 5 and two requests simultaneously buy 4, a `SELECT stock → if stock>=4 → UPDATE stock=stock-4` without a concurrency strategy can exceed inventory.

An illustrative option is atomic conditional SQL:

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :product_id
  AND stock >= :quantity;
```

The service inspects affected rows. Returning 0 rows means either the product does not exist or stock is insufficient; map the appropriate business error. You can also add `CHECK (stock >= 0)` in the DB; both act as complementary defenses.

### 9.2. Non-negative balances

A debit DTO can use `@Positive`, yet **knows nothing about the current balance**. The database can perform a conditional update:

```sql
UPDATE wallets
SET balance = balance - :amount
WHERE id = :wallet_id
  AND balance >= :amount;
```

The service distinguishes affected row count and authorization, while the DB maintains atomicity. A `CHECK (balance >= 0)` guards final state if all paths update that column directly.

### 9.3. Referential integrity

`@NotNull Long customerId` does not prove the customer exists. Use a foreign key:

```sql
ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id) REFERENCES customers(id);
```

This is illustrative SQL; no `orders`/`customers` tables exist in the runnable demo. The service must still verify which tenant/caller owns the customer; an FK enforces referential existence, **not access control**.

## 10. `@Version`, Optimistic Locking, and Limitations

With a JPA entity carrying `@Version Long version`:

```text
Transaction A reads row version=3
Transaction B reads row version=3
A updates -> updates with condition version=3 -> version=4
B updates -> version=3 is stale -> conflict
```

Exact SQL depends on the JPA provider and DB. On conflict, Spring may raise `OptimisticLockingFailureException` or a subtype like `ObjectOptimisticLockingFailureException`, and the API can return 409 so the client reloads and retries.

However, optimistic locking:

- Does not prevent duplicate emails across two concurrent **INSERT**s.
- Does not protect aggregate limits spanning multiple entities/rows.
- Can be bypassed by native SQL that ignores `version`.
- Does not replace authorization or state-machine checks.
- Does not mean every operation is safe to auto-retry; payments, inventory, and side effects require idempotency.

When business rules span multiple rows, evaluate pessimistic locks, unique/composite constraints, atomic SQL, appropriate isolation levels, or alternative transaction strategies—and test concurrent execution on a real DB.

## 11. Classify Errors Properly Instead of Collapsing Everything to 400

| Failure | Usually appropriate HTTP status | Example API code |
| --- | --- | --- |
| Invalid DTO field | 400 | `INPUT_INVALID` |
| Unreadable JSON | 400 | `UNREADABLE_BODY` |
| Confirmed duplicate email | 409 | `EMAIL_ALREADY_EXISTS` |
| Activation requested while unverified | 409 or 422 per contract | `EMAIL_NOT_VERIFIED` |
| Resource does not exist | 404 | `ACCOUNT_NOT_FOUND` |
| Stale version | 409 | `CONCURRENT_MODIFICATION` |
| Known unique DB constraint | 409 | `DATA_CONFLICT` or business code |
| Unexpected `NOT NULL` from server bug | 5xx | `INTERNAL_ERROR` |
| Unauthorized access | 403/404 per policy | `FORBIDDEN` |

HTTP status codes are **part of the API contract**, not automatically inferred from annotation names. Never turn every `DataIntegrityViolationException` into `EMAIL_ALREADY_EXISTS` or every business rule into a Bean Validation field error. Clients rely on stable machine codes, while human messages can be localized.

**Never return raw SQL messages or rejected values:** they can expose emails, tokens, table names, and constraint details. Logs should use redaction and trace IDs, and responses should contain only safe data.

## 12. Production Protection Checklist

- [ ] Use task-specific DTOs; never bind domain entities directly from HTTP.
- [ ] Apply `@Valid`/Jakarta constraints for format, requiredness, range, and length.
- [ ] Enforce business checks in service/domain layers using trusted state.
- [ ] Enforce authentication and authorization per actor, action, and resource.
- [ ] Define `UNIQUE` on the canonicalized business identity, not `existsBy` alone.
- [ ] Enforce `NOT NULL`, `FK`, `CHECK`, `PK`, and migrations for invariants enforceable in the DB.
- [ ] Verify production schemas actually hold the constraints, not just Java annotations.
- [ ] Configure appropriate transaction boundaries and rollback rules.
- [ ] Apply race-prevention strategies: atomic SQL, locking, versioning, or isolation per invariant.
- [ ] Never confuse `saveAndFlush` with a committed transaction.
- [ ] Never trigger external side effects before commit without an outbox/idempotency plan.
- [ ] Map known DB constraints to API codes; fall back safely to 5xx for unknown errors.
- [ ] Never serialize SQL exceptions, raw rejected values, or stack traces.
- [ ] Test invalid requests before DB, business transitions, and direct repository constraints.
- [ ] Test concurrency across two transactions on the target DBMS for sensitive invariants.
- [ ] Verify case sensitivity, collation, and normalization of unique keys.
- [ ] Test services called by jobs/consumers bypassing MVC validation.
- [ ] Monitor validation failures, business conflicts, and DB constraint violations.

## 13. Conclusion

**Input validation, business rules, and database constraints do not replace one another.** `@Email` does not stop duplicate emails; `existsByEmailNormalized` does not eliminate TOCTOU; `@Transactional` does not automatically make check-then-write atomic; `@Version` does not automatically enforce multi-row invariants.

A resilient design is: **validate input early for friendly feedback, enforce business rules and permissions in the service/domain, and guard ultimate consistency with database constraints, transactions, and concurrency controls**, then translate errors into a stable and safe API contract.
