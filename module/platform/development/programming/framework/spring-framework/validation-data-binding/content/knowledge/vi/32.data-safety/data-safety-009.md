# Validation không thay thế ràng buộc database hay kiểm tra nghiệp vụ

## 1. Bài toán: tại sao @Valid pass mà dữ liệu vẫn sai?

Trong Spring MVC, `@Valid`, `@Validated` và Jakarta Bean Validation giúp phát hiện request thiếu trường, sai định dạng hay vượt giới hạn. Ví dụ `@Email` kiểm tra định dạng email, `@NotBlank` kiểm tra chuỗi không rỗng, `@Min(1)` kiểm tra số tối thiểu. Đây là lớp bảo vệ đầu vào quan trọng, nhưng **validation thành công không bảo đảm hành động được phép, dữ liệu không trùng, hoặc database commit được**.

Hãy xét chức năng đăng ký tài khoản:

- Request A gửi `lan@example.org` và vượt qua `@Email`.
- Service A kiểm tra email chưa có trong database.
- Gần như đồng thời, request B cũng kiểm tra email này chưa có.
- Hai request cùng cố tạo row mới. Nếu database thiếu `UNIQUE`, cả hai có thể được lưu.
- Nếu tài khoản chưa xác minh email, service cũng phải từ chối hành động kích hoạt tài khoản dù email có định dạng hợp lệ.

Đây là **ba nhóm vấn đề khác nhau**: kiểm tra dữ liệu đầu vào, quy tắc nghiệp vụ dựa trên trạng thái tin cậy và ràng buộc dữ liệu ở database.

**Mục tiêu:** biết mỗi lớp cần kiểm tra gì, tránh lỗi TOCTOU (time-of-check to time-of-use), sử dụng `@Transactional`/constraint phù hợp, xử lý exception an toàn và viết kiểm thử có chứng cứ cho cả ba lớp.

Bài viết dùng Java 17, Spring Framework 6.x, Spring Boot 3.x, Spring MVC, Jakarta Validation, Spring Data JPA và relational database. Những fragment minh họa không có đủ type/import sẽ được ghi rõ; ví dụ Maven trong phần 6 là một project riêng có thể triển khai và kiểm thử.

## 2. Ba lớp kiểm soát có trách nhiệm khác nhau

| Lớp | Câu hỏi | Ví dụ | Điều không tự bảo đảm |
| --- | --- | --- | --- |
| **Input validation** | Giá trị từ request có đúng format/shape/range? | `@NotBlank`, `@Email`, `@Size`, `@Min` | Quyền truy cập, uniqueness, concurrency |
| **Business/domain checks** | Action có hợp lệ với trạng thái, actor và resource? | Chỉ active khi email verified; không đặt vượt số ghế; chỉ chủ tài khoản được sửa | Atomicity DB nếu không thiết kế transaction |
| **Database constraints** | State sau INSERT/UPDATE/COMMIT có thỏa invariant dữ liệu? | `UNIQUE`, `NOT NULL`, `FOREIGN KEY`, `CHECK`, primary key | Logic actor/permission, toàn bộ workflow nghiệp vụ |

Một API đủ an toàn không chọn **một trong ba** mà kết hợp:

```text
Client gửi dữ liệu không tin cậy
           |
           v
  DTO + input validation
           |
           v
  Service/domain + authorization
           |
           v
  Transaction / concurrency control
           |
           v
  Database: PK, UNIQUE, FK, NOT NULL, CHECK
           |
           v
  Commit thành công -> response thành công
           |
           +--> Failure -> rollback và safe error mapping
```

### 2.1. @Valid chỉ biết điều kiện nó được cung cấp

```java
public record RegisterRequest(
        @NotBlank @Email String email,
        @NotBlank @Size(max = 80) String displayName) {
}
```

Đây là fragment DTO (cần imports `jakarta.validation.constraints.*`). Spring MVC có thể dùng `@Valid @RequestBody RegisterRequest` để từ chối email sai định dạng. Nhưng không thể từ một `@Email` suy ra email đã được xác minh, còn trống trong database, thuộc người gửi hoặc phù hợp với quy tắc đăng ký.

### 2.2. Business invariant thường cần dữ liệu đang lưu

Ví dụ: tài khoản có trạng thái `PENDING` hoặc `ACTIVE`; chỉ cho kích hoạt khi đã verified. Điều kiện không được nhận từ một field client tự khai:

```java
// Fragment bên trong domain/service:
if (!account.isEmailVerified()) {
    throw new BusinessRuleException("EMAIL_NOT_VERIFIED");
}
if (account.getState() != AccountState.PENDING) {
    throw new BusinessRuleException("INVALID_STATE_TRANSITION");
}
```

Nguồn `emailVerified` phải do **workflow xác minh đáng tin** cập nhật, không phải do request có `"verified":true`. Việc account có quyền kích hoạt hay không còn cần **authorization** dựa trên actor/resource.

### 2.3. Database bảo vệ nhiều đường ghi khác ngoài HTTP

Ngoài controller còn có scheduled job, message consumer, import script, admin tool, service khác và SQL chạy trực tiếp. Nếu chỉ đặt `@Valid` trên controller, những đường này có thể bypass. Một **UNIQUE constraint** tại database giúp bảo vệ mọi writer cùng sử dụng bảng, miễn constraint thật sự tồn tại và được áp dụng.

Ví dụ DDL có những bảo vệ cơ bản:

```sql
CREATE TABLE accounts (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email_normalized VARCHAR(254) NOT NULL,
    display_name VARCHAR(80) NOT NULL,
    state VARCHAR(16) NOT NULL,
    email_verified BOOLEAN NOT NULL,
    version BIGINT NOT NULL,
    CONSTRAINT uk_accounts_email UNIQUE (email_normalized),
    CONSTRAINT ck_accounts_state
      CHECK (state IN ('PENDING', 'ACTIVE'))
);
```

**Đây là SQL minh họa**, không phải migration của project bên dưới; cú pháp và DDL cần điều chỉnh theo DBMS. Nó phân biệt `NOT NULL`, `UNIQUE`, `CHECK` với các constraints trên DTO. `CHECK` bảo đảm giá trị state thuộc tập cho phép, nhưng không biết actor có quyền kích hoạt hay email đã verified theo quy trình nào.

## 3. Vì sao kiểm tra tồn tại rồi insert vẫn có race condition?

Mẫu code:

```java
if (repository.existsByEmailNormalized(email)) {
    throw new DuplicateEmailException();
}
repository.save(account);
```

Đây là **fragment**. Nó hữu ích như một friendly precheck, nhưng **không đủ để ngăn trùng**.

```text
Thời gian        Transaction A                 Transaction B
----------------------------------------------------------------
T1               exists(email) -> false
T2                                             exists(email) -> false
T3               INSERT same email
T4                                             INSERT same email
T5               COMMIT
T6                                             COMMIT / CONFLICT

Không có UNIQUE: cả hai có thể commit thành hai rows.
Có UNIQUE: database chặn một trong hai writes/commits.
```

Từ lúc kiểm tra đến lúc sử dụng, dữ liệu có thể bị thay đổi. Đây là lỗi **TOCTOU**. `@Transactional` không mặc nhiên khiến `SELECT exists` + `INSERT` trở thành một phép kiểm tra/ghi nguyên tử với isolation mặc định của mọi database.

**Cách xử lý đúng hơn:**

1. Chuẩn hóa email theo chính sách (ví dụ `strip + lowercase`) một cách nhất quán.
2. Precheck `existsBy...` nếu muốn trả lỗi sớm.
3. Đặt **UNIQUE trên chính cột/biểu thức đại diện business identity**.
4. Để database là thẩm quyền cuối cùng khi concurrency xảy ra.
5. Chuyển **known constraint failure** thành mã API an toàn sau khi transaction fail; không trả SQL/driver message.

Nếu business coi `LAN@EXAMPLE.ORG` và `lan@example.org` là cùng email, unique trên cột raw phân biệt hoa/thường chưa chắc phù hợp. Bài demo lưu `emailNormalized`. Chính sách normalization trong sản phẩm thật phải được xác định rõ; không giả định mọi hệ thống email/collation xử lý Unicode/case giống nhau.

### Khi nào exception DB xuất hiện?

JPA có persistence context và flush:

- `save(...)` có thể chưa gửi hết SQL xuống database.
- `saveAndFlush(...)` yêu cầu flush sớm để nhìn thấy nhiều DB errors trước khi method trả.
- **Flush không đồng nghĩa commit**. Một constraint có thể được kiểm tra ở commit tùy database và chế độ constraint.
- Transaction rollback có thể xảy ra khi transactional proxy kết thúc method, không chỉ ngay tại dòng `save()`.

Do đó không được gửi email xác nhận, message queue event hoặc response “đã ghi thành công” dựa trên giả định một entity đã gọi `save()` chắc chắn sẽ commit. Với side effects ngoài DB, cân nhắc transactional outbox, after-commit processing và idempotency.

## 4. Phân biệt validation annotations, JPA metadata và constraints thực tế

| Công cụ | Vai trò chính | Giới hạn |
| --- | --- | --- |
| `@Email` | Input format | Không xác minh quyền sở hữu/duy nhất |
| `@NotBlank` | Giá trị String phải có nội dung | Không tự tạo NOT NULL ở mọi database path |
| `@Min(1)` | Số đạt ngưỡng | Không bảo vệ stock/số dư khi concurrency |
| `@Valid` | Yêu cầu cascade/object validation | Không phải authorization |
| `@Column(nullable=false)` | Metadata JPA/DDL được tạo khi cấu hình | Không thay migration thực tế nếu schema đã tồn tại |
| `@Table(uniqueConstraints=...)` | Metadata JPA cho schema generation | Cần verify UNIQUE thật ở DB production |
| `@Version` | Optimistic locking của JPA | Không bảo vệ mọi invariant qua nhiều rows |
| `@Transactional` | Transaction scope/rollback | Không tự sinh CHECK, UNIQUE, FK hoặc locking strategy |

Một Hibernate/JPA provider cũng có thể kích hoạt Bean Validation trước insert/update trong lifecycle của entity, nhưng **không nên coi đây là thay thế ràng buộc DB**. Một SQL client hoặc hệ thống khác ghi vào cùng bảng sẽ không chạy Jakarta Validator của Java process.

Trong production, sử dụng migration như Flyway/Liquibase, kiểm tra schema đã được áp dụng, và không bật `spring.jpa.hibernate.ddl-auto=create-drop` trên dữ liệu thật.

## 5. Quy tắc nào nên bảo vệ ở lớp nào?

| Quy tắc | DTO/HTTP | Service/domain | Database |
| --- | --- | --- | --- |
| Display name có 1–80 ký tự | `@NotBlank`, `@Size` | Trim/normalize | NOT NULL, length và CHECK nếu cần |
| Email đúng format | `@Email` | Chuẩn hóa, policy nội bộ | Cột đủ chiều dài |
| Email không trùng | Không bảo đảm | Friendly precheck | **UNIQUE** |
| Order có customer hợp lệ | Kiểm tra ID shape | Verify relation + authorization | **FOREIGN KEY** |
| Không bán vượt kho | Positive request quantity | Reserve logic/transaction | Atomic conditional UPDATE, CHECK/locking |
| Số dư không âm | Positive spend amount | Business balance rule | **CHECK** và atomic update |
| Chỉ owner được sửa | Không | **Authorization** | Row-level security khi có thiết kế |
| Chỉ verified mới active | Không dựa vào client | **State machine** | CHECK/trigger có thể hỗ trợ |
| Tránh lost update | Không | Retry/conflict policy | **@Version / locking** |

Đừng cố viết tất cả domain rules bằng Jakarta custom constraint có database query. Nếu custom validator kiểm tra `exists()`, race condition vẫn còn; hơn nữa validation có side effects/I/O khó dự đoán. Business logic cần đặt ở boundary có transaction phù hợp.

## 6. Project runnable: Spring Boot MVC + JPA + H2

Ví dụ sau có một quy trình đăng ký tài khoản và kích hoạt.

- `POST /accounts`: validate JSON, normalize email, precheck duplicate và ghi `AccountEntity`.
- `GET /accounts/{id}`: đọc trạng thái.
- `POST /accounts/{id}/activate`: chỉ cho phép kích hoạt account `PENDING` đã được verify bằng nguồn đáng tin.
- Entity có UNIQUE trên email normalized, NOT NULL các trường, `@Version`.
- Exception handler phân loại input errors, business conflicts, persistence conflicts.
- Test vừa đi qua MockMvc, vừa ghi thẳng repository để chứng minh UNIQUE hoạt động khi bỏ qua controller/precheck.

**Lưu ý bảo mật:** demo **không triển khai login, email verification workflow thật hoặc phân quyền theo accountId**; không đưa trực tiếp lên Internet. Nó cố ý cô lập logic validation/business/DB cho mục tiêu học tập.

### 6.6. src/main/java/demo/AccountEntity.java

```java
package demo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;
import jakarta.persistence.Version;

enum AccountState {
    PENDING, ACTIVE
}

@Entity
@Table(
    name = "accounts",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_account_email_normalized",
        columnNames = "email_normalized"
    )
)
public class AccountEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "email_normalized",
            nullable = false, length = 254)
    private String emailNormalized;

    @Column(nullable = false, length = 80)
    private String displayName;

    @Column(nullable = false)
    private boolean emailVerified;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 16)
    private AccountState state;

    @Version
    private Long version;

    protected AccountEntity() {
        // Constructor cho JPA.
    }

    private AccountEntity(String email, String name) {
        this.emailNormalized = email;
        this.displayName = name;
        this.emailVerified = false;
        this.state = AccountState.PENDING;
    }

    public static AccountEntity pending(
            String normalizedEmail, String displayName) {
        return new AccountEntity(normalizedEmail, displayName);
    }

    // Chỉ trusted verification workflow được phép gọi.
    // Package-private cho phép test trong package demo mô phỏng.
    void markEmailVerified() {
        this.emailVerified = true;
    }

    void activate() {
        this.state = AccountState.ACTIVE;
    }

    public Long getId() {
        return id;
    }

    public String getEmailNormalized() {
        return emailNormalized;
    }

    public String getDisplayName() {
        return displayName;
    }

    public boolean isEmailVerified() {
        return emailVerified;
    }

    public AccountState getState() {
        return state;
    }

    public Long getVersion() {
        return version;
    }
}
```

Phân tích:

- `@Table(uniqueConstraints=...)` giúp Hibernate tạo DB UNIQUE trong cấu hình DDL demo.
- `nullable=false` giúp mô tả DB NOT NULL cho email, displayName, verified flag và state.
- `@Version` hỗ trợ optimistic locking cho updates qua JPA provider.
- Domain state khởi đầu là `PENDING`, `emailVerified=false` và **không có public setter** để HTTP client chọn state.
- `markEmailVerified()` chỉ dùng để giả lập một trusted verification trong test; project không có endpoint xác minh email tùy tiện.
- Không đặt `@Email` lên entity rồi coi đó là “UNIQUE”; hai loại bảo vệ khác nhau.
- Khi triển khai bằng migration, vẫn cần kiểm tra thực tế unique index/constraint, không suy từ annotation mã nguồn.

### 6.8. src/main/java/demo/AccountView.java

public record AccountView(
        Long id,
        String displayName,
        String email,

### 6.10. src/main/java/demo/AccountService.java

```java
package demo;

import java.util.Locale;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AccountService {

    private final AccountRepository repository;

    public AccountService(AccountRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public AccountView register(SignupRequest request) {
        String normalized = request.email()
                .strip()
                .toLowerCase(Locale.ROOT);

        if (repository.existsByEmailNormalized(normalized)) {
            throw new DuplicateEmailException();
        }

        AccountEntity account = repository.saveAndFlush(
                AccountEntity.pending(
                        normalized,
                        request.displayName().strip()
                )
        );

        return AccountView.from(account);
    }

    @Transactional(readOnly = true)
    public AccountView find(long id) {
        AccountEntity entity = repository.findById(id)
                .orElseThrow(AccountNotFoundException::new);

        return AccountView.from(entity);
    }

    @Transactional
    public AccountView activate(long id) {
        AccountEntity entity = repository.findById(id)
                .orElseThrow(AccountNotFoundException::new);

        if (entity.getState() != AccountState.PENDING) {
            throw new BusinessRuleException("ALREADY_ACTIVE");
        }

        if (!entity.isEmailVerified()) {
            throw new BusinessRuleException("EMAIL_NOT_VERIFIED");
        }

        entity.activate();
        repository.flush();
        return AccountView.from(entity);
    }
}
```

Đọc code theo lớp:

1. `SignupRequest` đi vào service sau HTTP validation, nhưng service cần thêm input defense khi có caller khác từ job/consumer hoặc unit test; ví dụ chỉ xây dựng một HTTP path.
2. `strip().toLowerCase(Locale.ROOT)` xác định một policy normalization. Để UNIQUE có hiệu lực, **mọi đường ghi** phải dùng policy hoặc database enforce normalized identity.
3. `existsByEmailNormalized` giúp trường hợp duplicate thông thường trả mã dễ hiểu, nhưng vẫn có race.
4. `saveAndFlush` yêu cầu DB flush trước method trả; UNIQUE là tuyến cuối khi hai request cùng vượt precheck. **Flush chưa phải commit**.
5. `activate` kiểm tra **trusted stored state**, không nhận `verified=true` từ client.
6. `@Transactional` tạo transaction cho use case; nếu throw runtime exception, Spring mặc định rollback.
7. `repository.flush()` trong activate giúp optimistic lock/DB errors xuất hiện sớm hơn trong nhiều provider, nhưng vẫn cần xử lý failure lúc commit.

**Không coi `@Version` là universal concurrency solution:** nó hỗ trợ lost-update detection trên entity đã versioned; không tự ngăn cross-row overselling hoặc enforce uniqueness khi insert.

### 6.12. src/main/java/demo/ErrorAdvice.java

```java
package demo;

import java.util.List;

import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

@RestControllerAdvice
public class ErrorAdvice extends ResponseEntityExceptionHandler {

    public record ApiError(
            String code,
            String message,
            List<String> fields) {
    }

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex,
            HttpHeaders headers,
            HttpStatusCode status,
            WebRequest request) {

        List<String> fields = ex.getBindingResult()
                .getFieldErrors().stream()
                .map(FieldError::getField)
                .distinct().sorted().toList();

        return new ResponseEntity<>(
                new ApiError(
                        "INPUT_INVALID",
                        "Submitted data is invalid",
                        fields),
                headers, status);
    }

    @ExceptionHandler(DuplicateEmailException.class)
    public ResponseEntity<ApiError> duplicate() {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "EMAIL_ALREADY_EXISTS",
                        "Email already registered",
                        List.of("email")));
    }

    @ExceptionHandler(AccountNotFoundException.class)
    public ResponseEntity<ApiError> missing() {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError(
                        "ACCOUNT_NOT_FOUND",
                        "Account does not exist",
                        List.of()));
    }

    @ExceptionHandler(BusinessRuleException.class)
    public ResponseEntity<ApiError> business(
            BusinessRuleException ex) {

        String msg = switch (ex.code()) {
            case "EMAIL_NOT_VERIFIED" ->
                    "Email must be verified before activation";
            case "ALREADY_ACTIVE" ->
                    "Account is already active";
            default -> "Transition is not allowed";
        };

        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        ex.code(), msg, List.of()));
    }

    @ExceptionHandler(OptimisticLockingFailureException.class)
    public ResponseEntity<ApiError> stale() {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "CONCURRENT_MODIFICATION",
                        "Resource changed; reload and retry",
                        List.of()));
    }

    @ExceptionHandler(DataIntegrityViolationException.class)
    public ResponseEntity<ApiError> integrity() {
        // Fallback minh họa; không tự coi mọi DB error là
        // duplicate email hoặc lỗi input của client.
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError(
                        "DATA_CONFLICT",
                        "Write violates a data constraint",
                        List.of()));
    }
}
```

**Quan trọng khi triển khai thật:** `DataIntegrityViolationException` có thể đại diện UNIQUE, NOT NULL, FK, CHECK hoặc lỗi khác. Không gộp tất cả thành `EMAIL_ALREADY_EXISTS`. Demo trả `DATA_CONFLICT` với 409 để đơn giản hóa; production nên map **known unique constraint** sang conflict nghiệp vụ tương ứng, còn unexpected persistence fault có thể cần **5xx** và log nội bộ có redaction. Loại exception xảy ra ở flush/commit cũng tùy provider và transaction manager.

Không serializes trực tiếp `ex.getMessage()` vì nó có thể chứa SQL, tên bảng, key value hoặc PII. Lỗi public dùng mã ổn định; thông điệp hiển thị có thể được dịch bằng `MessageSource` theo locale.

## 8. Business validation cần transaction và authorization

Một quy tắc nghiệp vụ thường phụ thuộc vào trạng thái tại thời điểm hành động:

- Chỉ gửi hàng khi đơn ở trạng thái đã thanh toán.
- Chỉ kích hoạt tài khoản sau email verification.
- Không chuyển tiền vượt số dư.
- Không bán quá số chỗ còn lại.
- Chỉ chủ tài khoản hoặc admin được chỉnh sửa dữ liệu cụ thể.

Đừng chỉ gắn annotation lên request DTO rồi giả định nó bao phủ các điều kiện này. Service/domain cần xác định actor/resource và kiểm tra state đúng thời điểm.

### 8.1. @Transactional không thay database constraints

Spring `@Transactional` thiết lập transaction boundary; mặc định thường rollback cho `RuntimeException` và `Error`, không mặc định rollback cho mọi checked exception nếu không cấu hình `rollbackFor`. Bản thân nó không tự sinh UNIQUE, FOREIGN KEY hay CHECK; và isolation level mặc định thuộc transaction manager/database.

**Self-invocation caveat:** một method Spring bean gọi `this.anotherTransactionalMethod()` không đi qua proxy AOP trong cấu hình proxy mặc định, nên annotation trên method nội bộ có thể không được kích hoạt như lời gọi từ bean khác.

### 8.2. Đừng catch database error rồi giả vờ thành công

Một fragment anti-pattern:

```java
try {
    repository.saveAndFlush(entity);
} catch (DataIntegrityViolationException ex) {
    return successResponse();
}
```

Đoạn này không phải chương trình độc lập. Sau constraint failure, transaction/persistence context có thể bị đánh dấu rollback-only. Không tiếp tục ghi trong cùng transaction hay gửi success; hãy rollback và mapping lỗi ở boundary phù hợp.

### 8.3. External side effects cần thiết kế riêng

Nếu transaction ghi order rồi gửi email hoặc gọi payment API, rollback database **không undo** được email/payment. Tránh thao tác bên ngoài trước khi commit nếu có thể. Dùng transactional outbox, idempotency key, event sau commit hoặc saga theo độ phức tạp nghiệp vụ.

## 9. Ràng buộc trên nhiều rows: stock, balance, FK và CHECK

### 9.1. Không bán vượt tồn kho

`@Positive int quantity` chỉ kiểm tra request yêu cầu số lượng dương. Nếu stock còn 5 mà hai request cùng mua 4, một `SELECT stock → if stock>=4 → UPDATE stock=stock-4` thiếu concurrency strategy có thể vượt giới hạn.

Một phương án minh họa là atomic conditional SQL:

```sql
UPDATE products
SET stock = stock - :quantity
WHERE id = :product_id
  AND stock >= :quantity;
```

Service kiểm tra affected rows. Trả 0 row nghĩa là product không tồn tại hoặc stock không đủ; cần xác định lỗi nghiệp vụ phù hợp. Có thể thêm `CHECK (stock >= 0)` ở DB; cả hai là lớp phòng vệ bổ sung.

### 9.2. Số dư không âm

Một DTO chi tiền có thể dùng `@Positive`, nhưng **không biết balance hiện tại**. Database có thể thực hiện conditional update:

```sql
UPDATE wallets
SET balance = balance - :amount
WHERE id = :wallet_id
  AND balance >= :amount;
```

Service phân biệt row count và authorization, DB giữ atomicity. Một `CHECK (balance >= 0)` bảo vệ final state nếu tất cả paths cập nhật trực tiếp vào cột đó.

### 9.3. Referential integrity

`@NotNull Long customerId` không chứng minh customer tồn tại. Dùng foreign key:

```sql
ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer
FOREIGN KEY (customer_id) REFERENCES customers(id);
```

Đây là SQL minh họa, không có bảng orders/customers trong runnable demo. Service vẫn cần kiểm tra customer thuộc tenant/caller nào; FK bảo vệ tồn tại dữ liệu tham chiếu, **không bảo vệ quyền truy cập**.

## 10. @Version, optimistic locking và giới hạn

Với JPA entity có `@Version Long version`:

```text
Transaction A đọc row version=3
Transaction B đọc row version=3
A cập nhật -> update với điều kiện version=3 -> version=4
B cập nhật -> version=3 đã cũ -> conflict
```

SQL thực tế tùy JPA provider và DB. Khi conflict, Spring có thể phát sinh `OptimisticLockingFailureException` hoặc subtype như `ObjectOptimisticLockingFailureException`, và API có thể trả 409 để client reload/retry.

Nhưng optimistic locking:

- Không tự chặn trùng email khi hai **INSERT**.
- Không tự bảo vệ tổng hạn mức qua nhiều entities/rows.
- Có thể bị bypass bởi native SQL không xét version.
- Không thay authorization hoặc kiểm tra state machine.
- Không có nghĩa mọi operation đều nên retry tự động; payment, inventory và side effects cần idempotency.

Khi business rule trải nhiều rows, cân nhắc pessimistic locks, unique/composite constraints, atomic SQL, isolation mức phù hợp hoặc transaction strategy khác, đồng thời kiểm thử concurrent operations trên DB thật.

## 11. Phân loại lỗi đúng thay vì gom tất cả thành 400

| Lỗi | HTTP thường phù hợp | Mã API ví dụ |
| --- | --- | --- |
| Invalid DTO field | 400 | `INPUT_INVALID` |
| JSON không đọc được | 400 | `UNREADABLE_BODY` |
| Email trùng đã xác nhận | 409 | `EMAIL_ALREADY_EXISTS` |
| Chưa verify nhưng active | 409 hoặc 422 theo contract | `EMAIL_NOT_VERIFIED` |
| Resource không tồn tại | 404 | `ACCOUNT_NOT_FOUND` |
| Stale version | 409 | `CONCURRENT_MODIFICATION` |
| Known unique DB constraint | 409 | `DATA_CONFLICT` hoặc mã nghiệp vụ |
| Unexpected NOT NULL due server bug | 5xx | `INTERNAL_ERROR` |
| Không có quyền truy cập | 403/404 theo policy | `FORBIDDEN` |

Mã HTTP là **một phần API contract**, không suy tự động từ tên annotation. Không biến mọi `DataIntegrityViolationException` thành `EMAIL_ALREADY_EXISTS` hoặc mọi business rule thành Bean Validation field error. Client cần code ổn định để xử lý, còn message có thể được dịch.

**Không trả thẳng SQL message hoặc rejected values:** chúng có thể chứa email, token, thông tin bảng và constraint. Log có redaction và trace ID, response chỉ có thông tin an toàn.

## 12. Checklist bảo vệ production

- [ ] Dùng DTO theo tác vụ, không bind thẳng domain entity từ HTTP.
- [ ] Có `@Valid`/Jakarta constraints cho format, required, range, length.
- [ ] Có business checks tại service/domain dựa trên trusted state.
- [ ] Có authentication/authorization theo actor, action và resource.
- [ ] Có UNIQUE đúng business identity đã chuẩn hóa, không chỉ `existsBy`.
- [ ] Có NOT NULL, FK, CHECK, PK và migration cho invariants có thể enforce ở DB.
- [ ] Kiểm tra schema production thực sự có constraints, không chỉ Java annotations.
- [ ] Có transaction boundaries và rollback rules phù hợp.
- [ ] Có strategy chống race: atomic SQL, locking, version, isolation tùy invariant.
- [ ] Không nhầm `saveAndFlush` với committed transaction.
- [ ] Không gọi external side effect trước commit mà thiếu outbox/idempotency plan.
- [ ] Map known DB constraint sang API code; unknown errors có fallback 5xx an toàn.
- [ ] Không serializes SQL exception, raw rejected values hoặc stack traces.
- [ ] Test invalid request trước DB, business transition và trực tiếp repository constraint.
- [ ] Test concurrency trên hai transactions với target DBMS khi invariant nhạy cảm.
- [ ] Kiểm tra case sensitivity/collation/normalization của unique keys.
- [ ] Test service được gọi từ job/consumer mà không qua MVC validation.
- [ ] Có monitoring cho validation failures, business conflicts và DB constraint violations.

## 13. Kết luận

**Input validation, business rules và database constraints không thay thế nhau.** `@Email` không ngăn email trùng; `existsByEmailNormalized` không loại bỏ TOCTOU; `@Transactional` không tự biến hai bước kiểm tra/ghi thành thao tác atomic; `@Version` không tự giải quyết mọi invariant trải nhiều rows.

Thiết kế vững chắc là: **kiểm tra input sớm để phản hồi thân thiện, kiểm tra nghiệp vụ và quyền ở service/domain, bảo vệ tính nhất quán cuối cùng bằng constraints/transaction/concurrency controls của database**, rồi dịch lỗi thành hợp đồng API ổn định và an toàn.
