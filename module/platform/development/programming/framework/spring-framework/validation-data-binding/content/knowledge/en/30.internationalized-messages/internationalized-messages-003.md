# DefaultMessageCodesResolver and Message Code Fallback Order

In Spring MVC, a binding or Bean Validation error does not necessarily have only one message code. For example, when a form submits `age=abc` while the JavaBean declares `Integer age`, Spring can produce a `FieldError` containing **four ordered message keys**:

~~~text
typeMismatch.registration.age
typeMismatch.age
typeMismatch.java.lang.Integer
typeMismatch
~~~

These keys are generated by **`DefaultMessageCodesResolver`**. **`MessageSource`** then looks up the corresponding language resource to choose the message shown to the user, such as “Tuổi phải là số nguyên.” (Vietnamese) or “Age must be a whole number.” (English). When a specific key is absent, Spring tries a less specific one: this is the **message code fallback order**.

This lesson belongs to the **Internationalized Messages** series of Spring Framework, covering the code generation algorithm for field/object/nested collections, interaction with `BindingResult` and `MessageSource`, resource bundles, prefix/formatter customization, a Spring Boot 3.5 / Spring Framework 6.2 / Java 17+ example, and MockMvc integration tests. Do not mix Servlet MVC mechanisms with Spring WebFlux when choosing exceptions or resolvers.

## 1. Distinguishing Error Codes from Translated Text

| Component | Responsibility | Example |
|---|---|---|
| `DataBinder` / `WebDataBinder` | Binding, type conversion, recording errors | `"abc"` fails to convert to `Integer` |
| `Errors` / `BindingResult` | Stores errors on the object/fields | `errors.getFieldErrors()` |
| `ObjectError` / `FieldError` | An error with `codes`, `arguments`, `defaultMessage` | Field `age` has four codes |
| `MessageCodesResolver` | Strategy for generating ordered codes from error metadata | `resolveMessageCodes(...)` |
| `DefaultMessageCodesResolver` | Default implementation of the strategy | `typeMismatch.registration.age` then fallbacks |
| `MessageSource` | Looks up keys by locale and interpolates the message | `getMessage(fieldError, locale)` |
| `messages_vi.properties` | Vietnamese translations | `typeMismatch.age=Tuổi phải là số.` |

The two steps must not be conflated:

~~~text
Form request: age=abc
     |
     v
WebDataBinder -> conversion fail
     |
     v
BindingResult has FieldError(code="typeMismatch")
     |
     v
DefaultMessageCodesResolver
     |  generates ordered candidates
     v
["typeMismatch.registration.age",
 "typeMismatch.age",
 "typeMismatch.java.lang.Integer",
 "typeMismatch"]
     |
     v
MessageSource + Locale(vi/en)
     |  finds first matching key
     v
Message in selected language
~~~

`DefaultMessageCodesResolver` does **not** open `messages.properties` files itself and does **not** translate sentences. It creates **the keys**. `MessageSource` performs the language lookup. To understand why a user sees a particular sentence, inspect **both the codes in `FieldError.getCodes()` and the keys present in the bundles**.

## 2. Exact API

Interface:

~~~java
org.springframework.validation.MessageCodesResolver
~~~

Default implementation:

~~~java
org.springframework.validation.DefaultMessageCodesResolver
~~~

There are two overloads:

~~~java
String[] resolveMessageCodes(
    String errorCode,
    String objectName);

String[] resolveMessageCodes(
    String errorCode,
    String objectName,
    String field,
    Class<?> fieldType);
~~~

These are abbreviated API signatures for study; you do not need to redefine them. The first overload handles **object-level** errors; the second handles **field-level** errors. `fieldType` may be `null` if the framework cannot determine the Java type.

The base `errorCode` can be:

- `typeMismatch` when binding/type conversion fails.
- `required` when the binding mechanism marks a required field as missing.
- `NotBlank`, `Min`, `Size`, etc., when a Jakarta Bean Validation constraint is adapted into a Spring error.
- `account.invalid` or `tooYoung` when a developer explicitly calls `errors.reject(...)`/`rejectValue(...)`.

**The base code is determined by the error source**; the resolver does not enforce `@Min`, check values, or decide HTTP statuses.

## 3. ObjectError: Exactly Two Fallback Codes

Example:

~~~java
var resolver = new DefaultMessageCodesResolver();
String[] codes = resolver.resolveMessageCodes(
    "account.invalid", "registration");
~~~

Result:

~~~text
account.invalid.registration
account.invalid
~~~

With the default formatter, the order is:

1. `errorCode.objectName` — specific message for an error on the model with that name.
2. `errorCode` — general message.

Example:

~~~properties
account.invalid.registration=Registration details are invalid.
account.invalid=Invalid data.
~~~

If both keys exist, `account.invalid.registration` takes precedence. If the first key is missing, `account.invalid` serves as the fallback.

An object error can arise when a Spring `Validator` calls:

~~~java
errors.reject("account.invalid", "Registration is invalid");
~~~

This is a snippet inside a method that has an `errors` variable, not a standalone Java program. `reject` records an **object-level** error; `rejectValue` records a **field-level** error.

The `objectName` matters: if a controller uses `@ModelAttribute("registration")`, the `BindingResult` object name is `registration`. Changing the model name to `signupForm` changes the highest-priority code to `account.invalid.signupForm`. When renaming a form/model, also check the message resources.

## 4. FieldError: Four Codes, from Specific to General

Direct example:

~~~java
var resolver = new DefaultMessageCodesResolver();
String[] codes = resolver.resolveMessageCodes(
    "typeMismatch",
    "registration",
    "age",
    Integer.class);
~~~

Exact result:

~~~text
typeMismatch.registration.age
typeMismatch.age
typeMismatch.java.lang.Integer
typeMismatch
~~~

| Priority | Formula | Scope |
|---|---|---|
| 1 | `code.objectName.field` | A specific field in a specific model |
| 2 | `code.field` | The same field name in any model |
| 3 | `code.fieldType` | The same Java type, when the type is known |
| 4 | `code` | Any error with the same base code |

If you define:

~~~properties
typeMismatch.registration.age=Registration age must be a whole number.
typeMismatch.age=Age must be numeric.
typeMismatch.java.lang.Integer=Please enter an integer.
typeMismatch=Invalid format.
~~~

an error on `registration.age` picks the first line. If that line is absent, Spring can use `typeMismatch.age`. If another form has `Integer quantity` without a specific key, Spring can choose `typeMismatch.java.lang.Integer`.

### Primitive and Wrapper Have Two Different Type Names

For `int.class`, the type-specific code is `typeMismatch.int`. For `Integer.class`, it is `typeMismatch.java.lang.Integer`. Do not define only `typeMismatch.int` and assume it covers properties declared as `Integer`.

If `fieldType` is unknown (`null`), adding a Java-type key makes no sense; in that case, the list will not necessarily contain four entries.

### Fallback Codes Do Not Depend on Existing Translations

`DefaultMessageCodesResolver` generates the exact same list even if the resource bundle has **zero** keys. Only `MessageSource` inspects available translations and picks the matching message. Therefore, testing the “code list” and testing the “localized message” must be **two separate checks**.

## 5. Nested Properties, Indexed Lists, and Maps: More Than Four Codes

In a form with `groups[0].name`, Spring generates codes for both the **specific element** and the **unindexed property path** so messages can be reused across the collection.

According to Spring 6.2 Javadoc:

~~~java
resolver.resolveMessageCodes(
    "typeMismatch",
    "user",
    "groups[0].name",
    String.class);
~~~

Resulting **seven ordered keys**:

~~~text
typeMismatch.user.groups[0].name
typeMismatch.user.groups.name
typeMismatch.groups[0].name
typeMismatch.groups.name
typeMismatch.name
typeMismatch.java.lang.String
typeMismatch
~~~

Meaning:

- The key with `user.groups[0].name` allows a custom message for one specific element.
- The key `user.groups.name` applies to elements of that collection on the `user` object.
- The key `groups[0].name` applies to that indexed field path across models.
- The key `groups.name` applies to the same field regardless of index or object.
- The key `name` applies to any leaf field named `name`.
- The Java-type key and base key serve as broader fallbacks.

Example:

~~~properties
typeMismatch.user.groups[0].name=The first group name is invalid.
typeMismatch.user.groups.name=Group name is incorrect.
typeMismatch.name=Invalid name.
typeMismatch=Invalid value.
~~~

If you want one shared message for every element, the unindexed key is enough. **Do not assume every nested field produces exactly seven codes**: the count depends on the field path structure, number of indices/keys, and the active formatter. Inspect the actual `FieldError.getCodes()`.

## 6. How Does `MessageSource` Look Up Codes and Locale?

`ObjectError`/`FieldError` implements `MessageSourceResolvable` with:

- `String[] getCodes()` — **ordered** list of candidate codes.
- `Object[] getArguments()` — message arguments.
- `String getDefaultMessage()` — default sentence, if any.

`MessageSource` provides the overload:

~~~java
String getMessage(
    MessageSourceResolvable resolvable,
    Locale locale);
~~~

Used in a controller:

~~~java
for (FieldError error : result.getFieldErrors()) {
    String[] candidates = error.getCodes();
    String translated = messageSource.getMessage(
        error, locale);
    // Send translated to the client, or add it to the model view.
}
~~~

This is a snippet inside a method that already has `result`, `messageSource`, and `locale`. `MessageSource` tries candidates in order. If none exist, a valid `defaultMessage` may be used. If no code is resolved and no default message exists, this overload can throw `NoSuchMessageException`.

### Three Layers of Fallback Commonly Confused

1. **Fallback across error codes:** from `typeMismatch.registration.age` to `typeMismatch`.
2. **Fallback across locales/resource bundles:** from the requested locale's translation to the configured default bundle.
3. **Fallback to `defaultMessage`:** when no key is found but the error carries a suitable default message.

These are **three distinct mechanisms**. A very specific key in the default bundle can beat a less specific key present only in another locale's translation, depending on how `MessageSource` organizes and resolves resources. To avoid responses mixing Vietnamese and English, translate all key codes for every supported locale.

## 7. Coming from DataBinder, @Valid, or Spring Validator?

### Conversion failure

Request:

~~~text
age=abc
~~~

while the DTO has `Integer age`. The binder fails to construct a number and records a `FieldError` with base code `typeMismatch`. This is a **data type** error, not `@Min(18)` failing on a successfully converted `Integer`.

### Bean Validation failure

If the request sends `age=17`, conversion succeeds. If the DTO has:

~~~java
@Min(18)
private Integer age;
~~~

and the handler places `@Valid` properly, Jakarta Validation detects the violation. The Spring adapter typically creates a `FieldError` with base code `Min`, for example:

~~~text
Min.registration.age
Min.age
Min.java.lang.Integer
Min
~~~

If the `name` field violates `@NotBlank`, the corresponding codes may be:

~~~text
NotBlank.registration.name
NotBlank.name
NotBlank.java.lang.String
NotBlank
~~~

### Spring Validator Explicitly Rejecting

A custom `org.springframework.validation.Validator` can call:

~~~java
errors.rejectValue(
    "age", "tooYoung", "User is under age");
~~~

With object name `registration` and field `Integer age`, the resolver can generate:

~~~text
tooYoung.registration.age
tooYoung.age
tooYoung.java.lang.Integer
tooYoung
~~~

This is an illustrative snippet inside a `validate(Object,Errors)` method, not a standalone class. Detecting the error is still the validator's job; the resolver only adds fallback codes for the **base code `tooYoung`**.

A class-level error such as a constraint checking `startDate <= endDate` can be turned into an `ObjectError` instead of a `FieldError`, thus using two codes instead of four. Do not assume every Jakarta violation is a field error.

## 8. Vietnamese and English Resource Bundles

In Spring Boot 3.5, you can use:

~~~text
src/main/resources/
  messages.properties
  messages_vi.properties
  application.properties
~~~

To auto-configure `MessageSource` by default, `messages.properties` is needed at the classpath root (or the configured basename). Having only `messages_vi.properties` without a base bundle may prevent Boot from auto-configuring `MessageSource` as expected.

`messages.properties` — default English:

~~~properties
typeMismatch.registration.age=Age must be a whole number.
typeMismatch.age=Age must be numeric.
typeMismatch.java.lang.Integer=Enter a valid integer.
typeMismatch=Invalid format.
Min.registration.age=Age must be at least 18.
Min.age=Age is below the minimum.
Min=Value is too small.
NotBlank.registration.name=Name is required.
NotBlank.name=This field must not be blank.
NotBlank=Cannot be blank.
NotNull.registration.age=Age is required.
NotNull=Required value is missing.
~~~

`messages_vi.properties` — Vietnamese:

~~~properties
typeMismatch.registration.age=Tuổi phải là số nguyên.
typeMismatch.age=Tuổi phải là số.
typeMismatch.java.lang.Integer=Vui lòng nhập số nguyên.
typeMismatch=Định dạng không hợp lệ.
Min.registration.age=Tuổi phải từ 18 trở lên.
Min.age=Tuổi chưa đạt mức tối thiểu.
~~~

In `application.properties`:

~~~properties

~~~

These properties illustrate how to pin the encoding/basename and reduce the impact of the system locale. Spring Boot provides defaults for basename and encoding, so you do not always need to repeat these lines when using the standard setup. Save resource files as UTF-8.

**Distinguish keys from object paths:** `typeMismatch.registration.age` is a **string key**, not `MessageSource` reflecting on a Java object to access `registration.age`.

~~~java
package com.example.codes;

import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

public class RegistrationForm {
    @NotBlank
    private String name;

    @NotNull
    @Min(18)
    private Integer age;

    public RegistrationForm() {
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public Integer getAge() {
        return age;
    }

    public void setAge(Integer age) {
        this.age = age;
    }

~~~

### 9.5. `RegistrationController.java`

`src/main/java/com/example/codes/RegistrationController.java`:

~~~java
package com.example.codes;

import java.util.Arrays;
import java.util.List;
import java.util.Locale;

import jakarta.validation.Valid;
import org.springframework.context.MessageSource;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.BindingResult;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class RegistrationController {
    private final MessageSource messages;

    public RegistrationController(MessageSource messages) {
        this.messages = messages;
    }

    @PostMapping(
        path = "/registration",
        consumes = MediaType.APPLICATION_FORM_URLENCODED_VALUE
    )
    public ResponseEntity<FormReply> register(
            @Valid @ModelAttribute("registration")
            RegistrationForm form,
            BindingResult errors,
            Locale locale) {

        if (!errors.hasErrors()) {
            return ResponseEntity.ok(
                new FormReply(true, List.of()));
        }

        List<FieldIssue> details =
            errors.getFieldErrors()
                .stream()
                .map(error -> toIssue(error, locale))
                .toList();

        return ResponseEntity.badRequest().body(
            new FormReply(false, details));
    }

    private FieldIssue toIssue(
            FieldError error, Locale locale) {

        String[] candidates = error.getCodes();

        return new FieldIssue(
            error.getField(),
            candidates == null
                ? List.of()
                : Arrays.asList(candidates),
            messages.getMessage(error, locale)
        );
    }

    public record FormReply(
        boolean valid, List<FieldIssue> errors) {
    }

    public record FieldIssue(
        String field, List<String> codes, String message) {
    }
}
~~~

`@ModelAttribute("registration")` fixes the object name; `BindingResult` is placed **immediately after** the object. `@Valid` activates Jakarta Validation. When errors occur, `FieldError.getCodes()` lets us inspect the specific-to-general order, while `messages.getMessage(error,locale)` displays the localized message. The demo endpoint returns only field errors, omitting object-level errors and rejected values.

Do not instantiate `new DefaultMessageCodesResolver()` to handle HTTP requests in this controller: Spring's binder already generates the codes. The standalone printer component only helps study and verify the rules.

### 9.6. Running and Testing with curl

~~~bash
./gradlew bootRun
~~~

On Windows PowerShell:

~~~powershell
.\gradlew.bat bootRun
~~~

With the resources in Section 8 and the default port 8080, the request:

~~~bash
curl -i -X POST "http://localhost:8080/registration" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -H "Accept-Language: vi" \
  --data-urlencode "name=Lan" \
  --data-urlencode "age=abc"
~~~

expects **HTTP 400** with a JSON body equivalent to:

~~~json
{
  "valid": false,
  "errors": [
    {
      "field": "age",
      "codes": [
        "typeMismatch.registration.age",
        "typeMismatch.age",
        "typeMismatch.java.lang.Integer",
        "typeMismatch"
      ],
      "message": "Tuổi phải là số nguyên."
    }
  ]
}
~~~

Changing the header to `Accept-Language: en` keeps the codes **unchanged**, and the message becomes:

~~~text
Age must be a whole number.
~~~

If you send `age=17` and `name=Lan`, Bean Validation creates a `Min` violation, and the Vietnamese message is `"Tuổi phải từ 18 trở lên."`. If you send `age=20`, `name=""`, you get `NotBlank.registration.name` and the message `"Vui lòng nhập họ tên."`. If you send `age=20` and `name=Lan`, you get HTTP **200**:

~~~json
{"valid":true,"errors":[]}
~~~

A controller can encounter multiple errors at once. Do not write tests that depend on the order between **`FieldError`s of different fields** unless the framework/validator guarantees an order; however, **the order within `getCodes()` of each individual error** is a contract of the default `DefaultMessageCodesResolver`.

## 10. JUnit and MockMvc Testing

A unit test for the resolver verifies key ordering. An HTTP integration test verifies that real data is bound/validated and `MessageSource` looks up the right translation.

~~~java
package com.example.codes;

import org.junit.jupiter.api.Test;
import org.springframework.validation.DefaultMessageCodesResolver;

import static org.junit.jupiter.api.Assertions.assertArrayEquals;

class MessageCodesResolverTest {
    private final DefaultMessageCodesResolver resolver =
        new DefaultMessageCodesResolver();

    @Test
    void fieldCodesHaveExpectedPriority() {
        assertArrayEquals(
            new String[] {
                "typeMismatch.registration.age",
                "typeMismatch.age",
                "typeMismatch.java.lang.Integer",
                "typeMismatch"
            },
            resolver.resolveMessageCodes(
                "typeMismatch", "registration",
                "age", Integer.class));
    }

    @Test
    void objectCodesHaveTwoEntries() {
        assertArrayEquals(
            new String[] {
                "registration.invalid.registration",
                "registration.invalid"

                "registration.invalid", "registration"));

    @Test
    void indexedPathCreatesSevenCodes() {

                "typeMismatch.groups.name",

                "typeMismatch"
~~~

~~~java
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.errors[0].codes[0]")
                .value("Min.registration.age"))
            .andExpect(jsonPath("$.errors[0].message")
                .value("Tuổi phải từ 18 trở lên."));
    }

    @Test
    void blankNameUsesNotBlankKey()
            throws Exception {
        mvc.perform(post("/registration")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .header(HttpHeaders.ACCEPT_LANGUAGE, "vi")
                .param("name", "")
                .param("age", "20"))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.errors[0].codes[0]")
                .value("NotBlank.registration.name"))
            .andExpect(jsonPath("$.errors[0].message")
                .value("Vui lòng nhập họ tên."));
    }

    @Test
    void validFormHasNoErrors() throws Exception {
        mvc.perform(post("/registration")
                .contentType(MediaType.APPLICATION_FORM_URLENCODED)
                .param("name", "Lan")
                .param("age", "20"))

            .andExpect(jsonPath("$.valid").value(true))
~~~

## 11. How to Test Fallbacks in a Controlled Way

Do not delete keys in a production application just to “see what Spring picks”. In a unit test, use `StaticMessageSource` and add only the keys you want to test:

~~~java
var resolver = new DefaultMessageCodesResolver();

var source =
    new org.springframework.context.support.StaticMessageSource();

source.addMessage(
    "typeMismatch.age",
    Locale.forLanguageTag("vi"),
    "Tuổi phải là số.");
source.addMessage(
    "typeMismatch",
    Locale.forLanguageTag("vi"),
    "Định dạng không hợp lệ.");

var error = new org.springframework.validation.FieldError(
    "registration",
    "age",
    "abc",
    true,
    resolver.resolveMessageCodes(
        "typeMismatch", "registration",
        "age", Integer.class),
    null,
    "Giá trị không hợp lệ");

String chosen = source.getMessage(
    error, Locale.forLanguageTag("vi"));
System.out.println(chosen);
~~~

This is a **snippet inside a method** with imports for `DefaultMessageCodesResolver` and `java.util.Locale`; not a standalone class. Output:

~~~text
Tuổi phải là số.
~~~

Because `typeMismatch.registration.age` **does not exist** in this source, the message source moves on and finds `typeMismatch.age`. If you add the first key, the new message takes priority. `StaticMessageSource` is useful for isolated tests without modifying application resource bundles.

## 12. Customizing Prefix and Formatter

`DefaultMessageCodesResolver` provides:

~~~java
resolver.setPrefix("validation.");
~~~

Then the four-code example becomes:

~~~text
validation.typeMismatch.registration.age
validation.typeMismatch.age
validation.typeMismatch.java.lang.Integer
validation.typeMismatch
~~~

If you add a prefix without adding that prefix to the keys in your properties files, messages may not be found. Another organizational option is changing the formatter:

~~~java
resolver.setMessageCodeFormatter(
    DefaultMessageCodesResolver.Format.POSTFIX_ERROR_CODE);
~~~

The default formatter is `PREFIX_ERROR_CODE`, which produces `typeMismatch.registration.age`. `POSTFIX_ERROR_CODE` puts the error code at the end, e.g., `registration.age.typeMismatch`. Change this only when you have standardized on a single naming convention across all bundles.

You must attach the resolver to the **right DataBinder** for it to take effect:

~~~java
binder.setMessageCodesResolver(resolver);
~~~

The line above is a snippet with `binder` and `resolver` in scope. In MVC, you can customize per form:

~~~java
@InitBinder("registration")
public void configureCodes(WebDataBinder binder) {
    var resolver = new DefaultMessageCodesResolver();
    resolver.setPrefix("validation.");
    binder.setMessageCodesResolver(resolver);
}
~~~

This is an **alternative example**; do not add it to the project in Section 9 unless you also migrate resource keys to `validation.*`. Imports for `@InitBinder`, `WebDataBinder`, and `DefaultMessageCodesResolver` are required when using it.

To apply the rule to every binder, you can configure `ConfigurableWebBindingInitializer` and call `setMessageCodesResolver(...)` in MVC infrastructure, while preserving the default conversion service and validator. Do not replace the global configuration just because one form uses a different key convention.

## 13. Common Mistakes

| Symptom | Cause | How to Handle |
|---|---|---|
| Only the general `typeMismatch` message appears | Specific translations are missing | Add `typeMismatch.object.field`, `typeMismatch.field` |
| Defined `typeMismatch.int` but it does not match | Property is `Integer`, not `int` | Check `getCodes()`, add key `typeMismatch.java.lang.Integer` |
| Form-named key does not match | `@ModelAttribute` uses a different objectName | Check `BindingResult.getObjectName()` |
| Form key exists but translation is not picked | A more specific key comes earlier | Print all `FieldError.getCodes()` |
| `vi` locale displays English | Missing translation, falls back to default bundle | Add translations and test by locale |
| Boot fails to load message bundle | Missing `messages.properties` or wrong basename | Verify resource path and `spring.messages.*` |
| Vietnamese diacritics are garbled | File/MessageSource encoding mismatch | Save as UTF-8 and check `spring.messages.encoding` |
| `getDefaultMessage()` is not translated via Spring keys | Code bypasses `MessageSource` | Call `getMessage(fieldError, locale)` |
| `NoSuchMessageException` | No matching keys and no suitable default message | Provide general translations and a safe fallback |
| The four keys differ from expectations | `fieldType` is null, nested path, custom prefix/formatter | Use actual `getCodes()`, write unit tests |
| `age=abc` error lacks `Min` key | Type conversion failed before `@Min` | Handle `typeMismatch` separately |
| `age=17` reports `Min` | Conversion succeeded, constraint failed | This is the expected behavior |
| Renamed `@ModelAttribute("registration")` | Specific keys change with object name | Update bundles or use general keys |
| API returns rejected password | Serializing `FieldError` straight to JSON | Return only field, code, and controlled message |
| Resolver unit test PASSES but HTTP still fails | Different Locale/MessageSource/binder | Check integration with MockMvc |

### Step-by-Step Debugging Order

1. Did the error originate from **type conversion**, Bean Validation, or a custom validator?
2. What is the object name from `BindingResult.getObjectName()`?
3. What keys in what order does `FieldError.getCodes()` or `ObjectError.getCodes()` return?
4. Which keys exist in `messages.properties`/`messages_vi.properties`?
5. Is the locale selected from `Accept-Language` correct?
6. Which message does `MessageSource.getMessage(error,locale)` select?
7. Is there a custom resolver, prefix, formatter, or initializer?
8. Does a MockMvc integration test verify the right HTTP contract?

## 14. Self-Check

**Question 1.** What is the first code for `typeMismatch` on `registration.age` of type `Integer`? — `typeMismatch.registration.age`.

**Question 2.** What is the third key? — `typeMismatch.java.lang.Integer`, not `typeMismatch.int`.

**Question 3.** How many keys does object error `account.invalid` on object `registration` have? — Two: `account.invalid.registration`, `account.invalid`.

**Question 4.** Why can `groups[0].name` produce more than four codes? — Spring generates both indexed and non-indexed property paths.

**Question 5.** Does `DefaultMessageCodesResolver` read Vietnamese bundle files? — No; `MessageSource` looks up bundles.

**Question 6.** When the first key is not found, does Spring try the next key? — Yes, following the order of `getCodes()`.

**Question 7.** Are `@Min(18)` and `typeMismatch` the same? — No. One is a constraint on a converted number; the other is a type conversion error.

**Question 8.** Can changing the model name affect i18n? — Yes, because `code.objectName.field` changes.

**Question 9.** What must you do when adding `setPrefix("validation.")`? — Synchronize the keys in the resource bundles.

**Question 10.** How do you verify both fallbacks and translations? — Unit test the resolver for code order and test `MessageSource`/MockMvc per locale.

## 15. Checklist

- [ ] Identify the base code and error type before designing translations.
- [ ] Remember **two object-level keys**, **four field-level keys** in the standard case.
- [ ] Check collection/nested fields with multiple indexed and non-indexed keys.
- [ ] Understand the difference between `int` and `Integer` for type-based keys.
- [ ] Use `BindingResult`/`FieldError.getCodes()` to confirm actual keys.
- [ ] Use `MessageSource.getMessage(error,locale)` for translated messages.
- [ ] Have a base `messages.properties` and required language files, encoded in UTF-8.
- [ ] Test vi/en and fallback scenarios where specific keys are missing.
- [ ] Do not confuse `getDefaultMessage()` with Spring code-based i18n.
- [ ] When changing an object name, update or verify fallback message keys.
- [ ] If customizing prefix/formatter, migrate all affected keys.
- [ ] Never leak rejected values or stack traces in responses.
- [ ] Verify with both algorithm unit tests and HTTP integration tests.

**Remember:** `DefaultMessageCodesResolver` generates code lists **from specific to general**: object errors usually have **2 codes**, simple field errors usually have **4 codes**, and nested collections can have more. `MessageSource` uses those keys and the locale to choose the message. Error codes let an application reuse rules, while translations help users understand errors in the right language.
