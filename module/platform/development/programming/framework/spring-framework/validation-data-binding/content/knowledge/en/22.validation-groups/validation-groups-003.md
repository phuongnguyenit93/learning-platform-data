# Passing Groups to `Validator` or `@Validated` in Spring Framework

## 1. Goal: Select the Right Rule Set to Validate by Context

A single DTO can serve multiple business flows: creating (`Create`), updating (`Update`), or submitting for review (`Submit`). The requirements on the same field are not always identical across flows:

- On **create**, `id` is generated by the server, so it must be `null`.
- On **update**, `id` must be non-null.
- Product name (`name`) is always required; in many designs it belongs to the default `Default` group.
- Quantity (`quantity`) must be positive on create or update.

Jakarta Bean Validation **validation groups** let you declare constraint sets per context and **pass groups at validation time**, rather than duplicating constraints or writing branching `if` logic inside a validator.

This article focuses on **two ways of passing groups**:

1. **Calling `jakarta.validation.Validator` programmatically:** `validator.validate(bean, Create.class)`, `validateProperty(...)`, or `validateValue(...)`.
2. **Having Spring trigger validation:** `@Validated(Create.class)` on an MVC parameter or in method validation configuration, depending on the applicable integration point.

Key takeaway: **Jakarta's `@Valid` has no attribute for selecting groups**, whereas **Spring's `@Validated` allows specifying groups**. However, where `@Validated` is placed (controller parameter vs. service type) determines *which mechanism* executes; not every `@Validated` annotation behaves the same way.

## 2. Defining Groups and Assigning Constraints to Groups

A group is typically an **empty marker interface**. No method implementations are required:

```java
public interface Create {}
public interface Update {}
```

These are two illustrative interfaces; in the standalone runnable code in section 5, they are declared as nested interfaces inside a class.

Declaring constraints:

```java
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Null;

public class ProductForm {

    @NotBlank
    private String name;

    @Null(groups = Create.class)
    @NotNull(groups = Update.class)
    private Long id;

    @Min(value = 1, groups = {Create.class, Update.class})
    private int quantity;
}
```

Meaning:

- `@NotBlank` omits `groups` ⇒ belongs to **`jakarta.validation.groups.Default`**.
- `@Null(groups=Create.class)` belongs only to the `Create` group.
- `@NotNull(groups=Update.class)` belongs only to the `Update` group.
- `@Min(..., groups={Create.class,Update.class})` belongs to both groups.
- Placing `@Null` and `@NotNull` on the same property **does not conflict** here because they belong to two groups used in **different operations**. However, validating both `Create` and `Update` simultaneously on the same object means `id` cannot satisfy both conditions.

> Think of `groups` on an annotation as **which groups a rule is registered for**, and the `groups` argument passed to `Validator` or `@Validated` as **which groups are requested to execute**.

### 2.1. The Default Group Does Not Automatically Run Alongside Other Groups

If a constraint does not declare `groups`, it resides in the `Default` group. When no group is passed to the API, Bean Validation automatically selects `Default`.

```java
validator.validate(form);                          // Default
validator.validate(form, Default.class);           // Explicit Default
validator.validate(form, Create.class);            // Create
validator.validate(form, Update.class);            // Update
validator.validate(form, Default.class, Create.class);
```

When passing **only** `Create.class`, constraints belonging solely to `Default` **do not automatically run alongside it**, unless **group inheritance, a group sequence, group conversion**, or related metadata causes that effect. This is a common pitfall: a form returns an empty violation set when `Create` is selected even though `name` is blank, because `name` only has `@NotBlank` in `Default`.

There are three design options if you want `name` validated during Create:

1. Assign the constraint to both groups: `@NotBlank(groups={Default.class,Create.class})`.
2. When calling programmatically, pass `Default.class, Create.class`.
3. Design explicit group inheritance or a group sequence when it makes long-term sense.

Do not use groups arbitrarily without knowing which constraints are covered.

## 3. Passing Groups Directly via `jakarta.validation.Validator`

The standard `jakarta.validation.Validator` interface accepts varargs `Class<?>... groups`. Three commonly used methods:

| API | Input | Scope |
| --- | --- | --- |
| `validate(T object, Class<?>... groups)` | Existing bean + groups | All constraints within the matching object graph, cascading via `@Valid` |
| `validateProperty(T object, String propertyName, Class<?>... groups)` | Bean + property name + groups | Constraints on **one existing property**, no cascade |
| `validateValue(Class<T> beanType, String propertyName, Object value, Class<?>... groups)` | Bean class + property name + candidate + groups | Constraints on **one property for a hypothetical value**, no instance needed, no cascade |

These methods return `Set<ConstraintViolation<T>>`. An empty set means **the selected constraints in the current call scope** found no violations; it does not prove every application rule was checked.

### 3.1. Example Passing One or Multiple Groups

```java
Set<ConstraintViolation<ProductForm>> createErrors =
        validator.validate(form, Create.class);

Set<ConstraintViolation<ProductForm>> updateErrors =
        validator.validate(form, Update.class);

Set<ConstraintViolation<ProductForm>> combinedErrors =
        validator.validate(form, Default.class, Create.class);
```

All three calls use the **same object**, differing only in the group list. **No execution order is guaranteed** simply because `Default.class` is passed before `Create.class`. To evaluate sequentially and stop when an earlier group fails, use `@GroupSequence` (section 7).

**Note:** passing both `Create` and `Update` in an example with `@Null` and `@NotNull` on the same ID is not useful: for any ID, at least one of the two groups fails. Groups represent *scenarios*, not rule sets to merge indiscriminately.

### 3.2. `validateProperty` and `validateValue` Still Select Groups

When you only need to check the ID in a UI step:

```java
validator.validateProperty(form, "id", Create.class);

validator.validateValue(
        ProductForm.class, "id", 123L, Create.class);
```

The first call checks the **ID value currently held in `form`**. The second checks `123L` against `id`'s constraints in the `Create` group, **without instantiating a new `ProductForm`** and **without mutating `form`**.

Limitations of these two field-level APIs:

- They do not execute class-level or cross-field constraints just because those involve the property.
- They do not cascade into child beans via `@Valid`.
- With `validateValue`, the value must match the constraint's expected type; it is not an HTTP string conversion tool.
- Do not use a single field-level result to conclude that the entire DTO is valid.
- `propertyName` must be a valid property; an invalid name or disallowed null arguments can throw an exception rather than always returning an empty violation set.

For the final request-acceptance step, prefer validating the entire object with `validate(bean, groups...)` or the equivalent Spring mechanism.

### 3.3. Distinguishing `jakarta.validation.Validator` and Spring `Validator`

Two interfaces share the same name but have different methods:

```text
jakarta.validation.Validator
    validate(bean, Class<?>... groups)
    validateProperty(bean, "field", Class<?>... groups)
    validateValue(Bean.class, "field", candidate, Class<?>... groups)

org.springframework.validation.Validator
    supports(Class<?> clazz)
    validate(Object target, Errors errors)

org.springframework.validation.SmartValidator
    validate(Object target, Errors errors, Object... validationHints)
```

`org.springframework.validation.SmartValidator` extends Spring's `Validator` interface and allows passing **validation hints**; with a `LocalValidatorFactoryBean` backed by Jakarta Bean Validation, `Class<?>` hints can act as validation groups.

Spring integration example (not a standalone runnable program):

```java
import org.springframework.validation.BeanPropertyBindingResult;
import org.springframework.validation.SmartValidator;

SmartValidator springValidator = /* Spring-configured bean */;
ProductForm form = /* bound bean */;
var errors = new BeanPropertyBindingResult(form, "form");

// Hint Create.class is converted to a validation group via the Jakarta adapter.
springValidator.validate(form, errors, Create.class);

boolean hasErrors = errors.hasErrors();
```

This snippet illustrates API usage inside a class/method where variables already exist. If you want `Set<ConstraintViolation>` directly and explicit group selection, inject `jakarta.validation.Validator`. If you are handling binding and `BindingResult` in MVC, Spring's validator/adapter is helpful because it maps errors to `FieldError`/`ObjectError`.

## 4. `@Valid` and `@Validated`: Both Trigger Validation, Differ in Group Selection

### 4.1. `@Valid` from Jakarta

`@Valid` import:

```java
import jakarta.validation.Valid;
```

Used on a controller object parameter:

```java
@PostMapping("/products")
public ResponseEntity<?> create(@Valid @RequestBody ProductForm form) {
    return ResponseEntity.ok().build();
}
```

When processed by Spring MVC with an appropriate Bean Validation provider, `@Valid` on a command object requests default validation (`Default`). `@Valid` itself **has no `value()` attribute to pass `Create.class`**. It is also used on properties/type arguments to **cascade** into child objects during whole-bean validation.

### 4.2. `@Validated` from Spring

`@Validated` import:

```java
import org.springframework.validation.annotation.Validated;
```

To select the `Create` group for a DTO in Spring MVC:

```java
@PostMapping("/products")
public ResponseEntity<?> create(
        @Validated(Create.class) @RequestBody ProductForm form) {
    return ResponseEntity.ok().build();
}
```

`@Validated(Create.class)` requests constraints belonging to `Create` through the applicable MVC argument validation mechanism. Important difference: it **does not implicitly add `Default`** to `Create`. If you want both, write:

```java
@Validated({Default.class, Create.class})
@RequestBody ProductForm form
```

That is a valid declaration at a **method parameter** position; this example is only two lines of a signature, not standalone code.

### 4.3. Comparison Table

| Aspect | `@Valid` | `@Validated` |
| --- | --- | --- |
| Package | `jakarta.validation.Valid` | `org.springframework.validation.annotation.Validated` |
| Specify groups via attribute | No | Yes: `value = {Group.class,...}` |
| Used on Spring MVC command object parameter | Yes | Yes |
| Group typically used | `Default` on top-level call, or active group on cascade | Declared groups, or default context if omitted |
| Cascade on property/type argument | Yes, specifically for cascading | Does not replace `@Valid` in object graphs |
| Trigger method validation via AOP on Spring service | Not the equivalent Spring AOP trigger | Can act as a class-level trigger if AOP/method validation infrastructure is enabled |
| Is it a constraint like `@NotBlank`? | No | No |

**Do not put `@Validated` on a child field expecting it to cascade automatically.** To descend into nested beans, you still need `@Valid`. To switch groups during cascade, use group propagation rules or `@ConvertGroup` (section 8).

## 5. Standalone Runnable Java 17+ Example: Observing `Default`, `Create`, and `Update`

The walkthrough below uses **Jakarta Bean Validation 3.x + Hibernate Validator 8.x**. You do not need to boot Spring to understand how groups are passed to `Validator`; this helps establish predictable results before integrating with Spring MVC.

### 5.1. `pom.xml`

Create `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>example</groupId>
    <artifactId>groups-validated-demo</artifactId>
    <version>1.0.0</version>
    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.hibernate.validator</groupId>
            <artifactId>hibernate-validator</artifactId>
            <version>8.0.1.Final</version>
        </dependency>
    </dependencies>
</project>
```

`hibernate-validator` is the **provider** implementing Jakarta Bean Validation and brings in the required dependencies. The CLI example selects Hibernate Validator's `ParameterMessageInterpolator` so it does not require separate Jakarta Expression Language (EL) configuration. That is a **provider-specific** detail; applications using EL expressions in message templates must include a compatible configuration.

### 5.2. `GroupPassingDemo.java`

Create a file matching the class name `GroupPassingDemo.java` in the directory containing `pom.xml`:

```java
import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import jakarta.validation.ValidatorFactory;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Null;
import jakarta.validation.groups.Default;

import org.hibernate.validator.HibernateValidator;
import org.hibernate.validator.messageinterpolation.ParameterMessageInterpolator;

import java.util.List;
import java.util.Set;

public class GroupPassingDemo {

    public interface Create {}
    public interface Update {}

    public static final class ProductForm {
        @NotBlank
        private final String name;

        @Null(groups = Create.class)
        @NotNull(groups = Update.class)
        private final Long id;

        @Min(value = 1, groups = {Create.class, Update.class})
        private final int quantity;

        public ProductForm(String name, Long id, int quantity) {
            this.name = name;
            this.id = id;
            this.quantity = quantity;
        }

        public Long getId() {
            return id;
        }
    }

    private static void show(
            String label, Set<? extends ConstraintViolation<?>> violations) {
        List<String> paths = violations.stream()
                .map(v -> v.getPropertyPath().toString())
                .sorted()
                .toList();
        System.out.println(label + " -> " + paths);
    }

    public static void main(String[] args) {
        try (ValidatorFactory factory = Validation
                .byProvider(HibernateValidator.class)
                .configure()
                .messageInterpolator(new ParameterMessageInterpolator())
                .buildValidatorFactory()) {

            Validator validator = factory.getValidator();

            ProductForm form = new ProductForm("", 7L, 0);

            show("Default", validator.validate(form));
            show("Create", validator.validate(form, Create.class));
            show("Update", validator.validate(form, Update.class));
            show("Default+Create",
                    validator.validate(form, Default.class, Create.class));
            show("property id / Create",
                    validator.validateProperty(form, "id", Create.class));
            show("candidate id=null / Update",
                    validator.validateValue(
                            ProductForm.class, "id", null, Update.class));
            show("candidate quantity=2 / Create",
                    validator.validateValue(
                            ProductForm.class, "quantity", 2, Create.class));

            ProductForm fresh = new ProductForm("Ready", null, 2);
            show("fresh / Create",
                    validator.validate(fresh, Create.class));
            show("fresh / Update",
                    validator.validate(fresh, Update.class));

            System.out.println("originalId=" + form.getId());
        }
    }
}
```

### 5.3. Compile and Run

Requires **JDK 17+** and **Maven**. Run in the directory containing `pom.xml` and `GroupPassingDemo.java`.

Linux/macOS (Bash):

```bash
mvn -q dependency:build-classpath -Dmdep.outputFile=classpath.txt
CP="$(cat classpath.txt)"
javac -encoding UTF-8 -cp "$CP" GroupPassingDemo.java
java -cp ".:$CP" GroupPassingDemo
```

Windows (PowerShell):

```powershell
mvn -q dependency:build-classpath -Dmdep.outputFile=classpath.txt
$cp = (Get-Content -Raw classpath.txt).Trim()
javac -encoding UTF-8 -cp $cp GroupPassingDemo.java
java -cp ".;$cp" GroupPassingDemo
```

**Expected stdout** (excluding Maven or provider logs/warnings):

```text
Default -> [name]
Create -> [id, quantity]
Update -> [quantity]
Default+Create -> [id, name, quantity]
property id / Create -> [id]
candidate id=null / Update -> [id]
candidate quantity=2 / Create -> []
fresh / Create -> []
fresh / Update -> [id]
originalId=7
```

Line-by-line analysis:

1. `Default -> [name]`: `@NotBlank name` is in `Default`; `name=""` violates it. The ID and `@Min` constraints do not belong to `Default`, so they do not run.
2. `Create -> [id, quantity]`: `id=7L` violates `@Null(groups=Create.class)`; `quantity=0` violates `@Min(1,groups=Create.class)`. The blank `name` **is not detected in this call** because `@NotBlank` belongs only to `Default`.
3. `Update -> [quantity]`: ID is non-null so `@NotNull(groups=Update.class)` passes; quantity still fails.
4. `Default+Create -> [id, name, quantity]`: both groups are requested, so all three rules apply.
5. `property id / Create -> [id]`: validates only the `id` property under `Create`, without checking `name` or `quantity`.
6. `candidate id=null / Update -> [id]`: `validateValue` evaluates a hypothetical value; `Update`'s `@NotNull` fails.
7. `candidate quantity=2 / Create -> []`: `2` satisfies minimum `1`.
8. `fresh / Create -> []`: `id=null` and `quantity=2` satisfy `Create`. Even though `fresh` has a valid name, that does not cause `Default` to run automatically.
9. `fresh / Update -> [id]`: null ID violates the `Update` requirement.
10. `originalId=7`: all validation calls only inspect and never mutate the object.

The `show` helper sorts `getPropertyPath()` so it does not rely on `Set<ConstraintViolation<?>>` iteration order. If multiple constraints fail on the same property, the path can repeat; the size of the violation set does not always equal the number of invalid fields.

**Scope note:** this code **runs standalone** with Hibernate Validator 8. The Spring snippets in the following sections are **integration code** that belong in a Spring Boot/Spring MVC project with the appropriate dependencies, imports, and configuration; they do not belong in `GroupPassingDemo.java`.

## 6. Passing Groups in Spring MVC with `@Validated` on Parameters

When data from HTTP JSON or forms is bound into a DTO, you can select groups in the controller.

### 6.1. Illustrative DTO for Create/Update

In a Spring Boot 3.x project (Jakarta namespace):

```java
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Null;

public class ProductRequest {
    public interface Create {}
    public interface Update {}

    @NotBlank(groups = {Create.class, Update.class})
    private String name;

    @Null(groups = Create.class)
    @NotNull(groups = Update.class)
    private Long id;

    @Min(value = 1, groups = {Create.class, Update.class})
    private int quantity;

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }

    public int getQuantity() { return quantity; }
    public void setQuantity(int quantity) { this.quantity = quantity; }
}
```

In this example, `@NotBlank` declares both groups to ensure `name` is validated on both create and update, avoiding the `Default` trap from section 5. Nesting groups inside the DTO keeps the example short; real projects often place marker interfaces in a dedicated package for consistent use across controllers and services.

### 6.2. Controller Selecting the Matching Group

```java
import org.springframework.http.ResponseEntity;
import org.springframework.validation.BindingResult;
import org.springframework.validation.annotation.Validated;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/products")
public class ProductController {

    @PostMapping
    public ResponseEntity<?> create(
            @Validated(ProductRequest.Create.class)
            @RequestBody ProductRequest input,
            BindingResult errors) {
        if (errors.hasErrors()) {
            return ResponseEntity.badRequest()
                    .body(errors.getFieldErrors().stream()
                            .map(e -> e.getField() + ":" + e.getCode())
                            .toList());
        }
        // Service applies authorization, business checks, and generates ID.
        return ResponseEntity.ok("Accepted create");
    }

    @PutMapping("/{id}")
    public ResponseEntity<?> update(
            @PathVariable Long id,
            @Validated(ProductRequest.Update.class)
            @RequestBody ProductRequest input,
            BindingResult errors) {
        if (errors.hasErrors() || !id.equals(input.getId())) {
            return ResponseEntity.badRequest().body("Invalid update");
        }
        // Service verifies edit permission, state, and persistence data.
        return ResponseEntity.ok("Accepted update");
    }
}
```

In the signatures above:

- `@Validated(ProductRequest.Create.class)` passes **one group** for DTO validation on `POST`.
- `@Validated(ProductRequest.Update.class)` passes a different group on `PUT`.
- `BindingResult` sits immediately after the corresponding DTO parameter so Spring MVC has a target for errors when parameter validation follows this path.
- `@RequestBody` handles JSON deserialization before constraint validation; malformed JSON or object-creation failures can throw a different exception before entering the controller.
- Comparing path ID and body ID only illustrates a consistency rule; production code must handle null bodies, authorization, missing records, and state conflicts.

If you only use `@Valid` on `ProductRequest` when all constraints declare `Create`/`Update` groups, **`Default` does not contain those constraints**; `POST`/`PUT` may skip critical rules. Selecting the right group with `@Validated` accurately reflects each operation's contract.

### 6.3. Two Validation Paths in Spring MVC

Modern Spring MVC supports:

1. **Per-command-object validation**: `@ModelAttribute`, `@RequestBody`, or `@RequestPart` with `@Valid`/`@Validated` under eligible conditions; errors can flow into `BindingResult` if declared properly by the handler, or become `MethodArgumentNotValidException`.
2. **Method validation**: when constraints are declared directly on method parameters or return values, or other signature traits trigger method validation; this can raise `HandlerMethodValidationException`. Method validation can include constraints on nested objects via `@Valid`.

Do not claim every case raises only one exception type. Error handling depends on the handler signature, Spring version, whether `BindingResult` immediately follows the failing parameter, and whether method parameter constraints are present.

**Specific to Spring Framework 6.1+:** Spring MVC has **built-in method validation** for controllers. If a controller places `@Validated` at the **class level**, method validation may route through an AOP proxy instead of the built-in path. The Spring guide recommends **omitting class-level `@Validated` on controllers** when you want built-in method validation, while still allowing `@Validated(Group.class)` **on command object parameters** to select groups. Those two positions serve different roles and should not be conflated.

## 7. Group Inheritance and `@GroupSequence` When Multiple Groups Are Needed

### 7.1. Multiple Groups Have No Default Ordering

```java
validator.validate(form, Default.class, Create.class);
```

This statement requests validating constraints in both `Default` and `Create`. It **does not** mean "run `Default` first; stop if it fails". Evaluation order across groups in a non-sequence call **is not guaranteed**.

If an application needs cheap groups to run before expensive groups, use `@GroupSequence`:

```java
import jakarta.validation.GroupSequence;
import jakarta.validation.groups.Default;

interface ExpensiveChecks {}

@GroupSequence({Default.class, ExpensiveChecks.class})
interface FullChecks {}
```

These are illustrative interfaces. When calling `validator.validate(form, FullChecks.class)`:

1. `Default` is evaluated first;
2. If `Default` has violations, later groups **are not validated**;
3. Only when `Default` passes is `ExpensiveChecks` evaluated.

Constraints belonging to `ExpensiveChecks` must declare `groups=ExpensiveChecks.class`. Do not mix ordered groups with `validate(form, Default.class, ExpensiveChecks.class)` expecting short-circuit behavior. When **redefining the `Default` group sequence on a class**, specific declaration rules apply (you must include that class itself in the sequence); do not mechanically substitute `Default.class` in the class-level annotation.

**Some providers offer fail-fast configuration**, but that is not a portable replacement for `@GroupSequence`. Fail-fast has its own semantics and violation selection order; do not rely on it to enforce business ordering.

### 7.2. Group Inheritance

A child group can extend another marker interface:

```java
interface BaseChecks {}
interface StrictChecks extends BaseChecks {}
```

When `StrictChecks` is requested, constraints declared in `BaseChecks` are also within validation scope via group inheritance rules. However, **no execution order** is imposed between constraints solely from interface inheritance. Use a dedicated sequence when ordering and short-circuiting are required.

Overly complex group models make APIs hard to maintain. When Create and Update differ substantially in field structure, consider separate DTOs instead of stacking many interfaces and sequences.

## 8. Cascading `@Valid` and `@ConvertGroup`: Where Do Groups Propagate?

Suppose `OrderRequest` contains `Customer`. The validator will not automatically check constraints inside `Customer` just because the field is non-null; `@Valid` is required to enable cascading on that field.

```java
class Customer {
    @NotBlank(groups = Create.class)
    String displayName;
}

class OrderRequest {
    @Valid
    Customer customer;
}
```

When calling `validator.validate(order, Create.class)`, the `Create` group is **propagated along the cascade path** to `Customer` per Jakarta Bean Validation rules; thus `displayName` is checked when `customer` is present. `@Valid` does not forbid `customer == null` by itself; if presence is required, add `@NotNull` at the property level in the desired group.

Sometimes the root bean uses `Default` while the child bean needs `Create`. `@ConvertGroup` can switch groups during cascade:

```java
import jakarta.validation.Valid;
import jakarta.validation.groups.ConvertGroup;
import jakarta.validation.groups.Default;

class OrderRequest {
    @Valid
    @ConvertGroup(from = Default.class, to = Create.class)
    Customer customer;
}
```

This example describes a cascade path and assumes `Customer` and `Create` are defined in the project. When validating `OrderRequest` with `Default`, `Default` is converted to `Create` upon entering `customer`. `@ConvertGroup` **does not execute** without a valid `@Valid` cascade point and does not alter constraints on the root bean or container. With `validateProperty`/`validateValue`, there is no cascaded validation, so group conversion effects cannot be inferred across the full object graph.

### 8.1. Containers and Elements

Some constraints attach to the container, while others attach to elements:

```java
@NotEmpty(groups = Create.class)
List<@NotBlank(groups = Create.class) String> codes;
```

When the validator runs `Create`, it checks both that the container is non-empty and that each code is non-blank. When running only `Default` with no other configuration, neither `Create` constraint is invoked. You do not need `@Valid` just to apply `@NotBlank` to `String` elements: that is a container-element constraint, not a cascade into a child bean.

## 9. `@Validated` on Services: Method Validation Differs from Manual DTO Validation

Beyond controllers, `@Validated` also acts as a trigger for **Spring method validation**. Consider a service with annotated parameter constraints:

```java
import jakarta.validation.constraints.NotBlank;
import org.springframework.stereotype.Service;
import org.springframework.validation.annotation.Validated;

@Service
@Validated
public class CodeService {
    public void reserve(@NotBlank String code) {
        // Service logic...
    }
}
```

When method validation infrastructure is configured (such as `MethodValidationPostProcessor` or appropriate auto-configuration), calling `reserve("")` **through the Spring proxy** is validated and can be intercepted before running the method body. Class-level `@Validated` serves as the AOP trigger; **merely having the annotation does not mean every internal Java call is validated**.

### 9.1. Selecting Groups for Service Method Validation

Example service dedicated to Create operations:

```java
@Service
@Validated(Create.class)
public class CreateCodeService {
    public void reserve(
            @NotBlank(groups = Create.class) String code) {
        // If method validation proxy is active, a blank code causes a violation.
    }
}
```

`@Validated(Create.class)` on the class specifies the group used for method validation under the corresponding Spring AOP mechanism. If a method adds `@Validated` to override groups, verify the Spring version, method validation configuration, and method-level rules; do not infer behavior from an annotation placement that your specific Spring stack does not process.

Practical prerequisites:

- A compatible Bean Validation provider on the classpath.
- Spring method validation infrastructure enabled (possibly auto-configured by Boot).
- The service is a Spring-managed bean and calls go **through the appropriate proxy/interceptor**.
- The method must be interceptable by the proxy (e.g., a public method); self-invocation such as `this.reserve("")` within the same instance can **bypass the proxy**.
- Constraints must belong to the requested group.

Do not use method validation proxies as a substitute for authorization, transaction integrity, database state checks, or business policies.

### 9.2. Distinguishing Three Placements of `@Validated`

| Placement | Primary purpose |
| --- | --- |
| `@Validated(Create.class)` on a DTO parameter in Spring MVC | Selects groups when validating the bound command object |
| `@Validated` on a Spring service class | Marks the type for proxy-based method validation when infrastructure is configured |
| `@Validated` at Spring MVC controller class level | Can trigger AOP-based method validation; in Spring MVC 6.1+ avoid it if you want built-in method validation |
| `@Valid` on a property or type argument in a DTO | Enables cascading into child beans; does not select groups |

**Do not mechanically apply** `@Validated(Create.class)` at the controller class level assuming every `@RequestBody`/`@ModelAttribute` across all handlers will automatically validate `Create` via the same path. Placing it on the specific parameter is clearer when controlling payload validation groups.

## 10. Distinguishing Validation Errors from Binding/Serialization Errors

In Spring MVC, the processing pipeline typically follows:

1. **Deserialize/bind:** JSON, form fields, or query parameters are converted into Java objects.
2. **Validate:** Bean Validation checks constraints in the selected groups, including groups passed from `@Validated` or controller adapters.
3. **Business processing:** services verify rules that cannot be expressed purely with annotations, authorization, and database uniqueness.
4. **Return appropriate errors:** controllers or exception handlers map errors to the HTTP contract without leaking sensitive data.

For example, if JSON sends `{"quantity":"abc"}` when the DTO defines `int quantity`, Jackson or the binder can report a type conversion error **before `@Min` ever gets a chance to run**. Validation groups do not convert mismatched input types into valid Java values.

Conversely, sending `{"quantity":0}` for a Create DTO creates the `int` and can violate `Create`'s `@Min(1)`. When using primitive `int` in a DTO, a missing field may result in the default `0` or be rejected by a strict deserialization policy; if you need to distinguish "omitted" from `0`, use `Integer` and `@NotNull` in the appropriate group.

### 10.1. `BindingResult` and Error Codes

In a handler using `@Validated(Create.class) @RequestBody ProductRequest input, BindingResult errors`, `errors` binds to the input parameter immediately preceding it. You can inspect `errors.getFieldErrors()` for field/code pairs and `errors.getGlobalErrors()` for object-level rules. If the method signature changes in a way that triggers direct method validation, the error-delivery mechanism can also change.

Avoid returning `ConstraintViolation.getInvalidValue()`, passwords, tokens, or private data directly to clients. Use localized messages and stable error codes per your API contract. Do not use translated `getMessage()` strings as long-term logical identifiers.

### 10.2. `@Valid` Does Not Equal Method Validation

`@Valid` is a signal for cascading or validating an input object in Spring MVC, not a constraint annotation like `@NotNull`. Placing `@Valid` alone on a method parameter does not create executable method validation; when direct parameter constraints such as `@NotNull` or `@Min` are present, method validation can be triggered. In Spring Framework 6.1+, the execution path may be MVC's built-in method validation, distinct from AOP `@Validated` on service or controller classes.

## 11. API Selection Table by Scenario

| Scenario | How to select groups | Why |
| --- | --- | --- |
| Service needs to validate whole DTO under `Create` | `jakartaValidator.validate(dto, Create.class)` | Explicit, returns `ConstraintViolation` |
| Check an existing field under `Update` | `validateProperty(dto, "id", Update.class)` | Single property only, no cascade |
| Check a prospective ID before assigning | `validateValue(Dto.class, "id", candidate, Update.class)` | No instance needed, no mutation |
| MVC POST body needs `Create` group | `@Validated(Create.class) @RequestBody Dto dto` | Spring selects group during argument validation |
| MVC PUT body needs `Update` group | `@Validated(Update.class) @RequestBody Dto dto` | Same DTO type, different rule set |
| MVC wants both `Default` and `Create` | `@Validated({Default.class, Create.class})` | Explicitly requests two groups |
| Service needs method parameter validation | `@Validated` on bean + constraints on method parameters | Proxy-based method validation when configured |
| Constraints on a child bean | `@Valid` on field/type argument | Enables cascading down the object graph |
| Child bean needs a different group from parent | `@Valid` + `@ConvertGroup` | Converts group at the cascade point |
| Want group B to run only if group A passes | `@GroupSequence` | Provides ordering and short-circuiting |
| Check constraints on a single independent field | `validateValue`/`validateProperty` | Convenient for UI, not conclusive for the whole bean |

## 12. Common Errors and Fixes

| Symptom | Cause | Fix |
| --- | --- | --- |
| `@Validated(Create.class)` skips `@NotBlank` with no `groups` | `@NotBlank` belongs to `Default`; `Create` does not include it implicitly | Declare groups or also pass `Default` |
| `@Valid` does not check `Create` constraints | `@Valid` cannot select groups; usually runs `Default` | Use `@Validated(Create.class)` on the appropriate parameter |
| Passing `Create.class,Update.class` causes ID errors for any value | The two groups contain conflicting `@Null`/`@NotNull` | Choose a single context or redesign the constraints |
| Calling `validate(form, Default.class, Create.class)` expecting ordering | Group varargs do not guarantee execution order | Use `@GroupSequence` |
| Validation returns empty even though the object has invalid fields | Only the selected fields/groups were checked | Verify groups and scope; validate whole object at the boundary |
| `validateValue` misses cross-field rules | No full bean instance; class-level constraints are skipped | Use `validate(dto, ...)` |
| `validateProperty` misses nested errors | Does not cascade through `@Valid` | Validate the root bean or child bean |
| Importing `org.springframework.validation.Validator` and calling `validate(dto,Create.class)` | Spring `Validator` API differs from Jakarta `Validator` | Import `jakarta.validation.Validator` |
| Putting `@Validated` on a nested field expecting cascade | `@Validated` does not replace `@Valid` in object graphs | Use `@Valid` and `@ConvertGroup` where needed |
| Service has `@Validated` but internal method call is not intercepted | Self-invocation bypasses the AOP proxy | Invoke through the bean/proxy or refactor the boundary |
| Adding `@Validated` on controller class changes error handling | May switch to AOP method validation instead of MVC built-in | Place annotations carefully, especially in Spring 6.1+ |
| No errors produced despite annotations on DTO | Missing provider or validation not enabled | Configure `LocalValidatorFactoryBean`/appropriate starter |
| Wrong-type JSON treated as group not running | Failure happens before Bean Validation | Handle deserialization/binding separately |
| Root constraint group works, but child bean is not validated | Missing `@Valid` cascade or wrong group conversion | Configure the cascade path and write tests |
| Selecting `Create` for PATCH while wanting omitted fields preserved | No distinction between absent and `null` | Use a dedicated PATCH model rather than groups as a deserialization policy |
| Assuming group validation enforces field write permissions | Groups validate data rules, not authorization | Enforce authorization and mass-assignment protection in service/binder |

### 12.1. Minimum Test Coverage

1. `validate(dto)` without groups and `validate(dto, Default.class)` yield equivalent results when metadata has no custom sequence/redefinition.
2. `Create` and `Update` differ on null/non-null ID, and shared rules are verified in each group.
3. `@Validated(Create.class)` on `@RequestBody` actually runs `Create` in a valid MVC request test.
4. Malformed HTTP bodies are distinguished from constraint violations; assert status codes and error contracts.
5. `BindingResult` immediately following the model parameter captures errors on supported validation paths.
6. Service method validation is triggered through the proxy; self-invocation is not relied upon as proof.
7. Group inheritance and sequences are tested to prove short-circuit behavior without relying on `Set` order.
8. Constraints on child beans execute when `@Valid` is present and groups propagate/convert properly.
9. Data boundaries: nested lists, very large DTOs, untrusted inputs, and database access.
10. When upgrading Spring or the validation provider, run integration tests for exception types and groups, especially for controller method validation.

## 13. Rules to Remember

- **Groups are assigned to constraints via `groups={...}`; groups are selected at execution time via arguments to `Validator` or `@Validated`.**
- **Passing no group ⇒ `Default`. Passing `Create` ⇒ only rules in `Create` and rules included by group metadata, never `Default` implicitly.**
- **`@Valid` has no attribute to pass groups; `@Validated` does.** `@Valid` is still required to cascade into child objects.
- **`jakarta.validation.Validator` and `org.springframework.validation.Validator` have different APIs.** The former returns a violation set and takes group varargs; the latter works with `Errors`. `SmartValidator` is the appropriate adapter for hints.
- **Spring MVC argument validation and Spring AOP method validation are two distinct mechanisms.** Place `@Validated` intentionally.
- **Multiple groups do not imply ordering or fail-fast behavior by default;** use `@GroupSequence` when business logic requires it.
- **Do not treat groups as an authorization mechanism or a substitute for separate DTOs** when Create and Update differ significantly in accepted fields.
- After early checks with `validateProperty`/`validateValue`, still validate the **final state of the entire bean** before persisting or submitting important data.
