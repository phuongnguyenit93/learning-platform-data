# Part ordering and mail client compatibility

An email is not just an HTML string. When you need a **plain text version**, **HTML**, **images rendered right inside the content**, and **attachments**, the email message is organized into multiple parts under the **MIME** (Multipurpose Internet Mail Extensions) standard. Choosing the `multipart/*` type, ordering the parts, and nesting them determines whether mail clients can pick the right content, render images in the right place, and recognize attachments.

In **Spring Framework Mail**, `JavaMailSender` sends the message, while `MimeMessage` and `MimeMessageHelper` help construct the MIME structure. This lesson focuses on **part ordering** and its effect on compatibility across email-reading applications.

## 1. Reading a MIME message like a tree

An email has message-level headers such as `From`, `To`, and `Subject`. The body can be a single piece of content or a **structure composed of multiple MIME parts**. Each part can have its own `Content-Type`, `Content-Disposition`, `Content-ID`, and payload.

Example:

```text
Email
├── Message headers: From, To, Subject, ...
└── Body: multipart/mixed
    ├── Part 1: multipart/related
    │   ├── Part 1.1: multipart/alternative
    │   │   ├── Part 1.1.1: text/plain
    │   │   └── Part 1.1.2: text/html
    │   └── Part 1.2: image/png; Content-ID: <logo>
    └── Part 2: application/pdf; attachment; filename="report.pdf"
```

Meaning:

- `multipart/alternative`: **mutually alternative** representations of the same content, typically plain text and HTML.
- `multipart/related`: parts **related to presenting one piece of content**, such as HTML referencing images via `cid:...`.
- `multipart/mixed`: combines relatively independent components, typically **the primary content and attachments**.

The `multipart/*` types carry **different semantics**. You cannot arbitrarily replace `alternative` with `mixed` or flatten all parts hoping every mail client figures it out.

## 2. `multipart/alternative`: ordering from simpler to richer representation

A notification message can contain the same information in two forms:

1. `text/plain`: readable by recipients when HTML is unsupported or plain text is preferred.
2. `text/html`: a fuller representation with formatting, links, and layout.

The MIME convention for `multipart/alternative` is to **place options in ascending order of representational richness**, typically **plain text first, HTML second**. The mail client may select the last option it understands and is permitted to render, rather than showing both as two separate emails.

```text
multipart/alternative
├── 1. text/plain     ← basic option, appears first
└── 2. text/html      ← richer representation, appears second
```

Illustrative MIME structure example (omitting some headers and encoding details):

```text
MIME-Version: 1.0
Content-Type: multipart/alternative; boundary="alt-demo"

--alt-demo
Content-Type: text/plain; charset=UTF-8

Hello!
View order at https://example.com/orders/123

--alt-demo
Content-Type: text/html; charset=UTF-8

<html>
  <body>
    <p>Hello!</p>
    <p><a href="https://example.com/orders/123">View order</a></p>
  </body>
</html>

--alt-demo--
```

The snippet above only illustrates part ordering and separation; real MIME generated by Jakarta Mail also includes transfer-encoding headers matching the payload.

**Both versions must convey the same business information.** If the HTML version has a confirmation link, transaction terms, or key details missing from plain text, users choosing text-only mode lose information.

### What happens if the order is reversed?

Suppose `text/html` appears before `text/plain`. A client following `multipart/alternative` preference order may choose the trailing text version even though it supports HTML. Other clients have their own handling. Therefore, wrong ordering can cause inconsistencies across clients.

**There is no rule that “HTML is always chosen”.** MIME describes options and preference order; the final choice still depends on mail client capabilities, settings, security policies, and rendering engines.

## 3. `multipart/related`: HTML and resources displayed together

An HTML email can reference an image located inside the very same message:

```html
<p>Hello!</p>
<img src="cid:brandLogo" alt="Brand logo">
```

`cid:brandLogo` references the MIME part carrying the matching `Content-ID` header:

```text
Content-Type: image/png
Content-ID: <brandLogo>
Content-Disposition: inline
```

The mail client can locate the image part by Content-ID and use it to render HTML. Typically this structure is placed inside `multipart/related`:

```text
multipart/related
├── text/html                ← root part, references cid:brandLogo
└── image/png                ← Content-ID: <brandLogo>
```

Here order affects compatibility. Per the MIME related structure, the **root part** can be specified via the `start` parameter; if that parameter is absent, the **first part** is usually treated as root. Hence, for simple structures, put the **primary HTML content part first**, then add the inline resources it references.

Notes:

- HTML uses `cid:brandLogo`, while the MIME header has `Content-ID: <brandLogo>`; angle brackets on the header are Content-ID syntax.
- `Content-ID` must match the `cid:` reference; typos stop the image from rendering.
- `Content-Disposition: inline` expresses intent to render within content, yet **does not guarantee** the mail client renders the image at the desired spot.
- Inline images may additionally appear in a mail client's attachment list, especially when MIME structure is suboptimal or the client applies its own rules.
- Images loaded from external URLs (`https://...`) are not inline MIME resources; external image blocking, image proxies, and mail client privacy policies can affect them.

With Spring, a practical rule is to **call `setText(...)` before `addInline(...)`**. `MimeMessageHelper` also recommends this order to avoid some mail readers mishandling inline image references.

## 4. `multipart/mixed`: attachments are separate parts

When sending a PDF or downloadable document alongside, the common structure is outermost `multipart/mixed`:

```text
multipart/mixed
├── Main email content
└── application/pdf
    ├── Content-Disposition: attachment
    └── filename="report.pdf"
```

The attachment part typically has `Content-Disposition: attachment` and a file name. The main body is placed first so clients easily recognize which part is readable content and which is an attachment.

Do not treat every part in `multipart/mixed` as alternative options: they are **coexisting components**. Placing `text/plain` and `text/html` as two direct sibling parts of `multipart/mixed` can make some mail clients render both or treat one part as an attachment. To pick **one of the two**, nest them inside `multipart/alternative`.

### When plain, HTML, inline image, and PDF are all present

This is a common structure matching how `MimeMessageHelper` builds with `MULTIPART_MODE_MIXED_RELATED`:

```text
multipart/mixed
├── multipart/related
│   ├── multipart/alternative
│   │   ├── text/plain
│   │   └── text/html (with <img src="cid:brandLogo">)
│   └── image/png; Content-ID: <brandLogo>; inline
└── application/pdf; attachment; filename="report.pdf"
```

In this structure:

- Outer `mixed` separates primary content from attached files.
- `related` groups displayable content with accompanying images.
- `alternative` groups plain and HTML versions in preference order.
- The PDF is an independent attachment part at the `mixed` level.

Another MIME variant is:

```text
multipart/mixed
├── multipart/alternative
│   ├── text/plain
│   └── multipart/related
│       ├── text/html
│       └── image/png; Content-ID: <brandLogo>
└── application/pdf; attachment
```

This variant bundles the entire HTML version and its resources into one alternative branch. When building emails with Spring Mail, you do not need to arrange boundaries by hand or force every structure to match one diagram. What matters is preserving **the semantics of each MIME group**, then checking results on target mail clients.

## 5. How does Spring Framework Mail build MIME structures?

Spring Mail typically uses:

- `JavaMailSender`: creates and sends `MimeMessage`.
- `MimeMessageHelper`: sets recipients, subject, text/HTML body, inline resources, and attachments.
- `MimeMessageHelper.MULTIPART_MODE_*`: chooses how multiparts are organized inside the message.

### 5.1. Choosing the right multipart mode

`MimeMessageHelper` offers primary modes:

| Mode | Overall structure | When to consider |
|---|---|---|
| `MULTIPART_MODE_NO` | No multipart initialized | Email has only one simple body, no inline resources or attachments. |
| `MULTIPART_MODE_MIXED` | A `multipart/mixed` at root level | Useful when combining components, though caution is needed with clients that may treat inline resources as attachments. |
| `MULTIPART_MODE_RELATED` | A `multipart/related` at root level | Fits content groups with related resources; presentation of independent attachments may vary by client. |
| `MULTIPART_MODE_MIXED_RELATED` | Outer `multipart/mixed`, inner `multipart/related` | Pragmatic choice when having both content/inline images and attachments; Spring's recommended structure for many cases. |

Example:

```java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper = new MimeMessageHelper(
    message,
    MimeMessageHelper.MULTIPART_MODE_MIXED_RELATED,
    "UTF-8"
);
```

The constructor `new MimeMessageHelper(message, true, "UTF-8")` uses the helper's default multipart mode (typically `MIXED_RELATED` in modern Spring Framework versions), yet naming the constant explicitly in learning examples makes the structural intent clear.

No MIME structure guarantees identical rendering across all mail clients. Choosing a mode is the **message design** step; testing on real target clients and receiving environments remains necessary before deploying important emails.

### 5.2. Complete example: plain text + HTML + inline logo + PDF

Suppose the Spring Boot application has configured `JavaMailSender` via `spring-boot-starter-mail` and SMTP server details. Two resources sit on the classpath:

```text
src/main/resources/
└── mail/
    ├── brand-logo.png
    └── report.pdf
```

Mail-sending service:

```java
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import java.nio.charset.StandardCharsets;
import org.springframework.core.io.ClassPathResource;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Service;

@Service
public class ReportEmailService {

    private final JavaMailSender mailSender;

    public ReportEmailService(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendReport(String recipient) throws MessagingException {
        MimeMessage message = mailSender.createMimeMessage();

        MimeMessageHelper helper = new MimeMessageHelper(
                message,
                MimeMessageHelper.MULTIPART_MODE_MIXED_RELATED,
                StandardCharsets.UTF_8.name()
        );

        helper.setFrom("reports@example.com");
        helper.setTo(recipient);
        helper.setSubject("Monthly report");

        String plainText = """
                Your monthly report is ready.
                See the attached report.pdf file.
                """;

        String htmlText = """
                <html>
                  <body>
                    <img src="cid:brandLogo" alt="Logo" width="120">
                    <h1>Monthly report</h1>
                    <p>Your monthly report is ready.</p>
                    <p>See the attached <strong>report.pdf</strong> file.</p>
                  </body>
                </html>
                """;

        // Set body first so the helper builds alternative in the right position.
        helper.setText(plainText, htmlText);

        // cid:brandLogo must match the inline image's Content-ID.
        helper.addInline(
                "brandLogo",
                new ClassPathResource("mail/brand-logo.png"),
                "image/png"
        );

        // Attachment belongs to the mixed group, separate from displayed content.
        helper.addAttachment(
                "report.pdf",
                new ClassPathResource("mail/report.pdf"),
                "application/pdf"
        );

        mailSender.send(message);
    }
}
```

Here, the API call order expresses intent:

1. Create `MimeMessage` and helper in two-tier `mixed/related` mode.
2. Set headers and **two content variants** with `setText(plainText, htmlText)`; the helper builds `multipart/alternative` with plain first, HTML second.
3. Call `addInline(...)` after `setText(...)` to place the logo in the related group and link it via `cid:brandLogo`.
4. Call `addAttachment(...)` to add the PDF as an attachment, independent of the inline image.
5. Send via `JavaMailSender`, letting Jakarta Mail handle MIME normalization, content encoding, and SMTP exchange.

The example uses static resources for easy reading. In real applications, report files can be generated dynamically via `ByteArrayResource` or suitable data sources. Ensure the resource remains readable when the mail library actually writes MIME content to the connection.

### 5.3. Plain text and HTML only, no inline or attachment needed

When there are only two content versions, `multipart/alternative` is still useful:

```java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper =
        new MimeMessageHelper(message, true, "UTF-8");

helper.setFrom("notifications@example.com");
helper.setTo("user@example.org");
helper.setSubject("Registration confirmation");

helper.setText(
        "Registration successful. Visit https://example.com/account",
        "<p>Registration successful. " +
        "<a href=\"https://example.com/account\">Open your account</a></p>"
);

mailSender.send(message);
```

`setText(plain, html)` is the overload designed to build **alternative contents**. Conversely, `setText(html, true)` only sets HTML content and does not auto-generate an equivalent-quality plain text version. To support text-only readers well, supply real plain text.

## 6. Other MIME headers also affect renderability

Ordering is one part of structure; **Content-Type**, charset, and disposition help clients understand each part.

| Header / attribute | Meaning | Example |
|---|---|---|
| `Content-Type` | Content type or multipart structure | `text/plain`, `text/html`, `image/png`, `multipart/alternative` |
| `charset` | Character encoding of a text part | `charset=UTF-8` |
| `boundary` | Delimiter string separating parts of a multipart | `boundary="mix-123"` |
| `Content-Disposition` | Hint to display inline or as an attachment | `inline`, `attachment; filename="report.pdf"` |
| `Content-ID` | Identifies a MIME part for HTML references | `<brandLogo>` |
| `Content-Transfer-Encoding` | How payload is encoded for mail transport | `quoted-printable`, `base64`, `7bit` |

For Vietnamese content, choose UTF-8 right when creating the helper. Mail libraries typically pick appropriate `quoted-printable` or `base64`; do not concatenate boundaries or encode strings manually unless genuinely needing low-level MIME control.

`Content-Disposition` and file name help clients detect attachments, yet many clients also infer from `Content-Type`, position in the tree, Content-ID, and their file-handling policies. Thus, an `inline` image may still show up in some clients' attachment lists; this is not always a `JavaMailSender` bug.

## 7. Compatibility across mail clients

Mail clients have differing HTML rendering engines, security policies, and attachment presentations. Beyond the specific app, **version, operating system, enterprise configuration, and gateway hops** can also alter outcomes.

| Situation | Possible symptom | Design for better compatibility |
|---|---|---|
| Client prefers plain text or disables HTML | Sees only text, no HTML layout | Always create a `text/plain` version carrying complete info and needed links. |
| HTML precedes plain in `alternative` | Some clients pick text instead of HTML | Put `text/plain` before `text/html`. |
| HTML and plain are direct siblings in `mixed` | Client shows duplicate content or treats one part as attachment | Nest both versions inside `multipart/alternative`. |
| CID image placed in wrong group or mismatched Content-ID | Broken image, only alt text shows, or appears as attachment | Use `multipart/related`, match `cid:...` to ID, and add inline after setting body. |
| Email uses Internet-hosted images | Images hidden until recipient allows loading | Never put critical info in images alone; provide alt text and text body. |
| HTML uses complex CSS or scripts | Inconsistent layout or stripped elements | Write simple email HTML, compatible CSS, avoid JavaScript reliance. |
| Multiple files or international characters in names | File names/attachment icons vary by client | Use helper APIs and proper encoding; test target file names. |
| Oversized email | Rejected, clipped, or slowly processed by provider | Cap attachments; consider access-controlled download links. |

### Examples across client families

- **Gmail (web/app):** may sanitize HTML, proxy images, and enforce reader protection policies; inline images/attachments should be verified under realistic receiving conditions.
- **Outlook:** rendering differs across classic desktop, new Outlook, and web; complex HTML/CSS layouts and inline images require separate testing.
- **Apple Mail and mobile clients:** may auto-scale content, apply dark mode, and adapt attachment display; responsive design and plain fallbacks help.
- **Text-only clients, alerting systems, and automated processors:** may ignore HTML completely, so `text/plain` must never be a useless sentence like “Please view the HTML version”.

The examples above are **areas to watch**, not absolute guarantees for every version. Clean MIME structure reduces bugs yet cannot control every receiver-side rendering policy.

## 8. Two kinds of “order” to distinguish

When speaking of “MIME order”, distinguish:

**Semantic preference order in `multipart/alternative`**

- Later parts are more preferred representations if supported by the client.
- With plain and HTML, normally **plain first → HTML second**.
- Wrong ordering can cause clients to pick the wrong version.

**Build and placement order of resources in `multipart/related` / `mixed`**

- The root part of related should be specified explicitly or placed first if `start` is absent.
- Attachments usually follow primary content in mixed.
- When using Spring Mail, call `setText(...)` then `addInline(...)` for better compatibility with some mail readers.

Apart from these two, **visual display order** is decided by the mail client. For example, a client may place attachments as an icon bar at the top even though they follow the body in MIME. Never use UI display order to deduce exact MIME part order; inspect the **raw message source** when needed.

## 9. How to inspect MIME structure on the receiving side

When an email looks unexpected, looking only at the rendered view can hide the cause. Inspect the MIME tree:

1. Send the email to a **test SMTP server** or test mailbox. Tools such as Mailpit and GreenMail help inspect content, headers, and attachments.
2. View the **raw email source** (*show original*, *view source*, or equivalent). Locate the message's `MIME-Version` and `Content-Type: multipart/...`.
3. Identify boundaries and the nested tree; for `alternative`, check the order of `text/plain` and `text/html`.
4. For HTML with inline images, verify `src="cid:brandLogo"` has a matching `Content-ID: <brandLogo>` part and the image part sits inside the appropriate related group.
5. For attachments, inspect `Content-Disposition: attachment`, file name, data type, and the `mixed` group.
6. Open the email in **the actual clients your recipients use**, including web/mobile/desktop if relevant. Observe body, links, alt text, inline images, file names, and line wrapping.

If a Spring app sends over SMTP and the server returns `250` after `DATA`, that means the server **accepted the message for processing**—with no guarantee all clients will display the content identically. Intermediate gateways, anti-spam systems, security filters, or newsletter services can add headers and even rewrite parts.

### Symptoms and where to check first

| Symptom | Related possibility | Where to inspect |
|---|---|---|
| Reader sees the same content twice | Plain and HTML versions were not grouped inside `alternative` | `multipart/*` tree and part positions |
| Sees only plain text despite having HTML | `alternative` in wrong order or client disables HTML | Order of `text/plain`/`text/html` and client settings |
| Logo shows as attachment icon | Inline part not in suitable related group, or client's own display style | `Content-ID`, `Content-Disposition`, `multipart/related` |
| Logo blank or red X | `cid:` mismatch, part missing, unsupported image format, or blocked by client | HTML, image part, MIME type, client policy |
| Vietnamese diacritics garbled | Inconsistent charset/transfer encoding or bug when building body | `charset=UTF-8` and source data |
| PDF missing | Attached in wrong group, filtered, or exceeded size limit | `multipart/mixed`, provider logs, received message |
| HTML layout broken | CSS/HTML unsupported by client | Received HTML, CSS, and target renderer |

## 10. Principles for authoring reliable MIME emails

To avoid over-relying on any single mail client, design from **semantic layers**:

1. **Content:** complete `text/plain` version; if HTML exists, place it afterward in `alternative`.
2. **Display resources:** HTML and CID images belong in a proper `related` group; manage Content-IDs accurately.
3. **Attachments:** keep separate from inline resources via outer `mixed` when needed.
4. **Encoding:** set appropriate charset, usually UTF-8; delegate MIME formatting and transfer encoding to the mail library.
5. **Readability:** the email must stay usable when images fail to load or HTML is disabled; alt text only assists images and never replaces essential text content.
6. **Devices and clients:** test recipients' primary mail clients, avoiding HTML/CSS features that work on only one engine.
7. **Spring code:** use `MimeMessageHelper` instead of assembling raw MIME manually; pick an explicit multipart mode when using inline resources or attachments, and call `setText(...)` before `addInline(...)`.

When looking at an email containing HTML, a logo, and a PDF, ask yourself three questions: **Are the plain/HTML versions marked as alternative? Does the image belong to HTML content via related or is it being treated as an attachment? Is the PDF separated from the main content in mixed?** Answering these three questions locates most issues involving MIME ordering and mail client compatibility.
