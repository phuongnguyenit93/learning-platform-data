# Testing Plain Text Content and Unicode Characters

In **Spring Framework Mail**, an email may be sent successfully yet still display incorrectly: Vietnamese loses its diacritics, the `₫` character turns into a question mark, emojis break, verification links get truncated, or the email only has HTML without a **plain-text** part for plain-text mail clients. These bugs typically do not show up in a unit test that only checks whether `JavaMailSender.send(...)` was called.

To test email content meaningfully, you need to test **two separate layers**:

1. **Logical content rendered by the application**: does the plain-text `String` have the right information, Unicode characters, URLs, line breaks, and formatting?
2. **MIME representation generated by Spring/Jakarta Mail**: does the `text/plain` part exist, declare the right charset, and preserve Unicode characters after MIME encoding/decoding? If HTML is used, are both `text/plain` and `text/html` present inside `multipart/alternative`?

This lesson focuses on **unit testing** in Spring Mail using **JUnit 5, AssertJ, Mockito, and in-memory Jakarta Mail**. You do not need to connect to a real SMTP server just to verify plain-text content or Unicode. SMTP integration testing is a separate test layer and is clearly distinguished at the end of the lesson.

## 1. Testing goals

After this lesson, you will be able to design tests that verify:

- Transactional emails include a usable `text/plain` version.
- Vietnamese Unicode such as `Đặng, Nguyễn, Ứng dụng, Xác nhận` stays intact.
- Currency symbol `₫`, punctuation, accented letters, and emojis are not lost or replaced with `?`.
- Email subjects containing Unicode decode accurately.
- Plain text retains business content: order code, amount, deadline, and action URL.
- Plain text does not accidentally contain HTML tags or `cid:` references instead of readable text.
- A `multipart/alternative` email contains plain and HTML parts with the same business facts.
- MIME parts declare an appropriate charset, typically UTF-8.
- Whitespace, paragraphs, and line breaks are intentional.
- Tests do not depend on SMTP credentials, network connectivity, or how a specific mail client renders.

**A successfully sent email does not automatically prove the content is correct.** Conversely, good content tests do not prove that the provider will deliver the email to the Inbox.

## 2. Four layers of an email to distinguish

A common pipeline:

```text
Business data
  |
  v
Template / plain-text renderer
  |
  | Java String, Unicode text
  v
MimeMessageHelper
  |
  | text/plain; charset=UTF-8
  | text/html; charset=UTF-8 (if present)
  v
Jakarta Mail MIME serializer
  |
  | Quoted-printable / base64 / headers
  v
JavaMailSender / SMTP
  |
  v
Recipient mail client
```

Unit tests can verify the **renderer**, **MIME structure**, and **string decoded from the message** without calling SMTP. Meanwhile:
- SMTP AUTH/TLS;
- relay responses;
- provider bounces/deferrals;
- inbox placement;
- rendering fidelity on Outlook, Gmail, or specific devices

are concerns of integration, end-to-end, or compatibility testing.

### 2.1. Test boundary table

| What to check | Appropriate unit test | Needs real SMTP? |
|---|---|---|
| Plain text has order code and URL | Renderer test | No |
| Vietnamese diacritics and emojis stay intact | Renderer and MIME decode test | No |
| `text/plain` is present in the message | Traverse in-memory MIME tree | No |
| MIME charset declares UTF-8 | Inspect MIME parts | No |
| Unicode Subject header reads back properly | `MimeMessage.getSubject()` | No |
| Spring service passes right message to sender | Mockito capture `MimeMessage` | No |
| Provider accepts SMTP and signs DKIM | Integration test with provider | Yes |
| Email lands in Inbox and renders on client | End-to-end / client test | Yes |

Do not use a mock without inspecting the message to conclude that content was encoded properly.

## 3. Plain text is an independent content version

A good plain-text version is not a one-liner saying "Please enable HTML." It must be complete enough for the recipient to understand and act.

Example order confirmation email:

```text
Xin chào Nguyễn Thị Ánh,

Đơn hàng ORD-2026-001 của bạn đã được xác nhận.

Tổng tiền: 450.000 ₫
Dự kiến giao: 15/11/2026

Xem chi tiết đơn hàng:
https://shop.example.com/orders/ORD-2026-001

Nếu cần hỗ trợ, hãy trả lời email này.
```

Information that must remain usable when there is no HTML at all:
- name and context;
- status;
- reference code;
- amount and currency unit;
- dates;
- full link;
- support channel;
- conditions or deadlines if applicable.

When HTML has a button:

```html
<a href="https://accounts.example.com/verify?token=example">Xác minh tài khoản</a>
```

plain text must contain the link:

```text
Xác minh tài khoản tại:
https://accounts.example.com/verify?token=example
```

Do not assert only that the text has the phrase "Xác minh tài khoản" while omitting the actual URL.

## 4. Prepare testing dependencies

With Spring Boot and Gradle, a common dependency setup:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-mail'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
```

The test starter typically provides JUnit Jupiter, Mockito, and AssertJ through Spring Boot's dependency management. Depending on your current version and build setup, verify the exact test libraries in your project.

The examples use:
- **Spring Framework 6+/Spring Boot 3+**, thus importing `jakarta.mail.*` rather than legacy `javax.mail.*`;
- **Java 17+** for text blocks and records;
- **JUnit Jupiter** for `@Test`, `@ParameterizedTest`;
- **AssertJ** for readable assertions;
- **Mockito** when capturing the message passed by a service to `JavaMailSender`.

No SMTP host, username, or password needs to be configured to test an in-memory `MimeMessage`.

## 5. Test the pure renderer before testing MIME

Separate the content-rendering step from the sending step. A simple renderer needs no Spring context or SMTP, making it fast, repeatable, and easy to pinpoint where bugs originate.

### 5.1. Data model

```java
package com.example.mail;

public record ReceiptData(
    String customerName,
    String orderId,
    String amountText,
    String deliveryDateText,
    String orderUrl
) {}
```

Here values are already normalized at the business layer: amount is formatted for the locale, delivery date is converted to the target timezone, and the URL is built from a trusted source. The renderer focuses on content.

### 5.2. Plain-text renderer

```java
package com.example.mail;

public class ReceiptPlainRenderer {

    public String render(ReceiptData data) {
        return """
            Xin chào %s,

            Đơn hàng %s của bạn đã được xác nhận.

            Tổng tiền: %s
            Dự kiến giao: %s

            Xem chi tiết đơn hàng:
            %s

            Nếu cần hỗ trợ, hãy trả lời email này.
            """.formatted(
                data.customerName(),
                data.orderId(),
                data.amountText(),
                data.deliveryDateText(),
                data.orderUrl()
            );
    }
}
```

Using a Java text block expresses paragraphs clearly. Still, keep in mind:
- a trailing newline at the end of a text block can be significant;
- incidental indentation is stripped by Java at compile time;
- input content may contain Unicode;
- the renderer must not accidentally strip information via `trim()` or unintended character replacements.

When production needs complex templates, Thymeleaf/Freemarker or another renderer can be used. **The logical output is still a plain-text string**, so the same testing strategy applies.

## 6. Unit test comparing the full expected content

A reliable renderer test can assert the exact expected content using `isEqualTo`.

```java
package com.example.mail;

import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;

class ReceiptPlainRendererTest {

    private final ReceiptPlainRenderer renderer =
        new ReceiptPlainRenderer();

    private ReceiptData sampleData() {
        return new ReceiptData(
            "Nguyễn Thị Ánh",
            "ORD-2026-001",
            "450.000 ₫",
            "15/11/2026",
            "https://shop.example.com/orders/ORD-2026-001"
        );
    }

    @Test
    void rendersCompleteVietnamesePlainText() {
        String actual = renderer.render(sampleData());

        String expected = """
            Xin chào Nguyễn Thị Ánh,

            Đơn hàng ORD-2026-001 của bạn đã được xác nhận.

            Tổng tiền: 450.000 ₫
            Dự kiến giao: 15/11/2026

            Xem chi tiết đơn hàng:
            https://shop.example.com/orders/ORD-2026-001

            Nếu cần hỗ trợ, hãy trả lời email này.
            """;

        assertThat(actual).isEqualTo(expected);
    }
}
```

This test helps catch when:
- someone editing the template accidentally changes an amount, link, or line break;
- data is no longer interpolated in the right place;
- Vietnamese characters are lost;
- business content is replaced with an uninformative sentence.

**Not every email needs character-by-character comparison.** For templates whose wording changes often, combine full-text tests for stable parts with assertions on key facts to reduce unnecessary test churn.

## 7. Unit test against key business conditions

For emails whose editorial copy changes frequently, asserting every space can be too rigid. You can test the **content contract**:

```java
@Test
void plainTextKeepsBusinessFactsAndActionUrl() {
    ReceiptData data = sampleData();

    String plain = renderer.render(data);

    assertThat(plain)
        .contains("Nguyễn Thị Ánh")
        .contains("ORD-2026-001")
        .contains("450.000 ₫")
        .contains("15/11/2026")
        .contains("https://shop.example.com/orders/ORD-2026-001")
        .contains("Nếu cần hỗ trợ");
}
```

For verification or password-reset emails, do not only assert the CTA label; assert the actual URL that the user can copy.

### 7.1. Do not let HTML leak into plain text

```java
@Test
void plainTextDoesNotContainHtmlMarkup() {
    String plain = renderer.render(sampleData());

    assertThat(plain)
        .doesNotContain("<html")
        .doesNotContain("<a ")
        .doesNotContain("<table")
        .doesNotContain("cid:");
}
```

Substring tests act as a simple guard for controlled renderers, **not a full HTML parser**. For complex user-supplied content, decide explicitly whether literal angle brackets, code snippets, or `<` characters are permitted in text. Never build every "safety" rule solely by searching for a few tags.

### 7.2. Avoid unrendered placeholders

When a template engine uses placeholders, sent output must never leave them unrendered:

```text
Xin chào `customerName`
Đơn hàng ${orderId}
```

Tests can check for known placeholder tokens, though you should avoid overly broad regexes that flag valid symbols inside user content as errors.

## 8. What is Unicode and why can String.length be misleading?

Java `String` stores text as **UTF-16 code units**. That is an in-JVM representation, **not the MIME charset used when transmitting email**.

Example:

```java
String vietnamese = "Đặng Thị Ánh";
String currency = "450.000 ₫";
String emoji = "🚀";
```

Common Vietnamese characters fit in a single BMP code point, while many emojis outside the BMP require a **surrogate pair** in UTF-16.

### 8.1. UTF-16 code unit, code point, and grapheme

Three concepts to distinguish:

| Concept | Meaning | Example |
|---|---|---|
| UTF-16 code unit | 16-bit unit counted by `String.length()` | Emoji `🚀` typically takes 2 units. |
| Unicode code point | Logical Unicode value | `🚀` is one code point. |
| Grapheme cluster | Unit a user perceives as one character | Some ZWJ emojis or base letter + combining marks span multiple code points. |

JUnit example:

```java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;

class UnicodeConceptTest {

    @Test
    void countsCodePointsNotOnlyUtf16Units() {
        String rocket = "🚀";

        assertThat(rocket.length()).isEqualTo(2);
        assertThat(
            rocket.codePointCount(0, rocket.length())
        ).isEqualTo(1);
    }
}
```

Do not set content limits based on `String.length()` assuming it always equals the number of "user-visible characters." For input validation, define limits explicitly in bytes, code points, or grapheme clusters.

### 8.2. Unicode in a Java String does not mean MIME defaults to UTF-8

A `String` can accurately hold `Đặng, Ánh, ₫, 🚀`, yet when writing out a MIME part, the library must pick an appropriate **charset** and **Content-Transfer-Encoding**. Pass charset `UTF-8` explicitly to `MimeMessageHelper` and verify the content after Jakarta Mail decodes it.

## 9. Test UTF-8 round-trip at the String layer

This test verifies byte-conversion logic in the application; **it is not a MIME test yet**:

```java
import java.nio.charset.StandardCharsets;

import static org.assertj.core.api.Assertions.assertThat;
import org.junit.jupiter.api.Test;

class Utf8TextTest {

    @Test
    void preservesVietnameseCurrencyAndEmojiAsUtf8() {
        String original =
            "Xin chào Nguyễn Thị Ánh — 450.000 ₫ 🎉🚀";

        byte[] bytes = original.getBytes(StandardCharsets.UTF_8);
        String decoded =
            new String(bytes, StandardCharsets.UTF_8);

        assertThat(decoded).isEqualTo(original);
    }
}
```

If this test passes, you can conclude that the UTF-8 encode/decode pair preserves the sample string. You **cannot** conclude from it that a `MimeMessage` used UTF-8. To verify MIME, inspect the actual `Content-Type` and decoded content from the `MimeMessage`.

### 9.1. Why not use the default charset?

Avoid:

```java
byte[] bytes = text.getBytes();
String decoded = new String(bytes);
```

The meaning of the default charset can depend on environment/JDK and runtime configuration. Even though newer JDKs default to UTF-8, **explicitly specifying `StandardCharsets.UTF_8`** keeps code and tests clearer and more reliable when exchanging data via files, network, or MIME.

## 10. Unicode normalization NFC and NFD

An accented character can be represented by multiple code-point sequences that look nearly identical to the eye.

For example, the letter `ắ`:
- Precomposed form: `\u1EAF`.
- Decomposed form: `a\u0306\u0301` (letter a + breve + acute accent).

In Java:

```java
import java.text.Normalizer;

String nfcForm = "\u1EAF";
String decomposed = "a\u0306\u0301";

boolean equalAsString = nfcForm.equals(decomposed); // false

String normalized = Normalizer.normalize(
    decomposed,
    Normalizer.Form.NFC
);

boolean equalAfterNfc = nfcForm.equals(normalized); // true
```

Test:

```java
import static org.assertj.core.api.Assertions.assertThat;

import java.text.Normalizer;
import org.junit.jupiter.api.Test;

class UnicodeNormalizationTest {

    @Test
    void supportsCanonicallyEquivalentVietnameseText() {
        String composed = "\u1EAF";
        String decomposed = "a\u0306\u0301";

        assertThat(composed).isNotEqualTo(decomposed);

        assertThat(
            Normalizer.normalize(decomposed, Normalizer.Form.NFC)
        ).isEqualTo(composed);
    }
}
```

### 10.1. When should you normalize?

If business logic requires comparing names or subjects under Unicode canonical equivalence, normalize to NFC at **one chosen point in the pipeline** and apply it consistently.

However, you should not always normalize all data:
- Digitally signed or byte-matched content may change under normalization.
- Tokens, verification codes, passwords, or URLs may follow strict byte rules.
- Auditing requires preserving original input in some systems.
- Compatibility normalization NFKC/NFKD can alter the visual meaning of some characters.

**Normalize only when it is an explicit system requirement.** If the renderer actively normalizes input, test that rule. If the renderer must preserve input verbatim, test that combining sequences are not altered unexpectedly.

### 10.2. Never use Unicode normalization to "fix" charset bugs

A string already corrupted into mojibake—for example, `Nguyễn` turning into garbled characters due to decoding with the wrong charset—cannot be reliably repaired by NFC/NFD. Fix the place where bytes are encoded or decoded.

## 11. Test plain text directly on an in-memory MimeMessage

Jakarta Mail lets you create a `MimeMessage` from a `Session` without network connections.

```java
import jakarta.mail.Session;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.MimeMessageHelper;

import java.util.Properties;

MimeMessage message = new MimeMessage(
    Session.getInstance(new Properties())
);

MimeMessageHelper helper =
    new MimeMessageHelper(message, false, "UTF-8");

helper.setFrom("no-reply@example.com");
helper.setTo("customer@example.net");
helper.setSubject("Xác nhận đơn hàng của Ánh 🎉");

String plainText =
    "Xin chào Nguyễn Thị Ánh,\nTổng tiền: 450.000 ₫ 🚀";

helper.setText(plainText, false);
message.saveChanges();
```

Here:
- `multipart=false` because we only want a plain-text message;
- `setText(plainText, false)` sets the plain-text content type;
- `saveChanges()` prepares necessary MIME headers and metadata;
- neither `Transport.send` nor `JavaMailSender.send` is called, so **there is no SMTP network request**.

### 11.1. Test decoded content

```java
import static org.assertj.core.api.Assertions.assertThat;

import jakarta.mail.Session;
import jakarta.mail.internet.MimeMessage;
import org.junit.jupiter.api.Test;
import org.springframework.mail.javamail.MimeMessageHelper;

import java.util.Properties;

class PlainMimeMessageTest {

    @Test
    void createsUtf8PlainTextAndPreservesUnicode()
            throws Exception {

        MimeMessage message = new MimeMessage(
            Session.getInstance(new Properties())
        );

        MimeMessageHelper helper =
            new MimeMessageHelper(message, false, "UTF-8");

        String original =
            "Nguyễn Thị Ánh — 450.000 ₫ — 🎉🚀";

        helper.setText(original, false);
        message.saveChanges();

        assertThat(message.isMimeType("text/plain")).isTrue();
        assertThat((String) message.getContent())
            .isEqualTo(original);
    }
}
```

This test is valuable because it exercises how Jakarta Mail represents content in MIME and then **reads back the decoded content**.

### 11.2. Verify the Content-Type charset

```java
import jakarta.mail.internet.ContentType;

ContentType contentType =
    new ContentType(message.getContentType());

assertThat(contentType.getBaseType())
    .isEqualToIgnoringCase("text/plain");

assertThat(contentType.getParameter("charset"))
    .isEqualToIgnoringCase("UTF-8");
```

Avoid asserting the entire `Content-Type` header as a literal string because parameter names, quoting styles, or ordering may vary. Parse the header semantically.

### 11.3. Do not equate Java source file encoding with MIME charset

Saving Java source files as UTF-8 is good practice, yet it **does not replace** declaring the proper charset on the MIME part. These are two separate layers: source code → Java String, then Java String → MIME bytes.

## 12. Why not assert fixed Base64 or quoted-printable?

When sending Unicode content via MIME, the library may choose:

```text
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable
```

or:

```text
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: base64
```

Depending on library, content, configuration, and serialization steps, transfer encoding can vary. Both preserve Unicode content when used properly.

**Resilient tests should compare the decoded string**, rather than asserting "the email must use Base64." Example:

```java
assertThat((String) message.getContent())
    .isEqualTo("Nguyễn Thị Ánh — 450.000 ₫ 🎉");
```

You can assert that the transfer encoding belongs to an allowed set if the system has specific compatibility requirements, but avoid turning unnecessary implementation details into a content contract.

### 12.1. Compare raw MIME when truly needed

To inspect MIME serialization in a test:

```java
import java.io.ByteArrayOutputStream;

ByteArrayOutputStream output = new ByteArrayOutputStream();
message.saveChanges();
message.writeTo(output);

byte[] rawMimeBytes = output.toByteArray();
```

Raw MIME contains headers, boundaries, transfer-encoded bytes, and email-standard line endings. Use it when verifying structure or debugging. Do not do `new String(rawMimeBytes, UTF_8)` and search directly for a Vietnamese string if the body is Base64/quoted-printable encoded; **decode via Jakarta Mail first**.

### 12.2. Re-parse MIME bytes

You can prove a full round-trip through serializer and parser:

```java
import jakarta.mail.Session;
import jakarta.mail.internet.MimeMessage;
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.util.Properties;

Session session = Session.getInstance(new Properties());

ByteArrayOutputStream raw = new ByteArrayOutputStream();
message.saveChanges();
message.writeTo(raw);

MimeMessage parsed = new MimeMessage(
    session,
    new ByteArrayInputStream(raw.toByteArray())
);

assertThat(parsed.isMimeType("text/plain")).isTrue();
assertThat((String) parsed.getContent())
    .isEqualTo(original);
```

This is stronger than just checking `getContent()` on the message that was just populated, because the parser must reconstruct it from serialized MIME message bytes.

## 13. Plain text in multipart/alternative: traverse the MIME tree

When an email has both HTML and plain text:

```java
MimeMessageHelper helper =
    new MimeMessageHelper(message, true, "UTF-8");

helper.setText(plainText, htmlText);
```

Spring Mail can create nested MIME multiparts to support attachments/inline resources, depending on constructor or multipart mode. Therefore **never assume `message.getContent()` is always a `String` or that `text/plain` is the first part of the root multipart**.

Illustrative structure:

```text
multipart/mixed
└── multipart/related
    └── multipart/alternative
        ├── text/plain; charset=UTF-8
        └── text/html; charset=UTF-8
```

When there are no attachments/inline resources, the library can produce a simpler structure. Tests should check semantic MIME parts rather than hardcoding nesting depth.

### 13.1. Recursive part-finder helper

```java
package com.example.mail;

import jakarta.mail.Multipart;
import jakarta.mail.Part;

import java.util.ArrayList;
import java.util.List;

public final class MimeTextParts {

    private MimeTextParts() {}

    public static List<Part> find(
            Part root,
            String mimeType) throws Exception {

        List<Part> result = new ArrayList<>();
        visit(root, mimeType, result);
        return result;
    }

    private static void visit(
            Part part,
            String mimeType,
            List<Part> result) throws Exception {

        if (part.isMimeType(mimeType)) {
            result.add(part);
            return;
        }

        Object content = part.getContent();

        if (content instanceof Multipart multipart) {
            for (int i = 0; i < multipart.getCount(); i++) {
                visit(
                    multipart.getBodyPart(i),
                    mimeType,
                    result
                );
            }
        }
    }
}
```

`Part.isMimeType("text/plain")` matches the MIME type without requiring an exact match on charset parameters. For the purposes of this lesson, this helper suffices to traverse standard `multipart` parts. If the system nests another `message/rfc822` email, decide whether traversal should include attached messages to avoid false positives; you can also exclude parts with disposition `attachment` when looking for the main **body**.

### 13.2. Test both plain and HTML

```java
import static org.assertj.core.api.Assertions.assertThat;

import jakarta.mail.Part;
import jakarta.mail.Session;
import jakarta.mail.internet.MimeMessage;

import org.junit.jupiter.api.Test;
import org.springframework.mail.javamail.MimeMessageHelper;

import java.util.List;
import java.util.Properties;

class AlternativeMimeTest {

    @Test
    void containsPlainAndHtmlWithoutLosingUnicode()
            throws Exception {

        MimeMessage message = new MimeMessage(
            Session.getInstance(new Properties())
        );

        MimeMessageHelper helper =
            new MimeMessageHelper(message, true, "UTF-8");

        String plain =
            "Xin chào Nguyễn Thị Ánh.\nTổng tiền: 450.000 ₫ 🎉";
        String html =
            "<html><body><p>Xin chào Nguyễn Thị Ánh.</p>"
                + "<p>Tổng tiền: 450.000 ₫ 🎉</p></body></html>";

        helper.setText(plain, html);
        message.saveChanges();

        List<Part> plainParts =
            MimeTextParts.find(message, "text/plain");

        List<Part> htmlParts =
            MimeTextParts.find(message, "text/html");

        assertThat(plainParts).hasSize(1);
        assertThat(htmlParts).hasSize(1);

        assertThat((String) plainParts.get(0).getContent())
            .isEqualTo(plain);

        assertThat((String) htmlParts.get(0).getContent())
            .isEqualTo(html);
    }
}
```

The two versions can differ in layout, yet must share the same business facts. For an HTML-only email, this test will catch the missing `text/plain` part.

### 13.3. Test charset for each alternative part

```java
import jakarta.mail.internet.ContentType;

for (Part part : MimeTextParts.find(message, "text/plain")) {
    ContentType type = new ContentType(part.getContentType());

    assertThat(type.getParameter("charset"))
        .isEqualToIgnoringCase("UTF-8");
}

for (Part part : MimeTextParts.find(message, "text/html")) {
    ContentType type = new ContentType(part.getContentType());

    assertThat(type.getParameter("charset"))
        .isEqualToIgnoringCase("UTF-8");
}
```

If there are multiple text parts by design, tests should distinguish which part is the main body versus an attachment or nested forwarded message. Do not lump them all together and pick an arbitrary part.

## 14. Test Spring Mail services with Mockito

Renderer unit tests verify strings; MIME tests verify encoding/structure. At the service layer, you must verify **the right message is handed to the sender**, while still avoiding SMTP connections.

Approach:
1. Mock `JavaMailSender`.
2. Return a real in-memory `MimeMessage` from `createMimeMessage()`.
3. Call the service.
4. Capture the `MimeMessage` passed to `send(...)`.
5. Inspect MIME parts and decoded content.

### 14.1. Service sending a plain-text email

```java
package com.example.mail;

import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;

import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

import java.nio.charset.StandardCharsets;

public class PlainReceiptMailService {

    private final JavaMailSender sender;
    private final ReceiptPlainRenderer renderer;

    public PlainReceiptMailService(
            JavaMailSender sender,
            ReceiptPlainRenderer renderer) {
        this.sender = sender;
        this.renderer = renderer;
    }

    public void send(
            String recipient,
            ReceiptData data) throws MessagingException {

        MimeMessage mime = sender.createMimeMessage();

        MimeMessageHelper helper = new MimeMessageHelper(
            mime,
            false,
            StandardCharsets.UTF_8.name()
        );

        helper.setFrom("no-reply@example.com");
        helper.setTo(recipient);
        helper.setSubject(
            "Xác nhận đơn hàng của " + data.customerName()
        );
        helper.setText(renderer.render(data), false);

        sender.send(mime);
    }
}
```

### 14.2. Mockito capture test

```java
package com.example.mail;

import static org.assertj.core.api.Assertions.assertThat;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

import jakarta.mail.Session;
import jakarta.mail.internet.MimeMessage;

import org.junit.jupiter.api.Test;
import org.mockito.ArgumentCaptor;
import org.springframework.mail.javamail.JavaMailSender;

import java.util.Properties;

class PlainReceiptMailServiceTest {

    @Test
    void sendsUnicodePlainContentWithoutSmtp()
            throws Exception {

        JavaMailSender sender = mock(JavaMailSender.class);
        MimeMessage mime = new MimeMessage(
            Session.getInstance(new Properties())
        );

        when(sender.createMimeMessage()).thenReturn(mime);

        PlainReceiptMailService service =
            new PlainReceiptMailService(
                sender,
                new ReceiptPlainRenderer()
            );

        ReceiptData data = new ReceiptData(
            "Nguyễn Thị Ánh",
            "ORD-2026-001",
            "450.000 ₫",
            "15/11/2026",
            "https://shop.example.com/orders/ORD-2026-001"
        );

        service.send("customer@example.net", data);

        ArgumentCaptor<MimeMessage> captor =
            ArgumentCaptor.forClass(MimeMessage.class);

        verify(sender).send(captor.capture());

        MimeMessage sent = captor.getValue();
        sent.saveChanges();

        assertThat(sent.isMimeType("text/plain")).isTrue();
        assertThat(sent.getSubject())
            .isEqualTo("Xác nhận đơn hàng của Nguyễn Thị Ánh");

        String decoded = (String) sent.getContent();

        assertThat(decoded)
            .contains("Nguyễn Thị Ánh")
            .contains("450.000 ₫")
            .contains("ORD-2026-001")
            .contains("https://shop.example.com/orders/ORD-2026-001");
    }
}
```

By default Mockito performs no sending action for `void send(MimeMessage)`. The test therefore never calls SMTP. Using a real `MimeMessage` instead of mocking the MIME object also tests how Jakarta Mail processes the content.

### 14.3. Why not just verify(send)?

Too weak of a test:

```java
verify(sender).send(any(MimeMessage.class));
```

It only proves the service invoked the method. Even if the plain text is blank, the encoding is wrong, the URL is missing, or the message is HTML-only, the test above can still pass.

Capture and assert on a real message, or test the renderer + MIME builder separately. You do not have to repeat every content check at every layer; pick assertions representing each layer's functional contract.

### 14.4. Do not accidentally call real send in unit tests

Using a real `JavaMailSenderImpl` in unit tests and calling `send` can connect to an SMTP provider if the machine has network/credential config. To test content:
- create an in-memory `MimeMessage`; or
- mock the sender and capture the message as above.

Integration tests hitting an SMTP test server or sandbox belong in a separate layer explicitly configured to prevent real email delivery.

## 15. Test Unicode in Subject and headers

Body content typically uses `text/plain; charset=UTF-8`, whereas **Subject** is an email header with its own encoding mechanism when containing Unicode. Never test Subject by assuming the raw header is always a literal UTF-8 string.

Example:

```java
MimeMessageHelper helper =
    new MimeMessageHelper(message, false, "UTF-8");

helper.setSubject("Thông báo cho Nguyễn Thị Ánh 🎉");
helper.setText("Nội dung tiếng Việt có dấu.", false);
message.saveChanges();
```

Meaningful test:

```java
assertThat(message.getSubject())
    .isEqualTo("Thông báo cho Nguyễn Thị Ánh 🎉");
```

`getSubject()` returns the value decoded by Jakarta Mail. Meanwhile the raw MIME header may use MIME encoded-words such as `=?UTF-8?...?=`, and exact chunking/folding can vary.

### 15.1. Separate decoded value tests from raw headers

You should test:
- `getSubject()` returns the exact Unicode string;
- the plain-text body decodes properly;
- sender display name/address parses properly if required.

Do not force the raw Subject to contain literal Unicode or a fixed Base64 string. That depends on implementation and encoding choices.

### 15.2. From display name containing Vietnamese text

```java
helper.setFrom(
    "no-reply@example.com",
    "Cửa hàng Ánh Dương"
);
```

A unit test can parse `InternetAddress` and verify the decoded personal display name via the appropriate API, rather than asserting that the raw From header is unencoded.

The actual email address and display name are two distinct components. Unicode in a display name does not imply the SMTP server supports Unicode local-parts/SMTPUTF8. If the application requires **email address internationalization**, that is a separate protocol requirement that must be tested against supporting SMTP/providers.

## 16. Test line breaks and whitespace

Plain text relies heavily on:
- blank lines between paragraphs;
- URLs on their own lines;
- list indentation;
- no extra whitespace breaking links;
- preventing the final paragraph from running into the footer;
- clean line wrapping on text-only clients.

### 16.1. Test formatting at the renderer

```java
@Test
void keepsReadableParagraphBreaks() {
    String plain = renderer.render(sampleData());

    assertThat(plain)
        .contains("đã được xác nhận.\n\nTổng tiền:")
        .contains("Xem chi tiết đơn hàng:\nhttps://")
        .contains("\n\nNếu cần hỗ trợ");
}
```

The test above assumes the renderer uses LF as its logical line break. This is a useful contract at the renderer layer.

### 16.2. When testing serialized MIME, CRLF may appear

Raw email on the wire uses `CRLF` line endings in many places. After parsing/serializing, do not jump to concluding content is wrong merely due to `\n` vs `\r\n`.

If the business requirement only cares about logical line structure, you can **normalize line endings in the test**:

```java
static String normalizeNewlines(String value) {
    return value
        .replace("\r\n", "\n")
        .replace('\r', '\n');
}
```

Then compare:

```java
assertThat(normalizeNewlines(decodedMimeText))
    .isEqualTo(normalizeNewlines(expectedText));
```

However, do not over-normalize:
- stripping all whitespace can hide word-concatenation bugs;
- `trim()` can remove a trailing newline required by contract;
- collapsing all paragraphs into one line prevents tests from catching unreadable output.

### 16.3. Do not manually insert MIME boundaries into Strings

The plain-text part is logical content. Jakarta Mail handles MIME boundaries, transfer encoding, and headers. Never manually insert `--boundary123` or embed raw `Content-Type` headers in the body.

## 17. Test URLs, lists, and tables in text-only email

HTML can use buttons, tables, and charts. In plain text, information must be transformed into a linear readable format.

HTML example:

```html
<table>
  <tr><th>Product</th><th>Quantity</th><th>Price</th></tr>
  <tr><td>Coffee</td><td>2</td><td>180.000 ₫</td></tr>
  <tr><td>Tea</td><td>1</td><td>90.000 ₫</td></tr>
</table>
```

Better plain text:

```text
Order details
-----------------
- Coffee
  Quantity: 2
  Price: 180.000 ₫

- Tea
  Quantity: 1
  Price: 90.000 ₫
```

Do not mechanically strip HTML tags, as the text can collapse into an unreadable string.

### 17.1. Assertions for action URLs

```java
@Test
void exposesFullActionUrlInPlainText() {
    String plain = renderer.render(sampleData());

    assertThat(plain).contains(
        "https://shop.example.com/orders/ORD-2026-001"
    );
}
```

For URLs with query strings, tests should ensure they are not truncated at `&` or `?`. If the URL contains a secret token, use a **dummy fixture token** in tests and never log real tokens.

### 17.2. Test monetary and date/time values

Do not compute amounts separately in the HTML renderer and plain renderer. Format amounts/dates in the view model and share them. Unit tests can verify both contain the same normalized representation such as `450.000 ₫` and `15/11/2026`.

If the plain version must display a timezone, assert `15/11/2026 09:00 ICT` or the system's specified timezone notation explicitly. Never rely on the CI runner's default timezone.

### 17.3. Content containing `<`, `>`, or `&`

Plain text may legitimately contain `2 < 3`, `A & B`, or code snippets. Do not "HTML-escape" the plain-text version and turn them into `&lt;` or `&amp;` unnecessarily.

The HTML renderer must escape according to HTML context; the plain renderer produces proper plain text. The two outputs **do not need to be byte-identical**, yet must remain consistent in information.

## 18. Parameterized tests for Vietnamese and Unicode

Testing a single accented name is not representative of diverse inputs. JUnit parameterized tests cover many cases with the same logic.

```java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

class VietnameseNameRenderingTest {

    private final ReceiptPlainRenderer renderer =
        new ReceiptPlainRenderer();

    @ParameterizedTest
    @ValueSource(strings = {
        "Đặng Thu Hà",
        "Nguyễn Thị Ánh",
        "Trần Đức Thịnh",
        "Phạm Quốc Bảo",
        "Hồ Minh Khuê",
        "Mai 🎉"
    })
    void keepsRecipientName(String customerName) {
        ReceiptData data = new ReceiptData(
            customerName,
            "ORD-001",
            "450.000 ₫",
            "15/11/2026",
            "https://shop.example.com/orders/ORD-001"
        );

        String plain = renderer.render(data);

        assertThat(plain)
            .contains("Xin chào " + customerName + ",");
    }
}
```

You can add inputs such as:
- precomposed and combining accented letters;
- double quotes, apostrophes, em dashes;
- leading/trailing whitespace per policy;
- empty/null names if the business model permits;
- ZWJ emoji sequences;
- other languages if the product supports internationalization.

You do not necessarily need to send an email with invalid inputs to test rendering. Data validation and fallback decisions should have their own unit tests.

### 18.1. Test Unicode code points and surrogate pairs

```java
@Test
void doesNotSplitEmojiSurrogatePairs() {
    String name = "Mai 🚀";

    ReceiptData data = new ReceiptData(
        name,
        "ORD-001",
        "450.000 ₫",
        "15/11/2026",
        "https://shop.example.com/orders/ORD-001"
    );

    String plain = renderer.render(data);

    assertThat(plain).contains(name);
}
```

Never slice a `String` using `substring(...)` at an arbitrary index expecting emojis to stay intact. If character truncation is required, use code-point or grapheme-segmentation logic suited to the goal.

### 18.2. Test that the replacement character does not appear unintentionally

The `` character (U+FFFD) is often a symptom of an earlier decoding error, though it can also be part of valid input in some domains.

If the data contract **never permits replacement characters** in output emails, you can assert:

```java
assertThat(plain).doesNotContain("\uFFFD");
```

This does not catch every encoding bug. A mojibake string may contain no U+FFFD at all, so round-trip and concrete content tests remain essential.

## 19. Test emails with both HTML and plain text as Unicode data varies

Suppose the application uses one view model and two renderers:

```text
ReceiptData
    |
    +--> plain renderer --> text/plain
    |
    +--> HTML renderer --> text/html
    |
    v
MimeMessageHelper.setText(plain, html)
```

Tests should verify:
- both MIME representations exist;
- key values appear in both;
- Unicode remains intact after decoding;
- plain does not depend on HTML buttons/links;
- target URLs are equivalent, though HTML may escape `&` as `&amp;`;
- text-only clients can still find the full URL.

### 19.1. Do not force HTML to contain the exact plain string

HTML might be:

```html
<p>Tổng tiền: <strong>450.000 ₫</strong></p>
```

While plain is:

```text
Tổng tiền: 450.000 ₫
```

Comparing the two strings verbatim will fail pointlessly. Verify **equivalent business facts** using assertions appropriate for each format.

### 19.2. Do not make plain content depend on inline images

HTML:

```html
<img src="cid:logo" alt="Logo Example Store">
```

Plain:

```text
Example Store
```

Plain tests should prove `cid:logo` is absent while the organization name or information conveyed by the image is still present. If a chart in HTML conveys business data, the text version should state the key figures instead of just saying "see image."

## 20. Common bugs and root causes

| Symptom | Common cause | Test to add |
|---|---|---|
| Vietnamese turns into question marks | Wrong charset at encode/decode or data source already lost characters | UTF-8 round-trip + MimeMessage parse round-trip. |
| Unicode subject appears encoded in assertion | Comparing raw header instead of decoded Subject | Use `getSubject()`. |
| Test passes even with empty body | Only verifying `send(any())` | Capture message and inspect `getContent()`. |
| HTML-only email, text-only client sees nothing | Calling `setText(html, true)` without plain part | Assert `text/plain` part exists. |
| MIME test gets `Multipart` instead of `String` | Using `multipart/alternative` or mixed/related | Traverse MIME tree recursively. |
| Raw MIME inspection misses `Nguyễn` | Transfer encoding may be Base64/QP | Parse/decode with Jakarta Mail. |
| NFC and NFD look identical yet `equals` is false | Different Unicode code-point sequences | Test normalization policy. |
| Emoji split across surrogate pair | Truncating by wrong UTF-16 index | Test code-point/grapheme handling. |
| Action URL disappears | HTML has button while plain only has label text | Assert full action URL in plain. |
| `&amp;` appears in plain text | Reusing HTML-escaped string | Separate HTML and plain escaping. |
| Monetary amounts differ across versions | Two renderers use different formatting logic | Share normalized view model. |
| Test fails on CRLF vs LF | Comparing after MIME serialization ignoring line endings | Normalize line endings purposefully. |
| Test depends on developer machine | Relying on default timezone/locale/charset | Inject locale/clock, explicit UTF-8. |
| CI test sends real emails | Calling unmocked `JavaMailSenderImpl.send` | In-memory MIME + Mockito; separate SMTP tests. |
| U+FFFD character appears | Invalid input or decoding | Test data fixtures and decoding points. |
| Wrong MIME charset despite valid Java String | `MimeMessageHelper` not configured with explicit charset | Test `Content-Type` parameter. |
| Text content has HTML tags | Broken tag stripping or wrong renderer used | Test text contract, links, and formatting. |

## 21. Design test fixtures and CI stability

### 21.1. Where to place fixtures?

For short emails, you can use Java text blocks right inside the test. For long content or multi-language templates, store fixtures in `src/test/resources` as UTF-8:

```text
src/test/resources/mail/
  receipt-vi-plain.txt
  receipt-vi-html.html
  reset-password-plain.txt
```

Read explicitly as UTF-8:

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

String expected = Files.readString(
    Path.of("src/test/resources/mail/receipt-vi-plain.txt"),
    StandardCharsets.UTF_8
);
```

If tests run with a different working directory, read fixtures via classpath resources instead of relying on relative paths like above:

```java
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

try (InputStream stream = getClass()
        .getResourceAsStream("/mail/receipt-vi-plain.txt")) {

    if (stream == null) {
        throw new IllegalStateException("Missing test fixture");
    }

    String expected = new String(
        stream.readAllBytes(),
        StandardCharsets.UTF_8
    );
}
```

Fixture files must be reviewed just like code because a golden test can pass erroneously if the fixture itself has corrupted encoding.

### 21.2. Tests should be deterministic

Avoid:
- relying on default timezone/locale;
- calling `Instant.now()` directly inside renderers;
- uncontrolled random order IDs or tokens;
- sending real SMTP traffic in unit tests;
- fetching templates from unstable network sources;
- relying on default charset for fixtures;
- relying on insignificant MIME header ordering;
- assuming a specific CTE.

Instead use:
- `Clock.fixed(...)` when formatting dates;
- `Locale.forLanguageTag("vi-VN")` when Vietnamese locale is needed;
- `ZoneId.of("Asia/Ho_Chi_Minh")` if the business scenario requires that timezone;
- fixed, non-sensitive fixture IDs/tokens;
- explicit UTF-8;
- in-memory `MimeMessage` and body-part assertions.

### 21.3. Why avoid asserting every header byte-for-byte?

Jakarta Mail may automatically generate:
- `Message-ID`;
- `Date`;
- MIME boundaries;
- `Content-Transfer-Encoding`;
- varying header folding and encoding.

These details can change across library versions. When the test's goal is **text content and Unicode**, assert only what belongs to the application contract: decoded subject, MIME type/charset, decoded body parts, business facts, and CTA.

## 22. What unit tests do not prove

Even when all unit tests above pass, other test levels are still needed depending on criticality:

1. **SMTP sandbox integration test:** `JavaMailSenderImpl` can connect, STARTTLS/AUTH works, and the SMTP server accepts the message.
2. **Provider integration:** DKIM signing/domain authentication works if provider-signed, and custom headers and bounce routing apply.
3. **End-to-end MIME:** a test recipient mailbox receives the exact content parts/attachments after passing through real relays.
4. **Mail client compatibility:** Outlook/Gmail/mobile render the plain/HTML versions as intended.
5. **Accessibility:** screen readers and text-only workflows have sufficient context.
6. **Deliverability:** SPF/DKIM/DMARC, complaints, bounces, spam classification, and inbox placement.

Distinguish "SMTP accepted" from "delivered to recipient," and "delivered" from "read by recipient." Unit tests cannot infer those states from a mock sender alone.

## 24. Summary

**Testing plain-text content and Unicode characters** in Spring Framework Mail should start with the **pure renderer** and expand to **real in-memory MIME messages**.

Core principles:

1. Test plain text as an independent content version with complete facts and URLs; do not treat it as an afterthought to HTML.
2. Use JUnit/AssertJ to test Unicode strings, monetary amounts, links, paragraphs, and fallbacks.
3. Use `MimeMessageHelper` with charset `UTF-8` and verify `text/plain`/`text/html` parts semantically.
4. Read content back via `getContent()` or serialize/parse round-trips; **do not assert fixed raw Base64/quoted-printable**.
5. For multipart messages, traverse the **MIME tree recursively** instead of assuming plain text is always the root content.
6. Capture `MimeMessage` with Mockito to verify the service prepares and hands the right message to the sender **without calling real SMTP**.
7. Test Vietnamese Unicode, `₫`, emojis, NFC/NFD, and decoded Subjects; distinguish UTF-16 units, code points, and grapheme clusters.
8. Keep tests deterministic: explicit UTF-8, stable fixtures, and controlled locale/timezone/clock.
9. Separate content unit tests from SMTP integration tests and end-to-end client/deliverability tests.

A solid test suite does more than prove `send(...)` was called. It proves **what recipients read in the generated plain-text version is accurate, informative, and retains Unicode across every MIME representation step the application controls**.
