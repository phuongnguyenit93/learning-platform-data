# Message-ID and Message Identification

When a **Spring Framework Mail** application sends an email, developers often need to answer questions such as: "What identifier does this message have?", "Which email in the mail system corresponds to this application send log?", "How do recipients reply in the right conversation thread?", "Why did SMTP report success yet I cannot find the message?", or "Will resending with the same Message-ID prevent duplicate emails?".

At the center of those questions is the **`Message-ID`** header. It is a *message-level* identifier defined by email format standards, yet real systems also have **business event IDs**, **SMTP transaction IDs**, **server queue IDs**, and **email provider IDs**. Each ID solves a different problem; mixing them up easily leads to mismatched mail statuses, reconciliation errors, and broken email threads.

This lesson covers `Message-ID` syntax, how Spring/Jakarta Mail generates and uses it, and how to design tracing, threading, retries, and cross-system message identification.

## 1. What Is Message-ID?

**`Message-ID`** is an email header field defined in the Internet Message Format standard (RFC 5322). It identifies **a specific emitted version of a message** generated by a mail-creating system. Its value typically looks like:

```text
Message-ID: <b164ef38-96d3-4fc5-a05a-8bbdc4ce8411@mailer.example.com>
```

Inspecting this value:

- `Message-ID` is the **header field name**.
- The `<...>` part is the standardized `msg-id` value, typically consisting of an identifier portion on the left, `@`, and an identifying domain on the right.
- `mailer.example.com` is an identifying domain controlled by the mail-generating party in this example.
- The left-hand string must be distinct across emitted messages; a UUID is an easy choice.

In its common form, we can represent it as:

```text
Message-ID: <unique-id@domain>
             |         |
             |         +-- identifying namespace / domain
             +------------ message-distinguishing part
```

A `Message-ID` should be **globally unique** for each generated message. Uniqueness is primarily the responsibility of the ID generator, not something the SMTP server guarantees on its own. Never reuse a static ID across all emails in an application.

### 1.1. Message-ID Lives in Headers, Not SMTP Commands

Before transmitting message content, SMTP uses commands such as `MAIL FROM` and `RCPT TO` to declare the delivery envelope. When the `DATA` phase begins, the client transmits **headers and body**, which may include `Message-ID`:

```text
C: MAIL FROM:<no-reply@example.com>
S: 250 2.1.0 OK
C: RCPT TO:<alice@example.net>
S: 250 2.1.5 OK
C: DATA
S: 354 End data with <CRLF>.<CRLF>
C: From: Example Shop <no-reply@example.com>
C: To: alice@example.net
C: Subject: Order confirmation
C: Message-ID: <order-evt-93a0@mailer.example.com>
C: Date: Thu, 12 Nov 2026 08:00:00 +0000
C:
C: Your order has been recorded.
C: .
S: 250 2.0.0 Queued as Q7F28A
```

The `C:` and `S:` prefixes are illustrative client/server markers, not transmitted on the wire. After the SMTP server returns `250` for `DATA`, all you know is that the server at that hop **accepted responsibility for processing the message**. You cannot infer that the message reached the Inbox or was read by the recipient.

In the example above:

- `<order-evt-93a0@mailer.example.com>` is the **Message-ID of the message content**.
- `Q7F28A` is the **queue ID** assigned by the illustrative SMTP server upon acceptance.
- The two values are independent; there is no rule requiring Message-ID to contain the queue ID or vice versa.

### 1.2. Message-ID Differs from Common Addresses and Headers

| Field | What Is It Used For? | Is It Message-ID? |
|---|---|---|
| `From:` | Sender address displayed in the message. | No. |
| `To:` / `Cc:` | Recipient addresses displayed in the message content. | No. |
| `MAIL FROM` / `RCPT TO` | Addresses in the SMTP transaction envelope. | No; these are SMTP commands, not headers. |
| `Date:` | Origination timestamp of the message. | No; timestamps are not unique identifiers. |
| `Subject:` | Message subject line. | No; many messages can share the same subject. |
| `Message-ID:` | Internet email format identifier of the message. | Yes. |
| `In-Reply-To:` | References the Message-ID of the message being replied to. | No; it expresses a relationship between messages. |
| `References:` | List of Message-IDs referenced in a conversation thread. | No; it is threading metadata. |
| `Content-ID:` | Identifies **a single MIME part**, often used with inline images and `cid:`. | No; it identifies one part of a message. |
| `Received:` | Trace entries added by mail transfer hops. | No; it is routing trace history. |

An email can carry multiple kinds of IDs because they describe **different entities**.

## 2. Syntax, Uniqueness, and Where Message-ID Is Generated

Under RFC 5322, a `msg-id` value takes the general shape of angle brackets enclosing left and right parts separated by `@`. The full specification is stricter than concatenating arbitrary strings; a simple implementation approach uses only safe characters for the ID alongside a valid identifying domain.

Readable examples:

```text
Message-ID: <abc123@example.com>
Message-ID: <20261112.080000.845d28fd@mailer.example.com>
Message-ID: <6d34cc43-7dd0-47dd-9408-411ee17cc1fa@notifications.example.com>
```

These examples are illustrative; never reuse them literally in production systems.

### 2.1. Who Is Responsible for Generating It?

Typically, **the email-creating system** generates `Message-ID` or delegates generation to a library. It may be:

1. The application setting the header itself before handing off the message;
2. Jakarta Mail generating it when preparing the message for sending;
3. A mail service or provider generating/replacing `Message-ID` if incoming messages lack one or per provider policy.

The RFC recommends every message have a Message-ID. In practice, incoming emails can still **lack the header**, have malformed headers, or carry duplicate values. Mail-consuming systems must handle those cases defensively.

### 2.2. How Should an ID Be Generated?

A straightforward policy uses a **random UUID combined with a domain controlled by the application**:

```java
import java.util.UUID;

String messageId =
    "<" + UUID.randomUUID() + "@mailer.example.com>";
```

This illustrates constructing a **Message-ID string** without attaching it to any email yet. The right-hand domain provides a meaningful namespace, and the UUID minimizes collision probability.

Things to avoid:

- Sequential counters like `<1@localhost>` across runs, which easily collide across hosts.
- Pure timestamps at one-second granularity, since multiple messages can be emitted within the same second.
- Embedding recipient emails, phone numbers, access tokens, or secrets inside `Message-ID`.
- Including invalid characters in the identifier portion when concatenating strings manually.
- Assuming a Message-ID submitted by a client or received from an external party is an authenticated identifier.

**`Message-ID` is not a security token.** It can be observed, extracted, or copied by recipients, intermediate servers, and mail processors. Never use it as a key for sensitive actions such as account verification or private resource access.

### 2.3. Does Message-ID Exist Before Sending?

Do not assume a newly created `MimeMessage` already has a Message-ID. With Jakarta Mail, this value is typically generated when the message is prepared or saved via `saveChanges()`, and the sending library may invoke that step on the application's behalf.

API-level example:

```java
MimeMessage message = mailSender.createMimeMessage();

// Right after creation, message.getMessageID() may return null.
message.saveChanges();

// After saveChanges(), the implementation has typically generated Message-ID.
String generatedMessageId = message.getMessageID();
```

**Note:** `saveChanges()` does not send the email over the network. It finalizes the state and certain headers of the MIME object. Calling `saveChanges()` again later in the sending pipeline can affect Message-ID depending on the library/implementation. Therefore, a value read before sending is not guaranteed to be the final identifier present in the delivered message.

If you need an ID **stable even before sending**, maintain a separate **business ID** for the email-sending request, independent of the Message-ID chosen by the mail layer.

## 3. Distinguishing All "Message IDs" in a Mail-Sending System

This is the most critical part of system design: multiple strings called "message ID" can appear at different layers.

| Identifier | Issued By | Scope | Typical Purpose |
|---|---|---|---|
| **Application message ID / event ID** | Application | Business logic, database, queue | Tracing the "need to send email" event, preventing duplicate jobs, searching logs, and linking to orders. |
| **RFC Message-ID / Internet Message-ID** | Message creator or mail implementation/provider | Email message | Identifying the message in headers, building conversation threads, correlating with some mail systems. |
| **SMTP queue ID** | Receiving SMTP server at a hop | That server's queue | Looking up SMTP relay logs, e.g., the code after `250 Queued as ...`. |
| **Provider message ID** | Email service / API | Within the provider | Querying send status, correlating events, webhooks, and provider dashboards. |
| **Mailbox UID / internal ID** | Mailbox server or storage app | One mailbox or archive | Identifying a stored email record; may differ across mailboxes for the same message. |
| **Content-ID** | MIME builder | One MIME part | Linking inline images/resources in HTML via `cid:...`. |

Example identifier flow in an e-commerce system:

```text
Order ORD-1028
    |
    v
Email event EVT-f9b6                 <-- application_event_id
    |
    v
Outbox -> Worker -> MimeMessage
                       |
                       +-- Message-ID:
                       |   <5bd29a@mailer.example.com>
                       |
                       +-- X-Correlation-ID: EVT-f9b6
    |
    v
SMTP relay accepts message           <-- smtp_queue_id = Q7F28A
    |
    v
Email service / event callback       <-- provider_message_id = provider-8391
    |
    v
Delivery / Bounce / Complaint
```

Not every environment exposes all of the IDs above. For example, with a simple SMTP relay, an application might not receive a provider message ID or delivery events.

### 3.1. Why Not Use Message-ID as a Database Primary Key?

Reasons include:

- Message-ID may be generated late, after the application creates the send request.
- Some services rewrite or normalize headers.
- One business request may generate multiple distinct emails, such as one message per recipient.
- One message may be sent multiple times due to retries, whereas each send attempt and delivery outcome must be tracked separately.
- Incoming emails may omit or duplicate Message-ID; never place absolute trust in headers arriving from external sources.

Hence, **application ID** should be the primary correlation key internally. Message-ID and provider ID are supplementary observed metadata for reconciliation.

## 4. How JavaMailSender Handles Message-ID

In Spring Framework Mail, `JavaMailSender` is the email-sending interface. `JavaMailSenderImpl` typically uses Jakarta Mail and SMTP transport. With `SimpleMailMessage`, Spring converts content to MIME under the hood; with `MimeMessage`, the application can manipulate headers directly.

General flow:

```text
mailSender.createMimeMessage()
         |
         v
MimeMessageHelper sets From / To / Subject / Text
         |
         v
Add business headers if needed
         |
         v
Prepare MIME (Date, Message-ID, MIME boundaries...)
         |
         v
mailSender.send(message)
         |
         v
SMTP DATA carries actual headers
         |
         v
SMTP server accepts or reports error
```

The email library can **auto-generate Message-ID** upon sending. Whether an application-provided Message-ID is preserved depends on the Spring/Jakarta Mail version, implementation, and downstream provider; when an ID must remain intact, verify transport policy and inspect the actual delivered message.

### 4.1. Example: Sending an Email and Reading Message-ID

Example for Spring Boot 3.x / Spring Framework 6.x, Java 17+, Jakarta Mail:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-mail'
}
```

`application.yml` with STARTTLS-enabled SMTP:

```yaml
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SMTP_USERNAME}
    password: ${SMTP_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true
            required: true
          connectiontimeout: 5000
          timeout: 5000
          writetimeout: 5000
```

`SMTP_USERNAME` and `SMTP_PASSWORD` should come from environment variables or a secret store. The following example uses a separate **application ID** generated prior to sending:

```java
package com.example.mail;

import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import java.util.UUID;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Service;

@Service
public class OrderMailService {

    private final JavaMailSender mailSender;

    public OrderMailService(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public SentMailInfo sendOrderConfirmation(
            String recipient, String orderCode) throws MessagingException {

        String applicationId = UUID.randomUUID().toString();

        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper =
            new MimeMessageHelper(message, "UTF-8");

        helper.setFrom("no-reply@example.com");
        helper.setTo(recipient);
        helper.setSubject("Order confirmation " + orderCode);
        helper.setText(
            "Order " + orderCode + " has been recorded."
        );

        // ID to correlate SMTP logs with application business logic.
        message.setHeader("X-Correlation-ID", applicationId);

        // Library finalizes MIME and sends via SMTP.
        mailSender.send(message);

        // Header may have been generated during sending.
        String rfcMessageId = message.getMessageID();
        return new SentMailInfo(applicationId, rfcMessageId);
    }

    public record SentMailInfo(
        String applicationId,
        String rfcMessageId
    ) {}
}
```

Key observations:

1. `UUID.randomUUID()` creates an **application ID** before sending. If the business transaction already has an ID or outbox row ID, reuse that stable ID instead of generating a new one on every retry.
2. `message.setHeader("X-Correlation-ID", applicationId)` attaches tracing metadata to the message. Custom headers may be preserved, modified, or stripped by some systems; never treat them as an authentication mechanism.
3. `mailSender.send(message)` performs the send and may throw `MailException` on Spring Mail failure.
4. `message.getMessageID()` reads `MimeMessage`'s Message-ID after the API-level send succeeds. It can return `null` across differing implementations; treat it as optional metadata.
5. `applicationId` and `rfcMessageId` need not match, and a normal return from `send(...)` **does not prove the email reached the Inbox**.

If `send(...)` throws an exception, the method above never returns `SentMailInfo`. In an outbox-based system, **persist the application ID and send request first**, then record attempt status, errors, and observed IDs as outcomes arrive; never lose traceability just because an SMTP connection drops.

### 4.2. Should You Set the Message-ID Header Yourself?

There are cases where an application needs to explicitly set a valid `Message-ID` value. Syntactically, you can set the header:

```java
String customMessageId =
    "<" + UUID.randomUUID() + "@mailer.example.com>";

MimeMessage message = mailSender.createMimeMessage();
message.setHeader("Message-ID", customMessageId);
```

However, this snippet **only shows how to set the header**—it does not guarantee the value stays unchanged all the way to the receiving mailbox. Jakarta Mail has rules that update certain headers when `saveChanges()` runs; some Spring Mail versions/implementations preserve an application-set Message-ID, yet exact behavior depends on the environment and downstream sending services.

When an application-controlled Message-ID is required:

- Use valid syntax and a sufficiently unique ID-generation strategy.
- Understand the ordering of MIME construction, `saveChanges()`, and `send(...)` in your implementation.
- Capture the actual post-send value and compare headers on messages arriving at a receiving system.
- Check whether your email provider rewrites or transforms Message-ID.

For most transactional applications, **letting Jakarta Mail generate Message-ID and using a separate application ID for tracing** is simpler.

### 4.3. Why Is SimpleMailMessage Insufficient for Header Manipulation?

`SimpleMailMessage` suits plain-text sending and exposes common fields such as `from`, `to`, `subject`, and `text`. It is not a general API for editing arbitrary MIME headers. When you need to read or set `Message-ID`, `In-Reply-To`, `References`, or custom headers, create a **`MimeMessage`** via `JavaMailSender.createMimeMessage()`.

That **does not mean** plain-text emails sent via `SimpleMailMessage` lack a Message-ID; the transport can generate one during sending. The difference lies in your ability to **control and inspect headers** from application code.

## 5. Message-ID and Conversation Threads: In-Reply-To, References

A major purpose of `Message-ID` is enabling mail clients to **group replies into a conversation thread**.

Suppose the original email is:

```text
From: support@example.com
To: alice@example.net
Subject: Ticket #123
Message-ID: <ticket123-initial@support.example.com>
```

Alice replies:

```text
From: alice@example.net
To: support@example.com
Subject: Re: Ticket #123
Message-ID: <alice-reply-01@client.example.net>
In-Reply-To: <ticket123-initial@support.example.com>
References: <ticket123-initial@support.example.com>
```

Support replies back:

```text
From: support@example.com
To: alice@example.net
Subject: Re: Ticket #123
Message-ID: <ticket123-reply-02@support.example.com>
In-Reply-To: <alice-reply-01@client.example.net>
References: <ticket123-initial@support.example.com> <alice-reply-01@client.example.net>
```

Here:

- Each message's **`Message-ID`** is a **new** identifier.
- **`In-Reply-To`** points to the message to which the new email is replying.
- **`References`** stores the chain of related Message-IDs to help reconstruct the conversation tree.

The ordering and contents of `References` should be built from the original email's metadata following proper threading rules. Email clients may also examine the subject or other heuristics when grouping messages; do not assume `In-Reply-To`/`References` guarantees every client creates the exact same thread.

### 5.1. Creating a Reply Email in Spring

Suppose the application processed a trusted inbound email and obtained its `Message-ID`:

```java
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

public class ReplyMailService {
    private final JavaMailSender mailSender;

    public ReplyMailService(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendReply(
            String recipient,
            String originalMessageId,
            String existingReferences) throws MessagingException {

        MimeMessage reply = mailSender.createMimeMessage();
        MimeMessageHelper helper =
            new MimeMessageHelper(reply, "UTF-8");

        helper.setFrom("support@example.com");
        helper.setTo(recipient);
        helper.setSubject("Re: Support request");
        helper.setText("We have received your response.");

        // Values must come from parsed and validated headers.
        reply.setHeader("In-Reply-To", originalMessageId);

        String references = (existingReferences == null
                || existingReferences.isBlank())
            ? originalMessageId
            : existingReferences.trim() + " " + originalMessageId;
        reply.setHeader("References", references);

        // Reply's Message-ID is typically auto-generated by the library.
        mailSender.send(reply);
    }
}
```

**Preconditions for this example:** `originalMessageId` and `existingReferences` were extracted from a parsed message, checked for valid syntax/length, and sanitized against header injection. Never pass raw arbitrary user-supplied strings directly into `setHeader(...)`. Production systems should also normalize References lists to avoid duplicates or unbounded growth in long threads.

**Never copy the original message's `Message-ID` into the reply's `Message-ID`.** A reply is a new message and must have a new ID; link it to the previous message using `In-Reply-To` and `References`.

### 5.2. Does Having the Same Subject Put Emails in the Same Thread?

No. Many emails can share the subject “Order notification” while belonging to different recipients and events. Subject is not a unique identifier. Conversely, email clients can make different threading decisions even when reference headers are valid. When a support system needs a reliable business thread, maintain a **separate ticket ID** in the database rather than relying solely on how email clients group messages.

## 6. Message-ID with Multiple Recipients, Resending, and Retries

### 6.1. One Message Sent to Multiple Recipients

In a single SMTP transaction, a client can declare multiple `RCPT TO` addresses for the same message content. Because it is still **one message**, recipients may see the same `Message-ID`:

```text
MAIL FROM:<noreply@example.com>
RCPT TO:<alice@example.net>
RCPT TO:<bob@example.net>
DATA
Message-ID: <notice-001@mailer.example.com>
...
```

If the system instead generates **one personalized email per recipient** with differing content, send times, or headers, treat them as separate messages and assign each its own Message-ID.

Recipient count, SMTP transaction count, and Message-ID count therefore **do not always match one-to-one**.

### 6.2. Does Retrying Mean Keeping the Same Message-ID?

There is no rule that keeping the same Message-ID causes mail servers to automatically deduplicate messages. An SMTP relay or inbox can easily accept **two deliveries carrying the identical Message-ID**. While some systems implement deduplication logic, you should never rely on such unguaranteed behavior.

Suppose:

1. A worker transmits the full message data to the SMTP server.
2. The server accepts it, but the `250` response is lost due to a network issue.
3. The worker hits a timeout, marks an error, and retries.
4. The recipient may receive **two emails**, even if both attempts carried the exact same Message-ID.

Diagram:

```text
Outbox job EVT-202
       |
       +-- attempt 1 --> SMTP accepts message
       |                  but client never receives 250
       |
       +-- attempt 2 --> SMTP accepts message again
                          |
                          v
                    Duplicate delivery possible
```

Recommended strategy:

- Bind a stable **application message ID** or outbox ID to a single business request.
- Record each **send attempt** and its status separately.
- Use bounded retries with backoff and explicitly handle **unknown** outcomes.
- For payments, verifications, or sensitive workflows, design idempotency at the request origin and consider reconciling provider events.
- Never treat reusing a `Message-ID` as an "exactly-once" delivery guarantee.

### 6.3. Why Separate App ID from Message-ID During Retries?

Suppose an application uses an outbox:

| Field | Example Value | Purpose |
|---|---|---|
| `outbox_id` | `EVT-202` | Unique business request. |
| `attempt_no` | `1`, `2` | Send attempt number. |
| `internet_message_id` | `<e9cd@mailer.example.com>` | Message-ID observed at the email layer. |
| `smtp_queue_id` | `Q71F` | Queue ID returned by the SMTP relay, if available. |
| `provider_message_id` | `P-0092` | Provider-specific ID, if available. |
| `status` | `PENDING`, `SENT_TO_PROVIDER`, `UNKNOWN`, `FAILED` | Internal state based on observed evidence. |

One outbox event can have multiple send attempts. Each attempt may or may not capture an SMTP/provider ID. This design scales much better than collapsing everything into a single ambiguous `messageId` column.

## 7. Correlating Message-ID with SMTP and Provider Logs

Example trace:

```text
App log:       correlation_id=EVT-202
Message MIME:  Message-ID=<e9cd@mailer.example.com>
SMTP response: 250 2.0.0 queued as Q71F
Provider API:  provider_message_id=P-0092
Webhook:       event=delivered, provider_message_id=P-0092
```

These values can be linked in a correlation table if your infrastructure emits and retains them. **Do not assume an SMTP queue ID or provider API ID equals the Message-ID header.**

### 7.1. When Sending via SMTP

SMTP responses sometimes include a queue ID, though not always. `JavaMailSender.send(...)` is typically a high-level API that does not directly expose the server's queue ID to business code. For correlation, you may need relay logs, application-attached headers/metadata, and provider-specific event features.

### 7.2. When Sending via API/SDK

A provider may return its own ID immediately upon a successful HTTP request. That ID is useful for querying delivery events, bounces, or complaints. Still, a successful HTTP request usually only means **the provider accepted the request**, not that the recipient received the email.

If a webhook includes a Message-ID, check the provider's documentation: some services name their **internal ID** field `message_id`, others mean the RFC Message-ID, and others include both. Distinguish them with clear column names in your database.

### 7.3. Message-ID Does Not Prove Authenticity

A spoofed email can contain a completely valid-looking `Message-ID`. This header does not replace sender authentication (SPF, DKIM, DMARC), user authentication, or application signatures. A sender can also inject an ID colliding with an existing one.

If your system processes **inbound email**, treat Message-ID as untrusted metadata until validated within the mailbox/source context. Never rely on Message-ID alone to authorize permissions, payments, or sensitive operations.

## 8. Designing Identifier Storage in a Spring System

Illustrative data model:

```text
email_outbox
  id                   UUID / String  (PK)
  business_event_type  String
  business_event_id    String
  recipient            String
  template_code        String
  status               Enum
  created_at           Timestamp

email_send_attempt
  id                   UUID / String  (PK)
  outbox_id            FK -> email_outbox.id
  attempt_number       Integer
  started_at           Timestamp
  finished_at          Timestamp?
  internet_message_id  String?
  smtp_queue_id        String?
  provider_message_id  String?
  smtp_response_code   String?
  error_category       String?
  status               Enum
```

`?` denotes a nullable field, not SQL syntax. This is a conceptual model to separate identifier layers, not a mandatory schema for every application.

Processing flow can look like:

1. The business transaction creates a send request and persists a stable `email_outbox.id`; with a transactional outbox, this is committed in the same transaction as the business event.
2. A worker picks up the job, creates a new attempt record, and records the start time.
3. The worker composes MIME, adds a correlation header if appropriate, and calls `JavaMailSender.send(...)` or the provider API.
4. Record the API result and observed IDs, distinguishing "accepted by SMTP/provider" from "delivered."
5. When delivery or bounce webhooks arrive, correlate using the documented provider ID or correlation ID and update status.
6. For timeouts with uncertain outcomes, handle the `UNKNOWN` state via reconciliation/retry policies rather than assuming guaranteed failure.

For small applications sending only occasional notifications without per-attempt observability, the schema above may be overkill. Even then, keep clear which **ID belongs to business logic** and which **ID is an email header** so you do not mix them up when debugging.

## 9. Common Errors and Misconceptions

### 9.1. "Every email is guaranteed to have a Message-ID"

Most standards-compliant emails carry a `Message-ID`, yet mail-receiving systems can still encounter messages with missing headers, malformed headers, or duplicate IDs. Never assume incoming data is always well-formed.

### 9.2. "SMTP returning 250 means Message-ID reached the Inbox"

False. A 250 response after `DATA` only indicates the SMTP server **accepted the message at that hop**. Final delivery, bounces, and Inbox placement depend on subsequent processing.

### 9.3. "Message-ID can replace request ID and queue ID"

Wrong scope. Message-ID is message metadata; request IDs, queue IDs, and provider IDs have different lifecycles and issuers. Tracing across layers requires explicit mapping.

### 9.4. "Every call to send always generates a fresh Message-ID"

Do not assume that. Behavior depends on whether a MIME object is reused, whether a header was pre-set, `saveChanges()` calls, and implementation specifics. By application design, each new message should have its own Message-ID; when sending distinct messages, create independent `MimeMessage` instances.

### 9.5. "Same Message-ID guarantees no duplicate email will arrive"

False. Message-ID is not a universal SMTP idempotency key. Receiving infrastructure may handle two identical or different messages sharing a Message-ID in its own way.

### 9.6. "Message-ID is the Content-ID of an inline logo"

False. `Message-ID` identifies the entire email, whereas `Content-ID` identifies a single part such as an image. HTML `<img src="cid:logo">` references `Content-ID: <logo>`, not the whole message's Message-ID.

### 9.7. "To reply in the same thread, reuse the old message's Message-ID"

False. A reply gets a **new Message-ID** and links to the previous message via `In-Reply-To` / `References`. Reusing the original Message-ID defeats per-message identification.

## 10. Inspecting Message-ID in Sent Emails

When diagnosing issues, inspect the **raw message source (Show Original)** in an email client if supported. Useful fields include:

```text
Message-ID: <e9cd@mailer.example.com>
Date: Thu, 12 Nov 2026 08:00:00 +0000
From: Example Shop <no-reply@example.com>
To: alice@example.net
Subject: Order confirmation
In-Reply-To: <older@support.example.com>
References: <initial@support.example.com> <older@support.example.com>
```

Notes on the raw format:

- Header field names are case-insensitive, though canonical casing like `Message-ID` improves readability.
- Long headers can be folded across lines; when parsing, use a MIME/RFC-aware library instead of splitting manually on newlines.
- Do not assume every system preserves all custom headers intact.
- A copy stored in a mailbox may acquire extra headers added by receiving servers; Message-ID is one piece of metadata to read, not a complete record of the email's journey.

With Jakarta Mail, you can read:

```java
String messageId = mimeMessage.getMessageID();
String[] replies = mimeMessage.getHeader("In-Reply-To");
String[] references = mimeMessage.getHeader("References");
```

Handle `null` and multi-value headers safely; never assume every field is present. For inbound emails, normalize and validate values before storing them or using them for reply features.

## 11. Practice Exercises

### Exercise 1 — Identify Identifiers in Logs

Given the logs:

```text
OUTBOX: id=EVT-502
MIME: Message-ID=<ab54@mailer.example.com>
SMTP: 250 2.0.0 queued as Q7F28A
WEBHOOK: message_ref=P-884, status=delivered
```

Identify the business ID, RFC Message-ID, SMTP queue ID, and provider ID.

**Answer:** `EVT-502` is the application/outbox ID, `<ab54@mailer.example.com>` is the RFC Message-ID, `Q7F28A` is the SMTP queue ID, and `P-884` is the provider ID in this example. Maintain explicit mappings between them.

### Exercise 2 — Generating an Identifier for a New Email

Write Java code generating a UUID and combining it with domain `mailer.example.com` into a Message-ID formatted as `<uuid@mailer.example.com>`. Explain why you should not use a counter starting at 1 on each application startup.

**Hint:** UUIDs reduce collision risk across multiple hosts/processes; a local counter easily repeats on restarts or horizontal scaling.

### Exercise 3 — Constructing a Reply Message

Original email:

```text
Message-ID: <initial-001@support.example.com>
```

The reply email needs a new `Message-ID`, `In-Reply-To: <initial-001@support.example.com>`, and `References: <initial-001@support.example.com>`. If another reply follows, `References` expands with the conversation's ancestor messages.

### Exercise 4 — Analyzing a Timeout After DATA

A worker finished transmitting the email but lost the connection before receiving the `250` response. Should it record "definitely failed" and immediately retry with the same Message-ID?

**Hint:** You cannot be sure whether the server accepted it. Record an unknown status, use the application/outbox ID to manage attempts, consider reconciliation and bounded retries; reusing Message-ID does not guarantee duplicate suppression.

### Exercise 5 — Can Content-ID Replace Message-ID?

An HTML email contains:

```html
<img src="cid:brand-logo" alt="Logo">
```

The image part has `Content-ID: <brand-logo>`. Can `brand-logo` be used as the Message-ID for all emails in the system?

**Answer:** No. CID only identifies a MIME part for HTML references. Message-ID must uniquely identify each new message and avoid collisions across emitted emails.

## 12. Summary

**`Message-ID` is the email message's header identifier per Internet standards.** It helps identify messages and link reply threads via `In-Reply-To` / `References`. In Spring Framework Mail applications, Jakarta Mail typically generates or finalizes this header while preparing/sending a `MimeMessage`; applications can read it with `getMessageID()` and manipulate headers directly on `MimeMessage` when needed.

When building a reliable email-sending system, clearly separate **application/outbox ID**, **RFC Message-ID**, **SMTP queue ID**, and **provider message ID**. Use a stable application ID to coordinate business workflows, store Message-ID as message metadata, correlate IDs only with observed evidence, and never treat Message-ID as a delivery guarantee or duplicate-prevention mechanism.
