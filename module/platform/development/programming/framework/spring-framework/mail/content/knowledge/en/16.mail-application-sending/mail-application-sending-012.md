# Recording a Message Key to Trace an Email

When a user reports "I didn't receive the email", operations needs to locate the exact message produced by a business action: when the email was created, which worker processed it, how many send attempts ran, whether the SMTP relay accepted it, and whether the provider reported a bounce or delivery. Searching solely by subject, recipient address, or timestamp is rarely enough because those values can repeat.

In **Spring Framework Mail**, create an application-managed **application message key**, persist it alongside the send request, and carry it across the database, outbox, workers, logs, and provider events. You can attach the key to a custom MIME header such as `X-Application-Message-Key` to aid raw-email lookups. Headers are a correlation transport mechanism; the database/outbox remains the primary source of truth.

The message key must be distinguished from the RFC `Message-ID`, correlation ID, attempt ID, SMTP queue ID, and provider message ID. Each identifier has its own scope and purpose.

## 1. Emails pass through many layers

```text
Business logic (order, account, invoice)
       |
       v
Email service / template renderer
       |
       v
Outbox / queue / background worker
       |
       v
MimeMessage + JavaMailSender
       |
       v
SMTP relay / email provider
       |
       v
Recipient's mail server
       |
       v
Mailbox / spam filter / client
```

Each layer can have its own logs and IDs:
- Business logic creates an order confirmation email.
- The outbox stores the email-sending job.
- A worker picks up the job and creates a send attempt.
- Spring Mail constructs the MIME message.
- The SMTP relay accepts the message and logs a queue ID.
- The provider emits events such as delivered, bounced, or deferred.
- The destination mail server may accept the message yet place it in spam or user filters.

A good message key helps you:
- Link an email to its business record and send request.
- Look up worker and SMTP submission logs.
- Distinguish retry attempts of the same logical email.
- Correlate delivery/bounce webhooks back to the right email.
- Support incident debugging, reconciliation, and auditing.
- Avoid searching by body content or personal data.

## 2. Distinguishing identifier types

| Identifier | Who creates it? | Scope | Purpose |
|---|---|---|---|
| **Application message key** | Application | One logical/business email | Cross-system traceability. |
| **Correlation ID** | Request gateway or application | One business flow that may emit multiple emails | Links related operations together. |
| **Attempt ID** | Worker/application | One send attempt | Distinguishes individual retries. |
| **RFC Message-ID** | MIME library/provider or application per policy | One concrete MIME message | Standards-based email ID; supports threading/lookups. |
| **SMTP queue ID** | SMTP relay/MTA | One acceptance at a relay | Looks up MTA logs. |
| **Provider message ID** | Email provider | One submission at the provider | Looks up dashboards/APIs/webhooks. |
| **Provider event ID** | Provider | One specific event | Deduplicates and reconciles webhooks. |

### 2.1. Application message key

This is an identifier intentionally generated by the application, such as a UUID or ULID:

```text
email_01JCM7YQ5J3Z6T4F8A2N9K1M6P
```

The key should be:
- unique within the appropriate database/tenant scope;
- free of recipient emails, names, phone numbers, or sensitive data;
- stable across the entire lifecycle of one logical email;
- stored in the database and included in related logs;
- unchanged across retries.

A random key is not an authentication token. Knowing a message key does not grant permission to view email content or download attachments.

### 2.2. Correlation ID

A correlation ID typically ties to a request or broader business flow. Creating an order may trigger a confirmation email, a warehouse email, and a support notification. Those emails have **separate message keys yet share the same correlation ID**.

```text
correlation_id = flow_7f92...
  |
  +-- message_key = order-confirmation-...
  |
  +-- message_key = warehouse-notification-...
  |
  +-- message_key = customer-receipt-...
```

Do not automatically use the correlation ID as the message key; the two concepts have different scopes.

### 2.3. Attempt ID

If the same logical email is retried due to a transient error, the message key stays the same while each attempt receives its own attempt ID:

```text
message_key = msg_01J...
  |
  +-- attempt_id = att_001  -> timeout
  +-- attempt_id = att_002  -> SMTP accepted
```

### 2.4. RFC Message-ID

RFC `Message-ID` is a standard email header, typically formatted as:

```text
Message-ID: <unique-value@example-mail-host>
```

It identifies a concrete MIME message and can be used by mail clients for threading or raw-message lookups. Mail libraries or SMTP providers may generate `Message-ID` automatically. A retry may construct a new MIME message with a different `Message-ID`, even though it represents the same logical email.

**Do not overload the Message-ID header with the application key just for lookup convenience.** Keep `Message-ID` in its standard role and store it as supplementary metadata if obtainable. The application key should have its own database field and may be carried via a custom header.

### 2.5. SMTP queue ID and provider message ID

An SMTP relay may log a queue ID. That is an MTA-internal ID, not a cross-server standard. `JavaMailSender.send(...)` also has no general contract returning a queue ID.

Email providers may supply a provider message ID or custom metadata via API responses, webhooks, dashboards, or custom arguments. Do not assume Spring Mail automatically exposes every provider ID.

## 3. Generating and storing the message key

### 3.1. Using UUID or ULID

A straightforward choice is a random UUID:

```java
import java.util.UUID;

String messageKey = UUID.randomUUID().toString();
```

Or use a ULID if your system already has the library and conventions. Avoid sequential integers that could leak traffic volume or internal ordering when keys appear in headers/logs.

### 3.2. Generate the key once per logical email

The message key should be generated when the application decides to emit a logical email, before inserting the job into the queue/outbox.

For example:
- Order ORD-001 creates its first confirmation email: generate a key.
- Worker retries on a transient error: reuse that key.
- User intentionally requests resending an invoice next week as a new action: usually generate a new key, optionally linked to the same business entity/correlation.

What matters is distinguishing a retry of the same message from a new send request.

### 3.3. Enforcing a unique constraint

The database should enforce uniqueness on the key:

```sql
CREATE TABLE email_outbox (
    message_key       VARCHAR(64) PRIMARY KEY,
    correlation_id    VARCHAR(64),
    business_type     VARCHAR(40) NOT NULL,
    business_id       VARCHAR(100) NOT NULL,
    template_name     VARCHAR(120) NOT NULL,
    recipient_ref     VARCHAR(100) NOT NULL,
    status            VARCHAR(32) NOT NULL,
    created_at        TIMESTAMP NOT NULL,
    updated_at        TIMESTAMP NOT NULL
);
```

This is an illustrative schema. `recipient_ref` can be an internal ID or protected reference; you do not necessarily have to store plaintext email addresses in log tables. Add indexes on business type/ID, status, or created_at as needed.

If a business action may emit a notification type only once, add a business unique constraint—for example on business type, business ID, template name, and notification version. The message key identifies the row; the business constraint prevents creating two logical emails unintentionally.

## 4. Saving the key before sending: the Outbox pattern

Do not generate the key only in memory and send immediately when emails are critical and require traceability. If the application crashes after SMTP accepts the message but before recording state, the database will not know the email was sent. Conversely, if you record SENT before calling SMTP and the process crashes, the email may never leave the application.

The Outbox pattern records the send request inside the business transaction:

```text
Database transaction
  |
  +--> update business data
  |
  +--> insert email_outbox(message_key, status=PENDING)
  |
  v
COMMIT
  |
  v
Outbox worker claims row
  |
  v
Create attempt + send MIME
  |
  v
Persist result / provider events
```

Inside the order-creation transaction:
1. Save the order.
2. Generate the message key.
3. Insert an outbox record in `PENDING` state.
4. Commit both together.

A worker reads the outbox and sends. If the application restarts, the send request survives for continued processing.

An outbox does not guarantee exactly-once delivery on its own. SMTP/the provider may accept the message while the application loses connectivity before receiving the response. In that case, the state may be ambiguous; model `UNKNOWN` or an equivalent state with a reconciliation policy.

## 5. Attaching the message key to a MIME header in Spring Mail

You can add custom headers to `MimeMessage`:

```java
message.setHeader(
    "X-Application-Message-Key",
    messageKey
);
```

You can also add the correlation ID and attempt ID:

```java
message.setHeader("X-Correlation-ID", correlationId);
message.setHeader("X-Mail-Attempt-ID", attemptId);
```

Custom headers help operations inspect raw sources or find metadata in logs/providers if intermediate systems preserve them. However:
- Relays or intermediate systems may strip custom headers.
- Recipients can inspect raw headers; never place secrets or personal data there.
- Not every provider lets dashboards filter by custom headers.
- Verify header preservation by testing against your real provider.

**The database/outbox remains the primary source of truth.** Headers are only a mechanism for passing correlation keys across layers.

### 5.1. Example building a message with custom headers

```java
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Component;

@Component
public class TracedMailSender {

    private final JavaMailSender mailSender;

    public TracedMailSender(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void send(
            String recipient,
            String subject,
            String plainText,
            String htmlText,
            String messageKey,
            String correlationId,
            String attemptId) throws MessagingException {

        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper =
            new MimeMessageHelper(message, true, "UTF-8");

        helper.setFrom("no-reply@example.com");
        helper.setTo(recipient);
        helper.setSubject(subject);
        helper.setText(plainText, htmlText);

        message.setHeader(
            "X-Application-Message-Key",
            messageKey
        );

        if (correlationId != null && !correlationId.isBlank()) {
            message.setHeader("X-Correlation-ID", correlationId);
        }

        message.setHeader("X-Mail-Attempt-ID", attemptId);

        mailSender.send(message);
    }
}
```

Keys in this example must be server-generated, bounded in format, and free of CR/LF. Never take raw headers from requests and forward them onto outgoing messages; if accepting a correlation ID from a request, validate it against trusted system rules.

### 5.2. Message construction order

Set custom headers after creating `MimeMessageHelper` and after calling `setText(...)`. Jakarta Mail preserves headers when preparing the message. Do not write MIME boundaries manually or inject headers into the body string.

If inline resources exist, preserve the order:
1. `helper.setText(plainText, htmlText)`;
2. `helper.addInline(...)` for referenced resources;
3. `helper.addAttachment(...)` for standalone attachments;
4. send after completing the message.

### 5.3. Do not use custom headers for secrets

Avoid:

```text
X-Application-Message-Key: customer-email=alice@example.com
X-Reset-Password-Token: secret-token-value
X-Internal-Database-ID: 123456
```

Headers can appear in raw emails, relay logs, provider systems, or forwarded messages. Use only opaque identifiers; never embed passwords, reset tokens, session IDs, financial details, or unnecessary personal data.

## 6. Storing Message-ID and provider-generated IDs

After preparing and sending a message, you can read the RFC `Message-ID` from `MimeMessage` if the implementation generated the header:

```java
mailSender.send(message);

String rfcMessageId = message.getMessageID();
```

With `JavaMailSenderImpl`, MIME preparation typically calls `saveChanges()` before sending, and `Message-ID` may be generated during that process. However, custom implementations or providers may behave differently; treat the value as optional and verify with integration tests in a real sending environment.

You can store `rfcMessageId` as an additional attribute of the attempt:

```sql
CREATE TABLE email_attempt (
    attempt_id          VARCHAR(64) PRIMARY KEY,
    message_key         VARCHAR(64) NOT NULL,
    attempt_number      INTEGER NOT NULL,
    rfc_message_id      VARCHAR(255),
    provider_message_id VARCHAR(255),
    smtp_queue_id       VARCHAR(255),
    started_at          TIMESTAMP NOT NULL,
    accepted_at         TIMESTAMP,
    outcome             VARCHAR(32) NOT NULL
);
```

Do not overwrite the application message key with `Message-ID`. `Message-ID` can differ across retries; the message key preserves the link to the logical email.

SMTP queue IDs and provider message IDs must be captured from wherever they are provided:
- SMTP server logs if your organization operates the relay;
- provider API responses when using a sending API;
- provider event webhooks;
- provider dashboards/search APIs;
- provider-supported metadata or custom arguments.

Generic SMTP does not guarantee `JavaMailSender` returns a queue ID. If that ID is needed, define a specific integration with your MTA/provider.

## 7. Data model for messages and attempts

A clean model separates the logical email from individual send attempts:

```text
email_outbox
  message_key (PK)
  correlation_id
  business_type / business_id
  template_name / template_version
  recipient_ref
  status
  created_at / updated_at
       |
       | 1-to-many
       v
email_attempt
  attempt_id (PK)
  message_key (FK)
  attempt_number
  rfc_message_id
  provider_message_id
  smtp_queue_id
  started_at / accepted_at
  outcome / error_code
       |
       | 1-to-many
       v
email_event
  event_id (PK)
  attempt_id or provider_message_id
  event_type
  provider_event_time
  received_at
  metadata_ref
```

Roles:
- `email_outbox` describes the logical email to send.
- `email_attempt` describes each worker send attempt.
- `email_event` stores asynchronous events such as delivered, bounced, or complained.

There is no need to store full HTML or file attachments in log tables. If content must be retained for auditing, use storage with explicit access controls, encryption, and retention; the outbox usually only needs template/version and references to the data to render.

## 8. Delivery states: SMTP accepted does not mean delivered

States should accurately express what the system actually knows:

| State | Meaning |
|---|---|
| `PENDING` | Send request created, not yet picked up by a worker. |
| `SENDING` | A worker is executing an attempt. |
| `SMTP_ACCEPTED` | SMTP relay accepted the message at submission. |
| `DELIVERED` | Provider reported delivered/accepted by the destination mail server per provider event definition. |
| `DEFERRED` | Provider or mail server temporarily deferred delivery. |
| `BOUNCED` | Provider reported non-delivery. |
| `COMPLAINED` | Complaint/spam report event occurred if supported by the provider. |
| `FAILED` | Definite error before the message was accepted. |
| `UNKNOWN` | Uncertain outcome, e.g., connection timed out after the relay may have received the message. |

`SMTP_ACCEPTED` states only that the SMTP server accepted the message; it does not prove the email reached the Inbox, avoided spam filters, or was read by the recipient. A provider `delivered` event usually reflects acceptance by the receiving mail server, not that a human opened or read it.

Not every SMTP provider offers delivery/bounce webhooks. With plain generic SMTP, terminal tracking may stop at `SMTP_ACCEPTED` or rely on internal MTA logs.

## 9. Retries and idempotency

### 9.1. Keep the message key, create a new attempt ID

A retry is another attempt for the same logical email:

```text
message_key = msg_abc
  |
  +-- attempt_id = att_001
  |      outcome = UNKNOWN
  |
  +-- attempt_id = att_002
         outcome = SMTP_ACCEPTED
```

Never generate a new message key on retry, or the history of one logical email fragments across unlinked records. Attempt IDs must be new to distinguish each send attempt.

Create a fresh `MimeMessage` on each attempt. Never reuse the same mutable message or `MimeMessageHelper` across threads or retries.

### 9.2. SMTP does not provide exactly-once by default

A difficult scenario:
1. The worker sends the message.
2. The SMTP relay accepts it successfully.
3. The connection drops before the application receives the reply.
4. The worker records a timeout and retries.

Here the first email may already have been sent, and the retry may produce a second email. The message key shows both belong to the same request, yet **does not by itself prevent SMTP from sending duplicates**.

Mitigations:
- Explicit outbox and attempt states.
- Provider API idempotency keys if supported by the provider.
- Reconciliation via provider logs/events before retrying `UNKNOWN` cases.
- Bounded retries with backoff.
- Unique constraints so two logical emails are not created for the same business event.
- Reference codes in content so recipients recognize duplicates if they still occur.

Never claim exactly-once delivery solely because an application message key is unique.

### 9.3. How does an idempotency key differ from a message key?

A message key identifies a logical email. An idempotency key is a token used by an API/provider to recognize repeated requests and prevent duplicate execution within a provider-defined scope and window. You can use the same value if the provider permits and semantics match, but never assume every SMTP relay treats a custom header as an idempotency key.

## 10. Correlating provider webhooks back to the message key

When a provider sends a webhook event, the event may contain a provider message ID, recipient, event type, timestamp, SMTP response/bounce reason, custom metadata, and its own event ID.

Processing flow:

```text
Provider webhook
      |
      v
Verify signature / authenticate source
      |
      v
Persist event metadata safely
      |
      v
Deduplicate by provider event ID
      |
      v
Map provider message ID / custom metadata
      |
      v
Find email_attempt and message_key
      |
      v
Update event history and aggregate status
```

Key precautions:
1. Verify webhook signatures or the provider's authentication mechanism.
2. Never trust an event body merely because the endpoint received a request.
3. Store provider event IDs with a unique constraint so redelivered webhooks do not create duplicate events.
4. Correlate by provider message ID or custom metadata that has been configured and tested.
5. Accept late or out-of-order webhooks; append event history rather than assuming states always arrive in order.
6. Never take a recipient from a webhook to modify business data without authenticating the event.
7. Retain only needed metadata; bounce reasons may contain addresses or sensitive details.

The custom `X-Application-Message-Key` header may be preserved by providers, though there is no universal guarantee across relays. When a provider supports custom arguments/tags or metadata fields, prefer the provider's official mechanism and verify how metadata appears in events. Database mappings should still link provider message IDs and message keys.

## 11. Example worker: recording attempts and sending keyed messages

The snippet below illustrates a worker. The repository is an application-defined interface; row claiming and transactions must be implemented appropriately for your database/queue.

```java
package com.example.mail;

import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import java.time.Instant;
import java.util.UUID;

import org.springframework.mail.MailException;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Component;

@Component
public class EmailOutboxWorker {

    private final JavaMailSender mailSender;
    private final EmailOutboxRepository repository;

    public EmailOutboxWorker(
            JavaMailSender mailSender,
            EmailOutboxRepository repository) {
        this.mailSender = mailSender;
        this.repository = repository;
    }

    public void deliver(EmailOutboxItem item) {
        String attemptId = UUID.randomUUID().toString();
        Instant startedAt = Instant.now();

        repository.markSending(
            item.messageKey(),
            attemptId,
            startedAt
        );

        try {
            MimeMessage message = mailSender.createMimeMessage();
            MimeMessageHelper helper =
                new MimeMessageHelper(message, true, "UTF-8");

            helper.setFrom("no-reply@example.com");
            helper.setTo(item.recipient());
            helper.setSubject(item.subject());
            helper.setText(item.plainText(), item.htmlText());

            message.setHeader(
                "X-Application-Message-Key",
                item.messageKey()
            );
            message.setHeader(
                "X-Mail-Attempt-ID",
                attemptId
            );

            if (item.correlationId() != null) {
                message.setHeader(
                    "X-Correlation-ID",
                    item.correlationId()
                );
            }

            mailSender.send(message);

            // RFC Message-ID may have been generated during
            // saveChanges/send; store it if the implementation provides it.
            String rfcMessageId = null;
            try {
                rfcMessageId = message.getMessageID();
            } catch (MessagingException ignored) {
                // Message-ID is supplementary metadata; do not reverse
                // a successful SMTP submission result.
            }

            repository.markSmtpAccepted(
                item.messageKey(),
                attemptId,
                rfcMessageId,
                Instant.now()
            );

        } catch (MailException | MessagingException ex) {
            // Not every error proves SMTP did not receive the message.
            // The repository must separate definite failures from
            // ambiguous outcomes to avoid blind retries.
            repository.recordSendError(
                item.messageKey(),
                attemptId,
                classify(ex),
                Instant.now()
            );
        }
    }

    private String classify(Exception ex) {
        return ex.getClass().getSimpleName();
    }
}
```

This is a skeleton illustrating the relationship between message keys and attempts. In a real system:
- `EmailOutboxItem` should be loaded from safely claimed outbox rows.
- `markSending` and `markSmtpAccepted` must guard against contention among multiple workers.
- Classifying `MailException` must consider error type, response, and whether submission outcome is known; do not lump everything into `FAILED`.
- If SMTP times out at an uncertain point, record `UNKNOWN` or an equivalent state and reconcile before retrying.
- Never log `ex.getMessage()` verbatim if it may contain recipients, hosts, body content, or sensitive details.
- Inject a testable `Clock` rather than calling `Instant.now()` directly everywhere.

## 12. Logging and querying to investigate emails

A useful log entry might contain:

```json
{
  "event": "email.smtp_accepted",
  "messageKey": "msg_01JCM7YQ5J3Z6T4F8A2N9K1M6P",
  "attemptId": "att_8e71...",
  "correlationId": "flow_7f92...",
  "rfcMessageId": "<abc123@example-mail-host>",
  "template": "order-confirmation",
  "provider": "smtp-relay-a",
  "durationMs": 842
}
```

This is a structured log example; you do not need to log full recipients or email bodies for lookups.

A support investigation workflow might be:
1. User provides an order code or ticket reference through support channels.
2. Authorized staff look up the business record to find the message key.
3. Use the message key to query the outbox record and attempts.
4. Inspect timestamps, states, normalized errors, and `Message-ID` if present.
5. If `SMTP_ACCEPTED`, use the provider ID/SMTP logs to investigate further.
6. If the provider reported `BOUNCED`, inspect the bounce category/reason per access permissions.
7. If the provider reported `DELIVERED` yet the user cannot find it, guide them to check spam/quarantine and verify their mailbox; never claim the recipient read it.

Example SQL query:

```sql
SELECT
    o.message_key,
    o.correlation_id,
    o.status,
    o.created_at,
    a.attempt_id,
    a.attempt_number,
    a.rfc_message_id,
    a.provider_message_id,
    a.smtp_queue_id,
    a.outcome,
    a.accepted_at
FROM email_outbox o
LEFT JOIN email_attempt a
    ON a.message_key = o.message_key
WHERE o.message_key = :messageKey
ORDER BY a.attempt_number;
```

In larger systems, look up by an authorized business reference first and then retrieve the message key. Never expose a public endpoint accepting an arbitrary message key and returning full send history; a key is not an authorization mechanism.

## 13. Security and privacy

Message keys can appear across multiple systems. Therefore:
- Use opaque keys; never embed emails, names, phone numbers, or sensitive customer IDs.
- Never use keys as bearer tokens or passwords.
- Never write reset tokens, tokenized URLs, email bodies, or Base64 attachments into logs.
- Restrict email-history lookup permissions by role.
- Mask/encrypt recipients if stored in identifiable form.
- Maintain retention policies for outbox, attempts, events, and provider payloads.
- Limit stored webhook data; retain only necessary fields.
- Never place custom headers containing sensitive internal data into outgoing emails.
- Control log access and audit support lookups.

Custom headers may be visible to recipients in raw message source. Treat headers as externally exposed data. If you do not want to expose the application key, use an opaque external correlation token or store the mapping solely in provider metadata when supported.

## 14. Common misconceptions

### "Message-ID is the message key"

No. RFC `Message-ID` identifies one MIME message; the application message key identifies one logical email in the application. A retried email can have a different `Message-ID` while keeping the same application key.

### "SMTP send without exception means the email reached the Inbox"

No. It usually means only that the SMTP relay accepted the message. Delivery, spam filtering, and whether the user opens the message are separate steps.

### "Adding X-Application-Message-Key to headers is enough"

No. Headers aid tracing, yet may be stripped or unindexed by providers. You must persist the key in the outbox/database and include it in application logs.

### "Retries need a new message key"

Not when retrying the same logical email. Keep the message key and create a new attempt ID. A new intentional resend requested by a user may be a new logical message under business rules.

### "A unique message key guarantees no duplicates"

No. SMTP does not automatically provide idempotency on custom headers. You need an outbox, unique constraints, provider idempotency when available, and handling for `UNKNOWN` outcomes.

### "Provider message ID is always available in JavaMailSender"

No. Generic SMTP does not guarantee the send API returns a provider-specific ID. You must use a provider API, webhooks, or relay logs.

### "You can log all email content for easy searching"

Avoid this. Use message keys, attempt IDs, template/version, status, and provider IDs; keep sensitive content in access-controlled storage only if auditing truly requires it.

## 15. Common mistakes and fixes

| Symptom | Cause | Fix |
|---|---|---|
| Cannot find email by business ID | Business reference → message key mapping not saved | Store business type/ID in outbox or mapping table. |
| Multiple emails with same subject get confused | Searching by subject and timestamp | Look up by message key. |
| Retry treated as a new logical email | Generating key on each worker run | Generate key when creating the outbox item; keep across retries. |
| Cannot distinguish send attempts | Single status column on outbox | Create an attempt table with dedicated attempt IDs. |
| Message-ID is null in logs | Not yet generated or implementation/provider does not expose it | Store optionally; verify with integration tests. |
| Custom header missing in received mail | Relay/provider stripped the header | Keep DB mapping; use official provider metadata. |
| Provider event cannot be mapped | Provider message ID/custom metadata not saved | Add mapping and inspect webhook payloads. |
| Webhook updates status twice | Provider retried event without deduplication | Unique constraint on provider event ID. |
| Status regresses on out-of-order events | Assuming webhooks always arrive in order | Store event history and enforce ordered state transitions. |
| Timeouts cause duplicate sends | Uncertain whether relay accepted the message | Record UNKNOWN, reconcile before retry; use idempotency APIs if available. |
| Logs leak personal data | Logging full MIME/exceptions/recipients | Log keys and minimal metadata; mask sensitive details. |
| Message key used as access token | Confusing correlation ID with authorization | Enforce independent authorization on every lookup endpoint. |

## 17. Summary

To trace an email in Spring Framework Mail, generate an **application message key** when creating the send request, store the key with the outbox/business reference, and carry it across logs, workers, attempts, and provider events. You can attach the key to a custom MIME header like `X-Application-Message-Key` to aid raw-email lookups, while keeping the database/outbox as the source of truth because intermediate systems may strip headers.

Distinguish this key from **correlation ID**, **attempt ID**, RFC **Message-ID**, SMTP queue ID, and provider message ID. Keep the message key across retries, issue a new attempt ID per try, record `SMTP_ACCEPTED` separately from `DELIVERED`, and handle `UNKNOWN` outcomes on submission timeouts. Finally, authenticate webhooks, deduplicate events, enforce lookup authorization, and keep sensitive data out of headers and logs. With these practices, any email can be traced from its originating business action through every send attempt and delivery event without relying on subjects or message bodies.
