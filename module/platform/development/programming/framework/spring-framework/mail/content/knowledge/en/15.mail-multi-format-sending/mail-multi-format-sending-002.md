# Choosing the Preferred Part When a Mail Client Supports Multiple Types

An email can provide the same content in multiple representations. For example, an order confirmation email may have:

- **Plain text** so it is readable in any basic email environment, assistive devices, or clients that do not render HTML.
- **HTML** to present headings, product tables, colors, and an order view button.

If only HTML is sent, users who configure their email client in text-only mode or systems that filter HTML may not see the content as intended. If only plain text is sent, the recipient can still read it but lacks rich layout. The MIME standard solves this problem with the **`multipart/alternative`** structure: a single message containing multiple semantically equivalent parts, each using a different format.

The key point of this lesson is that **the order of representation parts expresses the sender's preference**. According to MIME rules, parts are ordered from the least preferred format to the most preferred format; the last part is the most preferred choice. The email client picks the part it can display based on its capabilities and user settings.

For typical emails, applications usually place **plain text first, HTML second**. When the client supports both, HTML is the preferred option; when the client only supports text, it can use the plain text part. Spring Mail supports this via `MimeMessageHelper.setText(plainText, htmlText)`.

## 1. Why Does an Email Need Multiple Formats?

Not all recipients view email in the same environment:

- Some users use email clients that display only plain text.
- Some organizations disable HTML or strip active content to reduce security risks.
- Screen readers may work better with simple text content that has a clear reading order.
- Some clients on small devices do not render HTML/CSS the same way a browser does.
- Email gateways may filter or transform certain MIME parts.
- Users may choose text-only view mode even when their client is capable of rendering HTML.

An HTML-only email may look great in one client but be hard to read in another environment. Conversely, a text-only email is broadly compatible but makes it difficult to present product tables or action buttons.

**Multipart alternative** lets the application send both representations in the same message instead of sending two separate emails. The recipient still receives one email and the client selects the appropriate part.

### 1.1. The Parts Must Have the Same Meaning

The parts in `multipart/alternative` are alternative representations of **the same content**. For example:

| Business content | Plain text | HTML |
| --- | --- | --- |
| Order code | Order A123 has been confirmed. | Heading "Order A123 has been confirmed" |
| Total amount | Total: 220,000 VND | Summary table with labels and typography |
| Action | View order: full URL | "View order" button pointing to the same URL |
| Support | Contact support@example.com | Email link to support@example.com |

You should not put one amount in the HTML version and a different amount in the plain text version. Nor should you put important information only into HTML and leave text readers with no way to access it. If one part contains completely different data from the rest, it is not an equivalent alternative; you should consider another MIME structure or redesign the content.

## 2. How Does `multipart/alternative` Work?

MIME defines a container that can hold multiple body parts. With `multipart/alternative`, each part describes the same information in a different format.

A simple email may have the structure:

~~~text
Content-Type: multipart/alternative; boundary="mail-boundary"

--mail-boundary
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

Hello Nguyen An,

Order A123 has been confirmed.
Total: 220,000 VND
View order: https://app.example.com/orders/A123

--mail-boundary
Content-Type: text/html; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

<html>
  <body>
    <h1>Order A123 has been confirmed</h1>
    <p>Hello Nguyen An,</p>
    <strong>Total: 220,000 VND</strong>
    <a href="https://app.example.com/orders/A123">View order</a>
  </body>
</html>

--mail-boundary--
~~~

This is an abbreviated example to show the structure, not fixed headers that every library must generate identically. Actual boundaries and transfer encodings are generated by the MIME library.

The parts:

1. The outermost header declares `Content-Type: multipart/alternative`.
2. `boundary` separates the body parts.
3. The first part has `Content-Type: text/plain`.
4. The second part has `Content-Type: text/html`.
5. The final boundary marker adds `--` to close the multipart container.

The email client parses this structure, identifies the content types it supports, and picks the appropriate representation. It does not need to display both plain text and HTML one after another.

### 2.1. Ordering Rule: Least Preferred First, Most Preferred Last

According to the `multipart/alternative` rule in MIME (RFC 2046), parts are arranged in **increasing order of preference**. The last part is considered the most preferred part.

Common example:

~~~text
1. text/plain       # fallback, less preferred
2. text/html        # richer presentation, more preferred
~~~

If the client supports both plain text and HTML, it usually chooses HTML because it is the last part and is more preferred by the sender. If the client does not support HTML, it can choose plain text.

You can think of it as:

1. **Part 1 — `text/plain` (fallback):** simple text content with wide compatibility.
2. **Part 2 — `text/html` (preferred):** layout, tables, links, and presentation formatting.

The order in `multipart/alternative` goes from least preferred to most preferred; the last part is the sender's preferred choice.

This order is a **preference signal per the MIME standard**, not a mandatory command forcing every email client to display HTML. Clients may apply user settings, security policies, content filters, or their own rendering limitations.

### 2.2. What If the Order Is Reversed?

Suppose a message contains:

~~~text
1. text/html
2. text/plain
~~~

By the ordering rule, plain text becomes the more preferred choice because it is last. A client supporting both may choose plain text, even though HTML is richer. A client supporting only HTML can still use HTML because it is the only part it supports.

Therefore, if the goal is to **prefer HTML while keeping a text fallback**, put text first and HTML second. Do not reverse the order just because you want "HTML to appear first" in raw MIME.

## 3. Distinguishing multipart/alternative from Other MIME Structures

Not every email with multiple parts uses `multipart/alternative`. You must choose the right structure according to the meaning of the parts.

| MIME type | Purpose | Example |
| --- | --- | --- |
| `multipart/alternative` | Multiple equivalent representations of the same content | Plain text and HTML |
| `multipart/mixed` | Multiple independent components sent together | Email body and an attached PDF file |
| `multipart/related` | Parts related to each other to form a complete piece of content | HTML body and inline images referenced via CID |

### 3.1. Alternative Is Not an Attachment List

Do not put plain text and HTML inside `multipart/mixed` just to send two versions:

~~~text
multipart/mixed
  text/plain
  text/html
~~~

`multipart/mixed` states that the parts are components coexisting in a single message. Some clients may display one part, treat the other part as an attachment, or exhibit unexpected behavior.

For two equivalent versions, use `multipart/alternative` so the client understands that it **only needs to choose one representation**.

### 3.2. When There Is an Attachment

If an email has both a plain/HTML body and a PDF, the typical structure is `multipart/mixed` on the outside, containing the alternative body and the attachment:

~~~text
multipart/mixed
  |
  +-- multipart/alternative
  |     |
  |     +-- text/plain
  |     |
  |     +-- text/html
  |
  +-- application/pdf
       Content-Disposition: attachment
~~~

Here:

- `multipart/mixed` groups the email body and the attached file.
- `multipart/alternative` lets the client choose plain text or HTML.
- `application/pdf` is a separate file, not an alternative version of the body.

### 3.3. When HTML Has Inline Images

HTML can reference images by Content-ID:

~~~html
<img src="cid:company-logo" alt="Company logo">
~~~

Inline images related to HTML are normally packaged in `multipart/related`. When combining plain text, HTML, and an inline image, the conceptual structure can be:

~~~text
multipart/mixed
  |
  +-- multipart/alternative
  |     |
  |     +-- text/plain
  |     |
  |     +-- multipart/related
  |           |
  |           +-- text/html
  |           +-- image/png (Content-ID: company-logo)
  |
  +-- application/pdf (attachment)
~~~

Nesting multiparts helps distinguish:

- **Alternative:** plain text or the HTML version.
- **Related:** which inline resources HTML needs.
- **Mixed:** which independent files the message also includes.

The library may generate a specific nesting structure depending on the multipart mode; what matters is that the MIME semantics are preserved.

## 4. Creating Both Versions with Spring Mail

`SimpleMailMessage` only supports simple text messages. To send multiple formats in the same email, use `MimeMessage` via `JavaMailSender` and `MimeMessageHelper`.

### 4.1. Using setText(plainText, htmlText)

Example:

~~~java
import java.nio.charset.StandardCharsets;
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

public class OrderMailService {
    private final JavaMailSender mailSender;

    public OrderMailService(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendConfirmation(String recipient)
            throws MessagingException {

        String plainText = """
                Hello Nguyen An,

                Order A123 has been confirmed.
                Total: 220,000 VND

                View order:
                https://app.example.com/orders/A123

                If you need support, please reply to this email.
                """;

        String htmlText = """
                <!DOCTYPE html>
                <html lang="en">
                <body>
                  <h1>Order A123 has been confirmed</h1>
                  <p>Hello Nguyen An,</p>
                  <p><strong>Total: 220,000 VND</strong></p>
                  <p>
                    <a href="https://app.example.com/orders/A123">
                      View order
                    </a>
                  </p>
                  <p>If you need support, please reply to this email.</p>
                </body>
                </html>
                """;

        MimeMessage mime = mailSender.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(
                mime,
                true,
                StandardCharsets.UTF_8.name()
        );

        helper.setFrom("orders@example.com");
        helper.setTo(recipient);
        helper.setSubject("Order A123 Confirmation");

        // Plain text is the first alternative, HTML is the second alternative.
        helper.setText(plainText, htmlText);

        mailSender.send(mime);
    }
}
~~~

The key point is the call:

~~~java
helper.setText(plainText, htmlText);
~~~

The two parameters are ordered as:

1. `plainText` — the plain text version.
2. `htmlText` — the HTML version.

Spring Mail uses them to create alternative content. With this standard call, plain text is the fallback and HTML is the preferred part.

### 4.2. Why Does the Constructor Take multipart = true?

In the example:

~~~java
new MimeMessageHelper(mime, true, "UTF-8");
~~~

The `true` parameter instructs the helper to work with a multipart structure. This is the right choice when you need an alternative body, inline resources, or attachments. `false` is suitable for a simple body that does not need multipart; do not use it for the plain + HTML example above.

### 4.3. setText(html, true) vs. setText(plain, html)

The two calls have different meanings:

~~~java
// Only an HTML part; no plain-text alternative.
helper.setText(htmlText, true);

// Two equivalent parts: plain text and HTML.
helper.setText(plainText, htmlText);
~~~

In the first overload, the boolean parameter indicates that the string is HTML. It does **not** mean "enable HTML and auto-generate plain text". If a fallback is needed, the application must construct the plain text content itself and call the two-string overload.

### 4.4. Do Not Put HTML Tags into SimpleMailMessage

~~~java
SimpleMailMessage message = new SimpleMailMessage();
message.setText("<h1>Hello</h1>");
~~~

This still creates **plain text** containing literal `<h1>` characters, because `SimpleMailMessage` does not mark the body as HTML and does not create a MIME alternative. To send HTML or multiple formats, `MimeMessage` is required.

## 5. Creating multipart/alternative Manually with Jakarta Mail

`MimeMessageHelper.setText(plainText, htmlText)` is the simple choice for the common order. If the application needs to **actively choose a different preference order**, it can construct `MimeMultipart("alternative")` directly.

### 5.1. Preferring HTML with Plain Text as Fallback

~~~java
import java.nio.charset.StandardCharsets;
import jakarta.mail.Message;
import jakarta.mail.Multipart;
import jakarta.mail.internet.InternetAddress;
import jakarta.mail.internet.MimeBodyPart;
import jakarta.mail.internet.MimeMessage;
import jakarta.mail.internet.MimeMultipart;
import org.springframework.mail.javamail.JavaMailSender;

public void sendHtmlPreferred(
        JavaMailSender sender,
        String recipient,
        String plainText,
        String htmlText) throws Exception {

    MimeMessage message = sender.createMimeMessage();
    message.setFrom(new InternetAddress("news@example.com"));
    message.setRecipients(
            Message.RecipientType.TO,
            InternetAddress.parse(recipient, true)
    );
    message.setSubject("New Notification", StandardCharsets.UTF_8.name());

    MimeMultipart alternative = new MimeMultipart("alternative");

    MimeBodyPart plainPart = new MimeBodyPart();
    plainPart.setText(plainText, StandardCharsets.UTF_8.name());
    alternative.addBodyPart(plainPart); // Less preferred.

    MimeBodyPart htmlPart = new MimeBodyPart();
    htmlPart.setContent(
            htmlText,
            "text/html; charset=UTF-8"
    );
    alternative.addBodyPart(htmlPart); // Most preferred.

    message.setContent(alternative);
    sender.send(message);
}
~~~

The part addition order is **plain first, HTML second**, so HTML is the last alternative and is preferred according to MIME.

The example uses `InternetAddress.parse(..., true)` for stricter address parsing and `setSubject(..., UTF-8)` to set a subject that may contain Vietnamese characters. In production code, catch/declare specific exceptions appropriate to the method signature instead of using a generic `throws Exception`.

### 5.2. Preferring Plain Text

If a product has a special requirement that **plain text is the preferred representation**, the order can be reversed:

~~~java
MimeMultipart alternative = new MimeMultipart("alternative");

MimeBodyPart htmlPart = new MimeBodyPart();
htmlPart.setContent(htmlText, "text/html; charset=UTF-8");
alternative.addBodyPart(htmlPart); // Less preferred.

MimeBodyPart plainPart = new MimeBodyPart();
plainPart.setText(plainText, "UTF-8");
alternative.addBodyPart(plainPart); // Most preferred.

message.setContent(alternative);
~~~

A client supporting both is recommended to pick the last part according to MIME preference order, though it can still be influenced by text-only settings, policies, or client-specific behavior.

Do not reverse the order merely for arbitrary experimentation. Have a clear product reason, such as an environment requiring content that does not rely on HTML, and then test on target clients.

## 6. Choosing the Format Based on Mail Client Capabilities

The sender cannot know every rendering capability of the recipient's client. `multipart/alternative` tells the client what representations are available and their preference order, but **the client makes the final decision**.

A simple interpretation:

| Client / setting | Usable parts | Typical outcome |
| --- | --- | --- |
| Supports only plain text | `text/plain` | Displays the text version |
| Supports HTML and text | Both | Usually chooses HTML if HTML is last |
| User selects text-only | Both in message | May display plain text per setting |
| Gateway strips HTML | Remaining text part | Recipient reads the fallback |
| Client does not understand a content type | Parts the client understands | Picks an appropriate supported part |
| Client has HTML filtering policy | Depends on policy | May switch to text or transform content |

This is a general behavioral model. You cannot deduce the exact appearance across every Outlook, Gmail, Apple Mail, webmail, or mobile app solely from MIME order.

### 6.1. The Sender Cannot Force a Client to Render HTML

Placing HTML last in multipart alternative means **the sender prefers HTML**, not that the client is forced to render HTML. The recipient may:

- enable text-only reading mode;
- use a mail reader that does not support HTML;
- go through a security gateway that strips or transforms HTML;
- open the email with a tool that extracts only text.

Therefore, plain text must be self-contained with the important information. Do not write text like "Your email viewer does not support HTML" and omit all transaction details.

### 6.2. Do Not Send Multiple Emails to Replace Multipart

An inappropriate approach is sending one HTML email and one separate text email to the same recipient. This can cause the user to receive two messages, create two threads, cause confusion, and increase send volume.

`multipart/alternative` bundles both representations into **a single email**. The client picks only one part to display according to its capabilities and settings.

## 7. Content in Both Parts Must Stay Synchronized

If HTML and plain text are authored in two separate places, they can drift apart over time:

~~~text
HTML:       Total 220,000 VND
Plain text: Total 200,000 VND
~~~

This is a serious content bug because recipients may see different information depending on their client.

### 7.1. Use One Model for Both

Instead of creating two data-fetching flows:

~~~text
Order -> HTML query -> HTML
Order -> Text query -> Plain text
~~~

create a single unified model:

~~~text
Order
  |
  v
OrderConfirmationMailModel
  |                         |
  v                         v
HTML template          Plain-text renderer
  |                         |
  +-----------+-------------+
              |
              v
        MimeMessage
~~~

Example:

~~~java
public record OrderMailModel(
        String customerName,
        String orderNumber,
        List<String> lineTexts,
        String totalText,
        String orderUrl) {
}
~~~

HTML and plain text both read `customerName`, `orderNumber`, `lineTexts`, `totalText`, and `orderUrl`. As a result, both parts share the same source data.

### 7.2. Generating Plain Text from the Model

~~~java
public String renderPlainText(OrderMailModel model) {
    StringBuilder text = new StringBuilder();
    text.append("Hello ")
            .append(model.customerName())
            .append(",\n\n");
    text.append("Order ")
            .append(model.orderNumber())
            .append(" has been confirmed.\n\n");

    for (String line : model.lineTexts()) {
        text.append("- ").append(line).append('\n');
    }

    text.append("\nTotal: ")
            .append(model.totalText())
            .append("\n");
    text.append("View order: ")
            .append(model.orderUrl())
            .append("\n");
    return text.toString();
}
~~~

This is a simple plain text renderer. With multiple email types and locales, dedicated text templates can be used instead of string concatenation. Whichever approach is chosen, both parts should still be generated from **the same model and the same business rules**.

### 7.3. Synchronizing Links and Actions

If HTML has a button:

~~~html
<a href="https://app.example.com/orders/A123">View order</a>
~~~

plain text must have an equivalent URL or instruction:

~~~text
View order:
https://app.example.com/orders/A123
~~~

Do not leave text readers unable to perform the action. URLs must be generated from a trusted domain, use HTTPS where appropriate, and verify authorization on the backend when the recipient opens them.

## 8. Charset and Transfer Encoding for Each Alternative

Each MIME part has its own headers. For Vietnamese content, both plain text and HTML should have an explicitly defined charset:

~~~text
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

...

Content-Type: text/html; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

...
~~~

`charset=UTF-8` indicates that the bytes of the text part should be decoded using UTF-8. `Content-Transfer-Encoding` describes how bytes are represented for transport, such as quoted-printable or base64.

Do not confuse them:

- **Charset:** how Unicode text is converted into bytes.
- **Transfer encoding:** how bytes are represented inside MIME.
- **Alternative order:** which part the client is hinted to prefer.

These are three independent aspects.

### 8.1. Configuring UTF-8 with Spring Mail

When using the helper:

~~~java
MimeMessageHelper helper =
        new MimeMessageHelper(mime, true, StandardCharsets.UTF_8.name());
~~~

At the same time, you can set Spring Boot's default encoding:

~~~yaml
spring:
  mail:
    default-encoding: UTF-8
~~~

When the helper constructor specifies an encoding, that encoding is used for the text parts the helper creates under this configuration. Inspect raw MIME if Vietnamese diacritics appear garbled; do not manually convert Unicode strings to Base64 before calling `setText`.

### 8.2. Do Not Pre-Encode the Entire HTML in Base64

Do not do this:

~~~java
String encodedHtml = Base64.getEncoder().encodeToString(
        htmlText.getBytes(StandardCharsets.UTF_8)
);
helper.setText(plainText, encodedHtml);
~~~

When you do that, the part declared as HTML actually contains only Base64 characters. The email client will not automatically decode it into HTML as you expect. Pass the original Unicode string; the MIME library handles transfer encoding.

## 9. Combining Alternative with Attachments

An invoice email may need:

- a plain text version;
- an HTML version;
- an invoice PDF file.

Spring Mail:

~~~java
MimeMessage mime = sender.createMimeMessage();
MimeMessageHelper helper =
        new MimeMessageHelper(mime, true, "UTF-8");

helper.setFrom("billing@example.com");
helper.setTo("customer@example.net");
helper.setSubject("Invoice A123");
helper.setText(
        "Invoice A123 has been issued. Total: 220,000 VND.",
        "<html><body>"
        + "<h1>Invoice A123</h1>"
        + "<p>Total: <strong>220,000 VND</strong></p>"
        + "</body></html>"
);
helper.addAttachment(
        "Invoice-A123.pdf",
        new FileSystemResource(invoiceFile)
);

sender.send(mime);
~~~

`setText(plain, html)` still creates the alternative for the body. `addAttachment(...)` adds an independent MIME part. The exact structure may nest multiparts depending on the helper mode, but semantically:

~~~text
multipart/mixed
  multipart/alternative
    text/plain
    text/html
  application/pdf
~~~

The PDF file is **not** an alternative for the body. The recipient needs the body (choosing one of the two representations) plus the attachment.

### 9.1. Combining Inline Images

If HTML references an image via CID:

~~~html
<img src="cid:logo" alt="Logo">
~~~

the helper can add an inline image:

~~~java
helper.setText(plainText, htmlText);
helper.addInline(
        "logo",
        new ClassPathResource("mail/logo.png"),
        "image/png"
);
~~~

Set the content first, then add inline resources as guided by `MimeMessageHelper`. Images related to HTML should be represented using `multipart/related`; the helper has appropriate multipart modes to manage that structure. Plain text does not need to contain the image, but should include the organization name or information conveyed by the logo if that is essential content.

## 10. When Should the Preference Order Be Changed?

The common default is **plain text first, HTML second**. Only change it when there is a specific reason.

| Goal | Order to consider | Reason |
| --- | --- | --- |
| Prefer HTML, keep text fallback | text/plain → text/html | Most common usage |
| Prefer plain text, keep HTML alternative | text/html → text/plain | Last part is text |
| Send text content only | Only text/plain | No multipart alternative needed |
| Send HTML only | Only text/html | No fallback; consider compatibility |
| Body plus attachment | alternative for body inside mixed | Attachment is independent content |

If using only `MimeMessageHelper.setText(plain, html)`, Spring provides the standard plain-then-HTML order. If you want a different preference order, you can build `MimeMultipart("alternative")` directly and add parts in the desired order.

### 10.1. Do Not Use Order to Replace Security Policy

If an organization disallows HTML, reversing the order is not a sufficient measure to eliminate HTML. Clients may still support and select HTML based on their own settings; gateways may also process the message according to other policies.

If you genuinely need to send text-only for security or compliance reasons, **create only a `text/plain` part**, rather than creating HTML and hoping the client does not select it.

### 10.2. Do Not Use HTML Just for a Button

Plain text can also contain full URLs and clear instructions. If an email is very simple and does not need layout or images, sending text only can be a more maintainable option. Multipart alternative is useful when two presentations are genuinely needed, not a mandatory requirement for every email.

## 11. Testing Alternative Ordering

When using `MimeMessageHelper`, you should inspect the generated MIME rather than only asserting that the method was called. You can serialize the message to bytes or read the multipart content in tests.

### 11.1. Inspecting MIME Structure with Jakarta Mail

Example test skeleton once the message is constructed:

~~~java
Object content = mimeMessage.getContent();
assertTrue(content instanceof Multipart);

Multipart multipart = (Multipart) content;
~~~

Depending on the `MimeMessageHelper` multipart mode and whether attachments or inline images are present, the outermost `Multipart` may be `mixed` or `related`, not necessarily `alternative` directly. Therefore, real tests should **traverse through the parts** and locate the multipart with subtype `alternative`.

A recursive helper can traverse:

~~~java
void inspectPart(Part part) throws Exception {
    Object content = part.getContent();

    if (content instanceof Multipart multipart) {
        System.out.println(
                multipart.getContentType()
        );
        for (int i = 0; i < multipart.getCount(); i++) {
            inspectPart(multipart.getBodyPart(i));
        }
    } else {
        System.out.println(part.getContentType());
    }
}
~~~

This is illustrative code showing how to traverse the structure; tests should use assertions rather than only printing to the console. When encountering `multipart/alternative`, verify:

- the expected number of parts;
- the text part has `Content-Type` `text/plain`;
- the HTML part has `Content-Type` `text/html`;
- plain text comes before HTML if HTML is the preferred part;
- the content of both parts carries the same business information.

### 11.2. Testing via Raw MIME

You can save a test message as an `.eml` file or use a mock SMTP server such as Mailpit/GreenMail to view the raw message. Verify:

1. The multipart header has subtype `alternative`.
2. Boundaries properly separate the parts.
3. The `Content-Type` and charset of each part are correct.
4. Plain text appears before HTML when HTML is intended to be preferred.
5. Unicode content is decoded properly.
6. If an attachment is present, it resides in an independent MIME branch and is not treated as an alternative.

Do not write tests requiring boundary strings, transfer encodings, or header folding to match an example verbatim. The library may generate different boundaries and encodings while still remaining valid. Parse the message and check **MIME semantics**.

### 11.3. Testing Email Client Behavior

Beyond raw MIME, test with the clients the product must support:

- clients rendering HTML;
- clients configured as text-only;
- clients on mobile devices;
- environments with gateways that filter HTML;
- screen readers or tools that consume text content.

This testing reveals whether the preferred part is interpreted as intended in practice. No Java unit test completely replaces viewing the email in target clients.

## 12. Common Mistakes

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Recipient sees raw HTML tags | Sent with `SimpleMailMessage` or HTML flagged wrongly | Use `MimeMessageHelper` and MIME HTML |
| Email has HTML but no text fallback | Only called `setText(html, true)` | Call `setText(plainText, htmlText)` |
| Client supporting both chooses plain text | Plain text is last in alternative | Place HTML after plain text to prefer HTML |
| Text-only client sees no content | No `text/plain` created or text part is too sparse | Create a self-contained fallback |
| Client shows both parts as two files | Used `multipart/mixed` instead of `multipart/alternative` for two representations | Use the `alternative` subtype |
| Attachment is picked as the body | Attachment placed inside the alternative branch | Use `multipart/mixed` on the outside |
| CID image does not display | Mismatched related/CID structure | Use appropriate helper multipart mode, check Content-ID |
| HTML and text show different totals | Built with two separate data flows | Use the same model for both renderers |
| Vietnamese diacritics garbled in one part | Mismatched charset or bytes in that part | Use UTF-8 consistently and check raw MIME |
| Assuming HTML last forces every client to use HTML | Confusing MIME preference with client control | Respect recipient-side settings and policies |
| Library produces nested MIME differing from example | Multipart mode or attachment/inline resource changes nesting | Traverse MIME tree, do not assume root is always alternative |

### 12.1. Error from Missing Plain-Text Alternative

HTML-only example:

~~~java
helper.setText("<h1>Order confirmed</h1>", true);
~~~

Some clients may display it well, but text-only clients will have no fallback version. For transactional emails, create a text version:

~~~java
helper.setText(
        "Order A123 has been confirmed. Total: 220,000 VND.",
        "<html><body><h1>Order A123 has been confirmed</h1>"
        + "<p>Total: 220,000 VND.</p></body></html>"
);
~~~

### 12.2. Error from Using mixed for Two Versions

If plain and HTML are added as two body parts in `multipart/mixed`, clients may treat them as two separate components rather than two alternative display options. Choose the subtype based on **the semantic relationship between parts**, not just on how many parts exist.

### 12.3. Error from Assuming the Helper Always Creates Root Alternative

When the helper enables multipart and adds inline images or attachments, the message may have nested containers. A test that only checks `mimeMessage.getContent()` for the alternative subtype directly at the root can fail even though the actual structure is valid.

Traverse the MIME tree and find the part with `multipart/alternative`. For attachments, also check `Content-Disposition` to identify downloadable parts.

## 13. A Complete Service Example with Dynamic Data

The example below uses the same data to generate plain text and HTML:

~~~java
package com.example.mail.application;

import java.nio.charset.StandardCharsets;
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Service;

@Service
public class NotificationMailService {
    private final JavaMailSender sender;

    public NotificationMailService(JavaMailSender sender) {
        this.sender = sender;
    }

    public void sendOrderConfirmed(OrderMailModel model)
            throws MessagingException {

        String plainText = """
                Hello %s,

                Order %s has been confirmed.
                Total: %s

                View order:
                %s
                """.formatted(
                model.customerName(),
                model.orderNumber(),
                model.totalText(),
                model.orderUrl()
        );

        // Dynamic data in HTML must be escaped according to context.
        // This example assumes variables are rendered through a template engine.
        String htmlText = renderHtml(model);

        MimeMessage mime = sender.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(
                mime,
                true,
                StandardCharsets.UTF_8.name()
        );

        helper.setFrom("orders@example.com");
        helper.setTo(model.recipient());
        helper.setSubject(
                "Order confirmation " + model.orderNumber()
        );
        helper.setText(plainText, htmlText);

        sender.send(mime);
    }

    private String renderHtml(OrderMailModel model) {
        // In a real application, render with Thymeleaf/FreeMarker
        // so dynamic data is escaped properly per context.
        return "<html><body><h1>Order confirmed</h1>"
                + "<p>Total: "
                + escapeHtml(model.totalText())
                + "</p></body></html>";
    }

    private String escapeHtml(String value) {
        return value.replace("&", "&amp;")
                .replace("<", "&lt;")
                .replace(">", "&gt;")
                .replace("\"", "&quot;")
                .replace("'", "&#39;");
    }
}
~~~

This is an abbreviated example to illustrate the flow. In real applications, use a template engine instead of a hand-written escape function, and escape **each value according to its exact context** (text node, attribute, or URL). `OrderMailModel` is an application-defined DTO containing `recipient`, `customerName`, `orderNumber`, `totalText`, and `orderUrl`.

The key point remains `helper.setText(plainText, htmlText)`: both representations are placed into the same message. When HTML is preferred, it comes after the text part in alternative.

## 14. Rules for Choosing the Preferred Part in Email Design

When building a new email, you can decide using these steps:

1. **Identify core content:** what must the recipient know even if reading only text?
2. **Create complete plain text:** information, amounts, deadlines, and URLs independent of HTML.
3. **Create equivalent HTML:** add layout and formatting without changing the meaning.
4. **Choose order:** usually text first, HTML second to prefer HTML.
5. **Use the right MIME subtype:** `multipart/alternative` for two representations, `mixed` for attachments, `related` for inline resources.
6. **Set charset:** consistent UTF-8 for Unicode content.
7. **Verify MIME tree:** confirm part order and nesting relationships.
8. **Test on target clients:** ensure text-only remains readable and HTML does not break.

### 14.1. Quick Selection Matrix

| Requirement | How to build content |
| --- | --- |
| Text-only email | `SimpleMailMessage` or MIME `text/plain` |
| HTML with text fallback | `MimeMessageHelper.setText(plain, html)` |
| HTML without fallback | `MimeMessageHelper.setText(html, true)` |
| Plain text preferred over HTML | Manually build `multipart/alternative` with HTML first, text second |
| HTML + PDF | `multipart/mixed` on the outside, alternative for body |
| HTML + inline image + text | alternative containing text and a related branch for HTML/images |
| HTML + inline image + PDF | Combine alternative, related, and mixed per part relationships |

## 15. End-to-End Scenario: Multi-Format Invoice Email

An application sends an invoice to customer Nguyen An. The content needs to include:

- Invoice code INV-2026-001.
- Total amount 2,200,000 VND.
- Link to view the invoice.
- An attached PDF file.
- Company logo in the HTML version.

Plain text content:

~~~text
Hello Nguyen An,

Invoice INV-2026-001 has been issued.
Total: 2,200,000 VND.

View invoice:
https://app.example.com/invoices/INV-2026-001

The PDF file is attached to this email.
~~~

The HTML content can display an information table, logo, and a "View invoice" button. Both use the same invoice code, total amount, and URL. MIME is structured semantically as:

~~~text
multipart/mixed
  |
  +-- multipart/alternative
  |     |
  |     +-- text/plain
  |     |
  |     +-- multipart/related
  |           |
  |           +-- text/html
  |           +-- image/png (company logo)
  |
  +-- application/pdf (invoice attachment)
~~~

When the client supports HTML, it can choose the HTML part and display the layout along with the logo. When the client only reads text, it uses the plain text part and still has the invoice code, total amount, link, and information about the attached file. The PDF remains a separate attachment regardless of which body part the client selects.

**Choosing the preferred part** is therefore not toggling a format flag in a UI. It is the sender **packaging representations in compliance with MIME and ordering them by preference**, so the recipient's client has full information to decide how to display the message.
