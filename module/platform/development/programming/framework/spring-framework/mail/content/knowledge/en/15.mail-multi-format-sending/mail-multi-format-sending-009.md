# Handling Plain-Text-Only Clients

Emails are not always opened in an application capable of rendering HTML. Some gateways extract only plain text, some users disable HTML for security or accessibility reasons, and some mail clients/devices display only the **plain text** part. If a Spring Mail application creates only HTML, recipients may see an empty email, miss important links, or not know what action to take.

In **Spring Framework Mail**, the standard way to support both groups of clients is sending emails in MIME **`multipart/alternative`** format, containing a `text/plain` part and a `text/html` part expressing the same message. With `MimeMessageHelper`, create both versions using `helper.setText(plainText, htmlText)`. Mail clients can choose the HTML version if supported; plain-text-only clients can use the plain text version.

Plain text must be **a complete content version**, not merely a sentence saying "Please enable HTML to view this email". Recipients still need the main facts, links, deadlines, contact info, and next actions even when HTML is completely ignored.

## 1. Why Support Plain-Text Clients?

There are many reasons HTML may not be displayed:

- The mail client or gateway extracts only `text/plain`.
- The recipient chooses plain-text view mode.
- Organizational security policies strip HTML or active content.
- The email device/app has limited rendering capabilities.
- Mail readers, archiving, search, or ticketing systems process only plain text.
- The user needs a screen reader or a simple interface without relying on HTML layout.
- HTML is blocked due to formatting errors, sanitizers, or mail client policies.

An HTML-only email may look good in some apps yet lose information in other environments. If the CTA is only an HTML button and the URL does not appear in text, plain-text recipients cannot access that action.

**Plain text is part of the product content**, not just a technical fallback. This content must be authored and tested alongside HTML.

## 2. How Does MIME multipart/alternative Work?

MIME allows an email to hold multiple content parts. With `multipart/alternative`, the parts are alternative presentations of **the same message**.

Conceptual structure example:

```text
MIME-Version: 1.0
Content-Type: multipart/alternative; boundary="alt-001"

--alt-001
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

Hello An,

Order ORD-2026-001 has been confirmed.
View order: https://shop.example.com/orders/ORD-2026-001

--alt-001
Content-Type: text/html; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

<html>
  <body>
    <h1>Hello An!</h1>
    <p>Order <strong>ORD-2026-001</strong> has been confirmed.</p>
    <a href="https://shop.example.com/orders/ORD-2026-001">
      View order
    </a>
  </body>
</html>

--alt-001--
```

This is an abbreviated illustrative example; actual boundaries and encodings are generated by the MIME library.

Key points to remember:

- Each part has its own `Content-Type`.
- `text/plain` holds plain text content.
- `text/html` holds HTML markup.
- Both parts express the same message and must not contradict each other.
- `multipart/alternative` tells the client that the parts are alternative choices.
- By MIME convention, the richer representation is normally placed later; thus plain text usually comes before HTML.

The mail client chooses the version suited to its capabilities and settings. The sending application cannot force every client to display HTML.

### 2.1. Difference Between alternative, mixed, and related

| MIME type | Purpose | Example |
|---|---|---|
| `multipart/alternative` | Multiple presentations of the same content | Plain text and HTML. |
| `multipart/mixed` | Combines main content with independent parts | Email with a PDF. |
| `multipart/related` | Attaches resources related to a content part | HTML referencing images via CID. |

An email can combine multiple multipart types. For example, an email with plain text, HTML, an inline image, and a PDF can have a nested structure:

```text
multipart/mixed
└── multipart/related
    ├── multipart/alternative
    │   ├── text/plain
    │   └── text/html (references cid:brand-logo)
    └── image/png (Content-ID: <brand-logo>)
└── application/pdf (attachment)
```

The exact structure depends on MIME creation and `MimeMessageHelper` mode. Do not concatenate boundaries manually as strings; let Jakarta Mail and Spring build the MIME parts.

## 3. Creating Both Plain Text and HTML with MimeMessageHelper

### 3.1. Dependencies and Basic Configuration

With Spring Boot, you can use the mail starter:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-mail'
}
```

Example SMTP configuration via `application.yml`:

```yaml
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SMTP_USERNAME}
    password: ${SMTP_PASSWORD}
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true
            required: true
          connectiontimeout: 5000
          timeout: 5000
          writetimeout: 5000
```

Credentials must be supplied from the environment or a secret store; never commit real passwords to the repository. Port and TLS mechanism must match your SMTP provider's instructions.

### 3.2. Using the setText(plainText, htmlText) Overload

This is the most important part:

```java
MimeMessage message = mailSender.createMimeMessage();

MimeMessageHelper helper =
    new MimeMessageHelper(message, true, "UTF-8");

helper.setFrom("orders@example.com");
helper.setTo("customer@example.net");
helper.setSubject("Order Confirmation ORD-2026-001");

String plainText = """
    Hello An,

    Your order ORD-2026-001 has been confirmed.

    Total: 450,000 VND
    Estimated delivery: 15/11/2026

    View order details:
    https://shop.example.com/orders/ORD-2026-001

    If you need support, please reply to this email.
    """;

String htmlText = """
    <!DOCTYPE html>
    <html lang="en">
      <body>
        <h1>Hello An!</h1>
        <p>Your order <strong>ORD-2026-001</strong>
           has been confirmed.</p>
        <p><strong>Total:</strong> 450,000 VND</p>
        <p><strong>Estimated delivery:</strong> 15/11/2026</p>
        <p>
          <a href="https://shop.example.com/orders/ORD-2026-001">
            View order details
          </a>
        </p>
        <p>If you need support, please reply to this email.</p>
      </body>
    </html>
    """;

// Create two alternative versions of the same content.
helper.setText(plainText, htmlText);

mailSender.send(message);
```

This overload lets Spring create plain and HTML content inside an appropriate multipart structure. The first parameter is the plain text version; the second parameter is HTML.

**Do not use `setText(htmlText, true)` if the goal is supporting plain-text-only clients.** That only declares HTML content; it does not automatically generate a complete plain text version.

### 3.3. Do Not Send Plain Text and HTML as Two Separate Emails

Do not send two separate SMTP messages, one text message and one HTML message. Doing so can cause recipients to receive two duplicate emails, cause notification duplication, and complicate tracking.

Send **one MimeMessage** with multiple alternative MIME parts. The mail client picks the appropriate part.

## 4. Plain Text Must Contain the Same Important Information

A good plain text version should preserve all business facts present in HTML:

- Greeting and context.
- Transaction/order code or required identifier.
- Status and key information.
- Amount, date/time, and time zone where applicable.
- Full action URL.
- Deadlines or applicable terms.
- Support channel and contact details.
- Unsubscribe details when required by marketing emails.

For example, HTML has a button:

```html
<a href="https://accounts.example.com/verify?token=abc123">
  Verify account
</a>
```

Plain text must show both the label and the URL:

```text
Verify account:
https://accounts.example.com/verify?token=abc123
```

If plain text only says "Click the blue button to verify", the user has no button to click. If it only says "Verify account" without a URL, the action may be impossible to complete.

For URLs containing tokens, do not log or share real values. In production emails, tokens must be created with proper permissions and expiration, use HTTPS, and have appropriate protection policies.

### 4.1. Avoid Conflicting Content

HTML could display a total of 450,000 VND while plain text displays 405,000 VND if the two versions are built from two different data sources. That is a serious content bug.

Generate both versions from **the same normalized view model**:

```text
Order data
    |
    v
Validated email view model
    |
    +--> Render plain text
    |
    +--> Render HTML
    |
    v
MimeMessageHelper.setText(plain, html)
```

Do not recompute prices, statuses, delivery dates, or links in two independent places. Shared values should be prepared once and passed to both templates.

## 5. Organizing Separate Renderers for Plain Text and HTML

For complex emails, separate content generation from sending. A renderer can return two strings:

```java
package com.example.mail;

public record RenderedEmail(
    String plainText,
    String htmlText
) {}
```

A renderer sharing business data:

```java
package com.example.mail;

import java.text.NumberFormat;
import java.time.ZoneId;
import java.time.format.DateTimeFormatter;
import java.util.Locale;

import org.springframework.stereotype.Component;

@Component
public class OrderEmailRenderer {

    public RenderedEmail render(OrderMailData data) {
        String customerName =
            data.customerName() == null
                || data.customerName().isBlank()
                ? "there"
                : data.customerName().strip();

        NumberFormat currency =
            NumberFormat.getCurrencyInstance(
                Locale.forLanguageTag("vi-VN")
            );

        String amount = currency.format(data.total());

        String deliveryDate = DateTimeFormatter
            .ofPattern("dd/MM/yyyy HH:mm", Locale.forLanguageTag("vi-VN"))
            .withZone(ZoneId.of("Asia/Ho_Chi_Minh"))
            .format(data.estimatedDelivery());

        String orderUrl =
            "https://shop.example.com/orders/" + data.orderId();

        String plain = """
            Hello %s,

            Your order %s has been confirmed.

            Total: %s
            Estimated delivery: %s

            View order details:
            %s

            If you need support, please reply to this email.
            """.formatted(
                customerName,
                data.orderId(),
                amount,
                deliveryDate,
                orderUrl
            );

        // Use a template engine to escape data in HTML.
        String html = renderHtml(
            customerName,
            data.orderId(),
            amount,
            deliveryDate,
            orderUrl
        );

        return new RenderedEmail(plain, html);
    }

    private String renderHtml(
            String customerName,
            String orderId,
            String amount,
            String deliveryDate,
            String orderUrl) {
        // Illustration: in a real application, use Thymeleaf/FreeMarker
        // to escape text data and HTML attributes.
        throw new UnsupportedOperationException(
            "Implement using a template engine"
        );
    }
}
```

`OrderMailData` is an application-defined business model. This example focuses on preparing shared data; HTML generation is delegated to a template engine rather than concatenating strings with user data.

### 5.1. Why Have a Separate Plain Template?

A plain text version is not always HTML with tags stripped. It may require different presentation:
- Use headings and dividers.
- Put URLs on separate lines.
- Represent tables as labeled lines.
- Replace images with descriptions.
- Trim decorative details.
- Arrange content for linear reading.

HTML table example:

```html
<table>
  <tr><th>Product</th><th>Quantity</th><th>Price</th></tr>
  <tr><td>Coffee</td><td>2</td><td>180,000 VND</td></tr>
  <tr><td>Tea</td><td>1</td><td>90,000 VND</td></tr>
</table>
```

Plain text can represent this as:

```text
Order details
-------------
- Coffee
  Quantity: 2
  Price: 180,000 VND

- Tea
  Quantity: 1
  Price: 90,000 VND

Total: 450,000 VND
```

If you merely strip HTML tags, the content can collapse into an unreadable string like "ProductQuantityPriceCoffee2180,000 VND". Design the text layout intentionally.

## 6. Using Thymeleaf for Both HTML and Plain Text

You can keep both templates in resources:

```text
src/main/resources/templates/mail/
├── order-confirmation.html
└── order-confirmation.txt
```

### 6.1. HTML Template

`order-confirmation.html`:

```html
<!DOCTYPE html>
<html lang="en" xmlns:th="http://www.thymeleaf.org">
<body>
  <h1>Hello, <span th:text="${customerName}">there</span>!</h1>

  <p>
    Order <strong th:text="${orderId}">ORD-001</strong>
    has been confirmed.
  </p>

  <p>
    <strong>Total:</strong>
    <span th:text="${totalText}">0 VND</span>
  </p>

  <p>
    <strong>Estimated delivery:</strong>
    <span th:text="${deliveryText}">15/11/2026</span>
  </p>

  <p>
    <a th:href="${orderUrl}">View order details</a>
  </p>
</body>
</html>
```

### 6.2. Plain-Text Template

`order-confirmation.txt`:

```text
[# th:mode="TEXT"]
Hello, [(${customerName})]!

Order [(${orderId})] has been confirmed.

Total: [(${totalText})]
Estimated delivery: [(${deliveryText})]

View order details:
[(${orderUrl})]
[/]
```

With Thymeleaf, text mode inline syntax must be declared properly. Use escaping matching your deployed Thymeleaf version/configuration; never enable unescaped mode for untrusted data. If the template engine or dialect is not configured for text mode, generate plain text using a Java renderer or a supported text template engine.

### 6.3. Rendering Both Templates with the Same Context

Example:

```java
Context context = new Context(Locale.forLanguageTag("vi"));
context.setVariable("customerName", customerName);
context.setVariable("orderId", orderId);
context.setVariable("totalText", totalText);
context.setVariable("deliveryText", deliveryText);
context.setVariable("orderUrl", orderUrl);

String html = templateEngine.process(
    "mail/order-confirmation.html", context
);

String plain = templateEngine.process(
    "mail/order-confirmation.txt", context
);

RenderedEmail rendered = new RenderedEmail(plain, html);
```

Template paths and resolver configuration must match your project. The main point is that **the same context** is used for both templates.

## 7. Sending HTML and Plain Text Emails with Spring Mail

A sending service can consume the rendered result:

```java
package com.example.mail;

import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Service;

@Service
public class OrderMailService {

    private final JavaMailSender mailSender;
    private final OrderEmailRenderer renderer;

    public OrderMailService(
            JavaMailSender mailSender,
            OrderEmailRenderer renderer) {
        this.mailSender = mailSender;
        this.renderer = renderer;
    }

    public void send(
            String recipient,
            OrderMailData data) throws MessagingException {

        RenderedEmail rendered = renderer.render(data);

        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper =
            new MimeMessageHelper(message, true, "UTF-8");

        helper.setFrom("orders@example.com");
        helper.setTo(recipient);
        helper.setSubject("Order Confirmation " + data.orderId());

        helper.setText(
            rendered.plainText(),
            rendered.htmlText()
        );

        mailSender.send(message);
    }
}
```

When a mail client reads only plain text, it uses the `text/plain` part. When a client supports HTML and selects that version, it uses the `text/html` part.

Do not use `SimpleMailMessage` for this example because MIME multipart/alternative is required. `SimpleMailMessage` suits simple plain-text emails, not messages carrying two representations inside the same MIME message.

## 8. Plain Text with Inline Images and Attachments

### 8.1. Inline Images Are Absent from Plain Text

HTML can use:

```html
<img src="cid:brand-logo" alt="Brand logo">
```

Plain text cannot display images via CID. Replace the image with a description or the organization name:

```text
[Brand logo]

Notification from Example Store
```

Do not put the string `cid:brand-logo` into plain text because that is an internal MIME reference, not a URL the user can open.

### 8.2. Combining setText and addInline

When there is HTML, plain text, and an inline image:

```java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper = new MimeMessageHelper(
    message,
    MimeMessageHelper.MULTIPART_MODE_RELATED,
    "UTF-8"
);

helper.setFrom("news@example.com");
helper.setTo(recipient);
helper.setSubject("Monthly Newsletter");

helper.setText(plainText, htmlText);

// Body content is set before inline resources.
helper.addInline(
    "brand-logo",
    new ClassPathResource("mail/logo.png"),
    "image/png"
);

mailSender.send(message);
```

In plain text, the main content must be readable without images. `addInline` only serves the HTML/MIME part with CIDs; it does not create an image for text-only clients.

### 8.3. Combining Independent Attachments

If the email also has a PDF:

```java
helper.setText(plainText, htmlText);

helper.addInline(
    "brand-logo",
    new ClassPathResource("mail/logo.png"),
    "image/png"
);

helper.addAttachment(
    "invoice.pdf",
    new ClassPathResource("mail/invoice.pdf"),
    "application/pdf"
);
```

Plain text should clearly state which file is attached and its purpose:

```text
The PDF invoice is attached to this email.
Filename: invoice.pdf
```

Users reading only plain text still know a document is attached, even though downloading the file depends on their client and policies.

## 9. Designing Plain Text for Different Email Types

### 9.1. Account Verification Email

Plain text needs:
- why the recipient received the email;
- the service name;
- full verification URL;
- link expiration time;
- what to do if the recipient did not request it.

Example:

```text
Hello An,

You recently requested to create an account at Example.

To verify your email address, open the following link:
https://accounts.example.com/verify?token=...

This link is valid for 30 minutes.

If you did not request an account, please ignore this email.
```

Do not only write "Click the button below" since the text version has no button.

### 9.2. Password Reset Email

Plain text needs:
- a clear statement that this is a password reset request;
- full HTTPS URL;
- expiration time;
- a warning not to share the link;
- what to do if someone else requested it.

Never put a new password or secret in the email. Tokens in links must have appropriate expiration and scope.

### 9.3. Invoice Email

Plain text should retain:
- invoice code;
- issue date;
- total amount and currency;
- payment status;
- link to view the invoice;
- PDF filename if attached.

Never leave financial details solely inside an image or HTML table.

### 9.4. Marketing Email

Plain text needs:
- brand/sender name;
- offer details and key conditions;
- clear destination URL;
- contact information;
- unsubscribe instructions when required.

Do not merely write an unrecognizable shortened link or omit offer terms in the text version. Email-level unsubscribe headers must also be configured per system requirements; plain-text copy does not replace unsubscribe headers or endpoints.

### 9.5. System Alert Email

Plain text should present:
- which system or service experienced the event;
- timestamp and time zone;
- severity/impact;
- event ID for lookup;
- dashboard/runbook link if the recipient is authorized to access it;
- next actions.

If HTML includes a chart, the text version should summarize key metrics rather than merely saying "see chart".

## 10. Should Plain Text Be Generated from HTML?

One approach is automatically stripping HTML tags to produce text. It can work for simple templates, yet **is not the best default solution** for business emails.

HTML example:

```html
<p>Order <strong>ORD-001</strong> is confirmed.</p>
<p><a href="https://shop.example.com/orders/ORD-001">View order</a></p>
```

If tags are simply stripped, the result might be:

```text
Order ORD-001 is confirmed.
View order
```

The URL is lost, so the reader cannot perform the action. A good converter must handle:
- links: preserve both label and URL;
- tables: preserve column and row order;
- headings: create spacing/titles;
- lists: use bullets/numbers;
- images: extract alt text or descriptions;
- hidden/conditional content: avoid leaking non-visible content into text;
- whitespace and paragraph boundaries.

For emails with critical information, **creating a separate plain template** is usually clearer and easier to control. HTML-to-text conversion can serve as a fallback or utility, but must be tested on real templates.

## 11. Verifying Consistency Between Plain Text and HTML

The two versions do not need identical layouts, but must be consistent in business events and facts.

| Information | Plain text | HTML |
|---|---|---|
| Order code | Present | Present |
| Status | Present | Present |
| Total amount | Present | Present |
| Delivery date | Present | Present |
| Action URL | Full URL present | Link to same target |
| Conditions/deadlines | Present | Present |
| Support/contact | Present | Present |
| Unsubscribe (if applicable) | Instructions present | Link/instructions present |

Shared data should be created once:
- order ID;
- formatted currency value;
- timezone-converted date/time;
- constructed and validated URL;
- normalized display name.

Then render both versions. Never calculate totals separately in two templates or build two URLs with two different pieces of logic.

## 12. Verifying the MIME Message in Tests

Do not only test that `send(...)` was called. Verify that the MIME message actually contains both parts.

With a mocked `JavaMailSender`, you can capture the message passed to `send`:

```java
ArgumentCaptor<MimeMessage> captor =
    ArgumentCaptor.forClass(MimeMessage.class);

verify(mailSender).send(captor.capture());

MimeMessage sent = captor.getValue();
sent.saveChanges();
```

Then traverse the MIME tree to find `text/plain` and `text/html`. With multipart structures nesting related/mixed, write a recursive function iterating each `Multipart` instead of assuming both parts are always direct children at the top level.

Illustrative pseudo-code:

```java
void collectTextParts(
        jakarta.mail.Part part,
        List<String> plainParts,
        List<String> htmlParts) throws Exception {

    if (part.isMimeType("text/plain")) {
        plainParts.add((String) part.getContent());
        return;
    }

    if (part.isMimeType("text/html")) {
        htmlParts.add((String) part.getContent());
        return;
    }

    Object content = part.getContent();
    if (content instanceof jakarta.mail.Multipart multipart) {
        for (int i = 0; i < multipart.getCount(); i++) {
            collectTextParts(
                multipart.getBodyPart(i),
                plainParts,
                htmlParts
            );
        }
    }
}
```

This is a test inspection helper, not production code. MIME parts may have different content wrappers or data types depending on the provider; tests should handle the cases the application produces.

### 12.1. Assertions to Include

- At least one `text/plain` part exists.
- A `text/html` part exists when the HTML template is enabled.
- Plain text is non-empty.
- Plain text contains the business code and required CTA/link.
- HTML and plain text share the same transaction code, amount, and status.
- URLs in plain text and HTML point to the same target.
- Plain text contains no unintended raw HTML markup.
- No unresolved template placeholders remain.
- Charset is appropriate, usually UTF-8.
- When attachments are present, both body representations still exist.
- When inline images are present, CID parts serve only HTML and do not replace plain content.

## 13. Example Testing the Renderer with JUnit

Suppose `OrderEmailRenderer` returns `RenderedEmail`. A test can verify both versions:

```java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;

class OrderEmailRendererTest {

    private final OrderEmailRenderer renderer =
        new OrderEmailRenderer(/* dependencies */);

    @Test
    void rendersEquivalentPlainAndHtmlContent() {
        OrderMailData data = sampleOrder();

        RenderedEmail result = renderer.render(data);

        assertThat(result.plainText())
            .contains(data.orderId())
            .contains("450.000")
            .contains("View order details")
            .contains("https://shop.example.com/orders/");

        assertThat(result.htmlText())
            .contains(data.orderId())
            .contains("450.000")
            .contains("View order details");
    }
}
```

`sampleOrder()` is a test-defined fixture. In a real project, inject the renderer and required dependencies rather than using an illustrative constructor if the renderer needs a template engine.

### 13.1. Testing That the URL Appears in Plain Text

```java
@Test
void plainTextContainsUsableActionUrl() {
    RenderedEmail result = renderer.render(sampleOrder());

    assertThat(result.plainText())
        .contains("https://shop.example.com/orders/ORD-2026-001");
}
```

This test ensures the CTA does not exist solely as an anchor tag in HTML.

### 13.2. Testing That Plain Text Does Not Depend on Images

```java
@Test
void plainTextDoesNotRequireInlineCid() {
    RenderedEmail result = renderer.render(sampleOrder());

    assertThat(result.plainText())
        .doesNotContain("cid:");
    assertThat(result.plainText())
        .contains("Example Store");
}
```

If the HTML template has a logo, the text version should include the brand name or an appropriate description, not an internal CID.

## 14. Encoding and Special Characters in Plain Text

Plain text still needs proper encoding. Use `UTF-8` for `MimeMessageHelper` and ensure content is built from valid Java `String`s.

Example content:

```text
Hello Nguyễn Thị Ánh,

Your order has been confirmed.
Total: 1.250.000 ₫
Address: Đắk Lắk
```

When reading MIME source, verify:
- `Content-Type: text/plain; charset=UTF-8` or appropriate charset;
- `Content-Transfer-Encoding` such as quoted-printable or base64;
- content after decoding preserves Vietnamese diacritics and currency symbols.

Do not manually Base64-encode strings before putting them into the text body. The MIME library handles content-transfer-encoding. Manual encoding usually causes recipients to see encoded text instead of readable content.

### 14.1. Line Endings and Line Wrapping

Plain text relies on newlines to separate paragraphs. Java text blocks use source line breaks; Jakarta Mail normalizes them per protocol rules when building MIME. There is no need to manually insert MIME boundaries or craft headers.

Verify:
- blank lines exist between paragraphs;
- URLs are not wrapped at positions that break the link;
- lists use bullets/numbers;
- empty data does not produce hundreds of blank lines;
- line lengths fit older text-only clients if your audience uses them.

## 15. Accessibility and Linear Reading Experience

Plain text supports users reading emails sequentially. Even for HTML clients, plain content remains valuable for text-processing systems.

Principles:
- Write a specific email subject.
- Put important information near the top.
- Use labels before values, e.g., `Order code: ORD-001`.
- Never convey status solely through color or icons.
- Use contextual URLs rather than merely writing "click here".
- For informative images, express that information in text.
- For tables, convert into labeled line groups.
- Use clear language, short sentences, and purposeful paragraphs.

For example, instead of:

```text
🟢
450,000
15/11
```

write:

```text
Status: Confirmed
Total: 450,000 VND
Estimated delivery: 15/11/2026
```

Colors or emojis can be decorative, but should never be the sole means of conveying meaning.

## 16. Common Mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Text-only client gets empty email | Sent only `text/html` | Use `setText(plainText, htmlText)`. |
| Plain text only says "Enable HTML to view" | No separate text content designed | Write a plain version with full info and CTAs. |
| Link cannot be opened | HTML has anchor, plain has only label | Put full URL into plain text. |

| Vietnamese text is garbled | Inconsistent charset or manual encoding | Use UTF-8 and let the MIME library encode. |
| Table collapses into unreadable text | Simple HTML tag stripping | Create a dedicated structured plain template. |
| Image missing in plain | Expecting CID to render in text | Replace with description/alt text or brand name. |
| Attachment not mentioned | Plain template ignores attached file | Add filename and document purpose. |
| Email received twice | Sent two separate messages for HTML and text | Use one multipart/alternative message. |
| Test only verifies send was called | MIME body not inspected | Traverse MIME tree and assert both parts. |

| Plain text exposes markup | HTML string mistakenly used as text version | Render a dedicated text template or convert properly. |

## 18. Summary

To handle plain-text-only clients, send **one MIME message containing both `text/plain` and `text/html`**. In Spring Framework Mail, use `MimeMessageHelper.setText(plainText, htmlText)` with the helper in multipart mode. Plain text must contain complete business facts, CTAs, and usable URLs, while staying consistent with HTML.

Build both versions from the same view model or normalized data; do not merely strip HTML tags mechanically to produce text. When inline images exist, replace images with descriptions in the text version; when attachments exist, clearly state the filename and purpose. Finally, inspect the MIME tree to confirm both representations exist, then test on a text-only client or test inbox. **A good email still conveys the full message even when the HTML part is not displayed.**
