# Designing multipart/alternative for Plain Text and HTML

## 1. Why Should an Email Include Both Plain Text and HTML?

In **Spring Framework Mail**, a message can provide multiple representations of the same content. For example, an order confirmation email can be written as plain text so it is easy to read in any environment, while also having an HTML version with a heading, an information table, and an action button.

Instead of sending two separate emails, the application can place both versions into the same MIME **multipart/alternative** structure. The email client receives the message and chooses the representation that suits its capabilities and display preferences.

An email with two versions typically has the following meaning:

- **text/plain**: text content without HTML markup, easy to read, search, copy, and use in constrained environments.
- **text/html**: content with layout structure, links, tables, images, or typography.
- **multipart/alternative**: declares that the parts above are alternative representations of the same content.

For example, a confirmation message:

~~~text
Plain text:
Order ORD-2026-015 has been confirmed.
View details: https://example.com/orders/ORD-2026-015

HTML:
<h1>Order Confirmed</h1>
<p>Order code: ORD-2026-015</p>
<a href="https://example.com/orders/ORD-2026-015">View order</a>
~~~

Users reading in text mode still have complete information and the URL. Users reading HTML can see headings, layout, and the CTA. Both versions express **one notification**, not two different messages.

**The goal of multipart/alternative is to provide equivalent representation choices for the same content**, not to create two versions with conflicting data or actions.

## 2. What Does multipart/alternative Mean in MIME?

MIME allows an email to have multiple content parts. The **alternative** subtype is used when the parts are interchangeable representations of one another. For example:

~~~text
MimeMessage
└── multipart/alternative
    ├── text/plain
    └── text/html
~~~

A MIME part typically has headers such as:

~~~text
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

Order ORD-2026-015 has been confirmed.
View details: https://example.com/orders/ORD-2026-015
~~~

The HTML part may have:

~~~text
Content-Type: text/html; charset=UTF-8
Content-Transfer-Encoding: quoted-printable

<html lang="en">
  <body>
    <h1>Order Confirmed</h1>
    <p>Order code: ORD-2026-015</p>
    <a href="https://example.com/orders/ORD-2026-015">View order</a>
  </body>
</html>
~~~

The example above illustrates the meaning of the MIME parts; during actual sending, Jakarta Mail generates the necessary boundaries, headers, and transfer encoding. Applications should use the Spring Mail API instead of concatenating raw MIME manually.

### Part Order Matters

By MIME convention, parts in multipart/alternative are ordered from the least preferred representation to the most preferred representation. Therefore, the standard ordering is:

1. **text/plain** first.
2. **text/html** second.

The email client can choose the part that best fits its capabilities and preferences. Placing HTML after plain text indicates that HTML is the richer representation when the client supports it.

You should not reverse the order arbitrarily or add two different HTML parts expecting the client to treat them as sequential content steps. If the parts are independent pieces of content, a different MIME structure must be chosen.

## 3. multipart/alternative vs. multipart/mixed and multipart/related

These three subtypes solve three different needs:

| MIME subtype | Meaning | Example |
|---|---|---|
| **multipart/alternative** | Multiple alternative representations of the same content | Plain text and HTML |
| **multipart/mixed** | Multiple independent components sent together in one email | Email body and an attached PDF file |
| **multipart/related** | Related parts combined to form a single piece of content | HTML and inline images referenced via CID |

For example:

~~~text
Email with only two content versions:
multipart/alternative
  ├── text/plain
  └── text/html

Email with content and a PDF file:
multipart/mixed
  ├── multipart/alternative
  │   ├── text/plain
  │   └── text/html
  └── application/pdf (attachment)

Email with HTML referencing an inline image:
multipart/related
  ├── text/html
  └── image/png (Content-ID)
~~~

When an email has plain text, HTML, an inline image, and an attachment, the parts can be nested:

~~~text
MimeMessage
└── multipart/mixed
    ├── multipart/related
    │   ├── multipart/alternative
    │   │   ├── text/plain
    │   │   └── text/html
    │   └── image/png (Content-ID)
    └── application/pdf (attachment)
~~~

This is a logical relationship diagram. The exact MIME tree generated by MimeMessageHelper and Jakarta Mail may differ depending on the multipart mode. What matters is that **alternative is for alternative versions**, **mixed is for independent parts**, and **related is for resources referenced by the content part**.

Do not place a PDF file as an alternative version of HTML. A PDF is a separate attachment, not an alternative representation of the body.

## 4. When Should Both Versions Be Provided?

For business emails, having both plain text and HTML is often useful because:

- Some clients or users prefer text mode.
- The content remains readable when CSS, images, or parts of HTML do not render.
- Plain text is often easier to copy and search.
- Screen readers and constrained display environments can consume text content more conveniently.
- Some gateways, archiving tools, or email-processing systems may need a simple text part.
- Recipients still understand the notification when an email client strips markup or does not support certain HTML elements.

### Examples of Content That Should Have Both Versions

| Email type | Required plain text | What HTML can add |
|---|---|---|
| Order confirmation | Order code, status, URL to view order | Heading, summary table, CTA |
| Password reset | Reason for sending, reset link, expiration time | Instructional layout and button |
| Invoice | Invoice code, amount, how to view/download | Detail table and links |
| Report | Key takeaways, important metrics | Charts, tables, and heading hierarchy |
| Schedule notification | Time, location, instructions | Calendar layout and add-to-app button |

For an email with only a simple single line of text, creating HTML is not strictly necessary. **SimpleMailMessage** is usually sufficient. When two representations, HTML, or complex MIME are needed, use **JavaMailSender** and **MimeMessage**.

## 5. Plain Text and HTML Must Be Equivalent in Meaning

The two versions do not need to have the same visual layout or character count, but they must provide **the same business information and the same primary actions**.

For example, HTML has:

- Order code.
- Order status.
- Estimated delivery date.
- View order button.

Plain text must also contain that information, along with the actual URL so the recipient can open it.

### Poor Example

~~~text
Your order has been confirmed.
Please enable HTML to view details.
~~~

If the user chooses plain text, they do not have the order code, status, delivery date, or the necessary link.

### Better Example

~~~text
Order Confirmed

Order code: ORD-2026-015
Status: Confirmed
Estimated delivery date: 20/11/2026

View details:
https://example.com/orders/ORD-2026-015

Need support:
https://example.com/support
~~~

HTML can present that data using tables, headings, and buttons. Plain text remains complete enough for the recipient to understand and take action.

### Do Not Let the Two Versions Contradict Each Other

Common mistakes:

- Plain text states delivery date 20/11 while HTML states 21/11.
- The HTML button points to one order while the plain text URL points to another order.
- HTML says payment is completed while plain text says pending.
- HTML displays the amount formatted in one currency while plain text uses another currency.
- One version contains an important deadline or warning that the other version omits.

Both versions should be generated from **the same validated data model**, rather than writing two independent data-fetching flows.

## 6. Creating multipart/alternative with MimeMessageHelper

In Spring Framework Mail, the common approach is to use **JavaMailSender** to create a MimeMessage, and then use the **MimeMessageHelper.setText(plainText, htmlText)** overload:

~~~java
helper.setText(plainText, htmlText);
~~~

This overload tells Spring that the application provides two content representations. The helper creates the appropriate alternative structure in the MimeMessage.

Example:

~~~java
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import java.nio.charset.StandardCharsets;

import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

public class NotificationMailService {

    private final JavaMailSender mailSender;

    public NotificationMailService(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendOrderAccepted(String recipient)
            throws MessagingException {
        String plainText = """
                Order Confirmed

                Order code: ORD-2026-015
                Status: Confirmed

                View details:
                https://example.com/orders/ORD-2026-015
                """;

        String htmlText = """
                <!doctype html>
                <html lang="en">
                  <head>
                    <meta charset="UTF-8">
                  </head>
                  <body>
                    <h1>Order Confirmed</h1>
                    <p><strong>Order code:</strong> ORD-2026-015</p>
                    <p><strong>Status:</strong> Confirmed</p>
                    <p>
                      <a href="https://example.com/orders/ORD-2026-015">
                        View order details
                      </a>
                    </p>
                  </body>
                </html>
                """;

        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(
                message,
                true,
                StandardCharsets.UTF_8.name()
        );

        helper.setFrom("orders@example.com");
        helper.setTo(recipient);
        helper.setSubject("Order Confirmed");
        helper.setText(plainText, htmlText);

        mailSender.send(message);
    }
}
~~~

The example assumes the application already has a validly configured **JavaMailSender**, the SMTP server permits the From address, and the illustrative URL is replaced with the application's real domain.

### Explanation

1. **createMimeMessage()** creates a new MIME message.
2. **MimeMessageHelper(..., true, UTF-8)** enables multipart mode and sets the encoding.
3. **setFrom**, **setTo**, and **setSubject** set the basic headers.
4. **setText(plainText, htmlText)** sets the two alternative representations.
5. **send(message)** hands the message over to the mail transport.

In the example, plain text is placed first in the call and HTML is in the second parameter. Do not swap the two parameters because the method signature defines the order as **plainText, htmlText**.

## 7. Difference Between setText(plainText, htmlText) and setText(htmlText, true)

This is an important point when designing multiple formats.

### Providing Both Plain Text and HTML

~~~java
helper.setText(plainText, htmlText);
~~~

This method creates two representations:

- A **text/plain** part.
- A **text/html** part.

This is the appropriate choice when the application wants to use **multipart/alternative**.

### Providing Only HTML

~~~java
helper.setText(htmlText, true);
~~~

The boolean parameter indicates that the content is HTML. This sets a single HTML body; it **does not automatically generate an equivalent plain text version**.

| API | Result | Use case |
|---|---|---|
| **setText(text)** | text/plain body | Text-only email |
| **setText(html, true)** | HTML body | Email providing only HTML |
| **setText(plain, html)** | Two alternative representations | Email wanting to support both text and HTML |

If you call multiple setters sequentially on the same helper, a later call may replace or alter the previously set content. You should not call **setText(html, true)** and then **setText(plain, html)** expecting the two calls to append body parts automatically. Choose the overload that matches your goal from the start.

## 8. Configuring Charset and Encoding

Emails with Vietnamese content must be handled with the right charset. For example:

~~~java
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        true,
        StandardCharsets.UTF_8.name()
);
~~~

UTF-8 allows representing characters such as **ă, â, ê, ô, ơ, ư, đ** and tone marks. If the charset is not configured properly, recipients may see garbled characters or question marks.

### Charset and Content-Transfer-Encoding Are Two Different Concepts

- **charset** specifies how bytes are decoded into characters, for example UTF-8.
- **Content-Transfer-Encoding** describes how data is encoded for transport over MIME, for example quoted-printable or base64.

Example of a part:

~~~text
Content-Type: text/plain; charset=UTF-8
Content-Transfer-Encoding: quoted-printable
~~~

Jakarta Mail selects an appropriate transfer encoding while building the message. Applications should use the Spring Mail API to set the encoding rather than manually encoding the body into base64 or quoted-printable before passing it to setText.

### Subject and Sender Name

A Subject with Vietnamese diacritics also needs proper MIME handling. When using **MimeMessageHelper** with UTF-8 encoding, the helper/Jakarta Mail can encode headers using the appropriate mechanism. Do not manually concatenate base64 strings into the subject.

## 9. Organizing Shared Data for Both Versions

A common design mistake is writing two independent templates and querying the database separately for each template. This can cause the two content versions to differ if the data changes between the two queries.

You should build a unified notification model:

~~~text
Order / Business event
          |
          v
Notification data
  - customerName
  - orderCode
  - orderStatus
  - deliveryDate
  - orderUrl
          |
          +-------------------+
          |                   |
          v                   v
   Plain text renderer    HTML renderer
          |                   |
          v                   v
      plainText             htmlText
          |                   |
          +---------+---------+
                    |
                    v
       MimeMessageHelper.setText(...)
                    |
                    v
          JavaMailSender.send(...)
~~~

Example data record:

~~~java
import java.time.LocalDate;

public record OrderEmailData(
        String customerName,
        String orderCode,
        String orderStatus,
        LocalDate deliveryDate,
        String orderUrl
) {
}
~~~

From the same **OrderEmailData** object, two renderers produce content with different presentations while using the same order code, status, delivery date, and URL.

### Why Not Fetch Data Twice?

Suppose the order status changes from **Processing** to **Confirmed** between two queries. If plain text is rendered first and HTML is rendered later, the recipient may receive an email whose two versions contradict each other. Snapshotting the data before rendering helps avoid that situation.

If email sending is deferred in a queue, store the necessary data or snapshot identifier so both versions are rendered from the exact same business state. Do not hold onto a mutable object that could be modified by another thread while a callback or template is running.

## 10. Rendering HTML and Plain Text with a Template Engine

For simple emails, text blocks as in the earlier example can be used. For systems with many email types, a template engine such as **Thymeleaf** or **FreeMarker** helps manage content separately for each format.

Typical flow:

~~~text
Notification model
        |
        +--> templates/order-accepted.txt
        |          |
        |          v
        |       plainText
        |
        +--> templates/order-accepted.html
                   |
                   v
                htmlText
        |
        v
MimeMessageHelper.setText(plainText, htmlText)
~~~

One renderer can be used per type:

~~~java
String plainText = plainTextRenderer.render("order-accepted", data);
String htmlText = htmlRenderer.render("order-accepted", data);

helper.setText(plainText, htmlText);
~~~

**plainTextRenderer** and **htmlRenderer** are components built by the application; they are not default Spring Mail APIs.

### Plain Text Template

~~~text
Hello, ${customerName}!

Order ${orderCode} has been confirmed.
Status: ${orderStatus}
Estimated delivery date: ${deliveryDate}

View details:
${orderUrl}
~~~

### HTML Template

~~~html
<h1>Order Confirmed</h1>
<p>Hello, <strong>${customerName}</strong>!</p>
<p>Order code: ${orderCode}</p>
<p>Status: ${orderStatus}</p>
<p>Estimated delivery date: ${deliveryDate}</p>
<p><a href="${orderUrl}">View order details</a></p>
~~~

The **${...}** placeholders in the example are illustrative syntax and do not imply that any specific template engine understands them with this exact syntax. You need to configure the corresponding template engine and model.

### Context-Aware Data Escaping

User names and strings from business data may contain special characters. In HTML, text and href attributes must be escaped according to their context. URLs need domain/scheme validation, path/query encoding, and then HTML-escaping when placed inside attributes.

Do not concatenate untrusted data directly into HTML. Template engines usually support escaping, but the right mode must be used; do not enable raw HTML insertion mode for user content unless it has been sanitized.

Plain text does not need HTML escaping, though unwanted control characters should still be stripped or handled and URLs should be formatted sensibly.

## 11. Designing a Readable Plain Text Version

Plain text should not be an HTML string with tags mechanically stripped out. It should be authored to read naturally:

- Use a short heading at the top of the message.
- Separate paragraphs with blank lines.
- Use labels for values such as order code, status, and time.
- Include the actual URL for the primary action.
- Use bullet points for lists.
- Do not cram all data onto a single long line.
- If there is an HTML table, convert it into an appropriate label–value format or list.

Example:

~~~text
OCTOBER REPORT

Revenue: 125,000,000 VND
Number of orders: 340
Growth vs. previous month: 8%

Key points:
- Group A grew well.
- Group B needs a return-rate review.

Open full report:
https://example.com/reports/2026-10
~~~

HTML can use tables and charts, while plain text still preserves the takeaways and the link.

## 12. HTML Should Have Clear Structure and Fallbacks

The HTML version can use headings, paragraphs, tables, and links:

~~~html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width,initial-scale=1">
  </head>
  <body>
    <h1>October Report</h1>
    <p>Revenue: <strong>125,000,000 VND</strong></p>
    <p>Number of orders: <strong>340</strong></p>
    <p>Growth: <strong>8%</strong></p>
    <h2>Key points</h2>
    <ul>
      <li>Group A grew well.</li>
      <li>Group B needs a return-rate review.</li>
    </ul>
    <p>
      <a href="https://example.com/reports/2026-10">
        Open full report
      </a>
    </p>
  </body>
</html>
~~~

Important information should not appear only in images or colors. If images are blocked, HTML still needs to convey the core message; plain text also needs the takeaways and URL.

For emails viewed on mobile phones, use a flexible single-column layout, sufficiently large text, clearly labeled links, and CTAs with an adequate touch target. Do not rely on JavaScript, forms, or modern CSS that email clients may strip out.

## 13. Example with an HTML CTA Button and a Plain Text URL

An HTML button should be an **a** tag with a real href, styled like a button:

~~~html
<a
  href="https://example.com/orders/ORD-2026-015"
  style="
    display:inline-block;
    padding:14px 24px;
    background-color:#174ea6;
    color:#ffffff;
    font:700 16px/22px Arial,sans-serif;
    text-decoration:none;">
  View order
</a>
~~~

Plain text must include the corresponding URL:

~~~text
View order details:
https://example.com/orders/ORD-2026-015
~~~

Do not just write:

~~~text
Click the button below to view your order.
~~~

because in plain text there is no button for the reader to click.

For sensitive links such as password reset or transaction confirmation, URLs must use HTTPS, a controlled domain, and tokens with appropriate scope and expiration. Do not log tokens and do not use GET to immediately execute an irreversible action just because an email scanner may visit the URL automatically.

## 14. Combining multipart/alternative with Attachments

If an email has plain text, HTML, and a PDF attachment, the MIME structure typically uses **multipart/mixed** on the outer layer, with the body part as **multipart/alternative**:

~~~text
MimeMessage
└── multipart/mixed
    ├── multipart/alternative
    │   ├── text/plain
    │   └── text/html
    └── application/pdf
        └── Content-Disposition: attachment
~~~

Example:

~~~java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        true,
        StandardCharsets.UTF_8.name()
);

helper.setFrom("billing@example.com");
helper.setTo(recipient);
helper.setSubject("Your invoice");
helper.setText(
        "Your invoice is attached to this email.",
        "<html lang=\"en\"><body>"
                + "<h1>Your invoice</h1>"
                + "<p>The PDF invoice is attached.</p>"
                + "</body></html>"
);
helper.addAttachment(
        "invoice.pdf",
        new ClassPathResource("mail/invoice.pdf"),
        "application/pdf"
);

mailSender.send(message);
~~~

The example assumes **recipient**, **mailSender**, and the PDF resource have been validly prepared. **setText(plain, html)** creates the two content representations; **addAttachment** adds an independent part.

### Why Does the Attachment Not Go Inside alternative?

If a PDF is placed as an alternative to HTML, a client may interpret the PDF as another representation of the body and pick one replacement part, rather than treating it as a file accompanying the message. **Attachments have an independent purpose**, so they normally reside in multipart/mixed.

## 15. Combining multipart/alternative with Inline Resources

When HTML references an image via CID, the HTML part and the image need a **multipart/related** relationship. If plain text is also present, one logical structure can be:

~~~text
MimeMessage
└── multipart/related
    ├── multipart/alternative
    │   ├── text/plain
    │   └── text/html
    │       └── <img src="cid:brandLogo">
    └── image/png
        └── Content-ID: <brandLogo>
~~~

When an attachment is also present, there may be an enclosing multipart/mixed. The exact tree depends on MimeMessageHelper's multipart mode and how Jakarta Mail organizes the body.

Example:

~~~java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        MimeMessageHelper.MULTIPART_MODE_MIXED_RELATED,
        StandardCharsets.UTF_8.name()
);

helper.setFrom("news@example.com");
helper.setTo(recipient);
helper.setSubject("Latest newsletter");
helper.setText(
        "The new newsletter is ready. View it at https://example.com/news",
        """
        <html lang="en">
          <body>
            <img src="cid:brandLogo" alt="Brand logo">
            <h1>Latest newsletter</h1>
            <p>This month's newsletter is ready.</p>
            <a href="https://example.com/news">Read newsletter</a>
          </body>
        </html>
        """
);
helper.addInline(
        "brandLogo",
        new ClassPathResource("mail/brand-logo.png"),
        "image/png"
);

mailSender.send(message);
~~~

The order to use is **setText before addInline**. The plain text version must keep the content and link; the logo image is only a supporting element for HTML.

## 16. Multipart Modes in MimeMessageHelper

MimeMessageHelper provides the following multipart modes:

| Mode | General purpose | Use case |
|---|---|---|
| **MULTIPART_MODE_NO** | Do not use multipart | Simple content, no extra MIME parts needed |
| **MULTIPART_MODE_MIXED** | multipart/mixed | Body with attachments |
| **MULTIPART_MODE_RELATED** | multipart/related | HTML with inline resources |
| **MULTIPART_MODE_MIXED_RELATED** | Combines mixed and related | Email with inline resources and attachments |

With **setText(plainText, htmlText)**, the helper creates alternative content. When attachments or inline resources need to be added, enable multipart and choose the appropriate mode so parts are nested for the right purpose.

Common constructor example:

~~~java
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        true,
        StandardCharsets.UTF_8.name()
);
~~~

The **true** parameter enables multipart. When there are multiple part types, choosing an explicit mode makes the code's intent clearer:

~~~java
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        MimeMessageHelper.MULTIPART_MODE_MIXED_RELATED,
        StandardCharsets.UTF_8.name()
);
~~~

You should not assume that a multipart constructor always generates the exact same MIME tree in every situation. The final structure depends on which setText, addInline, addAttachment calls the application makes and which multipart mode is chosen.

## 17. Spring Boot Configuration for JavaMailSender

In a Spring Boot application, the commonly used dependency is:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-mail'
}
~~~

Example SMTP submission configuration over STARTTLS:

~~~yaml
spring:
  mail:
    host: smtp.example.com
    port: 587
    username: ${SMTP_USERNAME}
    password: ${SMTP_PASSWORD}
    default-encoding: UTF-8
    properties:
      mail:
        smtp:
          auth: true
          starttls:
            enable: true
            required: true
          connectiontimeout: 5000
          timeout: 5000
          writetimeout: 5000
~~~

**smtp.example.com** is only an illustrative host. In real environments, replace it with your organization's SMTP server and load username/password from environment variables or a secret manager. Do not commit real credentials to the repository.

Spring Boot can auto-configure the **JavaMailSender** bean when the dependency and configuration are appropriate. Services only need to inject the interface; creating plain text and HTML content remains the application's responsibility.

If the application defines multiple JavaMailSender beans, you must select explicitly using **@Qualifier** or a router. Auto-configuration does not decide on its own which email should go through which sender.

## 18. Generating Dynamic Content from a Model

Example service receiving a model:

~~~java
public record OrderEmailData(
        String customerName,
        String orderCode,
        String status,
        String orderUrl
) {
}
~~~

A renderer can generate both versions:

~~~java
public record RenderedMail(String plainText, String htmlText) {
}

public RenderedMail render(OrderEmailData data) {
    String plainText = """
            Hello %s,

            Order %s has status: %s.
            View details: %s
            """.formatted(
            data.customerName(),
            data.orderCode(),
            data.status(),
            data.orderUrl()
    );

    String htmlText = """
            <html lang="en">
              <body>
                <h1>Order Information</h1>
                <p>Hello %s!</p>
                <p>Order code: %s</p>
                <p>Status: %s</p>
                <p><a href="%s">View order details</a></p>
              </body>
            </html>
            """.formatted(
            escapeHtml(data.customerName()),
            escapeHtml(data.orderCode()),
            escapeHtml(data.status()),
            escapeHtmlAttribute(data.orderUrl())
    );

    return new RenderedMail(plainText, htmlText);
}
~~~

In the example, **escapeHtml** and **escapeHtmlAttribute** are illustrative helper functions that must be implemented using an appropriate library or replaced with a template engine that provides context-aware escaping. Do not use the same escape function everywhere if the HTML contexts differ. URLs must also have their scheme/domain validated before being placed into href.

After rendering:

~~~java
RenderedMail rendered = renderer.render(data);
helper.setText(rendered.plainText(), rendered.htmlText());
~~~

Separating rendering from sending makes it easier to verify each version and ensures both originate from a single data snapshot.

## 19. Verifying Equivalence Between the Two Versions

There is no simple string comparison that proves plain text and HTML are equivalent in meaning. However, the application can verify that required fields from the model appear in both versions.

Examples of required fields:

| Data | Plain text | HTML |
|---|---|---|
| Order code | Present | Present |
| Status | Present | Present |
| Delivery date | Present | Present |
| Action URL | Full URL | href with exact URL |
| Support info | Present if needed | Present if needed |

### Example Check at the Renderer Layer

~~~java
RenderedMail rendered = renderer.render(data);

if (!rendered.plainText().contains(data.orderCode())) {
    throw new IllegalStateException("Plain text is missing order code");
}

if (!rendered.htmlText().contains(escapeHtml(data.orderCode()))) {
    throw new IllegalStateException("HTML is missing order code");
}
~~~

This is a simple verification example. With templated HTML, data may be escaped or placed inside attributes, so checks should inspect the DOM or validate the template/rendered output appropriately. Do not rely on a simple contains check as comprehensive proof of safety or correctness.

In addition, check that the URL in the text version and the href in HTML point to the same business target. If a link contains a token, do not put the real token into test logs or reports.

## 20. Inspecting MIME Structure After Creating the Message

During development, you can build a MimeMessage without sending it over SMTP, then inspect Content-Type or body parts to confirm alternative is present. Example with Jakarta Mail:

~~~java
MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper = new MimeMessageHelper(
        message,
        true,
        StandardCharsets.UTF_8.name()
);
helper.setText(plainText, htmlText);

message.saveChanges();
String contentType = message.getContentType();
~~~

When deeper inspection is needed, read **Multipart** and traverse each BodyPart to verify:

- There is a **text/plain** part.
- There is a **text/html** part.
- The plain text part comes before the HTML part inside alternative.
- The charset is appropriate.
- If there is an attachment, that part is placed in an appropriate mixed structure.
- If there is an inline image, Content-ID matches the cid reference.

You should not check only the root Content-Type string and conclude the entire MIME tree is correct; for nested messages, you need to traverse the parts.

### Using an SMTP Test Server

Unit tests can verify the renderer and MIME message without sending real mail. Integration tests can use a test SMTP server or sandbox to inspect the raw message. Avoid sending test content to production customers.

## 21. Email Client Behavior When Receiving multipart/alternative

Email clients usually pick one part suited to their reading mode and support capabilities. Some users may choose to view plain text, while most modern clients can render HTML.

Scenarios:

- Client renders HTML: the recipient sees layout, links, tables, and typography.
- Client or setting prefers text: the recipient reads the text/plain part.
- HTML is partially filtered: the text content or remaining HTML still needs to carry enough meaning.
- Images are blocked: text content and alt text help the reader understand the message.
- Archiving or parsing gateway: can extract the simple text part.

**multipart/alternative does not require clients to display both versions simultaneously.** It allows selecting one representation. If you want users to see both a text version and an HTML version in the same display area, that is a different content design and not the standard purpose of alternative.

## 22. Common Mistakes When Building multipart/alternative

| Symptom | Common cause | Fix |
|---|---|---|
| Only HTML visible, no plain text | Using **setText(html, true)** | Use **setText(plainText, htmlText)** |
| Plain text shows raw HTML tags | Passing an HTML string to setText(text) | Generate separate text content, do not use HTML as plain text |
| Two versions have different info | Rendered from different data sources or queries | Create a shared snapshot/model |
| Link only appears in HTML | Plain text lacks the full URL | Include the URL in the text version |
| Vietnamese characters are garbled | Charset not set consistently | Use UTF-8 in MimeMessageHelper |
| Attachment replaces body | Placing attachment inside alternative | Use multipart/mixed wrapping alternative |
| CID image does not appear | Missing related part or wrong Content-ID | Check multipart/related and addInline |
| Body part gets overwritten | Calling multiple setText setters improperly | Pick one overload and set it once |
| Email is too large | Embedding too many images or attachments | Optimize images, use secure download links where appropriate |
| HTML is hard to read on mobile | Fixed layout, small fonts, multiple columns | Design single-column, inline CSS, and test on clients |
| SMTP send fails | Wrong host, credentials, TLS, or recipient | Investigate MailException and SMTP responses |
| send() succeeds but email misses Inbox | SMTP acceptance does not guarantee final delivery | Check provider bounces, logs, and events |

## 23. Security Considerations with Two Content Versions

Having both plain text and HTML improves accessibility, but also creates additional places where sensitive data can appear. You need to control:

- **Same recipient, same permissions:** both versions must contain only data the recipient is authorized to view.
- **URLs and tokens:** validate domain, scheme, permissions, and expiration; do not log tokens.
- **HTML escaping:** avoid inserting untrusted user content directly into markup.
- **Headers:** do not let Subject, From, Reply-To, or recipient come from unvalidated input.
- **Images and attachments:** do not embed another user's private data or unauthorized resources.
- **Logs and archives:** raw MIME can contain the full contents of both versions, links, and attachments.
- **Consistent content:** avoid having HTML expose extra sensitive data that plain text omits, or vice versa.

### Do Not Turn URLs into Automatic Actions

Email scanners may automatically open URLs for safety checks. For sensitive operations such as changing a password, deleting an account, or confirming a transaction, do not complete the action merely because a GET request was made. Use a landing page with an explicit confirmation step or appropriate authentication.

## 24. Performance and Size

Having both text/plain and text/html parts makes the message larger than having a single part, though for typical transactional emails, this increase is usually much smaller than images and attachments.

Factors that bloat email size:

- HTML containing excessive markup or repeated inline CSS.
- Base64-encoded inline images.
- Multiple attachments.
- Long tracking URLs.
- Overly repetitive template content.

Keep HTML concise, use only necessary CSS, and do not embed large images without reason. If a chart is large, you can provide a link to a protected dashboard instead of sending the full image data.

### Do Not Sacrifice Plain Text to Save a Few Bytes

Plain text is usually small and valuable whenever HTML is not rendered. Dropping the text part just to save a tiny amount of space can make the email much less usable in many environments. If a message is too large, examine images and attachments first and apply reasonable size limits.

## 25. Separating Content Preparation Errors from SMTP Sending Errors

When using **JavaMailSender.send(message)**, errors can occur at different layers:

| Layer | Example errors | How to investigate |
|---|---|---|
| Text rendering | Missing data, template error | Check model and renderer |
| HTML rendering | Template error, wrong escaping | Check HTML output and template engine |
| MIME building | MessagingException, invalid charset or part | Check MimeMessageHelper and body parts |
| SMTP authentication | Wrong username/password or permissions | Check credentials and provider |
| SMTP transport | Timeout, TLS, relay rejected | Check host, port, network, and SMTP response |
| Post-SMTP delivery | Bounce, spam, quarantine | Check provider and receiving system logs/events |

Spring Mail may throw exceptions from the **MailException** hierarchy, such as **MailAuthenticationException**, **MailSendException**, or **MailPreparationException**. When constructing a MimeMessage, Jakarta Mail can also throw **MessagingException**.

Do not retry an HTML rendering error or charset error as if it were a network error. Conversely, fixing a template will not resolve incorrect SMTP credentials.

If a timeout occurs after data has been sent to the SMTP server but before the client receives a response, the outcome may be ambiguous. Retrying immediately risks creating duplicate emails. Critical systems should record a notification ID, an attempt ID, and reconcile with the provider whenever possible.

## 26. Synchronous Sending or via Queue?

The call:

~~~java
mailSender.send(message);
~~~

normally executes synchronously on the calling thread. **multipart/alternative does not automatically create background jobs, queues, or retries**.

If an email is the result of a business transaction and requires high reliability, you can record the intent to send in an outbox and let a worker build the content:

~~~text
Business transaction
        |
        v
Write data + notification outbox
        |
      COMMIT
        |
        v
Background worker
        |
        v
Create email data snapshot
        |
        +--> Render plain text
        |
        +--> Render HTML
        |
        v
MimeMessageHelper.setText(plain, html)
        |
        v
JavaMailSender.send()
        |
        v
Record attempt and result
~~~

The worker needs to render both versions from the same data snapshot to avoid inconsistencies. An outbox keeps the intent to send consistent with the database transaction, but does not guarantee exactly-once delivery on its own; retries and ambiguous states still need to be managed.

## 27. Checklist When Designing Two Versions

| Item | Question |
|---|---|
| Meaning | Do plain text and HTML have the same business content? |
| Order | Does text/plain precede text/html in alternative? |
| URL | Do links in both versions point to the same destination? |
| Data | Are both rendered from the same snapshot? |
| Charset | Does Vietnamese content use UTF-8 appropriately? |
| HTML | Is markup escaped according to context? |
| Accessibility | Is the content readable when images or CSS are blocked? |
| Attachment | Is mixed used for attachments instead of alternative? |
| Inline resource | Are related and Content-ID used when HTML needs CID images? |
| Testing | Have you inspected raw MIME and opened the message on target clients? |
| Operations | Have you separated rendering errors, sending errors, and post-SMTP bounces? |

These are design points to guide implementation; they are not an automated QA mechanism of Spring Mail.

## 28. Takeaways

**multipart/alternative** is a MIME structure used to provide multiple alternative representations of the same email content. With Spring Framework Mail, applications typically create a MimeMessage and use **MimeMessageHelper.setText(plainText, htmlText)** to supply both **text/plain** and **text/html** parts. Plain text should be placed first, HTML second; the email client selects the appropriate representation.

The two versions need to be consistent in information and actions, rendered from the same data model. Plain text must contain the content and real URLs, while HTML can add headings, tables, CTA buttons, and images. Use **multipart/mixed** for attachments and **multipart/related** for inline resources; do not confuse these MIME relationships with alternative.

When implementing, set an appropriate charset such as UTF-8, escape HTML data according to context, validate URLs and MIME structure, and test on target email clients. **Good multipart/alternative design helps emails retain their meaning and usability whether the recipient reads in text or HTML.**
