# Selecting a Fallback Provider When the Primary Provider Fails

In an application using **Spring Framework Mail**, the system often sends email through a single SMTP server or email service (Email Service Provider, abbreviated **ESP**). When that provider suffers connectivity incidents, rate limiting, policy changes, or temporarily stops accepting mail, critical notifications such as order confirmations, password resets, and receipts can be delayed. A **multi-provider** architecture lets you select a fallback provider to reduce single-point-of-failure dependency.

However, **selecting a fallback provider does not mean "whenever calling provider A fails, immediately send through provider B."** A failure can occur **after provider A has already accepted the email**, while the application never receives the final response due to a timeout or connection drop. If you resend via B, the recipient may receive **two copies**. Therefore, failover must be based on failure category, evidence about submission state, the remaining provider's ability to accept the mail, and an explicit duplicate-risk tolerance policy.

This lesson explains how to design primary/backup provider selection in Spring Framework Mail, distinguish **SMTP** from **HTTP mail APIs**, build safe failover policies, and combine transactional outbox, health checks, circuit breakers, rate limits, suppression, operational observability, and testing for provider failure scenarios.

> **Core principle:** Automatically switch to a backup provider only when there is evidence that **no email was accepted by the previous provider**, or when a provider-supported idempotency mechanism provides appropriate guarantees. If the outcome is **UNKNOWN**, reconcile or act under a risk policy rather than failing over blindly.

## 1. What Problem Does Multi-Provider Solve?

An email flow with only one provider:

~~~text
Spring Application
      |
      v
JavaMailSender
      |
      v
SMTP Provider A
      |
      v
Receiving Mail Systems
~~~

If A is unavailable, persisting the notification in the database can still succeed, while **SMTP submission** is blocked. With a backup provider:

~~~text
                       +--> Provider A (primary) --+
Application -> MailRouter -|                          +--> Recipient
                       +--> Provider B (backup) --+
~~~

This architecture can:

- Reduce downtime when the primary provider stops accepting mail.
- Isolate resilience by notification type: security/transactional may need higher priority than marketing.
- Leverage different geographic regions or transport infrastructure when providers and data policies allow.
- Maintain sending flow during **transient errors** that can be verified cleanly before submission.
- Enable controlled provider maintenance and migrations.

However, it **does not automatically solve**:

- Both providers losing Internet connectivity or sharing a failing DNS/CA/network path.
- Invalid recipient data or unsubscribed recipients.
- Sending domains not yet verified with provider B.
- Template/MIME errors generated by the application.
- SMTP accepted, yet the message bounces, triggers spam filtering, or is blocked on the receiving side.
- Timeouts where the outcome of sending via A is unknown.

Backup selection must be designed alongside **business policy** and **transport observability**, not merely by adding another SMTP hostname.

## 2. Distinguishing Provider, Transport, Route, and Notification

In a multi-provider system, several concepts should be kept distinct:

| Concept | Meaning | Example |
| --- | --- | --- |
| **Notification** | One logical business intent to send an email | Send confirmation for order ORD-1528 |
| **Attempt** | One trial submitting the notification to a provider | Attempt #1 via A |
| **Provider** | Mail service provider with its own account and policies | A, B |
| **Transport** | Mechanism for sending through the provider | SMTP via JavaMailSender or HTTP API |
| **Route** | Provider/transport selected for a specific attempt | transactional -> A |
| **Failover** | Selecting a backup route when the primary route cannot be used safely | A unavailable -> B |
| **Idempotency key** | Durable logical identifier to limit duplicate sends | ORDER_CONFIRMED:ORD-1528:R |
| **Correlation ID** | Trace identifier across logs, provider events, and reconciliation | mail-notification-6b91 |

**Notification ID** must not change every time a new provider is chosen. **Attempt ID** can change to clearly record each trial. If a provider offers an official idempotency API, verify what scope that key actually covers: **provider A's key usually has no deduplication effect on provider B**.

### Example Lifecycle of One Notification

~~~text
Notification #42
  business key: ORDER_CONFIRMED:ORD-1528:user-392
  recipient:   customer@example.test
  purpose:     ORDER_RECEIPT
  status:      PENDING

  Attempt #1 -> Provider A -> could not connect (not submitted)
  Attempt #2 -> Provider B -> SMTP accepted

Notification #42 -> ACCEPTED
~~~

In situations where **you cannot prove attempt #1 was not submitted**, you cannot automatically create attempt #2 while still claiming there is no duplicate risk.

## 3. When Is Failover Actually Useful?

A backup provider helps most when errors occur **before the sending boundary where side effects can happen**.

Example:

~~~text
Connection to Provider A fails before an SMTP session starts
                 |
                 v
Confirmed that no MAIL FROM / RCPT TO / DATA
was sent over the failed connection
                 |
                 v
Does Provider B have valid config/health/authorization?
          |                      |
          v                      v
         Yes                    No
          |                      |
          v                      v
  Safer to fail over          Wait/retry later
          |
          v
      Provider B
~~~

Conversely:

~~~text
Provider A finishes receiving DATA
       |
       v
SMTP server may have queued the mail
       |
       v
Lost 250 response / read timeout
       |
       v
Outcome = UNKNOWN
       |
       v
DO NOT automatically send the same notification via B
~~~

Some HTTP mail APIs provide idempotency keys or submission lookup; that lowers risk **within the scope of that API and provider**. Still, switching to another vendor requires evidence that the first vendor did not accept the email, or a specially coordinated design; global idempotency does not exist merely because the application sends the same key to A and B.

## 4. Classifying Errors Before Switching Providers

A failover strategy needs an **error classification** layer rather than catching every exception and calling the backup.

| Error category | Example | Switch immediately to B? | Explanation |
| --- | --- | --- | --- |
| **Unavailable before submission** | Connect refused, DNS failed to resolve before opening connection | Possible, with evidence of non-submission | No submission occurred |
| **TLS handshake failure before sending** | Invalid CA/certificate/hostname | Not by default | May be a security/config issue; do not bypass controls |
| **Authentication/config error** | Invalid SMTP AUTH, unauthorized sender | Not by default | Fix configuration or policy, not a capacity outage |
| **Rate limit/quota** | Provider reports quota or temporary throttling before receiving DATA | Conditional | Depends on response, B's quota, load rules, consent |
| **Temporary recipient rejection** | RCPT TO temporarily rejected | With caution | May reflect shared recipient/policy; avoid hammering like spam |
| **Permanent recipient rejection** | Invalid address, suppressed | No | Sending via B will not make the recipient valid |
| **SMTP final 2xx accepted** | Server confirmed receipt of message | No | Notification is already submitted |
| **Read timeout after DATA** | Server may have accepted | Not automatically | Outcome UNKNOWN |
| **Crash after submission** | Worker dies before DB update | Not automatically | Provider may have accepted |
| **HTTP API 2xx + request ID** | Provider accepted request | No | Already submitted via A |
| **HTTP API timeout after request body** | Unclear if provider processed it | Not automatically | Outcome UNKNOWN, needs lookup/idempotency |
| **Application template render error** | Missing data, invalid MIME | No | Shared message error; switching providers will not fix it |

Not every SMTP or HTTP **4xx/5xx** code means the same thing. SMTP 4xx is a transient reply and 5xx is typically a permanent failure at a given stage; HTTP 429 is usually rate limiting, while HTTP 5xx can occur after partial request processing. **Protocol stage and acceptance evidence** matter more than relying on a status number alone.

### Do Not Infer Outcomes from Generic Exception Classes

Spring provides exception types such as **MailAuthenticationException**, **MailSendException**, and **MailParseException**, yet not every instance of an exception type tells you whether the provider received the message. For example, a **MailSendException** wrapping a socket read timeout can happen before or after critical SMTP steps.

Outcome classification must be based on transport/provider information actually observed. If the transport layer only exposes a generic exception without evidence, choose **UNKNOWN** rather than guessing "definitely not sent."

## 5. Three Safe Outcomes for Each Attempt

To avoid collapsing every exception into the same action, you can define:

~~~text
                    Attempt Result
                           |
               +-----------+------------+
               |           |            |
               v           v            v
          ACCEPTED     NOT_ACCEPTED    UNKNOWN
                          |
                  +-------+-------+
                  |               |
                  v               v
              RETRYABLE       PERMANENT
~~~

- **ACCEPTED:** evidence exists that the provider/SMTP accepted the submission; do not fail over.
- **NOT_ACCEPTED_RETRYABLE:** evidence exists of non-acceptance and the error permits trying another route or retrying after a delay.
- **NOT_ACCEPTED_PERMANENT:** evidence exists of permanent rejection; do not cycle through providers.
- **UNKNOWN:** cannot determine whether accepted or not; no automatic failover by default.

Java type example:

~~~java
public enum SubmissionOutcome {
    ACCEPTED,
    NOT_ACCEPTED_RETRYABLE,
    NOT_ACCEPTED_PERMANENT,
    UNKNOWN
}
~~~

These states are an **application model**, not states returned natively by Spring Framework Mail. They separate **provider-selection logic** from the exception details of individual SDKs/transports.

### Failover Is a Decision, Not Merely a Retry

A new attempt may still use provider A after backoff, switch to B, or pause for reconciliation. The decision depends on:

1. The outcome of the previous attempt.
2. Retry/failover rules per error category.
3. Health, quota, and capabilities of the backup provider.
4. Whether the message is still eligible to send.
5. Remaining request lifetime (deadline, OTP expiry, business SLA).
6. Legal, geographic, and privacy constraints.

It cannot be designed properly with a simple **if (!providerA.available()) sendViaB()**.

## 6. Criteria for Selecting a Backup Provider

A backup provider is only useful if it can **actually send the notification type currently needed**. Good health does not mean every sender, file type, size, and region is supported.

| Criterion | Practical question |
| --- | --- |
| **Sender identity** | Are the domain and From address verified with B? |
| **SPF/DKIM/DMARC** | Is B authorized to send, sign DKIM, and pass alignment under the domain policy? |
| **Transport security** | Does B's SMTP require STARTTLS/SMTPS, and are certificates and hostnames verified? |
| **Capabilities** | Does B support SMTP/API, MIME multipart, HTML, inline CIDs, and needed attachments? |
| **Message size** | Does B accept total email size after MIME/base64 encoding? |
| **Rate limits** | Is remaining quota/concurrency sufficient or already throttled? |
| **Purpose** | Is B authorized to send SECURITY, TRANSACTIONAL, or MARKETING? |
| **Geography/privacy** | Is transmitting content/PII to B allowed under data policies? |
| **Suppression** | Are opt-outs, complaints, and bounce suppressions enforced consistently before sending? |
| **Webhook** | Are accepted, delivered, bounce, and complaint events tracked when switching to B? |
| **Cost** | Does failover carry pricing/business limits to account for? |
| **Reliability** | How independent is B from A's DNS, network, cloud region, and other shared infrastructure? |

### Example Policy by Purpose

~~~text
SECURITY_ALERT:
  primary = provider-a
  backup  = provider-b
  priority = HIGH

ORDER_RECEIPT:
  primary = provider-a
  backup  = provider-b
  priority = MEDIUM

MARKETING_NEWSLETTER:
  primary = provider-a
  backup  = NONE
  priority = LOW
~~~

In this example, marketing is not automatically routed to B. Perhaps B is provisioned only to rescue transactional email, or legal/consent boundaries for marketing are not synchronized. Do not grant every mail category failover rights just because B has a working SMTP connection.

### Backup Quality Depends on Independence

If A and B run on two different providers yet the application has only a single NAT gateway or one broken DNS resolver, both routes can lose connectivity together. Likewise, sharing a domain whose DKIM is not configured on B can yield poor delivery through B even when SMTP returns 250.

Analyze **shared dependencies**: network egress, DNS, TLS truststore, secret manager, message composer, database outbox, queue workers, and sender domains.

## 7. Common Routing Strategies

### Primary–backup (active–passive)

~~~text
Notification -> Provider A
                    |
               A unavailable?
                    |
                    v
                Provider B
~~~

**Pros:** simple, low management overhead, easy to determine default sender.

**Cons:** if B is never exercised regularly, B's configuration/certificates/credentials can rot silently. Backups must be tested periodically in a safe way, without necessarily sending real user mail.

### Weighted Active–Active

~~~text
                +--- 80% ---> Provider A
Notification ---|
                +--- 20% ---> Provider B
~~~

**Pros:** provider B is exercised continuously, surfacing failures early and distributing capacity.

**Cons:** requires managing sender reputation, quotas, recipient suppression, and provider webhooks in both places. For a single notification, choose **one initial route**; never send two simultaneous copies just to "increase reliability."

### Routing by Purpose or Region

For example, SECURITY_ALERT goes to B in one region while marketing goes to A in another. This is **policy routing**, not necessarily failover; one route may be the default because of the mail category's traits.

### Manual Failover

An operator shifts new traffic from A to B after investigating an incident. This is often safer than **automatic failover** on ambiguous errors because it allows verifying provider B, checking domain identity, and scoping jobs properly.

### Do Not Send Hedged Requests over SMTP

Hedged requests send the same request over multiple paths to take the faster response. For an idempotent read, that can be useful. For **sending email**, calling A and B in parallel can produce two SMTP submissions.

~~~text
                  +--> send to A --> accepted
One notification -|
                  +--> send to B --> accepted

Result: Two emails may reach the recipient.
~~~

Do not use parallel active–active for **the same logical notification**, unless there is a genuine guaranteed global coordination/idempotency mechanism—which standard SMTP does not provide.

## 8. Separate Route Selection from the Sending Action

A clean architecture:

~~~text
Business Event / API
        |
        v
Transactional Outbox
        |
        v
Mail Dispatcher
        |
        v
Delivery Policy (recipient, suppression, purpose)
        |
        v
Provider Route Policy
        |
        +--> Provider Registry / capabilities
        +--> Health / circuit breaker
        +--> Quota / rate limit
        +--> Allowed sender domains
        |
        v
Mail Provider Adapter
        |
        +--> SMTP / JavaMailSender A
        '--> SMTP / JavaMailSender B
        |
        v
Attempt History + Outcome
~~~

Responsibilities should be layered:

1. **Business service** decides the content and authorized recipients.
2. **Outbox** durably stores work and prevents duplicate logical notifications.
3. **Delivery policy** checks consent/suppression, email category, and deadlines.
4. **Route policy** selects the right provider; it has no authority to bypass suppression.
5. **Provider adapter** converts MIME/API data into a concrete submission and returns an outcome with evidence.
6. **Attempt repository** stores provider, timestamps, status, and correlation.
7. **Recovery/reconciler** resolves UNKNOWN or provider events.

### Route Policy Must Not Cause Accidental Side Effects

The **selectProvider(...)** method should decide the choice without sending mail or overwriting outcomes. That makes it easy to unit test many scenarios without opening SMTP connections:

~~~java
public record MailRouteRequest(
        String tenantId,
        String notificationId,
        MailPurpose purpose,
        String fromDomain,
        long estimatedMessageBytes
) {
}

public enum MailPurpose {
    SECURITY_ALERT,
    ORDER_RECEIPT,
    MARKETING_NEWSLETTER
}

public interface MailRoutePolicy {
    ProviderId selectInitialProvider(MailRouteRequest request);
}

public enum ProviderId {
    PRIMARY,
    BACKUP
}
~~~

The types above are **application design APIs**, not built-in Spring Mail classes. In production, validation also needs recipient domain, tenant capabilities, region, cost, and appropriate sending permissions.

## 9. Defining Clear Provider Results for the Router

An interface can hide differences between SMTP and HTTP APIs:

~~~java
public record MailSubmission(
        String notificationId,
        MailPurpose purpose,
        String recipientEmail,
        String subject,
        String plainBody,
        String htmlBody
) {
}

public enum FailureCategory {
    NONE,
    CONNECT_UNAVAILABLE,
    PROVIDER_THROTTLED,
    PROVIDER_TEMPORARY,
    RECIPIENT_REJECTED,
    AUTHENTICATION,
    TLS_SECURITY,
    CONFIGURATION,
    AMBIGUOUS_TIMEOUT,
    UNKNOWN_FAILURE
}

public record ProviderResult(
        ProviderId providerId,
        SubmissionOutcome outcome,
        FailureCategory failureCategory,
        String providerMessageId
) {
}

public interface MailProvider {
    ProviderId id();

    ProviderResult submit(MailSubmission submission);
}
~~~

**providerMessageId** is the ID/queue ID when the provider supplies one; never fabricate a value and claim it was confirmed by the provider. With SMTP, not every server returns a queue ID usable via API. With HTTP APIs, a request ID may be returned per contract.

### Adapters Must Preserve Error Semantics

If an HTTP provider returns a response **confirmed rejected before submission**, the adapter can return **NOT_ACCEPTED_RETRYABLE** or **NOT_ACCEPTED_PERMANENT** as appropriate.

If a **timeout occurs after transmitting the request**, the adapter must not infer "not received" merely because the client could not read the response. Return **UNKNOWN**.

If an adapter catches every `RuntimeException` and returns **NOT_ACCEPTED_RETRYABLE**, the router will make dangerous mistakes. Design conservative exception mapping, capture the protocol stage when evidenced, and allow ambiguous outcomes.

## 10. Failover Decision Table

A policy should express clear allow/deny conditions:

| Outcome A | Failure category | B ready and right capability? | Decision |
| --- | --- | --- | --- |
| ACCEPTED | NONE | Any | Do not fail over |
| NOT_ACCEPTED_RETRYABLE | CONNECT_UNAVAILABLE, proven no submission | Yes | May try B |
| NOT_ACCEPTED_RETRYABLE | PROVIDER_THROTTLED with explicit rejection | Yes, quota available | May try B per policy |
| NOT_ACCEPTED_RETRYABLE | PROVIDER_TEMPORARY with evidence of non-acceptance | Yes | May try B or wait for A |
| NOT_ACCEPTED_PERMANENT | RECIPIENT_REJECTED | Yes | Do not send via B |
| NOT_ACCEPTED_PERMANENT | AUTHENTICATION/CONFIGURATION | Yes | Stop/escalate; do not bypass policy |
| UNKNOWN | AMBIGUOUS_TIMEOUT | Yes | Do not automatically fail over |
| UNKNOWN | UNKNOWN_FAILURE | Yes | Keep UNKNOWN/reconcile |

Even for failures eligible to try B, verify **the notification is still eligible to send** at failover time. A user may have unsubscribed while A was failing; retrying via B must not bypass suppression.

### Do Not Use a Single "primaryHealthy" Flag as the Only Condition

Having A's circuit breaker in OPEN state means **do not start new attempts on A**. It says nothing about the outcome of an earlier attempt. A notification currently UNKNOWN on A does not become safe to send via B just because A is now marked unhealthy.

Route choice and outcome for each notification must be stored and evaluated independently.

## 11. Example Conservative Failover Policy in Java

Suppose the application automatically fails over from A to B only for two cases proven **before any submission**: connection failure before opening an SMTP session, or a provider quota rejection before accepting the message. Other failures must be handled by separate policies.

~~~java
public record FailoverDecision(
        boolean allowed,
        String reason
) {
    public static FailoverDecision allow(String reason) {
        return new FailoverDecision(true, reason);
    }

    public static FailoverDecision deny(String reason) {
        return new FailoverDecision(false, reason);
    }
}
~~~

~~~java
import java.util.EnumSet;
import java.util.Set;

public final class ConservativeFailoverPolicy {

    private static final Set<FailureCategory> SAFE_CATEGORIES =
            EnumSet.of(
                    FailureCategory.CONNECT_UNAVAILABLE,
                    FailureCategory.PROVIDER_THROTTLED
            );

    public FailoverDecision evaluate(
            ProviderResult previous,
            boolean backupEligible,
            boolean notificationStillEligible
    ) {
        if (previous.outcome()
                != SubmissionOutcome.NOT_ACCEPTED_RETRYABLE) {
            return FailoverDecision.deny(
                    "Previous submission was accepted, permanent or unknown"
            );
        }

        if (!SAFE_CATEGORIES.contains(
                previous.failureCategory()
        )) {
            return FailoverDecision.deny(
                    "Failure is not in safe-failover allowlist"
            );
        }

        if (!notificationStillEligible) {
            return FailoverDecision.deny(
                    "Notification no longer eligible"
            );
        }

        if (!backupEligible) {
            return FailoverDecision.deny(
                    "Backup capability or health not sufficient"
            );
        }

        return FailoverDecision.allow(
                "Safe failure with eligible backup"
        );
    }
}
~~~

**Important:** Having **CONNECT_UNAVAILABLE** in the allowlist **does not prove safety by itself**. The adapter may return that category with NOT_ACCEPTED_RETRYABLE only when it confirms the failure happened **before any external submission**. If the stage cannot be determined, return UNKNOWN. Likewise, PROVIDER_THROTTLED can only trigger failover when the provider gives rejection evidence prior to creating a submission.

### Do Not Turn Decisions Into an Infinite Retry Loop

For example, route policy must enforce an **attempt cap**, prevent A→B→A→B oscillation, and respect provider backoff requests:

~~~text
Attempt #1: A -> proven NOT_ACCEPTED_RETRYABLE
Policy:      B eligible
Attempt #2: B -> ACCEPTED
Stop:        notification ACCEPTED
~~~

If B also fails in a retryable way, the job can move to RETRY_WAIT with backoff or follow a concrete route plan. Nothing requires trying every provider inside a single HTTP request.

### Healthy Provider Yet Unauthorized to Send

Provider B may report health=UP while lacking configured sender identity for tenant X. In that case **backupEligible=false**. User and data policies outweigh having a working TCP path to B.

## 12. Creating Two JavaMailSenderImpl Instances in Spring

Spring Mail provides **JavaMailSenderImpl** for sending over SMTP. With two accounts/providers, create two independent senders, each with its own host, port, credentials, TLS, and timeouts.

Configuration example:

~~~yaml
app:
  mail:
    providers:
      primary:
        host: smtp-a.example.test
        port: 587
        username: ${SMTP_A_USER}
        password: ${SMTP_A_PASSWORD}
      backup:
        host: smtp-b.example.test
        port: 587
        username: ${SMTP_B_USER}
        password: ${SMTP_B_PASSWORD}
~~~

The hosts, usernames, and environment variables are placeholders. Real secrets must live in a secret manager or protected environment, never committed to Git. Because the configuration uses the **app.mail.providers** prefix, Spring Boot will **not automatically create two JavaMailSender beans from that YAML alone**; the application must bind them and declare the beans explicitly.

### Binding Properties with a Record

With modern Spring Boot supporting record-based configuration properties:

~~~java
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "app.mail.providers")
public record ProviderMailProperties(
        Smtp primary,
        Smtp backup
) {
    public record Smtp(
            String host,
            int port,
            String username,
            String password
    ) {
    }
}
~~~

### Factory Creating an SMTP Sender with Mandatory TLS

~~~java
import org.springframework.mail.javamail.JavaMailSenderImpl;

public final class SmtpSenderFactory {

    private SmtpSenderFactory() {
    }

    public static JavaMailSenderImpl create(
            ProviderMailProperties.Smtp cfg
    ) {
        JavaMailSenderImpl sender = new JavaMailSenderImpl();
        sender.setHost(cfg.host());
        sender.setPort(cfg.port());
        sender.setUsername(cfg.username());
        sender.setPassword(cfg.password());
        sender.setDefaultEncoding("UTF-8");

        var props = sender.getJavaMailProperties();
        props.put("mail.transport.protocol", "smtp");
        props.put("mail.smtp.auth", "true");
        props.put("mail.smtp.starttls.enable", "true");
        props.put("mail.smtp.starttls.required", "true");
        props.put("mail.smtp.ssl.checkserveridentity", "true");
        props.put("mail.smtp.connectiontimeout", "5000");
        props.put("mail.smtp.timeout", "10000");
        props.put("mail.smtp.writetimeout", "10000");
        return sender;
    }
}
~~~

Timeouts are in milliseconds and serve as examples to tune per SLA. The factory illustrates **STARTTLS on SMTP submission**; if provider B only supports **implicit TLS**, configure it appropriately with **mail.smtp.ssl.enable=true** rather than assuming the same property set works for every provider.

### Declaring Two Explicitly Named Beans

~~~java
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.mail.javamail.JavaMailSenderImpl;

@Configuration
@EnableConfigurationProperties(ProviderMailProperties.class)
public class MultiProviderMailConfiguration {

    @Bean("primaryMailSender")
    public JavaMailSenderImpl primaryMailSender(
            ProviderMailProperties cfg
    ) {
        return SmtpSenderFactory.create(cfg.primary());
    }

    @Bean("backupMailSender")
    public JavaMailSenderImpl backupMailSender(
            ProviderMailProperties cfg
    ) {
        return SmtpSenderFactory.create(cfg.backup());
    }
}
~~~

Because the application has multiple beans of the same type, injection at adapters should specify **@Qualifier**:

~~~java
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.mail.javamail.JavaMailSender;

public SmtpPrimaryMailProvider(
        @Qualifier("primaryMailSender")
        JavaMailSender sender
) {
    this.sender = sender;
}
~~~

The constructor snippet only shows how to disambiguate the dependency; a complete class adds composition and outcome handling. With Spring Boot, declaring two mail senders yourself can affect default auto-configuration and other injection points. Make sure every injection site knows which sender it receives, avoiding **NoUniqueBeanDefinitionException** or accidentally wiring the wrong bean.

### Do Not Mutate One Sender's Host/Credentials at Runtime per Message

An error-prone design:

~~~java
sharedSender.setHost(selectHost(job));
sharedSender.setPassword(selectPassword(job));
sharedSender.send(message);
~~~

When multiple threads send concurrently, configuration can be overwritten between attempts, causing messages to use the wrong credentials/host. Instead, **each provider gets its own JavaMailSenderImpl**, immutable after initialization; the router picks the right instance. Secret rotation requires a safe procedure for updating beans/connections/sessions, never arbitrarily mutating a concurrently used singleton.

## 13. SMTP Provider Adapter Must Control MIME and Outcomes

Example adapter building email with JavaMailSender, separated from route policy:

~~~java
import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.mail.MailException;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

public final class SmtpMailProvider implements MailProvider {

    private final ProviderId id;
    private final JavaMailSender sender;
    private final String verifiedFrom;

    public SmtpMailProvider(
            ProviderId id,
            JavaMailSender sender,
            String verifiedFrom
    ) {
        this.id = id;
        this.sender = sender;
        this.verifiedFrom = verifiedFrom;
    }

    @Override
    public ProviderId id() {
        return id;
    }

    @Override
    public ProviderResult submit(MailSubmission notification) {
        try {
            MimeMessage message = sender.createMimeMessage();
            MimeMessageHelper helper =
                    new MimeMessageHelper(
                            message,
                            MimeMessageHelper.MULTIPART_MODE_MIXED,
                            "UTF-8"
                    );

            helper.setFrom(verifiedFrom);
            helper.setTo(notification.recipientEmail());
            helper.setSubject(notification.subject());
            helper.setText(
                    notification.plainBody(),
                    notification.htmlBody()
            );

            sender.send(message);
            return new ProviderResult(
                    id,
                    SubmissionOutcome.ACCEPTED,
                    FailureCategory.NONE,
                    null
            );
        } catch (MessagingException ex) {
            // Composition error, not transport failover.
            throw new IllegalArgumentException(
                    "Unable to compose MIME message",
                    ex
            );
        } catch (MailException ex) {
            // Do not assume SMTP did not receive the email.
            return new ProviderResult(
                    id,
                    SubmissionOutcome.UNKNOWN,
                    FailureCategory.UNKNOWN_FAILURE,
                    null
            );
        }
    }
}
~~~

**This example is intentionally conservative:** when `JavaMailSender` throws `MailException` and the adapter lacks sufficient protocol evidence, the outcome is UNKNOWN. That means the router **does not automatically try B**. In a real system, you can add a transport-evidenced classifier to handle pre-submission connect failures; never map every exception to retryable.

**Important distinction:** if the error stems from MIME construction, invalid addresses, or bad data, calling another provider solves nothing. Validation of recipients, From, Subject, and HTML/templates must occur in a trusted composer/policy layer before submission.

### Returning ACCEPTED Is Not DELIVERED

When `sender.send(...)` completes normally, the application may record **SMTP submission accepted** per transport semantics; it cannot conclude the message reached the Inbox or was opened. Bounces, complaints, and delivery statuses must be tracked separately through the provider when needed.

### Provider-Specific Senders and Sender Identity

Provider A might use **orders@example.test**, whereas B may require a different verified sender identity for the same brand. Never take From arbitrarily from a request or switch to an uncontrolled domain just to force delivery.

If the sender domain changes on failover, assess impacts on SPF/DKIM/DMARC, reply routing, bounce addresses, and recipient trust. Ideally, prepare verified identities and DNS records **before an incident**.

## 14. Coordinating Failover Through a Dedicated Service

A router needs to cap attempts, ensure each attempt has its own provider ID, verify eligibility, and stop when the outcome is unsafe to continue.

The following example illustrates **decision logic only**; it does not implement transactions, a persistent outbox, or rate limiting:

~~~java
import java.util.Map;

public final class ConservativeMailRouter {

    private final Map<ProviderId, MailProvider> providers;
    private final ConservativeFailoverPolicy failoverPolicy;
    private final BackupEligibility backupEligibility;
    private final MailEligibility mailEligibility;

    public ConservativeMailRouter(
            Map<ProviderId, MailProvider> providers,
            ConservativeFailoverPolicy failoverPolicy,
            BackupEligibility backupEligibility,
            MailEligibility mailEligibility
    ) {
        this.providers = Map.copyOf(providers);
        this.failoverPolicy = failoverPolicy;
        this.backupEligibility = backupEligibility;
        this.mailEligibility = mailEligibility;
    }

    public ProviderResult submitWithConservativeFailover(
            MailRouteRequest route,
            MailSubmission submission
    ) {
        if (!mailEligibility.allowed(route)) {
            throw new IllegalStateException(
                    "Recipient/purpose not eligible"
            );
        }

        ProviderResult primaryResult =
                providers.get(ProviderId.PRIMARY).submit(submission);

        if (primaryResult.outcome()
                == SubmissionOutcome.ACCEPTED) {
            return primaryResult;
        }

        boolean backupReady = backupEligibility.allowed(
                ProviderId.BACKUP,
                route
        );

        FailoverDecision decision = failoverPolicy.evaluate(
                primaryResult,
                backupReady,
                mailEligibility.allowed(route)
        );

        if (!decision.allowed()) {
            return primaryResult;
        }

        return providers.get(ProviderId.BACKUP).submit(submission);
    }
}
~~~

Illustrative check interfaces:

~~~java
public interface BackupEligibility {
    boolean allowed(
            ProviderId provider,
            MailRouteRequest request
    );
}

public interface MailEligibility {
    boolean allowed(MailRouteRequest request);
}
~~~

This router pattern is **not complete production code**. For instance, adapter exceptions need policy-driven outcome mapping; attempt state must be durably recorded before external I/O; checking eligibility twice does not eliminate races if a user unsubscribes concurrently; and `sender.send(...)` needs appropriate timeouts. Those gaps are addressed by an outbox/worker in the next section.

### Do Not Hold an HTTP Request Open to Retry Indefinitely

Failover can take several seconds per provider, or wait for circuit breakers and retry-after windows. A business endpoint must not block indefinitely while SMTP is unstable. For transactional emails, **transactional outbox + worker** usually provides a cleaner boundary: the API persists the sending intent and returns per business flow, while workers process attempts within deadlines and retry policies.

### When Provider A Is Already Unhealthy Before the Attempt

If A's circuit breaker is already OPEN, the router can select B **from the start** for a notification **with no prior attempts**. This is not failover after a failed submission; it is **health-based initial routing**.

~~~text
New notification
  No attempts yet
  Primary breaker OPEN
  Backup eligible and healthy
          |
          v
      Choose B first
~~~

This is usually safer than trying A when it is known to be down and only then falling back to B. Still, you must verify B is authorized and appropriate for the purpose, and have a policy when both providers are unavailable.

## 15. Transactional Outbox Makes Failover Durable

A reliable flow:

~~~text
Business transaction
       |
       +--> Save business state
       '--> Insert mail_outbox(PENDING, stable_notification_key)
       |
       v
      COMMIT
       |
       v
Worker claim job atomically
       |
       v
Check consent / suppression / deadline
       |
       v
Choose provider (primary or backup)
       |
       v
Create persisted attempt with provider + identity
       |
       v
Submit via provider outside database transaction
       |
       +-- ACCEPTED ------------------------> Outbox ACCEPTED
       |
       +-- Proven NOT_ACCEPTED_RETRYABLE ---> Re-evaluate route / retry
       |
       +-- PERMANENT -----------------------> Outbox PERMANENT_FAILED
       |
       '-- UNKNOWN -------------------------> Outbox UNKNOWN
                                                 |
                                                 v
                                            Reconciliation
~~~

The outbox stores **one logical notification**; attempt history records **each trial**. Use a unique constraint to prevent the same event from being enqueued multiple times due to message-broker redelivery or client retries.

### Basic Schema Example

~~~sql
CREATE TABLE mail_outbox (
    id UUID PRIMARY KEY,
    tenant_id VARCHAR(80) NOT NULL,
    notification_key VARCHAR(250) NOT NULL,
    purpose VARCHAR(80) NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    available_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_provider VARCHAR(80),
    lease_owner VARCHAR(120),
    lease_token BIGINT NOT NULL DEFAULT 0,
    lease_until TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_mail_outbox_notification
        UNIQUE (tenant_id, notification_key)
);

CREATE TABLE mail_attempt (
    id UUID PRIMARY KEY,
    notification_id UUID NOT NULL REFERENCES mail_outbox(id),
    provider VARCHAR(80) NOT NULL,
    outcome VARCHAR(40) NOT NULL,
    failure_category VARCHAR(80),
    provider_message_id VARCHAR(250),
    started_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMPTZ,
    correlation_id VARCHAR(150) NOT NULL
);

CREATE INDEX idx_mail_attempt_notification_time
ON mail_attempt (notification_id, started_at);

CREATE INDEX idx_mail_outbox_due
ON mail_outbox (available_at, id)
WHERE status IN ('PENDING', 'RETRY_WAIT');
~~~

The schema above is a PostgreSQL example, not a built-in Spring Mail feature. To enforce strict parallel retry/attempt fencing in production, a real system also needs version/CAS constraints, durable message snapshots, timeouts, unique attempt identities, and step-by-step transaction persistence.

### The Same Notification Must Not Generate a New Key on Failover

Do not do:

~~~text
Attempt via A: notification key = ORDER-1528-primary
Attempt via B: notification key = ORDER-1528-backup
~~~

Doing so causes the two trials to be treated as **two separate business jobs** and defeats duplicate-enqueue protection. Instead:

~~~text
Notification key = ORDER_CONFIRMED:ORD-1528:user-392
Attempt #1       = provider A, attempt id = a1
Attempt #2       = provider B, attempt id = a2
~~~

If email/content changes due to an intentional resend, create a new notification per business workflow and link it to the original notification rather than silently mutating the payload under the same key.

## 16. Atomic Job Claiming with Multiple Workers

If two workers both spot a PENDING job and both pick B, the recipient may receive two emails. A provider router **does not** replace outbox claiming.

A PostgreSQL example:

~~~sql
WITH next_job AS (
    SELECT id
    FROM mail_outbox
    WHERE status IN ('PENDING', 'RETRY_WAIT')
      AND available_at <= CURRENT_TIMESTAMP
    ORDER BY available_at ASC, id ASC
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE mail_outbox AS m
SET
    status = 'IN_FLIGHT',
    lease_owner = :worker_id,
    lease_token = m.lease_token + 1,
    lease_until = CURRENT_TIMESTAMP + INTERVAL '2 minutes',
    updated_at = CURRENT_TIMESTAMP
FROM next_job
WHERE m.id = next_job.id
RETURNING
    m.id,
    m.tenant_id,
    m.notification_key,
    m.purpose,
    m.lease_token;
~~~

The claim transaction must commit **before opening the SMTP connection**, avoiding holding database row locks during slow network I/O. The worker records the attempt before sending, submits the message, and then updates the outcome in a short transaction conditioned on the lease token.

### What Does the Fencing Token Protect?

If worker A pauses too long and its lease expires, recovery may change the job state. A must not overwrite the row after losing ownership:

~~~sql
UPDATE mail_outbox
SET
    status = 'ACCEPTED',
    last_provider = :provider,
    updated_at = CURRENT_TIMESTAMP
WHERE id = :notification_id
  AND status = 'IN_FLIGHT'
  AND lease_owner = :worker_id
  AND lease_token = :lease_token;
~~~

If UPDATE affects 0 rows, the stale worker must handle the late outcome via attempt/reconciliation rather than overwriting the newer state.

**Limitation:** fencing tokens only prevent stale database writes; **they do not retract an email already submitted over SMTP**. On expired leases, do not assume not-sent; transition to UNKNOWN/reconciliation if evidence is missing.

## 17. Avoid Failover After Crashes or Unknown-Outcome Timeouts

Consider this scenario:

~~~text
T1 Worker claims notification N
T2 Worker chooses A and persists attempt A1
T3 A receives SMTP DATA
T4 A replies 250, but the response is lost in transit
T5 Worker records timeout or process crashes
T6 Lease expires
T7 Recovery sees N is not ACCEPTED
~~~

If T7 switches straight to B, the recipient may receive emails from both A and B. Better:

~~~text
Expired IN_FLIGHT
       |
       v
UNKNOWN (possible accepted by A)
       |
       v
Provider A logs/API/events or operator review
       |
       +--> accepted confirmed -> ACCEPTED, no B
       |
       +--> not accepted proven -> eligible for retry/B
       |
       '--> evidence incomplete -> HOLD / manual risk decision
~~~

### Difference Between Delivery Failure and Submission Ambiguity

If provider A **ACCEPTED** and later sends a **BOUNCED** webhook, the notification was already submitted. A separate business workflow may handle bounces, fix recipients, or choose another contact channel. Do not treat a bounce as "A failed to send so fail over to B," as that can cause spam or violate suppression.

If provider A returns a **temporary 4xx before accepting the message**, depending on the stage and evidence, retrying via B may make more sense. Distinguish **provider rejected the submission** from **provider accepted then downstream delivery failed**.

### Reconciliation Is Investigation, Not Another Name for Retry

A reconciler should inspect:

- Attempt ID, provider ID, and send timestamp.
- Correlation ID/Message-ID if the provider stores a trace.
- Provider request/queue ID if received.
- Validly signed accepted/delivered/bounced webhooks.
- SMTP server logs/lookup APIs when available with clear semantics.

**Plain SMTP does not provide a standard API to ask "was the message with key K received?"** You cannot guarantee exactly-once email delivery merely by inserting the same Message-ID header across A and B.

## 18. Provider Health Checks: Being Reachable Does Not Mean Able to Send

Provider health has multiple levels:

| Check level | What does it confirm? | What does it not confirm? |
| --- | --- | --- |
| DNS resolve | Host has queryable records | SMTP is accepting mail |
| TCP connect | An endpoint is listening on the port | TLS, AUTH, quota, or sender permissions |
| SMTP greeting/EHLO | SMTP protocol responds | Credentials/mail will be accepted |
| TLS handshake | Server has valid TLS/certificate | Account is still allowed to send |
| AUTH succeeds | Credentials accepted | Specific recipient/message will be accepted |
| Isolated test submission | A test mail can be submitted | All production messages will deliver |
| Provider status API | Provider self-reports health | Does not guarantee no localized failure |
| Recent accepted rate | Live traffic is succeeding | Insufficient sample when traffic is 0 |

For example, **JavaMailSenderImpl.testConnection()** can verify transport connectivity and AUTH depending on config **without sending a MIME message**. However, calling it frequently still costs connections/handshakes and can trigger rate limits or look like abnormal traffic to the provider.

### Do Not Treat a TCP Ping as the Sole Oracle

A provider can answer TCP while having a bad TLS certificate or revoked SMTP AUTH. Conversely, a single `testConnection` failure from transient network noise is not enough to mark the entire provider DOWN for a long period.

Good health assessment combines:

- Passive health: outcomes from real submissions, errors by category.
- Active health: probes bounded in frequency and scope.
- Provider status page/API when supported.
- Circuit breaker state, rate limiters, and remaining capacity.
- Evaluation by region/tenant/sender identity when provider policies differ.

### Separate Liveness, Readiness, and Mail Provider Availability

If SMTP provider A is DOWN, the Spring application does not necessarily need Kubernetes to restart it repeatedly. Process liveness can remain UP while **mail route availability** reports degraded.

A readiness check can reflect the app's ability to serve critical requests, though care is needed: if the system uses an outbox and B is available, marking the entire app DOWN just because A failed takes down business APIs even though the outbox can still accept jobs. Expose a dedicated health indicator for the mail subsystem with matching alerts rather than tying everything to liveness.

## 19. Circuit Breakers to Stop Piling Requests onto a Failing Provider

A **circuit breaker** temporarily stops calling a provider after repeated prior failures, then lets a few probe requests through to check whether the provider has recovered.

~~~text
           Calls healthy
                |
                v
              CLOSED
                |
        Failures exceed threshold
                |
                v
               OPEN
                |
         Wait open duration
                |
                v
             HALF_OPEN
          +-----+------+
          |            |
       Probe OK      Probe fail
          |            |
          v            v
        CLOSED        OPEN
~~~

### A Circuit Breaker Is Not Evidence of a Notification's Result

If A is OPEN, a new notification with no attempts can route straight to B. However, a notification already **UNKNOWN from attempt A** must remain UNKNOWN; an OPEN breaker says nothing about whether that attempt was accepted by SMTP.

### Do Not Count Every Failure Against Provider Health

For instance, **invalid recipient**, unauthorized sender, invalid template, or opt-out errors do not mean provider A is dead. If those errors trip the circuit breaker OPEN, the system may shift floods of valid traffic to B without fixing the underlying cause.

A classification table:

| Failure | Count toward breaker health? |
| --- | --- |
| Connect refused, network unavailable | Yes |
| Server 5xx from outage, if semantics clear | Maybe |
| Rate limit 429/SMTP throttle | Usually needs dedicated rate limiter/backoff |
| TLS certificate mismatch | Do not auto-failover; alert security/config incident |
| Wrong credentials | Not pure provider health; needs config fix |
| Invalid recipient / hard bounce | No |
| Suppressed by consent | No |
| Message rendering error | No |
| Ambiguous timeout | May contribute to health signal, yet notification stays UNKNOWN |

Counting a timeout toward breaker health **does not mean that same notification is eligible for retry/failover**. Those are two independent decisions.

### Example Using an Abstract Health Gate

~~~java
public interface ProviderHealth {

    boolean canTryNewSubmission(ProviderId provider);
}

public final class HealthAwareBackupEligibility
        implements BackupEligibility {

    private final ProviderHealth health;
    private final ProviderCapabilities capabilities;

    public HealthAwareBackupEligibility(
            ProviderHealth health,
            ProviderCapabilities capabilities
    ) {
        this.health = health;
        this.capabilities = capabilities;
    }

    @Override
    public boolean allowed(
            ProviderId provider,
            MailRouteRequest request
    ) {
        return health.canTryNewSubmission(provider)
                && capabilities.supports(provider, request);
    }
}

public interface ProviderCapabilities {
    boolean supports(ProviderId provider, MailRouteRequest request);
}
~~~

**ProviderHealth** can be backed by a Resilience4j CircuitBreaker, internal state, or provider health metrics. The types above are custom APIs, not library methods. When using Resilience4j, configure exception/result predicates and minimum sample sizes properly; never let invalid recipient errors open a system-wide breaker.

### Half-Open Must Bound Retries

When A moves from OPEN to HALF_OPEN, do not immediately dump an entire backlog of tens of thousands of notifications back onto A. Allow only a small number of probes/new attempts, then ramp traffic up gradually as accepted rates stabilize. This prevents a **retry storm** right as the provider recovers.

## 20. Rate Limiters, Quotas, and Backpressure

A provider can be healthy yet out of **quota** for the current minute or day. Choosing B then may fit policy, provided you throttle to B's actual capacity.

Types of limits you may encounter:

- Messages per second or minute.
- Recipients per second.
- Concurrent connections.
- Messages per SMTP session.
- Limits by account, tenant, sender domain, or region.
- Total email size limits.
- Daily quota or cost budget.

### Backpressure Instead of Trying to Send Everything Immediately

~~~text
Outbox due jobs: 50.000

Provider A quota: 100 messages/second
Provider B quota: 30 messages/second

Router + rate limiters
       |
       +--> A capacity 100/s
       '--> B capacity 30/s

Excess jobs -> REMAIN PENDING/RETRY_WAIT
~~~

If B only has 30 messages/s yet workers scale to 300 threads and shove every attempt through B, the system will keep getting throttled. **Failover does not create infinite quota.**

### Provider B May Have Very Different Rate Limits Than A

A disaster recovery plan should anticipate: does B have enough capacity for all critical emails? If not, apply a **priority policy**:

1. Reserve capacity for SECURITY/TRANSACTIONAL.
2. Pause marketing or send in small batches.
3. Defer non-essential notifications.
4. Tune concurrency based on accepted latency and actual quota.

Ramping up sending must respect suppression and provider retry-after/backoff. Never bulk-update `available_at` to force every job to run at once.

### Use Retry-After When Provided by the Provider

An HTTP provider API may return **429 Too Many Requests** with a `Retry-After` header. SMTP has its own transient replies, though not every provider supports the same retry-hint format. The adapter should normalize **retryAt** or backoff advice when evidenced, and workers should persist retry timestamps per policy.

Do not unconditionally shift A→B when A is rate-limited if doing so violates terms of service, blows past another account's quota, or triggers an unexpected flood of emails.

## 21. Coordinating Retries and Failover Over Time

A strategy can include multiple levels:

~~~text
T0: Notification due
  |
  v
Choose A
  |
  +-- ACCEPTED ------------------------------> DONE
  |
  +-- NOT_ACCEPTED_RETRYABLE, B eligible
  |        |
  |        v
  |      Choose B, at most once in this cycle
  |        |
  |        +-- ACCEPTED ----------------------> DONE
  |        |
  |        +-- NOT_ACCEPTED_RETRYABLE --------> RETRY_WAIT
  |        |
  |        '-- UNKNOWN ----------------------> RECONCILE
  |
  +-- NOT_ACCEPTED_RETRYABLE, B not eligible -> RETRY_WAIT
  |
  +-- NOT_ACCEPTED_PERMANENT ----------------> PERMANENT_FAILED
  |
  '-- UNKNOWN ------------------------------> RECONCILE
~~~

Another attempt can occur after **exponential backoff + jitter** and must re-check health, suppression, message TTL, and quota. Never use just a single `retries=3` counter without defining when provider switching happens, which timeouts are safe, and which outcomes are UNKNOWN.

### Illustrative Timing Policy Example

~~~text
Initial attempt -> A
Safe reject     -> try B if within budget/eligible
Both unavailable -> retry after 30s + jitter
Retry #2         -> pick route by latest health
Retry #3         -> longer backoff
Deadline reached -> DEADLINE_EXPIRED / NEEDS_REVIEW
UNKNOWN          -> do not continue automatic retries
~~~

The timings/attempt values are examples, not Spring Mail defaults. A short-lived OTP email should probably not be retried once the code expires; a receipt may tolerate a longer delay. Check the **business deadline**, not only network policy.

### Do Not Retry When Suppression Has Changed

While A is failing, a newsletter recipient may unsubscribe. Every provider switch or retry must re-invoke **MailDeliveryPolicy**. Provider B must never become a bypass around stored opt-outs, complaints, or hard bounces.

### Do Not Reset Attempt History on Failover

If a notification tried A then B, history must reflect both. Deleting attempt A just because the provider changed makes reconciliation unable to tell whether A ever received the email and raises duplicate-retry risk.

## 22. Failback: Returning to the Primary Provider After Recovery

Failover means choosing B when A is unusable; **failback** means routing new traffic back to A after A recovers.

Do not swing all traffic back to A the instant a single health probe succeeds:

~~~text
A DOWN -> All eligible new traffic to B
         |
       A reports UP once
         |
       Immediate all-to-A
         |
       A throttles again
         |
       All-to-B
       ...
~~~

This oscillation is called **flapping**. Mitigations include:

- Circuit breaker HALF_OPEN for a controlled handful of probes.
- Cooldown period before failback.
- Thresholds/hysteresis: require more success signals to close the breaker.
- Canary: 1%, 5%, 20%, then gradually ramp up.
- Cap throughput ramp rate steadily.
- Keep UNKNOWN notifications on their original route until reconciled.

### Do Not Mutate the Provider of an In-Flight Attempt

During failback, decide routes only for **valid new attempts**. Never overwrite the provider ID of an IN_FLIGHT or UNKNOWN attempt; that record is vital evidence for querying logs/webhooks after the incident.

### Failback Can Put Fresh Pressure on Reputation Signals

When shifting large volumes between providers, DKIM selectors, return-paths, and outbound IP reputation can differ. A may have recovered technically yet not be ready to absorb full traffic or maintain strong delivery reputation immediately. Monitor accepted rates, bounces, and complaints—not only TCP health.

## 23. Sender Domain, SPF, DKIM, and DMARC When Using B

A common outage surprise: provider A accepts mail from **example.test**; provider B also connects over SMTP, yet the sending domain has not been verified there.

Items to prepare before enabling failover:

| Component | Provider A | Provider B | What to verify |
| --- | --- | --- | --- |
| Verified sender domain | Configured | Must be pre-configured | Never send on behalf of unauthorized domains |
| DKIM signing | Selector/key A | Selector/key B | Public DNS and signing work |
| SPF authorization | Route matching A | Route matching B | Avoid accidentally exceeding SPF DNS lookup limits |
| DMARC alignment | From aligned | From must also align | Check SPF/DKIM alignment |
| Bounce/return-path | Domain/subdomain A | Domain/subdomain B | Handle bounces on the right route |
| Feedback loop/webhook | Event pipeline A | Event pipeline B | Sync suppression and statuses |
| Reply-To | Managed mailbox | May be shared | Avoid losing reply messages |

**SPF, DKIM, and DMARC** are not mechanisms `JavaMailSender` enables automatically just from setting a host. They involve DNS domain authentication, outbound mail server policies, and providers. A backup provider must be configured and verified ahead of time—never start adding DNS records mid-incident after mail starts getting rejected.

### Different DKIM Does Not Mean a Message Is Deduplicated

Two providers can sign DKIM with different selectors. Even with identical Subject, Message-ID, and body, a recipient can still receive two messages. DKIM authenticates domain origin/signature; **it does not enforce exactly-once**.

### SPF Has Limits—You Cannot Blindly Add Every Provider

Adding multiple **include:** mechanisms to SPF must respect syntax and standard DNS lookup limits. Never blindly paste every include given by vendors without checking, or SPF can become invalid or end in `permerror`.

### Consistent Transactional Content

Emails received from provider A or B must carry the exact same business facts: order number, amount, reply address, and links from trusted domains. Never let fallback regenerate invoice contents, issue a fresh OTP token, or swap tenant branding without authorization.

## 24. Privacy, Data Residency, and Cross-Provider Suppression

Failing over to provider B means sending email data—potentially addresses, customer names, transactions, and attachments—to a different processor. Technical capability on B is not sufficient authorization to transfer data there.

Policies to verify:

- Is B approved to process the class of data being sent?
- Are data protection agreements and processing scopes in place?
- In which geographic regions does B store/transmit data?
- Are there limits on attachment types or sensitive fields?
- What are retention, deletion, audit, and support-access terms?
- Are webhooks/tracking pixels allowed for this mail type?
- Which tenants are prohibited by contract from using provider B?

### Suppression Cannot Live Only Inside Provider A

Suppose a recipient clicked unsubscribe in a marketing email sent via A; A records the suppression in its own system, yet the application never updates central records. When A fails, the router sends the same marketing email via B, and B has no idea the recipient opted out.

~~~text
Provider A: recipient UNSUBSCRIBED
          |
          X Webhook has not updated app
          |
MailRouter -> Provider B (lacks suppression)
          |
          v
Recipient keeps receiving unwanted marketing
~~~

**Solution:** application-layer delivery policy/suppression acts as a shared gate in front of both A and B, alongside syncing provider events and suppression lists per API contract. Handle duplicate/late webhooks and reconcile when events are missed.

### Do Not Use B to Circumvent Hard Bounces or Complaints

When A records a hard bounce or spam complaint, do not try B hoping the message will "get through." B might still accept the SMTP submission, yet doing so harms deliverability and ignores the recipient's intent or mailbox validity.

Store **suppression reason** explicitly:

~~~text
OPT_OUT
COMPLAINT
HARD_BOUNCE
MANUAL_DO_NOT_CONTACT
INVALID_RECIPIENT
~~~

Reasons have different recovery workflows. A single resubscribe does not automatically clear every suppression caused by complaints or bounces.

### Email Tokens and Secrets in Route Logs

If a notification contains a password reset token or OTP, never log raw MIME bodies, link tokens, SMTP usernames/passwords, provider API bearer tokens, or full recipient addresses. Logs can use opaque notification IDs, attempt IDs, provider IDs, error categories, and durations.

## 25. Multi-Provider Monitoring with Micrometer

A dashboard lets operators see why the system switched to B and whether failover actually improved submission rates.

### Recommended Metrics

| Metric | Type | Meaning |
| --- | --- | --- |
| **mail_provider_attempts** | Counter | Attempt counts by provider/outcome |
| **mail_provider_failover_decisions** | Counter | Allow/deny decisions and reasons |
| **mail_provider_submission_seconds** | Timer | Submission duration by provider |
| **mail_provider_circuit_state** | Gauge | Breaker state CLOSED/OPEN/HALF_OPEN |
| **mail_provider_health_probe_failures** | Counter | Active health probe failures |
| **mail_provider_rate_limited** | Counter | Throttle counts |
| **mail_provider_inflight** | Gauge | Currently executing requests/SMTP attempts |
| **mail_outbox_due** | Gauge | Due jobs not yet processed |
| **mail_outbox_unknown** | Gauge | Jobs with undetermined outcome |
| **mail_provider_reconciliation** | Counter | Reconciliation succeeded/failed/no evidence |
| **mail_provider_webhook_events** | Counter | Accepted/delivered/bounce/complaint per provider |

These are **application-designed metric names**, not built-in Spring Mail metrics. With Prometheus, Counters may be exported with a **_total** suffix and normalized names; inspect the actual metrics endpoint before writing alerts.

### Tags You Should and Should Not Use

Low-cardinality tags:

~~~text
provider=primary|backup
purpose=security|transactional|marketing
outcome=accepted|retryable|permanent|unknown
reason=connect_unavailable|throttled|...
~~~

Do not put **recipient email**, **order ID**, **notification ID**, **message ID**, or raw exception messages into metric labels. High-cardinality data can overload the metrics backend and expose sensitive information.

### Instrumenting Duration

~~~java
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;

public final class MeteredMailProvider implements MailProvider {

    private final MailProvider delegate;
    private final MeterRegistry registry;

    public MeteredMailProvider(
            MailProvider delegate,
            MeterRegistry registry
    ) {
        this.delegate = delegate;
        this.registry = registry;
    }

    @Override
    public ProviderId id() {
        return delegate.id();
    }

    @Override
    public ProviderResult submit(MailSubmission submission) {
        Timer.Sample sample = Timer.start(registry);
        ProviderResult result = null;
        try {
            result = delegate.submit(submission);
            registry.counter(
                    "mail_provider_attempts",
                    "provider", delegate.id().name(),
                    "outcome", result.outcome().name()
            ).increment();
            return result;
        } finally {
            sample.stop(
                    registry.timer(
                            "mail_provider_submission_seconds",
                            "provider", delegate.id().name()
                    )
            );
        }
    }
}
~~~

This is a duration-measurement example, not a complete implementation for exception metrics. If the delegate can throw exceptions, the wrapper must classify errors appropriately before incrementing Counters and ensure outcomes are recorded in attempt history. Never record an ACCEPTED state or assume a send failed without proper classification.

### Alerts Should Reflect Recovery, Not Just "Provider A DOWN"

Examples:

- A breaker OPEN, B healthy: alert **degraded**, though critical notifications can still be processed.
- Both A and B unavailable: trigger critical incident alert by purpose.
- Failover rate climbing, backup quota running low: capacity alert.
- UNKNOWN rising: reconciliation alert, not just SMTP availability.
- Due backlog/oldest age climbing: users are starting to be impacted.
- Provider B webhooks failing: risk of missing bounce/complaint suppressions.

Do not alert solely on one brief health probe failure while ignoring accepted rates and user impact. Conversely, a green provider health check while the outbox fails to drain must still be caught via due backlog and terminal throughput.

### Trace Spans by Boundary

~~~text
mail.dispatch.notification
  |
  +-- mail.policy.check
  |
  +-- mail.route.select
  |
  +-- mail.attempt.persist
  |
  +-- mail.provider.submit (A)
  |
  +-- mail.failover.decide
  |
  '-- mail.provider.submit (B)
~~~

Do not put passwords, OTPs, reset tokens, or raw MIME into span attributes. Traces can include **provider**, **purpose**, **opaque notification ID**, **outcome**, and failure category.

### Late-Arriving Provider Events Must Attach to the Right Attempt

A webhook from A may arrive after the notification has already been retried on B. Event handlers must distinguish **providerMessageId** and provider ID, map to the exact attempt, handle duplicate/out-of-order events, and avoid flipping the entire notification into the wrong state.

A DELIVERED webhook from A when the notification was already ACCEPTED via B can be a sign of duplicate sending or crucial evidence for reconciliation. Do not ignore it merely because "A is currently backup" or because the active route changed.

## 27. Testing the Router with Fake Providers

Unit testing routing must simulate multiple outcomes without connecting to real SMTP servers. The goal is to prove:

- A accepted -> B is not invoked.
- A unreachable **and definitely no submission** -> B is tried if eligible.
- A ambiguous timeout -> B is **not invoked**.
- A permanent recipient failure -> B is not invoked.
- B lacks authorization/capabilities -> B is not tried.
- Recipient is suppressed -> not sent via any provider.
- B accepted -> notification completes, no third attempt.

### Fake Provider Counting Invocations

~~~java
import java.util.concurrent.atomic.AtomicInteger;

public final class FakeMailProvider implements MailProvider {

    private final ProviderId providerId;
    private final ProviderResult result;
    private final AtomicInteger calls = new AtomicInteger();

    public FakeMailProvider(
            ProviderId providerId,
            SubmissionOutcome outcome,
            FailureCategory failureCategory
    ) {
        this.providerId = providerId;
        this.result = new ProviderResult(
                providerId,
                outcome,
                failureCategory,
                null
        );
    }

    @Override
    public ProviderId id() {
        return providerId;
    }

    @Override
    public ProviderResult submit(MailSubmission submission) {
        calls.incrementAndGet();
        return result;
    }

    public int callCount() {
        return calls.get();
    }
}
~~~

Policy must re-check eligibility before failover, because consent can change while connecting to A fails.

## 28. Integration Testing with Two Isolated SMTP Servers

Unit tests show the decision logic is sound, yet multi-provider still depends on wiring **two JavaMailSenderImpl instances** and network transport. For integration tests, use two test SMTP servers running on loopback/container networks.

~~~text
Spring Test Context
        |
        +--> JavaMailSender A --> SMTP fixture A
        |                         - Local mailbox A
        |                         - Dynamic port A
        |
        '--> JavaMailSender B --> SMTP fixture B
                                  - Local mailbox B
                                  - Dynamic port B
~~~

**GreenMail** works well for basic send/capture MIME tests; when you need to simulate SMTP commands, per-stage DATA failures, or detailed TLS/AUTH behaviors, use a project-controlled SMTP test fixture or a server container capable of fault injection. Do not assume every default SMTP catcher can reproduce "server accepted yet response lost" accurately.

### Essential Integration Scenarios

| Test | A | B | Expected |
| --- | --- | --- | --- |
| Normal primary | Healthy | Healthy | Only A receives message |
| A down before connect | Connection refused | Healthy | B receives message if policy permits |
| A accepted | Accepted | Healthy | B does not receive |
| A read timeout after DATA | Possibly accepted | Healthy | B not called automatically, job UNKNOWN |
| A TLS identity mismatch | Security failure | Healthy | Do not bypass policy to B |
| A SMTP AUTH invalid | Config/auth error | Healthy | B not called under conservative policy |
| A provider throttled before accept | Proven rejected | Healthy with quota | B may receive |
| A recipient permanently rejected | Rejected | Healthy | Do not send via B |
| A down, B down | Connection failure | Connection failure | RETRY_WAIT with backoff, no loop |
| A down, B sender unverified | Connection failure | Invalid config | Do not send via B |
| B accepted, app crash before DB commit | Accepted | No third route | Recovery UNKNOWN, no blind retry |
| User unsubscribes after enqueue | A fails | B healthy | Do not send marketing |
| A recovery | Half-open healthy | Healthy | Gradual canary/failback |

### Intentionally Blocking the Primary from Opening a Socket

In a test fixture, you can point provider A to an **unserved loopback port** and confirm connection fails **before sending SMTP DATA**. To test failover end to end, the adapter must explicitly classify that connect failure as proven not accepted.

A fairly durable testing technique is a **fake transport with stage tracking**: only when the client never crossed the connection/SMTP submission threshold does it return NOT_ACCEPTED_RETRYABLE. Never see **MailSendException** and blindly label every nested failure as proven not accepted.

### Fault Injection After DATA

The most critical case:

~~~text
1. Worker sends MAIL FROM and RCPT TO to A
2. Worker finishes sending DATA + end-of-data marker
3. A records message accepted
4. Connection drops before client receives final response
5. Adapter returns UNKNOWN
6. Router does not call B
7. Reconciler looks for acceptance evidence on A
~~~

If the fixture can prove A accepted while the client lost the acknowledgement, this test catches **failover-induced duplicate sends**. A mock throwing an exception before creating an external side effect is not enough to test that scenario.

### Do Not Use Real Email Accounts

Integration tests should use:

- SMTP fixtures that do not relay to the Internet.
- Recipients in test domains.
- Test-only usernames/passwords.
- Dynamic hosts/ports injected into the Spring test context.
- Test TLS certificates/truststores when testing STARTTLS/SMTPS.
- Post-test cleanup of mailboxes/fixtures so tests do not read each other's messages.

Never use production SMTP to simulate failover, as it can send real emails, consume quota, hurt sender reputation, or leak user data.

### Verify Selected Content During Failover Too

If provider B succeeds, tests should not merely count messages—also check:

- Subject, recipient, and verified From.
- Template version and business content match the original logical notification.
- Corresponding HTML/plain parts and attachments.
- No new OTP/token generated simply because the provider changed.
- Correlation ID allows tracing the attempt.
- Outbox record reaches ACCEPTED only once.

Do not compare raw MIME byte-for-byte when Message-ID, header folding, or multipart boundaries are auto-generated; use a parser to check meaningful content and structure.

## 29. Runbook When the Primary Provider Fails

When the system alerts **provider A degraded/down**, do not immediately flip all jobs to B. Identify the failure type, which notifications already have attempts, and whether provider B can handle those mail categories.

### Step 1 — Verify Symptoms

Check:

- Accepted, rejected, UNKNOWN rates, and latency on A.
- Whether failures are TCP connect, DNS, TLS, AUTH, provider quota, or business validation.
- Circuit breaker state and when it moved to OPEN.
- Any recent deploys, secret rotations, DNS updates, or policy changes.
- SMTP status page/API and affected region/account scope.
- Outbox due backlog, oldest due age, and affected notification types.

If A returns **authentication failed** after secret rotation, shifting everything to B can mask a misconfiguration and leave a security issue unresolved. Find root cause before broadening route policies.

### Step 2 — Confirm Provider B Is Eligible

Check independently:

~~~text
B account enabled?
B sender domain verified?
B DKIM/DMARC alignment suitable?
B TLS/auth configuration valid?
B accepts required MIME/attachments?
B quota + concurrency sufficient?
B allowed for affected tenant/purpose/region?
B suppression and webhook sync working?
~~~

**A passing TCP health check is not enough.** Ensure B is ready for production requirements and privacy rules.

### Step 3 — Classify Jobs by State

| Group | Switch immediately to B? |
| --- | --- |
| **PENDING, no attempts yet** | Can select B if B is eligible |
| **RETRY_WAIT with proof of non-acceptance** | Can follow policy/backoff |
| **IN_FLIGHT A** | Do not mutate route of an in-flight attempt |
| **UNKNOWN A** | Not automatically; must reconcile |
| **ACCEPTED A** | Do not resend |
| **PERMANENT_FAILED recipient** | Do not bypass via B |
| **SUPPRESSED** | Do not send |
| **CANCELLED** | Do not send |

An incident usually involves multiple groups simultaneously. Never run a blanket **UPDATE provider='backup' WHERE status <> 'ACCEPTED'**.

### Step 4 — Choose How to Fail Over

If A is clearly unreachable and B is approved, you can:

1. Open policy routing **new PENDING notifications** to B.
2. For attempts already proven NOT_ACCEPTED_RETRYABLE, allow B within quota/backoff.
3. Keep UNKNOWN in reconciliation-required state.
4. Leave SUPPRESSED, PERMANENT_FAILED, or ACCEPTED jobs untouched.
5. Cap throughput to provider B and prioritize essential emails.

Record **operator, timestamp, reason, and tenant/purpose scope** of route changes if done manually. When policy decides automatically, record the corresponding reason code in attempt history/logs.

### Step 5 — Observe After Failover

Monitor:

- Whether B's accepted rate increases as expected.
- Whether due backlog/oldest age for transactional/security mail drops.
- Whether B begins rate-limiting or rejecting sender identities.
- Whether UNKNOWN outcomes appear on B.
- Whether bounces/complaints/suppressions update via B.
- Any signs of duplicates or multiple emails for the same notification.

Do not declare "recovered" solely because B's health=UP. Confirm **critical notifications are actually being accepted promptly** and the backlog is draining in a controlled way.

### Step 6 — Partial Failback

When A recovers:

- Verify TLS/AUTH/sender identity and accepted rates.
- Route a small fraction of **new eligible notifications** back to A.
- Gradually increase percentage as outcomes stabilize.
- Never replay UNKNOWN or ACCEPTED from A/B.
- Reconcile all unresolved attempts before closing the incident.

### Step 7 — Postmortem

Document:

- Root cause and outage duration.
- How many notifications were delayed/unsent, broken down by purpose.
- How many attempts went through B, and whether throttling or bounces occurred.
- How many UNKNOWN outcomes occurred and how they were reconciled.
- Whether any duplicates or suppression violations occurred.
- Whether capacity, health checks, or route policies need changes.
- Which integration/fault-injection tests should be added to prevent recurrence.

## 30. Common Implementation Mistakes

### Mistake 1 — Catching MailException and Unconditionally Calling B

~~~java
try {
    primaryMailSender.send(message);
} catch (MailException ex) {
    backupMailSender.send(message);
}
~~~

**Problem:** the exception may happen after A already accepted; sending via B can create duplicates. **Fix:** classify outcomes by evidence; UNKNOWN never fails over automatically.

### Mistake 2 — Assuming an SMTP Timeout Means the Message Never Reached the Server

A read timeout after DATA can occur when the server already queued the message yet the response was lost.

**Fix:** record UNKNOWN and reconcile or make an audited risk decision.

### Mistake 3 — Sending the Same Notification to Two Providers in Parallel

Sending in parallel just to "use whichever provider is faster" can cause both to deliver.

**Fix:** one logical notification has only one active attempt via claim/lease, pick the route before submitting; never hedge SMTP.

### Mistake 4 — Relying on the Same Message-ID for Global Deduplication

SMTP does not require providers to drop messages sharing a Message-ID.

**Fix:** keep Message-ID/correlation for lookup, not as an exactly-once contract.

### Mistake 5 — Treating SMTP AUTH/TLS Errors as Ordinary Provider Outages

Switching to B can mask wrong secrets, truststores, or hostnames.

**Fix:** classify as CONFIGURATION/TLS_SECURITY and alert; never automatically downgrade security to push mail out.

### Mistake 6 — Provider B Lacks Domain Verification

B connects fine, yet DKIM/DMARC fails alignment or the provider rejects From.

**Fix:** prepare sender identities, DNS, TLS, and quotas in advance; test periodically.

### Mistake 7 — Using One JavaMailSenderImpl and Calling setHost per Request

Under concurrent threads, the sender gets mutated mid-attempt.

**Fix:** create separate beans/adapters so each provider keeps stable configuration.

### Mistake 8 — Bypassing Suppression When Switching Providers

Recipient opt-out is stored at provider A while B has not received the webhook/suppression.

**Fix:** shared policy/suppression in the application; sync and reconcile provider events.

### Mistake 9 — Using Provider B to Bypass Hard Bounces

A mailbox flagged as hard bounce by A does not magically become valid when tried on B.

**Fix:** classify recipient failures; never use failover to evade suppression.

### Mistake 10 — Exceeding B's Concurrency Limits

B has lower quotas than A and gets hit with continuous rate limits.

**Fix:** rate limiters, backpressure, purpose-based priority, and attempt caps.

### Mistake 11 — Opening the Circuit Breaker on Invalid Recipients

Recipient errors do not reflect overall provider health.

**Fix:** feed only appropriate failure categories into breaker metrics.

### Mistake 12 — Switching 100% of Traffic Back the Instant A Recovers

A gets overloaded again, causing flapping.

**Fix:** half-open, canary, hysteresis, gradual ramp-up.

### Mistake 13 — Not Recording Provider ID on the Attempt

When webhooks arrive or investigation is needed, you cannot tell whether to check A or B.

**Fix:** persist provider, attempt ID, correlation ID, timestamps, outcome, and provider message ID when available.

### Mistake 14 — Creating a New notification_key on Failover

Two attempts look like two separate business notifications, breaking deduplication.

**Fix:** one stable notification key, multiple attempt IDs.

### Mistake 15 — Checking Health Only When Creating a Campaign

By the time workers send, B's quota or sender capability may have changed.

**Fix:** check health/capability at route-selection time, honoring deadlines, rate limits, and current policies.

### Mistake 16 — Treating SMTP Accepted as Delivered

Even when B's SMTP returns success, the mailbox can still bounce or filter to spam.

**Fix:** track provider delivery events separately; never conflate ACCEPTED with DELIVERED.

### Mistake 17 — Sending PII to an Unapproved Vendor

Technical failover can violate data residency or data agreements.

**Fix:** enforce provider allowlists by tenant/purpose/data class; verify governance before enabling routes.

### Mistake 18 — Never Testing the Backup Until A Fails

B's credentials have expired or TLS certificates/hostnames do not match.

**Fix:** safe probes, isolated smoke tests, canaries, or bounded periodic checks.

### Mistake 19 — Retrying UNKNOWN on Worker Restart

After a crash, the outbox still shows IN_FLIGHT or UNKNOWN, so the system resends via B.

**Fix:** recover via UNKNOWN/reconciliation and fencing; never treat lease expiry as not-sent.

### Mistake 20 — Failing to Separate Policy Errors from Provider Errors

An invalid template or unauthorized recipient gets retried across both A and B.

**Fix:** validate content/recipient/sender and authorization before routing; never fail over on shared message errors.

## 31. Practice Scenarios on Selecting a Backup Provider

### Scenario A — Unable to Open TCP Connection to Provider A

Connection is refused immediately when opening the socket; no SMTP session existed and no message was submitted.

**Question:** can you try B?

**Answer:** yes, if the error is conclusively **NOT_ACCEPTED_RETRYABLE**, B has sufficient health/capabilities, the recipient is still eligible, and rate limits/attempt budget permit. Record attempt A then try B without creating a new notification.

### Scenario B — Read Timeout After Client Sent DATA

SMTP server A may have accepted the message, yet the client never received the final 250.

**Question:** should you automatically send via B?

**Answer:** no. Record UNKNOWN, keep provider A in attempt history, and seek evidence in logs/provider APIs when available; do not switch to B just because A is now unhealthy.

### Scenario C — Provider A Returns Wrong Password

SMTP AUTH fails because the secret was just rotated.

**Question:** is this a signal to fail all jobs over to B?

**Answer:** not by default. This is a configuration/authentication error; alert and fix the secret. If the organization has a manual disaster recovery policy already authorizing B for new notifications, that is a scoped operational decision, not a catch-all retry for attempts with unknown outcomes.

### Scenario D — Provider A Throttles, B Has Quota

A returns an explicit throttling error before accepting submission; B has been verified and has remaining quota.

**Question:** can you fail over?

**Answer:** possibly per policy if the outcome is proven NOT_ACCEPTED_RETRYABLE and retry/attempt limits, suppression, and provider contracts permit. Do not treat every transient error as rejected before submission.

### Scenario E — B Has Not Signed DKIM for the From Domain

B's health is UP and it accepts SMTP AUTH, yet the sending domain is unverified.

**Question:** can critical mail be sent through B?

**Answer:** do not bypass sender identity. Domain and DNS must be pre-configured, or use an approved verified sender identity per policy. A TCP health check is not enough.

### Scenario F — Recipient Unsubscribed from Newsletter

A marketing notification has been in the outbox since yesterday; A is down and B is healthy.

**Question:** should marketing fail over to B?

**Answer:** no if the recipient is no longer eligible. The shared delivery policy must be checked before every attempt, independent of route.

### Scenario G — A Accepted Before Worker Crash

A sent SMTP 250, the worker died before UPDATE ACCEPTED, and the lease expired.

**Question:** can the job move immediately to B?

**Answer:** no. Recovery marks UNKNOWN or a reconciliation state per policy, looks for acceptance evidence, and prevents duplicates.

### Scenario H — B Shares A's Provider Group, Different Hostname

A and B are two endpoints sharing one control plane, the same quota, and the same region.

**Question:** is this an independent backup?

**Answer:** it may cover only certain endpoint failures, not necessarily a control-plane or quota outage. Threat-model shared dependencies and test correlated failure modes.

### Scenario I — Provider A Returns Accepted, Minutes Later Webhook Reports Bounce

The mailbox rejected the mail even though SMTP accepted it.

**Question:** automatically resend through B?

**Answer:** not as a submission failover. A bounce is a separate delivery event; classify and handle it under recipient/delivery policy. Sending via B may not help or may distribute unwanted mail.

### Scenario J — A's Circuit Breaker Is OPEN

A new notification has no attempts yet; calls to A are currently paused, and B is authorized and healthy.

**Question:** must you try A once before going to B?

**Answer:** not necessarily. Initial routing can select B straight away. However, prior UNKNOWN notifications on A must still be reconciled and never automatically rerouted.

### Scenario K — A's Circuit Breaker Is HALF_OPEN

A begins recovering and one probe succeeded.

**Question:** should you push 100% of the backlog back to A immediately?

**Answer:** no. Use canary/ramp-up while watching errors, latency, quota, and accepted rate. Avoid flapping or retry storms.

### Scenario L — OTP Email Expires While Waiting

A is down and B has quota, yet the notification's OTP code has already expired.

**Question:** should you fail over and send the old code?

**Answer:** usually pointless. Enforce business deadlines; when the user requests a new code, create a new event with its own token and policy rather than using retries to silently mint a new OTP under the same notification key.

### Scenario M — Same Message-ID Across A and B

Both providers accept a message bearing the same Message-ID.

**Question:** is there a universal protocol mechanism forcing the mailbox to keep only one copy?

**Answer:** no. Message-ID aids correlation/threading; it is not an across-provider idempotency guarantee.

### Scenario N — Provider A's API Has Idempotency-Key

A supports an HTTP API with documented idempotency. The first request times out, and B is another vendor.

**Question:** is sending the same Idempotency-Key to B safe?

**Answer:** not by default. A's idempotency normally applies only inside A. Query A's status or obtain proof A did not accept before sending to B.

### Scenario O — Application Has Three Worker Replicas

Three workers read the same PENDING notification simultaneously and each chooses a provider.

**Question:** how do you prevent duplicate sends?

**Answer:** atomic claim/lease with transactions and fencing, never SELECT-then-send without owning the job. A router alone is not enough.

### Scenario P — Provider B Has Storage Region Restrictions

Tenant X requires email processing within a specific region, while B uses out-of-region infrastructure.

**Question:** can B be used during a major outage on A?

**Answer:** only if data policies/contracts/authorizations permit. If B is ineligible, hold the job or invoke an approved procedure; speed never overrides privacy obligations.

### Scenario Q — Provider B Fails AUTH

A had a proven pre-send connect failure; B turns out to have wrong credentials.

**Question:** should you immediately bounce back to A and loop forever?

**Answer:** no. Classify B's failure, cap attempts, audit, alert on configuration, and wait for recovery. Never loop A→B→A indefinitely.

### Scenario R — Backup Receives Mail Yet Lacks Bounce Webhooks

B returns SMTP accepted and the outbox dashboard shows ACCEPTED, yet the provider event pipeline is unconfigured.

**Question:** can you declare deliverability fully covered?

**Answer:** not yet. Integrate bounce/complaint/suppression events for B or explicitly document the observability gap; do not infer delivered from accepted.

### Scenario S — User Clicks "Resend Confirmation Email"

The prior notification was ACCEPTED and the user actively requested another send.

**Question:** should you trigger failover on the old notification?

**Answer:** no. This is an **intentional resend** and should normally create a new notification with its own business event/key linked to the original notification. Rate limits, consent, and identity policies still apply.

### Scenario T — Metrics Show 100% Failover Yet Low Inbox Rate

B accepts SMTP submissions, yet bounces/spam placement rise.

**Question:** is watching HTTP/SMTP 2xx enough?

**Answer:** no. Monitor bounces, complaints, delivery events, and sender reputation; switching providers solves only part of the sending pipeline.

## 32. Checklist for Deploying Multi-Provider Failover

Before enabling failover in production, the team can verify the following items:

### Business and Data

- A **notification key** stable per business event exists.
- Recipient/purpose/tenant pass authorization and suppression checks before sending.
- Template/payload remain stable across attempts; no new tokens or invoices are generated during retries.
- Appropriate deadlines exist for OTP, security, transactional, and marketing.
- Provider B is approved to handle the data per tenant/region/data class.

### Sending Infrastructure

- A and B have separate beans/adapters, separate credentials, and TLS/hostname verification.
- Verified sender identities and SPF/DKIM/DMARC are prepared for B.
- Size limits, attachments, and MIME capabilities have been verified.
- Rate limits/quotas and provider webhooks work for both.
- The backup is probed/canaried periodically in a safe manner.
- Shared network/DNS/region dependencies have been evaluated.

### Route Decisions

- Outcomes are classified as **ACCEPTED / NOT_ACCEPTED_RETRYABLE / NOT_ACCEPTED_PERMANENT / UNKNOWN**.
- UNKNOWN never fails over automatically.
- Only failures with evidence of non-acceptance and policy approval fail over.
- Circuit breakers are never opened by invalid recipients or content errors.
- Provider health, quota, capabilities, and sender policies are checked during route selection.
- Attempt limits, backoff, jitter, and anti-ping-pong protections are in place.
- Gradual failback is implemented to avoid flapping.

### Outbox and Operations

- Workers claim notifications atomically with leases/fencing tokens.
- Attempt history stores provider ID, outcome, timestamps, and correlation.
- Crashes/expired leases transition through UNKNOWN when outcomes are ambiguous.
- Reconciliation with providers exists where supported, plus manual review when evidence is lacking.
- Dashboards show accepted, retryable, unknown, due backlog, quota, and provider health.
- Runbooks enable audited rollbacks/route changes without bulk-resetting states.
- Integration tests cover safe failover, ambiguous timeouts, duplicate prevention, sender identity, and suppression.

Even a fully checked list does not prove the system achieves exactly-once delivery; that requires external provider contracts or explicit business tradeoffs. The checklist reduces design bugs that easily cause **duplicate sends, lost emails, or wrong recipient permissions**.

## 34. Principles to Remember

~~~text
Primary down                      != every notification can go to backup
Provider health UP                != sender/tenant/purpose are all valid
MailException                     != definitely not sent
SMTP 250 accepted                 != email reached the Inbox
Timeout after DATA                -> UNKNOWN
UNKNOWN                           -> reconciliation, no auto failover
Same Message-ID                   != cross-provider deduplication
Provider A idempotency key        != provider B idempotency
Circuit breaker OPEN              != proof the previous attempt failed
Verified sender A                 != verified sender B
Recipient opt-out                 -> do not send via A or B
Provider B rate limit             -> must apply backpressure, no retry storm
Outbox UNIQUE + atomic claim      -> reduces logical duplicates
Outbox and fencing                != exactly-once external SMTP
Failback                          -> canary, hysteresis, no blind route flipping
~~~

**Selecting a fallback provider when the primary provider fails** is a decision combining **business eligibility**, **provider capabilities**, **transport outcomes**, **health/circuit breakers**, **quotas**, and **reconciliation capability**. In Spring Framework Mail, you can configure two **JavaMailSenderImpl** instances and route through separate adapters, yet choosing B must occur under policy rather than inside a blanket catch block for every `MailException`. When A clearly has not accepted the message, failover can keep critical notifications flowing. When the outcome via A is unclear, the **UNKNOWN** state and reconciliation form the guardrail against duplicates. A resilient multi-provider design needs an outbox/attempt history, sending-permission controls, DNS authentication, shared suppression, per-provider observability, and controlled failback—while acknowledging SMTP's limits instead of promising an exactly-once delivery guarantee the protocol does not offer.
