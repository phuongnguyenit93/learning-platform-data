# Storing Message IDs and Processing State

## 1. Why Does a Mail-Receiving Application Need to Remember How Far It Has Processed?

In a system using **Spring Framework Mail**, we usually know `JavaMailSender` for **sending** emails via SMTP. However, many applications also need to **receive emails** from customer support mailboxes, reply mailboxes, reconciliation mailboxes, email-submitted registrations, or DSN/bounce handling systems.

Examples:

- A customer sends an email to `support@example.com`, and the application creates a ticket.
- The system receives a reply to an order email and attaches it to the prior order.
- A mailbox automatically receives partner reports, extracts data, and stores it in a database.
- A bounce address receives delivery failure notices to update delivery status.

The application typically **polls** a mailbox via IMAP, receives webhooks from a provider, or consumes events from an inbound email gateway. In all of these approaches, **an email can be observed more than once**:

- The poller restarts and reads the same email again.
- A consumer crashes between saving the ticket and recording the email as processed.
- A webhook is resent by the provider due to a request timeout.
- A worker runs slowly, causing its lease to expire and another worker to pick up the same job.
- A user moves a message between folders, changing its IMAP ID.
- A mailbox is restored/migrated, changing `UIDVALIDITY` or server-assigned IDs.

If you rely solely on `message.getSubject()` or the mailbox's `SEEN` status to determine what has been processed, the system can create duplicate tickets, skip unprocessed messages, or lose the ability to recover after failures.

**Goal:** Persist an appropriate identifier for each received email, track processing state across polls/worker restarts, and make business operations **idempotent** so a single message never triggers unintended duplicate side effects.

~~~text
Mailbox / inbound provider
           |
           v
    Fetch message metadata
           |
           v
  Establish mailbox-scoped identity
    (IMAP UID / UIDVALIDITY)
           |
           v
    Persist discovery record
           |
           v
         Work queue
           |
           v
 Claim + parse + validate + process
           |
        +--+----------------+----------------+
        |                   |                |
        v                   v                v
    PROCESSED             RETRY           FAILED
        |                   |                |
        v                   v                v
 Business effect      Next attempt    Review / dead letter
        |
        v
   Audit + metrics
~~~

> **Boundary to remember:** Spring Framework Mail primarily provides sending APIs (`JavaMailSender`). Reading IMAP/POP3, storing cursors, parsing MIME, handling inbound webhooks, and persisting state/idempotency typically use **Jakarta Mail** alongside application-built services, repositories, and workers; they do not materialize automatically from `spring-boot-starter-mail`.

## 2. Distinguishing the Types of IDs Related to an Email

"Message ID" is not just one thing. At minimum, separate these concepts:

| Identifier | Issued By? | Scope / Characteristics | What Is It Used For? |
| --- | --- | --- | --- |
| **RFC `Message-ID` header** | Sender / sending library, per email format | Can be missing, duplicated, or spoofed | Thread linking, tracing original email, secondary correlation |
| **IMAP UID** | IMAP server | Meaningful only within **one mailbox/folder with the same `UIDVALIDITY`** | Identifying message entries on the server, incremental sync |
| **IMAP `UIDVALIDITY`** | IMAP server | Marks the "generation" of UIDs in a folder | Detecting when old UIDs are no longer valid |
| **IMAP message sequence number** | Current folder state | Can shift when messages are deleted/expunged | Session-local access only; **not a durable key** |
| **POP3 UIDL** | POP3 server if supported | Token identifying a message across sessions, scoped per mailbox/server | Preventing re-reads in the POP3 model |
| **Provider inbound event ID** | Provider / gateway | Per provider contract | Deduplicating webhook/event deliveries |
| **Application `inboundMessageId`** | Application's database | Internal UUID/ID, immutable | Primary key, processing state, auditing |
| **`In-Reply-To` / `References`** | Headers created by mail clients | References `Message-ID`s of prior emails | Threading/correlation, not the current email's UID |

A solid design typically has **two layers of identity**:

1. **Source identity:** a key identifying an email as observed at a specific source, e.g., `(mailbox_id, folder_key, uid_validity, uid)`.
2. **Internal identity:** `inbound_message.id` (UUID) generated by the application and used across all business/log/attempt tables.

The `Message-ID` header should be **stored as metadata and for correlation**, not assumed to be a globally unique key for all inbound emails.

### 2.1. RFC Message-ID Is a Header, Not an Unconditionally Trusted Database Key

An email might contain:

~~~text
From: customer@example.net
To: support@example.com
Subject: I need support
Date: Thu, 12 Nov 2026 10:00:00 +0700
Message-ID: <request.20261112.abc123@example.net>
~~~

`Message-ID` was designed as a message identifier under Internet Message Format (RFC 5322), and standard sending software tries to generate sufficiently unique values. Yet at the **mail-receiving boundary**, never assume:

- Every email has a `Message-ID`.
- The header is always syntactically valid.
- Two different emails can never share the same `Message-ID`.
- The sender-declared value is trustworthy or authorized to touch internal data.
- The header will be preserved untouched across all gateways, forwards, or imports.

An attacker can craft a message with a `Message-ID` matching an older message. If a schema puts `UNIQUE(message_id)` system-wide and drops later arrivals, legitimate users can lose emails or attackers can disrupt processing.

### 2.2. IMAP UIDs Are Only Durable Within the Right Scope

Suppose there are two folders:

~~~text
Mailbox: support@example.com
  INBOX:
    UIDVALIDITY = 1710000000
    UID 1200 -> message A

  Processed:
    UIDVALIDITY = 1710000500
    UID 1200 -> message B
~~~

Two UIDs equal to `1200` do not prove both records are the same email. Even in the **same folder**, when `UIDVALIDITY` changes, old UIDs can no longer serve as stable keys.

Therefore, the recommended IMAP key is:

~~~text
(mailbox_id, folder_key, uid_validity, uid)
~~~

`mailbox_id` must be a **managed internal** account/mailbox source identifier, not merely a display email string that could collide across environments. `folder_key` is a canonical folder key per account/server, consistent with your system's namespace rules.

### 2.3. Sequence Numbers Must Never Be Used as Checkpoints

In IMAP, `Message.getMessageNumber()` is the ordinal position in the folder at one moment. After messages are expunged, the positions of remaining messages can shift.

~~~text
Before expunge: seq=1(A), seq=2(B), seq=3(C)
Delete + expunge A
After expunge:  seq=1(B), seq=2(C)
~~~

If you store "processed up to `messageNumber=2`", the next poll may skip C or process the wrong item. Use UID and `UIDVALIDITY` when supported by the IMAP server, never sequence numbers as database keys.

### 2.4. Provider ID and Message-ID Are Not the Same

An inbound email provider may send:

~~~json
{
  "eventId": "evt-5e2f...",
  "providerMessageId": "msg-a490...",
  "headers": {
    "Message-ID": "<request.abc@example.net>"
  }
}
~~~

`eventId` typically represents the **event delivery**; `providerMessageId` represents the message in the provider's system; the `Message-ID` header is declared by the email sender. Rely on the provider's exact contract to define deduplication keys. Never conflate all three fields into an ambiguous `messageId`.

## 3. Two Scenarios That Can Drop Messages or Create Duplicates

### 3.1. Using Message-ID as a System-Wide UNIQUE Key

Suppose a customer sends two distinct emails, but a buggy mail client reuses the same header:

~~~text
Email #1:
  IMAP UID=501
  Message-ID=<same-id@example.net>
  Body="I want to change my address."

Email #2:
  IMAP UID=502
  Message-ID=<same-id@example.net>
  Body="I want to cancel my order."
~~~

If code executes:

~~~sql
INSERT INTO inbound_message(message_id, body)
VALUES (:message_id, :body)
ON CONFLICT (message_id) DO NOTHING;
~~~

Email #2 may be dropped. For IMAP sources, identify each entry by `mailbox_id/folder/uid_validity/uid` and store RFC `Message-ID` as **non-unique, indexed metadata**.

### 3.2. Relying on the SEEN Flag as Proof of Processing

Suppose:

~~~text
Poller opens email
  |
  v
Marks message SEEN
  |
  v
Process crashes before saving ticket
  |
  v
Next poll searches UNSEEN only
  |
  v
Message is skipped forever
~~~

IMAP's `\\Seen` reflects mailbox display/read status, not an application transaction commit. Staff mail clients can also set `SEEN`, or servers/libraries may alter flags during reads.

To persist processing state, use an **internal database/outbox** and use IMAP flags only as secondary signals or user-facing workflows when truly needed.

### 3.3. Distinguish "Discovered" and "Processed"

An email that has been discovered but not yet processed may sit in the database as:

~~~text
id = 9ad...
source = IMAP
mailbox_id = support-vn
folder_key = INBOX
uid_validity = 1710000000
uid = 501
rfc_message_id = <same-id@example.net>
status = DISCOVERED
~~~

After the worker creates the ticket and commits state:

~~~text
status = PROCESSED
processed_at = ...
ticket_id = ...
~~~

The two steps must not be collapsed into a single "read" marker on the IMAP server.

## 4. Defining the Processing State Lifecycle

An inbound workflow can use:

| State | Meaning | May a Worker Pick It Up? |
| --- | --- | --- |
| `DISCOVERED` | Metadata/mail source durably recorded | Yes, when eligible |
| `FETCHED` (optional) | Content downloaded/snapshotted to internal storage | Yes |
| `PROCESSING` | Worker holds claim/lease | Do not reclaim while lease is valid |
| `RETRY` | Recoverable error; next attempt scheduled | Yes, when `next_attempt_at` is due |
| `PROCESSED` | Defined business side effects committed | Do not reprocess automatically |
| `IGNORED` | Intentionally skipped per rule, with reason | No |
| `FAILED` | Automatic retries halted; awaiting triage/dead letter | No |
| `QUARANTINED` | Suspicious content / failed security checks | Not for normal handlers |
| `UNKNOWN` (optional) | External task outcome unclear | Needs reconciliation |

A state diagram:

~~~text
DISCOVERED ---> FETCHED (optional)
     |               |
     +-------+-------+
             |
             v
         PROCESSING
             |
     +-------+----------+---------------+--------------+
     |                  |               |              |
     v                  v               v              v
 PROCESSED            RETRY           FAILED        IGNORED
                        |               |
                        |               v
                        |          Operator triage
                        |               |
                        +-- next due <--+  (approved redrive)

Any suspicious input -> QUARANTINED
Ambiguous external side effect -> UNKNOWN/reconciliation
~~~

### 4.1. "Processed" Must Have a Concrete Meaning

Depending on business logic:

- Support email: ticket created and linked to the inbound message.
- Invoice email: data parsed, validated, and persisted to the system.
- Reply email: comment/reply attached to the conversation.
- DSN/bounce: event normalized, correlated, and delivery state updated per policy.

Never mark `PROCESSED` merely because `getContent()` did not throw an exception, as that is only MIME reading/parsing. Conversely, intentionally skipped spam can be marked `IGNORED` rather than pretending to be a processed ticket.

### 4.2. Terminal State Does Not Mean the Email Was Deleted

`PROCESSED` and `FAILED` in the database are internal business states. The original email may stay in `INBOX` or be moved to another folder depending on retention/workflow. Moving/deleting on IMAP should not be the sole step deciding processing completion.

### 4.3. Retry Count Tracks Business Attempts

A clear model:

~~~text
attempt_count = 0  no worker has claimed yet
attempt_count = 1  first processing attempt started
attempt_count = 2  first retry started
...
~~~

If `attempt_count` is only incremented inside `catch(Exception)`, crashes before `catch` lose attempt history. Increment inside the **claim transaction** and keep separate attempt events when auditing is required.

## 5. Ingestion Architecture: Discovery and Processing Are Separate Steps

For IMAP, an architecture can split into:

~~~text
IMAP server
   |
   | Poll/read UID metadata
   v
Mailbox sync worker
   |
   +--> Compare UIDVALIDITY
   +--> Discover new UIDs
   +--> Insert inbound_message rows (idempotent)
   +--> Commit sync cursor only after inserts
   |
   v
Durable database / queue
   |
   v
Processing worker
   |
   +--> Atomically claim a row
   +--> Load/snapshot MIME content
   +--> Validate sender/content/attachments
   +--> Apply business handler
   +--> Commit outcome
   |
   v
Business database / event outbox
   |
   v
Optional IMAP mark/move + downstream actions
~~~

Benefits:

- The poller only discovers and durably persists new emails without letting one huge attachment stall the entire folder.
- Processing workers can retry independently of polling.
- An email with the same UID may be observed multiple times, yet creates only **one record** thanks to the unique constraint.
- After restarts, `DISCOVERED`, `RETRY`, and lease-expired `PROCESSING` rows can resume smoothly.
- The checkpoint reflects **safe discovery progress**, without pretending every email before the cursor is `PROCESSED`.

### 5.1. Discovery Cursor Differs from Processing Checkpoint

Suppose at one moment:

~~~text
IMAP UID 701 -> PROCESSED
IMAP UID 702 -> RETRY (timeout)
IMAP UID 703 -> PROCESSED
IMAP UID 704 -> DISCOVERED

last_discovered_uid = 704
~~~

This is a valid state. The poller has saved emails up to UID 704, while workers have not finished 702 and 704 yet. **You cannot use `last_discovered_uid=704` to conclude all emails ≤704 are complete.**

Processing state and attempt history must be attached to each inbound row. With only a single "last processed UID" number, one failed email in the middle forces a choice between re-reading everything or skipping unprocessed messages.

### 5.2. When Should Content Be Snapshotted?

There are two options:

| Option | Pros | Risks |
| --- | --- | --- |
| **Store metadata + IMAP UID**, worker fetches MIME when processing | Less internal storage, fast discovery | Email may be deleted/moved before worker fetches; prolonged IMAP dependency |
| **Store MIME/parsed payload snapshot** in durable storage before worker processing | Can retry even if IMAP folder changes | Uses storage, holds PII/attachments, requires quotas, encryption, retention |

If the application must guarantee every accepted email can be processed even if staff delete/move messages, consider snapshotting payloads. If using only UIDs, define a `SOURCE_MISSING` state when the source becomes unreadable along with an investigation workflow; **never mark `PROCESSED`** to gloss over the error.

For snapshots, you do not have to store raw emails inside a database column. Store MIME as an object in dedicated storage and keep only `payload_ref`, checksum, size, and tenant/retention metadata in the DB. Ordering must ensure the object is durably written before the processing record references it, with a reconciler for orphan objects if the DB transaction fails.

### 5.3. One Email Triggering Multiple Independent Workflows

If an email must both create a ticket and update analytics reports, do not collapse both into one ambiguous flag. You can use:

~~~text
inbound_message (message identity + snapshot)
    |
    +--> inbound_workflow_state(type="TICKET")
    |       DISCOVERED -> PROCESSING -> PROCESSED
    |
    +--> inbound_workflow_state(type="ANALYTICS")
            DISCOVERED -> PROCESSING -> RETRY
~~~

Each workflow has a unique key `(inbound_message_id, workflow_type)` and its own attempt history. For small systems with a single inbound handler, one status on `inbound_message` may suffice; choose your schema to match business needs.

## 6. PostgreSQL Schema for Message Identity and State

A clean design covers **source mailbox**, **sync cursor**, **discovered emails**, and **attempt history**. The SQL below illustrates a single-workflow IMAP model; real applications may add tenant tables, data retention, encrypted payload references, and ownership.

### 6.1. Source Mailbox Identity

~~~sql
CREATE TABLE inbound_mailbox (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    logical_name VARCHAR(120) NOT NULL,
    source_type VARCHAR(30) NOT NULL DEFAULT 'IMAP',
    account_ref VARCHAR(200) NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(tenant_id, logical_name)
);
~~~

`account_ref` is a system-managed configuration/secret reference; **never store IMAP passwords** in this table. A display address like `support@example.com` may exist across multiple environments or switch providers; mailbox `id` keeps identity unambiguous.

### 6.2. Per-Folder Sync Cursor

~~~sql
CREATE TABLE inbound_mailbox_cursor (
    mailbox_id UUID NOT NULL REFERENCES inbound_mailbox(id),
    folder_key VARCHAR(250) NOT NULL,
    uid_validity BIGINT,
    last_discovered_uid BIGINT NOT NULL DEFAULT 0,
    last_successful_scan_at TIMESTAMPTZ,
    last_error_code VARCHAR(100),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY(mailbox_id, folder_key)
);
~~~

Meaning:

- `uid_validity`: current UID generation of the folder.
- `last_discovered_uid`: upper bound of UIDs **successfully scanned and identity-persisted**, not business-processed UIDs.
- `last_successful_scan_at`: indicates whether the poller is still alive.
- `last_error_code`: normalized error code for alerting.

When `UIDVALIDITY` changes, never continue with the old generation's cursor. Start a new scan epoch with reconciliation to avoid duplicate side effects.

### 6.3. The inbound_message Table

~~~sql
CREATE TABLE inbound_message (
    id UUID PRIMARY KEY,
    mailbox_id UUID NOT NULL REFERENCES inbound_mailbox(id),
    folder_key VARCHAR(250) NOT NULL,
    uid_validity BIGINT NOT NULL,
    imap_uid BIGINT NOT NULL,

    rfc_message_id VARCHAR(512),
    subject_excerpt VARCHAR(300),
    payload_ref VARCHAR(500),
    payload_sha256 CHAR(64),

    status VARCHAR(30) NOT NULL DEFAULT 'DISCOVERED',
    attempt_count INT NOT NULL DEFAULT 0,
    max_attempts INT NOT NULL DEFAULT 5,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    claim_token UUID,
    lease_owner VARCHAR(100),
    lease_until TIMESTAMPTZ,
    last_error_code VARCHAR(100),
    last_error_kind VARCHAR(30),
    terminal_reason VARCHAR(100),

    discovered_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    processed_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT uq_inbound_imap_identity UNIQUE(
        mailbox_id, folder_key, uid_validity, imap_uid
    ),
    CONSTRAINT chk_inbound_uid_positive CHECK (imap_uid > 0),
    CONSTRAINT chk_inbound_attempt_nonnegative CHECK (attempt_count >= 0)
);

CREATE INDEX ix_inbound_ready
    ON inbound_message(status, next_attempt_at);

CREATE INDEX ix_inbound_lease
    ON inbound_message(status, lease_until);

CREATE INDEX ix_inbound_header_message_id
    ON inbound_message(rfc_message_id);

CREATE INDEX ix_inbound_mailbox_recent
    ON inbound_message(mailbox_id, discovered_at DESC);
~~~

**Two key points:**

1. The unique constraint is on `mailbox_id + folder_key + uid_validity + imap_uid`, not on `rfc_message_id`.
2. `rfc_message_id` is indexed for lookup/correlation, but **is not forced unique or `NOT NULL`**.

In production, if you need to store a `Message-ID` header longer than `VARCHAR(512)`, keep the raw header in bounded metadata or store a cryptographic fingerprint with size controls, or adjust schema per policy. Never truncate a long value and treat the truncated string as an exact ID. Setting ingestion bounds against abnormal payloads is sensible, as long as outcomes are explicitly recorded.

`subject_excerpt` is illustrative only; subjects may contain PII. You do not have to store subject, body, or sender addresses in the database if business logic does not require them. For sensitive systems, store only minimal metadata and encrypted payload references.

### 6.4. Processing History and Side Effects

~~~sql
CREATE TABLE inbound_processing_attempt (
    id UUID PRIMARY KEY,
    inbound_message_id UUID NOT NULL
        REFERENCES inbound_message(id),
    attempt_no INT NOT NULL,
    claim_token UUID NOT NULL,
    worker_id VARCHAR(100),
    outcome VARCHAR(40) NOT NULL DEFAULT 'STARTED',
    error_code VARCHAR(100),
    safe_reason VARCHAR(300),
    started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at TIMESTAMPTZ,
    UNIQUE(inbound_message_id, attempt_no)
);

CREATE TABLE support_ticket_origin (
    id UUID PRIMARY KEY,
    inbound_message_id UUID NOT NULL
        REFERENCES inbound_message(id),
    ticket_id UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(inbound_message_id)
);
~~~

`support_ticket_origin.UNIQUE(inbound_message_id)` adds a **business idempotency** layer: if a worker retries after a crash, the same inbound record cannot create another ticket. If a message serves multiple workflow types, use a composite key including workflow type.

Attempt history records how many times workers started, when they failed, and with what error. There is no need to serialize full exceptions, SMTP/IMAP transcripts, or MIME bodies into the audit table.

### 6.5. Re-Observing the Same UID Must Not Reset State

When the poller sees the same UID again:

~~~sql
INSERT INTO inbound_message (
    id, mailbox_id, folder_key, uid_validity,
    imap_uid, rfc_message_id, status
)
VALUES (
    :id, :mailbox_id, :folder_key, :uid_validity,
    :imap_uid, :message_id, 'DISCOVERED'
)
ON CONFLICT (
    mailbox_id, folder_key, uid_validity, imap_uid
) DO NOTHING;
~~~

`DO NOTHING` preserves the existing row, including `PROCESSED`, `RETRY`, `FAILED`, attempt count, and audit fields. **Never write `ON CONFLICT DO UPDATE SET status='DISCOVERED'`**: doing so lets a poller drag already-processed emails back into the queue on every scan.

If you want to update new header metadata, ensure the update touches only permitted fields without resetting state or silently replacing the body snapshot of a processed delivery.

## 7. Reading IMAP with Jakarta Mail and Retrieving UIDs Properly

For IMAP, use **Jakarta Mail** APIs such as `Session`, `Store`, `Folder`, `Message`, and `UIDFolder`. The example below uses `imaps` to connect over TLS to a test server or organization-authorized provider.

### 7.1. Initializing the Connection

~~~java
import java.util.Properties;
import jakarta.mail.Session;
import jakarta.mail.Store;

Properties props = new Properties();
props.setProperty("mail.store.protocol", "imaps");
props.setProperty("mail.imaps.ssl.checkserveridentity", "true");
props.setProperty("mail.imaps.connectiontimeout", "5000");
props.setProperty("mail.imaps.timeout", "15000");
props.setProperty("mail.imaps.writetimeout", "15000");

Session session = Session.getInstance(props);
Store store = session.getStore("imaps");
store.connect(
        "imap.example.net",
        993,
        imapUsername,
        imapPassword);
~~~

`imapUsername` and `imapPassword` must be injected from runtime configuration/a secret manager, never hardcoded. Many mailbox providers require OAuth2 or app-specific credentials; **password login is a protocol example**, not advice to bypass provider authentication policies.

`mail.imaps.ssl.checkserveridentity=true` verifies host identity against the certificate. Never disable certificate verification just to make tests pass in production. For IMAP over STARTTLS/port 143, properties differ from `imaps` and must match the actual endpoint.

### 7.2. Opening the Folder and Reading UIDVALIDITY

~~~java
import jakarta.mail.Folder;
import jakarta.mail.UIDFolder;

Folder folder = store.getFolder("INBOX");
folder.open(Folder.READ_ONLY);

if (!(folder instanceof UIDFolder uidFolder)) {
    throw new IllegalStateException(
            "IMAP folder does not expose UID operations");
}

long uidValidity = uidFolder.getUIDValidity();
long nextUid = uidFolder.getUIDNext();
~~~

**Read `UIDVALIDITY` before using an old cursor.** `getUIDNext()` returns the predicted next UID of the folder at query time; `uidNext - 1` can serve as an upper bound for a scan pass with snapshot metadata. If the server does not return a useful value or the folder is unstable, the adapter must use another safe strategy rather than assuming an arbitrary upper bound.

### 7.3. Why Not Scan Up to an Arbitrary Future UID?

Suppose:

~~~text
last_discovered_uid = 100
current UIDNEXT = 121

Poller queries UID range 101..600
Existing messages: 101..120
Poller stores cursor = 600

New mail arrives with UID 121
Next scan starts at 601 => UID 121 was skipped!
~~~

This is a subtle bug. Only mark scanning complete up to **the upper limit already allocated by the server at snapshot time** (typically `UIDNEXT - 1`) or up to the last UID verified by a safe scan algorithm. Never unconditionally set `start + batchSize` as the final cursor when it exceeds UIDs that could have been assigned.

### 7.4. Illustrative Poller with Bounded Batches

A skeleton separating connectivity from the repository:

~~~java
package com.example.mail.inbound;

import java.util.ArrayList;
import java.util.List;
import java.util.Properties;
import java.util.UUID;

import jakarta.mail.Folder;
import jakarta.mail.Message;
import jakarta.mail.Session;
import jakarta.mail.Store;
import jakarta.mail.UIDFolder;
import jakarta.mail.internet.MimeMessage;

public final class ImapDiscoveryPoller {

    private static final int BATCH_UID_RANGE = 200;

    private final InboundDiscoveryRepository repository;
    private final InboundCursorService cursorService;

    public ImapDiscoveryPoller(
            InboundDiscoveryRepository repository,
            InboundCursorService cursorService) {
        this.repository = repository;
        this.cursorService = cursorService;
    }

    public void scan(
            UUID mailboxId,
            String host,
            String username,
            String password) throws Exception {

        Properties props = new Properties();
        props.put("mail.store.protocol", "imaps");
        props.put("mail.imaps.ssl.checkserveridentity", "true");
        props.put("mail.imaps.connectiontimeout", "5000");
        props.put("mail.imaps.timeout", "15000");

        Session session = Session.getInstance(props);
        Store store = null;
        Folder folder = null;

        try {
            store = session.getStore("imaps");
            store.connect(host, 993, username, password);
            folder = store.getFolder("INBOX");
            folder.open(Folder.READ_ONLY);

            if (!(folder instanceof UIDFolder uidFolder)) {
                throw new IllegalStateException(
                        "UIDFolder required for durable IMAP sync");
            }

            String folderKey = "INBOX";
            long validity = uidFolder.getUIDValidity();
            long uidNext = uidFolder.getUIDNext();

            if (validity <= 0 || uidNext <= 0) {
                throw new IllegalStateException(
                        "Invalid IMAP UID metadata");
            }

            CursorSnapshot cursor = cursorService
                    .forCurrentGeneration(
                            mailboxId, folderKey, validity);

            long highestAllocatedAtStart = uidNext - 1;
            long start = Math.max(1L, cursor.lastDiscoveredUid() + 1);

            while (start <= highestAllocatedAtStart) {
                long end = Math.min(
                        highestAllocatedAtStart,
                        start + BATCH_UID_RANGE - 1L);

                Message[] messages =
                        uidFolder.getMessagesByUID(start, end);
                List<DiscoveredImapMessage> found =
                        new ArrayList<>();

                for (Message message : messages) {
                    if (message == null) {
                        continue;
                    }
                    long uid = uidFolder.getUID(message);
                    if (uid <= 0) {
                        continue;
                    }
                    String rfcId =
                            message instanceof MimeMessage mime
                                    ? mime.getMessageID()
                                    : null;
                    found.add(new DiscoveredImapMessage(
                            uid, rfcId));
                }

                // Atomic DB transaction:
                // insert all discovered identities idempotently;
                // update cursor only after that persistence succeeds,
                // and only for matching mailbox/folder/UIDVALIDITY.
                repository.persistBatchAndAdvanceCursor(
                        mailboxId, folderKey, validity,
                        cursor, end, found);

                cursor = new CursorSnapshot(validity, end);
                start = end + 1;
            }
        } finally {
            if (folder != null && folder.isOpen()) {
                folder.close(false);
            }
            if (store != null && store.isConnected()) {
                store.close();
            }
        }
    }
}
~~~

`InboundDiscoveryRepository`, `InboundCursorService`, `CursorSnapshot`, and `DiscoveredImapMessage` are **application-implemented abstractions**, not built-in Jakarta Mail or Spring APIs. In Java, declare the corresponding records/classes in appropriate files.

Example records:

~~~java
public record CursorSnapshot(
        long uidValidity,
        long lastDiscoveredUid) {
}

public record DiscoveredImapMessage(
        long uid,
        String rfcMessageId) {
}
~~~

The class above is a **technical skeleton**, lacking backoff, mailbox-level leases, storage snapshots, size limits, per-folder retries, server-side expunge handling, or version-aware reconciliation. Do not copy it verbatim as a production mail importer.

**Concurrency concern:** if two pollers scan the same mailbox/folder, `persistBatchAndAdvanceCursor` must use a transaction and optimistic compare-and-swap or a mailbox-level lease so two processes cannot advance the cursor past unsaved batches. A single poller per mailbox/folder is the simplest starting choice.

**UIDVALIDITY change concern:** if the server changes UID generation mid-scan, the new batch must not overwrite another generation's cursor. Re-read `UIDVALIDITY`, use generation guards in the transaction, and restart scanning when changes are detected.

### 7.5. When the Server Has Deleted a UID in the Range

IMAP UIDs can have gaps due to expunged messages. A batch of UIDs 101..200 might contain only messages 105, 109, and 193. This does **not** mean 194..200 were skipped; with a valid snapshot upper bound, the range can be marked scanned.

If a message is deleted **before the poller discovers it**, current IMAP cannot recover the lost content. If zero-loss guarantees are required for critical workflows, use inbound gateway push, provider journaling, or long-enough mail retention with timely snapshots. Storing a cursor alone does not create a "zero lost email" guarantee if the source permits deletion before scanning.

### 7.6. IMAP Polling Should Not Automatically Mark SEEN

Opening the folder with `Folder.READ_ONLY` during discovery is a simple way to avoid mutating mailbox flags. Do not design the poller around `Flag.SEEN` to decide what to scan. Workers can read in `READ_ONLY` mode and track application state in the database.

If post-processing requires moving the message to a `Processed` folder or setting flags, treat that as a **retryable/idempotent post-processing step**, not the sole transaction confirming business completion.

## 8. Committing Cursors Properly to Avoid Skipping Mail

A safe algorithm per batch:

~~~text
Read current mailbox cursor C and generation V
          |
          v
Read IMAP snapshot for UID range (C+1)..E
          |
          v
BEGIN DB transaction
          |
          +--> Verify cursor generation still V
          +--> Insert each discovered UID (ON CONFLICT DO NOTHING)
          +--> Update cursor to E, guarded by V and old C
          |
          v
COMMIT
          |
          v
Continue next batch
~~~

If inserting any message or updating the cursor fails, **roll back the entire batch and do not advance the cursor**. The next poll will re-read that range. The unique constraint makes repeating safe.

### 8.1. Conditional Cursor Update Example

~~~sql
UPDATE inbound_mailbox_cursor
SET last_discovered_uid = :end_uid,
    last_successful_scan_at = now(),
    updated_at = now()
WHERE mailbox_id = :mailbox_id
  AND folder_key = :folder_key
  AND uid_validity = :expected_validity
  AND last_discovered_uid = :expected_previous_uid;
~~~

The application must verify that **the updated row count is 1**. If it is 0, another poller already updated the cursor or `UIDVALIDITY` just changed; reload state and decide what to re-scan rather than treating the batch as committed.

This is only part of the transaction. All `INSERT`s and the `UPDATE` for a batch must commit together. If the transaction rolls back, never update the cursor in an in-memory cache and persist it later.

### 8.2. When Higher Throughput Is Needed

You can:

- Run multiple workers **processing** already-persisted inbound records.
- Keep **one discovery coordinator** per mailbox/folder or clear partitioned leases.
- Use batch inserts and indexes on source identity.
- Fetch only metadata during discovery and offload large attachment downloads to workers.
- Use IMAP IDLE or push notifications **as a wakeup signal**, still reconciling with UID/cursors.

Do not split one IMAP folder into UID ranges processed by multiple pollers without tracking per-range completion if you only have a single integer cursor. A higher range committing before a lower range is persisted creates a risk of skipping mail.

### 8.3. IMAP IDLE Does Not Replace Checkpoints

IMAP `IDLE` can cut down continuous polling when supported by the server. Yet connections can drop, networks can jitter, and notifications are not a durable application event log. Upon reconnecting, you still must **re-scan UIDs after the committed cursor** to avoid losing messages during downtime.

## 9. Atomic Claims: Preventing Two Workers from Processing the Same Email Concurrently

After discovery, multiple workers may read `DISCOVERED` and `RETRY` rows. If both simultaneously run:

~~~text
SELECT ... WHERE status='DISCOVERED'
       |
       +-- worker A sees row #1
       +-- worker B also sees row #1
       |
       +-- A creates ticket
       +-- B creates ticket again
~~~

processing is duplicated. Use a transaction to **claim atomically** and set a lease/claim token before doing heavy work.

### 9.1. PostgreSQL: FOR UPDATE SKIP LOCKED

Example selecting a due inbound job:

~~~sql
WITH selected AS (
    SELECT id
    FROM inbound_message
    WHERE status IN ('DISCOVERED', 'FETCHED', 'RETRY')
      AND next_attempt_at <= now()
    ORDER BY next_attempt_at, discovered_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE inbound_message AS m
SET status = 'PROCESSING',
    attempt_count = m.attempt_count + 1,
    claim_token = :claim_token,
    lease_owner = :worker_id,
    lease_until = now() + INTERVAL '2 minutes',
    updated_at = now()
FROM selected
WHERE m.id = selected.id
RETURNING m.id,
          m.attempt_count,
          m.mailbox_id,
          m.folder_key,
          m.uid_validity,
          m.imap_uid,
          m.payload_ref;
~~~

`:claim_token` is a UUID generated by the worker per claim attempt. With multiple workers, a row may be locked by another worker; `SKIP LOCKED` lets other workers pick different rows without blocking.

**Execute the claim in a short transaction and commit**, never holding the transaction/row lock while reading MIME or calling business APIs.

### 9.2. Recording Attempt History in the Same Claim Transaction

Right after claiming:

~~~sql
INSERT INTO inbound_processing_attempt (
    id, inbound_message_id, attempt_no,
    claim_token, worker_id, outcome
)
VALUES (
    :attempt_id, :inbound_message_id, :attempt_no,
    :claim_token, :worker_id, 'STARTED'
);
~~~

The claim and `INSERT attempt` should sit **in the same transaction**, so that if inserting history fails, the row is not stranded in `PROCESSING` without an audit trail.

### 9.3. Result Updates Must Use Fencing

After processing completes, the worker updates:

~~~sql
UPDATE inbound_message
SET status = 'PROCESSED',
    processed_at = now(),
    claim_token = NULL,
    lease_owner = NULL,
    lease_until = NULL,
    last_error_code = NULL,
    updated_at = now()
WHERE id = :inbound_message_id
  AND status = 'PROCESSING'
  AND claim_token = :claim_token;
~~~

If the update count is `0`, the worker likely lost job ownership or another worker reclaimed it. **Never overwrite newer state** with the outcome of an old attempt.

If a worker needs to heartbeat/extend the lease during slow attachment processing:

~~~sql
UPDATE inbound_message
SET lease_until = now() + INTERVAL '2 minutes'
WHERE id = :inbound_message_id
  AND status = 'PROCESSING'
  AND claim_token = :claim_token;
~~~

The heartbeat only succeeds while the token remains valid. Never extend leases infinitely if the worker stops making progress; the system needs timeouts and rules for stuck jobs.

### 9.4. Claim Tokens Only Prevent Stale Writes, Not Duplicate Side Effects by Themselves

Suppose:

~~~text
Worker A claims job, lease=2m
Worker A blocks on external ticket API
Lease expires
Worker B reclaims and starts same job
Worker A resumes and calls ticket API
Worker B also calls ticket API
~~~

The fencing token protects the **database status update**, yet if the ticket API lacks an idempotency key, **two tickets** can still be created. Coordinate with an atomic DB transaction or an idempotency key on the side-effect receiver.

## 10. Idempotent Business Processing

Inbound systems over IMAP/webhooks typically have **at-least-once** semantics: a message or event may be re-read/redelivered after a crash. The goal is **never creating duplicate side effects** even when a handler executes more than once.

### 10.1. Creating the Ticket and Marking PROCESSED in One Transaction

If tickets and inbound state reside in the same PostgreSQL database, use **one database transaction**:

~~~text
Worker owns inbound_message claim token
        |
        v
BEGIN transaction
        |
        +--> Validate claim still current
        |
        +--> INSERT business ticket / comment
        |
        +--> INSERT support_ticket_origin
        |    UNIQUE(inbound_message_id)
        |
        +--> UPDATE inbound_message status=PROCESSED
        |    WHERE id and claim_token match
        |
        v
COMMIT
~~~

If the transaction rolls back, both the ticket and `PROCESSED` status roll back together. On retry, the worker can run again without leaving a half-committed ticket.

In real code, order operations and locks so an existing origin never lets a worker insert a new ticket before hitting the unique violation. Use `INSERT ... ON CONFLICT`, check the origin record first, or wrap in an atomic idempotent service.

### 10.2. Illustrative Java/Spring @Transactional Example

~~~java
package com.example.mail.inbound;

import java.util.UUID;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public final class InboundTicketHandler {

    private final InboundMessageRepository inbound;
    private final SupportTicketRepository tickets;

    public InboundTicketHandler(
            InboundMessageRepository inbound,
            SupportTicketRepository tickets) {
        this.inbound = inbound;
        this.tickets = tickets;
    }

    @Transactional
    public void completeTicketProcessing(
            UUID inboundId,
            UUID claimToken,
            ParsedInboundMail parsed) {

        InboundRecord current = inbound
                .lockForClaim(inboundId, claimToken)
                .orElseThrow(() ->
                        new StaleClaimException(inboundId));

        if (current.isProcessed()) {
            return;
        }

        tickets.createFromInboundOnce(
                current.tenantId(),
                inboundId,
                parsed);

        if (!inbound.markProcessed(inboundId, claimToken)) {
            throw new StaleClaimException(inboundId);
        }
    }
}
~~~

`InboundMessageRepository`, `SupportTicketRepository`, `ParsedInboundMail`, and `StaleClaimException` are **application-implemented abstractions**, not built-in Spring Mail classes.

Both `createFromInboundOnce` and `markProcessed` must use real database uniqueness/claim guards; an in-memory `exists(...)` check is **insufficient** against concurrent workers. The transaction only covers tables under the same transaction manager/database.

### 10.3. When Side Effects Live in an External Service

Suppose the handler calls an HTTP API to create a ticket in another system:

~~~text
POST remote ticket API -> success
      |
      v
Local DB commit fails
      |
      v
Inbound row remains RETRY/PROCESSING
      |
      v
Retry calls POST again -> duplicate ticket possible
~~~

There is no single transaction spanning IMAP, the local DB, and an HTTP API. Solutions:

- Send a stable `Idempotency-Key` per **business operation** if supported by the external API.
- Use a **transactional outbox** to record the ticket-creation intent alongside the inbound commit, then have a dispatcher push the command to the API.
- Persist the external object ID and reconcile if a request times out after the remote service already processed it.
- If deduplication is impossible, document the duplicate risk and operational procedure rather than claiming exactly-once.

Example:

~~~text
inbound_message.id = 8c4...
business operation = CREATE_SUPPORT_TICKET
idempotencyKey = "inbound-ticket:8c4..."
~~~

One inbound email can lead to multiple distinct business operations, so the key should include the **operation**, not just the message ID. Never generate a fresh random key per retry when idempotency is the goal.

### 10.4. When One Email Reaches Multiple Mailboxes or Folders

Two distinct needs arise:

1. **Technical dedupe:** the same entry in the same folder/`UIDVALIDITY` creates only one inbound row.
2. **Business dedupe:** the same customer request forwarded/copied to multiple mailboxes, where the product only wants one ticket.

IMAP keys solve (1); (2) must rely on trustworthy business rules, such as an application-issued case ID, verified reply token, external document reference, or tenant-verified business identifier.

**Never use RFC `Message-ID` alone to merge emails across all mailboxes**: attackers can craft matching headers to bypass or misattach content, and mail clients can also generate unintentional collisions.

## 11. Retries and Dead-Lettering for Inbound Emails

Mail-reading or payload-processing failures can be transient or permanent:

| Stage | Example | Recommended Handling |
| --- | --- | --- |
| IMAP connect/auth | Server unavailable, wrong credentials | Retry connect with backoff; alert on auth if credentials revoked |
| IMAP source read | Timeout, folder temporarily unavailable | Retry fetch if source identity remains valid |
| MIME parse | Corrupt MIME, too deep, odd charset | Classify; quarantine/`FAILED` if unsafe to process |
| Attachment scanning | Scanner temporarily offline | Retry after backoff |
| Malicious attachment | Malware or disallowed file | `QUARANTINED`, do not normally retry |
| Business validation | Missing order code, tenant mismatch | `IGNORED`/`FAILED` per policy; do not guess |
| Database write | Deadlock/temporary outage | Bounded retries |
| External API | Timeout after task may have succeeded | `UNKNOWN`/reconcile/idempotency key |
| Source disappeared | Email deleted/moved before fetch | `FAILED`/`SOURCE_MISSING` or locate valid snapshot |

Never label every exception as "IMAP error". Record normalized `failure_stage` and `error_code` so operators know whether to fix connectivity, the MIME parser, business data, or an external system.

### 11.1. Backoff and Max Attempts

An example policy:

~~~text
max_attempts = 5
initial_delay = 30 seconds
max_delay = 15 minutes
jitter = enabled

Attempt #1 fails transiently -> RETRY after 30s
Attempt #2 fails transiently -> RETRY after 60s
Attempt #3 fails transiently -> RETRY after 120s
Attempt #4 fails transiently -> RETRY after 240s
Attempt #5 fails transiently -> FAILED / dead letter
~~~

This is an **example policy**, not a Spring Mail default. For critical emails, retention on the IMAP source must last long enough for workers to access content throughout the retry window; otherwise, capture a durable snapshot upfront.

### 11.2. Updating RETRY with a Claim Token

~~~sql
UPDATE inbound_message
SET status = 'RETRY',
    next_attempt_at = :next_attempt_at,
    last_error_code = :error_code,
    last_error_kind = 'TRANSIENT',
    lease_owner = NULL,
    claim_token = NULL,
    lease_until = NULL,
    updated_at = now()
WHERE id = :inbound_message_id
  AND status = 'PROCESSING'
  AND claim_token = :claim_token;
~~~

The retry-handling transaction should update both attempt history and the inbound row together. Once attempts are exhausted, status can move to `FAILED` with `terminal_reason=MAX_ATTEMPTS_EXHAUSTED`. Do not convert every transient error into "permanent" merely because retries ran out; preserve both **error kind** and **stop reason**.

### 11.3. Dead Letters Must Retain Enough Recovery Info

A `FAILED` record should retain:

- Inbound source identity: mailbox/folder/`UIDVALIDITY`/UID or provider event ID.
- Internal inbound message ID and tenant/workflow scope.
- Status and attempt history.
- Normalized error code and failure stage.
- Protected snapshot/correlation metadata, if retained.
- Failure timestamp, attempt count, and operator/redrive actor.

If the payload was purged due to retention, never blindly redrive assuming data still exists. Report `PAYLOAD_UNAVAILABLE` or request retransmission through a valid channel.

### 11.4. Redrives Must Be Audited

A manual retry operation should:

1. Verify operator permissions and tenant scope.
2. Confirm the root cause has been fixed.
3. Verify source/snapshot availability, deadlines, and security policies.
4. Ensure no side effect already completed without recording state.
5. Audit actor, reason, timestamp, and before/after state.
6. Schedule with bounded concurrency/rate limits.

Never reset `attempt_count` to 0 or delete attempt history just to "allow more retries". If granting a new retry cycle, define it explicitly in policy and preserve prior audit records.

## 12. UIDVALIDITY Changes: One of the Most Critical Cases

Under IMAP semantics, UIDs are only considered durable identifiers within **one mailbox under the same `UIDVALIDITY`**. When a server rebuilds a folder, restores data, migrates mailboxes, or changes UID generation, `UIDVALIDITY` can change.

Suppose:

~~~text
Before restore:
  folder=INBOX
  UIDVALIDITY=1000
  UID=50 -> Customer mail A
  last_discovered_uid=300

After restore:
  folder=INBOX
  UIDVALIDITY=2000
  UID=50 -> Customer mail B
  next UID=75
~~~

If the poller skips checking `UIDVALIDITY` and resumes scanning from `301`, it **skips every message in the new generation**. If it treats `UID=50` of the new generation as the old message, it **wrongly skips customer mail B**.

### 12.1. Detection Mechanism

Every time the folder is opened:

~~~text
stored UIDVALIDITY = 1000
server UIDVALIDITY = 2000
           |
           v
Generation mismatch
           |
           v
Stop using old cursor
           |
           v
Start new epoch scan / reconciliation
~~~

Never write `uid_validity=2000` while keeping `last_discovered_uid=300`. Reset the cursor for the new epoch **with auditing**, e.g., back to `0` before scanning, and never delete old-epoch inbound rows just to reuse overlapping UID numbers.

### 12.2. Do Not Delete Old History When UIDVALIDITY Changes

Instead of:

~~~sql
DELETE FROM inbound_message
WHERE mailbox_id = :mailbox_id
  AND folder_key = :folder_key;
~~~

retain history keyed by `uid_validity`, while the cursor tracks the current generation. If content reappears in the new epoch, it can create a new source identity and pass through **business deduplication** to decide whether side effects should run again.

Never use `Message-ID` as a unique key to automatically drop all copies in the new epoch, because spoofed/duplicate headers or valid new messages sharing headers could exist.

### 12.3. Atomic Cursor Reset

SQL example in a transaction under a mailbox-level lock/lease:

~~~sql
UPDATE inbound_mailbox_cursor
SET uid_validity = :new_uid_validity,
    last_discovered_uid = 0,
    last_error_code = NULL,
    updated_at = now()
WHERE mailbox_id = :mailbox_id
  AND folder_key = :folder_key
  AND uid_validity = :old_uid_validity;
~~~

If the cursor has not been initialized yet, use a separate `INSERT` branch. Check the update count, since another poller may have just updated the epoch. Never trigger repeated resets based solely on a stale in-memory variable.

A rescan can create many new inbound records for older emails still sitting in the folder. Distinguish **duplicate source copies** from **business duplicates**; manual review may be appropriate for flows with sensitive side effects.

### 12.4. PROCESSING Rows from an Old Epoch

If a worker already claimed a row with `UIDVALIDITY=1000` while the server now only exposes epoch `2000`, the worker can no longer fetch the message by its old UID. If a durable snapshot exists, process from that snapshot. Otherwise:

- Mark the attempt failed with `SOURCE_GENERATION_CHANGED` or `SOURCE_UNAVAILABLE`.
- Never silently fetch the same numeric UID in the new epoch.
- Never mark `PROCESSED` without sufficient data to complete the side effect.
- You may relocate the corresponding source via extra metadata if permitted by policy, but never rely solely on RFC `Message-ID`.

This is why content snapshots can be essential for critical inbound workflows.

## 13. Moving or Copying Messages Between Folders

In IMAP, UIDs are scoped to a folder. Moving an email from `INBOX` to `Processed` usually gives it a different UID in the destination folder, as the server may create a new entry.

~~~text
INBOX:
  (UIDVALIDITY=10, UID=201) -> mail A
            |
            | MOVE/COPY
            v
Processed:
  (UIDVALIDITY=20, UID=87) -> mail A
~~~

Two different source identities can hold the same email content. Therefore:

- If the app only scans `INBOX`, moving messages after processing can be a clean workflow.
- If scanning both `INBOX` and `Processed`, prevent duplicate side effects via business policy.
- Never assume the destination folder UID equals the source UID.
- Never move the message to `Processed` **before** committing business state if doing so hides it from a poller that needs to retry.

### 13.1. Post-Processing Order

~~~text
Fetch/parse input
   |
   v
Commit business side effect + inbound PROCESSED
   |
   v
Optional IMAP flag/move
   |
   v
Record move/flag result for retry if needed
~~~

If the move step fails, the DB already knows the email is `PROCESSED`; retrying the folder operation must not create another ticket.

If the app has a requirement to "only mark `PROCESSED` after the email has moved successfully", model an intermediate state such as `POST_PROCESSING_PENDING` rather than letting every move failure re-trigger the business handler.

### 13.2. Do Not Use Message-ID to Prove Two Entries Are Identical

An email copied across folders may retain the same RFC `Message-ID`, yet an attacker can also send a different email with the same header. To prevent duplicate side effects, store:

- An application-created link at move time when both source and destination are known.
- A provider message identity if the provider exposes reliable cross-folder IDs.
- A payload fingerprint/normalized content hash **purely as a supporting signal** under strict policy.
- A business operation key verified across tenant/conversation/ticket.

Do not equate nearly identical content with the same action. Two "OK" replies from the same customer can be two distinct valid emails.

## 14. POP3 UIDL and Differences from IMAP

If the system receives mail via **POP3**, it normally lacks IMAP-style folders/`UIDVALIDITY`. Many POP3 servers support the `UIDL` command to return a stable per-message ID across sessions.

~~~text
POP3 mailbox:
  message sequence 1 -> UIDL ab123
  message sequence 2 -> UIDL xy456
~~~

**Never store POP3 message numbers** as durable keys because the message list shifts when messages are deleted. Store a source key:

~~~text
(pop3_account_id, uidl)
~~~

This is the standard pattern when the server properly supports `UIDL`. Verify actual server/implementation behavior; servers can behave differently during mailbox migrations/rebuilds, and POP3 provides less metadata and synchronization support than IMAP.

### 14.1. POP3 Risks When Deleting Messages After Reading

A POP3 flow:

~~~text
Connect
  |
  v
List UIDL values
  |
  v
Fetch mail
  |
  v
Persist durable inbound record
  |
  v
Process safely
  |
  v
Delete from server when policy allows
~~~

Never delete a message immediately upon fetching before the database has durably persisted it and recovery requirements are met. POP3 deletions typically commit when the session ends; the adapter must understand how the server handles `DELETE`/`QUIT` and connection drops.

### 14.2. If the POP3 Server Does Not Support UIDL

There is no durable key equivalent to IMAP `UID + UIDVALIDITY`. Options:

- Prefer switching to IMAP or an inbound gateway if infrastructure allows.
- Compute a bounded fingerprint from metadata + content, treating it as a heuristic rather than an absolute identifier.
- Snapshot content immediately upon receipt and rely on DB records/business idempotency.
- Provide manual review for collision/duplicate cases.

**Never treat standalone RFC `Message-ID` as a perfect replacement for `UIDL`.**

## 15. Inbound Webhooks: Store Event IDs and Message IDs Separately

Some email services provide **inbound routing** and invoke an HTTP webhook to the application when new mail arrives. Unlike IMAP polling, you must receive and verify the event before parsing content.

~~~text
Inbound email provider
       |
       v
POST /webhooks/inbound-mail
       |
       v
Verify provider signature / timestamp
       |
       v
Extract provider event ID + message ID
       |
       v
Persist durable event (unique provider + event ID)
       |
       v
Ack HTTP only after durable receipt
       |
       v
Worker parses MIME / performs business handler
~~~

A provider may resend **the same event** on request timeout. In that case, a unique key such as:

~~~text
(provider_id, provider_event_id)
~~~

can block webhook redeliveries per provider contract. However, **one email can emit multiple distinct events**, and a provider event ID does not necessarily equal the provider message ID. If the app also polls IMAP for the same mailbox, add a shared business correlation/dedupe layer rather than mixing the two source keys.

### 15.1. Webhook Event Schema

~~~sql
CREATE TABLE inbound_provider_event (
    id UUID PRIMARY KEY,
    provider_id VARCHAR(100) NOT NULL,
    provider_event_id VARCHAR(250) NOT NULL,
    provider_message_id VARCHAR(250),
    rfc_message_id VARCHAR(512),
    inbound_message_id UUID,
    status VARCHAR(40) NOT NULL DEFAULT 'RECEIVED',
    received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(provider_id, provider_event_id)
);
~~~

Only apply the unique constraint when the provider **guarantees stable event IDs across redeliveries** with a clear namespace. If the provider reuses one ID across multiple event types, include `event_type` in the composite key per real schema.

### 15.2. Preventing Double Processing on Webhook Redelivery

Example:

~~~text
POST event E1
  -> signature valid
  -> INSERT event E1
  -> COMMIT
  -> return 200/202

Provider retries E1
  -> signature valid
  -> ON CONFLICT DO NOTHING
  -> return 200/202
  -> no duplicate processing side effect
~~~

Condition: the event must be **durably persisted** before returning a success response. If code returns `200` and only then pushes onto an in-memory queue, a crash can lose the email while the provider believes it was accepted.

### 15.3. Never Trust Unauthenticated Webhooks

Emails with arbitrary headers can arrive from outsiders; HTTP webhooks can also be forged on public endpoints. Always:

- Verify signatures/secrets/mTLS per provider.
- Use the raw request body if the signing algorithm requires it.
- Block replays via timestamps/event IDs when supported by the provider.
- Limit request size, attachment counts, and MIME nesting.
- Never allow the payload to self-declare `tenantId` or mailbox owner while bypassing authorized account mapping.
- Never log raw bodies containing PII/attachments.

## 16. Message-ID in Reply Flows and Conversation Threading

Beyond deduplication, RFC `Message-ID` is very useful when the application receives **reply emails**. Mail clients usually add `In-Reply-To` or `References` containing IDs of previous messages in the thread.

Example support email system:

~~~text
Outbound email:
  From: support@example.com
  To: customer@example.net
  Subject: Ticket #T123
  Message-ID: <ticket-T123-001@mail.example.com>

Inbound reply:
  From: customer@example.net
  To: support@example.com
  Subject: Re: Ticket #T123
  Message-ID: <reply-customer-777@example.net>
  In-Reply-To: <ticket-T123-001@mail.example.com>
  References: <ticket-T123-001@mail.example.com>
~~~

In this case:

- The `Message-ID` of the **received email** is `<reply-customer-777@example.net>`.
- `In-Reply-To` points to the ID of the **previous email**.
- `References` captures the reference chain.
- The `IMAP UID` of the reply email is **completely distinct** from the headers above.

By storing all three kinds of data, the system can:

1. Use IMAP UID + `UIDVALIDITY` to know whether the message was already discovered.
2. Use the internal inbound ID to manage processing state.
3. Use `In-Reply-To`/`References` to **locate candidate tickets/conversations**.

### 16.1. Persisting Outbound Message-IDs for Correlation

A simple mapping table:

~~~sql
CREATE TABLE outbound_message_reference (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    ticket_id UUID NOT NULL,
    outbound_delivery_id UUID NOT NULL,
    rfc_message_id VARCHAR(512) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(tenant_id, outbound_delivery_id)
);

CREATE INDEX ix_outbound_reference_message_id
    ON outbound_message_reference(tenant_id, rfc_message_id);
~~~

Do not enforce system-wide uniqueness on `rfc_message_id` if the application cannot guarantee exact generation and preservation, and never treat an ID declared by an inbound email as an access privilege. For application-managed outbound emails, explicitly set or capture the `Message-ID` actually used by the transport per Jakarta Mail/provider behavior, and store the mapping durably.

With SMTP, `JavaMailSender.send(...)` does not return a standard provider-specific message ID. Setting/reading `Message-ID` and ensuring the header is preserved must be tested against your actual MIME/Jakarta Mail implementation. Some transports generate or overwrite the header during `saveChanges()`/send. Therefore, store correlation info alongside the attempt and verify against actual sent messages.

### 16.2. Do Not Trust In-Reply-To Alone to Authorize Ticket Edits

An attacker can send:

~~~text
From: attacker@example.net
In-Reply-To: <ticket-T123-001@mail.example.com>
~~~

If the application merely matches `In-Reply-To` and attaches content to another customer's ticket, **conversation hijacking** or data leakage can occur.

A verification suite should check:

- The ticket belongs to the right tenant and data boundary.
- The sender/correspondent is authorized to participate in the ticket.
- Addresses and thread references are canonicalized safely.
- Any reply tokens used have high entropy, expiry/scope, and cannot be guessed.
- Content/attachments are sanitized/quarantined before creating visible comments.
- Never infer from a standalone `From` header that the sender is authenticated; email `From` can be spoofed.

`In-Reply-To` assists **context lookup**, not authorization.

### 16.3. Bounded References Parsing

`References` can hold multiple Message-IDs:

~~~text
References:
  <root@example.com>
  <followup@example.net>
  <ticket-T123-001@mail.example.com>
~~~

The application should:

1. Parse according to email header format rather than using naive `split(" ")` everywhere.
2. Bound the number of tokens/header bytes.
3. Preserve exact ID form/case when storing; do not arbitrarily lowercase the entire string.
4. Look up only within the matching tenant/conversation scope.
5. Resolve cases where multiple references map to different tickets via explicit policy rather than guessing.

For support mailboxes, a **dedicated tokenized reply-to alias** (e.g., `support+opaqueTicketToken@example.com`) is sometimes more reliable than relying solely on subjects/thread headers, though it also requires protection, routing, and authorization. Never build tokens from predictable sequential ticket numbers and treat them as secrets.

### 16.4. Subject Is Not a Conversation ID

Example of multiple emails sharing a subject:

~~~text
Subject: Bug report
Subject: Re: Bug report
Subject: Bug report
~~~

This does not prove they belong to the same ticket. Subjects can be edited, `Re:` prefixes vary across clients and languages, and attackers can choose arbitrary subjects. Without reliable correlation, open a new conversation or route to triage per policy.

## 17. Handling DSNs/Bounces with Message IDs

An inbound system may also receive bounce emails:

~~~text
Original outbound:
  Message-ID: <delivery-abc@mail.example.com>
  Envelope MAIL FROM: bounces@bounce.example.com

Later inbound DSN:
  MIME type: multipart/report
  Inner part: message/delivery-status
  Final-Recipient: rfc822; unknown@example.net
  Action: failed
  Status: 5.1.1
~~~

A DSN may attach headers or the original message, containing the original `Message-ID`. Yet not every DSN includes complete metadata, and a single DSN can report status for **multiple recipients**.

Therefore:

- Persist the inbound IMAP identity of **the DSN itself** to avoid processing it twice.
- Persist any provider/DSN event ID to block redeliveries.
- Parse per-recipient `Action`, `Status`, and `Final-Recipient`.
- Correlate to the outbound delivery and recipient via trusted sources such as envelope tokens/VERP or provider message IDs.
- Never use a single RFC `Message-ID` to update every recipient in an outbound batch.
- Never suppress an address solely because an email has `From: MAILER-DAEMON` or a self-proclaimed DSN failure; incoming messages can be spoofed.

If a DSN is unauthenticated or cannot be mapped to an outbound delivery, its status should be `UNKNOWN/NEEDS_REVIEW`. Ignoring these principles can let attackers trick the system into halting notifications to legitimate users.

## 18. Security and Privacy When Storing Inbound Metadata

Received emails can carry more sensitive data than outgoing ones: uncontrolled customer content, unfamiliar files, personal data, or accidentally emailed secrets. Storing state/message IDs must include data protection policies.

### 18.1. Data Classification

| Data | Risk | Recommendation |
| --- | --- | --- |
| `rfc_message_id` | May reveal sender domains/identifiers | Never use as metric labels; limit logging |
| `From` / `To` / `Reply-To` | PII, spoofable | Store minimally; restrict access |
| `Subject` | May contain medical, invoice, or account info | Avoid storing if unneeded; never log raw |
| MIME body/attachments | PII, malware, secrets, dangerous HTML | Quarantine/scan; store encrypted with retention |
| IMAP UID | Technical metadata | Always scope by mailbox/folder/`UIDVALIDITY` |
| IMAP/OAuth credentials | Mailbox access secrets | Secret manager, least privilege, rotation |
| Processing state/attempts | Internal info, event history | RBAC, auditing, and retention |
| Raw inbound webhook payload | May contain full MIME | Verify before processing; restrict retention |

### 18.2. Message-ID and Other Headers Are Untrusted Data

When persisting to SQL:

- Use prepared statements/ORM binding; never concatenate headers directly into SQL.
- Enforce length/charset/control-character limits per data contract.
- Never place raw headers into an HTML dashboard without context-appropriate escaping.
- Never use headers as filesystem paths, arbitrary object keys, or metric label names.
- Never treat `Message-ID` as authorization to modify a ticket.
- When logging, use internal UUIDs/opaque correlation IDs instead of raw email addresses.

Headers can contain newlines/folding. When parsing or forwarding metadata to HTTP responses, prevent CRLF injection into HTTP headers or log fields.

### 18.3. Never Automatically Open Uninspected Attachments

Inbound parsers can encounter:

- `multipart/mixed` with PDF/ZIP/Office files.
- HTML containing scripts/tracking links.
- Nested `message/rfc822`.
- Multi-layered compressed archives or deep MIME trees.
- Attachments declaring false content types.

The ingestion layer should enforce:

1. Limits on message bytes and attachment bytes.
2. Limits on MIME depth, part count, and charset decoding.
3. Malware scanning/allowlists per workflow.
4. Never trusting filenames/content-types as proof of safety.
5. Never auto-executing attachments or loading HTML active content.
6. Isolating quarantine from normal business processing.
7. Limiting workers processing large messages to prevent DoS.

An unparseable email or one containing dangerous files must not retry forever. Record `QUARANTINED` or `FAILED` with an explicit reason.

### 18.4. Data Residency and Multi-Tenancy

If an application serves multiple mailboxes by tenant/region:

- `mailbox_id` must link to an authorized tenant.
- Queues, snapshot object storage, and audits must obey approved data boundaries.
- A worker must never process another tenant's inbound message merely by knowing its UUID.
- `In-Reply-To` and `References` lookups must filter by tenant.
- Never send raw MIME to a shared dashboard lacking authorization.
- Switching providers/mailboxes must never accidentally merge emails into a shared ID namespace.

Naming a mailbox `eu-support` does not prove data/backups/logs are processed inside the EU. Data residency policies must cover the entire path from ingest → storage → processing → events.

### 18.5. Retention and Deletion Rights

A retention strategy may separate:

~~~text
Original MIME snapshot: short, encrypted retention
Attachments: quarantine/TTL according to content policy
Processing events: sufficient for audit, without raw body
RFC Message-ID: retain only as long as correlation requires
Business ticket: separate domain retention and legal policy
~~~

There is no universal day count for all applications. When payloads are deleted upon request, prevent dead-letter redrives from silently recreating or re-exporting data beyond permitted scope.

## 19. Logs, Metrics, and Alerting

A mail-receiving system must observe **inputs, sync progress, and handler outcomes**; knowing only that IMAP is connected is insufficient.

| Metric | Type | Question |
| --- | --- | --- |

| `inbound_processing_attempt_total` | Counter | How many attempts did workers execute? |
| `inbound_processing_completed_total` | Counter | How many workflows actually completed? |
| `inbound_processing_failed_total` | Counter | Terminal errors by reason/stage? |
| `inbound_retry_scheduled_total` | Counter | How many retries were scheduled? |
| `inbound_queue_ready` | Gauge | How many due emails remain unprocessed? |
| `inbound_queue_inflight` | Gauge | How many emails currently hold a lease? |
| `inbound_oldest_ready_age_seconds` | Gauge | How long has the oldest due email waited? |
| `inbound_imap_poll_duration_seconds` | Timer | How long does scanning a folder take? |

| `inbound_source_missing_total` | Counter | How many UIDs could no longer be fetched? |
| `inbound_unmatched_reply_total` | Counter | How many replies failed to map to a ticket? |

### 19.1. Distinguishing Discovered Mail Count from Processed Mail Count

Suppose:

~~~text
discovered_last_5m = 200
processed_last_5m = 50
retry_due = 30
processing = 10
oldest_ready_age = 12 minutes
~~~

The poller is still running, yet processing workers are falling behind. If a dashboard only shows `IMAP connected=true`, operators may miss the growing backlog.

Conversely, if `discovered=0` while the mailbox genuinely has no mail, that can be normal. Combine mail creation sources/schedules and last successful scan timestamps to distinguish **no new mail** from **dead poller**.

### 19.2. Structured Logs

~~~json
{
  "event": "inbound.processing.retry_scheduled",
  "inboundMessageId": "opaque-uuid",
  "sourceType": "IMAP",
  "mailboxLogicalGroup": "support",
  "workflow": "TICKET",
  "attempt": 3,
  "failureStage": "BUSINESS_API",
  "safeErrorCode": "REMOTE_TIMEOUT",
  "nextAttemptAt": "2026-11-12T12:15:00Z"
}
~~~

Never log passwords, OAuth tokens, full message bodies, attachments, or raw error messages that may contain PII. If UID lookups are needed, log internal IDs and look up source identities in an access-controlled admin system.

### 19.3. Actionable Alerts

- **Mailbox not polled successfully within SLO:** check network, AUTH, `UIDVALIDITY`/IMAP errors.
- **Oldest ready age rising:** worker backlog or slow business handlers.
- **UIDVALIDITY resets rising:** likely server migration/restore; evaluate duplicates/reruns.
- **Source missing rising:** users/clients may be moving/deleting before snapshot, or retention is too short.
- **Failed/quarantine rising:** parser regression, malware campaign, or incompatible data.
- **Expired leases rising:** worker crashes, long timeouts, or overly short leases.
- **External side-effect UNKNOWN rising:** requires reconciliation before retrying.

Never use email addresses, RFC `Message-ID`s, UIDs, or high-cardinality tenant UUIDs as Prometheus labels. Use bounded lists of source type, mailbox group, workflow, status, and error category.

## 20. Testing Message ID, Cursor, and Processing State Persistence

For inbound mechanisms, tests need more than reading a single email. The hardest bugs hide in **retries, race conditions, folder mutations, `UIDVALIDITY`, duplicate headers, and database transaction boundaries**.

### 20.1. Minimum Test Matrix

| Scenario | Setup | Expected Outcome |
| --- | --- | --- |
| New IMAP UID | `UIDVALIDITY=1, UID=10` does not exist | Insert one `DISCOVERED` row |
| Re-scan same UID | Second observation of `(mailbox, folder, 1, 10)` | No new row, no state reset |
| Two UIDs, same RFC `Message-ID` | UIDs 10 and 11 share header | Persist **two source records**, do not drop 11 |
| Missing `Message-ID` | Header absent/null | Still persist source record by UID |
| Same UID in two folders | `INBOX/10` and `Archive/10` | Two distinct source identities |
| Same UID, different `UIDVALIDITY` | `V1/10` and `V2/10` | Do not treat as the same source identity |
| Sequence number shifts after expunge | Message numbers change | Dedupe/cursor still tracks UID |
| User marks SEEN before poll | `SEEN` flag already set | Poller still discovers unrecorded UID |
| Poller crashes before batch commit | Insert/cursor transaction uncommitted | Batch re-scanned, nothing skipped |
| Poller crashes after batch commit | DB persisted rows + cursor | No duplicate side effects |
| Worker crashes before processing | Row `PROCESSING`, lease expires | Reclaimed per policy |
| Worker crashes after ticket commit | Ticket+`PROCESSED` in same transaction | No second ticket created |
| External API succeeds, local commit fails | Ambiguous outcome | Reconcile or idempotency key |
| Corrupt or oversized MIME | Intentionally invalid payload | `FAILED`/`QUARANTINED`, no infinite retries |
| Email moved across folders | New UID in destination folder | Business behavior matches dedupe policy |
| Webhook redelivers same event ID | Two identical HTTP POSTs | One durable event, one side effect |
| Spoofed `In-Reply-To` | Header points to another tenant's ticket | Must not attach to unauthorized ticket |
| Cursor generation changes mid-batch | Concurrent `UIDVALIDITY` update | Abort/reload, do not advance wrong epoch |
| Many UID gaps | Range contains few messages | Cursor still advances to valid snapshot upper bound |

### 20.2. Unit Testing Identity Keys

Example identity model:

~~~java
import java.util.UUID;

public record ImapSourceIdentity(
        UUID mailboxId,
        String folderKey,
        long uidValidity,
        long uid) {

    public ImapSourceIdentity {
        if (mailboxId == null || folderKey == null
                || folderKey.isBlank()
                || uidValidity <= 0 || uid <= 0) {
            throw new IllegalArgumentException(
                    "Invalid IMAP source identity");
        }
    }
}
~~~

JUnit test:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.util.UUID;
import org.junit.jupiter.api.Test;

class ImapIdentityTest {

    @Test
    void uidMustBeScopedByFolderAndValidity() {
        UUID mailboxId = UUID.randomUUID();

        ImapSourceIdentity inboxOld =
                new ImapSourceIdentity(
                        mailboxId, "INBOX", 100, 22);
        ImapSourceIdentity inboxNew =
                new ImapSourceIdentity(
                        mailboxId, "INBOX", 200, 22);
        ImapSourceIdentity archive =
                new ImapSourceIdentity(
                        mailboxId, "Archive", 100, 22);

        assertThat(inboxOld).isNotEqualTo(inboxNew);
        assertThat(inboxOld).isNotEqualTo(archive);
    }
}
~~~

This test only checks the **domain model**; it does not prove database unique constraints are configured properly. Include integration tests against a database engine matching production.

### 20.3. Testing Unique Constraints with PostgreSQL

Using Testcontainers PostgreSQL or a production-compatible test database:

1. Insert row `(M1, INBOX, V1, UID10)`.
2. Insert the exact same source identity again with `ON CONFLICT DO NOTHING`.
3. Assert inbound row count = 1 and initial status was not reset.
4. Insert row `(M1, INBOX, V1, UID11)` with the **same `rfc_message_id`**.
5. Assert row count = 2.
6. Insert row `(M1, Archive, V1, UID10)`.
7. Assert row count = 3.
8. Insert row `(M1, INBOX, V2, UID10)`.
9. Assert row count = 4.

Do not use default H2 to prove PostgreSQL `ON CONFLICT`, row locks, or `SKIP LOCKED` behavior, as SQL dialects and concurrency semantics can differ.

### 20.4. Testing Atomic Cursor Advance

Scenario:

~~~text
Stored cursor: lastUid=100, validity=10
IMAP UIDNEXT snapshot: 121
Available UIDs: 101, 102, 108, 120

Expected:
  persist each available identity
  commit lastDiscoveredUid=120
  no skipping of UID121 arriving later
~~~

Add fault injection:

- Repository insert throws an exception before commit.
- Transaction rolls back completely.
- Cursor remains `100`.
- Next pass still scans UIDs `101..120`.

If code commits the cursor before inserting all records, this test must fail.

### 20.5. Testing UIDVALIDITY Reset

Fixture:

~~~text
Database: validity=100, cursor=700
IMAP server: validity=200, nextUid=41
~~~

Expectations:

- Does not scan from `UID 701`.
- Does not update `validity=200` while keeping `cursor=700`.
- Creates/activates the new generation with cursor 0 per policy.
- Scans UIDs in generation 200.
- Does not delete history from generation 100.
- Deduplicates business side effects if older messages reappear and policy deems them the same business item.

Forcing a test IMAP server to change `UIDVALIDITY` can be tricky; you can test **cursor service** logic with fake UID metadata while using GreenMail/IMAP servers in integration tests to verify real paths.

### 20.6. Testing Two Workers Claiming Concurrently

Scenario:

~~~text
Insert DISCOVERED row D1
Worker A and worker B claim at the same time
       |
       v
Exactly one obtains claimToken for D1
       |
       v
attempt_count = 1
one STARTED attempt row
~~~

With PostgreSQL, run two transactions on independent connections to verify `FOR UPDATE SKIP LOCKED`/claim-state logic. Then simulate lease expiration, have Worker C reclaim, and let Worker A attempt to write `PROCESSED` with the old token: the update count must be 0.

### 20.7. Testing Business Handler Idempotency

Suppose an inbound email creates a ticket:

~~~text
Attempt 1:
  inboundId=D1
  create ticket T1
  commit support_ticket_origin(D1 -> T1)
  commit inbound_message.PROCESSED

Attempt 2 (manual replay):
  inboundId=D1
  should not create T2
  result still maps to T1
~~~

If side effects live outside the database, tests must simulate external API retries with the **same idempotency key** and duplicate responses per API contract.

### 20.8. Testing Webhook Redelivery

- Event E1 with valid signature → persisted to DB.
- Send E1 again → single record/event, business counter does not increment twice.
- Invalid signature → nothing persisted.
- Event ID E1 from another provider → namespaced properly per contract.
- Same provider message ID with different event ID → do not treat all events as identical.
- Out-of-order events → projection is not overwritten wrongly.

Never test webhooks with a controller returning `200` without verifying the transaction committed; that is precisely where systems tend to drop events.

### 20.9. Testing Real IMAP with a Mock Mail Server

A test mail server supporting SMTP+IMAP such as **GreenMail** can be used to:

1. Start a test mailbox with a dedicated account and dummy credentials.
2. Send a sample email via SMTP to the test mailbox.
3. Connect over IMAP using Jakarta Mail.
4. Read UID, `UIDVALIDITY`, and RFC `Message-ID`.
5. Run the poller and assert the inbound row is persisted.
6. Run the poller again and assert no duplicate row.
7. Mark `SEEN` via another IMAP client; assert the poller does not skip unrecorded emails.
8. Run the worker and assert database state and business side effects.

Choose a GreenMail dependency compatible with `jakarta.mail.*` in your Spring Boot version. SMTP sinks that only capture and hold mail like Mailpit **do not necessarily provide an IMAP server**, so mail-receiving tests require a tool supporting the right protocol.

Test servers validate the local SMTP→IMAP flow, not the behavior of every production IMAP provider; run staging smoke tests with an authorized account if your provider has special quirks.

## 21. Runbook: Received Email Was Processed Twice

When users report one email created two tickets or an invoice was imported twice:

**Step 1 — Locate internal inbound IDs.** Identify the ticket/business records, source mailbox, discovery timestamps, and request correlations. Never search solely by subject, as subjects can collide.

**Step 2 — Compare source identities.** Did the two side effects come from:

- The exact same `(mailbox, folder, uid_validity, uid)`? → Likely a **claim/idempotency** bug.
- Two different UIDs with the same RFC `Message-ID`? → Possibly two distinct emails, a copy/forward, or duplicate `Message-ID`.
- Two different folders/epochs with identical content? → Check moves/copies/`UIDVALIDITY` resets.
- Both webhook and IMAP ingesting one email? → Check multi-source business deduplication.

**Step 3 — Inspect attempt history.** Did multiple workers claim concurrently? Did `PROCESSING` expire its lease while the old worker continued side effects? Was there an error after the side effect before committing `PROCESSED`?

**Step 4 — Verify unique constraints.** Do `uq_inbound_imap_identity` and the unique business origin key exist in the real database? Application-level `existsBy...` followed by insert can race.

**Step 5 — Determine impact.** How many tickets/comments/billing operations were duplicated? Reconcile per business rules without automatically deleting original emails or audit trails.

**Step 6 — Fix and re-test.** Add atomic claim/fencing and business idempotency keys, and test crash windows before re-enabling workers.

### 21.1. Why Is "UNIQUE(Message-ID)" Not a Complete Fix?

It may cut down some duplicates while introducing new failures:

- Blocks legitimate emails when senders reuse headers.
- Can be abused by attackers to make new emails get ignored.
- Fails when emails **lack a `Message-ID`**.
- Does not solve cases where a business side effect occurred before state commit failed.
- Does not distinguish webhook event IDs from original emails.

Preventing duplicate processing requires **source-level dedup + business-level idempotency**, not merely a unique index on a header.

## 22. Runbook: Messages Missed After Restart

Symptom: the mailbox contains emails, yet the application creates no records—typically seen after deploys, restores, or connection interruptions.

1. Check that the configured mailbox/folder is right and the account has read permissions.
2. Check `last_successful_scan_at` and poller error codes.
3. Compare current `UIDVALIDITY` against the DB; if different, do not use the old cursor.
4. Confirm `last_discovered_uid` is not higher than the new generation's upper bound.
5. Check whether code uses `getMessageNumber()` or `SEEN` as a checkpoint.
6. Check whether the cursor was committed **before** all inbound rows were inserted.
7. Check whether users/clients moved/expunged emails before the poller scanned.
8. If backfill is needed, re-select the UID/generation range under a mailbox-level lock and let unique constraints prevent duplicate inserts.
9. Never reset all `PROCESSED` states back to `DISCOVERED` to "re-read just to be sure".

### 22.1. Handling Generation-Mismatched Cursors

Example:

~~~text
Database:
  UIDVALIDITY=1422
  last_discovered_uid=58000

IMAP:
  UIDVALIDITY=1433
  UIDNEXT=90
~~~

The right fix is recording the **new UID generation** and scanning from the start of the new generation, rather than continuing at `UID 58001`. Keep audits for emails processed in the old generation; if copies reappear, handle them via business deduplication policy.

## 23. Runbook: PROCESSING State Never Finishes

An inbound record staying `PROCESSING` unusually long can be caused by:

- Worker died after claiming.
- IMAP fetch hung or oversized attachment.
- MIME parser/antivirus scanner running past deadline.
- External ticket API not responding.
- Lease/heartbeat failing.
- Database unable to persist outcome.

Before reclaiming:

1. Inspect `lease_until` and the current claim token.
2. Inspect worker heartbeats and logs by internal inbound ID.
3. Determine whether external side effects **may have already completed**.
4. If the worker simply died before processing, retrying is safe.
5. If external API outcome is ambiguous, use reconciliation/idempotency keys before calling again.
6. When a new worker claims, generate a new claim token and require all state updates to check it.
7. Track reclaim counts and causes to tune timeouts/concurrency.

Never increase lease duration infinitely just to mask stuck workers. Conversely, an overly short lease can cause two workers to double-process a large MIME attachment; choose balanced timeouts and heartbeats.

## 25. Frequently Asked Questions

**"Are `Message-ID` and IMAP UID the same?"**  
No. RFC `Message-ID` is an email header created by the sender; an IMAP UID is assigned by the mailbox server to a folder entry and is valid within its `UIDVALIDITY` scope. They serve two different purposes.

**"Should `Message-ID` be the primary key?"**  
Usually not when ingesting untrusted emails. The header can be missing, duplicated, or spoofed. Use an internal UUID as primary key and a unique source identity for IMAP, keeping `Message-ID` for search/threading.

**"What if an email has no `Message-ID`?"**  
Still record it using a source key like `mailbox + folder + UIDVALIDITY + UID`. Leave `rfc_message_id=NULL` and enable correlation features only when sufficient data exists.

**"If the same `Message-ID` appears twice, is it a duplicate?"**  
Not necessarily. It could be the same message copied/forwarded, a sender bug, or a spoofed message. Deduplicate sources by UID; deduplicate business actions based on verified conditions and keys.

**"What if `Message-ID` differs while the body is identical?"**  
Two emails can still be two valid separate actions. Content hashes should only be a supporting signal, never blindly merging all messages with matching bodies.

**"Can we store a hash of `Message-ID` instead of the raw string?"**  
Yes, if exact lookup is needed while minimizing raw header storage, though hashing does not solve duplicate/spoofed `Message-ID`s. Use stable canonicalization and appropriate security policies.

**"Do we need to store the IMAP folder name?"**  
Yes, if using UID as source identity; the same UID in two folders does not mean the same entry. Store a stable folder key aligned with the account/server namespace.

**"Are UIDs contiguous like 1, 2, 3?"**  
Not necessarily. UIDs can have gaps because messages no longer exist on the server. Pollers must handle UID gaps without treating them as errors.

**"What is `UIDVALIDITY` for?"**  
It indicates which UID generation a folder belongs to. If `UIDVALIDITY` changes, old UIDs must not be used to identify messages in the new generation.

**"Should we persist `message.getMessageNumber()`?"**  
It can be logged transiently for session debugging, never as a durable identifier or checkpoint; message numbers shift when a folder is expunged.

**"How do we avoid missing new mail when scanning a UID range?"**  
Pick the upper bound from a valid UID metadata snapshot (e.g., `UIDNEXT-1`), save every record in the range, and commit the cursor in the same transaction. Never advance the cursor to a future UID not yet issued by the server.

**"Can we read only `UNSEEN` to save time?"**  
Only as a secondary filter if business rules tolerate the risk. For systems requiring complete ingestion, `SEEN` flags can be altered by users/mail clients; unique UID + cursor is far more reliable.

**"Can we mark `SEEN` once processed?"**  
Yes, as a post-processing action, while database `PROCESSED` remains the source of business truth. If the IMAP operation fails, never re-execute business side effects.

**"If an email moves to `Processed`, does its UID stay the same?"**  
Do not assume so. The UID issued in the destination folder can differ; identity must include folder and `UIDVALIDITY`.

**"Why is the cursor past an email's UID while its row is still `RETRY`?"**  
The discovery cursor only indicates the email was found and persisted. Processing state is independent; a lower-UID email can still be retrying while higher UIDs are already `PROCESSED`.

**"Can one inbound mailbox have multiple pollers?"**  
Yes, provided there is a mailbox-level lease or explicit range/completion partitioning. With a single simple cursor, one coordinated poller per folder makes avoiding skips and races much easier.

**"What if the server deletes the email before the worker fetches it?"**  
If only the UID was stored, the content may be gone. Mark a source-missing error or recover from a snapshot; for critical workflows, store a durable payload before it is too late.

**"Does POP3 have `UIDVALIDITY`?"**  
Not in the IMAP sense. POP3 usually has `UIDL` to identify messages across sessions when supported by the server. Never use POP3 sequence numbers as durable keys.

**"What if POP3 does not support `UIDL`?"**  
Consider switching to IMAP/an inbound provider, or use snapshots + monitored fingerprints/heuristics. RFC `Message-ID` is not a perfect substitute.

**"Is a webhook event ID the email's `Message-ID`?"**  
Not necessarily. Event ID describes a provider delivery event, provider message ID is their internal ID, and RFC `Message-ID` is the sender header. Store them separately per provider schema.

**"Why does returning HTTP 200 on a webhook still lose emails?"**  
If you return `200` before saving the event to a database/durable queue, a crash can lose the event even though the provider believes delivery succeeded. Ack only after durable intake.

**"What do at-least-once and idempotent mean?"**  
At-least-once permits the same email to reach a handler more than once. Idempotency guarantees repeated execution causes no unintended extra side effects, using business keys and transactions/remote idempotency keys.

**"Does a claim token guarantee only one ticket is created?"**  
Not by itself. Claim tokens protect worker state updates, yet external side effects can run twice inside a lease-race window. Require a unique business origin or idempotency key on the actual operation.

**"Should every MIME error be retried?"**  
No. Corrupt MIME or malicious attachments rarely turn valid a few seconds later. Classify, quarantine/`FAILED`, and investigate.

**"After how many retries should a message become `FAILED`?"**  
There is no single number. Base it on SLA, likelihood the mail source still exists, error category, business deadlines, and cost. Store `max_attempts` and clear terminal reasons.

**"What if creating a ticket via external API succeeds, then DB commit fails?"**  
The side-effect outcome becomes ambiguous. Use a remote idempotency key, transactional outbox, or reconciliation; never resend with a brand-new key on every retry.

**"Can `In-Reply-To` identify a ticket?"**  
It can serve as a signal to locate candidate tickets alongside `References` or reply tokens. Never skip tenant/sender authorization checks, as headers can be spoofed.

**"Is `Subject: Re: Ticket #123` enough to attach a comment?"**  
No. Subjects can be edited or spoofed. Require reliable correlation and permission checks before updating tickets.

**"Should the entire raw email be stored in the database?"**  
It depends on business needs. If replay/auditing is required, store encrypted MIME snapshots in object storage with a reference in the DB. Bound sizes, access control, retention, and malicious attachment handling.

**"Does `PROCESSED` mean the mail was deleted from the server?"**  
No. It means the business handler completed according to the application's definition. `SEEN`, `MOVE`, or `DELETE` on the server are separate operations.

**"Why does a `UIDVALIDITY` reset increase duplicate counts?"**  
When the UID generation changes, old copies can be rediscovered under new identities. Technically these are new sources; business deduplication/reconciliation decides whether a new side effect is needed.

**"Should inbound metrics attach email addresses as labels?"**  
No. It explodes time-series cardinality and leaks PII. Use bounded groups/source types/workflows/error categories, keeping UUIDs/UIDs in access-controlled logs if needed.

## 26. Checklist for Designing Message ID and State Persistence

### Source Identification

1. Identify the receiving source: IMAP, POP3 `UIDL`, or inbound webhook.
2. For IMAP, use composite identity `mailbox_id + folder_key + uid_validity + uid`.
3. Never use IMAP message sequence numbers as checkpoints.
4. Check `UIDVALIDITY` at the start of every scan and handle generation changes.
5. For POP3, use `UIDL` when supported by the server; never sequence numbers.
6. For webhooks, store provider ID and event/message ID per the provider's exact contract.
7. Store RFC `Message-ID` as nullable, non-unique metadata for threading/correlation.
8. Never trust `From`, `Message-ID`, `Subject`, or `References` headers as proof of ownership.
9. Maintain a stable internal inbound UUID linking processing state and audits.

### Discovery and Cursors

10. The cursor tracks **discovery** progress, not business processing progress.
11. Read UIDs up to an observed upper bound; never arbitrarily advance past `UIDNEXT-1`.
12. Expect UID gaps when messages are expunged.
13. Insert inbound rows and advance the cursor in the **same transaction**.
14. Use unique source identity + `ON CONFLICT DO NOTHING`; never reset `PROCESSED` on re-scan.
15. With multiple pollers, use mailbox-level ownership or cursor compare-and-swap.
16. Never rely on `SEEN`/`UNSEEN` flags to prevent duplicate processing.
17. If processing must survive source mutations, persist a bounded durable MIME snapshot.

### Processing and Idempotency

18. Clearly define `DISCOVERED`, `PROCESSING`, `RETRY`, `PROCESSED`, `FAILED`, `IGNORED`, and `QUARANTINED` as needed.
19. Claim jobs atomically and increment `attempt_count` right at the claim boundary.
20. Use leases and claim tokens/fencing to stop stale workers from writing state.
21. When side effects live in the same DB, commit them alongside `PROCESSED` in one transaction.
22. Maintain a unique business operation key or origin mapping so tickets/comments are never duplicated.
23. For external systems, use idempotency keys or outbox/reconciliation.
24. Retry only recoverable errors, with backoff, jitter, and attempt caps.
25. `FAILED`/dead-letter records must retain error code, stage, attempt history, and audit metadata.
26. Redrives must verify permissions, payload availability, and prior side-effect state.

### Threading and Access Control

27. Distinguish the current email's `Message-ID` from `In-Reply-To`/`References` pointing to prior messages.
28. Use `References`/`Message-ID` as conversation-lookup signals, not authorization.
29. Verify ticket/tenant/sender permissions before attaching replies.
30. Never match conversations solely by `Subject`.
31. For DSNs/bounces, process per recipient and verify source/correlation before suppression.

### Security, Testing, and Operations

32. Mailbox credentials/OAuth secrets come from secure runtime sources.
33. Use IMAPS/TLS with endpoint hostname verification.
34. Limit MIME size, part count, attachments, and parser depth.
35. Quarantine suspicious data; never execute unverified attachments.
36. Never place MIME bodies, passwords, PII, or raw `Message-ID`s into metric labels.
37. Enforce retention/encryption/RBAC on snapshots and audits.
38. Test duplicate headers, missing headers, UID gaps, `UIDVALIDITY` changes, and folder moves.
39. Test transaction rollbacks between row inserts and cursor commits.
40. Test two workers claiming concurrently, expired leases, and stale worker updates.
41. Test webhook signatures/redeliveries and side-effect idempotency.
42. Track metrics for freshness, backlog age, retry counts, failed/quarantined items, and `UIDVALIDITY` resets.

## 27. End-to-End Example: Support Email Processed Exactly Once

Suppose a system receives mail at `support@example.com` and creates tickets. A customer sends an email:

~~~text
From: customer@example.net
To: support@example.com
Subject: Cannot log in
Message-ID: <m-a1@example.net>
~~~

### Step 1 — Discovery

The poller connects over IMAP:

~~~text
mailbox_id = M1
folder_key = INBOX
UIDVALIDITY = 500
UID = 2201
rfc_message_id = <m-a1@example.net>
~~~

The poller persists the row:

~~~text
inbound_id = D1
source_identity = (M1, INBOX, 500, 2201)
status = DISCOVERED
attempt_count = 0
~~~

The unique constraint ensures that even if the poller reads UID 2201 again, only one `D1` exists. After persisting the batch, the cursor can advance to UID 2201 or a safely scanned upper bound.

### Step 2 — Worker Claim

Worker A performs an atomic claim:

~~~text
inbound_id = D1
status = PROCESSING
attempt_count = 1
claim_token = C1
lease_until = ...
~~~

Attempt history records `STARTED`. The worker reads the snapshot or fetches `UID=2201` in `UIDVALIDITY=500`, parses MIME, and validates policies.

### Step 3 — Ticket Creation

Inside a single transaction:

~~~text
ticket_id = T1
support_ticket_origin(D1 -> T1)
inbound_message(D1).status = PROCESSED
processed_at = ...
COMMIT
~~~

If the worker crashes before commit, the transaction rolls back and another worker can retry. If commit succeeds but the worker crashes before setting `SEEN` or moving the email, the database already knows `D1` is processed.

### Step 4 — Poller Re-Scans

IMAP still contains UID 2201. The poller attempts to insert the same source identity, hits the unique constraint conflict, and executes `DO NOTHING`.

~~~text
Existing D1:
  status = PROCESSED
  ticket_id = T1
No new ticket
~~~

Even if the email was moved to another folder and re-scanned as a new source copy, business policy can check mappings/correlations to decide whether a valid new action is warranted.

### Step 5 — Customer Sends a Reply

New email:

~~~text
Message-ID: <m-a2@example.net>
In-Reply-To: <outbound-ticket-T1@mail.example.com>
Subject: Re: Cannot log in
~~~

This is a **brand-new inbound message**, with a new UID and a new internal ID. The handler can locate ticket T1 via `In-Reply-To`/mappings from the outbound message, but attaches the comment only after verifying the sender and permissions. Never treat a reply as a duplicate of the original email merely because the subject matches.

### Step 6 — Reconciliation After UIDVALIDITY Reset

Weeks later, the server restores the folder and `UIDVALIDITY` changes from 500 to 600. The poller starts a new generation instead of scanning with the old cursor. If a copy of email D1 appears under a new UID:

- The database may store a **new source record** reflecting the real IMAP entry.
- It does not create ticket T2 if business deduplication determines it is merely a copy of the same business request per permitted evidence.
- Never rely solely on `<m-a1@example.net>` to merge if content/source is untrusted.
- Record an audit entry so operations knows a UID generation reset occurred.

### Key Principles to Remember

- **RFC `Message-ID` is not an IMAP UID** and is not reliable enough as a system-wide deduplication key.
- **IMAP UIDs are meaningful only within a mailbox/folder with the same `UIDVALIDITY`**.
- **Discovery cursors differ from processing states**; scanning past a higher UID does not prove lower UIDs finished business processing.
- **Never replace database state with `SEEN`/`UNSEEN` or message sequence numbers**.
- **Persist source identities and cursors in the same transaction** to avoid crashes dropping UIDs.
- **Atomic claims + attempt history + fencing tokens** handle concurrency; **business idempotency** prevents duplicate side effects.
- **`In-Reply-To`/`References` assist threading**, never authorization.
- **Quarantine and retries need explicit policies**, never swallowing errors or retrying infinitely.
- **Keep snapshots, retention, and data controls** if the IMAP source could disappear before workers process it.

## Conclusion

**Storing message IDs and processing state** is the foundation for building a reliable email-receiving system in a Spring Framework Mail application. Rather than treating the `Message-ID` header or `SEEN` flag as "finished reading", the application must persist **properly scoped source identities**, generate an **internal ID**, and track **discovery progress** and **business state** as two independent layers.

With IMAP, the composite key `mailbox + folder + UIDVALIDITY + UID` alongside transactional checkpoints prevents missing or misidentifying messages. With webhooks, event IDs must be verified and deduplicated per provider; with POP3, `UIDL` supports cross-session tracking when available. Finally, **leased claims, idempotent processing, attempt history, and retry/dead-letter strategies** enable the system to recover from crashes while preserving explainability, auditability, and customer data protection.
