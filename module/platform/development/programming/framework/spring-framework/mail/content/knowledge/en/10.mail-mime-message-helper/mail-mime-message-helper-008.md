# Attachment name and content type

A Spring Boot application sends electronic invoices to customers. The file on the server is named `8f6c9e0a-7a62-4b59-9bc9.pdf`, but the recipient needs to see **`hoa-don-DH1024.pdf`** in the email. At the same time, the email client must understand that this is a PDF file rather than a piece of plain text. If the invoice has a Vietnamese name, such as `Hóa đơn tháng 11.pdf`, the problem also involves how **filenames in MIME headers** are encoded.

In **Spring Framework Mail**, `MimeMessageHelper` helps solve those needs with methods such as:

```java
helper.addAttachment("hoa-don-DH1024.pdf", pdfResource, "application/pdf");
```

These three parameters are not the same thing: **display filename**, **data source**, and **MIME content type**. Understanding each part helps the application create emails that are easy to read, properly formatted, compatible, and do not accidentally leak internal paths or trust the wrong file type.

## 1. What is an attachment in a MIME email?

An **attachment** is a content part (*MIME body part*) sent along with the email message, usually for the recipient to view or download as an independent file.

An email containing text and a PDF can be organized as follows:

```text
MimeMessage
├── From: billing@example.com
├── To: customer@example.net
├── Subject: Invoice for order DH1024
└── multipart/mixed
    ├── text/plain; charset=UTF-8
    │   └── "Please see the attached invoice."
    └── application/pdf
        ├── Content-Disposition: attachment; filename="hoa-don-DH1024.pdf"
        ├── Content-Transfer-Encoding: base64
        └── [PDF data encoded for transport]
```

This is an illustrative structure: the actual multipart boundaries, parameter names, encoding, and header ordering are generated by the Jakarta Mail library. An email may also contain HTML, inline images, or multiple attachments.

Components to distinguish:

| Component | Role | Example |
|---|---|---|
| **Attachment name** (*filename*) | Suggested name for the email client to display/save the file | `hoa-don-DH1024.pdf` |
| **MIME content type** | Specifies the type of data in the MIME part | `application/pdf` |
| **Data source** | Supplies the actual bytes of the file to the transport | `FileSystemResource`, `ByteArrayResource`, `DataSource` |
| **Content-Disposition** | Hints whether to display as an attached file or inline content | `attachment` |
| **Content-Transfer-Encoding** | How bytes are represented on the MIME transport path | `base64` |
| **Content-ID** | Identifier to reference a part in HTML, usually used for inline images | `<brand-logo>` |

You should not treat all of these as “the file extension”. The name `report.pdf` is only a metadata string; whether the file is truly a PDF depends on the **content bytes** and how the application created/verified it.

### 1.1. The filename on disk and the display name in the email are two different things

Example:

```text
Source path:
    /srv/app/storage/2026/11/8f6c9e0a-7a62-4b59.pdf

Attachment name sent to customer:
    hoa-don-DH1024.pdf
```

When using `MimeMessageHelper.addAttachment(...)`, the application usually passes the **display name** as the first parameter and the data source as the next parameter. That way it does not have to put internal file paths or storage identifiers into headers for the recipient.

Example:

```java
FileSystemResource pdf =
        new FileSystemResource(Path.of(
                "storage", "2026", "11", "8f6c9e0a-7a62-4b59.pdf"));

helper.addAttachment("hoa-don-DH1024.pdf", pdf, "application/pdf");
```

In the email, the desired name is `hoa-don-DH1024.pdf`. `MimeMessageHelper` does not change the physical filename on disk.

## 2. Content-Type and Content-Disposition: two headers with different purposes

### 2.1. `Content-Type` indicates the data type

A MIME part can contain:

```text
Content-Type: application/pdf
```

Meaning: the part is described as a **PDF** file. A few common types:

| Content | Common MIME type |
|---|---|
| PDF | `application/pdf` |
| Plain text | `text/plain` |
| HTML | `text/html` |
| CSV | `text/csv` |
| JSON | `application/json` |
| PNG | `image/png` |
| JPEG | `image/jpeg` |
| ZIP | `application/zip` |
| Microsoft Word (.docx) | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| Microsoft Excel (.xlsx) | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| Unknown binary type | `application/octet-stream` |

**A MIME type is metadata declared by the sender, not a safety verification mechanism for the file.** Someone can name non-PNG data `photo.png` or send HTML content with a `.txt` extension. A receiving application should not blindly trust `Content-Type` or the extension when deciding how to handle untrusted files.

### 2.2. `Content-Disposition` describes display intent

Example:

```text
Content-Disposition: attachment; filename="hoa-don-DH1024.pdf"
```

- **`attachment`**: hints to the email client to present the content as an attached file.
- **`filename`**: hints the filename when saving or displaying.

Conversely, HTML content referencing an image can use:

```text
Content-Disposition: inline
Content-ID: <brand-logo>
Content-Type: image/png
```

However, **the email client is the party that decides the final display**. Some clients allow viewing PDFs right inside the interface; some clients display inline images as attachments. That is not necessarily a bug in Spring Mail.

### 2.3. `Content-Transfer-Encoding` is not Content-Type

A binary PDF is usually converted to base64 to be transported safely over email:

```text
Content-Type: application/pdf
Content-Disposition: attachment; filename="hoa-don-DH1024.pdf"
Content-Transfer-Encoding: base64

JVBERi0xLjQKJcTl8uXrp...
```

In the example:

- `application/pdf` is the **asserted content type**.
- `attachment` is the **suggested display method**.
- `base64` is **how bytes are represented in the MIME part during transport**.

`base64` does not turn the PDF into plain text and does not cryptographically secure the content. The email client decodes base64 to recover the original file bytes.

## 3. How does `MimeMessageHelper.addAttachment(...)` work?

In Spring Boot, when needing to send attachments, use `JavaMailSender` to create a `MimeMessage` and a `MimeMessageHelper` in **multipart mode**.

```java
import jakarta.mail.internet.MimeMessage;
import org.springframework.core.io.FileSystemResource;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;

import java.nio.file.Path;

MimeMessage message = mailSender.createMimeMessage();
MimeMessageHelper helper =
        new MimeMessageHelper(message, true, "UTF-8");

helper.setFrom("billing@example.com");
helper.setTo("customer@example.net");
helper.setSubject("Invoice for order DH1024");
helper.setText("Please see the attached PDF file.", false);

FileSystemResource pdf = new FileSystemResource(
        Path.of("storage", "invoice.pdf"));
helper.addAttachment("hoa-don-DH1024.pdf", pdf, "application/pdf");

mailSender.send(message);
```

Here:

1. `createMimeMessage()` creates the email object represented by Jakarta Mail.
2. The constructor `MimeMessageHelper(message, true, "UTF-8")` enables **multipart** and sets the charset used when the helper creates content.
3. `addAttachment(...)` adds an attachment MIME part.
4. `mailSender.send(message)` sends **the exact message object** built by the helper.

If using a constructor with `multipart=false`, `addAttachment(...)` cannot create the required multipart structure; the helper will report an error. Choose multipart mode right when creating the helper.

### 3.1. Common overloads

Common ways to add attachments:

```java
// 1. Physical file
helper.addAttachment("report.pdf", pdfFile);

// 2. Resource readable from file
helper.addAttachment("report.pdf", new FileSystemResource(pdfFile));

// 3. Resource and explicit content type
helper.addAttachment(
        "report.pdf",
        new FileSystemResource(pdfFile),
        "application/pdf");

// 4. Byte array in memory and explicit content type
helper.addAttachment(
        "export.csv",
        new ByteArrayResource(csvBytes),
        "text/csv");

// 5. Jakarta Activation DataSource
helper.addAttachment("report.pdf", dataSource);
```

In the illustration snippet, `pdfFile` is a `java.io.File`, `csvBytes` is a `byte[]`, and `dataSource` is a prepared `jakarta.activation.DataSource`. `ByteArrayResource` and `FileSystemResource` belong to `org.springframework.core.io`.

Choose the overload based on the **actual available byte source** and how much you want to control `Content-Type`, not just based on the file extension.

### 3.2. When content type is not passed, where does the library get it?

Some overloads allow omitting the `contentType` parameter. In that case, the helper can use **`FileTypeMap`** to infer the content type from the **attachment name** and the environment's mapping configuration.

This is convenient for familiar extensions, but has limitations:

- The mapping may not recognize custom or new extensions.
- Mapping by name **does not inspect actual bytes**.
- The same file can be classified differently if the mapping/runtime changes.
- If unrecognized, it may fall back to a generic binary type like `application/octet-stream`.

For files **generated by the application itself whose format is known accurately**, specify an explicit content type:

```java
helper.addAttachment(
        "invoice.pdf", new FileSystemResource(invoicePath), "application/pdf");
```

For untrusted files uploaded by users, **never use the extension alone to decide whether a file is safe**. You must inspect the format and enforce upload policies before allowing an email to carry that file.

## 4. How is the attachment name put into headers?

A MIME message may have the following fields:

```text
Content-Type: application/pdf; name="hoa-don-DH1024.pdf"
Content-Disposition: attachment; filename="hoa-don-DH1024.pdf"
Content-Transfer-Encoding: base64
```

This is a **structural example**. Some libraries/clients may generate `filename` in `Content-Disposition`, `name` in `Content-Type`, or both for compatibility. When determining the filename, do not assume **both parameters are always present**.

### 4.1. A filename is not a path

The name:

```text
hoa-don-DH1024.pdf
```

differs from the path:

```text
/var/app/data/customers/1024/invoice.pdf
C:\services\billing\exports\invoice.pdf
```

Only send the **display name**, do not send internal paths. Exposing paths can reveal system structure or sensitive directory names.

The `attachmentFilename` parameter in `addAttachment` is metadata for the email client; it should not be mixed with the mechanism that locates the **source file**.

### 4.2. What makes a compatible filename?

Highly compatible names usually:

- Are short and meaningful to the recipient: `invoice-DH1024.pdf`.
- Have an extension matching the actual format: `.pdf` for PDF, `.csv` for CSV.
- Contain no CR, LF, NUL, or control characters.
- Contain no path separators `/`, `\` or directory information.
- Are not overly long; avoid causing trouble for the recipient's client and operating system.
- Do not use misleading names, such as `invoice.pdf.exe` or an extension different from the content's true nature.

The display name **does not have to equal the filename on the server**. The application can store files by UUID to prevent collisions and send a clear name to the customer.

## 5. Vietnamese attachment names, Unicode, and encoding mechanisms

A filename could be:

```text
Hóa đơn tháng 11.pdf
Bảng đối soát – Quý IV.xlsx
Hồ sơ Nguyễn Văn An.zip
```

These names contain Unicode characters. In traditional MIME, header parameters need to be **safely represented on the transport path**; you cannot assume every Unicode string placed verbatim into `Content-Disposition: filename=...` is compatible.

### 5.1. RFC 2231 and the filename parameter

One way to encode internationalized parameters is the extended syntax per **RFC 2231**, for example conceptually:

```text
Content-Disposition: attachment;
 filename*=UTF-8''H%C3%B3a%20%C4%91%C6%A1n%20th%C3%A1ng%2011.pdf
```

Meaning:

- `filename*` signals this is an extended parameter with charset and encoding.
- `UTF-8` indicates the character set.
- `''` here separates the charset from an empty language tag.
- Bytes unsuitable to appear directly are represented in percent-encoded `%HH` form.

RFC 2231 also has a mechanism to **split a long parameter into multiple parts** (*continuation*) when needed. This is a header-layer representation, not the filename the user should see after the email client decodes it.

**Do not replace the filename string with generic URL-encoding yourself and assume the header is standard.** MIME parameter syntax has its own rules; let Jakarta Mail handle the encoding, folding, and quoting process.

### 5.2. RFC 2047 is not the same as RFC 2231

**RFC 2047** defines encoded-words such as:

```text
=?UTF-8?B?...?=
```

It is usually used for **display names in address headers** or **Subject**, where encoded-words are allowed according to header rules.

**The `filename` parameter in `Content-Disposition`** has a different problem. RFC 2231 is the mechanism designed for **MIME parameters** with internationalized characters. Some applications and libraries have an RFC 2047-style filename encoding mechanism as a **compatibility option for certain email clients**, but encoded-word should not be regarded as the same standard syntax as RFC 2231 for every parameter position.

In Spring Framework, `MimeMessageHelper` has a `setEncodeFilenames(boolean)` option in supported versions, affecting how the helper handles filenames. Understand this as a **compatibility decision**; final behavior also depends on the Spring/Jakarta Mail version and the JavaMail provider's MIME properties.

Example only when compatibility with the target recipients has been verified:

```java
MimeMessageHelper helper =
        new MimeMessageHelper(message, true, "UTF-8");

// Option for email clients needing a specific filename encoding method.
// Do not enable by default without understanding provider/client behavior.
helper.setEncodeFilenames(true);

helper.addAttachment(
        "Hóa đơn tháng 11.pdf",
        new FileSystemResource(invoicePath),
        "application/pdf");
```

**Note:** enabling `setEncodeFilenames(true)` is not a universal answer to every Unicode error. When issues occur, inspect the actual generated headers, the Jakarta Mail version, parameter encoding settings, and the decoding capabilities of target email clients. For maximum compatibility without relying on Unicode characters in filenames, a meaningful ASCII name like `hoa-don-thang-11.pdf` is often a useful fallback.

### 5.3. Body content charset differs from filename charset

The configuration:

```java
new MimeMessageHelper(message, true, "UTF-8");
```

helps with generating MIME content and corresponding text fields. However, **body content**, **recipient display names**, **Subject**, and **the filename parameter** have **different header encoding rules**. Do not just set `charset=UTF-8` for `text/html` and concatenate a Unicode filename into `Content-Disposition` yourself.

When troubleshooting errors such as “recipient sees `=?UTF-8?...?=`”, “filename has garbled diacritics”, or “filename displays literal `%C3%A1`”, inspect the **attachment's MIME headers**, not just the body.

## 6. How to provide an explicit Content-Type

### 6.1. PDF

```java
helper.addAttachment(
        "hoa-don-DH1024.pdf",
        new FileSystemResource(invoicePath),
        "application/pdf");
```

Since the system creates a PDF invoice file and knows the format, `application/pdf` describes the meaning accurately.

### 6.2. CSV

```java
byte[] csvBytes = """
        order_id,total
        DH1024,120000
        DH1025,95000
        """.getBytes(StandardCharsets.UTF_8);

helper.addAttachment(
        "don-hang.csv",
        new ByteArrayResource(csvBytes),
        "text/csv; charset=UTF-8");
```

In the example:

- The data is generated as UTF-8 bytes.
- Content type `text/csv` indicates the data type.
- The `charset=UTF-8` parameter describes the charset of the text part, when the library/recipient processes it per MIME rules.

**CSV also has an issue regarding data interpretation by spreadsheet applications**. If a user-entered field starts with `=`, `+`, `-`, or `@`, spreadsheet software may interpret it as a formula depending on context. Sending CSV requires an additional safety-handling step matching the intended use, not just setting the right content type.

### 6.3. JSON

```java
byte[] jsonBytes = """
        {"orderId":"DH1024","status":"PAID"}
        """.getBytes(StandardCharsets.UTF_8);

helper.addAttachment(
        "order.json",
        new ByteArrayResource(jsonBytes),
        "application/json");
```

JSON is standardized on Unicode/UTF-8 in modern interchange; `application/json` is the commonly used MIME type. Creating the file from a Java string still requires the right encoding when converting to bytes.

### 6.4. ZIP or unidentified data

```java
helper.addAttachment(
        "documents.zip",
        new FileSystemResource(zipPath),
        "application/zip");
```

When the format is not known with certainty or intentionally sending generic binary data, `application/octet-stream` may be appropriate. However, choosing a generic type does not make a dangerous file safe and does not bypass the receiving system's attachment filtering policy.

## 7. Complete Spring Boot example: building filenames from business logic

Suppose the application sends PDF invoices:

- Files on the server are stored by an immutable code or UUID.
- The recipient wants to see `invoice-DH1024.pdf`.
- The MIME type must be `application/pdf`.
- Do not pass client paths directly into the sender.
- Only send files the application has permission to read and has generated/verified.

### 7.1. Dependency and SMTP configuration

Example with Gradle:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-mail'
}
```

`application.yml` for port 587 submission with STARTTLS:

```yaml
spring:
  mail:
    host: ${MAIL_HOST}
    port: 587
    username: ${MAIL_USERNAME}
    password: ${MAIL_PASSWORD}
    protocol: smtp
    default-encoding: UTF-8
    properties:
      "[mail.smtp.auth]": true
      "[mail.smtp.starttls.enable]": true
      "[mail.smtp.starttls.required]": true
      "[mail.smtp.ssl.checkserveridentity]": true
      "[mail.smtp.connectiontimeout]": 5000
      "[mail.smtp.timeout]": 10000
      "[mail.smtp.writetimeout]": 10000
```

Environment variables are supplied by the deployment infrastructure. This is an example for a server supporting STARTTLS on 587, not the right config for every SMTP provider. Providers using implicit TLS on 465 need a configuration matching that mechanism.

### 7.2. Invoice sending service

```java
package com.example.mail;

import jakarta.mail.MessagingException;
import jakarta.mail.internet.MimeMessage;
import org.springframework.core.io.FileSystemResource;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.mail.javamail.MimeMessageHelper;
import org.springframework.stereotype.Service;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Objects;

@Service
public class InvoiceMailer {

    private static final long MAX_PDF_BYTES = 12L * 1024 * 1024;
    private final JavaMailSender mailSender;

    public InvoiceMailer(JavaMailSender mailSender) {
        this.mailSender = mailSender;
    }

    public void sendInvoice(
            String customerEmail,
            String orderCode,
            Path storedInvoice)
            throws IOException, MessagingException {

        Objects.requireNonNull(customerEmail, "customerEmail");
        Objects.requireNonNull(orderCode, "orderCode");
        Objects.requireNonNull(storedInvoice, "storedInvoice");

        // The file path here is provided by a trusted storage layer,
        // DO NOT accept an arbitrary Path directly from the user.
        if (!Files.isRegularFile(storedInvoice)
                || !Files.isReadable(storedInvoice)) {
            throw new IllegalArgumentException(
                    "Invoice PDF is not a readable file");
        }

        if (Files.size(storedInvoice) > MAX_PDF_BYTES) {
            throw new IllegalArgumentException("Invoice PDF is too large");
        }

        // orderCode is an identifier controlled at the business layer,
        // e.g. only [A-Za-z0-9-] with a length limit.
        if (!orderCode.matches("[A-Za-z0-9-]{1,40}")) {
            throw new IllegalArgumentException("Invalid order code");
        }

        MimeMessage message = mailSender.createMimeMessage();
        MimeMessageHelper helper =
                new MimeMessageHelper(message, true, "UTF-8");

        helper.setFrom("billing@example.com", "Billing department");
        helper.setTo(customerEmail);
        helper.setSubject("Invoice for order " + orderCode);
        helper.setText(
                "Please see the attached PDF invoice for order "
                        + orderCode + ".", false);

        String visibleFilename = "invoice-" + orderCode + ".pdf";

        helper.addAttachment(
                visibleFilename,
                new FileSystemResource(storedInvoice),
                "application/pdf");

        mailSender.send(message);
    }
}
```

The snippet above illustrates controlling the **attachment display name** from business data and **explicit content type**. In a real deployment, you must add email address checking, requester authentication, invoice download authorization, order status checks, PDF format verification, and send error handling.

Especially important: **`Files.isRegularFile(...)` and `Files.size(...)` do not prove the file's bytes are a PDF**. For files generated by the application itself via a trusted PDF library, the format can be assured at the generation step. For uploaded files, there must be a separate verification and content-control workflow.

### 7.3. Why build the display name from the order code?

Example physical file:

```text
storage/2026-11/3d8df61b-1b79-4eb2-ae2a.bin
```

The file may be generated/renamed by storage and not carry the original name. The name in the email is built from the validated order code:

```text
invoice-DH1024.pdf
```

The recipient sees a meaningful name without the application having to expose the physical filename or internal path. If using a customer's name or phone number in the filename, consider **privacy**, because attachment names can appear in previews, mail gateway logs, or security scanning systems.

## 8. Passing bytes in memory: ByteArrayResource and DataSource

Not every attachment is pre-saved as a physical file. CSV/JSON reports or small documents may be generated right in memory.

Example:

```java
import java.nio.charset.StandardCharsets;
import org.springframework.core.io.ByteArrayResource;

String csv = "code,total\\r\\nDH1024,120000\\r\\n";
byte[] bytes = csv.getBytes(StandardCharsets.UTF_8);

helper.addAttachment(
        "summary.csv",
        new ByteArrayResource(bytes),
        "text/csv; charset=UTF-8");
```

`ByteArrayResource` keeps bytes in memory and provides a **fresh InputStream when requested**. This is a useful characteristic because Jakarta Mail can read attachment content more than once during serialization/sending.

However, this approach has drawbacks:

- All bytes reside on the JVM heap.
- Large files or sending many emails concurrently can increase RAM usage.
- If you accidentally create multiple copies of the byte array, memory pressure is even higher.

For large files, using `FileSystemResource` or a re-readable data source without loading everything into RAM is usually more appropriate.

### 8.1. Why shouldn't you use a read-once InputStream?

A source like `InputStreamResource` wrapping an already-opened stream may only allow reading once. In many Jakarta Mail flows, the attachment source must **reopen the stream** to write/serialize the message. If the stream is exhausted, sending the email may fail or the file content may be incomplete.

Principle:

> An object passed to `addAttachment` as an `InputStreamSource` must be able to supply valid data whenever the library requests a read, even when MIME creation/sending needs to open the stream multiple times.

For physical files, `FileSystemResource` is usually appropriate. For small bytes already in hand, `ByteArrayResource` is appropriate. For remote content or read-once streams, buffer temporarily in a **re-readable** source, while applying size limits and storage lifecycles.

### 8.2. DataSource when you need control over source and MIME type

Jakarta Activation has the `DataSource` abstraction with related methods:

```java
String getContentType();
String getName();
InputStream getInputStream() throws IOException;
OutputStream getOutputStream() throws IOException;
```

A `DataSource` can provide content type and bytes from many sources. When using:

```java
helper.addAttachment("export.dat", dataSource);
```

the application should ensure `dataSource.getContentType()` accurately describes a permitted format and `getInputStream()` can supply valid data each time it is called. The `attachmentFilename` parameter still represents **the name you want to send**, not necessarily `dataSource.getName()`.

## 9. Filename and MIME type do not verify a file

Suppose someone uploads a file named `invoice.pdf` whose actual bytes are an executable program or a document with malicious code.

If the application does:

```java
helper.addAttachment(
        "invoice.pdf",
        uploadedFileResource,
        "application/pdf");
```

then it **only labels** the MIME part as PDF; it does not turn the data into a real PDF and does not remove dangerous content.

### 9.1. Layers of protection needed for untrusted files

1. **Restrict file types:** based on business purpose, allow only permitted formats.
2. **Check size:** enforce limits on HTTP upload, storage, and **message size after MIME encoding**.
3. **Inspect actual format:** use a parser or appropriate signature/structure verification mechanism; simple magic-bytes checking is only a first step and is not enough for every format.
4. **Security scanning when appropriate:** use file scanning tools/pipelines per system security requirements.
5. **Storage and access rights:** do not use client-provided paths directly to access arbitrary files on the server.
6. **Control display name:** avoid control characters, separators, names containing sensitive data, or misleading extensions.
7. **Observe and handle failures:** log errors at the necessary detail level, do not log the entire attachment.

**Content-Type is descriptive metadata, not a security layer.** Both the sending system and receiving system must have appropriate policies for untrusted files.

### 9.2. Filenames with paths: path traversal risk

The attachment name field can be abused when a system **receives a file and saves it directly under the name from the email**:

```text
../../private/secret.txt
..\..\windows\system.ini
```

For the **sending** side, never put names containing paths or separators into headers. For the **receiving** side, **never concatenate the MIME filename value directly into the storage directory**. The receiving side needs to choose a safe name, control the destination directory, prevent overwrites, and set size limits. The rules on both sides are independent but complement each other.

### 9.3. Misleading Unicode characters

A filename can contain characters that look like Latin letters but belong to another script, text-direction control characters, or ambiguous separators. Such display names can mislead users about the extension or nature of the file.

To reduce risk, filenames generated by the application should have a predictable structure, contain little free-form input, and have a policy to filter unnecessary control/directional characters. **Do not strip all Unicode mechanically** if the product needs to support Vietnamese names; instead, weigh client compatibility and input data risks.

## 10. Checking and building safe filenames

An example utility to process display names generated by business logic:

```java
import java.text.Normalizer;

public final class AttachmentNames {

    private AttachmentNames() {}

    public static String requireSafeDisplayName(String raw) {
        if (raw == null) {
            throw new IllegalArgumentException("Attachment name is required");
        }

        String name = Normalizer.normalize(
                raw.strip(), Normalizer.Form.NFC);

        if (name.isBlank()) {
            throw new IllegalArgumentException("Attachment name is blank");
        }
        if (name.codePoints().anyMatch(Character::isISOControl)) {
            throw new IllegalArgumentException(
                    "Attachment name contains control characters");
        }
        if (name.indexOf('/') >= 0 || name.indexOf('\\') >= 0) {
            throw new IllegalArgumentException(
                    "Attachment name must not contain path separators");
        }
        if (name.equals(".") || name.equals("..")) {
            throw new IllegalArgumentException("Invalid attachment name");
        }
        if (name.codePointCount(0, name.length()) > 120) {
            throw new IllegalArgumentException("Attachment name is too long");
        }

        return name;
    }
}
```

This function:

- Rejects missing or blank names.
- Normalizes Unicode to **NFC** to reduce equivalent representations.
- Removes control characters, including CR/LF.
- Rejects path separators so only a **filename** is sent, not a path.
- Applies a 120-code-point limit as an **illustrative product policy**.

The function **does not validate file type**, does not detect every kind of Unicode spoofing, and is not sufficient to replace a file upload/scan policy. Depending on the environment and receiving OS, additional rules may be needed for special device names or forbidden characters.

Usage:

```java
String filename = AttachmentNames.requireSafeDisplayName(
        "Hóa đơn tháng 11.pdf");

helper.addAttachment(
        filename,
        new FileSystemResource(invoicePath),
        "application/pdf");
```

### 10.1. Should you take the filename from HTTP upload?

Suppose a user submits a `MultipartFile` to an API. The name from `getOriginalFilename()` is **client-supplied data**, which may be missing, untrusted, or contain path separators. You should not pass this value straight to the file system or `addAttachment` without a policy.

For an application forwarding attachments, an appropriate workflow might be:

1. Authenticate the user and their permission to send files.
2. Enforce HTTP request and file size limits.
3. Verify actual content and permitted file types.
4. Store bytes under an **internal server-generated name**.
5. Generate a sanitized display filename, or rebuild the name from business data.
6. Attach the accurate MIME type from trusted classification/format results.
7. Send via a worker, monitor errors, and clean up temporary files according to lifecycle.

**Do not treat `getContentType()` from an HTTP upload as an absolute source of truth.** The request's `Content-Type` header sent by the client can be wrong or forged.

## 11. Attachments differ from inline images

An email can have two forms of including resources:

### 11.1. Attachment for downloading

```java
helper.addAttachment(
        "company-logo.png",
        new ClassPathResource("mail/logo.png"),
        "image/png");
```

The email client usually displays the logo as a downloadable file.

### 11.2. Inline for HTML reference

```java
helper.setText(
        "Notice from the company.",
        "<p>Notice from the company.</p>"
                + "<img src=\"cid:company-logo\" alt=\"Logo\">");

helper.addInline(
        "company-logo",
        new ClassPathResource("mail/logo.png"),
        "image/png");
```

For inline:

- `company-logo` is the **logical Content-ID** for HTML to reference via `cid:company-logo`.
- `image/png` describes the **content type**.
- The image is usually placed inside a `multipart/related` structure.
- An attachment-style display name is **not the main goal** of `addInline`.

Call **`setText(...)` before `addInline(...)`** so email clients easily recognize the relationship between HTML and the image. For messages containing both inline resources and attached files, `MULTIPART_MODE_MIXED_RELATED` mode is a suitable choice.

Example:

```java
MimeMessageHelper helper = new MimeMessageHelper(
        message, MimeMessageHelper.MULTIPART_MODE_MIXED_RELATED, "UTF-8");
```

Do not mistakenly think that simply changing an attachment's `Content-Disposition` to `inline` fully sets up the CID reference in HTML.

## 12. Filenames affect how recipients use attachments

Filenames are part of the product experience, not just a protocol requirement.

For example, a recipient gets three files:

```text
file1.pdf
file2.pdf
file3.pdf
```

compared to:

```text
invoice-DH1024.pdf
payment-receipt-DH1024.pdf
delivery-note-DH1024.pdf
```

The second group is easier to understand and archive. When naming:

- Use terms familiar to the recipient; do not expose internal keys.
- Include the order code or reporting period if needed to distinguish them.
- Keep names short and avoid sensitive personal data.
- Do not use names implying a file is encrypted/protected when it is not.
- Keep extensions consistent with the MIME type and actual content.
- Avoid compatibility-sensitive characters if recipients use many older email systems.

### 12.1. One message with multiple attachments

```java
helper.addAttachment(
        "invoice-DH1024.pdf",
        new FileSystemResource(invoicePath),
        "application/pdf");

helper.addAttachment(
        "orders-DH1024.csv",
        new ByteArrayResource(csvBytes),
        "text/csv; charset=UTF-8");
```

Each attachment has its own **name**, **byte source**, and **content type**. Do not assume all parts of a message use the same `Content-Type`. If names collide, some clients still allow saving but may prompt to rename or cause confusion; therefore generate sufficiently distinct names.

## 13. Attachment size differs from email size

Even when the name and content type are right, an email can still be rejected by the SMTP server for being too large.

Binary files are usually represented using base64 in MIME. Every **3 bytes** of original data become **4 base64 characters**, plus newline characters, headers, and multipart boundaries. For large files, the total base64 MIME size is roughly **1.37 times** the initial byte size.

Illustrative example:

| Original file size | Estimated base64 MIME part size |
|---:|---:|
| 1 MiB | About 1.37 MiB |
| 10 MiB | About 13.68 MiB |
| 20 MiB | About 27.37 MiB |

These numbers do not add all the headers, HTML, text, and other MIME parts. Thus, a provider advertising “25 MiB max message” **does not mean you can attach a 25 MiB file**.

In Spring Boot:

- `spring.servlet.multipart.max-file-size` controls **file uploads via HTTP servlet**, not SMTP message limits.
- `MimeMessageHelper` helps attach files to MIME, **not automatically ensuring the file is under the provider's size ceiling**.
- The application must enforce appropriate limits on original file size, total files, expected MIME size, and recipient count.
- For overly large documents, **sending an authorized, time-limited download link** is usually better than an attachment.

There is no need to base64-encode files yourself before calling `addAttachment`: Jakarta Mail handles appropriate transfer encoding when creating the message. Pre-encoding yourself can cause the recipient to download base64 text instead of the original file or cause MIME to be double-encoded.

## 14. Diagnosing name and content-type errors

| Symptom | Possible cause | Direction to handle |
|---|---|---|
| Recipient sees a name like `=?UTF-8?B?...?=` | Filename encoding was not decoded by client, or encoded in the wrong context | Inspect actual MIME headers, RFC 2231/RFC 2047, and library encoding options. |
| Vietnamese filename has broken diacritics | Charset/parameter encoding or client lacks proper support | Generate logical Unicode names, use library APIs, try an ASCII fallback name when needed. |
| File shows a UUID name or internal path | Storage filename was used as the display name | Pass `attachmentFilename` from safe business data. |
| PDF file appears as generic binary data | Content type unspecified or mapping did not recognize it | Set `application/pdf` explicitly when the file is known to be a real PDF. |
| Email client receives file but cannot open it | Corrupted content, wrong data type, or exhausted stream source | Inspect source bytes and re-readable source; do not just change the extension. |
| Image does not appear in HTML | Used `addAttachment` instead of `addInline`, wrong `cid:`, or client blocks images | Check Content-ID, `addInline`, and related structure. |
| Attachment missing data when sent | `InputStreamSource` cannot reopen or file changed during send | Use an immutable re-readable source, safeguard file lifecycle. |
| Mail rejected with `552 5.3.4` | MIME message exceeds server limit | Estimate/measure email size after encoding, shrink file, or send a link. |
| Mail blocked despite small file | Anti-malware policy, file type, or MIME mismatch | Check SMTP/provider response; do not try to bypass filters by renaming extension. |
| Saving received file produces abnormal path | Receiving system uses MIME filename as a path | Sanitize and build safe storage paths on the receiving side. |

### 14.1. Should you inspect raw MIME headers when diagnosing?

It may be necessary in a controlled environment, especially when Unicode names display incorrectly. Headers to observe:

```text
Content-Type
Content-Disposition
Content-Transfer-Encoding
Content-ID
```

However, a MIME email can contain **personal addresses, confidential content, tokens, and attachments**. Do not permanently enable full-message logging in production. Collect only necessary metadata, mask sensitive information, and limit retention time.

### 14.2. What does success in `send(...)` indicate?

`JavaMailSender.send(message)` completing means the transport did not report an error at send time. It **does not guarantee the email reached the Inbox**. A file may be rejected at the receiving system's filter gateway after the SMTP submission server has accepted the message.

If you need to track final outcomes, the system must handle **bounce/DSN** or dedicated provider events. A filename error in an email client may also just be a display issue, not meaning SMTP failed.

## 16. Summary

In **Spring Framework Mail**, when using `MimeMessageHelper.addAttachment(...)`, actively distinguish:

1. **Attachment name**: the string displayed to the recipient, not necessarily matching the internal storage filename or path.
2. **Content-Type**: describes the MIME data type such as `application/pdf`, `text/csv`, or `image/png`, but **does not verify file safety**.
3. **Data source**: the actual bytes taken from `FileSystemResource`, `ByteArrayResource`, or `DataSource`; the source must be readable when creating/sending the email and re-readable when the library requests it.
4. **Content-Disposition**: distinguishes an attached part from inline-displayed content; `addInline` also involves Content-ID and `cid:`.
5. **Encoding and size**: Unicode filenames require appropriate MIME parameter encoding, while attachment data is usually transfer-encoded with base64, increasing message size.

For production systems, **filenames should be generated/controlled from business logic**, MIME types should be based on verified formats, untrusted data must be checked, and sizes must fit SMTP provider policies. `MimeMessageHelper` helps build the MIME structure, but the responsibility for verifying files, limiting sending rights, managing secrets, and tracking delivery still belongs to the application.
