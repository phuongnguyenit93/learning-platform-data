# Parameter Names, Bean Names, and the Role of the `-parameters` Compiler Option in Spring

## 1. Why Can a Parameter Name Determine Which Bean Gets Injected?

In Spring Core Container, **an injection point is typically resolved first by Java type**, such as a constructor taking a `Gateway`. If two beans `emailGateway` and `smsGateway` both implement `Gateway`, looking at the type alone is not enough to pick a single object.

Spring has candidate selection rules: **qualifiers**, **primary/fallback**, generic types, field/parameter names, and other metadata. When multiple candidates share the same type and **no higher-priority selection directive takes precedence**, Spring can compare the **injection point's name** against **bean names or aliases**, and use the matching candidate.

Example:

~~~java
// Snippet inside a Spring-managed bean:
OrderService(Gateway smsGateway) {
    this.gateway = smsGateway;
}
~~~

Suppose two beans exist:
- `emailGateway`, of type `Gateway`;
- `smsGateway`, also of type `Gateway`.

If Spring can see that the **actual Java parameter name is `smsGateway`**, it can use that name as a resolution cue and inject the `smsGateway` bean. However, the JVM **does not guarantee preserving original parameter names for reflection** under every compilation mode. That is why you need to understand the **`javac -parameters`** option.

### Three Concepts That Must Not Be Mixed Up

| Concept | Example | Origin | Role |
| --- | --- | --- | --- |
| **Bean name** | `smsGateway` | Spring registration via `@Bean`, `@Component`, XML, aliases | Identifies the bean inside the IoC Container |
| **Java parameter name** | `smsGateway` in `OrderService(Gateway smsGateway)` | Java source signature, depending on compilation metadata | Spring can use it when picking among same-type beans |
| **Java field name** | `private Gateway smsGateway;` | Field declaration and field reflection info | Spring can inspect the field name for field injection |

**`-parameters` concerns constructor/method parameter-name metadata**; it **does not change bean names**, add `@Qualifier`, or **turn field names into parameter names**. Field names have their own reflection path, so `-parameters` is not required to read a field's name.

Lesson goals: determine where bean names come from, when Spring uses injection-point names, the purpose and limits of `javac -parameters`, how to enable it properly in Maven/IDEs, debugging techniques, and verification with **Java 17 + Spring Framework 7.0.9**.

## 2. Where Do Bean Names Come From?

Spring manages bean definitions by **bean name** inside a container. This name is not necessarily the Java class name or a variable name in your business code.

### 2.1. `@Bean` Defaults to the Method Name

~~~java
@Configuration(proxyBeanMethods = false)
class GatewayConfig {
    @Bean
    Gateway emailGateway() {
        return new EmailGateway();
    }
}
~~~

If no explicit name is given, the method `emailGateway()` typically registers a bean named **`emailGateway`**. The underlying instance class may be `EmailGateway`, yet that **does not automatically change the bean name** to `EmailGateway`.

You can specify a name different from the method:

~~~java
@Bean("smsGateway")
Gateway createSmsChannel() {
    return new SmsGateway();
}
~~~

The Java method is `createSmsChannel`, while the bean name is **`smsGateway`** because it was declared explicitly. If an injection point expects `smsGateway`, it must match the **actual bean name**, not be inferred from the method name or concrete class.

### 2.2. Aliases Do Not Create New Objects

~~~java
@Bean(name = {"smsGateway", "oldSmsGateway"})
Gateway createSmsChannel() {
    return new SmsGateway();
}
~~~

The first name is typically the primary bean name; the remaining ones are **aliases** pointing to the same bean. `getBean("oldSmsGateway")` and `getBean("smsGateway")` in the same context normally return the same reference for a default singleton. An injection point named **`oldSmsGateway`** can also match via the alias.

### 2.3. `@Component` and Naming Strategy

~~~java
@Component("gatewayForTests")
class FakeGateway implements Gateway {
    // ...
}
~~~

Under appropriate component scanning, the bean name is explicitly `gatewayForTests`. If no name is given, Spring uses a name generated by its naming strategy, usually derived from the short class name by convention. Naming rules for classes with unusual capitalization, custom generators, or nested classes can differ; **check the actual bean name** rather than guessing from the filename.

### 2.4. XML and Programmatic Registration

~~~xml
<bean id="emailGateway" class="demo.EmailGateway"/>
<alias name="emailGateway" alias="primaryEmailGateway"/>
~~~

XML uses `id/name` and aliases. APIs such as `registerBean` also let you supply a name at registration time. **Bean names are container metadata**, not properties attached by the JVM to each Java class.

**Scope note:** two definitions with the same bean class but different names are **two registrations**, which can have distinct instances, lifecycles, and scopes. An alias, by contrast, does not create a second registration.

## 3. How Does the JVM Store Java Parameter Names?

Java source:

~~~java
public ReportService(Gateway smsGateway, int retries) {
    // ...
}
~~~

In source code, you see `smsGateway` and `retries`. However, when reading a method or constructor via **Java Reflection**, parameter names are preserved as reliable metadata only when the compiler is instructed to emit them.

In **JDK 8+**, the option:

~~~bash
javac -parameters ReportService.java
~~~

instructs the Java compiler to emit the **`MethodParameters` attribute** containing parameter names into the `.class` file. Reflection can access them via `java.lang.reflect.Parameter.getName()` and check `Parameter.isNamePresent()`.

Without this metadata, reflection typically reports synthetic names such as `arg0`, `arg1`, with `isNamePresent() == false`. Those synthetic names **are not the originally declared parameter names** for Spring to use as fallback bean-name matching.

| Aspect | Compiled with `-parameters` | Without `-parameters` |
| --- | --- | --- |
| Java bytecode runs the app | Works | Works |
| Method/constructor parameters have source-name metadata | Yes, for code compiled with the flag | Usually not |
| Reflection `getName()` | e.g., `smsGateway` | Typically `arg0` |
| Reflection `isNamePresent()` | `true` | `false` |
| Spring infers parameter name for by-name matching | Has metadata basis | Should not rely on this mechanism |
| Explicit `@Qualifier` | Still works when bean/qualifier are valid | Still works, independent of source names |
| `@Primary` | Still takes effect when applicable | Still takes effect |
| Java field names via reflection | Still present | Still present |

**`-parameters` is different from `-g`:** `-g` emits debug info such as line-number and local-variable data; it **does not replace** `MethodParameters` for parameter-name discovery in Spring Framework 6.1+. Also do not confuse `-parameters` with a JVM runtime option: it is a **compile-time flag**, not an argument to the `java` command.

## 4. Since Spring 6.1: Parameter-Name Discovery Requires Proper Metadata

Spring Framework documentation and upgrade notes confirm: **as of Spring Framework 6.1**, support for inferring parameter names by reading the bytecode **Local Variable Table** was removed. Therefore, if an application relies on constructor or factory-method parameter names to pick beans, compile Java with **`-parameters`**.

Previously, some setups happened to work via debug info even without the flag. After upgrading to 6.1/6.2/7.x, applications may encounter autowiring failures like “multiple beans of type...” because Spring no longer knows that `smsGateway` is the parameter's real name.

Starting in **Spring 6.2**, when a parameter name matches a bean name and no other type/qualifier/primary/fallback rule overrides the selection, Spring can use **fast shortcut resolution** for the name match. This is an **optimization**, not a change turning Spring into a system that always picks by name before type.

State this accurately:

- `@Autowired` remains **type-driven dependency injection**.
- Parameter/field names are a **fallback resolution cue** in eligible situations.
- Primary, qualifiers, fallback, and generic metadata can cause a bean with a matching name **not** to be selected.
- **The name must still align with a compatible type**; a bean name cannot make an object of the wrong Java type assignable.
- A dependency expecting **one bean** can still fail if no rule resolves multiple candidates; enabling `-parameters` does not guarantee every case will resolve.
- To request a bean **explicitly and resiliently across refactorings**, use `@Qualifier` or `@Primary` according to the domain contract.

## 5. Candidate Selection Flow and Precedence Rules to Understand

When Spring needs to resolve:

~~~java
@Autowired
void configure(Gateway smsGateway) {
    // ...
}
~~~

Conceptual flow:

~~~text
Injection point: Gateway smsGateway
                 |
                 v
      Find beans compatible with Gateway
                 |
                 v
   Filter autowire candidates + qualifiers
                 |
                 v
   Is a single candidate already clear?
                 |
       Any other precedence rule?
       /                    \
   Valid primary/qualifier   No overriding
   or fallback               precedence rule
       |                         |
       v                         v
    Select by                Real field name or
   that metadata             parameter name present?
                                  |
                            Matching bean by name?
                             /           \
                           Yes           No
                            |               |
                            v               v
                     Consider named     Remaining resolution
                      candidate         steps or error
~~~

This diagram is a mental model; the internal algorithm also includes branches for dependency name shortcuts, priority, default-candidate, self-references, generic types, aliases, `ObjectProvider`, collections, and special mechanisms.

**Concrete distinguishing examples:**

| Scenario | Selected bean / failure |
| --- | --- |
| Two `Gateway` beans `emailGateway` and `smsGateway`, param `Gateway smsGateway`, with `-parameters`, no primary/qualifier | Can select **`smsGateway`** via matching name |
| Two beans of the same type, param `Gateway arbitraryName`, and no other rule | Can report ambiguity |
| Two beans of the same type, `emailGateway` is `@Primary`, param `Gateway smsGateway` | Typically selects **`emailGateway`** (primary takes precedence) |
| Param `@Qualifier("smsGateway") Gateway emailGateway` | Selects **`smsGateway`** because the qualifier is valid, despite the different param name |
| `Gateway oldSmsGateway`, bean `smsGateway` has alias `oldSmsGateway` | Can select **`smsGateway`** via alias |
| Param expects `SmsGateway`, bean with matching name only has type `EmailGateway` | Cannot bypass type compatibility check |
| Only one `Gateway` candidate exists | Does not need parameter name |
| `List<Gateway>` instead of `Gateway` | Injects multiple candidates; does not use name matching to pick just one |

**Watch out for `@Bean` parameter names:** The code below uses factory method `nameSelection(Gateway smsGateway,...)`, so the registered bean name is `nameSelection`, **not** the parameter name `smsGateway`. Spring resolves those parameters when invoking the factory method to construct the returned object.

## 6. Configuring Maven to Retain Parameter Names

A Maven project using Java 17 and Spring Framework 7.0.9 can enable:

~~~xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <maven.compiler.parameters>true</maven.compiler.parameters>
</properties>
~~~

The **`maven.compiler.parameters=true`** property is supported by the Maven Compiler Plugin; it instructs `javac` to generate reflection metadata equivalent to `-parameters`. No separate annotation processor is needed for Spring autowiring to work: this is compiler metadata, and IoC handles injection at runtime.

You can also configure it directly inside the plugin:

~~~xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <version>3.13.0</version>
    <configuration>
        <release>17</release>
        <parameters>true</parameters>
    </configuration>
</plugin>
~~~

**Choose one consistent configuration source** in a real project. The runnable example in section 7 uses **properties**, without duplicating the `parameters` config in the plugin. When using Gradle, an IDE build, or manual `javac`, configure the flag on the **compiler that actually produces the `.class` files**, rather than adding a Maven property in a file that build tool does not use.

### Verifying the Flag Is Actually Active

- Run `mvn -q clean compile` to wipe old class artifacts and recompile.
- Use `java.lang.reflect.Executable.getParameters()` and `Parameter.isNamePresent()` to confirm.
- You can run `javap -v -p` to inspect the class and look for **`MethodParameters`**, which is distinct from `LocalVariableTable`.
- When changing IDE compiler settings, always **clean/rebuild**; do not rely on class files from an earlier build.

**Check both `compile` and `testCompile`** if tests also have factory methods or constructor parameter naming; the Maven Compiler Plugin applies the property across compilation goals. If another module is built by a different tool, a neighboring module's Maven property does not automatically apply.

## 7. Runnable Spring 7.0.9 + Java 17 Project

The demo includes three isolated contexts and a Reflection step:

1. **NameConfig without `@Primary`:** registers `emailGateway` and `smsGateway` (alias `oldSmsGateway`); one factory method takes an unqualified **`Gateway smsGateway`** parameter → Spring selects **SMS** via parameter name. Another parameter has `@Qualifier("emailGateway")` → selects EMAIL regardless of the parameter name `preferred`.
2. **AliasSelection** takes `Gateway oldSmsGateway` → fallback name matches the alias → SMS. **FieldSelection** has `@Autowired Gateway smsGateway` → selects SMS by **field name**, without needing `-parameters` to know the field name.
3. **PrimaryConfig:** `emailGateway` is `@Primary`; a parameter named `smsGateway` still receives **EMAIL**. A parameter named `emailGateway` annotated with `@Qualifier("smsGateway")` receives **SMS**.
4. **AmbiguousConfig:** two beans of the same type, injection parameter named `unknownGateway` matching neither bean name nor alias, and no primary/qualifier → the container cannot resolve a single bean; the error is caught.
5. **Java Reflection:** the program prints the actual parameter name and `isNamePresent()` to verify `-parameters` on the freshly compiled class.

No Spring Boot, web server, database, or network calls are used.

### 7.3. Complete `src/main/java/demo/ParameterNamesDemo.java`

~~~java
package demo;

import java.lang.reflect.Method;
import java.lang.reflect.Parameter;
import java.util.Arrays;

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;

public final class ParameterNamesDemo {
    private ParameterNamesDemo() {
    }

    @FunctionalInterface
    interface Gateway {
        String id();
    }

    static final class NameSelection {
        private final Gateway byParameterName;
        private final Gateway byQualifier;

        NameSelection(Gateway byParameterName, Gateway byQualifier) {
            this.byParameterName = byParameterName;
            this.byQualifier = byQualifier;
        }

        String paramId() {
            return byParameterName.id();
        }

        String qualifierId() {
            return byQualifier.id();
        }
    }

    static final class AliasSelection {
        private final Gateway gateway;

        AliasSelection(Gateway gateway) {
            this.gateway = gateway;
        }

        String id() {
            return gateway.id();
        }
    }

    static final class FieldSelection {
        @Autowired
        private Gateway smsGateway;

        String id() {
            return smsGateway.id();
        }
    }

    static final class PrimarySelection {
        private final Gateway byName;
        private final Gateway byQualifier;

        PrimarySelection(Gateway byName, Gateway byQualifier) {
            this.byName = byName;
            this.byQualifier = byQualifier;
        }

        String namedArgumentId() {
            return byName.id();
        }

        String qualifiedId() {
            return byQualifier.id();
        }
    }

    static final class AmbiguousSelection {
        AmbiguousSelection(Gateway gateway) {
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class NameConfig {
        @Bean("emailGateway")
        public Gateway emailGateway() {
            return () -> "EMAIL";
        }

        @Bean(name = {"smsGateway", "oldSmsGateway"})
        public Gateway smsGatewayFactory() {
            return () -> "SMS";
        }

        @Bean
        public NameSelection nameSelection(
                Gateway smsGateway,
                @Qualifier("emailGateway") Gateway preferred) {
            return new NameSelection(smsGateway, preferred);
        }

        @Bean
        public AliasSelection aliasSelection(Gateway oldSmsGateway) {
            return new AliasSelection(oldSmsGateway);
        }

        @Bean
        public FieldSelection fieldSelection() {
            return new FieldSelection();
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class PrimaryConfig {
        @Bean("emailGateway")
        @Primary
        public Gateway emailGateway() {
            return () -> "EMAIL";
        }

        @Bean("smsGateway")
        public Gateway smsGateway() {
            return () -> "SMS";
        }

        @Bean
        public PrimarySelection primarySelection(
                Gateway smsGateway,
                @Qualifier("smsGateway") Gateway emailGateway) {
            return new PrimarySelection(smsGateway, emailGateway);
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class AmbiguousConfig {
        @Bean("emailGateway")
        public Gateway emailGateway() {
            return () -> "EMAIL";
        }

        @Bean("smsGateway")
        public Gateway smsGateway() {
            return () -> "SMS";
        }

        @Bean
        public AmbiguousSelection ambiguousSelection(Gateway unknownGateway) {
            return new AmbiguousSelection(unknownGateway);
        }
    }

    public static void main(String[] args) throws ReflectiveOperationException {
        Method factory = NameConfig.class.getDeclaredMethod(
                "nameSelection", Gateway.class, Gateway.class);
        Parameter parameter = factory.getParameters()[0];
        System.out.println("reflection.name=" + parameter.getName());
        System.out.println("reflection.present=" + parameter.isNamePresent());

        try (var context =
                new AnnotationConfigApplicationContext(NameConfig.class)) {
            var named = context.getBean(NameSelection.class);
            var alias = context.getBean(AliasSelection.class);
            var field = context.getBean(FieldSelection.class);

            System.out.println("name.selected=" + named.paramId());
            System.out.println("name.qualified=" + named.qualifierId());
            System.out.println("alias.selected=" + alias.id());
            System.out.println("field.selected=" + field.id());
            String[] beanNames = context.getBeanNamesForType(Gateway.class);
            Arrays.sort(beanNames);
            System.out.println("names=" + String.join(",", beanNames));
            System.out.println("alias.same="
                    + (context.getBean("oldSmsGateway")
                       == context.getBean("smsGateway")));
        }

        try (var context =
                new AnnotationConfigApplicationContext(PrimaryConfig.class)) {
            var primary = context.getBean(PrimarySelection.class);
            System.out.println("primary.namedArgument="
                    + primary.namedArgumentId());
            System.out.println("primary.qualified=" + primary.qualifiedId());
        }

        try (var context =
                new AnnotationConfigApplicationContext(AmbiguousConfig.class)) {
            System.out.println("ambiguous.unexpected");
        } catch (BeansException expected) {
            System.out.println("ambiguous.failed=true");
        }
    }
}
~~~

**Explanation:**
- `getDeclaredMethod(...)` queries the factory method with two `Gateway` parameters. The real name of the first parameter must be **`smsGateway`** because the POM enables `-parameters`; Reflection `isNamePresent()` must be `true`.
- `NameConfig` registers two `Gateway` beans. `nameSelection(Gateway smsGateway, ...)` lacks a qualifier on its first parameter, so **name matching** resolves the type ambiguity to SMS.
- The `preferred` parameter carries **`@Qualifier("emailGateway")`** and selects EMAIL; the parameter name `preferred` has no effect.
- `oldSmsGateway` is an alias of `smsGateway`. Parameter `Gateway oldSmsGateway` matches the alias name and selects SMS.
- Field `@Autowired Gateway smsGateway` also selects SMS by field name; **field names remain available even when the compiler does not enable `-parameters`**.
- In `PrimaryConfig`, parameter `smsGateway` selects **EMAIL** thanks to the valid `@Primary`, proving primary can take precedence over name fallback. Parameter `@Qualifier("smsGateway") Gateway emailGateway` selects SMS.
- `AmbiguousConfig` intentionally omits primary/qualifier and parameter `unknownGateway` matches no bean name/alias; eager singleton creation fails, and the demo catches `BeansException` to print a single line.
- Each context is isolated, so identically named beans across different configs **do not override each other**.

**Intentional limitation:** the program does not mutate Java bytecode or compile without `-parameters` at runtime, because compiler flags can only be changed at build time. The on/off control comparison is performed **in the standalone Java Reflection example in section 9**.

## 9. Plain Java 17: Comparing With and Without `-parameters`

Create a standalone file **`ParameterReflectionDemo.java`** in a sample directory without Maven or Spring:

~~~java
import java.lang.reflect.Method;
import java.lang.reflect.Parameter;

public class ParameterReflectionDemo {
    static void configure(String emailGateway, int retries) {
    }

    public static void main(String[] args) throws Exception {
        Method method = ParameterReflectionDemo.class.getDeclaredMethod(
                "configure", String.class, int.class);
        for (Parameter parameter : method.getParameters()) {
            System.out.println("name=" + parameter.getName()
                    + ",present=" + parameter.isNamePresent());
        }
    }
}
~~~

### Compiling **With** Parameter Names Preserved

~~~bash
javac -parameters ParameterReflectionDemo.java
java ParameterReflectionDemo
~~~

Exact stdout on JDK 17:

~~~text
name=emailGateway,present=true
name=retries,present=true
~~~

### Compiling **Without** Parameter Names Preserved

Recompile the **same file**, overwriting `ParameterReflectionDemo.class` with the command below (do not keep the old class file from the previous step):

~~~bash
javac ParameterReflectionDemo.java
java ParameterReflectionDemo
~~~

Exact stdout from Java Reflection without source `MethodParameters` names:

~~~text
name=arg0,present=false
name=arg1,present=false
~~~

**Technical indicator:** `isNamePresent=false` proves Reflection sees synthetic names rather than `emailGateway`/`retries`. Both runs produce identical **method behavior**, differing only in metadata for reflection/frameworks. Local variable names inside a method body are not preserved just by enabling `-parameters`.

You can inspect the class file with:

~~~bash
javap -v -p ParameterReflectionDemo.class
~~~

and look for the **`MethodParameters`** section. When compiled with the flag, the attribute holds `emailGateway` and `retries`; without the flag, that name metadata is absent. Whenever you switch build tools, clean and rebuild to avoid reading stale class artifacts.

### Windows PowerShell, cmd, and Linux

The `javac` and `java` commands above work in PowerShell, Command Prompt, and Linux/macOS shells when `JAVA_HOME`/`PATH` are configured properly. Do not use `export JAVA_TOOL_OPTIONS` or OS environment variables to enable `-parameters`: the flag belongs to **`javac`** and must be passed at the compile step.

## 10. Common Errors and How to Debug

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Java Reflection reports `arg0`/`isNamePresent=false` | Class compiled without `-parameters` | Enable the flag in the actual build tool and clean-compile |
| Worked before Spring 6.1+, fails with `NoUniqueBeanDefinitionException` after upgrade | Previously relied on `LocalVariableTable`/debug symbols for parameter names | Compile with `-parameters`, or use explicit qualifiers |
| Maven property enabled, yet running in IDE still fails to match by param name | IDE compiler does not use Maven config or stale classes remain | Check build delegation/compiler args, clean rebuild, and test Reflection |
| `@Bean smsGateway()` exists, yet Spring sees a different name | `@Bean(name=...)` or naming strategy overrides default method name | Inspect actual bean names via `getBeanNamesForType` |
| Parameter name matches, yet bean has the wrong type | Name cannot replace Java assignability | Fix contract types, return types, or bean registrations |
| `@Primary` bean is picked despite parameter having another bean's name | Primary is a valid precedence rule | Use a qualifier if the use case requires a specific bean |
| `@Qualifier("smsGateway")` picks SMS despite a different param name | Qualifier filters candidates as designed | Do not confuse name fallback with explicit qualifiers |
| No bean matches param name, yet only one candidate exists | Dependency can still resolve by type | `-parameters` is not required for every injection |
| Constructor has multiple parameters of the same type | Each parameter needs independent resolution; qualifiers may be needed | Use meaningful names, retain metadata, and add qualifiers when needed |
| Does an alias appear in `getBeanNamesForType`? | Type discovery lists primary bean names; an alias is not a new bean | Compare `getAliases(name)` and `containsBeanDefinition` |
| Passed `-parameters` to the `java` command | Wrong stage | Pass it to `javac` or the Maven Compiler Plugin |
| Enabled `-g`, yet Spring still cannot see param names | Debug info is no longer a fallback in Spring 6.1+ | Use `-parameters` |
| Renaming a parameter changes wiring | Code depends implicitly on name fallback | Use `@Qualifier` or an explicit `@Primary` policy |
| Field names work, yet constructor parameter names are lost | Field reflection differs from parameter-name metadata | Check `Parameter.isNamePresent()` rather than relying on field tests |
| `NoUniqueBeanDefinitionException` with multiple candidates | Insufficient selector at the injection point | Check type, qualifier, primary/fallback, and name/alias |
| App startup fails even when compiled with the right flag | Real DI error or business configuration bug | Read root cause; verify registrations, context, and bean types |

### Ordered Diagnostic Checklist

1. Confirm the **right `ApplicationContext`** and bean registrations; print names with `getBeanNamesForType(RequiredType.class)`.
2. Check **type compatibility**: inspect declared `@Bean` return types, generic qualifications, and proxies if applicable.
3. Check whether the injection point has **`@Qualifier`**, `@Primary`, `@Fallback`, `autowireCandidate`, or other rules.
4. If relying on names, verify the exact **field name or method/constructor parameter name** and corresponding bean name/alias.
5. Use **Reflection `isNamePresent()`** to check method/constructor parameter names.
6. Cross-check `maven.compiler.parameters`, IDE compiler flags, toolchains, and rebuild outputs.
7. Do not slap `@Primary` onto a bean just to mask misconfiguration when you actually intend to select a specific implementation.

## 11. When to Rely on Parameter Names vs. Qualifiers?

**Parameter names can be a convenient fallback** when multiple beans share a type and injection-point names carry natural meaning. They reduce repetitive annotations, and Spring 6.2+ can optimize resolution in simple cases. Still, it remains a **contract coupled to source signatures + compile metadata + candidate selection rules**.

Consider using `@Qualifier` when:
- A use case demands **a specific implementation** even if another bean is `@Primary`.
- Renaming a parameter during refactoring should not silently change wiring.
- Multiple beans of the same type represent distinct **roles**, such as `primaryGateway` and `auditGateway`.
- Selecting a bean by name/alias is a policy worth stating explicitly in code reviews and integration tests.

Use `@Primary` when there truly is a reasonable **common default** for single injection, rather than sprinkling verbose qualifiers across every single consumer.

Use `@Resource(name="...")` on fields/setters when the requirement is **by-name lookup** under Jakarta injection semantics. That is a different mechanism from type-driven `@Autowired`, and the two should not be treated as completely interchangeable aliases.

**Prefer constructor injection** for mandatory dependencies so objects are valid upon construction; even with constructors, you can still place `@Qualifier` on constructor parameters when needed. This does not depend on setters or field annotations.

## 13. Conclusion and Official Documentation

**Summary:** Parameter names can help Spring pick a matching bean when multiple beans share the same type, yet this is **one part of dependency resolution**, not a rule that Spring “always injects by name”. For Spring to read constructor or `@Bean` method parameter names accurately from Java class files, enable `javac -parameters` (or `maven.compiler.parameters=true`). Since Spring 6.1, relying on `-g` debug symbols to recover missing parameter names no longer works; since 6.2, name matching can take a fast shortcut when not overridden by other rules.
