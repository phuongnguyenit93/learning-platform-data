# Class-Based Proxy Limitations and Interceptable Methods in Spring Framework

## 1. Context: Cross-Scope Dependencies and Why Spring Needs Proxies

In the Spring IoC Container, a `singleton` bean is created once per bean definition per container, whereas a `prototype` bean is created every time Spring is explicitly asked to produce an instance. Web scopes such as `request` and `session` hold instances per HTTP request or HTTP session. When a singleton depends directly on a bean with a shorter lifetime, we must determine **when** Spring selects the dependency's target.

Consider this design:

```java
@Service
class ReportService {
    private final UserContext userContext;

    ReportService(UserContext userContext) {
        this.userContext = userContext;
    }

    String report() {
        return userContext.currentUser();
    }
}
```

Here `UserContext` is a bean representing per-request data; this illustrative snippet cannot run standalone because it omits the `UserContext` definition and imports. If the **real target** were injected when creating the singleton `ReportService`, we would face a lifecycle mismatch: at singleton initialization time there may not be an HTTP request yet, or the singleton would risk holding onto one request's state for too long. With a **scoped proxy**, the singleton receives a stable reference; the proxy locates the target corresponding to the active scope at method invocation time.

```text
                         Spring IoC Container
                               |
                          ReportService
                          (singleton)
                               |
                               v
                    UserContext scoped proxy
                               |
            +------------------+------------------+
            |                                     |
     HTTP request A                          HTTP request B
       target A                                target B

Singleton holds PROXY long-term;
proxy selects TARGET per request when calling an interceptable method.
```

This has two design consequences:

1. The proxy must sit at the **call boundary**: only calls passing through the proxy and targeting methods the proxy can intercept are redirected properly.
2. The proxy type determines whether the bean can be represented as a class or an interface and which methods can be intercepted.

For request/session scopes, `@RequestScope` and `@SessionScope` default `proxyMode` to `ScopedProxyMode.TARGET_CLASS`. For ordinary `@Scope("prototype")`, no scoped proxy is created by default; it can be requested via the `proxyMode` attribute. A prototype with a scoped proxy gets a new target **on each method call forwarded by the proxy**, because every prototype resolution creates a new instance. Consequently, a workflow needing the same target across multiple method calls usually fits `ObjectProvider` better.

## 2. How Does a Class-Based Proxy (CGLIB) Work?

When `ScopedProxyMode.TARGET_CLASS` is chosen, Spring creates a proxy assignable to the target's class type. Typically Spring uses CGLIB, generating a **runtime subclass** (CGLIB is repackaged inside `spring-core`). The proxy overrides overridable instance methods; the interception code generated by Spring can resolve the scoped target before forwarding the call.

```text
class UserContext
      ▲
      | extends
class UserContext$$SpringCGLIB$$...     (proxy, class name is illustrative only)
      |
      +-- public String currentUser()  → intercept → scoped target.currentUser()

class UserContext (actual scoped target)
      |
      +-- business logic and per-request/session state
```

Annotation example creating a class proxy:

```java
import org.springframework.context.annotation.Scope;
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;

@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class UserContext {
    public String currentUser() {
        return "user-of-current-request";
    }
}
```

The class above illustrates syntax, but only runs properly in a Spring web-aware context with an actual request. A class proxy permits injection as `UserContext` (concrete type), because the proxy is a subtype of `UserContext`.

**Do not confuse the two roles:**

- A `Scoped proxy` primarily selects the right target for the scope, such as an HTTP request.
- A `Spring AOP proxy` can apply advice such as transactions, caching, security, or logging to supported method calls.

Both use proxying mechanisms and share override/interface limitations. However, their business behavior differs: bypassing an AOP proxy can skip advice; bypassing a scoped proxy can fail to resolve the right target in scope. Nor should the CGLIB class supporting `@Configuration(proxyBeanMethods=true)` (intercepting calls to `@Bean` methods) be confused with the scoped proxies discussed here; they serve different configuration purposes.

## 3. Which Methods Can CGLIB Intercept?

The foundational requirement is that a Java subclass can **override** the method and Spring can reach the method through the proxy. The table below assumes Spring uses a class-based proxy, not AspectJ weaving.

| Java construct | Interceptable by CGLIB class proxy? | Reason / note |
| --- | --- | --- |
| `public` instance method, non-`final` | **Yes**, the standard case | Subclass overrides and routes the call through the interceptor |
| `protected` instance method, non-`final` | **Possibly**, if accessible | Whether advice applies also depends on each Spring facility's matching rules |
| package-private instance method | **Depends on accessibility** | Methods not visible to a subclass in another package cannot be overridden; prefer a public API when proxying is intended |
| `public final` or `protected final` method | **No** | `final` forbids overriding, so it cannot be intercepted via subclassing |
| `private` method | **No** | Private methods are not inherited for overriding |
| `static` method | **No** on proxy instance | Static calls bind to the class, not dispatched to proxy overrides |
| Constructor | **No** | Constructors are not overridable instance methods |
| Entire `final` class / Java `record` | **Cannot create class proxy** for that class | A subclass cannot `extends` a `final` class |
| `abstract` instance method | Overridable in Java, but requires a concrete target implementation | Not a workaround for needing an instantiable bean |
| Method only on implementation, not on interface | CGLIB **can** intercept if overridable | JDK interface proxies only expose methods via interfaces |

A note of caution regarding non-public methods: since Spring Framework 6.x, some AOP features like transactions can support protected/package-private methods on class-based proxies; however, **technical CGLIB overridability** and **whether annotation/advisor rules match** are two separate steps. Before relying on them, check the documentation for the specific annotation and test on your Spring version. Public methods through the proxy remain the clearest choice.

### 3.1. Final Classes and Records

```java
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
@Component
public final class FinalRequestContext {
    public String userId() {
        return "U1";
    }
}
```

The snippet above requires importing `Scope`, `ScopedProxyMode`, and `Component`; it deliberately illustrates an **invalid** configuration. Spring cannot generate a subclass for `FinalRequestContext` because the class is `final`. When proxy instantiation is needed, the application can fail bean creation, often with `AopConfigException`/CGLIB errors in the cause chain; do not rely on exact exception message text as it varies across versions and configurations.

A Java `record` is also a `final` class, so you cannot use a record as a class-based scoped proxy target. Records are great as immutable values returned from services; an ordinary service can return a record per request instead of turning the record itself into a scoped bean needing subclassing.

Kotlin makes classes/methods `final` by default unless marked `open`. When integrating with Spring, ensure classes/methods using class proxies can be extended; the Kotlin Spring/all-open plugin can help where configured.

### 3.2. Final Methods: Proxy May Be Created, but Calls Are Not Forwarded as Expected

```java
public class RequestData {
    private final String token = "stored-in-real-target";

    public String ordinaryMethod() {
        return token;
    }

    public final String finalMethod() {
        return token;
    }

    private String helper() {
        return token;
    }

    public String ordinaryCallsPrivate() {
        return helper();
    }
}
```

If a scoped class proxy subclasses `RequestData`:

- `ordinaryMethod()` can be intercepted and forwarded to the scope's corresponding target.
- `finalMethod()` **cannot be overridden**, so calls to the proxy are not forwarded by the scoped-target interceptor in the normal way. It may execute the inherited method directly on the **proxy object**, so the state read may not be the real target's state. Never rely on that method returning the target's `token`.
- Private `helper()` is not an independently interceptable entry point. However, if the proxy forwards `ordinaryCallsPrivate()` to the real target, and the target then calls `helper()`, the private method still **runs normally on the target**. "Cannot intercept" does not mean "private methods are disabled."

The `RequestData` example only illustrates the technical mechanics, not a full runnable Spring program; avoid calling `finalMethod()` on a scoped proxy to inspect a target. Spring often instantiates proxies via Objenesis to avoid invoking the target constructor twice, making inspecting uninitialized fields on the proxy even less reliable. Never treat coincidental matching values between proxy and target as a contract.

### 3.3. Static Methods, Constructors, and Additional Caveats

Class-based proxies do not turn Java static dispatch into dynamic dispatch; `ClassName.staticMethod()` calls still bypass the proxy. The target's constructor runs when Spring actually creates the target according to its bean lifecycle; constructor invocations do not go through the proxy's method interceptor.

Several other practical limitations:

- Constructor/package access or Java visibility constraints can prevent Spring from generating a subclass as expected.
- The Java Platform Module System (JPMS) enforces module access and `opens` rules. Class proxies via CGLIB may fail for types in closed modules/packages; for example, attempting to proxy classes from `java.lang` on the module path is heavily restricted.
- Non-public beans, private nested classes, or inaccessible APIs can complicate proxy setup and verification.
- Methods from `Object` such as `equals`, `hashCode`, and `toString` have special handling depending on the proxy mechanism; do not use them to infer the active scoped target or identity across requests.
- Proxies do not automatically make mutable fields thread-safe; even when a target is session-scoped, multiple HTTP requests in the same session can run concurrently.

## 4. Interface-Based Proxy (JDK Dynamic Proxy) as an Alternative

If an interface captures the full external behavior, you can choose `ScopedProxyMode.INTERFACES`:

```java
public interface CurrentUser {
    String id();
}
```

```java
import org.springframework.context.annotation.ScopedProxyMode;
import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.RequestScope;

@Component
@RequestScope(proxyMode = ScopedProxyMode.INTERFACES)
public final class HttpCurrentUser implements CurrentUser {
    @Override
    public String id() {
        return "resolved-for-request";
    }
}
```

In a real application, the singleton service should receive `CurrentUser`:

```java
import org.springframework.stereotype.Service;

@Service
public class AuditService {
    private final CurrentUser currentUser;

    public AuditService(CurrentUser currentUser) {
        this.currentUser = currentUser;
    }

    public String currentActor() {
        return currentUser.id();
    }
}
```

The three sources above must be placed in three Java files matching their public type names, in the same package, running inside a web-aware Spring MVC context. `HttpCurrentUser` is `final`, yet **a JDK dynamic proxy does not need to extend the implementation**, so the interface proxy remains valid. Spring creates a proxy assignable to `CurrentUser`. Choose to inject `CurrentUser`, not `HttpCurrentUser`:

```java
// Invalid with INTERFACES proxy:
private final HttpCurrentUser currentUser;

// Valid with INTERFACES proxy:
private final CurrentUser currentUser;
```

A JDK proxy only exposes methods belonging to the interfaces it implements. If `HttpCurrentUser` has an extra `internalDetail()` method not declared on `CurrentUser`, a consumer holding the `CurrentUser` proxy cannot invoke that method directly. Casting a JDK proxy to `HttpCurrentUser` in Java is also invalid. With a JDK proxy, calls through the interface pass through the invocation handler to the target even if the implementation method on the class is `final`, provided the method satisfies the interface contract and is invoked via the proxy. That is why interfaces help bypass the limitation against subclassing `final` classes.

| Criterion | `TARGET_CLASS` (CGLIB) | `INTERFACES` (JDK proxy) |
| --- | --- | --- |
| What proxy is created? | Subclass of target class | Object implementing one or more interfaces |
| Suitable injection point | Concrete class or its interface | Interface |
| `final` target class | Unsuitable | Usable, if an interface exists |
| `final` target method | Not intercepted via override | Interface calls still forward to implementation |
| Extra method declared only on class | Proxiable if overridable | Not exposed through interface proxy |
| API extensibility | Depends on inheritance | Depends on interface contract |
| Preference | Need concrete-type injection and class is proxiable | Stable business interface exists, or want to support final implementations |

For code where adding an interface is impossible or proxying is undesirable, `ObjectProvider<T>`/lookup at point of use provides explicit target control.

## 5. Complete Spring Core Example: Subclass Proxy and Prototype Dependency

The following example runs without a Servlet container or web server, letting you observe precisely how a singleton holds a class-based scoped proxy. We use `prototype` because Spring Core always supports this scope. The same class/method limitation principles explain why request/session-scoped class proxies must use interceptable methods.

Requirements: **JDK 17+, Maven 3.9+**. The example specifies Spring Framework **6.2.19**. The program keeps the proxy stable and creates two distinct prototype targets across two calls. If working with Spring Framework 7.x, you can substitute the version matching your project's dependency set.

Structure:

```text
class-proxy-demo/
├── pom.xml
└── src/main/java/edu/example/proxy/
    ├── App.java
    ├── AppConfig.java
    ├── VisitToken.java
    └── Viewer.java
```

**pom.xml**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>edu.example</groupId>
    <artifactId>class-proxy-demo</artifactId>
    <version>1.0.0</version>
    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-context</artifactId>
            <version>6.2.19</version>
        </dependency>
    </dependencies>
    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>

                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.5.0</version>
                <configuration>
                    <mainClass>edu.example.proxy.App</mainClass>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

**src/main/java/edu/example/proxy/VisitToken.java**

```java
package edu.example.proxy;

import java.util.concurrent.atomic.AtomicInteger;

public class VisitToken {
    private static final AtomicInteger SEQUENCE = new AtomicInteger();

    private final int number = SEQUENCE.incrementAndGet();

    // Must be overridable if you want the class proxy to forward calls to the target.
    public int number() {
        return number;
    }
}
```

**src/main/java/edu/example/proxy/Viewer.java**

```java
package edu.example.proxy;

public class Viewer {
    private final VisitToken tokenProxy;

    public Viewer(VisitToken tokenProxy) {
        this.tokenProxy = tokenProxy;
    }

    public int number() {
        return tokenProxy.number();
    }
}
```

**src/main/java/edu/example/proxy/AppConfig.java**

```java
package edu.example.proxy;

import org.springframework.beans.factory.config.ConfigurableBeanFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Scope;
import org.springframework.context.annotation.ScopedProxyMode;

@Configuration(proxyBeanMethods = false)
public class AppConfig {
    @Bean
    @Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE,
           proxyMode = ScopedProxyMode.TARGET_CLASS)
    public VisitToken visitToken() {
        return new VisitToken();
    }

    @Bean
    public Viewer viewer(VisitToken visitToken) {
        return new Viewer(visitToken);
    }
}
```

**src/main/java/edu/example/proxy/App.java**

```java
package edu.example.proxy;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class App {
    public static void main(String[] args) {
        try (AnnotationConfigApplicationContext context =
                     new AnnotationConfigApplicationContext(AppConfig.class)) {

            VisitToken firstProxy = context.getBean(VisitToken.class);
            VisitToken secondProxy = context.getBean(VisitToken.class);
            Viewer viewer = context.getBean(Viewer.class);

            int firstTargetNumber = viewer.number();
            int secondTargetNumber = viewer.number();

            System.out.println("same proxy: " + (firstProxy == secondProxy));
            System.out.println("distinct targets: "
                    + (firstTargetNumber != secondTargetNumber));
            System.out.println("positive ids: "
                    + (firstTargetNumber > 0 && secondTargetNumber > 0));
        }
    }
}
```

Run from the directory containing `pom.xml`:

```bash
mvn -q compile exec:java
```

**stdout of the three `println` statements:**

```text
same proxy: true
distinct targets: true
positive ids: true
```

Explanation: Spring registers a scoped proxy under the bean name `visitToken`; the actual prototype target sits behind the resolution mechanism. Repeated `getBean(VisitToken.class)` calls return the same singleton proxy because the proxy bean definition is managed in singleton scope. `Viewer` is also a singleton holding that reference; each time `tokenProxy.number()` is intercepted, a new prototype target is created, so the retrieved numbers are two distinct positive integers.

The output states only relationships between values because exact integers can shift if another bean accesses a target early. This is a **prototype scoped proxy**, not a measurement of request/session scope; the point to observe is the subclassing and call-forwarding mechanism.

**Experiment to try:** Mark `VisitToken` as `final` or make the `number()` method `final`. With a `final` class, CGLIB class proxy creation will fail. With a `final` method, the proxy cannot override it to forward the call; if the method reads a field, it may observe proxy state rather than target state and the result must not be trusted. Both variants are analyzed anti-patterns, **not** part of the runnable sample provided.

## 6. Equivalent Scenario with Request Scope

In a Spring MVC application, suppose the request-handling context looks like this:

```java
package edu.example.web;

import java.util.UUID;
import org.springframework.stereotype.Component;
import org.springframework.web.context.annotation.RequestScope;

@Component
@RequestScope
public class RequestTrace {
    private final String id = UUID.randomUUID().toString();

    public String id() {
        return id;
    }
}
```

```java
package edu.example.web;

import org.springframework.stereotype.Service;

@Service
public class TraceService {
    private final RequestTrace trace;

    public TraceService(RequestTrace trace) {
        this.trace = trace;
    }

    public String currentTrace() {
        return trace.id();
    }
}
```

The two classes above are Spring MVC components, requiring a web-aware `ApplicationContext`, annotation scanning, and calls executing inside a request; they are not a standalone `main` program. `@RequestScope` defaults to `TARGET_CLASS` and `id()` is public and non-final. Spring injects a class-based proxy into the singleton `TraceService`. Within one request, the `RequestTrace` target is reused; across different requests, a different target with a different ID is used. Making `RequestTrace` a `final class` prevents the class-based proxy from being created, while making `id()` `final` prevents the proxy from intercepting that method.

This does **not** mean every call to `TraceService.currentTrace()` is valid. When called from a background thread outside request binding, the scoped proxy cannot find a request context; typically `ScopeNotActiveException` or a cause such as "No thread-bound request found" occurs. A proxy resolves lifecycle mismatches, but does not fabricate a request context or propagate it to an executor.

`@SessionScope` and `@ApplicationScope` likewise default to creating class-based scoped proxies under Spring's annotation model. Be mindful that the same session bean may be accessed concurrently by multiple request threads, even when all methods are properly proxied.

## 7. Self-Invocation: Do Internal Calls Go Through the Proxy?

With **Spring AOP proxies** such as `@Transactional`, `@Cacheable`, or a custom advice, a `this.anotherMethod()` call from inside the target normally does **not** go back through the proxy. Consider this illustrative code:

```java
@Service
public class PaymentService {
    public void placeOrder() {
        charge(); // this.charge(): direct call inside target
    }

    @Transactional
    public void charge() {
        // Database operations
    }
}
```

This snippet requires importing `Service` and `Transactional` along with Spring transaction configuration; it is not a standalone runnable project. If external code calls `paymentService.placeOrder()` through the proxy while `placeOrder()` has no transaction advice, the internal call to `charge()` will not automatically activate `@Transactional` advice on `charge()`. If external code calls `paymentService.charge()` **through the proxy**, advice can apply depending on transaction config and method signature.

```text
External caller → proxy → target.placeOrder()
                                  |
                                  +-- this.charge() [bypasses AOP proxy]

External caller → proxy → advice → target.charge()
```

**Distinguishing from scoped proxies:** Once an external caller invokes a public method through a scoped proxy, the proxy selects the scoped target; if that target method calls an internal helper (private, public, etc.), the helper still runs on **that already-selected target**. Self-invocation there does not switch to another scope's target, and usually does not need to re-resolve scope. However, if the helper needs another AOP advice, self-invocation can still bypass that advice. That is why you should not generalize that every internal call breaks scoped beans.

Solutions when advice must intercept the method:

1. Move the advised method into another collaborating Spring bean and invoke it via the injected bean so the call genuinely passes through the proxy.
2. If a sensible interface already exists, use an interface-based proxy with the target method declared on the interface.
3. Only when there is a clear reason, use `AopContext.currentProxy()` and enable `exposeProxy`, as it couples business code to Spring's proxy mechanism.
4. If you must intercept **self-invocation/constructors/private methods** at the bytecode level, Spring AOP proxies cannot do this; consider AspectJ weaving or restructuring the calls appropriately. Weaving carries its own deployment constraints.

## 8. ObjectProvider: Avoiding Subclass Proxies or Controlling Target per Operation

When a concrete class is final, or an operation needs to keep **the same prototype target across multiple method calls**, you can inject `ObjectProvider<T>` and request the target **inside the method**, when the scope context is ready:

```java
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.stereotype.Service;

@Service
public class GenerateReportService {
    private final ObjectProvider<ReportBuilder> builders;

    public GenerateReportService(ObjectProvider<ReportBuilder> builders) {
        this.builders = builders;
    }

    public String createReport(String title) {
        ReportBuilder builder = builders.getObject();
        builder.title(title);
        builder.addLine("Content");
        return builder.build();
    }
}
```

This snippet illustrates the API; `ReportBuilder` must be an application-declared prototype bean with `title`, `addLine`, and `build` methods. `getObject()` resolves the target at runtime. If it is a prototype, each time `createReport` calls `getObject()`, it receives a new instance and then **holds that instance** across the three method calls. If a prototype scoped proxy were used to call `title`, `addLine`, and `build` separately, each call could hit a different target, losing accumulated data.

With a request-scoped target, `ObjectProvider.getObject()` succeeds only when a request scope is active. Calling it during application startup or from a background task lacking a request context will still fail. Using a provider does not extend scope lifetimes or copy request contexts automatically.

Practical choices:

| Situation | Approach |
| --- | --- |
| Singleton needs to call a request bean method per HTTP request, non-final class | `@RequestScope` / `@Scope(..., TARGET_CLASS)` and public overridable method |
| Final class with a stable shared interface | `ScopedProxyMode.INTERFACES`, inject via interface |
| Need a dedicated prototype target for an **entire multi-step operation** | `ObjectProvider<T>.getObject()` once inside the operation |
| Want to avoid depending on web beans | Pass request data as method parameters or immutable DTOs |
| Proxy needs to intercept private/static/constructors | Redesign the API; ordinary Java proxies do not support this |
| AOP advice must take effect on internal calls | Delegate through a proxied collaborator bean or use weaving when justified |

## 9. Practical Troubleshooting

| Symptom | Possible cause | How to check and fix |
| --- | --- | --- |
| `Cannot subclass final class` / bean creation failure | `TARGET_CLASS` on a final class or record | Remove `final` if sensible, switch to an interface proxy, or use a provider |
| Final method reads wrong state, differing from target | Subclass proxy does not intercept final methods | Make the dispatched method non-final; call via interface proxy; do not rely on coincidental matches |
| Private method with `@Transactional` does not start a transaction | Private methods are not Spring proxy interception points | Place transaction boundary on a public method called via proxy, or split into another bean |
| `No thread-bound request found` | Request target resolved outside a web request | Call within a request; pass needed data into async tasks |
| Injecting implementation class fails with type error when using `INTERFACES` | JDK proxy is not a subtype of the implementation | Inject the declared interface |
| Prototype injected into singleton is created only once | Direct injection resolves target at initialization | `ObjectProvider` or prototype scoped proxy when appropriate |
| Prototype scoped proxy returns missing state across multiple methods | Each intercepted method resolves a new target | Fetch one target via provider and use it for the whole operation |
| `@Transactional` on internally called method has no effect | Self-invocation bypasses the AOP proxy | Route the call through a proxied bean |
| Proxy fails under Java module path | Module/package not open for subclassing/reflective access | Check module exports/opens, use interface proxies where suitable |
| Kotlin bean works unproxied but fails when proxied | Classes/methods are final by default | Ensure classes/methods are open for Spring to proxy, or use interfaces |

### Systematic Debugging

- Verify that the bean definition actually has the intended `scope` and appropriate `proxyMode`.
- Inspect the type at the injection point instead of blindly assuming the proxy is the concrete class. For an AOP bean, `AopUtils.isAopProxy(bean)` and `AopUtils.isCglibProxy(bean)` can help when debugging. They are Spring APIs—avoid putting business branching logic based on proxy types into production code.
- Check how the call is made: does the external caller go through the injected proxy, or is it using `new`, `this.`, self-invocation, or a final/private method?
- If real tracing is needed, enable appropriate logging for bean creation/AOP in a test environment and inspect the exception root cause; do not rely on dynamically generated proxy names like `$$SpringCGLIB$$...` as a stable API.
- Write an integration test in a web-aware context and execute **two requests** to confirm scope-based target selection while testing the proxied methods.
- If thread-safety is required, test concurrency/invariants separately. Proxies do not replace thread-safety testing.

## 10. Design Rules to Remember

1. **Class-based scoped proxies require subclassable classes and overridable methods.** Avoid `final` on classes/methods Spring must intercept; `private`, `static`, and constructors cannot be intercepted by subclass proxies.
2. **Explicit public methods are the most reliable interception points.** Protected/package-private methods should only be used after verifying visibility and the specific Spring facility.
3. **Inject via interface when the contract is stable or the implementation is final.** JDK proxies do not expose the concrete type; dependencies must be declared using the interface.
4. **Distinguish proxy from target:** the injected bean may be a long-lived proxy; each valid call resolves the target matching `request`, `session`, or `prototype`.
5. **A single prototype target for multiple steps should be obtained once via a provider.** A prototype scoped proxy may resolve a different object on each method call.
6. **Self-invocation bypasses Spring AOP proxy advice.** It does not mean helpers on the target fail to execute, but it can prevent annotation advice from taking effect.
7. **Do not confuse lifecycle, interception, and concurrency.** Scope/proxy governs instance retrieval; transactions, thread synchronization, and data consistency are separate designs.

## 11. Self-Check Questions

1. Why can't a `final` class be represented by a class-based CGLIB scoped proxy? Do `record`s face the same limitation?
2. A non-final class has `public final String id()`. Can a class-based proxy be created? Will it intercept `id()` to delegate to the request target?
3. A private helper is called from a public method that a scoped proxy has forwarded to the target: does the helper run? Is it independently intercepted?
4. If a singleton injects a prototype bean via `@Scope(value="prototype", proxyMode=TARGET_CLASS)`, will two method calls on the proxy hit the same target?
5. Why does an interface-based proxy work with a final implementation yet fail to inject into a field typed as the implementation?
6. Outside scoped proxies, in a Spring AOP proxy why can `this.pay()` called from `placeOrder()` cause `@Transactional` on `pay()` not to be applied?
7. To keep one `ReportBuilder` prototype for `setTitle`, `addLine`, and `build` within the same operation, should you choose a provider or a scoped proxy called three times?
8. A request-scoped proxy is invoked inside `@Async` where the new thread has no request context: if the class has non-final methods, will it run properly on its own?

**Suggested answers:** (1) CGLIB must create a subclass, and final classes/records forbid inheritance. (2) A proxy of the class can be created, but final methods cannot be intercepted. (3) The helper runs on the target if the public method already delegated; the private method itself cannot be overridden/intercepted. (4) Same target is not guaranteed; each intercepted call can create a new prototype. (5) A JDK proxy implements the interface rather than extending the implementation. (6) Self-invocation executes directly on the target, bypassing proxy interception. (7) Provider, retrieving the target once per operation. (8) No; lacking an active scope context when resolving the target will fail.
