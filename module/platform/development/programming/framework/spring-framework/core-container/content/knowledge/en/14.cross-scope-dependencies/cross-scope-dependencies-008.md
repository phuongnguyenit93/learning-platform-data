# @Lookup Limitations with Final Classes and Objects Created by @Bean

## 1. The Problem and Key Conclusions

In the Spring Core Container, **lookup method injection** is a technique for a bean—typically a **singleton**—to request another bean at method execution time, typically a **prototype** bean needing a fresh instance for each task. The `@Lookup` annotation lets you declare a method that Spring replaces with logic to retrieve a bean from the container.

However, `@Lookup` **does not work with every kind of class or every bean registration method**. Two core limitations:

1. **The class containing the lookup method cannot be `final`, and the lookup method itself cannot be `final`.** Spring must generate a **dynamic subclass** and override the method; Java forbids subclassing a `final class` and forbids overriding a `final method`.
2. **Lookup method injection does not work on objects created by factory methods, especially instances returned from `@Bean` methods in `@Configuration`.** Spring receives an instance already constructed by the factory method, so it has no opportunity to use a dynamic subclass to substitute that instance's creation.

These limitations are explicitly documented in Spring Framework's *Method Injection* documentation; they are constraints of the mechanism, not annotation naming rules.

**Practical choice:** use `@Lookup` for overridable classes/methods that Spring **instantiates directly via constructor and manages as a bean definition**. For `final` classes, `final` methods, or `@Bean` products, consider **injecting `ObjectProvider<T>` or `ObjectFactory<T>`** and calling `getObject()` at the moment of use.

## 2. Recap: Why @Lookup Is Needed for Cross-Scope Dependencies

Suppose a `CheckoutService` is a singleton yet needs a prototype-scoped `CheckoutAttempt` for each execution. If you write direct constructor injection:

```java
@Service
public class CheckoutService {
    private final CheckoutAttempt attempt;

    public CheckoutService(CheckoutAttempt attempt) {
        this.attempt = attempt;
    }

    public void process() {
        attempt.execute();
    }
}
```

The snippet above is **illustrative code**, requiring a `CheckoutAttempt` class with a prototype bean definition and the `@Service` import. Singleton `CheckoutService` is created once; the prototype dependency is resolved when that singleton is created. Therefore, repeated calls to `process()` still reuse **the same injected object**, rather than creating a new instance per call.

If `CheckoutService` qualifies for lookup method injection, you can write:

```java
@Component
public class CheckoutService {
    public void process() {
        CheckoutAttempt attempt = newAttempt();
        attempt.execute();
    }

    @Lookup("checkoutAttempt")
    protected CheckoutAttempt newAttempt() {
        throw new IllegalStateException("Spring must override this method");
    }
}
```

This is also **illustrative integration code**; it requires importing `@Component` and `@Lookup`, a bean named `checkoutAttempt`, and an `execute()` method. When Spring creates a `CheckoutService` bean via its normal constructor and processes `@Lookup`, the container generates a **dynamic subclass** with an overridden version of `newAttempt()`. When `process()` calls that method on the Spring-supplied bean, the call turns into a lookup of the target bean.

The original method body above intentionally throws an exception so that **not being overridden by Spring** becomes obvious. If you use an object created via `new CheckoutService()` outside Spring, the original method runs and throws `IllegalStateException`. The annotation does not transform the bytecode of every instance of the class automatically.

If no name is specified in `@Lookup`, Spring resolves the target bean by the method's **return type**. Specifying `@Lookup("checkoutAttempt")` explicitly by name is useful when the container holds multiple beans of the same type; that name must match the bean definition.

## 3. Technical Mechanism: Why Java `final` Blocks @Lookup

Spring implements **method injection via CGLIB-based dynamic subclassing**. Conceptually, when Spring creates a bean of a class like this:

```java
public class CommandManager {
    @Lookup("command")
    protected Command obtainCommand() {
        throw new UnsupportedOperationException();
    }
}
```

Spring needs to generate a subclass whose behavior is **equivalent** to this explanatory code:

```java
// PSEUDOCODE to visualize the mechanism, not Java source generated by Spring.
class CommandManagerGeneratedSubclass extends CommandManager {
    @Override
    protected Command obtainCommand() {
        return beanFactory.getBean("command", Command.class);
    }
}
```

The second snippet is **contextual pseudocode assuming `Command` and `beanFactory`**, not standalone compilable; the actual subclass is generated by Spring via bytecode. The key lies in the `extends` and `@Override` keywords:

- To use `extends CommandManager`, `CommandManager` must permit subclassing.
- To `@Override obtainCommand()`, the method must be an overridable instance method.
- When a client invokes the method on the **container-supplied subclass instance**, Java virtual dispatch enters the Spring-generated implementation.
- When a client constructs the original instance manually via `new CommandManager()`, there is no subclass and no lookup injection.
- Even when Spring overrides successfully, **the target bean's scope still decides** whether each lookup yields a new object or an existing one. `@Lookup` does not turn a singleton into a prototype.

### 3.1. Final Class: Cannot Generate a Subclass

```java
@Component
public final class FinalCommandManager {
    @Lookup("command")
    protected Command obtainCommand() {
        throw new UnsupportedOperationException();
    }
}
```

**Invalid configuration sample; do not run:** this requires a matching `Command` type, yet even if the target bean exists, Spring cannot subclass `FinalCommandManager`. There is no `@Lookup` override mechanism on a `final` class. Depending on the bean creation path and Spring version, the issue can surface during bean creation or at method call time; **do not assume one fixed exception** across all configurations.

You should not casually remove `final` if class immutability or architectural rules call for `final`: you can keep the class `final` and inject a provider via constructor instead.

### 3.2. Final Method: The Subclass Cannot Override It Either

```java
@Component
public class FinalMethodManager {
    @Lookup("command")
    protected final Command obtainCommand() {
        throw new UnsupportedOperationException();
    }
}
```

**Invalid configuration sample.** `FinalMethodManager` can be subclassed, yet Java **forbids overriding** `protected final obtainCommand()`. Having `@Lookup` on the method does not lift that restriction. In some cases Spring may still create the bean, but calls to the `final` method will not turn into lookups as expected; exact failure behavior depends on configuration handling. Never rely on the mere presence of the annotation as proof that method injection is active.

### 3.3. Other Method Types Are Also Unsuitable

`static` methods lack virtual dispatch like instance methods and cannot be overridden. `private` methods are not overridden by subclasses. Constructors are not overridable methods. Therefore, design lookup methods as **non-`final` `protected` or `public` instance methods** whose return type specifies the bean to retrieve. You may declare them `abstract` if the bean registration mechanism accepts that abstract class and Spring generates the subclass, or provide a concrete stub method (often more convenient with component scanning and unit tests).

A Java 17 example of overriding rules, without Spring:

```java
public class FinalRulesDemo {
    static class Parent {
        protected String changeable() { return "parent"; }
        protected final String fixed() { return "fixed"; }
    }

    static class Child extends Parent {
        @Override
        protected String changeable() { return "child"; }
        // Cannot override fixed() here.
    }

    public static void main(String[] args) {
        Parent obj = new Child();
        System.out.println(obj.changeable());
        System.out.println(obj.fixed());
    }
}
```

Save as `FinalRulesDemo.java` and run:

```bash
javac FinalRulesDemo.java
java FinalRulesDemo
```

Exact stdout:

```text
child
fixed
```

If you add a `fixed()` method with the same signature to `Child`, `javac` fails to compile because a `final` method cannot be overridden. Likewise, changing `Parent` to `final class Parent` prevents `extends Parent` from compiling. These are Java rules that Spring cannot bypass.

## 4. Specific Limitation for Objects Created by @Bean

Place two ways of creating the same service side by side:

```java
@Component
public class ContainerCreatedManager {
    @Lookup("taskContext")
    protected TaskContext currentContext() {
        throw new UnsupportedOperationException();
    }
}
```

In this case, Spring can directly pick the class to instantiate and substitute a dynamic subclass when eligible. `@Component` and component scanning (or registering the class directly in `AnnotationConfigApplicationContext`) give the container ownership over instantiation.

In contrast:

```java
@Configuration(proxyBeanMethods = false)
public class AppConfig {
    @Bean
    FactoryCreatedManager factoryCreatedManager() {
        return new FactoryCreatedManager();
    }
}

public class FactoryCreatedManager {
    @Lookup("taskContext")
    protected TaskContext currentContext() {
        throw new UnsupportedOperationException();
    }
}
```

This is **illustrative code**, requiring Spring imports and a `TaskContext` class. Here Spring invokes the **factory method** `factoryCreatedManager()` and receives the object returned by `new FactoryCreatedManager()`. The container cannot directly substitute a subclass for the `new` statement sitting inside the factory method. **`@Lookup` on `FactoryCreatedManager.currentContext()` is not replaced** by standard lookup method injection.

Distinguish these three situations carefully:

| Bean and annotation location | Can lookup method injection be used? | Why? |
|---|---|---|
| Non-final `@Component` class, non-final `@Lookup` method, instantiated directly by Spring | **Yes**, if bean definition and lookup target are valid | Spring directly instantiates a dynamic subclass |
| Object **returned by** `@Bean FactoryCreatedManager factoryCreatedManager()`, where the product class has `@Lookup` | **No** under the standard mechanism | The factory already instantiated the product; Spring does not replace the returned instance with a subclass |
| `@Bean` method placed on a `@Configuration` class returning another bean | **Not `@Lookup` itself** | `@Bean` is a factory declaration to produce a bean; it is not lookup method injection |

**`@Configuration(proxyBeanMethods = true)` does not fix this limitation.** That mode relates to Spring intercepting `@Bean` method calls within the configuration class to preserve bean reference semantics; it is **different** from replacing `@Lookup` inside a **product class** returned by a factory method. Do not use `proxyBeanMethods=true` as a trick to enable lookup method injection on `@Bean` products.

Nor should you mistakenly assume that `@Lookup` can never be used anywhere in an app that uses `@Configuration`. What matters is **how the bean containing the lookup method is instantiated**; the question here concerns **objects produced by `@Bean` factory methods**. Avoid overgeneralizing to "whenever a project uses `@Bean`, all `@Lookup` annotations stop working."

## 5. Java 17+ Spring Experiment: @Lookup Overridden vs. @Bean Not Overridden

This lab places both creation paths side by side. `ComponentManager` is created directly by Spring, so `@Lookup` works; `FactoryManager` is returned by a `@Bean` method, so its `@Lookup` method is not overridden. Finally, `ProviderManager` shows how to solve the `@Bean` case reliably with `ObjectProvider`.

**Requirements:** JDK 17+ and Maven 3.9+. Uses Spring Framework 6.2.0 (plain Core Container, no Spring Boot or server required).

Structure:

```text
├── pom.xml
└── src/main/java/example/LookupLimitsDemo.java
```

File `src/main/java/example/LookupLimitsDemo.java`:

```java
package example;

import java.util.concurrent.atomic.AtomicInteger;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.beans.factory.annotation.Lookup;
import org.springframework.beans.factory.config.ConfigurableBeanFactory;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

public class LookupLimitsDemo {

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(
                Config.class, ComponentManager.class)) {

            ComponentManager component = ctx.getBean(ComponentManager.class);
            WorkUnit first = component.createWorkUnit();
            WorkUnit second = component.createWorkUnit();

            System.out.println("Component lookup A: " + first.id());
            System.out.println("Component lookup B: " + second.id());
            System.out.println("Different prototypes: " + (first != second));

            FactoryManager factory = ctx.getBean(FactoryManager.class);
            try {
                factory.createWorkUnit();
                System.out.println("Unexpected factory lookup success");
            } catch (IllegalStateException ex) {
                System.out.println("Factory lookup: original stub invoked");
            }

            ProviderManager provider = ctx.getBean(ProviderManager.class);
            WorkUnit third = provider.createWorkUnit();
            WorkUnit fourth = provider.createWorkUnit();

            System.out.println("Provider lookup A: " + third.id());
            System.out.println("Provider lookup B: " + fourth.id());
            System.out.println("Provider objects differ: " + (third != fourth));
        }
    }

    // Prototype bean used as the target for all three lookup approaches.
    public static final class WorkUnit {
        private static final AtomicInteger SEQUENCE = new AtomicInteger();
        private final int id = SEQUENCE.incrementAndGet();

        public int id() {
            return id;
        }
    }

    @Configuration(proxyBeanMethods = false)
    public static class Config {
        @Bean
        @Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
        public WorkUnit workUnit() {
            return new WorkUnit();
        }

        // Spring receives the FactoryManager already created by the factory method.
        @Bean
        public FactoryManager factoryManager() {
            return new FactoryManager();
        }

        // Factory method still uses provider injection successfully.
        @Bean
        public ProviderManager providerManager(ObjectProvider<WorkUnit> units) {
            return new ProviderManager(units);
        }
    }

    // This class is registered DIRECTLY with the container (via ctx).
    @Component
    public static class ComponentManager {
        @Lookup("workUnit")
        public WorkUnit createWorkUnit() {
            throw new IllegalStateException("Spring did not override @Lookup");
        }
    }

    // This instance, in turn, is returned by @Bean factoryManager().
    public static class FactoryManager {
        @Lookup("workUnit")
        public WorkUnit createWorkUnit() {
            throw new IllegalStateException("Factory stub was not overridden");
        }
    }

    // No dynamic subclass needed: provider holds on-demand bean lookup logic.
    public static final class ProviderManager {
        private final ObjectProvider<WorkUnit> units;

        public ProviderManager(ObjectProvider<WorkUnit> units) {
            this.units = units;
        }

        public WorkUnit createWorkUnit() {
            return units.getObject();
        }
    }
}
```

Deliberate points in the example design:

- `ComponentManager` is a **public static nested class**, non-final with a public non-final lookup method, so Spring can generate a subclass. This class is registered directly with `AnnotationConfigApplicationContext`, not produced by a `@Bean` method.
- `FactoryManager` is also non-final with a non-final method; the example removes `final` to isolate **specifically the factory-method instantiation limitation**.
- `ProviderManager` is intentionally `final` and still works with `ObjectProvider<WorkUnit>` because the provider does not need to subclass `ProviderManager`.
- `WorkUnit` can be `final` because it is the **target bean being looked up**, not the **class needing subclassing to override `@Lookup`**. The `final` limitation here applies to the **class containing the lookup method**, not automatically to every bean being looked up. Do not misattribute the constraint to the target.
- Both `@Lookup`-annotated methods have exception-throwing stubs so it is unmistakable when Spring has overridden them.

In the directory containing `pom.xml`, run:

```bash
mvn -q compile exec:java -Dexec.mainClass=example.LookupLimitsDemo
```

Expected program stdout (excluding Maven's own logs):

```text
Component lookup A: 1
Component lookup B: 2
Different prototypes: true
Factory lookup: original stub invoked
Provider lookup A: 3
Provider lookup B: 4
Provider objects differ: true
```

**Line-by-line comparison:**

1. `ctx.getBean(ComponentManager.class)` returns a Spring-created instance with a dynamic subclass. Two calls to `component.createWorkUnit()` resolve the prototype `workUnit` and receive objects with IDs 1 and 2.
2. `Different prototypes: true` confirms two distinct references. `@Lookup` itself does **not** create prototypes; the `@Scope(PROTOTYPE)` annotation on the target is what creates a new instance per lookup.
3. `factory.createWorkUnit()` runs **the stub in the original class**; `IllegalStateException` is caught so the program continues. This is the consequence of `FactoryManager` having been pre-instantiated by the `@Bean` factory method.
4. `provider.createWorkUnit()` calls `ObjectProvider.getObject()`; the third and fourth calls create `WorkUnit` IDs 3 and 4.
5. `Provider objects differ: true` illustrates that using a provider still works inside a `final` class created from `@Bean`.

If you change `ComponentManager` to `final` or `createWorkUnit()` to `final`, **do not treat that modified sample as still valid**. It violates method injection's subclassing/overriding requirement. There is no need to include such invalid configurations in the main runnable sample, because startup behavior/failure timing can depend on how the container creates beans and processes annotations.

## 6. The Kotlin Issue: Classes and Methods Are Final by Default

Kotlin generates classes and member functions as **final** by default, unlike Java where classes/methods are inheritable unless marked `final`. Consequently, Kotlin code like:

```kotlin
@Component
class TaskManager {
    @Lookup("task")
    fun newTask(): Task {
        error("Not overridden")
    }
}
```

can hit the exact same subclass/override limitation. This is illustrative code requiring `Task` and Spring Kotlin setup; it is not a standalone program.

You can use `open class TaskManager` and `open fun newTask()` where appropriate. In projects using the Kotlin `kotlin-spring`/`all-open` plugin, certain Spring annotations can cause classes/members to be compiled as `open` per configuration; **you must verify the actual bytecode and plugin setup** rather than assuming all `final` modifiers disappeared. If you prefer not to depend on whether a class can be opened, `ObjectProvider<T>` usually expresses the requirement more cleanly.

## 7. Why Can @Bean / proxyBeanMethods Cause Confusion?

Several mechanisms in Spring use proxy/subclass generation, yet they solve different problems:

| Mechanism | Goal | Object being intercepted |
|---|---|---|
| `@Lookup` method injection | Resolve a bean when the method is called, e.g., obtain a fresh prototype | **Class containing the lookup method** created directly by the container |
| `@Configuration(proxyBeanMethods = true)` | Intercept calls between `@Bean` methods to enforce bean semantics in full configuration classes | **Configuration class** and its `@Bean` method calls |
| Spring AOP proxy | Apply advice at supported join points such as method calls through the proxy | Proxied bean reference (JDK interface proxy/CGLIB proxy per configuration) |
| `ObjectProvider<T>` | Look up dependencies when code calls `getObject()` | Provider interacts with `BeanFactory`; no client subclassing needed |

Seeing a `@Configuration` enhanced with CGLIB **does not mean** the object returned by a `@Bean` method is also turned by Spring into a subclass supporting `@Lookup`. Enabling `proxyBeanMethods` is a decision about configuration-class semantics, not a fix for lookup methods on `@Bean` products.

Different proxy/AOP types may have their own `final` restrictions; however, avoid taking one AOP rule and mechanically applying it to every `@Lookup` case. When debugging, always identify **which bean** is subclassed, **which method** is overridden, and **who** instantiates the object.

## 8. Replacing @Lookup with ObjectProvider When Constrained

A design that works even when the class is `final` and created by `@Bean`:

```java
public final class InvoiceProcessor {
    private final ObjectProvider<InvoiceWork> works;

    public InvoiceProcessor(ObjectProvider<InvoiceWork> works) {
        this.works = works;
    }

    public void process(String invoiceId) {
        InvoiceWork work = works.getObject();
        work.execute(invoiceId);
    }
}

@Configuration(proxyBeanMethods = false)
class InvoiceConfig {
    @Bean
    InvoiceProcessor invoiceProcessor(ObjectProvider<InvoiceWork> works) {
        return new InvoiceProcessor(works);
    }
}
```

This is **illustrative integration code**, not a standalone program. It requires importing `ObjectProvider`, `@Configuration`, `@Bean`, registering an `InvoiceWork` bean, and providing `execute(String)`. This approach has two direct advantages:

1. `InvoiceProcessor` can remain `final` to protect class design.
2. The `@Bean` factory receives the Spring-injected provider and explicitly passes it to the constructor; Spring does not need to replace an already-created object.

**How `ObjectProvider` works:** at `works.getObject()`, Spring looks up the target bean according to its current definition and scope. If `InvoiceWork` is a prototype, each lookup typically creates a new instance; if singleton, the provider returns the same singleton. Using a provider does not automatically change scope or guarantee thread safety.

When a dependency may be optional, `getIfAvailable()`/`ifAvailable(...)` can fit. When multiple implementations exist, declare appropriate qualifiers/priorities or iterate `stream()`/`orderedStream()`; do not call `getObject()` and ignore multiple-bean errors. Using a provider to look up beans by name/type only changes the call style—scope and bean resolution rules still belong to the Spring container.

### 8.1. Choosing Between @Lookup and Provider

| Criterion | `@Lookup` | `ObjectProvider<T>` |
|---|---|---|
| Resolved at method execution time | Yes, when Spring overrides successfully | Yes, when calling the provider API |
| Client class allowed to be `final` | No | Yes |
| Client method allowed to be `final` | Lookup method: no | Method using provider can be `final` |
| Client bean created by `@Bean` method | Lookup injection not supported on product | Supports injecting provider into `@Bean` method or constructor |
| Requires Spring to subclass client | Yes | No |
| Dependency visibility in constructor | Lookup dependency appears indirectly in method annotation | Provider is declared directly in constructor |
| Plain Java tests without booting Spring | Must stub/override lookup method if invoked | Can pass a fake provider; tests control lookup clearly |
| Prototype target bean | Each lookup creates a new instance per scope | Each `getObject()` creates a new instance per scope |
| Singleton target bean | Returns the existing singleton | Returns the existing singleton |
| Prototype cleanup | Client is responsible | Client is responsible |

An additional option is an **application-defined factory** such as `WorkUnitFactory` with a `newWorkUnit()` method; that factory can itself receive `ObjectProvider` or be implemented appropriately. When creation logic takes many business parameters, a factory with a clear interface can be easier to test than querying the container directly.

### 8.2. Cleaning Up Prototypes Returned by Provider or Lookup

Regardless of whether `@Lookup` or `ObjectProvider` is used, Spring **does not automatically invoke destroy callbacks for prototype beans** after handing the instance to the caller. If a prototype holds streams, sockets, connections, or resources needing release, the caller/resource owner must close them on time. For example, a `WorkSession implements AutoCloseable` can be used as:

```java
try (WorkSession session = sessions.getObject()) {
    session.execute();
}
```

This snippet is illustrative in a context with `ObjectProvider<WorkSession> sessions`. With `@Lookup` results, use `try (WorkSession session = createSession()) { ... }` following the same principle. **Never close a shared singleton bean** after each lookup; cleanup must align with actual ownership and scope.

## 9. Common Application Errors

### 9.1. "I Added @Lookup, Yet the Method Still Runs the Original Code"

Check **how the object is created**:

- If code calls `new Service()`, it is a plain Java object; Spring does not subclass objects created outside the container.
- If the service is returned by a `@Bean` factory method, lookup method injection does not replace methods on that product.
- If the service is a `final class`, or the method is marked `final`, CGLIB cannot override as required.
- If the method is `private`/`static`, overriding should not be expected either.
- If the bean is properly managed directly, verify the bean definition, target bean name, and scope.

If the original method returns `null` instead of throwing an error, the problem can surface as a `NullPointerException` far away from bean registration. For learning examples, an exception-throwing stub makes errors obvious; for production, a controllable provider/factory design is usually preferred.

### 9.2. "The Target Bean Is Final, So @Lookup Isn't Allowed?"

Not necessarily. `@Lookup`'s subclassing restriction applies to **the class containing the method to be overridden**. The target bean, such as `WorkUnit`, can be a `final` class created by Spring via `@Bean`; the container can still resolve it if its bean definition is valid. In the runnable example in section 5, `WorkUnit` is `final`, yet the `@Lookup` component still retrieves it.

### 9.3. "Does @Lookup Guarantee a New Object on Every Call?"

No. `@Lookup` resolves beans according to **scope**. If the target bean is a singleton, two lookups can return the same object. When one instance per execution is needed, you must genuinely declare prototype scope or a scope matching the job semantics.

### 9.4. "Does Enabling proxyBeanMethods = true Fix @Lookup on a @Bean Product?"

No. It alters how `@Bean` methods are intercepted on `@Configuration` classes; it does not turn a factory-returned product into a lookup subclass of that product. Use `ObjectProvider`, `ObjectFactory`, or a factory abstraction if late resolution is required.

### 9.5. "Why Do Tests Using `new` Fail, While Running Inside Spring Works?"

Because `@Lookup` relies on a **Spring-generated subclass**. Unit tests directly calling `new ComponentManager()` execute the original method. You can test via an integration context, create a test subclass overriding the lookup method to return a fake, or refactor to use a constructor-passed provider. Tests should assert instance counts within the required scope, not merely check that an annotation is present.

### 9.6. "With Multiple Beans of the Same Return Type, Does Unnamed @Lookup Still Work?"

It depends on Spring's bean selection rules, qualifiers, and `@Primary`. If a single target cannot be uniquely determined, return-type lookup can fail due to ambiguity. `@Lookup("beanName")` explicitly names the target bean, provided the name and type are compatible.

### 9.7. "Should @Lookup Be Used to Fix Circular Dependencies or Web Scopes?"

`@Lookup` primarily solves **when to look up a bean**; it is not a general tool to cure all circular dependencies. For request/session scopes, `ObjectProvider` or a scoped proxy is usually more intuitive, though execution must still occur while the required scope is active. If no request is active, never assume lookup will create a request context on its own.

## 10. Implementation and Verification Checklist

Before accepting a `@Lookup` in a Spring project, answer in sequence:

1. **Bean containing lookup method:** Does Spring instantiate this class directly from its constructor bean definition, or is the object returned by an external `@Bean`/factory method?
2. **Overridability:** Is the class `final`? Is the method `final`, `private`, or `static`? In Kotlin, does the `all-open` plugin truly open the class/member?
3. **Target bean:** Does the name in `@Lookup("...")` exist? If looking up by type, is there one unambiguously selectable candidate?
4. **Target scope:** Is it truly `prototype` when expecting a new object? If singleton, repeated lookups can return the same reference.
5. **Call path:** Is the method called on the bean **returned by Spring**, or on a manually `new`'d object / another copy?
6. **Resources and concurrency:** Does the retrieved object hold resources needing closing, mutable state, or thread-bound scoped context?
7. **Tests:** Is there an actual test verifying two prototype retrievals yield two distinct instances, and for `@Bean`-created classes that the replacement provider works?

A small check usable in integration tests:

```java
ComponentManager manager = ctx.getBean(ComponentManager.class);
WorkUnit a = manager.createWorkUnit();
WorkUnit b = manager.createWorkUnit();
boolean fresh = a != b;
```

This is **illustrative code in a context with `ctx` Spring context** from section 5's example. `fresh` is `true` when `workUnit` is prototype and lookup injection was applied successfully. Do not infer this solely from the `createWorkUnit` method name or annotation without actually running it.

## 11. Self-Check Questions

**1. Why does a `final class` prevent `@Lookup` from working?**  
Because Spring must generate a dynamic subclass to override the method; Java forbids another class from using `extends` on a `final` class.

**2. Why is a `final method` in a non-final class still invalid?**  
Because even though Spring can subclass the class, a `final` method still cannot be overridden.

**3. A `@Bean` method returns an object with a `@Lookup` method; does Spring automatically override that method?**  
Not under the standard mechanism. The factory already instantiated the object; the container cannot replace that object creation with a dynamic subclass.

**4. Does `@Configuration(proxyBeanMethods=true)` fix the issue above?**  
No. It intercepts calls to `@Bean` methods on the configuration class; it does not automatically subclass `@Bean` products.

**5. Does a `final class` target bean always prevent another bean from using `@Lookup` to fetch it?**  
No. The class that must be subclassable is the one **containing the lookup method**; the target class only has to satisfy creation and scope rules for the target bean.

**6. If the client must be `final` or created from `@Bean`, what should be used?**  
Use `ObjectProvider<T>`/`ObjectFactory<T>` or an explicit factory, calling lookup at the exact point the bean is needed.

**7. Does `@Lookup` of a singleton target bean create a new instance on each call?**  
No. Lookup merely fetches the bean according to its scope; a singleton still normally returns the same instance.
