# Role of the Temporary Future from the Target Method vs. the Proxy-Returned Future in Spring @Async

## 1. The Question: Why Must an @Async Method Return a Future Itself If the Proxy Already Returns a Future?

In Spring Framework, a method annotated with `@Async` can declare a return type of `Future<T>` or `CompletableFuture<T>`. When invoked through a Spring AOP proxy, **the caller receives a Future representing the asynchronous execution**; this Future is created by Spring/executor infrastructure to track the task, and is not necessarily the exact Future object created inside the target method body.

Read the following snippet:

```java
@Async("workExecutor")
public CompletableFuture<String> calculate() {
    String value = expensiveCalculation();
    return CompletableFuture.completedFuture(value);
}
```

This is a fragment, requiring a Spring-managed bean, `@EnableAsync` configuration, an executor named `workExecutor`, and a real `expensiveCalculation()` function. Two questions commonly arise:

1. If the method already returns `CompletableFuture.completedFuture(value)` — an **already completed** future — why can the caller still see a Future that is **pending**?
2. If there is already a `CompletableFuture` created by the target, why does Spring still need to create a proxy Future?

The answer: there are **two roles** and typically **two objects**.

- **Target-side temporary Future:** the object returned from the method body after it finishes computing, used to pass the value or error to the advice mechanism executing the task on the worker.
- **Caller-facing async Future (proxy Future):** the object Spring returns immediately to the caller when turning the call into a task on the executor; it represents the execution process, including when the target method has not yet started or is still running.

This point is explained directly in Spring 6.2's `org.springframework.scheduling.annotation.Async` Javadoc: the target method must still satisfy the `Future` signature, so it can return a temporary handle merely carrying the value after computation; the proxy provides the real asynchronous handle to the client.

**Quick rule to remember:** *The temporary Future helps the method honor its return contract and hand off the result; the proxy Future helps the caller observe the completion timeline of the asynchronous call.*

## 2. Two Processing Layers: Call Boundary and Result Handoff

To understand properly, split an `@Async` invocation into two parts.

### 2.1. The Call Going Through the Proxy

Another service or caller receives the bean from the Spring context:

```java
Future<String> clientFuture = workService.calculate();
```

If `workService` is a Spring proxy and the method qualifies to be advised, the async interceptor picks the executor and **submits** the target method invocation. It returns a `Future` corresponding to the submitted task. This is not an assertion that the caller already has the result; the task may still be sitting in the queue or running.

### 2.2. The Method Body Executing on the Worker

On the worker, Spring invokes the target method. The method must conform to its declared return type:

```java
@Async("workExecutor")
public Future<String> calculate() {
    String computed = doWork();
    return CompletableFuture.completedFuture(computed);
}
```

This is a fragment: `doWork()` is business logic, not a call generated by Spring. After running `doWork()`, the target returns an already completed `Future<String>` carrying `computed`.

### 2.3. The Async Interceptor Transfers the Result to the Caller's Future

In the Spring Framework 6.2 model, after the target method returns:

1. The advice retrieves the result object from the invocation.
2. If it is a `Future<?>`, the advice may call `get()` on the target Future to obtain the value or error.
3. This result/exception is used to complete the task in the executor.
4. The `Future` the caller received from the proxy becomes completed/failed accordingly.

Visualization:

```text
Caller thread                        Spring proxy                Worker thread
    |                                     |                            |
    | call @Async method                  |                            |
    |------------------------------------>|                            |
    |                                     | submit invocation task     |
    |                                     |--------------------------->|
    |<------------------------------------|                            |
    | caller-facing Future<T>             |                   invoke target method
    | (often still pending)               |                            |
    |                                     |                   compute business value
    |                                     |                            |
    |                                     |                 return temporary Future<T>
    |                                     |                            |
    |                                     |                   unwrap temporary future
    |                                     |                     (get value or error)
    |                                     |                            |
    | caller Future completes             |<-------- completion -------|
    |                                     |                            |
    | callerFuture.get() -> T             |                            |
```

**Do not misunderstand:** the target does not directly "send" the temporary Future object to the caller via a regular Java return path. In proxy mode, Spring intercepts the call and supplies **a proxy-level result**. The final value may be the same, but object identity, completion timing, and tracking responsibility differ.

## 3. Must the Temporary Future Already Be Completed?

In the common pattern, **you should return an already completed Future** after computation:

```java
return CompletableFuture.completedFuture(value);
```

It creates no new task and does not by itself move work to another thread. The method itself was already moved to the worker **thanks to the `@Async` proxy**, so creating a `CompletableFuture.completedFuture(...)` at the end of the method is a clean way to satisfy the signature and hand over the result.

However, a target method can return an incomplete `Future`. Under Spring 6.2's interceptor mechanism, the worker may have to wait on `targetFuture.get()`, keeping the worker occupied until the temporary Future completes.

A bad example for pool efficiency (this is an **anti-pattern illustration**, not a standalone program):

```java
@Async("workExecutor")
public CompletableFuture<String> load() {
    return CompletableFuture.supplyAsync(
            () -> slowBlockingCall(),
            anotherExecutor);
}
```

Here, the outer call was placed onto `workExecutor`, while `supplyAsync` dispatches work to `anotherExecutor`. With Spring's proxy/execution bridge, the first worker may have to wait for the inner Future's result. That is **double scheduling**, not automatic optimization or non-blocking execution.

If `anotherExecutor` is the same small pool already saturated by parent tasks, waiting on a child Future can cause **thread starvation deadlock**. If you genuinely need a multi-step asynchronous pipeline, explicitly design the orchestration layer, choose an appropriate executor, or use `CompletableFuture` composition/async APIs without unnecessarily wrapping an `@Async` method.

**Reasonable exception:** there are integrations returning a Future from an existing API. Even then, you must still understand how the worker handles that result and test under load; do not assume every layer is non-blocking by default.

## 4. Return Signatures: void, Future, and CompletableFuture

Spring `@Async` in standard proxy mode only supports appropriate return-type categories:

| Declared method type | Future target must return | Caller observes | Key notes |
| --- | --- | --- | --- |
| `void` | None | No result handle from method | Exceptions cannot be delivered via Future; use error handler/monitoring |
| `Future<T>` | A temporary `Future<T>`, usually already completed | Actual proxy `Future<T>` | Caller uses `get()`, `isDone()`, `cancel()` |
| `CompletableFuture<T>` | A temporary `CompletableFuture<T>`, usually `completedFuture(value)` | Actual proxy `CompletableFuture<T>` | Can chain `thenApply`, `thenCompose`, `exceptionally` |

`CompletableFuture<T>` is a subtype of `Future<T>` so it is supported. Conversely, a method declaring plain `CompletionStage<T>` (not a subtype of `Future`), `String`, `Mono<T>`, or a business object is not by default a valid return type for standard Spring `@Async`. Reactor has its own concurrency model; do not mix up the APIs.

### 4.1. When to Choose Future<T>?

Use when the caller only needs to wait and retrieve the result via `get()`:

```java
@Async("workExecutor")
public Future<Integer> count() {
    int count = calculateCount();
    return CompletableFuture.completedFuture(count);
}
```

This is a fragment needing `calculateCount()`. Even though the target uses a temporary `CompletableFuture`, the caller can only rely on the `Future<Integer>` contract if the method is declared that way. Do not cast the proxy Future to `CompletableFuture` assuming compatibility — declare `CompletableFuture<Integer>` from the start if composition is needed.

### 4.2. When to Choose CompletableFuture<T>?

Use if the caller wants to compose results without calling `get()` immediately:

```java
@Async("workExecutor")
public CompletableFuture<Integer> countAsync() {
    int count = calculateCount();
    return CompletableFuture.completedFuture(count);
}
```

The caller can do:

```java
CompletableFuture<String> displayed = service.countAsync()
        .thenApply(number -> "count=" + number)
        .exceptionally(ex -> "unavailable");
```

These fragments require `calculateCount()` and an appropriate `service` variable. `thenApply` does not necessarily run on another worker; the callback may run on the thread completing the stage when using the variant without the `Async` suffix. Thus, choose `CompletableFuture` to **compose results**, and do not infer that every stage spawns a new thread.

### 4.3. No Need to Create Threads Manually Inside the Target

Once using `@Async` through a proxy, the target does not need `new Thread(...)` or `CompletableFuture.supplyAsync(...)` just to "make it async." The switch to the executor already happened before the target started running.

## 5. Runnable Experimental Example: Comparing Temporary Future and Proxy Future

The following example uses **Java 21, Maven, and Spring Framework 6.2.1**, without Spring Boot. It verifies four scenarios:

1. A method declaring `Future<String>` returns a completed temporary Future, while the proxy Future remains pending because the worker is still waiting on a latch.
2. A method declaring `CompletableFuture<String>` also has two objects and two potentially different completion timestamps.
3. A target method returns an **incomplete** `CompletableFuture`; the proxy Future only completes when the target Future is released.
4. A temporary Future completes with an error; the caller sees the corresponding error through the proxy Future.

### 5.2. Complete Java File

**File `src/main/java/demo/FutureBridgeDemo.java`:**

```java
package demo;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicReference;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.Async;
import org.springframework.scheduling.annotation.EnableAsync;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

public class FutureBridgeDemo {
    public static class Signals {
        final AtomicReference<Future<String>> targetFuture = new AtomicReference<>();
        final AtomicReference<CompletableFuture<String>> targetCompletable =
                new AtomicReference<>();
        final AtomicReference<CompletableFuture<String>> targetPending =
                new AtomicReference<>();
        final CountDownLatch futureReady = new CountDownLatch(1);
        final CountDownLatch futureRelease = new CountDownLatch(1);
        final CountDownLatch completableReady = new CountDownLatch(1);
        final CountDownLatch completableRelease = new CountDownLatch(1);
        final CountDownLatch pendingReady = new CountDownLatch(1);
    }

    public static class WorkService {
        private final Signals signals;

        public WorkService(Signals signals) {
            this.signals = signals;
        }

        @Async("workExecutor")
        public Future<String> loadFuture() throws InterruptedException {
            Future<String> temporary = CompletableFuture.completedFuture("F:42");
            signals.targetFuture.set(temporary);
            signals.futureReady.countDown();
            signals.futureRelease.await();
            return temporary;
        }

        @Async("workExecutor")
        public CompletableFuture<String> loadCompletable()
                throws InterruptedException {
            CompletableFuture<String> temporary =
                    CompletableFuture.completedFuture("CF:ok");
            signals.targetCompletable.set(temporary);
            signals.completableReady.countDown();
            signals.completableRelease.await();
            return temporary;
        }

        @Async("workExecutor")
        public CompletableFuture<String> pendingTarget() {
            CompletableFuture<String> temporary = new CompletableFuture<>();
            signals.targetPending.set(temporary);
            signals.pendingReady.countDown();
            return temporary;
        }

        @Async("workExecutor")
        public CompletableFuture<String> failedTarget() {
            return CompletableFuture.failedFuture(
                    new IllegalArgumentException("bad-input"));
        }
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAsync
    public static class AppConfig {
        @Bean("workExecutor")
        public ThreadPoolTaskExecutor workExecutor() {
            ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
            executor.setCorePoolSize(2);
            executor.setMaxPoolSize(2);
            executor.setQueueCapacity(8);
            executor.setThreadNamePrefix("async-");
            executor.setWaitForTasksToCompleteOnShutdown(true);
            executor.setAwaitTerminationSeconds(5);
            return executor;
        }

        @Bean
        public Signals signals() {
            return new Signals();
        }

        @Bean
        public WorkService workService(Signals signals) {
            return new WorkService(signals);
        }
    }

    private static void await(CountDownLatch latch, String label)
            throws InterruptedException {
        if (!latch.await(5, TimeUnit.SECONDS)) {
            throw new IllegalStateException("Timeout waiting for " + label);
        }
    }

    public static void main(String[] args) throws Exception {
        try (var context = new AnnotationConfigApplicationContext(AppConfig.class)) {
            WorkService service = context.getBean(WorkService.class);
            Signals signals = context.getBean(Signals.class);
            try {
                Future<String> callerFuture = service.loadFuture();
                await(signals.futureReady, "futureReady");
                System.out.println("futureTargetDone=" +
                        signals.targetFuture.get().isDone());
                System.out.println("futureProxyPending=" + !callerFuture.isDone());
                System.out.println("futureDistinct=" +
                        (callerFuture != signals.targetFuture.get()));
                signals.futureRelease.countDown();
                System.out.println("futureValue=" +
                        callerFuture.get(5, TimeUnit.SECONDS));

                CompletableFuture<String> callerCompletable =
                        service.loadCompletable();
                await(signals.completableReady, "completableReady");
                System.out.println("completableTargetDone=" +
                        signals.targetCompletable.get().isDone());
                System.out.println("completableProxyPending=" +
                        !callerCompletable.isDone());
                System.out.println("completableDistinct=" +
                        (callerCompletable != signals.targetCompletable.get()));
                signals.completableRelease.countDown();
                System.out.println("completableValue=" +
                        callerCompletable.get(5, TimeUnit.SECONDS));

                CompletableFuture<String> callerPending = service.pendingTarget();
                await(signals.pendingReady, "pendingReady");
                System.out.println("pendingProxyBefore=" +
                        !callerPending.isDone());
                signals.targetPending.get().complete("P:ready");
                System.out.println("pendingValue=" +
                        callerPending.get(5, TimeUnit.SECONDS));

                CompletableFuture<String> failure = service.failedTarget();
                try {
                    failure.get(5, TimeUnit.SECONDS);
                    throw new AssertionError("Expected failure");
                } catch (ExecutionException ex) {
                    System.out.println("failedCause=" +
                            ex.getCause().getClass().getSimpleName());
                }
            } finally {
                signals.futureRelease.countDown();
                signals.completableRelease.countDown();
                CompletableFuture<String> pending = signals.targetPending.get();
                if (pending != null && !pending.isDone()) {
                    pending.completeExceptionally(
                            new IllegalStateException("cleanup"));
                }
            }
        }
    }
}
```

**Why is there a separate `Signals` bean?** This is a harness verifying both sides of the call. `WorkService` is proxied by Spring; reading fields attached directly to the proxy object does not necessarily read the same state as the target instance. Therefore, the test puts `CountDownLatch` and `AtomicReference` into a **separate Signals bean**, injected into the target and also retrieved from the context in the caller. This is an illustrative testing/coordination technique, **not advice to store all production task state in a singleton**.

## 6. Explaining Each Group of Results

### 6.1. Future<T>: Target Completed, Proxy Not Yet

When the worker enters `loadFuture()`:

```java
Future<String> temporary = CompletableFuture.completedFuture("F:42");
signals.targetFuture.set(temporary);
signals.futureReady.countDown();
signals.futureRelease.await();
return temporary;
```

`temporary.isDone()` is `true` immediately after `completedFuture(...)`. However, the worker is still waiting on `futureRelease`, so **the target method has not returned yet** and the interceptor's task has not finished. Therefore:

```text
futureTargetDone=true
futureProxyPending=true
futureDistinct=true
```

Two independent objects have different states at the exact same moment. After the caller opens the latch, the target returns the temporary Future, and the interceptor extracts the value and pushes it out to the proxy Future. The caller receives `F:42`.

### 6.2. CompletableFuture<T>: Still Two Roles

`loadCompletable()` repeats the idea, merely changing the signature to `CompletableFuture<String>`:

```text
completableTargetDone=true
completableProxyPending=true
completableDistinct=true
completableValue=CF:ok
```

Even with the exact same `CompletableFuture<String>` type, the object created by the target **is not** the object received by the caller from the proxy in the example. Both are Futures, yet they carry different responsibilities.

This explains why writing `return CompletableFuture.completedFuture(value)` at the end of an `@Async` method **does not disable the asynchronous nature** of the call: running on the executor is decided at the proxy boundary; the target merely packages the value after processing.

### 6.3. Temporary Future Still Pending

`pendingTarget()` creates an incomplete `CompletableFuture<>` and returns it. At that point:

```text
pendingProxyBefore=true
```

When the caller completes `temporary` with:

```java
signals.targetPending.get().complete("P:ready");
```

the interceptor can retrieve the value and complete the proxy Future; the caller reads:

```text
pendingValue=P:ready
```

The test shows **the proxy Future depends on the completion state of the target Future** in Spring 6.2's bridge mechanism. With an unfinished temporary Future, the worker may be waiting on `get()`. That is why you should be wary of methods returning another background Future and waiting nested inside a small pool.

### 6.4. Temporary Future Completes with Error

`failedTarget()` returns:

```java
return CompletableFuture.failedFuture(
        new IllegalArgumentException("bad-input"));
```

The caller invokes `failure.get(...)` on the proxy Future and receives `ExecutionException` with cause `IllegalArgumentException`, so the program prints:

```text
failedCause=IllegalArgumentException
```

Do not assume target and proxy share the exact same exception wrapper object. The key point to observe is that the **business cause** can be transferred across the proxy/worker boundary and surface when the caller reads the result.

## 7. Different Completion Timestamps and Why Tests Easily Go Wrong

Suppose the caller calls `service.calculate()` when the pool has no idle worker. The call normally returns the proxy Future after the task is accepted, while execution on the worker may not have started yet.

The sequence can unfold as:

1. `t0`: caller receives the proxy Future in pending state.
2. `t1`: worker starts executing the target method.
3. `t2`: target finishes computing and creates temporary `completedFuture(value)`.
4. `t3`: target returns the temporary Future.
5. `t4`: interceptor unwraps the result.
6. `t5`: proxy Future completes so the caller can receive `value`.

In the latch-based example, `t2 < t3` is intentionally stretched to prove `temporary.isDone() == true` while `proxyFuture.isDone() == false`.

In a real application, a very fast computation can make the proxy Future already `isDone()==true` by the moment the caller inspects it, even though the call **genuinely did run through the executor**. Thus, you cannot rely solely on `isDone()` right after the call to conclude whether the proxy executed asynchronously or not.

To verify concurrency, prefer latches/Phasers controlling checkpoints or instrumentation recording submit/start/finish timestamps; do not rely merely on `Thread.sleep(...)`.

## 8. How Are Exceptions from the Target Future Propagated?

There are two error sources to distinguish.

### 8.1. Errors Occurring in the Target Body

Example:

```java
@Async("workExecutor")
public CompletableFuture<String> failFast() {
    throw new IllegalStateException("invalid");
}
```

When going through the proxy, the method body runs on the executor. With `Future`/`CompletableFuture` return types, the caller normally observes errors via the async handle, such as `future.get()` throwing `ExecutionException` or `future.join()` throwing `CompletionException`.

### 8.2. Target Returns a Failed Future

The example verified this with `failedFuture(...)`. The interceptor extracts the result from the temporary Future; if the temporary Future reports an error, that error is transferred into the async result for the caller. Do not fixate overly on the outer wrapper exception class: inspect `getCause()` appropriately.

### 8.3. Errors Right at Submission Time

If the executor/queue is overloaded or already shut down, Spring may reject the task **before the proxy returns a usable Future** with `TaskRejectedException`. This is not a computation error inside the method's temporary Future, because the method may not have run at all.

Handling pattern:

```java
try {
    CompletableFuture<String> result = service.calculateAsync();
    // Continue processing result when it completes.
} catch (TaskRejectedException ex) {
    // Handle case where executor does not accept the task.
}
```

This is a fragment requiring a service with `calculateAsync()` and `TaskRejectedException` imported. Retries must be bounded; never use unbounded retries that worsen overload.

## 9. Why Shouldn't You Arbitrarily Return CompletableFuture.supplyAsync(...) Inside @Async?

When an `@Async` method has already been moved by Spring onto pool A, calling `CompletableFuture.supplyAsync(..., poolB)` inside creates an additional task on pool B. If the target returns pool B's incomplete Future, the bridge on pool A's worker may wait for pool B's result.

Consequences:

- Loses a pool A worker waiting for work on pool B.
- If pool B is also tightly bounded or is actually pool A itself, waiting can cause starvation/deadlock.
- Harder to track timeouts, cancellation, MDC, transactions, and exceptions due to an extra boundary.
- Does not magically produce non-blocking I/O: blocking JDBC/HTTP calls still occupy some worker.

**Better approach:** if the work is synchronous and you want to offload it to a worker, simply compute inside the `@Async` method and `return CompletableFuture.completedFuture(value)`. If you already have an API natively returning `CompletableFuture` and the goal is composition without blocking a worker, consider removing the redundant `@Async` wrapper and returning/combining futures through proper composition APIs.

For genuine multi-step pipelines, design executor ownership and stage chaining explicitly instead of unknowingly mixing both the annotation and `supplyAsync`.

## 10. Proxy Boundary: When There Is No Proxy-Created Future

The entire target Future / proxy Future comparison above **only holds when the call actually goes through Spring async advice**. If the caller invokes the method directly on an object not managed by Spring or the target invokes an internal method on itself:

```java
public CompletableFuture<String> selfCall() {
    return this.calculateAsync(); // Bypasses proxy in AdviceMode.PROXY.
}
```

This is a fragment; `calculateAsync()` must belong to the same class. Under the default `@EnableAsync` mode (`AdviceMode.PROXY`), `this.calculateAsync()` does not trigger a new interceptor pass. The method runs as a normal Java call and may return **the exact Future created by the method itself**, because there is no proxy bridge at the call site.

Do not conclude that "proxy Future and temporary Future are the same object" just from observing a self-invocation case; that is a **different-mechanism** call path.

Proxy checklist:

- Are `@EnableAsync` or XML `<task:annotation-driven>` present in the context?
- Is the bean retrieved/injected from the Spring container rather than manually instantiated with `new`?
- Is the method called **from outside** through the bean reference/proxy?
- Are the method/return type suitable for proxy mode? Private/final methods are not reliable places for `@Async`.
- Does `@Async("workExecutor")` match the executor bean?
- Is `Future.get()` called immediately on the request thread, causing the caller to still block?

If self-invocation is an issue, prefer extracting the async method to another bean or explicitly submitting tasks via `AsyncTaskExecutor`; do not just increase pool size to fix a broken call path.

## 11. Is the Proxy Future Guaranteed to Be the Same Object or Same Implementation as the Target?

**No.** The target Future object may be a `CompletableFuture.completedFuture(...)`; the proxy Future is created according to the declared return type and actual executor.

In Spring Framework 6.2:

- If the method declares `Future<T>`, Spring may use `AsyncTaskExecutor.submit(...)` to create the task's Future.
- If the method declares `CompletableFuture<T>`, Spring may use `AsyncTaskExecutor.submitCompletable(...)` to provide an appropriate handle to the caller.
- Inside the worker, the advice extracts the value/exception from the target Future and then completes the task.

Therefore, never assume `targetFuture == proxyFuture`, never make business logic depend on the concrete runtime class of the Future, and never cast `Future<T>` to `CompletableFuture<T>` when the method only promises `Future<T>`. Rely solely on the declared public type contract.

**Version-change note:** the exact bridge structure and wrapper classes are Spring implementation details; invariants should rely on the `@Async` contract and execution outcomes, not internal class names.

## 12. Timeouts and Cancellation Across the Two Future Layers

Suppose the caller has:

```java
CompletableFuture<String> callerFuture = service.calculateAsync();
```

The caller can use `get(2, TimeUnit.SECONDS)`, `orTimeout(...)`, `cancel(...)`, or error-handling stages. However, these operations primarily affect **the handle held by the caller**. Do not assume all underlying Futures or downstream tasks will automatically be cancelled or rolled back.

Boundaries to distinguish:

- **Caller timeout:** waiting time for the result expired; does not mean the worker stopped.
- **Caller Future cancellation:** cancel state of the proxy handle; whether the worker is interrupted depends on implementation and Future type.
- **Target temporary Future cancellation:** state of the Future returned from the target; not always bidirectionally wired to the proxy Future automatically.
- **I/O/network cancellation:** may require timeouts/cancellation on the HTTP client, JDBC, socket, or external API itself.

Specifically, JDK `CompletableFuture.cancel(true)` does not guarantee interrupting the running thread just because `mayInterruptIfRunning=true`; do not rely on it as a guaranteed stop switch. For work with side effects, design idempotency, cleanup, downstream timeouts, and final state persistence.

Do not assume the temporary Future is the source of truth for a client to cancel work, because the client normally **does not hold** that temporary Future in proxy mode.

## 13. Caller-Side Result Handling Snippets

The caller can choose blocking `get` with timeout:

```java
try {
    String value = result.get(3, TimeUnit.SECONDS);
    apply(value);
} catch (ExecutionException ex) {
    Throwable original = ex.getCause();
    // Record business error.
} catch (TimeoutException ex) {
    // Task might still be running; decide timeout/cancel/retry.
} catch (InterruptedException ex) {
    Thread.currentThread().interrupt();
    // Let caller terminate per interruption policy.
}
```

This is a fragment; `result` is `Future<String>`, `apply` is a business processing function, and appropriate `java.util.concurrent` imports must be present.

If the method declares `CompletableFuture<String>`, you can choose:

```java
service.calculateAsync()
       .thenApply(String::trim)
       .thenAccept(value -> save(value))
       .exceptionally(ex -> {
           logError(ex);
           return null;
       });
```

This is a fragment, requiring `save(...)` and `logError(...)`. With `CompletableFuture`, `exceptionally` at the end receives `Throwable` and must return a value matching the stage type at that point (here the stage from `thenAccept` is `Void`, so `return null` fits). Do not assume callbacks automatically use the original `@Async` executor; stages without the `Async` suffix may run on the thread completing the future.

If you want the caller not to block, prefer composition/callbacks over calling `get()` right after the invocation.

## 14. Observing Threads, Errors, and Consistency

After going through the proxy, target code runs on an executor worker (with an async pool configured as in this lesson). Therefore:

- **ThreadLocal, MDC, SecurityContext:** are not copied from the caller by default. Proper propagation is required for correlation/logging/security if business requirements demand it.
- **Transactions:** a transaction bound to the caller thread does not automatically transfer intact to the worker. If the task performs DB work, configure an explicit transaction boundary on the worker.
- **Side effects:** when the caller receives the proxy Future, the work may not have run yet. Never respond "processed successfully" merely because no exception occurred at method invocation time.
- **Rejection:** the executor has a queue and max workers; overload can throw rejection errors on the submission path.
- **Shutdown:** an in-memory executor has no durability. If the process dies before the Future finishes, there is no automatic replay capability.
- **Error reporting:** for methods returning `Future`, the caller needs to read the result or have another place observe completion. For `void` async methods, use `AsyncUncaughtExceptionHandler` or appropriate logging/metrics mechanisms.

These issues belong to the lifecycle of **the proxy Future and the real task**; they are not solved merely by the target returning `completedFuture(value)`.

## 15. Why Does the Example Use a Separate Signals Bean Instead of Proxy Fields?

Spring AOP can expose a **proxy object** distinct from the **target object**. With class-based proxies, reading a field directly through the proxy reference is not equivalent to a getter method being advised/delegated to the target.

Snippet illustrating the hazard:

```java
WorkService service = context.getBean(WorkService.class);
// Do not assume service.someField is the same instance field
// that the target's method reads/writes when invoked through the proxy.
```

In this lesson's experiment, we want to observe both the target Future and the proxy Future. Therefore `Signals` is a **separate bean**:

- The target receives `Signals` via constructor injection.
- The caller retrieves **the same Signals bean** from the ApplicationContext.
- The `CountDownLatch` and `AtomicReference` instances live on the deliberately shared Signals object.
- The caller does not have to read proxy fields to infer target state.

This is a clean testing technique enabling controlled comparison of identity and timing. In real business code, avoid having a singleton `Signals` hold state for many requests; attach task IDs, per-request state, and ensure thread-safety.

## 16. Common Mistakes

| Misconception/bad design | Consequence | Correct understanding or fix |
| --- | --- | --- |
| Seeing `completedFuture(value)` in target and thinking the call isn't async | Confusing temporary Future with proxy Future | Async is decided at the proxy boundary; target only hands over the value |
| Thinking target Future and caller Future are always the same object | Wrong identity and completion timing assumptions | Compare by contract/results, not object identity |
| Target returning `new CompletableFuture<>()` that nobody completes | Worker may wait forever and caller Future stays pending | Return completedFuture after computation or complete the future with a clear strategy |
| Wrapping `supplyAsync(...)` inside every `@Async` method | Double scheduling, worker waiting on child Future | Do not add a second async layer unless needed |
| Waiting on a child Future on the same single-worker pool | Starvation deadlock | Avoid nested blocking, use proper composition |
| Casting proxy `Future<T>` to `CompletableFuture<T>` when method only promises Future | Possible `ClassCastException` | Declare `CompletableFuture<T>` in the API if chaining is needed |
| Calling `this.asyncMethod()` and comparing Futures | Bypasses advice; target's Future may be returned directly | Call through another Spring-managed bean |
| Using `isDone()` as the sole test check | Fast tasks can finish before inspection | Use latches/instrumentation to prove ordering |
| Thinking `get(timeout)` automatically cancels the task | Worker may keep running | Make explicit cancel/cleanup decisions |
| Thinking `cancel(true)` definitely stops all work | Many tasks/CFs do not support interrupts as expected | Design cooperative cancellation and downstream timeouts |
| Ignoring `ExecutionException.getCause()` | Hides actual error from target | Unwrap exception cause, log appropriately |
| Treating successful submission as completed processing | Task might still be in queue | Track proxy Future, metrics, and business status |
| Reading Spring proxy fields as target fields | Broken/hanging tests due to mismatched state | Use a separate state bean or proper getter API |
| Using in-memory Futures instead of durable job tracking | No replay across restarts | Use outbox/broker/status store when required |

## 17. Self-Check Questions

**Question 1.** An `@Async` method returns `CompletableFuture.completedFuture("done")`. Can the caller receive a Future with `isDone() == false`?

Yes. The target's temporary Future is already completed, while the proxy task may not have reached that point or finished yet. The two Futures have different roles and completion times.

**Question 2.** If a method declares `Future<Integer>`, should you cast the proxy Future to `CompletableFuture<Integer>` to use `thenApply`?

No. The public contract only promises `Future<Integer>`; the concrete runtime object is decided by the executor/proxy. Declare `CompletableFuture<Integer>` upfront if composition is needed.

**Question 3.** Why must the target still return a Future despite having an async interceptor?

Because the Java method must honor its declared return signature. The temporary Future is how the target hands off the value or error for Spring infrastructure to transfer to the proxy-provided Future.

**Question 4.** If the target returns an incomplete `CompletableFuture` from another executor, what can happen?

The bridge on the Spring worker may have to wait for the target Future to complete. This consumes a worker, especially risking starvation when tasks depend on each other in a small pool.

**Question 5.** Does a timeout on the proxy Future guarantee the temporary Future is cancelled?

No. A timeout when calling `get(timeout)` only applies to the caller's wait time. Cancellation and propagation to the target/downstream depend on design and implementation; it is not bidirectional by default.

**Question 6.** If a proxy bean exists yet `this.asyncMethod()` runs synchronously, does that contradict the two-Future model?

No. Self-invocation bypasses the proxy, so there is no new caller-facing proxy Future for that call. It is a different call path.

**Question 7.** What should a test use to prove the two Futures have different states?

Create a completed temporary Future inside the worker, use a latch to hold the target before returning, obtain the proxy Future from the caller, then compare state/identity and release the latch. Do not use arbitrary sleep durations.

## 18. Checklist When Designing Result-Returning @Async Methods

- **Signature:** `Future<T>` or `CompletableFuture<T>`? Do we actually need to receive/chain results?
- **Target method:** compute work on the worker and return an appropriate temporary Future, usually `CompletableFuture.completedFuture(value)`.
- **Caller:** hold the proxy's Future and use it to retrieve results/exceptions; do not expect object identity equality with the temporary Future.
- **Proxy boundary:** is `@EnableAsync` enabled, is the bean Spring-managed, and is there no self-invocation?
- **No nested blocking:** does the target accidentally submit another task to the same pool and wait on the child Future?
- **Timeout/cancel:** are timeouts set at both the caller and real I/O, and do we understand cancellation semantics at each layer?
- **Exceptions:** do we distinguish errors inside target/temporary Future from `TaskRejectedException` at submission?
- **Operations:** do we monitor queue wait, execution time, active workers, rejections, errors, and shutdown?
- **Context:** are transactions/MDC/security and input data handled safely on the worker thread?
- **Durability:** if the task must survive restarts, are appropriate state persistence/durable queues used?

## 19. Conclusion

In Spring `@Async`, **the temporary Future returned by the target method** and **the Future returned to the caller by the Spring proxy** do not share the same responsibility:

1. The temporary Future honors the method signature and passes the value or error once the worker finishes computing.
2. The proxy Future is the result of the asynchronous invocation at the AOP/executor boundary; the caller uses it to wait, inspect status, handle errors, and compose stages.
3. They may be different objects with different completion times; a completed temporary Future **does not mean** the proxy Future is already completed.
4. Returning an incomplete temporary Future can force the worker to wait for the result; avoid double scheduling and nested blocking unless genuinely required.
5. The entire bridge only happens if the call is intercepted by Spring async advice; self-invocation in proxy mode is a separate case.
