# Correlation IDs and Tracking Late-Arriving Results

In messaging systems, a request may traverse multiple services, split into multiple branches, and receive replies in arbitrary order. A reply may arrive after a timeout, after a group has already been aggregated, or after the application has resent the request. Relying solely on message arrival order or per-message auto-generated IDs makes it easy to mismatch results, process duplicates, or reopen an already completed group.

A Correlation ID solves the problem of identifying which messages belong to the same business operation. Tracking late-arriving results adds state and lifecycle policies so the application knows what to do when a reply arrives after the wait deadline.

This lesson focuses on Spring Messaging and Spring Integration. Spring Messaging provides the Message and headers abstractions; Spring Integration adds correlation headers, splitters, aggregators, message stores, and group handling strategies.

## 1. Distinguishing Types of IDs

Do not use one type of ID for every purpose. The following values have distinct lifecycles and meanings:

| Value | Meaning | When to use |
|---|---|---|
| Message ID | Identifies a single Message instance | Logging, debugging a specific message |
| Correlation ID | Identifies a request or a group of related messages | Matching requests with replies, gathering multi-branch results |
| Sequence number | Position of a message within a group | Ordering or identifying missing elements |
| Sequence size | Expected total number of elements in a group | Determining when a group is complete for release |
| Operation ID | Identifies a business operation across retries | Idempotency, reconciliation |
| Trace ID | Identifies a distributed observability trace | Tracing spans across services |

In Spring, MessageHeaders.ID is a UUID generated by the framework for each Message. When a message is recreated or transformed into another instance, its ID may change. Therefore, do not use MessageHeaders.ID as the request/reply matching key across multiple hops.

Spring Integration defines the CORRELATION_ID header in IntegrationMessageHeaderAccessor. This header's value is an Object used to link two or more messages. SEQUENCE_NUMBER and SEQUENCE_SIZE add group position and size. SEQUENCE_DETAILS stores a stack of correlation details for nested splitters/aggregators.

At broker or service boundaries, use a stable value that is easy to transmit and observe, such as a String UUID. Key values must have stable equals() and hashCode(); never use mutable objects as correlation keys. Do not embed personal data or secrets into IDs.

## 2. Creating and Propagating Correlation IDs

Generate the correlation ID when starting an operation that needs tracking. Register the pending state before sending the request to avoid a race where a very fast reply arrives before the application creates its pending entry.

Example creating a Spring Message:

~~~java
import java.util.UUID;

import org.springframework.integration.IntegrationMessageHeaderAccessor;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

String correlationId = UUID.randomUUID().toString();

Message<String> request = MessageBuilder.withPayload("calculate-total")
        .setHeader(IntegrationMessageHeaderAccessor.CORRELATION_ID, correlationId)
        .build();
~~~

When creating a reply, keep the request's correlation ID:

~~~java
Message<String> reply = MessageBuilder.withPayload("125000")
        .setHeader(IntegrationMessageHeaderAccessor.CORRELATION_ID, correlationId)
        .build();
~~~

If transforming an existing Message, MessageBuilder.fromMessage(request) helps retain necessary headers:

~~~java
Message<String> reply = MessageBuilder.fromMessage(request)
        .setPayload("125000")
        .build();
~~~

MessageHeaders is a read-only structure. Do not mutate it directly with put(), remove(), or clear(); create a new Message via MessageBuilder instead. When an endpoint builds output solely from a payload, Spring Integration normally forwards inbound headers. If transformer code returns a complete Message, that code is responsible for providing headers to keep. Options like not-propagated-headers can also explicitly drop headers from the path.

For messages crossing brokers or other protocols, check whether the adapter maps correlation ID into wire headers/properties and returns it on the reply. Having a header in an internal Message does not guarantee the broker preserves that header end-to-end automatically.

## 3. Two Common Correlation Patterns

### 3.1. One-to-One Request/Reply

Each request has its own correlation ID. A pending table stores the ID, future/callback, deadline, and status. When a reply arrives, the consumer looks up the exact ID, completes the future, and clears the pending entry.

~~~text
Client                 Message flow                 Reply handler
  |                         |                            |
  |-- request, id=R17 ----->|--------------------------->|
  |                         |                            |
  |                         |<----- reply, id=R17 --------|
  |                         |                            |
  |<--------------- complete future for R17 ------------|
~~~

If the ID is not found in the pending registry, the reply may be a late result, a duplicate delivery, or a message belonging to a request this instance does not manage. Do not assume all of these cases are the same error.

### 3.2. Fan-out/Fan-in with Aggregator

One request is split into multiple child messages. The child messages share the group's correlation ID; each part has its own sequence number and usually the same sequence size. The Aggregator stores them in a MessageGroupStore and uses a ReleaseStrategy to decide when the group is ready to aggregate.

Spring Integration groups messages by IntegrationMessageHeaderAccessor.CORRELATION_ID by default. The default ReleaseStrategy relies on SEQUENCE_SIZE and sequence numbers. Splitters automatically add the required sequence headers. If fan-out is built using a publish-subscribe channel or recipient list router, enable apply-sequence to attach CORRELATION_ID, SEQUENCE_NUMBER, and SEQUENCE_SIZE.

If branch count varies by data or a branch is dropped by a filter, a strategy waiting for the full SEQUENCE_SIZE may never release. In that case, use a custom ReleaseStrategy, or emit a compensating message indicating a branch was skipped. Do not simply increase timeouts to mask a group that can never complete.

## 4. Retries: Separating Correlation ID from Operation ID

A retry can create multiple executions for the same business operation. Reusing the previous attempt's correlation ID risks matching a late reply from an old attempt to a new attempt.

Separate the two concepts:

- Operation ID stays constant across retries, allowing downstream to recognize the same business operation and enforce idempotency.
- A fresh Correlation ID is generated for each attempt, ensuring replies match the exact send that produced them.

Example:

| Send | Operation ID | Correlation ID | Outcome |
|---|---|---|---|
| Attempt 1 | order-842 | req-a1 | Timeout |
| Attempt 2 | order-842 | req-a2 | Successful reply |
| Late reply attempt 1 | order-842 | req-a1 | Record late; do not complete req-a2 |

If the system requires keeping the same correlation ID across retries, add an attempt number and a rule for picking the winning response. Never let two attempts race to complete the same future without an explicit policy.

## 5. State Model and Handling Late Replies

A client timeout only means the client stopped waiting within the configured deadline. It does not prove the downstream service stopped processing. Replies can still arrive after timeout due to queues, retries, slow networks, or congested consumers.

A request registry can use these states:

- PENDING: registered and waiting for a reply.
- COMPLETED: valid reply received.
- TIMED_OUT: wait deadline expired.
- CANCELLED: application intentionally canceled the operation.
- FAILED: operation ended with a non-retryable local error.

State transitions must be atomic. Reply handling and timeout may run on different threads; only one side may transition PENDING to a terminal state. Use compareAndSet or remove(key, expectedValue) so only one side wins the race.

When a reply arrives after timeout:

1. Look up correlation ID in the pending registry.
2. If the request is still PENDING, accept the reply, transition to COMPLETED, and cancel the timeout task.
3. If the request is already TIMED_OUT, record a late reply and apply the chosen policy.
4. If the request is already COMPLETED, treat it as a duplicate reply.
5. If there is no pending or terminal record, classify as an unknown reply.

Policy for late replies depends on business needs: ignore with logs/metrics, route to a quarantine channel, store for reconciliation, or trigger a reconciliation/compensation flow. Never automatically re-execute side effects just because a reply arrived late. If the outcome carries financial or business state significance, persist it for human or automated reconciliation.

Keep a terminal record (tombstone) for a period after a request completes or times out. This record distinguishes late replies from unknown-origin replies and duplicates. The TTL should exceed the maximum expected delay plus the retry/replay window. Once the TTL expires, an ultra-late reply will be classified as unknown; track metrics to detect this condition.

Do not reuse correlation IDs while the terminal record is still active. If an ID is reused too early, an old reply can match a brand-new request.

## 6. Group Tracking in Spring Integration Aggregator

Aggregator is stateful and needs a MessageGroupStore to hold messages while waiting for group completion. Distinguish two ending moments:

- Normal completion: ReleaseStrategy decides the group is ready. By default, expire-groups-upon-completion is false; an empty group is retained to recognize and discard late messages sharing the same correlation ID.
- Timeout expiration: group-timeout or MessageGroupStoreReaper forces the group to end. By default, expire-groups-upon-timeout is true; the group is deleted completely and a late message can start a new group.

To retain metadata of timed-out groups and discard late replies instead of creating a new group, configure expire-groups-upon-timeout="false". The XML configuration example below assumes the corresponding Spring Integration channels and namespaces are declared:

~~~xml
<int:aggregator input-channel="results"
                output-channel="completed"
                discard-channel="late-or-discarded"
                group-timeout="30000"
                expire-groups-upon-completion="false"
                expire-groups-upon-timeout="false"
                send-partial-result-on-expiry="false"/>
~~~

In this example, group-timeout is 30 seconds measured from the last message arriving in the group. On timeout, ReleaseStrategy is queried once more. If still not eligible, the group expires. With send-partial-result-on-expiry="false", remaining messages of the expired group go to discard-channel rather than emitting a partial aggregated result. Messages arriving after a group completed while metadata still exists can also be routed to discard-channel.

If you want to return partial results on timeout, set send-partial-result-on-expiry="true" and design consumers to recognize incomplete results explicitly. Never interpret a partial result as a complete result. With group-timeout-expression, deadlines can be computed from group creation time instead of last message arrival time. group-timeout and group-timeout-expression are mutually exclusive options.

Keeping metadata indefinitely causes MessageGroupStore to grow unbounded. Configure MessageGroupStoreReaper and empty-group-min-timeout to match the maximum window during which late replies can still arrive. Remove tombstones only after the system accepts that replies past that point will no longer be correlated automatically.

By default, MessageGroupStore is an in-memory store, suitable for simple flows but not surviving restarts. If groups must recover after an application restart, use an appropriate persistent store such as JDBC MessageStore. When multiple instances update a shared store, a shared LockRegistry is required to synchronize operations on the same correlation key. Each aggregator should have its own store/lock registry per configuration; do not arbitrarily share one MessageGroupStore across independent aggregators.

## 7. Java 17 Example: Registry Handling Replies, Timeouts, and Late Replies

The following example uses pure JDK to illustrate the request/reply part. It registers the request before sending, uses ScheduledExecutorService for timeouts, AtomicReference to resolve the race between reply and timeout, and TTL terminal records to recognize late replies. In real applications, receive() is invoked from a message listener after reading the correlation ID from reply headers.

Save as CorrelationTrackerDemo.java:

~~~java
import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.atomic.AtomicReference;

public final class CorrelationTrackerDemo {

    private enum Status { PENDING, COMPLETED, TIMED_OUT }

    private record Terminal(Status status, long expiresAtNanos) {}

    private static final class Pending {
        private final CompletableFuture<String> result = new CompletableFuture<>();
        private final AtomicReference<Status> status =
                new AtomicReference<>(Status.PENDING);
        private volatile ScheduledFuture<?> timeoutTask;

        private void cancelTimeout() {
            ScheduledFuture<?> task = timeoutTask;
            if (task != null) {
                task.cancel(false);
            }
        }
    }

    private static final class Tracker implements AutoCloseable {
        private final ConcurrentMap<String, Pending> pending =
                new ConcurrentHashMap<>();
        private final ConcurrentMap<String, Terminal> terminal =
                new ConcurrentHashMap<>();
        private final ScheduledExecutorService scheduler =
                Executors.newSingleThreadScheduledExecutor();
        private final long timeoutNanos;
        private final long tombstoneTtlNanos;

        private Tracker(Duration timeout, Duration tombstoneTtl) {
            if (timeout.isZero() || timeout.isNegative()
                    || tombstoneTtl.isZero() || tombstoneTtl.isNegative()) {
                throw new IllegalArgumentException("Durations must be positive");
            }
            this.timeoutNanos = timeout.toNanos();
            this.tombstoneTtlNanos = tombstoneTtl.toNanos();

            long cleanupPeriodMillis = Math.max(1, tombstoneTtl.toMillis() / 2);
            scheduler.scheduleAtFixedRate(
                    this::purgeExpiredTombstones,
                    cleanupPeriodMillis,
                    cleanupPeriodMillis,
                    TimeUnit.MILLISECONDS);
        }

        private synchronized CompletableFuture<String> register(String correlationId) {
            if (correlationId == null || correlationId.isBlank()) {
                throw new IllegalArgumentException("correlationId is required");
            }
            purgeExpiredTombstones();
            if (terminal.containsKey(correlationId)) {
                throw new IllegalArgumentException(
                        "correlationId is still in the retention window");
            }

            Pending request = new Pending();
            if (pending.putIfAbsent(correlationId, request) != null) {
                throw new IllegalArgumentException("correlationId is already pending");
            }

            try {
                request.timeoutTask = scheduler.schedule(
                        () -> timeout(correlationId, request),
                        timeoutNanos,
                        TimeUnit.NANOSECONDS);
            }
            catch (RuntimeException ex) {
                pending.remove(correlationId, request);
                throw ex;
            }
            return request.result;
        }

        private void timeout(String correlationId, Pending request) {
            if (request.status.compareAndSet(Status.PENDING, Status.TIMED_OUT)) {
                remember(correlationId, Status.TIMED_OUT);
                pending.remove(correlationId, request);
                request.result.completeExceptionally(
                        new TimeoutException("Timed out: " + correlationId));
            }
        }

        private void receive(String correlationId, String payload) {
            if (correlationId == null || correlationId.isBlank()) {
                System.out.println("reply without correlation ID ignored");
                return;
            }

            Pending request = pending.get(correlationId);
            if (request != null) {
                if (request.status.compareAndSet(Status.PENDING, Status.COMPLETED)) {
                    remember(correlationId, Status.COMPLETED);
                    pending.remove(correlationId, request);
                    request.cancelTimeout();
                    request.result.complete(payload);
                    return;
                }
                Status current = request.status.get();
                if (current == Status.TIMED_OUT) {
                    System.out.println("late reply ignored: " + correlationId);
                    return;
                }
                if (current == Status.COMPLETED) {
                    System.out.println("duplicate reply ignored: " + correlationId);
                    return;
                }
            }

            Terminal marker = terminal.get(correlationId);
            if (marker != null
                    && System.nanoTime() - marker.expiresAtNanos() < 0) {
                if (marker.status() == Status.TIMED_OUT) {
                    System.out.println("late reply ignored: " + correlationId);
                }
                else {
                    System.out.println("duplicate reply ignored: " + correlationId);
                }
            }
            else {
                if (marker != null) {
                    terminal.remove(correlationId, marker);
                }
                System.out.println("unknown reply ignored: " + correlationId);
            }
        }

        private synchronized void remember(String correlationId, Status status) {
            terminal.put(correlationId,
                    new Terminal(status, System.nanoTime() + tombstoneTtlNanos));
        }

        private void purgeExpiredTombstones() {
            long now = System.nanoTime();
            terminal.entrySet().removeIf(
                    entry -> now - entry.getValue().expiresAtNanos() >= 0);
        }

        @Override
        public void close() {
            scheduler.shutdownNow();
        }
    }

    public static void main(String[] args) throws Exception {
        try (Tracker tracker = new Tracker(
                Duration.ofMillis(100), Duration.ofSeconds(5))) {

            CompletableFuture<String> fast = tracker.register("req-1");
            tracker.receive("req-1", "OK");
            System.out.println("reply req-1: " + fast.get(1, TimeUnit.SECONDS));

            CompletableFuture<String> slow = tracker.register("req-2");
            try {
                slow.get(1, TimeUnit.SECONDS);
            }
            catch (ExecutionException ex) {
                if (ex.getCause() instanceof TimeoutException) {
                    System.out.println("request req-2 timed out");
                }
                else {
                    throw ex;
                }
            }

            tracker.receive("req-2", "too late");
        }
    }
}
~~~

Compile and run with Java 17+:

~~~bash
javac --release 17 CorrelationTrackerDemo.java
java CorrelationTrackerDemo
~~~

Exact stdout:

~~~text
reply req-1: OK
request req-2 timed out
late reply ignored: req-2
~~~

This example illustrates the policy of ignoring late replies. In production, replace System.out with a logger and metrics; route business-critical late replies to storage/reconciliation if needed. The terminal map in the demo uses a 5-second TTL to illustrate bounding memory. In the demo, `register()` and `remember()` synchronize on the same Tracker so tombstone checking and adding a pending entry do not race with recording a terminal status. Real TTLs should be chosen from maximum latency, retry policies, and broker retention. An in-memory registry works only inside one JVM; if a request may be sent on instance A while the reply arrives at instance B, a shared pending store/response router or reply routing back to the originating instance is needed.

## 8. Observation and Operations

Every request/reply log should contain correlation ID, operation ID, attempt, message ID, sequence number if present, status, and wait time. Use the same correlation ID across service logs to trace the full journey of an operation. Trace ID serves distributed tracing; correlation ID serves business and message linking. The two values can be linked in logs, yet should not blindly replace each other.

Useful metrics:

- Number of PENDING requests and age of the oldest request.
- Timeout rate by destination/operation.
- Counts of late replies, duplicate replies, and unknown replies.
- Latency from send to reply receipt, including p50/p95/p99 percentiles.
- Waiting message groups, expired groups, and MessageGroupStore size.
- Partial results, discards, and reconciliation successes/failures.

If late replies increase, check queue depth, consumer lag, retries, downstream processing time, configured timeouts, and network transit time. Do not simply raise timeouts without finding the root cause; overly long timeouts keep many pending requests and message groups in memory.

## 9. Common Mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Using MessageHeaders.ID as correlation key | ID changes when a new Message is created; reply fails to match original request | Generate a separate correlation ID and propagate it across all hops |
| Sharing one correlation ID across independent requests | Reply of one request gets matched to another | Generate a distinct ID per request/attempt |
| Retrying while reusing ID without an attempt policy | Late reply from old attempt can complete new attempt | Fresh ID per attempt; stable operation ID for idempotency |
| Deleting pending entry immediately on timeout without keeping a terminal record | Cannot distinguish late replies from unknown replies | Retain tombstones for a reasonable delay window |
| Letting timed-out groups be deleted completely | Late reply can start a new group that never completes | Consider expire-groups-upon-timeout=false |
| Keeping aggregator metadata forever | MessageGroupStore grows unbounded | Use reaper and empty-group-min-timeout |
| Waiting for full sequence size when a branch was filtered out | Aggregator never releases normally | Custom ReleaseStrategy or compensation message |
| Logging payloads without correlation ID | Hard to trace out-of-order messages | Log correlation ID, attempt, status, and timestamps |
| Treating timeout as downstream cancellation | Side effects can still happen after timeout | Design separate cancel protocols or reconciliation |

## 10. Design Checklist

- Generate a unique correlation ID before sending a request and register pending state prior to sending.
- Use one correlation ID for exactly one request or one fan-in group; never reuse across independent operations.
- Keep operation ID stable across retries to support idempotency; use separate attempt/correlation IDs if individual attempts must be distinguished.
- Ensure every response, error reply, and child message carries the right correlation ID.
- If using splitter/aggregator, verify sequence number, sequence size, apply-sequence, and release strategy.
- Define post-timeout outcome rules clearly: discard, quarantine, store for reconciliation, or compensate.
- Guarantee only one thread wins the race between reply and timeout.
- Retain terminal records long enough to identify late/duplicate replies, then prune with bounds.
- Use persistent/shared state when requests and replies can traverse multiple instances or must survive restarts.
- Track timeouts, late, duplicate, unknown replies, and waiting groups via metrics.
- Verify header propagation and broker/transport header mapping along the real message path.
