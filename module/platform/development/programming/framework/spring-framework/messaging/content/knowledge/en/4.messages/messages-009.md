# Comparing Spring Message with jakarta.jms.Message

In the Java ecosystem, the word "message" can refer to a data envelope inside an application or a message sent through a messaging system. Two common types are **org.springframework.messaging.Message<T>** from Spring Messaging and **jakarta.jms.Message** from Jakarta Messaging (JMS).

Both describe data accompanied by metadata, yet they serve different layers:

- **Spring Message<T>** is Spring's general-purpose message abstraction. It carries a Java-typed payload and headers for components inside an application to exchange with one another.
- **jakarta.jms.Message** is the message type of the JMS API. It represents a message sent/received through a JMS provider, such as a Jakarta Messaging-compatible broker, with a body, JMS headers, properties, and JMS delivery rules.

A Spring Message is not a JMS Message. When an application needs to use JMS, Spring JMS provides converters and adapters to convert between the two models.

## 1. Two Interfaces and Two Purposes

### Spring Messaging Message<T>

The **org.springframework.messaging.Message<T>** interface has two main parts:

- **getPayload()** returns the primary data with generic type T.
- **getHeaders()** returns metadata as **MessageHeaders**.

Example:

~~~java
Message<String> message = MessageBuilder
        .withPayload("Order created")
        .setHeader("eventType", "OrderCreated")
        .setHeader("correlationId", "checkout-001")
        .build();
~~~

The message above exists as an object in the JVM. It can be passed through a **MessageChannel**, handled by a **MessageHandler**, flow through Spring Integration, or be forwarded by an adapter to another infrastructure.

The interface itself does not specify how to send messages over the network, store messages on a broker, guarantee delivery, retry, or acknowledge consumption. Those behaviors belong to the channel, adapter, broker, and integration layer in use.

### Jakarta Messaging Message

The **jakarta.jms.Message** interface belongs to the Jakarta Messaging API. It describes a message in the JMS model, consisting of:

- Standard JMS headers, such as **JMSMessageID**, **JMSTimestamp**, **JMSCorrelationID**, **JMSReplyTo**, and **JMSDestination**.
- User-defined properties, such as **eventType**, **schemaVersion**, or **tenantId**.
- Body, which can be accessed via the body API or specialized sub-interfaces.

JMS has common message types:

| Message type | Body content |
|---|---|
| **TextMessage** | Text, commonly used for JSON, XML, or plain text. |
| **BytesMessage** | Binary data. |
| **MapMessage** | A set of name/value pairs supported by JMS. |
| **StreamMessage** | A sequence of values read/written in order. |
| **ObjectMessage** | A Java object serialized per the JMS mechanism. |
| **Message** | A general message, possibly without an application body. |

Example of creating a **TextMessage** using a JMS Session:

~~~java
TextMessage message = session.createTextMessage(
        "{\"orderId\":\"ORD-1001\",\"total\":125.50}"
);
message.setStringProperty("eventType", "OrderCreated");
message.setJMSCorrelationID("checkout-001");
~~~

This snippet requires a **jakarta.jms.Session** created from a **ConnectionFactory**; it illustrates how to create a message and attach metadata. Sending the message also requires a producer or **JMSContext/JMSProducer** depending on how the API is used.

## 2. Structural Comparison: Payload/Headers vs. Body/Headers/Properties

| Aspect | Spring **Message<T>** | Jakarta **Message** |
|---|---|---|
| Primary data | Payload T, retrieved via **getPayload()**. | Body, retrieved via the body API or a sub-interface such as **TextMessage**. |
| Metadata | **MessageHeaders**, a Spring header map. | Standard JMS headers and user-defined properties. |
| Data types | Generic T enables compile-time type checking in Java code. | Non-generic interface; body and properties follow JMS data types. |
| Identifier | **id** header generated by Spring if absent. | **JMSMessageID** usually assigned by the provider upon sending. |
| Timestamp | Spring's **timestamp** header records message creation time in the application. | **JMSTimestamp** usually assigned by the provider when sending the message. |
| Destination | No universal destination in core Message; channel or adapter determines the path. | **JMSDestination** describes the JMS destination of the message. |
| Reply | Can use the **replyChannel** header in an appropriate Spring flow. | Uses **JMSReplyTo** with a JMS Destination. |
| Correlation | Can use an application-defined header or another module's abstraction. | Has the standard **JMSCorrelationID** header. |
| Delivery | Does not define broker acknowledgment or delivery mode. | Integrates with JMS session, producer, consumer, acknowledgment mode, and delivery metadata. |
| Purpose | Exchanging messages across Spring abstractions. | Exchanging messages under the JMS protocol/API between application and provider. |

### Payload and body are not the same kind of contract

Spring Message<T> holds the payload as a Java object. For example, the payload can be an **OrderCreated** record. When the message passes through a channel within the same JVM, the consumer can receive that object without serialization.

A JMS message is designed to be sent through a provider. The body must conform to a JMS-supported message form or be converted into a form that provider and consumer can exchange. With JSON, the body is usually a string in **TextMessage** or bytes in **BytesMessage**.

Spring's generic T is not automatically transmitted as a schema on the broker. If the payload is **OrderCreated**, a consumer in another process needs to know how to deserialize JSON/bytes into the corresponding data type.

### Spring headers vs. JMS properties

**MessageHeaders** can contain object metadata according to Spring conventions. Common headers include **id**, **timestamp**, **contentType**, **replyChannel**, and **errorChannel**; the application can also add custom headers.

JMS separates metadata into two groups:

- **JMS headers** are standard fields defined by the API/provider, such as **JMSCorrelationID**, **JMSReplyTo**, **JMSDestination**, **JMSDeliveryMode**, **JMSPriority**, **JMSExpiration**, and **JMSRedelivered**.
- **JMS properties** are application-named metadata. Property values must belong to JMS-supported types such as boolean, byte, short, int, long, float, double, or String. You cannot arbitrarily put any Java object into a property the way you can put an object into Spring's header map.

Example:

~~~java
jmsMessage.setStringProperty("eventType", "OrderCreated");
jmsMessage.setIntProperty("schemaVersion", 2);
jmsMessage.setBooleanProperty("requiresAudit", true);
~~~

If metadata is a complex object, put it in the body or serialize it to a string according to an agreed contract.

## 3. Differences in Lifecycle and Delivery Responsibilities

This is an important distinction when choosing an abstraction.

### Lifecycle of a Spring Message

A Spring Message is a message object in the Spring programming model. Once created, the message is usually treated as an immutable envelope: if you need to change the payload or headers, create a new message using **MessageBuilder** or an appropriate accessor.

A processing flow can take place in memory:

~~~text
MessageBuilder
      |
      v
Message<T>
      |
      v
MessageChannel
      |
      v
MessageHandler
~~~

A message can be held in a channel's internal queue, yet queueing and dispatch behavior depend on the channel implementation. Core Message does not by itself guarantee that the message has been durably stored or that the consumer processed it successfully.

### Lifecycle of a JMS Message

A JMS message passes through the components of the API/provider:

~~~text
Producer
   |
   | send(message)
   v
JMS Provider / Broker
   |
   | deliver
   v
Consumer
   |
   | process + acknowledge
   v
Provider updates delivery status
~~~

The provider and JMS configuration determine many details: which destination the message is sent to, persistent vs. non-persistent delivery mode, priority, expiration, redelivery, and transactions.

JMS has acknowledgment modes and transacted sessions. **jakarta.jms.Message** also has an **acknowledge()** method in **CLIENT_ACKNOWLEDGE** mode; acknowledgment has scope and behavior according to the session acknowledgment mode. With other modes, the provider/session manages acknowledgment according to the JMS contract. Therefore, do not infer that calling **getBody()** or reading a message means the message has been acknowledged.

Spring Message<T> has no **acknowledge()** method. When an application uses a Spring JMS listener, delivery acknowledgment still depends on listener container configuration, session transactions, and the provider; the Spring Message object created for the processing layer does not replace JMS delivery rules.

### Who assigns ID and timestamp?

Fields with similar names do not necessarily share the same origin:

- Spring's **id** and **timestamp** headers are generated on the application side when building the message, if the default generation mechanism is enabled.
- JMS **JMSMessageID** and **JMSTimestamp** are usually assigned by the provider upon sending. A provider can be configured to disable timestamp generation; a message before being sent does not necessarily have these values yet.

Therefore, a Spring Message's timestamp reflects when the envelope was created in the application; **JMSTimestamp** reflects the send time recorded by the provider. If a business event time is needed, put it in the payload or metadata per a separate contract.

## 4. Destination, Reply, and Correlation

Spring Messaging and JMS represent addressing differently.

### Spring channel

**MessageChannel** is the abstraction that receives messages on the Spring side. Producers send through a channel via **send(message)**. Channel names and how they connect to handlers or adapters are determined by application configuration.

Core Spring Message does not require a header named **destination**. With Spring Integration, routing can rely on channels, routers, or application-conventional headers. With other adapters, addresses can be mapped from external configuration.

### JMS destination

JMS uses **Destination**, usually a **Queue** or **Topic**. Producers send messages to a destination; consumers subscribe to receive from the corresponding destination.

Some standard fields:

- **JMSDestination**: the destination the provider associates with the message.
- **JMSReplyTo**: the destination for the consumer to send a reply to.
- **JMSCorrelationID**: identifier linking a request and reply or a group of related messages.

Example of creating a reply destination:

~~~java
Queue replyQueue = session.createQueue("orders.reply");
TextMessage request = session.createTextMessage("{\"orderId\":\"ORD-1001\"}");
request.setJMSReplyTo(replyQueue);
request.setJMSCorrelationID("checkout-001");
~~~

This snippet illustrates JMS fields. The Queue created here is a destination object by name; whether the queue is pre-provisioned or auto-created by the broker depends on the provider and environment.

### Do not map header names mechanically

Spring's **replyChannel** and JMS's **JMSReplyTo** can both appear in request/reply flows, yet they are not the same kind of object. One may represent an internal Spring channel; the other is a JMS Destination.

Similarly, an application-set **correlationId** header in Spring does not automatically become **JMSCorrelationID**. The adapter or header mapper must explicitly define how to map them. If building a custom adapter, agree on names, types, and handling rules when values are missing.

## 5. Converting Between Spring Message and JMS Message

When using JMS in a Spring application, you normally do not need to manually copy each field between the two interfaces. The **Spring JMS** module provides converters to translate payloads and metadata.

Two converter abstractions should be distinguished:

- **org.springframework.messaging.converter.MessageConverter** belongs to Spring Messaging, converting between payloads/objects and Spring message forms.
- **org.springframework.jms.support.converter.MessageConverter** belongs to Spring JMS, converting between application objects and **jakarta.jms.Message**.

Spring JMS also has **MessagingMessageConverter**, an adapter bridging the two models. It converts a JMS message into a Spring Messaging Message and vice versa, using a payload converter along with a header mapper to handle body and metadata.

This can be visualized as:

~~~text
Spring Application
    |
    | Message<OrderCreated>
    v
MessagingMessageConverter
    |
    | payload converter + JMS header mapper
    v
jakarta.jms.Message
    |
    v
JMS Provider / Broker
~~~

On the receiving side, the reverse happens: Spring JMS reads the JMS message, converts the body into an appropriate payload, and maps supported headers into a Spring Message.

### Example of sending and receiving with Spring JMS

With **JmsTemplate**, an application can send an object via **convertAndSend** if an appropriate JMS MessageConverter is configured:

~~~java
jmsTemplate.convertAndSend("orders.queue", orderCreated);
~~~

On the receiving side, a listener can receive a DTO if the listener container's converter converts the body into the right type:

~~~java
@JmsListener(destination = "orders.queue")
public void handle(OrderCreated event) {
    orderService.process(event);
}
~~~

These snippets illustrate sending/receiving; they require a **ConnectionFactory**, converter configuration, destination, and appropriate broker. Without configuring a converter for JSON or DTO types, the default converter can handle simple types but does not automatically serialize arbitrary objects to JSON.

### Choosing a converter by contract

- Use a text/JSON converter when multiple services need to exchange data with a clear schema.
- Use bytes when the payload is a binary format or the application controls serialization itself.
- Use object serialization only when both sides tightly control class versions and accept the compatibility, security, and Java-coupling risks.
- Check the header mapper to know which headers are mapped between Spring and JMS; do not assume all internal headers are forwarded.

## 6. Runnable Example with Spring Message<T>

The following example creates a plain Spring Message to show payload and headers. It does not require a JMS broker, because the goal is to illustrate the Spring Messaging abstraction.

### Maven

Create the file **pom.xml**:

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>spring-message-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-messaging</artifactId>
            <version>6.1.8</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.2.0</version>
            </plugin>
        </plugins>
    </build>
</project>
~~~

### Java

Create the file **src/main/java/com/example/messaging/SpringMessageExample.java**:

~~~java
package com.example.messaging;

import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.util.MimeTypeUtils;

public class SpringMessageExample {

    public record OrderCreated(
            String orderId,
            BigDecimal total,
            Instant occurredAt
    ) {
    }

    public static void main(String[] args) {
        OrderCreated payload = new OrderCreated(
                "ORD-1001",
                new BigDecimal("125.50"),
                Instant.parse("2026-11-07T03:00:00Z")
        );

        Message<OrderCreated> message = MessageBuilder
                .withPayload(payload)
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        MimeTypeUtils.APPLICATION_JSON
                )
                .setHeader("eventType", "OrderCreated")
                .setHeader("correlationId", "checkout-001")
                .build();

        System.out.println("payloadType="
                + message.getPayload().getClass().getSimpleName());
        System.out.println("orderId=" + message.getPayload().orderId());
        System.out.println("contentType="
                + message.getHeaders().get(MessageHeaders.CONTENT_TYPE));
        System.out.println("eventType="
                + message.getHeaders().get("eventType"));
        System.out.println("correlationId="
                + message.getHeaders().get("correlationId"));
        System.out.println("idPresent="
                + (message.getHeaders().get(MessageHeaders.ID) != null));
        System.out.println("timestampPresent="
                + (message.getHeaders().get(MessageHeaders.TIMESTAMP) != null));
    }
}
~~~

Run from the directory containing **pom.xml**:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=com.example.messaging.SpringMessageExample
~~~

Output:

~~~text
payloadType=OrderCreated
orderId=ORD-1001
contentType=application/json
eventType=OrderCreated
correlationId=checkout-001
idPresent=true
timestampPresent=true
~~~

The example shows that **Message<T>** keeps the **OrderCreated** object intact as the payload. The content type header describes the intended format if the payload is converted, yet calling **MessageBuilder** does not automatically serialize the record to JSON, nor does it send the message through a broker.

## 7. When to Use Each Type?

| Need | Appropriate choice |
|---|---|
| Passing payload and metadata between Spring components in the JVM. | **org.springframework.messaging.Message<T>**. |
| Sending/receiving messages through a JMS provider or JMS-compatible broker. | **jakarta.jms.Message** with **ConnectionFactory**, producer/consumer, or Spring JMS. |
| Handling channels and handlers via Spring abstractions. | Spring Messaging and **MessageChannel**. |
| Needing queues/topics, JMS headers, properties, delivery mode, and acknowledgment. | Jakarta Messaging API and a JMS provider. |
| Wanting to use Spring abstractions while transporting over JMS. | Spring JMS converter/adapter, such as **MessagingMessageConverter**, with a listener container or **JmsTemplate**. |
| Exchanging messages across multiple languages or independent services. | Choose an explicit wire format and schema such as JSON/Avro/Protobuf; use JMS or an appropriate broker if transport is needed. |

In a Spring Boot application, you can use Spring Messaging in the internal processing layer and Spring JMS in the broker communication layer. Both message types appear in one flow, with each keeping the responsibility of its own layer.

## 8. Common Misconceptions

1. **"Spring Message<T> is the same as JMS Message."** Incorrect. One is Spring's message abstraction; the other belongs to the Jakarta Messaging API.
2. **"Spring's payload is always serialized when creating a Message."** Incorrect. **MessageBuilder** only creates an in-memory envelope. Serialization happens when a converter or adapter runs.
3. **"JMS properties can hold any Java object."** Incorrect. JMS properties only support JMS-specified data types; complex data belongs in the body or must be serialized.
4. **"Spring headers and JMS headers are the exact same set of fields."** Incorrect. Spring has its own header map; JMS has standard fields and properties with their own rules. A header mapper is needed to convert between them.
5. **"Spring Message has acknowledgment like JMS."** Incorrect. Core Spring Message does not manage acknowledgment; JMS Message has the **acknowledge()** API and acknowledgment also depends on session mode.
6. **"Spring's timestamp and JMSTimestamp have the same meaning."** Not necessarily. Spring records message creation time in the application; the JMS provider usually records send time.
7. **"replyChannel and JMSReplyTo can directly substitute for each other."** Incorrect. One is metadata for a Spring flow; the other is a JMS Destination.
8. **"Using Spring Boot means you don't need to know the JMS API."** Incorrect if the application communicates with a JMS provider. Understanding destinations, bodies, headers, properties, acknowledgment, and transactions remains essential.
9. **"Just changing javax.jms imports to jakarta.jms makes all versions compatible."** Incorrect. Spring Framework 6 and Spring Boot 3 moved to the Jakarta namespace; you must choose compatible versions of the JMS provider, API, and Spring libraries.

## 9. Key Takeaways

- **org.springframework.messaging.Message<T>** consists of a Java-typed payload and **MessageHeaders**; it is Spring's message-exchange abstraction.
- **jakarta.jms.Message** describes a message under Jakarta Messaging, with a body, JMS headers, properties, and provider delivery rules.
- Spring Message does not by itself provide a broker, delivery guarantees, or acknowledgment.
- JMS Message participates in delivery through sessions/providers; delivery mode, destination, expiration, priority, and acknowledgment belong to the JMS contract.
- Spring JMS provides converters and adapters to bridge the two models; clearly understand payload conversion and header mapping.
- When exchanging between systems, agree on a wire format and schema instead of relying on generic types or Java classes of a single process.

First determine whether a message serves internal communication within Spring or communication through a JMS provider. From there, choose the right abstraction, converter, and the layer responsible for routing, serialization, and delivery.
