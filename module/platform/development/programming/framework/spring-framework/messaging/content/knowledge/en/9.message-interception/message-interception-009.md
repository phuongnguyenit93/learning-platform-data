# Propagating Tracing Context, Identity, and Thread-Bound Data in Spring Messaging

## 1. Context in a Message Processing Flow

A request or message often carries information beyond the business payload. When an order passes through an API gateway, order service, payment service, and notification service, each step needs to know which request the message belongs to, who initiated the operation, which tenant owns the data, and which trace it is running in.

This group of information is commonly referred to collectively as **context**. In a Spring application, context can live in several places:

- **Payload:** the primary business data, such as OrderCreated or PaymentCommand.
- **Message headers:** metadata accompanying Message<T>, such as correlationId, traceId, actorId, or schemaVersion.
- **ThreadLocal:** context bound to the current thread, commonly used for logging MDC, observation, or SecurityContextHolder.
- **Reactor Context:** context bound to a subscription in a reactive pipeline, not fixed to a single thread.
- **Transport headers/properties:** metadata serialized and transmitted over HTTP, JMS, or a broker.

There is no single mechanism that automatically carries every type of context across every boundary. You must determine which context must travel with the message, which context only needs to exist for a single execution, and which context must be re-verified at the receiving service.

| Context Type | Examples | Purpose |
|---|---|---|
| Technical tracing | traceId, spanId, traceparent | Link processing steps into a single trace |
| Business correlation | correlationId, requestId, orderId | Link multiple messages belonging to the same business workflow |
| Identity and security | SecurityContext, Authentication, principal | Identify the caller and permitted actions |
| Business metadata | tenantId, locale, schemaVersion, source | Preserve context needed to process data properly |
| Execution context | MDC, Observation, ThreadLocal | Make current context readable to logging, tracing, or synchronous code |

These categories may be related, yet they do not replace one another. A Trace ID helps locate logs and spans; it does not prove a user is authorized to read an order.

## 2. Message Headers as the Explicit Metadata Channel

Spring Messaging uses Message<T> to wrap the payload and MessageHeaders. MessageHeaders is an immutable metadata structure; use MessageBuilder to create a new message when headers need to be added or replaced.

~~~java
Message<OrderCreated> message = MessageBuilder
    .withPayload(event)
    .setHeader("correlationId", "order-2026-113")
    .setHeader("traceId", "trace-abc")
    .setHeader("actorId", "user-42")
    .setHeader("schemaVersion", 2)
    .build();
~~~

Headers are suitable for small data with simple types and stable semantics between producer and consumer. Common examples:

- correlationId: identifier linking messages of a single business workflow.
- traceId: technical trace ID if the application manages propagation via its own convention.
- actorId: identifier of the principal initiating the operation, for auditing or display.
- tenantId: the tenant to which the message belongs, once verified at a trust boundary.
- locale: language or locale required by downstream processing steps.
- schemaVersion: payload schema version.
- source: component emitting the message, if the value is generated by a trusted system.

Do not place request objects, SecurityContext, Authentication, or entire sessions into headers for transmission through channels. Those objects typically lack a stable serialization contract and may carry far more sensitive data than consumers need.

### 2.1. Distinguishing Message ID, Correlation ID, and Trace ID

These three identifiers answer three different questions:

| Identifier | Question Answered | Lifecycle |
|---|---|---|
| Message ID | Which message instance is this? | One specific message |
| Correlation ID | Which business workflow/request does this message belong to? | Can be shared across many messages |
| Trace ID | Which technical operations belong to the same trace? | One distributed trace |

Spring normally generates an ID and timestamp by default for MessageHeaders. Do not use that message ID in place of a business correlation ID. If a business flow emits multiple events or a retry creates a new message, the correlation ID can stay the same while the message ID changes.

A Trace ID does not necessarily equal the correlation ID either. One business workflow may span multiple traces due to retries, background jobs, or a new request; conversely, a single trace can contain multiple messages and multiple operations.

### 2.2. Enriching Context at the Send Boundary

If the application has a verified context at the calling layer, it can attach the required fields before sending:

~~~java
Message<?> enriched = MessageBuilder
    .fromMessage(message)
    .setHeaderIfAbsent("correlationId", requestContext.correlationId())
    .setHeader("actorId", authenticatedActor.id())
    .build();

channel.send(enriched);
~~~

This snippet illustrates creating a new message. requestContext and authenticatedActor must come from a trusted application context. Do not take actorId or tenantId directly from a client-supplied header and treat it as a verified identity.

If using a ChannelInterceptor to standardize metadata, preSend runs on the send path of the channel where the interceptor is registered. The interceptor applies only to that channel; constructing a MessageBuilder on its own does not run interceptors. Keep this logic fast and deterministic, because slow checks in preSend will slow down send operations.

## 3. Propagating Tracing Context

Distributed tracing connects operations across multiple threads or services into one trace. Typically, each operation has its own span; spans link together using trace context and parent-child or link relationships.

### 3.1. Trace Context Differs from Correlation ID

Trace context holds data that lets a tracer create and link spans. Depending on the configured propagator, it may be represented via W3C Trace Context such as traceparent/tracestate or another format such as B3.

Do not hand-craft traceparent by concatenating traceId and spanId strings. The tracer must create spans, manage scopes, inject context into outgoing carriers, and extract context upon receipt. If you merely copy a traceId string into a custom header, you may be able to search logs by ID, yet fail to establish accurate span relationships.

Correlation ID remains useful at the business layer. It can be preserved across retries, events, and background jobs even when a new trace starts.

### 3.2. Micrometer Observation and Micrometer Tracing

Micrometer Observation provides an abstraction for recording an operation. When an appropriate ObservationHandler is present, an Observation can produce metrics and spans. Micrometer Tracing provides the tracer, span, baggage, and propagation APIs.

At the message boundary, sender instrumentation can inject trace context into headers/carriers before sending. The consumer extracts context from headers and creates a continuing observation/span. The exact mechanism depends on the transport or messaging integration in use.

**Spring Messaging core does not automatically create a distributed trace merely because a Message has a traceId header.** For each transport or broker, instrumentation or adapters supporting trace context injection/extraction and proper header mapping are required.

Spring Framework provides instrumentation for JMS via Micrometer when the `io.micrometer:micrometer-jakarta9` dependency is on the classpath. To enable observation for JMS sending, configure ObservationRegistry on JmsTemplate; to enable observation for processing, configure the registry on the listener container factory. When configured, the instrumentation records publish/process observations and propagates tracing context via JMS message headers.

With Spring Integration, enable observation on the corresponding channels and consumers to build a chain of spans across the flow; this is a capability of Spring Integration, not an automatic behavior of every MessageChannel in Spring Framework core.

### 3.3. Baggage: Propagating Additional Metadata in a Trace

Baggage is metadata attached to trace context that can be propagated across services. For example, you might carry a locale or a classification code needed for downstream processing, if system policy permits.

Do not put arbitrary business information into baggage. Configure only fields that are necessary and permitted for remote propagation. Avoid tokens, passwords, cookies, personal data, and information that could alter access permissions. Baggage may also appear in logs or be forwarded through multiple services; treat it as widely shared metadata.

## 4. Propagating Identity and SecurityContext

### 4.1. Actor Metadata Is Not Proof of Authentication

An actorId header can tell the consumer who initiated an operation for auditing purposes. However, a string such as `actorId=user-42` does not prove that user-42 is logged in or authorized to perform the operation.

Separate the two purposes:

- **Audit context:** which authenticated actor initiated the operation; may store actorId, source, or requestId.
- **Authorization context:** which principal is authenticated, what authorities it holds, and whether it is allowed to access a specific resource.

Do not use self-declared actorId, role, or tenantId from an external message as the basis for granting permissions. The consumer must verify identity and permissions at its own security boundary.

### 4.2. Thread-Bound SecurityContext

In Spring Security, SecurityContextHolder typically stores the SecurityContext per thread. When code runs on a new thread, the calling thread's context does not automatically appear on the new thread.

If a background task needs to run under the current identity, Spring Security provides wrappers such as:

- DelegatingSecurityContextRunnable
- DelegatingSecurityContextCallable
- DelegatingSecurityContextExecutor
- DelegatingSecurityContextExecutorService
- DelegatingSecurityContextAsyncTaskExecutor

Example using an executor wrapper:

~~~java
Executor securityAwareExecutor =
    new DelegatingSecurityContextExecutor(delegateExecutor);

securityAwareExecutor.execute(() -> {
    securedService.performOperation();
});
~~~

With a constructor that does not pass a fixed SecurityContext, the wrapper captures the current SecurityContext at task submission time, installs that context while the task runs, and clears the context after the task finishes. An explicit SecurityContext can be passed if the task must run under a designated service identity.

This is a **Spring Security** API, not Spring Framework Messaging. Choose the right executor for tasks needing SecurityContext; do not assume ContextPropagatingTaskDecorator automatically propagates every kind of SecurityContext without a corresponding ThreadLocalAccessor.

### 4.3. Across Service or Broker Boundaries

Do not send raw SecurityContext or Authentication objects inside message headers. Those objects are tied to the framework and internal authentication process, not an inter-service transport contract.

If a consumer in another service needs to authenticate the caller, use a system-supported authentication mechanism: signed credentials/tokens or secure references transmitted over a protected channel, after which the consumer verifies issuer, audience, expiry, scope/authority, and related conditions. If a message is emitted by an intermediary service, explicitly define whether the identity is the original user, the emitting service, or both; never conflate these roles.

In asynchronous event-driven systems, often the consumer only needs a verified actorId for auditing, while permission to process the event is decided by the service identity and its own policy. This avoids depending on a user login session that may have expired long ago.

## 5. ThreadLocal Does Not Automatically Follow Tasks to Another Thread

ThreadLocal stores values only on the current thread. If a producer sends a message through an executor or invokes an asynchronous task, a different worker thread will not automatically see the producer's ThreadLocal.

Do not solve this by using InheritableThreadLocal with a thread pool. Thread pools reuse workers; stale context can linger between tasks or fail to update on new submissions.

Spring provides TaskDecorator to wrap a Runnable before the executor runs it. Since Spring Framework 6.1, ContextPropagatingTaskDecorator integrates with Micrometer Context Propagation to capture and restore registered contexts.

Two components are required:

1. ThreadLocalAccessor describing how to read, set, and clear a specific ThreadLocal type.
2. ContextPropagatingTaskDecorator capturing context when a task is submitted and restoring context when the task runs.

Example of registering an accessor for a custom ThreadLocal:

~~~java
ContextRegistry.getInstance().registerThreadLocalAccessor(
    new ThreadLocalAccessor<String>() {
        @Override
        public Object key() {
            return "demo.trace-context";
        }

        @Override
        public String getValue() {
            return TRACE_CONTEXT.get();
        }

        @Override
        public void setValue(String value) {
            if (value == null) {
                TRACE_CONTEXT.remove();
            }
            else {
                TRACE_CONTEXT.set(value);
            }
        }

        @Override
        public void setValue() {
            TRACE_CONTEXT.remove();
        }
    }
);
~~~

Then attach the decorator to the executor:

~~~java
ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
executor.setCorePoolSize(4);
executor.setMaxPoolSize(8);
executor.setQueueCapacity(100);
executor.setTaskDecorator(new ContextPropagatingTaskDecorator());
executor.initialize();
~~~

When a task is submitted, contexts with registered accessors can be restored on the worker thread. The scope is closed after the task finishes to return the worker to its prior context state, preventing data leaks into the next task.

The decorator incurs overhead from capturing/restoring context. Do not enable it blindly for millions of tiny tasks without measuring cost. Register only needed accessors and ensure each accessor implements exact clear/reset logic.

### 5.1. ContextPropagatingTaskDecorator Is Not a Message Transport Mechanism

The decorator only propagates context across task/thread boundaries within the same process. It does not serialize metadata into a Message, does not send headers through a broker, and does not replace W3C Trace Context or security tokens.

Therefore, both mechanisms may be needed together:

- Message headers carry explicit metadata across messages, channels, and transports.
- TaskDecorator restores execution context such as observation or logging context when a task runs on a worker thread.

## 6. Context in Reactive Pipelines

In Reactor, a pipeline can switch threads multiple times due to publishOn, subscribeOn, or schedulers. Hence, ThreadLocal should not be treated as the primary context store for a reactive chain.

Reactor Context is tied to the subscription rather than a thread. When imperative code needs to read context from Reactor or reactive code needs to use a ThreadLocal-based library, Micrometer Context Propagation can bridge between the context types.

Spring MVC also documents Context Propagation integration when controllers return Flux or Mono: if the library is on the classpath, ThreadLocals with a registered ThreadLocalAccessor can be written into the Reactor Context. For other async scenarios, ContextSnapshot can be used directly to capture and restore.

Practical rules:

- Imperative code: use the appropriate imperative context API, such as ThreadLocal or SecurityContextHolder.
- Reactive code: use Reactor Context for subscription-scoped data.
- When crossing imperative/reactive or executor boundaries: use Context Propagation with the appropriate accessors.
- Never rely on two pieces of code happening to run on the same thread.

## 7. Bringing Context into Message Flows and Preserving the Data Contract

A message may pass through multiple channels, interceptors, handlers, and adapters. Each step must decide which metadata is retained, added, modified, or stripped.

A sample workflow:

1. At the request ingress boundary, authenticate the caller and create correlation/trace context.
2. Construct the business payload; add permitted headers such as correlationId, actorId, and schemaVersion.
3. Before dispatching through an executor, configure context propagation for necessary ThreadLocals.
4. The consumer reads payload and metadata; verifies tenant/actor if they affect permissions or data scope.
5. When sending to a broker or another service, inject trace context via the propagator and forward only allowlisted headers.
6. The consumer on the other side extracts trace context, validates credentials if needed, and creates a new context for its processing run.

Do not assume every header is preserved across every adapter. Header mappers, message converters, or protocols may support only specific data types. Check mappings in both outbound and inbound directions, especially with JMS properties, HTTP headers, or broker native headers.

For metadata not allowed to propagate onward, strip it before the message leaves the trust boundary. When building a new message, use MessageBuilder to copy headers selectively rather than copying all headers blindly.

## 8. Standalone Runnable Java 17+ Example

The example below combines two context propagation paths:

- Message headers carry traceId, correlationId, and actorId alongside the payload.
- Micrometer Context Propagation restores a ThreadLocal trace context on the worker thread of an ExecutorSubscribableChannel.

actorId in the example is audit metadata set by the server after authentication. It does not replace SecurityContext or access-control decisions.

**src/main/java/demo/ContextPropagationDemo.java**

~~~java
package demo;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicReference;

import io.micrometer.context.ContextRegistry;
import io.micrometer.context.ThreadLocalAccessor;
import org.springframework.core.task.support.ContextPropagatingTaskDecorator;
import org.springframework.messaging.Message;
import org.springframework.messaging.support.ExecutorSubscribableChannel;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

public class ContextPropagationDemo {

    private static final String TRACE_KEY = "demo.trace-context";
    private static final ThreadLocal<String> TRACE_CONTEXT = new ThreadLocal<>();

    public static void main(String[] args) throws InterruptedException {
        ContextRegistry.getInstance().registerThreadLocalAccessor(
            new ThreadLocalAccessor<String>() {
                @Override
                public Object key() {
                    return TRACE_KEY;
                }

                @Override
                public String getValue() {
                    return TRACE_CONTEXT.get();
                }

                @Override
                public void setValue(String value) {
                    if (value == null) {
                        TRACE_CONTEXT.remove();
                    }
                    else {
                        TRACE_CONTEXT.set(value);
                    }
                }

                @Override
                public void setValue() {
                    TRACE_CONTEXT.remove();
                }
            }
        );

        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(1);
        executor.setMaxPoolSize(1);
        executor.setQueueCapacity(10);
        executor.setThreadNamePrefix("message-worker-");
        executor.setTaskDecorator(new ContextPropagatingTaskDecorator());
        executor.initialize();

        try {
            ExecutorSubscribableChannel channel =
                new ExecutorSubscribableChannel(executor);

            CountDownLatch handled = new CountDownLatch(1);
            AtomicReference<String> payload = new AtomicReference<>();
            AtomicReference<String> messageTrace = new AtomicReference<>();
            AtomicReference<String> correlation = new AtomicReference<>();
            AtomicReference<String> actor = new AtomicReference<>();
            AtomicReference<String> threadTrace = new AtomicReference<>();

            channel.subscribe(message -> {
                payload.set(message.getPayload().toString());
                messageTrace.set(
                    (String) message.getHeaders().get("traceId")
                );
                correlation.set(
                    (String) message.getHeaders().get("correlationId")
                );
                actor.set(
                    (String) message.getHeaders().get("actorId")
                );
                threadTrace.set(TRACE_CONTEXT.get());
                handled.countDown();
            });

            TRACE_CONTEXT.set("trace-113");

            Message<String> message = MessageBuilder
                .withPayload("order-created")
                .setHeader("traceId", "trace-113")
                .setHeader("correlationId", "order-113")
                .setHeader("actorId", "user-42")
                .build();

            boolean accepted = channel.send(message);

            if (!handled.await(5, TimeUnit.SECONDS)) {
                throw new IllegalStateException(
                    "Message was not handled in time"
                );
            }

            System.out.println("payload=" + payload.get());
            System.out.println("messageTraceId=" + messageTrace.get());
            System.out.println("correlationId=" + correlation.get());
            System.out.println("actorId=" + actor.get());
            System.out.println("workerThreadTraceContext=" + threadTrace.get());
            System.out.println("sendAccepted=" + accepted);
        }
        finally {
            TRACE_CONTEXT.remove();
            executor.shutdown();
        }
    }
}
~~~

Run from the context-propagation-demo directory:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=demo.ContextPropagationDemo
~~~

**stdout**

~~~text
payload=order-created
messageTraceId=trace-113
correlationId=order-113
actorId=user-42
workerThreadTraceContext=trace-113
sendAccepted=true
~~~

In the example, message headers remain present when the consumer processes the message; the ThreadLocal trace context is also restored on the worker thread thanks to ContextPropagatingTaskDecorator. These two results illustrate two different scopes: data attached to the message and context attached to the task execution.

trace-113 in the example is only an illustrative value in a custom ThreadLocal/header. A real distributed tracing application needs a tracer to create spans and a propagator to inject/extract trace context in the configured format; do not use this demo snippet to hand-craft W3C traceparent.

## 9. Common Pitfalls

1. **Equating traceId with correlationId:** traceId serves tracing; correlationId serves business correlation. They can differ.
2. **Assuming MessageHeaders automatically carry every context:** a message only carries the headers created on it; adapters or transports may filter or transform them.
3. **Assuming ThreadLocal automatically follows an executor:** a different worker thread does not automatically receive the sender's ThreadLocal. Use TaskDecorator or an appropriate propagation mechanism.
4. **Using InheritableThreadLocal with thread pools:** reused workers can retain stale context or fail to receive new context as expected.
5. **Passing SecurityContext as a custom header:** do not serialize Authentication or SecurityContext into messages. Use Spring Security concurrency wrappers in-process and proper authentication mechanisms across service boundaries.
6. **Trusting actorId or tenantId from external messages:** these values can be spoofed. Verify origin and permissions before use.
7. **Using baggage to carry arbitrary data:** baggage can propagate widely and appear in traces/logs. Allowlist only small, necessary, non-sensitive fields.
8. **Not cleaning up context after a task finishes:** leftover ThreadLocal/MDC can cause the next task's logs to carry the wrong user or trace.
9. **Assuming ContextPropagatingTaskDecorator handles every context:** only values with a registered accessor are captured/restored; SecurityContext requires the corresponding Spring Security integration.
10. **Logging all headers:** can leak tokens, cookies, personal data, or routing metadata. Log only approved fields.
11. **Using context to replace the payload:** metadata describes origin and how to process; business data must still live in the payload.
12. **Assuming send succeeding means the consumer finished processing:** sendAccepted only reflects that the channel accepted the send per its mechanism; it does not replace acknowledgements or transaction outcomes.

## 10. Context Propagation Design Checklist

Before implementing a message flow, answer:

1. Which context must travel with the payload through queues/brokers, and which is only needed on the current thread?
2. Which tracer/propagator creates and injects/extracts traces?
3. Is the business correlation ID preserved across retries and new messages?
4. Is Actor ID taken from an authenticated principal and used only for auditing?
5. Does SecurityContext need to continue inside async tasks; if so, is the executor wrapped with Spring Security?
6. Do required ThreadLocals have a ThreadLocalAccessor and executor decorator?
7. If using Reactor, is context stored in Reactor Context and properly bridged when crossing imperative code?
8. Which headers are allowlisted across each transport; which headers must be stripped?
9. Are tenant, destination, and routing metadata verified before use?
10. Is context restored/cleared after processing to prevent leaking into the next task?
11. Do logs and metrics avoid tokens, personal data, and high-cardinality tags?
12. Are there integration tests proving trace/correlation/actor context flows accurately across channels, executors, and transports?

## 11. Conclusion

Propagating context in Spring Messaging requires combining multiple mechanisms at the proper boundaries. Message headers carry explicit metadata through the message flow; Micrometer Context Propagation and TaskDecorator restore context when tasks switch threads; Reactor Context manages subscription-scoped data; Spring Security provides dedicated wrappers to propagate SecurityContext across synchronous/asynchronous tasks.

Trace context, correlation ID, actor metadata, and authorization are distinct concepts. Use tracers/propagators for distributed tracing, correlation ID for business correlation, verified actorId for auditing, and SecurityContext or verified credentials for authorization. Propagate only necessary headers, validate them at trust boundaries, and always clean up context after processing.
