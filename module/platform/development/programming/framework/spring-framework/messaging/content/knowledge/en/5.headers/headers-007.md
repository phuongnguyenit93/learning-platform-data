# Correlation IDs and Linking Requests with Replies

In a messaging system, a request may traverse multiple components before a result is returned. When multiple requests are processed concurrently, the sender needs to know which reply belongs to which request. A correlation ID solves this problem by attaching a shared identifier to messages belonging to the same exchange.

Spring Messaging represents metadata using Message headers. Spring Integration adds routing and request/reply mechanisms so components can send requests, return replies to the right destination, and pair related messages. This lesson explains the role of correlation IDs, reply channels, and how to build a small example to observe the entire path.

## 1. The Problem of Linking Requests with Replies

Consider an ordering application. The client sends an order creation request to OrderService. The service may process it immediately or delegate work to another component before returning a result.

When there is only one request at a time, it is easy to see which request led to which reply. However, in real-world systems, multiple requests typically run concurrently:

~~~text
Client
  |-- Request A -------------------->
  |-- Request B -------------------->
  |-- Request C -------------------->

Service processes on its own schedule:
  |<-- Reply B ----------------------
  |<-- Reply A ----------------------
  |<-- Reply C ----------------------
~~~

Reply order may differ from request order. If the client relies solely on arrival order, it could mismatch results with requests. This is especially dangerous when each request represents a different business transaction.

A request/reply system must solve two things:

1. **Reply routing:** knowing which channel or endpoint to send the reply to.
2. **Reply correlation:** knowing which request or exchange the reply belongs to.

These are two related yet distinct concepts. Reply channel determines where to deliver the reply; correlation ID determines the logical relationship between request and reply.

## 2. What Is a Correlation ID?

A correlation ID is an identifier value attached to messages belonging to the same processing flow or exchange. The producer creates the ID when starting the request, puts it in a header, and involved components propagate that value across messages stemming from the initial request.

Example:

~~~text
Request:
  payload: CreateOrder(orderId=1024)
  headers:
    correlationId: corr-req-001

Reply:
  payload: OrderAccepted(orderId=1024)
  headers:
    correlationId: corr-req-001
~~~

When the client receives the reply, it reads correlationId and identifies which request the reply belongs to.

A correlation ID is usually generated using a UUID or an identifier sufficiently unique within the system's scope. In distributed applications, choose an appropriate uniqueness scope to avoid generating IDs that could collide among active requests.

### Correlation ID Differs from Message ID

These two IDs serve different purposes:

| Identifier | Meaning | Example |
|---|---|---|
| Message ID | Identifies a specific Message | ID generated by MessageBuilder |
| Correlation ID | Links multiple Messages in the same exchange | corr-req-001 |
| Business ID | Identifies a business entity | orderId=1024 |
| Trace ID | Links spans in a distributed trace | trace ID per tracing system |

A request and reply are two separate Messages, so they can have different Message IDs while sharing the same correlation ID.

Business ID should not be used as a correlation ID by default either. An order can generate many different requests over its lifecycle, such as order creation, payment, refund, and cancellation. If all of them reuse orderId as the correlation ID, distinguishing individual request/reply exchanges becomes harder.

Trace ID serves cross-service observability and tracing. A trace can include multiple operations and multiple message exchanges; therefore, trace ID and correlation ID may be related without necessarily being identical. Propagate trace context per your active tracing standard, while preserving a business correlation ID if the application needs to pair requests and replies.

## 3. Correlation ID in Spring Messaging

A Message in Spring Messaging consists of a payload and MessageHeaders. Correlation ID is typically passed as a header:

~~~java
Message<String> request = MessageBuilder
        .withPayload("Create order #1024")
        .setHeader("correlationId", "corr-req-001")
        .build();
~~~

Here:

- The payload contains the request content.
- The correlationId header holds the correlation identifier.
- MessageBuilder creates a new Message with the set of headers.
- MessageHeaders is metadata attached to the Message and must not be mutated directly after the Message is created.

In Spring Integration, correlation ID is also used by components such as aggregators and resequencers to group or reorder messages belonging to the same group. For simple request/reply, the application can create and pass correlation ID as shown in the example.

When creating a reply, copy the correlation ID from the request:

~~~java
Message<String> reply = MessageBuilder
        .withPayload("Order accepted")
        .setHeader("correlationId", request.getHeaders().get("correlationId"))
        .build();
~~~

This copying must be done intentionally. MessageBuilder creates a new Message, so the reply's Message ID will differ from the request's Message ID. The correlation ID is preserved so both messages remain part of the same exchange.

## 4. Reply Channel and Correlation ID Solve Two Different Problems

A request/reply message usually needs metadata indicating where to send the reply. In Spring Messaging, the standard replyChannel header can hold a MessageChannel or a channel name depending on the routing mechanism and configuration.

Example setting a channel in a header:

~~~java
QueueChannel replyChannel = new QueueChannel();

Message<String> request = MessageBuilder
        .withPayload("Create order #1024")
        .setHeader("correlationId", "corr-req-001")
        .setHeader("replyChannel", replyChannel)
        .build();
~~~

The service receives the request, retrieves replyChannel from the header, and sends the result there:

~~~java
MessageChannel replyTo =
        (MessageChannel) request.getHeaders().get("replyChannel");

replyTo.send(reply);
~~~

Distinction:

- replyChannel: where to receive the reply.
- correlationId: identifier used to match the reply to the request.
- messageId: unique identifier of the current message.

In simple examples, each request has its own QueueChannel so the reply is sent back to that request's dedicated queue. In systems with multiple concurrent requests sharing a single reply channel, a correlator or registry mechanism is needed to match replies by correlation ID. Do not rely solely on message order in the queue.

## 5. General Request/Reply Flow

An exchange may proceed as follows:

~~~text
Client / Producer
    |
    | Create correlationId
    | Create replyChannel
    | Send request + headers
    v
Request Channel
    |
    v
Service / MessageHandler
    |
    | Read payload and correlationId
    | Process business logic
    | Create new reply
    | Re-attach correlationId
    | Send reply to replyChannel
    v
Reply Channel
    |
    v
Client / Requester
    |
    | Read reply
    | Match correlationId
    v
Complete exchange
~~~

If the request is processed asynchronously, the client can continue other work while awaiting the reply. When waiting for a bounded time, the client must set a timeout and handle the case where no reply arrives. When a reply arrives late after timeout, the system needs a policy to ignore it, log it, or handle it as a late-arriving event.

## 6. Complete Example: Request and Reply Across Two Channels

The following example uses Spring Integration to observe a request entering a DirectChannel, a handler processing it, and sending a reply through a QueueChannel attached in the header. The client receives the reply and checks the correlation ID.

The example uses Java 17 and Spring Integration 6.4.6. The program runs in a single process without needing a broker or a Spring ApplicationContext.

### src/main/java/demo/CorrelationDemo.java

~~~java
package demo;

import org.springframework.integration.channel.DirectChannel;
import org.springframework.integration.channel.QueueChannel;
import org.springframework.messaging.Message;
import org.springframework.messaging.MessageChannel;
import org.springframework.messaging.MessageHandler;
import org.springframework.messaging.support.MessageBuilder;

public class CorrelationDemo {

    public static void main(String[] args) {
        DirectChannel requestChannel = new DirectChannel();

        MessageHandler orderService = request -> {
            Object correlationValue =
                    request.getHeaders().get("correlationId");
            Object replyChannelValue =
                    request.getHeaders().get("replyChannel");

            if (!(correlationValue instanceof String correlationId)) {
                throw new IllegalArgumentException(
                        "Missing correlationId header");
            }

            if (!(replyChannelValue instanceof MessageChannel replyTo)) {
                throw new IllegalArgumentException(
                        "Missing or invalid replyChannel header");
            }

            System.out.println("[service] received: " + request.getPayload());
            System.out.println("[service] correlationId = " + correlationId);

            Message<String> reply = MessageBuilder
                    .withPayload("Accepted: " + request.getPayload())
                    .setHeader("correlationId", correlationId)
                    .build();

            if (!replyTo.send(reply)) {
                throw new IllegalStateException(
                        "Reply channel rejected the message");
            }
        };

        requestChannel.subscribe(orderService);

        String correlationId = "corr-req-001";
        QueueChannel replyChannel = new QueueChannel();

        Message<String> request = MessageBuilder
                .withPayload("Create order #1024")
                .setHeader("correlationId", correlationId)
                .setHeader("replyChannel", replyChannel)
                .build();

        System.out.println("[client] request correlationId = "
                + correlationId);

        if (!requestChannel.send(request)) {
            throw new IllegalStateException(
                    "Request channel rejected the message");
        }

        Message<?> reply = replyChannel.receive(1000);

        if (reply == null) {
            throw new IllegalStateException("Timed out waiting for reply");
        }

        System.out.println("[client] reply payload = " + reply.getPayload());
        System.out.println("[client] reply correlationId = "
                + reply.getHeaders().get("correlationId"));
    }
}
~~~

Run from the directory containing pom.xml:

~~~shell
mvn -q compile exec:java -Dexec.mainClass=demo.CorrelationDemo
~~~

Output:

~~~text
[client] request correlationId = corr-req-001
[service] received: Create order #1024
[service] correlationId = corr-req-001
[client] reply payload = Accepted: Create order #1024
[client] reply correlationId = corr-req-001
~~~

### Analyzing the Request and Reply Path

**Step 1 — Create request channel:** DirectChannel acts as the request receiving point. The service is registered as a subscriber via subscribe(orderService).

**Step 2 — Create reply channel:** the client creates a dedicated QueueChannel for this exchange. QueueChannel is a PollableChannel, so the client can retrieve the reply with receive(timeout).

**Step 3 — Create correlation ID:** the example uses a fixed value corr-req-001 so the output is easy to compare. In real applications, generate a unique ID, such as via UUID.

**Step 4 — Attach metadata:** the request contains both correlationId and replyChannel. The two headers serve two distinct purposes: identifying the exchange and directing the reply.

**Step 5 — Service receives request:** the handler checks the types and presence of both headers before processing. If correlation ID or reply channel is missing, the example throws a clear error rather than silently producing an uncorrelatable reply.

**Step 6 — Create reply:** the service builds a new Message, sets the result payload, and copies the correlation ID from the request.

**Step 7 — Send reply:** the service extracts the MessageChannel from the replyChannel header and sends the reply into the client's QueueChannel.

**Step 8 — Client receives and matches:** the client calls receive(1000), waiting up to 1,000 milliseconds. After receiving the reply, it reads correlationId and confirms the value matches the sent request.

DirectChannel invokes the handler synchronously, so in this example the reply has already been placed into the QueueChannel before requestChannel.send(request) returns. The client still calls receive to demonstrate how a caller retrieves a reply from a PollableChannel. In asynchronous systems, request and reply may occur at different times.

## 7. Handling Multiple Concurrent Requests

When there are multiple simultaneous requests, each exchange needs its own correlation ID. Example:

| Request | Correlation ID | Reply |
|---|---|---|
| Create order 1024 | corr-A | Order 1024 accepted |
| Create order 1025 | corr-B | Order 1025 accepted |
| Create order 1026 | corr-C | Order 1026 accepted |

If replies arrive in order C, A, B, the client still pairs them accurately using the correlation ID.

There are two common organizational approaches:

**Dedicated reply channel per request:** the client creates a separate QueueChannel or receiving mechanism per request and attaches that channel to the replyChannel header. This approach is simple to illustrate and prevents requests from competing for each other's replies. However, channel lifecycles, timeouts, and resource cleanup must be managed once requests complete.

**Multiple requests sharing a reply channel:** replies are sent to a shared channel. A correlator component reads each reply, extracts correlationId, and looks up the waiting request in a registry. Cases such as request not found, late replies, duplicates, or expired registry entries must be handled.

Do not let multiple request threads call receive on a shared QueueChannel without a pairing mechanism. One thread could steal a reply meant for another thread.

In Spring Integration, gateways and request/reply components can manage temporary reply channel creation and correlation for callers. When using a gateway, prefer the framework's standard mechanism instead of building a custom registry if the gateway already satisfies the requirements.

## 8. Correlation ID and Related Headers

| Header or data | Purpose | Notes |
|---|---|---|
| correlationId | Pairs messages belonging to the same exchange | Must be propagated or copied intentionally |
| replyChannel | Specifies where to send the reply | Can be a channel object or channel name depending on configuration |
| errorChannel | Routes error messages in flows supporting this mechanism | Must be configured with a clear understanding of the error flow |
| id | Identifies a specific Message | Request and reply typically have different IDs |
| timestamp | Time the Message was created | Do not use in place of correlation ID |
| trace context | Links operations in distributed tracing | Follows the system's tracing standard |

Some notes:

- Do not use timestamp as a correlation ID because multiple requests can be created within the same time unit.
- Do not use the request's Message ID as the correlation ID if the reply is a new Message and a shared ID is needed for the entire exchange.
- Do not place personal data or secrets inside a correlation ID.
- Do not treat correlation ID as proof of authentication. A client can send arbitrary values; access permissions must still be verified independently.
- When crossing a broker or serialization boundary, ensure the header is supported by the adapter and converted with the right data type.

## 9. Timeouts, Late Replies, and Errors

Request/reply always requires a policy for when no reply arrives.

### Timeout

The client should set a wait duration based on the operation's SLA. In the example, receive(1000) waits up to one second. If no reply arrives, the result is null, and the code throws IllegalStateException.

In real applications, distinguish timeouts from business failures. A timeout only tells the client it did not receive a reply within the deadline; it does not prove the service failed to process the request. The service may have already created the order while the reply was delayed or lost.

### Replies arriving after timeout

If the client has already timed out and a reply still arrives, a handling policy is needed:

- Discard the reply if the result is no longer needed.
- Emit a log or metric to detect abnormal latency.
- Persist the result if the business logic requires later retrieval.
- Cancel or expire correlation entries to prevent memory leaks.

### Retries and duplicate handling

If a client retries after a timeout, the new request might trigger another business operation. For order creation or payment commands, this can cause duplicate data or multiple charges.

Distinguish:

- **Correlation ID:** links request/reply of a single exchange.
- **Idempotency key:** protects a business operation from unintended repeated execution.

The two values may be related, yet they should not be assumed identical. When retrying the same business operation, the application typically needs to preserve the appropriate idempotency key, whereas each retry attempt can have a new correlation ID to trace each individual exchange.

### Technical errors and business errors

If the service cannot process a request, it may emit an error message over an error channel or return a reply carrying an error status per the application contract. Clearly specify whether the client receives an exception, an error message, or a business rejection.

Example:

- OrderRejected is a valid business outcome: the order is rejected due to insufficient stock.
- DatabaseUnavailable is a technical error: the service cannot reach the database.
- Timeout is the condition where the client did not receive a reply in time.

Do not collapse all scenarios into one generic error string, as the client will struggle to decide whether to retry or notify the user.

## 10. Best Practices When Designing Correlation

1. **Generate sufficiently unique IDs:** use UUIDs or IDs from a standardized identification system.
2. **Set the ID at the start of the exchange:** every message spawned from the request should carry the same correlation ID while part of the same processing flow.
3. **Preserve the ID when building replies:** the reply is a new Message, yet it must carry back the request's correlation ID.
4. **Separate IDs from business data:** orderId, paymentId, and correlationId serve different roles.
5. **Manage reply channel lifecycles properly:** do not keep temporary channels alive after a request finishes.
6. **Set timeouts:** prevent requests from waiting indefinitely and registries from growing unboundedly.
7. **Handle late and duplicate replies:** specify clearly how to ignore, record, or reprocess them.
8. **Protect data:** correlation IDs must not contain PII, tokens, or secrets.
9. **Combine with tracing:** use trace context for cross-service tracing and correlation ID for business exchange pairing.
10. **Validate header types:** verify correlationId and replyChannel before using them, especially when receiving messages from external sources.

## 11. Common Misconceptions

**Correlation ID is the same as Message ID:** false. Every Message has its own ID; multiple Messages in the same exchange can share a correlation ID.

**Correlation ID is the reply channel:** false. An exchange identifier cannot by itself tell where to send the reply. Separate routing metadata is required.

**Preserving send order is enough to pair replies:** false. Consumers processing in parallel may reply in a different order. Use correlation ID for pairing.

**Using orderId for all correlation:** easily causes confusion if an order undergoes multiple independent request/reply exchanges. Separate entity identifiers from exchange identifiers.

**Timeout means the request failed:** false. The client only knows it did not receive a reply on time. The business operation on the service side may have already completed.

**Retries are always safe:** false. Retries can create duplicate side effects. Appropriate idempotency keys or deduplication mechanisms are required.

**Headers are automatically preserved across every broker:** do not assume this. Adapters, serializers, and brokers may convert or restrict headers; verify the actual configuration.

## 12. Key Takeaways

- Correlation ID links requests and replies belonging to the same exchange.
- Message ID identifies each individual Message; request and reply typically have different Message IDs.
- replyChannel determines where to send the reply, while correlationId determines which request the reply belongs to.
- Spring Messaging passes metadata via MessageHeaders; MessageBuilder is used to create Messages and attach headers.
- Spring Integration supports request/reply flows, channels, and gateways for routing and receiving replies.
- When handling multiple concurrent requests, dedicated IDs and a reply-pairing mechanism are needed; do not rely on message ordering.
- A timeout does not prove the business logic did not execute; retries must be designed alongside idempotency.
- Correlation ID aids tracing and reconciliation, but does not replace authentication, authorization, or trace context.
