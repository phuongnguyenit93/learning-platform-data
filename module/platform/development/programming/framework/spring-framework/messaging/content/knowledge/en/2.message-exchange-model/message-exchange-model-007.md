# Correlation of Time, Addressing, and Data Structure in Spring Messaging

A message in a Spring application typically carries more information than just the business data. When a service sends a message to another component, the system needs to know **when the message was created, where it is routed, and what structure or representation the payload has**. Spring Messaging separates these concerns into payload and headers so components can coordinate without cramming all metadata into the business data.

The three dimensions—time, addressing, and data structure—are related but serve distinct purposes:

- **Time** establishes when a message was created, occurred, or was received.
- **Addressing** identifies the channel, endpoint, queue, topic, or processing destination.
- **Data structure** describes which fields the payload contains and how it should be converted or interpreted.

Understanding this separation helps design stable message contracts, route accurately, and process messages reliably across multiple components or systems.

## 1. The Message Model: Payload and Headers

In Spring Messaging, a message is represented by the **Message<T>** interface:

- **Payload** is the primary data that the consumer needs to process. Type `T` may be a Java object, record, string, byte array, or another data type.
- **Headers** are a key/value metadata set accompanying the payload. Headers can describe identifiers, timestamps, content type, reply channels, error channels, or application-defined metadata.

This can be pictured as:

~~~text
Message<T>
    |
    +-- payload: T
    |      Business data to transmit
    |
    +-- headers: MessageHeaders
           id, timestamp, contentType, ...
           metadata for routing and processing
~~~

For example, a message announcing an order was created might contain:

- Payload: order ID, total amount, business occurrence time.
- Headers: message ID, Spring message creation timestamp, content type, logical destination label, correlation ID, and schema version.

Payload and headers travel together in the same message, but should not substitute for each other's roles. Order ID and total amount are business data and belong in the payload. Technical IDs, routing info, or content type usually belong in headers.

### MessageHeaders and MessageBuilder

**MessageHeaders** is the header structure readable by consumers. Common Spring Messaging headers include:

| Header | Meaning |
|---|---|
| **id** | Message identifier generated by Spring if not already provided. |
| **timestamp** | Message creation time according to the system clock, in milliseconds since the Unix epoch. |
| **contentType** | MIME type describing how to interpret the payload, e.g., **application/json**. |
| **replyChannel** | Reply channel information in request/reply flows that use it. |
| **errorChannel** | Error channel information in flows supporting this mechanism. |

**MessageBuilder** is a convenient way to create a message and attach headers:

~~~java
Message<String> message = MessageBuilder
        .withPayload("Order created")
        .setHeader("app.destination", "orders.created")
        .build();
~~~

When built, Spring creates a **Message** with the payload and headers. ID and timestamp are usually generated automatically if corresponding values are not already present and default generation remains enabled.

**MessageHeaders** is designed to be immutable once the message is created. If metadata needs to be changed, create a new message using **MessageBuilder** or use **MessageHeaderAccessor** in flows that need controlled mutable state. Do not treat the headers of an emitted message as an arbitrary map that can be mutated anywhere.

## 2. Time Correlation

Time appears at several different stages of a message's lifecycle. Merging them into a single field can cause consumers to misunderstand business timing or miscalculate latency.

### Distinguishing Message Creation Time from Business Event Time

Spring Messaging provides the **timestamp** header. This is when the message was created in the application according to the system clock. It is useful for observing the message lifecycle, but is not necessarily when the business event actually occurred.

For example, an order might be created at 09:00, while the service emits the message at 09:00:03 after writing data and completing several steps. In that case:

- The message's **timestamp** reflects when the message was created.
- **occurredAt** in the payload reflects when the business event of creating the order occurred.
- **receivedAt**, if recorded by the application itself, reflects when the consumer or adapter received the message.

These three timestamps answer three different questions. When analyzing latency, be explicit about which interval is being measured, such as from when the event occurred until the consumer received it.

### ID and Timestamp Are Not Business Keys

**id** distinguishes a message instance. It is not automatically an order ID, transaction ID, or business idempotency key. When a message is recreated from the same event, the message ID may differ.

Similarly, timestamps do not guarantee processing order across the system. Two services may have clock skew; a message broker may redeliver messages; consumers may process concurrently. If ordering guarantees are required, design around partition keys, business sequence/version numbers, or broker and consumer ordering mechanisms.

Useful principles:

- Use **Instant** or an explicit timezone-aware format for business event times.
- Use the message ID to trace a single message emission.
- Use a business event ID or idempotency key to recognize the same business operation upon retries.
- Do not infer absolute ordering from timestamps alone.
- When measuring latency across multiple machines, account for clock synchronization and define the measurement start and end points.

### Example of Representing Time

~~~java
public record OrderCreated(
        String orderId,
        Instant occurredAt
) {
}
~~~

**occurredAt** belongs in the payload because it is part of the meaning of the OrderCreated event. The **timestamp** header belongs in message metadata because it describes when the message was created in the messaging flow.

## 3. Addressing and Routing Correlation

Addressing answers the question: **which component or system will this message go to?** In Spring, there is no single **destination** field that applies uniformly across every kind of messaging. Addressing depends on the layer the application uses.

### MessageChannel in Spring Messaging

At the Spring Messaging level, **MessageChannel** is the abstraction representing where messages are sent. Producers call **send(message)** on the channel; the channel and components connected to it decide how the message is forwarded.

~~~text
Producer
   |
   | send(message)
   v
MessageChannel
   |
   v
Consumer / MessageHandler
~~~

A channel name in application configuration is an internal address within the processing flow. It does not automatically become a queue or topic name on a broker. Specific adapters or binders are responsible for mapping internal application flows to external infrastructure.

### Addressing Across Different Layers

| Layer | Common Address or Identifier | Role |
|---|---|---|
| Spring Messaging | **MessageChannel** | In-application message sending channel. |
| Spring Integration | Channel, router, gateway, adapter | Connects processing steps and routes messages between endpoints. |
| JMS / AMQP | Queue, exchange, routing key, destination | Routes via a broker according to the respective protocol. |
| Apache Kafka | Topic, partition, key | Identifies storage streams and record partitioning. |
| WebSocket / STOMP | Destinations like **/topic/orders** or **/app/orders** | Routes frames/messages per STOMP conventions and broker configuration. |

These names are not arbitrarily interchangeable. A **MessageChannel** in an application may be wired to a Kafka adapter, yet the channel itself is not a Kafka topic.

### Routing Headers and Destinations

Some flows use headers to carry routing information, such as **replyChannel**, **errorChannel**, or custom application-defined headers. Adapters and integration frameworks can read this metadata to determine the next step.

However, do not assume an arbitrary header named **destination** will be understood by every Spring component. If the application needs a custom logical destination label, define a clear convention such as **app.destination**, and write routers or adapters that explicitly read that header.

Keep infrastructure addresses in configuration or the adapter layer whenever possible. This keeps business logic from depending directly on environment-specific queue, topic, or endpoint names.

## 4. Data Structure Correlation

Data structure describes how the payload is organized and how consumers must interpret it. Spring Messaging allows payloads to have concrete Java types, yet when a message crosses a network boundary, a Java type does not automatically become a shared schema across all systems.

### Payload Is Data, contentType Is Metadata

A payload can be:

- A Java object or record, suitable when components share the same data types.
- **String**, suitable for text or already serialized data.
- **byte[]**, suitable when the application works directly with binary data.
- A specialized data type provided by a library or adapter.

The **contentType** header describes the format of the payload, for example:

- **application/json**: JSON.
- **application/xml**: XML.
- **text/plain**: plain text.
- **application/octet-stream**: binary data without a specific attached format.

Content type helps message converters select the right conversion strategy. It does not by itself define the full business schema. Two payloads that are both JSON can still have completely different structures.

### Schemas and Data Versioning

When multiple services exchange messages, a contract must be agreed upon: field names, data types, required fields, value semantics, and version compatibility rules.

The schema version can be placed in a header or inside a payload envelope. Whichever you choose, producer and consumer must agree on its location and interpretation. For example:

~~~text
payload:
  orderId: "ORD-1001"
  total: 125.50
  occurredAt: "2026-11-07T03:00:00Z"

headers:
  contentType: application/json
  app.schemaVersion: 1
~~~

Some design principles:

1. Use DTOs or records as exchange contracts; avoid sending persistence-coupled entities directly.
2. Use explicit types for money, time, and identifiers; avoid turning every value into an unstandardized string.
3. Specify how missing fields, new fields, and invalid values are handled.
4. Evolve schemas compatibly whenever possible; test both producers and consumers.
5. Serialize only the data the consumer needs; avoid including entire object graphs or unnecessary internal details in the payload.
6. Do not treat a content type header as a substitute for a schema registry or contract documentation.

### MessageConverter and Payload Conversion

In Spring flows that support conversion, a message converter transforms a payload from one representation to another. For example, a Java object can be converted to JSON on send and JSON converted back to a DTO on receive, depending on converter configuration and content type.

When conversion fails, check:

- Does the content type match the actual bytes?
- Do producer and consumer agree on the schema?
- Can the target Java type accept the present fields and data types?
- Is the converter configured and registered in the right flow?

Do not rely on a Java class name in one service to assume another service can deserialize the exact same object. Process boundaries require an agreed exchange format and contract.

## 5. Complete Example: Creating a Message with Time, Logical Address, and Schema

The following example uses Spring Messaging directly without starting a Spring Boot application context. The message carries an **OrderCreated** payload; headers contain content type, logical address, schema version, and correlation ID. Spring generates the message ID and timestamp.

### Maven Configuration

Create **pom.xml**:

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>message-metadata-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <maven.compiler.release>17</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-messaging</artifactId>
            <version>6.1.8</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
            </plugin>
            <plugin>
                <groupId>org.codehaus.mojo</groupId>
                <artifactId>exec-maven-plugin</artifactId>
                <version>3.2.0</version>
            </plugin>
        </plugins>
    </build>
</project>
~~~

### Java Code

Create **src/main/java/com/example/messaging/MessageMetadataExample.java**:

~~~java
package com.example.messaging;

import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.messaging.Message;
import org.springframework.messaging.MessageHeaders;
import org.springframework.messaging.support.MessageBuilder;
import org.springframework.util.MimeTypeUtils;

public class MessageMetadataExample {

    public record OrderCreated(
            String orderId,
            BigDecimal total,
            Instant occurredAt
    ) {
    }

    public static void main(String[] args) {
        OrderCreated event = new OrderCreated(
                "ORD-1001",
                new BigDecimal("125.50"),
                Instant.parse("2026-11-07T03:00:00Z")
        );

        Message<OrderCreated> message = MessageBuilder
                .withPayload(event)
                .setHeader(
                        MessageHeaders.CONTENT_TYPE,
                        MimeTypeUtils.APPLICATION_JSON
                )
                .setHeader("app.destination", "orders.created")
                .setHeader("app.schemaVersion", 1)
                .setHeader("app.correlationId", "checkout-2026-001")
                .build();

        System.out.println("orderId=" + message.getPayload().orderId());
        System.out.println("occurredAt=" + message.getPayload().occurredAt());
        System.out.println("contentType="
                + message.getHeaders().get(MessageHeaders.CONTENT_TYPE));
        System.out.println("destination="
                + message.getHeaders().get("app.destination"));
        System.out.println("schemaVersion="
                + message.getHeaders().get("app.schemaVersion"));
        System.out.println("messageIdPresent="
                + (message.getHeaders().get(MessageHeaders.ID) != null));
        System.out.println("timestampPresent="
                + (message.getHeaders().get(MessageHeaders.TIMESTAMP) != null));
    }
}
~~~

Run from the directory containing **pom.xml**:

~~~bash
mvn -q compile exec:java -Dexec.mainClass=com.example.messaging.MessageMetadataExample
~~~

Output:

~~~text
orderId=ORD-1001
occurredAt=2026-11-07T03:00:00Z
contentType=application/json
destination=orders.created
schemaVersion=1
messageIdPresent=true
timestampPresent=true
~~~

The example shows the three dimensions placed in their proper locations:

- **occurredAt** belongs in the payload because it describes when the business event happened.
- **timestamp** belongs in headers because it describes when the message was created.
- **app.destination** is an application-defined logical destination label. It only carries routing meaning when a channel, router, or adapter is configured to read it.
- **contentType** describes how to interpret the payload; **app.schemaVersion** describes the contract version agreed upon by the application.

The sample code builds the message in memory. It does not yet send the message to a queue, topic, or network endpoint; actual transmission requires a corresponding **MessageChannel**, handler, or adapter.

## 6. Combining the Three Dimensions in a Messaging Flow

A complete exchange flow typically requires all three groups of information together:

~~~text
Producer
   |
   | Create payload according to agreed schema
   | Attach event time / correlation metadata
   v
Message<T>
   |
   | Headers: id, timestamp, contentType, ...
   | Payload: business data
   v
Channel / Router / Adapter
   |
   | Select destination: channel, queue, topic, or endpoint
   v
Consumer
   |
   | Validate contract and content type
   | Handle idempotency, timing, and business logic
   v
Result / Reply / Error handling
~~~

Example with an order event:

1. The order service creates an **OrderCreated** payload with order ID, total amount, and occurrence time.
2. Spring creates the message, attaching ID and timestamp; the application adds content type, correlation ID, and schema version.
3. The producer sends the message to the chosen channel.
4. An adapter forwards the message to a queue or topic if the architecture uses a broker.
5. The consumer receives the message, checks format and schema, and then executes business processing.
6. If a response is needed, a request/reply flow can use a reply channel or the protocol's reply mechanism. For error handling, the application defines error handling appropriate to the channel and adapter in use.

Each layer is responsible for one part. Clear separation allows changing the broker or endpoint without having to change the business data structure in every case.

## 7. Common Design Mistakes

- **Using the message timestamp as the business event time:** the two times can differ. Store event time explicitly in the payload or agreed business metadata.
- **Using the message ID as an idempotency key:** retried or re-emitted messages may have different IDs. Use a stable event ID or business key to guard against duplicate processing.
- **Assuming every message has a destination header:** addressing depends on the channel, adapter, and protocol. Only use a routing header when a component actually reads it.
- **Hardcoding queue/topic names directly into business logic:** this couples code to the environment. Configure addresses in the integration or adapter layer.
- **Stuffing business data into headers:** headers suit short control or descriptive metadata. The payload should hold the data the consumer needs to process.
- **Assuming content type sufficiently describes the schema:** content type only specifies the general format. Versioning and contracts are needed to describe concrete structure.
- **Sending Java entities directly across systems:** entities can carry lazy relationships, internal fields, or persistence dependencies. Use intentional DTO/event contracts.
- **Using timestamps to guarantee ordering:** timestamps do not replace broker ordering, sequence numbers, or business versions.
- **Putting sensitive information in headers:** headers can be logged, copied, or forwarded across adapters. Transmit only necessary metadata and control logging carefully.

## 8. Key Takeaways

- **Message<T>** consists of payload and headers; payload holds primary data, headers hold metadata.
- **id** identifies the message instance; **timestamp** reflects message creation time by the system clock.
- Business times like **occurredAt** must be modeled separately when consumers need to know when the event happened.
- An address can be a **MessageChannel**, queue, topic, or endpoint; there is no universal destination header across all transports.
- **contentType** describes payload format; schemas and schema versions require their own contracts.
- When designing messages, clearly define which data belongs in the payload, which metadata belongs in headers, who owns routing, and how consumers maintain schema compatibility.

A well-designed message helps consumers accurately understand the data, timing, and processing context without overly depending on the producer's internal details.
