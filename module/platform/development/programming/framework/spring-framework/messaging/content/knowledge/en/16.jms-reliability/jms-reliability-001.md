# JMSMessageID, JMSCorrelationID, and JMSReplyTo

In JMS, these three headers support message identification and request/reply coordination between components:

- **JMSMessageID** is an identifier the JMS provider assigns to a message when it is sent.
- **JMSCorrelationID** is a value the application uses to link a message to another message, usually to link a reply to its request.
- **JMSReplyTo** is the Destination the receiver can send a reply to. The value can be a Queue or a Topic; if it is null, the request does not declare where to receive a reply.

The three headers play different roles and cannot substitute for one another. The Message ID identifies a specific message; the Correlation ID describes the relationship between messages; ReplyTo indicates where the response is sent. Understanding these three values correctly helps you build request/reply, match responses to their corresponding requests, handle multiple concurrent requests, and investigate failures in a messaging system.

## 1. Where the three headers sit in a JMS Message

A JMS Message consists of standard headers, properties, and a body:

- **Header:** standard metadata defined by JMS, for example JMSMessageID, JMSCorrelationID, JMSReplyTo, JMSTimestamp, JMSDestination, and JMSRedelivered.
- **Properties:** attributes added by the application or the provider for routing, filtering, or carrying business metadata.
- **Body:** the message content, such as TextMessage, BytesMessage, MapMessage, ObjectMessage, or StreamMessage.

JMSMessageID, JMSCorrelationID, and JMSReplyTo are standard headers. Do not create a property with a similar name and expect the broker or consumer to treat it as the corresponding JMS header.

~~~mermaid
flowchart TD
    A["JMS Message"] --> B["Standard headers"]
    A --> C["Properties"]
    A --> D["Body"]
    B --> E["JMSMessageID"]
    B --> F["JMSCorrelationID"]
    B --> G["JMSReplyTo"]
    C --> H["Application metadata"]
    D --> I["Text / Bytes / Map / Object"]
~~~

The methods for reading and writing headers are on the jakarta.jms.Message interface in modern Jakarta Messaging. With older Spring Framework versions that use the earlier JMS API, the package may be javax.jms. Use the package that matches the application's Spring version and provider.

## 2. JMSMessageID: the provider-assigned identifier

JMSMessageID is a unique value the provider assigns to each message that is sent. It is useful for:

- Finding a specific message in logs or broker administration tools.
- Linking a request and a reply when the message ID is used as the correlation key.
- Investigating redelivery or reconciling messages between producer and consumer.
- Recording a message trail in monitoring systems or history stores.

### 2.1. The provider assigns the ID on send

The client creates the message before sending it but does not decide the JMSMessageID. When the send or publish method returns, the provider has already assigned the ID value, and the message can be read through:

~~~java
String messageId = message.getJMSMessageID();
~~~

In Jakarta Messaging, provider-generated message ID values must start with the prefix **ID:**. The scope of ID uniqueness is determined by the provider; at a minimum it must cover the messages within one installation of the provider. Do not assume IDs are globally unique across multiple brokers or multiple vendors.

The client must not use setJMSMessageID() to set the ID itself. This method is intended for the provider when it sends a message. If the application needs a business identifier that it manages itself, put it in an application property or use JMSCorrelationID for its intended purpose of linking messages.

### 2.2. Message ID generation can be disabled

JMS allows the client to give a hint that the provider does not need to generate a message ID, through MessageProducer.setDisableMessageID(true). Spring JmsTemplate also has a messageIdEnabled property to control the corresponding behavior.

If the provider accepts this hint, the JMSMessageID of the outgoing message must be null. The provider may ignore the hint and still generate the ID as usual.

Only disable MessageID when the application is certain it does not use the ID for correlation, logging, tracing, or diagnostics. If the receiver needs to take the request's JMSMessageID to set the JMSCorrelationID of the reply, you must not rely on the message ID once this feature has been disabled.

### 2.3. MessageID is not a business idempotency key

JMSMessageID identifies a single send of a message handled by the provider. If the application resends the same event as a new message, the provider may assign a different JMSMessageID. Therefore, do not use MessageID as the unique key to prevent duplicate processing at the business level.

If you need idempotency, carry an event ID or request ID generated by the application in a property/body and record what has been processed by that key. JMSMessageID is still useful for tracing each specific send.

## 3. JMSCorrelationID: linking related messages

JMSCorrelationID is used to link one message to another. The most common pattern is to attach a reply to the original request.

Example:

~~~text
Request:
  JMSMessageID     = ID:provider-001
  JMSCorrelationID = order-request-42

Reply:
  JMSMessageID     = ID:provider-002
  JMSCorrelationID = ID:provider-001
~~~

In this example, the reply carries a JMSCorrelationID equal to the request's JMSMessageID. This lets the sender determine which request the reply corresponds to.

### 3.1. Two common ways to use CorrelationID

There are two common conventions:

**Approach A — The reply references the request's JMSMessageID**

1. The producer sends the request.
2. The provider assigns a JMSMessageID to the request.
3. The consumer processing the request reads the JMSMessageID.
4. The consumer creates the reply and sets its JMSCorrelationID to the request's JMSMessageID.
5. The producer receives the reply and compares the JMSCorrelationID with the ID of the request it sent.

This is the standard approach and is easy to understand when the sender can obtain the request's ID after the send completes.

**Approach B — Use an application-generated correlation ID**

1. The producer creates a unique request ID, for example a UUID.
2. The producer sets the request ID into JMSCorrelationID before sending.
3. The consumer reads the request's JMSCorrelationID.
4. The consumer copies that value into the reply's JMSCorrelationID.
5. The producer uses the known value to match the reply with the pending request.

Approach B is convenient when there are many concurrent requests and the application wants to know the correlation key right before sending. It also allows the same request ID to be kept across multiple processing steps.

Do not mix the two conventions in the same flow if the components do not agree. The producer and consumer must know whether the reply will return the original JMSMessageID or JMSCorrelationID.

### 3.2. Valid value types

JMSCorrelationID can contain:

- A provider-specific message ID, usually the request's JMSMessageID.
- An application-defined String.
- A byte[] in the provider's native format.

Using byte[] for CorrelationID is not portable. A provider that does not support the concept of a native correlation ID is not required to support the byte-array methods. In multi-provider applications, prefer String.

If the application sets a String correlation ID itself, the value must not start with **ID:** because this prefix is reserved for provider-generated message IDs.

Example:

~~~java
request.setJMSCorrelationID(UUID.randomUUID().toString());
~~~

A UUID value is a suitable choice because it is easy to generate, has a very low probability of collision, and does not use the ID: prefix.

### 3.3. CorrelationID does not by itself guarantee ordering or delivery

JMSCorrelationID is only linking metadata. It does not:

- Guarantee that the request has been processed.
- Guarantee that a reply will be sent.
- Guarantee that the reply arrives before the timeout.
- Automatically create a transaction between request and reply.
- Prevent the broker from redelivering the message.
- Replace the message ID or event ID used for idempotency.

The application must define timeouts, retries, handling of late replies, and cleanup of pending correlation data.

## 4. JMSReplyTo: specifying where the response goes

JMSReplyTo is a header that holds a **Destination** object. This Destination can be a Queue or a Topic. The producer sets this value on the request to tell the consumer where it can send the reply.

Example:

~~~java
request.setJMSReplyTo(replyQueue);
~~~

The receiver reads the destination with:

~~~java
Destination replyTo = request.getJMSReplyTo();
~~~

If JMSReplyTo is null, the request does not declare where to receive a reply. This usually means the message only carries data or a one-way notification. If ReplyTo is present, the sender usually expects a response, but JMS does not require the consumer to send a reply.

### 4.1. ReplyTo is a Destination, not the response content

JMSReplyTo indicates the address to send the response to. It does not contain the processing result and does not send a message by itself. The consumer must actively create the reply and send it to this destination.

~~~mermaid
sequenceDiagram
    participant A as Requester
    participant Q as Request Queue
    participant B as Responder
    participant R as Reply Queue
    A->>Q: Request + JMSReplyTo + JMSCorrelationID
    Q->>B: Deliver request
    B->>B: Process request
    B->>R: Reply + JMSCorrelationID
    R->>A: Deliver matching reply
~~~

A Queue is commonly used for replies because each reply is delivered to one suitable consumer. If you use a Topic, you need to understand subscriptions and the possibility that multiple subscribers receive the same publication. If the requester has not registered a subscription when the reply is published, the reply may not be received, according to Topic semantics.

### 4.2. TemporaryQueue and TemporaryTopic

The requester can create a temporary destination for one request or for one working session:

~~~java
TemporaryQueue replyQueue = session.createTemporaryQueue();
request.setJMSReplyTo(replyQueue);
~~~

A temporary destination is useful because there is no need to pre-configure a shared reply queue. The responder can send the reply to the destination provided in the request.

A temporary destination has a lifecycle tied to the Connection that created it. When the Connection is closed, the temporary destination is deleted according to the JMS provider's semantics. Therefore:

- Do not keep a temporary destination for long-term use after the Connection is closed.
- Do not send a reply after the requester has closed the Connection and the temporary destination no longer exists.
- If the application needs a shared reply queue or long-lived asynchronous processing, use a suitably administered destination.
- Check the broker permissions that allow the responder to send to the temporary destination.

## 5. Request/reply with JMS: the full flow

A request/reply exchange typically has these steps:

1. The requester creates or chooses a reply destination.
2. The requester creates the request message.
3. The requester sets JMSReplyTo and the correlation key.
4. The requester sends the request to the processing destination.
5. The responder receives the request and reads JMSReplyTo and the correlation key.
6. The responder performs the business processing.
7. The responder creates the reply and sets JMSCorrelationID according to the agreed convention.
8. The responder sends the reply to JMSReplyTo.
9. The requester receives the reply and matches it with the pending request.
10. The requester completes or times out, then cleans up the correlation state.

Example of a request with an application correlation ID:

~~~java
String correlationId = UUID.randomUUID().toString();

jmsTemplate.send("orders.request", session -> {
    TextMessage request =
            session.createTextMessage("Create order ORD-42");

    request.setJMSCorrelationID(correlationId);
    request.setJMSReplyTo(replyQueue);

    return request;
});
~~~

The responder copies the correlation ID into the reply:

~~~java
@JmsListener(destination = "orders.request")
public void handle(Message request) throws JMSException {
    Destination replyTo = request.getJMSReplyTo();

    if (replyTo == null) {
        return; // The request does not require a reply.
    }

    String correlationId = request.getJMSCorrelationID();

    jmsTemplate.send(replyTo, session -> {
        TextMessage reply =
                session.createTextMessage("Order ORD-42 accepted");

        if (correlationId != null) {
            reply.setJMSCorrelationID(correlationId);
        }

        return reply;
    });
}
~~~

This is an example using the Jakarta JMS API in modern Spring Framework. If the project uses an older Spring, replace the jakarta.jms import with the corresponding javax.jms. In a real application, you need to decide how to handle a missing correlation ID, an invalid reply destination, or business logic that cannot produce a result.

## 6. Using JmsTemplate.sendAndReceive()

Spring provides synchronous request/reply through JmsTemplate.sendAndReceive(). The template creates a TemporaryQueue for the operation, puts that Queue into the request's JMSReplyTo, and then waits for the reply.

Example:

~~~java
Message reply = jmsTemplate.sendAndReceive(
        "orders.request",
        session -> session.createTextMessage("Create order ORD-42")
);

if (reply instanceof TextMessage textReply) {
    String result = textReply.getText();
    // Process the result.
}
else if (reply == null) {
    // The receive timeout expired without receiving a reply.
}
~~~

JmsTemplate manages the creation and release of resources within the scope of the operation. You can configure the receive timeout with setReceiveTimeout(). If the timeout expires, sendAndReceive() may return null.

In the model with a dedicated temporary queue per call, the requester has its own destination to wait for the reply, so no correlation selector is needed to distinguish multiple replies on the same queue. Even so, the responder can still set the reply's JMSCorrelationID to the request's JMSMessageID or JMSCorrelationID to preserve tracing context.

JmsTemplate suits synchronous request/reply: the calling thread blocks while waiting for the response. If the number of requests is large or processing takes a long time, consider an asynchronous model so as not to hold too many threads waiting.

## 7. Shared reply queue and message selector

When multiple requests share one reply Queue, the requester must distinguish which reply belongs to which request. A common approach is a JMS message selector that filters by JMSCorrelationID.

Example of the requester generating the correlation ID before sending:

~~~java
String correlationId = UUID.randomUUID().toString();

jmsTemplate.send("orders.request", session -> {
    TextMessage request = session.createTextMessage("Create order");
    request.setJMSCorrelationID(correlationId);
    request.setJMSReplyTo(replyQueue);
    return request;
});
~~~

After the responder copies the correlation ID into the reply, the requester can receive the correct reply:

~~~java
String selector =
        "JMSCorrelationID = '" + correlationId + "'";

Message reply = jmsTemplate.receiveSelected(
        "orders.reply",
        selector
);
~~~

JmsTemplate uses the configured receive timeout. If the timeout expires, receiveSelected() returns null.

In the example above, the correlation ID is an application-generated UUID, so it contains no single quotes. If the selector is built from an external value, you must escape single-quote characters according to selector syntax and validate the input. Do not concatenate untrusted data directly into a message selector.

### 7.1. One consumer or many consumers on the reply queue?

If each request creates a consumer with its own selector, multiple consumers can listen on the same reply queue. You need to check how the provider handles selectors and message distribution. With a large number of requests, continually creating consumers can increase cost.

Another model is to use one shared reply listener for the reply queue, then route replies to pending requests using a correlation table:

~~~text
correlationId -> CompletableFuture / pending request
~~~

When a reply arrives, the listener reads the JMSCorrelationID, finds the corresponding future, and completes it. When a timeout occurs or the request ends, remove the entry from the table. You need to handle the case where a reply arrives after the timeout to avoid memory leaks.

Spring Integration JMS Gateway provides many built-in correlation mechanisms for request/reply. If the application needs an asynchronous gateway or manages a shared reply listener, consider using the gateway instead of implementing the entire router yourself.

## 8. JMS headers in Spring Messaging

Spring JMS provides the **org.springframework.jms.support.JmsHeaders** interface with standard header names to map JMS metadata to a Spring Message:

| JmsHeaders constant | JMS field | Meaning |
|---|---|---|
| MESSAGE_ID | JMSMessageID | ID assigned by the provider |
| CORRELATION_ID | JMSCorrelationID | Message linking key |
| REPLY_TO | JMSReplyTo | Destination that receives the reply |
| DESTINATION | JMSDestination | Current destination |
| REDELIVERED | JMSRedelivered | Indicator that the message was redelivered |

SimpleJmsHeaderMapper can map the standard JMS headers between jakarta.jms.Message and org.springframework.messaging.Message. With a Spring Message, you can read the headers through JmsMessageHeaderAccessor:

~~~java
JmsMessageHeaderAccessor accessor =
        JmsMessageHeaderAccessor.wrap(springMessage);

String messageId = accessor.getMessageId();
String correlationId = accessor.getCorrelationId();
Destination replyTo = accessor.getReplyTo();
~~~

Note that Spring Messaging's **MessageHeaders.ID** is a UUID generated by Spring for the Spring Message object. It is not the JMSMessageID issued by the broker. When you need the ID of the JMS message, use JmsHeaders.MESSAGE_ID or JmsMessageHeaderAccessor.getMessageId().

JMSMessageID is a read-only value in the standard header mapping. The application should not try to set it by writing into the Spring header map. If you need a business ID generated by the application, use JMSCorrelationID or a custom property.

## 9. Correlation conventions in a multi-service system

When a request passes through multiple services, the correlation ID can be kept unchanged to trace the entire processing chain.

Example:

~~~text
API Gateway
  correlationId = req-7f31
      |
      v
Order Service
  request JMSCorrelationID = req-7f31
      |
      v
Inventory Service
  reply JMSCorrelationID = req-7f31
      |
      v
Order Service
  response correlationId = req-7f31
~~~

Some principles:

- Generate the correlation ID at the request's first boundary if one does not already exist.
- Keep the correlation ID unchanged across the processing steps belonging to the same request.
- If one message spawns multiple independent branches, consider adding an event ID or parent ID to express the parent-child relationship.
- Do not use one shared correlation ID for all messages.
- Do not confuse the correlation ID with the trace ID of distributed tracing; the two values can be linked but have different purposes and lifecycles.
- Write the correlation ID to logs, metrics, or traces to find request/reply chains.

JMSCorrelationID is not a security mechanism and does not prove who the sender is. Do not use it to authenticate identity or grant access.

## 10. Reliability, timeouts, and late messages

Request/reply can encounter many states:

- The request has not yet been received by the broker.
- The request has been received but the responder has not processed it.
- The responder has processed it but the reply has not been sent.
- The reply has been sent but the requester timed out before receiving it.
- The reply arrives after the requester has cleaned up the correlation state.
- The request or reply is redelivered after a rollback.

A timeout only indicates that the requester stopped waiting within the specified time. It does not prove the responder has not processed the request. If the requester resends after a timeout, the business operation may be performed twice.

You need to design:

1. **Stable request ID:** helps identify the same business request across retries.
2. **Idempotency:** the responder records processed requests to avoid repeating side effects.
3. **Timeout:** limit the time spent waiting for a reply and record the timeout state.
4. **Late reply handling:** decide whether to ignore, store, or raise an alert when a reply arrives after the timeout.
5. **Retry policy:** determine which errors can be retried and the number of attempts.
6. **Expiration/TTL:** can limit the lifetime of the request/reply if the business allows it.
7. **DLQ:** keep messages that cannot be processed for investigation instead of retrying indefinitely.

JMSMessageID, JMSCorrelationID, and JMSReplyTo do not by themselves provide exactly-once processing. Reliability also depends on delivery mode, transactions, acknowledgement, broker persistence, redelivery policy, and application idempotency.

## 11. Security when using JMSReplyTo

JMSReplyTo is a Destination carried in the message. If the consumer receives a request from an untrusted source, it should not by default send a reply to whatever destination the request specifies.

Measures to consider:

- Only allow replies to destinations within a configured namespace or allowlist.
- Check the broker's send permissions for temporary and dynamic destinations.
- Do not allow clients to freely choose sensitive internal destinations.
- Log the destination after removing sensitive information.
- Limit the number of pending requests and the number of temporary destinations created.
- Set a reasonable TTL and timeout to avoid waiting resources that are never released.
- Escape and validate the correlation ID when putting it into a selector.

If the system is multi-tenant, you need to check that the requester has permission to receive replies for the corresponding tenant. A correlation ID can help route the right request but does not replace permission checks.

## 12. Common mistakes and how to handle them

### 12.1. Setting JMSMessageID yourself

The client tries to call setJMSMessageID() to assign a business ID. This is a provider-managed field.

Fix: use an application property or JMSCorrelationID for application-generated values.

### 12.2. Disabling MessageID but still using it as the correlation key

When the provider accepts disabling the message ID, JMSMessageID may be null. A reply cannot reference an ID that does not exist.

Fix: keep MessageID if needed or generate an application correlation ID before sending.

### 12.3. Request and reply use two different conventions

The requester expects the reply to return the application correlation ID but the responder sets the request's JMSMessageID, or vice versa.

Fix: state clearly whether the reply correlation must equal the request JMSMessageID or the request JMSCorrelationID, and test both sides.

### 12.4. JMSReplyTo is null

The consumer cannot find where to send the reply.

Fix: determine whether the request really requires a response; if so, the producer must set ReplyTo or use JmsTemplate.sendAndReceive().

### 12.5. Reply arrives at the wrong request

Multiple requests share one correlation ID or the reply does not copy the value correctly.

Fix: use a unique correlation ID for each pending request, check the selector, and log the value on both sides.

### 12.6. The reply queue no longer exists

The requester uses a TemporaryQueue and then closes the Connection before the responder sends the reply.

Fix: keep the Connection/destination valid until the reply completes or use an administered reply destination with a longer lifecycle.

### 12.7. Reply arrives after the timeout

The requester has already removed the correlation entry but the reply still arrives.

Fix: have a policy for late replies, record metrics, and ensure the pending request table is cleaned up properly.

### 12.8. Using JMSMessageID as an idempotency key

Each resend of the same event may produce a new ID, so deduplicating by JMSMessageID does not prevent business duplicates.

Fix: add an application-generated eventId/requestId and store it together with the processed state.

## 13. Java 17 example: simulating request/reply with the three headers

The following example uses plain JDK to illustrate how the three headers work together. DemoMessage is a record defined by the program itself, not a jakarta.jms.Message. The MessageID is simulated as an ID issued by the provider; the program does not connect to a broker.

Create the file **JmsRequestReplyHeadersDemo.java**:

~~~java
public class JmsRequestReplyHeadersDemo {

    record DemoMessage(
            String messageId,
            String correlationId,
            String replyTo,
            String body) {}

    static DemoMessage createRequest() {
        // Simulates the JMS provider assigning a MessageID after sending.
        return new DemoMessage(
                "ID:provider-001",
                "order-request-42",
                "orders.reply",
                "Create order ORD-42"
        );
    }

    static DemoMessage createReply(DemoMessage request) {
        if (request.replyTo() == null) {
            throw new IllegalArgumentException(
                    "Request has no JMSReplyTo destination");
        }

        // Convention: reply CorrelationID = request MessageID.
        return new DemoMessage(
                "ID:provider-002",
                request.messageId(),
                null,
                "Order ORD-42 accepted"
        );
    }

    public static void main(String[] args) {
        DemoMessage request = createRequest();
        DemoMessage reply = createReply(request);

        boolean matched = request.messageId()
                .equals(reply.correlationId());

        System.out.println(
                "Request JMSMessageID: " + request.messageId());
        System.out.println(
                "Request JMSCorrelationID: " + request.correlationId());
        System.out.println(
                "Request JMSReplyTo: " + request.replyTo());
        System.out.println(
                "Reply JMSCorrelationID: " + reply.correlationId());
        System.out.println("Reply matched request: " + matched);
    }
}
~~~

Compile and run with Java 17 or later:

~~~bash
javac JmsRequestReplyHeadersDemo.java
java JmsRequestReplyHeadersDemo
~~~

Output:

~~~text
Request JMSMessageID: ID:provider-001
Request JMSCorrelationID: order-request-42
Request JMSReplyTo: orders.reply
Reply JMSCorrelationID: ID:provider-001
Reply matched request: true
~~~

The example uses the convention that the reply's JMSCorrelationID equals the request's JMSMessageID. If the system chooses the application correlation ID convention, the responder would set the reply correlation ID to order-request-42 instead of ID:provider-001. Both sides must agree on the same convention.

## 14. Request/reply design checklist

Before implementing, determine:

- Who issues the JMSMessageID, and does the application need to keep this ID?
- Is there a need to disable message ID generation for performance reasons?
- Is the correlation key the JMSMessageID or an application-generated JMSCorrelationID?
- Which correlation value must the reply copy?
- Is JMSReplyTo a Queue, a Topic, a TemporaryQueue, or a shared destination?
- Who owns and closes the temporary destination?
- Does the requester wait for the reply synchronously or receive it asynchronously?
- If a shared reply queue is used, how are the selector or correlation map managed?
- How are timeouts, late replies, retries, and the DLQ handled?
- Is the responder idempotent when a request is redelivered?
- Is the destination in JMSReplyTo validated and permission-restricted?
- Do the logs store the message ID, correlation ID, and destination in a safe way?

JMSMessageID identifies a message sent by the provider; JMSCorrelationID links a request with its reply or related messages; JMSReplyTo specifies the destination that receives the response. When combined correctly, the three headers form a clear request/reply protocol. In Spring, JmsTemplate.sendAndReceive() simplifies synchronous request/reply using a temporary queue, while a shared reply queue needs a unique correlation ID and either a selector or a routing listener. Reliability still requires timeouts, transactions, retries, idempotency, and control over the destination lifecycle.
