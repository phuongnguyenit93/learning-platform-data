# MessageHeaders.ID, TIMESTAMP, and Identifier Lifecycle

## Objectives

After this lesson, you will be able to:

- Explain the meaning and data types of `MessageHeaders.ID` and `MessageHeaders.TIMESTAMP`.
- Track how these two headers are regenerated when a Spring Message is constructed or transformed.
- Distinguish message ID from business ID, event ID, correlation ID, trace ID, and broker-assigned IDs.
- Use `MessageBuilder` and `MessageHeaderAccessor` to read, copy, and add headers properly.
- Choose the right timestamp for message creation time, business occurrence time, and processing duration measurement.
- Avoid bugs when passing messages through transformers, splitters, aggregators, retries, and external transports.

## 1. Message and MessageHeaders

In Spring Messaging, `Message<T>` is a wrapper consisting of a payload and headers:

~~~java
public interface Message<T> {
    T getPayload();
    MessageHeaders getHeaders();
}
~~~

- **Payload** contains the main data that the consumer needs to process, such as an order DTO, a JSON string, or a record.
- **Headers** contain metadata accompanying the message, such as identifiers, timestamp, content type, correlation information, or transport information.

Two standard headers to understand clearly:

| Header | Constant | Data type | Meaning |
|---|---|---|---|
| Message ID | `MessageHeaders.ID` | `java.util.UUID` | Identifier of a Spring Message instance |
| Timestamp | `MessageHeaders.TIMESTAMP` | `java.lang.Long` | Time when the message was created |

They can be accessed via getters:

~~~java
UUID messageId = message.getHeaders().getId();
Long timestamp = message.getHeaders().getTimestamp();
~~~

Or accessed by constant name:

~~~java
Object id = message.getHeaders().get(MessageHeaders.ID);
Object createdAt = message.getHeaders().get(MessageHeaders.TIMESTAMP);
~~~

Using typed getters is generally easier to read and reduces casting. `MessageHeaders.ID` and `MessageHeaders.TIMESTAMP` are standard header names; there is no need to hardcode `"id"` or `"timestamp"` strings.

## 2. MessageHeaders.ID: Identifier of a Message Instance

### Meaning

`MessageHeaders.ID` has type `UUID` and is automatically generated by Spring when constructing an ordinary message. It identifies the message instance currently being processed in Spring Messaging.

Example:

~~~java
Message<String> message = MessageBuilder.withPayload("hello").build();

UUID id = message.getHeaders().getId();
System.out.println(id);
~~~

The actual value is a UUID, so it may differ on each run. Do not hardcode a UUID into examples or rely on a specific value in logs.

This ID answers the question: **"Which message instance is this?"** It does not by itself answer:

- Which business event occurred?
- Which request or workflow does this message belong to?
- Which ID did the broker store the message under?
- Which delivery attempt is this?
- Which distributed trace does this request belong to?

These are distinct identification concepts and require separate headers or data fields.

### Why does the ID change when a message is transformed?

Message and MessageHeaders are designed to be immutable. When an endpoint creates a new message, the new message has its own ID. In Spring Integration, every time a message is transformed—for example, through a transformer—the framework assigns a new message ID. The timestamp of the new message also reflects when the new message was created. `ID` and `TIMESTAMP` are read-only headers and are not overwritten when copying headers with `MessageBuilder`.

Lifecycle example:

~~~text
Create message A
  ID = id-A
  TIMESTAMP = time-A
       |
       v
Forward A without modification
  Still message A
       |
       v
Transformer creates message B
  ID = id-B
  TIMESTAMP = time-B
  Other business headers can be preserved
       |
       v
Handler creates message C
  ID = id-C
  TIMESTAMP = time-C
~~~

Not every endpoint creates a new message. A bridge or router that merely forwards a message without modification can preserve the same instance and ID. The key is distinguishing a forwarding operation from an operation that creates an output message.

### Do not manually set ID for ordinary messages

You should not use `setHeader(MessageHeaders.ID, ...)` or manually insert `id` into a header map to turn ID into a business code. Spring Framework's Javadoc specifies that ID is an auto-generated UUID; only when deserializing a serialized Message and needing to restore a previously generated UUID is there an exception for restoring this value.

If you need a stable code across processing steps, create a dedicated header such as `eventId`, `requestId`, `orderId`, or `correlationId`.

## 3. MessageHeaders.TIMESTAMP: Message Creation Time

### Meaning and how to read it

`MessageHeaders.TIMESTAMP` has type `Long`, representing the message creation time. For messages constructed normally, the value is epoch milliseconds: the number of milliseconds since 1970-01-01T00:00:00Z.

~~~java
Long timestamp = message.getHeaders().getTimestamp();

if (timestamp != null) {
    Instant createdAt = Instant.ofEpochMilli(timestamp);
    System.out.println(createdAt);
}
~~~

You can format it into UTC or a display time zone using the `java.time` API. Keep the epoch value in the header for exchange and format it only when displaying or logging.

### Timestamp changes across the message lifecycle

When a transformer or handler creates a new output message, the timestamp reflects the creation time of that output message. It is not an immutable milestone representing the entire journey of a business event.

For example:

- `time-A`: when Spring created the initial message.
- `time-B`: when the transformer created the payload-normalized message.
- `time-C`: when a handler created the result message.

Timestamp has millisecond resolution. Two messages created very close together can still have the same timestamp value if created within the same millisecond. Therefore, do not use `timestampA != timestampB` to prove two messages are different; use the ID to identify a message instance.

### Timestamp is not synonymous with business time

A `PaymentCaptured` event may be emitted after the payment operation has already occurred. A Spring Message's timestamp is when the message wrapper was created, which may be later than the business time.

If you need to record the business time, put a dedicated field in the payload or a clearly named header:

- `occurredAt`: when the business event actually occurred.
- `publishedAt`: when the producer emitted the event externally.
- `receivedAt`: when the consumer received the data.
- `MessageHeaders.TIMESTAMP`: when the Spring Message instance was created.

Do not use one generic name like `timestamp` for multiple concepts if the system needs to distinguish them.

Timestamp uses the system clock. When comparing timestamps across multiple machines, be mindful of clock skew between machines. To measure duration within the same process, use a monotonic clock such as `System.nanoTime()`; do not take two epoch timestamps from unsynchronized machines as an absolute latency measurement.

## 4. Distinguishing Types of Identifiers

Different types of IDs can appear together on one message yet have different lifecycles and purposes:

| Identifier type | Example | Lifecycle and purpose |
|---|---|---|
| Spring message ID | `MessageHeaders.ID` | UUID for a Spring Message instance; changes when creating a new message |
| Message timestamp | `MessageHeaders.TIMESTAMP` | Creation time of the Spring Message instance; changes when creating a new message |
| Business ID | `orderId`, `paymentId` | Identifies a business entity; stable over the entity's lifecycle |
| Event ID | `eventId` | Identifies a business event; kept stable on replay or retry of the same event |
| Correlation ID | `correlationId`, `requestId` | Links messages belonging to the same request, workflow, or processing group |
| Trace ID | `traceId` | Links spans within a distributed trace |
| Transport message ID | `JMSMessageID`, AMQP messageId | Transport-system identifier; managed by producer, broker, or provider depending on protocol |

For example, a message can carry simultaneously:

~~~text
MessageHeaders.ID = UUID of the current Spring Message
MessageHeaders.TIMESTAMP = time when Spring created the current instance
eventId = evt-2026-00042
correlationId = checkout-9001
orderId = ORD-1001
traceId = 4bf92f3577b34da6a3ce929d0e0e4736
~~~

When a transformer creates a new message, Spring ID and timestamp change; `eventId`, `correlationId`, `orderId`, and trace context can be preserved according to propagation policies.

### Message ID is not a deduplication key

A broker may redeliver the same message when a consumer fails or acknowledgement has not completed. Depending on the adapter and how inbound messages are built, each delivery may be wrapped in a new Spring Message instance. Thus, `MessageHeaders.ID` is not a stable deduplication key across retries or redeliveries.

If business deduplication is needed, the producer should generate a stable `eventId` and the consumer should record processed events by that key or by a unique business key. If the same event is replayed, keep the same `eventId`; do not generate a new eventId merely because a new Spring Message wrapper was created.

### Correlation ID in Spring Integration

Spring Integration provides the constant `IntegrationMessageHeaderAccessor.CORRELATION_ID` for the correlation header. This header is used to link messages, such as messages produced by a splitter waiting to be combined by an aggregator.

For request/reply, a request ID or correlation ID should be preserved according to the application's contract. Do not use `MessageHeaders.ID` as a correlation ID because the ID changes when a new message is created.

### Trace ID

Trace ID belongs to tracing systems such as Micrometer Tracing or OpenTelemetry. It links spans across multiple services and processes. Message ID may appear in a span's logs to assist investigation, yet it does not replace trace ID or span ID.

## 5. Header Propagation as a Message Flows

Spring Integration typically forwards inbound headers to the outbound message produced by an endpoint so business and routing metadata remain available in the flow.

Several rules to know:

1. When a service activator or message-producing endpoint creates an outbound message, inbound headers are usually propagated.
2. Headers already present on the outbound message take precedence; inbound headers are copied only if that name does not yet exist on the output.
3. `MessageHeaders.ID` and `MessageHeaders.TIMESTAMP` are read-only and are not overwritten by the source message's values.
4. If a transformer returns a plain payload, the framework can propagate inbound headers.
5. If a transformer itself returns a complete `Message`, the transformer code is responsible for building all headers needed on the outbound message.
6. You can configure an endpoint not to propagate certain headers via `setNotPropagatedHeaders()`, `addNotPropagatedHeaders()`, or the `notPropagatedHeaders()` option in Java DSL.

### Splitter and Aggregator

When a splitter creates multiple child messages from one input message:

- Each child message is a new message instance and has its own ID.
- Child messages need to be linked by a correlation ID.
- Spring Integration can add sequence number and sequence size so the aggregator knows the position and total count of messages in the group.
- When the aggregator creates the aggregated message, the result gets a new ID; correlation metadata is managed according to aggregator semantics.

Do not use the first message's ID to represent all child messages. ID identifies each individual instance; correlation ID represents the group relationship.

### Transformer returning Message vs. payload?

The two return styles have different meanings:

~~~java
// Return payload: framework can propagate inbound headers.
String normalize(String payload) {
    return payload.trim();
}

// Return Message: code is responsible for headers that need to be preserved.
Message<String> normalizeMessage(Message<String> input) {
    return MessageBuilder.withPayload(input.getPayload().trim())
            .copyHeaders(input.getHeaders())
            .build();
}
~~~

In the second example, `copyHeaders` preserves custom headers such as `eventId` or `correlationId`, while the source message's ID and timestamp are not copied over the two read-only headers. The output message has its own identifier and creation time.

## 6. Creating a New Message Properly with MessageBuilder

`MessageHeaders` implements `Map` but is an immutable map. Calling `put`, `remove`, or `clear` directly on the map causes `UnsupportedOperationException`.

Do not modify directly:

~~~java
message.getHeaders().put("stage", "validated"); // UnsupportedOperationException
~~~

Use `MessageBuilder` to create a new message:

~~~java
Message<String> next = MessageBuilder.fromMessage(message)
        .setHeader("stage", "validated")
        .build();
~~~

Useful methods:

- `MessageBuilder.withPayload(payload)`: creates a builder with a new payload.
- `MessageBuilder.fromMessage(message)`: creates a builder from the source message's payload and headers.
- `copyHeaders(map)`: copies custom headers; does not overwrite ID and timestamp.
- `copyHeadersIfAbsent(map)`: copies only headers not yet present.
- `setHeader(name, value)`: adds or updates a custom header.
- `removeHeader(name)`: removes a custom header.

Do not use `setHeader` or `copyHeaders` to force an old message's ID/timestamp onto a new message.

### Using MessageHeaderAccessor

When you need to manipulate multiple headers or need a typed access API, use `MessageHeaderAccessor`:

~~~java
MessageHeaderAccessor accessor = new MessageHeaderAccessor();
accessor.setHeader("correlationId", "checkout-9001");
accessor.setHeader("eventId", "evt-2026-00042");

MessageHeaders headers = accessor.getMessageHeaders();
Message<String> message =
        MessageBuilder.createMessage("payment-captured", headers);
~~~

By default, when `getMessageHeaders()` is called, the accessor transitions to a state where further modification is disallowed and the returned headers are immutable. If `setLeaveMutable(true)` is set, `setImmutable()` must be called upon completion before passing the message to another component or thread. The mutable mechanism should only be used during message initialization on a single thread.

You can retrieve the accessor attached to a message with `MessageHeaderAccessor.getAccessor(message)`; this method may return `null` if the message was not created via a corresponding accessor. If you only need to read ID and timestamp, the direct getters on `MessageHeaders` are simpler.

## 7. Java 17 Example: Tracking ID and Timestamp Across Transformation

The example uses Spring Framework 6.2.18 and requires only the `spring-messaging` module. The program creates an initial message, creates a new message with a normalized payload, retains business headers, and compares the two IDs.

Directory structure:

~~~

File `src/main/java/demo/MessageIdentityDemo.java`:

~~~java
package demo;

import java.time.Instant;
import java.util.UUID;

import org.springframework.messaging.Message;
import org.springframework.messaging.support.MessageBuilder;

public class MessageIdentityDemo {

    public static void main(String[] args) {
        Message<String> original = MessageBuilder
                .withPayload("  invoice-paid  ")
                .setHeader("eventId", "evt-2026-00042")
                .setHeader("correlationId", "checkout-9001")
                .build();

        Message<String> normalized = MessageBuilder
                .withPayload(original.getPayload().trim())
                .copyHeaders(original.getHeaders())
                .setHeader("normalized", true)
                .build();

        UUID originalId = original.getHeaders().getId();
        UUID normalizedId = normalized.getHeaders().getId();
        Long timestamp = normalized.getHeaders().getTimestamp();

        Instant createdAt = Instant.ofEpochMilli(timestamp);

        System.out.println("payload=" + normalized.getPayload());
        System.out.println("newMessageId=" + !originalId.equals(normalizedId));
        System.out.println("eventId=" + normalized.getHeaders().get("eventId"));
        System.out.println("correlationId=" + normalized.getHeaders().get("correlationId"));
        System.out.println("normalized=" + normalized.getHeaders().get("normalized"));
        System.out.println("timestampPresent=" + (timestamp != null));
        System.out.println("timestampType=" + timestamp.getClass().getSimpleName());
        System.out.println("createdAtParsed=" + (createdAt != null));
    }
}
~~~

Run from the directory containing `pom.xml`:

~~~bash
mvn -q compile org.codehaus.mojo:exec-maven-plugin:3.5.0:java -Dexec.mainClass=demo.MessageIdentityDemo
~~~

Stdout output:

~~~text
payload=invoice-paid
newMessageId=true
eventId=evt-2026-00042
correlationId=checkout-9001
normalized=true
timestampPresent=true
timestampType=Long
createdAtParsed=true
~~~

Explanation:

- The initial message receives a Spring-generated UUID and timestamp.
- The `normalized` message is a new instance, so it has a new UUID.
- `copyHeaders` preserves `eventId` and `correlationId`.
- The ID and TIMESTAMP headers of the initial message are not copied over onto the new message.
- Timestamp is read as a `Long` and converted to `Instant` using `Instant.ofEpochMilli(...)`.
- The program does not print concrete UUID or time values, so the stdout above is stable across runs.

## 8. Identifiers When Crossing Brokers and Protocols

When a message leaves the application, adapters may map Spring headers to transport attributes. You should not assume every transport preserves all headers or uses the same names.

### RabbitMQ / AMQP

Spring AMQP has dedicated headers in `AmqpHeaders`, such as `AmqpHeaders.MESSAGE_ID` and `AmqpHeaders.CORRELATION_ID`. A header mapper decides which values are transferred between Spring Message and AMQP MessageProperties.

With Spring Integration's `DefaultAmqpHeaderMapper`, since Spring Integration 5.1, if an outbound message does not yet have a corresponding AMQP message ID or timestamp header, the mapper may use `MessageHeaders.ID` and `MessageHeaders.TIMESTAMP` as fallback values for the `MessageProperties.messageId` and `MessageProperties.timestamp` properties. On the inbound side, native properties are mapped into AMQP headers with dedicated prefixes.

Therefore, distinguish:

- `MessageHeaders.ID`: ID of the Spring Message.
- `AmqpHeaders.MESSAGE_ID`: header representing message ID at the AMQP layer.
- `eventId`: business ID defined and kept stable by the producer.

The fact that two values may be linked by a mapper in a specific configuration does not turn them into the same concept. Check the header mapper and library version before relying on mapping behavior.

### JMS

Spring JMS has `JmsHeaders.MESSAGE_ID`, `JmsHeaders.CORRELATION_ID`, and other headers for accessing JMS message properties. The JMS provider may assign `JMSMessageID`; applications should not confuse this native value with Spring `MessageHeaders.ID`.

Header mappers are responsible for converting between Spring headers and JMS properties. For example, `JMSCorrelationID` is commonly used to correlate request/reply; Spring Integration also has a `correlationId` concept for grouping related messages, and these two concepts can be mapped according to specific policies.

### Across service boundaries

When sending events over HTTP, Kafka, RabbitMQ, or JMS, define a clear contract:

~~~json
{
  "eventId": "evt-2026-00042",
  "eventType": "PaymentCaptured",
  "schemaVersion": 1,
  "occurredAt": "2026-11-07T03:00:00Z",
  "correlationId": "checkout-9001",
  "paymentId": "PAY-1001"
}
~~~

The payload above contains business identifiers and business time. When a consumer creates a new Spring Message, Spring may assign a new `MessageHeaders.ID` and `TIMESTAMP` to the local wrapper. `eventId` and `occurredAt` remain intact per the contract.

## 9. Customizing ID Generation and Advanced Notes

Spring provides the `org.springframework.util.IdGenerator` abstraction to customize the UUID generation strategy. Spring Integration allows declaring a bean implementing this interface to change the message ID generation strategy.

Consider carefully before customizing:

- The default ID strategy is already optimized for UUID generation.
- One classloader uses only one UUID strategy. Multiple ApplicationContexts in the same classloader share that strategy.
- If multiple contexts declare an `IdGenerator`, they must use the same implementation class; different parameter configurations do not create context-isolated strategies.
- Do not use an incrementing counter as a distributed ID if multiple processes emit messages; a local counter does not guarantee uniqueness across processes.
- Changing the ID generator does not replace event ID, correlation ID, or trace ID.

`MessageHeaderAccessor` and `IdTimestampMessageHeaderInitializer` provide mechanisms for customizing ID/timestamp generation in certain header creation flows or protocol integrations. Only disable automatic ID/timestamp generation when an adapter or contract truly requires it and all consumers are designed for that case.

## 10. Common Mistakes

1. **Using `MessageHeaders.ID` as an event ID.** ID changes when a new message is created; retries or adapters may create another wrapper. Create a separate `eventId`.
2. **Using ID as a correlation ID.** Child messages or output messages have their own IDs. Use a stable correlation ID to link them.
3. **Using timestamp as the business time.** Spring's timestamp is when the message wrapper was created. Store `occurredAt` separately in the event.
4. **Trying to overwrite ID/timestamp with MessageBuilder.** These are read-only headers in Spring Integration and are not copied over in the usual way.
5. **Directly modifying MessageHeaders.** The header map is immutable. Use `MessageBuilder` or `MessageHeaderAccessor`.
6. **Assuming every endpoint creates a new ID.** Endpoints that merely forward messages without modification may preserve the same instance. A new ID appears when a new message is created.
7. **Assuming all headers are automatically preserved.** A transformer returning a complete Message must supply the needed headers itself; endpoints can also be configured to filter header propagation.
8. **Using epoch timestamps from multiple machines to compute latency without clock synchronization.** Clock skew can distort results. Use tracing or appropriate measurements.
9. **Using a native broker ID as a business ID.** Broker IDs may be provider-assigned and subject to transport rules. Keep a separate eventId in the contract if cross-system deduplication is needed.
10. **Putting a mutable object in a header and modifying it after sending.** An immutable header map does not make objects inside deeply immutable. Prefer immutable values such as String, UUID, numbers, and Instant.

## 11. Checklist When Designing Message Identity

- [ ] Read `MessageHeaders.ID` via `getId()` and treat it as the ID of the Spring Message instance.
- [ ] Read `MessageHeaders.TIMESTAMP` via `getTimestamp()` and convert epoch milliseconds to `Instant` when needed.
- [ ] Do not manually assign ID/timestamp for ordinary messages.
- [ ] Generate a stable `eventId` if deduplication or event replay is needed.
- [ ] Use correlation ID to link request/reply, splitter/aggregator, or workflows.
- [ ] Use trace context to track flows across multiple processes.
- [ ] Explicitly define which headers must propagate through transformers and adapters.
- [ ] Verify the mapping between Spring headers and native AMQP/JMS headers.
- [ ] Do not assume retry/redelivery preserves the Spring Message ID.
- [ ] Log message ID, event ID, and correlation ID together when investigating; avoid logging sensitive payloads.
- [ ] Use a dedicated business timestamp when you need to know when the event actually occurred.

## 12. Conclusion

`MessageHeaders.ID` identifies a Spring Message instance with a UUID; `MessageHeaders.TIMESTAMP` records when that instance was created. When a flow creates a new message, these two values belong to the new message and can change, whereas event ID, business ID, correlation ID, and trace context are preserved for their own purposes. Use `MessageBuilder` or `MessageHeaderAccessor` to create and adjust headers, distinguish wrapper creation time from business time, and check mapping rules when messages cross a broker.
