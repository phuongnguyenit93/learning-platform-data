# Testing User Destinations with Multiple Users and Multiple Sessions

## 1. What Problem Do User Destinations Solve?

In Spring STOMP over WebSocket, clients can subscribe to private notifications using a destination starting with `/user/`. For example:

```text
SUBSCRIBE /user/queue/notifications
```

The client does not need to know the internal session ID. Spring intercepts this subscription via `UserDestinationMessageHandler` and translates it into a destination dedicated to the connected session, for example:

```text
/user/queue/notifications
        |
        | UserDestinationMessageHandler
        v
/queue/notifications-userA1
```

Another session of the same user also subscribes to `/user/queue/notifications`, yet Spring creates a different physical destination, such as `/queue/notifications-userA2`. Consequently, two sessions can use the same logical destination name without mistakenly receiving each other's notifications.

On the sending side, the application can send to `/user/{username}/queue/notifications`. Spring looks up that user's active sessions in `SimpUserRegistry`, then resolves one target destination per session.

```text
/user/alice/queue/notifications
        |
        +--> /queue/notifications-userA1
        |
        +--> /queue/notifications-userA2
```

The session-suffixed names above are illustrative only. Do not write tests that depend on the exact suffix string generated by Spring. Verify which sessions receive the message and which sessions do not.

## 2. Distinguishing Multiple Users and Multiple Sessions

A single user can open multiple browser tabs, sign in across multiple devices, or establish multiple WebSocket connections. Each connection creates a distinct session, while multiple sessions can still belong to the same principal.

Example active state:

| User | Session | Subscription |
|---|---|---|
| alice | alice-1 | `/user/queue/notifications` |
| alice | alice-2 | `/user/queue/notifications` |
| bob | bob-1 | `/user/queue/notifications` |
| charlie | charlie-1 | `/user/queue/notifications` |

When the application sends to user `alice`, only sessions `alice-1` and `alice-2` are targeted. Sessions belonging to `bob` and `charlie` do not receive the message despite subscribing to the same logical destination.

Both dimensions must be tested separately:

- **Cross-user isolation:** messages sent to Alice must never reach Bob.
- **Same-user fan-out:** messages sent to Alice are delivered to every Alice session subscribed to the corresponding destination.

`SimpUserRegistry` is the source of truth for connected users and sessions. `DefaultUserDestinationResolver` uses this registry to locate sessions and build target destinations. The APIs `SimpUser.getSessions()`, `SimpSession.getSubscriptions()`, and `SimpSubscription.getDestination()` are useful when inspecting connection state in tests.

## 3. Broadcast Behavior of @SendToUser

`@SendToUser` defaults to `broadcast = true`. If a user has multiple sessions, the reply is sent to all of that user's sessions subscribed to the corresponding destination.

```java
@Controller
public class NotificationController {

    @MessageMapping("/notify-all")
    @SendToUser("/queue/notifications")
    public String notifyAllSessions(String message, Principal principal) {
        return principal.getName() + ":" + message;
    }

    @MessageMapping("/notify-current")
    @SendToUser(value = "/queue/notifications", broadcast = false)
    public String notifyCurrentSession(String message, Principal principal) {
        return principal.getName() + ":" + message;
    }
}
```

With two sessions for Alice:

- Sending `/app/notify-all` from `alice-1`: both `alice-1` and `alice-2` receive the reply if both subscribe to `/user/queue/notifications`.
- Sending `/app/notify-current` from `alice-1`: only `alice-1` receives the reply. `alice-2` does not receive it.

`broadcast = false` is useful for responses tied to a specific tab's action or error. For example, the tab that submitted a profile update needs to receive validation errors, whereas another tab open under the same account does not need to receive that error.

For sessions without an authenticated principal, Spring still supports user destinations keyed by session ID. In that case, `@SendToUser` behaves like sending exclusively to the current session, equivalent to `broadcast = false`.

## 4. Sending Notifications from a Service with SimpMessagingTemplate

Not every notification originates from a `@MessageMapping` handler. A service, scheduler, or event listener can send directly to a user using `SimpMessagingTemplate`.

```java
import org.springframework.messaging.simp.SimpMessagingTemplate;
import org.springframework.stereotype.Service;

@Service
public class NotificationService {

    private final SimpMessagingTemplate messagingTemplate;

    public NotificationService(SimpMessagingTemplate messagingTemplate) {
        this.messagingTemplate = messagingTemplate;
    }

    public void notifyUser(String username, String message) {
        messagingTemplate.convertAndSendToUser(
                username,
                "/queue/notifications",
                message
        );
    }
}
```

The first argument is the username from `Principal.getName()`. The second argument is the logical queue path, such as `/queue/notifications`; do not prepend `/user/{username}` to this argument because `convertAndSendToUser` applies the user destination prefix automatically.

When Alice has two sessions subscribed to the queue, calling `notifyUser("alice", "...")` delivers to both sessions. When Bob has the same subscription, Bob still does not receive the message.

Usernames must be stable and unique within the registry scope. If multiple tenants can share the same username, use a globally unique identifier such as `tenantId:userId` or implement `DestinationUserNameProvider` to supply a unique destination username. Do not use display names that can collide as routing identifiers.

## 5. Configuring the STOMP Endpoint and Broker for Tests

User destination tests require a STOMP endpoint, application prefix, user prefix, and broker prefixes. Example configuration:

```java
import java.security.Principal;
import java.util.Map;

import org.springframework.context.annotation.Configuration;
import org.springframework.http.server.ServerHttpRequest;
import org.springframework.messaging.simp.config.MessageBrokerRegistry;
import org.springframework.web.socket.WebSocketHandler;
import org.springframework.web.socket.config.annotation.EnableWebSocketMessageBroker;
import org.springframework.web.socket.config.annotation.StompEndpointRegistry;
import org.springframework.web.socket.config.annotation.WebSocketMessageBrokerConfigurer;
import org.springframework.web.socket.server.support.DefaultHandshakeHandler;
import org.springframework.web.util.UriComponentsBuilder;

@Configuration
@EnableWebSocketMessageBroker
public class StompTestConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.setPreserveReceiveOrder(true);

        registry.addEndpoint("/ws")
                .setHandshakeHandler(new DefaultHandshakeHandler() {
                    @Override
                    protected Principal determineUser(
                            ServerHttpRequest request,
                            WebSocketHandler wsHandler,
                            Map<String, Object> attributes) {

                        String username = UriComponentsBuilder
                                .fromUri(request.getURI())
                                .build()
                                .getQueryParams()
                                .getFirst("testUser");

                        return (username != null ? () -> username : null);
                    }
                });
    }

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.setApplicationDestinationPrefixes("/app");
        registry.setUserDestinationPrefix("/user");
        registry.enableSimpleBroker("/queue", "/topic");
    }
}
```

Explanation:

- `/ws` is the WebSocket handshake URL.
- `/app` is the prefix for messages routed to `@MessageMapping` methods.
- `/queue` and `/topic` are prefixes handled by the simple broker.
- `/user` is the prefix handled by `UserDestinationMessageHandler` before forwarding to the broker.
- `setPreserveReceiveOrder(true)` instructs Spring to process incoming messages from the same WebSocket session in receive order. This feature is available from Spring Framework 6.1 onward.

`determineUser` in the example reads a query parameter to assign distinct principals for test clients. This is strictly a way to simulate identity in integration tests. Real applications must obtain the principal from HTTP handshake authentication or a secured STOMP authentication mechanism; never trust a self-declared username in a query parameter.

Do not include `/user` in the broker prefix list. If the broker directly receives `/user/...` destinations, `UserDestinationMessageHandler` cannot perform the translation from logical destinations to per-session destinations.

## 6. Creating a Controller for Integration Tests

The following controller provides three handlers: one that broadcasts to all sessions of a user, one that replies only to the originating session, and one that confirms subscription readiness.

```java
import java.security.Principal;

import org.springframework.messaging.handler.annotation.MessageMapping;
import org.springframework.messaging.simp.annotation.SendToUser;
import org.springframework.stereotype.Controller;

@Controller
public class UserDestinationTestController {

    @MessageMapping("/ready")
    @SendToUser(value = "/queue/replies", broadcast = false)
    public String ready(String value) {
        return "READY:" + value;
    }

    @MessageMapping("/broadcast")
    @SendToUser("/queue/replies")
    public String broadcast(String value, Principal principal) {
        return principal.getName() + ":" + value;
    }

    @MessageMapping("/session-only")
    @SendToUser(value = "/queue/replies", broadcast = false)
    public String sessionOnly(String value, Principal principal) {
        return principal.getName() + ":" + value;
    }
}
```

The `/ready` handler produces a response sent only to the current session. The test subscribes first and then sends `/app/ready`. Upon receiving `READY:ready`, the test knows the subscription has been processed and is ready to receive subsequent messages.

This barrier is useful with the simple broker because the simple broker does not support STOMP receipts. `setPreserveReceiveOrder(true)` guarantees that the `SUBSCRIBE` frame and the following `SEND` frame on the same session are processed in order. With an external broker supporting receipts, you can use the receipt of the `SUBSCRIBE` command to confirm the broker processed the subscription.

## 7. Integration Test with Two Users and Three Sessions

A realistic integration test should open at least three connections:

- Alice opens two sessions to simulate two tabs or two devices.
- Bob opens one session to verify isolation between users.
- All three subscribe to `/user/queue/replies`.

Typical test dependencies required:

```groovy
dependencies {
    testImplementation("org.springframework.boot:spring-boot-starter-test")
    testImplementation("org.springframework.boot:spring-boot-starter-websocket")
}
```

The example below uses `WebSocketStompClient` to connect to a server running on a random port. The test assumes the test application imports `StompTestConfig` and `UserDestinationTestController`.

```java
import java.lang.reflect.Type;
import java.time.Duration;
import java.util.List;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.TimeUnit;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.context.annotation.Import;
import org.springframework.messaging.simp.SimpMessagingTemplate;
import org.springframework.messaging.simp.stomp.StompFrameHandler;
import org.springframework.messaging.simp.stomp.StompHeaders;
import org.springframework.messaging.simp.stomp.StompSession;
import org.springframework.messaging.simp.stomp.StompSessionHandlerAdapter;
import org.springframework.messaging.simp.user.SimpUser;
import org.springframework.messaging.simp.user.SimpUserRegistry;
import org.springframework.messaging.converter.StringMessageConverter;
import org.springframework.web.socket.client.standard.StandardWebSocketClient;
import org.springframework.web.socket.messaging.WebSocketStompClient;

import static java.util.concurrent.TimeUnit.SECONDS;
import static org.assertj.core.api.Assertions.assertThat;
import static org.awaitility.Awaitility.await;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Import({StompTestConfig.class, UserDestinationTestController.class})
class UserDestinationIntegrationTest {

    @LocalServerPort
    int port;

    @Autowired
    SimpUserRegistry userRegistry;

    @Autowired
    SimpMessagingTemplate messagingTemplate;

    private WebSocketStompClient stompClient;

    private final List<StompSession> sessions =
            new CopyOnWriteArrayList<>();

    @BeforeEach
    void setUp() {
        stompClient = new WebSocketStompClient(
                new StandardWebSocketClient());
        stompClient.setMessageConverter(new StringMessageConverter());
    }

    @AfterEach
    void tearDown() {
        sessions.forEach(session -> {
            if (session.isConnected()) {
                session.disconnect();
            }
        });
        stompClient.stop();
    }

    @Test
    void routesMessagesToCorrectUsersAndSessions() throws Exception {
        StompSession alice1 = connect("alice");
        StompSession alice2 = connect("alice");
        StompSession bob1 = connect("bob");

        BlockingQueue<String> alice1Messages =
                subscribeAndConfirm(alice1);
        BlockingQueue<String> alice2Messages =
                subscribeAndConfirm(alice2);
        BlockingQueue<String> bobMessages =
                subscribeAndConfirm(bob1);

        // Default broadcast: both sessions belonging to Alice receive it.
        alice1.send("/app/broadcast", "fan-out");

        assertThat(alice1Messages.poll(5, SECONDS))
                .isEqualTo("alice:fan-out");
        assertThat(alice2Messages.poll(5, SECONDS))
                .isEqualTo("alice:fan-out");
        assertNoMessage(bobMessages);

        // broadcast=false: only the session that sent the request receives it.
        alice1.send("/app/session-only", "private-reply");

        assertThat(alice1Messages.poll(5, SECONDS))
                .isEqualTo("alice:private-reply");
        assertNoMessage(alice2Messages);
        assertNoMessage(bobMessages);

        // A service can also send to all active sessions of a user.
        messagingTemplate.convertAndSendToUser(
                "alice", "/queue/replies", "service-event");

        assertThat(alice1Messages.poll(5, SECONDS))
                .isEqualTo("service-event");
        assertThat(alice2Messages.poll(5, SECONDS))
                .isEqualTo("service-event");
        assertNoMessage(bobMessages);

        // After one Alice session disconnects, only the remaining one is active.
        alice2.disconnect();

        await().atMost(Duration.ofSeconds(5)).untilAsserted(() -> {
            SimpUser alice = userRegistry.getUser("alice");
            assertThat(alice).isNotNull();
            assertThat(alice.getSessions()).hasSize(1);
        });

        messagingTemplate.convertAndSendToUser(
                "alice", "/queue/replies", "after-disconnect");

        assertThat(alice1Messages.poll(5, SECONDS))
                .isEqualTo("after-disconnect");
        assertNoMessage(bobMessages);
    }

    private StompSession connect(String username) throws Exception {
        String url = "ws://localhost:" + port
                + "/ws?testUser=" + username;

        StompSession session = stompClient.connectAsync(
                url,
                new StompSessionHandlerAdapter() {
                }
        ).get(5, SECONDS);

        sessions.add(session);
        return session;
    }

    private BlockingQueue<String> subscribeAndConfirm(
            StompSession session) throws Exception {

        BlockingQueue<String> messages = new LinkedBlockingQueue<>();

        session.subscribe("/user/queue/replies", new StompFrameHandler() {
            @Override
            public Type getPayloadType(StompHeaders headers) {
                return String.class;
            }

            @Override
            public void handleFrame(StompHeaders headers, Object payload) {
                messages.add((String) payload);
            }
        });

        // Receive-order preservation ensures SUBSCRIBE is processed before SEND.
        session.send("/app/ready", "ready");

        assertThat(messages.poll(5, SECONDS))
                .isEqualTo("READY:ready");

        return messages;
    }

    private void assertNoMessage(BlockingQueue<String> messages)
            throws InterruptedException {

        assertThat(messages.poll(500, TimeUnit.MILLISECONDS)).isNull();
    }
}
```

Key points of the test:

1. `connect("alice")` is called twice. The two connections share the principal name `alice` but have distinct session IDs.
2. Bob has a different principal name and is stored as a different user in the registry.
3. All three sessions subscribe to the same logical destination. Spring automatically resolves them into distinct per-session internal destinations.
4. The message sent to `/app/broadcast` is returned by the handler with default `@SendToUser`, so both Alice sessions receive it.
5. The message sent to `/app/session-only` is returned only to the Alice session that sent the request.
6. `convertAndSendToUser` tests the service sending path independently of controllers.
7. After Alice-2 disconnects, the registry retains only one session. The next notification is delivered only to Alice-1.

The `/app/ready` barrier keeps the test from sending business messages before the subscription is ready. In projects using Awaitility, use `await().untilAsserted(...)` to wait for the registry update instead of relying on a fixed sleep duration.

## 8. Testing SimpUserRegistry and UserDestinationResolver Directly

Integration tests verify end-to-end behavior. When diagnosing failures at the destination-resolution layer, you can inspect `SimpUserRegistry` and `UserDestinationResolver` directly.

Information you can verify:

- `userRegistry.getUser("alice")` returns user Alice when an active session exists.
- `user.getSessions()` returns Alice's current sessions.
- `session.getSubscriptions()` lists the session's subscriptions.
- `subscription.getDestination()` reports the destination the session subscribed to.
- `DefaultUserDestinationResolver.resolveDestination(...)` produces a `UserDestinationResult` containing the source destination, target destinations, and corresponding session IDs.

Example logical expectations:

| Check | Result |
|---|---|
| Alice has two sessions | `getSessions().size() == 2` |
| Bob has one session | `getSessions().size() == 1` |
| Send to Alice | Two target destinations |
| Send to Bob | One target destination |
| Send to offline user | No local target sessions |
| Alice-2 disconnects | Registry has one remaining session |

When testing the resolver, verify the count of target destinations and the set of session IDs. Do not compare against the auto-generated suffix string because that detail can change across runs or framework versions.

To write a resolver unit test, prepare a message with destination `/user/alice/queue/replies`, initialize a registry with simulated users/sessions, and call `resolveDestination`. If you only want to verify controller behavior, use `clientInboundChannel` with Spring TestContext so Spring processes `@MessageMapping` and `@SendToUser` annotations just as at runtime.

## 9. Testing When a User Has Multiple Sessions but Only Some Subscribe to a Queue

Fan-out applies to sessions with subscriptions matching the destination. A user having three sessions does not mean all three receive every notification.

Example:

| Session | Subscribed to `/user/queue/alerts`? |
|---|---|
| alice-1 | Yes |
| alice-2 | No |
| alice-3 | Yes |

When sending to Alice on the `alerts` queue, only `alice-1` and `alice-3` receive the message.

There should be a dedicated test for this case:

1. Connect three sessions with the same principal `alice`.
2. Have only session 1 and session 3 subscribe to `/user/queue/alerts`.
3. Send `convertAndSendToUser("alice", "/queue/alerts", ...)`.
4. Verify session 1 and session 3 receive the message.
5. Verify session 2 does not receive the message.

This matters when an application has multiple screens or tabs where each screen subscribes to a different subset of notifications.

## 10. Testing Multiple Application Servers

When running multiple Spring instances, each instance typically knows only about locally connected user sessions. If Alice connects to node A while a service on node B sends a notification to Alice, node B needs to know that the session exists on node A.

With a STOMP broker relay and a shared broker, you can configure user registry broadcasting and unresolved user destination broadcasting:

```java
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.setApplicationDestinationPrefixes("/app");

    registry.enableStompBrokerRelay("/topic", "/queue")
            .setUserRegistryBroadcast("/topic/simp-user-registry")
            .setUserDestinationBroadcast(
                    "/topic/unresolved-user-destination");
}
```

The two broadcast channels serve different purposes:

- `setUserRegistryBroadcast` publishes local user registry state so other nodes keep an up-to-date view of remote sessions.
- `setUserDestinationBroadcast` forwards user destinations that could not be resolved on the current node so another node can handle them.

A cluster test requires at least two application instances and one shared STOMP broker:

1. Connect two Alice sessions to node A.
2. Connect Bob to node B.
3. Wait for the user registry broadcast to propagate.
4. Send a notification to Alice from a service running on node B.
5. Verify both Alice sessions receive it and Bob does not.
6. Disconnect one Alice session and verify the remote registry updates.
7. Send another notification to verify only the remaining active Alice session receives it.

The simple in-memory broker is not suitable for cluster testing because its subscriptions and messages live strictly in each application instance's memory. Use a broker relay with a STOMP-capable broker for multi-node integration tests.

If you need to test offline users or messages sent when no session is active, design separate persistence. User destinations themselves are not durable queues storing messages for offline users.

## 11. Common Testing Pitfalls

| Symptom | Common Cause | How to Fix |
|---|---|---|
| Alice-1 receives it but Alice-2 does not | The two sessions have different principal names or Alice-2 has not subscribed | Check `Principal.getName()` and the registry |
| Bob receives Alice's notification | Principals were given the same name or the service passed the wrong username | Check user identity in handshake and the name passed to the template |
| No message reaches the user | Broker handles `/user` before `UserDestinationMessageHandler` or prefixes are misconfigured | Check the user destination prefix and broker prefixes |
| Test fails intermittently due to missing messages | Sending before the subscription was processed | Use STOMP receipts if the broker supports them or use a response barrier with receive-order preservation |
| Reply appears on every tab | Using default `@SendToUser` when a per-session reply is needed | Set `broadcast = false` |
| Still sends to old session after disconnect | Disconnect not yet processed or test did not wait for registry update | Wait for `SimpUserRegistry` to reflect the updated sessions |
| Unconnected user still does not receive notifications | User destinations do not store offline messages | Use separate persistence/notification inbox |
| Single-node test passes but cluster fails | User registry holds only local sessions | Configure user registry broadcast and broker relay |
| Multiple tenants with same username mix sessions | `Principal.getName()` is not globally unique | Use a globally unique identifier or `DestinationUserNameProvider` |

Tips when writing tests:

1. Each test should use its own usernames and payloads to avoid receiving messages from other tests.
2. Use `BlockingQueue`, `CountDownLatch`, or Reactor `StepVerifier` to synchronize message reception.
3. Do not use arbitrary `Thread.sleep` as a mechanism to confirm subscription readiness.
4. Always disconnect sessions and stop the client in `@AfterEach`.
5. Test both one user with multiple sessions and multiple users subscribing to the same logical destination.
6. Also test sessions that did not subscribe to the destination being sent to.
7. With a broker relay, check broker availability and heartbeat configuration when tests run long.
8. When running thousands of simulated clients, consider disabling heartbeats in performance tests unless measuring heartbeat behavior; each client can schedule its own heartbeat task.
9. The simple broker does not support STOMP ACK and receipts. If tests depend on these features, use an external broker.
10. Do not print tokens, cookies, or real credentials in test logs.

## 12. Testing Checklist

- [ ] User destination prefix `/user` is configured and handled by Spring.
- [ ] Application prefix `/app` and broker prefixes `/queue`, `/topic` do not overlap.
- [ ] Every user has a stable, unique principal name.
- [ ] Two sessions of the same user are grouped under the same user in the registry.
- [ ] Two different users do not share a session identity.
- [ ] Sessions subscribing to the same logical destination do not cross-receive messages.
- [ ] Default `@SendToUser` sends to all subscribed sessions of the user.
- [ ] `broadcast = false` sends only to the originating session.
- [ ] `SimpMessagingTemplate.convertAndSendToUser` delivers to the right user.
- [ ] Sessions not subscribed to the destination do not receive the message.
- [ ] Disconnect updates the user registry.
- [ ] Tests wait for subscription readiness before publishing.
- [ ] Cluster tests use an external broker and user registry broadcast when multiple nodes exist.
- [ ] Offline notifications are handled by separate persistence if business requirements require storing them.
