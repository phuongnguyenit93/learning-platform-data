# Distinguishing Spring Boot Events from ApplicationContext Events

## 1. Objective and Core Answer

In a Spring Boot application, you may encounter very similar names such as `ApplicationStartedEvent`, `ContextStartedEvent`, `ApplicationReadyEvent`, and `ContextRefreshedEvent`. They are **not different names for the same event**.

There are two main lifecycle groups:

1. **Spring Boot application events**: events generated by `SpringApplication.run(...)` to describe the progress of **starting up a Boot application**, from initial launch through preparation, running runners, becoming ready to serve, or failing.
2. **Spring Framework ApplicationContext events**: events reflecting the lifecycle of **an `ApplicationContext`**, such as the context having refreshed, or having `start()`, `stop()`, or `close()` invoked. They do not require Spring Boot; a plain Spring Framework application can publish these events too.

A third point of confusion: the phrase "context event" is sometimes used to mean **any event dispatched by `ApplicationContext.publishEvent(...)`**, including custom business events and some Boot events. In this article, when referring to **`ApplicationContextEvent`**, we mean the **specific class family** in package `org.springframework.context.event`.

After this lesson, you will know how to distinguish them by **publisher origin, class type, timing milestone, listener registration method, bean/context readiness, and intended use**; and run a Java 17+ example yourself to observe the difference.

## 2. Three Layers to Separate: Origin, Type, and Dispatch Mechanism

### 2.1. Boot and Spring Framework Share Event Infrastructure

Spring Framework provides:

- `ApplicationEvent`: base class for events with a source.
- `ApplicationEventPublisher`: event-publishing API; `ApplicationContext` also implements this interface.
- `ApplicationListener<E>` and `@EventListener`: two ways to receive events.
- `ApplicationEventMulticaster`: strategy for dispatching events to matching listeners.

Spring Boot **uses this exact infrastructure** to announce its own lifecycle events. Thus, "Boot events" do not imply a completely separate event bus. Boot has a mechanism to publish certain early events before the context exists and uses the context mechanism at later stages.

### 2.2. Class Hierarchy

~~~text
java.util.EventObject
└── org.springframework.context.ApplicationEvent
    ├── org.springframework.boot.context.event.SpringApplicationEvent
    │   ├── ApplicationStartingEvent
    │   ├── ApplicationEnvironmentPreparedEvent
    │   ├── ApplicationContextInitializedEvent
    │   ├── ApplicationPreparedEvent
    │   ├── ApplicationStartedEvent
    │   ├── ApplicationReadyEvent
    │   └── ApplicationFailedEvent
    │
    └── org.springframework.context.event.ApplicationContextEvent
        ├── ContextRefreshedEvent
        ├── ContextStartedEvent
        ├── ContextStoppedEvent
        └── ContextClosedEvent
~~~

The diagram lists representative lifecycle classes in Spring Boot 3.3.x and Spring Framework 6.1.x. It is **not exhaustive** of all event types in Spring; for instance, `AvailabilityChangeEvent` and `WebServerInitializedEvent` also exist in Boot, so do not assume every event in an `org.springframework.boot` package is a direct subclass of `SpringApplicationEvent`.

**Distinction rule:** `ApplicationStartedEvent` belongs to **Boot**; `ContextStartedEvent` belongs to **Framework**. Both are `ApplicationEvent`s, yet **neither inherits from the other**.

### 2.3. Comparison by Criterion

| Criterion | Spring Boot Application Events | Framework ApplicationContext Events |
| --- | --- | --- |
| Origin | Boot's `SpringApplication` run process | `ApplicationContext` lifecycle |
| Typical package | `org.springframework.boot.context.event` | `org.springframework.context.event` |
| Base class | `SpringApplicationEvent` for primary Boot lifecycle group | `ApplicationContextEvent` |
| Existence condition | Application started through Boot | Any compatible Spring `ApplicationContext` |
| Events before context is formed? | **Yes**, e.g. `ApplicationStartingEvent` | **No**, because a context is needed as the source |
| Always caught by bean `@EventListener`? | No, especially early Boot events | Usually yes for events occurring after the bean listener is registered |
| Meaning of "started" | Boot refreshed the context, **runners not yet run** | `ConfigurableApplicationContext.start()` explicitly called |
| Meaning of "ready" | Boot finished runners, moving toward ready state | No equivalent `ContextReadyEvent` in the context family |
| Event on close | Boot has no single general equivalent `ApplicationStoppedEvent` | `ContextClosedEvent` when context closes |

Do not guess from class names; check the **package** and **publication timing**.

## 3. Spring Boot Event Sequence During Startup

Per Spring Boot 3.3.x, in a normal successful startup, the main milestones are published in order:

| Order | Boot Event / Milestone | Context and Beans at That Time | When Needed |
| --- | --- | --- | --- |
| 1 | `ApplicationStartingEvent` | No complete `Environment` or `ApplicationContext` yet | Very early observation of Boot starting |
| 2 | `ApplicationEnvironmentPreparedEvent` | Environment prepared; context not yet created | Read/influence Environment before context creation (when validly needed) |
| 3 | `ApplicationContextInitializedEvent` | Context prepared, initializers ran; bean definitions not yet loaded | Observe context initialized milestone |
| 4 | `ApplicationPreparedEvent` | Bean definitions loaded, **context not yet refreshed** | Intervene/observe pre-refresh stage within appropriate lifecycle limits |
| 5 | Framework's `ContextRefreshedEvent` (interleaved milestone) | Context refreshed successfully | Observe context ready at Spring Framework level |
| 6 | `ApplicationStartedEvent` | Context refreshed, **`ApplicationRunner` / `CommandLineRunner` not yet executed** | Work after refresh and before runners |
| 7 | `AvailabilityChangeEvent` with `LivenessState.CORRECT` | Boot announces live state | Track liveness |
| 8 | `ApplicationRunner` and `CommandLineRunner` invoked | Context refreshed | Tasks running at startup |
| 9 | `ApplicationReadyEvent` | Runners completed | Observe Boot startup completion and readiness to serve |
| 10 | `AvailabilityChangeEvent` with `ReadinessState.ACCEPTING_TRAFFIC` | Boot announces readiness | Track ability to accept traffic |

A `WebServerInitializedEvent` can also occur in web applications when the web server is initialized, before `ApplicationStartedEvent`. In applications **without a web server**, there is no reason to expect this milestone.

If startup fails, Boot publishes **`ApplicationFailedEvent`** instead of confirming readiness. The failure event can occur **before `ApplicationContext` exists**, and its `getApplicationContext()` may return `null`.

These milestones show:

- `ApplicationStartingEvent` is completely different from `ApplicationStartedEvent`: "Starting" means **beginning startup**, "Started" means **after refresh**.
- `ApplicationStartedEvent` **does not mean the application is ready to serve**. Runners have not executed yet at this point.
- `ApplicationReadyEvent` is a later milestone. If a runner fails, the run may publish `ApplicationFailedEvent` without ever reaching `ApplicationReadyEvent`.
- `ContextRefreshedEvent` appears during Boot startup, yet it is emitted by **Framework context refresh**; it does not turn into a `SpringApplicationEvent`.

Do not treat the sequence above as a rigid schedule for every application: child contexts, reruns, additional refreshes, failures, shutdown, and separately published availability events can produce extra events in practice.

## 4. ApplicationContext Lifecycle in Spring Framework

The `ApplicationContextEvent` family does not depend on the `SpringApplication` class:

### 4.1. `ContextRefreshedEvent`

Published when the context **initializes or refreshes successfully**. With proper configuration, this is usually when beans have been instantiated and processed by post-processors. A context supporting multiple refreshes can publish this event multiple times; some implementations disallow a second refresh.

In Spring Boot, `ContextRefreshedEvent` typically occurs during `SpringApplication.run(...)` **before** `ApplicationStartedEvent`. However, a `ContextRefreshedEvent` listener is **not the standard way to know runners have finished**.

### 4.2. `ContextStartedEvent`

Published when **`ConfigurableApplicationContext.start()`** is called. It relates to the context's start lifecycle and `Lifecycle` beans, and is **not automatically published merely because Spring Boot started running**.

Do not write code "waiting for `ContextStartedEvent` to know Spring Boot finished starting" unless the application genuinely has an explicitly designed `context.start()` call.

### 4.3. `ContextStoppedEvent`

Published when **`ConfigurableApplicationContext.stop()`** is called. It describes stopping the context under the lifecycle contract; it is not synonymous with closing all resources completely or halting the JVM. After `stop()`, the context can still exist and be restarted under the applicable contract.

### 4.4. `ContextClosedEvent`

Published when the context is **closed** via `close()` or a shutdown hook. This is the context-closing milestone in Spring Framework; Boot applications receive it too when Boot's context closes.

Do not use `ContextClosedEvent` to infer a "startup failed" cause: a context can close due to normal shutdown, test completion, or after an error, so it must be distinguished from `ApplicationFailedEvent`.

~~~text
Plain Spring Framework context:
    new AnnotationConfigApplicationContext()
              |
              +--> refresh() --> ContextRefreshedEvent
              +--> start()   --> ContextStartedEvent
              +--> stop()    --> ContextStoppedEvent
              +--> close()   --> ContextClosedEvent

Standard Spring Boot run:
    SpringApplication.run()
              |
              +--> create/refresh context --> ContextRefreshedEvent
              +--> ApplicationStartedEvent
              +--> runners
              +--> ApplicationReadyEvent

    (There is no automatic call to context.start() when Boot is started.)
~~~

## 5. "Similar Names, Different Meanings" Table

| Commonly Confused Pair | Key Difference |
| --- | --- |
| `ApplicationStartingEvent` vs `ApplicationStartedEvent` | Boot **beginning startup** vs Boot **having refreshed the context** |
| `ApplicationStartedEvent` vs `ContextStartedEvent` | **Boot before runners** vs **Framework upon calling `context.start()`** |
| `ApplicationReadyEvent` vs `ContextRefreshedEvent` | Boot **after runners** vs Framework **after refresh** |
| `ApplicationFailedEvent` vs `ContextClosedEvent` | Boot **startup failure** vs Framework **context closing** (which can be completely normal) |
| `ApplicationPreparedEvent` vs `ContextRefreshedEvent` | Boot **before refresh**, bean definitions loaded, vs Framework **after refresh** |
| `ApplicationContextInitializedEvent` vs `ContextRefreshedEvent` | Boot right past initializers, **bean definitions not yet loaded**, vs context **refreshed** |
| `AvailabilityChangeEvent` vs `ApplicationReadyEvent` | Availability describes **state** (liveness/readiness), which can change; Ready describes a **startup milestone** |
| Events via `ApplicationContext.publishEvent(...)` vs `ApplicationContextEvent` subclasses | The former is a **publishing mechanism** for all event types; the latter is a **type family** dedicated to context lifecycle |

Several names contain the word `Application`, yet still differ in package, timing, event source, and responsible publisher.

## 6. Listener Registration: @EventListener, ApplicationListener, and Events Arriving Too Early

### 6.1. Listener as a Spring Bean

For events occurring **after the context refreshes**, a bean can be used:

~~~java
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.context.event.ContextRefreshedEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;

@Component
public class LifecycleObservers {

    @EventListener
    public void onContextRefresh(ContextRefreshedEvent event) {
        // Framework context has refreshed.
    }

    @EventListener
    public void onBootReady(ApplicationReadyEvent event) {
        // Spring Boot has finished running runners.
    }
}
~~~

This is an **integration code snippet**, not yet a standalone program. Once the class is component-scanned and the listener bean is registered, the two methods receive the exact event types. Prefer methods with specific parameter types instead of receiving a generic `ApplicationEvent` and guessing by name.

### 6.2. Listener Needing Very Early Boot Events

`ApplicationStartingEvent` and `ApplicationEnvironmentPreparedEvent` arrive **before Spring creates context beans**. At that point, an `@EventListener` method in a bean **does not exist yet**, so it cannot receive these early events in the usual way.

Register an `ApplicationListener` directly **before running** `SpringApplication`:

~~~java
SpringApplication app = new SpringApplication(DemoApplication.class);

app.addListeners(
    (ApplicationListener<ApplicationStartingEvent>) event ->
        System.out.println("Boot starting"),
    (ApplicationListener<ApplicationEnvironmentPreparedEvent>) event ->
        System.out.println("Environment prepared")
);

app.run(args);
~~~

This is an illustrative snippet requiring imports and the `DemoApplication` class; a complete example is in section 7.

You can register via `SpringApplicationBuilder.listeners(...)` or via `META-INF/spring.factories` so Boot automatically finds the listener by key:

~~~properties
org.springframework.context.ApplicationListener=example.BootEarlyListener
~~~

`BootEarlyListener` must be a class implementing `ApplicationListener` with the appropriate event type and a constructor instantiable by the loading mechanism. This is an **illustrative configuration line**; there is no need to create `spring.factories` for the full runnable example below because it uses `addListeners(...)`.

**Limitation:** early-running listeners must not assume `@Autowired` application beans, repositories, or transactions exist. Use only information already available at that event's timing (for example, `Environment` in `ApplicationEnvironmentPreparedEvent`), and keep tasks lightweight.

### 6.3. Listeners After Refresh

`ApplicationStartedEvent`, `ApplicationReadyEvent`, and `ContextRefreshedEvent` normally arrive once listener beans have been recognized. `@EventListener` can handle these events.

`ApplicationFailedEvent` is a special case: startup errors can happen **before beans exist**, so if you need to track errors across all startup stages, use an early-registered listener via `addListeners(...)` or an equivalent mechanism; do not rely solely on `@EventListener` beans.

## 7. Runnable Java 17+ Example: Seeing Both Event Categories in One Boot Run

The example below runs **Spring Boot 3.3.13**, using `WebApplicationType.NONE` so no web server is needed. It registers two early Boot listeners via `SpringApplication.addListeners(...)`; at the same time it defines a Spring bean containing listeners for `ContextRefreshedEvent`, `ApplicationStartedEvent`, `ApplicationReadyEvent`, `ContextStartedEvent`, `ContextStoppedEvent`, and `ContextClosedEvent`. After Boot is ready, the code **explicitly** calls `context.start()`, `stop()`, and `close()` to contrast the true meaning of context events.

### 7.2. Complete Source Code

`src/main/java/example/BootVsContextEventsDemo.java`:

~~~java
package example;

import org.springframework.boot.Banner;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.event.ApplicationEnvironmentPreparedEvent;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.boot.context.event.ApplicationStartedEvent;
import org.springframework.boot.context.event.ApplicationStartingEvent;
import org.springframework.context.ApplicationListener;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.event.ContextClosedEvent;
import org.springframework.context.event.ContextRefreshedEvent;
import org.springframework.context.event.ContextStartedEvent;
import org.springframework.context.event.ContextStoppedEvent;
import org.springframework.context.event.EventListener;

@SpringBootApplication(proxyBeanMethods = false)
public class BootVsContextEventsDemo {

    @Bean
    public LifecycleObservers lifecycleObservers() {
        return new LifecycleObservers();
    }

    @Bean
    public CommandLineRunner runner() {
        return args -> System.out.println("runner: executed");
    }

    public static final class LifecycleObservers {

        @EventListener
        public void onContextRefreshed(ContextRefreshedEvent event) {
            System.out.println("context: refreshed");
        }

        @EventListener
        public void onBootStarted(ApplicationStartedEvent event) {
            System.out.println("boot: started");
        }

        @EventListener
        public void onBootReady(ApplicationReadyEvent event) {
            System.out.println("boot: ready");
        }

        @EventListener
        public void onContextStarted(ContextStartedEvent event) {
            System.out.println("context: started (explicit)");
        }

        @EventListener
        public void onContextStopped(ContextStoppedEvent event) {
            System.out.println("context: stopped (explicit)");
        }

        @EventListener
        public void onContextClosed(ContextClosedEvent event) {
            System.out.println("context: closed");
        }
    }

    public static void main(String[] args) {
        SpringApplication application =
                new SpringApplication(BootVsContextEventsDemo.class);

        application.setWebApplicationType(WebApplicationType.NONE);
        application.setBannerMode(Banner.Mode.OFF);
        application.setLogStartupInfo(false);

        // Register before run(): receives very early Boot events.
        application.addListeners(
            (ApplicationListener<ApplicationStartingEvent>) event ->
                System.out.println("boot: starting"),
            (ApplicationListener<ApplicationEnvironmentPreparedEvent>) event ->
                System.out.println("boot: environment prepared")
        );

        ConfigurableApplicationContext context = application.run(args);

        // The next three operations are called explicitly to trigger context events.
        context.start();
        context.stop();
        context.close();
    }
}
~~~

### 7.3. Running the Program

In the `boot-context-events-demo` directory, with JDK 17+ and Gradle installed:

~~~bash
gradle bootRun
~~~

Or use the Gradle Wrapper if configured in the project: `./gradlew bootRun` on Linux/macOS or `gradlew.bat bootRun` on Windows.

Lines **explicitly printed by `System.out.println(...)` statements in the source code**, in order:

~~~text
boot: starting
boot: environment prepared
context: refreshed
boot: started
runner: executed
boot: ready
context: started (explicit)
context: stopped (explicit)
context: closed
~~~

Gradle, logging library, and framework logs may appear interleaved depending on the environment. Therefore, the output above does not claim total stdout of a run consists of only nine lines, but rather shows **the order of demo lines to observe**.

### 7.4. Why Does the Output Accurately Demonstrate the Difference?

- The two lines `boot: starting` and `boot: environment prepared` appear because listeners were registered directly on `SpringApplication` **before the context was created**, not as beans.
- `context: refreshed` arrives before `boot: started` because Framework refreshes the context first, and only then does Boot announce started.
- `boot: started` arrives **before** `runner: executed`; this matches the `ApplicationStartedEvent` contract.
- `boot: ready` arrives **after** `runner: executed`, clearly showing why `ApplicationReadyEvent` cannot be replaced by `ContextRefreshedEvent`.
- `context: started (explicit)` and `context: stopped (explicit)` exist solely because `main` itself called `context.start()` and `context.stop()`. Boot starting up **does not implicitly publish these events**.
- `context: closed` shows the context closing after `main` calls `close()`, not a startup failure.

If you remove the last three calls `start()`, `stop()`, `close()`, the program will no longer emit the start/stop context events along this path. A shutdown hook may still close the context when the JVM exits and generate `ContextClosedEvent`; the timing of closure then differs from the explicit calls in the demo.

## 8. Plain ApplicationContext Still Has Context Events, Without Boot

This is illustrative code using **Spring Framework** and registering listeners before refresh:

~~~java
import org.springframework.context.ApplicationListener;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.event.ContextClosedEvent;
import org.springframework.context.event.ContextRefreshedEvent;

AnnotationConfigApplicationContext context =
        new AnnotationConfigApplicationContext();

context.addApplicationListener(
        (ApplicationListener<ContextRefreshedEvent>) event ->
                System.out.println("framework: refreshed"));

context.addApplicationListener(
        (ApplicationListener<ContextClosedEvent>) event ->
                System.out.println("framework: closed"));

context.refresh();
context.close();
~~~

This is an **illustrative code snippet needing placement inside a Java method with `spring-context` dependency**, not yet a standalone program. It demonstrates that `ContextRefreshedEvent` and `ContextClosedEvent` can work **without any `SpringApplication`**. Thus there will be no `ApplicationStartingEvent`, `ApplicationStartedEvent`, or `ApplicationReadyEvent` in this plain context example.

Spring Boot is simply one way to build and run a Spring application; the foundational context lifecycle is still executed by Spring Framework.

## 9. What Information Can Be Retrieved from Each Event?

### 9.1. Boot Events

Events under `SpringApplicationEvent` can provide the `SpringApplication` instance and run arguments via `getSpringApplication()` and `getArgs()`. Each subclass may provide additional information:

- `ApplicationEnvironmentPreparedEvent#getEnvironment()`: `Environment` is ready, while context has not yet been created.
- `ApplicationContextInitializedEvent#getApplicationContext()`: context has been processed by initializers, before loading bean definitions.
- `ApplicationPreparedEvent#getApplicationContext()`: context prepared, not yet refreshed.
- `ApplicationStartedEvent#getApplicationContext()`: context refreshed.
- `ApplicationReadyEvent#getApplicationContext()`: context after runners.
- `ApplicationFailedEvent#getException()`: error cause. `getApplicationContext()` **may be null** if failure occurred too early.

Do not call `getBean(...)` when the event is at a pre-refresh stage without a real need and clear understanding of limitations. The fact that a context object **already exists** does not mean all beans have finished initializing.

### 9.2. Context Events

`ApplicationContextEvent` has `getApplicationContext()` returning the source context; subclasses such as `ContextRefreshedEvent` also have this method.

When **parent/child contexts** exist, context events from a child can be propagated up to the parent. A listener in the parent may therefore see multiple events of the same type belonging to different contexts.

If a listener needs to distinguish contexts:

~~~java
@EventListener
public void onRefresh(ContextRefreshedEvent event) {
    if (event.getApplicationContext() != this.applicationContext) {
        return; // Ignore events from child contexts.
    }

    // Handle events published by the current context itself.
}
~~~

This is an **illustrative snippet**, assuming the listener class was injected with an `applicationContext` field of type `ApplicationContext`. Only use identity comparison when you need to exclude child context events; do not automatically filter every event when a single-context application lacks that duplication issue.

## 10. Which Event Should You Choose for Each Need?

| Practical Need | Recommended Event/Mechanism |
| --- | --- |
| Read/adjust `Environment` very early | `ApplicationEnvironmentPreparedEvent`, listener registered before `run()` |
| Work with initializers / stage before loading bean definitions | `ApplicationContextInitializedEvent` and appropriate initializer mechanism |
| Observe context finishing refresh | `ContextRefreshedEvent` |
| Work after refresh but before runners | `ApplicationStartedEvent` |
| Run an explicitly ordered task at startup | `ApplicationRunner` or `CommandLineRunner` |
| Observe Boot finishing runners | `ApplicationReadyEvent` |
| Check whether service can accept traffic | `AvailabilityChangeEvent` / `ApplicationAvailability` and readiness state |
| Start/stop beans via explicit lifecycle | `ContextStartedEvent`/`ContextStoppedEvent` when genuinely using `start()`/`stop()` |
| Release resources when context closes | `ContextClosedEvent` or appropriate lifecycle callback such as `@PreDestroy` |
| Collect all startup failures even before beans exist | Early-registered `ApplicationFailedEvent` listener |
| Propagate business event "order created" | Custom business event via `ApplicationEventPublisher`; do not misuse Boot lifecycle events |

Note: long startup work inside a listener can **block the startup thread** under synchronous dispatch. Do not turn `ApplicationReadyEvent` into a place executing tasks so long that the application takes excessive time to finish starting up. For specific orchestration needs, runners, lifecycle components, or a dedicated scheduler/worker may be clearer.

## 11. Failure Cases and Common Misconceptions

| Misconception / Error | Correct Understanding |
| --- | --- |
| `ApplicationStartedEvent` is equivalent to `ContextStartedEvent` | Two classes in different packages and semantics: Boot after refresh before runners; context event on `start()` |
| `ContextRefreshedEvent` means Boot is ready to receive requests | No, Boot runners may still be pending; check `ApplicationReadyEvent` and readiness |
| Adding `@EventListener(ApplicationStartingEvent.class)` to a bean catches the early event | The bean is not created yet at that moment; use `SpringApplication.addListeners(...)` or `spring.factories` |
| `ApplicationPreparedEvent` arrives after refresh | It arrives **before** refresh |
| `ApplicationContextInitializedEvent` means all beans are initialized | Not yet; bean definitions have not been loaded |
| `ApplicationReadyEvent` is always published even if startup fails | No; if startup fails, Boot may publish `ApplicationFailedEvent` |
| `ApplicationFailedEvent#getApplicationContext()` is always non-null | May be null if failure occurs before context creation |
| Every `ApplicationEvent` is an `ApplicationContextEvent` | False; `SpringApplicationEvent` and business events can be separate branches |
| Boot has a general `ApplicationStoppedEvent` for every stop | No equivalent standard event in this core lifecycle set; use context close/stop as appropriate |
| `ContextStartedEvent` fires automatically whenever the JVM runs Boot | Only when the context receives a `start()` call per the Framework contract |
| `@Order` makes Boot ready before Context refresh | `@Order` only affects listener ordering for **the same event**, without inverting the lifecycle |
| Event listeners guarantee asynchronous execution | By default event listeners usually run synchronously; configure async if needed and understand completion ordering |
| Receiving an event twice is definitely a bug | May be due to parent/child contexts, multiple contexts, or multiple runs; check `getApplicationContext()` and event source |
| Event listeners can replace durable messaging | Spring application events are mainly an internal mechanism; they do not persist across restarts or retry like brokers/outboxes |

### Exceptions in Listeners

With the default synchronous multicasting mechanism, an unhandled exception from a listener can propagate back to the event publisher and affect startup. Therefore:

- Even an `ApplicationReadyEvent` listener can cause startup to report failure if it throws an exception during the same publishing call.
- Very early listeners should not run error-prone tasks or depend on uncreated beans.
- If configuring an async multicaster, completion order and error paths change; **do not infer Boot finished an async task merely because the event was published**.

## 12. Diagnosing When a Listener Does Not Run

Check step by step:

1. **Which event are you actually listening to?** Check the full class name and imports; Boot's `ApplicationStartedEvent` differs from Framework's `ContextStartedEvent`.
2. **Does the event occur before or after the listener bean is created?** For early events, register directly via `addListeners(...)`.
3. **Does the application run via `SpringApplication.run(...)`?** A plain Spring Framework context does not publish all Boot startup events.
4. **Did you call `context.start()` or `context.stop()`?** If not, do not expect `ContextStartedEvent`/`ContextStoppedEvent` to occur on their own.
5. **Did a runner block or throw an error?** In that case `ApplicationStartedEvent` may have occurred while `ApplicationReadyEvent` has not.
6. **Are there parent/child contexts?** Events propagated to the parent can cause a listener to receive them multiple times.
7. **Is the listener a bean / properly registered?** `@EventListener` must belong to a Spring-discovered bean, while early `ApplicationListener`s must be registered before `run()`.
8. **Is asynchronicity involved?** Log lines from multiple threads do not necessarily preserve completion order even though lifecycle events have a publication order.
9. **Was the application closed immediately?** Identify when the context closes and whether runners ran before/after the event to avoid misinterpretation.

To observe behavior, log **event name, context ID (if present), thread name, and timestamp**. Limit writing sensitive data from Environment/command-line arguments into logs.

## 13. How to Test Ordering Reliably

For Boot applications, an integration test aiming to prove ordering must actually **run `SpringApplication`** with listeners registered before startup. Do not instantiate `ApplicationContext` and call `onBootReady(...)` directly, as that does not verify Boot publishes the event at the right lifecycle point.

You can use a thread-safe collector:

~~~java
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

List<String> trace = new CopyOnWriteArrayList<>();

SpringApplication application = new SpringApplication(DemoApplication.class);
application.setWebApplicationType(WebApplicationType.NONE);
application.addListeners(
    (ApplicationListener<ApplicationStartingEvent>) event ->
        trace.add("starting"),
    (ApplicationListener<ApplicationEnvironmentPreparedEvent>) event ->
        trace.add("environment")
);
~~~

This is an **illustrative snippet for collecting evidence**, requiring `DemoApplication`/imports and an `application.run(...)` invocation to execute. To measure `ContextRefreshedEvent` and `ApplicationReadyEvent` with a bean, share the same collector injected/registered from appropriate configuration. Do not wire two independent collectors and compare two logs lacking a common anchor.

Essential checks:

- Register before `run()` and assert `ApplicationStartingEvent` and `ApplicationEnvironmentPreparedEvent` occur.
- Use bean listeners to receive `ContextRefreshedEvent`, `ApplicationStartedEvent`, and `ApplicationReadyEvent`; assert relative order: **refreshed → started → runner → ready**.
- Without calling `context.start()`, **do not expect** `ContextStartedEvent` merely because Boot started.
- Explicitly call `start()`, `stop()`, `close()` to assert the corresponding events.
- Create a runner throwing a controlled exception in a separate test to assert `ApplicationFailedEvent` occurs and `ApplicationReadyEvent` is never reached; the test must handle/close the context safely.
- When using parent–child contexts, assert that listeners filter by context identity if required.

**Note on `@SpringBootTest`:** the test context may be cached and initialization is coordinated by the test framework. If the goal is testing **early events before beans are created**, a test that only autowires a listener into the test class after startup makes a poor oracle for already-occurred events. Register the listener before calling `SpringApplication.run(...)` in a controlled integration test, or use a startup recorder initialized at the right moment.

## 14. Self-Check Questions

**Question 1.** Are `ApplicationStartedEvent` and `ContextStartedEvent` both published when a Spring Boot application opens up?

**Answer:** No. Boot publishes `ApplicationStartedEvent` after refresh, before runners; `ContextStartedEvent` only appears if `ConfigurableApplicationContext.start()` is called.

**Question 2.** To execute a block of code after all `CommandLineRunner`s complete, which event should you listen to?

**Answer:** `ApplicationReadyEvent`. However, if that code is an ordered business startup step or requires retries, a dedicated runner/workflow mechanism may be more appropriate.

**Question 3.** Does `ContextRefreshedEvent` occur in a Spring Framework application that does not use Boot?

**Answer:** Yes. The event is emitted by the context lifecycle; `SpringApplication` is not required.

**Question 4.** Can you catch `ApplicationEnvironmentPreparedEvent` with an `@EventListener` method on an ordinary component bean?

**Answer:** Not in the normal way, because this event occurs before the context/beans are created; you must register an `ApplicationListener` early via `addListeners(...)`, builder, or `spring.factories`.

**Question 5.** A runner throws an exception before finishing. Is it possible that `ApplicationStartedEvent` already occurred while `ApplicationReadyEvent` did not?

**Answer:** Yes. Started occurs before runners, Ready after runners; failure may be published when startup fails.

**Question 6.** In `ContextRefreshedEvent`, which method reveals the actual source context?

**Answer:** `event.getApplicationContext()`. It can be used to check identity when an application has multiple contexts.

**Question 7.** Does Boot share Spring Framework's `ApplicationEventPublisher` and listener mechanism?

**Answer:** Yes. The difference lies primarily in origin/lifecycle milestones and classes, not that every Boot event travels through an entirely different bus.
