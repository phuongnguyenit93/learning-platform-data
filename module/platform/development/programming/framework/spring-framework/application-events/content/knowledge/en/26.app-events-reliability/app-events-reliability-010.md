# Tracking Event Processing State in Spring Framework Application Events

Calling `ApplicationEventPublisher.publishEvent(event)` **is not proof that every listener succeeded in handling the event**. A listener may merely be scheduled on an executor, run after transaction commit, throw an exception, get killed by a process crash, or need to retry. In critical business flows, we need to know which step an event is on, which handler finished, which handler failed, whether work is stuck, and whether it can be safely reprocessed.

**Tracking event processing state** means designing a lifecycle with identities, state records, state transition rules, attempt history, and recovery mechanisms. This differs from merely logging `"event received"` or counting how many times `publishEvent` was called. In particular, the same event can go to **multiple listeners**, so the state of the event and the state of **each processing target** must be separated.

This lesson focuses on the reliability of Spring Application Events: the `PENDING → PROCESSING → SUCCEEDED/FAILED → DEAD` model, transaction boundaries, atomic claims, retries, leases, idempotency, observability, and Spring Modulith's Event Publication Registry. At the end is a Java 17+ integration test using Spring Framework, JDBC, H2, and JUnit 5 illustrating the flow **register publication in business transaction → handle AFTER_COMMIT → update status in a separate transaction → retry**.

## 1. What State Needs Tracking?

An event might carry ID `evt-103` of type `order.paid`. Suppose three independent handlers care about this event:

~~~text
                       OrderPaid(evt-103)
                              |
               +--------------+---------------+
               |              |               |
           invoice         email           analytics
           SUCCEEDED       FAILED          PROCESSING
~~~

Saying `evt-103 = DONE` is ambiguous. Invoice finished, email failed to send, and analytics is still running. A practical design tracks status by **(event_id, handler_id)** or by a unique `publication_id` representing that pair.

| Object | Meaning | Example |
| --- | --- | --- |
| **Event** | A single created logical event | `event_id=evt-103`, `event_type=order.paid` |
| **Publication / delivery target** | Delivering the event to a specific handler | `(evt-103, email)` |
| **Attempt** | One try running the publication's handler | Attempt 1 failed, attempt 2 succeeded |
| **Outcome** | Result of an attempt or final state | `FAILED`, `SUCCEEDED`, `DEAD` |
| **Checkpoint/lease** | Worker coordination info when work may take time | `claimed_by`, `lease_until`, `version` |

Handler identities must stay stable across deployments if you want to recover old publications. Do not use autogenerated bean names or class names that can change freely on refactoring without a migration plan. Once a handler succeeds, replays of the same logical event **must not create side effects again**.

### Published, Dispatched, Processed, and Committed Are Not Synonymous

- `PUBLISHED`: code requested publishing or the publication was persisted, per the system's definition.
- `DISPATCHED`: a task was handed to an executor/broker; the handler has not necessarily started.
- `PROCESSING`: a handler/worker claimed and started an attempt.
- `SUCCEEDED`: work was confirmed successful by the handler under its contract.
- `COMMITTED`: a specific database transaction committed; not automatically synonymous with all handlers completing.
- `ACKNOWLEDGED`: a specific target acknowledged per API, not implicitly "the end user received the notification".

Status names carry no magic guarantees. **Every transition must be tied to a verifiable real event.**

## 2. Minimal Lifecycle Model

A state machine can start as follows:

~~~text
CREATE event + publication
         |
         v
      PENDING ----------------------+
         |                         |
    claim/lease                     |
         v                         |
     PROCESSING                     |
      /      \                      |
  success    failure/crash           |
    |          |                    |
    v          v                    |
 SUCCEEDED    FAILED --retry------+
               |
        max attempts /
        non-retryable error
               |
               v
              DEAD

PROCESSING past lease expiry -> mark stale and reclaim
(only when safe fencing/recovery mechanisms exist)
~~~

You may name `SUCCEEDED` as `COMPLETED` or `DEAD` as `DEAD_LETTERED`; the core point is **defining state transitions and retry contracts**.

| State | Meaning | Should it auto-run further? |
| --- | --- | --- |
| `PENDING` | Valid publication exists, awaiting handler claim | Yes, when due |
| `PROCESSING` | A worker has claimed an attempt | Do not claim concurrently while lease is valid |
| `SUCCEEDED` | Handler finished per defined contract | Do not retry side effects |
| `FAILED` | Attempt failed; still eligible for retry | Yes, per `next_attempt_at` and backoff |
| `DEAD` | Retries exhausted or permanent error | Do not auto-retry; needs operator/reconciliation |
| `CANCELLED` (optional) | Business command canceled the remaining work | Only when policy permits |

**Distinguish transient errors from permanent errors.** Gateway timeouts and HTTP 503 can be retried; payloads violating schemas or deleted destinations may need `DEAD` immediately. Not every exception deserves 100 retries.

## 3. Required Data Fields

A publication tracking table may contain:

| Field | Role |
| --- | --- |
| `publication_id` | Unique ID per publication |
| `event_id` | Stable ID of the logical event across retries |
| `event_type` | Event type with explicit version/schema |
| `handler_id` | Processing target, e.g., `send-receipt-email` |
| `status` | Current status |
| `attempts` | Number of claimed/started attempts |
| `created_at` | When the publication was registered |
| `started_at` | When the latest attempt started |
| `completed_at` | When processing succeeded |
| `next_attempt_at` | Earliest time a retry may run |
| `lease_until` | Claim expiry to detect abandoned workers |
| `claimed_by` | Identity of the worker currently holding the claim |
| `version` / `fencing_token` | Prevents an old worker from overwriting a new worker's result |
| `last_error_code` | Categorized error code scrubbed of sensitive data |
| `correlation_id` | Links related logs and traces |
| `payload_ref` or small payload | How a worker reconstructs the work to retry |

A unique constraint on `(event_id, handler_id)` prevents creating multiple publications to the same target for the same logical event. However, if the system **intentionally processes the same event multiple times** due to distinct handler configurations, define the matching uniqueness key; never drop unique constraints arbitrarily.

### Reference SQL Schema

This is a **suggested schema**, not Spring Modulith's automatic schema:

~~~sql
CREATE TABLE event_publication (
  publication_id VARCHAR(64) PRIMARY KEY,
  event_id VARCHAR(64) NOT NULL,
  handler_id VARCHAR(100) NOT NULL,
  event_type VARCHAR(120) NOT NULL,
  status VARCHAR(24) NOT NULL,
  attempts INTEGER NOT NULL DEFAULT 0,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  started_at TIMESTAMP NULL,
  completed_at TIMESTAMP NULL,
  next_attempt_at TIMESTAMP NULL,
  lease_until TIMESTAMP NULL,
  claimed_by VARCHAR(100) NULL,
  fencing_token BIGINT NOT NULL DEFAULT 0,
  last_error_code VARCHAR(100) NULL,
  correlation_id VARCHAR(100) NULL,
  UNIQUE (event_id, handler_id),
  CHECK (attempts >= 0)
);
~~~

The schema above needs migrations/indexes suited to the real DB. For instance, workers need indexes on `(status, next_attempt_at)` or `(status, lease_until)` to fetch due publications, rather than indexing only `event_id` and scanning the table. Table names, column lengths, timestamp/timezone handling, and lock strategies must be verified against the target database.

**Never store serialized credentials or full JPA managed objects in the publication table.** If retries need data as of event creation time, store a small immutable snapshot or a durable reference with versioning/checksums/access control. If a worker only reloads by aggregate ID, data may have changed since the initial publish.

## 4. Transaction Boundary: Register First, Process After Commit

Most common problem: a service writes an order and publishes an event in a transaction, then a listener runs `@Async` or `AFTER_COMMIT`. If the app dies **after DB commit but before the async task is scheduled**, in-memory logs alone are not enough to know work was missed.

~~~text
BEGIN transaction
  UPDATE orders
  INSERT event_publication(event_id, handler_id, PENDING)
COMMIT
  |
  +-- after commit: attempt to dispatch handler
         |
         +-- on success: PROCESSING -> SUCCEEDED
         +-- on error: PROCESSING -> FAILED
         +-- on crash before dispatch: publication stays PENDING
~~~

That is why **transactional registration** matters: the publication row and the business change commit together, or roll back together. Workers/recovery tools can scan outstanding publications to execute later. Conversely, calling `publishEvent` **does not automatically create a durable publication record** in plain Spring Framework.

`@TransactionalEventListener(phase = AFTER_COMMIT)` lets the listener start in the right transaction phase, yet **on its own it creates neither a durable queue nor post-crash retries**. If the callback throws an exception, the already-committed source transaction cannot be undone. If after-commit handling needs to **persist a new DB status**, open an appropriate new transaction (e.g., `REQUIRES_NEW` or an equivalent `TransactionTemplate`). Old transaction resources may still be bound during the callback, with no subsequent commit.

In applications without a transaction at publish time, `@TransactionalEventListener` **does not run** by default unless `fallbackExecution=true` is configured. Therefore, test events both inside and outside transactions.

## 5. Safe State Transitions with Multiple Workers

A worker must never read `status=PENDING` and then update to `PROCESSING` in two unprotected steps, because two workers can both read `PENDING` and both process it.

**Atomic claim** pattern with state conditions:

~~~sql
UPDATE event_publication
   SET status = 'PROCESSING',
       attempts = attempts + 1,
       started_at = CURRENT_TIMESTAMP,
       claimed_by = :worker_id,
       lease_until = :lease_until,
       fencing_token = fencing_token + 1
 WHERE publication_id = :publication_id
   AND status IN ('PENDING', 'FAILED')
   AND (next_attempt_at IS NULL OR next_attempt_at <= CURRENT_TIMESTAMP)
   AND attempts < :max_attempts;
~~~

A worker processes only when the UPDATE affects **exactly one row**. Another worker seeing 0 affected rows must skip. This is a conceptual SQL pattern using named parameters and cannot run directly on every JDBC client without binding them. Under high volume, claiming can use `SELECT ... FOR UPDATE SKIP LOCKED`, optimistic locking, or DB-specific atomic update/returning; test on the real DB's isolation level.

### When a Worker Crashes in PROCESSING

A `PROCESSING` status can persist forever if the process dies without running `catch/finally`. The system needs a **lease timeout** or stale-publication monitor. However, simply moving expired `PROCESSING` rows back to `FAILED` is not enough: the old slow worker might wake up and send a side effect after a new worker already claimed it.

Mitigations by severity:

1. `lease_until` defines when a claim may be considered expired.
2. `fencing_token` increments on every claim; every result update must carry the held token.
3. An old worker with a stale token cannot overwrite the new owner's status.
4. For side effects outside the DB, DB fencing **cannot stop** a request already sent to an external system; use downstream idempotency keys whenever possible.
5. For long processing, use a heartbeat to renew the lease; if renewal fails, halt or finish the attempt per policy.

Example conditional update:

~~~sql
UPDATE event_publication
   SET status = 'SUCCEEDED', completed_at = CURRENT_TIMESTAMP
 WHERE publication_id = :publication_id
   AND status = 'PROCESSING'
   AND claimed_by = :worker_id
   AND fencing_token = :expected_token;
~~~

If affected rows = 0, the worker must record a stale claim/concurrency conflict and never report fake success. Do not use `UPDATE ... WHERE event_id=?` omitting handler and token in a multi-consumer system.

## 6. Retries, Idempotency, and Delivery Semantics

**At-least-once** means a handler can receive a logical event multiple times, especially when it finishes the side effect and the process crashes **before recording `SUCCEEDED`**. Thus, publication tracking does not eliminate the need for **idempotency**.

~~~text
Worker claims event X (attempt 1)
  -> sends email/payment request successfully
  -> process crashes before marking SUCCEEDED

Recovery sees incomplete publication
  -> retries event X (attempt 2)
  -> risk of duplicate send
~~~

Strategies:

- Provide a stable idempotency key per `(event_id, handler_id)` to gateways/brokers that support it.
- For side effects in the same database, use a `processed_event` table with a unique constraint, checking and updating business state in the same transaction.
- For HTTP/email side effects lacking idempotency support, accept/reconcile duplicates or build locking/ledger mechanisms and duplicate-handling procedures.
- Retry using exponential backoff + jitter, `next_attempt_at`, and `max_attempts`; classify retryable vs. permanent errors.
- After `DEAD`, have dashboards, alerts, classification reasons, and controlled manual handling/replay workflows.

An idempotency key **must not change across attempts** when the goal is preventing duplicate processing of the same event. Nor should a key be reused for **two distinct business actions**. Define identity before choosing policy.

### Why Can't End-to-End Exactly-Once Be Claimed?

A DB transaction and an out-of-process API normally do not share a single atomic commit. Application events + a `SUCCEEDED` status alone cannot guarantee an email/charge/HTTP request happened strictly once. You can achieve an "effectively exactly-once" outcome **for a specific side effect** with the right protocol/idempotent sink, but you must evaluate every boundary and failure window.

## 7. Java 17+ Integration Test: Spring Events and Publication State in H2

This example demonstrates a **minimal hand-rolled registry** to understand the principles; it **does not replace Spring Modulith** and does not yet include leases/schedulers for automatic recovery. The status table is written inside the business transaction, while the listener is `@TransactionalEventListener(AFTER_COMMIT)`. Listener status updates use `TransactionTemplate` with `PROPAGATION_REQUIRES_NEW` so data commits independently after the source transaction.

The test suite verifies: successful commit, rollback creating no publication, safe failure and retry on the same event ID, and transitioning to `DEAD` when attempts are exhausted. The gateway here is a controllable fake; real gateways need idempotency.

### 7.2. File src/test/java/example/events/EventStatusTrackingTest.java

~~~java
package example.events;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;
import javax.sql.DataSource;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DriverManagerDataSource;
import org.springframework.test.context.junit.jupiter.SpringJUnitConfig;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;
import org.springframework.transaction.support.TransactionTemplate;

@SpringJUnitConfig(EventStatusTrackingTest.Config.class)
class EventStatusTrackingTest {

    @Autowired JdbcTemplate jdbc;
    @Autowired PublisherService publisherService;
    @Autowired DeliveryHandler handler;
    @Autowired Registry registry;
    @Autowired FakeGateway gateway;

    @BeforeEach
    void reset() {
        jdbc.execute(
            "CREATE TABLE IF NOT EXISTS work_item (" +
            "id VARCHAR(64) PRIMARY KEY)"
        );
        jdbc.execute(
            "CREATE TABLE IF NOT EXISTS event_state (" +
            "event_id VARCHAR(64) NOT NULL," +
            "handler VARCHAR(40) NOT NULL," +
            "status VARCHAR(24) NOT NULL," +
            "attempts INT NOT NULL," +
            "last_error VARCHAR(120)," +
            "updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP," +
            "PRIMARY KEY(event_id, handler))"
        );
        jdbc.update("DELETE FROM event_state");
        jdbc.update("DELETE FROM work_item");
        gateway.reset();
    }

    @Test
    void successfulCommitIsTracked() {
        publisherService.create("e-success", false);

        assertEquals("SUCCEEDED", registry.status("e-success"));
        assertEquals(1, registry.attempts("e-success"));
        assertEquals(1, registry.itemCount("e-success"));
        assertEquals(1, gateway.calls());
    }

    @Test
    void rollbackRemovesBusinessDataAndPendingPublication() {
        assertThrows(
            IllegalStateException.class,
            () -> publisherService.create("e-rollback", true)
        );

        assertEquals(0, registry.itemCount("e-rollback"));
        assertEquals(0, registry.publicationCount("e-rollback"));
        assertEquals(0, gateway.calls());
    }

    @Test
    void failedAttemptCanBeRetriedWithoutNewPublication() {
        gateway.failNext();
        publisherService.create("e-retry", false);

        assertEquals("FAILED", registry.status("e-retry"));
        assertEquals(1, registry.attempts("e-retry"));

        // In production, a scheduler/recovery worker would do this.
        handler.retry("e-retry");

        assertEquals("SUCCEEDED", registry.status("e-retry"));
        assertEquals(2, registry.attempts("e-retry"));
        assertEquals(1, registry.publicationCount("e-retry"));
        assertEquals(2, gateway.calls());
    }

    @Test
    void repeatedFailureStopsAtMaxAttempts() {
        gateway.setAlwaysFail(true);
        publisherService.create("e-dead", false);
        handler.retry("e-dead");
        handler.retry("e-dead");
        handler.retry("e-dead");

        assertEquals("DEAD", registry.status("e-dead"));
        assertEquals(3, registry.attempts("e-dead"));
        assertEquals(3, gateway.calls());
    }

    record WorkAccepted(String eventId) { }

    static class FakeGateway {
        private final AtomicBoolean failNext = new AtomicBoolean();
        private final AtomicBoolean alwaysFail = new AtomicBoolean();
        private final AtomicInteger calls = new AtomicInteger();

        void failNext() {
            failNext.set(true);
        }

        void setAlwaysFail(boolean value) {
            alwaysFail.set(value);
        }

        void reset() {
            failNext.set(false);
            alwaysFail.set(false);
            calls.set(0);
        }

        int calls() {
            return calls.get();
        }

        void send(String eventId) {
            calls.incrementAndGet();
            if (alwaysFail.get() || failNext.getAndSet(false)) {
                throw new IllegalStateException("gateway-unavailable");
            }
        }
    }

    static class Registry {
        private final JdbcTemplate jdbc;
        private final TransactionTemplate statusTx;

        Registry(JdbcTemplate jdbc, TransactionTemplate statusTx) {
            this.jdbc = jdbc;
            this.statusTx = statusTx;
        }

        int claim(String eventId) {
            return statusTx.execute(status -> jdbc.update(
                "UPDATE event_state SET status='PROCESSING'," +
                "attempts=attempts+1, updated_at=CURRENT_TIMESTAMP " +
                "WHERE event_id=? AND handler='email' " +
                "AND status IN ('PENDING','FAILED') AND attempts<3",
                eventId
            ));
        }

        void success(String eventId) {
            statusTx.executeWithoutResult(status -> jdbc.update(
                "UPDATE event_state SET status='SUCCEEDED'," +
                "last_error=NULL, updated_at=CURRENT_TIMESTAMP " +
                "WHERE event_id=? AND handler='email' " +
                "AND status='PROCESSING'",
                eventId
            ));
        }

        void failure(String eventId, String errorCode) {
            statusTx.executeWithoutResult(status -> jdbc.update(
                "UPDATE event_state SET status=" +
                "CASE WHEN attempts >= 3 THEN 'DEAD' " +
                "ELSE 'FAILED' END, last_error=?," +
                "updated_at=CURRENT_TIMESTAMP " +
                "WHERE event_id=? AND handler='email' " +
                "AND status='PROCESSING'",
                errorCode, eventId
            ));
        }

        String status(String eventId) {
            return jdbc.queryForObject(
                "SELECT status FROM event_state " +
                "WHERE event_id=? AND handler='email'",
                String.class, eventId
            );
        }

        int attempts(String eventId) {
            return jdbc.queryForObject(
                "SELECT attempts FROM event_state " +
                "WHERE event_id=? AND handler='email'",
                Integer.class, eventId
            );
        }

        int publicationCount(String eventId) {
            return jdbc.queryForObject(
                "SELECT COUNT(*) FROM event_state WHERE event_id=?",
                Integer.class, eventId
            );
        }

        int itemCount(String eventId) {
            return jdbc.queryForObject(
                "SELECT COUNT(*) FROM work_item WHERE id=?",
                Integer.class, eventId
            );
        }
    }

    static class PublisherService {
        private final JdbcTemplate jdbc;
        private final TransactionTemplate tx;
        private final ApplicationEventPublisher publisher;

        PublisherService(JdbcTemplate jdbc, TransactionTemplate tx,
                         ApplicationEventPublisher publisher) {
            this.jdbc = jdbc;
            this.tx = tx;
            this.publisher = publisher;
        }

        void create(String eventId, boolean rollback) {
            tx.executeWithoutResult(status -> {
                jdbc.update(
                    "INSERT INTO work_item(id) VALUES (?)", eventId
                );
                jdbc.update(
                    "INSERT INTO event_state(" +
                    "event_id,handler,status,attempts) " +
                    "VALUES (?,?,?,?)",
                    eventId, "email", "PENDING", 0
                );
                publisher.publishEvent(new WorkAccepted(eventId));
                if (rollback) {
                    throw new IllegalStateException("forced-rollback");
                }
            });
        }
    }

    static class DeliveryHandler {
        private final Registry registry;
        private final FakeGateway gateway;

        DeliveryHandler(Registry registry, FakeGateway gateway) {
            this.registry = registry;
            this.gateway = gateway;
        }

        @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
        public void onWork(WorkAccepted event) {
            handle(event.eventId());
        }

        // Recovery entry point: calls the same logic from the scheduler.
        void retry(String eventId) {
            handle(eventId);
        }

        private void handle(String eventId) {
            if (registry.claim(eventId) != 1) {
                return; // SUCCEEDED, DEAD, or already PROCESSING
            }
            try {
                gateway.send(eventId);
                registry.success(eventId);
            } catch (RuntimeException ex) {
                // Classified error code; do not persist raw payload/stack.
                registry.failure(eventId, "GATEWAY_ERROR");
            }
        }
    }

    @Configuration(proxyBeanMethods = false)
    static class Config {
        @Bean
        DataSource dataSource() {
            return new DriverManagerDataSource(
                "jdbc:h2:mem:event_state_demo;DB_CLOSE_DELAY=-1",
                "sa", ""
            );
        }

        @Bean
        JdbcTemplate jdbcTemplate(DataSource ds) {
            return new JdbcTemplate(ds);
        }

        @Bean
        DataSourceTransactionManager transactionManager(DataSource ds) {
            return new DataSourceTransactionManager(ds);
        }

        @Bean("publicationTx")
        TransactionTemplate publicationTx(
                DataSourceTransactionManager manager) {
            return new TransactionTemplate(manager);
        }

        @Bean("statusTx")
        TransactionTemplate statusTx(
                DataSourceTransactionManager manager) {
            TransactionTemplate template =
                new TransactionTemplate(manager);
            template.setPropagationBehavior(
                TransactionDefinition.PROPAGATION_REQUIRES_NEW
            );
            return template;
        }

        @Bean
        Registry registry(JdbcTemplate jdbc,
                @Qualifier("statusTx") TransactionTemplate statusTx) {
            return new Registry(jdbc, statusTx);
        }

        @Bean
        FakeGateway fakeGateway() {
            return new FakeGateway();
        }

        @Bean
        DeliveryHandler handler(Registry registry, FakeGateway gateway) {
            return new DeliveryHandler(registry, gateway);
        }

        @Bean
        PublisherService publisherService(
                JdbcTemplate jdbc,
                @Qualifier("publicationTx") TransactionTemplate tx,
                ApplicationEventPublisher publisher) {
            return new PublisherService(jdbc, tx, publisher);
        }
    }
}
~~~

The test also uses a **synchronous AFTER_COMMIT listener** without `@Async`. Thus assertions reading status right after `publisherService.create(...)` work in this example because the after-commit callback and status-updating transactions finish before the call returns. If switched to `@Async`, you must **await observable outcomes with a timeout** (Awaitility/`CompletableFuture`/latch), never assert immediately.

## 8. Spring Modulith Event Publication Registry: Using Built-In Components

If an application is split into modules in Spring Boot, **Spring Modulith** provides an Event Publication Registry to record publications sent to transactional event listeners inside the business transaction. Once a listener finishes successfully, the registry marks the publication completed; on error or process crash, incomplete publications can be inspected and resubmitted through the appropriate mechanism.

A module listener is typically written as:

~~~java
@Component
class BillingListener {

    @ApplicationModuleListener
    void on(OrderPaid event) {
        // Perform work belonging to the billing module.
    }
}
~~~

This is a **Spring Modulith snippet**, requiring its dependency, imports, and the application's `OrderPaid` type; it is not part of the H2 project above. `@ApplicationModuleListener` combines transactional event listener ideas with module event handling; exact semantics depend on the Modulith version and transaction configuration.

### Lifecycle and APIs by Version

- In Spring Modulith versions prior to 2.0, the registry focused on **incomplete/completed publications** and resubmission; failure states could be inferred from incomplete records rather than assuming a multi-state enum existed.
- **Spring Modulith 2.0+** introduces explicit lifecycles such as `PUBLISHED`, `PROCESSING`, `COMPLETED`, `FAILED`, `RESUBMITTED`, along with completion attempts and resubmission metadata. These are **Modulith's state names**, distinct from the `PENDING/SUCCEEDED/DEAD` names we chose in the example.
- Spring Modulith provides `IncompleteEventPublications` and, in supported 2.0+ releases, `FailedEventPublications` to help locate/resubmit publications. Verify APIs against your project's exact version; do not copy code from another version.
- Resubmitting outstanding publications on restart can be configured with the version-appropriate property (e.g., `spring.modulith.events.republish-outstanding-events-on-restart` per current docs).
- The registry does not inherently prove external side effects are exactly-once. A listener can produce a side effect and crash before completion is recorded; idempotency still matters.

Persistence options have matching starters (JDBC, JPA, and several other datastores). Completion modes also require retention planning: `UPDATE` keeps completed records for querying, `DELETE` removes them once done, and `ARCHIVE` moves them to historical storage depending on version/backend support. Never let completion records grow without bound without housekeeping.

**Choose the built-in registry when** your architecture fits Spring Modulith, listeners need transactional delivery tracking, and you want to avoid writing all ledger/recovery logic yourself. **Use a dedicated outbox/broker/consumer tracker when** workflows span processes/services, require broker acks, partitioning, DLQs, different lifecycles, or monitoring/retention aligned with an external message bus.

## 9. Observability and Operations: Logs, Metrics, Alerts

A state table is only useful if operators can spot backlogs and failures. For example, a log record should keep consistent, meaningful fields:

~~~json
{
  "message": "event_handler_state_transition",
  "event_id": "evt-103",
  "handler_id": "send-receipt-email",
  "previous_state": "PROCESSING",
  "new_state": "FAILED",
  "attempt": 2,
  "error_code": "DOWNSTREAM_TIMEOUT",
  "correlation_id": "corr-77"
}
~~~

Never put passwords, access tokens, raw request payloads, or PII-containing stack traces casually into ledgers/logs. `last_error_code` should be a categorized/sanitized value, not `exception.toString()` over sensitive data.

Important metrics:

| Metric | What is it for? |
| --- | --- |
| `pending_publications` | How many publications are waiting to be processed |
| `oldest_pending_age_seconds` | Oldest backlogged work item |
| `processing_age_seconds` | Detects slow or stuck workers |
| `failed_publications` | Scale of failed work still retriable |
| `dead_publications` | Number of publications needing intervention |
| `processing_duration_seconds` | P50/P95/P99 handler latency |
| `attempts_per_publication` | Abnormal retry spikes |
| `resubmission_rate` | Recovery rate and retry storm risk |
| `outbox_lag_seconds` | Delay from commit to downstream delivery |

Never use `event_id` or `publication_id` as metric labels due to high cardinality; use controlled values like `event_type`, `handler_id`, and `status`. Use structured logs + trace IDs/correlation IDs to investigate **one specific event**.

### Alerts Should Be Time-Based, Not Count-Only

A backlog of 200 publications during peak traffic can be normal, whereas a publication stuck `PENDING` for 12 hours or `PROCESSING` past its lease is a much more serious signal. Alerts should combine:

- age of the oldest publication;
- newly appearing `DEAD` items;
- `FAILED`/retry ratio per handler;
- processing throughput vs. arrival rate;
- lease expiry frequency;
- DB/broker/repository errors causing **status writes** to fail.

**Note on status-write failures:** if the side effect succeeded yet `mark SUCCEEDED` failed, never assume for sure the handler has not run. It may be in an **unknown outcome** state, requiring reconciliation/idempotency before retrying.

## 10. Often-Overlooked Transaction and Concurrency Issues

### 10.1. Independent States Across Multiple Handlers

An event processed by invoice, email, and analytics is not a single unit of success. Each handler may commit to a different DB, call its own gateway, and retry independently. An aggregate-level summary like `ALL_DONE` must only be derived from each target's state and explicit rules.

### 10.2. Event Producer Rollback

When the source transaction rolls back, publications written in that same transaction must also roll back. If a publication was auto-committed before the business logic rolled back, a worker may process an event whose business state never committed.

### 10.3. Two Workers Claiming Simultaneously

An atomic `UPDATE ... WHERE status='PENDING'` limits duplicate claims inside the database, yet does not solve crashes/scheduling on its own. Leases and fencing must accompany retries after timeouts.

### 10.4. Infinite `PROCESSING`

If status only transitions inside `catch`, crashes never execute `catch`. You need stale/lease monitoring and recovery. Still, do not resubmit every `PROCESSING` row the moment you see it: the task may be running normally.

### 10.5. Changing Status Before the Side Effect

Marking `SUCCEEDED` **before** calling the gateway is wrong: the gateway can fail, leaving a false success in the ledger. Marking after the side effect still leaves a failure window between the two operations; that is why idempotency is needed.

### 10.6. Purging Publications Too Early

If completed records are deleted immediately, operators lose full history. Choose retention per audit/compliance needs. Conversely, keeping everything forever without purging lets storage/indexes grow unboundedly. Completion mode is a trade-off, with no single right value for every system.

### 10.7. Duplicate Publication Differs from Duplicate Attempt

A unique constraint can block two publications for the same event/handler, yet a worker can still perform multiple attempts on **one publication**. Never alter `event_id` between retries if it is still the same logical event.

## 11. Designing Production Retry/Recovery

A recovery loop needs clear steps:

~~~text
periodic scheduler
  -> find due PENDING + due retriable FAILED
  -> claim atomically with worker ID/lease/fencing token
  -> call handler with stable idempotency key
  -> on success: commit SUCCEEDED (matching token)
  -> on error: record error code, next_attempt_at, FAILED or DEAD
  -> on crash: staleness monitor detects expired lease
  -> alert if DEAD/oldest pending exceeds threshold
~~~

Sample backoff: `min(cap, base × 2^(attempt-1)) + jitter`. Never use a fixed uniform deadline that makes thousands of publications retry simultaneously, causing a "thundering herd".

Define a policy table upfront:

| Failure | Suggested action |
| --- | --- |
| Network timeout / HTTP 503 / transient DB lock | Retry with backoff and limits |
| Schema/version validation error | `DEAD` or quarantine; requires data fix |
| Permanent permission denied | Do not blindly retry; needs policy/reconfiguration |
| Duplicate detected by idempotent sink | Check contract and treat as prior success or reconcile |
| Unknown result after timeout calling payment gateway | Query status using idempotency key before retrying |
| Crash during `PROCESSING` | Lease expiry + fencing + downstream idempotency |
| Error writing `SUCCEEDED` status | Reconciliation; avoid assuming side effect never ran |

For payments/billing, **never automatically retry a charge with a fresh request lacking an idempotency key** just because the publication is still `FAILED`. Reliability must be engineered end-to-end across both sides.

## 12. Which Tests Prove State Tracking Is Reliable?

The H2 test suite illustrates basic transitions, while production should add these tests:

1. **Commit + listener succeeds:** publication reaches the right terminal state.
2. **Producer rollback:** no orphan publication contradicting business state remains.
3. **Failure + retry:** same event ID, attempts increment, single publication.
4. **Max retries / permanent error:** transitions to `DEAD`, no infinite loops.
5. **Two concurrent workers:** only one claim wins at the same instant.
6. **Process dies mid-PROCESSING:** lease goes stale, recovery works, and stale token cannot mark succeeded.
7. **Side effect succeeds yet status write fails:** retries do not duplicate side effects thanks to idempotency.
8. **Multiple handlers:** email failure does not wipe out invoice completion.
9. **Async listener:** await observable outcomes via Awaitility/latch with timeout, never `Thread.sleep`.
10. **After-commit transaction:** test real commits; do not slap `@Transactional` on the test and let Spring TestContext roll back by default.
11. **Monitoring:** status counters, oldest age, and dead alerts are emitted/read properly.
12. **Schema migration and restart:** old publications still rehydrate cleanly in the new version.

Concurrency and crash tests should use production-like databases/persistence (for example via Testcontainers) because H2 does not emulate all PostgreSQL/MySQL isolation/locking behavior.

## 13. Implementation Checklist

- [ ] Every logical event has a stable `event_id` and explicit event type/version.
- [ ] State is tracked per **event + handler**, not only for the event overall.
- [ ] Publications are registered transactionally with business changes when durability is required.
- [ ] Atomic claim, max attempts, backoff, and error-classification policies exist.
- [ ] Leases/staleness detection and fencing tokens exist when running multiple workers.
- [ ] Idempotency exists for side effects across DB/broker/external APIs.
- [ ] `published`, `processing`, and `completed` are distinguished from commit/ack semantics.
- [ ] `@TransactionalEventListener(AFTER_COMMIT)` is not mistaken for a durable queue.
- [ ] Replay/recovery exists for outstanding publications after restarts.
- [ ] `DEAD` or quarantine status exists for non-retriable failures.
- [ ] Metrics track backlog age, failure ratios, processing times, and retry storms.
- [ ] Sensitive credentials/raw payloads are never logged or stored in the ledger.
- [ ] Appropriate retention/cleanup exists for completion records.
- [ ] Real tests cover commits, rollbacks, failures, retries, crashes, and concurrency.

## 14. Self-Check Questions

**Question 1:** Does `publishEvent()` returning normally mean an async listener has finished?

No. It normally only confirms dispatch/scheduling per configuration. To know whether processing finished, observe each handler's outcome.

**Question 2:** Why must state be tracked per `(event_id, handler_id)`?

Because one event may be completed by invoicing, failed by email, and in-progress for analytics. A single shared `DONE` state loses information and causes wrong retries.

**Question 3:** What does writing `PENDING` and business data in the same transaction provide?

If the transaction commits, both data and publication exist; if it rolls back, both disappear. That enables recovery after crashes at the dispatch step.

**Question 4:** Why are `PROCESSING` plus leases/fencing needed?

To distinguish claimed from unclaimed, detect worker crashes, and stop old workers from overwriting a new worker's status. Leases alone do not eliminate duplicate side effects.

**Question 5:** Does marking `SUCCEEDED` after calling the gateway successfully guarantee exactly-once?

Not yet. There is a window between gateway success and the status write; crashing in that window can trigger retries. Downstream idempotency/reconciliation is still needed.

**Question 6:** Does `@TransactionalEventListener(AFTER_COMMIT)` durably persist events on its own?

No. It binds callbacks to a transaction phase; durability/recovery requires a registry or appropriate outbox/persistence.

**Question 7:** How does Spring Modulith's Registry differ from the hand-rolled table in the example?

Modulith provides infrastructure for recording publications and completion/resubmission, with expanded lifecycles in 2.x versions. The example's custom table only illustrates a few state transitions without crash recovery/leases/production durability.

**Remember:** Reliable event tracking must answer **which event, to which handler, on which attempt, whether the outcome committed, whether it can be safely retried, and how to recover after a crash**. Only a state machine + transactionally persisted publication ledger + idempotency + recovery/metrics forms a complete solution; calling `publishEvent` or logging "done" alone is never enough.
