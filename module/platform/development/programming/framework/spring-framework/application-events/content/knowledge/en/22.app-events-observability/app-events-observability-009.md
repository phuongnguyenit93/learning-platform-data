# Structured Event Logging in Spring Framework Application Events

**Structured event logging** is the practice of recording when an application event is published, received, and processed using fields with stable names, types, and meanings, instead of concatenating all information into a single prose sentence. In the Spring ecosystem, this is especially valuable because the same business event can be handled by multiple `@EventListener`s running synchronously, asynchronously, or only after a transaction commits.

For example, instead of logging:

~~~text
INFO Received order event ORD-123 from someone, trace abc
~~~

we emit a JSON log record queryable by `event_type`, `event_id`, `aggregate_id`, `correlation_id`, `handler`, and `processing_phase`:

~~~json
{
  "@timestamp": "2026-11-11T05:00:00.000Z",
  "level": "INFO",
  "message": "domain_event_observed",
  "event_type": "order.paid",
  "event_id": "evt-123",
  "aggregate_type": "order",
  "aggregate_id": "ORD-123",
  "correlation_id": "corr-456",
  "handler": "order-paid-audit",
  "processing_phase": "received",
  "schema_version": 1
}
~~~

This is **JSON illustrating business fields**, not a guarantee that every logging backend version outputs the exact keys or timestamp shown. Spring Boot may add `logger_name`, `thread_name`, `process.pid`, and other fields depending on the format. The timestamp in the example is illustrative only; real logs generate timestamps at write time in the backend.

The goal is not to produce the largest volume of logs, but to produce consistent **observable data** answering: "Which event, belonging to which aggregate, triggered by which action, handled by which handler at which stage, succeeded or failed?"

## 1. Distinguishing domain event, application event, and log record

Three distinct artifacts:

| Concept | Role | Example |
| --- | --- | --- |
| **Domain event** | Expresses a business fact that occurred in the domain model | `OrderPaid(orderId)` |
| **Application event** | Object dispatched by `ApplicationEventPublisher` to listeners in the Spring context | Publishing a Java record `OrderPaid` |
| **Structured log record** | Operational record carrying metadata for search, filtering, and analysis | `event_type=order.paid`, `processing_phase=received` |

An application event published in memory **does not automatically become** a log. Spring does not automatically generate complete records for every domain event with all desired fields. You must log at meaningful points or use appropriate instrumentation.

Conversely, a log record **cannot replace** an event bus, transactional outbox, message broker, or event store. A log line saying "event published" does not prove the broker received it, the listener finished processing it, or the database committed.

### Common operability questions

- In the past 15 minutes, how many `order.paid` events were actually received by listeners?
- Which handlers did event `evt-123` pass through? Did any handler fail or retry?
- After trace `corr-456` issued a payment command, which services hold all related logs?
- Does aggregate `ORD-123` have a `received` log yet lack a `processed` log?
- Did duplicate delivery with the same `event_id` occur?
- After a rollback, is there still a "sent email" log, and do phase labels accurately reflect the lifecycle?

You cannot answer reliably using fuzzy substring searches or relying on interleaved stdout ordering across multiple replicas. Structured fields make queries clearer, though consistent semantic design and log collection are still required.

## 2. Designing the field schema for event logs

Each organization may choose snake_case, camelCase, or standards such as Elastic Common Schema (ECS). What matters most is **stability and consistency**. A pragmatic schema for Spring application events:

| Field | Suggested type | Meaning |
| --- | --- | --- |
| `@timestamp` | ISO-8601 timestamp | Time the backend wrote the log, typically generated by the encoder |
| `level` or `log.level` | string | Log level per backend format |
| `message` | string | Stable message code, e.g., `domain_event_observed` |
| `event_type` | string | Stable business name such as `order.paid`, independent of Java package |
| `event_id` | string/UUID | Identity of one logical event, preserved across retries/redeliveries |
| `aggregate_type` | string | Aggregate type, e.g., `order` |
| `aggregate_id` | string | Related aggregate ID |
| `correlation_id` | string | Links logs of the same request/workflow |
| `causation_id` | string, optional | ID of the event/command that caused this event |
| `handler` | string | Stable listener/consumer name, not necessarily FQCN |
| `processing_phase` | enum-like string | `published`, `received`, `processed`, `failed`, `skipped`, ... |
| `attempt` | number, optional | Processing attempt count from an actual retry mechanism |
| `duration_ms` | number, optional | Actually measured processing duration, not guessed |
| `schema_version` | integer | Version of the domain event or log contract schema, explicitly defined |
| `trace_id`, `span_id` | string, optional | Links to distributed tracing when instrumented |

**Distinguish two timestamps:** `event_occurred_at` in the payload describes when the business event was created; `@timestamp` in the log describes when the log record was emitted. Event queues, transactions, and async execution can separate these two values significantly.

**Distinguish two IDs:** `event_id` identifies a single logical event, while `correlation_id` links multiple events/logs across one workflow. When event B is spawned by event A, use `causation_id` to express causality; never reuse the same `event_id` for two independent events.

**Distinguish level and outcome:** `INFO` / `WARN` / `ERROR` represent severity/attention level; `processing_phase=failed` or `outcome=failure` is business/operational data. Not every intentional skip is an error.

### Query examples

On a search backend supporting field-based queries, a filter idea might look like:

~~~text
service.name = "order-service"
AND event_type = "order.paid"
AND processing_phase = "failed"
~~~

Exact syntax depends on Logstash/Elastic/Kibana/OpenSearch/Loki/Datadog and your organization's mappings; this is only a **conceptual filter pattern**, not a literal command runnable across all systems.

## 3. Using Spring Boot's built-in structured logging

Since **Spring Boot 3.4**, Boot supports JSON structured logging out of the box. In Spring Boot 3.5, you can choose `ecs`, `logstash`, or `gelf` formats; applications using the default logging starter typically use Logback.

Example `src/main/resources/application.properties`:

~~~properties
spring.application.name=order-service
logging.structured.format.console=logstash
logging.level.example.events=INFO
~~~

At runtime, framework logs are emitted as individual JSON records in Logstash format rather than the default text pattern. If separate file output is needed:

~~~properties
logging.structured.format.file=logstash
logging.file.name=logs/order-service.json
~~~

Those two lines are **optional configuration**, not required for the console example. Avoid enabling multiple duplicate appenders to the same target or building an extra JSON encoder when Boot already outputs JSON.

Selecting ECS:

~~~properties
spring.application.name=order-service
logging.structured.format.console=ecs
logging.structured.ecs.service.environment=staging
~~~

With ECS, base field structure can differ from Logstash (for example, `log.level` instead of `level`). **Do not hardcode dependencies on a specific JSON path** before settling on an encoder. Spring Boot integrates MDC fields and key-value pairs from SLF4J fluent logging into JSON for ECS/Logstash.

**Custom Logback configuration note:** if the project defines its own `logback-spring.xml`, the `logging.structured.format.console` property may not be enough to override a hardcoded appender encoder. Update the custom logging configuration to honor `CONSOLE_LOG_STRUCTURED_FORMAT` per the Boot documentation, and verify the JSON output.

### Why shouldn't you concatenate JSON strings into log messages manually?

Error-prone approach:

~~~java
log.info("{\"event_id\":\"" + id + "\",\"status\":\"ok\"}");
~~~

This snippet is an excerpt **to avoid**: `message` can end up holding a nested JSON string inside the backend's JSON log, input values are not properly escaped, numbers become strings, injection risks arise, and querying becomes difficult. Use **logging APIs that pass key-value fields**, delegating JSON serialization to the backend.

## 4. SLF4J 2 fluent API: `addKeyValue(...)`

SLF4J 2 allows attaching key-value pairs directly to a log statement:

~~~java
log.atInfo()
    .setMessage("domain_event_observed")
    .addKeyValue("event_type", "order.paid")
    .addKeyValue("event_id", event.eventId())
    .addKeyValue("aggregate_id", event.orderId())
    .addKeyValue("handler", "order-paid-audit")
    .addKeyValue("processing_phase", "received")
    .log();
~~~

This is an **excerpt** inside a listener with `log` and `event` variables. With a backend supporting structured logging, key-value pairs become independent JSON fields. Under a standard console pattern, the same API still runs, though the backend may render them differently. That is, `addKeyValue` **does not guarantee JSON on its own** unless a structured encoder is enabled.

Comparison:

~~~java
// Hard to query by field:
log.info("Event {} for order {} handled by {}",
    event.eventId(), event.orderId(), "order-paid-audit");

// Structured: data types and semantics are separated from the message.
log.atInfo()
    .setMessage("domain_event_observed")
    .addKeyValue("event_id", event.eventId())
    .addKeyValue("aggregate_id", event.orderId())
    .addKeyValue("handler", "order-paid-audit")
    .log();
~~~

These two snippets are **alternatives**; there is no need to log both for the same action. Keep `message` as a stable action code rather than generating a prose sentence with dynamic data for every event; put dynamic values into fields.

## 5. Complete Java 17+ example: logging a Spring application event as JSON

The example set below uses **Spring Boot 3.5.x**, Java 17+, SLF4J 2, default Logback, and JUnit 5. When the application starts, a `CommandLineRunner` publishes `OrderPaid`; an `@EventListener` writes **one** log record containing event metadata as JSON. A test publishes another event with its own ID and parses the real log using Jackson.

### 5.1. `settings.gradle`

~~~groovy
rootProject.name = 'structured-event-logging'
~~~

### 5.2. `build.gradle`

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.5.16'
}

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    implementation 'org.springframework.boot:spring-boot-starter-json'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
~~~

The Spring Boot plugin manages dependency versions; there is no need to manually add a mismatched `slf4j-api` or Logback provider. If the project already uses other Spring Boot starters or an organizational BOM, leverage the compatible dependency set already in use.

### 5.3. `application.properties`

Create `src/main/resources/application.properties`:

~~~properties
spring.application.name=order-service
logging.structured.format.console=logstash
logging.level.example.events=INFO
~~~

This configuration is used both for `bootRun` and loaded into the test environment via `@SpringBootTest`.

### 5.4. `EventLogApplication.java`

Create `src/main/java/example/events/EventLogApplication.java`:

~~~java
package example.events;

import java.time.Instant;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.annotation.Bean;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@SpringBootApplication
public class EventLogApplication {

    public static void main(String[] args) {
        SpringApplication.run(EventLogApplication.class, args);
    }

    @Bean
    CommandLineRunner publishDemoEvent(
            ApplicationEventPublisher publisher) {
        return args -> publisher.publishEvent(new OrderPaid(
            "evt-demo-001",
            "ORD-001",
            "corr-demo-001",
            1,
            Instant.parse("2026-11-11T05:00:00Z")
        ));
    }
}

// Immutable payload, not a Logback/JSON object.
record OrderPaid(
    String eventId,
    String orderId,
    String correlationId,
    int schemaVersion,
    Instant occurredAt
) { }

@Component
class OrderPaidLogListener {

    private static final Logger log =
        LoggerFactory.getLogger(OrderPaidLogListener.class);

    @EventListener
    public void onOrderPaid(OrderPaid event) {
        log.atInfo()
            .setMessage("domain_event_observed")
            .addKeyValue("event_type", "order.paid")
            .addKeyValue("event_id", event.eventId())
            .addKeyValue("aggregate_type", "order")
            .addKeyValue("aggregate_id", event.orderId())
            .addKeyValue("correlation_id", event.correlationId())
            .addKeyValue("schema_version", event.schemaVersion())
            .addKeyValue("event_occurred_at",
                event.occurredAt().toString())
            .addKeyValue("handler", "order-paid-audit")
            .addKeyValue("processing_phase", "received")
            .log();
    }
}
~~~

`OrderPaid` here is a Java record (it does not extend `ApplicationEvent`). Spring can publish a payload object as an application event and map it to `@EventListener(OrderPaid)`. `OrderPaidLogListener` logs **event reception**; it does not prove the DB transaction committed or that external consumers finished processing.

When running from a project with the Gradle wrapper:

~~~bash
./gradlew bootRun
~~~

On Windows PowerShell, use `./gradlew.bat bootRun`. Among the startup JSON log lines, there will be a line **with a similar shape** (Boot-added fields or key ordering may vary):

~~~json
{"@timestamp":"2026-11-11T05:30:00Z","@version":"1","message":"domain_event_observed","logger_name":"example.events.OrderPaidLogListener","thread_name":"main","level":"INFO","event_type":"order.paid","event_id":"evt-demo-001","aggregate_type":"order","aggregate_id":"ORD-001","correlation_id":"corr-demo-001","schema_version":1,"event_occurred_at":"2026-11-11T05:00:00Z","handler":"order-paid-audit","processing_phase":"received"}
~~~

**This is illustrative output, not verbatim stdout from an actual run.** `@timestamp` and real system metadata are generated at logging time; `event_occurred_at` comes from the event record, so the two timestamps may differ.

## 6. Testing real JSON logs with `OutputCaptureExtension`

Do not merely assert that the listener was invoked. To verify the **structured logging contract**, tests should inspect a JSON line for required fields and accurate data types. Spring Boot provides `OutputCaptureExtension` and `CapturedOutput` to capture stdout/stderr in JUnit 5.

Create `src/test/java/example/events/StructuredEventLogTest.java`:

~~~java
package example.events;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.time.Instant;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.system.CapturedOutput;
import org.springframework.boot.test.system.OutputCaptureExtension;
import org.springframework.context.ApplicationEventPublisher;

@SpringBootTest(
    classes = EventLogApplication.class,
    webEnvironment = SpringBootTest.WebEnvironment.NONE
)
@ExtendWith(OutputCaptureExtension.class)
class StructuredEventLogTest {

    @Autowired ApplicationEventPublisher publisher;
    @Autowired ObjectMapper mapper;

    @Test
    void eventLogContainsQueryableFieldsAndNoCredentials(
            CapturedOutput output) throws Exception {

        publisher.publishEvent(new OrderPaid(
            "evt-test-249",
            "ORD-249",
            "corr-test-249",
            1,
            Instant.parse("2026-11-11T05:00:00Z")
        ));

        String jsonLine = output.getOut()
            .lines()
            .filter(line -> line.startsWith("{"))
            .filter(line -> line.contains(
                "\"event_id\":\"evt-test-249\""))
            .findFirst()
            .orElseThrow(() -> new AssertionError(
                "No structured event log found"
            ));

        JsonNode log = mapper.readTree(jsonLine);

        assertEquals(
            "domain_event_observed",
            log.path("message").asText()
        );
        assertEquals("order.paid", log.path("event_type").asText());
        assertEquals("evt-test-249", log.path("event_id").asText());
        assertEquals("ORD-249", log.path("aggregate_id").asText());
        assertEquals(
            "corr-test-249",
            log.path("correlation_id").asText()
        );
        assertEquals("received", log.path("processing_phase").asText());
        assertEquals(1, log.path("schema_version").asInt());
        assertEquals("INFO", log.path("level").asText());

        assertTrue(log.has("@timestamp"));
        assertFalse(log.has("password"));
        assertFalse(log.has("access_token"));
    }
}
~~~

Run:

~~~bash
./gradlew test --tests "example.events.StructuredEventLogTest"
~~~

Windows PowerShell:

~~~powershell
./gradlew.bat test --tests "example.events.StructuredEventLogTest"
~~~

**What the test actually proves:**

1. The event was published via `ApplicationEventPublisher`, and the listener was invoked by Spring's real mechanism.
2. The JSON log emitted by the **logging backend** has `message` and queryable business keys, not merely a simulated JSON string.
3. `schema_version` is verified as an integer and IDs as text, independent of JSON property order.
4. The test locates a log event with a dedicated `event_id`, without confusing it with startup logs or the `CommandLineRunner` demo event.
5. The two sensitive keys `password` and `access_token` are **verified** absent from the record.

The test verifies **one specific record**, not that every log across the entire system is redacted. Ensuring privacy requires additional tests with sensitive data, code reviews, logging policies, and input validation.

If a project uses custom Logback/Log4j2 configuration, `CapturedOutput` may need configuration so appenders write to the stream captured by the test. Using Spring Boot's default logging as in the example avoids that discrepancy. Depending on Gradle version and test execution flags, Gradle may not print full JSON to the build stdout; assertions read the `CapturedOutput` object directly rather than relying on Gradle's console text.

## 7. Logging across lifecycle stages: published, received, processed, failed

An event can pass through multiple listeners and boundaries. **Log each milestone with its true meaning rather than labeling success prematurely.**

~~~text
Command processing
   |
   +-- domain event created
   +-- publishEvent(event)
          |
          +-- @EventListener A receives --> processes --> log processed / failed
          |
          +-- @EventListener B receives --> processes --> log processed / failed
          |
          +-- @TransactionalEventListener(AFTER_COMMIT)
                  |
                  +-- post-commit callback --> log observed_after_commit
                  +-- external side effect succeeds --> log delivery_succeeded
~~~

With default synchronous dispatch, `publishEvent` can invoke listeners directly on the publisher thread before the database commits. With `@Async`, the caller can return before the listener runs. With `@TransactionalEventListener`, callbacks are tied to transaction phases. Therefore, do not use a single `event_sent` label for all milestones.

| Logging point | Example message/phase | What can be concluded? | What must not be concluded |
| --- | --- | --- | --- |
| Before `publishEvent` | `event_publish_requested` | Application code intends to publish | Listener received it |
| Listener starts | `domain_event_observed` / `received` | Listener was invoked | Processing completed |
| After successful processing | `domain_event_processed` / `processed` | Handler finished the logged work | Entire transaction committed |
| Inside `catch` | `domain_event_failed` / `failed` | Handler recorded a failure | System retried successfully |
| `AFTER_COMMIT` callback | `after_commit_handler_started` | Source DB transaction committed | Email/broker received it |
| After broker ACK | `integration_event_published` | Per configured broker ACK semantics | Downstream consumer finished processing |

In particular: when a synchronous `@EventListener` throws an exception, `publishEvent` can throw back to the service. If code logged "published successfully" **before** the publish call and then rolled back, that log still remains; use labels like `attempted` or `publish_requested`, never `business_committed`.

### Structured error logging

When a listener encounters an exception, do not dump the entire payload and sensitive exception messages into logs:

~~~java
try {
    handler.process(event);
} catch (RuntimeException ex) {
    log.atError()
        .setMessage("domain_event_processing_failed")
        .addKeyValue("event_type", "order.paid")
        .addKeyValue("event_id", event.eventId())
        .addKeyValue("handler", "order-paid-audit")
        .addKeyValue("processing_phase", "failed")
        .setCause(ex)
        .log();
    throw ex;
}
~~~

This is an **excerpt** requiring `handler`, `event`, and `log` to be declared. `setCause(ex)` lets the backend log exception/stack trace info per configuration, which can contain sensitive data from messages/stacks. In environments with sensitive data, apply masking policies, exception-type controls, and stack-trace limits. Do not omit `throw ex` automatically if the error must trigger a business transaction rollback.

## 8. Correlation ID, trace ID, and MDC

**Correlation ID** is typically created by the application or API gateway to connect steps across a workflow. **Trace ID/span ID** comes from a distributed tracing system when instrumentation is enabled. They may relate, yet are not identical: one correlation ID can span multiple traces, retries, and message brokers.

To attach a shared field across multiple logs within the same synchronous flow, SLF4J provides `MDC` (Mapped Diagnostic Context):

~~~java
try (MDC.MDCCloseable ignored =
        MDC.putCloseable("correlation_id", correlationId)) {
    log.info("business_step_started");
    publisher.publishEvent(event);
}
~~~

This is an excerpt requiring `org.slf4j.MDC` and variables `correlationId`, `publisher`, `event`. `MDC.putCloseable` removes the field on `close()`; it does not automatically carry context across thread pools or process boundaries. If the same key was already in MDC beforehand, consider restoring the previous value instead of assuming removal is always right.

In Spring Boot ECS/Logstash JSON, MDC values can be included in structured logs. However, **when a listener runs `@Async`**, MDC is usually thread-local and does not automatically transfer across executors. You can use `TaskDecorator`/Micrometer Context Propagation when appropriate and configured, or put `correlation_id` inside the immutable event payload and attach it via `addKeyValue` right inside the listener. The latter is more reliable when events cross brokers or are reprocessed later.

### Example of an async listener reading correlation directly from payload

~~~java
@Async("eventExecutor")
@EventListener
public void onOrderPaid(OrderPaid event) {
    log.atInfo()
        .setMessage("domain_event_observed")
        .addKeyValue("event_id", event.eventId())
        .addKeyValue("correlation_id", event.correlationId())
        .addKeyValue("handler", "async-notification")
        .addKeyValue("processing_phase", "received")
        .log();
}
~~~

This snippet is an **alternative approach**; do not add both at once to the demo app if you only want one handler. It requires `@EnableAsync` and an `eventExecutor` bean. Do not expect `@Async` to automatically bring `SecurityContext`, MDC, or thread-bound transactions from publisher to worker. The `correlation_id` in the event must originate from a trusted source at the application layer.

## 9. Privacy, security, and log volume cost

An event payload can hold emails, addresses, tokens, payment details, or sensitive fields. Structured logging **makes data easier to query**, which can also make sensitive data easier to find if poorly designed.

**Should log:** event ID, event type, aggregate type, sensitivity-reviewed aggregate ID, correlation ID, handler, processing milestone, duration, categorized error state.

**Should not log by default:** passwords, access tokens, authorization headers, refresh tokens, API keys, card data, raw request/response payloads, entire serialized entities, records containing unnecessary PII.

When an aggregate ID is sensitive, consider pseudonymization/hashing aligned with query needs, enforce log read access controls, and set retention policies. Do not use `event.toString()` as the log message if the record contains secret fields.

### Cardinality and logging volume

- `event_type`, `handler`, `processing_phase`: typically have relatively low cardinality, suited for grouping/aggregation.
- `event_id`, `aggregate_id`, `correlation_id`: typically high cardinality, useful for tracing/debugging; avoid turning them into **metric labels** indiscriminately.
- A stream of thousands of events/sec across many listeners can produce huge log volumes. Choose log levels, sampling, and retention per requirements. Do not blindly sample audit or security-critical events required for compliance.
- Do not treat JSON logs as a transactionally consistent database or source of truth for billing/ledgers.

An event can be processed multiple times due to retries or duplicate delivery. When logging retry attempt 3, keep the same `event_id` and add `attempt=3`; do not assign a new event ID on each retry if you want to reconstruct the history of the same logical event.

## 10. Combining logs, metrics, and distributed tracing

Observability is not logs alone. Three complementary signals:

| Signal | Question answered best | Example |
| --- | --- | --- |
| **Log** | What happened for a specific event? | `event_id=evt-123`, `handler=order-paid-audit`, `processing_phase=failed` |
| **Metric** | How many events/s? What are error rates and latencies? | Counters by `event_type`, `handler`, outcome; processing timers |
| **Trace** | Which steps and services did the event traverse? | Publish/consume spans with trace/span IDs |

A solid design: records include `event_id` and `correlation_id` for individual case lookup; metrics count by `event_type` and `handler` (not by event ID); tracing links synchronous/async work via appropriate instrumentation.

Spring Boot Actuator/Micrometer helps add metrics/tracing, yet **enabling structured logging does not auto-create spans for every domain event**. If spans are needed, create/propagate context through observation/tracing infrastructure. Likewise, when messages cross brokers, propagate context via appropriate headers; do not confuse that with serializing raw MDC or `SecurityContext`.

## 11. Common design mistakes

**1. Switching to JSON while keeping free-form messages.** A line with `message: "Order ORD-123 paid"` still forces parsers to split strings. Use a stable message code and put values in fields.

**2. Calling `log.info(event.toString())`.** Hard to query by field and easy to leak payloads. Log an allowlisted set of fields.

**3. Generating a new `event_id` on every retry.** Loses the ability to link attempts; preserve the logical event ID and log `attempt` separately.

**4. Confusing event timestamp and log timestamp.** `event_occurred_at` is business data; `@timestamp` is when the log was written, not necessarily equal.

**5. Logging `processing_phase=processed` before the handler completes.** When an exception occurs afterward, the log misleads. Log `processed` only after the step genuinely succeeds.

**6. Logging `committed` merely because `publishEvent` was called.** Inside `@Transactional`, events can be published before commit and roll back later. Use labels reflecting confirmed transaction completion only.

**7. Relying on MDC in async listeners without propagation.** Worker threads may lack MDC or reuse stale context. Put correlation ID in the event or use tested context propagation.

**8. Logging full stack traces or sensitive payloads unmodified.** Exposes PII/tokens to widely accessible log stores. Apply redaction, classification, retention, RBAC, and code review.

**9. Attaching `event_id` as a metric label.** Unbounded cardinality growth; use small-catalog dimensions for aggregate metrics.

**10. Believing structured logs prove durable delivery.** Logs do not replace outboxes, broker ACKs, idempotency, or event stores.

**11. Mixing incompatible logging providers.** SLF4J 2, Logback, and Spring Boot should use a synchronized dependency set; multiple logging backends in one project can emit duplicates or broken formats.

**12. Tests asserting only `output.contains("evt-123")`.** Can match raw text patterns without verifying JSON fields. Parse JSON and assert keys, types, and the exact event ID record.

## 12. Implementation checklist

- [ ] Identified which event types and handlers need observation instead of logging every object indiscriminately.
- [ ] Established a stable field schema: `event_type`, `event_id`, `aggregate_id`, `correlation_id`, `handler`, `processing_phase`.
- [ ] Defined rules for preserving `event_id` on retries and distinguishing `causation_id`/`correlation_id`.
- [ ] Used SLF4J fluent `addKeyValue` or controlled MDC; backend actually emits JSON.
- [ ] Standardized on ECS, Logstash, or the log platform's schema; never assume identical key names across formats.
- [ ] Excluded raw credentials/PII; applied masking and retention policies.
- [ ] Phase labels accurately reflect synchronous/async/transaction boundaries.
- [ ] Never assumed `@Async` automatically propagates MDC, tracing, or `SecurityContext`.
- [ ] Added integration tests verifying JSON output, types, IDs, and absence of sensitive fields.
- [ ] Added metrics/tracing where needed, with controlled cardinality.
- [ ] Never treated logs as a replacement for an event store, outbox, or durable delivery.

## 13. Self-check questions

**Question 1:** Why is `log.info("Order " + orderId + " paid")` not yet structured event logging?

Because `orderId` is embedded in free-form prose; systems must parse strings to query it. Structured logging puts `aggregate_id` in its own field and uses a stable message code.

**Question 2:** Does calling `addKeyValue(...)` automatically produce JSON?

No. The API represents structured data; the backend/encoder determines output format. In Spring Boot 3.5, you can enable `logging.structured.format.console=logstash` or `ecs`.

**Question 3:** How do `event_id` and `correlation_id` differ?

`event_id` identifies a single event; `correlation_id` links multiple activities/events in one workflow. Across retries of the same logical event, preserve `event_id` and increment `attempt`.

**Question 4:** Can an event be called "committed" right after `publishEvent`?

No. Publishing in Spring's event system does not confirm the database transaction committed; synchronous listeners can run pre-commit and the event source can still roll back.

**Question 5:** Why is `MDC.put(...)` insufficient for an async listener?

MDC is typically thread-bound; `@Async` switches to an executor thread. Proper context propagation or carrying correlation ID in the immutable event payload is required.

**Question 6:** Can `event_id` be used as a metric label to count errors?

No: nearly unique IDs cause metric cardinality to explode. Group metrics by type/handler/outcome; use logs to investigate specific event IDs.

**Key takeaway:** structured logging for Spring application events requires **a stable schema, clearly typed fields, correlation metadata, honest lifecycle labels, sensitive-data protection, and integration tests parsing real JSON**. It improves observability, but does not make application events durable or replace transaction/message delivery guarantees.
