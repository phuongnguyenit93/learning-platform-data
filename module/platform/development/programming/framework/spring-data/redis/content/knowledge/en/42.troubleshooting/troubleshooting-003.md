# Keys with Binary Prefixes or Unexpected Type Metadata in Spring Data Redis

> **Module:** Spring Data Redis  
> **Chapter:** Troubleshooting  
> **Lesson:** Identify Redis keys containing binary bytes, prefixes such as `AC ED 00 05`, unexpected `_class` fields or `@class` properties; distinguish serializers, keyspace, Redis data types, and metadata generated by Spring Data Redis; safely investigate, configure consistently, and migrate data without losing keys.

## 1. Scenario: Redis keys look "strange" even though the application still works

A Spring Boot application stores data using `RedisTemplate`:

```java
redisTemplate.opsForValue()
        .set("customer:101", customer);
```

When opening Redis CLI or RedisInsight, the developer expects:

```text
customer:101
```

Instead, the tool displays a key similar to:

```text
\xac\xed\x00\x05t\x00\x0ccustomer:101
```

Sometimes the value also begins with:

```text
\xac\xed\x00\x05...
```

Or a Redis Hash has an extra field:

```text
_class = com.example.customer.Customer
```

Or a JSON cache has the property:

```json
{
  "@class": "com.example.customer.Customer",
  "id": "101",
  "name": "An"
}
```

The application may still be able to read the data, but Redis CLI becomes difficult to operate, other tools cannot find the key, or a new service fails when changing the serializer.

This is usually **not caused by Redis automatically attaching a binary prefix or generating a Java class name**. The common cause lies in Spring Data Redis's **key/value serialization** mechanism or **mapping metadata**.

### 1.1. Three phenomena often mistaken for one

| Phenomenon | Example | Responsible layer |
|---|---|---|
| **Key has binary bytes** | `AC ED 00 05 ... customer:101` | Application-side key serializer |
| **Value has Java type bytes/metadata** | `AC ED ...` in String value; JSON `@class` | Value serializer/JSON typing |
| **Redis Hash has `_class`** | `_class` field in `HGETALL` | Spring Data Redis mapping/type metadata |

Another phenomenon needs to be separated:

| Phenomenon | Example | Responsible layer |
|---|---|---|
| **Wrong Redis data type** | `WRONGTYPE` when `GET`ting a Hash | Redis server data type and command |

A key having binary bytes **does not mean its Redis data type is also "binary"**. Redis keys are inherently byte sequences; Redis `TYPE` can still return `string`, `hash`, `list`, `set`, `zset`, or another type supported by the Redis version.

### 1.2. Diagnostic goals

After this lesson, you should be able to:

1. Read key bytes accurately instead of only looking at the CLI display representation.
2. Recognize signs of Java/JDK serialization.
3. Distinguish `RedisTemplate`, `StringRedisTemplate`, Spring Cache, and Redis Repository.
4. Explain why `GET customer:101` returns nil even though the application can read the data.
5. Distinguish `TYPE`, `OBJECT ENCODING`, `_class`, and `@class`.
6. Inspect the serializers for key, value, hash key, and hash value.
7. Choose how to read legacy data when changing serializers.
8. Avoid flushing all of Redis or changing serializers abruptly in a multi-application environment.
9. Test byte formats and keyspaces to prevent the issue from recurring.

## 2. Redis stores keys and values as bytes

A foundational concept:

> **Redis does not know `String`, `Customer`, `ProductDto`, or Java packages. Redis receives key names as bytes and stores the corresponding data structure.**

For a Redis String:

```text
Key bytes   -> Redis String value bytes
```

For a Redis Hash:

```text
Key bytes   -> Hash
               field bytes -> field value bytes
               field bytes -> field value bytes
```

Spring Data Redis converts Java objects into bytes via `RedisSerializer`.

### 2.1. Key serializer

Java key:

```java
String key = "customer:101";
```

If using `StringRedisSerializer`, Redis key bytes are typically UTF-8:

```text
63 75 73 74 6f 6d 65 72 3a 31 30 31
 c  u  s  t  o  m  e  r  :  1  0  1
```

If using `JdkSerializationRedisSerializer`, the bytes will include Java serialization stream metadata:

```text
ac ed 00 05 74 00 0c 63 75 73 74 6f 6d 65 72 3a 31 30 31
```

Here `customer:101` has 12 ASCII characters, so the sample payload has length `00 0c`. The exact byte representation varies depending on object type and serializer.

These two keys are **completely different** to Redis:

```text
UTF-8 bytes of "customer:101"
JDK-serialized bytes of Java String "customer:101"
```

They only happen to represent the same logical name on the Java side.

### 2.2. Value serializer

For the same key bytes, a Redis String value can be:

```text
"An"                       -> UTF-8
{"id":"101","name":"An"}    -> JSON UTF-8
AC ED 00 05 ...            -> Java serialization
binary protocol bytes      -> custom/Protobuf/CBOR/MessagePack
```

The application must know the appropriate value serializer/codec to decode it. A successful `GET` at the Redis level does not mean Java object decoding will succeed.

### 2.3. Hash key serializer and hash value serializer

`RedisTemplate` has different serializer slots:

- `keySerializer`: primary Redis key.
- `valueSerializer`: Redis String value.
- `hashKeySerializer`: field name in a Redis Hash.
- `hashValueSerializer`: field value in a Redis Hash.
- `defaultSerializer`: fallback serializer when slots are not explicitly configured, depending on `RedisTemplate` setup.

A template with UTF-8 keys but JDK-serialized hash fields will create a Redis Hash with a **readable primary key name but unreadable field names**.

For example:

```text
Key: customer:101                   (UTF-8)
Hash field bytes: AC ED ... "name" (JDK)
Hash value bytes: AC ED ... "An"   (JDK)
```

If you only change `keySerializer`, old hash fields and values will still remain in the old format.

## 3. What is the AC ED 00 05 prefix?

In the Java Object Serialization Stream Protocol, the byte sequence:

```text
AC ED 00 05
```

is a typical indicator of a stream header. When serializing a Java String, it may be followed by:

```text
74 00 0c ...
```

Where:

- `AC ED`: Java serialization stream magic.
- `00 05`: stream version.
- `74`: type code `TC_STRING` in the case of a normal String.
- `00 0c`: byte length of the UTF-8 String in the protocol's modified UTF-8 format in the short example.
- Following part: serialized String content.

**Do not identify a serializer based solely on four bytes while ignoring context.** Coincidentally matching bytes can still appear in other formats; to conclude, compare with the actual serializer and verify decoding in a trusted environment.

### 3.1. Why does a key have a Java serialization header?

A common possibility:

```java
RedisTemplate<String, Object> redisTemplate = ...;
redisTemplate.opsForValue().set("customer:101", customer);
```

If the template uses `JdkSerializationRedisSerializer` for keys due to the default serializer or non-explicit configuration, the Java String key name is also Java-serialized.

By default in many versions/configurations, `RedisTemplate` uses Java serialization when no specific serializer is set. However, **do not guess**; read the bean configuration of the exact application.

### 3.2. Redis does not generate the header itself

The Redis server does not prepend `AC ED 00 05` to keys. The driver/Spring sent those bytes over the Redis protocol.

Another Java application, ETL script, or other client can also write binary keys; non-UTF-8 keys are supported by Redis.

### 3.3. The byte count of a Java serialized String differs from the character count

Do not manually compute a serialized key by concatenating:

```text
AC ED 00 05 + Java String raw UTF-8
```

Because Java serialization includes type codes, lengths, object references, and Modified UTF-8 rules. With names containing Unicode or non-String objects, the format can be complex.

When you need to operate on legacy keys, use the **exact serializer** or raw bytes already read by the client; do not guess and manually construct prefixes.

## 4. Common signs in Redis CLI

### 4.1. Redis key has escape characters

The CLI may display:

```text
"\xac\xed\x00\x05t\x00\x0ccustomer:101"
```

This is how the tool **represents non-printable bytes**. The quotation marks and `\x..` sequences are the tool's representation, not necessarily literal characters stored inside the Redis key.

### 4.2. RedisInsight may display garbled characters

A UI tool attempting to decode a key as UTF-8 may display:

```text
��...customer:101
```

or a sequence of unreadable characters. That alone is not enough to conclude data corruption; it may simply be a **binary key incompatible with a text viewer**.

### 4.3. GET by logical name returns nil

Running:

```bash
redis-cli GET customer:101
```

Redis returns nil, yet the application can read the data.

Possibilities:

- The actual key is Java-serialized bytes rather than UTF-8.
- Spring Cache adds a prefix like `products::customer:101`.
- Repository uses a keyspace like `customers:101`.
- The application connects to a different Redis database/cluster/endpoint than the CLI.
- The key's TTL expired or the data is being recreated.
- Different tenant/environment prefix.
- The Java client uses a different serializer than the CLI.

Do not take a single nil `GET` as proof that the key does not exist anywhere in Redis.

### 4.4. GET fails with WRONGTYPE

CLI returns:

```text
WRONGTYPE Operation against a key holding the wrong kind of value
```

In this case, the key exists and **its Redis data type is not String**. It might be a Hash written by a Spring Data Redis Repository. Use `TYPE` before deciding whether to run `GET`, `HGETALL`, or `LRANGE`.

## 5. Distinguishing Redis TYPE, OBJECT ENCODING, and Java type metadata

Three distinct concepts:

### 5.1. TYPE — Redis data structure

```bash
redis-cli TYPE customer:101
```

Can return:

```text
string
hash
list
set
zset
stream
none
```

Supported types can vary by Redis version/extensions.

`TYPE` identifies the **Redis data type** of the exact key bytes passed in. It does not explain Java classes or JSON formats.

### 5.2. OBJECT ENCODING — Redis internal representation

```bash
redis-cli OBJECT ENCODING customer:101
```

The result may be an internal encoding such as `raw`, `embstr`, `listpack`, `hashtable`, `quicklist`, `skiplist`, depending on Redis version, data type, and structure.

This is **not** equivalent to:

```text
StringRedisSerializer
JdkSerializationRedisSerializer
Jackson JSON serializer
```

For example, a Redis String containing JSON may have internal encoding `raw`; a Redis String containing JDK bytes may also have `raw`. `OBJECT ENCODING` does not determine Spring's value codec.

### 5.3. `_class` or `@class` — application type metadata

For example:

```text
Redis Hash field: _class = com.example.Customer
```

or JSON:

```json
{"@class":"com.example.Customer","id":"101"}
```

That is metadata **placed into the Redis value by application mapping/serializers**, not the output of `TYPE`.

### 5.4. Reference table

| Observed component | Question answered | Cannot answer |
|---|---|---|
| Redis `TYPE` | Does the key hold String/Hash/List...? | Which Java class serialized it |
| Redis `OBJECT ENCODING` | What internal layout does Redis use? | Jackson vs JDK serializer |
| Java bytes `AC ED...` | Are there signs of Java serialization? | Redis data type if TYPE has not been called |
| Hash field `_class` | Which Java type did the mapper store? | Whether Redis actually enforces access control |
| JSON `@class` | Which type metadata did the serializer write? | What the Redis key serializer is |
| Key prefix `cache::` | Which app/cache namespace is it? | Whether the value format is compatible |

## 6. Where does `_class` in a Redis Hash come from?

A Spring Data Redis Repository can map a Java entity to a Redis Hash. For example:

```java
@RedisHash("customers")
public class Customer {

    @Id
    private String id;

    private String name;
}
```

With a repository, the data might look like:

```text
Key: customers:101
Redis type: hash

Fields:
  _class = com.example.customer.Customer
  id     = 101
  name   = An
```

`_class` is typically a type hint written by the mapping converter to support object reconstruction, especially with polymorphic/nested structures depending on configuration.

### 6.1. `_class` is not Redis server metadata

Redis has no concept of Java classes. `_class` is just **an ordinary hash field** at the Redis level. Redis does not add this field itself.

If read using:

```bash
redis-cli HGETALL customers:101
```

you can see `_class` as a separate field.

### 6.2. Why is a type hint needed?

When a Redis Repository reads a Hash and builds a Java object, the type hint can help:

- Choose the concrete Java type.
- Distinguish subtypes within a hierarchy.
- Restore nested objects/polymorphism according to mapping configuration.
- Interact with Spring Data mapping metadata.

It is not an authorization mechanism and does not protect data by itself.

### 6.3. Refactoring packages/classes can make old data unreadable

If metadata contains:

```text
com.oldpkg.Customer
```

but the class has changed to:

```text
com.newpkg.Customer
```

the mapping layer may fail or be unable to restore the type as before, depending on how type aliases/type mappers are used.

Therefore, repository keyspace/type metadata is **part of the data contract** and must be accounted for during migration.

### 6.4. @TypeAlias and class-name-independent schemas

Spring Data mapping supports type alias mechanisms in certain cases, for example:

```java
@TypeAlias("customer")
@RedisHash("customers")
public class Customer {
    @Id
    private String id;
}
```

Aliases can help reduce reliance on fully qualified Java class names when the mapping configuration recognizes the type correctly. However:

- It does not automatically rewrite previously written metadata.
- It does not guarantee every class/nested subtype is known to the mapping context.
- It does not mean the `_class` field disappears.
- It must be tested with the Spring Data Redis version in use.

If you want to omit type metadata, design an appropriate custom mapping/serializer and determine the impact on polymorphic reads; do not simply run `HDEL _class` in production.

## 7. Where does `@class` in JSON come from?

Some JSON serializers may include type information to decode the object back to its original Java type.

For example, with generic/polymorphic JSON serialization:

```json
{
  "@class": "com.example.customer.Customer",
  "id": "101",
  "name": "An"
}
```

This can appear when using `GenericJackson2JsonRedisSerializer` or a corresponding Jackson polymorphic typing configuration.

**Do not assume every JSON serializer adds `@class`.** How metadata is written depends on the serializer, Jackson configuration, root type, default typing, metadata field name, and version.

### 7.1. `Jackson2JsonRedisSerializer<T>` differs from a generic serializer

With a serializer that has a specific target type such as:

```java
Jackson2JsonRedisSerializer<Customer> serializer = ...;
```

the decoder already knows `Customer` is the target type. It may not need to write the fully qualified Java class name into every JSON value, depending on the ObjectMapper/configuration.

With a generic serializer used to read multiple object types, type metadata may be enabled to identify the object type.

### 7.2. `@class` is not a business field

A service API may serialize a DTO to JSON **without** `@class`, while the Redis cache JSON **has** `@class` due to a generic serializer. Therefore:

- Do not treat Redis cache JSON as an API contract by default.
- Do not treat `@class` as information added automatically by Redis Server.
- Do not strip the field and assume the old serializer can still deserialize it.
- Do not let external clients dictate Java class names for Jackson to instantiate.

### 7.3. Polymorphic deserialization security

Type metadata can introduce risks if the decoder accepts uncontrolled Java classes from untrusted bytes.

You should:

- Use concrete DTO schemas when appropriate.
- Restrict the Java types allowed to be deserialized.
- Avoid enabling broad default typing without a type validator/allowlist.
- Protect Redis with ACLs, TLS, and network segmentation.
- Never treat Redis data as unconditionally trusted if multiple writers/services have write access.
- Do not expose raw serialized payloads or fully qualified internal class names through public APIs.

## 8. RedisTemplate and StringRedisTemplate: important differences

### 8.1. RedisTemplate

`RedisTemplate<K,V>` is a general-purpose template. In many configurations/versions, if no explicit serializer is set and default serialization is enabled, it uses the JDK serializer.

For example:

```java
RedisTemplate<String, Object> template = ...;

template.opsForValue().set("customer:101", customer);
```

If the key serializer is still JDK, a Java String key can be encoded as:

```text
AC ED 00 05 ...
```

If the value serializer is JDK, the value also has a binary header.

Do not infer from the generic parameter `RedisTemplate<String,Object>` that keys will be stored as UTF-8. **Java generic types do not determine the wire format.**

### 8.2. StringRedisTemplate

`StringRedisTemplate` is designed for String keys/values and uses String serialization.

```java
StringRedisTemplate template = ...;

template.opsForValue().set(
        "customer:101",
        "{\"id\":\"101\",\"name\":\"An\"}");
```

Keys and String values are typically human-readable in Redis CLI.

However:

- If the actual key was written by an older service using the JDK serializer, StringRedisTemplate will look up a **different UTF-8 key**.
- StringRedisTemplate does not automatically migrate legacy data.
- It does not automatically enforce JSON schema validity or security.
- Data in Hashes/Lists/Sets requires using the corresponding operations.

### 8.3. Spring Boot auto-configuration

Spring Boot typically auto-configures the connection factory, RedisTemplate, and StringRedisTemplate based on present dependencies/properties/beans. However:

- A custom `RedisTemplate` bean can override defaults.
- A custom `RedisCacheManager` bean may not use RedisTemplate's serializers.
- Different Spring Data Redis/Boot versions may configure things differently.
- `RedisRepository` mapping has its own serializer/mapping path.
- `ReactiveRedisTemplate` has its own `RedisSerializationContext`.

**Inspect the actual bean being injected and that bean's serializer properties.**

## 9. Explicitly configuring RedisTemplate to avoid unexpected binary keys

A Java 17+ template using String keys/hash fields and JSON values:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.StringRedisSerializer;

@Configuration
public class RedisSerializationConfiguration {

    @Bean("jsonRedisTemplate")
    RedisTemplate<String, Object> jsonRedisTemplate(
            RedisConnectionFactory connectionFactory) {

        RedisTemplate<String, Object> template =
                new RedisTemplate<>();

        template.setConnectionFactory(connectionFactory);
        template.setKeySerializer(new StringRedisSerializer());
        template.setHashKeySerializer(new StringRedisSerializer());

        template.setValueSerializer(
                new GenericJackson2JsonRedisSerializer());
        template.setHashValueSerializer(
                new GenericJackson2JsonRedisSerializer());

        template.afterPropertiesSet();
        return template;
    }
}
```

This is a **configuration example**. The generic JSON serializer may still generate type metadata; if `@class` is undesired, consider concrete DTO/schema types, appropriate Jackson configuration, or using `StringRedisTemplate` with explicit JSON DTO encoding.

### 9.1. Configuration must match existing data

If legacy keys are JDK bytes, the bean above cannot read them using Java String keys. Simply changing the bean in production without migration can cause the application to perceive the cache as empty.

### 9.2. `hashKeySerializer` is often forgotten

A bean like:

```java
template.setKeySerializer(new StringRedisSerializer());
template.setValueSerializer(new GenericJackson2JsonRedisSerializer());
```

is not necessarily enough. Hash field names/values may still use the default serializer. Set all serializers the application needs **explicitly**.

### 9.3. StringRedisTemplate for contract-driven JSON DTOs

If you want to avoid generic `@class` metadata:

```java
public record CustomerCache(
        int schemaVersion,
        String customerId,
        String name) {
}
```

You can store JSON text:

```java
CustomerCache dto = new CustomerCache(1, "101", "An");

String json = objectMapper.writeValueAsString(dto);

stringRedisTemplate.opsForValue()
        .set("customer:v1:101", json);
```

When reading:

```java
String json = stringRedisTemplate.opsForValue()
        .get("customer:v1:101");

if (json != null) {
    CustomerCache dto =
            objectMapper.readValue(json, CustomerCache.class);
}
```

`ObjectMapper` is provided by Spring/the application; `writeValueAsString`/`readValue` throw checked exceptions that must be declared or handled in production code.

Benefits:

- UTF-8 key bytes.
- Controlled JSON schema payload.
- Explicit schema version.
- Independent of Java package names if the DTO only contains business fields.
- Easy to test golden bytes and compatible across multiple languages.

## 10. Redis Cache: why do key names have unexpected prefixes?

With Spring Cache:

```java
@Cacheable(cacheNames = "customers", key = "#id")
public CustomerDto findById(String id) {
    return repository.load(id);
}
```

`RedisCacheManager`/RedisCache can create a key like:

```text
customers::101
```

A key name with `customers::` is a **cache prefix** added by Spring Cache, not a JDK binary prefix.

If the application configures:

```java
RedisCacheConfiguration.defaultCacheConfig()
        .computePrefixWith(
                name -> "app:prod:v2:cache:" + name + "::");
```

the key can become:

```text
app:prod:v2:cache:customers::101
```

### 10.1. RedisCacheConfiguration has its own serializers

In many versions of Spring Data Redis, the default Redis Cache configuration uses:

- String key serialization.
- JDK value serialization.
- A prefix based on cache name.
- Default TTL depending on configuration, often unlimited unless set by the app.

This is **separate from the RedisTemplate bean**. Changing the RedisTemplate value serializer does not automatically change the Cache Manager value serializer.

### 10.2. A readable key with a binary value

For example:

```text
Key: customers::101
Value: AC ED 00 05 ...
```

Check **RedisCacheConfiguration.serializeValuesWith(...)** or the cache-specific serializer, rather than modifying the key serializer.

### 10.3. A key containing `::` is not broken

Prefixes prevent collisions between cache names. Do not try to remove prefixes by flushing all of Redis unless the application has an explicit migration plan.

### 10.4. @Cacheable key and null/missing values

A cache key may not match `id` as expected because:

- `@Cacheable(key=...)` uses SpEL.
- Default `KeyGenerator` uses object parameters.
- Cache prefix/version changed.
- Custom key conversion.
- Tenant environment scope.
- A different cache manager bean than the one you are inspecting.

Inspect the exact cache key expression and final serialized key bytes.

## 11. Redis Repository differs from RedisTemplate and Spring Cache

A Redis Repository:

```java
@RedisHash("customers")
public class CustomerEntity {

    @Id
    private String id;

    private String name;
}
```

differs from:

```java
redisTemplate.opsForValue().set("customers:101", entity);
```

Repositories typically store entities using Redis Hash mapping, whereas `opsForValue()` stores Redis String bytes.

### 11.1. Same logical name but different Redis TYPE

For example:

```text
Repository:
  Key: customers:101
  TYPE: hash
  HGETALL => id, name, _class

RedisTemplate.opsForValue:
  Key: customers:101
  TYPE: string
  GET => serialized Java object or JSON bytes
```

If two code paths write to **the same raw Redis key**, they can overwrite the data type or cause `WRONGTYPE`. Keyspace ownership must be unified.

### 11.2. Secondary indexes and metadata

Repositories may generate additional keys for:

- Secondary indexes.
- Keyspace metadata.
- TTL/expired object handling.
- Entity references depending on mapping configuration.

A Redis scan may reveal keys "not explicitly set by you" that are used by Repository infrastructure. Do not delete them hastily without knowing the owner.

### 11.3. `_class` may appear inside nested Hashes

Type hints can serve nested/polymorphic mapping. If they appear unexpectedly, inspect `MappingRedisConverter` and entity mappings before deciding that data is leaked or malformed.

### 11.4. Do not treat `_class` as authorization

A value containing:

```text
_class = com.example.AdminUser
```

does not prove the caller has admin privileges. Authorization must be enforced via Spring Security/business policy; type metadata is technical deserialization information.

## 12. Diagnosing with Redis CLI: TYPE first, GET later

A safe workflow for an **exact, known UTF-8 key**:

```bash
redis-cli EXISTS customer:101
redis-cli TYPE customer:101
redis-cli PTTL customer:101
redis-cli MEMORY USAGE customer:101
redis-cli OBJECT ENCODING customer:101
```

Not every Redis provider permits all diagnostic commands. Use least privilege and an appropriate environment.

### 12.1. If TYPE = string

You can read it:

```bash
redis-cli GET customer:101
```

However, binary values can cause the terminal to print escape sequences or control bytes. Do not copy raw values into logs/emails/public tickets if they contain sensitive data.

### 12.2. If TYPE = hash

Use:

```bash
redis-cli HGETALL customer:101
redis-cli HKEYS customer:101
redis-cli HGET customer:101 _class
```

For large Hashes, `HGETALL` can return large amounts of data and put load on Redis/the client. Prefer `HSCAN` with a cursor or select known fields in production when payloads are large.

### 12.3. If TYPE = list/set/zset/stream

Use the corresponding command:

- List: `LRANGE` with a bounded range.
- Set: `SSCAN`.
- Sorted Set: `ZSCAN` or `ZRANGE` with a bounded range.
- Stream: `XRANGE` with a bounded `COUNT`.

Do not use `GET` for these structures.

### 12.4. If TYPE = none

Possible reasons:

- The key genuinely does not exist/has expired.
- CLI is connected to the wrong endpoint/database/cluster node.
- The key bytes are binary-serialized.
- The app adds a prefix/cache name/tenant.
- The key was evicted/expired.
- The app only writes when a specific condition is met.

Do not conclude "Redis lost data" without verifying key bytes and connection context.

## 13. SCAN, KEYS, and binary key challenges

### 13.1. SCAN operates on bytes

Redis `SCAN` iterates over Redis keys; pattern matching is applied on the Redis side against the raw key bytes. If the actual key has a JDK header before `customer:101`, a pattern starting with:

```text
customer:*
```

may **fail to find** that key.

For example:

```bash
redis-cli --scan --pattern 'customer:*'
```

can find ordinary UTF-8 keys, but will not match JDK-serialized names that have a binary prefix.

### 13.2. Using bounded full SCAN to identify key bytes

```bash
redis-cli --scan
```

Use for observation in small/test environments. On large production keyspaces, scanning still generates load and can yield millions of results; do not dump everything to a terminal or log.

The CLI may escape or print control bytes depending on output mode. Text-printed output **is not guaranteed to be copy/pasteable to recreate the exact bytes**.

### 13.3. Do not run KEYS * indiscriminately

```bash
redis-cli KEYS '*'
```

`KEYS` can perform heavy work and impact latency when the keyspace has many keys. Use `SCAN` or bounded observability tools in production.

### 13.4. A pitfall with serialized wildcards

If you call:

```java
redisTemplate.keys("customer:*");
```

and `redisTemplate` uses a JDK key serializer, the pattern string `"customer:*"` can also be serialized as Java object bytes.

The wildcard `*` sits **after the Java serialization header/length**, so it does not have the same logical prefix matching semantics as a UTF-8 pattern. Because serialization encoding includes length metadata, the pattern bytes do not resemble a prefix of serialized `"customer:101"`.

Therefore, **do not use `RedisTemplate.keys("prefix*")` with a JDK key serializer as proof that legacy keys do not exist**.

### 13.5. SCAN is not a snapshot

Even with the right pattern, Redis SCAN:

- May return the same key multiple times.
- Does not guarantee an immutable snapshot while keys are being added/deleted.
- `COUNT` is only a hint.
- May require scanning all primary nodes in Redis Cluster.
- Is not a mechanism to strictly guarantee all data was migrated while writers remain active.

For diagnosis, capture a controlled sample of keys. For migration, design an idempotent scanner and reconciliation.

## 14. Reading raw key bytes with Spring Data Redis

When a key cannot be copied accurately from the CLI, a more reliable approach is retrieving the raw `byte[]` from `RedisConnection`.

### 14.1. Illustrative Java 17+ utility

```java
import java.nio.ByteBuffer;
import java.nio.charset.CharacterCodingException;
import java.nio.charset.CodingErrorAction;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

final class RedisByteDebug {

    static String hex(byte[] bytes) {
        return HexFormat.of().formatHex(bytes);
    }

    static String utf8IfValid(byte[] bytes) {
        try {
            return StandardCharsets.UTF_8
                    .newDecoder()
                    .onMalformedInput(CodingErrorAction.REPORT)
                    .onUnmappableCharacter(CodingErrorAction.REPORT)
                    .decode(ByteBuffer.wrap(bytes))
                    .toString();
        } catch (CharacterCodingException ex) {
            return "<non-UTF8>";
        }
    }

    private RedisByteDebug() {}
}
```

Use Java 17's `HexFormat` to print hex instead of trying to display raw bytes with `%s`.

### 14.2. Scanning raw bytes in a RedisTemplate callback

```java
import org.springframework.data.redis.core.Cursor;
import org.springframework.data.redis.core.RedisCallback;
import org.springframework.data.redis.core.ScanOptions;
import org.springframework.data.redis.core.StringRedisTemplate;

public class RedisKeyInspector {

    private final StringRedisTemplate template;

    public RedisKeyInspector(StringRedisTemplate template) {
        this.template = template;
    }

    public void inspectSample(int maxKeys) {
        template.execute((RedisCallback<Void>) connection -> {
            int inspected = 0;

            ScanOptions options = ScanOptions.scanOptions()
                    .count(200)
                    .build();

            try (Cursor<byte[]> cursor = connection.scan(options)) {
                while (cursor.hasNext() && inspected < maxKeys) {
                    byte[] rawKey = cursor.next();

                    String hex = RedisByteDebug.hex(rawKey);
                    String utf8 =
                            RedisByteDebug.utf8IfValid(rawKey);

                    System.out.println(
                            "keyHex=" + hex
                            + " utf8=" + utf8
                            + " redisType="
                            + connection.type(rawKey));

                    inspected++;
                }
            }

            return null;
        });
    }
}
```

This is a **minimal diagnostic** utility:

- `connection.scan(options)` returns raw keys from the connection API where supported.
- `connection.type(rawKey)` passes the exact key bytes without re-serializing a Java String.
- `utf8IfValid` only accepts valid UTF-8 keys.
- `maxKeys` limits output to avoid dumping millions of keys.
- Does not automatically read every value.
- Do not use in production without authorization and redaction.
- In Redis Cluster, scan behavior via the connection/API may be node-scoped; check each primary or use cluster-aware tooling depending on Spring Data Redis version.

**Important:** printing a key's hex can still expose identifiers/PII if the key contains sensitive data. Do not leave scanners as permanent logging features, and do not paste raw results into public tickets.

### 14.3. Why not use new String(byte[]) for inspection?

By default:

```java
new String(rawKey, StandardCharsets.UTF_8)
```

can replace invalid byte sequences with the replacement character `�`. This makes a binary key **look like a String** while losing the original bytes. If you use that string to delete or modify the key, you may operate on the wrong key.

To operate accurately on raw binary keys, preserve `byte[]` throughout and pass it via the low-level Redis connection API.

## 15. Safely diagnosing value bytes

Once you have the **raw key bytes** and know `TYPE = string`, you can read the raw value:

```java
byte[] rawValue = connection.stringCommands().get(rawKey);
```

This returns bytes from the Redis String. It does not invoke JDK deserialization or Jackson.

Restrictions to follow:

- Do not read excessively large values without bounds.
- Do not print raw values containing PII/sessions/tokens.
- Do not decode using classes from untrusted sources.
- Do not use `GET` if `TYPE` is not `string`.

### 15.1. Checking magic bytes

On a sample value in a test environment, inspect the first few bytes:

```text
ac ed 00 05 ...  -> suspected JDK serialization
7b 22 ...        -> UTF-8 JSON object typically starts with {"...
5b ...           -> JSON array or another format
```

A header alone does not prove the format; cross-check the writer/serializer configuration and test decoding against the exact schema.

### 15.2. `DUMP` is not Java serialization

Redis:

```bash
redis-cli DUMP customer:101
```

produces a Redis-specific internal serialized representation for use with `RESTORE`. It **does not prove** the value was saved using `JdkSerializationRedisSerializer`. Do not treat `DUMP` bytes as JSON or a Java serialized DTO.

## 16. Wrong serializers can cause three distinct types of errors

### 16.1. Key not found

V1 writes JDK key bytes, V2 uses UTF-8 keys:

```text
V1 SET JDK("customer:101") ...
V2 GET UTF8("customer:101")
=> nil
```

Even though Redis still holds the old data, the key bytes differ.

### 16.2. Redis returns WRONGTYPE

One service writes a Redis Hash:

```redis
HSET customer:101 name An
```

Another service calls:

```java
stringRedisTemplate.opsForValue().get("customer:101");
```

Redis returns WRONGTYPE because the raw key holds type `hash`, not `string`.

This is a **Redis data structure mismatch** error, not necessarily related to JDK/JSON serializers.

### 16.3. Redis GET succeeds but Java deserialization fails

V1 writes JSON:

```json
{"id":"101","name":"An"}
```

V2 reads with a JDK serializer:

```text
GET raw bytes: OK
Java deserialize: failed
```

You may see `SerializationException`, `SerializationFailedException`, a Jackson mapping exception, or a wrapped exception depending on the Spring Data Redis API.

Do not treat every cache read exception as a connection failure.

### 16.4. JSON parses successfully but the object is the wrong type

For example, a generic JSON serializer returns a `Map` instead of `Customer`, and then code casts it:

```java
Customer customer = (Customer) result;
```

which can throw `ClassCastException`.

Check the target type, type metadata, JSON mapping, and version mismatches; this is not a Redis server bug.

## 17. Quick symptom identification table

| Symptom | First hypothesis | How to confirm |
|---|---|---|
| Key starts with `AC ED 00 05` | JDK key serializer | Check RedisTemplate key serializer/raw bytes |
| Key has `` characters | Binary key/incorrect UI UTF-8 decoding | Scan raw bytes and hex |
| `GET customer:101` is nil but Java get returns a value | Different key bytes or different prefix | Compare actual key serializer, endpoint, prefix |
| Redis key `customers::101` | Spring Cache prefix | Check CacheManager/cache name |
| Redis value starts with `AC ED` | JDK value serialization | Check value serializer and raw value bytes |
| Redis JSON has `@class` | Generic JSON polymorphic type metadata | Check serializer/ObjectMapper |
| HGETALL has `_class` | Redis Repository/MappingRedisConverter | Check @RedisHash and mapping |
| Redis `TYPE` = hash, GET fails | Data structure mismatch | HGETALL/HSCAN instead of GET |
| Redis `TYPE` = string but app parse fails | Value codec/schema mismatch | Raw bytes, serializer, DTO |
| Spring Data Repository finder misses entity | Different keyspace/ID/index metadata | Check entity keyspace/indexes |
| Only new app version fails to read data | Missing compatibility in serializer/key schema migration | Compare old/new writers/readers |
| Only cluster node A sees keys | Endpoint/slot routing/scanning | Check Cluster topology |
| A key disappears after TTL | Expiration/eviction | PTTL, INFO stats/memory |
| `OBJECT ENCODING=raw` | Redis internal string encoding | Do not infer JSON/JDK from encoding |

Do not jump to conclusions from a single symptom; use evidence from raw bytes, Redis type, and application configuration.

## 18. Misleading defaults in Spring Boot

### 18.1. RedisTemplate is not synonymous with StringRedisTemplate

A generic template can serialize Java String keys in JDK format; StringRedisTemplate uses String format. Hence, two beans both calling `get("customer:101")` can read **two different Redis keys**.

### 18.2. RedisCacheManager does not automatically inherit a custom RedisTemplate

If you configure:

```java
@Bean
RedisTemplate<String, Object> redisTemplate(...) {
    // custom serializers
}
```

Spring Cache may still use a `RedisCacheManager` with its own `RedisCacheConfiguration`. Consequently, the key or value format from `@Cacheable` may differ from operations performed via RedisTemplate.

### 18.3. Repositories use mapping conversion

A `@RedisHash` Repository is not the same as `opsForValue().set(entity)`; it can write a Redis Hash with `_class` and secondary index keys. Changing the value serializer does not necessarily alter Repository mapping metadata.

### 18.4. ReactiveRedisTemplate uses RedisSerializationContext

For reactive operations:

```java
ReactiveRedisTemplate<K, V>
```

codecs/serializers are configured through the corresponding `RedisSerializationContext`; do not assume it takes serializers from an imperative RedisTemplate.

### 18.5. Spring Boot properties vary across versions

Redis connection settings such as `spring.data.redis.*` in Spring Boot 3 and `spring.redis.*` in some older versions may differ. This relates to endpoints/connections, **not automatically to the key/value serializers** of custom beans.

When investigating, verify the exact application/Boot/Spring Data Redis/driver versions and actual beans.

## 19. When are binary keys valid?

Binary keys are not inherently a bug. Redis allows arbitrary binary-safe key bytes (subject to length/protocol limits per Redis protocol/version).

A system may intentionally use:

- Hash digest bytes.
- Compact binary composite identifiers.
- Custom binary key protocols.
- Non-UTF-8 identifiers from specialized clients.
- JDK-serialized keys from a legacy application.

However, binary keys have operational drawbacks:

- Difficult to read in Redis CLI.
- Pattern-based diagnostics/cleanup are error-prone.
- Easy to confuse logical keys and key bytes.
- Hard to share across multi-language clients.
- Cluster hash tag/slot placement can be hard to observe.
- Serializer migration can easily create duplicate logical keys.
- ACL key patterns must account for raw bytes.

If the project wants text keys, explicitly configure `StringRedisSerializer`. However, **do not switch immediately** while legacy data is still being read/written.

## 20. Redis Cluster: bytes and hash slots

Redis Cluster calculates slots based on raw key bytes, supporting hash tags `{...}` when valid braces are present.

For example:

```text
shop:{tenant-17}:order:101
shop:{tenant-17}:order:102
```

two keys with the same hash tag are mapped to the same hash slot.

### 20.1. Key serializer affects placement

If a serializer alters the raw key bytes, the slot can change. If a binary serializer still embeds `{tenant-17}` as a contiguous range of raw bytes, the hash tag mechanism may still apply, but do not assume that from Java String logic without checking the **actual serialized bytes**.

### 20.2. Do not put all keys under a global tag

```text
app:{all}:tenant:A:...
app:{all}:tenant:B:...
```

forces keys into a single slot, easily creating a hot shard. Hash tags should be scoped to the required atomic multi-key operation.

### 20.3. CROSSSLOT is not simply a serializer mismatch

If a multi-key command sends raw keys belonging to different slots, Redis Cluster can return `CROSSSLOT`. Changing serializers can alter slots; use `CLUSTER KEYSLOT` on the exact raw keys in supporting tools or inspect the key/tag layout at the byte level.

### 20.4. Scanning the entire Cluster

A `SCAN` connected to a single primary node typically only sees keys managed by that node. Depending on the Spring Data Redis/driver API, scan operations might not automatically cover every primary.

When using Redis Cluster, identify node ownership and use cluster-aware key enumeration per your API/version; do not conclude "keys vanished" simply because one node returns nothing.

## 21. ACL key patterns, binary keys, and security

Redis ACLs can restrict key access by patterns. If an application expects:

```text
app:prod:customers:*
```

but the key serializer actually writes JDK bytes with a binary prefix, that pattern may **not match** the actual key bytes.

The result can be:

- `NOPERM` even though the code appears to use the right key prefix.
- Service accounts having to be granted broader patterns than intended.
- A deployment accidentally using admin credentials to bypass errors.
- Access permissions drifting out of sync with old/new keyspaces during migration.

**Do not resolve this by granting `+@all` or `~*` unconditionally.** Determine the actual serialized bytes and keyspace, then design least-privilege ACLs.

### 21.1. Redis key names may contain sensitive data

Key names sometimes contain:

- User identifiers.
- Emails.
- Session tokens.
- Tenant IDs.
- API keys.
- Resource IDs.

Even if a key is binary-serialized or displayed escaped, data can still leak via logs, dumps, monitoring, or raw key scans.

### 21.2. Never use JDK deserialization on untrusted data

If you find `AC ED` and want to "try deserializing":

- Only do so on data from trusted origins in a controlled environment.
- Never allow callers to specify arbitrary classes or serializers.
- Never run a generic `ObjectInputStream` on raw unknown bytes from shared Redis/untrusted producers.
- Consider JDK deserialization filters/allowlists and plan to migrate off JDK format if possible.
- Avoid logging entire objects/payloads.

Java deserialization is a security-sensitive boundary; diagnostic reads must respect the trust boundary.

## 22. Moving from binary keys to UTF-8 keys: not just changing one bean

Suppose legacy is:

```text
Legacy key bytes:
  JDK("customer:101")

New key bytes:
  UTF8("app:prod:customers:v2:101")
```

If you only deploy the new key serializer:

```text
Old data stays at the legacy key
New app cannot find it
Old app may still keep writing to the legacy key
```

For rebuildable caches, you can pick a new namespace and warm it from the canonical source. When Redis is the sole data source, you need a migration covering exact bytes, consistency, and rollback.

### 22.1. Two common migration approaches (and variants)

| Strategy | When appropriate | Risk |
|---|---|---|
| **New namespace and rebuild** | Cache backed by DB/source | Cold cache, DB stampede |
| **Read legacy and write new** | Want to preserve existing data | Decoding trusted bytes, concurrent writes, TTL |
| **Dual-reader/bridge** | Multiple versions running concurrently | Requires compatibility contract |
| **Background backfill** | Large key count, migration deadline | SCAN is not a snapshot, memory overhead |
| **In-place replace** | Controlled reader-first rollout | Old app may fail to read |
| **Resource migration** | Moving Redis instance/cluster | Cutover/replication/ownership |

### 22.2. Expand → migrate → contract

A safe sequence:

1. **Inventory:** identify old key/value serializers, prefixes, TTLs, writers/readers.
2. **Expand:** deploy code capable of reading both old/new formats (if needed).
3. **Introduce a versioned namespace:** do not force old readers to read new bytes.
4. **Migrate:** rebuild from source or decode legacy → validate → encode new.
5. **Coexistence:** handle invalidation/reads/writes across old/new versions.
6. **Monitor:** legacy reads, conversion failures, Redis memory, eviction, cache hit ratio.
7. **Rollback window:** retain the ability to roll back to a version with compatible data.
8. **Contract:** retire legacy writers/readers once verified.
9. **Cleanup:** delete old keys with scoped, rate-limited deletion.

### 22.3. When multiple versions run simultaneously

If V1 writes JDK format to a key while V2 writes JSON to **the same key bytes**, interleaved requests will flip the format back and forth. V1/V2 may fail deserialization intermittently.

How to avoid: roll out reader-first or use separate versioned keyspaces. For mutable business data, implement **cross-version invalidation** so V2 does not serve stale cache when V1 only deletes the V1 key.

### 22.4. TTL must not be ignored

When copying from old to new:

- Retrieve the remaining TTL of the old key.
- Avoid inventing an overly long new TTL that causes stale cache.
- If `PTTL = -1`, verify whether policy allows no TTL.
- If `PTTL = -2`, the key is gone; skip/re-read.
- Separate GET and PTTL calls have a race condition if the old key is modified in between.
- For canonical data, use version checks/CAS or an appropriate migration window.

Do not assume `RENAME` or `DUMP/RESTORE` converts Java serialization to JSON; Redis commands do not understand Java schemas.

## 23. Do not delete data just because it looks unreadable

A dangerous reaction:

```bash
redis-cli FLUSHALL
```

or:

```bash
redis-cli KEYS '*' | xargs redis-cli DEL
```

Never run these on shared Redis/production to "clean up strange keys".

Risks:

- Deletes sessions, locks, counters, streams, and caches of other services.
- Loses idempotency state causing duplicate side effects.
- Loses irrecoverable canonical data.
- Triggers DB stampedes when the cache goes cold.
- Causes downtime or impacts other tenants.

Identify the key owner, raw bytes, Redis TYPE, TTL, serializer, and whether the data is cache or canonical before modifying anything.

### 23.1. Deleting the exact raw key

Once a binary key is confirmed for deletion, use the exact raw bytes via a controlled low-level Redis connection API or a migration script that knows the old serializer.

Do not try to manually construct the Java serialization prefix and type escaped text in the CLI to delete—the risk of targeting the wrong bytes is high.

### 23.2. Do not use a lossy decoded String key

If raw key bytes contain invalid UTF-8, decoding to a String with `�` and re-encoding does not produce the same key. Preserve `byte[]`.

### 23.3. Be careful with Repository metadata/indexes

A "strange" key might be a secondary index, Redis Hash, or keyspace metadata created by a Spring Data Repository. Deleting metadata alone can cause repository queries to miss records. Check the model and namespace owner.

## 24. Reading a Redis Hash containing `_class`: handling it properly

A sample:

```bash
redis-cli TYPE customers:101
# hash

redis-cli HGETALL customers:101
# id -> 101
# name -> An
# _class -> com.example.customer.Customer
```

If the app uses a Repository mapper, the presence of `_class` may be completely normal.

### 24.1. If you do not want to store the Java class name

Options depend on design:

- Use a DTO + fixed JSON schema via `StringRedisTemplate`.
- Use an appropriate alias/type mapper in Spring Data mapping.
- Configure a controlled converter/mapping strategy if supported by the framework version.
- Use a custom representation and avoid relying on automatic polymorphic reconstruction.

**Do not delete `_class` from all Hashes immediately**: running readers may need it to distinguish subtypes.

### 24.2. If `_class` differs from the current package

Ask:

- Which application version wrote the data?
- Was the class renamed/moved to another package?
- Is there alias compatibility?
- Does the reader version have a mapping context containing old/new classes?
- Is there a corresponding DTO migration?
- Is the data cache or canonical?
- Are multiple services writing to the same Hash keyspace?

If unsure, copy an **authorized, anonymized** fixture into a test environment and test conversion rather than editing production directly.

## 25. JSON with `@class`: handling it properly

Given a value:

```json
{
  "@class": "com.example.customer.Customer",
  "id": "101",
  "name": "An"
}
```

Determine:

- Is the writer using `GenericJackson2JsonRedisSerializer`?
- Is there a custom `ObjectMapper.activateDefaultTyping(...)` or `@JsonTypeInfo` annotation?
- What is the actual type metadata field name?
- Is there nested object metadata?
- Does the new version still have that class?
- Is the current DTO/schema version compatible?
- Are there allowlist/trust restrictions?

### 25.1. Do not treat @class as a Redis data type indicator

Redis `TYPE` can return `string` for JSON text regardless of whether the JSON has `@class`. This is JSON serializer metadata, not a Redis internal type.

### 25.2. Do not manually strip @class from cached JSON

If the old serializer needs type metadata to reconstruct `Object`, removing the field can make deserialization fail or return a `Map` instead of the DTO.

To remove the metadata, migrate with a reader that understands the old format and a new writer using a typed DTO schema, with a compatible versioned keyspace/cutover.

### 25.3. Multi-language data sharing

Python/Node/Go clients generally do not want fully qualified Java class names. If Redis is shared cross-language, use a stable JSON schema/Protobuf/Avro contract instead of JDK serialization or Java-specific polymorphic metadata.

## 26. Reading the wrong Redis key due to endpoint, DB, or tenant mix-ups

Not every "strange" key case is a serializer issue.

### 26.1. Redis endpoint and logical database

If:

```text
Spring Boot -> redis-prod:6379, DB 1
redis-cli   -> redis-dev:6379, DB 0
```

then the CLI will not see keys the application just wrote.

Check the connection configuration from the app deployment and CLI session rather than relying on defaults.

Redis Cluster only supports database 0. Do not use `SELECT 1` to isolate tenants in Cluster mode.

### 26.2. Environment prefix

The application may write:

```text
app:prod:customer:101
```

while the CLI searches for:

```text
customer:101
```

### 26.3. Tenant prefix

Multi-tenant cache:

```text
app:prod:customers:tenant:t-17:id:101
```

Require a verified tenant context; do not infer tenants from key substrings or unverified user-supplied headers.

### 26.4. TTL/eviction

A key that just appeared may expire:

```bash
redis-cli PTTL app:prod:customer:101
redis-cli INFO stats
redis-cli INFO memory
```

`PTTL=-2` indicates the key does not exist at the time of inspection; `PTTL=-1` indicates the key exists with no expiration. Redis eviction/memory pressure can remove keys before TTL.

Do not blame the wrong serializer when the root cause is expiration or the wrong endpoint.

## 27. Testing to prevent key/value byte incidents

### 27.1. Testing key serializers

In an integration test with real Redis or Testcontainers:

1. Create a `RedisTemplate` matching the deployed configuration.
2. Write the logical key `"customer:101"`.
3. Use raw `RedisConnection.scan(...)` to retrieve the actual key bytes.
4. Compare with the expected UTF-8 bytes.
5. Verify no JDK header appears if the requirement is readable keys.
6. Verify the data type is String/Hash as expected.

Do not only assert that Java `redisTemplate.opsForValue().get("customer:101")` succeeds, because the same misconfigured serializer can still read back data it wrote itself.

### 27.2. Testing StringRedisTemplate and other templates

If the application has multiple Redis templates, test that they produce the same raw key bytes **when designed to share a keyspace**, or test that they use separate namespaces when formats are incompatible.

### 27.3. Testing Spring Cache

For `@Cacheable`:

- Cache name and prefix are correct.
- Key expression includes tenant/environment/version.
- Cache value serializer is correct.
- Cache hits do not throw `ClassCastException`.
- Old/new serializers do not write to the same namespace if incompatible.
- `@CacheEvict` deletes the exact key that was created.
- Cache misses are distinguished from deserialization errors.

### 27.4. Testing Redis Repository

For `@RedisHash`:

- `TYPE` is Hash as expected.
- Entity id and keyspace are correct.
- `_class` metadata is understood or aliases are compatible.
- Secondary index queries work.
- TTL and expiration handling are correct.
- Other applications do not use the same key as a String.

### 27.5. Testing migration and rollback

- Old version writes key/value.
- New version reads it or intentionally separates namespaces.
- New version does not write formats that crash old readers.
- TTL is preserved/bounded.
- Concurrent reads/writes do not create staleness beyond policy.
- Rollback target can still read existing data.
- Key cleanup does not delete metadata of other services/tenants.

### 27.6. Testing untrusted data

Do not take arbitrary binary values and attempt JDK deserialization in production. Use fixtures of known provenance, verify type/format validators, and parsers that restrict allowed classes.

## 28. A diagnostic runbook for production incidents

### Step 1 — Identify the symptom

For example:

```text
Symptom:
  RedisInsight shows "\xac\xed..."
  redis-cli GET customer:101 -> nil
  Spring service can read Customer
```

Do not modify configuration yet.

### Step 2 — Check connectivity

- Redis endpoint/port.
- Standalone vs Cluster.
- Logical DB index if applicable.
- User/ACL.
- TLS.
- Environment/tenant prefixes.

### Step 3 — Determine raw key bytes

Use a bounded raw SCAN sample or tooling with binary-safe key enumeration. Print hex with redaction in an authorized environment.

### Step 4 — Determine Redis TYPE and TTL

Pass the **exact raw key bytes** to `TYPE`/`PTTL`. If the key is `hash`, do not call GET.

### Step 5 — Identify the serializer

Check:

- `RedisTemplate.getKeySerializer()`.
- `RedisTemplate.getValueSerializer()`.
- `getHashKeySerializer()`.
- `getHashValueSerializer()`.
- `RedisCacheConfiguration` for Spring Cache.
- Repository mapping converter/type mapper.
- Reactive serialization context if present.
- Old and new writer versions.

You may inspect bean configurations, but do not instantiate a new serializer solely to test against untrusted production data.

### Step 6 — Distinguish metadata

- `AC ED`: sign of JDK serialization bytes.
- `_class` in Redis Hash: mapping type hint.
- `@class` in JSON: polymorphic JSON type metadata.
- `TYPE hash`: Redis data type, not a Java class.
- `OBJECT ENCODING`: Redis internal representation.

### Step 7 — Classify the data

- Cache with canonical source?
- Sessions?
- Idempotency state?
- Distributed locks?
- Counters/quotas?
- Stream work queues?
- Repository canonical state?

Do not apply "flush cache and rebuild" to every kind of data.

### Step 8 — Choose remediation

- Only need to explain the key: update dashboards/tooling/docs.
- Need UTF-8 keys for new data: configure an explicit String key serializer and v2 namespace.
- Need to read legacy binary keys: use legacy serializer/low-level raw access with safeguards.
- Do not want `@class`: use typed DTOs/new JSON serializer and compatible migration.
- Do not want `_class`: review mapping strategy/type aliases and plan data conversion.
- WRONGTYPE: fix key ownership/operation, not just the serializer.

### Step 9 — Observe after changes

- Cache hit/miss/error rates.
- Deserialization exceptions.
- Memory/eviction.
- Legacy/new key counts.
- Spring Cache/Repository queries.
- TTL/correctness.
- Security/ACL.
- Rollback behavior.

## 29. Common mistakes

### 29.1. "A key with strange characters means Redis is corrupted"

Not necessarily. Redis supports binary keys; Java serializers can produce non-printable bytes.

### 29.2. "Using a String key in Java guarantees Redis stores UTF-8"

False. `RedisTemplate<String,V>` can still use a JDK key serializer. Java generic types do not dictate the bytes.

### 29.3. "Switching to StringRedisTemplate will read old keys"

Not if old keys used JDK bytes. StringRedisTemplate looks up a different UTF-8 key.

### 29.4. "Seeing AC ED means the data is a Redis Hash"

False. AC ED is a sign of Java serialization in bytes; Redis data type must be checked with `TYPE`.

### 29.5. "Redis TYPE returning string means JSON"

False. A Redis String holds any bytes—UTF-8 text, JSON, or a JDK-serialized object.

### 29.6. "OBJECT ENCODING=raw means raw value serializer"

False. That is Redis's internal encoding, not a Spring serializer.

### 29.7. "`_class` is added automatically by the Redis server"

False. Spring Data Redis mapping can write a type hint into a Redis Hash.

### 29.8. "`@class` is a DTO field so it should be removed"

Not necessarily. It may be metadata required by a generic JSON serializer. Removing it can break deserialization.

### 29.9. "RedisCacheManager automatically uses RedisTemplate's serializer"

Do not assume this. RedisCacheConfiguration has its own settings.

### 29.10. "If GET returns nil, the key definitely doesn't exist"

Not if you pass a logical UTF-8 name while actual key bytes are JDK-serialized, or if cache prefix/endpoint differs.

### 29.11. "`KEYS customer:*` found nothing so there are no customers"

False if keys have a binary prefix or a different cache/repository namespace; also avoid running KEYS across an entire production keyspace.

### 29.12. "SCAN always returns a complete, duplicate-free snapshot"

False. SCAN is not a snapshot while a dataset changes, and COUNT is only a hint.

### 29.13. "Redis RENAME can convert JDK to JSON"

False. RENAME changes the key name and keeps value bytes intact; it does not transform application schemas.

### 29.14. "You can delete `_class` from a Hash and repositories will definitely still work"

No. The mapper may need the type hint, especially for polymorphic types.

### 29.15. "Just disabling serializer metadata is safer"

Not if old data still relies on metadata or the decoder needs it; migration must remain compatible.

### 29.16. "A WRONGTYPE error is caused by a JDK binary prefix"

Not necessarily. WRONGTYPE means the wrong Redis data structure for the exact raw key. Binary prefixes are a separate key encoding issue.

### 29.17. "Pasting full raw keys/values into a bug ticket is harmless"

No. Keys/values can contain PII, tokens, sessions, internal class names, and tenant IDs.

### 29.18. "FLUSHALL can be used to clean up unreadable keys"

Never on shared Redis/production. It can wipe sessions, locks, counters, streams, or unrecoverable data.

## 30. Frequently Asked Questions

**Q1. Why does a key start with `\xac\xed\x00\x05`?**

That is the classic signature of a Java Object Serialization stream. Check the serializer encoding the key, usually `JdkSerializationRedisSerializer`.

**Q2. Does Redis add binary prefixes to keys itself?**

No. Redis stores the bytes sent by the client. Prefixes are typically produced by the application/serializer.

**Q3. Why can't `StringRedisTemplate` see a key written by `RedisTemplate`?**

The two templates may use different key serializers, producing two different raw Redis keys for the same Java String.

**Q4. Does RedisTemplate always default to the JDK serializer?**

In many configurations/versions, RedisTemplate uses JDK serialization when no custom serializer is set. However, inspect the injected bean because custom configuration can change behavior.

**Q5. Why does `@Cacheable` produce the key `products::101`?**

RedisCacheManager/RedisCache uses a cache-name prefix. This is a normal text namespace, not a binary prefix.

**Q6. How does Redis Cache serialize values by default?**

In many Spring Data Redis configurations, the default is a JDK value serializer and usually a String key serializer. Verify `RedisCacheConfiguration` for your exact application/version.

**Q7. What does `_class` in a Redis Hash mean?**

A type hint written by the Spring Data Redis mapping converter to help reconstruct the Java object. It is a Hash field, not Redis server metadata.

**Q8. Where does `@class` in JSON come from?**

It may be polymorphic type metadata added by `GenericJackson2JsonRedisSerializer` or Jackson configuration. Not every JSON serializer uses it.

**Q9. What is the difference between `TYPE` and `OBJECT ENCODING`?**

`TYPE` tells you whether the Redis key is String/Hash/List..., while `OBJECT ENCODING` tells you what internal layout Redis uses. Neither identifies the Java serializer.

**Q10. Is a GET returning WRONGTYPE caused by the wrong serializer?**

The cause may be code/namespace writing a Redis Hash while the reader calls String GET. Confirm with `TYPE` on the exact raw key bytes.

**Q11. How do I list JDK-serialized keys?**

Use binary-safe raw key enumeration via Redis connection/SCAN, printing hex with limits/PII controls. Prefix matches like `customer:*` may miss them because the bytes start with a Java header.

**Q12. Can I use `redis-cli --scan`?**

Useful for observation, but text output is unreliable for reconstructing arbitrary binary key bytes. Use a raw byte API for exact operations.

**Q13. Can I call `new String(keyBytes, UTF_8)` and then delete the key?**

Unsafe if the bytes are not valid UTF-8; the decoder may replace invalid bytes with `�`. Preserve raw bytes when operating on keys.

**Q14. Can I delete `_class` to save memory?**

Not arbitrarily. The mapper may need it; the cost of breaking compatibility usually outweighs the few bytes saved.

**Q15. If I rename a Java package, can old `_class` data still be read?**

Depends on mapping/aliases/converters. Test migration; consider type aliases or DTO conversion.

**Q16. Should I use JDK serialization for Redis values long-term?**

Evaluate security risks and coupling to Java classes. For data requiring interoperability/stable schemas, JSON DTOs/Protobuf/explicit formats are generally easier to maintain.

**Q17. Does Redis Cluster affect binary keys?**

Yes. Slot calculation relies on raw bytes/hash tags, and scans may be node-scoped. Changing serializers can alter placement/behavior.

**Q18. Is a binary-prefixed key immediately dangerous?**

Not inherently dangerous. The main risks are operational difficulty, serializer/migration mistakes, ACL patterns, and deserializing untrusted bytes.

**Q19. Is a key missing because of TTL or because of the serializer?**

Compare the actual raw key, endpoint, `TYPE`, `PTTL`, `INFO stats`, and keyspace/version prefixes before concluding.

**Q20. Is it enough to just change the serializer and deploy?**

Not if old data and old versions are still running. You need expand–migrate–contract, versioned namespaces or a bridge reader, and a rollback plan.

## 31. Practical diagnostic checklist

1. **Verify endpoint/database/cluster** used by CLI and Spring.
2. **Determine raw key bytes** using a binary-safe tool, not just a text viewer.
3. **Check `TYPE` before GET/HGETALL**.
4. **Check `PTTL` and eviction** if keys are missing.
5. **Recognize `AC ED 00 05`** as a sign of JDK serialization rather than guessing solely from display strings.
6. **Inspect key/value/hash serializers** of the exact RedisTemplate bean.
7. **Inspect RedisCacheConfiguration** separately for Spring Cache.
8. **Inspect Redis Repository mapping** if Hash `_class` appears.
9. **Inspect Jackson polymorphic typing** if JSON has `@class`.
10. **Distinguish Redis TYPE and OBJECT ENCODING** from serializer metadata.
11. **Check cache prefix, @Cacheable key expression, and tenant scope**.
12. **Do not use UTF-8 patterns to conclude binary keys are absent**.
13. **Compare raw bytes across application versions**.
14. **Test decoding legacy data only within the trust boundary** and preserve the cause on error.
15. **Do not read/export raw PII/session values** casually for debugging.
16. **Do not change serializers on a shared keyspace while old readers are still running**.
17. **Have migration/rollback for the new keyspace** when needed.
18. **Respect Redis Cluster hash slots, ACLs, and node-local scans**.
19. **Do not delete data owned by another Repository/cache**.
20. **Test at the byte level, including cache hit/miss, WRONGTYPE, and metadata fields**.
21. **Never use FLUSHALL/FLUSHDB** to handle strange keys in production.
22. **Measure after changes:** hit ratio, decode errors, memory, legacy/new key counts.

## 32. Summary

**Redis keys with binary prefixes or unexpected type metadata do not necessarily mean Redis is broken.** In Spring Data Redis, they usually stem from serialization and mapping mechanisms:

- **`AC ED 00 05` in keys/values:** common signature of `JdkSerializationRedisSerializer`.
- **Key not found via CLI text:** may be due to different key bytes, Spring Cache prefix, repository keyspace, tenant/environment prefix, or a different endpoint.
- **`_class` in a Redis Hash:** type hint written by Spring Data Redis mapping/repository.
- **`@class` in JSON:** type metadata written by a JSON serializer/Jackson polymorphic typing.
- **`WRONGTYPE`:** the Redis key holds a different data structure than the operation called; confirm with `TYPE`.
- **`OBJECT ENCODING`:** Redis's internal representation, not a Jackson/JDK serializer.

The right approach is **verify raw key bytes → check Redis TYPE/TTL → identify the actual serializer/mapper → evaluate keyspace ownership → choose the right configuration or migration**.

When you want readable keys and cross-service compatibility, you can use `StringRedisSerializer` for keys, explicit typed JSON DTOs/schemas for values, and versioned namespaces. However, do not switch serializers abruptly if Redis holds legacy data or multiple versions are running concurrently. Migrations must preserve data correctness, tenant isolation, TTLs, and rollback capability.
