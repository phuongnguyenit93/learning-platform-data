# Boundaries Between Spring Cache, Spring Session, and Spring Data Redis

In a Spring Boot application, **Spring Cache**, **Spring Session**, and **Spring Data Redis** can all use the same Redis server. Because of this, newcomers often assume all three libraries do the same job, or that adding a Redis dependency automatically stores caches, sessions, and all objects in Redis.

In reality, each library operates within a **different responsibility boundary**:

- **Spring Cache** manages *reusing computation or query results* through a unified caching API.
- **Spring Session** manages *the lifecycle and state of user sessions*, replacing the web server's default session store.
- **Spring Data Redis** provides *the means for applications to connect to and interact with Redis*: issuing commands, handling keys/values, data structures, Redis repositories, and integration hooks so other libraries can use Redis as a backing store.

**A Redis server is infrastructure; caching, sessions, and Redis data are three distinct usage purposes.** Sharing a Redis server does not change each component's API contract, expiration rules, consistency guarantees, or error-handling strategy.

## 1. Quick comparison of the three scopes

| Criterion | Spring Cache | Spring Session | Spring Data Redis |
|---|---|---|---|
| Core question | "Can I reuse the result of this method?" | "How do I identify and preserve a user's session across HTTP requests?" | "How do I read, write, and leverage Redis data structures?" |
| Central abstractions | `Cache`, `CacheManager`, method interceptor | `Session`, `SessionRepository`, `HttpSession`/`WebSession` integration | `RedisConnectionFactory`, `RedisTemplate`, `StringRedisTemplate`, Redis repositories |
| Common entry points | `@Cacheable`, `@CachePut`, `@CacheEvict` | `HttpSession`, session cookie, Spring Security session | `opsForValue()`, `opsForHash()`, `opsForZSet()`, `@RedisHash` |
| Is Redis mandatory? | No; Caffeine, ConcurrentMap, etc. can be used | No; sessions can use JDBC or other stores | Yes; the module's purpose is communicating with Redis |
| How is Redis used? | `RedisCacheManager` is a `CacheManager` implementation | Redis-backed `SessionRepository` provided by Spring Session | Direct Redis APIs and Redis adapters |
| Typical data | Catalog query results, rarely changing configuration | Session shopping cart, session attributes, security context when session-based | Counters, leaderboards, rate limiting, temporary markers, Redis-suited domain data |
| Expiration | TTL per **cache entry**, per cache configuration | **Session inactivity timeout** and session expiration mechanism | Application sets TTL explicitly, or chooses no expiration |
| Who determines the key? | Cache name + key generated by the cache operation | Session repository manages session IDs and internal keys | Application code / repository designs keys |
| When a value disappears | Usually recomputable/re-fetchable from the source of truth | Session may expire; user loses session state and may need to sign in again | Depends on key semantics: may lose a temporary counter or critical state |
| Consistent with DB? | Requires invalidation/TTL design | Not a business-data synchronization mechanism with DB | Application-designed; Redis does not auto-sync with DB |
| What it does not solve | Does not create distributed sessions | Does not cache arbitrary business methods | Does not auto-enable `@Cacheable` or replace web server sessions |

The three libraries can be summarized in three distinct lines of code:

~~~java
// Spring Cache: check the cache before executing the business method
@Cacheable(cacheNames = "products", key = "#id")
public ProductView getProduct(long id) { ... }

// Spring Session: access session state via the HTTP API
httpSession.setAttribute("language", "vi");

// Spring Data Redis: interact with Redis for business logic directly
stringRedisTemplate.opsForValue().increment("metrics:page-views");
~~~

All three snippets **can create keys inside Redis**, yet ownership of those keys differs completely.

## 2. Position in the Spring architecture

~~~text
                       SPRING BOOT APPLICATION
 +--------------------------------------------------------------------+
 |                                                                    |
 |  Business method call                 HTTP request / session       |
 |                 |                               |                  |
 |                 v                               v                  |
 |     Spring Cache abstraction          Spring Session               |
 |     @Cacheable / @CacheEvict           SessionRepositoryFilter      |
 |                 |                       SessionRepository           |
 |                 v                               |                  |
 |         RedisCacheManager              Redis-backed repository      |
 |                 |                               |                  |
 |                 +---------------+---------------+                  |
 |                                 |                                  |
 |  Business code ─> StringRedisTemplate / RedisTemplate / Repositories|
 |                                 |                                  |
 |                                 v                                  |
 |                      RedisConnectionFactory                       |
 |                          (e.g. Lettuce)                           |
 +---------------------------------+----------------------------------+
                                   |
                                   v
                        Redis server / Sentinel / Cluster
~~~

The diagram shows **sharing of the connection layer**, not components invoking one another:

- `@Cacheable` does not require Spring Session and does not go through `SessionRepository`.
- Spring Session does not require `@Cacheable` or `RedisCacheManager` to store sessions.
- Calling `RedisTemplate` directly does not make Spring Cache cache a method, nor does it cause Spring Session to create sessions.
- `RedisCacheManager` and Redis-backed `SessionRepository` can both leverage the `RedisConnectionFactory` configured by Spring Boot. Each component still maintains its own key formats, serializers, and expiration policies.

Note: Redis Cache typically operates via `RedisCacheWriter` and Redis connections. Do not assume modifying serializers on an arbitrary `RedisTemplate` bean automatically changes cache or session serialization formats.

## 3. Spring Cache: boundary of caching method results

### 3.1. Spring Cache is an abstraction

Spring Cache targets business methods: before executing a method, Spring checks whether a result already exists under a **cache key**.

~~~text
Client calls CatalogService.getProduct(42)
                    |
                    v
              Cache interceptor
                    |
              Key 42 present?
               /           \
              Yes           No
              |              |
         Return cached    Invoke real method
            result        -> query DB/API
                              |
                              v
                         Write result
                           to cache
                              |
                              v
                         Return result
~~~

Spring Cache provides a uniform contract; the actual store can be in-JVM memory or Redis. When choosing Redis, Spring uses a matching `CacheManager`—commonly `RedisCacheManager` in Spring Boot applications using Spring Data Redis.

### 3.2. Example of @Cacheable and @CacheEvict

~~~java
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Service
public class CatalogService {

    private final ProductRepository productRepository;

    public CatalogService(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @Cacheable(cacheNames = "catalogProducts", key = "#id")
    public ProductView getProduct(Long id) {
        Product product = productRepository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Not found: " + id));

        return new ProductView(product.getId(), product.getName());
    }

    @CacheEvict(cacheNames = "catalogProducts", key = "#id")
    public void renameProduct(Long id, String newName) {
        Product product = productRepository.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Not found: " + id));
        product.setName(newName);
        productRepository.save(product);
    }
}
~~~

In this example, `ProductRepository`, `Product`, and `ProductView` are hypothetical domain types. Expected flow:

1. First call to `getProduct(42)`: cache miss, runs the repository query, and caches the result.
2. Subsequent calls with the same key: returns the cached result without querying the repository again.
3. After `renameProduct(42, ...)`: the `catalogProducts` entry for key `42` is evicted so the next read fetches the updated name.

If the repository reads data written by external systems or another write path bypasses `renameProduct`, the cache **does not automatically know** source data changed. Design appropriate TTLs, eviction, versioned keys, or invalidation events.

### 3.3. Related annotations

| Annotation | Effect | Key considerations |
|---|---|---|
| `@Cacheable` | Checks cache first, runs method on miss, then stores result | Applies to calls passing through the Spring proxy/interceptor |
| `@CachePut` | Always executes the method and updates the cache with the result | Not a general substitute for `@Cacheable` |
| `@CacheEvict` | Removes one or more cache entries | Supports `allEntries = true` to clear an entire cache; weigh the cost |
| `@Caching` | Combines multiple cache operations on one method | Useful when evicting across multiple cache names |
| `@CacheConfig` | Declares shared cache settings for a class | Does not enable caching on its own |

You can control caching conditions with `condition` and decide whether to store results with `unless`. For example:

~~~java
@Cacheable(
    cacheNames = "catalogProducts",
    key = "#id",
    unless = "#result == null"
)
public ProductView getProduct(Long id) {
    // ...
}
~~~

**Important technical boundaries:**

- In default proxy mode, one bean method calling another `@Cacheable` method on **the same object** (*self-invocation*) bypasses the interceptor, so the annotation has no effect.
- `@EnableCaching` is required to activate annotation-driven caching. Declaring cache dependencies alone is not enough.
- Redis Cache uses its own TTL from `CacheManager` configuration. That TTL is **not** the HTTP session lifetime.
- Caching does not automatically participate in database transactions. Evicting a cache entry before a DB transaction commits and then rolling back can create an inconsistency window. Align invalidation timing with transaction boundaries in your design.
- When Redis is unreachable, cache calls may throw exceptions per the active `CacheErrorHandler`. Do not assume cache failures automatically fall back to querying the DB.

### 3.4. When is Spring Cache the right tool?

It fits values that **can be recomputed/reloaded** from a reliable source: product catalogs, display configurations, reference data, expensive query results, and repeated calculations.

Never treat cache entries as the sole source of truth for orders, account balances, or critical audit logs. If an entry expires or is evicted, the application must be able to recover it or accept losing it.

## 4. Spring Session: boundary of HTTP session state

### 4.1. The problem without centralized sessions

In traditional servlet web applications, sessions are managed by the servlet container. Stored in a single instance's memory, a session is absent on other instances.

~~~text
                Browser
            Session ID cookie
                    |
                Load balancer
                 /        \
                v          v
          Spring App A   Spring App B
          memory A       memory B

   Request 1 goes to A -> stores session on A
   Request 2 goes to B -> B cannot see A's session
~~~

Sticky sessions at the load balancer mitigate this partially, yet state remains tied to individual instances and lost if an instance goes down. Spring Session moves session state into a shared store such as Redis:

~~~text
                Browser
            Session ID cookie
                    |
                Load balancer
                 /        \
                v          v
          Spring App A   Spring App B
                 \        /
                  \      /
                Spring Session
                       |
                       v
                  Shared Redis
                  Session store
~~~

Both app instances can access the same session when sharing Spring Session configuration and receiving the same valid session ID.

### 4.2. What does Spring Session change?

Spring Session plugs into the web framework's pipeline, such as via `SessionRepositoryFilter` in Servlet apps. Controller code can keep using `HttpSession` as before:

~~~java
import jakarta.servlet.http.HttpSession;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/profile")
public class ProfileController {

    @GetMapping("/language")
    public String language(HttpSession session) {
        String language = (String) session.getAttribute("language");
        return language == null ? "vi" : language;
    }

    @GetMapping("/language/en")
    public String chooseEnglish(HttpSession session) {
        session.setAttribute("language", "en");
        return "saved";
    }
}
~~~

The controller does not need to know whether sessions live in memory, Redis, or JDBC. With Redis-backed Spring Session installed and configured, loading/saving sessions delegates to `SessionRepository`.

General flow:

1. The browser sends a cookie carrying the session ID.
2. Spring Session reads the ID, looks up the session record in Redis, and exposes the corresponding `HttpSession`.
3. Controllers or Spring Security read/write session attributes.
4. The session repository persists changes according to the configured save mode.
5. Once invalidated or past its inactivity timeout, the session is no longer valid.

Spring Session can persist the **Spring Security context** when using HTTP-session authentication. However, Spring Session **does not perform login, authorization, or JWT issuance itself**; those belong to Spring Security and the application's chosen auth protocol.

### 4.3. Session data and TTL

Sessions hold data scoped to **one client's session**, such as language preferences, a session shopping cart, cross-request attributes, or login state under session authentication.

Session lifetime is typically governed by **max inactive interval**: after a period of inactivity, the session expires. Managing TTLs and expiration indexes in Redis is the responsibility of the Spring Session implementation, which can vary by repository mode or version.

Unlike caching a query result:

- Cache entries can be refreshed per each cache's policy.
- Sessions bind to an ID, support `invalidate()`, session creation, session ID rotation, and lifecycle management.
- Evicting `catalogProducts` **does not** log out active sessions.
- Calling `session.invalidate()` **does not** evict user-related `@Cacheable` results.

In reactive WebFlux applications, Spring Session works with `WebSession` and reactive components. The `HttpSession` examples here target Spring MVC/Servlet applications.

### 4.4. Security and reliability

- A session ID is a **credential** referencing the session; protect cookies with HTTPS, `Secure`, `HttpOnly`, and appropriate `SameSite` policies.
- Never write session IDs, auth tokens, or sensitive attributes into uncontrolled logs.
- Configure serialization for stored session attributes. Putting arbitrary objects into sessions can break deserialization during new application deployments.
- Redis outages can fail requests requiring sessions. Redis evicting session keys can prematurely log users out.
- Sharing sessions in Redis **does not mean** every request continues uninterrupted during a Redis failover, nor does it guarantee zero loss of recent updates.

In fully **stateless** JWT architectures where servers retain no session state, Spring Session may be unnecessary. When using `HttpSession` or stateful authentication, Spring Session solves a different problem than self-contained tokens.

## 5. Spring Data Redis: boundary of Redis operations

### 5.1. The Redis API layer

Spring Data Redis does not pre-classify keys as cache, session, or business data. It supplies tools for applications to work with Redis:

- `RedisConnectionFactory` creates and manages connections through drivers like **Lettuce**.
- `RedisTemplate<K, V>` provides an API to execute Redis operations with serializers.
- `StringRedisTemplate` is a `RedisTemplate` optimized for string keys and values.
- `opsForValue()`, `opsForHash()`, `opsForList()`, `opsForSet()`, and `opsForZSet()` match Redis data-structure groups.
- Supports Pub/Sub, Redis Streams, Lua scripts, pipelines, and transaction capabilities depending on the API.
- Redis repositories with `@RedisHash` offer repository-style object mapping when appropriate.

Direct Spring Data Redis usage is ideal when business logic needs **specific Redis data structures or commands**, such as sorted sets for leaderboards, counters, TTL-bound markers, Redis Streams queues, or publish/subscribe channels.

### 5.2. Example of direct operations

~~~java
import java.time.Duration;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

@Service
public class MetricsService {

    private final StringRedisTemplate redis;

    public MetricsService(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public Long recordProductView(long productId) {
        String key = "metrics:product-views:" + productId;
        return redis.opsForValue().increment(key);
    }

    public void rememberLastViewed(long userId, long productId) {
        String key = "user:last-viewed:" + userId;
        redis.opsForValue().set(
                key,
                Long.toString(productId),
                Duration.ofHours(24)
        );
    }
}
~~~

Here:

- `increment` executes the Redis numeric increment operation.
- `set(..., Duration)` writes a value with a TTL **chosen by the application**.
- Neither key **automatically becomes a Spring Cache entry**.
- Neither key **becomes an HTTP session** or is managed by Spring Session's lifecycle.

Counters like these suit metrics that can tolerate loss characteristics of your Redis deployment. If business requirements demand exact, auditable counts or cross-database transactions, build stronger storage and synchronization architecture.

### 5.3. Are Redis repositories Spring Cache?

No. Consider a Redis entity:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.redis.core.RedisHash;

@RedisHash("tempCart")
public class TempCart {

    @Id
    private String id;

    private String ownerId;

    // Constructors, getters, and setters
}
~~~

With proper setup, its repository can be an interface:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface TempCartRepository
        extends CrudRepository<TempCart, String> {
}
~~~

This is **repository-style object storage**, not Spring caching arbitrary method return values. Deleting records, updating TTLs, and enforcing business invariants remain the responsibility of the repository and application design.

Combining `CrudRepository<TempCart, String>` with `@Cacheable` on a method returning `TempCart` introduces **two distinct storage layers**: the Redis repository stores records, while the cache stores method results on top. Only combine them intentionally so you do not create duplicate data and tangled invalidation.

### 5.4. Do not confuse RedisTemplate with CacheManager

A common configuration mistake is changing a `RedisTemplate`'s serializer and assuming caches and sessions switch to JSON as well.

In practice:

- `RedisTemplate` uses the serializers configured on that template.
- `RedisCacheManager` uses `RedisCacheConfiguration`/`RedisCacheWriter`, with its own serialization and key prefix.
- Spring Session Redis uses Spring Session's serializer and storage model; customizing it requires its dedicated serializer configuration, such as a bean named `springSessionDefaultRedisSerializer` in compatible setups.

Thus, the three components **can share connections without sharing serialization policies**. Whenever changing JSON/JDK serialization formats, account for reading existing keys and migration plans.

## 6. Example of one Spring Boot app using all three

Consider an e-commerce app with:

- A catalog read API caching database query results.
- A web UI storing language preferences and session state.
- A view-counter feature using Redis directly.

All three can share one Redis connection inside a single Spring Boot application while remaining cleanly separated across three APIs.

### 6.1. Key dependencies

Maven example (`<dependencies>` in a Spring Boot project):

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-redis</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-cache</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.session</groupId>
        <artifactId>spring-session-data-redis</artifactId>
    </dependency>
</dependencies>
~~~

In the Spring Boot 3.x ecosystem managed by the Spring Boot BOM/parent, explicit versions for these dependencies are normally omitted.

Dependency roles:

- `spring-boot-starter-data-redis`: Redis connectivity and Spring Data Redis APIs.
- `spring-boot-starter-cache`: cache abstraction infrastructure; with Redis and matching config, enables `RedisCacheManager`.
- `spring-session-data-redis`: Redis-backed session repository; in web apps with auto-configuration, Boot configures Spring Session.
- `spring-boot-starter-web`: illustrates a Servlet web app using `HttpSession`.

When you only need one feature, do not pull in all three dependencies unnecessarily. For example, a REST API caching products in Redis does not need `spring-session-data-redis` just because it uses caching.

### 6.2. Illustrative configuration

~~~yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379

  cache:
    type: redis
    cache-names:
      - catalogProducts
    redis:
      time-to-live: 10m
      cache-null-values: false

  session:
    timeout: 30m
    redis:
      namespace: shop:session
~~~

This example sets a dedicated session namespace, a 10-minute cache TTL, and a 30-minute session inactivity timeout. The two durations do not interfere with each other.

These properties illustrate Spring Boot 3.x configuration; verify exact property names against your deployed Boot and Spring Session versions. Production setups also add username/password, ACLs, TLS, or Sentinel/Cluster configuration under Redis connection properties.

To enable annotation caching:

~~~java
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Configuration;

@Configuration
@EnableCaching
public class CacheConfig {
}
~~~

Do not place `@EnableCaching` on controllers—it belongs on application context configuration. Spring Session activates via Spring Boot auto-configuration once the session starter/module and web stack are present; if adding explicit enable annotations or custom repository beans, understand how they override defaults to avoid conflicting configurations.

### 6.3. Three requests in the same application

**Request A — read product:**

~~~text
GET /products/42
 -> CatalogService.getProduct(42)
 -> Spring Cache checks catalogProducts::42
 -> On miss: reads DB and caches for 10 minutes
 -> Returns ProductView
~~~

**Request B — update language preference:**

~~~text
GET /profile/language/en
 Cookie: SESSION=<session-id>

 -> Spring Session looks up session by session ID
 -> ProfileController calls session.setAttribute("language", "en")
 -> Spring Session persists session per its configured policy
 -> Subsequent requests can read back "en"
~~~

The cookie name illustrates Spring Session Servlet's default cookie resolver (`SESSION`); cookie name and attributes can be customized.

**Request C — increment view count:**

~~~text
POST /metrics/products/42/view
 -> MetricsService.recordProductView(42)
 -> StringRedisTemplate INCR metrics:product-views:42
 -> Returns counter value
~~~

All three requests write to the same Redis server, yet:

- A owns cache invalidation and cache TTL.
- B owns session IDs, session expiration, and security context.
- C owns key schemas, TTLs, and counter correctness.

**There is no automatic cross-synchronization** across the three keyspaces. Logging out does not delete counter keys; `@CacheEvict` does not delete sessions; calling `RedisTemplate.delete()` on an arbitrary key does not notify other abstractions to update internal state.

## 7. Keyspace, serializers, and TTL: three easily overlooked boundaries

### 7.1. Partitioning keys by responsibility

Example keys you might observe in Redis:

~~~text
catalogProducts::42                 # Spring Cache (default key illustration)
shop:session:sessions:<session-id>  # Spring Session (keyspace illustration)
metrics:product-views:42            # Direct Spring Data Redis
~~~

Exact key names vary with cache prefix, namespace, repository type, Spring Session implementation, and version. Never build business logic tied to Spring Session's internal key layout.

Suggested convention:

| Key owner | Example prefix | Who is allowed to manage lifecycle? |
|---|---|---|
| Spring Cache | `cache:catalogProducts:` | `CacheManager`, cache operations, invalidation policy |
| Spring Session | `shop:session:` | Spring Session |
| Direct Redis | `shop:metrics:`, `shop:ranking:` | Corresponding domain component |

Separate prefixes lower key-collision risk and make key counts, TTLs, and memory usage easier to monitor. **Prefixes do not provide security or resource isolation**: if strict resource isolation is needed, consider separate Redis deployments.

### 7.2. Each layer configures its own serializers

For example, caches may use JSON for DTOs, sessions may use a dedicated serializer for session attributes, and `StringRedisTemplate` writes UTF-8 strings. Do not expect all three layers to read each other's keys/values interchangeably.

Issues to anticipate:

- With JDK serialization, changing classes, `serialVersionUID`, or dependencies can cause deserialization errors across application versions.
- With JSON, define type representation, date/time formats, polymorphism limits, and input trust boundaries.
- With Spring Session, session attributes must remain compatible across app instances and rolling deployments.
- When changing serializers, old keys persist until TTL expiration or deletion; new readers may fail on legacy payloads.

Treat format changes as controlled data migrations or namespace bumps rather than merely tweaking one bean.

### 7.3. TTLs mean different things

Suppose Redis holds three entries at the same moment:

| Key | TTL | Reason for expiration |
|---|---|---|
| `catalogProducts::42` | 10 minutes | Cache tolerates reusing results for a bounded window |
| Session with ID `abc` | 30 minutes of inactivity | Session expires if the user stops interacting |
| `user:last-viewed:7` | 24 hours | Business rule for recently viewed products |

Reading a product does not extend the user's session. Using a session does not extend the product cache's TTL. Direct Redis commands only get TTLs when explicitly requested or governed by application policy.

Session TTLs can also involve internal Spring Session expiration/index keys; do not assume running `EXPIRE` manually on one matching key properly updates the entire session policy.

## 8. Responsibilities when data changes or Redis fails

| Event | Spring Cache | Spring Session | Direct Spring Data Redis |
|---|---|---|---|
| DB updates product name | Must update/evict cache or wait for TTL | Session untouched | Self-managed keys only change if code writes to them |
| User logs out | Product cache may remain intact | Session must be invalidated per auth flow | Counters/leaderboards are not auto-deleted |
| Key expires by TTL | Next read is a cache miss | Session expires or becomes invalid | Value disappears; application decides recovery |
| Redis disconnects | Cache calls may error or hit fallback strategy | Requests needing sessions may error | Redis operations may error/timeout |
| Redis failover | Cache commands may interrupt or retry per config | May affect sessions and in-flight requests | Must evaluate idempotency, retries, and lost writes |
| New deployment changes model | Cached DTOs may fail deserialization | Old session attributes may fail deserialization | Depends on self-defined key/value formats |

### 8.1. Why shouldn't cache and session be lumped together?

Caching targets performance: on a cache miss, the system can reload from the source of truth. Hence caches typically run with TTLs and bounded memory that tolerate eviction.

Sessions carry authentication and workflow state: unintended eviction forces users to re-authenticate or drops their in-progress cart state. Therefore:

- Do not assume a cache-oriented eviction policy is safe for production sessions.
- Monitor `used_memory`, `evicted_keys`, network errors, latency, session counts, and failover times.
- When availability requirements and blast radii differ sharply, separate the Redis instance/cluster for **sessions** from the Redis used for **caches and ephemeral data**.
- If still sharing Redis, strictly govern memory sizing, TTLs, eviction policies, namespaces, access control, and failover behavior across all three workloads.

### 8.2. Cache fallback is not session fallback

If a Redis cache fails, an application can sometimes **bypass the cache and query the DB**. That mechanism must be designed, configured, and tested deliberately; not every cache error automatically degrades into a cache miss by default.

If a Redis session store fails, you cannot simply synthesize an empty session and treat the user as logged in. Doing so violates authentication contracts and creates security flaws. Define explicit timeout, retry, error-display, or re-authentication rules.

If a direct Redis call fails, determine whether the command may have executed on Redis before the client timed out. Retrying `INCR` blindly can double-count; retrying arbitrary writes is not automatically safe.

## 9. Common misconceptions

### Misconception 1 — "Adding spring-boot-starter-data-redis makes @Cacheable work automatically"

False. Spring Data Redis provides connectivity and Redis operations. Annotation-based caching requires Spring Cache infrastructure, `@EnableCaching`, and an appropriate `CacheManager`.

### Misconception 2 — "Once RedisTemplate is configured, sessions automatically live in Redis"

False. `RedisTemplate` is only a Redis access helper. Redis-backed sessions require integrating Spring Session and its repository. An app using `RedisTemplate` may still be storing HTTP sessions in servlet-container memory.

### Misconception 3 — "With Spring Session, Spring Security is no longer needed"

False. Spring Session provides session storage and lifecycle management. Spring Security handles authentication, authorization, and web-layer security controls.

### Misconception 4 — "Spring Cache stores data permanently"

False. Caches are designed to allow eviction, TTL expiration, and misses. Even with long or no expiration, never treat a cache as the canonical system of record.

### Misconception 5 — "Changing RedisTemplate's serializer changes all of Redis"

False. Serializers belong to each individual component: `RedisTemplate`, `RedisCacheManager`, and session repositories maintain separate lifecycles, key models, and serializers.

### Misconception 6 — "Logging out clears all user-related cache entries"

False. Session invalidation and cache invalidation are separate operations. If caches store user-private data, design keys, access checks, TTLs, and explicit eviction per business flow rather than relying on logout to clean caches.

### Misconception 7 — "Cache, session, and Redis repositories share Redis, so they share one TTL"

False. TTL belongs to individual keys or each layer's policy. Cache entry TTL, session inactivity timeout, and business-key TTL operate independently.

### Misconception 8 — "Sharing Redis means identical operational cost"

False. One server can host workloads with very different growth patterns: caches generate short-lived keys, sessions require stable retention, and leaderboards or Streams grow differently. Plan memory, persistence, eviction, and redundancy according to each dataset's role.

## 10. How to inspect boundaries in a real project

When reading Spring Boot code that uses Redis, trace these four questions:

**1. Who owns the API being called?**

~~~text
@Cacheable / CacheManager          -> Spring Cache
HttpSession / SessionRepository    -> Spring Session
RedisTemplate / RedisRepository    -> Spring Data Redis
~~~

**2. Who determines the key and expiration time?**

- Cache: cache name, key expression, `CacheManager`, cache TTL.
- Session: session ID, `SessionRepository`, inactivity timeout.
- Direct Redis: key conventions, commands, and TTLs defined by the feature.

**3. If Redis loses all data, what happens?**

- Cache: users experience higher latency while the system reloads from origin.
- Session: users lose active sessions and must sign in again or rebuild session state.
- Direct data: impact depends on the feature; some keys can be rebuilt, while others lose metrics or important state.

**4. Are corresponding invalidation and retry policies in place?**

- Caches need updates/evictions when source data changes.
- Sessions need accurate lifecycles and credential protection.
- Direct Redis operations need consistency rules, atomicity, and command-appropriate idempotency.

Looking at **the purpose of the data** and **the abstraction owning its lifecycle** is far more reliable than seeing a key in Redis and calling everything a “cache.”

## 11. Thought exercise: picking the right API

| Requirement | Primary component to use | Why? |
|---|---|---|
| Method loading product config from DB is slow and results can be 5 minutes stale | Spring Cache + `RedisCacheManager` | Caches method results while the DB remains the source of truth |
| Two Spring Boot instances must share login sessions | Spring Session + Redis | `SessionRepository` shares sessions across instances |
| Store the user's language choice for the current session | `HttpSession` managed by Spring Session | Value tied to session lifecycle |
| Count video views per key | `StringRedisTemplate` and `INCR` | Application manages counters directly rather than caching a method result |
| Build a score-based leaderboard | `RedisTemplate.opsForZSet()` | Requires sorted sets and score ordering |
| Cache product reads by ID while updates always go to the canonical DB | Spring Cache + DB repository layer | Separates cache from source-of-truth writes |
| Store Redis objects with ID-based CRUD | Spring Data Redis repository | Needs direct object/key mapping, not necessarily caching |
| Authorize APIs with Bearer JWT and no server-side session | Spring Security resource server; Spring Session not needed by default | Stateless token verification needs no session repository |

## 12. Summary by architectural responsibility

~~~text
                 "I need to reuse method results"
                                  |
                                  v
                             SPRING CACHE
                         Cache / CacheManager
                                  |
                       RedisCacheManager (if using Redis)
                                  |
                                  v
                                 Redis

               "I need to preserve HTTP sessions across requests"
                                  |
                                  v
                            SPRING SESSION
                      SessionRepository / HttpSession
                                  |
                     Redis-backed SessionRepository
                                  |
                                  v
                                 Redis

               "I need Redis commands or Redis structures"
                                  |
                                  v
                           SPRING DATA REDIS
                       RedisTemplate / Repositories
                                  |
                                  v
                                 Redis
~~~

Spring Cache decides **which results get reused**. Spring Session decides **whose session exists and when it expires**. Spring Data Redis provides **the mechanics to work with Redis** for both applications and other adapters.

When designing a Spring application, first identify whether data belongs to caching, session state, or self-managed business/ephemeral state; only then select the matching dependencies, APIs, key namespaces, serializers, TTLs, error-handling strategies, and operational requirements.
