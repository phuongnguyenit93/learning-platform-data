# Self-Assigning UUIDs or Identifiers Before Saving

In Spring Data Relational R2DBC, an entity's identifier can be generated by the database or assigned directly in the application before writing. Self-assigning UUIDs lets the application know the ID as soon as the object is created, which is convenient for establishing relationships between objects, emitting events, logging, handling distributed data, and designing idempotent operations.

However, assigning an ID before calling `save` comes with an important consideration: Spring Data must determine whether the entity is new or already exists. An entity with a non-`null` ID may be treated as an existing entity and updated instead of inserted. Therefore, choosing an ID strategy must go hand in hand with how Spring Data detects an entity's new state.

This lesson explains how to generate UUIDs in the application, how to map UUIDs to the schema, how to control new-entity detection, how to choose between application-assigned and database-generated IDs, as well as considerations for uniqueness, performance, and testing.

## 1. What Role Does an ID Play in a Data Model?

An ID is the stable identifier of a record. It enables the application to reference an entity without relying on mutable attributes such as name, email, or status.

A good primary key typically has these characteristics:

- Unique within the table or the designed scope.
- Stable throughout the lifetime of the record.
- Free of business meaning that changes easily.
- Consistent in data type and representation across entities, schemas, and references.
- Backed by a database constraint to prevent two records from sharing the same ID.

For example, an email can be used to sign in, yet it is not always a good primary key. Users can change their email; a dedicated ID allows other tables to keep referencing the same person.

In Spring Data Relational, the primary key property is normally marked with `@Id`:

```java
import java.util.UUID;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
    @Id UUID id,
    String email,
    String displayName
) {}
```

`@Id` tells Spring Data which property is the entity's identifier. This annotation does not itself dictate where the ID is generated. ID generation can happen in the application, in the database, or in a dedicated ID-issuing system.

## 2. Generating UUIDs in the Application

Java provides `java.util.UUID`. The simplest way to generate a random UUID is `UUID.randomUUID()`:

```java
import java.util.UUID;

UUID id = UUID.randomUUID();
```

This method generates a version 4 UUID based on random numbers. The ID can be created before accessing the database, so the application knows the identifier right when constructing the entity.

Order creation example:

```java
import java.math.BigDecimal;
import java.util.UUID;

public record NewOrder(
    UUID id,
    Long customerId,
    BigDecimal total
) {
    public static NewOrder create(
            Long customerId,
            BigDecimal total) {
        return new NewOrder(
            UUID.randomUUID(),
            customerId,
            total
        );
    }
}
```

The service can convert the command into an entity and save it:

```java
public Mono<Order> create(NewOrder command) {
    Order order = new Order(
        command.id(),
        command.customerId(),
        command.total(),
        OrderStatus.NEW,
        null
    );

    return orders.save(order);
}
```

The example above assumes the `Order` entity has a nullable version property used to detect a new entity; this will be covered in the following sections. If the entity only has a pre-assigned ID and no suitable new-entity detection mechanism, calling `save` can take the update branch.

### Benefits of Assigning IDs Early

Self-assigning IDs before saving is useful in these scenarios:

- Building an aggregate composed of multiple objects that need to reference each other before writing.
- Including the ID in logs, traces, or events as soon as business processing begins.
- Creating messages or commands with a stable identifier prior to the database write transaction.
- Implementing idempotent operations, where a retried request continues to use the same predetermined ID.
- Generating data across multiple nodes without asking a database for the next sequence number.

Having an ID early does not mean the record already exists in the database. The application must distinguish the "already has an identifier" state from the "successfully persisted" state.

## 3. Choosing a UUID Type and Storage Format

A UUID is logically 128 bits long. Java represents it with `java.util.UUID`, while database storage depends on the database engine.

| Database Engine | Commonly Used Type | Notes |
| --- | --- | --- |
| PostgreSQL | `UUID` | Has a native UUID type and R2DBC driver supports corresponding mapping. |
| MySQL | `BINARY(16)` or `CHAR(36)` | Requires consistent byte order and converters if using binary form. |
| SQL Server | `uniqueidentifier` | Has a database-specific UUID type. |
| Engines without native UUID | `CHAR(36)`, `VARCHAR(36)`, or `BINARY(16)` | Choose a clear format and conversion rule. |

With PostgreSQL, the schema can be declared as:

```sql
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    total NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL
);
```

The entity uses the corresponding `UUID` type:

```java
@Table("orders")
public record Order(
    @Id UUID id,
    @Column("customer_id") Long customerId,
    BigDecimal total,
    OrderStatus status,
    @Version Long version
) {}
```

With MySQL, if storing UUIDs as `BINARY(16)`, check whether the driver maps `UUID` directly. If not, you may need converters between UUID and byte array. If using `CHAR(36)`, standardize casing, hyphens, collation, and column length.

Do not switch column types between `BINARY(16)` and `CHAR(36)` without a data migration. Other applications and services referencing the same ID must use the same representation convention.

## 4. UUID v4, UUID v7, and Other Options

Not all identifiers share the same properties.

| Identifier Type | Characteristics | When to Consider |
| --- | --- | --- |
| UUID v4 | Random; does not reflect chronological order. Java's `UUID.randomUUID()` generates this type. | Suitable for distributed identification and simple setup. |
| UUID v7 | Includes a timestamp component so IDs are roughly ordered by creation time. | Consider when wanting to improve index locality while still needing UUIDs. |
| ULID | 26-character string with timestamp and random components. | Useful when needing string IDs with lexicographical time ordering. |
| Snowflake-style ID | Integer combining timestamp, node, and sequence via an algorithm. | Suitable when needing ordered numeric IDs and managed ID-issuing infrastructure. |
| Identity/sequence | Database issues numbers via its engine mechanism. | Suitable when wanting integer keys and accepting ID generation from the database. |

UUID v4 values are randomly distributed. With certain B-tree structures, inserting random IDs can increase page splits and reduce locality compared to ordered keys. UUID v7 includes a time component, which can improve sequentiality of inserts under certain workloads. Actual impact depends on the database, indexes, write distribution, and storage layout; measure with a realistic workload.

UUID v7 also reveals approximate creation time. If creation time is sensitive information in the business domain, consider this implication.

Java's `UUID.randomUUID()` does not generate UUID v7. If you choose UUID v7, use a library or mechanism explicitly supported on your platform and keep the format consistent across all producers.

ULID is not a UUID. If the schema uses a native UUID type, you cannot blindly bind a ULID string as a UUID. Choose the appropriate column type and converter.

## 5. Key Issue: How Does Spring Data Detect New Entities?

`ReactiveCrudRepository.save(entity)` does not simply always run `INSERT`. Spring Data must determine whether the entity is new or existing to choose insert or update.

By default, Spring Data checks the version property if the entity has `@Version`; otherwise, it typically checks the ID. With a pre-assigned, non-`null` ID, the entity may be detected as existing.

Example of an entity with only an ID:

```java
@Table("orders")
public record Order(
    @Id UUID id,
    Long customerId,
    BigDecimal total
) {}
```

When creating the object:

```java
Order order = new Order(
    UUID.randomUUID(),
    42L,
    new BigDecimal("125.00")
);
```

`id` is already non-`null`. Under the default detection strategy based solely on ID, Spring Data can treat the entity as existing and perform an update. Because the record is not yet in the database, the update may affect zero rows or produce unexpected behavior.

You must explicitly design how new entities are marked.

## 6. Using `@Version` to Detect New Entities with Pre-Assigned IDs

A suitable approach is adding a nullable version property annotated with `@Version`:

```java
import java.math.BigDecimal;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public record Order(
    @Id UUID id,
    Long customerId,
    BigDecimal total,
    @Version Long version
) {}
```

When creating a new entity, pass the assigned ID while leaving `version` as `null`:

```java
Order order = new Order(
    UUID.randomUUID(),
    42L,
    new BigDecimal("125.00"),
    null
);
```

Spring Data uses the version property to detect a new entity. An unpopulated version indicates the entity has not been persisted yet. After inserting, Spring Data initializes the version for optimistic locking. When the entity is read back, the version has a value and the next `save` is processed as an update.

You can declare the schema as:

```sql
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    total NUMERIC(12, 2) NOT NULL,
    version BIGINT NOT NULL
);
```

Version serves more than just new-state detection. It also enables optimistic locking: update statements check the current version. If another transaction has modified the record, an operation with an outdated version fails to update and Spring Data reports an optimistic locking error.

Service example:

```java
public Mono<Order> create(Long customerId, BigDecimal total) {
    Order order = new Order(
        UUID.randomUUID(),
        customerId,
        total,
        null
    );

    return orders.save(order);
}
```

Preserve the version property on loaded entities and pass it through update steps. Never reset version to `null` on an existing entity, as doing so can cause Spring Data to misinterpret the entity's state.

If the application does not want optimistic locking, `@Version` still introduces concurrency semantics. Decide deliberately whether you want concurrent-update protection rather than adding a version column mechanically.

## 7. Using `Persistable` When You Want Direct Control Over New State

Another option is implementing `Persistable<ID>`. This interface provides `getId()` and `isNew()`, allowing the entity to decide for itself whether it is new or existing.

Structural example:

```java
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public class Customer implements Persistable<UUID> {

    @Id
    private UUID id;

    private String email;

    @Transient
    private boolean newEntity = true;

    protected Customer() {
    }

    public Customer(UUID id, String email) {
        this.id = id;
        this.email = email;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markNotNew() {
        this.newEntity = false;
    }
}
```

`@Transient` marks `newEntity` as in-memory state, not a table column. `isNew()` returns `true` to request an insert and `false` to request an update.

What needs careful management is when `newEntity` transitions to `false`. Mark the entity as existing only after the insert succeeds. If you mark it before the publisher completes and the insert fails, a retry could be routed to an update.

For entities loaded from the database, `newEntity` must be initialized to `false`. You can manage this using a Spring Data Relational entity callback or a centralized mapping mechanism. A reloaded entity should never report `isNew() == true`.

Choose `Persistable` when the application has a clear reason to manage new state manually. If the entity already has `@Version` and a suitable version property, relying on the version mechanism is usually simpler.

## 8. Distinguishing Pre-Assigned IDs from Database-Generated IDs

There are two main strategies:

### Application-Assigned IDs

The application generates a UUID before calling the repository:

```java
UUID id = UUID.randomUUID();

Order order = new Order(
    id,
    customerId,
    total,
    OrderStatus.NEW,
    null
);

return orders.save(order);
```

Advantages:

- ID is available immediately upon creating the entity.
- References can be constructed before writing.
- Independent of database sequences or identity columns.
- Convenient for messages, events, logs, and idempotency keys.
- Easy to generate data across multiple application instances.

Points to watch out for:

- New-entity detection must be handled properly.
- The database still needs a primary key or unique constraint.
- UUID formatting must be consistent across services.
- Random UUIDs can affect index locality depending on workload.

### Database-Assigned IDs

With auto-incrementing IDs or database-side UUID defaults, the application typically leaves the ID as `null` and the database generates the value on insert.

PostgreSQL example:

```sql
CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id BIGINT NOT NULL,
    total NUMERIC(12, 2) NOT NULL
);
```

The entity has a null ID before inserting:

```java
Order order = new Order(
    null,
    customerId,
    total,
    OrderStatus.NEW,
    null
);
```

Spring Data can detect the new entity based on ID/version and issue an insert. However, retrieving the database-generated value depends on the driver and how generated values are supported. If you need certainty about receiving the UUID immediately after insert, verify behavior with the real driver or use explicit SQL that returns the ID.

With PostgreSQL, you can use `DatabaseClient` and `RETURNING`:

```java
return databaseClient.sql("""
        INSERT INTO orders (customer_id, total)
        VALUES (:customerId, :total)
        RETURNING id
        """)
    .bind("customerId", customerId)
    .bind("total", total)
    .map((row, metadata) -> row.get("id", UUID.class))
    .one();
```

The statement omits the `id` column, so the `gen_random_uuid()` default applies. `RETURNING` emits the newly generated ID. This syntax is PostgreSQL-specific; other database engines have their own generated-key mechanisms.

## 9. Do Not Confuse `@Id` with JPA's `@GeneratedValue`

Spring Data Relational R2DBC uses `org.springframework.data.annotation.Id` to mark the ID. Do not copy JPA's `@GeneratedValue` strategy directly into R2DBC and expect the driver to handle it like Hibernate.

ID generation in Spring Data Relational depends on how an entity is detected as new, mapping metadata, driver generated-values support, and the database schema. With self-assigned UUIDs, the application assigns the value directly. With database-assigned IDs, the schema and insert statement must give the database the opportunity to generate the value.

If a project uses both JPA and R2DBC, avoid importing the wrong same-named annotation or assuming a single entity mapping works unmodified across both technologies.

## 10. Pre-Generating IDs for Multi-Object Aggregates

A clear benefit of UUIDs is being able to generate IDs for multiple related objects before saving.

Example of an order with multiple order lines:

```java
UUID orderId = UUID.randomUUID();

Order order = new Order(
    orderId,
    customerId,
    total,
    OrderStatus.NEW,
    null
);

List<OrderLine> lines = items.stream()
    .map(item -> new OrderLine(
        UUID.randomUUID(),
        orderId,
        item.productId(),
        item.quantity()
    ))
    .toList();
```

Each `OrderLine` can reference `orderId` even before the order is inserted. This is helpful when the application needs to construct an entire command or data structure before writing begins.

However, having pre-assigned IDs does not replace transactions. If the order and its lines must be saved together, use a reactive transaction to ensure the entire operation succeeds or rolls back as required.

If objects belong to separate independent aggregates, do not automatically bundle them into one long transaction just because IDs were generated beforehand. Define consistency boundaries according to business requirements.

## 11. UUIDs and Uniqueness in Distributed Systems

UUID v4 has a vast identifier space, so the probability of random collision is extremely low when generated properly. Still, never omit constraints just because the probability is low.

Always declare a primary key or unique constraint:

```sql
CREATE TABLE customer (
    id UUID PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

The database is the final guarantor of uniqueness. Applications should handle duplicate-key errors if they occur rather than assuming collisions are impossible.

A few guidelines:

- Do not invent custom UUIDs by concatenating timestamps and arbitrary random strings.
- Do not use `Math.random()` to build UUIDs manually.
- Do not truncate a UUID to a shorter segment just to make IDs look nicer.
- Do not remove database constraints just because the application generates IDs.
- When retrying a request that requires idempotency, keep the same ID or idempotency key for that business operation; do not generate a new ID on every attempt if the goal is to avoid creating duplicate records.

A UUID is not an authorization mechanism. An unpredictable ID does not replace checking whether the user has permission to access the record.

## 12. Using Stable IDs for Idempotency

In reactive systems, a request can time out after the database commits but before the client receives the response. A client retrying the request could create duplicate records if the application generates a new ID on every retry.

One solution is accepting an idempotency key from the client or creating a stable operation ID at the request ingress boundary. The database stores that key with a unique constraint:

```sql
CREATE TABLE payment_request (
    id UUID PRIMARY KEY,
    idempotency_key VARCHAR(100) NOT NULL UNIQUE,
    amount NUMERIC(12, 2) NOT NULL,
    status VARCHAR(20) NOT NULL
);
```

When receiving the same key again, the service can look up the already-processed result instead of creating a new operation. You must clearly define the key's uniqueness scope, retention period, how to handle requests with the same key but different payloads, and in-progress states.

The entity's UUID and the idempotency key can be two separate values. An ID identifies a record; an idempotency key identifies a business request that may be retried.

## 13. Ordered IDs and Index Impact

Sequential keys such as identity or sequences typically have good locality in B-trees because new values concentrate at the trailing end of the index. Random UUID v4 values distribute inserts across many regions of the index.

Depending on the database and workload, this can increase page splits, cache misses, or index size. Still, do not assume UUIDs are always slower than integers. Index size, write rate, caching, partitioning, and query design all affect the outcome.

Options to consider:

- UUID v7 if you need UUIDs with approximate chronological ordering.
- Database-issued numeric IDs if you want compact keys and have a central database.
- Binary UUID instead of 36-character strings if the database engine and driver support stable mapping.
- Using UUID as a public identifier and an internal numeric key if the system has a clear reason to separate the two identifiers.

If using UUID v7 or time-based identifiers, consider potential exposure of creation time and clock synchronization across nodes.

Measure performance with realistic data and queries. Do not switch ID types based solely on an assumption that one format is universally better in every system.

## 14. Error Handling and Retries When Saving Entities with UUIDs

When calling `save`, the publisher can emit either the saved entity or an error signal. Errors appear only when the publisher is subscribed to, so error handling must live inside the reactive chain.

Example:

```java
return orders.save(order)
    .onErrorMap(
        DuplicateKeyException.class,
        ex -> new OrderIdConflictException(order.id(), ex)
    );
```

This example illustrates mapping a duplicate-key error to a domain error. Exact exception names and categorization depend on the driver and Spring's exception translation layer.

Do not blindly retry every insert error. If the error is a duplicate key, generating a new UUID can mask a logic bug or break idempotency. If the error is a timeout where the server might already have committed, query by ID or idempotency key before deciding to retry.

When generating a UUID before the transaction, the application can retain that ID across retries. That makes it possible to inspect the outcome of the previous write attempt and avoid creating a new identifier for the same business operation.

## 15. Testing a Self-Assigned UUID Strategy

You should test ID generation, new-entity detection, and database behavior together.

| Scenario | Expected Outcome to Verify |
| --- | --- |
| Create new entity with UUID and null version | Spring Data executes insert. |
| Insert succeeds | Returned entity has configured ID and version. |
| Reload entity | Entity is detected as existing. |
| Save reloaded entity | Spring Data executes update. |
| Two entities with the same UUID | Primary key/unique constraint rejects the duplicate record. |
| Update with stale version | Optimistic locking detects conflict if `@Version` is used. |
| Database-generated UUID | Insert omits ID column and returns ID via driver-supported mechanism. |
| Retry after timeout | No duplicate business record is created; idempotency key is preserved. |

Testing example with Reactor Test:

```java
@Test
void insertsOrderWithApplicationAssignedUuid() {
    UUID id = UUID.randomUUID();

    Order order = new Order(
        id,
        42L,
        new BigDecimal("125.00"),
        OrderStatus.NEW,
        null
    );

    StepVerifier.create(orders.save(order))
        .assertNext(saved -> {
            assertEquals(id, saved.id());
            assertNotNull(saved.version());
        })
        .verifyComplete();
}
```

Tests should run against a real compatible database with a schema that includes the version column. Mocking the repository neither proves Spring Data chose insert vs. update nor confirms the driver maps UUIDs properly.

## 16. Process for Choosing and Implementing an ID Strategy

When designing identifiers for an aggregate, you can follow this sequence:

1. **Choose the identifier scope:** Is the ID unique within a single table, a database, or across a distributed system?
2. **Choose the type:** UUID, integer, ULID, or a custom-algorithm identifier.
3. **Choose where it is generated:** application, database, or an ID-issuing service.
4. **Design the schema:** column type, primary key, unique constraints, and indexes.
5. **Choose entity mapping:** `@Id`, Java/Kotlin types, and converters if needed.
6. **Design new-entity detection:** null ID, `@Version`, or `Persistable.isNew()`.
7. **Define transactions:** do related objects need to be persisted atomically?
8. **Design idempotency:** do retries preserve the same ID or request key?
9. **Test with the real driver:** verify insert/update, generated values, duplicate keys, and optimistic locking.
10. **Measure performance:** check index size and write throughput with representative data.

Self-assigning UUIDs gives applications an identifier prior to persistence and supports distributed workflows. To use it properly in Spring Data R2DBC, you must align the ID type, schema, new-entity detection mechanism, and how the driver executes inserts. When those decisions are consistent, UUIDs become a natural part of the data model and reactive processing flow.
