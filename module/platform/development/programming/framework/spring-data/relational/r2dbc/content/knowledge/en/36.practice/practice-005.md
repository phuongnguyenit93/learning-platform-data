# Handling Concurrent Updates with `@Version` and Conflict Responses

In a Spring Data Relational R2DBC application, multiple requests can read and update the same record concurrently. If two requests read the same version and then write sequentially, the later write can unintentionally overwrite the earlier change. This is a lost update: both requests appear to succeed, yet one change vanishes.

Spring Data Relational supports optimistic locking via the `@Version` annotation. The framework stores a version value on the entity, checks the current version during updates, and increments it when a write succeeds. If the entity being saved carries an outdated version, the update matches zero rows and Spring Data throws `OptimisticLockingFailureException`. The application can translate this error into an HTTP `409 Conflict` response, or use conditional requests with `ETag`/`If-Match` to return `412 Precondition Failed` when the client's precondition no longer holds.

## 1. The concurrent update problem

Suppose a document starts with:

```text
id = 42
title = "Draft"
version = 5
```

Users A and B both open the document. Both receive version 5. A edits the title; B edits the content. If the update statement only has `WHERE id = 42`, the second write can overwrite the entire row with its stale snapshot and erase the earlier change.

Timeline:

```mermaid
sequenceDiagram
    participant A as Request A
    participant B as Request B
    participant DB as Database

    A->>DB: SELECT document id=42 (version 5)
    B->>DB: SELECT document id=42 (version 5)
    A->>DB: UPDATE document ... WHERE id=42 AND version=5
    DB-->>A: 1 row updated; version becomes 6
    B->>DB: UPDATE document ... WHERE id=42 AND version=5
    DB-->>B: 0 rows updated
    Note over B: Optimistic locking conflict
```

Request A succeeds and the version advances to 6. Request B still sends version 5, so zero rows are updated. The framework signals a conflict rather than silently overwriting the newer data.

## 2. What is optimistic locking?

Optimistic locking assumes conflicts happen infrequently. Instead of locking a row upon reading and holding that lock for the entire time a user edits, the application lets multiple requests read the same data. On write, the system checks whether the row is still at the version the request originally read.

Basic flow:

1. Read the entity along with its current version.
2. Apply changes in memory.
3. Submit an update conditioned on `id` and the old `version`.
4. If one row is updated, increment the version and treat the operation as successful.
5. If zero rows match, signal a conflict so the caller decides whether to reload, merge, or prompt the user.

Optimistic locking does not hold database locks while a user keeps an editor open. It detects conflicts at write time. This suits read-heavy, write-light workloads and interactive edits with a gap between read and write.

## 3. Declaring a `@Version` property

Spring Data Relational uses `@Version` from `org.springframework.data.annotation.Version`. The version property must use a supported numeric type such as `int`, `Integer`, `long`, or `Long`.

Mutable entity example:

```java
@Table("document")
public class Document {

    @Id
    private Long id;

    private String title;

    private String content;

    @Version
    private Long version;

    // Constructor, getters, and required methods.
}
```

For an immutable model, you can use a Java record:

```java
@Table("document")
public record Document(
        @Id Long id,
        String title,
        String content,
        @Version long version
) {
}
```

When creating a new entity, the initial version is initialized according to Spring Data rules (typically 0 for primitive types). On update, the framework increments the version. For immutable/record entities, always use the instance emitted by the `save()` publisher to obtain the new version; never assume the input object was mutated.

## 4. Table schema needs a version column

The database must include a column matching the version property. PostgreSQL example:

```sql
CREATE TABLE document (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(250) NOT NULL,
    content TEXT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);
```

The SQL type must be compatible with the Java type. If using primitive `long`, `BIGINT NOT NULL` is a good fit. A database default does not replace Spring Data's version management; the framework may bind the initial version value on insert.

When adding `@Version` to an existing populated table, write a migration adding the column and assigning initial versions to existing rows:

```sql
ALTER TABLE document
    ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

Verify legacy rows and migrations before deploying. If multiple application versions run concurrently during a rolling deployment, every running version must remain compatible with the new schema and versioning strategy.

## 5. How Spring Data performs conditional updates

When saving an existing entity with `@Version`, Spring Data Relational generates an update equivalent to:

```sql
UPDATE document
SET title = :title,
    content = :content,
    version = :newVersion
WHERE id = :id
  AND version = :oldVersion;
```

The `version = :oldVersion` predicate is the conflict check. When another request has already updated the row, the database version no longer matches. The update affects 0 rows, and Spring Data treats this as an optimistic locking failure.

This is a conceptual description; actual SQL varies by dialect, mapping, updated columns, and Spring Data version. Applications do not need to write this statement manually when using standard repository or template entity saves.

## 6. Saving new entities and receiving the framework-managed version

Reactive repository:

```java
public interface DocumentRepository
        extends ReactiveCrudRepository<Document, Long> {
}
```

When creating a new record:

```java
public Mono<Document> create(CreateDocumentRequest request) {
    Document document = new Document(
            null,
            request.title(),
            request.content(),
            0L);

    return documentRepository.save(document);
}
```

The caller should use the entity emitted by `save()`. With a record, Spring Data returns a new instance populated with the mapped ID and version; the original `document` instance remains unchanged.

Example:

```java
return documentRepository.save(document)
        .map(saved -> new DocumentResponse(
                saved.id(),
                saved.title(),
                saved.content(),
                saved.version()));
```

Never increment the version manually before calling `save()` in standard entity mapping flows. Spring Data needs the current version to construct the update predicate and manage the next version.

## 7. Updating via repository `save()`

A service can read the current entity, create a copy with updated data, and call `save()`:

```java
@Service
public class DocumentService {

    private final DocumentRepository repository;

    public DocumentService(DocumentRepository repository) {
        this.repository = repository;
    }

    public Mono<Document> update(Long id, UpdateDocumentRequest request) {
        return repository.findById(id)
                .switchIfEmpty(Mono.error(
                        new DocumentNotFoundException(id)))
                .flatMap(current -> {
                    Document changed = new Document(
                            current.id(),
                            request.title(),
                            request.content(),
                            current.version());

                    return repository.save(changed);
                });
    }
}
```

If two requests read version 5 before either writes, both copies carry version 5. The first request saves successfully and the version becomes 6. The second request saves with version 5 and emits `OptimisticLockingFailureException`.

In this example, `save()` performs the optimistic check at write time. If the API accepts a version from the client, the service must also compare the client's expected version as shown next; otherwise, an older request could reload the latest entity and overwrite newer changes without noticing the client edited a stale copy.

## 8. Distinguishing a race between two writes from a client sending stale data

There are two distinct scenarios:

**Race between two save operations:** two requests read the same version earlier and both attempt to write. `@Version` catches the second write automatically.

**Client edits for a long time and submits stale data:** when the request reaches the server, the service reads the latest entity. If the service ignores the client's version and uses the newly read version, it can overwrite fresh state with the client's stale payload without triggering an optimistic conflict.

Dangerous example:

```java
public Mono<Document> update(Long id, UpdateDocumentRequest request) {
    return repository.findById(id)
            .flatMap(current -> repository.save(new Document(
                    current.id(),
                    request.title(),
                    request.content(),
                    current.version())));
}
```

If the request carries no `expectedVersion`, the server does not know which version the client originally read. `@Version` only checks whether the entity the server is saving is still current at update time; it cannot know which snapshot the browser was displaying.

For client-driven edit APIs, pass the expected version in the request body or HTTP `If-Match` header and compare it against the current version before saving. This protects the entire period while the user edits outside the server.

## 9. Checking expected version in the service

Request DTO:

```java
public record UpdateDocumentRequest(
        String title,
        String content,
        long expectedVersion
) {
}
```

Service:

```java
public Mono<Document> update(Long id, UpdateDocumentRequest request) {
    return repository.findById(id)
            .switchIfEmpty(Mono.error(
                    new DocumentNotFoundException(id)))
            .flatMap(current -> {
                if (current.version() != request.expectedVersion()) {
                    return Mono.error(new DocumentVersionConflictException(
                            id,
                            request.expectedVersion(),
                            current.version()));
                }

                Document changed = new Document(
                        current.id(),
                        request.title(),
                        request.content(),
                        current.version());

                return repository.save(changed);
            });
}
```

This comparison catches stale client edits before calling `save`. `@Version` is still required because another request could update the database after the service reads `current` and before `save(changed)` executes. The two checks complement each other:

- `expectedVersion` comparison: detects that the client edited a stale snapshot.
- `@Version` in the SQL update: detects a race occurring after the server read the entity.

Never remove database-level optimistic locking just because you compare versions in Java. A Java-only check leaves a race window between check and write.

## 10. HTTP `409 Conflict` responses

When an optimistic lock fails, REST APIs commonly return `409 Conflict`. This tells the caller the request cannot be applied because the resource's state has changed.

Exception handler in Spring WebFlux:

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler({
            DocumentVersionConflictException.class,
            OptimisticLockingFailureException.class
    })
    public ResponseEntity<ProblemDetail> handleVersionConflict(Exception ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.CONFLICT);
        problem.setTitle("Document version conflict");
        problem.setDetail(
                "The document has changed. Reload it and apply your changes again.");

        return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
    }
}
```

`OptimisticLockingFailureException` belongs to Spring's DAO exception hierarchy. Specific subclasses may be thrown depending on the repository/driver layer. Handlers should avoid leaking SQL, stack traces, sensitive internal versions, or another user's data.

In a WebFlux annotated controller, exception handlers can return `ResponseEntity` or an equivalent reactive publisher. If the handler must call the database to construct the response, return `Mono<ResponseEntity<...>>` and keep all work inside the reactive chain.

## 11. When to use `409` vs. `412`?

The two status codes fit different API contracts:

| HTTP status | Meaning | Typical use case |
| --- | --- | --- |
| `409 Conflict` | Request conflicts with the resource's current state | API accepts `expectedVersion` in the body or detects an optimistic lock on save |
| `412 Precondition Failed` | HTTP precondition sent by the client is not met | Request uses `If-Match` with a stale ETag |

If the API uses a body field `expectedVersion`, `409` is clear and natural. If it uses HTTP conditional requests, `If-Match` mismatches align with `412` under HTTP semantics.

Pick one consistent contract and document it clearly in API docs. Never return `200 OK` with a `conflict=true` field if clients rely on HTTP status codes to handle precondition failures.

## 12. Using ETag and `If-Match`

Versions can be represented as HTTP ETags. On read, the server returns an ETag matching the version:

```java
@GetMapping("/{id}")
public Mono<ResponseEntity<DocumentResponse>> get(@PathVariable Long id) {
    return documentService.findById(id)
            .map(document -> ResponseEntity.ok()
                    .eTag("\"" + document.version() + "\"")
                    .body(DocumentResponse.from(document)));
}
```

Example response header:

```http
ETag: "5"
```

The client sends back the read version when updating:

```http
PUT /documents/42
If-Match: "5"
Content-Type: application/json
```

The server must parse and validate `If-Match` per HTTP semantics. This example shows a simple version-based ETag; production implementations must handle ETag syntax, multiple tags, wildcard `*`, weak tags, and malformed headers per the API contract. `If-Match` uses strong comparison; do not ignore header syntax carelessly.

The controller can pass the parsed version as `expectedVersion` to the service:

```java
@PutMapping("/{id}")
public Mono<ResponseEntity<DocumentResponse>> update(
        @PathVariable Long id,
        @RequestHeader(HttpHeaders.IF_MATCH) String ifMatch,
        @RequestBody UpdateDocumentBody body) {

    long expectedVersion = etagParser.requireSingleVersion(ifMatch);

    return documentService.update(id, expectedVersion, body)
            .map(saved -> ResponseEntity.ok()
                    .eTag(etagFor(saved.version()))
                    .body(DocumentResponse.from(saved)));
}
```

If `If-Match` does not match the current version, return `412 Precondition Failed`. If a race occurs after the service check and `@Version` throws an optimistic locking exception, map that error to `412` as well to preserve the conditional update contract.

## 13. Service example supporting expected version

You can write a service method that accepts `expectedVersion` directly:

```java
public Mono<Document> update(
        Long id,
        long expectedVersion,
        UpdateDocumentBody body) {

    return repository.findById(id)
            .switchIfEmpty(Mono.error(new DocumentNotFoundException(id)))
            .flatMap(current -> {
                if (current.version() != expectedVersion) {
                    return Mono.error(new DocumentVersionConflictException(id));
                }

                Document changed = new Document(
                        current.id(),
                        body.title(),
                        body.content(),
                        current.version());

                return repository.save(changed)
                        .onErrorMap(
                                OptimisticLockingFailureException.class,
                                error -> new DocumentVersionConflictException(id, error));
            });
}
```

If multiple conflict paths exist, map them to a unified domain exception for the controller to translate to the HTTP status. Retain the original exception as the cause for internal logging/tracing, but do not expose the cause to clients.

## 14. Updating immutable entities and the new version

With records, every modification creates a new instance. Helper methods should preserve the old version so Spring Data uses it in the update predicate:

```java
public record Document(
        @Id Long id,
        String title,
        String content,
        @Version long version
) {

    public Document withContent(String newContent) {
        return new Document(id, title, newContent, version);
    }

    public Document withTitle(String newTitle) {
        return new Document(id, newTitle, content, version);
    }
}
```

After saving:

```java
return repository.save(current.withContent(request.content()))
        .map(saved -> {
            // saved.version() is the new version returned by Spring Data.
            return DocumentResponse.from(saved);
        });
```

Never write `withContent` to increment the version itself. Creating a record with `current.version() + 1` before calling `save()` causes the update predicate to check the wrong version, triggering false conflicts or corrupting mappings. Let Spring Data manage the version during standard entity saves.

## 15. Handling `OptimisticLockingFailureException` in a reactive chain

Optimistic lock errors are emitted through the publisher and should be handled via reactive operators or `@ExceptionHandler` at the WebFlux boundary:

```java
return repository.save(changed)
        .onErrorMap(
                OptimisticLockingFailureException.class,
                error -> new DocumentVersionConflictException(id, error));
```

Or handle it in controller advice. Never call `block()` to catch exceptions in a reactive service. Never call `subscribe()` and handle errors on a detached stream; the HTTP caller may receive a response before the conflict even happens.

When using `onErrorResume`, translate only the specific optimistic locking exception. Never convert every database error into `409`, since timeouts, connection failures, SQL syntax errors, and constraint violations carry different meanings.

## 16. `@Version` is not a pessimistic lock

Optimistic locking does not lock rows on read. Two transactions can still read the same version; conflicts are detected only during the conditional update.

Pessimistic locking uses database locking constructs such as `SELECT ... FOR UPDATE`, holding locks until commit or rollback. R2DBC supports reactive transactions, though locking syntax depends on the database and driver. Do not reach for pessimistic locks solely to avoid conflict handling when the workload does not require them.

| Criterion | Optimistic locking (`@Version`) | Pessimistic locking |
| --- | --- | --- |
| When conflicts are detected/blocked | At write time | At lock acquisition / locking read |
| Holds DB lock while user edits | No | Possible if the transaction holds the lock |
| Best suited for | Read-heavy, write-light workloads with relatively rare conflicts | High contention or strict serialization of specific operations |
| Cost | Must handle conflicts/retries | Can increase lock waits and deadlocks |
| Behavior under concurrent edits | One update wins; stale updates are rejected | Later requests may wait on locks |

For long-lived editing screens, optimistic locking is usually a better fit because it does not hold transactions and locks while the user thinks.

## 17. `@Version` applies automatically only to version-mapped entity persistence

When using `repository.save(entity)` or equivalent Spring Data Relational entity-mapping APIs, the framework has metadata to inspect `@Version` and enforce optimistic locking.

Do not assume every SQL statement in the application is automatically version-checked. The following paths bypass entity version checks:

- `DatabaseClient.sql(...)` with hand-written `UPDATE` statements.
- R2DBC SPI `Connection.createStatement(...)`.
- Direct bulk updates and deletes.
- Stored procedures updating tables directly.
- SQL executed by external tools or other services.

If direct write paths exist, include the version predicate and increment in SQL, or ensure only one write path mutates that entity. `@Version` does not magically add optimistic locking to every SQL statement touching the table.

## 18. Writing updates with a version predicate using `DatabaseClient`

For custom SQL, perform an atomic update:

```java
public Mono<Void> updateTitle(
        Long id,
        long expectedVersion,
        String title) {

    return databaseClient.sql("""
            UPDATE document
            SET title = :title,
                version = version + 1
            WHERE id = :id
              AND version = :expectedVersion
            """)
            .bind("title", title)
            .bind("id", id)
            .bind("expectedVersion", expectedVersion)
            .fetch()
            .rowsUpdated()
            .flatMap(updated -> {
                if (updated == 1) {
                    return Mono.empty();
                }

                return Mono.error(new OptimisticLockingFailureException(
                        "Document was changed or does not exist"));
            });
}
```

The version predicate and version increment live in the same SQL statement, so the database checks and updates atomically. Never split this into `SELECT version` followed by `UPDATE WHERE id = :id`, because a race can happen between the two statements.

When `rowsUpdated()` is `0`, either the ID does not exist or the version no longer matches. If the API must distinguish `404` from `409`, you can query for existence afterward, accepting that state could still change between the update and the lookup. Many APIs return a general conflict for unsatisfied preconditions or use an appropriate query/transaction strategy.

## 19. Using `@Modifying` with `@Query`

If a repository uses modifying queries, write the version predicate and increment explicitly:

```java
public interface DocumentRepository
        extends ReactiveCrudRepository<Document, Long> {

    @Modifying
    @Query("""
            UPDATE document
            SET title = :title,
                version = version + 1
            WHERE id = :id
              AND version = :expectedVersion
            """)
    Mono<Integer> updateTitleIfVersionMatches(
            @Param("id") Long id,
            @Param("title") String title,
            @Param("expectedVersion") long expectedVersion);
}
```

Then check the updated row count:

```java
return repository.updateTitleIfVersionMatches(id, title, expectedVersion)
        .flatMap(updated -> updated == 1
                ? Mono.empty()
                : Mono.error(new DocumentVersionConflictException(id)));
```

Affected-row return signatures and modifying query support depend on your Spring Data R2DBC version. If your version does not support the return type shown, use `DatabaseClient.fetch().rowsUpdated()` or the return type documented for that version.

`@Modifying` does not apply optimistic locking metadata like entity `save()`. Writing the version predicate and increment is the responsibility of the custom SQL.

## 20. Bulk updates can bypass entity optimistic locking

A multi-row update statement normally does not materialize individual entities or run entity lifecycle hooks like `save()`:

```sql
UPDATE document
SET archived = TRUE
WHERE last_accessed_at < :cutoff;
```

If the table uses `version` to guard concurrent edits, decide whether bulk operations must increment `version`:

```sql
UPDATE document
SET archived = TRUE,
    version = version + 1
WHERE last_accessed_at < :cutoff;
```

Incrementing `version` ensures previously loaded entities become stale on subsequent saves. If a bulk operation skips incrementing `version`, a stale entity can overwrite the bulk change undetected. Define explicit versioning semantics for every write path.

## 21. Handling conflicts: fail, reload, or merge?

No single conflict resolution fits every domain. Common strategies:

| Strategy | When appropriate | Notes |
| --- | --- | --- |
| Return `409 Conflict` | Users must inspect new state and decide | Never silently overwrite someone else's changes |
| Return `412 Precondition Failed` | API uses ETag/`If-Match` | Client must GET the resource or fresh ETag |
| Reload and merge automatically | Fields change independently with clear merge rules | Must revalidate business invariants |
| Retry with fresh version | Operation can be safely recomputed from new state | Never blindly replay an entire stale snapshot |
| Route to manual review | High business impact conflicts | Preserve both versions or an audit trail |

For documents with two content fields, you can let users diff the current version against their edits. For account balances or inventory counts, never merge absolute values automatically; model updates as commands/operations recomputed against the new state.

## 22. Do not blindly retry on optimistic lock failure

A dangerous pattern is catching a conflict, reading the latest version, and saving the request's old payload with the new version:

```java
// Avoid: can overwrite newer changes with a stale snapshot.
return repository.save(changed)
        .onErrorResume(OptimisticLockingFailureException.class,
                error -> repository.findById(id)
                        .flatMap(latest -> repository.save(
                                new Document(
                                        latest.id(),
                                        changed.title(),
                                        changed.content(),
                                        latest.version()))));
```

This bypasses the conflict by grabbing the fresh version while keeping the stale content. It recreates the exact lost update `@Version` was meant to prevent.

When retrying, determine which commands are safe to replay and how to merge. For example, an `incrementViewCount` command can safely recompute over the new state, whereas `replaceEntireDocument` generally requires user confirmation when the snapshot is stale. Never retry infinitely; cap attempts and monitor conflict rates.

## 23. Distinguishing optimistic conflicts from other database errors

Never map every database exception to `409`:

| Error | Typical meaning | Appropriate response |
| --- | --- | --- |
| `OptimisticLockingFailureException` | Stale version or row no longer matches | `409` or `412` per contract |
| Entity not found | ID does not exist | `404 Not Found` |
| Unique constraint violation | Value duplicates a unique constraint | `409 Conflict` or validation error per API |
| Foreign key violation | Invalid reference | `409`/`422` depending on domain |
| Query timeout | Database did not finish in time | `503`/`504` depending on layer and policy |
| Connection failure | Unable to reach the database | `503 Service Unavailable` or system error |
| SQL syntax/mapping error | Code or configuration bug | `500 Internal Server Error` |

An optimistic locking exception can occur when a row was deleted or its version changed. If you need to distinguish concurrent deletion from concurrent update, the service can recheck existence and map according to the API contract.

## 24. Testing optimistic locking with two snapshots

Integration tests should create two snapshots with the same version, then save sequentially:

```java
@SpringBootTest
class DocumentOptimisticLockingTest {

    @Autowired
    DocumentRepository repository;

    @Test
    void rejectsSecondSaveFromStaleSnapshot() {
        Document initial = new Document(
                null, "Original", "Initial body", 0L);

        Mono<Void> scenario = repository.save(initial)
                .flatMap(saved -> Mono.zip(
                                repository.findById(saved.id()),
                                repository.findById(saved.id()))
                        .flatMap(snapshots -> {
                            Document first = snapshots.getT1();
                            Document stale = snapshots.getT2();

                            Document firstChange = new Document(
                                    first.id(),
                                    "Changed by A",
                                    first.content(),
                                    first.version());

                            Document secondChange = new Document(
                                    stale.id(),
                                    "Changed by B",
                                    stale.content(),
                                    stale.version());

                            return repository.save(firstChange)
                                    .then(repository.save(secondChange))
                                    .then();
                        }));

        StepVerifier.create(scenario)
                .expectError(OptimisticLockingFailureException.class)
                .verify();
    }
}
```

The test performs both reads before the first write, so both snapshots share the same version. Save A succeeds; save B uses the stale version and must emit an optimistic locking exception.

In real tests, clean up fixtures via R2DBC or use an isolated test database/schema. After catching the error, query the document in a fresh subscription to verify A's data persisted and the version incremented. Test with your production database and driver because affected-row counts and transaction behavior are driver-dependent.

## 25. Verifying version increments after save

A success test should verify the version advances:

```java
StepVerifier.create(repository.save(new Document(
                null, "Title", "Body", 0L)))
        .assertNext(saved -> {
            assertThat(saved.id()).isNotNull();
            assertThat(saved.version()).isEqualTo(0L);
        })
        .verifyComplete();
```

Then update:

```java
StepVerifier.create(repository.findById(id)
                .flatMap(current -> repository.save(
                        new Document(
                                current.id(),
                                "Updated title",
                                current.content(),
                                current.version()))))
        .assertNext(updated ->
                assertThat(updated.version()).isEqualTo(1L))
        .verifyComplete();
```

This example assumes primitive `long` with an initial version of `0` under the mapping. Use the values and behavior of your actual Spring Data version and schema. The goal is to prove the post-update version increases relative to the prior version, not to hardcode assumptions if the application uses another versioning strategy.

## 26. Testing HTTP conflicts with WebTestClient

At the API layer, verify exceptions translate to the right HTTP status:

```java
webTestClient.put()
        .uri("/documents/{id}", documentId)
        .contentType(MediaType.APPLICATION_JSON)
        .bodyValue(new UpdateDocumentRequest(
                "New title", "New content", staleVersion))
        .exchange()
        .expectStatus().isEqualTo(HttpStatus.CONFLICT)
        .expectBody()
        .jsonPath("$.title").isEqualTo("Document version conflict");
```

Tests should advance the stored record to a newer version before sending the stale request. Besides status, verify the response does not leak SQL, stack traces, or another updater's data.

If the API uses `If-Match`, test that a matching ETag succeeds and returns a new ETag, while a stale ETag receives `412 Precondition Failed`. Malformed headers should return `400 Bad Request` per the API contract.

## 27. Versions and transaction boundaries

Optimistic locking relies on an atomic conditional update. When a transaction spans multiple database operations, use `R2dbcTransactionManager` to ensure all changes in the same database commit or roll back together.

Example:

```java
return transactionalOperator.transactional(
        documentRepository.save(changed)
                .flatMap(saved -> auditRepository.save(
                                AuditEntry.documentUpdated(saved.id(), saved.version()))
                        .thenReturn(saved))
);
```

If optimistic locking fails on `save`, the publisher emits an error and the transaction rolls back. If `save` succeeds but the audit insert fails, the transaction also rolls back the document change when both use the same `ConnectionFactory` and transaction manager.

Never call `subscribe()` separately for the audit write. If the audit store lives in a separate database, a single R2DBC transaction manager will not roll it back automatically; use an outbox or dedicated coordination mechanism.

## 28. `@Version` does not replace validation and authorization

A version only detects that state changed. It does not prove the caller has permission to update the entity or that the payload is valid.

The service must still:

- Verify the entity exists.
- Enforce ownership/tenant authorization before updating.
- Validate new data and domain invariants.
- Check expected version if clients edit from older snapshots.
- Map conflicts to the right status code.
- Record audits if business rules require them.

Example query scoped by ID and tenant:

```java
@Query("""
        SELECT * FROM document
        WHERE id = :id AND tenant_id = :tenantId
        """)
Mono<Document> findForTenant(
        @Param("id") Long id,
        @Param("tenantId") Long tenantId);
```

Tenant ID must come from the authenticated security context. Never treat version or ID as an authorization mechanism.

## 29. Compatibility when adding versions to a live application

When rolling out `@Version` to a system with existing data, plan the migration and rolling deployment:

1. Add the `version` column with a suitable initial value for all existing rows.
2. Deploy version-aware code and verify compatibility across instances.
3. Update APIs/clients to send `expectedVersion` or ETags if protecting long-lived edits.
4. Monitor conflict rates and locate any un-updated direct write paths.
5. Retire older application instances without version support before relying fully on the new mechanism.

If an older instance keeps updating the table without incrementing `version`, newer instances will miss updates made by the old code. Every write path must follow the same versioning policy, or you need a compatibility strategy during rollout.

Check bulk updates, background jobs, stored procedures, and admin tools to see whether they increment `version`. A version column only remains reliable when all significant write paths maintain consistent semantics.

## 30. Handling conflicts in the UI

An API returning `409` or `412` should guide client recovery. An editor UI can:

1. Preserve the user's unsaved draft.
2. Fetch the latest version from the server.
3. Display the newer server changes alongside the user's pending edits.
4. Allow the user to compare, copy, or merge changes.
5. Resubmit with the new version/ETag after user confirmation.

Never silently reload and resubmit the old payload without notifying the user. Doing so merely turns a lost update into an overwrite that looks successful.

For independent fields, field-level merging may be supported if business rules permit. For rich text or collaborative documents, consider specialized merge algorithms, operational transformation, or CRDTs rather than relying solely on a scalar version.

## 31. Monitoring conflict rates

Optimistic locking detects conflicts, but frequent conflicts signal an ill-suited update model or UX.

Track:

- Optimistic locking failure counts by entity type and use case.
- Conflict rate relative to total updates.
- Client retry counts after conflicts.
- Time elapsed between read and write if measurable.
- Conflict rates by endpoint or operation using low-cardinality tags.
- Conflicts caused by bulk updates or background jobs.

Never use document ID, user ID, or tenant ID as high-cardinality metric tags. You can record those identifiers in appropriately secured logs, while metrics use stable operation/entity-type tags.

If conflicts happen frequently, consider splitting aggregates, shortening edit windows, switching to command-based updates, merging per field, or serializing specific operations appropriately.

## 32. Common pitfalls

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Forgetting `@Version` | Updates can overwrite concurrent changes | Add a version property and column migration |
| Version SQL type mismatches Java type | Mapping/bind errors or overflow | Align numeric Java type and SQL column |
| Incrementing version before calling `save()` | Update predicate uses wrong version | Let Spring Data manage entity versions |
| Reusing stale entity after immutable save | Caller keeps sending old version | Use the instance emitted by `save()` |
| Relying only on `@Version` without expected version | Stale client edits overwrite fresh data after server reload | Compare expected version/ETag with current version |
| Checking version only in Java without atomic predicate | Race condition between check and update | Use `@Version` or SQL `WHERE version = :expected` |
| Hand-written SQL forgets to increment version | Subsequent updates miss changes | Increment version in the same update statement |
| Bulk updates skip incrementing version | Stale entities can overwrite bulk changes | Increment version or define explicit policy |
| Catching conflict and saving old snapshot with new version | Reintroduces lost updates | Merge/recompute per business rules or return conflict |
| Mapping all DB exceptions to 409 | Masks timeouts, connection, and schema errors | Map only optimistic conflicts and classified errors |
| Using version as authorization | Users can edit unauthorized resources | Enforce ownership/tenant checks independently |
| Testing only with mocks | Fails to verify affected-row counts and driver exceptions | Write integration tests against a real database |

## 33. Workflow for implementing optimistic locking

When you need to detect concurrent updates, follow this order:

1. Identify which entities/aggregates need protection against lost updates.
2. Add a numeric `@Version` property and matching database column.
3. Use repository/template entity saves so Spring Data performs version checks.
4. For immutable entities, keep the existing version in updated copies and adopt the new instance returned by `save()`.
5. For long-lived client edits, accept `expectedVersion` or `ETag`/`If-Match`.
6. Compare `expectedVersion` against the current entity before calling `save()`.
7. Keep `@Version` to catch races occurring between the read and the update.
8. Map optimistic lock exceptions to `409` or `412` per API contract.
9. For hand-written SQL or bulk updates, add atomic version predicates and increments.
10. Define conflict handling: reload, merge, controlled retry, or user resolution.
11. Test dual-snapshot conflicts, version increments, HTTP status codes, and transaction rollbacks.
12. Monitor conflict rates and ensure every write path maintains versions.

## 34. Practical guidelines

- Use `@Version` to detect updates based on stale entity versions.
- Use numeric types supported by Spring Data Relational with matching SQL columns.
- Let Spring Data increment the version on entity `save()`; never pre-increment before calling `save()`.
- For records/immutable entities, retain the old version in the update copy and use the entity returned by `save()`.
- Remember `@Version` catches write-time races; it does not know which snapshot the client edited.
- Accept `expectedVersion` or `ETag`/`If-Match` to protect the user's editing window.
- Use `409 Conflict` for application-level version conflicts or `412 Precondition Failed` for failed `If-Match` preconditions.
- Never blindly retry by attaching a fresh version to an entire stale payload.
- With `DatabaseClient`, `@Modifying`, bulk SQL, or stored procedures, add version predicates and increments manually.
- Enforce authorization, tenant checks, and validation independently of optimistic locking.
- Never turn every database error into a conflict response.
- Test dual snapshots with matching versions against a real database and driver.
- Monitor conflict rates to refine data models and editing UX.

## 35. Conclusion

`@Version` helps Spring Data Relational R2DBC detect lost updates using optimistic locking. The framework includes the current version in the update condition, increments it on successful writes, and emits `OptimisticLockingFailureException` when the entity is stale. This fits editing screens and workflows where multiple requests read the same entity without holding long-lived database locks.

To protect the entire client editing window as well, APIs should accept an expected version or `ETag`/`If-Match` and compare it against current state. `@Version` remains the atomic database safeguard catching races after the server reads. Return `409 Conflict` or `412 Precondition Failed` per your HTTP contract, provide intentional reload/merge paths, and avoid blind retries with stale snapshots. For custom SQL and bulk updates, maintain explicit version predicates and increments, and verify conflict behavior against a real driver and database.
