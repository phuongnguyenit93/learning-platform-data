# Khác biệt về khóa ghép, upsert, batch và savepoint

Khi làm việc với nhiều hệ quản trị cơ sở dữ liệu trong Spring Data Relational R2DBC, bốn chủ đề thường cần chú ý là khóa ghép, upsert, batch và savepoint. Chúng đều liên quan đến cách database xác định bản ghi, thực thi nhiều thao tác và kiểm soát transaction, nhưng cú pháp và mức hỗ trợ khác nhau giữa PostgreSQL, MySQL, SQL Server, Oracle, SQLite và các hệ khác.

Spring Data R2DBC cung cấp abstraction chung cho repository, mapping và reactive transaction. Abstraction đó không làm cho mọi khả năng SQL của các database trở nên giống nhau. Đặc biệt:

- Mapping repository chuẩn được xây dựng quanh một thuộc tính định danh @Id; không nên giả định @EmbeddedId hoặc @IdClass của JPA có semantics tương đương.
- save() chọn INSERT hoặc UPDATE dựa trên trạng thái mới của entity; nó không tự động là lệnh upsert theo unique key.
- saveAll() nhận nhiều entity nhưng không bảo đảm mọi driver sẽ gửi một câu batch duy nhất.
- Batch statement và cú pháp multi-row INSERT phụ thuộc driver, database và giới hạn bind parameter.
- Savepoint phụ thuộc khả năng của database/driver và transaction manager; savepoint không phải một transaction độc lập.

Muốn ứng dụng chạy ổn định trên nhiều hệ quản trị, cần tách rõ phần portable của Spring Data khỏi phần SQL/dialect đặc thù, đồng thời kiểm thử với đúng R2DBC driver và database triển khai.

## 1. Bức tranh tổng thể

| Chủ đề | Abstraction chung | Khác biệt cần kiểm tra |
|---|---|---|
| Khóa ghép | Entity mapping, @Id, repository query | Mapping repository với nhiều cột định danh, unique constraint, NULL và collation |
| Upsert | save() và custom repository | Cú pháp ON CONFLICT, ON DUPLICATE KEY UPDATE, MERGE, generated values |
| Batch | saveAll(), R2DBC Statement.add() | Driver có hỗ trợ batching ra sao, giới hạn parameter, lỗi một phần, generated keys |
| Savepoint | R2DBC Connection và transaction manager | Database/driver có hỗ trợ, cú pháp release, nested propagation |

Một nguyên tắc hữu ích: dùng Spring Data abstraction cho thao tác CRUD có thể biểu diễn thống nhất; dùng SQL riêng hoặc custom repository cho tính năng phụ thuộc hệ quản trị. Đặt SQL đặc thù trong một adapter/repository có tên rõ ràng để phần nghiệp vụ không phải biết mọi dialect.

## 2. Khóa chính đơn và khóa ghép

Khóa chính xác định duy nhất một dòng trong bảng. Khóa chính đơn dùng một cột:

~~~sql
CREATE TABLE customer (
    id BIGINT PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);
~~~

Khóa ghép dùng nhiều cột:

~~~sql
CREATE TABLE tenant_customer (
    tenant_id BIGINT NOT NULL,
    external_customer_id VARCHAR(100) NOT NULL,
    name VARCHAR(200) NOT NULL,
    PRIMARY KEY (tenant_id, external_customer_id)
);
~~~

Trong bảng này, tenant_id riêng lẻ không duy nhất và external_customer_id riêng lẻ cũng không duy nhất. Chỉ cặp (tenant_id, external_customer_id) mới định danh một dòng.

Khóa ghép thường xuất hiện ở:

- Bảng liên kết nhiều-nhiều.
- Dữ liệu phân vùng theo tenant.
- Bảng lưu mã tham chiếu từ hệ thống bên ngoài.
- Bảng quan hệ theo ngôn ngữ, khu vực hoặc phiên bản.
- Bảng lịch sử có khóa nghiệp vụ kết hợp thời điểm hoặc sequence.

Khóa ghép là khả năng của database. Nhưng việc database cho phép một bảng có nhiều cột trong PRIMARY KEY không đồng nghĩa repository mapping của mọi ORM/framework đều có thể biểu diễn nó trực tiếp.

## 3. Giới hạn khóa định danh trong Spring Data Relational

Spring Data Relational mapping được tổ chức quanh một thuộc tính định danh của entity được đánh dấu bằng @Id. Không nên mặc định rằng các annotation JPA như @EmbeddedId hoặc @IdClass sẽ được Spring Data R2DBC hiểu giống Hibernate.

Ví dụ entity thông thường:

~~~java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;
}
~~~

Entity này có một thuộc tính ID duy nhất. Với schema có primary key gồm hai cột, cần xác định chiến lược mapping phù hợp với phiên bản Spring Data Relational đang dùng. Không nên chỉ tạo một class TenantCustomerId rồi đánh dấu @Id và giả định framework tự bung object thành hai cột khóa ghép.

Với repository CRUD chuẩn, lựa chọn dễ dự đoán thường là dùng surrogate key:

~~~sql
CREATE TABLE tenant_customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    external_customer_id VARCHAR(100) NOT NULL,
    name VARCHAR(200) NOT NULL,
    CONSTRAINT uq_tenant_customer_external
        UNIQUE (tenant_id, external_customer_id)
);
~~~

Entity:

~~~java
@Table("tenant_customer")
public class TenantCustomer {

    @Id
    private Long id;

    private Long tenantId;
    private String externalCustomerId;
    private String name;
}
~~~

Database vẫn bảo đảm cặp (tenant_id, external_customer_id) duy nhất, còn Spring Data repository dùng id làm định danh entity.

### Surrogate key không loại bỏ unique business key

Thêm cột id không có nghĩa bỏ ràng buộc nghiệp vụ. Nếu cặp tenant và external ID phải duy nhất, vẫn cần unique constraint:

~~~sql
ALTER TABLE tenant_customer
ADD CONSTRAINT uq_tenant_customer_external
UNIQUE (tenant_id, external_customer_id);
~~~

Unique constraint bảo vệ dữ liệu trước race condition giữa nhiều request hoặc nhiều instance ứng dụng. Kiểm tra bằng Java trước khi insert không thay thế được ràng buộc ở database.

## 4. Khi schema bắt buộc giữ khóa ghép

Nếu không thể thêm surrogate key vì schema đã được chuẩn hóa theo khóa ghép hoặc do hệ thống ngoài quản lý, có thể viết custom repository dùng DatabaseClient để truy vấn theo tất cả thành phần khóa.

Ví dụ tìm một dòng:

~~~java
public Mono<TenantCustomerView> findByBusinessKey(
        Long tenantId,
        String externalCustomerId) {

    return databaseClient.sql(
            "SELECT tenant_id, external_customer_id, name " +
            "FROM tenant_customer " +
            "WHERE tenant_id = :tenantId " +
            "AND external_customer_id = :externalCustomerId"
        )
        .bind("tenantId", tenantId)
        .bind("externalCustomerId", externalCustomerId)
        .map((row, metadata) -> new TenantCustomerView(
            row.get("tenant_id", Long.class),
            row.get("external_customer_id", String.class),
            row.get("name", String.class)
        ))
        .one();
}
~~~

Với custom SQL, phải dùng đầy đủ các thành phần khóa trong:

- WHERE khi đọc.
- WHERE khi UPDATE.
- WHERE khi DELETE.
- JOIN giữa các bảng.
- Conflict target của upsert nếu database hỗ trợ.

Nếu chỉ lọc theo tenant_id, có thể cập nhật hoặc xóa nhiều dòng ngoài ý muốn.

Một custom repository có thể định nghĩa contract theo business key:

~~~java
public interface TenantCustomerStore {

    Mono<TenantCustomerView> findByBusinessKey(
        Long tenantId,
        String externalCustomerId
    );

    Mono<Long> updateName(
        Long tenantId,
        String externalCustomerId,
        String newName
    );
}
~~~

Implementation dùng DatabaseClient và ánh xạ kết quả sang DTO hoặc domain object. Cách này giữ được schema khóa ghép mà không giả định repository CRUD có khả năng composite ID portable.

## 5. Unique constraint ghép và các khác biệt về NULL

Unique constraint nhiều cột thường dùng để bảo đảm tổ hợp giá trị không trùng:

~~~sql
UNIQUE (tenant_id, external_customer_id)
~~~

Tuy nhiên, cách database xử lý NULL trong unique constraint khác nhau. Nhiều hệ quản trị cho phép nhiều dòng có NULL trong một hoặc nhiều thành phần unique key vì NULL không được xem như một giá trị bằng NULL theo cách so sánh thông thường. Một số hệ quản trị hoặc phiên bản có tùy chọn thay đổi semantics này.

Nếu các thành phần khóa nghiệp vụ bắt buộc phải có, khai báo NOT NULL:

~~~sql
tenant_id BIGINT NOT NULL,
external_customer_id VARCHAR(100) NOT NULL,
UNIQUE (tenant_id, external_customer_id)
~~~

Ngoài NULL, cần chú ý collation và quy tắc so sánh chuỗi:

- Một số collation của MySQL thường không phân biệt chữ hoa/chữ thường.
- PostgreSQL với kiểu text/varchar và collation mặc định thường phân biệt chữ hoa/chữ thường trong phép so sánh bằng.
- SQL Server phụ thuộc collation của database hoặc cột.
- SQLite có quy tắc collation được chỉ định như BINARY hoặc NOCASE.

Vì vậy, ABC và abc có thể được coi là cùng hoặc khác business key tùy database/collation. Nếu key không phân biệt hoa thường, hãy chuẩn hóa dữ liệu hoặc định nghĩa collation/index phù hợp và kiểm thử trên hệ quản trị đích.

## 6. save() không phải upsert

Trong Spring Data R2DBC, save(entity) xác định entity mới hay đã tồn tại rồi chọn INSERT hoặc UPDATE:

| Entity state | Hành vi của save() |
|---|---|
| New | INSERT |
| Existing | UPDATE |

Trạng thái mới có thể được xác định qua Persistable.isNew(), thuộc tính @Version hoặc ID theo quy tắc của Spring Data Relational.

save() không mặc định chạy một câu SQL dạng:

~~~sql
INSERT ...
ON CONFLICT (...) DO UPDATE ...
~~~

Nó cũng không mặc định SELECT trước để kiểm tra dòng có tồn tại rồi tự chuyển nhánh. Nếu entity được nhận diện là existing nhưng dòng không tồn tại, UPDATE có thể ảnh hưởng zero row. Nếu entity được nhận diện là new nhưng unique key đã tồn tại, INSERT có thể lỗi constraint.

### Vì sao SELECT rồi INSERT không thay thế upsert?

Một cách dễ mắc race condition:

~~~text
Request A: SELECT key -> không thấy
Request B: SELECT key -> không thấy
Request A: INSERT key -> thành công
Request B: INSERT key -> duplicate key
~~~

Kiểm tra trước bằng ứng dụng không nguyên tử với thao tác insert. Unique constraint là hàng rào cuối cùng, còn database-native upsert có thể giải quyết xung đột trong một statement theo semantics của hệ quản trị.

## 7. Upsert là gì?

Upsert kết hợp insert và update:

- Nếu khóa xung đột chưa tồn tại, thêm dòng mới.
- Nếu khóa xung đột đã tồn tại, cập nhật các cột được chỉ định.

Một use case phổ biến là đồng bộ dữ liệu từ hệ thống ngoài theo business key:

~~~text
Nhận (tenant_id, external_id, name)
                 |
                 v
          Database kiểm tra
                 |
          +------+------+
          |             |
       Chưa có        Đã có
          |             |
          v             v
        INSERT         UPDATE
          |             |
          +------+------+
                 |
                 v
        Trả kết quả persisted
~~~

Upsert thường dựa trên PRIMARY KEY hoặc UNIQUE constraint/index. Nếu không có ràng buộc duy nhất phù hợp, database không có conflict target đáng tin cậy để phân biệt bản ghi cần cập nhật.

## 8. PostgreSQL: INSERT ... ON CONFLICT

PostgreSQL hỗ trợ ON CONFLICT:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (
    :tenantId,
    :externalCustomerId,
    :name
)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET
    name = EXCLUDED.name;
~~~

EXCLUDED đại diện cho dòng đang được đề nghị insert. Conflict target có thể chỉ ra danh sách cột hoặc constraint phù hợp.

Nếu cần trả về bản ghi sau upsert:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (:tenantId, :externalCustomerId, :name)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name
RETURNING id, tenant_id, external_customer_id, name;
~~~

Spring DatabaseClient có thể thực thi SQL PostgreSQL và map kết quả:

~~~java
Mono<TenantCustomerView> upsert =
    databaseClient.sql(postgresUpsertSql)
        .bind("tenantId", tenantId)
        .bind("externalCustomerId", externalId)
        .bind("name", name)
        .map((row, metadata) -> new TenantCustomerView(
            row.get("id", Long.class),
            row.get("tenant_id", Long.class),
            row.get("external_customer_id", String.class),
            row.get("name", String.class)
        ))
        .one();
~~~

Đây là SQL đặc thù PostgreSQL. Không dùng nguyên câu lệnh này cho MySQL hoặc SQL Server.

## 9. MySQL: INSERT ... ON DUPLICATE KEY UPDATE

MySQL hỗ trợ ON DUPLICATE KEY UPDATE. Khi insert vi phạm primary key hoặc unique key, database thực hiện nhánh update:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (
    :tenantId,
    :externalCustomerId,
    :name
) AS incoming
ON DUPLICATE KEY UPDATE
    name = incoming.name;
~~~

Cú pháp row alias sau VALUES có hỗ trợ theo phiên bản MySQL. Các phiên bản cũ thường dùng VALUES(name) trong phần update; cách dùng VALUES() này đã bị deprecated ở các phiên bản MySQL mới hơn. Hãy đối chiếu tài liệu phiên bản database đang triển khai.

Khác với PostgreSQL, MySQL không yêu cầu chỉ rõ conflict target ngay trong câu ON DUPLICATE KEY UPDATE. Bất kỳ primary key hoặc unique key nào bị xung đột cũng có thể kích hoạt nhánh update. Điều này cần được cân nhắc nếu bảng có nhiều unique constraint độc lập.

MariaDB có lịch sử cú pháp và hỗ trợ riêng; không nên mặc định mọi cú pháp alias của MySQL đều tương thích với mọi phiên bản MariaDB.

## 10. SQLite: UPSERT với ON CONFLICT

SQLite hỗ trợ cú pháp UPSERT theo dạng:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (:tenantId, :externalId, :name)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET
    name = excluded.name;
~~~

Từ khóa excluded tham chiếu giá trị được đề nghị insert. Tính năng UPSERT được bổ sung từ SQLite 3.24.0; cần xác nhận phiên bản SQLite mà driver sử dụng.

SQLite cũng có khác biệt về concurrency và locking so với database server nhiều kết nối. Khi chạy nhiều writer, cần kiểm tra busy timeout, journal mode và cách driver xử lý transaction.

## 11. SQL Server và Oracle: MERGE

SQL Server và Oracle hỗ trợ MERGE với cú pháp riêng. Ví dụ minh họa dạng SQL Server:

~~~sql
MERGE INTO dbo.tenant_customer AS target
USING (
    SELECT
        @tenantId AS tenant_id,
        @externalId AS external_customer_id,
        @name AS name
) AS source
ON target.tenant_id = source.tenant_id
AND target.external_customer_id = source.external_customer_id
WHEN MATCHED THEN
    UPDATE SET name = source.name
WHEN NOT MATCHED THEN
    INSERT (tenant_id, external_customer_id, name)
    VALUES (
        source.tenant_id,
        source.external_customer_id,
        source.name
    );
~~~

MERGE của SQL Server có những lưu ý về concurrency, trigger và các trường hợp cạnh tranh. Không nên chọn MERGE chỉ vì muốn một câu lệnh ngắn. Cần đọc hướng dẫn và các lưu ý của phiên bản SQL Server, đồng thời kiểm thử dưới tải đồng thời. Một số hệ thống chọn chiến lược UPDATE rồi INSERT trong transaction với unique constraint và locking phù hợp.

Oracle cũng có MERGE INTO ... USING ... WHEN MATCHED ... WHEN NOT MATCHED ..., nhưng bind marker, cú pháp và cách trả kết quả khác SQL Server. Không thể dùng nguyên câu lệnh ở trên cho Oracle.

## 12. So sánh nhanh cú pháp upsert

| Hệ quản trị | Cách thường gặp | Lưu ý |
|---|---|---|
| PostgreSQL | INSERT ... ON CONFLICT ... DO UPDATE | Có conflict target và RETURNING |
| MySQL | INSERT ... ON DUPLICATE KEY UPDATE | Bất kỳ unique key xung đột có thể kích hoạt update; cú pháp alias tùy phiên bản |
| MariaDB | INSERT ... ON DUPLICATE KEY UPDATE | Kiểm tra khác biệt phiên bản với MySQL |
| SQLite | INSERT ... ON CONFLICT ... DO UPDATE | Cần phiên bản hỗ trợ UPSERT |
| SQL Server | MERGE hoặc chiến lược UPDATE/INSERT có khóa | Xem xét concurrency và semantics theo phiên bản |
| Oracle | MERGE INTO | Cú pháp riêng, không portable |

Không có một câu upsert SQL duy nhất chạy nguyên trạng trên tất cả database. Nếu sản phẩm hỗ trợ nhiều database, có thể:

- Tạo implementation repository riêng theo dialect.
- Dùng strategy/adapter được chọn theo database.
- Dùng Spring Data Dialect hoặc metadata để cấu hình phần phù hợp khi abstraction hỗ trợ.
- Giữ phần nghiệp vụ gọi một interface chung, còn SQL nằm trong implementation cụ thể.

## 13. Thiết kế upsert theo khóa ghép

Với business key gồm tenant_id và external_customer_id, phải có unique constraint tương ứng:

~~~sql
ALTER TABLE tenant_customer
ADD CONSTRAINT uq_tenant_external
UNIQUE (tenant_id, external_customer_id);
~~~

Sau đó PostgreSQL có thể dùng conflict target:

~~~sql
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name
~~~

MySQL sẽ kích hoạt ON DUPLICATE KEY UPDATE khi bất kỳ unique key nào xung đột. Vì vậy, nếu bảng có cả unique email và unique external ID, cần cân nhắc việc xung đột email có dẫn đến cập nhật nhầm dòng hay không.

Một số quy tắc:

- Các thành phần business key bắt buộc nên là NOT NULL.
- Unique constraint phải phản ánh đúng phạm vi tenant.
- Không bỏ tenant_id khỏi conflict target nếu cùng external ID có thể tồn tại ở nhiều tenant.
- Không cho phép upsert cập nhật các cột thuộc quyền sở hữu của hệ thống khác nếu nghiệp vụ không cho phép.
- Xác định cột nào được cập nhật khi conflict và cột nào phải giữ nguyên.
- Nếu cần phát hiện dữ liệu cũ khác dữ liệu mới, so sánh rõ ràng hoặc dùng điều kiện update phù hợp.

## 14. Trả về ID và dữ liệu sau upsert

Khả năng trả về generated ID hoặc dòng sau upsert khác nhau:

- PostgreSQL hỗ trợ RETURNING.
- SQL Server có OUTPUT INSERTED... trong nhiều dạng DML.
- MySQL thường lấy generated key qua driver/API, nhưng việc trả toàn bộ dòng sau nhánh update không giống PostgreSQL RETURNING.
- Oracle có cơ chế returning và cú pháp riêng.
- SQLite có RETURNING ở các phiên bản hỗ trợ.

R2DBC driver quyết định cách kết quả được phơi bày cho ứng dụng. Đừng giả định DatabaseClient.fetch().one() hoạt động giống nhau với mọi câu upsert hoặc mọi driver.

Nếu chỉ cần số dòng bị ảnh hưởng, dùng API rows updated phù hợp. Nếu cần entity sau upsert, chọn cú pháp trả về dữ liệu được database/driver hỗ trợ và map thành DTO. Nếu driver không trả được row theo cách mong muốn, có thể cần truy vấn tiếp trong cùng transaction bằng business key.

## 15. Batch là gì?

Batch gom nhiều thao tác cùng dạng để giảm overhead của việc gửi từng statement riêng lẻ. Có một số cách khác nhau:

1. Gửi cùng một prepared statement nhiều lần với các bộ bind khác nhau.
2. Dùng một câu INSERT có nhiều bộ VALUES.
3. Dùng API bulk insert/update của framework hoặc database.
4. Gửi một nhóm câu lệnh SQL trong cùng transaction.

Các cách này không đồng nghĩa với nhau:

| Cách | Mô tả |
|---|---|
| Nhiều lần gọi save() | Framework xử lý từng entity |
| saveAll() | Nhận Publisher nhiều entity; cách thực thi cụ thể tùy framework/version |
| R2DBC Statement.add() | Thêm nhiều bộ bind cho cùng một statement |
| Multi-row INSERT | Một câu SQL có nhiều bộ VALUES |
| Transaction | Bảo đảm nhóm thao tác commit/rollback cùng nhau nếu mọi thao tác tham gia transaction |

Batch có thể giảm round trip hoặc chi phí chuẩn bị statement, nhưng không tự động làm dữ liệu atomic nếu không có transaction.

## 16. saveAll() không nhất thiết là một SQL batch

Repository có phương thức:

~~~java
Flux<Customer> saveAll(Publisher<Customer> entities);
~~~

Phương thức này thuận tiện khi nhận một stream entity. Tuy nhiên, không nên giả định saveAll() luôn biến toàn bộ Publisher thành một câu multi-row INSERT hoặc một R2DBC batch statement. Cách triển khai phụ thuộc Spring Data version, loại entity, trạng thái new/existing và driver.

Ví dụ:

~~~java
Flux<Customer> saved =
    customerRepository.saveAll(
        Flux.fromIterable(customers)
    );
~~~

Nếu cần bảo đảm tất cả entity được lưu trong cùng transaction:

~~~java
@Transactional
public Flux<Customer> saveCustomers(List<Customer> customers) {
    return customerRepository.saveAll(
        Flux.fromIterable(customers)
    );
}
~~~

Transaction giúp nhóm các thao tác cùng commit hoặc rollback nếu chúng tham gia cùng transaction context. Nó không khẳng định driver chỉ gửi một batch duy nhất.

Hãy quan sát SQL/driver behavior hoặc tài liệu đúng phiên bản trước khi tuyên bố saveAll đã tối ưu thành batch.

## 17. R2DBC SPI Statement.add()

R2DBC SPI cho phép thêm nhiều bộ bind cho cùng một statement bằng Statement.add(), nếu driver hỗ trợ batch execution theo cách này.

Ví dụ với câu INSERT có ba tham số:

~~~java
Statement statement = connection.createStatement(
    "INSERT INTO tenant_customer " +
    "(tenant_id, external_customer_id, name) " +
    "VALUES ($1, $2, $3)"
);

statement
    .bind(0, 10L)
    .bind(1, "ext-001")
    .bind(2, "An")
    .add();

statement
    .bind(0, 10L)
    .bind(1, "ext-002")
    .bind(2, "Binh");

Publisher<? extends Result> results = statement.execute();
~~~

Giải thích:

1. Tạo một statement với các bind marker.
2. Bind bộ giá trị thứ nhất.
3. Gọi add() để đưa bộ giá trị hiện tại vào batch.
4. Bind bộ giá trị tiếp theo.
5. Gọi execute() để thực thi.

Chỉ số marker bắt đầu từ 0 trong R2DBC SPI. Cú pháp $1, $2, $3 ở ví dụ là kiểu marker của một số driver, chẳng hạn PostgreSQL; driver khác có thể dùng marker khác.

### Ví dụ xử lý kết quả batch

~~~java
Flux<Long> rowCounts =
    Flux.from(statement.execute())
        .concatMap(Result::getRowsUpdated);
~~~

Kết quả cụ thể và cách driver phát Result phụ thuộc implementation. Nếu cần tổng số dòng:

~~~java
Mono<Long> totalRows =
    rowCounts.reduce(0L, Long::sum);
~~~

Không nên giả định mỗi phần tử batch luôn trả đúng một Result hoặc một row count theo cùng cách trên mọi driver. Kiểm thử với driver mục tiêu và đọc API của driver.

### Bind NULL trong batch

Nếu một giá trị của bộ bind là null, dùng bindNull() với kiểu Java:

~~~java
statement
    .bind(0, 10L)
    .bind(1, "ext-003")
    .bindNull(2, String.class)
    .add();
~~~

Không truyền Java null vào bind(). Sau add(), bind đầy đủ bộ giá trị tiếp theo theo đúng thứ tự marker.

## 18. Batch bằng multi-row INSERT

Một cách khác là tạo một câu INSERT có nhiều bộ VALUES:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES
    (:tenant1, :external1, :name1),
    (:tenant2, :external2, :name2),
    (:tenant3, :external3, :name3);
~~~

Ưu điểm:

- Có thể giảm số statement và round trip.
- SQL thể hiện rõ một nhóm row được insert cùng nhau.
- Có thể kết hợp với upsert theo cú pháp database hỗ trợ.

Hạn chế:

- Số bind parameter tăng theo số dòng.
- Giới hạn kích thước SQL và packet khác nhau giữa database.
- Cần sinh tên placeholder duy nhất cho từng giá trị nếu dùng named parameters.
- Cách trả về generated keys khác nhau.
- Batch quá lớn có thể tốn bộ nhớ và làm tăng thời gian giữ transaction.

Với tập dữ liệu lớn, chia thành chunk có kích thước phù hợp thay vì tạo một câu SQL khổng lồ.

## 19. Batch, transaction và lỗi một phần

Batch không tự đồng nghĩa với atomicity.

Nếu chạy nhiều statement không có transaction chung, có thể xảy ra:

~~~text
INSERT row 1 -> thành công
INSERT row 2 -> thành công
INSERT row 3 -> lỗi
INSERT row 4 -> không chạy hoặc vẫn được driver xử lý tùy batch
~~~

Hai dòng đầu có thể đã được commit tùy auto-commit và cách driver thực thi. Nếu yêu cầu cả nhóm phải thành công hoặc thất bại cùng nhau, hãy bao batch trong transaction:

~~~java
return transactionalOperator.transactional(
    executeBatch(connectionFactory, items)
);
~~~

Transaction chỉ bảo vệ các thao tác dùng connection được transaction manager quản lý. Nếu batch được thực thi trên một connection tự tạo bên ngoài transaction context, nó có thể không tham gia transaction đó.

Với batch lớn, có thể chia thành nhiều chunk và mỗi chunk là một transaction. Khi đó, tính nguyên tử chỉ áp dụng trong từng chunk; các chunk trước có thể đã commit khi chunk sau lỗi. Đây là quyết định nghiệp vụ cần được nêu rõ.

## 20. Giới hạn batch khác nhau theo database

Các hệ quản trị có giới hạn và hành vi khác nhau:

- Số bind parameter tối đa.
- Độ dài câu SQL hoặc packet.
- Kích thước batch mà driver xử lý hiệu quả.
- Hỗ trợ generated keys hoặc RETURNING trong batch.
- Cách báo lỗi khi một phần tử trong batch thất bại.
- Cách xử lý duplicate key trong multi-row insert.

Ví dụ, SQL Server có giới hạn số parameter cho một request; Oracle có giới hạn riêng đối với một số biểu thức như danh sách IN; MySQL có giới hạn packet; PostgreSQL và driver cũng có giới hạn thực tế về số bind và kích thước statement.

Không sao chép một batch size cố định giữa các database. Đo throughput, latency, memory và connection usage trên môi trường gần production.

## 21. Batch với khóa ghép và upsert

Khi đồng bộ nhiều tenant customer, mỗi row có business key (tenant_id, external_customer_id). Có thể batch upsert nếu database hỗ trợ:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES
    (:tenant1, :external1, :name1),
    (:tenant2, :external2, :name2)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name;
~~~

Đây là ví dụ PostgreSQL. Trước khi dùng:

- Bảo đảm unique constraint tồn tại trên đúng cặp cột.
- Kiểm tra batch không chứa hai phần tử có cùng conflict key nếu câu lệnh hoặc database không cho phép cập nhật cùng target row nhiều lần trong một statement.
- Xác định chính sách khi hai bản ghi trong batch có giá trị khác nhau nhưng cùng business key.
- Chia chunk để giới hạn số parameter.
- Kiểm thử generated values và row counts.

Với MySQL, câu upsert và semantics conflict khác; với SQL Server/Oracle, dùng chiến lược theo dialect tương ứng. Không đưa một SQL batch upsert vào repository dùng chung cho mọi database nếu cú pháp không portable.

## 22. Savepoint là gì?

Savepoint là một điểm đánh dấu bên trong transaction đang mở. Nó cho phép rollback một phần công việc về điểm đánh dấu mà vẫn giữ transaction ngoài tiếp tục hoạt động, nếu database/driver hỗ trợ.

~~~text
BEGIN
  |
  v
Ghi dữ liệu chính
  |
  v
SAVEPOINT optional_part
  |
  v
Thực hiện phần tùy chọn
  |
  +---- Thành công ----> RELEASE SAVEPOINT
  |                         |
  |                         v
  |                    Tiếp tục transaction
  |
  +---- Thất bại ------> ROLLBACK TO SAVEPOINT
                            |
                            v
                       Tiếp tục transaction
  |
  v
COMMIT hoặc ROLLBACK transaction ngoài
~~~

Savepoint không commit độc lập. Khi transaction ngoài commit, mọi thay đổi còn lại sau savepoint được commit cùng nhau. Khi transaction ngoài rollback, toàn bộ thay đổi trong transaction bị hủy, kể cả các phần trước savepoint.

## 23. Savepoint khác REQUIRES_NEW

Hai cơ chế thường bị nhầm:

| Cơ chế | Connection/transaction | Khi rollback |
|---|---|---|
| Savepoint | Cùng transaction và connection bên ngoài | Quay lại điểm đánh dấu; transaction ngoài có thể tiếp tục |
| PROPAGATION_NESTED | Thường được triển khai bằng savepoint nếu manager hỗ trợ | Rollback phần nested về savepoint |
| PROPAGATION_REQUIRES_NEW | Transaction độc lập; thường cần connection riêng khi transaction ngoài đang bị suspend | Rollback transaction độc lập, không rollback transaction ngoài |

Savepoint không giải phóng connection và không tạo transaction commit độc lập. REQUIRES_NEW có thể cần thêm connection trong khi connection của transaction ngoài vẫn được giữ, nên cần tính đến pool size và nguy cơ chờ tài nguyên.

Nếu nghiệp vụ muốn phần audit hoặc log kỹ thuật được commit độc lập, savepoint không đáp ứng yêu cầu đó. Cần transaction riêng hoặc cơ chế ghi bền vững phù hợp.

## 24. Savepoint trong R2DBC SPI

R2DBC SPI cung cấp các thao tác savepoint trên Connection:

- createSavepoint(name): tạo savepoint.
- rollbackTransactionToSavepoint(name): rollback về savepoint.
- releaseSavepoint(name): giải phóng savepoint nếu database/driver hỗ trợ.

Các phương thức trả Publisher và phải được compose trong reactive chain. Không tự subscribe hoặc block.

Ví dụ minh họa sử dụng connection đang được Spring transaction quản lý:

~~~java
public Mono<Void> runOptionalWork() {
    return ConnectionFactoryUtils.getConnection(connectionFactory)
        .flatMap(connection ->
            Mono.from(connection.createSavepoint("optional_work"))
                .then(
                    optionalRepository.perform()
                        .onErrorResume(error ->
                            Mono.from(
                                connection.rollbackTransactionToSavepoint(
                                    "optional_work"
                                )
                            ).then()
                        )
                )
        );
}
~~~

Phương thức này phải được gọi bên trong transaction đang hoạt động trên cùng ConnectionFactory. ConnectionFactoryUtils.getConnection() lấy connection gắn với transaction context khi có transaction tương ứng. Không tự đóng connection transaction-bound; transaction manager chịu trách nhiệm giải phóng nó.

Ví dụ cố ý phục hồi lỗi của phần việc tùy chọn sau khi rollback về savepoint. Nếu lỗi không được phép bỏ qua, hãy để lỗi tiếp tục đi ra để transaction ngoài rollback.

### Giải phóng savepoint

Sau khi hoàn tất phần việc, có thể gọi releaseSavepoint() nếu driver/database hỗ trợ:

~~~java
Mono.from(connection.releaseSavepoint("optional_work"));
~~~

Không phải mọi database có cú pháp release giống nhau. SQL Server và Oracle có khác biệt so với PostgreSQL/MySQL/SQLite; R2DBC driver chịu trách nhiệm ánh xạ API SPI sang khả năng thực tế. Nếu release không được hỗ trợ, kiểm tra driver và tài liệu database thay vì giả định lời gọi luôn thành công.

## 25. Savepoint và Propagation.NESTED

Spring transaction propagation NESTED biểu diễn một phạm vi transaction lồng bên trong transaction hiện tại. Với transaction manager có hỗ trợ, phạm vi này thường được triển khai bằng savepoint.

Ví dụ:

~~~java
@Transactional(transactionManager = "r2dbcTransactionManager")
public Mono<Void> outerOperation() {
    return writeMainRecord()
        .then(optionalService.writeOptionalRecord());
}
~~~

Nếu dùng NESTED cho optionalService, cần cấu hình propagation trên method được gọi qua Spring proxy và xác nhận R2dbcTransactionManager, R2DBC driver cùng database hỗ trợ savepoint cho trường hợp đó.

Không phải mọi transaction manager hoặc driver đều hỗ trợ nested transaction. Nếu savepoint không được hỗ trợ, thao tác nested có thể báo lỗi thay vì âm thầm hoạt động như transaction độc lập.

### NESTED không phải REQUIRES_NEW

- NESTED dùng cùng transaction vật lý và savepoint khi được hỗ trợ.
- REQUIRES_NEW suspend transaction hiện tại và mở transaction độc lập theo khả năng manager.
- Commit nested scope không commit transaction ngoài.
- Commit transaction REQUIRES_NEW có thể tồn tại ngay cả khi transaction ngoài rollback.

Hãy chọn theo yêu cầu atomicity, không chỉ theo tên propagation.

## 26. Khác biệt savepoint giữa các hệ quản trị

| Hệ quản trị | Khả năng thường gặp | Lưu ý |
|---|---|---|
| PostgreSQL | SAVEPOINT, ROLLBACK TO SAVEPOINT, RELEASE SAVEPOINT | Lỗi statement có thể làm transaction aborted; rollback về savepoint có thể khôi phục trạng thái transaction |
| MySQL InnoDB | Savepoint trong transaction | Engine phải hỗ trợ transaction; không áp dụng giống nhau cho mọi storage engine |
| MariaDB | Savepoint trong transaction với engine phù hợp | Kiểm tra engine và phiên bản |
| SQLite | Savepoint và nested transaction semantics | Có thể dùng savepoint ngay cả khi không có transaction ngoài theo cách riêng của SQLite |
| SQL Server | SAVE TRANSACTION, ROLLBACK TRANSACTION savepoint_name | Không có lệnh RELEASE SAVEPOINT tương đương PostgreSQL |
| Oracle | SAVEPOINT, ROLLBACK TO SAVEPOINT | Cú pháp và quy tắc release khác các hệ khác |

Đây là mô tả khái quát. R2DBC driver có thể chưa triển khai đầy đủ một tính năng dù database có hỗ trợ SQL tương ứng. Luôn kiểm tra driver version và thực hiện integration test.

Một số câu lệnh DDL có semantics transaction khác nhau hoặc có thể gây implicit commit tùy database. Không dùng savepoint để giả định mọi DDL đều có thể rollback giống DML.

## 27. Batch và savepoint kết hợp

Savepoint hữu ích khi một phần batch là tùy chọn:

1. Bắt đầu transaction ngoài.
2. Ghi dữ liệu chính.
3. Tạo savepoint.
4. Thực thi batch phụ.
5. Nếu batch thành công, tiếp tục.
6. Nếu batch thất bại và database cho phép rollback về savepoint, rollback phần batch rồi xử lý phần còn lại theo nghiệp vụ.
7. Commit transaction ngoài.

Ví dụ khái niệm:

~~~java
return transactionalOperator.transactional(
    writeRequiredData()
        .then(createSavepointAndRunOptionalBatch())
        .then(writeFinalStatus())
);
~~~

Nếu một batch insert bị duplicate key, database có thể đánh dấu transaction ở trạng thái lỗi. Với PostgreSQL, cần rollback về savepoint trước khi chạy tiếp các câu lệnh khác trong transaction. Chỉ bắt exception bằng onErrorResume mà không rollback savepoint không bảo đảm transaction có thể tiếp tục.

Nếu lỗi batch phải làm toàn bộ nghiệp vụ thất bại, không cần nuốt lỗi hoặc dùng savepoint; để lỗi đi ra và rollback transaction ngoài.

## 28. Chọn batch size và savepoint boundary

Batch size ảnh hưởng:

- Số bind parameter.
- Kích thước packet hoặc statement.
- Bộ nhớ ứng dụng.
- Thời gian giữ connection.
- Khả năng rollback một nhóm dữ liệu.
- Độ trễ và throughput.

Savepoint boundary ảnh hưởng phạm vi có thể rollback một phần. Không nên tạo một savepoint cho từng row trong batch lớn nếu không có yêu cầu nghiệp vụ; số savepoint quá nhiều có thể làm tăng overhead.

Một chiến lược thường dùng:

- Chia dữ liệu thành chunk vừa phải.
- Mỗi chunk nằm trong transaction riêng nếu chấp nhận commit từng phần.
- Nếu nhiều bước trong cùng chunk cần phục hồi một phần, dùng savepoint ở ranh giới nghiệp vụ rõ ràng.
- Theo dõi số row thành công, số row lỗi và business key gây lỗi.

Nếu tất cả chunk phải atomic như một đơn vị, một transaction dài có thể giữ connection/lock lâu. Cần cân nhắc lại yêu cầu nghiệp vụ, thiết kế staging table hoặc quy trình bù trừ thay vì mở transaction rất lớn.

## 29. Thiết kế abstraction để hỗ trợ nhiều database

Không nên để service chứa nhiều nhánh SQL theo database:

~~~java
if (databaseType.equals("postgres")) {
    // SQL PostgreSQL
} else if (databaseType.equals("mysql")) {
    // SQL MySQL
}
~~~

Thay vào đó, định nghĩa một contract theo nghiệp vụ:

~~~java
public interface TenantCustomerUpsert {

    Mono<TenantCustomerView> upsert(
        Long tenantId,
        String externalId,
        String name
    );
}
~~~

Sau đó cung cấp implementation theo dialect:

~~~text
TenantCustomerUpsert
        |
        +-- PostgresTenantCustomerUpsert
        |
        +-- MySqlTenantCustomerUpsert
        |
        +-- SqlServerTenantCustomerUpsert
~~~

Mỗi implementation dùng DatabaseClient được tạo từ đúng ConnectionFactory. Chọn implementation bằng Spring profile, conditional configuration hoặc cấu hình rõ ràng khi khởi động.

Tương tự, có thể tách contract cho batch writer và savepoint executor nếu các khả năng này là một phần của kiến trúc. Không cần tạo abstraction quá rộng nếu ứng dụng chỉ triển khai một database; chỉ trừu tượng hóa những khác biệt thực sự cần hỗ trợ.

## 30. Kiểm thử với đúng database và R2DBC driver

Mock repository không thể chứng minh cú pháp upsert, batch hoặc savepoint hoạt động đúng trên database. Nên dùng integration test với Testcontainers hoặc môi trường database tương ứng.

### Kiểm thử khóa ghép

- Insert hai dòng có cùng external ID nhưng khác tenant.
- Insert trùng cả tenant ID và external ID.
- Xác nhận unique constraint từ chối duplicate.
- Kiểm tra hành vi với NULL nếu schema cho phép.
- Kiểm tra collation/case sensitivity của business key.
- Xác nhận UPDATE/DELETE luôn dùng đủ thành phần khóa.

### Kiểm thử upsert

- Key chưa tồn tại: tạo dòng.
- Key đã tồn tại: cập nhật đúng cột.
- Xung đột trên unique key khác: xác nhận chính sách.
- Hai request upsert cùng key đồng thời: không tạo duplicate.
- Xác nhận ID và giá trị trả về sau upsert.
- Kiểm tra trường created/updated và version nếu có.

### Kiểm thử batch

- Batch có một và nhiều phần tử.
- Batch có giá trị null cần bindNull.
- Batch vượt kích thước chunk thông thường.
- Một phần tử lỗi giữa batch.
- Xác nhận row count và generated key.
- Kiểm tra transaction rollback toàn batch hoặc từng chunk theo thiết kế.

### Kiểm thử savepoint

- Tạo savepoint sau một thao tác ghi thành công.
- Ghi thêm dữ liệu sau savepoint.
- Rollback về savepoint.
- Xác nhận dữ liệu trước savepoint còn và dữ liệu sau savepoint mất.
- Tiếp tục ghi và commit transaction ngoài.
- Kiểm tra release savepoint nếu driver hỗ trợ.
- Kiểm tra lỗi database có thể phục hồi sau rollback savepoint hay không.

## 31. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
|---|---|---|
| Giả định @EmbeddedId của JPA hoạt động như nhau trong R2DBC | Mapping repository không đúng | Dùng một @Id hoặc custom repository cho khóa ghép |
| Thêm surrogate ID nhưng bỏ unique business key | Dữ liệu nghiệp vụ bị trùng | Tạo unique constraint trên toàn bộ thành phần khóa |
| Chỉ kiểm tra tồn tại trước INSERT | Race condition khi request đồng thời | Dựa vào unique constraint và database upsert |
| Nghĩ save() là upsert | Nhánh INSERT/UPDATE không như mong muốn | Dùng SQL upsert theo dialect |
| Dùng PostgreSQL ON CONFLICT trên MySQL | SQL syntax error | Tách implementation theo database |
| Bỏ tenant ID khỏi conflict target | Có thể cập nhật nhầm tenant | Dùng đầy đủ business key |
| Không xét NULL/collation của unique key | Quy tắc trùng lặp khác giữa DB | NOT NULL và chuẩn hóa/cấu hình collation |
| Nghĩ saveAll() luôn là batch | Số statement vẫn có thể tăng theo entity | Kiểm tra implementation/driver; dùng SPI batch nếu cần |
| Gọi Statement.add() nhưng bind thiếu marker | Batch lỗi hoặc dữ liệu sai cột | Bind đầy đủ mỗi parameter set |
| Dùng một batch quá lớn | Vượt parameter/packet limit, tăng memory | Chia chunk và đo theo database |
| Nghĩ batch tự atomic | Có thể commit một phần | Bao trong transaction nếu cần all-or-nothing |
| Nuốt batch error mà không rollback savepoint | Transaction có thể vẫn ở trạng thái lỗi | Rollback về savepoint hoặc rollback transaction |
| Nghĩ savepoint là transaction độc lập | Hiểu sai phạm vi commit | Savepoint chỉ đánh dấu trong transaction hiện tại |
| Dùng REQUIRES_NEW thay cho savepoint mà không tính pool | Cần connection riêng, có thể cạn pool | Chọn NESTED/savepoint nếu phù hợp |
| Giả định mọi driver hỗ trợ release savepoint | Runtime error hoặc unsupported operation | Kiểm tra driver/database |
| Dùng SQL dialect đặc thù trong repository dùng chung | Không chạy trên DB khác | Tách adapter/implementation |

## 32. Quy trình lựa chọn giải pháp

Khi thiết kế thao tác dữ liệu cần khóa ghép, upsert, batch hoặc savepoint, hãy xác định:

1. Khóa chính của bảng có một cột hay nhiều cột?
2. Spring Data repository có thể biểu diễn định danh đó theo mapping đang dùng không?
3. Có thể dùng surrogate ID và giữ unique business key không?
4. Nếu giữ khóa ghép, custom SQL có dùng đầy đủ các thành phần khóa không?
5. Database nào đang được triển khai và cú pháp upsert tương ứng là gì?
6. Conflict target có được bảo vệ bởi unique constraint không?
7. Cần trả về ID hay toàn bộ row sau upsert không?
8. Batch là saveAll, SPI Statement.add, multi-row INSERT hay bulk SQL?
9. Driver có hỗ trợ batch và generated values theo cách mong muốn không?
10. Batch cần atomic toàn bộ, theo chunk hay cho phép một phần thành công?
11. Có cần rollback một phần công việc trong transaction không?
12. Database và driver có hỗ trợ savepoint và release savepoint không?
13. NESTED có được transaction manager hỗ trợ không, hay cần transaction độc lập?
14. Đã kiểm thử dưới concurrency và với đúng phiên bản database/driver chưa?

## 33. Ghi nhớ

- Spring Data Relational repository mapping xoay quanh một thuộc tính @Id; không mặc định hỗ trợ @EmbeddedId/@IdClass như JPA.
- Với khóa ghép, có thể dùng surrogate primary key kết hợp unique constraint trên business key; nếu giữ schema composite PK, dùng custom SQL/repository và luôn bind đủ thành phần khóa.
- NULL, collation và case sensitivity có thể làm unique key khác nhau giữa hệ quản trị.
- save() chọn INSERT hoặc UPDATE theo new-state detection; nó không phải database-native upsert.
- PostgreSQL/SQLite thường dùng ON CONFLICT; MySQL/MariaDB dùng ON DUPLICATE KEY UPDATE; SQL Server/Oracle có cú pháp MERGE riêng và semantics riêng.
- Upsert an toàn cần primary key hoặc unique constraint phù hợp; SELECT rồi INSERT không loại bỏ race condition.
- saveAll() không bảo đảm một statement batch duy nhất.
- R2DBC SPI Statement.add() hỗ trợ nhiều bộ bind cho một statement khi driver triển khai; bind lại đầy đủ từng bộ và kiểm thử row count.
- Multi-row INSERT, SPI batch và transaction là ba khái niệm khác nhau.
- Batch không tự atomic; dùng transaction khi cần tất cả thao tác cùng commit hoặc rollback.
- Batch size và parameter limit phụ thuộc database, driver và phiên bản.
- Savepoint đánh dấu một điểm trong transaction hiện tại; rollback về savepoint không commit phần còn lại độc lập.
- PROPAGATION_NESTED thường dựa trên savepoint khi transaction manager/driver hỗ trợ; REQUIRES_NEW là transaction độc lập.
- R2DBC SPI có createSavepoint, rollbackTransactionToSavepoint và releaseSavepoint; khả năng thực tế phụ thuộc driver/database.
- Tách SQL theo dialect vào implementation riêng và kiểm thử bằng database/driver thực tế.
