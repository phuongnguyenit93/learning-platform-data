# Thiết kế đa khách thuê và bảo vệ ranh giới dữ liệu

Trong hệ thống multi-tenant, một ứng dụng phục vụ nhiều khách hàng tổ chức hoặc tenant trên cùng nền tảng. Mỗi tenant có dữ liệu riêng và chỉ người dùng được phép mới có thể đọc hoặc thay đổi dữ liệu đó. Spring Data R2DBC cung cấp repository, mapping và transaction reactive, nhưng không tự tạo một ranh giới tenant an toàn cho mọi câu SQL.

Vì vậy, thiết kế multi-tenant cần được thực hiện xuyên suốt từ xác thực người dùng, xác định tenant, chọn database/schema, xây dựng query, kiểm soát transaction, đến cache, message và kiểm thử. Một lỗi thiếu điều kiện tenant trong một câu SELECT, UPDATE hoặc DELETE có thể làm lộ hoặc thay đổi dữ liệu của tenant khác.

Có ba mô hình lưu trữ phổ biến:

- **Shared database, shared schema:** mọi tenant dùng chung bảng; mỗi hàng có cột tenant_id.
- **Shared database, schema per tenant:** mỗi tenant có schema riêng trong cùng database.
- **Database per tenant:** mỗi tenant có database và thường có ConnectionFactory/pool riêng.

Mỗi mô hình có mức cô lập, chi phí vận hành và khả năng mở rộng khác nhau. Hãy chọn theo yêu cầu bảo mật, quy mô, khả năng vận hành và mức độ tùy biến của tenant.

## 1. Multi-tenancy và ranh giới dữ liệu

Tenant là một phạm vi dữ liệu độc lập về mặt nghiệp vụ, ví dụ một công ty, tổ chức, cửa hàng hoặc workspace. Một user có thể thuộc một tenant hoặc nhiều tenant; quyền truy cập tenant cần được xác minh trước khi truy vấn dữ liệu.

Ví dụ hệ thống quản lý bán hàng:

~~~text
Tenant A
  customers
  orders
  products

Tenant B
  customers
  orders
  products
~~~

Hai tenant có thể có cùng loại dữ liệu và thậm chí có cùng mã khách hàng hoặc mã đơn hàng. Tuy nhiên, tenant A không được đọc hoặc thay đổi dữ liệu của tenant B.

### 1.1. Ranh giới tenant phải được kiểm tra ở nhiều lớp

Một thiết kế an toàn thường có nhiều lớp bảo vệ:

1. **Identity và authorization:** xác định user đã đăng nhập và tenant mà user được phép truy cập.
2. **Tenant context:** truyền tenant đã xác thực xuyên suốt reactive pipeline.
3. **Data access:** mọi query được giới hạn trong tenant hoặc được route tới đúng database/schema.
4. **Database constraints:** khóa, foreign key và row-level security ngăn dữ liệu liên tenant sai lệch.
5. **Transaction:** mọi statement trong cùng nghiệp vụ dùng cùng tenant context và connection phù hợp.
6. **Cache và messaging:** key cache, event và consumer đều giữ đúng tenant scope.
7. **Testing và observability:** kiểm thử truy cập chéo tenant và theo dõi hành vi truy vấn.

Không nên xem tenant_id trong request body là bằng chứng quyền truy cập. Client có thể sửa giá trị này. Tenant phải được xác định từ principal đã xác thực và kiểm tra membership/authorization ở server.

## 2. Chọn mô hình lưu trữ cho nhiều tenant

### 2.1. Shared database, shared schema

Tất cả tenant dùng chung database, schema và bảng. Mỗi bảng chứa dữ liệu tenant có cột tenant_id:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(240),
    created_at TIMESTAMP NOT NULL,
    last_modified_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_customer_tenant_email UNIQUE (tenant_id, email)
);

CREATE INDEX ix_customers_tenant_name
    ON customers (tenant_id, name);
~~~

Ưu điểm:

- Hạ tầng đơn giản, ít database và connection pool.
- Dễ triển khai migration một lần cho toàn bộ tenant.
- Tận dụng tài nguyên database tốt khi số tenant lớn nhưng mỗi tenant có ít dữ liệu.
- Có thể chạy báo cáo tổng hợp nếu nghiệp vụ cho phép.

Nhược điểm:

- Mọi query phải có tenant predicate chính xác.
- Một lỗi thiếu tenant_id có thể gây truy cập chéo dữ liệu.
- Tenant lớn có thể ảnh hưởng hiệu năng của tenant khác nếu không có giới hạn tài nguyên.
- Một số thao tác quản trị hoặc migration cần chú ý dữ liệu của tất cả tenant.

Đây là mô hình thường dễ bắt đầu nhất, nhưng yêu cầu kỷ luật truy vấn và kiểm soát ở database.

### 2.2. Shared database, schema per tenant

Các tenant dùng chung một database server/database nhưng có schema riêng:

~~~text
database: saas
  schema tenant_a
    customers
    orders
    products
  schema tenant_b
    customers
    orders
    products
~~~

Ưu điểm:

- Tách namespace và đối tượng database theo tenant.
- Có thể cấp quyền database/schema riêng.
- Dễ backup/restore hoặc chuyển một tenant hơn so với shared tables, tùy hệ quản trị.
- Query trong schema thường không cần tenant_id trên mọi bảng.

Nhược điểm:

- Quản lý schema và migration phức tạp khi số tenant tăng.
- Connection cần được định tuyến đúng schema.
- Thay đổi schema session trên connection pool có nguy cơ rò trạng thái giữa request nếu không được reset.
- Báo cáo tổng hợp nhiều tenant cần truy vấn nhiều schema hoặc cơ chế hợp nhất riêng.

Nếu database hỗ trợ schema qualification, query có thể chỉ rõ schema. Nếu dựa vào search path hoặc schema mặc định của connection, cần quản lý context theo transaction và connection.

### 2.3. Database per tenant

Mỗi tenant có database riêng, có thể cùng server hoặc ở các cluster khác nhau:

~~~text
Tenant A -> ConnectionFactory A -> Database A
Tenant B -> ConnectionFactory B -> Database B
Tenant C -> ConnectionFactory C -> Database C
~~~

Ưu điểm:

- Mức cô lập dữ liệu và tài nguyên cao hơn.
- Có thể backup, restore, migrate hoặc chuyển tenant độc lập.
- Dễ đáp ứng yêu cầu một số khách hàng phải dùng database riêng.
- Có thể tùy biến cấu hình database theo tenant.

Nhược điểm:

- Số ConnectionFactory và connection pool tăng theo tenant.
- Provisioning, migration, credential rotation và monitoring phức tạp.
- Chi phí vận hành cao hơn.
- Query xuyên tenant và transaction nhiều database khó hơn.

Với số lượng tenant rất lớn, không nên mặc định tạo một pool không giới hạn cho mỗi tenant. Cần chiến lược pool lifecycle, giới hạn connection tổng, idle eviction và quản lý tenant database registry.

### 2.4. So sánh nhanh

| Tiêu chí | Shared schema | Schema per tenant | Database per tenant |
| --- | --- | --- | --- |
| Cô lập dữ liệu | Dựa nhiều vào tenant predicate và constraint | Tách namespace/schema | Tách database |
| Số connection pool | Thường ít | Có thể dùng chung database pool | Thường nhiều pool hoặc routing pool |
| Migration | Một schema chung | Lặp theo từng schema | Lặp theo từng database |
| Chi phí vận hành | Thấp hơn | Trung bình | Cao hơn |
| Báo cáo liên tenant | Thuận tiện nếu được phép | Phải hợp nhất schema | Phải hợp nhất database |
| Tenant lớn cần tách riêng | Cần shard hoặc chuyển tenant | Có thể chuyển schema | Đã có ranh giới database |
| Rủi ro thiếu tenant predicate | Cao | Thấp hơn nếu schema routing đúng | Thấp hơn nếu routing đúng |

Có thể dùng mô hình kết hợp: đa số tenant ở shared schema, tenant lớn hoặc có yêu cầu tuân thủ riêng ở database riêng. Điều này đòi hỏi một tenant registry và một lớp routing thống nhất.

## 3. Xác định tenant từ danh tính đã xác thực

Tenant context nên được tạo sau bước authentication và authorization. Một request có thể gửi tenant slug hoặc tenant ID trong host, header hoặc path, nhưng server phải xác minh user có quyền với tenant đó.

Luồng khái niệm:

~~~text
HTTP request
    |
    v
Authenticate user
    |
    v
Resolve requested tenant
    |
    v
Check user membership and permissions
    |
    v
Create trusted TenantContext
    |
    v
Execute reactive service and repository calls
~~~

Ví dụ, user đăng nhập có thể thuộc tenant 10 và tenant 20. Request chọn tenant 20 chỉ được chấp nhận nếu membership hiện tại cho phép user hoạt động trong tenant đó.

### 3.1. Không tin tenant ID từ body

Tránh:

~~~java
public Mono<Order> createOrder(CreateOrderRequest request) {
    return orderRepository.save(new Order(
            request.tenantId(),
            request.customerId(),
            request.totalAmount()));
}
~~~

Client có thể thay tenantId trong payload để ghi dữ liệu sang tenant khác.

Thay vào đó, lấy tenant từ context đã xác thực:

~~~java
public Mono<Order> createOrder(CreateOrderRequest request) {
    return tenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository.save(
                    Order.newOrder(
                            tenantId,
                            request.customerId(),
                            request.totalAmount())));
}
~~~

Ví dụ giả định tenantContext chỉ phát tenant đã được authorization layer xác minh. Với endpoint quản trị cho phép chọn tenant khác, phải có quyền riêng, audit actor và quy tắc kiểm tra rõ ràng.

### 3.2. Tenant context cho job nền và message consumer

Job nền thường không có HTTP security context. Message có thể chứa tenant ID, nhưng consumer vẫn cần xác thực nguồn phát và kiểm tra schema của message.

Một event có thể mang:

~~~json
{
  "eventId": "evt-901",
  "tenantId": 20,
  "aggregateId": 481,
  "eventType": "OrderCreated"
}
~~~

Tenant ID trong message chỉ được tin cậy khi message đến từ producer/service đã xác thực và có integrity phù hợp. Consumer cần đưa tenant vào context trước khi truy cập dữ liệu và tránh xử lý message thiếu tenant nếu event thuộc loại tenant-scoped.

## 4. Truyền tenant context trong ứng dụng reactive

Spring Data R2DBC và Reactor không nên dựa vào ThreadLocal để truyền tenant giữa các bước reactive. Một pipeline có thể đổi thread hoặc scheduler; ThreadLocal không phải cơ chế context phù hợp cho reactive flow.

Reactor Context được truyền cùng subscription và có thể được đọc bằng deferContextual.

### 4.1. Định nghĩa tenant context

~~~java
public final class TenantContext {

    public static final String TENANT_ID = "tenantId";

    private TenantContext() {
    }

    public static Mono<Long> currentTenantId() {
        return Mono.deferContextual(context -> {
            if (!context.hasKey(TENANT_ID)) {
                return Mono.error(new IllegalStateException(
                        "Tenant context is missing"));
            }
            return Mono.just(context.get(TENANT_ID));
        });
    }

    public static <T> Mono<T> withTenant(
            Long tenantId,
            Mono<T> publisher) {
        return publisher.contextWrite(context ->
                context.put(TENANT_ID, tenantId));
    }
}
~~~

Ví dụ dùng context:

~~~java
Mono<Order> result = tenantContext.withTenant(
        20L,
        orderService.createOrder(command));
~~~

Đây chỉ là lớp minh họa. Trong ứng dụng thật, tenant ID phải được lấy từ authorization layer chứ không phải một hằng số do endpoint tùy ý chọn.

### 4.2. Đọc context ở service/repository adapter

~~~java
public Mono<Order> createOrder(CreateOrderCommand command) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository.save(
                    Order.newOrder(
                            tenantId,
                            command.customerId(),
                            command.totalAmount())));
}
~~~

Không lưu tenant hiện tại vào một static mutable field hoặc singleton field có thể bị request khác ghi đè. Mỗi subscription cần có context riêng.

### 4.3. Reactive Security Context

Nếu dùng Spring Security WebFlux, có thể đọc authentication bằng ReactiveSecurityContextHolder. Từ principal, lấy tenant đã chọn và kiểm tra membership. Sau khi authorization hoàn tất, đưa tenant đã xác thực vào Reactor Context để tầng data access dùng thống nhất.

Không nên dùng SecurityContextHolder theo kiểu imperative trong một reactive pipeline để suy ra tenant. Thread-local có thể không còn đúng khi pipeline chuyển scheduler.

## 5. Bảo vệ shared schema bằng tenant_id

Trong shared schema, tenant_id là một phần của khóa phạm vi dữ liệu. Cần áp dụng nhất quán cho mọi thao tác:

- SELECT: chỉ đọc hàng của tenant hiện tại.
- INSERT: gán tenant_id từ context đáng tin cậy.
- UPDATE: predicate phải chứa tenant_id.
- DELETE: predicate phải chứa tenant_id.
- JOIN: các quan hệ phải bảo đảm tenant của hai phía tương thích.
- Aggregate/report: mọi bảng nguồn phải được giới hạn tenant theo cùng quy tắc.

### 5.1. Repository method có tenant scope

Không nên chỉ cung cấp method tìm theo ID nếu ID không phải ranh giới authorization:

~~~java
public interface OrderRepository
        extends ReactiveCrudRepository<Order, Long> {

    Mono<Order> findByIdAndTenantId(Long id, Long tenantId);

    Flux<Order> findAllByTenantIdAndStatus(Long tenantId, String status);
}
~~~

Service:

~~~java
public Mono<Order> findOrder(Long orderId) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository
                    .findByIdAndTenantId(orderId, tenantId));
}
~~~

Nếu ID là global unique, điều kiện tenant vẫn hữu ích để xác nhận quyền sở hữu ở database. Nếu ID chỉ unique trong tenant, khóa chính phải là composite hoặc repository query phải luôn mang tenant.

### 5.2. Không để controller/service gọi repository không có tenant scope

Một repository generic có findById(id) rất tiện nhưng có thể trở thành đường truy cập bỏ qua tenant. Có thể:

- Dùng repository chuyên biệt với các method có tenant.
- Đóng gói repository sau tenant-aware service/adapter.
- Tạo custom repository base có tenant context bắt buộc.
- Hạn chế visibility của repository để controller không gọi trực tiếp.
- Dùng row-level security làm lớp bảo vệ database bổ sung.

Không nên chỉ dựa vào quy ước tên method. Review và test phải xác nhận tất cả đường truy cập đều được giới hạn.

### 5.3. Query trực tiếp bằng @Query

Với native SQL hoặc @Query, thêm tenant predicate rõ ràng:

~~~java
@Query("""
       SELECT *
       FROM orders
       WHERE id = :orderId
         AND tenant_id = :tenantId
       """)
Mono<Order> findTenantOrder(
        @Param("orderId") Long orderId,
        @Param("tenantId") Long tenantId);
~~~

Đối với update/delete:

~~~java
@Modifying
@Query("""
       UPDATE orders
       SET status = :status
       WHERE id = :orderId
         AND tenant_id = :tenantId
       """)
Mono<Integer> updateStatus(
        @Param("orderId") Long orderId,
        @Param("tenantId") Long tenantId,
        @Param("status") String status);
~~~

Không chỉ thêm tenant predicate vào SELECT. Một câu UPDATE thiếu điều kiện tenant có thể thay đổi hàng của nhiều tenant dù endpoint đã kiểm tra quyền ở controller.

### 5.4. Query bằng R2dbcEntityTemplate

Với Query và Update, thêm tenant vào Criteria:

~~~java
public Mono<Long> updateStatus(
        Long orderId,
        String status) {

    return TenantContext.currentTenantId()
            .flatMap(tenantId -> {
                Query query = query(
                        where("id").is(orderId)
                                .and("tenantId").is(tenantId));

                Update update = Update.update("status", status);

                return template.update(Order.class)
                        .matching(query)
                        .apply(update);
            });
}
~~~

Property tenantId được mapping sang cột tenant_id theo metadata entity. Nếu dùng DatabaseClient hoặc SQL thuần, phải dùng tên cột và bind tenant ID trực tiếp.

### 5.5. INSERT phải lấy tenant từ server

~~~java
public Mono<Order> createOrder(CreateOrderCommand command) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> {
                Order order = Order.newOrder(
                        tenantId,
                        command.customerId(),
                        command.totalAmount());
                return orderRepository.save(order);
            });
}
~~~

Không cho client quyết định tenant_id của hàng mới. Nếu entity nhận tenant ID qua constructor, chỉ tầng đã xác thực/ủy quyền mới được tạo giá trị đó.

## 6. Dùng khóa và constraint để ngăn liên kết chéo tenant

Predicate trong query giúp giới hạn truy cập, nhưng database constraint cũng cần ngăn một hàng thuộc tenant A tham chiếu đến hàng thuộc tenant B.

Giả sử customers và orders đều có tenant_id:

~~~sql
CREATE TABLE customers (
    id BIGINT NOT NULL,
    tenant_id BIGINT NOT NULL,
    name VARCHAR(160) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_customers_tenant_id_id UNIQUE (tenant_id, id)
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_order_customer_same_tenant
        FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers (tenant_id, id)
);
~~~

Khóa unique tổng hợp trên customers cho phép foreign key tham chiếu đồng thời tenant_id và customer_id. Nhờ vậy, order của tenant A không thể tham chiếu customer của tenant B, ngay cả khi code ứng dụng truyền nhầm ID.

### 6.1. Unique constraint cần bao gồm tenant

Nếu email chỉ cần duy nhất trong từng tenant:

~~~sql
CREATE UNIQUE INDEX uk_customers_tenant_email
ON customers (tenant_id, email);
~~~

Không tạo unique index chỉ trên email nếu hai tenant được phép có cùng địa chỉ email.

Tương tự, mã đơn hàng có thể duy nhất theo tenant:

~~~sql
UNIQUE (tenant_id, order_number)
~~~

Quy tắc uniqueness là quyết định nghiệp vụ. Nếu email phải duy nhất toàn hệ thống, dùng unique toàn cục; nếu chỉ duy nhất trong tenant, dùng composite key.

### 6.2. Index phải bắt đầu từ tenant khi query có tenant predicate

Với query thường dùng:

~~~sql
SELECT *
FROM orders
WHERE tenant_id = :tenantId
  AND status = :status
ORDER BY created_at DESC;
~~~

Index có thể phù hợp:

~~~sql
CREATE INDEX ix_orders_tenant_status_created
ON orders (tenant_id, status, created_at DESC);
~~~

Thứ tự cột index cần dựa trên query thực tế, selectivity và execution plan của database. Không nên tạo index theo công thức cố định cho mọi bảng.

## 7. Row-Level Security làm lớp bảo vệ database

Với shared schema, một số database hỗ trợ Row-Level Security (RLS). RLS áp dụng policy ở database để giới hạn hàng mà database role có thể đọc hoặc thay đổi.

PostgreSQL là ví dụ phổ biến:

~~~sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY orders_tenant_policy
ON orders
USING (
    tenant_id = current_setting('app.tenant_id', true)::BIGINT
)
WITH CHECK (
    tenant_id = current_setting('app.tenant_id', true)::BIGINT
);
~~~

Ý nghĩa:

- USING giới hạn các hàng được đọc hoặc được target bởi UPDATE/DELETE.
- WITH CHECK kiểm tra hàng mới hoặc hàng sau update có thỏa policy hay không.
- Nếu app.tenant_id không được thiết lập, biểu thức trả NULL và không hàng nào thỏa phép so sánh tenant_id = NULL.

RLS giúp bảo vệ cả những câu SQL vô tình thiếu tenant predicate, nhưng cần cấu hình role và context cẩn thận.

### 7.1. Thiết lập tenant context theo transaction trong PostgreSQL

PostgreSQL hỗ trợ set_config với tham số is_local = true:

~~~sql
SELECT set_config('app.tenant_id', :tenantId, true);
~~~

Lệnh này đặt tenant ID trong phạm vi transaction hiện tại. Sau đó các query trên cùng transaction/connection chịu policy RLS tương ứng.

Trong Spring Data R2DBC, có thể thực hiện bằng DatabaseClient bên trong reactive transaction:

~~~java
public <T> Mono<T> inTenantTransaction(
        Long tenantId,
        Mono<T> work) {

    Mono<Void> setTenant = databaseClient.sql(
                    "SELECT set_config('app.tenant_id', :tenantId, true)")
            .bind("tenantId", tenantId.toString())
            .fetch()
            .rowsUpdated()
            .then();

    return transactionalOperator.transactional(
            setTenant.then(work));
}
~~~

Đoạn code minh họa cần được điều chỉnh theo kiểu trả về và cách bind của phiên bản DatabaseClient. Điểm bắt buộc là set_config và mọi query được bảo vệ bởi RLS phải dùng cùng transaction connection. Không chạy set_config ở một connection rồi query ở connection khác.

### 7.2. Bảo vệ role database

PostgreSQL table owner thường có thể bypass RLS trừ khi bật FORCE ROW LEVEL SECURITY; superuser và role có BYPASSRLS vẫn có quyền bypass. Ứng dụng nên dùng database role có quyền tối thiểu, không dùng superuser.

Có thể cân nhắc:

~~~sql
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
~~~

Kiểm tra quyền của role ứng dụng, owner, migration role và các job quản trị. Migration role có thể cần quyền cao hơn nhưng không nên được dùng bởi request runtime.

### 7.3. RLS không thay thế authorization

RLS bảo vệ hàng ở database dựa trên context đã thiết lập. Nó không xác minh user có quyền thuộc tenant đó hay không. Nếu ứng dụng lấy tenant ID từ request không đáng tin cậy rồi đặt vào app.tenant_id, policy sẽ bảo vệ nhầm tenant mà attacker yêu cầu.

Hãy xác thực user, kiểm tra membership trước, sau đó mới thiết lập tenant context trong transaction.

### 7.4. Test RLS với đúng role runtime

Test bằng database owner có thể bỏ qua RLS và tạo cảm giác hệ thống an toàn. Integration test cần kết nối bằng role tương tự ứng dụng runtime và xác nhận:

- Không có tenant context thì không đọc/ghi được hàng tenant-scoped.
- Tenant A không đọc hoặc sửa được hàng tenant B.
- INSERT với tenant_id khác context bị từ chối.
- UPDATE không thể chuyển hàng từ tenant A sang tenant B.
- Connection được trả về pool không giữ tenant setting cho request tiếp theo.

RLS là tính năng đặc thù database; schema per tenant và database per tenant cần chiến lược bảo vệ khác.

## 8. Routing schema hoặc database theo tenant

Với schema-per-tenant hoặc database-per-tenant, ứng dụng cần chọn đúng ConnectionFactory/database trước khi thực thi repository query.

Spring Framework R2DBC có cơ chế routing ConnectionFactory như AbstractRoutingConnectionFactory ở các phiên bản hỗ trợ. Cơ chế routing xác định lookup key rồi chọn target ConnectionFactory. Với ứng dụng reactive, lookup key cần được lấy từ Reactor Context thay vì ThreadLocal.

### 8.1. Tenant registry

Server cần một registry ánh xạ tenant đã xác thực sang cấu hình lưu trữ:

~~~java
public record TenantDatabaseConfig(
        Long tenantId,
        String connectionFactoryKey,
        String schemaName
) {
}
~~~

Registry có thể lưu metadata tenant, database key, schema và trạng thái provisioning. Không lưu password hoặc secret dạng plain text trong object được log; credential nên đến từ secret manager hoặc cơ chế quản lý cấu hình an toàn.

### 8.2. Routing key từ Reactor Context

Một routing ConnectionFactory có thể lấy tenant key từ reactive context:

~~~java
public class TenantRoutingConnectionFactory
        extends AbstractRoutingConnectionFactory {

    @Override
    protected Mono<Object> determineCurrentLookupKey() {
        return Mono.deferContextual(context -> {
            if (!context.hasKey(TenantContext.TENANT_ID)) {
                return Mono.error(new IllegalStateException(
                        "Tenant routing key is missing"));
            }
            Long tenantId = context.get(TenantContext.TENANT_ID);
            return Mono.just(tenantId);
        });
    }
}
~~~

Đây là ví dụ khái niệm. Cần cấu hình target ConnectionFactory map, default target policy và API theo phiên bản Spring Framework/Spring Data đang sử dụng. Với tenant không có mapping, nên fail closed thay vì route về database mặc định chứa dữ liệu tenant khác.

### 8.3. Transaction phải dùng cùng routing context

Khi reactive transaction bắt đầu, connection được lấy và gắn vào transaction context. Tenant phải được xác định trước khi transaction lấy connection. Không đổi tenant giữa chừng trong cùng transaction.

Luồng đúng:

~~~text
Authenticate and authorize tenant
    |
    v
Write tenant ID into Reactor Context
    |
    v
Start reactive transaction
    |
    v
Routing ConnectionFactory selects target
    |
    v
Execute all statements on transaction connection
    |
    v
Commit or rollback
~~~

Nếu tenant được thay đổi sau khi transaction đã lấy connection, statement sau vẫn có thể chạy trên connection của tenant ban đầu. Hãy coi tenant là bất biến trong suốt một transaction.

### 8.4. Database-per-tenant và connection pool

Mỗi database có thể có ConnectionFactory/pool riêng. Tenant registry chọn đúng factory. Cần cân nhắc:

- Pool không được tạo vô hạn cho mọi tenant.
- Tenant ít hoạt động có thể dùng pool lazy và idle eviction.
- Tổng connection của tất cả pool không vượt giới hạn database server.
- Credential rotation và connection validation.
- Pool đóng/mở an toàn khi tenant được provision hoặc deprovision.
- Metrics theo tenant/database nhưng tránh cardinality quá lớn.

Nếu có hàng chục nghìn tenant, một pool độc lập cho từng tenant có thể không khả thi. Có thể dùng nhóm database/shard, pool dùng chung theo cluster và routing schema hoặc database trên một số connection.

### 8.5. Schema-per-tenant và connection pool

Nếu chọn schema bằng session state, connection pool có thể tái sử dụng connection giữa tenant. Vì vậy, không được để schema của tenant trước còn hiệu lực khi connection được trả về pool.

Các lựa chọn:

- Dùng schema-qualified table name được tạo từ registry đã tin cậy.
- Thiết lập schema bằng transaction-local setting nếu database hỗ trợ.
- Đảm bảo reset connection state trước khi trả connection về pool.
- Dùng pool/ConnectionFactory tách biệt theo schema khi số tenant cho phép.

Không nối schema name trực tiếp từ input của client vào SQL. Schema identifier không thể được bind như một value parameter; phải lấy từ registry và kiểm tra/quote theo quy tắc database.

## 9. Nhiều database và giới hạn transaction

Một reactive transaction manager thường quản lý transaction trên một ConnectionFactory. Nếu một nghiệp vụ cần ghi vào hai database tenant khác nhau hoặc database tenant và database trung tâm, không nên giả định một @Transactional sẽ tạo distributed atomic transaction cho cả hai.

Ví dụ:

~~~text
Database tenant:
  INSERT order

Central database:
  INSERT billing record
~~~

Nếu database tenant commit thành công nhưng central database thất bại, trạng thái có thể không đồng nhất.

### 9.1. Không coi hai ConnectionFactory là một transaction

Hai repository dùng hai ConnectionFactory khác nhau thường không tự tham gia cùng một local R2DBC transaction. R2DBC không tự cung cấp distributed two-phase commit chỉ vì service có một annotation @Transactional.

Nếu cần atomicity giữa nhiều database, phải chọn một giải pháp distributed transaction được hỗ trợ thực tế bởi driver, database và transaction manager. Trong nhiều hệ thống SaaS, saga/outbox thường dễ vận hành hơn distributed transaction.

### 9.2. Saga hoặc outbox cho nghiệp vụ nhiều database

Một luồng có thể:

1. Ghi order vào database tenant và ghi outbox event cùng transaction.
2. Worker đọc outbox và gửi sự kiện billing.
3. Billing service ghi dữ liệu vào central database idempotently.
4. Billing phát kết quả hoặc event xác nhận.
5. Nếu bước sau thất bại, saga thực hiện retry hoặc compensation theo nghiệp vụ.

Outbox giúp không mất ý định phát event khi transaction tenant commit. Consumer phải idempotent vì message có thể được giao lại.

### 9.3. Tránh transaction xuyên tenant nếu không cần thiết

Một request thông thường nên hoạt động trong một tenant. Nếu nghiệp vụ quản trị cần tổng hợp hoặc thay đổi dữ liệu nhiều tenant, hãy thiết kế use case riêng, xác thực quyền quản trị, giới hạn phạm vi, audit đầy đủ và xử lý từng tenant theo batch.

## 10. Bảo vệ quan hệ, join và truy vấn tổng hợp

Shared schema cần đặc biệt chú ý query join. Chỉ lọc tenant ở bảng cha không đủ nếu quan hệ có thể tham chiếu sai tenant hoặc dữ liệu legacy không có constraint.

Ví dụ:

~~~sql
SELECT o.id, o.order_number, c.name
FROM orders o
JOIN customers c
  ON c.id = o.customer_id
 AND c.tenant_id = o.tenant_id
WHERE o.tenant_id = :tenantId;
~~~

Điều kiện join tenant_id giúp xác nhận cả hai phía thuộc cùng tenant. Composite foreign key vẫn là lớp bảo vệ mạnh hơn vì ngăn dữ liệu sai được ghi vào ngay từ đầu.

### 10.1. Aggregate và subquery

Mọi bảng nguồn trong subquery cũng phải được giới hạn tenant:

~~~sql
SELECT o.id,
       (
           SELECT COUNT(*)
           FROM order_items i
           WHERE i.order_id = o.id
             AND i.tenant_id = o.tenant_id
       ) AS item_count
FROM orders o
WHERE o.tenant_id = :tenantId;
~~~

Nếu order_items có tenant_id, điều kiện tenant trong subquery giúp tránh kết hợp dữ liệu sai. Nếu composite foreign key đảm bảo order_items.order_id tham chiếu cùng tenant, predicate vẫn có ích để thể hiện ranh giới và hỗ trợ defense in depth.

### 10.2. Cross-tenant reporting

Báo cáo toàn hệ thống có thể cần dữ liệu nhiều tenant. Đây là quyền đặc biệt, không nên thực hiện bằng cách bỏ predicate tenant trong repository dùng cho request thông thường.

Hãy tạo một reporting path riêng với:

- Role/service identity có quyền cross-tenant.
- Authorization quản trị rõ ràng.
- Audit log cho người yêu cầu và phạm vi dữ liệu.
- Giới hạn trường dữ liệu, batch size và export.
- Database view hoặc warehouse riêng nếu workload báo cáo lớn.

## 11. Cache cũng phải có tenant scope

Nếu cache key chỉ dùng order ID, hai tenant có thể va chạm khi ID chỉ unique trong tenant hoặc dữ liệu được lưu trong cùng cache namespace.

Không nên:

~~~java
@Cacheable("orders")
public Mono<OrderView> findOrder(Long orderId) {
    // ...
}
~~~

Key nên bao gồm tenant:

~~~text
orders:{tenantId}:{orderId}
~~~

Ví dụ logic:

~~~java
public Mono<OrderView> findOrder(Long orderId) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> cache.get(
                    "orders:" + tenantId + ":" + orderId,
                    () -> orderReadRepository.findByIdAndTenantId(
                            orderId, tenantId)));
}
~~~

Nếu dùng annotation caching, cần cấu hình key expression hoặc custom key generator để thêm tenant context một cách reactive-safe. Không dựa vào ThreadLocal để lấy tenant trong cache key.

Khi invalidation, event cache cũng cần tenant ID. Một event xóa cache theo order ID toàn cục có thể xóa nhầm hoặc để sót cache nếu ID chỉ duy nhất trong tenant.

## 12. File, object storage và search index

Ranh giới tenant không chỉ nằm trong database:

- File/object key nên có tenant namespace.
- Download phải kiểm tra quyền tenant trước khi tạo signed URL.
- Search document nên chứa tenant ID và query search phải lọc tenant.
- Vector index, analytics store và data lake cũng cần tenant scope.
- Export/report cần kiểm tra tenant trước khi đọc và trước khi phát file.

Không coi đường dẫn object như tenant authorization. Người dùng biết object key hoặc URL không có nghĩa họ được quyền tải file.

Ví dụ object key:

~~~text
tenant/20/orders/481/invoice.pdf
~~~

Prefix giúp tổ chức dữ liệu, nhưng quyền đọc vẫn phải được kiểm tra ở server hoặc storage policy phù hợp.

## 13. Migration và provisioning tenant

Multi-tenant cần quy trình tạo mới, nâng cấp và ngừng tenant.

### 13.1. Shared schema

Migration thường chạy một lần trên schema chung. Cần đảm bảo:

- Cột tenant_id được thêm và backfill dữ liệu hiện có.
- Các index và unique constraint có tenant scope đúng.
- Foreign key composite được tạo sau khi dữ liệu cũ đã hợp lệ.
- Query cũ không còn truy cập bảng tenant-scoped mà thiếu predicate.
- RLS policy được bật và kiểm tra bằng runtime role.

Với bảng lớn, thêm NOT NULL hoặc index có thể cần chiến lược migration online theo database.

### 13.2. Schema/database per tenant

Mỗi tenant cần schema/database ở đúng phiên bản:

~~~text
Tenant registry
   |
   +--> tenant A: schema version 42
   +--> tenant B: schema version 42
   +--> tenant C: schema version 41 (pending migration)
~~~

Migration runner nên theo dõi trạng thái từng tenant, retry an toàn và có khả năng tiếp tục sau khi job bị dừng. Không đánh dấu tenant đã nâng cấp nếu migration chỉ chạy được một phần.

### 13.3. Provisioning và deprovisioning

Khi tạo tenant:

1. Tạo tenant record trong registry.
2. Tạo schema/database hoặc phân bổ shared-schema tenant ID.
3. Cấp credential/role theo chính sách.
4. Chạy migration và seed dữ liệu ban đầu.
5. Kiểm tra health/version.
6. Chỉ sau đó đánh dấu tenant ACTIVE.

Khi ngừng tenant, cần quy trình khóa truy cập, export/retention, backup, xóa hoặc ẩn dữ liệu theo chính sách. Không xóa database/schema ngay khi chỉ nhận một yêu cầu hủy chưa được xác minh.

## 14. Bảo mật connection và cấu hình database

Với database-per-tenant:

- Credential của tenant nên được quản lý trong secret store.
- Không log connection URL có password.
- Dùng TLS khi kết nối qua mạng không tin cậy.
- Cấp role tối thiểu cần thiết cho ứng dụng.
- Không dùng migration owner/superuser cho runtime query.
- Rotate credential và đóng pool cũ theo quy trình.
- Giới hạn connection tổng trên toàn bộ tenant.

Với shared database:

- Không cho runtime role quyền truy cập schema quản trị không cần thiết.
- RLS policy phải được bật trên mọi bảng nhạy cảm cần bảo vệ.
- Kiểm tra role không có BYPASSRLS ngoài ý muốn.
- Không để một endpoint debug/export bỏ qua tenant scope.

## 15. Những lỗi thường gặp trong thiết kế multi-tenant

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| User tenant A đọc được order tenant B | Query chỉ lọc theo ID | Thêm tenant predicate và kiểm thử cross-tenant |
| UPDATE thay đổi nhiều tenant | Thiếu tenant_id trong WHERE | Bắt buộc tenant predicate cho mọi DML |
| Order tham chiếu customer tenant khác | Foreign key chỉ kiểm tra customer_id | Composite foreign key gồm tenant_id |
| Email tenant này bị tenant khác chiếm | Unique constraint toàn cục không đúng nghiệp vụ hoặc thiếu tenant scope | Chọn unique index theo tenant |
| Request chạy trên schema sai | Tenant context không được truyền hoặc connection state bị rò | Routing từ Reactor Context và reset state |
| Tenant A ảnh hưởng tenant B qua cache | Cache key không có tenant ID | Thêm tenant vào key và invalidation |
| Message consumer ghi nhầm tenant | Message thiếu tenant context hoặc tin payload không xác thực | Xác thực producer và dựng tenant context |
| RLS không bảo vệ như mong đợi | Runtime role bypass RLS hoặc context chưa set | Kiểm tra role, FORCE RLS và transaction setting |
| Tenant lớn làm chậm toàn hệ thống | Shared resources không có quota/isolation | Rate limit, workload controls hoặc tách tenant |
| Pool tăng không giới hạn | Mỗi tenant tạo một pool lâu dài | Pool lifecycle, idle eviction và giới hạn tổng |
| Transaction dùng sai database | Tenant routing diễn ra sau khi connection đã được bind | Resolve tenant trước transaction |
| Migration tenant không đồng đều | Không theo dõi version từng schema/database | Tenant migration registry và retryable migration |
| Cross-tenant report lộ dữ liệu | Dùng repository thông thường bỏ filter | Reporting path riêng và audit quyền quản trị |

## 16. Kiểm thử ranh giới tenant

Test multi-tenant cần chứng minh dữ liệu không thể vượt ranh giới, kể cả khi caller cố thay ID hoặc gửi query trực tiếp qua service.

### 16.1. Test SELECT chéo tenant

Chuẩn bị:

- Customer 101 thuộc tenant 10.
- Customer 202 thuộc tenant 20.

Với context tenant 10:

- Tìm customer 101 thành công.
- Tìm customer 202 trả rỗng hoặc lỗi không tìm thấy theo hợp đồng API.

Không nên trả thông tin cho biết hàng có tồn tại ở tenant khác nếu điều đó có thể làm lộ dữ liệu.

### 16.2. Test INSERT

Gọi API tạo order trong tenant 10 nhưng gửi tenantId = 20 trong request body. Xác nhận:

- Server bỏ qua hoặc từ chối field tenantId do client cung cấp.
- Hàng mới có tenant_id = 10 lấy từ context đã xác thực.
- Không có dữ liệu được ghi vào tenant 20.

### 16.3. Test UPDATE và DELETE

Trong context tenant 10, thử update/delete order của tenant 20 bằng ID hợp lệ. Xác nhận số hàng bị tác động bằng 0 hoặc API trả kết quả không tìm thấy/không được phép theo chính sách.

Kiểm tra cả:

- Repository query method.
- @Query và @Modifying.
- R2dbcEntityTemplate.
- DatabaseClient.
- Bulk job.

### 16.4. Test liên kết chéo tenant

Thử tạo order tenant 10 với customer ID thuộc tenant 20. Composite foreign key phải từ chối thao tác ngay cả khi service có bug.

### 16.5. Test reactive context isolation

Chạy hai request đồng thời:

- Request A mang tenant 10.
- Request B mang tenant 20.

Dùng scheduler và publisher bất đồng bộ để xác nhận tenant context không bị trộn giữa hai subscription. Không chỉ test tuần tự trên một thread.

### 16.6. Test routing và connection pool

Với schema/database routing:

- Tenant A được route tới target A.
- Tenant B được route tới target B.
- Tenant không tồn tại bị từ chối, không rơi về default tenant.
- Connection trả về pool không giữ schema/tenant setting cũ.
- Tenant context được resolve trước khi transaction lấy connection.
- Transaction không đổi tenant giữa các statement.

### 16.7. Test RLS

Chạy test bằng runtime role tương tự production, không dùng owner/superuser. Xác nhận query thiếu tenant predicate vẫn không thể đọc dữ liệu tenant khác nếu RLS được kỳ vọng là lớp bảo vệ.

## 17. Ví dụ service tenant-aware

Ví dụ shared schema với tenant_id trong entity:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("tenant_id")
    private Long tenantId;

    @Column("customer_id")
    private Long customerId;

    private String status;
    private BigDecimal totalAmount;

    public static Order newOrder(
            Long tenantId,
            Long customerId,
            BigDecimal totalAmount) {
        Order order = new Order();
        order.tenantId = tenantId;
        order.customerId = customerId;
        order.totalAmount = totalAmount;
        order.status = "NEW";
        return order;
    }
}
~~~

Repository:

~~~java
public interface TenantOrderRepository
        extends ReactiveCrudRepository<Order, Long> {

    Mono<Order> findByIdAndTenantId(Long id, Long tenantId);

    Flux<Order> findAllByTenantIdOrderByIdDesc(Long tenantId);
}
~~~

Service:

~~~java
@Service
public class OrderService {

    private final TenantOrderRepository repository;
    private final TenantContextService tenantContext;

    public OrderService(
            TenantOrderRepository repository,
            TenantContextService tenantContext) {
        this.repository = repository;
        this.tenantContext = tenantContext;
    }

    public Mono<Order> create(CreateOrderCommand command) {
        return tenantContext.currentTenantId()
                .flatMap(tenantId -> repository.save(
                        Order.newOrder(
                                tenantId,
                                command.customerId(),
                                command.totalAmount())));
    }

    public Mono<Order> find(Long orderId) {
        return tenantContext.currentTenantId()
                .flatMap(tenantId -> repository
                        .findByIdAndTenantId(orderId, tenantId));
    }
}
~~~

Ví dụ này minh họa tenant scoping ở service và repository. Trong ứng dụng thực tế, cần bảo đảm customerId cũng thuộc tenant hiện tại, tốt nhất bằng composite foreign key và/hoặc query kiểm tra cùng tenant trước khi tạo order.

## 18. Quy trình thiết kế multi-tenant

1. Xác định tenant là tổ chức, workspace hay phạm vi nghiệp vụ nào.
2. Xác định user có thể thuộc một hay nhiều tenant và cách kiểm tra membership.
3. Chọn shared schema, schema per tenant hoặc database per tenant theo yêu cầu cô lập và vận hành.
4. Tạo tenant context từ principal đã xác thực và truyền bằng Reactor Context.
5. Với shared schema, bắt buộc tenant predicate trong SELECT, INSERT, UPDATE, DELETE và join.
6. Thiết kế composite unique key/foreign key để ngăn liên kết chéo tenant.
7. Cân nhắc RLS như lớp bảo vệ bổ sung nếu database hỗ trợ.
8. Với schema/database routing, resolve tenant trước khi transaction lấy connection và fail closed khi không có mapping.
9. Đưa tenant ID vào cache key, message, object storage và search query.
10. Thiết kế migration, provisioning, credential, pool và deprovisioning cho vòng đời tenant.
11. Tạo reporting/admin path riêng cho thao tác cross-tenant.
12. Viết integration test đồng thời cho hai tenant và kiểm tra mọi đường ghi/đọc.

## 20. Kết luận

Thiết kế multi-tenant an toàn đòi hỏi ranh giới dữ liệu được giữ từ authentication tới database, cache và message. Shared schema cần tenant_id trong mọi thao tác đọc/ghi, composite constraint để ngăn liên kết chéo tenant và có thể bổ sung RLS. Schema per tenant hoặc database per tenant cần routing dựa trên tenant context reactive, quản lý connection pool và migration theo vòng đời tenant.

Trong Spring Data R2DBC, không dựa vào ThreadLocal để truyền tenant. Hãy lấy tenant từ principal đã xác thực, kiểm tra membership, đưa vào Reactor Context và resolve trước khi transaction lấy connection. Với direct SQL, repository custom và bulk update, luôn kiểm tra tenant scope; với database routing, không cho tenant không xác định rơi về database mặc định. Cache, event, object storage và báo cáo cũng phải có tenant boundary riêng.

Cuối cùng, hãy dùng database constraint và integration test làm lớp bảo vệ độc lập với code ứng dụng. Một thiết kế tốt phải chứng minh rằng request của tenant A không thể đọc, sửa, xóa hoặc liên kết dữ liệu tenant B, kể cả khi có query thiếu điều kiện hoặc hai tenant hoạt động đồng thời.
