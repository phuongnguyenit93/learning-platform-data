# Thứ tự ghi, xóa và trách nhiệm duy trì ràng buộc tham chiếu

Trong cơ sở dữ liệu quan hệ, các hàng có thể tham chiếu nhau qua khóa ngoại (foreign key). Vì vậy, thứ tự insert, update và delete phải tôn trọng quan hệ giữa hàng được tham chiếu và hàng tham chiếu. Spring Data R2DBC giúp ánh xạ aggregate và thực thi các thao tác dữ liệu, nhưng **database mới là nơi thực thi ràng buộc tham chiếu**. Ứng dụng cần thiết kế aggregate, transaction và chính sách xóa phù hợp để các thao tác nhiều bước luôn giữ dữ liệu nhất quán.

Khi làm việc với Spring Data Relational, cần phân biệt hai phạm vi:

- **Các phần tử thuộc cùng aggregate**: được quản lý thông qua aggregate root và mapping của Spring Data Relational.
- **Các aggregate độc lập tham chiếu nhau**: vòng đời của chúng do nghiệp vụ và service phối hợp; Spring Data không tự động cascade toàn bộ object graph giữa các aggregate.

## 1. Khóa ngoại và thứ tự thao tác trong cơ sở dữ liệu

Giả sử có hai bảng: purchase_order và order_line. Mỗi dòng hàng thuộc về một đơn hàng, được liên kết bằng cột order_id.

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE order_line (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT pk_order_line PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_order(id)
        ON DELETE RESTRICT
);
~~~

Trong cấu trúc này:

- purchase_order là bảng cha (parent).
- order_line là bảng con (child).
- order_line.order_id là khóa ngoại tham chiếu purchase_order.id.
- Một hàng order_line chỉ hợp lệ khi hàng purchase_order tương ứng đã tồn tại.

Ràng buộc khóa ngoại được database kiểm tra khi thực thi lệnh. Nếu insert hàng con với order_id không tồn tại, database từ chối. Nếu xóa hàng cha trong khi vẫn còn hàng con và chính sách là RESTRICT/NO ACTION, database cũng từ chối.

### 1.1. Quy tắc thứ tự cơ bản

Với khóa ngoại tham chiếu từ bảng con sang bảng cha, thứ tự an toàn thường là:

**Ghi dữ liệu**

1. Insert hàng cha để tạo khóa chính.
2. Lấy khóa chính của hàng cha.
3. Insert các hàng con sử dụng khóa ngoại đó.

**Xóa dữ liệu**

1. Xóa các hàng con đang tham chiếu.
2. Xóa hàng cha sau khi không còn tham chiếu bị cấm.

Nếu database hỗ trợ và được cấu hình ON DELETE CASCADE, lệnh xóa hàng cha có thể khiến database tự xóa các hàng con. Khi đó ứng dụng không cần tự phát lệnh delete cho từng hàng con trong trường hợp đó. Chính sách cascade phải được lựa chọn có chủ đích.

### 1.2. Ràng buộc không chỉ áp dụng khi insert/delete

Khóa ngoại cũng ảnh hưởng khi cập nhật khóa được tham chiếu hoặc cập nhật giá trị FK:

- Đổi order_line.order_id sang một ID không tồn tại sẽ bị từ chối.
- Đổi purchase_order.id có thể bị chặn nếu còn hàng con tham chiếu, trừ khi database có hành vi ON UPDATE phù hợp.
- Đặt FK thành NULL chỉ hợp lệ nếu cột cho phép NULL và quan hệ nghiệp vụ cho phép một hàng con không có cha.

Trong thiết kế thông thường, khóa chính của aggregate root nên ổn định sau khi tạo. Hạn chế đổi ID giúp tránh phải cập nhật hàng loạt tham chiếu.

## 2. Aggregate và aggregate root trong Spring Data Relational

Spring Data Relational tổ chức dữ liệu theo mô hình aggregate. Aggregate root là điểm truy cập chính cho một nhóm đối tượng được lưu như một đơn vị nghiệp vụ.

Ví dụ một PurchaseOrder có các OrderLine. Dòng hàng chỉ có ý nghĩa trong phạm vi đơn hàng; ứng dụng thêm, sửa hoặc xóa dòng hàng thông qua aggregate PurchaseOrder.

~~~mermaid
flowchart TB
    A["PurchaseOrder<br/>Aggregate root"]
    B["OrderLine 1"]
    C["OrderLine 2"]
    D["OrderLine 3"]
    A --> B
    A --> C
    A --> D
~~~

Khi ánh xạ theo aggregate, Spring Data Relational biết các đối tượng con thuộc về root nào và cách ghi chúng vào bảng liên quan. Ứng dụng thao tác qua root để lưu trạng thái aggregate.

### 2.1. Ánh xạ collection bằng @MappedCollection

Ví dụ:

~~~java
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @MappedCollection(
        idColumn = "order_id",
        keyColumn = "line_no"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderNumber, List<OrderLine> lines) {
        this.orderNumber = orderNumber;
        this.lines = new ArrayList<>(lines);
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }
}
~~~

Kiểu phần tử:

~~~java
import org.springframework.data.relational.core.mapping.Table;

@Table("order_line")
public record OrderLine(
    String sku,
    Integer quantity
) {}
~~~

Trong ví dụ:

- @MappedCollection chỉ định order_id là cột liên kết các dòng hàng với ID của aggregate root.
- keyColumn = "line_no" lưu vị trí/key của phần tử collection trong trường hợp mapping cần khóa collection.
- Spring Data dùng metadata này để ánh xạ các dòng hàng thuộc PurchaseOrder.

**@MappedCollection mô tả mapping; nó không thay thế foreign key constraint trong database.** Ràng buộc thực tế vẫn cần được tạo trong schema, thường thông qua migration.

### 2.2. Aggregate root chịu trách nhiệm cho vòng đời phần tử con

Nếu OrderLine là thành phần của PurchaseOrder, các thay đổi về dòng hàng nên đi qua nghiệp vụ của đơn hàng:

- Thêm dòng hàng vào đơn hàng.
- Đổi số lượng của dòng hàng.
- Bỏ dòng hàng khỏi đơn hàng.
- Lưu lại aggregate root.

Không nên coi mỗi OrderLine là một aggregate độc lập chỉ vì nó nằm ở bảng riêng. Một bảng riêng không tự động tạo ra ranh giới aggregate.

Ngược lại, nếu một đối tượng có vòng đời và quy tắc nghiệp vụ độc lập, hãy xem nó là aggregate riêng. Khi đó, nên tham chiếu bằng ID và phối hợp thao tác qua service thay vì mong Spring Data tự cascade giữa các object.

## 3. Thứ tự insert trong một aggregate

Khi tạo một aggregate mới, khóa chính của root có thể được database sinh tự động. Các hàng con cần giá trị khóa đó trong cột FK.

Luồng khái niệm:

~~~mermaid
sequenceDiagram
    participant App as Service
    participant SD as Spring Data R2DBC
    participant DB as Database

    App->>SD: save(PurchaseOrder mới)
    SD->>DB: INSERT purchase_order
    DB-->>SD: ID được sinh
    SD->>DB: INSERT order_line với order_id
    DB-->>SD: Kết quả insert dòng hàng
    SD-->>App: Entity aggregate đã lưu
~~~

Điểm quan trọng là hàng cha phải tồn tại trước khi các hàng con tham chiếu tới nó, trừ khi database và schema sử dụng một cơ chế constraint trì hoãn phù hợp. Với khóa chính tự sinh, framework cần nhận được ID root để ghi các phần tử phụ thuộc.

Khi dùng Repository:

~~~java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface PurchaseOrderRepository
        extends ReactiveCrudRepository<PurchaseOrder, Long> {
}
~~~

Service lưu aggregate:

~~~java
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    public Mono<PurchaseOrder> create(PurchaseOrder order) {
        return repository.save(order);
    }
}
~~~

Khi entity dùng ID được database sinh, hãy sử dụng aggregate được phát ra từ publisher save. Với entity immutable, instance kết quả có thể chứa ID mới; instance đầu vào vẫn giữ trạng thái ban đầu.

### 3.1. Insert bằng R2dbcEntityTemplate

Template cũng có thể lưu entity ở mức aggregate:

~~~java
Mono<PurchaseOrder> saved =
    template.insert(PurchaseOrder.class)
        .using(order);
~~~

Khi entity được ánh xạ như aggregate có các phần tử con, Spring Data Relational phối hợp việc ghi các phần tử đó theo mapping. Không nên tự insert lại các dòng con bằng SQL riêng nếu thao tác insert aggregate đã chịu trách nhiệm ghi chúng; điều đó có thể tạo bản ghi trùng.

### 3.2. Thứ tự khi có nhiều cấp phụ thuộc

Một aggregate có thể có nhiều cấp đối tượng con. Quy tắc chung vẫn là ghi đối tượng được tham chiếu trước đối tượng tham chiếu đến nó.

Ví dụ:

~~~text
purchase_order
    └── order_line
            └── line_note
~~~

Nếu line_note có FK tới order_line, cần có hàng order_line trước khi insert line_note. Tương tự, order_line phải có order_id hợp lệ.

Spring Data Relational sử dụng metadata aggregate để điều phối các thao tác thuộc mapping. Nếu có quan hệ bảng bổ sung nằm ngoài aggregate hoặc được thao tác qua repository khác, service phải bảo đảm thứ tự phù hợp.

## 4. Thứ tự khi lưu hoặc cập nhật aggregate đã tồn tại

Spring Data Relational không hoạt động như một ORM có persistence context và dirty checking cho toàn bộ object graph. Việc gọi save truyền trạng thái aggregate cần lưu; framework tạo các thao tác ghi dựa trên mapping và trạng thái entity.

Đối với các collection mapped thuộc aggregate, chiến lược lưu có thể thay thế các hàng con hiện có bằng tập hàng con hiện tại: xóa các hàng con cũ rồi insert lại các hàng con trong aggregate được gửi lên. Đây là điểm cần lưu ý khi thiết kế bảng con và các tham chiếu bên ngoài.

Điều này có nghĩa:

- Không nên giả định mỗi OrderLine được dirty-check và update từng cột như JPA.
- Việc lưu root có thể phát sinh nhiều câu SQL cho bảng con.
- Nếu bảng con có định danh riêng được các bảng ngoài tham chiếu, việc thay thế hàng con có thể ảnh hưởng các tham chiếu đó.
- Hãy giữ phần tử phụ thuộc đúng ranh giới aggregate và kiểm tra SQL thực tế khi cần hiểu chi tiết hành vi theo phiên bản.

Thứ tự câu SQL chính xác có thể phụ thuộc loại thao tác, mapping, chiến lược truy cập dữ liệu và phiên bản Spring Data. Tuy nhiên, các ràng buộc quan hệ vẫn yêu cầu hàng được tham chiếu phải tồn tại trước khi ghi FK và các hàng con phải được xử lý trước khi xóa cha nếu không có cascade.

### 4.1. Cập nhật root và collection

Ví dụ một đơn hàng đã có ID và được thay đổi số lượng dòng hàng:

~~~java
PurchaseOrder changed = /* aggregate mới với cùng ID và danh sách dòng hàng mới */;

return repository.save(changed);
~~~

Spring Data nhận aggregate root và phối hợp lưu các phần tử thuộc aggregate. Nếu cần update một bảng độc lập khác như inventory, đó là một thao tác nghiệp vụ riêng; không nên nhét nó vào collection chỉ để mong save tự động cập nhật bảng đó.

### 4.2. Tránh cập nhật một phần aggregate bằng một object thiếu dữ liệu

Nếu tải một phần dữ liệu rồi dựng aggregate root mới chỉ chứa vài dòng hàng, save có thể được hiểu là trạng thái aggregate cần lưu. Các phần tử không có trong object có thể bị xóa khỏi tập collection được quản lý.

Vì vậy:

- Khi cần sửa aggregate, tải đầy đủ phần cần quản lý theo mô hình persistence.
- Thực hiện thay đổi thông qua hành vi của aggregate.
- Lưu lại aggregate root.
- Nếu chỉ muốn cập nhật một cột hoặc một tập hàng mà không thay toàn bộ aggregate, dùng thao tác update tường minh bằng Query/Criteria hoặc SQL phù hợp.

Không dùng DTO projection một phần làm aggregate đầu vào cho save.

## 5. Thứ tự delete và chính sách ON DELETE

Khi xóa một aggregate, database phải không còn hàng con tham chiếu đến root nếu constraint không cho phép orphan.

Có hai cách phổ biến.

### 5.1. Ứng dụng hoặc Spring Data xóa hàng con trước

Với FK RESTRICT/NO ACTION, các hàng con phải được xóa trước hàng cha.

~~~mermaid
sequenceDiagram
    participant App as Service
    participant SD as Spring Data R2DBC
    participant DB as Database

    App->>SD: delete(PurchaseOrder)
    SD->>DB: DELETE order_line WHERE order_id = ?
    DB-->>SD: Thành công
    SD->>DB: DELETE purchase_order WHERE id = ?
    DB-->>SD: Thành công
    SD-->>App: Hoàn tất
~~~

Khi các dòng hàng được mapping là thành phần của aggregate, thao tác delete root qua Spring Data Relational có thể phối hợp xóa các phần tử phụ thuộc trước khi xóa root. Ứng dụng không cần tự xóa từng dòng nếu framework đã quản lý chúng theo aggregate mapping.

### 5.2. Database xóa hàng con bằng ON DELETE CASCADE

Schema có thể khai báo:

~~~sql
FOREIGN KEY (order_id)
    REFERENCES purchase_order(id)
    ON DELETE CASCADE
~~~

Khi xóa purchase_order, database tự xóa các hàng order_line liên quan. Đây là chính sách ở tầng database, không phải một annotation cascade của Spring Data.

ON DELETE CASCADE phù hợp khi vòng đời hàng con thực sự phụ thuộc hàng cha và việc xóa cha luôn có nghĩa xóa con. Nếu dữ liệu con cần được giữ lại hoặc phải qua nghiệp vụ riêng, dùng RESTRICT/NO ACTION và thực hiện quy trình xóa tường minh.

### 5.3. Chọn RESTRICT, CASCADE hay SET NULL

| Chính sách | Hành vi khi xóa hàng cha | Dùng khi |
|---|---|---|
| RESTRICT / NO ACTION | Từ chối nếu còn hàng con tham chiếu | Không cho xóa cha khi còn dữ liệu phụ thuộc |
| CASCADE | Database xóa các hàng con liên quan | Hàng con không có vòng đời độc lập |
| SET NULL | Đặt FK của hàng con thành NULL | Hàng con được phép tồn tại mà không có cha |
| SET DEFAULT | Đặt FK về giá trị mặc định | Có giá trị mặc định hợp lệ và được thiết kế rõ |

Không chọn CASCADE chỉ vì nó giúp lệnh delete chạy dễ dàng. Xóa dây chuyền có thể xóa lượng dữ liệu lớn hơn caller dự đoán. Với dữ liệu tài chính, kiểm toán hoặc lịch sử, có thể cần trạng thái archive/soft delete thay vì xóa vật lý.

SET NULL chỉ hợp lệ khi cột FK nullable và nghiệp vụ cho phép mất liên kết. SET DEFAULT cần giá trị mặc định tham chiếu tới hàng cha hợp lệ nếu constraint vẫn được kiểm tra.

### 5.4. Xóa root bằng repository

Với aggregate đã mapping:

~~~java
Mono<Void> deleteOrder(Long orderId) {
    return repository.deleteById(orderId);
}
~~~

Nếu các dòng hàng là phần tử phụ thuộc thuộc aggregate, Spring Data Relational quản lý việc xóa các hàng phụ thuộc theo mapping. Nếu có các bảng tham chiếu khác nằm ngoài aggregate, thao tác delete root có thể bị FK constraint chặn; service cần phối hợp xử lý các bảng đó hoặc dựa trên chính sách cascade được thiết kế trong schema.

## 6. Aggregate độc lập tham chiếu nhau

Không phải mọi quan hệ FK đều là quan hệ cha-con trong cùng aggregate.

Ví dụ một PurchaseOrder tham chiếu Customer. Customer có vòng đời độc lập: có thể được dùng bởi nhiều đơn hàng, được cập nhật riêng và không bị xóa chỉ vì một đơn hàng bị xóa.

Trong trường hợp này, mô hình đơn hàng nên giữ customerId thay vì chứa toàn bộ Customer như một đối tượng con cần cascade:

~~~java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String orderNumber,
    Long customerId
) {}
~~~

Schema:

~~~sql
ALTER TABLE purchase_order
ADD CONSTRAINT fk_purchase_order_customer
FOREIGN KEY (customer_id)
REFERENCES customer(id)
ON DELETE RESTRICT;
~~~

Khi tạo đơn hàng:

1. Customer phải tồn tại.
2. Ứng dụng gán customerId vào PurchaseOrder.
3. Lưu PurchaseOrder.
4. Database kiểm tra FK.

Khi xóa Customer:

- Nếu còn đơn hàng tham chiếu, RESTRICT/NO ACTION chặn thao tác.
- Nếu chính sách là CASCADE, database có thể xóa các đơn hàng, điều này thường không phù hợp nếu đơn hàng cần được giữ lại.
- Nếu chính sách SET NULL, purchase_order.customer_id phải nullable và nghiệp vụ phải cho phép đơn hàng không còn liên kết khách hàng.

Spring Data không tự động tải hoặc cascade Customer khi lưu PurchaseOrder chỉ vì entity có customerId. Service quyết định cách phối hợp các aggregate.

### 6.1. Tham chiếu bằng ID tạo ranh giới rõ ràng

Dùng ID cho tham chiếu giữa aggregate giúp:

- Tránh một object graph lớn được lưu ngoài ý muốn.
- Tránh vòng tham chiếu hai chiều.
- Tách transaction và vòng đời của các aggregate.
- Làm rõ service nào chịu trách nhiệm kiểm tra sự tồn tại của đối tượng được tham chiếu.
- Giảm nguy cơ lưu một object cũ ghi đè dữ liệu của aggregate khác.

Nếu cần hiển thị thông tin Customer cùng PurchaseOrder, service có thể truy vấn hai aggregate và kết hợp kết quả trong luồng reactive. Đó là thao tác đọc; không đồng nghĩa hai aggregate thuộc cùng một đơn vị persistence.

## 7. Bảng liên kết và quan hệ nhiều-nhiều

Quan hệ nhiều-nhiều thường được biểu diễn bằng bảng liên kết:

~~~sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY
);

CREATE TABLE tag (
    id BIGINT PRIMARY KEY
);

CREATE TABLE product_tag (
    product_id BIGINT NOT NULL,
    tag_id BIGINT NOT NULL,
    PRIMARY KEY (product_id, tag_id),
    FOREIGN KEY (product_id) REFERENCES product(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id) REFERENCES tag(id) ON DELETE RESTRICT
);
~~~

Bảng product_tag có FK tới cả product và tag. Khi insert liên kết, cả hai hàng được tham chiếu phải tồn tại trước. Khi xóa product, có thể cascade xóa các hàng liên kết product_tag. Khi xóa tag, RESTRICT sẽ ngăn xóa nếu còn product_tag tham chiếu.

Nếu bảng liên kết chứa thuộc tính nghiệp vụ như assignedAt, role hoặc quantity, hãy mô hình hóa nó thành một association entity rõ ràng. Khi đó, cần xác định association entity thuộc aggregate nào hoặc có vòng đời độc lập hay không.

Không giả định Spring Data R2DBC tự quản lý mọi quan hệ many-to-many như ORM. Thiết kế mapping và service cần thể hiện rõ các thao tác trên bảng liên kết.

## 8. Trách nhiệm được chia ở những tầng nào?

Việc duy trì ràng buộc tham chiếu là trách nhiệm phối hợp, nhưng mỗi tầng có một vai trò riêng.

| Tầng | Trách nhiệm |
|---|---|
| Database schema | Định nghĩa PK, FK, NOT NULL, UNIQUE và hành vi ON DELETE/ON UPDATE |
| Spring Data Relational mapping | Mô tả bảng, cột, aggregate root và phần tử phụ thuộc |
| Spring Data R2DBC / Spring R2DBC | Thực thi các câu lệnh ghi/xóa qua ConnectionFactory và driver |
| Domain model | Quy định phần tử nào thuộc aggregate, điều kiện thêm/xóa và quy tắc nghiệp vụ |
| Application service | Điều phối nhiều aggregate, thứ tự thao tác và transaction |
| Migration/schema management | Tạo, thay đổi và triển khai constraint nhất quán giữa các môi trường |

### 8.1. Database là hàng rào toàn vẹn cuối cùng

Không chỉ dựa vào kiểm tra ở Java như “đã tìm thấy Customer trước khi insert Order”. Dữ liệu có thể thay đổi giữa lúc kiểm tra và lúc insert, hoặc một ứng dụng khác có thể ghi cùng database.

Foreign key constraint đảm bảo database không nhận một tham chiếu mồ côi ngay cả khi có nhiều client cùng thao tác.

### 8.2. Mapping không tự tạo constraint

@MappedCollection cho Spring Data biết cách liên kết các phần tử thuộc aggregate. @Table, @Column và @Id mô tả mapping entity. Những annotation này không có nghĩa database đã có FOREIGN KEY constraint.

Constraint phải tồn tại trong schema. Nên quản lý DDL bằng migration có version như Flyway hoặc Liquibase, hoặc cơ chế schema management mà dự án lựa chọn. Kiểm tra schema ở local, test, staging và production phải nhất quán.

### 8.3. Service quyết định nghiệp vụ giữa các aggregate

Nếu một thao tác cần:

- Tạo đơn hàng.
- Giảm tồn kho.
- Ghi lịch sử thanh toán.
- Tạo bản ghi audit.

thì đây là nhiều thao tác nghiệp vụ có thể liên quan nhiều aggregate hoặc bảng độc lập. Service phải xác định thứ tự, transaction boundary và cách xử lý lỗi. Không nên kỳ vọng save một aggregate root tự động thực hiện các bước đó.

## 9. Transaction khi ghi hoặc xóa nhiều hàng

Một thao tác aggregate có thể phát sinh nhiều câu SQL. Nếu một câu thành công nhưng câu tiếp theo thất bại, dữ liệu có nguy cơ ở trạng thái không đầy đủ nếu các thao tác không cùng transaction.

Ví dụ tạo đơn hàng gồm root và các dòng hàng:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import reactor.core.publisher.Mono;

@Service
public class OrderApplicationService {

    private final PurchaseOrderRepository orderRepository;

    public OrderApplicationService(
            PurchaseOrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public Mono<PurchaseOrder> place(PurchaseOrder order) {
        return orderRepository.save(order);
    }
}
~~~

Với reactive transaction, phương thức trả về Mono hoặc Flux và transaction được gắn với reactive context. Cần có R2dbcTransactionManager phù hợp với ConnectionFactory mà repository sử dụng.

### 9.1. Nhiều thao tác cần cùng transaction

Ví dụ một quy trình đặt hàng cần lưu đơn và cập nhật tồn kho:

~~~java
@Transactional
public Mono<PurchaseOrder> placeOrder(
        PurchaseOrder order,
        Long productId,
        int quantity) {

    return orderRepository.save(order)
        .flatMap(saved ->
            inventoryRepository.decrease(productId, quantity)
                .thenReturn(saved)
        );
}
~~~

Ví dụ giả định hai repository sử dụng cùng ConnectionFactory và transaction manager. Nếu cập nhật tồn kho thất bại, transaction có thể rollback phần lưu đơn hàng khi lỗi được truyền qua cùng reactive chain.

Không gọi subscribe() bên trong phương thức transactional để khởi chạy một publisher tách rời. Không gọi block() tùy tiện để lấy kết quả đồng bộ. Hai cách đó có thể làm thao tác chạy ngoài reactive transaction context hoặc khiến transaction hoàn tất trước thao tác thực tế.

### 9.2. Một transaction không tự bao trùm nhiều database

Nếu các thao tác sử dụng nhiều ConnectionFactory hoặc nhiều database, một R2dbcTransactionManager cục bộ không tự tạo transaction phân tán. Cần thiết kế quy trình phù hợp như outbox, saga hoặc cơ chế điều phối khác nếu nghiệp vụ yêu cầu tính nhất quán xuyên nhiều hệ thống.

### 9.3. Constraint có thể được kiểm tra ở thời điểm khác nhau

Nhiều database kiểm tra FK ngay trong statement. Một số hệ quản trị hỗ trợ constraint có thể defer đến cuối transaction nếu được khai báo phù hợp.

Không nên dựa vào deferred constraint để đảo thứ tự thao tác nếu ứng dụng cần chạy trên nhiều hệ quản trị. Thiết kế insert parent trước child và delete child trước parent thường dễ portable hơn.

## 10. Xử lý lỗi ràng buộc tham chiếu

Khi database từ chối một thao tác vì vi phạm FK, driver phát sinh lỗi và Spring có thể dịch thành ngoại lệ truy cập dữ liệu phù hợp.

Các tình huống thường gặp:

| Lỗi | Nguyên nhân | Hướng xử lý |
|---|---|---|
| Insert child thất bại | FK trỏ tới parent không tồn tại | Kiểm tra ID và thứ tự insert |
| Delete parent thất bại | Vẫn còn child tham chiếu với RESTRICT/NO ACTION | Xóa child theo nghiệp vụ hoặc chọn chính sách phù hợp |
| Update FK thất bại | ID cha mới không tồn tại | Kiểm tra đối tượng được tham chiếu |
| Delete cascade xóa quá nhiều | Chính sách CASCADE rộng hơn dự kiến | Rà soát schema và phạm vi aggregate |
| Transaction rollback | Một thao tác trong chuỗi ghi thất bại | Xử lý lỗi ở service và kiểm tra toàn bộ đơn vị công việc |
| Vi phạm unique khi insert lại child | Collection bị ghi trùng hoặc khóa/key mapping không đúng | Kiểm tra keyColumn, khóa chính và dữ liệu aggregate |

Không nên bắt lỗi FK rồi bỏ qua để tiếp tục như thể thao tác đã thành công. Lỗi thường biểu thị vi phạm một quy tắc toàn vẹn hoặc thứ tự thao tác; cần xử lý theo ngữ nghĩa nghiệp vụ.

Có thể chuyển lỗi persistence thành lỗi domain/API rõ nghĩa ở tầng service, ví dụ “không thể xóa khách hàng đang có đơn hàng”. Không đưa thông tin SQL nhạy cảm hoặc chi tiết nội bộ database vào phản hồi công khai.

## 11. Xóa mềm và lịch sử dữ liệu

Không phải lúc nào xóa vật lý cũng là lựa chọn phù hợp. Với dữ liệu cần kiểm toán hoặc lịch sử, ứng dụng có thể dùng soft delete:

~~~java
@Table("customer")
public record Customer(
    @Id Long id,
    String fullName,
    Boolean deleted
) {}
~~~

Khi soft delete, hàng cha vẫn tồn tại trong database nên FK của hàng con vẫn hợp lệ. Tuy nhiên, ứng dụng phải thống nhất cách loại các bản ghi đã xóa mềm khỏi truy vấn thông thường.

Soft delete không tự động thay thế FK constraint. Nó là quy tắc nghiệp vụ ở tầng ứng dụng; database vẫn thấy hàng cha tồn tại cho đến khi bị xóa vật lý.

Nếu sau này có tác vụ purge dữ liệu, tác vụ đó vẫn phải tuân thủ thứ tự FK hoặc chính sách cascade như xóa vật lý thông thường.

## 12. Vòng tham chiếu và thứ tự không thể sắp xếp

Thiết kế có thể tạo vòng tham chiếu:

~~~text
table_a.b_id → table_b.id
table_b.a_id → table_a.id
~~~

Nếu cả hai FK đều NOT NULL và được kiểm tra ngay khi insert, không thể insert hàng A trước B hoặc B trước A vì hàng còn lại chưa tồn tại.

Một số cách giải quyết:

- Thiết kế lại để chỉ một chiều tham chiếu là cần thiết.
- Cho phép một FK nullable trong bước tạo ban đầu, sau đó cập nhật liên kết trong cùng transaction.
- Dùng deferred constraint nếu database hỗ trợ và ứng dụng chấp nhận phụ thuộc database đó.
- Tách quan hệ thành một bảng liên kết được tạo sau khi hai đầu đã tồn tại.

Trong mô hình aggregate, vòng tham chiếu giữa hai aggregate độc lập thường là dấu hiệu cần xem lại ranh giới domain. Giữ tham chiếu một chiều bằng ID thường dễ quản lý hơn object graph hai chiều.

## 13. Kiểm thử ràng buộc và thứ tự ghi/xóa

Các kiểm thử cần chạy trên database có hành vi gần với production. H2 có thể hữu ích cho một số kiểm thử cơ bản nhưng không đảm bảo mọi chi tiết constraint, DDL, cascade và dialect giống PostgreSQL, MySQL hay hệ quản trị khác.

Các tình huống có thể kiểm thử:

- Insert aggregate mới tạo root và các hàng con với FK đúng.
- Insert child tham chiếu ID không tồn tại bị database từ chối.
- Save aggregate đã tồn tại giữ được các hàng con theo trạng thái mong muốn.
- Xóa aggregate có RESTRICT xử lý các hàng con theo mapping hoặc bị chặn đúng như thiết kế.
- ON DELETE CASCADE chỉ xóa các hàng được phép cascade.
- Xóa parent đang được aggregate khác tham chiếu bị từ chối.
- Lỗi ở thao tác cuối trong transaction làm rollback các thao tác trước đó.
- Cập nhật FK sang parent không tồn tại bị từ chối.
- Collection mapping với keyColumn tạo khóa và thứ tự đúng.

Kiểm thử nên xác nhận cả trạng thái database sau thao tác, không chỉ xác nhận publisher hoàn tất. Với transaction rollback, cần đọc lại dữ liệu để chứng minh không còn phần ghi dở dang.

## 14. Nguyên tắc thiết kế thực tế

- Xác định rõ aggregate root và các đối tượng thực sự thuộc aggregate.
- Dùng @MappedCollection để mô tả collection phụ thuộc; dùng migration để tạo FK constraint thật.
- Insert hàng được tham chiếu trước hàng tham chiếu đến nó.
- Xóa hàng con trước hàng cha nếu không dùng ON DELETE CASCADE.
- Chọn RESTRICT, CASCADE hoặc SET NULL theo quy tắc nghiệp vụ và khả năng giữ lịch sử.
- Không giả định Spring Data tự cascade giữa các aggregate độc lập.
- Tham chiếu aggregate khác bằng ID và điều phối qua service.
- Tránh để bảng ngoài tham chiếu tới phần tử con có thể bị thay thế khi save aggregate.
- Dùng transaction reactive cho nhiều câu SQL cần cùng thành công hoặc rollback.
- Giữ các publisher trong cùng reactive chain; không subscribe/block tùy tiện trong service.
- Giữ khóa chính ổn định; tránh thay ID của hàng cha đang được tham chiếu.
- Kiểm thử FK và thứ tự thao tác trên hệ quản trị mục tiêu.
- Theo dõi lỗi integrity constraint thay vì bỏ qua chúng.
- Dùng soft delete hoặc archive khi dữ liệu cần giữ lịch sử.

## 15. Ghi nhớ

Khóa ngoại là quy tắc của database: hàng được tham chiếu phải tồn tại và không thể bị xóa nếu còn tham chiếu bị cấm. Vì vậy, với quan hệ cha-con thông thường, insert parent trước child và delete child trước parent, trừ khi schema có chính sách cascade hoặc cơ chế constraint khác được thiết kế rõ ràng.

Spring Data Relational quản lý các phần tử được ánh xạ trong cùng aggregate thông qua aggregate root; @MappedCollection mô tả quan hệ mapping nhưng không tự tạo foreign key. Với aggregate độc lập, ứng dụng tham chiếu bằng ID và service điều phối thứ tự, transaction và chính sách xóa. Database constraint là hàng rào toàn vẹn cuối cùng, mapping giúp framework biết cách ghi dữ liệu, còn domain/service quyết định vòng đời và ý nghĩa nghiệp vụ của các thao tác.
