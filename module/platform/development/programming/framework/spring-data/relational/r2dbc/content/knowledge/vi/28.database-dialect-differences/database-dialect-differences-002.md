# PostgreSQL: định danh sinh tự động, JSON và mảng

PostgreSQL có một số kiểu dữ liệu và cơ chế SQL đặc thù thường được dùng trong ứng dụng Spring Data Relational R2DBC: identity/sequence để sinh khóa, `json`/`jsonb` để lưu dữ liệu bán cấu trúc và kiểu mảng để lưu tập giá trị cùng kiểu trong một cột. Những tính năng này giúp tận dụng khả năng của PostgreSQL, nhưng cách bind, đọc và ánh xạ kiểu Java phụ thuộc R2DBC PostgreSQL driver và phiên bản Spring Data đang sử dụng.

Khi làm việc với các kiểu này, cần phân biệt ba lớp:

- **Schema và SQL PostgreSQL:** kiểu cột, identity, sequence, toán tử JSONB, toán tử mảng và `RETURNING`.
- **R2DBC driver:** codec chuyển kiểu PostgreSQL thành kiểu Java và ngược lại, cách bind array/JSON và cách lấy giá trị được sinh.
- **Spring Data R2DBC:** mapping entity, `@Id`, converter, repository, `R2dbcEntityTemplate` và `DatabaseClient`.

Một câu SQL hợp lệ trong PostgreSQL chưa chắc tự động ánh xạ thành một property Java bất kỳ. Với JSON và mảng, hãy kiểm tra codec của driver, dùng kiểu Java tương thích hoặc khai báo converter tường minh.

## 1. Định danh sinh tự động trong PostgreSQL

Một khóa chính số thường được khai báo bằng identity column:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE
);
```

PostgreSQL tự sinh giá trị cho `id` khi INSERT không cung cấp cột này. Identity dựa trên một sequence nội bộ do PostgreSQL quản lý.

Trong entity Spring Data R2DBC:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;

    private String email;

    // Constructor, getters và setters.
}
```

Dùng `Long` thay cho primitive `long` khi cần biểu diễn entity chưa có ID. Giá trị `null` giúp Spring Data nhận diện một entity mới theo cơ chế newness thông thường. Nếu primitive `long` mặc định bằng `0`, ứng dụng có thể vô tình làm phức tạp việc nhận diện trạng thái mới/cũ.

Khi lưu entity mới:

```java
Mono<Customer> createCustomer(String name, String email) {
    Customer customer = new Customer(null, name, email);
    return customerRepository.save(customer);
}
```

Với cấu hình Spring Data R2DBC và PostgreSQL driver phù hợp, thao tác INSERT có thể lấy giá trị được database sinh và gán lại vào entity được phát ra. Hãy kiểm thử trên đúng phiên bản driver/database, đặc biệt nếu dùng custom SQL hoặc một kiểu ID khác `Long`.

### 1.1. GENERATED ALWAYS và GENERATED BY DEFAULT

PostgreSQL hỗ trợ hai chế độ identity:

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

và:

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Khác biệt chính:

| Chế độ | Khi INSERT không truyền ID | Khi INSERT truyền ID tường minh |
|---|---|---|
| `GENERATED ALWAYS` | Database sinh ID | Từ chối giá trị tường minh theo mặc định; có cú pháp override riêng |
| `GENERATED BY DEFAULT` | Database sinh ID | Cho phép giá trị được cung cấp ghi đè giá trị tự sinh |

`GENERATED ALWAYS` bảo vệ quy tắc database luôn kiểm soát ID tốt hơn. `GENERATED BY DEFAULT` hữu ích khi cần nạp dữ liệu có ID được giữ nguyên từ hệ thống cũ, nhưng phải kiểm soát quyền và cách đồng bộ sequence sau import.

Với `GENERATED ALWAYS`, PostgreSQL có cú pháp đặc biệt để nạp ID tường minh:

```sql
INSERT INTO customer(id, name, email)
OVERRIDING SYSTEM VALUE
VALUES (1000, 'An', 'an@example.com');
```

Chỉ dùng override trong migration/import được kiểm soát. Không để API thông thường cho client tự chọn khóa chính nếu nghiệp vụ không cho phép.

### 1.2. SERIAL là kiểu khai báo cũ dựa trên sequence

PostgreSQL vẫn có cú pháp:

```sql
CREATE TABLE legacy_customer (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);
```

`SERIAL`, `BIGSERIAL` và `SMALLSERIAL` là shorthand lịch sử tạo cột số, sequence và default `nextval(...)`. Chúng không phải kiểu dữ liệu độc lập trong PostgreSQL. Với schema mới, identity column thường diễn đạt ý định rõ hơn và theo chuẩn SQL hơn.

Ứng dụng Spring Data R2DBC thường chỉ cần mapping `@Id` và để database sinh ID; không cần biết tên sequence nếu không có yêu cầu đặc biệt.

## 2. Không tự tạo ID bằng MAX(id) + 1

Không dùng cách sau:

```sql
SELECT COALESCE(MAX(id), 0) + 1 FROM customer;
```

Hai transaction đồng thời có thể đọc cùng một giá trị MAX và cùng tính ra ID tiếp theo. Điều đó tạo race condition và có thể gây duplicate key. Sequence/identity được thiết kế để cấp giá trị an toàn khi có nhiều transaction đồng thời.

Không cần khóa toàn bảng để tự tăng ID. Hãy để PostgreSQL quản lý identity/sequence hoặc dùng UUID theo chiến lược đã chọn.

## 3. Lấy ID được sinh bằng RETURNING

PostgreSQL hỗ trợ `RETURNING` để trả các cột được tạo hoặc cập nhật ngay từ câu lệnh DML:

```sql
INSERT INTO customer(name, email)
VALUES (:name, :email)
RETURNING id, name, email;
```

Đây là cách đáng tin cậy để lấy ID và các giá trị do database sinh trong cùng thao tác. Không cần chạy một câu `SELECT currval(...)` riêng sau INSERT.

Ví dụ với `DatabaseClient`:

```java
Mono<Customer> insertCustomer(String name, String email) {
    return databaseClient.sql("""
            INSERT INTO customer(name, email)
            VALUES (:name, :email)
            RETURNING id, name, email
            """)
        .bind("name", name)
        .bind("email", email)
        .map((row, metadata) -> new Customer(
            row.get("id", Long.class),
            row.get("name", String.class),
            row.get("email", String.class)
        ))
        .one();
}
```

`RETURNING` là tính năng PostgreSQL, không phải SQL portable cho mọi database. Với custom INSERT cần lấy generated values, đây thường là lựa chọn rõ ràng hơn việc tự truy vấn sequence sau đó.

### 3.1. Vì sao không nên gọi currval ở connection khác?

Sequence có các hàm như `nextval`, `currval` và `setval`. `currval(sequence)` trả giá trị gần nhất được lấy bởi session hiện tại. Trong ứng dụng dùng connection pool, câu INSERT và câu `currval` có thể vô tình chạy trên hai connection khác nhau nếu không giữ đúng connection/session. Khi đó `currval` có thể chưa được gọi trên session thứ hai hoặc trả giá trị không liên quan.

Nếu cần dùng sequence tường minh, có thể lấy `nextval` trong cùng câu INSERT hoặc dùng `RETURNING`:

```sql
INSERT INTO customer(id, name, email)
VALUES (nextval('customer_id_seq'), :name, :email)
RETURNING id;
```

Trong hầu hết trường hợp identity column kết hợp `RETURNING` đơn giản và an toàn hơn.

### 3.2. Sequence không bảo đảm ID liên tục

Sequence được thiết kế để cấp số duy nhất, không phải để tạo dãy không có khoảng trống. Một số tình huống tạo gap:

- Transaction lấy `nextval` rồi rollback.
- INSERT thất bại sau khi sequence đã cấp giá trị.
- Sequence cache giá trị trong session hoặc backend.
- Import hoặc thao tác quản trị làm thay đổi sequence.

Không dùng ID identity làm số hóa đơn liên tục, số chứng từ không có gap hoặc thứ tự commit tuyệt đối. Nếu nghiệp vụ yêu cầu số thứ tự có quy tắc pháp lý, cần thiết kế bộ cấp số riêng với khóa và transaction semantics phù hợp.

## 4. UUID và định danh sinh ở database

PostgreSQL hỗ trợ kiểu `UUID`. Có thể tạo UUID ở ứng dụng hoặc dùng default ở database:

```sql
CREATE TABLE api_request (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    request_type VARCHAR(80) NOT NULL
);
```

`gen_random_uuid()` có sẵn trong các phiên bản PostgreSQL hiện đại; hãy xác nhận phiên bản server mục tiêu. Nếu ID được sinh tại database và ứng dụng cần nhận lại, dùng `RETURNING id`.

Entity:

```java
@Table("api_request")
public class ApiRequest {

    @Id
    private UUID id;

    private String requestType;
}
```

UUID có thể thuận tiện khi cần tạo ID trước khi ghi hoặc trao đổi giữa nhiều hệ thống. Đổi lại, UUID chiếm nhiều dung lượng hơn `BIGINT` và đặc tính locality/index phụ thuộc loại UUID và cách sinh. Không chọn UUID chỉ vì muốn tránh sequence mà chưa xét kích thước index, khả năng sắp xếp và nhu cầu phân tán.

## 5. JSON và JSONB trong PostgreSQL

PostgreSQL có hai kiểu cột JSON phổ biến:

- `json`: lưu văn bản JSON và kiểm tra cú pháp JSON khi ghi.
- `jsonb`: lưu biểu diễn nhị phân đã phân tích, hỗ trợ toán tử và indexing phong phú hơn cho truy vấn.

Ví dụ schema:

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb
);
```

`jsonb` thường phù hợp khi ứng dụng cần truy vấn theo key/value, containment hoặc tạo GIN/expression index. `json` có thể phù hợp khi cần giữ nguyên văn bản JSON đầu vào theo đặc tính của kiểu dữ liệu, nhưng không hỗ trợ cùng tập indexing/operator như `jsonb`.

### 5.1. Khác biệt json và jsonb

| Đặc điểm | `json` | `jsonb` |
|---|---|---|
| Kiểm tra cú pháp | Có | Có |
| Biểu diễn | Lưu văn bản JSON | Lưu dạng nhị phân đã phân tích |
| Khoảng trắng và thứ tự key | Giữ cách trình bày đầu vào | Không giữ thứ tự key/khoảng trắng như văn bản gốc |
| Key trùng lặp | Giữ các key trùng trong văn bản | Chỉ giữ một giá trị cho key trùng theo quy tắc parser, thường là giá trị cuối |
| Truy vấn theo cấu trúc | Có toán tử nhưng xử lý văn bản | Có tập toán tử và indexing phong phú hơn |
| Index GIN cho nội dung JSON | Không giống `jsonb` | Hỗ trợ GIN |

Nếu cần so sánh hoặc tìm kiếm theo cấu trúc JSON, `jsonb` thường là lựa chọn mặc định hợp lý. Nếu cần giữ chính xác văn bản JSON gốc để ký số hoặc lưu payload nguyên bản, `json` có thể không đủ để bảo toàn mọi chi tiết như khoảng trắng và thứ tự; cân nhắc lưu nguyên văn trong `text` hoặc một cột riêng cùng metadata.

## 6. JSON không tự tạo schema nghiệp vụ

PostgreSQL kiểm tra cú pháp JSON, nhưng không tự biết rằng object phải có `currency`, `quantity` hoặc `shippingAddress` theo quy tắc domain của ứng dụng.

Ví dụ cả hai payload đều là JSON hợp lệ:

```json
{"color":"blue","size":"M"}
```

```json
{"colour":42,"unknown":true}
```

Nếu nghiệp vụ yêu cầu cấu trúc cụ thể, hãy xác thực ở application layer bằng DTO/schema validator. Có thể bổ sung `CHECK` constraint cho invariant đơn giản trong database, nhưng không nên coi JSONB là thay thế hoàn toàn cho relational schema.

Ví dụ kiểm tra JSON có key bắt buộc:

```sql
ALTER TABLE product
ADD CONSTRAINT ck_product_attributes_object
CHECK (jsonb_typeof(attributes) = 'object');
```

Constraint trên chỉ kiểm tra top-level là object, không xác nhận toàn bộ cấu trúc nghiệp vụ.

## 7. Mapping JSONB với R2DBC PostgreSQL driver

R2DBC PostgreSQL driver cung cấp kiểu `io.r2dbc.postgresql.codec.Json` để biểu diễn giá trị JSON/JSONB. Đây là kiểu driver-specific, không phải kiểu Java chung của Spring Data.

Có thể giữ property entity ở kiểu `Json`:

```java
import io.r2dbc.postgresql.codec.Json;

@Table("product")
public class Product {

    @Id
    private Long id;

    private String name;

    private Json attributes;
}
```

Khi tạo giá trị:

```java
Json attributes = Json.of("""
    {"color":"blue","size":"M"}
    """);
```

Khi đọc từ `Row`, có thể yêu cầu kiểu `Json` rồi lấy văn bản:

```java
Json json = row.get("attributes", Json.class);
String jsonText = json == null ? null : json.asString();
```

Kiểu `Json` giúp driver chọn codec JSON phù hợp. Kiểu API và codec có thể thay đổi theo phiên bản R2DBC PostgreSQL driver; hãy dùng đúng package/version trong dependency của dự án.

### 7.1. Bind JSON bằng DatabaseClient

Ví dụ INSERT:

```java
Mono<Long> insertProduct(String name, String jsonText) {
    Json json = Json.of(jsonText);

    return databaseClient.sql("""
            INSERT INTO product(name, attributes)
            VALUES (:name, :attributes)
            """)
        .bind("name", name)
        .bind("attributes", json)
        .fetch()
        .rowsUpdated();
}
```

`Json.of(...)` không thay thế validation nghiệp vụ. Nếu chuỗi không phải JSON hợp lệ, việc tạo/bind hoặc thực thi có thể thất bại tùy codec và driver. Hãy xác thực payload trước khi ghi.

Nếu bind một `String` thay vì `Json`, PostgreSQL có thể suy luận tham số là `varchar` và không tự chuyển sang `jsonb` trong mọi ngữ cảnh. Có thể dùng cast tường minh:

```sql
INSERT INTO product(name, attributes)
VALUES (:name, CAST(:attributes AS jsonb));
```

Ví dụ bind String với cast phù hợp API và driver. Không nên trộn hai cách bind mà không kiểm tra kiểu SQL được driver gửi.

### 7.2. Đọc JSONB qua DatabaseClient

```java
Mono<ProductJsonView> findProduct(Long id) {
    return databaseClient.sql("""
            SELECT id, name, attributes
            FROM product
            WHERE id = :id
            """)
        .bind("id", id)
        .map((row, metadata) -> {
            Json attributes = row.get("attributes", Json.class);
            return new ProductJsonView(
                row.get("id", Long.class),
                row.get("name", String.class),
                attributes == null ? null : attributes.asString()
            );
        })
        .one();
}
```

Không giữ đối tượng `Row` sau callback mapping. Chuyển dữ liệu sang DTO/kiểu domain ngay trong callback.

## 8. Ánh xạ JSONB sang kiểu domain bằng converter

Nếu ứng dụng thường xuyên đọc/ghi một cấu trúc JSON cụ thể, không nhất thiết để domain model chứa driver-specific `Json`. Có thể dùng converter giữa kiểu domain và `Json`.

Ví dụ domain type:

```java
public record ProductAttributes(
    String color,
    String size,
    List<String> labels
) {}
```

Converter ghi:

```java
@WritingConverter
public class ProductAttributesWriteConverter
        implements Converter<ProductAttributes, Json> {

    private final ObjectMapper objectMapper;

    public ProductAttributesWriteConverter(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    @Override
    public Json convert(ProductAttributes source) {
        try {
            return Json.of(objectMapper.writeValueAsString(source));
        } catch (JsonProcessingException error) {
            throw new IllegalArgumentException(
                "Không thể serialize ProductAttributes",
                error
            );
        }
    }
}
```

Converter đọc:

```java
@ReadingConverter
public class ProductAttributesReadConverter
        implements Converter<Json, ProductAttributes> {

    private final ObjectMapper objectMapper;

    public ProductAttributesReadConverter(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    @Override
    public ProductAttributes convert(Json source) {
        try {
            return objectMapper.readValue(
                source.asString(),
                ProductAttributes.class
            );
        } catch (JsonProcessingException error) {
            throw new IllegalArgumentException(
                "Không thể deserialize ProductAttributes",
                error
            );
        }
    }
}
```

Đăng ký converter qua `R2dbcCustomConversions` theo dialect PostgreSQL. Cách cấu hình bean hoặc override configuration hook phụ thuộc phiên bản Spring Data R2DBC/Spring Boot:

```java
@Bean
R2dbcCustomConversions r2dbcCustomConversions(
        ObjectMapper objectMapper) {

    return R2dbcCustomConversions.of(
        PostgresDialect.INSTANCE,
        List.of(
            new ProductAttributesWriteConverter(objectMapper),
            new ProductAttributesReadConverter(objectMapper)
        )
    );
}
```

Trong cấu hình thực tế, kiểm tra cơ chế Spring Boot đang dùng để tạo `R2dbcCustomConversions` và tránh khai báo hai bean xung đột. Converter ghi và đọc cần được đánh dấu hướng rõ ràng để Spring Data không suy luận nhầm chiều chuyển đổi.

Entity có thể dùng kiểu domain:

```java
@Table("product")
public class Product {

    @Id
    private Long id;

    private String name;

    private ProductAttributes attributes;
}
```

### 8.1. Xử lý JSON null và SQL NULL

Có sự khác nhau giữa:

- SQL `NULL`: cột không có giá trị.
- JSON `null`: giá trị JSON hợp lệ có literal `null`.
- JSON object rỗng `{}`: object không có property.
- JSON array rỗng `[]`: array JSON không có phần tử.

Các trường hợp này không tương đương. Ví dụ `attributes IS NULL` kiểm tra SQL NULL; JSONB `attributes = 'null'::jsonb` kiểm tra giá trị JSON null. Hãy chọn một quy ước và validation nhất quán trong domain.

## 9. Truy vấn JSONB bằng toán tử PostgreSQL

PostgreSQL có nhiều toán tử JSONB hữu ích:

| Toán tử | Ý nghĩa | Ví dụ |
|---|---|---|
| `->` | Lấy object/array con dưới dạng JSON | `attributes -> 'color'` |
| `->>` | Lấy giá trị dưới dạng text | `attributes ->> 'color'` |
| `#>` | Lấy giá trị theo path dạng mảng key | `attributes #> '{dimensions,width}'` |
| `#>>` | Lấy text theo path | `attributes #>> '{dimensions,width}'` |
| `@>` | Kiểm tra JSONB bên trái chứa JSONB bên phải | `attributes @> '{"color":"blue"}'` |
| `?` | Kiểm tra key hoặc phần tử tồn tại | `attributes ? 'color'` |
| `-` | Loại key hoặc phần tử | `attributes - 'internalNote'` |
| `jsonb_set` | Thay đổi giá trị tại path | `jsonb_set(attributes, '{color}', '"red"')` |

Ví dụ lọc sản phẩm theo màu:

```sql
SELECT id, name
FROM product
WHERE attributes ->> 'color' = 'blue';
```

Ví dụ containment:

```sql
SELECT id, name
FROM product
WHERE attributes @> '{"color":"blue"}'::jsonb;
```

Containment hữu ích khi cần kiểm tra object có chứa một cấu trúc con. Để so sánh scalar, cần chú ý kiểu JSON; chuỗi, số và boolean không giống nhau.

### 9.1. Path lồng nhau

Với JSON:

```json
{
  "dimensions": {
    "width": 12,
    "height": 8
  }
}
```

Có thể lấy chiều rộng:

```sql
SELECT attributes #>> '{dimensions,width}' AS width
FROM product;
```

`#>>` trả text. Nếu cần so sánh số, hãy cast tường minh và xác nhận dữ liệu luôn có định dạng số hợp lệ:

```sql
WHERE (attributes #>> '{dimensions,width}')::integer >= 10;
```

Nếu JSON có thể chứa string hoặc giá trị sai định dạng, cast có thể phát lỗi. Nên xác thực schema dữ liệu hoặc dùng điều kiện an toàn trước khi cast.

### 9.2. Cập nhật một phần JSONB

Không nhất thiết đọc toàn bộ JSON về ứng dụng, sửa một field rồi ghi lại toàn object. PostgreSQL có `jsonb_set`:

```sql
UPDATE product
SET attributes = jsonb_set(
    attributes,
    '{color}',
    to_jsonb(:color::text),
    true
)
WHERE id = :id;
```

Đây là SQL PostgreSQL minh họa. Cú pháp cast named parameter cần được kiểm tra với parser của `DatabaseClient`; có thể dùng `CAST(:color AS text)` nếu phù hợp. `jsonb_set` cập nhật path đã chỉ định, tham số cuối `true` cho phép tạo key còn thiếu ở vị trí cuối path theo semantics của hàm.

Thao tác phía database tránh vòng đọc-sửa-ghi ở ứng dụng, nhưng vẫn cần transaction/điều kiện concurrency nếu nhiều request cùng sửa các path có liên quan. Nếu hai request thay toàn bộ JSON bằng snapshot cũ, một request có thể ghi đè thay đổi của request kia. Cập nhật theo path hoặc optimistic locking giúp kiểm soát lost update.

## 10. Index cho JSONB

Truy vấn JSONB có thể quét toàn bảng nếu không có index phù hợp. PostgreSQL hỗ trợ GIN index cho JSONB:

```sql
CREATE INDEX idx_product_attributes_gin
ON product
USING GIN (attributes);
```

GIN index hữu ích cho một số toán tử containment/key-existence. Có các operator class như `jsonb_ops` và `jsonb_path_ops` với tập toán tử và đặc tính khác nhau. Chọn theo loại truy vấn thực tế, không chỉ theo kích thước JSON.

Nếu thường xuyên lọc một key cụ thể, expression index có thể nhỏ và phù hợp hơn:

```sql
CREATE INDEX idx_product_color
ON product ((attributes ->> 'color'));
```

Index expression cần khớp với biểu thức truy vấn để optimizer sử dụng hiệu quả. Kiểm tra bằng `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu đại diện.

Index làm tăng chi phí INSERT/UPDATE và dung lượng. JSONB thay đổi thường xuyên có thể khiến GIN index tốn tài nguyên. Chỉ index những truy vấn có giá trị thực tế.

## 11. Khi nào JSONB không phù hợp?

Không nên chuyển mọi thuộc tính vào một cột JSONB chỉ để tránh migration schema.

Các dấu hiệu nên dùng cột quan hệ bình thường:

- Trường luôn tồn tại và có kiểu cố định.
- Cần `NOT NULL`, `UNIQUE`, foreign key hoặc CHECK constraint rõ ràng.
- Cần join thường xuyên với bảng khác.
- Cần sort/filter theo field trong hầu hết truy vấn.
- Field tham gia khóa nghiệp vụ hoặc phân quyền.
- Dữ liệu cần thống kê, aggregate hoặc index với nhiều kiểu truy vấn.

JSONB phù hợp hơn cho metadata mở rộng, thuộc tính tùy biến theo loại sản phẩm, payload bên ngoài hoặc cấu trúc ít ổn định nhưng vẫn cần truy vấn một số key.

Một mô hình cân bằng là giữ các field quan hệ quan trọng ở cột riêng và chỉ dùng JSONB cho phần mở rộng:

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    sku VARCHAR(80) NOT NULL,
    name VARCHAR(200) NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb,
    CONSTRAINT uk_product_tenant_sku UNIQUE (tenant_id, sku)
);
```

`tenant_id`, `sku` và `name` có schema rõ ràng; `attributes` chứa phần metadata linh hoạt.

## 12. Mảng PostgreSQL

PostgreSQL hỗ trợ cột kiểu mảng cho nhiều kiểu dữ liệu cơ bản và một số kiểu khác. Ví dụ:

```sql
CREATE TABLE article (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(250) NOT NULL,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[]
);
```

`tags` là mảng các giá trị text. Một hàng có thể lưu:

```sql
ARRAY['r2dbc', 'postgresql', 'reactive']::TEXT[]
```

Mảng PostgreSQL là một giá trị SQL có kiểu phần tử xác định, khác với JSON array. Dùng mảng khi tập giá trị có cùng kiểu và cấu trúc đơn giản; dùng bảng quan hệ khi mỗi phần tử cần khóa riêng, constraint, thuộc tính riêng hoặc quan hệ phức tạp.

## 13. Mapping PostgreSQL array sang Java

R2DBC PostgreSQL driver hỗ trợ codec cho nhiều kiểu mảng. Với cột `TEXT[]`, kiểu Java thường dùng là `String[]`:

```java
@Table("article")
public class Article {

    @Id
    private Long id;

    private String title;

    private String[] tags;
}
```

Đọc giá trị qua `Row`:

```java
String[] tags = row.get("tags", String[].class);
```

Ghi bằng `DatabaseClient`:

```java
Mono<Long> insertArticle(String title, String[] tags) {
    return databaseClient.sql("""
            INSERT INTO article(title, tags)
            VALUES (:title, :tags)
            """)
        .bind("title", title)
        .bind("tags", tags)
        .fetch()
        .rowsUpdated();
}
```

Driver suy luận kiểu array từ kiểu Java và ngữ cảnh SQL. Với collection rỗng, kiểu phần tử vẫn cần rõ ràng; `new String[0]` giữ được component type. Một `List<String>` không nhất thiết được driver xem như một PostgreSQL array trong mọi API. Dùng Java array hoặc kiểu được driver hỗ trợ và kiểm tra integration test.

### 13.1. Kiểu phần tử phải tương thích

Một số mapping thường gặp:

| PostgreSQL | Java thường dùng |
|---|---|
| `TEXT[]`, `VARCHAR[]` | `String[]` |
| `BIGINT[]` | `Long[]` |
| `INTEGER[]` | `Integer[]` |
| `UUID[]` | `UUID[]` |
| `BOOLEAN[]` | `Boolean[]` |
| `NUMERIC[]` | `BigDecimal[]` |

Khả năng cụ thể phụ thuộc phiên bản driver và codec đã đăng ký. Kiểu primitive array như `long[]` có thể không tương đương `Long[]` đối với codec hoặc giá trị NULL; wrapper array thường phù hợp hơn khi cần biểu diễn phần tử null.

### 13.2. NULL array và array rỗng

Hai giá trị này khác nhau:

- SQL `NULL`: không có giá trị mảng.
- `ARRAY[]::TEXT[]`: mảng có 0 phần tử.

Nếu cột `NOT NULL DEFAULT ARRAY[]::TEXT[]`, hàng mới có thể có mảng rỗng. Nếu bind null, cần dùng `bindNull` với kiểu array phù hợp hoặc để cột nhận default bằng cách bỏ cột khỏi INSERT. Đừng coi null và empty array là một trạng thái.

## 14. Truy vấn PostgreSQL array

PostgreSQL có các toán tử mảng hữu ích:

| Toán tử/hàm | Ý nghĩa | Ví dụ |
|---|---|---|
| `= ANY(array)` | Giá trị bằng ít nhất một phần tử | `'r2dbc' = ANY(tags)` |
| `@>` | Mảng bên trái chứa mọi phần tử bên phải | `tags @> ARRAY['r2dbc']` |
| `<@` | Mảng bên trái là tập con của bên phải | `tags <@ ARRAY['r2dbc','sql']` |
| `&&` | Hai mảng có phần tử giao nhau | `tags && ARRAY['r2dbc','jdbc']` |
| `array_length` | Lấy độ dài theo chiều | `array_length(tags, 1)` |
| `cardinality` | Tổng số phần tử | `cardinality(tags)` |
| `unnest` | Mở rộng phần tử thành các hàng | `SELECT unnest(tags)` |
| `array_position` | Vị trí phần tử đầu tiên | `array_position(tags, 'r2dbc')` |

Ví dụ tìm bài viết có tag `r2dbc`:

```sql
SELECT id, title
FROM article
WHERE 'r2dbc' = ANY(tags);
```

Ví dụ tìm bài viết có ít nhất một tag trong tập lọc:

```sql
SELECT id, title
FROM article
WHERE tags && ARRAY['r2dbc', 'postgresql']::TEXT[];
```

### 14.1. Truyền mảng làm tham số bằng ANY

Với danh sách ID, có thể bind một PostgreSQL array và dùng `ANY`:

```java
Flux<Customer> findCustomers(Long[] ids) {
    return databaseClient.sql("""
            SELECT id, name, email
            FROM customer
            WHERE id = ANY(:ids)
            ORDER BY id
            """)
        .bind("ids", ids)
        .map((row, metadata) -> new Customer(
            row.get("id", Long.class),
            row.get("name", String.class),
            row.get("email", String.class)
        ))
        .all();
}
```

Đây là PostgreSQL-specific array binding, khác với việc mở rộng collection thành nhiều placeholder trong `IN (:ids)`. Câu lệnh có một array parameter thay vì một marker cho mỗi ID. Hãy kiểm tra kiểu array được driver bind và dùng cast tường minh nếu ngữ cảnh không đủ để suy luận:

```sql
WHERE id = ANY(CAST(:ids AS BIGINT[]))
```

### 14.2. Semantics của array rỗng và NULL

Với `x = ANY(empty_array)`, kết quả là false vì không có phần tử nào khớp. Với `x = ANY(NULL)`, kết quả là NULL/unknown. Nếu mảng có phần tử NULL và không có phần tử khớp, kết quả cũng có thể là unknown.

Vì vậy, trước khi bind array từ request, hãy xác định:

- Array rỗng có nghĩa là không có kết quả hay bỏ qua filter?
- Array null có được phép không?
- Phần tử null có hợp lệ không?
- Có cần loại duplicates không?
- Kích thước tối đa là bao nhiêu?

Nếu collection rỗng nghĩa là không chọn ID nào, có thể trả `Flux.empty()` trước khi truy vấn. Nếu rỗng nghĩa là bỏ qua filter, hãy xây dựng nhánh query không có điều kiện đó. Không để null/empty tự quyết định semantics nghiệp vụ.

### 14.3. Array indexing trong PostgreSQL

Mảng PostgreSQL thường đánh chỉ số từ 1, khác Java array bắt đầu từ 0. Ví dụ:

```sql
SELECT tags[1]
FROM article;
```

trả phần tử đầu tiên. PostgreSQL còn cho phép khai báo lower bound khác 1 trong một số trường hợp; không giả định mọi mảng đều có lower bound cố định nếu dữ liệu được tạo từ nhiều nguồn.

Khi ánh xạ toàn bộ array sang Java array, driver xử lý biểu diễn giá trị. Nhưng khi dùng SQL truy cập phần tử hoặc cập nhật slice, hãy nhớ quy tắc chỉ số của PostgreSQL.

## 15. Index cho PostgreSQL array

GIN index có thể hỗ trợ các toán tử mảng như containment và overlap:

```sql
CREATE INDEX idx_article_tags_gin
ON article
USING GIN (tags);
```

Index này có thể hữu ích cho truy vấn `@>`, `<@` hoặc `&&` tùy operator class và execution plan. Không phải mọi biểu thức `ANY` đều sử dụng GIN theo cùng cách; hãy kiểm tra query plan và kiểu truy vấn.

Index làm tăng chi phí ghi và dung lượng. Nếu array rất lớn hoặc thay đổi thường xuyên, đánh giá workload trước khi tạo index.

## 16. PostgreSQL array hay bảng quan hệ?

Mảng không phải thay thế tổng quát cho bảng con.

| Nhu cầu | PostgreSQL array | Bảng quan hệ |
|---|---|---|
| Danh sách tag text đơn giản | Phù hợp | Có thể dư thừa nếu không cần metadata |
| Mỗi phần tử có ID và thuộc tính riêng | Khó quản lý | Phù hợp |
| Cần foreign key cho từng phần tử | Không thuận tiện như quan hệ hàng | Phù hợp |
| Cần join/filter/report từng phần tử thường xuyên | Có thể dùng `unnest`, nhưng phức tạp hơn | Phù hợp |
| Thứ tự phần tử có ý nghĩa và tập nhỏ | Mảng có thể phù hợp | Bảng có `position` cũng phù hợp |
| Cần uniqueness trên từng phần tử theo phạm vi | Khó áp constraint từng phần tử | Dễ dùng unique constraint |
| Tập giá trị nhỏ, cùng kiểu, đọc/ghi cùng entity | Phù hợp | Có thể không cần thêm bảng |

Ví dụ nếu mỗi article có danh sách tag đơn giản, `TEXT[]` có thể phù hợp. Nếu tag có mô tả, trạng thái, người tạo, quan hệ nhiều-nhiều hoặc cần thống kê độc lập, nên dùng bảng `tag` và bảng liên kết `article_tag`.

## 17. JSON array và PostgreSQL array không giống nhau

Hai kiểu đều có thể lưu danh sách nhưng semantics khác nhau:

| Tiêu chí | PostgreSQL array | JSON/JSONB array |
|---|---|---|
| Kiểu phần tử | Một kiểu SQL xác định | Có thể trộn string, number, object, boolean và null |
| Codec R2DBC | Java array theo codec driver | `Json` hoặc converter domain |
| Toán tử | `ANY`, `@>`, `&&`, `unnest`... | `->`, `->>`, `@>`, `jsonb_array_elements`... |
| Validation kiểu | Database biết kiểu phần tử | Cần kiểm tra schema JSON ở application/constraint |
| Quan hệ phần tử | Không có foreign key riêng cho từng phần tử | Không có foreign key riêng cho từng phần tử |
| Phù hợp | Danh sách giá trị đồng kiểu | Payload linh hoạt hoặc danh sách object bán cấu trúc |

Ví dụ `TEXT[]` phù hợp cho danh sách tag cùng kiểu. JSONB array phù hợp hơn nếu mỗi phần tử là object có nhiều field và cấu trúc thay đổi. Nếu từng phần tử cần quan hệ và constraint mạnh, dùng bảng quan hệ.

## 18. Kết hợp identity, JSONB và array trong một entity

Một bảng PostgreSQL có thể dùng cả ba tính năng:

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    sku VARCHAR(80) NOT NULL,
    name VARCHAR(200) NOT NULL,
    attributes JSONB NOT NULL DEFAULT '{}'::jsonb,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[],
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_product_tenant_sku UNIQUE (tenant_id, sku)
);
```

Entity có thể dùng driver-specific `Json` và Java array:

```java
@Table("product")
public class Product {

    @Id
    private Long id;

    private Long tenantId;

    private String sku;

    private String name;

    private Json attributes;

    private String[] tags;

    private Instant createdAt;
}
```

Nếu muốn domain model không phụ thuộc driver, thay `Json` bằng `ProductAttributes` và đăng ký converter như phần trước.

### 18.1. Lưu và nhận lại generated ID

Với custom SQL:

```java
Mono<Long> createProduct(
        Long tenantId,
        String sku,
        String name,
        Json attributes,
        String[] tags) {

    return databaseClient.sql("""
            INSERT INTO product(tenant_id, sku, name, attributes, tags)
            VALUES (:tenantId, :sku, :name, :attributes, :tags)
            RETURNING id
            """)
        .bind("tenantId", tenantId)
        .bind("sku", sku)
        .bind("name", name)
        .bind("attributes", attributes)
        .bind("tags", tags)
        .map((row, metadata) -> row.get("id", Long.class))
        .one();
}
```

`RETURNING id` vừa lấy khóa vừa tránh query sequence riêng. Câu lệnh cần xử lý unique conflict cho `(tenant_id, sku)` theo quy tắc nghiệp vụ.

## 19. Các lưu ý về hiệu năng và vận hành

### 19.1. Generated ID

- Dùng `BIGINT` khi quy mô ID có thể vượt giới hạn `INTEGER`.
- Không giả định sequence không có gap.
- Không dùng `MAX(id) + 1`.
- Không truy vấn `currval` trên connection khác.
- Dùng `RETURNING` khi cần lấy ID hoặc giá trị database sinh.
- Nếu import ID tường minh, kiểm tra và đồng bộ sequence sau import theo cách an toàn.

### 19.2. JSONB

- Chỉ dùng JSONB cho dữ liệu thực sự linh hoạt hoặc bán cấu trúc.
- Xác thực payload trước khi ghi; JSON hợp lệ về cú pháp chưa chắc hợp lệ nghiệp vụ.
- Chọn `Json` codec hoặc custom converter rõ ràng.
- Dùng bind parameter; không nối JSON vào SQL.
- Dùng GIN/expression index theo query thực tế.
- Cẩn thận SQL NULL khác JSON null.
- Cập nhật path bằng SQL phù hợp để giảm read-modify-write khi cần.
- Theo dõi kích thước document và chi phí cập nhật/index.

### 19.3. Array

- Dùng Java array tương thích codec, ví dụ `String[]` cho `TEXT[]`.
- Phân biệt array rỗng và SQL NULL.
- Kiểm tra phần tử null và kiểu phần tử.
- Dùng `ANY`/array operator khi phù hợp PostgreSQL.
- Không giả định `List<T>` tự động bind thành SQL array.
- Xem xét GIN index cho containment/overlap query.
- Chuyển sang bảng quan hệ nếu cần constraint hoặc metadata trên từng phần tử.

## 20. Kiểm thử tích hợp với PostgreSQL R2DBC

Mock repository không đủ để xác nhận codec PostgreSQL. Cần integration test với đúng R2DBC PostgreSQL driver và phiên bản server mục tiêu.

### 20.1. Kiểm thử identity và RETURNING

- INSERT entity có ID null.
- Xác nhận entity được phát ra có ID.
- INSERT nhiều hàng và kiểm tra ID trả về tương ứng.
- Kiểm tra rollback vẫn có thể tạo gap sequence.
- Kiểm tra import ID tường minh và trạng thái sequence.
- Kiểm tra `GENERATED ALWAYS` và `BY DEFAULT` theo schema thực tế.

### 20.2. Kiểm thử JSONB

- Ghi và đọc JSON object lồng nhau.
- Kiểm tra string, number, boolean, array và null.
- Phân biệt SQL NULL, JSON null, `{}` và `[]`.
- Kiểm tra converter với payload không hợp lệ.
- Kiểm tra toán tử `->>`, `@>`, `jsonb_set`.
- Kiểm tra index bằng execution plan trên dữ liệu đại diện.

### 20.3. Kiểm thử array

- Ghi và đọc array có nhiều phần tử.
- Ghi array rỗng và SQL NULL.
- Kiểm tra array có phần tử null nếu domain cho phép.
- Bind `String[]`, `Long[]` và kiểu cần dùng.
- Kiểm tra `ANY`, `@>`, `&&`, `unnest`.
- Kiểm tra kích thước lớn và giới hạn payload/driver.
- Xác nhận thứ tự và indexing 1-based khi dùng SQL truy cập phần tử.

Ví dụ test đơn giản:

```java
StepVerifier.create(articleRepository.findById(articleId))
    .assertNext(article -> {
        assertArrayEquals(
            new String[] {"r2dbc", "postgresql"},
            article.getTags()
        );
    })
    .verifyComplete();
```

Test cần tạo dữ liệu trước đó bằng repository hoặc fixture SQL và đọc lại từ database để xác nhận codec hai chiều.

## 21. Những lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Dùng primitive `long` cho ID mới | Giá trị mặc định `0` gây nhập nhằng newness | Dùng `Long` nullable khi phù hợp |
| Tự tạo ID bằng `MAX(id) + 1` | Race condition khi nhiều request cùng ghi | Dùng identity/sequence hoặc UUID |
| Dùng `currval` trên connection khác | Không lấy đúng giá trị của session INSERT | Dùng `INSERT ... RETURNING` |
| Giả định sequence không có gap | Sinh số nghiệp vụ không đúng yêu cầu | Không dùng identity làm số chứng từ liên tục |
| Cho client truyền ID vào cột `GENERATED ALWAYS` | INSERT bị từ chối | Chỉ override trong import có kiểm soát hoặc dùng BY DEFAULT khi phù hợp |
| Bind JSON String như scalar mà không cast | PostgreSQL có thể suy luận kiểu không phù hợp | Dùng `Json` codec hoặc cast sang `jsonb` |
| Giả định POJO tự động ánh xạ JSONB | Mapping/conversion có thể thất bại | Dùng `Json` hoặc custom converter |
| Ghi JSON hợp lệ cú pháp nhưng sai schema domain | Dữ liệu khó đọc hoặc lỗi ở consumer | Validate payload trước khi ghi |
| Nhầm SQL NULL với JSON null | Truy vấn và logic fallback sai | Xác định semantics riêng cho từng trạng thái |
| Lưu mọi field vào JSONB | Mất constraint, join và kiểu dữ liệu rõ ràng | Giữ field quan trọng ở cột quan hệ |
| Tạo GIN index cho mọi JSONB | Tăng chi phí ghi và dung lượng | Index theo query workload |
| Bind `List<T>` và giả định là array | Driver có thể không tìm được codec | Dùng Java array/codec được hỗ trợ |
| Nhầm array rỗng với NULL | `ANY` và filter cho kết quả khác nhau | Xử lý empty/null rõ ràng |
| Dùng `IN (:ids)` khi muốn PostgreSQL array parameter | Named collection expansion khác với array binding | Dùng `= ANY(:ids)` và bind array đúng kiểu |
| Dùng array cho quan hệ cần foreign key | Không bảo vệ được từng phần tử như bảng con | Dùng bảng liên kết quan hệ |

## 22. Quy trình lựa chọn và triển khai

Khi thiết kế một bảng PostgreSQL cho Spring Data R2DBC, có thể đi theo trình tự:

1. **Chọn định danh:** dùng identity `BIGINT`, UUID sinh ở ứng dụng hay UUID default ở database theo yêu cầu phân tán và index.
2. **Chọn chế độ identity:** `ALWAYS` nếu database phải kiểm soát ID; `BY DEFAULT` nếu có nhu cầu import ID tường minh được kiểm soát.
3. **Xác định cách lấy ID:** dùng repository/template mapping hoặc `RETURNING` cho custom SQL.
4. **Chọn kiểu JSON:** dùng `jsonb` nếu cần query/index cấu trúc; dùng `json` hoặc `text` khi có yêu cầu giữ payload theo cách khác.
5. **Chọn cách mapping JSON:** dùng driver `Json` hoặc custom converter sang domain type.
6. **Xác thực JSON:** kiểm tra schema nghiệp vụ và phân biệt SQL NULL với JSON null.
7. **Chọn array hay quan hệ:** dùng SQL array cho tập giá trị cùng kiểu đơn giản; dùng bảng liên kết khi từng phần tử có identity/constraint riêng.
8. **Chọn kiểu Java:** dùng `String[]`, `Long[]` hoặc kiểu codec hỗ trợ; không giả định mọi `Collection` là SQL array.
9. **Thiết kế query/index:** chọn JSONB operator, array operator và index theo execution plan thực tế.
10. **Kiểm thử driver:** xác nhận bind, read, write, generated values và kiểu dữ liệu trên PostgreSQL mục tiêu.

## 23. Nguyên tắc cần nhớ

- PostgreSQL identity column dùng sequence nội bộ; `GENERATED ALWAYS` và `BY DEFAULT` khác nhau ở quyền cung cấp ID tường minh.
- Với entity mới, dùng ID nullable như `Long` để Spring Data nhận diện trạng thái mới theo cơ chế thông thường.
- Không dùng `MAX(id) + 1`; để identity/sequence cấp giá trị an toàn khi ghi đồng thời.
- Dùng `INSERT ... RETURNING` để lấy ID/giá trị database sinh trong cùng statement.
- Sequence có thể tạo gap và không phải bộ cấp số liên tục cho chứng từ nghiệp vụ.
- `jsonb` phù hợp cho dữ liệu bán cấu trúc cần query/index; JSON hợp lệ cú pháp chưa chắc hợp lệ nghiệp vụ.
- R2DBC PostgreSQL driver cung cấp `io.r2dbc.postgresql.codec.Json`; dùng codec hoặc custom converter để ánh xạ domain type.
- Bind JSON bằng kiểu phù hợp hoặc cast tường minh; không nối chuỗi payload vào SQL.
- Phân biệt SQL NULL, JSON null, object rỗng và array rỗng.
- Dùng JSONB operators và GIN/expression index theo query workload; không index mọi field một cách máy móc.
- Dùng PostgreSQL array cho danh sách đồng kiểu đơn giản và Java array tương thích codec.
- `ANY`, `@>`, `&&` và `unnest` là công cụ truy vấn array; empty array khác NULL.
- PostgreSQL array đánh chỉ số thường từ 1, khác Java array bắt đầu từ 0.
- JSON array linh hoạt về kiểu phần tử; SQL array có kiểu phần tử rõ ràng.
- Dùng bảng quan hệ khi từng phần tử cần foreign key, metadata, uniqueness hoặc join thường xuyên.
- Kiểm thử trên đúng phiên bản PostgreSQL và R2DBC driver vì codec và mapping phụ thuộc implementation.

PostgreSQL identity, JSONB và array cung cấp các khả năng mạnh cho ứng dụng Spring Data Relational R2DBC. Identity/sequence giải quyết việc cấp khóa đồng thời và `RETURNING` lấy lại giá trị database sinh; JSONB lưu metadata linh hoạt có thể truy vấn và index; array lưu tập giá trị cùng kiểu với các toán tử chuyên biệt. Khi phân biệt rõ kiểu SQL với kiểu Java, dùng codec/converter phù hợp và kiểm thử trên driver thật, ứng dụng có thể tận dụng các tính năng PostgreSQL mà vẫn giữ mapping, transaction và hợp đồng dữ liệu dễ kiểm soát.
