# Requesting Generated Columns from Write Operations

When writing data to a relational database, not every column value in a row is generated by the application. The database may auto-generate an identity primary key, fetch a value from a sequence, populate a default timestamp, evaluate a generated/computed column, or assign data via a trigger. After an `INSERT` or `UPDATE` operation, the application sometimes needs those values back to build a response, continue business processing, or update an in-memory object.

In Spring Data R2DBC, distinguish two tasks: **asking the database to return the generated values** and **mapping the returned values into an entity/DTO**. Repositories and `R2dbcEntityTemplate` handle the common generated-ID flow. For direct SQL via `DatabaseClient`, you can request generated values through the R2DBC SPI or use database-specific syntax like `RETURNING` or `OUTPUT`. If the driver does not support returning the required columns, the application must re-read the row after writing.

## 1. Types of Columns That Can Be Generated by the Database

A write operation can produce several kinds of values:

| Value Type | How the Database Produces It | Example |
|---|---|---|
| Identity / auto-increment | Database allocates a new number on insert | Auto-incrementing `id` |
| Sequence | Fetches the next number from a sequence | `nextval('person_id_seq')` in PostgreSQL |
| Default value | Applies a default expression when insert omits the column | `created_at DEFAULT CURRENT_TIMESTAMP` |
| Generated / computed column | Computed from other columns via a declared expression | `normalized_name GENERATED ALWAYS AS (lower(name))` |
| Trigger-generated value | A trigger modifies or populates data during the write | Reference code, timestamp, or status set by a trigger |
| Value produced by an update | Database recomputes a column during `UPDATE` | `updated_at`, balance, or computed column |

Not every value is returned through the same mechanism. Identity keys are usually supported via the driver's generated-values facility. Defaults, generated columns, and trigger-assigned values may require specifying column names explicitly or using SQL with `RETURNING`/`OUTPUT`.

## 2. Distinguishing DEFAULT from Generated/Computed Columns

These two concepts are often confused:

**DEFAULT** supplies a value when an insert statement omits a value for that column. The application can still actively pass a different value if the schema and permissions allow it.

**A generated/computed column** is computed by the database from a declared expression. Normally, the application is not permitted to write to this column directly; the database recalculates it from source data.

PostgreSQL example:

```sql
CREATE TABLE person (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    normalized_name VARCHAR(200)
        GENERATED ALWAYS AS (lower(name)) STORED
);
```

In this table:

- `id` is assigned by the database on insert.
- `created_at` receives the current timestamp if omitted from the insert.
- `normalized_name` is computed from `name`; the application should not supply a value for this column.

If the SQL explicitly writes `created_at = NULL`, the database receives null instead of applying `DEFAULT`, unless a constraint or expression handles it differently. To apply the default, omit the column from the insert column list or use the `DEFAULT` keyword per database syntax.

For generated columns, omit the column from insert/update column lists. Attempting to write a value directly may be rejected by the database.

## 3. Auto-Generated Values When Using ReactiveCrudRepository

For an entity with an identity primary key, Spring Data R2DBC can retrieve the database-generated ID after insert and populate it on the returned entity.

```java
@Table("person")
public record Person(
    @Id Long id,
    String name
) {}
```

Repository:

```java
public interface PersonRepository
        extends ReactiveCrudRepository<Person, Long> {
}
```

Service:

```java
public Mono<Person> create(String name) {
    Person person = new Person(null, name);
    return personRepository.save(person);
}
```

When `id` is null and mapping/database determines this is a new entity, `save` performs an insert. The database-generated ID is retrieved via the driver's generated-values mechanism and set on the resulting entity. The publisher emits the entity with its ID populated after the operation completes.

Prefer reference types like `Long` for auto-generated IDs so the unpopulated state is represented by `null`. With a primitive like `long`, the default value `0` does not clearly represent an unassigned ID and can interfere with new-entity detection strategies.

Do not assume every entity with a non-null ID is inserted or updated identically. `save` chooses insert or update according to Spring Data's newness detection strategy, which may rely on ID, `@Version`, or `Persistable` depending on the entity. If IDs are pre-assigned by the application, design appropriate newness detection.

## 4. Using R2dbcEntityTemplate to Receive Auto-Generated IDs

If the application uses `R2dbcEntityTemplate`, an insert operation also returns the entity after writing:

```java
public Mono<Person> create(String name) {
    Person person = new Person(null, name);
    return template.insert(Person.class).using(person);
}
```

This is a clean choice when using Spring Data's entity API instead of direct SQL. The template uses mapping metadata and dialect to generate the insert statement and coordinates with the R2DBC driver to fetch generated IDs as supported by the database.

When the goal is solely retrieving an identity ID, Repository or Template is typically the simplest choice. When you also need other database-generated columns like `created_at`, `normalized_name`, or trigger-set values, verify whether your Spring Data version, dialect, and driver return those columns on insert. Do not infer that automatic ID assignment means all generated columns were refreshed on the entity.

## 5. Marking Read-Only Columns with @ReadOnlyProperty

Spring Data Relational provides `@ReadOnlyProperty` to mark properties that are read from the database but excluded from inserts or updates performed by Spring Data.

Entity example:

```java
@Table("person")
public record Person(
    @Id Long id,
    String name,
    @ReadOnlyProperty
    @Column("created_at")
    OffsetDateTime createdAt,
    @ReadOnlyProperty
    @Column("normalized_name")
    String normalizedName
) {}
```

`createdAt` and `normalizedName` are read when querying the entity, but Spring Data omits them from generated insert/update statements. This is useful for default or generated columns that the application must not write directly.

`@ReadOnlyProperty` controls property writing through Spring Data mapping; the annotation does not guarantee the driver returns those values immediately after insert. If you need the newly generated values within the same request, explicitly request generated values or re-query the row after writing.

Do not apply `@ReadOnlyProperty` to columns the application needs to update actively. If a column should only be written on insert and skipped on update, check other annotations and semantics such as `@InsertOnlyProperty` if supported by your Spring Data version.

## 6. Requesting Generated Values via the R2DBC SPI

The R2DBC SPI defines `Statement.returnGeneratedValues(String... columns)` to ask the driver to return database-generated values produced during statement execution.

With `DatabaseClient`, you can add a `StatementFilterFunction` to configure the statement prior to execution:

```java
public Mono<PersonCreated> insertPerson(String name) {
    return databaseClient.sql("""
            INSERT INTO person (name)
            VALUES (:name)
            """)
        .bind("name", name)
        .filter((statement, next) -> {
            statement.returnGeneratedValues(
                "id",
                "created_at",
                "normalized_name"
            );
            return next.execute(statement);
        })
        .map((row, metadata) -> new PersonCreated(
            row.get("id", Long.class),
            row.get("created_at", OffsetDateTime.class),
            row.get("normalized_name", String.class)
        ))
        .one();
}
```

DTO:

```java
public record PersonCreated(
    Long id,
    OffsetDateTime createdAt,
    String normalizedName
) {}
```

Execution flow:

1. `sql(...)` declares the insert statement; `id`, `created_at`, and `normalized_name` are omitted from the insert column list.
2. `bind(...)` attaches the value for the `name` parameter.
3. `filter(...)` receives the statement before execution and invokes `returnGeneratedValues(...)`.
4. `next.execute(statement)` passes the configured statement to the next execution step.
5. `map(...)` maps the generated-values row into a DTO.
6. `one()` expects a single result and returns `Mono<PersonCreated>`.

`returnGeneratedValues` is part of the R2DBC SPI, but actual support depends on the driver and DBMS. A driver may only return an identity column, may not support arbitrary column names, or may impose restrictions on which columns are returned. Check the documentation for your exact driver version and run integration tests against the target database.

If the driver does not support extra generated columns, do not assume `row` will contain all requested columns. Choose one of the alternatives: use database-specific `RETURNING`/`OUTPUT` SQL or run a `SELECT` after insert.

## 7. Using RETURNING in PostgreSQL

PostgreSQL supports the `RETURNING` clause for `INSERT`, `UPDATE`, and `DELETE`. This is a direct way to receive columns from the newly modified row.

Example inserting and receiving ID, default timestamp, and generated column:

```java
public Mono<PersonCreated> insertPerson(String name) {
    return databaseClient.sql("""
            INSERT INTO person (name)
            VALUES (:name)
            RETURNING id, created_at, normalized_name
            """)
        .bind("name", name)
        .map((row, metadata) -> new PersonCreated(
            row.get("id", Long.class),
            row.get("created_at", OffsetDateTime.class),
            row.get("normalized_name", String.class)
        ))
        .one();
}
```

Here, `RETURNING` is PostgreSQL SQL syntax, not portable across every database. The advantage is that writing and retrieving generated values happen in one operation, avoiding an extra round trip solely to re-read the row.

While `RETURNING *` is possible, it is usually better to list needed columns explicitly to avoid transferring extra data and to keep the DTO contract clear. If the schema contains sensitive columns or large payloads, returning only required columns is even more important.

### UPDATE RETURNING

A column may change upon update, such as `updated_at` updated by a database default/trigger or a generated expression. PostgreSQL can return the post-update values:

```java
public Mono<PersonUpdated> rename(Long id, String newName) {
    return databaseClient.sql("""
            UPDATE person
            SET name = :name
            WHERE id = :id
            RETURNING id, name, created_at, normalized_name
            """)
        .bind("name", newName)
        .bind("id", id)
        .map((row, metadata) -> new PersonUpdated(
            row.get("id", Long.class),
            row.get("name", String.class),
            row.get("created_at", OffsetDateTime.class),
            row.get("normalized_name", String.class)
        ))
        .one();
}
```

If the ID does not exist or the predicate does not match, `one()` completes empty. The service can translate an empty result into a not-found error or treat it as a no-op depending on the API contract.

### DELETE RETURNING

PostgreSQL can also return columns from deleted rows:

```java
public Flux<Long> deleteAndReturnIds(String status) {
    return databaseClient.sql("""
            DELETE FROM person
            WHERE status = :status
            RETURNING id
            """)
        .bind("status", status)
        .map((row, metadata) -> row.get("id", Long.class))
        .all();
}
```

This is useful when recording audit trails or emitting events based on deleted IDs. Consider the number of returned rows so you do not collect an overly large result set in memory.

## 8. SQL Server OUTPUT Clause

SQL Server supports the `OUTPUT` clause to retrieve values from inserted, updated, or deleted rows. Example:

```sql
INSERT INTO person (name)
OUTPUT INSERTED.id,
       INSERTED.created_at,
       INSERTED.normalized_name
VALUES (@name);
```

When using `DatabaseClient`, placeholders and binding must fit the R2DBC SQL Server driver in use. `OUTPUT INSERTED...` syntax is SQL Server-specific; you cannot copy a PostgreSQL statement with `RETURNING` verbatim to SQL Server.

Other DBMSs may use different syntax or APIs to obtain generated values. Consequently, if the application must support multiple databases, consider the R2DBC SPI abstraction when drivers support it consistently, or separate SQL statements by dialect.

## 9. Default Values Are Only Generated When the Column Is Omitted

The database applies a default when the insert statement does not supply a value for that column or uses the `DEFAULT` keyword per database syntax.

Example:

```sql
-- DEFAULT is applied for created_at.
INSERT INTO person (name)
VALUES ('An');

-- This statement explicitly writes NULL; default does not replace NULL.
INSERT INTO person (name, created_at)
VALUES ('Binh', NULL);
```

In direct SQL, omit defaulted columns from the insert column list if you want the database to generate the value. In entity mapping, `@ReadOnlyProperty` helps exclude the property from Spring Data write operations. For nullable properties where null must occasionally be passed deliberately, clearly distinguish "omitted to apply default" from "explicitly writing null."

Do not assume binding a null value is equivalent to omitting the column. Binding null passes a SQL null value to the placeholder; it does not trigger the default.

## 10. Generated Columns Are Not Updated by the Application

A generated column is computed by the database from other columns. Example:

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    quantity INTEGER NOT NULL,
    line_total NUMERIC(19, 2)
        GENERATED ALWAYS AS (unit_price * quantity) STORED
);
```

The application only writes `name`, `unit_price`, and `quantity`. The database computes `line_total`. Attempting to insert or update `line_total` may fail because it is a generated column.

In the entity, mark this column read-only:

```java
@Table("product")
public record Product(
    @Id Long id,
    String name,
    BigDecimal unitPrice,
    Integer quantity,
    @ReadOnlyProperty
    @Column("line_total")
    BigDecimal lineTotal
) {}
```

When querying `Product`, `lineTotal` is read from the database. After insert/update, if the framework/driver does not return that column in generated values, re-read the row to obtain the updated value.

## 11. Triggers Can Generate or Modify Values

Triggers can assign values before or after a write operation depending on the DBMS and trigger type. For instance, a trigger might set `updated_at`, normalize data, or generate a reference code.

When trigger-generated values must be retrieved, verify whether the database and driver return those values in generated values/`RETURNING`. Behavior can differ between before-write triggers, after-write triggers, and the database's result-returning mechanism.

If the value is not returned, the general approach is to re-query the row after the write using its ID or a unique business key. Avoid running a `SELECT` based solely on non-unique values like a user name or an approximate timestamp.

## 12. Re-Reading the Row After Writing

If the driver does not return extra generated columns, the application can insert and then select again. For example, once the auto-generated ID is received:

```java
public Mono<Person> createAndReload(String name) {
    Person person = new Person(null, name, null, null);

    return personRepository.save(person)
        .flatMap(saved -> personRepository.findById(saved.id()));
}
```

This example assumes the `Person` entity has read-only properties `createdAt` and `normalizedName`, and `save` returns the generated ID. The second query loads all columns from the database, including defaults and generated columns.

Re-reading incurs an extra round trip. If the response immediately needs generated values and the database supports `RETURNING` or `returnGeneratedValues`, receiving them in the same operation is usually more efficient.

If you need insert followed by select within the same transaction, place both operations inside one reactive transaction and return a continuous publisher chain. This ensures the subsequent query sees the newly written changes according to database isolation semantics.

Do not rely on functions like `last_insert_id()` in an independent statement on a connection pool without guaranteeing both statements share the exact same connection/session. Another operation could be assigned a different connection. Use generated values, `RETURNING`, or explicitly managed transactions/connections.

## 13. Using Sequences When You Need to Acquire the ID Proactively

Some schemas use standalone sequences instead of identity columns. In PostgreSQL:

```sql
CREATE SEQUENCE person_id_seq START WITH 1 INCREMENT BY 1;

CREATE TABLE person (
    id BIGINT PRIMARY KEY DEFAULT nextval('person_id_seq'),
    name VARCHAR(200) NOT NULL
);
```

Normally, you can let the database apply the sequence default and request the generated ID after insert. If business logic needs the ID before inserting, you can query the sequence:

```sql
SELECT nextval('person_id_seq');
```

Then use the retrieved value to insert. Pre-fetching can be useful when assigning the ID across multiple records in the same workflow, provided the sequence belongs to the right schema and permissions are configured.

Never compute IDs via `MAX(id) + 1`. Two concurrent requests can read the same max value and produce duplicate IDs. Use identity columns, sequences, or another safe ID-generation mechanism.

## 14. Generated Values and Multi-Row Inserts

A single insert statement can add multiple rows at once. Support for returning generated values for each row depends on the database, driver, and statement form.

PostgreSQL example:

```sql
INSERT INTO person (name)
VALUES ('An'), ('Binh'), ('Chi')
RETURNING id, name, created_at;
```

The `RETURNING` result can contain one row per inserted row. In `DatabaseClient`, use `.all()` to receive multiple rows:

```java
public Flux<PersonCreated> insertMany(List<String> names) {
    // Example SQL must be built for the number of rows with bind parameters
    // or use a driver-supported batch/statement mechanism.
    return databaseClient.sql("""
            INSERT INTO person (name)
            VALUES (:name)
            RETURNING id, name, created_at
            """)
        .bind("name", names.get(0))
        .map((row, metadata) -> new PersonCreated(
            row.get("id", Long.class),
            row.get("created_at", OffsetDateTime.class),
            row.get("name", String.class)
        ))
        .all();
}
```

The snippet above only illustrates a single insert with `RETURNING`; it is not a full batch implementation for the entire `names` list. For multiple rows, you can use batch statements or build a multi-values insert statement using supported APIs/drivers. Verify the ordering and number of generated-value rows returned; do not assume every driver preserves order across all batch forms.

If you need to correlate each generated ID with its corresponding input, use a business key or an identifying column returned alongside the ID. Do not rely solely on ordering unless the database/driver guarantees it.

## 15. Distinguishing Generated Values from rowsUpdated

`rowsUpdated()` reports the number of affected rows. It does not automatically return the ID or generated columns.

Example:

```java
Mono<Long> count = databaseClient.sql("""
        INSERT INTO person (name)
        VALUES (:name)
        """)
    .bind("name", name)
    .fetch()
    .rowsUpdated();
```

The result tells you how many rows were inserted, without providing the ID value. If you need the ID, request generated values, use SQL `RETURNING`/`OUTPUT`, or re-read the row via a unique key.

You cannot infer the new ID by querying `MAX(id)` after insert, because concurrent transactions may insert simultaneously. Nor should you assume the ID equals the number of inserted rows or increments by exactly one from the previous ID.

## 16. Impact of Driver and Database Dialect

The R2DBC SPI defines a common contract, but the database and driver determine how returning generated values is actually implemented. When choosing an approach, consider:

- Whether the driver supports `Statement.returnGeneratedValues(...)`.
- Which columns the driver returns: identity only, requested columns, or the entire row.
- Whether the database provides `RETURNING`, `OUTPUT`, or an equivalent mechanism.
- Whether the driver supports generated values for multi-row inserts, updates, and deletes.
- Whether returned data types map cleanly to the desired Java types.
- Whether generated columns or triggers are reflected in the returned results.
- Whether behavior differs across driver or database server versions.

If the application supports multiple DBMSs, do not place a PostgreSQL `RETURNING` statement into a shared layer expecting SQL Server or Oracle to run it. Create dialect-specific implementations or use the common abstraction when drivers consistently support the required capabilities.

## 17. Handling Null Values and Generated Data Types

A generated value can be null if the schema allows it or if the value expression evaluates to null. Mappers should use appropriate reference types:

```java
Long id = row.get("id", Long.class);
OffsetDateTime createdAt = row.get("created_at", OffsetDateTime.class);
```

Do not use primitive types when a column may be null. For timestamps, match the SQL type and driver support. For numeric values, use `BigDecimal` when decimal precision is required. For UUID, enum, JSON, or database-specific types, check converters and actual returned types.

Column names in `returnGeneratedValues` and names used in `row.get(...)` must match the metadata the driver can return. When using `RETURNING`, explicit aliases keep mappers stable:

```sql
INSERT INTO person (name)
VALUES (:name)
RETURNING id AS person_id,
          created_at AS created_time;
```

## 18. Testing Generated Columns

Test on the exact target database and driver planned for deployment:

- Insert omitting identity and receive a valid ID.
- Insert omitting a defaulted column and verify the database populates the default.
- Insert passing explicit null and verify it is not confused with omitting the column.
- Generated/computed columns are calculated accurately from source data by the database.
- Spring Data does not write to properties marked `@ReadOnlyProperty`.
- `Statement.returnGeneratedValues` returns the columns the driver promises to support.
- `RETURNING`/`OUTPUT` returns accurate values after insert/update/delete.
- Re-reading the row returns accurate defaults, generated columns, and trigger-set values.
- Concurrent operations do not cause the application to correlate IDs incorrectly or receive wrong values.
- Transaction rollback leaves no partial data behind.

Testcontainers is helpful for running integration tests against the same database engine. H2 can differ from PostgreSQL or SQL Server in identity, generated columns, triggers, generated-value syntax, and data types; H2 tests do not substitute for testing on the production database.

## 19. Workflow for Choosing How to Retrieve Generated Columns

When a write operation needs values back from the database, follow this sequence:

**Step 1 — List auto-generated columns.** Classify identity, sequence, default, generated/computed, and trigger-generated values.

**Step 2 — Identify columns the application is allowed to write.** Exclude generated columns from insert/update column lists; use `@ReadOnlyProperty` if entity mapping needs read-only markers.

**Step 3 — Choose the appropriate abstraction.** For entity CRUD and auto-generated IDs, prefer Repositories or `R2dbcEntityTemplate`. For direct SQL, use `DatabaseClient`.

**Step 4 — Choose the retrieval mechanism.** Use Spring Data's automatic generated ID, `Statement.returnGeneratedValues`, `RETURNING`/`OUTPUT`, or a post-write SELECT.

**Step 5 — Verify driver and dialect.** Confirm exact columns returned, data types, and version-specific limitations.

**Step 6 — Map into DTO/entity.** Use stable aliases, compatible Java types, and explicit null handling.

**Step 7 — Run integration tests.** Verify defaults, generated columns, triggers, concurrency, and transactions against a real database.

## 20. Conclusion

When the database generates values during write operations, the application must explicitly decide how to retrieve them. Spring Data Repositories and `R2dbcEntityTemplate` handle common generated-ID flows. For direct SQL, `Statement.returnGeneratedValues(...)` provides an R2DBC SPI abstraction, while `RETURNING` and `OUTPUT` leverage DBMS-specific syntax. If the driver does not return the needed columns, the row can be re-queried after writing.

Distinguish identity, default, and generated columns; omit database-managed columns from inserts/updates; use `@ReadOnlyProperty` for read-only properties in mapping; and do not confuse `rowsUpdated()` with generated values. Checking driver behavior, dialect, data types, and running integration tests on a real database ensures the application receives accurate IDs, timestamps, computed values, and trigger-generated data after each write.
