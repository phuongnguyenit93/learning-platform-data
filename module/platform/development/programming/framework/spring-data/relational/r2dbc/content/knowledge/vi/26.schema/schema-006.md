# Thiết kế bảng, chỉ mục và ràng buộc phù hợp truy vấn

Trong ứng dụng Spring Data Relational R2DBC, hiệu năng và tính đúng của truy vấn phụ thuộc rất nhiều vào cách thiết kế schema database. Entity mapping giúp ánh xạ property Java sang bảng và cột, nhưng không thể bù cho khóa chính thiếu ổn định, quan hệ không có foreign key, index sai thứ tự cột hoặc kiểu dữ liệu không phù hợp với điều kiện lọc.

Thiết kế schema tốt bắt đầu từ các truy vấn mà ứng dụng thực sự chạy: tìm một bản ghi theo ID, lọc theo trạng thái, lấy danh sách mới nhất, join dữ liệu theo foreign key, phân trang, đếm số lượng hoặc cập nhật theo điều kiện. Từ các access pattern đó, hãy chọn primary key, foreign key, unique/check/not-null constraints và index. Sau đó kiểm tra execution plan với dữ liệu có quy mô gần thực tế.

Spring Data R2DBC cung cấp mapping metadata qua `@Table`, `@Column`, `@Id`, `@Version` và các API repository/template. Những thành phần này mô tả cách Java object tương ứng với schema. Việc tạo bảng, thay đổi cột, thêm index và constraint nên được quản lý bằng migration có version như Flyway hoặc Liquibase. Không nên xem entity annotation là công cụ thay thế cho thiết kế và triển khai schema.

## 1. Bắt đầu từ truy vấn, không bắt đầu từ danh sách field

Một bảng thường được thiết kế theo dữ liệu nghiệp vụ, nhưng index cần được thiết kế theo cách dữ liệu được đọc và ghi. Trước khi tạo index, hãy liệt kê các truy vấn quan trọng và mô tả:

- Bảng nào được đọc?
- Điều kiện lọc nằm trên cột nào?
- Điều kiện join dùng khóa nào?
- Có sắp xếp theo cột nào và chiều nào?
- Có phân trang bằng `LIMIT/OFFSET` hay cursor không?
- Truy vấn lấy bao nhiêu cột và có cần aggregate không?
- Tần suất đọc/ghi và kích thước dữ liệu dự kiến là bao nhiêu?

Ví dụ một màn hình customer có thể chạy các truy vấn:

| Access pattern | SQL tiêu biểu | Schema cần chú ý |
| --- | --- | --- |
| Tìm theo ID | `WHERE id = :id` | Primary key/index trên `id` |
| Tìm customer theo email | `WHERE email = :email` | Unique constraint/index nếu email duy nhất |
| Lọc customer đang hoạt động | `WHERE status = 'ACTIVE'` | Index phụ thuộc selectivity và các truy vấn đi kèm |
| Danh sách theo tenant, mới nhất | `WHERE tenant_id = :tenant ORDER BY created_at DESC, id DESC` | Composite index theo filter và sort |
| Lấy order của customer | `WHERE customer_id = :id ORDER BY created_at DESC` | Index trên `orders.customer_id` và có thể thêm cột sort |
| Đếm order theo customer | `WHERE customer_id = :id` | Index foreign key có thể hỗ trợ |
| Phân trang tiếp theo | Predicate theo `(created_at, id)` | Composite index khớp cursor và sort |

Không nên tạo một index riêng cho mọi cột chỉ vì cột đó xuất hiện trong entity. Index cần hỗ trợ một truy vấn cụ thể hoặc một nhóm truy vấn có cùng access pattern. Index thừa làm tăng dung lượng, chi phí insert/update/delete và công việc bảo trì của database.

## 2. Thiết kế bảng theo entity và aggregate

Spring Data Relational ánh xạ entity vào bảng quan hệ. Một entity đơn giản có thể khai báo:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("tenant_id")
    private UUID tenantId;

    private String email;

    private String name;

    private String status;

    // Constructor, getter và setter.
}
```

`@Table` xác định tên bảng, `@Column` ánh xạ property sang cột và `@Id` đánh dấu identifier. Các annotation này không tự chứng minh rằng cột đã tồn tại hoặc schema có constraint/index đúng. Database migration cần tạo schema tương ứng.

### Chuẩn hóa dữ liệu

Chuẩn hóa giúp tránh lưu trùng dữ liệu và giữ tính nhất quán. Ví dụ, nếu nhiều order thuộc một customer, thông tin tên/email customer thường được lưu ở bảng `customer`, còn bảng `orders` lưu `customer_id` làm foreign key.

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    order_number VARCHAR(40) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL
);
```

Nếu lưu lại `customer_name` trong mọi order, tên có thể không đồng bộ khi customer đổi tên. Tuy nhiên, có những trường hợp lưu snapshot là chủ ý, ví dụ tên và địa chỉ giao hàng tại thời điểm đặt hàng. Khi đó dữ liệu lặp có ý nghĩa lịch sử và không phải lỗi chuẩn hóa.

Thiết kế bảng nên phân biệt dữ liệu tham chiếu hiện tại với snapshot nghiệp vụ bất biến. Đừng join ngược về dữ liệu hiện tại nếu nghiệp vụ cần giữ nguyên thông tin tại thời điểm giao dịch.

## 3. Chọn primary key

Primary key định danh duy nhất một hàng và là mục tiêu của các quan hệ foreign key. Một khóa tốt cần ổn định, không null và duy nhất.

### Khóa số tự tăng

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Ưu điểm:

- Nhỏ gọn, dễ join và truyền qua API.
- Index thường gọn hơn khóa chuỗi dài.
- Tăng tuần tự có thể giúp locality của B-tree index đối với insert thông thường.

Điểm cần cân nhắc:

- ID có thể tiết lộ gần đúng thứ tự hoặc quy mô bản ghi.
- Khi ghi dữ liệu từ nhiều hệ thống độc lập, cần chiến lược cấp ID phù hợp.
- Không nên giả định sequence không bao giờ có khoảng trống; rollback hoặc cấp ID trước insert có thể tạo gap.

### UUID

```sql
id UUID PRIMARY KEY
```

UUID thuận tiện khi cần tạo identifier ở ứng dụng hoặc nhiều node mà không phải xin sequence chung. Tuy nhiên, UUID có kích thước lớn hơn `BIGINT`; UUID ngẫu nhiên có thể làm index phân tán và tăng page split/cache pressure tùy database và workload. Nếu chọn UUID, cân nhắc UUID có tính locality như UUIDv7 nếu hệ sinh thái hỗ trợ và yêu cầu bảo mật/khả năng đoán phù hợp.

### Khóa tự nhiên và khóa thay thế

Email, mã đơn hàng hoặc mã sản phẩm có thể là khóa nghiệp vụ. Chúng thường nên được bảo vệ bằng unique constraint, nhưng không nhất thiết phải làm primary key. Có thể dùng một surrogate key như `BIGINT`/`UUID` làm PK và thêm unique constraint cho khóa nghiệp vụ.

Ví dụ:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    CONSTRAINT uk_customer_email UNIQUE (email)
);
```

Nếu quy tắc duy nhất phụ thuộc tenant:

```sql
CONSTRAINT uk_customer_tenant_email UNIQUE (tenant_id, email)
```

Hãy đưa đúng phạm vi nghiệp vụ vào unique constraint. Nếu email chỉ cần duy nhất trong một tenant, unique riêng trên `email` sẽ quá chặt; nếu email phải duy nhất toàn hệ thống, unique trên `(tenant_id, email)` lại chưa đủ.

## 4. Foreign key bảo vệ quan hệ

Foreign key đảm bảo giá trị tham chiếu trỏ tới một hàng hợp lệ ở bảng cha:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customer(id)
);
```

`NOT NULL` trên `customer_id` thể hiện order bắt buộc phải có customer. Nếu quan hệ là tùy chọn, cột có thể nullable và foreign key chỉ kiểm tra khi giá trị không null.

Foreign key bảo vệ tính toàn vẹn dữ liệu kể cả khi ghi đến từ nhiều service, job hoặc SQL trực tiếp. Chỉ kiểm tra trong Java là chưa đủ vì hai request đồng thời có thể cùng vượt qua kiểm tra trước khi một bên xóa hàng cha.

### Index trên foreign key

Nhiều database tự tạo index cho primary key và unique constraint, nhưng không phải database nào cũng tự tạo index ở cột tham chiếu foreign key. Ví dụ PostgreSQL không tự tạo index trên `orders.customer_id` chỉ vì khai báo foreign key.

Nếu ứng dụng thường chạy:

```sql
SELECT id, order_number
FROM orders
WHERE customer_id = :customerId;
```

hãy cân nhắc:

```sql
CREATE INDEX idx_orders_customer_id
ON orders(customer_id);
```

Index này cũng có thể giúp database tìm các order cần kiểm tra khi customer bị xóa hoặc cập nhật khóa tham chiếu, tránh scan toàn bộ bảng con trong những tình huống phù hợp.

### ON DELETE và ON UPDATE

Foreign key có thể khai báo hành vi khi hàng cha bị xóa:

```sql
FOREIGN KEY (customer_id)
    REFERENCES customer(id)
    ON DELETE RESTRICT
```

Các lựa chọn phổ biến:

| Hành vi | Ý nghĩa |
| --- | --- |
| `RESTRICT` / `NO ACTION` | Ngăn xóa hàng cha khi còn hàng con tham chiếu, theo semantics của database |
| `CASCADE` | Xóa hàng con khi xóa hàng cha |
| `SET NULL` | Đặt khóa ngoại ở hàng con thành NULL nếu cho phép |
| `SET DEFAULT` | Đặt giá trị mặc định nếu database hỗ trợ và giá trị đó hợp lệ |

Chỉ dùng `CASCADE` khi vòng đời dữ liệu con thực sự phụ thuộc dữ liệu cha. Xóa customer không nên tự động xóa hóa đơn hoặc dữ liệu pháp lý cần lưu lâu dài. Hành vi cascade có thể tác động nhiều hàng và tạo tải lớn; cần hiểu rõ phạm vi trước khi áp dụng.

## 5. Dùng NOT NULL, DEFAULT và CHECK constraint

Constraint giúp database bảo vệ quy tắc dữ liệu ngay tại nơi lưu trữ.

### NOT NULL

```sql
email VARCHAR(320) NOT NULL,
status VARCHAR(20) NOT NULL
```

Dùng `NOT NULL` cho property bắt buộc. Nếu cột bắt buộc trong nghiệp vụ, chỉ kiểm tra `@NotNull` ở Java không đủ để bảo vệ dữ liệu từ mọi đường ghi. Database constraint là lớp bảo vệ cuối cùng.

### DEFAULT

```sql
status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
```

`DEFAULT` được dùng khi câu lệnh insert bỏ qua cột hoặc dùng từ khóa `DEFAULT`. Nếu ứng dụng luôn bind `NULL`, default thông thường không tự thay null thành giá trị mặc định. Cần phân biệt không truyền cột với truyền SQL NULL.

### CHECK

```sql
CONSTRAINT ck_orders_total_nonnegative
    CHECK (total_amount >= 0)
```

Constraint này ngăn giá trị âm được lưu. Một số quy tắc phức tạp liên quan nhiều hàng/bảng không thể diễn đạt bằng CHECK đơn giản; cần unique/FK, trigger hoặc transaction logic tùy nghiệp vụ.

Ví dụ trạng thái chỉ nhận một tập giá trị:

```sql
CONSTRAINT ck_customer_status
    CHECK (status IN ('ACTIVE', 'INACTIVE', 'PENDING'))
```

CHECK là ràng buộc ở database, giúp dữ liệu không hợp lệ bị chặn dù thao tác đến từ repository, batch import hay SQL trực tiếp. Nếu dùng native enum hoặc kiểu riêng của database, cần cân nhắc khả năng migration và tương thích giữa môi trường.

## 6. Unique constraint khác với kiểm tra tồn tại trong ứng dụng

Một mẫu không an toàn là:

```java
return repository.findByEmail(email)
        .hasElement()
        .flatMap(exists -> exists
                ? Mono.error(new DuplicateEmailException())
                : repository.save(new Customer(email)));
```

Hai request đồng thời có thể cùng đọc `false` rồi cùng insert. Kiểm tra tồn tại chỉ hỗ trợ thông báo thân thiện, không thay thế unique constraint.

Hãy tạo constraint:

```sql
ALTER TABLE customer
ADD CONSTRAINT uk_customer_email UNIQUE (email);
```

Sau đó xử lý lỗi duplicate key theo nghiệp vụ. Có thể kiểm tra trước để hiển thị lỗi sớm, nhưng database vẫn phải là nơi bảo đảm tính duy nhất.

### Unique constraint có thể cho phép nhiều NULL

Semantics unique với `NULL` khác nhau theo database. Nhiều hệ quản trị coi các NULL là không bằng nhau và cho phép nhiều hàng null trong unique index; một số hệ hỗ trợ `NULLS NOT DISTINCT` hoặc cú pháp riêng. Nếu cột cần duy nhất và bắt buộc, kết hợp `NOT NULL` với `UNIQUE` để tránh khác biệt này.

## 7. Index B-tree cho equality và range query

B-tree là loại index mặc định/phổ biến cho các truy vấn equality, range và sort trong nhiều hệ quản trị quan hệ.

Ví dụ:

```sql
CREATE INDEX idx_customer_status
ON customer(status);
```

Có thể hỗ trợ:

```sql
SELECT id, name
FROM customer
WHERE status = 'ACTIVE';
```

Và một số điều kiện range/sort phù hợp tùy database. Tuy nhiên, nếu `status` chỉ có vài giá trị và phần lớn hàng cùng giá trị, index đơn trên status có thể không chọn lọc đủ tốt để rẻ hơn sequential scan. Optimizer có thể chủ động bỏ qua index khi đọc phần lớn bảng là phương án rẻ hơn.

Index không phải lúc nào cũng giúp query. Hãy xem số hàng phù hợp, độ chọn lọc, kích thước bảng và query plan.

## 8. Composite index và thứ tự cột

Composite index chứa nhiều cột theo một thứ tự cụ thể:

```sql
CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC);
```

Index này có thể hỗ trợ truy vấn:

```sql
SELECT id, order_number, created_at
FROM orders
WHERE customer_id = :customerId
  AND status = :status
ORDER BY created_at DESC;
```

Thứ tự cột trong index quan trọng. Với B-tree, các cột ở đầu index thường quyết định khả năng tìm một vùng liên tiếp phù hợp. Một index `(customer_id, status, created_at)` không tương đương với `(status, customer_id, created_at)`.

### Quy tắc leftmost prefix

Trong nhiều B-tree implementation, index `(a, b, c)` hữu ích nhất cho các predicate bắt đầu từ `a`, ví dụ:

- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c >= ?`

Nó thường không hiệu quả tương đương cho `WHERE b = ?` nếu không có điều kiện trên `a`. Chi tiết optimizer có thể khác theo database, nhưng không nên kỳ vọng index composite tự phục vụ tốt mọi tổ hợp cột.

### Equality, range và sort

Một nguyên tắc khởi đầu hữu ích khi thiết kế composite index là:

1. Các cột thường được lọc bằng equality (`=`) hoặc tenant/partition scope.
2. Cột range (`>`, `<`, `BETWEEN`) và cột dùng để seek.
3. Các cột sort còn lại theo đúng thứ tự và chiều truy vấn cần.

Đây không phải công thức tuyệt đối. Nếu query có nhiều pattern khác nhau, sort hỗn hợp hoặc predicate có độ chọn lọc đặc biệt, hãy kiểm tra execution plan. Index phải khớp query thực tế chứ không chỉ khớp một quy tắc lý thuyết.

Ví dụ truy vấn danh sách order theo tenant và thời gian:

```sql
SELECT id, created_at, total_amount
FROM orders
WHERE tenant_id = :tenantId
  AND status = 'PAID'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Index ứng viên:

```sql
CREATE INDEX idx_orders_tenant_status_created_id
ON orders(tenant_id, status, created_at DESC, id DESC);
```

Hai cột đầu hỗ trợ equality filter; các cột sau hỗ trợ thứ tự. Cần đo với cardinality thật và kiểm tra optimizer có sử dụng index không.

## 9. Index cho ORDER BY và pagination

Một truy vấn phân trang cần thứ tự xác định:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100;
```

Index ứng viên:

```sql
CREATE INDEX idx_article_status_created_id
ON article(status, created_at DESC, id DESC);
```

Index có thể giúp database lọc theo status và duyệt theo thứ tự yêu cầu. Thêm `id` làm tie-breaker duy nhất để phân trang ổn định khi nhiều bài có cùng `created_at`.

### Keyset pagination

Với cursor `(created_at, id)` theo thứ tự giảm dần:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
  AND (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Index `(status, created_at DESC, id DESC)` là ứng viên phù hợp. Tuple comparison và cách tối ưu phụ thuộc database; có thể viết predicate lexicographic bằng `OR` nếu dialect không hỗ trợ tuple comparison theo cách cần thiết.

Nếu sort key nullable, cần xác định `NULLS FIRST/LAST` và predicate cursor tương ứng. Đơn giản nhất thường là chọn sort key `NOT NULL`.

## 10. Index cho JOIN và foreign key

Join thường dùng equality giữa khóa ngoại và khóa chính:

```sql
SELECT c.id, c.name, o.id AS order_id
FROM customer c
JOIN orders o ON o.customer_id = c.id
WHERE c.id = :customerId;
```

Primary key của customer đã có index. Để tìm các order theo customer, index trên `orders.customer_id` thường hữu ích:

```sql
CREATE INDEX idx_orders_customer_id
ON orders(customer_id);
```

Nếu truy vấn thường lấy order theo customer và sắp xếp theo thời gian:

```sql
SELECT id, order_number, created_at
FROM orders
WHERE customer_id = :customerId
ORDER BY created_at DESC, id DESC;
```

Index `(customer_id, created_at DESC, id DESC)` có thể phục vụ cả predicate và sort. Tránh tạo đồng thời index đơn `customer_id` và composite index bắt đầu bằng `customer_id` nếu không có workload khác chứng minh index đơn vẫn cần; index thừa làm tăng chi phí ghi.

### Many-to-many

Với quan hệ nhiều-nhiều, dùng bảng nối:

```sql
CREATE TABLE customer_group (
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    group_id BIGINT NOT NULL REFERENCES customer_group_type(id),
    PRIMARY KEY (customer_id, group_id)
);
```

Primary key composite `(customer_id, group_id)` hỗ trợ tra cứu group theo customer và ngăn liên kết trùng. Nếu ứng dụng cũng thường tra ngược group sang customer, thêm index theo chiều ngược:

```sql
CREATE INDEX idx_customer_group_group_customer
ON customer_group(group_id, customer_id);
```

Một index composite không tự phục vụ hiệu quả cả hai hướng nếu cột cần tìm không ở prefix phù hợp.

## 11. Covering index và INCLUDE

Một truy vấn có thể chỉ cần một vài cột:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Ở PostgreSQL, có thể cân nhắc `INCLUDE` để lưu thêm payload trong leaf pages của index:

```sql
CREATE INDEX idx_article_status_created_id_cover
ON article(status, created_at DESC, id DESC)
INCLUDE (title);
```

Điều này có thể cho phép index-only scan khi điều kiện visibility map và query phù hợp. `INCLUDE` là cú pháp riêng của PostgreSQL và không phải database nào cũng hỗ trợ giống vậy.

Không nên đưa mọi cột của bảng vào index chỉ để tạo covering index. Payload lớn làm index phình to, giảm cache efficiency và tăng chi phí ghi. Chỉ thêm cột được truy vấn thường xuyên và có lợi ích đo được.

## 12. Partial index cho tập dữ liệu thường xuyên truy vấn

Một số database hỗ trợ partial/filtered index, chỉ index các hàng thỏa predicate. Ví dụ PostgreSQL:

```sql
CREATE INDEX idx_orders_pending_created
ON orders(created_at DESC, id DESC)
WHERE status = 'PENDING';
```

Index này có thể nhỏ hơn index trên toàn bảng nếu hàng `PENDING` chiếm tỷ lệ thấp. Nó phù hợp với query có điều kiện tương ứng:

```sql
SELECT id, created_at
FROM orders
WHERE status = 'PENDING'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Optimizer chỉ dùng partial index khi có thể chứng minh predicate query phù hợp với predicate index. Nếu query dùng điều kiện tổng quát hoặc parameterized predicate khiến planner không chứng minh được quan hệ, index có thể không được chọn trong một số plan.

Partial index là tính năng phụ thuộc database; kiểm tra cú pháp và execution plan thực tế. Không dùng nó nếu cần portability tuyệt đối giữa nhiều hệ quản trị.

## 13. Expression index và truy vấn không phân biệt hoa/thường

Nếu ứng dụng thường tìm email không phân biệt hoa/thường, truy vấn có thể dùng biểu thức:

```sql
SELECT id, email
FROM customer
WHERE LOWER(email) = LOWER(:email);
```

Index thông thường trên `email` có thể không hỗ trợ hiệu quả biểu thức `LOWER(email)`. Với PostgreSQL, có thể tạo expression index:

```sql
CREATE UNIQUE INDEX uk_customer_email_lower
ON customer(LOWER(email));
```

Index này vừa hỗ trợ lookup theo biểu thức, vừa bảo vệ quy tắc không phân biệt hoa/thường nếu đó là semantics nghiệp vụ mong muốn. Tuy nhiên, cần cân nhắc collation/Unicode và việc lưu email chuẩn hóa.

Một lựa chọn khác là lưu giá trị canonical đã chuẩn hóa vào cột riêng, ví dụ `email_normalized`, rồi tạo unique index trên cột đó. Cách này làm rõ semantics nhưng cần bảo đảm mọi đường ghi cập nhật cột canonical đồng bộ.

Expression index là tính năng database-specific. Nếu dùng Spring Data derived query `IgnoreCase`, hãy kiểm tra SQL được sinh và đảm bảo index phù hợp với biểu thức thực tế mà dialect dùng.

## 14. Index cho LIKE và tìm kiếm chuỗi

B-tree thường có thể hỗ trợ prefix search như:

```sql
WHERE name LIKE 'Lan%'
```

nhưng không thường hỗ trợ hiệu quả pattern bắt đầu bằng wildcard:

```sql
WHERE name LIKE '%Lan%'
```

Khả năng tối ưu còn phụ thuộc collation, operator class và database. Với PostgreSQL, có thể dùng `pg_trgm` và GIN/GiST index cho tìm kiếm substring/fuzzy phù hợp:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_customer_name_trgm
ON customer USING gin (name gin_trgm_ops);
```

Đây là ví dụ riêng PostgreSQL. Với full-text search, nên cân nhắc full-text index/search vector thay vì cố dùng B-tree cho mọi truy vấn `Containing`.

Trong Spring Data, `Containing`, `StartingWith` hoặc `Like` tạo semantics lọc chuỗi. Index cần khớp pattern và collation thật; không thể kết luận rằng có index trên cột chuỗi thì mọi truy vấn LIKE đều nhanh.

## 15. Index cho cột boolean và low-cardinality

Cột như `active`, `enabled` hoặc `status` có ít giá trị phân biệt. Index đơn trên boolean thường ít chọn lọc nếu phần lớn hàng có cùng giá trị. Ví dụ:

```sql
CREATE INDEX idx_customer_active
ON customer(active);
```

có thể không giúp query `WHERE active = true` nếu 95% bảng đều true. Optimizer có thể chọn sequential scan.

Index composite có thể phù hợp hơn khi boolean đi cùng tenant hoặc sort:

```sql
CREATE INDEX idx_customer_tenant_active_created
ON customer(tenant_id, active, created_at DESC, id DESC);
```

Hoặc partial index trên subset hiếm gặp nếu database hỗ trợ:

```sql
CREATE INDEX idx_customer_inactive
ON customer(created_at DESC)
WHERE active = false;
```

Hãy xem selectivity và phân bố dữ liệu. Low-cardinality không có nghĩa tuyệt đối không nên index; nó có thể hữu ích khi kết hợp với cột khác hoặc khi một giá trị rất hiếm.

## 16. Index có chi phí ghi

Mỗi index bổ sung cần được cập nhật khi insert, delete hoặc thay đổi cột thuộc index. Một bảng có quá nhiều index có thể:

- Insert chậm hơn vì phải thêm entry vào nhiều index.
- Update chậm hơn nếu sửa cột được index.
- Delete tốn thêm công việc xóa entry.
- Tốn disk và cache memory.
- Tăng thời gian vacuum/maintenance hoặc rebuild tùy database.
- Làm migration thêm index lớn kéo dài và ảnh hưởng tải hệ thống.

Vì vậy, hãy đánh giá tổng workload đọc/ghi. Một index giúp query hiếm khi chạy nhưng làm chậm mọi insert có thể không đáng giữ. Theo dõi index usage và workload trước khi xóa index; không xóa chỉ vì thống kê ngắn hạn cho thấy ít được dùng.

## 17. Kiểu dữ liệu phù hợp với điều kiện truy vấn

Kiểu cột ảnh hưởng kích thước hàng/index, semantics so sánh, khả năng bind và cách database tối ưu.

### Numeric

- Dùng `BIGINT` cho số nguyên có miền giá trị lớn hơn `INTEGER`.
- Dùng `NUMERIC/DECIMAL(p,s)` cho tiền và giá trị cần precision thập phân chính xác.
- Tránh `FLOAT/DOUBLE` cho phép tính tiền cần chính xác decimal.
- Chọn precision/scale phù hợp nghiệp vụ, không đặt tùy tiện quá lớn.

### Chuỗi

- Chọn độ dài giới hạn phù hợp nếu database hỗ trợ và nghiệp vụ có giới hạn.
- Unique index trên chuỗi dài có thể tốn dung lượng.
- Cân nhắc collation, case sensitivity và Unicode khi thiết kế tìm kiếm/unique.
- Không dùng kiểu text lớn làm khóa join nếu có thể dùng ID nhỏ, ổn định.

### Thời gian

- Chọn kiểu timestamp có semantics timezone rõ ràng.
- Dùng `Instant` cho mốc thời gian tuyệt đối nếu phù hợp mapping/driver.
- Chuẩn hóa quy ước UTC ở tầng ứng dụng.
- Index cột thời gian khi query thường lọc theo khoảng hoặc sort theo thời gian.
- Nếu query luôn lọc tenant và khoảng thời gian, composite index `(tenant_id, created_at)` có thể phù hợp hơn index đơn `created_at`.

### UUID

UUID tiện cho định danh phân tán nhưng index lớn hơn numeric key. Chọn representation native UUID nếu database hỗ trợ, thay vì tùy tiện lưu thành chuỗi 36 ký tự. Mapping Java `UUID` cần driver codec tương ứng.

### JSON/JSONB

JSON phù hợp với dữ liệu linh hoạt, ít dùng làm khóa quan hệ. Nếu truy vấn thường xuyên theo một field JSON, cân nhắc expression index hoặc generated/computed column theo database. Nếu field là thuộc tính cốt lõi cần filter/join/sort liên tục, cột quan hệ có kiểu rõ ràng thường dễ tối ưu và ràng buộc hơn.

## 18. Thiết kế schema cho tenant isolation

Ứng dụng multi-tenant thường lọc dữ liệu theo `tenant_id`. Nếu mọi truy vấn luôn có tenant scope, cột tenant nên được xem là một phần quan trọng của access pattern.

Ví dụ:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
```

Query:

```sql
SELECT id, status, created_at
FROM orders
WHERE tenant_id = :tenantId
  AND status = :status
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Index ứng viên:

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders(tenant_id, status, created_at DESC, id DESC);
```

Nếu khóa ngoại customer cũng cần bảo đảm không tham chiếu sang tenant khác, chỉ foreign key `customer_id -> customer.id` có thể chưa đủ để thể hiện quy tắc tenant. Có thể dùng composite unique/foreign key theo `(tenant_id, customer_id)` nếu schema và database hỗ trợ:

```sql
ALTER TABLE customer
ADD CONSTRAINT uk_customer_tenant_id
UNIQUE (tenant_id, id);

ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer_tenant
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customer(tenant_id, id);
```

Thiết kế này giúp database bảo vệ quan hệ cùng tenant, nhưng cần cân nhắc index và unique constraint tương ứng. Ở tầng ứng dụng vẫn cần kiểm tra authorization; foreign key không thay thế kiểm soát truy cập.

## 19. Index và constraint cho query derived của Spring Data

Tên method repository giúp tạo query, nhưng không tự tạo index. Ví dụ:

```java
Flux<Customer> findByStatusAndCreatedAtAfterOrderByCreatedAtDesc(
        String status,
        Instant after
);
```

Query tương ứng có điều kiện equality trên `status`, range trên `created_at` và sort theo `created_at`. Index ứng viên có thể là:

```sql
CREATE INDEX idx_customer_status_created
ON customer(status, created_at DESC);
```

Nếu query luôn theo tenant:

```java
Flux<Customer> findByTenantIdAndStatusOrderByCreatedAtDesc(
        UUID tenantId,
        String status
);
```

index ứng viên:

```sql
CREATE INDEX idx_customer_tenant_status_created
ON customer(tenant_id, status, created_at DESC, id DESC);
```

Các index trên chỉ là ứng viên dựa trên access pattern. Cần kiểm tra SQL thực tế do Spring Data/dialect tạo, đặc biệt với `IgnoreCase`, `Containing`, `In`, sort động và property mapping. Query method không bảo đảm optimizer dùng index.

### Derived query `In`

```java
Flux<Order> findByCustomerIdIn(Collection<Long> customerIds);
```

Index trên `customer_id` có thể hỗ trợ lookup. Nhưng danh sách ID rất lớn có thể tạo nhiều bind parameters hoặc kế hoạch query kém; chia batch hoặc dùng giải pháp database-specific khi cần.

### Count và exists

Các method `countByStatus` và `existsByEmail` cũng cần được xem xét theo predicate. `existsByEmail` được hỗ trợ tốt bởi unique index trên email. `countByStatus` có thể cần scan nhiều hàng nếu status có cardinality thấp; index chỉ có lợi khi optimizer và workload chứng minh được.

## 20. Index cho truy vấn join nhiều bảng

Giả sử endpoint lấy order cùng customer:

```sql
SELECT o.id, o.created_at, c.name
FROM orders o
JOIN customer c ON c.id = o.customer_id
WHERE o.status = :status
ORDER BY o.created_at DESC, o.id DESC
LIMIT 50;
```

Các index có thể xem xét:

```sql
CREATE INDEX idx_orders_status_created_id
ON orders(status, created_at DESC, id DESC);

-- customer.id đã được index bởi primary key.
```

Nếu query bắt đầu từ customer rồi lọc order theo `customer_id`, index trên `orders(customer_id, ...)` có thể phù hợp hơn. Index tối ưu phụ thuộc join order mà optimizer chọn và độ chọn lọc của predicate.

Với one-to-many, index foreign key ở bảng con thường quan trọng. Nếu có thêm filter theo trạng thái và sort thời gian:

```sql
CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC, id DESC);
```

Không nên tạo cả mọi biến thể index trước khi đo. Hãy lấy các truy vấn chậm nhất, kiểm tra plan và chọn index giải quyết đúng bottleneck.

## 21. Ràng buộc và index cho upsert

Một thao tác upsert thường dựa vào unique constraint để xác định conflict:

```sql
INSERT INTO customer (email, name)
VALUES (:email, :name)
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name;
```

Đây là cú pháp PostgreSQL. Conflict target `(email)` cần có unique constraint hoặc unique index phù hợp. Không thể chỉ dựa vào một index không unique để bảo đảm upsert không tạo duplicate.

Nếu quy tắc duy nhất theo tenant, conflict target phải phù hợp:

```sql
ON CONFLICT (tenant_id, email)
DO UPDATE SET name = EXCLUDED.name
```

Với Spring Data R2DBC, câu lệnh có thể được thực hiện qua `DatabaseClient` hoặc `@Query` phù hợp. Spring Data không tự suy luận upsert chỉ từ `save`; `save` dùng newness detection và persistence semantics riêng. Khi cần upsert atomic theo unique key, hãy viết SQL theo database và kiểm thử kết quả.

## 22. Version column cho optimistic locking

Nếu nhiều request có thể cùng sửa một entity, `@Version` giúp phát hiện update dựa trên entity stale:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Version
    private Long version;

    private String name;
}
```

Schema cần cột version:

```sql
version BIGINT NOT NULL DEFAULT 0
```

Spring Data R2DBC có thể sử dụng version trong điều kiện update và tăng version theo entity persistence path được hỗ trợ. Nếu update trực tiếp bằng SQL, ứng dụng phải tự viết điều kiện version và tăng version:

```sql
UPDATE customer
SET name = :name,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

Index trên primary key thường đủ để tìm hàng theo ID; version được kiểm tra sau khi tìm hàng. Không nhất thiết tạo index riêng `(id, version)` vì `id` đã duy nhất, trừ khi query pattern/plan đặc biệt chứng minh có lợi.

## 23. Schema cho quan hệ aggregate trong Spring Data Relational

Spring Data Relational tập trung vào aggregate root. Các object con thuộc aggregate có thể được ánh xạ qua `@MappedCollection` theo mô hình được hỗ trợ.

Ví dụ:

```java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private List<PurchaseOrderLine> lines;
}
```

Schema:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE purchase_order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES purchase_order(id),
    product_code VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);

CREATE INDEX idx_purchase_order_line_order
ON purchase_order_line(order_id);
```

`idColumn = "order_id"` cần khớp cột tham chiếu root trong bảng con. Index trên `order_id` hỗ trợ tìm các line thuộc order. `@MappedCollection` không phải lazy loading như JPA; hãy hiểu rõ aggregate persistence và truy vấn mà Spring Data thực hiện trong phiên bản dự án.

## 24. Quản lý schema bằng migration

Spring Data R2DBC chủ yếu đảm nhiệm mapping và truy cập dữ liệu; không nên phụ thuộc vào việc ứng dụng tự tạo schema từ entity ở môi trường production. Dùng migration có version để quản lý thay đổi bảng, index và constraint.

Ví dụ migration SQL:

```sql
-- V001__create_customer.sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    email VARCHAR(320) NOT NULL,
    name VARCHAR(200) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT ck_customer_status
        CHECK (status IN ('ACTIVE', 'INACTIVE', 'PENDING')),
    CONSTRAINT uk_customer_tenant_email
        UNIQUE (tenant_id, email)
);
```

Migration tiếp theo thêm index:

```sql
-- V002__index_customer_lookup.sql
CREATE INDEX idx_customer_tenant_status_created
ON customer(tenant_id, status, created_at DESC, id DESC);
```

Migration tách riêng giúp thay đổi schema được review, triển khai và rollback theo quy trình. Tên migration và cú pháp phụ thuộc công cụ; ví dụ trên theo quy ước phổ biến của Flyway.

### Thêm index trên bảng lớn

Với bảng production lớn, tạo index có thể khóa hoặc ảnh hưởng workload tùy database. PostgreSQL hỗ trợ `CREATE INDEX CONCURRENTLY` để giảm blocking ghi trong nhiều trường hợp, nhưng câu lệnh này có giới hạn transaction và cần triển khai migration phù hợp. Database khác có cú pháp online index riêng.

Không nên chạy migration thêm index lớn mà không đánh giá lock, disk, replication lag và thời gian thực hiện. Thử trên bản sao dữ liệu có kích thước gần production.

## 25. Thay đổi constraint trên dữ liệu đã có

Thêm `NOT NULL`, unique hoặc foreign key vào bảng đang có dữ liệu có thể thất bại nếu dữ liệu hiện tại vi phạm.

Quy trình an toàn thường gồm:

1. Kiểm tra và làm sạch hàng vi phạm trước.
2. Thêm cột nullable hoặc constraint ở trạng thái phù hợp với database.
3. Backfill dữ liệu theo batch nếu bảng lớn.
4. Kiểm tra lại không còn null/duplicate/orphan.
5. Thêm constraint cuối cùng và chuyển cột sang `NOT NULL` nếu cần.
6. Cập nhật ứng dụng để luôn ghi giá trị hợp lệ.

Ví dụ kiểm tra duplicate trước khi thêm unique:

```sql
SELECT tenant_id, email, COUNT(*)
FROM customer
GROUP BY tenant_id, email
HAVING COUNT(*) > 1;
```

Kiểm tra orphan trước khi thêm foreign key:

```sql
SELECT o.customer_id
FROM orders o
LEFT JOIN customer c ON c.id = o.customer_id
WHERE c.id IS NULL;
```

Đừng thêm constraint trong production rồi mới phát hiện dữ liệu cũ không hợp lệ. Migration cần có bước kiểm tra và kế hoạch xử lý dữ liệu.

## 26. Kiểm tra index bằng EXPLAIN

Sau khi tạo index, cần xác nhận database có dùng nó. Ví dụ PostgreSQL:

```sql
EXPLAIN
SELECT id, name
FROM customer
WHERE tenant_id = :tenantId
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Khi cần số liệu thực tế, PostgreSQL hỗ trợ:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
FROM customer
WHERE tenant_id = '00000000-0000-0000-0000-000000000001'
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

`EXPLAIN ANALYZE` thực sự chạy câu query. Chỉ dùng trên môi trường production khi hiểu tác động của truy vấn. Với các database khác, cú pháp và thông tin plan khác nhau.

Quan sát:

- Loại scan được chọn: sequential/table scan, index scan, index-only scan hoặc bitmap scan.
- Có sort riêng hay index đã cung cấp thứ tự.
- Estimated rows so với actual rows.
- Số hàng đi qua từng node.
- Buffer/page đọc và thời gian thực tế.
- Join strategy: nested loop, hash join, merge join hoặc lựa chọn tương ứng của database.
- Query plan có thay đổi theo giá trị bind/selectivity hay không.

Nếu index không được dùng, không nhất thiết index vô ích. Optimizer có thể thấy scan toàn bảng rẻ hơn vì query lấy phần lớn dữ liệu. Ngược lại, plan dùng index cũng chưa chắc nhanh nếu có quá nhiều random heap reads.

## 27. Statistics và dữ liệu thực tế

Optimizer dựa vào statistics để ước tính số hàng phù hợp. Khi dữ liệu thay đổi lớn mà statistics cũ, database có thể chọn plan kém.

Các điểm cần quan sát:

- Phân bố giá trị của cột lọc.
- Tỷ lệ NULL.
- Số giá trị distinct/cardinality.
- Tương quan giữa các cột trong composite predicate.
- Tần suất insert/update/delete.
- Statistics được cập nhật đúng theo cơ chế database hay chưa.

Một index hoạt động tốt với dữ liệu test vài trăm hàng có thể không phù hợp với production hàng triệu hàng. Hãy tạo dữ liệu benchmark có phân bố gần thực tế và đo cả trường hợp phổ biến lẫn trường hợp hiếm.

## 28. Tích hợp schema với mapping R2DBC

Schema và entity mapping phải thống nhất về tên, kiểu và nullability.

Ví dụ:

```java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    @Column("order_number")
    private String orderNumber;

    @Column("created_at")
    private Instant createdAt;

    @Version
    private Long version;
}
```

Schema tương ứng cần có:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    order_number VARCHAR(40) NOT NULL UNIQUE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC, id DESC);
```

Các điểm cần khớp:

- `@Table("orders")` tương ứng table `orders`.
- `@Column("customer_id")` tương ứng cột `customer_id`.
- `@Id` tương ứng primary key.
- `@Version` tương ứng cột version và semantics optimistic locking.
- `Instant` cần kiểu SQL/codec tương thích.
- `NOT NULL` trong schema cần được phản ánh trong validation/domain model.

Mapping metadata không thay thế constraint database. Ngược lại, constraint không tự tạo property trong Java. Hai lớp cần được thiết kế đồng bộ.

## 29. Kiểm thử constraint và index

Integration test với database/driver thật nên xác nhận:

- Insert thiếu field bắt buộc bị database từ chối.
- Unique constraint chặn duplicate theo đúng phạm vi tenant/business key.
- Foreign key chặn orphan reference.
- Check constraint chặn giá trị ngoài miền.
- Default được áp dụng khi cột bị bỏ khỏi INSERT, và hiểu rõ hành vi khi bind NULL.
- `@Version` mapping khớp cột version.
- Các query quan trọng trả kết quả đúng với schema/index hiện tại.
- Query plan ở môi trường benchmark có sử dụng access path mong muốn khi phù hợp.

Không nên viết unit test giả lập optimizer để khẳng định index được sử dụng. Index usage và query plan là hành vi của database; cần kiểm tra bằng integration/performance test trên đúng hệ quản trị.

### Kiểm thử unique constraint trong trường hợp đồng thời

Một test tốt nên gửi hai insert có cùng business key gần như đồng thời và xác nhận chỉ một insert thành công. Đây là cách chứng minh constraint database bảo vệ race condition mà kiểm tra `existsBy...` ở service không thể ngăn.

## 30. Những sai lầm thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Query theo foreign key chậm | Bảng con không có index trên FK | Tạo index theo access pattern của bảng con |
| Index có nhưng optimizer không dùng | Predicate không chọn lọc, thứ tự index không phù hợp hoặc scan rẻ hơn | Xem EXPLAIN và cardinality |
| Composite index không hỗ trợ query | Cột lọc không nằm ở prefix phù hợp | Sắp xếp cột theo predicate thực tế và đo lại |
| Sort vẫn tốn kém | Index không khớp thứ tự/chiều sort hoặc filter | Thiết kế index khớp filter và ORDER BY |
| Unique check vẫn tạo duplicate | Chỉ kiểm tra tồn tại ở Java, thiếu unique constraint | Thêm unique constraint và xử lý conflict |
| Xóa parent rất chậm | Thiếu index FK hoặc cascade quá rộng | Index cột tham chiếu và xem lại delete policy |
| Bảng có quá nhiều index | Index được tạo theo từng field mà không xét workload ghi | Đánh giá usage và chi phí ghi |
| `LIKE '%text%'` chậm dù có B-tree | Pattern có wildcard đầu không phù hợp B-tree | Full-text/trigram/expression index theo database |
| Page sâu chậm | Offset lớn phải bỏ qua nhiều hàng | Cân nhắc keyset và index cursor |
| Join tạo nhiều hàng trùng | Thiếu constraint quan hệ hoặc join cardinality khác dự kiến | Xác định cardinality, unique/FK và group đúng |
| Entity mapping lỗi cột | Tên property và schema không khớp | Dùng `@Column` và migration thống nhất |
| `@Version` lỗi khi save | Thiếu cột hoặc giá trị/version semantics sai | Đồng bộ entity và schema migration |
| Migration thêm unique thất bại | Dữ liệu cũ đã có duplicate | Dọn dữ liệu trước khi thêm constraint |
| Index migration gây ảnh hưởng production | Build index khóa hoặc tiêu tốn I/O lớn | Dùng chiến lược online/concurrent theo database và triển khai có kế hoạch |

## 31. Quy trình thiết kế schema theo access pattern

Một quy trình có thể áp dụng cho mỗi aggregate hoặc module:

1. Liệt kê các truy vấn đọc/ghi quan trọng từ API và service.
2. Xác định entity, aggregate root và quan hệ one-to-one/one-to-many/many-to-many.
3. Chọn primary key ổn định và unique constraint cho business key.
4. Khai báo foreign key và delete policy theo vòng đời dữ liệu.
5. Thêm `NOT NULL`, `DEFAULT`, `CHECK` để database bảo vệ invariant.
6. Xác định kiểu dữ liệu phù hợp cho numeric, string, time, UUID, JSON và version.
7. Thiết kế index theo equality filter, range, join, sort và pagination.
8. Kiểm tra composite index, prefix, partial/expression/covering index theo database.
9. Viết migration có version, kiểm tra dữ liệu cũ và đánh giá lock khi triển khai.
10. Ánh xạ schema vào entity bằng `@Table`, `@Column`, `@Id`, `@Version` và converters phù hợp.
11. Chạy integration test constraint và mapping với driver thật.
12. Dùng EXPLAIN/benchmark trên dữ liệu gần production, đo cả read và write cost.
13. Theo dõi index usage và workload sau triển khai; chỉ thêm/bỏ index dựa trên bằng chứng.

## 32. Ghi nhớ

- Thiết kế schema và index từ access pattern thực tế: predicate, join, sort, pagination, count và update.
- `@Table`, `@Column`, `@Id` và `@Version` mô tả mapping; migration quản lý bảng, index và constraint.
- Chọn primary key ổn định; dùng unique constraint cho business key và đúng phạm vi tenant.
- Foreign key bảo vệ quan hệ ở database; cột foreign key thường cần index nếu query/join hoặc delete parent sử dụng nó.
- `NOT NULL`, `DEFAULT`, `CHECK` và `UNIQUE` giữ invariant ngay cả khi dữ liệu được ghi ngoài repository.
- Composite B-tree index phụ thuộc thứ tự cột; prefix và equality/range/sort cần khớp query thực tế.
- Index có thể hỗ trợ JOIN, ORDER BY, pagination và keyset khi được thiết kế đúng, nhưng không bảo đảm optimizer luôn dùng nó.
- Partial, expression, INCLUDE, trigram và JSON index phụ thuộc database; kiểm tra portability và query plan.
- Index làm tăng chi phí insert/update/delete, dung lượng và maintenance; tránh index thừa.
- Chọn kiểu dữ liệu theo semantics và driver codec; chuẩn hóa thời gian và xử lý nullability rõ ràng.
- Với multi-tenant, cân nhắc composite key/foreign key để bảo vệ quan hệ cùng tenant ở database.
- `@Version` cần cột version trong schema; direct SQL phải tự thực hiện điều kiện và tăng version.
- Dùng Flyway/Liquibase hoặc migration có version để triển khai schema an toàn; không dựa vào entity mapping để tự tạo production schema.
- Dùng `EXPLAIN` và benchmark với dữ liệu thực tế; query plan quan trọng hơn suy đoán từ tên index.

Schema tốt cho Spring Data R2DBC là schema phản ánh đúng invariant nghiệp vụ và hỗ trợ những truy vấn hệ thống thực sự chạy. Hãy để database bảo vệ tính toàn vẹn bằng khóa và constraint, dùng index có chủ đích cho các access pattern quan trọng, rồi xác nhận hiệu quả bằng execution plan và benchmark. Entity mapping của Spring Data chỉ là lớp nối giữa mô hình Java và schema đã được thiết kế, không thay thế các quyết định đó.
