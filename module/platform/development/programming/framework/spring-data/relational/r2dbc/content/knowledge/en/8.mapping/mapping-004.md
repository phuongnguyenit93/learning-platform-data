# Identifying the Primary Key with `@Id`

In Spring Data Relational R2DBC, `@Id` marks the property that represents an entity's identifier. Spring Data uses this information when building mapping metadata between a Java class and a relational table, especially during find-by-ID, save, update, and delete operations.

`@Id` belongs to Spring Data Commons, not JPA. When working with R2DBC, you must use `org.springframework.data.annotation.Id`. This annotation tells Spring Data which property is the identifier; primary key structure, the `PRIMARY KEY` constraint, and how the database generates values are still defined in the database schema.

## 1. Role of `@Id` in Relational Mapping

An entity usually maps to a table, and each instance represents a row. Spring Data needs to know which property uniquely identifies that row to perform CRUD operations.

For example, table `customer` has column `id` as its primary key:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);
```

Corresponding entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("full_name")
    private String name;

    public Customer() {
    }

    public Customer(Long id, String name) {
        this.id = id;
        this.name = name;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

In this example:

- `@Table("customer")` maps the entity to the `customer` table.
- `@Id` designates `id` as the entity's identifier property.
- `@Column("full_name")` maps the `name` property to the `full_name` column.
- `Long` allows an unassigned ID value to be represented by `null`.

`@Id` is metadata for the mapping layer. It does not automatically create the `id` column, add a `PRIMARY KEY` constraint, or configure ID auto-generation. Those belong to the schema and database migrations.

## 2. Using the Right Spring Data Annotation

In Java there are several annotations named `Id`. For Spring Data R2DBC, the required import is:

```java
import org.springframework.data.annotation.Id;
```

Do not confuse it with:

```java
import jakarta.persistence.Id;
```

`jakarta.persistence.Id` belongs to JPA. R2DBC does not use a JPA persistence context and does not rely on Hibernate ORM to map entities. If you accidentally import the JPA annotation in an R2DBC entity, Spring Data Relational may fail to recognize that property as the entity's identifier.

Similarly, use Spring Data Relational mapping annotations when modeling tables and columns:

```java
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.data.relational.core.mapping.Column;
```

Mixing JPA and Spring Data Relational annotations in the same entity can produce unexpected metadata. Choose the annotation set that matches the persistence technology used by the repository.

## 3. Which Property Should `@Id` Be Placed On?

`@Id` must mark the property that actually represents the row's identifying key. In a typical Java entity, you can place the annotation on the field:

```java
@Table("orders")
public class Order {

    @Id
    private Long orderId;

    private String status;
}
```

The property name does not have to be `id`; `orderId`, `customerKey`, or another meaningful name can be used as the identifier when annotated with `@Id`. If the property name differs from the column name in the database, declare `@Column` to map it explicitly:

```java
@Id
@Column("order_key")
private Long orderId;
```

Then `orderId` is the Java property name and `order_key` is the column name in the table. Spring Data uses this metadata to generate statements matching the mapping.

You can place the annotation on a property accessor if the entity model uses the corresponding property access style. Within a Java class, maintain a consistent access style and place the annotation where Spring Data can read it per the class's property structure. For entities using field access like the examples above, placing `@Id` directly on the field helps readers spot the identifier immediately.

### One Identifier per Entity

Standard CRUD repository operations work with a single ID type, such as `Long`, `Integer`, `UUID`, or another simple type supported by mapping/conversion:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

The second generic parameter (`Long`) must match the type of the property annotated with `@Id`. If an entity has an `@Id` property of type `UUID` while the repository declares `Long`, the type mismatch will cause compilation errors or errors when using repository APIs.

Spring Data Relational focuses on a single identifier property for standard CRUD operations. If a table uses a composite primary key across multiple columns, do not assume that placing multiple `@Id` annotations will make the framework automatically understand a composite key. Consider a surrogate key or use custom SQL via `DatabaseClient`/`R2dbcEntityTemplate` for models requiring composite keys.

## 4. `@Id` and the Primary Key Column Name

The Java property name and database column name may differ. `@Id` identifies the identifier property, while `@Column` specifies the column name used during mapping.

Example of a table using column `customer_key`:

```sql
CREATE TABLE customer_profile (
    customer_key BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(200) NOT NULL
);
```

Entity:

```java
@Table("customer_profile")
public class CustomerProfile {

    @Id
    @Column("customer_key")
    private Long id;

    @Column("display_name")
    private String displayName;
}
```

Spring Data recognizes `id` as the entity identifier and uses the `customer_key` column in SQL. If `@Column` is omitted, converting the property name to a column name depends on Spring Data Relational's naming strategy. When the schema has special column names, legacy names, or non-standard names, declaring `@Column` explicitly keeps mapping readable and less dependent on implicit conventions.

`@Id` does not mean the column must be named `id`. Conversely, having a column named `id` in the database does not automatically replace declaring the identifier explicitly in the entity. Check mapping metadata and the schema if the framework uses the wrong column in CRUD statements.

## 5. How Does `@Id` Affect CRUD Operations?

The identifier is the basis for Spring Data to build conditions that find, update, or delete the right row. For example, with a repository:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

Some commonly used operations:

| API | How the Identifier Is Used |
| --- | --- |
| `findById(id)` | Finds a row by ID value |
| `existsById(id)` | Checks whether a row with the corresponding ID exists |
| `deleteById(id)` | Deletes a row by ID |
| `save(entity)` | Determines new/existing state of the entity; when updating, the ID identifies which row to update |
| `findAllById(ids)` | Finds rows whose IDs are in the supplied collection |

Example of finding and deleting by ID in a reactive flow:

```java
public Mono<Void> deleteCustomer(Long id) {
    return customerRepository.findById(id)
            .switchIfEmpty(Mono.error(
                    new IllegalArgumentException("Customer does not exist: " + id)
            ))
            .flatMap(customer -> customerRepository.delete(customer));
}
```

`findById` uses the identifier declared in metadata. Repository operations return `Mono` or `Flux`; SQL executes when the publisher is subscribed.

## 6. `@Id` and Distinguishing INSERT from UPDATE

When calling `save(entity)`, Spring Data needs to determine whether the entity represents a new record or an existing one. This state check is commonly called *newness detection*.

For entities that do not implement `Persistable`, Spring Data Relational typically checks the `@Version` property if the entity has a version property; if there is no version property, it checks the identifier:

- If the version property is `null` (for object types) or `0` (for primitive numeric types), the entity is treated as new.
- If there is no version property, an ID that is `null` (or `0` for primitive numeric types) is typically treated as a new entity.
- When an entity is treated as new, `save` performs an insert.
- When an entity is treated as existing, `save` performs an update by identifier.

Details of newness detection can be customized with `Persistable` or affected by the mapping/version strategy in the Spring Data version being used.

Example of a new entity without an ID:

```java
Customer newCustomer = new Customer(null, "Nguyen An");

Mono<Customer> savedCustomer = customerRepository.save(newCustomer);
```

With a `null` ID, Spring Data detects the entity as new (assuming no version property changes the outcome). Upon subscription, the repository executes an insert. If the database generates the primary key, the value is read from the insert result and assigned to the entity emitted by the publisher.

### Why Use Wrapper Types Like `Long`?

With `Long`, a new entity can represent an unassigned ID using `null`. With primitive `long`, the default value is `0`, so Spring Data has to use the zero-value convention to detect new entities. Wrappers usually express state more clearly:

```java
@Id
private Long id;
```

If the ID is auto-generated, do not assign a dummy value like `-1` or `0` to a wrapper just to indicate a new record. Leave the ID unassigned until the database returns the generated key.

### Entities with Pre-Assigned IDs

If the application assigns IDs itself—such as a UUID or business code—a new entity may already have an ID value before insertion. Relying solely on the ID, Spring Data may treat the entity as existing and choose update. This is why you must understand newness detection before calling `save` with manually assigned IDs.

Depending on requirements, there are several approaches:

- Use an explicit insert operation via `R2dbcEntityTemplate.insert(entity)` or SQL via `DatabaseClient` when you are certain a new row must be created.
- Implement `Persistable<ID>` to provide `isNew()` based on the entity's business state. When using this approach, the application must manage the transition from new to persisted accurately.
- Use a version property if the model requires optimistic locking and version state fits the newness detection rules.

Do not try to force `save` to perform an insert by setting an invalid ID. Choose an API that reflects the insert intent or define the entity's state explicitly.

## 7. Database-Generated Primary Keys

In many relational schemas, the database generates the primary key on insert. For example, PostgreSQL uses an identity column:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);
```

Entity declaring the ID with a wrapper type:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("full_name")
    private String fullName;

    public Customer() {
    }

    public Customer(String fullName) {
        this.fullName = fullName;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }
}
```

Saving the entity:

```java
Mono<Customer> saved = customerRepository.save(
        new Customer("Nguyen An")
);

return saved.doOnNext(customer ->
        log.info("Database-generated ID: {}", customer.getId())
);
```

When the insert completes, Spring Data R2DBC uses the driver/database's generated-values capability to retrieve the ID and populate it on the emitted entity. Always use the entity emitted by `save` to obtain the ID after saving. For immutable entities, the framework can construct a new instance containing the ID instead of mutating the original instance.

`@Id` does not automatically enable auto-increment or identity. The schema must define the key generation mechanism and the driver/database must support returning generated values. Identity, sequence, or generated-key syntax varies across database systems; the PostgreSQL example above is not universal DDL for every database.

### Do Not Confuse `@Id` with `@GeneratedValue`

`@GeneratedValue` is a common annotation in JPA for describing an ORM key generation strategy. Spring Data Relational R2DBC does not rely on that JPA generation strategy. With R2DBC, ID generation is usually determined by the database schema and the driver's generated-values capability; Spring Data identifies the property via `@Id` and handles the returned value.

If you need sequences or specialized ID allocation, review the features of Spring Data Relational and the database in use, or assign IDs proactively in the application. Do not add JPA annotations to an R2DBC entity expecting them to control key generation.

## 8. ID and Optimistic Locking with `@Version`

`@Id` and `@Version` serve different purposes:

- `@Id` identifies which row corresponds to the entity being operated on.
- `@Version` stores the entity version to detect concurrent updates (optimistic locking).

Example:

```java
@Table("inventory")
public class InventoryItem {

    @Id
    private Long id;

    @Version
    private Long version;

    private Integer quantity;
}
```

In the corresponding schema, column `id` is the primary key; column `version` stores the version number. When updating, Spring Data can use both the ID and current version in the update condition while incrementing the version. If no row is updated because the version changed, the operation can raise an optimistic locking error.

The version property can also participate in newness detection. Therefore, if an entity has `@Version`, do not look solely at the ID to conclude whether `save` will definitely execute an insert or update. Check the version state according to Spring Data rules and the current mapping.

## 9. Immutable Entities, Records, and Kotlin Data Classes

Spring Data Relational supports mapping entity models that do not necessarily have setters for every property. With immutable entities, data can be initialized via a constructor. When the database generates an ID after insert, the framework needs to create an instance containing the new ID using an entity-creation mechanism supported by the mapping context.

Java record example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        @Column("full_name") String fullName
) {
}
```

Repository:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

When saving a new record with `id == null`, the repository emits a record mapped with the ID returned by the database. Continue using the emitted value rather than assuming the original object is mutated in place.

With a Kotlin data class, place `@Id` on the corresponding constructor property and choose a nullable type like `Long?` if the ID is database-generated. Annotation use-site syntax may need adjustment depending on how the compiler places annotations on fields or properties; ensure Spring Data can read the annotation on the persistent property.

## 10. Testing Identifier Mapping

You can test the repository with a compatible R2DBC database and `StepVerifier`. Example:

```java
StepVerifier.create(customerRepository.save(new Customer(null, "Nguyen An")))
        .assertNext(saved -> {
            assertThat(saved.getId()).isNotNull();
            assertThat(saved.getFullName()).isEqualTo("Nguyen An");
        })
        .verifyComplete();
```

After saving, you can use the emitted ID to read the record back:

```java
Mono<Customer> roundTrip = customerRepository
        .save(new Customer(null, "Nguyen An"))
        .flatMap(saved -> customerRepository.findById(saved.getId()));
```

Other helpful tests include:

- Saving an entity with a `null` ID and verifying the database generates an ID.
- Reading the entity with `findById` using the newly generated ID.
- Updating a property and verifying `save` updates the right row by ID.
- Deleting the entity by ID and verifying the row no longer exists.
- Verifying mapping when the property name differs from the column name and uses `@Column`.
- Verifying behavior with pre-assigned IDs and `Persistable.isNew()` if the application uses assigned IDs.
- Verifying optimistic locking if the entity has `@Version`.

Tests must subscribe to the publisher. Creating a `Mono` from a repository without consuming it does not execute the SQL operation.

## 11. Common Errors When Identifying Primary Keys

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Spring Data does not recognize the identifier properly | Missing `@Id` or mistakenly imported `jakarta.persistence.Id` | Use `org.springframework.data.annotation.Id` on the persistent property |
| Repository generic ID mismatch | `ReactiveCrudRepository<Entity, ID>` declares the wrong type | Align `ID` with the type of the property annotated with `@Id` |
| SQL uses the wrong key column name | Property and column mapping do not match the schema | Declare `@Column("...")` with the right column name and check migrations |
| `save` executes UPDATE instead of INSERT | Entity has a pre-assigned ID so it is detected as existing | Use explicit insert or customize newness detection with `Persistable` |
| ID remains null after insert | Schema does not generate ID, driver does not return generated values, or mapping is wrong | Check DDL, dialect, driver, and generated-key support |
| Update affects no rows | Wrong ID, row does not exist, or version mismatch | Check ID value, data, and `@Version` |
| Using multiple `@Id` annotations but CRUD does not work as expected | Model tries to represent a composite key with multiple properties | Use a supported single identifier or custom SQL for composite keys |
| Using `@GeneratedValue` yet ID is not auto-generated | Applying a JPA annotation to R2DBC | Configure key generation in the database and check driver generated values |

When investigating, check in this order: annotation import, placement of `@Id`, repository ID type, column name in schema, ID/version state before calling `save`, and then database/driver support for generating and returning keys.

## 12. Distinguishing Related Concepts

| Concept | Role |
| --- | --- |
| `@Id` | Marks the identifier property in Spring Data metadata |
| `PRIMARY KEY` | Database constraint ensuring uniqueness and non-nullness of the primary key |
| `@Column` | Maps a Java property to a database column name |
| `@Version` | Manages version to detect concurrent updates and assist newness detection in some cases |
| `Persistable.isNew()` | Lets an entity supply its own new/existing status |
| Database identity/sequence/default | Mechanism that creates key values on insert |

These concepts work together without replacing one another. An entity with `@Id` whose database lacks a corresponding primary key can still lead to duplicate data or integrity errors. A database with `PRIMARY KEY` whose entity marks the wrong property can also cause Spring Data to generate incorrect CRUD SQL.

## 13. Key Takeaways

- Use `org.springframework.data.annotation.Id` to mark the identifier property in Spring Data Relational R2DBC.
- Do not mistakenly use `jakarta.persistence.Id` or rely on JPA annotations to control R2DBC mapping.
- The property name does not have to be `id`; `@Column` maps the property to the primary key column name when needed.
- The ID type in `ReactiveCrudRepository<Entity, ID>` must match the type of the `@Id` property.
- `@Id` only describes the identifier for Spring Data; the database schema must still define the primary key and ID generation mechanism if needed.
- `save` relies on newness detection to choose insert or update. ID, `@Version`, and `Persistable.isNew()` can participate in that decision.
- For database-generated keys, use a wrapper type such as `Long`, save new entities with an unassigned ID, and read the entity emitted by the `save` publisher.
- If the application assigns IDs manually, define new/existing state explicitly or use explicit insert operations.
- `@Version` is not a primary key; it supports optimistic locking and can affect new-entity detection.
- For composite primary keys, do not assume multiple `@Id` annotations produce automatic composite-key mapping; consider surrogate keys or custom SQL.

When mapping an R2DBC entity, identify which property serves as the identifier, verify the annotation and ID type, and match it against the primary key column in the schema. Once that relationship is clear, repository operations can find, save, update, and delete the right rows using the metadata Spring Data builds.
