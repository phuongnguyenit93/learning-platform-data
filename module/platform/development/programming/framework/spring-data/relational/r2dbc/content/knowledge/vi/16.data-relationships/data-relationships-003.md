# Mô hình bảng liên kết cho quan hệ nhiều-nhiều

Trong cơ sở dữ liệu quan hệ, quan hệ nhiều-nhiều (many-to-many) mô tả trường hợp một bản ghi ở bảng thứ nhất có thể liên kết với nhiều bản ghi ở bảng thứ hai, đồng thời mỗi bản ghi ở bảng thứ hai cũng có thể liên kết với nhiều bản ghi ở bảng thứ nhất. Ví dụ, một sinh viên có thể đăng ký nhiều khóa học và mỗi khóa học có thể có nhiều sinh viên.

Quan hệ này thường được biểu diễn bằng **bảng liên kết** (association table hoặc junction table). Bảng liên kết lưu khóa ngoại đến hai bảng chính; mỗi hàng thể hiện một mối liên kết cụ thể. Trong Spring Data R2DBC, nên mô hình hóa hàng liên kết thành một entity riêng có các thuộc tính định danh, thay vì giả định framework tự tải và đồng bộ một đồ thị đối tượng nhiều-nhiều như ORM.

## 1. Quan hệ nhiều-nhiều trong mô hình quan hệ

Giả sử hệ thống quản lý đào tạo có hai thực thể:

- **Student**: sinh viên.
- **Course**: khóa học.

Một sinh viên có thể đăng ký nhiều khóa học. Một khóa học có thể có nhiều sinh viên. Nếu chỉ đặt một cột course_id trong bảng student, mỗi sinh viên chỉ gắn được một khóa học. Nếu lưu danh sách ID trong một cột, việc kiểm tra khóa ngoại, tìm kiếm, cập nhật và lập chỉ mục sẽ phức tạp.

Mô hình quan hệ chuẩn tách quan hệ này thành ba bảng:

~~~mermaid
erDiagram
    STUDENT ||--o{ STUDENT_COURSE : registers
    COURSE ||--o{ STUDENT_COURSE : has
    STUDENT {
        bigint id PK
        varchar name
    }
    COURSE {
        bigint id PK
        varchar title
    }
    STUDENT_COURSE {
        bigint id PK
        bigint student_id FK
        bigint course_id FK
        timestamptz enrolled_at
    }
~~~

Mỗi hàng trong STUDENT_COURSE liên kết đúng một sinh viên với đúng một khóa học. Nhiều hàng có thể cùng student_id nhưng khác course_id; nhiều hàng cũng có thể cùng course_id nhưng khác student_id.

Về mặt cardinality, hai quan hệ một-nhiều kết hợp qua bảng liên kết tạo thành quan hệ nhiều-nhiều giữa Student và Course.

## 2. Vì sao cần bảng liên kết?

Bảng liên kết giải quyết ba vấn đề chính:

1. **Biểu diễn quan hệ:** lưu hai khóa ngoại để xác định cặp bản ghi có liên kết.
2. **Bảo đảm toàn vẹn:** foreign key ngăn tạo liên kết đến sinh viên hoặc khóa học không tồn tại.
3. **Ngăn liên kết trùng:** unique constraint trên cặp khóa ngoại có thể bảo đảm một sinh viên không đăng ký cùng một khóa học nhiều lần.

Bảng liên kết còn có thể lưu thuộc tính của chính mối quan hệ, ví dụ ngày đăng ký, trạng thái, điểm số, vai trò hoặc người tạo liên kết. Khi đó, nó không chỉ là bảng kỹ thuật để nối hai bảng; nó mang dữ liệu nghiệp vụ riêng.

Ví dụ: quan hệ sinh viên đăng ký khóa học có thể lưu ngày đăng ký và trạng thái:

| student_id | course_id | enrolled_at | status |
| --- | --- | --- | --- |
| 10 | 101 | 2026-09-01 | ACTIVE |
| 10 | 102 | 2026-09-03 | ACTIVE |
| 11 | 101 | 2026-09-04 | WAITLISTED |

Sinh viên 10 tham gia hai khóa học; khóa học 101 có hai sinh viên. Mỗi hàng là một đăng ký độc lập.

## 3. Thiết kế schema cho bảng liên kết

Ví dụ DDL với PostgreSQL:

~~~sql
CREATE TABLE student (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE course (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(250) NOT NULL
);

CREATE TABLE student_course (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    enrolled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_student_course_student
        FOREIGN KEY (student_id) REFERENCES student(id),
    CONSTRAINT fk_student_course_course
        FOREIGN KEY (course_id) REFERENCES course(id),
    CONSTRAINT uk_student_course_pair
        UNIQUE (student_id, course_id)
);

CREATE INDEX idx_student_course_course_student
    ON student_course(course_id, student_id);
~~~

Trong thiết kế này:

- ID của bảng liên kết là khóa chính độc lập.
- student_id và course_id là hai khóa ngoại.
- Unique constraint trên cặp student_id/course_id ngăn một cặp bị ghi trùng.
- Index theo course_id hỗ trợ truy vấn ngược từ khóa học sang danh sách sinh viên.

Có thể dùng cặp khóa ngoại làm khóa chính thay cho ID riêng:

~~~sql
CREATE TABLE student_course (
    student_id BIGINT NOT NULL REFERENCES student(id),
    course_id BIGINT NOT NULL REFERENCES course(id),
    enrolled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (student_id, course_id)
);
~~~

Khóa chính kép thể hiện trực tiếp rằng một cặp sinh viên-khóa học chỉ xuất hiện một lần. Tuy nhiên, khi ánh xạ với Spring Data Relational, composite ID có thể làm việc với repository và mapping phức tạp hơn; khả năng hỗ trợ cụ thể cần được xác nhận theo phiên bản Spring Data đang dùng. Dùng một ID riêng kết hợp unique constraint trên cặp khóa ngoại thường thuận tiện hơn khi muốn mô hình hóa bảng liên kết thành entity có repository riêng.

Không nên bỏ unique constraint chỉ vì service đã kiểm tra cặp ID trước khi insert. Hai request đồng thời có thể cùng kiểm tra “chưa tồn tại” rồi cùng insert. Constraint ở database là hàng rào cuối cùng bảo vệ dữ liệu.

## 4. Mô hình entity trong Spring Data R2DBC

Trong Spring Data R2DBC, mỗi aggregate root được lưu qua repository hoặc template. Quan hệ tham chiếu sang aggregate khác thường được biểu diễn bằng ID. Framework không tự động triển khai một quan hệ object graph nhiều-nhiều kiểu ORM.

Entity Student:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("student")
public record Student(
        @Id Long id,
        String name
) {}
~~~

Entity Course:

~~~java
@Table("course")
public record Course(
        @Id Long id,
        String title
) {}
~~~

Entity cho bảng liên kết:

~~~java
import java.time.Instant;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("student_course")
public record StudentCourse(
        @Id Long id,
        @Column("student_id") Long studentId,
        @Column("course_id") Long courseId,
        @Column("enrolled_at") Instant enrolledAt,
        String status
) {}
~~~

StudentCourse giữ hai định danh. Nó không cần chứa đối tượng Student và Course để biểu diễn quan hệ. Khi cần tên sinh viên hoặc tiêu đề khóa học, ứng dụng chủ động truy vấn hoặc dùng SQL JOIN để tạo read model.

Nếu bảng liên kết có các trường nghiệp vụ như status hoặc enrolledAt, việc có entity riêng đặc biệt hữu ích: có thể tạo, cập nhật, tìm kiếm và xóa từng mối liên kết như một bản ghi.

## 5. Repository cho hai bảng chính và bảng liên kết

Khai báo repository:

~~~java
public interface StudentRepository
        extends ReactiveCrudRepository<Student, Long> {
}

public interface CourseRepository
        extends ReactiveCrudRepository<Course, Long> {
}

public interface StudentCourseRepository
        extends ReactiveCrudRepository<StudentCourse, Long> {

    Flux<StudentCourse> findByStudentId(Long studentId);

    Flux<StudentCourse> findByCourseId(Long courseId);

    Mono<Long> countByStudentId(Long studentId);
}
~~~

Các phương thức derived query dùng tên thuộc tính Java của entity StudentCourse, ví dụ studentId và courseId. Spring Data chuyển các thuộc tính này sang cột tương ứng theo mapping metadata.

Những repository này quản lý từng loại entity. Gọi studentRepository.save(student) không tự tạo các hàng StudentCourse; gọi courseRepository.deleteById(id) cũng không tự hiểu phải xóa hoặc cập nhật các liên kết trừ khi database có foreign key action tương ứng.

## 6. Tạo một liên kết mới

Ví dụ đăng ký sinh viên vào khóa học. Service có thể kiểm tra hai đối tượng tồn tại rồi lưu hàng liên kết:

~~~java
import java.time.Instant;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import reactor.core.publisher.Mono;

@Service
public class EnrollmentService {

    private final StudentRepository studentRepository;
    private final CourseRepository courseRepository;
    private final StudentCourseRepository enrollmentRepository;

    public EnrollmentService(
            StudentRepository studentRepository,
            CourseRepository courseRepository,
            StudentCourseRepository enrollmentRepository) {
        this.studentRepository = studentRepository;
        this.courseRepository = courseRepository;
        this.enrollmentRepository = enrollmentRepository;
    }

    @Transactional
    public Mono<StudentCourse> enroll(Long studentId, Long courseId) {
        return studentRepository.findById(studentId)
                .switchIfEmpty(Mono.error(
                        new StudentNotFoundException(studentId)
                ))
                .then(courseRepository.findById(courseId))
                .switchIfEmpty(Mono.error(
                        new CourseNotFoundException(courseId)
                ))
                .then(Mono.defer(() ->
                        enrollmentRepository.save(new StudentCourse(
                                null,
                                studentId,
                                courseId,
                                Instant.now(),
                                "ACTIVE"
                        ))
                ));
    }
}
~~~

Ý tưởng của pipeline:

1. Tìm Student theo ID; nếu không tồn tại thì phát lỗi nghiệp vụ.
2. Tìm Course theo ID; nếu không tồn tại thì phát lỗi nghiệp vụ.
3. Sau khi cả hai bước hoàn tất, tạo StudentCourse mới.
4. Lưu hàng liên kết và trả entity đã lưu.

Vì đây là reactive pipeline, các thao tác được nối bằng publisher. Không dùng block() để lấy Student hoặc Course rồi mới gọi repository tiếp theo.

Kiểm tra tồn tại trước khi insert giúp trả thông báo nghiệp vụ dễ hiểu, nhưng vẫn có thể xảy ra race condition nếu một bản ghi bị xóa giữa lúc kiểm tra và insert. Foreign key trong database bảo vệ tính toàn vẹn tại thời điểm ghi. Transaction reactive giúp các thao tác trong cùng database được phối hợp commit/rollback; nó không loại bỏ mọi tình huống cạnh tranh với transaction khác.

## 7. Ngăn đăng ký trùng

Giả sử hai request đồng thời cùng đăng ký student 10 vào course 101. Cả hai có thể cùng chạy truy vấn kiểm tra và đều thấy chưa có liên kết. Nếu chỉ kiểm tra ở Java mà không có unique constraint, hai hàng trùng có thể được tạo.

Constraint:

~~~sql
CONSTRAINT uk_student_course_pair
    UNIQUE (student_id, course_id)
~~~

đảm bảo database chỉ chấp nhận một hàng cho cặp đó.

Ứng dụng có thể kiểm tra trước để cải thiện thông báo:

~~~java
public Mono<StudentCourse> enroll(Long studentId, Long courseId) {
    return enrollmentRepository
            .findByStudentId(studentId)
            .filter(link -> link.courseId().equals(courseId))
            .next()
            .flatMap(existing -> Mono.<StudentCourse>error(
                    new AlreadyEnrolledException(studentId, courseId)
            ))
            .switchIfEmpty(Mono.defer(() ->
                    enrollmentRepository.save(new StudentCourse(
                            null,
                            studentId,
                            courseId,
                            Instant.now(),
                            "ACTIVE"
                    ))
            ));
}
~~~

Ví dụ này minh họa logic kiểm tra; nếu danh sách liên kết của sinh viên lớn, truy vấn toàn bộ rồi lọc ở Java không hiệu quả. Nên khai báo truy vấn chính xác theo cả hai thuộc tính:

~~~java
public interface StudentCourseRepository
        extends ReactiveCrudRepository<StudentCourse, Long> {

    Mono<StudentCourse> findByStudentIdAndCourseId(
            Long studentId,
            Long courseId
    );
}
~~~

Ngay cả khi dùng truy vấn chính xác, unique constraint vẫn cần thiết để xử lý cạnh tranh. Khi insert vi phạm unique constraint, driver/database phát lỗi; tầng service có thể chuyển lỗi duplicate key thành AlreadyEnrolledException theo chính sách của ứng dụng.

Với PostgreSQL, có thể thiết kế thao tác idempotent bằng INSERT ... ON CONFLICT DO NOTHING. Đây là SQL đặc thù database; nếu dùng cách này, cần chọn rõ muốn trả về số hàng, hàng đã tồn tại hay trạng thái đã đăng ký. Không giả định repository save tự cung cấp semantics upsert.

## 8. Truy vấn danh sách khóa học của một sinh viên

Khi cần danh sách khóa học mà một sinh viên tham gia, có thể dùng SQL JOIN để đọc dữ liệu trong một truy vấn:

~~~java
public record CourseSummary(
        Long id,
        String title,
        String enrollmentStatus
) {}

public Flux<CourseSummary> findCoursesForStudent(Long studentId) {
    return databaseClient.sql("""
            SELECT c.id,
                   c.title,
                   sc.status AS enrollment_status
            FROM student_course sc
            JOIN course c ON c.id = sc.course_id
            WHERE sc.student_id = :studentId
            ORDER BY c.title
            """)
            .bind("studentId", studentId)
            .map((row, metadata) -> new CourseSummary(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

Truy vấn đọc bảng liên kết trước, nối sang course, lọc theo student_id và trả dữ liệu cần cho màn hình. Không cần tải từng StudentCourse rồi gọi courseRepository.findById() cho từng hàng.

Nếu chỉ cần các ID khóa học, truy vấn có thể đơn giản hơn:

~~~sql
SELECT course_id
FROM student_course
WHERE student_id = :studentId;
~~~

Hãy chỉ lấy những cột cần thiết. Với danh sách lớn, Flux cho phép tiêu thụ từng kết quả; nếu giao diện cần phân trang, hãy thêm ORDER BY ổn định và giới hạn LIMIT/OFFSET hoặc dùng keyset pagination.

## 9. Truy vấn danh sách sinh viên của một khóa học

Chiều ngược lại dùng course_id:

~~~java
public record StudentSummary(
        Long id,
        String name,
        String enrollmentStatus
) {}

public Flux<StudentSummary> findStudentsForCourse(Long courseId) {
    return databaseClient.sql("""
            SELECT s.id,
                   s.name,
                   sc.status AS enrollment_status
            FROM student_course sc
            JOIN student s ON s.id = sc.student_id
            WHERE sc.course_id = :courseId
            ORDER BY s.name
            """)
            .bind("courseId", courseId)
            .map((row, metadata) -> new StudentSummary(
                    row.get("id", Long.class),
                    row.get("name", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

Đây là lý do nên có index theo course_id. Unique index (student_id, course_id) thường hỗ trợ tốt các truy vấn bắt đầu bằng student_id; truy vấn theo course_id cần index riêng nếu có tải đáng kể theo chiều ngược lại.

## 10. Khi nào dùng repository, khi nào dùng JOIN?

Có thể lấy các hàng liên kết bằng derived query:

~~~java
Flux<StudentCourse> links =
        studentCourseRepository.findByStudentId(studentId);
~~~

Sau đó ứng dụng có thể tải thông tin Course cho từng liên kết. Cách này dễ tái sử dụng repository, nhưng có thể dẫn đến N+1 query nếu mỗi liên kết tạo một truy vấn riêng.

Một JOIN bằng DatabaseClient thường phù hợp hơn khi màn hình cần dữ liệu từ nhiều bảng:

| Cách làm | Ưu điểm | Hạn chế |
| --- | --- | --- |
| Tìm link bằng repository | Mapping entity rõ ràng, dễ tái sử dụng | Cần truy vấn thêm để lấy dữ liệu hai phía |
| JOIN bằng DatabaseClient | Một truy vấn có thể lấy dữ liệu cần thiết từ nhiều bảng | Phải viết SQL và mapping projection |
| Tải từng đối tượng bằng flatMap | Pipeline reactive dễ ghép theo logic | Có nguy cơ N+1 và nhiều round trip |
| Truy vấn theo lô bằng ID | Giảm số lần truy vấn so với từng ID | Cần quản lý kích thước lô và ghép kết quả |

Reactive không làm biến mất N+1. Nếu có 200 hàng liên kết và mỗi hàng gọi một truy vấn lấy Course, ứng dụng vẫn có thể tạo khoảng 200 truy vấn bổ sung. Hãy dùng JOIN hoặc truy vấn theo lô khi cần đọc danh sách.

## 11. Cập nhật thuộc tính của bảng liên kết

Khi bảng liên kết có dữ liệu nghiệp vụ, có thể cập nhật nó như entity thông thường. Ví dụ chuyển đăng ký từ WAITLISTED sang ACTIVE:

~~~java
public Mono<StudentCourse> activateEnrollment(Long linkId) {
    return enrollmentRepository.findById(linkId)
            .switchIfEmpty(Mono.error(
                    new EnrollmentNotFoundException(linkId)
            ))
            .map(link -> new StudentCourse(
                    link.id(),
                    link.studentId(),
                    link.courseId(),
                    link.enrolledAt(),
                    "ACTIVE"
            ))
            .flatMap(enrollmentRepository::save);
}
~~~

Nếu chỉ cập nhật một trường và không cần tải entity, có thể dùng R2dbcEntityTemplate hoặc DatabaseClient để thực hiện UPDATE có điều kiện. Với thao tác cập nhật trạng thái, cần kiểm soát điều kiện hiện tại nếu nghiệp vụ có chuyển trạng thái hợp lệ, ví dụ chỉ cho phép WAITLISTED chuyển sang ACTIVE.

Nếu nhiều request có thể cập nhật cùng một liên kết, cân nhắc thêm cột version và optimistic locking hoặc thể hiện trạng thái mong đợi ngay trong WHERE:

~~~sql
UPDATE student_course
SET status = 'ACTIVE'
WHERE id = :id
  AND status = 'WAITLISTED';
~~~

Số hàng cập nhật bằng 0 cho biết điều kiện không còn đúng hoặc hàng không tồn tại. Cách diễn giải cần theo nghiệp vụ.

## 12. Xóa một mối liên kết

Hủy đăng ký một sinh viên khỏi một khóa học thường có nghĩa xóa hàng trong bảng student_course, không xóa Student hoặc Course:

~~~java
public Mono<Long> unenroll(Long studentId, Long courseId) {
    return databaseClient.sql("""
            DELETE FROM student_course
            WHERE student_id = :studentId
              AND course_id = :courseId
            """)
            .bind("studentId", studentId)
            .bind("courseId", courseId)
            .fetch()
            .rowsUpdated();
}
~~~

Publisher trả số hàng bị xóa. Giá trị 1 thường có nghĩa liên kết đã được xóa; 0 có nghĩa cặp đó không tồn tại. Không xóa hàng ở bảng course vì các sinh viên khác vẫn có thể tham gia khóa học đó.

Nếu association entity có ID riêng, cũng có thể xóa theo ID của StudentCourse qua repository. Xóa theo cặp studentId/courseId thể hiện trực tiếp khóa nghiệp vụ và không cần tải entity trước.

## 13. Xóa một phía và hành vi foreign key

Khi xóa một Student, các hàng StudentCourse tham chiếu đến sinh viên đó phải được xử lý. Có hai chiến lược phổ biến:

1. **RESTRICT/NO ACTION:** database từ chối xóa Student nếu còn hàng liên kết. Service phải xóa các link trước hoặc từ chối yêu cầu.
2. **ON DELETE CASCADE trên foreign key của bảng liên kết:** database tự xóa các hàng StudentCourse khi Student bị xóa.

Ví dụ:

~~~sql
FOREIGN KEY (student_id)
    REFERENCES student(id)
    ON DELETE CASCADE
~~~

Cascade ở đây chỉ xóa các hàng liên kết trong student_course. Nó không xóa các hàng Course vì student_course chỉ có foreign key đến Course theo chiều ngược lại.

Không nên cấu hình cascade từ bảng liên kết để xóa đối tượng ở bảng đầu kia. Xóa một sinh viên không được làm mất khóa học đang có sinh viên khác đăng ký.

Nếu không dùng ON DELETE CASCADE, service có thể xóa link trước rồi xóa Student trong cùng transaction:

~~~java
@Transactional
public Mono<Void> deleteStudent(Long studentId) {
    return databaseClient.sql("""
            DELETE FROM student_course
            WHERE student_id = :studentId
            """)
            .bind("studentId", studentId)
            .fetch()
            .rowsUpdated()
            .then(studentRepository.deleteById(studentId));
}
~~~

Transaction bảo đảm thao tác xóa liên kết và xóa sinh viên được phối hợp trong cùng đơn vị commit/rollback nếu cả hai dùng cùng database và reactive transaction manager.

## 14. Bảng liên kết có thuộc tính riêng

Khi mối quan hệ có dữ liệu riêng, association entity là mô hình tự nhiên:

- Thời điểm tạo liên kết.
- Trạng thái liên kết.
- Vai trò của đối tượng trong nhóm.
- Thứ tự hoặc vị trí.
- Người tạo liên kết.
- Thông tin audit.

Ví dụ hệ thống nhóm người dùng:

~~~sql
CREATE TABLE team_member (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_id BIGINT NOT NULL REFERENCES team(id),
    user_id BIGINT NOT NULL REFERENCES app_user(id),
    role VARCHAR(30) NOT NULL,
    joined_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_team_member_pair UNIQUE (team_id, user_id)
);
~~~

Entity:

~~~java
@Table("team_member")
public record TeamMember(
        @Id Long id,
        @Column("team_id") Long teamId,
        @Column("user_id") Long userId,
        String role,
        @Column("joined_at") Instant joinedAt
) {}
~~~

Không nên coi TeamMember chỉ là một chi tiết kỹ thuật nếu role hoặc joinedAt có ý nghĩa nghiệp vụ. Nó có thể có service và repository riêng, cùng các quy tắc như một thành viên chỉ được có một role hiện hành trong một team.

## 15. Chọn khóa chính cho bảng liên kết

Có hai thiết kế phổ biến:

### Khóa chính kép

~~~sql
PRIMARY KEY (student_id, course_id)
~~~

Ưu điểm:

- Mô hình hóa trực tiếp tính duy nhất của cặp liên kết.
- Không cần cột ID bổ sung.
- Khóa chính đồng thời là constraint ngăn đăng ký trùng.

Hạn chế:

- Ánh xạ composite ID và repository có thể phức tạp hơn.
- Những bảng khác muốn tham chiếu riêng một liên kết phải dùng cả hai cột.
- Một số abstraction Spring Data làm việc thuận tiện hơn với ID đơn.

### ID riêng và unique constraint

~~~sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
UNIQUE (student_id, course_id)
~~~

Ưu điểm:

- Dùng repository với ID đơn giản.
- Dễ tham chiếu association row từ bảng khác.
- Dễ mở rộng association thành entity có vòng đời riêng.

Hạn chế:

- Cần thêm một cột ID.
- Vẫn phải có unique constraint trên cặp khóa ngoại để tránh trùng.

Trong nhiều ứng dụng Spring Data R2DBC, ID riêng kết hợp unique constraint là lựa chọn dễ ánh xạ và quản lý. Nếu mô hình dữ liệu đơn giản và phiên bản Spring Data hỗ trợ composite ID theo nhu cầu, khóa chính kép vẫn là lựa chọn hợp lệ.

## 16. Chỉ mục cho bảng liên kết

Truy vấn nhiều-nhiều thường đi theo hai hướng:

- Từ Student tìm các Course.
- Từ Course tìm các Student.

Do đó, index cần phản ánh cả hai hướng. Với unique index trên (student_id, course_id), database thường có thể sử dụng index đó cho điều kiện bắt đầu bằng student_id. Truy vấn chỉ lọc theo course_id thường cần index riêng:

~~~sql
CREATE UNIQUE INDEX uk_student_course_pair
    ON student_course(student_id, course_id);

CREATE INDEX idx_student_course_course_student
    ON student_course(course_id, student_id);
~~~

Nếu thường xuyên lọc theo status, có thể xem xét index phù hợp với truy vấn thực tế, ví dụ index ghép (student_id, status, course_id). Không tạo index tùy tiện vì mỗi index làm tăng chi phí insert, update và delete. Hãy dùng execution plan và số liệu tải để chọn.

## 17. Phân trang danh sách liên kết

Một sinh viên có thể tham gia hàng nghìn khóa học hoặc một khóa học có hàng chục nghìn người học. Không nên trả toàn bộ danh sách trong một request.

Ví dụ phân trang offset:

~~~java
public Flux<CourseSummary> findCourses(
        Long studentId,
        int limit,
        long offset) {

    return databaseClient.sql("""
            SELECT c.id, c.title, sc.status AS enrollment_status
            FROM student_course sc
            JOIN course c ON c.id = sc.course_id
            WHERE sc.student_id = :studentId
            ORDER BY c.title, c.id
            LIMIT :limit OFFSET :offset
            """)
            .bind("studentId", studentId)
            .bind("limit", limit)
            .bind("offset", offset)
            .map((row, metadata) -> new CourseSummary(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

Giá trị limit và offset phải được kiểm tra ở service/controller: limit cần có mức tối đa và offset không âm. Thứ tự ORDER BY nên có khóa phụ duy nhất để các trang không bị xáo trộn khi có tiêu đề trùng.

Với dữ liệu lớn hoặc liên tục thay đổi, keyset pagination thường ổn định hơn offset. Ví dụ, trang tiếp theo có thể lọc theo (title, id) lớn hơn cặp cuối của trang trước. Cần xây dựng điều kiện phù hợp với thứ tự sắp xếp và index.

## 18. Transaction khi thêm hoặc xóa nhiều liên kết

Một thao tác có thể thêm nhiều liên kết cùng lúc, ví dụ thêm sinh viên vào một nhóm khóa học. Nếu nghiệp vụ yêu cầu tất cả thành công hoặc thất bại cùng nhau, hãy dùng reactive transaction:

~~~java
@Transactional
public Flux<StudentCourse> enrollInCourses(
        Long studentId,
        List<Long> courseIds) {

    return Flux.fromIterable(courseIds)
            .concatMap(courseId ->
                    enrollmentRepository.save(new StudentCourse(
                            null,
                            studentId,
                            courseId,
                            Instant.now(),
                            "ACTIVE"
                    ))
            );
}
~~~

Ví dụ này minh họa việc ghi tuần tự các liên kết trong một transaction. Nếu một insert vi phạm unique constraint hoặc foreign key và lỗi được truyền ra ngoài, transaction có thể rollback toàn bộ lô theo cấu hình rollback.

Với danh sách rất lớn, transaction dài có thể giữ connection và khóa lâu. Có thể chia thành các lô với transaction riêng nếu nghiệp vụ chấp nhận kết quả từng phần. Khi đó cần có checkpoint, idempotency và cách tiếp tục sau lỗi.

Không gọi subscribe() bên trong phương thức transactional. Hãy trả publisher để Spring quản lý transaction context và thời điểm commit/rollback.

## 19. Kiểm thử mô hình nhiều-nhiều

Integration test nên xác nhận cả schema và hành vi:

1. Tạo hai Student và hai Course.
2. Tạo nhiều hàng StudentCourse để chứng minh một Student liên kết được nhiều Course và một Course liên kết được nhiều Student.
3. Xác nhận unique constraint từ chối cặp student_id/course_id trùng.
4. Xác nhận foreign key từ chối ID Student hoặc Course không tồn tại.
5. Truy vấn JOIN theo studentId và courseId để kiểm tra cả hai chiều.
6. Xóa một liên kết và xác nhận Student/Course vẫn còn.
7. Kiểm tra hành vi khi xóa Student hoặc Course theo chính sách foreign key đã chọn.
8. Kiểm tra transaction rollback khi một insert trong lô thất bại.

Ví dụ kiểm thử reactive:

~~~java
StepVerifier.create(
        studentCourseRepository.findByStudentId(studentId)
)
        .expectNextCount(2)
        .verifyComplete();

StepVerifier.create(
        enrollmentService.unenroll(studentId, courseId)
)
        .expectNext(1L)
        .verifyComplete();
~~~

Các test cần dùng dữ liệu độc lập và dọn dẹp sau khi chạy. Hãy chạy trên cùng loại database với môi trường triển khai để kiểm tra foreign key, unique constraint, transaction và cú pháp SQL thật.

## 20. Các lỗi thiết kế thường gặp

1. **Lưu danh sách ID trong một cột.** Khó bảo đảm foreign key, truy vấn và index.
2. **Thiếu bảng liên kết.** Quan hệ nhiều-nhiều không được biểu diễn chuẩn trong mô hình quan hệ.
3. **Thiếu unique constraint trên cặp khóa ngoại.** Hai request đồng thời có thể tạo liên kết trùng.
4. **Chỉ kiểm tra tồn tại ở Java.** Kiểm tra trước insert không thay thế foreign key và unique constraint.
5. **Giả định Spring Data R2DBC tự tải quan hệ.** Cần truy vấn repository hoặc JOIN rõ ràng.
6. **Dùng @MappedCollection như một cơ chế many-to-many ORM.** Nó phục vụ dữ liệu thuộc aggregate; tham chiếu đến aggregate độc lập nên được biểu diễn bằng ID và association entity.
7. **Dùng flatMap truy vấn từng đối tượng liên quan.** Có thể tạo N+1 query; cân nhắc JOIN hoặc truy vấn theo lô.
8. **Xóa Student rồi xóa Course liên quan.** Hủy một phía chỉ nên xóa các hàng link, không xóa đối tượng ở phía kia.
9. **Cascade sai chiều.** Xóa một Student không được xóa Course vẫn đang có người khác tham gia.
10. **Không có index cho chiều truy vấn ngược.** Truy vấn từ Course sang Student có thể chậm khi bảng liên kết lớn.
11. **Không giới hạn danh sách.** Tải tất cả liên kết có thể tốn bộ nhớ và tạo response quá lớn.
12. **Coi save link là upsert.** Repository save dựa trên trạng thái entity; dùng constraint và SQL upsert tường minh nếu cần tính idempotent.

## Quy tắc lựa chọn nhanh

- Dùng một bảng liên kết có hai foreign key để biểu diễn quan hệ nhiều-nhiều.
- Tạo unique constraint trên cặp khóa ngoại nếu một cặp chỉ được xuất hiện một lần.
- Mô hình hóa bảng liên kết thành entity riêng trong Spring Data R2DBC, đặc biệt khi nó có thuộc tính nghiệp vụ.
- Giữ ID của hai aggregate trong entity liên kết; tải thông tin hai phía bằng repository hoặc JOIN khi cần.
- Tạo index hỗ trợ truy vấn theo cả hai chiều.
- Xóa hàng liên kết khi hủy quan hệ; không xóa đối tượng ở phía còn lại.
- Dùng transaction reactive khi nhiều thao tác phải commit/rollback cùng nhau.
- Phân trang và tránh N+1 khi danh sách liên kết lớn.

Bảng liên kết là cách biểu diễn chuẩn cho quan hệ nhiều-nhiều trong cơ sở dữ liệu quan hệ. Trong Spring Data R2DBC, xem hàng liên kết như một entity có các khóa ngoại rõ ràng giúp ứng dụng quản lý việc tạo, đọc, cập nhật và xóa quan hệ một cách tường minh. Database bảo vệ tính toàn vẹn bằng foreign key và unique constraint; repository cùng DatabaseClient cung cấp các thao tác reactive; JOIN tạo read model hiệu quả khi cần thông tin từ cả hai phía. Cách thiết kế này giữ ranh giới aggregate rõ ràng và tránh phụ thuộc vào cơ chế tự động quản lý object graph của ORM.
