# Differences in Composite Keys, Upserts, Batches, and Savepoints

When working across multiple database engines in Spring Data Relational R2DBC, four areas deserve special attention: composite keys, upserts, batches, and savepoints. All four govern how databases identify records, execute multiple operations, and control transactions, yet their syntax and support levels vary across PostgreSQL, MySQL, SQL Server, Oracle, SQLite, and others.

Spring Data R2DBC provides common abstractions for repositories, mapping, and reactive transactions. Those abstractions do not make every SQL capability identical across databases. Specifically:

- Standard repository mapping is built around a single `@Id` identifier property; do not assume JPA's `@EmbeddedId` or `@IdClass` carry equivalent semantics.
- `save()` chooses INSERT or UPDATE based on entity newness state; it does not automatically perform an upsert on a unique key.
- `saveAll()` accepts multiple entities, yet does not guarantee every driver sends a single batch statement.
- Batch statements and multi-row INSERT syntax depend on the driver, database, and bind-parameter limits.
- Savepoints depend on database/driver and transaction manager capabilities; a savepoint is not an independent transaction.

For reliable multi-engine applications, keep portable Spring Data operations separate from dialect-specific SQL, and run integration tests against the exact R2DBC driver and target database.

## 1. The Big Picture

| Topic | Common Abstraction | Differences to Verify |
|---|---|---|
| Composite keys | Entity mapping, `@Id`, repository queries | Repository mapping across multiple key columns, unique constraints, NULLs, and collations |
| Upsert | `save()` and custom repositories | `ON CONFLICT`, `ON DUPLICATE KEY UPDATE`, `MERGE` syntax, and generated values |
| Batching | `saveAll()`, R2DBC `Statement.add()` | How the driver batches, parameter limits, partial errors, generated keys |
| Savepoints | R2DBC `Connection` and transaction manager | Database/driver support, release syntax, nested propagation |

A helpful rule of thumb: use Spring Data abstractions for CRUD operations that express cleanly across engines, and use explicit SQL or custom repositories for database-dependent features. Isolate engine-specific SQL inside clearly named adapters/repositories so business logic stays dialect-agnostic.

## 2. Single vs. Composite Primary Keys

A primary key uniquely identifies a row in a table. A single-column primary key uses one column:

~~~sql
CREATE TABLE customer (
    id BIGINT PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);
~~~

A composite primary key uses multiple columns:

~~~sql
CREATE TABLE tenant_customer (
    tenant_id BIGINT NOT NULL,
    external_customer_id VARCHAR(100) NOT NULL,
    name VARCHAR(200) NOT NULL,
    PRIMARY KEY (tenant_id, external_customer_id)
);
~~~

In this table, neither `tenant_id` alone nor `external_customer_id` alone is unique. Only the pair `(tenant_id, external_customer_id)` identifies a row.

Composite keys commonly appear in:

- Many-to-many join tables.
- Tenant-partitioned data.
- Tables storing external system reference codes.
- Tables keyed by language, region, or version.
- History tables keyed by business identifier plus timestamp or sequence.

Composite keys are a database capability. Just because a database allows multi-column PRIMARY KEYs does not mean every ORM/framework repository mapping can represent them directly.

## 3. Identifier Limitations in Spring Data Relational

Spring Data Relational mapping centers on a single entity identifier property annotated with `@Id`. Never assume JPA annotations such as `@EmbeddedId` or `@IdClass` work in Spring Data R2DBC the same way as in Hibernate.

Standard entity example:

~~~java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;
}
~~~

This entity has a single ID property. For schemas with two-column primary keys, verify the mapping strategy supported by your Spring Data Relational version. Do not simply create a `TenantCustomerId` class annotated with `@Id` assuming the framework automatically unpacks it into two composite key columns.

With standard CRUD repositories, the most predictable option is usually a surrogate key:

~~~sql
CREATE TABLE tenant_customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    external_customer_id VARCHAR(100) NOT NULL,
    name VARCHAR(200) NOT NULL,
    CONSTRAINT uq_tenant_customer_external
        UNIQUE (tenant_id, external_customer_id)
);
~~~

Entity:

~~~java
@Table("tenant_customer")
public class TenantCustomer {

    @Id
    private Long id;

    private Long tenantId;
    private String externalCustomerId;
    private String name;
}
~~~

The database still enforces uniqueness on `(tenant_id, external_customer_id)`, while the Spring Data repository uses `id` as the entity identifier.

### Surrogate Keys Do Not Replace Unique Business Keys

Adding an `id` column does not remove business uniqueness rules. If the pair of tenant and external ID must be unique, keep the unique constraint:

~~~sql
ALTER TABLE tenant_customer
ADD CONSTRAINT uq_tenant_customer_external
UNIQUE (tenant_id, external_customer_id);
~~~

Unique constraints guard data against race conditions across concurrent requests or application instances. Checking in Java before inserting cannot replace database constraints.

## 4. When Schemas Must Retain Composite Keys

If adding a surrogate key is impossible because the schema is already standardized on composite keys or owned externally, write a custom repository using `DatabaseClient` that filters by every key component.

Example reading a row:

~~~java
public Mono<TenantCustomerView> findByBusinessKey(
        Long tenantId,
        String externalCustomerId) {

    return databaseClient.sql(
            "SELECT tenant_id, external_customer_id, name " +
            "FROM tenant_customer " +
            "WHERE tenant_id = :tenantId " +
            "AND external_customer_id = :externalCustomerId"
        )
        .bind("tenantId", tenantId)
        .bind("externalCustomerId", externalCustomerId)
        .map((row, metadata) -> new TenantCustomerView(
            row.get("tenant_id", Long.class),
            row.get("external_customer_id", String.class),
            row.get("name", String.class)
        ))
        .one();
}
~~~

In custom SQL, always include all key columns in:

- `WHERE` on reads.
- `WHERE` on `UPDATE`.
- `WHERE` on `DELETE`.
- `JOIN` conditions across tables.
- Upsert conflict targets where supported by the database.

Filtering by `tenant_id` alone risks updating or deleting unintended rows.

A custom repository can expose a contract centered on the business key:

~~~java
public interface TenantCustomerStore {

    Mono<TenantCustomerView> findByBusinessKey(
        Long tenantId,
        String externalCustomerId
    );

    Mono<Long> updateName(
        Long tenantId,
        String externalCustomerId,
        String newName
    );
}
~~~

The implementation uses `DatabaseClient` and maps results into DTOs or domain objects. This preserves the composite-key schema without assuming CRUD repositories support portable composite IDs.

## 5. Composite Unique Constraints and NULL Differences

Multi-column unique constraints ensure combinations of values do not collide:

~~~sql
UNIQUE (tenant_id, external_customer_id)
~~~

However, databases handle NULLs in unique constraints differently. Many engines allow multiple rows containing NULL in one or more unique key columns because NULL is not considered equal to NULL under standard comparisons. Certain engines or versions offer options altering these semantics.

If business key components are mandatory, declare them `NOT NULL`:

~~~sql
tenant_id BIGINT NOT NULL,
external_customer_id VARCHAR(100) NOT NULL,
UNIQUE (tenant_id, external_customer_id)
~~~

Beyond NULLs, watch collations and string comparison rules:

- Some MySQL collations are case-insensitive by default.
- PostgreSQL `text`/`varchar` with default collations is typically case-sensitive in equality checks.
- SQL Server depends on database or column collations.
- SQLite uses declared collations such as `BINARY` or `NOCASE`.

Thus, `ABC` and `abc` may collide or remain distinct depending on the database/collation. If keys should be case-insensitive, normalize data or configure matching collations/indexes and test on the target engine.

## 6. save() Is Not an Upsert

In Spring Data R2DBC, `save(entity)` checks whether the entity is new or existing and chooses INSERT or UPDATE:

| Entity State | `save()` Behavior |
|---|---|
| New | INSERT |
| Existing | UPDATE |

Newness is determined via `Persistable.isNew()`, `@Version`, or `@Id` according to Spring Data Relational rules.

`save()` does not automatically execute SQL like:

~~~sql
INSERT ...
ON CONFLICT (...) DO UPDATE ...
~~~

Nor does it automatically run a `SELECT` first to check existence and branch dynamically. If an entity is treated as existing when the row is absent, `UPDATE` can affect zero rows. If an entity is treated as new when the unique key already exists, `INSERT` can fail with a constraint violation.

### Why SELECT-Then-INSERT Does Not Replace Upsert

A pattern prone to race conditions:

~~~text
Request A: SELECT key -> not found
Request B: SELECT key -> not found
Request A: INSERT key -> succeeds
Request B: INSERT key -> duplicate key
~~~

Application-level pre-checks are not atomic with inserts. Unique constraints act as the final safeguard, whereas database-native upserts resolve conflicts atomically in one statement per the engine's semantics.

## 7. What Is an Upsert?

An upsert combines insert and update:

- If the conflict key does not exist yet, insert a new row.
- If the conflict key already exists, update the specified columns.

A common use case is syncing records from external systems by business key:

~~~text
Receive (tenant_id, external_id, name)
                 |
                 v
           Database checks
                 |
          +------+------+
          |             |
      Not present    Present
          |             |
          v             v
        INSERT        UPDATE
          |             |
          +------+------+
                 |
                 v
      Return persisted result
~~~

Upserts typically rely on a PRIMARY KEY or a UNIQUE constraint/index. Without a matching uniqueness constraint, the database has no reliable conflict target to distinguish which row to update.

## 8. PostgreSQL: INSERT ... ON CONFLICT

PostgreSQL supports `ON CONFLICT`:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (
    :tenantId,
    :externalCustomerId,
    :name
)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET
    name = EXCLUDED.name;
~~~

`EXCLUDED` refers to the row proposed for insertion. Conflict targets can specify a column list or a matching constraint.

To return the row after upsert:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (:tenantId, :externalCustomerId, :name)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name
RETURNING id, tenant_id, external_customer_id, name;
~~~

Spring `DatabaseClient` can run PostgreSQL SQL and map results:

~~~java
Mono<TenantCustomerView> upsert =
    databaseClient.sql(postgresUpsertSql)
        .bind("tenantId", tenantId)
        .bind("externalCustomerId", externalId)
        .bind("name", name)
        .map((row, metadata) -> new TenantCustomerView(
            row.get("id", Long.class),
            row.get("tenant_id", Long.class),
            row.get("external_customer_id", String.class),
            row.get("name", String.class)
        ))
        .one();
~~~

This SQL is PostgreSQL-specific. Never send it unchanged to MySQL or SQL Server.

## 9. MySQL: INSERT ... ON DUPLICATE KEY UPDATE

MySQL supports `ON DUPLICATE KEY UPDATE`. When an insert violates a primary key or unique key, the database executes the update branch:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (
    :tenantId,
    :externalCustomerId,
    :name
) AS incoming
ON DUPLICATE KEY UPDATE
    name = incoming.name;
~~~

Row alias syntax after `VALUES` depends on the MySQL version. Older versions commonly used `VALUES(name)` in the update clause; `VALUES()` is deprecated in newer MySQL releases. Check documentation for your deployed database version.

Unlike PostgreSQL, MySQL does not specify an explicit conflict target in `ON DUPLICATE KEY UPDATE`. Any colliding primary key or unique key can trigger the update branch. Keep this in mind when tables have multiple independent unique constraints.

MariaDB has its own syntax and support history; never assume every MySQL alias syntax works across all MariaDB versions.

## 10. SQLite: UPSERT With ON CONFLICT

SQLite supports UPSERT syntax of the form:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES (:tenantId, :externalId, :name)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET
    name = excluded.name;
~~~

The `excluded` keyword references the proposed insert values. UPSERT was introduced in SQLite 3.24.0; verify the SQLite version bundled with your driver.

SQLite also differs in concurrency and locking compared to multi-connection database servers. Under concurrent writers, check busy timeouts, journal mode, and how the driver handles transactions.

## 11. SQL Server and Oracle: MERGE

SQL Server and Oracle support `MERGE` with distinct syntax. SQL Server illustrative example:

~~~sql
MERGE INTO dbo.tenant_customer AS target
USING (
    SELECT
        @tenantId AS tenant_id,
        @externalId AS external_customer_id,
        @name AS name
) AS source
ON target.tenant_id = source.tenant_id
AND target.external_customer_id = source.external_customer_id
WHEN MATCHED THEN
    UPDATE SET name = source.name
WHEN NOT MATCHED THEN
    INSERT (tenant_id, external_customer_id, name)
    VALUES (
        source.tenant_id,
        source.external_customer_id,
        source.name
    );
~~~

SQL Server `MERGE` carries known caveats around concurrency, triggers, and race conditions. Do not pick `MERGE` solely for brevity. Read the guidance and caveats for your SQL Server version and test under concurrent load. Some systems opt for an `UPDATE`-then-`INSERT` pattern inside a transaction with proper unique constraints and locking.

Oracle also has `MERGE INTO ... USING ... WHEN MATCHED ... WHEN NOT MATCHED ...`, yet bind markers, syntax, and result retrieval differ from SQL Server. The statement above cannot run unchanged on Oracle.

## 12. Quick Comparison of Upsert Syntax

| Database Engine | Common Approach | Notes |
|---|---|---|
| PostgreSQL | `INSERT ... ON CONFLICT ... DO UPDATE` | Supports conflict target and `RETURNING` |
| MySQL | `INSERT ... ON DUPLICATE KEY UPDATE` | Any conflicting unique key can trigger update; alias syntax depends on version |
| MariaDB | `INSERT ... ON DUPLICATE KEY UPDATE` | Verify version differences against MySQL |
| SQLite | `INSERT ... ON CONFLICT ... DO UPDATE` | Requires UPSERT-capable SQLite version |
| SQL Server | `MERGE` or locked `UPDATE`/`INSERT` pattern | Check concurrency and version semantics |
| Oracle | `MERGE INTO` | Engine-specific syntax, non-portable |

No single SQL upsert runs unmodified on all databases. If supporting multiple engines, you can:

- Build dialect-specific repository implementations.
- Use a database-selected strategy/adapter.
- Leverage Spring Data Dialect or metadata where abstractions support it.
- Keep business logic calling a shared interface while SQL resides in concrete implementations.

## 13. Designing Upserts Around Composite Keys

For a business key consisting of `tenant_id` and `external_customer_id`, ensure a matching unique constraint exists:

~~~sql
ALTER TABLE tenant_customer
ADD CONSTRAINT uq_tenant_external
UNIQUE (tenant_id, external_customer_id);
~~~

PostgreSQL can then target that conflict key:

~~~sql
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name
~~~

MySQL triggers `ON DUPLICATE KEY UPDATE` on any conflicting unique key. Thus, if a table has both a unique email and a unique external ID, consider whether an email collision could update the wrong row.

Design guidelines:

- Mandatory business key columns should be `NOT NULL`.
- Unique constraints must reflect tenant scoping accurately.
- Never omit `tenant_id` from conflict targets if the same external ID can exist across tenants.
- Never let upserts overwrite columns owned by another system unless business rules allow it.
- Define explicitly which columns update on conflict and which stay immutable.
- If detecting whether old data differs from new data, compare explicitly or guard the update predicate.

## 14. Returning IDs and Data After Upsert

Capabilities for returning generated IDs or rows after an upsert differ:

- PostgreSQL supports `RETURNING`.
- SQL Server supports `OUTPUT INSERTED...` in many DML forms.
- MySQL typically returns generated keys through driver/API mechanisms, yet returning full rows on the update branch is not equivalent to PostgreSQL `RETURNING`.
- Oracle uses its own returning mechanism and syntax.
- SQLite supports `RETURNING` in newer versions.

The R2DBC driver governs how results are exposed to the application. Never assume `DatabaseClient.fetch().one()` behaves identically across all upsert statements or drivers.

If you only need affected row counts, use the rows-updated API. If you need the entity after upsert, pick a database/driver-supported row-returning syntax and map to a DTO. If the driver does not return rows as needed, follow up with a query in the same transaction by business key.

## 15. What Is a Batch?

Batching groups multiple similar operations to reduce the overhead of dispatching individual statements. Several mechanisms exist:

1. Sending the same prepared statement multiple times with different parameter sets.
2. Using one `INSERT` statement with multiple `VALUES` tuples.
3. Using framework or database bulk insert/update APIs.
4. Executing a group of SQL statements inside one transaction.

These approaches are not synonymous:

| Approach | Description |
|---|---|
| Multiple `save()` calls | Framework processes each entity individually |
| `saveAll()` | Accepts a `Publisher` of entities; actual execution depends on framework/version |
| R2DBC `Statement.add()` | Adds multiple bind parameter sets to one statement |
| Multi-row `INSERT` | Single SQL statement with multiple `VALUES` sets |
| Transaction | Ensures grouped operations commit/roll back together when all participate in the transaction |

Batching reduces round trips or statement preparation costs, yet does not automatically provide atomicity without a transaction.

## 16. saveAll() Is Not Necessarily a Single SQL Batch

Repositories expose:

~~~java
Flux<Customer> saveAll(Publisher<Customer> entities);
~~~

This method is convenient for saving an entity stream. However, do not assume `saveAll()` always collapses the entire `Publisher` into one multi-row `INSERT` or one R2DBC batch statement. Actual behavior depends on Spring Data version, entity type, new/existing state, and the driver.

Example:

~~~java
Flux<Customer> saved =
    customerRepository.saveAll(
        Flux.fromIterable(customers)
    );
~~~

To ensure all entities commit or roll back together:

~~~java
@Transactional
public Flux<Customer> saveCustomers(List<Customer> customers) {
    return customerRepository.saveAll(
        Flux.fromIterable(customers)
    );
}
~~~

The transaction groups operations to commit or roll back together when they share the transaction context. It does not guarantee the driver sends only one batch.

Inspect actual SQL/driver behavior or version-specific documentation before claiming `saveAll` executes as a single batch.

## 17. R2DBC SPI Statement.add()

The R2DBC SPI lets you attach multiple parameter sets to a single statement via `Statement.add()`, when supported by the driver.

Example with a three-parameter `INSERT`:

~~~java
Statement statement = connection.createStatement(
    "INSERT INTO tenant_customer " +
    "(tenant_id, external_customer_id, name) " +
    "VALUES ($1, $2, $3)"
);

statement
    .bind(0, 10L)
    .bind(1, "ext-001")
    .bind(2, "An")
    .add();

statement
    .bind(0, 10L)
    .bind(1, "ext-002")
    .bind(2, "Binh");

Publisher<? extends Result> results = statement.execute();
~~~

Walkthrough:

1. Create a statement with bind markers.
2. Bind the first parameter set.
3. Call `add()` to queue the current parameter set into the batch.
4. Bind the next parameter set.
5. Call `execute()` to run the batch.

Marker indices start at 0 in the R2DBC SPI. The `$1, $2, $3` syntax in the example reflects drivers like PostgreSQL; other drivers use different markers.

### Handling Batch Results Example

~~~java
Flux<Long> rowCounts =
    Flux.from(statement.execute())
        .concatMap(Result::getRowsUpdated);
~~~

Exact results and how drivers emit `Result` objects depend on the implementation. To compute total rows:

~~~java
Mono<Long> totalRows =
    rowCounts.reduce(0L, Long::sum);
~~~

Never assume every batch element consistently yields one `Result` or one row count identically across all drivers. Test on the target driver and consult driver documentation.

### Binding NULLs in Batches

When a value in a parameter set is null, call `bindNull()` with the Java type:

~~~java
statement
    .bind(0, 10L)
    .bind(1, "ext-003")
    .bindNull(2, String.class)
    .add();
~~~

Never pass Java `null` to `bind()`. After `add()`, bind every parameter in the next set in exact marker order.

## 18. Batching via Multi-Row INSERT

Another approach uses one `INSERT` statement with multiple `VALUES` tuples:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES
    (:tenant1, :external1, :name1),
    (:tenant2, :external2, :name2),
    (:tenant3, :external3, :name3);
~~~

Advantages:

- Reduces statement count and network round trips.
- SQL clearly expresses inserting a group of rows together.
- Can be combined with engine-supported upsert syntax.

Limitations:

- Bind parameter count scales with row count.
- SQL length and packet size limits differ across databases.
- Unique placeholder names are needed for every value when using named parameters.
- Generated key retrieval behavior varies.
- Overly large batches consume memory and extend transaction hold times.

For large datasets, split inputs into appropriately sized chunks instead of building a giant SQL statement.

## 19. Batches, Transactions, and Partial Errors

Batching does not automatically guarantee atomicity.

Running multiple statements without a shared transaction can result in:

~~~text
INSERT row 1 -> succeeds
INSERT row 2 -> succeeds
INSERT row 3 -> fails
INSERT row 4 -> skipped or still processed depending on driver batching
~~~

The first two rows may already be committed depending on auto-commit and driver execution. When all-or-nothing atomicity is needed, wrap the batch in a transaction:

~~~java
return transactionalOperator.transactional(
    executeBatch(connectionFactory, items)
);
~~~

Transactions only protect operations running on the connection managed by the transaction manager. If a batch runs on a manually acquired connection outside the transaction context, it may not join that transaction.

For massive batches, you can chunk data and wrap each chunk in its own transaction. Atomicity then applies per chunk; earlier chunks remain committed if a later chunk fails. Document this as an explicit business decision.

## 20. Batch Limits Vary Across Databases

Database engines impose different constraints and behaviors:

- Maximum bind parameter count.
- Maximum SQL statement or packet length.
- Batch sizes the driver handles efficiently.
- Support for generated keys or `RETURNING` inside batches.
- Error reporting when an item mid-batch fails.
- Duplicate key handling in multi-row inserts.

For example, SQL Server limits parameters per request; Oracle has limits in certain expressions like `IN` lists; MySQL enforces packet size limits; PostgreSQL and its driver have practical limits on bind counts and statement size.

Never copy a hardcoded batch size blindly across databases. Measure throughput, latency, memory, and connection usage in production-like environments.

## 21. Batching With Composite Keys and Upserts

When syncing multiple tenant customers, each row carries the business key `(tenant_id, external_customer_id)`. You can batch upserts where supported:

~~~sql
INSERT INTO tenant_customer (
    tenant_id,
    external_customer_id,
    name
)
VALUES
    (:tenant1, :external1, :name1),
    (:tenant2, :external2, :name2)
ON CONFLICT (tenant_id, external_customer_id)
DO UPDATE SET name = EXCLUDED.name;
~~~

This is a PostgreSQL example. Before using it:

- Ensure the unique constraint exists on that exact column pair.
- Ensure the batch does not contain duplicate conflict keys if the statement or engine forbids updating the same target row twice in one statement.
- Define policies when two records in the same batch share a business key with different values.
- Chunk inputs to cap parameter counts.
- Test generated values and row counts.

With MySQL, upsert syntax and conflict semantics differ; with SQL Server/Oracle, use dialect-specific strategies. Never place a non-portable batch upsert SQL inside a shared multi-database repository.

## 22. What Is a Savepoint?

A savepoint marks a point inside an open transaction. It enables rolling back part of the work to that marker while keeping the outer transaction active, where supported by the database and driver.

~~~text
BEGIN
  |
  v
Write primary data
  |
  v
SAVEPOINT optional_part
  |
  v
Execute optional work
  |
  +---- Succeeds ----> RELEASE SAVEPOINT
  |                         |
  |                         v
  |                   Continue transaction
  |
  +---- Fails -------> ROLLBACK TO SAVEPOINT
                            |
                            v
                      Continue transaction
  |
  v
COMMIT or ROLLBACK outer transaction
~~~

Savepoints do not commit independently. When the outer transaction commits, all remaining changes after the savepoint commit together. When the outer transaction rolls back, all changes in the transaction are discarded—including work prior to the savepoint.

## 23. Savepoints vs. REQUIRES_NEW

Two mechanisms are frequently confused:

| Mechanism | Connection/Transaction | On Rollback |
|---|---|---|
| Savepoint | Same outer transaction and connection | Reverts to marker; outer transaction can continue |
| `PROPAGATION_NESTED` | Typically implemented via savepoints if manager supports it | Rolls back nested part to savepoint |
| `PROPAGATION_REQUIRES_NEW` | Independent transaction; usually requires a separate connection while outer suspends | Rolls back independent transaction without rolling back outer |

Savepoints do not release connections or create independent commits. `REQUIRES_NEW` can require a second connection while the outer transaction still holds its connection, demanding careful pool sizing to avoid connection starvation.

If business logic requires audit records or technical logs to commit independently, savepoints cannot achieve that. Use a separate transaction or an appropriate durable logging mechanism.

## 24. Savepoints in the R2DBC SPI

The R2DBC SPI exposes savepoint methods on `Connection`:

- `createSavepoint(name)`: creates a savepoint.
- `rollbackTransactionToSavepoint(name)`: rolls back to a savepoint.
- `releaseSavepoint(name)`: releases a savepoint if supported by the database/driver.

These methods return `Publisher`s and must be composed inside reactive chains. Never subscribe manually or block.

Illustrative example using a Spring transaction-managed connection:

~~~java
public Mono<Void> runOptionalWork() {
    return ConnectionFactoryUtils.getConnection(connectionFactory)
        .flatMap(connection ->
            Mono.from(connection.createSavepoint("optional_work"))
                .then(
                    optionalRepository.perform()
                        .onErrorResume(error ->
                            Mono.from(
                                connection.rollbackTransactionToSavepoint(
                                    "optional_work"
                                )
                            ).then()
                        )
                )
        );
}
~~~

This must be invoked inside an active transaction on the same `ConnectionFactory`. `ConnectionFactoryUtils.getConnection()` retrieves the connection bound to the transaction context when present. Never manually close a transaction-bound connection; the transaction manager releases it.

This example intentionally recovers from errors in the optional block after rolling back to the savepoint. If an error must not be suppressed, let it propagate so the outer transaction rolls back.

### Releasing Savepoints

After optional work succeeds, you can call `releaseSavepoint()` if supported by the driver/database:

~~~java
Mono.from(connection.releaseSavepoint("optional_work"));
~~~

Not every database shares the same release syntax. SQL Server and Oracle differ from PostgreSQL, MySQL, and SQLite; the R2DBC driver maps the SPI call to actual engine capabilities. If releasing is unsupported, consult driver and database documentation rather than assuming the call always succeeds.

## 25. Savepoints and Propagation.NESTED

Spring's `NESTED` propagation models a nested transactional scope inside an existing transaction. On supporting transaction managers, this scope is typically implemented via savepoints.

Example:

~~~java
@Transactional(transactionManager = "r2dbcTransactionManager")
public Mono<Void> outerOperation() {
    return writeMainRecord()
        .then(optionalService.writeOptionalRecord());
}
~~~

When using `NESTED` on `optionalService`, configure propagation on a Spring-proxied method call and verify that `R2dbcTransactionManager`, the R2DBC driver, and the database support savepoints in that scenario.

Not every transaction manager or driver supports nested transactions. If savepoints are unsupported, nested operations may throw errors rather than silently acting as independent transactions.

### NESTED Is Not REQUIRES_NEW

- `NESTED` shares the physical transaction and uses savepoints where supported.
- `REQUIRES_NEW` suspends the current transaction and opens an independent transaction per manager capabilities.
- Committing a nested scope does not commit the outer transaction.
- Committing a `REQUIRES_NEW` transaction can persist even if the outer transaction later rolls back.

Choose based on atomicity requirements, not propagation names alone.

## 26. Savepoint Differences Across Database Engines

| Database Engine | Typical Capabilities | Notes |
|---|---|---|
| PostgreSQL | `SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, `RELEASE SAVEPOINT` | Statement errors can put transaction in aborted state; rolling back to savepoint can restore transaction state |
| MySQL InnoDB | Savepoints within transactions | Engine must support transactions; does not apply identically to all storage engines |
| MariaDB | Savepoints in transactions with supporting engines | Verify engine and version |
| SQLite | Savepoints and nested transaction semantics | SQLite allows savepoints even outside explicit outer transactions with specific semantics |
| SQL Server | `SAVE TRANSACTION`, `ROLLBACK TRANSACTION savepoint_name` | No `RELEASE SAVEPOINT` equivalent like PostgreSQL |
| Oracle | `SAVEPOINT`, `ROLLBACK TO SAVEPOINT` | Syntax and release behavior differ from other engines |

These are high-level summaries. An R2DBC driver may not fully implement every feature even if the underlying SQL engine supports it. Always verify your driver version and run integration tests.

Some DDL statements have different transactional semantics or cause implicit commits depending on the database. Never use savepoints assuming all DDL rolls back like DML.

## 27. Combining Batches and Savepoints

Savepoints help when part of a batch is optional:

1. Start the outer transaction.
2. Write mandatory data.
3. Create a savepoint.
4. Execute the optional batch.
5. If the batch succeeds, continue.
6. If the batch fails and the engine allows rolling back to the savepoint, roll back the batch portion and handle fallback business logic.
7. Commit the outer transaction.

Conceptual example:

~~~java
return transactionalOperator.transactional(
    writeRequiredData()
        .then(createSavepointAndRunOptionalBatch())
        .then(writeFinalStatus())
);
~~~

If a batch insert hits a duplicate key, the database may mark the transaction as failed. In PostgreSQL, you must roll back to the savepoint before executing further statements in that transaction. Merely catching the exception with `onErrorResume` without rolling back to the savepoint does not guarantee the transaction can continue.

If a batch failure must abort the entire operation, do not swallow the error or use savepoints; let the error propagate and roll back the outer transaction.

## 28. Choosing Batch Sizes and Savepoint Boundaries

Batch size affects:

- Bind parameter count.
- Packet or statement size.
- Application memory consumption.
- Connection hold duration.
- Granularity of partial rollback.
- Latency and throughput.

Savepoint boundaries determine partial rollback scope. Avoid creating a savepoint for every single row in a large batch unless business logic demands it; excessive savepoints add overhead.

A common strategy:

- Split data into moderately sized chunks.
- Wrap each chunk in its own transaction if partial chunk commits are acceptable.
- If multiple steps within one chunk need partial recovery, place savepoints at clear business boundaries.
- Track succeeded row counts, failed row counts, and offending business keys.

If all chunks must be atomic as a single unit, a massive transaction can hold connections and locks too long. Re-evaluate business requirements, consider staging tables, or use compensating workflows instead of giant transactions.

## 29. Designing Abstractions for Multiple Databases

Avoid branching SQL inside services by database type:

~~~java
if (databaseType.equals("postgres")) {
    // PostgreSQL SQL
} else if (databaseType.equals("mysql")) {
    // MySQL SQL
}
~~~

Instead, define a business-focused contract:

~~~java
public interface TenantCustomerUpsert {

    Mono<TenantCustomerView> upsert(
        Long tenantId,
        String externalId,
        String name
    );
}
~~~

Then supply dialect-specific implementations:

~~~text
TenantCustomerUpsert
        |
        +-- PostgresTenantCustomerUpsert
        |
        +-- MySqlTenantCustomerUpsert
        |
        +-- SqlServerTenantCustomerUpsert
~~~

Each implementation uses a `DatabaseClient` wired to the right `ConnectionFactory`. Select implementations via Spring profiles, conditional configuration, or explicit startup wiring.

Similarly, you can extract contracts for batch writers and savepoint executors if those capabilities are core to your architecture. Avoid over-abstracting when deploying on a single database; abstract only the differences you truly need to support.

## 30. Testing With the Real Database and R2DBC Driver

Mock repositories cannot prove that upsert, batch, or savepoint syntax works on a real database. Use integration tests with Testcontainers or matching database instances.

### Testing Composite Keys

- Insert two rows with the same external ID under different tenants.
- Insert duplicates matching both tenant ID and external ID.
- Confirm the unique constraint rejects duplicates.
- Test NULL behavior if allowed by the schema.
- Test collation/case sensitivity on business keys.
- Confirm `UPDATE`/`DELETE` always include all key components.

### Testing Upsert

- Missing key: inserts a new row.
- Existing key: updates only permitted columns.
- Conflict on another unique key: verify policy behavior.
- Concurrent upserts for the same key: no duplicates created.
- Verify returned ID and post-upsert values.
- Verify created/updated timestamps and version fields if present.

### Testing Batches

- Single-item and multi-item batches.
- Batches containing nulls requiring `bindNull`.
- Batches exceeding typical chunk sizes.
- Failure on an item mid-batch.
- Verify row counts and generated keys.
- Verify transaction rollback across the full batch or per chunk per design.

### Testing Savepoints

- Create a savepoint after a successful write.
- Perform additional writes after the savepoint.
- Roll back to the savepoint.
- Confirm pre-savepoint writes remain and post-savepoint writes are reverted.
- Continue writing and commit the outer transaction.
- Test releasing savepoints where supported by the driver.
- Verify whether database errors recover cleanly after savepoint rollback.

## 31. Common Pitfalls

| Mistake | Consequence | Fix |
|---|---|---|
| Assuming JPA `@EmbeddedId` works identically in R2DBC | Broken repository mapping | Use a single `@Id` or custom repository for composite keys |
| Adding a surrogate ID and dropping unique business keys | Duplicate business records | Keep unique constraints across all key columns |
| Checking existence before INSERT only | Race conditions under concurrent requests | Rely on unique constraints and database upserts |
| Thinking `save()` is an upsert | Wrong INSERT/UPDATE branch | Use dialect-specific SQL upsert |
| Running PostgreSQL `ON CONFLICT` on MySQL | SQL syntax error | Separate implementations per database |
| Omitting tenant ID from conflict targets | Risk of updating another tenant's row | Include full business key |
| Ignoring NULL/collation rules in unique keys | Duplicate rules differ across DBs | Use `NOT NULL` and normalize/configure collations |
| Thinking `saveAll()` is always a batch | Statement count still scales per entity | Check implementation/driver; use SPI batching if needed |
| Calling `Statement.add()` with missing bind markers | Batch fails or shifts values into wrong columns | Bind every marker in each parameter set |
| Running an oversized batch | Hits parameter/packet limits, high memory use | Chunk and benchmark per database |
| Assuming batches are atomic | Partial commits can happen | Wrap in a transaction when all-or-nothing is required |
| Swallowing batch errors without savepoint rollback | Transaction may remain aborted | Roll back to savepoint or roll back transaction |
| Thinking savepoints are independent transactions | Misunderstood commit boundaries | Savepoints only mark points in the active transaction |
| Using `REQUIRES_NEW` instead of savepoints without sizing pools | Needs extra connections, risking pool exhaustion | Use `NESTED`/savepoints when appropriate |
| Assuming every driver supports releasing savepoints | Runtime error or unsupported operation | Check driver and database support |
| Putting dialect-specific SQL in shared repositories | Fails on other databases | Separate adapters/implementations |

## 32. Solution Selection Workflow

When designing data operations requiring composite keys, upserts, batches, or savepoints, check:

1. Does the table have a single-column or multi-column primary key?
2. Can Spring Data repositories map that identifier cleanly?
3. Can we use a surrogate ID while preserving a unique business key?
4. If retaining composite keys, does custom SQL include every key component?
5. Which database is deployed and what is its upsert syntax?
6. Is the conflict target backed by a unique constraint?
7. Must the upsert return an ID or full row?
8. Should batching use `saveAll`, SPI `Statement.add`, multi-row `INSERT`, or bulk SQL?
9. Does the driver support batching and generated values as expected?
10. Must the batch be atomic overall, per chunk, or allow partial success?
11. Is partial rollback inside a transaction required?
12. Do the database and driver support savepoints and releasing savepoints?
13. Does the transaction manager support `NESTED`, or is an independent transaction needed?
14. Have tests run under concurrency on the exact database and driver versions?

## 33. Key Takeaways

- Spring Data Relational repository mapping centers on a single `@Id` property; it does not support JPA `@EmbeddedId`/`@IdClass` by default.
- For composite keys, either use a surrogate primary key paired with a unique business key constraint, or retain the composite PK with custom SQL/repositories that always bind every key column.
- NULLs, collations, and case sensitivity can alter unique key semantics across engines.
- `save()` picks INSERT or UPDATE via new-state detection; it is not a database-native upsert.
- PostgreSQL/SQLite typically use `ON CONFLICT`; MySQL/MariaDB use `ON DUPLICATE KEY UPDATE`; SQL Server/Oracle have engine-specific `MERGE` syntax and semantics.
- Safe upserts require an appropriate primary key or unique constraint; `SELECT`-then-`INSERT` does not prevent race conditions.
- `saveAll()` does not guarantee a single batch statement.
- R2DBC SPI `Statement.add()` binds multiple parameter sets to one statement when supported by the driver; fully bind each set and verify row counts.
- Multi-row `INSERT`, SPI batching, and transactions are three distinct concepts.
- Batches are not automatically atomic; use transactions when all operations must commit or roll back together.
- Batch size and parameter limits depend on database, driver, and version.
- Savepoints mark a point within an active transaction; rolling back to a savepoint never commits other parts independently.
- `PROPAGATION_NESTED` typically relies on savepoints where supported; `REQUIRES_NEW` creates an independent transaction.
- The R2DBC SPI exposes `createSavepoint`, `rollbackTransactionToSavepoint`, and `releaseSavepoint`; real support depends on the driver and database.
- Isolate dialect-specific SQL in dedicated implementations and test against real databases and drivers.
