# Designing Tables, Indexes, and Constraints for Queries

In a Spring Data Relational R2DBC application, query performance and correctness depend heavily on database schema design. Entity mapping maps Java properties to tables and columns, but it cannot compensate for unstable primary keys, relationships without foreign keys, misordered index columns, or data types unsuited to filter predicates.

Good schema design starts from the queries the application actually runs: finding a record by ID, filtering by status, fetching the latest list, joining data by foreign key, paginating, counting, or conditional updates. From those access patterns, select primary keys, foreign keys, unique/check/not-null constraints, and indexes. Then inspect execution plans with data scaled near real-world volume.

Spring Data R2DBC provides mapping metadata via `@Table`, `@Column`, `@Id`, `@Version`, and repository/template APIs. These describe how Java objects correspond to the schema. Creating tables, altering columns, adding indexes, and adding constraints should be managed via versioned migrations such as Flyway or Liquibase. Do not treat entity annotations as a substitute for schema design and deployment.

## 1. Start from Queries, Not from a Field List

A table is usually structured around business data, while indexes must be designed around how data is read and written. Before creating indexes, list the critical queries and describe:

- Which table is read?
- Which columns appear in filter conditions?
- Which keys are used in joins?
- Which columns and directions are used for sorting?
- Is pagination using `LIMIT/OFFSET` or a cursor?
- How many columns does the query fetch, and does it aggregate?
- What are the expected read/write frequencies and data sizes?

For example, a customer screen might run the following queries:

| Access Pattern | Typical SQL | Schema Considerations |
| --- | --- | --- |
| Find by ID | `WHERE id = :id` | Primary key/index on `id` |
| Find customer by email | `WHERE email = :email` | Unique constraint/index if email is unique |
| Filter active customers | `WHERE status = 'ACTIVE'` | Index value depends on selectivity and companion filters |
| List by tenant, newest first | `WHERE tenant_id = :tenant ORDER BY created_at DESC, id DESC` | Composite index matching filter and sort |
| Fetch orders of a customer | `WHERE customer_id = :id ORDER BY created_at DESC` | Index on `orders.customer_id` and potentially sort column |
| Count orders per customer | `WHERE customer_id = :id` | Foreign key index can assist |
| Next-page pagination | Predicate on `(created_at, id)` | Composite index matching cursor and sort |

Do not create a separate index for every column just because that column exists on the entity. Each index should support a specific query or a group of queries sharing an access pattern. Redundant indexes increase storage, insert/update/delete overhead, and database maintenance work.

## 2. Designing Tables Around Entities and Aggregates

Spring Data Relational maps entities to relational tables. A simple entity can be declared as:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("tenant_id")
    private UUID tenantId;

    private String email;

    private String name;

    private String status;

    // Constructors, getters, and setters.
}
```

`@Table` specifies the table name, `@Column` maps a property to a column, and `@Id` marks the identifier. These annotations do not prove the columns exist or that the schema has the right constraints/indexes. Database migrations must create the corresponding schema.

### Data Normalization

Normalization avoids duplicate data storage and preserves consistency. For example, if multiple orders belong to one customer, customer name/email usually lives in the `customer` table, while `orders` stores `customer_id` as a foreign key.

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    order_number VARCHAR(40) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL
);
```

If `customer_name` were duplicated in every order, it could drift out of sync when a customer changes their name. However, there are intentional snapshot cases, such as storing the recipient name and shipping address at order placement time. In that case, duplicated data carries historical meaning and is not a normalization error.

Table design should distinguish current reference data from immutable business snapshots. Do not join back to current mutable data if business rules require preserving values from the time of the transaction.

## 3. Choosing a Primary Key

A primary key uniquely identifies a row and serves as the target of foreign key relationships. A good key is stable, non-null, and unique.

### Auto-Increment Numeric Keys

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Pros:

- Compact, easy to join and pass through APIs.
- Indexes are typically more compact than long string keys.
- Sequential increments can improve B-tree index locality for normal inserts.

Points to consider:

- IDs may leak approximate ordering or record volume.
- When writing data from multiple independent systems, an appropriate ID allocation strategy is needed.
- Never assume sequences are gap-free; rollbacks or pre-insert ID allocation can create gaps.

### UUID

```sql
id UUID PRIMARY KEY
```

UUIDs are convenient when identifiers must be generated in the application or across multiple nodes without requesting a shared sequence. However, UUIDs are larger than `BIGINT`; random UUIDs can scatter index inserts and increase page splits/cache pressure depending on the database and workload. If choosing UUID, consider locality-friendly UUIDs such as UUIDv7 if supported by the ecosystem and compatible with security/predictability requirements.

### Natural Keys and Surrogate Keys

Email, order number, or product code may be business keys. They should typically be protected by unique constraints, though they do not need to be primary keys. You can use a surrogate key like `BIGINT`/`UUID` as the PK and add a unique constraint for the business key.

Example:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    CONSTRAINT uk_customer_email UNIQUE (email)
);
```

If the uniqueness rule is scoped per tenant:

```sql
CONSTRAINT uk_customer_tenant_email UNIQUE (tenant_id, email)
```

Include the exact business scope in the unique constraint. If email only needs to be unique within a tenant, a unique constraint on `email` alone is too strict; if email must be globally unique, a unique constraint on `(tenant_id, email)` is insufficient.

## 4. Foreign Keys Protecting Relationships

Foreign keys guarantee that referenced values point to a valid row in the parent table:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customer(id)
);
```

`NOT NULL` on `customer_id` expresses that an order must belong to a customer. If the relationship is optional, the column can be nullable and the foreign key is checked only when the value is non-null.

Foreign keys protect data integrity even when writes come from multiple services, jobs, or direct SQL. Checking only in Java is insufficient because two concurrent requests can pass the check before one deletes the parent row.

### Indexing Foreign Keys

Many databases automatically create indexes for primary keys and unique constraints, but not every database automatically indexes foreign key columns. For example, PostgreSQL does not automatically create an index on `orders.customer_id` merely because a foreign key is declared.

If the application frequently runs:

```sql
SELECT id, order_number
FROM orders
WHERE customer_id = :customerId;
```

consider adding:

```sql
CREATE INDEX idx_orders_customer_id
ON orders(customer_id);
```

This index can also help the database locate referencing orders when a customer is deleted or a referenced key is updated, avoiding full scans of the child table in relevant scenarios.

### ON DELETE and ON UPDATE

Foreign keys can specify behavior when a parent row is deleted:

```sql
FOREIGN KEY (customer_id)
    REFERENCES customer(id)
    ON DELETE RESTRICT
```

Common options:

| Behavior | Meaning |
| --- | --- |
| `RESTRICT` / `NO ACTION` | Prevents deleting the parent row while child rows reference it, per database semantics |
| `CASCADE` | Deletes child rows when the parent row is deleted |
| `SET NULL` | Sets the foreign key on child rows to NULL if permitted |
| `SET DEFAULT` | Sets a default value if supported by the database and valid |

Only use `CASCADE` when child data lifecycle truly depends on parent data. Deleting a customer should not automatically delete invoices or legal records requiring long-term retention. Cascading behavior can affect many rows and generate heavy load; understand its scope before applying it.

## 5. Using NOT NULL, DEFAULT, and CHECK Constraints

Constraints enable the database to enforce data rules right at the storage layer.

### NOT NULL

```sql
email VARCHAR(320) NOT NULL,
status VARCHAR(20) NOT NULL
```

Use `NOT NULL` for required properties. When a column is required by business rules, validating `@NotNull` in Java alone does not protect against all write paths. Database constraints are the final line of defense.

### DEFAULT

```sql
status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
```

`DEFAULT` is used when an insert statement omits the column or uses the `DEFAULT` keyword. If the application always binds `NULL`, standard defaults do not replace null with the default value. Distinguish omitting a column from passing SQL NULL.

### CHECK

```sql
CONSTRAINT ck_orders_total_nonnegative
    CHECK (total_amount >= 0)
```

This constraint prevents negative amounts from being stored. Complex rules spanning multiple rows/tables cannot be expressed with simple CHECKs; those require unique/FK constraints, triggers, or transactional logic depending on business rules.

Example constraining status to a set of values:

```sql
CONSTRAINT ck_customer_status
    CHECK (status IN ('ACTIVE', 'INACTIVE', 'PENDING'))
```

CHECK is a database-level constraint, blocking invalid data regardless of whether writes come from repositories, batch imports, or direct SQL. If using native enums or database-specific types, weigh migration flexibility and cross-environment compatibility.

## 6. Unique Constraints vs. Existence Checks in the Application

An unsafe pattern is:

```java
return repository.findByEmail(email)
        .hasElement()
        .flatMap(exists -> exists
                ? Mono.error(new DuplicateEmailException())
                : repository.save(new Customer(email)));
```

Two concurrent requests can both read `false` and then both insert. Existence checks only assist in giving friendly feedback; they do not replace unique constraints.

Create the constraint:

```sql
ALTER TABLE customer
ADD CONSTRAINT uk_customer_email UNIQUE (email);
```

Then handle duplicate key errors according to business rules. You can check beforehand to return an error early, but the database must remain the guarantor of uniqueness.

### Unique Constraints May Allow Multiple NULLs

Unique semantics with `NULL` vary by database. Many engines treat NULLs as unequal and allow multiple null rows in a unique index; some engines support `NULLS NOT DISTINCT` or custom syntax. If a column must be both unique and required, combine `NOT NULL` with `UNIQUE` to avoid this discrepancy.

## 7. B-tree Indexes for Equality and Range Queries

B-tree is the default/common index type for equality, range, and sort queries in many relational databases.

Example:

```sql
CREATE INDEX idx_customer_status
ON customer(status);
```

Can assist:

```sql
SELECT id, name
FROM customer
WHERE status = 'ACTIVE';
```

As well as certain range/sort conditions depending on the database. However, if `status` has only a few values and most rows share one value, a single-column index on status may lack sufficient selectivity to beat a sequential scan. The optimizer may intentionally skip the index when scanning most of the table is cheaper.

Indexes do not always speed up queries. Examine matching row counts, selectivity, table size, and query plans.

## 8. Composite Indexes and Column Order

A composite index contains multiple columns in a specific order:

```sql
CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC);
```

This index can support:

```sql
SELECT id, order_number, created_at
FROM orders
WHERE customer_id = :customerId
  AND status = :status
ORDER BY created_at DESC;
```

Column order in an index matters. In B-trees, leading index columns normally determine the ability to locate a contiguous range. An index on `(customer_id, status, created_at)` is not equivalent to `(status, customer_id, created_at)`.

### Leftmost Prefix Rule

In many B-tree implementations, an index `(a, b, c)` is most useful for predicates starting from `a`, such as:

- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c >= ?`

It is generally not equally effective for `WHERE b = ?` without a predicate on `a`. Optimizer details vary by database, so do not expect a composite index to serve every column combination equally well.

### Equality, Range, and Sort

A useful starting guideline when designing composite indexes:

1. Columns commonly filtered with equality (`=`) or tenant/partition scope.
2. Range columns (`>`, `<`, `BETWEEN`) and seek columns.
3. Remaining sort columns in the exact order and direction needed by the query.

This is not an absolute formula. If queries have mixed patterns, mixed sort directions, or predicates with special selectivity, inspect execution plans. An index must match actual queries rather than just a theoretical rule.

Example query listing orders by tenant and time:

```sql
SELECT id, created_at, total_amount
FROM orders
WHERE tenant_id = :tenantId
  AND status = 'PAID'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Candidate index:

```sql
CREATE INDEX idx_orders_tenant_status_created_id
ON orders(tenant_id, status, created_at DESC, id DESC);
```

The first two columns support equality filters; the trailing columns support ordering. Measure with real cardinality and verify whether the optimizer uses the index.

## 9. Indexes for ORDER BY and Pagination

A paginated query requires deterministic ordering:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100;
```

Candidate index:

```sql
CREATE INDEX idx_article_status_created_id
ON article(status, created_at DESC, id DESC);
```

The index can help the database filter by status and scan in the requested order. Add `id` as a unique tie-breaker so pagination remains stable when multiple articles share the same `created_at`.

### Keyset Pagination

With cursor `(created_at, id)` in descending order:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
  AND (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Index `(status, created_at DESC, id DESC)` is a suitable candidate. Tuple comparison and optimization behavior depend on the database; lexicographic predicates can be written with `OR` if the dialect does not support tuple comparisons as needed.

If sort keys are nullable, specify `NULLS FIRST/LAST` and matching cursor predicates. Making sort keys `NOT NULL` is usually simplest.

## 10. Indexes for JOINs and Foreign Keys

Joins commonly use equality between foreign keys and primary keys:

```sql
SELECT c.id, c.name, o.id AS order_id
FROM customer c
JOIN orders o ON o.customer_id = c.id
WHERE c.id = :customerId;
```

Customer's primary key is already indexed. To look up orders by customer, an index on `orders.customer_id` is usually helpful:

```sql
CREATE INDEX idx_orders_customer_id
ON orders(customer_id);
```

If queries regularly fetch orders by customer sorted by time:

```sql
SELECT id, order_number, created_at
FROM orders
WHERE customer_id = :customerId
ORDER BY created_at DESC, id DESC;
```

Index `(customer_id, created_at DESC, id DESC)` can serve both predicate and sort. Avoid creating both a single-column `customer_id` index and a composite index starting with `customer_id` unless another workload proves the single-column index is still needed; redundant indexes increase write overhead.

### Many-to-Many

For many-to-many relationships, use a join table:

```sql
CREATE TABLE customer_group (
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    group_id BIGINT NOT NULL REFERENCES customer_group_type(id),
    PRIMARY KEY (customer_id, group_id)
);
```

The composite primary key `(customer_id, group_id)` supports looking up groups by customer and prevents duplicate associations. If the application also frequently looks up customers by group, add an index for the reverse direction:

```sql
CREATE INDEX idx_customer_group_group_customer
ON customer_group(group_id, customer_id);
```

A single composite index does not automatically serve both directions efficiently if the lookup column is not at an appropriate prefix.

## 11. Covering Indexes and INCLUDE

A query may only need a few columns:

```sql
SELECT id, created_at, title
FROM article
WHERE status = 'PUBLISHED'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

In PostgreSQL, you can consider `INCLUDE` to store extra payload columns in index leaf pages:

```sql
CREATE INDEX idx_article_status_created_id_cover
ON article(status, created_at DESC, id DESC)
INCLUDE (title);
```

This can enable an index-only scan when visibility map conditions and query shape align. `INCLUDE` is PostgreSQL-specific syntax and not supported identically across all databases.

Do not stuff every table column into an index just to make it covering. Large payloads bloat indexes, reduce cache efficiency, and increase write costs. Only include columns queried frequently with measurable benefit.

## 12. Partial Indexes for Frequently Queried Subsets

Some databases support partial/filtered indexes, indexing only rows matching a predicate. PostgreSQL example:

```sql
CREATE INDEX idx_orders_pending_created
ON orders(created_at DESC, id DESC)
WHERE status = 'PENDING';
```

This index can be much smaller than a full-table index if `PENDING` rows represent a small fraction. It fits queries with a matching predicate:

```sql
SELECT id, created_at
FROM orders
WHERE status = 'PENDING'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

The optimizer only uses a partial index when it can prove the query predicate implies the index predicate. If a query uses a generic or parameterized predicate preventing the planner from proving the relationship, the index may not be chosen in some plans.

Partial indexes are database-dependent; verify syntax and actual execution plans. Avoid them if strict portability across multiple database engines is required.

## 13. Expression Indexes and Case-Insensitive Queries

If the application regularly looks up emails case-insensitively, queries may use an expression:

```sql
SELECT id, email
FROM customer
WHERE LOWER(email) = LOWER(:email);
```

A regular index on `email` may not efficiently support the `LOWER(email)` expression. With PostgreSQL, you can create an expression index:

```sql
CREATE UNIQUE INDEX uk_customer_email_lower
ON customer(LOWER(email));
```

This index both supports expression lookups and enforces case-insensitive uniqueness if that matches business semantics. However, consider collation/Unicode rules and storing canonicalized emails.

An alternative is storing a normalized canonical value in a separate column, such as `email_normalized`, and creating a unique index on that column. This makes semantics explicit, though every write path must keep the canonical column updated in sync.

Expression indexes are database-specific. When using Spring Data derived queries with `IgnoreCase`, inspect the generated SQL and ensure the index matches the actual expression used by the dialect.

## 14. Indexes for LIKE and String Searches

B-trees can typically support prefix searches like:

```sql
WHERE name LIKE 'Lan%'
```

but generally cannot efficiently accelerate patterns starting with a wildcard:

```sql
WHERE name LIKE '%Lan%'
```

Optimization capabilities also depend on collation, operator classes, and the database. With PostgreSQL, `pg_trgm` and GIN/GiST indexes can support substring/fuzzy searches where appropriate:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_customer_name_trgm
ON customer USING gin (name gin_trgm_ops);
```

This is a PostgreSQL-specific example. For full-text search, consider full-text indexes/search vectors rather than trying to force B-trees for every `Containing` query.

In Spring Data, `Containing`, `StartingWith`, or `Like` produce string-filtering semantics. Indexes must match the actual pattern and collation; never conclude that having an index on a string column makes every LIKE query fast.

## 15. Indexes on Boolean and Low-Cardinality Columns

Columns like `active`, `enabled`, or `status` have few distinct values. A single-column index on a boolean is usually unselective if most rows share the same value. For example:

```sql
CREATE INDEX idx_customer_active
ON customer(active);
```

may not help `WHERE active = true` if 95% of the table is true. The optimizer may pick a sequential scan.

A composite index may fit better when the boolean combines with tenant or sort columns:

```sql
CREATE INDEX idx_customer_tenant_active_created
ON customer(tenant_id, active, created_at DESC, id DESC);
```

Or a partial index on the rare subset if supported by the database:

```sql
CREATE INDEX idx_customer_inactive
ON customer(created_at DESC)
WHERE active = false;
```

Look at selectivity and data distribution. Low cardinality does not mean "never index"; it can be effective when combined with other columns or when one value is very rare.

## 16. Indexes Have Write Costs

Every additional index must be updated on inserts, deletes, or updates to indexed columns. A table with too many indexes can suffer from:

- Slower inserts due to adding entries to multiple indexes.
- Slower updates when modifying indexed columns.
- Extra work on deletes to remove entries.
- Increased disk and cache memory usage.
- Longer vacuum/maintenance or rebuild times depending on the database.
- Prolonged index-creation migrations impacting system load.

Therefore, evaluate the combined read/write workload. An index serving a rarely run query while slowing every insert may not be worth keeping. Monitor index usage and workloads before dropping an index; do not drop one solely because short-term stats show low usage.

## 17. Data Types Matched to Query Predicates

Column types affect row/index size, comparison semantics, binding behavior, and database optimization.

### Numeric

- Use `BIGINT` for integers exceeding `INTEGER` range.
- Use `NUMERIC/DECIMAL(p,s)` for money and values requiring exact decimal precision.
- Avoid `FLOAT/DOUBLE` for financial calculations requiring exact decimals.
- Choose precision/scale appropriate to the domain rather than setting arbitrarily large values.

### Strings

- Choose bounded lengths when supported by the database and bounded by business rules.
- Unique indexes on long strings can consume substantial space.
- Consider collation, case sensitivity, and Unicode when designing search/uniqueness.
- Avoid large text types as join keys when small, stable IDs can be used.

### Time

- Choose timestamp types with clear timezone semantics.
- Use `Instant` for absolute timestamps if mapping/driver supports it well.
- Standardize on UTC conventions at the application layer.
- Index time columns when queries frequently filter by range or sort by time.
- If queries always filter by tenant and time range, a composite index `(tenant_id, created_at)` can be better than a single-column `created_at` index.

### UUID

UUIDs are convenient for distributed identifiers, though their indexes are larger than numeric keys. Choose native UUID representation if supported by the database instead of storing them arbitrarily as 36-character strings. Mapping Java `UUID` requires the corresponding driver codec.

### JSON/JSONB

JSON fits flexible data and is rarely suited as a relational join key. If querying frequently on a JSON field, consider expression indexes or generated/computed columns depending on the database. If a field is a core attribute continuously used for filtering/joining/sorting, a strongly typed relational column is usually easier to optimize and constrain.

## 18. Designing Schemas for Tenant Isolation

Multi-tenant applications routinely filter data by `tenant_id`. If every query carries a tenant scope, the tenant column should be treated as a central part of the access pattern.

Example:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
```

Query:

```sql
SELECT id, status, created_at
FROM orders
WHERE tenant_id = :tenantId
  AND status = :status
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

Candidate index:

```sql
CREATE INDEX idx_orders_tenant_status_created
ON orders(tenant_id, status, created_at DESC, id DESC);
```

If the customer foreign key must also prevent cross-tenant references, a simple `customer_id -> customer.id` foreign key may not express the tenant rule. You can use a composite unique/foreign key on `(tenant_id, customer_id)` if supported by the schema and database:

```sql
ALTER TABLE customer
ADD CONSTRAINT uk_customer_tenant_id
UNIQUE (tenant_id, id);

ALTER TABLE orders
ADD CONSTRAINT fk_orders_customer_tenant
FOREIGN KEY (tenant_id, customer_id)
REFERENCES customer(tenant_id, id);
```

This design lets the database enforce same-tenant relationships, though corresponding indexes and unique constraints must be weighed. Authorization checks remain required at the application layer; foreign keys do not replace access control.

## 19. Indexes and Constraints for Spring Data Derived Queries

Repository method names generate queries, not indexes. For example:

```java
Flux<Customer> findByStatusAndCreatedAtAfterOrderByCreatedAtDesc(
        String status,
        Instant after
);
```

The corresponding query has an equality condition on `status`, a range on `created_at`, and a sort on `created_at`. A candidate index can be:

```sql
CREATE INDEX idx_customer_status_created
ON customer(status, created_at DESC);
```

If queries are always tenant-scoped:

```java
Flux<Customer> findByTenantIdAndStatusOrderByCreatedAtDesc(
        UUID tenantId,
        String status
);
```

candidate index:

```sql
CREATE INDEX idx_customer_tenant_status_created
ON customer(tenant_id, status, created_at DESC, id DESC);
```

The indexes above are only candidates based on access patterns. Inspect the actual SQL generated by Spring Data/dialect, especially with `IgnoreCase`, `Containing`, `In`, dynamic sorting, and property mapping. A query method does not guarantee the optimizer uses an index.

### Derived `In` Queries

```java
Flux<Order> findByCustomerIdIn(Collection<Long> customerIds);
```

An index on `customer_id` can assist lookups. However, very large ID lists can produce many bind parameters or suboptimal plans; batch them or use database-specific solutions when necessary.

### Count and Exists

Methods like `countByStatus` and `existsByEmail` must also be evaluated against their predicates. `existsByEmail` is well supported by a unique index on email. `countByStatus` may scan many rows if status has low cardinality; an index only pays off when the optimizer and workload prove it.

## 20. Indexes for Multi-Table Join Queries

Suppose an endpoint fetches orders together with customers:

```sql
SELECT o.id, o.created_at, c.name
FROM orders o
JOIN customer c ON c.id = o.customer_id
WHERE o.status = :status
ORDER BY o.created_at DESC, o.id DESC
LIMIT 50;
```

Indexes to consider:

```sql
CREATE INDEX idx_orders_status_created_id
ON orders(status, created_at DESC, id DESC);

-- customer.id is already indexed by its primary key.
```

If the query starts from customer and filters orders by `customer_id`, an index on `orders(customer_id, ...)` may fit better. The optimal index depends on the join order chosen by the optimizer and predicate selectivity.

With one-to-many relationships, indexing the foreign key on the child table is usually important. When combining with a status filter and time sort:

```sql
CREATE INDEX idx_orders_customer_status_created
ON orders(customer_id, status, created_at DESC, id DESC);
```

Do not create every index variation before measuring. Identify the slowest queries, inspect plans, and select indexes that address actual bottlenecks.

## 21. Constraints and Indexes for Upserts

An upsert operation usually relies on a unique constraint to detect conflicts:

```sql
INSERT INTO customer (email, name)
VALUES (:email, :name)
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name;
```

This is PostgreSQL syntax. The conflict target `(email)` requires a matching unique constraint or unique index. You cannot rely on a non-unique index to prevent upserts from creating duplicates.

If uniqueness is scoped per tenant, the conflict target must match:

```sql
ON CONFLICT (tenant_id, email)
DO UPDATE SET name = EXCLUDED.name
```

With Spring Data R2DBC, this statement can run via `DatabaseClient` or `@Query` as appropriate. Spring Data does not infer upserts from `save` alone; `save` uses its own newness detection and persistence semantics. When atomic upsert by unique key is needed, write database-specific SQL and test the behavior.

## 22. Version Columns for Optimistic Locking

If multiple requests can modify the same entity concurrently, `@Version` helps detect updates based on stale entities:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Version
    private Long version;

    private String name;
}
```

The schema needs a version column:

```sql
version BIGINT NOT NULL DEFAULT 0
```

Spring Data R2DBC can include the version in update conditions and increment the version along supported entity persistence paths. When updating directly with SQL, the application must write the version condition and increment explicitly:

```sql
UPDATE customer
SET name = :name,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

The primary key index is usually sufficient to locate the row by ID; version is checked after locating the row. Creating a separate `(id, version)` index is generally unnecessary because `id` is already unique, unless a specific query pattern/plan proves a benefit.

## 23. Schema for Aggregate Relationships in Spring Data Relational

Spring Data Relational focuses on aggregate roots. Child objects belonging to an aggregate can be mapped via `@MappedCollection` under supported models.

Example:

```java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private List<PurchaseOrderLine> lines;
}
```

Schema:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE purchase_order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES purchase_order(id),
    product_code VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0)
);

CREATE INDEX idx_purchase_order_line_order
ON purchase_order_line(order_id);
```

`idColumn = "order_id"` must match the column referencing the root in the child table. The index on `order_id` supports finding lines belonging to an order. `@MappedCollection` is not JPA-style lazy loading; understand aggregate persistence and the queries Spring Data executes in your project version.

## 24. Managing Schemas with Migrations

Spring Data R2DBC primarily handles mapping and data access; do not rely on the application generating schemas from entities in production. Use versioned migrations to manage table, index, and constraint changes.

Example SQL migration:

```sql
-- V001__create_customer.sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    email VARCHAR(320) NOT NULL,
    name VARCHAR(200) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT ck_customer_status
        CHECK (status IN ('ACTIVE', 'INACTIVE', 'PENDING')),
    CONSTRAINT uk_customer_tenant_email
        UNIQUE (tenant_id, email)
);
```

A subsequent migration adds an index:

```sql
-- V002__index_customer_lookup.sql
CREATE INDEX idx_customer_tenant_status_created
ON customer(tenant_id, status, created_at DESC, id DESC);
```

Separate migrations allow schema changes to be reviewed, deployed, and rolled back systematically. Migration naming and syntax depend on the tool; the example above follows common Flyway conventions.

### Adding Indexes on Large Tables

On large production tables, creating an index can acquire locks or impact workloads depending on the database. PostgreSQL supports `CREATE INDEX CONCURRENTLY` to reduce write blocking in many cases, though this statement has transaction restrictions and requires appropriate migration handling. Other databases have their own online indexing syntax.

Never run a large index migration without evaluating locks, disk space, replication lag, and execution time. Test on a dataset scaled close to production size.

## 25. Modifying Constraints on Existing Data

Adding `NOT NULL`, unique, or foreign key constraints to a table with existing data can fail if existing rows violate them.

A safe workflow generally includes:

1. Identify and clean up violating rows first.
2. Add a nullable column or constraint in a database-appropriate validation state.
3. Backfill data in batches if the table is large.
4. Re-verify no nulls/duplicates/orphans remain.
5. Add the final constraint and switch the column to `NOT NULL` if needed.
6. Update the application to always write valid values.

Example checking duplicates before adding a unique constraint:

```sql
SELECT tenant_id, email, COUNT(*)
FROM customer
GROUP BY tenant_id, email
HAVING COUNT(*) > 1;
```

Checking orphans before adding a foreign key:

```sql
SELECT o.customer_id
FROM orders o
LEFT JOIN customer c ON c.id = o.customer_id
WHERE c.id IS NULL;
```

Do not add constraints in production only to discover legacy data is invalid. Migrations must include verification steps and a data remediation plan.

## 26. Verifying Indexes with EXPLAIN

After creating an index, verify whether the database actually uses it. PostgreSQL example:

```sql
EXPLAIN
SELECT id, name
FROM customer
WHERE tenant_id = :tenantId
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

When actual execution statistics are needed, PostgreSQL supports:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, name
FROM customer
WHERE tenant_id = '00000000-0000-0000-0000-000000000001'
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

`EXPLAIN ANALYZE` actually executes the query. Only run it in production when you understand the query's impact. Syntax and plan details differ on other databases.

Observe:

- Selected scan type: sequential/table scan, index scan, index-only scan, or bitmap scan.
- Whether there is a separate sort step or the index provides ordering.
- Estimated rows versus actual rows.
- Row counts flowing through each node.
- Buffer/page reads and actual execution time.
- Join strategy: nested loop, hash join, merge join, or the database's equivalent.
- Whether the query plan shifts depending on bind values/selectivity.

If an index is not used, it does not necessarily mean the index is useless. The optimizer may judge a full table scan cheaper when the query retrieves most rows. Conversely, a plan using an index is not guaranteed to be fast if it incurs excessive random heap reads.

## 27. Statistics and Realistic Data

The optimizer relies on statistics to estimate matching row counts. When data changes substantially while statistics are stale, the database can pick poor plans.

Factors to watch:

- Value distribution of filtered columns.
- Ratio of NULL values.
- Distinct value count/cardinality.
- Correlation between columns in composite predicates.
- Insert/update/delete frequency.
- Whether statistics are updated according to the database's mechanisms.

An index that performs well on test data with a few hundred rows may behave poorly on millions of production rows. Build benchmark datasets with realistic distributions and measure both common and rare cases.

## 28. Integrating the Schema with R2DBC Mapping

The schema and entity mapping must agree on names, types, and nullability.

Example:

```java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    @Column("order_number")
    private String orderNumber;

    @Column("created_at")
    private Instant createdAt;

    @Version
    private Long version;
}
```

The corresponding schema needs:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customer(id),
    order_number VARCHAR(40) NOT NULL UNIQUE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);

CREATE INDEX idx_orders_customer_created
ON orders(customer_id, created_at DESC, id DESC);
```

Points that must match:

- `@Table("orders")` corresponds to table `orders`.
- `@Column("customer_id")` corresponds to column `customer_id`.
- `@Id` corresponds to the primary key.
- `@Version` corresponds to the version column and optimistic locking semantics.
- `Instant` requires a compatible SQL type/codec.
- `NOT NULL` in the schema should be reflected in validation/domain models.

Mapping metadata does not replace database constraints. Conversely, constraints do not generate Java properties. Both layers must be designed together.

## 29. Testing Constraints and Indexes

Integration tests with a real database/driver should verify:

- Inserts missing required fields are rejected by the database.
- Unique constraints block duplicates within the exact tenant/business key scope.
- Foreign keys block orphan references.
- Check constraints block out-of-domain values.
- Defaults are applied when columns are omitted from INSERT, and behavior when binding NULL is clear.
- `@Version` mapping matches the version column.
- Key queries return expected results against the current schema/indexes.
- Query plans in benchmark environments use desired access paths where appropriate.

Do not write unit tests mocking the optimizer to assert an index is used. Index usage and query plans are database behaviors; verify them via integration/performance tests on the target database engine.

### Testing Unique Constraints Under Concurrency

A solid test sends two nearly simultaneous inserts with the same business key and confirms only one succeeds. This proves database constraints prevent race conditions that service-level `existsBy...` checks cannot block.

## 30. Common Mistakes

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Foreign key queries are slow | Child table lacks an index on FK | Create an index matching child table access patterns |
| Index exists but optimizer ignores it | Unselective predicate, wrong column order, or scan is cheaper | Check EXPLAIN and cardinality |
| Composite index does not help query | Filter column is not in a suitable prefix | Reorder columns to match actual predicates and re-measure |
| Sorting remains expensive | Index does not match sort order/direction or filters | Design index matching both filters and ORDER BY |
| Unique check still creates duplicates | Checked only in Java without a unique constraint | Add a unique constraint and handle conflicts |
| Deleting parent is very slow | Missing FK index or overly broad cascade | Index referencing columns and review delete policy |
| Table has too many indexes | Indexes created per field without considering write workload | Evaluate usage and write overhead |
| `LIKE '%text%'` is slow despite B-tree | Leading wildcard pattern is unsuited to B-trees | Use full-text/trigram/expression indexes per database |
| Deep pages are slow | Large offsets skip many rows | Consider keyset pagination and cursor indexes |
| Joins produce duplicate rows | Missing relationship constraints or unexpected join cardinality | Verify cardinality, unique/FK constraints, and grouping |
| Entity mapping column error | Property names and schema mismatch | Align `@Column` and migrations |
| `@Version` fails on save | Missing column or mismatched version semantics | Synchronize entity and schema migration |
| Unique constraint migration fails | Existing data already contains duplicates | Clean up data before adding constraint |
| Index migration impacts production | Index build locks or consumes heavy I/O | Use online/concurrent strategies per database and plan rollout |

## 31. Workflow for Designing a Schema from Access Patterns

A workflow applicable to each aggregate or module:

1. List critical read/write queries from APIs and services.
2. Identify entities, aggregate roots, and one-to-one/one-to-many/many-to-many relationships.
3. Choose stable primary keys and unique constraints for business keys.
4. Declare foreign keys and delete policies matching data lifecycles.
5. Add `NOT NULL`, `DEFAULT`, and `CHECK` so the database enforces invariants.
6. Choose appropriate data types for numeric, string, time, UUID, JSON, and version fields.
7. Design indexes around equality filters, ranges, joins, sorts, and pagination.
8. Evaluate composite indexes, prefixes, and partial/expression/covering indexes per database.
9. Write versioned migrations, inspect legacy data, and evaluate deployment locks.
10. Map schemas onto entities with `@Table`, `@Column`, `@Id`, `@Version`, and suitable converters.
11. Run integration tests for constraints and mapping using the real driver.
12. Use EXPLAIN/benchmarks on production-like data, measuring both read and write costs.
13. Monitor index usage and workloads post-deployment; add or remove indexes only based on evidence.

## 32. Takeaways

- Design schemas and indexes from real access patterns: predicates, joins, sorts, pagination, counts, and updates.
- `@Table`, `@Column`, `@Id`, and `@Version` describe mapping; migrations manage tables, indexes, and constraints.
- Choose stable primary keys; use unique constraints for business keys with the right tenant scope.
- Foreign keys protect relationships in the database; foreign key columns often need indexes if queries/joins or parent deletes rely on them.
- `NOT NULL`, `DEFAULT`, `CHECK`, and `UNIQUE` preserve invariants even when data is written outside repositories.
- Composite B-tree indexes depend on column order; prefixes and equality/range/sort columns must match real queries.
- Properly designed indexes assist JOINs, ORDER BY, pagination, and keyset queries, though optimizer usage is never guaranteed.
- Partial, expression, INCLUDE, trigram, and JSON indexes are database-dependent; check portability and query plans.
- Indexes increase insert/update/delete costs, storage, and maintenance; avoid redundant indexes.
- Choose data types based on semantics and driver codecs; standardize time handling and make nullability explicit.
- For multi-tenant apps, consider composite keys/foreign keys to enforce same-tenant relationships at the database level.
- `@Version` requires a version column in the schema; direct SQL must enforce the version check and increment explicitly.
- Use Flyway/Liquibase or versioned migrations to deploy schemas safely; do not rely on entity mapping to generate production schemas.
- Use `EXPLAIN` and realistic benchmarks; actual query plans matter more than guessing from index names.

A good schema for Spring Data R2DBC accurately models business invariants and supports the queries the system actually runs. Let the database protect integrity with keys and constraints, index key access patterns intentionally, and validate effectiveness via execution plans and benchmarks. Spring Data entity mapping is simply the bridge between the Java model and the designed schema—not a replacement for those decisions.
