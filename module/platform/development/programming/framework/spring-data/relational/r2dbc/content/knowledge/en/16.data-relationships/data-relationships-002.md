# Reading and Writing One-to-Many Relationships Explicitly

## 1. One-to-Many Relationships in Spring Data Relational R2DBC

A one-to-many relationship occurs when one parent object manages multiple child objects. For example, an order has multiple order lines, a customer has multiple shipping addresses, or a post has multiple comments.

In Spring Data Relational, a one-to-many relationship is typically modeled within the boundary of an **aggregate**. The parent object is the **aggregate root**; the child objects belong to the aggregate and are accessed through the root. The `@MappedCollection` annotation describes a collection stored in a separate table and linked to the root by a foreign key.

For example:

- `PurchaseOrder` is the aggregate root.
- `OrderLine` is a child object belonging to the order.
- One `PurchaseOrder` can have multiple `OrderLine`s.
- Each `OrderLine` belongs to exactly one `PurchaseOrder`.

In this model, the application loads and saves `PurchaseOrder` through the root's repository. There is no need to create a separate repository for `OrderLine` if order lines do not have an independent lifecycle.

Spring Data Relational uses an aggregate mapping model, not JPA's persistence context model. Do not expect JPA's `@OneToMany`, `@ManyToOne`, lazy loading, or cascade annotations to work in Spring Data R2DBC. Relationships must be declared using Spring Data Relational mappings and read/written explicitly.

## 2. Table Design for One-to-Many Relationships

Suppose we need to store orders and order lines. The PostgreSQL schema can be designed as follows:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE order_line (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    CONSTRAINT pk_order_line PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id) REFERENCES purchase_order(id)
);

CREATE INDEX ix_order_line_product_id ON order_line(product_id);
```

In this schema:

- `purchase_order.id` is the primary key of the aggregate root.
- `order_line.order_id` is the foreign key pointing to the order.
- `line_no` stores the position of the line within the order's list.
- The composite primary key `(order_id, line_no)` ensures each order cannot have two lines at the same position.
- `product_id` is an identifier referencing the product; this example does not embed the entire `Product` aggregate inside the order.

The foreign key guarantees no order line can reference a non-existent order. If order lines need to be deleted automatically when an order is deleted, `ON DELETE CASCADE` can be considered, but the deletion policy must match historical retention requirements. For order data, many systems prohibit physically deleting orders that have already generated transactions.

## 3. Mapping Collections with `@MappedCollection`

Spring Data Relational provides `@MappedCollection` to map a collection property of an aggregate root to another table.

Example root:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

import java.util.ArrayList;
import java.util.List;

@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }

    public void addLine(Long productId, int quantity, BigDecimal unitPrice) {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException("Only draft orders can be changed");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
        if (unitPrice == null || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("Unit price must not be negative");
        }

        lines.add(new OrderLine(productId, quantity, unitPrice));
    }

    public void removeLine(int lineIndex) {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException("Only draft orders can be changed");
        }
        if (lineIndex < 0 || lineIndex >= lines.size()) {
            throw new IndexOutOfBoundsException("Invalid order line index");
        }

        lines.remove(lineIndex);
    }
}
```

Child object:

```java
import org.springframework.data.relational.core.mapping.Table;

import java.math.BigDecimal;

@Table("order_line")
public class OrderLine {

    private Long productId;
    private Integer quantity;
    private BigDecimal unitPrice;

    protected OrderLine() {
    }

    public OrderLine(Long productId, Integer quantity, BigDecimal unitPrice) {
        this.productId = productId;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    public Long getProductId() {
        return productId;
    }

    public Integer getQuantity() {
        return quantity;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }
}
```

In this example, `OrderLine` has no independent ID. The key identifying a child row is formed from the root's key and the collection key. When using a `List`, `keyColumn = "line_no"` stores the element's position in the list. Column names in the annotation must match the actual schema.

`idColumn = "order_id"` specifies the column in the child table holding the aggregate root's ID. `keyColumn = "line_no"` specifies the column storing the key/position of the element in the collection. With a `Map`, the key column can store the map key; with an unordered collection, the key and mapping design must fit the collection type.

### 3.1. Why Use `List` and `keyColumn`?

A `List` is ordered. If the order of lines matters, the `line_no` column stores the position. For example:

| order_id | line_no | product_id | quantity |
| ---: | ---: | ---: | ---: |
| 1001 | 0 | 501 | 2 |
| 1001 | 1 | 502 | 1 |
| 1001 | 2 | 503 | 4 |

When the aggregate is read back, the mapping uses the key column to restore the collection by key/position. Check the SQL queries and ordering rules of your Spring Data Relational version if the application depends on stable ordering. If order is long-term business data, consider storing an explicit `position` property on the child object rather than relying solely on the `List` index.

If order does not matter, you can consider a `Set`. However, you must choose element keys so two distinct elements are not mistaken for the same one; do not rely on the database's default return order.

### 3.2. Table and Column Names

`@Table("purchase_order")` and `@Table("order_line")` make table names explicit. `@Column` can be used when Java property names differ from SQL column names:

```java
@Column("product_id")
private Long productId;

@Column("unit_price")
private BigDecimal unitPrice;
```

The column names in `idColumn` and `keyColumn` are also physical column names in the child table. Keep naming strategies, annotations, and DDL consistent; a single mismatched column name can cause read/write queries to fail at runtime.

## 4. Declaring a Repository for the Aggregate Root

The repository is created for `PurchaseOrder`, not for individual `OrderLine`s:

```java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface PurchaseOrderRepository
        extends ReactiveCrudRepository<PurchaseOrder, Long> {
}
```

Spring Data uses the root's mapping metadata to know that the `lines` collection is stored in the `order_line` table and linked via `order_id`. The root repository is the entry point for the aggregate.

There is no need to declare:

```java
// Unnecessary if OrderLine is solely a member of the PurchaseOrder aggregate
public interface OrderLineRepository
        extends ReactiveCrudRepository<OrderLine, Long> {
}
```

In this example, `OrderLine` does not have its own ID, so an independent CRUD repository for it would not reflect the model properly. If order lines need to be queried, edited, deleted, and managed with an independent lifecycle, consider making them a separate aggregate root with their own ID.

## 5. Reading a One-to-Many Aggregate via Repository

When reading an aggregate root, Spring Data Relational maps the aggregate's members according to metadata. For example:

```java
public Mono<PurchaseOrder> getOrder(Long orderId) {
    return purchaseOrderRepository.findById(orderId);
}
```

The publisher emits a `PurchaseOrder` if the order exists. The `lines` collection is loaded as part of the aggregate; if there are no lines, the collection will be empty according to the entity's initialization/mapping.

Usage:

```java
public Mono<OrderDetails> getOrderDetails(Long orderId) {
    return purchaseOrderRepository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .map(order -> new OrderDetails(
                    order.getId(),
                    order.getOrderNumber(),
                    order.getStatus(),
                    order.getLines()));
}
```

The key point is that the application reads the root and receives the collection according to the mapping. You do not need to call a child repository separately for order lines if they belong to the same aggregate.

### 5.1. No Lazy Loading Like JPA

Spring Data Relational does not use a persistence context or JPA-style lazy-loading proxies. When an aggregate is loaded, its mapped members are loaded according to Spring Data's mechanism. Do not write code expecting that calling `order.getLines()` will trigger an asynchronous database query at the moment the getter is invoked.

Therefore:

- The repository returns a publisher for reading the aggregate.
- The collection getter only accesses data already mapped in the object.
- If you need a query that fetches only part of a collection or a projection, declare a dedicated read query.
- You cannot rely on JPA's `FetchType.LAZY` or `FetchType.EAGER` in Spring Data R2DBC.

### 5.2. Reading Multiple Aggregates and Query Cost

`findAll()` can return multiple roots. When each root has a child collection, reading many aggregates may issue additional queries to load dependent components. The exact cost depends on the implementation and Spring Data Relational version.

For large tables, inspect the actual SQL and query count. Do not assume `findAll()` always produces a single `SELECT JOIN` or has zero collection-loading overhead. If a screen only needs a subset of columns, using a projection or custom `JOIN` query can be more efficient.

## 6. Inserting a New Root Together with Child Elements

When creating a new aggregate, instantiate the root and add child elements via domain methods:

```java
public Mono<PurchaseOrder> createOrder(
        PurchaseOrderRepository repository,
        String orderNumber) {

    PurchaseOrder order = new PurchaseOrder(orderNumber);
    order.addLine(501L, 2, new BigDecimal("125.00"));
    order.addLine(502L, 1, new BigDecimal("75.50"));

    return repository.save(order);
}
```

Spring Data persists the root and mapped collections according to the aggregate mapping. If the root's ID is database-generated, the framework needs to obtain that ID in order to insert child rows with the corresponding `order_id`.

The result of `save` is a publisher of the saved aggregate. Use the emitted root to obtain the generated ID and post-save state:

```java
return repository.save(order)
        .map(saved -> saved.getId());
```

Do not read `order.getId()` immediately after calling `save` assuming the ID has already been generated; the publisher must be subscribed to and complete the write operation first.

### 6.1. Illustrative SQL Statements

With the schema above, saving a new order logically requires:

1. Inserting a row into `purchase_order`.
2. Receiving the order ID if generated by the database.
3. Inserting each `OrderLine` into `order_line` with `order_id` equal to the root ID.
4. Writing `line_no` according to each element's position in the collection.

Illustrative SQL:

```sql
INSERT INTO purchase_order (order_number, status)
VALUES ('PO-2026-001', 'DRAFT')
RETURNING id;

INSERT INTO order_line (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 0, 501, 2, 125.00);

INSERT INTO order_line (order_id, line_no, product_id, quantity, unit_price)
VALUES (1001, 1, 502, 1, 75.50);
```

This illustrates the data semantics, not a guarantee that Spring Data will emit these exact SQL strings. The actual statements, parameter binding, and execution order depend on mapping metadata, dialect, driver, and Spring Data R2DBC version.

## 7. Updating an Aggregate and Its Collection

Suppose we need to add a line to an existing order. The aggregate approach is to load the root, call a domain method, and save the root again:

```java
@Service
public class OrderService {

    private final PurchaseOrderRepository repository;

    public OrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Mono<PurchaseOrder> addLine(
            Long orderId,
            Long productId,
            int quantity,
            BigDecimal unitPrice) {

        return repository.findById(orderId)
                .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
                .flatMap(order -> {
                    order.addLine(productId, quantity, unitPrice);
                    return repository.save(order);
                });
    }
}
```

`addLine` keeps the business rules inside the root. The service coordinates reading and saving. A reactive transaction ensures changes to the root and collection share a single commit/rollback unit when the transaction manager and `ConnectionFactory` are configured appropriately.

### 7.1. Removing a Child Element

Similarly, to remove an order line:

```java
@Transactional
public Mono<PurchaseOrder> removeLine(Long orderId, int lineIndex) {
    return repository.findById(orderId)
            .switchIfEmpty(Mono.error(new OrderNotFoundException(orderId)))
            .flatMap(order -> {
                order.removeLine(lineIndex);
                return repository.save(order);
            });
}
```

When the collection is saved again, Spring Data Relational synchronizes child rows according to its aggregate persistence strategy. Do not assume the framework always computes a minimal diff and runs a single `DELETE` for just the removed row. For collections managed as part of an aggregate, saving the root may replace existing child rows with the new set of child rows; inspect the actual SQL for your version.

This has performance implications: if an aggregate has thousands of child elements and changing a single element rewrites the entire collection, the aggregate may be too large. Consider bounding aggregate size or splitting child elements into separate aggregates when they have an independent lifecycle.

### 7.2. Updating an Order Line Property

If `OrderLine` remains part of the `PurchaseOrder` aggregate, modify it through the root:

```java
public void changeLineQuantity(int lineIndex, int quantity) {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException("Only draft orders can be changed");
    }
    if (quantity <= 0) {
        throw new IllegalArgumentException("Quantity must be positive");
    }

    OrderLine current = lines.get(lineIndex);
    lines.set(lineIndex, new OrderLine(
            current.getProductId(),
            quantity,
            current.getUnitPrice()));
}
```

Then save the root via the repository. This example illustrates replacing the element in the collection; in a real entity, you can call a method on `OrderLine` if it is mutable, or create a new copy if it is immutable.

## 8. Transactions for Writing Root and Child Rows

An aggregate may require multiple SQL statements: inserting/updating the root, inserting/updating child rows, and deleting removed child rows. If business rules require avoiding partial state, place a reactive transaction on the application service.

Example:

```java
@Transactional
public Mono<PurchaseOrder> createAndSave(PurchaseOrder order) {
    return purchaseOrderRepository.save(order);
}
```

The R2DBC transaction manager manages the connection and transaction context. Persistence operations must participate in the same reactive context to be committed or rolled back together.

Do not call `subscribe()` independently inside a `@Transactional` method. Return the publisher so Spring manages the transaction lifecycle. If a child-row write fails after the root has been inserted, a properly configured transaction rolls back all changes rather than leaving a root without its required collection.

Do not hold a transaction open while waiting on an HTTP call or remote service. An R2DBC transaction only covers the managed database scope; it does not create a distributed transaction across the network.

## 9. Difference Between Aggregate Children and Referencing Separate Aggregates

Not every one-to-many relationship in the database should use `@MappedCollection`.

### 9.1. Child Belongs to the Root's Lifecycle

Use `@MappedCollection` when:

- The child only makes sense within the root's scope.
- The child is not managed independently.
- Child changes must enforce the root's invariants.
- The application typically loads and saves children together with the root.

For example, `OrderLine` only exists within `PurchaseOrder`. When an order is deleted under an allowed policy, its lines must also be handled with the aggregate.

### 9.2. Child Object Is Actually an Independent Aggregate

Suppose `Customer` has many `Address`es, where each address can be managed, set as default, verified, and deleted independently. If an address has its own lifecycle, model `Address` as a separate aggregate root:

```java
@Table("customer_address")
public class CustomerAddress {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String street;
    private String city;
    private Boolean defaultAddress;
}
```

```java
public interface CustomerAddressRepository
        extends ReactiveCrudRepository<CustomerAddress, Long> {

    Flux<CustomerAddress> findByCustomerId(Long customerId);
}
```

Here `CustomerAddress` has its own ID and repository. `Customer` may hold IDs or omit the address collection from its object model. Use cases query addresses via `CustomerAddressRepository`.

If a customer has many addresses and addresses are independent aggregates, using `@MappedCollection` on `Customer` tightly couples address lifecycle to loading and saving the customer. Choose the model based on business rules, not solely on foreign key relationships.

### 9.3. Referencing Another Aggregate by ID

An `OrderLine` typically references `Product` by `productId`:

```java
private Long productId;
```

This is a logical reference. When reading `PurchaseOrder`, Spring Data does not automatically load the corresponding `Product` just because `productId` is present. If you need the current product name, query the product separately or use a `JOIN`/read model query. Snapshot data such as product name and unit price at purchase time can be stored on the order line if historical accuracy is required.

## 10. Reading Relational Data with JOIN for Read Models

Aggregate repositories fit when you need to load the root and its owned members. However, reporting screens may need combined data from multiple tables or only a few columns. In those cases, `DatabaseClient` can run a `JOIN` and map a projection.

Example DTO:

```java
public record OrderLineView(
        Long orderId,
        String orderNumber,
        String status,
        Integer lineNo,
        Long productId,
        Integer quantity,
        BigDecimal unitPrice) {
}
```

PostgreSQL query:

```java
public Flux<OrderLineView> findOrderLines(
        DatabaseClient databaseClient,
        Long orderId) {

    return databaseClient.sql("""
            SELECT o.id AS order_id,
                   o.order_number,
                   o.status,
                   l.line_no,
                   l.product_id,
                   l.quantity,
                   l.unit_price
            FROM purchase_order o
            LEFT JOIN order_line l ON l.order_id = o.id
            WHERE o.id = :orderId
            ORDER BY l.line_no
            """)
            .bind("orderId", orderId)
            .map((row, metadata) -> new OrderLineView(
                    row.get("order_id", Long.class),
                    row.get("order_number", String.class),
                    row.get("status", String.class),
                    row.get("line_no", Integer.class),
                    row.get("product_id", Long.class),
                    row.get("quantity", Integer.class),
                    row.get("unit_price", BigDecimal.class)))
            .all();
}
```

This is a flat read model: each result row corresponds to an order line. If the order has no lines, `LEFT JOIN` can still return one row with `NULL` values for `order_line` columns. The DTO must allow nullable line fields, or the query must handle the no-lines case explicitly.

If you need to group `JOIN` results into a DTO with a nested collection, the application must group rows by `order_id` and build the collection in the pipeline. Do not assume `DatabaseClient` reconstructs an aggregate graph like repository mapping.

### 10.1. JOIN Does Not Change Aggregate Boundaries

A read query can `JOIN` multiple tables for display. That does not mean those tables are merged into one aggregate or can all be modified arbitrarily through a single object graph.

Distinguish:

- **Write model:** uses aggregate roots and repositories to protect invariants during state changes.
- **Read model:** uses projections, `JOIN`s, or `DatabaseClient` to retrieve data shaped for screens and reports.

This is a common separation when the write model must remain strict while screens require aggregated data.

## 11. Querying Child Criteria

If you need to find orders containing a line for a given product, you can use an explicit SQL query:

```java
@Query("""
    SELECT DISTINCT o.id, o.order_number, o.status
    FROM purchase_order o
    JOIN order_line l ON l.order_id = o.id
    WHERE l.product_id = :productId
    """)
Flux<PurchaseOrderSummary> findOrdersContainingProduct(
        @Param("productId") Long productId);
```

This example returns a `PurchaseOrderSummary` projection, without necessarily returning the full aggregate with its `lines` collection. This is usually the right choice when only a summary list of orders is needed.

If business logic needs to load the full aggregate root to make modifications, retrieve the matching root IDs and load the roots through the repository using an appropriate strategy. Avoid using an incomplete projection to execute domain operations that enforce invariants across the entire aggregate.

## 12. Performance and Collection Size

A one-to-many aggregate can grow very large over time. If a customer has millions of events or an order has tens of thousands of items, loading and saving the entire collection with the root may no longer be appropriate.

Signs the design should be revisited:

- Every root read loads a massive collection even when the caller only needs one element.
- A small change causes many child rows to be reprocessed.
- Concurrent requests updating different children constantly conflict on the same root.
- Transactions hold connections open for a long time to write many rows.
- Children cannot be paginated without loading the entire aggregate.

Possible solutions include:

- Splitting children into a separate aggregate if they have an independent lifecycle.
- Querying and paginating children with a dedicated repository.
- Using a read model or `DatabaseClient` for screens needing only a subset of data.
- Batching large writes while clearly defining business atomicity.
- Keeping collections within aggregates at a manageable size.

Do not split an aggregate purely for query optimization if invariants require objects to change together. When splitting, redesign the consistency flow and intermediate state handling.

## 13. Indexing for One-to-Many Relationships

The foreign key on the child table is typically the column used to load the collection:

```sql
SELECT order_id, line_no, product_id, quantity, unit_price
FROM order_line
WHERE order_id = 1001
ORDER BY line_no;
```

The composite primary key `(order_id, line_no)` already leads with `order_id`, so it can support queries filtering by `order_id` and ordering by `line_no` in many database engines. If the schema uses a different primary key, a dedicated index may be needed:

```sql
CREATE INDEX ix_order_line_order_id_line_no
    ON order_line(order_id, line_no);
```

If queries frequently filter by `product_id`, an index on `product_id` can help:

```sql
CREATE INDEX ix_order_line_product_id
    ON order_line(product_id);
```

Indexes must be based on query workload and execution plans. Every index increases write overhead and storage usage, so do not index every column blindly.

## 14. Handling Ordering and Collection Updates

With a `List`, order can be part of the data. If an element in the middle is removed, subsequent indices shift. When Spring Data synchronizes the collection, key column values may be rewritten to match the new list state.

If ordering has business meaning and must stay stable across edits, consider storing `line_no` as an explicit domain property rather than treating it purely as a list position. For example:

```java
public class OrderLine {
    private Integer position;
    private Long productId;
    private Integer quantity;
    private BigDecimal unitPrice;
}
```

In that case, design the mapping so domain `position` is not confused with the internal collection key column. You can use `@MappedCollection` for the collection key alongside a separate domain column if required by the model, or use an explicit persistence adapter/SQL.

Never rely on the physical row order in the database. When querying the child table directly, always use `ORDER BY` on the defined ordering column.

## 15. Handling Generated IDs and Foreign Key References

When the root's ID is generated by the database, child rows must reference the generated ID after inserting the root. Spring Data Relational manages aggregate mapping so the root ID is propagated to child rows.

With application-assigned IDs, the root already has an ID upon creation. However, you must configure newness detection properly so Spring Data knows the aggregate is new. If Spring Data mistakes it for an existing entity, it may take the update path instead of insert.

For pre-assigned IDs, you can implement `Persistable<ID>` to provide `isNew()` where appropriate. After saving, the newness state must be managed properly so subsequent saves are not treated as new inserts.

Do not manually assign `order_id` on each `OrderLine` if collection mapping already manages the foreign key. Duplicating relationship state in both the child object and `@MappedCollection` can cause confusion over which field is authoritative.

## 16. Optimistic Locking for Aggregates with Collections

If the root has a `@Version` property, Spring Data Relational can use the version to detect concurrent updates on the aggregate:

```java
@Version
private Long version;
```

When two requests load the same `PurchaseOrder`, both may modify the `lines` collection. When the first request saves and increments the version, the second request using the stale version fails with an optimistic locking exception.

This prevents silently overwriting the entire aggregate state. However, if the collection is large and independent operations frequently edit different lines, root-level conflicts may happen often. This can be a sign that the aggregate groups together too many parts with independent lifecycles or update needs.

Do not automatically retry by saving the stale object again. Reload the fresh aggregate, reapply the business intent if still valid, and save with the new version.

## 17. Deleting the Root and Child Rows

When deleting an aggregate root, decide what happens to child rows. Options include:

- Deleting child rows first and then deleting the root in the same transaction.
- Using a foreign key with `ON DELETE CASCADE` if data policy permits.
- Disallowing root deletion while child data exists and returning a business error.
- Using soft delete to preserve history.

Do not assume `repository.deleteById(rootId)` automatically cascades through an object graph the same way JPA does. Spring Data Relational works directly with relational databases; schema constraints and cascade settings play a decisive role. Inspect the actual DDL and SQL.

If using `ON DELETE CASCADE`, the database deletes child rows when the root is deleted. Test this on the actual database and review audit, retention, regulatory, or transaction history requirements before enabling it.

## 18. Common Mistakes

| Symptom | Possible Cause | How to Fix |
| --- | --- | --- |
| Read collection is always empty | Wrong `idColumn`, child table name, or schema lacks rows referencing root | Check DDL, mapping metadata, and actual SQL |
| Saving root succeeds but child fails | Bad FK, ID type mismatch, or missing transaction wrapping the operation | Check constraints, bind types, and reactive transaction |
| List order is not restored properly | Missing/wrong `keyColumn` or query lacks explicit ordering | Declare key column and use an appropriate position column/`ORDER BY` |
| Creating a repository for a child without an ID | Child is actually an aggregate member | Operate via root repository or redesign child as its own aggregate with an ID |
| Changing one child rewrites many rows | Aggregate persistence may replace child collection on root save | Evaluate aggregate size and SQL; extract child if lifecycle is independent |
| Loading root pulls too much data | Large collection or overly broad aggregate model | Use projections/separate queries or split aggregate by domain |
| `@OneToMany` does not work | Using JPA annotation in Spring Data Relational | Use `@MappedCollection` for aggregate-owned collections |
| Product changes do not appear in OrderLine | Child only stores `productId`, does not auto-load `Product` | Query `Product` separately or use `JOIN`/read model |
| Deleting root fails with foreign key error | Child rows still reference root | Configure cascade or delete children first in a transaction |
| Updating collection hits optimistic locking | Another request modified the same root | Reload aggregate and handle conflict per business rules |

## 19. Testing One-to-Many Relationships

Domain unit tests should verify root invariants:

```java
@Test
void shouldAddLineToDraftOrder() {
    PurchaseOrder order = new PurchaseOrder("PO-TEST-1");

    order.addLine(501L, 2, new BigDecimal("10.00"));

    assertEquals(1, order.getLines().size());
    assertEquals(501L, order.getLines().get(0).getProductId());
}
```

Repository integration tests must verify data is saved and read back from the database:

```java
StepVerifier.create(purchaseOrderRepository.save(order)
        .flatMap(saved -> purchaseOrderRepository.findById(saved.getId())))
        .assertNext(loaded -> {
            assertEquals(2, loaded.getLines().size());
            assertEquals(501L, loaded.getLines().get(0).getProductId());
        })
        .verifyComplete();
```

These examples assume fixtures, constructors, and a test database are configured. Integration tests should run against the target R2DBC driver and database engine, as generated IDs, data types, transactions, constraints, and SQL behavior can differ across databases.

Scenarios to test:

- Saving a root with no children and reading back an empty collection.
- Saving a root with multiple children and verifying FK and key column values.
- Reading back a root and restoring collection order properly.
- Adding, modifying, and removing children then saving the root.
- Verifying transaction rollback of the root when a child insert fails.
- Deleting the root under the chosen cascade/constraint policy.
- Concurrent updates and optimistic locking.
- Reading projections via `JOIN` for roots with no children.

## 20. Workflow for Choosing How to Read and Write One-to-Many Relationships

When designing a one-to-many relationship in Spring Data R2DBC, follow this sequence:

1. Determine whether the parent object is an aggregate root.
2. Determine whether child objects depend on the root's lifecycle or should be a separate aggregate.
3. If children belong to the aggregate, declare the collection with `@MappedCollection`.
4. Design the child table with a foreign key pointing to the root and a key column suitable for `List`/`Map` or element identity.
5. Create a repository for the aggregate root.
6. Read the root via the repository when the full aggregate is required.
7. Create or update the collection through root domain methods and then call `save`.
8. Use a reactive transaction when root/child operations must be atomic.
9. Use `DatabaseClient`/projections/`JOIN` when only partial data or a combined read model is needed.
10. Test mapping, ordering, FKs, generated IDs, transactions, and optimistic locking against the real database.

`@MappedCollection` helps Spring Data Relational map one-to-many relationships residing within the same aggregate. The root repository is the primary read/write entry point; child elements are managed with the root and reference the root via a foreign key. When combined queries or partial reads are needed, dedicated SQL `JOIN`s and projections can be used. Choosing the right aggregate boundaries, foreign keys, key columns, and transactions keeps one-to-many relationships clear, consistent, and aligned with how Spring Data R2DBC works.
