# DTO-Based and Java Record Projections

In Spring Data Relational R2DBC, projections allow queries to return the exact data shape a caller needs, rather than always returning the full entity. A projection can be an interface declaring only required getters, a DTO class with an appropriate constructor, or a Java record. This approach is useful for API responses, list screens, lightweight reports, and queries needing only a subset of an aggregate's properties.

A projection is a way to define a read result. It does not change table structure, does not automatically create relationships between tables, and does not replace entities used for write operations. With R2DBC, results are still emitted via `Mono` or `Flux`; applications should keep reactive publishers end-to-end instead of blocking the stream to extract a DTO.

## 1. What Problem Do Projections Solve?

Suppose a `Customer` entity has many properties: ID, name, email, phone number, address, status, audit fields, and internal fields. A list screen only needs name and email. If the full entity is returned, the API layer receives more data than needed and risks accidentally exposing properties that should not appear in the response.

A projection clearly specifies the subset of data needed:

```java
public interface CustomerListItem {
    String getName();
    String getEmail();
}
```

The repository can return `Flux<CustomerListItem>` for the list query. The caller sees only the two properties declared in the projection.

Key benefits:

- **Reduces data in the application layer:** results can contain only the required properties instead of materializing the full entity.
- **Separates persistence models from responses:** DTOs/records do not need to be entities managed by Spring Data Relational.
- **Restricts exposed data:** APIs can return a purpose-built result type without leaking internal entity fields.
- **Improves clarity:** repository signatures express the exact data required by a use case.
- **Preserves reactive processing:** projections can be emitted in `Mono` or `Flux` just like regular entities.

Whether the database selects only the projection columns depends on the query type and how it is declared. For repository queries generated by Spring Data, the framework may optimize the column list according to the projection when supported by the store. For `@Query` or handwritten SQL, actively select the right columns and aliases. Changing the return type to a DTO alone does not guarantee that handwritten SQL has removed `SELECT *`.

## 2. Entity Used in Examples

Suppose the `customer` table has the following columns:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    email VARCHAR(320) NOT NULL,
    phone_number VARCHAR(30),
    internal_note VARCHAR(500),
    active BOOLEAN NOT NULL
);
```

Entity mapping the table:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;

    private String email;

    @Column("phone_number")
    private String phoneNumber;

    @Column("internal_note")
    private String internalNote;

    private Boolean active;

    // Constructor, getters, and setters.
}
```

The entity describes the persistence model. A projection can expose only `name` and `email` without modifying the entity or adding new relationships.

## 3. Interface-Based Projections

An interface projection declares getters for the properties to read. Spring Data creates an implementation/proxy for the interface and supplies values from the query result.

```java
public interface CustomerListItem {
    String getName();
    String getEmail();
}
```

The repository declares a method returning the projection:

```java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerListItem> findByActiveTrue();
}
```

This method returns active customers as `Flux<CustomerListItem>`. The caller accesses only `getName()` and `getEmail()`:

```java
public Flux<CustomerListItem> getActiveCustomerList() {
    return customerRepository.findByActiveTrue();
}
```

With interface projections, getter names must match entity properties following JavaBeans conventions. For example, `getPhoneNumber()` corresponds to property `phoneNumber`, even though the physical database column is `phone_number` via `@Column` mapping.

Interface projections work well when you want a small getter contract, especially when multiple different projection types are needed for the same entity. The proxy accesses properties via Spring Data; do not treat it as a full entity that can be saved back with `save()`.

## 4. Closed Projections and Computed Getters

A closed projection declares only properties that actually exist on the aggregate/entity:

```java
public interface CustomerNameView {
    String getName();
    String getEmail();
}
```

Because Spring Data knows exactly which properties are requested, the framework can optimize data retrieval when the store and query path support it.

An interface can also define default methods based on declared getters:

```java
public interface CustomerNameView {
    String getName();
    String getEmail();

    default String getLabel() {
        return getName() + " <" + getEmail() + ">";
    }
}
```

`getLabel()` is computed in Java from the two projection properties. It does not require a `label` column in the database.

Spring Data Commons also has open projections that use `@Value`/SpEL to compute values from the target object. With projections using arbitrary access expressions, the framework cannot always infer the exact columns needed for optimization. Specific support and optimization behavior should be verified for your Spring Data Relational version. For simple responses, closed projections or DTOs/records are typically more predictable.

## 5. Class-Based Projections Using DTOs

A class-based projection uses a DTO class with a constructor accepting the required properties. A DTO does not need `@Table` or `@Id` annotations if used solely as a query result type.

```java
public class CustomerSummary {

    private final String name;
    private final String email;

    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }
}
```

The repository can declare the DTO result type:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByActiveTrue();
}
```

Spring Data uses constructor mapping to create `CustomerSummary` from the read data. Constructor parameter names must match the projected properties and mapping metadata. With standard Java classes, compile with parameter name information (`-parameters`) or provide appropriate constructor metadata so Spring Data can accurately identify parameters. If multiple constructors exist, mark the constructor to be used with `@PersistenceCreator` according to the mapping rules of your version.

DTOs are typically read-only types. They do not need all entity properties and should not be used as entities to call repository `save()`.

## 6. Projections Using Java Records

Java records are a concise choice for immutable DTOs. Record components automatically generate accessors, a canonical constructor, and `equals`, `hashCode`, and `toString` methods.

```java
public record CustomerSummary(
        String name,
        String email
) {
}
```

The repository can return the record directly:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByActiveTrue();
}
```

The record components `name` and `email` correspond to the properties to fetch. Spring Data uses the canonical constructor to instantiate the record. Component names are preserved in record metadata, so constructor mapping is often clearer than in a DTO with multiple constructors.

Records are suitable for read results that do not need to change after creation. If a projection has nullable fields, use reference types such as `String`, `Long`, or `Boolean`; primitive types like `long` or `boolean` cannot represent SQL `NULL`.

## 7. DTOs/Records When Column Names Differ from Property Names

Java property names and SQL column names can differ. An entity may map `phoneNumber` to `phone_number` via `@Column`. When queries are generated by Spring Data from entity metadata, the framework uses the mapping context to resolve column names.

With custom SQL, alias columns to the names expected by the DTO/record:

```java
public record CustomerContactView(
        String name,
        String phoneNumber
) {
}
```

```java
@Query("""
       SELECT name,
              phone_number AS phoneNumber
       FROM customer
       WHERE active = TRUE
       """)
Flux<CustomerContactView> findActiveContacts();
```

The alias `phoneNumber` ensures the result column name matches the `phoneNumber` component. Case sensitivity rules and how drivers return column name metadata can vary by database. With custom SQL, use explicit aliases and test against the actual driver/database.

If a DTO uses component `firstName` while an entity property is `firstname`, unify the mapping name or alias appropriately. Do not assume Spring Data automatically infers every camelCase/snake_case variation in handwritten SQL.

## 8. Projections with `@Query`

With custom SQL queries, repository methods can return DTOs or records. The SQL must return the necessary columns and specify aliases matching the property/constructor names of the projection type.

```java
public record CustomerOrderCount(
        Long customerId,
        String customerName,
        Long orderCount
) {
}
```

```java
@Query("""
       SELECT c.id AS customerId,
              c.name AS customerName,
              COUNT(o.id) AS orderCount
       FROM customer c
       LEFT JOIN orders o ON o.customer_id = c.id
       WHERE c.active = TRUE
       GROUP BY c.id, c.name
       """)
Flux<CustomerOrderCount> findActiveCustomerOrderCounts();
```

This is an aggregate result projection. `CustomerOrderCount` is not an entity mapped to a table; it simply describes a result row. SQL performs the join and computes `COUNT`; Spring Data/the driver maps the returned columns into the record constructor.

With custom SQL, avoid `SELECT *` when only three fields are needed. Selecting the right columns and using clear aliases reduces data transfer, avoids duplicate column names across tables, and makes constructor mapping predictable.

`@Query` in Spring Data R2DBC uses the repository parameter binding mechanism. If parameter names are not retained during compilation or the project requires clarity, `@Param` can be used:

```java
@Query("SELECT id, name, email FROM customer WHERE active = :active")
Flux<CustomerSummary> findByActive(@Param("active") boolean active);
```

Do not concatenate user input into SQL. Use bind parameters for values; for table/column names or sort directions, use a whitelist because identifiers cannot be protected by binding like regular values.

## 9. Projections with Derived Query Methods

Derived query methods allow Spring Data to infer the query from the method name and the projection return type:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByCity(String city);

    Mono<CustomerNameView> findByEmail(String email);
}
```

The method returns `Flux<CustomerSummary>` when there can be many customers in a city; the method returns `Mono<CustomerNameView>` when querying by email and expecting at most one result. If nothing is found, `Mono` completes empty. If a single-result method receives multiple rows, the behavior may be an incorrect result size error per the query contract.

Method names and predicates still rely on entity properties. The projection return type defines the shape of data received by the caller. If the query requires joins, aggregates, or database-specific SQL, `@Query` is usually clearer.

## 10. Dynamic Projections

In repository query methods that support dynamic projections, the result type can be selected at call time via a `Class<T>` parameter:

```java
<T> Flux<T> findByCity(String city, Class<T> projectionType);
```

Usage example:

```java
Flux<CustomerSummary> summaries =
        customerRepository.findByCity("Hobbiton", CustomerSummary.class);

Flux<CustomerNameView> names =
        customerRepository.findByCity("Hobbiton", CustomerNameView.class);
```

Dynamic projections allow reusing query criteria across multiple result types. Exact support and syntax depend on the Spring Data Relational version and query method type. Confirm that your project's repository factory supports dynamic projections before using them. Otherwise, declare methods with static return types or use `R2dbcEntityTemplate`/`DatabaseClient` to control the results.

## 11. Projections and Reactive Return Types

Projections do not change the reactive semantics of repositories:

| Return Type | Meaning |
| --- | --- |
| `Mono<CustomerSummary>` | Zero or one projection; completes empty if no row exists |
| `Flux<CustomerSummary>` | Zero to many projections, emitted one by one |
| `Mono<Boolean>` | A single check value, if the query method is designed to return boolean |
| `Mono<Long>` | A single count or quantity value from the query |

Example service converting a DTO into an API response:

```java
public Flux<CustomerResponse> listActiveCustomers() {
    return customerRepository.findByActiveTrue()
            .map(item -> new CustomerResponse(item.getName(), item.getEmail()));
}
```

If the repository already returns a DTO in the exact response shape, that publisher can be returned directly from the service/controller without extra mapping. If additional data from another service is needed, use `flatMap`/`zipWhen` or suitable reactive operators.

Do not call `block()` to unwrap a projection inside a reactive service. Blocking can tie up event-loop threads and negate the non-blocking benefits of R2DBC.

## 12. Projections Are Not Write Entities

DTOs or interface projections are typically read results. They do not necessarily contain full IDs, state, or required aggregate properties. Do not pass a projection into repository `save()` as though it were an entity.

A clean update flow may look like:

1. Receive an input command/DTO from the API.
2. Load the entity or execute an appropriate update operation.
3. Apply business rules.
4. Save the entity via repository/template.
5. Return a DTO/projection constructed from the result or a fresh read query.

Example:

```java
public Mono<CustomerSummary> renameCustomer(Long id, String newName) {
    return customerRepository.findById(id)
            .switchIfEmpty(Mono.error(new CustomerNotFoundException(id)))
            .flatMap(customer -> {
                customer.setName(newName);
                return customerRepository.save(customer);
            })
            .map(saved -> new CustomerSummary(saved.getName(), saved.getEmail()));
}
```

Here the entity is used for the update; the `CustomerSummary` record is solely the returned result. For updating specific columns conditionally, `R2dbcEntityTemplate` fluent updates may be more suitable than loading the entity first.

## 13. Projections and Nested Properties

Spring Data Relational models aggregates and relationships according to relational mapping rules; do not assume nested projections will automatically create JOINs or lazy-load like some JPA ORMs. If a projection needs data from multiple tables, explicitly decide how to fetch it:

- Write `@Query` with a JOIN and column aliases into a DTO/record.
- Use `DatabaseClient` for complex SQL or results that do not naturally map to an entity.
- Execute multiple reactive queries intentionally and combine results if data volumes are suitable.
- Create a view or separate read model if the aggregated query is frequently used.

Example projection aggregated from two tables:

```java
public record OrderListItem(
        Long orderId,
        String customerName,
        BigDecimal total
) {
}
```

```java
@Query("""
       SELECT o.id AS orderId,
              c.name AS customerName,
              o.total AS total
       FROM orders o
       JOIN customer c ON c.id = o.customer_id
       WHERE o.status = :status
       """)
Flux<OrderListItem> findOrderList(@Param("status") String status);
```

Here the JOIN is written explicitly in SQL. The record describes the exact three columns to return; there is no need to declare a hypothetical object graph between `Order` and `Customer`.

## 14. Nulls and Data Types in DTOs/Records

Projections may contain nullable columns. If the database returns SQL `NULL`, the target type must be capable of representing that value.

Example:

```java
public record CustomerContactView(
        Long id,
        String name,
        String phoneNumber,
        Boolean active
) {
}
```

`phoneNumber` and `Boolean` are reference types, so they can accept null if the column allows it. If `long` or `boolean` is used for a nullable column, constructor mapping may fail or be unable to represent the null state properly. Choose wrapper types when columns may have missing values.

DTO types must be compatible with types returned by the driver. For instance, `NUMERIC` typically maps well to `BigDecimal`; temporal types must align with schema and dialect. With custom SQL, casts or aliases may be necessary if an expression returns a different type than the constructor parameter.

Do not use `Mono.empty()` to represent a row with null columns. `Mono.empty()` means the query emitted no rows; null columns still belong to an emitted projection.

## 15. DTOs with Multiple Constructors

Spring Data needs to identify which constructor to use to instantiate a DTO. A class with a single unambiguous constructor is usually easiest to map:

```java
public class CustomerSummary {
    private final String name;
    private final String email;

    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

If a DTO has multiple constructors, the persistence constructor can be marked with `@PersistenceCreator`:

```java
import org.springframework.data.annotation.PersistenceCreator;

public class CustomerSummary {
    private final String name;
    private final String email;

    public CustomerSummary(String name) {
        this(name, null);
    }

    @PersistenceCreator
    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

The chosen constructor must have parameters matching the projection data. With Java records, the canonical constructor is usually the natural choice, so there is no need to add extra constructors purely for mapping.

## 16. Projections with `R2dbcEntityTemplate`

When dynamic queries are needed or you prefer not to create a repository method for every filter combination, `R2dbcEntityTemplate`/`R2dbcEntityOperations` can be used. The fluent select API lets you specify the domain type and result type according to the capabilities of the Spring Data Relational version.

Example reading entities by criteria:

```java
Query query = Query.query(where("active").is(true));

Flux<Customer> customers = template.select(Customer.class)
        .matching(query)
        .all();
```

When DTO results are needed, check the projection/select APIs of your version. For SQL JOINs or aggregates, repository `@Query` returning a DTO/record or `DatabaseClient` is usually a clearer choice because it lets you specify exact columns and aliases.

Do not assume every `select(...)` overload accepts arbitrary DTO types across all versions. Spring Data Relational's fluent API can evolve; consult the Javadoc of your exact dependency before writing code.

## 17. When to Choose Interface, DTO Class, or Record?

| Criterion | Interface projection | DTO class | Java record |
| --- | --- | --- | --- |
| Declaration | Getters for properties to read | Constructor and accessors/getters | Components in record header |
| Immutability | Proxy depends on implementation | Can be designed immutable or mutable | Immutable by component |
| Computed getters | Can use default methods; open projections depend on support | Add normal methods | Add normal methods |
| Constructor mapping | No DTO constructor needed as Spring creates a proxy | Needs an appropriate constructor | Uses canonical constructor |
| Best suited for | Small views, multiple getter views, interface contracts | Legacy Java integration or DTOs with custom logic/constructors | Concise, immutable response DTOs |
| Limitations | Proxies and dynamic expressions can make optimization hard to predict | Must manage constructors and parameter names | Requires Java record support and compatible mapping |

There is no mandatory choice for every query. For simple result DTOs in modern Java, records are typically short and readable. Interfaces fit well when describing a view via getters. Standard DTO classes fit when compatibility with older codebases or more complex constructors/logic is needed.

## 18. Common Mistakes

| Symptom | Possible Cause | Fix |
| --- | --- | --- |
| Projection property is not mapped | Getter/component/constructor parameter does not match property or alias name | Check property names, `@Column`, aliases, and constructor metadata |
| DTO cannot be instantiated | Unsuitable constructor or parameter names not recognized | Use a single clear constructor, a record, or `@PersistenceCreator`; enable `-parameters` if needed |
| Value returns null despite column having data | Wrong alias, driver returning a different column name, or query missing the column | Use explicit aliases and test on the actual database |
| Error on nullable columns | DTO uses primitives or constructor does not accept null | Use wrapper types and define nullability |
| DTO receives wrong data type | Constructor type incompatible with driver-returned type | Use compatible types, converters, or cast in SQL |
| Custom SQL returns extra unnecessary columns | Using `SELECT *` or failing to restrict the column list | Select only required columns and alias clearly |
| Nested projection does not return expected data | Assuming Spring Data auto-JOINs or lazy-loads | Write explicit JOIN/DTO projections or compose reactive queries |
| Using a projection to update an entity | Projection is not a full aggregate | Load the entity or use an update API, then build a result DTO |
| Error when changing repository return type | Query method/store/version does not support the desired projection | Check version support and use `@Query`/`DatabaseClient` when needed |

## 19. Testing Projections

Projections should be tested at the repository level against a compatible database/driver. Unit tests that manually instantiate DTOs do not prove that mapping from `Row` or interface proxies works properly.

Cases to verify:

1. Interface projections expose only the declared getters.
2. DTO constructors receive the right values by property name.
3. Records are constructed via canonical constructors with accurate components.
4. SQL aliases match property/record component names.
5. Nullable columns map to appropriate wrapper types.
6. Numeric, temporal, enum, and specialized types are driver-compatible.
7. Aggregate/JOIN queries return the right types and aliases.
8. `Mono` completes empty when no row exists; `Flux` emits the expected row count.
9. Projections do not accidentally expose sensitive fields in responses.

Example with Reactor Test:

```java
StepVerifier.create(customerRepository.findByActiveTrue())
        .assertNext(item -> {
            assertThat(item.getName()).isEqualTo("An Nguyen");
            assertThat(item.getEmail()).isEqualTo("an@example.com");
        })
        .verifyComplete();
```

With records, use accessors such as `item.name()` and `item.email()`. Seed test data with multiple rows, null values, and unprojected fields to verify both mapping and data boundaries.

## 20. Practical Guidelines

- Choose a projection when the use case needs only part of an entity's data or a dedicated response type.
- Use interface projections for small getter contracts; use DTO classes when a dedicated result class is needed; use records for concise, immutable DTOs.
- Declare getters, constructor parameters, or record components matching the properties to map.
- With custom SQL, select only needed columns and alias them to the projection's property/constructor names.
- Use bind parameters for values in `@Query`; do not concatenate input into SQL.
- Do not assume nested projections automatically create JOINs or lazy loading like JPA.
- Use `@Query` or `DatabaseClient` when JOINs, aggregates, or multi-table results are needed.
- Use wrapper types for components that may receive SQL `NULL`.
- Keep projections as read results; use entities or update APIs to modify data.
- Return `Mono`/`Flux` and compose with reactive operators; do not block inside WebFlux services/controllers.
- Test constructor mapping, aliases, nulls, data types, and result counts against a compatible database.
- Check the projection capabilities of your exact Spring Data Relational version before relying on advanced APIs.

## 21. Conclusion

Projections in Spring Data Relational R2DBC let you define query result shapes using interfaces, DTO classes, or Java records. Interface projections expose getters for the properties to read; DTOs use constructor mapping; records leverage canonical constructors to produce immutable results. Repositories can return projections in `Mono` or `Flux`, while `@Query` provides control over SQL and aliases when JOINs or aggregated data are needed.

Choose the projection style based on caller needs, align property/constructor names with queried data, and explicitly handle SQL `NULL` and driver return types. Projections reduce entity coupling and constrain response payloads, though they do not replace relational associations, transactions, or update logic. Testing mappings against an actual database/driver ensures DTOs and records receive accurate data.
