# Phép chiếu dựa trên DTO hoặc Java record

Trong Spring Data Relational R2DBC, phép chiếu (projection) cho phép truy vấn trả về đúng hình dạng dữ liệu mà tầng gọi cần, thay vì luôn trả về toàn bộ entity. Một projection có thể là interface chỉ khai báo các getter cần thiết, một lớp DTO có constructor phù hợp hoặc một Java record. Cách tiếp cận này hữu ích cho API response, màn hình danh sách, báo cáo nhẹ và các truy vấn chỉ cần một phần thuộc tính của aggregate.

Projection là cách định nghĩa kết quả đọc. Nó không thay đổi cấu trúc bảng, không tự tạo quan hệ giữa các bảng và không thay thế entity dùng cho thao tác ghi. Với R2DBC, kết quả vẫn được phát qua `Mono` hoặc `Flux`; ứng dụng nên giữ publisher reactive xuyên suốt thay vì chặn luồng để lấy DTO.

## 1. Projection giải quyết vấn đề gì?

Giả sử entity `Customer` có nhiều thuộc tính: ID, tên, email, số điện thoại, địa chỉ, trạng thái, thông tin kiểm toán và các trường nội bộ. Một màn hình danh sách chỉ cần tên và email. Nếu trả toàn bộ entity, tầng API nhận dữ liệu nhiều hơn nhu cầu và có nguy cơ vô tình công khai thuộc tính không nên xuất hiện trong response.

Projection mô tả rõ phần dữ liệu cần dùng:

```java
public interface CustomerListItem {
    String getName();
    String getEmail();
}
```

Repository có thể trả `Flux<CustomerListItem>` cho truy vấn danh sách. Tầng gọi chỉ nhìn thấy hai thuộc tính được khai báo trong projection.

Các lợi ích chính:

- **Giảm dữ liệu ở tầng ứng dụng:** kết quả có thể chỉ chứa các thuộc tính cần thiết thay vì materialize toàn bộ entity.
- **Tách mô hình persistence khỏi response:** DTO/record không cần là entity được quản lý bởi Spring Data Relational.
- **Giới hạn dữ liệu được công khai:** API có thể trả một kiểu kết quả được thiết kế riêng, không để lộ các trường nội bộ của entity.
- **Tăng tính rõ ràng:** chữ ký repository thể hiện chính xác dữ liệu mà use case cần.
- **Giữ xử lý reactive:** projection có thể được phát trong `Mono` hoặc `Flux` như entity thông thường.

Việc database chỉ chọn đúng các cột projection phụ thuộc loại truy vấn và cách khai báo. Với truy vấn được Spring Data tạo từ repository, framework có thể tối ưu danh sách cột theo projection khi khả năng của store hỗ trợ. Với `@Query` hoặc SQL viết tay, hãy chủ động chọn đúng cột và alias. Chỉ đổi kiểu trả về thành DTO không tự động bảo đảm câu SQL thủ công đã bỏ `SELECT *`.

## 2. Entity dùng trong ví dụ

Giả sử bảng `customer` có các cột:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    email VARCHAR(320) NOT NULL,
    phone_number VARCHAR(30),
    internal_note VARCHAR(500),
    active BOOLEAN NOT NULL
);
```

Entity ánh xạ bảng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;

    private String email;

    @Column("phone_number")
    private String phoneNumber;

    @Column("internal_note")
    private String internalNote;

    private Boolean active;

    // Constructor, getters và setters.
}
```

Entity mô tả mô hình persistence. Projection có thể chỉ hiển thị `name` và `email` mà không cần thay đổi entity hoặc thêm quan hệ mới.

## 3. Interface-based projection

Interface projection khai báo getter cho các thuộc tính muốn đọc. Spring Data tạo implementation/proxy cho interface và cung cấp giá trị từ kết quả truy vấn.

```java
public interface CustomerListItem {
    String getName();
    String getEmail();
}
```

Repository khai báo phương thức trả về projection:

```java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerListItem> findByActiveTrue();
}
```

Phương thức trên trả về danh sách khách hàng đang hoạt động dưới dạng `Flux<CustomerListItem>`. Tầng gọi chỉ truy cập `getName()` và `getEmail()`:

```java
public Flux<CustomerListItem> getActiveCustomerList() {
    return customerRepository.findByActiveTrue();
}
```

Với projection interface, tên getter cần khớp property của entity theo quy ước JavaBeans. Ví dụ `getPhoneNumber()` tương ứng property `phoneNumber`, dù tên cột vật lý trong database là `phone_number` nhờ mapping `@Column`.

Interface projection phù hợp khi muốn một hợp đồng getter nhỏ, đặc biệt nếu cần nhiều kiểu projection khác nhau cho cùng entity. Proxy có thể thực hiện truy cập property thông qua Spring Data; không nên xem nó như một entity đầy đủ có thể lưu lại bằng `save()`.

## 4. Closed projection và getter tính toán

Một closed projection chỉ khai báo các property có thật trên aggregate/entity:

```java
public interface CustomerNameView {
    String getName();
    String getEmail();
}
```

Vì Spring Data biết rõ những property được yêu cầu, framework có thể tối ưu việc lấy dữ liệu nếu store và query path hỗ trợ.

Interface cũng có thể định nghĩa default method dựa trên các getter đã khai báo:

```java
public interface CustomerNameView {
    String getName();
    String getEmail();

    default String getLabel() {
        return getName() + " <" + getEmail() + ">";
    }
}
```

`getLabel()` được tính trong Java từ hai thuộc tính projection. Nó không cần một cột `label` trong database.

Spring Data Commons còn có khái niệm open projection dùng `@Value`/SpEL để tính giá trị dựa trên target object. Với projection có biểu thức truy cập tùy ý, framework không thể luôn suy ra chính xác những cột cần thiết để tối ưu. Khả năng hỗ trợ và hành vi tối ưu cụ thể cần được kiểm tra theo phiên bản Spring Data Relational. Với response đơn giản, closed projection hoặc DTO/record thường dễ dự đoán hơn.

## 5. Class-based projection bằng DTO

Class-based projection sử dụng một lớp DTO có constructor nhận các thuộc tính cần thiết. DTO không cần annotation `@Table` hoặc `@Id` nếu chỉ dùng làm kiểu kết quả truy vấn.

```java
public class CustomerSummary {

    private final String name;
    private final String email;

    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }
}
```

Repository có thể khai báo kiểu kết quả DTO:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByActiveTrue();
}
```

Spring Data dùng constructor mapping để tạo `CustomerSummary` từ dữ liệu đọc được. Tên tham số constructor cần tương ứng với property được chiếu và metadata mapping. Với lớp Java thông thường, nên biên dịch có thông tin tên tham số (`-parameters`) hoặc cung cấp metadata constructor phù hợp để Spring Data có thể nhận diện chính xác tham số. Nếu có nhiều constructor, có thể đánh dấu constructor được dùng bằng `@PersistenceCreator` theo quy tắc mapping của phiên bản đang sử dụng.

DTO thường là kiểu chỉ đọc. Nó không cần chứa toàn bộ thuộc tính của entity và không nên được dùng như một entity để gọi repository `save()`.

## 6. Projection bằng Java record

Java record là lựa chọn gọn cho DTO bất biến. Các component của record tự tạo accessor, constructor canonical và phương thức `equals`, `hashCode`, `toString`.

```java
public record CustomerSummary(
        String name,
        String email
) {
}
```

Repository có thể trả record trực tiếp:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByActiveTrue();
}
```

Record component `name` và `email` tương ứng với property cần lấy. Spring Data sử dụng canonical constructor để tạo record. Tên component được lưu trong metadata của record nên việc ánh xạ constructor thường rõ ràng hơn một DTO có nhiều constructor.

Record phù hợp cho kết quả đọc không cần thay đổi sau khi tạo. Nếu projection có trường nullable, hãy dùng kiểu tham chiếu như `String`, `Long`, `Boolean`; kiểu primitive như `long` hoặc `boolean` không thể biểu diễn SQL `NULL`.

## 7. DTO/record với tên cột khác tên property

Tên property Java và tên cột SQL có thể khác nhau. Entity có thể ánh xạ `phoneNumber` tới `phone_number` bằng `@Column`. Khi truy vấn do Spring Data tạo từ entity metadata, framework sử dụng mapping context để xử lý tên cột.

Với SQL tùy chỉnh, hãy alias cột về tên mà DTO/record mong đợi:

```java
public record CustomerContactView(
        String name,
        String phoneNumber
) {
}
```

```java
@Query("""
       SELECT name,
              phone_number AS phoneNumber
       FROM customer
       WHERE active = TRUE
       """)
Flux<CustomerContactView> findActiveContacts();
```

Alias `phoneNumber` giúp kết quả có tên phù hợp với component `phoneNumber`. Quy tắc chữ hoa/chữ thường và cách driver trả metadata tên cột có thể khác theo database. Với SQL tùy chỉnh, nên dùng alias tường minh và kiểm thử trên đúng driver/database.

Nếu DTO dùng component `firstName` nhưng entity property là `firstname`, hãy thống nhất tên mapping hoặc alias phù hợp. Đừng giả định Spring Data luôn tự suy ra mọi biến thể camelCase/snake_case trong một câu SQL thủ công.

## 8. Projection với `@Query`

Với truy vấn SQL tùy chỉnh, phương thức repository có thể trả DTO hoặc record. SQL cần trả các cột cần thiết và đặt alias phù hợp với tên property/constructor của kiểu projection.

```java
public record CustomerOrderCount(
        Long customerId,
        String customerName,
        Long orderCount
) {
}
```

```java
@Query("""
       SELECT c.id AS customerId,
              c.name AS customerName,
              COUNT(o.id) AS orderCount
       FROM customer c
       LEFT JOIN orders o ON o.customer_id = c.id
       WHERE c.active = TRUE
       GROUP BY c.id, c.name
       """)
Flux<CustomerOrderCount> findActiveCustomerOrderCounts();
```

Đây là projection kết quả tổng hợp. `CustomerOrderCount` không phải entity tương ứng với một bảng; nó chỉ mô tả một hàng kết quả. SQL chịu trách nhiệm join và tính `COUNT`; Spring Data/driver ánh xạ các cột trả về vào constructor record.

Với custom SQL, không nên dùng `SELECT *` khi chỉ cần ba trường. Chọn đúng cột và alias rõ ràng giúp giảm dữ liệu truyền, tránh tên cột trùng giữa nhiều bảng và làm constructor mapping dễ dự đoán.

`@Query` trong Spring Data R2DBC sử dụng cơ chế bind tham số của repository. Nếu tên tham số không được giữ lại khi biên dịch hoặc dự án cần rõ ràng, có thể dùng `@Param`:

```java
@Query("SELECT id, name, email FROM customer WHERE active = :active")
Flux<CustomerSummary> findByActive(@Param("active") boolean active);
```

Không nối dữ liệu người dùng vào SQL. Dùng bind parameter cho giá trị; với tên bảng/cột hoặc hướng sắp xếp, dùng whitelist vì identifier không thể được bảo vệ bằng cách bind như một giá trị thông thường.

## 9. Projection với derived query method

Derived query method cho phép Spring Data suy ra truy vấn từ tên phương thức và kiểu kết quả projection:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {

    Flux<CustomerSummary> findByCity(String city);

    Mono<CustomerNameView> findByEmail(String email);
}
```

Phương thức trả `Flux<CustomerSummary>` khi có nhiều khách hàng trong thành phố; phương thức trả `Mono<CustomerNameView>` khi truy vấn theo email và dự kiến có tối đa một kết quả. Nếu không tìm thấy, `Mono` hoàn tất rỗng. Nếu một phương thức dạng đơn kết quả nhận nhiều hàng, hành vi có thể là lỗi sai số lượng kết quả theo hợp đồng truy vấn.

Tên phương thức và điều kiện vẫn dựa trên property của entity. Kiểu trả về projection xác định hình dạng dữ liệu mà tầng gọi nhận được. Nếu truy vấn cần join, aggregate hoặc SQL đặc thù, `@Query` thường thể hiện rõ hơn.

## 10. Dynamic projections

Trong các repository query method hỗ trợ dynamic projections, có thể chọn kiểu kết quả tại thời điểm gọi bằng tham số `Class<T>`:

```java
<T> Flux<T> findByCity(String city, Class<T> projectionType);
```

Ví dụ sử dụng:

```java
Flux<CustomerSummary> summaries =
        customerRepository.findByCity("Hobbiton", CustomerSummary.class);

Flux<CustomerNameView> names =
        customerRepository.findByCity("Hobbiton", CustomerNameView.class);
```

Dynamic projection giúp tái sử dụng điều kiện truy vấn với nhiều kiểu kết quả. Khả năng và cú pháp chính xác phụ thuộc phiên bản Spring Data Relational và loại query method. Hãy xác nhận repository factory của dự án hỗ trợ dynamic projection trước khi dùng. Nếu không, khai báo các phương thức có kiểu trả về tĩnh hoặc dùng `R2dbcEntityTemplate`/`DatabaseClient` để điều khiển kết quả.

## 11. Projection và kiểu trả về reactive

Projection không thay đổi semantics reactive của repository:

| Kiểu trả về | Ý nghĩa |
| --- | --- |
| `Mono<CustomerSummary>` | Không hoặc một projection; hoàn tất rỗng nếu không có hàng |
| `Flux<CustomerSummary>` | Từ không đến nhiều projection, phát từng kết quả |
| `Mono<Boolean>` | Một giá trị kiểm tra, nếu phương thức truy vấn được thiết kế để trả boolean |
| `Mono<Long>` | Một giá trị đếm hoặc số lượng theo truy vấn |

Ví dụ service chuyển DTO sang API response:

```java
public Flux<CustomerResponse> listActiveCustomers() {
    return customerRepository.findByActiveTrue()
            .map(item -> new CustomerResponse(item.getName(), item.getEmail()));
}
```

Nếu repository đã trả DTO đúng hình dạng response, có thể trả tiếp publisher đó từ service/controller mà không cần map thêm. Nếu cần bổ sung dữ liệu từ dịch vụ khác, dùng `flatMap`/`zipWhen` hoặc toán tử reactive phù hợp.

Không gọi `block()` để lấy projection trong service reactive. Việc block có thể giữ event-loop thread và làm mất lợi ích non-blocking của R2DBC.

## 12. Projection không phải entity để ghi

DTO hoặc interface projection thường là kết quả đọc. Chúng không nhất thiết có đầy đủ ID, trạng thái hoặc các thuộc tính bắt buộc của aggregate. Không nên truyền một projection vào repository `save()` như thể nó là entity.

Một luồng cập nhật rõ ràng có thể gồm:

1. Nhận command/DTO đầu vào từ API.
2. Tải entity hoặc thực hiện thao tác update phù hợp.
3. Áp dụng quy tắc nghiệp vụ.
4. Lưu entity bằng repository/template.
5. Trả DTO/projection được tạo từ kết quả hoặc truy vấn đọc lại.

Ví dụ:

```java
public Mono<CustomerSummary> renameCustomer(Long id, String newName) {
    return customerRepository.findById(id)
            .switchIfEmpty(Mono.error(new CustomerNotFoundException(id)))
            .flatMap(customer -> {
                customer.setName(newName);
                return customerRepository.save(customer);
            })
            .map(saved -> new CustomerSummary(saved.getName(), saved.getEmail()));
}
```

Ở đây entity được dùng cho cập nhật; record `CustomerSummary` chỉ là kết quả trả về. Với update một số cột theo điều kiện, `R2dbcEntityTemplate` fluent update có thể phù hợp hơn việc tải entity trước.

## 13. Projection và nested property

Spring Data Relational mô hình hóa aggregate và quan hệ theo quy tắc relational mapping; không nên giả định projection lồng nhau sẽ tự tạo JOIN hoặc lazy-load như một số ORM JPA. Nếu projection cần thông tin từ nhiều bảng, hãy xác định rõ cách lấy dữ liệu:

- Viết `@Query` với JOIN và alias cột vào DTO/record.
- Dùng `DatabaseClient` cho SQL phức tạp hoặc kết quả không ánh xạ tự nhiên thành entity.
- Thực hiện nhiều truy vấn reactive có chủ đích và ghép kết quả nếu số lượng dữ liệu phù hợp.
- Tạo một view hoặc read model riêng nếu truy vấn tổng hợp được dùng thường xuyên.

Ví dụ projection tổng hợp từ hai bảng:

```java
public record OrderListItem(
        Long orderId,
        String customerName,
        BigDecimal total
) {
}
```

```java
@Query("""
       SELECT o.id AS orderId,
              c.name AS customerName,
              o.total AS total
       FROM orders o
       JOIN customer c ON c.id = o.customer_id
       WHERE o.status = :status
       """)
Flux<OrderListItem> findOrderList(@Param("status") String status);
```

Ở đây JOIN được viết rõ trong SQL. Record mô tả đúng ba cột cần trả về; không cần khai báo một object graph giả định giữa `Order` và `Customer`.

## 14. Null và kiểu dữ liệu trong DTO/record

Projection có thể chứa cột nullable. Nếu database trả SQL `NULL`, kiểu đích phải có khả năng biểu diễn giá trị đó.

Ví dụ:

```java
public record CustomerContactView(
        Long id,
        String name,
        String phoneNumber,
        Boolean active
) {
}
```

`phoneNumber` và `Boolean` là kiểu tham chiếu, do đó có thể nhận null nếu cột cho phép. Nếu dùng `long` hoặc `boolean` cho cột nullable, constructor mapping có thể thất bại hoặc không thể biểu diễn đúng trạng thái null. Chọn kiểu wrapper khi cột có thể không có giá trị.

Kiểu DTO cần tương thích với kiểu mà driver trả về. Ví dụ `NUMERIC` thường phù hợp với `BigDecimal`; kiểu thời gian phải tương thích với schema và dialect. Với SQL tùy chỉnh, cast hoặc alias có thể cần thiết nếu biểu thức trả về kiểu khác với constructor parameter.

Không dùng `Mono.empty()` để biểu diễn một hàng có cột null. `Mono.empty()` nghĩa là truy vấn không phát hàng nào; cột null vẫn thuộc một projection được phát ra.

## 15. DTO có nhiều constructor

Spring Data cần xác định constructor dùng để tạo DTO. Lớp có một constructor rõ ràng thường dễ ánh xạ nhất:

```java
public class CustomerSummary {
    private final String name;
    private final String email;

    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

Nếu DTO có nhiều constructor, có thể đánh dấu constructor persistence bằng `@PersistenceCreator`:

```java
import org.springframework.data.annotation.PersistenceCreator;

public class CustomerSummary {
    private final String name;
    private final String email;

    public CustomerSummary(String name) {
        this(name, null);
    }

    @PersistenceCreator
    public CustomerSummary(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

Constructor được chọn cần có tham số tương ứng với dữ liệu projection. Với Java record, canonical constructor thường là lựa chọn tự nhiên nên không cần tạo thêm constructor chỉ để ánh xạ.

## 16. Projection với `R2dbcEntityTemplate`

Khi cần query động hoặc không muốn tạo repository method cho từng kiểu lọc, có thể dùng `R2dbcEntityTemplate`/`R2dbcEntityOperations`. Fluent select API cho phép xác định domain type và kiểu kết quả theo khả năng của phiên bản Spring Data Relational.

Ví dụ đọc entity theo điều kiện:

```java
Query query = Query.query(where("active").is(true));

Flux<Customer> customers = template.select(Customer.class)
        .matching(query)
        .all();
```

Khi cần kết quả DTO, hãy kiểm tra API projection/select của phiên bản đang dùng. Với SQL JOIN hoặc aggregate, repository `@Query` trả DTO/record hoặc `DatabaseClient` thường là lựa chọn tường minh hơn vì cho phép chỉ rõ cột và alias.

Không nên giả định mọi overload của `select(...)` đều có thể nhận tùy ý kiểu DTO ở mọi phiên bản. API fluent của Spring Data Relational có thể thay đổi; đối chiếu Javadoc đúng dependency trước khi viết code.

## 17. Khi nào chọn interface, DTO class hay record?

| Tiêu chí | Interface projection | DTO class | Java record |
| --- | --- | --- | --- |
| Khai báo | Getter cho các property cần đọc | Constructor và accessor/getter | Component trong header record |
| Tính bất biến | Proxy phụ thuộc implementation | Có thể thiết kế immutable hoặc mutable | Bất biến theo component |
| Getter tính toán | Có thể dùng default method; open projection tùy hỗ trợ | Thêm method bình thường | Thêm method bình thường |
| Constructor mapping | Không cần constructor DTO do Spring tạo proxy | Cần constructor phù hợp | Dùng canonical constructor |
| Phù hợp | View nhỏ, nhiều kiểu getter, hợp đồng interface | Tích hợp Java cũ hoặc DTO có logic/constructor riêng | DTO response gọn, bất biến |
| Hạn chế | Proxy và biểu thức động có thể khó dự đoán tối ưu | Cần quản lý constructor và tên tham số | Yêu cầu Java hỗ trợ record và mapping tương thích |

Không có lựa chọn bắt buộc cho mọi truy vấn. Với DTO kết quả đơn giản trên Java hiện đại, record thường ngắn và dễ đọc. Interface phù hợp khi muốn mô tả một view bằng getter. Lớp DTO thông thường phù hợp khi cần tương thích codebase cũ hoặc cần constructor/logic phức tạp hơn.

## 18. Những lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Projection property không được ánh xạ | Getter/component/constructor parameter không khớp property hoặc tên alias | Kiểm tra property name, `@Column`, alias và metadata constructor |
| DTO không tạo được | Constructor không phù hợp hoặc tên tham số không được nhận diện | Dùng một constructor rõ ràng, record hoặc `@PersistenceCreator`; bật `-parameters` khi cần |
| Giá trị trả về null dù cột có dữ liệu | Alias sai, driver trả tên cột khác hoặc query chọn thiếu cột | Alias tường minh và kiểm thử trên database thực tế |
| Lỗi khi cột nullable | DTO dùng primitive hoặc constructor không chấp nhận null | Dùng wrapper và xác định nullability |
| DTO nhận dữ liệu sai kiểu | Kiểu constructor không tương thích kiểu driver trả về | Dùng kiểu phù hợp, converter hoặc cast trong SQL |
| SQL tùy chỉnh trả nhiều cột thừa | Dùng `SELECT *` hoặc không giới hạn danh sách cột | Chọn đúng cột cần thiết và alias rõ ràng |
| Projection lồng nhau không trả dữ liệu như mong đợi | Giả định Spring Data tự JOIN hoặc lazy-load | Viết JOIN/DTO projection rõ ràng hoặc ghép truy vấn reactive |
| Dùng projection để cập nhật entity | Projection không phải aggregate đầy đủ | Tải entity hoặc dùng API update phù hợp rồi tạo DTO kết quả |
| Lỗi khi đổi kiểu trả về repository | Query method/store/version không hỗ trợ projection mong muốn | Kiểm tra hỗ trợ của phiên bản và dùng `@Query`/DatabaseClient khi cần |

## 19. Kiểm thử projection

Nên kiểm thử projection ở mức repository với database/driver tương thích. Unit test tạo DTO thủ công không chứng minh mapping từ `Row` hoặc proxy interface hoạt động đúng.

Các trường hợp nên xác minh:

1. Interface projection chỉ đọc được các getter đã khai báo.
2. DTO constructor nhận đúng giá trị theo tên property.
3. Record được tạo qua canonical constructor với các component chính xác.
4. SQL alias khớp tên property/record component.
5. Cột nullable được ánh xạ vào kiểu wrapper phù hợp.
6. Kiểu số, thời gian, enum và kiểu đặc thù tương thích driver.
7. Truy vấn tổng hợp/JOIN trả đúng kiểu và alias.
8. `Mono` hoàn tất rỗng khi không có hàng; `Flux` phát đúng số lượng hàng.
9. Projection không vô tình đưa trường nhạy cảm vào response.

Ví dụ với Reactor Test:

```java
StepVerifier.create(customerRepository.findByActiveTrue())
        .assertNext(item -> {
            assertThat(item.getName()).isEqualTo("An Nguyen");
            assertThat(item.getEmail()).isEqualTo("an@example.com");
        })
        .verifyComplete();
```

Với record, dùng accessor như `item.name()` và `item.email()`. Seed dữ liệu có nhiều hàng, giá trị null và trường không được chiếu để xác minh cả mapping lẫn ranh giới dữ liệu.

## 20. Nguyên tắc thực hành

- Chọn projection khi use case chỉ cần một phần dữ liệu của entity hoặc cần kiểu kết quả riêng cho response.
- Dùng interface projection cho hợp đồng getter nhỏ; dùng DTO class khi cần lớp kết quả riêng; dùng record cho DTO bất biến, gọn.
- Khai báo getter, constructor parameter hoặc record component khớp với property cần ánh xạ.
- Với custom SQL, chọn đúng cột và alias theo tên property/constructor của projection.
- Dùng bind parameter cho giá trị trong `@Query`; không nối input vào SQL.
- Không giả định projection lồng nhau tự tạo JOIN hoặc lazy loading như JPA.
- Dùng `@Query` hoặc `DatabaseClient` khi cần JOIN, aggregate hoặc kết quả nhiều bảng.
- Dùng kiểu wrapper cho component có thể nhận SQL `NULL`.
- Giữ projection là kết quả đọc; dùng entity hoặc API update để thay đổi dữ liệu.
- Trả `Mono`/`Flux` và ghép bằng toán tử reactive; không block trong service/controller WebFlux.
- Kiểm thử constructor mapping, alias, null, kiểu dữ liệu và số lượng kết quả trên database tương thích.
- Kiểm tra khả năng projection của đúng phiên bản Spring Data Relational trước khi dựa vào API nâng cao.

## 21. Kết luận

Projection trong Spring Data Relational R2DBC cho phép định nghĩa hình dạng dữ liệu truy vấn bằng interface, DTO class hoặc Java record. Interface projection cung cấp các getter cho thuộc tính cần đọc; DTO dùng constructor mapping; record tận dụng canonical constructor để tạo kết quả bất biến. Repository có thể trả projection trong `Mono` hoặc `Flux`, còn `@Query` cho phép kiểm soát SQL và alias khi cần JOIN hoặc dữ liệu tổng hợp.

Hãy chọn kiểu projection theo nhu cầu của tầng gọi, khớp tên property/constructor với dữ liệu truy vấn và xử lý rõ SQL `NULL` cùng kiểu driver trả về. Projection giúp giảm phụ thuộc vào entity và giới hạn dữ liệu response, nhưng không tự thay thế quan hệ relational, transaction hay logic cập nhật. Kiểm thử mapping trên database/driver thực tế sẽ giúp bảo đảm DTO và record nhận đúng dữ liệu.
