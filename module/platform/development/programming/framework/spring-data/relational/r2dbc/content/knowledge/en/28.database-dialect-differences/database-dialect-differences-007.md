# Differences in Bind Markers, Identifier Quoting, and Reserved Keywords

## 1. Why Does SQL Differ Across Database Engines?

Spring Data R2DBC provides repositories, `R2dbcEntityTemplate`, and `DatabaseClient` for working with relational databases. However, R2DBC is a data-access abstraction; it does not turn PostgreSQL, MySQL, SQL Server, and H2 into a single engine sharing identical SQL syntax.

Common differences include:

- Bind parameter markers accepted by the driver.
- How table names, column names, schemas, and other identifiers are quoted.
- Sets of reserved keywords.
- Case-folding rules for unquoted identifiers.
- Pagination syntax, generated values, data types, and SQL functions.
- How the driver binds null values, collections, and specialized data types.

For example, native markers may be `$1` in PostgreSQL, `?` in MySQL, or driver-specific markers in SQL Server. A column named `order` can confuse the parser because of `ORDER BY`. A table named `user` can also collide with keywords or built-in names.

In Spring Data R2DBC, distinguish clearly:

1. **SQL generated by Spring Data:** the dialect helps choose bind markers, identifier quoting, and certain engine-specific syntax.
2. **SQL written by the application:** statements in `@Query` or `DatabaseClient.sql(...)` must still match the target database. Do not assume the framework translates every native SQL query to another engine.

Understanding this boundary prevents errors when switching databases or building multi-engine applications.

## 2. What Is a Bind Parameter?

A bind parameter is a placeholder in an SQL statement where the driver attaches a data value at execution time. The application writes a statement containing markers and binds values separately, rather than concatenating input data directly into SQL.

Conceptual example:

```sql
SELECT id, email_address
FROM customer
WHERE email_address = <parameter>;
```

`<parameter>` is just an illustrative placeholder; the actual marker depends on the driver and dialect.

Bind parameters help:

- Avoid string concatenation of input data into SQL.
- Reduce SQL injection risk for values.
- Pass data types separately from the SQL text.
- Enable the database to reuse execution plans.
- Separate SQL structure from data.

Never do this:

```java
// Unsafe
String sql = "SELECT * FROM customer WHERE email_address = '"
        + email + "'";
```

Bind values instead:

```java
databaseClient.sql("SELECT id FROM customer WHERE email_address = :email")
        .bind("email", email)
        .fetch()
        .all();
```

This example uses Spring `DatabaseClient` named parameters. Spring converts the marker according to the dialect/driver at execution time.

## 3. Native Bind Markers

The R2DBC SPI operates on `Statement` and bind slots exposed by the driver. Native markers are not uniform across all drivers.

| Database Engine / Driver | Common Native Markers | Example |
| --- | --- | --- |
| PostgreSQL R2DBC | `$1`, `$2`, ... | `WHERE id = $1` |
| MySQL R2DBC | `?` | `WHERE id = ?` |
| Microsoft SQL Server R2DBC | Named/ordinal markers such as `@P0` depending on driver | `WHERE id = @P0` |
| H2 R2DBC | Driver convention, typically positional | Check docs for exact version |

These are typical forms for recognizing syntax, not guarantees across every driver version. Check the documentation for the driver in use.

### 3.1. PostgreSQL

PostgreSQL typically uses 1-based positional markers starting at `$1`:

```sql
SELECT id, email_address
FROM customer
WHERE email_address = $1
  AND status = $2;
```

In the native R2DBC API, Java bind indices typically start at 0, whereas SQL markers start at `$1`:

```java
connection.createStatement("SELECT id FROM customer WHERE email_address = $1")
        .bind(0, email)
        .execute();
```

With common PostgreSQL drivers, `$1` maps to index `0` in `Statement.bind(0, value)`. Do not confuse SQL marker numbering with Java API index numbering.

### 3.2. MySQL

MySQL R2DBC typically uses question marks `?` as positional markers:

```sql
SELECT id, email_address
FROM customer
WHERE email_address = ?
  AND status = ?;
```

Values are bound in order of appearance:

```java
connection.createStatement(
        "SELECT id FROM customer WHERE email_address = ? AND status = ?")
        .bind(0, email)
        .bind(1, status)
        .execute();
```

Question marks carry no names. Reordering markers or binding the wrong index attaches values to the wrong columns.

### 3.3. SQL Server

The SQL Server driver uses its own marker convention, often representing parameters by name/ordinal such as `@P0`. Exact syntax and bind usage depend on the driver version:

```sql
SELECT id, email_address
FROM customer
WHERE email_address = @P0;
```

When using Spring `DatabaseClient`, prefer named parameters at the application layer and let the dialect/driver handle native markers. When using R2DBC `Statement` directly, follow the marker rules published by the SQL Server driver.

### 3.4. Never Convert Markers With String.replace

Never turn `:name` into `?`, `$1`, or `@P0` using `String.replace`. SQL statements can contain these characters inside string literals, comments, casts, or engine-specific expressions. Naive string replacement easily breaks SQL or misorders bindings.

Use `DatabaseClient`, Spring Data repositories, or `BindMarkersFactory` to handle markers per dialect.

## 4. Spring Named Parameters vs. Native Markers

Spring `DatabaseClient` supports writing named parameters:

```java
databaseClient.sql("""
        SELECT id, display_name
        FROM customer
        WHERE status = :status
          AND created_at >= :fromTime
        """)
        .bind("status", status)
        .bind("fromTime", fromTime)
        .fetch()
        .all();
```

`:status` and `:fromTime` are Spring named parameters. `DatabaseClient` expands them into markers suitable for the dialect/driver and binds the corresponding values.

Illustration of the same query across layers:

```text
Spring SQL:       WHERE status = :status
PostgreSQL SQL:   WHERE status = $1
MySQL SQL:        WHERE status = ?
SQL Server SQL:  WHERE status = @P0 (per driver)
```

Not every R2DBC API understands `:name`. `io.r2dbc.spi.Connection.createStatement(...)` expects SQL in the driver's native syntax; it does not provide Spring `DatabaseClient`'s named-parameter expansion.

### 4.1. Binding by Name

```java
databaseClient.sql("SELECT * FROM customer WHERE id = :id")
        .bind("id", 42L)
        .fetch()
        .one();
```

The name passed to `.bind("id", ...)` must match the `:id` marker.

### 4.2. Binding by Position

```java
databaseClient.sql("SELECT * FROM customer WHERE id = ?")
        .bind(0, 42L)
        .fetch()
        .one();
```

When using positional markers, adhere to the markers accepted by the driver/dialect and bind in exact order. Named parameters are generally more readable when an application supports multiple dialects.

### 4.3. Named Parameter Expansion

`DatabaseClient` provides named-parameter expansion in supported Spring Framework versions. If the application customizes the builder or disables this feature, `:name` markers may not be translated. Check your `DatabaseClient.Builder` configuration and framework version before relying on named parameters.

With Spring Data R2DBC `@Query`, method parameters are likewise handled by Spring Data's query mapping mechanism. Never blindly apply one driver's native marker syntax to all repository queries.

## 5. Bind Values, Not Table or Column Names

Bind parameters represent **data values**, not SQL identifiers.

The following does not mean `:column` gets replaced by a column name:

```sql
SELECT :column
FROM customer;
```

Once bound, the marker is treated as a scalar value. Likewise, you cannot bind a table name with a marker:

```sql
SELECT * FROM :tableName;
```

This is not valid identifier binding.

If dynamic sort columns are required, map input against an allowlist:

```java
private static final Map<String, String> SORT_COLUMNS = Map.of(
        "created", "created_at",
        "name", "display_name",
        "email", "email_address");

public Flux<Customer> findCustomers(String requestedSort) {
    String column = SORT_COLUMNS.get(requestedSort);
    if (column == null) {
        return Flux.error(new IllegalArgumentException("Unsupported sort field"));
    }

    String sql = "SELECT id, display_name, email_address FROM customer ORDER BY "
            + column;
    return databaseClient.sql(sql)
            .map(this::mapCustomer)
            .all();
}
```

Only identifiers selected from an application-controlled allowlist may be placed into SQL. Never concatenate client-supplied column names directly.

When dynamic identifier quoting is needed, use Spring Data Relational's `SqlIdentifier`/`IdentifierProcessing` where appropriate, or a dialect-specific quoting helper. `bind()` does not protect identifiers the way it protects values.

## 6. Identifier Quoting

Identifiers are SQL object names such as schemas, tables, columns, indexes, constraints, and sequences. Databases provide quote delimiters so parsers treat the enclosed text as an object name, especially when names collide with keywords or contain special characters.

| Database Engine | Common Identifier Quote Delimiters | Example |
| --- | --- | --- |
| PostgreSQL | Double quotes `"` | `"order"`, `"CreatedAt"` |
| MySQL | Backticks (grave accent) | Example: the name order enclosed in backticks |
| SQL Server | Square brackets `[]`; double quotes when `QUOTED_IDENTIFIER` is on | `[order]`, `[user]` |
| H2 | Double quotes `"` | `"order"` |

Single quotes `'` denote string literals, not table or column quotes:

```sql
SELECT 'customer' AS label; -- string literal
SELECT "customer".id FROM "customer"; -- quoted identifier in PostgreSQL/H2
```

## 7. Case-Sensitivity Differences for Identifiers

Unquoted identifiers may be case-folded by databases according to engine-specific rules.

### 7.1. PostgreSQL

PostgreSQL folds unquoted identifiers to lowercase:

```sql
CREATE TABLE Customer (
    id BIGINT PRIMARY KEY
);
```

The actual table name is `customer`. Unquoted references `Customer`, `CUSTOMER`, and `customer` all resolve to the same lowercase identifier.

When quoted:

```sql
CREATE TABLE "Customer" (
    id BIGINT PRIMARY KEY
);

SELECT * FROM "Customer";
```

Now the name is case-sensitive; `SELECT * FROM customer` will not resolve to `"Customer"`.

### 7.2. MySQL

MySQL uses backticks to quote identifiers. Case sensitivity for database and table names depends on the operating system and `lower_case_table_names` configuration. Column names in MySQL are generally case-insensitive.

Do not assume uppercase table names working on Windows will work identically on Linux. Standardizing on lowercase and `snake_case` avoids environment discrepancies.

### 7.3. SQL Server

SQL Server supports identifiers inside square brackets:

```sql
SELECT [Order], [User]
FROM [Sales].[OrderHeader];
```

Double quotes can also quote identifiers when `QUOTED_IDENTIFIER` is enabled. Case sensitivity depends on the database or server collation.

### 7.4. Safe Naming Rules

- Use lowercase table and column names.
- Use `snake_case`.
- Avoid quoting identifiers unless necessary.
- Avoid names colliding with SQL keywords.
- If quoting is unavoidable, quote consistently across DDL, queries, migrations, and mappings.
- Never mix casings for the same physical identifier.

## 8. Reserved Keywords and Identifier Names

SQL defines keywords used in syntax. Some are reserved keywords, meaning they cannot be used as unquoted identifiers in those syntactic positions.

Examples of conflict-prone names:

- `order` — frequently collides with `ORDER BY`.
- `group` — frequently collides with `GROUP BY`.
- `select` — query keyword.
- `user` — carries special meaning or is a keyword in several engines.
- `key` — can be a keyword in certain dialects.
- `limit`, `offset`, `rank`, `value` — can have special meaning depending on engine/version.

Reserved keyword lists are not identical across PostgreSQL, MySQL, SQL Server, and H2. A word can be reserved in one engine while remaining non-reserved or contextual in another.

Do not memorize a single generic list and assume it holds across every version. Consult your target database's keyword reference and prefer clear domain names.

Instead of:

```sql
CREATE TABLE order (
    id BIGINT PRIMARY KEY
);
```

use:

```sql
CREATE TABLE purchase_order (
    id BIGINT PRIMARY KEY
);
```

The name `purchase_order` is clearer and far less likely to collide.

## 9. Quoting Identifiers When Keyword Names Are Mandatory

If a legacy schema or integration contract forces keeping the name `order`, quote it per database rules.

PostgreSQL:

```sql
CREATE TABLE "order" (
    id BIGINT PRIMARY KEY,
    status VARCHAR(20) NOT NULL
);

SELECT id, status FROM "order";
```

MySQL encloses the table name in backticks:

```sql
CREATE TABLE `order` (
    id BIGINT PRIMARY KEY,
    status VARCHAR(20) NOT NULL
);

SELECT id, status FROM `order`;
```

SQL Server:

```sql
CREATE TABLE [order] (
    id BIGINT PRIMARY KEY,
    status VARCHAR(20) NOT NULL
);

SELECT id, status FROM [order];
```

Never take PostgreSQL DDL with double quotes and run it verbatim on MySQL with default settings, nor MySQL backtick syntax on PostgreSQL. When supporting multiple databases, maintain dialect-specific DDL or migrations per engine.

## 10. IdentifierProcessing and SqlIdentifier in Spring Data Relational

Spring Data Relational models identifiers via abstractions. `SqlIdentifier` represents an SQL name along with its quoted/unquoted status; `IdentifierProcessing` describes how a database quotes and transforms identifiers.

Example:

```java
SqlIdentifier table = SqlIdentifier.unquoted("customer");
SqlIdentifier column = SqlIdentifier.quoted("Order");
```

`SqlIdentifier.unquoted(...)` represents an unquoted name. `SqlIdentifier.quoted(...)` represents an identifier that should be quoted according to dialect rules when Spring generates SQL.

Spring Data Relational's SQL-building APIs use the dialect and `IdentifierProcessing` to render identifiers properly for the target engine. This helps when the framework generates SQL from mapping metadata.

Do not confuse `SqlIdentifier.quoted("Order")` with freely injecting quotes into raw SQL strings. It is metadata for the SQL generator; native queries must still follow the syntax of the running database.

### 10.1. Entity Mapping With @Table and @Column

```java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("order_status")
    private String status;
}
```

Annotation names must match physical schema names under your naming strategy and mapping configuration. If using names requiring quotes or case sensitivity, test how your Spring Data Relational version interprets metadata and renders identifiers.

For new schemas, prefer simple lowercase names that need no quoting. When integrating legacy schemas with special identifiers, write integration tests verifying the generated SQL runs on the real database.

## 11. Dialects in Spring Data R2DBC

A dialect captures the SQL differences of a database engine that Spring Data needs to know. Spring Data R2DBC ships dialects for databases/drivers such as PostgreSQL, H2, MySQL, or SQL Server depending on the supported version.

The dialect participates in:

- Generating appropriate bind markers.
- Quoting identifiers.
- Generating certain engine-specific SQL expressions.
- Handling generated IDs or pagination per database.
- Selecting mapping rules required by the engine.

With `ReactiveCrudRepository`, Spring Data generates many SQL queries from metadata and the dialect. With `@Query` or `DatabaseClient.sql(...)`, the application writes specific SQL and remains responsible for syntax and portability.

### 11.1. Dialects Are Not General SQL Translators

Do not expect Spring to automatically translate:

```sql
SELECT ...
LIMIT 10 OFFSET 20;
```

into SQL Server's pagination syntax, or convert every PostgreSQL function into a MySQL equivalent. The dialect helps the framework generate SQL within its supported abstractions; custom native SQL can still depend on the database engine.

When supporting multiple databases, isolate engine-specific SQL inside dialect-specific repository implementations or query strategies. Keep portable CRUD operations in standard repositories whenever possible.

### 11.2. One Repository and Multiple Dialects

A repository or template is usually built with a mapping context and a dialect tied to the configured `ConnectionFactory`. If a routing `ConnectionFactory` switches between databases with different dialects, do not assume Spring Data swaps dialects per connection on each request.

Simple routing fits best when target databases share compatible dialects, schemas, and data types. If routing between PostgreSQL and MySQL, use separate templates/repositories per dialect or isolated adapters rather than a single repository bound to one dialect for all targets.

## 12. Writing Portable Queries With Named Parameters

Simple queries using common SQL syntax and Spring named parameters are easier to maintain:

```java
databaseClient.sql("""
        SELECT id, email_address
        FROM customer
        WHERE status = :status
        """)
        .bind("status", "ACTIVE")
        .map((row, metadata) -> new CustomerSummary(
                row.get("id", UUID.class),
                row.get("email_address", String.class)))
        .all();
```

Named parameters avoid hard-coding `$1` or `?` in application code. Even so, queries still require valid syntax, table/column names, and compatible types on the target database.

For example, `LIMIT`, `RETURNING`, JSON operators, array operators, upserts, and date/time functions differ across engines. Named parameters do not make those clauses portable.

## 13. Binding NULL Values Properly

The R2DBC SPI does not permit binding Java `null` as a regular value via `.bind(index, null)`. Use the typed null-binding API:

```java
databaseClient.sql("UPDATE customer SET display_name = :name WHERE id = :id")
        .bindNull("name", String.class)
        .bind("id", customerId)
        .fetch()
        .rowsUpdated();
```

The Java class passed to `bindNull` tells the driver which SQL type to bind. With positional parameters, use the `bindNull(index, type)` overload if provided by your API version.

### 13.1. NULL Is Not an Empty String

- SQL `NULL`: absent/unknown value in SQL logic.
- `''`: empty string.
- `'   '`: whitespace string.
- `0`: numeric zero.

`column = NULL` is not the right way to find NULLs. Use `IS NULL`:

```sql
SELECT id
FROM customer
WHERE display_name IS NULL;
```

For optional query filters, you can write:

```sql
WHERE (:name IS NULL OR display_name = :name)
```

Typed null binding and database/driver type inference must be tested. For complex queries, building explicit SQL branches can be cleaner than stuffing every optional condition into one expression.

## 14. Binding Collections in IN Clauses

Some Spring APIs support expanding a collection parameter into multiple bind markers:

```java
databaseClient.sql("SELECT id, display_name FROM customer WHERE id IN (:ids)")
        .bind("ids", List.of(id1, id2, id3))
        .fetch()
        .all();
```

Spring can expand the list into individual markers matching the dialect. This is a feature of the named-parameter expansion layer, not every R2DBC driver accepting a Java `List` as a scalar parameter inside `IN`.

### 14.1. Empty Lists

`IN ()` is neither portable nor valid SQL. When a collection is empty, decide the business semantics in application code:

- If no IDs means no results, return `Flux.empty()` without sending SQL.
- If an empty collection means no filter, run a separate query branch.
- Never omit the `IN` predicate accidentally, as doing so can return the entire table.

Example:

```java
public Flux<Customer> findByIds(Collection<UUID> ids) {
    if (ids.isEmpty()) {
        return Flux.empty();
    }

    return databaseClient.sql(
                    "SELECT id, display_name FROM customer WHERE id IN (:ids)")
            .bind("ids", ids)
            .map(this::mapCustomer)
            .all();
}
```

Check database/driver bind-parameter limits. For very large lists, use batching, temporary tables, table-valued parameters, or engine-appropriate array mechanisms rather than generating thousands of markers in a single query.

## 15. Quoting in String Literals vs. Identifiers

Do not confuse delimiter types:

| Syntax | Common Meaning |
| --- | --- |
| `'text'` | String literal |
| `"column"` | Quoted identifier in PostgreSQL/H2; SQL Server when configured appropriately |
| Backtick-enclosed name | Quoted identifier in MySQL |
| `[column]` | Quoted identifier in SQL Server |
| `:value` | Named parameter in Spring APIs supporting named binding |
| `$1` | Native PostgreSQL positional marker |
| `?` | Positional marker in many drivers, including MySQL |

Example:

```sql
SELECT "order" FROM "purchase_order" WHERE status = 'PENDING';
```

Here `"order"` is an identifier, whereas `'PENDING'` is a string literal.

If you use double quotes for strings on MySQL in default mode, the database may interpret them as identifiers rather than strings. Always use single quotes for SQL string literals.

## 16. Reserved Keywords Change Across Versions

Reserved keywords can change between database releases. A word that was a valid unquoted identifier in an older version can become a keyword in a newer version when new syntax is added.

For instance, `rank`, `groups`, `system`, `window`, `json`, `key`, or `value` can carry special meaning in certain dialects or versions. Check the exact keyword list for your server version.

To minimize risk:

- Use clear domain names like `customer_order`, `user_account`, `group_membership`.
- Avoid overly generic names like `value`, `key`, `user`, `order`, `group`.
- When forced to keep conflict-prone legacy names, quote consistently.
- Run migrations and integration tests against the actual target database version.
- When upgrading servers, review release notes for newly added keywords or parser changes.

## 17. Native Queries and Database Portability

A repository can use query derivation:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, UUID> {

    Flux<Customer> findByStatusOrderByCreatedAtAscIdAsc(String status);
}
```

Query derivation lets Spring Data generate SQL from mapping metadata and the dialect. This is usually easier to port across databases when expressions are supported by Spring Data.

With native queries:

```java
@Query("SELECT * FROM customer WHERE status = :status ORDER BY created_at")
Flux<Customer> findActive(@Param("status") String status);
```

Table/column names, markers, and SQL expressions must fit the dialect. Named parameters are handled by Spring Data, while `SELECT *`, `ORDER BY`, SQL functions, or specialized clauses can remain database-dependent.

### 17.1. Splitting Queries by Dialect When Needed

If PostgreSQL needs `RETURNING` while SQL Server needs `OUTPUT INSERTED...`, do not cram both into a shared native query. You can:

- Keep a common repository interface for portable operations.
- Provide separate custom repository implementations per database.
- Use dialect-specific adapters/strategies to pick verified SQL.
- Maintain separate migrations and integration tests per database.

Never build a homebrew SQL translator using string replacements. Keep differences contained in well-tested persistence adapters.

## 18. Identifier Quoting and SQL Injection

Bind parameters protect **values**. They do not automatically protect identifiers concatenated into SQL.

Dangerous example:

```java
String sql = "SELECT * FROM customer ORDER BY " + request.sortField();
```

If `sortField` contains arbitrary SQL expressions, the query can be altered.

Map input through an allowlist instead:

```java
enum CustomerSort {
    CREATED("created_at"),
    NAME("display_name"),
    EMAIL("email_address");

    private final String column;

    CustomerSort(String column) {
        this.column = column;
    }

    public String column() {
        return column;
    }
}
```

Only use values from the enum/allowlist as SQL identifiers. If choosing sort direction dynamically, use a separate enum for `ASC`/`DESC` rather than concatenating arbitrary strings.

Quoting identifiers does not replace allowlists. A quoted malicious string can still reference an unauthorized identifier. Enforce authorization and allowlists before assembling queries.

## 19. Pagination Differences

Beyond bind markers and identifier quoting, pagination syntax also varies.

PostgreSQL and MySQL commonly support:

```sql
SELECT id, display_name
FROM customer
ORDER BY id
LIMIT :limit OFFSET :offset;
```

SQL Server commonly uses:

```sql
SELECT id, display_name
FROM customer
ORDER BY id
OFFSET @P0 ROWS FETCH NEXT @P1 ROWS ONLY;
```

These are native SQL examples; exact markers depend on the driver. When using `Pageable`, `Sort`, or Spring Data-supported query derivation, the framework/dialect can emit appropriate pagination syntax. With hand-written native queries, choose the syntax of the target database.

Pagination requires a deterministic `ORDER BY`. Without deterministic ordering, pages can duplicate or skip rows when execution plans or data change.

## 20. Data Types Also Affect Binding

Bind markers are only slots; Java values still must convert to SQL types understood by the driver and database.

| Meaning | PostgreSQL | MySQL | SQL Server |
| --- | --- | --- | --- |
| UUID | `UUID` | Usually stored as `BINARY(16)` or `CHAR(36)` per design | `UNIQUEIDENTIFIER` |
| Money | `NUMERIC(p,s)` | `DECIMAL(p,s)` | `DECIMAL(p,s)` |
| Offset date-time | `TIMESTAMPTZ` | Usually `TIMESTAMP`/`DATETIME` with explicit UTC convention | `DATETIMEOFFSET` |
| Boolean | `BOOLEAN` | `BOOLEAN` is an alias for `TINYINT(1)` in many configs | `BIT` |
| JSON | `JSON`/`JSONB` | `JSON` | Often stored in `NVARCHAR` with JSON functions |

This table is directional guidance. Exact mappings depend on drivers and Spring Data converters.

### 20.1. UUID

PostgreSQL has a native UUID type. MySQL typically stores UUIDs as strings or binaries; SQL Server has `UNIQUEIDENTIFIER`. When targeting multiple databases, define storage formats and converters clearly.

### 20.2. Boolean

One driver may encode Java `Boolean` as a native boolean type, while another database represents it as a bit or integer. Use SQL types and converters supported by the driver.

### 20.3. Timestamps

`Instant`, `OffsetDateTime`, and `LocalDateTime` have distinct meanings. Never simply rename SQL column types without defining timezone semantics. When storing absolute instants, standardize on UTC and test round-trips on the target database.

## 21. Dialect and ConnectionFactory Configuration

Spring Data R2DBC needs to know the database type to choose the right dialect. Normally the dialect is detected from `ConnectionFactory`/driver metadata.

If constructing `ConnectionFactory` manually, ensure the corresponding driver is on the runtime classpath and the URL uses the right scheme:

```text
r2dbc:postgresql://localhost:5432/app_db
r2dbc:mysql://localhost:3306/app_db
r2dbc:mssql://localhost:1433/app_db
```

The exact scheme must match the active driver. Never use JDBC URLs like `jdbc:postgresql://...` to configure R2DBC connections.

When multiple `ConnectionFactory` beans exist, wire repositories/templates to their matching factories. When routing across databases with different dialects, remember the dialect is tied to the template/repository configuration; runtime connection routing does not automatically swap dialects inside query generators per target.

## 22. Inspecting Generated Queries and Bind Errors

When encountering syntax or bind errors, identify which layer caused the failure:

1. SQL parser rejects the marker.
2. Marker count and bound value count mismatch.
3. Named parameter name does not match `.bind(...)` or `@Param`.
4. Java type cannot encode into the SQL type.
5. Identifier requires quoting or is misquoted.
6. Table/column name does not exist or has mismatched casing.
7. SQL uses syntax specific to another database.
8. Null parameter was bound without an explicit type.

Typical errors:

| Error | Possible Cause |
| --- | --- |
| Syntax error near `?` | Driver does not accept markers from another database |
| Parameter index out of range | Bind index mismatches marker count |
| No value specified for parameter | Missing bind for an SQL marker |
| Unknown column / invalid column | Wrong identifier or wrong quoting/casing |
| Syntax error near `order` | Identifier matches a reserved keyword |
| Cannot bind null | Used `.bind(name, null)` instead of `.bindNull(...)` |
| Type mismatch | Java type incompatible with SQL type/driver codec |

During development, enable appropriate Spring/driver SQL logging to inspect statements and error details. Never log passwords, tokens, or personal data.

## 23. Testing on Each Target Database Engine

A query running on H2 does not prove it runs properly on PostgreSQL or MySQL. H2 can differ in reserved keywords, quoting, data types, generated keys, and SQL syntax.

If production uses PostgreSQL, run critical integration tests against real PostgreSQL, typically with Testcontainers. If a product supports multiple databases, run dedicated tests for each supported dialect/driver.

Test setup example:

```java
@Testcontainers
@SpringBootTest
class CustomerRepositoryPostgresTest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void configure(DynamicPropertyRegistry registry) {
        registry.add("spring.r2dbc.url", () ->
                "r2dbc:postgresql://" + postgres.getHost() + ":"
                        + postgres.getFirstMappedPort() + "/"
                        + postgres.getDatabaseName());
        registry.add("spring.r2dbc.username", postgres::getUsername);
        registry.add("spring.r2dbc.password", postgres::getPassword);
    }
}
```

This is an illustrative configuration skeleton; test projects require the Testcontainers PostgreSQL and R2DBC PostgreSQL driver dependencies, plus schema initialization prior to tests.

Tests should cover:

- Named parameters translated and bound properly.
- Null parameters using typed `bindNull`.
- Collection parameters in `IN` expanded properly and empty lists handled safely.
- Normal identifiers and quoted identifiers working properly.
- Column names with mixed casing handled per schema.
- Queries avoiding unintended reserved keywords.
- `Sort`, `Pageable`, or native pagination working properly.
- UUID, decimal, boolean, and timestamp round-tripping accurately.
- Migrations creating the expected tables, columns, indexes, and constraints.

## 24. Common Pitfalls When Switching Database Engines

| Symptom | Possible Cause | Fix |
| --- | --- | --- |
| PostgreSQL query works but MySQL fails | Used `$1` native markers or PostgreSQL syntax | Use Spring named parameters or write MySQL-specific query |
| MySQL query uses `?` but SQL Server fails | Native markers differ across drivers | Use `DatabaseClient` named parameters or proper SQL Server markers |
| Table `order` cannot be queried | Reserved keyword | Rename to `purchase_order` or quote per dialect |
| Table `"Customer"` not found | PostgreSQL quoted identifiers are case-sensitive | Match exact casing and quote consistently |
| Backticks fail on PostgreSQL | Backticks are MySQL syntax | Use PostgreSQL double quotes or unquoted names |
| `"name"` becomes wrong identifier on MySQL | Double quotes depend on SQL mode | Use backticks or simple unquoted names |
| Binding table name fails | Parameter markers only bind values | Use allowlists and identifier processing |
| `IN (:ids)` fails on empty list | SQL expansion produces invalid empty list | Handle empty collections before querying |
| H2 test passes but production fails | Different dialect, keywords, types, or SQL syntax | Test against production database via Testcontainers |
| `bind(null)` fails | R2DBC requires a type for nulls | Use `.bindNull(name, type)` |
| Migrating MySQL to PostgreSQL breaks casing | Different identifier folding rules | Standardize physical names and schema migrations |
| Routing between PostgreSQL and MySQL produces bad SQL | One repository/template does not swap dialects per target | Separate templates/repository adapters per dialect |

## 25. Design Rules to Reduce Dialect Coupling

When building Spring Data R2DBC applications intended to run across multiple database engines:

1. Use query derivation or Spring Data APIs for standard CRUD operations.
2. Use `DatabaseClient` or `@Query` named parameters instead of hard-coding native markers where APIs support them.
3. Never bind identifiers; use fixed names, allowlists, and appropriate identifier processing.
4. Name tables and columns in lowercase `snake_case`, avoiding reserved keywords.
5. If forced to use a keyword as an identifier, quote per the target database consistently across migrations, queries, and mappings.
6. Establish clear Java and SQL type conventions for UUID, decimal, timestamp, boolean, and JSON.
7. Handle nulls using typed null-binding APIs.
8. Handle empty collections before constructing `IN` clauses.
9. Isolate engine-specific native queries in dialect-specific custom repositories/adapters.
10. Never treat H2 compatibility modes as proof of full production compatibility.
11. Test against the exact supported R2DBC driver and database versions.
12. When upgrading databases, review reserved keywords, identifier behavior, and driver changes.

## 26. Workflow for Diagnosing Non-Portable Queries

When a query runs on database A but fails on database B, check step by step:

1. Is the SQL generated by a repository or written directly by the application?
2. Are markers Spring named parameters or native driver markers?
3. Which markers and bind types does the active driver accept?
4. Are all parameters bound completely, with the right names/indices and types?
5. Are any null parameters missing `.bindNull(...)`?
6. Do any table or column names collide with reserved keywords?
7. Are identifiers quoted per the active dialect?
8. Does case folding cause physical names to differ from query names?
9. Does the query use engine-specific functions, operators, pagination, or data types?
10. Is a single template/repository shared across multiple distinct dialects?
11. Have tests actually run against the real database and driver?

Categorizing the root cause ensures fixes happen at the right layer: markers belong to binding, quotes belong to identifiers, keywords belong to naming/schema, and native clauses belong to query dialects.

Differences in bind markers, identifier quoting, and reserved keywords are common reasons native SQL fails to port across database engines. Spring Data R2DBC and `DatabaseClient` abstract part of this through dialects and named parameters, but they are not universal SQL translators. Bind parameters for values, choose safe identifiers, quote per target database when required, and test against the real driver/server to keep mappings and queries consistent.
