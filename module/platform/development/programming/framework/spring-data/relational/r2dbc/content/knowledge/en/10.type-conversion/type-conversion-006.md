# Mapping Dates, Times, Time Zones, and Temporal Precision

Date and time values are error-prone when moving between Java, Spring Data R2DBC, and the database. A value may represent a calendar date, a wall-clock time, an absolute instant, or a local time within a time zone. Choosing the wrong Java type or SQL column type can cause the application to store shifted instants, lose time zone information, or compare two values inaccurately.

When designing mappings, clarify three things: what the data represents, what temporal type the database uses to store it, and what precision needs to be preserved. Spring Data R2DBC supports mapping date/time types through its conversion infrastructure, though final conversion still depends on the R2DBC driver and the database management system's capabilities.

## 1. Distinguishing Dates, Local Times, and Absolute Instants

Types in `java.time` do not carry the same meaning:

| Java Type | Meaning | Contains time zone or offset? | Use when |
| --- | --- | --- | --- |
| `LocalDate` | A calendar date | No | Birth dates, invoice dates, holidays |
| `LocalTime` | Wall-clock time of day | No | Opening hours, daily start times |
| `LocalDateTime` | Local date and time | No | Local appointments when the time zone is stored separately |
| `Instant` | A point on the UTC timeline | Stores no offset; represents an absolute instant | Creation, update, or event timestamps |
| `OffsetDateTime` | Date and time with a UTC offset | Has offset | Instants paired with a specific offset |
| `ZonedDateTime` | Date and time with rules of a time zone region | Has `ZoneId` | Local schedules requiring time zone rules |
| `OffsetTime` | Time of day with a UTC offset | Has offset | Specialized cases involving time and offset |

For example:

```java
LocalDate birthday = LocalDate.of(1995, 4, 12);
LocalTime openingTime = LocalTime.of(8, 30);
LocalDateTime appointment = LocalDateTime.of(2026, 11, 15, 9, 0);

Instant createdAt = Instant.now();
OffsetDateTime receivedAt = OffsetDateTime.now(ZoneOffset.UTC);
ZonedDateTime meeting = ZonedDateTime.now(ZoneId.of("Asia/Ho_Chi_Minh"));
```

Do not pick `LocalDateTime` simply because it contains both date and time. This type does not identify an absolute instant because it lacks an offset or time zone. For instance, `2026-11-15T09:00` could be 09:00 in Hanoi, Tokyo, or Paris; each corresponds to a different UTC instant.

## 2. Temporal Types in SQL

SQL has common date and time types:

- `DATE`: calendar date, without time.
- `TIME`: time of day, without date.
- `TIMESTAMP` or `TIMESTAMP WITHOUT TIME ZONE`: date and time without a time zone.
- `TIMESTAMP WITH TIME ZONE`: an instant-like type with time zone/offset semantics defined by the DBMS.

Exact type names and behaviors vary across PostgreSQL, MySQL, SQL Server, Oracle, and other DBMSs. You cannot infer that two similarly named columns always store identical semantics.

PostgreSQL DDL example:

```sql
CREATE TABLE calendar_entry (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_date DATE NOT NULL,
    starts_at TIME(6) NOT NULL,
    local_start TIMESTAMP(6) NOT NULL,
    occurred_at TIMESTAMP(6) WITH TIME ZONE NOT NULL
);
```

In this example:

- `event_date` stores a date.
- `starts_at` stores a time of day.
- `local_start` stores a local date and time without an attached time zone.
- `occurred_at` stores a timestamp with absolute instant semantics.

PostgreSQL commonly uses `TIMESTAMP WITH TIME ZONE` or `TIMESTAMPTZ`. Both represent the same data type. PostgreSQL normalizes the instant when storing and formats it according to the session time zone; it does not preserve the original time zone region name supplied on input.

## 3. Choosing Java Types Matching SQL Types

A common mapping:

| SQL | Common Java Type | Notes |
| --- | --- | --- |
| `DATE` | `LocalDate` | No time component |
| `TIME` | `LocalTime` | Does not identify a date or time zone |
| `TIMESTAMP WITHOUT TIME ZONE` | `LocalDateTime` | Local date and time only |
| `TIMESTAMP WITH TIME ZONE` | `OffsetDateTime` or `Instant` via suitable conversion | Stores an absolute instant |

This is a common mapping guide, not an identical guarantee across all drivers. A driver may support some Java types directly and require conversion for others. Consult the documentation of the driver in use and test against the actual target database.

For event data such as `createdAt`, `paidAt`, `receivedAt`, or `processedAt`, prefer absolute instant semantics. In the domain model, `Instant` usually expresses intent well because it does not depend on the application server's time zone. If the driver works more directly with `OffsetDateTime`, you can use UTC offset at the persistence boundary and convert to `Instant` in the domain.

For an appointment at 09:00 in a specific city's local time, `LocalDateTime` should be paired with `ZoneId` if the schedule must obey time zone rules over time. A fixed offset like `+07:00` does not fully substitute for a region such as `Asia/Ho_Chi_Minh` or `Europe/Paris`, because regional rules can change by law.

## 4. Entity Mapping in Spring Data R2DBC

Spring Data Relational uses mapping metadata to link entity properties to database columns. For example:

```java
import java.time.Instant;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("calendar_entry")
public record CalendarEntry(
        @Id Long id,
        @Column("event_date") LocalDate eventDate,
        @Column("starts_at") LocalTime startsAt,
        @Column("local_start") LocalDateTime localStart,
        @Column("occurred_at") Instant occurredAt
) {}
```

The entity above expresses each property's meaning, but whether `Instant` maps directly to a `TIMESTAMP WITH TIME ZONE` column depends on the driver and configured Spring Data conversions. If the active driver does not support that type directly, use a driver-supported type like `OffsetDateTime` in the persistence model and convert explicitly.

Example using `OffsetDateTime` at the persistence layer:

```java
@Table("calendar_entry")
public record CalendarEntryRow(
        @Id Long id,
        @Column("event_date") LocalDate eventDate,
        @Column("starts_at") LocalTime startsAt,
        @Column("local_start") LocalDateTime localStart,
        @Column("occurred_at") OffsetDateTime occurredAt
) {}
```

When writing an `Instant`, you can convert it to a UTC offset:

```java
OffsetDateTime databaseValue =
        OffsetDateTime.ofInstant(instant, ZoneOffset.UTC);
```

When reading:

```java
Instant domainValue = row.occurredAt().toInstant();
```

Using UTC at the persistence boundary ensures values are interpreted consistently, provided the driver and database have matching mappings.

## 5. LocalDateTime Is Not an Instant

`LocalDateTime` contains only date and time. It does not tell you where an event happened and cannot determine a UTC instant without a time zone or offset.

For example:

```java
LocalDateTime local = LocalDateTime.of(2026, 11, 15, 9, 0);

Instant inHoChiMinh = local
        .atZone(ZoneId.of("Asia/Ho_Chi_Minh"))
        .toInstant();

Instant inTokyo = local
        .atZone(ZoneId.of("Asia/Tokyo"))
        .toInstant();
```

The two `Instant` values differ even though both share the same local date and time `09:00`. Therefore, if the database stores `LocalDateTime` in a column without a time zone, the application must agree on the column's meaning: which region's local time, or an internal convention storing UTC in a non-time-zone timestamp column.

If a `TIMESTAMP WITHOUT TIME ZONE` column actually stores UTC by internal convention, document that convention clearly in property names, schema documentation, and conversion code. Do not rely on the host machine's default time zone to interpret data.

## 6. OffsetDateTime, ZonedDateTime, and ZoneId

Offset and time zone are two different concepts:

- Offset, such as `+07:00`, is a specific offset relative to UTC at a point in time.
- ZoneId, such as `Asia/Ho_Chi_Minh` or `Europe/Paris`, is a region identifier with historical time rules that can change due to legislative decisions.

`OffsetDateTime` holds an offset but not regional rules. `ZonedDateTime` holds a `ZoneId` and the offset applicable at that instant.

With databases like PostgreSQL, a `TIMESTAMP WITH TIME ZONE` column stores the instant and does not retain the original region name such as `Europe/Paris`. If business logic needs the user's chosen time zone region to display future schedules, store `ZoneId` separately:

```sql
CREATE TABLE appointment (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    local_start TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    zone_id VARCHAR(64) NOT NULL
);
```

Entity:

```java
@Table("appointment")
public record Appointment(
        @Id Long id,
        @Column("local_start") LocalDateTime localStart,
        @Column("zone_id") String zoneId
) {}
```

When reading the schedule, the application combines the two values:

```java
ZonedDateTime scheduled =
        appointment.localStart().atZone(ZoneId.of(appointment.zoneId()));
```

This storage approach preserves the intent of "09:00 in this region" rather than only saving an offset that applied at creation time. It is useful for recurring meetings, opening hours, or future events affected by regional DST rules.

If business logic needs both the confirmed absolute instant and the user's chosen region, you can store both `Instant` and `ZoneId`. One column then represents the actual instant, while the other retains geographic context for display.

## 7. Daylight Saving Time: Non-Existent or Repeated Hours

In regions observing daylight saving time (DST), local clocks can:

- Spring forward over an hour interval. Certain `LocalDateTime` values do not exist in that region.
- Fall back over an hour interval. Certain `LocalDateTime` values occur twice and correspond to two distinct instants.

Consequently, converting a `LocalDateTime` into an `Instant` requires a `ZoneId` and a policy for special cases.

Java provides `ZoneRules` to check:

```java
LocalDateTime local = LocalDateTime.of(2026, 10, 25, 2, 30);
ZoneId zone = ZoneId.of("Europe/Paris");

List<ZoneOffset> validOffsets =
        zone.getRules().getValidOffsets(local);

if (validOffsets.isEmpty()) {
    // Local time falls within a skipped interval (DST gap).
} else if (validOffsets.size() == 1) {
    // Normal local instant.
} else {
    // Local time is repeated; choose an offset per business rules.
}
```

`LocalDateTime.atZone(zone)` uses Java's default gap/overlap resolution policy. In scheduling, financial, or recurring calendar systems, do not let default behavior silently decide an important instant. Explicitly define how to handle them: reject non-existent times, shift to the next valid time, or ask the user to choose one of the two offsets during an overlap.

For events that have already occurred, storing `Instant` yields a unique point in time. For future schedules, storing `LocalDateTime` with `ZoneId` allows reapplying zone rules when needed; depending on business requirements, you may also store the computed instant at confirmation time.

## 8. Temporal Precision: Nanoseconds and Fractional Seconds

Java Time supports precision down to nanoseconds (9 fractional second digits). Databases may support lower precision. For example, PostgreSQL supports precision from 0 to 6 fractional digits for timestamp/time types, corresponding to microseconds.

Java example:

```java
Instant value = Instant.parse("2026-11-15T02:30:45.123456789Z");
```

If stored into a column with only microsecond precision, the nanosecond portion cannot be preserved completely. The result may be rounded or truncated depending on the database, driver, and conversion path. Do not assume reading back will always equal the original Java value down to all 9 digits.

DDL example:

```sql
CREATE TABLE event_log (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    occurred_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    local_time TIMESTAMP(3) WITHOUT TIME ZONE
);
```

- `TIMESTAMP(6)` stores fractional seconds to microseconds.
- `TIMESTAMP(3)` stores to milliseconds.
- Omitting precision uses the database's default precision, which is not necessarily identical across DBMSs.

Column precision should reflect business needs. Regular logging systems may not require nanoseconds; telemetry or event synchronization systems may need higher precision if supported by the database and driver.

## 9. Normalizing Precision Before Comparison

If an application creates timestamps with nanoseconds while the database only stores microseconds, comparing values before and after reading can fail because the precision has changed.

You can normalize the value in Java before saving so it matches the schema:

```java
Instant normalized =
        instant.truncatedTo(ChronoUnit.MICROS);
```

Or with `LocalDateTime`:

```java
LocalDateTime normalized =
        localDateTime.truncatedTo(ChronoUnit.MICROS);
```

This example truncates to microseconds. If the database or driver rounds instead of truncating, apply the same policy in the application or compare at the precision guaranteed by the schema. Verify actual behavior with integration tests on your target driver/database.

When testing, you can compare normalized values or check within the column's precision rather than always requiring exact nanosecond equality.

## 10. Binding and Reading Dates and Times with DatabaseClient

`DatabaseClient` lets you bind Java values to SQL parameters and map returned columns. Example with PostgreSQL:

```java
public Mono<Instant> saveEventTime(Instant occurredAt) {
    OffsetDateTime utcValue =
            OffsetDateTime.ofInstant(occurredAt, ZoneOffset.UTC);

    return databaseClient.sql("""
            INSERT INTO event_log (occurred_at)
            VALUES (:occurredAt)
            RETURNING occurred_at
            """)
            .bind("occurredAt", utcValue)
            .map((row, metadata) ->
                    row.get("occurred_at", OffsetDateTime.class).toInstant()
            )
            .one();
}
```

This example converts `Instant` to UTC `OffsetDateTime` before binding and converts the read result back to `Instant`. Column type, driver, and mapping API must be compatible. `RETURNING` is PostgreSQL syntax; on other databases, retrieving post-insert values may differ.

With `DATE` and `TIME`, mapping is simpler:

```java
public Mono<LocalDate> findEventDate(Long id) {
    return databaseClient.sql("""
            SELECT event_date
            FROM calendar_entry
            WHERE id = :id
            """)
            .bind("id", id)
            .map((row, metadata) -> row.get("event_date", LocalDate.class))
            .one();
}
```

When a column is nullable, `row.get(...)` can return null. Design DTOs and mapping logic to handle null values; do not invoke methods on potentially null values without checking first.

## 11. Spring Data Conversion and Driver Codecs

There are two conversion layers to distinguish:

1. **Driver codec / R2DBC SPI mapping:** translates database wire-protocol data into Java types and vice versa.
2. **Spring Data conversion:** translates types between values supplied by the driver and entity or projection properties.

Spring Data R2DBC uses `R2dbcCustomConversions` to manage custom converters. If the domain model uses a custom type such as `BusinessDateTime`, you can write reading/writing converters to translate between a driver-supported type and the domain type.

Illustrative writing converter:

```java
@WritingConverter
public class InstantToOffsetDateTimeConverter
        implements Converter<Instant, OffsetDateTime> {

    @Override
    public OffsetDateTime convert(Instant source) {
        return OffsetDateTime.ofInstant(source, ZoneOffset.UTC);
    }
}
```

Reading converter:

```java
@ReadingConverter
public class OffsetDateTimeToInstantConverter
        implements Converter<OffsetDateTime, Instant> {

    @Override
    public Instant convert(OffsetDateTime source) {
        return source.toInstant();
    }
}
```

Converters must be registered in Spring Data R2DBC configuration matching your Spring Boot / Spring Data version. They do not replace driver codecs: the driver must still be able to read and write the underlying type used in the converter, `OffsetDateTime` in this example.

Do not register broad converters for all temporal types when only one column needs special rules. Global conversions can alter how other entities across the application are mapped. Choose converters with clear source/target types and test both reading and writing.

## 12. Time Zones of the JVM, Database Session, and Application

Three environments can have different default time zones:

- The JVM running the application.
- The database connection session.
- The user or tenant viewing the data.

If the application relies on the JVM's default time zone, results can change when deployed to containers or servers configured with different time zones. If the database session has a different time zone, timestamp display formatting may also shift accordingly.

For absolute events, use `Instant` in the domain and store it in a column type with appropriate instant semantics. At the driver boundary, use a type supported by the driver, often representable via UTC `OffsetDateTime`.

For local times, store `LocalDateTime` and `ZoneId` separately when the time zone region is part of the business domain. Do not treat the server's default time zone as a substitute for the user's selected region.

When displaying, convert from `Instant` to the desired time zone:

```java
ZonedDateTime displayTime =
        instant.atZone(ZoneId.of("Asia/Ho_Chi_Minh"));
```

Display conversion does not alter the stored instant.

## 13. Testing Date and Time Mappings

Testing should cover temporal types and precision boundaries:

- `LocalDate`: start/end of month, leap years.
- `LocalTime`: values with fractional seconds and values near midnight.
- `LocalDateTime`: no implicit time zone attached on read/write.
- `Instant` or `OffsetDateTime`: instants before and after UTC midnight, positive/negative offsets.
- DST: skipped hours and repeated hours in DST regions.
- Precision: values with 9 fractional digits written into precision 3 or 6 columns.
- Nullability: nullable and non-null temporal columns.

Round-trip test example:

```java
Instant original = Instant.parse("2026-11-15T02:30:45.123456Z");

StepVerifier.create(eventRepository.save(new Event(null, original)))
        .assertNext(saved -> {
            assertNotNull(saved.id());
            assertEquals(original, saved.occurredAt());
        })
        .verifyComplete();
```

This example assumes the column has microsecond precision and converters/drivers preserve the normalized value. If the input contains nanoseconds exceeding column precision, normalize before comparing.

Run integration tests against the same database and driver as the deployment environment. H2 or mocks can be useful for some tests, but they cannot replace testing time zone behavior, precision, and codecs of real PostgreSQL/MySQL/SQL Server instances.

## 14. Common Mistakes

1. **Using `LocalDateTime` for absolute events.** Without a time zone, it cannot identify a unique instant.
2. **Thinking `TIMESTAMP WITH TIME ZONE` preserves region names.** Many databases, including PostgreSQL, store the instant without keeping the original `ZoneId`.
3. **Using an offset instead of a time zone region.** `+01:00` does not carry DST and historical rules like `Europe/Paris`.
4. **Relying on the JVM's default time zone.** Behavior can vary across local, container, and production environments.
5. **Assuming Java nanoseconds are always preserved in the database.** Column precision may only reach milliseconds or microseconds.
6. **Comparing round-trips at higher precision than the schema.** Normalize or compare at actual supported precision.
7. **Assuming all R2DBC drivers support the same Java types.** Check codecs and documentation for the specific driver.
8. **Ignoring DST gaps/overlaps.** Local schedules may not exist or may occur twice.
9. **Using Spring converters to compensate for a driver that does not support the underlying type.** Converters only work when the driver can read/write the underlying type they require.
10. **Storing local times without the region when business logic requires the region.** Future schedules may be misinterpreted after time zone rule changes.

## Quick Selection Rules

- Use `LocalDate` for calendar dates, `LocalTime` for times of day.
- Use `Instant` for absolute instants in the domain.
- Use `OffsetDateTime` when carrying an offset across the persistence or driver boundary.
- Use `LocalDateTime` paired with `ZoneId` for local schedules that must retain region semantics.
- Use `TIMESTAMP WITH TIME ZONE` columns for absolute instants if supported by the database and driver mapping.
- Use `TIMESTAMP WITHOUT TIME ZONE` for local times with explicit conventions.
- Store `ZoneId` separately if you must preserve a region like `Europe/Paris`, not just an offset.
- Align precision across Java, SQL columns, and round-trip tests.
- Verify driver codecs and Spring Data converters before committing to domain types.

Accurate date and time mapping starts with business meaning rather than data type names. Distinguish dates, local times, and absolute instants; choose SQL columns with matching semantics; store time zone regions separately when needed; and align precision across Java, drivers, and databases. When these rules are clearly reflected in entities, conversions, and integration tests, temporal data is far less likely to drift or lose information across environments.
