# Managing Schema Versions with Flyway or Liquibase

In a Spring Data R2DBC application, Java entities and database table structures must evolve in sync. When adding columns, changing data types, creating indexes, or adding new tables, editing Java classes alone is not enough: the running database still holds the old schema. Schema version management (database schema migration) solves this through ordered, trackable changes that are applied automatically during deployment.

Flyway and Liquibase are two popular tools for managing migrations. Both record the history of applied changes, detect schema mismatches, and help development, test, staging, and production environments advance through the same sequence of versions.

One important point to understand in an R2DBC project: Flyway and Liquibase typically execute migrations over JDBC. That does not force business data access to switch to JDBC. The application can continue using R2DBC for repositories and DatabaseClient while using a separate JDBC connection for the migration tool to run DDL/DML at startup or in a deployment pipeline.

## 1. Why Version the Schema?

Suppose the initial Customer entity has fields id and name. In a later version, the application needs to store email as well:

~~~java
@Table("customer")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
~~~

If the production database does not yet have the email column, queries generated by Spring Data R2DBC can fail. Conversely, if the database already has the new column while the old application is still running, the old application may continue working or fail depending on how the schema was changed.

Migrations turn schema changes into versioned artifacts:

1. Create a migration describing the change.
2. Commit the migration to source control alongside the code.
3. The tool determines which migrations have not yet run.
4. Apply migrations in order.
5. Record the version and outcome in the database.
6. Test the application against the migrated schema.

As a result, a fresh database can be built from scratch using the full migration history, while an existing database only needs to apply pending changes.

## 2. Schema Migration vs. Entity Changes

Entities describe how the application maps data; migrations describe how the database structure changes. The two parts must stay consistent, yet they have distinct responsibilities.

| Component | Responsibility |
| --- | --- |
| Entity / record | Describes Java properties and table/column mapping |
| Repository | Queries and saves entities over R2DBC |
| DatabaseClient | Executes custom SQL in the application |
| Flyway / Liquibase | Tracks and applies schema changes |
| Migration SQL/changelog | Defines concrete database changes |

Example of adding a property:

~~~java
@Column("email")
String email
~~~

The corresponding migration can be:

~~~sql
ALTER TABLE customer
ADD COLUMN email VARCHAR(320);
~~~

Adding only the Java property without adding the column can cause read/write errors. Adding only the column without updating the mapping leaves the column unused. Therefore, a schema change usually includes the migration, entity/query updates, and compatibility testing.

## 3. How Do Flyway and Liquibase Work?

Both tools share the same goal, though they describe changes differently:

| Criterion | Flyway | Liquibase |
| --- | --- | --- |
| Describing migrations | Usually versioned or repeatable SQL; also supports Java migrations | XML, YAML, JSON, or Liquibase-formatted SQL changelogs |
| History | Flyway's schema history table | DATABASECHANGELOG and DATABASECHANGELOGLOCK tables |
| Change identification | Version and checksum | ChangeSet with id, author, and checksum |
| Rollback | Depends on migration type, edition, and database support; usually favors forward-only migrations | Rollback can be declared per changeSet; automatic generation depends on change type |
| Best suited for | Straightforward migration workflows, clear SQL, linear versioning | Structured changelogs, preconditions, contexts, labels, and explicit rollbacks |

There is no need to use both Flyway and Liquibase simultaneously for the same schema. Pick one tool as the source of truth for migration history to avoid two systems modifying the database without understanding each other's history.

## 4. The Role of JDBC in a Spring Data R2DBC Project

Spring Data R2DBC uses an R2DBC driver for reactive database access. In common Spring Boot setups, Flyway and Liquibase use JDBC to execute migrations.

An application can hold both connection configurations:

~~~yaml
spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
    username: app_user
    password: app_password

  flyway:
    url: jdbc:postgresql://localhost:5432/shop
    user: migration_user
    password: migration_password
    locations: classpath:db/migration
~~~

The example above illustrates two different protocols pointing to the same database:

- R2DBC URL is used for repositories and DatabaseClient.
- JDBC URL is used exclusively for Flyway.

For this configuration to work, the runtime needs both the R2DBC driver and the corresponding JDBC driver. Newer Flyway versions may require an additional database-specific module, such as the PostgreSQL module, according to the documentation for that Flyway version. Liquibase also requires a JDBC driver to connect to the database in standard setups.

Using JDBC during the migration phase does not make business queries blocking JDBC. Migrations typically run at startup or during a deployment stage before the application serves requests.

## 5. Configuring Flyway Dependencies with PostgreSQL

Gradle Kotlin DSL example:

~~~kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-r2dbc")
    runtimeOnly("org.postgresql:r2dbc-postgresql")

    implementation("org.flywaydb:flyway-core")
    runtimeOnly("org.postgresql:postgresql")
    // For Flyway versions with split database modules:
    runtimeOnly("org.flywaydb:flyway-database-postgresql")
}
~~~

This example illustrates dependency groups rather than fixed versions. Let Spring Boot dependency management handle compatible versions, and verify the Flyway guide for the selected version. Do not add a database module if your Flyway version already bundles that support.

With Maven, declare the equivalent dependencies in pom.xml and let the Spring Boot BOM manage versions where appropriate.

Do not pick Flyway, JDBC driver, and Spring Boot versions independently without checking compatibility. A newer Flyway release may split database support into a separate module or change Java version requirements.

## 6. Configuring Flyway in Spring Boot

Flyway can be configured in application.yml:

~~~yaml
spring:
  flyway:
    enabled: true
    url: jdbc:postgresql://localhost:5432/shop
    user: migration_user
    password: migration_password
    locations:
      - classpath:db/migration
    validate-on-migrate: true
~~~

Do not commit real passwords to source control. In deployment environments, retrieve connection credentials from environment variables, a secret manager, or the platform's secure configuration mechanism.

Common properties:

| Property | Meaning |
| --- | --- |
| enabled | Enables/disables Flyway auto migration |
| url | JDBC URL used for migration |
| user / password | Migration account credentials |
| locations | Where migrations are stored |
| schemas | Database schemas managed by Flyway |
| default-schema | Default schema |
| baseline-on-migrate | Allows baselining an existing database without a history table |
| validate-on-migrate | Verifies applied migrations still match their checksums |
| clean-disabled | Prevents clean from wiping the schema; usually keep enabled in critical environments |

Exact property names and defaults depend on the Spring Boot/Flyway version. Check configuration metadata and documentation for your project's versions.

## 7. Flyway Migration Directory Structure

By default, Flyway usually looks for migrations in:

~~~text
src/main/resources/
└── db/
    └── migration/
        ├── V1__create_customer.sql
        ├── V2__create_product.sql
        ├── V3__add_customer_email.sql
        └── R__refresh_reporting_view.sql
~~~

Versioned migration filenames have the form:

~~~text
V<version>__<description>.sql
~~~

Examples:

- V1__create_customer.sql
- V2__add_customer_email.sql
- V2_1__add_customer_status.sql

Two underscores separate the version and description. Versions must follow Flyway's comparison rules; do not use two files with the same version.

Repeatable migrations use the R__ prefix and re-apply whenever their content checksum changes, which is typically suitable for views, functions, or procedures that need updating to a new definition. Do not use repeatable migrations to replace standard versioned schema change history.

## 8. Writing the First Versioned Migration

File V1__create_customer.sql:

~~~sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
~~~

This migration creates the customer table with:

- A database-generated ID.
- A non-null name.
- A creation timestamp with database timezone semantics.

A migration should describe a purposeful change and remain small enough for reviewers to understand. If multiple tables with foreign key relationships need to be created, they can be placed in the same migration when they form an indivisible logical change; otherwise, split them into separate versions.

## 9. Adding a Column in a Subsequent Migration

When email is needed:

~~~sql
ALTER TABLE customer
ADD COLUMN email VARCHAR(320);
~~~

Save it as V2__add_customer_email.sql. If migration V1 has already run in any environment, do not edit V1 to add email. Create V2 instead.

Flyway stores version, description, checksum, status, and execution info in the schema history table, typically flyway_schema_history. When running migrate, Flyway compares migrations in the artifact against database history and applies unrun versions in order.

## 10. Do Not Modify Applied Versioned Migrations

Once a versioned migration has run in a shared environment, treat that file as immutable:

- Do not edit V1 to fix an error.
- Do not rename or change a released version.
- Create a new V2/V3 migration to fix or extend the schema.
- Keep released migrations in source control.

Reason: the database already stores the checksum of the old migration. If the file is edited, Flyway may report a checksum mismatch during validate/migrate. If one environment ran the old file and another runs the new file, schema history becomes inconsistent.

The repair command can adjust history metadata in certain cases, but it is not a tool to legitimize arbitrarily editing applied migrations. Only use repair when you understand the exact database state and follow a controlled recovery procedure.

## 11. Repeatable Migrations in Flyway

Repeatable migrations use filenames shaped like R__description.sql:

~~~sql
CREATE OR REPLACE VIEW active_customer AS
SELECT id, name, email
FROM customer
WHERE status = 'ACTIVE';
~~~

Flyway compares the repeatable migration's checksum against history. When the content changes, the migration re-runs after pending versioned migrations according to Flyway's rules.

Typical suitable use cases:

- Creating or replacing views.
- Defining functions/procedures.
- Database objects that can be recreated from their full definition.

Ensure repeatable scripts can safely re-run in the target database dialect. Do not use them to add columns or modify data incrementally without an explicit repeatability strategy.

## 12. Baselining an Existing Database

If a database already has a schema and data before adopting Flyway, you cannot always apply V1 to recreate all tables. You must determine which schema version the current database corresponds to.

Flyway baseline records a historical marker so migrations with versions less than or equal to that marker are considered already covered. You can configure a baseline version and baseline description, or run the baseline command via Flyway CLI/API.

The process should include:

1. Back up the database.
2. Compare the actual schema against the schema described by historical migrations.
3. Choose an appropriate baseline version.
4. Run baseline against the exact target database.
5. Run migrate to apply migrations after the baseline.
6. Verify the schema and the application.

The baseline-on-migrate property can be convenient for databases lacking a history table, but enabling it carelessly can mislabel an incorrect schema as already at the baseline. Do not use baseline to skip comparing the current schema.

## 13. Configuring Liquibase in Spring Boot

Liquibase uses a changelog as the source describing changes. With standard JDBC configuration:

~~~yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:/db/changelog/db.changelog-master.yaml
    url: jdbc:postgresql://localhost:5432/shop
    user: migration_user
    password: migration_password
~~~

Spring Boot can auto-configure Liquibase when the dependency and an appropriate JDBC datasource are present. In an application configured only for R2DBC, provide a JDBC URL/driver or dedicated migration datasource according to your Boot version's configuration.

Common properties:

| Property | Meaning |
| --- | --- |
| enabled | Enables/disables Liquibase |
| change-log | Path to the root changelog |
| url | JDBC URL for migration |
| user / password | Migration account credentials |
| default-schema | Default schema |
| contexts | Filter changeSets by context |
| labels | Filter changeSets by label |
| drop-first | Drops the schema before running; very dangerous outside test environments |

Do not enable drop-first in production. As with Flyway, manage authentication credentials via secrets/environment variables instead of storing real passwords in the repository.

## 14. Liquibase Changelog Structure

A common layout:

~~~text
src/main/resources/
└── db/
    └── changelog/
        ├── db.changelog-master.yaml
        └── changes/
            ├── 001-create-customer.yaml
            ├── 002-add-customer-email.yaml
            └── 003-create-product.yaml
~~~

The master changelog links the change files:

~~~yaml
databaseChangeLog:
  - include:
      file: changes/001-create-customer.yaml
      relativeToChangelogFile: true
  - include:
      file: changes/002-add-customer-email.yaml
      relativeToChangelogFile: true
  - include:
      file: changes/003-create-product.yaml
      relativeToChangelogFile: true
~~~

Liquibase also supports includeAll to load files in a directory. When using includeAll, control file ordering and naming conventions carefully so application order does not change unexpectedly.

## 15. ChangeSet as Liquibase's Unit of Change

Each changeSet has an identifier consisting of id, author, and changelog path. Example:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customer
      author: team
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: name
                  type: VARCHAR(200)
                  constraints:
                    nullable: false
              - column:
                  name: created_at
                  type: TIMESTAMP WITH TIME ZONE
                  constraints:
                    nullable: false
~~~

Liquibase records executed changeSets in DATABASECHANGELOG along with checksums and execution info. DATABASECHANGELOGLOCK coordinates ensuring only one Liquibase process modifies the schema at a time.

Once a changeSet has run, do not edit its contents. If the schema needs changes, create a new changeSet. Editing an old changeSet can cause checksum validation errors or leave environments with divergent histories.

## 16. Adding a Column with Liquibase

Next changeSet:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 002-add-customer-email
      author: team
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: email
                  type: VARCHAR(320)
~~~

Rollback can be declared:

~~~yaml
      rollback:
        - dropColumn:
            tableName: customer
            columnName: email
~~~

Rollback should only be declared when the reverse operation is genuinely safe. If the email column already holds data, dropColumn will lose that data. A technical rollback does not equal a safe business rollback.

For destructive or irreversible changes, prepare backups, recovery plans, or forward migrations instead of relying on automatic rollback.

## 17. SQL Changelogs in Liquibase

If the development team prefers SQL, Liquibase supports formatted SQL changelogs:

~~~sql
--liquibase formatted sql

--changeset team:001-create-customer
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

--rollback DROP TABLE customer;
~~~

The top of the file declares formatted SQL; each changeSet specifies id and author. Rollback can be declared using a special comment. SQL syntax and rollback support depend on the database.

Do not confuse Liquibase's SQL changelog with Flyway's SQL migrations. Flyway usually determines versions from filenames; Liquibase identifies changeSets from metadata inside the changelog.

## 18. Liquibase Preconditions, Contexts, and Labels

Preconditions allow checking database state before applying a changeSet:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 004-add-status
      author: team
      preConditions:
        - onFail: HALT
        - tableExists:
            tableName: customer
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: status
                  type: VARCHAR(30)
~~~

Preconditions are helpful when a migration depends on an existing object. Choose onFail/onError deliberately: HALT stops migration when the condition is unmet; MARK_RAN or CONTINUE have different semantics and can hide an invalid schema if used carelessly.

Contexts and labels can filter changeSets by environment or purpose, such as reference data for tests. Do not use contexts to make the production schema diverge unintentionally. Clearly define which changeSets are mandatory in every environment.

## 19. Choosing Flyway or Liquibase?

Choose based on your team's workflow and needs:

**Flyway fits well when:**

- The team wants to write SQL directly and control database statements.
- Schema history follows a straightforward linear version sequence.
- You want a simple workflow: add a new V file, run migrate.
- Repeatable migrations are useful for views or procedures.

**Liquibase fits well when:**

- The team wants to describe schemas via structured changelogs.
- You need preconditions, contexts, labels, or multi-file includes.
- You want to declare rollbacks for changeSets where feasible.
- You need multiple changelog formats and change inspection/diff capabilities.

Neither tool makes a migration safe on its own if a script is buggy or incompatible with production data. Reviewing SQL, testing on the same database type, and deployment planning remain essential.

## 20. Managing Migration Ordering and History

Migrations must have a deterministic order. Once a versioned migration has run, add a new version rather than inserting a file with an older version into the middle of history.

Flyway example:

~~~text
V1__create_customer.sql
V2__add_customer_email.sql
V3__create_order.sql
V4__add_order_status.sql
~~~

Liquibase example:

~~~text
001-create-customer
002-add-customer-email
003-create-order
004-add-order-status
~~~

Do not rename or delete migrations already applied in shared environments. If multiple feature branches create migrations concurrently, reconcile versions before release and verify there are no duplicate versions or unclear ordering dependencies.

## 21. Migration Transactions and DDL Differences by Database

Some databases support transactional DDL for many statement types; some DDL statements auto-commit or cannot roll back like DML. Flyway and Liquibase may adjust transaction behavior depending on the database and change type.

Do not assume a multi-statement migration is always atomic across every database engine. If the third step fails after the first two steps altered the schema, the database may be left in a partial state depending on the dialect.

Make sure to:

- Check database documentation on transactional DDL.
- Break migrations into small, observable steps.
- Test migrations from the prior schema on a real database.
- Prepare backups and recovery plans for risky changes.
- Inspect migration history state after a failure before retrying.

## 22. Expand-and-Contract for Zero-Downtime Deployments

Schema changes can break an older running application. For instance, renaming column name to full_name and dropping name immediately will cause old application instances still querying name to fail.

The expand-and-contract strategy splits changes across multiple deployments:

~~~mermaid
flowchart TD
    A[Current state: only name exists]
    B[Expand: add nullable full_name]
    C[New app reads/writes both compatibly]
    D[Backfill data from name to full_name]
    E[Switch app to full_name]
    F[Contract: drop name in a later release]
    A --> B --> C --> D --> E --> F
~~~

A typical sequence:

1. Add the new column in a way compatible with the old application.
2. Deploy code capable of reading/writing both old and new structures.
3. Backfill old data to the new column in batches.
4. Switch all instances to use the new column.
5. Verify no code still reads/writes the old column.
6. In a later release, drop the old column.

This strategy is especially important in rolling deployments where multiple application versions run concurrently. Migrations should not break the old application before the new version is ready.

## 23. Changing NOT NULL Columns and Existing Data

Adding a NOT NULL column to a table with existing data can fail if old rows have no value or may force an expensive database operation.

A safer approach:

1. Add a nullable column.
2. Deploy the application writing values for new records.
3. Backfill old records in batches.
4. Verify no NULL values remain.
5. Add the NOT NULL constraint in a separate migration.

Example:

~~~sql
ALTER TABLE customer
ADD COLUMN status VARCHAR(30);
~~~

Backfill:

~~~sql
UPDATE customer
SET status = 'ACTIVE'
WHERE status IS NULL;
~~~

After confirming the data:

~~~sql
ALTER TABLE customer
ALTER COLUMN status SET NOT NULL;
~~~

Column alteration syntax varies by database. On large tables, backfilling in a single UPDATE can create long transactions, locks, and heavy WAL/transaction log volume; consider batch processing and monitoring load.

## 24. Data Migrations

Migrations do not just create tables or columns. Sometimes data needs to be transformed:

- Normalizing statuses from legacy codes to new codes.
- Splitting one field into multiple columns.
- Merging data from an old table into a new table.
- Populating default values for historical records.

Example:

~~~sql
UPDATE customer
SET status = CASE
    WHEN enabled = TRUE THEN 'ACTIVE'
    ELSE 'INACTIVE'
END
WHERE status IS NULL;
~~~

For large tables, it is not necessary to run the entire data migration during a single startup. You can deploy a separate batch job that records checkpoints and can resume after errors. The schema must stay in a compatible state throughout the backfill.

Data migrations need verification of before/after row counts, transformation rules, invalid values, and re-run safety. Do not put environment-dependent business data into schema migrations when it can be loaded via a controlled separate seed step.

## 25. Database Privileges for Migrations and the Application

The migration account usually needs DDL privileges such as CREATE, ALTER, DROP, or schema modification permissions. The R2DBC application's runtime account typically only needs minimal DML privileges for business operations.

You can separate:

- Migration user: permitted to modify schemas and manage the migration history table.
- Application user: permitted to SELECT/INSERT/UPDATE/DELETE on required tables.

Separating privileges limits damage if the runtime application is compromised or has bugs. Do not run production applications with an owner/superuser account just so Flyway or Liquibase can create tables.

Migration accounts must be managed via secrets and granted only necessary privileges. If migrations run in a separate pipeline, credentials may exist only in the migration stage rather than being injected into every application pod.

## 26. Running Migrations at Startup or in CI/CD?

There are two common deployment patterns:

**Migrations at application startup**

- Spring Boot runs Flyway/Liquibase before the application context becomes ready.
- Suits small systems or single-instance environments.
- Multiple replicas may start together and all attempt to migrate; tools have history locking, but deployments still require control.
- A slow migration can delay application readiness.

**Migrations in a deployment pipeline or dedicated job**

- The pipeline runs migrations once before rolling out the application.
- Makes separating migration privileges from runtime easy.
- Allows verifying status and approving migrations before opening traffic.
- Must ensure the application only rolls out when migrations succeed.

In production with multiple replicas, a separate migration job usually provides clearer control over deployment ordering. Either way, the migration tool still relies on locks to prevent concurrent schema modifications.

Do not run manual migrations alongside the pipeline without a coordination plan. Designate one single authority responsible for applying schemas per release.

## 27. Configuring Development, Test, and Production Environments

Environments can use the same migration chain while differing in connections and data:

| Environment | Goal |
| --- | --- |
| Local | Developers can create a fresh database and run all migrations |
| Test | Initialize a clean schema from migrations and run integration tests |
| Staging | Rehearse migrations on production-shaped data |
| Production | Apply migrations with control, backups, and observability |

Do not maintain separate migration sets per environment due to differing schemas. If sample data is needed, separate seed data or use Liquibase contexts/labels deliberately. The core schema should remain consistent.

In tests, Testcontainers can launch the exact database type, after which Flyway/Liquibase applies migrations before repository integration tests run. This verifies real SQL dialects and constraints rather than relying solely on mocks or a different embedded database engine.

## 28. Integrating Migrations with Spring Data R2DBC

Once migrations create tables, R2DBC entities must map table/column names and data types accurately:

~~~java
@Table("customer")
public record Customer(
        @Id Long id,
        @Column("full_name") String fullName,
        String email,
        String status
) {}
~~~

Corresponding migration:

~~~sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL,
    email VARCHAR(320),
    status VARCHAR(30) NOT NULL
);
~~~

Check the following points:

- Table and column names match `@Table`/`@Column` or the naming strategy.
- SQL types are compatible with Java types and the R2DBC driver.
- Nullable columns align with the domain model and validation.
- Generated IDs/default values are read properly by the driver/Spring Data.
- Foreign keys, unique constraints, and indexes are created.
- Appropriate custom conversions are registered if using special domain types.

Spring Data R2DBC is not Hibernate schema generation. Do not rely on JPA properties such as spring.jpa.hibernate.ddl-auto to manage schemas for R2DBC. Use Flyway or Liquibase as the source of truth for the schema.

## 29. Verifying Migrations in the Pipeline

A basic pipeline can include:

1. Compile and unit tests.
2. Provision a test database.
3. Run Flyway migrate or Liquibase update.
4. Check migration status/validate.
5. Run repository integration tests against the migrated schema.
6. Build the application artifact.
7. Run production migration in a controlled stage.
8. Roll out the application compatible with the new schema.

With Flyway, the validate command detects checksum changes or invalid states in applied migrations. With Liquibase, validate checks the changelog and configuration before update. Exact commands depend on the plugin/CLI or Spring Boot integration.

Do not check only that the migration command exits with code 0. Run real repository queries to verify mapping, constraints, and read/write behavior.

## 30. Testing Migrations from Multiple Schema States

Migrations should be tested from every starting state they are expected to support:

- Completely empty database: all migrations run sequentially.
- Older-version database: only new migrations are applied.
- Already-migrated database: re-running does not alter history unexpectedly.
- Mid-migration failure: inspect schema and history table state after failure.
- Database with legacy data: backfill does not lose or corrupt data.
- Schema drifted due to manual changes: validate or preconditions catch critical discrepancies.

With Flyway, use validate and inspect schema history. With Liquibase, use validate/status and inspect DATABASECHANGELOG. Also test backup/restore procedures for destructive migrations or large data transformations.

## 31. Baseline, Repair, and Clean: Using Them Properly

Flyway provides administrative operations that must be clearly understood:

- **baseline:** marks an existing database at a specific version when adopting Flyway management.
- **validate:** checks that migrations and history match.
- **repair:** fixes history metadata in well-defined situations, such as removing failed entries or aligning checksums under a controlled process.
- **clean:** drops objects in managed schemas; extremely dangerous with real data.

Never run clean in production. Keep clean disabled in critical environments. Repair does not replace fixing schemas via new migrations and should not be used to hide modified migration files.

Liquibase has update, validate, status, rollback, and clearCheckSums; these also must be used in appropriate scenarios. clearCheckSums only clears stored checksums so they can be recalculated—it does not fix actual file content or schema state.

## 32. Procedure When a Migration Fails

When a migration fails, do not blindly re-run it:

1. Halt rollout of the new application.
2. Save complete tool and database logs.
3. Identify which statements succeeded and which failed.
4. Check the database's transaction/DDL behavior.
5. Inspect the history table and actual schema.
6. Decide whether it can re-run, needs migration state repair, or needs a recovery migration.
7. Back up before performing risky remediation actions.
8. Re-run validate/status and test the application.

Do not delete the history table or delete migration files to "clean up" state. Doing so can mislead the tool about schema version and re-run destructive DDL.

## 33. Common Mistakes

1. **Editing only entities without creating migrations.** Runtime queries may reference nonexistent columns.
2. **Using an R2DBC URL for Flyway JDBC.** Migration tools need a JDBC URL in standard setups.
3. **Missing JDBC driver.** The R2DBC driver does not replace a JDBC driver for Flyway/Liquibase.
4. **Using both Flyway and Liquibase on the same schema.** Two migration histories do not synchronize automatically.
5. **Modifying applied versioned migrations.** Checksums across environments will diverge.
6. **Adding a NOT NULL column immediately to a table with existing data.** Migration may fail or cause an expensive operation.
7. **Renaming/dropping a column immediately in a rolling release.** Old application instances can fail.
8. **Enabling baseline-on-migrate or baselining without inspecting the schema.** A mismatched database may be mistakenly marked at the right version.
9. **Running clean or drop-first in production.** Can wipe schemas and data.
10. **Running huge data backfills in a single startup transaction.** Can hold locks and keep the application unready for a long time.
11. **Letting every application replica manage migrations uncoordinated.** Causes startup contention and poor observability.
12. **Using the migration user as the runtime account.** Grants overly broad DDL permissions to the application.
13. **Not testing against the right database engine.** SQL types, DDL transactions, and index syntax can differ.
14. **Checking only that migrations succeed without testing repositories.** The schema may be created while R2DBC mapping remains broken.

## Selection and Implementation Workflow

- Choose one tool as the source of schema history: Flyway or Liquibase.
- Verify the tool and version use JDBC; add the appropriate JDBC driver/database module alongside the R2DBC driver.
- Keep migrations/changelogs in source control alongside the application.
- Create a new migration for every schema change; leave applied migrations untouched.
- Test from both an empty database and prior schema versions.
- Use expand-and-contract for breaking changes or rolling deployments.
- Separate migration credentials from runtime credentials whenever possible.
- Run migrations before rolling out code that depends on the new schema.
- Verify the schema with validate/status and repository integration tests.
- Prepare backups, monitoring, and recovery plans for high-risk changes.

Schema version management lets the database evolve with the application without relying on manual SQL operations in each environment. In Spring Data R2DBC projects, Flyway or Liquibase typically uses JDBC to run migrations, while repositories and DatabaseClient continue using R2DBC for business data access. Store migrations in source control, never edit applied history, test on the right database, and deploy changes compatible across multiple versions. When migrations, entity mappings, and deployment sequences are managed together, environments stay schema-consistent and applications reduce release risks.
