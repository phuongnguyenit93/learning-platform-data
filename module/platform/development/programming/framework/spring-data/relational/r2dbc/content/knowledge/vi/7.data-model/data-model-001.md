# Thiết kế thực thể lưu trữ và phân biệt với mô hình API

Trong ứng dụng Spring Data R2DBC, thực thể lưu trữ (*persistence entity*) mô tả cách dữ liệu được ánh xạ vào bảng và cột của cơ sở dữ liệu. Mô hình API (*API model* hoặc DTO) mô tả dữ liệu mà ứng dụng nhận từ client và trả về qua HTTP hoặc một giao thức khác. Hai mô hình có thể chứa một số thuộc tính giống nhau, nhưng chúng phục vụ hai ranh giới khác nhau và không nên bị buộc phải thay đổi cùng nhau.

Thiết kế tốt bắt đầu từ schema và quy tắc nghiệp vụ, sau đó xác định dữ liệu nào cần được lưu, dữ liệu nào được phép nhận từ bên ngoài và dữ liệu nào được phép công khai. Spring Data R2DBC hỗ trợ ánh xạ thực thể theo mô hình quan hệ; nó không tự biến entity thành một đối tượng API an toàn, cũng không cung cấp đầy đủ hành vi ORM như JPA/Hibernate.

## 1. Phân biệt các mô hình dữ liệu trong ứng dụng

Một ứng dụng thường có nhiều hình thức biểu diễn cùng một thông tin. Ví dụ, một khách hàng có thể được lưu trong bảng `customers`, được tạo từ request JSON và được trả về dưới dạng response JSON. Các hình thức này có mục đích khác nhau:

| Mô hình | Mục đích | Ví dụ thuộc tính |
|---|---|---|
| Persistence entity | Ánh xạ dữ liệu lưu trữ và metadata của Spring Data | `id`, `email`, `displayName`, `version` |
| Request DTO / command | Biểu diễn dữ liệu client được phép gửi cho một thao tác | `email`, `displayName` |
| Response DTO | Biểu diễn dữ liệu được phép trả về cho client | `id`, `email`, `displayName` |
| Domain model | Biểu diễn khái niệm và quy tắc nghiệp vụ, nếu ứng dụng tách riêng | `Customer`, hành vi đổi tên, quy tắc trạng thái |
| Query projection | Chỉ chứa các trường cần cho một truy vấn hoặc màn hình | `id`, `displayName`, `orderCount` |

Không phải dự án nào cũng cần một class riêng cho cả năm mô hình. Với ứng dụng CRUD nhỏ, persistence entity có thể đồng thời thể hiện một phần domain model. Tuy nhiên, request và response DTO vẫn nên được thiết kế theo hợp đồng API, đặc biệt khi ứng dụng có dữ liệu nội bộ, thông tin nhạy cảm hoặc quy tắc cập nhật phức tạp.

Luồng dữ liệu phổ biến:

```text
                 HTTP / JSON
                      |
                      v
              Request DTO / Command
                      |
             validation + mapping
                      |
                      v
               Service / Domain
                      |
                Repository API
                      |
                      v
              Persistence Entity
                      |
                Spring Data R2DBC
                      |
                      v
               Relational tables

Response path đi ngược lại qua mapping:
Entity / Domain -> Response DTO -> JSON
```

Controller xử lý giao thức, Service điều phối nghiệp vụ, Repository truy cập dữ liệu. Việc chuyển đổi giữa request/response và entity nên diễn ra tại một ranh giới có chủ đích, thường là mapper hoặc application service.

## 2. Thiết kế persistence entity từ schema quan hệ

### 2.1. Bắt đầu từ dữ liệu và vòng đời nghiệp vụ

Trước khi viết class Java, hãy xác định:

- Bảng lưu trữ đại diện cho khái niệm nào trong nghiệp vụ.
- Thuộc tính nào là bắt buộc, thuộc tính nào có thể rỗng.
- Khóa chính được sinh tự động hay do ứng dụng cấp.
- Những giá trị nào cần duy nhất hoặc cần ràng buộc trong database.
- Dữ liệu nào thuộc cùng một aggregate và có vòng đời phụ thuộc.
- Những quan hệ nào chỉ là tham chiếu tới aggregate khác.
- Các thao tác nào cần được thực hiện trong cùng transaction.

Ví dụ bảng `customers` có thể gồm:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL,
    version BIGINT
);
```

Schema quy định kiểu dữ liệu, tính bắt buộc, tính duy nhất và khóa chính. Entity Java cần ánh xạ đúng những quyết định đó. Không nên chỉ dựa vào kiểu thuộc tính Java để giả định database đã có constraint tương ứng; ràng buộc toàn vẹn phải được định nghĩa trong schema.

### 2.2. Dùng annotation ánh xạ của Spring Data Relational

Các annotation thường gặp:

| Annotation | Vai trò |
|---|---|
| `@Table` | Khai báo bảng mà entity ánh xạ tới |
| `@Id` | Đánh dấu thuộc tính định danh |
| `@Column` | Chỉ định tên cột khi cần |
| `@Transient` | Đánh dấu thuộc tính không được lưu trong mapping |
| `@Version` | Hỗ trợ optimistic locking bằng trường version |
| `@MappedCollection` | Khai báo cách ánh xạ collection thuộc aggregate vào bảng quan hệ |

Ví dụ entity `Customer`:

```java
package com.example.store.customer.persistence;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record CustomerEntity(
        @Id Long id,
        String email,
        @Column("display_name") String displayName,
        @Version Long version
) {
}
```

Trong ví dụ:

- `@Table("customers")` ánh xạ record với bảng `customers`.
- `@Id` đánh dấu khóa chính.
- `email` dùng tên cột theo quy tắc mapping mặc định.
- `@Column("display_name")` ánh xạ `displayName` sang `display_name`.
- `@Version` cung cấp phiên bản để Spring Data hỗ trợ kiểm soát cập nhật đồng thời theo optimistic locking.

Nếu tên bảng và cột đã tuân theo naming strategy mặc định, có thể bỏ một số annotation tường minh. Dùng `@Table` và `@Column` khi tên schema cần được thể hiện rõ hoặc khác tên thuộc tính Java.

### 2.3. Chọn kiểu Java tương thích với kiểu database

Kiểu Java phải phù hợp với kiểu cột và khả năng hỗ trợ của driver R2DBC. Một số lựa chọn phổ biến:

| Dữ liệu | Kiểu Java thường dùng | Lưu ý |
|---|---|---|
| Số nguyên định danh | `Long`, `Integer` | Chọn theo kiểu khóa chính trong schema; kiểu wrapper biểu diễn được giá trị chưa có |
| Chuỗi | `String` | Độ dài và quy tắc chuẩn hóa do schema và nghiệp vụ quyết định |
| Tiền tệ | `BigDecimal` | Tránh dùng `double` cho phép tính tiền cần độ chính xác thập phân |
| Ngày | `LocalDate` | Dùng khi chỉ quan tâm ngày lịch |
| Thời điểm | `Instant` hoặc kiểu thời gian phù hợp | Thống nhất quy ước múi giờ và kiểu cột với database |
| Boolean | `Boolean` hoặc `boolean` | Dùng wrapper nếu cột có thể `NULL` |
| Trạng thái có tập giá trị | `String` hoặc `enum` | Xác định rõ cách lưu và tương thích khi thêm trạng thái mới |

Không nên chọn kiểu dữ liệu chỉ vì nó thuận tiện cho JSON. Ví dụ, giá trị tiền trong entity nên là `BigDecimal`; API có thể biểu diễn nó dưới dạng JSON number hoặc chuỗi theo hợp đồng đã thống nhất. Việc định dạng tiền tệ và ký hiệu hiển thị thuộc trách nhiệm của API hoặc giao diện.

### 2.4. Khóa chính và vòng đời entity

Với khóa chính do database sinh, entity mới thường có `id == null`. Khi gọi `save`, Spring Data R2DBC thực hiện thao tác phù hợp với trạng thái mới/cũ và trả về entity được lưu; hãy sử dụng giá trị trả về vì nó có thể chứa ID được sinh và metadata được cập nhật.

```java
CustomerEntity newCustomer = new CustomerEntity(
        null,
        "linh@example.com",
        "Linh Nguyen",
        null
);

return customerRepository.save(newCustomer);
```

Không nên tự gán một ID giả chỉ để biểu diễn entity mới khi database chịu trách nhiệm sinh khóa. Nếu ứng dụng sử dụng ID được cấp trước hoặc một chiến lược nhận diện trạng thái mới đặc biệt, cần cấu hình chiến lược newness phù hợp với Spring Data Relational.

Entity bất biến, chẳng hạn Java record, giúp thể hiện rõ dữ liệu của một trạng thái. Khi thay đổi thuộc tính, tạo instance mới thay vì sửa trực tiếp. Spring Data hỗ trợ materialize entity qua constructor; hãy thiết kế constructor/record nhất quán với mapping và kiểu dữ liệu thực tế.

### 2.5. Optimistic locking với @Version

Khi nhiều request có thể cùng cập nhật một bản ghi, trường version giúp phát hiện cập nhật dựa trên dữ liệu cũ. Spring Data sử dụng version trong thao tác cập nhật và tăng version khi lưu thành công. Nếu bản ghi đã bị một giao dịch khác thay đổi, thao tác có thể thất bại do xung đột optimistic locking.

`@Version` không thay thế transaction và cũng không thay thế ràng buộc dữ liệu. Nó phù hợp khi muốn phát hiện xung đột cập nhật mà không giữ khóa database trong suốt thời gian người dùng chỉnh sửa. API có thể đưa version ra ngoài dưới dạng `ETag` hoặc trường version trong response nếu hợp đồng cần hỗ trợ cập nhật có điều kiện; không bắt buộc phải công khai thuộc tính nội bộ này.

## 3. Thiết kế aggregate và quan hệ giữa các thực thể

Spring Data Relational tổ chức thao tác ghi quanh aggregate. Aggregate root là điểm vào để lưu một nhóm đối tượng có vòng đời phụ thuộc và cần được quản lý như một đơn vị nghiệp vụ. Đây là cách thiết kế mô hình và ranh giới ghi; nó không đồng nghĩa với việc Spring Data tự tải mọi quan hệ giống lazy loading của JPA.

### 3.1. Phân biệt dữ liệu thuộc aggregate và tham chiếu tới aggregate khác

Giả sử hệ thống bán hàng có `PurchaseOrder`, `OrderLine` và `Customer`:

- Một đơn hàng sở hữu các dòng hàng; các dòng hàng không có ý nghĩa độc lập ngoài đơn hàng. Có thể mô hình chúng như thành phần thuộc aggregate đơn hàng.
- Khách hàng có vòng đời độc lập với từng đơn hàng. Đơn hàng thường lưu `customerId` làm tham chiếu tới khách hàng thay vì nhúng toàn bộ entity khách hàng vào aggregate đơn hàng.

Ví dụ entity đơn giản:

```java
@Table("purchase_orders")
public record PurchaseOrderEntity(
        @Id Long id,
        @Column("customer_id") Long customerId,
        String status,
        BigDecimal totalAmount,
        @Version Long version
) {
}
```

`customerId` là một giá trị khóa ngoại. Khi cần thông tin khách hàng, ứng dụng có thể truy vấn repository tương ứng hoặc viết truy vấn join/projection chuyên biệt. Không nên kỳ vọng chỉ khai báo một thuộc tính `CustomerEntity customer` là Spring Data R2DBC sẽ tự tải khách hàng theo cơ chế lazy/eager relationship của JPA.

### 3.2. Collection thuộc aggregate

Với collection các thành phần phụ thuộc, Spring Data Relational cung cấp `@MappedCollection` để khai báo cột liên kết và, nếu cần, cột khóa của phần tử trong collection. Ví dụ minh họa:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrderEntity {

    @Id
    private Long id;

    private Long customerId;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLineEntity> lines;

    // Constructor và accessor theo quy ước của dự án.
}
```

```java
public record OrderLineEntity(
        String productCode,
        Integer quantity,
        BigDecimal unitPrice
) {
}
```

`idColumn` chỉ định cột trong bảng phần tử dùng để liên kết về aggregate root; `keyColumn` có thể dùng để lưu vị trí hoặc khóa của phần tử collection. Tên bảng và các cột còn lại phải khớp với schema và naming strategy đang sử dụng. Hãy kiểm tra mapping bằng integration test trên database thực tế.

Chỉ dùng collection mapping khi các phần tử thực sự thuộc vòng đời aggregate. Nếu `OrderLine` cần được quản lý độc lập, có API riêng hoặc được nhiều aggregate tham chiếu, hãy cân nhắc mô hình hóa nó thành một thực thể/aggregate riêng và lưu khóa tham chiếu rõ ràng.

### 3.3. Không mô phỏng đầy đủ ORM quan hệ đối tượng

Spring Data R2DBC không cung cấp persistence context, dirty checking, lazy loading và hệ annotation quan hệ giống JPA/Hibernate. Do đó:

- Không thiết kế entity dựa trên giả định rằng truy cập `order.getCustomer()` sẽ tự phát sinh truy vấn.
- Không dùng object graph lớn với nhiều vòng tham chiếu hai chiều.
- Chủ động quyết định khi nào cần truy vấn một bảng, nhiều bảng hoặc một projection.
- Dùng transaction khi nhiều thao tác ghi cần tính nguyên tử.
- Giữ aggregate đủ nhỏ để có thể lưu và kiểm soát hiệu năng một cách dự đoán được.

Nếu cần một màn hình hiển thị đơn hàng cùng tên khách hàng và tổng số dòng, có thể viết truy vấn join trả về projection. Không nhất thiết phải tải toàn bộ entity khách hàng và toàn bộ aggregate chỉ để dựng một response.

## 4. Thiết kế API request và response độc lập

### 4.1. Request DTO chỉ chứa dữ liệu client được phép cung cấp

Request DTO mô tả hợp đồng đầu vào của một thao tác. Ví dụ tạo khách hàng:

```java
package com.example.store.customer.api;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCustomerRequest(
        @NotBlank @Email @Size(max = 254) String email,
        @NotBlank @Size(max = 120) String displayName
) {
}
```

Request không nhận `id` do database sinh, `version` nội bộ hoặc trường `isAdmin`/`role` mà client không được quyền quyết định. Những giá trị này phải do hệ thống xác định dựa trên danh tính đã xác thực và quy tắc nghiệp vụ.

Validation ở DTO giúp kiểm tra hình dạng dữ liệu đầu vào như chuỗi rỗng, email sai định dạng hoặc vượt quá độ dài. Service vẫn cần kiểm tra các quy tắc nghiệp vụ như email đã được sử dụng hay người dùng hiện tại có quyền thực hiện thao tác. Database cần unique constraint để bảo vệ tính duy nhất ngay cả khi có hai request đồng thời.

### 4.2. Response DTO chỉ công khai dữ liệu cần thiết

```java
package com.example.store.customer.api;

public record CustomerResponse(
        Long id,
        String email,
        String displayName
) {
}
```

Response không nhất thiết phải chứa mọi cột của bảng. Những trường như `passwordHash`, token, ghi chú nội bộ, thông tin kiểm toán hoặc version có thể không được công khai. Nếu một API cần trả thêm trường, hãy thêm vào response model theo nhu cầu của hợp đồng và cân nhắc ảnh hưởng tương thích với client.

### 4.3. Dùng DTO riêng cho từng thao tác khi ý nghĩa khác nhau

Không phải mọi thao tác đều nên dùng chung một DTO `CustomerDto` có tất cả trường nullable. Ví dụ:

- `CreateCustomerRequest` chứa trường cần thiết để tạo mới.
- `UpdateCustomerRequest` chứa tập trường được phép thay đổi khi cập nhật toàn bộ tài nguyên.
- `ChangeCustomerNameRequest` chỉ chứa tên mới cho một lệnh nghiệp vụ cụ thể.
- `CustomerResponse` chứa dữ liệu được công khai sau thao tác.

Đối với `PUT` và `PATCH`, cần định nghĩa rõ ngữ nghĩa. `PUT` thường thay thế biểu diễn của tài nguyên theo hợp đồng; `PATCH` thay đổi một phần. Nếu dùng `null` để vừa biểu diễn “không gửi trường” vừa biểu diễn “xóa giá trị hiện tại”, ứng dụng không thể phân biệt hai ý nghĩa này nếu không có kiểu dữ liệu hoặc quy ước bổ sung. Hãy thiết kế request cho cập nhật một phần một cách tường minh.

## 5. Chuyển đổi giữa API model và persistence entity

Mapping là ranh giới chuyển dữ liệu giữa hai mô hình. Với dự án nhỏ, có thể viết mapper thủ công; với dự án nhiều entity và DTO, có thể dùng MapStruct hoặc công cụ mapping khác. Dù chọn cách nào, mapping phải thể hiện rõ trường nào được phép đi qua ranh giới.

### 5.1. Mapper thủ công

```java
package com.example.store.customer.api;

import com.example.store.customer.persistence.CustomerEntity;
import org.springframework.stereotype.Component;

@Component
public class CustomerMapper {

    public CustomerEntity toNewEntity(CreateCustomerRequest request) {
        return new CustomerEntity(
                null,
                request.email().trim(),
                request.displayName().trim(),
                null
        );
    }

    public CustomerResponse toResponse(CustomerEntity entity) {
        return new CustomerResponse(
                entity.id(),
                entity.email(),
                entity.displayName()
        );
    }
}
```

Mapper tạo entity mới với ID và version chưa được gán. Những giá trị có quyền quyết định từ hệ thống không được sao chép tùy tiện từ request. Khi mapping response, chỉ chọn các trường được công khai.

### 5.2. Kết hợp mapper trong Service

```java
package com.example.store.customer.application;

import com.example.store.customer.api.CreateCustomerRequest;
import com.example.store.customer.api.CustomerMapper;
import com.example.store.customer.api.CustomerResponse;
import com.example.store.customer.persistence.CustomerRepository;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class CustomerService {

    private final CustomerRepository repository;
    private final CustomerMapper mapper;

    public CustomerService(CustomerRepository repository, CustomerMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }

    public Mono<CustomerResponse> create(CreateCustomerRequest request) {
        var entity = mapper.toNewEntity(request);
        return repository.save(entity).map(mapper::toResponse);
    }
}
```

Service nhận request model, áp dụng quy tắc nghiệp vụ, chuyển thành entity, lưu qua Repository và chuyển kết quả thành response. `save` trả về publisher; `map` chuyển entity đã lưu thành response khi có kết quả. Không cần gọi `.block()` để lấy entity trước khi mapping.

Trong ứng dụng thực tế, kiểm tra email trùng có thể được thực hiện bằng repository trước khi lưu để tạo thông báo thân thiện. Tuy nhiên, unique constraint ở database vẫn là lớp bảo vệ cuối cùng vì hai request có thể cùng vượt qua bước kiểm tra trước khi một request ghi dữ liệu. Cần xử lý lỗi vi phạm constraint thành lỗi nghiệp vụ/API phù hợp.

### 5.3. Không sao chép toàn bộ thuộc tính một cách mù quáng

Các hàm kiểu `BeanUtils.copyProperties(request, entity)` hoặc mapper tự động sao chép mọi trường cùng tên có thể vô tình cho phép client thay đổi thuộc tính nội bộ. Nếu dùng MapStruct, nên khai báo mapping rõ ràng và bỏ qua các trường như ID, version, trạng thái được hệ thống quản lý hoặc quan hệ không được phép cập nhật từ request.

Mapping tường minh có thêm mã nguồn, nhưng giúp reviewer thấy rõ ranh giới dữ liệu. Với trường nhạy cảm hoặc quy tắc phân quyền, cách này đặc biệt quan trọng để tránh lỗi mass assignment.

## 6. Khi nào nên dùng projection thay vì entity đầy đủ?

Một truy vấn phục vụ danh sách hoặc báo cáo có thể chỉ cần một vài trường. Tải toàn bộ entity rồi chuyển thành DTO có thể gây đọc thừa dữ liệu, đặc biệt với bảng có nhiều cột hoặc aggregate có cấu trúc phức tạp.

Ví dụ, màn hình danh sách khách hàng chỉ cần ID, tên hiển thị và số đơn hàng. Có thể tạo projection riêng:

```java
public record CustomerSummary(
        Long id,
        String displayName,
        Long orderCount
) {
}
```

Truy vấn tùy chỉnh có thể trả về projection nếu cách ánh xạ và driver hỗ trợ kiểu kết quả đã chọn. Với Spring Data R2DBC, cần khai báo SQL và mapping phù hợp với projection; kiểm thử integration để xác nhận tên cột, alias và kiểu dữ liệu. Không nên giả định mọi projection hoặc biểu thức truy vấn của JPA đều hoạt động giống hệt.

Phân biệt ba trường hợp:

- **Entity:** dùng khi cần đọc/ghi một thực thể theo mapping lưu trữ.
- **Response DTO:** dùng khi định nghĩa hợp đồng trả dữ liệu cho client; có thể được tạo từ entity hoặc projection.
- **Query projection:** dùng để lấy đúng tập dữ liệu cần cho một truy vấn, chẳng hạn báo cáo hoặc màn hình tổng hợp.

Một response DTO có thể được tạo từ query projection mà không cần dựng entity đầy đủ. Điều này hữu ích cho truy vấn chỉ đọc và dữ liệu tổng hợp.

## 7. Những quyết định thiết kế quan trọng

### 7.1. Tên thuộc tính và tên cột

Tên Java nên dễ đọc theo quy ước camelCase; tên cột nên nhất quán với quy ước schema của dự án. Dùng `@Column` khi cần ánh xạ rõ ràng, ví dụ `createdAt` với `created_at`. Tránh đổi tên cột chỉ vì muốn response JSON có tên khác; API có thể dùng `@JsonProperty` hoặc mapper mà không cần thay đổi schema.

### 7.2. Giá trị mặc định và trạng thái

Trạng thái nghiệp vụ như `PENDING`, `APPROVED`, `CANCELLED` cần được thay đổi qua hành vi nghiệp vụ có kiểm soát. Không nên để request nhận một entity hoàn chỉnh rồi ghi đè `status` tùy ý. Có thể dùng command riêng như `ApproveOrderRequest` hoặc một phương thức Service `approveOrder(...)` để kiểm tra quyền và chuyển trạng thái hợp lệ.

Nếu lưu enum, cần thống nhất cách biểu diễn trong database và khả năng tương thích khi thêm giá trị mới. Lưu tên enum dạng chuỗi thường dễ đọc hơn ordinal, vì thứ tự enum trong code có thể thay đổi. Tuy nhiên, vẫn cần quy trình triển khai khi thêm trạng thái để mọi phiên bản ứng dụng cùng hiểu dữ liệu.

### 7.3. Dữ liệu nhạy cảm và quyền truy cập

Entity có thể chứa dữ liệu mà API không được phép trả về. Không serialize entity trực tiếp thành JSON chỉ vì thuận tiện. Tách response DTO giúp kiểm soát trường công khai và giảm nguy cơ lộ thông tin nội bộ khi entity được mở rộng sau này.

Tương tự, request không được phép cập nhật tất cả thuộc tính entity. Quyền sở hữu, vai trò, trạng thái kiểm duyệt, giá tiền đã xác nhận và các trường audit cần được thiết lập từ ngữ cảnh xác thực hoặc quy tắc nghiệp vụ. Không tin giá trị do client gửi chỉ vì kiểu dữ liệu hợp lệ.

### 7.4. Trường audit và dữ liệu tính toán

Các trường như `createdAt`, `updatedAt`, `createdBy` có thể thuộc persistence model nếu database cần lưu và truy vấn chúng. Cần xác định thành phần chịu trách nhiệm gán giá trị: ứng dụng, callback auditing của Spring Data hoặc database default. Không để nhiều lớp cùng tự ý ghi giá trị khác nhau.

Giá trị tính toán chỉ dùng để hiển thị có thể nằm trong response DTO hoặc projection thay vì cột lưu trữ. Ngược lại, nếu giá trị là dữ liệu nghiệp vụ cần truy vết hoặc cần dùng trong truy vấn, hãy cân nhắc lưu nó và xác định cách cập nhật nhất quán.

### 7.5. Schema evolution và tương thích API

Schema database và API có vòng đời thay đổi khác nhau. Thêm cột lưu trữ không đồng nghĩa phải thêm trường vào response. Đổi tên JSON field không nhất thiết phải đổi tên cột. Một API version mới có thể trình bày dữ liệu khác trong khi persistence entity vẫn giữ nguyên.

Khi thay đổi schema, dùng migration có phiên bản và triển khai theo thứ tự tương thích với ứng dụng đang chạy. Khi thay đổi API, cân nhắc client cũ, field bắt buộc, field deprecated và quy tắc chuyển đổi. Không để một thay đổi ở database vô tình làm thay đổi hợp đồng JSON.

## 8. Các lỗi thường gặp khi thiết kế entity và API model

### Dùng entity làm request và response cho mọi endpoint

Điều này khiến client có thể gửi các trường nội bộ và khiến API vô tình công khai dữ liệu mới được thêm vào entity. Dùng request/response DTO để định nghĩa rõ dữ liệu vào và ra.

### Dùng một DTO duy nhất cho tạo, cập nhật và đọc

Các thao tác có quyền và yêu cầu dữ liệu khác nhau. Tách DTO theo use case giúp validation và mapping dễ hiểu, đồng thời tránh việc trường chỉ dành cho response bị client gửi ngược vào request.

### Nhúng toàn bộ quan hệ JPA vào entity R2DBC

R2DBC không tự tải quan hệ theo lazy loading. Mô hình hóa aggregate và tham chiếu bằng ID; viết truy vấn riêng hoặc projection khi cần dữ liệu kết hợp.

### Để API quyết định khóa chính hoặc trạng thái nội bộ

Không sao chép ID, role, ownerId, version hay trạng thái được bảo vệ từ request nếu client không có quyền đặt chúng. Hãy lấy thông tin định danh từ ngữ cảnh xác thực và áp dụng quy tắc trong Service.

### Chỉ kiểm tra dữ liệu ở Java

Validation DTO không ngăn được lỗi từ luồng ghi khác hoặc cạnh tranh đồng thời. Dùng constraint ở database cho tính duy nhất, khóa ngoại, `NOT NULL` và các điều kiện có thể biểu diễn bằng schema.

### Trả về entity trực tiếp vì mapping có vẻ dư thừa

Mapping là nơi xác định hợp đồng dữ liệu. Có thể dùng mapper đơn giản hoặc projection; không nên bỏ ranh giới API chỉ để giảm vài dòng code.

## 9. Kiểm thử mapping và hợp đồng dữ liệu

Nên kiểm thử riêng các phần có thể thay đổi độc lập:

| Phần cần kiểm thử | Nội dung |
|---|---|
| Persistence mapping | Entity ánh xạ đúng bảng, cột, kiểu dữ liệu, ID và version |
| Repository | Lệnh đọc/ghi, derived query, custom SQL và collection mapping hoạt động trên database mục tiêu |
| Mapper | Chỉ các trường được phép được chuyển từ request sang entity và entity sang response |
| Validation | Request thiếu trường, sai định dạng hoặc vượt giới hạn bị từ chối |
| Service | Quy tắc nghiệp vụ, quyền thay đổi trạng thái và xử lý xung đột được thực thi |
| API contract | JSON response không lộ trường nội bộ và giữ đúng cấu trúc đã công bố |

Ví dụ unit test mapper có thể xác nhận ID và version không bị lấy từ request:

```java
CreateCustomerRequest request = new CreateCustomerRequest(
        "linh@example.com",
        " Linh Nguyen "
);

CustomerEntity entity = mapper.toNewEntity(request);

assertThat(entity.id()).isNull();
assertThat(entity.version()).isNull();
assertThat(entity.email()).isEqualTo("linh@example.com");
assertThat(entity.displayName()).isEqualTo("Linh Nguyen");
```

Integration test nên chạy trên cùng hệ quản trị cơ sở dữ liệu hoặc một cấu hình tương thích với môi trường triển khai. Các khác biệt về kiểu dữ liệu, generated key, SQL và mapping collection có thể không xuất hiện khi chỉ kiểm thử bằng mock.

## 10. Quy trình thiết kế một tính năng mới

Khi thêm một tính năng lưu trữ dữ liệu, có thể đi theo trình tự sau:

1. Xác định use case và quy tắc nghiệp vụ: người dùng muốn thực hiện hành động gì, ai có quyền và điều kiện nào phải đúng.
2. Thiết kế bảng, khóa, constraint và transaction cần thiết.
3. Xác định aggregate root, thành phần phụ thuộc và tham chiếu tới aggregate khác.
4. Tạo persistence entity cùng annotation mapping phù hợp.
5. Tạo Repository với derived query hoặc SQL tùy chỉnh.
6. Thiết kế request DTO/command chỉ chứa dữ liệu đầu vào được phép.
7. Thiết kế response DTO hoặc query projection theo dữ liệu cần công khai.
8. Viết mapper tường minh giữa API model và persistence model.
9. Đặt quy tắc nghiệp vụ và phối hợp publisher trong Service; dùng transaction khi cần.
10. Kiểm thử mapping, truy vấn, validation, quyền truy cập và hợp đồng API.

## 11. Checklist thiết kế

- [ ] Entity phản ánh bảng và schema, có `@Table`, `@Id` và mapping cột cần thiết.
- [ ] Kiểu Java tương thích với kiểu cột và driver R2DBC.
- [ ] Khóa chính, constraint, index và quan hệ được định nghĩa trong schema.
- [ ] Aggregate root và vòng đời của collection được xác định rõ.
- [ ] Tham chiếu tới aggregate độc lập được thể hiện bằng khóa phù hợp; không giả định lazy loading kiểu JPA.
- [ ] Request DTO chỉ chứa trường client được phép gửi.
- [ ] Response DTO chỉ công khai trường cần thiết.
- [ ] Create, update, command và response được tách khi ngữ nghĩa khác nhau.
- [ ] Mapper không sao chép mù quáng ID, version, role hoặc trạng thái nội bộ từ request.
- [ ] Quy tắc nghiệp vụ được kiểm tra trong Service; constraint quan trọng được bảo vệ trong database.
- [ ] Projection được cân nhắc cho truy vấn chỉ đọc hoặc màn hình tổng hợp.
- [ ] Có unit test cho mapper và integration test cho mapping/repository trên database phù hợp.

Thiết kế persistence entity và API model thành hai mô hình có ranh giới rõ ràng giúp schema tập trung vào tính toàn vẹn dữ liệu, còn API tập trung vào trải nghiệm và hợp đồng với client. Spring Data R2DBC đảm nhiệm ánh xạ và truy cập dữ liệu reactive; Service và mapper chịu trách nhiệm điều phối nghiệp vụ cũng như chuyển đổi dữ liệu qua các ranh giới của ứng dụng.
