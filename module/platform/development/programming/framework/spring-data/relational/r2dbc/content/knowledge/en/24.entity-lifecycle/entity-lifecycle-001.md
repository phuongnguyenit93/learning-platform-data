# Entity Conversion, Persistence, and Retrieval Stages

In Spring Data Relational R2DBC, an entity goes through multiple stages from the moment it is created in the application, converted into write data, saved to the database, and then read and mapped back into a Java object. Understanding the order of these stages helps determine the right place for data initialization logic, auditing, type conversion, callbacks, and ID or version handling.

The entity lifecycle in Spring Data Relational differs from JPA/Hibernate in one important respect: Spring Data R2DBC does not maintain a persistence context to track every loaded object, does not perform automatic dirty checking, and does not automatically flush in-memory changes. When an application wants to persist changes, it must explicitly invoke a repository or template.

The lifecycle can be divided into two main flows:

- **Write flow:** create or receive an entity → determine whether the entity is new or existing → run callbacks before conversion/saving → convert the entity into column data → execute INSERT or UPDATE → receive the resulting ID/version and entity.
- **Read flow:** execute SELECT → receive rows from the driver → convert columns into Java properties → run callbacks after conversion → emit the entity to the reactive pipeline.

## 1. Entity lifecycle overview

Example of a Customer entity:

~~~java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Version
    private Long version;

    private String name;
    private String email;
    private Instant createdAt;
    private Instant updatedAt;

    protected Customer() {
    }

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public void rename(String newName) {
        this.name = newName;
    }

    public Long getId() {
        return id;
    }

    public Long getVersion() {
        return version;
    }

    public String getName() {
        return name;
    }
}
~~~

This entity has:

- An ID to identify the record.
- A version to support optimistic locking and potentially participate in new-state detection.
- Business properties.
- Timestamp properties that can be managed by auditing or application logic.

High-level flow:

~~~text
             CREATE ENTITY
                  |
                  v
       Entity exists in memory
                  |
                  v
         Call repository.save()
                  |
                  v
        Determine new / existing
             /           \
            /             \
           v               v
       INSERT             UPDATE
           \               /
            \             /
             v           v
      Convert entity to columns
                  |
                  v
            Execute SQL
                  |
                  v
     Receive saved entity and ID/version

                  READ
                   |
                   v
              SELECT SQL
                   |
                   v
              Database Row
                   |
                   v
         Convert row to entity
                   |
                   v
           Entity is emitted
~~~

This is a conceptual model. The exact callback order and whether the framework creates a new instance or updates an existing one depend on mapping metadata, the entity type, and the operation being performed.

## 2. Stage 1: creating the entity in the application

An entity is typically created by a service, factory, or application layer:

~~~java
Customer customer =
    new Customer("An", "an@example.com");
~~~

At this point, the object exists only in memory. No SQL statement has been executed, and the database is not aware of the object.

If the ID is generated by the database, the ID may not have a value yet. If the application assigns the ID itself, such as a UUID, the entity may already have an ID upon creation. Therefore, looking at the ID alone is not always sufficient to identify a new entity.

Some practical guidelines:

- Create the entity in a valid state according to domain rules.
- Do not assign the version arbitrarily if Spring Data is managing the version.
- Distinguish between an unprovided value and a value that needs to be stored as SQL NULL.
- Do not treat object instantiation as a persistence operation.
- Only call save when you want to start the persistence process.

### A new entity does not always mean a null ID

If the application assigns a UUID before inserting, a new entity can already have an ID. Spring Data needs an appropriate new-state detection strategy, such as a version property or the Persistable interface.

With the default mechanism, Spring Data prioritizes:

1. Persistable.isNew() if the entity implements Persistable.
2. The @Version property if the entity has a version property.
3. The ID if there is no version property.

Example of an entity using a wrapper-typed version:

~~~java
@Id
private UUID id;

@Version
private Long version;
~~~

With a wrapper version, null indicates a new state under the version-based detection strategy. A non-null version indicates an existing entity. Thus, an entity with a pre-assigned UUID whose version is still null can still be detected as new.

If using Persistable, the isNew() method provided by the entity determines the new state. This state must be managed at the right time, and the entity must not be marked as existing before the insert succeeds.

## 3. Stage 2: calling save() and determining state

Repositories provide save() for both new and existing entities:

~~~java
Mono<Customer> saved =
    customerRepository.save(customer);
~~~

save() does not mean always running UPDATE, nor is it a database upsert. Spring Data determines the new/existing state first and then chooses INSERT or UPDATE.

| Detected state | Operation |
|---|---|
| New | INSERT |
| Existing | UPDATE |

Spring Data does not run a SELECT by default to check whether the ID exists before every save. If an entity is detected as existing but the row has been deleted, UPDATE does not automatically switch to INSERT. If an entity is detected as new but the ID already exists, INSERT can fail with a primary key or unique constraint violation.

### Role of the ID

The ID identifies the record. When there is no version property and Persistable is not implemented, Spring Data generally uses the ID state to detect a new entity:

- A null wrapper ID usually indicates new.
- A primitive ID at its default value usually indicates new.
- An ID that already has a value usually indicates existing.

Details depend on the ID type and the detection strategy the entity uses.

### Role of @Version

Version both supports optimistic locking and can be used to detect a new entity:

- An unset version indicates new under version-based detection rules.
- A non-null version indicates existing.
- When an update succeeds, the version is incremented by Spring Data's mechanism.
- When the version in the object no longer matches the database, the operation may fail due to optimistic locking.

Do not use version as business data or modify it manually to force Spring Data to choose INSERT/UPDATE.

## 4. Stage 3: callbacks before converting the entity

Before converting the entity into column data for writing, Spring Data Relational provides entity callbacks. Callbacks allow the application to perform lifecycle-related processing, for example:

- Populating default values.
- Normalizing data.
- Assigning reference codes or metadata to be persisted.
- Executing auditing logic through the configured auditing mechanism.

A commonly used callback is BeforeConvertCallback:

~~~java
@Component
public class CustomerBeforeConvert
        implements BeforeConvertCallback<Customer> {

    @Override
    public Publisher<Customer> onBeforeConvert(
            Customer customer,
            SqlIdentifier table) {

        customer.normalizeName();
        return Mono.just(customer);
    }
}
~~~

The callback is invoked before the step that converts the entity into write data. It receives the entity and table information, and returns a Publisher containing the processed entity.

The example only illustrates the callback structure; the normalizeName() method needs to be defined in Customer. For reactive callbacks, return a Publisher and do not subscribe or block manually.

### BeforeSaveCallback

BeforeSaveCallback runs at the stage before saving the data, once Spring Data has prepared the OutboundRow:

~~~java
@Component
public class CustomerBeforeSave
        implements BeforeSaveCallback<Customer> {

    @Override
    public Publisher<Customer> onBeforeSave(
            Customer customer,
            OutboundRow row,
            SqlIdentifier table) {

        return Mono.just(customer);
    }
}
~~~

This callback can inspect or adjust the OutboundRow as needed for mapping. If modifying the row, you must clearly understand the columns and data types expected by the database/driver. Callbacks should not be used to replace complex business rules that belong in the service or domain model.

### Callbacks are not the place to call save() recursively

If a callback calls repository.save() again on the very entity being processed, it can create a callback loop or trigger hard-to-control nested writes. Callbacks should perform clearly scoped lifecycle processing; multi-step business operations should be orchestrated in a service.

## 5. Stage 4: converting the entity into write data

Spring Data Relational uses mapping metadata to convert entity properties into columns in an OutboundRow.

Example:

~~~java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("full_name")
    private String name;

    @Column("email_address")
    private String email;

    @Transient
    private String displayLabel;
}
~~~

The mapping metadata specifies:

- The entity corresponds to the customer table.
- The name property corresponds to the full_name column.
- The email property corresponds to email_address.
- displayLabel is not persisted as an entity column.
- id is marked as the identifier.

During the conversion stage, Spring Data uses mapping metadata and the conversion service to produce values compatible with the R2DBC driver. Special Java types may require a custom converter.

### Converter

When a Java type in the entity does not map directly to a database type, an appropriate converter can be registered.

Example of an enum:

~~~java
public enum CustomerStatus {
    ACTIVE,
    INACTIVE,
    CLOSED
}
~~~

If the database stores status as VARCHAR, a converter can convert the enum to String on write and String to enum on read. The specific converter configuration depends on the Spring Data Relational version and the application's mapping setup.

Callbacks should not be used for every type conversion. Converters are the more appropriate mechanism for consistent data conversion between Java types and storage types.

## 6. Stage 5: executing INSERT or UPDATE

After determining the state and preparing the write data, Spring Data executes the corresponding SQL statement.

### INSERT

For a new entity:

~~~sql
INSERT INTO customer (name, email, created_at)
VALUES (:name, :email, :createdAt);
~~~

If the ID is database-generated, the framework/driver can retrieve the generated value and assign it to the resulting entity according to the ID strategy and database capabilities.

If the application provides the ID itself, the ID is included in the INSERT statement according to the corresponding mapping and configuration.

### UPDATE

For an existing entity:

~~~sql
UPDATE customer
SET full_name = :name,
    email_address = :email
WHERE id = :id;
~~~

If @Version is present, the update is semantically guarded by a version condition:

~~~sql
UPDATE customer
SET full_name = :name,
    version = :nextVersion
WHERE id = :id
  AND version = :previousVersion;
~~~

The actual SQL generated by Spring Data and the dialect may differ from the illustrative presentation above. The key point is that the old version is used to detect concurrent modifications and the new version is set when the update succeeds.

### save() is not an upsert

If an entity is detected as new, Spring Data chooses INSERT. If an entity is detected as existing, Spring Data chooses UPDATE. Whether the row actually exists does not cause Spring to automatically switch branches.

If the business logic requires an upsert by a unique key, use a SQL statement or database-specific strategy designed for upsert. Do not rely on the name save() to infer this behavior.

## 7. Stage 6: callbacks after saving

After a write operation succeeds, Spring Data provides AfterSaveCallback:

~~~java
@Component
public class CustomerAfterSave
        implements AfterSaveCallback<Customer> {

    @Override
    public Publisher<Customer> onAfterSave(
            Customer customer,
            OutboundRow row,
            SqlIdentifier table) {

        return Mono.just(customer);
    }
}
~~~

This callback is suitable for post-save lifecycle processing, such as enriching the returned object or recording lightweight metrics. One should not assume that a side effect external to the database can roll back with the transaction simply because it is performed inside a callback.

If a callback sends an email or makes an HTTP call, the database transaction cannot automatically undo that side effect. For events that need to be emitted reliably after commit, consider the outbox pattern or a post-transaction event publishing mechanism.

### Using the entity returned from save()

Always continue the pipeline with the returned entity:

~~~java
return customerRepository.save(customer)
    .flatMap(saved -> {
        // saved is the post-persistence entity,
        // which may contain a new ID or version.
        return auditRepository.save(toAudit(saved))
            .thenReturn(saved);
    });
~~~

This is important for immutable entities or when the framework creates a new instance to assign the ID/version. Do not assume the original object is always mutated in place.

## 8. Generated IDs and immutable entities

With a database-generated ID, the ID value is only available after the INSERT succeeds and the driver/framework can retrieve the generated value.

Example:

~~~java
Customer customer =
    new Customer("An", "an@example.com");

return customerRepository.save(customer)
    .map(saved -> {
        Long generatedId = saved.getId();
        return new CustomerCreatedResponse(
            generatedId,
            saved.getName()
        );
    });
~~~

Do not read the ID from the input object and assume it is populated after insert. Use the object returned from save().

### Mutable entities

With a mutable entity, Spring Data can update the ID/version property through the appropriate property access mechanism. However, callers should still use the returned result to avoid depending on whether the instance was replaced or not.

### Immutable entities

With an immutable entity, the framework can create a new instance when it needs to assign an ID or version. Example of an entity using a constructor or record:

~~~java
public record Customer(
    @Id Long id,
    @Version Long version,
    String name,
    String email
) {
}
~~~

On insert or update, the returned entity may be a different instance from the original object. Continue using the value emitted by save() to ensure the pipeline has the latest ID/version.

## 9. Auditing in the write lifecycle

Spring Data Relational supports auditing to manage fields such as:

- createdDate: creation timestamp.
- lastModifiedDate: last modification timestamp.
- createdBy: creator.
- lastModifiedBy: last modifier.

Entity example:

~~~java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    private String name;

    @CreatedDate
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;

    @CreatedBy
    private String createdBy;

    @LastModifiedBy
    private String updatedBy;
}
~~~

Enabling auditing:

~~~java
@Configuration
@EnableR2dbcAuditing
public class R2dbcAuditingConfiguration {
}
~~~

If the current user needs to be resolved in a reactive application, an appropriate ReactiveAuditorAware can be provided:

~~~java
@Component
public class CurrentAuditor implements ReactiveAuditorAware<String> {

    @Override
    public Mono<String> getCurrentAuditor() {
        return currentUserService.currentUsername();
    }
}
~~~

Auditing annotations only take effect when auditing is enabled and the auditor infrastructure is configured appropriately. Database column names, temporal types, and principal types must match the application's mapping.

Auditing is part of the persistence flow managed by Spring Data. If writing with raw SQL via DatabaseClient, do not assume auditing callbacks run automatically; the application must assign audit fields manually or use a consistent separate mechanism.

## 10. Read stage 1: executing SELECT

When calling a repository:

~~~java
Mono<Customer> customer =
    customerRepository.findById(42L);
~~~

Spring Data generates and executes a SELECT via R2DBC when the publisher is subscribed to.

For queries returning multiple rows:

~~~java
Flux<Customer> customers =
    customerRepository.findByStatus("ACTIVE");
~~~

Each row from the database is read and converted into an entity. Flux emits entities along the result stream; the entire dataset does not necessarily have to be loaded into a List first.

For queries finding no results:

- findById() typically emits Mono.empty().
- Multi-row queries can emit Flux.empty().
- Connection errors or SQL errors go through onError.

Do not confuse the no-rows-found case with a query error.

## 11. Read stage 2: converting rows into entities

When receiving a row, Spring Data Relational uses mapping metadata to convert columns into Java properties.

Example:

~~~sql
SELECT id, full_name, email_address, version
FROM customer
WHERE id = :id;
~~~

Mapped columns:

| Database column | Java property |
|---|---|
| id | id |
| full_name | name |
| email_address | email |
| version | version |

Mapping may need to:

- Select the appropriate constructor to instantiate the object.
- Convert data types from driver types to Java types.
- Apply column names from @Column.
- Handle embedded value objects or supported mapping structures.
- Apply custom converters when Java and database types differ.

If a query only SELECTs a subset of columns yet maps into the full entity, unreturned properties may carry null or default values. Do not use such a partial object as a complete entity and pass it to save(), as there is a risk of overwriting data.

For partial read queries, map into a separate DTO/projection.

## 12. Read stage 3: callbacks after conversion

Spring Data Relational provides AfterConvertCallback to process an entity after a row is converted into an object:

~~~java
@Component
public class CustomerAfterConvert
        implements AfterConvertCallback<Customer> {

    @Override
    public Publisher<Customer> onAfterConvert(
            Customer customer,
            Row row,
            RowMetadata metadata) {

        return Mono.just(customer);
    }
}
~~~

This callback receives the mapped entity along with Row and RowMetadata. It can perform post-conversion processing, such as normalizing a computed property or populating state that is not directly persisted.

The callback must return an appropriate Publisher and must not subscribe or block manually. If the callback emits an error, the error enters the read reactive pipeline and the caller receives onError.

Do not use AfterConvertCallback to issue a database query per entity if avoidable. Doing so can cause an N+1 problem. If related data is needed, consider a JOIN projection or a batch query after collecting the list of IDs.

## 13. Reading an entity does not imply change tracking

An important difference compared to JPA/Hibernate:

- Spring Data R2DBC does not maintain an identity-map-style persistence context.
- There is no automatic dirty checking for loaded objects.
- Modifying entity properties in memory does not automatically trigger an UPDATE.
- There are no lazy-loading proxies that automatically query relationships when a getter is called.
- To persist changes, you must call save() or an explicit update statement.

Example:

~~~java
return customerRepository.findById(id)
    .map(customer -> {
        customer.rename("An Nguyen");
        return customer;
    });
~~~

The publisher above only emits an object modified in memory. It does not automatically save the change to the database.

To save:

~~~java
return customerRepository.findById(id)
    .flatMap(customer -> {
        customer.rename("An Nguyen");
        return customerRepository.save(customer);
    });
~~~

save() is an explicit persistence operation. If the entity has @Version, keep the loaded version intact so Spring Data can perform optimistic locking checks.

## 14. Entity callbacks and domain logic have distinct roles

Callbacks are extension points around mapping/persistence stages. They are suitable for technical logic tied to the lifecycle:

- Normalizing data before writing.
- Assigning metadata.
- Populating auditing values.
- Transforming technical state before or after mapping.

Domain logic consists of business rules deciding what an entity is allowed to do:

- Disallowing closing a customer who has pending transactions.
- Disallowing placing an order if inventory is insufficient.
- Disallowing state changes after finalization.

These rules should reside in the entity/domain service/application service so they can be invoked and tested independently. Important business logic should not be hidden inside callbacks where callers do not notice it.

Callbacks are also not the right place to orchestrate multiple repository calls. If a use case needs to read, validate, and write multiple aggregates, organize it in a service and compose the Publishers explicitly.

## 15. Reactive callbacks and execution order

Spring Data Relational callbacks are reactive and participate in the persistence pipeline. Representative callbacks include:

| Callback | Stage |
|---|---|
| BeforeConvertCallback | Before converting the entity into write data |
| BeforeSaveCallback | Before saving, when OutboundRow is available |
| AfterSaveCallback | After a successful save operation |
| AfterConvertCallback | After a row is converted into an entity |

Spring Data can apply callbacks in a configured order through the callback ordering mechanism. When multiple callbacks of the same type exist, specify an explicit order if a later callback depends on the result of an earlier one.

Do not assume callbacks are invoked when all database access paths go through different abstractions:

- Repositories and R2dbcEntityTemplate use Spring Data's mapping infrastructure.
- Raw SQL via DatabaseClient with manual mapping does not by default run all entity lifecycle callbacks the way template entity operations do.
- Direct SQL does not automatically perform auditing or version updates unless the application writes corresponding logic.

## 16. R2dbcEntityTemplate and DatabaseClient in the entity lifecycle

These two abstractions provide different levels of mapping support.

### Repository

Repositories are well-suited for CRUD and query methods:

~~~java
Mono<Customer> findById(Long id);
Mono<Customer> save(Customer customer);
Flux<Customer> findByStatus(String status);
~~~

Repositories work with entity metadata and the new-state detection, version, and lifecycle rules supported by Spring Data.

### R2dbcEntityTemplate

R2dbcEntityTemplate provides a more explicit API for entity operations:

~~~java
Mono<Customer> customer =
    r2dbcEntityTemplate.selectOne(
        Query.query(Criteria.where("id").is(42L)),
        Customer.class
    );
~~~

The template uses Spring Data Relational's mapping infrastructure and is suitable when building dynamic queries or performing entity operations without writing all SQL manually.

### DatabaseClient

DatabaseClient is suitable for custom SQL, JOINs, aggregate queries, and DTO mapping:

~~~java
Mono<CustomerSummary> summary =
    databaseClient.sql(
        "SELECT id, full_name, status " +
        "FROM customer WHERE id = :id"
    )
    .bind("id", 42L)
    .map((row, metadata) -> new CustomerSummary(
        row.get("id", Long.class),
        row.get("full_name", String.class),
        row.get("status", String.class)
    ))
    .one();
~~~

When using DatabaseClient, the application takes more explicit responsibility for the SQL statement, parameter binding, mapping, and attributes that need updating such as version or auditing.

## 17. Transactions wrapping write stages

A use case might need to save a Customer and then record an Audit. If both operations must succeed or fail together, use a reactive transaction:

~~~java
@Transactional
public Mono<Customer> rename(Long id, String newName) {
    return customerRepository.findById(id)
        .switchIfEmpty(
            Mono.error(new CustomerNotFoundException(id))
        )
        .flatMap(customer -> {
            customer.rename(newName);
            return customerRepository.save(customer);
        })
        .flatMap(saved ->
            auditRepository.save(toAudit(saved))
                .thenReturn(saved)
        );
}
~~~

The operations are chained within the same reactive pipeline. If the audit save step fails with a rollback-triggering error, the Customer change also rolls back.

Do not call subscribe() inside a transactional method. Doing so can create a subscription outside the transaction context and cause the method to complete before persistence finishes.

A database transaction cannot roll back external side effects such as emails or HTTP calls. For events that must be emitted after data commits, consider an outbox or post-commit processing mechanism.

## 18. Error handling and cancellation in the lifecycle

Stages can terminate with:

- Complete: operation succeeded or no rows returned.
- Error: mapping, conversion, SQL, connection, or callback error.
- Cancel: subscriber cancels consumption of the publisher.

Example:

~~~java
return customerRepository.findById(id)
    .map(CustomerSummary::from)
    .onErrorMap(
        DataAccessException.class,
        error -> new CustomerReadException(error)
    );
~~~

onErrorMap transforms the error type while preserving the onError signal. If the pipeline is inside a transaction, the transaction manager can still recognize the error.

If onErrorResume is used to turn an error into Mono.empty() inside a transaction, the publisher may complete normally and the transaction may commit. Only recover from errors when intentionally required by business logic.

Cancellation also matters in reactive transactions. If a subscriber cancels the write stream before completion, the transaction manager may roll back. Do not use take(), next(), or early cancellation in a write flow if the requirement is to commit the entire unit of work.

## 19. Common mistakes

| Mistake | Consequence | How to handle |
|---|---|---|
| Thinking creating an entity saves it | Database has no data | Call save() or template insert |
| Assuming save() always runs UPDATE | Wrong persistence branch selected | Understand new-state detection |
| Assuming save() is an upsert | Unexpected insert/update behavior | Design a dedicated upsert if needed |
| Entity with pre-assigned ID detected as existing | Framework chooses UPDATE | Use version or Persistable appropriately |
| Manually setting version arbitrarily | Breaks optimistic locking or new-state detection | Let Spring Data manage version |
| Ignoring the entity returned from save() | Missing new ID/version or new instance | Continue pipeline with the saved entity |
| Mapping missing columns into a full entity | Missing fields become null/default | Use a DTO/projection |
| Expecting JPA-like dirty checking | In-memory changes are not saved | Call save() explicitly |
| Expecting lazy loading | Relationships are not queried when getters are called | JOIN or separate/batch query |
| Calling subscribe() in callback/service | Detached from lifecycle and transaction | Return a Publisher |
| Using callbacks for complex business logic | Logic is hidden and hard to test | Move into domain/service |
| Using DatabaseClient and expecting auditing to run automatically | Audit fields may remain unset | Assign explicitly or use entity infrastructure |
| Callback emits an error that is mistakenly recovered | Persistence error is masked | Propagate onError or handle intentionally |
| Sending email in an after-save callback | Email does not roll back with the database | Outbox or post-commit processing |

## 20. Practical workflow when reading and saving entities

When implementing a use case, you can determine in order:

1. Is the entity newly created or loaded from the database?
2. Is the ID database-generated or application-assigned?
3. Will Spring Data detect the new state via Persistable, version, or ID?
4. Are callbacks needed before conversion or before saving?
5. Is auditing or a converter needed?
6. Will the entity be written with INSERT or UPDATE?
7. Are version and optimistic locking present?
8. After save(), does the pipeline use the returned entity?
9. When reading, does the query select all columns for the entity?
10. If only partial data is needed, is a DTO/projection being used?
11. Is dirty checking or lazy loading being expected mistakenly?
12. Do the operations need to be in the same transaction?
13. How are errors and cancellation handled?
14. Are there any raw SQL write paths that need to manage auditing/version manually?

This workflow helps clearly separate the responsibilities of the domain object, mapping infrastructure, callbacks, repository, transaction manager, and database.

## 21. Key takeaways

- An entity created in memory is not yet saved in the database.
- save() determines whether an entity is new or existing and then chooses INSERT or UPDATE; it is not an upsert by default.
- New-state detection uses Persistable.isNew(), the version property, or the ID in that priority order.
- BeforeConvertCallback runs before converting the entity into write data; BeforeSaveCallback can work with OutboundRow.
- Mapping metadata, converters, and annotations determine how Java properties become database columns.
- After saving, AfterSaveCallback can participate in lifecycle processing; use the entity returned from save() to obtain the new ID/version.
- @Version supports optimistic locking; do not assign version arbitrarily.
- Auditing must be enabled and configured with an appropriate auditor; raw SQL does not automatically trigger entity auditing callbacks.
- On read, a row is mapped into an entity and can pass through AfterConvertCallback.
- A partial projection is not a complete entity; do not pass an object missing columns into save().
- Spring Data R2DBC does not have a persistence context, dirty checking, or lazy loading in the way JPA typically provides.
- To save changes after reading, you must call save() or an explicit update statement.
- Callbacks are suited for lifecycle-bound technical processing; domain rules and multi-step use cases belong in domain/service layers.
- Reactive pipelines must be composed; do not manually subscribe or block in services/callbacks.
- A transaction only protects database operations participating in the same transaction manager/ConnectionFactory; external side effects require separate design.
