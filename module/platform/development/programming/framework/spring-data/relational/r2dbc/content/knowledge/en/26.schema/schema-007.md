# Defaults, Generated Columns, and Their Impact on Entity Mapping

In relational schema design, the database can supply a column's value on insert, auto-increment primary keys, compute a column from other columns, or update metadata via triggers. These mechanisms keep data consistent even when multiple applications write to the same database. However, they directly affect how Spring Data R2DBC builds SQL statements and maps result rows back to entities.

The key distinction is between default values and generated values. `DEFAULT` supplies a value only when an insert statement omits the column or explicitly specifies the `DEFAULT` keyword; an explicit SQL `NULL` generally does not trigger the default. Identity or generated columns have their own rules and should typically not be written directly by the application. On entities, annotations such as `@Id`, `@ReadOnlyProperty`, `@InsertOnlyProperty`, `@Transient`, and `@Column` control which properties participate in mapping and persistence writes.

## 1. Types of Database-Managed Values

The database can produce or update values in several ways. They may look similar from the application's perspective, yet they carry different semantics.

| Mechanism | When Applied | Example | Should App Write Directly? |
|---|---|---|---|
| `DEFAULT` | When insert omits column or specifies `DEFAULT` | `status DEFAULT 'NEW'` | Usually let database fill if default is desired |
| Identity/sequence | When inserting a new row | `id GENERATED ... AS IDENTITY` | Usually do not assign ID if database-managed |
| Generated/computed column | On insert/update of source columns | `line_total AS (quantity * unit_price)` | Do not write directly to computed column |
| Trigger-generated value | When trigger fires on insert/update | `created_at`, `updated_at`, audit metadata | Depends on rules; if trigger is authoritative, app should not overwrite |
| Application-assigned value | Before insert/update | `status`, `display_name` | Application is responsible for supplying it |

### 1.1. DEFAULT Is a Fallback Value When Unspecified

Example schema:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(32) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

When an insert supplies only `order_code`, the database fills `status` and `created_at`:

```sql
INSERT INTO orders (order_code)
VALUES ('ORD-000123');
```

Conversely, if the statement specifies `NULL` for `status`, the default is not used:

```sql
INSERT INTO orders (order_code, status)
VALUES ('ORD-000123', NULL);
```

Because `status` is `NOT NULL`, the statement above fails. If the column were nullable, the stored result would be `NULL`, not `'NEW'`.

You can explicitly request the default:

```sql
INSERT INTO orders (order_code, status)
VALUES ('ORD-000123', DEFAULT);
```

Key distinction to remember:

- Omit the column from the insert list: the database can apply the default.
- Specify `DEFAULT`: instructs the database to apply the column's default.
- Bind or write `NULL`: passes an explicit null value; standard defaults are not triggered.

## 2. How DEFAULT Affects INSERTs Generated by Spring Data R2DBC

Spring Data R2DBC generates SQL from entity metadata. For mapped persistent properties, the framework may include the column in the insert statement and bind the value from the entity. If a Java property is `null`, do not assume the framework automatically omits the column so the database applies a default. Depending on the write path, version, and mapping, null may be sent as an explicit SQL `NULL`.

Example entity:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @Column("created_at") Instant createdAt
) {
}
```

If an entity is instantiated with `status == null` and `createdAt == null`, whether these two properties are omitted to use defaults or bound as null depends on how mapping/insert is configured. Do not rely on assuming `null` always means "omit the column". Inspect the generated SQL and use appropriate annotations or insert patterns.

### 2.1. Using @ReadOnlyProperty for Database-Managed Values

`@ReadOnlyProperty` marks a property as readable from the database but not written to the database through Spring Data mapping. It fits columns automatically created or updated by the database, such as:

- Columns with defaults that the application always wants the database to supply.
- Generated/computed columns.
- Trigger-managed columns.
- Read-only metadata the application needs to receive when querying entities.

Example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt
) {
}
```

With `createdAt` annotated as `@ReadOnlyProperty`, Spring Data can still read the `created_at` column and map it onto the record, but excludes it from regular entity insert/update operations. On insert, the database can apply `DEFAULT CURRENT_TIMESTAMP`; on update, the application does not overwrite the database-managed value.

In exchange, the application cannot use that property to explicitly write an arbitrary timestamp via `save`. If a use case requires manual writes, design a separate write path or choose another model instead of marking it read-only everywhere.

### 2.2. @ReadOnlyProperty vs. @Transient

These two annotations are not interchangeable:

| Annotation | Read from Database | Write to Database | Purpose |
|---|---:|---:|---|
| `@ReadOnlyProperty` | Yes | No | Persistent property managed by the database or another source |
| `@Transient` | No | No | Property existing only on the Java object, not part of schema mapping |

For instance, a `totalAmount` computed by the database from other columns needs to be read back into the entity and can use `@ReadOnlyProperty`. A `formattedLabel` property computed solely in Java with no corresponding column should use `@Transient` or be excluded from the persistence constructor appropriately.

### 2.3. @InsertOnlyProperty for Properties Written Only on Insert

`@InsertOnlyProperty` marks a property to be written during inserts only, and excluded from updates. It is useful for values supplied by the application at creation time that must remain unchanged afterward, such as an intake channel code or an initial value captured at creation.

```java
import org.springframework.data.annotation.InsertOnlyProperty;

@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        @InsertOnlyProperty
        @Column("source_channel") String sourceChannel,
        String status
) {
}
```

`sourceChannel` can still be written on insert if the entity provides a value; on update, Spring Data does not overwrite this property. This annotation does not mean "omit the column to trigger a database default". If the goal is to always let the database generate the value, `@ReadOnlyProperty` is more suitable.

## 3. Identity Columns and Generated Primary Keys

### 3.1. Declaring a Database-Assigned ID

PostgreSQL example:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE
);
```

Entity:

```java
@Table("customers")
public record CustomerEntity(
        @Id Long id,
        String email
) {
}
```

When creating a new entity, `id` is typically `null`. Spring Data recognizes the new entity and executes an insert; the database assigns an ID via the identity strategy. `save` emits the saved entity, usually populated with the ID from the generated key returned by the driver.

```java
CustomerEntity draft = new CustomerEntity(null, "an@example.com");

return customerRepository.save(draft)
        .map(saved -> {
            // Use saved.id(); do not assume draft was mutated in place.
            return saved;
        });
```

With immutable entities like records, the new ID value appears in the instance emitted by the publisher. Always use the entity returned by `save` in subsequent steps.

### 3.2. A Non-Null ID Usually Means the Entity Already Exists

Under default new-entity detection, a non-null ID usually makes Spring Data treat the entity as existing and choose an update. If the application assigns IDs before insert, pay attention to new/existing state detection rules. A `@Version` property can participate in entity state detection; keep ID/version design consistent and verify behavior for your Spring Data version.

Do not assign a fake ID just to bypass generated keys. When using application-generated UUIDs, choose an appropriate ID strategy and ensure the repository knows the entity is new through a Spring Data-supported mechanism.

### 3.3. GENERATED BY DEFAULT and GENERATED ALWAYS

Some databases support two identity policies:

- `GENERATED BY DEFAULT`: the database generates an ID when the application supplies none; explicit values may be allowed per database rules.
- `GENERATED ALWAYS`: the database requires the identity value to be database-generated, barring special permitted override syntax.

Choose the policy matching your ID allocation design. If IDs are always database-managed, never send manual values from the application. Exact syntax differs across PostgreSQL, SQL Server, MySQL, and other engines.

### 3.4. Returning Generated Values Depends on Driver and Dialect

Spring Data R2DBC uses the R2DBC driver and dialect's generated-value support to retrieve IDs after insert. Support varies by database and driver. Generated IDs are the standard case handled by the framework, yet you should not generalize that every default, trigger, or generated expression column is automatically returned during `save`.

If the application needs generated values other than the ID, confirm whether the dialect/driver returns those columns. When they are not returned, re-read the entity after insert in a subsequent query or use SQL with `RETURNING` if supported by the database and appropriate for your query path.

## 4. Generated/Computed Columns

A generated column is a column whose value the database computes from an expression over other columns. The application should not send values to this column because the database is its sole generator.

PostgreSQL example:

```sql
CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    line_total NUMERIC(19, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
```

Entity:

```java
@Table("order_lines")
public record OrderLineEntity(
        @Id Long id,
        Integer quantity,
        @Column("unit_price") BigDecimal unitPrice,
        @ReadOnlyProperty
        @Column("line_total") BigDecimal lineTotal
) {
}
```

`lineTotal` is read from the database but never written from the entity. Whenever `quantity` or `unitPrice` changes, the database recalculates the value according to the generated column rule.

### 4.1. Generated Columns vs. DEFAULT

`DEFAULT` applies only when an insert omits a value for the column. A generated column is computed from its declared expression and can recalculate whenever source columns change.

For example:

- `status DEFAULT 'NEW'`: initial default value; afterward the application can update `status`.
- `line_total GENERATED ALWAYS AS (quantity * unit_price)`: computed from two source columns; the application never updates `line_total` directly.

### 4.2. Do Not Use @Transient for Generated Columns You Need to Read

If `lineTotal` is marked `@Transient`, Spring Data will not map the `line_total` column from the database into the entity. The application will not receive the computed value unless mapped manually via a projection or SQL callback. `@ReadOnlyProperty` is far more suitable when the column must be read but not written.

### 4.3. Generated Expressions and Database Limitations

Generated column capabilities, permitted expressions, stored vs. virtual behavior, and update recalculation vary across database engines. Some databases only allow deterministic expressions or restrict referencing certain columns. Check schema documentation for your target database and corresponding migrations.

## 5. Trigger-Generated Values

Triggers can populate or update metadata on insert/update. For example, a trigger setting `created_at` on insert and `updated_at` on every row modification.

```sql
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);
```

A `BEFORE INSERT OR UPDATE` trigger can assign `NEW.created_at` on insert and `NEW.updated_at` on every update. Corresponding entity:

```java
@Table("documents")
public record DocumentEntity(
        @Id Long id,
        String title,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt,
        @ReadOnlyProperty
        @Column("updated_at") Instant updatedAt
) {
}
```

When triggers are the authoritative timestamp source, mark these columns read-only so entity writes do not overwrite trigger values. If the application also uses Spring Data auditing (`@CreatedDate`, `@LastModifiedDate`) on the same columns, choose one clear source of ownership. Two mechanisms writing the same column can yield execution-order-dependent results.

### 5.1. Triggers and Returned Values After Insert/Update

Some databases/drivers can return trigger-modified rows via `RETURNING` or generated-value mechanisms. In other cases, only the ID is returned, excluding trigger-populated columns. Never assume the entity emitted by `save` always includes every trigger-generated value.

If fresh values are needed, re-read by ID after insert/update:

```java
return documentRepository.save(document)
        .flatMap(saved -> documentRepository.findById(saved.id()));
```

Re-reading incurs an extra query round-trip. If immediate post-write consistency is required, execute within an appropriate transaction and verify database/driver behavior. For custom SQL, `RETURNING` can be used where supported by the dialect.

## 6. Mapping Generated Values in Spring Data R2DBC

### 6.1. Role of @Column

`@Column` specifies the column name matching the Java property and can control column name quoting per configuration. It does not make a column generated, tell the database to use a default, or prevent writing values.

Example:

```java
@Column("created_at") Instant createdAt
```

only maps `createdAt` to `created_at`. To make the property read-only, use appropriate metadata like `@ReadOnlyProperty`; for a database default to apply, the schema must define a default and the insert statement must not provide an explicit value for that column.

### 6.2. Role of @ReadOnlyProperty

This annotation suits persistent columns read from the database but not written through Spring Data. Use it for generated columns, trigger-managed columns, or database-supplied defaults. The property can still appear in select results and materialize into entities.

### 6.3. Role of @InsertOnlyProperty

This annotation writes the property only on insert and skips it on update. Use it when the application supplies an initial value that should stay preserved. It is not a general-purpose way to omit nulls and trigger database defaults.

### 6.4. Role of @Transient

`@Transient` properties sit outside persistence mapping. Spring Data neither reads nor writes them as columns. Use it for Java-computed data or temporary state absent from the schema.

### 6.5. Role of @Id and @Version

`@Id` marks the primary key; when the database generates the key, Spring Data/driver can populate the generated ID on the resulting entity. `@Version` supports optimistic locking and is managed by Spring Data across supported persistence operations. Both carry specific semantics and do not replace `@ReadOnlyProperty` for regular computed columns.

## 7. Defaults Apply Only on Insert, Not Automatically on Update

A schema `DEFAULT` normally applies when an insert omits the column. If the application later updates that column to `NULL`, the database does not automatically replace null with the default.

Example:

```sql
UPDATE orders
SET status = NULL
WHERE id = :id;
```

This statement writes null if the schema allows it, or fails if the column is `NOT NULL`. It does not reset status back to `'NEW'`.

To restore a default via SQL, use:

```sql
UPDATE orders
SET status = DEFAULT
WHERE id = :id;
```

Support and syntax for `SET column = DEFAULT` depend on the database. If an API offers a "reset to default" action, model that action explicitly rather than overloading null as an ambiguous signal.

## 8. Distinguishing Null, Omitted, and Default Values in APIs

An update request may need to distinguish three states:

1. Property omitted: keep the current value unchanged.
2. `null` sent: clear the value if the column is nullable and business rules permit.
3. Concrete value sent: replace with that value.

For insert requests, there may also be the intent "let the database apply its default". A plain DTO with a nullable field cannot always distinguish all these cases. When needed, model presence explicitly using wrappers like `FieldUpdate<T>`, JSON Merge Patch semantics, or dedicated commands.

Command design example:

```java
public sealed interface FieldValue<T> {
    record Omitted<T>() implements FieldValue<T> {}
    record ExplicitNull<T>() implements FieldValue<T> {}
    record Present<T>(T value) implements FieldValue<T> {}
}
```

The Service layer interprets each state and decides whether to preserve, write null, write a value, or omit the column so the database uses its default. Do not collapse all three states into `null` before the persistence layer sees the command.

## 9. Using DatabaseClient When Explicit DEFAULT Control Is Needed

When dynamically choosing between omitting a column and specifying `DEFAULT`, custom SQL expresses intent more clearly than standard entity mapping.

### 9.1. Insert Omitting a Column

```java
return databaseClient.sql("""
        INSERT INTO orders (order_code)
        VALUES (:orderCode)
        RETURNING id, order_code, status, created_at
        """)
        .bind("orderCode", orderCode)
        .map((row, metadata) -> new OrderInsertResult(
                row.get("id", Long.class),
                row.get("order_code", String.class),
                row.get("status", String.class),
                row.get("created_at", OffsetDateTime.class)))
        .one();
```

This example uses PostgreSQL's `RETURNING` syntax to retrieve columns after insert. `RETURNING` is not portable SQL across every database; use the generated-values mechanism suited to other dialects/drivers. The Java type read from `created_at` also needs verification against your driver and registered conversions.

### 9.2. Using Explicit DEFAULT

```java
return databaseClient.sql("""
        INSERT INTO orders (order_code, status)
        VALUES (:orderCode, DEFAULT)
        RETURNING id, order_code, status
        """)
        .bind("orderCode", orderCode)
        .map((row, metadata) -> /* map result */)
        .one();
```

The `DEFAULT` keyword cannot be bound as a parameter value—it is SQL syntax. If column choices vary, select among predefined application SQL templates and safely bind data values; never concatenate raw request strings into SQL.

### 9.3. Splitting Insert Paths by Choice

If a request allows the client or business logic to optionally pick an initial status, you can have two insert statements:

- With status: insert `(order_code, status)` with `:status`.
- Using default: insert only `(order_code)` or use `DEFAULT`.

Both statements must bind values safely. Which statement executes is decided by an internal enum/command, never arbitrary SQL fragments from the client.

## 10. Generated Values and Immutable Entities

Immutable entities lack setters to receive database-generated values. Spring Data can instantiate a new instance via constructor mapping or an appropriate wither mechanism to carry the generated ID/returned values.

Record example:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("order_code") String orderCode,
        String status,
        @ReadOnlyProperty
        @Column("created_at") Instant createdAt
) {
}
```

After saving:

```java
return repository.save(new OrderEntity(
        null, "ORD-000123", "NEW", null));
```

Use the instance emitted by `save`. However, merely using a record does not guarantee every generated column is returned by the driver. If `createdAt` is missing on the returned instance, re-read by ID or use SQL with an appropriate generated-value retrieval mechanism.

For immutable classes with multiple constructors, ensure Spring Data picks the right persistence constructor via convention or `@PersistenceCreator`. Parameter names must match Java properties, while `@Column` handles database column names.

## 11. Auditing and Database Defaults Can Conflict

Spring Data auditing can populate `@CreatedDate` and `@LastModifiedDate` prior to writing an entity. The database may also define `DEFAULT CURRENT_TIMESTAMP` or timestamp-updating triggers.

If both manage the same column, pick one authoritative source:

- **Application-managed:** use `@CreatedDate`/`@LastModifiedDate`; the database may omit defaults or keep them strictly as fallbacks for other writers.
- **Database-managed:** use `@ReadOnlyProperty` on trigger/default-managed columns; do not let auditing write the same property.
- **Multiple independent writers:** consider trigger/database-level auditing so every writer follows the same rule.

Do not place `@CreatedDate` and `@ReadOnlyProperty` on the same property if auditing callbacks are meant to write the column; the two annotations express conflicting write policies. Decide ownership clearly before defining the entity.

## 12. Testing Defaults and Generated Columns

Mocked repositories cannot verify whether the database applies defaults or generated expressions properly. Integration tests against the real schema and driver are required.

### 12.1. Testing Database Defaults

Create an entity omitting read-only columns with defaults, insert via the Repository, then read back and verify the database assigned the values:

```java
StepVerifier.create(orderRepository.save(newOrder))
        .assertNext(saved -> {
            assertThat(saved.id()).isNotNull();
        })
        .verifyComplete();

StepVerifier.create(orderRepository.findById(savedId))
        .assertNext(found -> {
            assertThat(found.status()).isEqualTo("NEW");
            assertThat(found.createdAt()).isNotNull();
        })
        .verifyComplete();
```

This illustration requires capturing `savedId` from the returned entity in an actual test. If generated columns are returned by the driver immediately after insert, `saved` can be asserted directly; otherwise, a follow-up select verifies what was persisted.

### 12.2. Testing Explicit Nulls

Use `DatabaseClient` or test SQL to insert `NULL` into a nullable column and verify the stored value is null rather than the default. This is an important test proving the difference between omission and explicit null.

### 12.3. Testing Generated Columns

Insert/update source columns, then read back `line_total`. Verify the database computes it accurately and the application does not try to write to the generated column. If an SQL update attempts to alter a generated column, the database typically rejects it.

### 12.4. Testing Trigger-Generated Values

Perform inserts and updates, then read back timestamps/actors. Verify triggers fire on the intended operations and trigger-generated values are not overwritten by the application.

### 12.5. Testing Entity Mapping

Verify:

- `@ReadOnlyProperty` still reads columns into entities.
- `@ReadOnlyProperty` omits columns from regular inserts/updates.
- `@InsertOnlyProperty` is written on insert and skipped on update.
- `@Transient` does not participate in persistence reads/writes.
- `@Column` maps column names that differ from property names.
- Generated IDs are received from `save` and application code uses the returned instance.

## 13. Common Mistakes

### Expecting Java Null to Trigger DEFAULT

If the SQL statement still includes the column and binds `NULL`, the database does not use the default. Omit the column from insert or use explicit `DEFAULT`.

### Using @Transient for Generated Columns That Need to Be Read

`@Transient` excludes the property from mapping. Use `@ReadOnlyProperty` if the column needs to be read without being written.

### Using @InsertOnlyProperty to Trigger Defaults

This annotation only prevents writing the property on update; it is still written on insert if present. To let the database always generate the column, use read-only mapping or an SQL insert that omits the column.

### Assuming @Column Makes a Column Read-Only

`@Column` primarily defines column names and related mapping details. It does not replace `@ReadOnlyProperty`.

### Attempting to Write to Generated/Computed Columns

The database may reject the statement because the column is computed automatically. Mark it read-only and write only source columns.

### Expecting Every Trigger Value Back from save

Drivers/dialects may only return generated IDs or a supported subset of columns. Re-read the entity or use `RETURNING` when supported by the database.

### Thinking DEFAULT Applies to UPDATE

Defaults do not re-run when updating a column to null. Use `SET column = DEFAULT` if supported by the database and business logic requires resetting.

### Using Both Auditing Callbacks and Triggers on the Same Column

Two write sources can overwrite one another. Choose one primary owner or define explicit ordering and scope.

### Reusing the Pre-Save Entity Reference After save

Immutable entities do not receive generated IDs/values in place. Use the instance emitted by the publisher or re-read by ID.

### Testing Only with Unit Tests

Defaults, identities, generated columns, and triggers are database/driver behaviors. Integration tests against the real database engine are required.

## 14. Workflow for Designing Entities with Database-Managed Columns

1. Classify every column: application-supplied, database default, identity, generated expression, or trigger-managed.
2. Decide whether defaults apply only on insert or require resetting on update.
3. Design the schema with appropriate data types, nullability, default expressions, and generation rules.
4. Annotate database-assigned primary keys with `@Id`.
5. Use `@ReadOnlyProperty` for readable columns where the database is the authoritative writer.
6. Use `@InsertOnlyProperty` for values supplied by the app on insert and preserved on update.
7. Use `@Transient` for properties absent from the schema.
8. Use `@Column` to map property names to column names; do not confuse it with read-only policies.
9. Inspect actual insert SQL to confirm default columns are omitted rather than bound as null.
10. Verify the driver/dialect returns generated IDs and required generated values.
11. If values are not returned immediately, re-read the entity or use database-appropriate `RETURNING` SQL.
12. Write migrations and integration tests covering insert, update, null, default, generated expressions, and triggers.

## 15. Checklist

- [ ] Distinguished default, identity, generated column, and trigger-generated values.
- [ ] Understood that omission, `DEFAULT`, and explicit `NULL` have different meanings.
- [ ] Not assuming a null Java property automatically triggers a database default.
- [ ] `@ReadOnlyProperty` is used for columns read from the DB but not written via mapping.
- [ ] `@InsertOnlyProperty` is used only for values written on insert and preserved on update.
- [ ] `@Transient` is used only for properties excluded from persistence mapping.
- [ ] `@Column` is not confused with generated/read-only policies.
- [ ] Generated IDs are taken from the entity returned by `save`.
- [ ] Generated columns are not written directly by the application.
- [ ] Generated values beyond IDs are verified for the driver/dialect.
- [ ] Auditing callbacks and triggers do not accidentally write the same column.
- [ ] Raw SQL/DatabaseClient handles defaults and audit columns explicitly when needed.
- [ ] APIs distinguish omitted values, explicit null, and default requests when required by business rules.
- [ ] Integration tests run against the target database/driver.

Defaults and generated columns let the database enforce data rules in one place, but Spring Data R2DBC can only map correctly when entities clearly declare which columns are written and which are read-only. Understanding the differences between omitting a column, sending null, using `DEFAULT`, identities, computed columns, and triggers prevents subtle insert/update bugs. By properly using `@ReadOnlyProperty`, `@InsertOnlyProperty`, `@Transient`, and `@Id`—and verifying generated values with your driver and dialect—entities can accurately reflect the state persisted by the database.
