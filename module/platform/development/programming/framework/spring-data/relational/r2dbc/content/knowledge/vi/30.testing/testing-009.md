# Kiểm thử mapping, converter, callback và auditing

Spring Data R2DBC chuyển đổi dữ liệu giữa hàng trong relational database và object Java. Quá trình này bao gồm đọc metadata của entity, ánh xạ tên bảng/cột, chuyển kiểu dữ liệu, gọi entity callback và cập nhật các trường auditing. Một repository test chỉ kiểm tra rằng save hoặc findById không phát lỗi là chưa đủ để chứng minh toàn bộ quy trình hoạt động đúng.

Nên chia kiểm thử thành các lớp có mục tiêu rõ ràng:

- **Mapping:** entity được ánh xạ đúng bảng, cột, khóa, constructor và quan hệ dữ liệu.
- **Converter:** kiểu domain được chuyển đúng sang kiểu database và ngược lại.
- **Entity callback:** callback được gọi đúng thời điểm, thay đổi entity/OutboundRow đúng như hợp đồng.
- **Auditing:** created/modified date và actor được điền đúng, kể cả trong reactive context.
- **Đường ghi trực tiếp:** xác nhận SQL trực tiếp không tự chạy entity callback hoặc auditing nếu không có cơ chế riêng.

Unit test phù hợp để kiểm tra logic converter và callback độc lập. Integration test với R2DBC driver và database thật phù hợp để kiểm tra mapping, SQL type, callback lifecycle, transaction và auditing end-to-end.

## 1. Những phần cần kiểm thử trong Spring Data R2DBC

Khi gọi repository save hoặc findById, nhiều thành phần phối hợp:

1. Spring Data đọc metadata từ entity như @Table, @Column, @Id và @Version.
2. Mapping context xác định property, tên bảng, tên cột và constructor dùng để tạo object.
3. Mapping converter chuyển giá trị Java thành giá trị database khi ghi, hoặc chuyển giá trị hàng database thành Java khi đọc.
4. Entity callback có thể thay đổi entity hoặc dữ liệu chuẩn bị ghi trước/sau thao tác.
5. Auditing callback có thể điền actor và timestamp vào các property có annotation auditing.
6. R2DBC driver bind tham số, thực thi SQL và chuyển kết quả thành row.

Một lỗi mapping có thể chỉ xuất hiện khi dùng database cụ thể. Ví dụ, kiểu Instant có thể được map khác nhau tùy cột timestamp và dialect; converter hoạt động trong unit test nhưng SQL column type không tương thích; hoặc tên cột viết hoa/được quote không giống schema.

### 1.1. Bản đồ kiểm thử

| Thành phần | Kiểm tra chính | Loại test phù hợp |
| --- | --- | --- |
| Entity metadata | Table, column, ID, constructor, version | Unit test metadata khi cần; integration test |
| Reading converter | Database value thành domain value | Unit test converter và integration round-trip |
| Writing converter | Domain value thành database value | Unit test converter và integration round-trip |
| BeforeConvert callback | Thay đổi entity trước khi mapping | Unit test callback và repository integration test |
| BeforeSave callback | Thay đổi OutboundRow trước khi ghi | Unit test callback và database integration test |
| AfterSave callback | Phản ứng sau khi ghi thành công | Integration test |
| AfterConvert callback | Bổ sung/chuẩn hóa entity sau khi đọc | Integration test |
| Auditing | Created/modified date và actor | Integration test với auditing config |
| Direct SQL | Không giả định callback/auditing tự chạy | Integration test |
| Transaction | Rollback khi callback hoặc thao tác sau lỗi | Integration test với database thật |

Không cần kiểm thử mọi framework internals. Hãy tập trung vào hợp đồng mà ứng dụng phụ thuộc và các lỗi có thể làm dữ liệu sai.

## 2. Chuẩn bị entity mẫu có mapping rõ ràng

Ví dụ entity có tên bảng/cột khác tên property:

~~~java
@Table("customer_profiles")
public class CustomerProfile {

    @Id
    private Long id;

    @Column("display_name")
    private String displayName;

    @Column("email_address")
    private String email;

    @Column("active")
    private Boolean active;

    @Version
    private Long version;

    // Constructor, getter và setter được lược bớt.
}
~~~

Schema tương ứng:

~~~sql
CREATE TABLE customer_profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(160) NOT NULL,
    email_address VARCHAR(240),
    active BOOLEAN NOT NULL,
    version BIGINT NOT NULL
);
~~~

Tên bảng customer_profiles và các cột display_name, email_address được khai báo tường minh. Integration test cần xác nhận repository thực sự ghi/đọc đúng các tên này.

### 2.1. Kiểm tra round-trip mapping

Một bài test cơ bản:

~~~java
@Test
void shouldWriteAndReadMappedColumns() {
    CustomerProfile input = new CustomerProfile(
            "Nguyen An",
            "an@example.test",
            true);

    StepVerifier.create(repository.save(input)
                    .flatMap(saved -> repository.findById(saved.getId())))
            .assertNext(found -> {
                assertThat(found.getDisplayName()).isEqualTo("Nguyen An");
                assertThat(found.getEmail()).isEqualTo("an@example.test");
                assertThat(found.getActive()).isTrue();
            })
            .verifyComplete();
}
~~~

Test này kiểm tra đường ghi và đọc qua mapping converter cùng driver. Cần chuẩn bị schema và dọn dữ liệu giữa các test để kết quả ổn định.

### 2.2. Kiểm tra ID được sinh

Khi database tự sinh ID, entity đầu vào thường chưa có ID. Sau save, kiểm tra ID đã được gán và có thể dùng để đọc lại:

~~~java
StepVerifier.create(repository.save(input))
        .assertNext(saved -> {
            assertThat(saved.getId()).isNotNull();
            assertThat(saved.getVersion()).isNotNull();
        })
        .verifyComplete();
~~~

Kiểu ID, cơ chế identity/sequence và giá trị version khởi tạo phụ thuộc database và cấu hình Spring Data. Test nên dựa trên hợp đồng đã chọn, không giả định mọi dialect có cùng giá trị ID/version ban đầu.

## 3. Kiểm thử mapping các kiểu dữ liệu

Các kiểu Java và SQL cần tương thích. Một số mapping phổ biến:

| Java type | Kiểu SQL thường gặp | Điều cần kiểm tra |
| --- | --- | --- |
| String | VARCHAR, TEXT | Độ dài, collation, encoding |
| Integer/Long | INTEGER, BIGINT | Range và overflow |
| BigDecimal | DECIMAL/NUMERIC | Precision, scale và rounding |
| Boolean | BOOLEAN hoặc kiểu tương ứng của database | Giá trị true/false và nullability |
| LocalDate | DATE | Ngày không có timezone |
| LocalDateTime | TIMESTAMP | Không mang timezone |
| Instant | TIMESTAMP WITH TIME ZONE hoặc kiểu phù hợp dialect | Quy ước UTC và độ chính xác |
| UUID | UUID hoặc kiểu binary/character theo database | Format và native support |
| Enum | Thường là VARCHAR hoặc kiểu được cấu hình | Tên enum, converter và thay đổi giá trị |

Không nên chỉ kiểm tra object Java sau khi save nếu schema có thể làm mất precision. Với BigDecimal, hãy kiểm tra giá trị đọc lại và scale theo quy tắc nghiệp vụ. Với timestamp, hãy kiểm tra độ chính xác mà database hỗ trợ.

### 3.1. BigDecimal và precision/scale

Schema:

~~~sql
CREATE TABLE invoices (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    total_amount NUMERIC(12, 2) NOT NULL
);
~~~

Test:

~~~java
BigDecimal amount = new BigDecimal("123456.70");

StepVerifier.create(invoiceRepository.save(new Invoice(amount))
                .flatMap(saved -> invoiceRepository.findById(saved.getId())))
        .assertNext(found -> {
            assertThat(found.getTotalAmount())
                    .isEqualByComparingTo(new BigDecimal("123456.70"));
        })
        .verifyComplete();
~~~

Nếu nghiệp vụ yêu cầu scale cố định, kiểm tra thêm scale hoặc chuẩn hóa bằng domain constructor. Không dựa vào so sánh BigDecimal bằng equals nếu khác scale nhưng cùng giá trị số; isEqualByComparingTo phù hợp khi chỉ so sánh giá trị.

### 3.2. Timestamp và timezone

Test timestamp nên dùng thời điểm xác định:

~~~java
Instant expected = Instant.parse("2025-02-10T08:30:15Z");
~~~

Lưu và đọc lại bằng database thực tế, sau đó so sánh theo độ chính xác mà cột hỗ trợ. Một số database chỉ lưu microseconds hoặc milliseconds, vì vậy giá trị đọc lại có thể bị cắt phần nano giây.

Nếu ứng dụng thống nhất lưu UTC, hãy xác định rõ kiểu SQL và converter. Không so sánh chuỗi timestamp đã format theo timezone của máy test.

### 3.3. Nullability

Kiểm tra riêng:

- Property nullable được đọc thành null khi cột SQL NULL.
- Property bắt buộc không nhận null nếu schema có NOT NULL.
- Primitive Java không phù hợp với cột có thể null; cân nhắc wrapper type.
- INSERT thiếu giá trị có dùng default database hay gửi NULL, tùy mapping và câu SQL.

Một hàng tồn tại nhưng email null vẫn là một kết quả entity. Nó khác hoàn toàn với findById không tìm thấy và trả Mono.empty().

## 4. Kiểm thử constructor và immutable entity

Spring Data có thể tạo entity thông qua constructor phù hợp. Với immutable object hoặc Java record, tên/kiểu tham số cần tương thích với property metadata và quy tắc mapping của phiên bản đang dùng.

Ví dụ record:

~~~java
@Table("country_codes")
public record CountryCode(
        @Id Long id,
        @Column("country_code") String code,
        String name
) {
}
~~~

Integration test nên:

1. Insert một record.
2. Xác nhận ID được trả về theo chiến lược sinh ID.
3. Đọc lại record.
4. Xác nhận tất cả property được map đúng, kể cả tên cột khác tên property.

Nếu dùng constructor nhiều tham số thay vì record, kiểm tra parameter name metadata và annotation constructor nếu cần. Đừng để test chỉ chạy với entity mutable có no-args constructor rồi suy ra immutable mapping cũng đúng.

## 5. Kiểm thử custom converter

Custom converter dùng khi kiểu domain không được database driver hoặc Spring Data hỗ trợ trực tiếp theo cách ứng dụng cần. Có hai chiều:

- Writing converter: domain value sang kiểu có thể bind vào database.
- Reading converter: kiểu database sang domain value.

Ví dụ domain type Money lưu dưới dạng NUMERIC:

~~~java
public record Money(BigDecimal amount) {

    public Money {
        Objects.requireNonNull(amount, "amount");
        if (amount.scale() > 2) {
            throw new IllegalArgumentException("Money supports at most 2 decimals");
        }
    }
}
~~~

Writing converter:

~~~java
@WritingConverter
public class MoneyWritingConverter
        implements Converter<Money, BigDecimal> {

    @Override
    public BigDecimal convert(Money source) {
        return source.amount();
    }
}
~~~

Reading converter:

~~~java
@ReadingConverter
public class MoneyReadingConverter
        implements Converter<BigDecimal, Money> {

    @Override
    public Money convert(BigDecimal source) {
        return new Money(source);
    }
}
~~~

Đánh dấu hướng đọc/ghi giúp Spring Data tránh nhầm converter khi source và target là kiểu đơn giản hoặc kiểu database native.

### 5.1. Unit test converter độc lập

Writing converter:

~~~java
@Test
void shouldWriteMoneyAsDecimal() {
    MoneyWritingConverter converter = new MoneyWritingConverter();

    BigDecimal value = converter.convert(new Money(new BigDecimal("19.95")));

    assertThat(value).isEqualByComparingTo("19.95");
}
~~~

Reading converter:

~~~java
@Test
void shouldReadDecimalAsMoney() {
    MoneyReadingConverter converter = new MoneyReadingConverter();

    Money value = converter.convert(new BigDecimal("19.95"));

    assertThat(value.amount()).isEqualByComparingTo("19.95");
}
~~~

Unit test xác nhận logic chuyển đổi nhanh và không cần khởi động database. Tuy nhiên, nó không chứng minh Spring Data đã đăng ký converter hoặc driver bind đúng SQL type.

### 5.2. Đăng ký converter với R2DBC

Với cấu hình Java, có thể cung cấp custom conversions theo dialect:

~~~java
@Configuration
public class R2dbcConversionConfiguration {

    @Bean
    R2dbcCustomConversions r2dbcCustomConversions() {
        return R2dbcCustomConversions.of(
                PostgresDialect.INSTANCE,
                List.of(
                        new MoneyWritingConverter(),
                        new MoneyReadingConverter()
                ));
    }
}
~~~

API đăng ký converter có thể thay đổi theo phiên bản Spring Data R2DBC. Nếu dự án dùng AbstractR2dbcConfiguration hoặc Spring Boot auto-configuration, hãy khai báo custom conversions theo extension point được phiên bản đó hỗ trợ và tránh tạo hai bean cấu hình cạnh tranh.

### 5.3. Integration test converter qua repository

Entity:

~~~java
@Table("wallets")
public class Wallet {

    @Id
    private Long id;

    @Column("available_balance")
    private Money availableBalance;

    // Constructor, getter và setter được lược bớt.
}
~~~

Schema:

~~~sql
CREATE TABLE wallets (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    available_balance NUMERIC(14, 2) NOT NULL
);
~~~

Test:

~~~java
@Test
void shouldRoundTripMoneyThroughR2dbcMapping() {
    Wallet wallet = new Wallet(new Money(new BigDecimal("250.40")));

    StepVerifier.create(walletRepository.save(wallet)
                    .flatMap(saved -> walletRepository.findById(saved.getId())))
            .assertNext(found -> assertThat(found.getAvailableBalance().amount())
                    .isEqualByComparingTo("250.40"))
            .verifyComplete();
}
~~~

Test này xác nhận converter được Spring Data sử dụng theo cả hai chiều và database có thể lưu kiểu tương ứng.

### 5.4. Kiểm thử lỗi converter

Converter có thể từ chối dữ liệu không hợp lệ. Hãy kiểm tra:

- Giá trị domain không hợp lệ bị từ chối trước khi ghi.
- Dữ liệu legacy trong database không thể chuyển thành domain được xử lý có chủ đích.
- Exception không bị nuốt thành Mono.empty().
- Response/API không để lộ raw database value hoặc stack trace.

Nếu converter có thể phát sinh lỗi khi đọc một hàng, cần xác định API trả lỗi dữ liệu hay cách ly bản ghi lỗi trong batch import/report.

## 6. Kiểm thử enum và kiểu domain

Nếu enum được lưu bằng tên:

~~~java
public enum CustomerStatus {
    NEW,
    ACTIVE,
    SUSPENDED
}
~~~

Hãy kiểm thử round-trip để xác nhận giá trị được ghi/đọc đúng. Cân nhắc tác động khi đổi tên enum hoặc xóa giá trị đã tồn tại trong database.

Nếu tên enum không phải hợp đồng lưu trữ ổn định, dùng converter sang code riêng:

~~~java
public enum CustomerStatus {
    NEW("N"),
    ACTIVE("A"),
    SUSPENDED("S");

    private final String code;

    CustomerStatus(String code) {
        this.code = code;
    }

    public String code() {
        return code;
    }

    public static CustomerStatus fromCode(String code) {
        return Arrays.stream(values())
                .filter(value -> value.code.equals(code))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException(
                        "Unknown customer status code"));
    }
}
~~~

Converter đọc/ghi cần được test cho mọi code hợp lệ và code không xác định. Nếu hệ thống có dữ liệu cũ, test migration và compatibility khi thêm enum value.

## 7. Kiểm thử entity callback

Entity callback cho phép ứng dụng thực hiện logic tại các điểm trong lifecycle lưu/đọc entity. Các callback phổ biến trong Spring Data Relational/R2DBC gồm:

- BeforeConvertCallback: trước khi entity được chuyển thành dữ liệu relational.
- BeforeSaveCallback: trước khi dữ liệu được gửi để lưu, có thể nhận OutboundRow.
- AfterSaveCallback: sau khi thao tác lưu hoàn tất.
- AfterConvertCallback: sau khi một hàng được chuyển thành entity, tùy API/phiên bản.

Callback trong R2DBC là reactive; implementation trả publisher và không nên gọi block hoặc subscribe bên trong.

### 7.1. BeforeConvertCallback

Ví dụ chuẩn hóa tên trước khi mapping:

~~~java
@Component
public class CustomerNameCallback
        implements BeforeConvertCallback<CustomerProfile> {

    @Override
    public Publisher<CustomerProfile> onBeforeConvert(
            CustomerProfile entity,
            SqlIdentifier table) {

        entity.setDisplayName(entity.getDisplayName().trim());
        return Mono.just(entity);
    }
}
~~~

Callback được gọi trong quy trình lưu entity trước khi chuyển đổi entity thành dữ liệu ghi. Test nên xác nhận giá trị thực sự trong database đã được chuẩn hóa, không chỉ xác nhận callback method trả entity.

### 7.2. Unit test callback

~~~java
@Test
void shouldTrimDisplayNameBeforeConvert() {
    CustomerNameCallback callback = new CustomerNameCallback();
    CustomerProfile customer = new CustomerProfile(
            "  An Nguyen  ", "an@example.test", true);

    StepVerifier.create(Mono.from(callback.onBeforeConvert(
                    customer, SqlIdentifier.unquoted("customer_profiles"))))
            .assertNext(result ->
                    assertThat(result.getDisplayName()).isEqualTo("An Nguyen"))
            .verifyComplete();
}
~~~

Unit test này kiểm tra logic callback riêng. Integration test vẫn cần xác nhận callback được đăng ký trong application context và được gọi bởi repository save.

### 7.3. BeforeSaveCallback và OutboundRow

BeforeSaveCallback có thể thay đổi OutboundRow ngay trước khi lưu. Ví dụ này hữu ích khi cần thêm một giá trị được ghi vào row mà không biểu diễn bằng property entity.

~~~java
@Component
public class CustomerSourceCallback
        implements BeforeSaveCallback<CustomerProfile> {

    @Override
    public Publisher<CustomerProfile> onBeforeSave(
            CustomerProfile entity,
            OutboundRow row,
            SqlIdentifier table) {

        row.put(
                SqlIdentifier.unquoted("write_source"),
                Parameter.from("webflux-api"));
        return Mono.just(entity);
    }
}
~~~

Kiểu Parameter và cách tạo giá trị cần tương thích với phiên bản Spring Data R2DBC. Nếu field write_source có thể được biểu diễn như property entity bình thường, cách đó thường dễ hiểu và dễ test hơn.

### 7.4. Callback phải giữ tính reactive

Không nên:

~~~java
@Override
public Publisher<CustomerProfile> onBeforeConvert(
        CustomerProfile entity,
        SqlIdentifier table) {

    Mono.from(auditClient.record(entity.getId())).block();
    return Mono.just(entity);
}
~~~

Đoạn code blocking có thể làm nghẽn event-loop và phá vỡ lợi ích reactive. Nếu callback thật sự cần publisher phụ thuộc, hãy nối publisher đó vào kết quả callback:

~~~java
@Override
public Publisher<CustomerProfile> onBeforeConvert(
        CustomerProfile entity,
        SqlIdentifier table) {

    return auditClient.validate(entity.getId())
            .thenReturn(entity);
}
~~~

Tuy nhiên, callback chạy trong đường lưu entity; không nên đưa các lời gọi mạng chậm hoặc side effect khó rollback vào callback nếu chúng làm transaction giữ connection lâu. Những nghiệp vụ đó thường phù hợp hơn ở service layer.

### 7.5. Callback và direct SQL

Repository method dùng @Modifying @Query, DatabaseClient.sql hoặc SQL chạy ngoài Spring Data entity save thường không đi qua callback lifecycle của entity. Vì vậy, không kỳ vọng BeforeConvertCallback hoặc auditing callback tự chạy khi câu SQL trực tiếp thay đổi bảng.

Nếu hành vi cần áp dụng cho mọi writer, hãy cân nhắc database trigger. Nếu chỉ cần cho một use case, service có thể cập nhật tường minh.

## 8. Kiểm thử callback được đăng ký trong application context

Có thể dùng một callback test ghi nhận số lần được gọi:

~~~java
@TestConfiguration
static class CallbackTestConfiguration {

    @Bean
    AtomicInteger beforeConvertCalls() {
        return new AtomicInteger();
    }

    @Bean
    BeforeConvertCallback<CustomerProfile> countingCallback(
            AtomicInteger beforeConvertCalls) {

        return (entity, table) -> {
            beforeConvertCalls.incrementAndGet();
            return Mono.just(entity);
        };
    }
}
~~~

Trong integration test, inject counter, gọi repository.save và xác nhận callback được gọi. Sau đó chạy direct SQL update và xác nhận counter không tăng do đường SQL đó không đi qua entity callback.

Không nên dựa vào thứ tự giữa nhiều callback nếu ứng dụng chưa khai báo order rõ ràng. Nếu thứ tự có ý nghĩa, dùng cơ chế order được framework hỗ trợ và viết test kiểm tra thứ tự đó.

### 8.1. Kiểm tra callback lỗi

Nếu callback phát error, thao tác lưu entity có thể không tiếp tục tới database. Có thể kiểm tra:

- Publisher save kết thúc bằng exception mong đợi.
- Không có hàng mới được insert.
- Transaction được rollback nếu thao tác nằm trong transaction.
- Error được giữ nguyên hoặc chuyển thành lỗi application có ý nghĩa.

Callback không nên nuốt lỗi rồi trả entity nếu quy tắc callback là bắt buộc. Điều đó có thể khiến dữ liệu thiếu bước chuẩn hóa hoặc kiểm tra quan trọng.

## 9. Kiểm thử Spring Data auditing

Auditing là một nhóm callback chuyên biệt dùng metadata entity để điền các trường created/modified. Cần kiểm thử cả actor lẫn thời gian và cả create/update.

Entity:

~~~java
@Table("audited_customers")
public class AuditedCustomer {

    @Id
    private Long id;

    private String name;

    @CreatedDate
    @Column("created_at")
    private Instant createdAt;

    @CreatedBy
    @Column("created_by")
    private String createdBy;

    @LastModifiedDate
    @Column("last_modified_at")
    private Instant lastModifiedAt;

    @LastModifiedBy
    @Column("last_modified_by")
    private String lastModifiedBy;

    // Constructor, getter và setter được lược bớt.

~~~

### 9.1. Cấu hình auditing cho test

Một cấu hình test có thể dùng actor và clock xác định:

~~~java
@TestConfiguration
@EnableR2dbcAuditing(
        auditorAwareRef = "testAuditorAware",
        dateTimeProviderRef = "testDateTimeProvider"
)
static class AuditingTestConfiguration {

    static final Instant FIXED_TIME =
            Instant.parse("2025-03-01T10:15:30Z");

    @Bean
    ReactiveAuditorAware<String> testAuditorAware() {
        return () -> Mono.just("test-user");
    }

    @Bean
    DateTimeProvider testDateTimeProvider() {
        return () -> Optional.of(FIXED_TIME);
    }
}
~~~

Dùng thời gian cố định giúp assertion không phụ thuộc tốc độ chạy test. Trong test cần kiểm tra nhiều actor hoặc thời điểm, có thể dùng provider có thể điều khiển được.

### 9.2. Test create

~~~java
@Test
void shouldPopulateCreatedAndModifiedFieldsOnInsert() {
    AuditedCustomer input = new AuditedCustomer("Mai");

    StepVerifier.create(auditedCustomerRepository.save(input))
            .assertNext(saved -> {
                assertThat(saved.getCreatedBy()).isEqualTo("test-user");
                assertThat(saved.getLastModifiedBy()).isEqualTo("test-user");
                assertThat(saved.getCreatedAt())
                        .isEqualTo(AuditingTestConfiguration.FIXED_TIME);
                assertThat(saved.getLastModifiedAt())
                        .isEqualTo(AuditingTestConfiguration.FIXED_TIME);
            })
            .verifyComplete();
}
~~~

Test xác nhận auditing callback đã điền trường trước khi ghi. Cũng nên đọc lại hàng từ database để kiểm tra các giá trị thực sự được lưu.

### 9.3. Test update

Để kiểm tra created fields không bị thay đổi:

1. Tạo entity với actor và thời điểm ban đầu.
2. Đổi actor/time provider sang giá trị mới.
3. Đọc entity, thay đổi một property nghiệp vụ và save.
4. Xác nhận createdAt/createdBy giữ nguyên.
5. Xác nhận lastModifiedAt/lastModifiedBy phản ánh lần update.

Ví dụ kỳ vọng:

~~~text
Sau insert:
  created_by       = creator
  created_at       = T1
  last_modified_by = creator
  last_modified_at = T1

Sau update:
  created_by       = creator
  created_at       = T1
  last_modified_by = editor
  last_modified_at = T2
~~~

Nếu test chỉ dùng một actor/time cố định, nó không chứng minh được trường modified thay đổi. Hãy dùng provider có thể thay giá trị giữa hai lần lưu.

### 9.4. ReactiveAuditorAware phải lấy actor từ đúng context

Nếu ứng dụng dùng Spring Security WebFlux, auditor provider có thể đọc reactive security context:

~~~java
@Bean
ReactiveAuditorAware<String> auditorAware() {
    return () -> ReactiveSecurityContextHolder.getContext()
            .map(SecurityContext::getAuthentication)
            .filter(Authentication::isAuthenticated)
            .map(Authentication::getName);
}
~~~

Test có thể gắn SecurityContext vào Reactor Context:

~~~java
Authentication authentication =
        new UsernamePasswordAuthenticationToken(
                "alice", "n/a", List.of(new SimpleGrantedAuthority("ROLE_USER")));

SecurityContext securityContext =
        new SecurityContextImpl(authentication);

Mono<AuditedCustomer> save = auditedCustomerRepository.save(
        new AuditedCustomer("Test"));

StepVerifier.create(save.contextWrite(
                ReactiveSecurityContextHolder.withSecurityContext(
                        Mono.just(securityContext))))
        .assertNext(saved ->
                assertThat(saved.getCreatedBy()).isEqualTo("alice"))
        .verifyComplete();
~~~

Đoạn test xác nhận context được truyền theo subscription. Không chỉ đặt SecurityContextHolder thread-local trong test imperative rồi kết luận reactive auditing hoạt động.

### 9.5. Không có auditor

Quy định rõ behavior khi không có actor:

- Cho phép audit date nhưng actor null.
- Dùng actor hệ thống cho job nền.
- Từ chối thao tác nếu actor là bắt buộc.

Test từng trường hợp. Không để test vô tình chạy dưới một authentication mặc định khiến actor luôn có giá trị dù production không có context tương ứng.

## 10. Kiểm thử auditing khi dùng direct SQL

Một điểm quan trọng của Spring Data R2DBC: entity auditing callback không tự chạy cho mọi câu DML trực tiếp.

Ví dụ:

~~~java
@Modifying
@Query("UPDATE audited_customers SET name = :name WHERE id = :id")
Mono<Integer> updateNameDirectly(
        @Param("id") Long id,
        @Param("name") String name);
~~~

Test nên:

1. Tạo entity qua repository save và xác nhận auditing đã điền các cột.
2. Ghi lại last_modified_at/last_modified_by.
3. Gọi updateNameDirectly.
4. Đọc lại entity.
5. Xác nhận name đã đổi nhưng audit fields không tự thay đổi nếu query/trigger không cập nhật chúng.

Nếu câu SQL được sửa để bind modifiedAt và modifiedBy, kiểm tra hai trường thay đổi đúng. Nếu database có trigger, kiểm tra trigger bằng mọi đường ghi mà ứng dụng hỗ trợ.

### 10.1. Phân biệt callback với database trigger

Callback là logic trong ứng dụng Spring Data và chỉ chạy khi thao tác đi qua callback lifecycle. Trigger là logic trong database và có thể chạy với nhiều writer khác nhau.

Test nên xác định rõ nguồn nào sở hữu mỗi cột audit. Nếu cả callback và trigger cùng ghi last_modified_at, giá trị cuối có thể do trigger ghi đè callback; test cần phản ánh đúng hợp đồng đã chọn.

## 11. Kiểm thử @Version và callback/auditing kết hợp

Entity có thể dùng cả @Version và auditing:

~~~java
@Table("versioned_documents")
public class VersionedDocument {

    @Id
    private Long id;

    @Version
    private Long version;

    private String title;

    @LastModifiedDate
    @Column("last_modified_at")
    private Instant lastModifiedAt;

    @LastModifiedBy
    @Column("last_modified_by")
    private String lastModifiedBy;

    // Constructor, getter và setter được lược bớt.
}
~~~

Integration test nên xác nhận:

- Insert khởi tạo version và auditing fields theo cấu hình.
- Update với version mới thành công và tăng version.
- Update stale entity thất bại bằng optimistic locking.
- Khi update stale thất bại, dữ liệu và audit fields trong database không bị thay đổi bởi lần ghi thất bại.
- Lần update thành công tiếp theo ghi đúng actor/time.

Không nên chỉ assert exception. Hãy đọc lại database để xác nhận version, nội dung và audit columns vẫn nhất quán.

## 12. Cấu trúc integration test với Testcontainers

Testcontainers cho phép chạy database cùng loại với production trong test. Ví dụ PostgreSQL:

~~~java
@DataR2dbcTest
@Import({
        R2dbcConversionConfiguration.class,
        AuditingTestConfiguration.class
})
class CustomerMappingIntegrationTest {

    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void r2dbcProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.r2dbc.url", () ->
                "r2dbc:postgresql://" + postgres.getHost() + ":"
                        + postgres.getFirstMappedPort() + "/"
                        + postgres.getDatabaseName());
        registry.add("spring.r2dbc.username", postgres::getUsername);
        registry.add("spring.r2dbc.password", postgres::getPassword);
    }

    @Autowired
    CustomerProfileRepository repository;
}
~~~

Ví dụ cần dependency Testcontainers JUnit Jupiter và PostgreSQL module, cùng cấu hình container lifecycle phù hợp với phiên bản Testcontainers của dự án. Tùy phiên bản Spring Boot, có thể dùng service connection thay cho DynamicPropertySource.

### 12.1. Dùng đúng database của production

H2 hoặc mock có thể hữu ích cho test nhanh, nhưng không thay thế được database production khi kiểm tra:

- SQL dialect.
- Native type và converter.
- Timestamp/timezone semantics.
- Identity/sequence.
- Quoting và naming.
- Constraint và transaction behavior.
- Trigger, JSON, UUID hoặc array type.

Nếu production dùng PostgreSQL, integration test mapping quan trọng nên chạy PostgreSQL. Nếu production dùng nhiều database khác nhau, test riêng các dialect thực sự được hỗ trợ.

### 12.2. Chuẩn bị schema test

Có thể dùng migration tool giống production để tạo schema. Điều này giúp test phát hiện mapping lệch với migration.

Nếu test tạo schema bằng script riêng, nguy cơ schema test khác schema triển khai sẽ tăng. Nên chạy cùng Flyway/Liquibase migration hoặc bộ migration mà ứng dụng dùng trong môi trường thật.

### 12.3. Cô lập dữ liệu giữa các test

R2DBC là reactive và test có thể chạy song song. Hãy:

- Dùng ID riêng hoặc truncate bảng trước test khi an toàn.
- Không chia sẻ cùng một row giữa các test chạy đồng thời.
- Dọn dữ liệu theo transaction hoặc fixture rõ ràng.
- Không giả định @Transactional trên test method luôn bao bọc toàn bộ subscription giống cách test JDBC imperative.

Một số test slice có thể tự cấu hình transaction; hãy kiểm tra lifecycle của test framework và không dựa vào rollback tự động nếu chưa xác nhận.

## 13. Kiểm thử repository slice và full application context

Có thể dùng @DataR2dbcTest để tập trung vào repository/mapping, import converter và auditing config cần thiết. Tuy nhiên, slice test có thể không load toàn bộ callback hoặc component scan như ứng dụng thực.

Nên có ít nhất hai nhóm:

1. **Repository slice tests:** kiểm tra mapping, converter, query và callback cần thiết với context nhỏ.
2. **Application integration tests:** khởi tạo cấu hình gần production để kiểm tra auditing, security context, transaction manager và service pipeline.

Nếu callback được khai báo bằng @Component nhưng slice test không scan bean đó, import callback cụ thể vào test context. Đừng nhầm callback không được load với callback được load nhưng không chạy.

## 14. Kiểm thử callback và auditing bằng StepVerifier

StepVerifier kiểm tra publisher phát giá trị, hoàn tất hoặc lỗi theo thứ tự mong đợi.

Ví dụ xác nhận save thành công:

~~~java
StepVerifier.create(repository.save(customer))
        .assertNext(saved -> assertThat(saved.getId()).isNotNull())
        .verifyComplete();
~~~

Ví dụ xác nhận converter/callback phát lỗi:

~~~java
StepVerifier.create(repository.save(invalidCustomer))
        .expectErrorSatisfies(error ->
                assertThat(error).isInstanceOf(IllegalArgumentException.class))
        .verify();
~~~

Nếu lỗi được Spring Data bọc trong exception khác, hãy assert theo exception contract thực tế của phiên bản framework/driver, không chỉ assert một class giả định.

### 14.1. Không gọi block trong test reactive

Tránh:

~~~java
Customer saved = repository.save(customer).block();
~~~

Có thể dùng block trong một số test imperative được thiết kế riêng, nhưng StepVerifier giúp giữ test theo đúng mô hình reactive và dễ kiểm tra error/completion/cancellation. Không gọi block trên event-loop thread.

### 14.2. Kiểm thử publisher chỉ thực thi khi subscribe

Repository publisher thường lazy. Khi test cần xác nhận callback chỉ chạy khi có subscription, có thể dùng counter hoặc PublisherProbe. Tuy nhiên, test lazy behavior của Reactor không thay thế integration test ghi/đọc dữ liệu thật.

## 15. Kiểm thử transaction khi callback hoặc auditing lỗi

Giả sử service lưu entity rồi ghi một audit record trong cùng transaction. Nếu callback hoặc bước audit phát lỗi, dữ liệu nghiệp vụ cần rollback nếu toàn bộ thao tác nằm trong cùng transaction manager và error được truyền ra ngoài.

Ví dụ:

~~~java
@Transactional
public Mono<CustomerProfile> createWithAudit(CustomerProfile customer) {
    return customerRepository.save(customer)
            .flatMap(saved -> auditRepository.save(
                    AuditRecord.created(saved.getId()))
                    .thenReturn(saved));
}
~~~

Test:

1. Cấu hình audit repository phát lỗi sau khi entity đã được save.
2. Gọi service trong transaction thực tế.
3. Xác nhận publisher phát lỗi.
4. Dùng transaction/kết nối mới đọc database.
5. Xác nhận customer và audit record đều không tồn tại nếu rollback được kỳ vọng.

Nếu callback gọi dịch vụ ngoài hoặc publisher phụ thuộc không tham gia database transaction, rollback database không thể hoàn tác side effect ngoài đó. Không dùng callback để tạo một transaction phân tán ngầm.

## 16. Kiểm thử thứ tự callback

Khi có nhiều callback cùng loại hoặc callback ở nhiều giai đoạn, thứ tự có thể ảnh hưởng kết quả. Ví dụ một callback chuẩn hóa tên trước khi callback khác tạo search key.

Hãy:

- Dùng cơ chế order được Spring hỗ trợ nếu thứ tự là yêu cầu.
- Viết test ghi nhận chuỗi callback được gọi.
- Xác nhận dữ liệu cuối cùng trong database.
- Không phụ thuộc thứ tự tình cờ từ component scanning hoặc thứ tự khai báo bean.

Không nên tạo callback có side effect không idempotent. Callback có thể được gọi ở nhiều thao tác lưu và retry; nếu gửi email hoặc publish message trong callback, có nguy cơ side effect lặp hoặc xảy ra trước khi transaction commit.

## 17. Kiểm thử query trực tiếp và template update

Các đường ghi khác nhau cần test riêng vì chúng có lifecycle khác nhau:

| Đường ghi | Mapping entity | Entity callback | Auditing entity |
| --- | --- | --- | --- |
| Repository save(entity) | Có | Có theo lifecycle | Có nếu được cấu hình |
| Entity insert/save qua template | Có | Có theo API/lifecycle | Có nếu được cấu hình |
| @Modifying @Query | Dựa vào SQL/query đã khai báo | Không tự chạy lifecycle save entity | Không tự chạy |
| DatabaseClient | Bind SQL trực tiếp | Không | Không |
| Template update(Query, Update) | Mapping property/cột của update | Không có entity đầy đủ để chạy save callbacks | Không tự điền |

Với mỗi đường ghi đang dùng trong ứng dụng, hãy có một integration test kiểm tra các trường cần thiết như version, last_modified_at, last_modified_by và constraint.

## 18. Những lỗi thường gặp khi kiểm thử mapping và lifecycle

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Unit converter pass nhưng repository đọc sai | Converter chưa được đăng ký hoặc SQL type không tương thích | Integration round-trip trên database thật |
| Giá trị BigDecimal đổi scale | Column precision/scale hoặc converter chưa chuẩn hóa | Kiểm tra schema và quy tắc scale |
| Timestamp lệch hoặc mất nano giây | Database có độ chính xác khác Java | Test theo precision của column và quy ước UTC |
| Property luôn null sau khi đọc | Sai @Column, constructor mapping hoặc converter | Kiểm tra schema, metadata và row mapping |
| Callback unit test pass nhưng save không gọi | Callback bean chưa có trong application context hoặc sai callback type | Kiểm tra test slice/import và repository lifecycle |
| Direct SQL không cập nhật audit | SQL không set audit columns, không có trigger | Ghi tường minh hoặc kiểm thử trigger |
| Auditing actor luôn null | Reactive context không được truyền hoặc auditor provider rỗng | Test với Reactor Context và security context |
| created fields bị ghi đè | SQL/callback/trigger cập nhật sai trường | Tách quy tắc created và last-modified |
| Test pass với H2 nhưng fail production | Khác dialect/type/transaction semantics | Dùng Testcontainers đúng database |
| Callback blocking làm test treo | Dùng block hoặc gọi dịch vụ đồng bộ | Nối publisher reactive |
| Version không tăng khi bulk update | Direct SQL không tăng version | Thêm version = version + 1 và predicate |
| Test order phụ thuộc chạy trước/sau | Dữ liệu dùng chung, cleanup không rõ | Fixture độc lập và cleanup xác định |

## 21. Kết luận

Kiểm thử mapping, converter, callback và auditing cần kết hợp unit test với integration test. Unit test xác nhận logic chuyển đổi và callback độc lập; integration test xác nhận Spring Data đăng ký đúng converter, ánh xạ đúng schema, gọi callback theo lifecycle và ghi audit fields thực sự vào database.

Hãy dùng database cùng loại với production cho các test quan trọng về SQL type, timestamp, native type, constraint và transaction. Kiểm tra riêng entity save và direct DML vì @Modifying @Query, DatabaseClient và partial template update không tự đi qua entity auditing lifecycle. Với auditing, kiểm tra cả insert lẫn update, actor reactive, timestamp xác định và việc giữ nguyên created fields. Với callback, bảo đảm publisher reactive không block và lỗi được truyền đúng để transaction có thể rollback.

Một test đáng tin cậy không chỉ xác nhận publisher hoàn tất; nó đọc lại database và xác nhận giá trị đã lưu, version, audit metadata và các ràng buộc đúng như hợp đồng ứng dụng.
