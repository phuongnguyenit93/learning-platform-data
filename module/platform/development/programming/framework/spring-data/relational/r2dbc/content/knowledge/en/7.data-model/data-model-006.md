# Designing Nullable Data and Default Values

When designing a data model for Spring Data Relational R2DBC, you must clearly decide which properties are allowed to have no value, which are required, and which have default values. These three concepts are related but not synonymous. A column can allow `NULL` and still have a `DEFAULT`; a `NOT NULL` column can also have a `DEFAULT`; and a Java property set to `null` does not automatically tell the database to use a default value.

Correct design requires alignment across the schema, entities, APIs, and write statements. If these layers interpret null or default differently, the application can overwrite default values, reject valid data, or accidentally erase data during updates.

## 1. Distinguishing NULL, Omitted Values, and DEFAULT

When a record is created, at least three input states must be distinguished:

1. The client sends a specific value, such as `nickname = "An"`.
2. The client sends `null`, explicitly indicating the property has no value.
3. The client omits the property, which could mean using a default, preserving the existing value, or letting the business layer decide.

In SQL, `NULL` represents an unknown or absent value according to the column's semantics. It is not an empty string, the number 0, or a default value.

`DEFAULT` is an expression the database uses when a write statement requests applying the default. With `INSERT`, the default is typically applied when the column is omitted from the column list or when the statement specifies the `DEFAULT` keyword.

Example:

```sql
CREATE TABLE customer_profile (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    nickname VARCHAR(100) NULL,
    marketing_opt_in BOOLEAN NOT NULL DEFAULT FALSE,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

With the schema above:

- `email` must have a value.
- `nickname` is permitted to store `NULL`.
- `marketing_opt_in` cannot be `NULL`; if omitted from `INSERT`, the database uses `FALSE`.
- `status` cannot be `NULL`; if omitted from `INSERT`, the database uses `'NEW'`.
- `created_at` is assigned a default timestamp by the database when no value is passed.

| Write Method | Nullable Column Without Default | Column with `DEFAULT 'NEW'` |
| --- | --- | --- |
| Omit column from `INSERT` | Stores `NULL` if schema permits. | Database uses `'NEW'`. |
| Explicitly write `NULL` | Stores `NULL`. | Stores `NULL` if column permits; default is not triggered. |
| Write a specific value | Stores that value. | Stores that value, overriding default. |
| Write the `DEFAULT` keyword | Uses column default; if undeclared, behavior depends on database engine. | Database uses `'NEW'`. |

If a column has `NOT NULL DEFAULT ...`, explicitly writing `NULL` is usually rejected by the `NOT NULL` constraint. Having a default does not mean the database automatically replaces every `NULL` value with the default.

## 2. Designing Nullability in the Schema

Nullability should derive from business rules. Ask whether a property can be unknown, not yet provided, or inapplicable at the time the record is created.

Some examples:

- `middle_name` may not exist for a person.
- `delivered_at` has no value yet while an order has not been delivered.
- `cancelled_reason` only has a value when an order is cancelled.
- `email` may be required in a system using email as a login identifier.
- `created_at` usually must exist immediately upon record creation.

Do not make every column nullable just to make inserts easier. A loose schema lets invalid data slip into the system and forces every query to handle numerous edge cases.

### Use NOT NULL for Required Data

```sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(64) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    description TEXT NULL
);
```

`sku`, `name`, and `price` are required properties. `description` may be absent. The `NOT NULL` constraint is enforced by the database for every write path, even if data arrives from another application, direct SQL statements, or batch jobs.

`NOT NULL` is different from checking for a non-blank string. If `name` must not be whitespace-only, add application-layer validation and consider adding an appropriate database constraint.

### Use CHECK for Value Rules

Nullability only answers whether a column allows `NULL`. It does not define the full domain of valid values.

```sql
CREATE TABLE product_price (
    product_id BIGINT PRIMARY KEY,
    amount NUMERIC(12, 2) NOT NULL,
    currency CHAR(3) NOT NULL,
    CONSTRAINT chk_product_price_nonnegative CHECK (amount >= 0)
);
```

The `CHECK` constraint enforces the rule that `amount` is non-negative right in the database. Combine `NOT NULL` with `CHECK` when needed, because in SQL a `CHECK` expression evaluates to `UNKNOWN` for certain comparisons involving `NULL`; `CHECK (amount >= 0)` alone does not substitute for `NOT NULL`.

## 3. Representing Nullability in Java and Kotlin

The schema may allow `NULL`, so entity data types must be able to represent that state.

In Java, primitive types like `int`, `long`, and `boolean` cannot hold `null`. If a column can be null, use the corresponding wrapper type such as `Integer`, `Long`, or `Boolean`, or another appropriate reference type.

```java
import java.math.BigDecimal;
import java.time.LocalDateTime;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.lang.Nullable;

@Table("customer_profile")
public record CustomerProfile(
    @Id Long id,
    String email,
    @Nullable String nickname,
    Boolean marketingOptIn,
    String status,
    @Column("created_at") LocalDateTime createdAt
) {}
```

In this example:

- `nickname` is annotated with `@Nullable` because the schema permits `NULL`.
- `marketingOptIn` uses `Boolean`, allowing it to represent `true`, `false`, and `null`. It can be replaced with `boolean` if the application contract always requires a concrete value.
- `status` and `createdAt` are reference types, yet the schema requires `NOT NULL`; the application must ensure they have values before writing or let the database generate defaults via an appropriate insert statement.

`@Nullable` expresses intent and helps nullability analysis tools. It does not replace `NOT NULL` constraints in the database. Conversely, using a non-nullable Java type does not automatically create a schema constraint when the schema is managed separately.

For `Optional<T>`, it is generally best used as a return type or in APIs representing an absent result. For entity properties, nullable reference types and nullability annotations are usually more compatible with Spring Data mapping and constructors.

### Nullability in Kotlin

Kotlin expresses nullability directly in its type system:

```kotlin
@Table("customer_profile")
data class CustomerProfile(
    @Id val id: Long? = null,
    val email: String,
    val nickname: String?,
    val marketingOptIn: Boolean?,
    val status: String,
    val createdAt: LocalDateTime
)
```

`String?` permits `null`; `String` disallows null values in Kotlin's type system. When using Spring Data with Kotlin, Kotlin nullability metadata is used during mapping. Even so, the database remains the final enforcer of integrity constraints.

Do not declare `String?` merely to bypass validation errors. Use nullable types when the business rules genuinely allow missing values.

## 4. Do Default Values Belong in the Database or the Application?

Default values can be assigned at multiple layers:

- **Database default:** declared in DDL and applied when an insert omits the column or specifies `DEFAULT`.
- **Application default:** assigned in a factory, constructor, service, or DTO mapping before calling the repository.
- **Domain default:** an initialization rule of the domain model, usually reflecting a business decision.
- **Trigger or generated expression:** the database computes a value based on other columns or write time.

| Where to Place Default | Impact Scope | Best Fit When |
| --- | --- | --- |
| Database `DEFAULT` | All clients writing to the table. | You want consistent data protection even outside the current application. |
| Factory/service | Data creation flows passing through the application. | The value is a business decision that should be explicit in code. |
| Constructor/domain factory | Every object constructed via that model. | The value is an invariant or initial state of the domain object. |
| Trigger/generated column | Database must compute values from data or centralized rules. | The value depends on multiple write sources or must be enforced in the database. |

For example, if every new order must start with status `NEW`, a database default can guard even clients writing outside the application. If the initial status depends on order type, that rule should be decided in the domain/service and passed explicitly.

Avoid defining two conflicting defaults in the application and the database. For instance, Java defaults `status = "NEW"` while the database defaults `'PENDING'`. When a write path omits the value, the outcome will depend on how the statement is constructed. If both layers define a default, align on a single value and establish which layer is the primary source of truth.

### Default Is Not a Replacement for NULL

Suppose the `status` column has `DEFAULT 'NEW'`:

```sql
INSERT INTO orders (customer_id) VALUES (10);
-- status receives 'NEW'

INSERT INTO orders (customer_id, status) VALUES (10, NULL);
-- error if status is NOT NULL; if nullable, stores NULL
```

Defaults also do not automatically run when updating a column to `NULL`. To reset to default in an `UPDATE` statement, specify `SET status = DEFAULT` if the database engine supports that syntax.

## 5. How Database Defaults Interact with Spring Data R2DBC

This is the most common source of confusion when using entity mapping.

If the application wants the database to generate a default value, that column must be omitted from the `INSERT` statement or the statement must specify the `DEFAULT` keyword. If Spring Data generates a statement including that column and binds Java `null`, the database receives an explicit `NULL`. The default is not triggered.

Therefore, do not assume that setting an entity property to `null` guarantees Spring Data will omit that column from `INSERT`. Mapping behavior and generated statements depend on the write method, version, and metadata. Verify the actual SQL when relying on database defaults.

There are three common design approaches:

1. The application assigns the value itself before calling `save`.
2. The column is managed entirely by the database and marked read-only if appropriate.
3. Use a custom SQL statement to intentionally omit the column from the insert list.

### Application Assigns Default Before Save

If the default is an application business rule, a factory can be used:

```java
public record NewCustomerProfile(
    String email,
    String nickname,
    Boolean marketingOptIn
) {
    public static NewCustomerProfile create(
            String email,
            String nickname,
            Boolean marketingOptIn) {
        return new NewCustomerProfile(
            email,
            nickname,
            marketingOptIn != null ? marketingOptIn : Boolean.FALSE
        );
    }
}
```

The service converts the command into an entity with concrete values:

```java
public Mono<CustomerProfile> create(NewCustomerProfile command) {
    CustomerProfile profile = new CustomerProfile(
        null,
        command.email(),
        command.nickname(),
        command.marketingOptIn(),
        "NEW",
        LocalDateTime.now()
    );

    return repository.save(profile);
}
```

With this approach, the application sends `false`, `NEW`, and the creation timestamp explicitly. Database defaults are not the source of those values during this insert. Ensure other write paths follow the same rule if consistency is required.

### Database-Managed-Only Columns

Spring Data Relational provides the `@ReadOnlyProperty` annotation to mark a property that must not be written to the database during mapping-driven insert/update operations. The property can still be read when the entity is loaded.

Example:

```java
import org.springframework.data.annotation.ReadOnlyProperty;

@Table("customer_profile")
public record CustomerProfile(
    @Id Long id,
    String email,
    @ReadOnlyProperty
    @Column("created_at")
    LocalDateTime createdAt
) {}
```

This fits columns managed by the database that the application must not update. However, marking a property read-only does not mean every driver and insert path will automatically return all generated values. If you need the default value immediately after insert, check the driver's generated-value mechanism or reload the record by ID.

Do not use `@ReadOnlyProperty` for columns the application needs to change on subsequent updates. This annotation excludes the property from mapping write operations altogether, not just on insert.

### Using Explicit SQL to Omit Default Columns

When you need exact control over which columns are inserted, use `DatabaseClient` or a custom repository fragment. PostgreSQL example:

```java
import java.time.LocalDateTime;

import org.springframework.r2dbc.core.DatabaseClient;
import org.springframework.stereotype.Repository;
import reactor.core.publisher.Mono;

@Repository
public class CustomerProfileWriter {

    private final DatabaseClient databaseClient;

    public CustomerProfileWriter(DatabaseClient databaseClient) {
        this.databaseClient = databaseClient;
    }

    public Mono<CustomerProfile> insert(
            String email,
            String nickname) {

        return databaseClient.sql("""
                INSERT INTO customer_profile (email, nickname)
                VALUES (:email, :nickname)
                RETURNING id, email, nickname,
                          marketing_opt_in, status, created_at
                """)
            .bind("email", email)
            .bindNull("nickname", String.class)
            .map((row, metadata) -> new CustomerProfile(
                row.get("id", Long.class),
                row.get("email", String.class),
                row.get("nickname", String.class),
                row.get("marketing_opt_in", Boolean.class),
                row.get("status", String.class),
                row.get("created_at", LocalDateTime.class)
            ))
            .one();
    }
}
```

In this statement:

- `email` is bound with a required value.
- `nickname` is explicitly written as `NULL` using `bindNull`.
- `marketing_opt_in`, `status`, and `created_at` do not appear in the insert column list, so the database applies their declared defaults.
- `RETURNING` is PostgreSQL syntax to return the newly created row. Other database engines may require different ways of retrieving generated values.

R2DBC does not allow binding Java `null` with `.bind(name, null)` directly. Use `.bindNull(name, Type.class)` to pass SQL NULL. When you want a database default, do not bind `null`; omit the column from the statement or use appropriate `DEFAULT` syntax.

## 6. Watch Out for Primitive Types and Java Default Values

Java automatically assigns default values to primitive fields when creating objects:

| Primitive Type | Initial Value |
| --- | --- |
| `boolean` | `false` |
| `byte`, `short`, `int`, `long` | `0` |
| `float`, `double` | `0.0` |
| `char` | `\u0000` character |

These values do not represent SQL `NULL`. If an entity has `boolean marketingOptIn`, a new object holds `false` even if the client omitted that field. On save, the application may explicitly write `false` and prevent the database from using its default.

With wrapper types, the initial value is typically `null`, yet that still does not guarantee the column is omitted from the `INSERT` statement. Wrappers only allow modeling null in Java; how SQL is generated still depends on mapping/driver behavior.

Choose types based on the contract:

- Use primitives when a value is always required and meaningful immediately upon object creation.
- Use wrappers when distinguishing present values from absent values.
- Use `@Nullable` to explicitly express that a property can be null.
- Use factories or separate commands to distinguish omitted values from user-selected values.

## 7. NULL in SQL Queries and Query Methods

SQL uses three-valued logic: `TRUE`, `FALSE`, and `UNKNOWN`. Consequently, comparing against `NULL` with the `=` operator does not work like normal equality comparisons.

Do not write:

```sql
SELECT *
FROM customer_profile
WHERE nickname = NULL;
```

Use instead:

```sql
SELECT *
FROM customer_profile
WHERE nickname IS NULL;
```

To find existing values:

```sql
SELECT *
FROM customer_profile
WHERE nickname IS NOT NULL;
```

For derived query methods, Spring Data supports method names expressing null predicates, for example:

```java
Flux<CustomerProfile> findByNicknameIsNull();

Flux<CustomerProfile> findByNicknameIsNotNull();
```

If searching by a concrete value, use the corresponding query method:

```java
Flux<CustomerProfile> findByStatus(String status);
```

Do not pass `null` into `findByStatus` expecting Spring Data to interpret it as `IS NULL` in all cases. Declare methods that explicitly state the null condition or use an explicit query.

With custom SQL, if a parameter can be null, design the condition explicitly. For instance, a query with optional filters can use two SQL branches or build `Criteria` depending on whether the parameter is present. Avoid ambiguous conditions where a null value means both "ignore filter" and "find only rows where the column is null."

## 8. NULL, Empty Values, and Invalid Data

| Value | Meaning |
| --- | --- |
| SQL `NULL` | No value present according to column semantics. |
| String `''` | A string exists with length 0. |
| String `'   '` | A string containing only whitespace exists. |
| Number `0` | A valid numeric value, not null. |
| Boolean `false` | A valid boolean value, not null. |
| JSON `null` | A null value inside a JSON document; distinct from SQL NULL of the column itself. |

If business rules treat an empty string as absent data, normalize inputs or add validation. Do not rely on the database automatically converting empty strings to NULL because behavior differs across database engines.

For JSON columns, distinguish the column's SQL NULL from a JSON `null` value inside the document. They can produce different results in filtering, indexing, and JSON operators.

## 9. PATCH and the Semantics of Omitted Fields

A create request and a partial update request should not automatically share the same null semantics.

For create operations:

- An omitted field may receive a default.
- A field sent as `null` may store SQL NULL if the schema permits.
- Required fields must have valid values.

For PATCH:

- An omitted field usually means keeping the current value.
- A field sent as `null` may mean clearing the current value.
- A field sent with a concrete value means updating to that value.

A DTO with only nullable properties usually cannot distinguish "client omitted the field" from "client sent the field as null" after deserialization. If the API needs to distinguish these two states, use a representation with an explicit `present` flag, a JSON tree, or an appropriate wrapper.

Conceptual model example:

```java
public record FieldChange<T>(
    boolean present,
    T value
) {
    public static <T> FieldChange<T> absent() {
        return new FieldChange<>(false, null);
    }

    public static <T> FieldChange<T> of(T value) {
        return new FieldChange<>(true, value);
    }
}
```

When applied:

- `present = false`: leave the column unchanged.
- `present = true` and `value = null`: actively write SQL NULL if the schema allows it.
- `present = true` and `value` is non-null: update to that value.

This is a conceptual model for representing intent; the JSON deserializer must be designed to preserve whether the field appeared in the request. Never let a mapper assign `null` to every omitted field and pass the whole entity to `save`, as that could erase existing data.

## 10. Application Validation vs. Database Constraints

API validation returns clear errors before touching the database. Database constraints protect data across all write sources. The two layers complement each other.

Example DTO:

```java
import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCustomerRequest(
    @NotBlank
    @Email
    String email,

    @Size(max = 100)
    String nickname
) {}
```

In the controller, trigger validation with `@Valid` when Jakarta Bean Validation is configured:

```java
@PostMapping
public Mono<CustomerProfile> create(
        @Valid @RequestBody Mono<CreateCustomerRequest> request) {
    return request.flatMap(service::create);
}
```

Check how WebFlux handles validation for reactive request body types in the Spring version you use. Even when API validation passes, the database must still define `NOT NULL`, `UNIQUE`, `CHECK`, or foreign keys as needed to protect integrity.

Do not place `@NotNull` on a PATCH DTO if the contract allows clients to explicitly send null to clear a value. Validation must reflect the semantics of each request type.

## 11. Temporal Values and Defaults

Timestamp columns often require an explicit choice: application-supplied time or database-generated time.

```sql
CREATE TABLE audit_event (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    occurred_at TIMESTAMP NOT NULL,
    recorded_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

`occurred_at` can be the business event timestamp supplied by the application or event source. `recorded_at` can be the timestamp when the database recorded the row.

These two timestamps do not have to be identical. If consistent time across multiple applications is required, align time zones, column types, and clock sources. `CURRENT_TIMESTAMP` semantics depend on the database engine and transaction; read database docs to understand precision and evaluation timing.

With PostgreSQL, `TIMESTAMP WITH TIME ZONE` and `TIMESTAMP WITHOUT TIME ZONE` have different semantics. Pick Java types and converters that match the schema rather than renaming types without considering time zones.

## 12. Changing Nullability and Defaults via Migrations

Schema changes need a rollout path compatible with both existing data and running application instances.

Suppose you need to add a required `status` column with default `NEW` to a table that already contains data. A migration might run:

```sql
ALTER TABLE orders
ADD COLUMN status VARCHAR(20) DEFAULT 'NEW';

UPDATE orders
SET status = 'NEW'
WHERE status IS NULL;

ALTER TABLE orders
ALTER COLUMN status SET NOT NULL;
```

The syntax above is PostgreSQL. Other database engines may have different syntax and rollout strategies. For large tables, evaluate locks, backfill duration, and phased rollouts.

A safe rollout sequence usually includes:

1. Adding the column in a way compatible with currently running application versions.
2. Backfilling old data if needed.
3. Deploying the new application version that writes and reads the column.
4. Verifying no data violates the rule.
5. Adding or tightening the `NOT NULL` constraint.
6. Removing legacy compatibility logic once all instances are upgraded.

When dropping a default, check every write client. An older application might still rely on that default even though newer code passes explicit values.

## 13. Testing Nullability and Defaults with R2DBC

Testing with mock repositories does not prove the database applies defaults or constraints properly. Run integration tests against a real database type and driver.

| Case | What to Verify |
| --- | --- |
| Insert nullable column with SQL NULL | Database stores NULL and reads it back properly. |
| Insert omitting a column with default | Database generates the default value. |
| Insert passing an explicit value | Passed value overrides the default. |
| Insert NULL into a NOT NULL column | Database rejects the operation. |
| Update column to NULL | Succeeds only if schema permits. |
| PATCH omitting field | Existing value is preserved. |
| PATCH sending null | Column value is cleared per API contract. |
| Reading entity with nullable column | Mapping does not break when database value is NULL. |

With PostgreSQL, you can use Testcontainers and `@DataR2dbcTest` or a full Spring Boot test configuration. When testing database defaults, inspect whether the actual SQL statement omits that column from `INSERT`.

Example testing a publisher with Reactor Test:

```java
StepVerifier.create(repository.findByNicknameIsNull())
    .expectNextMatches(profile -> profile.nickname() == null)
    .verifyComplete();
```

The example assumes test data has already been prepared. In insert tests, read the record back from the database to verify what was actually persisted, rather than only asserting the input object.

## 14. Common Design Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Assuming Java null always triggers database default | Insert may write explicit NULL and bypass default. | Check SQL; omit column from insert or use SQL DEFAULT. |
| Using primitives for nullable columns | Cannot represent null; 0/false may be written unintentionally. | Use wrapper or appropriate nullable type. |
| Making required data nullable | Invalid data can propagate deep into the system. | Use validation and NOT NULL constraints. |
| Using empty strings instead of NULL | Queries and business rules can misinterpret data state. | Normalize and define clear semantics. |
| Using one DTO for both create and PATCH | Cannot distinguish omitted fields from fields sent as null. | Use commands/DTOs with distinct semantics. |
| Setting different defaults in Java and database | Outcome depends on the write path. | Pick an authoritative source and align values. |
| Assuming defaults auto-apply on UPDATE | Old values or NULL remain stored. | Use an appropriate update statement, e.g., SET column = DEFAULT if supported. |
| Testing only with mocks | Fails to catch mapping, SQL, constraint, or real default bugs. | Add integration tests on a compatible database. |

## 15. Workflow for Designing a Nullable or Defaulted Property

When adding a property to an entity and schema, follow this sequence:

1. **Determine business semantics:** can the value be unknown, inapplicable, or required?
2. **Decide nullability:** choose NULL or NOT NULL and declare the constraint explicitly in a migration.
3. **Decide default:** does the default belong to the database, domain, or application service?
4. **Choose Java/Kotlin types:** primitive vs. wrapper, nullable annotation vs. Kotlin nullable type.
5. **Define insert semantics:** client omits field, sends null, or sends a value? Must the database generate a default?
6. **Define update/PATCH semantics:** does null clear the value or keep it? What does an omitted field mean?
7. **Choose write mechanism:** standard repository mapping, read-only property for DB-managed columns, or custom SQL to omit columns.
8. **Test on a real database:** verify NULL, DEFAULT, constraints, mapping, and post-insert/update data.
9. **Roll out migrations in phases:** keep existing data and running application versions compatible.

A good data model makes the meaning of each state clear at every layer. `NULL` is a data state allowed by the schema; `DEFAULT` is a rule applied when a statement asks the database to generate a value; and omitting a field in an API is an application-contract decision. When these three concepts are distinguished and mapped consistently across Java/Kotlin, Spring Data R2DBC, and SQL, data becomes easier to govern and create/update operations avoid accidental data loss.
