# Distinguishing Java Defaults from Database Defaults

## 1. Two Places That Can Supply Default Values

When creating a record with Spring Data R2DBC, a property can receive a default value from two different places:

- **Java:** a value assigned to the object by the JVM, field initializers, constructors, factory methods, or application business logic.
- **Database:** a value defined in the schema via `DEFAULT`, identity, sequence, generated column, or trigger according to database system capabilities.

These two mechanisms operate at two different times. Java creates and initializes the object before the application sends a write command. The database applies defaults when executing the SQL statement if the statement allows the database to use them.

For example, an application has a `Task` entity with a `status` property. Java may initialize `status` to `PENDING`; the database may also define `status DEFAULT 'PENDING'`. The visible result may look the same, yet the source of decision differs:

- If Java assigns `PENDING` and the INSERT statement writes that value, the database receives the value sent by the application.
- Only if the INSERT statement omits the `status` column does the database have an opportunity to apply `DEFAULT 'PENDING'`.
- If the INSERT statement sends `NULL`, the database receives `NULL`; normal defaults do not automatically replace a `NULL` value.

In Spring Data R2DBC, you must understand both the Java object lifecycle and the SQL statement generated by the mapping layer. Inspecting field values in a debugger alone is not enough to know which default the database will apply.

## 2. Default Values When Java Instantiates an Object

When an object is created, the JVM initializes fields before running field initializers and the class constructor. If the developer does not assign a value, Java uses default values by data type.

| Field Type | Java Default Value |
| --- | --- |
| `byte`, `short`, `int`, `long` | `0` |
| `float`, `double` | `0.0` |
| `char` | Unicode character `\u0000` |
| `boolean` | `false` |
| Reference types such as `String`, `Integer`, `Long`, other entities | `null` |

Example:

```java
public class Task {
    private Long id;
    private String title;
    private int retryCount;
    private boolean enabled;
    private String status;
}
```

When calling `new Task()`, without other constructors or field initializers, the fields hold:

```text
id          = null
title       = null
retryCount  = 0
enabled     = false
status      = null
```

These are values in Java memory. They are not yet values persisted to the database.

### 2.1. Field Initializers and Constructors

An application can declare initial values directly on fields:

```java
public class Task {
    private Long id;
    private String title;
    private int retryCount = 3;
    private boolean enabled = true;
    private String status = "PENDING";
}
```

Or assign them in a constructor/factory method:

```java
public class Task {

    private Long id;
    private String title;
    private int retryCount;
    private boolean enabled;
    private String status;

    public static Task create(String title) {
        Task task = new Task();
        task.title = title;
        task.retryCount = 3;
        task.enabled = true;
        task.status = "PENDING";
        return task;
    }
}
```

The values `3`, `true`, and `PENDING` are application initialization policy. If Spring Data R2DBC writes these properties into the INSERT statement, the database receives those explicit values. Schema defaults will not be used for columns that already had values sent.

### 2.2. Primitives and Wrappers Have Different Meanings

A primitive field such as `int` always holds a numeric value, at least `0`; it cannot represent an "unprovided" state. The wrapper `Integer` can be `null`:

```java
private int retryCount;       // Java default is 0
private Integer maxAttempts;  // Java default is null
```

This distinction matters when you need to separate:

- The user explicitly chose `0`.
- The application has not received a value yet.
- The application wants the database to apply a default.

However, changing `int` to `Integer` only lets Java represent `null`; it does not automatically cause Spring Data R2DBC to omit the column from the INSERT statement. `null` and "omitting the column" are two different states at the SQL layer.

## 3. Default Values Supplied by the Database

The database defines defaults in the schema. PostgreSQL example:

```sql
CREATE TABLE task (
    id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title        VARCHAR(200) NOT NULL,
    status       VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    retry_count  INTEGER NOT NULL DEFAULT 3,
    enabled      BOOLEAN NOT NULL DEFAULT TRUE,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Here, the database can automatically supply:

- `id` via identity.
- `status` as `PENDING`.
- `retry_count` as `3`.
- `enabled` as `TRUE`.
- `created_at` as the current timestamp according to the database clock.

These defaults belong to the schema and are applied when an INSERT statement omits a value for the column or explicitly requests `DEFAULT`.

### 3.1. Omitting Columns from INSERT

When a column is omitted from the INSERT column list, the database can apply that column's default:

```sql
INSERT INTO task (title)
VALUES ('Send welcome email');
```

The database populates the remaining columns per the schema:

```text
title        = 'Send welcome email'
status       = 'PENDING'
retry_count  = 3
enabled      = TRUE
created_at   = current database timestamp
id           = assigned identity value
```

This is a clear way to instruct the database to apply defaults for columns absent from the INSERT statement.

### 3.2. Using the `DEFAULT` Keyword

SQL also allows explicitly requesting the default for a column in many database systems:

```sql
INSERT INTO task (title, status, retry_count)
VALUES ('Send receipt', DEFAULT, DEFAULT);
```

In this example, the database applies defaults for `status` and `retry_count`. Exact syntax may vary across database systems; consult your database's documentation.

### 3.3. Sending `NULL` Is Not the Same as Omitting a Column

This is the most important difference:

```sql
-- Database can apply DEFAULT 'PENDING'
INSERT INTO task (title)
VALUES ('Task A');

-- Database receives NULL for status; default does not automatically replace NULL
INSERT INTO task (title, status)
VALUES ('Task B', NULL);
```

If the `status` column has a `NOT NULL` constraint, the second statement typically fails because `NULL` was sent. If the column allows null, the stored value is `NULL`, not `PENDING`.

You can keep three distinct semantics in mind:

| Write Form | Meaning |
| --- | --- |
| Omitting column from INSERT list | Let the database decide based on default or column nullability |
| Passing the `DEFAULT` keyword | Instruct the database to use the defined default |
| Passing `NULL` value | Request storing SQL NULL, if the schema permits |

## 4. Direct Comparison of Java Defaults and Database Defaults

| Criterion | Java Default | Database Default |
| --- | --- | --- |
| Where defined | Fields, constructors, factories, or application logic | DDL/schema, identity, sequence, generated expression, or trigger |
| When applied | When instantiating the object or running application logic | When the database executes a compatible statement |
| Scope | Objects instantiated by that Java logic | Every client writing to the database under schema rules |
| Depends on DB connection | No | Yes |
| Can be overridden by sent values | Later code can change the field | Yes, if INSERT sends an explicit value instead of omitting the column or using DEFAULT |
| Representing `NULL` | Reference fields can be `null` | SQL `NULL` is a distinct value, separate from default |
| Clock source | Usually uses the application process clock | Can use the database clock |

These two mechanisms are not mutually exclusive. An application can set Java defaults so objects have valid state before saving, while also defining database defaults to protect data when another client writes. Yet you must clearly decide which source is authoritative and which write style is used.

## 5. What Happens When Spring Data R2DBC Saves an Entity?

Spring Data R2DBC uses mapping metadata and converters to translate a Java entity into data written to the database. The repository or `R2dbcEntityTemplate` then generates the appropriate SQL statement and executes it through the R2DBC SPI.

Entity example:

```java
@Table("task")
public class Task {

    @Id
    private Long id;

    private String title;
    private String status;
    private Integer retryCount;
}
```

Suppose the application creates an object:

```java
Task task = new Task();
task.setTitle("Send welcome email");
task.setStatus("PENDING");
task.setRetryCount(3);
```

When saving, `PENDING` and `3` already exist on the object. The mapping layer can write those values into the INSERT statement. When the database receives explicit values, column defaults are not used.

Crucially, a Java property being `null` does not mean the column is guaranteed to be omitted from the INSERT statement. The mapping layer may bind `null` as an SQL NULL parameter. Exactly how the statement is built depends on mapping metadata, annotations, the write API, and the Spring Data Relational version in use. Therefore, do not design around the assumption "if the field is null, the database applies the default." Inspect the actual SQL and bind parameters, or control the inserted column list explicitly.

### 5.1. Once Java Assigns a Default, the Database Does Not Automatically Replace It

Example:

```java
public class Task {
    private String status = "PENDING";
}
```

If the INSERT sends `status = 'PENDING'`, the database simply stores that value. Even if the schema specifies `DEFAULT 'NEW'`, the database does not overwrite the submitted value with `NEW`.

This can create discrepancies if Java and the schema declare inconsistent defaults:

```java
private String status = "PENDING";
```

```sql
status VARCHAR(30) NOT NULL DEFAULT 'NEW'
```

Records created through the Java application may receive `PENDING`, while records created from another SQL client may receive `NEW`. Unless intentional, align the default policy and update both code and schema migrations.

### 5.2. `null` Is Not a Reliable Column-Omission Mechanism

Example:

```java
Task task = new Task();
task.setTitle("Send welcome email");
task.setStatus(null);
```

From this object alone, you cannot conclude with certainty that the database will apply the default. If mapping generates `INSERT INTO task (title, status) VALUES (?, ?)` and binds the second parameter as SQL NULL, the default does not trigger.

When you need the database to supply the value, use an approach that guarantees the column is excluded from the INSERT statement or uses `DEFAULT` explicitly. With Spring Data Relational, consider `@ReadOnlyProperty` for properties managed entirely by the database, or use explicit SQL via `DatabaseClient` when you need exact per-column control.

## 6. Using `@ReadOnlyProperty` for Database-Managed Properties

Spring Data provides the `@ReadOnlyProperty` annotation in the `org.springframework.data.annotation` package. This annotation marks a property as read-only for Spring Data write operations: the property can still be read from the database and mapped onto the entity, yet it is not written like a normal property.

For example, if the database is always responsible for generating `status` and `created_at`:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Table;

import java.time.OffsetDateTime;

@Table("task")
public class Task {

    @Id
    private Long id;

    private String title;

    @ReadOnlyProperty
    private String status;

    @ReadOnlyProperty
    private OffsetDateTime createdAt;
}
```

With the schema:

```sql
CREATE TABLE task (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDING',
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

The `status` and `createdAt` properties are marked read-only so Spring Data does not write their Java values during normal write operations. This allows the database to apply defaults when creating rows.

`@ReadOnlyProperty` is suitable when the application must not set or modify that property itself. If a use case needs to submit a specific `status` value, this annotation is unsuitable for that property because it always excludes the property from mapping-based writes.

The annotation also does not mean the Java entity automatically receives every default value after INSERT. Whether database-generated values are returned and reassigned on the object depends on the generated-values mechanism, driver, dialect, and insert API used. If you need the value immediately after writing, use an appropriate returning mechanism or re-query the record.

## 7. Using `DatabaseClient` When You Need to Omit Columns Explicitly

If you want exact control over the INSERT statement so the database applies defaults, you can use `DatabaseClient` and list only the columns the application actually provides.

PostgreSQL example:

```java
public Mono<Task> createTask(DatabaseClient databaseClient, String title) {
    return databaseClient.sql("""
            INSERT INTO task (title)
            VALUES (:title)
            RETURNING id, title, status, retry_count, enabled, created_at
            """)
            .bind("title", title)
            .map((row, metadata) -> new Task(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("status", String.class),
                    row.get("retry_count", Integer.class),
                    row.get("enabled", Boolean.class),
                    row.get("created_at", OffsetDateTime.class)))
            .one();
}
```

The example assumes `Task` has a matching constructor. `RETURNING` is PostgreSQL syntax for returning values of the newly inserted row, including columns generated or defaulted by the database. Other databases may use different syntax or generated-values APIs.

The key point is that the INSERT lists only `title`. The database supplies `status`, `retry_count`, `enabled`, `created_at`, and `id` per the schema. `RETURNING` lets the application receive the database-determined values in the same operation.

Without `RETURNING` or a corresponding generated-values return mechanism, the application can execute a read query after insert to retrieve the full state. When doing so, identify the key for the newly created row and use an appropriate transaction.

### 7.1. Using `DEFAULT` Explicitly

If an SQL statement needs to pass values for some columns while instructing the database to pick defaults for others, you can write:

```java
databaseClient.sql("""
        INSERT INTO task (title, status, retry_count)
        VALUES (:title, DEFAULT, DEFAULT)
        RETURNING id, title, status, retry_count
        """)
        .bind("title", title)
        .map((row, metadata) -> /* map result */)
        .one();
```

This clearly expresses the intent to "use default" in SQL. Do not bind a parameter for a position holding the `DEFAULT` keyword. Verify syntax on your specific database and driver.

### 7.2. When Choosing Between an Application Value and a Database Default

Suppose a use case lets the user pick `status`; if omitted, the database uses the default. You must distinguish "omitted" from "supplied NULL." You can branch between two SQL statements with different column lists:

```java
if (status == null) {
    return databaseClient.sql("""
            INSERT INTO task (title)
            VALUES (:title)
            RETURNING id, title, status
            """)
            .bind("title", title)
            .map((row, metadata) -> /* map result */)
            .one();
}

return databaseClient.sql("""
        INSERT INTO task (title, status)
        VALUES (:title, :status)
        RETURNING id, title, status
        """)
        .bind("title", title)
        .bind("status", status)
        .map((row, metadata) -> /* map result */)
        .one();
```

This snippet only illustrates separating the two cases. In real applications, encapsulate statement construction and mapping inside a repository or persistence adapter rather than putting SQL directly in controllers. Table and column names must be constants or strictly controlled; never concatenate identifiers from user input.

## 8. Choosing Where to Place Defaults by Data Responsibility

There is no universal rule that all defaults belong in Java or all defaults belong in the database. Placement depends on what the data means and who is authoritative.

### 8.1. Put Defaults in Java When They Are Domain Rules

For instance, a new request object always starts in the `DRAFT` state. That can be a domain rule rather than merely a storage detail:

```java
public class PurchaseOrder {

    private OrderStatus status;

    private PurchaseOrder() {
        this.status = OrderStatus.DRAFT;
    }

    public static PurchaseOrder create() {
        return new PurchaseOrder();
    }
}
```

The factory method ensures new objects created via the domain API start in a valid state. When saving, the application can write `DRAFT` to the database. The schema should still have `NOT NULL` and may include `DEFAULT` as an extra safeguard for other clients, while the business rule is expressed in the domain model.

### 8.2. Put Defaults in the Database When the Database Is Authoritative

Certain values are best determined by the database:

- `created_at` using the database clock so every writing application shares one consistent time source.
- Identity or sequence IDs allocated by the database.
- Default status flags shared across multiple heterogeneous clients.
- Values computed from expressions or triggers under centralized data policies.

Example:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

If Java sets `Instant.now()`, the timestamp depends on the clock and time-zone configuration of each application instance. If the database sets `CURRENT_TIMESTAMP`, the time source resides in the database. The two values can diverge if clocks drift or transactions execute at different moments.

### 8.3. Combining Both Layers Consistently

An application can initialize defaults in Java so objects are always valid and also declare defaults in the database to guard writes from other clients. However, keep both policies aligned and verify the write path.

For example, both Java and the schema use `PENDING`. If another SQL client omits the status column, the database still assigns `PENDING`. If the Java application creates an object and writes `PENDING`, the result is also `PENDING`. If the default changes to `QUEUED`, update both factory/domain logic and schema migrations if that is the desired business change.

Avoid accidentally maintaining two different defaults, as data created through different write paths will behave differently.

## 9. Defaults, NULL, and the NOT NULL Constraint

Defaults and `NOT NULL` solve two distinct problems:

- `DEFAULT` supplies a value when INSERT omits the column or uses the `DEFAULT` keyword.
- `NOT NULL` prevents storing SQL NULL in the column.

Example:

```sql
status VARCHAR(30) NOT NULL DEFAULT 'PENDING'
```

Combining both means:

- INSERT omitting `status`: database uses `PENDING`.
- INSERT writing `DEFAULT` for `status`: database uses `PENDING`.
- INSERT writing `NULL` for `status`: database rejects due to `NOT NULL`.
- INSERT writing `'ACTIVE'`: database stores `'ACTIVE'` if other constraints allow.

`NOT NULL` does not supply a default automatically. If a column has only `NOT NULL` without `DEFAULT`, an INSERT omitting that column may fail because there is no valid value to store.

Similarly, a Java field being `null` does not prove the database column allows null. The schema defines the final constraint. Keep entity nullability, application validation, and database constraints consistent.

## 10. Database-Generated Values and Returning Data to the Entity

After the database applies a default, the Java object in memory does not necessarily have the new value automatically. For instance, the database may generate `created_at`, yet `task.getCreatedAt()` may remain `null` if the insert operation does not return that column and the mapping layer does not update the entity.

Distinguish between:

1. **Persisted value:** the database has written the default or generated value into the row.
2. **Value in the Java object:** the object only contains what the application assigned or what the persistence operation returned and reassigned.

For generated IDs, Spring Data R2DBC handles generated IDs depending on the database and driver. For other default columns, retrieval depends on the API, dialect, and driver. Do not assume every `DEFAULT` column will be populated back onto the object after `save`.

If business logic immediately needs `created_at` or `status` after saving, you can:

- Use a statement with `RETURNING` or a generated-values mechanism supported by the database/driver.
- Re-read the record after insert.
- Assign the value in Java if the application is authoritative and does not need the database's value.

Verify actual behavior using integration tests with the exact driver and database. A Java unit test creating an object in memory cannot prove the database applied a default.

## 11. Defaults for Dates/Times and Clock Differences

Timestamps are an area where two default sources easily diverge.

Java might assign:

```java
private Instant createdAt = Instant.now();
```

The database might assign:

```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
```

If multiple applications write to the same database, using database-supplied timestamps centralizes the time source. If the domain needs the timestamp when an event was created in the application prior to writing, Java may be the appropriate source. Define clearly what a timestamp represents:

- When the user performed an action.
- When the application received the request.
- When the database committed the transaction.
- When a processing job completed.

These moments are not necessarily identical. Do not overload a single `createdAt` field with multiple meanings.

In addition, `CURRENT_TIMESTAMP` and `Instant.now()` can differ due to clock precision, how the database represents time zones, and how the driver converts types. Use appropriate temporal types such as `Instant` or `OffsetDateTime`, standardize on UTC at integration boundaries, and test driver mappings.

## 12. Defaults for IDs, Sequences, and Generated Columns

IDs are another kind of value that can be generated in Java or in the database.

### 12.1. Java-Generated IDs

The application can generate a UUID before insert:

```java
UUID id = UUID.randomUUID();
```

The advantage is that the ID is available before writing and can be used in objects or events prior to database confirmation. On the other hand, the application must align UUID types and representations with the schema, driver, and related systems.

### 12.2. Database-Generated IDs

The database can use identity or sequences:

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

The application leaves the ID unassigned and the persistence layer uses the appropriate generated-ID mechanism. The database assigns the ID during insert. Whether the ID is returned and populated on the entity depends on the database, driver, and how Spring Data executes the insert.

Do not set `0` on a primitive ID field expecting every driver to treat that as "no ID yet." For auto-generated IDs, wrapper types like `Long` represent an unassigned state as `null`; mapping metadata and generated-ID handling must still be configured properly.

### 12.3. Generated Columns and Triggers

Some databases support generated columns or triggers that compute values from other data. Those values are governed by the database. If the application must not send a value for that column, exclude the column from writes or use appropriate read-only mapping. Generated-column syntax and whether values can be returned to the entity depend on the database system.

## 13. Managing Defaults via Database Migrations

Defaults belong to the schema and should be managed through versioned migrations. Migration example:

```sql
ALTER TABLE task
    ALTER COLUMN status SET DEFAULT 'PENDING';

ALTER TABLE task
    ALTER COLUMN created_at SET DEFAULT CURRENT_TIMESTAMP;
```

Changing a default usually affects only rows inserted after the schema change. It does not automatically update older rows that already have values. If historical data needs updating, the migration must include a separate UPDATE statement whose impact is evaluated beforehand.

Example:

```sql
UPDATE task
SET status = 'PENDING'
WHERE status IS NULL;
```

This UPDATE is an explicit data modification, separate from setting a default for future INSERTs. Before running a data migration, verify how many rows are affected and the business meaning of existing values.

In Spring Data R2DBC, mapping annotations do not replace schema migrations. `@Table`, `@Column`, and `@ReadOnlyProperty` describe how entities map; they do not guarantee the schema has the right defaults, constraints, or generated expressions. Schemas must be created and evolved through an appropriate migration or database management workflow.

## 14. Testing the Difference Between Both Default Types

To verify database defaults, test against a real database or a test database running the exact target database system and driver. Java unit tests only verify in-memory object initialization.

An integration test can verify both write paths:

1. INSERT omitting `status` and assert the database returns `PENDING`.
2. INSERT passing `status = 'ACTIVE'` and assert the database stores `ACTIVE`.
3. If the column is `NOT NULL`, try passing SQL NULL and assert the database rejects it.
4. Read the record back to verify generated values such as ID and `created_at`.

Test SQL example:

```sql
INSERT INTO task (title)
VALUES ('Default status test')
RETURNING status;

INSERT INTO task (title, status)
VALUES ('Explicit status test', 'ACTIVE')
RETURNING status;
```

Expected results are `PENDING` and `ACTIVE` respectively, assuming the schema has `DEFAULT 'PENDING'`. The `RETURNING` clause in this example is PostgreSQL syntax; for other database systems, re-query the row or use the corresponding generated-values return mechanism.

When testing via a repository, know what SQL Spring Data emits. You can enable SQL logging in test environments or inspect driver statements to verify the column list and bound parameters. Avoid enabling logs containing sensitive data in production.

## 15. Common Errors

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Database always receives `0` despite a different column default | Java primitive field `int` holds `0` and is written explicitly | Use a wrapper if needing to represent unprovided; explicitly omit the column from INSERT when wanting DB default |
| Database receives `NULL` instead of default | Mapping binds SQL NULL for a `null` Java property | Inspect SQL; omit the column or use explicit `DEFAULT` |
| Stored value differs from schema default | Java initializer/constructor already assigned a value and INSERT sent it | Align default sources or let the database manage the column |
| Entity after `save` still has `createdAt = null` | Database generated the value, yet the insert did not return/assign that column onto the entity | Use generated values/`RETURNING` or re-read the record |
| Different clients create rows with different statuses | Java and schema have inconsistent defaults | Synchronize policies and migrations |
| INSERT fails due to NOT NULL | Column was sent NULL or omitted without a default | Check schema and parameter binding; add a default or supply a valid value |
| Generated column gets overwritten | Application still sends a value to a database-managed column | Exclude the column from writes or use appropriate read-only mapping |

## 16. Selection Rules in a Spring Data R2DBC Application

When designing a property that has a default, evaluate these questions in order:

1. Is the value an invariant or domain rule that must exist as soon as the object is created? If yes, express it in the constructor or factory method.
2. Do multiple different applications/clients share the need for a default? If yes, a database default can serve as a shared safeguard.
3. Is the database the authoritative source for the value, such as record creation timestamp or ID? If yes, let the database generate it and do not overwrite from Java.
4. Does the INSERT statement genuinely omit the column or use `DEFAULT`? Inspect generated SQL; never infer this from a `null` field.
5. Does the entity need the value back immediately after insert? If yes, use a generated-values return mechanism or re-query.
6. Do Java mapping and schema migrations agree on nullability, defaults, and data types?
7. Are there integration tests verifying behavior on the actual driver/database?

Java defaults give objects initialized state under application logic. Database defaults let the schema supply values when an INSERT omits a column or requests `DEFAULT`. In Spring Data R2DBC, the deciding boundary lies in the SQL and parameters that the mapping layer actually sends to the database. Understanding the difference between explicit values, SQL NULL, and columns omitted from INSERT helps prevent subtle data bugs when an application has multiple write paths or relies on database-generated values.
