# Reading an Identifier Set and Querying in Batches

In a Spring Data R2DBC application, a screen often needs data from multiple tables. For example, an order list page needs to read the orders first and then fetch the order lines belonging to each order. Calling a repository once per order increases query count with order volume and easily causes an N+1 query issue. A more efficient organization is to read the identifier set of the displayed group, query related data by ID batch, and assemble the results in memory.

This pattern typically involves two query rounds:

1. Fetch the list of parent records or their ID set using a clear predicate and result limit.
2. Use that ID set to fetch all related records in one `IN` query, or split the IDs into smaller batches if the set is too large.

The application then groups child records by foreign key and combines them with parent records. This is deliberate data loading in the relational model; Spring Data R2DBC does not automatically lazy-load relationships like JPA/Hibernate.

## 1. The Problem and Rationale for Batch Reading

Suppose the database has two tables:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_code VARCHAR(32) NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(19, 2) NOT NULL
);

CREATE INDEX idx_order_lines_order_id ON order_lines(order_id);
```

An order has multiple order lines. When displaying the 30 most recent orders with their lines, several approaches exist:

- Read the orders, then call `findByOrderId(...)` individually for each order.
- Join `orders` with `order_lines` in a single SQL statement.
- Read the order list first, extract its IDs, and query all order lines for that ID set.

The first approach is easy to write but creates N+1 queries: one query for orders and N queries for lines. With 30 orders, the application makes 31 database round trips. Network latency and repeated execution overhead grow with order count.

Batch reading usually drops round trips to two: one query for orders and one query for all lines whose `order_id` is in the fetched ID set. This keeps parent and child data in two manageable result streams while avoiding the parent-column duplication caused by a one-to-many join.

```text
N+1 query

Query 1: SELECT orders ...
    |
    +-- Query 2: SELECT order_lines WHERE order_id = 101
    +-- Query 3: SELECT order_lines WHERE order_id = 102
    +-- Query 4: SELECT order_lines WHERE order_id = 103
    `-- ... one query per order

Batch reading

Query 1: SELECT orders ...
    |
    v
IDs = [101, 102, 103, ...]
    |
    v
Query 2: SELECT order_lines WHERE order_id IN (101, 102, 103, ...)
    |
    v
Group order lines by order_id and attach to each order
```

## 2. Entity and Repository Design

### 2.1. Entities Representing Foreign Keys by ID

In Spring Data Relational, relationships between two aggregates can be represented using a scalar foreign key. For example:

```java
@Table("orders")
public record OrderEntity(
        @Id Long id,
        @Column("customer_id") Long customerId,
        @Column("order_code") String orderCode,
        String status,
        @Column("created_at") Instant createdAt
) {
}
```

```java
@Table("order_lines")
public record OrderLineEntity(
        @Id Long id,
        @Column("order_id") Long orderId,
        @Column("product_code") String productCode,
        Integer quantity,
        @Column("unit_price") BigDecimal unitPrice
) {
}
```

`OrderLineEntity.orderId` holds the ID of the owning order. This is relational link data in the schema; declaring `orderId` alone does not make Spring Data automatically load `OrderEntity`. When data from both tables is needed, the application decides the queries and assembly strategy.

### 2.2. Repository for Fetching the Parent Group

```java
public interface OrderRepository
        extends ReactiveCrudRepository<OrderEntity, Long> {

    Flux<OrderEntity> findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(
            Long customerId);
}
```

This example caps the order set to at most the 50 most recent records for a customer. Bounding the parent set upfront bounds the number of IDs passed to the second query and the amount of data held in memory.

If the application needs an arbitrary page, you can use `R2dbcEntityTemplate` with `Query`/`Criteria`, or a query method/SQL with limit and offset. Always enforce deterministic ordering, typically adding the primary key as a secondary sort criterion when the primary sort field can have ties.

### 2.3. Repository for Fetching Children by ID Set

```java
public interface OrderLineRepository
        extends ReactiveCrudRepository<OrderLineEntity, Long> {

    Flux<OrderLineEntity> findByOrderIdInOrderByOrderIdAscIdAsc(
            Collection<Long> orderIds);
}
```

The `In` keyword in a derived query expresses membership in a value set, corresponding to SQL shaped like `WHERE order_id IN (...)`. The repository returns a `Flux` because an order can have multiple lines and the whole ID group can match many records.

Adding `OrderByOrderIdAscIdAsc` gives results a deterministic order by foreign key and then ID. This sorting helps when line order matters or deterministic output across runs is desired. If business logic defines a `line_number` column, sort by that column instead of `id` to reflect true display order.

## 3. Executing Two Query Rounds and Assembling Results

### 3.1. Result Type for the Screen

You can define a DTO holding an order along with its lines:

```java
public record OrderWithLines(
        OrderEntity order,
        List<OrderLineEntity> lines
) {
}
```

This is a read result model, not necessarily an entity persisted in the database. The DTO provides the API or service layer with a pre-assembled structure.

### 3.2. Basic Reactive Flow

```java
@Service
public class OrderQueryService {

    private final OrderRepository orderRepository;
    private final OrderLineRepository lineRepository;

    public OrderQueryService(
            OrderRepository orderRepository,
            OrderLineRepository lineRepository) {
        this.orderRepository = orderRepository;
        this.lineRepository = lineRepository;
    }

    public Mono<List<OrderWithLines>> findRecentOrders(Long customerId) {
        return orderRepository
                .findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(customerId)
                .collectList()
                .flatMap(orders -> {
                    if (orders.isEmpty()) {
                        return Mono.just(List.of());
                    }

                    List<Long> orderIds = orders.stream()
                            .map(OrderEntity::id)
                            .distinct()
                            .toList();

                    return lineRepository
                            .findByOrderIdInOrderByOrderIdAscIdAsc(orderIds)
                            .collectMultimap(OrderLineEntity::orderId)
                            .map(linesByOrderId -> orders.stream()
                                    .map(order -> new OrderWithLines(
                                            order,
                                            List.copyOf(linesByOrderId.getOrDefault(
                                                    order.id(), List.of()))))
                                    .toList());
                });
    }
}
```

Execution flow:

1. The repository emits orders as `Flux<OrderEntity>`.
2. `collectList()` gathers up to 50 orders into a `List`, because the next step needs all IDs for the current page.
3. If the list is empty, return an empty list immediately without calling the line repository.
4. Extract IDs, deduplicate them, and build the parameter set for the `IN` query.
5. `findByOrderIdIn...` fetches all lines in a single batched query.
6. `collectMultimap(OrderLineEntity::orderId)` groups each line by `orderId`.
7. Iterate the original order list and pair each order with its line group. Orders with no lines receive an empty list.

`collectMultimap` creates a `Mono` containing a map from key to a collection of values. The assembly step iterates the original `orders` list, preserving the initial parent order. Never iterate map keys directly if parent ordering is part of the expected output.

### 3.3. Why Use collectList Then flatMap?

The second query depends on the IDs emitted by the first query. `collectList()` produces a publisher that emits the list only after the parent query completes. `flatMap` then uses that list to launch the child query and chain results into the same pipeline.

Do not call `subscribe()` inside the service to launch the second query. Subscribing manually breaks returning a single publisher representing the whole task; callers could receive control before the child query finishes and error handling for the second step becomes difficult.

Do not use `map` to directly call a repository method returning `Mono` or `Flux`, as that produces nested publishers like `Mono<Flux<OrderLineEntity>>`. `flatMap` or `flatMapMany` is the right operator when the next step returns a publisher.

## 4. Handling Empty ID Sets and Incomplete Data

### 4.1. Do Not Issue an IN Query with an Empty List

When there are no parent records, there is no reason to query child records. Some dialects/databases reject `IN ()` syntax; even when the framework handles it, an explicit empty branch avoids an unnecessary round trip.

```java
if (orderIds.isEmpty()) {
    return Mono.just(List.of());
}
```

### 4.2. Parent Records Without Child Records

The resulting map only contains keys for `orderId`s that have at least one line. When assembling, use `getOrDefault(order.id(), List.of())` so orders without lines still appear with an empty list.

This differs from an inner join: an inner join omits orders with no lines from the result. If business requirements dictate retaining all parent orders, in-memory assembly or SQL `LEFT JOIN` must preserve that behavior.

### 4.3. Null IDs and Unsaved Records

IDs read from entities retrieved from the database should normally be non-null. If an ID source comes from unsaved objects, define clearly whether they belong in the batch query. Do not silently strip null IDs if that hides a bug in the business flow; ensure the input ID set represents valid existing records.

### 4.4. Duplicate IDs

A query ID set should usually be deduplicated to reduce parameters and avoid redundant work. Use `distinct()` when building the ID list. If the ID is a primary key queried directly from a table, duplicates rarely occur; deduplication is still useful when IDs are gathered from multiple sources.

## 5. Splitting Large ID Sets into Smaller Batches

`IN` queries have practical limits. Databases or drivers may cap bind parameters per statement; huge ID sets also bloat SQL text and execution plans. For dozens or a few hundred IDs, one batch query is usually fine. For thousands or tens of thousands of IDs, split into batches.

### 5.1. Partitioning Helper

```java
private static <T> List<List<T>> partition(List<T> values, int batchSize) {
    if (batchSize <= 0) {
        throw new IllegalArgumentException("batchSize must be positive");
    }

    List<List<T>> batches = new ArrayList<>();
    for (int start = 0; start < values.size(); start += batchSize) {
        int end = Math.min(start + batchSize, values.size());
        batches.add(List.copyOf(values.subList(start, end)));
    }
    return batches;
}
```

This helper produces batches no larger than `batchSize`. `List.copyOf` returns an unmodifiable copy, preventing a batch from being mutated while a query reads it.

### 5.2. Querying Batches Sequentially

```java
private Flux<OrderLineEntity> findLinesInBatches(List<Long> orderIds) {
    return Flux.fromIterable(partition(orderIds, 500))
            .concatMap(lineRepository::findByOrderIdInOrderByOrderIdAscIdAsc);
}
```

`concatMap` waits for the current batch to finish before moving to the next. This keeps in-flight queries low and database load predictable. If batches are independent and the database has spare capacity for parallel work, you can use `flatMap` with an explicit concurrency bound:

```java
return Flux.fromIterable(partition(orderIds, 500))
        .flatMap(lineRepository::findByOrderIdInOrderByOrderIdAscIdAsc, 4);
```

The argument `4` limits concurrent batches. Never use unbounded concurrency for a large ID set, as it can exhaust the connection pool or spike database load.

### 5.3. Grouping Results Across Multiple Batches

After the batches finish, you can still collect all lines and group by `orderId`:

```java
return findLinesInBatches(orderIds)
        .collectMultimap(OrderLineEntity::orderId);
```

The final output is still a map used to pair with the parent list. Batch completion order may vary with parallel `flatMap`; if line ordering matters, sort in the repository, sort after collecting, or use `concatMap`.

### 5.4. Choosing Batch Size

No single number fits every database. Consider:

- Database/driver bind-parameter limits.
- Generated SQL statement length.
- Row payload size and total returned data.
- Connection pool size and concurrent query load.
- Network latency and per-batch execution time.
- Index selectivity on the foreign key column.

Start with a conservative batch size, measure timings and database load, and tune with metrics. Batch size only governs how many IDs go into each query; it does not replace bounding the total number of records a use case is allowed to load.

## 6. Very Large Datasets: Paginate Parents Instead of Collecting All IDs

Never load millions of IDs into a `List` just to issue an `IN` query. At large scale, break work down by parent pages:

1. Read a bounded page of orders.
2. Extract IDs for that page.
3. Query order lines for those page IDs.
4. Assemble and process or emit results for the page.
5. Move to the next page.

Example using a limit-bounded query method:

```java
Flux<OrderEntity> findTop100ByStatusOrderByIdAsc(String status);
```

For long-running processing streams, keyset pagination can fetch subsequent pages based on the last key of the previous page. Keyset pagination is typically stable and avoids high offset costs as datasets grow.

If processing records without needing to hold the entire result set for an HTTP response, process page by page in the pipeline and release memory after each page. If returning a single response containing all data, enforce a strict overall result cap; never turn a list endpoint into an unbounded load.

## 7. Batch Querying with DatabaseClient

The derived query `findByOrderIdIn(...)` works well for simple single-table queries. When custom SQL is required, `DatabaseClient` can bind a collection parameter.

```java
Flux<OrderLineEntity> findByOrderIds(Collection<Long> orderIds) {
    if (orderIds.isEmpty()) {
        return Flux.empty();
    }

    return databaseClient.sql("""
            SELECT id, order_id, product_code, quantity, unit_price
            FROM order_lines
            WHERE order_id IN (:orderIds)
            ORDER BY order_id, id
            """)
            .bind("orderIds", orderIds)
            .map((row, metadata) -> new OrderLineEntity(
                    row.get("id", Long.class),
                    row.get("order_id", Long.class),
                    row.get("product_code", String.class),
                    row.get("quantity", Integer.class),
                    row.get("unit_price", BigDecimal.class)))
            .all();
}
```

Named parameter expansion in Spring R2DBC `DatabaseClient` can expand a collection into corresponding bind markers inside an `IN` clause depending on the API and version used. Verify support for your Spring Framework and driver versions. Never concatenate IDs into SQL strings as a substitute for parameter binding.

If using a lower-level bind API or a driver lacking the desired expansion support, generate per-element placeholders using safe parameterized binding or use a derived query. Every ID value must still be bound; never inject input data into SQL via string concatenation.

## 8. When to Use JOIN Instead of Reading IDs and Batch Querying?

Batch reading is not always better than a join. Both solve the same need with different trade-offs.

### 8.1. JOIN in a Single Query

```sql
SELECT o.id AS order_id,
       o.order_code,
       o.status,
       l.id AS line_id,
       l.product_code,
       l.quantity,
       l.unit_price
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.id
WHERE o.customer_id = :customerId
ORDER BY o.created_at DESC, o.id DESC, l.id ASC
```

The advantage is that the database executes the join in one statement and the application makes a single round trip. The drawback is that order columns repeat on every line row. Code must group join rows into a parent-child structure; if multiple one-to-many relationships are joined together, row counts can multiply significantly.

### 8.2. Two Query Rounds by ID

The parent query returns one row per order. The child query returns one row per line. The application groups lines by `orderId` and attaches them to each order.

Pros:

- Avoids repeating parent columns on every child row.
- Easy to bound the parent set before loading related data.
- Reuses separate repositories per aggregate/table.
- Easy to query multiple independent child groups and attach them to the same parent.

Cons:

- At least two database round trips.
- Application must hold parent data and child groups in memory for assembly.
- Two queries can observe different database states without appropriate transaction/isolation settings.

### 8.3. Selection Table

| Scenario | Usually Suitable Approach |
|---|---|
| Small parent page, one child group per parent | Read IDs then batch query |
| Multiple independent child groups for the same parent set | Query each group by ID then assemble |
| Filtering or sorting across columns of multiple tables | Custom `JOIN`/SQL |
| Aggregates or reporting across multiple tables | `JOIN`, `GROUP BY`, or CTE |
| Very large parent set | Paginate parents, process in batches |
| Only a few columns needed and database handles it well | Projection or SQL join |
| Must retain all parents even without children | `LEFT JOIN` or batch assembly with empty lists |

Do not choose purely by counting SQL statements. Consider bytes transferred, intermediate row counts, execution plans, indexes, and assembly complexity.

## 9. Reading Multiple Data Groups for the Same Parent Set

A screen might need order lines, status history, and notes for the same list of orders. You can fetch parent IDs once and run one batch query per data type:

```java
return orderRepository.findTop50ByCustomerIdOrderByCreatedAtDescIdDesc(customerId)
        .collectList()
        .flatMap(orders -> {
            if (orders.isEmpty()) {
                return Mono.just(List.of());
            }

            List<Long> ids = orders.stream()
                    .map(OrderEntity::id)
                    .distinct()
                    .toList();

            Mono<Map<Long, Collection<OrderLineEntity>>> linesMono =
                    lineRepository.findByOrderIdIn(ids)
                            .collectMultimap(OrderLineEntity::orderId);

            Mono<Map<Long, Collection<OrderStatusHistory>>> historyMono =
                    historyRepository.findByOrderIdIn(ids)
                            .collectMultimap(OrderStatusHistory::orderId);

            return Mono.zip(linesMono, historyMono)
                    .map(data -> orders.stream()
                            .map(order -> new OrderDetailView(
                                    order,
                                    List.copyOf(data.getT1().getOrDefault(
                                            order.id(), List.of())),
                                    List.copyOf(data.getT2().getOrDefault(
                                            order.id(), List.of()))))
                            .toList());
        });
```

`Mono.zip` combines results of the two independent queries. They may be subscribed simultaneously; parallel query count should fit the connection pool and database capacity. If sequential execution is needed, chain with `flatMap` or `then` as appropriate. When either query errors, the error propagates through the combined publisher; do not swallow errors to return partial data without explicit business rules.

This illustrative code assumes corresponding repositories and DTOs exist. If one of the groups has no matching records, `collectMultimap` still emits an empty map, so `getOrDefault` supplies an empty list for that group.

## 10. Transactions and Consistency Between Read Rounds

When reading parents and children in two separate queries, data may change between rounds. For instance, an order line may be deleted after querying orders and before querying lines. The assembled result then reflects two different points in time.

If the use case tolerates near-concurrent reads, a long transaction may not be necessary. If a consistent snapshot is required, consider a reactive transaction and suitable database isolation level.

Example service transaction declaration:

```java
@Transactional(readOnly = true)
public Mono<List<OrderWithLines>> findRecentOrders(Long customerId) {
    // Pipeline querying parents, extracting IDs, querying children, and assembling results.
}
```

Reactive transactions use Reactor Context to propagate the transaction across the pipeline. Keep operations within the same pipeline; never call `subscribe()` manually or split work onto an independent stream if it needs to join the transaction.

`readOnly = true` expresses read-only intent and may be supported depending on the transaction manager and database; it does not automatically guarantee snapshot isolation. Actual consistency depends on the transaction isolation level and database engine. Choose a level suited to requirements, since higher isolation can affect concurrency and resource hold times.

## 11. Indexes, Data, and Performance

Batch queries typically look like:

```sql
SELECT ...
FROM order_lines
WHERE order_id IN (...)
ORDER BY order_id, id
```

Factors affecting performance:

- **Foreign key index:** an index on `order_lines(order_id)` speeds up locating lines for the ID group.
- **ID count:** larger ID sets produce larger statements and more bind markers.
- **Child rows per parent:** a page of 50 orders can still return tens of thousands of lines if each order has many lines.
- **Projection:** select only needed columns to cut network transfer and materialization cost.
- **Sort:** a matching index can help return rows in the desired order.
- **Batch concurrency:** running multiple batches in parallel can improve throughput but may cause connection contention.

Do not cap only parent order counts while ignoring the risk that each order has huge numbers of lines. You may need separate limits or pagination for lines, or a dedicated detail endpoint when opening a single order.

Measure with realistic data sizes, inspect execution plans, and monitor connection counts, query durations, and returned row counts. A well-indexed `IN` query is usually effective, though one huge batch is not guaranteed to outperform multiple smaller batches.

## 12. Common Mistakes

### Calling a Repository Once per Parent Record

This is the N+1 query pattern. Collect parent group IDs and fetch all child data in one query or bounded batches.

### Querying Children When the ID List Is Empty

No IDs means no query needed. Return an empty result immediately to avoid `IN ()` and a wasted database round trip.

### Not Grouping Results by Foreign Key

After fetching all child lines, build a map keyed by `orderId` or the corresponding key. Returning a flat list forces callers to search linearly, creating expensive nested loops.

### Losing Parent List Ordering

A `Map` is not a structure for representing parent order. When assembling, iterate the original parent list and look up by ID. If child ordering matters, sort children by their business column.

### Putting Too Many IDs in One IN Clause

Databases and drivers have parameter limits, and massive SQL statements can slow down. Split into batches, process with bounded concurrency, or paginate parents.

### Using Unbounded flatMap for Multiple Batches

This can open too many simultaneous queries and exhaust the connection pool. Use sequential `concatMap` or `flatMap` with an explicit concurrency limit.

### Using block or subscribe Inside a Service

Operations should be chained in the reactive pipeline via `flatMap`, `map`, `zip`, and appropriate operators. `block()` blocks threads; internal `subscribe()` strips callers of completion and error control.

### Missing Index on the Foreign Key

An `IN` query may fall back to a full table scan if `order_id` lacks a suitable index. Inspect execution plans and indexes on grouping columns.

### Confusing Batch Reading with SQL GROUP BY

Reading by an ID set is a strategy to fetch rows for a set of keys and group results in the application. SQL `GROUP BY` aggregates rows inside the database. The two concepts can be combined, but they are not the same thing.

### Ignoring Consistency Between Two Queries

If data mutates between parent and child reads, assembled results may not reflect a uniform snapshot. Use suitable transactions and isolation if business rules require it.

## 13. Implementation Workflow

1. Identify the parent records and child datasets to display.
2. Identify the foreign key or linking IDs between tables.
3. Read the parent set with clear filters, sorting, and limits.
4. Handle an empty parent set before calling the child repository.
5. Extract IDs, deduplicate them, and verify valid IDs.
6. Query child records by ID set via an `In` derived query, Template, or parameterized SQL.
7. If the ID set is large, split into batches and bound concurrency.
8. Group child results by foreign key via `collectMultimap` or an appropriate map structure.
9. Assemble by iterating the original parent list to preserve order and supply empty collections for childless parents.
10. Consider transactions/isolation when both reads require consistency.
11. Check indexes, returned row counts, memory footprint, and query latency.
12. Test empty cases, many children, duplicate IDs, batch boundaries, and concurrent data changes.

## 14. Key Checklist

- [ ] Parent query has a result limit and deterministic sort order.
- [ ] Foreign key is explicitly represented in the child entity.
- [ ] Child repository supports querying by ID set, e.g., `findByOrderIdIn(...)`.
- [ ] No separate child query is fired per parent record.
- [ ] Child query is skipped when the ID set is empty.
- [ ] IDs are deduplicated and keep the proper data type.
- [ ] Child results are grouped by foreign key.
- [ ] Assembly iterates the original parent list to preserve order.
- [ ] Parents with no children are still returned with empty collections if required.
- [ ] Large ID sets are batched or parent-paginated.
- [ ] Concurrent batch count matches connection pool capacity.
- [ ] Values are parameter-bound; IDs are never concatenated into SQL.
- [ ] Foreign key column has an index and execution plans were checked.
- [ ] Transaction/isolation matches data consistency requirements.
- [ ] No `block()` or internal `subscribe()` is used to stitch reactive pipelines.

Reading an identifier set and querying in batches is a practical pattern for loading related data in Spring Data R2DBC without triggering N+1 queries. By bounding the parent set, querying children with `IN`, grouping results by foreign key, and assembling them in the same reactive pipeline, the application controls database round trips and response structure. When ID sets grow large, split into batches or paginate; when a consistent snapshot is needed, configure database transactions and isolation appropriately.
