# Khởi tạo schema và dữ liệu kiểm thử có thể lặp lại

Kiểm thử Spring Data R2DBC chỉ đáng tin cậy khi mỗi lần chạy bắt đầu từ một trạng thái database đã biết. Nếu schema còn sót từ lần chạy trước, dữ liệu fixture bị thay đổi hoặc test phụ thuộc vào thứ tự thực thi, cùng một bộ test có thể lúc thành công lúc thất bại. Những lỗi này thường khó tái hiện trên máy lập trình viên và càng khó chẩn đoán trong CI.

Khởi tạo có thể lặp lại (*repeatable test initialization*) nghĩa là test có thể tạo đúng schema và dữ liệu cần thiết một cách dự đoán được, chạy lại nhiều lần mà không phụ thuộc trạng thái còn lại từ lần trước. Với R2DBC, cần chọn rõ ai sở hữu schema, dùng script hay migration, tạo database cô lập như thế nào, nạp fixture ra sao và dọn dữ liệu ở thời điểm nào.

Một quy trình tốt thường kết hợp database thật qua Testcontainers, schema được tạo bằng migration hoặc SQL script, fixture có giá trị xác định, truy vấn reactive được kiểm tra bằng `StepVerifier`, và cơ chế cô lập dữ liệu phù hợp với việc chạy test song song.

## 1. Vì sao cần khởi tạo lặp lại?

Một test repository có thể phụ thuộc vào nhiều điều kiện:

- Bảng và cột đã tồn tại với đúng kiểu dữ liệu.
- Primary key, unique constraint và foreign key đã được tạo.
- Dữ liệu cha được insert trước dữ liệu con.
- Timestamp, trạng thái và số tiền có giá trị xác định.
- Sequence/identity đang ở trạng thái hợp lệ.
- Không còn dữ liệu do test trước để lại.
- Database và driver có cùng hành vi như môi trường cần triển khai.

Nếu test chỉ chạy được sau khi một developer đã tự tạo schema bằng tay, test chưa độc lập. Nếu test thứ hai cần test thứ nhất chạy trước để có dữ liệu, test suite phụ thuộc thứ tự. Nếu chạy lại một test làm phát sinh duplicate key vì fixture cũ vẫn còn, khâu khởi tạo hoặc cleanup chưa lặp lại được.

### 1.1. Những mục tiêu cần đạt

Một quy trình khởi tạo tốt nên đáp ứng:

1. **Deterministic:** cùng một test setup tạo cùng cấu trúc và dữ liệu đầu vào.
2. **Isolated:** test không đọc hoặc sửa dữ liệu của test khác.
3. **Repeatable:** có thể chạy lại sau khi test trước thành công hoặc thất bại.
4. **Versioned:** schema thay đổi được quản lý bằng script/migration trong repository.
5. **Representative:** database test có hành vi gần với database mục tiêu.
6. **Observable:** khi khởi tạo lỗi, log chỉ ra script, migration hoặc constraint gây lỗi.

### 1.2. Không dùng một database developer dùng chung làm fixture

Database local có thể chứa dữ liệu thử thủ công, dữ liệu từ một nhánh code cũ hoặc schema không còn đồng bộ. Dùng database đó trong test khiến kết quả phụ thuộc máy. Tạo database/container riêng cho test hoặc ít nhất một schema riêng được reset theo quy trình tự động.

## 2. Chọn cách khởi tạo schema

Có ba cách thường gặp trong dự án Spring Data R2DBC:

| Cách | Phù hợp khi | Điểm cần lưu ý |
|---|---|---|
| `schema.sql` và `data.sql` | Test nhỏ, schema đơn giản, muốn setup nhanh | Script cần được quản lý cẩn thận; cú pháp có thể phụ thuộc database |
| Migration như Flyway/Liquibase | Schema phát triển theo phiên bản và cần cùng quy trình với production | Nhiều công cụ migration thường kết nối bằng JDBC; cần cấu hình riêng nếu ứng dụng chạy R2DBC |
| `ConnectionFactoryInitializer` và `ResourceDatabasePopulator` | Muốn chủ động chỉ định script R2DBC trong cấu hình test | Phải kiểm soát thứ tự khởi tạo và tránh chạy trùng với Boot SQL init |

Không dùng nhiều cơ chế cùng tạo một schema nếu chưa xác định rõ thứ tự và quyền sở hữu. Ví dụ, nếu migration là nguồn sự thật của schema, không để `schema.sql` tạo lại cùng bảng theo một cấu trúc khác.

## 3. Khởi tạo bằng schema.sql và data.sql

Spring Boot hỗ trợ khởi tạo database bằng SQL script. Với database không phải embedded như PostgreSQL trong Testcontainers, thường cần bật `spring.sql.init.mode=always` trong profile test.

Ví dụ cấu hình `application-test.yml`:

```yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:db/test/schema.sql
      data-locations: classpath:db/test/data.sql
      continue-on-error: false
```

`schema-locations` chỉ định script tạo schema; `data-locations` chỉ định fixture được nạp sau khi schema đã sẵn sàng. `continue-on-error: false` giúp test thất bại ngay khi script có lỗi, thay vì tiếp tục với database chỉ được khởi tạo một phần.

Spring Boot cũng hỗ trợ cấu hình script theo platform, chẳng hạn `schema-${platform}.sql` và `data-${platform}.sql` khi đặt `spring.sql.init.platform`. Cách này hữu ích nếu test chạy trên nhiều hệ quản trị có cú pháp DDL/DML khác nhau.

### 3.1. Ví dụ schema.sql

Ví dụ schema PostgreSQL cho khách hàng, đơn hàng và dòng hàng:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id),
    order_code VARCHAR(32) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL DEFAULT 'NEW',
    created_at TIMESTAMPTZ NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    line_number INTEGER NOT NULL,
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(19, 2) NOT NULL,
    CONSTRAINT uq_order_line_number UNIQUE (order_id, line_number)
);

CREATE INDEX idx_orders_customer_created
    ON orders(customer_id, created_at DESC);

CREATE INDEX idx_order_lines_order
    ON order_lines(order_id);
```

Script tạo bảng cha trước bảng con để foreign key có thể được khai báo. Index và constraint là một phần của schema cần kiểm thử; không nên bỏ chúng chỉ để test insert dễ hơn nếu ứng dụng production dựa vào chúng.

### 3.2. Ví dụ data.sql với fixture xác định

```sql
INSERT INTO customers (email, display_name)
VALUES
    ('an@example.test', 'An Nguyen'),
    ('binh@example.test', 'Binh Tran');

INSERT INTO orders (customer_id, order_code, status, created_at)
SELECT id, 'ORD-TEST-001', 'PAID', TIMESTAMPTZ '2026-01-10 08:00:00+00'
FROM customers
WHERE email = 'an@example.test';

INSERT INTO orders (customer_id, order_code, status, created_at)
SELECT id, 'ORD-TEST-002', 'NEW', TIMESTAMPTZ '2026-01-11 09:00:00+00'
FROM customers
WHERE email = 'binh@example.test';

INSERT INTO order_lines (order_id, line_number, product_code, quantity, unit_price)
SELECT id, 1, 'BOOK-001', 2, 125000.00
FROM orders
WHERE order_code = 'ORD-TEST-001';
```

Fixture không dựa vào ID identity cụ thể. Script tìm khóa cha bằng natural key ổn định như email hoặc order code. Cách này tránh giả định rằng ID đầu tiên luôn là 1, nhất là khi database không được tạo mới hoặc sequence đã tăng từ một test khác.

Timestamp được ghi tường minh thay vì dùng `CURRENT_TIMESTAMP`, nhờ đó test có thể so sánh chính xác và không phụ thuộc thời điểm chạy. Với dữ liệu cần timezone, dùng literal và kiểu cột phù hợp với database.

### 3.3. Script mặc định có thể chạy lại không?

`CREATE TABLE` thông thường sẽ lỗi nếu bảng đã tồn tại; `INSERT` thông thường sẽ lỗi nếu fixture vi phạm unique constraint sau lần chạy trước. Vì vậy, một cặp script không tự động trở thành repeatable chỉ vì được lưu trong `schema.sql` và `data.sql`.

Có hai chiến lược phổ biến:

- Tạo database/schema mới cho mỗi suite hoặc test class, sau đó chạy script một lần.
- Reset schema test về trạng thái rỗng trước khi tạo lại và nạp fixture.

Trong database cô lập dành riêng cho test, có thể bắt đầu `schema.sql` bằng lệnh drop bảng theo thứ tự phụ thuộc rồi tạo lại. Tuyệt đối không dùng script reset kiểu này cho database dùng chung hoặc production.

Ví dụ PostgreSQL test-only:

```sql
DROP TABLE IF EXISTS order_lines;
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS customers;

-- Sau đó là các câu CREATE TABLE và CREATE INDEX.
```

Lệnh drop có chủ đích destructive. Chỉ chạy khi test đang kết nối đến database/container được tạo riêng cho test.

### 3.4. Idempotent seed bằng upsert

Nếu không reset toàn bộ schema, có thể thiết kế seed script idempotent bằng upsert. Ví dụ PostgreSQL:

```sql
INSERT INTO customers (email, display_name)
VALUES ('an@example.test', 'An Nguyen')
ON CONFLICT (email)
DO UPDATE SET display_name = EXCLUDED.display_name;
```

Chạy lại script sẽ đưa bản ghi về cùng trạng thái fixture. Tuy nhiên, upsert không thay thế cleanup nếu test tạo thêm dữ liệu khác. Nó cũng không phải cú pháp portable; database khác có thể dùng `MERGE` hoặc cú pháp riêng.

Chỉ dùng `ON CONFLICT DO NOTHING` khi việc bỏ qua bản ghi đã có thực sự đúng. Nó có thể che giấu fixture cũ với nội dung khác. `DO UPDATE` rõ ràng hơn khi mục tiêu là đưa dữ liệu về trạng thái chuẩn.

## 4. Cấu hình SQL initialization theo test profile

Không nên vô tình chạy script test trên môi trường phát triển hoặc production. Đặt cấu hình trong `src/test/resources/application-test.yml` và kích hoạt profile từ test:

```java
@ActiveProfiles("test")
@DataR2dbcTest
class OrderRepositoryTest {
    // tests
}
```

Ví dụ cấu trúc tài nguyên:

```text
src/
  main/
    resources/
      application.yml
  test/
    resources/
      application-test.yml
      db/
        test/
          schema.sql
          data.sql
```

Profile test có thể cấu hình:

```yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:db/test/schema.sql
      data-locations: classpath:db/test/data.sql
      continue-on-error: false
```

Ở môi trường production, nếu migration tool quản lý schema, thường đặt script initialization ở trạng thái không chạy để tránh hai cơ chế cùng tác động database. Luôn kiểm tra profile thực tế khi khởi động test; không dựa vào tên file mà không xác nhận Spring đã nạp đúng cấu hình.

## 5. Dùng ConnectionFactoryInitializer khi cần cấu hình tường minh

Spring Framework cung cấp `ConnectionFactoryInitializer` và `ResourceDatabasePopulator` trong R2DBC để chạy script qua `ConnectionFactory`.

```java
@TestConfiguration
public class R2dbcTestDatabaseConfiguration {

    @Bean
    ConnectionFactoryInitializer testDatabaseInitializer(
            ConnectionFactory connectionFactory) {

        ConnectionFactoryInitializer initializer =
                new ConnectionFactoryInitializer();
        initializer.setConnectionFactory(connectionFactory);
        initializer.setDatabasePopulator(new ResourceDatabasePopulator(
                new ClassPathResource("db/test/schema.sql"),
                new ClassPathResource("db/test/data.sql")));
        return initializer;
    }
}
```

Các import tương ứng thường gồm:

```java
import org.springframework.context.annotation.Bean;
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.core.io.ClassPathResource;
import org.springframework.r2dbc.connection.init.ConnectionFactoryInitializer;
import org.springframework.r2dbc.connection.init.ResourceDatabasePopulator;
import io.r2dbc.spi.ConnectionFactory;
```

Initializer này hữu ích khi muốn tự chọn script, thứ tự hoặc cấu hình riêng. Nếu đã dùng `spring.sql.init.*` để chạy cùng script, không đăng ký thêm initializer chạy trùng. Chọn một cơ chế và kiểm tra thứ tự khởi tạo trước khi repository được sử dụng.

## 6. Dùng migration để kiểm thử schema theo phiên bản

Trong ứng dụng có schema phát triển theo thời gian, migration thường phù hợp hơn một `schema.sql` lớn. Mỗi thay đổi schema được lưu thành migration có thứ tự, ví dụ:

```text
src/main/resources/db/migration/
  V1__create_customers.sql
  V2__create_orders.sql
  V3__add_order_status_index.sql
```

Test chạy migrations từ đầu trên database mới sẽ xác nhận toàn bộ lịch sử schema có thể được áp dụng. Điều này giúp phát hiện migration cũ bị lỗi hoặc migration mới không tương thích với database mục tiêu.

### 6.1. Flyway/Liquibase và ứng dụng R2DBC

Nhiều công cụ migration phổ biến như Flyway và Liquibase thường sử dụng JDBC để kết nối và thay đổi schema. Ứng dụng có thể dùng R2DBC cho truy vấn runtime nhưng dùng một kết nối JDBC riêng để chạy migration trên cùng database. Khi làm vậy:

- Thêm JDBC driver và cấu hình migration connection nếu công cụ yêu cầu.
- Giữ URL, database, schema và credential của migration cùng môi trường với R2DBC.
- Chạy migration trước khi test repository bắt đầu truy vấn.
- Không để `schema.sql` tạo lại các bảng đã được migration quản lý.
- Xác nhận migration tool và phiên bản hỗ trợ database server đang dùng.

Không giả định migration tool tự chạy qua R2DBC chỉ vì ứng dụng có `spring.r2dbc.url`. Kiểm tra loại connection mà công cụ thực sự sử dụng.

### 6.2. Test migration từ database rỗng

Một bài test quan trọng là khởi tạo database mới hoàn toàn, chạy tất cả migration và thực hiện một số thao tác repository cơ bản. Không chỉ test migration trên database đã có schema cũ, vì trạng thái cũ có thể che giấu migration thiếu bước.

### 6.3. Test nâng cấp từ phiên bản trước

Nếu sản phẩm hỗ trợ nâng cấp database đã có dữ liệu, cần thêm test từ schema version trước đó với dữ liệu đại diện. Test này xác nhận migration không chỉ chạy trên database rỗng mà còn bảo toàn hoặc chuyển đổi dữ liệu hiện có đúng quy tắc.

## 7. Dùng Testcontainers để có database gần production

H2 hoặc một database embedded rất tiện cho test nhanh, nhưng không thể đại diện đầy đủ cho PostgreSQL, MySQL, SQL Server hoặc Oracle. Khác biệt có thể xuất hiện ở kiểu dữ liệu, cú pháp SQL, identity, generated column, JSON, collation, transaction isolation và lỗi constraint.

Testcontainers khởi chạy database thật trong container để integration test sử dụng đúng engine và driver dự kiến.

### 7.1. Khai báo dependency

Ví dụ với PostgreSQL và JUnit 5, dự án thường cần:

```gradle
testImplementation("org.testcontainers:junit-jupiter")
testImplementation("org.testcontainers:postgresql")
testImplementation("org.springframework.boot:spring-boot-starter-test")
testImplementation("io.projectreactor:reactor-test")
runtimeOnly("org.postgresql:r2dbc-postgresql")
```

Quản lý version bằng Spring Boot dependency management hoặc Testcontainers BOM phù hợp. Không đặt các version độc lập nếu dự án đã có BOM.

### 7.2. Tạo container và cấu hình R2DBC URL

```java
@Testcontainers
@DataR2dbcTest
@ActiveProfiles("test")
class OrderRepositoryIntegrationTest {

    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16.4-alpine")
                    .withDatabaseName("store_test")
                    .withUsername("test_user")
                    .withPassword("test_password");

    @DynamicPropertySource
    static void configureR2dbc(DynamicPropertyRegistry registry) {
        registry.add("spring.r2dbc.url", () ->
                "r2dbc:postgresql://" + postgres.getHost() + ":"
                        + postgres.getMappedPort(5432) + "/"
                        + postgres.getDatabaseName());
        registry.add("spring.r2dbc.username", postgres::getUsername);
        registry.add("spring.r2dbc.password", postgres::getPassword);
    }

    @Autowired
    OrderRepository orderRepository;
}
```

Ví dụ dùng image đã pin version để kết quả CI có thể tái tạo. R2DBC URL được tạo từ host và mapped port mà Testcontainers cung cấp; không dùng cổng mặc định của máy host vì container thường được ánh xạ sang cổng động.

`@DynamicPropertySource` đăng ký các thuộc tính trước khi Spring tạo `ConnectionFactory`. Test cần có R2DBC driver tương ứng trong test runtime. Nếu dự án dùng phiên bản Spring Boot có cơ chế service connection phù hợp cho R2DBC, có thể dùng cách đó; hãy kiểm tra hỗ trợ của phiên bản đang dùng thay vì giả định annotation luôn tự cấu hình đúng.

### 7.3. Khởi tạo script trong container

Với profile test ở phần trước, Spring Boot có thể chạy `schema.sql` và `data.sql` trên database container khi ApplicationContext khởi động. Vì container là database thật, script sẽ được kiểm tra bằng đúng cú pháp PostgreSQL và đúng driver R2DBC.

Nếu dùng migration tool, hãy cấu hình migration chạy trên cùng container trước khi test repository. Tránh đồng thời chạy migration và `schema.sql` cho cùng bảng.

### 7.4. Pin image và môi trường

Không dùng `postgres:latest` trong test cần tính tái tạo. Pin major/minor hoặc patch version đã được dự án xác nhận. Với test nhạy cảm, ghi rõ image digest hoặc quy trình cập nhật image. Cũng cần cố định locale, timezone, extension và cấu hình server nếu chúng ảnh hưởng kết quả.

## 8. Tổ chức fixture sao cho xác định

Fixture tốt làm cho test đọc dễ hiểu và không phụ thuộc dữ liệu ngẫu nhiên.

### 8.1. Dùng natural key ổn định

Ưu tiên tìm bản ghi bằng mã nghiệp vụ cố định như `ORD-TEST-001` hoặc `an@example.test` thay vì giả định ID identity luôn là một con số cụ thể.

```java
repository.findByOrderCode("ORD-TEST-001");
```

Nếu test cần kiểm tra generated ID, xác nhận ID khác null và có thể đọc lại theo ID vừa nhận; không cần giả định nó bằng `1`.

### 8.2. Cố định thời gian

Tránh fixture dùng `CURRENT_TIMESTAMP`, `now()` hoặc `Instant.now()` nếu assertion phụ thuộc chính xác timestamp. Dùng giá trị cố định:

```java
Instant createdAt = Instant.parse("2026-01-10T08:00:00Z");
```

Nếu test cần kiểm tra auditing dùng clock hiện tại, inject `Clock` và dùng clock cố định trong test. Điều này tránh test thất bại khi chạy qua ranh giới giây, ngày hoặc timezone.

### 8.3. Tạo fixture qua builder/factory

Khi entity có nhiều thuộc tính, tạo factory test để các giá trị mặc định được quản lý tập trung:

```java
final class OrderFixtures {

    private OrderFixtures() {
    }

    static OrderEntity newOrder(String orderCode, Long customerId) {
        return new OrderEntity(
                null,
                customerId,
                orderCode,
                "NEW",
                Instant.parse("2026-01-10T08:00:00Z"));
    }
}
```

Factory không nên che giấu dữ liệu quan trọng. Khi test kiểm tra trạng thái `PAID`, hãy truyền rõ trạng thái đó trong test hoặc tạo factory có tên thể hiện ý nghĩa.

### 8.4. Tôn trọng thứ tự foreign key

Insert dữ liệu cha trước con; cleanup con trước cha nếu không dùng cascade. Ví dụ:

1. Insert customer.
2. Insert order tham chiếu customer.
3. Insert order line tham chiếu order.

Khi xóa:

1. Xóa order lines.
2. Xóa orders.
3. Xóa customers.

Không tắt foreign key trong test chỉ để fixture dễ nạp, vì làm vậy bỏ qua một phần quan trọng của schema.

## 9. Cleanup và reset dữ liệu giữa các test

Có nhiều cách reset dữ liệu; lựa chọn phụ thuộc tốc độ, isolation và khả năng chạy song song.

### 9.1. Dùng database mới cho mỗi suite hoặc class

Đây là cách cô lập tốt và dễ hiểu. Testcontainers tạo database/container mới, chạy schema và fixture một lần cho suite. Khi container kết thúc, toàn bộ trạng thái biến mất.

Ưu điểm:

- Không phụ thuộc dữ liệu từ lần chạy trước.
- Có thể dùng script destructive an toàn trong database riêng.
- Dễ kiểm tra migration từ trạng thái rỗng.

Nhược điểm là khởi động container có chi phí. Có thể dùng một container cho một test class hoặc suite và reset dữ liệu giữa các test.

### 9.2. Xóa dữ liệu có chọn lọc

Với một database dùng chung cho class, có thể xóa fixture do test tạo trước mỗi test. Ví dụ dùng `DatabaseClient`:

```java
Mono<Void> cleanOrderFixtures() {
    return databaseClient.sql("DELETE FROM order_lines")
            .fetch().rowsUpdated()
            .then(databaseClient.sql("DELETE FROM orders")
                    .fetch().rowsUpdated())
            .then(databaseClient.sql("DELETE FROM customers")
                    .fetch().rowsUpdated())
            .then();
}
```

Thứ tự xóa tuân theo foreign key. Có thể giới hạn theo mã fixture hoặc tenant test nếu nhiều test chia sẻ database. Không dùng cleanup toàn bảng khi test khác có thể đang chạy trên cùng database.

### 9.3. TRUNCATE và reset identity

PostgreSQL hỗ trợ:

```sql
TRUNCATE TABLE order_lines, orders, customers
RESTART IDENTITY CASCADE;
```

Lệnh này xóa nhanh dữ liệu, reset sequence/identity và xử lý quan hệ theo cascade. Đây là cú pháp phụ thuộc PostgreSQL; database khác có quy tắc truncate khác nhau. Chỉ chạy trong database test cô lập, không dùng trên database dùng chung hoặc production.

### 9.4. Transaction rollback trong test reactive

Rollback có thể giúp dọn dữ liệu sau test, nhưng không nên mặc định rằng mọi test R2DBC tự động rollback chỉ vì có annotation `@Transactional`. Transaction test phụ thuộc transaction manager và cách subscription reactive được quản lý. Hãy xác nhận hỗ trợ của phiên bản Spring Test/Spring Boot và cách test thực sự subscribe publisher.

Một lựa chọn rõ ràng là bọc các thao tác test trong `TransactionalOperator` khi cần transaction reactive và đánh dấu rollback-only trong luồng test. Tuy nhiên, nếu test đang kiểm tra commit, transaction isolation, nhiều connection hoặc dữ liệu cần tồn tại sau khi publisher kết thúc, rollback có thể làm sai kịch bản. Với các test đó, dùng database/schema cô lập và cleanup tường minh thường dễ dự đoán hơn.

### 9.5. Không trộn rollback với test concurrency một cách vô ý

Test optimistic locking hoặc transaction isolation cần nhiều transaction/connection thực sự. Nếu toàn bộ setup và thao tác được bọc trong một transaction test, test có thể không mô phỏng đúng hai request đồng thời. Thiết kế transaction boundary theo chính kịch bản cần kiểm tra.

## 10. Viết test reactive với StepVerifier

Repository R2DBC trả về `Mono` hoặc `Flux`; test nên subscribe và kiểm tra publisher bằng `StepVerifier`.

Ví dụ:

```java
@Test
void findsSeededOrder() {
    StepVerifier.create(orderRepository.findByOrderCode("ORD-TEST-001"))
            .assertNext(order -> {
                assertThat(order.orderCode()).isEqualTo("ORD-TEST-001");
                assertThat(order.status()).isEqualTo("PAID");
            })
            .verifyComplete();
}
```

`StepVerifier` xác nhận publisher phát đúng dữ liệu và hoàn tất. Với `Flux`, có thể kiểm tra số lượng, thứ tự, lỗi và thời gian nếu cần.

### 10.1. Không dùng block trong code ứng dụng

Không gọi `.block()` trong Service/Repository để làm test dễ viết. Điều đó phá vỡ mô hình reactive và có thể deadlock hoặc chặn event loop. Trong test, `StepVerifier` là lựa chọn tự nhiên vì nó điều khiển subscription và assertion.

Một số test setup/cleanup imperative có thể gọi `.block()` trên thread JUnit thông thường, nhưng hãy giới hạn ở ranh giới test và không chạy nó từ Reactor event-loop thread. Nếu có thể, kết hợp setup/cleanup vào publisher của test để toàn bộ luồng vẫn reactive.

### 10.2. Kết hợp setup và hành động trong cùng test

```java
@Test
void savesAndReadsOrder() {
    Mono<OrderEntity> scenario = cleanOrderFixtures()
            .then(customerRepository.save(
                    new CustomerEntity(null, "test@example.test", "Test User")))
            .flatMap(customer -> orderRepository.save(
                    OrderFixtures.newOrder("ORD-NEW-001", customer.id())))
            .flatMap(saved -> orderRepository.findById(saved.id()));

    StepVerifier.create(scenario)
            .assertNext(found -> {
                assertThat(found.id()).isNotNull();
                assertThat(found.orderCode()).isEqualTo("ORD-NEW-001");
            })
            .verifyComplete();
}
```

Ví dụ minh họa setup, insert và read trong một pipeline. Trong suite có nhiều test, nên đưa cleanup vào `@BeforeEach` hoặc một helper nhất quán, đồng thời bảo đảm các fixture có key riêng để không va chạm.

## 11. Kiểm thử bằng @DataR2dbcTest

`@DataR2dbcTest` là test slice của Spring Boot dành cho Spring Data R2DBC. Nó tập trung vào các thành phần persistence như repository, mapping và cấu hình R2DBC cần thiết, thay vì khởi tạo toàn bộ web application.

Ví dụ cấu trúc:

```java
@DataR2dbcTest
@ActiveProfiles("test")
class OrderRepositoryTest {

    @Autowired
    OrderRepository orderRepository;

    @Autowired
    DatabaseClient databaseClient;

    @Test
    void readsOrderFromFixture() {
        StepVerifier.create(orderRepository.findByOrderCode("ORD-TEST-001"))
                .expectNextMatches(order -> order.status().equals("PAID"))
                .verifyComplete();
    }
}
```

Test slice giúp test nhanh hơn và giới hạn phạm vi bean. Nếu cần cấu hình Testcontainers, custom converter, auditing hoặc repository bổ sung, import cấu hình test cần thiết bằng annotation phù hợp. Không giả định mọi bean của ứng dụng đã được load trong `@DataR2dbcTest`.

Nếu test cần WebFilter, Security chain, Controller hoặc toàn bộ Service graph, dùng `@SpringBootTest` hoặc một test slice khác phù hợp thay vì cố mở rộng `@DataR2dbcTest` thành integration test toàn ứng dụng.

## 12. @Sql có phải lựa chọn cho R2DBC không?

Annotation `@Sql` của Spring Test thuộc cơ chế thực thi SQL qua JDBC `DataSource`. Nó không tự động chạy script bằng `ConnectionFactory` R2DBC chỉ vì test class dùng `@DataR2dbcTest`.

Nếu dự án có cả JDBC `DataSource` và R2DBC `ConnectionFactory`, `@Sql` có thể chạy script qua JDBC connection, nhưng đó là một đường kết nối riêng. Cần bảo đảm cả hai kết nối trỏ cùng database/schema và script chạy trước khi test R2DBC truy vấn.

Với test chỉ dùng R2DBC, ưu tiên:

- Spring Boot `spring.sql.init.*`.
- `ConnectionFactoryInitializer`/`ResourceDatabasePopulator`.
- Migration tool được cấu hình rõ ràng.
- `DatabaseClient` để setup/cleanup bằng publisher.

Không chọn `@Sql` chỉ vì nó quen thuộc trong test JDBC.

## 13. Chạy test song song an toàn

Khi bật parallel test execution, nhiều test có thể cùng truy cập một database/container. Một test reset bảng trong lúc test khác đang đọc sẽ làm kết quả không xác định.

### 13.1. Các chiến lược cô lập

| Chiến lược | Mức cô lập | Chi phí | Phù hợp |
|---|---|---|---|
| Container/database riêng cho mỗi test class | Cao | Khởi tạo nhiều hơn | Test cần schema/data độc lập |
| Schema riêng cho mỗi worker/test class | Cao nếu search path được cấu hình đúng | Trung bình | Nhiều test chạy song song trên một server |
| Tenant hoặc fixture key riêng | Trung bình | Thấp | Test chỉ thao tác dữ liệu có thể phân vùng |
| Một database chung và TRUNCATE trước mỗi test | Thấp khi chạy song song | Thấp | Test chạy tuần tự |
| Tắt parallel cho nhóm test dùng chung DB | Tránh race trong nhóm | Có thể chậm hơn | Test có cleanup toàn bảng hoặc dùng ID cố định |

### 13.2. Không dùng chung fixture key giữa test song song

Nếu hai test cùng insert `ORD-TEST-001`, unique constraint sẽ làm một test thất bại. Dùng database/schema riêng hoặc tạo key test có namespace riêng. Nếu key được sinh ngẫu nhiên, vẫn cần lưu key vào biến test để cleanup đúng bản ghi; đừng dựa vào thứ tự chạy.

### 13.3. Tránh reset toàn bảng trong @BeforeEach khi chạy song song

`TRUNCATE` hoặc `DELETE FROM` không phân biệt dữ liệu của test hiện tại và test khác. Khi nhiều test dùng chung schema, cleanup toàn bảng có thể xóa dữ liệu mà test khác đang sử dụng. Dùng schema/database riêng hoặc cleanup theo fixture key.

### 13.4. Connection pool trong test

Nhiều test song song cũng tạo tải lên connection pool. Nếu pool quá nhỏ, test có thể timeout dù logic đúng; nếu pool quá lớn, container database có thể bị quá tải. Chọn pool size phù hợp với số test đồng thời và tài nguyên CI. Không tăng pool để che deadlock hoặc query bị giữ connection.

## 14. Schema test và migration production

Có thể dùng cùng migration production cho integration test để xác nhận schema thực tế. Đây thường là cách tốt nhất khi migration là nguồn sự thật của database.

Nếu test cần dữ liệu tối giản hơn, tạo fixture riêng nhưng vẫn dùng schema đã được migration tạo. Tránh duy trì một `schema.sql` test khác biệt lâu dài với production, vì nó có thể khiến test pass trong khi migration production thiếu cột, index hoặc constraint.

Nếu có nhu cầu test nhiều phiên bản schema:

- Test database rỗng chạy toàn bộ migration.
- Test nâng cấp từ phiên bản schema cũ có dữ liệu đại diện.
- Test tương thích với các constraint và index quan trọng.
- Test rollback/forward strategy nếu quy trình vận hành yêu cầu.

## 15. Các lỗi thường gặp

### Script chỉ chạy được một lần

`CREATE TABLE` và `INSERT` có thể lỗi khi chạy lại. Tạo database mới, reset schema test hoặc dùng seed upsert có chủ đích.

### Dùng ID identity cố định trong assertion

ID có thể thay đổi theo sequence hoặc lịch sử database. Dùng natural key để tìm fixture; chỉ kiểm tra ID được sinh có giá trị nếu đó là điều cần xác nhận.

### Insert dữ liệu con trước dữ liệu cha

Foreign key làm script thất bại. Nạp dữ liệu theo dependency order và cleanup theo thứ tự ngược lại.

### Dùng timestamp hiện tại trong fixture

Test phụ thuộc thời điểm chạy và có thể thất bại ở ranh giới thời gian. Dùng timestamp cố định hoặc clock giả lập.

### Dùng H2 thay database production cho mọi test

Test có thể bỏ sót khác biệt SQL, data type, identity, JSON, transaction và error mapping. Dùng Testcontainers cho các hành vi phụ thuộc database.

### Chạy đồng thời migration và schema.sql

Hai cơ chế cùng tạo bảng hoặc thay đổi cột có thể xung đột. Chọn một nguồn quản lý schema.

### Giả định @Sql chạy qua R2DBC

`@Sql` sử dụng JDBC `DataSource`. Với R2DBC, dùng initializer hoặc DatabaseClient nếu không có JDBC path được cấu hình rõ.

### Cho rằng test tự rollback

Reactive transaction trong test cần được xác nhận theo transaction manager và cách subscription. Dùng cleanup hoặc database cô lập khi không chắc chắn.

### Cleanup toàn bảng khi test chạy song song

Một test có thể xóa dữ liệu test khác. Cô lập schema/database hoặc cleanup theo fixture key.

### Dùng Testcontainers image latest

Server version thay đổi có thể làm test không tái tạo được. Pin image version và cập nhật có chủ đích.

### Test chỉ kiểm tra mock repository

Mock không kiểm tra schema, SQL dialect, mapping, foreign key hoặc driver. Bổ sung integration test trên database thật.

## 16. Quy trình thiết lập bộ test có thể lặp lại

1. Chọn database engine và version gần production.
2. Tạo database/container hoặc schema riêng cho test.
3. Pin image và dependency version để môi trường có thể tái tạo.
4. Chọn một nguồn sở hữu schema: migration hoặc SQL initialization.
5. Cấu hình profile test để script không chạy nhầm ở môi trường khác.
6. Tạo schema theo đúng dependency order, gồm constraint và index quan trọng.
7. Nạp fixture bằng giá trị xác định, natural key và timestamp cố định.
8. Xác định cách reset: database mới, schema reset, cleanup chọn lọc hoặc transaction rollback đã được xác nhận.
9. Dùng `StepVerifier` để kiểm tra repository và pipeline reactive.
10. Kiểm thử generated ID, default, constraint và mapping trên đúng driver.
11. Cô lập dữ liệu nếu test chạy song song; tránh truncate database dùng chung.
12. Chạy migration từ database rỗng và test nâng cấp nếu dự án có yêu cầu.
13. Ghi log rõ script/migration nào thất bại và dừng test khi initialization lỗi.
14. Chạy lại cùng test nhiều lần và trong CI để xác nhận không phụ thuộc trạng thái máy.

## 17. Checklist ghi nhớ

- [ ] Database test được tạo tự động và không phụ thuộc database developer dùng chung.
- [ ] Database engine/version gần với production cho các integration test quan trọng.
- [ ] Testcontainers image và dependency được pin version.
- [ ] Chỉ có một cơ chế chính quản lý schema cho mỗi test context.
- [ ] `spring.sql.init.mode` và locations được cấu hình trong test profile khi dùng script.
- [ ] `continue-on-error` không che lỗi khởi tạo schema.
- [ ] Fixture có natural key ổn định và timestamp xác định.
- [ ] Dữ liệu cha được nạp trước dữ liệu con.
- [ ] ID identity không bị giả định là một giá trị cố định.
- [ ] Seed script có chiến lược chạy lại rõ ràng.
- [ ] Cleanup tuân thủ foreign key và không xóa dữ liệu test khác.
- [ ] Không mặc định `@Transactional` tự rollback mọi reactive test.
- [ ] `@Sql` không bị nhầm là script runner R2DBC.
- [ ] Test repository dùng `StepVerifier` và kiểm tra cả giá trị lẫn completion/error.
- [ ] Test song song có database/schema/fixture isolation phù hợp.
- [ ] Migration production được chạy trong integration test nếu là nguồn schema chính.
- [ ] Bộ test có thể chạy lại nhiều lần trên máy khác và CI.

Khởi tạo schema và fixture có thể lặp lại là nền tảng của integration test R2DBC đáng tin cậy. Khi database được cô lập, schema có một nguồn quản lý rõ ràng, dữ liệu kiểm thử xác định và cleanup phù hợp với cách chạy song song, mỗi lần test sẽ bắt đầu từ trạng thái có thể dự đoán. Kết hợp Testcontainers, migration hoặc SQL initializer và `StepVerifier` giúp kiểm tra cả hành vi của Spring Data lẫn database/driver thực tế mà ứng dụng sử dụng.
