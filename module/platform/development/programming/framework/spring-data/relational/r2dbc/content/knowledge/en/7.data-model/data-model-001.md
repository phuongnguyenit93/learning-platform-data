# Designing Persistence Entities vs. API Models

In a Spring Data R2DBC application, a *persistence entity* describes how data is mapped to database tables and columns. An *API model* (or DTO) describes the data an application receives from a client and returns over HTTP or another protocol. The two models may contain some of the same properties, but they serve two different boundaries and should not be forced to change together.

Good design starts from the schema and business rules, then determines which data needs to be stored, which data is allowed to be accepted from the outside, and which data is allowed to be exposed. Spring Data R2DBC supports entity mapping under the relational model; it does not automatically turn an entity into a safe API object, nor does it provide full ORM behavior like JPA/Hibernate.

## 1. Distinguishing Data Models in an Application

An application often has multiple representations of the same information. For example, a customer might be stored in the `customers` table, created from a JSON request, and returned as a JSON response. These representations serve different purposes:

| Model | Purpose | Example properties |
|---|---|---|
| Persistence entity | Maps stored data and Spring Data metadata | `id`, `email`, `displayName`, `version` |
| Request DTO / command | Represents data the client is allowed to send for an operation | `email`, `displayName` |
| Response DTO | Represents data allowed to be returned to the client | `id`, `email`, `displayName` |
| Domain model | Represents domain concepts and business rules, if the application separates it | `Customer`, rename behavior, state rules |
| Query projection | Contains only the fields needed for a query or screen | `id`, `displayName`, `orderCount` |

Not every project needs a separate class for all five models. For a small CRUD application, the persistence entity can also represent part of the domain model. However, request and response DTOs should still be designed around the API contract, especially when the application has internal data, sensitive information, or complex update rules.

Typical data flow:

```text
                 HTTP / JSON
                      |
                      v
              Request DTO / Command
                      |
             validation + mapping
                      |
                      v
               Service / Domain
                      |
                Repository API
                      |
                      v
              Persistence Entity
                      |
                Spring Data R2DBC
                      |
                      v
               Relational tables

Response path goes in reverse through mapping:
Entity / Domain -> Response DTO -> JSON
```

The Controller handles the protocol, the Service orchestrates business logic, and the Repository accesses data. Converting between request/response and entity should happen at an intentional boundary, typically a mapper or application service.

## 2. Designing a Persistence Entity from a Relational Schema

### 2.1. Start from Data and Business Lifecycle

Before writing the Java class, determine:

- Which domain concept the storage table represents.
- Which properties are required and which can be nullable.
- Whether the primary key is auto-generated or assigned by the application.
- Which values need to be unique or constrained in the database.
- Which data belongs to the same aggregate and has a dependent lifecycle.
- Which relationships are only references to other aggregates.
- Which operations need to execute within the same transaction.

For example, the `customers` table might include:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(254) NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL,
    version BIGINT
);
```

The schema defines data types, requiredness, uniqueness, and the primary key. The Java entity should map those decisions accurately. Do not rely solely on Java property types to assume the database has the corresponding constraints; integrity constraints must be defined in the schema.

### 2.2. Using Spring Data Relational Mapping Annotations

Common annotations:

| Annotation | Role |
|---|---|
| `@Table` | Declares the table that the entity maps to |
| `@Id` | Marks the identifier property |
| `@Column` | Specifies the column name when needed |
| `@Transient` | Marks a property that is not persisted in the mapping |
| `@Version` | Supports optimistic locking using a version field |
| `@MappedCollection` | Declares how an aggregate's collection is mapped to a relational table |

Example `Customer` entity:

```java
package com.example.store.customer.persistence;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record CustomerEntity(
        @Id Long id,
        String email,
        @Column("display_name") String displayName,
        @Version Long version
) {
}
```

In this example:

- `@Table("customers")` maps the record to the `customers` table.
- `@Id` marks the primary key.
- `email` uses the column name according to the default mapping rules.
- `@Column("display_name")` maps `displayName` to `display_name`.
- `@Version` provides a version so Spring Data can support concurrent update control via optimistic locking.

If table and column names already follow the default naming strategy, some explicit annotations can be omitted. Use `@Table` and `@Column` when the schema name needs to be stated explicitly or differs from the Java property name.

### 2.3. Choosing Java Types Compatible with Database Types

Java types must match the column types and R2DBC driver support. Common choices include:

| Data | Common Java Type | Notes |
|---|---|---|
| Integer identifier | `Long`, `Integer` | Choose based on the primary key type in the schema; wrapper types can represent an unset value |
| String | `String` | Length and normalization rules are governed by the schema and business rules |
| Currency | `BigDecimal` | Avoid using `double` for monetary calculations that require decimal precision |
| Date | `LocalDate` | Use when only a calendar date matters |
| Point in time | `Instant` or an appropriate temporal type | Align time zone conventions and column types with the database |
| Boolean | `Boolean` or `boolean` | Use the wrapper if the column can be `NULL` |
| Finite set of states | `String` or `enum` | Clearly define storage format and compatibility when adding new states |

Do not choose a data type solely because it is convenient for JSON. For example, a monetary amount in an entity should be `BigDecimal`; the API can represent it as a JSON number or string according to the agreed contract. Currency formatting and display symbols belong to the API or UI layer.

### 2.4. Primary Keys and Entity Lifecycle

With a database-generated primary key, a new entity typically has `id == null`. When calling `save`, Spring Data R2DBC performs the operation appropriate for the new/existing state and returns the saved entity; use the returned value because it may contain the generated ID and updated metadata.

```java
CustomerEntity newCustomer = new CustomerEntity(
        null,
        "linh@example.com",
        "Linh Nguyen",
        null
);

return customerRepository.save(newCustomer);
```

Do not assign a dummy ID just to represent a new entity when the database is responsible for key generation. If the application uses pre-assigned IDs or a custom newness detection strategy, configure the newness strategy appropriate for Spring Data Relational.

Immutable entities, such as Java records, help represent the data of a single state clearly. When changing a property, create a new instance instead of mutating it directly. Spring Data supports materializing entities via constructors; design constructors/records consistently with the actual mapping and data types.

### 2.5. Optimistic Locking with @Version

When multiple requests may update the same record concurrently, a version field helps detect updates based on stale data. Spring Data uses the version in update operations and increments it upon a successful save. If the record has already been modified by another transaction, the operation may fail due to an optimistic locking conflict.

`@Version` does not replace transactions, nor does it replace data constraints. It is suitable when you want to detect update conflicts without holding database locks while a user is editing. The API can expose the version as an `ETag` or a version field in the response if the contract needs conditional updates; exposing this internal property is not mandatory.

## 3. Designing Aggregates and Entity Relationships

Spring Data Relational organizes write operations around aggregates. An aggregate root is the entry point for persisting a group of objects that have a dependent lifecycle and must be managed as a business unit. This is a way of designing the model and write boundary; it does not mean Spring Data automatically loads all relationships like JPA lazy loading.

### 3.1. Distinguishing Data Inside an Aggregate from References to Other Aggregates

Suppose a sales system has `PurchaseOrder`, `OrderLine`, and `Customer`:

- An order owns its order lines; order lines have no independent meaning outside an order. They can be modeled as members of the order aggregate.
- A customer has an independent lifecycle from each order. An order typically stores `customerId` as a reference to the customer rather than embedding the entire customer entity inside the order aggregate.

Simple entity example:

```java
@Table("purchase_orders")
public record PurchaseOrderEntity(
        @Id Long id,
        @Column("customer_id") Long customerId,
        String status,
        BigDecimal totalAmount,
        @Version Long version
) {
}
```

`customerId` is a foreign key value. When customer details are needed, the application can query the corresponding repository or write a dedicated join/projection query. Do not expect that merely declaring a `CustomerEntity customer` property will cause Spring Data R2DBC to automatically load the customer via JPA-style lazy/eager relationships.

### 3.2. Collections Belonging to an Aggregate

For collections of dependent members, Spring Data Relational provides `@MappedCollection` to declare the link column and, if needed, the key column of elements in the collection. Illustrative example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrderEntity {

    @Id
    private Long id;

    private Long customerId;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLineEntity> lines;

    // Constructors and accessors following project conventions.
}
```

```java
public record OrderLineEntity(
        String productCode,
        Integer quantity,
        BigDecimal unitPrice
) {
}
```

`idColumn` specifies the column in the element table used to link back to the aggregate root; `keyColumn` can be used to store the position or key of the collection element. The table name and remaining columns must match the schema and active naming strategy. Verify the mapping with integration tests against a real database.

Only use collection mapping when the elements truly belong to the aggregate's lifecycle. If `OrderLine` needs to be managed independently, has its own API, or is referenced by multiple aggregates, consider modeling it as a separate entity/aggregate and storing explicit reference keys.

### 3.3. Do Not Replicate Full Object-Relational ORM Behavior

Spring Data R2DBC does not provide a persistence context, dirty checking, lazy loading, or a JPA/Hibernate-style relationship annotation system. Therefore:

- Do not design entities assuming that accessing `order.getCustomer()` will automatically trigger a query.
- Do not build large object graphs with many bidirectional reference cycles.
- Deliberately decide when to query one table, multiple tables, or a projection.
- Use transactions when multiple write operations require atomicity.
- Keep aggregates small enough to persist and control performance predictably.

If a screen needs to display orders along with customer names and line counts, you can write a join query returning a projection. It is not necessary to load the entire customer entity and the entire aggregate just to build a response.

## 4. Designing Independent API Requests and Responses

### 4.1. Request DTOs Contain Only Client-Allowed Data

A request DTO describes the input contract of an operation. Example for creating a customer:

```java
package com.example.store.customer.api;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateCustomerRequest(
        @NotBlank @Email @Size(max = 254) String email,
        @NotBlank @Size(max = 120) String displayName
) {
}
```

The request must not accept a database-generated `id`, internal `version`, or `isAdmin`/`role` fields that the client has no authority to decide. These values must be determined by the system based on authenticated identity and business rules.

DTO validation checks input shape such as blank strings, malformed emails, or exceeded lengths. The Service still needs to verify business rules such as whether the email is already in use or whether the current user has permission to perform the operation. The database needs unique constraints to protect uniqueness even under concurrent requests.

### 4.2. Response DTOs Expose Only Necessary Data

```java
package com.example.store.customer.api;

public record CustomerResponse(
        Long id,
        String email,
        String displayName
) {
}
```

The response does not need to include every column of the table. Fields such as `passwordHash`, tokens, internal notes, audit details, or version may be kept private. If an API needs to return additional fields, add them to the response model according to contract needs and consider client compatibility impacts.

### 4.3. Use Separate DTOs per Operation When Semantics Differ

Not every operation should share a single `CustomerDto` with all nullable fields. For example:

- `CreateCustomerRequest` contains fields needed for creation.
- `UpdateCustomerRequest` contains the set of fields allowed to change when replacing the whole resource.
- `ChangeCustomerNameRequest` contains only the new name for a specific business command.
- `CustomerResponse` contains the data exposed after the operation.

For `PUT` and `PATCH`, semantics must be clearly defined. `PUT` typically replaces the resource representation according to the contract; `PATCH` performs a partial update. If `null` is used to represent both "field omitted" and "clear current value," the application cannot distinguish the two meanings without an additional data type or convention. Design partial-update requests explicitly.

## 5. Converting Between API Models and Persistence Entities

Mapping is the data-transfer boundary between the two models. For small projects, manual mappers can be written; for projects with many entities and DTOs, MapStruct or another mapping tool can be used. Whichever approach is chosen, mapping must make explicit which fields are permitted to cross the boundary.

### 5.1. Manual Mapper

```java
package com.example.store.customer.api;

import com.example.store.customer.persistence.CustomerEntity;
import org.springframework.stereotype.Component;

@Component
public class CustomerMapper {

    public CustomerEntity toNewEntity(CreateCustomerRequest request) {
        return new CustomerEntity(
                null,
                request.email().trim(),
                request.displayName().trim(),
                null
        );
    }

    public CustomerResponse toResponse(CustomerEntity entity) {
        return new CustomerResponse(
                entity.id(),
                entity.email(),
                entity.displayName()
        );
    }
}
```

The mapper creates a new entity with an unassigned ID and version. System-governed values are not arbitrarily copied from the request. When mapping the response, only select fields intended for exposure.

### 5.2. Integrating the Mapper in a Service

```java
package com.example.store.customer.application;

import com.example.store.customer.api.CreateCustomerRequest;
import com.example.store.customer.api.CustomerMapper;
import com.example.store.customer.api.CustomerResponse;
import com.example.store.customer.persistence.CustomerRepository;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class CustomerService {

    private final CustomerRepository repository;
    private final CustomerMapper mapper;

    public CustomerService(CustomerRepository repository, CustomerMapper mapper) {
        this.repository = repository;
        this.mapper = mapper;
    }

    public Mono<CustomerResponse> create(CreateCustomerRequest request) {
        var entity = mapper.toNewEntity(request);
        return repository.save(entity).map(mapper::toResponse);
    }
}
```

The Service receives the request model, applies business rules, converts it into an entity, saves it via the Repository, and transforms the result into a response. `save` returns a publisher; `map` transforms the saved entity into a response once available. There is no need to call `.block()` to obtain the entity before mapping.

In a real application, checking for duplicate emails can be done via the repository before saving to produce a user-friendly message. However, a database unique constraint remains the final safeguard because two requests can pass the check concurrently before either writes. Constraint violations must be translated into appropriate business/API errors.

### 5.3. Do Not Blindly Copy All Properties

Functions like `BeanUtils.copyProperties(request, entity)` or automatic mappers that copy every matching field name can inadvertently allow clients to modify internal properties. If using MapStruct, declare mappings explicitly and ignore fields such as ID, version, system-managed state, or relationships not permitted to be updated from the request.

Explicit mapping requires more code, but helps reviewers clearly see data boundaries. For sensitive fields or authorization rules, this approach is especially important to prevent mass assignment vulnerabilities.

## 6. When Should Projections Be Used Instead of Full Entities?

A query serving a list or report may only need a few fields. Loading the full entity and then converting it to a DTO can cause unnecessary data reads, especially for tables with many columns or complex aggregates.

For example, a customer list screen only needs the ID, display name, and order count. A dedicated projection can be created:

```java
public record CustomerSummary(
        Long id,
        String displayName,
        Long orderCount
) {
}
```

Custom queries can return projections if the mapping approach and driver support the chosen result type. With Spring Data R2DBC, SQL and mappings must be declared appropriately for the projection; run integration tests to confirm column names, aliases, and data types. Do not assume all JPA projections or query expressions behave identically.

Distinguish three cases:

- **Entity:** used when reading/writing an entity according to persistence mapping.
- **Response DTO:** used when defining the contract for returning data to clients; can be constructed from an entity or projection.
- **Query projection:** used to fetch the exact dataset needed for a query, such as a report or summary screen.

A response DTO can be built from a query projection without constructing a full entity. This is useful for read-only queries and aggregated data.

## 7. Key Design Decisions

### 7.1. Property Names and Column Names

Java names should be readable following camelCase conventions; column names should stay consistent with the project's schema conventions. Use `@Column` when explicit mapping is needed, such as `createdAt` to `created_at`. Avoid renaming database columns just because you want different JSON response field names; the API can use `@JsonProperty` or a mapper without altering the schema.

### 7.2. Default Values and States

Business states such as `PENDING`, `APPROVED`, `CANCELLED` should be changed through controlled business behavior. Do not allow a request to accept a full entity and arbitrarily overwrite `status`. You can use a dedicated command such as `ApproveOrderRequest` or a Service method `approveOrder(...)` to verify permissions and perform valid state transitions.

If storing enums, agree on the database representation and compatibility when adding new values. Storing enum names as strings is usually more readable than ordinals, because enum order in code can change. Even so, a deployment process is still required when adding states so all running application versions understand the data.

### 7.3. Sensitive Data and Access Permissions

Entities may contain data that the API is not allowed to return. Do not serialize entities directly to JSON purely for convenience. Separating a response DTO controls exposed fields and reduces the risk of leaking internal information when the entity expands later.

Similarly, requests must not be allowed to update all entity properties. Ownership, roles, moderation status, confirmed prices, and audit fields must be set from the authenticated context or business rules. Do not trust client-supplied values just because their data type is valid.

### 7.4. Audit Fields and Computed Data

Fields like `createdAt`, `updatedAt`, and `createdBy` can belong to the persistence model if the database needs to store and query them. Clearly decide which component assigns their values: application code, Spring Data auditing callbacks, or database defaults. Do not let multiple layers independently write conflicting values.

Computed values used purely for display can live in a response DTO or projection instead of stored columns. Conversely, if a value is business data needed for traceability or querying, consider persisting it and defining how it is updated consistently.

### 7.5. Schema Evolution and API Compatibility

Database schemas and APIs have different change lifecycles. Adding a storage column does not mean a field must be added to the response. Renaming a JSON field does not require renaming a column. A new API version can present data differently while the persistence entity stays unchanged.

When evolving the schema, use versioned migrations and deploy in an order compatible with running applications. When changing the API, consider older clients, required fields, deprecated fields, and conversion rules. Do not let a database change accidentally break the JSON contract.

## 8. Common Mistakes When Designing Entities and API Models

### Using the Entity as Request and Response for Every Endpoint

This allows clients to send internal fields and causes the API to accidentally expose newly added entity fields. Use request/response DTOs to clearly define input and output data.

### Using a Single DTO for Create, Update, and Read

Operations have different permissions and data requirements. Separating DTOs by use case makes validation and mapping easier to understand while preventing response-only fields from being sent back in requests.

### Embedding Full JPA Relationships into R2DBC Entities

R2DBC does not automatically load relationships via lazy loading. Model aggregates and reference them by ID; write separate queries or projections when combined data is needed.

### Letting the API Decide Primary Keys or Internal State

Do not copy ID, role, ownerId, version, or protected states from a request if the client is not authorized to set them. Obtain identity from the authenticated context and apply rules in the Service.

### Validating Data Only in Java

DTO validation cannot prevent errors from other write paths or concurrent race conditions. Use database constraints for uniqueness, foreign keys, `NOT NULL`, and conditions expressible in the schema.

### Returning Entities Directly Because Mapping Seems Redundant

Mapping is where the data contract is defined. A simple mapper or projection can be used; do not remove the API boundary just to save a few lines of code.

## 9. Testing Mappings and Data Contracts

Components that can change independently should be tested separately:

| Part to Test | Scope |
|---|---|
| Persistence mapping | Entity maps accurately to table, columns, data types, ID, and version |
| Repository | Read/write commands, derived queries, custom SQL, and collection mappings work on the target database |
| Mapper | Only permitted fields are transferred from request to entity and entity to response |
| Validation | Requests with missing fields, invalid formats, or out-of-bounds values are rejected |
| Service | Business rules, state-change permissions, and conflict handling are enforced |
| API contract | JSON responses do not leak internal fields and maintain the published structure |

An example mapper unit test can verify that ID and version are not taken from the request:

```java
CreateCustomerRequest request = new CreateCustomerRequest(
        "linh@example.com",
        " Linh Nguyen "
);

CustomerEntity entity = mapper.toNewEntity(request);

assertThat(entity.id()).isNull();
assertThat(entity.version()).isNull();
assertThat(entity.email()).isEqualTo("linh@example.com");
assertThat(entity.displayName()).isEqualTo("Linh Nguyen");
```

Integration tests should run against the same database engine or a configuration compatible with the deployment environment. Differences in data types, generated keys, SQL, and collection mapping may not appear when testing only with mocks.

## 10. Workflow for Designing a New Feature

When adding a data-persistence feature, you can follow this sequence:

1. Identify the use case and business rules: what action the user wants to perform, who has permission, and which conditions must hold.
2. Design the required tables, keys, constraints, and transactions.
3. Identify the aggregate root, dependent members, and references to other aggregates.
4. Create the persistence entity with appropriate mapping annotations.
5. Create the Repository with derived queries or custom SQL.
6. Design the request DTO/command containing only allowed input data.
7. Design the response DTO or query projection for the data to be exposed.
8. Write an explicit mapper between the API model and the persistence model.
9. Place business rules and publisher coordination in the Service; use transactions when needed.
10. Test mappings, queries, validation, access permissions, and the API contract.

## 11. Design Checklist

- [ ] Entity reflects the table and schema, with `@Table`, `@Id`, and necessary column mappings.
- [ ] Java types are compatible with column types and the R2DBC driver.
- [ ] Primary keys, constraints, indexes, and relationships are defined in the schema.
- [ ] Aggregate root and collection lifecycles are clearly defined.
- [ ] References to independent aggregates are expressed with appropriate keys; no assumption of JPA-style lazy loading.
- [ ] Request DTOs contain only fields the client is permitted to send.
- [ ] Response DTOs expose only necessary fields.
- [ ] Create, update, command, and response models are separated when semantics differ.
- [ ] Mappers do not blindly copy ID, version, role, or internal state from requests.
- [ ] Business rules are enforced in the Service; critical constraints are protected in the database.
- [ ] Projections are considered for read-only queries or summary screens.
- [ ] Unit tests exist for mappers, and integration tests exist for mappings/repositories on an appropriate database.

Designing persistence entities and API models as two models with clear boundaries lets the schema focus on data integrity while the API focuses on client experience and contracts. Spring Data R2DBC handles reactive mapping and data access; Services and mappers take responsibility for orchestrating business logic and transforming data across application boundaries.
