# Unique Constraints as a Safeguard Under Concurrent Writes

In Spring Data Relational R2DBC, multiple requests can check the same value and simultaneously attempt to write data to the database. For example, two users might register the same email concurrently, two workers might process the same transaction code, or two retry requests might create the same record. If the application only checks "this value does not exist yet" before running an INSERT, both requests can still pass the check and both write the data.

A database unique constraint (`UNIQUE` constraint or unique index) is the final safeguard for uniqueness invariants. The database enforces uniqueness during write execution and coordinates competing transactions. One operation can succeed; the other must receive a conflict if it produces a violating value. The application needs to translate that conflict into an appropriate business outcome while designing idempotency, transactions, and retries so they do not produce duplicate side effects.

## 1. Why Is Application-Level Checking Insufficient?

A common implementation reads first and writes afterward:

```java
public Mono<User> register(String email, String name) {
    return userRepository.existsByEmail(email)
        .flatMap(exists -> {
            if (exists) {
                return Mono.error(new EmailAlreadyRegisteredException(email));
            }

            return userRepository.save(new User(email, name));
        });
}
```

With a single request, this approach appears correct. However, when two requests run concurrently, the following sequence can occur:

```text
Request A                         Request B
---------                         ---------
SELECT email -> not found
                                  SELECT email -> not found
INSERT email
                                  INSERT email
COMMIT
                                  COMMIT
```

Without a unique constraint in the database, both INSERTs can succeed and create two users with the same email. `existsByEmail` does not lock the value in a way that prevents another request from writing concurrently.

This is a *check-then-act* race condition: the check result can become stale before the write executes. Regardless of using `Mono`, `Flux`, `flatMap`, or `@Transactional`, pre-checking does not automatically guarantee uniqueness when multiple transactions contend.

## 2. Placing the Uniqueness Invariant in the Database

If an email must be unique, express that rule in the schema:

```sql
CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    display_name VARCHAR(200) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_app_user_email UNIQUE (email)
);
```

The `uk_app_user_email` constraint requires that no two rows share the same `email` value. `NOT NULL` makes it explicit that email cannot be left empty with SQL NULL. If a second request attempts to write an existing email, the database rejects the violating operation.

Unique constraints are typically enforced by the database via a unique index or equivalent index structure. Name constraints explicitly to make error identification, schema tracking, and migrations easier. The constraint name may appear in error metadata from the database/driver, though you should not rely solely on error message text for classification.

### 2.1. Constraints vs. Unique Indexes

Two common approaches:

```sql
-- Unique constraint declared on the table.
ALTER TABLE app_user
ADD CONSTRAINT uk_app_user_email UNIQUE (email);
```

Or:

```sql
-- Direct unique index.
CREATE UNIQUE INDEX ux_app_user_email
ON app_user(email);
```

Both can prevent duplicate values at the database level. A unique constraint clearly states the schema integrity rule; a unique index can be useful when database-specific features such as partial unique indexes are needed. Exact syntax and capabilities depend on the database system.

Do not create both a constraint and a redundant unique index on the same column if the database already creates an index to enforce the constraint. Redundant indexes add write overhead and storage cost.

## 3. Composite Multi-Column Unique Constraints

Many uniqueness rules apply only within a scope. For example, a single tenant cannot have two users with the same email, whereas two different tenants may use the same email.

```sql
CREATE TABLE tenant_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    email VARCHAR(320) NOT NULL,
    display_name VARCHAR(200) NOT NULL,
    CONSTRAINT uk_tenant_user_email UNIQUE (tenant_id, email)
);
```

This constraint ensures the `(tenant_id, email)` pair is unique. It allows:

| tenant_id | email | Outcome |
|---:|---|---|
| 10 | `a@example.com` | Allowed |
| 10 | `b@example.com` | Allowed |
| 20 | `a@example.com` | Allowed |
| 10 | `a@example.com` again | Rejected |

Column order in a unique index also affects how the database can use the index for queries. Choose the order based on workload and execution plans, while the uniqueness rule still applies to the full column combination.

Other examples:

- `(tenant_id, external_reference)`: unique external reference per tenant.
- `(warehouse_id, product_id)`: each product has only one inventory row per warehouse.
- `(account_id, idempotency_key)`: unique idempotency key scoped to an account.
- `(country_code, phone_number)`: unique phone number per country, if required by business rules.

If the invariant is tenant-scoped, do not create a global unique constraint on email or code when that violates business requirements.

## 4. Data Types, NULL, and Defining Duplicate Values

A unique constraint alone does not fully define data normalization rules. The application must determine which values are considered equal.

### 4.1. NULL in Unique Constraints

Unique constraint behavior with multiple NULL values varies across database systems and may offer configuration options. For example, many databases allow multiple rows containing NULL in a unique column because NULL is not treated as equal under standard comparison; some systems support syntax or options to treat NULLs as non-distinct.

If a field is required and must be unique, combine `NOT NULL` with `UNIQUE`:

```sql
email VARCHAR(320) NOT NULL,
CONSTRAINT uk_app_user_email UNIQUE (email)
```

Do not rely on a unique constraint alone to prevent multiple rows missing an email. Verify the semantics of the target database.

### 4.2. Case Sensitivity and Collation

Emails, usernames, or business codes may require case-insensitive uniqueness. If a database compares strings case-sensitively, `An@example.com` and `an@example.com` may be treated as two distinct values.

One approach is storing a normalized value alongside it:

```sql
CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    normalized_email VARCHAR(320) NOT NULL,
    CONSTRAINT uk_app_user_normalized_email UNIQUE (normalized_email)
);
```

The application normalizes according to business rules before writing. You can also use a generated column or functional index if supported by the database, though syntax is dialect-dependent.

For example, PostgreSQL can use a unique index on `lower(email)`:

```sql
CREATE UNIQUE INDEX ux_app_user_email_lower
ON app_user (lower(email));
```

This is PostgreSQL syntax. Consider Unicode, locale, and real email normalization policies; Java's default `toLowerCase()` is not necessarily equivalent to every collation or database. Define a single normalization rule and apply it consistently for both queries and writes.

### 4.3. Whitespace and Character Equivalence

Values with leading/trailing whitespace or different Unicode normalization forms may be treated as distinct depending on the database and collation. If business logic treats them as the same value, normalize prior to saving, such as trimming whitespace or applying a chosen Unicode normalization form.

Do not blindly normalize every field. Some data carries meaning in whitespace or letter casing. Rules must be defined per identifier type.

## 5. Unique Constraints Arbitrate Concurrent Writes

With a unique constraint, contention unfolds as follows:

```text
Request A                         Request B
---------                         ---------
INSERT email
Database checks unique key
                                  INSERT same email
                                  Database waits/checks transaction A
COMMIT
                                  Unique conflict
                                  Statement rejected
```

The database coordinates competing operations on the unique key. One transaction wins; the other receives a unique violation error once the database determines the value has been committed or cannot coexist per engine semantics.

When the error surfaces depends on the database and constraint type. Standard unique constraints are checked immediately at the statement, whereas some databases support deferring constraints until transaction commit. In PostgreSQL, constraints can be declared `DEFERRABLE` and checked at commit when configured. Therefore, an application should not assume every unique error always occurs at the INSERT call itself; it may be detected at commit time.

The database constraint remains the final safeguard even if the application pre-checks, uses transactions, or runs across multiple instances. It does not depend on requests arriving at the same JVM or node.

## 6. Writing with Spring Data R2DBC and Handling Conflicts

Entities and repositories can be declared normally:

```java
@Table("app_user")
public class AppUser {

    @Id
    private Long id;

    private String email;

    private String displayName;

    // Constructors, getters, and setters.
}
```

```java
public interface AppUserRepository
        extends ReactiveCrudRepository<AppUser, Long> {

    Mono<AppUser> findByEmail(String email);
}
```

The save operation is reactive:

```java
Mono<AppUser> createUser(String email, String displayName) {
    AppUser user = new AppUser(null, email, displayName);
    return appUserRepository.save(user);
}
```

When two requests save the same email concurrently, one publisher can complete successfully while the other emits an error due to the unique constraint. `save()` does not automatically turn that error into an "already exists" business result. The service must map the error intentionally.

### 6.1. Do Not Rely Only on existsBy Before INSERT

You may keep a pre-check to return early in non-contended cases:

```java
return appUserRepository.existsByEmail(normalizedEmail)
    .flatMap(exists -> exists
        ? Mono.error(new EmailAlreadyRegisteredException(normalizedEmail))
        : appUserRepository.save(new AppUser(null, normalizedEmail, name)));
```

However, the unique constraint remains mandatory. Two requests can both receive `false` from `existsByEmail` before either executes INSERT. Pre-checking only improves user experience or avoids unnecessary writes; it does not replace the constraint.

If early notification is unnecessary, you can omit the exists query and execute INSERT directly, handling any conflict afterward. This avoids an extra round trip in the success case.

## 7. Identifying Unique Violation Errors

Spring R2DBC translates driver errors into Spring exceptions across many data access paths. Constraint errors may appear as `DataIntegrityViolationException` or an R2DBC exception whose root cause is `R2dbcException`, depending on the API and version.

Do not treat every `DataIntegrityViolationException` as a duplicate. This exception family can also include:

- Foreign key violations.
- `NOT NULL` violations.
- `CHECK` constraint violations.
- Unique constraint violations.
- Other data integrity errors.

If you need to map duplicates specifically, inspect the error code / SQLSTATE and constraint name according to the database. For example, PostgreSQL uses SQLSTATE `23505` for unique violations. SQL Server and MySQL have their own error codes; do not use PostgreSQL codes for every driver.

A simple helper to locate SQL state in the cause chain:

```java
private boolean isPostgresUniqueViolation(Throwable error) {
    Throwable current = error;

    while (current != null) {
        if (current instanceof R2dbcException r2dbcException) {
            return "23505".equals(r2dbcException.getSqlState());
        }
        current = current.getCause();
    }

    return false;
}
```

This helper is for PostgreSQL only. In multi-database applications, isolate classifiers by dialect/driver or rely on Spring's exception translation when it provides sufficient detail. Avoid parsing error message text because messages can change across languages, versions, or drivers.

### 7.1. Mapping to a Business Error

You can keep the signal as an error and map it to a business exception:

```java
Mono<AppUser> createUser(String email, String name) {
    Mono<AppUser> insert = appUserRepository.save(
        new AppUser(null, email, name)
    );

    return transactionalOperator.transactional(insert)
        .onErrorMap(this::isPostgresUniqueViolation,
            error -> new EmailAlreadyRegisteredException(email));
}
```

Here `onErrorMap` sits outside the transactional publisher. The transaction manager receives the database error and handles rollback first; the service then maps the error to a business exception so the controller can return HTTP 409 Conflict.

If using `@Transactional`, let the duplicate error propagate out of the method and map it at a caller layer outside the transaction boundary. Ensure the mapped exception preserves the original cause if logs or diagnostics need it.

### 7.2. Do Not Arbitrarily Swallow Conflicts Inside a Transaction

Do not write:

```java
@Transactional
public Mono<AppUser> createUser(String email, String name) {
    return appUserRepository.save(new AppUser(null, email, name))
        .onErrorResume(DataIntegrityViolationException.class,
            error -> Mono.empty());
}
```

This snippet converts an error into normal completion. The transaction boundary may see completion instead of an error and try to commit. Furthermore, on some databases such as PostgreSQL, once a statement errors inside a transaction, the transaction enters an aborted/failed state and cannot continue normal queries until rolled back. Catching the error and running another query inside the same transaction is not a safe recovery path.

Let the transaction roll back, then handle the conflict outside the boundary or use an atomic `ON CONFLICT`/upsert statement suited to the database.

## 8. Returning HTTP 409 or an Appropriate Business Result

If an email is already in use, an API can commonly return `409 Conflict`:

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(EmailAlreadyRegisteredException.class)
    ResponseEntity<ProblemDetail> handleDuplicateEmail(
            EmailAlreadyRegisteredException error) {

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.CONFLICT,
            "Email is already registered"
        );

        return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
    }
}
```

This is an HTTP-layer example; actual responses must follow your API contract. You do not necessarily need to echo back the email or sensitive data in the error message. For non-public endpoints, detailed information can be returned according to security policy.

Not every duplicate is an error to the caller. For an idempotent operation, resubmitting the same request may need to return the previously created result. In that case, conflict handling must look up by idempotency key and confirm the new request actually matches the original request.

## 9. Idempotency Keys and Preventing Duplicate Processing

Unique constraints are ideal for protecting idempotency keys. For instance, a client sends a payment creation request with an `Idempotency-Key`; if the client times out and retries, the server must not create two payments.

Illustrative schema:

```sql
CREATE TABLE payment_request (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    idempotency_key VARCHAR(100) NOT NULL,
    request_hash VARCHAR(128) NOT NULL,
    status VARCHAR(30) NOT NULL,
    result_reference VARCHAR(100),
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_payment_request_key
        UNIQUE (account_id, idempotency_key)
);
```

This constraint guarantees an account cannot create two requests with the same idempotency key. `request_hash` helps verify that the client did not reuse the same key for a different business payload.

Typical flow:

1. Receive `account_id`, idempotency key, and payload.
2. Canonicalize the payload and compute a hash using a deterministic rule.
3. Attempt to INSERT a request record with an initial status.
4. If INSERT succeeds, proceed with business processing per design.
5. On unique conflict, read the existing record after the failed transaction has ended.
6. Compare `request_hash`; if different, return an error for reusing a key with a different payload.
7. If identical, return the stored status/result or indicate the request is still in progress.

Re-reading after conflict should occur outside the failed transaction. With some databases, you can use an atomic upsert or `INSERT ... ON CONFLICT` to do this in one statement, though states and update conditions must be designed carefully.

## 10. Upsert and INSERT ... ON CONFLICT

Some databases support insert-or-update or insert-do-nothing syntax. This is an option when business logic wants to handle conflicts via an atomic rule rather than catching exceptions.

PostgreSQL example:

```sql
INSERT INTO app_user(email, display_name, created_at)
VALUES (:email, :displayName, :createdAt)
ON CONFLICT (email) DO NOTHING
RETURNING id, email, display_name;
```

If the email does not exist yet, the database inserts the row and returns the requested columns. If it already exists, `DO NOTHING` inserts nothing and returns no row for that operation.

The application can inspect the result:

```java
Mono<AppUser> inserted = databaseClient.sql("""
        INSERT INTO app_user(email, display_name, created_at)
        VALUES (:email, :displayName, :createdAt)
        ON CONFLICT (email) DO NOTHING
        RETURNING id, email, display_name
        """)
    .bind("email", email)
    .bind("displayName", name)
    .bind("createdAt", Instant.now())
    .map((row, metadata) -> new AppUser(
        row.get("id", Long.class),
        row.get("email", String.class),
        row.get("display_name", String.class)
    ))
    .one();
```

`Mono.empty()` can represent that no row was inserted due to conflict. The service can look up the existing row if business logic requires it. This example uses `RETURNING` and `ON CONFLICT` syntax specific to PostgreSQL; other databases may use `MERGE`, `ON DUPLICATE KEY UPDATE`, or their own syntax.

### 10.1. DO NOTHING vs. DO UPDATE

- `DO NOTHING`: leaves the existing row untouched and performs no update.
- `DO UPDATE`: updates the conflicting row according to specified assignments.

Upsert does not mean "on duplicate, overwrite all fields." Update only fields whose semantics are appropriate. If a retry carries a different payload, blind `DO UPDATE` can overwrite valid data.

### 10.2. Upsert Can Hide Business Conflicts

If an email already exists, updating the display name may not be the intended behavior for a registration API. For flows that must report "email already in use," `DO NOTHING` or a plain INSERT with unique-violation handling is usually more accurate than `DO UPDATE`.

Choose upsert based on business semantics, not merely to avoid exceptions.

## 11. Updates Can Also Violate Unique Constraints

Unique constraints do not apply solely to INSERTs. Two requests may simultaneously change the username/email of two different records to the same target value:

```sql
UPDATE app_user
SET email = 'new@example.com'
WHERE id = 10;
```

If another row already holds that email, the database rejects the UPDATE. With R2DBC, the error is emitted via the update publisher and must be handled as a business conflict.

If the application checks `existsByEmail` before UPDATE, the race condition still exists. Let the unique constraint protect it and translate the error to `EmailAlreadyRegisteredException` or the corresponding domain error.

With multi-column unique constraints, updating one key component can conflict with another row in the same scope. Tests must cover both INSERT and UPDATE.

## 12. Combining Unique Constraints with Optimistic Locking

Unique constraints and optimistic locking protect two distinct invariants:

- A unique constraint prevents two rows from sharing the same specified value or combination of values.
- Optimistic locking with `@Version` detects two transactions updating the same version of a single row.

Entity example:

```java
@Table("app_user")
public class AppUser {

    @Id
    private Long id;

    @Version
    private Long version;

    private String email;
}
```

`@Version` detects concurrent updates on the same entity when using Spring Data's optimistic locking mechanism. However, versioning does not replace a unique constraint: two rows with different IDs could still write the same email without a unique constraint.

A system frequently needs both: a unique constraint to guard table-wide or scoped business keys, and versioning to prevent lost updates on the same record.

## 13. Transaction Boundaries and Duplicate Errors

When an INSERT violates a unique constraint, the statement emits an error. If the operation runs inside a reactive transaction, an error crossing the transaction boundary typically triggers a rollback.

Example with `TransactionalOperator`:

```java
Mono<AppUser> createUser(AppUser user) {
    Mono<AppUser> insert = appUserRepository.save(user);

    return transactionalOperator.transactional(insert)
        .onErrorMap(this::isUniqueViolation,
            error -> new EmailAlreadyRegisteredException(user.getEmail()));
}
```

Putting `onErrorMap` outside the transaction boundary lets the transaction manager observe the database error first before the service translates it into a domain exception. The domain exception remains an error signal so callers can handle it and map to HTTP responses.

If using `@Transactional`, let the exception exit the method and translate it in controller advice or a service facade outside the same transaction. Avoid catching a duplicate and continuing to run queries on a transaction already marked failed by the database.

### 13.1. Constraints Deferred to Commit

Some databases support deferred constraints. In that mode, INSERT/UPDATE may not raise an error immediately; the transaction fails only at commit time. Therefore:

- Do not assume every duplicate is detected right at `save()`.
- Error handlers must wrap the entire transactional publisher, including the commit phase.
- Integration tests must verify errors occurring at transaction completion.

In PostgreSQL, certain constraints can be declared `DEFERRABLE INITIALLY DEFERRED`. This is a database-specific feature, not a portable default across all R2DBC drivers.

## 14. Why Shouldn't Distributed Locks Replace Unique Constraints?

Distributed locks can be useful to reduce contention or coordinate a workflow, but should not be the sole layer enforcing data uniqueness.

Locks can expire, drop connections, be released early, or leave two clients both thinking they own the lock due to network partitions and lease timeouts. A node can write data after its lock expired. The database constraint still enforces the invariant at write time.

You can combine locks with unique constraints when needed to shed load or avoid expensive duplicate work, while keeping the constraint as the final safeguard. If locks use leases, consider fencing tokens or another mechanism to stop stale owners from writing after losing ownership.

## 15. Migrations When Adding a Unique Constraint to Existing Data

Adding a unique constraint to a table that already contains data will fail if duplicate values exist. Before migrating, locate duplicates:

```sql
SELECT email, COUNT(*) AS duplicate_count
FROM app_user
GROUP BY email
HAVING COUNT(*) > 1;
```

For multi-column unique keys:

```sql
SELECT tenant_id, email, COUNT(*) AS duplicate_count
FROM tenant_user
GROUP BY tenant_id, email
HAVING COUNT(*) > 1;
```

A typical migration workflow includes:

1. Define the exact invariant and value normalization rules.
2. Find duplicate groups under the new rules.
3. Decide how to merge, rename, or remove duplicate records per business policy.
4. Deploy application code that normalizes new values consistently.
5. Add the constraint/index via a controlled migration.
6. Monitor write errors and migration duration.

For large tables, creating a unique index may lock or impact writes depending on the database. Some systems offer online/concurrent index creation options. Choose a rollout approach based on database documentation and operational plans; never run ad-hoc DDL in production.

## 16. Testing Contention with Multiple Subscriptions

Testing duplicate requests sequentially only verifies that the constraint works in simple cases. Concurrency tests are needed to prove two simultaneous operations do not create two rows.

Integration test idea:

```java
Mono<AppUser> first = userService.createUser(
    "same@example.com", "First"
);

Mono<AppUser> second = userService.createUser(
    "same@example.com", "Second"
);

Mono<List<Signal<AppUser>>> outcomes = Flux.merge(
        first.materialize(),
        second.materialize()
    )
    .collectList();
```

`materialize()` turns signals into values so the test can observe both completion and error without one error cancelling the entire `merge`. Subscribe two independent publishers so they run concurrently. Real tests must ensure each operation uses its own transaction when simulating two independent requests.

After both operations complete, verify:

- Only one row exists with that email.
- One operation succeeded.
- The other operation was handled as a unique conflict or idempotent result per design.
- No auxiliary records or side effects were duplicated.
- Connections are returned to the pool after both success and error.

Do not run two competing operations inside a single transaction-bound connection and conclude you simulated two independent requests. Use two separate subscriptions/transactions and a compatible real database.

### 16.1. Checking the Final Row Count

```java
StepVerifier.create(userRepository.countByEmail("same@example.com"))
    .expectNext(1L)
    .verifyComplete();
```

`countByEmail` is an illustrative derived query. Tests must prepare isolated data per run and clean up afterward to avoid cross-test interference.

### 16.2. Testing Retry After Timeout

An even more important scenario is when the server committed but the client never received the response. The client resends the same idempotency key. Tests must verify that the retry creates no extra records or side effects and returns the previous request's result if that is the API contract.

## 17. Observing and Operating Unique Errors

A unique violation can be a normal business conflict, though a sudden spike may indicate misbehaving client retries, race conditions, or data-generation bugs.

Track:

- Count of unique violations per constraint.
- Duplicate request rate by endpoint/tenant.
- Retry counts and idempotency key reuse counts.
- Rate of conflicts mapped to HTTP 409.
- INSERT/UPDATE latency and lock waits involving unique indexes.
- Count of upserts returning no rows or updating existing rows.

Logs should include correlation ID, normalized constraint name, operation type, and non-sensitive business context. Avoid logging full payloads or sensitive emails/identifiers unnecessarily.

Do not alert on every single duplicate if duplicates are expected API behavior. Alert on rates, trends, or abnormal spikes.

## 18. Common Pitfalls

| Pitfall | Consequence | Resolution |
|---|---|---|
| Using only `existsBy...` before INSERT | Two requests both see absent and both write | Enforce a unique constraint in the database |
| Using `@Transactional` without a unique constraint | Separate transactions can still contend and create duplicates | Guard invariant with a constraint/index |
| Not normalizing email/username | Values differing in case or whitespace slip through | Define normalized keys and enforce uniqueness on normalized values |
| Using UNIQUE while forgetting `NOT NULL` | Multiple NULLs may be allowed depending on database | Combine with `NOT NULL` if the field is required |
| Treating every `DataIntegrityViolationException` as a duplicate | Masks FK, CHECK, or NOT NULL errors | Inspect specific SQLSTATE, error code, and constraint |
| Parsing error messages to detect duplicates | Brittle when messages or drivers change | Use structured error codes and constraint metadata |
| Swallowing unique violations inside a transaction | Transaction may complete normally or remain in failed state | Let it roll back and handle outside boundary or use atomic upsert |
| Immediately retrying duplicate errors | Repeats a conflict that cannot self-resolve | Return conflict or look up idempotency result |
| Using unconditional DO UPDATE | Overwrites valid data on existing records | Explicitly specify updatable fields and upsert conditions |
| Missing idempotency keys on retryable operations | Client retries can duplicate side effects | Create a business-scoped unique key |
| Relying solely on distributed locks | Lock expiration or network glitches open race windows | Keep unique constraints as the final safeguard |
| Adding constraints when duplicate data exists | Migration fails | Find and clean up duplicates prior to migration |
| Testing sequentially only | Misses race conditions between transactions | Test two independent requests concurrently |
| Assuming errors always occur at INSERT | Deferred constraints can fail at commit | Wrap error handling around the entire transactional publisher |

## 19. Process for Designing Unique Writes

When a business flow requires preventing duplicate data, follow these steps:

1. **Define the invariant:** which field or combination of fields must be unique, globally or scoped per tenant/account.
2. **Define value semantics:** whether NULL is valid, and how case/Unicode/whitespace are normalized.
3. **Design the schema:** declare `UNIQUE` or a unique index and `NOT NULL` where appropriate; name constraints clearly.
4. **Normalize before writing:** apply the exact same rules for INSERT, UPDATE, lookups, and retries.
5. **Write reactively:** use repositories, templates, or `DatabaseClient` as needed.
6. **Let the database arbitrate conflicts:** never treat a pre-check query as a uniqueness guarantee.
7. **Classify errors:** accurately identify unique violations by database/driver, without lumping all integrity errors together.
8. **Handle business outcomes:** return conflict, read idempotent results, or use upsert when appropriate.
9. **Design retries:** retry only transient errors; use idempotency keys for retryable operations.
10. **Test contention:** run multiple independent transactions writing the same key concurrently and verify only one row exists.
11. **Manage migrations:** resolve existing duplicates before adding constraints and monitor conflicts post-deployment.

## 20. Key Principles to Remember

- `existsBy...` before INSERT is only a helper check; it does not prevent race conditions.
- A database unique constraint or unique index is the final safeguard for uniqueness invariants.
- Use single or composite unique keys matching business scope, such as `(tenant_id, email)`.
- Combine with `NOT NULL` when values are required; check NULL semantics of the target database.
- Normalize case, whitespace, and Unicode consistently prior to writing and querying.
- Constraints are checked at write time or potentially at commit if the database supports deferred constraints.
- Accurately classify unique violations via SQLSTATE/error code/constraint metadata; do not treat every integrity error as a duplicate.
- Let transactions roll back before handling errors outside the boundary; do not arbitrarily swallow constraint errors inside a transaction.
- Use `ON CONFLICT`, upsert, or `DO NOTHING` only when business semantics allow and syntax matches the database.
- Unique constraints protect uniqueness; `@Version` protects concurrent updates on the same entity. The two mechanisms complement each other.
- Use unique-constrained idempotency keys to handle retries and repeated requests safely.
- Distributed locks do not replace database constraints.
- Find and clean up duplicate data before migrations add unique constraints.
- Test multiple independent requests/transactions writing the same value concurrently, including timeout and retry scenarios.

In reactive systems, multiple subscriptions can execute INSERTs or UPDATEs almost simultaneously. Reactor coordinates execution flow, but does not automatically enforce data uniqueness. Database unique constraints protect invariants right at write time; Spring Data R2DBC propagates success or error signals back into the reactive pipeline for the service to handle. By combining properly scoped constraints, data normalization, transaction boundaries, conflict classification, and idempotency, an application keeps data consistent even under concurrent writes.
