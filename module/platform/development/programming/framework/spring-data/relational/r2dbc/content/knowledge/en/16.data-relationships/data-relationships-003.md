# Join Table Modeling for Many-to-Many Relationships

In relational databases, a many-to-many relationship describes a case where a record in the first table can link to multiple records in the second table, and each record in the second table can also link to multiple records in the first table. For example, a student can enroll in many courses and each course can have many students.

This relationship is typically represented by a **join table** (also called an association table or junction table). The join table stores foreign keys to both main tables; each row represents one specific association. In Spring Data R2DBC, it is best to model the join row as a separate entity with explicit identifier properties rather than assuming the framework automatically loads and synchronizes a many-to-many object graph like a traditional ORM.

## 1. Many-to-Many Relationships in the Relational Model

Suppose an education management system has two entities:

- **Student**: student.
- **Course**: course.

A student can enroll in multiple courses. A course can have multiple students. Placing a single course_id column in the student table limits each student to one course. Storing a list of IDs in a single column makes foreign key checks, searching, updating, and indexing difficult.

The standard relational model splits this relationship into three tables:

~~~mermaid
erDiagram
    STUDENT ||--o{ STUDENT_COURSE : registers
    COURSE ||--o{ STUDENT_COURSE : has
    STUDENT {
        bigint id PK
        varchar name
    }
    COURSE {
        bigint id PK
        varchar title
    }
    STUDENT_COURSE {
        bigint id PK
        bigint student_id FK
        bigint course_id FK
        timestamptz enrolled_at
    }
~~~

Each row in STUDENT_COURSE links exactly one student with exactly one course. Multiple rows can share student_id with different course_id values; multiple rows can also share course_id with different student_id values.

In terms of cardinality, two one-to-many relationships combined through the join table form a many-to-many relationship between Student and Course.

## 2. Why Is a Join Table Needed?

A join table solves three main problems:

1. **Representing the relationship:** stores two foreign keys to identify linked record pairs.
2. **Enforcing integrity:** foreign keys prevent creating links to non-existent students or courses.
3. **Preventing duplicate links:** a unique constraint on the foreign key pair ensures a student cannot enroll in the same course multiple times.

The join table can also store attributes of the relationship itself, such as enrollment date, status, grade, role, or creator. When it does, it is not merely a technical bridge table between two tables; it carries business data of its own.

Example: a student-course enrollment relationship can store enrollment date and status:

| student_id | course_id | enrolled_at | status |
| --- | --- | --- | --- |
| 10 | 101 | 2026-09-01 | ACTIVE |
| 10 | 102 | 2026-09-03 | ACTIVE |
| 11 | 101 | 2026-09-04 | WAITLISTED |

Student 10 is enrolled in two courses; course 101 has two students. Each row is an independent enrollment.

## 3. Schema Design for the Join Table

Example DDL for PostgreSQL:

~~~sql
CREATE TABLE student (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE course (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(250) NOT NULL
);

CREATE TABLE student_course (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    enrolled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_student_course_student
        FOREIGN KEY (student_id) REFERENCES student(id),
    CONSTRAINT fk_student_course_course
        FOREIGN KEY (course_id) REFERENCES course(id),
    CONSTRAINT uk_student_course_pair
        UNIQUE (student_id, course_id)
);

CREATE INDEX idx_student_course_course_student
    ON student_course(course_id, student_id);
~~~

In this design:

- The join table ID is an independent primary key.
- student_id and course_id are the two foreign keys.
- A unique constraint on the student_id/course_id pair prevents duplicate recordings of the same pair.
- An index on course_id supports reverse queries from a course to its list of students.

You can use the foreign key pair as the primary key instead of a separate ID:

~~~sql
CREATE TABLE student_course (
    student_id BIGINT NOT NULL REFERENCES student(id),
    course_id BIGINT NOT NULL REFERENCES course(id),
    enrolled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (student_id, course_id)
);
~~~

A composite primary key directly expresses that a student-course pair appears only once. However, when mapping with Spring Data Relational, composite IDs can make repository and mapping usage more complex; specific support should be verified for your Spring Data version. Using a separate surrogate ID combined with a unique constraint on the foreign key pair is often more convenient when modeling the join table as an entity with its own repository.

Do not omit the unique constraint simply because the service checks the ID pair before inserting. Two concurrent requests can both check "does not exist" and then both insert. Database constraints are the final safeguard protecting data.

## 4. Entity Modeling in Spring Data R2DBC

In Spring Data R2DBC, each aggregate root is persisted via a repository or template. References to other aggregates are typically represented by IDs. The framework does not automatically manage an ORM-style many-to-many object graph.

Student entity:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("student")
public record Student(
        @Id Long id,
        String name
) {}
~~~

Course entity:

~~~java
@Table("course")
public record Course(
        @Id Long id,
        String title
) {}
~~~

Entity for the join table:

~~~java
import java.time.Instant;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("student_course")
public record StudentCourse(
        @Id Long id,
        @Column("student_id") Long studentId,
        @Column("course_id") Long courseId,
        @Column("enrolled_at") Instant enrolledAt,
        String status
) {}
~~~

StudentCourse holds two identifiers. It does not need to hold Student and Course objects to represent the relationship. When student names or course titles are needed, the application queries explicitly or uses a SQL JOIN to build a read model.

When the join table carries business fields such as status or enrolledAt, having a dedicated entity is especially useful: each link can be created, updated, searched, and deleted as its own record.

## 5. Repositories for the Main Tables and Join Table

Declaring repositories:

~~~java
public interface StudentRepository
        extends ReactiveCrudRepository<Student, Long> {
}

public interface CourseRepository
        extends ReactiveCrudRepository<Course, Long> {
}

public interface StudentCourseRepository
        extends ReactiveCrudRepository<StudentCourse, Long> {

    Flux<StudentCourse> findByStudentId(Long studentId);

    Flux<StudentCourse> findByCourseId(Long courseId);

    Mono<Long> countByStudentId(Long studentId);
}
~~~

Derived query methods use the Java property names of the StudentCourse entity, such as studentId and courseId. Spring Data translates these properties to the corresponding columns via mapping metadata.

These repositories manage each entity type individually. Calling studentRepository.save(student) does not automatically create StudentCourse rows; calling courseRepository.deleteById(id) does not automatically know to delete or update links unless the database defines corresponding foreign key actions.

## 6. Creating a New Link

Example: enrolling a student in a course. The service can verify both objects exist and then save the association row:

~~~java
import java.time.Instant;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import reactor.core.publisher.Mono;

@Service
public class EnrollmentService {

    private final StudentRepository studentRepository;
    private final CourseRepository courseRepository;
    private final StudentCourseRepository enrollmentRepository;

    public EnrollmentService(
            StudentRepository studentRepository,
            CourseRepository courseRepository,
            StudentCourseRepository enrollmentRepository) {
        this.studentRepository = studentRepository;
        this.courseRepository = courseRepository;
        this.enrollmentRepository = enrollmentRepository;
    }

    @Transactional
    public Mono<StudentCourse> enroll(Long studentId, Long courseId) {
        return studentRepository.findById(studentId)
                .switchIfEmpty(Mono.error(
                        new StudentNotFoundException(studentId)
                ))
                .then(courseRepository.findById(courseId))
                .switchIfEmpty(Mono.error(
                        new CourseNotFoundException(courseId)
                ))
                .then(Mono.defer(() ->
                        enrollmentRepository.save(new StudentCourse(
                                null,
                                studentId,
                                courseId,
                                Instant.now(),
                                "ACTIVE"
                        ))
                ));
    }
}
~~~

Pipeline flow:

1. Find Student by ID; if missing, emit a business error.
2. Find Course by ID; if missing, emit a business error.
3. After both steps complete, create a new StudentCourse.
4. Save the link row and return the saved entity.

Because this is a reactive pipeline, operations are chained via publishers. Do not call block() to retrieve the Student or Course before calling the next repository.

Checking existence before inserting produces clear business error messages, though race conditions can still occur if a record is deleted between the check and the insert. Database foreign keys protect integrity at write time. A reactive transaction coordinates commits/rollbacks within the same database; it does not eliminate all contention with other transactions.

## 7. Preventing Duplicate Enrollments

Suppose two concurrent requests try to enroll student 10 into course 101. Both may run the existence check simultaneously and see no link yet. If checks exist only in Java without a unique constraint, two duplicate rows can be created.

Constraint:

~~~sql
CONSTRAINT uk_student_course_pair
    UNIQUE (student_id, course_id)
~~~

ensures the database accepts at most one row for that pair.

The application can check beforehand to improve error messaging:

~~~java
public Mono<StudentCourse> enroll(Long studentId, Long courseId) {
    return enrollmentRepository
            .findByStudentId(studentId)
            .filter(link -> link.courseId().equals(courseId))
            .next()
            .flatMap(existing -> Mono.<StudentCourse>error(
                    new AlreadyEnrolledException(studentId, courseId)
            ))
            .switchIfEmpty(Mono.defer(() ->
                    enrollmentRepository.save(new StudentCourse(
                            null,
                            studentId,
                            courseId,
                            Instant.now(),
                            "ACTIVE"
                    ))
            ));
}
~~~

This example illustrates the checking logic; if a student's link list is large, querying everything and filtering in Java is inefficient. You should declare an exact query on both properties:

~~~java
public interface StudentCourseRepository
        extends ReactiveCrudRepository<StudentCourse, Long> {

    Mono<StudentCourse> findByStudentIdAndCourseId(
            Long studentId,
            Long courseId
    );
}
~~~

Even when using an exact query, the unique constraint is still necessary to handle concurrency. When an insert violates the unique constraint, the driver/database raises an error; the service layer can translate the duplicate key error into AlreadyEnrolledException according to application policy.

With PostgreSQL, you can design an idempotent operation using INSERT ... ON CONFLICT DO NOTHING. This is database-specific SQL; if used, choose clearly whether to return row count, the existing row, or the enrolled status. Do not assume repository save automatically provides upsert semantics.

## 8. Querying the List of Courses for a Student

When you need the list of courses a student is enrolled in, a SQL JOIN can read the data in a single query:

~~~java
public record CourseSummary(
        Long id,
        String title,
        String enrollmentStatus
) {}

public Flux<CourseSummary> findCoursesForStudent(Long studentId) {
    return databaseClient.sql("""
            SELECT c.id,
                   c.title,
                   sc.status AS enrollment_status
            FROM student_course sc
            JOIN course c ON c.id = sc.course_id
            WHERE sc.student_id = :studentId
            ORDER BY c.title
            """)
            .bind("studentId", studentId)
            .map((row, metadata) -> new CourseSummary(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

The query reads the join table first, joins to course, filters by student_id, and returns the data needed by the screen. There is no need to load each StudentCourse and then call courseRepository.findById() for every row.

If only course IDs are needed, the query can be simpler:

~~~sql
SELECT course_id
FROM student_course
WHERE student_id = :studentId;
~~~

Select only the columns you need. For large lists, Flux lets you consume results item by item; if the UI needs pagination, add a deterministic ORDER BY and limit with LIMIT/OFFSET or use keyset pagination.

## 9. Querying the List of Students for a Course

The reverse direction queries by course_id:

~~~java
public record StudentSummary(
        Long id,
        String name,
        String enrollmentStatus
) {}

public Flux<StudentSummary> findStudentsForCourse(Long courseId) {
    return databaseClient.sql("""
            SELECT s.id,
                   s.name,
                   sc.status AS enrollment_status
            FROM student_course sc
            JOIN student s ON s.id = sc.student_id
            WHERE sc.course_id = :courseId
            ORDER BY s.name
            """)
            .bind("courseId", courseId)
            .map((row, metadata) -> new StudentSummary(
                    row.get("id", Long.class),
                    row.get("name", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

This is why an index on course_id is needed. The unique index on (student_id, course_id) typically supports queries starting with student_id well; queries filtering only by course_id generally require a dedicated index if reverse-direction load is significant.

## 10. When to Use Repositories vs. When to Use JOINs

You can fetch link rows using a derived query:

~~~java
Flux<StudentCourse> links =
        studentCourseRepository.findByStudentId(studentId);
~~~

The application can then load Course information for each link. This makes repository reuse easy, but can cause N+1 queries if each link triggers a separate query.

A JOIN with DatabaseClient is usually better when a screen needs data from multiple tables:

| Approach | Pros | Cons |
| --- | --- | --- |
| Fetch links via repository | Clear entity mapping, reusable | Requires extra queries to fetch both sides' data |
| JOIN via DatabaseClient | A single query can fetch needed fields across tables | Must write SQL and projection mapping |
| Load each object via flatMap | Easy to compose reactive pipeline logically | Risk of N+1 queries and multiple round trips |
| Batch query by IDs | Fewer queries than per-ID lookups | Must manage batch sizes and merge results |

Reactive programming does not eliminate N+1. If there are 200 link rows and each invokes a query to fetch its Course, the application can still issue around 200 extra queries. Use JOINs or batch queries when reading lists.

## 11. Updating Attributes on the Join Table

When the join table holds business data, it can be updated like a regular entity. For example, transitioning an enrollment from WAITLISTED to ACTIVE:

~~~java
public Mono<StudentCourse> activateEnrollment(Long linkId) {
    return enrollmentRepository.findById(linkId)
            .switchIfEmpty(Mono.error(
                    new EnrollmentNotFoundException(linkId)
            ))
            .map(link -> new StudentCourse(
                    link.id(),
                    link.studentId(),
                    link.courseId(),
                    link.enrolledAt(),
                    "ACTIVE"
            ))
            .flatMap(enrollmentRepository::save);
}
~~~

If updating only a single field without needing to load the entity, R2dbcEntityTemplate or DatabaseClient can execute a conditional UPDATE. For status updates, enforce valid state transitions by checking the current condition—for instance, allowing only WAITLISTED to transition to ACTIVE.

If concurrent requests may update the same link, consider adding a version column for optimistic locking or expressing the expected state directly in the WHERE clause:

~~~sql
UPDATE student_course
SET status = 'ACTIVE'
WHERE id = :id
  AND status = 'WAITLISTED';
~~~

An updated row count of 0 means either the condition no longer holds or the row does not exist. Interpret the outcome according to business rules.

## 12. Deleting a Link

Unenrolling a student from a course typically means deleting the row in student_course, not deleting the Student or Course:

~~~java
public Mono<Long> unenroll(Long studentId, Long courseId) {
    return databaseClient.sql("""
            DELETE FROM student_course
            WHERE student_id = :studentId
              AND course_id = :courseId
            """)
            .bind("studentId", studentId)
            .bind("courseId", courseId)
            .fetch()
            .rowsUpdated();
}
~~~

The publisher emits the number of deleted rows. A value of 1 usually means the link was deleted; 0 means that pair did not exist. Do not delete the course row because other students may still be enrolled in that course.

If the association entity has its own ID, you can also delete by the StudentCourse ID via the repository. Deleting by the studentId/courseId pair expresses the business key directly and avoids loading the entity first.

## 13. Deleting One Side and Foreign Key Behavior

When deleting a Student, StudentCourse rows referencing that student must be handled. Two common strategies exist:

1. **RESTRICT/NO ACTION:** the database rejects deleting Student while link rows remain. The service must delete links first or reject the request.
2. **ON DELETE CASCADE on the join table's foreign key:** the database automatically deletes StudentCourse rows when the Student is deleted.

Example:

~~~sql
FOREIGN KEY (student_id)
    REFERENCES student(id)
    ON DELETE CASCADE
~~~

Cascade here deletes only the link rows in student_course. It does not delete Course rows because student_course only holds a foreign key to Course in the opposite direction.

Never configure cascade from the join table to delete records in the opposite main table. Deleting one student must not wipe out a course that other students are still taking.

If not using ON DELETE CASCADE, the service can delete links first and then delete the Student inside the same transaction:

~~~java
@Transactional
public Mono<Void> deleteStudent(Long studentId) {
    return databaseClient.sql("""
            DELETE FROM student_course
            WHERE student_id = :studentId
            """)
            .bind("studentId", studentId)
            .fetch()
            .rowsUpdated()
            .then(studentRepository.deleteById(studentId));
}
~~~

The transaction ensures deleting the links and deleting the student are coordinated in the same commit/rollback unit if both use the same database and reactive transaction manager.

## 14. Join Tables with Their Own Attributes

When the relationship carries its own data, an association entity is the natural model:

- Timestamp when the link was created.
- Link status.
- Role of the entity within a group.
- Order or position.
- User who created the link.
- Audit fields.

Example team membership system:

~~~sql
CREATE TABLE team_member (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    team_id BIGINT NOT NULL REFERENCES team(id),
    user_id BIGINT NOT NULL REFERENCES app_user(id),
    role VARCHAR(30) NOT NULL,
    joined_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_team_member_pair UNIQUE (team_id, user_id)
);
~~~

Entity:

~~~java
@Table("team_member")
public record TeamMember(
        @Id Long id,
        @Column("team_id") Long teamId,
        @Column("user_id") Long userId,
        String role,
        @Column("joined_at") Instant joinedAt
) {}
~~~

Do not treat TeamMember as merely a technical detail if role or joinedAt carries business meaning. It can have its own service and repository, along with rules such as a member having only one active role per team.

## 15. Choosing a Primary Key for the Join Table

Two common designs exist:

### Composite Primary Key

~~~sql
PRIMARY KEY (student_id, course_id)
~~~

Pros:

- Directly models uniqueness of the link pair.
- No extra ID column required.
- The primary key doubles as the constraint preventing duplicate enrollments.

Cons:

- Composite ID mapping and repository usage can be more complex.
- Other tables wanting to reference a specific link must use both columns.
- Some Spring Data abstractions work more smoothly with a single ID.

### Surrogate ID and Unique Constraint

~~~sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
UNIQUE (student_id, course_id)
~~~

Pros:

- Uses repositories with a simple single ID.
- Easy for other tables to reference an association row.
- Easy to evolve the association into an entity with its own lifecycle.

Cons:

- Requires an extra ID column.
- Still requires a unique constraint on the foreign key pair to avoid duplicates.

In many Spring Data R2DBC applications, a separate surrogate ID combined with a unique constraint is easier to map and manage. If the data model is simple and your Spring Data version supports composite IDs as needed, a composite primary key remains a valid choice.

## 16. Indexing the Join Table

Many-to-many queries typically traverse in two directions:

- Finding Courses from a Student.
- Finding Students from a Course.

Therefore, indexes should reflect both directions. With a unique index on (student_id, course_id), the database can generally use that index for predicates starting with student_id. Queries filtering only by course_id typically need a separate index:

~~~sql
CREATE UNIQUE INDEX uk_student_course_pair
    ON student_course(student_id, course_id);

CREATE INDEX idx_student_course_course_student
    ON student_course(course_id, student_id);
~~~

If filtering frequently by status, consider an index tailored to actual queries, such as a composite index (student_id, status, course_id). Do not create indexes arbitrarily, as every index adds insert, update, and delete overhead. Use execution plans and workload metrics to choose.

## 17. Paginating Association Lists

A student might enroll in thousands of courses or a course might have tens of thousands of learners. Never return the entire list in a single request.

Example offset pagination:

~~~java
public Flux<CourseSummary> findCourses(
        Long studentId,
        int limit,
        long offset) {

    return databaseClient.sql("""
            SELECT c.id, c.title, sc.status AS enrollment_status
            FROM student_course sc
            JOIN course c ON c.id = sc.course_id
            WHERE sc.student_id = :studentId
            ORDER BY c.title, c.id
            LIMIT :limit OFFSET :offset
            """)
            .bind("studentId", studentId)
            .bind("limit", limit)
            .bind("offset", offset)
            .map((row, metadata) -> new CourseSummary(
                    row.get("id", Long.class),
                    row.get("title", String.class),
                    row.get("enrollment_status", String.class)
            ))
            .all();
}
~~~

Limit and offset values must be validated in the service/controller: limit needs a maximum bound and offset must be non-negative. ORDER BY should include a unique secondary key so pages do not shift when titles tie.

For large or rapidly changing datasets, keyset pagination is usually more stable than offset. For example, the next page can filter on (title, id) greater than the last pair of the previous page. Build the condition to align with the sort order and index.

## 18. Transactions When Adding or Deleting Multiple Links

An operation may add multiple links at once, such as enrolling a student in a group of courses. If business rules require all-or-nothing execution, use a reactive transaction:

~~~java
@Transactional
public Flux<StudentCourse> enrollInCourses(
        Long studentId,
        List<Long> courseIds) {

    return Flux.fromIterable(courseIds)
            .concatMap(courseId ->
                    enrollmentRepository.save(new StudentCourse(
                            null,
                            studentId,
                            courseId,
                            Instant.now(),
                            "ACTIVE"
                    ))
            );
}
~~~

This example illustrates writing links sequentially within a transaction. If one insert violates a unique constraint or foreign key and the error propagates out, the transaction can roll back the entire batch according to rollback configuration.

For very large lists, a long transaction can hold connections and locks too long. You can split into batches with separate transactions if partial results are acceptable to the business. In that case, you need checkpoints, idempotency, and error-recovery handling.

Do not call subscribe() inside a transactional method. Return the publisher so Spring manages the transaction context and commit/rollback timing.

## 19. Testing Many-to-Many Models

Integration tests should verify both schema constraints and behavior:

1. Create two Students and two Courses.
2. Create multiple StudentCourse rows proving one Student can link to many Courses and one Course can link to many Students.
3. Verify the unique constraint rejects duplicate student_id/course_id pairs.
4. Verify foreign keys reject non-existent Student or Course IDs.
5. Run JOIN queries by studentId and courseId to verify both directions.
6. Delete a link and verify both Student and Course remain.
7. Test behavior when deleting a Student or Course under the chosen foreign key policy.
8. Verify transaction rollback when an insert in a batch fails.

Example reactive test:

~~~java
StepVerifier.create(
        studentCourseRepository.findByStudentId(studentId)
)
        .expectNextCount(2)
        .verifyComplete();

StepVerifier.create(
        enrollmentService.unenroll(studentId, courseId)
)
        .expectNext(1L)
        .verifyComplete();
~~~

Tests should use isolated data and clean up after execution. Run against the same database type as deployment to verify real foreign keys, unique constraints, transactions, and SQL syntax.

## 20. Common Design Mistakes

1. **Storing a list of IDs in a single column.** Difficult to enforce foreign keys, query, and index.
2. **Missing a join table.** Many-to-many is not properly represented in the relational model.
3. **Missing a unique constraint on the foreign key pair.** Concurrent requests can create duplicate links.
4. **Checking existence only in Java.** Pre-insert checks do not replace foreign keys and unique constraints.
5. **Assuming Spring Data R2DBC auto-loads relationships.** Explicit repository or JOIN queries are required.
6. **Using @MappedCollection as an ORM many-to-many mechanism.** It serves aggregate-owned data; references to independent aggregates should use IDs and an association entity.
7. **Using flatMap to query each related object individually.** Can cause N+1 queries; consider JOINs or batch queries.
8. **Deleting a Student and deleting related Courses.** Removing one side should only delete link rows, not entities on the other side.
9. **Cascading in the wrong direction.** Deleting a Student must not delete a Course that other students are enrolled in.
10. **Missing an index for the reverse query direction.** Querying Students from a Course can become slow as the join table grows.
11. **Unbounded lists.** Loading all links can exhaust memory and produce oversized responses.
12. **Treating link save as an upsert.** Repository save depends on entity state; use constraints and explicit SQL upserts when idempotency is required.

## Quick Selection Rules

- Use a join table with two foreign keys to represent a many-to-many relationship.
- Create a unique constraint on the foreign key pair if each pair may appear only once.
- Model the join table as a separate entity in Spring Data R2DBC, especially when it holds business attributes.
- Store IDs of both aggregates in the association entity; load details from either side using repositories or JOINs when needed.
- Create indexes supporting queries in both directions.
- Delete link rows when removing an association; do not delete the entity on the opposite side.
- Use reactive transactions when multiple operations must commit or roll back together.
- Paginate and avoid N+1 queries when association lists are large.

A join table is the standard representation for many-to-many relationships in relational databases. In Spring Data R2DBC, treating the join row as an entity with explicit foreign keys helps the application manage creating, reading, updating, and deleting associations explicitly. The database enforces integrity with foreign keys and unique constraints; repositories and DatabaseClient provide reactive operations; and JOINs build efficient read models when information from both sides is needed. This design keeps aggregate boundaries clear and avoids relying on automatic ORM object-graph management.
