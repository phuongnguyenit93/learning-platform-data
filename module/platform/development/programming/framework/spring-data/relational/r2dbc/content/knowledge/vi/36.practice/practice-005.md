# Xử lý cập nhật đồng thời bằng `@Version` và phản hồi xung đột

Trong ứng dụng Spring Data Relational R2DBC, nhiều request có thể cùng đọc và cập nhật một bản ghi. Nếu hai request cùng đọc một phiên bản rồi lần lượt ghi dữ liệu, request ghi sau có thể vô tình ghi đè thay đổi của request trước. Đây là lost update (mất cập nhật): cả hai request đều có vẻ thành công, nhưng một thay đổi bị mất.

Spring Data Relational hỗ trợ optimistic locking (khóa lạc quan) thông qua annotation `@Version`. Framework lưu một giá trị version trên entity, kiểm tra version hiện tại khi cập nhật và tăng version khi ghi thành công. Nếu entity đang được lưu mang version cũ, update không khớp hàng nào và Spring Data phát lỗi `OptimisticLockingFailureException`. Ứng dụng có thể chuyển lỗi này thành phản hồi xung đột HTTP `409 Conflict`, hoặc dùng conditional request với `ETag`/`If-Match` để trả `412 Precondition Failed` khi điều kiện của client không còn đúng.

## 1. Vấn đề cập nhật đồng thời

Giả sử một tài liệu có dữ liệu ban đầu:

```text
id = 42
title = "Bản nháp"
version = 5
```

Hai người dùng A và B cùng mở tài liệu. Cả hai nhận version 5. A đổi tiêu đề; B đổi nội dung. Nếu câu update chỉ có `WHERE id = 42`, request ghi sau có thể ghi cả snapshot cũ lên dữ liệu mới và làm mất thay đổi trước đó.

Timeline:

```mermaid
sequenceDiagram
    participant A as Request A
    participant B as Request B
    participant DB as Database

    A->>DB: SELECT document id=42 (version 5)
    B->>DB: SELECT document id=42 (version 5)
    A->>DB: UPDATE document ... WHERE id=42 AND version=5
    DB-->>A: 1 row updated; version becomes 6
    B->>DB: UPDATE document ... WHERE id=42 AND version=5
    DB-->>B: 0 rows updated
    Note over B: Optimistic locking conflict
```

Request A thành công và version chuyển thành 6. Request B vẫn gửi version 5 nên không cập nhật được hàng nào. Framework báo xung đột thay vì âm thầm ghi đè dữ liệu mới.

## 2. Optimistic locking là gì?

Optimistic locking giả định xung đột không xảy ra thường xuyên. Thay vì khóa hàng ngay từ lúc đọc và giữ khóa trong toàn bộ thời gian người dùng chỉnh sửa, ứng dụng cho phép nhiều request đọc cùng dữ liệu. Khi ghi, hệ thống kiểm tra xem dữ liệu có còn ở version mà request đã đọc hay không.

Quy trình cơ bản:

1. Đọc entity cùng giá trị version hiện tại.
2. Thực hiện thay đổi trong bộ nhớ.
3. Gửi update với điều kiện `id` và `version` cũ.
4. Nếu một hàng được cập nhật, tăng version và coi thao tác thành công.
5. Nếu không có hàng nào khớp, báo conflict để caller quyết định đọc lại, merge hoặc yêu cầu người dùng xử lý.

Optimistic locking không giữ database lock trong lúc người dùng mở màn hình. Nó phát hiện xung đột tại thời điểm ghi. Cách này thường phù hợp với dữ liệu được đọc nhiều, cập nhật ít và các thao tác chỉnh sửa có thời gian giữa lần đọc và lần ghi.

## 3. Khai báo thuộc tính `@Version`

Spring Data Relational dùng `@Version` từ package `org.springframework.data.annotation.Version`. Thuộc tính version cần có kiểu số được hỗ trợ, ví dụ `int`, `Integer`, `long` hoặc `Long`.

Ví dụ entity mutable:

```java
@Table("document")
public class Document {

    @Id
    private Long id;

    private String title;

    private String content;

    @Version
    private Long version;

    // Constructor, getter và các phương thức cần thiết.
}
```

Với mô hình immutable, có thể dùng Java record:

```java
@Table("document")
public record Document(
        @Id Long id,
        String title,
        String content,
        @Version long version
) {
}
```

Khi tạo entity mới, version ban đầu được khởi tạo theo quy tắc của Spring Data (thường là 0 đối với kiểu primitive). Khi update, framework tăng version. Với entity immutable/record, hãy dùng instance được publisher `save()` phát ra để nhận version mới; không giả định object đầu vào bị thay đổi.

## 4. Cấu trúc bảng cần có cột version

Database phải có cột tương ứng với property version. Ví dụ PostgreSQL:

```sql
CREATE TABLE document (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(250) NOT NULL,
    content TEXT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);
```

Kiểu SQL phải tương thích với kiểu Java. Nếu dùng primitive `long`, cột `BIGINT NOT NULL` là lựa chọn phù hợp. Cấu hình default của database không thay thế cơ chế version do Spring Data quản lý; framework có thể bind giá trị version ban đầu trong insert.

Khi thêm `@Version` vào một bảng đã có dữ liệu, cần migration tạo cột và gán version ban đầu cho các hàng hiện có:

```sql
ALTER TABLE document
    ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

Hãy kiểm tra dữ liệu cũ và migration trước khi triển khai. Nếu ứng dụng có nhiều phiên bản chạy đồng thời trong quá trình rolling deployment, mọi phiên bản cần tương thích với schema mới và chiến lược version.

## 5. Spring Data thực hiện update có điều kiện như thế nào?

Khi lưu entity đã tồn tại có `@Version`, Spring Data Relational tạo update tương đương:

```sql
UPDATE document
SET title = :title,
    content = :content,
    version = :newVersion
WHERE id = :id
  AND version = :oldVersion;
```

Điều kiện `version = :oldVersion` là phần phát hiện xung đột. Khi một request khác đã cập nhật hàng, version trong database không còn khớp. Update ảnh hưởng 0 hàng, Spring Data xem đó là optimistic locking failure.

Đây là mô tả logic; SQL thực tế có thể khác theo dialect, mapping, các cột được cập nhật và phiên bản Spring Data. Ứng dụng không cần tự tạo câu lệnh này khi dùng repository/template entity save thông thường.

## 6. Lưu entity mới và nhận version được framework quản lý

Repository reactive:

```java
public interface DocumentRepository
        extends ReactiveCrudRepository<Document, Long> {
}
```

Khi tạo mới:

```java
public Mono<Document> create(CreateDocumentRequest request) {
    Document document = new Document(
            null,
            request.title(),
            request.content(),
            0L);

    return documentRepository.save(document);
}
```

Caller nên dùng entity được `save()` phát ra. Với record, Spring Data có thể tạo instance mới chứa ID và version được ánh xạ; object `document` ban đầu vẫn giữ nguyên.

Ví dụ:

```java
return documentRepository.save(document)
        .map(saved -> new DocumentResponse(
                saved.id(),
                saved.title(),
                saved.content(),
                saved.version()));
```

Không tự tăng version trước khi gọi `save()` trong luồng entity mapping thông thường. Spring Data cần version hiện tại để tạo điều kiện update và quản lý version tiếp theo.

## 7. Cập nhật bằng repository `save()`

Một service có thể đọc entity hiện tại, tạo bản sao chứa dữ liệu mới và gọi `save()`:

```java
@Service
public class DocumentService {

    private final DocumentRepository repository;

    public DocumentService(DocumentRepository repository) {
        this.repository = repository;
    }

    public Mono<Document> update(Long id, UpdateDocumentRequest request) {
        return repository.findById(id)
                .switchIfEmpty(Mono.error(
                        new DocumentNotFoundException(id)))
                .flatMap(current -> {
                    Document changed = new Document(
                            current.id(),
                            request.title(),
                            request.content(),
                            current.version());

                    return repository.save(changed);
                });
    }
}
```

Nếu hai request cùng đọc version 5 trước khi request nào ghi, cả hai bản sao đều mang version 5. Request đầu tiên save thành công và version chuyển thành 6. Request thứ hai save với version 5 sẽ phát `OptimisticLockingFailureException`.

Trong ví dụ này, `save()` thực hiện optimistic check ở thời điểm ghi. Nếu API nhận version từ client, service còn phải kiểm tra version kỳ vọng của client như phần tiếp theo; nếu không, request cũ có thể tải lại entity mới nhất rồi ghi đè dữ liệu mà không phát hiện client đang sửa một bản cũ.

## 8. Phân biệt xung đột giữa hai lần ghi với client gửi dữ liệu cũ

Có hai tình huống khác nhau:

**Race giữa hai thao tác save:** hai request đã đọc cùng version trước đó, cả hai cố ghi. `@Version` tự phát hiện request ghi sau.

**Client chỉnh sửa lâu rồi gửi lại dữ liệu cũ:** khi request đến server, service đọc entity mới nhất. Nếu service bỏ qua version client gửi và dùng version mới nhất vừa đọc, nó có thể ghi dữ liệu cũ của client lên trạng thái mới mà không có optimistic conflict.

Ví dụ nguy hiểm:

```java
public Mono<Document> update(Long id, UpdateDocumentRequest request) {
    return repository.findById(id)
            .flatMap(current -> repository.save(new Document(
                    current.id(),
                    request.title(),
                    request.content(),
                    current.version())));
}
```

Nếu request không mang `expectedVersion`, server không biết client đã đọc dữ liệu từ version nào. `@Version` chỉ kiểm tra entity mà server đang cố lưu có còn mới tại thời điểm update hay không; nó không tự biết snapshot mà trình duyệt đang hiển thị.

Với API chỉnh sửa từ client, hãy gửi version kỳ vọng trong request body hoặc HTTP `If-Match` header và so sánh với version hiện tại trước khi lưu. Điều này bảo vệ cả khoảng thời gian người dùng chỉnh sửa ngoài server.

## 9. Kiểm tra version kỳ vọng trong service

Request DTO:

```java
public record UpdateDocumentRequest(
        String title,
        String content,
        long expectedVersion
) {
}
```

Service:

```java
public Mono<Document> update(Long id, UpdateDocumentRequest request) {
    return repository.findById(id)
            .switchIfEmpty(Mono.error(
                    new DocumentNotFoundException(id)))
            .flatMap(current -> {
                if (current.version() != request.expectedVersion()) {
                    return Mono.error(new DocumentVersionConflictException(
                            id,
                            request.expectedVersion(),
                            current.version()));
                }

                Document changed = new Document(
                        current.id(),
                        request.title(),
                        request.content(),
                        current.version());

                return repository.save(changed);
            });
}
```

So sánh này phát hiện client đã gửi một version cũ trước khi gọi save. `@Version` vẫn cần thiết vì một request khác có thể cập nhật database sau khi service đọc `current` nhưng trước khi `save(changed)` thực thi. Hai lớp kiểm tra bổ sung cho nhau:

- So sánh `expectedVersion`: phát hiện client đã chỉnh sửa từ snapshot cũ.
- `@Version` trong SQL update: phát hiện race xảy ra sau khi server đọc entity.

Không bỏ optimistic locking ở database chỉ vì đã so sánh version trong Java. So sánh Java đơn thuần có race giữa check và write.

## 10. Phản hồi HTTP `409 Conflict`

Khi optimistic lock thất bại, ứng dụng REST thường trả `409 Conflict`. Đây là phản hồi cho biết request không thể áp dụng vì trạng thái tài nguyên đã thay đổi.

Exception handler trong Spring WebFlux:

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler({
            DocumentVersionConflictException.class,
            OptimisticLockingFailureException.class
    })
    public ResponseEntity<ProblemDetail> handleVersionConflict(Exception ex) {
        ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.CONFLICT);
        problem.setTitle("Document version conflict");
        problem.setDetail(
                "The document has changed. Reload it and apply your changes again.");

        return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
    }
}
```

`OptimisticLockingFailureException` thuộc Spring DAO exception hierarchy. Có thể có exception subclass cụ thể tùy tầng repository/driver. Handler nên tránh trả SQL, stack trace, version nội bộ nhạy cảm hoặc thông tin của người dùng khác.

Với WebFlux annotated controller, exception handler có thể trả `ResponseEntity` hoặc reactive publisher tương ứng. Nếu handler cần gọi database để tạo response, trả `Mono<ResponseEntity<...>>` và giữ toàn bộ công việc trong reactive chain.

## 11. Khi nào dùng `409` và khi nào dùng `412`?

Hai status code có thể dùng cho hai hợp đồng API khác nhau:

| HTTP status | Ý nghĩa | Trường hợp thường dùng |
| --- | --- | --- |
| `409 Conflict` | Request xung đột với trạng thái hiện tại của tài nguyên | API nhận `expectedVersion` trong body hoặc phát hiện optimistic lock khi save |
| `412 Precondition Failed` | Điều kiện HTTP mà client gửi không được thỏa mãn | Request dùng `If-Match` với ETag cũ |

Nếu API dùng body field `expectedVersion`, `409` là lựa chọn dễ hiểu. Nếu dùng HTTP conditional request, `If-Match` không khớp thì `412` phù hợp với semantics của HTTP.

Hãy chọn một hợp đồng nhất quán và ghi rõ trong API documentation. Không trả `200 OK` với một field `conflict=true` nếu client cần dựa vào HTTP status để xử lý lỗi điều kiện.

## 12. Dùng ETag và `If-Match`

Version có thể được biểu diễn thành HTTP ETag. Khi đọc tài liệu, server trả ETag tương ứng version:

```java
@GetMapping("/{id}")
public Mono<ResponseEntity<DocumentResponse>> get(@PathVariable Long id) {
    return documentService.findById(id)
            .map(document -> ResponseEntity.ok()
                    .eTag("\"" + document.version() + "\"")
                    .body(DocumentResponse.from(document)));
}
```

Ví dụ response header:

```http
ETag: "5"
```

Client gửi lại version đã đọc khi cập nhật:

```http
PUT /documents/42
If-Match: "5"
Content-Type: application/json
```

Server phải parse và kiểm tra `If-Match` theo semantics HTTP. Ví dụ minh họa một ETag đơn giản dạng version; implementation production cần xử lý cú pháp ETag, nhiều tag, wildcard `*`, weak tag và giá trị không hợp lệ theo hợp đồng API. `If-Match` sử dụng strong comparison; không tự bỏ qua cú pháp header.

Controller có thể chuyển version đã parse thành `expectedVersion` cho service:

```java
@PutMapping("/{id}")
public Mono<ResponseEntity<DocumentResponse>> update(
        @PathVariable Long id,
        @RequestHeader(HttpHeaders.IF_MATCH) String ifMatch,
        @RequestBody UpdateDocumentBody body) {

    long expectedVersion = etagParser.requireSingleVersion(ifMatch);

    return documentService.update(id, expectedVersion, body)
            .map(saved -> ResponseEntity.ok()
                    .eTag(etagFor(saved.version()))
                    .body(DocumentResponse.from(saved)));
}
```

Nếu `If-Match` không khớp version hiện tại, trả `412 Precondition Failed`. Nếu race xảy ra sau lần kiểm tra trong service và `@Version` phát optimistic locking exception, cũng có thể ánh xạ lỗi này thành 412 để giữ đúng hợp đồng conditional update.

## 13. Ví dụ service hỗ trợ expected version

Có thể viết service nhận version kỳ vọng trực tiếp:

```java
public Mono<Document> update(
        Long id,
        long expectedVersion,
        UpdateDocumentBody body) {

    return repository.findById(id)
            .switchIfEmpty(Mono.error(new DocumentNotFoundException(id)))
            .flatMap(current -> {
                if (current.version() != expectedVersion) {
                    return Mono.error(new DocumentVersionConflictException(id));
                }

                Document changed = new Document(
                        current.id(),
                        body.title(),
                        body.content(),
                        current.version());

                return repository.save(changed)
                        .onErrorMap(
                                OptimisticLockingFailureException.class,
                                error -> new DocumentVersionConflictException(id, error));
            });
}
```

Nếu có nhiều kiểu lỗi conflict, nên dùng một exception miền thống nhất để controller ánh xạ HTTP status. Giữ exception gốc làm cause để log/tracing nội bộ, nhưng không trả cause cho client.

## 14. Cập nhật entity immutable và version mới

Với record, mỗi lần thay đổi phải tạo instance mới. Phương thức helper có thể giữ nguyên version cũ để Spring Data dùng làm điều kiện update:

```java
public record Document(
        @Id Long id,
        String title,
        String content,
        @Version long version
) {

    public Document withContent(String newContent) {
        return new Document(id, title, newContent, version);
    }

    public Document withTitle(String newTitle) {
        return new Document(id, newTitle, content, version);
    }
}
```

Sau khi save:

```java
return repository.save(current.withContent(request.content()))
        .map(saved -> {
            // saved.version() là version mới do Spring Data trả về.
            return DocumentResponse.from(saved);
        });
```

Không viết `withContent` tự tăng version. Nếu tạo record với version `current.version() + 1` trước khi save, điều kiện update có thể dùng sai version và gây conflict giả hoặc làm lệch mapping. Hãy để Spring Data quản lý version cho entity save thông thường.

## 15. Xử lý `OptimisticLockingFailureException` trong reactive chain

Lỗi optimistic lock phát ra qua publisher nên cần được xử lý bằng reactive operators hoặc `@ExceptionHandler` ở WebFlux boundary:

```java
return repository.save(changed)
        .onErrorMap(
                OptimisticLockingFailureException.class,
                error -> new DocumentVersionConflictException(id, error));
```

Hoặc xử lý tại controller advice. Không gọi `block()` để bắt lỗi trong service reactive. Không gọi `subscribe()` rồi tự xử lý lỗi trong một luồng tách rời; khi đó HTTP caller có thể nhận response trước khi conflict xảy ra.

Nếu dùng `onErrorResume`, chỉ chuyển đúng loại optimistic locking exception. Không biến mọi lỗi database thành `409`, vì timeout, connection failure, SQL syntax error hoặc constraint violation có ý nghĩa khác.

## 16. `@Version` không phải pessimistic lock

Optimistic locking không khóa hàng ngay khi đọc. Hai transaction vẫn có thể đọc cùng version; xung đột chỉ được phát hiện khi update có điều kiện.

Pessimistic locking thường dùng cơ chế khóa database như `SELECT ... FOR UPDATE`, giữ lock tới commit/rollback. R2DBC hỗ trợ transaction reactive nhưng khả năng locking syntax phụ thuộc database và driver. Không dùng pessimistic lock chỉ để tránh phải xử lý conflict nếu workload không cần thiết.

| Tiêu chí | Optimistic locking (`@Version`) | Pessimistic locking |
| --- | --- | --- |
| Thời điểm phát hiện/chặn xung đột | Khi ghi | Khi lấy lock/đọc khóa |
| Giữ database lock trong lúc người dùng chỉnh sửa | Không | Có thể, nếu transaction giữ lock |
| Phù hợp | Đọc nhiều, ghi ít, conflict tương đối hiếm | Tranh chấp cao hoặc cần tuần tự hóa thao tác cụ thể |
| Chi phí | Có thể phải xử lý retry/conflict | Có thể tăng lock wait và deadlock |
| Hành vi khi nhiều request cùng sửa | Một update thắng, update stale bị từ chối | Request sau có thể phải chờ lock |

Đối với màn hình chỉnh sửa kéo dài, optimistic locking thường phù hợp hơn vì không giữ transaction và lock trong suốt thời gian người dùng suy nghĩ.

## 17. `@Version` chỉ tự động áp dụng cho entity persistence có mapping version

Khi dùng `repository.save(entity)` hoặc API entity mapping tương ứng của Spring Data Relational, framework có metadata để đọc `@Version` và thực hiện optimistic locking.

Không nên giả định mọi SQL trong ứng dụng đều tự động được bảo vệ. Các đường truy cập sau có thể bỏ qua cơ chế version entity:

- `DatabaseClient.sql(...)` với câu `UPDATE` tự viết.
- R2DBC SPI `Connection.createStatement(...)`.
- Bulk update/delete trực tiếp.
- Stored procedure tự cập nhật bảng.
- SQL chạy từ một công cụ hoặc service khác.

Nếu có đường ghi trực tiếp, cần thêm điều kiện version và tăng version trong SQL, hoặc đảm bảo chỉ một đường ghi được phép thay đổi entity đó. `@Version` không tự biến mọi câu SQL cùng bảng thành optimistic locking.

## 18. Tự viết update có version predicate bằng `DatabaseClient`

Với SQL tùy chỉnh, thực hiện update nguyên tử:

```java
public Mono<Void> updateTitle(
        Long id,
        long expectedVersion,
        String title) {

    return databaseClient.sql("""
            UPDATE document
            SET title = :title,
                version = version + 1
            WHERE id = :id
              AND version = :expectedVersion
            """)
            .bind("title", title)
            .bind("id", id)
            .bind("expectedVersion", expectedVersion)
            .fetch()
            .rowsUpdated()
            .flatMap(updated -> {
                if (updated == 1) {
                    return Mono.empty();
                }

                return Mono.error(new OptimisticLockingFailureException(
                        "Document was changed or does not exist"));
            });
}
```

Điều kiện version và phép tăng version nằm trong cùng một câu SQL nên database thực hiện kiểm tra/cập nhật nguyên tử. Không tách thành `SELECT version` rồi mới `UPDATE WHERE id = :id`, vì giữa hai câu lệnh có thể xảy ra race.

Khi `rowsUpdated()` bằng 0, có thể là ID không tồn tại hoặc version không còn khớp. Nếu API cần phân biệt 404 và 409, có thể truy vấn tồn tại sau đó; cần chấp nhận rằng trạng thái có thể thay đổi tiếp giữa update và query phân loại. Nhiều API chọn trả conflict chung cho precondition không được thỏa mãn hoặc dùng một chiến lược truy vấn/transaction phù hợp.

## 19. Dùng `@Modifying` với `@Query`

Nếu repository dùng modifying query, phải viết version predicate và tăng version tường minh:

```java
public interface DocumentRepository
        extends ReactiveCrudRepository<Document, Long> {

    @Modifying
    @Query("""
            UPDATE document
            SET title = :title,
                version = version + 1
            WHERE id = :id
              AND version = :expectedVersion
            """)
    Mono<Integer> updateTitleIfVersionMatches(
            @Param("id") Long id,
            @Param("title") String title,
            @Param("expectedVersion") long expectedVersion);
}
```

Sau đó kiểm tra số hàng được cập nhật:

```java
return repository.updateTitleIfVersionMatches(id, title, expectedVersion)
        .flatMap(updated -> updated == 1
                ? Mono.empty()
                : Mono.error(new DocumentVersionConflictException(id)));
```

Chữ ký số hàng cập nhật và hỗ trợ modifying query phụ thuộc phiên bản Spring Data R2DBC. Nếu API hiện tại không hỗ trợ kiểu trả về trong ví dụ, dùng `DatabaseClient.fetch().rowsUpdated()` hoặc kiểu được phiên bản đó tài liệu hóa.

`@Modifying` không tự áp dụng optimistic locking metadata như entity `save()`. Phần version predicate và increment là trách nhiệm của SQL tùy chỉnh.

## 20. Bulk update có thể bỏ qua optimistic locking entity

Một câu update nhiều hàng thường không materialize từng entity và không chạy entity lifecycle như `save()`:

```sql
UPDATE document
SET archived = TRUE
WHERE last_accessed_at < :cutoff;
```

Nếu bảng dùng version để bảo vệ thao tác cập nhật đồng thời, cần quyết định bulk operation có phải tăng version hay không:

```sql
UPDATE document
SET archived = TRUE,
    version = version + 1
WHERE last_accessed_at < :cutoff;
```

Tăng version giúp các entity đã được đọc trước đó trở thành stale khi save sau này. Nếu bulk operation không tăng version, một entity cũ có thể ghi đè thay đổi của bulk update mà không bị phát hiện. Xác định rõ semantics cho từng đường ghi.

## 21. Xử lý khi gặp conflict: trả lỗi, đọc lại hay merge?

Không có một cách xử lý conflict phù hợp cho mọi nghiệp vụ. Các lựa chọn phổ biến:

| Chiến lược | Khi phù hợp | Lưu ý |
| --- | --- | --- |
| Trả `409 Conflict` | Người dùng cần xem dữ liệu mới và quyết định lại | Không tự ghi đè thay đổi của người khác |
| Trả `412 Precondition Failed` | API dùng ETag/`If-Match` | Client cần GET lại tài nguyên hoặc ETag mới |
| Tự đọc lại và merge | Các field thay đổi độc lập và có quy tắc merge rõ | Phải kiểm tra lại invariant nghiệp vụ |
| Retry với version mới | Thao tác có thể tính lại an toàn từ trạng thái mới | Không replay nguyên snapshot cũ một cách mù quáng |
| Chuyển sang review thủ công | Xung đột có ý nghĩa nghiệp vụ cao | Giữ lại hai phiên bản hoặc audit trail |

Với tài liệu có hai trường nội dung, có thể cho người dùng so sánh phiên bản hiện tại và bản họ chỉnh sửa. Với số dư tài khoản hoặc tồn kho, không nên tự merge giá trị tuyệt đối; cần mô hình command/operation để tính lại theo trạng thái mới.

## 22. Không retry mù quáng khi optimistic lock thất bại

Một cách xử lý nguy hiểm là bắt conflict, đọc version mới nhất rồi tạo entity với toàn bộ dữ liệu cũ của request và save lại:

```java
// Không nên: có thể ghi đè thay đổi mới bằng snapshot cũ.
return repository.save(changed)
        .onErrorResume(OptimisticLockingFailureException.class,
                error -> repository.findById(id)
                        .flatMap(latest -> repository.save(
                                new Document(
                                        latest.id(),
                                        changed.title(),
                                        changed.content(),
                                        latest.version()))));
```

Đoạn code này bỏ qua xung đột bằng cách lấy version mới nhưng vẫn dùng nội dung cũ. Nó có thể tái tạo chính lost update mà `@Version` đang ngăn.

Nếu retry, phải xác định command nào có thể áp dụng lại và cách merge. Ví dụ command `incrementViewCount` có thể tính lại trên giá trị mới; command `replaceEntireDocument` thường cần người dùng xác nhận khi snapshot stale. Không retry vô hạn; giới hạn số lần và quan sát conflict rate.

## 23. Phân biệt optimistic conflict với lỗi database khác

Không ánh xạ mọi exception database thành `409`:

| Lỗi | Ý nghĩa thường gặp | Phản hồi có thể phù hợp |
| --- | --- | --- |
| `OptimisticLockingFailureException` | Version stale hoặc hàng không còn khớp | `409` hoặc `412` theo hợp đồng |
| Entity không tồn tại | ID không có | `404 Not Found` |
| Unique constraint violation | Giá trị trùng với ràng buộc duy nhất | `409 Conflict` hoặc lỗi validation theo API |
| Foreign key violation | Tham chiếu không hợp lệ | `409`/`422` tùy nghiệp vụ |
| Query timeout | Database không hoàn tất trong thời hạn | `503`/`504` tùy tầng và chính sách |
| Connection failure | Không thể giao tiếp với database | `503 Service Unavailable` hoặc lỗi hệ thống |
| SQL syntax/mapping error | Lỗi code hoặc cấu hình | `500 Internal Server Error` |

Optimistic locking exception có thể phát sinh khi hàng bị xóa hoặc version không khớp. Nếu cần phân biệt xóa với update cạnh tranh, service có thể kiểm tra lại sự tồn tại và ánh xạ theo hợp đồng API.

## 24. Kiểm thử optimistic locking với hai snapshot

Integration test cần tạo hai snapshot cùng version, sau đó save lần lượt:

```java
@SpringBootTest
class DocumentOptimisticLockingTest {

    @Autowired
    DocumentRepository repository;

    @Test
    void rejectsSecondSaveFromStaleSnapshot() {
        Document initial = new Document(
                null, "Original", "Initial body", 0L);

        Mono<Void> scenario = repository.save(initial)
                .flatMap(saved -> Mono.zip(
                                repository.findById(saved.id()),
                                repository.findById(saved.id()))
                        .flatMap(snapshots -> {
                            Document first = snapshots.getT1();
                            Document stale = snapshots.getT2();

                            Document firstChange = new Document(
                                    first.id(),
                                    "Changed by A",
                                    first.content(),
                                    first.version());

                            Document secondChange = new Document(
                                    stale.id(),
                                    "Changed by B",
                                    stale.content(),
                                    stale.version());

                            return repository.save(firstChange)
                                    .then(repository.save(secondChange))
                                    .then();
                        }));

        StepVerifier.create(scenario)
                .expectError(OptimisticLockingFailureException.class)
                .verify();
    }
}
```

Test tạo hai lần đọc trước khi ghi lần đầu nên cả hai snapshot có cùng version. Save A thành công; save B dùng version cũ và phải phát optimistic locking exception.

Trong test thực tế, cần dọn fixture bằng R2DBC hoặc dùng database/schema test riêng. Sau khi nhận lỗi, query lại document bằng subscription mới để xác nhận dữ liệu của A vẫn tồn tại và version đã tăng. Dùng đúng database/driver production vì affected-row count và transaction behavior phụ thuộc driver.

## 25. Xác minh version tăng sau save

Một test thành công nên kiểm tra version được tăng:

```java
StepVerifier.create(repository.save(new Document(
                null, "Title", "Body", 0L)))
        .assertNext(saved -> {
            assertThat(saved.id()).isNotNull();
            assertThat(saved.version()).isEqualTo(0L);
        })
        .verifyComplete();
```

Sau đó update:

```java
StepVerifier.create(repository.findById(id)
                .flatMap(current -> repository.save(
                        new Document(
                                current.id(),
                                "Updated title",
                                current.content(),
                                current.version()))))
        .assertNext(updated ->
                assertThat(updated.version()).isEqualTo(1L))
        .verifyComplete();
```

Ví dụ giả định primitive `long` và initial version là 0 theo mapping. Hãy dùng giá trị/behavior của phiên bản Spring Data và schema thực tế. Mục tiêu test là chứng minh version sau update tăng so với version trước, không hardcode giả định nếu ứng dụng có chiến lược version khác.

## 26. Kiểm thử HTTP conflict bằng WebTestClient

Ở tầng API, cần xác minh exception được chuyển thành status đúng:

```java
webTestClient.put()
        .uri("/documents/{id}", documentId)
        .contentType(MediaType.APPLICATION_JSON)
        .bodyValue(new UpdateDocumentRequest(
                "New title", "New content", staleVersion))
        .exchange()
        .expectStatus().isEqualTo(HttpStatus.CONFLICT)
        .expectBody()
        .jsonPath("$.title").isEqualTo("Document version conflict");
```

Test nên có dữ liệu đã được cập nhật lên version mới trước khi gửi request stale. Ngoài status, kiểm tra response không chứa SQL, stack trace hoặc dữ liệu của người cập nhật khác.

Nếu API dùng `If-Match`, test ETag đúng sẽ thành công và trả ETag mới; ETag cũ phải nhận `412 Precondition Failed`. Test header sai cú pháp nên nhận `400 Bad Request` theo hợp đồng API.

## 27. Version và transaction boundary

Optimistic locking thường hoạt động nhờ một câu update có điều kiện nguyên tử. Khi một transaction gồm nhiều thao tác database, có thể dùng `R2dbcTransactionManager` để bảo đảm các thay đổi trong cùng database cùng commit/rollback.

Ví dụ:

```java
return transactionalOperator.transactional(
        documentRepository.save(changed)
                .flatMap(saved -> auditRepository.save(
                                AuditEntry.documentUpdated(saved.id(), saved.version()))
                        .thenReturn(saved))
);
```

Nếu optimistic lock thất bại ở bước save, publisher phát lỗi và transaction có thể rollback. Nếu save thành công nhưng audit insert thất bại, transaction cũng rollback thay đổi document khi cả hai thao tác dùng cùng `ConnectionFactory` và transaction manager.

Không gọi `subscribe()` riêng cho audit. Nếu audit dùng database khác, một R2DBC transaction manager không tự rollback nguồn đó; cần thiết kế outbox hoặc cơ chế phối hợp riêng.

## 28. `@Version` không thay thế validation và authorization

Version chỉ phát hiện trạng thái đã thay đổi. Nó không chứng minh người dùng có quyền cập nhật entity hoặc dữ liệu gửi lên hợp lệ.

Service vẫn cần:

- Kiểm tra entity tồn tại.
- Kiểm tra quyền sở hữu/tenant trước khi cập nhật.
- Validate dữ liệu mới và các invariant domain.
- Kiểm tra version kỳ vọng nếu client chỉnh sửa từ snapshot cũ.
- Ánh xạ conflict sang status code đúng.
- Ghi audit nếu nghiệp vụ yêu cầu.

Ví dụ query theo ID và tenant:

```java
@Query("""
        SELECT * FROM document
        WHERE id = :id AND tenant_id = :tenantId
        """)
Mono<Document> findForTenant(
        @Param("id") Long id,
        @Param("tenantId") Long tenantId);
```

Tenant ID phải đến từ security context đã xác thực. Không dùng version hoặc ID như một biện pháp phân quyền.

## 29. Tương thích khi thêm version vào ứng dụng đang chạy

Khi triển khai `@Version` trên hệ thống đã có dữ liệu, cần có migration và kế hoạch rolling deployment:

1. Thêm cột version với giá trị khởi tạo phù hợp cho mọi hàng hiện tại.
2. Triển khai code hiểu version và kiểm tra tương thích giữa các instance.
3. Cập nhật API/client để gửi expected version hoặc ETag nếu cần bảo vệ chỉnh sửa từ snapshot cũ.
4. Theo dõi conflict rate và các đường ghi trực tiếp chưa được cập nhật.
5. Loại bỏ phiên bản ứng dụng cũ không hỗ trợ version trước khi dựa hoàn toàn vào cơ chế mới.

Nếu một phiên bản cũ tiếp tục update bảng mà không tăng version, phiên bản mới có thể không phát hiện thay đổi do code cũ tạo ra. Mọi đường ghi cần tuân thủ cùng chính sách version hoặc phải có chiến lược tương thích trong thời gian triển khai.

Với bulk update, job nền, stored procedure hoặc công cụ quản trị, kiểm tra chúng có tăng version hay không. Cột version chỉ hữu ích khi tất cả đường ghi quan trọng duy trì semantics nhất quán.

## 30. Xử lý conflict trong UI

API trả `409` hoặc `412` cần hướng dẫn client hành động. Một giao diện chỉnh sửa có thể:

1. Giữ bản nháp người dùng đang nhập.
2. Tải phiên bản mới nhất từ server.
3. Hiển thị thay đổi mới và nội dung người dùng định gửi.
4. Cho phép người dùng so sánh, copy hoặc merge phần thay đổi.
5. Gửi lại với version/ETag mới sau khi người dùng xác nhận.

Không tự động reload rồi gửi lại dữ liệu cũ mà không thông báo. Điều đó chỉ chuyển lost update thành một lần ghi đè có vẻ thành công.

Với trường dữ liệu độc lập, có thể hỗ trợ merge theo field nếu nghiệp vụ cho phép. Với rich text hoặc tài liệu cộng tác, cân nhắc merge algorithm chuyên dụng, operational transform hoặc CRDT thay vì chỉ dùng version scalar.

## 31. Theo dõi conflict rate

Optimistic locking giúp phát hiện xung đột nhưng conflict quá thường xuyên có thể là dấu hiệu mô hình cập nhật hoặc UX chưa phù hợp.

Nên theo dõi:

- Số optimistic locking failure theo loại entity/use case.
- Tỷ lệ conflict trên tổng số update.
- Số lần client retry sau conflict.
- Thời gian giữa lần đọc và lần ghi nếu ứng dụng có thể đo.
- Tỷ lệ conflict theo endpoint hoặc loại thao tác, với tag cardinality thấp.
- Số conflict do bulk update hoặc background job.

Không dùng document ID, user ID hoặc tenant ID làm metric tag có cardinality cao. Có thể ghi các giá trị đó trong log bảo mật phù hợp, nhưng metric nên dùng nhãn operation/entity type ổn định.

Nếu conflict thường xuyên, xem xét chia nhỏ aggregate, giảm thời gian chỉnh sửa, dùng command-based update, merge theo field hoặc chuyển một số thao tác sang cơ chế tuần tự hóa phù hợp.

## 32. Các lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
| --- | --- | --- |
| Quên `@Version` | Update có thể ghi đè thay đổi của request khác | Thêm version property và migration cột |
| Version SQL không tương thích kiểu Java | Mapping/bind lỗi hoặc overflow | Dùng kiểu số và cột SQL tương ứng |
| Tự tăng version trước khi gọi `save()` | Điều kiện update dùng version sai | Để Spring Data quản lý version entity |
| Dùng entity cũ sau save immutable | Caller tiếp tục gửi version cũ | Dùng instance được `save()` phát ra |
| Chỉ dùng `@Version`, không nhận expected version từ client | Client sửa snapshot cũ có thể ghi đè dữ liệu mới sau khi service reload | So sánh expected version/ETag với version hiện tại |
| Chỉ so sánh version trong Java, không có atomic predicate | Race xảy ra giữa check và update | Dùng `@Version` hoặc SQL `WHERE version = :expected` |
| Tự viết SQL nhưng quên tăng version | Các update sau không phát hiện thay đổi | Tăng version trong cùng câu update |
| Bulk update không tăng version | Entity cũ có thể ghi đè bulk change | Tăng version hoặc thiết kế chính sách rõ |
| Bắt conflict rồi lưu lại snapshot cũ với version mới | Tạo lost update | Merge/recalculate theo nghiệp vụ hoặc trả conflict |
| Ánh xạ mọi database exception thành 409 | Che giấu timeout/connection/schema lỗi | Chỉ ánh xạ optimistic conflict và lỗi đã phân loại |
| Dùng version làm authorization | Người dùng vẫn có thể sửa tài nguyên không thuộc quyền | Kiểm tra ownership/tenant độc lập |
| Test chỉ bằng mock | Không kiểm chứng affected-row và exception của driver | Integration test với database thật |

## 33. Quy trình triển khai optimistic locking

Khi cần phát hiện cập nhật đồng thời, thực hiện theo thứ tự:

1. Xác định entity/aggregate nào cần bảo vệ khỏi lost update.
2. Thêm property số có `@Version` và cột tương ứng trong database.
3. Dùng repository/template entity save để Spring Data thực hiện version check.
4. Với entity immutable, giữ version cũ khi tạo bản sao và dùng entity mới từ `save()` sau khi thành công.
5. Nếu client chỉnh sửa lâu, nhận expected version hoặc ETag/`If-Match`.
6. So sánh expected version với entity hiện tại trước khi save.
7. Vẫn dựa vào `@Version` để bắt race xảy ra giữa lần đọc và lần update.
8. Ánh xạ optimistic lock exception thành `409` hoặc `412` theo API contract.
9. Với SQL/bulk update tự viết, thêm version predicate và increment nguyên tử.
10. Quy định cách xử lý conflict: reload, merge, retry có kiểm soát hoặc yêu cầu người dùng giải quyết.
11. Kiểm thử hai snapshot cùng version, version tăng, HTTP status và transaction rollback.
12. Theo dõi conflict rate và bảo đảm mọi đường ghi duy trì version.

## 34. Nguyên tắc thực hành

- Dùng `@Version` để phát hiện update dựa trên entity version cũ.
- Dùng kiểu số được Spring Data Relational hỗ trợ và cột SQL tương thích.
- Để Spring Data tăng version khi entity save; không tự tăng trước khi gọi `save()`.
- Với record/immutable entity, giữ version cũ trong bản sao update và dùng entity được save trả về.
- Hiểu rằng `@Version` bắt race ở thời điểm ghi; nó không tự biết client đã chỉnh sửa từ snapshot nào.
- Nhận `expectedVersion` hoặc dùng ETag/`If-Match` để bảo vệ thời gian người dùng chỉnh sửa.
- Dùng `409 Conflict` cho xung đột ứng dụng hoặc `412 Precondition Failed` cho `If-Match` không thỏa mãn.
- Không retry mù quáng bằng cách gắn version mới lên toàn bộ dữ liệu cũ.
- Với `DatabaseClient`, `@Modifying`, bulk SQL hoặc stored procedure, tự thêm version predicate và increment.
- Kiểm tra authorization, tenant và validation độc lập với optimistic locking.
- Không biến mọi lỗi database thành conflict response.
- Kiểm thử bằng hai snapshot cùng version trên database/driver thực tế.
- Theo dõi conflict rate để điều chỉnh mô hình dữ liệu và trải nghiệm chỉnh sửa.

## 35. Kết luận

`@Version` giúp Spring Data Relational R2DBC phát hiện lost update bằng optimistic locking. Framework đưa version hiện tại vào điều kiện update, tăng version khi ghi thành công và phát `OptimisticLockingFailureException` nếu entity đã stale. Cơ chế này phù hợp với các màn hình chỉnh sửa hoặc nghiệp vụ có nhiều request cùng đọc một entity nhưng không muốn giữ database lock trong thời gian dài.

Để bảo vệ cả thời gian người dùng chỉnh sửa, API cần nhận version kỳ vọng hoặc ETag/`If-Match` và so sánh với trạng thái hiện tại. `@Version` vẫn là lớp kiểm tra nguyên tử ở database để bắt race sau lần đọc. Hãy trả `409 Conflict` hoặc `412 Precondition Failed` theo hợp đồng HTTP, cung cấp cách reload/merge có chủ đích và không retry snapshot cũ một cách mù quáng. Với SQL tùy chỉnh và bulk update, duy trì version predicate/increment tường minh; kiểm thử trên driver/database thật để xác nhận hành vi xung đột.
