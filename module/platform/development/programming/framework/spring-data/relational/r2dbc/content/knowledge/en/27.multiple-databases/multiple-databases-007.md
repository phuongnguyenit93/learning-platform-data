# Multi-Tenant Design and Protecting Data Boundaries

In a multi-tenant system, one application serves multiple organizational customers or tenants on the same platform. Each tenant has its own data, and only authorized users may read or modify that data. Spring Data R2DBC provides reactive repositories, mapping, and transactions, but it does not automatically enforce a safe tenant boundary across every SQL statement.

Therefore, multi-tenant design must be applied end-to-end—from user authentication, tenant resolution, database/schema selection, query construction, and transaction control to caching, messaging, and testing. A single missing tenant condition in a SELECT, UPDATE, or DELETE statement can expose or mutate another tenant's data.

There are three common storage models:

- **Shared database, shared schema:** all tenants share tables; each row has a tenant_id column.
- **Shared database, schema per tenant:** each tenant has its own schema within the same database.
- **Database per tenant:** each tenant has its own database and usually its own ConnectionFactory/pool.

Each model carries different isolation levels, operational costs, and scalability characteristics. Choose based on security requirements, scale, operational capability, and tenant customization needs.

## 1. Multi-Tenancy and Data Boundaries

A tenant is an independent business data scope, such as a company, organization, store, or workspace. A user may belong to one tenant or multiple tenants; tenant access permissions must be verified before querying data.

Example sales management system:

~~~text
Tenant A
  customers
  orders
  products

Tenant B
  customers
  orders
  products
~~~

Two tenants may have the same types of data and even identical customer codes or order numbers. However, tenant A must never read or modify tenant B's data.

### 1.1. Tenant Boundaries Must Be Enforced Across Multiple Layers

A secure design typically has multiple layers of defense:

1. **Identity and authorization:** identify the signed-in user and the tenants the user is permitted to access.
2. **Tenant context:** propagate the verified tenant throughout the reactive pipeline.
3. **Data access:** every query is scoped to the tenant or routed to the right database/schema.
4. **Database constraints:** keys, foreign keys, and row-level security prevent cross-tenant data corruption.
5. **Transaction:** every statement in the same business operation uses the same tenant context and appropriate connection.
6. **Cache and messaging:** cache keys, events, and consumers all preserve the right tenant scope.
7. **Testing and observability:** test cross-tenant access and monitor query behavior.

Do not treat tenant_id in a request body as proof of authorization. A client can alter that value. The tenant must be resolved from an authenticated principal and checked against membership/authorization on the server.

## 2. Choosing a Storage Model for Multiple Tenants

### 2.1. Shared Database, Shared Schema

All tenants share the same database, schema, and tables. Each table holding tenant data has a tenant_id column:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(240),
    created_at TIMESTAMP NOT NULL,
    last_modified_at TIMESTAMP NOT NULL,
    CONSTRAINT uk_customer_tenant_email UNIQUE (tenant_id, email)
);

CREATE INDEX ix_customers_tenant_name
    ON customers (tenant_id, name);
~~~

Advantages:

- Simple infrastructure, fewer databases and connection pools.
- Easy to roll out migrations once for all tenants.
- Good database resource utilization when tenant count is high and each tenant has modest data.
- Can run cross-tenant aggregate reports if business rules permit.

Disadvantages:

- Every query must have an accurate tenant predicate.
- One missing tenant_id condition can cause cross-tenant data access.
- Large tenants can affect other tenants' performance without resource limits.
- Some administrative operations or migrations must account for all tenants' data.

This is typically the easiest model to start with, but it demands query discipline and database-level safeguards.

### 2.2. Shared Database, Schema Per Tenant

Tenants share a database server/database but have separate schemas:

~~~text
database: saas
  schema tenant_a
    customers
    orders
    products
  schema tenant_b
    customers
    orders
    products
~~~

Advantages:

- Separates namespaces and database objects per tenant.
- Can grant separate database/schema permissions.
- Easier to back up/restore or move a single tenant compared to shared tables, depending on the DBMS.
- Queries inside a schema generally do not need tenant_id on every table.

Disadvantages:

- Schema management and migrations grow complex as tenant count increases.
- Connections must be routed to the right schema.
- Switching session schemas on pooled connections risks state leaks between requests if not reset.
- Aggregated reporting across tenants requires querying multiple schemas or a separate consolidation mechanism.

If the database supports schema qualification, queries can specify the schema explicitly. If relying on search path or the connection's default schema, manage context per transaction and connection.

### 2.3. Database Per Tenant

Each tenant has its own database, on the same server or across separate clusters:

~~~text
Tenant A -> ConnectionFactory A -> Database A
Tenant B -> ConnectionFactory B -> Database B
Tenant C -> ConnectionFactory C -> Database C
~~~

Advantages:

- Higher data and resource isolation.
- Can back up, restore, migrate, or move tenants independently.
- Easily meets requirements for certain customers needing dedicated databases.
- Can customize database settings per tenant.

Disadvantages:

- Number of ConnectionFactory beans and connection pools grows with tenant count.
- Provisioning, migrations, credential rotation, and monitoring are complex.
- Higher operational cost.
- Cross-tenant queries and multi-database transactions are harder.

With a very large number of tenants, do not default to creating an unbounded pool per tenant. You need a pool lifecycle strategy, total connection caps, idle eviction, and a tenant database registry.

### 2.4. Quick Comparison

| Criterion | Shared schema | Schema per tenant | Database per tenant |
| --- | --- | --- | --- |
| Data isolation | Relies heavily on tenant predicates and constraints | Separates namespaces/schemas | Separates databases |
| Connection pool count | Usually few | Can share a database pool | Usually many pools or a routing pool |
| Migrations | One shared schema | Iterates over each schema | Iterates over each database |
| Operational cost | Lower | Moderate | Higher |
| Cross-tenant reporting | Convenient if allowed | Must consolidate schemas | Must consolidate databases |
| Large tenant needing separation | Needs sharding or tenant migration | Can move schema | Already has a database boundary |
| Risk of missing tenant predicate | High | Lower if schema routing is correct | Lower if routing is correct |

A hybrid model can be used: most tenants in a shared schema, while large or compliance-constrained tenants have dedicated databases. This requires a tenant registry and a unified routing layer.

## 3. Identifying the Tenant from an Authenticated Identity

Tenant context should be established after authentication and authorization. A request may send a tenant slug or tenant ID in the host, header, or path, but the server must verify that the user has permission for that tenant.

Conceptual flow:

~~~text
HTTP request
    |
    v
Authenticate user
    |
    v
Resolve requested tenant
    |
    v
Check user membership and permissions
    |
    v
Create trusted TenantContext
    |
    v
Execute reactive service and repository calls
~~~

For example, a signed-in user may belong to tenant 10 and tenant 20. A request selecting tenant 20 is only accepted if current membership permits the user to operate in that tenant.

### 3.1. Do Not Trust Tenant ID from the Request Body

Avoid:

~~~java
public Mono<Order> createOrder(CreateOrderRequest request) {
    return orderRepository.save(new Order(
            request.tenantId(),
            request.customerId(),
            request.totalAmount()));
}
~~~

A client can alter tenantId in the payload to write data into another tenant.

Instead, obtain the tenant from the authenticated context:

~~~java
public Mono<Order> createOrder(CreateOrderRequest request) {
    return tenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository.save(
                    Order.newOrder(
                            tenantId,
                            request.customerId(),
                            request.totalAmount())));
}
~~~

The example assumes tenantContext only emits a tenant verified by the authorization layer. For admin endpoints that allow selecting another tenant, enforce dedicated permissions, actor auditing, and explicit validation rules.

### 3.2. Tenant Context for Background Jobs and Message Consumers

Background jobs typically have no HTTP security context. Messages may contain a tenant ID, yet consumers still need to authenticate the sender and validate the message schema.

An event may carry:

~~~json
{
  "eventId": "evt-901",
  "tenantId": 20,
  "aggregateId": 481,
  "eventType": "OrderCreated"
}
~~~

The tenant ID in a message should only be trusted when the message originates from an authenticated producer/service with proper integrity guarantees. The consumer must place the tenant into context before accessing data and avoid processing messages missing a tenant if the event is tenant-scoped.

## 4. Propagating Tenant Context in Reactive Applications

Spring Data R2DBC and Reactor should not rely on ThreadLocal to pass the tenant across reactive steps. A pipeline can switch threads or schedulers; ThreadLocal is not an appropriate context mechanism for reactive flows.

Reactor Context is propagated alongside the subscription and can be read using deferContextual.

### 4.1. Defining Tenant Context

~~~java
public final class TenantContext {

    public static final String TENANT_ID = "tenantId";

    private TenantContext() {
    }

    public static Mono<Long> currentTenantId() {
        return Mono.deferContextual(context -> {
            if (!context.hasKey(TENANT_ID)) {
                return Mono.error(new IllegalStateException(
                        "Tenant context is missing"));
            }
            return Mono.just(context.get(TENANT_ID));
        });
    }

    public static <T> Mono<T> withTenant(
            Long tenantId,
            Mono<T> publisher) {
        return publisher.contextWrite(context ->
                context.put(TENANT_ID, tenantId));
    }
}
~~~

Context usage example:

~~~java
Mono<Order> result = tenantContext.withTenant(
        20L,
        orderService.createOrder(command));
~~~

This is an illustrative class only. In real applications, the tenant ID must come from the authorization layer rather than a constant chosen arbitrarily by an endpoint.

### 4.2. Reading Context in Service/Repository Adapters

~~~java
public Mono<Order> createOrder(CreateOrderCommand command) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository.save(
                    Order.newOrder(
                            tenantId,
                            command.customerId(),
                            command.totalAmount())));
}
~~~

Do not store the current tenant in a mutable static field or singleton field that another request can overwrite. Each subscription needs its own context.

### 4.3. Reactive Security Context

If using Spring Security WebFlux, authentication can be read with ReactiveSecurityContextHolder. From the principal, extract the selected tenant and verify membership. Once authorization completes, place the verified tenant into Reactor Context so the data-access layer uses it consistently.

Do not use imperative ThreadLocal-based SecurityContextHolder inside a reactive pipeline to infer the tenant. Thread-local state may no longer be valid when the pipeline switches schedulers.

## 5. Protecting a Shared Schema with tenant_id

In a shared schema, tenant_id is part of the data scope key. Apply it consistently across all operations:

- SELECT: read only rows of the current tenant.
- INSERT: assign tenant_id from trusted context.
- UPDATE: predicate must include tenant_id.
- DELETE: predicate must include tenant_id.
- JOIN: relationships must ensure both sides belong to compatible tenants.
- Aggregates/reports: every source table must be tenant-scoped by the same rule.

### 5.1. Tenant-Scoped Repository Methods

Do not expose only find-by-ID methods if ID is not an authorization boundary:

~~~java
public interface OrderRepository
        extends ReactiveCrudRepository<Order, Long> {

    Mono<Order> findByIdAndTenantId(Long id, Long tenantId);

    Flux<Order> findAllByTenantIdAndStatus(Long tenantId, String status);
}
~~~

Service:

~~~java
public Mono<Order> findOrder(Long orderId) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> orderRepository
                    .findByIdAndTenantId(orderId, tenantId));
}
~~~

Even if IDs are globally unique, the tenant condition remains valuable to verify ownership in the database. If IDs are only unique per tenant, the primary key must be composite or repository queries must always include the tenant.

### 5.2. Do Not Let Controllers/Services Call Unscoped Repositories

A generic repository with findById(id) is convenient, yet it can become an access path bypassing tenant checks. You can:

- Use specialized repositories with tenant-scoped methods.
- Encapsulate repositories behind a tenant-aware service/adapter.
- Create a custom repository base requiring tenant context.
- Restrict repository visibility so controllers cannot invoke them directly.
- Use row-level security as an additional database defense layer.

Do not rely solely on method naming conventions. Code reviews and tests must verify that all access paths are scoped.

### 5.3. Direct Queries with @Query

For native SQL or @Query, add an explicit tenant predicate:

~~~java
@Query("""
       SELECT *
       FROM orders
       WHERE id = :orderId
         AND tenant_id = :tenantId
       """)
Mono<Order> findTenantOrder(
        @Param("orderId") Long orderId,
        @Param("tenantId") Long tenantId);
~~~

For updates/deletes:

~~~java
@Modifying
@Query("""
       UPDATE orders
       SET status = :status
       WHERE id = :orderId
         AND tenant_id = :tenantId
       """)
Mono<Integer> updateStatus(
        @Param("orderId") Long orderId,
        @Param("tenantId") Long tenantId,
        @Param("status") String status);
~~~

Do not add tenant predicates only to SELECT. An UPDATE missing a tenant condition can modify rows across multiple tenants even if the controller checked permissions.

### 5.4. Querying with R2dbcEntityTemplate

With Query and Update, include the tenant in Criteria:

~~~java
public Mono<Long> updateStatus(
        Long orderId,
        String status) {

    return TenantContext.currentTenantId()
            .flatMap(tenantId -> {
                Query query = query(
                        where("id").is(orderId)
                                .and("tenantId").is(tenantId));

                Update update = Update.update("status", status);

                return template.update(Order.class)
                        .matching(query)
                        .apply(update);
            });
}
~~~

The tenantId property maps to the tenant_id column according to entity metadata. When using DatabaseClient or raw SQL, use the column name and bind the tenant ID directly.

### 5.5. INSERT Must Derive the Tenant from the Server

~~~java
public Mono<Order> createOrder(CreateOrderCommand command) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> {
                Order order = Order.newOrder(
                        tenantId,
                        command.customerId(),
                        command.totalAmount());
                return orderRepository.save(order);
            });
}
~~~

Never let the client decide the tenant_id of a new row. If the entity accepts a tenant ID via constructor, only the authenticated/authorized layer may supply that value.

## 6. Using Keys and Constraints to Prevent Cross-Tenant Links

Query predicates restrict access, while database constraints also prevent a row in tenant A from referencing a row in tenant B.

Suppose both customers and orders have tenant_id:

~~~sql
CREATE TABLE customers (
    id BIGINT NOT NULL,
    tenant_id BIGINT NOT NULL,
    name VARCHAR(160) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT uk_customers_tenant_id_id UNIQUE (tenant_id, id)
);

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_order_customer_same_tenant
        FOREIGN KEY (tenant_id, customer_id)
        REFERENCES customers (tenant_id, id)
);
~~~

The composite unique key on customers allows the foreign key to reference both tenant_id and customer_id simultaneously. As a result, an order in tenant A cannot reference a customer in tenant B, even if application code passes the wrong ID.

### 6.1. Unique Constraints Should Include the Tenant

If emails only need to be unique within each tenant:

~~~sql
CREATE UNIQUE INDEX uk_customers_tenant_email
ON customers (tenant_id, email);
~~~

Do not create a unique index on email alone if two tenants are allowed to have the same email address.

Similarly, order numbers can be unique per tenant:

~~~sql
UNIQUE (tenant_id, order_number)
~~~

Uniqueness rules are business decisions. If email must be globally unique across the system, use a global unique constraint; if unique only within a tenant, use a composite key.

### 6.2. Indexes Should Lead with Tenant When Queries Filter by Tenant

For a common query:

~~~sql
SELECT *
FROM orders
WHERE tenant_id = :tenantId
  AND status = :status
ORDER BY created_at DESC;
~~~

A suitable index might be:

~~~sql
CREATE INDEX ix_orders_tenant_status_created
ON orders (tenant_id, status, created_at DESC);
~~~

Index column order should be based on actual queries, selectivity, and database execution plans. Do not create indexes using a rigid formula for every table.

## 7. Row-Level Security as a Database Defense Layer

For shared schemas, some databases support Row-Level Security (RLS). RLS applies policies in the database to restrict which rows a database role can read or modify.

PostgreSQL is a common example:

~~~sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY orders_tenant_policy
ON orders
USING (
    tenant_id = current_setting('app.tenant_id', true)::BIGINT
)
WITH CHECK (
    tenant_id = current_setting('app.tenant_id', true)::BIGINT
);
~~~

Meaning:

- USING restricts rows that can be read or targeted by UPDATE/DELETE.
- WITH CHECK verifies whether newly inserted or updated rows satisfy the policy.
- If app.tenant_id is not set, the expression yields NULL and no row satisfies tenant_id = NULL.

RLS protects even against SQL statements that accidentally omit a tenant predicate, though roles and context must be configured carefully.

### 7.1. Setting Transaction-Scoped Tenant Context in PostgreSQL

PostgreSQL supports set_config with is_local = true:

~~~sql
SELECT set_config('app.tenant_id', :tenantId, true);
~~~

This sets the tenant ID for the scope of the current transaction. Subsequent queries on the same transaction/connection are governed by the corresponding RLS policy.

In Spring Data R2DBC, this can be executed using DatabaseClient inside a reactive transaction:

~~~java
public <T> Mono<T> inTenantTransaction(
        Long tenantId,
        Mono<T> work) {

    Mono<Void> setTenant = databaseClient.sql(
                    "SELECT set_config('app.tenant_id', :tenantId, true)")
            .bind("tenantId", tenantId.toString())
            .fetch()
            .rowsUpdated()
            .then();

    return transactionalOperator.transactional(
            setTenant.then(work));
}
~~~

This illustrative snippet must be adapted to the return type and binding API of your DatabaseClient version. The mandatory requirement is that set_config and all RLS-protected queries use the same transaction connection. Never run set_config on one connection and query on another.

### 7.2. Securing the Database Role

A PostgreSQL table owner can normally bypass RLS unless FORCE ROW LEVEL SECURITY is enabled; superusers and roles with BYPASSRLS still bypass it. Applications should use a least-privilege database role, never a superuser.

Consider:

~~~sql
ALTER TABLE orders FORCE ROW LEVEL SECURITY;
~~~

Audit permissions of the application role, owner, migration role, and admin jobs. A migration role may need elevated privileges but should not be used for request runtime.

### 7.3. RLS Does Not Replace Authorization

RLS protects rows in the database based on the configured context. It does not verify whether a user is authorized to belong to that tenant. If the application takes a tenant ID from an untrusted request and puts it into app.tenant_id, the policy will enforce the wrong tenant requested by an attacker.

Authenticate the user and verify membership first, then set the tenant context inside the transaction.

### 7.4. Testing RLS with the Actual Runtime Role

Testing as the database owner can bypass RLS and create a false sense of security. Integration tests must connect using a role matching runtime production and verify:

- Without tenant context, no tenant-scoped rows can be read or written.
- Tenant A cannot read or modify tenant B's rows.
- INSERT with a tenant_id differing from context is rejected.
- UPDATE cannot move a row from tenant A to tenant B.
- Connections returned to the pool do not retain tenant settings for the next request.

RLS is a database-specific feature; schema-per-tenant and database-per-tenant require different protection strategies.

## 8. Routing Schemas or Databases by Tenant

With schema-per-tenant or database-per-tenant, the application must select the right ConnectionFactory/database before executing repository queries.

Spring Framework R2DBC provides ConnectionFactory routing mechanisms such as AbstractRoutingConnectionFactory in supported versions. Routing resolves a lookup key and selects a target ConnectionFactory. In reactive applications, the lookup key must be retrieved from Reactor Context instead of ThreadLocal.

### 8.1. Tenant Registry

The server needs a registry mapping verified tenants to storage configuration:

~~~java
public record TenantDatabaseConfig(
        Long tenantId,
        String connectionFactoryKey,
        String schemaName
) {
}
~~~

The registry can store tenant metadata, database key, schema, and provisioning status. Do not store plain-text passwords or secrets in objects that get logged; credentials should come from a secret manager or secure configuration mechanism.

### 8.2. Routing Key from Reactor Context

A routing ConnectionFactory can retrieve the tenant key from reactive context:

~~~java
public class TenantRoutingConnectionFactory
        extends AbstractRoutingConnectionFactory {

    @Override
    protected Mono<Object> determineCurrentLookupKey() {
        return Mono.deferContextual(context -> {
            if (!context.hasKey(TenantContext.TENANT_ID)) {
                return Mono.error(new IllegalStateException(
                        "Tenant routing key is missing"));
            }
            Long tenantId = context.get(TenantContext.TENANT_ID);
            return Mono.just(tenantId);
        });
    }
}
~~~

This is a conceptual example. Configure the target ConnectionFactory map, default target policy, and API according to the Spring Framework/Spring Data version you use. For unmapped tenants, fail closed rather than routing to a default database containing another tenant's data.

### 8.3. Transactions Must Use the Same Routing Context

When a reactive transaction begins, a connection is acquired and bound to the transaction context. The tenant must be resolved before the transaction acquires the connection. Never change the tenant midway within the same transaction.

Correct flow:

~~~text
Authenticate and authorize tenant
    |
    v
Write tenant ID into Reactor Context
    |
    v
Start reactive transaction
    |
    v
Routing ConnectionFactory selects target
    |
    v
Execute all statements on transaction connection
    |
    v
Commit or rollback
~~~

If the tenant is changed after the transaction has already acquired a connection, subsequent statements may still execute on the original tenant's connection. Treat the tenant as immutable for the duration of a transaction.

### 8.4. Database-Per-Tenant and Connection Pools

Each database can have its own ConnectionFactory/pool. The tenant registry selects the right factory. Considerations:

- Pools must not be created unboundedly for every tenant.
- Low-activity tenants can use lazy pools and idle eviction.
- Total connections across all pools must not exceed the database server limit.
- Credential rotation and connection validation.
- Safe pool opening/closing when tenants are provisioned or deprovisioned.
- Metrics per tenant/database without excessive cardinality.

If there are tens of thousands of tenants, an independent pool per tenant may be infeasible. Consider database/shard groups, cluster-level shared pools, and schema or database routing over a bounded number of connections.

### 8.5. Schema-Per-Tenant and Connection Pools

If schemas are selected via session state, connection pools can reuse connections across tenants. Therefore, the previous tenant's schema must never remain active when a connection returns to the pool.

Options:

- Use schema-qualified table names constructed from a trusted registry.
- Set schema via a transaction-local setting if supported by the database.
- Ensure connection state is reset before returning connections to the pool.
- Use separate pools/ConnectionFactory beans per schema when tenant count permits.

Never concatenate schema names directly from client input into SQL. Schema identifiers cannot be bound as value parameters; obtain them from a registry and validate/quote them per database rules.

## 9. Multiple Databases and Transaction Limits

A reactive transaction manager typically manages transactions on a single ConnectionFactory. If a business operation needs to write to two different tenant databases or a tenant database and a central database, do not assume one @Transactional creates a distributed atomic transaction across both.

For example:

~~~text
Tenant database:
  INSERT order

Central database:
  INSERT billing record
~~~

If the tenant database commits successfully while the central database fails, state can become inconsistent.

### 9.1. Do Not Treat Two ConnectionFactory Beans as One Transaction

Two repositories using two different ConnectionFactory beans do not automatically participate in the same local R2DBC transaction. R2DBC does not automatically provide distributed two-phase commit simply because a service method carries @Transactional.

If atomicity across multiple databases is required, choose a distributed transaction solution genuinely supported by the drivers, databases, and transaction manager. In many SaaS systems, saga/outbox is easier to operate than distributed transactions.

### 9.2. Saga or Outbox for Multi-Database Workflows

A flow can:

1. Write the order to the tenant database and write an outbox event in the same transaction.
2. A worker reads the outbox and dispatches the billing event.
3. The billing service writes data to the central database idempotently.
4. Billing emits a result or confirmation event.
5. If a later step fails, the saga executes retries or business compensation.

Outbox prevents losing the intent to emit an event when the tenant transaction commits. Consumers must be idempotent because messages may be redelivered.

### 9.3. Avoid Cross-Tenant Transactions Unless Necessary

A normal request should operate within a single tenant. If an administrative workflow needs to aggregate or modify data across multiple tenants, build a dedicated use case, verify admin permissions, restrict scope, audit thoroughly, and process tenants in batches.

## 10. Protecting Relationships, Joins, and Aggregate Queries

Shared schemas require special attention to join queries. Filtering by tenant only on the parent table is insufficient if relationships can reference the wrong tenant or legacy data lacks constraints.

For example:

~~~sql
SELECT o.id, o.order_number, c.name
FROM orders o
JOIN customers c
  ON c.id = o.customer_id
 AND c.tenant_id = o.tenant_id
WHERE o.tenant_id = :tenantId;
~~~

The tenant_id join condition verifies both sides belong to the same tenant. Composite foreign keys remain a stronger safeguard because they prevent bad links from being written in the first place.

### 10.1. Aggregates and Subqueries

Every source table inside a subquery must also be tenant-scoped:

~~~sql
SELECT o.id,
       (
           SELECT COUNT(*)
           FROM order_items i
           WHERE i.order_id = o.id
             AND i.tenant_id = o.tenant_id
       ) AS item_count
FROM orders o
WHERE o.tenant_id = :tenantId;
~~~

If order_items has tenant_id, the tenant condition in the subquery avoids combining mismatched data. Even when a composite foreign key guarantees order_items.order_id references the same tenant, the predicate clarifies boundaries and supports defense in depth.

### 10.2. Cross-Tenant Reporting

System-wide reports may require data from multiple tenants. That is a privileged capability and should not be implemented by dropping tenant predicates in repositories used for regular requests.

Create a separate reporting path with:

- A role/service identity with cross-tenant privileges.
- Explicit administrative authorization.
- Audit logs recording the requester and data scope.
- Field, batch size, and export restrictions.
- Dedicated database views or a warehouse if reporting workloads are heavy.

## 11. Caches Must Also Be Tenant-Scoped

If cache keys use only order ID, two tenants can collide when IDs are only unique per tenant or when data shares the same cache namespace.

Avoid:

~~~java
@Cacheable("orders")
public Mono<OrderView> findOrder(Long orderId) {
    // ...
}
~~~

Keys should include the tenant:

~~~text
orders:{tenantId}:{orderId}
~~~

Logical example:

~~~java
public Mono<OrderView> findOrder(Long orderId) {
    return TenantContext.currentTenantId()
            .flatMap(tenantId -> cache.get(
                    "orders:" + tenantId + ":" + orderId,
                    () -> orderReadRepository.findByIdAndTenantId(
                            orderId, tenantId)));
}
~~~

If using caching annotations, configure a key expression or custom key generator that includes tenant context in a reactive-safe manner. Do not rely on ThreadLocal to read the tenant inside cache keys.

During invalidation, cache events also need the tenant ID. A cache eviction event keyed only by global order ID may evict the wrong entry or miss entries if IDs are only unique within a tenant.

## 12. Files, Object Storage, and Search Indexes

Tenant boundaries do not exist solely in the database:

- File/object keys should have a tenant namespace.
- Downloads must check tenant authorization before generating signed URLs.
- Search documents should include the tenant ID and search queries must filter by tenant.
- Vector indexes, analytics stores, and data lakes also require tenant scope.
- Exports/reports must verify the tenant before reading and before delivering files.

Do not treat object paths as tenant authorization. Knowing an object key or URL does not mean a user is authorized to download the file.

Example object key:

~~~text
tenant/20/orders/481/invoice.pdf
~~~

Prefixes help organize data, but read access must still be enforced on the server or via appropriate storage policies.

## 13. Tenant Migrations and Provisioning

Multi-tenancy requires workflows for creating, upgrading, and retiring tenants.

### 13.1. Shared Schema

Migrations usually run once on the shared schema. Ensure:

- tenant_id columns are added and existing data is backfilled.
- Indexes and unique constraints have the right tenant scope.
- Composite foreign keys are created after legacy data is valid.
- Legacy queries no longer access tenant-scoped tables without predicates.
- RLS policies are enabled and tested with the runtime role.

On large tables, adding NOT NULL or indexes may require database-specific online migration strategies.

### 13.2. Schema/Database Per Tenant

Each tenant must have its schema/database at the right version:

~~~text
Tenant registry
   |
   +--> tenant A: schema version 42
   +--> tenant B: schema version 42
   +--> tenant C: schema version 41 (pending migration)
~~~

The migration runner should track per-tenant state, retry safely, and resume after job interruptions. Do not mark a tenant as upgraded if migrations only ran partially.

### 13.3. Provisioning and Deprovisioning

When creating a tenant:

1. Create the tenant record in the registry.
2. Create the schema/database or allocate a shared-schema tenant ID.
3. Provision credentials/roles according to policy.
4. Run migrations and seed initial data.
5. Verify health/version.
6. Only then mark the tenant ACTIVE.

When retiring a tenant, establish workflows for access lockout, export/retention, backups, deletion, or data hiding per policy. Do not drop a database/schema immediately upon receiving an unverified cancellation request.

## 14. Connection Security and Database Configuration

With database-per-tenant:

- Tenant credentials should be managed in a secret store.
- Do not log connection URLs containing passwords.
- Use TLS when connecting over untrusted networks.
- Grant the least-privilege role required by the application.
- Never use a migration owner/superuser for runtime queries.
- Rotate credentials and close old pools via a controlled process.
- Cap total connections across all tenants.

With shared databases:

- Do not grant the runtime role unnecessary access to administrative schemas.
- RLS policies must be enabled on all sensitive tables needing protection.
- Verify the role does not unexpectedly carry BYPASSRLS.
- Do not leave any debug/export endpoint bypassing tenant scope.

## 15. Common Mistakes in Multi-Tenant Design

| Symptom | Possible Cause | Fix |
| --- | --- | --- |
| Tenant A user reads tenant B's order | Query filters only by ID | Add tenant predicate and test cross-tenant access |
| UPDATE modifies multiple tenants | Missing tenant_id in WHERE | Mandate tenant predicates on all DML |
| Order references another tenant's customer | Foreign key checks only customer_id | Composite foreign key including tenant_id |
| One tenant's email blocks another tenant | Global unique constraint violates business rules or lacks tenant scope | Scope unique index by tenant |
| Request runs on the wrong schema | Tenant context not propagated or connection state leaked | Route from Reactor Context and reset state |
| Tenant A affects tenant B via cache | Cache key lacks tenant ID | Include tenant in keys and invalidations |
| Message consumer writes to wrong tenant | Message lacks tenant context or trusts unverified payload | Authenticate producer and build tenant context |
| RLS does not protect as expected | Runtime role bypasses RLS or context unset | Verify role, FORCE RLS, and transaction setting |
| Large tenant slows down the whole system | Shared resources lack quotas/isolation | Rate limiting, workload controls, or isolate tenant |
| Pools grow unboundedly | Every tenant creates a long-lived pool | Pool lifecycle, idle eviction, and total cap |
| Transaction uses wrong database | Tenant routing happens after connection binding | Resolve tenant before transaction |
| Tenant migrations drift out of sync | No per-schema/database version tracking | Tenant migration registry and retryable migrations |
| Cross-tenant report leaks data | Regular repositories drop filters | Dedicated reporting path and admin permission audits |

## 16. Testing Tenant Boundaries

Multi-tenant tests must prove data cannot cross boundaries, even when callers tamper with IDs or invoke services directly.

### 16.1. Cross-Tenant SELECT Test

Setup:

- Customer 101 belongs to tenant 10.
- Customer 202 belongs to tenant 20.

In tenant 10 context:

- Finding customer 101 succeeds.
- Finding customer 202 returns empty or a not-found error per API contract.

Do not return information revealing that the row exists in another tenant if that could leak data.

### 16.2. INSERT Test

Call the order creation API in tenant 10 while sending tenantId = 20 in the request body. Verify:

- The server ignores or rejects the client-supplied tenantId field.
- The new row has tenant_id = 10 from the authenticated context.
- No data is written to tenant 20.

### 16.3. UPDATE and DELETE Tests

In tenant 10 context, attempt to update/delete tenant 20's order using a valid ID. Verify the affected row count is 0 or the API returns not-found/unauthorized per policy.

Test across all access paths:

- Repository query methods.
- @Query and @Modifying.
- R2dbcEntityTemplate.
- DatabaseClient.
- Bulk jobs.

### 16.4. Cross-Tenant Association Test

Attempt to create a tenant 10 order with a customer ID belonging to tenant 20. The composite foreign key must reject the operation even if a service has a bug.

### 16.5. Reactive Context Isolation Test

Run two concurrent requests:

- Request A carries tenant 10.
- Request B carries tenant 20.

Use asynchronous schedulers and publishers to verify tenant context does not mix across the two subscriptions. Do not test only sequentially on a single thread.

### 16.6. Routing and Connection Pool Tests

With schema/database routing:

- Tenant A routes to target A.
- Tenant B routes to target B.
- Nonexistent tenants are rejected without falling back to a default tenant.
- Connections returned to the pool do not retain old schema/tenant settings.
- Tenant context is resolved before the transaction acquires a connection.
- A transaction does not switch tenants between statements.

### 16.7. RLS Test

Run tests with a runtime role matching production, not owner/superuser. Verify a query missing a tenant predicate still cannot read another tenant's data when RLS is expected as a safeguard.

## 17. Example of a Tenant-Aware Service

Shared-schema example with tenant_id on the entity:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("tenant_id")
    private Long tenantId;

    @Column("customer_id")
    private Long customerId;

    private String status;
    private BigDecimal totalAmount;

    public static Order newOrder(
            Long tenantId,
            Long customerId,
            BigDecimal totalAmount) {
        Order order = new Order();
        order.tenantId = tenantId;
        order.customerId = customerId;
        order.totalAmount = totalAmount;
        order.status = "NEW";
        return order;
    }
}
~~~

Repository:

~~~java
public interface TenantOrderRepository
        extends ReactiveCrudRepository<Order, Long> {

    Mono<Order> findByIdAndTenantId(Long id, Long tenantId);

    Flux<Order> findAllByTenantIdOrderByIdDesc(Long tenantId);
}
~~~

Service:

~~~java
@Service
public class OrderService {

    private final TenantOrderRepository repository;
    private final TenantContextService tenantContext;

    public OrderService(
            TenantOrderRepository repository,
            TenantContextService tenantContext) {
        this.repository = repository;
        this.tenantContext = tenantContext;
    }

    public Mono<Order> create(CreateOrderCommand command) {
        return tenantContext.currentTenantId()
                .flatMap(tenantId -> repository.save(
                        Order.newOrder(
                                tenantId,
                                command.customerId(),
                                command.totalAmount())));
    }

    public Mono<Order> find(Long orderId) {
        return tenantContext.currentTenantId()
                .flatMap(tenantId -> repository
                        .findByIdAndTenantId(orderId, tenantId));
    }
}
~~~

This example illustrates tenant scoping in the service and repository. In real applications, also ensure customerId belongs to the current tenant, preferably via a composite foreign key and/or a query verifying tenant match before creating the order.

## 18. Multi-Tenant Design Workflow

1. Define what a tenant represents—an organization, workspace, or business scope.
2. Determine whether users can belong to one or multiple tenants and how membership is checked.
3. Choose shared schema, schema per tenant, or database per tenant based on isolation and operational requirements.
4. Build tenant context from the authenticated principal and propagate it via Reactor Context.
5. For shared schemas, enforce tenant predicates in SELECT, INSERT, UPDATE, DELETE, and joins.
6. Design composite unique keys/foreign keys to prevent cross-tenant links.
7. Consider RLS as an additional safeguard if supported by the database.
8. For schema/database routing, resolve the tenant before the transaction acquires a connection and fail closed when no mapping exists.
9. Include tenant ID in cache keys, messages, object storage, and search queries.
10. Design migrations, provisioning, credentials, pools, and deprovisioning for the tenant lifecycle.
11. Create a dedicated reporting/admin path for cross-tenant operations.
12. Write concurrent integration tests for two tenants and verify every read/write path.

## 20. Conclusion

Secure multi-tenant design requires maintaining data boundaries from authentication down to the database, cache, and messages. Shared schemas require tenant_id in all read/write operations, composite constraints to prevent cross-tenant associations, and optionally RLS. Schema per tenant or database per tenant requires routing based on reactive tenant context, connection pool management, and lifecycle-aware tenant migrations.

In Spring Data R2DBC, never rely on ThreadLocal to propagate tenants. Extract the tenant from an authenticated principal, verify membership, place it into Reactor Context, and resolve it before the transaction acquires a connection. With direct SQL, custom repositories, and bulk updates, always verify tenant scope; with database routing, never let an unknown tenant fall back to a default database. Caches, events, object storage, and reports must also enforce their own tenant boundaries.

Finally, use database constraints and integration tests as safeguards independent of application code. A sound design must prove that requests from tenant A cannot read, modify, delete, or link tenant B's data, even when a query omits a condition or two tenants execute concurrently.
