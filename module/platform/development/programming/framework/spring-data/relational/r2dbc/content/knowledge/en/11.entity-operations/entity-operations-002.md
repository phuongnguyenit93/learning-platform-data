# Inserting Entities and Retrieving Post-Save Results

## 1. Inserting Entities in Spring Data R2DBC

Creating new data typically starts with a Java object constructed by the business layer. The application needs to convert the object's properties into values writable to the database, execute an INSERT statement, receive the result from the R2DBC driver, and return the entity's post-save state.

In Spring Data R2DBC, two APIs are commonly used:

- **ReactiveCrudRepository.save(entity):** The familiar repository API. Spring Data determines whether the entity is new or existing to choose between insert and update.
- **R2dbcEntityTemplate.insert(...).using(entity):** The template API that explicitly expresses an insert operation, suitable when you want to mandate creating a new record.

Both APIs return reactive publishers. The emitted result is not always the exact same input object. The database may generate primary keys, versions, or default values; Spring Data may create a new instance populated with that metadata and emit it through the returned publisher.

Therefore, when inserting, you need to understand three things: when Spring Data decides to insert, what values the database returns, and how to use the saved entity once the publisher completes.

## 2. Insert Flow from Entity to Database

Suppose an application needs to create a new customer in PostgreSQL. The Java entity has `id`, `name`, and `email` fields; the database auto-generates the `id` value.

~~~text
Service creates a new entity
        |
        v
Repository.save(entity)
or R2dbcEntityTemplate.insert(...)
        |
        v
MappingR2dbcConverter
        |
        v
Generate INSERT and bind values
        |
        v
R2DBC Driver
        |
        v
PostgreSQL executes INSERT
        |
        v
Database generates ID / default / version
        |
        v
Driver returns supported results
        |
        v
Spring Data maps results
        |
        v
Mono<Saved Entity>
~~~

Key steps:

1. The business layer creates an entity with input values.
2. Spring Data reads mapping metadata such as `@Table`, `@Id`, and `@Column`.
3. The mapping converter transforms the required properties into store values.
4. Spring Data constructs the INSERT statement and binds parameters via the R2DBC driver.
5. The database checks constraints, writes the row, and may generate values such as identity or version.
6. The driver and dialect supply the returned data Spring Data needs to complete the entity.
7. The publisher emits the saved entity on success or emits an error if the operation fails.

Retrieving auto-generated IDs depends on the database, dialect, and driver support for returning generated values. For dialects supported by Spring Data, the mapping infrastructure handles most of these details. When using specialized databases or drivers, verify generated-key retrieval and actual runtime behavior.

## 3. Declaring Entities and Schemas with Auto-Generated Primary Keys

### 3.1. Entity with @Id

Example using a Java record:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
~~~

`@Table("customers")` maps the record to the `customers` table. `@Id` marks the identifier property. `Long` is a nullable type, suitable when a new entity does not yet have an ID and the database will generate it upon insert.

### 3.2. PostgreSQL Schema

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE
);
~~~

The `id` column is automatically populated by PostgreSQL when INSERT omits a value for it. The `name` and `email` columns are required; `email` also has a unique constraint.

When a new entity has `id = null`, Spring Data can recognize it as a new entity and perform an insert. The database generates the ID, and Spring Data populates that ID into the returned result.

Avoid setting dummy IDs like `0L` to represent a new entity. Use a nullable wrapper type like `Long` and leave the ID unset until the database creates it. With primitive ID types, default values can participate in newness detection rules, but wrapper types generally express intent more clearly.

## 4. Creating Records with ReactiveCrudRepository.save()

### 4.1. Declaring the Repository

~~~java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
~~~

`ReactiveCrudRepository<Customer, Long>` provides reactive CRUD operations. The `save(S entity)` method returns `Mono<S>`, a publisher that emits the entity once the operation completes.

### 4.2. Calling save with a New Entity

~~~java
Customer input = new Customer(
        null,
        "An Nguyen",
        "an@example.test"
);

Mono<Customer> savedCustomer = customerRepository.save(input);
~~~

The snippet above creates a publisher describing the save operation. Because Reactor uses a lazy execution model, assigning the result to `savedCustomer` does not mean the INSERT statement has already run. The operation executes when the publisher gets a subscriber—for example, when WebFlux processes a response or a test runs StepVerifier.

You can use the entity emitted after saving:

~~~java
return customerRepository.save(input)
        .doOnNext(saved ->
                log.info("Created customer with id={}", saved.id()));
~~~

Here, the log only executes when the publisher emits the saved entity. If the insert fails, the publisher emits an error and `doOnNext` is not invoked.

### 4.3. Always Use the Returned Value

For mutable entities, Spring Data may populate the ID or version onto the instance. For immutable entities such as Java records, Spring Data cannot reassign properties. Instead, it creates a new instance containing the database-generated values and emits that instance.

Therefore, write:

~~~java
return customerRepository.save(input)
        .flatMap(saved -> {
            log.info("Generated id: {}", saved.id());
            return customerRepository.findById(saved.id());
        });
~~~

Do not assume `input.id()` has an ID right after calling `save(input)`. With records, the input object remains unchanged; the ID must be read from the object emitted by the publisher.

This principle is also helpful for immutable entities with constructors or withers. Treat the result of `save` as the version finalized by the persistence layer and use it in subsequent steps.

## 5. Using R2dbcEntityTemplate.insert() for Explicit Inserts

Repository `save` chooses insert or update based on the entity's new/existing state. If business logic wants to explicitly state that the operation must create a new record, you can use `R2dbcEntityTemplate`.

~~~java
import org.springframework.data.r2dbc.core.R2dbcEntityTemplate;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class CustomerService {

    private final R2dbcEntityTemplate template;

    public CustomerService(R2dbcEntityTemplate template) {
        this.template = template;
    }

    public Mono<Customer> insert(Customer customer) {
        return template.insert(Customer.class).using(customer);
    }
}
~~~

The fluent API `insert(Customer.class).using(customer)` explicitly specifies the entity type and object to insert. The returned publisher is `Mono<Customer>`, allowing you to receive the entity after Spring Data completes the operation.

Use explicit insert in situations such as:

- An operation is strictly allowed to create a new record only.
- Avoiding ambiguity between insert and update when an entity has a pre-assigned ID.
- Preferring the template API over a repository.
- Coordinating insert operations with specialized queries or updates at the persistence layer.

If the primary key already exists, the database typically rejects the insert due to a primary key or unique constraint violation. Insert does not automatically fall back to an update and is not an upsert statement.

## 6. Distinguishing save, insert, and upsert

These terms carry distinct meanings:

| API / Concept | How It Decides | Meaning |
|---|---|---|
| `ReactiveCrudRepository.save(entity)` | Based on whether the entity is detected as new or existing | Inserts a new entity or updates an existing one |
| `R2dbcEntityTemplate.insert(...).using(entity)` | Always requests an insert operation | Creates a new record; errors on constraint violation |
| PostgreSQL SQL `INSERT ... ON CONFLICT ...` | Based on the conflict target specified in SQL | Inserts or executes an action on conflict |
| Database SQL `MERGE` or upsert | Based on database-specific syntax and conditions | Combines insert/update according to explicit rules |

`save` is not synonymous with SQL upsert. Spring Data determines whether the entity is new or existing before executing the operation. It does not guarantee atomic "if the key exists, update; otherwise insert" semantics in a single statement.

If business logic requires an upsert on a unique key, use a SQL statement or database API that supports upsert for your database engine. In PostgreSQL, you can use `INSERT ... ON CONFLICT` via `DatabaseClient`, while explicitly designing result handling and mapping.

PostgreSQL SQL example:

~~~sql
INSERT INTO customers (name, email)
VALUES (:name, :email)
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name
RETURNING id, name, email;
~~~

This syntax is specific to PostgreSQL. Do not assume it can be copied verbatim to every database. Using upsert also requires clearly defining which fields may be overwritten to avoid losing newer updates or data outside the current request's ownership.

## 7. How Spring Data Detects a New Entity

When calling `save`, Spring Data needs to know whether to insert or update. This rule is known as **entity state detection** (or new/existing state detection).

### 7.1. Based on ID

For entities without a version property, Spring Data typically checks the ID:

- ID is `null`: the entity is treated as new, performing an insert.
- ID has a value: the entity is treated as existing, performing an update.

Example:

~~~java
Customer newCustomer = new Customer(
        null,
        "An Nguyen",
        "an@example.test"
);

customerRepository.save(newCustomer); // new entity -> insert
~~~

When the ID is already assigned:

~~~java
Customer existingCustomer = new Customer(
        42L,
        "An Nguyen",
        "an@example.test"
);

customerRepository.save(existingCustomer); // existing state -> update
~~~

This rule is straightforward when IDs are database-generated and new entities do not yet have an ID.

### 7.2. Using @Version for Newness Detection and Optimistic Locking

If an entity has a property annotated with `@Version`, Spring Data can use the version to determine state before examining the ID. With a wrapper-typed version property, `null` indicates a new entity; after insert, the version is initialized. On update, the version is checked and incremented under optimistic locking.

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        @Version Long version,
        String name,
        String email
) {}
~~~

This approach is useful when IDs are assigned on the application side—such as UUIDs—yet the entity still needs to be recognized as new. The schema must have a corresponding version column.

Do not add `@Version` merely to force an insert if the application has no need for optimistic locking. Version is part of concurrency control and must be managed consistently.

### 7.3. Using Persistable for Custom Newness Rules

When IDs are manually assigned and no version is used, you can implement `Persistable<ID>` to supply custom new/existing state via `isNew()`.

~~~java
import org.springframework.data.domain.Persistable;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_customers")
public class ExternalCustomer implements Persistable<String> {

    @Id
    private String id;

    @Transient
    private boolean newEntity = true;

    @Override
    public String getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markPersisted() {
        this.newEntity = false;
    }
}
~~~

This illustrates the mechanism. In real applications, `newEntity` must be flipped to false after a successful insert, either via lifecycle callbacks supported by your Spring Data version or by managing state in the domain/persistence layer. If the flag stays true, a subsequent save call may attempt another insert.

For immutable entities, maintaining newness state may require a different design, such as a version property or an appropriate factory/state object. Avoid using an arbitrary mutable flag without clearly defining when it gets updated.

## 8. Receiving Database-Generated IDs and Values

### 8.1. Database-Generated Identity

With an identity column:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL UNIQUE
);
~~~

A new entity can set its ID to null:

~~~java
Customer input = new Customer(null, "An Nguyen", "an@example.test");
~~~

After inserting, the database generates the ID. When the driver/dialect supports returning generated values and mapping is configured properly, Spring Data populates the ID into the resulting entity.

~~~java
return customerRepository.save(input)
        .map(saved -> {
            Long generatedId = saved.id();
            return saved;
        });
~~~

Do not run a separate SELECT statement to guess the newly created ID or use `MAX(id)`. That approach is unsafe under concurrent insert requests. Always obtain generated keys from the insert result managed by the driver and Spring Data.

### 8.2. Columns with Default Values

Databases can assign default values automatically:

~~~sql
CREATE TABLE audit_events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_type VARCHAR(80) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

If the application omits `created_at`, the database can apply the default. However, whether the default value appears in the returned entity depends on how Spring Data and the driver retrieve generated values. Do not assume every default column is automatically returned across all dialects.

If you need to be certain the value is present in the resulting object, verify the returning/generated-values capabilities of your database and driver. With custom SQL, PostgreSQL can use `RETURNING` to request specific columns back:

~~~sql
INSERT INTO audit_events (event_type)
VALUES (:eventType)
RETURNING id, event_type, created_at;
~~~

This is PostgreSQL syntax. When using `DatabaseClient`, map the returned columns into an object explicitly.

### 8.3. Version Values

If an entity uses `@Version`, Spring Data manages the version during insert/update. A new entity typically starts with a null version (for wrapper types); after insert, the version is initialized according to Spring Data's rules. On update, the version is used to detect data modified by another transaction.

Always use the version from the returned entity for further processing. With immutable entities, the input object may still hold a null version while the result object holds the new version.

## 9. Mutable and Immutable Entities After Insert

### 9.1. Mutable Entities

A standard entity class may have a setter for the ID:

~~~java
@Table("customers")
public class MutableCustomer {

    @Id
    private Long id;

    private String name;

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getName() {
        return name;
    }
}
~~~

The mapping infrastructure may populate the generated ID onto the entity according to the mapping mechanism. Even so, application code should still use the entity emitted by the publisher since that represents the state finalized by the persistence layer.

### 9.2. Immutable Entities

With records:

~~~java
@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
~~~

No setter can be called to update the ID. Spring Data uses its constructor/property population strategy to create an instance holding the updated values. Hence:

~~~java
return customerRepository.save(
        new Customer(null, "An Nguyen", "an@example.test")
).flatMap(saved -> {
    // Use saved.id(), not the ID from the input record
    return customerRepository.findById(saved.id());
});
~~~

This is a key reason never to ignore the return value of `save` or `insert`.

### 9.3. Do Not Assume the Input Object Is Always Updated

Some mutable entities may have their ID updated on the same instance; immutable entities require a new instance. The exact behavior depends on the entity model and mapping strategy. The safest code uses the value emitted by the publisher rather than depending on whether the input object is mutated.

## 10. Handling Insert Results in a Reactive Pipeline

### 10.1. Using flatMap for Subsequent Steps

If creating a customer requires creating a related record afterward, extract the ID from the saved entity:

~~~java
public Mono<CustomerProfile> createCustomer(CreateCustomerRequest request) {
    Customer customer = new Customer(
            null,
            request.name(),
            request.email()
    );

    return customerRepository.save(customer)
            .flatMap(savedCustomer -> {
                CustomerProfile profile = new CustomerProfile(
                        null,
                        savedCustomer.id(),
                        request.displayName()
                );

                return profileRepository.save(profile);
            });
}
~~~

The profile publisher is created only after the customer has been inserted and the ID is available. This is how dependent operations are chained in Reactor without calling `block()`.

If both operations must succeed or roll back together, configure a reactive transaction at the service layer and ensure the entire publisher is returned within the same pipeline.

### 10.2. Using map for Synchronous Result Transformation

If you only need to transform the saved entity into a response DTO, use `map`:

~~~java
return customerRepository.save(customer)
        .map(saved -> new CustomerResponse(
                saved.id(),
                saved.name(),
                saved.email()
        ));
~~~

`map` is suitable for synchronous transformations that do not return another publisher. If the next step needs to call another repository or reactive service, use `flatMap`.

### 10.3. Do Not Call block or subscribe Inside Services

Avoid writing:

~~~java
Customer saved = customerRepository.save(customer).block();
~~~

or:

~~~java
customerRepository.save(customer).subscribe();
~~~

`block()` blocks the thread waiting for the result and can stall event-loop threads in WebFlux. `subscribe()` creates an independent subscription, causing the caller to lose lifecycle, error, cancellation, and transaction management.

Return `Mono<Customer>` so the framework or caller registers the subscription. In WebFlux, controllers can return the publisher directly for Spring to handle.

## 11. Building a POST API That Returns the Saved Entity

Service example:

~~~java
@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Mono<Customer> create(String name, String email) {
        Customer customer = new Customer(null, name, email);
        return repository.save(customer);
    }
}
~~~

WebFlux controller:

~~~java
@RestController
@RequestMapping("/customers")
public class CustomerController {

    private final CustomerService service;

    public CustomerController(CustomerService service) {
        this.service = service;
    }

    @PostMapping
    public Mono<ResponseEntity<Customer>> create(
            @RequestBody CreateCustomerRequest request) {

        return service.create(request.name(), request.email())
                .map(saved -> ResponseEntity
                        .created(URI.create("/customers/" + saved.id()))
                        .body(saved));
    }
}
~~~

A successful response can include HTTP 201 Created, a Location header pointing to the newly created resource, and a body containing the database-generated ID. Returning the entity directly is suitable only for simple APIs; real-world applications typically use response DTOs to control public exposure and avoid leaking internal fields or sensitive data.

## 12. Inserting Multiple Entities with saveAll

Reactive repositories provide `saveAll` to save a collection of entities:

~~~java
Flux<Customer> inputs = Flux.just(
        new Customer(null, "An Nguyen", "an@example.test"),
        new Customer(null, "Binh Tran", "binh@example.test")
);

Flux<Customer> savedCustomers = customerRepository.saveAll(inputs);
~~~

The result is a `Flux<Customer>` emitting the saved entities. If the database generates IDs, read the ID from each emitted element.

Do not assume `saveAll` always produces a single multi-row SQL INSERT or a single batch. Execution depends on the repository implementation, driver, and Spring Data version. If bulk insert performance is required, benchmark it and consider batch APIs or database-specific SQL.

If one item violates a unique constraint, the publisher may emit an error. Determine whether the business requirement expects all-or-nothing atomicity or partial processing. Transaction boundaries and how the publisher is consumed determine the rollback scope; do not assume every `saveAll` automatically shares a single transaction.

## 13. Transactions for Multi-Step Inserts

Suppose a business flow creates an Order and then its OrderLines. The Order's ID is only available after the root insert succeeds. Steps can be chained with `flatMap`:

~~~java
@Transactional
public Mono<Order> createOrder(CreateOrderRequest request) {
    Order order = new Order(null, request.customerId(), "NEW");

    return orderRepository.save(order)
            .flatMap(savedOrder -> {
                List<OrderLine> lines = request.lines().stream()
                        .map(line -> new OrderLine(
                                null,
                                savedOrder.id(),
                                line.sku(),
                                line.quantity()
                        ))
                        .toList();

                return orderLineRepository.saveAll(lines)
                        .then(Mono.just(savedOrder));
            });
}
~~~

This example illustrates saving OrderLine through a separate repository; if order lines belong to an aggregate in Spring Data Relational, design the mapping and save the aggregate root according to the appropriate aggregate model. The key point here is obtaining the generated ID from `savedOrder` to construct the dependent records.

With reactive transactions, the transactional method must return the publisher so Spring can manage the subscription and transaction context. Do not subscribe manually inside it. If the second operation fails and the publishers participate in the same transaction, the transaction manager can roll back the earlier operation.

If write steps span multiple databases or multiple transaction managers, a single `@Transactional` does not automatically create a distributed transaction. In that case, design an appropriate consistency mechanism such as the outbox pattern or a saga depending on the architecture.

## 14. Handling Errors During Insert

Inserts can fail for many reasons:

- Primary key or unique constraint violation.
- Missing value for a NOT NULL column.
- Incompatible data type or value exceeding length limits.
- Foreign key referencing a non-existent record.
- Database connection loss or timeout.
- Driver not supporting the expected binding or generated value type.

These failures propagate as error signals in the reactive publisher. Persistence-layer exceptions can be translated into business exceptions or API errors at the service/web boundary.

Illustrative example of mapping a unique constraint error:

~~~java
return customerRepository.save(customer)
        .onErrorMap(
                DuplicateKeyException.class,
                ex -> new EmailAlreadyRegisteredException(customer.email())
        );
~~~

Exception names and how drivers map constraint violations can differ by database/driver. Inspect the root cause or SQL state to classify accurately. Avoid catching every exception and returning an "email already exists" message, as network or schema errors would be masked.

If a client retries a request after a timeout, consider idempotency. The first insert might have succeeded on the database while the response was lost in transit. A retried request could hit a unique constraint. For critical create operations, use an idempotency key or a business key with a unique constraint to look up the previously created result.

## 15. Inserting with Application-Assigned IDs

Not all systems use auto-incrementing IDs. Some domains generate a UUID or identifier prior to writing.

Example:

~~~java
UUID id = UUID.randomUUID();

Customer customer = new Customer(
        id,
        "An Nguyen",
        "an@example.test"
);
~~~

If the entity lacks a version property and its ID already has a value, Spring Data may treat the entity as existing and choose update when `save` is called. Therefore, do not simply assign an ID and assume `save` will definitely execute an insert.

There are several options:

- Use `R2dbcEntityTemplate.insert(...).using(entity)` to request an insert explicitly.
- Use a wrapper `@Version` property if it aligns with optimistic locking and newness detection needs.
- Implement `Persistable<ID>` to provide custom `isNew()` rules while properly managing when the entity transitions to a persisted state.

Example using the template:

~~~java
UUID id = UUID.randomUUID();
Customer customer = new Customer(id, "An Nguyen", "an@example.test");

return template.insert(Customer.class).using(customer);
~~~

This syntax requests an insert even though the ID is already assigned. The database still enforces primary key and unique constraints. If the ID already exists, the insert fails unless custom upsert SQL is designed.

## 16. Considerations for IDs and Data Types

### 16.1. ID Type Must Match the Schema

If the ID column is BIGINT, the entity typically uses `Long`. If the database uses UUID, the entity can use `UUID` if supported by the driver/dialect. Avoid unnecessarily converting IDs to String, which can cause mapping errors or lose native type support.

### 16.2. Do Not Use Temporary ID Values as Arbitrary Newness Signals

Some applications use ID 0 or negative numbers to mark a new entity. This can interact unexpectedly with state detection rules. Use null for database-generated IDs, or explicit `Persistable`/version rules for assigned IDs.

### 16.3. Generated IDs Do Not Represent Business Ordering

Identity IDs are primarily for identifying and linking records. Do not infer creation time, business sequence, or request ordering from IDs alone. If business rules require timestamps or separate sequences, store dedicated fields and use an intentional generation mechanism.

## 17. Testing Inserts and Post-Save Results

### 17.1. Testing Repositories with StepVerifier

~~~java
@Test
void shouldInsertCustomerAndReturnGeneratedId() {
    Customer input = new Customer(
            null,
            "An Nguyen",
            "an@example.test"
    );

    StepVerifier.create(customerRepository.save(input))
            .assertNext(saved -> {
                assertThat(saved.id()).isNotNull();
                assertThat(saved.name()).isEqualTo("An Nguyen");
            })
            .verifyComplete();
}
~~~

This test subscribes to the publisher and asserts that the returned entity has an ID. Use a real test database or Testcontainers to verify generated keys and driver behavior.

### 17.2. Verifying That Data Actually Persisted

You can read the record back using the returned ID:

~~~java
StepVerifier.create(
        customerRepository.save(input)
                .flatMap(saved -> customerRepository.findById(saved.id()))
)
.assertNext(found -> {
    assertThat(found.email()).isEqualTo("an@example.test");
})
.verifyComplete();
~~~

Reading back confirms both the insert and the read-side mapping. Checking only that the publisher emits an entity does not verify that every column was written accurately.

### 17.3. Testing Constraint Violations

Include tests for scenarios such as:

- Duplicate email violating the unique constraint.
- Missing NOT NULL fields.
- Non-existent foreign key.
- Assigned ID already present in the database.
- Values exceeding length limits or of invalid types.
- Multi-step transactional insert rolling back when a subsequent step fails.

Mocking repositories is useful for service unit tests, but it does not replace integration tests because mocks do not validate SQL, generated keys, constraints, or the driver.

## 18. Checklist When Creating New Entities

When implementing insert functionality, verify that:

1. The entity has `@Table` and `@Id` matching the schema.
2. The ID type is compatible with the database column.
3. The ID generation strategy is clearly database-generated or application-assigned.
4. New entities are recognized as new by Spring Data via ID, version, or `Persistable`.
5. `save` is chosen when letting the repository decide insert/update; template `insert` is chosen when an explicit insert is required.
6. The publisher is returned to the caller and actually consumed by a subscriber.
7. The entity emitted by the publisher is used to read the generated ID, version, and updated values.
8. `save` is not assumed to be an upsert.
9. Unique, foreign key, and NOT NULL constraints are handled as error signals.
10. Reactive transactions are used when multiple operations require atomicity.
11. Tests run against an actual database/driver to validate generated values and mapping.

## 19. Conclusion

Spring Data R2DBC supports inserting entities reactively via `ReactiveCrudRepository.save` or explicit `R2dbcEntityTemplate` insert operations. Repository `save` relies on new/existing state detection to pick insert or update; template insert always expresses creating a new record. Neither operation is synonymous with SQL upsert.

When the database generates IDs, versions, or default values, read that information from the entity emitted by the publisher. This is especially crucial for immutable entities like records, where the input object is not modified. Chain subsequent steps with `map` or `flatMap`, keep reactive transactions intact across the pipeline when needed, and let database errors propagate cleanly through the reactive pipeline.

Understanding state detection, generated values, and post-save results makes insert operations safer, more consistent, and easier to test in Spring Data R2DBC applications.
