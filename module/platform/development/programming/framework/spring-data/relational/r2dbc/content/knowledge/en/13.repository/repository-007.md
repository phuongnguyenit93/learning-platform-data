# Combining Conditions, Static Sorting, and Limits from Method Names

Spring Data R2DBC lets you declare queries directly in repository method names. Spring Data parses the method name, recognizes entity properties and keywords such as `And`, `Or`, `GreaterThan`, `OrderBy`, `First`, or `Top`, and then builds SQL suited to the entity mapping and database dialect.

This approach works well for queries with stable structure: filtering by multiple conditions, always sorting in the same order, and returning at most a fixed number of results. As a result, the repository clearly expresses query intent right in the Java contract, and the application avoids manually concatenating SQL strings.

## 1. Query Method Name Structure

A derived query name typically has the following parts:

```text
find[Distinct][TopN|FirstN]By<Predicate>OrderBy<Property><Asc|Desc>
```

Meaningful components:

- `find`, `read`, `get`, `query`, or `search` describes the read operation.
- `Distinct` requests removing duplicate rows according to query semantics.
- `TopN` or `FirstN` caps the maximum number of results.
- `By` starts the filtering predicate.
- Predicate contains property names and comparison keywords, optionally combined with `And` or `Or`.
- `OrderBy` starts the static sorting section.
- `Asc` and `Desc` specify the sort direction for each property.

For example:

```java
Flux<Product> findTop20ByStatusAndCategoryOrderByCreatedAtDescIdDesc(
    String status,
    String category
);
```

The method name expresses a query finding products by `status` and `category`, sorted by `createdAt` descending then `id` descending, returning at most 20 products.

Not every word in the method name is a SQL column name. Spring Data interprets them as properties on the entity class, then uses mapping metadata to resolve the corresponding column names and data types.

## 2. Declaring the Reactive Repository

Suppose we have a `Product` entity:

```java
import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("product")
public class Product {

    @Id
    private Long id;

    private String name;

    private String status;

    private String category;

    private BigDecimal price;

    @Column("created_at")
    private Instant createdAt;

    // Constructors, getters, and setters omitted.
}
```

Repository extending `ReactiveCrudRepository`:

```java
import java.math.BigDecimal;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface ProductRepository
        extends ReactiveCrudRepository<Product, Long> {

    Flux<Product> findByStatusAndCategory(
        String status,
        String category
    );

    Flux<Product> findByPriceGreaterThanEqual(BigDecimal minPrice);

    Flux<Product> findByStatusOrderByCreatedAtDescIdDesc(String status);

    Flux<Product> findTop20ByStatusOrderByCreatedAtDescIdDesc(String status);

    Mono<Product> findFirstByNameOrderByCreatedAtDescIdDesc(String name);
}
```

Spring Data generates implementations for the query methods when initializing the repository. The application only declares the method signatures; no method bodies are needed to run the SQL.

## 3. Combining Conditions with And and Or

`And` and `Or` allow describing multiple conditions directly in the method name.

### 3.1. Combining with AND

Example finding products with status `ACTIVE`, belonging to a specified category, and priced at or above a minimum amount:

```java
Flux<Product> findByStatusAndCategoryAndPriceGreaterThanEqual(
    String status,
    String category,
    BigDecimal minPrice
);
```

Parameters are bound to conditions in the order they appear in the predicate:

| Method name segment | Parameter | Meaning |
|---|---|---|
| `Status` | `status` | Status equals the supplied value |
| `AndCategory` | `category` | Must also belong to the supplied category |
| `AndPriceGreaterThanEqual` | `minPrice` | Price is greater than or equal to the minimum |

Logically, the query corresponds to:

```sql
SELECT ...
FROM product
WHERE status = :status
  AND category = :category
  AND price >= :minPrice;
```

This is illustrative SQL to explain semantics. Actual SQL is generated by Spring Data and the driver's dialect, and may use different bind markers.

### 3.2. Combining with OR

Example finding products with status `ACTIVE` or belonging to category `FEATURED`:

```java
Flux<Product> findByStatusOrCategory(
    String status,
    String category
);
```

The condition means:

```sql
WHERE status = :status OR category = :category
```

`Or` broadens the result set: satisfying either branch allows a row to be returned.

### 3.3. Combining Multiple AND/OR Branches

A method name can combine both keywords, though long expressions become hard to read and easy to misinterpret. For example:

```java
Flux<Product> findByStatusAndCategoryOrFeaturedTrue(
    String status,
    String category
);
```

When you need explicit parentheses—for example `(status = ? AND category = ?) OR featured = true`—verify how the parser groups predicates in your Spring Data version. Do not embed a critical business expression inside an overly long method name without an integration test.

If logic needs multiple nested groups or complex parentheses, `@Query` with explicit SQL or `R2dbcEntityTemplate` with `Criteria` is usually easier to control.

## 4. Commonly Used Comparison Keywords

Spring Data supports many keywords to express conditions on entity properties. Common keywords include:

| Keyword | Meaning | Example |
|---|---|---|
| `Is`, `Equals` | Equal | `findByStatus(String status)` |
| `Not` | Not equal | `findByStatusNot(String status)` |
| `GreaterThan` | Greater than | `findByPriceGreaterThan(BigDecimal price)` |
| `GreaterThanEqual` | Greater than or equal | `findByPriceGreaterThanEqual(BigDecimal price)` |
| `LessThan` | Less than | `findByPriceLessThan(BigDecimal price)` |
| `LessThanEqual` | Less than or equal | `findByPriceLessThanEqual(BigDecimal price)` |
| `Between` | Within range | `findByPriceBetween(BigDecimal from, BigDecimal to)` |
| `After`, `Before` | After or before a suitable temporal/ordered value | `findByCreatedAtAfter(Instant time)` |
| `In` | Within a set | `findByStatusIn(Collection<String> statuses)` |
| `NotIn` | Not within a set | `findByStatusNotIn(Collection<String> statuses)` |
| `IsNull` | Null value | `findByDeletedAtIsNull()` |
| `IsNotNull` | Non-null value | `findByDeletedAtIsNotNull()` |
| `Like` | Matches LIKE pattern | `findByNameLike(String pattern)` |
| `Containing` | Contains substring | `findByNameContaining(String part)` |
| `StartingWith` | Starts with string | `findByNameStartingWith(String prefix)` |
| `EndingWith` | Ends with string | `findByNameEndingWith(String suffix)` |
| `True`, `False` | Boolean value | `findByFeaturedTrue()` |

Keyword availability and interpretation may depend on the Spring Data Relational version. When using less common keywords, check the documentation/Javadoc of the version managed by Spring Boot in your project.

Example finding products within a price range and specific status:

```java
Flux<Product> findByStatusAndPriceBetween(
    String status,
    BigDecimal minPrice,
    BigDecimal maxPrice
);
```

Example finding by a set of statuses:

```java
Flux<Product> findByStatusIn(Collection<String> statuses);
```

If the collection is empty, define the business behavior before calling the repository. Do not let an empty list accidentally lead to an overly broad query or confusing results.

## 5. Static Sorting with OrderBy

`OrderBy` lets you declare a fixed sort order in the method name. For example:

```java
Flux<Product> findByStatusOrderByCreatedAtDesc(String status);
```

This method filters by status and always sorts by creation time descending. The application does not need to pass a `Sort` object on every call.

You can sort by multiple properties:

```java
Flux<Product> findByStatusOrderByStatusAscCreatedAtDescIdDesc(
    String status
);
```

Spring Data reads property-and-direction pairs from left to right:

1. `status` ascending.
2. `createdAt` descending.
3. `id` descending.

In many queries, sorting by a single property is sufficient. However, if the sort column is not unique, multiple rows may share the same value. Adding a unique key like `id` as the final tiebreaker makes the order deterministic.

### 5.1. Why Is a Deterministic Order Needed?

Suppose multiple products share the same `createdAt`. Sorting only by creation time lets the database return rows with identical timestamps in different orders across executions. When combined with limits or pagination, this can cause rows to repeat or be skipped between reads.

Declare instead:

```java
Flux<Product> findByStatusOrderByCreatedAtDescIdDesc(String status);
```

Because `id` is a unique key, it breaks ties deterministically when `createdAt` values match. This is especially helpful when fetching batches or building cursor-based pagination.

### 5.2. OrderBy Uses Entity Property Names

In the example entity, the Java property is `createdAt`, while the database column is `created_at`:

```java
@Column("created_at")
private Instant createdAt;
```

The method name uses `CreatedAt`:

```java
findByStatusOrderByCreatedAtDesc(...)
```

Spring Data uses mapping metadata to translate the property to the column name. Do not write `OrderByCreated_atDesc` just because the physical column name contains an underscore.

## 6. Limiting Results with First and Top

You can cap the maximum number of rows directly in the method name using `First` or `Top`.

```java
Flux<Product> findTop10ByStatusOrderByCreatedAtDescIdDesc(
    String status
);
```

This method returns at most 10 products matching the status, ordered by creation time and ID descending.

`First` and `Top` have identical result-limiting semantics. You can write:

```java
Flux<Product> findFirst10ByStatusOrderByCreatedAtDescIdDesc(
    String status
);
```

If no number follows `First` or `Top`, the limit defaults to one result:

```java
Mono<Product> findFirstBySku(String sku);
```

When selecting one row out of many matching rows, combine it with `OrderBy` to determine which row is picked:

```java
Mono<Product> findFirstByCategoryOrderByCreatedAtDescIdDesc(
    String category
);
```

Without ordering, "first" gives no guarantee as to which row the database picks. Return order can shift depending on execution plans or data changes.

### 6.1. Top/First Combined with Multiple Conditions

Limit keywords appear before `By`, while the predicate and sort follow after:

```java
Flux<Product> findTop20ByStatusAndCategoryOrderByCreatedAtDescIdDesc(
    String status,
    String category
);
```

The limit applies to the result set matching the conditions and sort order. Conceptually, the database locates matching rows, sorts them, and returns at most 20 rows.

### 6.2. Limit Means Maximum Count

`Top20` does not guarantee there will always be 20 rows. If only 7 rows match, the result has at most 7 rows. If no rows match, `Flux` completes without emitting elements.

For a method returning `Mono<T>` with no results, the publisher completes empty. Using `switchIfEmpty`, the service can turn that into a business error or fallback as required.

## 7. Combining Conditions, Sort, and Limit in One Repository

Example repository for a product listing feature:

```java
public interface ProductRepository
        extends ReactiveCrudRepository<Product, Long> {

    // AND condition.
    Flux<Product> findByStatusAndCategory(
        String status,
        String category
    );

    // Comparison condition.
    Flux<Product> findByPriceGreaterThanEqual(BigDecimal minPrice);

    // Static sorting by multiple properties.
    Flux<Product> findByStatusOrderByCreatedAtDescIdDesc(String status);

    // Combining AND + static sort + limit 20 rows.
    Flux<Product> findTop20ByStatusAndCategoryOrderByCreatedAtDescIdDesc(
        String status,
        String category
    );

    // Pick the single newest result.
    Mono<Product> findFirstByCategoryOrderByCreatedAtDescIdDesc(
        String category
    );

    // Aggregate queries.
    Mono<Long> countByStatus(String status);

    Mono<Boolean> existsBySku(String sku);
}
```

A service can call it directly:

```java
public Flux<Product> findFeaturedProducts(String category) {
    return productRepository
        .findTop20ByStatusAndCategoryOrderByCreatedAtDescIdDesc(
            "ACTIVE",
            category
        );
}
```

The publisher is returned to the caller. In WebFlux, the framework subscribes and writes the results reactively; there is no need to call `block()` in the service.

## 8. Meaning of Mono and Flux Return Types

The return type should reflect the expected result count and how the application processes the data:

| Return type | Meaning |
|---|---|
| `Flux<Product>` | Zero, one, or many products; suitable for listings and Top N |
| `Mono<Product>` | At most one product; suitable for `First` or queries by unique key |
| `Mono<Long>` | A count value, typically used with `countBy...` |
| `Mono<Boolean>` | An existence check value, typically used with `existsBy...` |

For example:

```java
Mono<Long> activeCount = productRepository.countByStatus("ACTIVE");
Mono<Boolean> skuExists = productRepository.existsBySku("SKU-100");
```

Do not use `Mono<List<Product>>` solely because the query has a small limit if `Flux<Product>` already expresses the data stream cleanly. If an in-memory list is needed for a specific use case, explicitly call `collectList()` in the service layer after limiting the row count.

## 9. Null Parameters and Optional Conditions

Derived queries represent a fixed condition structure. For example:

```java
Flux<Product> findByStatusAndCategory(String status, String category);
```

This method always applies both conditions. Passing `null` does not automatically skip the corresponding condition. For equality comparisons, Spring Data typically interprets a null parameter as a null check (`IS NULL`) according to derived query semantics.

If you want to omit a filter when a request omits a value, choose another approach:

- Create separate repository methods when optional filter combinations are small and stable.
- Use `R2dbcEntityTemplate` with `Query`/`Criteria` to add conditions based on the request.
- Use `@Query` when dynamic SQL has a clear, well-controlled structure.

Example filter where `category` can be omitted:

```java
Flux<Product> search(ProductFilter filter) {
    if (filter.category() == null) {
        return repository.findByStatusOrderByCreatedAtDescIdDesc(
            filter.status()
        );
    }

    return repository.findByStatusAndCategory(
        filter.status(),
        filter.category()
    );
}
```

With many optional filters, the number of method combinations grows rapidly. In those cases, `Criteria` is usually much easier to maintain than creating dozens of derived methods.

## 10. Property Names and Nested Property Paths

Spring Data resolves property names against the domain model. If an entity has nested properties, query derivation can traverse property paths.

For example:

```java
public class Address {
    private String city;
    private String postalCode;
}

public class Customer {
    @Id
    private Long id;

    private Address address;
}
```

A method can use a property path such as:

```java
Flux<Customer> findByAddressCity(String city);
```

When property names could cause ambiguity, an underscore can clarify the path boundary for the parser:

```java
Flux<Customer> findByAddress_City(String city);
```

Whether nested objects map to columns or relationships depends on Spring Data Relational's model and how the entity is configured. This is not automatic multi-table joining according to JPA ORM rules. If multi-table joins are needed, consider explicit SQL or an appropriate projection.

## 11. IgnoreCase, Containing, and String Search

Several keywords support string searches:

```java
Flux<Product> findByNameContainingIgnoreCase(String part);

Flux<Product> findByNameStartingWithIgnoreCase(String prefix);

Flux<Product> findByNameEndingWith(String suffix);
```

`Containing` represents a substring search, usually translated into a LIKE pattern with wildcards on both ends. `StartingWith` and `EndingWith` represent prefix and suffix matching respectively. `IgnoreCase` requests case-insensitive comparison within what the database/dialect supports.

Collation, Unicode, and case-folding behaviors depend on the database. For languages with complex casing rules, test with real data rather than assuming `IgnoreCase` always produces results matching your linguistic rules.

When users enter `%` or `_`, those characters may be interpreted as LIKE wildcards. If business rules require literal matching, escape them according to your dialect.

## 12. Conditional Counting and Existence Checks

Derived queries do not only return entities. You can declare aggregate queries:

```java
Mono<Long> countByStatusAndCategory(String status, String category);

Mono<Boolean> existsByStatusAndPriceGreaterThanEqual(
    String status,
    BigDecimal minPrice
);
```

`countBy...` returns the number of matching rows; `existsBy...` returns the existence check result. Use these methods when business logic needs a count or boolean, avoiding loading full entities just to count or check whether data exists.

Exact counting can be expensive on large tables depending on predicates, indexes, and the database. Inspect execution plans and only run counts when the use case truly needs them.

## 13. Static Limits vs. Dynamic Pagination

`TopN` and `FirstN` are handy when the limit is a fixed part of the domain logic, for example:

- Fetching the 5 most recent orders for a dashboard.
- Fetching 10 featured products.
- Fetching the single latest record per unique criterion.
- Fetching at most 100 events to process in one run.

If the result count or offset changes per request, static method names may no longer fit. In that case, consider APIs supporting `Pageable`/`Limit` in your Spring Data R2DBC version, or use `R2dbcEntityTemplate` with `Query.limit(...)` and `Query.offset(...)`.

Reactive repositories typically return `Flux` rather than a `Page` containing both data and total page counts. If a UI needs exact totals, evaluate the cost of a separate count query. For large datasets read sequentially, keyset pagination can be more efficient than offset pagination.

## 14. Limits and Performance Protection

`TopN` limits returned rows, yet does not automatically make a query cheap. For example:

```java
Flux<Product> findTop20ByStatusOrderByCreatedAtDescIdDesc(String status);
```

If the table is very large and the database lacks suitable indexes on `status`, `created_at`, and `id`, the database may still scan or sort many rows before finding the top 20 results.

For frequent queries, consider indexes aligned with the filter conditions and sort order. For instance, in PostgreSQL, an index like `(status, created_at DESC, id DESC)` might be considered, though the optimal index depends on selectivity, workload, query patterns, and the database engine.

Points to check:

- Is the predicate selective enough?
- Do filter and sort columns have appropriate indexes?
- Should fewer columns be selected via a projection?
- Is `TopN` small enough for the SLA and downstream memory?
- Is the sort order deterministic with a unique tiebreaker key?
- Does the query plan use the expected index?

## 15. When Should You Switch to @Query or Criteria?

Derived queries are readable when conditions are simple and method names remain short. Still, there are cases where another representation is better.

| Situation | Commonly suitable approach |
|---|---|
| A few simple AND conditions | Derived query |
| Comparisons, static sort, and Top N | Derived query |
| Optional filters with many combinations | `R2dbcEntityTemplate` + `Criteria` |
| Complex nested AND/OR expressions | `Criteria` or `@Query` with explicit SQL |
| Multi-table joins and DTO projections | `@Query` or `DatabaseClient` |
| CTEs, window functions, or database-specific SQL | `@Query` or `DatabaseClient` |
| Overly long and hard-to-read method names | Move logic into an explicit query |

Example `@Query` when a clear SQL expression is needed:

```java
@Query("""
    SELECT id, name, status, category, price, created_at
    FROM product
    WHERE (status = :status AND category = :category)
       OR featured = true
    ORDER BY created_at DESC, id DESC
    LIMIT 20
    """)
Flux<Product> findMatchingFeatured(
    String status,
    String category
);
```

This SQL snippet uses `LIMIT` in PostgreSQL/MySQL syntax, which is not universal across all database engines. For other databases, adjust to the dialect. The advantage is clear logical grouping with parentheses; the trade-off is that the application maintains the SQL against the schema and dialect.

## 16. Testing Derived Queries

Integration tests should confirm that Spring Data parses the method name and generates valid queries on a compatible database and driver.

Scenarios to verify:

- Combining multiple AND and OR conditions.
- Boundary values for `GreaterThan`, `GreaterThanEqual`, `Between`, `Before`, and `After`.
- Sort ordering when multiple rows share the same value in the first sort column.
- `TopN`/`FirstN` returning no more than the requested row count.
- Empty results for `Flux` and `Mono`.
- `In` with an empty or null collection per the API contract.
- Null parameters and `IsNull`/`IsNotNull` conditions.
- `IgnoreCase`, `Containing`, wildcards, and real collation behavior.
- Property names where `@Column` differs from the physical column name.
- Indexes and execution plans on realistic data sizes.

Example with `StepVerifier`:

```java
StepVerifier.create(
        productRepository.findTop2ByStatusOrderByCreatedAtDescIdDesc("ACTIVE")
    )
    .expectNextCount(2)
    .verifyComplete();
```

The example assumes the database contains at least two `ACTIVE` products. Real tests should seed rows with identical timestamps to confirm the `id` tiebreaker orders them as expected.

## 17. Common Mistakes

| Mistake | Consequence | Resolution |
|---|---|---|
| Wrong property name in method | Spring Data fails to parse query or looks up nonexistent property | Use the entity's exact Java property name |
| Using physical column name instead of property name | Derived query mismatches mapping metadata | Use properties like `createdAt`, not `created_at` |
| Passing parameters in wrong order | Conditions receive wrong values | Order parameters to match predicate order in method name |
| Overly long AND/OR method names | Hard to understand logic and condition grouping | Switch to Criteria or `@Query` |
| Assuming null automatically skips filter | May generate `IS NULL` instead of omitting predicate | Use dynamic Criteria or separate methods |
| Using `First` without sorting | Selected row has nondeterministic order | Add `OrderBy` with a tiebreaker key |
| Using `TopN` without indexes | Database may still scan/sort many rows | Inspect execution plans and indexes |
| Using Top/First like dynamic pagination | Limit cannot vary per request | Use proper pagination APIs or template Query |
| Sorting by arbitrary column names from client | Uncontrolled SQL identifiers | Whitelist properties or use controlled sort mappings |
| Assuming every database shares the same limit syntax | SQL may differ by dialect | Let Spring Data generate queries or adapt explicit SQL per dialect |
| Using `Mono<T>` when multiple rows can match | Incompatible cardinality | Use `Flux<T>` or ensure unique conditions |

## 18. Process for Designing a Derived Query

When adding a repository method, follow these steps:

1. Identify the entity and persistent properties involved in the conditions.
2. Write the predicate using simple keywords like `Is`, `GreaterThanEqual`, `In`, `IsNull`.
3. Connect conditions with `And`/`Or` while keeping the method name readable.
4. Add `OrderBy` if result ordering is a fixed part of the domain requirement.
5. Add `FirstN`/`TopN` if the business rule has a fixed maximum limit.
6. Choose `Mono` or `Flux` based on cardinality.
7. Check null parameters, empty collections, and empty-result handling.
8. Test against the target database and inspect the execution plan if the query runs frequently.
9. Switch to Criteria or explicit SQL whenever the method name becomes overly complex.

## 19. Principles to Remember

- Derived queries are generated from repository method names and entity metadata.
- `And` requires all connected conditions to hold; `Or` allows either branch to match.
- Parameters are passed in the order they appear in the predicate.
- `OrderBy` declares static sorting using Java property names and `Asc`/`Desc` directions.
- You can sort by multiple properties; add a unique key as the last criterion for deterministic ordering.
- `TopN` and `FirstN` cap the maximum number of rows; they do not guarantee N rows are always returned.
- Use `Mono` for at most one result and `Flux` for result collections.
- Passing null to a derived query parameter does not automatically skip the condition.
- Use Criteria for optional filters and `@Query` when explicit SQL or logical parentheses are needed.
- Use exact entity property names so mapping metadata translates them to physical column names.
- `TopN` does not replace proper indexing or execution-plan tuning.
- Test sorting, limits, nulls, and boundary values against an actual database and driver.

Combining conditions, static sorting, and limits in method names lets repositories express common queries concisely. When predicates stay simple, `OrderBy` captures domain ordering, and `Top`/`First` captures result limits, derived queries are an easy-to-read option. Once dynamic filters or logical expressions grow complex, moving to `Criteria` or explicit SQL keeps queries understandable and easy to control.
