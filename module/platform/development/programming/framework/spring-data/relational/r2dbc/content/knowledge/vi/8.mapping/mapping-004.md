# Nhận diện khóa chính bằng `@Id`

Trong Spring Data Relational R2DBC, `@Id` đánh dấu thuộc tính đại diện cho định danh của một entity. Spring Data dùng thông tin này khi xây dựng metadata ánh xạ giữa class Java và bảng quan hệ, đặc biệt trong các thao tác tìm theo ID, lưu, cập nhật và xóa entity.

`@Id` thuộc Spring Data Commons, không phải annotation của JPA. Khi làm việc với R2DBC, cần dùng đúng `org.springframework.data.annotation.Id`. Annotation này cho Spring Data biết property nào là identifier; cấu trúc khóa chính, ràng buộc `PRIMARY KEY` và cách database sinh giá trị vẫn được định nghĩa trong schema của database.

## 1. Vai trò của `@Id` trong ánh xạ quan hệ

Một entity thường ánh xạ tới một bảng, còn mỗi instance đại diện cho một hàng. Spring Data cần biết property nào xác định duy nhất hàng đó để thực hiện các thao tác CRUD.

Ví dụ bảng `customer` có cột `id` làm khóa chính:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);
```

Entity tương ứng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("full_name")
    private String name;

    public Customer() {
    }

    public Customer(Long id, String name) {
        this.id = id;
        this.name = name;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

Trong ví dụ:

- `@Table("customer")` ánh xạ entity tới bảng `customer`.
- `@Id` xác định `id` là thuộc tính định danh của entity.
- `@Column("full_name")` ánh xạ property `name` tới cột `full_name`.
- `Long` cho phép giá trị ID chưa được gán biểu diễn bằng `null`.

`@Id` là metadata cho tầng ánh xạ. Nó không tự tạo cột `id`, không thêm constraint `PRIMARY KEY` và cũng không tự cấu hình cơ chế tăng ID. Những việc đó thuộc schema và database migration.

## 2. Dùng đúng annotation của Spring Data

Trong Java có một số annotation cùng tên `Id`. Với Spring Data R2DBC, import cần dùng là:

```java
import org.springframework.data.annotation.Id;
```

Không nhầm với:

```java
import jakarta.persistence.Id;
```

`jakarta.persistence.Id` thuộc JPA. R2DBC không dùng persistence context của JPA và không dựa trên Hibernate ORM để ánh xạ entity. Nếu vô tình import annotation JPA trong entity R2DBC, Spring Data Relational có thể không nhận diện property đó như identifier của entity.

Tương tự, nên dùng các annotation mapping của Spring Data Relational khi mô hình hóa bảng và cột:

```java
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.data.relational.core.mapping.Column;
```

Việc trộn annotation JPA và Spring Data Relational trong cùng entity có thể khiến metadata không như mong đợi. Hãy chọn bộ annotation phù hợp với công nghệ persistence mà repository đang sử dụng.

## 3. Đặt `@Id` trên property nào?

`@Id` phải đánh dấu property thực sự đại diện cho khóa định danh của hàng. Trong entity Java thông thường, có thể đặt annotation trên field:

```java
@Table("orders")
public class Order {

    @Id
    private Long orderId;

    private String status;
}
```

Tên property không bắt buộc phải là `id`; `orderId`, `customerKey` hoặc tên có ý nghĩa khác đều có thể được dùng làm identifier khi được đánh dấu bằng `@Id`. Nếu tên property khác tên cột trong database, khai báo `@Column` để ánh xạ rõ ràng:

```java
@Id
@Column("order_key")
private Long orderId;
```

Khi đó, `orderId` là tên property trong Java còn `order_key` là tên cột trong bảng. Spring Data dùng metadata này để tạo các câu lệnh phù hợp với mapping.

Có thể dùng annotation trên property accessor nếu mô hình entity sử dụng cách truy cập thuộc tính tương ứng. Trong một class Java, nên duy trì một kiểu truy cập nhất quán và đặt annotation ở vị trí Spring Data có thể đọc được theo cấu trúc property của class. Với entity dùng field access như các ví dụ trên, đặt `@Id` ngay trên field giúp người đọc nhận ra identifier trực tiếp.

### Một identifier cho entity

Các thao tác repository CRUD thông thường làm việc với một kiểu ID duy nhất, ví dụ `Long`, `Integer`, `UUID` hoặc một kiểu đơn giản được mapping/conversion hỗ trợ:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

Tham số generic thứ hai (`Long`) phải tương ứng với kiểu của property được đánh dấu `@Id`. Nếu entity có property `@Id` kiểu `UUID` nhưng repository khai báo `Long`, kiểu dữ liệu không nhất quán sẽ gây lỗi khi biên dịch hoặc khi sử dụng API repository.

Spring Data Relational tập trung vào một property định danh cho các thao tác CRUD chuẩn. Nếu bảng dùng khóa chính ghép từ nhiều cột, không nên giả định rằng chỉ cần đặt nhiều `@Id` là framework tự hiểu composite key. Hãy cân nhắc một khóa thay thế (surrogate key) hoặc dùng câu SQL tùy chỉnh qua `DatabaseClient`/`R2dbcEntityTemplate` cho mô hình cần khóa ghép.

## 4. `@Id` và tên cột khóa chính

Tên property Java và tên cột database có thể khác nhau. `@Id` xác định property định danh, còn `@Column` xác định tên cột được dùng khi ánh xạ.

Ví dụ bảng dùng cột `customer_key`:

```sql
CREATE TABLE customer_profile (
    customer_key BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(200) NOT NULL
);
```

Entity:

```java
@Table("customer_profile")
public class CustomerProfile {

    @Id
    @Column("customer_key")
    private Long id;

    @Column("display_name")
    private String displayName;
}
```

Spring Data hiểu `id` là identifier của entity và dùng cột `customer_key` trong SQL. Nếu bỏ `@Column`, việc chuyển tên property sang tên cột sẽ phụ thuộc naming strategy của Spring Data Relational. Khi schema có tên cột đặc biệt, tên legacy hoặc tên không theo quy ước, khai báo `@Column` tường minh giúp mapping dễ đọc và ít phụ thuộc vào quy ước ngầm.

`@Id` không có nghĩa cột phải tên là `id`. Ngược lại, một cột tên `id` trong database cũng không tự động thay thế việc khai báo identifier rõ ràng trong entity. Hãy kiểm tra metadata mapping và schema nếu framework đang dùng nhầm cột trong câu lệnh CRUD.

## 5. `@Id` ảnh hưởng tới các thao tác CRUD như thế nào?

Identifier là căn cứ để Spring Data tạo điều kiện tìm, cập nhật hoặc xóa đúng hàng. Ví dụ với repository:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

Một số thao tác thường dùng:

| API | Cách identifier được sử dụng |
| --- | --- |
| `findById(id)` | Tìm hàng theo giá trị ID |
| `existsById(id)` | Kiểm tra hàng có ID tương ứng tồn tại hay không |
| `deleteById(id)` | Xóa hàng theo ID |
| `save(entity)` | Xác định trạng thái mới/cũ của entity; khi cập nhật, ID được dùng để xác định hàng cần cập nhật |
| `findAllById(ids)` | Tìm các hàng có ID thuộc tập giá trị được cung cấp |

Ví dụ tìm và xóa theo ID trong luồng reactive:

```java
public Mono<Void> deleteCustomer(Long id) {
    return customerRepository.findById(id)
            .switchIfEmpty(Mono.error(
                    new IllegalArgumentException("Customer không tồn tại: " + id)
            ))
            .flatMap(customer -> customerRepository.delete(customer));
}
```

`findById` sử dụng identifier đã khai báo trong metadata. Các thao tác repository trả `Mono` hoặc `Flux`; SQL được thực thi khi publisher được subscribe.

## 6. `@Id` và việc phân biệt INSERT với UPDATE

Khi gọi `save(entity)`, Spring Data cần xác định entity đang đại diện cho bản ghi mới hay bản ghi đã tồn tại. Trạng thái này thường được gọi là *newness detection*.

Với entity không triển khai `Persistable`, Spring Data Relational thường dựa vào thuộc tính `@Version` nếu entity có version property; nếu không có version property thì dựa vào identifier:

- Nếu version property là `null` (với kiểu object) hoặc `0` (với kiểu số nguyên thủy), entity được xem là mới.
- Nếu không có version property, ID là `null` (hoặc `0` với kiểu số nguyên thủy) thường được xem là entity mới.
- Khi entity được xem là mới, `save` thực hiện insert.
- Khi entity được xem là đã tồn tại, `save` thực hiện update theo identifier.

Chi tiết nhận diện trạng thái có thể được tùy chỉnh bằng `Persistable` hoặc chịu ảnh hưởng của mapping/version strategy trong phiên bản Spring Data đang dùng.

Ví dụ entity mới chưa có ID:

```java
Customer newCustomer = new Customer(null, "Nguyen An");

Mono<Customer> savedCustomer = customerRepository.save(newCustomer);
```

Với ID `null`, Spring Data nhận diện entity là mới (giả sử không có version property làm thay đổi kết quả). Khi subscribe, repository thực hiện insert. Nếu database sinh khóa chính, giá trị được đọc từ kết quả insert và gán vào entity được phát ra bởi publisher.

### Vì sao nên dùng kiểu wrapper như `Long`?

Với `Long`, entity mới có thể biểu diễn ID chưa tồn tại bằng `null`. Với kiểu nguyên thủy `long`, giá trị mặc định là `0`, nên Spring Data phải dùng quy ước giá trị zero để nhận diện entity mới. Wrapper thường diễn tả trạng thái rõ hơn:

```java
@Id
private Long id;
```

Nếu ID được sinh tự động, không nên tự gán một giá trị giả như `-1` hoặc `0` cho wrapper chỉ để biểu thị bản ghi mới. Hãy để ID chưa có giá trị cho tới khi database trả khóa được sinh.

### Entity có ID được gán trước

Nếu ứng dụng tự cấp ID, ví dụ UUID hoặc mã nghiệp vụ, entity mới có thể đã có giá trị ID trước khi insert. Khi chỉ dựa vào ID, Spring Data có thể xem entity là cũ và chọn update. Đây là lý do cần hiểu newness detection trước khi dùng `save` với ID được gán thủ công.

Có một số cách xử lý tùy yêu cầu:

- Dùng thao tác insert tường minh qua `R2dbcEntityTemplate.insert(entity)` hoặc câu SQL qua `DatabaseClient` khi chắc chắn cần tạo hàng mới.
- Triển khai `Persistable<ID>` để cung cấp `isNew()` theo trạng thái nghiệp vụ của entity. Khi dùng cách này, ứng dụng cần quản lý đúng thời điểm entity chuyển từ mới sang đã lưu.
- Dùng version property nếu mô hình có nhu cầu optimistic locking và version state phù hợp với quy tắc newness detection.

Không nên cố ép `save` thành insert bằng cách đặt ID không hợp lệ. Hãy chọn API phản ánh đúng ý định insert hoặc định nghĩa trạng thái entity rõ ràng.

## 7. Khóa chính do database sinh

Trong nhiều schema quan hệ, database tự sinh khóa chính khi insert. Ví dụ PostgreSQL dùng identity column:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(200) NOT NULL
);
```

Entity khai báo ID bằng kiểu wrapper:

```java
@Table("customer")
public class Customer {

    @Id
    private Long id;

    @Column("full_name")
    private String fullName;

    public Customer() {
    }

    public Customer(String fullName) {
        this.fullName = fullName;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }
}
```

Lưu entity:

```java
Mono<Customer> saved = customerRepository.save(
        new Customer("Nguyen An")
);

return saved.doOnNext(customer ->
        log.info("ID được database sinh: {}", customer.getId())
);
```

Khi insert hoàn tất, Spring Data R2DBC sử dụng khả năng trả generated values của driver/database để lấy ID và đưa nó vào entity được phát ra. Hãy dùng entity được phát ra từ `save` để lấy ID sau khi lưu. Với entity bất biến (immutable), framework có thể tạo instance mới chứa ID thay vì thay đổi instance ban đầu.

`@Id` không tự bật auto-increment hay identity. Schema phải định nghĩa cơ chế sinh khóa và driver/database phải hỗ trợ trả về generated value. Cú pháp identity, sequence hoặc generated key khác nhau giữa các hệ quản trị; ví dụ PostgreSQL ở trên không phải DDL dùng chung cho mọi database.

### Không nhầm `@Id` với `@GeneratedValue`

`@GeneratedValue` là annotation thường gặp trong JPA để mô tả chiến lược sinh khóa của ORM. Spring Data Relational R2DBC không dựa vào JPA generation strategy đó. Với R2DBC, việc sinh ID thường do database schema và khả năng generated values của driver quyết định; Spring Data nhận diện property bằng `@Id` rồi xử lý giá trị được trả về.

Nếu cần sequence hoặc cách cấp ID đặc thù, hãy xem tính năng của Spring Data Relational và database đang dùng, hoặc chủ động cấp ID trong ứng dụng. Không thêm annotation JPA vào entity R2DBC với kỳ vọng nó sẽ điều khiển cách sinh khóa.

## 8. ID và optimistic locking với `@Version`

`@Id` và `@Version` có vai trò khác nhau:

- `@Id` xác định hàng nào là entity đang được thao tác.
- `@Version` lưu phiên bản của entity để phát hiện cập nhật đồng thời (optimistic locking).

Ví dụ:

```java
@Table("inventory")
public class InventoryItem {

    @Id
    private Long id;

    @Version
    private Long version;

    private Integer quantity;
}
```

Trong schema tương ứng, cột `id` là khóa chính; cột `version` lưu số phiên bản. Khi cập nhật, Spring Data có thể dùng cả ID và version hiện tại trong điều kiện update, đồng thời tăng version. Nếu không có hàng nào được cập nhật do version đã thay đổi, thao tác có thể phát sinh lỗi optimistic locking.

Version property cũng có thể được dùng trong quá trình nhận diện entity mới. Vì vậy, nếu entity có `@Version`, đừng chỉ nhìn ID để kết luận `save` chắc chắn chạy insert hay update. Cần xét trạng thái version theo quy tắc của Spring Data và mapping hiện tại.

## 9. Entity bất biến, record và Kotlin data class

Spring Data Relational hỗ trợ mapping các mô hình entity không nhất thiết phải có setter cho mọi property. Với entity bất biến, dữ liệu có thể được khởi tạo qua constructor. Khi database sinh ID sau insert, framework cần tạo instance chứa ID mới theo cơ chế tạo entity mà mapping context hỗ trợ.

Ví dụ Java record:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        @Column("full_name") String fullName
) {
}
```

Repository:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

Khi lưu một record mới với `id == null`, repository phát ra record được ánh xạ với ID database trả về. Hãy tiếp tục sử dụng giá trị phát ra thay vì giả định object ban đầu được thay đổi tại chỗ.

Với Kotlin data class, đặt `@Id` trên constructor property tương ứng và chọn kiểu nullable như `Long?` nếu ID được database sinh. Cú pháp annotation use-site có thể cần điều chỉnh theo cách compiler đặt annotation lên field hoặc property; cần bảo đảm Spring Data đọc được annotation trên persistent property.

## 10. Kiểm thử mapping của identifier

Có thể kiểm thử repository với database R2DBC phù hợp và `StepVerifier`. Ví dụ:

```java
StepVerifier.create(customerRepository.save(new Customer(null, "Nguyen An")))
        .assertNext(saved -> {
            assertThat(saved.getId()).isNotNull();
            assertThat(saved.getFullName()).isEqualTo("Nguyen An");
        })
        .verifyComplete();
```

Sau khi lưu, có thể dùng ID phát ra để đọc lại:

```java
Mono<Customer> roundTrip = customerRepository
        .save(new Customer(null, "Nguyen An"))
        .flatMap(saved -> customerRepository.findById(saved.getId()));
```

Các kiểm thử hữu ích khác gồm:

- Lưu entity có ID `null` và xác nhận database sinh ID.
- Đọc entity bằng `findById` với ID vừa sinh.
- Cập nhật một property và xác nhận `save` cập nhật đúng hàng theo ID.
- Xóa entity theo ID và xác nhận hàng không còn tồn tại.
- Kiểm tra mapping khi tên property khác tên cột và có `@Column`.
- Kiểm tra hành vi với ID được gán trước và `Persistable.isNew()` nếu ứng dụng dùng assigned ID.
- Kiểm tra optimistic locking nếu entity có `@Version`.

Kiểm thử cần subscribe publisher. Chỉ tạo `Mono` từ repository mà không tiêu thụ nó thì thao tác SQL chưa được thực hiện.

## 11. Lỗi thường gặp khi nhận diện khóa chính

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Spring Data không nhận đúng identifier | Thiếu `@Id` hoặc import nhầm `jakarta.persistence.Id` | Dùng `org.springframework.data.annotation.Id` trên persistent property |
| Repository generic ID không khớp | `ReactiveCrudRepository<Entity, ID>` khai báo sai kiểu | Đồng bộ `ID` với kiểu property được đánh dấu `@Id` |
| SQL dùng sai tên cột khóa | Property và column mapping không khớp schema | Khai báo `@Column("...")` đúng tên cột và kiểm tra migration |
| `save` chạy UPDATE thay vì INSERT | Entity có ID được gán trước nên bị nhận diện là cũ | Dùng insert tường minh hoặc tùy chỉnh newness detection bằng `Persistable` |
| ID sau insert vẫn null | Schema không sinh ID, driver không trả generated values hoặc mapping sai | Kiểm tra DDL, dialect, driver và generated-key support |
| Update không tác động hàng nào | ID sai, hàng không tồn tại hoặc version không khớp | Kiểm tra giá trị ID, dữ liệu và `@Version` |
| Dùng nhiều `@Id` nhưng CRUD không hoạt động như mong muốn | Mô hình đang cố biểu diễn composite key bằng nhiều property | Dùng một identifier được hỗ trợ hoặc SQL tùy chỉnh cho khóa ghép |
| Dùng `@GeneratedValue` nhưng ID không tự sinh | Đang áp dụng annotation của JPA cho R2DBC | Cấu hình sinh khóa ở database và kiểm tra generated values của driver |

Khi điều tra, hãy kiểm tra theo thứ tự: import annotation, vị trí `@Id`, kiểu ID của repository, tên cột trong schema, trạng thái ID/version trước khi gọi `save`, rồi khả năng sinh và trả generated key của database/driver.

## 12. Phân biệt các khái niệm liên quan

| Khái niệm | Vai trò |
| --- | --- |
| `@Id` | Đánh dấu property định danh trong metadata Spring Data |
| `PRIMARY KEY` | Ràng buộc ở database bảo đảm tính duy nhất và không null của khóa chính |
| `@Column` | Ánh xạ property Java tới tên cột database |
| `@Version` | Quản lý version để phát hiện cập nhật đồng thời và hỗ trợ nhận diện trạng thái mới trong một số trường hợp |
| `Persistable.isNew()` | Cho phép entity tự cung cấp trạng thái mới/cũ |
| Identity/sequence/default của database | Cơ chế tạo giá trị khóa khi insert |

Những khái niệm này phối hợp với nhau nhưng không thay thế nhau. Entity có `@Id` mà database không có khóa chính tương ứng vẫn có thể dẫn tới dữ liệu trùng hoặc lỗi integrity. Database có `PRIMARY KEY` nhưng entity đánh dấu sai property cũng có thể khiến Spring Data tạo SQL CRUD không đúng.

## 13. Ghi nhớ

- Dùng `org.springframework.data.annotation.Id` để đánh dấu property định danh trong Spring Data Relational R2DBC.
- Không dùng nhầm `jakarta.persistence.Id` hoặc dựa vào annotation JPA để điều khiển mapping R2DBC.
- Tên property không bắt buộc là `id`; `@Column` ánh xạ property tới tên cột khóa chính khi cần.
- Kiểu ID trong `ReactiveCrudRepository<Entity, ID>` phải khớp với kiểu property `@Id`.
- `@Id` chỉ mô tả identifier cho Spring Data; schema database vẫn phải định nghĩa primary key và cơ chế sinh ID nếu cần.
- `save` dựa trên newness detection để chọn insert hoặc update. ID, `@Version` và `Persistable.isNew()` có thể tham gia quyết định đó.
- Với khóa do database sinh, dùng kiểu wrapper như `Long`, lưu entity mới với ID chưa có và đọc entity được phát ra từ publisher `save`.
- Nếu ứng dụng tự gán ID, hãy định nghĩa rõ trạng thái mới/cũ hoặc dùng thao tác insert tường minh.
- `@Version` không phải khóa chính; nó hỗ trợ optimistic locking và có thể ảnh hưởng nhận diện entity mới.
- Với composite primary key, không giả định nhiều `@Id` tạo ra mapping khóa ghép tự động; cân nhắc khóa thay thế hoặc SQL tùy chỉnh.

Khi ánh xạ một entity R2DBC, hãy xác định property nào là định danh, kiểm tra đúng annotation và kiểu ID, rồi đối chiếu với cột khóa chính trong schema. Khi đã rõ quan hệ đó, các thao tác repository có thể tìm, lưu, cập nhật và xóa đúng hàng theo metadata mà Spring Data xây dựng.
