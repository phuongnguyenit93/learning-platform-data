# Controlling Write Ordering and Concurrency

When writing multiple records with Spring Data R2DBC, two key questions are **in what order must operations run** and **how many operations may run concurrently**. Choosing the wrong Reactor operator can alter completion order, overload the connection pool, cause lock contention, or leave partial data committed when another part fails.

Reactive does not mean every operation should run in parallel. If record B depends on record A, you must ensure A finishes before writing B. If records are independent, you can increase concurrency to leverage asynchronous I/O, bounded by database and pool capacity. If an entire batch must be atomic, all operations must sit within the same reactive transaction boundary and use the right `ConnectionFactory`.

A helpful perspective is separating four often-confused concepts:

- **Input order:** the order elements appear in the source `Flux` or collection.
- **Execution start order:** which database operation is dispatched first.
- **Completion/commit order:** which operation finishes or commits first.
- **Read result order:** the order rows return when querying data.

These orders do not match automatically. `flatMap` may pull input items in source order while allowing inner operations to finish out of order. Even when inserts are dispatched sequentially, databases do not guarantee a subsequent `SELECT` returns rows in insert order without an `ORDER BY`.

## 1. Why write ordering and concurrency matter?

Suppose an import needs to write three groups of data:

1. Create orders.
2. Write order lines referencing each order.
3. Write processing history referencing orders and order lines.

These steps have foreign key dependencies. Writing an order line before its order exists may fail with a foreign key violation. If history needs an ID generated by an earlier operation, the later step must wait for that ID.

Conversely, when importing 1,000 independent customer records with no dependencies and no business ordering requirements, running multiple operations concurrently can raise throughput substantially over row-by-row sequential writes.

Too little concurrency underutilizes I/O. Too much concurrency can cause:

- Connection pool exhaustion with many publishers waiting to acquire connections.
- Database overload from too many simultaneous statements.
- Lock contention, deadlocks, and serialization failures.
- Increased memory from prefetching, queues, and buffered pending emissions.
- Higher response times from saturated CPU, disk, or network.
- Difficulty determining which records were written when a group fails.

Choose operators based on dependencies, atomicity requirements, and resource limits—not simply on which code looks shorter.

## 2. Common Reactor operators for multi-record writes

| Operator | How inner publishers run | Result emission order | When appropriate |
|---|---|---|---|
| `concatMap` | Subscribes inner publishers one at a time; waits for current to finish before next | Source order | Dependent operations or when serialization is required. |
| `flatMap` | Allows multiple inner publishers concurrently, bounded by `concurrency` if set | Not guaranteed to match source order | Independent operations needing higher throughput. |
| `flatMapSequential` | Subscribes multiple inner publishers concurrently, buffering emissions into source order | Source order | Need concurrency while downstream needs results in source order. |
| `concatMapDelayError` | Sequential like `concatMap`, deferring error emission per config | Source order | Need to collect remaining results before signaling errors; consider partial writes. |
| `buffer` | Collects elements into groups before processing | Element order within each chunk | Batch/chunked writes. |

Important point: `flatMapSequential`'s emission order does not mean database side effects execute or commit sequentially. Inner publishers still run concurrently; the operator only queues outputs to emit them in source order. If write B must start only after write A finishes, use `concatMap` or chain with `then`.

## 3. Using concatMap when write order is mandatory

Example writing each record strictly in input order:

```java
Mono<Void> saveInOrder(Flux<Customer> customers) {
    return customers
        .concatMap(customerRepository::save)
        .then();
}
```

`concatMap` subscribes to the next `save` publisher only after the current one completes. Thus writes are composed sequentially in source order.

This is the right choice when:

- Later records depend on IDs or state created by earlier records.
- Business constraints require processing in event order.
- Operations update the same aggregate and must preserve order.
- You want to limit concurrent connections/statements in an import flow.
- You want ordered error isolation and to stop on the first error.

`concatMap` can lower throughput because each operation awaits the previous one. Use it when ordering truly matters; for independent rows, bounded concurrency can be used.

### 3.1 concatMap does not create a transaction

The following code serializes operations but does not ensure they all commit or roll back together:

```java
return Flux.fromIterable(customers)
    .concatMap(customerRepository::save)
    .then();
```

If each `save` executes outside an enclosing transaction, earlier writes may already be committed when a later record fails. If all-or-nothing is required, set an explicit transaction boundary:

```java
Mono<Void> saveAllAtomically(List<Customer> customers) {
    return transactionalOperator.transactional(
        Flux.fromIterable(customers)
            .concatMap(customerRepository::save)
            .then());
}
```

`TransactionalOperator` must be built from the `ReactiveTransactionManager` bound to the same `ConnectionFactory` used by the repository. If the repository uses a different factory, its operations may not participate in the expected transaction.

## 4. Using flatMap when operations are independent

If records are independent, several operations can run concurrently:

```java
Mono<Void> saveConcurrently(Flux<Customer> customers) {
    return customers
        .flatMap(customerRepository::save, 8)
        .then();
}
```

The `8` argument is the maximum concurrency of inner publishers managed by `flatMap` within this subscription. When one operation finishes, the operator can subscribe to the next. Results emit as inner publishers complete, so source order is not guaranteed.

Use this only when:

- Records have no ordering dependencies.
- No invariants are broken by concurrent updates.
- The database and connection pool can sustain the chosen load.
- Error handling and partial success rules are well defined.
- Downstream does not require emissions in input order.

Do not rely on `flatMap`'s default concurrency in persistence code. Specify the value explicitly so readers see an intentional limit that can be tuned via configuration.

## 5. flatMapSequential preserves output order, not write order

Example:

```java
Flux<Customer> saved = customers
    .flatMapSequential(customerRepository::save, 8);
```

Up to 8 `save` publishers can be subscribed concurrently. If the second save completes before the first, the second save's result waits in a queue so it emits after the first.

This operator is useful if downstream needs outputs in source order—for instance, writing an ordered report after independent operations finish. However, never use `flatMapSequential` when a later record must be written strictly after an earlier one. Database statements can still run concurrently, and commit order is not guaranteed.

| Requirement | Choice |
|---|---|
| Write A completely before starting write B | `concatMap` |
| Write A and B concurrently, results in any order | `flatMap` |
| Write A and B concurrently, downstream receives results in source order | `flatMapSequential` |

## 6. Input order is not SELECT order

Databases do not guarantee row order in queries lacking `ORDER BY`. Inserting A then B does not mean `SELECT * FROM table` always returns A before B.

If the application needs to read in business order, store an appropriate sequence/timestamp/order column and query explicitly:

```sql
SELECT id, event_type, created_at
FROM account_event
WHERE aggregate_id = :aggregateId
ORDER BY aggregate_version ASC;
```

`ORDER BY created_at` may not suffice if multiple records share identical timestamps. Add a unique key or aggregate version as a tie-breaker for deterministic ordering.

Never treat physical row storage order, incidental query return order, identity generation order, or batch result order as a business contract unless the database guarantees it.

## 7. Writing dependent records

For parent/child records, write the parent first, then the children:

```java
Mono<Order> createOrder(CreateOrderCommand command) {
    Order order = Order.from(command);

    return orderRepository.save(order)
        .flatMap(savedOrder ->
            Flux.fromIterable(command.lines())
                .map(line -> line.withOrderId(savedOrder.getId()))
                .concatMap(orderLineRepository::save)
                .then(Mono.just(savedOrder)));
}
```

The parent must be saved and its ID read from the returned entity before creating children. Children in this example are saved sequentially; if they are independent once the parent exists, bounded concurrency could be used, provided the transaction/driver supports it and no ordering constraint exists among children.

To make the whole operation atomic:

```java
Mono<Order> createOrderAtomically(CreateOrderCommand command) {
    return transactionalOperator.transactional(createOrder(command));
}
```

If one child violates a constraint, the transaction rolls back the parent and any previously saved children. Without a transaction, the parent and a subset of children could remain in the database.

## 8. Serializing per aggregate key

Sometimes records belong to many independent aggregates, yet records within the same aggregate must be written in strict order. For example, events for account A must be processed sequentially, while events for account B can run in parallel.

Group by key and use `concatMap` within each group:

```java
Mono<Void> processEvents(Flux<AccountEvent> events) {
    return events
        .groupBy(AccountEvent::accountId)
        .flatMap(group ->
            group.concatMap(event -> eventRepository.save(event)),
            16)
        .then();
}
```

Here events for the same `accountId` run sequentially, while up to 16 groups run concurrently via `flatMap`. Different groups can progress in parallel.

Use `groupBy` carefully with very large or unbounded key spaces. Groups must be subscribed and drained; if many groups are created without being consumed, buffers can grow. For massive streams, consider fixed-count partitions/shards, keyed queues, or database-level serialization.

If multiple application instances process events for the same aggregate, `groupBy` only serializes within one subscription/process. It does not lock other workers. Use broker partitioning by key, distributed locks/leases, or database optimistic versioning/conditional updates to protect across instances.

## 9. Limiting flatMap concurrency

`flatMap` has overloads accepting concurrency and prefetch:

```java
source.flatMap(this::writeOne, 8, 1);
```

- `8` is the maximum number of inner publishers subscribed concurrently within this subscription.
- `1` is the prefetch for the source publisher in this example; prefetch affects how many elements are requested/buffered, not an application-wide connection cap.

Choose concurrency based on measurements:

- Pool size and connections reserved for other requests.
- Database max connections and load from other applications.
- Per-statement cost, locks, and indexes.
- Payload sizes and query durations.
- How many bulk requests can run simultaneously.
- Pool timeouts and backlog.

Never blindly set concurrency equal to pool max size. The pool needs headroom for normal requests, health checks, other jobs, and admin queries. If 20 concurrent requests each run a batch at concurrency 10, total active inner publishers can reach roughly 200, even though each request only specifies 10.

## 10. Per-request concurrency is not system-wide concurrency

The `flatMap(..., concurrency)` parameter only caps inner publishers inside the current subscription. It does not create a global semaphore across all application requests.

For example, an endpoint with concurrency 8 receiving 100 concurrent bulk requests can still spawn up to 800 active or queued operations. The connection pool caps checked-out connections, while the rest sit waiting in the queue and may time out.

If global load limiting is needed, use:

- Admission control or bulkheads at the service layer.
- Bounded work queues with fixed worker counts.
- Capping the number of concurrent bulk jobs.
- Rate limiting per tenant or caller.
- Pool acquire timeouts and pending acquire limits.
- Tuning concurrency to match workload and database capacity.

`limitRate` shapes upstream demand in batches; it is not a global semaphore and does not automatically cap concurrent queries across requests.

## 11. Connection pools and concurrency

R2DBC connection pools typically enforce a maximum connection count and an acquire queue. When bulk write concurrency exceeds available connections, operations wait in the pool. If wait time exceeds the acquire timeout, the publisher fails.

Guidelines:

- Size pool max connections based on database limits and total application replicas.
- Reserve connections for other workloads, migrations, monitoring, and admin tasks.
- Monitor active, idle, pending acquires, acquire latency, and timeouts.
- Do not raise pool size merely to mask slow queries or long transactions.
- Cap concurrent bulk jobs at the application layer.
- Set sensible acquire and query timeouts.

For instance, if the database permits 200 connections and the application runs 4 replicas, setting `maxSize=100` per replica can exceed the limit when all replicas peak together. Calculate total connections across all replicas and sibling services, not a single pod's config.

## 12. Do not assume concurrent statements are safe inside one transaction

Spring reactive transactions typically bind a single connection to the transaction context. If inside a transaction you use `flatMap` to issue concurrent statements on that same connection, the driver may not support multiple concurrent statements on one connection; some drivers throw errors, some serialize internally, and others behave differently.

Code requiring caution:

```java
transactionalOperator.transactional(
    Flux.fromIterable(rows)
        .flatMap(repository::save, 8)
        .then());
```

This snippet can trigger concurrent save operations within the same reactive transaction. Do not assume this is universally supported by drivers or faster. For all-or-nothing transactions, the safe and predictable default is serializing statements with `concatMap`, unless you have explicitly verified driver/database support for concurrency on a single transaction connection.

If running multiple independent transactions concurrently, each transaction needs its own connection/resource, and you must account for pool capacity, isolation, deadlocks, partial success, and idempotency. You cannot achieve a single atomic transaction by running multiple transactions in parallel.

## 13. Batch writes with buffer

When the source has many records, group them into chunks:

```java
Mono<Void> saveInChunks(Flux<Customer> customers) {
    return customers
        .buffer(500)
        .concatMap(batch -> saveBatch(batch))
        .then();
}
```

`buffer(500)` collects up to 500 elements into a `List` before emitting a batch. `concatMap` processes batches sequentially so the next batch starts only after the previous one finishes.

Chunking helps:

- Bound the number of items held in memory.
- Reduce coordination overhead compared to single-item operations if `saveBatch` genuinely uses batch SQL.
- Establish checkpoint/commit boundaries if each chunk runs in its own transaction.
- Size chunks to fit bind parameter and payload limits.

However, `buffer(500)` by itself does not turn 500 `save` calls into one SQL statement. If `saveBatch` internally runs `concatMap(repository::save)`, it can still emit 500 statements; the benefit then lies in batch/checkpoint management rather than reducing round-trips.

## 14. Choosing batch size

Too-small batches cause excessive round-trips and overhead. Too-large batches can:

- Exceed driver/database bind parameter limits.
- Generate huge SQL statements.
- Increase memory for inputs, bind values, and results.
- Hold transactions and locks too long.
- Make retrying a failed batch expensive.
- Increase rollback duration and database log pressure.

No single batch size fits every system. Measure based on column count, data size, driver limits, query plans, network latency, and transaction duration. Start with a moderate batch size and tune via benchmarks and metrics.

If payloads include a large JSON or binary column, rows per batch should be smaller than for a table with only a few numeric or short columns. Batch sizes should be configurable and validated, never accepting arbitrarily large values from client requests.

## 15. One transaction for the entire batch or per chunk?

The two models have distinct semantics:

**One transaction for the entire dataset**

```java
Mono<Void> importAtomically(List<Customer> customers) {
    return transactionalOperator.transactional(
        Flux.fromIterable(customers)
            .concatMap(customerRepository::save)
            .then());
}
```

If one record fails, the whole transaction rolls back. This works when dataset sizes are moderate and all-or-nothing is required. For very large imports, long transactions can hold locks, connections, and transaction logs too long.

**One transaction per chunk**

```java
Mono<Void> importByChunks(Flux<Customer> customers) {
    return customers
        .buffer(500)
        .concatMap(batch -> transactionalOperator.transactional(
            saveBatch(batch)))
        .then();
}
```

Each chunk commits independently. If chunk 4 fails, the first three chunks remain committed. Checkpoints, import status tracking, idempotency, and resume logic are required to avoid duplicates on rerun.

Never describe a chunked import as atomic for the whole file. Make the contract explicit: whether the entire batch or each chunk is the unit of success.

## 16. Using Statement.add when the driver supports batching

The R2DBC SPI offers `Statement.add()` to append the current binding set to a batch statement. Support and effectiveness depend on the driver. Conceptual example with positional bind markers:

```java
Mono<Void> insertBatch(List<CustomerRow> rows) {
    return Mono.usingWhen(
        connectionFactory.create(),
        connection -> {
            Statement statement = connection.createStatement(
                "INSERT INTO customer (id, display_name) VALUES ($1, $2)");

            for (int i = 0; i < rows.size(); i++) {
                CustomerRow row = rows.get(i);
                statement.bind(0, row.id())
                    .bind(1, row.displayName());

                if (i < rows.size() - 1) {
                    statement.add();
                }
            }

            return Flux.from(statement.execute())
                .flatMap(Result::getRowsUpdated)
                .then();
        },
        Connection::close);
}
```

This example uses PostgreSQL-style placeholders (`$1`, `$2`) and 0-based bind indices; markers must be adapted per driver/database. `Statement.add()` appends the current binding set to the batch and allows setting the next binding set under R2DBC SPI semantics.

Before using in production, confirm the driver supports `add()` for that statement, understand how the driver emits `Result`/rows updated, and test what happens when one batch element violates a constraint. Not all drivers execute batches identically or yield the same speedup.

`DatabaseClient` is a convenient abstraction for SQL and mapping, though you should not assume every `DatabaseClient` call turns a list of bindings into a single batch statement. When SPI batching is required, `Connection`/`Statement` can be used directly inside an adapter with explicit cleanup and proper transaction manager integration.

## 17. Multi-row INSERT

Another option is inserting multiple value tuples in one statement if supported by the database:

```sql
INSERT INTO customer (id, display_name, status)
VALUES
    (:id1, :name1, :status1),
    (:id2, :name2, :status2),
    (:id3, :name3, :status3);
```

This reduces round-trips and parse/execute overhead compared to separate statements. However:

- Syntax and value/bind-marker limits depend on the database.
- Columns times rows increases bind parameter count.
- Generated values may require specific return mechanisms.
- Row order in `RETURNING`/`OUTPUT` results should not be assumed unless guaranteed by the database.
- One constraint failure can fail the whole statement; exact semantics must be verified.

To match generated IDs to inputs, use client-generated keys or a stable correlation key returned with each row. Do not correlate results by list position unless the database/driver guarantees matching order.

## 18. Set-based UPDATE instead of many individual UPDATEs

When many rows need the same conditional change, a single set-based SQL statement is usually far more efficient than many update statements:

```sql
UPDATE customer
SET status = :newStatus,
    modified_at = :modifiedAt
WHERE tenant_id = :tenantId
  AND status = :oldStatus;
```

The database updates all matching rows in one statement. Use `rowsUpdated()` to check the affected row count and verify it falls within expected business bounds.

If each row needs a distinct new value, use batch statements, a staging table followed by a joined update, or a `CASE`/`VALUES` statement as supported by the database. Choose based on dialect and dataset size.

Do not use a set-based update if each row requires individual validation or authorization that SQL cannot express. Performance must not come at the expense of skipping business rules.

## 19. Ordering with foreign keys and constraints

When a child table references a parent table, ensure the parent exists before the child unless the database supports deferred constraints and the transaction is designed accordingly.

A common sequence:

```java
Mono<Void> saveAggregate(Order order, List<OrderLine> lines) {
    return orderRepository.save(order)
        .flatMap(saved ->
            Flux.fromIterable(lines)
                .map(line -> line.withOrderId(saved.getId()))
                .concatMap(orderLineRepository::save)
                .then());
}
```

When multiple parents are independent, each aggregate can be processed with bounded concurrency:

```java
Mono<Void> saveAggregates(Flux<OrderWithLines> aggregates) {
    return aggregates.flatMap(aggregate ->
        transactionalOperator.transactional(
            saveAggregate(aggregate.order(), aggregate.lines())),
        4);
}
```

Each aggregate gets its own transaction in this example, with up to four aggregates running concurrently. This allows independent aggregates to run in parallel while parent/child operations inside each aggregate stay sequential.

If the entire list of aggregates must be atomic, do not give each aggregate its own transaction; wrap the entire chain in one transaction, weighing transaction duration and sequential execution.

## 20. Writing across multiple tables sequentially with then

When steps form a clear dependency chain, `then` expresses ordering cleanly:

```java
Mono<Void> createOrderGraph(Order order,
                            List<OrderLine> lines,
                            OrderAudit audit) {
    return orderRepository.save(order)
        .flatMap(saved ->
            saveLines(saved.getId(), lines)
                .then(saveAudit(saved.getId(), audit)))
        .then();
}
```

`saveLines` must finish before `saveAudit`. If `saveLines` errors, `saveAudit` never runs. Wrap the entire chain in a transaction if all tables must commit or roll back together.

Do not use `Mono.when` for dependent steps because `when` subscribes to all publishers simultaneously. `Mono.when` fits independent tasks waiting for all to finish, though concurrency on a single transaction connection must still be considered.

## 21. Error handling with concatMap and flatMap

By default, when an inner publisher errors, `concatMap` or `flatMap` terminates the chain and cancels related subscriptions per Reactor semantics. However, other database operations may already have completed or be in flight; cancellation cannot undo an already-committed transaction.

**Sequential outside a transaction:** if record 5 fails, records 1–4 may already be committed. Record 6 onward is not processed after the terminal error.

**Concurrent outside a transaction:** when one inner publisher fails, some other operations may already be committed, others running or canceled. Never assume all other operations rolled back.

**Inside a shared transaction:** if the error propagates out of the transaction publisher, the transaction can roll back all participating operations. This relies on all operations truly sharing the same transaction context/connection.

Decide explicitly between all-or-nothing and partial success before selecting operators.

## 22. Avoid using onErrorContinue to arbitrarily skip write errors

`onErrorContinue` has operator-dependent semantics and can obscure which elements failed. In persistence code, skipping an error can leave missing data while the pipeline reports completion.

If business rules permit each record to succeed or fail independently, model the outcome explicitly:

```java
Flux<WriteResult> results = records.flatMap(record ->
    repository.save(record)
        .map(saved -> WriteResult.success(record.id()))
        .onErrorResume(error -> Mono.just(
            WriteResult.failure(record.id(), classify(error)))),
    8);
```

This turns per-record errors into `WriteResult` objects so the pipeline can proceed. It fits when each record has an independent transaction/commit and partial success is acceptable. Never put `onErrorResume` inside an all-or-nothing transaction if turning errors into success causes the transaction to commit incomplete data.

Record failed record IDs, stable error codes, and retry/resume mechanics. Do not log sensitive record payloads in error logs.

## 23. Retries and idempotency in multi-record writes

Retrying a write can create duplicate records if the first attempt committed while the response was lost. This is especially critical when failure occurs after the database executed the command or the connection dropped before the client got the reply.

Safeguards:

- Use business keys/unique constraints to block duplicates.
- Use idempotency keys per command or batch/chunk.
- Design upsert/insert operations matching database semantics and test under concurrency.
- Save checkpoints after each chunk commits.
- Retry the entire transaction on transient transaction errors rather than retrying a single step relying on stale state.
- Do not retry validation, foreign key, or permission errors as if they were transient.

When retrying an entire transaction, use `Mono.defer` so each retry creates a fresh publisher and transaction:

```java
Mono<Void> writeTransaction(List<Row> batch) {
    return Mono.defer(() ->
        transactionalOperator.transactional(
            Flux.fromIterable(batch)
                .concatMap(repository::save)
                .then()))
        .retryWhen(retryTransientTransactionFailure());
}
```

Retries must have attempt limits, backoff, and error filters. For previously committed chunks, idempotency/checkpoints must guarantee reruns do not write duplicates.

## 24. Deadlocks and lock ordering

High concurrency can cause multiple transactions to update the same set of rows in opposite orders. For example, transaction T1 locks account A then B, while T2 locks B then A; both wait on each other and the database detects a deadlock.

To reduce deadlocks:

- Acquire locks in a consistent key order, such as sorting account IDs ascending.
- Index update predicates to avoid wide table/range scans and locks.
- Keep transactions short.
- Never make HTTP/broker calls or wait on user input while holding a transaction or locks.
- Limit concurrent operations touching the same key/aggregate.
- Selectively retry deadlock/serialization errors with backoff.

Deadlocks cannot be completely eliminated just by using `concatMap` in one request; concurrent requests and other services can still contend on the same data. Database constraints and concurrency strategies must protect system-wide invariants.

## 25. Partitioning concurrency by key instead of globally

Some workloads require preserving order per customer/account while still processing many customers concurrently. Partition data by a stable key and serialize within each partition.

Conceptual example:

```java
events.groupBy(Event::accountId)
    .flatMap(group -> group.concatMap(eventRepository::save), 12);
```

This maintains ordering within each group in one subscription. However, if two pods receive events for the same account, each pod can still run part of the stream in parallel. For system-wide guarantees, partition the message broker by account ID or use optimistic versioning/conditional updates and unique constraints in the database.

Avoid `groupBy` over unbounded key cardinality without evaluating lifecycle and buffering. For very large aggregate counts, fixed partition counts or broker partitions are easier to manage.

## 26. Batching and generated value ordering

When inserting many rows and the database returns generated IDs, do not assume the first ID belongs to the first input item and the second to the second, unless the database/driver API explicitly guarantees that order.

Solutions:

- Generate IDs in the application before inserting if domain rules permit.
- Supply a unique `client_reference`/correlation key and retrieve it alongside the ID.
- Use `RETURNING`/`OUTPUT` with an explicit reference column when supported by the engine.
- Re-query by unique business key/correlation key.
- Do not pair results solely by list position if return order is not guaranteed.

Even when sequences/identities increase over time, ID values are not a business ordering contract. Rollbacks and concurrency can leave gaps or yield unexpected orderings.

## 27. Backpressure and pending items in flight

Reactive Streams coordinate demand, yet operators can still buffer elements. `flatMap` has concurrency and prefetch; `buffer` holds chunks; `collectList` holds all results. If the source emits faster than the database writes, queues/buffers grow and consume memory.

Guidelines:

- Use demand-driven sources whenever possible.
- Specify concurrency and prefetch explicitly.
- Use `buffer(n)` with bounded sizes.
- Avoid `collectList()` on large or unbounded sources.
- Never use unbounded `onBackpressureBuffer()` to hide a slow database.
- Monitor pending items, queue depth, and processing times.

Backpressure propagates demand within a pipeline; it does not replace caps on concurrent bulk jobs or system-wide resource limits.

## 28. Separating CPU work from database writes

If each record needs CPU-heavy transformation or validation, do not assume all work should share one thread or carelessly use `parallel()` followed by database calls. R2DBC drivers have their own scheduler/connection behavior; never inject blocking JDBC calls into reactive chains.

Pure validation can run before opening a transaction or on an appropriate CPU scheduler while preserving required order and context. When switching schedulers, Reactor Context generally propagates across Reactor operators, though custom `ThreadLocal`-based mechanisms may not work as expected.

Do not use `parallel()` as an automatic database throughput booster. Parallel rails do not give the database extra connections or CPU; they only change pipeline scheduling. For I/O, bounded `flatMap` concurrency usually expresses intent much more clearly.

## 29. Evaluating saveAll and actual implementation behavior

Repositories may expose `saveAll(Iterable)` or `saveAll(Publisher)`. These are convenient APIs for submitting multiple entities, though you should not assume a `saveAll` call always becomes one SQL batch or uses identical execution order across all Spring Data/driver versions.

Determine:

- Does the current implementation use `concatMap`, `flatMap`, or another mechanism?
- Does the driver support batch statements?
- How are generated values returned?
- Where does the transaction boundary sit?
- If one entity fails, have earlier entities already committed?
- Is output order guaranteed?

When exact ordering or batch behavior is required, compose it explicitly in your service/adapter or use a verified driver API. Never infer performance semantics merely from the name `saveAll`.

## 30. Bounded-concurrency chunked import pattern

Example importing many independent customers, each chunk in its own transaction, with up to three chunks running concurrently:

```java
Mono<Void> importCustomers(Flux<Customer> source) {
    return source
        .buffer(250)
        .flatMap(batch ->
            transactionalOperator.transactional(
                saveBatchSequentially(batch)),
            3)
        .then();
}

Mono<Void> saveBatchSequentially(List<Customer> batch) {
    return Flux.fromIterable(batch)
        .concatMap(customerRepository::save)
        .then();
}
```

In this example:

- Each chunk has at most 250 items.
- Items within a chunk are written sequentially.
- Each chunk has its own transaction.
- Up to three chunk transactions are subscribed concurrently.
- A failing chunk rolls back only itself; other chunks may have committed or still be running.

This pattern fits only when chunks are independent and partial success across chunks is acceptable. If all 10,000 records must succeed or roll back together, use a single enclosing transaction and weigh long-transaction costs; do not use per-chunk transactions.

Inside one reactive transaction, the driver may limit concurrent statements on the same connection. Here, operations inside each chunk are serialized. Independent chunks with separate transactions/connections run concurrently, depending on the transaction manager, pool, and driver.

## 31. Ordered fail-fast write pattern

If a batch needs strict ordering and all-or-nothing semantics:

```java
Mono<Void> writeOrderedAtomically(List<ImportRow> rows) {
    return transactionalOperator.transactional(
        Flux.fromIterable(rows)
            .concatMap(row -> validate(row)
                .then(repository.save(mapToEntity(row))))
            .then());
}
```

`concatMap` ensures the next row runs only after the prior row completes. If validation or save signals an error, the chain stops and the transaction rolls back. Keep transactions short and bound import size to avoid holding connections/locks too long.

If validation can run completely outside the transaction, validate beforehand to avoid holding a transaction open during pure checks. Database-dependent invariants must still be verified inside the transaction.

## 32. Independent writes with configurable concurrency

Concurrency can come from application configuration, validated with min/max bounds:

```yaml
app:
  bulk-write:
    concurrency: 6
    batch-size: 250
```

```java
@ConfigurationProperties(prefix = "app.bulk-write")
public record BulkWriteProperties(int concurrency, int batchSize) {
    public BulkWriteProperties {
        if (concurrency < 1 || concurrency > 32) {
            throw new IllegalArgumentException("Invalid bulk concurrency");
        }
        if (batchSize < 1 || batchSize > 2000) {
            throw new IllegalArgumentException("Invalid batch size");
        }
    }
}
```

The limits `32` and `2000` are illustrative examples, not universal optima. Set bounds according to your pool, database, workload, and benchmarks. Never let clients pass arbitrary concurrency values that could exhaust resources.

Using the configuration:

```java
Mono<Void> saveAll(Flux<Customer> source) {
    return source
        .flatMap(customerRepository::save,
            properties.concurrency())
        .then();
}
```

If system-wide limits are required, per-subscription configuration is not enough; add a service/job-runner bulkhead or queue.

## 33. Measuring throughput and tuning concurrency

Do not pick concurrency by guesswork. Benchmark ascending small steps such as 1, 2, 4, 8, and 16 under identical data conditions.

Monitor:

- Total batch write time and records/second.
- p50/p95/p99 latency per operation.
- Connection pool active/idle/pending counts and acquire timeouts.
- Database CPU, I/O, lock waits, and deadlock counts.
- Constraint/timeout/serialization error counts.
- Heap, GC, and buffered item counts.
- Transaction durations and affected row counts.

If increasing concurrency fails to increase throughput while lock waits, pending acquires, or timeouts climb, you have passed the point of diminishing returns. If the database has spare capacity while the pool is tiny, tuning the pool may help; if the database is saturated, raising pool size or concurrency makes things worse.

## 34. Observing ordering and errors in production

When bulk writes misbehave, logs/metrics should answer:

- Which batch/import ID is running?
- Which chunk number and size?
- What is the configured concurrency?
- How many records succeeded/failed?
- What are connection wait and query durations?
- Are there deadlocks, lock timeouts, or serialization failures?
- What was the last committed checkpoint?
- Were retries attempted, and how many?

Do not log full records or bound values containing sensitive data. Log batch IDs, safe record IDs, operation names, and classified error categories.

## 35. Testing ordering with StepVerifier

With mock publishers, you can demonstrate that `concatMap` emits results in order:

```java
StepVerifier.create(
        Flux.just(1, 2, 3)
            .concatMap(value -> Mono.delay(Duration.ofMillis(10))
                .thenReturn(value)))
    .expectNext(1, 2, 3)
    .verifyComplete();
```

With `flatMap`, do not write tests assuming results always preserve source order when inner publishers finish at varying times. To test concurrency, use publishers whose completion timing you control, such as `TestPublisher`, and assert the maximum concurrent inner subscriptions.

Publisher tests only verify Reactor semantics. They do not prove the database commits in the same order; that requires integration tests against the database/driver inspecting final state.

## 36. Testing bounded concurrency

You can use counters in tests to confirm no more than N inner publishers are active at once:

```java
AtomicInteger active = new AtomicInteger();
AtomicInteger maxActive = new AtomicInteger();

Flux<Integer> work = Flux.range(1, 100)
    .flatMap(value -> Mono.defer(() -> {
        int current = active.incrementAndGet();
        maxActive.accumulateAndGet(current, Math::max);

        return Mono.delay(Duration.ofMillis(5))
            .thenReturn(value)
            .doFinally(signal -> active.decrementAndGet());
    }), 4);

StepVerifier.create(work)
    .expectNextCount(100)
    .verifyComplete();

assertThat(maxActive.get()).isLessThanOrEqualTo(4);
```

This is a Reactor pipeline test that does not hit a database. It verifies the concurrency cap within one subscription. Separate integration tests are needed to measure connection pool and database load.

## 37. Testing atomicity and partial success

For an all-or-nothing transaction:

1. Prepare multiple valid rows and one row intentionally violating a constraint.
2. Execute the batch inside a single transaction.
3. Verify the publisher emits an error.
4. Query the database in a separate transaction.
5. Verify no rows from the batch committed.

For chunked transactions:

1. Prepare multiple chunks and inject a failure in a specific chunk.
2. Run the import with the chosen ordering/concurrency policy.
3. Verify which chunks committed and which rolled back.
4. Confirm checkpoints accurately reflect committed chunks.
5. Rerun the job and confirm no duplicates are created.

Do not use mocked repositories to draw conclusions about real database rollbacks. Integration tests against the real R2DBC driver and database engine are required.

## 38. Testing parent/child dependency ordering

Write a test where children reference a parent ID generated on insert. Verify:

- The parent is written before the children.
- Children receive the exact parent ID from the returned entity.
- If the parent insert fails, zero children are written.
- If a child fails inside a shared transaction, the parent and earlier children roll back.
- If each child/aggregate has its own transaction, partial success matches the contract.

Do not check only that the returned list is ordered. Query the database with `ORDER BY`/foreign keys to confirm actual persisted state.

## 39. Anti-patterns to avoid

| Anti-pattern | Problem | Resolution |
|---|---|---|
| Using default `flatMap` for all bulk writes | Unclear concurrency and ordering | Choose operator and concurrency explicitly. |
| Using `flatMapSequential` to enforce write order | Side effects can still run concurrently | Use `concatMap`. |
| Raising concurrency very high | Exhausts pool, increases lock contention and memory | Measure and cap within capacity. |
| Assuming concurrency 8 is application-wide | Each request has its own subscription | Use a global bulkhead/queue if needed. |
| Concurrent statements in one transaction without checking driver | Driver may not support concurrency on one connection | Serialize or verify support via integration tests. |
| Using `buffer` and assuming SQL batching | Buffer only groups items | Use multi-row SQL/`Statement.add` if driver-supported. |
| One giant transaction for a huge import | Locks, logs, and connections held too long | Chunk transactions and checkpoint if partial commit is allowed. |
| Chunked transactions while claiming all-or-nothing | Earlier chunks may already be committed | Document partial success or use a shared transaction. |
| Retrying individual non-idempotent statements | Can write duplicates | Retry full transactions and enforce idempotency. |
| Relying on natural SELECT order | Not guaranteed by databases | Use deterministic `ORDER BY`. |
| Pairing generated IDs by batch position | Result order may not be guaranteed | Use a stable correlation key. |
| `onErrorContinue` to hide write errors | Missing data while job reports success | Emit explicit per-record outcomes. |
| `collectList()` on large sources | High heap consumption | Use bounded buffering/streaming. |

## 40. Workflow for choosing operators and concurrency

Before writing bulk persistence logic, answer in order:

1. Are records independent, or do parent/child/aggregate dependencies exist?
2. Which ordering is required: start, completion, commit, or emission order only?
3. Must the whole batch be atomic, or may individual records/chunks commit independently?
4. Can set-based SQL, multi-row inserts, or batch statements replace many round-trips?
5. If sequential is needed, use `concatMap`/`then`; if independent, use `flatMap` with explicit concurrency.
6. If ordered output is needed for independent operations, consider `flatMapSequential` while remembering it does not serialize side effects.
7. If per-key order is needed, serialize within each aggregate and protect across instances via database/broker.
8. Tune batch size, concurrency, and prefetch for pool/database capacity.
9. Define error handling, retries, idempotency, checkpoints, and partial success.
10. Test ordering, concurrency, rollbacks, and generated values against the real driver and database.

## 41. Implementation conclusion

In Spring Data R2DBC, `concatMap` is the clear choice when a later write must await the previous one; `flatMap` fits independent writes with bounded concurrency; `flatMapSequential` preserves output emission order only while allowing side effects to run concurrently. `buffer` splits data into chunks but does not create a SQL batch on its own. For true batching, use multi-row SQL or R2DBC `Statement.add()` when supported by the driver.

Concurrency must be controlled both per subscription and system-wide. Inside a reactive transaction, statements typically share a connection context; never assume multiple statements can safely execute concurrently on the same connection. When atomicity is needed, compose operations within one transaction on the proper `ConnectionFactory`, usually serializing dependent statements. When splitting transactions per chunk, accept partial commits and implement checkpoints/idempotency for resume. Finally, databases do not guarantee row read order without `ORDER BY`; store business ordering keys and query deterministically. Combining the right operators, bounded batches, clear transactions, and real-database concurrency testing delivers high-throughput bulk writes while preserving data invariants.
