# Role of Identity in Insert, Update, and Save

In Spring Data R2DBC, an identifier (ID) identifies a row of data and usually serves as the basis for Spring Data to know whether an entity is newly created or already exists. When calling `save(entity)` on a reactive repository, Spring Data uses the entity's new/existing state to choose between an insert or an update operation. Therefore, the ID value directly affects data-saving behavior.

An important point is that `save` does not, by default, query the database to check whether a row exists before deciding. Under its new-entity detection mechanism, Spring Data typically relies on a `@Version` property if present, and otherwise on the `@Id` property; an entity can also define its own state using `Persistable.isNew()`. Understanding this rule helps avoid situations where an entity with a pre-assigned ID is treated as a record that needs an update.

## 1. What Does an ID Represent?

In a relational database, a primary key uniquely identifies a row in a table. In a Spring Data R2DBC entity, the property annotated with `@Id` maps to that primary key.

Example customer table:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

Corresponding entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
```

`@Id` tells Spring Data which property is the entity's identifier. With database-generated keys, the application can create a new entity with `id = null`; after inserting, the database generates the key and Spring Data returns an entity populated with the ID.

An identifier can be an auto-incrementing number, a UUID, or another type compatible with the schema and driver. What matters is that the ID generation rules stay consistent between the application and the database.

## 2. How Do Insert and Update Differ?

**Insert** creates a new row in a table. The database can generate the ID automatically if the primary key column is configured as identity/sequence or an equivalent mechanism.

**Update** modifies an already identified row, usually with a condition based on the primary key. The ID is used to locate the row to update.

SQL examples:

```sql
INSERT INTO customer (name, email)
VALUES ('An', 'an@example.com');

UPDATE customer
SET name = 'An Nguyen'
WHERE id = 42;
```

Insert creates a new record and can receive a generated ID. Update targets a record that already has an ID. If the update condition matches no rows, data is not automatically created just because the update could not find a record.

In Spring Data R2DBC, `insert` and `update` are two distinct operations. The repository's `save` method selects one of the two based on entity state.

## 3. How ReactiveCrudRepository.save() Chooses Insert or Update

A typical repository:

```java
public interface CustomerRepository
        extends ReactiveCrudRepository<Customer, Long> {
}
```

`ReactiveCrudRepository` provides the method:

```java
<S extends T> Mono<S> save(S entity);
```

Conceptually, Spring Data performs:

```text
save(entity)
    |
    v
Determine whether the entity is new
    |
    +---- new entity ------> INSERT
    |
    +---- existing entity -> UPDATE
    |
    v
Return publisher containing the saved entity
```

Default rules for detecting a new entity:

1. If the entity has a `@Version` property, Spring Data uses the version value to determine new/existing state.
2. If there is no version property, Spring Data checks the ID property.
3. If a custom rule is needed, the entity can implement `Persistable` and provide `isNew()`.

With an object-type ID such as `Long`, `null` generally indicates a new entity; a non-null ID indicates an existing entity. With a primitive ID, a default value such as `0` may be used to detect a new entity. Using a wrapper type such as `Long` usually makes the "no ID yet" state clearer.

If the entity has `@Version`, version state takes precedence in the detection mechanism. With a wrapper version, `null` indicates a new entity; after saving, Spring Data manages the version for subsequent updates.

## 4. Insert When the ID Has Not Been Assigned

With a database-generated primary key, a new entity usually has a null ID:

```java
Customer newCustomer = new Customer(
        null,
        "An",
        "an@example.com"
);

Mono<Customer> savedPublisher = customerRepository.save(newCustomer);
```

Because the ID is missing, the entity is detected as new and `save` takes the insert branch. When the publisher is subscribed to and the insert succeeds, the database generates the ID.

Use the entity emitted by the publisher:

```java
return customerRepository.save(newCustomer)
        .doOnNext(saved -> log.info(
                "Created customer with id {}", saved.id()
        ));
```

With an immutable entity such as a Java record, Spring Data may create a new instance containing the generated ID rather than mutating the original instance. Therefore, do not ignore the emitted value and continue using the input object assuming its ID was updated.

A complete service example:

```java
public Mono<Customer> createCustomer(String name, String email) {
    Customer customer = new Customer(null, name, email);
    return customerRepository.save(customer);
}
```

The service returns `Mono<Customer>`; the controller or downstream caller receives the saved entity once the publisher completes.

## 5. Update When the ID Already Has a Value

When an entity has a non-null ID and no other detection rule applies, Spring Data typically treats the entity as existing:

```java
Customer changedCustomer = new Customer(
        42L,
        "An Nguyen",
        "an@example.com"
);

Mono<Customer> updatedPublisher =
        customerRepository.save(changedCustomer);
```

In this case, `save` takes the update branch. The ID `42` is used to identify the row to update.

That means a non-null ID only tells Spring Data that the entity is considered existing under the detection rules; it does not prove that a corresponding row actually exists in the database.

If the ID matches no rows, `save` does not automatically fall back to insert to create a new row. Exact behavior when an update affects zero rows depends on the operation, versioning, and access layer being used. For an entity with `@Version`, failing to update the expected row is typically reported as an optimistic locking failure.

Therefore, do not treat `save` as a SQL upsert meaning "update if present, insert if absent." It chooses insert or update based on entity state on the application side.

## 6. Summary Table of Detection Rules

| Entity State | Default Rule | `save` Branch |
| --- | --- | --- |
| No `@Version`, `Long` ID is null | New entity | Insert |
| No `@Version`, `Long` ID is non-null | Existing entity by ID state | Update |
| Has `@Version Long`, version is null | New entity | Insert |
| Has `@Version Long`, version has a value | Existing entity by version | Update |
| Implements `Persistable` | Based on `isNew()` result | Insert or update per custom rule |

The table above describes typical detection behavior. When using version or `Persistable`, make sure you understand the state of that property and update it properly after saving.

## 7. Role of @Version in Save

The ID identifies the row to update, while the version helps detect concurrent updates. This is optimistic locking.

Example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("inventory_item")
public record InventoryItem(
        @Id Long id,
        String name,
        int quantity,
        @Version Long version
) {}
```

For a new entity:

```java
InventoryItem item = new InventoryItem(
        null,
        "Keyboard",
        10,
        null
);

return inventoryRepository.save(item);
```

A null version indicates a new entity under the version-based rule. When the insert succeeds, Spring Data initializes the version. When updating, the version is incremented and used to protect the operation from overwriting changes from another transaction.

A versioned update is generally equivalent in intent to:

```sql
UPDATE inventory_item
SET quantity = 9,
    version = 4
WHERE id = 10
  AND version = 3;
```

The `version = 3` condition ensures the row is still at the version the application read. If another transaction already updated the row and changed the version to 4 beforehand, the stale update no longer matches. Spring Data detects that the expected row was not updated and raises an optimistic locking error instead of silently overwriting.

The specific version values in this example are for illustration only. Use the entity returned after each save because Spring Data may return an instance containing the new version, especially for immutable entities.

### Do Not Discard the Returned Version

Suppose the application reads an entity with version 3, saves changes, and receives a new entity with version 4. If a subsequent update still uses the old object with version 3, optimistic locking may reject the operation. Therefore:

```java
return inventoryRepository.findById(id)
        .switchIfEmpty(Mono.error(new InventoryItemNotFoundException(id)))
        .map(item -> new InventoryItem(
                item.id(),
                item.name(),
                item.quantity() - 1,
                item.version()
        ))
        .flatMap(inventoryRepository::save);
```

The `save` publisher emits the entity containing the new version. The caller must retain that result if it performs further version-based operations.

## 8. Pre-Assigned IDs and the New-Entity Detection Problem

Not every application uses auto-generated IDs. Many systems generate UUIDs on the application side before inserting:

```java
UUID id = UUID.randomUUID();
Customer customer = new Customer(id, "An", "an@example.com");
return customerRepository.save(customer);
```

If the entity has no `@Version` and uses the default ID-based rule, a non-null ID causes Spring Data to treat the entity as existing. `save` may choose update even though that UUID row has never been inserted.

This is something to watch out for when using assigned IDs. There are several ways to solve it:

- Use a wrapper `@Version` and leave the version null on new entities, if versioning fits the data model.
- Implement `Persistable<ID>` to supply the new/existing state yourself.
- Use an explicit insert operation via `R2dbcEntityTemplate` when business logic knows it is creating a new record.

Do not set the ID to null just to force an insert if the ID is a required business identifier and the database does not generate it.

## 9. Using Persistable to Define isNew() Yourself

`Persistable<ID>` lets an entity supply its ID and new/existing state via `getId()` and `isNew()`. This is useful when the ID is assigned before inserting but the application still needs `save` to take the insert branch.

Example of an entity with an application-assigned UUID:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_customer")
public class ExternalCustomer implements Persistable<UUID> {

    @Id
    private final UUID id;

    private final String name;

    @Transient
    private boolean newEntity;

    @PersistenceCreator
    public ExternalCustomer(UUID id, String name) {
        this.id = id;
        this.name = name;
        this.newEntity = false;
    }

    public static ExternalCustomer newCustomer(UUID id, String name) {
        ExternalCustomer customer = new ExternalCustomer(id, name);
        customer.newEntity = true;
        return customer;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markNotNew() {
        this.newEntity = false;
    }
}
```

In this example:

- The ID is assigned right when creating the object via the `newCustomer(...)` factory.
- `isNew()` returns true to indicate that the entity needs to be inserted.
- `@Transient` prevents the internal `newEntity` state from becoming a database column.
- After a successful insert, the state must transition to false so subsequent saves are detected as updates.

The constructor annotated with `@PersistenceCreator` sets the default state to false when Spring Data reconstructs the entity from a stored row. The `newCustomer(...)` factory enables the new state only for objects created to be inserted.

The application must manage the timing of the state transition consistently. With a simple mutable model, it can be updated after `save` completes:

```java
return externalCustomerRepository.save(customer)
        .doOnNext(ExternalCustomer::markNotNew);
```

This illustrates the `Persistable` mechanism; in a real project, ensure the new/existing state is also restored properly when the entity is reloaded from the database. An entity read from the database must be treated as an existing entity. You can use callbacks or entity factories to set the appropriate state according to the application lifecycle.

Do not implement `isNew()` based solely on a flag that is always true without a mechanism to transition the state after insert. If the flag does not change, subsequent saves may keep taking the insert branch and cause duplicate primary key errors.

## 10. Choosing Explicit Insert or Update with R2dbcEntityTemplate

Repository `save` is convenient when you want Spring Data to decide insert or update based on entity state. If business logic already knows clearly whether it is creating or updating, you can use `R2dbcEntityTemplate` to express the operation explicitly.

Insert example:

```java
public Mono<Customer> insertCustomer(Customer customer) {
    return template.insert(customer);
}
```

Update example:

```java
public Mono<Customer> updateCustomer(Customer customer) {
    return template.update(customer);
}
```

An explicit insert expresses the intent to create a new row; an explicit update expresses the intent to update an existing row. Be sure to use the right overload and mapping for the Spring Data Relational version in your project.

When updating only a few fields conditionally, you can use the template's fluent API or `DatabaseClient` with an explicit SQL statement. That avoids rewriting all properties of the entity when the use case only changes part of the data.

SQL update example:

```java
public Mono<Long> renameCustomer(Long id, String newName) {
    return databaseClient.sql("""
            UPDATE customer
            SET name = :name
            WHERE id = :id
            """)
            .bind("name", newName)
            .bind("id", id)
            .fetch()
            .rowsUpdated();
}
```

In this example, the updated row count is returned so the service can distinguish a row being updated from no matching row. `rowsUpdated()` returns a publisher of the number of affected rows; keep the exact type provided by the API version you are using.

## 11. Save Is Not Upsert

In SQL, upsert typically means insert if the row does not exist or update if it already exists, based on a defined key or constraint. Specific syntax depends on the database; for example, PostgreSQL has `INSERT ... ON CONFLICT ... DO UPDATE`.

`repository.save(entity)` does not perform that operation by default. It chooses insert or update based on the new/existing state determined by Spring Data.

For example, for an entity with ID 42:

- If the entity is detected as new, Spring Data performs an insert. If key 42 already exists, the database may report a primary key violation.
- If the entity is detected as existing, Spring Data performs an update. If no row with ID 42 exists, it does not automatically insert a new row.

If business logic genuinely needs an upsert by a unique key, use the database's native mechanism, appropriate constraints, and explicit SQL via `DatabaseClient` or a custom query method. Test the behavior carefully with the target database and driver.

## 12. SaveAll and the State of Each Entity

`ReactiveCrudRepository.saveAll(...)` accepts a collection of entities and returns a publisher of the saved entities:

```java
Flux<Customer> saveAllCustomers(List<Customer> customers) {
    return customerRepository.saveAll(customers);
}
```

Each entity must have the appropriate new/existing state. A list can contain both new entities with null IDs and existing entities with non-null IDs; Spring Data determines the save operation per entity state.

Do not assume `saveAll` is always equivalent to a single SQL bulk insert statement. Execution and optimization depend on the implementation, driver, and database. If you need bulk inserts with specific performance characteristics, consider appropriate batch APIs or SQL and benchmark against the target database.

For versioned entities, use the version values returned after saving. Reusing old objects with stale versions can cause subsequent updates to fail due to optimistic locking.

## 13. ID and Version During Concurrent Updates

An ID identifies a record, but by itself it does not prevent two requests from overwriting each other's data.

For example:

1. Request A reads row ID 42.
2. Request B also reads row ID 42.
3. Request A updates the name and commits.
4. Request B updates the email based on the stale data snapshot.

Without optimistic locking or an appropriate concurrency strategy, request B could unintentionally overwrite with stale values depending on how the update is constructed.

With `@Version`, an update can succeed only if the version in the database still equals the version the request read. The later request receives an optimistic locking error and can reload the data, inspect the conflict, and prompt the user to handle it.

Optimistic locking is suitable when conflicts are infrequent and you want to avoid long-lived pessimistic locks. It does not replace business validation or transactions; it simply detects certain cases where a record has changed since it was read.

## 14. Testing Insert, Update, and Save

An integration test suite should verify the state branches:

### Insert and Generated ID

```java
StepVerifier.create(customerRepository.save(
                new Customer(null, "An", "an@example.com")
        ))
        .assertNext(saved -> {
            assertNotNull(saved.id());
            assertEquals("An", saved.name());
        })
        .verifyComplete();
```

The test verifies that the publisher emits the entity after insert and that the returned entity has an ID.

### Update by ID

```java
StepVerifier.create(
        customerRepository.save(
                new Customer(existingId, "An Nguyen", "an@example.com")
        )
)
        .assertNext(saved -> {
            assertEquals(existingId, saved.id());
            assertEquals("An Nguyen", saved.name());
        })
        .verifyComplete();
```

This test assumes `existingId` was created beforehand and the corresponding row exists.

### Assigned ID

If using pre-assigned IDs, verify that `save` chooses insert via `Persistable.isNew()` or a null version. After insert, verify that the entity transitions to the existing state and the next save takes the update branch.

### Optimistic Locking

For an entity with `@Version`, read the same record twice, save one modified copy first, and then try saving the other copy with the stale version. Verify that the second operation receives an optimistic locking error. The test requires a real database or a test database that supports Spring Data R2DBC versioning behavior.

## 15. Common Pitfalls

1. **Thinking save always checks whether the row exists first.** Spring Data determines entity state from version, ID, or `Persistable`; do not treat save as an existence-check query followed by an upsert.
2. **Assigning a UUID before calling save and expecting automatic insert.** With the default ID-based rule, a non-null ID can cause the entity to be treated as existing.
3. **Ignoring the entity returned by save.** The auto-generated ID or new version may reside on the returned instance.
4. **Using ID to prevent concurrent updates.** The ID identifies the row; `@Version` supports optimistic locking.
5. **Using a primitive ID without understanding default values.** A wrapper type like `Long` clearly distinguishes null from an existing ID.
6. **Making `isNew()` always return true.** After insert, the state must transition so subsequent saves do not keep attempting inserts.
7. **Assuming an update that finds no row will insert automatically.** Update is not upsert.
8. **Using save to update a few fields without considering stale data.** Choose an update API or explicit SQL when controlled partial changes are needed.
9. **Assuming saveAll is always bulk SQL.** It is an API for saving multiple entities; the execution strategy depends on the implementation.
10. **Using the old version after a save.** Keep the returned entity to avoid optimistic locking errors with a stale version.

## Quick Selection Rules

- For database-generated IDs, initialize new entities with a null ID and use `save` to insert.
- For entities with an existing ID, use `save` to update according to the detection state.
- For pre-assigned IDs, configure new state using `@Version`, `Persistable.isNew()`, or use explicit insert.
- Use `@Version` when concurrent update detection is required.
- Use `R2dbcEntityTemplate.insert` or explicit SQL when you want to clearly express an insert operation.
- Use explicit update when business logic definitely modifies an existing row.
- Use native SQL upsert when the requirement is truly insert-or-update by a database constraint.
- Always use the entity emitted by the save publisher to retain the new ID or version.

In Spring Data R2DBC, the ID is a crucial part of persistence state: it identifies the row and participates in deciding whether an entity is new or existing. `save` uses entity state to choose insert or update; version and `Persistable` can alter the default detection. Understanding these rules helps applications handle auto-generated IDs, pre-assigned IDs, concurrent updates, and cases requiring explicit insert/update accurately.
