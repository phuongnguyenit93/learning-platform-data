# Coordinating Migrations with R2DBC Application Startup

## 1. Why Must Migrations Be Coordinated with Startup?

A Spring Data R2DBC application usually requires the database schema to exist before repositories and services begin handling requests. The schema includes tables, columns, primary keys, unique constraints, foreign keys, indexes, views, and other database objects that queries depend on.

In a development environment, a manual table-creation script might suffice for quick experiments. When the application is deployed repeatedly across multiple environments or multiple versions coexist, schema changes must be managed with tracked history and deterministic repeatability. This is the role of **database migration**.

Migrations are a versioned set of schema or data changes. A tool like Flyway or Liquibase reads the migrations, checks which changes have already been applied, and executes the remaining ones.

With an R2DBC application, two things must be coordinated:

1. Migrations must complete before the application executes queries depending on the new schema.
2. The runtime application must connect to the database through the R2DBC driver and ConnectionFactory.

An important point is that many popular migration tools like Flyway and Liquibase use JDBC to connect to the database, while the application's data access path can still use R2DBC. These two connection paths serve different responsibilities and can coexist in a single application.

## 2. Distinguishing Migrations from the Runtime R2DBC Connection

You can visualize the architecture as follows:

~~~text
                    Spring Boot startup
                            |
             +--------------+--------------+
             |                             |
             v                             v
      Migration subsystem            R2DBC runtime
      Flyway / Liquibase             Spring Data R2DBC
             |                             |
             v                             v
       JDBC DataSource                 ConnectionFactory
             |                             |
             v                             v
        JDBC Driver                    R2DBC Driver
             |                             |
             +--------------+--------------+
                            |
                            v
                      Same Database
                            |
                            v
                Schema / tables / indexes
~~~

The migration subsystem modifies the schema over JDBC. The R2DBC runtime reads and writes business data using a reactive driver.

| Component | Responsibility |
|---|---|
| Flyway or Liquibase | Manages and applies migrations |
| JDBC DataSource | Provides JDBC connections to the migration tool |
| JDBC driver | Communicates with the database over JDBC |
| R2DBC ConnectionFactory | Provides reactive connections to the application |
| R2DBC driver | Communicates with the database over the R2DBC SPI |
| Spring Data R2DBC | Maps entities and provides repositories/templates |
| Schema history/changelog | Records applied migrations |

Using JDBC for migrations does not switch the application to JDBC at runtime. The application can still use ReactiveCrudRepository, R2dbcEntityTemplate, and DatabaseClient for all normal data operations.

Conversely, declaring only an R2DBC driver does not automatically provide a JDBC driver for Flyway or Liquibase. If the migration tool requires JDBC, the classpath and configuration must include the corresponding JDBC driver.

## 3. Choosing a Schema Management Tool

### 3.1. Flyway

Flyway manages migrations by version and order. The common approach is creating SQL files following a naming convention:

~~~text
src/main/resources/
└── db/
    └── migration/
        ├── V1__create_customers.sql
        ├── V2__create_orders.sql
        ├── V3__add_customer_status.sql
        └── R__customer_active_view.sql
~~~

- Versioned migrations typically follow V1, V2, V3 and are applied in order.
- The descriptive name after two underscores helps readers understand the purpose.
- Repeatable migrations use the R prefix and re-run when their content changes according to Flyway's rules.
- Flyway records migration history in a schema history table, typically `flyway_schema_history` by default.

Example first migration:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
~~~

A subsequent migration can add a column:

~~~sql
ALTER TABLE customers
ADD COLUMN status VARCHAR(30) NOT NULL DEFAULT 'ACTIVE';
~~~

Once a migration has been applied in a shared environment, do not edit the old file to rewrite history. Create a new version instead. Editing an already-applied migration can cause checksum mismatches and trigger Flyway validation errors.

### 3.2. Liquibase

Liquibase manages changes via a changelog. Changelogs can be written in XML, YAML, JSON, or supported SQL formats.

Example structure:

~~~text
src/main/resources/
└── db/
    └── changelog/
        ├── db.changelog-master.yaml
        └── changes/
            ├── 001-create-customers.yaml
            └── 002-add-customer-status.yaml
~~~

A simple YAML changelog:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customers
      author: team
      changes:
        - createTable:
            tableName: customers
            columns:
              - column:
                  name: id
                  type: BIGINT
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: name
                  type: VARCHAR(150)
                  constraints:
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(320)
                  constraints:
                    nullable: false
~~~

Liquibase records executed changeSets in the `DATABASECHANGELOG` and `DATABASECHANGELOGLOCK` tables. The master changelog serves as the entry point for Liquibase to locate changeSets.

### 3.3. Do Not Run Two Migration Tools on the Same Schema Unintentionally

Flyway and Liquibase each manage schema history in their own way. If both automatically alter the same schema without a clear convention, the following can happen:

- Two unsynchronized sources of migration history.
- One tool unaware of changes made by the other.
- Difficulty determining change ordering.
- Difficulty recovering or auditing schemas across environments.

Normally, choose one tool as the primary schema management source per database/schema. If an organization has a reason to use multiple tools, establish explicit ownership boundaries, such as separate schemas and separate pipelines.

## 4. Configuring Flyway with Spring Data R2DBC

Suppose the application uses PostgreSQL. Gradle can declare dependencies as follows:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-r2dbc'

    runtimeOnly 'org.postgresql:r2dbc-postgresql'

    implementation 'org.flywaydb:flyway-core'
    runtimeOnly 'org.flywaydb:flyway-database-postgresql'
    runtimeOnly 'org.postgresql:postgresql'
}
~~~

Spring Boot dependency management should manage compatible versions. Depending on the Flyway version, a separate database module like `flyway-database-postgresql` may be a required dependency.

The two drivers serve different roles:

- `org.postgresql:r2dbc-postgresql` is the R2DBC driver for runtime.
- `org.postgresql:postgresql` is the JDBC driver for Flyway.

### 4.1. Configuring Both URLs

Example application.yml:

~~~yaml
spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
    username: shop_app
    password: change-me

  flyway:
    url: jdbc:postgresql://localhost:5432/shop
    user: shop_migrator
    password: change-me
    locations: classpath:db/migration
    enabled: true
~~~

Both URLs point to the same database but use different schemes and drivers:

- The R2DBC URL starts with `r2dbc:`.
- The JDBC URL starts with `jdbc:`.

The same account can be used in development, but production should generally separate privileges:

- The migration account is granted DDL privileges needed to create/alter tables, indexes, and constraints.
- The runtime account has only the DML privileges required by the application, such as SELECT, INSERT, UPDATE, and DELETE on permitted tables.

Separating privileges reduces risk if the runtime application is compromised or contains data-writing bugs. There is no need to grant ALTER/DROP rights to the runtime account if the application does not require them.

Do not commit real passwords to the repository. Use environment variables, a secret manager, or the deployment platform's secret management mechanism.

### 4.2. Where Does Flyway Run During Startup?

When Flyway auto-configuration is enabled, Spring Boot creates the Flyway bean and runs migrations during application context initialization. Boot's database initialization dependency infrastructure ensures beans depending on database initialization are initialized after migrations finish.

Expected flow:

~~~text
Application startup
       |
       v
Create migration DataSource
       |
       v
Flyway validates history
       |
       v
Flyway applies pending migrations
       |
       v
Migration completed
       |
       v
R2DBC repositories/services
       |
       v
Application ready
~~~

If migration fails, startup normally fails rather than letting the application serve requests against an invalid schema. This fail-fast behavior is valuable in production: migration errors must be caught at deployment/startup.

For custom beans that execute queries immediately during initialization, define dependency ordering clearly. Avoid running database queries inside a constructor or `@PostConstruct` before verifying migrations have run. When a bean genuinely depends on database initialization, use Spring Boot's appropriate dependency mechanism such as `@DependsOnDatabaseInitialization` on supported versions.

## 5. Configuring Liquibase with R2DBC

Liquibase also commonly uses JDBC to execute changelogs. With PostgreSQL, dependencies may include:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-r2dbc'
    runtimeOnly 'org.postgresql:r2dbc-postgresql'

    implementation 'org.liquibase:liquibase-core'
    runtimeOnly 'org.postgresql:postgresql'
}
~~~

`application.yml` configuration:

~~~yaml
spring:
  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
    username: shop_app
    password: change-me

  liquibase:
    url: jdbc:postgresql://localhost:5432/shop
    user: shop_migrator
    password: change-me
    change-log: classpath:db/changelog/db.changelog-master.yaml
    enabled: true
~~~

Liquibase reads the master changelog, determines which changeSets have not yet been applied, and executes them over JDBC. History is recorded in `DATABASECHANGELOG`; `DATABASECHANGELOGLOCK` coordinates changelog execution.

Do not configure both Flyway and Liquibase to manage the same schema without clear ownership and migration ordering. Choose one tool that fits your team's workflow and standardize execution across local, CI, and production.

## 6. Spring Boot SQL Script Initialization

Spring Boot also supports initializing the database using scripts such as `schema.sql` and `data.sql`. This is a simple mechanism for creating an initial schema or initial data, often useful in small examples, tests, or development environments.

Example:

~~~text
src/main/resources/
├── schema.sql
└── data.sql
~~~

schema.sql:

~~~sql
CREATE TABLE IF NOT EXISTS customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL
);
~~~

data.sql:

~~~sql
INSERT INTO customers (name, email)
VALUES ('An Nguyen', 'an@example.test');
~~~

Configuration:

~~~yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:schema.sql
      data-locations: classpath:data.sql
~~~

Spring Boot supports script initialization for both JDBC and R2DBC. With R2DBC, scripts execute through the ConnectionFactory-based initialization infrastructure. Properties under `spring.sql.init` configure this behavior.

### 6.1. Initialization Modes

Common `mode` values:

| Value | Meaning |
|---|---|
| embedded | Initializes only embedded databases by default |
| always | Always runs script initialization |
| never | Disables script initialization |

If a schema is needed for PostgreSQL/MySQL in development, `always` mode can enable scripts. However, do not ship schema-recreation or sample-data-insertion scripts into production without fully understanding the impact.

### 6.2. When Using Flyway or Liquibase

If Flyway/Liquibase is the source of schema management, disable unnecessary script initialization:

~~~yaml
spring:
  sql:
    init:
      mode: never
~~~

This avoids having two mechanisms create or modify tables during startup. A schema can end up modified in an unpredictable order if script initialization and a migration tool run concurrently without explicit dependencies.

Script initialization does not provide full migration history, checksums, versioning, and upgrade workflows like Flyway/Liquibase. Thus, it suits simple schemas, tests, or prototypes better than long-term production change management.

## 7. Ensuring Migrations Finish Before the Application Serves Requests

Startup ordering is the most critical part of coordinating migrations and R2DBC.

### 7.1. Relying on Standard Spring Boot Auto-Configuration

When using Flyway or Liquibase in a standard setup, let Spring Boot manage the migration bean and dependency ordering. Do not run another migration manually inside `ApplicationRunner` or `CommandLineRunner` if auto-configuration already performs it.

Adding an extra manual migration step can cause:

- Migrations running twice.
- Two components competing for the same migration lock.
- Difficulty diagnosing which step failed during migration.
- Startup depending on accidental bean ordering.

### 7.2. Do Not Query the Schema in a Constructor

Avoid doing this:

~~~java
@Component
class StartupVerifier {

    StartupVerifier(DatabaseClient client) {
        client.sql("SELECT COUNT(*) FROM customers")
                .fetch()
                .one()
                .block();
    }
}
~~~

Constructors are invoked when Spring instantiates beans. Querying here may happen before migrations finish, while also blocking a thread during startup.

If data checks are needed after migration, use an explicitly ordered startup task where the reactive publisher is consumed properly, or let a deployment health check verify after the application is ready. Never put blocking work in a constructor.

### 7.3. Distinguishing Application Startup from Readiness

A process may already have its HTTP port open before it is ready to serve business traffic. In orchestrated environments, readiness probes should succeed only once migrations and required dependencies are ready.

If migrations run as a separate job before deployment, application readiness should confirm the schema version is compatible with the running binary. Do not check only whether the TCP port is open or the process is alive.

### 7.4. Fail-Fast Migrations

If migrations cannot connect to the database, checksums mismatch, or DDL fails, the application must not silently continue as though the schema were ready.

Let the deployment fail, capture migration logs, and resolve the root cause. Disabling migrations just to make startup succeed can leave the application running on the wrong schema version and corrupt data on the first request.

## 8. Migrations in Multi-Replica Environments

In Kubernetes or scaled-out environments, multiple application instances may start nearly simultaneously. If every instance runs migrations itself, the migration tool has to handle contention.

Flyway and Liquibase use locking/history mechanisms to coordinate migrations. However, a deployment pattern that is usually easier to control is running migrations once in a dedicated pipeline or job before scaling up application replicas.

Example deployment flow:

~~~text
Build artifact
     |
     v
Run migration job
     |
     v
Migration successful?
     |
  +--+--+
  |     |
 No    Yes
  |     |
  v     v
Stop  Deploy application
      replicas
         |
         v
      Readiness
         |
         v
      Serve traffic
~~~

Benefits:

- Only a single step is responsible for modifying the schema.
- Separate DDL credentials can be granted solely to the migration job.
- The application runtime needs no schema-modification privileges.
- Migration logs stay separate from runtime logs.
- Deployment can be halted if the migration fails.
- Easy to align migrations with the binary version being released.

If auto-migration remains enabled in every instance, verify locking, timeouts, and behavior when multiple processes start concurrently for your tool and database versions.

## 9. Managing Profiles and Environments

Migration configurations often differ across local, test, staging, and production.

Example local profile:

~~~yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration

  r2dbc:
    url: r2dbc:postgresql://localhost:5432/shop
~~~

Example test profile using a database provided by Testcontainers:

~~~yaml
spring:
  flyway:
    enabled: true

  sql:
    init:
      mode: never
~~~

Production can run migrations in a separate deployment job and disable auto-migration in the application:

~~~yaml
spring:
  flyway:
    enabled: false
~~~

With this choice, the pipeline must ensure the migration job completes before the new application version is deployed. Otherwise, the application may start ahead of the schema.

Never allow the test profile to accidentally use a development or production database. URL, username, and password must be supplied by the respective environment. Avoid storing real credentials in committed YAML files.

## 10. Versioning Migrations and the Rule Against Editing History

Migrations need clear ordering and intent. For example:

~~~text
V1__create_customers.sql
V2__create_orders.sql
V3__add_customer_status.sql
V4__create_customer_email_index.sql
~~~

Once V2 has run in staging or production, if a missing column is discovered, create V5 to fix it. Do not edit V2 and expect all environments to return to the same state automatically.

Reasons:

- Environment A may have already run the old V2.
- Environment B may not have run V2 yet.
- Migration checksums will diverge.
- Some databases do not support full DDL rollback.
- Deployment history becomes non-reproducible.

With Liquibase, applied changeSets should also be treated as immutable. If the schema needs fixes, create a new changeSet rather than editing one already run in a shared environment.

Migration history is part of system state. Keep migrations in version control alongside source code and review them like application changes.

## 11. Designing Rolling-Deployment-Compatible Migrations

A schema change may be deployed while old and new application versions run simultaneously. Migrations must therefore account for backward and forward compatibility.

Suppose you want to rename column `name` to `display_name`.

Dangerous approach:

1. Rename `name` to `display_name` immediately.
2. Deploy new code.
3. Old replicas still running query `name`.
4. Requests on old replicas fail.

A safer approach is **expand-and-contract**:

### Phase 1: Expand

Add the new column while keeping the old column:

~~~sql
ALTER TABLE customers
ADD COLUMN display_name VARCHAR(150);
~~~

### Phase 2: Deploy Compatible Code

Deploy code that can read either column and dual-write both according to the transition plan. During the rolling deployment, old versions still use the old column.

### Phase 3: Backfill

Copy legacy data into the new column:

~~~sql
UPDATE customers
SET display_name = name
WHERE display_name IS NULL;
~~~

For large tables, backfilling should be batched or run as a separate job to avoid oversized transactions and prolonged locks.

### Phase 4: Switch the Application

Deploy the version that exclusively uses `display_name` once data has been backfilled and all old replicas have stopped.

### Phase 5: Contract

In a later release, once no code uses the old column, drop `name`:

~~~sql
ALTER TABLE customers
DROP COLUMN name;
~~~

Splitting phases reduces the risk of a new schema breaking older application versions during a rolling deployment.

## 12. Data Migrations and Backfills

Migrations do not just create tables or add columns. Older data may need transformation to fit a new structure.

Example adding `normalized_email`:

~~~sql
ALTER TABLE customers
ADD COLUMN normalized_email VARCHAR(320);
~~~

Backfill:

~~~sql
UPDATE customers
SET normalized_email = LOWER(TRIM(email))
WHERE normalized_email IS NULL;
~~~

Afterward, a unique index can be created if business rules require normalized emails to be unique:

~~~sql
CREATE UNIQUE INDEX uq_customers_normalized_email
ON customers (normalized_email);
~~~

Before creating the unique index, identify and resolve existing duplicate data. If multiple emails normalize to the same value, the migration will fail or be unable to create the constraint.

On large tables, do not assume a full-table UPDATE is safe. Consider:

- Table size and write throughput.
- Lock duration.
- Transaction log/WAL growth.
- Replication lag.
- Batch size and checkpoints.
- Job restartability.
- Handling new records written while backfilling.

Long backfills generally suit observable, retryable jobs better than a startup migration holding a massive transaction.

## 13. DDL Transactions and Rollback Limitations

Not all databases support transactions for every DDL statement in the same way. Some schema changes commit implicitly or have limitations when executed inside a transaction.

Therefore:

- Do not assume a failed migration always rolls back all DDL.
- Verify the DDL semantics of the target database.
- Keep migrations small so post-failure state is easy to determine.
- Have a forward-fix plan when safe rollback is impossible.
- Back up and test restores before high-risk changes.
- Avoid dropping or changing the type of columns holding critical data in the same step as an application deploy.

Flyway/Liquibase help manage history and execute migrations, but they cannot make every DDL change rollbackable on their own. Rollback capability depends on the database and migration contents.

## 14. Migration Locks and Concurrent Startup Handling

When multiple processes execute migrations simultaneously, the tool needs a mechanism to prevent two processes from altering the schema concurrently.

- Flyway uses schema history and locking mechanisms to coordinate migrations.
- Liquibase uses the `DATABASECHANGELOGLOCK` table to manage locks.

If a process crashes mid-migration, inspect database state, logs, and locks before intervening manually. Do not arbitrarily delete the history table or lock row without confirming whether a migration is still running.

In production, a single migration job usually reduces contention. If using startup migrations across multiple replicas, configure timeouts and monitor scenarios where a replica has to wait on a migration lock.

## 15. Configuring Multiple Databases or Multiple Schemas

An application may use multiple R2DBC ConnectionFactories and multiple schemas/databases. Each database needs its own migration plan.

Example:

~~~text
Application
├── Customer database
│   ├── R2DBC ConnectionFactory
│   └── Customer migrations
└── Order database
    ├── R2DBC ConnectionFactory
    └── Order migrations
~~~

Do not share one migration location across multiple databases if the changes do not apply to both.

With multiple databases, you can:

- Run a separate migration job per database.
- Create separate Flyway/Liquibase instances with their respective JDBC URL, schema, and changelog/locations.
- Use separate migration accounts per database.
- Verify each migration succeeds before the application depending on that database marks readiness.
- Separate repositories/templates/ConnectionFactories per database.

One R2DBC transaction manager only manages the ConnectionFactory it is configured for. Migrating both databases successfully does not create a distributed transaction for runtime operations across them.

If business logic needs to write to two databases concurrently, design a saga, outbox, or appropriate coordination mechanism. Startup migrations only manage each database's schema.

## 16. Creating Sample Data and Seed Data

Initialization data can be divided into two categories:

- **Reference data:** stable catalogs such as status types, units of measure, or country codes.
- **Sample/test data:** illustrative data intended only for local or test use.

Reference data can be managed via migrations if its changes need versioning. Use stable keys and operations safe for repeatable execution when supported by the tool.

Sample data should live in separate profiles or test scripts. Never let `data.sql` containing sample users, default passwords, or demo records be loaded into production accidentally.

If using Flyway repeatable migrations to manage views or reference data, understand that the file can re-run whenever its checksum changes. Statements must be designed to handle re-execution safely.

Do not use migrations to load massive amounts of business data. Large imports should be batch jobs with independent checkpoints, monitoring, and retries.

## 17. Verifying Schema Compatibility with the Application

A successful migration does not automatically prove runtime code is compatible. The application may require:

- New tables or columns.
- Exact data types.
- Unique constraints or foreign keys.
- Indexes supporting queries.
- Proper default values and nullability.
- Created views or functions.
- Access privileges for the runtime account.

You can add a schema version check or smoke query after migration. With Flyway, history can be read from schema history; with Liquibase, from `DATABASECHANGELOG`. However, application code should not modify the schema itself just to match a version.

If specific checks are needed, run a small query via R2DBC after migration completes and before marking the instance ready. Such checks must have explicit ordering and must not be placed inside bean constructors.

## 18. Testing Migrations with R2DBC Using Testcontainers

Integration tests should verify both connection paths:

1. The database container starts.
2. Flyway/Liquibase runs migrations over JDBC.
3. Spring Data R2DBC creates the ConnectionFactory.
4. Repositories or R2dbcEntityTemplate access the newly created schema.
5. Tests exercise real CRUD and queries.

Example test dependencies for PostgreSQL:

~~~groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testImplementation 'org.testcontainers:junit-jupiter'
    testImplementation 'org.testcontainers:postgresql'
}
~~~

Testcontainers can provide a single PostgreSQL instance shared by migrations and R2DBC. Test configuration must provide both URLs:

- JDBC URL for Flyway/Liquibase.
- R2DBC URL for Spring Data R2DBC.

Conceptual configuration example using `DynamicPropertySource`:

~~~java
@DynamicPropertySource
static void databaseProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.flyway.url", postgres::getJdbcUrl);
    registry.add("spring.flyway.user", postgres::getUsername);
    registry.add("spring.flyway.password", postgres::getPassword);

    registry.add("spring.r2dbc.url", () ->
            postgres.getJdbcUrl().replace(
                    "jdbc:postgresql:",
                    "r2dbc:postgresql:"
            )
    );
    registry.add("spring.r2dbc.username", postgres::getUsername);
    registry.add("spring.r2dbc.password", postgres::getPassword);
}
~~~

The illustrative snippet assumes the PostgreSQL container is declared and started in the test class. Check URL syntax for your driver and versions; never hardcode host/port because Testcontainers assigns dynamic ports.

### 18.1. Verifying Migrations Ran

You can verify that tables or columns were created with a query via `DatabaseClient`:

~~~java
StepVerifier.create(
        databaseClient.sql("""
                SELECT COUNT(*)
                FROM information_schema.tables
                WHERE table_name = 'customers'
                """)
            .map((row, metadata) -> row.get(0, Long.class))
            .one()
    )
    .expectNext(1L)
    .verifyComplete();
~~~

Metadata query syntax depends on the database. With PostgreSQL, `information_schema` or the appropriate catalog can be used. The goal is to confirm schema existence via the R2DBC runtime path.

### 18.2. Verifying Repositories Use the New Schema

After migrations, perform an insert/select through the repository:

~~~java
StepVerifier.create(
        customerRepository.save(
                new Customer(null, "An", "an@example.test", "ACTIVE")
        )
)
.assertNext(saved -> assertThat(saved.id()).isNotNull())
.verifyComplete();
~~~

This test proves migrations and R2DBC mapping work together. Merely checking that the Flyway bean succeeded is insufficient if runtime code might use a wrong URL, schema, or credentials.

## 19. CI/CD Pipeline for Migrations

A deployment pipeline can be organized as:

~~~text
Compile / unit tests
        |
        v
Build application artifact
        |
        v
Start ephemeral database
        |
        v
Run migrations
        |
        v
Run R2DBC integration tests
        |
        v
Package / publish artifact
        |
        v
Backup / deployment approval as required
        |
        v
Run production migration job
        |
        v
Deploy application version
        |
        v
Readiness and smoke tests
~~~

CI should test migrations from an empty schema as well as upgrades from the previous schema version if the project must support upgrades. Empty-schema tests verify the full history can build a fresh database; upgrade tests verify new migrations are compatible with existing data.

The production migration job should:

- Use the exact release artifact/changelog.
- Have dedicated DDL credentials.
- Run once per deployment orchestration.
- Log and retain output.
- Halt deployment if migration fails.
- Have a backup/restore or forward-fix plan suited to the risk level.

Do not run production migrations using the application's runtime account when privileges can be separated.

## 20. Observing and Troubleshooting Startup Errors

Common errors:

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Flyway cannot find JDBC driver | Only R2DBC driver declared | Add the JDBC driver for the database |
| R2DBC connects successfully but migration fails | Wrong JDBC URL/driver/credentials | Check `spring.flyway.url` and JDBC dependencies |
| Migration reports checksum mismatch | Versioned file modified after being applied | Restore history or create a new migration per procedure |
| Migrations not found | Wrong locations or file naming | Check classpath and filename conventions |
| App fails due to missing table | Migration disabled or ran after initialization query code | Enable migration or fix startup ordering |
| Multiple replicas waiting on migration | Multiple processes competing for lock | Use a dedicated migration job or configure appropriate wait settings |
| SQL scripts run twice | Both script initializer and Flyway/Liquibase active | Choose one schema management mechanism |
| Runtime gets permission denied | R2DBC account lacks DML or schema usage rights | Grant minimal required privileges |
| Migration succeeds but repository fails | Mapping/column/schema mismatch or R2DBC URL points elsewhere | Compare JDBC and R2DBC targets; check entity mapping |
| Migration timeout | Database unready, locks, or long DDL | Check database health, locks, and migration duration |
| DDL fails partway through | Database has DDL transaction limitations | Assess actual state and safely forward-fix |
| Tests pass locally but fail in CI | Database/driver version or URL differences | Use the same database type/version in Testcontainers |

### 20.1. Checking That JDBC and R2DBC Point to the Same Database

A dangerous mistake is Flyway running migrations against database A while the R2DBC app connects to database B. Both connections may succeed, yet repositories still report missing tables.

Compare:

- Host and port.
- Database name.
- Schema/catalog.
- Username and privileges.
- Search path/default schema.
- SSL and connection parameters.
- Active profile.

Do not compare environment names alone. Verify actual database identity with a suitable query if necessary.

### 20.2. Do Not Ignore Migration Errors to Keep the App Alive

If migrations fail, avoid configuring the app to keep serving requests on an incompatible schema. Doing so can cause partial write errors or data corruption.

Categorize connection, checksum, lock, permission, and DDL errors. Then fix the migration or environment and re-run per tool policy. Never delete migration history to force startup to succeed.

## 21. Anti-Patterns to Avoid

- Using `schema.sql` and Flyway/Liquibase together to modify the same schema without ordering.
- Declaring only the R2DBC driver while forgetting the JDBC driver needed by the migration tool.
- Placing migration logic inside a constructor or `@PostConstruct`.
- Calling `block()` during reactive application initialization.
- Running migrations with a runtime account holding overly broad DDL rights.
- Editing migration files already applied in shared environments.
- Letting every replica perform large backfills at startup.
- Manually deleting history or lock rows without determining status.
- Deploying new binaries before the schema is compatible.
- Renaming/dropping columns immediately in a single release while old replicas still run.
- Allowing the app to serve traffic even when required migrations fail.
- Using migrations to import massive volumes of business data.
- Assuming migration rollbacks always restore DDL across every database.

## 22. Checklist for Coordinating Migrations and R2DBC Startup

Before deploying, verify:

1. One primary migration tool is selected for the database/schema.
2. Migration files are in version control with clear names/versions.
3. A JDBC driver is added if Flyway/Liquibase requires JDBC.
4. The R2DBC driver and ConnectionFactory are configured separately for runtime.
5. JDBC URL and R2DBC URL point to the exact same database/schema.
6. Migration credentials have the necessary DDL privileges.
7. Runtime credentials have only minimal data privileges.
8. Migrations run before runtime operations depending on the schema.
9. No database queries execute in constructors or unordered startup hooks.
10. Script initializers are disabled if the migration tool is the primary schema source.
11. Migration failures fail deployment/startup per policy.
12. Multiple replicas do not trigger uncontrolled migration races.
13. Migrations are compatible with rolling deployments or split into expand/contract.
14. Large backfills have dedicated batching and observability plans.
15. Testcontainers confirms migrations and R2DBC repositories work together.
16. CI verifies both a fresh database and upgrades from existing schemas as needed.
17. Backup/restore or forward-fix plans exist for high-risk changes.
18. Readiness succeeds only once the schema and required dependencies are ready.

## 23. Conclusion

Coordinating migrations with R2DBC application startup requires clearly separating schema changes from runtime data access. Flyway or Liquibase typically uses JDBC to apply migrations; Spring Data R2DBC continues using the R2DBC ConnectionFactory and driver for repositories, templates, and DatabaseClient. Consequently, an application may need both a JDBC driver and an R2DBC driver for the same database.

With standard Spring Boot configuration, migrations can run during application context initialization, and components depending on database initialization are ordered accordingly. Do not query the database inside constructors or ignore migration errors. `schema.sql`/`data.sql` scripts fit simple bootstrapping; projects needing long-term schema management should use a migration tool with tracked history.

In production, consider running migrations as a standalone job prior to deploying application replicas, using a dedicated DDL account, keeping applied migrations immutable, and designing changes compatible with rolling deployments. Test with a real database or Testcontainers, verifying both JDBC migrations and R2DBC queries. Only when both connection paths see the exact same schema and readiness opens after migrations succeed can the application start up and serve data reliably.
