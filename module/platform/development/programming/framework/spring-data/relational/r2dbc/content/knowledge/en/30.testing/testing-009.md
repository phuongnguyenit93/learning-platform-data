# Testing Mapping, Converters, Callbacks, and Auditing

Spring Data R2DBC converts data between rows in a relational database and Java objects. This process includes reading entity metadata, mapping table/column names, converting data types, invoking entity callbacks, and updating auditing fields. A repository test that only checks that save or findById does not emit an error is insufficient to prove the entire pipeline works properly.

Tests should be divided into layers with clear goals:

- **Mapping:** entities map to the right tables, columns, keys, constructors, and data relationships.
- **Converters:** domain types convert properly to database types and back.
- **Entity callbacks:** callbacks run at the right moments and mutate entities/OutboundRow per contract.
- **Auditing:** created/modified dates and actors are populated properly, including inside reactive contexts.
- **Direct write paths:** verify that direct SQL does not automatically invoke entity callbacks or auditing without a separate mechanism.

Unit tests fit checking isolated converter and callback logic. Integration tests with a real R2DBC driver and database fit checking mapping, SQL types, callback lifecycles, transactions, and end-to-end auditing.

## 1. What Needs Testing in Spring Data R2DBC

When calling repository save or findById, multiple components collaborate:

1. Spring Data reads entity metadata such as @Table, @Column, @Id, and @Version.
2. The mapping context resolves properties, table names, column names, and constructors used to instantiate objects.
3. The mapping converter transforms Java values into database values on write, or database row values into Java values on read.
4. Entity callbacks can modify the entity or outbound write data before/after operations.
5. Auditing callbacks can populate actors and timestamps on properties carrying auditing annotations.
6. The R2DBC driver binds parameters, executes SQL, and turns results into rows.

A mapping bug may surface only on a specific database. For instance, Instant may map differently depending on timestamp columns and dialects; a converter may pass unit tests while the SQL column type is incompatible; or uppercase/quoted column names may differ from the schema.

### 1.1. Testing Map

| Component | Primary check | Appropriate test type |
| --- | --- | --- |
| Entity metadata | Table, column, ID, constructor, version | Metadata unit test when needed; integration test |
| Reading converter | Database value to domain value | Converter unit test and integration round-trip |
| Writing converter | Domain value to database value | Converter unit test and integration round-trip |
| BeforeConvert callback | Mutating entity before mapping | Callback unit test and repository integration test |
| BeforeSave callback | Mutating OutboundRow before write | Callback unit test and database integration test |
| AfterSave callback | Reacting after write succeeds | Integration test |
| AfterConvert callback | Enriching/normalizing entity after read | Integration test |
| Auditing | Created/modified dates and actors | Integration test with auditing config |
| Direct SQL | Do not assume callbacks/auditing run automatically | Integration test |
| Transactions | Rollback when callback or subsequent operation fails | Integration test with real database |

There is no need to test framework internals exhaustively. Focus on contracts the application depends on and bugs that could corrupt data.

## 2. Preparing a Sample Entity with Explicit Mapping

Example entity whose table/column names differ from property names:

~~~java
@Table("customer_profiles")
public class CustomerProfile {

    @Id
    private Long id;

    @Column("display_name")
    private String displayName;

    @Column("email_address")
    private String email;

    @Column("active")
    private Boolean active;

    @Version
    private Long version;

    // Constructors, getters, and setters omitted.
}
~~~

Corresponding schema:

~~~sql
CREATE TABLE customer_profiles (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(160) NOT NULL,
    email_address VARCHAR(240),
    active BOOLEAN NOT NULL,
    version BIGINT NOT NULL
);
~~~

The table name customer_profiles and columns display_name, email_address are declared explicitly. Integration tests should verify that the repository actually reads and writes those exact names.

### 2.1. Testing Round-Trip Mapping

A basic test:

~~~java
@Test
void shouldWriteAndReadMappedColumns() {
    CustomerProfile input = new CustomerProfile(
            "Nguyen An",
            "an@example.test",
            true);

    StepVerifier.create(repository.save(input)
                    .flatMap(saved -> repository.findById(saved.getId())))
            .assertNext(found -> {
                assertThat(found.getDisplayName()).isEqualTo("Nguyen An");
                assertThat(found.getEmail()).isEqualTo("an@example.test");
                assertThat(found.getActive()).isTrue();
            })
            .verifyComplete();
}
~~~

This test checks the write and read paths through the mapping converter and driver. Prepare schemas and clean data between tests for stable results.

### 2.2. Testing Generated IDs

When the database generates IDs, the input entity usually has no ID yet. After save, verify the ID was populated and can be used to read back:

~~~java
StepVerifier.create(repository.save(input))
        .assertNext(saved -> {
            assertThat(saved.getId()).isNotNull();
            assertThat(saved.getVersion()).isNotNull();
        })
        .verifyComplete();
~~~

The ID type, identity/sequence mechanism, and initial version value depend on the database and Spring Data configuration. Tests should assert against the chosen contract rather than assuming every dialect starts ID/version at the exact same value.

## 3. Testing Data Type Mapping

Java and SQL types must be compatible. Common mappings:

| Java type | Common SQL type | What to verify |
| --- | --- | --- |
| String | VARCHAR, TEXT | Length, collation, encoding |
| Integer/Long | INTEGER, BIGINT | Range and overflow |
| BigDecimal | DECIMAL/NUMERIC | Precision, scale, and rounding |
| Boolean | BOOLEAN or database equivalent | True/false values and nullability |
| LocalDate | DATE | Date without timezone |
| LocalDateTime | TIMESTAMP | Without timezone |
| Instant | TIMESTAMP WITH TIME ZONE or dialect-appropriate type | UTC convention and precision |
| UUID | UUID or binary/character type per database | Format and native support |
| Enum | Usually VARCHAR or configured type | Enum name, converter, and value changes |

Do not inspect only the Java object returned by save if the schema could truncate precision. For BigDecimal, inspect the read-back value and scale per business rules. For timestamps, verify the precision supported by the database.

### 3.1. BigDecimal and Precision/Scale

Schema:

~~~sql
CREATE TABLE invoices (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    total_amount NUMERIC(12, 2) NOT NULL
);
~~~

Test:

~~~java
BigDecimal amount = new BigDecimal("123456.70");

StepVerifier.create(invoiceRepository.save(new Invoice(amount))
                .flatMap(saved -> invoiceRepository.findById(saved.getId())))
        .assertNext(found -> {
            assertThat(found.getTotalAmount())
                    .isEqualByComparingTo(new BigDecimal("123456.70"));
        })
        .verifyComplete();
~~~

If business rules require a fixed scale, check `scale()` as well or normalize in a domain constructor. Do not rely on comparing `BigDecimal` with `equals` when scales differ for the same numeric value; `isEqualByComparingTo` is appropriate when comparing numeric values only.

### 3.2. Timestamps and Timezones

Timestamp tests should use a deterministic instant:

~~~java
Instant expected = Instant.parse("2025-02-10T08:30:15Z");
~~~

Save and read back via the real database, then compare at the precision supported by the column. Some databases store only microseconds or milliseconds, so read-back values may truncate nanoseconds.

If the application standardizes on storing UTC, specify the SQL type and converter explicitly. Never compare formatted timestamp strings tied to the test machine's local timezone.

### 3.3. Nullability

Verify separately:

- Nullable properties read back as null when the SQL column is NULL.
- Required properties reject null when the schema enforces NOT NULL.
- Java primitives are unsuitable for nullable columns; consider wrapper types.
- An INSERT omitting a value either uses a database default or sends NULL, depending on mapping and SQL statement.

A row that exists with a null email is still a returned entity. It is completely different from findById finding no row and returning Mono.empty().

## 4. Testing Constructors and Immutable Entities

Spring Data can instantiate entities via an appropriate constructor. With immutable objects or Java records, parameter names/types must be compatible with property metadata and the mapping rules of the version in use.

Record example:

~~~java
@Table("country_codes")
public record CountryCode(
        @Id Long id,
        @Column("country_code") String code,
        String name
) {
}
~~~

Integration tests should:

1. Insert a record.
2. Verify the ID is returned according to the ID generation strategy.
3. Read the record back.
4. Verify all properties map properly, including columns whose names differ from property names.

If using multi-argument constructors instead of records, check parameter name metadata and constructor annotations if needed. Do not test only mutable entities with no-arg constructors and assume immutable mapping works too.

## 5. Testing Custom Converters

Custom converters are used when domain types are not directly supported by the database driver or Spring Data in the way the application requires. There are two directions:

- Writing converter: domain value to a type bindable to the database.
- Reading converter: database type to domain value.

Example Money domain type stored as NUMERIC:

~~~java
public record Money(BigDecimal amount) {

    public Money {
        Objects.requireNonNull(amount, "amount");
        if (amount.scale() > 2) {
            throw new IllegalArgumentException("Money supports at most 2 decimals");
        }
    }
}
~~~

Writing converter:

~~~java
@WritingConverter
public class MoneyWritingConverter
        implements Converter<Money, BigDecimal> {

    @Override
    public BigDecimal convert(Money source) {
        return source.amount();
    }
}
~~~

Reading converter:

~~~java
@ReadingConverter
public class MoneyReadingConverter
        implements Converter<BigDecimal, Money> {

    @Override
    public Money convert(BigDecimal source) {
        return new Money(source);
    }
}
~~~

Annotating the read/write direction helps Spring Data avoid converter ambiguity when source and target are simple or database-native types.

### 5.1. Isolated Converter Unit Tests

Writing converter:

~~~java
@Test
void shouldWriteMoneyAsDecimal() {
    MoneyWritingConverter converter = new MoneyWritingConverter();

    BigDecimal value = converter.convert(new Money(new BigDecimal("19.95")));

    assertThat(value).isEqualByComparingTo("19.95");
}
~~~

Reading converter:

~~~java
@Test
void shouldReadDecimalAsMoney() {
    MoneyReadingConverter converter = new MoneyReadingConverter();

    Money value = converter.convert(new BigDecimal("19.95"));

    assertThat(value.amount()).isEqualByComparingTo("19.95");
}
~~~

Unit tests verify conversion logic quickly without starting a database. However, they do not prove Spring Data registered the converter or that the driver binds the SQL type properly.

### 5.2. Registering Converters with R2DBC

In Java configuration, you can supply custom conversions per dialect:

~~~java
@Configuration
public class R2dbcConversionConfiguration {

    @Bean
    R2dbcCustomConversions r2dbcCustomConversions() {
        return R2dbcCustomConversions.of(
                PostgresDialect.INSTANCE,
                List.of(
                        new MoneyWritingConverter(),
                        new MoneyReadingConverter()
                ));
    }
}
~~~

The converter registration API can vary across Spring Data R2DBC versions. If the project uses AbstractR2dbcConfiguration or Spring Boot auto-configuration, declare custom conversions via the extension point supported by that version and avoid creating two competing configuration beans.

### 5.3. Converter Integration Tests Through the Repository

Entity:

~~~java
@Table("wallets")
public class Wallet {

    @Id
    private Long id;

    @Column("available_balance")
    private Money availableBalance;

    // Constructors, getters, and setters omitted.
}
~~~

Schema:

~~~sql
CREATE TABLE wallets (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    available_balance NUMERIC(14, 2) NOT NULL
);
~~~

Test:

~~~java
@Test
void shouldRoundTripMoneyThroughR2dbcMapping() {
    Wallet wallet = new Wallet(new Money(new BigDecimal("250.40")));

    StepVerifier.create(walletRepository.save(wallet)
                    .flatMap(saved -> walletRepository.findById(saved.getId())))
            .assertNext(found -> assertThat(found.getAvailableBalance().amount())
                    .isEqualByComparingTo("250.40"))
            .verifyComplete();
}
~~~

This test confirms Spring Data invokes the converters in both directions and the database can store the corresponding type.

### 5.4. Testing Converter Errors

Converters can reject invalid data. Verify:

- Invalid domain values are rejected before writing.
- Legacy database values that cannot convert to domain values are handled intentionally.
- Exceptions are not swallowed into Mono.empty().
- Responses/APIs do not leak raw database values or stack traces.

If a converter can fail when reading a row, decide whether the API returns a data error or quarantines malformed records during batch imports/reports.

## 6. Testing Enums and Domain Types

If an enum is stored by name:

~~~java
public enum CustomerStatus {
    NEW,
    ACTIVE,
    SUSPENDED
}
~~~

Test round-trips to verify values are written and read properly. Consider the impact of renaming an enum constant or removing a value already present in the database.

If enum names are not a stable storage contract, use converters to a dedicated code:

~~~java
public enum CustomerStatus {
    NEW("N"),
    ACTIVE("A"),
    SUSPENDED("S");

    private final String code;

    CustomerStatus(String code) {
        this.code = code;
    }

    public String code() {
        return code;
    }

    public static CustomerStatus fromCode(String code) {
        return Arrays.stream(values())
                .filter(value -> value.code.equals(code))
                .findFirst()
                .orElseThrow(() -> new IllegalArgumentException(
                        "Unknown customer status code"));
    }
}
~~~

Read/write converters should be tested for every valid code as well as unknown codes. If the system has legacy data, test migrations and compatibility when adding enum values.

## 7. Testing Entity Callbacks

Entity callbacks let an application execute logic at specific points in the entity save/read lifecycle. Common callbacks in Spring Data Relational/R2DBC include:

- BeforeConvertCallback: before the entity is converted into relational data.
- BeforeSaveCallback: before data is sent to be saved, optionally receiving OutboundRow.
- AfterSaveCallback: after the save operation completes.
- AfterConvertCallback: after a row is converted into an entity, depending on API/version.

Callbacks in R2DBC are reactive; implementations return a publisher and should not call block or subscribe internally.

### 7.1. BeforeConvertCallback

Example normalizing a name before mapping:

~~~java
@Component
public class CustomerNameCallback
        implements BeforeConvertCallback<CustomerProfile> {

    @Override
    public Publisher<CustomerProfile> onBeforeConvert(
            CustomerProfile entity,
            SqlIdentifier table) {

        entity.setDisplayName(entity.getDisplayName().trim());
        return Mono.just(entity);
    }
}
~~~

The callback runs during entity saving before converting the entity into outbound write data. Tests should verify that the value actually persisted in the database is normalized, not just that the callback method returns the entity.

### 7.2. Callback Unit Test

~~~java
@Test
void shouldTrimDisplayNameBeforeConvert() {
    CustomerNameCallback callback = new CustomerNameCallback();
    CustomerProfile customer = new CustomerProfile(
            "  An Nguyen  ", "an@example.test", true);

    StepVerifier.create(Mono.from(callback.onBeforeConvert(
                    customer, SqlIdentifier.unquoted("customer_profiles"))))
            .assertNext(result ->
                    assertThat(result.getDisplayName()).isEqualTo("An Nguyen"))
            .verifyComplete();
}
~~~

This unit test verifies callback logic in isolation. Integration tests are still needed to confirm the callback is registered in the application context and invoked by repository save.

### 7.3. BeforeSaveCallback and OutboundRow

BeforeSaveCallback can mutate OutboundRow right before saving. This is useful when adding a value written to the row without representing it as an entity property.

~~~java
@Component
public class CustomerSourceCallback
        implements BeforeSaveCallback<CustomerProfile> {

    @Override
    public Publisher<CustomerProfile> onBeforeSave(
            CustomerProfile entity,
            OutboundRow row,
            SqlIdentifier table) {

        row.put(
                SqlIdentifier.unquoted("write_source"),
                Parameter.from("webflux-api"));
        return Mono.just(entity);
    }
}
~~~

The Parameter type and value construction must match your Spring Data R2DBC version. If write_source can be represented as a normal entity property, that approach is usually clearer and easier to test.

### 7.4. Callbacks Must Stay Reactive

Avoid:

~~~java
@Override
public Publisher<CustomerProfile> onBeforeConvert(
        CustomerProfile entity,
        SqlIdentifier table) {

    Mono.from(auditClient.record(entity.getId())).block();
    return Mono.just(entity);
}
~~~

Blocking code can stall event loops and break reactive benefits. If a callback genuinely needs a dependent publisher, chain that publisher into the callback return value:

~~~java
@Override
public Publisher<CustomerProfile> onBeforeConvert(
        CustomerProfile entity,
        SqlIdentifier table) {

    return auditClient.validate(entity.getId())
            .thenReturn(entity);
}
~~~

However, callbacks run on the entity save path; avoid putting slow network calls or hard-to-roll-back side effects inside callbacks if they hold database connections open in a transaction for too long. Such operations usually belong in the service layer.

### 7.5. Callbacks and Direct SQL

Repository methods using @Modifying @Query, DatabaseClient.sql, or SQL executed outside Spring Data entity saves typically bypass the entity callback lifecycle. Therefore, do not expect BeforeConvertCallback or auditing callbacks to run automatically when direct SQL updates a table.

If behavior must apply to every writer, consider a database trigger. If it applies only to one use case, let the service update it explicitly.

## 8. Testing Callbacks Registered in the Application Context

You can use a test callback that counts invocations:

~~~java
@TestConfiguration
static class CallbackTestConfiguration {

    @Bean
    AtomicInteger beforeConvertCalls() {
        return new AtomicInteger();
    }

    @Bean
    BeforeConvertCallback<CustomerProfile> countingCallback(
            AtomicInteger beforeConvertCalls) {

        return (entity, table) -> {
            beforeConvertCalls.incrementAndGet();
            return Mono.just(entity);
        };
    }
}
~~~

In an integration test, inject the counter, call repository.save, and verify the callback was invoked. Then run a direct SQL update and verify the counter does not increment because that SQL path bypasses entity callbacks.

Do not rely on ordering among multiple callbacks unless the application declares an explicit order. If ordering matters, use the ordering mechanism supported by the framework and write a test verifying that order.

### 8.1. Testing Failing Callbacks

If a callback emits an error, saving the entity should not proceed to the database. Verify:

- The save publisher ends with the expected exception.
- No new row is inserted.
- The transaction rolls back if the operation runs inside a transaction.
- The error is preserved or translated into a meaningful application error.

Callbacks should not swallow errors and return the entity when the callback rule is mandatory. Doing so can leave data unnormalized or skip critical checks.

## 9. Testing Spring Data Auditing

Auditing is a specialized set of callbacks using entity metadata to populate created/modified fields. Test both actor and timestamp, and both create and update.

Entity:

~~~java
@Table("audited_customers")
public class AuditedCustomer {

    @Id
    private Long id;

    private String name;

    @CreatedDate
    @Column("created_at")
    private Instant createdAt;

    @CreatedBy
    @Column("created_by")
    private String createdBy;

    @LastModifiedDate
    @Column("last_modified_at")
    private Instant lastModifiedAt;

    @LastModifiedBy
    @Column("last_modified_by")
    private String lastModifiedBy;

    // Constructors, getters, and setters omitted.
}
~~~

### 9.1. Configuring Auditing for Tests

A test configuration can provide deterministic actor and clock providers:

~~~java
@TestConfiguration
@EnableR2dbcAuditing(
        auditorAwareRef = "testAuditorAware",
        dateTimeProviderRef = "testDateTimeProvider"
)
static class AuditingTestConfiguration {

    static final Instant FIXED_TIME =
            Instant.parse("2025-03-01T10:15:30Z");

    @Bean
    ReactiveAuditorAware<String> testAuditorAware() {
        return () -> Mono.just("test-user");
    }

    @Bean
    DateTimeProvider testDateTimeProvider() {
        return () -> Optional.of(FIXED_TIME);
    }
}
~~~

Using a fixed timestamp prevents assertions from depending on test execution speed. In tests checking multiple actors or timestamps, use controllable providers.

### 9.2. Testing Create

~~~java
@Test
void shouldPopulateCreatedAndModifiedFieldsOnInsert() {
    AuditedCustomer input = new AuditedCustomer("Mai");

    StepVerifier.create(auditedCustomerRepository.save(input))
            .assertNext(saved -> {
                assertThat(saved.getCreatedBy()).isEqualTo("test-user");
                assertThat(saved.getLastModifiedBy()).isEqualTo("test-user");
                assertThat(saved.getCreatedAt())
                        .isEqualTo(AuditingTestConfiguration.FIXED_TIME);
                assertThat(saved.getLastModifiedAt())
                        .isEqualTo(AuditingTestConfiguration.FIXED_TIME);
            })
            .verifyComplete();
}
~~~

The test verifies that auditing callbacks populated fields before writing. Also read the row back from the database to verify the actually persisted values.

### 9.3. Testing Update

To verify created fields remain unchanged:

1. Create an entity with the initial actor and timestamp.
2. Switch the actor/time provider to new values.
3. Read the entity, change a business property, and save.
4. Verify createdAt/createdBy remain unchanged.
5. Verify lastModifiedAt/lastModifiedBy reflect the update.

Expected state example:

~~~text
After insert:
  created_by       = creator
  created_at       = T1
  last_modified_by = creator
  last_modified_at = T1

After update:
  created_by       = creator
  created_at       = T1
  last_modified_by = editor
  last_modified_at = T2
~~~

If a test uses only one fixed actor/time, it does not prove that modified fields change. Use providers whose values can change between the two saves.

### 9.4. ReactiveAuditorAware Must Read the Actor from the Right Context

If the application uses Spring Security WebFlux, the auditor provider can read the reactive security context:

~~~java
@Bean
ReactiveAuditorAware<String> auditorAware() {
    return () -> ReactiveSecurityContextHolder.getContext()
            .map(SecurityContext::getAuthentication)
            .filter(Authentication::isAuthenticated)
            .map(Authentication::getName);
}
~~~

A test can attach a SecurityContext into Reactor Context:

~~~java
Authentication authentication =
        new UsernamePasswordAuthenticationToken(
                "alice", "n/a", List.of(new SimpleGrantedAuthority("ROLE_USER")));

SecurityContext securityContext =
        new SecurityContextImpl(authentication);

Mono<AuditedCustomer> save = auditedCustomerRepository.save(
        new AuditedCustomer("Test"));

StepVerifier.create(save.contextWrite(
                ReactiveSecurityContextHolder.withSecurityContext(
                        Mono.just(securityContext))))
        .assertNext(saved ->
                assertThat(saved.getCreatedBy()).isEqualTo("alice"))
        .verifyComplete();
~~~

This test verifies context propagation across subscription. Do not merely set the thread-local SecurityContextHolder in an imperative test and conclude reactive auditing works.

### 9.5. Missing Auditor

Define clear behavior when no actor is present:

- Allow audit dates while leaving actor null.
- Use a system actor for background jobs.
- Reject the operation if an actor is mandatory.

Test each case. Do not let tests accidentally run under a default authentication that always yields an actor even when production lacks that context.

## 10. Testing Auditing When Using Direct SQL

An important detail of Spring Data R2DBC: entity auditing callbacks do not automatically run for all direct DML statements.

Example:

~~~java
@Modifying
@Query("UPDATE audited_customers SET name = :name WHERE id = :id")
Mono<Integer> updateNameDirectly(
        @Param("id") Long id,
        @Param("name") String name);
~~~

Tests should:

1. Create an entity via repository save and confirm auditing populated the columns.
2. Record last_modified_at/last_modified_by.
3. Call updateNameDirectly.
4. Read the entity back.
5. Verify name changed while audit fields did not automatically change unless the query/trigger updates them.

If the SQL statement is updated to bind modifiedAt and modifiedBy, verify both fields update properly. If the database uses triggers, test triggers through every write path supported by the application.

### 10.1. Distinguishing Callbacks from Database Triggers

Callbacks are application logic inside Spring Data and run only when operations go through the callback lifecycle. Triggers are database logic and can fire across multiple writers.

Tests should clarify which source owns each audit column. If both a callback and a trigger write last_modified_at, the final value may be overwritten by the trigger; tests must reflect the chosen contract.

## 11. Testing @Version Combined with Callbacks and Auditing

An entity can use both @Version and auditing:

~~~java
@Table("versioned_documents")
public class VersionedDocument {

    @Id
    private Long id;

    @Version
    private Long version;

    private String title;

    @LastModifiedDate
    @Column("last_modified_at")
    private Instant lastModifiedAt;

    @LastModifiedBy
    @Column("last_modified_by")
    private String lastModifiedBy;

    // Constructors, getters, and setters omitted.
}
~~~

Integration tests should verify:

- Insert initializes version and auditing fields per configuration.
- Update with the latest version succeeds and increments version.
- Updating a stale entity fails with optimistic locking.
- When a stale update fails, database data and audit fields are not altered by the failed write.
- A subsequent valid update records the right actor/timestamp.

Do not assert only the exception. Read back from the database to confirm version, content, and audit columns remain consistent.

## 12. Structuring Integration Tests with Testcontainers

Testcontainers lets you run the same database type as production during tests. PostgreSQL example:

~~~java
@DataR2dbcTest
@Import({
        R2dbcConversionConfiguration.class,
        AuditingTestConfiguration.class
})
class CustomerMappingIntegrationTest {

    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void r2dbcProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.r2dbc.url", () ->
                "r2dbc:postgresql://" + postgres.getHost() + ":"
                        + postgres.getFirstMappedPort() + "/"
                        + postgres.getDatabaseName());
        registry.add("spring.r2dbc.username", postgres::getUsername);
        registry.add("spring.r2dbc.password", postgres::getPassword);
    }

    @Autowired
    CustomerProfileRepository repository;
}
~~~

The example requires Testcontainers JUnit Jupiter and PostgreSQL dependencies, plus container lifecycle settings suited to your project's Testcontainers version. Depending on your Spring Boot version, service connections may be used instead of DynamicPropertySource.

### 12.1. Using the Production Database

H2 or mocks can help with fast tests, but cannot replace the production database when checking:

- SQL dialects.
- Native types and converters.
- Timestamp/timezone semantics.
- Identities/sequences.
- Quoting and naming.
- Constraints and transaction behavior.
- Triggers, JSON, UUID, or array types.

If production uses PostgreSQL, run critical mapping integration tests on PostgreSQL. If production supports multiple databases, test each supported dialect separately.

### 12.2. Preparing Test Schemas

Use the same migration tool as production to create the schema. This lets tests detect drift between mappings and migrations.

If tests build schemas with separate scripts, the risk of test schemas diverging from deployed schemas increases. Run the same Flyway/Liquibase migrations or migration suite used in live environments.

### 12.3. Isolating Data Between Tests

R2DBC is reactive and tests can run in parallel. Remember to:

- Use distinct IDs or truncate tables before tests when safe.
- Never share the same row across concurrently running tests.
- Clean up data via explicit transactions or fixtures.
- Never assume @Transactional on a test method wraps the entire subscription like imperative JDBC tests.

Some test slices may configure transactions automatically; check your test framework lifecycle and do not rely on automatic rollback without verifying it.

## 13. Testing Repository Slices vs. Full Application Contexts

You can use @DataR2dbcTest to focus on repositories/mappings while importing required converters and auditing configs. However, slice tests may not load all callbacks or component-scanned beans like the live application.

Maintain at least two groups:

1. **Repository slice tests:** verify mappings, converters, queries, and required callbacks with a small context.
2. **Application integration tests:** start configuration close to production to verify auditing, security contexts, transaction managers, and service pipelines.

If a callback is declared with @Component and the slice test does not scan that bean, import the specific callback into the test context. Do not mistake an unloaded callback for a loaded callback that failed to trigger.

## 14. Testing Callbacks and Auditing with StepVerifier

StepVerifier checks that publishers emit values, complete, or error in expected sequence.

Example verifying a successful save:

~~~java
StepVerifier.create(repository.save(customer))
        .assertNext(saved -> assertThat(saved.getId()).isNotNull())
        .verifyComplete();
~~~

Example verifying a converter/callback error:

~~~java
StepVerifier.create(repository.save(invalidCustomer))
        .expectErrorSatisfies(error ->
                assertThat(error).isInstanceOf(IllegalArgumentException.class))
        .verify();
~~~

If errors are wrapped by Spring Data in another exception, assert according to the actual exception contract of your framework/driver version rather than an assumed class.

### 14.1. Do Not Call block in Reactive Tests

Avoid:

~~~java
Customer saved = repository.save(customer).block();
~~~

block can be used in specific imperative tests designed for it, but StepVerifier keeps tests aligned with the reactive model and makes verifying errors, completion, and cancellation straightforward. Never call block on an event-loop thread.

### 14.2. Testing That Publishers Execute Only Upon Subscription

Repository publishers are normally lazy. When tests need to verify that callbacks run only on subscription, use counters or PublisherProbe. However, testing Reactor laziness does not substitute for integration tests that actually write and read real data.

## 15. Testing Transactions When Callbacks or Auditing Fail

Suppose a service saves an entity and then writes an audit record in the same transaction. If a callback or audit step emits an error, business data must roll back when all operations share the transaction manager and the error escapes outward.

Example:

~~~java
@Transactional
public Mono<CustomerProfile> createWithAudit(CustomerProfile customer) {
    return customerRepository.save(customer)
            .flatMap(saved -> auditRepository.save(
                    AuditRecord.created(saved.getId()))
                    .thenReturn(saved));
}
~~~

Test:

1. Configure the audit repository to emit an error after the entity has been saved.
2. Call the service inside a real transaction.
3. Verify the publisher emits the error.
4. Read the database using a new transaction/connection.
5. Verify neither the customer nor the audit record exists when rollback is expected.

If a callback calls an external service or a secondary publisher that does not participate in the database transaction, database rollback cannot undo that external side effect. Do not use callbacks to hide an implicit distributed transaction.

## 16. Testing Callback Ordering

When multiple callbacks share the same phase or span multiple phases, execution order can affect outcomes. For instance, one callback normalizes a name before another builds a search key.

Make sure to:

- Use Spring's supported ordering mechanism if order is required.
- Write tests recording the sequence of callbacks invoked.
- Verify the final persisted state in the database.
- Never depend on accidental ordering from component scanning or bean declaration order.

Avoid writing callbacks with non-idempotent side effects. Callbacks can run across multiple saves and retries; sending emails or publishing messages inside a callback risks duplicate side effects or executing before transaction commit.

## 17. Testing Direct Queries and Template Updates

Different write paths need separate tests because they follow different lifecycles:

| Write path | Entity mapping | Entity callbacks | Entity auditing |
| --- | --- | --- | --- |
| Repository save(entity) | Yes | Yes, per lifecycle | Yes, if configured |
| Entity insert/save via template | Yes | Yes, per API/lifecycle | Yes, if configured |
| @Modifying @Query | Based on declared SQL/query | Does not run entity save lifecycle automatically | Does not run automatically |
| DatabaseClient | Direct SQL parameter binding | No | No |
| Template update(Query, Update) | Maps update properties/columns | Lacks full entity to run save callbacks | Does not populate automatically |

For every write path used in the application, maintain an integration test verifying critical fields such as version, last_modified_at, last_modified_by, and constraints.

## 18. Common Mistakes When Testing Mapping and Lifecycle

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Converter unit test passes but repository reads wrong value | Converter not registered or SQL type incompatible | Integration round-trip on real database |
| BigDecimal value changes scale | Column precision/scale or converter lacks normalization | Check schema and scale rules |
| Timestamp offset or nanoseconds lost | Database precision differs from Java | Test per column precision and UTC convention |
| Property always null after read | Wrong @Column, constructor mapping, or converter | Check schema, metadata, and row mapping |
| Callback unit test passes but save never invokes it | Callback bean missing from context or wrong callback type | Check test slice/imports and repository lifecycle |
| Direct SQL fails to update audit fields | SQL omits audit columns and no trigger exists | Set explicitly or test database trigger |
| Auditing actor is always null | Reactive context not propagated or auditor provider empty | Test with Reactor Context and security context |
| Created fields get overwritten | SQL/callback/trigger updates wrong fields | Separate created and last-modified rules |
| Test passes with H2 but fails in production | Different dialect/type/transaction semantics | Use Testcontainers with target database |
| Blocking callback hangs tests | Calls block or synchronous service | Chain reactive publishers |
| Version fails to increment on bulk update | Direct SQL does not increment version | Add version = version + 1 and predicate |
| Test order depends on prior/next tests | Shared data, unclear cleanup | Independent fixtures and deterministic cleanup |

## 19. Testing Checklist

- [ ] Entity metadata matches real schema: table, columns, ID, and version.
- [ ] Repository save/find round-trips all properties accurately.
- [ ] Constructors or immutable mappings are tested if used by the application.
- [ ] Nullable and NOT NULL columns are tested separately.
- [ ] BigDecimal precision/scale is verified.
- [ ] Date/time values are tested per database timezone and precision.
- [ ] Reading converters have unit tests.
- [ ] Writing converters have unit tests.
- [ ] Custom conversions are registered in the application context.
- [ ] Converters are round-trip tested through repositories.
- [ ] Callbacks have unit tests and integration tests confirming invocation.
- [ ] Callbacks do not block or call subscribe independently.
- [ ] Failing callbacks produce appropriate rollback behavior.
- [ ] Auditing create and update are tested separately.
- [ ] ReactiveAuditorAware reads the right actor from context.
- [ ] Direct SQL is verified not to trigger entity auditing automatically.
- [ ] Triggers, if present, are tested across all write paths.
- [ ] @Version and stale updates are tested using two entity snapshots.
- [ ] Transaction rollback is confirmed with a fresh connection/transaction.
- [ ] Tests run against a database/dialect close to production.
- [ ] Tests do not depend on other tests' data or execution order.

## 21. Conclusion

Testing mapping, converters, callbacks, and auditing requires combining unit tests with integration tests. Unit tests verify conversion and callback logic in isolation; integration tests confirm Spring Data registers the right converters, maps accurately to the schema, invokes callbacks along the lifecycle, and writes actual audit fields to the database.

Use the same database type as production for critical tests covering SQL types, timestamps, native types, constraints, and transactions. Test entity saves and direct DML separately because @Modifying @Query, DatabaseClient, and partial template updates do not automatically pass through the entity auditing lifecycle. For auditing, test both inserts and updates, reactive actors, deterministic timestamps, and preservation of created fields. For callbacks, ensure reactive publishers never block and errors propagate properly so transactions can roll back.

A trustworthy test does more than verify that a publisher completed; it reads back from the database and confirms stored values, versions, audit metadata, and constraints match the application contract.
