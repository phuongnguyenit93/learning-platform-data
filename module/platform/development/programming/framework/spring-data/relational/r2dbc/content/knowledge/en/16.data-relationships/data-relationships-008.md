# Write Order, Delete Order, and Responsibility for Maintaining Referential Constraints

In a relational database, rows can reference one another through foreign keys. Therefore, insert, update, and delete order must respect the relationship between referenced rows and referencing rows. Spring Data R2DBC maps aggregates and executes data operations, but **the database is what enforces referential constraints**. Applications must design appropriate aggregates, transactions, and deletion policies so multi-step operations always keep data consistent.

When working with Spring Data Relational, distinguish two scopes:

- **Elements belonging to the same aggregate**: managed through the aggregate root and Spring Data Relational mapping.
- **Independent aggregates referencing one another**: their lifecycles are coordinated by business logic and services; Spring Data does not automatically cascade an entire object graph across aggregates.

## 1. Foreign Keys and Operation Order in the Database

Suppose there are two tables: `purchase_order` and `order_line`. Each order line belongs to an order, linked by the `order_id` column.

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE order_line (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT pk_order_line PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_order(id)
        ON DELETE RESTRICT
);
~~~

In this structure:

- `purchase_order` is the parent table.
- `order_line` is the child table.
- `order_line.order_id` is a foreign key referencing `purchase_order.id`.
- An `order_line` row is valid only when the corresponding `purchase_order` row already exists.

Foreign key constraints are checked by the database when statements execute. Inserting a child row with a non-existent `order_id` is rejected by the database. Deleting a parent row while child rows still exist under `RESTRICT`/`NO ACTION` is also rejected.

### 1.1. Basic Ordering Rules

With a foreign key pointing from the child table to the parent table, the safe order is typically:

**Writing data**

1. Insert the parent row to create its primary key.
2. Obtain the parent row's primary key.
3. Insert child rows using that foreign key.

**Deleting data**

1. Delete referencing child rows.
2. Delete the parent row once no prohibited references remain.

If the database supports and is configured with `ON DELETE CASCADE`, deleting the parent row causes the database to delete child rows automatically. The application then does not need to issue delete statements for each child row in that case. Cascade policies must be chosen deliberately.

### 1.2. Constraints Apply Beyond Insert and Delete

Foreign keys also govern updates to referenced keys or FK values:

- Changing `order_line.order_id` to a non-existent ID will be rejected.
- Changing `purchase_order.id` may be blocked while child rows still reference it, unless the database has a suitable `ON UPDATE` action.
- Setting an FK to `NULL` is valid only if the column is nullable and business rules permit an unattached child row.

In standard designs, an aggregate root's primary key should remain immutable after creation. Avoiding ID changes prevents cascading mass updates across references.

## 2. Aggregates and Aggregate Roots in Spring Data Relational

Spring Data Relational organizes data around the aggregate model. An aggregate root is the primary entry point for a group of objects persisted together as one business unit.

For example, a `PurchaseOrder` has `OrderLine`s. Order lines make sense only within an order; the application adds, edits, or removes lines through the `PurchaseOrder` aggregate.

~~~mermaid
flowchart TB
    A["PurchaseOrder<br/>Aggregate root"]
    B["OrderLine 1"]
    C["OrderLine 2"]
    D["OrderLine 3"]
    A --> B
    A --> C
    A --> D
~~~

When mapped as an aggregate, Spring Data Relational knows which child objects belong to which root and how to persist them to related tables. The application operates through the root to save aggregate state.

### 2.1. Mapping Collections with @MappedCollection

Example:

~~~java
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @MappedCollection(
        idColumn = "order_id",
        keyColumn = "line_no"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderNumber, List<OrderLine> lines) {
        this.orderNumber = orderNumber;
        this.lines = new ArrayList<>(lines);
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }
}
~~~

Element type:

~~~java
import org.springframework.data.relational.core.mapping.Table;

@Table("order_line")
public record OrderLine(
    String sku,
    Integer quantity
) {}
~~~

In this example:

- `@MappedCollection` specifies `order_id` as the column linking order lines to the aggregate root ID.
- `keyColumn = "line_no"` stores the collection element's position/key when mapping requires a collection key.
- Spring Data uses this metadata to map order lines belonging to `PurchaseOrder`.

**`@MappedCollection` describes mapping; it does not replace foreign key constraints in the database.** Real constraints must still be created in the schema, typically via migrations.

### 2.2. The Aggregate Root Owns Child Element Lifecycles

If `OrderLine` is a member of `PurchaseOrder`, changes to lines should go through order business logic:

- Add a line to the order.
- Update a line's quantity.
- Remove a line from the order.
- Save the aggregate root.

Do not treat each `OrderLine` as an independent aggregate merely because it sits in its own table. A separate table does not automatically define an aggregate boundary.

Conversely, if an object has an independent lifecycle and independent business rules, treat it as its own aggregate. Reference it by ID and coordinate operations via services rather than expecting Spring Data to cascade across objects automatically.

## 3. Insert Order Within an Aggregate

When creating a new aggregate, the root's primary key may be auto-generated by the database. Child rows need that key value in their FK column.

Conceptual flow:

~~~mermaid
sequenceDiagram
    participant App as Service
    participant SD as Spring Data R2DBC
    participant DB as Database

    App->>SD: save(new PurchaseOrder)
    SD->>DB: INSERT purchase_order
    DB-->>SD: Generated ID
    SD->>DB: INSERT order_line with order_id
    DB-->>SD: Order line insert result
    SD-->>App: Saved aggregate entity
~~~

The crucial rule is that the parent row must exist before child rows can reference it, unless the database and schema use an appropriate deferred constraint mechanism. With auto-generated primary keys, the framework must obtain the root ID in order to write dependent elements.

Using a Repository:

~~~java
import org.springframework.data.repository.reactive.ReactiveCrudRepository;

public interface PurchaseOrderRepository
        extends ReactiveCrudRepository<PurchaseOrder, Long> {
}
~~~

Service saving the aggregate:

~~~java
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    public Mono<PurchaseOrder> create(PurchaseOrder order) {
        return repository.save(order);
    }
}
~~~

When entities use database-generated IDs, consume the aggregate emitted by the `save` publisher. With immutable entities, the resulting instance contains the new ID while the input instance retains its original state.

### 3.1. Inserting with R2dbcEntityTemplate

`R2dbcEntityTemplate` can also persist entities at the aggregate level:

~~~java
Mono<PurchaseOrder> saved =
    template.insert(PurchaseOrder.class)
        .using(order);
~~~

When an entity is mapped as an aggregate with child elements, Spring Data Relational coordinates persisting those elements per the mapping. Do not manually insert the same child lines with separate SQL if aggregate insertion is already responsible for writing them; doing so can create duplicate records.

### 3.2. Ordering with Multiple Dependent Levels

An aggregate can have multiple nested levels of child objects. The general rule remains: write the referenced object before the object referencing it.

Example:

~~~text
purchase_order
    └── order_line
            └── line_note
~~~

If `line_note` has an FK to `order_line`, the `order_line` row must exist before inserting `line_note`. Likewise, `order_line` must have a valid `order_id`.

Spring Data Relational uses aggregate metadata to coordinate operations within the mapping. If additional table relationships sit outside the aggregate or are accessed via other repositories, the service must guarantee proper ordering.

## 4. Order When Saving or Updating an Existing Aggregate

Spring Data Relational does not operate like an ORM with a persistence context and dirty checking across an entire object graph. Calling `save` passes the target aggregate state to persist; the framework generates write operations from mapping metadata and entity state.

For mapped collections belonging to an aggregate, the save strategy may replace existing child rows with the current child collection: deleting old child rows and re-inserting child rows from the submitted aggregate. Keep this in mind when designing child tables and external references.

This implies:

- Do not assume each `OrderLine` is dirty-checked and updated column by column like JPA.
- Saving the root can emit multiple SQL statements for child tables.
- If a child table has its own identifier referenced by external tables, replacing child rows can break or disrupt those external references.
- Keep dependent elements aligned with aggregate boundaries and inspect actual SQL when version-specific behavior matters.

Exact SQL order can depend on operation type, mapping, data access strategy, and Spring Data version. Regardless, relational constraints still require referenced rows to exist before writing FKs and child rows to be handled before deleting parents when cascade is absent.

### 4.1. Updating the Root and Collection

Example of an existing order with an ID whose line items changed:

~~~java
PurchaseOrder changed = /* new aggregate with same ID and updated line list */;

return repository.save(changed);
~~~

Spring Data receives the aggregate root and coordinates saving aggregate members. If another independent table such as inventory also needs updating, that is a separate business operation; never cram it into a collection just hoping `save` will update that table automatically.

### 4.2. Avoid Updating a Partial Aggregate Using an Incomplete Object

If you load partial data and construct a new aggregate root containing only a subset of lines, `save` may treat it as the full desired aggregate state. Elements missing from the object can be deleted from the managed collection.

Therefore:

- When modifying an aggregate, load the full scope managed by persistence.
- Apply changes through aggregate behavior.
- Save the aggregate root again.
- If you only want to update a single column or subset of rows without replacing the entire aggregate, use an explicit update via `Query`/`Criteria` or suitable SQL.

Never pass a partial DTO projection as the aggregate input to `save`.

## 5. Delete Order and ON DELETE Policies

When deleting an aggregate, no child rows referencing the root may remain in the database if constraints disallow orphans.

Two common approaches exist.

### 5.1. Application or Spring Data Deletes Child Rows First

With `RESTRICT`/`NO ACTION` FKs, child rows must be deleted before the parent row.

~~~mermaid
sequenceDiagram
    participant App as Service
    participant SD as Spring Data R2DBC
    participant DB as Database

    App->>SD: delete(PurchaseOrder)
    SD->>DB: DELETE order_line WHERE order_id = ?
    DB-->>SD: Success
    SD->>DB: DELETE purchase_order WHERE id = ?
    DB-->>SD: Success
    SD-->>App: Complete
~~~

When order lines are mapped as aggregate members, deleting the root via Spring Data Relational can coordinate deleting dependent members before deleting the root. The application does not need to manually delete every line when the framework manages them via aggregate mapping.

### 5.2. Database Deletes Child Rows via ON DELETE CASCADE

The schema can declare:

~~~sql
FOREIGN KEY (order_id)
    REFERENCES purchase_order(id)
    ON DELETE CASCADE
~~~

When `purchase_order` is deleted, the database automatically deletes related `order_line` rows. This is a database-level policy, not a Spring Data cascade annotation.

`ON DELETE CASCADE` fits when child lifecycles truly depend on the parent and deleting the parent always means deleting the children. If child data must be retained or go through a separate business workflow, use `RESTRICT`/`NO ACTION` and implement an explicit deletion process.

### 5.3. Choosing RESTRICT, CASCADE, or SET NULL

| Policy | Behavior When Parent Row Is Deleted | Use When |
|---|---|---|
| `RESTRICT` / `NO ACTION` | Rejects if referencing child rows remain | Parent deletion must be blocked while dependent data exists |
| `CASCADE` | Database deletes related child rows | Child rows have no independent lifecycle |
| `SET NULL` | Sets child row FK to `NULL` | Child rows are allowed to exist without a parent |
| `SET DEFAULT` | Sets FK to a default value | A valid default exists and is explicitly designed |

Do not pick `CASCADE` just to make delete statements succeed easily. Cascading deletes can wipe out far more data than callers expect. For financial, audit, or historical data, archiving or soft deletion may be required instead of physical deletion.

`SET NULL` is valid only when the FK column is nullable and business rules allow breaking the link. `SET DEFAULT` requires a default value pointing to a valid parent row if constraints remain enforced.

### 5.4. Deleting the Root via Repository

With a mapped aggregate:

~~~java
Mono<Void> deleteOrder(Long orderId) {
    return repository.deleteById(orderId);
}
~~~

When order lines are aggregate-owned members, Spring Data Relational manages deleting dependent rows according to the mapping. If other tables outside the aggregate also hold references, deleting the root may be blocked by FK constraints; the service must handle those tables or rely on schema cascade policies designed for them.

## 6. Independent Aggregates Referencing One Another

Not every FK relationship represents a parent-child relationship within a single aggregate.

For instance, a `PurchaseOrder` references `Customer`. `Customer` has an independent lifecycle: it can be used across many orders, updated independently, and is not deleted simply because one order is deleted.

In this case, the order model should hold `customerId` rather than embedding the full `Customer` as a cascaded child object:

~~~java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String orderNumber,
    Long customerId
) {}
~~~

Schema:

~~~sql
ALTER TABLE purchase_order
ADD CONSTRAINT fk_purchase_order_customer
FOREIGN KEY (customer_id)
REFERENCES customer(id)
ON DELETE RESTRICT;
~~~

When creating an order:

1. Customer must exist.
2. Application sets `customerId` on `PurchaseOrder`.
3. Save `PurchaseOrder`.
4. Database checks the FK.

When deleting a Customer:

- If orders still reference it, `RESTRICT`/`NO ACTION` blocks the operation.
- If the policy is `CASCADE`, the database would delete orders, which is usually inappropriate if orders must be retained.
- If the policy is `SET NULL`, `purchase_order.customer_id` must be nullable and business rules must allow unlinked orders.

Spring Data does not automatically load or cascade `Customer` when saving `PurchaseOrder` merely because `customerId` is present. The service decides how aggregates coordinate.

### 6.1. Referencing by ID Creates Clear Boundaries

Using IDs for inter-aggregate references helps:

- Prevent accidentally saving a huge object graph.
- Avoid bidirectional reference cycles.
- Decouple transactions and lifecycles of aggregates.
- Clarify which service is responsible for verifying the referenced entity exists.
- Reduce the risk of saving a stale object that overwrites another aggregate's data.

If you need to display `Customer` info alongside `PurchaseOrder`, the service can query both aggregates and combine them in the reactive stream. That is a read operation; it does not mean both aggregates belong to the same persistence unit.

## 7. Join Tables and Many-to-Many Relationships

Many-to-many relationships are commonly modeled with a join table:

~~~sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY
);

CREATE TABLE tag (
    id BIGINT PRIMARY KEY
);

CREATE TABLE product_tag (
    product_id BIGINT NOT NULL,
    tag_id BIGINT NOT NULL,
    PRIMARY KEY (product_id, tag_id),
    FOREIGN KEY (product_id) REFERENCES product(id) ON DELETE CASCADE,
    FOREIGN KEY (tag_id) REFERENCES tag(id) ON DELETE RESTRICT
);
~~~

`product_tag` holds FKs to both `product` and `tag`. When inserting a link, both referenced rows must already exist. Deleting a product can cascade-delete `product_tag` link rows. Deleting a tag with `RESTRICT` prevents deletion while `product_tag` references remain.

If the join table carries business attributes like `assignedAt`, `role`, or `quantity`, model it as an explicit association entity. Then determine which aggregate owns the association entity or whether it has an independent lifecycle.

Do not assume Spring Data R2DBC manages all many-to-many relationships like an ORM. Mapping and service design must represent join-table operations explicitly.

## 8. How Are Responsibilities Divided Across Layers?

Maintaining referential constraints is a shared responsibility, with each layer serving a distinct role.

| Layer | Responsibility |
|---|---|
| Database schema | Defines PK, FK, `NOT NULL`, `UNIQUE`, and `ON DELETE`/`ON UPDATE` actions |
| Spring Data Relational mapping | Describes tables, columns, aggregate roots, and dependent elements |
| Spring Data R2DBC / Spring R2DBC | Executes write/delete statements via `ConnectionFactory` and driver |
| Domain model | Defines which elements belong to the aggregate, add/remove preconditions, and business rules |
| Application service | Coordinates multiple aggregates, operation order, and transactions |
| Migration/schema management | Creates, alters, and deploys constraints consistently across environments |

### 8.1. The Database Is the Final Integrity Guard

Do not rely solely on Java checks like "found Customer before inserting Order". Data can change between the check and the insert, or another application can write to the same database.

Foreign key constraints ensure the database never accepts an orphaned reference even under concurrent clients.

### 8.2. Mapping Does Not Automatically Create Constraints

`@MappedCollection` tells Spring Data how to link aggregate elements. `@Table`, `@Column`, and `@Id` describe entity mapping. Those annotations do not mean the database actually has a `FOREIGN KEY` constraint.

Constraints must exist in the schema. Manage DDL using versioned migrations such as Flyway or Liquibase, or your project's schema management tool. Verify schemas remain consistent across local, test, staging, and production.

### 8.3. Services Coordinate Business Logic Across Aggregates

If an operation must:

- Create an order.
- Decrease inventory.
- Record payment history.
- Create an audit entry.

then these are multiple business operations potentially spanning multiple aggregates or independent tables. The service must define ordering, transaction boundaries, and error handling. Do not expect saving one aggregate root to execute those steps automatically.

## 9. Transactions When Writing or Deleting Multiple Rows

A single aggregate operation may generate multiple SQL statements. If one statement succeeds and the next fails, data risks being left in a partial state if operations are not inside the same transaction.

Example creating an order with root and lines:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import reactor.core.publisher.Mono;

@Service
public class OrderApplicationService {

    private final PurchaseOrderRepository orderRepository;

    public OrderApplicationService(
            PurchaseOrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public Mono<PurchaseOrder> place(PurchaseOrder order) {
        return orderRepository.save(order);
    }
}
~~~

With reactive transactions, the method returns `Mono` or `Flux` and the transaction binds to the reactive context. You must have an `R2dbcTransactionManager` matching the `ConnectionFactory` used by the repository.

### 9.1. Multiple Operations Requiring One Transaction

Example order placement flow saving the order and updating inventory:

~~~java
@Transactional
public Mono<PurchaseOrder> placeOrder(
        PurchaseOrder order,
        Long productId,
        int quantity) {

    return orderRepository.save(order)
        .flatMap(saved ->
            inventoryRepository.decrease(productId, quantity)
                .thenReturn(saved)
        );
}
~~~

This example assumes both repositories share the same `ConnectionFactory` and transaction manager. If inventory update fails, the transaction rolls back the order insert when the error propagates along the same reactive chain.

Do not call `subscribe()` inside a transactional method to launch a detached publisher. Do not call `block()` arbitrarily to force synchronous results. Both practices can execute work outside the reactive transaction context or allow the transaction to finish before the operation completes.

### 9.2. A Single Transaction Does Not Automatically Span Multiple Databases

If operations use multiple `ConnectionFactory` instances or multiple databases, a local `R2dbcTransactionManager` does not create a distributed transaction. Design workflows using outbox, saga, or other coordination patterns when consistency spans multiple systems.

### 9.3. Constraints Can Be Checked at Different Times

Many databases check FKs immediately per statement. Some database engines support deferring constraints until the end of a transaction if declared accordingly.

Do not rely on deferred constraints to reverse operation order if the application must run across multiple database engines. Designing inserts as parent-before-child and deletes as child-before-parent is far more portable.

## 10. Handling Referential Constraint Errors

When the database rejects an operation due to an FK violation, the driver raises an error and Spring can translate it into an appropriate data access exception.

Common scenarios:

| Error | Cause | Handling |
|---|---|---|
| Child insert fails | FK points to a non-existent parent | Verify ID and insert order |
| Parent delete fails | Referencing children remain under `RESTRICT`/`NO ACTION` | Delete children per business flow or pick appropriate policy |
| FK update fails | New parent ID does not exist | Verify the referenced entity |
| Delete cascade deletes too much | `CASCADE` policy is broader than intended | Review schema and aggregate scope |
| Transaction rollback | One operation in the write chain failed | Handle error in service and inspect entire unit of work |
| Unique violation re-inserting children | Collection written with duplicates or wrong key mapping | Check `keyColumn`, primary key, and aggregate data |

Never catch an FK error and ignore it as if the operation succeeded. Errors indicate a broken integrity rule or operation order; handle them according to business semantics.

You can translate persistence errors into clear domain/API errors in the service layer, such as "cannot delete a customer with existing orders". Never expose raw SQL or internal database details in public responses.

## 11. Soft Delete and Data History

Physical deletion is not always appropriate. For data needing auditing or history, applications can use soft delete:

~~~java
@Table("customer")
public record Customer(
    @Id Long id,
    String fullName,
    Boolean deleted
) {}
~~~

With soft delete, the parent row stays in the database so child FKs remain valid. However, the application must consistently exclude soft-deleted records from normal queries.

Soft delete does not replace FK constraints. It is an application-layer business rule; the database still sees the parent row as present until physically deleted.

If a data purge job runs later, that job must still obey FK order or cascade rules just like normal physical deletion.

## 12. Circular References and Unorderable Dependencies

Designs can accidentally create circular references:

~~~text
table_a.b_id → table_b.id
table_b.a_id → table_a.id
~~~

If both FKs are `NOT NULL` and checked immediately on insert, neither row A nor row B can be inserted first because the other row does not yet exist.

Ways to resolve this:

- Redesign so only one direction of reference is needed.
- Allow one FK to be nullable on initial insert, then update the link within the same transaction.
- Use deferred constraints if supported by the database and vendor lock-in is acceptable.
- Extract the relationship into a join table created after both endpoints exist.

In aggregate modeling, a circular reference between two independent aggregates is usually a sign to revisit domain boundaries. Keeping unidirectional references by ID is easier to manage than a bidirectional object graph.

## 13. Testing Constraints and Write/Delete Order

Tests should run on a database whose behavior closely matches production. H2 can help for basic checks, but does not guarantee identical constraint, DDL, cascade, and dialect behavior compared to PostgreSQL, MySQL, or other engines.

Scenarios to test:

- Inserting a new aggregate creates the root and child rows with valid FKs.
- Inserting a child referencing a non-existent ID is rejected by the database.
- Saving an existing aggregate preserves child rows in the expected state.
- Deleting an aggregate under `RESTRICT` handles child rows per mapping or is blocked as designed.
- `ON DELETE CASCADE` deletes only the rows permitted to cascade.
- Deleting a parent referenced by another aggregate is rejected.
- Failure on the final step inside a transaction rolls back earlier steps.
- Updating an FK to a non-existent parent is rejected.
- Collection mappings with `keyColumn` produce valid keys and ordering.

Tests should inspect final database state after operations, not merely verify that the publisher completed. For transaction rollbacks, re-query data to prove no partial writes remain.

## 14. Practical Design Principles

- Define aggregate roots and which objects truly belong inside each aggregate.
- Use `@MappedCollection` for dependent collections; use migrations to create real FK constraints.
- Insert referenced rows before rows referencing them.
- Delete child rows before parent rows unless using `ON DELETE CASCADE`.
- Choose `RESTRICT`, `CASCADE`, or `SET NULL` based on business rules and retention needs.
- Do not assume Spring Data automatically cascades across independent aggregates.
- Reference other aggregates by ID and coordinate via services.
- Avoid letting external tables reference child elements that may be replaced when saving an aggregate.
- Use reactive transactions when multiple SQL statements must succeed or roll back together.
- Keep publishers inside the same reactive chain; do not `subscribe`/`block` arbitrarily in services.
- Keep primary keys immutable; avoid changing IDs of referenced parent rows.
- Test FKs and operation ordering on the target database engine.
- Surface integrity constraint errors rather than silently ignoring them.
- Use soft delete or archiving when data must retain history.

## 15. Key Takeaways

Foreign keys are a database rule: referenced rows must exist and cannot be deleted while prohibited references remain. Therefore, in standard parent-child relationships, insert the parent before the child and delete the child before the parent, unless the schema defines an explicit cascade policy or alternative constraint mechanism.

Spring Data Relational manages mapped members of an aggregate via the aggregate root; `@MappedCollection` describes mapping relationships without creating foreign keys itself. For independent aggregates, applications reference by ID and services coordinate ordering, transactions, and deletion policies. Database constraints serve as the final integrity guard, mapping tells the framework how to persist data, and the domain/service layers determine the lifecycle and business meaning of operations.
