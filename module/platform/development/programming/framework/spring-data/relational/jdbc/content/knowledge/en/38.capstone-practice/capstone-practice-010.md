# Extended Practice: Soft Delete, Multiple DataSources, and Batch Import

In this lab, you will build a product catalog synchronization pipeline from a source database to a target database using Spring Data Relational JDBC. The system preserves history of discontinued records via **soft delete**, reads and writes across **two DataSources**, and imports data in **batches** to bound memory usage and connection hold times.

Three skills are combined in one workflow:

1. Soft delete changes an aggregate's business status while keeping the row in the database.
2. Multiple DataSources require separating JDBC operations and transaction managers per database.
3. Batch import splits large work into chunks that can be retried and resumed from checkpoints.

The scenario is a catalog system pulling product snapshots from a legacy system. Each import has its own run ID. Products appearing in the snapshot are marked as seen in that run. Only after the entire snapshot has been read and written successfully are synchronized products missing from the snapshot soft-deleted. If an import fails mid-run, the system must not mass-delete products.

## 1. Objectives and architecture

Upon completion, you will be able to:

- Design `deleted_at` and `deleted_by` columns and write queries returning only active records.
- Implement soft delete and restore using conditional SQL.
- Understand that Spring Data JDBC does not automatically filter every query to hide soft-deleted records.
- Configure separate source and target DataSources.
- Choose the right transaction manager for each operation.
- Read source records using keyset pagination and write target records in batches.
- Save checkpoints in the same transaction as each chunk's data.
- Re-run imports without creating duplicate records.
- Soft-delete missing records only after verifying snapshot completeness.
- Test commits, rollbacks, retries, and mid-chunk failures.

Overall architecture:

~~~text
Legacy database
    |
    | sourceDataSource
    v
Import coordinator
    |
    +--> read one page by source ID
    +--> validate / normalize
    |
    v
Catalog writer
    |
    | targetDataSource
    | catalogTransactionManager
    v
Catalog database
    +--> catalog_product
    +--> catalog_import_run
    +--> catalog_import_error
~~~

The source database and target database have separate transactions. Each chunk written to the catalog commits independently; the entire job is not a distributed transaction.

## 2. Business rules

Lock down rules before writing code:

| Question | Lab rule |
|---|---|
| When is a product soft-deleted? | When it does not appear in a fully completed snapshot |
| Is it physically deleted immediately? | No; retain the row for lookup and recovery |
| Should an admin-soft-deleted product automatically reactivate on import? | No; manual delete wins |
| What if a SKU is already used by another active product? | Reject the conflicting record and log an import error |
| What if the import fails midway? | Do not execute the final soft-delete step |
| Can the same import be re-run? | Yes; use run ID, source ID, and checkpoint for idempotency |
| Can two imports for the same source run concurrently? | No; only one active run per scope/source |

Without explicit rules, batch imports can accidentally resurrect manually deleted records, wipe out products on a source read error, or overwrite an actively used SKU.

## 3. Designing the target database schema

Examples use PostgreSQL to illustrate partial unique indexes and `ON CONFLICT`. For other databases, adapt upsert and index syntax to the target dialect.

### 3.1. Product table

~~~sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    source_system VARCHAR(40) NOT NULL,
    source_id VARCHAR(100) NOT NULL,
    sku VARCHAR(80) NOT NULL,
    name VARCHAR(250) NOT NULL,
    last_seen_import_run_id UUID,
    deleted_at TIMESTAMPTZ,
    deleted_by VARCHAR(120),
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_modified_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_catalog_source_record
        UNIQUE (source_system, source_id)
);

CREATE UNIQUE INDEX uq_catalog_active_sku
    ON catalog_product (sku)
    WHERE deleted_at IS NULL;

CREATE INDEX ix_catalog_import_run_seen
    ON catalog_product (source_system, last_seen_import_run_id);
~~~

`source_system` and `source_id` identify the record in the source system. This pair lets imports recognize the same product across runs, even if its SKU changes.

`last_seen_import_run_id` indicates which snapshot last observed the product. The finalization step uses this column to find missing records.

`deleted_at IS NULL` means the product is active. The timestamp represents both the deletion status and deletion time; `deleted_by` records the actor who performed the action.

The partial unique index guarantees SKU uniqueness only among active products. Soft-deleted records can keep their old SKUs for historical tracking. This is PostgreSQL syntax; for databases without partial indexes, design an alternative unique key such as a generated column or an active-SKU tracking table.

### 3.2. Import run tracking table

~~~sql
CREATE TABLE catalog_import_run (
    id UUID PRIMARY KEY,
    source_system VARCHAR(40) NOT NULL,
    scope_key VARCHAR(100) NOT NULL,
    status VARCHAR(20) NOT NULL,
    source_high_watermark VARCHAR(100),
    last_processed_source_id VARCHAR(100),
    expected_count BIGINT,
    processed_count BIGINT NOT NULL DEFAULT 0,
    started_at TIMESTAMPTZ NOT NULL,
    completed_at TIMESTAMPTZ,
    error_message TEXT
);

CREATE INDEX ix_catalog_import_run_scope_status
    ON catalog_import_run (source_system, scope_key, status);
~~~

Statuses can be `RUNNING`, `COMPLETED`, `FAILED`, or `CANCELLED`. `last_processed_source_id` is the checkpoint of the last committed chunk.

### 3.3. Import error table

~~~sql
CREATE TABLE catalog_import_error (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    import_run_id UUID NOT NULL,
    source_id VARCHAR(100),
    row_number BIGINT,
    error_code VARCHAR(80) NOT NULL,
    message TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX ix_catalog_import_error_run
    ON catalog_import_error (import_run_id);
~~~

The error table preserves why a row was rejected without losing information about the import run. Whether to continue or halt when data errors occur must be defined by business policy.

## 4. Mapping the aggregate with Spring Data JDBC

The Java entity models soft-delete state as regular properties:

~~~java
import java.time.Instant;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("catalog_product")
public class CatalogProduct {

    @Id
    private final Long id;

    @Column("source_system")
    private final String sourceSystem;

    @Column("source_id")
    private final String sourceId;

    private final String sku;
    private final String name;

    @Column("last_seen_import_run_id")
    private final UUID lastSeenImportRunId;

    @Column("deleted_at")
    private final Instant deletedAt;

    @Column("deleted_by")
    private final String deletedBy;

    @Version
    private final Long version;

    // Persistence constructor, getters, and withers matching the mapping.
}
~~~

This is a mapping skeleton for an immutable entity. When implementing, provide a persistence constructor and withers or whatever instantiation mechanism your Spring Data JDBC version supports. You can use Lombok `@Value` and `@With` to reduce boilerplate.

Repository:

~~~java
public interface CatalogProductRepository
        extends CrudRepository<CatalogProduct, Long> {

    @Query("""
        SELECT *
        FROM catalog_product
        WHERE id = :id
          AND deleted_at IS NULL
        """)
    Optional<CatalogProduct> findActiveById(@Param("id") Long id);

    @Query("""
        SELECT *
        FROM catalog_product
        WHERE sku = :sku
          AND deleted_at IS NULL
        """)
    Optional<CatalogProduct> findActiveBySku(@Param("sku") String sku);
}
~~~

This example highlights that business queries must explicitly include `deleted_at IS NULL`. If using derived queries, you can declare methods on the `deletedAt` property with an `IsNull` condition, provided the mapping and property name match.

**Spring Data JDBC does not automatically add a soft-delete filter to every query.** `findById`, custom queries, `JdbcTemplate` SQL, reports, and relational queries must all obey this policy. A `deletedAt` property is not an automatic filtering mechanism.

## 5. Implementing soft delete and restore

Soft delete is a conditional `UPDATE` operation rather than calling the repository's `deleteById()`.

### 5.1. Soft delete via SQL

~~~sql
UPDATE catalog_product
SET deleted_at = :deletedAt,
    deleted_by = :actor,
    version = version + 1,
    last_modified_at = :deletedAt
WHERE id = :id
  AND deleted_at IS NULL
  AND version = :expectedVersion;
~~~

The `deleted_at IS NULL` predicate prevents repeated calls from re-deleting an already deleted record. The `version` predicate protects against updates based on stale state when optimistic locking is used.

Illustrative service:

~~~java
@Service
public class CatalogLifecycleService {

    private final NamedParameterJdbcOperations jdbc;
    private final Clock clock;

    public CatalogLifecycleService(
            @Qualifier("catalogJdbcOperations")
            NamedParameterJdbcOperations jdbc,
            Clock clock) {
        this.jdbc = jdbc;
        this.clock = clock;
    }

    @Transactional(transactionManager = "catalogTransactionManager")
    public void softDelete(long id, long expectedVersion, String actor) {
        Instant now = Instant.now(clock);

        MapSqlParameterSource parameters = new MapSqlParameterSource()
            .addValue("id", id)
            .addValue("expectedVersion", expectedVersion)
            .addValue("deletedAt", Timestamp.from(now))
            .addValue("actor", actor);

        int updated = jdbc.update(SOFT_DELETE_SQL, parameters);

        if (updated != 1) {
            throw new IllegalStateException(
                "Product is missing, already deleted, or version changed"
            );
        }
    }
}
~~~

`SOFT_DELETE_SQL` is a constant holding the `UPDATE` statement above. This example assumes `actor` has been authenticated at the application layer. Never accept an arbitrary actor from an untrusted payload when reliable identity tracking is required.

### 5.2. Restore with conflict checking

Restore clears `deleted_at` and `deleted_by` back to `NULL`:

~~~sql
UPDATE catalog_product
SET deleted_at = NULL,
    deleted_by = NULL,
    version = version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NOT NULL;
~~~

Because the unique index applies only to active rows, restore can fail if another active product has claimed that SKU. That is a business conflict to surface to the caller rather than silently altering the SKU.

You can check SKU availability before restoring to provide a friendly error message, while still handling the unique constraint because two requests can race concurrently.

### 5.3. Do not soft-delete by deleting child rows

Spring Data JDBC treats the aggregate as the unit of persistence. When soft-deleting a root, child rows remain in the database. That is usually desirable to preserve history.

Decide explicitly:

- Can child rows be accessed directly after the root is soft-deleted?
- Must child queries `JOIN` the root and filter `deleted_at IS NULL`?
- When the root is restored, does child data automatically become available again?
- Are there separate history or audit tables that must be preserved?

Do not physically delete child rows just because the root transitions to soft-deleted if the business needs to restore the aggregate.

## 6. Separating DataSources for source and target

This lab uses two resources:

- `sourceDataSource`: reads snapshots from the legacy database.
- `catalogDataSource`: writes products, import runs, checkpoints, and errors to the target database.

Each resource has its own JDBC operations and transaction manager:

~~~java
@Configuration
public class ImportDataSourceConfiguration {

    @Bean
    @ConfigurationProperties("app.datasource.source")
    DataSource sourceDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    @ConfigurationProperties("app.datasource.catalog")
    DataSource catalogDataSource() {
        return DataSourceBuilder.create().build();
    }

    @Bean
    NamedParameterJdbcOperations sourceJdbcOperations(
            @Qualifier("sourceDataSource") DataSource source) {
        return new NamedParameterJdbcTemplate(source);
    }

    @Bean
    NamedParameterJdbcOperations catalogJdbcOperations(
            @Qualifier("catalogDataSource") DataSource catalog) {
        return new NamedParameterJdbcTemplate(catalog);
    }

    @Bean
    PlatformTransactionManager sourceTransactionManager(
            @Qualifier("sourceDataSource") DataSource source) {
        return new JdbcTransactionManager(source);
    }

    @Bean
    PlatformTransactionManager catalogTransactionManager(
            @Qualifier("catalogDataSource") DataSource catalog) {
        return new JdbcTransactionManager(catalog);
    }
}
~~~

If Spring Data JDBC repositories are used for the catalog, configure `@EnableJdbcRepositories` so the repository package points to `catalogJdbcOperations` and `catalogTransactionManager`. Source access can use `JdbcTemplate` or `NamedParameterJdbcTemplate` directly if it only reads legacy data.

Never use the catalog transaction manager to manage queries running on `sourceDataSource`. Nor should you assume two JDBC transaction managers automatically form a single atomic transaction.

## 7. Reading source data with keyset pagination

Do not load the entire legacy table into a `List`. Read page by page using ascending keys:

~~~sql
SELECT id, sku, product_name
FROM legacy_product
WHERE id > :lastSeenId
  AND id <= :highWatermark
ORDER BY id
LIMIT :pageSize;
~~~

`highWatermark` is the highest ID captured at the start of the snapshot. It stops newly inserted rows with higher IDs from endlessly extending the job. If the source receives content updates during the import, you also need a consistent snapshot, an immutable export table, a CDC watermark, or an appropriate locking mechanism; pinning the max ID alone does not freeze existing rows' values.

Source read DTO:

~~~java
public record SourceProduct(
    long id,
    String sku,
    String name
) {
}
~~~

Reader:

~~~java
public class LegacyProductReader {

    private final NamedParameterJdbcOperations sourceJdbc;

    public LegacyProductReader(
            @Qualifier("sourceJdbcOperations")
            NamedParameterJdbcOperations sourceJdbc) {
        this.sourceJdbc = sourceJdbc;
    }

    public List<SourceProduct> readPage(
            long lastSeenId,
            long highWatermark,
            int pageSize) {

        return sourceJdbc.query("""
            SELECT id, sku, product_name
            FROM legacy_product
            WHERE id > :lastSeenId
              AND id <= :highWatermark
            ORDER BY id
            LIMIT :pageSize
            """,
            new MapSqlParameterSource()
                .addValue("lastSeenId", lastSeenId)
                .addValue("highWatermark", highWatermark)
                .addValue("pageSize", pageSize),
            (rs, rowNum) -> new SourceProduct(
                rs.getLong("id"),
                rs.getString("sku"),
                rs.getString("product_name")
            )
        );
    }
}
~~~

The SQL example uses `LIMIT` for PostgreSQL/MySQL. SQL Server or Oracle require different pagination syntax. The reader returns a bounded page; the source connection can return to the pool right after the query finishes.

## 8. Creating import runs and checkpoints

Before reading data, create a run record in the catalog database:

~~~sql
INSERT INTO catalog_import_run (
    id, source_system, scope_key, status,
    source_high_watermark, last_processed_source_id,
    expected_count, processed_count, started_at
)
VALUES (
    :runId, :sourceSystem, :scopeKey, 'RUNNING',
    :highWatermark, NULL, :expectedCount, 0, CURRENT_TIMESTAMP
);
~~~

The run ID must remain stable throughout the run and be persisted where it can be recovered after a worker restart. Generating a fresh run ID on every restart without an idempotency key makes it hard to distinguish retries from new imports.

The checkpoint stores the last source ID of the committed chunk. Updating products and updating the checkpoint must happen in the same catalog transaction:

~~~text
BEGIN catalog transaction
    UPSERT chunk products
    UPDATE catalog_import_run checkpoint/count
COMMIT
~~~

If the transaction rolls back, both the upsert and the checkpoint roll back. On retry, the chunk is re-read from the previous checkpoint and safely reapplied via idempotent upserts.

## 9. Writing chunks with batch upserts

For high-volume imports, use `NamedParameterJdbcTemplate.batchUpdate` to minimize database round trips. Sample PostgreSQL SQL:

~~~sql
INSERT INTO catalog_product (
    source_system, source_id, sku, name,
    last_seen_import_run_id, deleted_at, deleted_by,
    version, last_modified_at
)
VALUES (
    :sourceSystem, :sourceId, :sku, :name,
    :runId, NULL, NULL, 0, CURRENT_TIMESTAMP
)
ON CONFLICT (source_system, source_id)
DO UPDATE SET
    sku = EXCLUDED.sku,
    name = EXCLUDED.name,
    last_seen_import_run_id = EXCLUDED.last_seen_import_run_id,
    version = catalog_product.version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE catalog_product.deleted_at IS NULL;
~~~

The final predicate preserves products that were manually soft-deleted. If the business wants imports to automatically restore reappearing source products, design an explicit restore policy and handle SKU collisions before enabling that behavior.

The writer can construct batch parameters:

~~~java
public record ImportProduct(
    String sourceId,
    String sku,
    String name
) {
}

@Service
public class CatalogImportWriter {

    private final NamedParameterJdbcOperations catalogJdbc;

    public CatalogImportWriter(
            @Qualifier("catalogJdbcOperations")
            NamedParameterJdbcOperations catalogJdbc) {
        this.catalogJdbc = catalogJdbc;
    }

    @Transactional(transactionManager = "catalogTransactionManager")
    public void writeChunk(
            UUID runId,
            String sourceSystem,
            List<ImportProduct> chunk,
            String lastProcessedSourceId) {

        SqlParameterSource[] parameters = chunk.stream()
            .map(product -> new MapSqlParameterSource()
                .addValue("sourceSystem", sourceSystem)
                .addValue("sourceId", product.sourceId())
                .addValue("sku", product.sku())
                .addValue("name", product.name())
                .addValue("runId", runId))
            .toArray(SqlParameterSource[]::new);

        catalogJdbc.batchUpdate(UPSERT_SQL, parameters);

        catalogJdbc.update("""
            UPDATE catalog_import_run
            SET last_processed_source_id = :lastId,
                processed_count = processed_count + :chunkSize
            WHERE id = :runId
              AND status = 'RUNNING'
            """,
            new MapSqlParameterSource()
                .addValue("lastId", lastProcessedSourceId)
                .addValue("chunkSize", chunk.size())
                .addValue("runId", runId));
    }
}
~~~

`UPSERT_SQL` is a constant containing the SQL statement above. In production code, inspect batch results, handle `BatchUpdateException`, and distinguish actual update counts from special JDBC driver constants like `SUCCESS_NO_INFO`. Never assume every driver always returns an exact row count of `1` per entry.

A chunk should commit only once both the product data and the checkpoint have been persisted successfully.

## 10. Coordinating the batch import

The coordinator does not hold one long catalog transaction across the entire job. It reads a source page, validates it, and invokes the writer to commit one chunk:

~~~java
@Service
public class CatalogImportCoordinator {

    private final LegacyProductReader reader;
    private final CatalogImportWriter writer;
    private final ImportRunService runs;

    public CatalogImportCoordinator(
            LegacyProductReader reader,
            CatalogImportWriter writer,
            ImportRunService runs) {
        this.reader = reader;
        this.writer = writer;
        this.runs = runs;
    }

    public void execute(ImportRun run, int pageSize) {
        long lastId = run.lastProcessedSourceIdAsLong();

        while (true) {
            List<SourceProduct> page = reader.readPage(
                lastId,
                run.highWatermark(),
                pageSize
            );

            if (page.isEmpty()) {
                break;
            }

            List<ImportProduct> valid = validateAndMap(page);
            String checkpoint = Long.toString(
                page.get(page.size() - 1).id()
            );

            writer.writeChunk(
                run.id(),
                run.sourceSystem(),
                valid,
                checkpoint
            );

            lastId = page.get(page.size() - 1).id();
        }

        runs.completeAndSoftDeleteMissing(run.id());
    }
}
~~~

This is a coordination skeleton. Validation must explicitly decide whether an invalid row halts the run or gets logged to the error table and skipped. If skipping invalid rows is allowed, never mark the run as complete as if it were a full snapshot and soft-delete old data. You can require zero critical errors before finalization.

In real implementations, read the checkpoint from the catalog database upon restart instead of keeping it only in a local variable. After each chunk commits, update `lastId` from the saved checkpoint.

## 11. Soft-deleting missing records only after import completion

This is the most critical step. If missing products were marked deleted after each page, a product appearing on a later unread page would be wrongly soft-deleted.

Run finalization only after:

- The entire source snapshot range has been read.
- All required chunks have committed.
- The checkpoint has reached the high watermark.
- Processed counts match expected counts or the error policy.
- No errors occurred that render the snapshot incomplete.
- The run is still `RUNNING` and has not been finalized by another worker.

Finalization SQL:

~~~sql
UPDATE catalog_product
SET deleted_at = CURRENT_TIMESTAMP,
    deleted_by = :actor,
    version = version + 1,
    last_modified_at = CURRENT_TIMESTAMP
WHERE source_system = :sourceSystem
  AND deleted_at IS NULL
  AND (
      last_seen_import_run_id IS NULL
      OR last_seen_import_run_id <> :runId
  );
~~~

In practice, further restrict by `scope_key`, tenant, or data segment owned by the run. Never execute this `UPDATE` across the entire catalog when the source manages only a subset of data.

After soft-deleting, mark the run `COMPLETED` in the same catalog transaction:

~~~sql
UPDATE catalog_import_run
SET status = 'COMPLETED',
    completed_at = CURRENT_TIMESTAMP
WHERE id = :runId
  AND status = 'RUNNING';
~~~

If updating the run status fails, the finalization transaction must roll back so data is not left soft-deleted while the run fails to record completion.

### 11.1. Guarding against abnormally empty snapshots

If the source returns zero rows due to a connection glitch, wrong filter, or schema change, finalization could soft-delete the entire scoped catalog.

Add guards:

- Compare `expected_count` against actual read count.
- Reject empty snapshots if business rules forbid an empty catalog.
- Set a threshold for abnormal count drops.
- Log and require confirmation when snapshot counts drop sharply.
- Proceed to finalization only after the import run passes all guards.

A valid empty snapshot can still happen, yet it must be an explicit business decision.

## 12. Retries, idempotency, and failure recovery

A job may stop after several chunks have already committed. The design must allow resuming without creating duplicates or mislabeling records.

### 12.1. Idempotency by source identity

The unique constraint on `(source_system, source_id)` ensures the same source record never produces multiple target products. Upsert updates the existing record and records the new run ID.

If the same chunk is re-executed:

- Records are not duplicated.
- Product attributes are updated from the source.
- `last_seen_import_run_id` stays set to the current run.
- The checkpoint is rewritten inside the chunk's transaction.

External side effects like sending emails or publishing events need their own idempotency keys; upserts alone do not prevent them from firing twice.

### 12.2. Recovering when a chunk fails

If a chunk fails:

1. The catalog transaction rolls back.
2. Products in that chunk are not partially saved.
3. The checkpoint does not advance.
4. The coordinator logs the error or leaves the run eligible for retry per policy.
5. On restart, the worker reads the latest committed checkpoint.
6. The uncommitted chunk is re-read and reprocessed.

Never advance the checkpoint before the batch upsert succeeds. Advancing the checkpoint ahead of the data causes retries to skip unwritten rows.

### 12.3. When the source database cannot roll back with the target

The reader only reads from the source; the writer writes to the target. Two databases do not share an atomic transaction. If the source mutates during the import, the snapshot may become inconsistent.

Solutions depending on requirements:

- Create an immutable snapshot/export table at the source.
- Use a snapshot/read-only transaction on the source if read duration and database capabilities allow.
- Capture a high watermark or CDC offset.
- Use `updated_at` and `version` to detect mutations, with explicit resolution rules.
- Persist each page's payload into target staging tables before applying.

Do not hold distributed transactions open just to lock two databases across a long-running job.

## 13. Running multiple imports and avoiding race conditions

Two concurrent runs for the same source/scope can corrupt `last_seen_import_run_id`. For instance, runs A and B interleave writes to the same product; A's finalization might treat a product recently updated by B as missing.

Choose a locking mechanism per source/scope:

- A unique constraint allowing only one `RUNNING` run per scope if the database supports partial unique indexes.
- A lock/job-lease table with owner and expiry.
- A distributed lock with fencing tokens.
- A job scheduler preventing overlapping executions.

At finalization, verify the run still holds valid ownership. Do not rely solely on `status = 'RUNNING'` if multiple workers could process the same run.

A worker can resume a run after restart, but lease/heartbeats or fencing is needed so an old worker cannot continue writing after ownership transfers.

## 14. Handling already soft-deleted products

An import may encounter a source record matching a product that was manually soft-deleted. This lab picks the **manual delete wins** policy:

- Upsert does not modify rows where `deleted_at IS NOT NULL`.
- The record stays excluded from active queries.
- The import does not erase the administrator's audit state.
- Restoring requires calling an explicit restore operation with SKU validation.

If the business treats the source as the single source of truth and reappearing records must auto-restore, adjust the upsert/finalization logic to reflect that policy. Record a clear restore actor and handle unique SKU conflicts.

Never let an import silently resurrect records merely because they appear in a snapshot when the prior deletion was an intentional administrative decision.

## 15. Integrating Spring Batch at scale

For complex jobs, Spring Batch provides the `Job`, `Step`, `ItemReader`, `ItemProcessor`, and `ItemWriter` model with chunked transactions.

~~~text
CatalogImportJob
    |
    +--> Step 1: CreateImportRun
    |
    +--> Step 2: Read / validate / write chunks
    |       +--> source reader
    |       +--> item processor
    |       +--> catalog writer
    |
    +--> Step 3: Verify snapshot completeness
    |
    +--> Step 4: Soft-delete missing products
    |
    +--> Step 5: Mark run COMPLETED
~~~

Spring Batch manages checkpoints and restart metadata per job/step execution. You still must configure the right transaction manager for the writer database. When reader and writer use two DataSources, separate reader and writer transactions; committing a chunk on the target does not commit/roll back the source transaction in a distributed fashion.

For smaller exercises, a hand-written coordinator may suffice. For production jobs needing retry policies, skip policies, restarts, metrics, and execution history, Spring Batch is usually a better fit.

## 16. Testing with a real database

Use Testcontainers or an equivalent integration test environment to verify the target database dialect. H2 cannot substitute for PostgreSQL when tests rely on partial indexes, `ON CONFLICT`, UUIDs, or specific transaction semantics.

Use two separate databases or two separate containers to test resource boundaries. Even if using two schemas on one server, recognize they share physical infrastructure and do not form a distributed transaction.

### 16.1. Testing soft delete

- Create an active product.
- Call soft delete.
- Confirm `deleted_at` and `deleted_by` are populated.
- Confirm active queries exclude the product.
- Confirm admin queries can still read the deleted product.
- Call soft delete a second time and verify idempotent behavior.
- Restore the product and confirm it reappears in active queries.
- Create a SKU conflict and confirm restore is rejected.

### 16.2. Testing a successful batch import

1. Seed 1,200 products in the source database.
2. Run the import with page size 200.
3. Verify multiple chunks committed.
4. Verify `processed_count` and the checkpoint.
5. Confirm the catalog contains all products.
6. Confirm the run transitioned to `COMPLETED`.
7. Confirm old products absent from the snapshot were soft-deleted.

### 16.3. Testing mid-run failures

- Let the first chunk commit.
- Force the next chunk to fail.
- Verify the checkpoint stays at the last committed chunk.
- Verify the run is not yet `COMPLETED`.
- Verify finalization has not run.
- Restart the same run.
- Verify retried chunks do not create duplicates.
- Verify missing records are soft-deleted only after full completion.

### 16.4. Testing DataSource separation

## 19. Conclusion

This lab combines soft delete, multiple DataSources, and batch import into a resilient synchronization pipeline. Soft delete preserves history and requires all active queries to filter out deleted records; Spring Data JDBC does not apply this filter automatically across access paths. Two DataSources require distinct JDBC operations and transaction managers because standard JDBC transactions do not provide cross-database atomicity.

Batch imports should read by keyset pages, write in chunks, and update checkpoints in the same transaction as chunk data. Upserts keyed by source identity make retries idempotent. Most importantly, soft-delete missing products only after the snapshot is verified complete and the run finalizes successfully. If an import stops midway, previously committed chunks are preserved and work resumes from the checkpoint; the final soft-delete sweep must wait until the entire snapshot finishes.

In production, add scope locking, empty-snapshot guards, import run monitoring, data-error policies, and integration tests against the real database and driver. These safeguards keep data synchronization safe across retries, restarts, source changes, and multiple workers.
