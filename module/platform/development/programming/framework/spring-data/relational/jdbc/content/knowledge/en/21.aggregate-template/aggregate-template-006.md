# Combining `Query`, `Sort`, and `Pageable` with the Template

In **Spring Data JDBC**, `JdbcAggregateTemplate` provides a lower-level API than repositories for working directly with aggregate roots. When you need to build search criteria from runtime parameters, sort by multiple criteria, and paginate results, you can combine three Spring Data abstractions:

- **`Query`** describes filter criteria, selected columns, sort order, and query limit/offset.
- **`Sort`** describes ascending/descending ordering across one or more properties.
- **`Pageable`** describes the requested page, page size, and associated `Sort`.

`JdbcAggregateTemplate` accepts a `Query` to read aggregates. `Query.with(pageable)` translates page details into `offset`, `limit`, and sort order. In current Spring Data Relational APIs, the template returns a `List` from `findAll(Query, Class)`; to build a `Page<T>` with the total element count, the application also calls `count(Query, Class)` and constructs a `PageImpl`.

## 1. Role of `JdbcAggregateTemplate`

Repositories usually fit operations expressed as methods like `findByStatus(...)`, `findByCreatedAtAfter(...)`, or `findAll(Pageable)`. `JdbcAggregateTemplate` becomes useful when query criteria are built dynamically—for example, a search screen with multiple optional filters—or when a service coordinates aggregate operations without declaring numerous repository methods.

The template operates at the **aggregate root boundary**. When querying and mapping a `PurchaseOrder`, Spring Data JDBC uses the metadata of the root and its owned aggregate components to build objects. `Query` here is a structured query model, not an arbitrary SQL string like `@Query`.

In a Spring Boot application with standard Spring Data JDBC configuration, `JdbcAggregateTemplate` can be injected directly:

```java
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;

@Service
public class PurchaseOrderSearchService {
    private final JdbcAggregateTemplate template;

    public PurchaseOrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }
}
```

Do not call the template's constructor manually in a service. Spring Boot/Spring Data JDBC creates and configures the JDBC infrastructure, mapping context, converters, and data access strategy that the template relies on.

## 2. Data Model Used in Examples

Suppose an order management system has the following attributes:

- `orderNumber`: order number.
- `status`: current status.
- `total`: total order amount.
- `createdAt`: creation timestamp.

Aggregate root entity:

```java
import java.math.BigDecimal;
import java.time.LocalDateTime;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        String status,
        BigDecimal total,
        LocalDateTime createdAt
) {}
```

Illustrative DDL for H2:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    total DECIMAL(18, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Java property names are mapped by Spring Data Relational according to metadata/naming strategy—for example, `orderNumber` to `order_number` and `createdAt` to `created_at`. In the `Criteria` and `Sort` examples below, use aggregate property names such as `status`, `total`, `createdAt`, and `id`.

## 3. `Query`: Describing Filter Conditions

`Query` belongs to package `org.springframework.data.relational.core.query`. You can build a query from `Criteria`:

```java
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Query query = Query.query(
        Criteria.where("status").is("OPEN")
);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Equivalent SQL semantics:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?;
```

The value `OPEN` is passed as a predicate parameter; the query API does not require concatenating user values into a SQL string.

### Combining Multiple Conditions

`Criteria` supports operators such as `is`, `greaterThan`, `greaterThanOrEquals`, `lessThan`, `between`, `in`, `like`, `isNull`, and `isNotNull`, along with `and`/`or` combinators.

Example finding open orders with a total of 1,000 or more:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .and("total").greaterThanOrEquals(new BigDecimal("1000.00"));

Query query = Query.query(criteria);
List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Equivalent SQL semantics:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
  AND total >= ?;
```

You can also add time range predicates:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .and("createdAt").greaterThanOrEquals(from)
        .and("createdAt").lessThan(to);
```

### Combining `OR`

Example finding orders that are open or marked urgent:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .or("priority").is("URGENT");
```

When conditions involve multiple `AND`/`OR` groups, build explicit `Criteria` groups to express the intended logical parentheses. Do not rely on long chained calls without verifying the desired SQL expression.

### Query Without Conditions

When you want to query all aggregates while still applying `Sort`, `limit`, or `offset`, you can use:

```java
Query query = Query.empty();
```

Or use the overload `template.findAll(PurchaseOrder.class, sort)` if you simply need to load all orders in sorted order. `Query.empty()` is helpful when building a unified structured query without requiring a `WHERE` clause.

## 4. `Sort`: Ordering by One or More Properties

`Sort` belongs to `org.springframework.data.domain`. A `Sort` can contain one or more `Sort.Order` entries.

Sorting by creation timestamp descending:

```java
import org.springframework.data.domain.Sort;

Sort sort = Sort.by(Sort.Order.desc("createdAt"));

List<PurchaseOrder> orders = template.findAll(
        PurchaseOrder.class,
        sort
);
```

Sorting by total descending, then by ID ascending:

```java
Sort sort = Sort.by(
        Sort.Order.desc("total"),
        Sort.Order.asc("id")
);

Query query = Query.query(Criteria.where("status").is("OPEN"))
        .sort(sort);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Equivalent SQL semantics:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
ORDER BY total DESC, id ASC;
```

The secondary `id ASC` ordering makes results deterministic when multiple orders share the same total. This is especially important with pagination: if rows tie on the primary sort value and lack a unique tie-breaker, rows can shift positions across page reads.

### Ascending/Descending and Multiple Criteria

```java
Sort sort = Sort.by(
        Sort.Order.asc("status"),
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("id")
);
```

Orders are applied in declaration order. The database sorts by `status` first, breaks ties by `createdAt` descending, and breaks remaining ties by `id` ascending.

`Sort` takes property paths that the mapping can resolve—not arbitrary SQL snippets. If `sortBy` comes from an HTTP request, validate it against a whitelist of allowed properties; never pass raw client strings directly into query configuration.

## 5. Combining `Query` and `Sort`

`Query.sort(sort)` returns a new `Query` with the sort information attached:

```java
Query query = Query.query(
        Criteria.where("status").is("OPEN")
                .and("total").greaterThan(new BigDecimal("500.00"))
).sort(Sort.by(Sort.Order.desc("createdAt")));

List<PurchaseOrder> result = template.findAll(query, PurchaseOrder.class);
```

`JdbcAggregateTemplate.findAll(Query, Class)` executes the query, materializes the matching aggregates, and returns a `List`. If the `Query` has a `Sort`, the list is ordered accordingly.

Note that `Query` is **immutable**. Methods such as `sort`, `limit`, `offset`, `columns`, and `with` create a new instance. You must capture the return value:

```java
Query query = Query.query(Criteria.where("status").is("OPEN"));
query = query.sort(Sort.by("createdAt").descending());
```

The following does not modify `query` because the newly returned instance is discarded:

```java
query.sort(Sort.by("createdAt").descending()); // New Query is discarded
```

## 6. `Pageable`: Page, Page Size, and Order

`Pageable` belongs to `org.springframework.data.domain`. The typical factory is `PageRequest.of(pageNumber, pageSize, sort)`:

```java
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);
```

Parameters:

- `pageNumber`: zero-based page index, so `0` is the first page.
- `pageSize`: maximum number of rows per page.
- `sort`: ordering applied to the page data.

For page `2` with size `20`, the offset is `2 × 20 = 40`. The query skips the first 40 rows under the specified sort order and then fetches at most 20 rows.

`Pageable` does not execute SQL directly. It merely carries pagination and sorting metadata; the template receives that information via `Query.with(pageable)` or through an API overload appropriate to the Spring Data JDBC version.

## 7. Applying `Pageable` to `Query` with `with`

`Query.with(pageable)` merges page settings into the query. According to the Spring Data Relational API, this sets `offset`, `limit`, and applies the `Sort` contained in `Pageable`.

```java
Criteria criteria = Criteria.where("status").is("OPEN");
Query baseQuery = Query.query(criteria);

Pageable pageable = PageRequest.of(
        1,
        10,
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);

Query pageQuery = baseQuery.with(pageable);
List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
```

In this example:

- `baseQuery` only contains the `status = OPEN` predicate.
- `pageable` requests the second page (page number `1`), 10 rows per page.
- `pageQuery` contains the predicate, sort, offset `10`, and limit `10`.
- `findAll(pageQuery, PurchaseOrder.class)` returns a list of up to 10 aggregates.

Equivalent SQL semantics:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
ORDER BY created_at DESC, id ASC
OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;
```

The actual row-limiting syntax depends on the dialect. Some databases use `LIMIT ... OFFSET ...`, while others use `OFFSET ... FETCH NEXT ...` or another syntax. `JdbcAggregateTemplate` and the dialect handle generating the corresponding SQL.

When using a `Pageable` that includes a `Sort`, avoid also calling `query.sort(...)` with a different sort unless intentional. Keep sorting in one place to avoid confusion when two sort sources exist.

## 8. Building `Page<T>` from the Template in Current APIs

One version detail to note: `JdbcAggregateTemplate.findAll(Query, Class, Pageable)` previously returned `Page<T>`, but since Spring Data Relational **4.0** it has been marked deprecated for removal in a future release. Combining data retrieval with total element counting places pagination responsibilities on the template that fit repositories better.

Current APIs provide these operations:

- `findAll(Query, Class<T>)`: returns `List<T>` for a query with conditions, sort, limit, and offset.
- `count(Query, Class<T>)`: counts total aggregates matching the query.
- `Query.with(Pageable)`: translates page, size, and sort into query settings.

Therefore, to return `Page<T>`, execute the page content query, execute the count query on the **unpaginated query**, and build a `PageImpl`:

```java
import java.util.List;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderSearchService {
    private final JdbcAggregateTemplate template;

    public PurchaseOrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional(readOnly = true)
    public Page<PurchaseOrder> findOpenOrders(Pageable pageable) {
        Query baseQuery = Query.query(
                Criteria.where("status").is("OPEN")
        );

        Query pageQuery = baseQuery.with(pageable);
        List<PurchaseOrder> content = template.findAll(
                pageQuery,
                PurchaseOrder.class
        );

        long total = template.count(baseQuery, PurchaseOrder.class);

        return new PageImpl<>(content, pageable, total);
    }
}
```

`PageImpl` belongs to `org.springframework.data.domain`. It accepts the page content, `Pageable`, and total element count. The result exposes helpers such as `getContent()`, `getNumber()`, `getSize()`, `getTotalElements()`, `getTotalPages()`, `hasNext()`, and `hasPrevious()`.

### Why Keep `baseQuery` Separate?

`baseQuery` represents the full filtered dataset, such as all `OPEN` orders. `pageQuery` is simply a copy of that query with offset, limit, and sort applied for the current page.

```java
Query baseQuery = Query.query(Criteria.where("status").is("OPEN"));
Query pageQuery = baseQuery.with(pageable);

List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
long total = template.count(baseQuery, PurchaseOrder.class);
```

Do not pass the paginated query into `count`:

```java
long total = template.count(pageQuery, PurchaseOrder.class); // Not the total across the whole filtered set
```

`Page.getTotalElements()` represents the total count of orders matching the filter, not the row count on the current page alone. Thus, the count query uses the same filter criteria without page limits.

### Transactions and Consistency Between the Two Queries

Building a `Page` this way executes at least two queries: one to fetch `content` and one `COUNT` query. If data changes between the two executions, `content` and `total` can reflect two different points in time. `@Transactional(readOnly = true)` groups both into the same transaction, though consistent snapshot visibility depends on isolation level and database behavior. If business rules require strict snapshot consistency, choose an appropriate isolation level and evaluate locking/concurrency costs.

## 9. Combining Dynamic Filters, Sort, and Pageable

Real search screens often have optional filters. You can construct `Criteria` first and then apply `Sort`/`Pageable`.

Example service accepting status and minimum total:

```java
@Transactional(readOnly = true)
public Page<PurchaseOrder> search(
        String status,
        BigDecimal minimumTotal,
        Pageable pageable
) {
    Criteria criteria = Criteria.where("status").is(status)
            .and("total").greaterThanOrEquals(minimumTotal);

    Query baseQuery = Query.query(criteria);
    List<PurchaseOrder> content = template.findAll(
            baseQuery.with(pageable),
            PurchaseOrder.class
    );
    long total = template.count(baseQuery, PurchaseOrder.class);

    return new PageImpl<>(content, pageable, total);
}
```

If filters are truly optional, only append a predicate when its parameter has a value. For example:

```java
Criteria criteria = Criteria.empty();

if (status != null && !status.isBlank()) {
    criteria = criteria.and("status").is(status);
}

if (minimumTotal != null) {
    criteria = criteria.and("total").greaterThanOrEquals(minimumTotal);
}

Query baseQuery = Query.query(criteria);
```

Both `Criteria` and `Query` follow an immutable API style. After calling `and`, `or`, `sort`, `limit`, `offset`, or `with`, assign the returned object back to a variable. In versions or APIs where `Criteria.empty()` has specific limitations when chaining the first predicate, you can build a list of criteria and combine them with `Criteria.from(...)`; always check the signatures for your project's Spring Data Relational version.

Never construct a query by concatenating column names or request values into SQL strings. `Criteria` keeps predicates structured and ensures values are bound via JDBC.

## 10. Using `Sort` Standalone When `Page` Is Not Needed

If a use case only needs a filtered and sorted list, there is no need to construct a `Page`:

```java
Query query = Query.query(
        Criteria.where("status").is("OPEN")
).sort(
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Or if simply loading every aggregate in sorted order:

```java
List<PurchaseOrder> orders = template.findAll(
        PurchaseOrder.class,
        Sort.by(Sort.Order.asc("orderNumber"))
);
```

Do not run `count` if the caller does not need the total element count. Avoid executing an expensive count query merely to return a list.

## 11. Using `limit` and `offset` Directly on `Query`

`Query` also allows setting limit and offset without creating a `Pageable`:

```java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("id")
);

Query query = Query.query(Criteria.where("status").is("OPEN"))
        .sort(sort)
        .limit(20)
        .offset(40);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

This retrieves up to 20 rows after skipping the first 40 rows in the chosen sort order. It is handy for internal batch jobs or when callers just need a data window without a `Page` object.

Comparison:

| API | Information Represented | Result |
|---|---|---|
| `Query.sort(sort)` | Ordering | Sorted query |
| `Query.limit(n)` | Maximum row count | Bounded query |
| `Query.offset(n)` | Rows to skip | Query starting after offset |
| `Query.with(pageable)` | Sort + page size + page offset | Query with complete page info |
| `template.findAll(query, type)` | Executes query | `List<T>` |
| `template.count(query, type)` | Counts matching set | `long` |

## 12. Distinguishing `Page`, `Slice`, and `List`

When designing a search API, decide whether the caller genuinely needs the total element count.

| Return Type | Information Provided | Typical Cost |
|---|---|---|
| `List<T>` | Content of fetched rows | One data query |
| `Page<T>` | Content, current page, total elements, total pages | Typically one data query plus one count query |
| `Slice<T>` | Content and whether a next page exists | Can fetch one extra row to determine `hasNext`, no total count needed |

`JdbcAggregateTemplate.findAll(Query, Class)` returns `List`, not `Page` or `Slice` directly. If you need `Page`, combine `findAll` with `count` as shown above. If you only need to know whether more data exists, you can fetch `pageSize + 1` rows via `limit`, inspect the extra row, and return a DTO or `Slice` constructed at the application layer. Skip `count` when totals are unused.

On repository methods, Spring Data JDBC supports pagination types such as `Pageable` and `Page` directly on query methods. If the use case is a standard repository query, repository pagination can be more concise than manually pairing two template queries.

## 13. Why Template `Pageable` Overloads Require Version Attention

In current APIs, the following overloads were deprecated starting in Spring Data Relational 4.0 and scheduled for removal:

```java
template.findAll(PurchaseOrder.class, pageable);

template.findAll(query, PurchaseOrder.class, pageable);
```

They previously returned `Page<T>` directly. Current API documentation recommends using:

```java
Query pageQuery = query.with(pageable);
List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
long total = template.count(query, PurchaseOrder.class);
Page<PurchaseOrder> page = new PageImpl<>(content, pageable, total);
```

This snippet cleanly separates concerns: `Query` defines the page data, `count` determines the total count, and `PageImpl` packages page metadata. If your project uses an older Spring Data JDBC version, signatures and deprecation status may differ; check the Javadoc for the exact version declared in your build file before applying.

## 14. Limitations When Querying by Aggregate

`JdbcAggregateTemplate` reads aggregate roots along with their owned aggregate components according to Spring Data JDBC mapping. A query returning many roots may incur the cost of loading child collections/entities depending on the model.

Therefore:

- Do not paginate by calling unbounded `findAll()` and slicing with `subList`; push `limit`/`offset` down to the database via `Query`.
- Filter on properties supported by the mapping; do not treat `Criteria` as a tool for writing arbitrary JOINs across independent aggregates.
- If you need JOIN reports or projections rather than full aggregates, consider repository queries, custom repository fragments, or `JdbcTemplate` with DTO/`RowMapper`.
- If a root has a very large child collection, paginating roots does not paginate individual children inside each root.
- If you need to stream a large dataset, consider `streamAll(Query, Class)` and manage stream/transaction/resource lifecycles properly; do not leave streams open longer than the needed transaction scope.

`Query.columns(...)` can restrict selected columns, but when constructing a full aggregate, ensure all columns required by the mapping are returned. Partial projections are usually better served by dedicated DTO/read models.

## 15. `Pageable` Performance: Offset Pagination and Stable Ordering

`Pageable` pagination is typically implemented via offset/limit. This is easy to understand and fits numbered-page UIs, but large offsets can force the database to skip many rows before returning the desired page.

For example, page 500 with size 50 requires an offset of 24,950. On large tables, skipping tens of thousands of rows can become costly depending on execution plans and indexes.

For reliable pagination:

1. Always specify a `Sort` when display order matters.
2. Append a unique key as the final tie-breaker, such as `id ASC`, when sort values can tie.
3. Add indexes matching filter conditions and sort order when execution plans show they are needed.
4. Cap page size at the API layer to prevent oversized requests.
5. For very large datasets or deep pages, consider keyset/seek pagination instead of offset pagination.

Keyset pagination typically uses the last values from the previous page as the starting cursor for the next page—such as `(created_at, id) < (:lastCreatedAt, :lastId)` for descending sort. It requires dedicated queries and cursor conditions; do not assume `PageRequest` converts itself into keyset pagination.

## 16. Safe Dynamic Sorting

An API may accept `sortBy` and `direction` from a client. Never forward arbitrary property names straight into a query. Map allowed options instead:

```java
private Sort resolveSort(String sortBy, boolean descending) {
    String property = switch (sortBy) {
        case "created" -> "createdAt";
        case "amount" -> "total";
        case "number" -> "orderNumber";
        default -> "createdAt";
    };

    Sort.Direction direction = descending
            ? Sort.Direction.DESC
            : Sort.Direction.ASC;

    return Sort.by(
            new Sort.Order(direction, property),
            Sort.Order.asc("id")
    );
}
```

Then:

```java
Pageable pageable = PageRequest.of(
        pageNumber,
        pageSize,
        resolveSort(sortBy, descending)
);
```

This snippet permits only three known sort fields. In production APIs, also validate `pageNumber >= 0`, cap `pageSize`, and handle invalid sort names according to the application's contract.

## 17. Common Mistakes

| Symptom | Common Cause | Resolution |
|---|---|---|
| `findAll(query, type)` returns too many rows | Query lacks limit/offset or `Pageable` was not applied | Use `query.with(pageable)` or `.limit().offset()` |
| Sort has no effect | Forgot to assign new `Query` returned by `.sort()`, or `Pageable` has no `Sort` | Capture fluent call return value and inspect `pageable.getSort()` |
| Pages show duplicate or shifting rows | Sort lacks a unique tie-breaker when values match | Add `id` as a secondary sort criterion |
| `Page.getTotalElements()` equals only the page row count | Passed paginated query into `count` | Count using `baseQuery` without offset/limit |
| `Page` content and total do not match | Two queries ran at different times under concurrent writes | Consider transaction and isolation level |
| API reports empty page despite large total | Page number out of range or offset miscalculated | Remember page numbers are 0-based and verify size |
| Sorting by column name fails | Used an identifier that the mapping cannot resolve | Use valid aggregate property names and verify metadata |
| Clients can sort by arbitrary columns | Unvalidated sort property passed directly | Map client input via a whitelist of allowed properties |
| Deprecation warnings on `findAll(..., Pageable)` | Project uses Spring Data Relational 4.0+ | Use `Query.with(pageable)`, `findAll(Query, Class)`, `count`, and `PageImpl` |
| Dynamic query yields wrong filtering | Misgrouped `and`/`or` `Criteria` chains | Build explicit groups and verify equivalent SQL |
| Deep pagination is slow | Large offset or missing index | Inspect execution plan and consider keyset pagination |

## 18. Practice Exercise: Filtering, Sorting, and Paginating Orders

Using the `PurchaseOrder` entity and `purchase_orders` table from Section 2, populate data with various statuses and totals. Then perform the following:

1. Use `Query.query(Criteria.where("status").is("OPEN"))` to fetch only open orders.
2. Use `Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))` to sort by newest creation time first, then by ID.
3. Use `PageRequest.of(0, 10, sort)` to request the first page of up to 10 orders.
4. Apply `baseQuery.with(pageable)` and call `template.findAll(pageQuery, PurchaseOrder.class)`.
5. Call `template.count(baseQuery, PurchaseOrder.class)` to retrieve the total open orders and build `PageImpl`.
6. Move to the second page (`PageRequest.of(1, 10, sort)`) and verify the offset is 10.
7. Add `total >= 1000` to `Criteria` and ensure both the content query and count query share the same filter.
8. Remove the secondary `id` sort criterion, create multiple orders with identical `createdAt`, and observe why page ordering can become unstable.
9. Use `Query.limit(10).offset(20)` directly and compare it with `Query.with(Pageable)`.
10. Enable SQL logging in development to inspect the `WHERE`, `ORDER BY`, `LIMIT/OFFSET`, or dialect-specific pagination clauses generated.

The goal is to understand how filter conditions, sorting, and page windows work together, while seeing clearly why `Page` requires a separate total count alongside page content.

## 19. Key Principles to Remember

- `Query` describes `Criteria`, columns, sort, limit, and offset; it is an immutable object.
- `Criteria` builds `WHERE` clauses using predicates such as `is`, `greaterThanOrEquals`, `between`, `in`, `isNull`, and `and`/`or` combinators.
- `Sort` describes ordering by one or more properties; include a unique key like `id` for deterministic ordering.
- `Pageable` holds the zero-based page number, page size, and `Sort`.
- `Query.with(pageable)` applies offset, limit, and `Sort` onto a new `Query`.
- `template.findAll(Query, Class)` returns `List<T>`; `template.count(Query, Class)` counts matching aggregates.
- To build `Page<T>` in current APIs, keep the base query, fetch content with the paginated query, count with the unpaginated query, and wrap in `PageImpl`.
- `JdbcAggregateTemplate.findAll(..., Pageable)` overloads are deprecated as of Spring Data Relational 4.0; check Javadoc for your exact project version.
- If you only need a `List`, skip `count`; if you need `Page` metadata, compute the total.
- Offset pagination can degrade on deep pages; consider keyset pagination when data scale demands it.

When combining `Query`, `Sort`, and `Pageable` with `JdbcAggregateTemplate`, keep **filter conditions**, **sort order**, **data window**, and **total result count** clearly separated. `Query` defines the query, `Sort` defines ordering, `Pageable` translates pages into limit/offset, and `count` supplies the total for building `Page`. This separation makes dynamic queries predictable and avoids depending on deprecated pagination overloads in newer Spring Data Relational versions.
