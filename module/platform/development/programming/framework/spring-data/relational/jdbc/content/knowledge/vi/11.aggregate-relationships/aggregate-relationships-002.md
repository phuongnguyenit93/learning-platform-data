# Ánh xạ Set cho tập entity con

Trong một aggregate của Spring Data JDBC, aggregate root có thể sở hữu nhiều entity con. Khi các phần tử con cần được quản lý như một tập hợp **không trùng lặp**, Java `Set` là một lựa chọn phù hợp. Spring Data Relational cung cấp `@MappedCollection` để mô tả collection thuộc aggregate, trong đó bảng con lưu khóa ngoại trỏ về aggregate root.

Ánh xạ `Set` có một số điểm cần phân biệt với `List` và `Map`: Set không biểu diễn thứ tự hay vị trí phần tử, tính duy nhất phụ thuộc vào `equals()`/`hashCode()` của phần tử, và database vẫn cần constraint riêng nếu tính duy nhất là một quy tắc dữ liệu bắt buộc. Bài học này trình bày cách khai báo, lưu và kiểm thử tập entity con trong Spring Data JDBC.

## 1. Set trong mô hình aggregate

Giả sử hệ thống bán hàng có aggregate `PurchaseOrder`. Một đơn hàng chứa nhiều `OrderLine`. Các dòng hàng được tạo, sửa và xóa thông qua đơn hàng; chúng không có vòng đời nghiệp vụ độc lập với root.

Nếu một dòng hàng được xác định bằng một khóa ổn định và không cho phép cùng một dòng xuất hiện hai lần trong tập, có thể biểu diễn collection bằng:

```java
private Set<OrderLine> lines = new LinkedHashSet<>();
```

`Set` thể hiện ngữ nghĩa tập hợp:

- Mỗi phần tử chỉ xuất hiện một lần theo quy tắc so sánh của Java.
- Không có vị trí phần tử như `List`.
- Không có key riêng cho từng phần tử như `Map`.
- Thứ tự duyệt phụ thuộc implementation của Set; không nên xem thứ tự đó là thứ tự lưu trữ trong database.

`Set` phù hợp khi nghiệp vụ quan tâm **những thành viên nào thuộc tập hợp**, không quan tâm chúng được thêm ở vị trí thứ mấy.

### 1.1. Aggregate root vẫn là điểm truy cập

Ví dụ:

```text
PurchaseOrder (aggregate root)
    |
    +-- OrderLine (entity con)
    +-- OrderLine (entity con)
    +-- OrderLine (entity con)
```

Bên ngoài aggregate nên gọi hành vi trên `PurchaseOrder` như `addLine` hoặc `removeLine`. Không nên để nhiều service tự sửa Set con, vì như vậy các invariant như trạng thái đơn hàng, số lượng hợp lệ và quy tắc dòng hàng trùng lặp có thể bị bỏ qua.

Trong Spring Data JDBC, repository thông thường được định nghĩa cho **aggregate root**. Tập `OrderLine` được lưu/nạp như một phần của aggregate khi root được persistence.

## 2. @MappedCollection dùng để làm gì?

Annotation `@MappedCollection` thuộc Spring Data Relational:

```java
import org.springframework.data.relational.core.mapping.MappedCollection;
```

Annotation mô tả quan hệ giữa property collection trên root và dữ liệu được lưu ở bảng con. Hai thuộc tính quan trọng:

| Thuộc tính | Ý nghĩa |
| --- | --- |
| `idColumn` | Tên cột trong bảng con dùng để lưu ID của aggregate root sở hữu collection. |
| `keyColumn` | Tên cột dùng để lưu key hoặc vị trí của phần tử đối với các kiểu collection có key/index phù hợp, chẳng hạn `Map` hoặc `List`. |

Với `Set`, không có index hay key collection do Set không có vị trí phần tử. Thông thường chỉ cần chỉ định `idColumn`:

```java
@MappedCollection(idColumn = "order_id")
private Set<OrderLine> lines = new LinkedHashSet<>();
```

Ví dụ này nói rằng các hàng trong bảng con được liên kết với root qua cột `order_id`. Spring Data JDBC dùng mapping metadata để tìm và ghi các phần tử thuộc đơn hàng.

**Không cần tạo một cột thứ tự chỉ để ánh xạ Set.** Nếu schema có cột sequence dùng để xác định thứ tự nghiệp vụ, cần xem xét liệu collection thực sự nên là `List` hay dữ liệu cần được sắp xếp bằng truy vấn riêng.

## 3. Schema quan hệ cho tập entity con

Giả sử bảng root và bảng con được định nghĩa như sau:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL UNIQUE,
    status VARCHAR(24) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_key UUID NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),
    CONSTRAINT uq_order_lines_key
        UNIQUE (order_id, line_key),
    CONSTRAINT ck_order_lines_quantity
        CHECK (quantity > 0)
);
```

Trong cấu trúc này:

- `purchase_orders.id` là khóa chính của aggregate root.
- `order_lines.id` là khóa chính của entity con.
- `order_lines.order_id` là khóa ngoại trỏ về root.
- `line_key` là định danh ổn định của dòng hàng trong domain, được ứng dụng tạo ra.
- `UNIQUE(order_id, line_key)` bảo đảm một dòng có cùng identity không bị ghi hai lần trong cùng đơn.
- `CHECK(quantity > 0)` bảo vệ thêm một invariant ở database.

`@MappedCollection(idColumn = "order_id")` phải khớp chính xác với cột foreign key `order_lines.order_id`. Tên bảng/cột trong ví dụ có thể được cấu hình bằng annotation hoặc NamingStrategy tùy convention của dự án.

### 3.1. Quan hệ Set không nhất thiết cần join table

Với entity con được root sở hữu, mô hình thường là bảng con chứa foreign key về root:

```text
purchase_orders
  id (PK)
  order_number
  status
       |
       | 1 - N
       v
order_lines
  id (PK)
  order_id (FK)
  line_key
  sku
  quantity
```

Đây là quan hệ một-nhiều theo ownership của aggregate. `@MappedCollection` không có nghĩa rằng framework luôn tạo một bảng nối riêng. Trong ví dụ này, bảng `order_lines` vừa lưu dữ liệu dòng hàng vừa lưu khóa ngoại về root.

Nếu một đối tượng được nhiều aggregate độc lập cùng tham chiếu, không nên biến nó thành child chỉ vì muốn đưa nó vào một Set. Khi đó cần mô hình hóa tham chiếu bằng ID hoặc thiết kế quan hệ liên kết phù hợp với ownership.

## 4. Khai báo aggregate root với Set

Ví dụ root đơn giản:

```java
import java.util.Collections;
import java.util.LinkedHashSet;
import java.util.Set;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;
    private OrderStatus status;

    @MappedCollection(idColumn = "order_id")
    private Set<OrderLine> lines = new LinkedHashSet<>();

    protected PurchaseOrder() {
        // Dùng cho cơ chế materialization.
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
        this.status = OrderStatus.DRAFT;
    }

    public void addLine(String sku, int quantity) {
        requireDraft();

        OrderLine line = OrderLine.create(sku, quantity);
        if (!lines.add(line)) {
            throw new IllegalArgumentException(
                "Dòng hàng đã tồn tại trong đơn"
            );
        }
    }

    public void removeLine(java.util.UUID lineKey) {
        requireDraft();
        lines.removeIf(line -> line.hasKey(lineKey));
    }

    public Set<OrderLine> getLines() {
        return Collections.unmodifiableSet(lines);
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    private void requireDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                "Chỉ có thể sửa đơn hàng ở trạng thái DRAFT"
            );
        }
    }
}
```

`LinkedHashSet` giữ thứ tự chèn **trong bộ nhớ Java**, thuận tiện khi debug hoặc duyệt collection trong cùng một instance. Điều này không biến Set thành collection có thứ tự được database bảo đảm. Khi tải lại aggregate, thứ tự hàng được database trả về không được bảo đảm nếu truy vấn không có `ORDER BY` và mapping không lưu một cột thứ tự.

Phương thức `getLines()` trả về view không cho caller thêm/xóa phần tử trực tiếp. Root giữ quyền điều khiển collection để kiểm tra trạng thái và invariant.

Ví dụ enum:

```java
public enum OrderStatus {
    DRAFT,
    SUBMITTED,
    CANCELLED
}
```

## 5. Thiết kế entity con và equals/hashCode

Điểm quan trọng nhất khi dùng Set là **tính duy nhất của Java Set được quyết định bởi equals/hashCode**. Nếu không thiết kế hai phương thức này đúng, collection có thể loại nhầm phần tử hoặc chứa những phần tử được xem là trùng nhau theo cách không phù hợp với nghiệp vụ.

Một cách làm là gán cho mỗi dòng hàng một identity ổn định ngay khi tạo:

```java
import java.util.Objects;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("line_key")
    private UUID lineKey;

    private String sku;
    private int quantity;

    protected OrderLine() {
        // Dùng cho cơ chế materialization.
    }

    private OrderLine(UUID lineKey, String sku, int quantity) {
        if (lineKey == null) {
            throw new IllegalArgumentException("lineKey bắt buộc");
        }
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU bắt buộc");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity phải dương");
        }

        this.lineKey = lineKey;
        this.sku = sku;
        this.quantity = quantity;
    }

    public static OrderLine create(String sku, int quantity) {
        return new OrderLine(UUID.randomUUID(), sku, quantity);
    }

    public boolean hasKey(UUID key) {
        return lineKey.equals(key);
    }

    public UUID getLineKey() {
        return lineKey;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (!(other instanceof OrderLine that)) {
            return false;
        }
        return lineKey.equals(that.lineKey);
    }

    @Override
    public int hashCode() {
        return Objects.hash(lineKey);
    }
}
```

Trong ví dụ:

- `id` là khóa chính database, có thể được database sinh khi insert.
- `lineKey` được tạo khi dòng hàng hình thành, không đổi trong vòng đời của entity.
- `equals` và `hashCode` dựa trên `lineKey` ổn định, không dựa trên `id` có thể thay đổi từ `null` thành giá trị database cấp.
- `quantity` có thể thay đổi mà không làm thay đổi hash của phần tử.

Đây là một chiến lược minh họa. Nếu domain có một khóa tự nhiên bất biến và duy nhất phù hợp, có thể dùng khóa đó. Nếu dòng hàng được nhận diện bởi nhiều thuộc tính, hãy xác định rõ quy tắc identity nghiệp vụ thay vì tùy tiện so sánh toàn bộ field.

### 5.1. Tránh hashCode dựa trên ID database được sinh

Một lỗi phổ biến là:

```java
@Override
public int hashCode() {
    return Objects.hash(id);
}
```

Khi object mới được thêm vào `HashSet`, `id` có thể đang là `null`. Sau khi lưu, database sinh ID và framework gán ID mới vào object hoặc tạo object kết quả mới. Nếu hashCode của phần tử thay đổi sau khi nó đã được đặt vào HashSet, cấu trúc nội bộ của HashSet không còn tra cứu phần tử theo bucket cũ một cách đáng tin cậy.

Điều này có thể làm `contains` hoặc `remove` hoạt động bất ngờ.

Nếu dùng identity database được cấp sau insert, cần thiết kế equals/hashCode phù hợp với lifecycle đó. Dùng một identity ứng dụng bất biến như `lineKey` là một lựa chọn rõ ràng trong ví dụ này.

### 5.2. Đừng dùng mọi field mutable để so sánh

Nếu equals/hashCode dựa trên `sku` và `quantity`, thay đổi quantity sau khi phần tử đã nằm trong HashSet có thể làm hash thay đổi. Tương tự, nếu nghiệp vụ cho phép hai dòng cùng SKU nhưng khác giá, tùy chọn hoặc khuyến mãi, so sánh chỉ bằng SKU có thể khiến Set loại nhầm một dòng hợp lệ.

Hãy tách biệt:

- **Identity của entity:** xác định cùng một dòng hàng.
- **Business uniqueness constraint:** ví dụ một SKU chỉ xuất hiện tối đa một lần trong đơn.
- **Thuộc tính có thể thay đổi:** quantity, note, giá được chốt, v.v.

Ba khái niệm này đôi khi trùng nhau, nhưng không mặc định giống nhau.

## 6. Repository lưu aggregate root

Repository được định nghĩa cho `PurchaseOrder`:

```java
import org.springframework.data.repository.ListCrudRepository;

public interface PurchaseOrderRepository
        extends ListCrudRepository<PurchaseOrder, Long> {
}
```

Application service điều phối transaction và lưu root:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder create(String orderNumber) {
        PurchaseOrder order = new PurchaseOrder(orderNumber);
        order.addLine("BOOK-001", 2);
        order.addLine("PEN-002", 3);
        return orders.save(order);
    }

    @Transactional
    public PurchaseOrder addLine(Long orderId, String sku, int quantity) {
        PurchaseOrder order = orders.findById(orderId)
            .orElseThrow(() ->
                new IllegalArgumentException("Không tìm thấy đơn hàng")
            );

        order.addLine(sku, quantity);
        return orders.save(order);
    }
}
```

Khi lưu root, Spring Data JDBC xử lý collection được ánh xạ theo aggregate. Không cần gọi một `OrderLineRepository` riêng cho các entity con thuộc quyền sở hữu của đơn hàng.

`@Transactional` giúp các thao tác persistence cần thiết cho một use case được commit/rollback nhất quán trong transaction. Nó không thay thế các kiểm tra nghiệp vụ của root.

### 6.1. Spring Data JDBC không có dirty checking như JPA

Spring Data JDBC không giữ persistence context theo cách Hibernate/JPA thường làm. Việc tải một root, sửa collection rồi kết thúc transaction không tự động có nghĩa rằng thay đổi đã được lưu.

Hãy gọi `repository.save(root)` một cách tường minh sau khi thực hiện thay đổi.

Khi cập nhật aggregate đã tồn tại, Spring Data JDBC có thể xóa các entity được tham chiếu rồi ghi lại trạng thái collection theo mô hình persistence của aggregate. Vì vậy, một thay đổi nhỏ trong Set không nhất thiết chỉ tạo một INSERT hoặc DELETE đơn lẻ. Cần tính đến số lượng phần tử con và tác động của trigger, audit, foreign key hoặc bảng khác đang tham chiếu chúng.

Đây cũng là một lý do nên giữ aggregate vừa phải và không gom một tập dữ liệu khổng lồ vào root chỉ vì có thể biểu diễn bằng Set.

## 7. Set khác List và Map như thế nào?

Các kiểu collection Java thể hiện những semantics khác nhau và ảnh hưởng tới cách ánh xạ.

| Đặc điểm | Set | List | Map |
| --- | --- | --- | --- |
| Có phần tử trùng theo quy tắc collection? | Không, dựa trên `equals/hashCode` | Có | Key không trùng; value có thể trùng |
| Có thứ tự/vị trí trong collection? | Không có semantics vị trí | Có index | Có key |
| Cần cột key/index cho mapping thông thường? | Không | Có thể dùng `keyColumn` để lưu index | Có thể dùng `keyColumn` để lưu map key |
| Phù hợp với | Tập thành viên không trùng | Danh sách có thứ tự | Tra cứu theo key |
| Cần sắp xếp khi hiển thị? | Có, nếu yêu cầu thứ tự | Có thể dựa trên index đã lưu | Có thể dựa trên key hoặc sort riêng |

### 7.1. Set: tập thành viên

```java
@MappedCollection(idColumn = "order_id")
private Set<OrderLine> lines = new LinkedHashSet<>();
```

Không có index được lưu cho từng phần tử. Nếu nghiệp vụ không quan tâm thứ tự, đây là mô hình tự nhiên.

### 7.2. List: danh sách có vị trí

```java
@MappedCollection(
    idColumn = "order_id",
    keyColumn = "line_position"
)
private List<OrderLine> lines = new ArrayList<>();
```

`line_position` có thể lưu vị trí phần tử. Khi nghiệp vụ cần thứ tự do người dùng sắp xếp, thứ tự ưu tiên hoặc thứ tự thực hiện, List thường diễn đạt đúng hơn Set.

### 7.3. Map: tập phần tử có key

```java
@MappedCollection(
    idColumn = "order_id",
    keyColumn = "line_code"
)
private Map<String, OrderLine> linesByCode = new LinkedHashMap<>();
```

`line_code` lưu key của Map. Mỗi key là duy nhất trong Map, nhưng nhiều key có thể trỏ tới value có nội dung giống nhau. Đây là semantics khác với Set.

Không nên dùng Set chỉ vì muốn “không cần viết index”. Hãy chọn kiểu collection theo ý nghĩa domain trước, rồi cấu hình mapping phù hợp.

## 8. Thứ tự phần tử và truy vấn

Set không đảm bảo thứ tự. Ngay cả khi dùng `LinkedHashSet`:

- Trong bộ nhớ, nó duy trì thứ tự chèn của instance hiện tại.
- Khi tải từ database, thứ tự các row trả về không được bảo đảm nếu SQL không chỉ định `ORDER BY`.
- Spring Data JDBC không tự suy ra một thứ tự nghiệp vụ cho Set.
- Khi API cần trả danh sách theo SKU, tên hoặc thời điểm tạo, hãy sắp xếp rõ ràng.

Ví dụ chuyển Set sang danh sách đã sắp xếp khi tạo response:

```java
List<OrderLineResponse> response = order.getLines().stream()
    .sorted(Comparator.comparing(OrderLine::getSku))
    .map(line -> new OrderLineResponse(
        line.getSku(),
        line.getQuantity()
    ))
    .toList();
```

Đây là bước trình bày/query ở application layer; nó không làm thay đổi semantics của aggregate collection.

Nếu thứ tự là dữ liệu nghiệp vụ phải được lưu và khôi phục, hãy dùng `List` cùng cột vị trí hoặc mô hình thứ tự riêng, thay vì dựa vào thứ tự ngẫu nhiên của Set.

## 9. Tính duy nhất ở Java và tính duy nhất ở database

`Set` chỉ bảo đảm tính duy nhất theo quy tắc Java `equals/hashCode` trong một instance collection. Nó không tự tạo unique constraint trong database.

Có hai lớp bảo vệ:

1. **Trong domain model:** ngăn phần tử trùng được thêm vào Set và kiểm tra các invariant liên quan.
2. **Trong database:** dùng primary key, unique constraint và foreign key để bảo vệ dữ liệu trước nhiều transaction hoặc writer khác nhau.

Ví dụ schema có:

```sql
CONSTRAINT uq_order_lines_key
    UNIQUE (order_id, line_key)
```

Constraint này ngăn hai hàng có cùng `line_key` trong một đơn hàng, kể cả khi dữ liệu được ghi bởi ứng dụng khác hoặc hai transaction chạy đồng thời.

Nếu quy tắc nghiệp vụ là mỗi SKU chỉ xuất hiện một lần trong đơn, constraint có thể là:

```sql
ALTER TABLE order_lines
ADD CONSTRAINT uq_order_lines_sku
UNIQUE (order_id, sku);
```

Chỉ thêm constraint này khi nó đúng với nghiệp vụ. Nếu một SKU có thể xuất hiện thành hai dòng vì khác cấu hình, giá hoặc chương trình khuyến mãi, unique constraint trên SKU sẽ quá chặt.

### 9.1. Set không thay thế validation và constraint

Giả sử hai request cùng thêm một SKU vào đơn hàng. Mỗi request có thể tải một bản root và thực hiện kiểm tra trong bộ nhớ; nếu không có optimistic locking hoặc database constraint phù hợp, cả hai vẫn có thể ghi dữ liệu theo cách vi phạm quy tắc.

Vì vậy:

- Kiểm tra trùng trong root giúp phản hồi lỗi nghiệp vụ rõ ràng.
- Unique constraint bảo vệ tính duy nhất ở tầng lưu trữ.
- Transaction và concurrency control giúp xử lý cập nhật đồng thời.
- Nếu dùng `@Version` trên root, Spring Data JDBC có thể phát hiện stale update theo cơ chế optimistic locking.

Không nên dựa duy nhất vào `Set.add` để bảo vệ một invariant quan trọng trước nhiều transaction.

## 10. Set entity con và aggregate độc lập

Một collection Set trên root nên chứa các đối tượng thuộc **cùng aggregate**. Nếu một object có vòng đời độc lập và được nhiều root tham chiếu, nó không nên trở thành entity con chỉ vì cần biểu diễn một nhóm.

Ví dụ, một đơn hàng có thể tham chiếu các sản phẩm:

```java
private Set<Long> productIds;
```

hoặc dùng kiểu tham chiếu aggregate phù hợp. Không nên nhúng toàn bộ `Product` vào Set child của `PurchaseOrder` nếu Product là aggregate root riêng, có thể được nhiều đơn hàng cùng sử dụng và được quản lý độc lập.

Nếu cần lưu quan hệ nhiều-nhiều, thường cần mô hình hóa entity liên kết với ownership và lifecycle rõ ràng. Trong Spring Data JDBC, aggregate references và child collections có semantics riêng; không nên giả định rằng mọi `Set<A>` tự động trở thành một quan hệ many-to-many có join table.

Ví dụ một sản phẩm có thể được nhiều đơn hàng tham chiếu, nhưng một `OrderLine` lại thuộc về một đơn hàng cụ thể. Dòng hàng có thể lưu `productId` hoặc SKU cùng snapshot thông tin tại thời điểm đặt, trong khi Product vẫn là aggregate riêng.

## 11. Kiểm thử ánh xạ Set

Một bài kiểm thử repository nên xác nhận ít nhất việc lưu root, đọc lại tập con và các quy tắc uniqueness trong domain.

Ví dụ khung:

```java
@DataJdbcTest
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void persistsAndReloadsChildSet() {
        PurchaseOrder order = new PurchaseOrder("PO-SET-001");
        order.addLine("BOOK-001", 2);
        order.addLine("PEN-002", 3);

        PurchaseOrder saved = orders.save(order);

        PurchaseOrder loaded = orders.findById(saved.getId())
            .orElseThrow();

        assertThat(loaded.getLines()).hasSize(2);
        assertThat(loaded.getLines())
            .extracting(OrderLine::getSku)
            .containsExactlyInAnyOrder("BOOK-001", "PEN-002");
    }
}
```

`containsExactlyInAnyOrder` phù hợp với Set vì không khẳng định thứ tự. Nếu test dùng `containsExactly`, nó có thể thất bại không ổn định dù tập phần tử đúng.

Một số kiểm thử bổ sung:

- Thêm cùng một identity hai lần vào Set và xác nhận domain xử lý theo quy tắc đã chọn.
- Thay đổi một field mutable rồi xác nhận `contains`/`remove` vẫn hoạt động; điều này giúp phát hiện hashCode phụ thuộc field mutable.
- Lưu root đã có dữ liệu rồi xóa một phần tử và lưu lại; xác nhận database phản ánh trạng thái collection.
- Kiểm tra constraint database khi ghi trùng key.
- Kiểm tra dữ liệu khi tải lại từ database không dựa vào thứ tự row.
- Kiểm tra optimistic locking nếu nhiều transaction có thể cập nhật cùng root.

Test slice `@DataJdbcTest` cần có datasource test, schema và dependency driver phù hợp. Với PostgreSQL-specific DDL, nên chạy integration test trên PostgreSQL (chẳng hạn Testcontainers) thay vì chỉ dựa vào H2.

## 12. Những lỗi thường gặp khi ánh xạ Set

| Hiện tượng | Nguyên nhân thường gặp | Hướng xử lý |
| --- | --- | --- |
| Phần tử biến mất sau khi thêm vào Set | Hai object bằng nhau theo `equals/hashCode` nên Set từ chối phần tử sau. | Xác định identity và business uniqueness chính xác. |
| `contains` hoặc `remove` không tìm thấy object | `hashCode` thay đổi sau khi object đã vào HashSet, thường do dùng ID được sinh hoặc field mutable. | Dựa trên identity bất biến. |
| Tải lại thấy thứ tự khác | Set không lưu semantics thứ tự; SQL không có `ORDER BY`. | Sort ở query/application hoặc dùng List nếu thứ tự là dữ liệu. |
| Cột foreign key không đúng | `idColumn` không khớp tên cột trong bảng con. | Đối chiếu `@MappedCollection` với DDL thật. |
| Cố thêm `keyColumn` cho Set để giữ thứ tự | Set không có vị trí/index. | Dùng List nếu cần thứ tự được lưu. |
| Database vẫn có bản ghi trùng theo nghiệp vụ | Java Set chỉ bảo vệ một collection trong bộ nhớ, không thay unique constraint. | Thêm constraint phù hợp và xử lý concurrency. |
| Lưu root tạo nhiều thao tác SQL | Spring Data JDBC đồng bộ aggregate; collection con có thể bị xóa/ghi lại khi update root. | Giữ aggregate phù hợp kích thước và xem xét mô hình dữ liệu. |
| Set chứa object của aggregate khác | Nhầm lẫn ownership với reference. | Tham chiếu aggregate độc lập bằng ID hoặc mô hình liên kết riêng. |

## 13. Khi nào nên dùng Set?

Chọn Set khi tất cả điều kiện sau phù hợp với ngữ nghĩa nghiệp vụ:

- Tập hợp không có thứ tự quan trọng.
- Không cần lưu index hoặc vị trí phần tử.
- Mỗi phần tử có identity/equality được xác định rõ.
- Các phần tử thực sự thuộc ownership của aggregate root.
- Việc đồng bộ cả collection khi lưu root phù hợp với kích thước và tần suất cập nhật.

Chọn List khi thứ tự là dữ liệu cần lưu hoặc phần tử trùng là hợp lệ. Chọn Map khi cần truy cập theo một key riêng. Nếu phần tử là aggregate độc lập, hãy tham chiếu bằng ID thay vì biến nó thành child collection.

### Bảng quyết định

| Nhu cầu nghiệp vụ | Mô hình gợi ý |
| --- | --- |
| Các thành viên duy nhất, không có thứ tự | `Set<Child>` |
| Danh sách có thứ tự được lưu | `List<Child>` + key/index column |
| Tra cứu phần tử bằng key do domain quy định | `Map<Key, Child>` |
| Nhiều aggregate độc lập cùng tham chiếu một đối tượng | ID/reference hoặc entity liên kết |
| Tập dữ liệu con rất lớn, cập nhật độc lập thường xuyên | Xem xét tách aggregate và thiết kế query/persistence riêng |

## 14. Quy trình triển khai trong Spring Data JDBC

1. Xác định collection có thực sự là một phần của aggregate root hay chỉ là tham chiếu tới aggregate độc lập.
2. Chọn Set chỉ khi domain không cần thứ tự và cần semantics thành viên duy nhất.
3. Khai báo `@MappedCollection(idColumn = "...")` trỏ đúng tới foreign key trong bảng con.
4. Thiết kế identity và `equals/hashCode` ổn định; tránh field mutable hoặc ID được sinh sau khi object đã nằm trong HashSet.
5. Định nghĩa primary key, foreign key, unique constraint và check constraint trong schema theo đúng invariant.
6. Thay đổi collection thông qua hành vi root, sau đó gọi `repository.save(root)` trong transaction phù hợp.
7. Kiểm thử persistence round-trip, uniqueness, remove/update và không giả định thứ tự.
8. Nếu cần thứ tự, key riêng hoặc ownership khác, chọn List/Map/reference thay vì ép mọi cấu trúc vào Set.

> **`@MappedCollection(idColumn = "...")` ánh xạ Set entity con bằng khóa ngoại trỏ về aggregate root. Set biểu diễn tập thành viên không trùng theo `equals/hashCode` và không lưu thứ tự; tính duy nhất quan trọng vẫn cần được bảo vệ bằng constraint ở database.**
