# Version values on insert, update, and delete

In **Spring Data Relational JDBC**, optimistic locking uses a numeric property annotated with **@Version** on the **aggregate root**. The version value represents the version of the aggregate in the database. When updating or deleting an aggregate, Spring Data JDBC uses the ID together with the version to confirm that the data has not been modified by another transaction since the previous read.

The version lifecycle has three milestones:

- **Insert:** a new aggregate has an unset version. Spring Data JDBC initializes the version upon a successful write. With a **Long** wrapper property starting at **null**, the initial stored value is **0**.
- **Update:** the update statement succeeds only if the version in the database still equals the object's version. After a successful update, the version increments by one in both the database and the returned object.
- **Delete:** the delete statement also checks the version. If the version has changed, the delete operation fails with **OptimisticLockingFailureException**. On a successful delete, the version does not increment because the row has been removed.

Understanding the exact version value at each stage helps avoid using stale objects, overwriting newer changes, deleting data by mistake, and mishandling concurrency errors.

## 1. What does the version represent?

Suppose an application manages purchase orders:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── status
  └── lines
        ├── OrderLine
        └── OrderLine
```

**version** is the version sequence number of the entire aggregate. When a save operation on the aggregate succeeds, the new version indicates a state written after the previous version.

The version is not the aggregate's ID, a global sequence number, an update timestamp, or the number of times a user opened a screen. A version is meaningful only within the scope of a single aggregate root. Two different orders can both have version 3.

## 2. Declaring @Version on the aggregate root

Spring Data JDBC supports optimistic locking with a numeric property annotated with **@Version**. Example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status
) {
    public PurchaseOrder withStatus(String newStatus) {
        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                newStatus
        );
    }
}
```

In this example, **@Id** identifies the aggregate root, **@Version** marks the property used for optimistic locking, and **Long** allows representing an unversioned state as null. The withStatus method creates a new instance while preserving the version that was read; Spring Data uses that version to verify the update.

The version should live on the aggregate root. Child entities belonging to the aggregate are protected via the root's version when the application saves the aggregate. If an object has an independent lifecycle and is managed as its own aggregate root, it can have its own version.

### 2.1. Data types and schema

Use numeric types such as Long or Integer with a compatible column type. Do not use String, UUID, or timestamp as the @Version property for Spring Data JDBC optimistic locking.

Illustrative PostgreSQL DDL:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL
);
```

The version column must exist and have a type compatible with the Java property. Spring Data JDBC manages the version value on insert/update; the application should not manually increment the version inside domain methods.

If the database has a trigger that increments the version or another service updates this column directly, it must be designed in alignment with Spring Data's mechanism. Two mechanisms both modifying the version can cause subsequent saves to suffer optimistic locking failures.

## 3. Version value on insert (INSERT)

A new aggregate with a Long wrapper property typically starts like this:

```java
PurchaseOrder draft = new PurchaseOrder(
        null,
        null,
        "PO-261",
        "DRAFT"
);
```

At this point, id is null and version is null. Calling the repository:

```java
PurchaseOrder saved = repository.save(draft);
```

Because version is unset, Spring Data JDBC identifies the aggregate as new and performs an insert. The version is initialized during the write. With a Long wrapper, the initial value is typically 0.

After saving:

| Property | Before insert | After insert |
| --- | --- | --- |
| id | null | Database-generated ID |
| version | null | 0 |
| orderNumber | PO-261 | PO-261 |
| status | DRAFT | DRAFT |

Use the instance returned from save:

```java
PurchaseOrder saved = repository.save(draft);

Long id = saved.id();
Long version = saved.version(); // 0 after insert
```

Especially with immutable entities like records, do not assume the input object will be mutated in place to receive the ID or version. The returned value represents the state to use for subsequent operations.

### 3.1. Illustrative SQL on insert

With the schema above, the statement has the equivalent meaning:

```sql
INSERT INTO purchase_order (
    order_number,
    status,
    version
)
VALUES (
    'PO-261',
    'DRAFT',
    0
);
```

This is illustrative SQL, not a guarantee of the verbatim statement across all dialects. Spring Data JDBC and the dialect determine how IDs are generated, how the version is bound, and how database-generated IDs are retrieved.

### 3.2. Version also participates in new-entity detection

When an aggregate has a @Version property, Spring Data uses this property in its strategy for determining whether an entity is new. A null wrapper version indicates a new instance; a populated version indicates an existing instance. For primitive integer types, 0 is used as the initial value indicating newness.

This is useful when the application assigns IDs before insert. For instance, an aggregate with a UUID ID whose version is still null can be recognized as new thanks to the version property.

Do not manually set the version to an arbitrary number on a new object. If the version already has a value, Spring Data may treat the aggregate as existing and take the update path. When the row does not exist yet, an update cannot substitute for an insert.

## 4. Version value on update (UPDATE)

After inserting, suppose the aggregate has:

```text
id      = 261
version = 0
status  = DRAFT
```

The application loads the aggregate:

```java
PurchaseOrder current = repository.findById(261L)
        .orElseThrow();
```

Modify the status and save:

```java
PurchaseOrder changed = current.withStatus("CONFIRMED");
PurchaseOrder updated = repository.save(changed);
```

Spring Data JDBC generates a conditional update matching the ID and current version. Conceptually:

```sql
UPDATE purchase_order
SET status = 'CONFIRMED',
    version = 1
WHERE id = 261
  AND version = 0;
```

If the row in the database still has version 0, the update succeeds. Spring Data increments the version to 1 both in the database and in the returned instance.

| Property | Before update | After successful update |
| --- | --- | --- |
| id | 261 | 261 |
| version | 0 | 1 |
| status | DRAFT | CONFIRMED |

The SQL above only describes the compare-and-set principle. The actual statement may differ in bind parameters, column lists, and syntax depending on the dialect.

### 4.1. Each successful update increments the version

Suppose a subsequent save starts from version 1:

```java
PurchaseOrder current = repository.findById(261L)
        .orElseThrow();

PurchaseOrder changed = current.withStatus("SHIPPED");
PurchaseOrder updated = repository.save(changed);
```

The database checks version 1, then saves version 2. The version continues to increment with each successful aggregate update.

In Spring Data JDBC, there is no JPA-style dirty checking to skip updates when no fields actually changed. When the application calls save for an existing aggregate, the save still goes through the update mechanism and the version increments upon a successful update. Therefore, do not call save unnecessarily just to retrieve data.

### 4.2. Modifying child entities also changes the root version

If PurchaseOrder owns a collection of lines, adding/modifying/removing a line and saving the aggregate root is also part of updating the aggregate:

1. Load the current PurchaseOrder through the repository.
2. Call a domain method on the aggregate to add, modify, or remove an OrderLine.
3. Call repository.save with the modified aggregate.

The domain method might be named addLine, changeQuantity, or removeLine depending on your domain model. The key point is that the save goes through the root; Spring Data checks the root's version and increments it after the aggregate update succeeds.

The root's version is checked and incremented. As a result, two transactions modifying different parts of the same aggregate can still detect conflicts at the aggregate boundary.

If a child genuinely needs to be updated independently with its own concurrency, reconsider the aggregate boundary rather than trying to use the root version as an independent version for each child.

## 5. What happens when two transactions update the same version?

Suppose the database currently holds:

```text
PurchaseOrder #261
version = 4
status  = DRAFT
```

Two transactions A and B both read the order. Both hold objects with version 4.

```text
Database: version 4
       /             \
      ▼               ▼
Transaction A     Transaction B
reads version 4   reads version 4
      │               │
      ▼               │
save succeeds         │
version becomes 5     │
      │               ▼
      │          save with version 4
      │               │
      └──────► WHERE version = 4
                      │
                      ▼
              0 rows updated
                      │
                      ▼
          OptimisticLockingFailureException
```

A updates first, so the database version becomes 5. B still sends an object with version 4; the condition WHERE id = 261 AND version = 4 no longer matches. Spring Data JDBC throws OptimisticLockingFailureException.

This error means the object being saved is no longer based on the current version. It does not necessarily mean the database is corrupted or the SQL is broken.

### 5.1. Handling OptimisticLockingFailureException

The service can catch the error to translate it into a business/API response:

```java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long id, String status) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = current.withStatus(status);

        try {
            return repository.save(changed);
        } catch (OptimisticLockingFailureException ex) {
            throw new OrderConflictException(
                    "The order changed while this request was being processed",
                    ex
            );
        }
    }
}
```

OrderConflictException is an application-defined business exception. Depending on the API, the application can return HTTP 409 Conflict so the client knows to load the latest state.

Do not catch the error and immediately call save again on the same stale object. That object still holds the stale version and may contain business decisions made on outdated state. The safe approach is to load the latest aggregate, compare changes, and decide whether the command can be reapplied or requires user confirmation.

### 5.2. Not every conflict can be blindly retried

Retrying can make sense for an idempotent command with clear merge rules. However, if two users change the price, approval status, or item quantity simultaneously, automatically reapplying the command may violate one party's intent.

Before retrying, verify whether the command can run multiple times without creating duplicate side effects, whether the change can be applied to the new state without violating invariants, whether the user needs to see the other party's changes before deciding, and whether the failed transaction has fully rolled back.

## 6. Version value on delete (DELETE)

Optimistic locking also applies to deleting an aggregate. When deleting an aggregate with @Version, Spring Data JDBC checks the version before deleting.

Suppose the object currently has:

```text
id      = 261
version = 5
```

Equivalent SQL meaning:

```sql
DELETE FROM purchase_order
WHERE id = 261
  AND version = 5;
```

If the database still has version 5, the delete succeeds. If another transaction has already updated the aggregate to version 6, the condition fails to match and Spring Data JDBC throws OptimisticLockingFailureException.

**The version does not increment on delete.** Once deleted successfully, the row is removed from the database; there is no next version stored for that row.

### 6.1. Comparing versions before and after delete

| State | Version |
| --- | ---: |
| Newly inserted aggregate | 0 |
| After 1st successful update | 1 |
| After 2nd successful update | 2 |
| Aggregate read before delete | 2 |
| Successful delete | Row no longer exists; version does not increment |

Do not interpret delete as a final update producing version 3. Spring Data uses the version to verify permission to delete against the version that was read, then deletes the row.

### 6.2. Deleting a stale object

Suppose transaction A reads version 2. Transaction B updates first and saves version 3. Then A calls:

```java
repository.delete(oldOrder);
```

Because oldOrder still carries version 2, the delete operation is not allowed to remove version 3, which A never saw. Spring Data JDBC reports an optimistic locking failure.

This is an important behavior: a delete request based on stale state does not silently erase someone else's newer changes.

### 6.3. delete(entity) vs deleteById(id)

The two calls take different input information:

```java
repository.delete(order);
repository.deleteById(orderId);
```

- delete(entity) accepts an object containing both the ID and version. The version on the object is used to verify the state the caller read.
- deleteById(id) accepts only an ID. The repository may load the current entity and then delete using the loaded entity's version. Because the caller does not pass the observed version, this method cannot directly express "delete only if it is still the version the client saw."

If an API needs to protect a delete operation based on the version the client read, pass that version in the command/ETag and compare it against the current aggregate before deleting; or load the entity under application-controlled checks. Do not skip version checking simply because a request only provides an ID.

Bulk delete methods such as deleteAll() and custom SQL may have different semantics from deleting individual aggregates. Do not assume all bulk deletes perform per-row version checks; inspect the contract of the specific method and the Spring Data version in use.

## 7. Summary table of the version lifecycle

| Operation | Input version | Database condition | Version outcome | On version mismatch |
| --- | --- | --- | --- | --- |
| Insert new aggregate | null with Long wrapper | Row not yet created | Initialized to 0 | Insert/constraint error on data conflict |
| First update | 0 | id matches and version is 0 | Increments to 1 | OptimisticLockingFailureException |
| Subsequent update | 1 | id matches and version is 1 | Increments to 2 | OptimisticLockingFailureException |
| Delete | Current version, e.g. 2 | id matches and version is 2 | Does not increment; row deleted | OptimisticLockingFailureException |

Illustrative SQL sequence:

```sql
-- Create new.
INSERT INTO purchase_order (order_number, status, version)
VALUES ('PO-261', 'DRAFT', 0);

-- Update version 0 to 1.
UPDATE purchase_order
SET status = 'CONFIRMED', version = 1
WHERE id = 261 AND version = 0;

-- Update version 1 to 2.
UPDATE purchase_order
SET status = 'SHIPPED', version = 2
WHERE id = 261 AND version = 1;

-- Delete while version is still 2.
DELETE FROM purchase_order
WHERE id = 261 AND version = 2;
```

This SQL sequence illustrates the semantics. Spring Data JDBC generates the actual SQL via mapping metadata and the dialect, while managing the version value on the object.

## 8. Version and new-entity state detection

Version does more than support concurrency; it also participates in the new-entity detection strategy.

| Entity configuration | Initial value | Typical meaning |
| --- | --- | --- |
| @Version Long version | null | New entity |
| @Version Long version | 0 after insert | Inserted entity |
| @Version Long version | 1, 2, ... | Existing entity |
| @Version long version | 0 | Initial primitive value, treated as new |

If an entity has @Version, Spring Data uses the version to determine newness; without a version, the default strategy usually relies on the ID. Persistable.isNew() is another customization mechanism and must be configured consistently if used by the entity.

A common mistake is manually constructing an entity with an ID and setting the version to a positive number even though the row does not exist yet. Spring Data may treat it as an existing entity and attempt an update. If the row is missing, the update will not insert a new row.

Conversely, do not reset an existing entity's version back to null to force an insert. Doing so can cause Spring Data to choose insert and the database to report a duplicate key error.

## 9. Aggregate root version and child entities

Spring Data JDBC places the version on the aggregate root. When saving an aggregate:

- Root updates are protected by the ID/version condition.
- Changes to child entities belonging to the aggregate go along with saving the root.
- The root version increments after a successful aggregate update.
- Deleting the aggregate checks the root version before deleting.

Example root with a collection:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String status,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines
) {}
```

There is no need to add an independent @Version to each OrderLine just to protect changes inside this aggregate. If a line genuinely needs to be edited and saved independently, that is a sign to re-evaluate the ownership model and aggregate boundary.

Because Spring Data JDBC does not maintain a persistence context like JPA, saving an existing aggregate can resynchronize child entities to match the object's state. Optimistic locking on the root detects when another transaction updated the aggregate before the current transaction wrote its state.

## 10. Transactions and atomicity of update/delete

A single aggregate update may execute multiple SQL statements: checking/updating the root, deleting old child rows, and re-inserting children according to the current state. With @Version, the root update is the concurrency checkpoint.

If the root update fails due to a version mismatch, the aggregate save must not leave behind partial child changes. Ensure the use case's SQL statements execute inside an appropriate transaction:

```java
@Transactional
public PurchaseOrder replaceLines(
        Long orderId,
        List<OrderLine> newLines) {

    PurchaseOrder current = repository.findById(orderId)
            .orElseThrow();

    PurchaseOrder changed = current.withLines(newLines);
    return repository.save(changed);
}
```

Transactions are also important when deleting an aggregate with children: related delete statements must complete as one unit of work. The transaction manager must be configured to use the same DataSource as Spring Data JDBC.

@Version does not replace transactions. It detects conflicts between writes; transactions ensure that the SQL statements within an operation commit or roll back together.

## 11. When custom SQL or another service updates data

Optimistic locking is only effective if every write path respects the version. A custom SQL statement such as:

```sql
UPDATE purchase_order
SET status = 'CANCELLED'
WHERE id = 261;
```

neither checks the version nor increments it. If this statement runs while another application holds an object at version 2, the application's subsequent save may still match version 2 and miss the out-of-band change.

If custom SQL must update a versioned aggregate, include both the version condition and the version increment in the statement:

```sql
UPDATE purchase_order
SET status = 'CANCELLED',
    version = version + 1
WHERE id = 261
  AND version = 2;
```

The application must inspect the affected row count:

- 1 row: update succeeded and the version incremented.
- 0 rows: aggregate does not exist or version mismatched; distinguish the two cases if business rules require it.

If custom SQL modifies children without updating the root version, other transactions may fail to detect that the aggregate changed. Synchronize the root version in the same transaction or move the operation to the repository/template managed by Spring Data.

## 12. Distinguishing optimistic locking from pessimistic locking

@Version is an **optimistic locking** mechanism:

- Does not lock rows while the user edits on screen.
- Allows multiple transactions to read the same version concurrently.
- Checks the version at write time.
- Rejects operations based on stale snapshots.

Pessimistic locking uses database locks to restrict other transactions from updating during the lock window. It fits workflows that require serialization starting from the read, but requires managing lock duration and deadlock risks.

Do not use @Version as a placeholder locking mechanism. It does not stop other transactions from reading or starting to modify objects; it only detects conflicts on write/delete.

## 13. Version in REST APIs and user interfaces

If a client reads an order and later sends an update command, you can include the read version in the response:

```json
{
  "id": 261,
  "version": 4,
  "orderNumber": "PO-261",
  "status": "DRAFT"
}
```

The client sends the command along with the version:

```json
{
  "status": "CONFIRMED",
  "expectedVersion": 4
}
```

The service loads the current aggregate, compares the client-supplied version against the current version, and executes the domain command. Spring Data JDBC still checks the version at save time; checking in the service provides clearer feedback, but does not replace the SQL version condition because another transaction could still write between the check and the save.

An HTTP alternative is to use ETag for the version and require clients to send If-Match. If the ETag no longer matches, the API can return 412 Precondition Failed per HTTP contract. If the application represents business conflicts with 409 Conflict, use it consistently across your API.

Do not take a version from the client and assign it directly to the entity to increment it. The client only provides the expected version; Spring Data JDBC and the database perform the check/increment.

## 14. Common mistakes

| Symptom | Possible cause | Fix |
| --- | --- | --- |
| New insert fails due to null version or schema disallowing it | Version column is misconfigured or custom mapping is wrong | Declare @Version with a numeric type and a compatible version column |
| New aggregate is updated instead of inserted | Version was already assigned an existing value or Persistable.isNew() reports incorrectly | Leave wrapper version null for new instances and check state detection |
| First save succeeds but old object still has version null | Caller continues using the input instance instead of the returned value | Use the instance returned by save |
| Update fails with OptimisticLockingFailureException | Another transaction incremented the version or the row no longer exists | Reload the aggregate and handle the conflict |
| Version does not increment after custom update | Custom SQL did not update the version column | Compare version and increment it in the same SQL/transaction |
| Deleting a stale object fails | Database already has a newer version than the object | Load the current state and prompt for a new delete decision |
| Delete succeeds but version does not increment | This is the expected behavior for delete | Do not expect a next version for a deleted row |
| Two services overwrite each other undetected | One write path bypasses the version check | Ensure every write path updates the root version |
| deleteAll() does not show per-object version checking | Bulk operations have different contracts | Use entity-level operations when per-version checks are required; verify the specific API |
| Automatic retry corrupts data | Retry uses stale object/command without reconciling new state | Reload and apply business rules before retrying |

## 15. Practice exercises

**Exercise 1 — Insert version.** Add @Version Long version to PurchaseOrder. Create a new aggregate with version null, call save, and observe the version in the returned object as well as in the database.

**Exercise 2 — Update version.** Read the aggregate at version 0, change status, and save. Verify the version increments to 1. Save another change and verify the version increments to 2.

**Exercise 3 — Concurrent updates.** Across two transactions, read the same aggregate at version 2. Save the first transaction, then save the stale object in the second transaction. Verify OptimisticLockingFailureException.

**Exercise 4 — Delete with matching version.** Read the aggregate at its current version and call repository.delete(entity). Verify the row is deleted and no new version is created.

**Exercise 5 — Delete stale object.** Read the aggregate at version 3, update it in another transaction to version 4, and then call delete with the version 3 object. Verify the delete is rejected.

**Exercise 6 — Child entities.** Add a lines collection. Update one line through the aggregate root, save, and verify the root version increments. Try having two transactions edit two different lines on the same root to observe conflict at the aggregate boundary.

**Exercise 7 — Custom SQL.** Write an update statement with WHERE id = ? AND version = ?, increment the version, and check the affected row count. Retry with a stale version and verify zero rows are updated.

**Exercise 8 — REST expected version.** Return the version in the response and require the client to send expectedVersion on update. Test the stale-version case and translate the optimistic locking error into an appropriate API response.
