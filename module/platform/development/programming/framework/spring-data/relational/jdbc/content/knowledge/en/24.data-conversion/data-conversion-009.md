# Testing Round-Trip Mapping, Nulls, and Legacy Data Compatibility

When using Spring Data JDBC, a domain object typically passes through two conversion directions:

- **Writing:** the Java object is mapped into JDBC values and stored in relational columns.
- **Reading:** SQL values are converted and materialized back into the domain object.

A mapping is only trustworthy when data read back preserves its business meaning. However, symmetric round-trip behavior does not necessarily mean every Java value must be byte-for-byte identical after a save/load cycle. The database may normalize decimal scale, timestamp precision, default values, or enum representations. What must be guaranteed is that **data semantics are preserved according to defined rules**.

This lesson covers how to test round-trip mapping, handle SQL NULLs, test bidirectional converters, and ensure new code can still read legacy data. Examples focus on Spring Data Relational/JDBC.

## 1. What Is Symmetric Round-Trip Mapping?

Suppose a domain object holds a monetary amount:

```java
Customer customer = new Customer(
    null,
    "Nguyen An",
    new BigDecimal("125.50"),
    true
);
```

When saving, Spring Data JDBC converts Java values into SQL data. When reading back, the framework converts SQL data back into Java types.

This can be expressed as two transformations:

```text
Java object
    |
    | write mapping
    v
Database row
    |
    | read mapping
    v
Restored Java object
```

A desired round-trip satisfies:

```text
read(write(value)) ≈ normalize(value)
```

The `≈` symbol means equivalent under domain rules, while `normalize` represents intentional adjustments introduced by the database or storage format.

Examples:

- The database stores DECIMAL with a fixed scale, so `125.5` may be read back as `125.50`.
- Timestamps have microsecond precision, so nanoseconds may be rounded or truncated.
- Java enum `ACTIVE` is stored as legacy code `A` or canonical string `ACTIVE`.
- ID, version, and creation time may be generated by the database/framework upon insert.

Therefore, tests should not always call `equals` across the entire input and reloaded objects. Identify which properties must remain exact, which are normalized, and which are database-generated.

## 2. Distinguishing Converter Tests from Repository Tests

There are two complementary testing layers.

| Test Layer | Goal | Catches |
| --- | --- | --- |
| Converter unit test | Verify Java ↔ SQL value conversion. | Wrong parse/format rules, enum mapping, timezone, or legacy formats. |
| Repository integration test | Verify the full path through Spring Data JDBC and the database. | Wrong column mapping, JDBC type, NULL handling, DDL, defaults, triggers, precision, and converter registration. |

Converter unit tests are fast and isolated, but they do not prove the converters are registered with Spring Data JDBC. Repository integration tests pass through the JDBC driver and actual schema, catching bugs at the database boundary.

Never test only the converter and assume persistence round-trip works.

## 3. Building the Domain Model and Schema for the Example

Suppose a customer table stores display name, credit limit, loyalty points, and status:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(160) NOT NULL,
    middle_name VARCHAR(120),
    credit_limit DECIMAL(12, 2),
    loyalty_points INTEGER,
    status VARCHAR(24) NOT NULL,
    active BOOLEAN NOT NULL
);
```

Columns `middle_name`, `credit_limit`, and `loyalty_points` allow NULL. The domain model uses wrapper/reference types to represent those states:

```java
import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
    @Id Long id,
    @Column("display_name") String displayName,
    @Column("middle_name") String middleName,
    @Column("credit_limit") BigDecimal creditLimit,
    @Column("loyalty_points") Integer loyaltyPoints,
    CustomerStatus status,
    boolean active
) {}
```

`boolean active` is a primitive because the schema declares `NOT NULL`. If a column can hold SQL NULL, use `Boolean` to represent three states: true, false, and null.

Repository:

```java
import org.springframework.data.repository.ListCrudRepository;

public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {
}
```

`@Column` maps Java properties to physical column names. In tests, use a schema matching the mapping rather than only asserting on in-memory objects.

## 4. Writing a Repository Round-Trip Test

A basic round-trip test saves an entity and reloads it by ID:

```java
@DataJdbcTest
class CustomerRepositoryRoundTripTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void preservesValuesAfterSaveAndReload() {
        Customer input = new Customer(
            null,
            "Nguyen An",
            "Van",
            new BigDecimal("125.50"),
            120,
            CustomerStatus.ACTIVE,
            true
        );

        Customer saved = customers.save(input);

        Customer loaded = customers.findById(saved.id())
            .orElseThrow();

        assertThat(loaded.displayName()).isEqualTo("Nguyen An");
        assertThat(loaded.middleName()).isEqualTo("Van");
        assertThat(loaded.creditLimit())
            .isEqualByComparingTo(new BigDecimal("125.50"));
        assertThat(loaded.loyaltyPoints()).isEqualTo(120);
        assertThat(loaded.status()).isEqualTo(CustomerStatus.ACTIVE);
        assertThat(loaded.active()).isTrue();
    }
}
```

Points to note:

1. Use the ID from the object returned by `save`. With database-generated IDs, do not assume the input object is always mutated in place.
2. Call `findById` to verify data truly went through the database and read mapping.
3. Assert each property according to its semantics.
4. For `BigDecimal`, `isEqualByComparingTo` compares numeric value without requiring identical scale as `equals` does.
5. Run the test with a matching schema and JDBC driver.

If the entity uses `@Version`, the version may change on save. If there are generated IDs, timestamps, or audit properties, assert them using their own rules instead of comparing the entire object against the initial input.

## 5. Testing SQL NULL

NULL is part of the data, not a special Java value to skip in tests. If a column is nullable, verify both directions:

- Java null is written as SQL NULL.
- SQL NULL is read back as Java null.

Example:

```java
@Test
void preservesNullableProperties() {
    Customer input = new Customer(
        null,
        "Tran Binh",
        null,
        null,
        null,
        CustomerStatus.ACTIVE,
        true
    );

    Customer saved = customers.save(input);

    Customer loaded = customers.findById(saved.id())
        .orElseThrow();

    assertThat(loaded.middleName()).isNull();
    assertThat(loaded.creditLimit()).isNull();
    assertThat(loaded.loyaltyPoints()).isNull();
}
```

This test verifies NULL mapping for three nullable properties. It also catches cases where code accidentally replaces NULL with a default value in Java.

### 5.1. Use Wrappers for Nullable Columns

Do not map nullable columns to primitives:

```java
private int loyaltyPoints;
private boolean marketingOptIn;
```

Java primitives always have a default value (`0` or `false`) and cannot represent SQL NULL. If the database can contain NULL, use:

```java
private Integer loyaltyPoints;
private Boolean marketingOptIn;
```

If the business wants NULL to mean 0 or false, convert explicitly in the domain/service or migration. Do not let primitives silently erase the distinction between "unknown/not provided" and "value equals 0/false".

### 5.2. NULL Differs from a Database Default Value

Example:

```sql
CREATE TABLE customers (
    loyalty_points INTEGER DEFAULT 0
);
```

The database applies DEFAULT when an INSERT omits the column or explicitly requests DEFAULT. If an INSERT passes `NULL` for the column, the default does not automatically replace NULL with 0; the outcome depends on constraints and the statement.

Thus, these three states are distinct:

| Situation | Meaning |
| --- | --- |
| Column omitted from INSERT and has DEFAULT | The database may apply the default value automatically. |
| Column INSERTed with NULL | The database receives NULL, if the schema allows it. |
| Java property has value 0 | Value 0 is supplied by the application and can be written to the database. |

If the database owns the default value and the application needs to read it, design the mapping accordingly—for example using `@ReadOnlyProperty`—and reload the aggregate when the database-generated value is needed.

### 5.3. NULL, Empty Strings, and Whitespace

The following values are not equivalent:

- `null`: no value.
- `""`: empty string.
- `"   "`: string containing spaces.

Tests should cover these cases if the domain has normalization rules for names or text. If empty strings should be treated as NULL, normalize intentionally and test both writing and reading.

## 6. Testing Precision and Data Types

Not every Java type round-trips byte-for-byte through a database. The JDBC driver and column type may normalize values.

### 6.1. BigDecimal and Scale

`BigDecimal` distinguishes value and scale:

```java
new BigDecimal("10.5").equals(new BigDecimal("10.50")); // false
new BigDecimal("10.5").compareTo(new BigDecimal("10.50")); // 0
```

If the column is `DECIMAL(12, 2)`, tests should check the value against the scale/precision committed by the schema:

```java
assertThat(loaded.creditLimit())
    .isEqualByComparingTo("10.50");
```

If scale is part of domain rules, normalize before saving or use suitable custom conversions. Do not rely on a specific database to infer scale rules without testing.

### 6.2. Timestamps and Precision

Some databases store timestamps to microsecond precision, while other configurations or column types have different precision. Java `Instant` has nanosecond precision; after a round-trip it may not retain all 9 fractional digits.

For example, a test can align with the schema's precision:

```java
Instant input = Instant.parse("2026-11-13T09:15:30.123456Z");

Customer saved = customers.save(customerWithTimestamp(input));
Customer loaded = customers.findById(saved.id()).orElseThrow();

assertThat(loaded.createdAt())
    .isEqualTo(input);
```

This example only passes if the column type/driver preserves that precision. If the database only retains microseconds, compare against values truncated/rounded to the precision your system guarantees.

Do not use the machine's default system clock or timezone to construct expected values. Use fixed timestamps and explicit timezones so tests are deterministic across local and CI environments.

### 6.3. UUID, Boolean, and Enums

Types such as UUID, Boolean, and enums also need testing on a real database:

- UUID may be stored as a native UUID type or character string depending on the database.
- Boolean may be represented as BOOLEAN, BIT, or an equivalent type.
- Enums may be stored as enum names, legacy codes, or canonical strings.
- Custom converters can change representations on read/write.

A test on H2 is not enough to guarantee the same mapping behaves identically on PostgreSQL, MySQL, or SQL Server.

## 7. Testing Bidirectional Custom Converters

When a domain type has a different representation from SQL, Spring Data JDBC can use custom converters. For example, a legacy database stored customer status using codes:

| Legacy Value | Domain Meaning |
| --- | --- |
| `A` | ACTIVE |
| `I` | INACTIVE |

New code wants to write canonical `ACTIVE` and `INACTIVE`, while still reading legacy data.

Enum:

```java
public enum CustomerStatus {
    ACTIVE,
    INACTIVE,
    UNKNOWN
}
```

Reading converter:

```java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToCustomerStatus
        implements Converter<String, CustomerStatus> {

    @Override
    public CustomerStatus convert(String source) {
        return switch (source) {
            case "A", "ACTIVE" -> CustomerStatus.ACTIVE;
            case "I", "INACTIVE" -> CustomerStatus.INACTIVE;
            case "UNKNOWN" -> CustomerStatus.UNKNOWN;
            default -> throw new IllegalArgumentException(
                "Unsupported customer status: " + source
            );
        };
    }
}
```

Writing converter:

```java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class CustomerStatusToString
        implements Converter<CustomerStatus, String> {

    @Override
    public String convert(CustomerStatus source) {
        return switch (source) {
            case ACTIVE -> "ACTIVE";
            case INACTIVE -> "INACTIVE";
            case UNKNOWN -> "UNKNOWN";
        };
    }
}
```

Reads both legacy codes and canonical values; writes a single canonical format. This **tolerant reader, canonical writer** strategy is often useful during data transitions.

Do not automatically turn every unrecognized value into `UNKNOWN` if doing so could mask corrupt data. Only use a fallback when the domain clearly defines the semantics of an unknown state; otherwise throw an informative exception so anomalous data is caught.

### 7.1. Registering Converters in Spring Data JDBC

Converters must be registered with relational/JDBC configuration. Example using `AbstractJdbcConfiguration`:

```java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class JdbcConversionConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
            new StringToCustomerStatus(),
            new CustomerStatusToString()
        );
    }
}
```

The exact configuration approach must fit your project's Spring Data JDBC version and Spring Boot setup. If the project already declares `JdbcCustomConversions` or a custom `AbstractJdbcConfiguration`, add converters to the existing configuration rather than registering multiple competing conversion sets.

### 7.2. Converter Unit Test

```java
class CustomerStatusConverterTest {

    private final StringToCustomerStatus reader =
        new StringToCustomerStatus();

    private final CustomerStatusToString writer =
        new CustomerStatusToString();

    @Test
    void readsLegacyAndCanonicalValues() {
        assertThat(reader.convert("A"))
            .isEqualTo(CustomerStatus.ACTIVE);
        assertThat(reader.convert("ACTIVE"))
            .isEqualTo(CustomerStatus.ACTIVE);
        assertThat(reader.convert("I"))
            .isEqualTo(CustomerStatus.INACTIVE);
    }

    @Test
    void writesCanonicalValues() {
        assertThat(writer.convert(CustomerStatus.ACTIVE))
            .isEqualTo("ACTIVE");
        assertThat(writer.convert(CustomerStatus.INACTIVE))
            .isEqualTo("INACTIVE");
    }
}
```

This test verifies converter logic. It does not prove Spring Data JDBC has picked up the converters; that requires a repository integration test.

## 8. Testing Legacy Data Using Database Fixtures

A round-trip test that only inserts data through new code often misses backward compatibility bugs. To test legacy data, insert fixtures in the legacy format directly into the database, then read them with the new code.

Example repository test:

```java
@DataJdbcTest
class CustomerLegacyDataTest {

    @Autowired
    CustomerRepository customers;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void readsLegacyStatusAndWritesCanonicalStatus() {
        jdbc.update("""
            INSERT INTO customers
                (id, display_name, status, active)
            VALUES (?, ?, ?, ?)
            """,
            9001L,
            "Le Minh",
            "A",
            true
        );

        Customer loaded = customers.findById(9001L)
            .orElseThrow();

        assertThat(loaded.status())
            .isEqualTo(CustomerStatus.ACTIVE);

        customers.save(loaded);

        String storedStatus = jdbc.queryForObject(
            "SELECT status FROM customers WHERE id = ?",
            String.class,
            9001L
        );

        assertThat(storedStatus).isEqualTo("ACTIVE");
    }
}
```

This test confirms two things:

1. The new code reads legacy code `A` into domain value `ACTIVE`.
2. When saved back, the converter emits the canonical value `ACTIVE`.

Fixtures must supply all NOT NULL columns and use IDs compatible with the test schema. If the table uses identity/sequences, handle manual ID insertion and sequence state according to the database.

### 8.1. Legacy Data with NULL Values

If the old schema allowed a column to be NULL or historical rows contain NULL, create a dedicated fixture:

```sql
INSERT INTO customers (
    id, display_name, middle_name, credit_limit,
    loyalty_points, status, active
)
VALUES (
    9002, 'Pham Hoa', NULL, NULL,
    NULL, 'A', TRUE
);
```

Then confirm the new code reads the nullable properties as null or applies domain-defined normalization.

Do not assume legacy data obeys new schema constraints. If the new schema tightens a column to NOT NULL, backfill data before adding the constraint.

## 9. Legacy Data Compatibility Is Not Only About Converters

Converters resolve differences in **values and representations**. They cannot fix every schema change on their own.

Distinguish three cases:

| Change | Can a Converter Solve It? | Approach |
| --- | --- | --- |
| Status column uses code `A` instead of `ACTIVE` | Yes, if the converter is registered and understands both formats. | Reader accepts legacy codes; writer emits canonical values. |
| Nullable column contains NULL while new code needs explicit representation | Possibly, through matching mapping/types and domain rules. | Use wrapper/reference types, test NULLs, and normalize if needed. |
| Old table lacks column `loyalty_points` | No. | Migration/schema compatibility before querying that column. |
| Column renamed from `display_name` to `name` | Not via value converters alone. | Migration, mapping compatibility, or an appropriate view. |
| Column type changed from VARCHAR to JSON | May need a converter, but also depends on SQL type and driver. | Migration, conversion, and integration tests on a real database. |

If a column does not exist yet, generated SQL may still reference that column name and the database will return an error. A converter never gets a chance to run for a missing column.

## 10. Backward-Compatible Migration Strategies

When deploying new code against a database with existing legacy data, break changes into safely deployable steps.

For example, changing a status column from short codes to descriptive strings:

1. **Expand:** allow both old and new values during the transition; deploy a reader that understands both.
2. **Deploy compatible readers:** roll out new application instances capable of reading both `A`/`I` and `ACTIVE`/`INACTIVE`.
3. **Switch writers:** new application starts writing the canonical format.
4. **Backfill:** convert legacy rows to the canonical format via migration.
5. **Verify:** check that no legacy values remain and all running instances understand the new format.
6. **Contract:** remove the legacy format reader branch or compatibility constraints/columns only when no old writers or readers remain.

This is the **expand-and-contract migration** pattern. It is especially critical during rolling deployments when old and new code access the database concurrently for a period of time.

Do not deploy new code writing a format that older application instances cannot read until all old instances are upgraded or have a compatibility layer in place.

### 10.1. Adding a New Column

Suppose `loyalty_points` needs to be added:

```sql
ALTER TABLE customers
ADD COLUMN loyalty_points INTEGER;
```

Initially, the column should be nullable if existing rows lack values. New code must understand what NULL means. Then backfill:

```sql
UPDATE customers
SET loyalty_points = 0
WHERE loyalty_points IS NULL;
```

Only once data is backfilled and the application handles it properly should you consider:

```sql
ALTER TABLE customers
ALTER COLUMN loyalty_points SET NOT NULL;
```

DDL syntax varies by database. Migrations must use the right dialect and be tested on the same database engine as production.

### 10.2. Renaming a Column

Directly renaming a column can break older application instances immediately. A safer workflow is:

- Add the new column.
- Sync data between old and new columns during the transition.
- Deploy code that reads from the new schema while maintaining legacy compatibility if required.
- Switch writers to the new column.
- Backfill and verify.
- Drop the old column in a later migration once no application version depends on it.

If using database views or triggers to maintain compatibility, test both read and write paths because views/triggers can have distinct semantics.

## 11. Symmetry Does Not Mean Writer and Reader Must Emit the Same Format

During migration, you can deliberately configure:

- A reader accepting multiple old/new formats.
- A writer emitting only a single canonical format.

Example:

```text
Legacy rows:
"A"         -> CustomerStatus.ACTIVE
"ACTIVE"    -> CustomerStatus.ACTIVE
"I"         -> CustomerStatus.INACTIVE
"INACTIVE"  -> CustomerStatus.INACTIVE

New writes:
CustomerStatus.ACTIVE   -> "ACTIVE"
CustomerStatus.INACTIVE -> "INACTIVE"
```

This is still an intentional mapping. The goal is preserving domain meaning, not necessarily preserving historical representations.

Determine when to retire the old format. If old writers are still active, they can keep writing `A` even after backfill has run. Therefore, data migrations must be coordinated with the deployment status of all writers.

## 12. Testing Schema Migrations and Multi-Version Compatibility

Beyond repository tests, projects should include migration tests:

- Create a database at the older schema version.
- Insert fixtures in the legacy data format.
- Execute migrations in order.
- Boot the new code's mapping/repositories.
- Read legacy rows.
- Write a new row.
- Confirm new data uses the canonical format.
- Confirm new constraints do not drop valid data.
- Re-verify NULL and default cases.

For rolling deployments, define a compatibility matrix:

| Reader | Writer | Required Guarantee |
| --- | --- | --- |
| Old code | Old code | Existing pre-migration behavior. |
| New code | Old code | New reader still reads old format. |
| New code | New code | Reader/writer use canonical format. |
| Old code | New code | Safe only if new writer still emits a format old code understands. |

The last row is why switching the write format must be delayed until old readers are retired or a compatibility layer exists.

## 13. Testing with the Right Database and JDBC Driver

H2 is convenient for fast tests, but does not fully represent PostgreSQL, MySQL, SQL Server, or Oracle. Differences can appear in:

- UUID types and storage formats.
- Timestamp precision/timezones.
- DECIMAL precision/scale.
- Boolean representations.
- NULL parameter casting.
- Enums/custom types.
- Defaults, generated columns, and triggers.
- Migration and constraint syntax.
- Collation/case sensitivity.

For database-dependent behavior, use Testcontainers or a test database matching your production engine and major version.

Example Testcontainers PostgreSQL setup for tests:

```java
@Testcontainers
@DataJdbcTest
@AutoConfigureTestDatabase(
    replace = AutoConfigureTestDatabase.Replace.NONE
)
class CustomerPostgresRoundTripTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void configureDatasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

This illustrates container configuration; the project needs the Testcontainers PostgreSQL dependency, schema/migration configuration, and an image version matching its deployment environment.

## 14. Recommended Test Matrix

For an aggregate with converters, nullable fields, and historical data, cover the key scenarios:

| Scenario | Written Data / Fixture | What to Verify |
| --- | --- | --- |
| Normal round-trip | All properties have valid values | Each property's semantics are preserved. |
| Nullable fields | One or more properties null | SQL NULL is written and read back accurately. |
| Empty string | `""` | Not unintentionally confused with NULL. |
| Database defaults | Column omitted from insert or DB-generated | Default value is read back per mapping. |
| Decimal precision | Value with scale differing from schema | Round-tripped value conforms to precision/scale. |
| Timestamp precision | Instant with nanoseconds | Compare at the precision committed by the database. |
| Legacy enum | Old code `A`/`I` | New reader maps to the expected domain value. |
| Canonical enum | New string `ACTIVE` | Reader parses the new format. |
| Unknown enum | Unsupported value | Error or fallback per defined policy. |
| Legacy NULL | Legacy row with nullable column NULL | New code handles nullability properly. |
| Schema migration | Database at older version | Migration completes and new code accesses data cleanly. |
| Rolling deployment | Old and new writers/readers | Data format remains compatible during transition. |

There is no need to cram everything into one giant test. Separate converter unit tests, repository integration tests, and migration tests so failures are easy to pinpoint.

## 15. Common Pitfalls

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Reloaded object differs from input | Database normalized scale, precision, or default values. | Compare per domain rules and normalize expected values. |
| SQL NULL turns into 0/false | Used primitive for nullable column or unclear normalization. | Use wrappers and define NULL semantics. |
| NULL written as a default value | Code assigned default before save or column is NOT NULL. | Distinguish null, default, and application-provided values. |
| Converter unit tests pass but repository fails | Converter not registered or wrong SQL type mapping. | Add an integration test through Spring Data JDBC. |
| Legacy data cannot be read | Reader only understands the new format. | Allow reader to accept legacy formats during migration. |
| Unknown values become UNKNOWN and hide bugs | Fallback lacks clear domain policy. | Choose fail-fast or intentional fallback with proper logging/observability. |
| New code fails on old schema | New columns/constraints not yet migrated. | Deploy expand migrations before code depending on the new schema. |
| H2 tests pass while production fails | Dialect/driver/precision/NULL behavior differences. | Test against a database matching production's engine. |
| Flaky timestamp tests | Relies on local clock/timezone or unstable precision. | Use fixed timestamps and normalize to schema precision. |
| Old writers keep writing legacy format after backfill | Rolling deployment still has old instances. | Keep compatible readers until all old writers have stopped. |

## 16. Workflow for Building Round-Trip and Compatibility Tests

When adding properties, converters, or schema changes:

1. Identify the Java type, SQL type, nullability, and precision of each property.
2. Define round-trip rules: preserve exact, normalize, or database-generated.
3. Write unit tests for every reading and writing converter.
4. Write repository integration tests saving and reloading aggregates.
5. Test SQL NULL, empty strings, and default values separately.
6. Test DECIMAL precision, DATE/TIMESTAMP precision, and database-specific types.
7. Create fixtures in legacy formats to verify new code still reads them.
8. Verify new writers emit the canonical format.
9. Test migrations from older schema versions to the new one.
10. Design expand-and-contract steps for rolling deployments if multiple application versions run concurrently.
11. Run integration tests against the actual database/driver for production-sensitive behavior.
12. Remove legacy converters/compatibility paths only when no data or writers depend on them.

> **A good round-trip preserves domain meaning, even when the database normalizes representation.** Separately test converters, repository mapping, SQL NULLs, precision, and legacy fixtures; converters can handle multiple value formats, but cannot replace migrations when schemas lack columns or constraints change.
