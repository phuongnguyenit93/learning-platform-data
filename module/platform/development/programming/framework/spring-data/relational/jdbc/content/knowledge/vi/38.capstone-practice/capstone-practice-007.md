# Bổ sung auditing và sự kiện sau commit

Trong ứng dụng **Spring Data Relational JDBC**, auditing và domain event giúp ghi nhận ai đã thay đổi dữ liệu, thay đổi lúc nào và thông báo cho các thành phần khác sau một thao tác nghiệp vụ. Khi chuyển từ JPA sang Spring Data JDBC, cần đặt hai cơ chế này đúng vào lifecycle mới: auditing được thực hiện trong quá trình persistence chuẩn bị ghi aggregate, còn sự kiện cần chạy sau khi transaction commit phải được gắn với transaction.

Bài thực hành này bổ sung bốn trường audit cho aggregate đơn hàng, cấu hình `@EnableJdbcAuditing`, cung cấp `AuditorAware` và `DateTimeProvider`, sau đó phát sự kiện `OrderConfirmed` và xử lý bằng `@TransactionalEventListener(phase = AFTER_COMMIT)`. Cuối cùng, bài học phân biệt callback persistence với application event, kiểm tra hành vi khi rollback và giới thiệu transactional outbox cho side effect cần độ tin cậy cao.

## 1. Auditing và sự kiện giải quyết vấn đề gì?

Auditing trả lời các câu hỏi:

- Bản ghi được tạo khi nào?
- Ai tạo bản ghi?
- Lần cập nhật gần nhất diễn ra khi nào?
- Ai thực hiện lần cập nhật gần nhất?

Sự kiện nghiệp vụ trả lời câu hỏi khác: sau khi một hành động như xác nhận đơn hàng đã được lưu thành công, thành phần nào cần được thông báo để gửi email, cập nhật read model hoặc phát message?

Hai trách nhiệm này có thời điểm và mục đích khác nhau:

| Cơ chế | Thời điểm | Mục đích |
| --- | --- | --- |
| Auditing | Trong lifecycle ghi aggregate | Gán created/modified date và actor |
| Entity callback | Trước hoặc sau một bước persistence | Bổ sung hoặc điều chỉnh dữ liệu trong lifecycle |
| Persistence lifecycle event | Khi Spring Data JDBC thực hiện bước load/save | Quan sát hoạt động persistence |
| Application/domain event | Khi use case hoàn thành một hành động nghiệp vụ | Thông báo một sự kiện có ý nghĩa với domain |
| Transaction-bound event listener | Sau commit hoặc rollback theo phase | Chạy side effect đúng với kết quả transaction |
| Transactional outbox | Ghi cùng transaction với aggregate | Bảo đảm có bản ghi chờ gửi event dù process dừng sau commit |

Không nên dùng một callback BeforeSave để gửi email hoặc gọi HTTP. Callback đó chạy trong quá trình ghi, khi transaction vẫn có thể rollback. Side effect bên ngoài cần được đặt sau commit hoặc dùng outbox.

## 2. Bổ sung audit fields cho aggregate

Giả sử đơn hàng có bốn trường:

- `createdAt`: thời điểm tạo.
- `createdBy`: actor tạo.
- `lastModifiedAt`: thời điểm sửa gần nhất.
- `lastModifiedBy`: actor sửa gần nhất.

Entity:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Version
    private Long version;

    private String orderNumber;
    private OrderStatus status;

    @CreatedDate
    private Instant createdAt;

    @CreatedBy
    private String createdBy;

    @LastModifiedDate
    private Instant lastModifiedAt;

    @LastModifiedBy
    private String lastModifiedBy;
}
~~~

Các annotation auditing thuộc Spring Data Commons:

| Annotation | Ý nghĩa |
| --- | --- |
| `@CreatedDate` | Thời điểm entity được tạo |
| `@CreatedBy` | Actor tạo entity |
| `@LastModifiedDate` | Thời điểm entity được cập nhật gần nhất |
| `@LastModifiedBy` | Actor cập nhật gần nhất |

`@Version` có trách nhiệm riêng: phát hiện concurrent update. Không dùng version thay cho `lastModifiedAt`, và không dùng audit timestamp thay cho optimistic locking.

### 2.1. Kiểu dữ liệu thời gian

Các kiểu Java time như `Instant`, `LocalDateTime`, `OffsetDateTime` hoặc `LocalDate` có thể được dùng tùy mapping và nhu cầu nghiệp vụ. Với audit timestamp xuyên nhiều hệ thống, `Instant` thường thuận tiện vì biểu diễn một thời điểm trên timeline UTC.

Ví dụ schema:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(24) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    created_by VARCHAR(120),
    last_modified_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_modified_by VARCHAR(120)
);
~~~

Kiểu timestamp chính xác phụ thuộc database. Hãy chọn kiểu cột tương thích với Java type và thống nhất timezone giữa ứng dụng, database và log.

### 2.2. Audit field không phải dữ liệu do client tự quyết định

Không nhận `createdBy`, `createdAt`, `lastModifiedBy` từ request rồi tin tưởng ghi trực tiếp. Các trường này nên do backend xác định từ actor đã xác thực và clock của ứng dụng. Nếu cho phép client gửi chúng, caller có thể giả mạo lịch sử thay đổi.

## 3. Bật auditing bằng @EnableJdbcAuditing

Spring Data JDBC cung cấp `@EnableJdbcAuditing` để bật hạ tầng auditing. Đặt annotation trong một configuration class được nạp bởi application context:

~~~java
import java.time.Clock;
import java.time.Instant;
import java.util.Optional;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.auditing.DateTimeProvider;
import org.springframework.data.domain.AuditorAware;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing(
        auditorAwareRef = "auditorAware",
        dateTimeProviderRef = "dateTimeProvider"
)
public class JdbcAuditingConfiguration {

    @Bean
    AuditorAware<String> auditorAware(CurrentActor currentActor) {
        return currentActor::currentActor;
    }

    @Bean
    DateTimeProvider dateTimeProvider(Clock clock) {
        return () -> Optional.of(Instant.now(clock));
    }

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }
}
~~~

`CurrentActor` là abstraction của ứng dụng để lấy actor hiện tại. Ví dụ có thể triển khai bằng Spring Security, tenant context hoặc service identity. Cách tách này giúp auditing không phụ thuộc trực tiếp vào HTTP request.

Nếu không cần tùy chỉnh clock, có thể bỏ `DateTimeProvider` và để auditing dùng nguồn thời gian mặc định. Việc cung cấp `Clock` giúp kiểm thử thời gian nhất quán và dễ điều khiển.

### 3.1. AuditorAware cung cấp actor

`AuditorAware<T>` trả về `Optional<T>` cho actor hiện tại. Ví dụ với Spring Security:

~~~java
import java.util.Optional;

import org.springframework.data.domain.AuditorAware;
import org.springframework.security.authentication.AnonymousAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;

public class SecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication authentication =
                SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null
                || !authentication.isAuthenticated()
                || authentication instanceof AnonymousAuthenticationToken) {
            return Optional.empty();
        }

        return Optional.of(authentication.getName());
    }
}
~~~

Đăng ký bean:

~~~java
@Bean
AuditorAware<String> auditorAware() {
    return new SecurityAuditorAware();
}
~~~

Với thao tác chạy nền, không có người dùng đăng nhập. Có thể trả về actor hệ thống như `system:order-import`, hoặc `Optional.empty()` nếu schema và chính sách cho phép. Chọn quy ước nhất quán để audit record giải thích được nguồn thay đổi.

### 3.2. Không dùng request context làm nguồn duy nhất

Auditing có thể chạy trong scheduler, message consumer, batch job hoặc integration test. Vì vậy, không nên giả định mọi thao tác đều có HTTP request và `SecurityContext` của người dùng. Một `CurrentActor` abstraction có thể cung cấp actor từ nhiều nguồn:

- Người dùng đã xác thực.
- Service account.
- Batch job.
- Message consumer.
- System process.

Nếu không có actor, quyết định rõ nên ghi `null`, một system identity hay từ chối thao tác. Không tự gán một người dùng giả.

### 3.3. DateTimeProvider và Clock

`DateTimeProvider` cung cấp thời gian cho auditing. Dùng `Clock` giúp test không phụ thuộc thời gian hệ thống:

~~~java
@Bean
Clock auditClock() {
    return Clock.systemUTC();
}

@Bean
DateTimeProvider dateTimeProvider(Clock auditClock) {
    return () -> Optional.of(Instant.now(auditClock));
}
~~~

Nếu ứng dụng cần timezone hiển thị, hãy chuyển đổi ở tầng presentation. Audit timestamp nên giữ một quy ước thống nhất, thường là UTC.

## 4. Auditing diễn ra trong lifecycle persistence

Khi gọi repository save, Spring Data JDBC thực hiện các bước chuyển aggregate thành dữ liệu ghi. Auditing infrastructure dùng entity callback để gán audit fields trước khi entity được chuyển đổi và lưu.

Luồng khái quát:

~~~text
Application service
       |
       v
repository.save(aggregate)
       |
       v
Auditing callback
  - created date/by nếu là insert
  - modified date/by khi ghi
       |
       v
Entity conversion
       |
       v
SQL INSERT / UPDATE
       |
       v
Transaction commit hoặc rollback
~~~

Vì audit values được gán trong persistence operation, hãy dùng instance trả về từ `save` nếu cần đọc các giá trị đã được bổ sung.

### 4.1. Created và modified fields

Khi insert:

- `createdAt` và `createdBy` được gán theo auditor/time provider.
- `lastModifiedAt` và `lastModifiedBy` có thể cũng được gán khi tạo, tùy cấu hình `modifyOnCreate`.

Khi update:

- `createdAt` và `createdBy` giữ ý nghĩa lịch sử tạo.
- `lastModifiedAt` và `lastModifiedBy` được cập nhật theo lần ghi hiện tại.

Nếu cần thay đổi behavior mặc định, xem các thuộc tính của `@EnableJdbcAuditing` trong phiên bản Spring Data Relational đang dùng, đặc biệt `modifyOnCreate` và `setDates`.

### 4.2. Insert và update phải được xác định đúng

Auditing phụ thuộc thao tác persistence được nhận diện là insert hay update. Nếu entity có ID được ứng dụng gán sẵn, hãy cấu hình newness strategy đúng, chẳng hạn dùng `Persistable.isNew()` hoặc `@Version` theo mô hình phù hợp. Nếu entity mới bị nhận nhầm là đã tồn tại, cả SQL operation và audit semantics có thể sai.

### 4.3. Ghi trực tiếp bằng JDBC template

Một câu `JdbcTemplate.update(...)` không đi qua toàn bộ aggregate mapping và auditing callback pipeline:

~~~java
jdbcTemplate.update(
        "UPDATE purchase_order SET status = ? WHERE id = ?",
        "CANCELLED",
        orderId
);
~~~

Nếu dùng SQL trực tiếp, ứng dụng phải tự cập nhật audit fields:

~~~java
jdbcTemplate.update("""
        UPDATE purchase_order
        SET status = ?,
            last_modified_at = ?,
            last_modified_by = ?
        WHERE id = ?
        """,
        "CANCELLED",
        Instant.now(clock),
        currentActor.requireActor(),
        orderId
);
~~~

Nếu bảng có `@Version`, câu SQL trực tiếp cũng phải kiểm tra version và tăng version. Hãy đặt các quy tắc này trong một persistence adapter dùng chung để tránh mỗi nơi ghi một kiểu.

## 5. Entity callbacks và persistence lifecycle events

Spring Data Relational cung cấp callback để can thiệp vào lifecycle của entity/aggregate. Một số callback thường dùng:

| Callback | Thời điểm |
| --- | --- |
| `BeforeConvertCallback<T>` | Trước khi aggregate được chuyển thành dữ liệu ghi |
| `BeforeSaveCallback<T>` | Trước khi dữ liệu được lưu |
| `AfterSaveCallback<T>` | Sau khi thao tác save hoàn tất |
| `AfterConvertCallback<T>` | Sau khi dữ liệu đọc được chuyển thành entity |

Chữ ký callback và kiểu dữ liệu đi kèm có thể thay đổi theo phiên bản Spring Data Relational. Hãy kiểm tra API trong dependency của ứng dụng khi triển khai.

### 5.1. Callback phù hợp để làm gì?

Callback phù hợp cho logic kỹ thuật gắn với lifecycle persistence:

- Chuẩn hóa hoặc bổ sung metadata trước khi convert.
- Tạo giá trị phụ thuộc vào thời điểm lưu.
- Điều chỉnh dữ liệu trước khi ghi.
- Quan sát kết quả persistence để cập nhật state kỹ thuật.

Ví dụ minh họa `BeforeConvertCallback`:

~~~java
@Component
public class OrderNumberNormalization
        implements BeforeConvertCallback<PurchaseOrder> {

    @Override
    public PurchaseOrder onBeforeConvert(PurchaseOrder aggregate) {
        aggregate.normalizeOrderNumber();
        return aggregate;
    }
}
~~~

Đây là callback đồng bộ, chạy trong luồng persistence. Chỉ dùng nó cho thao tác nhanh và xác định. Không gửi email, gọi payment gateway hoặc chờ HTTP response trong callback.

### 5.2. Callback khác application event

Callback thường có thể trả về aggregate đã thay đổi và được dùng trong bước persistence tiếp theo. Application event chủ yếu thông báo rằng một điều gì đó đã xảy ra để listener phản ứng.

Không dùng callback để triển khai business workflow dài. Nếu callback ném exception, thao tác persistence có thể thất bại và transaction bị rollback.

### 5.3. Persistence lifecycle events

Spring Data Relational cũng có thể phát các lifecycle event như `BeforeConvertEvent`, `BeforeSaveEvent`, `AfterSaveEvent`, `AfterLoadEvent` hoặc `AfterConvertEvent` tùy loại thao tác và phiên bản. Chúng giúp observer theo dõi hoạt động persistence.

Lifecycle event thường xảy ra trước khi transaction commit. Một listener `@EventListener` thông thường được gọi ngay khi event được publish; nó không tự đợi commit. Nếu listener thực hiện side effect bên ngoài, transaction có thể rollback sau đó và side effect vẫn đã xảy ra.

## 6. Phát domain event khi đơn hàng được xác nhận

Một event nghiệp vụ nên mô tả điều đã xảy ra, ví dụ `OrderConfirmed`, thay vì chỉ mô tả rằng một row database vừa được update.

Event nên là dữ liệu bất biến, chứa ID và các thông tin cần thiết:

~~~java
public record OrderConfirmed(
        Long orderId,
        String orderNumber,
        Long aggregateVersion
) {
}
~~~

Application service:

~~~java
@Service
public class OrderApplicationService {

    private final PurchaseOrderRepository orders;
    private final ApplicationEventPublisher events;

    public OrderApplicationService(
            PurchaseOrderRepository orders,
            ApplicationEventPublisher events
    ) {
        this.orders = orders;
        this.events = events;
    }

    @Transactional
    public PurchaseOrder confirm(Long id) {
        PurchaseOrder order = orders.findById(id).orElseThrow();
        order.confirm();

        PurchaseOrder saved = orders.save(order);

        events.publishEvent(new OrderConfirmed(
                saved.getId(),
                saved.getOrderNumber(),
                saved.getVersion()
        ));

        return saved;
    }
}
~~~

Event được publish sau khi repository save thành công nhưng vẫn ở bên trong transaction. Listener sẽ quyết định chờ đến phase nào.

Không nên đưa toàn bộ aggregate mutable vào event nếu listener chỉ cần ID và một vài fact. Event nhỏ, bất biến giúp tránh listener vô tình phụ thuộc vào object đã thay đổi hoặc vào lazy behavior của một ORM khác.

## 7. Chạy listener sau commit bằng @TransactionalEventListener

Listener:

~~~java
@Component
public class OrderConfirmedListener {

    private final ConfirmationEmailGateway emailGateway;

    public OrderConfirmedListener(
            ConfirmationEmailGateway emailGateway
    ) {
        this.emailGateway = emailGateway;
    }

    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    public void on(OrderConfirmed event) {
        emailGateway.sendConfirmation(
                event.orderId(),
                event.orderNumber()
        );
    }
}
~~~

`@TransactionalEventListener` gắn listener với transaction hiện tại. Với `AFTER_COMMIT`, listener chỉ chạy sau khi transaction commit thành công.

### 7.1. Vì sao publish trước commit nhưng listener chạy sau commit?

Application event được publish trong method `confirm`, khi transaction vẫn đang mở. Spring ghi nhận listener cần xử lý khi transaction hoàn tất. Khi commit thành công, callback của transaction kích hoạt listener.

~~~text
BEGIN
  |
  +-- load PurchaseOrder
  |
  +-- change status
  |
  +-- repository.save(...)
  |
  +-- publish OrderConfirmed
  |       |
  |       +-- listener được đăng ký chờ AFTER_COMMIT
  |
COMMIT
  |
  +-- OrderConfirmedListener.on(...)
          |
          +-- gửi confirmation email
~~~

Nếu transaction rollback, listener `AFTER_COMMIT` không chạy. Đây là điểm khác biệt chính so với `@EventListener` thông thường.

### 7.2. TransactionPhase

`@TransactionalEventListener` hỗ trợ các phase:

| Phase | Thời điểm |
| --- | --- |
| `BEFORE_COMMIT` | Trước khi transaction commit |
| `AFTER_COMMIT` | Sau khi commit thành công |
| `AFTER_ROLLBACK` | Sau khi rollback |
| `AFTER_COMPLETION` | Sau khi transaction hoàn tất, dù commit hay rollback |

Với email xác nhận đơn hàng, thường chọn `AFTER_COMMIT`. Với việc giải phóng tài nguyên hoặc ghi nhận một kết quả bất kể commit/rollback, cân nhắc `AFTER_COMPLETION` hoặc `AFTER_ROLLBACK` theo đúng ý nghĩa.

### 7.3. Không có transaction thì sao?

Mặc định, transactional event listener cần transaction đang hoạt động. Nếu publish event khi không có transaction, listener không được thực thi.

Thuộc tính `fallbackExecution = true` cho phép listener chạy ngay cả khi không có transaction. Nhưng khi đó không còn bảo đảm “sau commit” vì không có transaction để chờ. Chỉ bật fallback nếu nghiệp vụ thực sự chấp nhận cả trường hợp không có transaction.

Để bảo đảm semantics sau commit, hãy gọi application service có `@Transactional` qua Spring proxy và publish event trong transaction đó.

## 8. Event listener ghi database cần transaction mới

Sau commit, transaction ban đầu đã hoàn tất. Nếu listener cần ghi một bảng khác, chẳng hạn tạo bản ghi audit phụ hoặc notification status, hãy mở transaction mới:

~~~java
@Component
public class OrderProjectionListener {

    private final OrderProjectionRepository projections;

    public OrderProjectionListener(
            OrderProjectionRepository projections
    ) {
        this.projections = projections;
    }

    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void on(OrderConfirmed event) {
        projections.markConfirmed(
                event.orderId(),
                event.aggregateVersion()
        );
    }
}
~~~

Sau commit, transaction resources của transaction trước có thể vẫn còn được bind trong quá trình completion callback. Nếu listener ghi dữ liệu mà tham gia transaction cũ đã commit, thay đổi đó có thể không được commit như mong đợi. `REQUIRES_NEW` tạo transaction riêng cho thao tác ghi của listener.

Nếu listener chỉ gọi một external gateway, `REQUIRES_NEW` không làm remote call trở nên atomic với database. Nó chỉ quản lý transaction database của phần xử lý local.

## 9. Event listener bất đồng bộ

Nếu side effect mất thời gian, có thể dùng `@Async` cùng `@EnableAsync`:

~~~java
@Configuration
@EnableAsync
public class AsyncConfiguration {
}
~~~

~~~java
@Component
public class OrderEmailListener {

    @Async("applicationTaskExecutor")
    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    public void on(OrderConfirmed event) {
        // Gửi email hoặc gọi dịch vụ bên ngoài.
    }
}
~~~

Lúc này listener chạy trên executor sau khi transaction commit. Cần cấu hình executor có giới hạn thread/queue và theo dõi lỗi. Không dùng executor không giới hạn khiến tải tăng đột biến tạo quá nhiều thread hoặc task trong bộ nhớ.

### 9.1. Async không đồng nghĩa durable

Nếu process dừng sau commit nhưng trước khi task được xử lý, event trong bộ nhớ có thể bị mất. `@Async` chỉ thay đổi thread thực thi; nó không tạo hàng đợi bền vững.

Nếu yêu cầu giao event đáng tin cậy, dùng transactional outbox hoặc message broker có cơ chế xác nhận và retry phù hợp.

## 10. Domain events từ aggregate root

Spring Data repository hỗ trợ domain events từ aggregate root thông qua `@DomainEvents` và `@AfterDomainEventPublication`. Có thể dùng `AbstractAggregateRoot` để đăng ký event trong domain method:

~~~java
import org.springframework.data.domain.AbstractAggregateRoot;

@Table("purchase_order")
public class PurchaseOrder
        extends AbstractAggregateRoot<PurchaseOrder> {

    @Id
    private Long id;

    private OrderStatus status;

    public void confirm() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Order is not pending");
        }

        status = OrderStatus.CONFIRMED;
        registerEvent(new OrderConfirmed(id, null, null));
    }
}
~~~

Khi repository save aggregate, Spring Data repository infrastructure phát các domain event đã đăng ký. Event được publish trong quá trình gọi repository; listener có thể dùng `@TransactionalEventListener(AFTER_COMMIT)` để chỉ xử lý sau khi transaction thành công.

Nếu cần event chứa version mới hoặc dữ liệu được persistence bổ sung, hãy cân nhắc publish explicit application event sau khi nhận object trả về từ `save`, như ví dụ trước. Domain method thường chạy trước khi version mới được gán.

Khi dùng `JdbcAggregateTemplate` hoặc SQL trực tiếp thay cho repository proxy, không giả định repository domain event publisher sẽ tự chạy. Hãy publish event qua `ApplicationEventPublisher` trong application service sau thao tác ghi, hoặc dùng cơ chế event phù hợp đã cấu hình cho persistence path đó.

## 11. Transactional outbox cho side effect cần độ tin cậy cao

`@TransactionalEventListener(AFTER_COMMIT)` bảo đảm listener không chạy khi transaction rollback, nhưng không bảo đảm side effect bên ngoài sẽ hoàn tất. Có thể xảy ra:

1. Database commit thành công.
2. Process dừng trước khi listener gửi message.
3. Aggregate đã được xác nhận nhưng hệ thống khác không nhận event.

Nếu không được phép mất event, dùng transactional outbox. Trong cùng transaction, lưu aggregate và một outbox record:

~~~java
@Transactional
public PurchaseOrder confirm(Long id) {
    PurchaseOrder order = orders.findById(id).orElseThrow();
    order.confirm();

    PurchaseOrder saved = orders.save(order);

    outbox.save(OutboxMessage.pending(
            UUID.randomUUID(),
            "OrderConfirmed",
            saved.getId(),
            saved.getVersion()
    ));

    return saved;
}
~~~

Hai thao tác commit cùng nhau:

~~~text
BEGIN
  |
  +-- UPDATE purchase_order
  |
  +-- INSERT outbox_message
  |
COMMIT
  |
  +-- poller/dispatcher đọc outbox
          |
          +-- publish message
          |
          +-- đánh dấu delivered
~~~

Nếu transaction rollback, cả update aggregate và outbox row đều rollback. Nếu process dừng sau commit, outbox row vẫn còn để dispatcher xử lý sau khi ứng dụng khởi động lại.

### 11.1. Cấu trúc outbox cơ bản

~~~sql
CREATE TABLE outbox_message (
    id UUID PRIMARY KEY,
    event_type VARCHAR(120) NOT NULL,
    aggregate_id BIGINT NOT NULL,
    aggregate_version BIGINT,
    payload TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    delivered_at TIMESTAMP WITH TIME ZONE,
    attempts INTEGER NOT NULL DEFAULT 0
);
~~~

Trong hệ thống thực tế, có thể bổ sung trạng thái, next-attempt time, error code, partition key và index phục vụ dispatcher. Payload cần có version/schema contract để consumer tương thích khi event thay đổi.

### 11.2. Dispatcher và idempotency

Dispatcher cần:

- Chọn các outbox row chưa gửi.
- Claim/lock row để nhiều worker không gửi cùng lúc ngoài ý muốn.
- Publish message tới broker hoặc external endpoint.
- Chỉ đánh dấu delivered sau khi nhận xác nhận phù hợp.
- Retry lỗi tạm thời với backoff và giới hạn.
- Đưa lỗi kéo dài vào dead-letter/operations workflow.

Không thể luôn bảo đảm exactly-once delivery xuyên database và message broker chỉ bằng một transaction JDBC. Thực tế thường dùng at-least-once delivery cùng consumer idempotent. Consumer lưu event ID đã xử lý hoặc dùng unique constraint để một event được áp dụng hiệu quả một lần.

### 11.3. Khi nào dùng AFTER_COMMIT, khi nào dùng outbox?

| Nhu cầu | Cách tiếp cận |
| --- | --- |
| Cập nhật cache best-effort sau commit | `@TransactionalEventListener(AFTER_COMMIT)` |
| Gửi email nội bộ, chấp nhận retry vận hành | AFTER_COMMIT listener và cơ chế theo dõi lỗi |
| Phát message không được phép mất | Transactional outbox |
| Cập nhật read model trong cùng database | Listener với `REQUIRES_NEW` hoặc outbox tùy yêu cầu nhất quán |
| Gọi dịch vụ thanh toán | Workflow có idempotency, retry và trạng thái rõ ràng; không gọi trong callback save |

## 12. Kiểm thử auditing

Với `@DataJdbcTest`, có thể import auditing configuration vào slice:

~~~java
@DataJdbcTest
@Import(AuditingTestConfiguration.class)
class PurchaseOrderAuditingTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void recordsCreatedAndModifiedAuditFields() {
        PurchaseOrder created = orders.save(
                PurchaseOrder.pending("PO-AUDIT", OrderStatus.PENDING)
        );

        assertThat(created.getCreatedAt()).isNotNull();
        assertThat(created.getCreatedBy()).isEqualTo("test-user");
        assertThat(created.getLastModifiedAt()).isNotNull();
        assertThat(created.getLastModifiedBy()).isEqualTo("test-user");

        Instant originalCreatedAt = created.getCreatedAt();

        created.changeStatus(OrderStatus.CONFIRMED);
        PurchaseOrder updated = orders.save(created);

        assertThat(updated.getCreatedAt()).isEqualTo(originalCreatedAt);
        assertThat(updated.getCreatedBy()).isEqualTo("test-user");
        assertThat(updated.getLastModifiedAt()).isNotNull();
        assertThat(updated.getLastModifiedBy()).isEqualTo("test-user");
    }
}
~~~

Test configuration:

~~~java
@TestConfiguration(proxyBeanMethods = false)
@EnableJdbcAuditing
class AuditingTestConfiguration {

    @Bean
    AuditorAware<String> auditorAware() {
        return () -> Optional.of("test-user");
    }
}
~~~

Nếu test cần xác nhận chính xác thời gian tăng giữa insert và update, cung cấp một `DateTimeProvider` điều khiển được thay vì dựa vào `Instant.now()` và giả định clock luôn tick giữa hai thao tác. Test cũng nên kiểm tra created fields không bị ghi đè khi update.

## 13. Kiểm thử AFTER_COMMIT và rollback

Một test dùng `@DataJdbcTest` mặc định có transaction do Spring Test quản lý và thường rollback khi test kết thúc. Vì vậy, listener `AFTER_COMMIT` không chạy cho tới khi transaction test thực sự commit.

Có hai cách kiểm thử:

### 13.1. Điều khiển transaction bằng TestTransaction

Trong test transactional:

~~~java
@Test
void handlesEventOnlyAfterCommit() {
    orderService.confirm(orderId);

    assertThat(listener.receivedEvents()).isEmpty();

    TestTransaction.flagForCommit();
    TestTransaction.end();

    assertThat(listener.receivedEvents()).hasSize(1);
}
~~~

`orderService.confirm` tham gia transaction test nếu propagation mặc định là REQUIRED. Listener chỉ chạy sau khi test transaction commit qua `TestTransaction.end()`.

### 13.2. Tắt transaction bao ngoài của test

Có thể đặt:

~~~java
@DataJdbcTest
@Transactional(propagation = Propagation.NOT_SUPPORTED)
class OrderAfterCommitTest {
}
~~~

Khi đó test không có transaction bao ngoài. Gọi application service có `@Transactional` sẽ mở transaction riêng và commit trước khi method trả về. Listener AFTER_COMMIT được thực thi trong quá trình transaction hoàn tất.

### 13.3. Kiểm thử rollback

Dùng `TransactionTemplate` và đánh dấu rollback-only:

~~~java
transactionTemplate.execute(status -> {
    orderService.confirm(orderId);
    status.setRollbackOnly();
    return null;
});

assertThat(listener.receivedEvents()).isEmpty();
assertThat(orders.findById(orderId).orElseThrow().getStatus())
        .isEqualTo(OrderStatus.PENDING);
~~~

Service tham gia transaction hiện tại. Khi transaction rollback, listener AFTER_COMMIT không được gọi và trạng thái đơn hàng trở lại giá trị trước đó.

### 13.4. Test listener không được gọi khi thiếu transaction

Nếu event được publish ngoài transaction, transactional listener mặc định không thực thi. Có thể kiểm tra hành vi này để tránh một call path vô tình bỏ qua application service transactional. Không bật `fallbackExecution` chỉ để test qua; điều đó thay đổi semantics production.

## 14. Những lỗi thường gặp

| Lỗi | Nguyên nhân | Cách xử lý |
| --- | --- | --- |
| Audit fields luôn null | Chưa bật `@EnableJdbcAuditing` hoặc cấu hình không được nạp | Import/register auditing configuration |
| `createdBy` không có giá trị | Thiếu `AuditorAware` hoặc actor context rỗng | Cung cấp actor cho user và background job |
| Audit actor luôn là anonymous | Không lọc anonymous authentication | Trả `Optional.empty()` hoặc system actor phù hợp |
| `createdAt` bị client giả mạo | Bind audit fields từ request | Để backend auditing gán giá trị |
| `lastModifiedAt` không đổi với SQL trực tiếp | `JdbcTemplate` bỏ qua entity callbacks | Cập nhật audit fields trong SQL/adapter |
| Dùng audit timestamp thay `@Version` | Timestamp không phải concurrency token đáng tin cậy | Dùng `@Version` cho optimistic locking |
| Listener chạy dù transaction rollback | Dùng `@EventListener` thông thường | Dùng `@TransactionalEventListener(AFTER_COMMIT)` |
| Listener không chạy | Không có transaction hoặc transaction không commit | Publish trong application service transactional |
| Listener ghi DB nhưng dữ liệu không commit | Tham gia resources của transaction đã hoàn tất | Dùng `REQUIRES_NEW` |
| Email gửi trước khi transaction commit | Gửi từ callback hoặc listener thông thường | Chờ AFTER_COMMIT |
| Event bị mất khi process dừng | Event chỉ tồn tại trong bộ nhớ | Dùng transactional outbox |
| Event bị xử lý hai lần | Retry hoặc nhiều dispatcher | Dùng event ID và consumer idempotency |
| Test AFTER_COMMIT không chạy | Test transaction mặc định rollback | Dùng TestTransaction hoặc NOT_SUPPORTED |
| Async task bị mất | Executor queue không bền vững | Dùng outbox/broker khi cần delivery bền vững |

## 15. Quy trình bổ sung auditing và event cho một use case

1. **Xác định audit fields:** chọn actor, created time và modified time cần lưu.
2. **Cập nhật schema/entity:** thêm cột và annotation auditing.
3. **Bật auditing:** đăng ký `@EnableJdbcAuditing`, `AuditorAware` và `DateTimeProvider` nếu cần.
4. **Xác định actor nguồn:** user, service account, batch hoặc system process.
5. **Kiểm tra insert/update:** bảo đảm newness strategy và audit behavior đúng.
6. **Xác định domain event:** đặt tên theo hành động nghiệp vụ và dùng payload bất biến.
7. **Publish trong transaction:** sau khi thao tác ghi thành công và trước khi transaction kết thúc.
8. **Đăng ký listener:** dùng `@TransactionalEventListener(AFTER_COMMIT)` cho side effect sau commit.
9. **Tạo transaction mới nếu listener ghi DB:** dùng `REQUIRES_NEW`.
10. **Dùng outbox nếu event không được phép mất:** ghi outbox row cùng transaction aggregate.
11. **Kiểm thử commit và rollback:** xác nhận audit fields, listener phase, idempotency và failure path.
12. **Theo dõi vận hành:** đo retry, listener failures, outbox backlog và event age.

## Ghi nhớ

Spring Data JDBC auditing được bật bằng `@EnableJdbcAuditing`. `AuditorAware` cung cấp actor; `DateTimeProvider` cung cấp thời gian. Các annotation `@CreatedDate`, `@CreatedBy`, `@LastModifiedDate` và `@LastModifiedBy` được xử lý trong persistence lifecycle khi aggregate được lưu qua Spring Data JDBC. SQL trực tiếp qua `JdbcTemplate` không tự chạy auditing callbacks, nên phải cập nhật audit columns tường minh. `@Version` vẫn là cơ chế riêng cho optimistic locking.

Để xử lý side effect sau khi đơn hàng được xác nhận, publish một application/domain event bên trong transaction và dùng `@TransactionalEventListener(phase = AFTER_COMMIT)`. Listener chỉ chạy khi commit thành công; rollback không kích hoạt nó. Nếu listener ghi database, dùng transaction `REQUIRES_NEW`. Nếu event không được phép mất khi process dừng sau commit, lưu outbox row cùng transaction và dispatch với retry/idempotency. Kiểm thử cả commit lẫn rollback; lưu ý `@DataJdbcTest` mặc định rollback transaction test nên cần điều khiển commit bằng `TestTransaction` hoặc tắt transaction bao ngoài cho test phù hợp.
