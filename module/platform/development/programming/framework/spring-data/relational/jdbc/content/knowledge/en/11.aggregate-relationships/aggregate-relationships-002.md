# Mapping a Set for a Child Entity Collection

In a Spring Data JDBC aggregate, an aggregate root can own multiple child entities. When child elements need to be managed as a **non-duplicate** collection, Java's `Set` is a suitable choice. Spring Data Relational provides `@MappedCollection` to describe a collection belonging to an aggregate, where the child table stores a foreign key pointing to the aggregate root.

Mapping a `Set` has several differences compared to `List` and `Map`: a `Set` does not represent element order or position, uniqueness depends on the elements' `equals()`/`hashCode()`, and the database still needs its own constraint if uniqueness is a mandatory data rule. This lesson explains how to declare, persist, and test a collection of child entities in Spring Data JDBC.

## 1. Set in the aggregate model

Suppose a sales system has a `PurchaseOrder` aggregate. An order contains multiple `OrderLine` items. Order lines are created, modified, and deleted through the order; they have no business lifecycle independent of the root.

If an order line is identified by a stable key and the same line must not appear twice in the collection, you can represent the collection with:

```java
private Set<OrderLine> lines = new LinkedHashSet<>();
```

`Set` expresses set semantics:

- Each element appears only once according to Java equality rules.
- There is no element position as in `List`.
- There is no separate key per element as in `Map`.
- Iteration order depends on the `Set` implementation; that order should not be treated as the database storage order.

`Set` is appropriate when the business cares about **which members belong to the collection**, not the position in which they were added.

### 1.1. The aggregate root remains the access point

Example:

```text
PurchaseOrder (aggregate root)
    |
    +-- OrderLine (child entity)
    +-- OrderLine (child entity)
    +-- OrderLine (child entity)
```

Outside the aggregate, callers should invoke behaviors on `PurchaseOrder` such as `addLine` or `removeLine`. Multiple services should not mutate the child `Set` directly, because invariants such as order status, valid quantities, and duplicate-line rules could be bypassed.

In Spring Data JDBC, a repository is typically defined for the **aggregate root**. The `OrderLine` set is saved/loaded as part of the aggregate when the root is persisted.

## 2. What is @MappedCollection used for?

The `@MappedCollection` annotation comes from Spring Data Relational:

```java
import org.springframework.data.relational.core.mapping.MappedCollection;
```

This annotation describes the relationship between the collection property on the root and the data stored in the child table. Two key attributes:

| Attribute | Meaning |
| --- | --- |
| `idColumn` | Name of the column in the child table used to store the ID of the aggregate root owning the collection. |
| `keyColumn` | Name of the column used to store the key or element position for collection types that have a key/index, such as `Map` or `List`. |

With `Set`, there is no collection index or key because a `Set` has no element position. Typically, you only need to specify `idColumn`:

```java
@MappedCollection(idColumn = "order_id")
private Set<OrderLine> lines = new LinkedHashSet<>();
```

This example states that rows in the child table are linked to the root via the `order_id` column. Spring Data JDBC uses the mapping metadata to find and write the elements belonging to the order.

**Do not create an order column just to map a Set.** If the schema has a sequence column used to determine business order, consider whether the collection should actually be a `List` or whether the data should be sorted using a separate query.

## 3. Relational schema for a child entity collection

Suppose the root table and child table are defined as follows:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL UNIQUE,
    status VARCHAR(24) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_key UUID NOT NULL,
    sku VARCHAR(64) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),
    CONSTRAINT uq_order_lines_key
        UNIQUE (order_id, line_key),
    CONSTRAINT ck_order_lines_quantity
        CHECK (quantity > 0)
);
```

In this structure:

- `purchase_orders.id` is the primary key of the aggregate root.
- `order_lines.id` is the primary key of the child entity.
- `order_lines.order_id` is the foreign key pointing to the root.
- `line_key` is a stable domain identifier for the order line, generated by the application.
- `UNIQUE(order_id, line_key)` ensures a line with the same identity cannot be written twice in the same order.
- `CHECK(quantity > 0)` enforces an additional invariant in the database.

`@MappedCollection(idColumn = "order_id")` must match the foreign key column `order_lines.order_id` exactly. Table/column names in the example can be configured with annotations or a `NamingStrategy` depending on project conventions.

### 3.1. A Set relationship does not necessarily need a join table

For child entities owned by the root, the model is typically a child table containing a foreign key back to the root:

```text
purchase_orders
  id (PK)
  order_number
  status
       |
       | 1 - N
       v
order_lines
  id (PK)
  order_id (FK)
  line_key
  sku
  quantity
```

This is a one-to-many relationship following aggregate ownership. `@MappedCollection` does not mean the framework always creates a separate join table. In this example, the `order_lines` table stores both the order line data and the foreign key to the root.

If an object is referenced by multiple independent aggregates, do not turn it into a child just because you want to put it in a `Set`. In that case, model the reference by ID or design an association relationship appropriate to the ownership.

## 4. Declaring an aggregate root with a Set

Simple root example:

```java
import java.util.Collections;
import java.util.LinkedHashSet;
import java.util.Set;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;
    private OrderStatus status;

    @MappedCollection(idColumn = "order_id")
    private Set<OrderLine> lines = new LinkedHashSet<>();

    protected PurchaseOrder() {
        // Used by the materialization mechanism.
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
        this.status = OrderStatus.DRAFT;
    }

    public void addLine(String sku, int quantity) {
        requireDraft();

        OrderLine line = OrderLine.create(sku, quantity);
        if (!lines.add(line)) {
            throw new IllegalArgumentException(
                "Order line already exists in the order"
            );
        }
    }

    public void removeLine(java.util.UUID lineKey) {
        requireDraft();
        lines.removeIf(line -> line.hasKey(lineKey));
    }

    public Set<OrderLine> getLines() {
        return Collections.unmodifiableSet(lines);
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    private void requireDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                "Only orders in DRAFT status can be modified"
            );
        }
    }
}
```

`LinkedHashSet` preserves insertion order **in Java memory**, which is convenient when debugging or iterating over the collection within the same instance. This does not make `Set` a database-guaranteed ordered collection. When reloading the aggregate, the row order returned by the database is not guaranteed if the query has no `ORDER BY` and the mapping does not store an order column.

The `getLines()` method returns a view that prevents callers from directly adding or removing elements. The root retains control over the collection to enforce status checks and invariants.

Enum example:

```java
public enum OrderStatus {
    DRAFT,
    SUBMITTED,
    CANCELLED
}
```

## 5. Designing the child entity and equals/hashCode

The most critical point when using `Set` is that **uniqueness in a Java Set is determined by equals/hashCode**. Without designing these two methods properly, the collection might reject the wrong element or hold elements considered duplicates in a way inconsistent with business rules.

One approach is to assign each order line a stable identity upon creation:

```java
import java.util.Objects;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("line_key")
    private UUID lineKey;

    private String sku;
    private int quantity;

    protected OrderLine() {
        // Used by the materialization mechanism.
    }

    private OrderLine(UUID lineKey, String sku, int quantity) {
        if (lineKey == null) {
            throw new IllegalArgumentException("lineKey is required");
        }
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }

        this.lineKey = lineKey;
        this.sku = sku;
        this.quantity = quantity;
    }

    public static OrderLine create(String sku, int quantity) {
        return new OrderLine(UUID.randomUUID(), sku, quantity);
    }

    public boolean hasKey(UUID key) {
        return lineKey.equals(key);
    }

    public UUID getLineKey() {
        return lineKey;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (!(other instanceof OrderLine that)) {
            return false;
        }
        return lineKey.equals(that.lineKey);
    }

    @Override
    public int hashCode() {
        return Objects.hash(lineKey);
    }
}
```

In this example:

- `id` is the database primary key, which may be generated by the database on insert.
- `lineKey` is generated when the order line is created and does not change during the entity's lifecycle.
- `equals` and `hashCode` are based on the stable `lineKey`, not on `id` which can change from `null` to a database-assigned value.
- `quantity` can change without altering the element's hash.

This is an illustrative strategy. If the domain has a suitable immutable, unique natural key, you can use that key. If an order line is identified by multiple attributes, clearly define the business identity rules rather than arbitrarily comparing all fields.

### 5.1. Avoid hashCode based on a database-generated ID

A common mistake is:

```java
@Override
public int hashCode() {
    return Objects.hash(id);
}
```

When a new object is added to a `HashSet`, `id` may still be `null`. After saving, the database generates an ID and the framework assigns the new ID to the object or creates a new result object. If an element's hashCode changes after it has been placed into a `HashSet`, the `HashSet`'s internal structure can no longer reliably look up the element in its old bucket.

This can cause `contains` or `remove` to behave unexpectedly.

If you use a database identity assigned after insert, design `equals`/`hashCode` to match that lifecycle. Using an immutable application identity like `lineKey` is a clear option in this example.

### 5.2. Do not compare using all mutable fields

If `equals`/`hashCode` is based on `sku` and `quantity`, changing `quantity` after the element is already in a `HashSet` can change the hash. Similarly, if business rules allow two lines with the same SKU but different prices, options, or promotions, comparing by SKU alone could cause the `Set` to wrongly reject a valid line.

Separate:

- **Entity identity:** identifies the same order line.
- **Business uniqueness constraint:** for example, a SKU appears at most once in an order.
- **Mutable attributes:** quantity, note, locked-in price, etc.

These three concepts sometimes overlap, but they are not the same by default.

## 6. Repository saving the aggregate root

The repository is defined for `PurchaseOrder`:

```java
import org.springframework.data.repository.ListCrudRepository;

public interface PurchaseOrderRepository
        extends ListCrudRepository<PurchaseOrder, Long> {
}
```

An application service coordinates the transaction and saves the root:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder create(String orderNumber) {
        PurchaseOrder order = new PurchaseOrder(orderNumber);
        order.addLine("BOOK-001", 2);
        order.addLine("PEN-002", 3);
        return orders.save(order);
    }

    @Transactional
    public PurchaseOrder addLine(Long orderId, String sku, int quantity) {
        PurchaseOrder order = orders.findById(orderId)
            .orElseThrow(() ->
                new IllegalArgumentException("Order not found")
            );

        order.addLine(sku, quantity);
        return orders.save(order);
    }
}
```

When saving the root, Spring Data JDBC handles the mapped collection as part of the aggregate. There is no need to call a separate `OrderLineRepository` for child entities owned by the order.

`@Transactional` ensures the persistence operations required for a use case commit/rollback consistently within the transaction. It does not replace the root's business checks.

### 6.1. Spring Data JDBC does not have JPA-style dirty checking

Spring Data JDBC does not maintain a persistence context the way Hibernate/JPA usually does. Loading a root, modifying the collection, and ending the transaction does not automatically mean the changes have been saved.

Call `repository.save(root)` explicitly after making changes.

When updating an existing aggregate, Spring Data JDBC may delete the referenced entities and re-insert the collection state according to its aggregate persistence model. Thus, a small change in a `Set` does not necessarily produce just a single INSERT or DELETE. You need to account for the number of child elements and the impact on triggers, audits, foreign keys, or other tables referencing them.

This is also a reason to keep aggregates reasonably sized and not cram a huge dataset into a root just because it can be represented as a `Set`.

## 7. How does Set differ from List and Map?

Java collection types express different semantics and affect how they are mapped.

| Characteristic | Set | List | Map |
| --- | --- | --- | --- |
| Allows duplicate elements per collection rules? | No, based on `equals/hashCode` | Yes | Unique keys; values may repeat |
| Has order/position in the collection? | No positional semantics | Has index | Has key |
| Needs key/index column for standard mapping? | No | Can use `keyColumn` to store index | Can use `keyColumn` to store map key |
| Suited for | Set of unique members | Ordered list | Lookup by key |
| Needs sorting for display? | Yes, if order is required | Can rely on stored index | Can rely on key or separate sort |

### 7.1. Set: set of members

```java
@MappedCollection(idColumn = "order_id")
private Set<OrderLine> lines = new LinkedHashSet<>();
```

No index is stored for individual elements. If the business does not care about order, this is the natural model.

### 7.2. List: positional list

```java
@MappedCollection(
    idColumn = "order_id",
    keyColumn = "line_position"
)
private List<OrderLine> lines = new ArrayList<>();
```

`line_position` can store element positions. When the business requires user-arranged order, priority order, or execution order, `List` usually expresses this more accurately than `Set`.

### 7.3. Map: keyed collection of elements

```java
@MappedCollection(
    idColumn = "order_id",
    keyColumn = "line_code"
)
private Map<String, OrderLine> linesByCode = new LinkedHashMap<>();
```

`line_code` stores the Map key. Each key is unique within the Map, though multiple keys can point to values with identical content. This has different semantics from `Set`.

Do not use `Set` just to "avoid writing an index." Choose the collection type based on domain meaning first, then configure the appropriate mapping.

## 8. Element order and queries

`Set` does not guarantee order. Even when using `LinkedHashSet`:

- In memory, it maintains the insertion order of the current instance.
- When loaded from the database, the returned row order is not guaranteed if the SQL does not specify `ORDER BY`.
- Spring Data JDBC does not infer a business order for a `Set`.
- When an API needs to return a list sorted by SKU, name, or creation time, sort it explicitly.

Example converting a `Set` to a sorted list when building a response:

```java
List<OrderLineResponse> response = order.getLines().stream()
    .sorted(Comparator.comparing(OrderLine::getSku))
    .map(line -> new OrderLineResponse(
        line.getSku(),
        line.getQuantity()
    ))
    .toList();
```

This is a presentation/query step at the application layer; it does not alter the semantics of the aggregate collection.

If order is business data that must be stored and restored, use a `List` with a position column or a separate ordering model rather than relying on the arbitrary order of a `Set`.

## 9. Uniqueness in Java vs. uniqueness in the database

`Set` only enforces uniqueness according to Java's `equals/hashCode` rules within one collection instance. It does not automatically create a unique constraint in the database.

There are two layers of protection:

1. **In the domain model:** prevent duplicate elements from being added to the `Set` and validate related invariants.
2. **In the database:** use primary keys, unique constraints, and foreign keys to protect data across multiple concurrent transactions or different writers.

For example, the schema has:

```sql
CONSTRAINT uq_order_lines_key
    UNIQUE (order_id, line_key)
```

This constraint prevents two rows from having the same `line_key` in the same order, even if data is written by another application or two concurrent transactions.

If the business rule is that each SKU appears only once in an order, the constraint could be:

```sql
ALTER TABLE order_lines
ADD CONSTRAINT uq_order_lines_sku
UNIQUE (order_id, sku);
```

Only add this constraint when it matches the business rules. If one SKU can appear as two lines due to different configurations, prices, or promotions, a unique constraint on SKU will be too restrictive.

### 9.1. Set does not replace validation and constraints

Suppose two requests add the same SKU to an order simultaneously. Each request might load a copy of the root and perform an in-memory check; without optimistic locking or an appropriate database constraint, both could still write data in a way that violates the rule.

Therefore:

- Checking duplicates in the root gives clear business error feedback.
- Unique constraints enforce uniqueness at the storage layer.
- Transactions and concurrency control handle concurrent updates.
- If `@Version` is used on the root, Spring Data JDBC can detect stale updates via optimistic locking.

Do not rely solely on `Set.add` to protect a critical invariant across multiple transactions.

## 10. Child entity Set vs. independent aggregates

A `Set` collection on a root should contain objects belonging to the **same aggregate**. If an object has an independent lifecycle and is referenced by multiple roots, it should not become a child entity just to represent a group.

For example, an order can reference products:

```java
private Set<Long> productIds;
```

or use an appropriate aggregate reference type. Do not embed full `Product` entities inside `PurchaseOrder`'s child `Set` if `Product` is a separate aggregate root that can be shared across many orders and managed independently.

If you need to store a many-to-many relationship, you typically need to model an association entity with clear ownership and lifecycle. In Spring Data JDBC, aggregate references and child collections have distinct semantics; do not assume every `Set<A>` automatically becomes a many-to-many relationship with a join table.

For example, one product can be referenced by many orders, whereas an `OrderLine` belongs to one specific order. The order line can store `productId` or SKU along with a snapshot of information at ordering time, while `Product` remains a separate aggregate.

## 11. Testing Set mapping

A repository test should at minimum verify saving the root, reading back the child set, and domain uniqueness rules.

Skeleton example:

```java
@DataJdbcTest
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void persistsAndReloadsChildSet() {
        PurchaseOrder order = new PurchaseOrder("PO-SET-001");
        order.addLine("BOOK-001", 2);
        order.addLine("PEN-002", 3);

        PurchaseOrder saved = orders.save(order);

        PurchaseOrder loaded = orders.findById(saved.getId())
            .orElseThrow();

        assertThat(loaded.getLines()).hasSize(2);
        assertThat(loaded.getLines())
            .extracting(OrderLine::getSku)
            .containsExactlyInAnyOrder("BOOK-001", "PEN-002");
    }
}
```

`containsExactlyInAnyOrder` fits `Set` because it does not assert order. If a test uses `containsExactly`, it can fail flakily even when the element set is right.

Some additional tests:

- Add the same identity twice to the `Set` and verify the domain handles it per the chosen rule.
- Mutate a mutable field and verify `contains`/`remove` still work; this helps catch a `hashCode` that depends on mutable fields.
- Save a root with data, remove an element, and save again; verify the database reflects the collection state.
- Test the database constraint when writing duplicate keys.
- Verify that data reloaded from the database does not rely on row order.
- Test optimistic locking if multiple transactions can update the same root.

The `@DataJdbcTest` test slice needs a test datasource, schema, and appropriate driver dependencies. For PostgreSQL-specific DDL, run integration tests against PostgreSQL (e.g., Testcontainers) rather than relying solely on H2.

## 12. Common pitfalls when mapping a Set

| Symptom | Common cause | How to resolve |
| --- | --- | --- |
| Element disappears after being added to Set | Two objects are equal per `equals/hashCode`, so the Set rejects the second one. | Define entity identity and business uniqueness accurately. |
| `contains` or `remove` cannot find object | `hashCode` changed after the object entered the HashSet, often due to generated ID or mutable fields. | Base it on an immutable identity. |
| Reloading shows a different order | `Set` stores no order semantics; SQL has no `ORDER BY`. | Sort in query/application or use `List` if order is data. |
| Wrong foreign key column | `idColumn` does not match the column name in the child table. | Cross-check `@MappedCollection` with actual DDL. |
| Trying to add `keyColumn` to Set to keep order | `Set` has no position/index. | Use `List` if order needs to be persisted. |
| Database still gets business-level duplicates | Java `Set` only protects one collection in memory, not a replacement for unique constraints. | Add appropriate constraints and handle concurrency. |
| Saving root generates many SQL statements | Spring Data JDBC synchronizes the aggregate; child collection may be deleted/reinserted on root update. | Keep aggregates appropriately sized and review the data model. |
| Set holds objects of another aggregate | Confusing ownership with reference. | Reference independent aggregates by ID or a separate association model. |

## 13. When should you use Set?

Choose `Set` when all of the following match the business semantics:

- Collection order does not matter.
- No index or element position needs to be persisted.
- Each element has a well-defined identity/equality.
- Elements genuinely belong to the aggregate root's ownership.
- Synchronizing the entire collection on root save fits the size and update frequency.

Choose `List` when order is data that must be saved or duplicate elements are valid. Choose `Map` when access by a dedicated key is needed. If elements are independent aggregates, reference them by ID instead of turning them into a child collection.

### Decision table

| Business need | Suggested model |
| --- | --- |
| Unique members, unordered | `Set<Child>` |
| Ordered list persisted in storage | `List<Child>` + key/index column |
| Lookup elements by a domain-defined key | `Map<Key, Child>` |
| Multiple independent aggregates referencing one object | ID/reference or association entity |
| Very large child dataset, frequent independent updates | Consider splitting aggregates and designing dedicated query/persistence |

## 14. Implementation workflow in Spring Data JDBC

1. Determine whether the collection is truly part of the aggregate root or merely a reference to independent aggregates.
2. Choose `Set` only when the domain needs no ordering and requires unique-member semantics.
3. Declare `@MappedCollection(idColumn = "...")` pointing accurately to the foreign key in the child table.
4. Design a stable identity and `equals/hashCode`; avoid mutable fields or IDs generated after the object is already inside a `HashSet`.
5. Define primary key, foreign key, unique constraints, and check constraints in the schema matching the invariants.
6. Modify the collection through root behaviors, then call `repository.save(root)` within an appropriate transaction.
7. Test persistence round-trip, uniqueness, remove/update, and do not assume order.
8. If ordering, a dedicated key, or different ownership is needed, choose `List`/`Map`/reference instead of forcing every structure into a `Set`.

> **`@MappedCollection(idColumn = "...")` maps a Set of child entities via a foreign key pointing to the aggregate root. A Set represents a non-duplicate set of members according to `equals/hashCode` and stores no order; critical uniqueness still needs database-level constraint protection.**
