# Auto-Increment IDs, Generated Keys, and Return Values After Insert

When saving a new record with **Spring Data Relational JDBC (Spring Data JDBC)**, the application often does not yet know the primary key assigned by the database. For example, when creating a new order, the Java object may have `id = null`; the database generates the ID when executing `INSERT`; Spring Data JDBC retrieves the newly generated key and returns the entity with its populated ID for the application to use in subsequent steps.

This flow involves three concepts:

- **Auto-increment ID (generated identity):** the database mechanism that generates a primary key on insert.
- **Generated key:** the key value that the JDBC driver/framework retrieves from the database after insert.
- **Return value of save:** the entity that the repository returns after persisting; this is the object the application should continue using.

## 1. Why are auto-increment IDs and generated keys needed?

Suppose an application creates an order with multiple order items. At the start, the application knows the customer, status, and list of items, but does not yet have an `order_id`. The database assigns a key for the order record; the order items then need to use that exact key as their foreign key.

~~~mermaid
sequenceDiagram
    participant App as Application Service
    participant Repo as OrderRepository
    participant JDBC as Spring Data JDBC / JDBC Driver
    participant DB as Database

    App->>Repo: save(new Order(id = null))
    Repo->>JDBC: INSERT root (without passing id)
    JDBC->>DB: INSERT INTO shop_orders (...)
    DB-->>JDBC: generated key = 501
    JDBC-->>Repo: entity with id = 501
    Repo-->>App: savedOrder(id = 501)
    App->>Repo: use savedOrder or persist subsequent references
~~~

The generated ID is the **persistence identity** of the record. It is usually different from the business code visible to users, such as `orderNumber = "ORD-2026-00051"`. Do not force the displayed order code to be the auto-increment number in the database.

## 2. Distinguishing primary key, auto-increment ID, and business code

| Concept | Example | Purpose |
|---|---|---|
| Primary key | `shop_orders.id = 501` | Uniquely identifies a row in the table |
| Generated ID | Database auto-assigns `501` on insert | Avoids the application computing IDs itself and avoids conflicts across concurrent requests |
| Business key | `order_number = "ORD-2026-00051"` | Code with business meaning, suitable for display or lookup |
| Foreign key | `order_items.order_id = 501` | Links an order item to the order that owns it |

A table can store both a technical ID and a business code:

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);
~~~

`id` serves linking and data access; `order_number` follows business numbering rules. An auto-increment ID is not guaranteed to be contiguous, is not a meaningful order sequence number, and should not be used to infer creation time or total number of orders created.

## 3. Declaring auto-increment columns in PostgreSQL and MySQL

Spring Data JDBC does not automatically turn every `@Id` column into an auto-increment column. **The database schema must declare the corresponding ID generation mechanism.** The following examples use the `shop_orders` table for both database systems; choose only the applicable DDL.

### PostgreSQL: IDENTITY

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);
~~~

`GENERATED BY DEFAULT AS IDENTITY` tells PostgreSQL to auto-generate a value when the insert statement does not supply `id`. `GENERATED ALWAYS AS IDENTITY` can also be used when you want the database to reject user-supplied values unless an explicit override syntax is intentionally used.

In older PostgreSQL schemas, you may encounter:

~~~sql
id BIGSERIAL PRIMARY KEY
~~~

`BIGSERIAL` is a historical convenience syntax that creates a large integer column bound to a sequence. For new schemas, `IDENTITY` clearly expresses that this is an automatically generated identity column.

### MySQL: AUTO_INCREMENT

~~~sql
CREATE TABLE shop_orders (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
) ENGINE=InnoDB;
~~~

MySQL uses `AUTO_INCREMENT` to generate a value when insert omits the `id` column or requests an auto-generated value with appropriate syntax. InnoDB tables support transactions and foreign keys for the aggregate examples in related lessons.

### Java types should match SQL types

| SQL column | Common Java type | Notes |
|---|---|---|
| `INTEGER GENERATED ...` / `INT AUTO_INCREMENT` | `Integer` | 32-bit integer |
| `BIGINT GENERATED ...` / `BIGINT AUTO_INCREMENT` | `Long` | 64-bit integer |
| Application-assigned UUID | `UUID` | Created by application before insert, not an auto-increment numeric identity |

For a `BIGINT` key, use `Long`. For new entities, a **wrapper type** can represent `null` before insert. The primitive type `long` always has a default numeric value (0) and cannot express the "no ID yet" state as clearly as `Long null`.

## 4. Mapping IDs in a Spring Data JDBC entity

Spring Data JDBC uses the `@Id` annotation from `org.springframework.data.annotation.Id` to identify the primary key property. Example entity:

~~~java
package com.example.sales.order;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    protected Order() {
        // For Spring Data JDBC mapping mechanism.
    }

    public Order(Long customerId) {
        if (customerId == null || customerId <= 0) {
            throw new IllegalArgumentException("Invalid customer ID");
        }
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }
}
~~~

Key points:

- `@Table("shop_orders")` specifies the table storing the root.
- `@Id` identifies the ID column according to the entity mapping; the default column name is derived from the `id` property, or can be configured explicitly if the schema uses a different name.
- A new entity is created without setting `id`, so `id == null`.
- `Order` is an aggregate entity; when there is a list of child objects, the ID generated for the root is also used to link child rows.

The `@Id` annotation is **not** JPA's `@GeneratedValue` annotation. You do not need to add `@GeneratedValue(strategy = GenerationType.IDENTITY)` for Spring Data JDBC to retrieve the ID. Key generation lives in the schema, and Spring Data JDBC uses the dialect/JDBC strategy to retrieve the database-generated key.

## 5. Repository and return value after insert

Minimal repository:

~~~java
package com.example.sales.order;

import org.springframework.data.repository.CrudRepository;

public interface OrderRepository extends CrudRepository<Order, Long> {
}
~~~

When creating an order:

~~~java
Order draft = new Order(101L);

System.out.println(draft.getId()); // null

Order saved = orderRepository.save(draft);

System.out.println(saved.getId()); // Database-assigned ID, e.g., 501
~~~

**Use the object returned from `save`.** Spring Data JDBC may need to create a new instance when setting the ID value, especially with immutable entities or records. Therefore, do not rely on the assumption that the passed-in instance is always mutated in place.

Recommended style:

~~~java
Order saved = orderRepository.save(draft);
Long orderId = saved.getId();
~~~

Avoid writing:

~~~java
orderRepository.save(draft);
Long orderId = draft.getId(); // Do not assume draft has been assigned an ID.
~~~

For mutable classes, some mapping paths may update the passed-in instance; however, **the safe usage contract is to take the returned entity**. This also holds when working with immutable entities.

### Immutable entities or Java records

If using a record, the ID value cannot change after initialization. Spring Data JDBC creates a suitable instance with the generated ID and returns that instance:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public record Order(
    @Id Long id,
    Long customerId,
    String status
) {}
~~~

Creating and saving:

~~~java
Order draft = new Order(null, 101L, "DRAFT");
Order saved = orderRepository.save(draft);

Long generatedId = saved.id();
~~~

`draft.id()` remains `null`; `saved.id()` holds the generated ID. Retaining the returned object is essential with records and immutable aggregates.

## 6. How is the generated key retrieved?

Conceptually, the process follows these steps:

1. Spring Data JDBC determines a new entity needs to be inserted.
2. It builds an insert statement based on mapping; the database-generated ID column is handled according to the dialect's strategy.
3. The JDBC driver executes the statement and provides the generated key (or equivalent result depending on database capabilities).
4. Spring Data JDBC creates/updates the returned entity with the received ID value.
5. The repository returns the saved entity to the application service.

The application **does not need to run a SELECT query to guess the next ID**. Manually reading `MAX(id) + 1` is wrong under concurrent requests and can cause key collisions.

### PostgreSQL and RETURNING

PostgreSQL supports returning the ID directly in the insert result:

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT')
RETURNING id;
~~~

The returned result contains the ID of the newly inserted row. This is illustrative SQL syntax; when using Spring Data JDBC, let the framework and dialect handle generated key retrieval instead of manually writing `RETURNING` into basic repositories.

### MySQL and generated keys

The MySQL JDBC driver supports retrieving the generated key after insert. At the SQL client level, you can observe the newly assigned ID with:

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT');

SELECT LAST_INSERT_ID();
~~~

`LAST_INSERT_ID()` is scoped to the **connection/session**. If used manually in JDBC, the query must run on the same connection as the insert statement. Do not open a separate connection and call `LAST_INSERT_ID()` expecting the ID from the previous connection.

With Spring Data JDBC, you do not need to manually stitch these two SQL statements together. The framework invokes the JDBC driver/dialect generated-keys mechanism and returns the ID in the resulting entity.

### Generated keys are not predictable values

Example of two transactions inserting concurrently:

~~~text
Transaction A          Database identity          Transaction B
INSERT ---------------------> assigns 501
                                                   INSERT
                              assigns 502 <--------
~~~

Request order, commit order, and ID order may not match. The database safely manages key assignment; the application must never infer the next ID.

## 7. Saving an aggregate with child objects: how is the root ID used?

An Order can own multiple OrderItems. Spring Data JDBC maps collections using `@MappedCollection`:

~~~java
import java.util.ArrayList;
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_position")
    private List<OrderItem> items = new ArrayList<>();

    protected Order() {}

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public void addItem(String sku, int quantity) {
        if (sku == null || sku.isBlank() || quantity <= 0) {
            throw new IllegalArgumentException("Invalid item");
        }
        items.add(new OrderItem(sku, quantity));
    }

    public Long getId() {
        return id;
    }
}
~~~

Child object:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_items")
public class OrderItem {

    @Id
    private Long id;

    private String sku;
    private int quantity;

    protected OrderItem() {}

    OrderItem(String sku, int quantity) {
        this.sku = sku;
        this.quantity = quantity;
    }
}
~~~

Corresponding schema (PostgreSQL):

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES shop_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, line_position)
);
~~~

When calling `save` for a new Order:

1. The framework inserts the root row into `shop_orders`.
2. The database generates `shop_orders.id` and Spring Data JDBC retrieves the generated key.
3. The framework uses the received root ID to write `order_items.order_id` for the items.
4. The repository returns the saved Order; the root ID can be read from the returned entity.

~~~java
Order draft = new Order(101L);
draft.addItem("BOOK-01", 2);
draft.addItem("PEN-02", 1);

Order saved = orderRepository.save(draft);
Long orderId = saved.getId();
~~~

Therefore, when using an aggregate, you do not need to set `order_id` manually on each item before saving. The `@MappedCollection(idColumn = "order_id")` mapping expresses ownership and the FK column so Spring Data JDBC attaches items to the root.

## 8. Auto-increment IDs are not application-assigned IDs

There are two common strategies:

| Strategy | When is the ID present? | Example |
|---|---|---|
| Database-generated | After insert | PostgreSQL IDENTITY, MySQL AUTO_INCREMENT |
| Application-assigned | Before insert | UUID generated in Java, system-issued identifier code |

With auto-increment IDs, a new entity normally has `id = null`. This signals Spring Data JDBC to detect a new entity and perform an insert.

With application-assigned IDs, the entity already has an ID before `save` is called. Under the default new/existing detection strategy, a non-null ID can cause Spring Data JDBC to treat the entity as existing and follow the update path. If you want to use application-assigned IDs for new entities, configure an appropriate newness detection strategy, typically by implementing `Persistable<ID>` and providing `isNew()` (or using an appropriate version/newness mechanism).

Skeleton example for an entity using a self-assigned UUID:

~~~java
import java.util.UUID;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_orders")
public class ExternalOrder implements Persistable<UUID> {

    @Id
    private UUID id;

    private String status;

    @Transient
    private boolean newEntity = true;

    protected ExternalOrder() {}

    public ExternalOrder(String status) {
        this.id = UUID.randomUUID();
        this.status = status;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markPersisted() {
        this.newEntity = false;
    }
}
~~~

This is an illustrative skeleton for **application-generated IDs**; after the first save succeeds, the object's lifecycle must transition to a non-new state (for instance via appropriate application logic/callbacks). If using immutable entities or multiple object creation paths, design a consistent newness strategy rather than leaving the `newEntity` flag always true. When IDs are auto-generated by the database, this mechanism is unnecessary: leave the ID null and use generated keys.

## 9. What happens if you ignore the return value of save?

Suppose creation code does:

~~~java
Order order = new Order(101L);
orderRepository.save(order);

// Using order.getId() here is unsafe.
~~~

If the implementation returns a new instance to attach the generated ID, the `order` variable still points to the original object with `id = null`. When you need to use the ID to:

- return an HTTP response containing the newly created resource's ID;
- write logs or construct a URL to access the order;
- establish a relationship from another operation;
- pass the ID to the next processing step in the same use case;

retrieve it from the returned entity:

~~~java
Order saved = orderRepository.save(order);
return saved.getId();
~~~

In a REST controller, you can return `201 Created` along with the URI or response body containing the newly generated ID:

~~~java
@PostMapping("/orders")
public ResponseEntity<OrderCreatedResponse> create(
        @RequestBody CreateOrderRequest request) {
    Order order = new Order(request.customerId());
    Order saved = orderRepository.save(order);

    URI location = URI.create("/orders/" + saved.getId());
    return ResponseEntity.created(location)
        .body(new OrderCreatedResponse(saved.getId()));
}
~~~

The controller snippet assumes the corresponding DTOs and imports are defined. The key point is using `saved.getId()` for both the URI and the response.

## 10. Transactions, rollbacks, and gaps in ID sequences

Generated IDs are usually allocated during insert, before the transaction commits. If the transaction rolls back afterward, the data row does not exist, yet **the allocated ID value may not be reused**.

Example:

~~~text
INSERT Order -> database assigns ID 501
INSERT OrderItem -> constraint error
ROLLBACK transaction

Result:
- Order 501 is not committed
- ID 501 may be left as a gap
- Next insert may receive ID 502 or higher
~~~

This is normal behavior of identity/sequence mechanisms; it is not data loss or an ID increment bug. Do not:

- require contiguous IDs without gaps;
- use `MAX(id) + 1` to allocate IDs yourself;
- assume a larger ID always means an earlier commit in every scenario;
- treat an auto-increment ID as an invoice/receipt number that must be strictly sequential under business regulations.

If the business requires **gapless sequential document numbers** with specific numbering rules, design a dedicated numbering mechanism with appropriate transaction control and business rules. Do not substitute an identity column.

When an application service uses `@Transactional`, the ID may already appear in memory before the transaction commits. If the transaction later rolls back, never treat that ID as a durably persisted resource or emit external notifications as if the order were successfully created. For event integration, consider publishing events after commit or using a transactional outbox.

## 11. Verifying IDs with SQL

You can test directly against the database to understand the ID generation mechanism. Run each command group for the database system you use.

### PostgreSQL

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT')
RETURNING id;
~~~

The result returns the ID of the newly inserted row. Then use that ID to read it back:

~~~sql
SELECT id, customer_id, status
FROM shop_orders
ORDER BY id DESC
LIMIT 5;
~~~

### MySQL

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT');

SELECT LAST_INSERT_ID() AS generated_id;
~~~

Both MySQL statements must run on the same session/connection. Do not fetch `LAST_INSERT_ID()` from another SQL window if your tool creates a new connection per statement.

### Observing the stored ID in the table

~~~sql
SELECT id, customer_id, status
FROM shop_orders
WHERE id = :generated_id;
~~~

`:generated_id` is an illustrative placeholder; replace it with the received value or bind a parameter from the application.

## 12. Common errors and how to handle them

| Symptom | Possible cause | Resolution |
|---|---|---|
| Returned entity still has no ID | Code ignored the return value or entity is misconfigured | Assign the `save` result to a new variable and check `@Id` |
| Insert fails due to missing ID | DB column has no default/identity while application passes no ID | Fix the schema or choose an application-assigned ID strategy |
| Insert attempts to pass null ID unexpectedly | Mapping/schema or custom SQL does not use the right generated-key strategy | Check DDL, dialect, actual SQL statement, and driver |
| Save takes the update path instead of insert | ID already has a value so entity is treated as existing | For generated IDs, leave ID null; for assigned IDs, configure `Persistable.isNew()` or a newness strategy |
| Incompatible ID type | `BIGINT` column while code uses a type that is too small or mismatched | Use `Long` matching `BIGINT` |
| Parent record has ID but items are not linked | Wrong collection/FK mapping or items are outside aggregate mapping | Check `@MappedCollection(idColumn = ...)` and FK column name |
| Gaps in IDs | Rollback, deleted rows, concurrent ID allocation | Normal behavior; do not use identity as gapless numbers |
| Returned ID exists but immediate subsequent query does not find it | Transaction rolled back, reading wrong database/schema, or wrong transaction context | Check commit, URL, schema, and transaction |
| Duplicate business codes despite different IDs | Missing unique constraint on business key | Add a unique constraint and dedicated code generation rules |

For generated-key issues, a useful troubleshooting order is **schema → entity mapping → newness detection → JDBC driver/dialect → repository return value**. Never fix code by manually taking `MAX(id) + 1`.

## 13. Hands-on exercise

1. Create the `shop_orders` table with an auto-increment ID in PostgreSQL or MySQL.
2. Write an entity with `@Id Long id` and a repository extending `CrudRepository<Order, Long>`.
3. Create a new Order, confirming its ID before save is `null`.
4. Call `save`, keep the returned entity, and print its ID. Verify the ID exists in the table using SQL.
5. Use a Java record instead of a mutable class; demonstrate that the input object and the returned object can differ in ID value.
6. Create an Order with two OrderItems; save the aggregate and verify the items share the `order_id` FK matching the generated root ID.
7. Try rolling back a transaction after inserting the root; observe the ID gap and explain why it is not a bug.
8. Create an entity using an application-generated UUID. Compare how new entities are detected with an IDENTITY-based entity.

Quick verification example in a service:

~~~java
@Transactional
public Long createOrder(long customerId) {
    Order draft = new Order(customerId);

    if (draft.getId() != null) {
        throw new IllegalStateException("New order should not have an ID");
    }

    Order saved = orderRepository.save(draft);
    if (saved.getId() == null) {
        throw new IllegalStateException("Database did not return an ID");
    }

    return saved.getId();
}
~~~

This example illustrates the flow; real applications may use dedicated domain exceptions and handle database errors at the appropriate layer.

## 14. Key points to remember when working with generated IDs

The standard sequence with auto-increment IDs in Spring Data JDBC is:

~~~text
Database schema:
  id = IDENTITY / AUTO_INCREMENT

New Java entity:
  @Id Long id = null

Repository:
  Order saved = repository.save(newOrder)

Result:
  saved.getId() = generated key
~~~

**The database generates the ID; the JDBC driver/dialect retrieves the generated key; Spring Data JDBC populates the ID on the resulting entity; the application service uses the returned entity.** Keeping these four responsibilities clear prevents null ID bugs after insert, avoids racy manual key computation, and ensures child objects use the aggregate root's foreign key properly.
