# Quy tắc `USE_NULL`, `USE_EMPTY`, `@Embedded.Nullable` và `@Embedded.Empty`

Trong **Spring Data JDBC**, một value object được đánh dấu `@Embedded` sẽ được ánh xạ thành các cột nằm ngay trong bảng của aggregate root. Khi đọc một hàng, Spring Data cần quyết định: nếu **tất cả cột thuộc object nhúng đều có giá trị `NULL`**, thuộc tính Java nên nhận `null` hay một object đã được khởi tạo nhưng các thuộc tính bên trong đều rỗng?

Đây là mục đích của hai lựa chọn `USE_NULL` và `USE_EMPTY`:

- **`USE_NULL`**: nếu tất cả cột của object nhúng đều `NULL`, trả thuộc tính embedded là `null`.
- **`USE_EMPTY`**: nếu tất cả cột đều `NULL`, vẫn tạo một object embedded; các giá trị thành phần được ánh xạ từ các cột `NULL`.

Spring Data Relational cung cấp hai annotation lồng nhau để viết ngắn gọn hai lựa chọn này: `@Embedded.Nullable` tương ứng `USE_NULL`, còn `@Embedded.Empty` tương ứng `USE_EMPTY`. Chọn đúng chính sách giúp mô hình Java thể hiện chính xác ý nghĩa của dữ liệu rỗng, đặc biệt khi dùng value object bất biến như Java `record`.

## 1. Object nhúng được lưu như thế nào?

Giả sử một khách hàng có địa chỉ giao hàng. Địa chỉ là một nhóm giá trị thuộc khách hàng, không cần một ID riêng và không được quản lý như một aggregate độc lập.

```java
public record Address(
        String street,
        String city,
        String postalCode
) {}
```

Với `@Embedded`, các property của `Address` được trải thành các cột trong cùng bảng `customers`. Ví dụ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        @Embedded(prefix = "shipping_") Address shippingAddress
) {}
```

DDL minh họa:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20)
);
```

Ở đây `Address` **không tạo bảng riêng**. Các property của nó được ánh xạ thành `shipping_street`, `shipping_city`, `shipping_postal_code`. Prefix phân biệt các nhóm cột và tránh xung đột nếu aggregate có nhiều object cùng kiểu.

Khi ghi, một lệnh `INSERT` hoặc `UPDATE` vào `customers` mang các cột địa chỉ. Khi đọc, Spring Data lấy các cột đó và dựng `Address`. Quy tắc `USE_NULL`/`USE_EMPTY` quyết định object được dựng ra sao khi các cột embedded không có dữ liệu.

## 2. Vì sao cần quy tắc khi tất cả cột đều `NULL`?

Một object nhúng có thể được biểu diễn bằng nhiều cột. Database không có một cột duy nhất cho biết object đó “không tồn tại”; trạng thái thường được suy ra từ các giá trị cột thành phần.

Ví dụ hàng trong database:

| id | name | shipping_street | shipping_city | shipping_postal_code |
|---:|---|---|---|---|
| 1 | Lan | `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` |
| 2 | Minh | `NULL` | `NULL` | `NULL` |
| 3 | Hoa | `NULL` | `Da Nang` | `NULL` |

Với hàng 1, địa chỉ có dữ liệu rõ ràng. Với hàng 2, toàn bộ cột của địa chỉ đều `NULL`; Spring Data cần một quy tắc để quyết định `shippingAddress` là `null` hay một `Address` rỗng. Với hàng 3, có ít nhất một cột có giá trị, do đó Spring Data có dữ liệu để tạo object `Address` với `street = null`, `city = "Da Nang"`, `postalCode = null`.

**Khác biệt giữa hai chính sách chỉ xuất hiện khi tất cả cột của object nhúng đều `NULL`.** Nếu ít nhất một cột có giá trị, embedded object được tạo trong cả hai trường hợp; các property tương ứng với cột `NULL` vẫn nhận giá trị null theo mapping.

## 3. `USE_NULL`: tất cả cột `NULL` thì thuộc tính embedded là `null`

Khai báo tường minh:

```java
@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL, prefix = "shipping_")
Address shippingAddress
```

Hoặc dùng annotation ngắn gọn:

```java
@Embedded.Nullable(prefix = "shipping_")
Address shippingAddress
```

Hai cách trên biểu đạt cùng chính sách. `USE_NULL` cũng là lựa chọn mặc định của `@Embedded` khi không chỉ định `onEmpty`.

Kết quả đọc:

| `shipping_street` | `shipping_city` | `shipping_postal_code` | Giá trị Java theo `USE_NULL` |
|---|---|---|---|
| `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` | `Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")` |
| `NULL` | `NULL` | `NULL` | `null` |
| `NULL` | `Da Nang` | `NULL` | `Address(null, "Da Nang", null)` |

Chính sách này phù hợp khi **không có giá trị nào trong nhóm cột** mang nghĩa “không có địa chỉ”. Code nghiệp vụ có thể kiểm tra:

```java
if (customer.shippingAddress() == null) {
    // Khách hàng chưa cung cấp địa chỉ giao hàng.
}
```

Với `USE_NULL`, thuộc tính Java có thể không tồn tại dưới dạng object. Vì vậy, mọi đoạn code truy cập `shippingAddress.street()` cần xử lý trường hợp `shippingAddress == null`, hoặc ứng dụng phải bảo đảm dữ liệu/constructor không tạo trạng thái này.

## 4. `USE_EMPTY`: tất cả cột `NULL` vẫn tạo object embedded

Khai báo tường minh:

```java
@Embedded(onEmpty = Embedded.OnEmpty.USE_EMPTY, prefix = "shipping_")
Address shippingAddress
```

Hoặc dùng annotation ngắn gọn:

```java
@Embedded.Empty(prefix = "shipping_")
Address shippingAddress
```

Hai cách trên cùng yêu cầu Spring Data tạo embedded object ngay cả khi tất cả các cột của nó đều `NULL`.

Với `Address` là record gồm các kiểu tham chiếu `String`, kết quả có thể được biểu diễn như sau:

```java
new Address(null, null, null)
```

Bảng kết quả:

| `shipping_street` | `shipping_city` | `shipping_postal_code` | Giá trị Java theo `USE_EMPTY` |
|---|---|---|---|
| `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` | `Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")` |
| `NULL` | `NULL` | `NULL` | `Address(null, null, null)` |
| `NULL` | `Da Nang` | `NULL` | `Address(null, "Da Nang", null)` |

Khi đó, code có thể làm việc với object mà không cần kiểm tra null ở cấp `shippingAddress`:

```java
Address address = customer.shippingAddress();

if (address == null) {
    // Trường hợp này không được tạo ra bởi USE_EMPTY
    // khi toàn bộ cột embedded đều NULL.
}

if (address.street() == null) {
    // Object có tồn tại nhưng chưa có street.
}
```

Lưu ý: `USE_EMPTY` **không tự tạo dữ liệu mặc định** như chuỗi rỗng, thành phố mặc định hay mã bưu chính giả. Nó yêu cầu tạo object; các giá trị thành phần vẫn được lấy từ cột database. Nếu cột là `NULL`, property tương ứng vẫn có thể là `null`.

## 5. Đối chiếu bốn cách khai báo

| Khai báo | Chính sách khi tất cả cột embedded là `NULL` | Ý nghĩa |
|---|---|---|
| `@Embedded` | `USE_NULL` (mặc định) | Object được xem là không có |
| `@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL)` | `USE_NULL` | Viết rõ chính sách null |
| `@Embedded.Nullable` | `USE_NULL` | Shortcut annotation cho object có thể vắng mặt |
| `@Embedded(onEmpty = Embedded.OnEmpty.USE_EMPTY)` | `USE_EMPTY` | Tạo object dù mọi cột đều null |
| `@Embedded.Empty` | `USE_EMPTY` | Shortcut annotation cho object rỗng |

`@Embedded.Nullable` và `@Embedded.Empty` là các annotation lồng trong `Embedded` của Spring Data Relational. Chúng không phải annotation nullability tổng quát của Java hoặc Jakarta. Ví dụ, `org.springframework.lang.Nullable` hay `jakarta.annotation.Nullable` có mục đích biểu đạt nullability trong API; chúng không thay thế quy tắc `onEmpty` khi Spring Data dựng object nhúng.

Khi dùng một trong hai shortcut, không cần đặt thêm `@Embedded` thứ hai trên cùng property. Chọn **một cách khai báo** cho mỗi embedded property để chính sách dễ đọc và tránh metadata chồng chéo.

## 6. Ví dụ có hai object cùng kiểu nhưng chính sách khác nhau

Một khách hàng có thể có địa chỉ giao hàng tùy chọn và địa chỉ thanh toán mà ứng dụng muốn biểu diễn bằng object ngay cả khi chưa có dữ liệu:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        @Embedded.Nullable(prefix = "shipping_")
        Address shippingAddress,
        @Embedded.Empty(prefix = "billing_")
        Address billingAddress
) {}
```

DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20),
    billing_street VARCHAR(180),
    billing_city VARCHAR(100),
    billing_postal_code VARCHAR(20)
);
```

Giả sử một hàng có tất cả cột `shipping_*` và `billing_*` là `NULL`. Sau khi đọc:

```text
customer.shippingAddress() == null

customer.billingAddress()
    == Address(null, null, null)
```

Ví dụ này cho thấy **chính sách là thuộc tính của từng embedded property**, không phải một thiết lập toàn cục cho mọi object trong ứng dụng. Hai property cùng dùng kiểu `Address` nhưng có thể có ý nghĩa nghiệp vụ khác nhau.

## 7. Prefix và tên cột phải khớp DDL

Khi một bảng có nhiều embedded object, prefix giúp tạo ra các tên cột không trùng nhau:

```java
@Embedded.Nullable(prefix = "shipping_")
Address shippingAddress,

@Embedded.Empty(prefix = "billing_")
Address billingAddress
```

Theo naming strategy thông dụng, các property của `Address` sẽ được ánh xạ thành:

| Property trong `Address` | Embedded property | Tên cột |
|---|---|---|
| `street` | `shippingAddress` | `shipping_street` |
| `city` | `shippingAddress` | `shipping_city` |
| `postalCode` | `shippingAddress` | `shipping_postal_code` |
| `street` | `billingAddress` | `billing_street` |
| `city` | `billingAddress` | `billing_city` |
| `postalCode` | `billingAddress` | `billing_postal_code` |

Prefix trong annotation và tên cột trong DDL phải thống nhất. Nếu annotation dùng `billing_` nhưng bảng chỉ có `bill_street`, các câu SQL do Spring Data tạo sẽ tham chiếu tên cột không tồn tại.

Ví dụ SQL đọc có ý nghĩa tương đương:

```sql
SELECT id, name,
       shipping_street, shipping_city, shipping_postal_code,
       billing_street, billing_city, billing_postal_code
FROM customers
WHERE id = ?;
```

Embedded object không tạo thêm `JOIN` chỉ vì nó là một object Java. Các cột được đọc từ cùng hàng trong bảng root.

## 8. Quy tắc này tác động đến đọc dữ liệu, không phải một lệnh tạo object mặc định

`USE_NULL` và `USE_EMPTY` mô tả **cách ánh xạ một hàng database thành object Java** khi toàn bộ cột thuộc embedded property đều `NULL`. Chúng không phải:

- Cấu hình để database tự tạo giá trị mặc định.
- Lệnh `INSERT` một hàng vào bảng riêng cho object nhúng.
- Cơ chế thay thế `DEFAULT`, `NOT NULL` hoặc `CHECK` trong DDL.
- Cách đánh dấu tất cả property bên trong là chuỗi rỗng.
- Cơ chế tự gọi constructor nghiệp vụ để sinh địa chỉ mặc định.

Khi ghi một entity có embedded object, Spring Data JDBC vẫn phải tạo SQL theo metadata và giá trị của object. Nếu object là `null`, các cột tương ứng thường được ghi `NULL`; nếu object tồn tại nhưng các property đều null, các cột cũng có thể được ghi `NULL`. Khi đọc lại, chính sách `onEmpty` quyết định hai trạng thái lưu trữ giống nhau đó được biểu diễn thành `null` hay object rỗng.

Điều này tạo ra một hệ quả quan trọng: **database có thể không phân biệt được “embedded property là null” với “embedded object tồn tại nhưng tất cả thành phần đều null”** nếu cả hai trường hợp đều lưu thành một nhóm cột `NULL`. `USE_EMPTY` chọn cách diễn giải tất cả nhóm cột null thành object; `USE_NULL` chọn cách diễn giải thành `null`.

Nếu nghiệp vụ bắt buộc phân biệt hai trạng thái đó, cần thêm một cột chỉ thị riêng (ví dụ `has_shipping_address`) hoặc lưu một giá trị phân biệt khác. Chỉ đổi `USE_NULL` sang `USE_EMPTY` không thể khôi phục thông tin mà schema đã không lưu.

## 9. Ảnh hưởng của nullability và kiểu dữ liệu bên trong

Với `USE_EMPTY`, Spring Data vẫn phải ánh xạ giá trị cột `NULL` vào từng property. Vì thế, kiểu Java của thành phần embedded rất quan trọng.

Nên dùng kiểu tham chiếu/wrapper nếu cột có thể null:

```java
public record Address(
        String street,
        String city,
        Integer buildingNumber
) {}
```

Trong ví dụ này, `street`, `city`, `buildingNumber` có thể nhận `null`. Nếu dùng primitive như `int`, Java không có giá trị `null`; việc ánh xạ cột `NULL` sang primitive có thể tạo giá trị mặc định hoặc gây vấn đề tùy đường khởi tạo/conversion. Không nên dựa vào giá trị mặc định `0` để biểu diễn “không biết số nhà” nếu nghiệp vụ cần phân biệt rõ. Dùng `Integer` thường diễn đạt trường hợp thiếu dữ liệu tốt hơn.

Nếu cột embedded khai báo `NOT NULL`, `USE_EMPTY` không tự làm cho thao tác ghi hợp lệ. Ví dụ:

```sql
shipping_city VARCHAR(100) NOT NULL
```

Một `Address(null, null, null)` vẫn có thể khiến lệnh ghi bị database từ chối do `shipping_city` là `NULL`. Chính sách tạo object khi đọc không thay đổi constraint khi ghi.

Các value object có invariant mạnh (ví dụ `Money` bắt buộc có amount và currency, hoặc `Address` bắt buộc có country) cần được thiết kế cùng nullability của schema. Nếu mọi cột đều null nhưng constructor không chấp nhận giá trị null, `USE_EMPTY` không thể tự tạo một object nghiệp vụ hợp lệ. Khi ấy nên chọn `USE_NULL`, dùng object mặc định hợp lệ theo domain, hoặc thay đổi mô hình lưu trữ để biểu diễn rõ trạng thái.

## 10. Chọn `USE_NULL` hay `USE_EMPTY` theo ý nghĩa nghiệp vụ

Không nên chọn chỉ vì muốn giảm số lần kiểm tra `null` trong code. Hãy xác định ý nghĩa của nhóm cột khi toàn bộ đều trống:

| Trường hợp nghiệp vụ | Chính sách thường phù hợp | Lý do |
|---|---|---|
| Địa chỉ giao hàng chưa được cung cấp | `USE_NULL` | Không có địa chỉ là trạng thái vắng mặt rõ ràng |
| Thông tin tùy chọn, ví dụ ghi chú phụ | `USE_NULL` | Không có nội dung thì không cần object |
| Nhóm cài đặt luôn được xem là một phần của entity, dù chưa có giá trị nào | `USE_EMPTY` | Caller có thể thao tác với object cài đặt rỗng |
| Value object có các default hợp lệ và constructor tạo được trạng thái rỗng | Có thể dùng `USE_EMPTY` | Object luôn hiện diện theo mô hình domain |
| Value object bắt buộc có một số field để hợp lệ | Thường `USE_NULL` hoặc thay đổi schema | Object rỗng không đáp ứng invariant |

Ví dụ, một `Preferences` có thể cho phép tất cả lựa chọn chưa được thiết lập:

```java
public record Preferences(
        Boolean emailNotifications,
        Boolean smsNotifications
) {}
```

Nếu ứng dụng muốn mọi khách hàng luôn có một object preferences để đọc và cập nhật từng lựa chọn, `USE_EMPTY` có thể phù hợp. Wrapper `Boolean` biểu diễn trạng thái chưa thiết lập rõ ràng; primitive `boolean` sẽ ép giá trị về `false` và làm mất khác biệt giữa “chưa chọn” và “đã tắt”.

Ngược lại, với `Address`, không có dữ liệu địa chỉ thường có nghĩa khách hàng chưa khai báo địa chỉ; `USE_NULL` giúp code thể hiện điều đó trực tiếp.

## 11. So sánh kết quả bằng ví dụ đọc cụ thể

Giả sử query trả về ba hàng:

```sql
SELECT id, shipping_street, shipping_city, shipping_postal_code
FROM customers
ORDER BY id;
```

Dữ liệu:

```text
id=1: "12 Nguyen Hue", "Ho Chi Minh City", "700000"
id=2: NULL, NULL, NULL
id=3: NULL, "Da Nang", NULL
```

Kết quả theo `USE_NULL`:

```text
Customer 1 -> Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")
Customer 2 -> null
Customer 3 -> Address(null, "Da Nang", null)
```

Kết quả theo `USE_EMPTY`:

```text
Customer 1 -> Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")
Customer 2 -> Address(null, null, null)
Customer 3 -> Address(null, "Da Nang", null)
```

Hàng 1 và 3 giống nhau giữa hai chính sách. Chỉ hàng 2 khác nhau vì **toàn bộ cột của embedded object đều null**.

## 12. Kiểm tra SQL và mapping khi debug

Khi object nhúng không được dựng như kỳ vọng, kiểm tra lần lượt:

1. **Annotation trên property**: dùng `@Embedded`, `@Embedded.Nullable` hay `@Embedded.Empty`? Có chỉ định `onEmpty` rõ ràng không?
2. **Prefix**: `shipping_`/`billing_` có khớp tên cột vật lý không?
3. **Các cột thuộc object**: tất cả cột đều null hay có ít nhất một cột có giá trị? Chính điều kiện này quyết định nhánh `onEmpty`.
4. **Kiểu Java**: property là wrapper/reference hay primitive? Constructor/record có chấp nhận các giá trị null không?
5. **DDL**: cột có cho phép null không? Có default, constraint hoặc migration nào thay đổi giá trị trước khi đọc không?
6. **SQL runtime**: câu `SELECT` có lấy đủ cột embedded không? Query tùy chỉnh có bỏ sót một cột cần thiết không?

Có thể bật log Spring JDBC trong môi trường phát triển:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Log giúp nhìn câu SQL và tham số bind. Với truy vấn tùy chỉnh, hãy chắc chắn danh sách `SELECT` có đầy đủ cột cần thiết cho object embedded. Nếu chỉ lấy `id`, `name` nhưng lại yêu cầu dựng `Address`, kết quả mapping không thể có đủ dữ liệu địa chỉ.

Khi dùng `@Query`, tên cột là tên vật lý trong database. Ví dụ:

```java
@Query("""
    SELECT id, name,
           shipping_street, shipping_city, shipping_postal_code
    FROM customers
    WHERE id = :id
    """)
Optional<Customer> findCustomer(@Param("id") Long id);
```

SQL này dùng đúng các cột đã khai báo trong DDL. `@Embedded.Nullable` hay `@Embedded.Empty` không tự thêm cột vào câu query viết tay.

## 13. Các nhầm lẫn thường gặp

| Nhầm lẫn | Cách hiểu đúng |
|---|---|
| `USE_EMPTY` tạo chuỗi rỗng cho mọi field. | Nó tạo object embedded; từng field vẫn nhận giá trị từ cột, kể cả `null`. |
| `USE_NULL` làm tất cả property con thành null trong mọi trường hợp. | Nó chỉ trả embedded property là null khi **tất cả cột của object** đều null. Nếu một cột có dữ liệu, object được tạo. |
| `@Embedded.Empty` tạo bảng riêng. | Embedded object được trải thành cột trong bảng của root. |
| `@Embedded.Nullable` là `@Nullable` tổng quát. | Đây là shortcut của Spring Data Relational cho chính sách `USE_NULL` của embedded mapping. |
| `USE_EMPTY` làm DDL chấp nhận null. | DDL vẫn quyết định `NULL`/`NOT NULL`; chính sách chỉ ảnh hưởng quá trình đọc và dựng object. |
| Hai chính sách khác nhau trong mọi hàng. | Chúng chỉ khác khi tất cả cột embedded đều `NULL`. |
| Object rỗng và object null luôn được phân biệt khi lưu. | Nếu cả hai đều ghi ra toàn cột null, database không giữ được khác biệt nếu không có cột chỉ thị riêng. |
| Có thể dùng primitive cho mọi property vì `USE_EMPTY` luôn tạo object. | Property vẫn có thể nhận null từ cột; chọn kiểu Java phù hợp với nullability và invariant. |

## 14. Bài thực hành tự quan sát

Với bảng `customers` ở phần đầu, có thể thực hành theo các bước:

1. Tạo ba hàng: một hàng có địa chỉ đầy đủ, một hàng có tất cả cột địa chỉ `NULL`, một hàng chỉ có `shipping_city`.
2. Ánh xạ `shippingAddress` bằng `@Embedded.Nullable(prefix = "shipping_")`, đọc cả ba hàng và quan sát hàng thứ hai nhận `null`.
3. Đổi sang `@Embedded.Empty(prefix = "shipping_")`, đọc lại cùng dữ liệu và quan sát hàng thứ hai nhận `Address(null, null, null)`.
4. Giữ `USE_EMPTY`, chỉ đặt `shipping_city = 'Da Nang'` cho hàng thứ ba; quan sát kết quả không khác `USE_NULL` ở hàng có ít nhất một cột khác null.
5. Thử thêm một embedded property thứ hai với prefix `billing_` và khai báo chính sách khác; kiểm tra DDL và SQL có đầy đủ hai nhóm cột.
6. Thử dùng một property primitive trong embedded object với cột nullable để hiểu vì sao kiểu wrapper thường phù hợp hơn cho dữ liệu có thể vắng mặt.

Khi hoàn thành, ghi nhận kết quả theo ba lớp: **các cột database**, **annotation/prefix trên property**, và **object Java sau khi đọc**. Không cần thay đổi dữ liệu để ép một chính sách cho ra kết quả của chính sách kia; cùng một hàng có thể được diễn giải khác nhau chỉ bằng metadata `onEmpty`.

## 15. Nguyên tắc lựa chọn

`USE_NULL` phù hợp khi một nhóm cột hoàn toàn rỗng có nghĩa **không có object**. `USE_EMPTY` phù hợp khi mô hình muốn **object luôn hiện diện**, ngay cả khi các thành phần của nó chưa được thiết lập. `@Embedded.Nullable` và `@Embedded.Empty` giúp thể hiện hai lựa chọn đó ngắn gọn ngay tại property.

Khi thiết kế, hãy đối chiếu chính sách với ý nghĩa nghiệp vụ, nullability của cột, kiểu Java và constructor của value object. Đặc biệt, nhớ rằng embedded object được lưu dưới dạng các cột của aggregate root: chính sách `onEmpty` chỉ quyết định cách Spring Data JDBC dựng object khi đọc một hàng có toàn bộ cột embedded là `NULL`; nó không thay thế DDL, không tự sinh giá trị mặc định và không tạo một bảng quan hệ riêng.
