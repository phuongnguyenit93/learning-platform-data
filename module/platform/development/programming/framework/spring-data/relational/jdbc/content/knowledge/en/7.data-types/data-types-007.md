# Arrays, Binary Data, and Database Support Limitations

Java applications frequently need to store data beyond strings, numbers, or dates: lists of product tags, sets of optional codes, thumbnails, attachments, or binary payloads. Relational databases offer multiple ways to represent these values, yet support varies across PostgreSQL, MySQL, Oracle, SQL Server, SQLite, and H2.

In Spring Data JDBC, you must distinguish three things: **the Java data type**, **the SQL column type**, and **the conversion capability of the JDBC driver/framework**. A Java type may be valid yet lack a matching default mapping across every database. This lesson uses a storefront example to explain SQL arrays, binary data, how to choose a storage model, and how to handle cases where Spring Data JDBC does not map vendor-specific types directly.

## 1. Start from the Data Requirements

Suppose a product catalog contains the following information:

- Product name and selling price: ordinary scalar data.
- A tag list such as `["keyboard", "office", "wireless"]`: a set of simple values that can be represented via SQL arrays, JSON, or a join table.
- Thumbnail images or document content: binary data, typically stored in a binary/LOB column or in file/object storage.

Do not pick a SQL type simply because Java already has `String[]` or `byte[]`. Determine how the application needs to query and update the data:

| Requirement | Design Question |
| --- | --- |
| Store a tag list | Do you need to search products by a single tag? Do tags need to reference a canonical catalog? |
| Store multiple optional codes | Are elements ordered? Are duplicates allowed? Do you need joins with other tables? |
| Store images/files | What is the maximum size? Is streaming needed? Are they always loaded alongside product details? |
| Share data across multiple DBs | Do the DBMSs share the same data types and JDBC behavior? |
| Update individual elements | Do you need to add/remove a single tag without rewriting the entire list? |

These answers determine whether to use SQL ARRAY, JSON, a child table, a binary column, or a separate file storage system.

## 2. Java Arrays and SQL Arrays Are Two Different Concepts

Java has arrays such as `String[]`, `Long[]`, and `int[]`. Some DBMSs provide SQL-level array types—for instance, PostgreSQL has `text[]` and `integer[]`. However, **not every relational database has an equivalent ARRAY column type**.

PostgreSQL example:

```sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[]
);

INSERT INTO catalog_product (name, tags)
VALUES ('Mechanical Keyboard', ARRAY['keyboard', 'office', 'wireless']);

SELECT id, name, tags
FROM catalog_product
WHERE 'wireless' = ANY(tags);
```

Here `tags` is a column of SQL ARRAY type containing multiple text elements. It remains **one column of one row**, not a separate table. The `ANY(tags)` query uses PostgreSQL syntax, not portable SQL across all databases.

The same information can be represented in Java:

```java
public record ProductTags(
    Long productId,
    String[] tags
) {}
```

However, merely declaring `String[]` does not guarantee that Spring Data JDBC will automatically read/write an ARRAY column on every driver. Conversion depends on support in your Spring Data Relational version, the JDBC type returned by the driver, and the active database dialect. For vendor-specific SQL types, verify on the actual target database; when necessary, use custom conversions or a repository method running explicit JDBC.

### Do Not Confuse Child Collections with an ARRAY Column

In Spring Data JDBC, a collection inside an aggregate carries meaning regarding **aggregate boundaries and data lifecycle**. For example:

```java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
    List<OrderLine> lines
) {}
```

`lines` represents order line items belonging to the order aggregate; each element can be stored as a row in the child table `order_line`. This is not a directive to pack the entire list into a SQL ARRAY column.

Comparison:

| Model | Storage Approach | When Appropriate |
| --- | --- | --- |
| SQL ARRAY | Multiple values of the same type stored in one column of one row. | Small scalar lists, typically read/written together, with strong DB support. |
| Aggregate child collection | Each element is stored in a child table per aggregate mapping. | Elements are structured, have their own attributes, or share a lifecycle tied to the root. |
| Standalone join/link table | Each element/relationship is a row with its own keys. | Needs independent searching, constraints, joins, or updates. |
| JSON | A structured document stored in a single column. | Flexible data with few per-element relational constraints. |

If tags require frequent filtering, aggregation, constraints, or joins, a normalized join table is usually easier to manage. If they are just a few scalar labels read together with the product and the database supports ARRAY well, an SQL array may fit.

## 3. How Does JDBC Represent SQL ARRAY?

JDBC defines `java.sql.Array` and methods such as `Connection.createArrayOf(...)`, `PreparedStatement.setArray(...)`, and `ResultSet.getArray(...)`. However, exact support depends on the driver and database.

PostgreSQL example with Spring `JdbcTemplate`:

```java
import java.sql.Array;
import java.sql.PreparedStatement;
import java.util.Arrays;

import org.springframework.jdbc.core.ConnectionCallback;
import org.springframework.jdbc.core.JdbcTemplate;

public class ProductTagJdbcRepository {

    private final JdbcTemplate jdbcTemplate;

    public ProductTagJdbcRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public void replaceTags(long productId, String[] tags) {
        jdbcTemplate.execute((ConnectionCallback<Void>) connection -> {
            Array sqlArray = connection.createArrayOf("text", tags);

            try (PreparedStatement statement = connection.prepareStatement(
                    "UPDATE catalog_product SET tags = ? WHERE id = ?")) {
                statement.setArray(1, sqlArray);
                statement.setLong(2, productId);
                statement.executeUpdate();
            } finally {
                sqlArray.free();
            }

            return null;
        });
    }
}
```

Key points to understand:

- `createArrayOf("text", tags)` asks the driver to create a SQL ARRAY with text elements. The element type name is database/driver-specific; this example targets PostgreSQL.
- `setArray(...)` binds the JDBC ARRAY object as a parameter instead of concatenating tag strings into SQL.
- `JdbcTemplate` manages acquiring/releasing the connection via Spring's mechanism; if the method runs within an active Spring transaction, the operation participates in that transaction.
- `Array.free()` releases the JDBC resources held by the array object after use.

This is explicit JDBC usage illustrating driver capabilities. It is **not** an example showing that every `String[]` property in a Spring Data JDBC entity maps this way automatically. If you want to integrate ARRAY types into an aggregate repository, verify custom conversion/mapping for your Spring Data version and test both reads and writes. Another approach is keeping ARRAY operations inside a custom repository fragment using `JdbcTemplate`, with clear conventions around that field.

Reading an ARRAY via JDBC also requires resource cleanup:

```java
Array sqlArray = resultSet.getArray("tags");
try {
    String[] tags = sqlArray == null
        ? null
        : (String[]) sqlArray.getArray();
    // Convert tags to domain type here.
} finally {
    if (sqlArray != null) {
        sqlArray.free();
    }
}
```

The exact Java type returned from `getArray()` depends on the driver. Do not cast blindly in multi-database code; verify actual output and write an adapter/converter into the application's normalized type.

## 4. Alternatives to SQL ARRAY

If the database lacks native ARRAY support or flexible querying is needed, several alternative models exist.

### 4.1. Child Table or Join Table

For a searchable and manageable tag list, you can design:

```sql
CREATE TABLE product_tag (
    product_id BIGINT NOT NULL,
    tag VARCHAR(80) NOT NULL,
    PRIMARY KEY (product_id, tag),
    FOREIGN KEY (product_id) REFERENCES catalog_product(id)
);

CREATE INDEX idx_product_tag_tag
    ON product_tag(tag);
```

Advantages:

- Broadly supported across relational DBMSs.
- Supports indexing individual tags, joins, counting, and efficient filtering.
- Supports unique constraints and foreign keys.
- Allows updating a single element without rewriting the entire list.

The drawback is extra rows, joins, and write operations. If tags are part of the Product aggregate, model them as a child collection persisted through the root; if tags are independent or shared entities, consider an appropriate join table or separate aggregate.

### 4.2. JSON

Some databases support JSON or binary JSON types. PostgreSQL example:

```sql
CREATE TABLE catalog_product_json (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags JSONB NOT NULL DEFAULT '[]'::jsonb
);

SELECT id, name
FROM catalog_product_json
WHERE tags @> '["wireless"]'::jsonb;
```

JSON is useful when structure evolves or attributes are flexible. However, JSON is not equivalent to ARRAY:

- JSON can contain objects, arrays, strings, numbers, booleans, and null.
- Indexing, querying, and validating JSON vary by database.
- Per-element relational constraints are harder to express than in normalized tables.
- Requires application-level JSON schema conventions so records do not drift into arbitrary shapes.

MySQL has a JSON type; PostgreSQL has `json/jsonb`; SQL Server and Oracle offer JSON capabilities with version-specific syntax; SQLite typically relies on JSON functions/extensions and text storage. Do not assume a JSON query behaves identically across all DBMSs.

### 4.3. Delimited Strings

You could store `"keyboard,office,wireless"` in a text column, though this is usually poor for queryable data:

- Tags containing the delimiter require escaping.
- Hard to distinguish empty elements, nulls, and whitespace strings.
- Indexing individual elements is difficult and query-dependent.
- No per-element foreign keys or unique constraints.

Only choose delimited strings for very simple data that never needs per-element querying and follows a strictly controlled format. For most business cases, a child table or JSON is cleaner.

## 5. Binary Data in Java and SQL

Binary data is a sequence of bytes, such as images, PDFs, attachments, encrypted payloads, or hashes. Java typically uses `byte[]` for payloads loaded into memory.

Example of a record storing metadata and small image content:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("product_asset")
public record ProductAsset(
    @Id Long id,
    Long productId,
    String fileName,
    String contentType,
    byte[] content
) {}
```

`byte[]` differs semantically from `String[]`: it is a byte sequence acting as **a single binary value**, not a collection of child records. Spring Data JDBC and the driver can map this binary scalar into a corresponding binary column. Still, the exact SQL type depends on the database and must be verified against the actual dialect/driver.

### Binary Column Types by DBMS

| Database | Common Type | Notes |
| --- | --- | --- |
| PostgreSQL | `BYTEA` | Stores a byte sequence in one value; JDBC driver supports `byte[]`. |
| MySQL | `BLOB`, `MEDIUMBLOB`, `LONGBLOB` | Choose size limits based on needs; each variant has different capacity limits. |
| Oracle | `BLOB` | Large Object; JDBC driver provides LOB APIs. |
| SQL Server | `VARBINARY(n)`, `VARBINARY(MAX)` | `MAX` handles values exceeding normal length limits. |
| SQLite | `BLOB` | SQLite stores binary data under the BLOB storage class. |
| H2 | `BLOB` | Handy for demos/tests, yet does not reflect every production database behavior. |

PostgreSQL DDL:

```sql
CREATE TABLE product_asset (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id BIGINT NOT NULL,
    file_name VARCHAR(255) NOT NULL,
    content_type VARCHAR(120) NOT NULL,
    content BYTEA NOT NULL
);
```

MySQL might use `LONGBLOB` for large files; SQL Server commonly uses `VARBINARY(MAX)`; Oracle uses `BLOB`. Choose a type matching your size limits and DBMS backup/replication policies.

### Writing and Reading via JDBC

```java
jdbcTemplate.update(
    "INSERT INTO product_asset " +
    "(product_id, file_name, content_type, content) " +
    "VALUES (?, ?, ?, ?)",
    productId,
    fileName,
    contentType,
    contentBytes
);
```

`JdbcTemplate` binds `byte[]` to the JDBC parameter. Reading small/medium values:

```java
byte[] content = jdbcTemplate.queryForObject(
    "SELECT content FROM product_asset WHERE id = ?",
    (resultSet, rowNum) -> resultSet.getBytes("content"),
    assetId
);
```

With Spring Data JDBC, a `byte[]` property in an aggregate can be mapped if the mapping/driver supports the corresponding binary type. Test inserts, selects, and updates against the target database; do not rely solely on H2 as proof that every other driver behaves identically.

## 6. BLOB/LOB and Large Data Sizes

The term LOB (Large Object) refers to large data, encompassing binary large objects (BLOB) and character large objects (CLOB). DBMSs differ in APIs, size limits, physical storage, and streaming behavior.

Key distinctions:

- `byte[]` typically loads the entire payload into Java memory.
- `java.sql.Blob` can represent a LOB tied to a connection/transaction; locator lifetime depends on the driver and connection.
- JDBC streaming can avoid holding the entire content on the heap, yet requires managing streams, connections, and transactions across the proper lifecycle.
- Storing large data directly in the database increases backup size, replication volume, and I/O load; in exchange, the data participates in database transactions and unified backups.

For small images, avatars, or payloads of a few KB/MB with modest read frequency, `byte[]` can be straightforward. For videos, large files, or assets downloaded independently of order details, consider object storage / file storage and store only metadata + an object key in the database.

Metadata example:

```java
@Table("product_asset")
public record ProductAsset(
    @Id Long id,
    Long productId,
    String fileName,
    String contentType,
    Long sizeInBytes,
    String storageKey
) {}
```

When choosing object storage, the application must handle access control, encryption, expiring URLs, orphan file cleanup, and consistency between database operations and upload/delete calls. A SQL transaction does not automatically roll back a file uploaded to an external service; design compensating workflows or intermediate states.

### Why Shouldn't You Load Every File Alongside the Aggregate?

Suppose a product listing screen only needs the name, price, and thumbnail URL. If every `Product` load pulls a large BLOB, the application wastes bandwidth, heap memory, and query time on unused data.

Separate metadata and binary content into distinct aggregates/tables, or use query projections selecting only needed columns. For large files, provide a dedicated streaming path. Never place large payloads inside an aggregate solely because they can be represented as a Java field.

## 7. Varying Support Across Databases

The table below serves as a design guide; actual support depends on the database version, JDBC driver, dialect, and specific SQL type.

| Database | Native Array Column | Binary | Common Approach Without ARRAY |
| --- | --- | --- | --- |
| PostgreSQL | Yes, e.g., `text[]`, `integer[]`. | `BYTEA`, plus Large Object API. | ARRAY, join table, or JSONB as needed. |
| MySQL | No general SQL ARRAY column type equivalent to PostgreSQL. | `BLOB` family. | Join table or JSON. |
| Oracle | Has SQL collection types like VARRAY/nested table; mapping typically uses Oracle JDBC. | `BLOB`. | Relational table or collection type/JSON per architecture. |
| SQL Server | No general native ARRAY column. Table-valued parameters pass datasets into routines, not as stored column types. | `VARBINARY(MAX)`. | Join table, table-valued parameter for inputs, or JSON. |
| SQLite | No native ARRAY column. | `BLOB`. | Join table or controlled JSON/text. |
| H2 | Has database-level ARRAY support, though not guaranteed equivalent to other vendors. | `BLOB`. | Useful for basic tests; still test against target database. |

### Key Limitations to Note

**PostgreSQL.** Native arrays are convenient for homogeneous scalar sets and come with dedicated operators and functions. The driver supports JDBC ARRAY, though element type names, retrieving Java arrays, and certain element types may require explicit handling. PostgreSQL arrays do not provide per-element foreign key constraints like normalized tables do.

**MySQL.** Use JSON when a column needs a flexible list, or a child table when you need joins, per-element indexing, and foreign keys. MySQL JSON has its own functions and version-dependent indexing limits; do not treat it as a native SQL ARRAY.

**Oracle.** Supports SQL collection types, yet defining types, binding/reading collections, and converting to Java typically tie into Oracle JDBC APIs and schema-defined type names. Integration testing on real Oracle is required; do not extrapolate from H2 tests.

**SQL Server.** Table-valued parameters can pass multiple rows into a stored procedure/function, but they are not an ARRAY column type stored per row. For persisting lists long-term, join tables or JSON are usually more suitable.

**SQLite.** Has no ARRAY column. Use join tables or JSON/text based on querying needs and data-integrity requirements. `BLOB` stores raw bytes.

**H2.** H2 is useful for fast tests, yet ARRAY types, syntax, metadata, and driver behavior can differ from PostgreSQL/MySQL/Oracle/SQL Server. Even H2's compatibility modes do not replace testing against the real engine.

## 8. How Does Spring Data JDBC Handle These Types?

Spring Data JDBC focuses on aggregate mapping and uses Spring JDBC / the driver to exchange data. It has a simple-type/conversion system and supports custom conversions; however, you cannot assume every database-specific type is supported automatically.

Situations can be categorized as follows:

| Java Property Type | Recommended Handling |
| --- | --- |
| `byte[]` | Typically a binary scalar; match against BLOB/BYTEA/VARBINARY columns and driver. |
| `String[]` or `Integer[]` | Do not assume automatic compatibility with native ARRAY; verify mapping and driver. |
| `List<OrderLine>` | Child collection within an aggregate; use a child table and mapping such as `@MappedCollection`. |
| `List<String>` | Clarify whether this is a collection stored as child rows or scalar/ARRAY/JSON data; never leave semantics ambiguous. |
| Custom value object | Register custom converters or convert inside a custom repository. |
| `java.sql.Array`/`Blob` | Connection-bound JDBC resource types; never hold locators after the connection closes. |

### Custom Conversion and Custom Repositories

When you want to use native ARRAYs in the domain model, there are two general approaches:

1. **Custom conversion:** define how to convert between the Java domain type and a type Spring Data JDBC / the driver can bind/read. Register the conversion using the extension point supported by your Spring Data JDBC version. Verify both read and write directions and actual JDBC/SQL types.
2. **Custom repository / JdbcTemplate:** isolate vendor-specific SQL in a dedicated adapter using `Connection.createArrayOf`, `PreparedStatement.setArray`, and `ResultSet.getArray`. This clarifies database-specific boundaries and ensures control over JDBC resources.

Do not write a single shared converter across all databases if each driver requires different APIs. You can define a domain interface such as `ProductTagStore` and provide separate implementations for PostgreSQL, MySQL, or other databases.

Example interface boundary:

```java
public interface ProductTagStore {
    void replaceTags(long productId, List<String> tags);
    List<String> findTags(long productId);
}
```

A PostgreSQL implementation can use SQL ARRAY; a MySQL implementation can use JSON or a child table. The service calls a uniform interface while JDBC details stay inside the corresponding adapter.

### Do Not Mix Two Persistence Models for the Same Property

If an aggregate repository and custom JDBC both write to the same column, define clearly which one owns updates. For example, if `PurchaseOrderRepository.save(order)` does not understand a native ARRAY field while a custom DAO modifies that column, a subsequent aggregate save could fail to preserve the value as expected depending on mapping/conversion. Assign clear ownership, write round-trip tests, and avoid uncoordinated dual write paths.

## 9. Choosing a Model by Business Criteria

| Criterion | SQL ARRAY | Child/Join Table | JSON | Binary/LOB |
| --- | --- | --- | --- | --- |
| Multiple scalar elements of same type | Good fit if DB supports it. | Good fit. | Possible, though more flexible than needed. | Not applicable. |
| Per-element search/indexing | Vendor-specific; can work well on supporting DBs. | Excellent fit with relational indexes/SQL. | Possible, engine-dependent. | Not applicable. |
| Per-element FK | Usually unsuitable. | Good fit. | Inconvenient. | Not applicable. |
| Add/remove single element | May require rewriting array or using custom operators. | Update a single row. | Possible via vendor-specific JSON functions. | Not applicable. |
| Multi-DB portability | Low to medium. | High. | Medium, varies in syntax/capabilities. | Binary types are common, though names/limits differ. |
| Very large data | Unsuitable for file payloads. | Unsuitable for large files. | Usually suboptimal for binary. | Fits if DB-managed; consider streaming/object storage. |

Memorable selection rules:

- Lists of elements with identity, relationships, or per-element querying: use a child table / join table.
- Small scalar lists that rarely change, on a DB with solid native ARRAY support where vendor coupling is acceptable: consider SQL ARRAY.
- Flexible nested structures needing few per-node foreign keys: consider JSON.
- Small/medium byte payloads requiring transactional consistency with other data: consider a binary column.
- Large files downloaded independently or needing CDN delivery: consider object storage and store metadata/keys in the database.

## 10. Testing on Real Databases

Testing with H2 is helpful for verifying basic repository flows, but it is not enough to prove SQL ARRAY or LOB behavior matches production databases.

An appropriate testing strategy:

1. **Domain unit tests:** verify duplicate tags, empty lists, nulls, payload sizes, and business validation.
2. **Integration tests on the target engine:** run PostgreSQL if production uses PostgreSQL; likewise for MySQL, Oracle, or SQL Server.
3. **Round-trip tests:** write and read back ARRAY, binary, JSON, or LOB values; verify exact values and null/empty semantics.
4. **Boundary tests:** test empty arrays, null elements (if allowed), Unicode strings, empty byte arrays, near-limit payloads, and oversized payloads.
5. **Resource tests:** ensure `java.sql.Array.free()`/streams/LOBs are released properly and connections return to the pool.
6. **Transaction tests:** trigger an error after a write operation to verify rollback of data within the same datasource/transaction.
7. **Portability tests:** if supporting multiple DBs, run the same contract test suite on each engine rather than relying solely on H2 compatibility mode.

Testcontainers can spin up real databases in integration tests. The goal is not only to check that SQL runs, but also to verify which Java types the driver returns, what SQL the dialect generates, and real capacity limits.

## 11. Combined Product Example

Suppose a product has a list of tags and a small preview image. PostgreSQL can use ARRAY for tags and BYTEA for the image:

```sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[],
    preview_image BYTEA
);
```

At the Java layer, metadata and binary content can be represented as:

```java
public record ProductAssetView(
    Long productId,
    String name,
    String[] tags,
    byte[] previewImage
) {}
```

This is an illustrative return DTO, not a guarantee that Spring Data JDBC automatically maps all fields cleanly across every driver. In a PostgreSQL implementation, an adapter can use JDBC ARRAY for `tags` and binary binding for `preview_image`. When switching to MySQL, tags can move to JSON or a `product_tag` table, and the image column switches to the BLOB family. Domain/services keep a stable contract for tags and images while adapters handle storage specifics.

If tags require heavy filtering, moving to a `product_tag` table can make more sense even on PostgreSQL. If preview images grow large or many screens do not need the image, storing files outside the database and retaining only an object key reduces query overhead.

- Why does `String[]` in Java not mean every database can store it directly in an ARRAY column?
- How do `java.sql.Array` and `byte[]` differ in purpose and lifecycle?
- Why should `List<OrderLine>` in an aggregate not be interpreted as an SQL ARRAY?
- Which databases in your stack support native ARRAY? How does the JDBC driver bind/read them?
- When should a tag list move to a join table instead of staying in ARRAY or JSON?
- What are the differences between PostgreSQL `BYTEA`, MySQL `LONGBLOB`, and SQL Server `VARBINARY(MAX)`?
- Why can `byte[]` create heap pressure when loading many aggregates with large files?
- Why do passing H2 tests not prove that PostgreSQL ARRAY or Oracle collection mapping works?
- When using a custom repository for ARRAYs, how do you ensure it coordinates properly with transactions and aggregate saves?

A sound storage decision aligns **business domain semantics, Java types, SQL types, JDBC driver capabilities, and querying strategy**. Spring Data JDBC helps structure data operations around aggregates; for specialized ARRAY, JSON, and LOB types, the application must clearly define what is handled by default mapping and what requires dedicated adapters or converters.
