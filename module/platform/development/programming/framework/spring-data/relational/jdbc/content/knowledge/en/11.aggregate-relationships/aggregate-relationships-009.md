# Adding, Replacing, and Removing Child Elements and Their Data Lifecycle

In Spring Data JDBC, child elements belonging to an aggregate are managed through the **aggregate root**. For example, a §PurchaseOrder§ owns a list of §OrderLine§ items. When business logic adds, replaces, or removes an order line, the application updates the state of the aggregate root and then saves the root via its repository.

The key point is that **a child element's lifecycle is tied to the lifecycle of the aggregate that owns it**:

- A new element only becomes persisted data when the aggregate root is persisted.
- An element that is replaced or removed from the collection no longer belongs to the current aggregate state; that change is synchronized to the database when saving the root.
- When the aggregate root is deleted, the entities owned inside it are also handled according to the aggregate lifecycle.
- An element that frequently needs to be modified, queried, or exist independently may no longer fit the owned child entity model.

This lesson uses the example of an order with a list of order lines to explain adding, replacing, and removing child elements, how Spring Data JDBC synchronizes collections, the SQL impact, and the signs that indicate aggregate boundaries should be revisited.

## 1. The aggregate root manages child elements

An aggregate is a business consistency boundary. The aggregate root is the primary entry point for creating, modifying, and saving the components within that boundary.

Order example:

§§§text
PurchaseOrder aggregate
┌─────────────────────────────────────────┐
│ PurchaseOrder (aggregate root)          │
│ id                                      │
│ status                                  │
│                                         │
│ lines                                   │
│   ├── OrderLine: SKU-A, quantity = 2    │
│   ├── OrderLine: SKU-B, quantity = 1    │
│   └── OrderLine: SKU-C, quantity = 4    │
└─────────────────────────────────────────┘
                 |
                 v
         PurchaseOrderRepository
                 |
                 v
           Spring Data JDBC
                 |
                 v
        purchase_orders + order_lines
§§§

§PurchaseOrder§ enforces rules such as:

- Only allow modifying order lines while the order is in an editable status.
- Quantity must be greater than 0.
- Do not add a line with an invalid SKU.
- Only confirm an order when it has at least one order line.
- When removing a line, the overall state of the order must remain valid.

§OrderLine§ is an owned element. In this example, it has no separate repository, and callers must not arbitrarily write an order line directly while bypassing the order's rules.

**Having a child table does not mean having a separate aggregate root.** An aggregate can be persisted across multiple tables; repositories are normally defined for the root.

## 2. Mapping a collection of child elements

Spring Data JDBC uses §@MappedCollection§ to map a collection of owned entities to the corresponding table.

PostgreSQL schema example:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL
        REFERENCES purchase_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_position)
);
§§§

The §order_lines§ table has:

- §order_id§: foreign key pointing to the aggregate root.
- §line_position§: position of the element in the §List§.
- §sku§ and §quantity§: data of the order line.
- Composite primary key §(order_id, line_position)§: identifies an element by its position in the order's list.

Java mapping:

§§§java
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public record OrderLine(String sku, int quantity) {

    public OrderLine {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive");
        }
    }
}
§§§

Aggregate root:

§§§java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_position"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String status) {
        this.status = status;
    }

    public Long getId() {
        return id;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }
}
§§§

§idColumn§ specifies the foreign key column in the child table; §keyColumn§ specifies the column storing element positions in the list. Spring Data JDBC uses this metadata to restore the collection when reading the aggregate and synchronize it when writing.

## 3. Adding child elements

When business logic adds an order line, perform the change through a method on the aggregate root.

Example adding a method:

§§§java
public void addLine(String sku, int quantity) {
    ensureEditable();
    lines.add(new OrderLine(sku, quantity));
}

private void ensureEditable() {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException(
                "Only draft orders can be changed"
        );
    }
}
§§§

Then the service loads the root, adds the line, and saves again:

§§§java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder addLine(
            Long orderId, String sku, int quantity
    ) {
        PurchaseOrder order = orders.findById(orderId)
                .orElseThrow();

        order.addLine(sku, quantity);

        return orders.save(order);
    }
}
§§§

Execution flow:

§§§text
Load PurchaseOrder
       |
       v
order.addLine("SKU-D", 3)
       |
       v
In-memory collection gains new OrderLine
       |
       v
orders.save(order)
       |
       v
Spring Data JDBC synchronizes aggregate to database
§§§

Point to remember: §lines.add(...)§ only mutates the object in memory. Database data is only updated when a persist operation succeeds. If the request fails before save, the new element has not been written to the database.

### 3.1. Adding to a new aggregate

For an aggregate without an ID yet, you can create the root together with child elements and save once:

§§§java
PurchaseOrder order = new PurchaseOrder("DRAFT");

order.addLine("SKU-A", 2);
order.addLine("SKU-B", 1);

PurchaseOrder saved = orders.save(order);
§§§

Spring Data JDBC creates the root row, receives the database-assigned ID, and saves the child elements with the corresponding foreign key. Use the aggregate returned from §save§ to obtain the ID after saving.

### 3.2. Adding multiple elements in one operation

Multiple lines can be added in a single business operation:

§§§java
@Transactional
public PurchaseOrder addLines(
        Long orderId, List<NewOrderLine> requestedLines
) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    for (NewOrderLine requested : requestedLines) {
        order.addLine(requested.sku(), requested.quantity());
    }

    return orders.save(order);
}
§§§

If one element is invalid and the method throws an exception, the transaction can roll back the entire operation per configured rollback rules. Avoid saving individual elements through a separate repository because that bypasses the aggregate's consistency boundary.

## 4. Replacing child elements

Replacing an element means changing the content or position of an element in the collection while keeping it within the aggregate.

Example changing the quantity of the first order line:

§§§java
public void replaceLine(int position, String sku, int quantity) {
    ensureEditable();

    if (position < 0 || position >= lines.size()) {
        throw new IndexOutOfBoundsException(position);
    }

    lines.set(position, new OrderLine(sku, quantity));
}
§§§

Service:

§§§java
@Transactional
public PurchaseOrder replaceLine(
        Long orderId,
        int position,
        String sku,
        int quantity
) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    order.replaceLine(position, sku, quantity);

    return orders.save(order);
}
§§§

Before and after state:

§§§text
Before:
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-B, quantity 1

Replace position 1:
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-C, quantity 5
§§§

In the §List§ model, §position§ is the element's key in the collection. Replacing the element at that position means the content at that slot changes.

### 4.1. Replacing vs. mutating a single property

With immutable child objects such as records, we typically create a new instance and put it into the collection. In domain terms, this replaces the value at the corresponding position.

With mutable child objects, you can change a property on the existing object through a controlled method. Still, mutating the object in memory must be persisted through the root.

Whichever style you choose, ensure:

- Callers cannot mutate the collection inside the root directly.
- Business rules are validated before replacing.
- Positions are preserved if ordering is meaningful.
- Identity or historical data is not accidentally altered if elements have specific identity requirements.

### 4.2. Replacing the entire collection

Sometimes business logic submits a new list to replace the entire old list. You can define an explicit method:

§§§java
public void replaceAllLines(List<OrderLine> replacement) {
    ensureEditable();

    if (replacement == null) {
        throw new IllegalArgumentException(
                "Replacement lines must not be null"
        );
    }

    this.lines = new ArrayList<>(replacement);
}
§§§

This method has a different meaning from adding an element. It replaces the entire current collection state with a new collection.

Before allowing a full replacement, verify:

- Is the new list valid?
- Are any existing lines required by business rules to be retained?
- Does a trace of replaced lines need to be kept?
- How should totals, taxes, inventory, or order status be recalculated?
- Is the API sending a full list or only a partial update?

Do not treat a PATCH request containing a few elements as a full list and accidentally delete elements omitted from the request.

## 5. Removing child elements from the collection

When an element no longer belongs to the aggregate, remove it through a method on the root.

Example:

§§§java
public void removeLine(int position) {
    ensureEditable();

    if (position < 0 || position >= lines.size()) {
        throw new IndexOutOfBoundsException(position);
    }

    lines.remove(position);
}
§§§

Service:

§§§java
@Transactional
public PurchaseOrder removeLine(Long orderId, int position) {
    PurchaseOrder order = orders.findById(orderId)
            .orElseThrow();

    order.removeLine(position);

    return orders.save(order);
}
§§§

Before removing:

§§§text
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-B, quantity 1
  position 2 -> SKU-C, quantity 4
§§§

After removing position 1:

§§§text
Order 501
  position 0 -> SKU-A, quantity 2
  position 1 -> SKU-C, quantity 4
§§§

When saving the aggregate, the new collection state is synchronized down to the child table. The removed element no longer belongs to the aggregate, and its corresponding data row is handled according to Spring Data JDBC's persistence mechanism.

**Removing from a collection in Java does not mean immediate deletion in the database.** If save is not called or the transaction rolls back, the persisted data remains intact.

### 5.1. Removing by condition instead of position

If the collection is a §List§ but business logic identifies lines by SKU, you can find the element by condition:

§§§java
public void removeLineBySku(String sku) {
    ensureEditable();

    boolean removed = lines.removeIf(
            line -> line.sku().equals(sku)
    );

    if (!removed) {
        throw new IllegalArgumentException(
                "Line not found: " + sku
        );
    }
}
§§§

If the same SKU can appear multiple times in an order, the code above removes all lines matching that SKU. If business rules only allow removing a single specific line, a clear line identifier is needed or the match count must be checked before removing.

Do not use list position as a business identity if positions can shift and external operations need stable references to individual lines.

### 5.2. Empty collection after removing the last element

After deleting the last element, the collection may become empty:

§§§java
order.removeLine(0);

if (order.getLines().isEmpty()) {
    // The order currently has no order lines.
}
§§§

This does not necessarily mean the aggregate root must be deleted. The root can still exist in DRAFT status so the user can add other lines. If business rules disallow confirming an empty order, enforce that rule in the §confirm§ method.

Do not turn an empty collection into §null§ just to indicate there are no elements. An empty collection is usually a much clearer representation for "the aggregate exists but currently has no child elements".

## 6. Lifecycle of child elements in Spring Data JDBC

The lifecycle of an owned child entity is tied to the aggregate root.

| Domain operation | In-memory state | When saving aggregate |
| --- | --- | --- |
| Create new aggregate with child elements | New root, collection has elements | Inserts root and child elements. |
| Add element to existing root | Collection grows | Synchronizes new collection to database. |
| Replace element | Collection has new instance/value at the corresponding position | Synchronizes new collection state. |
| Remove element | Collection no longer contains that element | Corresponding child row is removed from saved aggregate state. |
| Delete root | Root no longer exists | Owned entities are also deleted with the aggregate. |
| Mutate object without saving | Memory changes, database unchanged | No corresponding write operation occurs. |
| Save fails and transaction rolls back | Persistence operation does not commit | Database retains pre-transaction state. |

### 6.1. Child entities have no independent lifecycle

In the §OrderLine§ example:

- Do not create §OrderLineRepository§.
- Do not allow any service to call save directly on a single line.
- Do not expose the line's ID as a public reference if the line has no business identity.
- Add, edit, and remove operations all go through §PurchaseOrder§.

This keeps rules such as total quantity, order status, and confirmation requirements controlled at one place.

### 6.2. Deleting the root and owned entities

When deleting §PurchaseOrder§, Spring Data JDBC handles the referenced entities inside the aggregate according to the root's lifecycle. This differs from deleting an independent aggregate that the root only references by ID.

Example:

§§§text
PurchaseOrder 501
  ├── OrderLine A
  ├── OrderLine B
  └── OrderLine C

orders.deleteById(501)

PurchaseOrder 501 is deleted
OrderLine A, B, C are handled according to ownership
Customer referenced by order (if any) still exists
§§§

If child entities contain data referenced by another table via foreign keys, deletion/replacement can be blocked by the database. That is a signal to evaluate whether the child entity should truly be an owned component or become a separate aggregate.

## 7. How does Spring Data JDBC synchronize collections?

A major difference of Spring Data JDBC compared to an ORM with a persistence context is **there is no continuous dirty checking on the object graph**.

When saving an existing aggregate, Spring Data JDBC needs to synchronize the passed-in aggregate state. For entities referenced inside the aggregate, the collection update mechanism is typically:

1. Update the aggregate root row.
2. Delete existing owned child entity rows for the aggregate.
3. Re-insert child entities according to the new collection state.

This strategy keeps the persistence model clear: the database reflects the submitted aggregate state. However, it also has performance and identity consequences.

For example, an order has 100 lines, and only one line's quantity changes. Do not assume Spring Data JDBC emits only one §UPDATE§ statement for that single row. Collection synchronization may delete and re-insert child rows.

§§§text
Database before:
order_lines
  501 | 0 | SKU-A | 2
  501 | 1 | SKU-B | 1
  501 | 2 | SKU-C | 4

Object after modification:
  501
    0 -> SKU-A, 2
    1 -> SKU-B, 5
    2 -> SKU-C, 4

Save aggregate:
  Root is updated
  Collection is synchronized to new state
  Child rows may be deleted/reinserted
§§§

Exact SQL details depend on the version and mapping, but when designing you should account for the collection being saved as part of the aggregate state rather than a set of entities with row-by-row dirty tracking.

### 7.1. Implications for child element IDs

If a child entity has its own key, be cautious about assuming its ID stays preserved across root saves. With a delete/re-insert strategy for owned entities, child rows can be recreated and database-generated identifiers may change depending on the mapping.

If another system needs stable references to individual child elements, or needs to update them independently, that is a strong indicator that the element may need to become a separate aggregate root.

### 7.2. Implications for foreign keys pointing to child entities

Suppose another table references §order_lines.id§. If Spring Data JDBC deletes child rows and re-inserts them during aggregate save, foreign keys from external tables can:

- Block deleting the child rows.
- Cascade-delete related data if cascade is configured.
- Become orphaned references if no constraint protects them.

Therefore, **an owned child entity should not be the target of independent references from other aggregates** if saving the root can recreate child rows.

If you need an entity with a stable identity referenced from many places, consider splitting it into a separate aggregate root and having other aggregates reference its ID.

## 8. Element order and replacement in List, Set, and Map

The collection type affects how elements are added, replaced, and removed.

### 8.1. List: position is meaningful

§List§ preserves order. With §@MappedCollection(keyColumn = "line_position")§, positions can be stored in the child table.

Operations:

§§§java
lines.add(new OrderLine("SKU-D", 1));  // Append to end
lines.set(1, replacement);             // Replace at position 1
lines.remove(1);                       // Remove position 1
§§§

When inserting or deleting in the middle, subsequent positions can shift. Do not treat §line_position§ as a durable business ID if order can change.

If stable references to an order line are needed, give it a dedicated line code and design the model accordingly.

### 8.2. Set: uniqueness by equality

§Set§ does not represent order and does not hold duplicate elements under §equals/hashCode§ rules.

Example:

§§§java
private Set<Tag> tags = new LinkedHashSet<>();

public void addTag(Tag tag) {
    tags.add(tag);
}

public void removeTag(Tag tag) {
    tags.remove(tag);
}
§§§

When using §Set§, define equality/hash code appropriate for the domain. If a mutable property is used in §hashCode§ and then modified while the element is inside the Set, lookup/removal may misbehave.

### 8.3. Map: key is identity within the collection

§Map§ fits when each element is identified by a key within the scope of the aggregate:

§§§java
private Map<String, DeliveryInstruction> instructions =
        new LinkedHashMap<>();

public void putInstruction(String key, DeliveryInstruction value) {
    instructions.put(key, value);
}

public void removeInstruction(String key) {
    instructions.remove(key);
}
§§§

§put§ with an existing key replaces the old value; §remove§ drops the element by key. The key column in the mapping must be able to store the key and have a compatible SQL type.

A Map key is an identity within the collection scope, not automatically an independent aggregate ID.

## 9. Complete example with add, replace, and remove operations

A version of the root with full behaviors:

§§§java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Objects;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_position"
    )
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String status) {
        this.status = Objects.requireNonNull(status);
    }

    public Long getId() {
        return id;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    public void addLine(String sku, int quantity) {
        ensureEditable();
        lines.add(new OrderLine(sku, quantity));
    }

    public void replaceLine(
            int position, String sku, int quantity
    ) {
        ensureEditable();
        checkPosition(position);
        lines.set(position, new OrderLine(sku, quantity));
    }

    public void removeLine(int position) {
        ensureEditable();
        checkPosition(position);
        lines.remove(position);
    }

    public void removeLineBySku(String sku) {
        ensureEditable();

        boolean removed = lines.removeIf(
                line -> line.sku().equals(sku)
        );

        if (!removed) {
            throw new IllegalArgumentException("Line not found");
        }
    }

    public void confirm() {
        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "Cannot confirm an empty order"
            );
        }
        ensureEditable();
        status = "CONFIRMED";
    }

    private void ensureEditable() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                    "Only draft orders can be edited"
            );
        }
    }

    private void checkPosition(int position) {
        if (position < 0 || position >= lines.size()) {
            throw new IndexOutOfBoundsException(position);
        }
    }
}

import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

            String sku, int quantity

        PurchaseOrder order = load(orderId);
        order.replaceLine(position, sku, quantity);
        return orders.save(order);

    public PurchaseOrder removeLine(

        PurchaseOrder order = load(orderId);

The service keeps one transaction per business operation. The repository is responsible for persisting the aggregate; the root is responsible for enforcing rules and modifying the collection.

In a real project, add handling for order-not-found, business errors, optimistic locking if concurrent updates occur, and appropriate API responses.

## 10. How do adding, replacing, and removing elements affect the database?

| Operation | Aggregate state after operation | Persistence consequence |
| --- | --- | --- |
| §addLine§ | Element added | Saves new collection state; new element is inserted into child table. |
| §replaceLine§ | One element replaced with new value | Saves new collection state; may synchronize by deleting/re-inserting child rows. |
| §removeLine§ | Element no longer in collection | Corresponding child row is removed from saved aggregate state. |
| §replaceAllLines§ | Entire collection changed | Database is synchronized with new list; old elements no longer present may be deleted. |
| §save§ not yet called | Only in-memory object changed | Database has not received the changes. |
| §save§ rolls back | Transaction did not commit | Changes are not durably persisted. |
| §delete(root)§ | Aggregate no longer exists | Owned entities are also handled per the root's lifecycle. |

This table describes business meaning and expected outcomes. Exact counts, order, and details of SQL statements depend on the mapping, database, and Spring Data JDBC version.

### 10.1. Do not equate replace with updating a single row

In ORMs with a persistence context, dirty checking can detect a single changed property and emit an update for that row. Spring Data JDBC has a different aggregate persistence model; do not rely on dirty checking to infer SQL statements.

If technical requirements strictly demand updating exactly one child row without recreating the collection, consider a custom SQL query or designing the element as an independent aggregate. However, when bypassing the root repository, the application must uphold the related invariants itself.

### 10.2. Transactions for aggregate changes

When a business operation consists of multiple SQL statements to save the root and collection, a transaction ensures those changes commit or roll back together as configured. CRUD repositories typically have default transaction configuration; placing §@Transactional§ on the service clearly defines the boundary of the business operation, especially when coordinating multiple repositories or steps.

Do not split a single aggregate modification across multiple independent transactions if doing so could leave the root and collection in an inconsistent state.

## 11. When should a child element become a separate aggregate?

Reconsider the design if a child element exhibits one or more of these characteristics:

- Has a stable business identity referenced from many places.
- Has a lifecycle independent of the root.
- Needs to be created, edited, and deleted via its own API or repository.
- Has a large volume of data requiring pagination.
- Is updated frequently and independently of the root.
- Can be referenced by multiple aggregates simultaneously.
- Saving the root causes costly re-synchronization of the entire collection.
- Other data references the child element's ID and requires preserving a stable identity.

For example, if §OrderLine§ must be independently referenced by fulfillment, invoicing, and analytics systems, consider making §OrderLine§ an aggregate root with its own ID, while §PurchaseOrder§ retains a reference to it per an appropriate domain design.

Diagram before splitting:

§§§text
PurchaseOrder aggregate
  ├── OrderLine A
  ├── OrderLine B
  └── OrderLine C
§§§

After splitting:

§§§text
PurchaseOrder aggregate
  id = 501

OrderLine aggregate A
  id = 7001
  orderId = 501

OrderLine aggregate B
  id = 7002
  orderId = 501
§§§

At that point, adding or removing an §OrderLine§ is a separate repository operation and the service must enforce any required cross-aggregate rules. Do not split solely to dodge collection delete/insert behavior if the element must still always stay consistent with the root.

## 12. Common pitfalls

**"Adding an element to the List means the database already has a new row."** Incorrect. Only the in-memory collection changed; the aggregate root must be persisted.

**"I can create an OrderLineRepository for all order lines."** Advisable not to if §OrderLine§ is an owned child entity. Independent operations can bypass §PurchaseOrder§'s rules.

**"Removing from the List immediately deletes the child row."** Incorrect. Database rows are synchronized when saving the root and committing the transaction.

**"Replacing one element only issues an UPDATE for that row."** Do not assume this. Spring Data JDBC may delete and re-insert owned entities when updating an aggregate.

**"List position is the stable ID of the order line."** Incorrect. Positions can change when inserting or removing earlier elements.

**"An empty collection means the aggregate root must be deleted."** Incorrect. The root can exist in a state with no elements yet; business rules decide whether that state is allowed.

**"Deleting the root only deletes the root row."** Incorrect for aggregates with owned entities. Owned components also belong to the root's lifecycle.

**"If a child has an ID, it must be an aggregate root."** Incorrect. A child entity can still have its own key while being managed inside an aggregate root.

**"Putting ON DELETE CASCADE on every foreign key simplifies code."** Incorrect. Cascade in the wrong direction can wipe out independent or historical data. Distinguish internal ownership from cross-aggregate references.

**"Sending a trimmed list from an API and calling save only updates the sent elements."** Incorrect if the API is replacing the entire collection. Distinguish targeted add/remove/replace operations from replacing the full list state.

## 13. Workflow for implementing safe collection operations

When adding, replacing, or removing child elements, follow this sequence:

1. **Load the aggregate root** using the repository.
2. **Check permissions and status** to confirm the root allows modifications.
3. **Invoke a domain method** such as §addLine§, §replaceLine§, or §removeLine§.
4. **Validate invariants**: valid quantities, no duplicates, collection limits, order status.
5. **Save the root** via the repository.
6. **Commit the transaction**; on error, handle rollback and respond appropriately.
7. **Use the aggregate returned** from §save§ when you need the ID or persisted state.
8. **Evaluate data impact** if the collection is large, has dependent FKs, or requires a stable identity.

If multiple users can edit the same aggregate concurrently, consider optimistic locking with §@Version§. Otherwise, a request loading stale state can overwrite another request's changes under the aggregate-saving strategy.

## 15. Takeaways

- Child entities belonging to an aggregate are created, replaced, and removed through the aggregate root.
- Modifying a collection in Java does not change the database; the root must be saved and the transaction committed.
- §@MappedCollection§ defines the collection's relationship to the child table via the foreign key and key column.
- With §List§, position is the key within the collection, not necessarily a stable business identity.
- Spring Data JDBC does not rely on persistence-context dirty checking; updating an owned collection may delete and re-insert child rows to synchronize aggregate state.
- An element removed from the collection will no longer belong to the aggregate once the new state is persisted.
- Deleting an aggregate root also handles owned entities according to the root's lifecycle; independent aggregates referenced only by ID are not deleted alongside it.
- Large collections, elements with stable identities, pagination needs, or independent updates are signs to re-evaluate aggregate boundaries.
- Transactions, foreign keys, and optimistic locking must work together to protect data under concurrent operations.

When designed properly, adding, replacing, and removing child elements are controlled mutations on the aggregate root. **Data lifecycle in the database must reflect the domain lifecycle**: owned elements follow the root; elements with an independent lifecycle need their own aggregate boundary and reference policy.
