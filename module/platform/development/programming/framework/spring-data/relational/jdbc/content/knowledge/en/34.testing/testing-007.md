# Test Data via Migrations, @Sql, and Fixtures in Spring Data JDBC

## 1. Why Do We Need a Test Data Strategy?

A repository test is only meaningful when the database contains data matching the scenario under test. With Spring Data JDBC, test data must accurately reflect aggregate structure, foreign keys, constraints, and schema data types.

For example, when testing loading an order with order lines, the database must contain:

- The aggregate root row in the `orders` table.
- Child rows in the `order_lines` table.
- The `order_id` foreign key pointing properly to the order.
- Status values, quantities, and business fields needed for assertions.

There are multiple ways to prepare data: migrations, SQL fixtures, the `@Sql` annotation, or Java builders/object factories. Each approach has a different scope and lifecycle. Choosing the right one keeps tests readable, independent, and stable both locally and in CI.

A practical strategy usually separates test data into three layers:

1. **Schema migration:** creates and evolves database structure following the application's version history.
2. **Test baseline data:** shared, stable data needed by a group of tests.
3. **Scenario fixture:** data specific to an individual test case, created before the test and rolled back or cleaned up afterward.

Do not use a single SQL file to both create the schema and hold all data for every test. When responsibilities are separated, each test clearly expresses the input data it requires.

## 2. Distinguishing Migrations and Fixtures

Both migrations and fixtures can be SQL, yet they solve two different problems.

| Component | Purpose | Lifecycle |
|---|---|---|
| Schema migration | Create tables, columns, indexes, constraints, and evolve schema | Follows application versions, runs in order |
| Test-only migration | Create baseline data shared across tests | Runs only in test configuration |
| @Sql fixture | Prepare data for a test class or method | Before/after test per execution phase |
| Java fixture/builder | Construct entities and aggregates via Java API | Inside tests or setup methods |
| Cleanup script | Delete data created by tests | After test or via transaction rollback |

Example migration creating tables:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);
~~~

This migration describes the schema that must exist in every environment. It should not include a dummy order serving only one specific test.

A fixture can insert one order and two order lines to test the repository:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-001', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92001, 91001, 'SKU-A', 2),
    (92002, 91001, 'SKU-B', 1);
~~~

The IDs in this example are fixed for easy reference inside tests. If a table uses a sequence/identity and subsequent tests insert with generated IDs, ensure the sequence will not collide with manually inserted IDs. You can use a fixture builder to obtain auto-generated IDs or advance the sequence per database.

## 3. Using Migrations to Create the Test Schema

Spring Data JDBC does not automatically create the full schema from entity mappings in every configuration. Applications typically use Flyway or Liquibase to manage schemas. Tests should run the same migration chain the application uses to build the database from scratch.

Example Flyway structure:

~~~text
src/
  main/
    resources/
      db/
        migration/
          V1__create_orders.sql
          V2__add_order_status.sql
          V3__create_order_lines.sql
  test/
    resources/
      db/
        migration/
          V9999__test_reference_data.sql
~~~

Flyway runs migrations in version order. Spring Boot looks in `classpath:db/migration` by default, configurable via `spring.flyway.locations`.

Example configuration:

~~~properties
spring.flyway.locations=classpath:db/migration
~~~

If you need baseline data available only in tests, place an extra migration in `src/test/resources`. That migration is not packaged into production artifacts. However, test-only migrations usually run when the test application context starts, not before each test method. Therefore, use them only for shared, stable reference data; scenario-specific data should use `@Sql` or fixture builders.

### 3.1. Do Not Mix Multiple Schema Creation Mechanisms

Spring Boot recommends choosing one primary mechanism to create and initialize schemas. If a project uses Flyway or Liquibase for schema management, do not simultaneously use `schema.sql`/`data.sql` as a second migration system.

When using Flyway:

- Place schema migrations in `src/main/resources/db/migration`.
- Place test-only migrations in `src/test/resources` if shared baseline data is needed.
- Never edit migrations already applied in shared environments; create new migrations.
- Use the exact target database engine when migrations contain vendor-specific SQL.

When using Liquibase, you can tag test data changesets with a context:

~~~sql
--liquibase formatted sql

--changeset sample:1 context:@test
INSERT INTO product_categories (id, name)
VALUES (99001, 'Test category');
~~~

Then configure the test context:

~~~properties
spring.liquibase.contexts=test
~~~

Only changesets with matching contexts are applied in the test environment. Do not put test data into un-contextualized production changesets just to give tests a few pre-loaded rows.

## 4. Test Slice for Spring Data JDBC

Spring Boot provides `@DataJdbcTest` to test the Spring Data JDBC persistence layer. This slice typically configures:

- A test DataSource, preferring an embedded database by default if present.
- Spring Data JDBC repositories.
- `JdbcTemplate`.
- Test transactions with default rollback after each test method.

Example:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    void savesAndLoadsOrder() {
        Order saved = orders.save(
                Order.create("TEST-001")
        );

        Order loaded = orders.findById(saved.getId())
                .orElseThrow();

        assertThat(loaded.getOrderNumber()).isEqualTo("TEST-001");
    }
}
~~~

This is the appropriate test slice for repositories and mapping. It does not auto-scan every `@Component` or service like a full application context. If a test needs service beans or custom configuration, import the needed configuration or use `@SpringBootTest` for broader integration tests.

Test annotation package names can vary across major Spring Boot versions. Use annotations from the test module and version matching your project.

### 4.1. Using a Real Database Instead of an Embedded Database

Embedded databases keep tests fast, yet can differ from production in:

- SQL dialect.
- Data types and constraints.
- Sequences/identity.
- Locking and isolation.
- Functions, triggers, and migration syntax.
- Query planner.

If you need to use the configured DataSource, instruct Spring Boot not to replace it with an embedded database:

~~~java
@DataJdbcTest
@AutoConfigureTestDatabase(
        replace = AutoConfigureTestDatabase.Replace.NONE
)
class OrderRepositoryIntegrationTest {
    // Tests against the DataSource configured for testing.
}
~~~

A popular choice is Testcontainers to start a database matching production. Tests still use real Spring Data JDBC repositories and run migrations against the container database.

Do not conclude that migrations or queries are production-compatible just because tests pass on H2 if the project deploys on PostgreSQL, MySQL, or another DBMS.

## 5. Using @Sql to Load Test Data

The `@Sql` annotation allows running SQL scripts before or after a test class or method. This is a convenient option when fixtures are best expressed in SQL.

Example fixture file:

~~~text
src/test/resources/fixtures/orders-with-lines.sql
~~~

Contents:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-001', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92001, 91001, 'SKU-A', 2),
    (92002, 91001, 'SKU-B', 1);
~~~

Used in a repository test:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/orders-with-lines.sql")
    void loadsOrderWithItsLines() {
        Order order = orders.findById(91001L)
                .orElseThrow();

        assertThat(order.getLines()).hasSize(2);
        assertThat(order.getLines())
                .extracting(OrderLine::getSku)
                .containsExactlyInAnyOrder("SKU-A", "SKU-B");
    }
}
~~~

A path starting with `/` is an absolute classpath resource. When using a relative path, Spring resolves it relative to the test class's package.

By default, `@Sql` scripts run before the test method. This is the right moment to insert fixture data for the test.

### 5.1. Using @Sql at Class and Method Level

Shared data can be placed at the class level:

~~~java
@DataJdbcTest
@Sql("/fixtures/reference-categories.sql")
class ProductRepositoryTest {

    @Test
    void findsProductsByCategory() {
        // Uses shared category data.
    }

    @Test
    @Sql("/fixtures/products-for-search.sql")
    void searchesProductsByName() {
        // Uses additional method-specific data.
    }
}
~~~

By default, method-level `@Sql` overrides class-level `@Sql`. To combine class-level shared scripts with method-specific scripts, use `@SqlMergeMode`:

~~~java
@DataJdbcTest
@Sql("/fixtures/reference-categories.sql")
@SqlMergeMode(SqlMergeMode.MergeMode.MERGE)
class ProductRepositoryTest {
    // Method-level @Sql is merged with class-level @Sql.
}
~~~

If a specific method does not need the class-level data, you can set `OVERRIDE` mode on that method to return to default behavior.

### 5.2. Multiple Scripts and Execution Order

Multiple scripts can be passed in one annotation:

~~~java
@Test
@Sql({
        "/fixtures/orders.sql",
        "/fixtures/order-lines.sql",
        "/fixtures/payments.sql"
})
void loadsCompleteOrder() {
    // ...
}
~~~

Scripts should be ordered by foreign key dependencies: insert parents first, children later. When cleaning up via SQL, usually delete children before parents when cascades are absent.

Spring also supports repeatable `@Sql` annotations if separate groups need different configurations or execution phases.

## 6. Using @SqlConfig and Fixture Transactions

An important detail is that `@Sql` scripts can join an existing transaction, run without a transaction, or run in an isolated transaction. Spring TestContext infers behavior from `transactionMode`, `DataSource`, and `PlatformTransactionManager` in the test context.

For tests marked `@Transactional`, `@Sql` scripts normally join the test's transaction. When the test ends and the transaction rolls back, data inserted by the script rolls back with it.

Example:

~~~java
@DataJdbcTest
@Transactional
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/orders-with-lines.sql")
    void loadsFixture() {
        assertThat(orders.findById(91001L)).isPresent();
    }
}
~~~

No `DELETE` cleanup script is needed if both the fixture and test run in the same test-managed transaction without separate commits.

### 6.1. When Is ISOLATED Transaction Mode Needed?

Sometimes a script must commit data outside the test's transaction. For example, a test starts an HTTP server on a separate thread, and requests handled by the server need to see committed fixture data.

In that case, use `ISOLATED` transactionMode:

~~~java
@Test
@Sql(
        scripts = "/fixtures/create-order.sql",
        config = @SqlConfig(
                transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
)
@Sql(
        scripts = "/fixtures/delete-order.sql",
        config = @SqlConfig(
                transactionMode = SqlConfig.TransactionMode.ISOLATED
        ),
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
void requestReadsCommittedOrder() {
    // Send request to server.
}
~~~

Both the data-creation and cleanup scripts run in their own transactions. Cleanup is configured at `AFTER_TEST_METHOD` to remove data after the test ends.

Use `ISOLATED` only when separate commit semantics are needed. For regular repository tests, letting the script join the test transaction and roll back automatically is usually simpler.

### 6.2. Controlling DataSource and Transaction Manager

If the test context has multiple DataSources or transaction managers, Spring may not infer the right resource for the script.

You can specify them explicitly in `@SqlConfig`:

~~~java
@Sql(
        scripts = "/fixtures/orders.sql",
        config = @SqlConfig(
                dataSource = "ordersDataSource",
                transactionManager = "ordersTransactionManager"
        )
)
~~~

Bean names must match application configuration. Do not use a different database's transaction manager to execute fixtures when the repository under test uses its own DataSource.

### 6.3. Post-Test Cleanup Scripts

`@Sql` supports `executionPhase = AFTER_TEST_METHOD`:

~~~java
@Test
@Sql("/fixtures/create-test-customer.sql")
@Sql(
        scripts = "/fixtures/delete-test-customer.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
void performsCustomerOperation() {
    // ...
}
~~~

If tests run in auto-rollback transactions, cleanup scripts are usually unnecessary. Explicit cleanup suits non-transactional tests, separately committed data, or tests using shared database resources.

For parallel tests, avoid overly broad cleanup predicates like deleting an entire table. Use test-specific IDs or business keys to delete only rows created by that test.

## 7. Creating Fixtures with Java Builders or Repositories

Not all data should be written in SQL. When tests aim to exercise Spring Data JDBC aggregate behavior and mapping, construct entities via constructors/builders and save them with repositories.

Example helper:

~~~java
private Order createOrder(
        OrderRepository orders,
        String orderNumber,
        String... skus
) {
    List<OrderLine> lines = Arrays.stream(skus)
            .map(sku -> new OrderLine(sku, 1))
            .toList();

    return orders.save(
            new Order(orderNumber, "PENDING", lines)
    );
}
~~~

Test:

~~~java
@Test
void savesAggregateWithMultipleLines() {
    Order saved = createOrder(
            orders,
            "TEST-ORDER-002",
            "SKU-A",
            "SKU-B"
    );

    Order loaded = orders.findById(saved.getId())
            .orElseThrow();

    assertThat(loaded.getLines()).hasSize(2);
}
~~~

Advantages of fixture builders:

- Uses real domain constructors and factory methods.
- Less coupled to column names and SQL syntax.
- Easy to create many data variations.
- Data reflects the application's aggregate creation rules.
- Generated IDs are obtained from the entity returned by the repository.

The downside is that tests must go through persistence to create the fixture, and it is hard to set up special states such as legacy invalid values or records in states the current domain API forbids creating.

Therefore, Java fixtures and SQL fixtures can coexist. Choose whichever expresses the test's intent most clearly.

## 8. When Should Each Fixture Type Be Used?

| Scenario | Suitable Approach |
|---|---|
| Repository test verifying aggregate mapping | Construct objects and save via repository |
| Need complex multi-table data with exact values | SQL fixture with `@Sql` |
| Many tests share a stable reference dataset | Test-only migration or class-level `@Sql` |
| Each test needs its own data | Method-level `@Sql` or Java builder |
| Need data impossible to create via domain API | SQL fixture |
| Need to verify schema upgrade | Run migrations from old version to new version on test database |
| Need testing on a real database engine | Testcontainers combined with migrations and fixtures |
| Need dynamically ID-generated data | Java builder or setup method |

Do not force all tests to use a single fixture style. What matters is that every test makes clear where data is created, when it is created, and how it is cleaned up.

## 9. Testing Migrations and Schema Evolution

Migration tests should start from an empty database or an older schema version, then execute the application's real migrations.

Some objectives:

- New migrations create proper tables and constraints.
- Migrations adding columns provide proper defaults.
- Legacy data is preserved across schema changes.
- Indexes and foreign keys are created properly.
- Migrations run on the target database.
- Repositories work against the post-migration schema.

Example Flyway workflow:

~~~text
1. Create a clean test database.
2. Run all production migrations.
3. Run test-only migrations if baseline data is needed.
4. Load scenario fixtures with @Sql or builders.
5. Run repository/service tests.
6. Destroy the test database or roll back/clean up fixtures.
~~~

If you need to test upgrading from a specific version, build the database at that version and then run the remaining migrations. Do not test only the final schema state; a migration might build the new schema while corrupting or losing legacy data.

### 9.1. Test-Only Migrations with Flyway

Spring Boot allows placing test-only migrations in `src/test/resources`. Example:

~~~text
src/test/resources/db/migration/
  V9999__test_reference_data.sql
~~~

Contents can insert category codes or reference data needed across many tests.

Remember that test-only migrations typically run once according to the database/context migration history. They do not automatically reset data before every test method. Data can be shared, so never let one test mutate or delete baseline rows that other tests depend on.

### 9.2. Test Contexts with Liquibase

With Liquibase, you can tag data changesets with a test context:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: test-reference-data
      author: sample
      context: "@test"
      changes:
        - insert:
            tableName: product_categories
            columns:
              - column:
                  name: id
                  valueNumeric: 99001
              - column:
                  name: name
                  value: Test category
~~~

In test configuration:

~~~properties
spring.liquibase.contexts=test
~~~

The `@test` context requires the test context to be explicitly specified when running Liquibase; this keeps test-only changesets from accidentally running in environments that do not pass the context. Do not put method-specific scenario data into shared changelogs if that data can couple tests together.

## 10. How Do DataJdbcTest and SpringBootTest Differ?

| Annotation | Scope | When to Use |
|---|---|---|
| `@DataJdbcTest` | Slice for Spring Data JDBC, repositories, and JDBC infrastructure | Testing mapping, repositories, queries |
| `@JdbcTest` | Lower-level JDBC slice, not focused on Spring Data JDBC repositories | Testing JdbcTemplate/SQL DAOs |
| `@SpringBootTest` | Broader application context, including services and application configuration | Cross-layer integration tests |
| `@SpringBootTest(webEnvironment = RANDOM_PORT)` | Starts a real server on a random port | Testing HTTP endpoints with a database |

JDBC test slices are usually transactional and roll back at the end of each test. This makes data isolation convenient.

With `@SpringBootTest` and `webEnvironment = RANDOM_PORT`, the HTTP client and server run on separate threads. The test's transaction does not cover the transaction handled by the server for the request. Therefore, do not assume server-written data rolls back just because the test method has `@Transactional`. Use a dedicated test database, cleanup fixtures, or an appropriate isolation mechanism.

## 11. Complete Example: Repository Test with Migrations and @Sql

Suppose the schema is created by Flyway migrations in `src/main/resources/db/migration`. Test fixtures live in `src/test/resources/fixtures`.

Fixture:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-003', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92011, 91001, 'SKU-C', 3),
    (92012, 91001, 'SKU-D', 2);
~~~

Test:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/order-with-lines.sql")
    void loadsAggregateFromSqlFixture() {
        Order order = orders.findById(91001L)
                .orElseThrow();

        assertThat(order.getOrderNumber())
                .isEqualTo("TEST-ORDER-003");

        assertThat(order.getLines())
                .extracting(OrderLine::getSku)
                .containsExactly("SKU-C", "SKU-D");
    }

    @Test
    void savesAggregateUsingDomainFixture() {
        Order order = new Order(
                "TEST-ORDER-004",
                "PENDING",
                List.of(
                        new OrderLine("SKU-E", 1),
                        new OrderLine("SKU-F", 4)
                )
        );

        Order saved = orders.save(order);

        assertThat(saved.getId()).isNotNull();
        assertThat(saved.getLines()).hasSize(2);
    }
}
~~~

In this example:

- Flyway migrations create the schema before repository tests run.
- `@Sql` inserts an aggregate with exact values to test load mapping.
- The second test builds an aggregate through Java and the repository to test save mapping.
- Because `@DataJdbcTest` manages transactions by default, both fixtures and repository operations roll back after each test method.

This combines migrations, SQL fixtures, and Java fixtures without overloading any single mechanism.

## 12. Common Mistakes

| Symptom | Possible Cause | Fix |
|---|---|---|
| Test reports missing table | Migrations did not run or test uses a different DataSource | Check Flyway/Liquibase and test DataSource |
| Fixture runs before tables exist | Incorrect ordering of schema initialization and scripts | Let migrations finish on application context startup; use `@Sql` for method fixtures |
| Method-level `@Sql` does not run with class-level scripts | Method-level declaration overrides class-level by default | Use `@SqlMergeMode(MERGE)` when combining |
| Fixture rolled back before server request reads it | Script joined test transaction while server runs on another thread | Use `ISOLATED` or seed committed data |
| Test data remains after test | Non-transactional test or isolated fixture | Use cleanup scripts or a dedicated database |
| Primary key collision | Fixture uses fixed IDs on a shared database | Use unique IDs, rollback, or isolated schema/database |
| Second test depends on first test's data | Shared fixture mutated or overly broad cleanup | Create isolated fixtures per test and avoid mutating baseline data |
| Flyway reports checksum mismatch | Migration was edited after running | Create a new migration instead of editing applied ones |
| Test passes on H2 but fails in production | Dialect, constraint, sequence, or SQL differences | Run integration tests against the target database |
| `@Sql` cannot find file | Relative resource path or wrong package | Use absolute classpath path starting with `/` |
| Script inserts child before parent | Foreign key violation | Insert root first, child second |
| Cleanup deletes other tests' data | `DELETE` predicate is too broad | Delete by test-specific ID or business key |
| Test slice lacks service bean | `@DataJdbcTest` does not scan regular components | Import needed beans or use `@SpringBootTest` |
| Using `schema.sql` alongside Flyway/Liquibase | Competing schema initialization mechanisms | Choose one primary schema management mechanism |

## 13. Workflow for Choosing and Managing Fixtures

1. Determine whether the test verifies a repository, service, or full application.
2. Use the application's real migrations to create the schema.
3. Use test-only migrations only for stable shared baseline data.
4. Choose `@Sql` for explicit SQL fixtures or Java builders for aggregates created via the domain API.
5. Keep fixtures scenario-specific and name files to reflect intent.
6. Specify whether scripts run before or after tests using `executionPhase`.
7. Decide whether fixtures join the test transaction or need `ISOLATED`.
8. Rely on automatic rollback for transactional tests; otherwise clean up by unique ID.
9. Run tests on the target database when migrations or SQL depend on dialect.
10. Keep tests independent so each can run standalone and in any order.

## 15. Key Takeaways

- Migrations manage schemas by version; fixtures supply data for test scenarios.
- Use production migrations so test databases match actual application structure.
- Test-only migrations fit shared baseline data, not per-method scenario fixtures.
- `@Sql` runs scripts before test methods by default and can run after tests for cleanup.
- Method-level `@Sql` overrides class-level `@Sql` by default; use `@SqlMergeMode` when merging.
- In transactional tests, `@Sql` normally joins the test transaction and rolls back at the end.
- Use `transactionMode = ISOLATED` when scripts must commit independently of the test transaction.
- `@DataJdbcTest` fits repository/mapping tests; `@SpringBootTest` fits broader integration tests.
- Tests hitting a real HTTP server run transactions on another thread, so test-method rollback does not roll back server changes.
- Spring Boot recommends choosing one primary schema management mechanism; avoid arbitrarily mixing `schema.sql`/`data.sql` with Flyway or Liquibase.
- Run migrations and fixtures on the target database when SQL, sequences, constraints, or dialects may differ from embedded databases.
