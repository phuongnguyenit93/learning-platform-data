# Distinguishing SQL Initialization from Versioned Migrations

Spring Data JDBC maps aggregates to relational tables, but it does not infer and generate the entire database schema from the domain model. The application still needs a way to manage tables, columns, foreign keys, indexes, and constraints before repositories can work.

In Spring Boot, two common ways to prepare a schema are **SQL initialization** using scripts such as `schema.sql`/`data.sql` and **versioned database migrations** using Flyway or Liquibase. Both can run SQL on application startup, yet they solve two different problems:

- SQL initialization primarily loads a set of initialization scripts according to startup configuration.
- Versioned migrations manage schema changes by version, record which changes have already been applied, and continue from the database's current state.

Understanding the difference accurately helps prevent re-running table-creation scripts against a database that already has data, prevents two tools from modifying the same schema simultaneously, and ensures application versions can be deployed safely.

## 1. Database Schema in Spring Data JDBC

Suppose the domain has a `Customer` aggregate root:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String name,
    String email,
    boolean active
) {}
```

Repository:

```java
public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {
}
```

Spring Data JDBC uses mapping metadata to generate SQL for reading and writing the aggregate. However, the `customers` table must exist with compatible columns and types:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

Spring Data JDBC does not automatically create schemas from entities like an ORM with schema generation. Mappings describe how objects correspond to the schema; the schema must be prepared by scripts, migrations, or a separate database provisioning process.

Besides root tables, the schema may require:

- Child tables and foreign keys for collections mapped with `@MappedCollection`.
- Version columns for optimistic locking when using `@Version`.
- Unique constraints protecting invariants.
- Indexes for common queries.
- Database-managed defaults, triggers, and generated columns.
- Tables supporting auditing or outbox patterns.

These database objects are part of the persistence contract. They need to be managed alongside the application's source code.

## 2. What Is SQL Initialization?

SQL initialization is a mechanism to run one or more SQL scripts when Spring Boot initializes the datasource/application context. Scripts are typically used to:

- Create an initial schema.
- Create tables and indexes for a fresh database.
- Load sample data or reference data.
- Prepare an embedded database for development/testing.

Spring Boot supports default scripts named `schema.sql` and `data.sql`. They can be placed on the classpath, usually in `src/main/resources`.

Example layout:

```text
src/main/resources/
├── schema.sql
└── data.sql
```

`schema.sql` contains DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

`data.sql` contains initialization data:

```sql
INSERT INTO customers (name, email, active)
VALUES
    ('An Nguyen', 'an@example.test', TRUE),
    ('Binh Tran', 'binh@example.test', TRUE);
```

When script initialization is enabled, Spring Boot runs schema scripts before data scripts so tables are created before data is inserted.

### 2.1. SQL Initialization Is Not a Migration History

These scripts describe the state to initialize at startup time. Spring Boot does not treat every edit to `schema.sql` as a new migration version, nor does it store a history of individual schema changes.

For example, after the application has run once, a developer edits `schema.sql` to add a column:

```sql
ALTER TABLE customers ADD COLUMN phone VARCHAR(30);
```

If the script runs again against a database that already has the table, the initial `CREATE TABLE` statement may fail because the table already exists. If you only append an ALTER statement at the end, the next startup may try adding the same column again and fail.

You can write idempotent DDL such as `CREATE TABLE IF NOT EXISTS` or check object existence before creating. However, that does not replace versioned migrations: the script still does not record which changes the database has undergone, in what order, or how existing data should be transformed.

## 3. Configuring SQL Initialization in Spring Boot

Spring Boot provides properties under the `spring.sql.init` prefix.

Example:

```yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:/db/init/schema.sql
      data-locations: classpath:/db/init/data.sql
      continue-on-error: false
```

Commonly used properties:

| Property | Meaning |
| --- | --- |
| `spring.sql.init.mode` | Controls whether initialization scripts run. |
| `spring.sql.init.schema-locations` | Locations of DDL scripts that create/update the schema. |
| `spring.sql.init.data-locations` | Locations of scripts that load data. |
| `spring.sql.init.platform` | Platform name used to select database-specific scripts. |
| `spring.sql.init.continue-on-error` | Whether to continue on script error or halt startup. |
| `spring.sql.init.encoding` | Character encoding of script files. |
| `spring.sql.init.separator` | Statement separator character in scripts. |

### 3.1. Choosing the Mode

`spring.sql.init.mode` accepts the following values:

| Value | Behavior |
| --- | --- |
| `embedded` | Runs initialization only for embedded databases. This is the typical default. |
| `always` | Runs scripts even for non-embedded databases such as PostgreSQL/MySQL. |
| `never` | Disables initialization scripts. |

For example, when you want Spring Boot to run scripts against PostgreSQL in development:

```yaml
spring:
  sql:
    init:
      mode: always
```

In production using a migration tool, SQL initialization is typically disabled:

```yaml
spring:
  sql:
    init:
      mode: never
```

Avoid setting `always` globally and shipping table-creation or sample-data scripts to production without knowing their impact when the application restarts multiple times.

### 3.2. Selecting Scripts by Database Platform

You can declare:

```yaml
spring:
  sql:
    init:
      mode: always
      platform: postgresql
```

Spring Boot can look for generic scripts and platform-specific scripts, for example:

```text
src/main/resources/
├── schema.sql
├── data.sql
├── schema-postgresql.sql
└── data-postgresql.sql
```

This is useful when development uses multiple databases with differing DDL syntax. However, as the number of schema changes grows, maintaining multiple parallel sets of initialization scripts becomes difficult to manage. Versioned migrations are usually better suited for schemas evolving over time.

### 3.3. Continue on Error

By default, script initialization stops on error. You can set `continue-on-error` to proceed, but never enable it merely to hide schema errors.

For instance, if a `CREATE TABLE` statement fails yet `data.sql` keeps trying to insert, the application may start with an improperly prepared database. For important schema scripts, failing fast helps catch misconfigurations earlier.

### 3.4. Custom Script Locations

You can organize scripts in dedicated folders:

```yaml
spring:
  sql:
    init:
      schema-locations: classpath:/db/init/schema.sql
      data-locations: classpath:/db/init/reference-data.sql
```

If multiple files are needed, declare multiple resource locations using Spring Boot property syntax. Check the exact resource path inside the packaged artifact; a file present in the source tree but missing from the JAR classpath cannot be read at startup.

## 4. What Is a Versioned Migration?

A versioned migration is a database change named/identified by version and tracked by a migration tool once applied.

Suppose an application evolves its schema through these steps:

1. Create the `customers` table.
2. Add a `phone` column.
3. Add an index on `email`.
4. Add an email verification status column.
5. Backfill old data and add a constraint.

Instead of editing a single schema file, each step is stored as a separate migration:

```text
src/main/resources/db/migration/
├── V1__create_customers.sql
├── V2__add_phone_to_customers.sql
├── V3__add_email_index.sql
└── V4__add_email_verified.sql
```

The migration tool reads the files, determines which versions have already run, and applies the missing versions in order. It stores metadata in a history table inside the database.

This creates an auditable history: which schema version the database has reached and via which migrations.

## 5. Flyway with Spring Boot

Flyway is a popular migration tool in Spring Boot applications. When you add the Flyway dependency matching your Spring Boot and database versions, Boot can auto-configure Flyway to run migrations when the application context starts.

Default versioned SQL files typically live in:

```text
src/main/resources/db/migration/
```

Example:

```text
V1__create_customers.sql
V2__add_phone_to_customers.sql
V3__create_customer_status_index.sql
```

The naming convention typically follows:

- `V`: versioned migration.
- Version number: ordering/version identifier.
- `__`: double-underscore separator between version and description.
- Description: brief explanation of the change.

### 5.1. First Migration

`V1__create_customers.sql`:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

### 5.2. Subsequent Migrations

`V2__add_phone_to_customers.sql`:

```sql
ALTER TABLE customers
ADD COLUMN phone VARCHAR(30);
```

`V3__create_customer_status_index.sql`:

```sql
CREATE INDEX idx_customers_active
ON customers(active);
```

Each file represents an independent change. Once a database has applied V1 and V2, the next run only needs to apply V3 if no newer migrations exist.

### 5.3. Flyway Schema History Table

Flyway stores executed migration info in a history table, usually `flyway_schema_history`. This table records version, description, checksum, execution timestamp, and execution status.

Checksums help detect when an already-applied migration file has had its contents modified afterward. A key principle is **do not modify versioned migrations that have already run in shared/production environments**. When further changes are needed, create a new versioned migration.

If an older migration has not yet been applied to any shared database, the team may choose to revise it under internal development workflows. Once released, however, migration history should be treated as immutable.

### 5.4. Configuring Flyway

Spring Boot example:

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
```

Commonly used properties:

| Property | Meaning |
| --- | --- |
| `spring.flyway.enabled` | Enables/disables Flyway auto-configuration. |
| `spring.flyway.locations` | Migration locations. |
| `spring.flyway.schemas` | Database schemas managed by Flyway as configured. |
| `spring.flyway.table` | Name of the migration history table. |
| `spring.flyway.baseline-on-migrate` | Allows baselining a non-empty database as configured. |

Check specific property names and options against the Spring Boot/Flyway version you are using. Do not enable `baseline-on-migrate` merely to bypass migration errors on an existing database; baselining requires a process to verify the prior schema state.

## 6. Liquibase with Spring Boot

Liquibase also manages schema changes by version, but defines changes primarily using changelogs and changesets.

A typical layout:

```text
src/main/resources/db/changelog/
├── db.changelog-master.yaml
└── changes/
    ├── 001-create-customers.yaml
    └── 002-add-phone.yaml
```

The master changelog can include child files:

```yaml
databaseChangeLog:
  - include:
      file: changes/001-create-customers.yaml
      relativeToChangelogFile: true
  - include:
      file: changes/002-add-phone.yaml
      relativeToChangelogFile: true
```

A changeset creating a table:

```yaml
databaseChangeLog:
  - changeSet:
      id: 001-create-customers
      author: app-team
      changes:
        - createTable:
            tableName: customers
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: name
                  type: VARCHAR(160)
                  constraints:
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(255)
                  constraints:
                    nullable: false
                    unique: true
```

Liquibase identifies a changeset by attributes such as `id`, `author`, and changelog path. Executed changesets are recorded in the `DATABASECHANGELOG` table; Liquibase also uses the `DATABASECHANGELOGLOCK` table to coordinate changelog execution.

### 6.1. Configuring Liquibase

Example:

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:/db/changelog/db.changelog-master.yaml
```

Liquibase can define schema changes using YAML, XML, JSON, or SQL changelogs. Choosing a format mainly depends on team preferences, review needs, and change expressiveness.

### 6.2. Changesets and Checksums

Liquibase tracks executed changesets and their checksums. Do not modify already-deployed changesets to alter historical outcomes. Create a new changeset for the next change, unless handling an unreleased development scenario under an explicit workflow.

Liquibase supports changeset-level rollback when a rollback definition is provided or can be inferred for certain change types. However, not every SQL change can be rolled back automatically and safely. For data deletions or irreversible transformations, design dedicated rollback/restore plans.

## 7. Comparing SQL Initialization, Flyway, and Liquibase

| Criterion | SQL initialization | Flyway | Liquibase |
| --- | --- | --- | --- |
| Primary goal | Initialize schema/data at startup | Manage migrations by version | Manage schema changes via changelogs/changesets |
| Format | SQL scripts | SQL or Java migrations depending on config | YAML, XML, JSON, SQL |
| History tracking | No standard migration history | History table | `DATABASECHANGELOG` table |
| Ordering of changes | By configured scripts/resources | By migration version | By changeset/changelog order |
| Detects edits to applied files | No equivalent built-in migration checksum | Checksum | Changeset checksum |
| Best fit | Embedded DBs, tests, simple bootstrapping | Schemas evolving sequentially by version | Schemas needing multi-format changelogs and changeset metadata |
| Rollback | Developer writes/coordinates manually | Needs suitable rollback strategy; not all SQL is reversible by default | Rollback support depending on change type and rollback definition |
| Existing production data | Does not manage version transitions automatically | Baseline/migration history | Baseline/changelog sync by workflow |

The biggest difference is that **migration tools manage database change history**, whereas SQL initialization simply executes scripts based on startup configuration.

Flyway and Liquibase solve similar problems and should not run simultaneously to manage the same schema. Pick one tool as the source of truth for database migrations.

## 8. Do Not Run Multiple Schema-Creation Mechanisms in Parallel

A common configuration mistake is having all of these active at once:

- `schema.sql` creating tables.
- Flyway running `V1__create_tables.sql` creating the same tables.
- Liquibase running changelogs creating the same tables.

The result can be "table already exists" errors, double-seeded data, or inconsistent schema states across environments.

If a project chooses Flyway:

```yaml
spring:
  sql:
    init:
      mode: never
  flyway:
    enabled: true
```

If it chooses Liquibase:

```yaml
spring:
  sql:
    init:
      mode: never
  liquibase:
    enabled: true
```

You may keep fixture-loading scripts for tests or reference data, provided schema ownership and execution order are clearly separated. Avoid letting SQL initialization and a migration tool create/modify the same set of tables.

In particular, do not use `data.sql` to seed production business data on every application startup. Required reference data can be managed via migrations or a separate idempotent seeding process.

## 9. Which Approach to Choose for Each Environment?

A common breakdown:

| Environment | Approach |
| --- | --- |
| Unit tests without a database | No schema initialization needed. |
| Test slices using an embedded database | Can use `schema.sql`/`data.sql` or migrations if testing the real schema. |
| PostgreSQL/MySQL integration tests | Run migrations on Testcontainers to verify the exact dialect. |
| Fresh local development | Versioned migrations keep the local database in sync with code. |
| Staging/production | Flyway or Liquibase manages the schema before code depending on changes runs. |
| One-off demo database | SQL initialization can be simple and sufficient. |

### 9.1. SQL Initialization for Tests

Test slice example:

```java
@DataJdbcTest
class CustomerRepositoryTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void savesAndReadsCustomer() {
        Customer saved = customers.save(
            new Customer(null, "An Nguyen", "an@example.test", true)
        );

        assertThat(customers.findById(saved.id()))
            .contains(saved);
    }
}
```

When using an embedded database and schema scripts, Boot can run initialization under the default mode. If you want to test migrations, add the Flyway/Liquibase dependency and run the same migrations as production. Avoid letting both mechanisms create overlapping schemas.

### 9.2. Integration Tests with Testcontainers

When production uses PostgreSQL, testing migrations on a PostgreSQL container catches DDL, data type, index, and constraint differences:

```java
@Testcontainers
@DataJdbcTest
@AutoConfigureTestDatabase(
    replace = AutoConfigureTestDatabase.Replace.NONE
)
class CustomerPostgresMigrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void configure(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

The example illustrates datasource configuration. The project needs the Testcontainers PostgreSQL dependency, Flyway or Liquibase if testing migrations, and a container version matching production.

## 10. Migrations That Change Schema and Data

Migrations do more than create tables. They also have to migrate old data into the new structure.

Suppose the `customers` table initially only has:

```sql
CREATE TABLE customers (
    id BIGINT PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);
```

A later version needs a required email. You should not simply add a `NOT NULL` column if the table already holds rows without email values.

A safer strategy:

### Step 1: Expand — Add a Nullable Column

```sql
ALTER TABLE customers
ADD COLUMN email VARCHAR(255);
```

### Step 2: Backfill Existing Data

```sql
UPDATE customers
SET email = CONCAT('legacy-', id, '@example.invalid')
WHERE email IS NULL;
```

The backfill value is only an example; real data requires valid business rules, and fake addresses should not be fabricated if email is used for authentication.

### Step 3: Deploy Compatible Code

New code can read both old and new rows during the transition period, or write email for new records. If a rolling deployment runs multiple application versions simultaneously, ensure old code does not fail once the schema is expanded.

### Step 4: Tighten the Constraint Once Data Is Valid

```sql
ALTER TABLE customers
ALTER COLUMN email SET NOT NULL;
```

Constraint-alteration syntax depends on the database. Only apply `NOT NULL` after backfilling and verifying no NULLs remain.

This is an example of an **expand-and-contract migration**: expand the schema so old and new code both work, migrate data and traffic, and only then remove old structures or tighten constraints.

## 11. Principles for Writing Safe Migrations

A good migration should:

- Have a clear scope of change and a descriptive name.
- Be independently reviewable in code review.
- Be tested on the target database/dialect.
- Never alter the contents of migrations already applied in shared environments.
- Account for table lock duration and impact on large datasets.
- Include a backfill and rollback/restore plan if needed.
- Be compatible with application deployment order.
- Run through the same workflow across local, CI, staging, and production.

### 11.1. Do Not Bundle Unrelated Changes

A migration may contain multiple statements required for a single business change, but avoid bundling unrelated changes into one massive file. Small, focused migrations make debugging and understanding schema history much easier.

### 11.2. Do Not Edit Released Migrations

Suppose `V2__add_phone_to_customers.sql` has already run on staging and production. If you later discover the column type needs to change, create `V4__change_phone_type.sql` or the next appropriate version. Do not edit V2 expecting databases that already ran it to pick up the new contents.

Migration tools typically store checksums. Editing an already-executed file can cause Flyway/Liquibase to report a checksum mismatch or require deliberate repair operations. Do not use repair to conceal improperly altered migration history.

### 11.3. DDL Transactions Depend on the Database

Some databases support transactional DDL for many statements; certain statements or databases may auto-commit or have transaction limits. Therefore, rolling back a migration does not always return the database to its exact pre-migration state.

For high-risk migrations, have a backup/restore strategy and rehearse on a data copy close to production size.

## 12. Spring Data JDBC Mapping Must Evolve Alongside Migrations

A domain model change usually entails a schema change.

For example, adding a property:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String name,
    String email,
    @Column("email_verified") boolean emailVerified
) {}
```

The corresponding migration needs to create the `email_verified` column:

```sql
ALTER TABLE customers
ADD COLUMN email_verified BOOLEAN NOT NULL DEFAULT FALSE;
```

In this example, the default gives existing rows a valid value if the database supports and applies the default per the DDL statement. After the migration, Spring Data JDBC can read/write the new property.

When changing mappings, check synchronization across:

- Table and column names.
- SQL types compatible with Java types.
- Nullability.
- ID and version columns.
- Foreign keys for aggregate children.
- Indexes and unique constraints.
- Defaults, triggers, and generated columns.
- Converters when stored data differs from domain types.

An entity compiling cleanly does not prove the production schema is compatible.

## 13. Managing Reference Data and Sample Data

Distinguish three categories of data:

| Data type | Example | Recommended management |
| --- | --- | --- |
| Schema structure | Tables, columns, indexes, constraints | Flyway/Liquibase or provisioning tools. |
| Required reference data | Countries, standard status types, default permissions | Versioned migrations or controlled seeding workflow. |
| Test/demo fixtures | A few sample customers for tests/UI demos | Test fixtures, `@Sql`, factories, or profile-specific scripts. |

Do not let a `data.sql` containing demo data run in every environment, especially production. Demo data can cause unique key collisions, pollute reports, or create unwanted accounts.

For reference data, migrations can insert required values and track them alongside schema versions. If operators edit that data frequently, define clear ownership and a dedicated sync mechanism; do not overwrite operational changes on every migrate.

## 14. Checking Schema State and Startup

When the application starts, establish a clear sequence:

1. Database is ready to accept connections.
2. Migration tool inspects history and applies missing migrations.
3. Spring Data JDBC repositories initialize and use a compatible schema.
4. Application begins serving traffic.

With SQL initialization, scripts must run in the proper order and mode. With Flyway/Liquibase, migrations must complete before code executes queries relying on the new schema.

In systems where multiple application instances start concurrently, migration tools use history/locking mechanisms to stop instances from arbitrarily re-running the same migration. Even so, organize deployments so migrations do not cause prolonged locks or unexpected downtime.

If a migration fails, the application should fail startup or refuse traffic rather than continuing to run against an incompatible schema.

## 15. Common Pitfalls

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Startup reports table already exists | `schema.sql` re-ran on an already-populated DB or multiple mechanisms create the schema. | Designate one schema owner; use migrations for long-lived changes. |
| Startup fails with duplicate key running `data.sql` | Seed script re-ran against existing data. | Use test fixtures or controlled idempotent seeding. |
| Edited `schema.sql` but old database was not updated | SQL initialization does not track schema version history. | Create a new migration. |
| Flyway reports checksum mismatch | Already-executed migration file was modified. | Restore the old migration and create a new one; only repair intentionally. |
| Liquibase reports changeset changed | Changeset checksum differs from previous run. | Do not edit deployed changesets; create a new changeset. |
| Repository fails with missing column | New mapping deployed before column-creation migration. | Deploy compatible migration before code relying on the column. |
| Production has old rows and adding NOT NULL fails | Values were not backfilled before tightening constraint. | Expand nullable, backfill, verify, then set NOT NULL. |
| H2 tests pass but PostgreSQL fails | DDL, types, functions, or constraints differ by dialect. | Run migration tests on the exact database using Testcontainers. |
| Flyway and Liquibase both modify tables | Two migration tools managing one schema. | Choose a single source of truth for schema migrations. |
| SQL init runs unexpectedly in production | `spring.sql.init.mode` set to `always` or shared profile. | Disable with `never` in migration-managed environments. |
| Migration takes too long during deploy | Large backfill or lock-holding DDL. | Split migrations, batch backfills, and rehearse on production-like data. |

## 16. Selection and Implementation Workflow

When designing a schema for a Spring Data JDBC application:

1. Identify the environment and purpose: ephemeral database, tests, demo, or long-lived data.
2. For simple one-off schemas, consider `schema.sql`/`data.sql`.
3. For schemas evolving across multiple versions, choose Flyway or Liquibase.
4. Designate a single tool as the source of truth for schema changes.
5. Store migrations in source control alongside code.
6. Write focused migrations per change and never edit released files.
7. Backfill data before adding mandatory constraints.
8. Use expand-and-contract when rolling deployments are needed.
9. Run migrations in CI and integration tests with the target database/dialect.
10. Ensure migrations complete before the application serves traffic.
11. Disable SQL initialization in environments already managed by a migration tool.
12. Manage test fixtures and reference data with separate ownership.

> **SQL initialization prepares a database using scripts executed per startup configuration; versioned migrations record and apply individual schema changes according to version history.** With Spring Data JDBC, use simple scripts for ephemeral databases or suitable tests, and use Flyway/Liquibase to manage long-lived evolving schemas across environments. Never let multiple mechanisms create or modify the same schema simultaneously.
