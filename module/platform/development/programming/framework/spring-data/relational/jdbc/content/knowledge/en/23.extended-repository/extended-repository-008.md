# Keeping Mapping and Transaction Rules Synchronized Between Generated Code and Hand-Written SQL

In **Spring Data JDBC**, repositories and **JdbcAggregateTemplate** can generate SQL from aggregate metadata. When specialized operations are needed, applications can also write SQL directly using **@Query**, **JdbcTemplate**, or **NamedParameterJdbcTemplate**. Both approaches can coexist in one application, provided they share a single data contract: table/column names, data types, IDs, versions, aggregate relationships, and transaction boundaries.

The critical point is that **hand-written SQL does not automatically inherit all behaviors of the aggregate save path**. A direct JDBC statement only executes what the SQL specifies. It does not automatically apply mapping metadata, custom converters, entity callbacks, auditing, optimistic locking, or child collection synchronization like **repository.save(...)**. Authors must identify which parts Spring Data manages and which parts must be handled explicitly.

This lesson explains how to coordinate both data access paths so data stays consistent, transactions roll back together, and mapping rules never drift apart.

## 1. Two SQL Execution Paths in the Same Application

Spring Data JDBC applications typically have two groups of operations:

1. **Spring Data generated SQL**: CRUD repositories or **JdbcAggregateTemplate** use entity/aggregate metadata to generate statements. The framework understands **@Table**, **@Column**, **@Id**, **@Version**, embedded objects, and mapped collections.
2. **Application-written SQL**: **@Query**, repository fragments using **JdbcTemplate**, or other JDBC code execute developer-defined statements. This path fits specialized queries/bulk updates, audit logging, reporting, or integrating legacy tables.

~~~mermaid
flowchart TD
    A[Application Service] --> B[Spring Data Repository / JdbcAggregateTemplate]
    A --> C[Custom Repository Fragment / JdbcTemplate]
    B --> D[Mapping metadata + generated SQL]
    C --> E[Application-written SQL]
    D --> F[Spring-managed DataSource / transaction]
    E --> F
    F --> G[(Database)]
~~~

Both paths can participate in the same transaction if they use **the same Spring-managed DataSource and transaction manager**. However, they do not offer the same level of automation:

| Capability | Repository / Aggregate Template | SQL via JdbcTemplate |
|---|---|---|
| Uses entity metadata | Yes | Not automatic |
| Generates table/column names | Yes, per mapping | Developer writes physical identifiers |
| Converts types per Spring Data mapping | Yes | Usually must bind/map JDBC types explicitly |
| Saves aggregates and children per mapping | Yes | Only performs what the SQL specifies |
| Generated ID on aggregate insert | Supported by mechanism | Must retrieve generated key manually if needed |
| Optimistic locking via @Version | Yes, on standard aggregate save path | Must write version predicate and increment manually |
| Entity callbacks/auditing | Integrated in appropriate Spring Data paths | Does not run automatically just by sharing DataSource |
| Transactions | Participates in Spring transactions | Participates if sharing DataSource/transaction manager |

Do not treat the two approaches as equivalent implementations. They are two different abstraction levels over the same database.

## 2. Mapping Metadata Is the Shared Contract with the Schema

Example aggregate root:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        @Version Long version,
        @Column("display_name") String name,
        String email,
        boolean active
) {}
~~~

Corresponding DDL:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    display_name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
~~~

The metadata specifies:

- **@Table("customers")** maps the aggregate root to the **customers** table.
- **@Id** identifies the primary key **id**.
- **@Version** marks the version column used for optimistic locking.
- **@Column("display_name")** maps the Java property **name** to the physical column **display_name**.
- **email** and **active** use column names derived by the default naming strategy in the example.

The repository can use auto-generated CRUD:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {
}
~~~

When Spring Data generates SQL, it consults metadata to know which columns to read/write. When writing SQL manually, you must use **the actual database table and column names**, not Java property names when they differ.

For example, direct SQL must use **display_name**:

~~~sql
UPDATE customers
SET display_name = ?
WHERE id = ?;
~~~

Do not write **SET name = ?** just because the record property is named **name**. **@Column** does not rewrite SQL that the developer wrote by hand.

## 3. Which Rules Does the Automatic Save Path Preserve?

With the operation:

~~~java
Customer current = customers.findById(id).orElseThrow();

Customer changed = new Customer(
        current.id(),
        current.version(),
        "New Name",
        current.email(),
        current.active()
);

Customer saved = customers.save(changed);
~~~

Spring Data JDBC uses mapping metadata to generate the appropriate **UPDATE** statement. For entities with **@Version**, the statement includes the old version predicate and sets the new version. Conceptually, the SQL is equivalent to:

~~~sql
UPDATE customers
SET display_name = ?,
    email = ?,
    active = ?,
    version = ?
WHERE id = ?
  AND version = ?;
~~~

Exact column ordering and syntax depend on dialect, but the framework manages property mapping, value binding, and optimistic locking on the standard aggregate save path.

Additionally, depending on application configuration, the Spring Data path can integrate:

- Custom conversions registered with Spring Data Relational.
- Entity callbacks and lifecycle events.
- Auditing annotations such as **@CreatedDate**, **@LastModifiedDate**, **@CreatedBy**, and **@LastModifiedBy**.
- Mapping for embedded properties and collections belonging to the aggregate.
- Mechanisms to retrieve database-generated IDs.

When moving an operation from **repository.save(...)** to direct SQL, determine which behaviors from that list are still required and enforce them yourself.

## 4. Hand-Written SQL Uses Physical Names and Parameter Binding

Suppose you need to record customer change history in an audit table:

~~~sql
CREATE TABLE customer_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    event_type VARCHAR(40) NOT NULL,
    customer_version BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT fk_customer_audit_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);
~~~

This is a separate audit table, not a property of the **Customer** aggregate. A custom repository fragment can use **NamedParameterJdbcTemplate**:

~~~java
public interface CustomerAuditOperations {
    int insertAudit(Long customerId, String eventType, Long version);
}
~~~

Implementation:

~~~java
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;

public class CustomerAuditOperationsImpl
        implements CustomerAuditOperations {

    private final NamedParameterJdbcTemplate jdbc;

    public CustomerAuditOperationsImpl(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public int insertAudit(
            Long customerId,
            String eventType,
            Long version
    ) {
        String sql = """
            INSERT INTO customer_audit (
                customer_id,
                event_type,
                customer_version,
                created_at
            )
            VALUES (
                :customerId,
                :eventType,
                :version,
                CURRENT_TIMESTAMP
            )
            """;

        var parameters = new MapSqlParameterSource()
                .addValue("customerId", customerId)
                .addValue("eventType", eventType)
                .addValue("version", version);

        return jdbc.update(sql, parameters);
    }
}
~~~

Repository combining CRUD and fragments:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                CustomerAuditOperations,
                CustomerSqlOperations {
}
~~~

For custom fragments, implementations are typically named after the fragment plus the **Impl** postfix—here **CustomerAuditOperationsImpl**. Spring Data composes the fragment implementation into the repository proxy.

Input values are bound using named parameters. This lets the driver handle JDBC types and avoids concatenating user data directly into SQL strings. Table/column names remain developer-managed identifiers.

## 5. Keeping Operations in the Same Transaction

A use case may both update an aggregate via a repository and write an audit entry via hand-written SQL. If both operations must succeed or fail together, place the transaction on the application service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer rename(Long id, String newName) {
        Customer current = customers.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Customer not found"));

        Customer changed = new Customer(
                current.id(),
                current.version(),
                newName,
                current.email(),
                current.active()
        );

        Customer saved = customers.save(changed);

        int auditRows = customers.insertAudit(
                saved.id(),
                "RENAMED",
                saved.version()
        );

        if (auditRows != 1) {
            throw new IllegalStateException(
                    "Expected one audit row, got " + auditRows);
        }

        return saved;
    }
}
~~~

In standard Spring configurations, JDBC repositories and **NamedParameterJdbcTemplate** share the Spring-managed DataSource. When both participate in the same transaction manager, the repository's **UPDATE** and the audit **INSERT** join the same transaction.

Outcome:

- If both updating the customer and writing the audit succeed, the transaction commits both.
- If writing the audit fails and the exception rolls back the transaction, the customer change also rolls back.
- If the use case throws an error after both statements but before commit, both changes still roll back with the transaction.

Never call **Connection.commit()** or open an independent connection inside a fragment. Doing so can detach manual SQL from the transaction Spring is managing.

### Conditions for Sharing a Transaction

Ensure that:

1. The repository and **JdbcTemplate/NamedParameterJdbcTemplate** use the same DataSource.
2. Operations are coordinated by the same transaction manager bound to that DataSource.
3. The service method executes inside a Spring transaction activated by **@Transactional**.
4. JDBC code uses Spring templates, rather than opening its own connection and committing independently.
5. Operations are not dispatched to another thread while expecting the thread-bound transaction to propagate automatically.

If the application uses multiple DataSources, each source may have its own transaction manager. Two operations across two different DataSources do not automatically become one atomic transaction merely by sharing a **@Transactional** method. When consistency across multiple systems/databases is needed, design distributed transactions or a transactional outbox/saga as required.

## 6. Directly Updating an Aggregate Must Maintain Optimistic Locking Manually

Sometimes hand-written SQL must update a column on the aggregate root itself. If the root uses **@Version**, direct SQL must enforce version rules itself.

Example adding a method to a custom fragment:

~~~java
public interface CustomerSqlOperations {
    int updateEmailIfVersionMatches(
            Long id,
            Long expectedVersion,
            String newEmail
    );
}
~~~

Implementation:

~~~java
@Override
public int updateEmailIfVersionMatches(
        Long id,
        Long expectedVersion,
        String newEmail
) {
    String sql = """
        UPDATE customers
        SET email = :email,
            version = version + 1
        WHERE id = :id
          AND version = :expectedVersion
        """;

    var parameters = new MapSqlParameterSource()
            .addValue("id", id)
            .addValue("expectedVersion", expectedVersion)
            .addValue("email", newEmail);

    return jdbc.update(sql, parameters);
}
~~~

This SQL statement handles three things explicitly:

1. Finds the exact root by **id**.
2. Updates only if the database version still equals **expectedVersion**.
3. Increments the version upon successful update.

The service interprets the update count:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.transaction.annotation.Transactional;

@Transactional
public Customer changeEmailWithSql(
        Long id,
        Long expectedVersion,
        String newEmail
) {
    int affected = customers.updateEmailIfVersionMatches(
            id,
            expectedVersion,
            newEmail
    );

    if (affected == 0) {
        throw new OptimisticLockingFailureException(
                "Customer no longer has the expected version");
    }

    if (affected != 1) {
        throw new IllegalStateException(
                "Expected one updated customer, got " + affected);
    }

    return customers.findById(id).orElseThrow();
}
~~~

After the SQL statement, re-read the aggregate to obtain the updated email and new version from the database. Direct SQL does not automatically update an in-memory **Customer** object.

Without checking and incrementing version, a stale request can overwrite newer changes undetected by optimistic locking. Never assume that annotating the entity with **@Version** causes Spring Data JDBC to rewrite custom **UPDATE** statements automatically.

### When to Prefer save Over Direct Updates?

If an operation merely changes normal aggregate state without special SQL requirements, the safer path is usually:

1. Load the root.
2. Invoke domain behavior to produce the new state.
3. Call **repository.save(...)**.
4. Use the returned object to obtain the new version.

Use direct updates when there is a specific reason—such as bulk operations, specialized SQL expressions, or measured optimizations—and when you have explicitly designed how version, auditing, and side effects are preserved.

## 7. Manual Mapping Must Match Converters and Data Types

Spring Data JDBC can use custom converters to translate domain types to storage types. When using **JdbcTemplate**, do not assume Spring Data converters run automatically for every parameter and **ResultSet** processed by JdbcTemplate.

For example, suppose an entity has an enum:

~~~java
enum CustomerStatus {
    ACTIVE, SUSPENDED
}
~~~

If Spring Data mapping stores the enum by name, direct SQL must pass the corresponding value:

~~~java
parameters.addValue("status", CustomerStatus.ACTIVE.name());
~~~

If the application uses a converter storing codes **A/S**, manual SQL must also use those exact codes or call a shared mapper/conversion component. Otherwise, the repository path may expect **ACTIVE** while the hand-written SQL path writes **A**, or vice versa.

Points that must align:

| Data | Spring Data Mapping | Hand-Written SQL Caution |
|---|---|---|
| Enum | Custom converter or default storage rule | Bind the exact physical value stored by schema |
| BigDecimal | Appropriate converter/JDBC type | Preserve precision/scale; avoid converting via double |
| Date/time | Converters and temporal types | Use matching DATE, TIMESTAMP, and timezone semantics |
| UUID | Converter/driver/database type | Use matching physical type and binding |
| Value object | Converter or embedded mapping | Convert manually if SQL accesses value object columns |
| Nullable properties | Mapped to wrappers/references | Do not bind primitives/defaults instead of NULL unintentionally |

When manual SQL reads data back into objects, **RowMapper** must convert values according to the same domain rules. Never have two conflicting interpretations of the same column across two code paths.

## 8. Embedded Objects and Column Prefixes

An **@Embedded** object is flattened into columns in the root table. For example:

~~~java
public record Address(String street, String city) {}

@Table("customers")
public record Customer(
        @Id Long id,
        @Embedded(prefix = "shipping_") Address shippingAddress
) {}
~~~

DDL:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100)
);
~~~

Repositories/aggregate templates understand embedded metadata and map the **Address** object via **shipping_street** and **shipping_city**.

Hand-written SQL must use those physical names:

~~~sql
UPDATE customers
SET shipping_street = :street,
    shipping_city = :city
WHERE id = :id;
~~~

Do not treat **shippingAddress** as a hypothetical JSON column, and do not reference **street** if the DDL lacks that column. If the embedded object uses **USE_NULL/USE_EMPTY** semantics, manual SQL must also preserve the meaning of the column group when all columns are null; an **UPDATE** statement itself does not apply Spring Data's object instantiation policy.

## 9. Child Collections and Aggregate Boundaries

Spring Data JDBC manages aggregates by root. With **@MappedCollection**, metadata describes the child table, the ID column referencing the root, and optionally a key/index column. When saving the root through a repository, the framework knows how to synchronize the collection per the mapping.

For example:

~~~java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
        List<OrderLine> lines
) {}

@Table("order_lines")
public record OrderLine(String sku, int quantity) {}
~~~

Direct SQL updating a row in **order_lines** affects only the specified row. It does not synchronize the collection the way **repository.save(order)** does. An aggregate save can replace child rows according to the current collection state, meaning direct SQL and a subsequent save can overwrite or wipe out changes if both paths do not share a consistent state view.

Before writing direct SQL against a child table, answer:

- Does the child truly belong to the aggregate root's lifecycle?
- Are **order_id** and **line_no** preserved properly?
- Could it violate invariants between order lines and order totals?
- Could a subsequent **save(root)** overwrite the child rows just modified?
- Is root locking/versioning needed to prevent concurrent updates?

If the child belongs to the aggregate, prefer modifying the collection on the root and saving the root. Only update child tables directly when the write path is designed to coordinate with the aggregate, versioning, transactions, and invariants. If the child genuinely has an independent lifecycle, consider modeling it as a separate aggregate instead of bypassing ownership boundaries.

## 10. Entity Callbacks and Auditing Do Not Run Automatically with Arbitrary JDBC SQL

Spring Data JDBC can integrate entity callbacks and auditing into Spring Data-managed persistence operations. For example, auditing can populate **createdAt** or **lastModifiedAt** before saving.

A statement like:

~~~sql
UPDATE customers
SET display_name = :name
WHERE id = :id;
~~~

executed through **JdbcTemplate** does not invoke aggregate callbacks. Nor does it update **last_modified_at** just because the entity has **@LastModifiedDate**.

If direct SQL must maintain auditing, include those columns in the statement:

~~~sql
UPDATE customers
SET display_name = :name,
    last_modified_at = CURRENT_TIMESTAMP
WHERE id = :id;
~~~

If the system uses auditor fields such as **lastModifiedBy**, the SQL must receive the actor from business context and bind it explicitly. Keep timezone, clock, and default value rules aligned with the automatic save path.

Do not assume database defaults, triggers, and Spring auditing always produce the exact same value. Pick one clear source of truth or ensure cooperating mechanisms do not overwrite one another.

## 11. Distinguishing @Query from JdbcTemplate

Hand-written SQL can appear at several levels:

| Approach | Who Manages Execution? | Result Mapping |
|---|---|---|
| Derived repository method | Spring Data repository | By property and metadata |
| @Query on repository | Spring Data repository infrastructure | By supported return type and mapping |
| @Modifying @Query | Spring Data repository infrastructure executes DML | Usually returns update count or void; does not return updated entity automatically |
| Custom fragment + JdbcTemplate | Application fragment code | Handled by RowMapper/ResultSetExtractor or custom code |
| JdbcAggregateTemplate | Spring Data JDBC aggregate infrastructure | By aggregate metadata |

**@Query** still runs through repository infrastructure, yet the SQL and identifiers are developer-defined. Do not mistakenly assume that because a method sits on a repository, all **save** rules apply automatically to a custom **UPDATE** statement.

**JdbcTemplate** is lower-level: the application directly controls SQL, parameters, RowMappers, and affected row counts. In exchange, the application takes greater responsibility for mapping and lifecycle handling.

## 12. @Modifying and Update Counts

A modifying query can return the affected row count:

~~~java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE id = :id
    """)
int deactivate(@Param("id") Long id);
~~~

The update count can be:

- **1**: one row reported as affected.
- **0**: no rows reported as affected; the ID may not exist, predicates may not match, or the version may be stale.
- **Greater than 1**: multiple rows affected; possibly expected for bulk queries, but unexpected if targeting a single root.

For custom SQL using **JdbcTemplate**, **update(...)** also returns the affected row count. Interpret the count based on the **WHERE** predicates and database/driver semantics. Do not automatically assume **0** always means "not found" if the statement includes status or version predicates.

## 13. Avoid Two Write Paths Updating the Same Data Without a Shared Convention

A common design mistake is allowing the same property to be updated by:

- **repository.save(entity)**,
- **@Modifying @Query**,
- **JdbcTemplate.update(...)**,
- a batch job or another application.

If each path uses its own rules, data consistency breaks down. For example, the repository increments **version**, while direct SQL forgets; one path updates **last_modified_at**, another skips it; one stores enums by name, another by code.

Establish clear conventions:

1. Choose the standard write path for aggregates.
2. Document when direct SQL is permitted.
3. Whenever direct SQL modifies a versioned aggregate, always check and increment version.
4. Keep auditing columns and converters aligned.
5. Never update children outside the root if they belong to the aggregate lifecycle.
6. Put coordinated operations into the same transaction.
7. Write integration tests proving both write paths do not corrupt reloaded state.

If direct SQL and **save** both modify the same root in one transaction, always use the latest version/state. Never continue saving an old object with a stale version after direct SQL has incremented the version; that operation should be rejected by optimistic locking when versioning is implemented properly.

## 14. Verifying That Transactions Are Truly Shared

A practical way to test this is creating a use case with two steps:

1. The repository updates an aggregate column.
2. A custom fragment inserts an audit row.

Then deliberately force the audit step to fail in a test environment. If both share a transaction, the aggregate change must also roll back. If the aggregate change persists while the audit row is absent, the two operations are not in the same transaction as expected or rollback was not triggered.

Common causes:

- The two templates use different DataSources.
- The repository and JDBC template are bound to different transaction managers.
- One code path manually opens a connection and commits.
- One operation executes on a different thread.
- The transaction is split by propagation such as **REQUIRES_NEW**.
- An exception is caught and swallowed before the transaction manager knows to roll back.
- A method is called internally on the same object, preventing proxy-based **@Transactional** from applying as intended.

Never commit manually after individual SQL statements inside a service transaction. The Spring transaction manager handles connections and commits/rollbacks when the transaction boundary ends.

## 15. Integration Testing for Consistency

You can write integration tests proving repositories and custom SQL join the same transaction. For instance, renaming a customer and writing an audit record; when the audit write fails, the customer's name must remain unchanged.

Conceptual test pattern:

~~~java
@Test
void rollsBackAggregateUpdateWhenAuditInsertFails() {
    Customer before = customerRepository.save(
            new Customer(null, null, "Lan", "lan@example.com", true)
    );

    assertThrows(RuntimeException.class, () ->
            customerService.renameAndFailAudit(before.id(), "Lan Nguyen")
    );

    Customer after = customerRepository.findById(before.id()).orElseThrow();

    assertEquals("Lan", after.name());
    assertEquals(0, auditRepository.countByCustomerId(before.id()));
}
~~~

This illustrates the test idea; real tests require database setup, transaction test configuration, and a proper way to induce the audit failure. Avoid merely mocking repositories/JdbcTemplate if the goal is verifying the transaction manager and DataSource genuinely coordinate.

## 16. Common Errors When Mixing Generated SQL and Hand-Written SQL

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Direct SQL reports column not found | Using Java property name instead of physical column name | Cross-check @Table, @Column, naming strategy, and DDL |
| Repository reads fine but RowMapper reads wrong values | Two paths convert enums/time/UUID differently | Standardize converters or manual mapping |
| Version fails to detect concurrent updates | Direct SQL omits version predicate or fails to increment version | Add WHERE version = :expectedVersion and increment version |
| Save after direct update throws optimistic-lock failure | In-memory object holds stale version | Reload aggregate or use new version after direct update |
| Audit persists while aggregate rolls back or vice versa | Operations are not in the same transaction | Check DataSource, transaction manager, and propagation |
| Children disappear after root save | Direct SQL altered children while root collection was stale | Sync aggregate state before saving |
| lastModifiedAt does not update | Manual SQL skips auditing callbacks | Update column in SQL or use the Spring Data path |
| Manual insert ID is not returned | Using JdbcTemplate.update without retrieving generated key | Use KeyHolder/PreparedStatementCreator or repository save |
| Enum data cannot be read back | SQL saved a code different from converter | Share one conversion rule |
| Update affects unexpectedly many rows | Overly broad WHERE predicate | Tighten keys/predicates and check update count |
| Transaction does not roll back on error | Exception swallowed or transaction does not cover both paths | Propagate error or configure rollback rules; check proxy and transaction manager |

## 17. Workflow for Coordinating Both Persistence Paths

When adding hand-written SQL to a Spring Data JDBC application, follow these steps:

1. **Identify the aggregate root and schema**: know the tables, IDs, versions, child tables, and constraints.
2. **Choose the canonical write path**: repository/template vs. custom SQL; avoid uncoordinated duplicate write paths.
3. **Align metadata**: @Table, @Column, @Id, @Version, embedded prefixes, @MappedCollection.
4. **Write SQL with physical identifiers**: table and column names must match deployed migrations.
5. **Align data types**: enums, temporal types, UUIDs, currency, nullability, and custom converters.
6. **Preserve invariants**: update root/children, version, auditing, and constraints per business rules.
7. **Set transaction boundaries**: place @Transactional on the application service when multiple operations must be atomic.
8. **Check update counts and generated keys**: understand what manual SQL returns.
9. **Reload when latest database state is needed**: in-memory objects do not update themselves after direct DML.
10. **Write integration tests**: verify rollbacks, mapping, and concurrency with the target database/driver.

~~~mermaid
flowchart TD
    A[Use case needs data access] --> B{Can use repository/template?}
    B -->|Yes| C[Let Spring Data generate SQL from metadata]
    B -->|No or needs custom SQL| D[Write @Query or custom JDBC fragment]
    C --> E{Mix with hand-written SQL?}
    D --> E
    E -->|Yes| F[Align mapping, version, callbacks, and children]
    E -->|No| G[Verify standard path transaction]
    F --> H[Set shared transaction boundary]
    G --> I[Execute]
    H --> I
    I --> J[Verify result and reloaded state]
~~~

## 18. Principles to Remember

- Repositories and **JdbcAggregateTemplate** generate SQL from mapping metadata; hand-written SQL must use the exact physical identifiers in the database.
- **@Table**, **@Column**, **@Id**, **@Version**, converters, and embedded/collection mappings form the contract between Java and the schema.
- **JdbcTemplate** does not automatically apply Spring Data mappings, entity callbacks, auditing, or optimistic locking.
- Direct SQL updating a versioned root must check the old version and increment the version itself.
- Direct SQL on child tables must respect aggregate boundaries, **idColumn**, keys/indexes, and collection synchronization rules.
- Use the same DataSource and transaction manager so repositories and JDBC templates join one Spring transaction.
- Place **@Transactional** on the application service when multiple operations must commit/roll back together.
- Never open connections or commit independently inside custom fragments if they must join the active transaction.
- Update counts are not generated IDs or updated entities; reload when you need the freshest state.
- Align enums, temporal values, UUIDs, nullability, auditing, and converters across both write paths.
- Use integration tests against a real database or Testcontainers to prove transactions and mappings work together.

In Spring Data JDBC, framework-generated SQL and hand-written SQL can be combined safely as long as both adhere to **one mapping contract, one set of aggregate rules, and one clear transaction boundary**. Let repositories/templates handle normal aggregate persistence; reserve direct SQL for parts that genuinely require fine-grained control, and take explicit ownership of the mapping, versioning, auditing, child data, and transactions that the automated path normally provides.
