# Dữ liệu kiểm thử bằng migration, @Sql và fixture trong Spring Data JDBC

## 1. Vì sao cần chiến lược dữ liệu kiểm thử?

Một repository test chỉ có ý nghĩa khi database chứa dữ liệu phù hợp với tình huống cần kiểm tra. Với Spring Data JDBC, dữ liệu kiểm thử cần phản ánh đúng cấu trúc aggregate, khóa ngoại, constraint và kiểu dữ liệu của schema.

Ví dụ, khi kiểm thử tải một đơn hàng có các dòng hàng, database phải có:

- Hàng aggregate root trong bảng orders.
- Các hàng con trong bảng order_lines.
- Khóa ngoại order_id trỏ đúng về đơn hàng.
- Giá trị trạng thái, số lượng và dữ liệu nghiệp vụ cần thiết cho assertion.

Có nhiều cách chuẩn bị dữ liệu: migration, SQL fixture, annotation @Sql hoặc builder/object factory trong Java. Mỗi cách có phạm vi và vòng đời khác nhau. Chọn đúng cách giúp test dễ đọc, độc lập và chạy ổn định trên máy phát triển lẫn CI.

Một chiến lược thực tế thường chia dữ liệu kiểm thử thành ba lớp:

1. **Schema migration:** tạo và thay đổi cấu trúc database theo lịch sử version của ứng dụng.
2. **Test baseline data:** dữ liệu chung, ổn định cần có cho một nhóm test.
3. **Scenario fixture:** dữ liệu riêng của từng test case, được tạo trước test và rollback hoặc dọn sau test.

Không nên dùng một file SQL duy nhất để vừa tạo schema, vừa chứa mọi dữ liệu của mọi test. Khi tách trách nhiệm, mỗi test có thể diễn tả rõ dữ liệu đầu vào mà nó cần.

## 2. Phân biệt migration và fixture

Migration và fixture đều có thể là SQL, nhưng chúng giải quyết hai vấn đề khác nhau.

| Thành phần | Mục đích | Vòng đời |
|---|---|---|
| Schema migration | Tạo bảng, cột, index, constraint và thay đổi schema | Theo version ứng dụng, chạy theo thứ tự |
| Test-only migration | Tạo dữ liệu nền dùng chung cho test | Chỉ chạy trong test configuration |
| @Sql fixture | Chuẩn bị dữ liệu cho một class hoặc method test | Trước/sau test theo execution phase |
| Java fixture/builder | Tạo entity và aggregate bằng API Java | Trong test hoặc setup method |
| Cleanup script | Xóa dữ liệu do test tạo | Sau test hoặc theo transaction rollback |

Ví dụ migration tạo bảng:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);
~~~

Migration này mô tả schema cần tồn tại trong mọi môi trường. Nó không nên chứa một đơn hàng giả chỉ phục vụ một test cụ thể.

Fixture có thể chèn một đơn hàng và hai dòng hàng để test repository:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-001', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92001, 91001, 'SKU-A', 2),
    (92002, 91001, 'SKU-B', 1);
~~~

Các ID trong ví dụ là ID cố định để dễ tham chiếu trong test. Nếu bảng dùng sequence/identity và test tiếp tục insert bằng generated ID, cần bảo đảm sequence không sinh lại ID đã chèn thủ công. Có thể dùng fixture builder để nhận ID sinh tự động hoặc điều chỉnh sequence theo database.

## 3. Dùng migration để tạo schema kiểm thử

Spring Data JDBC không tự tạo toàn bộ schema theo entity mapping trong mọi cấu hình. Ứng dụng thường dùng Flyway hoặc Liquibase để quản lý schema. Test nên chạy cùng chuỗi migration mà ứng dụng dùng để tạo database từ trạng thái trống.

Ví dụ cấu trúc Flyway:

~~~text
src/
  main/
    resources/
      db/
        migration/
          V1__create_orders.sql
          V2__add_order_status.sql
          V3__create_order_lines.sql
  test/
    resources/
      db/
        migration/
          V9999__test_reference_data.sql
~~~

Flyway chạy các migration theo version. Spring Boot mặc định tìm migration trong classpath:db/migration, có thể đổi bằng spring.flyway.locations.

Ví dụ cấu hình:

~~~properties
spring.flyway.locations=classpath:db/migration
~~~

Nếu cần một tập dữ liệu nền chỉ có trong test, có thể đặt migration bổ sung trong src/test/resources. Migration đó không được đóng gói vào artifact production. Tuy nhiên, test-only migration thường chạy khi test application context khởi động, không phải trước từng method. Vì vậy, chỉ dùng nó cho dữ liệu tham chiếu chung, ổn định; dữ liệu riêng của từng scenario nên dùng @Sql hoặc fixture builder.

### 3.1. Không trộn nhiều cơ chế tạo schema

Spring Boot khuyến nghị dùng một cơ chế chính để tạo và khởi tạo schema. Nếu project dùng Flyway hoặc Liquibase để quản lý schema, không nên đồng thời dùng schema.sql/data.sql như một hệ thống migration thứ hai.

Nếu dùng Flyway:

- Đặt migration schema trong src/main/resources/db/migration.
- Đặt test-only migration trong src/test/resources nếu cần dữ liệu nền chung.
- Không sửa migration đã được áp dụng ở môi trường dùng chung; tạo migration mới.
- Dùng đúng database engine khi migration chứa SQL đặc thù.

Nếu dùng Liquibase, có thể đánh dấu change set dữ liệu test bằng context:

~~~sql
--liquibase formatted sql

--changeset sample:1 context:@test
INSERT INTO product_categories (id, name)
VALUES (99001, 'Test category');
~~~

Sau đó cấu hình context test:

~~~properties
spring.liquibase.contexts=test
~~~

Chỉ change set có context phù hợp mới được áp dụng trong môi trường test. Không đặt dữ liệu kiểm thử vào change set production không có context chỉ vì muốn test có sẵn một vài hàng.

## 4. Test slice cho Spring Data JDBC

Spring Boot cung cấp @DataJdbcTest để kiểm thử phần persistence của Spring Data JDBC. Slice này thường cấu hình:

- DataSource kiểm thử, mặc định ưu tiên embedded database nếu có.
- Spring Data JDBC repositories.
- JdbcTemplate.
- Transaction test và rollback sau mỗi test method theo mặc định.

Ví dụ:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    void savesAndLoadsOrder() {
        Order saved = orders.save(
                Order.create("TEST-001")
        );

        Order loaded = orders.findById(saved.getId())
                .orElseThrow();

        assertThat(loaded.getOrderNumber()).isEqualTo("TEST-001");
    }
}
~~~

Đây là test slice phù hợp cho repository và mapping. Nó không tự quét tất cả @Component hoặc service như một application context đầy đủ. Nếu test cần service bean hoặc cấu hình riêng, có thể import cấu hình cần thiết hoặc dùng @SpringBootTest cho integration test rộng hơn.

Tên package của annotation test có thể thay đổi giữa các major version Spring Boot. Hãy dùng annotation từ module test và version tương ứng với project.

### 4.1. Dùng database thật thay cho embedded database

Embedded database giúp test nhanh, nhưng có thể khác production về:

- SQL dialect.
- Kiểu dữ liệu và constraint.
- Sequence/identity.
- Locking và isolation.
- Function, trigger và cú pháp migration.
- Query planner.

Nếu cần dùng DataSource đã cấu hình, có thể yêu cầu Spring Boot không thay thế nó bằng embedded database:

~~~java
@DataJdbcTest
@AutoConfigureTestDatabase(
        replace = AutoConfigureTestDatabase.Replace.NONE
)
class OrderRepositoryIntegrationTest {
    // Test trên DataSource được cấu hình cho test.
}
~~~

Một lựa chọn phổ biến là Testcontainers để khởi chạy database cùng loại với production. Test vẫn dùng repository Spring Data JDBC thật và chạy migration trên database container.

Đừng kết luận migration hoặc query tương thích production chỉ vì test pass trên H2 nếu project triển khai PostgreSQL, MySQL hoặc hệ quản trị khác.

## 5. Dùng @Sql để nạp dữ liệu cho test

Annotation @Sql cho phép chạy SQL script trước hoặc sau test class/method. Đây là lựa chọn thuận tiện khi fixture cần thể hiện rõ bằng SQL.

Ví dụ file fixture:

~~~text
src/test/resources/fixtures/orders-with-lines.sql
~~~

Nội dung:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-001', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92001, 91001, 'SKU-A', 2),
    (92002, 91001, 'SKU-B', 1);
~~~

Dùng trong repository test:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/orders-with-lines.sql")
    void loadsOrderWithItsLines() {
        Order order = orders.findById(91001L)
                .orElseThrow();

        assertThat(order.getLines()).hasSize(2);
        assertThat(order.getLines())
                .extracting(OrderLine::getSku)
                .containsExactlyInAnyOrder("SKU-A", "SKU-B");
    }
}
~~~

Đường dẫn bắt đầu bằng dấu / là absolute classpath resource. Nếu dùng đường dẫn tương đối, Spring diễn giải nó tương đối với package của test class.

Theo mặc định, script @Sql được chạy trước test method. Đây là thời điểm phù hợp để chèn dữ liệu fixture cho test.

### 5.1. Dùng @Sql ở cấp class và method

Có thể đặt dữ liệu chung ở cấp class:

~~~java
@DataJdbcTest
@Sql("/fixtures/reference-categories.sql")
class ProductRepositoryTest {

    @Test
    void findsProductsByCategory() {
        // Dùng dữ liệu category chung.
    }

    @Test
    @Sql("/fixtures/products-for-search.sql")
    void searchesProductsByName() {
        // Dùng thêm dữ liệu dành riêng cho method.
    }
}
~~~

Theo mặc định, @Sql ở method ghi đè cấu hình @Sql ở class. Nếu muốn kết hợp script chung ở class và script riêng ở method, dùng @SqlMergeMode:

~~~java
@DataJdbcTest
@Sql("/fixtures/reference-categories.sql")
@SqlMergeMode(SqlMergeMode.MergeMode.MERGE)
class ProductRepositoryTest {
    // Method-level @Sql được kết hợp với class-level @Sql.
}
~~~

Nếu không cần dữ liệu class-level cho một method cụ thể, có thể dùng chế độ OVERRIDE ở method đó để quay về hành vi mặc định.

### 5.2. Nhiều script và thứ tự chạy

Có thể truyền nhiều script trong một annotation:

~~~java
@Test
@Sql({
        "/fixtures/orders.sql",
        "/fixtures/order-lines.sql",
        "/fixtures/payments.sql"
})
void loadsCompleteOrder() {
    // ...
}
~~~

Các script nên được sắp xếp theo dependency của foreign key: insert parent trước, child sau. Nếu cleanup bằng SQL, thường xóa child trước parent khi không có cascade.

Spring cũng cho phép khai báo nhiều @Sql annotation lặp lại nếu từng nhóm cần cấu hình hoặc execution phase riêng.

## 6. Dùng @SqlConfig và transaction của fixture

Một điểm quan trọng là script @Sql có thể tham gia transaction đang tồn tại, chạy không có transaction hoặc chạy trong transaction riêng. Spring TestContext suy luận hành vi dựa trên transactionMode, DataSource và PlatformTransactionManager có trong test context.

Với test được đánh dấu @Transactional, script @Sql thông thường tham gia transaction của test. Khi test kết thúc và transaction rollback, dữ liệu được script chèn cũng rollback theo.

Ví dụ:

~~~java
@DataJdbcTest
@Transactional
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/orders-with-lines.sql")
    void loadsFixture() {
        assertThat(orders.findById(91001L)).isPresent();
    }
}
~~~

Không cần viết cleanup DELETE nếu fixture và test đều chạy trong cùng test-managed transaction và không có thao tác commit riêng.

### 6.1. Khi nào cần transaction ISOLATED?

Đôi khi script phải commit dữ liệu bên ngoài transaction của test. Ví dụ, test khởi chạy HTTP server trên thread riêng và request xử lý ở server cần nhìn thấy dữ liệu fixture đã commit.

Khi đó có thể dùng transactionMode ISOLATED:

~~~java
@Test
@Sql(
        scripts = "/fixtures/create-order.sql",
        config = @SqlConfig(
                transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
)
@Sql(
        scripts = "/fixtures/delete-order.sql",
        config = @SqlConfig(
                transactionMode = SqlConfig.TransactionMode.ISOLATED
        ),
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
void requestReadsCommittedOrder() {
    // Gửi request tới server.
}
~~~

Script tạo dữ liệu và cleanup chạy trong transaction riêng. Cleanup được cấu hình AFTER_TEST_METHOD để xóa dữ liệu sau khi test kết thúc.

Chỉ dùng ISOLATED khi cần semantics commit riêng. Với test repository thông thường, để script tham gia transaction test và rollback tự động thường đơn giản hơn.

### 6.2. Kiểm soát DataSource và transaction manager

Nếu test context có nhiều DataSource hoặc nhiều transaction manager, Spring có thể không suy luận đúng resource mà script cần dùng.

Có thể khai báo rõ trong @SqlConfig:

~~~java
@Sql(
        scripts = "/fixtures/orders.sql",
        config = @SqlConfig(
                dataSource = "ordersDataSource",
                transactionManager = "ordersTransactionManager"
        )
)
~~~

Tên bean phải khớp với cấu hình ứng dụng. Không dùng transaction manager của database khác để chạy fixture nếu test repository đang sử dụng DataSource riêng.

### 6.3. Script cleanup sau test

@Sql hỗ trợ executionPhase AFTER_TEST_METHOD:

~~~java
@Test
@Sql("/fixtures/create-test-customer.sql")
@Sql(
        scripts = "/fixtures/delete-test-customer.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
void performsCustomerOperation() {
    // ...
}
~~~

Nếu test chạy trong transaction tự rollback, cleanup script thường không cần thiết. Cleanup rõ ràng phù hợp với test không transactional, dữ liệu được commit riêng hoặc test dùng tài nguyên database dùng chung.

Đối với test chạy song song, tránh cleanup theo điều kiện quá rộng như xóa toàn bộ bảng. Dùng ID hoặc business key riêng của test để chỉ xóa dữ liệu do test đó tạo.

## 7. Tạo fixture bằng Java builder hoặc repository

Không phải mọi dữ liệu đều nên viết bằng SQL. Nếu muốn test thể hiện hành vi aggregate và mapping của Spring Data JDBC, tạo entity qua constructor/builder rồi lưu bằng repository.

Ví dụ helper:

~~~java
private Order createOrder(
        OrderRepository orders,
        String orderNumber,
        String... skus
) {
    List<OrderLine> lines = Arrays.stream(skus)
            .map(sku -> new OrderLine(sku, 1))
            .toList();

    return orders.save(
            new Order(orderNumber, "PENDING", lines)
    );
}
~~~

Test:

~~~java
@Test
void savesAggregateWithMultipleLines() {
    Order saved = createOrder(
            orders,
            "TEST-ORDER-002",
            "SKU-A",
            "SKU-B"
    );

    Order loaded = orders.findById(saved.getId())
            .orElseThrow();

    assertThat(loaded.getLines()).hasSize(2);
}
~~~

Ưu điểm của fixture builder:

- Dùng domain constructor và factory method thực tế.
- Ít phụ thuộc vào tên cột và cú pháp SQL.
- Dễ tạo nhiều biến thể dữ liệu.
- Dữ liệu phản ánh quy tắc tạo aggregate của ứng dụng.
- Generated ID được nhận từ entity trả về của repository.

Nhược điểm là test phải chạy qua persistence để tạo fixture, và khó tạo một số trạng thái dữ liệu đặc biệt như giá trị legacy không hợp lệ hoặc record ở trạng thái mà domain API hiện tại không cho phép tạo.

Vì vậy, Java fixture và SQL fixture có thể cùng tồn tại. Chọn cách thể hiện rõ nhất mục đích của test.

## 8. Khi nào nên dùng từng loại fixture?

| Tình huống | Cách phù hợp |
|---|---|
| Test repository cần kiểm tra aggregate mapping | Tạo object và save qua repository |
| Cần tạo dữ liệu phức tạp với nhiều bảng và giá trị chính xác | SQL fixture bằng @Sql |
| Nhiều test dùng chung một tập dữ liệu tham chiếu ổn định | Test-only migration hoặc class-level @Sql |
| Mỗi test cần dữ liệu riêng | Method-level @Sql hoặc Java builder |
| Cần dữ liệu không thể tạo qua domain API | SQL fixture |
| Cần kiểm thử schema upgrade | Chạy migration từ version cũ sang version mới trên database test |
| Cần test trên database engine thật | Testcontainers kết hợp migration và fixture |
| Cần dữ liệu phát sinh động theo ID | Java builder hoặc setup method |

Không cần ép toàn bộ test dùng một kiểu fixture. Điều quan trọng là mỗi test phải hiểu được dữ liệu nào được tạo ở đâu, lúc nào và được dọn bằng cách nào.

## 9. Kiểm thử migration và schema evolution

Test migration cần bắt đầu từ database trống hoặc từ schema version cũ, sau đó chạy migration thật của ứng dụng.

Một số mục tiêu:

- Migration mới tạo đúng bảng và constraint.
- Migration thêm cột có default phù hợp.
- Dữ liệu cũ vẫn được giữ khi đổi schema.
- Index và foreign key được tạo đúng.
- Migration chạy được trên database mục tiêu.
- Repository hoạt động với schema sau migration.

Ví dụ workflow với Flyway:

~~~text
1. Tạo database test sạch.
2. Chạy toàn bộ migration production.
3. Chạy test-only migration nếu cần dữ liệu nền.
4. Nạp fixture riêng bằng @Sql hoặc builder.
5. Chạy repository/service test.
6. Hủy database test hoặc rollback/dọn fixture.
~~~

Nếu cần kiểm tra upgrade từ một version cụ thể, tạo database ở version đó rồi chạy migration còn thiếu. Không chỉ test trạng thái schema cuối cùng; một migration có thể tạo được schema mới nhưng làm mất dữ liệu cũ.

### 9.1. Test-only migration với Flyway

Spring Boot cho phép đặt migration chỉ dành cho test trong src/test/resources. Ví dụ:

~~~text
src/test/resources/db/migration/
  V9999__test_reference_data.sql
~~~

Nội dung có thể chèn các mã danh mục hoặc dữ liệu tham chiếu mà nhiều test đều cần.

Hãy nhớ test-only migration thường chạy một lần theo lịch sử migration của database/context. Nó không tự reset dữ liệu trước mỗi test method. Dữ liệu có thể được dùng chung, vì vậy không để một test sửa/xóa các hàng nền mà test khác phụ thuộc.

### 9.2. Test context với Liquibase

Với Liquibase, có thể gắn context test cho change set dữ liệu:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: test-reference-data
      author: sample
      context: "@test"
      changes:
        - insert:
            tableName: product_categories
            columns:
              - column:
                  name: id
                  valueNumeric: 99001
              - column:
                  name: name
                  value: Test category
~~~

Trong test configuration:

~~~properties
spring.liquibase.contexts=test
~~~

Context @test yêu cầu context test phải được chỉ định rõ khi chạy Liquibase; điều này giúp change set test-only không vô tình chạy trong môi trường không truyền context. Không thêm dữ liệu scenario riêng của từng method vào changelog dùng chung nếu dữ liệu đó có thể làm các test phụ thuộc lẫn nhau.

## 10. DataJdbcTest và SpringBootTest khác nhau thế nào?

| Annotation | Phạm vi | Khi nào dùng |
|---|---|---|
| @DataJdbcTest | Slice cho Spring Data JDBC, repositories và JDBC infrastructure | Test mapping, repository, query |
| @JdbcTest | Slice JDBC cấp thấp, không tập trung vào Spring Data JDBC repository | Test JdbcTemplate/SQL DAO |
| @SpringBootTest | Application context rộng hơn, có thể gồm service và cấu hình ứng dụng | Integration test qua nhiều tầng |
| @SpringBootTest(webEnvironment = RANDOM_PORT) | Khởi chạy server thật trên port ngẫu nhiên | Test HTTP endpoint với database |

Các test slice JDBC thường transactional và rollback cuối test. Điều này tiện để cô lập dữ liệu.

Với @SpringBootTest và webEnvironment RANDOM_PORT, HTTP client và server chạy trên thread riêng. Transaction của test không bao phủ transaction do server xử lý request. Vì vậy, không giả định dữ liệu server ghi sẽ rollback chỉ vì test method có @Transactional. Hãy dùng database riêng cho test, cleanup fixture hoặc cơ chế cô lập phù hợp.

## 11. Một ví dụ hoàn chỉnh: repository test với migration và @Sql

Giả sử schema được tạo bằng Flyway migration trong src/main/resources/db/migration. Test fixture nằm trong src/test/resources/fixtures.

Fixture:

~~~sql
INSERT INTO orders (id, order_number, status)
VALUES (91001, 'TEST-ORDER-003', 'PENDING');

INSERT INTO order_lines (id, order_id, sku, quantity)
VALUES
    (92011, 91001, 'SKU-C', 3),
    (92012, 91001, 'SKU-D', 2);
~~~

Test:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    @Sql("/fixtures/order-with-lines.sql")
    void loadsAggregateFromSqlFixture() {
        Order order = orders.findById(91001L)
                .orElseThrow();

        assertThat(order.getOrderNumber())
                .isEqualTo("TEST-ORDER-003");

        assertThat(order.getLines())
                .extracting(OrderLine::getSku)
                .containsExactly("SKU-C", "SKU-D");
    }

    @Test
    void savesAggregateUsingDomainFixture() {
        Order order = new Order(
                "TEST-ORDER-004",
                "PENDING",
                List.of(
                        new OrderLine("SKU-E", 1),
                        new OrderLine("SKU-F", 4)
                )
        );

        Order saved = orders.save(order);

        assertThat(saved.getId()).isNotNull();
        assertThat(saved.getLines()).hasSize(2);
    }
}
~~~

Trong ví dụ:

- Flyway migration tạo schema trước khi test repository chạy.
- @Sql chèn một aggregate có dữ liệu chính xác để test load mapping.
- Test thứ hai tạo aggregate qua Java và repository để test save mapping.
- Nếu @DataJdbcTest quản lý transaction mặc định, fixture và thao tác repository được rollback sau mỗi test method.

Đây là cách kết hợp migration, SQL fixture và Java fixture mà không để mỗi thành phần phải làm quá nhiều việc.

## 12. Những lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Test báo thiếu bảng | Migration không chạy hoặc test dùng DataSource khác | Kiểm tra Flyway/Liquibase và DataSource của test |
| Fixture chạy trước khi có bảng | Thứ tự khởi tạo schema và script chưa đúng | Để migration hoàn tất khi application context khởi tạo, dùng @Sql cho fixture method |
| Method-level @Sql không chạy cùng class-level script | Method-level declaration ghi đè class-level theo mặc định | Dùng @SqlMergeMode(MERGE) nếu cần kết hợp |
| Fixture bị rollback trước khi request server đọc được | Script tham gia test transaction nhưng server chạy thread khác | Dùng ISOLATED hoặc setup dữ liệu đã commit |
| Dữ liệu test còn lại sau test | Test không transactional hoặc fixture chạy isolated | Dùng cleanup script hoặc database riêng |
| Test bị trùng khóa chính | Fixture dùng ID cố định và chạy trên database dùng chung | Dùng ID riêng, rollback hoặc schema/database cô lập |
| Test thứ hai phụ thuộc dữ liệu test thứ nhất | Fixture dùng chung bị thay đổi hoặc cleanup quá rộng | Tạo fixture riêng cho từng test và tránh mutation dữ liệu nền |
| Flyway báo checksum mismatch | Migration đã được chỉnh sửa sau khi chạy | Tạo migration mới thay vì sửa migration đã áp dụng |
| Test pass trên H2 nhưng fail production | Khác biệt dialect, constraint, sequence hoặc SQL | Chạy integration test với database mục tiêu |
| @Sql không tìm thấy file | Đường dẫn resource tương đối/sai package | Dùng absolute classpath path bắt đầu bằng dấu / |
| Script insert child trước parent | Vi phạm foreign key | Insert root trước, child sau |
| Cleanup xóa dữ liệu của test khác | DELETE dùng predicate quá rộng | Dùng ID/business key riêng của test |
| Test slice không có service bean | @DataJdbcTest không scan component thông thường | Import bean cần thiết hoặc dùng @SpringBootTest |
| Dùng schema.sql cùng Flyway/Liquibase | Nhiều cơ chế khởi tạo schema cạnh tranh | Chọn một cơ chế quản lý schema chính |

## 13. Quy trình chọn và quản lý fixture

1. Xác định test cần kiểm tra repository, service hay toàn bộ application.
2. Dùng migration thật của ứng dụng để tạo schema.
3. Chỉ dùng test-only migration cho dữ liệu nền ổn định dùng chung.
4. Chọn @Sql cho fixture SQL rõ ràng hoặc Java builder cho aggregate được tạo qua domain API.
5. Đặt fixture riêng theo scenario và dùng tên file thể hiện mục đích.
6. Xác định script chạy trước hay sau test bằng executionPhase.
7. Xác định fixture tham gia test transaction hay cần ISOLATED.
8. Dùng rollback tự động khi test transactional; nếu không, cleanup theo ID riêng.
9. Chạy test trên database mục tiêu khi migration hoặc SQL phụ thuộc dialect.
10. Bảo đảm test độc lập, có thể chạy riêng lẻ và theo thứ tự bất kỳ.

## 14. Bài tập thực hành

### Bài 1 — Migration schema

Tạo Flyway migration tạo bảng orders và order_lines với primary key, foreign key và constraint. Chạy test trên database sạch để xác nhận migration hoàn tất.

### Bài 2 — SQL fixture

Tạo file fixture chèn một order và hai order lines. Dùng @Sql trước repository test, sau đó kiểm tra aggregate được dựng đầy đủ.

### Bài 3 — Transaction rollback

Đánh dấu test bằng @Transactional và chèn fixture qua @Sql. Xác nhận dữ liệu không còn sau khi test kết thúc bằng cách chạy test tiếp theo hoặc truy vấn database sau transaction.

### Bài 4 — Script cleanup

Tạo cleanup script và cấu hình AFTER_TEST_METHOD. Chạy test không transactional để xác nhận fixture được xóa đúng phạm vi.

### Bài 5 — Fixture builder

Tạo helper Java xây dựng Order có nhiều OrderLine rồi lưu qua repository. Viết test kiểm tra generated ID và quan hệ parent-child.

### Bài 6 — Class-level và method-level @Sql

Đặt reference data ở class level, scenario data ở method level. Quan sát hành vi mặc định rồi bật @SqlMergeMode(MERGE) và so sánh.

### Bài 7 — Test-only Flyway migration

Tạo một migration chỉ nằm trong src/test/resources để nạp dữ liệu danh mục dùng chung. Xác nhận migration không xuất hiện trong artifact production và không bị chạy lại sau khi đã được ghi nhận.

### Bài 8 — Liquibase test context

Tạo change set có context test và cấu hình spring.liquibase.contexts=test. Xác nhận dữ liệu chỉ xuất hiện trong test context.

### Bài 9 — Database thật

Chạy cùng migration và fixture trên database bằng Testcontainers. So sánh kết quả với embedded database, chú ý sequence, constraint và kiểu dữ liệu.

### Bài 10 — Test độc lập và chạy song song

Chạy từng test riêng, chạy cả class và bật parallel execution nếu project hỗ trợ. Loại bỏ phụ thuộc vào thứ tự test và dữ liệu dùng chung có thể bị sửa.

## 15. Ghi nhớ

- Migration quản lý schema theo version; fixture tạo dữ liệu cho scenario test.
- Dùng cùng migration production để test database được dựng theo cấu trúc ứng dụng thực tế.
- Test-only migration phù hợp với dữ liệu nền dùng chung, không thay thế fixture riêng cho từng test method.
- @Sql chạy script trước test method theo mặc định và có thể chạy sau test để cleanup.
- Method-level @Sql ghi đè class-level theo mặc định; dùng @SqlMergeMode khi cần kết hợp.
- Với test transactional, @Sql thường tham gia transaction test và dữ liệu được rollback cuối test.
- Dùng transactionMode ISOLATED khi script cần commit độc lập với test transaction.
- @DataJdbcTest phù hợp với repository/mapping test; @SpringBootTest phù hợp với integration test rộng hơn.
- Test qua HTTP server thật chạy transaction ở thread khác, nên rollback của test method không tự rollback thay đổi từ server.
- Spring Boot khuyến nghị chọn một cơ chế quản lý schema chính; không trộn tùy tiện schema.sql/data.sql với Flyway hoặc Liquibase.
- Chạy migration và fixture trên database mục tiêu khi SQL, sequence, constraint hoặc dialect có thể khác embedded database.
