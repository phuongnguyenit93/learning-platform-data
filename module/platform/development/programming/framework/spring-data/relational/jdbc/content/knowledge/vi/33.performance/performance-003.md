# Đo chi phí xóa–chèn lại entity con trong aggregate lớn

Spring Data JDBC quản lý dữ liệu theo aggregate root. Khi lưu một aggregate mới, framework chèn root rồi chèn các entity được tham chiếu. Khi lưu một aggregate đã tồn tại, Spring Data JDBC xóa các entity được tham chiếu, cập nhật aggregate root rồi chèn lại các entity con theo trạng thái hiện tại của object được truyền vào.

Cách làm này giúp framework chuyển trạng thái aggregate trong bộ nhớ thành trạng thái tương ứng trong database mà không cần theo dõi từng thay đổi nhỏ. Tuy nhiên, với aggregate lớn, chi phí có thể cao: chỉ sửa một property của root hoặc một dòng con cũng có thể khiến toàn bộ tập entity con được xóa và chèn lại.

Để quyết định có cần thay đổi thiết kế hay không, cần hiểu chính xác phạm vi thao tác, ước lượng write amplification, đo trên dữ liệu đại diện và so sánh các phương án vẫn giữ đúng invariant nghiệp vụ.

## 1. Hành vi lưu aggregate hiện tại

Giả sử một PurchaseOrder có một collection OrderLine. Khi tạo đơn mới, Spring Data JDBC chèn aggregate root rồi chèn các dòng hàng.

Khi aggregate đã tồn tại, quy trình lưu về mặt khái niệm là:

1. Xóa các entity được tham chiếu thuộc aggregate.
2. Cập nhật hàng aggregate root.
3. Chèn lại các entity được tham chiếu theo trạng thái collection hiện tại.

Điều này xảy ra vì Spring Data JDBC không giữ snapshot trước đó của aggregate để so sánh từng child row. Framework nhận object mới và phải đưa database về trạng thái được mô tả bởi object đó.

~~~mermaid
flowchart TD
    A[repository.save(existingAggregate)] --> B[Nhận diện aggregate đã tồn tại]
    B --> C[Xóa các entity được tham chiếu]
    C --> D[Cập nhật aggregate root]
    D --> E[Chèn lại toàn bộ entity con]
    E --> F[Transaction commit]
~~~

Đây là hành vi được mô tả trong tài liệu Spring Data Relational ở phần Persisting Entities. Với aggregate mới, framework insert root rồi insert các entity được tham chiếu; với aggregate đã tồn tại, các entity được tham chiếu bị delete và insert lại sau khi root được update.

Điểm cần nhớ là thao tác này áp dụng cho **referenced entities thuộc aggregate**, ví dụ collection được ánh xạ bằng @MappedCollection. Property @Embedded được lưu thành cột trên cùng bảng với entity chứa nó, nên không tạo tập child rows riêng để xóa và chèn lại theo cách này.

## 2. Ví dụ aggregate có collection lớn

Giả sử hệ thống bán hàng có aggregate:

~~~java
import java.math.BigDecimal;
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        BigDecimal total,
        @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
        List<OrderLine> lines
) {}

public record OrderLine(
        String sku,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

Bảng root và child có thể được thiết kế như sau:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    total DECIMAL(18, 2) NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Giả sử một đơn hàng có 2.000 dòng. Khi service đọc đơn, thay đổi status rồi gọi repository.save(order), Spring Data JDBC không chỉ cập nhật status trên hàng purchase_orders. Các hàng order_lines được tham chiếu cũng được xóa và chèn lại theo collection được gửi vào.

Ngay cả khi chỉ một dòng hàng thay đổi quantity, framework không tự suy ra rằng chỉ cần update đúng dòng đó. Nó không theo dõi trạng thái cũ để tạo diff.

## 3. Ước lượng write amplification

Gọi:

- N là tổng số entity con được tham chiếu trực tiếp và gián tiếp trong aggregate.
- K là số entity con thực sự thay đổi giữa trạng thái cũ và trạng thái mới.
- K có thể nhỏ hơn rất nhiều so với N.

Với thao tác save trên aggregate đã tồn tại, lượng công việc child ở mức hàng có thể xấp xỉ:

- N hàng bị xóa.
- N hàng được chèn lại.
- Root được cập nhật.

Do đó, số hàng child bị ghi có thể gần 2N, dù chỉ K hàng thực sự thay đổi.

Ví dụ:

| Tổng child rows N | Child rows thực sự đổi K | Child rows delete | Child rows insert | Tổng child row changes |
|---:|---:|---:|---:|---:|
| 10 | 1 | 10 | 10 | 20 |
| 100 | 1 | 100 | 100 | 200 |
| 1.000 | 1 | 1.000 | 1.000 | 2.000 |
| 5.000 | 1 | 5.000 | 5.000 | 10.000 |
| 10.000 | 10 | 10.000 | 10.000 | 20.000 |

Bảng là mô hình ước lượng số hàng bị tác động, không phải cam kết số SQL statement hay số network round trip. Driver, dialect, batching, cách mapping và cấu trúc aggregate có thể làm thay đổi số statement thực tế.

Có thể biểu diễn write amplification của child theo tỷ lệ:

\[
WA = \frac{\text{Child rows deleted + inserted}}{\text{Child rows actually changed}}
\]

Nếu chỉ một dòng thay đổi trong aggregate 5.000 dòng, mô hình đơn giản cho thấy 10.000 child row changes cho một thay đổi logic. Tỷ lệ này không phải metric chuẩn của Spring Data; nó là cách định lượng để so sánh mức ghi thừa trong use case.

Nếu aggregate có nhiều collection lồng nhau, N cần tính tổng số entity được tham chiếu trong toàn bộ cây aggregate, không chỉ collection nhìn thấy trực tiếp ở root.

## 4. Chi phí không chỉ nằm ở số câu SQL

Delete và insert lại child rows có thể tạo nhiều loại chi phí:

- **CPU database**: xử lý predicate delete, insert, kiểm tra constraint và chuyển đổi kiểu.
- **I/O**: đọc/ghi page dữ liệu, index và transaction log.
- **Index maintenance**: xóa entry cũ rồi thêm entry mới cho mỗi index liên quan.
- **Foreign key checks**: kiểm tra tham chiếu khi insert; delete có thể bị chặn nếu bảng khác tham chiếu child.
- **Trigger**: trigger DELETE/INSERT có thể chạy lại dù dữ liệu cuối cùng giống như trước.
- **Audit table**: trigger hoặc audit logic có thể ghi thêm lịch sử cho từng lần xóa/chèn.
- **Locking**: transaction giữ khóa lâu hơn, làm tăng khả năng chờ và contention.
- **Transaction log/WAL**: lượng log tăng, có thể ảnh hưởng replication và backup.
- **Network và driver overhead**: nhiều lần bind/execute hoặc batch có thể tăng chi phí giao tiếp.
- **Connection pool usage**: transaction kéo dài giữ connection lâu hơn.

Một aggregate có 5.000 child rows và ba index trên bảng child không chỉ tạo 10.000 row changes. Nó còn làm phát sinh công việc trên các index, constraint, trigger và transaction log.

## 5. Xóa rồi chèn lại có thể ảnh hưởng tới khóa ngoại bên ngoài

Trong mô hình aggregate, referenced entity thuộc vòng đời của root. Spring Data JDBC giả định các entity này được quản lý qua aggregate root. Nếu một bảng độc lập khác tham chiếu trực tiếp đến một child row, việc delete child có thể gây vấn đề:

- Foreign key với ON DELETE RESTRICT có thể làm thao tác save thất bại.
- ON DELETE CASCADE có thể xóa thêm dữ liệu phụ thuộc.
- Nếu child được chèn lại với khóa mới, tham chiếu cũ có thể không còn hợp lệ.
- Trigger audit có thể ghi nhận delete/insert dù người dùng chỉ sửa một property.

Đây thường là dấu hiệu cần xem lại ranh giới aggregate. Nếu một entity con cần được tham chiếu và quản lý độc lập, nó có thể nên là aggregate root riêng, còn aggregate khác lưu ID hoặc AggregateReference tới nó.

Không nên dựa vào ID của child như một định danh độc lập ổn định nếu thiết kế persistence của child thuộc về collection aggregate và có thể bị thay thế trong quá trình save.

## 6. Khi nào chi phí này đáng quan tâm?

Không phải mọi aggregate đều cần tối ưu. Với collection nhỏ, cách lưu đơn giản và transaction ngắn có thể tốt hơn việc tự quản lý từng child row.

Chi phí đáng quan tâm khi có một hoặc nhiều dấu hiệu:

- Aggregate thường có hàng trăm hoặc hàng nghìn entity con.
- Use case chỉ sửa root scalar nhưng vẫn save aggregate có collection lớn.
- Một request chỉ đổi một child nhưng phải ghi lại toàn bộ collection.
- Bảng child có nhiều index, trigger hoặc foreign key.
- Save aggregate nằm trên đường request có latency nhạy cảm.
- Có nhiều transaction đồng thời cập nhật các aggregate lớn.
- Transaction log, replication lag hoặc database write IOPS tăng bất thường.
- Connection pool bị chiếm lâu do các lần save lớn.
- Tác vụ batch save nhiều aggregate có collection lớn.

Hãy bắt đầu bằng số liệu thực tế. Một aggregate 1.000 child rows có thể vẫn đáp ứng yêu cầu trên database mạnh và tải thấp; một aggregate 100 child rows có nhiều trigger, index và concurrency cao vẫn có thể gây vấn đề.

## 7. Đo đúng chi phí của một lần save

Để đánh giá, cần tách ba câu hỏi:

1. Spring Data JDBC tạo và thực thi bao nhiêu thao tác persistence?
2. Database thực sự xóa/chèn/cập nhật bao nhiêu hàng và mất bao lâu?
3. Toàn bộ use case, bao gồm commit transaction, có latency và throughput ra sao?

Không nên chỉ đo thời gian một lời gọi repository.save bên trong method @Transactional rồi kết luận đó là toàn bộ thời gian. Nếu đo từ bên trong method, transaction có thể chưa commit. Hãy đo từ caller bên ngoài Spring proxy để bao gồm thời gian commit/rollback.

### Thiết kế dataset đại diện

Tạo các aggregate có cardinality khác nhau:

| Nhóm | Child rows mỗi aggregate | Mục đích |
|---|---:|---|
| Nhỏ | 10 | Baseline |
| Trung bình | 100 | Tải thường gặp |
| Lớn | 1.000 | Xác định điểm bắt đầu tăng chi phí |
| Rất lớn | 5.000 | Kiểm tra write amplification rõ rệt |
| Cực lớn | 10.000 hoặc hơn | Xác định giới hạn vận hành nếu nghiệp vụ thực sự có quy mô này |

Không chỉ dùng một aggregate có kích thước trung bình. Phân phối thực tế thường có nhiều aggregate nhỏ và một số aggregate rất lớn; cần kiểm tra cả tail size.

### Các kịch bản phải đo

Với cùng một aggregate và cùng cardinality, đo riêng:

1. **Save không đổi child**: thay đổi một property trên root, giữ collection nguyên trạng.
2. **Save đổi một child**: chỉ thay đổi quantity của một OrderLine.
3. **Save đổi một phần nhỏ**: thay đổi 1% child rows.
4. **Save thay toàn bộ collection**: thay đổi mọi child.
5. **Targeted SQL**: cập nhật trực tiếp đúng một child row, nếu đây là phương án đang cân nhắc và đã xử lý concurrency/invariant.
6. **Split aggregate**: lưu root riêng và cập nhật child aggregate độc lập, nếu mô hình domain cho phép.

Các kịch bản 1 và 2 đặc biệt quan trọng: nếu child persistence theo delete/reinsert, lượng child row changes có thể gần như nhau dù một trường hợp không đổi child và trường hợp kia chỉ đổi một dòng.

### Các số liệu nên thu thập

- Thời gian toàn use case, gồm transaction commit.
- p50, p95 và p99 latency.
- Throughput theo request/second.
- Số SQL statements.
- Số batch executions và kích thước batch nếu có.
- Số child rows deleted và inserted.
- Database CPU và I/O.
- Transaction log/WAL volume.
- Lock wait, deadlock và transaction duration.
- Connection pool active/pending connections.
- Số lỗi optimistic locking hoặc constraint.

SQL statement count không đồng nghĩa row count. Một câu DELETE có thể xóa 5.000 hàng; một batch insert có thể chèn hàng trăm hàng trong một lần execute. Cần đo cả statement và rows affected.

## 8. Công cụ quan sát SQL và database

Trong môi trường phát triển hoặc test, có thể dùng:

- Log SQL của Spring JDBC/Spring Data để xem hình dạng câu lệnh.
- DataSource proxy để đếm query, batch và thời gian.
- P6Spy để quan sát SQL được thực thi trong môi trường debug.
- Micrometer và metrics của connection pool để theo dõi latency, active connections và pending requests.
- Công cụ native của DBMS để xem query statistics, lock waits, I/O và transaction log.
- EXPLAIN hoặc execution plan để xem cách database thực thi DELETE/INSERT.

Không nên bật log SQL/parameter đầy đủ trong benchmark chính thức vì logging tạo thêm overhead và có thể làm sai số đo. Dùng một lượt riêng để xác nhận SQL, sau đó tắt log chi tiết khi đo hiệu năng.

Với DELETE dạng:

~~~sql
DELETE FROM order_lines
WHERE order_id = ?;
~~~

hãy kiểm tra index trên order_id. Nếu không có index phù hợp, database có thể phải quét nhiều hàng để tìm các child rows. Với INSERT, kiểm tra index trên primary key, unique key và các cột có index khác.

## 9. Quy trình benchmark có thể lặp lại

Một benchmark có giá trị nên giữ cố định các điều kiện:

1. Dùng cùng DBMS và phiên bản gần môi trường triển khai.
2. Dùng đúng JDBC driver và cấu hình connection pool.
3. Dùng schema, index, trigger và foreign key giống production.
4. Nạp dataset có cardinality và phân phối gần thực tế.
5. Warm up ứng dụng và database trước khi lấy số liệu.
6. Chạy mỗi kịch bản nhiều lần, không lấy một lần chạy duy nhất.
7. Tách thời gian đọc aggregate khỏi thời gian save nếu muốn phân tích từng giai đoạn.
8. Đo toàn bộ service call từ bên ngoài transaction proxy để bao gồm commit.
9. Chạy cả tải đơn luồng và tải đồng thời.
10. Ghi lại p50/p95/p99, rows affected, SQL/batch count và database metrics.
11. Lặp lại benchmark sau khi thay đổi schema/index hoặc code.
12. So sánh các phương án trên cùng dữ liệu và cùng điều kiện tải.

Không chạy benchmark trên database production bằng dữ liệu thật nếu chưa có quy trình cho phép. Dùng database test có cấu hình tương đương để tránh ảnh hưởng workload đang phục vụ người dùng.

## 10. Ví dụ về cách bố trí benchmark

Có thể viết một service benchmark riêng để tạo các biến thể aggregate. Phần đo thời gian phải nằm ở caller bên ngoài service transaction:

~~~java
@Service
public class OrderSaveService {

    private final PurchaseOrderRepository repository;

    public OrderSaveService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long orderId, String status) {
        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow();

        PurchaseOrder changed = new PurchaseOrder(
                current.id(),
                current.version(),
                current.orderNumber(),
                status,
                current.total(),
                current.lines()
        );

        return repository.save(changed);
    }
}
~~~

Caller benchmark:

~~~java
long started = System.nanoTime();

PurchaseOrder saved = orderSaveService.changeStatus(orderId, "PROCESSING");

long elapsedNanos = System.nanoTime() - started;
~~~

Nếu orderSaveService là Spring bean được gọi qua proxy, lời gọi trở về sau khi transaction interceptor hoàn tất commit/rollback. Đoạn mã chỉ minh họa ranh giới đo; benchmark thực tế cần warmup, nhiều lần lặp, phân phối dữ liệu và thống kê percentile. Không dùng một vòng lặp đơn giản như microbenchmark cuối cùng vì JIT, connection pool, cache database và garbage collection có thể làm kết quả sai lệch.

## 11. So sánh save aggregate với targeted child update

Giả sử chỉ cần đổi quantity của một dòng hàng. Save aggregate có thể xóa và chèn lại toàn bộ collection. Một câu SQL trực tiếp có thể chỉ cập nhật một hàng:

~~~sql
UPDATE order_lines
SET quantity = :quantity
WHERE order_id = :orderId
  AND line_no = :lineNo;
~~~

Về số hàng, targeted update tác động một child row thay vì xóa và chèn lại N child rows. Nhưng hai cách không hoàn toàn tương đương về semantics.

Khi dùng SQL trực tiếp, ứng dụng phải tự đảm bảo:

- Dòng hàng thuộc đúng đơn hàng.
- Quantity hợp lệ theo domain invariant.
- Tổng tiền đơn hàng được tính lại hoặc cập nhật đúng.
- Aggregate root version được kiểm tra/tăng nếu version bảo vệ toàn aggregate.
- Auditing và domain event được xử lý.
- Transaction bao trùm mọi thay đổi liên quan.
- Object PurchaseOrder đã load trong bộ nhớ không được tiếp tục dùng với trạng thái cũ.

Ví dụ cập nhật có kiểm tra version root:

~~~sql
UPDATE purchase_orders
SET version = version + 1
WHERE id = :orderId
  AND version = :expectedVersion;
~~~

Sau đó chỉ cập nhật child khi bước kiểm tra version thành công, trong cùng transaction. Nếu một bước thất bại, rollback toàn bộ. Thứ tự và câu lệnh chính xác cần phù hợp với invariant của domain; không copy ví dụ này như một giải pháp hoàn chỉnh cho mọi aggregate.

Nếu bỏ qua version hoặc cập nhật child mà không khóa/kiểm tra root, hai transaction có thể sửa các phần khác nhau của cùng aggregate nhưng không phát hiện xung đột.

## 12. Phương án 1: giữ aggregate và chấp nhận delete/reinsert

Đây là phương án đơn giản nhất khi:

- Collection nhỏ hoặc vừa.
- Tần suất save thấp.
- Transaction ngắn.
- Không có bảng ngoài phụ thuộc vào ID child.
- Index, trigger và constraint không tạo chi phí đáng kể.
- Tính nhất quán của toàn aggregate quan trọng hơn tối ưu từng row.

Ưu điểm:

- Code domain đơn giản.
- Spring Data JDBC quản lý toàn bộ aggregate.
- Ít SQL tùy chỉnh.
- Optimistic locking của root được tích hợp trên đường save.
- Không cần tự tạo thuật toán diff giữa trạng thái cũ và mới.

Nhược điểm:

- Write amplification tăng theo kích thước aggregate.
- Trigger/audit có thể chạy lại cho các row không thay đổi.
- Nhiều child rows làm transaction kéo dài.
- Có thể gây lock contention và tăng transaction log.

Đừng tối ưu sớm nếu số liệu cho thấy cách lưu hiện tại đáp ứng SLO và tải dự kiến.

## 13. Phương án 2: giảm kích thước aggregate

Nếu collection có thể tăng vô hạn, hãy xem lại aggregate boundary. Aggregate nên gom những dữ liệu cần được bảo vệ bởi cùng invariant và cùng transaction, không nhất thiết gom mọi dữ liệu có quan hệ khóa ngoại.

Ví dụ, một PurchaseOrder có thể giữ các thuộc tính quan trọng và một tham chiếu tới OrderLine collection được quản lý độc lập nếu nghiệp vụ cho phép.

Thay vì lưu object con như một phần aggregate, root có thể lưu ID hoặc AggregateReference tới aggregate khác. Khi đó cập nhật một child aggregate không cần save lại toàn bộ root.

Cần đánh giá:

- Child có vòng đời độc lập không?
- Child có thể được cập nhật mà không cần tải root không?
- Invariant nào cần được bảo vệ đồng thời giữa root và child?
- Có cần transaction xuyên hai aggregate không?
- Xóa root có còn xóa child tự động không, hay phải có quy trình riêng?
- Có cần khóa/version độc lập cho child aggregate không?

Việc tách aggregate làm giảm chi phí save root nhưng chuyển trách nhiệm consistency sang application service hoặc transaction boundary khác. Không nên tách chỉ vì số row lớn nếu domain vẫn yêu cầu mọi child thay đổi cùng root như một đơn vị nguyên tử.

## 14. Phương án 3: dùng custom SQL cho thao tác cập nhật nhỏ

Khi aggregate boundary vẫn hợp lý nhưng một số use case cần cập nhật một child row, có thể dùng custom repository fragment, JdbcTemplate hoặc MyBatis để viết targeted SQL.

Ví dụ:

~~~java
public interface OrderLineOperations {
    int updateQuantity(
            Long orderId,
            Integer lineNo,
            int quantity
    );
}
~~~

Implementation dùng NamedParameterJdbcTemplate hoặc mapper phù hợp. Service cần đặt @Transactional và điều phối version, tổng tiền, audit cùng các invariant.

Ưu điểm:

- Chỉ ghi các hàng thực sự cần đổi.
- Có thể giảm index maintenance và transaction log.
- Có thể dùng điều kiện SQL nguyên tử.
- Phù hợp với bulk operation được thiết kế rõ.

Chi phí:

- Phải duy trì SQL cùng schema và dialect.
- Phải tự giữ optimistic locking nếu thay đổi aggregate.
- Callback/auditing của aggregate save không tự chạy.
- Phải reload hoặc đồng bộ object trong bộ nhớ.
- Phải kiểm thử concurrency, rollback và mọi đường ghi khác.

Đây là tối ưu có chủ đích cho use case cụ thể. Không nên chuyển toàn bộ CRUD sang SQL tùy chỉnh chỉ vì một collection lớn.

## 15. Phương án 4: dùng thao tác bulk có giới hạn

Nếu nghiệp vụ cập nhật hàng loạt child theo cùng một điều kiện, một câu UPDATE có thể hiệu quả hơn tải toàn aggregate rồi save:

~~~sql
UPDATE order_lines
SET unit_price = :newPrice
WHERE order_id = :orderId
  AND sku = :sku;
~~~

Hoặc cập nhật nhiều hàng theo danh sách ID. Tuy nhiên, bulk SQL thường bỏ qua entity callbacks và aggregate lifecycle. Cần kiểm tra:

- Có cần tăng version root không?
- Có cần cập nhật tổng tiền hoặc trạng thái root không?
- Có cần ghi audit từng child hay chỉ ghi một sự kiện bulk?
- Có cần optimistic locking cho từng hàng không?
- Danh sách ID có thể vượt giới hạn bind parameter của database không?
- Có cần chia batch để tránh transaction quá lớn?

Bulk operation có thể giảm round trip nhưng tăng độ phức tạp về consistency. Hãy xác định contract trước khi triển khai.

## 16. Phân biệt child entity, embedded object và AggregateReference

Không phải mọi property lồng nhau đều chịu chi phí delete/reinsert như referenced entities.

| Mapping | Lưu trữ | Ảnh hưởng khi save root |
|---|---|---|
| @Embedded | Cột trên cùng bảng với root | Các giá trị embedded được lưu cùng root row |
| @MappedCollection | Entity con ở bảng riêng, thuộc aggregate | Các referenced entities bị delete và insert lại khi save aggregate đã tồn tại |
| AggregateReference | Tham chiếu ID tới aggregate khác | Không kéo toàn bộ aggregate được tham chiếu vào save của root |
| Property ID đơn giản | Giá trị ID được lưu trong cột | Không tự động biến entity được tham chiếu thành child aggregate |

Nếu một collection lớn thực sự là danh sách child thuộc aggregate, delete/reinsert là hành vi cần tính vào thiết kế. Nếu đó là quan hệ giữa hai aggregate độc lập, dùng ID/AggregateReference phù hợp hơn với ranh giới domain.

## 17. Tác động của optimistic locking

Khi aggregate root dùng @Version, Spring Data JDBC kiểm tra version khi cập nhật root. Điều này giúp phát hiện hai transaction cùng sửa một aggregate dựa trên version cũ.

Tuy nhiên, không nên suy ra rằng mỗi child row đều có version độc lập hoặc có thể được cập nhật trực tiếp mà không cần bảo vệ root. Version của root bảo vệ aggregate theo quy tắc lưu của framework.

Khi thay save aggregate bằng custom SQL:

- Kiểm tra expected version trong điều kiện WHERE.
- Tăng version theo quy tắc thống nhất.
- Kiểm tra update count.
- Thực hiện thay đổi child trong cùng transaction.
- Rollback nếu root version không còn khớp.
- Không tiếp tục save một object cũ với version cũ sau direct SQL.

Nếu hai transaction sửa hai child khác nhau của cùng một root, domain có thể yêu cầu một trong hai bị từ chối vì cả aggregate là một đơn vị consistency. Nếu muốn cho phép cập nhật độc lập, có thể đó là tín hiệu để tách child thành aggregate riêng.

## 18. Index và schema cho bảng child

Khi Spring Data JDBC xóa các child theo foreign key của root, điều kiện xóa thường dựa trên cột tham chiếu parent, ví dụ order_id.

Bảng child nên có index/primary key phù hợp với truy vấn và constraint:

~~~sql
CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Primary key ghép bắt đầu bằng order_id có thể hỗ trợ truy vấn/xóa theo order_id trong nhiều DBMS. Nhưng execution plan và index strategy cần xác nhận trên engine thực tế.

Nếu bảng child có thêm index theo sku, status hoặc created_at, mỗi lần delete/insert lại sẽ phát sinh maintenance cho các index đó. Không xóa index tùy tiện chỉ để tăng tốc save; phải cân nhắc các truy vấn đọc và constraint cần bảo vệ.

## 19. Cân nhắc trigger, audit và dữ liệu phụ thuộc

Delete/reinsert có thể kích hoạt trigger theo từng hàng. Nếu trigger ghi audit log, cập nhật counter hoặc phát tín hiệu, một lần save có thể tạo nhiều bản ghi phụ dù nội dung child không đổi.

Cần kiểm tra:

- Trigger BEFORE/AFTER DELETE và INSERT.
- ON DELETE CASCADE trên foreign key.
- Audit table và CDC/change data capture.
- Logical replication hoặc binlog volume.
- Materialized view hoặc bảng tổng hợp được cập nhật bởi trigger.
- External process đọc change stream.

Nếu một lần save root khiến CDC phát ra hàng nghìn delete/insert events, hệ thống downstream có thể chịu chi phí lớn hơn cả transaction database ban đầu.

Hãy xác định liệu consumer quan tâm trạng thái cuối cùng hay từng row event. Nếu cần semantic event “đơn hàng thay đổi”, đừng suy ra event nghiệp vụ từ các row delete/insert kỹ thuật.

## 20. Đánh giá bằng SLO và chi phí vận hành

Không phải mọi chỉ số thấp hơn đều đồng nghĩa kiến trúc tốt hơn. So sánh phương án theo các mục tiêu cụ thể:

| Tiêu chí | Câu hỏi cần trả lời |
|---|---|
| Latency | p95/p99 của save có nằm trong SLO không? |
| Throughput | Database xử lý được số save đồng thời dự kiến không? |
| Write volume | Bao nhiêu child rows bị ghi cho mỗi thay đổi logic? |
| Locking | Có lock wait hoặc deadlock tăng không? |
| Transaction log | WAL/binlog tăng bao nhiêu khi save aggregate lớn? |
| Connection pool | Transaction có giữ connection quá lâu không? |
| Correctness | Invariant, version, audit và rollback có còn đúng không? |
| Complexity | Có bao nhiêu SQL tùy chỉnh và quy tắc phải duy trì? |
| Portability | Có khóa vào một DBMS hoặc driver cụ thể không? |
| Operations | Có thể quan sát, cảnh báo và xử lý lỗi dễ dàng không? |

Một giải pháp targeted SQL có thể giảm latency nhưng tăng đáng kể chi phí bảo trì. Chỉ nên chọn khi mức cải thiện đo được giải quyết vấn đề thật và có test bảo vệ semantics.

## 21. Bảng quyết định

| Tình huống | Hướng phù hợp để bắt đầu |
|---|---|
| Aggregate có 5–20 child rows, save ít | Giữ repository.save đơn giản |
| Aggregate có 100–500 child rows, thay đổi thường xuyên | Đo SQL/latency và xác định hot path |
| Aggregate có hàng nghìn child rows, chỉ đổi root scalar | Cân nhắc tách read/write use case hoặc thu nhỏ aggregate |
| Chỉ cập nhật một child row với tần suất cao | Cân nhắc targeted SQL có version/invariant |
| Child có vòng đời độc lập và được cập nhật riêng | Xem xét child là aggregate root riêng |
| Child phải nhất quán nguyên tử cùng root | Giữ trong aggregate; đo chi phí và tối ưu có kiểm soát |
| Bảng child có trigger/audit/CDC nặng | Đo cả side effects và downstream load |
| Custom SQL giảm thời gian nhưng bỏ qua domain rule | Chưa nên dùng cho tới khi semantics được bảo vệ |

## 22. Checklist đo trước khi tối ưu

Trước khi thay đổi persistence strategy, hãy ghi lại:

- Số child rows điển hình và lớn nhất của aggregate.
- Tần suất save theo từng use case.
- Tỷ lệ lần save chỉ đổi root, chỉ đổi một child hoặc thay đổi nhiều child.
- Số hàng delete/insert thực tế.
- Số SQL statements và batch executions.
- Thời gian transaction và commit.
- p50/p95/p99 latency.
- Index, trigger, foreign key và audit/CDC.
- Mức concurrency và lock wait.
- Version/optimistic locking behavior.
- Cách xử lý cache và object đã load.
- Kết quả benchmark của phương án thay thế.
- Chi phí code/test/maintenance của SQL tùy chỉnh.

Không dùng log SQL bật liên tục trên production như công cụ đo chính. Hãy dùng instrumentation phù hợp và chỉ bật log chi tiết trong khoảng debug có kiểm soát.

## 23. Bài thực hành: đo aggregate 10, 100, 1.000 và 5.000 child rows

Tạo các đơn hàng có số OrderLine tương ứng. Với mỗi kích thước, chạy các trường hợp:

1. Load aggregate, thay status của root, giữ nguyên lines và save.
2. Load aggregate, đổi quantity một line và save.
3. Load aggregate, đổi 1% lines và save.
4. Load aggregate, thay toàn bộ lines và save.
5. Thực hiện targeted UPDATE cho một line bằng custom repository trong transaction có kiểm tra version.
6. So sánh latency, rows affected, transaction duration, index/trigger cost và connection usage.

Ghi kết quả vào bảng:

| Child rows | Kịch bản | Delete rows | Insert rows | p50 | p95 | p99 | Ghi chú |
|---:|---|---:|---:|---:|---:|---:|---|
| 10 | Chỉ đổi root | | | | | | |
| 100 | Chỉ đổi root | | | | | | |
| 1.000 | Chỉ đổi root | | | | | | |
| 5.000 | Chỉ đổi root | | | | | | |
| 5.000 | Đổi một child | | | | | | |
| 5.000 | Targeted update | | | | | | |

Đây là bảng thu thập số liệu, không phải số liệu mẫu. Điền kết quả từ database/driver thật của dự án. Chạy nhiều lần, warm up trước và ghi rõ cấu hình môi trường để kết quả có thể lặp lại.

Sau khi đo, xác định điểm mà chi phí delete/reinsert bắt đầu ảnh hưởng SLO. Nếu chỉ aggregate rất lớn mới gặp vấn đề, tối ưu đúng use case đó thay vì làm phức tạp mọi thao tác persistence.

## 24. Nguyên tắc ghi nhớ

- Khi save một aggregate mới, Spring Data JDBC insert root rồi insert các entity được tham chiếu.
- Khi save aggregate đã tồn tại, Spring Data JDBC xóa referenced entities, cập nhật root và chèn lại referenced entities.
- Framework không giữ trạng thái cũ của aggregate để diff từng child row; vì vậy chỉ đổi một child vẫn có thể ghi lại toàn bộ collection.
- Với N child rows, có thể ước lượng gần N delete và N insert ở mức hàng; số SQL statements/batch thực tế phụ thuộc driver, mapping và database.
- Chi phí bao gồm index maintenance, foreign key checks, trigger, audit, transaction log, lock và connection pool.
- @Embedded nằm trên cùng bảng với root, khác với @MappedCollection có child table.
- AggregateReference biểu diễn tham chiếu tới aggregate khác và không kéo toàn bộ aggregate đó vào save của root.
- Đo trên cardinality và phân phối dữ liệu gần thực tế; thu thập row count, statement/batch count, p50/p95/p99 và database metrics.
- Đo toàn bộ service call từ bên ngoài transaction proxy để tính cả commit.
- Targeted SQL có thể giảm số row changes nhưng phải tự bảo vệ version, invariant, audit, callback và transaction.
- Nếu child có vòng đời độc lập, xem xét tách aggregate; nếu cần consistency nguyên tử cùng root, giữ ranh giới aggregate và đo chi phí.
- Chỉ tối ưu sau khi benchmark chứng minh write amplification ảnh hưởng latency, throughput hoặc chi phí vận hành.

Spring Data JDBC chọn cách lưu aggregate theo trạng thái đầy đủ của object, nên save một aggregate lớn có thể xóa và chèn lại nhiều entity con dù chỉ một phần nhỏ thay đổi. Hãy định lượng số hàng bị ghi và chi phí database trước khi chọn phương án khác. Khi cần targeted update hoặc tách aggregate, phải giữ nguyên các invariant, optimistic locking và transaction semantics mà đường save chuẩn đang cung cấp.
