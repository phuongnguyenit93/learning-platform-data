# Finding, Counting, Checking Existence, and Deleting Aggregates with the Template

In **Spring Data Relational JDBC (Spring Data JDBC)**, beyond repositories, applications can interact directly with aggregates through **JdbcAggregateTemplate**. The template provides operations to find by ID, find by conditions, count aggregates, check existence, and delete aggregates. This approach is useful when a service needs to coordinate multiple persistence operations or use a template API instead of a repository in part of an application.

All operations still follow Spring Data JDBC's aggregate model: the template works with the **aggregate root**, while child objects belonging to the aggregate are mapped according to the relationship configuration. When deleting an aggregate, the application must understand root ownership boundaries, foreign key constraints, and transactions to avoid unintended effects.

## 1. What Is JdbcAggregateTemplate?

`JdbcAggregateTemplate` is Spring Data JDBC's template-level API for aggregate operations. It uses Spring Data JDBC's mapping metadata, dialect, and data access mechanisms to save and load aggregates instead of requiring the application to write all SQL manually for standard operations.

Commonly used operation groups:

| Need | Template API |
|---|---|
| Find a single aggregate by ID | `findById(id, DomainType.class)` |
| Find multiple aggregates by conditions | `findAll(query, DomainType.class)` |
| Check whether a root exists | `existsById(id, DomainType.class)` |
| Count aggregate roots | `count(DomainType.class)` |
| Delete by ID | `deleteById(id, DomainType.class)` |
| Delete from an aggregate instance | `delete(aggregate)` |
| Delete all aggregates of a type | `deleteAll(DomainType.class)` |

Verify exact API names against the Spring Data JDBC version used by your project. In the examples below, we use `JdbcAggregateTemplate` and its common public methods.

### How Does the Template Differ from a Repository?

A repository encapsulates operations under an interface bound to an aggregate type:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long> {
}
~~~

The template is an injected collaborator that takes the aggregate type as a parameter:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();
~~~

Both approaches use Spring Data JDBC mapping and both work with aggregates. Choose the template when you need a generic API, want to coordinate operations inside a service, or want to use `Query` directly. Repositories are usually better suited when you want an explicit per-aggregate interface and derived query methods.

## 2. Preparing the Order Aggregate

Suppose an order has root details and multiple order items:

~~~java
package com.example.sales.order;

import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_position")
    private List<OrderItem> items = new ArrayList<>();

    protected Order() {
        // Required by Spring Data JDBC.
    }

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderItem> getItems() {
        return List.copyOf(items);
    }
}
~~~

Child entity:

~~~java
package com.example.sales.order;

import org.springframework.data.relational.core.mapping.Table;

@Table("order_items")
public class OrderItem {

    private String sku;
    private int quantity;

    protected OrderItem() {
    }

    public OrderItem(String sku, int quantity) {
        this.sku = sku;
        this.quantity = quantity;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }
}
~~~

Illustrative PostgreSQL schema:

~~~sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_items (
    order_id BIGINT NOT NULL REFERENCES sales_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, line_position)
);
~~~

In this example, `Order` is the aggregate root; `OrderItem` is a component owned by the root. The template operations below accept `Order.class`, not `OrderItem.class` for operating independently on order items.

## 3. Injecting JdbcAggregateTemplate

In a Spring Boot application configured with Spring Data JDBC and a `DataSource`, Spring creates and manages the template. You can inject it via constructor injection:

~~~java
package com.example.sales.order;

import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderAggregateService {

    private final JdbcAggregateTemplate template;

    public OrderAggregateService(JdbcAggregateTemplate template) {
        this.template = template;
    }
}
~~~

Do not instantiate `JdbcAggregateTemplate` with `new` inside a service. Spring needs to provide the mapping context, dialect, converters, data access strategy, and related infrastructure components. Injecting the configured bean ensures the template uses the application's proper metadata and transaction infrastructure.

## 4. Finding an Aggregate by ID with findById

The `findById` method accepts the ID and the aggregate root class:

~~~java
Optional<Order> result =
    template.findById(orderId, Order.class);
~~~

Because the order might not exist, the result is represented as `Optional<Order>`. Handling both cases:

~~~java
public Order getOrder(Long orderId) {
    return template.findById(orderId, Order.class)
        .orElseThrow(() -> new IllegalArgumentException(
            "Order not found: " + orderId
        ));
}
~~~

When the `Order` is found, Spring Data JDBC constructs the aggregate according to the declared mapping. Child components belonging to the aggregate, such as the `items` list, are loaded according to Spring Data JDBC's mapping rules.

`findById` does not automatically load independent aggregates referenced by ID. For instance, if `Order` holds `customerId`, the template does not automatically build a `Customer` object. To display `Customer` information, query `Customer` separately or use an appropriate read query.

### Comparing with existsById

If you only need to know whether an `Order` exists, do not load the entire aggregate:

~~~java
boolean exists = template.existsById(orderId, Order.class);
~~~

If you next need to modify the `Order`, calling `findById` directly usually avoids an extra query:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();

// Perform changes on the aggregate root.
~~~

Do not call `existsById` followed by `findById` just to check before loading; `findById` already indicates whether the aggregate was found.

## 5. Finding Multiple Aggregates by Conditions with Query

The template supports querying via Spring Data Relational's `Query` and `Criteria`. Example finding orders with status `OPEN`:

~~~java
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Iterable<Order> orders = template.findAll(
    Query.query(Criteria.where("status").is("OPEN")),
    Order.class
);
~~~

`Criteria.where("status")` refers to the entity property; Spring Data JDBC maps that property to the column via metadata. If the Java property is `createdAt` and the SQL column is `created_at`, query criteria should use the property `createdAt`.

Conditions can be combined:

~~~java
Query query = Query.query(
    Criteria.where("status").is("OPEN")
        .and("customerId").is(customerId)
);

Iterable<Order> orders =
    template.findAll(query, Order.class);
~~~

This example fetches `OPEN` orders for a given `Customer`. The customer condition is a scalar reference on `Order`; the template does not need to load `Customer` to filter by `customerId`.

### Combining Sorting, Limit, and Offset

~~~java
import org.springframework.data.domain.Sort;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Query query = Query.query(
        Criteria.where("status").is("OPEN")
    )
    .sort(Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
    ))
    .limit(20)
    .offset(0);

Iterable<Order> firstBatch =
    template.findAll(query, Order.class);
~~~

The sort order includes `id` as a secondary key to reduce nondeterminism when multiple orders share the same creation timestamp. `limit` caps the number of returned aggregates; `offset` specifies how many results to skip before taking the batch.

Property names in `Sort`/`Criteria` must match the domain type's mapping. Never pass raw column names or arbitrary SQL expressions from a request into `Criteria`/`Sort`; validate and restrict sort choices at the API layer.

## 6. Counting Aggregates with count

The template can count the number of aggregate roots of a type:

~~~java
long totalOrders = template.count(Order.class);
~~~

The return type is `long`, suited for counts that can exceed `int` range. In this example, `count(Order.class)` counts root rows in `sales_orders`, not adding rows from `order_items`.

To count by conditions, pass a `Query`:

~~~java
Query openOrders = Query.query(
    Criteria.where("status").is("OPEN")
);

long openOrderCount = template.count(openOrders, Order.class);
~~~

An example counting orders for a `Customer`:

~~~java
Query customerOrders = Query.query(
    Criteria.where("customerId").is(customerId)
);

long customerOrderCount =
    template.count(customerOrders, Order.class);
~~~

Counting runs in the database and returns only a number. Do not call `findAll(query, Order.class)`, convert to a list, and call `size()` when all you need is the count.

### Counting Roots Differs from Counting Child Components

If an `Order` has 5 `OrderItem`s, it is still **one `Order` aggregate**. Therefore:

~~~java
long orderCount = template.count(Order.class);
~~~

does not return the total number of items. To count order lines, query the `order_items` table using Spring JDBC, a custom query, or another appropriate specialized query. Do not treat `OrderItem.class` as an aggregate root if `OrderItem` is merely an owned component inside `Order`.

## 7. Checking Existence with existsById

To check whether an aggregate root exists by ID:

~~~java
boolean exists = template.existsById(orderId, Order.class);
~~~

Example in a service:

~~~java
public void ensureOrderExists(Long orderId) {
    if (!template.existsById(orderId, Order.class)) {
        throw new IllegalArgumentException(
            "Order not found: " + orderId
        );
    }
}
~~~

`existsById` returns a boolean without returning the `Order` payload. It is well suited for use cases that only need an existence check, such as before returning a status result or validating a reference.

### Checking Existence by Conditions

For a more complex condition, you could query a small slice and inspect the result, but if you only need existence, use a conditional exists API if your template version provides one or use a dedicated SQL `EXISTS` query. Do not load the entire dataset just to check whether a list is empty.

Equivalent SQL example for conditions:

~~~sql
SELECT EXISTS (
    SELECT 1
    FROM sales_orders
    WHERE customer_id = :customerId
      AND status = :status
);
~~~

This SQL illustrates when a multi-condition existence query is needed. `JdbcAggregateTemplate.existsById` is designed for checking by root ID; it does not replace every business `EXISTS` query.

### Exists Does Not Guarantee the Data Will Still Exist Later

One request may verify that an `Order` exists, and then another transaction deletes the `Order` before the first request writes related data. Therefore:

- `existsById` reflects state at the moment of the query.
- Foreign keys and constraints enforce integrity at write time.
- Transactions and locking must be designed for concurrency requirements.
- Always handle errors when writes may conflict with concurrent changes from other requests.

Do not rely on an `exists` result as a guarantee that the record will remain present throughout subsequent steps.

## 8. Deleting an Aggregate by ID with deleteById

When you need to delete an `Order` by ID:

~~~java
template.deleteById(orderId, Order.class);
~~~

The command takes both the ID and the aggregate root type so the template can determine the root table and aggregate mapping. For aggregates with owned child components, Spring Data JDBC handles rows belonging to the aggregate according to the mapping when deleting the root.

Service example:

~~~java
public void deleteOrder(Long orderId) {
    if (!template.existsById(orderId, Order.class)) {
        throw new IllegalArgumentException(
            "Order not found: " + orderId
        );
    }

    template.deleteById(orderId, Order.class);
}
~~~

This snippet provides a clear business error message, but issues two queries and still has a race condition between `exists` and `delete`. If the use case simply needs deletion by ID, you can call `deleteById` directly and handle the outcome or exceptions according to the API contract and constraints of your version.

### Deleting from an Aggregate Instance

If the service has already loaded the `Order` and wants to delete that aggregate:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();

template.delete(order);
~~~

This is appropriate when the use case already needed to load the aggregate to check its status or deletion permissions. Do not load the aggregate solely to delete it if `deleteById` already meets the requirement.

## 9. Deleting All Aggregates with deleteAll

The template provides an operation to delete all aggregates of a given type:

~~~java
template.deleteAll(Order.class);
~~~

This is a broad-impact operation: it deletes every `Order` of that type within the connected database/schema scope. If `Order` owns `OrderItem`, child data is also handled according to the aggregate mapping.

Use it only for administrative tasks, test data resets, or use cases with an explicit requirement. Never invoke it from a public endpoint merely because a client omitted a filter parameter.

If you want to delete conditionally, identify the matching set of IDs and delete them in a controlled transaction, or use a dedicated SQL operation if business rules allow. Do not confuse `deleteAll(Order.class)` with deleting only orders matching a `Criteria`.

## 10. Transactions When Finding, Counting, and Deleting

Template operations can participate in a Spring transaction when sharing the configured `DataSource` and transaction manager. For use cases involving multiple related steps, place transaction boundaries on the application service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderMaintenanceService {

    private final JdbcAggregateTemplate template;

    public OrderMaintenanceService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional
    public void removeDraftOrder(Long orderId) {
        Order order = template.findById(orderId, Order.class)
            .orElseThrow(() -> new IllegalArgumentException(
                "Order not found: " + orderId
            ));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Only draft orders can be removed"
            );
        }

        template.delete(order);
    }
}
~~~

This example demonstrates loading an aggregate, checking its status, and deleting it within the same transaction. If any step throws an error and the transaction rolls back, database operations in that transaction are rolled back by the transaction manager.

Do not assume `@Transactional` solves all race conditions on its own. If two requests concurrently check a status and then delete or update, consider optimistic locking, pessimistic locking, or an appropriate isolation level.

### Read-Only Transactions for Queries

~~~java
@Transactional(readOnly = true)
public long countOpenOrders() {
    Query query = Query.query(
        Criteria.where("status").is("OPEN")
    );
    return template.count(query, Order.class);
}
~~~

`readOnly = true` is metadata/a hint for the transaction manager and persistence infrastructure. It does not replace database read-only permissions and is not a security mechanism.

## 11. Foreign Keys and Deletion Policies

Suppose the `OrderItem` table has an FK pointing to `Order`:

~~~sql
ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_order
FOREIGN KEY (order_id)
REFERENCES sales_orders(id);
~~~

Spring Data JDBC manages child rows belonging to the aggregate when deleting the root. However, if another table references `sales_orders` or `order_items`, database constraints can still prevent deletion.

For example, a `shipments` table referencing `Order`:

~~~sql
CREATE TABLE shipments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales_orders(id),
    tracking_code VARCHAR(80) NOT NULL
);
~~~

If `shipment` is independent data that must be preserved, deleting `Order` may be rejected by the FK. The application must define the business policy: block deletion, cancel/archive the `Order`, handle shipments first, or use an appropriate archival model. Do not blindly enable cascade delete just to bypass historical constraints.

**Deleting an aggregate does not mean deleting every related piece of data across the entire system.** The template only understands ownership relationships in its mapping; other aggregates maintain independent lifecycles and database constraints protect references between them.

## 12. Distinguishing Physical Delete from Soft Delete

The methods `delete`, `deleteById`, and `deleteAll` are persistence-mapping deletions, typically corresponding to physical deletes. They do not automatically flip a `deleted` flag to true or populate `deleted_at`.

If business rules require preserving history:

~~~java
public void cancel() {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException("Order cannot be cancelled");
    }
    status = "CANCELLED";
}
~~~

Persist the aggregate via `update` or `save` using the appropriate mechanism to represent the cancelled state. Subsequent read queries must then filter by status/soft-delete policy if cancelled records should not be displayed.

Soft delete is a domain and query rule; it does not happen automatically simply by using the template.

## 13. Template vs. Repository: Choosing the Right Tool

| Need | Repository | JdbcAggregateTemplate |
|---|---|---|
| Find by ID | `findById(id)` | `findById(id, Order.class)` |
| Check ID existence | `existsById(id)` | `existsById(id, Order.class)` |
| Count all | `count()` | `count(Order.class)` |
| Delete by ID | `deleteById(id)` | `deleteById(id, Order.class)` |
| Find by property | Derived query method | `findAll(Query, Order.class)` |
| Count by Criteria | Derived/custom query | `count(Query, Order.class)` |
| Delete a loaded root | `delete(order)` | `delete(order)` |
| Per-aggregate interface | Very well suited | Requires passing type on each call |

Repositories shine when the API should be discoverable and expose domain-named query methods. The template is useful when a service builds dynamic `Criteria`, works across multiple aggregate types, or uses a generic persistence API.

Do not maintain both a repository and template calls for the exact same operation without a reason. Using one approach consistently per use case keeps code readable and reduces redundant queries.

## 14. Performance and Query Scope

Guidelines when using the template:

1. Use `existsById` when you only need a boolean; do not load the aggregate just to check existence.
2. Use `count` with `Query` when you only need a count; do not load a list and call `size()`.
3. Use `findById` when you actually need the aggregate's data for processing.
4. Use `Criteria` with clear predicates and avoid unbounded `findAll` on large tables.
5. Include a unique key as the final sort criterion when using offset-based pagination.
6. Create indexes suited to actual filter conditions and query ordering.
7. For multi-aggregate JOIN reports, consider Spring JDBC and DTOs instead of loading aggregates and joining in a loop.

Example indexes:

~~~sql
CREATE INDEX idx_sales_orders_status
    ON sales_orders(status);

CREATE INDEX idx_sales_orders_customer_id
    ON sales_orders(customer_id);
~~~

Specific indexes must be based on workload and execution plans. Indexes speed up certain queries while increasing insert/update overhead and storage usage.

## 15. Common Mistakes

| Mistake | Consequence | Resolution |
|---|---|---|
| Calling `findById` just to check existence | Loads object graph unnecessarily | Use `existsById` |
| Calling `findAll` then taking `size()` | Loads many aggregates just to count | Use `count` or `count(Query, type)` |
| Assuming `count(Order.class)` counts `OrderItem`s too | Incorrect reporting metrics | Distinguish root table from child table |
| Calling `deleteById` with a child entity class | Confuses child component with aggregate root | Pass the managed root type |
| Assuming `deleteAll(Query, type)` is always available | Uses a nonexistent API method | Use the public API of your version; filter IDs or custom SQL if needed |
| Assuming deleting root deletes every table with an FK to root | Constraint violation or unintended data loss | Define ownership and reference policies |
| Calling `exists` then `delete` in two steps as a guarantee | Introduces race conditions | Rely on transactions/constraints and handle conflicts |
| Using physical delete for data needing history | Loss of business audit trail | Use a cancelled status or domain soft delete |
| Using `findAll(Query, type)` without limits | Loads too many aggregates | Add filters, limit/offset, or batch processing |
| Mixing template and repository for the same operation needlessly | Persistence flow becomes hard to follow | Pick an API based on needs and stay consistent |

## 17. Key Takeaways

`JdbcAggregateTemplate` provides direct operations on aggregate roots: `findById` to load an aggregate, `findAll(Query, type)` to search by conditions, `count` to count roots, `existsById` to check an ID, and `delete`/`deleteById` to delete aggregates.

Because the template uses Spring Data JDBC's mapping, it understands child components belonging to the aggregate; it does not automatically load or own separate aggregates merely because of a foreign key reference. Use `exists` when you only need a boolean, `count` when you only need a count, `find` when you need the data, and `delete` when business rules allow deletion. For multi-step operations, place transactions on the service, respect FK constraints, and distinguish physical deletion from soft deletion.
