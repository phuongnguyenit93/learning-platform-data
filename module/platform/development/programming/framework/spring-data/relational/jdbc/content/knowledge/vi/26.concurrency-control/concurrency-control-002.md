# Optimistic locking bằng @Version trên aggregate root

Trong **Spring Data Relational JDBC (Spring Data JDBC)**, nhiều request có thể cùng đọc và cập nhật một aggregate. Nếu hai request cùng tải một phiên bản Order, sau đó lần lượt lưu thay đổi, thao tác sau có nguy cơ ghi đè dữ liệu mà thao tác trước vừa cập nhật. Đây là **lost update**.

Spring Data JDBC hỗ trợ **optimistic locking** bằng annotation `@Version` trên aggregate root. Framework dùng giá trị version đã đọc làm điều kiện khi cập nhật. Nếu hàng trong database đã có version khác, thao tác lưu không cập nhật được hàng như mong đợi và Spring báo lỗi xung đột. Cơ chế này phát hiện xung đột mà không khóa hàng trong suốt thời gian người dùng đọc và chỉnh sửa dữ liệu.

## 1. Vấn đề lost update

Giả sử một Order có trạng thái `DRAFT` và version bằng 4. Hai request A và B cùng tải Order đó:

~~~text
Database: Order #501, status = DRAFT, version = 4

Request A                         Request B
---------                         ---------
Đọc version 4                     Đọc version 4
Đổi status thành CONFIRMED        Đổi status thành CANCELLED
Lưu thay đổi                      Lưu thay đổi
Ghi CONFIRMED                     Ghi CANCELLED
~~~

Nếu câu UPDATE chỉ dựa vào ID, request B có thể ghi đè kết quả của A. Ứng dụng không nhận ra rằng dữ liệu mà B dựa vào đã cũ.

Optimistic locking bổ sung điều kiện version vào thao tác ghi:

~~~sql
UPDATE sales_orders
SET status = :newStatus,
    version = :nextVersion
WHERE id = :id
  AND version = :expectedVersion;
~~~

Nếu request A đã đổi version từ 4 thành 5, câu UPDATE của request B với `expectedVersion = 4` không khớp hàng nào. Spring Data JDBC nhận ra không có hàng được cập nhật và báo xung đột optimistic locking.

## 2. Ý nghĩa của @Version

`@Version` thuộc package `org.springframework.data.annotation`:

~~~java
import org.springframework.data.annotation.Version;
~~~

Đặt annotation trên một property version của **aggregate root**:

~~~java
@Version
private Long version;
~~~

Property này là token để nhận biết phiên bản aggregate mà ứng dụng đã đọc. Spring Data JDBC quản lý giá trị version trong quá trình insert/update. Ứng dụng không nên tự tăng hoặc tự gán version trong logic nghiệp vụ.

Một số điểm cần nhớ:

- Version được lưu trong một cột của bảng aggregate root.
- Khi tạo aggregate mới, framework khởi tạo version theo quy tắc của Spring Data JDBC (thông thường bắt đầu từ 0).
- Mỗi lần cập nhật thành công, version được tăng lên.
- Khi cập nhật một aggregate đã đọc với version cũ, framework chỉ ghi nếu version trong database vẫn khớp.
- Nếu không có hàng nào khớp ID và version mong đợi, thao tác thất bại với lỗi optimistic locking.

Tên cột mặc định thường là `version`. Có thể dùng `@Column` nếu schema đặt tên khác.

## 3. Đặt @Version trên aggregate root

Ví dụ entity Order:

~~~java
package com.example.sales.order;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String status;

    @Version
    private Long version;

    protected Order() {
        // Dành cho Spring Data JDBC.
    }

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public Long getVersion() {
        return version;
    }

    public void confirm() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                "Only a draft order can be confirmed"
            );
        }
        this.status = "CONFIRMED";
    }

    public void cancel() {
        if ("CONFIRMED".equals(status)) {
            throw new IllegalStateException(
                "A confirmed order cannot be cancelled here"
            );
        }
        this.status = "CANCELLED";
    }
}
~~~

`version` là metadata persistence để Spring Data JDBC kiểm soát đồng thời. Domain method `confirm()` và `cancel()` không thay đổi version; chúng chỉ thay đổi trạng thái nghiệp vụ.

### Schema database

~~~sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL
);
~~~

Nếu bảng đã có dữ liệu, cần migration thêm cột với giá trị khởi tạo:

~~~sql
ALTER TABLE sales_orders
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
~~~

Kiểu cột phải tương thích với kiểu Java đã chọn. Với schema lớn hoặc database cụ thể, hãy chọn chiến lược migration phù hợp để thêm cột an toàn.

## 4. Version thay đổi như thế nào?

### Khi insert aggregate mới

~~~java
Order order = new Order(101L);
Order saved = orderRepository.save(order);

System.out.println(saved.getId());
System.out.println(saved.getVersion());
~~~

Với một entity mới, Spring Data JDBC khởi tạo version theo cơ chế optimistic locking của framework. Thông thường version đầu tiên là 0. Không tự gán một số version tùy ý trong constructor hoặc controller.

### Khi update aggregate đã tồn tại

~~~java
Order order = orderRepository.findById(501L)
    .orElseThrow();

System.out.println(order.getVersion()); // Ví dụ: 4

order.confirm();
Order saved = orderRepository.save(order);

System.out.println(saved.getVersion()); // Ví dụ: 5
~~~

Khi lưu thành công, framework kiểm tra version cũ và ghi version kế tiếp. Giá trị `saved.getVersion()` phản ánh phiên bản mới mà thao tác lưu đã tạo.

Về mặt logic, thao tác update tương đương:

~~~sql
UPDATE sales_orders
SET status = 'CONFIRMED',
    version = 5
WHERE id = 501
  AND version = 4;
~~~

Đây là SQL minh họa cơ chế compare-and-set; câu SQL thực tế do Spring Data JDBC tạo và có thể khác về placeholder, danh sách cột hoặc cách bind version theo phiên bản framework và dialect.

## 5. Hai transaction cùng cập nhật một aggregate

Giả sử hai transaction cùng đọc Order #501 ở version 4:

~~~mermaid
sequenceDiagram
    participant A as Transaction A
    participant B as Transaction B
    participant DB as Database
    A->>DB: SELECT Order #501, version 4
    B->>DB: SELECT Order #501, version 4
    A->>DB: UPDATE ... WHERE id=501 AND version=4
    DB-->>A: 1 row updated, version becomes 5
    B->>DB: UPDATE ... WHERE id=501 AND version=4
    DB-->>B: 0 rows updated
    B-->>B: Optimistic locking failure
~~~

Kết quả:

1. A đọc version 4 và lưu thành công. Database chuyển version thành 5.
2. B vẫn giữ object có version 4.
3. B lưu với điều kiện version 4.
4. Database không tìm thấy hàng vừa có ID 501 vừa có version 4.
5. Spring Data JDBC ném lỗi optimistic locking thay vì âm thầm ghi đè thay đổi của A.

Optimistic locking không ngăn A và B cùng đọc. Nó phát hiện xung đột tại thời điểm ghi.

## 6. Repository và application service

Repository vẫn là interface CRUD thông thường:

~~~java
package com.example.sales.order;

import org.springframework.data.repository.CrudRepository;

public interface OrderRepository
        extends CrudRepository<Order, Long> {
}
~~~

Service tải aggregate, áp dụng hành vi domain rồi lưu:

~~~java
package com.example.sales.order;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final OrderRepository orders;

    public OrderService(OrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public Order confirm(Long orderId) {
        Order order = orders.findById(orderId)
            .orElseThrow(() -> new IllegalArgumentException(
                "Order not found: " + orderId
            ));

        order.confirm();
        return orders.save(order);
    }
}
~~~

Không cần tự đọc version, tự tạo câu UPDATE hoặc tăng version bằng Java. Khi property được đánh dấu `@Version`, Spring Data JDBC tích hợp kiểm tra version vào quy trình persistence của aggregate.

`@Transactional` đặt ranh giới cho use case đọc–thay đổi–lưu. Optimistic locking vẫn dựa vào điều kiện version ở thao tác ghi; transaction giúp các thay đổi database thuộc cùng use case được commit hoặc rollback nhất quán.

## 7. Lỗi optimistic locking được biểu diễn như thế nào?

Khi version không còn khớp, Spring Data JDBC phát sinh lỗi thuộc hệ thống exception truy cập dữ liệu của Spring, thường là `OptimisticLockingFailureException` (`org.springframework.dao`).

Có thể xử lý ở ranh giới application/API:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OptimisticLockingFailureException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ApiError handleOptimisticLocking(
            OptimisticLockingFailureException exception) {
        return new ApiError(
            "ORDER_CHANGED",
            "Order was changed by another request. Reload and try again."
        );
    }
}

public record ApiError(String code, String message) {}
~~~

HTTP 409 Conflict phù hợp khi client cần tải lại dữ liệu và quyết định lại thao tác. Không trả stack trace hoặc chi tiết SQL nội bộ cho client.

Tên exception cụ thể có thể được bọc trong lớp exception cao hơn tùy đường gọi và phiên bản framework; xử lý ở tầng API nên nhận abstraction phù hợp của Spring DAO.

## 8. Client nên làm gì khi có conflict?

Khi nhận conflict, client có thể:

1. Tải lại aggregate mới nhất.
2. Hiển thị dữ liệu mới và thông báo có thay đổi từ nơi khác.
3. Cho người dùng xem lại thao tác họ định thực hiện.
4. Gửi lại lệnh sau khi người dùng xác nhận, nếu thao tác vẫn hợp lệ.

Không tự động gửi lại object cũ với cùng version. Làm vậy chỉ lặp lại xung đột vì dữ liệu nền vẫn không đổi.

Nếu server muốn retry, phải tải lại aggregate, đánh giá lại quy tắc nghiệp vụ và áp dụng lại **command** lên trạng thái mới. Chỉ retry tự động khi thao tác an toàn, có giới hạn số lần và có thể bảo đảm không nhân đôi side effect.

Ví dụ:

~~~java
// Không nên: giữ nguyên object cũ rồi lặp save.
orders.save(staleOrder);

// Khi retry được nghiệp vụ cho phép:
Order latest = orders.findById(orderId).orElseThrow();
latest.confirm(); // kiểm tra lại trạng thái hiện tại
Order saved = orders.save(latest);
~~~

Đoạn thứ hai chỉ minh họa việc tải lại và áp dụng lại hành vi. Nếu trạng thái mới không còn cho phép confirm, domain method phải từ chối.

## 9. @Version trên aggregate root bảo vệ phạm vi nào?

Spring Data JDBC quản lý dữ liệu theo aggregate root. Vì vậy, version được đặt trên root để bảo vệ việc cập nhật aggregate như một đơn vị.

Giả sử Order gồm:

~~~text
Order (root, version = 4)
├── OrderItem #1
├── OrderItem #2
└── OrderItem #3
~~~

Khi hai request cùng tải Order và thay đổi các thành phần thuộc Order, version ở root giúp phát hiện một request đã lưu aggregate trước. Việc này quan trọng ngay cả khi thay đổi nằm ở collection con.

Không cần đặt một `@Version` riêng trên từng `OrderItem` chỉ để bảo vệ thay đổi thuộc aggregate Order. Spring Data JDBC không xem từng thành phần con như một aggregate root độc lập chỉ vì nó được lưu ở bảng riêng.

### Aggregate khác không tự chia sẻ version

Nếu Order chỉ lưu `customerId` để tham chiếu Customer aggregate khác, thay đổi Customer không tự động tăng version của Order. Hai aggregate có vòng đời và concurrency token riêng.

~~~text
Order (version = 4) ---- customerId ----> Customer (version = 9)
~~~

Lưu Order không đồng nghĩa kiểm tra version của Customer. Nếu một use case cần bảo đảm dữ liệu từ hai aggregate nhất quán với nhau, cần thiết kế transaction và quy tắc phối hợp riêng; không giả định một `@Version` bảo vệ toàn bộ các bảng có liên quan bằng khóa ngoại.

## 10. Optimistic locking và thay đổi collection con

Spring Data JDBC lưu aggregate theo mapping root và các thành phần con. Một lần save có thể cập nhật hàng root và thay đổi các hàng collection. Version trên root giúp phát hiện hai lần lưu cạnh tranh trên cùng aggregate.

Ví dụ hai request cùng tải Order version 2:

- Request A thêm OrderItem và lưu thành công, root version chuyển thành 3.
- Request B xóa một OrderItem trên snapshot version 2 rồi lưu.
- Kiểm tra version của root phát hiện version đã thành 3; B nhận conflict.

Nếu không có version ở root, hai lần ghi collection có thể dẫn đến mất thay đổi tùy chiến lược persistence và thứ tự thao tác.

Transaction rất quan trọng: nếu một phần thao tác ghi aggregate đã chạy trước khi xung đột được phát hiện, transaction phải rollback để không để lại trạng thái ghi dở. Dùng transaction manager phù hợp với `DataSource` của Spring Data JDBC.

## 11. @Version không phải pessimistic locking

Hai cơ chế giải quyết cạnh tranh theo cách khác nhau:

| Tiêu chí | Optimistic locking (`@Version`) | Pessimistic locking |
|---|---|---|
| Khi đọc | Không khóa hàng để giữ quyền cập nhật | Có thể lấy khóa database ngay khi đọc |
| Khi có xung đột | Phát hiện lúc ghi và báo lỗi | Request khác có thể phải chờ khóa |
| Phù hợp | Xung đột ít, đọc nhiều | Xung đột thường xuyên hoặc cần tuần tự hóa |
| Tác động | Không giữ lock trong thời gian người dùng chỉnh sửa | Có thể giữ lock trong transaction |
| Cơ chế | So sánh version | Lock do database quản lý |

Optimistic locking thường phù hợp với request web ngắn: tải dữ liệu, người dùng chỉnh sửa, gửi lệnh cập nhật sau đó. Pessimistic locking có thể phù hợp với quy trình cần giữ tài nguyên trong một transaction ngắn và có nguy cơ tranh chấp cao.

`@Version` không tự tạo `SELECT ... FOR UPDATE`. Nếu nghiệp vụ cần pessimistic lock, hãy thiết kế query/transaction và cơ chế lock phù hợp với database, thay vì kỳ vọng annotation version sẽ khóa hàng.

## 12. Những đường ghi khác phải tôn trọng version

Optimistic locking của Spring Data JDBC chỉ có thể phát hiện thay đổi khi writer cập nhật version theo cùng quy ước.

Giả sử một tác vụ khác dùng `JdbcTemplate` để cập nhật trực tiếp:

~~~sql
UPDATE sales_orders
SET status = :status
WHERE id = :id;
~~~

Nếu câu lệnh không tăng version, một entity cũ trong ứng dụng Spring Data JDBC vẫn có thể mang version hiện tại trong database và ghi đè dữ liệu của tác vụ kia mà không phát hiện xung đột.

Một câu lệnh custom update cần tự thực hiện compare-and-set:

~~~sql
UPDATE sales_orders
SET status = :newStatus,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
~~~

Ứng dụng kiểm tra số hàng bị ảnh hưởng:

- 1 hàng: cập nhật thành công.
- 0 hàng: version không khớp hoặc hàng không tồn tại; cần xác định kết quả nghiệp vụ phù hợp.

Mọi batch job, script, ứng dụng khác hoặc custom SQL cùng ghi vào aggregate phải tuân thủ quy tắc version nếu muốn chia sẻ bảo đảm optimistic locking. Nếu có writer bỏ qua version, cơ chế không còn bảo vệ đầy đủ trước writer đó.

## 13. Version khác updatedAt và audit history

Không dùng version thay cho thời điểm cập nhật hoặc lịch sử thay đổi:

| Thuộc tính | Mục đích |
|---|---|
| `version` với `@Version` | Phát hiện cập nhật dựa trên snapshot cũ |
| `updatedAt` | Ghi nhận thời điểm cập nhật gần nhất |
| Audit log | Lưu ai thay đổi, thay đổi gì và khi nào |
| Event history | Lưu các sự kiện nghiệp vụ theo thời gian |

Version thường là số tăng dần, không phải timestamp. Nó không cho biết ai đã thay đổi aggregate, thay đổi field nào hoặc trạng thái trước đó là gì.

Có thể kết hợp `@Version` với auditing metadata như `@LastModifiedDate` nếu ứng dụng cần cả hai mục tiêu. Hai cơ chế giải quyết hai nhu cầu khác nhau.

## 14. Các lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Quên `@Version` trên root | Update cạnh tranh có thể ghi đè nhau | Thêm property version và cột schema |
| Đặt version trên thành phần con với kỳ vọng bảo vệ cả aggregate | Không phản ánh đúng concurrency boundary | Đặt version trên aggregate root |
| Tự tăng version trong domain method | Framework có thể so sánh sai snapshot hoặc tăng không đúng quy tắc | Để Spring Data JDBC quản lý |
| Không migration cột version cho dữ liệu cũ | Insert/update lỗi vì thiếu cột hoặc NULL | Thêm cột tương thích, khởi tạo version |
| Bắt exception rồi bỏ qua | Client tưởng cập nhật thành công | Trả conflict hoặc xử lý retry có kiểm soát |
| Retry liên tục cùng object cũ | Lặp lại conflict | Tải lại aggregate và đánh giá lại command |
| Nghĩ `@Transactional` tự ngăn mọi race condition | Vẫn có thể có lost update nếu không kiểm tra version | Dùng `@Version` hoặc lock phù hợp |
| Nghĩ `@Version` khóa hàng khi đọc | Hiểu sai cơ chế và thời gian lock | Đây là optimistic check tại lúc ghi |
| Custom SQL không tăng version | Writer khác có thể phá bảo đảm | Dùng điều kiện version và tăng version |
| Nhầm version với audit timestamp | Không có lịch sử nghiệp vụ | Dùng auditing/audit log riêng |
| Nghĩ version Order bảo vệ Customer | Xung đột giữa aggregate không được phát hiện | Mỗi aggregate có concurrency policy riêng |

## 15. Bài thực hành

1. Thêm property `@Version private Long version` vào Order aggregate root.
2. Thêm cột `version BIGINT NOT NULL` vào bảng `sales_orders`; migration dữ liệu cũ với giá trị ban đầu phù hợp.
3. Tạo Order mới, lưu qua repository và quan sát version được khởi tạo.
4. Tải Order, đổi trạng thái, lưu lại và xác nhận version tăng sau lần update thành công.
5. Tải cùng một Order hai lần thành hai object riêng trước khi cập nhật.
6. Lưu object thứ nhất; sau đó thử lưu object thứ hai vẫn mang version cũ.
7. Bắt `OptimisticLockingFailureException` và chuyển thành phản hồi HTTP 409.
8. Tải lại aggregate sau conflict và đánh giá xem command ban đầu còn hợp lệ không.
9. Thử cập nhật một OrderItem trong hai snapshot khác nhau; xác minh version root phát hiện xung đột.
10. Viết một custom SQL update có điều kiện version, tăng version và kiểm tra affected row count.
11. Thử một custom SQL không tăng version trong môi trường kiểm thử để quan sát vì sao nó phá bảo đảm concurrency.
12. So sánh optimistic locking với một transaction dùng pessimistic row lock; ghi nhận thời gian chờ và hành vi khi hai request cùng truy cập.

## 16. Ghi nhớ

`@Version` trên aggregate root cung cấp optimistic locking cho Spring Data JDBC. Framework lưu một version token, tăng token sau mỗi lần cập nhật thành công và chỉ ghi khi version trong database còn khớp với version mà aggregate đã đọc. Khi một request khác đã cập nhật trước, thao tác sau nhận lỗi optimistic locking thay vì âm thầm ghi đè dữ liệu mới.

Đặt version trên root để bảo vệ thay đổi thuộc aggregate, để framework quản lý giá trị và xử lý conflict ở ranh giới application/API. Optimistic locking không khóa hàng trong thời gian đọc, không tự bảo vệ aggregate khác được tham chiếu bằng ID và không thể phát hiện writer bỏ qua version. Mọi đường ghi cần cùng tuân thủ compare-and-increment nếu muốn giữ bảo đảm chống lost update.
