# Keyset Pagination with Custom Queries for Large Datasets in Spring Data JDBC

## 1. Why Do Large Datasets Need Keyset Pagination?

When a table has millions or tens of millions of records, APIs usually cannot load all data at once. The application needs to break results into chunks to cap memory, response latency, and network payload size.

The familiar approach is **offset pagination**: requesting page 1, page 2, then page 3. The SQL typically looks like:

~~~sql
SELECT id, occurred_at, event_type
FROM audit_events
ORDER BY occurred_at DESC, id DESC
LIMIT 50 OFFSET 500000;
~~~

The problem is that the database may still have to locate and skip a large number of rows before returning the next 50 rows. As the offset grows, the cost can increase significantly. Additionally, if data changes between two requests, row positions can shift, causing duplicated or skipped results.

**Keyset pagination** (also called seek pagination) uses the values of the last row on the current page as a marker to find the next page. Instead of saying “skip 500,000 rows”, the application says “fetch rows appearing after this sort key”.

With descending order by timestamp and ID:

~~~sql
SELECT id, occurred_at, event_type
FROM audit_events
WHERE occurred_at < :lastOccurredAt
   OR (
       occurred_at = :lastOccurredAt
       AND id < :lastId
   )
ORDER BY occurred_at DESC, id DESC
LIMIT :limit;
~~~

This condition gives the database an explicit starting point in the data order. With a suitable index, the database can seek from the cursor and read the next rows directly rather than skipping a huge offset.

Keyset pagination is especially useful for event tables, audit logs, transaction histories, large product catalogs, infinite-scroll APIs, and sequential batch-processing jobs.

## 2. Offset Pagination vs. Keyset Pagination

| Criterion | Offset pagination | Keyset pagination |
|---|---|---|
| How a page is identified | Number of rows to skip | Sort-key values of the previous page's last row |
| Query | LIMIT/OFFSET | Cursor predicate and LIMIT |
| First page | Simple | No cursor needed |
| Very deep pages | Can be costly due to skipping many rows | Usually more stable with a suitable index |
| Jumping directly to page N | More convenient | Unnatural; requires a known cursor or sequential traversal |
| Inserts/deletes between requests | Offsets can shift, causing duplicates/skips | Less affected by changes ahead of the cursor |
| Sorting | Can use many sort styles | Requires deterministic ordering and a cursor holding all sort keys |
| Best suited for | Small tables, UIs needing page numbers | Large datasets, sequential traversal |

Keyset pagination does not always replace offset. If a UI needs “go to page 37” or total page counts, offset/`Page` is usually more convenient. If users only need “load more” or a job needs sequential reads, cursors are usually a better fit.

A key requirement of both approaches is that **result ordering must be deterministic**. SQL does not guarantee row order without `ORDER BY`.

## 3. Designing the Cursor: Sort Keys Must Form a Total Order

Suppose an audit table has these columns:

~~~sql
CREATE TABLE audit_events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    event_type VARCHAR(80) NOT NULL,
    payload TEXT
);
~~~

The application wants to display newest events first:

~~~sql
ORDER BY occurred_at DESC
~~~

If multiple events share the same `occurred_at`, the order among them is undefined. An event could shift relative positions across queries. Therefore, a unique tie-breaker key—typically the primary key—is needed:

~~~sql
ORDER BY occurred_at DESC, id DESC
~~~

The cursor must contain **every value needed to pinpoint the position in that order**:

~~~java
public record EventCursor(
        Instant occurredAt,
        Long id
) {}
~~~

Here the cursor is the pair `(occurredAt, id)`. Two events sharing a timestamp are still distinguished by ID.

### 3.1. Key Rules

- The ordering must uniquely identify a position; usually append the primary key as a tie-breaker.
- The cursor must contain every column participating in the ordering.
- The next-page predicate must use the exact order and direction of `ORDER BY`.
- Sort columns should have immutable/stable values during traversal.
- Ideally sort columns are `NOT NULL`; if nulls are allowed, define explicit null ordering and include that rule in the predicate.
- Every page must use the same filters and the same tenant/security scope.

Using only `occurred_at` without `id` can cause rows with equal timestamps to be duplicated or skipped at page boundaries.

### 3.2. Why Use a Composite Key?

A sort key does not have to be the primary key. For example:

~~~sql
ORDER BY priority DESC, created_at ASC, id ASC
~~~

Here the cursor must hold `priority`, `created_at`, and `id`, and the next-page condition must accurately reflect all three sort directions. The more sort columns, the more complex the predicate becomes.

For this lesson's example, two columns `(occurred_at DESC, id DESC)` illustrate a common and manageable case.

## 4. Writing Custom Keyset Queries with `@Query`

Spring Data JDBC lets you declare custom SQL using the `@Query` annotation. We can separate the first-page query and the next-page query.

### 4.1. Entity

~~~java
import java.time.Instant;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("audit_events")
public record AuditEvent(
        @Id Long id,

        @Column("tenant_id")
        UUID tenantId,

        @Column("occurred_at")
        Instant occurredAt,

        @Column("event_type")
        String eventType,

        String payload
) {}
~~~

The entity maps columns with `@Column` when Java property names differ from physical database column names. In custom queries, `SELECT` must return the columns the entity needs for complete mapping.

### 4.2. Repository for the First Page

~~~java
import java.util.List;
import java.util.UUID;

import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface AuditEventRepository
        extends CrudRepository<AuditEvent, Long> {

    @Query("""
        SELECT id, tenant_id, occurred_at, event_type, payload
        FROM audit_events
        WHERE tenant_id = :tenantId
        ORDER BY occurred_at DESC, id DESC
        LIMIT :limit
        """)
    List<AuditEvent> findFirstPage(
            @Param("tenantId") UUID tenantId,
            @Param("limit") int limit
    );
}
~~~

The first page has no cursor. The query simply applies the tenant filter, sorts by the two columns, and fetches up to `limit` rows.

### 4.3. Repository for Subsequent Pages

Add a method:

~~~java
@Query("""
    SELECT id, tenant_id, occurred_at, event_type, payload
    FROM audit_events
    WHERE tenant_id = :tenantId
      AND (
          occurred_at < :lastOccurredAt
          OR (
              occurred_at = :lastOccurredAt
              AND id < :lastId
          )
      )
    ORDER BY occurred_at DESC, id DESC
    LIMIT :limit
    """)
List<AuditEvent> findNextPage(
        @Param("tenantId") UUID tenantId,
        @Param("lastOccurredAt") Instant lastOccurredAt,
        @Param("lastId") Long lastId,
        @Param("limit") int limit
);
~~~

This uses PostgreSQL SQL syntax. Other databases may use different row-limiting syntax such as `FETCH FIRST`, `FETCH NEXT`, or `TOP`. Adjust the SQL to match your application's actual dialect.

The condition has two branches:

1. `occurred_at` less than `lastOccurredAt`: fetches events with older timestamps.
2. `occurred_at` equal to `lastOccurredAt` and `id` less than `lastId`: when timestamps tie, fetches smaller IDs.

Because both columns are sorted descending, subsequent rows must have lexicographically smaller keys than the cursor.

### 4.4. Why Not Use a Simple `id < lastId` Condition?

When the ordering is `occurred_at DESC, id DESC`, IDs do not necessarily increase in lockstep with timestamps across the whole ordering the query demands. Using `id < lastId` alone can skip or fetch wrong rows whenever timestamps do not correlate monotonically with IDs.

The predicate must reflect **the entire `ORDER BY`**. This is the most important rule of keyset pagination.

## 5. A Variant Using Row-Value Comparison

Some databases support tuple/row-value comparisons. In PostgreSQL, you can write:

~~~sql
SELECT id, tenant_id, occurred_at, event_type, payload
FROM audit_events
WHERE tenant_id = :tenantId
  AND (occurred_at, id) < (:lastOccurredAt, :lastId)
ORDER BY occurred_at DESC, id DESC
LIMIT :limit;
~~~

The tuple expression is shorter and directly expresses lexicographical ordering. However, support and optimization vary across databases. The explicit `OR` form in the previous section is readable and usually easier to port across DBMSs, though the query plan still needs checking.

Do not switch to the shorter syntax merely for brevity if the target database does not support it or the planner optimizes it poorly.

## 6. Building a Cursor Page with `limit + 1`

The repository returns `List<AuditEvent>`. The service must decide whether a next page exists, which rows are returned to the client, and which row supplies the next cursor.

A common technique is **fetching one extra row**. If the client requests 50 rows, the query fetches 51 rows:

- If up to 50 rows are returned: there is no next page.
- If 51 rows are returned: there is a next page; discard the 51st row from the current response.

The new cursor must be taken from **the last row returned to the client**, not the extra row.

### 6.1. Response DTO

~~~java
import java.util.List;

public record CursorPage<T>(
        List<T> items,
        EventCursor nextCursor,
        boolean hasNext
) {}
~~~

### 6.2. Service

~~~java
import java.util.List;
import java.util.UUID;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AuditEventQueryService {

    private static final int MAX_PAGE_SIZE = 500;

    private final AuditEventRepository events;

    public AuditEventQueryService(AuditEventRepository events) {
        this.events = events;
    }

    @Transactional(readOnly = true)
    public CursorPage<AuditEvent> readNext(
            UUID tenantId,
            EventCursor cursor,
            int requestedSize
    ) {
        int pageSize = Math.max(1,
                Math.min(requestedSize, MAX_PAGE_SIZE));

        List<AuditEvent> fetched;

        if (cursor == null) {
            fetched = events.findFirstPage(tenantId, pageSize + 1);
        } else {
            fetched = events.findNextPage(
                    tenantId,
                    cursor.occurredAt(),
                    cursor.id(),
                    pageSize + 1
            );
        }

        boolean hasNext = fetched.size() > pageSize;

        List<AuditEvent> items = hasNext
                ? List.copyOf(fetched.subList(0, pageSize))
                : List.copyOf(fetched);

        EventCursor nextCursor = null;

        if (hasNext && !items.isEmpty()) {
            AuditEvent last = items.get(items.size() - 1);
            nextCursor = new EventCursor(last.occurredAt(), last.id());
        }

        return new CursorPage<>(items, nextCursor, hasNext);
    }
}
~~~

In this example, the service caps page size at 500 to prevent clients from requesting overly large pages. This number is only illustrative; systems should tune it based on row size, latency, and database capacity.

`@Transactional(readOnly = true)` creates a read-only transaction for fetching the page. Do not hold a long-running transaction across multiple “load more” clicks. Each request is typically an independent read operation.

### 6.3. Why Is the Cursor Taken from the Last Returned Row?

Suppose page size is 3, and the query fetches 4 rows:

~~~text
Fetched: [A, B, C, D]
Response: [A, B, C]
Next cursor: key of C
~~~

The next page must start after C. If the cursor were taken from D, row D would be skipped because the next query condition only fetches rows after D.

## 7. Creating Proper Indexes for Keyset Queries

Keyset pagination only shines when the database can seek and scan along the filter/order columns. For the query above, a matching index on PostgreSQL might be:

~~~sql
CREATE INDEX idx_audit_events_tenant_time_id
ON audit_events (tenant_id, occurred_at DESC, id DESC);
~~~

Why:

- `tenant_id` comes first because the query always filters by tenant.
- `occurred_at` and `id` follow in the exact traversal order.
- The database can use the index to seek to the target region and scan subsequent rows in order.

If the query has other fixed filters, column order in the index should be re-evaluated based on selectivity and workload. There is no mechanical rule to “put every WHERE column into the index”.

### 7.1. Inspecting the Query Plan

On PostgreSQL, you can run:

~~~sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, tenant_id, occurred_at, event_type, payload
FROM audit_events
WHERE tenant_id = '00000000-0000-0000-0000-000000000001'
  AND (
      occurred_at < TIMESTAMPTZ '2026-01-01 10:00:00+00'
      OR (
          occurred_at = TIMESTAMPTZ '2026-01-01 10:00:00+00'
          AND id < 900000
      )
  )
ORDER BY occurred_at DESC, id DESC
LIMIT 51;
~~~

Check whether the database uses the expected index, whether there is a large sort step, how many rows are read versus returned, buffer hits/reads, and execution time. Query plans can change when the cursor sits in a different data region.

`EXPLAIN ANALYZE` actually executes the query, so use it carefully in production if the query is heavy. Benchmark on data and environments close to production for meaningful results.

### 7.2. Indexes Cannot Compensate for a Wrong Predicate

Having an index with a wrong predicate can still skip or duplicate rows. Conversely, a correct predicate without an index can still scan large amounts of data. All three are required: accurate ordering and cursor logic, an index supporting filter/order, and a query plan confirming the database uses the index effectively.

## 8. Ascending vs. Descending Pagination

The earlier example sorted descending:

~~~sql
ORDER BY occurred_at DESC, id DESC
~~~

The next page uses less-than conditions:

~~~sql
occurred_at < :lastOccurredAt
OR (occurred_at = :lastOccurredAt AND id < :lastId)
~~~

If sorting ascending:

~~~sql
ORDER BY occurred_at ASC, id ASC
~~~

then the next-page condition uses greater-than:

~~~sql
occurred_at > :lastOccurredAt
OR (occurred_at = :lastOccurredAt AND id > :lastId)
~~~

If the sort has mixed directions, such as `priority DESC, created_at ASC, id ASC`, expand the predicate lexicographically:

~~~sql
WHERE priority < :lastPriority
   OR (
       priority = :lastPriority
       AND created_at > :lastCreatedAt
   )
   OR (
       priority = :lastPriority
       AND created_at = :lastCreatedAt
       AND id > :lastId
   )
~~~

Do not flip all comparison operators at once when sort columns have different directions. Each branch must reflect the direction of its corresponding column.

## 9. Cursors and NULL Data

The example uses `occurred_at NOT NULL` to keep predicates simple. If a sort column can be `NULL`, less-than, greater-than, or equality comparisons against `NULL` do not evaluate to true like normal value comparisons.

Two approaches:

- Design sort columns as `NOT NULL` if business rules permit.
- Incorporate null-ordering rules into `ORDER BY`, the cursor, and the predicate.

For example, you can use a null-ranking expression:

~~~sql
ORDER BY
    CASE WHEN occurred_at IS NULL THEN 1 ELSE 0 END,
    occurred_at DESC,
    id DESC
~~~

If choosing this approach, the cursor must include both the null-rank flag and the remaining values; the seek predicate must also compare those exact components. This is more complex and may require an expression index or normalized column depending on the database.

For large datasets, keeping sort columns non-null usually makes cursors and indexes easier to understand and optimize.

## 10. Data Changing Between Pages: Consistency and Limits

Keyset pagination avoids some offset issues, yet **does not create an immutable snapshot for the entire traversal**. Each next-page request typically runs in its own transaction.

For example, in descending order:

- A new event inserted ahead of the cursor usually does not shift rows behind the cursor the way offset pagination does.
- A row deleted before the cursor reaches it will not appear.
- A row inserted with an older timestamp behind the cursor may appear on a later page, even though it was created after traversal began.
- If a row's sort column is updated, the row can move across the cursor, causing duplication or omission.

### 10.1. Use Immutable Sort Columns

For audit logs or event streams, `occurred_at` usually stays unchanged after insertion. Combining it with a unique ID provides a more stable order.

Do not keyset-paginate on a frequently updated column like `display_name`, `status`, or `updated_at` if updates can move rows across the cursor position.

### 10.2. High-Water Mark

If you want to bound the dataset belonging to a single traversal, you can capture a **high-water mark** on the first page—for instance, the highest key at the start time. All subsequent pages add a condition not exceeding that mark.

With descending sort by `(occurred_at, id)`, the first cursor can act as an upper bound. However, a high-water mark only bounds rows by the sort key; it does not create a full snapshot if the system allows late inserts with older timestamps or updates/deletes during traversal.

If strong snapshot consistency is required, consider suitable transaction isolation/snapshots, a snapshot table/materialized result, or persisting the list of IDs to process. Holding a transaction open across many web requests is usually not a good choice because it ties up connections and snapshots for too long.

### 10.3. Data Processing Jobs and Checkpoints

For batch jobs, the cursor can be saved as a checkpoint after each chunk:

~~~text
last_occurred_at = 2026-01-01T10:00:00Z
last_id = 900000
~~~

When the job restarts, queries resume after the checkpoint. To avoid data loss if a job crashes:

- Update the checkpoint only after the chunk has been processed/committed successfully.
- Make processing idempotent so retries do not cause duplicate side effects.
- Persist the checkpoint in the same transaction as processing results when possible and in the same database.
- Define how late-arriving events or modified records are handled.
- Record the filter, tenant, and cursor version to resume the exact query.

A checkpoint should not store only an ID if the query order relies on multiple columns.

## 11. Designing Cursor Tokens for APIs

An API does not need to expose `occurredAt` and `id` as separate query parameters. They can be packaged into a single cursor token:

~~~json
{
  "occurredAt": "2026-01-01T10:00:00Z",
  "id": 900000
}
~~~

The server can serialize JSON, URL-safe Base64-encode it, and return it to the client. On the next request, the client sends back the token for the server to decode.

Notes:

- Base64 is only encoding, **not security encryption**.
- Do not put sensitive information into a cursor token if the token can be inspected.
- If clients must not tamper with cursors, sign tokens with HMAC or use opaque server-stored tokens.
- Bind the cursor to the filter/tenant/sort version so a cursor from one query cannot be used on another.
- Validate malformed, expired, or invalid tokens.
- Enforce page size limits on the server; do not trust client-supplied sizes.

Example response:

~~~json
{
  "items": [
    {
      "id": 900001,
      "eventType": "ORDER_CREATED"
    }
  ],
  "nextCursor": "eyJvY2N1cnJlZEF0IjoiLi4uIiwiaWQiOjk..."
}
~~~

This JSON illustrates an API response structure, not a format mandated by Spring Data JDBC.

## 12. Custom Queries with JdbcTemplate

If query logic must be built dynamically or repository `@Query` is not flexible enough, `NamedParameterJdbcTemplate` can be used. Example:

~~~java
import java.time.Instant;
import java.util.List;
import java.util.UUID;

import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class AuditEventKeysetDao {

    private final NamedParameterJdbcTemplate jdbc;

    public AuditEventKeysetDao(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<AuditEvent> findNext(
            UUID tenantId,
            Instant lastOccurredAt,
            Long lastId,
            int limit
    ) {
        String sql = """
                SELECT id, tenant_id, occurred_at, event_type, payload
                FROM audit_events
                WHERE tenant_id = :tenantId
                  AND (
                      occurred_at < :lastOccurredAt
                      OR (
                          occurred_at = :lastOccurredAt
                          AND id < :lastId
                      )
                  )
                ORDER BY occurred_at DESC, id DESC
                LIMIT :limit
                """;

        var parameters = new MapSqlParameterSource()
                .addValue("tenantId", tenantId)
                .addValue("lastOccurredAt", lastOccurredAt)
                .addValue("lastId", lastId)
                .addValue("limit", limit);

        return jdbc.query(sql, parameters, (rs, rowNum) ->
                new AuditEvent(
                        rs.getLong("id"),
                        rs.getObject("tenant_id", UUID.class),
                        rs.getTimestamp("occurred_at").toInstant(),
                        rs.getString("event_type"),
                        rs.getString("payload")
                )
        );
    }
}
~~~

With `JdbcTemplate`, the application handles mapping `ResultSet` to objects itself. Handle nullable columns, UUID types, and timestamps properly for the driver. When using `JdbcTemplate` instead of a repository, entity `@Column` annotations do not automatically drive a manual `RowMapper`.

This DAO can be used when highly customized SQL is needed, though you must maintain mapping and test against the target database.

## 13. Limitations and Caveats of `@Query`

`@Query` works well for fixed SQL and stable cursor structures. However:

- `LIMIT` syntax is not portable across all databases.
- Table/column names must match the schema and mapping.
- `SELECT` must return enough columns for the target entity or projection.
- Cursor values must be bound as parameters, never concatenated as strings.
- Sort directions and column names cannot safely be substituted via ordinary bind parameters; if clients pick sorts, allowlist predefined queries/sort options.
- Cursors must be validated before calling the repository.
- If many dynamic filters or sorts are required, a custom DAO can be clearer than an overly long repository method.

Keyset pagination usually does not need `Page<T>` with total pages. The goal is fetching the “next page” from a cursor; counting total rows can be expensive and unnecessary for infinite scroll or sequential jobs.

## 14. Common Errors

| Symptom | Cause | Solution |
|---|---|---|
| Rows duplicate across pages | Cursor lacks tie-breaker or cursor came from the extra row | Add ID to sort and take cursor from the last response row |
| Rows are skipped | Predicate mismatches sort direction or uses wrong cursor columns | Write predicate matching the full ORDER BY |
| First page and next pages differ in order | Missing deterministic ORDER BY or mutating sort key | Add a unique tie-breaker and use stable sort columns |
| Deep pages remain slow | Missing suitable index or query plan skips index | Create index matching filter + sort and inspect EXPLAIN |
| Cursors with matching timestamps break | Only using timestamp without ID tie-breaker | Use composite cursor `(occurred_at, id)` |
| NULL rows disappear | Less-than/greater-than comparisons do not treat NULL as regular values | Use NOT NULL or explicit null-ordering predicates |
| New data appears on later pages | Late inserts with sort keys behind the cursor | Choose live-feed semantics or use a high-water mark/snapshot |
| Rows jump across the cursor | Mutable sort column | Choose immutable sort keys or accept mutation semantics |
| Cursor used for wrong tenant/filter | Token is not bound to the original query | Bind cursor to tenant, filters, and sort |
| SQL LIMIT fails on another DB | Row-limiting syntax is dialect-dependent | Use syntax appropriate for the DBMS |
| Entity mapping missing properties | SELECT did not return enough columns | Select all required columns or use a projection |
| Cursor token tampered with | Plain Base64 encoding only | Use HMAC/signature or opaque server-side tokens |

## 15. Keyset Pagination Implementation Workflow

1. Identify the dataset and mandatory filters (e.g., tenant).
2. Choose a stable sort order with a unique tie-breaker.
3. Define the cursor containing all sort columns.
4. Write the first-page query without a cursor.
5. Write the next-page query with a predicate matching the sort order.
6. Create indexes supporting the filters and sort.
7. Use `limit + 1` to determine `hasNext`.
8. Build the cursor from the last actually returned row.
9. Validate cursor tokens and bind them to filters/tenant.
10. Verify consistency when data is inserted, updated, or deleted between requests.
11. Measure query plans and performance on large datasets.
12. Test page boundaries with multiple rows sharing the same sort keys.

## 17. Key Takeaways

- **Keyset pagination** fetches the next page using the sort-key values of the previous page's last row rather than skipping rows with `OFFSET`.
- Ordering must be uniquely determined; append the primary key as a tie-breaker if business sort columns are not unique.
- The cursor holds all sort columns and the predicate must match the exact ASC/DESC directions of `ORDER BY`.
- In Spring Data JDBC, custom cursor queries can be written using `@Query` or `NamedParameterJdbcTemplate`.
- Use `limit + 1` to detect whether a next page exists; the new cursor comes from the last returned row, not the extra row.
- Create indexes matching filters and sort order, then verify query plans on a real database.
- Keyset reduces deep-page access cost with a proper index, yet does not automatically create a consistent snapshot for mutating data.
- Choose stable sort keys, define semantics for late inserts/deletes/updates, and persist checkpoints at the right moment.
- Cursor tokens must be validated and bound to tenant/filters/sort; Base64 is only encoding, not security.
