# `@InsertOnlyProperty` và phạm vi hỗ trợ trên aggregate root

Trong **Spring Data JDBC**, `@InsertOnlyProperty` đánh dấu một thuộc tính chỉ được ghi khi aggregate được tạo mới (`INSERT`); thuộc tính đó không được đưa vào câu `UPDATE` khi lưu aggregate đã tồn tại. Annotation hữu ích cho các giá trị được xác lập một lần, chẳng hạn mã tham chiếu bên ngoài, thời điểm tạo hoặc nguồn khởi tạo bản ghi.

Điểm quan trọng của bài này là **phạm vi hỗ trợ**: `@InsertOnlyProperty` được hỗ trợ trên thuộc tính của **aggregate root**. Không nên suy rộng rằng đặt annotation lên mọi entity con hoặc mọi property trong object graph thì Spring Data JDBC sẽ áp dụng cùng quy tắc. Nếu một giá trị ở child entity cần bất biến sau insert, cần thiết kế đường ghi và cơ chế bảo vệ riêng phù hợp với mô hình đó.

## 1. Vấn đề: một số thuộc tính chỉ có ý nghĩa lúc tạo

Giả sử ứng dụng lưu tài liệu (`Document`). Mỗi tài liệu có:

- `externalReference`: mã được cấp từ hệ thống bên ngoài khi tài liệu được tạo.
- `title`: tiêu đề có thể thay đổi trong suốt vòng đời tài liệu.
- `createdAt`: thời điểm tạo, không nên bị thay đổi bởi các lần sửa sau.
- `version`: phiên bản kỹ thuật để phát hiện cập nhật đồng thời.

Nếu dùng một entity thông thường và gọi `save` mỗi khi đổi tiêu đề, Spring Data JDBC có thể đưa các thuộc tính persistent của root vào lệnh cập nhật. Nhưng `externalReference` và `createdAt` có ý nghĩa chỉ tại thời điểm tạo. Ta muốn database giữ nguyên giá trị ban đầu của hai cột này qua những lần cập nhật sau.

`@InsertOnlyProperty` biểu đạt quy tắc ghi này ngay tại metadata của property: **đưa vào thao tác insert, loại khỏi thao tác update**.

## 2. Khai báo `@InsertOnlyProperty` trên aggregate root

Ví dụ entity dùng Java `record`:

```java
import java.time.LocalDateTime;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.InsertOnlyProperty;
import org.springframework.data.relational.core.mapping.Table;

@Table("documents")
public record Document(
        @Id Long id,
        @Version Long version,
        @InsertOnlyProperty String externalReference,
        String title,
        @InsertOnlyProperty LocalDateTime createdAt
) {}
```

Các annotation có vai trò riêng:

- `@Table("documents")` xác định bảng của aggregate root.
- `@Id` xác định ID.
- `@Version` yêu cầu Spring Data JDBC quản lý version cho optimistic locking.
- `@InsertOnlyProperty` đánh dấu property chỉ được ghi khi insert root.

`@InsertOnlyProperty` nằm trong package `org.springframework.data.relational.core.mapping`. Không nhầm nó với annotation cùng ý nghĩa tự đặt trong ứng dụng hoặc annotation JPA. `@Id` và `@Version` trong ví dụ thuộc `org.springframework.data.annotation`.

DDL minh họa:

```sql
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    external_reference VARCHAR(80) NOT NULL,
    title VARCHAR(200) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Tên Java `externalReference` và `createdAt` được ánh xạ theo naming strategy thông dụng thành `external_reference` và `created_at`. DDL phải có các cột tương ứng; annotation không tạo bảng hoặc cột.

## 3. Khi insert: thuộc tính insert-only vẫn được ghi

Tạo một tài liệu mới:

```java
Document draft = new Document(
        null,
        null,
        "EXT-2026-0042",
        "Thiết kế hệ thống",
        LocalDateTime.of(2026, 11, 13, 9, 0)
);

Document saved = documentRepository.save(draft);
```

Vì aggregate mới chưa có ID/version theo quy tắc nhận diện tương ứng, Spring Data JDBC thực hiện `INSERT`. Các thuộc tính `externalReference` và `createdAt` được đưa vào lệnh insert cùng với `title`:

```sql
INSERT INTO documents (
    version,
    external_reference,
    title,
    created_at
)
VALUES (?, ?, ?, ?);
```

SQL trên minh họa ý nghĩa, không cam kết thứ tự cột hoặc cú pháp generated key giống nhau trên mọi dialect. Database sinh `id`; Spring Data JDBC nhận generated key và trả aggregate sau lưu. Với `record`, hãy dùng object trả về:

```java
Long documentId = saved.id();
Long currentVersion = saved.version();
```

`@InsertOnlyProperty` **không có nghĩa bỏ qua giá trị ở lần tạo**. Ngược lại, property được lưu ở lần insert. Nếu cột là `NOT NULL`, ứng dụng cần cung cấp giá trị hợp lệ hoặc thiết kế cơ chế mặc định ở database một cách tương thích với câu SQL thực tế.

## 4. Khi update: thuộc tính insert-only không được ghi lại

Giả sử tài liệu đã được lưu và có ID `42`, version `0`. Người dùng đổi tiêu đề:

```java
Document changed = new Document(
        saved.id(),
        saved.version(),
        saved.externalReference(),
        "Thiết kế hệ thống - bản cập nhật",
        saved.createdAt()
);

Document updated = documentRepository.save(changed);
```

Khi cập nhật root đã tồn tại, Spring Data JDBC loại các property có `@InsertOnlyProperty` khỏi phần `SET`. SQL có ý nghĩa tương đương:

```sql
UPDATE documents
SET title = ?,
    version = ?
WHERE id = ?
  AND version = ?;
```

Không có `external_reference` hoặc `created_at` trong phần `SET`. Vì thế, database giữ giá trị đã được insert ban đầu, ngay cả khi object đầu vào của lần save có giá trị khác ở hai property đó.

Luồng:

```mermaid
flowchart TD
    A[Load Document root] --> B[Thay đổi title]
    B --> C[repository.save(changed)]
    C --> D[Nhận diện root đã tồn tại]
    D --> E[Tạo UPDATE]
    E --> F[Loại externalReference và createdAt khỏi SET]
    F --> G[Cập nhật title và version]
    G --> H[Database giữ nguyên giá trị insert-only]
```

Đây là điểm khác biệt giữa `@InsertOnlyProperty` và một property persistent thông thường: property thường có thể được ghi trong update, còn insert-only property được giữ lại ở database sau lần tạo.

## 5. Đối tượng Java sau `save` và giá trị đang có trong database

Một điểm cần chú ý với entity bất biến: `@InsertOnlyProperty` điều khiển **các cột được ghi vào SQL**, không tự biến object đầu vào thành bản snapshot mới đọc lại từ database.

Ví dụ:

```java
Document changed = new Document(
        saved.id(),
        saved.version(),
        "EXT-CHANGED-BY-MISTAKE",
        "Tiêu đề mới",
        LocalDateTime.now()
);

Document result = documentRepository.save(changed);
```

SQL update không ghi `external_reference` và `created_at`, nên database vẫn giữ `EXT-2026-0042` và thời điểm tạo ban đầu. Tuy nhiên, không nên giả định object `result` đã được đọc lại từ database để tự khôi phục hai giá trị đó; nó có thể tiếp tục mang giá trị đã truyền vào. Nếu ứng dụng cần một snapshot chắc chắn khớp database sau thao tác, hãy đọc lại aggregate trong transaction/phạm vi phù hợp:

```java
Document persisted = documentRepository.findById(result.id())
        .orElseThrow();
```

Trong thực tế, tốt nhất vẫn là không sửa các property insert-only trong object ở các use case update. Đặt chúng từ lúc tạo và giữ nguyên khi dựng các phiên bản object tiếp theo giúp mô hình Java phản ánh đúng ý nghĩa của dữ liệu.

## 6. Phạm vi hỗ trợ: aggregate root

Spring Data JDBC tổ chức dữ liệu theo aggregate. Repository lưu và nạp aggregate thông qua root; các entity con/collection là phần dữ liệu được root sở hữu. `@InsertOnlyProperty` được hỗ trợ trên **aggregate root**, do đó không nên mặc định annotation có hiệu lực tương tự trên các entity con được ánh xạ bằng `@MappedCollection`.

Ví dụ root có child:

```java
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.InsertOnlyProperty;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @InsertOnlyProperty String sourceSystem,
        @MappedCollection(idColumn = "order_id")
        List<OrderLine> lines
) {}

@Table("order_lines")
public record OrderLine(
        String productCode,
        int quantity
) {}
```

Trong mô hình này, `sourceSystem` là property của aggregate root `PurchaseOrder`; đây là nơi annotation được hỗ trợ. `OrderLine` là entity con trong collection. Không nên đặt `@InsertOnlyProperty` lên `OrderLine.productCode` hoặc `OrderLine.quantity` rồi giả định framework sẽ giữ chúng nguyên vẹn qua các lần lưu aggregate.

Nếu cần quy tắc insert-only cho child, hãy chọn một cách thiết kế có chủ đích:

- Đưa giá trị bất biến lên aggregate root nếu nó thực sự thuộc root về mặt nghiệp vụ.
- Dùng callback/domain logic để bảo toàn giá trị child khi cập nhật collection, nếu phù hợp với vòng đời aggregate.
- Dùng custom SQL hoặc cơ chế database như trigger/permission nếu cần bảo đảm ở tầng lưu trữ; khi đó phải tự kiểm soát transaction, số hàng ảnh hưởng và optimistic locking liên quan.
- Tách child thành aggregate độc lập chỉ khi nó có vòng đời và quy tắc nhất quán riêng; không tách chỉ để né giới hạn annotation.

## 7. Phân biệt property trên root với object nhúng

Object `@Embedded` được trải thành các cột trong bảng root. Nếu một embedded object là property của aggregate root, cần xem metadata của property đó trong bối cảnh root và phiên bản Spring Data Relational đang dùng. Không nên suy rộng hỗ trợ insert-only sang mọi property bên trong mọi kiểu object lồng nhau.

Ví dụ một root có thông tin nguồn tạo được nhúng:

```java
public record Origin(
        String system,
        String reference
) {}

@Table("documents")
public record Document(
        @Id Long id,
        @Embedded(prefix = "origin_")
        @InsertOnlyProperty Origin origin,
        String title
) {}
```

Đoạn này minh họa việc đánh dấu property `origin` của root là insert-only. DDL cần có `origin_system` và `origin_reference`. Khi cập nhật, mục tiêu là không ghi lại các cột thuộc property được đánh dấu. Tuy nhiên, nếu cần kiểm soát chính xác cách annotation tương tác với mapping embedded trong một phiên bản cụ thể, hãy kiểm tra API/reference của đúng phiên bản Spring Data Relational và SQL runtime; không mặc định annotation áp dụng đệ quy lên mọi thuộc tính con của `Origin`.

Với child entity nằm trong `@MappedCollection`, phạm vi hỗ trợ không được mở rộng chỉ vì child có `@Table` hoặc được lưu trong một bảng riêng. Quan hệ sở hữu vẫn đặt child bên trong aggregate root.

## 8. So sánh với các annotation và cơ chế gần nghĩa

| Cơ chế | Ý nghĩa ghi dữ liệu | Khác biệt với `@InsertOnlyProperty` |
|---|---|---|
| `@InsertOnlyProperty` | Ghi property khi insert; bỏ khỏi update | Đây là cơ chế cần dùng cho property của aggregate root chỉ ghi lúc tạo |
| `@ReadOnlyProperty` | Property được đọc từ database nhưng không được ghi theo cơ chế mapping thông thường | Insert cũng không ghi property này |
| `@Transient` | Property không tham gia persistent mapping | Không được xem như một cột đọc/ghi của entity |
| `@Version` | Spring Data quản lý version khi insert/update để phát hiện ghi đồng thời | Version thay đổi qua các lần update; không phải giá trị bất biến |
| `@CreatedDate` | Annotation auditing đánh dấu thời điểm tạo để auditing infrastructure điền giá trị | Tự nó không đồng nghĩa với quy tắc bỏ property khỏi update |
| `DEFAULT` trong DDL | Database cung cấp giá trị mặc định khi insert thỏa điều kiện | Là hành vi của database, không phải metadata insert-only |

Ví dụ, nếu `createdAt` cần được auditing tự điền, có thể dùng `@CreatedDate` và bật JDBC auditing theo cấu hình ứng dụng. Nếu cũng cần ngăn các lần update ghi lại giá trị đó, `@InsertOnlyProperty` thể hiện quy tắc ghi insert-only. Hai annotation giải quyết hai khía cạnh khác nhau: **ai điền giá trị** và **khi nào property được ghi**.

## 9. `@InsertOnlyProperty` không phải ràng buộc bất biến ở database

Annotation ảnh hưởng đến SQL do Spring Data JDBC tạo trong đường lưu aggregate được hỗ trợ. Nó không tự tạo `IMMUTABLE` constraint, không cấm câu SQL khác cập nhật cột và không bảo vệ trước một ứng dụng khác ghi trực tiếp database.

Ví dụ, câu SQL sau vẫn có thể thay đổi cột nếu database user có quyền:

```sql
UPDATE documents
SET external_reference = 'MANUAL-CHANGE'
WHERE id = 42;
```

`@InsertOnlyProperty` không tự chặn câu lệnh đó. Nếu yêu cầu nghiệp vụ hoặc kiểm soát tuân thủ đòi hỏi cột không bao giờ được sửa sau khi tạo, hãy xem xét thêm cơ chế ở database (trigger, quyền cột, stored procedure hoặc quy trình migration được kiểm soát) và bảo đảm mọi đường ghi của ứng dụng tuân thủ cùng quy tắc.

Tương tự, một `@Query` có `UPDATE` tự viết hoặc một đoạn `JdbcTemplate` có thể cập nhật cột insert-only nếu SQL của nó chỉ định cột đó. Annotation không tự phân tích và sửa mọi SQL tùy chỉnh trong ứng dụng.

## 10. Ảnh hưởng của `save`, transaction và optimistic locking

`@InsertOnlyProperty` không thay thế cơ chế nhận diện entity mới/cũ:

- Root mới vẫn đi theo nhánh `INSERT` theo quy tắc `isNew` của Spring Data.
- Root đã tồn tại vẫn đi theo nhánh `UPDATE`.
- Property insert-only được đưa vào insert và loại khỏi update.

Nếu root có `@Version`, câu update vẫn cần kiểm tra version cũ và tăng version sau khi ghi thành công. Các property insert-only bị loại khỏi `SET`, còn cột version vẫn được framework quản lý theo cơ chế optimistic locking.

Ví dụ transaction service:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class DocumentService {
    private final DocumentRepository documents;

    public DocumentService(DocumentRepository documents) {
        this.documents = documents;
    }

    @Transactional
    public Document rename(Long id, String title) {
        Document current = documents.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Document not found"));

        Document changed = new Document(
                current.id(),
                current.version(),
                current.externalReference(),
                title,
                current.createdAt()
        );

        return documents.save(changed);
    }
}
```

Transaction đảm bảo các câu SQL liên quan của use case được commit/rollback theo ranh giới đã chọn. `@InsertOnlyProperty` chỉ ảnh hưởng danh sách cột được ghi trong câu update; nó không tự quyết định transaction boundary.

Nếu hai request cùng cập nhật root, `@Version` vẫn phát hiện xung đột. Property insert-only không làm mất hoặc thay thế optimistic locking.

## 11. Kiểm tra SQL thực tế

Để quan sát khác biệt giữa insert và update, có thể bật log trong môi trường phát triển:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Thực hiện hai thao tác:

1. Tạo `Document` mới và gọi `save`.
2. Nạp document, đổi `title`, gọi `save` lần nữa.

Khi đọc log, so sánh danh sách cột:

| Thao tác | Cột kỳ vọng có mặt | Cột insert-only |
|---|---|---|
| `INSERT` | `external_reference`, `title`, `created_at` và các cột cần thiết khác | Có mặt |
| `UPDATE` | `title`, `version` (nếu có), điều kiện ID/version | Không có trong `SET` |

SQL cụ thể phụ thuộc dialect và phiên bản framework; điều cần kiểm tra là `external_reference` và `created_at` có được loại khỏi phần cập nhật hay không. Không chỉ nhìn object Java sau `save`, vì object trong bộ nhớ không nhất thiết là bản đọc lại từ database.

Không nên bật log bind parameter ở mức chi tiết trong môi trường production nếu các giá trị có thể chứa thông tin nhạy cảm.

## 12. Các lỗi và nhầm lẫn thường gặp

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Property không được ghi ngay lần đầu | Entity không được nhận diện là mới hoặc property không persistent | Kiểm tra `@Id`, `isNew`, metadata và SQL insert |
| Property vẫn đổi trong database sau update | Đường ghi không đi qua cơ chế root được hỗ trợ, custom SQL hoặc mapping khác | Kiểm tra SQL runtime và mọi đường cập nhật |
| Child property vẫn bị ghi lại | Annotation được đặt trên entity con ngoài phạm vi hỗ trợ | Thiết kế lại owner/invariant hoặc dùng cơ chế bảo vệ riêng |
| Object trả về có giá trị khác database | Save không nhất thiết đọc lại toàn bộ row sau update | Dùng giá trị insert-only hiện có từ root; reload nếu cần snapshot |
| Cột `NOT NULL` lỗi khi insert | Giá trị insert-only không được cung cấp hoặc bind null | Cung cấp giá trị hợp lệ hoặc thiết kế default tương thích |
| Thêm annotation nhưng không có hiệu lực với SQL tùy chỉnh | Annotation không viết lại câu `@Query`/`JdbcTemplate` | Đưa điều kiện cột vào SQL và kiểm soát thủ công |
| Version không tăng hoặc update xung đột | DDL thiếu `@Version`, hoặc custom update bỏ qua version | Kiểm tra DDL và optimistic locking path |
| Cột insert-only vẫn bị sửa bởi ứng dụng khác | Annotation không phải database constraint | Dùng trigger/quyền database nếu cần bảo vệ tuyệt đối |

Khi debug, ghi lại: (1) property nằm trên root hay child; (2) SQL insert; (3) SQL update; (4) giá trị database sau khi reload. Bốn dữ kiện này giúp xác định annotation có đang được dùng trong phạm vi hỗ trợ hay đường ghi khác đang bỏ qua nó.

## 13. Bài thực hành: xác nhận insert-only trên root

Với bảng `documents` và entity ở phần đầu, có thể thực hành trên H2 hoặc database thử nghiệm:

1. Tạo một `Document` mới với `externalReference = "EXT-001"` và `createdAt` cố định; gọi `save`.
2. Đọc lại theo ID và ghi nhận hai giá trị được lưu trong database.
3. Tạo một object mới có cùng ID/version nhưng cố ý đổi `externalReference` và `createdAt`, đồng thời đổi `title`; gọi `save`.
4. Đọc lại từ database. Xác nhận `title` thay đổi còn hai cột insert-only giữ giá trị ban đầu.
5. Xem SQL runtime để xác nhận hai cột có trong `INSERT` nhưng không có trong `SET` của `UPDATE`.
6. Thử đặt một property cùng annotation trên child entity trong một ví dụ riêng để kiểm tra giới hạn của phiên bản framework; không dựa vào kết quả ngoài phạm vi hỗ trợ như một hợp đồng ổn định.
7. Thử cập nhật cột bằng SQL trực tiếp trên database thử nghiệm để thấy annotation không thay thế constraint ở tầng database.

Không thực hiện thử nghiệm sửa dữ liệu trên database thật. Khi kiểm tra object sau `save`, phân biệt giá trị đang nằm trong object với giá trị đã được database lưu.

## 14. Nguyên tắc ghi nhớ

- `@InsertOnlyProperty` đánh dấu property được ghi ở lần insert, không được ghi lại trong update do Spring Data JDBC tạo cho phạm vi hỗ trợ.
- Phạm vi hỗ trợ là **property trên aggregate root**; không tự suy rộng sang entity con trong `@MappedCollection`.
- `@Id` vẫn quyết định định danh và cơ chế nhận diện entity mới/cũ; `@Version` vẫn quản lý optimistic locking.
- Annotation không tạo schema, không sinh giá trị mặc định, không tự đọc lại database và không chặn SQL tùy chỉnh.
- Với entity bất biến, dùng object trả về từ `save` để nhận ID/version; reload khi cần xác nhận snapshot database của property insert-only.
- Nếu cần bất biến tuyệt đối trước mọi đường ghi, bổ sung ràng buộc hoặc quyền ở database.

Trong Spring Data JDBC, hãy dùng `@InsertOnlyProperty` cho các giá trị thuộc **aggregate root** được xác lập lúc tạo và cần giữ nguyên qua các lần cập nhật thông thường. Đối chiếu annotation với DDL và SQL runtime, đồng thời giữ rõ ranh giới root/child. Như vậy, metadata phản ánh đúng vòng đời dữ liệu mà ứng dụng muốn bảo vệ, còn các yêu cầu bất biến ở mức toàn database vẫn được xử lý bằng cơ chế phù hợp tại tầng lưu trữ.
