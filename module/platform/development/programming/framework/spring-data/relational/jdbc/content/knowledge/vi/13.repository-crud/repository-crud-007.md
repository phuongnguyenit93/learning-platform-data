# `delete`, `deleteById`, `deleteAllById` và `deleteAll` trong Spring Data JDBC

Trong **Spring Data JDBC**, repository kế thừa `CrudRepository` cung cấp nhiều cách xóa aggregate: truyền một object, truyền một ID, truyền một tập ID hoặc yêu cầu xóa toàn bộ aggregate của repository. Bốn API thường gặp là `delete`, `deleteById`, `deleteAllById` và `deleteAll`.

Các phương thức này khác nhau ở **đầu vào và phạm vi lựa chọn đối tượng**, nhưng đều phải được hiểu trong mô hình aggregate của Spring Data JDBC. Nếu `PurchaseOrder` là aggregate root và có các `OrderLine` thuộc sở hữu, xóa một đơn hàng đồng nghĩa xóa aggregate đó, bao gồm các phần tử con được mapping. Vì vậy, không thể suy luận rằng mỗi phương thức chỉ xóa một hàng trong bảng root.

Bài học giải thích chữ ký API, cách chọn phương thức phù hợp, ảnh hưởng đến quan hệ khóa ngoại, transaction, hiệu năng, xóa hàng loạt và những lỗi thường gặp.

## 1. Bốn phương thức xóa trong `CrudRepository`

Repository CRUD của Spring Data JDBC thường được khai báo như sau:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

`CrudRepository<T, ID>` cung cấp các phương thức xóa chính:

~~~java
void delete(T entity);

void deleteById(ID id);

void deleteAllById(Iterable<? extends ID> ids);

void deleteAll(Iterable<? extends T> entities);

void deleteAll();
~~~

Trong đó:

- `T` là kiểu aggregate root do repository quản lý.
- `ID` là kiểu của thuộc tính được đánh dấu `@Id`.
- Các phương thức trả về `void`; muốn kiểm tra kết quả nghiệp vụ, ứng dụng cần tự xác định điều kiện và đọc dữ liệu cần thiết.

### 1.1. Bảng so sánh nhanh

| Phương thức | Đầu vào | Phạm vi xóa | Khi thường dùng |
|---|---|---|---|
| `delete(entity)` | Một aggregate object | Aggregate có định danh tương ứng | Đã tải aggregate và quyết định xóa object đó |
| `deleteById(id)` | Một ID | Aggregate có ID được chỉ định | Chỉ có ID, không cần giữ object trong code gọi |
| `deleteAllById(ids)` | Iterable các ID | Các aggregate có ID trong danh sách | Có danh sách định danh cần xóa |
| `deleteAll(entities)` | Iterable các aggregate | Các aggregate trong collection | Đã có các object cụ thể cần xóa |
| `deleteAll()` | Không có đầu vào | Tất cả aggregate thuộc repository | Dọn toàn bộ dữ liệu trong môi trường được kiểm soát |

**Lưu ý:** tên `deleteAll` có thể khiến người học nghĩ rằng đây là lệnh SQL `TRUNCATE TABLE`. Không nên giả định như vậy. API có ngữ nghĩa xóa aggregate do repository quản lý; Spring Data JDBC phải xử lý các thành phần thuộc aggregate và các ràng buộc liên quan.

## 2. Mô hình ví dụ: một đơn hàng có nhiều dòng hàng

Để hiểu việc xóa aggregate, sử dụng hai bảng:

~~~text
purchase_orders
├── id (PK)
├── order_number
└── status

order_lines
├── id (PK)
├── order_id (FK -> purchase_orders.id)
├── product_id
└── quantity
~~~

Một đơn hàng có thể chứa nhiều dòng hàng. `PurchaseOrder` là aggregate root, còn `OrderLine` thuộc vòng đời của đơn:

~~~java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;
    private String status;

    @MappedCollection(idColumn = "order_id")
    private Set<OrderLine> lines = new LinkedHashSet<>();

    // Constructor, getter và các phương thức nghiệp vụ được lược bớt.
}
~~~

Bảng con có khóa ngoại:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Khi lưu aggregate, `@MappedCollection(idColumn = "order_id")` cho Spring Data JDBC biết `order_id` là cột liên kết các dòng con với root. Khi xóa root qua repository, framework xử lý các thành phần thuộc aggregate theo mapping, để các dòng con không bị bỏ lại như dữ liệu mồ côi.

Điều này khác với một bảng khác chỉ **tham chiếu** đến đơn hàng. Ví dụ `Shipment` có vòng đời độc lập và có `purchase_order_id` trỏ về đơn hàng thì không mặc nhiên là entity con được xóa cùng aggregate. Cần phân biệt ownership của aggregate với một foreign key bất kỳ.

## 3. `delete(entity)`: xóa một aggregate object

`delete(entity)` nhận một object thuộc kiểu aggregate root:

~~~java
PurchaseOrder order = repository.findById(1001L)
    .orElseThrow();

repository.delete(order);
~~~

Luồng sử dụng:

1. Ứng dụng tải đơn hàng cần xóa.
2. Có thể kiểm tra trạng thái và quyền xóa ở tầng service.
3. Gọi `delete(order)` để yêu cầu repository xóa aggregate tương ứng.

Phương thức này phù hợp khi nghiệp vụ đã cần object để kiểm tra điều kiện trước khi xóa, chẳng hạn chỉ cho phép xóa đơn ở trạng thái `DRAFT`.

### 3.1. Xóa theo định danh, không phải theo mọi field của object

Đừng hiểu `delete(order)` là “tìm một hàng có toàn bộ cột giống object rồi xóa”. Đây là thao tác xóa entity được xác định bằng định danh của nó. Các field như `orderNumber` hoặc `status` không trở thành điều kiện lọc xóa chỉ vì chúng có mặt trong object.

Vì thế, không nên tạo object giả chỉ với vài field rồi dùng `delete(entity)` như một câu SQL tùy ý. Nếu chỉ có ID, `deleteById(id)` diễn đạt ý định rõ hơn.

### 3.2. Object không còn trong database

Theo hợp đồng repository CRUD, thao tác xóa entity không tìm thấy trong persistence store thường được bỏ qua một cách im lặng. Do đó, không nên dựa vào `delete(order)` để xác nhận rằng một bản ghi chắc chắn đã tồn tại và bị xóa đúng một lần.

Nếu use case cần trả kết quả như “đã xóa”, “không tìm thấy” hoặc “không đủ điều kiện xóa”, hãy thiết kế logic kiểm tra và kết quả ở tầng service. Khi có cập nhật đồng thời hoặc optimistic locking, cần xử lý các ngoại lệ tương ứng.

## 4. `deleteById(id)`: xóa khi chỉ có ID

Khi code gọi chỉ biết khóa chính, có thể dùng:

~~~java
repository.deleteById(1001L);
~~~

Ví dụ một service:

~~~java
@Service
public class OrderDeletionService {

    private final PurchaseOrderRepository orders;

    public OrderDeletionService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void deleteDraft(long orderId) {
        PurchaseOrder order = orders.findById(orderId)
            .orElseThrow(() ->
                new NoSuchElementException("Không tìm thấy đơn hàng"));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Chỉ được xóa đơn ở trạng thái DRAFT");
        }

        orders.deleteById(orderId);
    }
}
~~~

Ở đây service tải aggregate trước để áp dụng quy tắc nghiệp vụ. Sau khi điều kiện hợp lệ, service dùng `deleteById` vì mục tiêu thao tác cuối cùng đã được xác định bằng ID.

### 4.1. ID không tồn tại

Theo hợp đồng của `CrudRepository`, nếu ID không có trong persistence store, `deleteById` được bỏ qua. Phương thức không trả về boolean để nói có bao nhiêu hàng thực sự bị xóa.

Nếu API bên ngoài cần trả HTTP `404` khi không tồn tại, hãy kiểm tra trước hoặc dùng một câu lệnh/xử lý có thể xác định số hàng bị tác động. Tuy nhiên, mô hình “kiểm tra rồi xóa” có thể gặp race condition nếu dữ liệu thay đổi giữa hai thao tác. Khi yêu cầu chặt chẽ, hãy xác định cách xử lý cạnh tranh và transaction phù hợp.

### 4.2. Không dùng `deleteById` để bỏ qua quy tắc domain

Một controller gọi thẳng:

~~~java
repository.deleteById(orderId);
~~~

có thể bỏ qua điều kiện như trạng thái đơn, quyền sở hữu hoặc yêu cầu lưu lịch sử. Nên để controller gọi application service; service tải aggregate, áp dụng quy tắc và yêu cầu repository thực hiện xóa.

## 5. `deleteAllById(ids)`: xóa theo một tập ID

Khi có một danh sách ID:

~~~java
List<Long> ids = List.of(1001L, 1002L, 1003L);
repository.deleteAllById(ids);
~~~

Phương thức nhận `Iterable<? extends ID>`, nên đầu vào không bắt buộc là `List`. Có thể truyền `Set`, collection hoặc một iterable khác phù hợp.

Ví dụ:

~~~java
Set<Long> selectedIds = Set.of(1001L, 1005L, 1010L);
repository.deleteAllById(selectedIds);
~~~

### 5.1. Khác gì với việc lặp `deleteById`?

Về ý nghĩa, `deleteAllById(ids)` biểu đạt một yêu cầu xóa nhiều aggregate theo ID. Không nên giả định API này luôn biến thành **một câu SQL duy nhất** hoặc một bulk delete tối ưu ở database. Việc thực thi cụ thể phụ thuộc implementation và phiên bản Spring Data JDBC; việc xóa aggregate còn phải tính đến các phần tử con được mapping.

Nếu hiệu năng là yêu cầu quan trọng, hãy đo SQL thực tế, số round-trip, kích thước tập ID và cách framework xử lý aggregate. Đừng suy luận rằng có chữ `All` thì chắc chắn database chỉ nhận một câu `DELETE ... WHERE id IN (...)`.

### 5.2. ID không tồn tại và ID trùng lặp

Nếu iterable có ID không tồn tại, repository CRUD thường bỏ qua ID đó theo ngữ nghĩa xóa. Nếu iterable có ID trùng, không nên dựa vào số lần framework xử lý ID đó; hãy chuẩn hóa danh sách đầu vào bằng `Set` nếu ý định là xóa mỗi định danh một lần.

Không truyền `null` làm iterable hoặc phần tử ID. Hãy xác thực dữ liệu đầu vào trước khi gọi repository, đặc biệt khi ID đến từ HTTP request hoặc file import.

### 5.3. Ví dụ service xóa nhóm đơn nháp

~~~java
@Service
public class BulkOrderService {

    private final PurchaseOrderRepository orders;

    public BulkOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void deleteDraftOrders(Collection<Long> ids) {
        if (ids == null || ids.isEmpty()) {
            return;
        }

        Set<Long> uniqueIds = new LinkedHashSet<>(ids);

        // Ví dụ này giả định use case đã xác định tập ID đủ điều kiện.
        orders.deleteAllById(uniqueIds);
    }
}
~~~

Đoạn code chỉ minh họa cách chuẩn hóa danh sách và đặt ranh giới transaction. Trong hệ thống thật, nếu chỉ được xóa đơn `DRAFT`, service cần tải/kiểm tra các aggregate tương ứng hoặc dùng một cơ chế truy vấn phù hợp để bảo đảm điều kiện trước khi xóa. Không thể chỉ dựa vào tên method `deleteAllById` để bảo vệ quy tắc trạng thái.

## 6. `deleteAll(entities)`: xóa một tập aggregate object

Khi đã có các aggregate object cần xóa, dùng:

~~~java
List<PurchaseOrder> ordersToDelete = List.of(orderA, orderB);
repository.deleteAll(ordersToDelete);
~~~

Phương thức này phù hợp khi code gọi đã tải object và đã xử lý nghiệp vụ trên chúng. Ví dụ:

~~~java
List<PurchaseOrder> selected = new ArrayList<>();

for (Long id : requestedIds) {
    PurchaseOrder order = repository.findById(id)
        .orElseThrow(() ->
            new NoSuchElementException("Không tìm thấy đơn " + id));

    if (!"DRAFT".equals(order.getStatus())) {
        throw new IllegalStateException(
            "Có đơn không ở trạng thái DRAFT");
    }
    selected.add(order);
}

repository.deleteAll(selected);
~~~

Đây là cách diễn đạt rõ ràng khi cần kiểm tra từng aggregate trước khi xóa. Nếu tập dữ liệu lớn, việc tải tất cả object và collection con có thể tốn bộ nhớ và nhiều truy vấn; hãy đánh giá lại cách thực hiện thay vì mặc định dùng phương thức này cho hàng triệu aggregate.

### 6.1. Khác `deleteAllById`

| Điểm khác | `deleteAllById(ids)` | `deleteAll(entities)` |
|---|---|---|
| Đầu vào | ID | Aggregate object |
| Cần có object trong code gọi? | Không | Có |
| Phù hợp khi | Chỉ có định danh cần xóa | Đã tải object và cần kiểm tra domain |
| Mục tiêu | Xóa theo ID | Xóa các aggregate được cung cấp |
| Có phải bulk SQL chắc chắn? | Không | Không |

Không nên tạo entity giả từ ID rồi truyền vào `deleteAll(entities)` chỉ để đổi kiểu đầu vào. Dùng `deleteAllById` trực tiếp sẽ diễn đạt đúng ý định và tránh object không đầy đủ.

## 7. `deleteAll()`: xóa tất cả aggregate của repository

Phương thức không tham số:

~~~java
repository.deleteAll();
~~~

có phạm vi rộng nhất: yêu cầu xóa **tất cả aggregate root do repository quản lý**. Nếu repository quản lý `PurchaseOrder`, nó có thể xóa tất cả đơn hàng cùng các `OrderLine` thuộc sở hữu theo mapping.

Đây là thao tác hữu ích trong:

- Dọn dữ liệu thử nghiệm trong môi trường test.
- Reset dữ liệu của một bảng aggregate trong môi trường phát triển.
- Một quy trình quản trị có chủ đích, được giới hạn quyền và môi trường.

Không nên gọi `deleteAll()` từ endpoint công khai hoặc luồng nghiệp vụ thông thường. Một lỗi truyền nhầm repository hoặc môi trường có thể xóa toàn bộ dữ liệu của loại aggregate đó.

### 7.1. Không đồng nghĩa với `TRUNCATE`

`deleteAll()` là API repository. Nó không cam kết:

- Chạy đúng một câu SQL `TRUNCATE TABLE`.
- Reset identity/sequence.
- Bỏ qua foreign key hoặc trigger.
- Xóa dữ liệu ở các aggregate độc lập chỉ vì chúng có tham chiếu đến root.
- Có cùng hiệu năng với lệnh truncate riêng của database.

Spring Data JDBC phải tôn trọng mapping aggregate và ràng buộc quan hệ. Nếu cần truncate bảng trong test hoặc migration, đó là thao tác SQL riêng, cần hiểu ảnh hưởng đến tất cả bảng liên quan và cơ chế quản lý schema.

### 7.2. Cẩn trọng với repository nhiều tenant

Nếu ứng dụng dùng chung bảng cho nhiều tenant, `deleteAll()` không tự hiểu phạm vi tenant của người dùng. Một repository CRUD thông thường không tự biến thao tác này thành “xóa mọi aggregate của tenant hiện tại”. Hãy thiết kế query và service có điều kiện tenant rõ ràng; không dùng `deleteAll()` cho thao tác xóa theo tenant.

## 8. Điều gì xảy ra với bảng con và foreign key?

Đây là điểm đặc biệt quan trọng trong Spring Data JDBC. Giả sử:

~~~text
purchase_orders
id = 1001

order_lines
id = 1, order_id = 1001
id = 2, order_id = 1001
id = 3, order_id = 1002
~~~

Khi xóa aggregate `PurchaseOrder` có ID `1001`, các `OrderLine` thuộc aggregate đó phải được xử lý cùng root. Kết quả mong đợi:

~~~text
Trước:
  purchase_orders: 1001, 1002
  order_lines:     (1,1001), (2,1001), (3,1002)

Sau khi xóa aggregate 1001:
  purchase_orders: 1002
  order_lines:     (3,1002)
~~~

Spring Data JDBC biết quan hệ sở hữu từ `@MappedCollection` và quản lý các thành phần aggregate khi xóa root. Thứ tự lệnh SQL cụ thể phụ thuộc implementation; về mặt ràng buộc, các hàng con cần được xử lý để không vi phạm foreign key khi xóa hàng cha.

### 8.1. Foreign key của aggregate khác

Giả sử có bảng `shipments`:

~~~sql
CREATE TABLE shipments (
    id BIGINT PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL,
    tracking_number VARCHAR(80) NOT NULL,
    FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_orders(id)
);
~~~

Nếu `Shipment` là aggregate độc lập, việc xóa `PurchaseOrder` không mặc nhiên có nghĩa xóa `Shipment`. Foreign key có thể chặn thao tác xóa root, hoặc database có hành động `ON DELETE` đã cấu hình. Ứng dụng phải quyết định nghiệp vụ:

- Không cho xóa đơn nếu đã có shipment.
- Hủy shipment theo một use case riêng trước khi xóa đơn.
- Dùng soft delete hoặc lưu trạng thái hủy thay vì xóa vật lý.
- Chọn hành động cascade ở database nếu đúng với lifecycle và đã đánh giá tác động.

Không nhầm **entity con thuộc aggregate** với **aggregate khác có foreign key tham chiếu**.

### 8.2. Có nên thêm `ON DELETE CASCADE`?

Có thể dùng `ON DELETE CASCADE` ở database trong một số mô hình, nhưng không cần thêm nó chỉ để Spring Data JDBC hiểu `@MappedCollection`. Mapping aggregate và ràng buộc database là hai lớp khác nhau.

Nếu database cascade đồng thời với framework xóa tường minh các phần tử con, cần kiểm tra hành vi thực tế, trigger và audit. Hãy chọn một thiết kế nhất quán và kiểm tra migration trên database mục tiêu.

## 9. Transaction khi xóa một hoặc nhiều aggregate

Một lệnh xóa aggregate thường cần nhiều thao tác database, đặc biệt khi có bảng con. Nếu use case còn có bước kiểm tra hoặc cập nhật dữ liệu liên quan, đặt transaction ở service để các bước cùng thành công hoặc rollback theo yêu cầu.

~~~java
@Service
public class OrderService {

    private final PurchaseOrderRepository orders;

    public OrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void cancelAndDeleteDraft(long id) {
        PurchaseOrder order = orders.findById(id)
            .orElseThrow(() ->
                new NoSuchElementException("Không tìm thấy đơn"));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Chỉ đơn nháp mới được xóa");
        }

        // Có thể ghi audit hoặc thực hiện thao tác nghiệp vụ liên quan ở đây.
        orders.delete(order);
    }
}
~~~

Spring quản lý transaction cho phương thức service khi lời gọi đi qua proxy. Mặc định, unchecked exception thường kích hoạt rollback; nếu có checked exception hoặc quy tắc rollback riêng, cần khai báo phù hợp.

### 9.1. Xóa nhiều aggregate có cần một transaction không?

Điều đó phụ thuộc nghiệp vụ:

- Nếu yêu cầu “xóa cả nhóm hoặc không xóa gì”, đặt toàn bộ thao tác trong một transaction.
- Nếu mỗi đơn có thể được xóa độc lập và tập rất lớn, có thể xử lý theo batch nhỏ, mỗi batch có transaction riêng và ghi nhận tiến độ.
- Nếu có bước gọi dịch vụ ngoài, không giữ transaction database mở trong lúc chờ network lâu. Cân nhắc quy trình bất đồng bộ, outbox hoặc saga khi phù hợp.

`deleteAllById` và `deleteAll(entities)` không tự trả về số lượng bản ghi đã xóa để ứng dụng xây tiến độ. Nếu cần audit số lượng, hãy thiết kế cách đo và ghi nhận riêng.

### 9.2. Optimistic locking và thao tác xóa

Nếu aggregate có `@Version`, version tham gia cơ chế optimistic locking của Spring Data JDBC. Khi dữ liệu thay đổi đồng thời, ứng dụng cần xử lý ngoại lệ optimistic locking theo phiên bản framework và đường xóa đang sử dụng. Dùng aggregate mới tải từ database và không giữ object cũ quá lâu trước khi xóa.

Không nên bắt mọi ngoại lệ rồi bỏ qua. Một xung đột có thể cho biết trạng thái đã đổi và điều kiện xóa không còn hợp lệ.

## 10. Xóa vật lý và soft delete

Các phương thức `delete...` của `CrudRepository` biểu đạt việc **xóa aggregate khỏi persistence store**. Chúng không tự động biến thành soft delete.

Soft delete là khi hàng vẫn tồn tại nhưng được đánh dấu, ví dụ:

~~~sql
ALTER TABLE purchase_orders
ADD COLUMN deleted_at TIMESTAMP NULL;
~~~

Thay vì gọi `deleteById`, ứng dụng cập nhật cột:

~~~java
@Modifying
@Query("""
    UPDATE purchase_orders
    SET deleted_at = CURRENT_TIMESTAMP
    WHERE id = :id AND deleted_at IS NULL
    """)
int markDeleted(@Param("id") Long id);
~~~

Đây là ví dụ SQL tùy chỉnh để minh họa; annotation và chữ ký query cụ thể cần phù hợp phiên bản Spring Data JDBC đang dùng. Một cách khác là tải aggregate, thay đổi trạng thái `deletedAt` rồi `save()` root.

Khi dùng soft delete, phải định nghĩa:

- Các query thông thường có loại bỏ hàng đã xóa không?
- Có cho phép khôi phục không?
- Unique constraint có tính cả hàng đã xóa không?
- Các bảng con có bị đánh dấu cùng không?
- Báo cáo và audit có cần thấy dữ liệu đã xóa?

Chỉ thêm `deleted_at` không đủ để toàn ứng dụng tự động bỏ qua dữ liệu đã xóa. Cần áp dụng điều kiện nhất quán ở query/repository/service.

## 11. Hiệu năng và xóa số lượng lớn

Không phải phương thức có tên “All” đều là bulk SQL. Với aggregate nhiều bảng, Spring Data JDBC phải giữ đúng quan hệ sở hữu và xóa các thành phần liên quan. Vì vậy, chi phí phụ thuộc:

- Số lượng aggregate cần xóa.
- Số entity con trong mỗi aggregate.
- Số lần round-trip đến database.
- Index trên khóa chính và khóa ngoại.
- Trigger, foreign key và các constraint.
- Kích thước transaction và mức độ cạnh tranh với giao dịch khác.

### 11.1. Xóa theo từng ID

~~~java
for (Long id : ids) {
    repository.deleteById(id);
}
~~~

Cách này dễ kiểm soát từng ID nhưng có thể tạo nhiều thao tác repository. Dùng khi số lượng nhỏ hoặc cần xử lý lỗi riêng từng mục.

### 11.2. Dùng `deleteAllById`

~~~java
repository.deleteAllById(ids);
~~~

Đây là API diễn đạt ý định xóa nhiều aggregate theo ID. Vẫn cần đo hành vi SQL thực tế của phiên bản đang dùng, nhất là khi aggregate có child collection.

### 11.3. Dùng SQL bulk trực tiếp

Nếu có nhu cầu dọn dữ liệu rất lớn, có thể cân nhắc SQL riêng qua Spring JDBC. Tuy nhiên, SQL bulk trực tiếp **đi vòng qua lifecycle và quy tắc aggregate của repository**. Cần tự xử lý thứ tự xóa bảng con/bảng cha, audit, ràng buộc, sự kiện và các invariant nghiệp vụ.

Ví dụ về mặt relational, nếu chủ động xóa các đơn theo một tập ID:

~~~sql
DELETE FROM order_lines
WHERE order_id IN (1001, 1002, 1003);

DELETE FROM purchase_orders
WHERE id IN (1001, 1002, 1003);
~~~

Hai câu lệnh cần nằm trong transaction phù hợp. Đây chỉ là minh họa cho thứ tự quan hệ; không nên sao chép vào production mà chưa xác định các aggregate con khác, audit, foreign key và quyền xóa.

### 11.4. Xóa theo batch

Với tập dữ liệu lớn, batch nhỏ có thể giúp giới hạn thời gian transaction và bộ nhớ. Một quy trình batch nên:

1. Lấy một nhóm ID theo tiêu chí ổn định.
2. Xác nhận điều kiện xóa.
3. Xóa trong transaction của batch.
4. Ghi nhận kết quả và lỗi.
5. Tiếp tục từ checkpoint an toàn.

Nếu dùng phân trang offset trong khi đang xóa các hàng của chính truy vấn đó, có thể bỏ sót dữ liệu vì vị trí hàng thay đổi. Dùng keyset pagination hoặc snapshot/ID range phù hợp với mô hình dữ liệu.

## 12. Các lỗi thường gặp

| Hiện tượng | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Xóa root thất bại do foreign key | Bảng khác tham chiếu đến root hoặc mapping child chưa đúng | Phân biệt owned child và aggregate tham chiếu; xử lý theo nghiệp vụ |
| Dòng con còn sót sau khi xóa | Quan hệ con không được mapping vào aggregate hoặc dữ liệu được ghi ngoài repository | Kiểm tra `@MappedCollection`, schema và đường ghi |
| Dùng `deleteAll()` nhưng chỉ muốn xóa một tenant | Chọn API không có điều kiện | Viết query/service giới hạn tenant, không gọi xóa toàn bộ |
| `delete(entity)` không xóa theo status | Method xóa theo định danh, không dùng mọi field làm predicate | Dùng query có điều kiện hoặc kiểm tra nghiệp vụ ở service |
| Nghĩ `deleteAllById` chỉ chạy một SQL | Nhầm tên API với bulk statement | Quan sát SQL và đo hiệu năng theo phiên bản |
| Xóa nhiều aggregate nhưng lỗi giữa chừng | Transaction boundary không đáp ứng yêu cầu atomicity | Xác định transaction toàn nhóm hay batch transaction |
| Gọi xóa nhưng cần giữ lịch sử | Đang dùng physical delete | Thiết kế soft delete/audit phù hợp |
| Batch xóa bỏ sót dữ liệu | Phân trang offset trên tập đang bị thay đổi | Dùng keyset pagination hoặc tập ID ổn định |
| Xóa đơn nhưng shipment bị ảnh hưởng ngoài ý muốn | Nhầm foreign key tham chiếu với ownership | Tách aggregate và định nghĩa quy trình xóa rõ ràng |

## 13. Chọn API nào trong tình huống thực tế?

| Tình huống | API thường phù hợp | Lý do |
|---|---|---|
| Đã tải aggregate và cần xóa object đó | `delete(entity)` | Ý định gắn với object đang được kiểm tra |
| Chỉ nhận ID từ request và không cần object trong code gọi | `deleteById(id)` | Đầu vào tối thiểu, rõ định danh |
| Có danh sách ID cần xóa | `deleteAllById(ids)` | Biểu đạt tập định danh |
| Đã tải và xác nhận nhiều aggregate | `deleteAll(entities)` | Xóa đúng các object đã chọn |
| Reset dữ liệu toàn bộ repository trong môi trường kiểm soát | `deleteAll()` | Phạm vi toàn bộ aggregate của repository |
| Xóa có điều kiện nghiệp vụ hoặc tenant | Service/query chuyên biệt | Các API xóa cơ bản không nhận predicate |
| Xóa cực lớn theo SQL tối ưu riêng | SQL bulk có kiểm soát | Cần tự chịu trách nhiệm về aggregate, FK và audit |
| Cần giữ lịch sử | Soft delete hoặc trạng thái hủy | `delete...` là xóa khỏi persistence store |

## 14. Bài tập thực hành

### Bài 1 — So sánh hai cách xóa một đơn

1. Tải đơn bằng `findById`.
2. Gọi `delete(order)`.
3. Tạo đơn mới và gọi `deleteById(orderId)`.
4. Đọc trực tiếp hai bảng `purchase_orders` và `order_lines`.
5. Giải thích vì sao cả hai cách đều xóa aggregate, dù đầu vào khác nhau.

### Bài 2 — Xóa nhiều ID

1. Tạo năm đơn, mỗi đơn có hai dòng hàng.
2. Gọi `deleteAllById` với ba ID.
3. Truy vấn số đơn còn lại và số dòng hàng còn lại.
4. Thử truyền một ID không tồn tại và quan sát hợp đồng xóa.
5. Xem log SQL để hiểu chi phí thực thi, không giả định một câu SQL duy nhất.

### Bài 3 — Xóa nhiều aggregate object

1. Tải một nhóm đơn nháp.
2. Kiểm tra tất cả đều ở trạng thái `DRAFT`.
3. Gọi `deleteAll(entities)`.
4. Thêm một đơn `SUBMITTED` và bảo đảm service từ chối xóa nếu quy tắc nghiệp vụ không cho phép.

### Bài 4 — Xóa tất cả trong test

1. Tạo nhiều aggregate và dòng con.
2. Gọi `deleteAll()`.
3. Xác nhận repository không còn root và các dòng con thuộc aggregate đã được xử lý.
4. Thử tạo một aggregate mới sau khi dọn dữ liệu.
5. Giải thích vì sao `deleteAll()` không đồng nghĩa `TRUNCATE` hoặc reset sequence.

## 15. Kết luận

`delete(entity)` xóa aggregate được chỉ định bằng object; `deleteById(id)` xóa theo một định danh; `deleteAllById(ids)` nhận tập ID; `deleteAll(entities)` nhận tập aggregate object; và `deleteAll()` yêu cầu xóa toàn bộ aggregate của repository. Khác biệt chính nằm ở đầu vào và phạm vi lựa chọn.

Trong **Spring Data JDBC**, các thao tác xóa phải được hiểu theo ranh giới aggregate. Nếu root sở hữu các entity con qua `@MappedCollection`, việc xóa root xử lý cả các thành phần thuộc aggregate. Một bảng khác chỉ tham chiếu root bằng foreign key không mặc nhiên bị xóa cùng; quy tắc đó phụ thuộc ownership, constraint và nghiệp vụ.

Hãy đặt điều kiện xóa, quyền hạn và transaction ở application service; chọn API repository đúng với dữ liệu đang có; đo hiệu năng khi xóa nhiều aggregate; và dùng soft delete nếu hệ thống cần giữ lịch sử. Đặc biệt, đừng coi `deleteAll()` là `TRUNCATE` hay coi `deleteAllById()` là cam kết một bulk SQL statement.
