# Kiểm thử đọc–ghi đối xứng, null và tương thích dữ liệu cũ

Khi dùng Spring Data JDBC, một domain object thường đi qua hai chiều chuyển đổi:

- **Ghi:** Java object được ánh xạ thành giá trị JDBC và lưu vào các cột quan hệ.
- **Đọc:** các giá trị SQL được chuyển đổi và materialize trở lại thành domain object.

Một mapping chỉ đáng tin cậy khi dữ liệu sau khi đọc lại vẫn giữ đúng ý nghĩa nghiệp vụ. Tuy nhiên, đọc–ghi đối xứng không nhất thiết có nghĩa mọi giá trị Java phải bằng tuyệt đối từng byte sau một vòng lưu. Database có thể chuẩn hóa scale của số thập phân, độ chính xác timestamp, giá trị mặc định hoặc cách biểu diễn enum. Điều cần bảo đảm là **ý nghĩa dữ liệu được giữ nguyên theo quy tắc đã xác định**.

Bài học này trình bày cách kiểm thử round-trip mapping, xử lý SQL NULL, kiểm thử converter hai chiều và bảo đảm code mới vẫn đọc được dữ liệu cũ. Các ví dụ tập trung vào Spring Data Relational/JDBC.

## 1. Đọc–ghi đối xứng là gì?

Giả sử domain object có một giá trị tiền:

```java
Customer customer = new Customer(
    null,
    "Nguyen An",
    new BigDecimal("125.50"),
    true
);
```

Khi lưu, Spring Data JDBC chuyển giá trị Java thành dữ liệu SQL. Khi đọc lại, framework chuyển dữ liệu SQL về kiểu Java.

Có thể mô tả bằng hai phép chuyển đổi:

```text
Java object
    |
    | write mapping
    v
Database row
    |
    | read mapping
    v
Java object được khôi phục
```

Một round-trip mong muốn thỏa mãn:

```text
read(write(value)) ≈ normalize(value)
```

Ký hiệu `≈` có nghĩa là tương đương theo quy tắc domain, còn `normalize` biểu diễn những thay đổi có chủ đích do database hoặc format lưu trữ tạo ra.

Ví dụ:

- Database lưu DECIMAL với scale cố định, nên `125.5` có thể được đọc thành `125.50`.
- Timestamp có độ chính xác microsecond, nên phần nanosecond có thể bị làm tròn hoặc cắt.
- Enum Java `ACTIVE` được lưu thành mã cũ `A` hoặc chuỗi chuẩn `ACTIVE`.
- ID, version và thời điểm tạo có thể được database/framework sinh sau khi insert.

Vì vậy, test không nên luôn dùng `equals` trên toàn bộ object đầu vào và object đọc lại. Hãy xác định property nào cần giữ nguyên, property nào được chuẩn hóa và property nào do database tạo.

## 2. Phân biệt test converter và test repository

Có hai lớp kiểm thử bổ sung cho nhau.

| Lớp kiểm thử | Mục tiêu | Phát hiện được |
| --- | --- | --- |
| Unit test converter | Kiểm tra chuyển đổi Java ↔ SQL value. | Sai quy tắc parse/format, mapping enum, timezone hoặc format cũ. |
| Repository integration test | Kiểm tra toàn bộ đường đi qua Spring Data JDBC và database. | Sai column mapping, JDBC type, NULL, DDL, default, trigger, precision và converter registration. |

Unit test converter nhanh và cô lập, nhưng không xác nhận converter đã được đăng ký vào Spring Data JDBC. Repository integration test đi qua JDBC driver và schema thực tế nên phát hiện lỗi ở ranh giới database.

Không nên chỉ test converter rồi kết luận persistence round-trip đã đúng.

## 3. Xây dựng domain model và schema cho ví dụ

Giả sử bảng khách hàng lưu tên hiển thị, hạn mức tín dụng, điểm tích lũy và trạng thái:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(160) NOT NULL,
    middle_name VARCHAR(120),
    credit_limit DECIMAL(12, 2),
    loyalty_points INTEGER,
    status VARCHAR(24) NOT NULL,
    active BOOLEAN NOT NULL
);
```

Các cột `middle_name`, `credit_limit` và `loyalty_points` cho phép NULL. Domain model dùng wrapper/reference types để biểu diễn trạng thái đó:

```java
import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
    @Id Long id,
    @Column("display_name") String displayName,
    @Column("middle_name") String middleName,
    @Column("credit_limit") BigDecimal creditLimit,
    @Column("loyalty_points") Integer loyaltyPoints,
    CustomerStatus status,
    boolean active
) {}
```

`boolean active` là primitive vì schema khai báo `NOT NULL`. Nếu cột có thể chứa SQL NULL, hãy dùng `Boolean` để biểu diễn ba trạng thái: true, false và null.

Repository:

```java
import org.springframework.data.repository.ListCrudRepository;

public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {
}
```

`@Column` giúp ánh xạ property Java sang tên cột vật lý. Trong các bài test, hãy dùng schema tương ứng với mapping thay vì chỉ kiểm tra object được tạo trong bộ nhớ.

## 4. Viết repository round-trip test

Một round-trip test cơ bản lưu entity rồi đọc lại bằng ID:

```java
@DataJdbcTest
class CustomerRepositoryRoundTripTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void preservesValuesAfterSaveAndReload() {
        Customer input = new Customer(
            null,
            "Nguyen An",
            "Van",
            new BigDecimal("125.50"),
            120,
            CustomerStatus.ACTIVE,
            true
        );

        Customer saved = customers.save(input);

        Customer loaded = customers.findById(saved.id())
            .orElseThrow();

        assertThat(loaded.displayName()).isEqualTo("Nguyen An");
        assertThat(loaded.middleName()).isEqualTo("Van");
        assertThat(loaded.creditLimit())
            .isEqualByComparingTo(new BigDecimal("125.50"));
        assertThat(loaded.loyaltyPoints()).isEqualTo(120);
        assertThat(loaded.status()).isEqualTo(CustomerStatus.ACTIVE);
        assertThat(loaded.active()).isTrue();
    }
}
```

Điểm cần chú ý:

1. Dùng ID từ object trả về bởi `save`. Với ID được database sinh, không giả định object đầu vào luôn được sửa tại chỗ.
2. Gọi `findById` để kiểm tra dữ liệu thực sự đi qua database và mapping đọc.
3. So sánh từng property theo semantics của nó.
4. Với `BigDecimal`, `isEqualByComparingTo` so sánh giá trị số và không bắt buộc scale phải giống nhau như `equals`.
5. Test cần chạy với schema và JDBC driver phù hợp.

Nếu entity dùng `@Version`, version có thể thay đổi khi lưu. Nếu có generated ID, timestamp hoặc audit property, hãy kiểm tra chúng theo quy tắc riêng thay vì so sánh toàn object với input ban đầu.

## 5. Kiểm thử SQL NULL

NULL là một phần của dữ liệu, không phải một giá trị Java đặc biệt có thể bỏ qua khi test. Nếu cột nullable, cần xác nhận cả hai chiều:

- Java null được ghi thành SQL NULL.
- SQL NULL được đọc lại thành Java null.

Ví dụ:

```java
@Test
void preservesNullableProperties() {
    Customer input = new Customer(
        null,
        "Tran Binh",
        null,
        null,
        null,
        CustomerStatus.ACTIVE,
        true
    );

    Customer saved = customers.save(input);

    Customer loaded = customers.findById(saved.id())
        .orElseThrow();

    assertThat(loaded.middleName()).isNull();
    assertThat(loaded.creditLimit()).isNull();
    assertThat(loaded.loyaltyPoints()).isNull();
}
```

Test này xác nhận mapping NULL cho ba property nullable. Nó cũng giúp phát hiện trường hợp code vô tình thay NULL bằng giá trị mặc định trong Java.

### 5.1. Dùng wrapper cho cột nullable

Không nên ánh xạ cột nullable vào primitive:

```java
private int loyaltyPoints;
private boolean marketingOptIn;
```

Primitive Java luôn có giá trị mặc định (`0` hoặc `false`) và không thể biểu diễn SQL NULL. Nếu database có thể chứa NULL, dùng:

```java
private Integer loyaltyPoints;
private Boolean marketingOptIn;
```

Nếu nghiệp vụ muốn NULL có nghĩa là 0 hoặc false, hãy chuyển đổi rõ ở domain/service hoặc migration. Đừng để kiểu primitive âm thầm xóa đi sự khác biệt giữa “không biết/chưa cung cấp” và “giá trị bằng 0/false”.

### 5.2. NULL khác giá trị mặc định của database

Ví dụ:

```sql
CREATE TABLE customers (
    loyalty_points INTEGER DEFAULT 0
);
```

Database áp dụng DEFAULT khi INSERT bỏ cột đó khỏi câu lệnh hoặc yêu cầu DEFAULT tường minh. Nếu INSERT truyền `NULL` cho cột, default không tự động thay NULL bằng 0; kết quả phụ thuộc constraint và câu lệnh.

Do đó, ba trạng thái sau khác nhau:

| Tình huống | Ý nghĩa |
| --- | --- |
| Cột bị bỏ khỏi INSERT và có DEFAULT | Database có thể tự áp dụng giá trị mặc định. |
| Cột được INSERT với NULL | Database nhận NULL, nếu schema cho phép. |
| Java property có giá trị 0 | Giá trị 0 được ứng dụng cung cấp và có thể được ghi xuống database. |

Nếu database phải sở hữu giá trị mặc định và ứng dụng cần đọc nó, hãy thiết kế mapping phù hợp, ví dụ `@ReadOnlyProperty`, rồi đọc lại aggregate khi cần giá trị do database sinh.

### 5.3. NULL, chuỗi rỗng và khoảng trắng

Các giá trị sau không tương đương:

- `null`: không có giá trị.
- `""`: chuỗi rỗng.
- `"   "`: chuỗi chứa dấu cách.

Test nên bao phủ các trường hợp này nếu domain có quy tắc chuẩn hóa tên hoặc nội dung. Nếu muốn coi chuỗi rỗng là NULL, hãy thực hiện normalization có chủ đích và kiểm thử cả lúc ghi lẫn lúc đọc.

## 6. Kiểm thử precision và kiểu dữ liệu

Không phải mọi kiểu Java đều có round-trip byte-for-byte qua database. JDBC driver và kiểu cột có thể chuẩn hóa giá trị.

### 6.1. BigDecimal và scale

`BigDecimal` phân biệt giá trị và scale:

```java
new BigDecimal("10.5").equals(new BigDecimal("10.50")); // false
new BigDecimal("10.5").compareTo(new BigDecimal("10.50")); // 0
```

Nếu cột là `DECIMAL(12, 2)`, test nên kiểm tra giá trị theo scale/precision mà schema cam kết:

```java
assertThat(loaded.creditLimit())
    .isEqualByComparingTo("10.50");
```

Nếu scale là một phần của quy tắc domain, hãy chuẩn hóa trước khi lưu hoặc dùng custom conversion phù hợp. Đừng dựa vào một database cụ thể để tự hiểu quy tắc scale mà không có test.

### 6.2. Timestamp và độ chính xác

Một số database lưu timestamp tới microsecond, một số cấu hình hoặc kiểu cột khác có thể có độ chính xác khác. Giá trị Java `Instant` có độ chính xác nanosecond; sau round-trip có thể không giữ đủ 9 chữ số phần lẻ.

Ví dụ test có thể chuẩn hóa theo precision của schema:

```java
Instant input = Instant.parse("2026-11-13T09:15:30.123456Z");

Customer saved = customers.save(customerWithTimestamp(input));
Customer loaded = customers.findById(saved.id()).orElseThrow();

assertThat(loaded.createdAt())
    .isEqualTo(input);
```

Ví dụ trên chỉ đúng nếu kiểu cột/driver giữ được độ chính xác của giá trị đó. Nếu database chỉ giữ microsecond, hãy so sánh với giá trị đã truncate/round theo precision mà hệ thống cam kết.

Không dùng giờ hệ thống mặc định hoặc timezone của máy chạy test để tạo giá trị mong đợi. Dùng thời điểm cố định và timezone tường minh để test ổn định giữa local và CI.

### 6.3. UUID, Boolean và enum

Các kiểu như UUID, Boolean và enum cũng cần kiểm tra trên database thực tế:

- UUID có thể được lưu bằng kiểu UUID native hoặc dạng ký tự tùy database.
- Boolean có thể được biểu diễn bằng BOOLEAN, BIT hoặc kiểu tương đương.
- Enum có thể được lưu thành tên enum, mã legacy hoặc một chuỗi canonical.
- Custom converter có thể thay đổi cách biểu diễn khi đọc/ghi.

Một test trên H2 không đủ để bảo đảm cùng mapping chạy giống hệt PostgreSQL, MySQL hoặc SQL Server.

## 7. Kiểm thử custom converter theo hai chiều

Khi domain type có cách biểu diễn khác với SQL, Spring Data JDBC có thể dùng custom converter. Ví dụ database cũ lưu trạng thái khách hàng bằng mã:

| Giá trị cũ | Ý nghĩa domain |
| --- | --- |
| `A` | ACTIVE |
| `I` | INACTIVE |

Code mới muốn ghi dạng canonical `ACTIVE` và `INACTIVE`, nhưng vẫn phải đọc được dữ liệu cũ.

Enum:

```java
public enum CustomerStatus {
    ACTIVE,
    INACTIVE,
    UNKNOWN
}
```

Converter đọc:

```java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToCustomerStatus
        implements Converter<String, CustomerStatus> {

    @Override
    public CustomerStatus convert(String source) {
        return switch (source) {
            case "A", "ACTIVE" -> CustomerStatus.ACTIVE;
            case "I", "INACTIVE" -> CustomerStatus.INACTIVE;
            case "UNKNOWN" -> CustomerStatus.UNKNOWN;
            default -> throw new IllegalArgumentException(
                "Customer status không được hỗ trợ: " + source
            );
        };
    }
}
```

Converter ghi:

```java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class CustomerStatusToString
        implements Converter<CustomerStatus, String> {

    @Override
    public String convert(CustomerStatus source) {
        return switch (source) {
            case ACTIVE -> "ACTIVE";
            case INACTIVE -> "INACTIVE";
            case UNKNOWN -> "UNKNOWN";
        };
    }
}
```

Đọc được cả mã cũ và giá trị canonical; ghi ra một định dạng chuẩn duy nhất. Đây là một chiến lược **tolerant reader, canonical writer** thường hữu ích trong quá trình chuyển đổi dữ liệu.

Không nên tự động biến mọi giá trị không nhận diện thành `UNKNOWN` nếu việc đó có thể che giấu dữ liệu hỏng. Chỉ dùng fallback khi domain đã xác định rõ ý nghĩa của trạng thái không biết; nếu không, ném lỗi có thông tin để dữ liệu bất thường được phát hiện.

### 7.1. Đăng ký converter trong Spring Data JDBC

Các converter cần được đăng ký với cấu hình relational/JDBC. Ví dụ dùng `AbstractJdbcConfiguration`:

```java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class JdbcConversionConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
            new StringToCustomerStatus(),
            new CustomerStatusToString()
        );
    }
}
```

Cách cấu hình cụ thể cần phù hợp với phiên bản Spring Data JDBC và cấu hình Spring Boot của dự án. Nếu dự án đã khai báo `JdbcCustomConversions` hoặc một `AbstractJdbcConfiguration` riêng, hãy bổ sung converter vào cấu hình hiện có thay vì đăng ký nhiều bộ conversion cạnh tranh.

### 7.2. Unit test converter

```java
class CustomerStatusConverterTest {

    private final StringToCustomerStatus reader =
        new StringToCustomerStatus();

    private final CustomerStatusToString writer =
        new CustomerStatusToString();

    @Test
    void readsLegacyAndCanonicalValues() {
        assertThat(reader.convert("A"))
            .isEqualTo(CustomerStatus.ACTIVE);
        assertThat(reader.convert("ACTIVE"))
            .isEqualTo(CustomerStatus.ACTIVE);
        assertThat(reader.convert("I"))
            .isEqualTo(CustomerStatus.INACTIVE);
    }

    @Test
    void writesCanonicalValues() {
        assertThat(writer.convert(CustomerStatus.ACTIVE))
            .isEqualTo("ACTIVE");
        assertThat(writer.convert(CustomerStatus.INACTIVE))
            .isEqualTo("INACTIVE");
    }
}
```

Test này kiểm tra logic converter. Nó không chứng minh converter đã được Spring Data JDBC nhận diện; phần đó cần repository integration test.

## 8. Kiểm thử dữ liệu cũ bằng fixture database

Một round-trip test chỉ tạo dữ liệu bằng code mới thường không phát hiện vấn đề tương thích ngược. Để kiểm tra dữ liệu cũ, hãy chèn fixture có định dạng legacy trực tiếp vào database, rồi đọc bằng code mới.

Ví dụ repository test:

```java
@DataJdbcTest
class CustomerLegacyDataTest {

    @Autowired
    CustomerRepository customers;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void readsLegacyStatusAndWritesCanonicalStatus() {
        jdbc.update("""
            INSERT INTO customers
                (id, display_name, status, active)
            VALUES (?, ?, ?, ?)
            """,
            9001L,
            "Le Minh",
            "A",
            true
        );

        Customer loaded = customers.findById(9001L)
            .orElseThrow();

        assertThat(loaded.status())
            .isEqualTo(CustomerStatus.ACTIVE);

        customers.save(loaded);

        String storedStatus = jdbc.queryForObject(
            "SELECT status FROM customers WHERE id = ?",
            String.class,
            9001L
        );

        assertThat(storedStatus).isEqualTo("ACTIVE");
    }
}
```

Test này xác nhận hai điều:

1. Code mới đọc được mã legacy `A` thành domain value `ACTIVE`.
2. Khi ghi lại, converter phát ra giá trị canonical `ACTIVE`.

Fixture cần cung cấp đầy đủ các cột NOT NULL và dùng ID phù hợp với schema test. Nếu bảng dùng identity/sequence, cần kiểm soát cách chèn ID thủ công và trạng thái sequence theo database.

### 8.1. Dữ liệu cũ có giá trị NULL

Nếu schema cũ cho phép một cột NULL hoặc dữ liệu lịch sử có NULL, hãy tạo fixture riêng:

```sql
INSERT INTO customers (
    id, display_name, middle_name, credit_limit,
    loyalty_points, status, active
)
VALUES (
    9002, 'Pham Hoa', NULL, NULL,
    NULL, 'A', TRUE
);
```

Sau đó xác nhận code mới đọc được các property nullable là null hoặc áp dụng normalization đã được domain quy định.

Không giả định dữ liệu cũ luôn tuân theo constraint của schema mới. Nếu schema mới siết NOT NULL, phải backfill dữ liệu trước khi thêm constraint.

## 9. Tương thích dữ liệu cũ không chỉ là converter

Converter giải quyết sự khác nhau về **giá trị và cách biểu diễn**. Nó không thể tự khắc phục mọi thay đổi schema.

Cần phân biệt ba trường hợp:

| Thay đổi | Converter có giải quyết được không? | Cách xử lý |
| --- | --- | --- |
| Cột status dùng mã `A` thay vì `ACTIVE` | Có, nếu converter được đăng ký và hiểu cả hai format. | Reader chấp nhận mã cũ, writer ghi canonical. |
| Cột nullable chứa NULL nhưng code mới muốn biểu diễn rõ | Có thể, thông qua mapping/type phù hợp và quy tắc domain. | Dùng wrapper/reference type, test NULL và normalization nếu cần. |
| Bảng cũ chưa có cột `loyalty_points` | Không. | Migration/schema compatibility trước khi query cột đó. |
| Tên cột đổi từ `display_name` sang `name` | Không chỉ bằng converter value. | Migration, mapping compatibility hoặc view phù hợp. |
| Kiểu cột đổi từ VARCHAR sang JSON | Có thể cần converter, nhưng còn phụ thuộc SQL type và driver. | Migration, conversion và integration test trên database thật. |

Nếu cột chưa tồn tại, SQL được sinh ra vẫn có thể tham chiếu tới tên cột đó và database trả lỗi. Converter không có cơ hội chạy để xử lý một column bị thiếu.

## 10. Chiến lược migration tương thích ngược

Khi triển khai code mới trên database đang có dữ liệu cũ, nên tách thay đổi thành các bước có thể triển khai an toàn.

Ví dụ đổi cột trạng thái từ mã ngắn sang chuỗi rõ nghĩa:

1. **Expand:** cho phép cả giá trị cũ và mới trong giai đoạn chuyển tiếp; bổ sung code reader hiểu cả hai.
2. **Deploy reader tương thích:** triển khai ứng dụng mới có thể đọc cả `A`/`I` và `ACTIVE`/`INACTIVE`.
3. **Chuyển writer:** ứng dụng mới bắt đầu ghi format canonical.
4. **Backfill:** chuyển các row cũ sang format canonical bằng migration.
5. **Verify:** kiểm tra không còn giá trị legacy và các ứng dụng đang chạy đều hiểu format mới.
6. **Contract:** loại bỏ nhánh đọc format cũ hoặc constraint/column compatibility chỉ khi không còn writer/reader cũ.

Đây là dạng **expand-and-contract migration**. Nó đặc biệt quan trọng khi nhiều instance ứng dụng được deploy rolling và trong một khoảng thời gian code cũ lẫn code mới cùng truy cập database.

Không triển khai code mới ghi format mà phiên bản ứng dụng cũ không thể đọc trước khi tất cả instance cũ đã được nâng cấp hoặc có lớp tương thích phù hợp.

### 10.1. Thêm cột mới

Giả sử cần thêm `loyalty_points`:

```sql
ALTER TABLE customers
ADD COLUMN loyalty_points INTEGER;
```

Trong giai đoạn đầu, cột nên nullable nếu dữ liệu cũ chưa có giá trị. Code mới cần hiểu NULL có nghĩa gì. Sau đó backfill:

```sql
UPDATE customers
SET loyalty_points = 0
WHERE loyalty_points IS NULL;
```

Chỉ khi dữ liệu đã được backfill và ứng dụng xử lý đúng, mới cân nhắc:

```sql
ALTER TABLE customers
ALTER COLUMN loyalty_points SET NOT NULL;
```

Cú pháp DDL khác nhau theo database. Migration cần dùng đúng dialect và được kiểm thử trên cùng loại database với production.

### 10.2. Thay đổi tên cột

Đổi tên cột trực tiếp có thể làm phiên bản ứng dụng cũ không còn truy cập được. Một quy trình an toàn hơn có thể là:

- Thêm cột mới.
- Đồng bộ dữ liệu giữa cột cũ và mới trong giai đoạn chuyển tiếp.
- Deploy code đọc được dữ liệu theo schema mới nhưng vẫn tương thích giai đoạn cũ nếu cần.
- Chuyển writer sang cột mới.
- Backfill và xác minh.
- Xóa cột cũ trong migration sau khi không còn phiên bản ứng dụng nào phụ thuộc.

Nếu dùng database view hoặc trigger để duy trì compatibility, cần kiểm thử cả read và write path vì view/trigger có thể có semantics riêng.

## 11. Đối xứng không có nghĩa writer và reader phải dùng cùng format

Trong quá trình migration, có thể chủ động dùng:

- Reader hiểu nhiều format cũ/mới.
- Writer chỉ phát ra một format canonical.

Ví dụ:

```text
Legacy rows:
"A"         -> CustomerStatus.ACTIVE
"ACTIVE"    -> CustomerStatus.ACTIVE
"I"         -> CustomerStatus.INACTIVE
"INACTIVE"  -> CustomerStatus.INACTIVE

New writes:
CustomerStatus.ACTIVE   -> "ACTIVE"
CustomerStatus.INACTIVE -> "INACTIVE"
```

Đây vẫn là một mapping có chủ đích. Mục tiêu là giữ ý nghĩa domain, không nhất thiết giữ nguyên biểu diễn lịch sử.

Cần xác định thời điểm loại bỏ format cũ. Nếu writer cũ vẫn đang hoạt động, nó có thể tiếp tục ghi mã `A` sau khi backfill đã chạy. Vì vậy migration dữ liệu phải phối hợp với trạng thái triển khai của tất cả writer.

## 12. Kiểm thử schema migration và tương thích nhiều phiên bản

Ngoài test repository, dự án nên có kiểm thử migration:

- Tạo database ở schema version cũ.
- Chèn fixture theo format dữ liệu cũ.
- Chạy migration theo đúng thứ tự.
- Khởi động mapping/repository của code mới.
- Đọc các row cũ.
- Ghi một row mới.
- Xác nhận dữ liệu mới có format canonical.
- Xác nhận constraint mới không làm mất dữ liệu hợp lệ.
- Kiểm tra lại các trường hợp NULL và default.

Nếu ứng dụng triển khai rolling, cần xác định compatibility matrix:

| Reader | Writer | Kết quả cần bảo đảm |
| --- | --- | --- |
| Code cũ | Code cũ | Hành vi hiện tại trước migration. |
| Code mới | Code cũ | Reader mới vẫn đọc format cũ. |
| Code mới | Code mới | Reader/writer dùng format canonical. |
| Code cũ | Code mới | Chỉ an toàn nếu writer mới vẫn phát format mà code cũ hiểu. |

Trường hợp cuối là lý do cần trì hoãn việc đổi format ghi cho tới khi reader cũ đã được loại bỏ hoặc có compatibility layer.

## 13. Kiểm thử với đúng database và JDBC driver

H2 tiện cho test nhanh nhưng không đại diện hoàn toàn cho PostgreSQL, MySQL, SQL Server hoặc Oracle. Khác biệt có thể xuất hiện ở:

- Kiểu UUID và cách lưu.
- Timestamp precision/timezone.
- DECIMAL precision/scale.
- Boolean representation.
- Cách cast parameter NULL.
- Enum/custom type.
- Default, generated column và trigger.
- Cú pháp migration và constraint.
- Collation/case sensitivity.

Với các đặc tính phụ thuộc database, dùng Testcontainers hoặc database test cùng engine/major version phù hợp với production.

Ví dụ cấu hình Testcontainers PostgreSQL cho test:

```java
@Testcontainers
@DataJdbcTest
@AutoConfigureTestDatabase(
    replace = AutoConfigureTestDatabase.Replace.NONE
)
class CustomerPostgresRoundTripTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void configureDatasource(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
```

Ví dụ minh họa cấu hình container; dự án cần dependency Testcontainers PostgreSQL, cấu hình migration/schema và phiên bản image phù hợp với môi trường triển khai.

## 14. Ma trận kiểm thử nên có

Với một aggregate có converter, nullable field và dữ liệu lịch sử, nên bao phủ các tình huống chính:

| Trường hợp | Dữ liệu ghi/fixture | Điều cần xác nhận |
| --- | --- | --- |
| Round-trip thông thường | Tất cả property có giá trị hợp lệ | Ý nghĩa từng property được giữ nguyên. |
| Nullable fields | Một hoặc nhiều property null | SQL NULL được ghi và đọc đúng. |
| Empty string | `""` | Không bị nhầm thành NULL ngoài ý muốn. |
| Default database | Bỏ cột khỏi insert hoặc để DB tạo | Giá trị mặc định được đọc lại theo mapping. |
| Decimal precision | Giá trị có scale khác schema | Giá trị sau round-trip tuân theo precision/scale. |
| Timestamp precision | Instant có nanosecond | So sánh theo precision database cam kết. |
| Legacy enum | Mã cũ `A`/`I` | Reader mới ánh xạ đúng domain value. |
| Canonical enum | Chuỗi mới `ACTIVE` | Reader đọc được format mới. |
| Unknown enum | Giá trị không hỗ trợ | Lỗi hoặc fallback theo policy đã xác định. |
| Legacy NULL | Row cũ có cột nullable NULL | Code mới xử lý đúng nullability. |
| Schema migration | Database ở version cũ | Migration hoàn tất và code mới truy cập được. |
| Rolling deployment | Writer/reader cũ và mới | Format dữ liệu tương thích trong giai đoạn chuyển tiếp. |

Không cần gom tất cả vào một test khổng lồ. Tách unit test converter, repository integration test và migration test để lỗi được định vị rõ.

## 15. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân | Hướng xử lý |
| --- | --- | --- |
| Object sau đọc lại khác input | Database chuẩn hóa scale, precision hoặc giá trị mặc định. | So sánh theo quy tắc domain và chuẩn hóa expected value. |
| SQL NULL trở thành 0/false | Dùng primitive cho cột nullable hoặc normalization không rõ ràng. | Dùng wrapper và quy định semantics NULL. |
| NULL bị ghi thành giá trị mặc định | Code gán default trước khi save hoặc cột không được phép NULL. | Phân biệt null, default và giá trị do ứng dụng cung cấp. |
| Converter unit test pass nhưng repository fail | Converter chưa được đăng ký hoặc mapping SQL type không đúng. | Thêm integration test qua Spring Data JDBC. |
| Dữ liệu legacy không đọc được | Reader chỉ hiểu format mới. | Cho reader chấp nhận cả format cũ trong giai đoạn migration. |
| Giá trị lạ bị biến thành UNKNOWN và che giấu lỗi | Fallback không có policy domain rõ. | Chọn fail-fast hoặc fallback có chủ đích và log/quan sát phù hợp. |
| Code mới không chạy trên schema cũ | Cột/constraint mới chưa được migration. | Triển khai expand migration trước code phụ thuộc schema mới. |
| H2 test pass nhưng production fail | Khác biệt dialect/driver/precision/NULL behavior. | Test trên database cùng engine với production. |
| Test timestamp chập chờn | Dựa vào clock/timezone hoặc precision không ổn định. | Dùng thời điểm cố định và normalize theo schema. |
| Writer cũ tiếp tục ghi format cũ sau backfill | Rolling deployment còn instance cũ. | Duy trì reader tương thích cho tới khi mọi writer cũ đã dừng. |

## 16. Quy trình xây dựng kiểm thử đọc–ghi và tương thích dữ liệu

Khi thêm property, converter hoặc thay đổi schema:

1. Xác định kiểu Java, kiểu SQL, nullability và precision của từng property.
2. Xác định quy tắc round-trip: giữ nguyên, chuẩn hóa hay được database sinh.
3. Viết unit test cho từng converter đọc và ghi.
4. Viết repository integration test lưu rồi đọc lại aggregate.
5. Kiểm thử riêng SQL NULL, empty string và giá trị mặc định.
6. Kiểm thử precision của DECIMAL, DATE/TIMESTAMP và kiểu đặc thù database.
7. Tạo fixture bằng định dạng cũ để xác nhận code mới vẫn đọc được.
8. Xác nhận writer mới phát ra format canonical.
9. Kiểm thử migration từ schema version cũ sang mới.
10. Thiết kế expand-and-contract cho rolling deployment nếu nhiều phiên bản ứng dụng cùng chạy.
11. Chạy integration test trên đúng database/driver cho production-sensitive behavior.
12. Chỉ loại bỏ converter/compatibility path cũ khi không còn dữ liệu hoặc writer nào cần nó.

> **Một round-trip tốt bảo toàn ý nghĩa domain, kể cả khi database chuẩn hóa cách biểu diễn.** Hãy kiểm thử riêng converter, repository mapping, SQL NULL, precision và fixture legacy; converter có thể giúp đọc nhiều format giá trị, nhưng không thay thế migration khi schema thiếu cột hoặc constraint đã thay đổi.
