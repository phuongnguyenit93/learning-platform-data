# Setting Up PostgreSQL or MySQL and Sample Data

To practice **Spring Data Relational JDBC** (Spring Data JDBC), you first need a stably running relational database, an account with access privileges, a schema with tables and foreign keys, and data you can inspect with SQL. This lesson walks through setting up an environment with **PostgreSQL or MySQL** and connecting it to a Spring Boot application.

You only need to **choose one database system** for learning. Both guides share the same sample data structure so that subsequent Spring Data JDBC lessons can focus on entities, aggregates, and repositories without changing the dataset each time.

## 1. Expected Outcome and Components

Once completed, you will have:

- A running PostgreSQL or MySQL instance on your development machine.
- A `jdbc_lab` database and a `jdbc_user` account for application connectivity.
- Two tables, `authors` and `books`, complete with primary keys, a foreign key, and sample rows.
- SQL queries verifying row counts, joins, and loaded data.
- `spring.datasource.*` configuration so Spring Data JDBC connects to the right database.

~~~mermaid
flowchart LR
    App["Spring Boot<br/>Spring Data JDBC"] -->|"JDBC URL + user/password"| Driver["JDBC Driver"]
    Driver -->|"SQL over TCP"| DB[("PostgreSQL<br/>or MySQL")]
    DB --> Author["authors"]
    DB --> Book["books"]
    Book -->|"author_id (FK)"| Author
    Script["schema + seed SQL"] --> DB
~~~

**Minimum requirements:** Docker Engine or Docker Desktop running, Docker Compose v2 (`docker compose` command), a terminal, and a Java/JDK version compatible with your Spring Boot project. If you already have PostgreSQL/MySQL installed locally, you can skip the Docker setup and use the SQL files below directly.

The names, accounts, and `localdev` passwords in this lesson are **dummy data for local machine learning**. For shared or production environments, manage passwords via secret configuration, restrict privileges, and never expose database ports to the public Internet.

## 2. Choose PostgreSQL or MySQL?

| Item | PostgreSQL | MySQL |
|---|---|---|
| JDBC driver | `org.postgresql:postgresql` | `com.mysql:mysql-connector-j` |
| Local JDBC URL | `jdbc:postgresql://localhost:5432/jdbc_lab` | `jdbc:mysql://localhost:3306/jdbc_lab` |
| Default port | `5432` | `3306` |
| Auto-increment primary key column in example | `GENERATED BY DEFAULT AS IDENTITY` | `AUTO_INCREMENT` |
| Application read/write via | JDBC / Spring Data JDBC | JDBC / Spring Data JDBC |

Spring Data JDBC works with **both** via their respective drivers and dialects. Some SQL DDL statements differ between the two systems, so this lesson provides **two separate schema files** and **one shared data file**.

## 3. Practice Directory Structure

Create a practice directory; the paths below show the **recommended structure**, not pre-existing project files:

~~~text
jdbc-lab/
├── compose.yaml
└── db/
    ├── schema-postgresql.sql
    ├── schema-mysql.sql
    └── data.sql
~~~

Run Docker Compose commands from the `jdbc-lab` directory where `compose.yaml` lives. Both services mount the `db` directory as read-only (`/scripts`) so scripts can be executed inside the container.

## 4. Starting PostgreSQL or MySQL with Docker Compose

Create `compose.yaml`:

~~~yaml
services:
  postgres:
    profiles: ["postgres"]
    image: postgres:16
    environment:
      POSTGRES_DB: jdbc_lab
      POSTGRES_USER: jdbc_user
      POSTGRES_PASSWORD: localdev
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - pg_data:/var/lib/postgresql/data
      - ./db:/scripts:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
      interval: 5s
      timeout: 3s
      retries: 20

  mysql:
    profiles: ["mysql"]
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: jdbc_lab
      MYSQL_USER: jdbc_user
      MYSQL_PASSWORD: localdev
      MYSQL_ROOT_PASSWORD: localroot
    ports:
      - "127.0.0.1:3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
      - ./db:/scripts:ro
    healthcheck:
      test: ["CMD-SHELL", "mysql -h 127.0.0.1 -u$$MYSQL_USER -p$$MYSQL_PASSWORD $$MYSQL_DATABASE -e 'SELECT 1' >/dev/null 2>&1"]
      interval: 5s
      timeout: 3s
      retries: 30

volumes:
  pg_data:
  mysql_data:
~~~

Meaning of the settings:

- `profiles` ensures only the database engine you select is started.
- `POSTGRES_DB` or `MYSQL_DATABASE` instructs the image to create the `jdbc_lab` database; the corresponding `USER` and `PASSWORD` variables initialize the practice account when the volume is first created.
- `127.0.0.1:5432:5432` and `127.0.0.1:3306:3306` bind ports only on the host loopback interface so applications running outside Docker can connect.
- `pg_data` and `mysql_data` preserve data when containers are stopped/removed and recreated. **Changing environment variables does not automatically change the user/password of a database already initialized inside an old volume.**
- `healthcheck` verifies when the service is ready to accept connections; `$$` tells Docker Compose to pass a literal `$` so the container's shell expands the environment variables.

### Option A: PostgreSQL

~~~powershell
docker compose --profile postgres up -d --wait
docker compose --profile postgres ps
docker compose exec postgres pg_isready -U jdbc_user -d jdbc_lab
~~~

Expected `pg_isready` output is `accepting connections`. If an older Compose version does not support `--wait`, run `docker compose --profile postgres up -d`, watch `docker compose ps`, and verify `pg_isready` once database initialization finishes.

### Option B: MySQL

~~~powershell
docker compose --profile mysql up -d --wait
docker compose --profile mysql ps
docker compose exec mysql mysql -ujdbc_user -plocaldev -D jdbc_lab -e "SELECT 1;"
~~~

A query returning a cell with value `1` means the connection works. The MySQL CLI may warn when a password is passed directly on the command line; this syntax is only for local demonstration environments, never for environments holding real data.

**Run only one option** per practice session. If port `5432` or `3306` is already occupied by another program, change the **left-hand port** in the port mapping (for example, `127.0.0.1:15432:5432`), then update the port in your JDBC URL to `15432`. The **right-hand port** remains the port inside the container.

## 5. Sample Data Design: Authors and Books

The schema consists of two tables:

~~~mermaid
erDiagram
    AUTHORS ||--o{ BOOKS : "author_id"
    AUTHORS {
        BIGINT id PK
        VARCHAR code UK
        VARCHAR full_name
    }
    BOOKS {
        BIGINT id PK
        BIGINT author_id FK
        VARCHAR book_code UK
        VARCHAR title
        DATE published_on
        BIGINT price_vnd
        INTEGER stock_quantity
    }
~~~

- `authors.id` and `books.id` are **primary keys** (PK), generated automatically by the database on insert.
- `books.author_id` is a **foreign key** (FK) referencing `authors.id`.
- `authors.code` and `books.book_code` are unique business codes, letting us look up sample rows without assuming auto-increment IDs are always `1`, `2`, `3`.
- `price_vnd` stores integer VND amounts, avoiding floating-point types for prices; `stock_quantity` is a non-negative inventory count.
- The sample data includes three books from two authors, including one out-of-stock book for testing filter queries.

These two tables support practicing SQL and Spring Data JDBC. **An FK relationship in a schema does not automatically define aggregate boundaries** in the domain model; when building entities/repositories, decide ownership based on business rules.

## 6. Creating the PostgreSQL Schema

Write `db/schema-postgresql.sql`:

~~~sql
-- FOR PRACTICE DATABASE ONLY:
-- Drop old tables so each schema run starts with the same initial state.
DROP TABLE IF EXISTS books;
DROP TABLE IF EXISTS authors;

CREATE TABLE authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code VARCHAR(20) NOT NULL UNIQUE,
    full_name VARCHAR(120) NOT NULL
);

CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    author_id BIGINT NOT NULL REFERENCES authors(id),
    book_code VARCHAR(30) NOT NULL UNIQUE,
    title VARCHAR(200) NOT NULL,
    published_on DATE,
    price_vnd BIGINT NOT NULL CHECK (price_vnd >= 0),
    stock_quantity INTEGER NOT NULL DEFAULT 0
        CHECK (stock_quantity >= 0)
);

CREATE INDEX idx_books_author_id ON books(author_id);
~~~

**Note on `DROP TABLE`:** the file intentionally removes existing data so you can practice from scratch. Run this only in the experimental `jdbc_lab` database. Never use this pattern on a database whose data must be preserved.

Run the schema once the PostgreSQL container is healthy:

~~~powershell
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U jdbc_user -d jdbc_lab -f /scripts/schema-postgresql.sql
~~~

With `psql`, `-v ON_ERROR_STOP=1` halts execution if any SQL statement fails. Once the command succeeds, you have two empty tables with primary keys, foreign key constraints, and the required columns.

## 7. Creating the MySQL Schema

Write `db/schema-mysql.sql`:

~~~sql
-- FOR PRACTICE DATABASE ONLY.
DROP TABLE IF EXISTS books;
DROP TABLE IF EXISTS authors;

CREATE TABLE authors (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    code VARCHAR(20) NOT NULL UNIQUE,
    full_name VARCHAR(120) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE books (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    author_id BIGINT NOT NULL,
    book_code VARCHAR(30) NOT NULL UNIQUE,
    title VARCHAR(200) NOT NULL,
    published_on DATE,
    price_vnd BIGINT NOT NULL CHECK (price_vnd >= 0),
    stock_quantity INT NOT NULL DEFAULT 0
        CHECK (stock_quantity >= 0),
    CONSTRAINT fk_books_author
        FOREIGN KEY (author_id) REFERENCES authors(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE INDEX idx_books_author_id ON books(author_id);
~~~

MySQL uses `AUTO_INCREMENT` to generate primary keys. `InnoDB` supports foreign keys and transactions; `utf8mb4` allows storing Vietnamese-accented book titles and author names. The `CHECK` constraints in the example are enforced on the selected MySQL 8.4 release.

Once the MySQL container is ready, execute the schema through the MySQL client inside the container:

~~~powershell
docker compose exec -T mysql mysql -ujdbc_user -plocaldev -D jdbc_lab -e "SOURCE /scripts/schema-mysql.sql"
~~~

`SOURCE` instructs the MySQL client to read the file mounted into `/scripts`. Most SQL statements in the PostgreSQL and MySQL schemas are similar, but auto-increment column syntax, certain data types, and DDL details differ. Therefore **do not run the other database's schema file by mistake**.

## 8. Loading Shared Sample Data for Both Databases

Write `db/data.sql`. This file does not hardcode auto-increment IDs; it looks up authors using their business `code`:

~~~sql
INSERT INTO authors (code, full_name) VALUES
    ('AU-01', 'Nguyễn Minh An'),
    ('AU-02', 'Lê Thu Hà');

INSERT INTO books (
    author_id, book_code, title, published_on, price_vnd, stock_quantity
) VALUES
    (
        (SELECT id FROM authors WHERE code = 'AU-01'),
        'BK-001', 'Nhập môn SQL', '2024-01-15', 129000, 20
    ),
    (
        (SELECT id FROM authors WHERE code = 'AU-01'),
        'BK-002', 'Thiết kế dữ liệu quan hệ', '2024-06-10', 169000, 8
    ),
    (
        (SELECT id FROM authors WHERE code = 'AU-02'),
        'BK-003', 'Spring JDBC thực hành', '2025-02-05', 219000, 0
    );
~~~

Run **one of the two commands**, matching the database you started and the schema you created:

**PostgreSQL:**

~~~powershell
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U jdbc_user -d jdbc_lab -f /scripts/data.sql
~~~

**MySQL:**

~~~powershell
docker compose exec -T mysql mysql -ujdbc_user -plocaldev -D jdbc_lab -e "SOURCE /scripts/data.sql"
~~~

After the first load, `authors` has **2 rows** and `books` has **3 rows**. The seed file is not designed to be run twice in a row on the same data: `code` or `book_code` will collide and trigger a `UNIQUE` constraint violation. To reset the lab, re-run **the matching database's schema file first**, then run `data.sql` again.

## 9. Verifying Data with SQL

Before starting Spring Boot, verify the data by **querying the database directly**. Use the same SQL statements for both PostgreSQL and MySQL:

~~~sql
SELECT COUNT(*) AS author_count FROM authors;
SELECT COUNT(*) AS book_count FROM books;

SELECT
    b.book_code,
    b.title,
    a.full_name AS author_name,
    b.price_vnd,
    b.stock_quantity
FROM books b
JOIN authors a ON a.id = b.author_id
ORDER BY b.book_code;

SELECT book_code, title
FROM books
WHERE stock_quantity = 0
ORDER BY book_code;
~~~

The count queries must return `author_count = 2` and `book_count = 3`. The join result displays:

| book_code | title | author_name | price_vnd | stock_quantity |
|---|---|---|---:|---:|
| BK-001 | Nhập môn SQL | Nguyễn Minh An | 129000 | 20 |
| BK-002 | Thiết kế dữ liệu quan hệ | Nguyễn Minh An | 169000 | 8 |
| BK-003 | Spring JDBC thực hành | Lê Thu Hà | 219000 | 0 |

The final query returns `BK-003` because its stock is 0. If rows are missing, authors do not match, or duplicate codes appear, check whether you ran the right database's schema and seeded only once.

You can quickly run a count query from the terminal:

~~~powershell
# PostgreSQL
docker compose exec -T postgres psql -U jdbc_user -d jdbc_lab -c "SELECT COUNT(*) FROM books;"

# MySQL
docker compose exec -T mysql mysql -ujdbc_user -plocaldev -D jdbc_lab -e "SELECT COUNT(*) FROM books;"
~~~

These two commands are independent alternatives; use the one matching your running database.

## 10. Connecting the Spring Boot / Spring Data JDBC Application

When connecting via JDBC, Spring Boot requires the matching driver on the classpath, the database address, username, and password. Example `build.gradle` for a Spring Boot application using Gradle:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jdbc'

    // Keep the driver for the database in use; you may keep both
    // if the same application switches between the two profiles.
    runtimeOnly 'org.postgresql:postgresql'
    runtimeOnly 'com.mysql:mysql-connector-j'
}
~~~

If using Maven, the corresponding artifacts are `spring-boot-starter-data-jdbc`, `postgresql`, and `mysql-connector-j` with versions managed by the Spring Boot BOM.

Create configurations for **two independent Spring profiles** so switching databases is easy. The examples below live in `src/main/resources/` of your Spring Boot project.

**`application.yml`** — shared configuration:

~~~yaml
spring:
  application:
    name: jdbc-lab
  sql:
    init:
      mode: never
~~~

`spring.sql.init.mode: never` means the application **does not automatically re-run schema/seed SQL on startup**; in this lesson we ran the files via the database client. This avoids accidentally resetting data on a second run.

**`application-postgres.yml`:**

~~~yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/jdbc_lab
    username: jdbc_user
    password: ${JDBC_DB_PASSWORD:localdev}
~~~

**`application-mysql.yml`:**

~~~yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/jdbc_lab
    username: jdbc_user
    password: ${JDBC_DB_PASSWORD:localdev}
~~~

The expression `${JDBC_DB_PASSWORD:localdev}` uses the `JDBC_DB_PASSWORD` environment variable if set; otherwise it falls back to the demo password `localdev`. That fallback is only appropriate for local labs.

Activate the profile matching your database. Example in a Spring Boot project with a Gradle wrapper:

~~~powershell
# Windows PowerShell: PostgreSQL
.\gradlew.bat bootRun --args="--spring.profiles.active=postgres"

# Windows PowerShell: MySQL
.\gradlew.bat bootRun --args="--spring.profiles.active=mysql"
~~~

On Linux/macOS, the corresponding command is `./gradlew bootRun --args='--spring.profiles.active=postgres'` (or `mysql`). Run one profile at a time. If the application runs **in another container on the same Compose network** instead of on the host machine, change the JDBC hostname to the service name `postgres`/`mysql` and keep the container port `5432`/`3306`, because `localhost` inside a container refers to that container itself.

### Testing Access with a Repository

Once Spring Data JDBC is configured, you can define a minimal aggregate root for the `books` table:

~~~java
import java.time.LocalDate;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.data.repository.CrudRepository;

@Table("books")
public record Book(
    @Id Long id,
    Long authorId,
    String bookCode,
    String title,
    LocalDate publishedOn,
    long priceVnd,
    int stockQuantity
) {}

public interface BookRepository extends CrudRepository<Book, Long> {}
~~~

In a real project, place `Book` and `BookRepository` in **two separate Java files** within packages scanned by the Spring Boot application. Under the default naming strategy, `bookCode` maps to `book_code`, `authorId` to `author_id`, and `priceVnd` to `price_vnd`. In this illustrative model, the author is referenced by `authorId`; there is no need to map a large object graph.

Calling `bookRepository.count()` in a service or runner will return **3** if the JDBC URL, credentials, driver, and schema are all correct. Use `findAll()` to read the sample records. In this lesson, checking directly with SQL in the previous section remains the best way to isolate database errors from Java mapping errors.

## 11. Step-by-Step Troubleshooting When the Application Cannot Connect

| Symptom | Possible Cause | How to Check or Fix |
|---|---|---|
| `Connection refused` / timeout | Database not started or wrong host/port | Check `docker compose ps`, healthcheck, and port in the JDBC URL |
| `password authentication failed` / `Access denied` | Wrong username, password, or an existing volume initialized different credentials | Compare environment variables with actual database accounts; update credentials with SQL admin commands if needed |
| `database "jdbc_lab" does not exist` / `Unknown database` | Database not created or connecting with the wrong name | List existing databases and choose the right name in the URL |
| `relation "books" does not exist` / `Table 'jdbc_lab.books' doesn't exist` | Schema not run or connected to the wrong DB/schema | Run the matching schema file and verify the active database |
| `Table ... already exists` or unique constraint error when seeding | Scripts run out of order or data loaded multiple times | Reset the schema **only in the lab database** and load data once |
| `No suitable driver` / missing JDBC driver | Missing JDBC dependency for the database in use | Add `postgresql` or `mysql-connector-j` to the runtime classpath |
| Unable to read accented names properly | Mismatched file/script or connection encoding | Save SQL files as UTF-8; for MySQL use `utf8mb4` as in the sample schema |
| Foreign key error when inserting a book | `author_id` does not exist | Insert the author first and look up its ID by `code` |
| Connects from host, fails from app inside Docker | Wrongly using `localhost` | Use the Compose service name as the hostname on the shared network |

An easy-to-verify debugging sequence is **container healthy → CLI login succeeds → tables exist → seed has exact row counts → Spring Boot connects → repository returns results**. If a failure happens at any step, fix that step before changing domain code.

## 12. Preserving Data or Starting Over

Restarting containers normally **does not delete data** because named volumes are used:

~~~powershell
docker compose --profile postgres down
docker compose --profile postgres up -d --wait
~~~

Or replace `postgres` with `mysql` if you chose MySQL. Once back up, previous data remains in the volume. If you only want to reset the **sample data** back to its initial state, re-run the matching `schema-<database>.sql` file and then `data.sql`; that intentionally drops the old lab tables.

Running `docker compose down -v` **deletes Compose-managed volumes**, erasing the entire database for this practice environment. Only use it when you truly want to discard all experimental data; never use it blindly to fix connection errors without diagnosing the root cause.

For real systems, replace schema reset and demo data mechanisms with **versioned migrations** (such as Flyway or Liquibase) and controlled seeding. Never run automatic `DROP TABLE` scripts when a production application starts.

## 13. Self-Practice

After loading the data:

1. Query titles of books with `stock_quantity > 0` ordered by ascending price.
2. Count each author's books using `JOIN` and `GROUP BY`; expect author `AU-01` to have 2 books and `AU-02` to have 1 book.
3. Insert a valid book row for `AU-02` without manually supplying `books.id`.
4. Try inserting a book with a non-existent `author_id`; observe how the FK constraint prevents orphaned data.
5. Change the host port mapping, update the JDBC URL, and verify the application still connects.

Example solution for task 2:

~~~sql
SELECT a.code, a.full_name, COUNT(b.id) AS book_count
FROM authors a
LEFT JOIN books b ON b.author_id = a.id
GROUP BY a.id, a.code, a.full_name
ORDER BY a.code;
~~~

Once you have a running database, consistent sample data, and a verified JDBC connection, you have the foundation to move on to building **entities, aggregate roots, repositories, and Spring Data JDBC queries** backed by real tables.
