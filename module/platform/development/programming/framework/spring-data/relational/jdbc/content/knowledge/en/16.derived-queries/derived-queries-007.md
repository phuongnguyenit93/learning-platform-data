# `Like`, `StartingWith`, `EndingWith`, and `Containing`

In **Spring Data JDBC**, derived queries let you search strings by pattern directly in repository method names. Four commonly used keywords are `Like`, `StartingWith`, `EndingWith`, and `Containing`. All four generate SQL conditions based on the `LIKE` operator, but they differ in how `%` and `_` wildcards are handled in the parameter value.

Key distinctions:

- **`Like`**: uses a `LIKE` pattern supplied by the caller; the caller controls wildcard placement.
- **`StartingWith`**: finds values starting with the passed string; Spring Data appends `%` to the end of the parameter.
- **`EndingWith`**: finds values ending with the passed string; Spring Data prepends `%` to the start of the parameter.
- **`Containing`**: finds values containing the passed string anywhere; Spring Data adds `%` on both ends.

These methods express common search needs without manually concatenating SQL strings. However, actual results also depend on collation, case-sensitivity rules, how the database treats empty strings, and the database engine's ability to use indexes.

## 1. How Does `LIKE` Work in SQL?

`LIKE` matches a string value against a pattern. Two important wildcards:

| Character | Meaning | Pattern example | Some matching strings |
|---|---|---|---|
| `%` | Zero or more arbitrary characters | `Ann%` | `Ann`, `Anna`, `Annette` |
| `_` | Exactly one arbitrary character | `A_n` | `Ann`, `A-n`, `A1n` |

SQL example:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE 'Ann%';
```

This query finds names starting with `Ann`. Meanwhile:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE '%son';
```

finds names ending with `son`, and:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE '%ann%';
```

finds names containing `ann` anywhere.

`LIKE` is an SQL operator; `StartingWith`, `EndingWith`, and `Containing` are keywords in Spring Data method names. Spring Data translates these intents into `LIKE` conditions and prepares the corresponding bound values.

## 2. Entity and Repository Example

Suppose an application manages customers:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(200) NOT NULL
);
```

Entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
```

Repository:

```java
import java.util.List;
import org.springframework.data.repository.ListCrudRepository;

public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {

    List<Customer> findByNameLike(String pattern);

    List<Customer> findByNameStartingWith(String prefix);

    List<Customer> findByNameEndingWith(String suffix);

    List<Customer> findByNameContaining(String fragment);
}
```

The method names reference the Java property `name`. If a property maps to a column with a different name via `@Column`, Spring Data uses metadata to pick the physical column. This example uses the `name` column directly so it is easy to compare with the DDL.

## 3. `Like`: Caller Supplies the Full Pattern

Method:

```java
List<Customer> findByNameLike(String pattern);
```

`Like` passes the supplied value as the SQL `LIKE` pattern. Spring Data does not automatically infer whether the caller wants a prefix, suffix, or substring search; placing `%` and `_` is the pattern's responsibility.

Example:

```java
repository.findByNameLike("Ann%");   // Starts with Ann
repository.findByNameLike("%son");   // Ends with son
repository.findByNameLike("%ann%");  // Contains ann
repository.findByNameLike("A_n");    // A, one arbitrary character, then n
```

Equivalent SQL meaning:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE ?;
```

The bound parameter is `Ann%`, `%son`, `%ann%`, or `A_n` respectively. Because `Like` takes a complete pattern, the caller must understand SQL wildcards. If a user types `100%`, the `%` character will be interpreted as a wildcard unless escaped according to pattern rules.

## 4. `StartingWith`: Adds a Trailing Wildcard

Method:

```java
List<Customer> findByNameStartingWith(String prefix);
```

When called:

```java
repository.findByNameStartingWith("Ann");
```

Spring Data creates a condition equivalent to:

```sql
WHERE name LIKE ?
```

with a bound value equivalent to `Ann%`.

The trailing `%` means zero or more characters may follow `Ann`. Thus results can include `Ann`, `Anna`, `Annette`, `Ann Marie`, etc.

Do not add `%` manually to the argument:

```java
// Pass the raw string, do not add wildcards manually.
repository.findByNameStartingWith("Ann");
```

If you pass `Ann%`, the `%` inside the input may be treated as a literal character to search for via derived-query escaping, and the framework still appends its own trailing wildcard. Pass the **actual prefix** rather than constructing a pattern manually for `StartingWith`.

## 5. `EndingWith`: Adds a Leading Wildcard

Method:

```java
List<Customer> findByNameEndingWith(String suffix);
```

The call:

```java
repository.findByNameEndingWith("son");
```

is equivalent in meaning to:

```sql
WHERE name LIKE ?
```

with bound parameter `%son`.

The leading wildcard allows zero or more characters before `son`, so `Jackson`, `Anderson`, or `son` can match.

As with `StartingWith`, the caller only passes the suffix. Do not prepend `%` manually when using this keyword.

## 6. `Containing`: Adds Wildcards on Both Ends

Method:

```java
List<Customer> findByNameContaining(String fragment);
```

The call:

```java
repository.findByNameContaining("ann");
```

is equivalent in meaning to:

```sql
WHERE name LIKE ?
```

with bound parameter `%ann%`.

This condition searches for `ann` anywhere in the string. It can match `Ann`, `Joanne`, or `Ann Marie` depending on the database's case-sensitivity rules.

`Containing` is convenient for free-text search boxes, but consider performance because a leading wildcard (`%ann%`) usually prevents standard B-tree indexes from assisting prefix-style lookups.

## 7. Comparing the Four Keywords

Assuming the input parameter is always the string `ann`:

| Derived keyword | Equivalent SQL pattern | Meaning |
|---|---|---|
| `Like` | `ann` | Matches pattern `ann` literally if no wildcards are included |
| `StartingWith` | `ann%` | Starts with `ann` |
| `EndingWith` | `%ann` | Ends with `ann` |
| `Containing` | `%ann%` | Contains `ann` |

The general SQL shape for all four methods is:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE ?;
```

The difference lies in the **prepared parameter value**. `Like` uses the pattern passed by the caller; the other three keywords add wildcards in their respective positions.

## 8. Concrete Data Example

Suppose the `customers` table contains:

| id | name |
|---:|---|
| 1 | Ann |
| 2 | Anna Smith |
| 3 | Joanne |
| 4 | Anderson |
| 5 | Susan |
| 6 | An-n |
| 7 | Bob |

With the string `Ann`:

- `findByNameLike("Ann")`: matches only the exact pattern `Ann` (no wildcards).
- `findByNameStartingWith("Ann")`: matches `Ann` and `Anna Smith`.
- `findByNameEndingWith("Ann")`: matches names ending with `Ann`; none in this sample dataset.
- `findByNameContaining("Ann")`: matches `Ann` and `Anna Smith` if comparisons are case-sensitive by default.

If you use the lowercase fragment `ann`, results may differ depending on collation and case sensitivity. Do not assume `LIKE` is always case-insensitive across every database.

## 9. Escaping User-Supplied Wildcard Characters

`%` and `_` are special characters in SQL `LIKE`. If a user wants to search for a literal percent sign or underscore, the application must prevent them from accidentally acting as wildcards.

For example, if a user searches for names containing `50%`:

```text
Intended input: 50%
Intended meaning: literal characters '5', '0', '%'
```

If the pattern is sent directly as `%50%%`, the `%` entered by the user also acts as a wildcard; results can be broader than intended. SQL provides `ESCAPE` syntax to define an escape character:

```sql
SELECT id, name
FROM customers
WHERE name LIKE '%50!%%' ESCAPE '!';
```

Here `!%` represents a literal `%`; the remaining `%` characters are wildcards.

For derived queries `StartingWith`, `EndingWith`, and `Containing`, Spring Data has a mechanism to escape wildcard characters in the argument so they are interpreted as search content, and then adds the wildcards needed for the operation. The escape character used by query derivation, specific configuration, and detailed behavior follow your application's Spring Data Relational/JDBC version. `Like` accepts a complete pattern, so the caller must build and escape it proactively if input may contain wildcards.

When writing custom SQL, specify an escape clause compatible with your database and bind parameters. Do not concatenate user input into SQL to construct patterns. Parameter binding prevents SQL injection, but **it does not automatically turn `%` and `_` into literal characters**; escaping wildcards is a separate concern specific to `LIKE` semantics.

## 10. Case Sensitivity and `IgnoreCase`

Default `LIKE` behavior depends on the database, collation, and column type/configuration. Some databases or collations compare case-insensitively; others are case-sensitive.

If you want to request case-insensitive matching via a derived query, you can use the `IgnoreCase` keyword when supported by the query type and module:

```java
List<Customer> findByNameContainingIgnoreCase(String fragment);
```

Spring Data can generate a case-normalized comparison, conceptually like:

```sql
WHERE UPPER(name) LIKE UPPER(?)
```

The exact SQL depends on the dialect. If you need guaranteed behavior for your specific database, you can write `@Query` using functions or collations supported by that DBMS. Calling `UPPER(name)` or `LOWER(name)` on a column can interfere with ordinary index usage; consider functional indexes or appropriate collations if the query is on a hot path.

`IgnoreCase` does not address all issues involving Vietnamese diacritics, accents, Unicode normalization, or locales. Comparing `a` with `á`, or differently encoded Unicode forms, depends on database collation and normalization rules. If your application requires accurate natural-language search, design explicit data normalization and search rules.

## 11. Combining with Other Conditions

String-matching keywords can be combined with `And`, `Or`, and other properties:

```java
List<Customer> findByActiveTrueAndNameStartingWith(String prefix);

List<Customer> findByNameContainingOrEmailContaining(
        String nameFragment,
        String emailFragment
);
```

The first example finds active customers whose name starts with `prefix`. The second finds customers whose name contains the fragment **or** whose email contains the fragment.

Equivalent SQL meaning for the second method:

```sql
WHERE name LIKE ?
   OR email LIKE ?
```

With `Containing`, both parameters are wrapped with wildcards by the query derivation mechanism. When a method has both `And` and `Or`, apply derived query grouping rules and verify the logical expression. If you need parentheses different from what the method name expresses, use `@Query` with explicit parentheses.

## 12. Writing `@Query` When Custom Patterns or Escaping Are Needed

Derived queries work well for common prefix/suffix/substring searches. If you need fine-grained SQL control, you can write:

```java
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.query.Param;

@Query("""
    SELECT id, name, email
    FROM customers
    WHERE name LIKE :pattern
    """)
List<Customer> searchByPattern(@Param("pattern") String pattern);
```

The caller passes a complete pattern, such as `Ann%`, `%son`, or `%ann%`. Because this is custom SQL, **the caller is responsible for preparing wildcards and escaping** properly for the SQL statement and database. Do not assume `@Query` automatically adds wildcards like `StartingWith` or `Containing`.

If you always want a prefix search, you can write:

```java
@Query("""
    SELECT id, name, email
    FROM customers
    WHERE name LIKE CONCAT(:prefix, '%')
    """)
List<Customer> searchByPrefix(@Param("prefix") String prefix);
```

However, `CONCAT` syntax is not identical across all databases. For portable SQL, consider preparing the pattern in Java and binding it, or using a derived query so the framework handles wildcard wrapping. Either way, data must still be passed via bind parameters.

## 13. `NULL`, Empty Strings, and Wildcards

`LIKE` does not return `TRUE` when either the column value or the pattern is `NULL`; the expression typically evaluates to `UNKNOWN` and the row is excluded by `WHERE`.

```sql
WHERE name LIKE NULL
```

is not equivalent to searching for an empty string. If the `name` property is nullable, `Like`/`Containing` methods do not automatically find null rows; a separate `IsNull` method is needed if business rules require them.

Empty strings `""` also require attention:

- With `StartingWith("")`, the pattern after adding the wildcard can become `%`.
- With `EndingWith("")`, the pattern can become `%`.
- With `Containing("")`, the pattern can become `%%`.
- `Like("")` is an empty pattern, typically matching only empty strings.

Exact results also depend on how the database treats empty strings. Some engines treat empty strings as `NULL`; therefore, do not use an empty string to mean "no filter" without verifying behavior across target databases. In the service layer, you can skip the query when input is blank or apply an explicit business rule.

## 14. Performance: Prefix, Suffix, and Substring Do Not Have Equal Cost

The three pattern shapes have different query characteristics:

| Search type | Pattern | Likelihood of using a standard B-tree index |
|---|---|---|
| Prefix | `Ann%` | Often has a chance to use an index because there is no leading wildcard; depends on collation, DBMS, and execution plan |
| Suffix | `%son` | Usually difficult to use a standard string-ordered B-tree index |
| Substring | `%ann%` | Usually difficult to use a standard B-tree index due to leading and trailing wildcards |
| Arbitrary pattern | Caller-supplied | Depends on pattern structure and optimizer |

For small tables, `Containing` can be perfectly sufficient. For large tables where substring search is a core feature, consider full-text search, trigram indexes, inverted indexes, or a dedicated search engine depending on the database and requirements.

Do not add indexes by guesswork. Inspect execution plans on realistically sized datasets, measure query times, and check whether collations or functions render existing indexes unusable.

### Avoid `Containing` for every search box

If users only need prefix suggestions, `StartingWith` usually has better characteristics than `Containing`. For example, searching customer codes can often use `findByCustomerCodeStartingWith(prefix)`, whereas free-text substring search in names may need `Containing` but should limit input length, result count, and execution time.

## 15. Limiting Results and Pagination

Substring queries can return many rows. If the repository returns `List<Customer>`, all matching rows are materialized into a `List`. For large datasets, limit the result count or use pagination/sorting mechanisms supported by your Spring Data JDBC version and query methods.

Example limiting results via a derived query:

```java
List<Customer> findTop20ByNameStartingWithOrderByNameAsc(String prefix);
```

This method limits results to at most 20 rows and sorts ascending by `name` per query derivation rules. Verify limiting keyword support and how the dialect generates SQL in your application's version.

If pagination is needed, use the paging and sorting abstractions supported by Spring Data JDBC; `List` by itself is not a `Page` and carries no total page count.

## 16. Common Mistakes

| Symptom | Common cause | Resolution |
|---|---|---|
| `findByNameLike("Ann")` does not find `Anna` | `Like` uses the pattern verbatim; missing `%` | Pass `Ann%` or use `StartingWith` |
| `StartingWith` does not match suffixes | Wrong keyword chosen | Use `EndingWith` |
| `Containing` returns too many rows | `%fragment%` can match anywhere | Limit input/results or use prefix search if appropriate |
| `%` in input makes query too broad | User-supplied wildcard interpreted as pattern syntax | Escape wildcards or use derived keywords with sanitization |
| Case sensitivity differs from expectations | Collation/DBMS differences | Check collation, `IgnoreCase`, or specific SQL |
| Search is slow on large tables | Pattern has a leading wildcard | Inspect execution plans, specialized indexes, or full-text search |
| Empty string returns too many rows | Pattern becomes `%`/`%%` | Handle empty input in the service layer |
| Rows with null names do not appear | `LIKE` with `NULL` never evaluates to true | Use `IsNull` if null rows must be found |
| Custom query fails to match prefixes | Caller forgot to add wildcard | Prepare pattern in Java or use `StartingWith` |
| SQL injection when building patterns | Concatenating input into SQL strings | Use bind parameters; escape wildcards separately |

## 18. Principles to Remember

- `LIKE` is an SQL operator; `%` matches zero or more characters, and `_` matches exactly one character.
- `Like` takes a complete pattern supplied by the caller.
- `StartingWith` appends `%` at the end of the input string.
- `EndingWith` prepends `%` at the start of the input string.
- `Containing` adds `%` at both ends.
- Derived queries use Java properties; custom SQL uses physical table and column names.
- Bind parameters protect against SQL injection but do not replace wildcard escaping.
- `NULL`, empty strings, case sensitivity, and diacritics depend on database SQL/collation semantics.
- Prefix searches generally have a better chance of using B-tree indexes than suffix/substring searches; measure execution plans before optimizing.
- Limit results when searches can return many rows.

In Spring Data JDBC, choose `Like` when the caller needs control over the pattern, `StartingWith` for prefix matching, `EndingWith` for suffix matching, and `Containing` for substring matching. Understanding how wildcards are added, how special characters are escaped, and your database's characteristics will keep your queries semantically accurate, safe against user input, and well-suited to real data volumes.
