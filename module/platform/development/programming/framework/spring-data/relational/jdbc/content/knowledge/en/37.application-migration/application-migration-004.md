# Redesigning Bidirectional Relationships, Cascades, and Lazy Loading in Spring Data JDBC

## 1. Starting from the Differences Between JPA and Spring Data JDBC

When migrating an application from Spring Data JPA to Spring Data JDBC, the hard part is usually not changing repository interfaces. The bigger challenge is how relationships between entities are modeled.

JPA allows object graphs with relationships such as `@OneToMany`, `@ManyToOne`, `@OneToOne`, and `@ManyToMany`. Applications can configure cascades, orphan removal, and fetch types `LAZY`/`EAGER`. A persistence context tracks entities and can load related data when the application accesses properties.

Spring Data JDBC uses a simpler model:

- Each aggregate has exactly one aggregate root.
- Repositories operate on aggregate roots.
- Entities inside an aggregate are referenced unidirectionally from the root downward.
- Relationships across aggregates are represented by IDs or `AggregateReference`.
- There is no persistence context, dirty tracking, or lazy-loading proxies.
- When loading an aggregate, Spring Data JDBC materializes the complete aggregate per mapping.
- When saving an existing aggregate, referenced entities inside the aggregate are currently deleted and recreated according to the submitted object state.

Therefore, you should not carry JPA annotations straight over to Spring Data JDBC and expect identical semantics.

## 2. Define Aggregate Boundaries Before Designing Relationships

An aggregate is a group of entities that must maintain consistency as a unit during a business change. The aggregate root is the entry point and coordinator for changes to that group.

Example of an order:

~~~text
Order (aggregate root)
 ├── OrderLine
 ├── OrderLine
 └── ShippingAddress
~~~

When an `Order` is confirmed, its line items and shipping address must remain consistent with the `Order`. Therefore, they can live within the same aggregate.

Conversely, a `Customer` can be referenced by many `Order`s:

~~~text
Customer (aggregate root)       Order (aggregate root)
          1                  N
          └───────────────────┘
                 customer_id
~~~

`Customer` is not lifecycle-owned by an `Order`. Deleting an `Order` must not delete the `Customer`. These two entities should be separate aggregates.

Questions that help establish boundaries:

- Does the entity need to be modified independently via its own repository?
- Do multiple other aggregates reference this entity?
- When deleting the root, should this entity also be deleted?
- Must changes be atomic within the same transaction?
- Does this entity need to be loaded every time the root is loaded?
- Can consistency be maintained through a use case/service rather than an object graph?

Do not define aggregates solely because tables have foreign keys. A foreign key is a database-level relationship; an aggregate boundary is a decision about domain ownership and consistency.

## 3. Relationships Inside an Aggregate: Unidirectional References

For child entities belonging to an aggregate, object references flow from root to child. Example:

~~~java
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    private String orderNumber;

    private String status;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // Constructor, getters, and domain methods.
}
~~~

Child entity:

~~~java
@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    private String sku;

    private int quantity;

    // Constructor, getters, and domain methods.
}
~~~

Spring Data JDBC maps the collection as a one-to-many relationship. The `order_id` column sits on the `order_lines` table referencing `Order`'s ID.

There is no need to declare an `Order` property on `OrderLine` just to store this relationship. Spring Data JDBC manages the back-reference at the relational mapping level.

### 3.1. Using @MappedCollection to Configure Foreign Keys

You can specify the foreign key column and the collection position/key column:

~~~java
@MappedCollection(
        idColumn = "order_id",
        keyColumn = "line_position"
)
private List<OrderLine> lines;
~~~

For `List`, Spring Data JDBC also stores element position. For `Map`, the key column stores the map key. For `Set`, no position column is needed.

Example schema:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);
~~~

Actual column names depend on `@MappedCollection` and `NamingStrategy`. Keep Java mappings and schema migrations aligned.

## 4. When a Child Needs Reverse Access to the Aggregate Root

Sometimes a method on a child needs information from the root—for example, `OrderLine` needing the order number to build a description.

You do not need a bidirectional object reference persisted in both directions. Two design options exist.

### 4.1. Pass the Root into the Method

The simplest approach is passing the required information when invoking the method:

~~~java
public class OrderLine {

    private String sku;
    private int quantity;

    public String descriptionFor(Order order) {
        return sku + " in order " + order.getOrderNumber();
    }
}
~~~

The root coordinates:

~~~java
public class Order {

    public String describeLines() {
        return lines.stream()
                .map(line -> line.descriptionFor(this))
                .collect(Collectors.joining(", "));
    }
}
~~~

This keeps the object graph unidirectional. The child does not need to know about or retain a long-lived reference to the parent.

### 4.2. Using a Transient Back-Reference for Domain Behavior

If many child methods need access to the root, you can maintain an in-memory-only back-reference. Annotate the property with Spring Data's `@Transient`:

~~~java
import org.springframework.data.annotation.Transient;

public class OrderLine {

    private String sku;

    private int quantity;

    @Transient
    private Order order;

    void attachTo(Order order) {
        this.order = order;
    }

    public String description() {
        return sku + " in order " + order.getOrderNumber();
    }
}
~~~

The root attaches the child when adding it to the collection:

~~~java
public void addLine(OrderLine line) {
    lines.add(line);
    line.attachTo(this);
}
~~~

When Spring Data JDBC reconstructs the aggregate from the database, the root also needs to re-attach the back-reference. This can be done in the persistence constructor:

~~~java
import java.util.Collection;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private final Long id;

    private final String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private final List<OrderLine> lines = new ArrayList<>();

    @PersistenceCreator
    Order(
            Long id,
            String orderNumber,
            Collection<OrderLine> lines
    ) {
        this.id = id;
        this.orderNumber = orderNumber;
        lines.forEach(this::addLine);
    }

    public void addLine(OrderLine line) {
        lines.add(line);
        line.attachTo(this);
    }
}
~~~

This example illustrates the concept; constructors and collection types should match your actual entity. The `@Transient` property is not fetched from the database and should not be a parameter that converters must read directly in the persistence constructor. The root receives the mapped collection and attaches the parent via its domain method.

Use `@Transient` from `org.springframework.data.annotation`, not JPA's `@Transient`. If you forget to mark it transient, the converter may attempt to map the parent back into another relationship, creating a circular reference.

Another option is using an `AfterConvertCallback` to set the transient back-reference after the aggregate is materialized. Callbacks should only populate in-memory state, not create a bidirectional persistence relationship.

## 5. Relationships Between Aggregates: Store IDs Instead of Object References

Suppose `Order` references `Customer`. `Customer` may be shared across many `Order`s and has its own repository.

Do not declare a `Customer` object directly as a property of `Order` and treat `Customer` as a child of `Order`. If you do, Spring Data JDBC may treat `Customer` as part of the `Order` aggregate and apply aggregate persistence lifecycles to it.

Instead, store the ID:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;

    private String orderNumber;
}
~~~

Or use `AggregateReference` to explicitly express a reference to another aggregate:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.jdbc.core.mapping.AggregateReference;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private AggregateReference<Customer, Long> customer;

    private String orderNumber;
}
~~~

Creating the reference:

~~~java
Order order = new Order(
        AggregateReference.to(customerId),
        "ORD-2026-001"
);
~~~

Reading `Customer` only when actually needed:

~~~java
Customer customer = customerRepository
        .findById(order.getCustomer().getId())
        .orElseThrow();
~~~

`AggregateReference<T, ID>` holds the target aggregate's ID and indicates the referenced aggregate type. It does not auto-load `Customer`, does not create lazy-loading proxies, and does not invoke repositories automatically.

### 5.1. Querying in the Reverse Direction

To find `Order`s belonging to a `Customer`, declare a query on `OrderRepository`:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long> {

    @Query("""
        SELECT *
        FROM orders
        WHERE customer_id = :customerId
        """)
    List<Order> findByCustomerId(Long customerId);
}
~~~

The name `customer_id` must match the actual schema and mapping. Adjust the SQL if you use a different naming strategy.

You can use query derivation with `AggregateReference` as a parameter in supported Spring Data JDBC versions:

~~~java
List<Order> findByCustomer(
        AggregateReference<Customer, Long> customer
);
~~~

This clarifies query direction: `Order` references `Customer` by ID, while reverse lookup is handled via a repository query.

## 6. Designing Many-to-Many Relationships

JPA can model `@ManyToMany` with object collections on both sides. Spring Data JDBC does not support a many-to-many object graph with those semantics.

Example `Book` and `Author`:

- A `Book` can have many `Author`s.
- An `Author` can write many `Book`s.
- Deleting a `Book` must not delete an `Author`.
- Deleting an `Author` should not automatically delete remaining `Book`s.

These are two independent aggregates. The join table can be modeled as link rows owned by one aggregate or as its own aggregate, depending on the business lifecycle.

Example where `Book` owns the association rows:

~~~java
@Table("books")
public class Book {

    @Id
    private Long id;

    private String title;

    @MappedCollection(idColumn = "book_id")
    private Set<BookAuthor> authors = new HashSet<>();
}

@Table("book_authors")
public class BookAuthor {

    @Id
    private Long id;

    private Long authorId;
}
~~~

Schema:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL
);

CREATE TABLE authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE book_authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    book_id BIGINT NOT NULL,
    author_id BIGINT NOT NULL,
    CONSTRAINT fk_book_author_book
        FOREIGN KEY (book_id) REFERENCES books(id),
    CONSTRAINT fk_book_author_author
        FOREIGN KEY (author_id) REFERENCES authors(id),
    CONSTRAINT uk_book_author
        UNIQUE (book_id, author_id)
);
~~~

`BookAuthor` is part of the `Book` aggregate. It stores `authorId`, not an `Author` object. Deleting a `Book` deletes the association rows belonging to that `Book`, without deleting the `Author`s.

If the association holds its own business data such as role, contribution order, or join date, store those properties on `BookAuthor`.

If the relationship requires an independent lifecycle—for example, associations that are approved, locked, or managed by a separate workflow—design the association as its own aggregate root referencing `Book` and `Author` IDs.

Do not add a `Book` collection to `Author` just to mirror the reverse side. Use repository queries to find `Book`s associated with an `Author`.

## 7. What Does Cascade Mean in Spring Data JDBC?

Spring Data JDBC does not use JPA cascade annotations such as:

- `CascadeType.PERSIST`
- `CascadeType.MERGE`
- `CascadeType.REMOVE`
- `CascadeType.ALL`
- `orphanRemoval = true`

Instead, persistence lifecycle is governed by aggregate boundaries and the object graph referenced from the root.

### 7.1. Inserting a New Aggregate

When saving a new aggregate:

~~~java
Order order = new Order(
        "ORD-001",
        List.of(
                new OrderLine("SKU-A", 2),
                new OrderLine("SKU-B", 1)
        )
);

Order saved = orderRepository.save(order);
~~~

Spring Data JDBC inserts the aggregate root, then inserts entities referenced directly or indirectly within the aggregate.

### 7.2. Updating an Existing Aggregate

Under the current implementation, when saving an existing aggregate:

1. Referenced entities within the aggregate are deleted.
2. The aggregate root is updated.
3. Referenced entities are re-inserted according to the new object state.

Spring Data JDBC does not hold a prior snapshot of the aggregate to dirty-track each child individually. Thus, even if only one child changed, referenced entities may be deleted and recreated.

This can generate extra SQL and affect child auto-generated IDs. Never design an aggregate whose child rows are directly referenced by multiple other aggregates.

If a child needs independent updates, stable IDs, and references from multiple places, consider extracting it into a separate aggregate.

### 7.3. Deleting an Aggregate Root

When deleting an aggregate root via a repository, Spring Data JDBC deletes the aggregate along with its owned entities.

~~~java
orderRepository.deleteById(orderId);
~~~

Child rows are managed as part of the `Order` aggregate. No `CascadeType.REMOVE` is needed to instruct the framework to delete them.

### 7.4. Removing a Child from a Collection

Suppose an `Order` has three `OrderLine`s. If the application removes one line from the collection and saves the aggregate, the new persistence state no longer includes that line. Under the current save mechanism, referenced entities are deleted and recreated from the submitted collection, so the removed line is not re-inserted.

In end result, this resembles `orphanRemoval` semantics, though the execution mechanism differs from JPA. Spring Data JDBC does not use dirty tracking to pinpoint which exact child was removed; it synchronizes the submitted aggregate state.

## 8. Distinguishing Internal Cascades from References to Other Aggregates

| Operation | Child Entity Inside Aggregate | Other Aggregate Referenced by ID |
|---|---|---|
| Insert root | Inserts child entities | Writes only the ID reference |
| Save existing root | Synchronizes child entities; current implementation deletes and recreates | Does not automatically save target aggregate |
| Remove child from collection | Child is no longer persisted | Not applicable |
| Delete root | Deletes aggregate members | Does not automatically delete target aggregate |
| Update target aggregate | Performed via target aggregate's repository | Not automatically updated from referencing root |

For example, `Order` references `Customer` via `AggregateReference`. When deleting `Order`:

- The `Order` row is deleted.
- `OrderLine`s belonging to `Order` are deleted.
- The `Customer` row remains intact.

If the database has a foreign key from `orders.customer_id` to `customers.id`, that constraint continues protecting reference validity. Configuring `ON DELETE RESTRICT`/`NO ACTION` or `SET NULL`/`CASCADE` is a database schema decision, not a Spring Data JDBC cascade annotation.

Choose database behavior appropriate for the domain. Specifically, `ON DELETE CASCADE` on a foreign key to another aggregate can delete more data than intended if not explicitly designed for.

## 9. No Lazy Loading in Spring Data JDBC

Spring Data JDBC does not provide JPA-style lazy-loading proxies. When loading an aggregate, the framework executes SQL and materializes the aggregate according to the mapping. Once the repository method returns, the caller receives an entity already loaded per that operation's contract.

Example:

~~~java
Order order = orderRepository.findById(orderId)
        .orElseThrow();

List<OrderLine> lines = order.getLines();
~~~

Accessing `getLines()` does not trigger a new lazy query like a JPA collection proxy. The collection was loaded during aggregate materialization.

This has several implications:

- No `LazyInitializationException` from accessing a proxy after a session closes.
- No persistence context holding entities and tracking mutations.
- Cannot use `FetchType.LAZY` to defer collection loading.
- A large aggregate can consume significant time and memory immediately upon loading.
- If only a subset of data is needed, use a dedicated query or read model.

### 9.1. Single Query Loading Is Not Lazy Loading

Starting in Spring Data JDBC 3.2, Single Query Loading can load multiple aggregates and their collections in a single SQL statement in supported cases.

It changes how loading is executed, not the semantics—it does not make relationships lazy. The aggregate is still materialized before the repository returns.

The feature has limitations regarding nested collections, `AggregateReference`, embedded entities, database dialects, and repository method types. Check documentation for your version and inspect actual SQL.

### 9.2. When You Do Not Want to Load the Whole Aggregate

If a screen only needs order number, status, and total amount, loading all `OrderLine`s may be unnecessary.

You can create a read model:

~~~java
public record OrderSummary(
        Long id,
        String orderNumber,
        String status,
        BigDecimal totalAmount
) {}
~~~

Use a custom repository query or `JdbcTemplate` to fetch only the required data:

~~~sql
SELECT
    o.id,
    o.order_number,
    o.status,
    COALESCE(SUM(l.quantity * p.price), 0) AS total_amount
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.id
LEFT JOIN products p ON p.sku = l.sku
WHERE o.id = :orderId
GROUP BY o.id, o.order_number, o.status;
~~~

Read models fit screens, reports, and aggregate summaries. When business mutations are needed, still use the aggregate root and domain methods to protect invariants.

## 10. Migrating Specific JPA Relationship Patterns

### 10.1. @OneToMany with Cascade ALL and orphanRemoval

JPA:

~~~java
@OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
)
private List<OrderLine> lines;
~~~

Spring Data JDBC:

~~~java
@MappedCollection(idColumn = "order_id")
private List<OrderLine> lines;
~~~

No `Order` property is needed on `OrderLine` to map the foreign key. The root owns the collection and controls adding/removing children.

### 10.2. @ManyToOne(fetch = LAZY)

JPA:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "customer_id")
private Customer customer;
~~~

Spring Data JDBC:

~~~java
@Column("customer_id")
private AggregateReference<Customer, Long> customer;
~~~

When `Customer` is needed:

~~~java
Customer customer = customerRepository
        .findById(order.getCustomer().getId())
        .orElseThrow();
~~~

This is an explicit read operation. No proxy automatically fetches `Customer` when `order.getCustomer()` is called.

### 10.3. @OneToOne

If the referenced entity truly belongs to the same aggregate, you can use a unidirectional object reference. For example, `Order` owns `ShippingAddress`:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    private ShippingAddress shippingAddress;
}
~~~

Spring Data JDBC treats `ShippingAddress` as an entity/value belonging to the `Order` aggregate according to the mapping. If `ShippingAddress` needs to be shared or managed independently, extract it into its own aggregate and store an ID/reference.

### 10.4. @ManyToMany

JPA:

~~~java
@ManyToMany
@JoinTable(name = "book_author")
private Set<Author> authors;
~~~

Spring Data JDBC:

- Split `Book` and `Author` into two aggregates.
- Model link rows using an association entity/aggregate.
- Store author IDs in the association.
- Use repository queries to search in the reverse direction.

Do not use `Set<Author>` as a child collection if `Author` is shared across multiple `Book`s. That breaks aggregate ownership and deletion semantics.

## 11. Coordinating Multiple Aggregates in a Service

When a use case must modify multiple aggregates, the service/application layer coordinates the repositories.

Example placing an order:

~~~java
@Service
public class OrderService {

    private final OrderRepository orders;
    private final CustomerRepository customers;

    public OrderService(
            OrderRepository orders,
            CustomerRepository customers
    ) {
        this.orders = orders;
        this.customers = customers;
    }

    @Transactional
    public Order placeOrder(Long customerId, List<OrderLine> lines) {
        Customer customer = customers.findById(customerId)
                .orElseThrow();

        customer.ensureCanPlaceOrder();

        Order order = new Order(
                AggregateReference.to(customer.getId()),
                lines
        );

        return orders.save(order);
    }
}
~~~

In this example, `Customer` and `Order` are two aggregates. The service loads `Customer` to enforce business checks and then creates an `Order` referencing `Customer`.

If a use case needs to update both aggregates, operations can share the same transaction when using the same `DataSource` and transaction manager. Nevertheless, aggregate boundaries remain independent; the service coordinates cross-aggregate changes.

Do not embed the entire `Customer` object inside `Order` just to call `customer.getName()` or `customer.getStatus()`. When data is needed, read `Customer` via its repository or build an appropriate read model.

## 12. Consistency Boundaries When Referencing Other Aggregates

Aggregates are designed to guarantee consistency within their own boundaries. Relationships between two aggregates can change across different transactions.

For example, `Customer` has an `ACTIVE` status. New `Order`s may only be placed while `Customer` is active.

Two approaches:

1. Load `Customer`, verify status, and create `Order` inside a suitable transaction.
2. If the process spans multiple steps or longer durations, use workflows/events for eventual consistency with compensating actions where needed.

Do not assume holding an object reference to `Customer` inside `Order` keeps `Customer` state automatically synchronized. `AggregateReference` only holds an ID.

If an invariant must be strictly enforced across multiple aggregates, re-evaluate boundaries or use transaction/locking mechanisms suited to the requirement. Do not create a giant aggregate just to avoid designing cross-aggregate consistency.

## 13. Performance Considerations When Redesigning

Replacing JPA associations with ID references and explicit queries gives control over when queries run, yet can also cause applications to issue many repository calls if fetching per ID inside a loop.

Inefficient example:

~~~java
for (Order order : orders) {
    Customer customer = customers.findById(
            order.getCustomer().getId()
    ).orElseThrow();

    // Build response.
}
~~~

If the list contains many `Order`s, this can issue N `Customer` queries.

You can batch-load `Customer`s by a list of IDs or use a JOIN read query to materialize a DTO:

~~~sql
SELECT
    o.id,
    o.order_number,
    c.name AS customer_name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = :status;
~~~

Use aggregate repositories for domain operations and custom read queries for screens needing data across multiple aggregates. Do not add bidirectional object references merely to avoid writing queries.

## 14. Redesign Workflow When Migrating from JPA

1. List existing JPA entities, tables, and relationships.
2. Identify aggregate roots based on invariants and lifecycle ownership.
3. Keep unidirectional object references for entities truly belonging to the same aggregate.
4. Use `@MappedCollection` to declare collections and foreign key columns.
5. Replace references to other aggregates with IDs or `AggregateReference`.
6. Remove object back-references from persistence mappings; if needed by the domain, use method parameters or `@Transient`.
7. Replace reverse traversal with repository queries or derived queries.
8. Replace JPA cascades with save/delete on the aggregate root and service orchestration.
9. Replace lazy loading with explicit repository calls, batch queries, or read models.
10. Update schema migrations, foreign keys, unique constraints, and indexes.
11. Evaluate delete/reinsert impact on referenced entities when saving existing aggregates.
12. Write integration tests for inserts, updates, child removals, root deletes, and cross-aggregate references.
13. Measure query counts and realistic data loads after redesigning.

## 15. Common Pitfalls

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Saving aggregate causes mapping cycle | Two entities hold persisted bidirectional object references | Keep unidirectional reference; mark back-reference `@Transient` |
| Deleting root deletes shared entity | Entity was modeled as a child inside the aggregate | Extract entity into a separate aggregate and store its ID |
| Children are not saved | Child is not in the object graph referenced by root | Place child in `@MappedCollection` or redesign ownership |
| Children are deleted and recreated on save | Spring Data JDBC syncs referenced entities via delete/reinsert | Keep children private to aggregate; extract children needing independent identity |
| Child IDs change unexpectedly | Child uses generated IDs and is recreated when root saves | Do not let other aggregates reference children; consider stable IDs or separate aggregate |
| Calling getter does not auto-load `Customer` | `AggregateReference` only holds ID | Call repository explicitly or use a read query |
| Loading lists issues many queries | Aggregates with collections are loaded via separate statements | Measure SQL; consider Single Query Loading or read models |
| `@ManyToMany` does not map like JPA | Spring Data JDBC does not support many-to-many object graphs | Use an association entity/aggregate and IDs |
| Deleting `Customer` is rejected by foreign key | `Order` still references `Customer` | Handle references or choose appropriate database deletion policy |
| Deleting `Customer` unexpectedly removes `Order`s | FK has inappropriate `ON DELETE CASCADE` | Review schema constraints and lifecycle policies |
| Cannot query entity in reverse direction | No automatic back-reference object | Write query in the repository of the aggregate owning the FK |
| Transient back-reference is null after load | Reference not re-attached during aggregate construction | Attach in persistence constructor or callback |
| Creating multiple repositories for child tables | Confusing per-table repositories with per-aggregate-root repositories | Create repositories for aggregate roots |
| Saving aggregate issues more SQL than JPA | No dirty tracking; children are resynchronized | Evaluate aggregate size and use custom persistence/read models when needed |

## 17. Key Takeaways

- Spring Data JDBC designs persistence around aggregate roots, not JPA-style bidirectional object graphs.
- Intra-aggregate relationships flow unidirectionally from root to children.
- `@MappedCollection` declares child collections and foreign-key/back-reference columns.
- If a child needs the root, pass the root into a method or use a `@Transient` back-reference attached in memory.
- Cross-aggregate relationships use IDs or `AggregateReference<T, ID>`.
- For reverse navigation, write repository queries based on the foreign key.
- Many-to-many should be modeled with an association entity/aggregate rather than mutually referencing object collections.
- Spring Data JDBC does not use JPA's `CascadeType` or `orphanRemoval`; aggregate boundaries govern which entities are saved and deleted with the root.
- When saving an existing aggregate, the current implementation deletes and recreates referenced entities; there is no per-child dirty tracking.
- Deleting an aggregate root does not automatically delete other aggregates referenced by ID.
- There are no lazy-loading proxies. Repository loads materialize aggregates per mapping before returning results.
- Single Query Loading changes SQL count on load but does not turn relationships lazy.
- Use repository queries, batch loading, or read models when only partial aggregate data or cross-aggregate data is needed.
- Update schema foreign keys and test deletion policies when migrating from JPA.
