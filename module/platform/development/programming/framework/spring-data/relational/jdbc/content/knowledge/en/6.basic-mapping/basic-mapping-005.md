# Excluding Non-Persisted Data with `@Transient`

In **Spring Data JDBC**, not every property on a Java object needs a corresponding column in the database. A domain object may hold temporary UI data, in-memory computed results, short-lived processing state, or supplementary data populated after reading from the database. That information is not necessarily part of the state that should be persisted.

The **`org.springframework.data.annotation.Transient`** annotation marks a property so that it **does not participate in Spring Data's persistence mapping**. Understanding this annotation prevents creating unnecessary columns, avoids confusing in-memory state with durable state, and keeps aggregate boundaries clean.

This lesson focuses on how to use `@Transient` in **Spring Data Relational JDBC**: which properties are read/written, the lifecycle of non-persisted data, how it interacts with constructors and repositories, how it differs from similarly named annotations, and common pitfalls.

## 1. How Does Spring Data JDBC Map Properties?

Spring Data JDBC uses entity and aggregate mapping metadata to convert back and forth between **Java objects** and **database rows**.

For example, a product entity has the properties:

~~~text
Product
  id              -> product.id
  sku             -> product.sku
  priceMinorUnits -> product.price_minor_units
  adminNote       -> temporary info used only in Java
~~~

Suppose the `product` table only has three columns:

~~~sql
CREATE TABLE product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL,
    price_minor_units BIGINT NOT NULL
);
~~~

Here, `adminNote` might be a note displayed while staff view or edit a product, yet **it is not a property that needs to be saved with the product**. If `adminNote` is mapped like an ordinary property, Spring Data JDBC may expect a corresponding column when generating read/write SQL statements. When that column does not exist, saving or reading can fail.

We want the model to have two groups of properties:

| Group | Example | When Saving via Repository | When Reading Back via Repository |
| --- | --- | --- | --- |
| Mapped properties | `id`, `sku`, `priceMinorUnits` | May participate in SQL `INSERT`/`UPDATE` per Spring Data JDBC mechanics | Restored from table data |
| `@Transient` properties | `adminNote` | Excluded by Spring Data JDBC from persistence mapping operations | Not populated from a database column |

`@Transient` does not require removing the field from the Java class. It only changes how **Spring Data recognizes persisted properties**.

## 2. Exact Syntax of `@Transient`

Required import:

~~~java
import org.springframework.data.annotation.Transient;
~~~

Apply it to the property you want to exclude from mapping:

~~~java
@Transient
private String adminNote;
~~~

In entities using Spring Data JDBC's default field access, placing the annotation on the field is readable and consistent. When a class is designed with a different property access style, annotation placement must align with the actual mapping strategy.

You can visualize it as:

~~~text
Application creates / modifies Product
             |
             v
        Product object
       /             \
 sku, price,...   adminNote
       |              |
       v              v
 Spring Data JDBC    @Transient
       |              |
       v              X   excluded from mapping
 INSERT / UPDATE
       |
       v
   product table
~~~

**Key distinction:** a `@Transient` property still exists in memory and can still be read or mutated through normal Java methods. Only Spring Data's persistence mapping ignores it.

## 3. Complete Example: Temporary Property in a Product Entity

Suppose the application has the `product` table from Section 1. A Spring Data JDBC class can be written as:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("product")
public class Product {

    @Id
    private Long id;

    private String sku;

    @Column("price_minor_units")
    private long priceMinorUnits;

    @Transient
    private String adminNote;

    public Product(Long id, String sku, long priceMinorUnits) {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU must not be blank");
        }
        if (priceMinorUnits < 0) {
            throw new IllegalArgumentException("Price must not be negative");
        }
        this.id = id;
        this.sku = sku;
        this.priceMinorUnits = priceMinorUnits;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public long getPriceMinorUnits() {
        return priceMinorUnits;
    }

    public String getAdminNote() {
        return adminNote;
    }

    public void setAdminNote(String adminNote) {
        this.adminNote = adminNote;
    }
}
~~~

In this example:

- `@Table("product")` specifies the table.
- `@Id` marks the identifier property.
- `@Column("price_minor_units")` specifies the column for `priceMinorUnits`.
- `@Transient` excludes `adminNote` from Spring Data JDBC mapping.
- The constructor takes **only the mapped properties**. `adminNote` is not a required parameter to reconstruct the entity from the database.

This is a regular Java class: `adminNote` has a getter/setter for business logic or UI use, yet it does not become a column in the `product` table.

### Repository

~~~java
import org.springframework.data.repository.CrudRepository;

public interface ProductRepository extends CrudRepository<Product, Long> {
}
~~~

### Saving and Reloading

~~~java
Product product = new Product(null, "BOOK-021", 185_000L);
product.setAdminNote("Previewing changes in the admin UI");

Product saved = productRepository.save(product);

Product reloaded = productRepository.findById(saved.getId())
        .orElseThrow();

System.out.println(reloaded.getSku());            // "BOOK-021"
System.out.println(reloaded.getPriceMinorUnits()); // 185000
System.out.println(reloaded.getAdminNote());       // null
~~~

In this example, `reloaded.getAdminNote()` returns `null` because the class does not initialize a value for it, and Spring Data JDBC does not load it from the database. If the class has a field initializer or constructor that sets a default value, the property may hold that default upon reload; **`@Transient` only ensures it is not populated from mapped database data**.

Spring Data JDBC does not provide a persistence context or managed-object cache like JPA. A typical `findById` call reads the aggregate fresh from the database, so the example clearly illustrates the boundary between in-memory state and persisted state.

### Which Columns Will Generated SQL Touch?

Conceptually, inserting a new product corresponds to:

~~~sql
INSERT INTO product (sku, price_minor_units)
VALUES (?, ?);
~~~

The `adminNote` property **does not appear** in the mapped column list. Actual SQL, generated-key retrieval, and parameter ordering depend on the Spring Data JDBC version, dialect, and configuration; do not treat illustrative SQL syntax as an exact snapshot for every database.

If you add a `@Transient` field to the class without adding a new column to the table, the schema does not need to change for that field.

## 4. How `@Transient` Affects Reads and Writes

This annotation has a clear scope:

**When writing data**

- Spring Data JDBC excludes transient properties from the mapped properties inserted or updated.
- Values assigned in Java do not become persistent state via `repository.save(...)`.
- Changing only a transient field does not turn it into a database column update.

**When reading data**

- The framework does not look up a column to populate a transient property.
- The property holds its Java default value or whatever the constructor/initializer sets.
- If you want that value populated after loading an entity, the application must **recompute it, assign it, or fetch it from another source** through an explicit design.

**In the database**

- `@Transient` does not create, drop, or alter schema columns.
- If the table already has a column with the same name, the annotation does not drop that column.
- Schema migrations remain the responsibility of DDL, Flyway/Liquibase, or database administration processes.

In particular, do not think of `@Transient` as a SQL command or a data-encryption mechanism. It is mapping metadata on the application side.

## 5. When Should You Use `@Transient`?

There are several valid use cases, as long as it is clear that the value will not be restored from the database when reloading the entity.

| Case | Example | Why Not Persist with the Aggregate? |
| --- | --- | --- |
| UI data for a single processing flow | `adminNote`, `selectedInUi` | Only meaningful during the current request or interactive session. |
| Derived values that can be recomputed | `displayLabel`, `formattedPrice` | Derived from persisted properties; avoids a second source of truth. |
| Temporary calculation previews | `calculatedDiscountPreview` | Used only for a preview screen before confirmation. |
| Internal processing status | `validationMessages`, `importWarnings` | Reflects the outcome of a processing step, not the product record itself. |
| Supplementary data from another system | `inventoryPreview` fetched from another service | Avoids turning on-the-fly fetched data into persisted aggregate state. |
| Local computation cache | `cachedPresentationText` | Can be regenerated and has its own refresh policy. |

Example with a display label:

~~~java
@Transient
private String displayLabel;

public void prepareDisplayLabel() {
    this.displayLabel = sku + " - " + priceMinorUnits + " minor units";
}
~~~

After the repository loads the object, code calls `prepareDisplayLabel()` if the screen needs that label. Do not assume the framework calls such a method automatically.

However, if a value is completely derived from persisted fields and cheap to compute, **avoiding a transient field altogether is often simpler**:

~~~java
public String getDisplayLabel() {
    return sku + " - " + priceMinorUnits + " minor units";
}
~~~

With this second approach, the value is computed on every call, no extra state needs to be kept, and nothing goes out of sync when `sku` or `priceMinorUnits` changes. With Spring Data JDBC's field access, a computed getter like this does not necessarily become a persistent property; if custom property access is configured, verify the mapping accordingly.

### Which Derived Data Should NOT Be Kept Only as `@Transient`?

If a result carries legal or business significance at **the moment it occurred** and must be preserved historically, do not assume it can always be recomputed from current data. For example:

- The locked-in price of an order line.
- The exchange rate applied at checkout time.
- The tax amount calculated and confirmed when an invoice was issued.

Such values may need to be persisted durably as part of business state. Being able to compute a value today does not mean you can accurately reconstruct a past transaction's value.

## 6. Distinguishing Different Kinds of “Not Persisted”

The following mechanisms look similar in name or effect, but are not interchangeable.

| Mechanism | System | Primary Meaning | Replaces Spring Data JDBC's `@Transient`? |
| --- | --- | --- | --- |
| `org.springframework.data.annotation.Transient` | Spring Data Commons, used by Spring Data JDBC | Excludes property from persistence mapping | **Yes**, this is the annotation being covered. |
| `transient` (Java keyword) | Java language and Java Object Serialization | Marks a field to skip Java's default serialization | Do not treat the two as equivalent; use the Spring annotation to express mapping intent clearly. |
| `jakarta.persistence.Transient` | JPA/Jakarta Persistence | Excludes property in the JPA model | Not the annotation used as Spring Data JDBC's mapping contract. |
| `com.fasterxml.jackson.annotation.JsonIgnore` | Jackson | Skips property during JSON processing per Jackson config | **No**; a field omitted from JSON can still be saved to the DB. |
| Spring Data's `@ReadOnlyProperty` | Spring Data | Property can be read from the store but is not written by mapping | **No**, because `@Transient` skips both reads and writes. |
| `static` (Java field) | Java language | Class-level state, not per-instance state | Not used to represent per-entity temporary data. |

### 6.1. `@Transient` Differs from `@JsonIgnore`

Suppose:

~~~java
@Transient
private String adminNote;
~~~

If the class has a getter and Jackson serializes it under standard configuration, `adminNote` **can still appear in JSON**. Spring Data mapping and JSON serialization are two independent pipelines:

~~~text
Product Entity
  |
  +--- Spring Data JDBC  -> SQL / product table
  |           |
  |           +--- @Transient: skips column mapping
  |
  +--- Jackson           -> JSON response
              |
              +--- @JsonIgnore: controls JSON property
~~~

If a field must neither be persisted nor returned in an API response, the application may need **two separate mechanisms**—for example `@Transient` for persistence and `@JsonIgnore` for JSON, or separating the entity from the response DTO.

Conversely, a field annotated with `@JsonIgnore` **can still be persisted by Spring Data JDBC** if it is a persistent property. Do not use JSON annotations to dictate database schema.

### 6.2. Spring Data's `@Transient` Differs from JPA's `@Transient`

The two imports look very similar:

~~~java
// Use when mapping with Spring Data JDBC:
import org.springframework.data.annotation.Transient;

// JPA annotation, belongs to a different persistence mechanism:
// import jakarta.persistence.Transient;
~~~

Spring Data JDBC uses the Spring Data Relational mapping system. Copying a JPA example verbatim and only swapping dependencies often leads to misunderstandings about behavior. Always check **the annotation's package**, not just the name `Transient`.

### 6.3. `@Transient` Differs from Read-Only Properties

Sometimes the database has a computed column or a field maintained by the database that the application needs to **read without overwriting**. In that case, excluding both reads and writes with `@Transient` does not meet the requirement. Look at read-only mapping mechanisms supported by Spring Data JDBC, such as `@ReadOnlyProperty` where appropriate, or use dedicated SQL queries/projections.

For example, a `last_synced_at` column updated by another process: if the entity needs to display that timestamp, `@Transient` would prevent it from being populated on load. The annotation only makes sense when you truly **do not want to map the value from the database at all**.

## 7. Notes on Constructors and Immutable Entities

Spring Data JDBC must instantiate objects from loaded data. The framework typically binds database column values into persistence constructor parameters or sets mapped properties after instantiation.

**A `@Transient` property has no database value to bind into a persistence constructor.** Therefore, do not make it a required parameter in the constructor Spring Data uses to materialize the entity.

### Example Prone to Problems

~~~java
public class ProductView {

    private final Long id;
    private final String sku;

    @Transient
    private final String editorMessage;

    // The only constructor requires editorMessage.
    public ProductView(Long id, String sku, String editorMessage) {
        this.id = id;
        this.sku = sku;
        this.editorMessage = editorMessage;
    }
}
~~~

When Spring Data JDBC materializes the entity, `editorMessage` has been excluded from mapping, so there is no corresponding data value to supply to that parameter. This design lacks a clean object-reconstruction contract.

### Better-Suited Design

~~~java
import org.springframework.data.annotation.Transient;

public class ProductView {

    private final Long id;
    private final String sku;

    @Transient
    private String editorMessage;

    public ProductView(Long id, String sku) {
        this.id = id;
        this.sku = sku;
    }

    public void attachEditorMessage(String message) {
        this.editorMessage = message;
    }
}
~~~

The constructor used to reconstruct the object requires only persisted data, while `editorMessage` is attached **after loading** when a workflow needs it.

If a class has multiple constructors or factories, ensure Spring Data can identify the persistence constructor (using `@PersistenceCreator` where appropriate) and has parameter name metadata available, such as compiling with `-parameters`. For temporary values that can be computed directly, a stateless method may be cleaner than even a transient field.

### Records and Immutable Types

Records fit value objects well where **every record component belongs to the persisted value**, such as `Money(amount, currency)`. If a record component appears in the canonical constructor yet is excluded from mapping with `@Transient`, object materialization requires careful thought: the framework has no column to pass to that component.

Avoid adding transient fields meant purely for “UI formatting” onto persistence records just because records are concise. Keep domain value objects clean, and create separate DTOs/view models for presentation data when needed.

## 8. `@Transient` and Aggregate Boundaries

Spring Data JDBC treats the aggregate root together with its mapped members as a persistence unit. Consequently, marking a reference property with `@Transient` can have a much broader impact than skipping a display string.

Example:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @Transient
    private List<OrderLine> previewLines;
}
~~~

Here, `previewLines` is a **temporary list**; Spring Data JDBC will not save those elements as an aggregate collection. If `previewLines` were actually the official list of order lines, marking it `@Transient` would silently prevent all child data from being saved as expected.

Distinguishing the cases:

| Property | Appropriate Design |
| --- | --- |
| Real order lines owned by the order that must be saved and restored | Map as an aggregate collection using the proper Spring Data JDBC mechanism, e.g., `@MappedCollection` and matching schema. |
| Simulated order lines used to preview a change | Can be `@Transient` if it exists solely in memory for that flow. |
| Customer info belonging to an independent aggregate | Usually store an ID/reference rather than pulling another root into the ownership graph; do not use `@Transient` as a workaround for a misdesigned relationship. |
| Audit history that must be preserved | Persist using an appropriate durable model; do not mark `@Transient` just because the column has not been added yet. |

Practical rule: **exclude from mapping only when the data genuinely does not belong to the aggregate's persistent state**. If a column is missing or a relationship has not been modeled yet, `@Transient` is not a substitute for a proper schema and domain model.

## 9. `@Transient` Does Not Create a Queryable Database Property

A field excluded from mapping has no column backing it. Therefore, do not build repositories assuming you can filter or sort in SQL by a transient field:

~~~java
@Transient
private String displayLabel;
~~~

For instance, the following repository method has no clear column-mapping basis for `displayLabel`:

~~~java
// Inappropriate if displayLabel is only temporary data in Java:
List<Product> findByDisplayLabel(String displayLabel);
~~~

Depending on how Spring Data builds queries and mappings, this setup can fail at query-creation time or runtime. To filter data efficiently in the database:

- Query by **persisted and mapped properties**, such as `sku`.
- If a computed SQL expression is needed, use SQL with the appropriate expression or a dedicated read projection.
- If filtering a small already-loaded subset in memory is enough, compute and filter in Java, keeping data size and loading cost in mind.

Similarly, writing manual SQL with `JdbcTemplate`/`JdbcClient` is a separate mechanism: custom SQL can select any column or expression the database supports. `@Transient` does not alter SQL written by the developer; it only governs Spring Data's mapping of persistent properties.

## 10. Should You Use `@Transient` for Sensitive Data?

Suppose code has a property:

~~~java
@Transient
private String temporaryVerificationCode;
~~~

This annotation prevents **the Spring Data JDBC repository from automatically saving that field** into the entity's table. By itself, however, it **does not**:

- Encrypt data in memory.
- Prevent the code from appearing in `toString()`, logs, exceptions, or debuggers.
- Prevent Jackson from serializing the value in an API response.
- Clear the value from memory after use.
- Guarantee other code does not write the value to the database via manual SQL.
- Provide expiration policies, access control, or data masking.

For sensitive or temporary data, first choose an appropriate storage location and lifecycle. A transient field on an entity can be convenient for short-lived handling, but it is not a complete security mechanism. For data used only during an HTTP request, a dedicated request or service object is usually clearer than attaching that state to a persisted entity.

## 11. Common Mistakes

| Error | Cause | Resolution |
| --- | --- | --- |
| Added a new field just for display, then repository reports column does not exist | Spring Data treats the field as a persistent property | Add `@Transient` if truly non-persisted; if it must be stored, add schema/mapping properly. |
| Set a transient value and expected `save` to preserve it across reloads | Confused in-memory state with database state | Recompute/re-attach the value or make it a persisted field if business rules require it. |
| Mistakenly imported `jakarta.persistence.Transient` | Used annotation out of JPA habit | Switch to `org.springframework.data.annotation.Transient` when working with Spring Data JDBC. |
| Used only `@JsonIgnore` to keep a field out of SQL | JSON serialization is independent of Spring Data persistence | Choose the right annotation for each boundary. |
| Persistence constructor requires a transient parameter | No mapped data exists to bind the parameter | Bind only persisted properties; initialize or compute temporary data afterward. |
| Marked a child entity collection with `@Transient` | Excluded an owned part that needed to be saved from the aggregate | Map real collections with the appropriate relational mechanism. |
| Used `@Transient` for data needed in SQL queries | No column backs the property | Persist the value, compute it in SQL, or use an appropriate projection. |
| Used `@Transient` for a database-read-only column | The annotation excludes reads as well as writes | Consider read-only mapping or query projections. |
| Treated `@Transient` as a security mechanism | The annotation only governs persistence mapping | Design logging, API, lifetime, and sensitive-data storage policies separately. |
| Put `@Transient` on ID or version to “hide” them | Breaks persistence identity and optimistic locking | Keep `@Id`/`@Version` mapped; hide them from APIs via DTOs/serialization when needed. |

### Why Shouldn't You Put `@Transient` on `@Id` or `@Version`?

`@Id` and `@Version` play vital roles in identifying entities, detecting new vs. existing state, and controlling concurrent updates. Excluding these properties from persistence mapping deprives the repository of metadata required by the underlying persistence mechanics. To omit ID/version from JSON, use a DTO or serialization configuration—**do not exclude them from JDBC mapping**.

## 12. Practice Scenarios

### Scenario A — Total Price Preview

The application lets staff enter quantities and unit prices, then displays `estimatedTotal` before confirming the order. Once confirmed, `finalTotal` carries business significance and must be persisted.

**How to distinguish:** `estimatedTotal` can be dynamically computed or transient in a preview model; `finalTotal` belongs to the order's durable state. Do not mark `finalTotal` as `@Transient` just because it can be calculated from order lines.

### Scenario B — Field for JSON Formatting

An entity has `name` and `price`. The API needs an extra `formattedPrice` for the frontend while the database only stores the raw numeric amount.

**How to design:** build a response DTO with `formattedPrice`, or compute it via a getter. If you truly need to cache that label on the entity, mark the cached field `@Transient`; keep in mind `@Transient` alone does not control what JSON outputs.

### Scenario C — “Disappearing” Transient Field

A service executes:

~~~java
Product product = repository.findById(id).orElseThrow();
product.setAdminNote("Need to review description");
repository.save(product);

Product anotherLoad = repository.findById(id).orElseThrow();
System.out.println(anotherLoad.getAdminNote());
~~~

**Expected result with the class from Section 3:** prints `null`. The note lived only in the Java object instance it was assigned to; it was never saved to the table, and a fresh load cannot restore it.

### Scenario D — Property Without a Column Yet

The development team adds `externalReference` to an entity. This value is a document code the business must keep permanently, but the table does not have the column yet. A developer suggests adding `@Transient` to avoid runtime errors.

**How to handle:** this is business data that must be persisted. Design the column and corresponding migration, update the mapping, and then deploy. Adding `@Transient` would silently drop the persistence behavior required by the business.

## 13. Checklist When Designing Mapping

When evaluating a property in Spring Data JDBC, ask in order:

1. **Does this value need to survive after the application stops or after the object is reloaded?** If yes, design proper persistence.
2. **Is the value only for a single calculation, display, or temporary processing step?** Compute it on demand, use a DTO, or mark it `@Transient` if it sits as a field on the entity.
3. **Does the value need to be queried, filtered, or sorted in SQL?** If yes, it must have a database source or an explicit SQL expression/query projection.
4. **Does the value participate in the persistence constructor?** If excluded from mapping by `@Transient`, do not require the framework to populate it from a nonexistent column.
5. **Could the value leak via JSON, logs, or other services?** `@Transient` does not control those channels; handle each layer's responsibilities separately.

**Core principle:** Spring Data's `@Transient` lets an entity hold in-memory information **without turning that information into state saved and loaded by the repository**. Use it when omitting persistence is an intentional modeling decision, while drawing a clear line from durable business data.
