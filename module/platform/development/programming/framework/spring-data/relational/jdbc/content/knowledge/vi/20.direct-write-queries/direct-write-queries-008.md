# Thiết kế xóa mềm bằng SQL tùy chỉnh và điều kiện đọc nhất quán

Xóa mềm (soft delete) đánh dấu một bản ghi là đã xóa nhưng vẫn giữ hàng dữ liệu trong database. Cách làm này hữu ích khi cần khôi phục dữ liệu, lưu dấu vết kiểm toán hoặc giữ các tham chiếu lịch sử. Với Spring Data JDBC, xóa mềm thường được triển khai bằng câu SQL `UPDATE` tùy chỉnh thay cho thao tác xóa vật lý.

Điểm khó nhất không nằm ở câu lệnh cập nhật cờ xóa. Nó nằm ở việc bảo đảm **mọi truy vấn đọc đều áp dụng cùng một điều kiện loại bản ghi đã xóa**. Nếu một màn hình dùng `deleted_at IS NULL` nhưng một báo cáo, truy vấn đếm hoặc repository method khác quên điều kiện này, dữ liệu đã xóa vẫn có thể xuất hiện trong ứng dụng.

Bài này dùng ví dụ `Customer` để trình bày schema, câu SQL xóa/khôi phục, thiết kế repository, quy tắc đọc nhất quán, ảnh hưởng đến quan hệ và index, cùng cách kiểm thử.

## 1. Xóa vật lý và xóa mềm

Xóa vật lý loại bỏ hàng khỏi bảng:

```sql
DELETE FROM customer
WHERE id = :id;
```

Xóa mềm giữ hàng và cập nhật trạng thái:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NULL;
```

Quy ước trong ví dụ này:

- `deleted_at IS NULL`: bản ghi đang hoạt động.
- `deleted_at IS NOT NULL`: bản ghi đã bị xóa mềm.
- Thời điểm được ghi nhận khi thao tác xóa diễn ra.

| Tiêu chí | Xóa vật lý | Xóa mềm |
| --- | --- | --- |
| Hàng còn trong bảng | Không | Có |
| Có thể khôi phục trực tiếp | Không, cần backup hoặc bản lưu khác | Có thể đặt lại trạng thái |
| Foreign key | Có thể kích hoạt `ON DELETE` | Không kích hoạt vì hàng vẫn tồn tại |
| Truy vấn đọc | Không thấy hàng đã xóa | Phải chủ động lọc |
| Kiểm toán | Cần cơ chế riêng nếu cần lịch sử | Có thể giữ thời điểm/người xóa, nhưng audit đầy đủ vẫn cần thiết kế riêng |

Xóa mềm không phải tính năng tự động khiến Spring Data JDBC ẩn bản ghi. Nếu repository vẫn chạy SELECT không có điều kiện, hàng đã đánh dấu xóa vẫn được đọc như bình thường.

## 2. Chọn mô hình trạng thái xóa

Có hai cách biểu diễn phổ biến.

### Dùng cột thời điểm deleted_at

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    deleted_at TIMESTAMP NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Ưu điểm là một cột thể hiện cả trạng thái và thời điểm. Điều kiện đọc dễ thống nhất: `deleted_at IS NULL`.

### Dùng cờ boolean

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    deleted BOOLEAN NOT NULL DEFAULT FALSE
);
```

Cách này đơn giản nếu chỉ cần trạng thái, nhưng không lưu thời điểm xóa. Nếu cần thời điểm và người thực hiện, có thể thêm `deleted_at` và `deleted_by`.

Trong bài này, các ví dụ dùng `deleted_at`. Chọn một quy ước duy nhất cho mỗi bảng và áp dụng nhất quán trong schema, domain và query.

## 3. Ánh xạ trạng thái xóa vào aggregate

Một entity đơn giản:

```java
package com.example.customer.domain;

import java.time.LocalDateTime;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
    @Id Long id,
    String email,
    String displayName,
    LocalDateTime deletedAt,
    LocalDateTime createdAt
) {
    public boolean isDeleted() {
        return deletedAt != null;
    }

    public Customer markDeleted(LocalDateTime deletedTime) {
        if (deletedAt != null) {
            return this;
        }
        return new Customer(
            id, email, displayName, deletedTime, createdAt
        );
    }

    public Customer restore() {
        if (deletedAt == null) {
            return this;
        }
        return new Customer(
            id, email, displayName, null, createdAt
        );
    }
}
```

Các method domain chỉ tạo trạng thái object mới. Việc cập nhật database vẫn do repository/service thực hiện. Nếu thao tác xóa cần xử lý concurrency hoặc audit, câu SQL có điều kiện và transaction vẫn là phần quan trọng.

Không để controller tự gán `deletedAt` mà bỏ qua quyền truy cập và quy tắc nghiệp vụ.

## 4. Xóa mềm bằng SQL tùy chỉnh

Câu lệnh xóa mềm thường là một UPDATE có điều kiện:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NULL;
```

Điều kiện `AND deleted_at IS NULL` có ý nghĩa:

- Chỉ xóa bản ghi đang hoạt động.
- Gọi lặp lại không thay đổi thời điểm xóa ban đầu.
- Số hàng bị cập nhật cho biết thao tác có chuyển trạng thái hay không.

Custom repository dùng `JdbcTemplate`:

```java
package com.example.customer.repository;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class CustomerWriteRepository {

    private final JdbcTemplate jdbc;

    public CustomerWriteRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public int softDelete(long customerId) {
        return jdbc.update("""
            UPDATE customer
            SET deleted_at = CURRENT_TIMESTAMP
            WHERE id = ?
              AND deleted_at IS NULL
            """, customerId);
    }
}
```

Giá trị `customerId` được bind qua JDBC. Tên bảng, cột và cấu trúc SQL là literal do ứng dụng định nghĩa.

Giá trị `int` trả về là số hàng được cập nhật:

- `1`: bản ghi tồn tại và vừa chuyển sang trạng thái đã xóa.
- `0`: không có hàng phù hợp; có thể ID không tồn tại hoặc bản ghi đã bị xóa trước đó.

Nếu API cần phân biệt `not found` và `already deleted`, service có thể đọc trạng thái hoặc dùng câu SQL/returning phù hợp với database. Không diễn giải mọi kết quả 0 là “không tồn tại” nếu chưa kiểm tra.
## 5. Không dùng deleteById mặc định cho thao tác xóa mềm

Phương thức deleteById của CrudRepository thực hiện xóa theo hợp đồng repository. Spring Data JDBC không tự chuyển nó thành UPDATE deleted_at. Vì vậy, nếu service gọi deleteById, hàng có thể bị xóa vật lý ngoài ý muốn.

Có thể thu hẹp API repository bằng marker Repository và chỉ khai báo các thao tác được phép:

```java
public interface ActiveCustomerRepository
        extends Repository<Customer, Long> {

    Customer save(Customer customer);

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNull();
}
```

Repository write riêng cung cấp softDelete bằng JdbcTemplate. Cách này tránh kế thừa deleteById/deleteAll cho luồng nghiệp vụ thông thường.

## 6. Điều kiện đọc nhất quán

Mọi truy vấn chỉ dành cho bản ghi đang hoạt động phải có predicate:

```sql
deleted_at IS NULL
```

Điều kiện này phải được áp dụng cho tìm theo ID, tìm kiếm, danh sách, count, exists, join, phân trang, báo cáo, export, batch job và custom SQL. Một màn hình lọc đúng không bảo vệ những đường đọc khác.
## 7. Đặt điều kiện active trong derived query

Nếu aggregate có property `deletedAt`, có thể khai báo method suy diễn:

```java
public interface ActiveCustomerRepository
        extends Repository<Customer, Long> {

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNull();

    Optional<Customer> findByEmailAndDeletedAtIsNull(String email);

    boolean existsByEmailAndDeletedAtIsNull(String email);

    long countByDeletedAtIsNull();
}
```

Các method trên thể hiện điều kiện active trong tên. Về ý nghĩa SQL:

```sql
SELECT ...
FROM customer
WHERE id = ?
  AND deleted_at IS NULL;
```

Method kế thừa như `findById(id)` hoặc `findAll()` không tự được bổ sung điều kiện `deleted_at IS NULL`. Nếu vẫn dùng `CrudRepository`, các method CRUD đọc mặc định có thể trả cả hàng đã xóa. Cần quyết định rõ method nào có semantics active-only và tránh gọi method không có filter từ nghiệp vụ thông thường.

## 8. Đọc bằng @Query hoặc custom repository

Với truy vấn phức tạp, viết điều kiện active trực tiếp trong SQL:

```java
public interface CustomerQueryRepository
        extends Repository<Customer, Long> {

    @Query("""
        SELECT id, email, display_name, deleted_at, created_at
        FROM customer
        WHERE deleted_at IS NULL
          AND email = :email
        """)
    Optional<Customer> findActiveByEmail(String email);
}
```

Tên tham số `:email` bind giá trị. Điều kiện `deleted_at IS NULL` được viết rõ trong SQL.

Với custom repository, có thể tạo phương thức đọc dùng chung:

```java
public List<CustomerSummary> findActiveCustomers(String namePart) {
    return jdbc.query("""
        SELECT id, email, display_name
        FROM customer
        WHERE deleted_at IS NULL
          AND display_name LIKE ?
        ORDER BY display_name, id
        """,
        summaryMapper,
        "%" + namePart + "%"
    );
}
```

Giá trị tìm kiếm vẫn được bind. Nếu muốn coi ký tự phần trăm và gạch dưới trong input là ký tự literal, cần escape wildcard theo semantics LIKE; đây là vấn đề khác với điều kiện xóa mềm.

Với custom SQL, hãy đặt tên method thể hiện rõ Active hoặc tổ chức class/query riêng cho dữ liệu active. Điều này giúp người đọc nhận ra điều kiện lọc là một phần bắt buộc.

## 9. Điều kiện xóa mềm trong JOIN

Giả sử đơn hàng tham chiếu khách hàng. Query lấy đơn cùng thông tin khách:

```sql
SELECT o.id,
       o.status,
       c.email,
       c.display_name
FROM purchase_order o
JOIN customer c ON c.id = o.customer_id
WHERE o.deleted_at IS NULL
  AND c.deleted_at IS NULL;
```

Cần xác định rõ nghiệp vụ muốn lọc những gì:

- `o.deleted_at IS NULL`: chỉ lấy đơn đang hoạt động.
- `c.deleted_at IS NULL`: chỉ hiển thị đơn có khách hàng đang hoạt động.

Có hệ thống vẫn cần hiển thị đơn lịch sử của khách đã xóa (ví dụ hóa đơn cũ). Khi đó không nhất thiết lọc khách ở mọi truy vấn; có thể chỉ lọc đơn active và giữ snapshot tên/email tại thời điểm mua. Điều kiện đọc phải theo ngữ nghĩa nghiệp vụ.

Với `LEFT JOIN`, vị trí điều kiện cũng quan trọng:

```sql
SELECT o.id, c.display_name
FROM purchase_order o
LEFT JOIN customer c
  ON c.id = o.customer_id
 AND c.deleted_at IS NULL
WHERE o.deleted_at IS NULL;
```

Đặt `c.deleted_at IS NULL` trong `ON` giữ đơn hàng ở kết quả dù khách hàng tương ứng đã xóa; các cột của customer sẽ null. Nếu đặt điều kiện đó trong `WHERE`, hành vi outer join có thể thay đổi do logic null của SQL. Chọn vị trí theo yêu cầu hiển thị.

## 10. Đếm, phân trang và export cũng phải lọc active

Một lỗi phổ biến là danh sách đã lọc nhưng count query thì chưa.

Danh sách:

```sql
SELECT id, email, display_name
FROM customer
WHERE deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
```

Count tương ứng:

```sql
SELECT COUNT(*)
FROM customer
WHERE deleted_at IS NULL;
```

Nếu count không có điều kiện active, giao diện có thể báo tổng số bản ghi lớn hơn số bản ghi thực tế có thể xem. Page count, trang cuối và thông tin tổng số cũng sai.

Tương tự, báo cáo/export cần cùng semantics:

```sql
SELECT status, COUNT(*) AS order_count
FROM purchase_order
WHERE deleted_at IS NULL
GROUP BY status;
```

Đừng chỉ kiểm tra endpoint danh sách. Hãy tìm mọi query đọc bảng trong repository, custom adapter, job, report và export.
## 15. Transaction và concurrency khi xóa mềm

Một thao tác xóa mềm có thể gồm:

1. Kiểm tra người dùng có quyền xóa bản ghi.
2. Xác nhận bản ghi tồn tại và đang active.
3. Cập nhật `deleted_at`.
4. Cập nhật child rows nếu domain yêu cầu cascade mềm.
5. Ghi audit record hoặc outbox event.
6. Commit transaction.

Nếu các thao tác cùng database và cần thành công/thất bại cùng nhau, đặt ranh giới transaction ở service:

```java
@Service
public class CustomerService {

    private final CustomerWriteRepository writes;

    public CustomerService(CustomerWriteRepository writes) {
        this.writes = writes;
    }

    @Transactional
    public void delete(long customerId) {
        int changed = writes.softDelete(customerId);

        if (changed == 0) {
            throw new CustomerNotActiveException(customerId);
        }

        // Ghi audit/outbox trong cùng transaction nếu cần.
    }
}
```

Điều kiện `WHERE deleted_at IS NULL` giúp thao tác có tính điều kiện: chỉ một request đầu tiên chuyển trạng thái active sang deleted; request sau nhận kết quả 0. Nếu cần phân biệt không tồn tại và đã xóa, service có thể truy vấn thêm hoặc dùng database-specific RETURNING.

Nếu có optimistic locking, có thể thêm cột `version` và đưa version mong đợi vào điều kiện cập nhật:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP,
    version = version + 1
WHERE id = :id
  AND deleted_at IS NULL
  AND version = :expectedVersion;
```

Số hàng cập nhật bằng 0 khi ID không phù hợp, đã xóa hoặc version đã đổi. Service cần phân loại lỗi theo hợp đồng nghiệp vụ. Nếu dùng custom SQL, ứng dụng tự chịu trách nhiệm tăng version và kiểm tra row count.

Transaction không tự bảo vệ khỏi mọi race condition. Điều kiện trong UPDATE, constraint database và chính sách concurrency phải phối hợp với nhau.

## 16. Tổ chức code để mọi đường đọc dùng cùng quy tắc

Có thể giảm khả năng quên filter bằng cách:

- Dùng tên method rõ như `findActiveById`, `findAllActive`, `countActive`.
- Đưa query active vào một repository/adapter chuyên trách.
- Không expose `findAll` hoặc `deleteById` vật lý cho luồng nghiệp vụ nếu không cần.
- Kiểm tra mọi query method, custom SQL, report, export và job.
- Tạo integration test xác nhận hàng deleted không xuất hiện ở mọi endpoint đọc active.

Một repository marker có thể định nghĩa rõ các thao tác được phép:

```java
public interface CustomerRepository
        extends Repository<Customer, Long> {

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNullOrderByCreatedAtDescIdDesc();

    Optional<Customer> findByEmailAndDeletedAtIsNull(String email);

    long countByDeletedAtIsNull();

    Customer save(Customer customer);
}
```

Với query khác, đặt tên method chứa `Active` hoặc viết điều kiện SQL rõ ràng. Không nên đặt tên method chung chung như `search` mà che giấu việc có/không lọc deleted.

Nếu hệ thống có nhu cầu quản trị xem cả bản ghi deleted, hãy tạo đường đọc riêng có tên rõ như `findIncludingDeletedById`, bảo vệ bằng quyền quản trị và tránh tái sử dụng nhầm trong API thông thường.

## 17. Những lỗi thường gặp

| Lỗi | Hậu quả | Cách xử lý |
| --- | --- | --- |
| Gọi `CrudRepository.deleteById` với ý định soft delete | Hàng bị xóa vật lý theo cơ chế repository. | Dùng custom `UPDATE`. |
| Chỉ lọc deleted ở một màn hình | Query khác vẫn trả bản ghi đã xóa. | Chuẩn hóa điều kiện active trên mọi đường đọc. |
| Dùng `findById` mặc định | Có thể tìm thấy cả bản ghi đã xóa. | Dùng `findByIdAndDeletedAtIsNull`. |
| Count query thiếu điều kiện | Tổng số/trang cuối không khớp danh sách. | Áp dụng cùng predicate cho SELECT và COUNT. |
| Quên filter trong JOIN | Dữ liệu liên quan đã xóa xuất hiện hoặc làm mất hàng outer join. | Xác định semantics và đặt predicate đúng trong ON/WHERE. |
| Nghĩ FK cascade sẽ soft delete child | Child rows vẫn tồn tại khi root được UPDATE. | Viết cascade mềm tường minh nếu domain yêu cầu. |
| Unique email toàn bảng ngăn tái sử dụng | Không thể đăng ký lại email của customer đã xóa. | Quyết định uniqueness active hay toàn bộ lịch sử. |
| Restore không kiểm tra constraint | Khôi phục có thể thất bại do trùng dữ liệu active. | Xử lý xung đột nghiệp vụ khi restore. |
| Quên batch/report/export | Bản ghi deleted vẫn xuất hiện trong file hoặc thống kê. | Rà soát mọi consumer đọc dữ liệu. |
| Cho client truyền tên cột/SQL fragment | Có nguy cơ SQL injection hoặc query ngoài hợp đồng. | Bind value và allowlist cấu trúc động. |

## 18. Kiểm thử xóa mềm và điều kiện đọc

Integration test nên xác nhận cả trạng thái database và hành vi repository.

Một kịch bản cơ bản:

1. Tạo customer active.
2. Đọc bằng `findByIdAndDeletedAtIsNull` và xác nhận tìm thấy.
3. Gọi service xóa mềm.
4. Kiểm tra hàng vẫn còn trong bảng và `deleted_at` khác null.
5. Đọc bằng các method active và xác nhận không còn thấy.
6. Kiểm tra count/list/search đều bỏ qua hàng deleted.
7. Gọi xóa lần hai và xác nhận chính sách idempotent/row count.
8. Restore, sau đó xác nhận truy vấn active tìm thấy lại.
9. Kiểm tra unique constraint khi có bản ghi active dùng cùng email.
10. Kiểm tra query join, export và count query nếu hệ thống có các đường đọc đó.

Ví dụ test theo ý nghĩa:

```java
@Test
void softDeletedCustomerIsExcludedFromActiveQueries() {
    Customer saved = customers.save(
        new Customer(null, "a@example.test", "An", null, now)
    );

    assertThat(customers.findByIdAndDeletedAtIsNull(saved.id()))
        .isPresent();

    assertThat(writes.softDelete(saved.id())).isEqualTo(1);

    assertThat(customers.findByIdAndDeletedAtIsNull(saved.id()))
        .isEmpty();

    assertThat(jdbc.queryForObject(
        "SELECT COUNT(*) FROM customer WHERE id = ?",
        Integer.class,
        saved.id()
    )).isEqualTo(1);

    assertThat(jdbc.queryForObject(
        "SELECT deleted_at IS NOT NULL FROM customer WHERE id = ?",
        Boolean.class,
        saved.id()
    )).isTrue();
}
```

Đây là ví dụ minh họa; tên repository, fixture, kiểu thời gian và cú pháp kiểm tra boolean phải phù hợp database/test setup của dự án.

Cần có test riêng cho các query custom vì một method active đúng không chứng minh tất cả query đều đúng. Tạo một bản ghi active và một bản ghi deleted, chạy từng đường đọc rồi xác nhận chỉ bản ghi active xuất hiện.

## 19. Quy trình triển khai tính năng soft delete

Khi bổ sung xóa mềm vào một bảng đang chạy, thực hiện theo thứ tự:

1. Xác định semantics: bản ghi nào được xem là active, có cho restore không, có tái sử dụng unique key không.
2. Thêm cột `deleted_at` nullable bằng migration. Hàng cũ có `NULL` nên được xem là active.
3. Ánh xạ property vào aggregate và cập nhật các repository query active.
4. Tạo custom SQL `UPDATE` cho soft delete/restore.
5. Bảo vệ luồng ghi để không gọi hard delete mặc định.
6. Rà soát SELECT, JOIN, COUNT, pagination, report, export và job.
7. Điều chỉnh unique constraint/index theo semantics active.
8. Viết integration test trên database/dialect đích.
9. Triển khai code và migration theo thứ tự tương thích; kiểm tra log và row count sau phát hành.

Không cần backfill `deleted_at` cho các hàng hiện có nếu `NULL` đã được quy ước là active. Nếu dùng boolean, migration cần đặt default `FALSE` cho dữ liệu hiện có theo khả năng của database.

## 20. Câu hỏi tự kiểm tra

- Xóa mềm khác xóa vật lý ở điểm nào?
- Vì sao `CrudRepository.deleteById` không tự chuyển thành cập nhật `deleted_at`?
- `deleted_at IS NULL` thể hiện trạng thái gì?
- Vì sao mọi query đọc active phải có cùng điều kiện?
- Tại sao count query và export cũng cần lọc bản ghi đã xóa?
- Trong `LEFT JOIN`, khi nào điều kiện deleted của bảng bên phải nên đặt trong `ON`?
- Xóa mềm root có tự kích hoạt `ON DELETE CASCADE` không?
- Khi nào cần cascade mềm xuống child rows?
- Partial unique index giúp gì khi email chỉ cần duy nhất giữa bản ghi active?
- Restore có thể gặp xung đột nào?
- Làm thế nào hạn chế việc service gọi nhầm hard delete?
- Những integration test nào chứng minh điều kiện đọc được áp dụng nhất quán?

Thiết kế xóa mềm hoàn chỉnh gồm hai nửa: **ghi trạng thái đã xóa bằng SQL có điều kiện** và **đọc dữ liệu active bằng predicate nhất quán**. Hãy định nghĩa rõ trạng thái trong schema, tránh để luồng nghiệp vụ gọi hard delete mặc định, áp dụng filter cho cả truy vấn danh sách/đếm/join/export và kiểm thử mọi đường đọc. Khi đó dữ liệu được giữ để khôi phục hoặc kiểm toán mà không vô tình xuất hiện trong các luồng nghiệp vụ thông thường.
## 11. Xóa mềm và các aggregate con

Giả sử `PurchaseOrder` có collection `OrderLine` trong bảng `order_line`. Khi xóa mềm root:

```sql
UPDATE purchase_order
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :orderId
  AND deleted_at IS NULL;
```

Các hàng `order_line` vẫn còn vì không có thao tác xóa vật lý root và foreign key `ON DELETE CASCADE` không được kích hoạt bởi một UPDATE.

Đây thường là hành vi mong muốn nếu child rows thuộc vòng đời root và cần giữ lại để khôi phục hoặc kiểm toán. Khi đọc aggregate active, ứng dụng chỉ truy vấn root có `deleted_at IS NULL`; child rows được đọc theo aggregate đó.

Nếu child table có thể được truy vấn độc lập, hoặc bản thân child có trạng thái xóa riêng, phải thiết kế thêm điều kiện tương ứng. Không mặc định rằng ẩn root sẽ tự ẩn mọi query trực tiếp trên bảng con.

| Chính sách | Cách thực hiện | Khi phù hợp |
| --- | --- | --- |
| Root quyết định khả năng hiển thị | Giữ child rows; chỉ truy cập child qua root active. | Child chỉ có ý nghĩa trong aggregate root. |
| Root và child có trạng thái riêng | Thêm `deleted_at` vào child và lọc cả hai khi cần. | Child có thể bị xóa/khôi phục độc lập. |
| Xóa mềm theo cascade nghiệp vụ | Service cập nhật root và child trong cùng transaction. | Domain yêu cầu mọi child chuyển trạng thái cùng root. |

Không dùng cascade vật lý để thay thế cascade mềm. Nếu nghiệp vụ yêu cầu cascade mềm, hãy viết các câu UPDATE tường minh và đặt trong một transaction.

## 12. Khôi phục bản ghi

Khôi phục thường đặt `deleted_at` về null:

```sql
UPDATE customer
SET deleted_at = NULL
WHERE id = :id
  AND deleted_at IS NOT NULL;
```

Custom repository:

```java
public int restore(long customerId) {
    return jdbc.update("""
        UPDATE customer
        SET deleted_at = NULL
        WHERE id = ?
          AND deleted_at IS NOT NULL
        """, customerId);
}
```

Giống soft delete, số hàng cập nhật cho biết trạng thái có được thay đổi không. Nên xác định rõ ai có quyền restore và liệu có giới hạn thời gian/điều kiện khôi phục hay không.

Khôi phục có thể gặp xung đột nghiệp vụ. Ví dụ email phải duy nhất giữa các customer active; trong lúc một customer bị xóa, người khác đã đăng ký cùng email. Khi restore, unique constraint có thể từ chối thao tác. Đây là lỗi domain cần xử lý rõ ràng, không nên bỏ qua constraint để ép restore.

Nếu soft delete theo cascade nhiều bảng, restore cũng phải tuân theo quy tắc nhất quán: khôi phục root có khôi phục toàn bộ child đã xóa cùng đợt không? Cần phân biệt child vốn đã bị xóa độc lập trước đó với child bị xóa do cascade mềm.

## 13. Unique constraint và dữ liệu active

Nếu email phải duy nhất giữa các khách hàng đang hoạt động, ràng buộc:

```sql
UNIQUE (email)
```

vẫn ngăn tạo customer mới dùng email của một customer đã soft delete, vì hàng cũ vẫn còn.

Trên PostgreSQL, có thể dùng partial unique index:

```sql
CREATE UNIQUE INDEX uq_customer_active_email
ON customer (email)
WHERE deleted_at IS NULL;
```

Index chỉ áp dụng cho hàng active. Customer đã xóa không còn chiếm email trong phạm vi ràng buộc đó.

Partial index là tính năng theo database; không có cú pháp portable tương đương hoàn toàn trên mọi hệ quản trị. Với database khác, có thể dùng generated/computed column, cột unique key có điều kiện hoặc thiết kế quy tắc tái sử dụng email khác. Cần kiểm tra cú pháp và semantics trên engine thực tế.

Nếu không cần cho phép tái sử dụng email sau khi xóa, giữ unique constraint toàn bảng có thể là lựa chọn đúng. Đây là quy tắc nghiệp vụ, không phải hệ quả bắt buộc của soft delete.

## 14. Index cho truy vấn active

Nếu phần lớn truy vấn chỉ lấy hàng chưa xóa, điều kiện `deleted_at IS NULL` có thể ảnh hưởng đến thiết kế index.

Ví dụ query thường dùng:

```sql
SELECT id, email, display_name
FROM customer
WHERE deleted_at IS NULL
  AND email = :email;
```

Một index ghép có thể phù hợp:

```sql
CREATE INDEX idx_customer_deleted_email
ON customer (deleted_at, email);
```

Với PostgreSQL, nếu active rows là tập dữ liệu chính, có thể cân nhắc partial index:

```sql
CREATE INDEX idx_customer_active_email
ON customer (email)
WHERE deleted_at IS NULL;
```

Không thêm index theo ví dụ một cách máy móc. Nếu `deleted_at` có độ chọn lọc thấp, index chỉ trên cột đó có thể ít hữu ích. Hãy kiểm tra execution plan, số lượng hàng active/deleted, tần suất query và chi phí ghi.

Với danh sách active theo ngày tạo:

```sql
CREATE INDEX idx_customer_active_created_id
ON customer (created_at DESC, id DESC)
WHERE deleted_at IS NULL;
```

Đây là ví dụ PostgreSQL partial index. Dialect khác có thể cần index ghép hoặc chiến lược khác.
