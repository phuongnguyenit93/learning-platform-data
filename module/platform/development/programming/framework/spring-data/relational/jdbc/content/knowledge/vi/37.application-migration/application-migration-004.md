# Thiết kế lại quan hệ hai chiều, cascade và lazy loading trong Spring Data JDBC

## 1. Bắt đầu từ khác biệt giữa JPA và Spring Data JDBC

Khi chuyển một ứng dụng từ Spring Data JPA sang Spring Data JDBC, phần khó thường không nằm ở việc đổi repository interface. Khó khăn lớn hơn là cách mô hình hóa quan hệ giữa các entity.

JPA cho phép mô hình object graph với các quan hệ như @OneToMany, @ManyToOne, @OneToOne, @ManyToMany. Ứng dụng có thể cấu hình cascade, orphan removal và fetch type LAZY/EAGER. Persistence context theo dõi entity và có thể tải dữ liệu liên quan khi ứng dụng truy cập property.

Spring Data JDBC sử dụng mô hình đơn giản hơn:

- Mỗi aggregate có đúng một aggregate root.
- Repository thao tác với aggregate root.
- Các entity nằm bên trong aggregate được tham chiếu theo một hướng từ root xuống.
- Quan hệ giữa các aggregate được biểu diễn bằng ID hoặc AggregateReference.
- Không có persistence context, dirty tracking hay lazy-loading proxy.
- Khi tải aggregate, Spring Data JDBC dựng aggregate hoàn chỉnh theo mapping.
- Khi lưu aggregate hiện có, các entity được tham chiếu trong aggregate hiện được xóa và tạo lại theo trạng thái object được gửi vào.

Do đó, không nên chuyển nguyên trạng annotation JPA sang Spring Data JDBC rồi kỳ vọng semantics giống nhau.

## 2. Xác định aggregate boundary trước khi thiết kế quan hệ

Aggregate là nhóm entity phải duy trì tính nhất quán như một đơn vị trong một lần thay đổi nghiệp vụ. Aggregate root là điểm truy cập và điều phối thay đổi của nhóm đó.

Ví dụ một đơn hàng:

~~~text
Order (aggregate root)
 ├── OrderLine
 ├── OrderLine
 └── ShippingAddress
~~~

Nếu một Order được xác nhận, các dòng hàng và địa chỉ giao hàng của nó phải nhất quán với Order. Vì vậy, chúng có thể nằm trong cùng aggregate.

Ngược lại, Customer có thể được nhiều Order tham chiếu:

~~~text
Customer (aggregate root)       Order (aggregate root)
          1                  N
          └───────────────────┘
                 customer_id
~~~

Customer không thuộc quyền sở hữu vòng đời của một Order. Xóa một Order không được xóa Customer. Hai entity này nên là hai aggregate riêng.

Một số câu hỏi giúp xác định boundary:

- Entity có cần được thay đổi độc lập qua repository riêng không?
- Có nhiều aggregate khác cùng tham chiếu entity này không?
- Khi xóa root, entity đó có nên bị xóa theo không?
- Các thay đổi có cần atomic trong cùng một transaction không?
- Có cần tải entity đó mỗi khi tải root không?
- Có thể duy trì tính nhất quán thông qua một use case/service thay vì một object graph không?

Đừng xác định aggregate chỉ dựa trên việc các bảng có foreign key. Foreign key là quan hệ ở database; aggregate boundary là quyết định về quyền sở hữu và tính nhất quán của domain.

## 3. Quan hệ bên trong aggregate: tham chiếu một chiều

Với entity con thuộc aggregate, object reference đi từ root tới child. Ví dụ:

~~~java
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    private String orderNumber;

    private String status;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // Constructor, getters và domain methods.
}
~~~

Entity con:

~~~java
@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    private String sku;

    private int quantity;

    // Constructor, getters và domain methods.
}
~~~

Spring Data JDBC ánh xạ collection thành quan hệ một-nhiều. Cột order_id nằm trong bảng order_lines để tham chiếu tới ID của Order.

Không cần khai báo một property Order trong OrderLine chỉ để lưu quan hệ này. Spring Data JDBC quản lý back-reference ở mức relational mapping.

### 3.1. Dùng @MappedCollection để cấu hình foreign key

Có thể đặt tên cột foreign key và cột vị trí/key của collection:

~~~java
@MappedCollection(
        idColumn = "order_id",
        keyColumn = "line_position"
)
private List<OrderLine> lines;
~~~

Với List, Spring Data JDBC lưu thêm vị trí phần tử. Với Map, cột key lưu khóa của map. Với Set, không cần cột vị trí.

Ví dụ schema:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);
~~~

Tên cột thực tế phụ thuộc @MappedCollection và NamingStrategy. Hãy giữ mapping Java và schema migration nhất quán.

## 4. Khi child cần truy cập ngược aggregate root

Đôi khi một phương thức trên child cần biết thông tin của root. Ví dụ OrderLine cần tên đơn hàng để tạo mô tả.

Không cần lưu một object reference hai chiều có thể được persistence mapping theo cả hai hướng. Có hai cách thiết kế.

### 4.1. Truyền root vào method

Cách đơn giản nhất là truyền thông tin cần thiết khi gọi method:

~~~java
public class OrderLine {

    private String sku;
    private int quantity;

    public String descriptionFor(Order order) {
        return sku + " in order " + order.getOrderNumber();
    }
}
~~~

Root điều phối:

~~~java
public class Order {

    public String describeLines() {
        return lines.stream()
                .map(line -> line.descriptionFor(this))
                .collect(Collectors.joining(", "));
    }
}
~~~

Cách này giữ object graph một chiều. Child không cần biết hoặc giữ reference lâu dài tới parent.

### 4.2. Dùng transient back-reference cho domain behavior

Nếu nhiều method của child cần truy cập root, có thể giữ một back-reference chỉ tồn tại trong bộ nhớ. Đánh dấu property bằng annotation @Transient của Spring Data:

~~~java
import org.springframework.data.annotation.Transient;

public class OrderLine {

    private String sku;

    private int quantity;

    @Transient
    private Order order;

    void attachTo(Order order) {
        this.order = order;
    }

    public String description() {
        return sku + " in order " + order.getOrderNumber();
    }
}
~~~

Root gắn child khi thêm vào collection:

~~~java
public void addLine(OrderLine line) {
    lines.add(line);
    line.attachTo(this);
}
~~~

Khi Spring Data JDBC dựng aggregate từ database, root cũng cần gắn lại back-reference. Có thể thực hiện trong persistence constructor:

~~~java
import java.util.Collection;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private final Long id;

    private final String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private final List<OrderLine> lines = new ArrayList<>();

    @PersistenceCreator
    Order(
            Long id,
            String orderNumber,
            Collection<OrderLine> lines
    ) {
        this.id = id;
        this.orderNumber = orderNumber;
        lines.forEach(this::addLine);
    }

    public void addLine(OrderLine line) {
        lines.add(line);
        line.attachTo(this);
    }
}
~~~

Ví dụ này minh họa ý tưởng; constructor và collection type cần khớp với entity thực tế. Property @Transient không được lấy từ database và không nên là tham số mà converter phải đọc trực tiếp trong persistence constructor. Root nhận collection đã mapping rồi gắn parent bằng domain method.

Dùng annotation @Transient của package org.springframework.data.annotation, không dùng annotation @Transient của JPA. Nếu quên đánh dấu transient, converter có thể cố mapping ngược parent thành một quan hệ khác và tạo vòng tham chiếu.

Một lựa chọn khác là dùng AfterConvertCallback để thiết lập transient back-reference sau khi aggregate được dựng. Callback chỉ nên bổ sung trạng thái trong bộ nhớ, không dùng nó để tạo một quan hệ persistence hai chiều.

## 5. Quan hệ giữa các aggregate: lưu ID thay vì object reference

Giả sử Order tham chiếu Customer. Customer có thể được nhiều Order dùng chung và có repository riêng.

Không nên khai báo Customer object trực tiếp như một property của Order rồi xem Customer là child của Order. Nếu làm vậy, Spring Data JDBC có thể coi Customer là thành phần thuộc aggregate Order và áp dụng vòng đời persistence của aggregate lên nó.

Thay vào đó, lưu ID:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;

    private String orderNumber;
}
~~~

Hoặc dùng AggregateReference để thể hiện rõ đây là reference tới aggregate khác:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.jdbc.core.mapping.AggregateReference;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private AggregateReference<Customer, Long> customer;

    private String orderNumber;
}
~~~

Tạo reference:

~~~java
Order order = new Order(
        AggregateReference.to(customerId),
        "ORD-2026-001"
);
~~~

Đọc Customer khi thật sự cần:

~~~java
Customer customer = customerRepository
        .findById(order.getCustomer().getId())
        .orElseThrow();
~~~

AggregateReference<T, ID> chứa ID của aggregate đích và cho biết kiểu aggregate được tham chiếu. Nó không tự tải Customer, không tạo lazy-loading proxy và không tự gọi repository.

### 5.1. Truy vấn theo hướng ngược lại

Nếu cần tìm các Order của một Customer, khai báo query ở OrderRepository:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long> {

    @Query("""
        SELECT *
        FROM orders
        WHERE customer_id = :customerId
        """)
    List<Order> findByCustomerId(Long customerId);
}
~~~

Tên customer_id phải khớp với schema và mapping thực tế. Nếu dùng naming strategy khác, hãy điều chỉnh SQL.

Có thể dùng query derivation với AggregateReference làm tham số trong các phiên bản Spring Data JDBC hỗ trợ:

~~~java
List<Order> findByCustomer(
        AggregateReference<Customer, Long> customer
);
~~~

Cách tiếp cận này làm rõ hướng truy vấn: Order tham chiếu Customer bằng ID, còn việc tìm ngược được thực hiện bằng repository query.

## 6. Thiết kế quan hệ nhiều-nhiều

JPA có thể biểu diễn @ManyToMany bằng một collection object ở cả hai phía. Spring Data JDBC không hỗ trợ một object graph nhiều-nhiều theo semantics đó.

Ví dụ Book và Author:

- Một Book có nhiều Author.
- Một Author có thể viết nhiều Book.
- Xóa Book không được xóa Author.
- Xóa Author không nên tự động xóa các Book còn lại.

Đây là hai aggregate độc lập. Bảng liên kết có thể được mô hình hóa thành các hàng liên kết thuộc một aggregate hoặc một aggregate riêng, tùy vòng đời nghiệp vụ.

Ví dụ Book sở hữu các association row:

~~~java
@Table("books")
public class Book {

    @Id
    private Long id;

    private String title;

    @MappedCollection(idColumn = "book_id")
    private Set<BookAuthor> authors = new HashSet<>();
}

@Table("book_authors")
public class BookAuthor {

    @Id
    private Long id;

    private Long authorId;
}
~~~

Schema:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL
);

CREATE TABLE authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE book_authors (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    book_id BIGINT NOT NULL,
    author_id BIGINT NOT NULL,
    CONSTRAINT fk_book_author_book
        FOREIGN KEY (book_id) REFERENCES books(id),
    CONSTRAINT fk_book_author_author
        FOREIGN KEY (author_id) REFERENCES authors(id),
    CONSTRAINT uk_book_author
        UNIQUE (book_id, author_id)
);
~~~

BookAuthor là thành phần của aggregate Book. Nó lưu authorId, không giữ Author object. Xóa Book sẽ xóa các association row thuộc Book, nhưng không xóa các Author.

Nếu association có dữ liệu nghiệp vụ riêng như role, thứ tự đóng góp hoặc ngày tham gia, có thể lưu các property đó trên BookAuthor.

Nếu quan hệ cần vòng đời độc lập, ví dụ association được phê duyệt, khóa hoặc quản lý bởi một quy trình riêng, có thể thiết kế association thành aggregate root riêng với ID tham chiếu Book và Author.

Không tạo collection Book trong Author chỉ để mô phỏng chiều ngược. Dùng repository query để tìm các Book có association tới Author.

## 7. Cascade trong Spring Data JDBC có nghĩa gì?

Spring Data JDBC không dùng các annotation cascade của JPA như:

- CascadeType.PERSIST
- CascadeType.MERGE
- CascadeType.REMOVE
- CascadeType.ALL
- orphanRemoval = true

Thay vào đó, vòng đời persistence được quyết định bởi aggregate boundary và object graph mà root tham chiếu.

### 7.1. Insert aggregate mới

Khi lưu một aggregate mới:

~~~java
Order order = new Order(
        "ORD-001",
        List.of(
                new OrderLine("SKU-A", 2),
                new OrderLine("SKU-B", 1)
        )
);

Order saved = orderRepository.save(order);
~~~

Spring Data JDBC insert aggregate root, sau đó insert các entity được tham chiếu trực tiếp hoặc gián tiếp trong aggregate.

### 7.2. Update aggregate hiện có

Theo implementation hiện tại, khi lưu aggregate đã tồn tại:

1. Các entity được tham chiếu trong aggregate bị xóa.
2. Aggregate root được update.
3. Các entity được tham chiếu được insert lại theo trạng thái object mới.

Spring Data JDBC không giữ snapshot trước đó của aggregate để dirty-track từng child. Vì vậy, ngay cả khi chỉ thay đổi một child, các referenced entities có thể bị xóa và tạo lại.

Điều này có thể gây thêm SQL và ảnh hưởng tới ID tự sinh của child. Không nên thiết kế một aggregate có các child row được nhiều aggregate khác tham chiếu trực tiếp.

Nếu child cần được cập nhật độc lập, có ID ổn định và có nhiều nơi tham chiếu, hãy cân nhắc tách nó thành aggregate riêng.

### 7.3. Xóa aggregate root

Khi xóa aggregate root bằng repository, Spring Data JDBC xóa aggregate cùng các entity thuộc aggregate đó.

~~~java
orderRepository.deleteById(orderId);
~~~

Các hàng con được quản lý như một phần của aggregate Order. Không cần thêm CascadeType.REMOVE để yêu cầu framework xóa chúng.

### 7.4. Xóa child khỏi collection

Giả sử một Order có ba OrderLine. Nếu ứng dụng loại một line khỏi collection rồi save aggregate, trạng thái persistence mới không còn line đó. Trong cơ chế save hiện tại, các referenced entities được xóa và tạo lại từ collection được gửi vào, nên line đã bị loại sẽ không được insert lại.

Đây là semantics gần với orphan removal ở kết quả cuối, nhưng cơ chế thực thi khác JPA. Spring Data JDBC không dùng dirty tracking để xác định chính xác một child vừa bị remove; nó đồng bộ trạng thái aggregate được truyền vào.

## 8. Phân biệt cascade nội bộ và quan hệ tới aggregate khác

| Thao tác | Entity con thuộc aggregate | Aggregate khác được tham chiếu bằng ID |
|---|---|---|
| Insert root | Insert các entity con | Chỉ ghi ID reference |
| Save root hiện có | Đồng bộ các entity con; implementation hiện tại xóa và tạo lại | Không tự save aggregate đích |
| Remove child khỏi collection | Child không còn được lưu | Không áp dụng |
| Delete root | Xóa aggregate members | Không tự xóa aggregate đích |
| Update aggregate đích | Thực hiện qua repository của aggregate đích | Không tự động cập nhật từ root đang tham chiếu |

Ví dụ Order tham chiếu Customer bằng AggregateReference. Khi xóa Order:

- Hàng Order bị xóa.
- OrderLine thuộc Order bị xóa.
- Hàng Customer vẫn tồn tại.

Nếu database có foreign key từ orders.customer_id tới customers.id, constraint đó tiếp tục bảo vệ tính hợp lệ của reference. Cấu hình ON DELETE RESTRICT/NO ACTION hoặc SET NULL/CASCADE là quyết định schema ở database, không phải cascade annotation của Spring Data JDBC.

Hãy chọn hành vi database phù hợp với domain. Đặc biệt, ON DELETE CASCADE trên foreign key tới aggregate khác có thể xóa nhiều dữ liệu hơn dự kiến nếu không được thiết kế rõ ràng.

## 9. Không có lazy loading trong Spring Data JDBC

Spring Data JDBC không cung cấp lazy-loading proxy như JPA. Khi tải aggregate, framework thực hiện SQL và dựng aggregate theo mapping. Sau khi repository method trả về, caller nhận entity đã được load theo contract của thao tác đó.

Ví dụ:

~~~java
Order order = orderRepository.findById(orderId)
        .orElseThrow();

List<OrderLine> lines = order.getLines();
~~~

Truy cập getLines() không kích hoạt một truy vấn lazy mới như một collection proxy của JPA. Collection được tải trong quá trình dựng aggregate.

Điều này có một số hệ quả:

- Không có LazyInitializationException do truy cập proxy sau khi session đóng.
- Không có persistence context để giữ entity và theo dõi thay đổi.
- Không thể dùng FetchType.LAZY để trì hoãn collection loading.
- Một aggregate lớn có thể tốn thời gian và bộ nhớ ngay lúc load.
- Nếu chỉ cần một phần dữ liệu, nên dùng query/read model riêng.

### 9.1. Single Query Loading không phải lazy loading

Từ Spring Data JDBC 3.2, Single Query Loading có thể tải nhiều aggregate cùng collection bằng một SQL statement trong những trường hợp được hỗ trợ.

Nó thay đổi cách thực hiện việc load, không thay đổi semantics thành lazy loading. Aggregate vẫn được dựng trước khi repository trả về.

Tính năng có giới hạn về nested collections, AggregateReference, embedded entities, database dialect và loại repository method. Hãy kiểm tra tài liệu của version đang dùng và xác nhận SQL thực tế.

### 9.2. Khi không muốn tải toàn bộ aggregate

Nếu một màn hình chỉ cần order number, status và tổng tiền, tải toàn bộ OrderLine có thể không cần thiết.

Có thể tạo read model:

~~~java
public record OrderSummary(
        Long id,
        String orderNumber,
        String status,
        BigDecimal totalAmount
) {}
~~~

Dùng custom repository query hoặc JdbcTemplate để lấy đúng dữ liệu cần thiết:

~~~sql
SELECT
    o.id,
    o.order_number,
    o.status,
    COALESCE(SUM(l.quantity * p.price), 0) AS total_amount
FROM orders o
LEFT JOIN order_lines l ON l.order_id = o.id
LEFT JOIN products p ON p.sku = l.sku
WHERE o.id = :orderId
GROUP BY o.id, o.order_number, o.status;
~~~

Read model phù hợp cho màn hình, báo cáo và truy vấn tổng hợp. Khi cần thực hiện thay đổi nghiệp vụ, vẫn dùng aggregate root và domain methods để bảo vệ invariant.

## 10. Chuyển đổi từng mẫu quan hệ từ JPA

### 10.1. @OneToMany với cascade ALL và orphanRemoval

JPA:

~~~java
@OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
)
private List<OrderLine> lines;
~~~

Spring Data JDBC:

~~~java
@MappedCollection(idColumn = "order_id")
private List<OrderLine> lines;
~~~

Không cần property Order trong OrderLine để mapping foreign key. Root là nơi sở hữu collection và điều khiển thêm/xóa child.

### 10.2. @ManyToOne(fetch = LAZY)

JPA:

~~~java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "customer_id")
private Customer customer;
~~~

Spring Data JDBC:

~~~java
@Column("customer_id")
private AggregateReference<Customer, Long> customer;
~~~

Khi cần Customer:

~~~java
Customer customer = customerRepository
        .findById(order.getCustomer().getId())
        .orElseThrow();
~~~

Đây là thao tác đọc tường minh. Không có proxy tự tải Customer khi gọi order.getCustomer().

### 10.3. @OneToOne

Nếu entity được tham chiếu thật sự thuộc cùng aggregate, có thể dùng object reference một chiều. Ví dụ Order sở hữu ShippingAddress:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    private ShippingAddress shippingAddress;
}
~~~

Spring Data JDBC xem ShippingAddress là entity/value thuộc aggregate Order theo mapping. Nếu ShippingAddress cần được chia sẻ hoặc quản lý độc lập, hãy tách thành aggregate riêng và lưu ID/reference.

### 10.4. @ManyToMany

JPA:

~~~java
@ManyToMany
@JoinTable(name = "book_author")
private Set<Author> authors;
~~~

Spring Data JDBC:

- Tách Book và Author thành hai aggregate.
- Mô hình hóa hàng liên kết bằng association entity/aggregate.
- Lưu author ID trong association.
- Dùng repository query để tìm chiều ngược lại.

Không dùng Set<Author> như một collection child nếu Author được nhiều Book dùng chung. Điều đó sẽ làm sai aggregate ownership và semantics xóa.

## 11. Điều phối nhiều aggregate trong service

Khi một use case cần thay đổi nhiều aggregate, service/application layer điều phối các repository.

Ví dụ đặt hàng:

~~~java
@Service
public class OrderService {

    private final OrderRepository orders;
    private final CustomerRepository customers;

    public OrderService(
            OrderRepository orders,
            CustomerRepository customers
    ) {
        this.orders = orders;
        this.customers = customers;
    }

    @Transactional
    public Order placeOrder(Long customerId, List<OrderLine> lines) {
        Customer customer = customers.findById(customerId)
                .orElseThrow();

        customer.ensureCanPlaceOrder();

        Order order = new Order(
                AggregateReference.to(customer.getId()),
                lines
        );

        return orders.save(order);
    }
}
~~~

Trong ví dụ, Customer và Order là hai aggregate. Service tải Customer để kiểm tra điều kiện nghiệp vụ rồi tạo Order với reference tới Customer.

Nếu use case cần cập nhật cả hai aggregate, các thao tác có thể nằm trong cùng transaction khi dùng cùng DataSource và transaction manager. Tuy nhiên, aggregate boundary vẫn độc lập; service là nơi điều phối thay đổi xuyên aggregate.

Không đưa toàn bộ object Customer vào Order chỉ để có thể gọi customer.getName() hoặc customer.getStatus(). Khi cần thông tin, đọc Customer qua repository hoặc tạo read model phù hợp.

## 12. Giới hạn nhất quán khi tham chiếu aggregate khác

Aggregate được thiết kế để bảo đảm consistency bên trong ranh giới của chính nó. Quan hệ giữa hai aggregate có thể thay đổi trong những transaction khác nhau.

Ví dụ Customer có trạng thái ACTIVE. Order mới chỉ được tạo nếu Customer còn active.

Có hai cách xử lý:

1. Tải Customer, kiểm tra trạng thái và tạo Order trong một transaction phù hợp.
2. Nếu quy trình có nhiều bước hoặc kéo dài, dùng workflow/event để xử lý nhất quán theo thời gian và có cơ chế bù trừ khi cần.

Không nên giả định việc giữ một object reference tới Customer trong Order làm cho trạng thái Customer tự đồng bộ. AggregateReference chỉ giữ ID.

Nếu một invariant cần được bảo đảm tuyệt đối giữa nhiều aggregate, hãy đánh giá lại boundary hoặc dùng cơ chế transaction/locking phù hợp với yêu cầu. Đừng tạo một aggregate khổng lồ chỉ để tránh thiết kế nhất quán liên aggregate.

## 13. Chú ý hiệu năng khi thiết kế lại

Thay quan hệ JPA bằng ID reference và explicit query giúp kiểm soát thời điểm truy vấn, nhưng cũng có thể khiến ứng dụng phát sinh nhiều repository calls nếu gọi từng ID trong vòng lặp.

Ví dụ không hiệu quả:

~~~java
for (Order order : orders) {
    Customer customer = customers.findById(
            order.getCustomer().getId()
    ).orElseThrow();

    // Dựng response.
}
~~~

Nếu danh sách có nhiều Order, cách này có thể tạo N truy vấn Customer.

Có thể batch-load Customer theo danh sách ID hoặc dùng read query JOIN để tạo DTO:

~~~sql
SELECT
    o.id,
    o.order_number,
    c.name AS customer_name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = :status;
~~~

Dùng aggregate repository cho thao tác domain và custom read query cho màn hình cần dữ liệu từ nhiều aggregate. Không thêm object reference hai chiều chỉ để tránh viết query.

## 14. Quy trình thiết kế lại khi chuyển từ JPA

1. Liệt kê entity, bảng và các quan hệ JPA hiện có.
2. Xác định aggregate root theo invariant và quyền sở hữu vòng đời.
3. Giữ object reference một chiều cho entity thực sự thuộc cùng aggregate.
4. Dùng @MappedCollection để khai báo collection và foreign key column.
5. Thay quan hệ tới aggregate khác bằng ID hoặc AggregateReference.
6. Loại bỏ object back-reference khỏi mapping persistence; nếu domain cần, dùng method parameter hoặc @Transient.
7. Thay truy vấn chiều ngược bằng repository query/derived query.
8. Thay cascade JPA bằng thao tác save/delete trên aggregate root và service orchestration.
9. Thay lazy loading bằng repository call tường minh, batch query hoặc read model.
10. Cập nhật schema migration, foreign key, unique constraint và index.
11. Kiểm tra tác động delete/reinsert của referenced entities khi save aggregate hiện có.
12. Viết integration test cho insert, update, remove child, delete root và tham chiếu giữa aggregate.
13. Đo query count và tải dữ liệu thực tế sau khi chuyển đổi.

## 15. Những lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách xử lý |
|---|---|---|
| Lưu aggregate gây vòng lặp mapping | Hai entity giữ object reference hai chiều đều được persist | Chỉ giữ reference một chiều; back-reference dùng @Transient |
| Xóa root làm mất entity dùng chung | Entity được mô hình hóa như child thuộc aggregate | Tách entity thành aggregate riêng và lưu ID |
| Child không được lưu | Child không nằm trong object graph được root tham chiếu | Đưa child vào @MappedCollection hoặc thiết kế lại ownership |
| Child bị xóa và tạo lại sau save | Spring Data JDBC đồng bộ referenced entities bằng delete/reinsert | Giữ child private trong aggregate; tách child cần identity độc lập |
| ID child thay đổi ngoài dự kiến | Child dùng generated ID và được tạo lại khi save root | Không để aggregate khác tham chiếu child; cân nhắc ID ổn định hoặc tách aggregate |
| Gọi getter nhưng không tự tải Customer | AggregateReference chỉ chứa ID | Gọi repository tường minh hoặc dùng read query |
| Tải danh sách phát nhiều query | Aggregate có collection được tải bằng statement riêng | Đo SQL, cân nhắc Single Query Loading hoặc read model |
| @ManyToMany không mapping như JPA | Spring Data JDBC không hỗ trợ object graph many-to-many | Dùng association entity/aggregate và ID |
| Xóa Customer bị foreign key từ chối | Order còn tham chiếu Customer | Xử lý reference hoặc chọn policy xóa phù hợp ở database |
| Xóa Customer làm Order bị mất ngoài dự kiến | FK có ON DELETE CASCADE không phù hợp | Review schema constraint và chính sách vòng đời |
| Không tìm được entity theo chiều ngược | Không có back-reference object tự động | Viết query trong repository của aggregate sở hữu foreign key |
| Transient back-reference bị null sau load | Chưa gắn lại reference khi dựng aggregate | Gắn trong persistence constructor hoặc callback |
| Tạo nhiều repository cho child table | Nhầm repository theo bảng với repository theo aggregate root | Tạo repository cho aggregate root |
| Save aggregate ghi nhiều SQL hơn JPA | Không có dirty tracking; child được đồng bộ lại | Đánh giá aggregate size và dùng custom persistence/read model khi cần |

## 16. Bài tập thực hành

### Bài 1 — Chuyển quan hệ Order và OrderLine

Tạo Order có List<OrderLine>. Thay @OneToMany và mappedBy bằng @MappedCollection. Lưu aggregate mới, đọc lại và kiểm tra cột order_id.

### Bài 2 — Back-reference transient

Cho OrderLine cần gọi tên Order. Thêm @Transient back-reference, gắn child khi thêm vào root và gắn lại trong persistence constructor. Kiểm tra không phát sinh cột parent object trong schema.

### Bài 3 — Chuyển ManyToOne thành AggregateReference

Thay Customer object trong Order bằng AggregateReference<Customer, Long>. Lưu order và kiểm tra customer_id. Đọc Customer qua CustomerRepository khi cần.

### Bài 4 — Truy vấn chiều ngược

Viết OrderRepository query tìm tất cả order theo customer_id. Kiểm tra kết quả khi Customer có nhiều Order.

### Bài 5 — Mô hình hóa many-to-many

Tạo Book, Author và BookAuthor association. Xóa Book rồi xác nhận association row bị xóa còn Author vẫn tồn tại. Kiểm tra unique constraint chống liên kết trùng.

### Bài 6 — Kiểm tra cascade theo aggregate

Tạo Order có ba lines. Xóa một line khỏi collection rồi save root. Đọc database và xác nhận line đó không còn. Quan sát SQL delete/insert.

### Bài 7 — So sánh generated child IDs

Tạo child dùng auto-increment ID. Save root, thay đổi một property root rồi save lại. Quan sát ID child và SQL persistence. Thảo luận khi nào cần tách child thành aggregate độc lập.

### Bài 8 — Thay lazy loading bằng read model

Tạo endpoint danh sách order và customer name. So sánh gọi customer repository từng order với một query JOIN trả DTO. Đo query count.

### Bài 9 — Kiểm tra delete policy

Tạo foreign key Order.customer_id tới Customer.id. Thử RESTRICT, SET NULL và CASCADE trong database test. Xác định policy phù hợp với domain và xác nhận Spring Data JDBC không tự xóa aggregate đích.

### Bài 10 — Integration test sau migration

Chạy schema migration mới trên database test, kiểm thử insert/update/delete và các query hai chiều. Xác nhận các aggregate độc lập không bị ghi/xóa ngoài ý muốn.

## 17. Ghi nhớ

- Spring Data JDBC thiết kế persistence quanh aggregate root, không quanh object graph hai chiều như JPA.
- Quan hệ nội bộ aggregate đi một chiều từ root tới child.
- @MappedCollection khai báo collection con và cột foreign key/back-reference.
- Nếu child cần biết root, truyền root vào method hoặc dùng back-reference @Transient và gắn lại trong bộ nhớ.
- Quan hệ giữa các aggregate dùng ID hoặc AggregateReference<T, ID>.
- Muốn điều hướng ngược, viết repository query dựa trên foreign key.
- Many-to-many nên được mô hình hóa bằng association entity/aggregate, không dùng hai collection object tham chiếu lẫn nhau.
- Spring Data JDBC không dùng CascadeType hoặc orphanRemoval của JPA; aggregate boundary quyết định entity nào được lưu và xóa cùng root.
- Khi save aggregate hiện có, implementation hiện tại xóa và tạo lại các referenced entities; không có dirty tracking cho từng child.
- Xóa aggregate root không tự xóa aggregate khác được tham chiếu bằng ID.
- Không có lazy-loading proxy. Repository load dựng aggregate theo mapping trước khi trả kết quả.
- Single Query Loading thay đổi số SQL khi load nhưng không biến quan hệ thành lazy.
- Dùng repository query, batch loading hoặc read model khi chỉ cần dữ liệu từ một phần aggregate hoặc từ nhiều aggregate.
- Cập nhật schema foreign key và test delete policy khi chuyển đổi từ JPA.
