# Business Keys, Surrogate Keys, and Unique Constraints in Spring Data JDBC

## 1. Why do we need to distinguish key types?

A row in a relational table needs a way to be identified and rules to prevent duplicate data. When designing a customer table, we may encounter several values that appear to identify a person or an organization:

- An internal ID generated by the database.
- A customer code issued by the business.
- A login email address.
- A customer code in a partner system.

These values may all be unique within some scope, yet they have **different roles and lifecycles**. Spring Data JDBC needs to know which property is the entity's identifier; the database needs to know which columns must be unique. These two concerns are related, not identical.

Three core concepts:

- **Business key / natural key:** an attribute or set of attributes that has meaning in the business domain and can identify an object, such as a contract code or a partner's customer code.
- **Surrogate key:** an identifier value created primarily as a technical key without business meaning, such as a §BIGINT§ identity ID or §UUID§.
- **Unique constraint:** a database rule requiring a column or combination of columns to have no duplicate values under the database's comparison rules.

A common design is to **use a surrogate key as the primary key while placing a unique constraint on the business key**. This keeps internal identity stable while the database continues to enforce the rule against duplicate business codes.

## 2. Primary key, business key, and surrogate key

### 2.1. Primary key

A primary key is the main key of a table. A primary key:

- Uniquely identifies a row.
- Must not contain §NULL§ values.
- Can consist of a single column or multiple columns (composite primary key).
- Is the common target referenced by foreign keys from other tables.

Example:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(30) NOT NULL
);
~~~

Here §id§ is the primary key. §customer_code§ may be a business key, but the schema has not yet placed a uniqueness rule on it.

### 2.2. Business key / natural key

A business key originates from the rules of the business domain. Examples:

- A company's tax ID.
- A contract code within an organization.
- A manufacturer's product code.
- An account identifier from an external system.
- A tenant code and customer code pair in a multi-tenant system.

Business keys can be stable, though not always. Some values can change due to organizational mergers, supplier switches, numbering convention changes, correcting bad data, or shifts in business scope. Emails and phone numbers usually should not be treated as permanent identifiers for a person because they can change or be recycled.

### 2.3. Surrogate key

A surrogate key is created to identify a row independently of business meaning:

~~~sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
~~~

or:

~~~sql
id UUID PRIMARY KEY
~~~

Common advantages:

- The identifier value remains stable even when the business code changes.
- Foreign keys from other tables can continue referencing the same ID.
- Related tables are not forced to copy a long or multi-column business key.
- Reduces impact when business rules change.
- Easy to link internal data with multiple external code sources.

Surrogate keys also have costs: an extra column, generating and managing the ID, and on their own they do not prevent duplicate business data. If §customer_code§ must be unique, you still must declare a unique constraint on that column.

### 2.4. Comparison

| Criterion | Business key | Surrogate key |
|---|---|---|
| Origin | Business rules or external systems | Technical mechanism of the application/database |
| Meaning to users | Usually meaningful | Usually has no business meaning |
| Stability | May change with business rules | Usually stays constant over the row's lifecycle |
| Uniqueness | Must be enforced via constraints if required | Guaranteed if it is the primary key |
| Use in URLs/APIs | Can fit if it is a stable public code | Can be used, depending on API policy |
| Internal foreign keys | Usable, though changes ripple outward | Usually more convenient and stable |

There is no single right choice for every system. What must be decided is **which value is truly the stable identifier**, which values are merely attributes that must be unique, and whether uniqueness is system-wide or scoped to a tenant/partner.

## 3. Unique constraints protect data in the database

Suppose each customer has a unique business code:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(30) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    email_address VARCHAR(320)
);

ALTER TABLE customers
    ADD CONSTRAINT uk_customers_customer_code
    UNIQUE (customer_code);
~~~

§UNIQUE (customer_code)§ forces the database to reject two rows with the same code according to the database's comparison rules. Naming the constraint §uk_customers_customer_code§ makes error identification and migration management easier.

### 3.1. Unique constraints differ from primary keys

| Characteristic | Primary key | Unique constraint |
|---|---|---|
| Purpose | Primary row identifier | Ensures a value/combination does not repeat |
| Count per table | Only one primary key | Can have multiple unique constraints |
| Allows §NULL§ | No | Depends on database and NULL handling |
| Used for foreign keys | Common reference target | Some databases allow referencing unique candidate keys |
| Role with Spring Data JDBC | Usually corresponds to the §@Id§ property | Enforces data rules; does not turn a property into §@Id§ |

A table can have one primary key and multiple unique constraints:

~~~sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(80) NOT NULL,
    email_address VARCHAR(320) NOT NULL,
    external_subject VARCHAR(200) NOT NULL,

    CONSTRAINT uk_users_username UNIQUE (username),
    CONSTRAINT uk_users_email UNIQUE (email_address),
    CONSTRAINT uk_users_external_subject UNIQUE (external_subject)
);
~~~

In this model, §id§ is the internal identifier. Username, email, and external subject are alternate candidate keys according to system rules. There is no need to mark all of them with §@Id§.

### 3.2. Unique constraints and unique indexes

Many database systems implement unique constraints using unique indexes or equivalent index structures. A **unique constraint** expresses a data integrity rule in the schema. A **unique index** can be created directly to enforce uniqueness and may support specialized forms such as partial/filtered indexes depending on the database.

Syntax, index names, and conditional index capabilities depend on the database system. For standard business rules, declare named constraints in DDL/migrations so schema intent is clear.

## 4. How does Spring Data JDBC map keys?

In Spring Data JDBC, §@Id§ marks a property as the entity's identifier. §@Column§ maps a property to a column name. **There is no second §@Id§ annotation for a business key merely because the business key is also unique.**

Example:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private Long id;

    @Column("customer_code")
    private String customerCode;

    @Column("display_name")
    private String displayName;

    @Column("email_address")
    private String emailAddress;

    // constructor, getters...
}
~~~

Here:

- §id§ is the identifier Spring Data JDBC uses for repository operations.
- §customerCode§ is the business key mapped to the §customer_code§ column.
- §emailAddress§ is another attribute, which can have a unique constraint if business rules require it.
- §@Column§ does not create a unique constraint or primary key in the database.

Repository:

~~~java
import java.util.Optional;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findByCustomerCode(String customerCode);

    Optional<Customer> findByEmailAddress(String emailAddress);
}
~~~

Derived queries reference **Java property names**, not physical column names. §findByCustomerCode§ is based on the §customerCode§ property, while mapping metadata resolves it to the §customer_code§ column.

§findByCustomerCode§ is a query by business key; §findById§ is a query by identifier. Both can locate the same entity, yet they serve different roles.

## 5. Complete example: surrogate primary key and unique business key

Suppose a sales system manages customers. Each customer has an internal ID and a business-issued customer code. Schema:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(30) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    email_address VARCHAR(320),

    CONSTRAINT uk_customers_customer_code
        UNIQUE (customer_code)
);
~~~

Entity:

~~~java
package com.example.customer;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private Long id;

    @Column("customer_code")
    private String customerCode;

    @Column("display_name")
    private String displayName;

    @Column("email_address")
    private String emailAddress;

    public Customer() {
    }

    public Customer(
            String customerCode,
            String displayName,
            String emailAddress
    ) {
        this.customerCode = customerCode;
        this.displayName = displayName;
        this.emailAddress = emailAddress;
    }

    public Long getId() {
        return id;
    }

    public String getCustomerCode() {
        return customerCode;
    }

    public String getDisplayName() {
        return displayName;
    }

    public String getEmailAddress() {
        return emailAddress;
    }
}
~~~

Repository:

~~~java
package com.example.customer;

import java.util.Optional;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findByCustomerCode(String customerCode);
}
~~~

Service:

~~~java
package com.example.customer;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer register(
            String customerCode,
            String displayName,
            String emailAddress
    ) {
        Customer customer = new Customer(
                customerCode,
                displayName,
                emailAddress
        );
        return customers.save(customer);
    }

    @Transactional(readOnly = true)
    public Customer getByCode(String customerCode) {
        return customers.findByCustomerCode(customerCode)
                .orElseThrow(() ->
                        new IllegalArgumentException(
                                "Customer not found: " + customerCode
                        )
                );
    }
}
~~~

When calling §register§, the new entity has §id == null§; the database generates the ID. The business key §customerCode§ is stored as regular data, yet the constraint §uk_customers_customer_code§ protects uniqueness.

If the application attempts to register two customers with the same §customerCode§, the database rejects the write that violates the constraint. Checking via the repository before inserting can improve early error messages, but the constraint remains the final line of defense.

## 6. Business keys can span multiple columns

Not every business key fits in a single column. For example, a customer code may only be unique **within each tenant**:

| tenant_id | customer_code | Meaning |
|---|---|---|
| §TENANT-A§ | §C001§ | Customer C001 of tenant A |
| §TENANT-B§ | §C001§ | Customer C001 of tenant B |
| §TENANT-A§ | §C002§ | Another customer of tenant A |

Here §customer_code§ can repeat across tenants, while the pair §(tenant_id, customer_code)§ must be unique:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id VARCHAR(40) NOT NULL,
    customer_code VARCHAR(30) NOT NULL,
    display_name VARCHAR(150) NOT NULL,

    CONSTRAINT uk_customers_tenant_code
        UNIQUE (tenant_id, customer_code)
);
~~~

Entity:

~~~java
@Table("customers")
public class Customer {

    @Id
    private Long id;

    @Column("tenant_id")
    private String tenantId;

    @Column("customer_code")
    private String customerCode;

    @Column("display_name")
    private String displayName;

    // constructor, getters...
}
~~~

Repository:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findByTenantIdAndCustomerCode(
            String tenantId,
            String customerCode
    );
}
~~~

A two-column unique constraint protects the exact business scope. Putting §UNIQUE(customer_code)§ alone would prevent tenant B from using code §C001§ even though that code is valid within tenant B's scope.

### 6.1. Column order in a unique constraint

§UNIQUE (tenant_id, customer_code)§ ensures no two rows share both values. It does not mean §tenant_id§ alone must be unique or §customer_code§ alone must be unique.

Column order can also affect how the database uses the index for queries. If the system frequently searches by §tenant_id§ and then §customer_code§, this order is usually helpful. Index design should be based on actual queries and query plans.

## 7. Business key, alternate key, and composite key

These terms are related, though not identical:

- **Candidate key:** minimal set of attributes that can uniquely identify a row in the data model.
- **Primary key:** candidate key chosen as the primary key.
- **Alternate key:** another candidate key not chosen as the primary key.
- **Business/natural key:** candidate key with meaning in the business domain.
- **Surrogate key:** identifier created for technical purposes without business meaning.
- **Composite key:** key consisting of multiple attributes.

For example, the §customers§ table has §id§ as its primary key and §customer_code§ as a unique alternate key. In a multi-tenant table, the pair §(tenant_id, customer_code)§ is a composite business key. We can still use §id§ as the surrogate primary key.

| Model | Primary key | Unique business key |
|---|---|---|
| Single-tenant customer | §id§ | §customer_code§ |
| Multi-tenant customer | §id§ | §(tenant_id, customer_code)§ |
| Login account | §id§ | §username§ or §email_address§ depending on policy |
| Products from multiple suppliers | §id§ | §(supplier_id, supplier_product_code)§ |

### Can a business key be used as the primary key?

Yes. If a code is genuinely immutable, unique, non-null, and has a stable lifecycle, it can be chosen as the primary key. For instance, an international standard code guaranteed not to change by its owning authority.

However, consider:

- If the business key changes, every foreign key referencing it may be affected.
- Long or multi-column keys make foreign keys in child tables wider.
- Business rules may change over time or across scopes.
- With application-assigned identifiers, Spring Data JDBC must accurately distinguish new vs. existing entities.

If a business key is used as §@Id§, that property becomes Spring Data JDBC's actual identifier. Do not simultaneously assume another §id§ column remains the repository identifier. With pre-assigned keys, design appropriate new-state detection (such as §Persistable§/§isNew()§ or a matching lifecycle strategy) because default rules normally rely on ID/version state.

## 8. Unique constraints and NULL values

An easily overlooked detail: **unique rules with NULL are not the same across all database systems**. Many databases allow multiple rows with §NULL§ in a unique column because NULL is treated as unknown; some database systems provide different syntax or options to treat NULLs as duplicates.

For example:

~~~sql
email_address VARCHAR(320) UNIQUE
~~~

may allow multiple customers who have not provided an email yet. If business rules require every customer to have an email and require emails to be unique:

~~~sql
email_address VARCHAR(320) NOT NULL,
CONSTRAINT uk_customers_email UNIQUE (email_address)
~~~

When using a composite unique constraint, behavior with NULL components also depends on the database. If all components of a business key are required, declare §NOT NULL§ on each column to express the rule accurately.

**Do not use NULL as a stand-in for an undetermined business code without clarifying semantics.** If a row lacks a code yet, decide whether an incomplete record is permitted to exist and design constraints accordingly.

## 9. Case-insensitive comparisons, whitespace, and normalization

Unique constraints typically use the database's collation, data type, and comparison rules. For instance, whether §ABC§ and §abc§ are considered equal depends on the database/collation. Leading/trailing whitespace, Unicode normalization, and equivalent characters can also matter.

If emails or usernames must be case-insensitive, writing only:

~~~sql
UNIQUE (email_address)
~~~

does not necessarily enforce the rule across all databases.

Several design approaches:

1. **Store canonicalized values:** normalize in the application before writing (e.g., trim and apply business-approved lowercase rules), storing into the column used for comparison.
2. **Separate normalized column:** keep a display value and a normalized column with a unique constraint.
3. **Functional/partial index or collation:** use database-specific capabilities if complex comparison is needed.

Example using a canonical column:

~~~sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email_address VARCHAR(320) NOT NULL,
    email_normalized VARCHAR(320) NOT NULL,

    CONSTRAINT uk_users_email_normalized
        UNIQUE (email_normalized)
);
~~~

The application can store §email_address§ for display and derive §email_normalized§ under a single policy. That same policy must be applied across every write path, including imports, batch jobs, and external integrations.

Do not automatically lowercase every business key if domain rules are case-sensitive. Normalization is a business decision, not just a technical trick.

## 10. Unique constraints and race conditions

A common mistake is checking data before writing:

~~~java
if (repository.findByCustomerCode(code).isPresent()) {
    throw new IllegalArgumentException("Code already exists");
}

repository.save(new Customer(code, name, email));
~~~

This snippet helps return a readable message when the code already exists at check time. However, it **does not guarantee uniqueness** when multiple requests run concurrently.

~~~mermaid
sequenceDiagram
    participant A as Request A
    participant B as Request B
    participant DB as Database
    A->>DB: SELECT code C001
    B->>DB: SELECT code C001
    DB-->>A: No row
    DB-->>B: No row
    A->>DB: INSERT C001
    B->>DB: INSERT C001
    DB-->>A: INSERT succeeds
    DB-->>B: UNIQUE constraint violation
~~~

Both A and B can read "does not exist yet". Without a unique constraint, both requests can write duplicates.

Therefore:

- Pre-checks can improve user experience.
- **Database unique constraints are the final and mandatory safeguard** when data must be unique.
- When an insert/update violates a constraint, handle the error and translate it into an appropriate business response.
- If multi-step operations are needed, choose transactions/isolation and concurrency mechanisms to match requirements.

### 10.1. Handling duplicate errors in Spring

Spring JDBC usually translates unique key violation errors into the §DataIntegrityViolationException§ family; in many specific cases this may be §DuplicateKeyException§. Classification depends on the driver and exception translator.

Example:

~~~java
import org.springframework.dao.DuplicateKeyException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerRegistrationService {

    private final CustomerRepository customers;

    public CustomerRegistrationService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer register(String code, String name, String email) {
        try {
            return customers.save(new Customer(code, name, email));
        } catch (DuplicateKeyException ex) {
            throw new CustomerCodeAlreadyUsedException(code, ex);
        }
    }
}
~~~

§CustomerCodeAlreadyUsedException§ is an application-defined business exception. In a real system, distinguish which constraint was violated if the database/driver provides reliable details, because duplicates could come from §customer_code§, email, or another key.

Do not catch every §DataIntegrityViolationException§ and always return "customer code already exists"; the error might come from a foreign key, NOT NULL, or another constraint.

Also mind transactions: depending on the database and transaction manager, a constraint failure may render the current transaction unable to continue. Usually, let the error propagate out of the transaction boundary and handle it at the appropriate business/API layer.

## 11. Is updating a business key safe?

A business key can change in some businesses. For instance, a customer's code changes after an organizational restructuring. If other tables directly reference the business key, changing the code can require cascading updates across many foreign keys.

With a surrogate primary key:

~~~text
customers
+----+---------------+
| id | customer_code |
+----+---------------+
| 42 | CUST-OLD      |
+----+---------------+

orders
+----+-------------+
| id | customer_id |
+----+-------------+
|  7 |          42 |
+----+-------------+
~~~

When the code changes to §CUST-NEW§, orders still reference §customer_id = 42§. That is the benefit of a stable internal ID.

However, if a business key must remain immutable for legal or audit reasons, do not allow changing it simply because the schema permits it. Determine who is allowed to change it, whether old codes must be retained in history, whether external systems still use this code, whether an alias from old code to new code is needed, and whether changes require an audit log.

A unique constraint only guarantees no duplicates at write time; it does not decide change permissions or keep history.

## 12. Business keys in relationships and join tables

Example of an order referencing a customer. With a surrogate key:

~~~sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL,

    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id),

    CONSTRAINT uk_orders_order_number
        UNIQUE (order_number)
);
~~~

Spring Data JDBC entity:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    @Column("order_number")
    private String orderNumber;

    // constructor, getters...
}
~~~

This example represents §customer_id§ as a plain data property. In Spring Data JDBC's aggregate model, object relationships and aggregate boundaries must be designed separately; do not treat having a foreign key column as automatically creating a JPA-style object graph.

If orders reference a business key instead of a surrogate ID, the schema and mapping must guarantee that key is unique, stable, and fits database foreign key rules. When a business key spans multiple columns, the child table must also store all referenced key columns.

## 13. Unique constraints for soft delete and historical data

A system may use soft delete via a §deleted_at§ or §active§ column. When a customer is soft-deleted, whether a new customer may reuse the old code is a business decision.

A plain constraint:

~~~sql
UNIQUE (customer_code)
~~~

still forbids reusing a soft-deleted code because the old row remains in the table.

If only active rows need uniqueness, some databases support **partial/filtered unique indexes**, for example PostgreSQL syntax:

~~~sql
CREATE UNIQUE INDEX uk_active_customer_code
ON customers (customer_code)
WHERE deleted_at IS NULL;
~~~

The syntax above is PostgreSQL-specific and not portable across all databases. On other database systems, you may need a status column, generated column, archive strategy, or another design.

Also consider history and restoration: if reusing codes is permitted, restoring an old row can conflict with a newer row using the same code.

## 14. Testing unique constraints

Test rules against the real database or a database compatible enough with the constraints in use. A Spring Data JDBC integration test can illustrate:

~~~java
@DataJdbcTest
class CustomerRepositoryTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void customerCodeMustBeUnique() {
        customers.save(new Customer("C001", "Lan", null));

        assertThatThrownBy(() ->
                customers.save(new Customer("C001", "Minh", null))
        ).isInstanceOf(DataIntegrityViolationException.class);
    }
}
~~~

This test assumes the test schema created the §uk_customers_customer_code§ unique constraint and the test database throws a compatible exception. Import the needed assertions/annotations and prepare a test schema matching your project.

Cases to cover:

- Two rows with the same single business key.
- Two rows with the same composite key pair.
- Same code under a different tenant accepted when uniqueness is tenant-scoped.
- NULL on unique columns, matching chosen database semantics.
- Case and whitespace comparisons matching canonicalization policy.
- Two concurrent requests inserting the same key.
- Updating a business key to a value already used by another row.
- Soft delete, restoration, and code reuse.

H2 tests are useful for basic logic, yet partial indexes, collation, and NULL handling can differ from the production database. For database-dependent rules, test against the exact target database system.

## 15. Migrations and existing data

When adding a unique constraint to a table that already contains data, the database must check existing rows. If duplicate values already exist, the migration will fail.

A deployment process typically includes:

1. Identify the business key and uniqueness scope.
2. Find duplicate groups in existing data.
3. Decide how to merge, fix, or archive duplicate records.
4. Normalize data if comparison rules require it.
5. Ensure required columns have values before setting §NOT NULL§.
6. Create the unique constraint/index in the migration.
7. Deploy application handling for duplicate errors under the new rules.
8. Monitor write errors and query performance.

Query to detect duplicates:

~~~sql
SELECT customer_code, COUNT(*) AS duplicate_count
FROM customers
GROUP BY customer_code
HAVING COUNT(*) > 1;
~~~

With a composite key:

~~~sql
SELECT tenant_id, customer_code, COUNT(*) AS duplicate_count
FROM customers
GROUP BY tenant_id, customer_code
HAVING COUNT(*) > 1;
~~~

Do not just add a constraint and hope the migration succeeds. Legacy data can violate new rules, and a cleanup plan is needed before applying them.

## 16. Common design mistakes

| Mistake | Consequence | Solution |
|---|---|---|
| Using email as primary key even though email can change | Changing email cascades updates across relationships | Use a surrogate primary key, unique email if needed |
| Checking existence only in Java without a unique constraint | Two concurrent requests can write duplicates | Enforce a unique constraint in the database |
| Marking both business key and surrogate key with §@Id§ | Identifier mapping does not match the model | Mark only one identifier per entity |
| Thinking §@Column§ creates a unique constraint | Database still accepts duplicate data | Declare constraints in DDL/migrations |
| Using §UNIQUE(customer_code)§ in a multi-tenant system | Other tenants cannot use the same code | Use §UNIQUE(tenant_id, customer_code)§ |
| Not defining NULL rules | Multiple rows missing keys may be accepted unexpectedly | Choose §NOT NULL§ or explicit NULL semantics |
| Not normalizing email/username | Case/whitespace differences create logical duplicates | Design canonicalization and matching constraints |
| Catching every integrity error as a duplicate business key | Returns wrong message for foreign key/NOT NULL errors | Distinguish specific constraints and exceptions |
| Adding a unique constraint onto old data without cleaning duplicates | Migration fails | Inspect and clean data beforehand |
| Allowing code reuse after soft delete without considering restore | Restoring an old record causes conflicts | Design a partial unique index or code policy |

## 18. Key takeaways

- A **business key** comes from business rules; a **surrogate key** is a technical identifier; a **unique constraint** is an integrity rule enforced by the database.
- A table can typically use a surrogate primary key alongside multiple alternate/business keys protected by unique constraints.
- In Spring Data JDBC, §@Id§ marks the entity's identifier; §@Column§ maps the column name. They do not create constraints automatically.
- A business key can be a single column or a combination of columns, such as §UNIQUE(tenant_id, customer_code)§.
- Unique rules regarding NULL, case sensitivity, collation, and partial indexes depend on the database system.
- Pre-checks before insert only help provide early feedback; **only a unique constraint protects uniqueness under concurrent requests**.
- Using a surrogate ID keeps internal relationships stable when business keys change, while history and code-change policies still need to be designed.
- When adding constraints to existing data, find and resolve duplicates before running the migration.
