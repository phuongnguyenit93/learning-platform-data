# Preserving Foreign Key Integrity When Aggregates Are Updated or Deleted

In Spring Data JDBC, one aggregate can reference another aggregate via an ID or §AggregateReference<T, ID>§. For example, §PurchaseOrder§ holds §customerId§ to know which customer the order belongs to. Both aggregates have separate lifecycles, yet the data in the database must still ensure that referenced IDs remain meaningful and do not point to a row deleted outside business policy.

This is the problem of **referential integrity**. The most reliable protection combines:

- **Clear aggregate boundaries:** each aggregate root manages its own state and lifecycle.
- **Foreign keys in the database:** prevent creating references to non-existent rows and protect references currently in use.
- **Appropriate update/delete policies:** define what happens when a referenced aggregate changes or is deleted.
- **Transactions and error handling:** coordinate related operations while handling concurrent data modifications.

A successful repository call does not replace these constraints. Conversely, a properly configured foreign key does not automatically decide business policies such as preserving order history, anonymizing customers, or rejecting deletion.

## 1. What Is an Aggregate Reference?

Suppose a sales system has two independent aggregates:

- §Customer§ manages customer profiles.
- §PurchaseOrder§ manages orders and the order lines owned inside each order.

One customer can have many orders. Each order references the customer via an ID:

§§§text
Customer aggregate                  PurchaseOrder aggregate
┌──────────────────────┐           ┌────────────────────────┐
│ Customer             │           │ PurchaseOrder          │
│ id = 42              │◄──────────│ customerId = 42        │
│ name = "Lan"         │  reference│ id = 501               │
└──────────────────────┘           │ status = "CONFIRMED"   │
          ▲                        │                        │
          │                        │ ├─ OrderLine A         │
          │                        │ └─ OrderLine B         │
          │                        └────────────────────────┘
          │
          └──── Another PurchaseOrder can also reference Customer 42
§§§

§PurchaseOrder§ does not own §Customer§. Changing a customer's name does not require re-saving every order; deleting an order must not automatically delete the customer. However, as long as an order exists, §customerId§ must comply with the defined reference policy.

In Spring Data JDBC, the reference can be represented using a simple type:

§§§java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Column("customer_id") Long customerId,
        String status
) {
}
§§§

Or by explicitly expressing the referenced aggregate type with §AggregateReference§:

§§§java
import org.springframework.data.jdbc.core.mapping.AggregateReference;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Column("customer_id")
        AggregateReference<Customer, Long> customer,
        String status
) {
}
§§§

Both approaches represent a reference ID. §AggregateReference§ does not automatically load §Customer§, does not automatically save §Customer§, and does not replace a foreign key in the schema. When customer details are needed, the application queries §CustomerRepository§ explicitly.

## 2. Why Must Foreign Keys Be Protected in the Database?

Suppose the §purchase_orders§ table has a §customer_id§ column. If you only check in Java that the customer exists, this scenario can still happen:

1. Request A checks that customer ID 42 exists.
2. Request B deletes customer ID 42.
3. Request A proceeds to insert an order referencing ID 42.

Without a foreign key in the database, the order can be saved with §customer_id = 42§ even though no matching customer exists anymore. This is an **orphan reference**.

A §FOREIGN KEY§ constraint forces the database to validate integrity at write time:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_purchase_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
§§§

When inserting or updating an order with a non-existent §customer_id§, the database rejects the operation. When deleting a customer referenced by orders, the database also enforces the foreign key behavior.

**Existence checks in the application and foreign keys in the database serve two different purposes:**

| Mechanism | Purpose |
| --- | --- |
| §customerRepository.existsById(id)§ | Lets the application return a user-friendly business error before writing. |
| §FOREIGN KEY§ | Protects data even under concurrent requests, SQL scripts, or direct writes from other applications. |
| §@Transactional§ | Ensures a group of operations in the same transaction commits/rolls back according to transaction rules. |
| §@Version§ | Detects certain cases of concurrent aggregate updates; does not replace a foreign key. |

In real-world systems, you should keep foreign keys in the database even when the service already validates the reference ID.

## 3. What Happens When a Referenced Aggregate Is Updated?

Suppose §PurchaseOrder§ references §Customer§ via §customer_id = 42§.

### 3.1. Updating Non-Key Attributes of Customer

For example, renaming the customer:

§§§sql
UPDATE customers
SET full_name = 'Lan Nguyen'
WHERE id = 42;
§§§

The primary key §id§ remains 42, so referencing orders are unaffected in terms of integrity. There is no need to update §purchase_orders§ simply because the customer's name changed.

Corresponding repository flow:

§§§java
@Transactional
public Customer renameCustomer(Long customerId, String newName) {
    Customer current = customers.findById(customerId)
            .orElseThrow();

    Customer updated = new Customer(current.id(), newName);
    return customers.save(updated);
}
§§§

This operation stays inside the §Customer§ aggregate. Any §PurchaseOrder§ referencing that customer keeps the same ID.

That does not mean every display field in an order automatically changes with it. If an order also stores a snapshot such as §customerNameAtPurchase§ to preserve history at purchase time, that snapshot belongs to the order and should not automatically update when the customer's name changes.

### 3.2. Updating Non-Referenced Key Data

Attributes such as name, email, active status, or phone number can change without breaking the foreign key, provided the referenced key column remains unchanged and other constraints stay valid.

For example:

§§§sql
UPDATE customers
SET full_name = 'Lan Nguyen',
    email = 'lan.nguyen@example.com'
WHERE id = 42;
§§§

Orders still reference ID 42. However, if the business requires emails to be unique, a §UNIQUE§ constraint on §customers.email§ must enforce that separately.

### 3.3. Changing a Referenced Primary Key

Changing an aggregate's ID is a far more sensitive operation:

§§§sql
UPDATE customers
SET id = 99
WHERE id = 42;
§§§

If orders reference ID 42, the database must have a policy for changing the referenced key. With default §NO ACTION§/§RESTRICT§ behavior, the operation will be rejected. If the schema declares §ON UPDATE CASCADE§, the database can update foreign keys from 42 to 99.

Even if the database supports cascading updates, **do not treat changing aggregate IDs as a routine data edit**. An ID is the stable identity of the aggregate. If a business code needs to change, use a separate attribute such as §customerCode§ rather than altering the primary key.

If a key truly must change, identify all referencing scopes, constraints, transactions, and effects on integrated systems. Do not rely on §ON UPDATE CASCADE§ as a default workaround for an unstable ID design.

## 4. What Happens When a Referenced Aggregate Is Deleted?

This is where the foreign key policy becomes critical.

With the default schema:

§§§sql
FOREIGN KEY (customer_id)
REFERENCES customers(id)
§§§

the database typically defaults to §NO ACTION§ when no delete behavior is specified. If orders still reference the customer, deleting the customer is rejected.

For example:

§§§sql
DELETE FROM customers
WHERE id = 42;
§§§

If §purchase_orders§ still has rows with §customer_id = 42§, the delete fails with a foreign key violation.

This usually matches transactional data needs: a customer with orders cannot be casually hard-deleted, because orders must preserve their historical link.

### 4.1. Four Common ON DELETE Policies

| Policy | Behavior | When to consider |
| --- | --- | --- |
| §RESTRICT§ | Rejects deleting the parent row if child rows still reference it. | Disallow deleting customers who still have orders. |
| §NO ACTION§ | Checks the constraint; typically similar to RESTRICT on immediate checks, though it can differ when constraints are declared deferred. | Default behavior or when checking at commit time is needed. |
| §CASCADE§ | Deletes referencing rows when the referenced row is deleted. | Child data is genuinely dependent and must be deleted together. |
| §SET NULL§ | Sets the foreign key column on referencing rows to SQL NULL. | The relationship can be cleared while referencing rows remain valid. |

Some DBMSs also support §SET DEFAULT§, though the default value must satisfy the foreign key constraint. This policy is less common and requires clear domain meaning.

**A crucial point about cascade direction:** if §purchase_orders.customer_id§ references §customers.id§, then §ON DELETE CASCADE§ on this foreign key means **deleting a Customer deletes the PurchaseOrders referencing that Customer**. It does not mean deleting a PurchaseOrder deletes the Customer.

§§§text
customers (referenced table)
      |
      | ON DELETE CASCADE
      v
purchase_orders (table holding the foreign key)

DELETE customers.id = 42
      |
      +----> deletes purchase_orders where customer_id = 42
§§§

Because §PurchaseOrder§ is usually transactional history that must be retained, cascading from Customer to Order is normally very dangerous.

### 4.2. RESTRICT / NO ACTION: Retaining Referencing Data

PostgreSQL schema example:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_purchase_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
        ON DELETE RESTRICT
        ON UPDATE RESTRICT
);
§§§

When orders exist, the database blocks deleting the customer. The application can transition the customer to an inactive status instead of performing a physical delete.

This is usually the best option when referencing data must survive for auditing, reporting, or transaction history.

### 4.3. CASCADE: Use Only When Child Data Is Truly Dependent

§ON DELETE CASCADE§ makes sense when referencing rows have no meaning once the parent row is removed, such as certain configuration entries or owned components.

Distinguish carefully:

- **Owned child within the same aggregate:** lifecycle depends on the root; when deleting the root, child components must be handled.
- **Cross-aggregate reference:** another aggregate has its own lifecycle; deleting the referenced root should not automatically delete referencing aggregates unless domain rules specify it.

For example, §Customer§ and §PurchaseOrder§ are two independent aggregates. Putting cascade on §purchase_orders.customer_id§ can wipe out entire order histories when a customer is deleted. Use it only when business requirements truly mandate it and all consequences have been evaluated.

### 4.4. SET NULL: Only Valid If the Relationship Is Optional

If an order can exist without an active customer link, the schema can allow §customer_id§ to be nullable:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_purchase_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
        ON DELETE SET NULL
);
§§§

In Java, the reference property must allow null:

§§§java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Column("customer_id") Long customerId,
        String status
) {
}
§§§

§Long customerId§ can represent SQL NULL; primitive §long customerId§ cannot. If the database sets §customer_id§ to null after a customer is deleted, reloading the aggregate must observe §customerId == null§.

Still, ask: is an order without a customer still valid? If the order must retain buyer identity for legal, accounting, or customer support purposes, §SET NULL§ can lose critical context. You may need a data snapshot or a dedicated anonymization policy.

### 4.5. SET DEFAULT: Use When a Replacement Value Has Clear Meaning

Some systems reassign references to a default record, such as an "anonymized" or "unknown" customer. If using §SET DEFAULT§, the default value must reference a valid row; otherwise the constraint still fails.

Do not invent a dummy ID like 0 just to bypass foreign key errors. Replacement records must have clear domain meaning and proper management.

## 5. Configuring Foreign Keys in Migrations

Spring Data JDBC maps objects and runs persistence operations; schemas and constraints are normally managed by migration tools like Flyway or Liquibase.

PostgreSQL migration example:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_purchase_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
        ON DELETE RESTRICT
        ON UPDATE RESTRICT
);

CREATE INDEX idx_purchase_orders_customer_id
    ON purchase_orders(customer_id);
§§§

Why is an index on §purchase_orders.customer_id§ needed?

- Helps the database find orders referencing a given customer faster.
- Supports querying order history per customer.
- Can make validating and handling deletes/updates on the referenced row more efficient.

In PostgreSQL, declaring a foreign key does not automatically create an index on the referencing column in the child table. Evaluate indexes based on actual queries and data volumes.

### 5.1. Adding a Foreign Key to a Table That Already Has Data

If the table already exists, inspect existing rows before adding the constraint:

§§§sql
SELECT po.id, po.customer_id
FROM purchase_orders po
LEFT JOIN customers c ON c.id = po.customer_id
WHERE po.customer_id IS NOT NULL
  AND c.id IS NULL;
§§§

This query detects orphan references. If any rows match, resolve them according to data policy before adding the foreign key.

Once data is valid:

§§§sql
ALTER TABLE purchase_orders
ADD CONSTRAINT fk_purchase_orders_customer
FOREIGN KEY (customer_id)
REFERENCES customers(id)
ON DELETE RESTRICT;
§§§

Do not bulk-delete or overwrite IDs just to make a migration pass. Identify why the data became invalid and how to restore valid relationships.

## 6. Updating a Referenced Aggregate Without Breaking Links

A referenced aggregate can be updated at several levels.

### 6.1. Updating Non-Key Attributes

This is the ordinary case:

§§§java
@Transactional
public Customer updateCustomerName(Long customerId, String name) {
    Customer current = customerRepository.findById(customerId)
            .orElseThrow();

    Customer updated = new Customer(
            current.id(),
            name
    );

    return customerRepository.save(updated);
}
§§§

The ID does not change, so foreign keys remain valid. There is no need to load and re-save all orders.

### 6.2. Reassigning an Order to Another Customer

This updates the reference on the aggregate holding the foreign key:

§§§java
@Transactional
public PurchaseOrder reassignCustomer(
        Long orderId,
        Long newCustomerId
) {
    Customer newCustomer = customerRepository.findById(newCustomerId)
            .orElseThrow(() ->
                    new IllegalArgumentException("Customer not found"));

    PurchaseOrder current = orderRepository.findById(orderId)
            .orElseThrow();

    PurchaseOrder updated = new PurchaseOrder(
            current.id(),
            newCustomer.id(),
            current.status()
    );

    return orderRepository.save(updated);
}
§§§

This example assumes §customerId§ is a simple reference property and the §PurchaseOrder§ constructor matches. If using §AggregateReference§, construct a reference from the new ID rather than passing §Long§ directly.

Changing the customer of an order can be a sensitive business action. The system should check permissions, order status, and ownership transfer rules before updating.

### 6.3. Changing the ID of a Referenced Aggregate

Usually this should not be done. If an ID genuinely must change, options include:

- Creating a new aggregate with the new ID and running a reference transfer workflow.
- Using §ON UPDATE CASCADE§ if the system and domain accept cascading updates to all related FKs.
- Running a controlled migration/transaction if bulk identity changes are needed.

Changing IDs can impact caches, events, logs, URLs, APIs, integrated systems, and historical records. IDs should stay stable; if a business identifier must change, create a separate attribute and keep the primary key unchanged.

## 7. Deleting a Referenced Aggregate with Spring Data JDBC

Repository declarations:

§§§java
public interface CustomerRepository
        extends CrudRepository<Customer, Long> {
}

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
§§§

A service can check for references before deleting:

§§§java
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository customers;
    private final PurchaseOrderRepository orders;

    public CustomerService(
            CustomerRepository customers,
            PurchaseOrderRepository orders
    ) {
        this.customers = customers;
        this.orders = orders;
    }

    @Transactional
    public void deleteCustomer(Long customerId) {
        Customer customer = customers.findById(customerId)
                .orElseThrow();

        if (orders.existsByCustomerId(customerId)) {
            throw new IllegalStateException(
                    "Cannot delete a customer with existing orders"
            );
        }

        customers.delete(customer);
    }
}
§§§

The snippet requires a corresponding query method on §PurchaseOrderRepository§:

§§§java
boolean existsByCustomerId(Long customerId);
§§§

Pre-checking helps return a clear business error. However, **pre-checking alone is insufficient to protect integrity under concurrent requests**. Another transaction can insert an order after the check and before the customer is deleted.

The database foreign key remains the last line of defense. Under contention, the delete can fail with a constraint violation; the application must translate that exception into an appropriate response.

Error-handling example at the service/API boundary:

§§§java
try {
    customerService.deleteCustomer(customerId);
} catch (DataIntegrityViolationException ex) {
    // Translate into a business error:
    // the customer is still referenced by other data
}
§§§

Do not swallow the error and return success. Distinguish FK errors from other data errors if the application needs accurate messaging; you can inspect the constraint name from the root cause depending on the driver/database.

### 7.1. Why Doesn't @Transactional Automatically Prevent Race Conditions?

A transaction protects the atomicity of operations within itself, but the default isolation level does not necessarily prevent another transaction from inserting a referencing row after the current transaction performs an existence check.

Example of two transactions:

§§§text
Transaction A                         Transaction B
--------------                         --------------
Check no Order exists
                                       INSERT Order(customer_id = 42)
                                       COMMIT
DELETE Customer(id = 42)
  |
  +-- FK checks and rejects
ROLLBACK
§§§

As a result, data remains consistent thanks to the foreign key even though the pre-check succeeded. Depending on the database and isolation level, how transactions wait or fail can vary, but never remove an FK merely because §@Transactional§ is present.

## 8. Deleting a Referencing Aggregate: Do Not Accidentally Delete the Referenced Aggregate

Distinguish the two directions of deletion:

- **Deleting Customer:** the referenced row; must consider orders pointing to it.
- **Deleting PurchaseOrder:** the row holding the foreign key; normally does not affect Customer.

For example:

§§§sql
DELETE FROM purchase_orders
WHERE id = 501;
§§§

This deletes order 501. It does not delete §customers.id = 42§. Components owned inside the order aggregate are handled according to their mapping and persistence policy.

If §PurchaseOrder§ has child tables such as §order_lines§, that is an ownership relationship distinct from the §customer_id§ reference. A cascade policy from §purchase_orders§ to §order_lines§ can make sense, whereas cascading from §customers§ to §purchase_orders§ can destroy history.

§§§text
Customer 42
    ^
    | FK: purchase_orders.customer_id
    |
PurchaseOrder 501
    |
    | ownership FK
    v
OrderLine rows

Delete Customer 42:
  May be RESTRICTED because PurchaseOrder 501 still references it.

Delete PurchaseOrder 501:
  Deletes/handles OrderLines belonging to the order.
  Customer 42 remains intact.
§§§

This is why you should not apply one uniform cascade policy to every relationship in the schema. Each FK must reflect its true domain relationship.

## 9. Soft Delete, Deactivation, and Preserving History

In business systems, physically deleting a referenced aggregate is often not the right choice. Instead, you can use **soft delete** or a deactivated state.

Example adding columns:

§§§sql
ALTER TABLE customers
ADD COLUMN deleted_at TIMESTAMP WITH TIME ZONE NULL,
ADD COLUMN active BOOLEAN NOT NULL DEFAULT TRUE;
§§§

When a customer requests account closure:

§§§sql
UPDATE customers
SET active = FALSE,
    deleted_at = CURRENT_TIMESTAMP
WHERE id = 42;
§§§

The §customers§ row still exists, so foreign keys from past orders remain valid. The application can:

- Prevent new orders from being placed for deactivated customers.
- Continue displaying required information for old orders.
- Hide or restrict personal data according to policy.
- Retain audit trails and transaction history.

Soft delete **does not automatically make rows disappear from queries**. Repositories and services must filter by status appropriately. If personal data deletion or anonymization is legally required, design a dedicated process that meets those requirements while preserving essential transaction records.

### 9.1. Snapshotting Data at Transaction Time

An order may need to keep certain customer details as they existed at purchase time:

§§§sql
ALTER TABLE purchase_orders
ADD COLUMN customer_name_at_purchase VARCHAR(150),
ADD COLUMN shipping_address_at_purchase VARCHAR(500);
§§§

Snapshot columns do not replace §customer_id§ in all cases; they preserve historical values needed so the order continues displaying accurately when customer info changes later.

The Java model might look like:

§§§java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        Long customerId,
        String customerNameAtPurchase,
        String shippingAddressAtPurchase,
        String status
) {
}
§§§

When creating an order, the service reads customer details, captures the required snapshot, and saves it with the order. Afterward, updating the customer profile does not alter the order's historical content.

Snapshots should be chosen based on business needs; do not copy the entire personal profile if unnecessary.

## 10. Updating and Deleting Across Multiple Aggregates in One Transaction

Sometimes a business workflow must update multiple aggregates together. For example, a controlled customer cancellation workflow may need to:

1. Check the customer and their orders.
2. Close or transition open orders according to rules.
3. Mark the customer inactive.
4. Save an audit event.

If all of these reside in the same database and require atomicity, the service can coordinate them with §@Transactional§. Still, this does not turn separate aggregates into a single aggregate.

Service skeleton example:

§§§java
@Transactional
public void deactivateCustomer(Long customerId) {
    Customer customer = customers.findById(customerId)
            .orElseThrow();

    // Check and handle open orders according to business rules.
    // Do not automatically delete order history.

    Customer deactivated = customer.deactivate();
    customers.save(deactivated);
}
§§§

If multiple orders must be updated, explicitly define allowed state transitions and how to handle an order that cannot be updated. Never use cascading deletes just to shorten code.

If the aggregates reside in different databases or services, an ordinary JDBC transaction cannot guarantee distributed atomicity. In that case, design workflows using outbox, saga, events, and eventual consistency as required by the system.

## 11. When Should You Use ON DELETE CASCADE for an Aggregate Reference?

Consider cascade only when all of the following hold:

- The referencing row genuinely has no meaning once the target aggregate is deleted.
- No history of the referencing row needs to be kept.
- No other aggregate or system depends on that data.
- Bulk deletion is well understood and can be audited/restored as required.
- This policy is reflected consistently across domain, migrations, and operations.

If the only goal is avoiding FK errors on delete, §CASCADE§ is not a universal fix. It can turn a simple delete into wiping out a large dataset.

For the §Customer → PurchaseOrder§ reference in the sales example, appropriate choices are typically:

- §ON DELETE RESTRICT§ or §NO ACTION§ to preserve history.
- Soft-deleting/deactivating Customer to stop further usage.
- Snapshotting transaction data when purchase-time details must be preserved.
- A dedicated anonymization workflow when personal data protection laws apply.

## 12. Handling Schema Changes and Existing Data

When changing an FK policy, do not only edit Java entities. You need a database migration and data plan.

For example, changing from §NOT NULL§ to an optional §SET NULL§ relationship:

§§§sql
ALTER TABLE purchase_orders
DROP CONSTRAINT fk_purchase_orders_customer;

ALTER TABLE purchase_orders
ALTER COLUMN customer_id DROP NOT NULL;

ALTER TABLE purchase_orders
ADD CONSTRAINT fk_purchase_orders_customer
FOREIGN KEY (customer_id)
REFERENCES customers(id)
ON DELETE SET NULL;
§§§

Then Java must allow null:

§§§java
@Column("customer_id")
private Long customerId;
§§§

This migration changes the domain contract: an order can exist without a referenced customer. Before applying it, check:

- Which code assumes §customerId§ is always non-null?
- Which queries/reports join §customers§ using an inner join?
- Can APIs return an order missing a customer?
- Do authorization and history rules change?
- How will legacy data be handled under the new policy?

Changing constraints without updating the domain can cause failures that surface only at runtime when loading or using the aggregate.

## 13. Common Misconceptions

**"Spring Data JDBC automatically protects all references by loading related aggregates."** False. ID references do not automatically load target aggregates. Database foreign keys protect referential integrity.

**"Checking existsById before saving is enough."** False. Concurrent requests or other write paths can alter data after the check. FKs are still necessary.

**"Deleting Customer automatically deletes Orders because there is an FK."** False. Behavior depends on the §ON DELETE§ policy. By default, deletion is usually rejected while references remain; cascading only occurs when declared.

**"ON DELETE CASCADE deletes the referenced object."** Read the direction carefully. With an FK on the Order table pointing to Customer, deleting Customer can cascade-delete Orders. Deleting an Order does not cascade backward to delete Customer.

**"Updating Customer's name requires re-saving all Orders."** Not necessary if Order only stores a reference ID. Historical snapshots are a separate requirement and do not sync automatically.

**"Aggregate IDs can be changed just like renaming a field."** Advisable against. IDs are stable identities; changing them can affect every foreign key, cache, event, and integrated system.

**"SET NULL is always safer than RESTRICT."** No. It can erase links needed to understand transaction history. Use it only when the referencing aggregate is valid without a target object.

**"Soft delete automatically removes rows from repositories."** No. Soft delete only updates a status/column; queries must apply appropriate filter conditions.

**"@Transactional replaces FKs."** No. Transactions manage atomicity and operation scope; FKs protect relationships between rows in the database.

## 14. Process for Designing a Referential Integrity Policy

When an aggregate references another aggregate, answer these in order:

1. **Who owns the data?** Identify the aggregate roots and keep only IDs in references.
2. **Which key is referenced?** Prefer stable IDs rather than mutable attributes such as name or email.
3. **Is the reference required?** If required, use a §NOT NULL§ column; if optional, use a wrapper type and allow SQL NULL.
4. **If the target aggregate's attributes change, what must change?** Usually references need no update if the ID stays constant.
5. **If the target ID changes, is there a policy?** Generally avoid changing IDs; if unavoidable, plan cascades or reference transfers.
6. **If the target aggregate is deleted, how are referencing records handled?** RESTRICT/NO ACTION, CASCADE, SET NULL, SET DEFAULT, or soft delete.
7. **Must historical data be retained?** Consider snapshots, auditing, and anonymization.
8. **Is there concurrent contention?** Add FKs, unique constraints, and database error handling; do not rely solely on application checks.
9. **Do multi-aggregate operations need atomicity?** Choose an appropriate transaction or distributed workflow.
10. **Are migrations and code aligned?** Verify schemas, mappings, queries, APIs, and existing data.

## 16. Key Takeaways

- References between independent aggregates are typically represented with an ID or §AggregateReference§; Spring Data JDBC does not auto-load or cascade-save the referenced aggregate.
- Database foreign keys are the final safeguard against orphan references, even under concurrent requests.
- Updating non-key attributes on a referenced aggregate normally does not affect FKs as long as the ID stays stable.
- Changing a referenced ID is sensitive; keep IDs stable and use a separate business code if mutable codes are needed.
- When deleting a referenced aggregate, §RESTRICT§/§NO ACTION§ preserves data, §CASCADE§ deletes referencing rows, and §SET NULL§ keeps rows while clearing the link if the column is nullable.
- Read FK direction correctly: deleting the referenced row triggers §ON DELETE§ policies on referencing rows.
- Deleting a referencing aggregate does not mean deleting the referenced aggregate; keep their lifecycles separate.
- §@Transactional§ does not replace FKs; application existence checks do not replace constraints either.
- For historical data, soft delete, archiving, snapshots, and anonymization should usually be considered before physical deletion.
- Migrations, Java mappings, repositories, services, and database policies must all reflect the same business rules.

When properly designed, each aggregate retains control over its own data while foreign keys safeguard the links between them. **Referential integrity is not just about avoiding SQL errors on delete; it is about ensuring data remains meaningful throughout the lifecycle of every aggregate.**
