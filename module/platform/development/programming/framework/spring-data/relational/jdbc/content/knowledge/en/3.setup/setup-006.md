# Creating Your First Aggregate Root and Repository with Spring Data JDBC

When starting a **Spring Data Relational JDBC** project, the most important step is not merely declaring an interface that extends `CrudRepository`. You must identify the **aggregate root**—the object representing a business consistency boundary—and let the repository operate through that root object.

This hands-on guide builds a small Java application that stores **books in a catalog** using **Spring Boot + Spring Data JDBC + H2**. Each `Book` is an independent aggregate root; the application creates the table, saves a book, looks it up by ID, looks it up by title, updates its price, and deletes it. The final section expands to a multi-table aggregate to clarify why Spring Data JDBC emphasizes the aggregate concept.

## 1. Learning Outcomes

Once completed, you will be able to:

1. Explain aggregates, aggregate roots, and the role of repositories in Spring Data JDBC.
2. Initialize a Spring Boot project using `spring-boot-starter-data-jdbc` and a relational database.
3. Map a Java record to a table using `@Table` and `@Id`.
4. Create a repository with `CrudRepository<Book, Long>` without writing basic CRUD SQL manually.
5. Observe the difference between creating, loading, updating, and deleting an aggregate.
6. Recognize when to add child entities with `@MappedCollection` versus keeping an ID reference only.

### Prerequisites

- **JDK 17 or higher**; this lesson uses Java records.
- A Java and Spring Boot IDE (IntelliJ IDEA, VS Code, or Eclipse).
- Maven or the Maven Wrapper included with the project.
- Basic knowledge of Java, SQL, primary keys, and dependency injection.

The examples use Spring Data JDBC APIs common across Spring Boot 3.x projects. When generating a project with Spring Initializr, select a stable Spring Boot version compatible with your JDK and let Initializr manage starter versions. The snippets focus on configuration and Spring Data JDBC usage rather than relying on a specific patch release.

## 2. What Is an Aggregate Root?

An **aggregate** is a cluster of data and domain objects treated as a single unit of consistency when changes occur. The **aggregate root** is the sole object through which external code makes modifications to that aggregate.

Consider two cases:

~~~text
Simple case: book catalog

Book (aggregate root)
├── id
├── title
└── price

More complex case: purchase order

PurchaseOrder (aggregate root)
├── id, customerId, status
├── OrderLine #1 (sku, quantity)
└── OrderLine #2 (sku, quantity)

Customer (separate aggregate root)
└── id, name
~~~

In the book example, the aggregate consists of **a single object**, making it the best starting point for learning repositories. In the order example, order lines belong to the order's lifecycle: to add or remove an order line, the application operates through `PurchaseOrder`. By contrast, customers have their own lifecycle; an order typically holds only `customerId` instead of treating the customer as a child entity of the order.

In Spring Data JDBC, key design principles include:

- **Every aggregate has one root**, which serves as the entry point to save and load the entire aggregate.
- Repositories are normally defined for **aggregate roots**. Child entities do not necessarily need their own repositories.
- Objects *owned by* an aggregate share the root's lifecycle. When saving the root, Spring Data JDBC executes database operations matching the aggregate mapping.
- Different aggregates usually reference each other by ID or `AggregateReference` to keep ownership boundaries clear.
- **There is no JPA-style persistence context or dirty checking.** Modifying an in-memory object does not automatically issue an `UPDATE`; you must call `save` to persist state.

**Do not think of an "aggregate root" merely as a class with `@Id`.** Choosing the root is a domain decision about change scope and consistency. `@Id` only helps Spring Data JDBC identify the database primary key.

## 4. Creating the Table and Connecting to H2

### 4.1. Creating `schema.sql`

Add `src/main/resources/schema.sql`:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    price DECIMAL(12, 2) NOT NULL
);
~~~

Meaning:

- `id` is a `BIGINT` primary key generated automatically by the database on insert.
- `title` is the book title and cannot be `NULL`.
- `price` stores exact decimal numbers, which is much better than `DOUBLE` for monetary amounts.

For this example, **table and column names are explicitly declared**. As mappings grow more complex, keep column naming explicit to avoid relying on default naming conversions.

### 4.2. Creating `application.yml`

Add `src/main/resources/application.yml`:

~~~yaml
spring:
  datasource:
    url: jdbc:h2:mem:catalogdb;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
    username: sa
    password:
  sql:
    init:
      mode: always

logging:
  level:
    org.springframework.jdbc.core: DEBUG
~~~

`spring.datasource.url` points to an in-memory H2 database. `DB_CLOSE_DELAY=-1` keeps the database alive when the last connection closes, until the Java process exits. `spring.sql.init.mode=always` instructs Spring Boot to execute SQL initialization scripts on startup. Enabling `DEBUG` logging lets you observe Spring JDBC activity; if the output is too verbose, you can omit the `logging` block.

**Spring Data JDBC does not automatically create tables from `@Table` like some Hibernate/JPA configurations do.** You must supply the schema. `schema.sql` is convenient for lessons; production projects usually manage schema changes with Flyway or Liquibase.

## 5. Writing the `Book` Aggregate Root

Create `src/main/java/com/example/catalog/domain/Book.java`:

~~~java
package com.example.catalog.domain;

import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public record Book(
        @Id Long id,
        String title,
        BigDecimal price
) {

    public Book {
        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException("Book title must not be blank");
        }
        if (price == null || price.signum() < 0) {
            throw new IllegalArgumentException("Book price must be >= 0");
        }
        title = title.strip();
    }

    public static Book newBook(String title, BigDecimal price) {
        return new Book(null, title, price);
    }

    public Book changePrice(BigDecimal newPrice) {
        return new Book(id, title, newPrice);
    }
}
~~~

### Understanding Each Part

**`@Table("books")`** specifies the table backing the aggregate root. The annotation comes from `org.springframework.data.relational.core.mapping.Table`, not `jakarta.persistence.Table`.

**`@Id`** marks the identifier property. With `Long id`, a `null` value in this model represents a new, unpersisted aggregate; the ID is generated by the database upon saving. The annotation is `org.springframework.data.annotation.Id`.

**The `Book` record** provides accessors `id()`, `title()`, and `price()` and models immutable data. Spring Data JDBC supports mapping immutable objects, including Java records. Therefore, updating the price produces a new `Book` instance instead of calling a setter.

**The compact constructor** enforces domain invariants for every `Book` created: the title must be non-blank and the price non-negative. Placing these rules inside the aggregate ensures both `newBook` and `changePrice` enforce them.

**`newBook`** creates an instance without an ID. **`changePrice`** preserves the existing ID while creating a new state for the repository to persist.

Note: Java checks inside the constructor **do not replace** database constraints. Here, both the class and the table enforce key invariants in ways appropriate to each layer.

### Why Choose `BigDecimal`?

`BigDecimal` represents decimal values accurately:

~~~java
BigDecimal price = new BigDecimal("149000.00");
~~~

Avoid `new BigDecimal(0.1)` because a `double` value can carry binary floating-point rounding errors. When handling real money, also standardize currency units, rounding rules, taxes, and storage precision.

## 6. Creating Your First Repository

Create `src/main/java/com/example/catalog/repository/BookRepository.java`:

~~~java
package com.example.catalog.repository;

import java.util.Optional;
import com.example.catalog.domain.Book;
import org.springframework.data.repository.CrudRepository;

public interface BookRepository extends CrudRepository<Book, Long> {

    Optional<Book> findByTitle(String title);
}
~~~

In just a few lines, you have a repository for the `Book` aggregate. The two generic type parameters mean:

- `Book`: the **aggregate root** type managed by the repository.
- `Long`: the primary key type matching `@Id Long id`.

`CrudRepository` provides common methods out of the box:

| Method | Purpose | Return Type |
|---|---|---|
| `save(Book entity)` | Inserts or updates an aggregate | `Book` |
| `findById(Long id)` | Finds by primary key | `Optional<Book>` |
| `findAll()` | Reads all aggregates | `Iterable<Book>` |
| `existsById(Long id)` | Checks whether an ID exists | `boolean` |
| `count()` | Counts aggregates | `long` |
| `deleteById(Long id)` | Deletes by ID | `void` |
| `delete(Book entity)` | Deletes the given aggregate | `void` |

`findByTitle(String title)` is a **derived query**. Spring Data parses the method name, recognizes the `title` property on `Book`, and generates the corresponding query. You do not need to write an implementation class, nor annotate the interface with `@Repository` because Spring Data creates the repository proxy automatically.

For `findByTitle` to work, the property name must match the Java model. If you rename `title` to `bookName`, update the method name accordingly—for example, `findByBookName`.

In Spring Data JDBC, repositories are backed by relational mapping and SQL infrastructure. This is **not** Spring Data JPA; no `EntityManager`, persistence context, or JPQL is involved.

## 7. Running the First CRUD Example

Open the main application file and put the following in `src/main/java/com/example/catalog/CatalogApplication.java`:

~~~java
package com.example.catalog;

import java.math.BigDecimal;
import com.example.catalog.domain.Book;
import com.example.catalog.repository.BookRepository;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class CatalogApplication {

    public static void main(String[] args) {
        SpringApplication.run(CatalogApplication.class, args);
    }

    @Bean
    CommandLineRunner demonstrateRepository(BookRepository repository) {
        return args -> {
            // 1. CREATE: a new object has id == null.
            Book newBook = Book.newBook(
                "Spring Data JDBC Basics",
                new BigDecimal("149000.00")
            );
            Book saved = repository.save(newBook);
            System.out.println("CREATED: " + saved);

            // 2. READ: look up by primary key.
            Book found = repository.findById(saved.id())
                .orElseThrow();
            System.out.println("FOUND: " + found);

            // 3. UPDATE: create new state, call save to persist.
            Book repriced = found.changePrice(
                new BigDecimal("129000.00")
            );
            Book updated = repository.save(repriced);
            System.out.println("UPDATED: " + updated);

            // 4. Derived query: look up by book title.
            System.out.println(
                "BY TITLE: " +
                repository.findByTitle("Spring Data JDBC Basics")
            );

            // 5. READ ALL: method inherited from CrudRepository.
            repository.findAll().forEach(
                book -> System.out.println("IN CATALOG: " + book)
            );

            // 6. DELETE and verify with Optional.empty().
            repository.deleteById(updated.id());
            System.out.println(
                "AFTER DELETE: " + repository.findById(updated.id())
            );
        };
    }
}
~~~

From the project root directory, run with the Maven Wrapper:

~~~powershell
.\mvnw.cmd spring-boot:run
~~~

On macOS/Linux:

~~~bash
./mvnw spring-boot:run
~~~

The application creates the table from `schema.sql`, Spring Data creates the `BookRepository` bean, and Spring Boot invokes the `CommandLineRunner`. Console output for this example will look like:

~~~text
CREATED: Book[id=1, title=Spring Data JDBC Basics, price=149000.00]
FOUND: Book[id=1, title=Spring Data JDBC Basics, price=149000.00]
UPDATED: Book[id=1, title=Spring Data JDBC Basics, price=129000.00]
BY TITLE: Optional[Book[id=1, title=Spring Data JDBC Basics, price=129000.00]]
IN CATALOG: Book[id=1, title=Spring Data JDBC Basics, price=129000.00]
AFTER DELETE: Optional.empty
~~~

The actual ID depends on database state; this example shows `1` when the table is newly created. With an in-memory H2 database as configured above, data is lost when the application exits. Because no web server dependency was added, the sample application **finishes running and exits**—that is normal behavior.

### Flow of a `save` Call

~~~mermaid
flowchart LR
    A["Book.newBook(...)\nid = null"] --> B["BookRepository.save(book)"]
    B --> C["Spring Data JDBC mapping"]
    C --> D["SQL INSERT"]
    D --> E[("books")]
    E --> F["Returned Book\nwith generated ID"]
~~~

For an update:

~~~mermaid
flowchart LR
    A["Book with existing ID"] --> B["changePrice(...)"]
    B --> C["repository.save(...)"]
    C --> D["SQL UPDATE by ID"]
    D --> E[("books")]
~~~

Both diagrams illustrate the basic flow. Actual SQL generated by the framework depends on mapping metadata, aggregate state, and mechanisms such as versioning if added.

## 8. Understanding the Aggregate Lifecycle on Save

### 8.1. Distinguishing New vs. Existing Objects

In our `Book` model:

~~~java
Book draft = Book.newBook("Practical Java", new BigDecimal("99000"));
System.out.println(draft.id()); // null

Book persisted = repository.save(draft);
System.out.println(persisted.id()); // ID generated by database
~~~

Because `Book` is an immutable record, **always use the instance returned by `save`**. Do not assume the `draft` variable now holds the generated ID.

By default, Spring Data JDBC determines whether an entity is new or existing based on its ID; if the model uses `@Version`, new-state detection also considers the version value. In this simple model with `Long id`, `null` denotes a new object.

### 8.2. No Dirty Checking Like JPA

An important rule:

~~~java
Book current = repository.findById(id).orElseThrow();
Book changed = current.changePrice(new BigDecimal("79000"));

// In the DB, the old price remains if you only construct 'changed'.
repository.save(changed); // Only now is the new state requested to be saved.
~~~

Spring Data JDBC does not "track" `current` or `changed` like a managed JPA entity. Calling `save` is an explicit persistence action. Even inside a `@Transactional` method, constructing a new object in memory never writes to the database automatically.

### 8.3. Do Not Treat `save` as a Generic "Upsert"

When an object is detected as new, the framework runs an insert path; when detected as existing, it runs an update path. **Do not expect that passing an arbitrary ID to `save` will insert a row if that row does not exist.** Whether the row exists, database constraints, and optimistic locking can all cause the update to fail.

### 8.4. Transactions in the Service Layer

A repository is the data-access unit. When a business operation requires multiple database operations to succeed together, place transaction boundaries in a **service**:

~~~java
package com.example.catalog.service;

import java.math.BigDecimal;
import java.util.NoSuchElementException;
import com.example.catalog.domain.Book;
import com.example.catalog.repository.BookRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class BookCatalogService {
    private final BookRepository repository;

    public BookCatalogService(BookRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Book changePrice(long id, BigDecimal newPrice) {
        Book book = repository.findById(id)
            .orElseThrow(() ->
                new NoSuchElementException("Book not found: " + id));

        return repository.save(book.changePrice(newPrice));
    }
}
~~~

This service is an optional extension; if added to the project, place it in its own file under the `service` package. Spring Boot detects `@Service` automatically under the base package.

`@Transactional` ensures compatible operations participate in the same transaction when called through the Spring bean/proxy. In standard JDBC environments, Spring manages transactions over a JDBC connection. A method calling another `@Transactional` method **within the same object** directly may bypass the proxy and thus fail to activate the transaction as expected.

Under concurrent updates, two tasks can read the same old price and overwrite each other. When business logic needs conflict detection, explore **`@Version` / optimistic locking** and add a matching version column to the table. A transaction alone does not replace a concurrency control strategy.

## 9. From One Table to a Multi-Entity Aggregate

Book is a single-table aggregate. To understand Spring Data JDBC's mindset thoroughly, let's expand to an example of **a purchase order with multiple order lines**. This section illustrates design principles; you do not need to add it to the book catalog project you just ran.

### 9.1. Ownership Model

~~~text
PurchaseOrder [root, table purchase_orders]
  └── Set<OrderLine> [children, table order_lines]

Data relationship:

purchase_orders.id
         │
         └── order_lines.order_id
~~~

Suppose an order contains multiple line items. `PurchaseOrder` is the root. `OrderLine` belongs inside the aggregate: it must not be saved arbitrarily via an independent repository that bypasses the order's business rules.

### 9.2. Mapping with `@MappedCollection`

~~~java
import java.util.Set;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        Long customerId,
        @MappedCollection(idColumn = "order_id")
        Set<OrderLine> lines
) {
}

@Table("order_lines")
public record OrderLine(
        @Id Long id,
        String sku,
        int quantity
) {
}
~~~

These are **two Java types**, so in a real project place them in two separate files `PurchaseOrder.java` and `OrderLine.java` (or declare them according to the one-public-top-level-type-per-file rule). Add the appropriate package and imports. `OrderLine` is mapped by Spring Data JDBC as a child entity, needing no `orderId` property on the class; `idColumn = "order_id"` specifies the foreign key column on the child table.

The corresponding schema might look like:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INT NOT NULL,
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

For this aggregate, the repository is:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

**There is no need to create `OrderLineRepository`** when all order line modifications go through the order. The root should expose methods such as `addLine`, `changeQuantity`, and `removeLine` to protect domain invariants; the record snippet above shows mapping only and does not implement those rules yet.

An important operational detail: when updating an aggregate with a child collection, Spring Data JDBC may **delete and re-insert child rows** according to its aggregate persistence strategy, rather than performing field-level dirty checking like JPA. Therefore, do not build massive aggregates just to map every related table. Keeping aggregate boundaries small and cohesive makes save behavior clear and avoids unnecessary SQL work.

If order line sequence matters, consider using `List` with `keyColumn` mapping and a position column. `Set` does not guarantee display ordering.

### 9.3. Referencing Another Aggregate by ID

In `PurchaseOrder`, `customerId` references a separate aggregate. This is usually the simplest, clearest choice:

~~~java
Long customerId; // Holds only the identifier; does not own Customer
~~~

Spring Data Relational also offers `AggregateReference<Customer, Long>` to represent aggregate references in the domain model without turning `Customer` into a child entity cascaded with the order.

Avoid placing a `Customer` object inside `PurchaseOrder` in a way Spring Data JDBC interprets as ownership merely because the database has a foreign key. **A foreign key is a data structure; aggregate ownership is a domain decision.** Another aggregate root has its own repository and lifecycle.

## 10. Extending the Repository When CRUD Is Not Enough

`CrudRepository` handles standard operations. When custom queries are required, Spring Data JDBC supports **derived queries** or explicit SQL.

Example adding a method to `BookRepository`:

~~~java
import java.math.BigDecimal;
import java.util.List;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.query.Param;

@Query("""
       SELECT id, title, price
       FROM books
       WHERE price >= :minPrice
       ORDER BY price
       """)
List<Book> findBooksFromPrice(@Param("minPrice") BigDecimal minPrice);
~~~

This is an **additional method inside the `BookRepository` interface**, not a standalone method outside the interface. The SQL in `@Query` is for Spring Data JDBC and returns columns matching the `Book` mapping directly. The named parameter `:minPrice` binds to `@Param("minPrice")`.

For reporting queries involving multiple JOINs or reading into DTOs, using `JdbcTemplate`/`NamedParameterJdbcTemplate` alongside Spring Data JDBC is also a sound choice. Repositories manage aggregates, while custom SQL serves read views without bloating an aggregate.

**Do not add query methods merely to duplicate built-in CRUD operations:** `findById`, `findAll`, `count`, and `deleteById` are already inherited. Keep your first repository simple and extend it only as real needs arise.

## 11. Common Mistakes in Your First Exercise

| Symptom | Common Cause | How to Fix |
|---|---|---|
| Table `BOOKS`/`books` not found error | `schema.sql` not created or not executed; mismatched table name | Check `src/main/resources/schema.sql`, `spring.sql.init.mode`, and `@Table("books")` |
| `No qualifying bean of type BookRepository` | Missing JDBC starter or repository is outside the scan package | Check dependencies and keep packages under `com.example.catalog` |
| Cannot connect to H2 | Missing H2 dependency or wrong URL/driver | Check runtime dependency and `spring.datasource.url` |
| Accidentally using `jakarta.persistence.Id` or `@Entity` | Mixing JPA annotations with Spring Data JDBC | Use `org.springframework.data.annotation.Id` and `org.springframework.data.relational.core.mapping.Table` |
| Calling `save`, yet the old record variable still has `id == null` | Records are immutable; the return value is the persisted instance | Assign `Book saved = repository.save(book)` |
| Modified object, yet database did not change | Spring Data JDBC has no dirty checking | Call `repository.save(changedBook)` |
| Updating an entity with an arbitrary assigned ID fails | Row does not exist or framework took the update path | Clearly separate creation and update; use actual IDs or configure appropriate new-entity detection |
| Updating a large aggregate generates many SQL statements | Child collections follow the root's lifecycle and may be deleted/reinserted | Shrink aggregate boundaries, observe SQL, and design write operations appropriately |
| Data disappears when the application stops | `jdbc:h2:mem:...` exists only inside the JVM | Use file-backed H2 or a persistent database if data must survive restarts |

### Three Questions to Check Your Understanding

**1. Why does `BookRepository` declare `Long`?** Because `Book.id` has type `Long`. The ID type is part of the `CrudRepository<Book, Long>` contract.

**2. Why does `save` return a new object?** Spring Data JDBC may need to populate a database-generated ID, a version, or values transformed during persistence. With immutable records, those updated values are represented by the returned instance.

**3. If `OrderLine` is a child entity, does it need its own repository?** Normally no. When order lines belong to the `PurchaseOrder` aggregate, modifications go through the root and `PurchaseOrderRepository` to enforce order invariants.

## 12. Next Steps

After your first example, you can grow the application in this sequence:

1. Add a **service** for read/write business operations and place `@Transactional` at sensible boundaries.
2. Add an **HTTP controller** if exposing a REST API; add `spring-boot-starter-web` when doing so.
3. Add **`@Version`** to the aggregate root and a version column to the table to explore optimistic locking.
4. Build a multi-entity aggregate with `@MappedCollection`, paying attention to lifecycle and child collection update costs.
5. Swap H2 for PostgreSQL or MySQL and manage schemas with migrations while keeping the same repository principles.
6. Write dedicated read queries when screen projections do not align with aggregate boundaries.

Key takeaway from this lesson: **the repository is the gateway to the aggregate root**, `@Id` provides database identity, `@Table` defines the mapping, and `save` expresses explicit intent to persist state. From a simple `Book`, you now have the foundation to build richer aggregates while keeping domain boundaries and data access clear.
