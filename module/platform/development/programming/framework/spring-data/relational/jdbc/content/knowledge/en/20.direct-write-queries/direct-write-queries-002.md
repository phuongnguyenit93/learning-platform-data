# Return Types and Affected Row Counts

In **Spring Data JDBC**, when declaring a direct write query with `@Query`, the `@Modifying` annotation tells Spring Data that the SQL statement is a data-modifying operation such as `UPDATE` or `DELETE`. The method's return type determines whether the application receives the **affected row count** or ignores that information.

Typically, the method can return `int`/`Integer` to receive the number of rows reported by the database as updated or deleted, or return `void` if the caller does not need this count. The count helps the application service know whether a command affected any data, affected exactly one row as expected, or affected multiple rows. It is **not** the updated entity, nor does it automatically supply a generated ID or the new state of the aggregate.

## 1. `@Query` and `@Modifying` Solve Two Different Things

`@Query` declares the SQL to execute. `@Modifying` marks that the method runs a data-modifying SQL statement rather than a query that reads a result set.

Example entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email,
        boolean active
) {}
```

DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    active BOOLEAN NOT NULL
);
```

Repository:

```java
import org.springframework.data.jdbc.repository.query.Modifying;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface CustomerRepository extends CrudRepository<Customer, Long> {

    @Modifying
    @Query("UPDATE customers SET active = :active WHERE id = :id")
    int updateActive(
            @Param("id") Long id,
            @Param("active") boolean active
    );
}
```

The two annotations have separate roles:

- `@Query`: supplies the SQL statement and bound parameters.
- `@Modifying`: instructs execution via the write-operation path to obtain an update count, rather than mapping an entity result set.

`@Modifying` belongs to the `org.springframework.data.jdbc.repository.query` package. Do not confuse it with the annotation of the same name in the Spring Data JPA module.

## 2. Return Type `int`: Receiving the Updated Row Count

When calling:

```java
int affected = customerRepository.updateActive(42L, false);
```

Spring Data JDBC executes the equivalent SQL:

```sql
UPDATE customers
SET active = ?
WHERE id = ?;
```

The database/JDBC returns the update count, and the method returns that number to the caller. Common cases:

| Reported row count | Common interpretation |
|---:|---|
| `0` | No rows were counted as affected by the statement. |
| `1` | One row was affected. |
| Greater than `1` | Multiple rows were affected; appropriate for bulk commands, but unexpected if the use case targets a single root. |

For example, if ID `42` exists and the update is performed, the result is usually `1`. If there is no row with ID `42`, the result is `0`.

**Note:** how the driver/database computes the update count for `UPDATE` can differ when the new value equals the old value. Some database engines report the number of matched rows, while some configurations/drivers report the number of rows actually changed. Therefore, `0` should be interpreted according to the database in use; it does not prove in every system that the ID does not exist.

## 3. Return Type `void`: Ignoring the Affected Row Count

If the caller does not need to know the row count, the method can be declared to return nothing:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
void deactivate(@Param("id") Long id);
```

Call:

```java
customerRepository.deactivate(42L);
```

The application simply asks to execute the statement. If you need to distinguish the case where no row was updated, a `void` method does not give the caller a count to inspect.

Choose `void` when:

- The use case does not care how many rows were affected.
- The system only needs to run the operation and handle SQL errors if any occur.
- The result is not used to decide the next business step.

Choose `int` when:

- You need to know whether the operation affected any row.
- You need to confirm that exactly one row was updated.
- You need to measure or report the number of modified rows in a bulk operation.
- You need to detect an optimistic locking conflict represented by an update count of `0`.

## 4. `Integer` and Other Return Types

For modifying queries, commonly supported return types are `void`, `int`, or `Integer` (depending on the Spring Data JDBC API/version). `int` is usually the simplest choice because a JDBC update count is an integer and the method always returns a number when the operation completes normally.

Do not arbitrarily declare `boolean`, `long`, `Optional<Integer>`, or an entity intending to receive an update count. That is not the standard contract for a modifying query method. If the application wants a boolean result, receive `int` and convert it in the service layer:

```java
boolean updated = customerRepository.updateActive(id, false) == 1;
```

If a specific Spring Data JDBC version has different signature constraints, follow the documentation/API of the version you are using. Avoid relying on the framework coercing `int` into an arbitrary return type.

## 5. Affected Row Count Is Not the Row Count from `SELECT`

Two operations can both return `int` or `long`, but their meanings differ:

### `SELECT COUNT(*)`

```java
@Query("SELECT COUNT(*) FROM customers WHERE active = TRUE")
long countActiveCustomers();
```

This is a read query. The database returns the **value of the `COUNT(*)` expression**; for example, if there are 25 active customers, the result is `25`.

### `UPDATE` with `@Modifying`

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE active = TRUE")
int deactivateAllActiveCustomers();
```

This is a write query. `int` is the **statement's update count**, for example 25 rows reported as updated. The method does not return the modified `Customer` rows.

| Characteristic | `COUNT(*)` | `@Modifying` update count |
|---|---|---|
| SQL type | `SELECT` | `UPDATE`, `DELETE`, or appropriate DML |
| Meaning of returned number | Number of rows satisfying the count condition | Number of rows the database/JDBC reports as affected |
| Modifies data? | No | Yes |
| How declared | Scalar-reading `@Query` | `@Modifying` combined with `@Query` |

Do not put `@Modifying` on a `SELECT COUNT(*)` query just because its result is an integer.

## 6. Using Update Count to Control a Single Operation

Suppose a use case only allows deactivating an active customer. You can put the status condition in SQL:

```java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE id = :id AND active = TRUE
    """)
int deactivateIfActive(@Param("id") Long id);
```

The application service interprets the update count:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public boolean deactivate(Long id) {
        int affected = customers.deactivateIfActive(id);

        if (affected > 1) {
            throw new IllegalStateException(
                    "Expected at most one customer, got " + affected);
        }

        return affected == 1;
    }
}
```

With `id` as the primary key, the expected valid result is `0` or `1`:

- `1`: one row satisfied the condition and was updated.
- `0`: no row was counted as affected; either the ID does not exist or the customer is already inactive.
- Greater than `1`: impossible if the condition uses a true primary key and the schema matches expectations; if it happens, investigate assumptions/schema/SQL.

The method returns `boolean` in the **application service**, not on the modifying repository method. The service translates the row count into an appropriate business outcome.

If you need to distinguish `NOT_FOUND` from `ALREADY_INACTIVE`, a single `0` does not carry enough information. You can read the state before or after using an appropriate transaction/locking strategy, or design a different business result. Do not assign a single meaning to `0` when the SQL has multiple reasons why no row matched.

## 7. Using Update Count for Bulk Operations

For an administrative task, you might need to deactivate all customers who have been inactive for a period of time:

```java
@Modifying
@Query("""
    UPDATE customers
    SET active = FALSE
    WHERE last_seen_at < :cutoff
      AND active = TRUE
    """)
int deactivateInactiveCustomers(@Param("cutoff") LocalDateTime cutoff);
```

The caller receives the number of rows the database reports as affected:

```java
int affected = customerRepository.deactivateInactiveCustomers(cutoff);
log.info("Deactivated {} customers", affected);
```

In a bulk update, a value greater than `1` is normal. It indicates the scope of affected data, not an error. However, consider:

- Does the `WHERE` condition restrict to the exact target set?
- Does the update bypass aggregate state transition rules?
- Do `version`, `updated_at`, or audit columns also need updating?
- Are caches, search indexes, outboxes, or read models affected?
- Will the transaction hold locks too long or create lock contention?
- Is the update count meaningful under the running driver/database?

Bulk DML can be more efficient than loading each aggregate and calling `save`, but it also skips many mechanisms of the normal aggregate save path. Only use it when business rules and related side effects have been handled intentionally.

## 8. `@Modifying` Does Not Manage the Transaction Boundary Automatically

`@Modifying` marks the query execution mode; it does not replace `@Transactional`. If a use case comprises multiple operations that must commit or roll back together, place the transaction on the application service:

```java
@Transactional
public void closeCustomerAndRecordAudit(Long id) {
    int affected = customers.deactivateIfActive(id);

    if (affected != 1) {
        throw new IllegalStateException("Customer was not deactivated");
    }

    auditRepository.save(new AuditEntry(id, "DEACTIVATED"));
}
```

If writing the audit fails and both operations share the same transaction manager/database transaction, the deactivation change can roll back together with the audit operation. Without a shared transaction, data can end up in a partial state.

A repository method declaring a custom query should not be assumed to already have the right transaction scope for every use case. Placing `@Transactional` on the service where the business boundary is defined usually makes intent clearer. If needed, transactions can be configured directly on repository methods, but avoid scattering transaction boundaries without reason.

## 9. `@Modifying` and Optimistic Locking: Including Version Manually in SQL

With `repository.save(aggregate)` on an entity that has `@Version`, Spring Data JDBC applies optimistic locking automatically from metadata. However, a handwritten `@Modifying` `UPDATE` statement **does not automatically get a version condition added** just because the entity has a `@Version` property.

Suppose the `invoices` table has a `version` column and the entity uses `@Version`. A modifying query that needs version control must write the condition itself:

```java
@Modifying
@Query("""
    UPDATE invoices
    SET status = :status,
        version = version + 1
    WHERE id = :id
      AND version = :expectedVersion
    """)
int updateStatusIfVersionMatches(
        @Param("id") Long id,
        @Param("expectedVersion") Long expectedVersion,
        @Param("status") String status
);
```

Interpreting the result:

- `1`: one row matched the ID and old version, updated successfully, and version incremented.
- `0`: no row matched; either the ID does not exist or the version has changed.
- Greater than `1`: abnormal if `id` is the primary key.

The service can translate `0` into a conflict error:

```java
int affected = invoices.updateStatusIfVersionMatches(id, expectedVersion, "PAID");

if (affected == 0) {
    throw new OptimisticLockingFailureException(
            "Invoice was changed or no longer exists");
}
```

This is a self-implemented mechanism; the application must ensure the version increments properly, keep an appropriate transaction, and interpret mismatches. Unless custom SQL is specifically required, using `findById`, mutating the aggregate, and calling `save` is usually safer because Spring Data JDBC manages optimistic locking on the standard save path.

## 10. `@Modifying` Does Not Return the Updated Entity

A method such as:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
int deactivate(@Param("id") Long id);
```

only returns the affected row count. It does not return a new `Customer`, does not automatically update any `Customer` object in memory, and does not provide generated keys.

If you need the object after updating, you can read it back:

```java
int affected = customers.deactivate(id);

if (affected == 0) {
    return Optional.empty();
}

return customers.findById(id);
```

Place both steps inside a transaction if the use case needs consistency between update and read. If you need to return the updated row in a single statement using syntax such as `UPDATE ... RETURNING` supported by some databases, do not assume a modifying query method will map that result set into an entity; the `@Modifying` path is designed to execute DML and receive an update count. Use a custom repository fragment with `JdbcTemplate`/`NamedParameterJdbcTemplate` and a `RowMapper` if you need to process a returned result set, or update and re-query as appropriate.

## 11. Generated IDs Differ from Update Counts

When inserting a new aggregate via `repository.save`, the application often needs the database-generated ID:

```java
Customer saved = customers.save(
        new Customer(null, "Lan", "lan@example.com", true)
);

Long id = saved.id();
```

The returned object contains the ID received via the generated-key mechanism. That is the contract of the aggregate save operation.

By contrast, a DML method returning `int` reports the number of affected rows. For example, an `INSERT` executed through a modifying query can return an update count, but the number `1` is not the generated ID. If you need a generated ID, use `save` or a custom JDBC implementation that explicitly handles generated keys.

| Information | How to obtain |
|---|---|
| New aggregate ID | Use the object returned from `repository.save(...)` |
| New aggregate version | Use the object returned from `save` when the root has `@Version` |
| Rows affected by DML | `int`/`Integer` return type of a modifying query |
| Entity after custom DML | Re-read or use a custom JDBC mapper/result-set path |

## 12. Direct DML Can Bypass Aggregate Rules

Spring Data JDBC designs repositories around the aggregate root. When calling `save(root)`, the framework uses metadata for the root and its child components belonging to the aggregate. A direct SQL `UPDATE` only affects the columns/rows named in the statement.

For example:

```sql
UPDATE customers
SET active = FALSE
WHERE city = 'Da Nang';
```

This query does not call a domain method `customer.deactivate()`, does not load each aggregate, and does not automatically handle per-customer side effects. It can bypass:

- Invariants checked inside the aggregate root.
- `@Version` update logic if not written explicitly in SQL.
- Auditing/callbacks attached to the standard aggregate save path.
- Updates to dependent child tables or read models.
- Writing outbox/events or audit records required by the use case.

This does not mean direct DML is always wrong. It fits bulk operations with clear rules, data that does not require per-aggregate processing, or controlled administrative tasks. Before using it, identify what behaviors are normally performed when saving the aggregate and handle what is needed explicitly.

## 13. Update Count When Using `DELETE`

`@Modifying` can also be used for `DELETE` statements:

```java
@Modifying
@Query("DELETE FROM customers WHERE active = FALSE")
int deleteInactiveCustomers();
```

The method returns the number of rows the database reports as deleted. The caller can log or check the count:

```java
int deleted = customers.deleteInactiveCustomers();
log.info("Deleted {} inactive customers", deleted);
```

If the table has foreign keys, the command can be rejected by the database or trigger cascades depending on the DDL. The update count typically reflects rows affected by the direct statement; do not assume it sums all rows cascaded across related tables. Check the specific behavior of your DBMS.

For an aggregate with children, deleting the root table directly can leave orphan children without proper cascades or cleanup. Use the root repository or intentionally design SQL/DDL so the entire aggregate is handled correctly.

## 14. Cases Where `0` Requires Careful Interpretation

An update count of `0` can happen for several reasons:

1. No row matches the `WHERE` condition.
2. The row does not exist.
3. The row exists but fails the current-state condition, such as already being inactive.
4. The version in the optimistic locking condition no longer matches.
5. The database/driver is configured to report actually modified rows and the new value equals the existing value.

Therefore, do not write:

```java
if (affected == 0) {
    throw new CustomerNotFoundException(id);
}
```

unless the SQL and database semantics guarantee `0` can only occur when no customer exists. If the statement also checks `active = TRUE`, a result of `0` may mean the customer exists but is no longer active.

Design a clear business contract:

```java
public enum DeactivationResult {
    DEACTIVATED,
    ALREADY_INACTIVE_OR_NOT_FOUND
}
```

If you need to distinguish the last two states, add a read step or use a SQL/transaction strategy that supplies sufficient information. A single update count carries no more meaning than the number it represents.

## 15. Inspecting SQL and Update Counts in Development

You can enable Spring JDBC logging to observe the SQL and bound parameters:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

When verifying a modifying query, record:

- The actual SQL and `WHERE` condition.
- Values/types of bound parameters.
- The row count returned by the method.
- Whether the transaction committed or rolled back.
- The database values when read back after the operation.

Do not rely solely on the update count to conclude data is persisted. If the method runs inside a transaction that later rolls back, the row count affected inside that transaction does not mean the final change was committed.

Bind-parameter logs can contain emails, personal information, or business data. Enable verbose logging only in development/controlled environments and turn it off when not needed.

## 16. Common Pitfalls

| Symptom | Common cause | Resolution |
|---|---|---|
| `@Query` update method does not run via DML path | Missing `@Modifying` | Mark the method as a modifying query |
| Want row count, but method returns `void` | Method contract discards the update count | Change to `int`/`Integer` if needed |
| Declared `boolean` for success/failure | Return type is not a common update count contract | Return `int` and convert to boolean in the service |
| Result `0` always treated as nonexistent | `WHERE` has extra status/version conditions or driver has specific semantics | Interpret according to conditions and DBMS |
| Result unexpectedly greater than `1` | Non-unique condition or missing filter | Check `WHERE`, unique constraints, and bulk intent |
| Expected method to return the new entity | Modifying queries return update counts, not mapped entities | Re-query or use a custom mapper for result sets |
| New ID confused with update count | Confusing generated keys with row counts | Use `save` to obtain IDs; DML count is only row count |
| `@Version` does not prevent overwrites | Custom SQL does not check/increment version | Add version predicate and increment manually or use `save` |
| Data changed even though later use-case step failed | Transaction does not span all operations | Place `@Transactional` on the application service |
| Children left behind after bulk delete/update | Direct DML does not manage the aggregate graph | Handle children/cascades and invariants explicitly |

## 17. Practice Exercise: Observing Affected Row Counts

Using the `customers` table, load test data:

```sql
INSERT INTO customers (name, email, active) VALUES
    ('Lan', 'lan@example.com', TRUE),
    ('Minh', 'minh@example.com', TRUE),
    ('Hoa', 'hoa@example.com', FALSE);
```

Declare three methods:

```java
@Modifying
@Query("UPDATE customers SET active = FALSE WHERE id = :id")
int deactivateById(@Param("id") Long id);

@Modifying
@Query("UPDATE customers SET active = FALSE WHERE active = TRUE")
int deactivateAllActive();

@Modifying
@Query("DELETE FROM customers WHERE active = FALSE")
int deleteInactive();
```

Try in order:

1. Call `deactivateById` with an existing ID; record the update count.
2. Call it again with a nonexistent ID; observe the `0` result.
3. Call `deactivateAllActive`; observe that the affected row count can be greater than `1`.
4. Call `deleteInactive`; observe the deleted row count and inspect the data afterward.
5. Change `deactivateById` to `void`; confirm the caller no longer receives the update count.
6. Execute an update inside a transaction and intentionally cause an error afterward; inspect the database after rollback to see that an update count before rollback does not prove the change committed.

Run these experiments on a dedicated learning database, not real data. Compare results against your database/driver because update-count semantics can vary in certain cases.

## 18. Key Principles to Remember

- Use `@Query` to declare SQL and `@Modifying` to mark a data-modifying query.
- `int`/`Integer` receives the update count; `void` discards that number.
- The update count is the number of rows the database/JDBC reports as affected, not an entity or generated ID.
- `0`, `1`, and values greater than `1` must be interpreted according to the `WHERE` condition, single/bulk intent, and database semantics.
- `SELECT COUNT(*)` returns a count value; a modifying query returns an update count. The two numbers have different origins.
- `@Modifying` does not automatically create a transaction boundary, update in-memory entities, or apply optimistic locking to handwritten SQL.
- If you need the entity after DML, re-read it or use an appropriate custom JDBC result mapping path.
- Direct DML can bypass aggregate behavior, auditing/callbacks, child updates, and side effects; handle those requirements intentionally.
- Use `repository.save` when you need standard aggregate persistence, generated IDs, and Spring Data JDBC–managed optimistic locking.

In Spring Data JDBC, choose a write query's return type based on what the use case needs. `void` fits when you only need execution; `int`/`Integer` fits when you need to know how many rows were affected and check the outcome. Combine update counts with clear `WHERE` conditions, appropriate transaction boundaries, and an understanding of optimistic locking to avoid over-interpreting a simple count as a definitive business conclusion.
