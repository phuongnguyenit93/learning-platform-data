# Tải lại dữ liệu được trigger hoặc giá trị mặc định sinh ra

Trong cơ sở dữ liệu quan hệ, một số giá trị được tạo hoặc thay đổi ngay bên trong database thay vì do Java cung cấp. Ví dụ:

- Cột `created_at` có `DEFAULT CURRENT_TIMESTAMP`.
- Trigger tự tạo mã kiểm toán khi một đơn hàng được insert.
- Trigger cập nhật `updated_at` sau mỗi lần update.
- Cột generated lưu kết quả của một biểu thức database.

Khi Spring Data JDBC gọi `repository.save(entity)`, database có thể đã lưu những giá trị đó, nhưng object Java trả về không tự động được tải lại toàn bộ để phản ánh mọi thay đổi do trigger/default tạo ra. Nếu ứng dụng cần sử dụng giá trị mới ngay sau khi ghi, cần **đọc lại aggregate từ database**.

Spring Data Relational cung cấp `@ReadOnlyProperty` để đánh dấu property do database quản lý: Spring Data không ghi property đó trong các thao tác persistence, nhưng vẫn đọc nó khi materialize entity. Bài học này giải thích cách kết hợp annotation với DDL, trigger, repository và transaction để đồng bộ trạng thái Java với dữ liệu thực tế.

## 1. Vì sao object sau save có thể chưa phản ánh database?

Giả sử ứng dụng tạo một đơn hàng:

```java
PurchaseOrder order = new PurchaseOrder("PO-2026-001");
PurchaseOrder saved = repository.save(order);
```

Database tự tạo:

- ID từ cột identity.
- Thời điểm tạo từ default.
- Mã audit từ trigger.
- Thời điểm cập nhật từ trigger.

Spring Data JDBC có thể lấy và gán **ID được sinh cho cột định danh** vào object trả về. Framework cũng quản lý giá trị `@Version` nếu aggregate sử dụng optimistic locking. Tuy nhiên, Spring Data JDBC **không tự động reload toàn bộ entity sau khi ghi** chỉ để lấy mọi giá trị khác do database sinh ra.

Do đó, có thể xảy ra trạng thái:

```text
Trong database sau INSERT:
id          = 101
created_at  = 2026-11-13T09:15:00Z
updated_at  = 2026-11-13T09:15:00Z
audit_token = PO-101

Object Java trả về từ save():
id          = 101
createdAt   = null
updatedAt   = null
auditToken  = null
```

Ví dụ trên minh họa sự khác nhau giữa ID được Spring Data JDBC lấy từ generated key và các cột khác được database tự tạo. Muốn sử dụng những cột sau, ứng dụng cần truy vấn lại.

**Nguyên tắc:** `save()` xác nhận thao tác persistence và trả về aggregate đã được xử lý theo cơ chế mapping; nó không đồng nghĩa với một lệnh refresh toàn bộ trạng thái từ database.

## 2. @ReadOnlyProperty: đọc từ database nhưng không ghi

Annotation `@ReadOnlyProperty` thuộc Spring Data Commons:

```java
import org.springframework.data.annotation.ReadOnlyProperty;
```

Ý nghĩa:

- Property được đọc khi Spring Data materialize entity từ database.
- Property không được Spring Data ghi xuống database trong thao tác insert/update.
- Giá trị của property có thể được database tạo bằng default, trigger hoặc generated column.

Ví dụ:

```java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @ReadOnlyProperty
    @Column("created_at")
    private Instant createdAt;

    @ReadOnlyProperty
    @Column("audit_token")
    private String auditToken;
}
```

`@Column` xác định tên cột vật lý. `@ReadOnlyProperty` cho biết Spring Data không ghi các property đó.

Đây là lựa chọn phù hợp khi **database là nơi sở hữu giá trị** và ứng dụng chỉ cần đọc giá trị đã được database tính toán.

### 2.1. @ReadOnlyProperty không có nghĩa là @Transient

Hai annotation có semantics khác nhau:

| Annotation | Ghi xuống database | Đọc từ database | Mục đích |
| --- | --- | --- | --- |
| `@ReadOnlyProperty` | Không | Có | Property do database quản lý, ứng dụng cần đọc. |
| `@Transient` | Không | Không | Property chỉ tồn tại trong Java, không thuộc mapping persistence. |

Nếu dùng `@Transient` cho `createdAt`, Spring Data sẽ bỏ qua property đó trong mapping; khi đọc aggregate, framework cũng không lấy giá trị từ cột `created_at`.

Vì vậy, với giá trị được tạo bởi trigger/default và cần trả về cho ứng dụng, `@ReadOnlyProperty` mới là annotation phù hợp.

### 2.2. @ReadOnlyProperty áp dụng cho collection

Annotation cũng có thể được dùng với property là entity hoặc collection entity. Trong trường hợp đó, Spring Data không thực hiện insert, delete hoặc update cho các row tương ứng.

Vì vậy, đừng đánh dấu nhầm một collection entity con cần được aggregate quản lý là read-only chỉ vì một vài cột trong bảng con được database tạo. Nếu chỉ một property như `createdAt` cần database sở hữu, hãy đánh dấu property đó thay vì đánh dấu cả collection.

## 3. Default của database và cách tránh ghi đè giá trị mặc định

Giả sử bảng có cột:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Database có thể tự đặt `created_at` khi insert **nếu câu INSERT không cung cấp giá trị cho cột đó hoặc yêu cầu DEFAULT**.

Nếu ứng dụng gửi một giá trị NULL tường minh, default không nhất thiết được áp dụng; database có thể lưu NULL hoặc từ chối do constraint NOT NULL.

Đó là lý do cần đánh dấu property được database quản lý bằng `@ReadOnlyProperty`:

```java
@ReadOnlyProperty
@Column("created_at")
private Instant createdAt;
```

Spring Data JDBC bỏ property khỏi thao tác ghi, để database áp dụng default. Khi aggregate được đọc sau đó, property vẫn được mapping từ cột `created_at`.

**Không nên chỉ để field Java bằng null rồi hy vọng mọi driver/database tự bỏ cột khỏi INSERT.** Hãy biểu diễn ownership của cột rõ ràng bằng mapping metadata và kiểm tra SQL thực tế nếu cần.

## 4. Trigger tạo hoặc cập nhật giá trị

Trigger có thể chạy khi insert/update để gán những giá trị mà ứng dụng không tự tính.

Ví dụ PostgreSQL:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(50) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    audit_token VARCHAR(80) NOT NULL
);

CREATE OR REPLACE FUNCTION set_purchase_order_audit()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        NEW.audit_token := 'PO-' || NEW.id::text;
    END IF;

    NEW.updated_at := CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_purchase_orders_audit
BEFORE INSERT OR UPDATE ON purchase_orders
FOR EACH ROW
EXECUTE FUNCTION set_purchase_order_audit();
```

Trigger trong ví dụ:

- Khi INSERT, tạo `audit_token` dựa trên ID.
- Khi INSERT hoặc UPDATE, gán `updated_at`.
- `created_at` dùng default của database.
- Các giá trị được xác định ở database, không cần Java truyền vào.

Với PostgreSQL, giá trị identity/default được áp dụng trước khi trigger BEFORE xử lý row mới, nên trigger có thể dùng `NEW.id` trong ví dụ này. Cú pháp trigger và thứ tự xử lý cần điều chỉnh nếu dùng MySQL, SQL Server, Oracle hoặc database khác.

Java entity:

```java
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;

    @ReadOnlyProperty
    @Column("created_at")
    private Instant createdAt;

    @ReadOnlyProperty
    @Column("updated_at")
    private Instant updatedAt;

    @ReadOnlyProperty
    @Column("audit_token")
    private String auditToken;

    protected PurchaseOrder() {
    }

    public PurchaseOrder(String orderNumber) {
        this.orderNumber = orderNumber;
    }

    public Long getId() {
        return id;
    }

    public String getOrderNumber() {
        return orderNumber;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }

    public Instant getUpdatedAt() {
        return updatedAt;
    }

    public String getAuditToken() {
        return auditToken;
    }
}
```

Các property database-managed được đánh dấu read-only. Khi Spring Data JDBC insert/update root, những cột này không được gửi như giá trị do ứng dụng sở hữu. Khi đọc root, các giá trị từ database được gán vào entity.

## 5. Tải lại aggregate sau khi save

Với repository:

```java
import org.springframework.data.repository.ListCrudRepository;

public interface PurchaseOrderRepository
        extends ListCrudRepository<PurchaseOrder, Long> {
}
```

Cách tạo mới và lấy dữ liệu trigger/default:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder createAndReload(String orderNumber) {
        PurchaseOrder saved = orders.save(
            new PurchaseOrder(orderNumber)
        );

        return orders.findById(saved.getId())
            .orElseThrow(() ->
                new IllegalStateException(
                    "Không tìm thấy đơn hàng vừa tạo"
                )
            );
    }
}
```

Luồng xử lý:

1. Tạo object Java với các property do database quản lý chưa có giá trị.
2. Gọi `orders.save`.
3. Spring Data JDBC thực hiện INSERT; database áp dụng default và trigger.
4. Spring Data JDBC nhận ID được sinh cho root và trả về object đã lưu.
5. Service dùng ID đó gọi `findById`.
6. Spring Data JDBC đọc lại row, ánh xạ các property `@ReadOnlyProperty` và trả aggregate có giá trị mới.

Kết quả trả về từ `createAndReload` có thể chứa `createdAt`, `updatedAt` và `auditToken` mà database đã sinh.

### 5.1. Vì sao dùng ID từ object trả về?

Với ID auto-increment/identity, Spring Data JDBC lấy generated key trong quá trình insert. Hãy dùng ID từ object `saved`:

```java
PurchaseOrder saved = orders.save(order);
Long id = saved.getId();
```

Không giả định rằng object đầu vào luôn được cập nhật tại chỗ. Với domain object bất biến, framework có thể trả về instance mới có ID được gán.

### 5.2. Không có repository refresh() như JPA

Spring Data JDBC không có persistence context giống JPA/Hibernate và không cung cấp cách gọi `EntityManager.refresh(entity)` theo mô hình đó.

Cách đơn giản để đồng bộ trạng thái sau ghi là truy vấn lại aggregate bằng repository:

```java
PurchaseOrder reloaded = orders.findById(saved.getId())
    .orElseThrow();
```

Nếu cần dùng `JdbcAggregateTemplate`, có thể đọc theo ID và kiểu aggregate:

```java
PurchaseOrder reloaded =
    jdbcAggregateTemplate.findById(id, PurchaseOrder.class);
```

Với repository-based application, `findById` thường là cách dễ hiểu và nhất quán nhất.

## 6. Đọc lại sau INSERT và sau UPDATE

Không chỉ INSERT mới có giá trị database sinh. Trigger có thể thay đổi property sau mỗi lần UPDATE, chẳng hạn `updated_at`.

Ví dụ:

```java
@Transactional
public PurchaseOrder renameAndReload(Long id, String newNumber) {
    PurchaseOrder order = orders.findById(id)
        .orElseThrow();

    order.rename(newNumber);

    PurchaseOrder saved = orders.save(order);

    return orders.findById(saved.getId())
        .orElseThrow();
}
```

Giả sử trigger cập nhật `updated_at` khi bảng được UPDATE. Object `saved` không tự động được reload toàn bộ để lấy timestamp mới; lần `findById` tiếp theo đọc giá trị trigger đã ghi.

Đối với aggregate có các entity con, việc tải lại root sẽ materialize aggregate theo mapping của nó. Điều đó có thể bao gồm các entity con và các property read-only của chúng, tùy mapping. Vì vậy chi phí reload phụ thuộc kích thước aggregate, không chỉ số cột được database sinh.

### 6.1. Read-after-write trong cùng transaction

Với trigger đồng bộ thông thường, truy vấn lại sau khi INSERT/UPDATE trong cùng transaction sẽ đọc được thay đổi của chính transaction đó. Ví dụ service phía trên có thể dùng `@Transactional` để hai thao tác cùng nằm trong một transaction.

Tuy nhiên, nếu giá trị được tạo bởi một tiến trình **bất đồng bộ** sau khi commit, một trigger deferred hoặc một worker bên ngoài, truy vấn ngay lập tức có thể chưa thấy giá trị cuối cùng. Khi đó cần xác định thời điểm dữ liệu sẵn sàng và đọc lại sau commit hoặc sau khi công việc bất đồng bộ hoàn tất.

Không nên thêm retry loop tùy tiện nếu database trigger vốn đồng bộ; trước tiên hãy xác định cơ chế tạo dữ liệu thực tế.

## 7. Phân biệt @ReadOnlyProperty và @InsertOnlyProperty

Spring Data Relational còn có `@InsertOnlyProperty`:

```java
import org.springframework.data.annotation.InsertOnlyProperty;
```

Annotation này có semantics khác:

| Annotation | INSERT | UPDATE | READ |
| --- | --- | --- | --- |
| `@ReadOnlyProperty` | Không ghi | Không ghi | Có đọc |
| `@InsertOnlyProperty` | Có ghi | Không ghi | Có đọc (theo mapping thông thường) |
| `@Transient` | Không ghi | Không ghi | Không đọc |

`@InsertOnlyProperty` phù hợp với giá trị **ứng dụng cung cấp khi tạo mới** nhưng không muốn thay đổi ở những lần update sau, chẳng hạn nguồn tạo record hoặc mã import ban đầu.

Ví dụ:

```java
@InsertOnlyProperty
@Column("source_system")
private String sourceSystem;
```

Nếu `sourceSystem` được ứng dụng gửi khi insert, Spring Data JDBC ghi giá trị đó ở lần insert và bỏ qua nó ở các lần update.

Nếu database phải tự tạo `created_at` bằng default, dùng `@ReadOnlyProperty` để Spring Data không ghi cột này ngay từ đầu.

**Không dùng @InsertOnlyProperty chỉ vì một cột được tạo khi insert.** Annotation đó vẫn cho phép Spring Data ghi giá trị của property trong câu INSERT; nó không có nghĩa “hãy để database tự tạo”.

## 8. Khi nào cần reload, khi nào không?

Không phải mọi lần save đều cần truy vấn lại. Reload thêm một round trip và có thể materialize toàn bộ aggregate. Chỉ nên thực hiện khi use case thực sự cần giá trị do database tạo hoặc cần trạng thái đã được database chuẩn hóa.

| Tình huống | Có cần reload? | Lý do |
| --- | --- | --- |
| Chỉ cần ID auto-generated | Thường không | Spring Data JDBC lấy ID được sinh và trả về trong object lưu. |
| Cần version mới sau save | Thường không | Spring Data JDBC quản lý và trả version đã cập nhật. |
| Cần giá trị DEFAULT của cột read-only | Có | Framework không tự reload các property khác sau ghi. |
| Cần giá trị trigger tạo trên INSERT | Có | Giá trị do database sinh không tự động được đưa về toàn bộ object. |
| Cần timestamp trigger cập nhật sau UPDATE | Có | Object save không được tự động reload toàn bộ. |
| Không dùng các cột database-generated trong response/use case | Không nhất thiết | Tránh round trip không cần thiết. |
| Trigger xử lý bất đồng bộ sau commit | Có, sau khi dữ liệu sẵn sàng | Đọc ngay có thể chưa thấy kết quả cuối. |

Nếu API cần trả lại dữ liệu chuẩn hóa từ database, hãy cân nhắc service method trả về aggregate đã reload hoặc DTO được truy vấn riêng.

## 9. Tải lại chỉ một phần dữ liệu hay toàn bộ aggregate?

`findById` đọc aggregate theo mapping. Nếu aggregate có nhiều collection con, việc reload có thể tốn chi phí.

Có ba lựa chọn thường gặp:

### 9.1. Reload toàn bộ aggregate

```java
PurchaseOrder reloaded = orders.findById(saved.getId())
    .orElseThrow();
```

Dùng khi caller cần trạng thái domain đầy đủ sau ghi, bao gồm các property generated và entity con.

### 9.2. Query riêng các cột generated

Nếu chỉ cần `created_at` và `audit_token`, có thể dùng custom query trả DTO:

```java
public record GeneratedOrderFields(
    Long id,
    Instant createdAt,
    String auditToken
) {}
```

Ví dụ SQL:

```sql
SELECT id, created_at, audit_token
FROM purchase_orders
WHERE id = :id;
```

Query này có thể được triển khai qua custom repository hoặc `NamedParameterJdbcOperations`. Nó tránh materialize toàn bộ aggregate nếu use case chỉ cần một vài cột.

### 9.3. Database RETURNING

Một số database hỗ trợ `INSERT ... RETURNING` hoặc `UPDATE ... RETURNING` để trả lại các cột sau khi ghi. Đây là cơ chế đặc thù của database và cần custom SQL/data access phù hợp nếu muốn kiểm soát trực tiếp.

Không nên mặc định rằng `repository.save` trong Spring Data JDBC sẽ trả lại mọi cột trigger/default chỉ vì database hỗ trợ RETURNING. Tài liệu Spring Data JDBC nêu rõ entity không được tự động reload sau khi ghi; nếu cần những property này, phải đọc lại rõ ràng hoặc xây dựng một đường truy cập tùy chỉnh.

## 10. Tác động tới transaction và response API

Một use case tạo đơn hàng có thể cần trả ngay:

```json
{
  "id": 101,
  "orderNumber": "PO-2026-001",
  "createdAt": "2026-11-13T09:15:00Z",
  "updatedAt": "2026-11-13T09:15:00Z",
  "auditToken": "PO-101"
}
```

Nếu các trường timestamp/token do database tạo, response phải lấy từ object đã được reload hoặc từ một query trả DTO sau insert.

Một controller không nên lấy trực tiếp object đầu vào hoặc object `save` chưa reload rồi giả định các property read-only đã có giá trị:

```java
@PostMapping("/orders")
public OrderResponse create(@RequestBody CreateOrderRequest request) {
    PurchaseOrder saved = service.createAndReload(request.orderNumber());
    return OrderResponse.from(saved);
}
```

Nếu transaction nằm trong service và response được tạo trước khi transaction commit, giá trị từ trigger đồng bộ thường đã có. Nếu một tác vụ deferred/asynchronous cập nhật sau commit, response cần phản ánh rõ trạng thái ban đầu hoặc dùng một bước đọc sau khi công việc hoàn tất.

### 10.1. Không để reload tạo thêm side effect

Một lần `findById` là thao tác đọc. Nó không nên kích hoạt logic domain như gửi email, phát sự kiện nghiệp vụ hay tạo thêm row. Constructor/factory được dùng cho mapping cũng nên thuần, không tạo side effect khi aggregate được khôi phục.

Nếu có domain event cần phát sau khi lưu, hãy đặt nó ở application/domain event mechanism phù hợp; đừng gắn vào getter hoặc logic materialization.

## 11. Kiểm thử default và trigger

Để xác nhận cơ chế hoạt động, test nên chạy trên database có hỗ trợ đúng DDL/trigger mà ứng dụng sử dụng. Với PostgreSQL-specific trigger, ưu tiên PostgreSQL thật hoặc Testcontainers PostgreSQL thay vì giả định H2 có cùng semantics.

Ví dụ test tích hợp:

```java
@DataJdbcTest
@AutoConfigureTestDatabase(
    replace = AutoConfigureTestDatabase.Replace.NONE
)
class PurchaseOrderGeneratedColumnsTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void reloadsDatabaseGeneratedValuesAfterInsert() {
        PurchaseOrder saved = orders.save(
            new PurchaseOrder("PO-TEST-001")
        );

        // Generated ID có thể đã có trên object save trả về.
        assertThat(saved.getId()).isNotNull();

        // Read-only properties cần được đọc lại.
        PurchaseOrder reloaded = orders.findById(saved.getId())
            .orElseThrow();

        assertThat(reloaded.getCreatedAt()).isNotNull();
        assertThat(reloaded.getUpdatedAt()).isNotNull();
        assertThat(reloaded.getAuditToken())
            .isEqualTo("PO-" + saved.getId());
    }
}
```

Test này giả định:

- Database test đã có bảng và trigger tương ứng.
- Test dùng đúng JDBC driver/database.
- Trigger chạy đồng bộ trong transaction.
- Entity có các property `@ReadOnlyProperty` như ví dụ.
- Repository được cấu hình và component scan phù hợp.

### 11.1. Kiểm thử UPDATE trigger

Có thể lưu đơn hàng, tải lại, đổi order number, lưu rồi đọc lại lần nữa:

```java
PurchaseOrder before = orders.findById(id).orElseThrow();

Instant oldUpdatedAt = before.getUpdatedAt();

before.rename("PO-RENAMED");
orders.save(before);

PurchaseOrder after = orders.findById(id).orElseThrow();

assertThat(after.getUpdatedAt()).isAfterOrEqualTo(oldUpdatedAt);
```

Để kiểm thử timestamp chính xác hơn, cần kiểm soát clock/độ phân giải của database hoặc so sánh khoảng thời gian hợp lý. Tránh test dựa trên giả định hai thao tác liên tiếp luôn tạo timestamp khác nhau đến từng millisecond.

### 11.2. Kiểm thử default có thật sự được áp dụng

Nếu property không có `@ReadOnlyProperty`, SQL INSERT có thể gửi NULL và database không dùng default như mong đợi. Test trên database thực tế sẽ phát hiện lỗi này tốt hơn test chỉ khởi tạo object Java.

Cũng nên kiểm tra rằng giá trị từ application không ghi đè cột mà database được quyền sở hữu. Khi dùng `@ReadOnlyProperty`, giá trị được gán vào field Java không tham gia lệnh ghi của Spring Data.

## 12. Những lỗi thường gặp

| Hiện tượng | Nguyên nhân | Hướng xử lý |
| --- | --- | --- |
| ID có nhưng createdAt vẫn null sau save | ID được lấy từ generated key; các property generated khác không tự reload. | Gọi `findById(saved.getId())` hoặc query read model. |
| Database default không chạy | INSERT đã gửi giá trị NULL tường minh vào cột. | Đánh dấu property DB-owned bằng `@ReadOnlyProperty` để bỏ khỏi write. |
| Trigger đã chạy nhưng object Java cũ vẫn giữ giá trị cũ | Spring Data JDBC không tự refresh toàn bộ aggregate. | Đọc lại aggregate sau thao tác ghi. |
| Property không được đọc sau reload | Dùng nhầm `@Transient` hoặc mapping tên cột sai. | Dùng `@ReadOnlyProperty` và kiểm tra `@Column`/NamingStrategy. |
| Giá trị trigger bị ghi đè bởi ứng dụng | Property không được đánh dấu read-only hoặc có custom SQL ghi giá trị. | Xác định ownership và loại property phù hợp. |
| Dùng @InsertOnlyProperty cho default DB | Annotation vẫn cho phép ghi property khi INSERT. | Dùng `@ReadOnlyProperty` nếu database phải tự sinh. |
| Reload không thấy giá trị cuối cùng | Công việc tạo dữ liệu chạy bất đồng bộ/deferred hoặc transaction visibility khác dự kiến. | Đọc sau commit hoặc sau khi worker hoàn tất. |
| Reload làm chậm request | Aggregate lớn hoặc query đọc quá nhiều child rows. | Query DTO các cột cần thiết hoặc tối ưu aggregate. |
| Trigger không chạy trong H2 test | DDL/trigger của database khác không tương thích. | Test trên đúng database/dialect, chẳng hạn Testcontainers. |

## 13. Quy trình áp dụng trong dự án

Khi tích hợp cột database-generated vào aggregate Spring Data JDBC:

1. Xác định cột nào do database sở hữu: identity, default, trigger hoặc generated expression.
2. Đảm bảo DDL/trigger tạo giá trị đúng ở thời điểm insert/update.
3. Đánh dấu property cần đọc bằng `@ReadOnlyProperty`; dùng `@Column` nếu tên cột khác property.
4. Tránh dùng `@Transient` cho property cần materialize từ database.
5. Lưu aggregate và dùng ID/version do Spring Data trả về khi cần.
6. Nếu use case cần giá trị generated, gọi `findById` hoặc query DTO sau ghi.
7. Đặt reload trong transaction phù hợp nếu cần thấy kết quả của trigger đồng bộ trước khi commit.
8. Nếu xử lý bất đồng bộ, xác định thời điểm dữ liệu cuối cùng sẵn sàng rồi mới đọc.
9. Kiểm thử trên database/dialect thực tế, đặc biệt với trigger và generated columns.
10. Đánh giá chi phí reload; chỉ đọc toàn bộ aggregate khi caller thực sự cần trạng thái đầy đủ.

> **Spring Data JDBC lấy ID được sinh theo cơ chế generated-key, nhưng không tự động reload mọi property được trigger/default tạo. Dùng `@ReadOnlyProperty` để database sở hữu cột, rồi đọc lại aggregate khi use case cần giá trị mới.**
