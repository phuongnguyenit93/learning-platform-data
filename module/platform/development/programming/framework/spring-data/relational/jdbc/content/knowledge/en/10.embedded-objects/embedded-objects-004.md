# Rules for `USE_NULL`, `USE_EMPTY`, `@Embedded.Nullable`, and `@Embedded.Empty`

In **Spring Data JDBC**, a value object annotated with `@Embedded` is mapped to columns located directly in the aggregate root's table. When reading a row, Spring Data must decide: if **all columns belonging to the embedded object have `NULL` values**, should the Java property receive `null` or an instantiated object whose internal properties are empty?

That is the purpose of the two options `USE_NULL` and `USE_EMPTY`:

- **`USE_NULL`**: if all columns of the embedded object are `NULL`, return `null` for the embedded property.
- **`USE_EMPTY`**: if all columns are `NULL`, still create an embedded object; component values are mapped from the `NULL` columns.

Spring Data Relational provides two nested annotations as shorthand for these two options: `@Embedded.Nullable` corresponds to `USE_NULL`, while `@Embedded.Empty` corresponds to `USE_EMPTY`. Choosing the right policy helps the Java model accurately express the meaning of empty data, especially when using immutable value objects such as Java `record`s.

## 1. How Are Embedded Objects Stored?

Suppose a customer has a shipping address. The address is a group of values belonging to the customer, needing no separate ID and not managed as an independent aggregate.

```java
public record Address(
        String street,
        String city,
        String postalCode
) {}
```

With `@Embedded`, the properties of `Address` are flattened into columns in the same `customers` table. For example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        @Embedded(prefix = "shipping_") Address shippingAddress
) {}
```

Illustrative DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20)
);
```

Here `Address` **does not create a separate table**. Its properties are mapped to `shipping_street`, `shipping_city`, and `shipping_postal_code`. The prefix distinguishes column groups and avoids collisions if the aggregate has multiple objects of the same type.

On write, an `INSERT` or `UPDATE` on `customers` carries the address columns. On read, Spring Data retrieves those columns and constructs `Address`. The `USE_NULL`/`USE_EMPTY` rule determines how the object is constructed when the embedded columns have no data.

## 2. Why Is a Rule Needed When All Columns Are `NULL`?

An embedded object can be represented by multiple columns. The database does not have a single column indicating that the object "does not exist"; its state is typically inferred from the component column values.

Example rows in the database:

| id | name | shipping_street | shipping_city | shipping_postal_code |
|---:|---|---|---|---|
| 1 | Lan | `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` |
| 2 | Minh | `NULL` | `NULL` | `NULL` |
| 3 | Hoa | `NULL` | `Da Nang` | `NULL` |

For row 1, the address clearly has data. For row 2, all address columns are `NULL`; Spring Data needs a rule to decide whether `shippingAddress` should be `null` or an empty `Address`. For row 3, at least one column has a value, so Spring Data has data to create an `Address` object with `street = null`, `city = "Da Nang"`, and `postalCode = null`.

**The difference between the two policies only appears when all columns of the embedded object are `NULL`.** If at least one column has a value, an embedded object is created in both cases; properties corresponding to `NULL` columns still receive null according to the mapping.

## 3. `USE_NULL`: When All Columns Are `NULL`, the Embedded Property Is `null`

Explicit declaration:

```java
@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL, prefix = "shipping_")
Address shippingAddress
```

Or using the shorthand annotation:

```java
@Embedded.Nullable(prefix = "shipping_")
Address shippingAddress
```

Both forms express the same policy. `USE_NULL` is also the default choice of `@Embedded` when `onEmpty` is not specified.

Read results:

| `shipping_street` | `shipping_city` | `shipping_postal_code` | Java Value Under `USE_NULL` |
|---|---|---|---|
| `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` | `Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")` |
| `NULL` | `NULL` | `NULL` | `null` |
| `NULL` | `Da Nang` | `NULL` | `Address(null, "Da Nang", null)` |

This policy fits when **having no values in the column group** means "there is no address". Business code can check:

```java
if (customer.shippingAddress() == null) {
    // Customer has not provided a shipping address yet.
}
```

With `USE_NULL`, the Java property may not exist as an object. Therefore, any code accessing `shippingAddress.street()` must handle the `shippingAddress == null` case, or the application must ensure data and constructors do not produce that state.

## 4. `USE_EMPTY`: When All Columns Are `NULL`, Still Create the Embedded Object

Explicit declaration:

```java
@Embedded(onEmpty = Embedded.OnEmpty.USE_EMPTY, prefix = "shipping_")
Address shippingAddress
```

Or using the shorthand annotation:

```java
@Embedded.Empty(prefix = "shipping_")
Address shippingAddress
```

Both forms instruct Spring Data to create the embedded object even when all of its columns are `NULL`.

With `Address` being a record of `String` reference types, the result can be represented as:

```java
new Address(null, null, null)
```

Result table:

| `shipping_street` | `shipping_city` | `shipping_postal_code` | Java Value Under `USE_EMPTY` |
|---|---|---|---|
| `12 Nguyen Hue` | `Ho Chi Minh City` | `700000` | `Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")` |
| `NULL` | `NULL` | `NULL` | `Address(null, null, null)` |
| `NULL` | `Da Nang` | `NULL` | `Address(null, "Da Nang", null)` |

Then code can work with the object without checking for null at the `shippingAddress` level:

```java
Address address = customer.shippingAddress();

if (address == null) {
    // This case is not produced by USE_EMPTY
    // when all embedded columns are NULL.
}

if (address.street() == null) {
    // The object exists, but street is not set yet.
}
```

Note: `USE_EMPTY` **does not automatically generate default data** such as empty strings, a default city, or a placeholder postal code. It asks to create the object; component values are still read from the database columns. If a column is `NULL`, the corresponding property can still be `null`.

## 5. Comparing the Four Declaration Forms

| Declaration | Policy When All Embedded Columns Are `NULL` | Meaning |
|---|---|---|
| `@Embedded` | `USE_NULL` (default) | Object is treated as absent |
| `@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL)` | `USE_NULL` | Explicitly specifies null policy |
| `@Embedded.Nullable` | `USE_NULL` | Shorthand annotation for an object that may be absent |
| `@Embedded(onEmpty = Embedded.OnEmpty.USE_EMPTY)` | `USE_EMPTY` | Creates an object even if all columns are null |
| `@Embedded.Empty` | `USE_EMPTY` | Shorthand annotation for an empty object |

`@Embedded.Nullable` and `@Embedded.Empty` are nested annotations inside Spring Data Relational's `Embedded`. They are not general-purpose Java or Jakarta nullability annotations. For instance, `org.springframework.lang.Nullable` or `jakarta.annotation.Nullable` are meant to express API nullability; they do not replace the `onEmpty` rule when Spring Data constructs embedded objects.

When using one of the two shorthand annotations, do not place a second `@Embedded` on the same property. Pick **one declaration style** per embedded property to keep the policy readable and avoid overlapping metadata.

## 6. Example with Two Objects of the Same Type Using Different Policies

A customer may have an optional shipping address and a billing address that the application prefers to represent as an object even before data is entered:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        @Embedded.Nullable(prefix = "shipping_")
        Address shippingAddress,
        @Embedded.Empty(prefix = "billing_")
        Address billingAddress
) {}
```

DDL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    shipping_street VARCHAR(180),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20),
    billing_street VARCHAR(180),
    billing_city VARCHAR(100),
    billing_postal_code VARCHAR(20)
);
```

Suppose a row has all `shipping_*` and `billing_*` columns set to `NULL`. After reading:

```text
customer.shippingAddress() == null

customer.billingAddress()
    == Address(null, null, null)
```

This example shows that **the policy is a property of each embedded field**, not a global setting for every object in the application. Two properties using the same `Address` type can carry different business semantics.

## 7. Prefixes and Column Names Must Match DDL

When a table has multiple embedded objects, prefixes help produce non-overlapping column names:

```java
@Embedded.Nullable(prefix = "shipping_")
Address shippingAddress,

@Embedded.Empty(prefix = "billing_")
Address billingAddress
```

Under the common naming strategy, the properties of `Address` are mapped to:

| Property in `Address` | Embedded Property | Column Name |
|---|---|---|
| `street` | `shippingAddress` | `shipping_street` |
| `city` | `shippingAddress` | `shipping_city` |
| `postalCode` | `shippingAddress` | `shipping_postal_code` |
| `street` | `billingAddress` | `billing_street` |
| `city` | `billingAddress` | `billing_city` |
| `postalCode` | `billingAddress` | `billing_postal_code` |

The prefix in the annotation and the column names in the DDL must match. If the annotation uses `billing_` while the table only has `bill_street`, the SQL queries generated by Spring Data will reference non-existent column names.

Equivalent read SQL example:

```sql
SELECT id, name,
       shipping_street, shipping_city, shipping_postal_code,
       billing_street, billing_city, billing_postal_code
FROM customers
WHERE id = ?;
```

An embedded object does not add a `JOIN` merely because it is a Java object. The columns are read from the same row in the root table.

## 8. This Rule Affects Reading Data, Not Creating Default Objects

`USE_NULL` and `USE_EMPTY` describe **how to map a database row into a Java object** when all columns belonging to the embedded property are `NULL`. They are not:

- Configuration for the database to generate default values.
- An `INSERT` statement into a separate table for the embedded object.
- A replacement for `DEFAULT`, `NOT NULL`, or `CHECK` in DDL.
- A way to populate all inner properties with empty strings.
- A mechanism that calls a domain constructor to synthesize a default address.

When writing an entity with an embedded object, Spring Data JDBC still generates SQL based on metadata and object values. If the object is `null`, the corresponding columns are typically written as `NULL`; if the object exists but all its properties are null, the columns may also be written as `NULL`. On read, the `onEmpty` policy determines whether those identical stored states are represented as `null` or as an empty object.

This leads to an important consequence: **the database cannot distinguish "embedded property is null" from "embedded object exists with all components null"** if both cases store an all-`NULL` group of columns. `USE_EMPTY` chooses to interpret any all-null column group as an object; `USE_NULL` chooses to interpret it as `null`.

If the business strictly requires distinguishing those two states, add a dedicated indicator column (such as `has_shipping_address`) or store another distinguishing value. Switching from `USE_NULL` to `USE_EMPTY` alone cannot recover information that the schema did not store.

## 9. Impact of Nullability and Inner Data Types

With `USE_EMPTY`, Spring Data still has to map `NULL` column values into each property. Therefore, the Java types of the embedded components matter greatly.

Use reference/wrapper types if columns can be null:

```java
public record Address(
        String street,
        String city,
        Integer buildingNumber
) {}
```

In this example, `street`, `city`, and `buildingNumber` can receive `null`. If a primitive such as `int` is used, Java has no `null` value; mapping a `NULL` column to a primitive can produce default values or cause issues depending on instantiation/conversion paths. Do not rely on a default value of `0` to represent "building number unknown" if the business needs to distinguish them clearly. Using `Integer` generally expresses missing data better.

If an embedded column is declared `NOT NULL`, `USE_EMPTY` does not automatically make writes valid. For example:

```sql
shipping_city VARCHAR(100) NOT NULL
```

An `Address(null, null, null)` can still be rejected by the database on write because `shipping_city` is `NULL`. The read-time object creation policy does not alter write-time constraints.

Value objects with strong invariants (for example, `Money` requiring both amount and currency, or `Address` requiring a country) must be designed alongside schema nullability. If all columns are null yet the constructor rejects null values, `USE_EMPTY` cannot construct a valid business object on its own. In that case, choose `USE_NULL`, use a domain-valid default object, or change the storage model to represent the state explicitly.

## 10. Choosing `USE_NULL` or `USE_EMPTY` by Business Meaning

Do not choose solely to reduce `null` checks in code. Determine the meaning of the column group when all columns are empty:

| Business Case | Usually Suitable Policy | Reason |
|---|---|---|
| Shipping address not yet provided | `USE_NULL` | Absence of an address is a clear missing state |
| Optional info, such as secondary notes | `USE_NULL` | Without content, no object is needed |
| A settings group always considered part of the entity, even if no values are set yet | `USE_EMPTY` | Caller can interact with an empty settings object |
| Value object with valid defaults and a constructor supporting an empty state | `USE_EMPTY` can be used | Object is always present per the domain model |
| Value object requiring certain fields to be valid | Usually `USE_NULL` or a schema change | An empty object violates invariants |

For example, a `Preferences` object may allow all choices to remain unset:

```java
public record Preferences(
        Boolean emailNotifications,
        Boolean smsNotifications
) {}
```

If the application wants every customer to always have a preferences object for reading and updating individual options, `USE_EMPTY` can be appropriate. The `Boolean` wrapper clearly represents an unset state; a primitive `boolean` would coerce it to `false` and lose the distinction between "not chosen yet" and "turned off".

Conversely, for `Address`, having no address data usually means the customer has not declared an address; `USE_NULL` lets the code express that directly.

## 11. Comparing Results with Concrete Read Examples

Suppose a query returns three rows:

```sql
SELECT id, shipping_street, shipping_city, shipping_postal_code
FROM customers
ORDER BY id;
```

Data:

```text
id=1: "12 Nguyen Hue", "Ho Chi Minh City", "700000"
id=2: NULL, NULL, NULL
id=3: NULL, "Da Nang", NULL
```

Results under `USE_NULL`:

```text
Customer 1 -> Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")
Customer 2 -> null
Customer 3 -> Address(null, "Da Nang", null)
```

Results under `USE_EMPTY`:

```text
Customer 1 -> Address("12 Nguyen Hue", "Ho Chi Minh City", "700000")
Customer 2 -> Address(null, null, null)
Customer 3 -> Address(null, "Da Nang", null)
```

Rows 1 and 3 are identical across both policies. Only row 2 differs because **all columns of the embedded object are null**.

## 12. Inspecting SQL and Mapping When Debugging

When an embedded object is not constructed as expected, check step by step:

1. **Annotation on the property**: is `@Embedded`, `@Embedded.Nullable`, or `@Embedded.Empty` used? Is `onEmpty` specified explicitly?
2. **Prefix**: does `shipping_`/`billing_` match the physical column names?
3. **The object's columns**: are all columns null, or does at least one column have a value? That condition determines the `onEmpty` branch.
4. **Java types**: are properties wrappers/reference types or primitives? Do the constructor/record accept null values?
5. **DDL**: do columns allow null? Are there defaults, constraints, or migrations changing values before reading?
6. **Runtime SQL**: does the `SELECT` statement fetch all embedded columns? Does a custom query omit a required column?

You can enable Spring JDBC logging in development:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Logs let you inspect SQL statements and bound parameters. With custom queries, make sure the `SELECT` list includes all columns required for the embedded object. If you only select `id` and `name` while asking to materialize `Address`, the mapping result cannot have complete address data.

When using `@Query`, column names are the physical database column names. For example:

```java
@Query("""
    SELECT id, name,
           shipping_street, shipping_city, shipping_postal_code
    FROM customers
    WHERE id = :id
    """)
Optional<Customer> findCustomer(@Param("id") Long id);
```

This SQL uses the exact columns declared in the DDL. `@Embedded.Nullable` or `@Embedded.Empty` does not automatically add columns to handwritten queries.

## 13. Common Misconceptions

| Misconception | Correct Understanding |
|---|---|
| `USE_EMPTY` creates empty strings for every field. | It creates the embedded object; each field still receives the column's value, including `null`. |
| `USE_NULL` makes all child properties null in every case. | It only returns null for the embedded property when **all columns of the object** are null. If one column has data, the object is created. |
| `@Embedded.Empty` creates a separate table. | Embedded objects are flattened into columns in the root's table. |
| `@Embedded.Nullable` is a general-purpose `@Nullable`. | It is Spring Data Relational's shorthand for the `USE_NULL` policy of embedded mapping. |
| `USE_EMPTY` makes the DDL allow nulls. | DDL still dictates `NULL`/`NOT NULL`; the policy only affects reading and object construction. |
| The two policies behave differently on every row. | They differ only when all embedded columns are `NULL`. |
| Empty objects and null objects are always distinguished on save. | If both write all null columns, the database cannot preserve the difference without a separate indicator column. |
| Primitives can be used for every property because `USE_EMPTY` always creates an object. | Properties can still receive null from columns; choose Java types matching nullability and invariants. |

## 14. Self-Observation Practice Exercise

Using the `customers` table from the beginning, you can practice with these steps:

1. Create three rows: one with a full address, one with all address columns `NULL`, and one with only `shipping_city`.
2. Map `shippingAddress` with `@Embedded.Nullable(prefix = "shipping_")`, read all three rows, and observe that the second row receives `null`.
3. Switch to `@Embedded.Empty(prefix = "shipping_")`, read the same data again, and observe that the second row receives `Address(null, null, null)`.
4. Keeping `USE_EMPTY`, set only `shipping_city = 'Da Nang'` on the third row; observe that the result does not differ from `USE_NULL` for rows with at least one non-null column.
5. Try adding a second embedded property with prefix `billing_` and a different policy; verify that DDL and SQL include both column groups.
6. Try using a primitive property in an embedded object with a nullable column to see why wrapper types usually fit data that can be absent.

When finished, record results across three layers: **database columns**, **annotation/prefix on the property**, and **resulting Java object after reading**. You do not need to modify data to force one policy to produce the other's result; the same row can be interpreted differently using only `onEmpty` metadata.

## 15. Selection Principles

`USE_NULL` fits when a completely empty group of columns means **there is no object**. `USE_EMPTY` fits when the model wants **the object to always be present**, even when its components are not set yet. `@Embedded.Nullable` and `@Embedded.Empty` express those two choices concisely right on the property.

When designing, align the policy with business meaning, column nullability, Java types, and the value object's constructor. In particular, remember that an embedded object is stored as columns on the aggregate root: the `onEmpty` policy only determines how Spring Data JDBC constructs the object when reading a row where all embedded columns are `NULL`; it does not replace DDL, does not auto-generate default values, and does not create a separate relational table.
