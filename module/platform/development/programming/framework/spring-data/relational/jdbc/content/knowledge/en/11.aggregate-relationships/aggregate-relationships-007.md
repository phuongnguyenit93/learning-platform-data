# Child Entities with IDs vs. Without IDs in Spring Data JDBC

## 1. Why can a child entity have or not have an ID?

Spring Data JDBC organizes data around **aggregates**. An aggregate root is the object at the top of a cluster of data sharing a consistent lifecycle; the entities/value objects inside it are saved and loaded as part of that aggregate.

Example of an order with multiple order lines:

~~~text
PurchaseOrder (aggregate root)
    ├── OrderLine (first order line)
    ├── OrderLine (second order line)
    └── OrderLine (third order line)
~~~

There are two common design approaches:

- **Child entity without its own ID:** the child object is identified within the aggregate context, via the foreign key pointing to the root and its position/key in the collection (if the collection needs a key).
- **Child entity with its own ID:** the child table has an additional row identifier column, such as `line_id`. Even with this ID, the object can still be a component belonging to the aggregate root and remain managed according to the aggregate's lifecycle.

Three concepts must be separated:

1. **Aggregate root ID:** identifies the aggregate and serves as the primary entry point via the repository.
2. **Child row ID:** technical identifier of a row in the child table, if the schema and mapping use one.
3. **Collection key:** the position of an element in a `List`, or the key of an element in a `Map`; it helps represent the collection structure and is not necessarily a business ID.

A child entity having an ID **does not automatically become an aggregate root**. Conversely, a child entity without its own ID can still be persisted completely because Spring Data JDBC knows which aggregate it belongs to.

## 2. Aggregate root and internal relationships in Spring Data JDBC

Spring Data JDBC focuses on aggregates rather than an arbitrary object graph like an ORM with lazy loading. Repositories are typically defined for the **aggregate root**:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

`PurchaseOrder` has `@Id`. The `OrderLine` instances in the collection are saved together with the aggregate through internal relationship mapping, usually using `@MappedCollection`.

Database relationship diagram:

~~~mermaid
erDiagram
    PURCHASE_ORDERS ||--o{ ORDER_LINES : contains
    PURCHASE_ORDERS {
        bigint id PK
        date ordered_on
    }
    ORDER_LINES {
        bigint order_id FK
        int line_number
        varchar product_code
        int quantity
    }
~~~

The `order_id` column in the child table holds the foreign key to the aggregate root. If the child has no ID of its own, the pair `(order_id, line_number)` can serve as the composite primary key in the schema. If the child has its own ID, `line_id` can be the primary key and `(order_id, line_number)` can still be marked unique so positions do not collide within the same order.

**Spring Data JDBC manages relationships through the aggregate root.** It does not provide an independent repository for every child object simply because that object is a Java class or has an ID column.

## 3. Child entity without its own ID

This model fits when the child object only has meaning inside the aggregate and does not need to be referenced or managed independently.

Example of an order line with product code, quantity, and unit price:

~~~java
import java.math.BigDecimal;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public record OrderLine(
        String productCode,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

`OrderLine` has no `@Id`. The aggregate root holds the list:

~~~java
import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private LocalDate orderedOn;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines = new ArrayList<>();

    // constructors, getters...
}
~~~

Here:

- `@Id` marks the aggregate root's ID.
- `@MappedCollection(idColumn = "order_id")` indicates the column in the child table storing the root's ID.
- `keyColumn = "line_number"` stores the element's position in the `List`.
- `OrderLine` needs no separate ID; it is stored as an element of the order's list.

The corresponding DDL can be:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ordered_on DATE NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,

    CONSTRAINT pk_order_lines
        PRIMARY KEY (order_id, line_number),

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

The `(order_id, line_number)` pair identifies a line within the scope of one order. `line_number` is the collection key, not an independent ID of `OrderLine`.

### 3.1. When to choose a child without an ID?

Choose this approach when:

- The child row has no meaning outside the aggregate root.
- No other aggregate needs to reference the child row directly.
- Changes to the child list are made through the root.
- The position or key in the collection suffices to identify the element within the aggregate.
- A stable child-row identifier does not need to be preserved across aggregate writes.

For example, `OrderLine`, an embedded `Address` in `Customer`, or `InvoiceItem` belonging to `Invoice` are objects that can often be managed as components of an aggregate.

### 3.2. How do List, Map, and Set affect this?

`@MappedCollection` can describe collection relationships. With `List`, `keyColumn` typically stores element positions. With `Map`, the key column stores the map key. With `Set`, there is no ordered position, so a key column for ordering is normally not needed.

Example of `Map<String, OrderLine>`:

~~~java
@MappedCollection(idColumn = "order_id", keyColumn = "line_code")
private Map<String, OrderLine> linesByCode = new HashMap<>();
~~~

The `line_code` column stores the map key. It is not automatically the table's primary key; if business rules require uniqueness within an order, add an appropriate constraint, such as `UNIQUE(order_id, line_code)`.

For `Set`, the Java collection prevents duplicate elements via `equals()`/`hashCode()` in memory, but that **does not automatically create a unique constraint in the database**. If data is written from multiple sources or via direct SQL, schema constraints are needed to protect uniqueness.

## 4. Child entity with its own ID

In some cases, the child table needs its own ID column—for example, an order line has a database-generated `line_id`. The Java model can declare:

~~~java
import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("product_code")
    private String productCode;

    private int quantity;

    @Column("unit_price")
    private BigDecimal unitPrice;

    // constructor, getters...
}
~~~

The aggregate root still holds the collection:

~~~java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines;

    // constructor, getters...
}
~~~

The DDL can use:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);

CREATE TABLE order_lines (
    line_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    product_code VARCHAR(40) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12, 2) NOT NULL,

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id),

    CONSTRAINT uk_order_lines_position
        UNIQUE (order_id, line_number)
);
~~~

`line_id` identifies the row in the `order_lines` table; `order_id` still determines which aggregate root owns that line. `line_number` holds the element's position in the `List`.

**Having its own ID does not mean having an independent lifecycle.** While `OrderLine` remains inside `PurchaseOrder.lines`, reading/writing it still belongs to operations on the aggregate root. Do not infer that simply adding `@Id` allows creating an `OrderLineRepository` and updating individual lines like a separate aggregate root.

Support for database-generated IDs on child entities and how those IDs are returned should be verified for your specific Spring Data JDBC version, dialect, and JDBC driver. If child IDs are database-generated, use the aggregate/entity returned after the save operation and verify the ID values in an integration test.

### 4.1. When is a child with an ID useful?

A child row ID can be useful when:

- The child table needs a single-column primary key to integrate with another system at the database level.
- Legacy data already has an ID column and the schema cannot be changed.
- Auxiliary or audit tables need to identify a child row at the storage layer.
- A single technical key is preferred over a long composite primary key.

Even so, if that ID must remain stable and be used widely to access/update the child independently, revisit the aggregate boundary. A child with a technical identifier that is still managed as a component of the root may not fit independent-update requirements.

## 5. Comparing child entities with and without IDs

| Criterion | Child without its own ID | Child with its own ID |
|---|---|---|
| Schema identification | Usually based on root FK and collection key | Has an additional child-row ID column |
| Java mapping | No `@Id` declared on child | Can declare `@Id` on child per supported mapping |
| Link to aggregate | Via `@MappedCollection` and FK to root | Still via `@MappedCollection` and FK to root |
| Independent repository | No | Not automatically; still a child of the aggregate |
| Lifecycle | Managed by the aggregate root | Still managed by the aggregate root while inside the collection |
| Schema complexity | Often simpler; can use composite key | Adds an ID and ID generation/maintenance mechanism |
| Reference from other aggregates | Should not be referenced directly | Having an ID does not automatically make the child an independently referenceable object |
| Suitable for | Value objects or root-dependent entities | Legacy schemas or technical requirements for a row identifier |

Another distinction to clarify: **a child object without an ID** does not mean the database cannot identify the row. The database can still use a composite primary key like `(order_id, line_number)`. "Without an ID" here means having no standalone identifier property in the child model, not that the child table lacks a key or a way to distinguish rows.

## 6. Saving the aggregate and the child's lifecycle

Spring Data JDBC operates by aggregate. When creating a new root, the framework writes the root and its child components per the mapping. When updating an aggregate, writing may involve deleting and re-writing dependent entities rather than tracking individual modified fields like JPA's dirty checking.

General flow:

~~~mermaid
flowchart TD
    A["purchaseOrderRepository.save(order)"] --> B{"Root already exists?"}
    B -->|No| C["INSERT aggregate root"]
    B -->|Yes| D["UPDATE aggregate root"]
    C --> E["Persist children per mapping"]
    D --> F["Replace/rewrite child data per aggregate strategy"]
    E --> G["Return saved aggregate"]
    F --> G
~~~

Implications:

- Do not assume a child row is updated column-by-column individually when calling `save(root)`.
- Order or collection keys can affect how child rows are rewritten.
- Auto-generated child IDs may not remain stable across aggregate saves if the update strategy replaces child rows.
- Tables outside the aggregate should not directly reference a child's ID simply because the child has an ID column.
- When per-child change history is required, consider dedicated audit/events or an appropriate aggregate model.

Exact SQL statements and persistence strategies depend on the version, relationship type, and configuration. The essential point is to **place lifecycle ownership on the right aggregate root**.

## 7. If the child needs independent access, consider splitting the aggregate

Suppose `OrderLine` needs to:

- Be updated by a separate use case without loading `PurchaseOrder`.
- Have its own repository and transaction boundary.
- Be referenced from multiple other aggregates.
- Maintain a stable ID across updates.
- Have a lifecycle independent of the order.

In that case, you may need to model `OrderLine` as an aggregate root or independent entity, rather than a child object inside `PurchaseOrder.lines`.

Design example:

~~~text
PurchaseOrder aggregate
    └── orderId, orderDate, customerId

OrderLine aggregate
    └── lineId, orderId, productId, quantity
~~~

DDL:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ordered_on DATE NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,

    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Root entity for the order line:

~~~java
@Table("order_lines")
public class OrderLine {

    @Id
    private Long id;

    @Column("order_id")
    private Long orderId;

    @Column("product_id")
    private Long productId;

    private int quantity;

    // constructor, getters...
}
~~~

Separate repository:

~~~java
public interface OrderLineRepository
        extends CrudRepository<OrderLine, Long> {

    List<OrderLine> findByOrderId(Long orderId);
}
~~~

In this model, `OrderLine` is an independent aggregate root; it has its own repository. `orderId` is a reference by ID to another aggregate, not an object-graph relationship automatically managed by Spring Data JDBC like an ORM.

Splitting aggregates means the application must actively manage transactions and invariants across `PurchaseOrder` and `OrderLine`. You can no longer assume changes across both aggregates are persisted automatically as a single operation. Appropriate use cases and consistency mechanisms must be designed.

## 8. Do not confuse child ID with collection key

The following three values can appear together in a child table, yet have distinct meanings:

| Column | Meaning |
|---|---|
| `line_id` | Child row's own ID, if any |
| `order_id` | ID of the aggregate root owning the child row |
| `line_number` | Position/key of the element in the collection |

Example of a row:

~~~text
line_id = 901
order_id = 42
line_number = 2
product_code = "P-200"
~~~

- `line_id = 901`: technical identifier of the row in the table.
- `order_id = 42`: the order line belongs to order number 42.
- `line_number = 2`: the element is currently at position/key 2 in the collection.

If the child has no `line_id`, the pair `(order_id, line_number)` can still uniquely identify the order line within the aggregate. Do not name the collection key column `id` if that causes readers to confuse it with the entity's `@Id`.

## 9. One-to-many relationship with an ID-less child: complete example

Suppose an order has many order lines, and each line exists only inside the order.

Child entity:

~~~java
import java.math.BigDecimal;

public record OrderLine(
        String productCode,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

Aggregate root:

~~~java
import java.time.LocalDate;
import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private LocalDate orderedOn;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_number")
    private List<OrderLine> lines = new ArrayList<>();

    public PurchaseOrder(LocalDate orderedOn, List<OrderLine> lines) {
        this.orderedOn = orderedOn;
        this.lines = new ArrayList<>(lines);
    }

    public Long getId() {
        return id;
    }

    public LocalDate getOrderedOn() {
        return orderedOn;
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }
}
~~~

Repository:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

Saving the aggregate:

~~~java
PurchaseOrder order = new PurchaseOrder(
        LocalDate.now(),
        List.of(
                new OrderLine("P-100", 2, new BigDecimal("50000")),
                new OrderLine("P-200", 1, new BigDecimal("75000"))
        )
);

PurchaseOrder saved = purchaseOrderRepository.save(order);
~~~

Spring Data JDBC saves the root and child elements. The child lines are linked to the root's ID via `order_id`; positions are stored in `line_number`.

There is no separate repository for `OrderLine`, because use cases operate on order lines through the `PurchaseOrder` aggregate.

## 10. Common errors

| Symptom | Possible cause | How to resolve |
|---|---|---|
| Child is not saved | Collection mapping not declared properly or table/columns mismatch | Check `@MappedCollection`, `idColumn`, `keyColumn`, and DDL |
| Child has no `@Id` yet is still saved | Normal behavior for a child belonging to an aggregate | Ensure the root has `@Id` and the relationship is mapped |
| Mistaking `line_number` for an independent ID | Misunderstanding the role of the collection key | Distinguish root FK, child ID, and collection key |
| Added `@Id` to child yet still no separate repository | Repositories are defined for aggregate roots | Create a separate aggregate root if the child needs an independent lifecycle |
| Child ID changes after re-saving the root | Child row may be replaced during aggregate update | Do not use child ID as a stable reference; consider splitting aggregates |
| List loads in wrong order | Missing/wrong `keyColumn` or incorrect key data | Check the position-storing column and schema |
| Map keys are not preserved | Map key column is not mapped properly | Declare `keyColumn` and inspect the data |
| Duplicate child rows exist | Java `Set` does not replace database constraints | Add primary/unique constraints matching the rules |
| Deleting root triggers foreign key error | Child rows or external references are unhandled | Review cascade/lifecycle and referencing relationships |
| Child is referenced from another aggregate | Aggregate boundaries are unsuitable | Convert child into an aggregate root and reference the root ID |

### Exercise 1 — Child without an ID

### Exercise 2 — Child with its own ID

Add an identity column `line_id` to `order_lines` and an `@Id Long id` property to `OrderLine`. Keep `order_id` and `line_number`. Observe the child ID after saving the aggregate and after updating/re-saving the root.

### Exercise 3 — Distinguishing the three columns

Given a row with `line_id = 901`, `order_id = 42`, `line_number = 2`, explain each value. Identify which column identifies the aggregate, which identifies the child row, and which holds the collection position.

Design a use case where an order line is edited independently and referenced from multiple places. Convert `OrderLine` into an aggregate root with its own repository, keeping only `orderId` as a reference. Determine the transactions and consistency rules needed between order and line.

## 12. Takeaways

- **Aggregate root ID** identifies the aggregate; repositories are normally defined for the root.
- A child **does not need its own ID** to be persisted. A foreign key to the root combined with the collection key can identify child rows within the aggregate.
- A child **with its own ID** can still just be a component of the aggregate; `@Id` on a child does not automatically create a repository or an independent lifecycle.
- `@MappedCollection` uses `idColumn` to store the foreign key to the root and `keyColumn` to store the collection position/key when needed.
- Child ID, root FK, and collection key are three distinct concepts, even though they may live together in the child table.
- Spring Data JDBC manages children through the aggregate root; when updating an aggregate, child data may be replaced/rewritten, so do not assume auto-generated child IDs always remain stable.
- If a child needs to be referenced, updated, and managed independently, consider turning it into a separate aggregate root and referencing it by ID.
