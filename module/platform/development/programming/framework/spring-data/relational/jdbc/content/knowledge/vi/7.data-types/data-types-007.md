# Mảng, dữ liệu nhị phân và giới hạn hỗ trợ theo cơ sở dữ liệu

Ứng dụng Java thường cần lưu những dữ liệu không chỉ là chuỗi, số hay ngày giờ: danh sách nhãn của sản phẩm, tập mã tùy chọn, ảnh thu nhỏ, tệp đính kèm hoặc nội dung nhị phân. Cơ sở dữ liệu quan hệ có nhiều cách biểu diễn các giá trị này, nhưng mức hỗ trợ khác nhau giữa PostgreSQL, MySQL, Oracle, SQL Server, SQLite và H2.

Trong Spring Data JDBC, cần phân biệt ba việc: **kiểu dữ liệu Java**, **kiểu cột SQL** và **khả năng chuyển đổi của JDBC driver/framework**. Một kiểu Java có thể hợp lệ nhưng không có ánh xạ mặc định tương ứng trên mọi database. Bài này dùng ví dụ cửa hàng để giải thích mảng SQL, dữ liệu nhị phân, cách chọn mô hình và cách xử lý khi Spring Data JDBC không ánh xạ trực tiếp kiểu vendor-specific.

## 1. Bắt đầu từ nhu cầu dữ liệu

Giả sử danh mục sản phẩm có các thông tin:

- Tên và giá bán: dữ liệu scalar thông thường.
- Danh sách tag như `["keyboard", "office", "wireless"]`: tập giá trị đơn giản, có thể được biểu diễn bằng mảng SQL, JSON hoặc bảng liên kết.
- Ảnh thu nhỏ hoặc nội dung tài liệu: dữ liệu nhị phân, thường được lưu trong cột binary/LOB hoặc kho file/object storage.

Không nên chọn kiểu SQL chỉ vì Java có sẵn `String[]` hoặc `byte[]`. Hãy xác định cách ứng dụng cần truy vấn và cập nhật dữ liệu:

| Nhu cầu | Câu hỏi thiết kế |
| --- | --- |
| Lưu danh sách tag | Có cần tìm sản phẩm theo một tag? Có cần ràng buộc từng tag với danh mục chuẩn? |
| Lưu nhiều mã tùy chọn | Các phần tử có thứ tự không? Có trùng lặp không? Có cần join với bảng khác không? |
| Lưu ảnh/tệp | Kích thước lớn nhất? Có cần stream? Có thường xuyên tải cùng dữ liệu sản phẩm không? |
| Chia sẻ dữ liệu nhiều DB | Các hệ quản trị có cùng kiểu dữ liệu và JDBC behavior không? |
| Cập nhật từng phần tử | Có cần thêm/xóa một tag mà không ghi lại cả danh sách không? |

Những câu trả lời này quyết định nên dùng SQL ARRAY, JSON, bảng con, cột binary hay hệ thống lưu file riêng.

## 2. Mảng trong Java và mảng trong SQL là hai khái niệm khác nhau

Java có mảng như `String[]`, `Long[]`, `int[]`. Một số hệ quản trị có kiểu mảng ở cấp SQL, ví dụ PostgreSQL có `text[]` và `integer[]`. Nhưng **không phải database quan hệ nào cũng có kiểu cột ARRAY tương đương**.

Ví dụ PostgreSQL:

```sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[]
);

INSERT INTO catalog_product (name, tags)
VALUES ('Mechanical Keyboard', ARRAY['keyboard', 'office', 'wireless']);

SELECT id, name, tags
FROM catalog_product
WHERE 'wireless' = ANY(tags);
```

Ở đây `tags` là một cột có kiểu SQL ARRAY chứa nhiều phần tử text. Nó vẫn là **một cột của một hàng**, không phải một bảng riêng. Câu truy vấn `ANY(tags)` là cú pháp của PostgreSQL, không phải SQL portable cho mọi database.

Có thể biểu diễn cùng thông tin trong Java:

```java
public record ProductTags(
    Long productId,
    String[] tags
) {}
```

Tuy nhiên, chỉ khai báo `String[]` không đảm bảo Spring Data JDBC sẽ tự động ghi/đọc được cột ARRAY trên tất cả driver. Việc chuyển đổi cần được hỗ trợ bởi phiên bản Spring Data Relational, kiểu JDBC mà driver trả về và database dialect đang dùng. Với kiểu SQL vendor-specific, phải kiểm chứng trên database thực tế; khi cần có thể dùng custom conversion hoặc một repository method chạy JDBC tường minh.

### Đừng nhầm collection con với một cột ARRAY

Trong Spring Data JDBC, collection nằm trong aggregate có ý nghĩa về **ranh giới aggregate và vòng đời dữ liệu**. Ví dụ:

```java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
    List<OrderLine> lines
) {}
```

`lines` biểu diễn các dòng hàng thuộc aggregate đơn hàng; mỗi phần tử có thể được lưu thành một hàng trong bảng con `order_line`. Đây không phải chỉ thị để lưu toàn bộ danh sách vào một cột SQL ARRAY.

So sánh:

| Mô hình | Cách lưu | Khi phù hợp |
| --- | --- | --- |
| SQL ARRAY | Nhiều giá trị cùng kiểu nằm trong một cột của một hàng. | Danh sách scalar nhỏ, thường đọc/ghi cùng nhau và database hỗ trợ tốt. |
| Collection thuộc aggregate | Mỗi phần tử được lưu ở bảng con theo mapping aggregate. | Phần tử có cấu trúc, có thuộc tính riêng hoặc có vòng đời gắn với root. |
| Bảng liên kết độc lập | Mỗi phần tử/quan hệ là một hàng có khóa riêng. | Cần tìm kiếm, ràng buộc, join hoặc cập nhật độc lập. |
| JSON | Một tài liệu có cấu trúc nằm trong một cột. | Dữ liệu linh hoạt, ít cần ràng buộc quan hệ ở từng phần tử. |

Nếu tag cần lọc, thống kê, ràng buộc hoặc join thường xuyên, bảng liên kết chuẩn hóa thường dễ kiểm soát hơn. Nếu chỉ là vài nhãn scalar được đọc cùng sản phẩm và database hỗ trợ ARRAY tốt, mảng SQL có thể phù hợp.

## 3. JDBC biểu diễn SQL ARRAY như thế nào?

JDBC có kiểu `java.sql.Array` và các phương thức như `Connection.createArrayOf(...)`, `PreparedStatement.setArray(...)`, `ResultSet.getArray(...)`. Nhưng khả năng hỗ trợ cụ thể phụ thuộc driver và database.

Ví dụ PostgreSQL với Spring `JdbcTemplate`:

```java
import java.sql.Array;
import java.sql.PreparedStatement;
import java.util.Arrays;

import org.springframework.jdbc.core.ConnectionCallback;
import org.springframework.jdbc.core.JdbcTemplate;

public class ProductTagJdbcRepository {

    private final JdbcTemplate jdbcTemplate;

    public ProductTagJdbcRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public void replaceTags(long productId, String[] tags) {
        jdbcTemplate.execute((ConnectionCallback<Void>) connection -> {
            Array sqlArray = connection.createArrayOf("text", tags);

            try (PreparedStatement statement = connection.prepareStatement(
                    "UPDATE catalog_product SET tags = ? WHERE id = ?")) {
                statement.setArray(1, sqlArray);
                statement.setLong(2, productId);
                statement.executeUpdate();
            } finally {
                sqlArray.free();
            }

            return null;
        });
    }
}
```

Điểm cần hiểu:

- `createArrayOf("text", tags)` yêu cầu driver tạo SQL ARRAY có phần tử kiểu text. Tên kiểu phần tử là thông tin phụ thuộc database/driver; ví dụ này nhắm đến PostgreSQL.
- `setArray(...)` truyền đối tượng JDBC ARRAY làm tham số, không ghép chuỗi tag vào SQL.
- `JdbcTemplate` quản lý việc lấy/trả connection theo cơ chế Spring; nếu phương thức được gọi trong transaction Spring phù hợp, thao tác có thể tham gia transaction đó.
- `Array.free()` giải phóng tài nguyên JDBC của đối tượng array sau khi dùng.

Đây là cách dùng JDBC tường minh để minh họa khả năng của driver. Nó **không phải** một ví dụ cho thấy mọi thuộc tính `String[]` trong entity Spring Data JDBC đều tự động được map theo cách trên. Nếu muốn tích hợp kiểu ARRAY vào aggregate repository, cần kiểm tra custom conversion/mapping phù hợp với phiên bản đang dùng và thử cả đọc lẫn ghi. Một hướng khác là giữ thao tác ARRAY trong custom repository fragment dùng `JdbcTemplate`, với quy ước rõ ràng về trường dữ liệu đó.

Đọc một ARRAY bằng JDBC cũng cần xử lý tài nguyên:

```java
Array sqlArray = resultSet.getArray("tags");
try {
    String[] tags = sqlArray == null
        ? null
        : (String[]) sqlArray.getArray();
    // Chuyển tags sang kiểu miền nghiệp vụ tại đây.
} finally {
    if (sqlArray != null) {
        sqlArray.free();
    }
}
```

Kiểu Java cụ thể được trả từ `getArray()` tùy driver. Không nên ép kiểu một cách mù quáng trong code dùng nhiều database; hãy xác minh kết quả thực tế và viết adapter/converter cho kiểu được ứng dụng chuẩn hóa.

## 4. Các lựa chọn thay SQL ARRAY

Nếu database không có native ARRAY hoặc cần khả năng truy vấn linh hoạt, có một số mô hình thay thế.

### 4.1. Bảng con hoặc bảng liên kết

Với danh sách tag cần tìm kiếm và quản trị, có thể thiết kế:

```sql
CREATE TABLE product_tag (
    product_id BIGINT NOT NULL,
    tag VARCHAR(80) NOT NULL,
    PRIMARY KEY (product_id, tag),
    FOREIGN KEY (product_id) REFERENCES catalog_product(id)
);

CREATE INDEX idx_product_tag_tag
    ON product_tag(tag);
```

Ưu điểm:

- Dùng được rộng rãi trên các hệ quản trị quan hệ.
- Có thể index từng tag, join, đếm và lọc hiệu quả.
- Có thể áp dụng unique constraint và foreign key.
- Có thể cập nhật một phần tử mà không ghi lại toàn bộ danh sách.

Nhược điểm là cần thêm hàng, join và thao tác ghi. Nếu tag là một phần của aggregate Product, có thể mô hình hóa nó thành collection con và để thao tác lưu đi qua root; nếu tag là thực thể độc lập hoặc dùng chung, cân nhắc bảng liên kết/aggregate phù hợp.

### 4.2. JSON

Một số database hỗ trợ kiểu JSON hoặc JSON binary. Ví dụ PostgreSQL:

```sql
CREATE TABLE catalog_product_json (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags JSONB NOT NULL DEFAULT '[]'::jsonb
);

SELECT id, name
FROM catalog_product_json
WHERE tags @> '["wireless"]'::jsonb;
```

JSON hữu ích khi cấu trúc thay đổi hoặc có các thuộc tính linh hoạt. Nhưng JSON không đồng nghĩa với ARRAY:

- JSON có thể chứa object, array, string, number, boolean và null.
- Cách index, truy vấn và validate JSON khác theo database.
- Ràng buộc quan hệ ở từng phần tử thường khó thể hiện hơn bảng chuẩn hóa.
- Cần quy ước schema JSON ở tầng ứng dụng để tránh mỗi bản ghi có cấu trúc tùy tiện.

MySQL có kiểu JSON; PostgreSQL có `json/jsonb`; SQL Server và Oracle có khả năng xử lý JSON với cú pháp/phiên bản riêng; SQLite thường dựa trên JSON functions/extension và cách lưu text. Không nên giả định một câu truy vấn JSON chạy giống nhau ở tất cả hệ quản trị.

### 4.3. Chuỗi phân tách

Có thể lưu `"keyboard,office,wireless"` trong một cột text, nhưng cách này thường không phù hợp cho dữ liệu cần truy vấn:

- Tag có dấu phân tách cần escaping.
- Khó phân biệt phần tử rỗng, null và chuỗi có khoảng trắng.
- Index từng phần tử khó và phụ thuộc truy vấn.
- Không có foreign key hoặc unique constraint ở cấp phần tử.

Chỉ nên chọn chuỗi phân tách cho dữ liệu rất đơn giản, không cần truy vấn từng phần tử và có định dạng được kiểm soát chặt. Với phần lớn nghiệp vụ, bảng con hoặc JSON rõ ràng hơn.

## 5. Dữ liệu nhị phân trong Java và SQL

Dữ liệu nhị phân là chuỗi byte, ví dụ ảnh, PDF, tệp đính kèm, nội dung mã hóa hoặc hash. Java thường dùng `byte[]` cho payload đã được đọc vào bộ nhớ.

Ví dụ một record lưu metadata và nội dung ảnh nhỏ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("product_asset")
public record ProductAsset(
    @Id Long id,
    Long productId,
    String fileName,
    String contentType,
    byte[] content
) {}
```

`byte[]` có ý nghĩa khác với `String[]`: nó là một dãy byte dùng làm **một giá trị nhị phân**, không phải collection các bản ghi con. Spring Data JDBC và driver có thể ánh xạ kiểu binary scalar này vào cột nhị phân tương ứng. Tuy vậy, kiểu SQL cụ thể vẫn phụ thuộc database và cần xác nhận trên dialect/driver thực tế.

### Kiểu cột binary theo hệ quản trị

| Database | Kiểu thường gặp | Ghi chú |
| --- | --- | --- |
| PostgreSQL | `BYTEA` | Lưu chuỗi byte trong một giá trị; driver JDBC hỗ trợ `byte[]`. |
| MySQL | `BLOB`, `MEDIUMBLOB`, `LONGBLOB` | Chọn giới hạn dung lượng theo nhu cầu; các loại có giới hạn khác nhau. |
| Oracle | `BLOB` | Large Object; JDBC driver có API hỗ trợ LOB. |
| SQL Server | `VARBINARY(n)`, `VARBINARY(MAX)` | `MAX` dành cho giá trị lớn hơn giới hạn độ dài thường. |
| SQLite | `BLOB` | SQLite lưu binary dưới storage class BLOB. |
| H2 | `BLOB` | Thích hợp cho demo/test, nhưng không đại diện mọi hành vi của database production. |

DDL PostgreSQL:

```sql
CREATE TABLE product_asset (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    product_id BIGINT NOT NULL,
    file_name VARCHAR(255) NOT NULL,
    content_type VARCHAR(120) NOT NULL,
    content BYTEA NOT NULL
);
```

Ví dụ MySQL có thể dùng `LONGBLOB` nếu cần lưu file lớn; SQL Server thường dùng `VARBINARY(MAX)`; Oracle dùng `BLOB`. Chọn kiểu phù hợp với giới hạn dung lượng và chính sách backup/replication của hệ quản trị.

### Ghi và đọc bằng JDBC

```java
jdbcTemplate.update(
    "INSERT INTO product_asset " +
    "(product_id, file_name, content_type, content) " +
    "VALUES (?, ?, ?, ?)",
    productId,
    fileName,
    contentType,
    contentBytes
);
```

`JdbcTemplate` sẽ bind `byte[]` vào tham số JDBC. Đọc giá trị nhỏ/vừa:

```java
byte[] content = jdbcTemplate.queryForObject(
    "SELECT content FROM product_asset WHERE id = ?",
    (resultSet, rowNum) -> resultSet.getBytes("content"),
    assetId
);
```

Với Spring Data JDBC, có thể ánh xạ một thuộc tính `byte[]` trong aggregate nếu mapping/driver hỗ trợ kiểu binary tương ứng. Nên kiểm thử insert, select và update với đúng database đích; không dùng riêng H2 làm bằng chứng rằng mọi driver khác đều hoạt động như nhau.

## 6. BLOB/LOB và kích thước dữ liệu lớn

Thuật ngữ LOB (Large Object) thường chỉ dữ liệu lớn, gồm binary large object (BLOB) và character large object (CLOB). Các hệ quản trị có API, giới hạn kích thước, cách lưu vật lý và hành vi streaming khác nhau.

Cần phân biệt:

- `byte[]` thường đưa toàn bộ payload vào bộ nhớ Java.
- `java.sql.Blob` có thể đại diện một LOB gắn với connection/transaction; thời gian sống của locator phụ thuộc driver và connection.
- Streaming qua JDBC có thể giảm nhu cầu giữ toàn bộ nội dung trong heap, nhưng cần quản lý stream, connection và transaction đúng vòng đời.
- Việc lưu dữ liệu lớn trực tiếp trong database làm tăng kích thước backup, replication và tải I/O; đổi lại dữ liệu có thể tham gia transaction và chính sách backup chung.

Với ảnh nhỏ, avatar hoặc nội dung vài KB/MB có tần suất đọc phù hợp, `byte[]` có thể đơn giản. Với video, file lớn hoặc dữ liệu được tải độc lập với thông tin đơn hàng, thường cân nhắc object storage/file storage và chỉ lưu metadata + object key trong database.

Ví dụ metadata:

```java
@Table("product_asset")
public record ProductAsset(
    @Id Long id,
    Long productId,
    String fileName,
    String contentType,
    Long sizeInBytes,
    String storageKey
) {}
```

Khi chọn object storage, ứng dụng cần xử lý quyền truy cập, mã hóa, URL hết hạn, xóa file mồ côi và nhất quán giữa thao tác database với upload/delete. Transaction SQL không tự rollback một file đã upload lên dịch vụ bên ngoài; cần thiết kế quy trình bù trừ hoặc trạng thái trung gian.

### Vì sao không nên tải mọi file cùng aggregate?

Giả sử màn hình danh sách sản phẩm chỉ cần tên, giá và ảnh thumbnail URL. Nếu mỗi lần tải `Product` đều kéo theo một BLOB lớn, ứng dụng tiêu tốn băng thông, heap và thời gian truy vấn cho dữ liệu không được dùng.

Có thể tách metadata và binary thành aggregate/bảng riêng, hoặc dùng query projection chỉ lấy các cột cần thiết. Với tệp lớn, dùng một đường truy cập streaming chuyên biệt. Không nên đặt payload lớn vào aggregate chỉ vì nó có thể biểu diễn bằng một field Java.

## 7. Mức hỗ trợ khác nhau giữa các database

Bảng dưới đây là định hướng thiết kế; hỗ trợ thực tế còn tùy phiên bản database, driver JDBC, dialect và kiểu SQL cụ thể.

| Database | Native array column | Binary | Hướng thường dùng khi không có ARRAY |
| --- | --- | --- | --- |
| PostgreSQL | Có, ví dụ `text[]`, `integer[]`. | `BYTEA`, ngoài ra có Large Object API. | ARRAY, bảng liên kết hoặc JSONB theo nhu cầu. |
| MySQL | Không có kiểu cột SQL ARRAY tổng quát tương đương PostgreSQL. | `BLOB` family. | Bảng liên kết hoặc JSON. |
| Oracle | Có SQL collection types như VARRAY/nested table; mapping thường cần xử lý theo Oracle JDBC. | `BLOB`. | Bảng quan hệ hoặc collection type/JSON theo kiến trúc. |
| SQL Server | Không có native ARRAY column tổng quát. Table-valued parameter là cơ chế truyền tập dữ liệu vào routine, không phải kiểu cột array. | `VARBINARY(MAX)`. | Bảng liên kết, table-valued parameter cho input, hoặc JSON. |
| SQLite | Không có native ARRAY column. | `BLOB`. | Bảng liên kết hoặc JSON/text có kiểm soát. |
| H2 | Có hỗ trợ ARRAY ở mức database, nhưng không bảo đảm tương đương các vendor khác. | `BLOB`. | Hữu ích cho test cơ bản; vẫn cần test với database đích. |

### Các giới hạn cần chú ý

**PostgreSQL.** Native array khá tiện cho tập scalar cùng kiểu, có toán tử và hàm truy vấn riêng. Driver có hỗ trợ JDBC ARRAY nhưng tên kiểu, cách lấy Java array và một số kiểu phần tử có thể cần xử lý rõ. PostgreSQL array không tự cung cấp ràng buộc khóa ngoại riêng cho từng phần tử như bảng chuẩn hóa.

**MySQL.** Dùng JSON nếu cần một cột chứa danh sách linh hoạt, hoặc bảng con nếu cần join, index từng phần tử và FK. JSON của MySQL có hàm riêng và giới hạn/indexing theo phiên bản; không coi nó là native SQL ARRAY.

**Oracle.** Có collection types ở SQL, nhưng việc tạo type, bind/đọc collection và chuyển sang Java thường gắn với Oracle JDBC API và type name do schema định nghĩa. Cần integration test trên Oracle thật; không suy ra từ test H2.

**SQL Server.** Table-valued parameter có thể truyền nhiều hàng vào stored procedure/function, nhưng đó không phải một kiểu cột ARRAY được lưu trong mỗi hàng. Nếu cần lưu danh sách lâu dài, bảng liên kết hoặc JSON thường phù hợp hơn.

**SQLite.** Không có ARRAY column. Dùng bảng liên kết hoặc JSON/text theo yêu cầu truy vấn và mức kiểm soát dữ liệu. Kiểu BLOB dùng để lưu byte.

**H2.** H2 hữu ích cho test nhanh, nhưng kiểu ARRAY, cú pháp, metadata và driver behavior có thể khác PostgreSQL/MySQL/Oracle/SQL Server. Chế độ tương thích của H2 cũng không thay thế kiểm thử trên engine thật.

## 8. Spring Data JDBC xử lý các kiểu này như thế nào?

Spring Data JDBC tập trung vào aggregate mapping và sử dụng Spring JDBC/driver để trao đổi dữ liệu. Nó có hệ thống simple type/conversion và hỗ trợ mở rộng conversion; nhưng không thể suy ra rằng mọi kiểu dữ liệu đặc thù của mọi database đều được hỗ trợ tự động.

Có thể chia tình huống:

| Kiểu thuộc tính Java | Hướng xử lý |
| --- | --- |
| `byte[]` | Thường là binary scalar; đối chiếu kiểu cột BLOB/BYTEA/VARBINARY và driver. |
| `String[]` hoặc `Integer[]` | Không giả định tự động tương thích với native ARRAY; xác minh mapping và driver. |
| `List<OrderLine>` | Collection con trong aggregate; dùng bảng con và mapping như `@MappedCollection`. |
| `List<String>` | Cần xác định đây là collection được lưu thành hàng con hay dữ liệu scalar/ARRAY/JSON; không để ý nghĩa mơ hồ. |
| Value object tùy biến | Đăng ký custom converter hoặc chuyển đổi ở custom repository. |
| `java.sql.Array`/`Blob` | Kiểu JDBC có vòng đời/tài nguyên phụ thuộc connection; không tùy tiện giữ locator sau khi connection đóng. |

### Custom conversion và custom repository

Khi muốn dùng native ARRAY trong domain model, có hai hướng tổng quát:

1. **Custom conversion:** định nghĩa cách chuyển giữa kiểu domain Java và kiểu mà Spring Data JDBC/driver có thể bind/read. Đăng ký conversion theo extension point được phiên bản Spring Data JDBC sử dụng hỗ trợ. Cần kiểm tra cả chiều ghi lẫn chiều đọc và loại JDBC/SQL thực tế.
2. **Custom repository/JdbcTemplate:** giữ SQL vendor-specific trong một adapter riêng, dùng `Connection.createArrayOf`, `PreparedStatement.setArray` và `ResultSet.getArray`. Cách này làm rõ ranh giới database-specific và cho phép kiểm soát tài nguyên JDBC.

Đừng viết converter chung cho mọi database nếu mỗi driver yêu cầu một API khác nhau. Có thể định nghĩa interface miền nghiệp vụ như `ProductTagStore` rồi cung cấp implementation riêng cho PostgreSQL, MySQL hoặc database khác.

Ví dụ ranh giới interface:

```java
public interface ProductTagStore {
    void replaceTags(long productId, List<String> tags);
    List<String> findTags(long productId);
}
```

Implementation PostgreSQL có thể dùng SQL ARRAY; implementation MySQL có thể dùng JSON hoặc bảng con. Service gọi interface thống nhất, trong khi chi tiết JDBC nằm ở adapter tương ứng.

### Không trộn hai mô hình lưu cùng một thuộc tính

Nếu repository aggregate và custom JDBC cùng ghi một cột, cần quy định ai sở hữu việc cập nhật. Ví dụ, nếu `PurchaseOrderRepository.save(order)` không hiểu trường native ARRAY nhưng một custom DAO lại sửa cột đó, lần lưu aggregate sau có thể không giữ được giá trị như mong muốn tùy mapping/conversion. Nên đặt rõ trách nhiệm, viết test round-trip và tránh hai đường ghi không phối hợp.

## 9. Chọn mô hình theo tiêu chí nghiệp vụ

| Tiêu chí | SQL ARRAY | Bảng con/liên kết | JSON | Binary/LOB |
| --- | --- | --- | --- | --- |
| Nhiều phần tử cùng kiểu scalar | Phù hợp nếu DB hỗ trợ. | Phù hợp. | Có thể, nhưng linh hoạt hơn cần thiết. | Không áp dụng. |
| Tìm kiếm/index từng phần tử | Vendor-specific; có thể hỗ trợ tốt ở DB phù hợp. | Rất phù hợp với index/SQL quan hệ. | Có thể nhưng phụ thuộc engine. | Không áp dụng. |
| FK cho từng phần tử | Thường không phù hợp. | Phù hợp. | Không thuận tiện. | Không áp dụng. |
| Thêm/xóa một phần tử | Có thể phải ghi lại array hoặc dùng toán tử riêng. | Cập nhật một hàng. | Có thể dùng JSON function nhưng vendor-specific. | Không áp dụng. |
| Tương thích nhiều DB | Thấp đến trung bình. | Cao. | Trung bình, khác cú pháp/khả năng. | Kiểu binary phổ biến nhưng tên/giới hạn khác. |
| Dữ liệu rất lớn | Không phù hợp cho payload file. | Không phù hợp cho file lớn. | Thường không tối ưu cho binary. | Phù hợp nếu cần DB quản lý; cân nhắc streaming/object storage. |

Quy tắc lựa chọn có thể nhớ:

- Danh sách phần tử có danh tính, quan hệ hoặc cần truy vấn từng phần tử: dùng bảng con/bảng liên kết.
- Danh sách scalar nhỏ, ít thay đổi, database hỗ trợ native ARRAY và ứng dụng chấp nhận phụ thuộc vendor: cân nhắc SQL ARRAY.
- Dữ liệu linh hoạt có cấu trúc lồng nhau, ít cần FK ở từng node: cân nhắc JSON.
- Byte payload nhỏ/vừa cần transaction cùng dữ liệu: cân nhắc binary column.
- File lớn, được tải độc lập hoặc cần CDN: cân nhắc object storage và lưu metadata/key trong database.

## 10. Kiểm thử trên database thật

Kiểm thử bằng H2 có ích để xác nhận luồng repository cơ bản, nhưng không đủ để chứng minh SQL ARRAY hoặc kiểu LOB hoạt động giống database production.

Một chiến lược kiểm thử phù hợp:

1. **Unit test domain:** kiểm tra tag trùng, danh sách rỗng, null, kích thước payload và validation nghiệp vụ.
2. **Integration test trên engine đích:** chạy PostgreSQL nếu production dùng PostgreSQL; tương tự với MySQL, Oracle hoặc SQL Server.
3. **Round-trip test:** ghi rồi đọc lại ARRAY, binary, JSON hoặc LOB; so sánh chính xác giá trị và null/empty semantics.
4. **Boundary test:** kiểm tra mảng rỗng, phần tử null (nếu cho phép), chuỗi Unicode, byte array rỗng, payload gần giới hạn và giá trị quá lớn.
5. **Resource test:** bảo đảm `java.sql.Array.free()`/stream/LOB được giải phóng đúng và connection được trả về pool.
6. **Transaction test:** tạo lỗi sau thao tác ghi để kiểm tra rollback của phần dữ liệu nằm trong cùng datasource/transaction.
7. **Portability test:** nếu hỗ trợ nhiều DB, chạy cùng contract test trên từng engine thay vì chỉ dùng H2 compatibility mode.

Có thể dùng Testcontainers để khởi chạy database thật trong integration test. Mục tiêu không chỉ là kiểm tra câu SQL chạy được mà còn kiểm tra driver trả kiểu Java nào, dialect tạo SQL ra sao và giới hạn dung lượng thực tế.

## 11. Ví dụ tổng hợp cho sản phẩm

Giả sử sản phẩm có danh sách tag và một ảnh preview nhỏ. PostgreSQL có thể dùng ARRAY cho tag và BYTEA cho ảnh:

```sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(180) NOT NULL,
    tags TEXT[] NOT NULL DEFAULT ARRAY[]::TEXT[],
    preview_image BYTEA
);
```

Ở tầng Java, metadata và binary có thể biểu diễn như:

```java
public record ProductAssetView(
    Long productId,
    String name,
    String[] tags,
    byte[] previewImage
) {}
```

Đây là DTO minh họa dữ liệu trả về, không phải cam kết rằng Spring Data JDBC tự động map mọi trường thành công với mọi driver. Trong một implementation PostgreSQL, adapter có thể dùng JDBC ARRAY cho `tags` và binary binding cho `preview_image`. Nếu chuyển sang MySQL, có thể thay tag bằng JSON hoặc bảng `product_tag`; kiểu ảnh chuyển sang BLOB family. Domain/service vẫn dùng hợp đồng tag và ảnh, còn adapter chịu trách nhiệm chi tiết lưu trữ.

Nếu tag cần lọc nhiều, chuyển sang bảng `product_tag` có thể hợp lý hơn ngay cả trên PostgreSQL. Nếu preview image lớn hoặc nhiều màn hình không cần tải ảnh, lưu file ngoài database và chỉ giữ object key có thể giảm tải cho truy vấn sản phẩm.

## 12. Câu hỏi tự kiểm tra

- Vì sao `String[]` trong Java không đồng nghĩa với việc mọi database có thể lưu trực tiếp bằng một cột ARRAY?
- `java.sql.Array` và `byte[]` khác nhau thế nào về mục đích và vòng đời?
- Vì sao `List<OrderLine>` trong aggregate không nên bị hiểu là một SQL ARRAY?
- Database nào trong hệ thống đang dùng có native ARRAY? Driver JDBC có hỗ trợ bind/read theo cách nào?
- Khi nào nên chuyển danh sách tag sang bảng liên kết thay vì lưu ARRAY hoặc JSON?
- Sự khác nhau giữa PostgreSQL `BYTEA`, MySQL `LONGBLOB` và SQL Server `VARBINARY(MAX)` là gì?
- Vì sao `byte[]` có thể gây áp lực heap khi tải nhiều aggregate có file lớn?
- Vì sao H2 test pass chưa chứng minh được PostgreSQL ARRAY hoặc Oracle collection mapping hoạt động?
- Khi dùng custom repository cho ARRAY, làm thế nào bảo đảm nó phối hợp đúng với transaction và đường lưu aggregate?

Một quyết định lưu trữ tốt cần khớp đồng thời **ngữ nghĩa miền nghiệp vụ, kiểu Java, kiểu SQL, khả năng JDBC driver và chiến lược truy vấn**. Spring Data JDBC giúp tổ chức thao tác dữ liệu theo aggregate; với ARRAY, JSON và LOB đặc thù, ứng dụng phải xác định rõ phần nào được mapping mặc định hỗ trợ và phần nào cần adapter/converter riêng.
