# `Like`, `StartingWith`, `EndingWith` và `Containing`

Trong **Spring Data JDBC**, derived query cho phép tìm chuỗi theo mẫu ngay trong tên phương thức repository. Bốn từ khóa thường gặp là `Like`, `StartingWith`, `EndingWith` và `Containing`. Chúng đều tạo điều kiện SQL dựa trên toán tử `LIKE`, nhưng khác nhau ở cách xử lý ký tự đại diện `%` và `_` trong giá trị tham số.

Điểm cần phân biệt:

- **`Like`**: dùng mẫu `LIKE` do caller truyền vào; caller tự quyết định vị trí wildcard.
- **`StartingWith`**: tìm giá trị bắt đầu bằng chuỗi truyền vào; Spring Data thêm `%` ở cuối tham số.
- **`EndingWith`**: tìm giá trị kết thúc bằng chuỗi truyền vào; Spring Data thêm `%` ở đầu tham số.
- **`Containing`**: tìm giá trị có chứa chuỗi truyền vào ở bất kỳ vị trí nào; Spring Data thêm `%` ở cả hai đầu.

Các method này giúp biểu đạt nhu cầu tìm kiếm phổ biến mà không phải tự nối chuỗi SQL. Tuy nhiên, kết quả còn phụ thuộc collation, quy tắc hoa/thường, cách database xử lý chuỗi rỗng và khả năng sử dụng index của hệ quản trị.

## 1. `LIKE` trong SQL hoạt động thế nào?

`LIKE` so khớp một giá trị chuỗi với một mẫu (pattern). Hai ký tự đại diện quan trọng:

| Ký tự | Ý nghĩa | Ví dụ mẫu | Một số chuỗi khớp |
|---|---|---|---|
| `%` | Không hoặc nhiều ký tự bất kỳ | `Ann%` | `Ann`, `Anna`, `Annette` |
| `_` | Chính xác một ký tự bất kỳ | `A_n` | `Ann`, `A-n`, `A1n` |

Ví dụ SQL:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE 'Ann%';
```

Truy vấn tìm các tên bắt đầu bằng `Ann`. Trong khi đó:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE '%son';
```

tìm các tên kết thúc bằng `son`, còn:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE '%ann%';
```

tìm các tên có chứa `ann` ở bất kỳ vị trí nào.

`LIKE` là toán tử SQL; `StartingWith`, `EndingWith` và `Containing` là từ khóa trong tên phương thức Spring Data. Spring Data chuyển các ý nghĩa này thành điều kiện `LIKE` và chuẩn bị giá trị bind tương ứng.

## 2. Ví dụ entity và repository

Giả sử ứng dụng quản lý khách hàng:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(200) NOT NULL
);
```

Entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email
) {}
```

Repository:

```java
import java.util.List;
import org.springframework.data.repository.ListCrudRepository;

public interface CustomerRepository
        extends ListCrudRepository<Customer, Long> {

    List<Customer> findByNameLike(String pattern);

    List<Customer> findByNameStartingWith(String prefix);

    List<Customer> findByNameEndingWith(String suffix);

    List<Customer> findByNameContaining(String fragment);
}
```

Tên method tham chiếu property Java `name`. Nếu property được ánh xạ sang một cột có tên khác bằng `@Column`, Spring Data dùng metadata để chọn cột vật lý. Ví dụ này dùng tên cột `name` trực tiếp nên dễ đối chiếu với DDL.

## 3. `Like`: caller cung cấp toàn bộ pattern

Method:

```java
List<Customer> findByNameLike(String pattern);
```

`Like` chuyển giá trị được truyền vào thành pattern của SQL `LIKE`. Spring Data không tự suy ra rằng caller muốn tìm prefix, suffix hay substring; vị trí `%` và `_` thuộc trách nhiệm của pattern.

Ví dụ:

```java
repository.findByNameLike("Ann%");   // Bắt đầu bằng Ann
repository.findByNameLike("%son");   // Kết thúc bằng son
repository.findByNameLike("%ann%");  // Có chứa ann
repository.findByNameLike("A_n");    // A, một ký tự bất kỳ, rồi n
```

SQL có ý nghĩa tương đương:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE ?;
```

Tham số bind lần lượt là `Ann%`, `%son`, `%ann%` hoặc `A_n`. Vì `Like` nhận pattern đầy đủ, caller cần hiểu rõ wildcard của SQL. Nếu người dùng nhập `100%`, ký tự `%` sẽ được hiểu là wildcard nếu không được escape theo quy tắc pattern.

## 4. `StartingWith`: thêm wildcard ở cuối

Method:

```java
List<Customer> findByNameStartingWith(String prefix);
```

Khi gọi:

```java
repository.findByNameStartingWith("Ann");
```

Spring Data tạo điều kiện tương đương:

```sql
WHERE name LIKE ?
```

với giá trị bind tương đương `Ann%`.

`%` ở cuối có nghĩa sau chuỗi `Ann` có thể không có ký tự nào hoặc có thêm nhiều ký tự. Vì vậy kết quả có thể gồm `Ann`, `Anna`, `Annette`, `Ann Marie`...

Không cần tự truyền `%` vào tham số:

```java
// Truyền chuỗi gốc, không thêm wildcard thủ công.
repository.findByNameStartingWith("Ann");
```

Nếu truyền `Ann%`, wildcard `%` trong dữ liệu đầu vào có thể được xử lý như ký tự cần tìm theo cơ chế escape của derived query, và framework vẫn tự thêm wildcard kết thúc. Hãy truyền **prefix thực tế** thay vì tự dựng pattern cho `StartingWith`.

## 5. `EndingWith`: thêm wildcard ở đầu

Method:

```java
List<Customer> findByNameEndingWith(String suffix);
```

Lời gọi:

```java
repository.findByNameEndingWith("son");
```

có ý nghĩa tương đương:

```sql
WHERE name LIKE ?
```

với tham số bind `%son`.

Wildcard ở đầu cho phép có không hoặc nhiều ký tự trước `son`, nên `Jackson`, `Anderson` hoặc `son` có thể khớp.

Tương tự `StartingWith`, caller chỉ truyền suffix. Không tự thêm `%` ở đầu khi dùng keyword này.

## 6. `Containing`: thêm wildcard ở cả hai đầu

Method:

```java
List<Customer> findByNameContaining(String fragment);
```

Lời gọi:

```java
repository.findByNameContaining("ann");
```

có ý nghĩa tương đương:

```sql
WHERE name LIKE ?
```

với tham số bind `%ann%`.

Điều kiện này tìm chuỗi `ann` ở bất kỳ vị trí nào. Nó có thể khớp `Ann`, `Joanne`, `Ann Marie` tùy quy tắc phân biệt hoa/thường của database.

`Containing` thường tiện cho ô tìm kiếm tự do, nhưng cần cân nhắc hiệu năng vì wildcard ở đầu (`%ann%`) thường khiến B-tree index thông thường khó hỗ trợ tìm kiếm theo prefix.

## 7. So sánh bốn từ khóa

Giả sử tham số đầu vào đều là chuỗi `ann`:

| Derived keyword | Pattern SQL tương đương | Ý nghĩa |
|---|---|---|
| `Like` | `ann` | Khớp chính xác pattern `ann` nếu không có wildcard |
| `StartingWith` | `ann%` | Bắt đầu bằng `ann` |
| `EndingWith` | `%ann` | Kết thúc bằng `ann` |
| `Containing` | `%ann%` | Có chứa `ann` |

SQL khái quát cho cả bốn method đều có dạng:

```sql
SELECT id, name, email
FROM customers
WHERE name LIKE ?;
```

Điểm khác nhau nằm ở **giá trị tham số đã được chuẩn bị**. `Like` dùng pattern caller truyền; ba keyword còn lại thêm wildcard theo vị trí tương ứng.

## 8. Ví dụ với dữ liệu cụ thể

Giả sử bảng `customers` có dữ liệu:

| id | name |
|---:|---|
| 1 | Ann |
| 2 | Anna Smith |
| 3 | Joanne |
| 4 | Anderson |
| 5 | Susan |
| 6 | An-n |
| 7 | Bob |

Với chuỗi `Ann`:

- `findByNameLike("Ann")`: chỉ khớp pattern chính xác `Ann` (không có wildcard).
- `findByNameStartingWith("Ann")`: khớp `Ann` và `Anna Smith`.
- `findByNameEndingWith("Ann")`: khớp các tên kết thúc bằng `Ann`; trong dữ liệu ví dụ không có hàng nào.
- `findByNameContaining("Ann")`: khớp `Ann` và `Anna Smith` nếu phép so sánh phân biệt hoa/thường theo mặc định.

Nếu dùng fragment `ann` chữ thường, kết quả có thể khác do collation/case sensitivity. Đừng suy luận rằng `LIKE` luôn không phân biệt hoa/thường trên mọi database.

## 9. Escape ký tự wildcard do người dùng nhập

`%` và `_` là ký tự đặc biệt của SQL `LIKE`. Nếu người dùng muốn tìm chính ký tự phần trăm hoặc gạch dưới, ứng dụng phải tránh để chúng vô tình trở thành wildcard.

Ví dụ người dùng tìm tên chứa chuỗi `50%`:

```text
Input mong muốn: 50%
Ý nghĩa mong muốn: ký tự '5', '0', '%' theo đúng nghĩa đen
```

Nếu pattern được gửi trực tiếp là `%50%%`, dấu `%` do người dùng nhập cũng là wildcard; kết quả có thể rộng hơn mong muốn. SQL có cú pháp `ESCAPE` để định nghĩa ký tự thoát:

```sql
SELECT id, name
FROM customers
WHERE name LIKE '%50!%%' ESCAPE '!';
```

Ở đây `!%` biểu diễn dấu `%` literal; các dấu `%` còn lại là wildcard.

Với derived query `StartingWith`, `EndingWith` và `Containing`, Spring Data có cơ chế escape các ký tự wildcard trong đối số để chúng được hiểu là nội dung tìm kiếm, sau đó thêm wildcard cần thiết cho phép toán. Ký tự escape được dùng bởi cơ chế query derivation; cấu hình cụ thể và hành vi chi tiết cần theo phiên bản Spring Data Relational/JDBC của ứng dụng. `Like` nhận một pattern hoàn chỉnh nên caller cần chủ động tạo pattern và escape nếu dữ liệu có thể chứa wildcard.

Khi viết SQL tùy chỉnh, hãy chỉ rõ cách escape tương thích với database và bind tham số. Không nối chuỗi người dùng vào SQL để tạo pattern. Bind parameter giúp tránh SQL injection, nhưng **không tự biến `%` và `_` thành ký tự literal**; escape wildcard là một vấn đề riêng với ngữ nghĩa `LIKE`.

## 10. Phân biệt hoa/thường và `IgnoreCase`

Hành vi mặc định của `LIKE` phụ thuộc database, collation và kiểu dữ liệu/cấu hình cột. Một số database hoặc collation so sánh không phân biệt hoa/thường; nơi khác phân biệt.

Nếu muốn yêu cầu không phân biệt hoa/thường qua derived query, có thể dùng keyword `IgnoreCase` khi kiểu query và module hỗ trợ:

```java
List<Customer> findByNameContainingIgnoreCase(String fragment);
```

Spring Data có thể tạo điều kiện so sánh dạng chuẩn hóa chữ hoa/chữ thường, ví dụ về ý nghĩa:

```sql
WHERE UPPER(name) LIKE UPPER(?)
```

SQL cụ thể phụ thuộc dialect. Nếu cần bảo đảm chính xác cho database đang dùng, có thể viết `@Query` theo hàm/collation được DBMS hỗ trợ. Việc dùng `UPPER(name)` hoặc `LOWER(name)` trên cột có thể ảnh hưởng khả năng sử dụng index thông thường; cân nhắc functional index hoặc collation thích hợp nếu truy vấn là đường nóng.

`IgnoreCase` không xử lý mọi vấn đề về dấu tiếng Việt, accent, chuẩn Unicode hoặc locale. So sánh `a` với `á`, hoặc các dạng Unicode được biểu diễn khác nhau, phụ thuộc collation và quy tắc normalization của database. Nếu ứng dụng cần tìm kiếm ngôn ngữ tự nhiên chính xác, phải thiết kế quy tắc chuẩn hóa dữ liệu và tìm kiếm rõ ràng.

## 11. Kết hợp với các điều kiện khác

Các keyword tìm chuỗi có thể kết hợp với `And`, `Or` và các property khác:

```java
List<Customer> findByActiveTrueAndNameStartingWith(String prefix);

List<Customer> findByNameContainingOrEmailContaining(
        String nameFragment,
        String emailFragment
);
```

Ví dụ đầu tìm khách hàng đang hoạt động và tên bắt đầu bằng prefix. Ví dụ sau tìm khách có tên chứa fragment **hoặc** email chứa fragment.

SQL có ý nghĩa tương đương cho method thứ hai:

```sql
WHERE name LIKE ?
   OR email LIKE ?
```

Với `Containing`, hai tham số được bao quanh bởi wildcard theo cơ chế derived query. Khi method có cả `And` và `Or`, hãy áp dụng quy tắc nhóm điều kiện của derived query và kiểm tra biểu thức logic. Nếu cần ngoặc khác với cách nhóm mà tên method biểu đạt, dùng `@Query` với dấu ngoặc tường minh.

## 12. Viết `@Query` khi cần pattern hoặc escape tùy chỉnh

Derived query phù hợp với các trường hợp tìm prefix/suffix/substring phổ biến. Nếu cần điều khiển SQL chi tiết, có thể viết:

```java
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.query.Param;

@Query("""
    SELECT id, name, email
    FROM customers
    WHERE name LIKE :pattern
    """)
List<Customer> searchByPattern(@Param("pattern") String pattern);
```

Caller truyền pattern hoàn chỉnh, ví dụ `Ann%`, `%son`, `%ann%`. Đây là SQL tùy chỉnh nên **caller chịu trách nhiệm chuẩn bị wildcard và escape** đúng với câu SQL/database. Không giả định `@Query` tự thêm wildcard như `StartingWith` hoặc `Containing`.

Nếu muốn luôn tìm prefix, có thể viết:

```java
@Query("""
    SELECT id, name, email
    FROM customers
    WHERE name LIKE CONCAT(:prefix, '%')
    """)
List<Customer> searchByPrefix(@Param("prefix") String prefix);
```

Nhưng `CONCAT` không phải cú pháp giống nhau ở mọi database. Với SQL đa nền tảng, cân nhắc chuẩn bị pattern trong Java rồi bind, hoặc dùng derived query để framework lo phần thêm wildcard. Dù chọn cách nào, dữ liệu vẫn phải được truyền bằng bind parameter.

## 13. `NULL`, chuỗi rỗng và wildcard

`LIKE` không trả `TRUE` khi giá trị cột hoặc pattern là `NULL`; biểu thức thường có kết quả `UNKNOWN` và hàng không được chọn trong `WHERE`.

```sql
WHERE name LIKE NULL
```

không tương đương với tìm chuỗi rỗng. Nếu property `name` cho phép null, các method `Like`/`Containing` không tự tìm các hàng null; cần method `IsNull` riêng nếu nghiệp vụ yêu cầu.

Chuỗi rỗng `""` cũng cần chú ý:

- Với `StartingWith("")`, pattern sau khi thêm wildcard có thể là `%`.
- Với `EndingWith("")`, pattern có thể là `%`.
- Với `Containing("")`, pattern có thể là `%%`.
- `Like("")` là pattern rỗng, thường chỉ khớp chuỗi rỗng.

Kết quả cụ thể còn phụ thuộc cách database xử lý chuỗi rỗng. Một số hệ quản trị xem chuỗi rỗng như `NULL`; vì vậy không nên dùng chuỗi rỗng làm điều kiện “không lọc” nếu chưa thống nhất behavior giữa các database. Ở tầng service, có thể bỏ qua query khi input trống hoặc áp dụng quy tắc nghiệp vụ rõ ràng.

## 14. Hiệu năng: prefix, suffix và substring không có chi phí như nhau

Ba dạng pattern có đặc điểm truy vấn khác nhau:

| Dạng tìm kiếm | Pattern | Khả năng tận dụng B-tree index thông thường |
|---|---|---|
| Prefix | `Ann%` | Thường có cơ hội sử dụng index vì không có wildcard ở đầu; phụ thuộc collation, DBMS và execution plan |
| Suffix | `%son` | Thường khó dùng index B-tree theo thứ tự chuỗi thông thường |
| Substring | `%ann%` | Thường khó dùng index B-tree thông thường vì wildcard ở đầu và giữa |
| Pattern tùy ý | Caller cung cấp | Phụ thuộc cấu trúc pattern và optimizer |

Với bảng nhỏ, `Containing` có thể hoàn toàn đủ. Với bảng lớn và tìm kiếm substring là chức năng quan trọng, cân nhắc full-text search, trigram index, inverted index hoặc công cụ tìm kiếm chuyên dụng tùy database và yêu cầu.

Đừng thêm index chỉ dựa trên cảm giác. Hãy kiểm tra execution plan trên dữ liệu có kích thước gần thực tế, đo thời gian truy vấn và xem collation/function có làm index hiện tại mất tác dụng không.

### Tránh `Containing` cho mọi ô tìm kiếm

Nếu người dùng chỉ cần gợi ý theo tiền tố, `StartingWith` thường có đặc tính tốt hơn `Containing`. Ví dụ tìm mã khách hàng thường có thể dùng `findByCustomerCodeStartingWith(prefix)`; còn tìm chuỗi tự do giữa tên có thể cần `Containing` nhưng nên giới hạn độ dài input, kết quả và thời gian xử lý.

## 15. Giới hạn kết quả và phân trang

Truy vấn substring có thể trả về nhiều hàng. Nếu repository trả `List<Customer>`, toàn bộ kết quả được materialize thành List. Với dữ liệu lớn, nên giới hạn số lượng kết quả hoặc dùng cơ chế phân trang/sắp xếp mà phiên bản Spring Data JDBC và query method hỗ trợ.

Ví dụ giới hạn kết quả bằng derived query:

```java
List<Customer> findTop20ByNameStartingWithOrderByNameAsc(String prefix);
```

Method này giới hạn tối đa 20 hàng và sắp xếp theo `name` tăng dần theo quy tắc query derivation. Kiểm tra hỗ trợ keyword giới hạn và cách dialect tạo SQL trong phiên bản ứng dụng đang dùng.

Nếu cần phân trang, sử dụng các abstraction paging/sorting tương ứng được Spring Data JDBC hỗ trợ; `List` tự nó không phải `Page` và không chứa tổng số trang.

## 16. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân thường gặp | Hướng xử lý |
|---|---|---|
| `findByNameLike("Ann")` không tìm `Anna` | `Like` dùng pattern đúng như truyền vào; thiếu `%` | Truyền `Ann%` hoặc dùng `StartingWith` |
| `StartingWith` không tìm theo suffix | Đã chọn sai keyword | Dùng `EndingWith` |
| `Containing` trả nhiều kết quả | `%fragment%` có thể khớp ở mọi vị trí | Giới hạn input/kết quả hoặc dùng prefix nếu phù hợp |
| `%` trong input làm query quá rộng | Wildcard người dùng nhập bị hiểu như ký tự pattern | Escape wildcard hoặc dùng derived keyword có cơ chế sanitization |
| Không phân biệt hoa/thường như mong đợi | Collation/DBMS khác nhau | Kiểm tra collation, `IgnoreCase` hoặc SQL cụ thể |
| Tìm kiếm chậm trên bảng lớn | Pattern có wildcard ở đầu | Xem execution plan, index chuyên dụng hoặc full-text search |
| Chuỗi rỗng trả quá nhiều hàng | Pattern trở thành `%`/`%%` | Xử lý input rỗng ở tầng service |
| Hàng có tên null không xuất hiện | `LIKE` với `NULL` không cho kết quả true | Dùng `IsNull` nếu cần tìm null |
| Query tùy chỉnh không tìm được prefix | Caller chưa thêm wildcard | Chuẩn bị pattern trong Java hoặc dùng `StartingWith` |
| SQL injection khi tạo pattern | Nối input vào chuỗi SQL | Dùng bind parameter; escape wildcard riêng biệt |

## 17. Bài thực hành: quan sát pattern được bind

Với bảng `customers` và repository ở phần 2, thêm một số dữ liệu:

```sql
INSERT INTO customers (name, email) VALUES
    ('Ann', 'ann@example.com'),
    ('Anna Smith', 'anna@example.com'),
    ('Joanne', 'joanne@example.com'),
    ('Anderson', 'anderson@example.com'),
    ('Susan', 'susan@example.com');
```

Gọi các method:

```java
repository.findByNameLike("Ann%");
repository.findByNameStartingWith("Ann");
repository.findByNameEndingWith("son");
repository.findByNameContaining("ann");
```

Sau đó bật log Spring JDBC trong môi trường phát triển:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Quan sát câu SQL `LIKE ?` và giá trị tham số được bind. So sánh `Like("Ann%")` với `StartingWith("Ann")`: chúng có thể tạo pattern cùng ý nghĩa, nhưng API diễn đạt ý định khác nhau. Thử input chứa `%` và `_` để thấy vì sao cần hiểu escaping, rồi kiểm tra kết quả trên DBMS thực tế.

## 18. Nguyên tắc ghi nhớ

- `LIKE` là toán tử SQL; `%` đại diện không hoặc nhiều ký tự, `_` đại diện đúng một ký tự.
- `Like` nhận pattern đầy đủ do caller truyền.
- `StartingWith` tự thêm `%` ở cuối chuỗi đầu vào.
- `EndingWith` tự thêm `%` ở đầu chuỗi đầu vào.
- `Containing` tự thêm `%` ở cả hai đầu.
- Derived query dùng property Java; SQL tùy chỉnh dùng tên bảng/cột vật lý.
- Bind parameter chống SQL injection nhưng không thay thế việc escape wildcard.
- `NULL`, chuỗi rỗng, hoa/thường và dấu tiếng Việt phụ thuộc ngữ nghĩa SQL/collation của database.
- Prefix search thường có cơ hội tận dụng B-tree index tốt hơn suffix/substring; đo execution plan trước khi tối ưu.
- Giới hạn kết quả khi tìm kiếm có thể trả về nhiều hàng.

Trong Spring Data JDBC, chọn `Like` khi caller cần kiểm soát pattern, `StartingWith` cho tìm tiền tố, `EndingWith` cho hậu tố và `Containing` cho chuỗi con. Hiểu cách wildcard được thêm, cách ký tự đặc biệt được escape và đặc tính của database sẽ giúp truy vấn đúng ý nghĩa, an toàn với dữ liệu đầu vào và phù hợp với kích thước dữ liệu thực tế.
