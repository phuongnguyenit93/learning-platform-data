# Khi nào cần converter thay vì đối tượng nhúng?

Trong Spring Data JDBC, một value object có thể được ánh xạ theo hai cách thường gặp: **đối tượng nhúng** bằng §@Embedded§ hoặc **custom converter** bằng Spring §Converter§. Cả hai đều giúp mô hình domain dùng kiểu Java có ý nghĩa, nhưng chúng tạo ra cấu trúc lưu trữ khác nhau.

- Dùng **§@Embedded§** khi các thuộc tính của value object cần trở thành nhiều cột riêng trong cùng bảng với entity cha.
- Dùng **converter** khi toàn bộ một thuộc tính domain cần được chuyển thành một giá trị database duy nhất, rồi khôi phục lại từ giá trị đó.
- Nếu đối tượng có identity, vòng đời hoặc quy tắc nghiệp vụ độc lập, hãy xem xét mô hình entity/aggregate riêng. Converter và embedded không thay thế ranh giới aggregate.

Ví dụ, địa chỉ giao hàng có đường, thành phố và mã bưu chính thường phù hợp với §@Embedded§ vì ứng dụng có thể lọc, sắp xếp và tạo index theo từng phần. Một kiểu §EmailAddress§ có thể phù hợp với converter vì toàn bộ giá trị email được lưu trong một cột §VARCHAR§.

Điểm quyết định không phải class Java có nhiều hay ít thuộc tính, mà là **database cần nhìn thấy value object như nhiều cột hay một giá trị đơn**.

## 1. Hai cách ánh xạ, hai cấu trúc lưu trữ

Giả sử aggregate §Customer§ có hai giá trị:

- §Address§ gồm đường, thành phố và mã bưu chính.
- §EmailAddress§ là một kiểu domain riêng bọc một địa chỉ email.

Một mô hình Java:

§§§java
@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address,

        EmailAddress email
) {
}

public record Address(
        String street,
        String city,
        String postalCode
) {
}

public record EmailAddress(String value) {
}
§§§

Hai thuộc tính §address§ và §email§ đều là value object, nhưng cách lưu phù hợp có thể khác nhau.

§§§text
Customer
  |
  +-- Address
  |     +-- street
  |     +-- city
  |     +-- postalCode
  |          |
  |          +----> nhiều cột trong bảng customers
  |
  +-- EmailAddress
        +-- value
             |
             +----> một cột email trong bảng customers
                       qua custom Converter
§§§

Bảng database có thể là:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,

    address_street VARCHAR(250),
    address_city VARCHAR(100),
    address_postal_code VARCHAR(20),

    email VARCHAR(320) NOT NULL
);
§§§

§Address§ được trải phẳng thành ba cột. §EmailAddress§ được chuyển thành một giá trị chuỗi và lưu trong một cột.

## 2. Đối tượng nhúng bằng @Embedded

§@Embedded§ dùng để ánh xạ các thuộc tính của một object vào **cùng bảng với entity chứa nó**. Object nhúng không cần ID riêng và không có repository riêng chỉ vì nó được khai báo thành một class Java.

Ví dụ:

§§§java
import org.springframework.data.relational.core.mapping.Embedded;

public record Address(
        String street,
        String city,
        String postalCode
) {
}

@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address
) {
}
§§§

Các cột được ánh xạ:

| Thuộc tính Java | Cột database |
| --- | --- |
| §id§ | §id§ |
| §name§ | §name§ |
| §address.street§ | §address_street§ |
| §address.city§ | §address_city§ |
| §address.postalCode§ | §address_postal_code§ |

Prefix giúp tránh trùng tên cột khi aggregate có nhiều value object cùng kiểu.

### 2.1. Khi nào embedded phù hợp?

Dùng embedded khi:

- Các trường của object có ý nghĩa riêng và cần được lưu ở các cột riêng.
- Ứng dụng thường lọc theo một hoặc nhiều thuộc tính bên trong object.
- Cần tạo index, unique constraint, check constraint hoặc sort theo từng thuộc tính.
- Các thuộc tính cần được cập nhật hoặc kiểm tra độc lập ở mức SQL.
- Object không có identity và vòng đời riêng; nó thuộc về entity/aggregate chứa nó.

Ví dụ, địa chỉ giao hàng có thể cần lọc tất cả khách hàng ở một thành phố:

§§§sql
SELECT id, name, address_street, address_city, address_postal_code
FROM customers
WHERE address_city = 'Hà Nội';
§§§

Do §city§ là một cột riêng, database có thể dùng index trên cột đó:

§§§sql
CREATE INDEX idx_customers_address_city
    ON customers(address_city);
§§§

Nếu toàn bộ địa chỉ được serialize thành một chuỗi opaque, việc lọc theo thành phố sẽ khó hơn và có thể cần các hàm xử lý chuỗi/JSON riêng của database.

### 2.2. Dùng nhiều embedded object cùng kiểu

Một entity có thể chứa hai địa chỉ cùng kiểu, chẳng hạn địa chỉ thanh toán và địa chỉ giao hàng:

§§§java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,

        @Embedded(prefix = "shipping_")
        Address shippingAddress,

        @Embedded(prefix = "billing_")
        Address billingAddress
) {
}
§§§

Schema có thể chứa hai nhóm cột:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    shipping_street VARCHAR(250),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20),

    billing_street VARCHAR(250),
    billing_city VARCHAR(100),
    billing_postal_code VARCHAR(20)
);
§§§

Hai object cùng kiểu Java nhưng được ánh xạ vào các cột khác nhau nhờ prefix.

### 2.3. Xử lý embedded object rỗng với onEmpty

§@Embedded§ có thuộc tính §onEmpty§ để quyết định cách khôi phục object khi tất cả cột được ánh xạ từ nó đều là SQL NULL.

Hai lựa chọn chính:

- §USE_NULL§: embedded property trở thành §null§ khi tất cả cột của nó đều null.
- §USE_EMPTY§: framework cố gắng tạo một instance với các thuộc tính null.

Ví dụ:

§§§java
@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL)
Address address
§§§

Hoặc dùng shortcut §@Embedded.Nullable§ tương ứng với hành vi §USE_NULL§; §@Embedded.Empty§ tương ứng với §USE_EMPTY§.

Điều này quan trọng khi domain phân biệt:

- Không có địa chỉ: §address == null§.
- Có object địa chỉ nhưng các trường hiện chưa có giá trị: object khác null, các thuộc tính có thể null.

Nếu embedded object chứa §Collection§ hoặc §Map§, Spring Data Relational luôn xem nó là non-empty vì collection/map ít nhất có thể tồn tại dưới dạng rỗng. Vì vậy, embedded object có collection/map sẽ không trở thành null chỉ vì các cột scalar đều null.

## 3. Custom converter là gì?

Custom converter là một Spring §Converter<S, T>§ dùng để chuyển đổi giữa kiểu domain và kiểu mà tầng JDBC có thể lưu hoặc đọc.

Trong Spring Data Relational, converter được áp dụng ở **cấp property**: một giá trị domain được chuyển thành một giá trị database và ngược lại. Converter không trải một object phức tạp thành nhiều cột.

Ví dụ, domain có kiểu riêng §EmailAddress§:

§§§java
public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(
                    "Email address is required"
            );
        }

        value = value.trim().toLowerCase(Locale.ROOT);
    }
}
§§§

Database chỉ cần một cột §VARCHAR§:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL
);
§§§

Converter ghi chuyển §EmailAddress§ thành §String§:

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public enum EmailAddressWriteConverter
        implements Converter<EmailAddress, String> {

    INSTANCE;

    @Override
    public String convert(EmailAddress source) {
        return source.value();
    }
}
§§§

Converter đọc chuyển §String§ từ database thành §EmailAddress§:

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public enum StringToEmailAddressConverter
        implements Converter<String, EmailAddress> {

    INSTANCE;

    @Override
    public EmailAddress convert(String source) {
        return new EmailAddress(source);
    }
}
§§§

Khi lưu §Customer§, giá trị §EmailAddress§ được ghi thành chuỗi. Khi đọc lại, chuỗi được chuyển thành object §EmailAddress§.

### 3.1. Converter không tạo thêm bảng hoặc nhiều cột

Giả sử:

§§§java
public record Money(
        BigDecimal amount,
        String currency
) {
}
§§§

Một converter có thể serialize toàn bộ object thành một giá trị chuỗi, ví dụ §"USD|125.50"§, rồi đọc lại từ cột §VARCHAR§. Khi đó database chỉ thấy một giá trị.

Converter không tự tạo hai cột §amount§ và §currency§. Nếu cần hai cột có thể lọc và index độc lập, dùng §@Embedded§ sẽ phù hợp hơn.

Một converter có thể chuyển sang kiểu database-specific mà JDBC driver hỗ trợ, hoặc dùng §JdbcValue§ nếu cần chỉ định rõ JDBC type. Dù vậy, kết quả vẫn là một giá trị cho một property, không phải cơ chế ánh xạ object thành nhiều cột.

### 3.2. Vì sao phải có cả converter đọc và ghi?

Để round-trip đầy đủ:

§§§text
Java domain value
      |
      | EmailAddressWriteConverter
      v
Database value (VARCHAR)
      |
      | StringToEmailAddressConverter
      v
Java domain value
§§§

Nếu chỉ đăng ký converter ghi, Spring Data có thể ghi được giá trị nhưng không có converter phù hợp để khôi phục kiểu domain khi đọc. Ngược lại, chỉ có converter đọc thì dữ liệu có thể được đọc nhưng chưa chắc ghi được kiểu domain.

Khi thiết kế custom type hai chiều, hãy cung cấp converter đọc và ghi tương ứng.

## 4. Đăng ký converter trong Spring Data JDBC

Converter không tự động được đăng ký chỉ vì class nằm trong component scan hoặc có annotation Spring. Spring Data yêu cầu đăng ký converter rõ ràng qua custom conversions.

Trong Spring Data Relational 4.1.2, cách cấu hình thông thường với §AbstractJdbcConfiguration§ là override §userConverters()§:

§§§java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class DataJdbcConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
                EmailAddressWriteConverter.INSTANCE,
                StringToEmailAddressConverter.INSTANCE
        );
    }
}
§§§

Framework kết hợp các converter người dùng với converter mặc định và converter theo JDBC dialect.

**Không nên tùy tiện override §jdbcCustomConversions()§ theo ví dụ của các phiên bản cũ.** Trong tài liệu hiện tại, phương thức này tập hợp conversion dùng chung, conversion do dialect đăng ký và conversion của ứng dụng. Nếu tự thay thế toàn bộ bằng một danh sách mới, bạn có thể làm mất converter mặc định hoặc converter riêng của dialect.

Nếu ứng dụng dùng Spring Boot để cấu hình Spring Data JDBC, có thể cung cấp bean §JdbcCustomConversions§ theo hướng dẫn cấu hình Boot. Chọn một cách cấu hình phù hợp với hạ tầng hiện tại và bảo đảm converter được đăng ký vào đúng conversion service mà §JdbcConverter§ đang sử dụng.

### 4.1. Phân biệt hướng đọc và hướng ghi

Hai converter có thể dùng các kiểu nguồn/đích đều là kiểu đơn giản. Ví dụ §String§ và §Long§ đều là kiểu mà JDBC xử lý trực tiếp. Khi đó, framework không thể luôn suy ra converter dùng cho đọc hay ghi.

§@ReadingConverter§ và §@WritingConverter§ giúp chỉ rõ hướng:

| Annotation | Hướng |
| --- | --- |
| §@WritingConverter§ | Từ kiểu domain sang kiểu database khi ghi. |
| §@ReadingConverter§ | Từ kiểu database sang kiểu domain khi đọc. |

Với §EmailAddress§ và §String§, dù một phía là custom type, việc khai báo annotation tường minh giúp code dễ hiểu và tránh đăng ký converter theo hướng không mong muốn.

### 4.2. Converter cần định dạng ổn định

Nếu converter serialize object thành chuỗi hoặc JSON, định dạng đó trở thành hợp đồng giữa ứng dụng và dữ liệu đã lưu.

Cần cân nhắc:

- Cách biểu diễn null.
- Quy tắc chuẩn hóa dữ liệu.
- Dấu phân cách và escaping.
- Locale, timezone và độ chính xác số.
- Khả năng đọc dữ liệu từ các phiên bản ứng dụng cũ.
- Cách xử lý chuỗi sai định dạng hoặc dữ liệu lịch sử không hợp lệ.

Không nên thay đổi định dạng converter một cách tùy tiện khi database đã chứa dữ liệu được ghi theo định dạng cũ. Có thể cần migration hoặc converter đọc tương thích ngược.

## 5. So sánh trực tiếp @Embedded và Converter

| Tiêu chí | §@Embedded§ | Custom converter |
| --- | --- | --- |
| Cấu trúc database | Nhiều cột trong bảng cha | Một giá trị database cho một property |
| Cách ánh xạ | Trải phẳng thuộc tính object | Chuyển object thành scalar/native database value |
| Truy vấn từng trường con | Dễ bằng SQL trên từng cột | Phụ thuộc kiểu lưu; thường khó hơn nếu giá trị opaque |
| Index từng trường | Có thể tạo index riêng | Thường chỉ index giá trị tổng thể hoặc dùng tính năng riêng của DB |
| Ràng buộc từng trường | Có thể dùng NOT NULL, CHECK, UNIQUE trên cột | Khó hơn nếu toàn bộ object nằm trong một cột |
| Mã chuyển đổi | Thường không cần converter | Cần converter đọc/ghi và đăng ký |
| Identity riêng | Không | Không |
| Vòng đời riêng | Không | Không |
| Lưu nhiều thuộc tính thành nhiều cột | Có | Không |
| Serialize vào một cột | Không phải mục tiêu của embedded | Có thể |

Cả hai đều có thể giữ mô hình domain giàu ý nghĩa. Khác biệt nằm ở hình dạng dữ liệu quan hệ mà chúng tạo ra.

## 6. Chọn embedded khi cần truy vấn theo từng thuộc tính

Địa chỉ là ví dụ điển hình:

§§§java
public record Address(
        String street,
        String city,
        String postalCode
) {
}
§§§

Nếu dùng §@Embedded§, có thể viết SQL:

§§§sql
SELECT id, name
FROM customers
WHERE address_city = 'Đà Nẵng'
ORDER BY address_postal_code;
§§§

Database có thể tạo index riêng:

§§§sql
CREATE INDEX idx_customers_city_postal
    ON customers(address_city, address_postal_code);
§§§

Nếu converter biến toàn bộ §Address§ thành một chuỗi như §"street|city|postalCode"§, query theo thành phố phải phân tích chuỗi hoặc dùng hàm database-specific. Điều này làm truy vấn khó đọc, khó tối ưu và dễ phụ thuộc định dạng serialize.

Vì vậy, khi các trường có ý nghĩa trong SQL, **embedded thường là lựa chọn tốt hơn**.

Các trường hợp phù hợp:

- Địa chỉ có street/city/postal code.
- Khoảng thời gian có start/end.
- Tọa độ có latitude/longitude nếu cần lọc theo từng chiều.
- Thông tin người liên hệ có tên/số điện thoại/email.
- Thông tin tiền tệ có amount/currency nếu cần truy vấn hoặc ràng buộc từng phần.

Nếu object có rất nhiều trường hoặc có collection/relationship, cần đánh giá thêm ranh giới aggregate và mapping collection; không phải mọi object lồng nhau đều chỉ nên là embedded.

## 7. Chọn converter khi giá trị cần được lưu như một đơn vị

Converter phù hợp khi domain muốn dùng kiểu riêng nhưng database chỉ cần một giá trị.

Ví dụ:

### 7.1. EmailAddress

Domain muốn kiểm tra và chuẩn hóa email ở constructor:

§§§java
public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Email is required");
        }
        value = value.trim().toLowerCase(Locale.ROOT);
    }
}
§§§

Database chỉ cần §email VARCHAR(320)§. Không có nhu cầu truy vấn riêng domain, username hay host qua các cột tách biệt.

### 7.2. Mã định danh theo domain

Ví dụ §CustomerCode§ có format chuẩn hóa:

§§§java
public record CustomerCode(String value) {

    public CustomerCode {
        if (value == null || !value.matches("[A-Z]{2}-[0-9]{6}")) {
            throw new IllegalArgumentException(
                    "Invalid customer code"
            );
        }
    }
}
§§§

Converter chuyển §CustomerCode§ thành §String§. Database lưu một cột §customer_code§ với unique constraint.

### 7.3. Giá trị đã serialize

Một object cấu hình nhỏ có thể được lưu dưới dạng JSON trong một cột nếu:

- Database và driver hỗ trợ kiểu cột phù hợp.
- Ứng dụng thường đọc/ghi toàn bộ object như một đơn vị.
- Không cần join hoặc ràng buộc quan hệ cho từng thuộc tính.
- Đã xác định chiến lược version hóa JSON và migration dữ liệu.

Converter có thể serialize object thành một giá trị JSON. Tuy nhiên, nếu dùng PostgreSQL §jsonb§ hoặc một kiểu native tương tự, cần kiểm tra cách driver bind kiểu SQL; có thể phải trả §JdbcValue§ với §JDBCType§ phù hợp thay vì chỉ trả một §String§ thông thường.

Không nên mặc định một chuỗi JSON được bind vào cột native JSON/JSONB sẽ luôn được database diễn giải đúng kiểu trên mọi dialect.

## 8. Khi nào không nên chọn converter?

Không dùng converter chỉ để tránh khai báo nhiều cột nếu database vẫn cần thao tác trên các trường riêng.

Hãy tránh converter trong các trường hợp:

- Cần tìm kiếm theo từng thuộc tính bên trong object.
- Cần sort theo một trường con.
- Cần unique constraint hoặc foreign key trên một phần dữ liệu.
- Cần index độc lập trên các thuộc tính.
- Cần cập nhật một trường con mà không ghi lại toàn bộ object.
- Object chứa collection entity hoặc quan hệ với aggregate khác.
- Dữ liệu có identity và vòng đời độc lập.

Ví dụ §OrderAddress§ có thể được lưu bằng converter thành một chuỗi, nhưng nếu báo cáo thường xuyên cần thống kê theo tỉnh/thành, embedded với cột §city§ riêng thường dễ tối ưu hơn.

Nếu object cần một bảng riêng hoặc có nhiều nơi tham chiếu, hãy xem xét entity/aggregate riêng thay vì converter. Converter chỉ giải quyết chuyển đổi kiểu property; nó không tạo quan hệ giữa các aggregate.

## 9. Khi nào không nên chọn @Embedded?

Embedded cũng không phải lựa chọn mặc định cho mọi class value object.

Không nên dùng §@Embedded§ nếu:

- Toàn bộ object cần được lưu như một giá trị opaque trong một cột.
- Định dạng lưu trữ cần được serialize/deserialize theo quy tắc riêng.
- Database driver có kiểu native phù hợp cho giá trị domain và cần mapping custom.
- Các thuộc tính không cần truy vấn riêng và việc trải phẳng chúng thành nhiều cột không mang lợi ích.
- Object thực chất có identity và vòng đời độc lập.

Ví dụ §EmailAddress§ chỉ có một giá trị chuỗi. Có thể dùng trực tiếp §String§, nhưng kiểu domain riêng giúp kiểm tra và chuẩn hóa ở một nơi. Converter là cách giữ kiểu domain đó trong Java trong khi database vẫn dùng một cột chuỗi.

Nếu dùng §@Embedded§ cho một class chỉ chứa §value§, nó sẽ tạo thêm một cột có prefix, nhưng không nhất thiết mang lại lợi ích so với converter. Hãy chọn cách thể hiện phản ánh đúng ý nghĩa lưu trữ.

## 10. Ví dụ hoàn chỉnh: kết hợp embedded và converter trong cùng aggregate

Một aggregate có thể dùng cả hai cách ở các property khác nhau.

### 10.1. Domain model

§§§java
import java.util.Locale;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address,

        EmailAddress email
) {
}

public record Address(
        String street,
        String city,
        String postalCode
) {
}

public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(
                    "Email address is required"
            );
        }

        value = value.trim().toLowerCase(Locale.ROOT);
    }
}

### 10.2. Converter ghi

import org.springframework.core.convert.converter.Converter;

    INSTANCE;

### 10.3. Converter đọc

import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter

        implements Converter<String, EmailAddress> {

    INSTANCE;

### 10.4. Đăng ký converter

## 11. Ảnh hưởng đến truy vấn và cập nhật

Lựa chọn mapping ảnh hưởng đến cách viết SQL và cách cập nhật dữ liệu.

### 11.1. Truy vấn embedded fields

Vì các thuộc tính embedded trở thành cột riêng, có thể lọc:

§§§sql
SELECT id, name
FROM customers
WHERE address_city = 'Hà Nội';
§§§

Có thể tạo index và constraint riêng cho cột địa chỉ.

### 11.2. Truy vấn converted property

Với §EmailAddress§ được chuyển thành §String§, database lưu một giá trị email. Có thể lọc bằng so sánh trên cột email:

§§§sql
SELECT id, name
FROM customers
WHERE email = 'an@example.com';
§§§

Khi dùng Spring Data query method hoặc Criteria với kiểu property đã đăng ký converter, hãy xác nhận conversion được áp dụng cho tham số theo mapping của phiên bản và query path đang sử dụng. Với SQL tùy chỉnh, có thể truyền giá trị đã chuẩn hóa từ §EmailAddress.value()§ hoặc dùng conversion phù hợp của JDBC.

Converter không tự tạo các cột phụ để truy vấn từng thành phần bên trong object.

### 11.3. Cập nhật value object

Với embedded object bất biến, có thể thay thế toàn bộ value object:

§§§java
Address newAddress = new Address(
        "25 Lê Lợi",
        "Đà Nẵng",
        "550000"
);
§§§

Với converter property, thay thế giá trị domain:

§§§java
EmailAddress newEmail =
        new EmailAddress("new@example.com");
§§§

Trong cả hai trường hợp, thay đổi aggregate thông qua domain behavior và lưu aggregate root theo quy tắc persistence của Spring Data JDBC. Converter không phải cơ chế partial update; nó chỉ chuyển đổi giá trị property khi đọc/ghi.

## 12. Converter với kiểu SQL đặc thù và JdbcValue

Thông thường, converter ghi có thể trả về một kiểu mà JDBC driver hỗ trợ, chẳng hạn §String§, §BigDecimal§, §byte[]§ hoặc kiểu native phù hợp.

Trong một số trường hợp, chỉ trả về giá trị Java là chưa đủ để chỉ định SQL type. Ví dụ, ứng dụng muốn bind một giá trị theo một JDBC type cụ thể. Spring Data JDBC cung cấp §JdbcValue§ để mang cả giá trị lẫn §JDBCType§.

Ý tưởng:

§§§java
@WritingConverter
public class DomainValueWriteConverter
        implements Converter<DomainValue, JdbcValue> {

    @Override
    public JdbcValue convert(DomainValue source) {
        return JdbcValue.of(
                source.value(),
                JDBCType.VARCHAR
        );
    }
}
§§§

Ví dụ này minh họa vai trò của §JdbcValue§; kiểu JDBC cụ thể phải khớp với cột và driver đang dùng. Với kiểu native như JSON/JSONB, hãy kiểm tra dialect và cách driver yêu cầu bind tham số. Không nên giả định §VARCHAR§ luôn thay thế được một native database type.

§JdbcValue§ vẫn biểu diễn một giá trị cho một property. Nó không biến converter thành cơ chế mapping object nhiều cột.

## 13. Kiểm thử converter và mapping

Custom converter nên được kiểm tra độc lập và qua integration test với database.

### 13.1. Unit test converter

### 13.3. Kiểm tra dữ liệu ở database

Ngoài kiểm tra object sau khi đọc, hãy xác nhận hình dạng dữ liệu:

§§§sql
SELECT
    id,
    address_street,
    address_city,
    address_postal_code,
    email

§§§

Kết quả mong đợi có các cột địa chỉ riêng và một giá trị email đã chuẩn hóa. Điều này giúp phát hiện trường hợp converter chưa được đăng ký hoặc embedded prefix không khớp schema.

### 13.4. Kiểm tra dữ liệu cũ và lỗi chuyển đổi

Nếu converter được thêm vào một cột đã có dữ liệu, hãy kiểm tra:

- Dữ liệu hiện tại có đúng định dạng mà converter đọc được không?
- Có giá trị null hoặc chuỗi rỗng không?
- Có bản ghi được ghi bởi phiên bản ứng dụng cũ không?
- Có cần migration chuẩn hóa dữ liệu không?
- Converter đọc có xử lý được các định dạng cũ không?

Một converter đọc ném exception khi gặp dữ liệu lịch sử không hợp lệ có thể làm cả thao tác tải aggregate thất bại. Hãy có chiến lược migration hoặc xử lý lỗi phù hợp.

## 14. Những sai lầm thường gặp

**“Converter có thể ánh xạ object thành nhiều cột.”** Không. Custom converter của Spring Data Relational áp dụng ở cấp property và chuyển một giá trị domain thành một giá trị database. Dùng §@Embedded§ khi cần nhiều cột.

**“@Embedded tạo một bảng riêng.”** Không. Các thuộc tính embedded được ánh xạ vào bảng của entity cha.

**“Dùng converter sẽ tự tạo một kiểu database mới.”** Không. Converter chuyển đổi sang kiểu mà JDBC/database có thể xử lý; nếu cần SQL type cụ thể, xem xét §JdbcValue§ và dialect.

**“Chỉ cần converter ghi là đủ.”** Không nếu ứng dụng cần đọc lại custom type. Hãy đăng ký converter đọc tương ứng.

**“Đặt converter thành @Component là Spring Data tự dùng.”** Không nên giả định. Converter cần được đăng ký tường minh qua custom conversions.

**“Không cần @ReadingConverter/@WritingConverter.”** Với các converter có source/target đều là kiểu đơn giản, framework có thể không xác định đúng hướng. Dùng annotation để phân biệt.

**“Có thể override jdbcCustomConversions bằng danh sách converter của riêng mình.”** Không nên theo hướng dẫn hiện tại. Phương thức đó còn tập hợp converter mặc định và converter của dialect; dùng §userConverters()§ trong §AbstractJdbcConfiguration§ theo API hiện tại.

**“Object có nhiều thuộc tính luôn phải dùng @Embedded.”** Không nhất thiết. Nếu toàn bộ object được lưu như một giá trị opaque trong một cột, converter có thể phù hợp. Cần xét cách truy vấn và ràng buộc dữ liệu.

**“Converter phù hợp cho entity có identity.”** Không. Converter không tạo quan hệ, foreign key, repository hoặc vòng đời độc lập.

**“JSON converter luôn dùng được với cột JSONB.”** Không nên mặc định. Cần bind đúng JDBC/database type theo dialect và driver, có thể dùng §JdbcValue§.

**“Embedded và converter có thể áp dụng đồng thời cho cùng một property.”** Không nên thiết kế theo cách đó. Chọn một chiến lược mapping rõ ràng cho property; dùng embedded cho nhóm cột hoặc converter cho một giá trị đơn.

**“Converter thay thế validation domain.”** Không. Converter chịu trách nhiệm chuyển đổi biểu diễn; validation và bất biến vẫn thuộc domain type hoặc service phù hợp.

## 15. Quy trình quyết định

Khi có một value object trong domain, hãy tự trả lời các câu hỏi:

1. **Object có identity riêng không?** Nếu có, hãy xem xét entity/aggregate riêng; converter và embedded không phù hợp để biểu diễn vòng đời độc lập.
2. **Các thuộc tính có cần thành cột riêng không?** Nếu có, chọn §@Embedded§.
3. **Ứng dụng có cần lọc, sort, index hoặc ràng buộc theo từng thuộc tính không?** Nếu có, embedded thường thuận tiện hơn.
4. **Toàn bộ object có thể được biểu diễn thành một database value không?** Nếu có, converter có thể phù hợp.
5. **Database driver có hỗ trợ kiểu đích không?** Nếu cần kiểu SQL cụ thể, kiểm tra dialect và §JdbcValue§.
6. **Có cần đọc và ghi hai chiều không?** Đăng ký converter đọc và ghi tương ứng.
7. **Converter có hướng rõ ràng không?** Dùng §@ReadingConverter§ và §@WritingConverter§ khi cần phân biệt.
8. **Định dạng lưu trữ có ổn định qua phiên bản không?** Xác định quy tắc serialization và migration.
9. **Object có cần truy vấn một phần hoặc cập nhật từng thuộc tính không?** Nếu có, tránh serialize toàn bộ thành một giá trị opaque.
10. **Đã kiểm thử round-trip với database thật chưa?** Xác nhận cả object Java lẫn hình dạng cột lưu trữ.

## 16. Bài tập thực hành

## 17. Ghi nhớ

- §@Embedded§ trải các thuộc tính của value object thành nhiều cột trong cùng bảng với entity cha.
- Custom converter của Spring Data Relational hoạt động ở cấp property: một giá trị domain được chuyển thành một giá trị database và ngược lại.
- Converter không ánh xạ một object phức tạp thành nhiều cột; dùng embedded nếu cần cấu trúc nhiều cột.
- Chọn embedded khi cần truy vấn, sort, index hoặc ràng buộc từng thuộc tính.
- Chọn converter khi toàn bộ object được lưu như một giá trị duy nhất, ví dụ §EmailAddress§ thành §VARCHAR§.
- Converter cần được đăng ký tường minh; cung cấp converter đọc và ghi nếu cần round-trip.
- Dùng §@ReadingConverter§ và §@WritingConverter§ để phân biệt hướng, nhất là khi source và target đều là kiểu đơn giản.
- Với Spring Data Relational 4.1.2, dùng §userConverters()§ trong §AbstractJdbcConfiguration§ theo hướng dẫn hiện tại; tránh override §jdbcCustomConversions()§ theo ví dụ cũ làm mất converter của dialect.
- §JdbcValue§ cho phép chỉ định JDBC type cụ thể khi giá trị ghi cần metadata kiểu SQL.
- Converter và embedded không tạo aggregate root hoặc vòng đời độc lập; nếu object có identity riêng, hãy mô hình hóa thành entity/aggregate.
- Kiểm thử converter riêng, kiểm thử round-trip và xác nhận dữ liệu thực tế trong database.
- Định dạng serialize phải ổn định và có kế hoạch tương thích/migration khi dữ liệu đã được lưu.

**Hãy quyết định theo hình dạng dữ liệu database cần lưu:** nếu cần nhiều cột có thể truy vấn riêng, dùng embedded; nếu cần một giá trị đơn có kiểu domain rõ ràng, dùng converter. Lựa chọn đúng giúp mô hình Java giữ được ý nghĩa nghiệp vụ mà schema vẫn hỗ trợ tốt cách ứng dụng đọc, lọc và cập nhật dữ liệu.
