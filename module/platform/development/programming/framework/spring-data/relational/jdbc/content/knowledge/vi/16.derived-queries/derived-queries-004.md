# So sánh Equals, Not, LessThan, GreaterThan và Between

Spring Data Relational JDBC hỗ trợ **truy vấn suy diễn (derived queries)**: lập trình viên đặt tên phương thức repository theo quy ước, Spring Data phân tích tên đó và tạo truy vấn phù hợp. Các từ khóa `Equals`, `Not`, `LessThan`, `GreaterThan` và `Between` mô tả điều kiện so sánh trên thuộc tính của entity.

Ví dụ, `findByPriceLessThan(...)` diễn đạt yêu cầu tìm sản phẩm có giá nhỏ hơn một giá trị truyền vào. `findByPriceBetween(min, max)` tìm sản phẩm có giá nằm trong khoảng từ min đến max. Hiểu đúng ý nghĩa toán học và SQL của từng từ khóa giúp bạn đặt tên repository dễ đọc, tránh nhầm lẫn ở biên khoảng và xử lý chính xác dữ liệu null.

Bài học dùng bảng sản phẩm làm ví dụ xuyên suốt, giải thích cú pháp method name, so sánh các toán tử, trường hợp biên, cách kết hợp điều kiện và những tình huống nên chọn query tường minh.

## 1. Truy vấn suy diễn là gì?

Trong Spring Data JDBC, repository có thể khai báo phương thức truy vấn mà không cần tự viết SQL cho từng phương thức. Spring Data phân tích tên phương thức, xác định property được truy vấn và toán tử đi kèm, rồi tạo query dựa trên mapping metadata.

~~~java
List<Product> findByPriceLessThan(BigDecimal maxPrice);
~~~

Phương thức trên được phân tích thành:

- `findBy`: phần mở đầu cho truy vấn tìm kiếm.
- `Price`: property `price` của entity `Product`.
- `LessThan`: toán tử so sánh nhỏ hơn.
- `maxPrice`: giá trị được bind vào điều kiện.

Về mặt logic, truy vấn tương đương:

~~~sql
SELECT *
FROM products
WHERE price < ?;
~~~

Dấu `?` chỉ biểu diễn tham số được bind; SQL cụ thể, tên cột, quoting và cách giới hạn kết quả phụ thuộc database dialect và phiên bản framework.

### Vì sao dùng derived query?

Derived query phù hợp khi điều kiện có thể diễn đạt gọn bằng tên phương thức:

- Tìm sản phẩm theo tên chính xác.
- Tìm sản phẩm có giá thấp hơn một ngưỡng.
- Tìm đơn hàng có tổng tiền lớn hơn một giá trị.
- Tìm giao dịch trong một khoảng thời gian.
- Kết hợp vài điều kiện đơn giản bằng `And` hoặc `Or`.

Tên phương thức cũng là tài liệu về ý định truy vấn. Người đọc có thể hiểu điều kiện cơ bản mà không phải mở một chuỗi SQL dài.

Tuy nhiên, derived query không thay thế SQL cho mọi trường hợp. Truy vấn có join phức tạp, phép tính đặc thù, CTE, window function hoặc cấu trúc database-specific có thể phù hợp hơn với query được khai báo tường minh.

## 2. Mô hình ví dụ

Giả sử ứng dụng quản lý sản phẩm với bảng:

~~~sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    category VARCHAR(80) NOT NULL,
    price NUMERIC(19, 4) NOT NULL,
    stock INTEGER NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
~~~

Entity Spring Data JDBC:

~~~java
import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("products")
public class Product {

    @Id
    private Long id;

    private String name;
    private String category;
    private BigDecimal price;
    private Integer stock;

    @Column("created_at")
    private Instant createdAt;

    protected Product() {
    }

    public Product(
            String name,
            String category,
            BigDecimal price,
            Integer stock,
            Instant createdAt) {
        this.name = name;
        this.category = category;
        this.price = price;
        this.stock = stock;
        this.createdAt = createdAt;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public BigDecimal getPrice() { return price; }
}
~~~

Repository:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface ProductRepository
        extends CrudRepository<Product, Long> {
}
~~~

Các ví dụ tiếp theo bổ sung phương thức truy vấn vào `ProductRepository`. Tên property trong method name là tên thuộc tính Java, ví dụ `price`, không phải tên cột SQL nếu hai tên khác nhau. Mapping `@Column("created_at")` nối property `createdAt` với cột vật lý `created_at`.

## 3. Equals: so sánh bằng

`Equals` biểu diễn phép so sánh bằng giữa giá trị của property và tham số truyền vào. Trong derived query, nếu không ghi toán tử sau property thì equality thường là mặc định.

Các cách viết equality quen thuộc:

~~~java
List<Product> findByName(String name);

List<Product> findByNameEquals(String name);

List<Product> findByNameIs(String name);
~~~

SQL khái niệm:

~~~sql
SELECT *
FROM products
WHERE name = ?;
~~~

Khi gọi:

~~~java
List<Product> products =
    repository.findByNameEquals("Mechanical Keyboard");
~~~

Spring Data bind chuỗi `Mechanical Keyboard` vào tham số truy vấn. Giá trị không được nối trực tiếp vào SQL.

### Equals không có nghĩa là tìm chuỗi gần giống

Equality là phép so sánh bằng theo semantics của kiểu dữ liệu và database. Nó không tự thực hiện:

- Tìm chuỗi chứa một từ.
- Bỏ khoảng trắng đầu/cuối.
- Chuẩn hóa chữ hoa/chữ thường.
- Tìm tiền tố hoặc hậu tố.

Ví dụ `findByNameEquals("Keyboard")` khác với tìm tên chứa `Keyboard`. Với truy vấn chuỗi, collation của database có thể ảnh hưởng cách so sánh chữ hoa/chữ thường và dấu. Không nên giả định mọi database xử lý equality giống hệt nhau.

### Khi nào dùng Equals tường minh?

`findByName("...")` ngắn và thường đủ rõ. `findByNameEquals("...")` hữu ích khi repository có nhiều phương thức với toán tử khác nhau trên cùng property hoặc muốn method name thể hiện rõ phép so sánh.

~~~java
List<Product> findByCategoryEquals(String category);

List<Product> findByCategoryNot(String category);
~~~

Hai tên method thể hiện hai điều kiện đối lập rõ ràng.

## 4. Not: khác giá trị được truyền vào

`Not` biểu diễn phép so sánh không bằng. Nó thường tương đương toán tử SQL `<>`:

~~~java
List<Product> findByCategoryNot(String category);
~~~

SQL khái niệm:

~~~sql
SELECT *
FROM products
WHERE category <> ?;
~~~

Nếu tham số là `"BOOKS"`, kết quả gồm các sản phẩm có category khác BOOKS theo quy tắc so sánh của database.

### Not không đồng nghĩa với NotNull

Hai yêu cầu sau khác nhau:

- `findByCategoryNot("BOOKS")`: category khác giá trị BOOKS.
- `findByCategoryIsNotNull()`: category có giá trị, không phải null.

~~~java
List<Product> findByCategoryNot(String category);

List<Product> findByCategoryIsNotNull();
~~~

Trong SQL:

~~~sql
WHERE category <> ?;
~~~

và:

~~~sql
WHERE category IS NOT NULL;
~~~

là hai điều kiện khác nhau.

### Vì sao NULL cần được xử lý riêng?

SQL dùng logic ba giá trị: TRUE, FALSE và UNKNOWN. Phép so sánh thông thường với NULL không cho kết quả TRUE/FALSE như so sánh hai giá trị thông thường.

Ví dụ:

~~~sql
SELECT *
FROM products
WHERE category <> 'BOOKS';
~~~

Hàng có `category IS NULL` không được chọn bởi biểu thức `category <> 'BOOKS'`. Nếu mục tiêu nghiệp vụ là lấy mọi hàng không thuộc BOOKS **bao gồm cả hàng chưa có category**, cần diễn đạt thêm điều kiện null:

~~~sql
WHERE category <> 'BOOKS'
   OR category IS NULL;
~~~

Đối với derived query, hãy dùng `IsNull` hoặc `IsNotNull` khi muốn diễn đạt null rõ ràng. Đừng dùng `Not` như một cách thay thế cho `IsNotNull`. Nếu truyền tham số null vào phương thức Not, hãy xác nhận semantics null của phiên bản Spring Data đang dùng; tên phương thức và mục tiêu nghiệp vụ nên thể hiện rõ ý định thay vì dựa vào một tham số null tình cờ.

### Not và NotIn

`Not` so sánh một property với một giá trị. Nó không phải phủ định của một tập giá trị.

- `findByCategoryNot("BOOKS")`: khác một giá trị.
- `findByCategoryNotIn(categories)`: không thuộc tập giá trị truyền vào.

Nếu cần loại trừ nhiều trạng thái, dùng từ khóa tập hợp phù hợp thay vì lặp nhiều điều kiện Not.

## 5. LessThan: nhỏ hơn nghiêm ngặt

`LessThan` tương đương toán tử SQL `<`. Giá trị tại đúng ngưỡng không được bao gồm.

~~~java
List<Product> findByPriceLessThan(BigDecimal maxPrice);
~~~

SQL khái niệm:

~~~sql
SELECT *
FROM products
WHERE price < ?;
~~~

Ví dụ dữ liệu:

| Sản phẩm | Giá |
| --- | ---: |
| A | 50.00 |
| B | 99.99 |
| C | 100.00 |
| D | 120.00 |

Gọi `findByPriceLessThan(new BigDecimal("100.00"))` trả về A và B. Sản phẩm C có giá đúng 100.00 nên không thỏa điều kiện.

### So sánh với LessThanEqual

`LessThanEqual` tương đương `<=`:

~~~java
List<Product> findByPriceLessThanEqual(BigDecimal maxPrice);
~~~

| Keyword | Toán tử | Giá trị đúng ngưỡng |
| --- | --- | --- |
| `LessThan` | `<` | Không bao gồm |
| `LessThanEqual` | `<=` | Có bao gồm |

Tên method phải phản ánh chính xác quy tắc nghiệp vụ. Nếu yêu cầu là “giá tối đa 100”, thông thường cần `LessThanEqual` vì giá 100 vẫn hợp lệ. Nếu yêu cầu là “nhỏ hơn 100”, dùng `LessThan`.

### Dùng với thời gian

~~~java
List<Product> findByCreatedAtLessThan(Instant cutoff);
~~~

Truy vấn lấy những sản phẩm được tạo trước thời điểm cutoff, không bao gồm đúng thời điểm cutoff. Với thời gian, hãy chú ý kiểu timestamp, múi giờ và độ chính xác mà database hỗ trợ.

## 6. GreaterThan: lớn hơn nghiêm ngặt

`GreaterThan` tương đương toán tử SQL `>`. Giá trị đúng ngưỡng không được bao gồm.

~~~java
List<Product> findByPriceGreaterThan(BigDecimal minPrice);
~~~

SQL khái niệm:

~~~sql
SELECT *
FROM products
WHERE price > ?;
~~~

Với dữ liệu:

| Sản phẩm | Giá |
| --- | ---: |
| A | 50.00 |
| B | 99.99 |
| C | 100.00 |
| D | 120.00 |

Gọi `findByPriceGreaterThan(new BigDecimal("100.00"))` chỉ trả về D. C có giá đúng 100.00 nên không được chọn.

### So sánh với GreaterThanEqual

`GreaterThanEqual` tương đương `>=`:

~~~java
List<Product> findByPriceGreaterThanEqual(BigDecimal minPrice);
~~~

| Keyword | Toán tử | Giá trị đúng ngưỡng |
| --- | --- | --- |
| `GreaterThan` | `>` | Không bao gồm |
| `GreaterThanEqual` | `>=` | Có bao gồm |

Ví dụ, “giá từ 100 trở lên” nên dùng `GreaterThanEqual`. “Giá cao hơn 100” nên dùng `GreaterThan`.

### So sánh với LessThan

Hai toán tử có tính đối xứng:

~~~java
findByPriceLessThan(limit);       // price < limit
findByPriceGreaterThan(limit);    // price > limit
~~~

Chúng không bao gồm giá trị đúng bằng limit. Khi yêu cầu có bao gồm biên, dùng `LessThanEqual` hoặc `GreaterThanEqual`.

## 7. Between: nằm trong một khoảng

`Between` biểu diễn một giá trị nằm trong khoảng giữa hai tham số. Trong SQL, `BETWEEN` bao gồm **cả hai đầu mút**:

~~~java
List<Product> findByPriceBetween(
    BigDecimal minPrice,
    BigDecimal maxPrice
);
~~~

SQL khái niệm:

~~~sql
SELECT *
FROM products
WHERE price BETWEEN ? AND ?;
~~~

Về mặt logic:

~~~sql
price >= minPrice AND price <= maxPrice
~~~

### Ví dụ với giá

~~~java
List<Product> products = repository.findByPriceBetween(
    new BigDecimal("50.00"),
    new BigDecimal("100.00")
);
~~~

| Sản phẩm | Giá | Kết quả |
| --- | ---: | --- |
| A | 49.99 | Không |
| B | 50.00 | Có |
| C | 75.00 | Có |
| D | 100.00 | Có |
| E | 100.01 | Không |

Cả giá thấp nhất và cao nhất đều được bao gồm. Đây là điểm quan trọng nhất khi chọn Between.

### Between không phải khoảng nửa mở

Nếu nghiệp vụ yêu cầu `min <= value < max`, `Between` không diễn đạt đúng vì nó bao gồm cả max.

Có thể dùng hai điều kiện:

~~~java
List<Product> findByPriceGreaterThanEqualAndPriceLessThan(
    BigDecimal minInclusive,
    BigDecimal maxExclusive
);
~~~

SQL khái niệm:

~~~sql
WHERE price >= ?
  AND price < ?;
~~~

Khoảng nửa mở `[min, max)` rất hữu ích khi chia dữ liệu thành các cửa sổ liên tiếp. Ví dụ, phân loại giao dịch theo từng ngày:

- Ngày 1: từ 00:00 ngày 1, bao gồm, đến 00:00 ngày 2, không bao gồm.
- Ngày 2: từ 00:00 ngày 2, bao gồm, đến 00:00 ngày 3, không bao gồm.

Hai khoảng không bị trùng tại thời điểm ranh giới và không cần đoán độ chính xác mili giây/nano giây cuối ngày.

### Thứ tự hai tham số

Tên `Between` không tự sắp xếp hai giá trị. Tham số đầu là cận dưới, tham số sau là cận trên. Nếu truyền min lớn hơn max, điều kiện thường không tìm được hàng nào.

Nên xác thực trước khi gọi repository:

~~~java
if (minPrice.compareTo(maxPrice) > 0) {
    throw new IllegalArgumentException(
        "minPrice must be less than or equal to maxPrice"
    );
}
~~~

Với kiểu `BigDecimal`, dùng `compareTo` để so sánh giá trị số; `equals` còn xét scale, nên `new BigDecimal("10.0").equals(new BigDecimal("10.00"))` là false dù hai giá trị số bằng nhau.

## 8. Bảng so sánh các toán tử

| Keyword | Ý nghĩa | SQL khái niệm | Bao gồm giá trị bằng biên? |
| --- | --- | --- | --- |
| `Equals` | Bằng | `= ?` | Có, nếu bằng chính xác |
| Không ghi hậu tố | Equality mặc định | `= ?` | Có, nếu bằng chính xác |
| `Not` | Khác | `<> ?` | Không |
| `LessThan` | Nhỏ hơn | `< ?` | Không |
| `GreaterThan` | Lớn hơn | `> ?` | Không |
| `LessThanEqual` | Nhỏ hơn hoặc bằng | `<= ?` | Có |
| `GreaterThanEqual` | Lớn hơn hoặc bằng | `>= ?` | Có |
| `Between` | Trong khoảng hai đầu mút | `BETWEEN ? AND ?` | Có cả hai đầu |

Một cách ghi nhớ:

~~~text
Equals           x = a
Not              x <> a
LessThan         x < a
GreaterThan      x > a
LessThanEqual    x <= a
GreaterThanEqual x >= a
Between          min <= x <= max
~~~

Khi viết method name, hãy bắt đầu từ câu mô tả nghiệp vụ, xác định có bao gồm biên hay không, sau đó chọn keyword tương ứng.

## 9. Khai báo các phương thức trong repository

Ví dụ đầy đủ:

~~~java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.springframework.data.repository.CrudRepository;

public interface ProductRepository
        extends CrudRepository<Product, Long> {

    List<Product> findByNameEquals(String name);

    List<Product> findByCategoryNot(String category);

    List<Product> findByPriceLessThan(BigDecimal maxPrice);

    List<Product> findByPriceGreaterThan(BigDecimal minPrice);

    List<Product> findByPriceBetween(
        BigDecimal minPrice,
        BigDecimal maxPrice
    );

    List<Product> findByCreatedAtLessThan(Instant cutoff);

    List<Product> findByCreatedAtGreaterThanEqual(Instant start);
}
~~~

Các phương thức này không cần tự viết SQL. Spring Data phân tích tên method khi tạo repository query.

### Chọn kiểu trả về

Kiểu trả về phụ thuộc số kết quả và nhu cầu của ứng dụng:

| Kiểu trả về | Ý nghĩa |
| --- | --- |
| `List<Product>` | Danh sách kết quả, có thể rỗng |
| `Optional<Product>` | Một kết quả hoặc không có; phù hợp khi điều kiện được bảo đảm duy nhất |
| `Product` | Một kết quả; cần cân nhắc trường hợp không có hoặc nhiều kết quả theo semantics framework |
| `long` | Thường dùng với phương thức đếm như `countBy...` |
| `boolean` | Thường dùng với phương thức tồn tại như `existsBy...` |

Nếu tìm theo giá trị không duy nhất như category, nên dùng danh sách. Không khai báo `Optional<Product>` chỉ vì mong muốn kết quả là một object nếu database có thể trả nhiều hàng.

~~~java
long countByPriceGreaterThan(BigDecimal threshold);

boolean existsByPriceBetween(
    BigDecimal minPrice,
    BigDecimal maxPrice
);
~~~

Các tiền tố `countBy` và `existsBy` thay đổi kiểu kết quả/ý nghĩa truy vấn, còn phần điều kiện vẫn dùng các keyword so sánh.

## 10. Kết hợp điều kiện bằng And và Or

Có thể kết hợp nhiều điều kiện trong một derived query:

~~~java
List<Product> findByCategoryEqualsAndPriceLessThan(
    String category,
    BigDecimal maxPrice
);
~~~

Ý nghĩa:

~~~sql
WHERE category = ?
  AND price < ?;
~~~

Ví dụ lấy sản phẩm thuộc BOOKS và có giá nhỏ hơn 100:

~~~java
List<Product> booksUnder100 =
    repository.findByCategoryEqualsAndPriceLessThan(
        "BOOKS",
        new BigDecimal("100.00")
    );
~~~

Có thể kết hợp hai điều kiện range:

~~~java
List<Product> findByPriceGreaterThanEqualAndPriceLessThan(
    BigDecimal minInclusive,
    BigDecimal maxExclusive
);
~~~

Đây là cách biểu đạt khoảng nửa mở `[min, max)` mà không cần query viết tay.

### Dùng Or cẩn thận

~~~java
List<Product> findByPriceLessThanOrPriceGreaterThan(
    BigDecimal lower,
    BigDecimal upper
);
~~~

SQL khái niệm:

~~~sql
WHERE price < ?
   OR price > ?;
~~~

Điều kiện này lấy sản phẩm nằm ngoài khoảng, không phải nằm trong khoảng. Với method name dài có nhiều `And` và `Or`, hãy kiểm tra cách parser nhóm điều kiện; ưu tiên phương thức ngắn hoặc `@Query` khi biểu thức trở nên khó đọc.

## 11. So sánh trên các kiểu dữ liệu khác nhau

Các toán tử không chỉ dùng cho `BigDecimal`. Chúng áp dụng với property có kiểu phù hợp và được mapping sang kiểu SQL có thể so sánh.

### 11.1. Số nguyên và số thập phân

~~~java
List<Product> findByStockLessThan(Integer quantity);

List<Product> findByPriceGreaterThan(BigDecimal price);
~~~

Số lượng thường là số nguyên; giá tiền nên dùng `BigDecimal` để tránh sai số dấu phẩy động. Kiểu tham số nên tương thích với kiểu property.

### 11.2. Ngày và thời gian

~~~java
List<Product> findByCreatedAtBetween(
    Instant startInclusive,
    Instant endInclusive
);
~~~

Với `Between`, hai thời điểm đều được bao gồm theo semantics SQL. Nếu truy vấn một ngày cụ thể, khoảng nửa mở thường rõ ràng hơn:

~~~java
List<Product> findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(
    Instant startInclusive,
    Instant nextDayStartExclusive
);
~~~

Đừng giả định “cuối ngày” luôn là 23:59:59.999. Độ chính xác timestamp có thể khác nhau giữa database và driver; dùng cận trên độc quyền ở đầu ngày tiếp theo thường tránh lỗi bỏ sót dữ liệu.

Với dữ liệu thời gian theo múi giờ, cần thống nhất quy ước lưu trữ (ví dụ Instant/UTC) và cách tạo start/end theo múi giờ nghiệp vụ. Ngày bắt đầu của một ngày địa phương không phải lúc nào cũng cách ngày bắt đầu tiếp theo đúng 24 giờ do quy tắc múi giờ.

### 11.3. Chuỗi

`Equals` và `Not` có thể dùng với chuỗi. `LessThan`, `GreaterThan` hoặc `Between` trên chuỗi phụ thuộc thứ tự so sánh/collation của database, thường là thứ tự từ điển chứ không phải thứ tự nghiệp vụ mà người dùng luôn mong đợi.

Nếu cần sắp xếp mã theo cấu trúc riêng, hãy chuẩn hóa hoặc lưu một giá trị có thứ tự rõ ràng thay vì dựa vào so sánh chuỗi mặc định.

### 11.4. Enum

Enum có thể được so sánh equality hoặc inequality nếu được mapping nhất quán. So sánh thứ tự enum bằng GreaterThan/LessThan thường không phải ý nghĩa nghiệp vụ tốt: thứ tự khai báo enum trong Java không nên trở thành thứ tự nghiệp vụ trong database.

Nếu trạng thái có thứ tự, nên lưu một rank hoặc trường thứ tự riêng và xác định mapping rõ ràng.

## 12. NULL và các trường hợp biên

Null là chủ đề quan trọng khi dùng các toán tử so sánh.

### 12.1. Equality với null

Trong SQL, để tìm giá trị null, dùng `IS NULL` chứ không phải `= NULL`:

~~~sql
WHERE category IS NULL;
~~~

Với derived query, biểu đạt ý định rõ ràng:

~~~java
List<Product> findByCategoryIsNull();

List<Product> findByCategoryIsNotNull();
~~~

Các keyword `IsNull` và `IsNotNull` phù hợp hơn việc dùng một tham số null để diễn đạt yêu cầu.

### 12.2. Not và null

SQL `category <> 'BOOKS'` không bao gồm các hàng có category null. Nếu muốn lấy cả null, cần kết hợp điều kiện null hoặc viết query diễn đạt đúng logic.

Đừng hiểu `Not` là “mọi giá trị không bằng, kể cả chưa có giá trị”. Null biểu diễn không biết/không có giá trị, nên không thể mặc nhiên coi là một giá trị khác.

### 12.3. LessThan/GreaterThan với null

Các phép so sánh thứ tự với null cũng không trả về TRUE trong SQL. Nếu property nullable, các hàng null thường không thỏa điều kiện so sánh. Nếu muốn bao gồm chúng, cần thêm điều kiện `IsNull` bằng cách kết hợp phù hợp hoặc viết query tường minh.

### 12.4. Between với null

Nếu một trong hai cận là null, phép so sánh khoảng không còn diễn đạt được miền giá trị mong muốn. Hãy xác thực hai cận trước khi gọi repository. Nếu một đầu khoảng có thể bỏ trống, dùng hai phương thức khác nhau hoặc tạo query động theo điều kiện thực tế.

## 13. Các lỗi thiết kế thường gặp

| Sai sót | Vì sao sai | Cách sửa |
| --- | --- | --- |
| Dùng `LessThan` cho yêu cầu “tối đa” | Giá trị bằng ngưỡng bị loại | Dùng `LessThanEqual` |
| Dùng `GreaterThan` cho “từ X trở lên” | Giá trị bằng X bị loại | Dùng `GreaterThanEqual` |
| Dùng `Between` nhưng mong cận trên không bao gồm | SQL BETWEEN bao gồm cả hai đầu | Kết hợp `GreaterThanEqual` và `LessThan` |
| Dùng `Not` thay cho `IsNotNull` | Hai điều kiện khác nhau | Dùng `IsNotNull` |
| Nghĩ `Not` bao gồm giá trị null | SQL có logic ba giá trị | Thêm điều kiện null nếu nghiệp vụ yêu cầu |
| Truyền min lớn hơn max | Khoảng không có ý nghĩa như mong muốn | Xác thực thứ tự cận |
| Dùng double cho giá tiền | Có thể có sai số nhị phân | Dùng `BigDecimal` |
| Dùng Between cho cửa sổ thời gian liên tiếp | Hai cửa sổ có thể cùng bao gồm điểm biên | Dùng khoảng nửa mở |
| Dùng chuỗi để so sánh thứ tự nghiệp vụ | Collation có thể không khớp ý nghĩa | Chuẩn hóa hoặc lưu trường thứ tự |
| Method name quá dài | Khó hiểu và khó bảo trì | Chia phương thức hoặc dùng query tường minh |

## 14. Khi nào nên dùng @Query thay vì derived query?

Derived query hữu ích cho điều kiện đơn giản. Khi tên phương thức trở nên dài hoặc logic SQL cần thể hiện rõ, có thể dùng `@Query`.

~~~java
import org.springframework.data.jdbc.repository.query.Query;

@Query("""
    SELECT id, name, category, price, stock, created_at
    FROM products
    WHERE price >= :minPrice
      AND price < :maxPrice
      AND (category = :category OR category IS NULL)
    """)
List<Product> findInPriceWindowIncludingUncategorized(
    BigDecimal minPrice,
    BigDecimal maxPrice,
    String category
);
~~~

Đây là SQL do lập trình viên viết. Tên bảng/cột phải khớp schema vật lý; Spring Data JDBC không tự đổi tên SQL trong chuỗi query dựa trên property mapping. Tham số vẫn được bind, tránh nối giá trị người dùng vào SQL.

Nên cân nhắc `@Query` khi:

- Cần điều kiện null kết hợp phức tạp.
- Cần biểu thức database-specific.
- Tên method dài tới mức khó đọc.
- Cần projection hoặc chọn cột cụ thể.
- Cần kiểm soát câu SQL để tối ưu theo truy vấn thực tế.

Không cần dùng `@Query` cho mọi điều kiện. Nếu `findByPriceBetween` đã diễn đạt đúng nghiệp vụ, derived query thường ngắn gọn hơn.

## 15. Kiểm thử các toán tử so sánh

Kiểm thử nên xác nhận cả trường hợp bên trong và đúng tại biên. Ví dụ:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;

@DataJdbcTest
class ProductRepositoryTest {

    @Autowired
    ProductRepository repository;

    @Test
    void betweenIncludesBothEndpoints() {
        repository.save(product("A", "50.00"));
        repository.save(product("B", "75.00"));
        repository.save(product("C", "100.00"));
        repository.save(product("D", "100.01"));

        List<Product> result = repository.findByPriceBetween(
            new BigDecimal("50.00"),
            new BigDecimal("100.00")
        );

        assertThat(result)
            .extracting(Product::getName)
            .containsExactlyInAnyOrder("A", "B", "C");
    }

    private Product product(String name, String price) {
        return new Product(
            name,
            "TEST",
            new BigDecimal(price),
            10,
            Instant.parse("2025-01-01T00:00:00Z")
        );
    }
}
~~~

Đây là ví dụ khung; cần có migration/schema test và repository tương ứng. Tên phương thức, constructor và các trường phải khớp entity trong dự án.

### Bộ dữ liệu kiểm thử biên

Với ngưỡng 100:

| Giá | LessThan 100 | LessThanEqual 100 | GreaterThan 100 | GreaterThanEqual 100 |
| ---: | --- | --- | --- | --- |
| 99.99 | Có | Có | Không | Không |
| 100.00 | Không | Có | Không | Có |
| 100.01 | Không | Không | Có | Có |

Với Between 50 và 100:

| Giá | Kết quả |
| ---: | --- |
| 49.99 | Không |
| 50.00 | Có |
| 75.00 | Có |
| 100.00 | Có |
| 100.01 | Không |

Các test biên giúp phát hiện nhầm lẫn giữa `<` và `<=`, `>` và `>=`, cũng như giả định sai về Between.

### Kiểm thử NULL

Nếu property nullable, thêm hàng có giá trị null và xác nhận:

- `IsNull` trả về hàng null.
- `IsNotNull` loại hàng null.
- So sánh equality/inequality và range có semantics phù hợp.
- Logic kết hợp null có đúng với yêu cầu nghiệp vụ hay không.

Nếu test dùng H2 nhưng production dùng PostgreSQL/MySQL, nên có integration test với database tương thích production cho những truy vấn phụ thuộc collation, kiểu dữ liệu, timezone hoặc SQL dialect.

## 16. Quy trình chọn keyword từ yêu cầu nghiệp vụ

Khi nhận một yêu cầu, hãy diễn đạt nó thành toán tử trước khi viết method name:

| Câu nghiệp vụ | Điều kiện | Method name gợi ý |
| --- | --- | --- |
| Tên bằng chính xác X | `name = X` | `findByNameEquals(X)` |
| Category khác X | `category <> X` | `findByCategoryNot(X)` |
| Giá thấp hơn X | `price < X` | `findByPriceLessThan(X)` |
| Giá tối đa X, bao gồm X | `price <= X` | `findByPriceLessThanEqual(X)` |
| Giá cao hơn X | `price > X` | `findByPriceGreaterThan(X)` |
| Giá từ X trở lên | `price >= X` | `findByPriceGreaterThanEqual(X)` |
| Giá từ X đến Y, gồm cả hai đầu | `X <= price <= Y` | `findByPriceBetween(X, Y)` |
| Giá từ X, chưa tới Y | `X <= price < Y` | `findByPriceGreaterThanEqualAndPriceLessThan(X, Y)` |
| Category chưa được gán | `category IS NULL` | `findByCategoryIsNull()` |
| Category đã được gán | `category IS NOT NULL` | `findByCategoryIsNotNull()` |

Cách làm này giảm lỗi ngữ nghĩa: xác định cận có bao gồm hay không, rồi mới chọn keyword.

## 17. Bài tập tự thực hành

### Bài 1 — Equals và Not

Tạo repository có hai phương thức `findByCategoryEquals` và `findByCategoryNot`. Chuẩn bị sản phẩm thuộc BOOKS, ELECTRONICS và một hàng category null. Ghi lại kết quả từng truy vấn và giải thích vì sao hàng null không phải một category khác theo logic SQL.

### Bài 2 — LessThan và LessThanEqual

Tạo các sản phẩm có giá 99.99, 100.00 và 100.01. Gọi hai phương thức với ngưỡng 100.00. Giải thích tại sao sản phẩm có giá đúng 100.00 chỉ xuất hiện trong kết quả LessThanEqual.

### Bài 3 — GreaterThan và GreaterThanEqual

Lặp lại bộ dữ liệu trên với hai toán tử lớn hơn. Xác nhận giá đúng ngưỡng được lấy bởi GreaterThanEqual nhưng không được lấy bởi GreaterThan.

### Bài 4 — Between

Tạo sản phẩm tại hai cận 50 và 100 cùng một sản phẩm ở giữa. Dùng `findByPriceBetween`. Xác nhận hai cận được bao gồm. Sau đó thử truyền cận dưới lớn hơn cận trên và quan sát kết quả.

### Bài 5 — Khoảng nửa mở

Viết method `findByCreatedAtGreaterThanEqualAndCreatedAtLessThan`. Tạo hai cửa sổ thời gian liền nhau. Đặt một hàng đúng tại ranh giới giữa hai cửa sổ và xác nhận hàng đó chỉ thuộc cửa sổ thứ hai.

### Bài 6 — Kết hợp And/Or

Viết truy vấn lấy sản phẩm thuộc category BOOKS và giá nhỏ hơn 100, hoặc sản phẩm thuộc category CLEARANCE. Viết lại bằng `@Query` nếu method name trở nên khó đọc. So sánh tính dễ hiểu và khả năng kiểm soát SQL.

### Bài 7 — Kiểm thử trên database production-like

Chạy các test so sánh chuỗi, BigDecimal và timestamp trên cùng loại database với môi trường production. Quan sát khác biệt về collation, precision và timezone nếu có.
