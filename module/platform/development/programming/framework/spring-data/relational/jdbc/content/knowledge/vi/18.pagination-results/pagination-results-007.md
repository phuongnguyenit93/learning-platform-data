# Keyset pagination bằng truy vấn tùy chỉnh cho dữ liệu lớn trong Spring Data JDBC

## 1. Vì sao dữ liệu lớn cần keyset pagination?

Khi một bảng có hàng triệu hoặc hàng chục triệu bản ghi, API thường không thể tải tất cả dữ liệu trong một lần. Ứng dụng cần chia kết quả thành từng phần để giới hạn bộ nhớ, thời gian phản hồi và lượng dữ liệu truyền qua mạng.

Cách quen thuộc là **offset pagination**: yêu cầu trang số 1, trang số 2, rồi trang số 3. SQL thường có dạng:

~~~sql
SELECT id, occurred_at, event_type
FROM audit_events
ORDER BY occurred_at DESC, id DESC
LIMIT 50 OFFSET 500000;
~~~

Vấn đề là database vẫn có thể phải tìm và bỏ qua một số lượng lớn hàng trước khi trả về 50 hàng tiếp theo. Khi offset càng lớn, chi phí có thể tăng đáng kể. Ngoài ra, nếu dữ liệu thay đổi giữa hai request, vị trí hàng có thể dịch chuyển, dẫn đến kết quả bị lặp hoặc bị bỏ sót.

**Keyset pagination** (còn gọi là seek pagination) dùng giá trị của hàng cuối cùng ở trang hiện tại làm mốc để tìm trang tiếp theo. Thay vì nói “bỏ qua 500.000 hàng”, ứng dụng nói “lấy các hàng đứng sau khóa sắp xếp này”.

Với thứ tự giảm dần theo thời điểm và ID:

~~~sql
SELECT id, occurred_at, event_type
FROM audit_events
WHERE occurred_at < :lastOccurredAt
   OR (
       occurred_at = :lastOccurredAt
       AND id < :lastId
   )
ORDER BY occurred_at DESC, id DESC
LIMIT :limit;
~~~

Điều kiện này cho database một điểm bắt đầu rõ ràng trong thứ tự dữ liệu. Khi có index phù hợp, database có thể tìm từ cursor và đọc tiếp các hàng kế tiếp, thay vì bỏ qua một offset lớn.

Keyset pagination đặc biệt hữu ích với bảng event, audit log, lịch sử giao dịch, danh sách sản phẩm lớn, API cuộn vô hạn và job xử lý dữ liệu tuần tự.

## 2. Offset pagination và keyset pagination

| Tiêu chí | Offset pagination | Keyset pagination |
|---|---|---|
| Cách xác định trang | Số hàng cần bỏ qua | Giá trị khóa sắp xếp cuối trang trước |
| Truy vấn | LIMIT/OFFSET | Predicate theo cursor và LIMIT |
| Trang đầu | Đơn giản | Không cần cursor |
| Trang rất sâu | Có thể tốn kém vì phải bỏ qua nhiều hàng | Thường ổn định hơn nếu có index phù hợp |
| Nhảy trực tiếp đến trang số N | Thuận tiện hơn | Không tự nhiên; cần cursor đã biết hoặc đi tuần tự |
| Dữ liệu thêm/xóa giữa các request | Offset có thể dịch chuyển gây lặp/bỏ sót | Ít bị ảnh hưởng bởi thay đổi ở phía trước cursor |
| Sắp xếp | Có thể dùng nhiều kiểu sort | Cần thứ tự xác định và cursor chứa đủ khóa sort |
| Phù hợp | Bảng nhỏ, giao diện cần số trang | Dữ liệu lớn, duyệt tuần tự |

Keyset pagination không phải lúc nào cũng thay thế offset. Nếu giao diện cần “đến trang 37” hoặc tổng số trang, offset/Page thường tiện lợi. Nếu người dùng chỉ cần “xem tiếp” hoặc job cần đọc tuần tự, cursor thường phù hợp hơn.

Một yêu cầu quan trọng của cả hai cách là **thứ tự kết quả phải xác định**. SQL không đảm bảo thứ tự hàng nếu thiếu ORDER BY.

## 3. Thiết kế cursor: khóa sắp xếp phải tạo thứ tự toàn phần

Giả sử bảng audit có các cột:

~~~sql
CREATE TABLE audit_events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id UUID NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    event_type VARCHAR(80) NOT NULL,
    payload TEXT
);
~~~

Ứng dụng muốn hiển thị event mới nhất trước:

~~~sql
ORDER BY occurred_at DESC
~~~

Nếu nhiều event có cùng occurred_at, thứ tự giữa chúng không được xác định. Một event có thể đổi vị trí tương đối giữa các lần truy vấn. Vì vậy cần thêm một khóa phân biệt duy nhất, thường là primary key:

~~~sql
ORDER BY occurred_at DESC, id DESC
~~~

Cursor phải chứa **tất cả giá trị cần để xác định vị trí trong thứ tự đó**:

~~~java
public record EventCursor(
        Instant occurredAt,
        Long id
) {}
~~~

Ở đây cursor là cặp (occurredAt, id). Hai event có cùng timestamp vẫn được phân biệt bằng ID.

### 3.1. Quy tắc quan trọng

- Thứ tự phải xác định duy nhất một vị trí; thường thêm primary key làm tie-breaker.
- Cursor phải chứa mọi cột tham gia thứ tự.
- Predicate trang tiếp theo phải dùng đúng thứ tự và chiều sort của ORDER BY.
- Các cột sort nên có giá trị ổn định trong quá trình duyệt.
- Tốt nhất các cột sort là NOT NULL; nếu cho phép null, phải xác định rõ thứ tự null và đưa quy tắc đó vào predicate.
- Mọi trang phải sử dụng cùng bộ lọc và cùng tenant/security scope.

Nếu chỉ dùng occurred_at mà không thêm id, những hàng có cùng timestamp có thể bị lặp hoặc bỏ sót ở ranh giới trang.

### 3.2. Vì sao dùng khóa ghép?

Một khóa sắp xếp không nhất thiết là primary key. Ví dụ:

~~~sql
ORDER BY priority DESC, created_at ASC, id ASC
~~~

Khi đó cursor cần chứa cả priority, created_at và id, và điều kiện tiếp theo phải phản ánh chính xác ba chiều sort. Càng nhiều cột sort, predicate càng phức tạp.

Với ví dụ bài học, dùng hai cột (occurred_at DESC, id DESC) để minh họa một trường hợp phổ biến và dễ kiểm soát.

## 4. Viết truy vấn keyset tùy chỉnh với @Query

Spring Data JDBC cho phép khai báo SQL tùy chỉnh bằng annotation @Query. Ta có thể tách truy vấn trang đầu và trang tiếp theo.

### 4.1. Entity

~~~java
import java.time.Instant;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("audit_events")
public record AuditEvent(
        @Id Long id,

        @Column("tenant_id")
        UUID tenantId,

        @Column("occurred_at")
        Instant occurredAt,

        @Column("event_type")
        String eventType,

        String payload
) {}
~~~

Entity ánh xạ các cột bằng @Column khi tên property Java khác tên vật lý trong database. Trong query tùy chỉnh, SELECT cần trả về các cột mà entity cần để được ánh xạ đầy đủ.

### 4.2. Repository với trang đầu

~~~java
import java.util.List;
import java.util.UUID;

import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface AuditEventRepository
        extends CrudRepository<AuditEvent, Long> {

    @Query("""
        SELECT id, tenant_id, occurred_at, event_type, payload
        FROM audit_events
        WHERE tenant_id = :tenantId
        ORDER BY occurred_at DESC, id DESC
        LIMIT :limit
        """)
    List<AuditEvent> findFirstPage(
            @Param("tenantId") UUID tenantId,
            @Param("limit") int limit
    );
}
~~~

Trang đầu không có cursor. Query chỉ áp dụng bộ lọc tenant, sắp xếp theo hai cột và lấy tối đa limit hàng.

### 4.3. Repository với trang tiếp theo

Thêm method:

~~~java
@Query("""
    SELECT id, tenant_id, occurred_at, event_type, payload
    FROM audit_events
    WHERE tenant_id = :tenantId
      AND (
          occurred_at < :lastOccurredAt
          OR (
              occurred_at = :lastOccurredAt
              AND id < :lastId
          )
      )
    ORDER BY occurred_at DESC, id DESC
    LIMIT :limit
    """)
List<AuditEvent> findNextPage(
        @Param("tenantId") UUID tenantId,
        @Param("lastOccurredAt") Instant lastOccurredAt,
        @Param("lastId") Long lastId,
        @Param("limit") int limit
);
~~~

Đây là dạng SQL PostgreSQL. Các database khác có thể dùng cú pháp giới hạn kết quả khác, chẳng hạn FETCH FIRST, FETCH NEXT hoặc TOP. Hãy điều chỉnh SQL theo dialect thực tế của ứng dụng.

Điều kiện có hai nhánh:

1. occurred_at nhỏ hơn lastOccurredAt: lấy các event có timestamp cũ hơn.
2. occurred_at bằng lastOccurredAt và id nhỏ hơn lastId: nếu timestamp bằng nhau, lấy ID nhỏ hơn.

Vì thứ tự là giảm dần trên cả hai cột, các hàng tiếp theo phải có khóa nhỏ hơn cursor theo thứ tự từ điển.

### 4.4. Vì sao không dùng một điều kiện đơn giản id < lastId?

Nếu thứ tự là occurred_at DESC, id DESC, ID không nhất thiết tăng cùng timestamp theo đúng thứ tự toàn cục mà query đang yêu cầu. Dùng riêng id < lastId có thể bỏ sót hoặc lấy sai hàng khi timestamp không tương quan với ID.

Predicate phải phản ánh **toàn bộ ORDER BY**. Đây là nguyên tắc quan trọng nhất của keyset pagination.

## 5. Một biến thể dùng row-value comparison

Một số database hỗ trợ so sánh tuple/row value. Với PostgreSQL, có thể viết:

~~~sql
SELECT id, tenant_id, occurred_at, event_type, payload
FROM audit_events
WHERE tenant_id = :tenantId
  AND (occurred_at, id) < (:lastOccurredAt, :lastId)
ORDER BY occurred_at DESC, id DESC
LIMIT :limit;
~~~

Biểu thức tuple ngắn hơn và thể hiện trực tiếp thứ tự từ điển. Tuy nhiên, khả năng hỗ trợ và cách tối ưu phụ thuộc database. Dạng OR tường minh ở phần trước dễ đọc và thường dễ chuyển đổi hơn giữa các hệ quản trị, dù query plan vẫn cần được kiểm tra.

Không nên thay đổi cú pháp chỉ vì ngắn hơn nếu database mục tiêu không hỗ trợ hoặc planner xử lý kém hơn.

## 6. Xây dựng cursor page với limit + 1

Repository trả về List<AuditEvent>. Service cần quyết định có trang tiếp theo hay không, những hàng nào được trả cho client và cursor tiếp theo được lấy từ hàng nào.

Một kỹ thuật phổ biến là **lấy dư một hàng**. Nếu client yêu cầu 50 hàng, query lấy 51 hàng:

- Nếu nhận tối đa 50 hàng: không có trang tiếp theo.
- Nếu nhận 51 hàng: có trang tiếp theo; bỏ hàng thứ 51 khỏi response hiện tại.

Cursor mới phải lấy từ **hàng cuối cùng được trả cho client**, không phải hàng dư.

### 6.1. DTO cho response

~~~java
import java.util.List;

public record CursorPage<T>(
        List<T> items,
        EventCursor nextCursor,
        boolean hasNext
) {}
~~~

### 6.2. Service

~~~java
import java.util.List;
import java.util.UUID;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AuditEventQueryService {

    private static final int MAX_PAGE_SIZE = 500;

    private final AuditEventRepository events;

    public AuditEventQueryService(AuditEventRepository events) {
        this.events = events;
    }

    @Transactional(readOnly = true)
    public CursorPage<AuditEvent> readNext(
            UUID tenantId,
            EventCursor cursor,
            int requestedSize
    ) {
        int pageSize = Math.max(1,
                Math.min(requestedSize, MAX_PAGE_SIZE));

        List<AuditEvent> fetched;

        if (cursor == null) {
            fetched = events.findFirstPage(tenantId, pageSize + 1);
        } else {
            fetched = events.findNextPage(
                    tenantId,
                    cursor.occurredAt(),
                    cursor.id(),
                    pageSize + 1
            );
        }

        boolean hasNext = fetched.size() > pageSize;

        List<AuditEvent> items = hasNext
                ? List.copyOf(fetched.subList(0, pageSize))
                : List.copyOf(fetched);

        EventCursor nextCursor = null;

        if (hasNext && !items.isEmpty()) {
            AuditEvent last = items.get(items.size() - 1);
            nextCursor = new EventCursor(last.occurredAt(), last.id());
        }

        return new CursorPage<>(items, nextCursor, hasNext);
    }
}
~~~

Trong ví dụ, service giới hạn page size tối đa 500 để tránh client yêu cầu một trang quá lớn. Giá trị này chỉ là lựa chọn minh họa; hệ thống cần điều chỉnh theo kích thước hàng, latency và năng lực database.

@Transactional(readOnly = true) tạo transaction chỉ đọc cho lần lấy trang. Không nên giữ một transaction dài xuyên suốt toàn bộ hành trình người dùng bấm “xem tiếp” nhiều lần. Mỗi request thường là một lần đọc độc lập.

### 6.3. Vì sao cursor lấy từ hàng cuối cùng được trả?

Giả sử page size là 3, query lấy 4 hàng:

~~~text
Fetched: [A, B, C, D]
Response: [A, B, C]
Next cursor: key của C
~~~

Trang sau phải bắt đầu sau C. Nếu lấy cursor của D, hàng D sẽ bị bỏ qua vì điều kiện query kế tiếp chỉ lấy các hàng đứng sau D.

## 7. Tạo index phù hợp cho keyset query

Keyset pagination chỉ phát huy hiệu quả khi database có thể tìm và duyệt theo các cột filter/order. Với query ở trên, một index phù hợp trên PostgreSQL có thể là:

~~~sql
CREATE INDEX idx_audit_events_tenant_time_id
ON audit_events (tenant_id, occurred_at DESC, id DESC);
~~~

Lý do:

- tenant_id đứng đầu vì query luôn lọc theo tenant.
- occurred_at và id tiếp theo theo đúng thứ tự duyệt.
- Database có thể dùng index để tìm vùng dữ liệu phù hợp và đọc tiếp các hàng theo thứ tự.

Nếu query có thêm filter cố định khác, thứ tự cột index cần được đánh giá lại theo selectivity và workload. Không có quy tắc “đưa mọi cột WHERE vào index” một cách máy móc.

### 7.1. Kiểm tra query plan

Với PostgreSQL, có thể dùng:

~~~sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, tenant_id, occurred_at, event_type, payload
FROM audit_events
WHERE tenant_id = '00000000-0000-0000-0000-000000000001'
  AND (
      occurred_at < TIMESTAMPTZ '2026-01-01 10:00:00+00'
      OR (
          occurred_at = TIMESTAMPTZ '2026-01-01 10:00:00+00'
          AND id < 900000
      )
  )
ORDER BY occurred_at DESC, id DESC
LIMIT 51;
~~~

Quan sát database có sử dụng index phù hợp không, có bước sort lớn hay không, số hàng được đọc so với số hàng trả về, buffer hit/read và thời gian thực thi. Query plan có thể thay đổi khi cursor nằm ở vùng dữ liệu khác.

EXPLAIN ANALYZE thực thi câu query, vì vậy cần dùng cẩn thận trên production nếu query nặng. Đo trên dữ liệu và môi trường gần với production để có kết quả có ý nghĩa.

### 7.2. Index không thể thay thế predicate đúng

Có index nhưng predicate sai vẫn có thể bỏ sót/lặp dữ liệu. Ngược lại, predicate đúng nhưng thiếu index vẫn có thể quét lượng lớn dữ liệu. Cần cả ba yếu tố: thứ tự và cursor logic chính xác, index hỗ trợ filter/order, và query plan xác nhận database thực sự dùng index hiệu quả.

## 8. Phân trang tăng dần và giảm dần

Ví dụ trước sắp xếp giảm dần:

~~~sql
ORDER BY occurred_at DESC, id DESC
~~~

Trang tiếp theo dùng điều kiện nhỏ hơn:

~~~sql
occurred_at < :lastOccurredAt
OR (occurred_at = :lastOccurredAt AND id < :lastId)
~~~

Nếu sắp xếp tăng dần:

~~~sql
ORDER BY occurred_at ASC, id ASC
~~~

thì điều kiện tiếp theo dùng lớn hơn:

~~~sql
occurred_at > :lastOccurredAt
OR (occurred_at = :lastOccurredAt AND id > :lastId)
~~~

Nếu sort có chiều hỗn hợp, ví dụ priority DESC, created_at ASC, id ASC, predicate cần khai triển theo thứ tự từ điển:

~~~sql
WHERE priority < :lastPriority
   OR (
       priority = :lastPriority
       AND created_at > :lastCreatedAt
   )
   OR (
       priority = :lastPriority
       AND created_at = :lastCreatedAt
       AND id > :lastId
   )
~~~

Đừng đảo tất cả dấu so sánh cùng lúc nếu các cột sort có chiều khác nhau. Mỗi nhánh phải phản ánh thứ tự của cột tương ứng.

## 9. Cursor và dữ liệu NULL

Ví dụ dùng occurred_at NOT NULL để predicate đơn giản. Nếu cột sort có thể là NULL, so sánh nhỏ hơn, lớn hơn hoặc bằng với NULL không cho kết quả true như so sánh giá trị thông thường.

Có hai hướng:

- Thiết kế cột sort NOT NULL nếu nghiệp vụ cho phép.
- Đưa quy tắc null ordering vào cả ORDER BY, cursor và predicate.

Ví dụ có thể dùng một biểu thức phân loại null:

~~~sql
ORDER BY
    CASE WHEN occurred_at IS NULL THEN 1 ELSE 0 END,
    occurred_at DESC,
    id DESC
~~~

Nếu chọn cách này, cursor phải chứa cả trạng thái null-rank và các giá trị tiếp theo; predicate tiếp tục cũng phải so sánh đúng các thành phần đó. Cách này phức tạp hơn và có thể cần expression index hoặc cột chuẩn hóa tùy database.

Với dữ liệu lớn, thiết kế cột sort không null thường giúp cursor và index dễ hiểu, dễ tối ưu hơn.

## 10. Dữ liệu thay đổi giữa các trang: consistency và giới hạn

Keyset pagination tránh một số vấn đề của offset, nhưng **không tạo snapshot bất biến cho toàn bộ quá trình duyệt**. Mỗi request trang tiếp theo thường chạy ở transaction riêng.

Ví dụ với thứ tự giảm dần:

- Một event mới được thêm vào trước cursor thường không làm các hàng phía sau cursor dịch chuyển như offset pagination.
- Một hàng bị xóa trước khi cursor tới nó sẽ không xuất hiện.
- Một hàng được thêm với timestamp cũ hơn cursor có thể xuất hiện ở trang sau, dù nó được tạo sau khi người dùng bắt đầu duyệt.
- Nếu cột sort của một hàng thay đổi, hàng có thể di chuyển qua cursor, gây lặp hoặc bỏ sót.

### 10.1. Dùng cột sort bất biến

Đối với audit log hoặc event stream, occurred_at thường được giữ nguyên sau khi ghi. Kết hợp với ID duy nhất tạo thứ tự ổn định hơn.

Không nên keyset theo một cột thường xuyên được cập nhật như display_name, status hoặc updated_at nếu việc thay đổi có thể di chuyển hàng qua vị trí cursor.

### 10.2. High-water mark

Nếu muốn giới hạn tập dữ liệu thuộc một lần duyệt, có thể lấy một **high-water mark** ở trang đầu, ví dụ khóa lớn nhất tại thời điểm bắt đầu. Mọi trang tiếp theo áp dụng thêm điều kiện không vượt quá mốc đó.

Với sort giảm dần theo (occurred_at, id), cursor đầu tiên có thể đóng vai trò mốc trên. Tuy nhiên, high-water mark chỉ giới hạn các hàng theo khóa sắp xếp; nó không tạo snapshot đầy đủ nếu hệ thống cho phép chèn dữ liệu muộn với timestamp cũ hoặc sửa/xóa hàng trong lúc duyệt.

Nếu cần snapshot nhất quán mạnh, hãy xem xét transaction isolation/snapshot phù hợp, bảng snapshot/materialized result hoặc lưu danh sách ID cần xử lý. Một transaction kéo dài qua nhiều request web thường không phải lựa chọn tốt vì giữ connection và snapshot lâu.

### 10.3. Job xử lý dữ liệu và checkpoint

Với batch job, cursor có thể được lưu làm checkpoint sau mỗi chunk:

~~~text
last_occurred_at = 2026-01-01T10:00:00Z
last_id = 900000
~~~

Khi job chạy lại, truy vấn tiếp tục sau checkpoint. Để tránh mất dữ liệu khi job crash:

- Chỉ cập nhật checkpoint sau khi chunk đã được xử lý/commit thành công.
- Xử lý idempotent để retry không gây side effect trùng.
- Ghi checkpoint cùng transaction với kết quả xử lý nếu có thể và cùng database.
- Định nghĩa cách xử lý event đến muộn hoặc dữ liệu bị sửa.
- Ghi lại bộ lọc, tenant và phiên bản cursor để resume đúng query.

Checkpoint không nên chỉ lưu một ID nếu thứ tự query dựa trên nhiều cột.

## 11. Thiết kế cursor token cho API

API không nhất thiết phải gửi hai field occurredAt và id dưới dạng query parameter riêng. Có thể đóng gói chúng thành một cursor token:

~~~json
{
  "occurredAt": "2026-01-01T10:00:00Z",
  "id": 900000
}
~~~

Server có thể serialize JSON, encode Base64 URL-safe rồi trả cho client. Ở request sau, client gửi token để server giải mã.

Lưu ý:

- Base64 chỉ là encoding, **không phải mã hóa bảo mật**.
- Không đưa thông tin nhạy cảm vào cursor token nếu token có thể bị đọc.
- Nếu client không được phép sửa cursor, có thể ký token bằng HMAC hoặc dùng token opaque lưu trạng thái ở server.
- Gắn cursor với filter/tenant/sort version để không thể dùng cursor của truy vấn khác.
- Kiểm tra token sai định dạng, hết hạn hoặc không còn hợp lệ.
- Giới hạn page size ở server, không tin giá trị do client gửi.

Ví dụ response:

~~~json
{
  "items": [
    {
      "id": 900001,
      "eventType": "ORDER_CREATED"
    }
  ],
  "nextCursor": "eyJvY2N1cnJlZEF0IjoiLi4uIiwiaWQiOjk..."
}
~~~

Đây là JSON minh họa cấu trúc API, không phải định dạng bắt buộc của Spring Data JDBC.

## 12. Truy vấn tùy chỉnh với JdbcTemplate

Nếu logic truy vấn cần được xây dựng động hoặc repository @Query không đủ linh hoạt, có thể dùng NamedParameterJdbcTemplate. Ví dụ:

~~~java
import java.time.Instant;
import java.util.List;
import java.util.UUID;

import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class AuditEventKeysetDao {

    private final NamedParameterJdbcTemplate jdbc;

    public AuditEventKeysetDao(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<AuditEvent> findNext(
            UUID tenantId,
            Instant lastOccurredAt,
            Long lastId,
            int limit
    ) {
        String sql = """
                SELECT id, tenant_id, occurred_at, event_type, payload
                FROM audit_events
                WHERE tenant_id = :tenantId
                  AND (
                      occurred_at < :lastOccurredAt
                      OR (
                          occurred_at = :lastOccurredAt
                          AND id < :lastId
                      )
                  )
                ORDER BY occurred_at DESC, id DESC
                LIMIT :limit
                """;

        var parameters = new MapSqlParameterSource()
                .addValue("tenantId", tenantId)
                .addValue("lastOccurredAt", lastOccurredAt)
                .addValue("lastId", lastId)
                .addValue("limit", limit);

        return jdbc.query(sql, parameters, (rs, rowNum) ->
                new AuditEvent(
                        rs.getLong("id"),
                        rs.getObject("tenant_id", UUID.class),
                        rs.getTimestamp("occurred_at").toInstant(),
                        rs.getString("event_type"),
                        rs.getString("payload")
                )
        );
    }
}
~~~

Với JDBC template, ứng dụng tự chịu trách nhiệm mapping ResultSet sang object. Cần xử lý đúng nullable columns, kiểu UUID và timestamp theo driver. Nếu dùng JdbcTemplate thay cho repository, annotation @Column của entity không tự động điều khiển RowMapper thủ công.

Có thể dùng DAO này khi cần SQL tùy biến cao, nhưng phải tự duy trì mapping và kiểm thử trên database mục tiêu.

## 13. Giới hạn và lưu ý khi dùng @Query

@Query phù hợp với SQL cố định và cursor có cấu trúc ổn định. Tuy nhiên:

- Cú pháp LIMIT không portable cho mọi database.
- Tên bảng/cột phải khớp schema và mapping.
- SELECT nên trả đủ cột cho entity hoặc projection đích.
- Giá trị cursor phải được bind bằng parameter, không nối chuỗi.
- Sort direction và column name không thể an toàn thay bằng bind parameter thông thường; nếu cho client chọn sort, cần allowlist các query/sort option đã định nghĩa.
- Cursor phải được validate trước khi gọi repository.
- Nếu cần thay đổi động nhiều filter hoặc sort, custom DAO có thể rõ ràng hơn một method repository rất dài.

Keyset pagination thường không cần Page<T> với tổng số trang. Mục tiêu là lấy “trang tiếp theo” dựa trên cursor; đếm tổng số hàng có thể tốn kém và không cần thiết với infinite scroll hoặc job tuần tự.

## 14. Các lỗi thường gặp

| Biểu hiện | Nguyên nhân | Hướng xử lý |
|---|---|---|
| Hàng bị lặp giữa hai trang | Cursor không chứa tie-breaker hoặc cursor lấy từ hàng dư | Thêm ID vào sort và lấy cursor từ hàng cuối response |
| Hàng bị bỏ sót | Predicate không khớp chiều sort hoặc dùng sai cột cursor | Viết predicate theo toàn bộ ORDER BY |
| Trang đầu và trang sau khác thứ tự | Thiếu ORDER BY xác định hoặc sort key thay đổi | Thêm unique tie-breaker và dùng cột sort ổn định |
| Trang sâu vẫn chậm | Thiếu index phù hợp hoặc query plan không dùng index | Tạo index theo filter + sort và kiểm tra EXPLAIN |
| Cursor có timestamp trùng gây lỗi | Chỉ dùng timestamp, không có ID tie-breaker | Dùng cursor ghép (occurred_at, id) |
| Có hàng NULL bị mất | So sánh nhỏ hơn/lớn hơn không xử lý NULL như giá trị thường | Dùng NOT NULL hoặc predicate null-ordering tường minh |
| Dữ liệu mới xuất hiện ở trang sau | Có insert muộn với sort key nằm sau cursor | Chọn semantics live feed hoặc dùng high-water mark/snapshot |
| Hàng di chuyển qua cursor | Cột sort có thể cập nhật | Chọn sort key bất biến hoặc chấp nhận semantics thay đổi |
| Cursor dùng nhầm tenant/filter | Token không gắn với truy vấn ban đầu | Ràng buộc cursor với tenant, filter và sort |
| SQL LIMIT không chạy trên DB khác | Cú pháp giới hạn hàng phụ thuộc dialect | Dùng cú pháp phù hợp hệ quản trị |
| Mapping entity thiếu property | SELECT không trả đủ cột | Chọn đủ cột hoặc dùng projection |
| Cursor token bị sửa | Chỉ Base64 encode | Dùng HMAC/signature hoặc opaque server-side token |

## 15. Quy trình triển khai keyset pagination

1. Xác định tập dữ liệu và filter bắt buộc (ví dụ tenant).
2. Chọn thứ tự sort ổn định, có tie-breaker duy nhất.
3. Xác định cursor gồm toàn bộ cột sort.
4. Viết query trang đầu không có cursor.
5. Viết query trang tiếp theo với predicate tương ứng thứ tự.
6. Tạo index hỗ trợ filter và sort.
7. Dùng limit + 1 để xác định hasNext.
8. Tạo cursor từ hàng cuối cùng thực sự trả về.
9. Validate cursor token và gắn nó với filter/tenant.
10. Kiểm tra consistency khi dữ liệu được thêm, sửa hoặc xóa giữa các request.
11. Đo query plan và hiệu năng trên dữ liệu lớn.
12. Kiểm thử ranh giới trang với nhiều hàng có cùng sort key.

## 16. Bài tập thực hành

### Bài 1 — Offset và keyset

Tạo bảng audit_events với ít nhất một triệu hàng. So sánh query LIMIT 50 OFFSET 500000 với query keyset tại một cursor tương ứng. Dùng EXPLAIN ANALYZE để quan sát số hàng đọc và thời gian.

### Bài 2 — Tie-breaker

Tạo nhiều hàng có cùng occurred_at. Thử keyset chỉ dùng timestamp, sau đó thêm id vào ORDER BY, cursor và predicate. Kiểm tra không lặp và không bỏ sót ở ranh giới trang.

### Bài 3 — limit + 1

Viết service lấy page size 20 nhưng query 21 hàng. Kiểm tra response, hasNext và nextCursor khi có 0, 20, 21 và 40 hàng.

### Bài 4 — Index

Tạo index (tenant_id, occurred_at DESC, id DESC). So sánh query plan trước và sau index. Thử đổi thứ tự cột index và giải thích ảnh hưởng.

### Bài 5 — Sort tăng dần

Chuyển query sang ORDER BY occurred_at ASC, id ASC. Sửa predicate sang > và kiểm thử cursor ở những timestamp trùng nhau.

### Bài 6 — Cursor token

Serialize cursor thành token URL-safe. Thử token hỏng, token thuộc tenant khác và token đã bị sửa. Thiết kế xác thực chữ ký hoặc opaque token.

### Bài 7 — Dữ liệu thay đổi

Đang duyệt các trang, thêm event mới, xóa một event và cập nhật sort key của một event. Ghi nhận hành vi. Quyết định API cần live-feed semantics, high-water mark hay snapshot consistency.

### Bài 8 — Checkpoint cho batch job

Tạo job xử lý event theo cursor. Lưu checkpoint sau mỗi chunk đã commit. Cố ý dừng job giữa chừng rồi chạy lại và xác nhận không mất hoặc xử lý trùng ngoài chính sách idempotency.

## 17. Ghi nhớ

- **Keyset pagination** lấy trang tiếp theo dựa trên giá trị khóa sắp xếp cuối trang trước, thay vì bỏ qua số lượng hàng bằng OFFSET.
- Thứ tự phải xác định duy nhất; thêm primary key làm tie-breaker nếu cột sort nghiệp vụ không unique.
- Cursor chứa toàn bộ cột sort và predicate phải khớp chính xác chiều ASC/DESC của ORDER BY.
- Với Spring Data JDBC, có thể viết truy vấn cursor tùy chỉnh bằng @Query hoặc NamedParameterJdbcTemplate.
- Dùng limit + 1 để biết có trang tiếp theo; cursor mới lấy từ hàng cuối cùng được trả về, không phải hàng dư.
- Tạo index theo filter và thứ tự sort, rồi kiểm tra query plan trên database thật.
- Keyset giảm chi phí truy cập trang sâu khi có index phù hợp, nhưng không tự tạo snapshot nhất quán cho dữ liệu thay đổi.
- Chọn sort key ổn định, xác định semantics cho insert muộn/delete/update và lưu checkpoint đúng thời điểm.
- Cursor token cần được validate và gắn với tenant/filter/sort; Base64 chỉ là encoding, không phải bảo mật.
