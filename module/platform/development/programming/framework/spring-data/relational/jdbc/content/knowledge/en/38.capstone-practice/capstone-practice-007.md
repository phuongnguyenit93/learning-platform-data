# Adding Auditing and Post-Commit Events

In a **Spring Data Relational JDBC** application, auditing and domain events help record who changed data, when it was changed, and notify other components after a business operation. When moving from JPA to Spring Data JDBC, you must place both mechanisms properly within the new lifecycle: auditing runs during the persistence pipeline preparing to write an aggregate, while events that must execute after transaction commit need to be bound to the transaction.

This lab adds four audit fields to the order aggregate, configures `@EnableJdbcAuditing`, provides `AuditorAware` and `DateTimeProvider`, then publishes an `OrderConfirmed` event and handles it via `@TransactionalEventListener(phase = AFTER_COMMIT)`. Finally, the lesson distinguishes persistence callbacks from application events, verifies rollback behavior, and introduces the transactional outbox for side effects requiring high reliability.

## 1. What problems do auditing and events solve?

Auditing answers these questions:

- When was the record created?
- Who created the record?
- When was the most recent update?
- Who performed the most recent update?

Business events answer a different question: after an action such as confirming an order has been saved successfully, which components need to be notified to send an email, update a read model, or publish a message?

These two responsibilities differ in timing and purpose:

| Mechanism | Timing | Purpose |
| --- | --- | --- |
| Auditing | During aggregate write lifecycle | Populate created/modified dates and actors |
| Entity callback | Before or after a persistence step | Enrich or adjust data during lifecycle |
| Persistence lifecycle event | When Spring Data JDBC executes load/save steps | Observe persistence activity |
| Application/domain event | When a use case completes a business action | Announce a domain-meaningful event |
| Transaction-bound event listener | After commit or rollback per phase | Run side effects consistent with transaction outcome |
| Transactional outbox | Written in the same transaction as the aggregate | Guarantee a pending event record even if the process stops after commit |

Do not use a `BeforeSave` callback to send emails or make HTTP calls. That callback runs during the write phase, when the transaction can still roll back. External side effects should happen after commit or via an outbox.

## 2. Adding audit fields to the aggregate

Suppose an order has four fields:

- `createdAt`: creation timestamp.
- `createdBy`: creating actor.
- `lastModifiedAt`: most recent modification timestamp.
- `lastModifiedBy`: most recent modifying actor.

Entity:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Version
    private Long version;

    private String orderNumber;
    private OrderStatus status;

    @CreatedDate
    private Instant createdAt;

    @CreatedBy
    private String createdBy;

    @LastModifiedDate
    private Instant lastModifiedAt;

    @LastModifiedBy
    private String lastModifiedBy;
}
~~~

Auditing annotations belong to Spring Data Commons:

| Annotation | Meaning |
| --- | --- |
| `@CreatedDate` | Timestamp when the entity was created |
| `@CreatedBy` | Actor that created the entity |
| `@LastModifiedDate` | Timestamp when the entity was last updated |
| `@LastModifiedBy` | Actor that performed the last update |

`@Version` has a separate responsibility: detecting concurrent updates. Do not use `version` in place of `lastModifiedAt`, and do not use audit timestamps in place of optimistic locking.

### 2.1. Temporal data types

Java time types such as `Instant`, `LocalDateTime`, `OffsetDateTime`, or `LocalDate` can be used depending on mapping and business needs. For audit timestamps across multiple systems, `Instant` is usually convenient because it represents a point on the UTC timeline.

Example schema:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(24) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    created_by VARCHAR(120),
    last_modified_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_modified_by VARCHAR(120)
);
~~~

Exact timestamp column types depend on the database. Choose a column type compatible with your Java type and keep timezones consistent across the application, database, and logs.

### 2.2. Audit fields are not client-supplied data

Do not accept `createdBy`, `createdAt`, or `lastModifiedBy` from incoming requests and trust them for direct persistence. These fields should be determined by the backend from the authenticated actor and the application's clock. Allowing clients to supply them lets callers forge change history.

## 3. Enabling auditing with @EnableJdbcAuditing

Spring Data JDBC provides `@EnableJdbcAuditing` to turn on the auditing infrastructure. Place the annotation on a configuration class loaded by the application context:

~~~java
import java.time.Clock;
import java.time.Instant;
import java.util.Optional;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.auditing.DateTimeProvider;
import org.springframework.data.domain.AuditorAware;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing(
        auditorAwareRef = "auditorAware",
        dateTimeProviderRef = "dateTimeProvider"
)
public class JdbcAuditingConfiguration {

    @Bean
    AuditorAware<String> auditorAware(CurrentActor currentActor) {
        return currentActor::currentActor;
    }

    @Bean
    DateTimeProvider dateTimeProvider(Clock clock) {
        return () -> Optional.of(Instant.now(clock));
    }

    @Bean
    Clock clock() {
        return Clock.systemUTC();
    }
}
~~~

`CurrentActor` is an application abstraction for retrieving the current actor. For instance, it can be implemented using Spring Security, tenant context, or service identity. This decoupling keeps auditing independent of HTTP requests.

If you do not need a custom clock, you can omit `DateTimeProvider` and let auditing use its default time source. Providing a `Clock` makes time-dependent testing deterministic and easy to control.

### 3.1. AuditorAware supplies the actor

`AuditorAware<T>` returns an `Optional<T>` for the current actor. Example with Spring Security:

~~~java
import java.util.Optional;

import org.springframework.data.domain.AuditorAware;
import org.springframework.security.authentication.AnonymousAuthenticationToken;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;

public class SecurityAuditorAware implements AuditorAware<String> {

    @Override
    public Optional<String> getCurrentAuditor() {
        Authentication authentication =
                SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null
                || !authentication.isAuthenticated()
                || authentication instanceof AnonymousAuthenticationToken) {
            return Optional.empty();
        }

        return Optional.of(authentication.getName());
    }
}
~~~

Register the bean:

~~~java
@Bean
AuditorAware<String> auditorAware() {
    return new SecurityAuditorAware();
}
~~~

For background operations, there is no logged-in user. You can return a system actor like `system:order-import`, or `Optional.empty()` if the schema and policy allow it. Choose a consistent convention so audit records clearly explain the source of changes.

### 3.2. Do not rely on request context as the sole source

Auditing can run inside schedulers, message consumers, batch jobs, or integration tests. Therefore, do not assume every operation has an HTTP request and a user `SecurityContext`. A `CurrentActor` abstraction can supply actors from multiple sources:

- Authenticated user.
- Service account.
- Batch job.
- Message consumer.
- System process.

If no actor is present, decide explicitly whether to record `null`, a system identity, or reject the operation. Never fabricate a fake user.

### 3.3. DateTimeProvider and Clock

`DateTimeProvider` supplies timestamps for auditing. Using `Clock` decouples tests from the system clock:

~~~java
@Bean
Clock auditClock() {
    return Clock.systemUTC();
}

@Bean
DateTimeProvider dateTimeProvider(Clock auditClock) {
    return () -> Optional.of(Instant.now(auditClock));
}
~~~

If the application needs a display timezone, convert at the presentation layer. Audit timestamps should follow one consistent convention, typically UTC.

## 4. Auditing runs in the persistence lifecycle

When calling repository `save`, Spring Data JDBC runs steps to convert the aggregate into writable data. The auditing infrastructure uses entity callbacks to populate audit fields before the entity is converted and saved.

Conceptual flow:

~~~text
Application service
       |
       v
repository.save(aggregate)
       |
       v
Auditing callback
  - created date/by if insert
  - modified date/by on write
       |
       v
Entity conversion
       |
       v
SQL INSERT / UPDATE
       |
       v
Transaction commit or rollback
~~~

Because audit values are populated during the persistence operation, use the instance returned from `save` if you need to read the populated values.

### 4.1. Created and modified fields

On insert:

- `createdAt` and `createdBy` are populated via the auditor/time provider.
- `lastModifiedAt` and `lastModifiedBy` may also be populated on creation, depending on the `modifyOnCreate` setting.

On update:

- `createdAt` and `createdBy` preserve creation history.
- `lastModifiedAt` and `lastModifiedBy` are updated for the current write.

If you need to change default behavior, check the attributes of `@EnableJdbcAuditing` in your Spring Data Relational version, especially `modifyOnCreate` and `setDates`.

### 4.2. Inserts and updates must be distinguished accurately

Auditing depends on whether the persistence operation is recognized as an insert or an update. If an entity uses application-assigned IDs, configure an appropriate newness strategy, such as `Persistable.isNew()` or `@Version` depending on your model. If a new entity is mistaken for an existing one, both the SQL operation and audit semantics will be wrong.

### 4.3. Writing directly with JdbcTemplate

A `JdbcTemplate.update(...)` call bypasses the aggregate mapping and auditing callback pipeline:

~~~java
jdbcTemplate.update(
        "UPDATE purchase_order SET status = ? WHERE id = ?",
        "CANCELLED",
        orderId
);
~~~

When using direct SQL, the application must update audit fields explicitly:

~~~java
jdbcTemplate.update("""
        UPDATE purchase_order
        SET status = ?,
            last_modified_at = ?,
            last_modified_by = ?
        WHERE id = ?
        """,
        "CANCELLED",
        Instant.now(clock),
        currentActor.requireActor(),
        orderId
);
~~~

If the table has `@Version`, direct SQL must also check and increment the version. Encapsulate these rules in a shared persistence adapter so writes stay consistent across the codebase.

## 5. Entity callbacks and persistence lifecycle events

Spring Data Relational provides callbacks to hook into the entity/aggregate lifecycle. Common callbacks include:

| Callback | Timing |
| --- | --- |
| `BeforeConvertCallback<T>` | Before the aggregate is converted into writable data |
| `BeforeSaveCallback<T>` | Before the data is saved |
| `AfterSaveCallback<T>` | After the save operation completes |
| `AfterConvertCallback<T>` | After read data is converted into an entity |

Callback signatures and accompanying types can vary across Spring Data Relational versions. Check the API in your application's dependencies when implementing.

### 5.1. What are callbacks suited for?

Callbacks are suited for technical logic tied to the persistence lifecycle:

- Normalizing or enriching metadata before conversion.
- Generating values dependent on save timing.
- Adjusting data prior to writing.
- Observing persistence outcomes to update technical state.

Illustrative `BeforeConvertCallback`:

~~~java
@Component
public class OrderNumberNormalization
        implements BeforeConvertCallback<PurchaseOrder> {

    @Override
    public PurchaseOrder onBeforeConvert(PurchaseOrder aggregate) {
        aggregate.normalizeOrderNumber();
        return aggregate;
    }
}
~~~

This is a synchronous callback executing inline during persistence. Use it only for fast, deterministic work. Never send emails, call payment gateways, or wait on HTTP responses inside a callback.

### 5.2. Callbacks differ from application events

Callbacks can typically return a modified aggregate to be used in the next persistence step. Application events primarily announce that something occurred so listeners can react.

Do not use callbacks to implement long-running business workflows. If a callback throws an exception, the persistence operation fails and the transaction rolls back.

### 5.3. Persistence lifecycle events

Spring Data Relational may also publish lifecycle events such as `BeforeConvertEvent`, `BeforeSaveEvent`, `AfterSaveEvent`, `AfterLoadEvent`, or `AfterConvertEvent` depending on operation type and version. They allow observers to monitor persistence activity.

Lifecycle events generally fire before the transaction commits. A standard `@EventListener` is invoked immediately when the event is published; it does not wait for commit. If the listener performs an external side effect, the transaction may later roll back while the side effect has already happened.

## 6. Publishing a domain event when an order is confirmed

A business event should describe what happened, such as `OrderConfirmed`, rather than merely stating that a database row was updated.

Events should be immutable data carrying the ID and necessary details:

~~~java
public record OrderConfirmed(
        Long orderId,
        String orderNumber,
        Long aggregateVersion
) {
}
~~~

Application service:

~~~java
@Service
public class OrderApplicationService {

    private final PurchaseOrderRepository orders;
    private final ApplicationEventPublisher events;

    public OrderApplicationService(
            PurchaseOrderRepository orders,
            ApplicationEventPublisher events
    ) {
        this.orders = orders;
        this.events = events;
    }

    @Transactional
    public PurchaseOrder confirm(Long id) {
        PurchaseOrder order = orders.findById(id).orElseThrow();
        order.confirm();

        PurchaseOrder saved = orders.save(order);

        events.publishEvent(new OrderConfirmed(
                saved.getId(),
                saved.getOrderNumber(),
                saved.getVersion()
        ));

        return saved;
    }
}
~~~

The event is published after the repository save succeeds, while still inside the transaction. The listener decides which phase to wait for.

Avoid putting an entire mutable aggregate into an event when listeners only need an ID and a few facts. Small, immutable events prevent listeners from accidentally depending on mutated objects or ORM-specific lazy behavior.

## 7. Running listeners after commit with @TransactionalEventListener

Listener:

~~~java
@Component
public class OrderConfirmedListener {

    private final ConfirmationEmailGateway emailGateway;

    public OrderConfirmedListener(
            ConfirmationEmailGateway emailGateway
    ) {
        this.emailGateway = emailGateway;
    }

    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    public void on(OrderConfirmed event) {
        emailGateway.sendConfirmation(
                event.orderId(),
                event.orderNumber()
        );
    }
}
~~~

`@TransactionalEventListener` binds the listener to the active transaction. With `AFTER_COMMIT`, the listener runs only after the transaction commits successfully.

### 7.1. Why publish before commit when the listener runs after commit?

The application event is published inside the `confirm` method while the transaction is still open. Spring registers the listener to execute when the transaction finishes. Once commit succeeds, the transaction synchronization callback triggers the listener.

~~~text
BEGIN
  |
  +-- load PurchaseOrder
  |
  +-- change status
  |
  +-- repository.save(...)
  |
  +-- publish OrderConfirmed
  |       |
  |       +-- listener registered to wait for AFTER_COMMIT
  |
COMMIT
  |
  +-- OrderConfirmedListener.on(...)
          |
          +-- send confirmation email
~~~

If the transaction rolls back, the `AFTER_COMMIT` listener does not run. This is the primary difference from a plain `@EventListener`.

### 7.2. TransactionPhase

`@TransactionalEventListener` supports these phases:

| Phase | Timing |
| --- | --- |
| `BEFORE_COMMIT` | Before the transaction commits |
| `AFTER_COMMIT` | After a successful commit |
| `AFTER_ROLLBACK` | After a rollback |
| `AFTER_COMPLETION` | After transaction completion, whether commit or rollback |

For order confirmation emails, `AFTER_COMMIT` is typically chosen. For releasing resources or recording an outcome regardless of commit/rollback, consider `AFTER_COMPLETION` or `AFTER_ROLLBACK` according to intent.

### 7.3. What if there is no active transaction?

By default, a transactional event listener requires an active transaction. If an event is published without a transaction, the listener is not executed.

The `fallbackExecution = true` attribute allows the listener to run even without a transaction. However, there is then no "after commit" guarantee because there is no transaction to wait on. Enable fallback only if the business genuinely accepts non-transactional execution.

To guarantee after-commit semantics, call a `@Transactional` application service through the Spring proxy and publish the event inside that transaction.

## 8. Event listeners writing to the database need a new transaction

After commit, the original transaction has already completed. If the listener needs to write to another table, such as creating a secondary audit record or notification status, open a new transaction:

~~~java
@Component
public class OrderProjectionListener {

    private final OrderProjectionRepository projections;

    public OrderProjectionListener(
            OrderProjectionRepository projections
    ) {
        this.projections = projections;
    }

    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void on(OrderConfirmed event) {
        projections.markConfirmed(
                event.orderId(),
                event.aggregateVersion()
        );
    }
}
~~~

After commit, resources from the previous transaction may still be bound during the completion callback. If the listener writes data while participating in the already-committed transaction, those changes might not commit as expected. `REQUIRES_NEW` creates a separate transaction for the listener's write operation.

If the listener only calls an external gateway, `REQUIRES_NEW` does not make the remote call atomic with the database. It only manages the database transaction for local work.

## 9. Asynchronous event listeners

If a side effect takes time, you can combine `@Async` with `@EnableAsync`:

~~~java
@Configuration
@EnableAsync
public class AsyncConfiguration {
}
~~~

~~~java
@Component
public class OrderEmailListener {

    @Async("applicationTaskExecutor")
    @TransactionalEventListener(
            phase = TransactionPhase.AFTER_COMMIT
    )
    public void on(OrderConfirmed event) {
        // Send email or call an external service.
    }
}
~~~

The listener then runs on the executor after the transaction commits. Configure a bounded thread/queue executor and monitor failures. Using an unbounded executor can cause traffic spikes to spawn excessive threads or queued tasks in memory.

### 9.1. Async does not mean durable

If the process stops after commit but before the task runs, in-memory events can be lost. `@Async` only changes the execution thread; it does not provide a durable queue.

If reliable event delivery is required, use a transactional outbox or a message broker with proper acknowledgments and retries.

## 10. Domain events from the aggregate root

Spring Data repositories support domain events from aggregate roots via `@DomainEvents` and `@AfterDomainEventPublication`. You can extend `AbstractAggregateRoot` to register events inside domain methods:

~~~java
import org.springframework.data.domain.AbstractAggregateRoot;

@Table("purchase_order")
public class PurchaseOrder
        extends AbstractAggregateRoot<PurchaseOrder> {

    @Id
    private Long id;

    private OrderStatus status;

    public void confirm() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Order is not pending");
        }

        status = OrderStatus.CONFIRMED;
        registerEvent(new OrderConfirmed(id, null, null));
    }
}
~~~

When the repository saves the aggregate, the Spring Data repository infrastructure publishes registered domain events. Events are published during the repository call; listeners can use `@TransactionalEventListener(AFTER_COMMIT)` to react only after the transaction succeeds.

If the event needs the new version or persistence-populated fields, consider publishing an explicit application event after receiving the object returned by `save`, as in the earlier example. Domain methods typically run before the new version is assigned.

When using `JdbcAggregateTemplate` or direct SQL instead of a repository proxy, do not assume the repository domain event publisher will run automatically. Publish events via `ApplicationEventPublisher` in the application service after the write, or use an event mechanism explicitly configured for that persistence path.

## 11. Transactional outbox for high-reliability side effects

`@TransactionalEventListener(AFTER_COMMIT)` guarantees the listener will not run when the transaction rolls back, but it does not guarantee the external side effect will finish. The following can happen:

1. Database commit succeeds.
2. Process stops before the listener sends the message.
3. The aggregate is confirmed, yet downstream systems never receive the event.

If losing an event is unacceptable, use a transactional outbox. In the same transaction, save both the aggregate and an outbox record:

~~~java
@Transactional
public PurchaseOrder confirm(Long id) {
    PurchaseOrder order = orders.findById(id).orElseThrow();
    order.confirm();

    PurchaseOrder saved = orders.save(order);

    outbox.save(OutboxMessage.pending(
            UUID.randomUUID(),
            "OrderConfirmed",
            saved.getId(),
            saved.getVersion()
    ));

    return saved;
}
~~~

Both operations commit together:

~~~text
BEGIN
  |
  +-- UPDATE purchase_order
  |
  +-- INSERT outbox_message
  |
COMMIT
  |
  +-- poller/dispatcher reads outbox
          |
          +-- publish message
          |
          +-- mark delivered
~~~

If the transaction rolls back, both the aggregate update and the outbox row roll back. If the process stops after commit, the outbox row remains for the dispatcher to process once the application restarts.

### 11.1. Basic outbox structure

~~~sql
CREATE TABLE outbox_message (
    id UUID PRIMARY KEY,
    event_type VARCHAR(120) NOT NULL,
    aggregate_id BIGINT NOT NULL,
    aggregate_version BIGINT,
    payload TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    delivered_at TIMESTAMP WITH TIME ZONE,
    attempts INTEGER NOT NULL DEFAULT 0
);
~~~

In production systems, you can add status, next-attempt timestamp, error code, partition key, and dispatcher indexes. Payloads should follow a version/schema contract so consumers remain compatible as events evolve.

### 11.2. Dispatcher and idempotency

The dispatcher must:

- Select unsent outbox rows.
- Claim/lock rows so multiple workers do not accidentally publish the same row concurrently.
- Publish the message to a broker or external endpoint.
- Mark delivered only after receiving appropriate acknowledgment.
- Retry transient failures with backoff and limits.
- Route persistent failures to a dead-letter or operations workflow.

You cannot always guarantee exactly-once delivery across a database and message broker with a single JDBC transaction alone. In practice, systems combine at-least-once delivery with idempotent consumers. Consumers record processed event IDs or use unique constraints so each event is effectively applied once.

### 11.3. When to use AFTER_COMMIT vs. outbox?

| Need | Approach |
| --- | --- |
| Best-effort cache refresh after commit | `@TransactionalEventListener(AFTER_COMMIT)` |
| Internal email where operational retry is acceptable | `AFTER_COMMIT` listener and error monitoring |
| Publishing messages that must never be lost | Transactional outbox |
| Updating a read model in the same database | Listener with `REQUIRES_NEW` or outbox depending on consistency needs |
| Calling a payment service | Workflow with idempotency, retries, and explicit states; never inside a save callback |

## 12. Testing auditing

With `@DataJdbcTest`, you can import the auditing configuration into the test slice:

~~~java
@DataJdbcTest
@Import(AuditingTestConfiguration.class)
class PurchaseOrderAuditingTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void recordsCreatedAndModifiedAuditFields() {
        PurchaseOrder created = orders.save(
                PurchaseOrder.pending("PO-AUDIT", OrderStatus.PENDING)
        );

        assertThat(created.getCreatedAt()).isNotNull();
        assertThat(created.getCreatedBy()).isEqualTo("test-user");
        assertThat(created.getLastModifiedAt()).isNotNull();
        assertThat(created.getLastModifiedBy()).isEqualTo("test-user");

        Instant originalCreatedAt = created.getCreatedAt();

        created.changeStatus(OrderStatus.CONFIRMED);
        PurchaseOrder updated = orders.save(created);

        assertThat(updated.getCreatedAt()).isEqualTo(originalCreatedAt);
        assertThat(updated.getCreatedBy()).isEqualTo("test-user");
        assertThat(updated.getLastModifiedAt()).isNotNull();
        assertThat(updated.getLastModifiedBy()).isEqualTo("test-user");
    }
}
~~~

Test configuration:

~~~java
@TestConfiguration(proxyBeanMethods = false)
@EnableJdbcAuditing
class AuditingTestConfiguration {

    @Bean
    AuditorAware<String> auditorAware() {
        return () -> Optional.of("test-user");
    }
}
~~~

If a test needs to verify that timestamps strictly advance between insert and update, provide a controllable `DateTimeProvider` instead of relying on `Instant.now()` and assuming the clock ticks between two operations. Tests should also confirm that created fields are not overwritten on update.

## 13. Testing AFTER_COMMIT and rollback

A `@DataJdbcTest` test by default runs inside a Spring Test-managed transaction and rolls back when the test finishes. Therefore, `AFTER_COMMIT` listeners do not run until the test transaction actually commits.

There are two ways to test this:

### 13.1. Controlling the transaction with TestTransaction

Inside a transactional test:

~~~java
@Test
void handlesEventOnlyAfterCommit() {
    orderService.confirm(orderId);

    assertThat(listener.receivedEvents()).isEmpty();

    TestTransaction.flagForCommit();
    TestTransaction.end();

    assertThat(listener.receivedEvents()).hasSize(1);
}
~~~

`orderService.confirm` joins the test transaction when default propagation is `REQUIRED`. The listener runs only after the test transaction commits via `TestTransaction.end()`.

### 13.2. Disabling the test's outer transaction

You can configure:

~~~java
@DataJdbcTest
@Transactional(propagation = Propagation.NOT_SUPPORTED)
class OrderAfterCommitTest {
}
~~~

Then the test has no enclosing outer transaction. Calling a `@Transactional` application service opens its own transaction and commits before the method returns. The `AFTER_COMMIT` listener executes as that transaction completes.

### 13.3. Testing rollback

Use `TransactionTemplate` and mark rollback-only:

~~~java
transactionTemplate.execute(status -> {
    orderService.confirm(orderId);
    status.setRollbackOnly();
    return null;
});

assertThat(listener.receivedEvents()).isEmpty();
assertThat(orders.findById(orderId).orElseThrow().getStatus())
        .isEqualTo(OrderStatus.PENDING);
~~~

The service participates in the current transaction. When the transaction rolls back, the `AFTER_COMMIT` listener is not invoked and the order status reverts to its prior value.

### 13.4. Testing that the listener is not called without a transaction

If an event is published outside a transaction, transactional listeners do not run by default. Test this behavior to catch call paths that accidentally bypass the transactional application service. Do not enable `fallbackExecution` just to make a test pass; doing so alters production semantics.

## 14. Common mistakes

| Error | Cause | Fix |
| --- | --- | --- |
| Audit fields are always null | `@EnableJdbcAuditing` not enabled or configuration not loaded | Import/register auditing configuration |
| `createdBy` has no value | Missing `AuditorAware` or empty actor context | Supply actors for users and background jobs |
| Audit actor is always anonymous | Anonymous authentication not filtered out | Return `Optional.empty()` or an appropriate system actor |
| `createdAt` forged by client | Binding audit fields from incoming requests | Let backend auditing assign the values |
| `lastModifiedAt` unchanged on direct SQL | `JdbcTemplate` bypasses entity callbacks | Update audit fields explicitly in SQL/adapter |
| Using audit timestamp instead of `@Version` | Timestamps are not reliable concurrency tokens | Use `@Version` for optimistic locking |
| Listener runs even on rollback | Using plain `@EventListener` | Use `@TransactionalEventListener(AFTER_COMMIT)` |
| Listener never runs | No transaction or transaction never commits | Publish inside a transactional application service |
| Listener writes DB but changes do not commit | Participating in resources of an already-completed transaction | Use `REQUIRES_NEW` |
| Email sent before transaction commits | Sent from a callback or standard listener | Wait for `AFTER_COMMIT` |
| Event lost when process stops | Event exists only in memory | Use a transactional outbox |
| Event processed twice | Retries or multiple dispatchers | Use event IDs and consumer idempotency |
| `AFTER_COMMIT` test does not run | Test transaction rolls back by default | Use `TestTransaction` or `NOT_SUPPORTED` |
| Async tasks lost | Executor queue is not durable | Use an outbox/broker when durable delivery is needed |

## 15. Workflow for adding auditing and events to a use case

1. **Identify audit fields:** choose actor, created time, and modified time to persist.
2. **Update schema/entity:** add columns and auditing annotations.
3. **Enable auditing:** register `@EnableJdbcAuditing`, `AuditorAware`, and `DateTimeProvider` if needed.
4. **Identify actor sources:** users, service accounts, batches, or system processes.
5. **Verify insert/update:** ensure newness strategy and audit behavior work properly.
6. **Define domain events:** name after business actions and use immutable payloads.
7. **Publish inside transaction:** after the write succeeds and before the transaction ends.
8. **Register listeners:** use `@TransactionalEventListener(AFTER_COMMIT)` for post-commit side effects.
9. **Open a new transaction if listener writes DB:** use `REQUIRES_NEW`.
10. **Use an outbox if events must never be lost:** write the outbox row in the aggregate's transaction.
11. **Test commit and rollback:** verify audit fields, listener phase, idempotency, and failure paths.
12. **Monitor operations:** track retries, listener failures, outbox backlog, and event age.

## Key takeaways

Spring Data JDBC auditing is enabled via `@EnableJdbcAuditing`. `AuditorAware` provides the actor; `DateTimeProvider` provides the timestamp. The `@CreatedDate`, `@CreatedBy`, `@LastModifiedDate`, and `@LastModifiedBy` annotations are processed in the persistence lifecycle when aggregates are saved through Spring Data JDBC. Direct SQL via `JdbcTemplate` does not run auditing callbacks automatically, so audit columns must be updated explicitly. `@Version` remains a separate mechanism for optimistic locking.

To handle side effects after an order is confirmed, publish an application/domain event inside the transaction and use `@TransactionalEventListener(phase = AFTER_COMMIT)`. The listener runs only when the commit succeeds; rollbacks do not trigger it. If the listener writes to the database, use a `REQUIRES_NEW` transaction. If an event must not be lost when the process stops after commit, persist an outbox row in the same transaction and dispatch with retries and idempotency. Test both commit and rollback; keep in mind `@DataJdbcTest` rolls back test transactions by default, so control commits with `TestTransaction` or disable the outer transaction for appropriate tests.
