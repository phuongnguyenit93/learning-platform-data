# Controlling Time with DateTimeProvider and Timezone Conventions

Spring Data JDBC supports auditing to automatically record creation timestamps, update timestamps, and the actor performing operations on an aggregate. Annotations such as `@CreatedDate` and `@LastModifiedDate` mark the properties to be populated; `DateTimeProvider` provides the time value used by the auditing infrastructure.

In applications running across multiple servers or serving users in multiple timezones, timestamps should not accidentally depend on the default timezone of the JVM, the database server, or the user's machine. Establish a unified convention: use an absolute point in time (typically `Instant` in UTC) for storing audit timestamps, control the time source using `Clock`/`DateTimeProvider`, and convert to local timezones only when displaying or processing business dates.

This lesson explains how to configure `DateTimeProvider`, choose temporal types, coordinate application and database timezones, handle DST, test with fixed clocks, and avoid common pitfalls.

## 1. Auditing Timestamps and DateTimeProvider

Auditing answers questions such as:

- When was the record created?
- When was the record last modified?
- Who created or updated the record?
- According to which time source were these values determined?

Commonly used annotations:

| Annotation | Meaning |
| --- | --- |
| `@CreatedDate` | Timestamp when the aggregate/record was created. |
| `@LastModifiedDate` | Timestamp of the most recent modification. |
| `@CreatedBy` | Actor who created the data. |
| `@LastModifiedBy` | Actor who last modified the data. |

`DateTimeProvider` is an abstraction that provides the current point in time to the auditing handler. It returns `Optional<TemporalAccessor>`, so it can supply `Instant`, `LocalDateTime`, or a temporal type matching the data model.

If no custom provider is configured, Spring Data uses a default time provider. The default provider is convenient for simple applications, but relies on the runtime's default time source. A custom provider centralizes the time convention, injects a `Clock`, and lets you swap the clock during testing.

Important point: `DateTimeProvider` determines the auditing value assigned inside the Spring Data pipeline. It does not change the database session timezone, configure the JDBC driver, or alter how the database formats timestamps.

## 2. Enabling Auditing for Spring Data JDBC

Enable auditing using `@EnableJdbcAuditing` in configuration:

```java
package com.example.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing
public class JdbcAuditingConfiguration {
}
```

Once enabled, Spring Data JDBC registers the auditing mechanism to populate annotated properties in aggregates during supported persistence operations.

Example aggregate:

```java
package com.example.orders.domain;

import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String status,
    BigDecimal totalAmount,
    @CreatedDate Instant createdAt,
    @LastModifiedDate Instant lastModifiedAt
) {
}
```

Illustrative PostgreSQL schema:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL,
    total_amount NUMERIC(18, 2) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_modified_at TIMESTAMP WITH TIME ZONE NOT NULL
);
```

In this example, `createdAt` and `lastModifiedAt` represent absolute points in time using `Instant`. The SQL column type must fit the database and JDBC driver in use; a later section distinguishes timestamp types across different DBMSs.

`@CreatedDate` is typically assigned on insert. `@LastModifiedDate` is assigned on insert and on update under the default `modifyOnCreate = true` setting. This behavior can be changed if business rules require the modified field to have a value only after the first edit.

## 3. Creating a Clock-Based DateTimeProvider

Avoid calling `Instant.now()` directly across domain or repository code. Injecting a `Clock` gives the application an explicit time source and allows substituting a fixed clock in tests.

```java
package com.example.config;

import java.time.Clock;
import java.time.Instant;
import java.time.temporal.TemporalAccessor;
import java.util.Optional;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.auditing.DateTimeProvider;
import org.springframework.data.jdbc.repository.config.EnableJdbcAuditing;

@Configuration
@EnableJdbcAuditing(dateTimeProviderRef = "auditDateTimeProvider")
public class JdbcAuditingConfiguration {

    @Bean
    Clock auditClock() {
        return Clock.systemUTC();
    }

    @Bean
    DateTimeProvider auditDateTimeProvider(Clock auditClock) {
        return () -> Optional.<TemporalAccessor>of(
            Instant.now(auditClock)
        );
    }
}
```

Key parts:

- `Clock.systemUTC()` provides a UTC clock.
- `Instant.now(auditClock)` reads the instant from the injected clock.
- `DateTimeProvider` wraps that value for the auditing infrastructure.
- `dateTimeProviderRef` explicitly specifies the provider bean used when JDBC auditing is enabled.

The bean name in `dateTimeProviderRef` must match the provider bean. If multiple `Clock` beans exist, use `@Qualifier` or mark the intended bean with `@Primary` to avoid injecting the wrong time source.

`Clock.systemUTC()` does not mean every timestamp in the database is automatically stored or displayed in UTC. It only ensures the provider generates an instant in UTC. The database column type, driver, and session timezone must still be configured appropriately.

## 4. Customizing Auditing Behavior on Creation

Auditing attributes can be configured explicitly:

```java
@Configuration
@EnableJdbcAuditing(
    dateTimeProviderRef = "auditDateTimeProvider",
    modifyOnCreate = true,
    setDates = true
)
public class JdbcAuditingConfiguration {
    // Clock and DateTimeProvider beans are declared here
}
```

- `setDates = true` enables assigning annotated date fields.
- `modifyOnCreate = true` allows `@LastModifiedDate` to be assigned immediately on creation.
- If `modifyOnCreate = false` is set, the modified field is not populated merely due to the initial insert; it will be updated on a subsequent edit per auditing behavior.

Choose the convention based on business meaning. Many systems want both created and last-modified fields populated right after insert, so keeping the default is appropriate. Do not use `createdAt` to represent an import timestamp or user registration time if those two concepts differ; add a separate field when needed.
## 5. Combining Time with Actor Information

Auditing can record both timestamps and actors:

```java
@Table("purchase_order")
public record PurchaseOrder(
    @Id Long id,
    String status,
    @CreatedDate Instant createdAt,
    @LastModifiedDate Instant lastModifiedAt,
    @CreatedBy String createdBy,
    @LastModifiedBy String lastModifiedBy
) {
}
```

Declare `AuditorAware` to obtain the current actor:

```java
@Bean
AuditorAware<String> auditorAware(CurrentActorProvider actors) {
    return () -> actors.currentActorId();
}
```

Enable both providers:

```java
@Configuration
@EnableJdbcAuditing(
    dateTimeProviderRef = "auditDateTimeProvider",
    auditorAwareRef = "auditorAware"
)
public class JdbcAuditingConfiguration {
    // auditClock, auditDateTimeProvider, and auditorAware beans.
}
```

Prefer storing a stable actor identifier, such as a user ID or service account ID, rather than a mutable display name. For background operations without a logged-in user, explicitly define system actors such as `SYSTEM_IMPORT` or `BATCH_RECONCILIATION` according to application conventions.

If `AuditorAware` returns `Optional.empty()`, auditing has no actor to assign. If the actor column is `NOT NULL`, ensure every write flow has a valid actor or provide an explicit system value. Do not assign a fake user just to avoid null.

### Request Threads and Background Workers

In synchronous requests, the actor is typically read from the current security context. With `@Async`, schedulers, or message consumers, do not assume the security context automatically carries over to another thread. Pass the actor/context explicitly or configure an appropriate propagation mechanism.

A scheduled job does not necessarily have a specific user; the actor may be a service account. What matters is that the audit accurately reflects the source of the change so it can be explained later.

## 6. Choosing Temporal Data Types

Not all Java time types represent the same concept:

| Java Type | Representation | Best Suited For |
| --- | --- | --- |
| `Instant` | An absolute point on the timeline, UTC-based. | Audit timestamps, creation/update times, event times. |
| `OffsetDateTime` | Date and time with a UTC offset, e.g., +07:00. | When preserving the offset at capture time is required. |
| `ZonedDateTime` | Date and time with a timezone carrying rules, e.g., Asia/Ho_Chi_Minh. | Schedules/events needing zone ID and DST rules; usually requires storing the zone separately when persisting. |
| `LocalDateTime` | Wall-clock date and time without offset or zone. | Business local time when the zone is managed separately. |
| `LocalDate` | Calendar date without time or zone. | Birthdays, invoice dates, business dates. |

For `createdAt` and `lastModifiedAt`, `Instant` is usually the clearest choice because auditing needs to know exactly when an event occurred on a shared timeline.

`LocalDateTime` cannot identify a unique instant without a timezone. For example, `2026-11-13T09:00` could mean 09:00 in Ho Chi Minh City or 09:00 in Tokyo; those are two different absolute instants. Do not use `LocalDateTime` for distributed audit timestamps unless a fixed zone convention is enforced across all layers.

`OffsetDateTime` preserves an offset, but an offset is not a zone name. `+07:00` does not store historical or future rules for `Asia/Ho_Chi_Minh`. If business logic needs to know which zone was chosen, store the zone ID separately as a string.

### Do Not Mix Instants with Local Time

Example:

```java
Instant occurredAt = Instant.now(clock);

ZonedDateTime displayTime =
    occurredAt.atZone(ZoneId.of("Asia/Ho_Chi_Minh"));
```

`occurredAt` is the system-wide point in time. `displayTime` is how that point in time is rendered on a local wall clock. Both variables represent the same event, not two independent timestamps.

## 7. UTC for Storage and Timezones for Display

An operationally clean convention for multi-region systems is:

1. Obtain instants from a UTC `Clock`.
2. Record audits as instants.
3. Transfer timestamps over APIs in ISO-8601 format with `Z` or an explicit offset.
4. Convert to the user's timezone only in the presentation layer.
5. When filtering by a local calendar date, convert the day boundaries into instants before binding to SQL.

Example API response:

```json
{
  "createdAt": "2026-11-13T02:00:00Z"
}
```

A UI in Ho Chi Minh City can display the same instant as 09:00 on 13/11/2026. A UI in another region will display it in its corresponding timezone. Never write UI-formatted values back into an audit column.

Use an explicit `ZoneId` instead of relying on the host's default timezone:

```java
ZoneId userZone = ZoneId.of("Asia/Ho_Chi_Minh");

ZonedDateTime localDisplay =
    createdAt.atZone(userZone);

String formatted =
    DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm")
        .withZone(userZone)
        .format(createdAt);
```

Formatting is strictly for display. For APIs and cross-system logs, prefer ISO-8601 with an offset so instant information is never lost.
## 8. Database Timestamp Types and JDBC Drivers

The SQL column type determines how the database stores and interprets time. Identical type names across DBMSs do not guarantee identical semantics.

| Database | Common Type | Semantics to Remember |
| --- | --- | --- |
| PostgreSQL | `timestamp with time zone` / `timestamptz` | Stores a normalized instant; when displayed, the value is rendered in the session's timezone. Does not preserve the original zone name. |
| PostgreSQL | `timestamp without time zone` | Stores date/time components without offset or timezone. |
| MySQL | `TIMESTAMP` | The database converts between the session timezone and UTC on write/read; session timezone has an effect. |
| MySQL | `DATETIME` | Stores literal date/time values without carrying a timezone. |
| SQL Server | `datetimeoffset` | Stores date/time along with an offset; does not store a zone name like `Asia/Ho_Chi_Minh`. |
| SQL Server | `datetime2` | Stores date/time without an offset. |

With PostgreSQL, `timestamptz` is suitable for audit instants. When queried, PostgreSQL may render the same instant with different offsets depending on session timezone; that does not mean the event changed.

With MySQL, configure the session timezone consistently and understand the difference between `TIMESTAMP` and `DATETIME`. If using `DATETIME` to store UTC, the application must enforce the convention that the date/time components in that column are always interpreted as UTC; the database cannot infer this from the column type.

With SQL Server, `datetimeoffset` retains the offset at save time but does not retain the zone ID or regional DST rules. If you need to reconstruct the selected zone, store the zone ID separately.

### Testing Actual Mapping

Spring Data JDBC, Spring Framework, and the JDBC driver all participate in converting Java time types to SQL types. Verify the mapping for your exact version and driver with integration tests against the target database. Do not assume that because a Java property is `Instant`, every database will automatically pick the same column semantics.

The convention must align across all three layers:

- Java property type.
- SQL column type.
- JDBC driver and session timezone behavior.

If a custom converter is needed, register it in Spring Data JDBC configuration and test round-trip behavior: write an instant with fractional nanoseconds, read it back, and compare according to the column's actual precision.

## 9. Avoid Mixing Application Time and Database Time

There are two common sources of time:

- Application clock: `DateTimeProvider` using a JVM `Clock`.
- Database clock: `CURRENT_TIMESTAMP` in defaults, triggers, or custom SQL.

The two sources can diverge due to server clocks, NTP, timezone configuration, transaction timestamp semantics, and precision. For example, an aggregate might have `createdAt` assigned by auditing using the app clock, while `lastModifiedAt` is updated by a trigger using the DB clock. Comparing them could show timestamps that do not advance as expected.

Pick one authoritative source per group of fields:

- If auditing is managed by the application, use `DateTimeProvider` consistently and avoid overwriting the same fields with `CURRENT_TIMESTAMP` in SQL.
- If the database is the canonical time source, use defaults/triggers or SQL updates using the DB clock consistently; do not simultaneously expect `@CreatedDate` to be the sole source for those fields.
- Synchronize host clocks using NTP or infrastructure time services. UTC alone does not fix clock skew between two machines.

`DateTimeProvider` is not a database clock provider. It only supplies time values to application-side auditing callbacks. If direct SQL writes timestamps itself, establish a consistent convention for that write path.

## 10. JVM, Connection, and Database Session Timezones

An application may run on a host whose default timezone differs from the database session timezone. If code calls `LocalDateTime.now()` or `ZoneId.systemDefault()`, results depend on the runtime environment.

To reduce discrepancies:

1. Use `Clock.systemUTC()` as the source of audit instants.
2. Configure database/connection session timezones to UTC where appropriate.
3. Never rely on the JVM default timezone as an implicit business rule.
4. Verify connection pool timezone state when borrowing and returning connections.
5. Log timestamps in ISO-8601 format with an offset or `Z`.
6. Run tests under a non-UTC JVM timezone to uncover hidden dependencies.

How session timezone is configured depends on the database and driver. For instance, PostgreSQL can set timezone at the database, role, or session level; MySQL has its own session timezone setting. Do not use a single `SET TIME ZONE` command across all DBMSs. If a connection pool executes session initialization statements, ensure state is reset/controlled so one request does not leak timezone state to the next.

## 11. Converting Local Dates to Time Intervals for Queries

A request like "fetch all orders created on November 13 in Ho Chi Minh City" is a query by local calendar day, not a fixed 24-hour UTC window.

Convert the date and zone into two instants:

```java
LocalDate requestedDate = LocalDate.of(2026, 11, 13);
ZoneId zone = ZoneId.of("Asia/Ho_Chi_Minh");

Instant fromInclusive =
    requestedDate.atStartOfDay(zone).toInstant();

Instant toExclusive =
    requestedDate.plusDays(1).atStartOfDay(zone).toInstant();
```

Then bind both instants into SQL as a half-open interval:

```sql
SELECT id, created_at
FROM purchase_order
WHERE created_at >= :fromInclusive
  AND created_at < :toExclusive
ORDER BY created_at, id;
```

Using `[from, to)` avoids constructing "23:59:59.999999" at the end of the day and prevents precision errors. The next local calendar day is the exclusive upper bound.

### Why Not Add a Fixed 24 Hours?

In regions with daylight saving time, a local day can be 23 or 25 hours long when clocks shift. Therefore, compute the start of the next day from `LocalDate.plusDays(1)` in the same `ZoneId`, rather than taking the start-of-day instant and adding `Duration.ofHours(24)`.

Vietnam does not currently observe DST, but applications serving multiple countries still need to handle regional timezone rules. Java's timezone database is updated with JDK releases; systems sensitive to regional schedules must keep the runtime timezone database up to date.

### Avoid Casting Timestamp Columns to Date Unnecessarily

Expressions like `DATE(created_at) = :date` can:

- Use a session timezone that does not match the user's timezone.
- Prevent standard index usage on the column due to applying a function.
- Introduce dialect differences across databases.

Computing the two boundary instants in the application and binding them to a range condition is usually clearer and more index-friendly.
## 12. When Should Local Time and Zone ID Be Kept?

Not all temporal data should be converted to `Instant`. An audit timestamp describes an event that already happened on the timeline. In contrast, an appointment may express the intent "meet at 09:00 in the customer's local time".

Appointment example:

```java
public record Appointment(
    LocalDateTime localStart,
    String zoneId
) {
    public ZonedDateTime startInZone() {
        return localStart.atZone(ZoneId.of(zoneId));
    }

    public Instant startInstant() {
        return startInZone().toInstant();
    }
}
```

Here, both the local date-time and zone ID are preserved because the business rule is "09:00 in this zone", even if timezone rules change in the future. For an appointment finalized to a specific execution instant, you can also store the resolved instant to know the exact execution time.

### Gaps and Overlapping Hours Caused by DST

When converting a `LocalDateTime` into a zone with DST, two special cases arise:

- Non-existent hour (gap): the clock jumps forward over an hour at DST start.
- Repeated hour (overlap): the clock falls back, so one local time corresponds to two instants.

You can check this with `ZoneRules`:

```java
LocalDateTime local = LocalDateTime.of(2026, 11, 1, 1, 30);
ZoneId zone = ZoneId.of("America/New_York");

List<ZoneOffset> validOffsets =
    zone.getRules().getValidOffsets(local);

if (validOffsets.isEmpty()) {
    throw new IllegalArgumentException("Local time is in a DST gap");
}

if (validOffsets.size() > 1) {
    // Repeated hour: business logic must choose the specific offset/occurrence.
}
```

For user-entered times, define a policy for repeated or non-existent times. Do not let important decisions depend on an API's default adjustment behavior during a DST transition.

## 13. Timestamp Precision and Round-Trip Behavior

Java's `Instant` has nanosecond precision, whereas database columns may store fewer fractional digits. For example, PostgreSQL timestamps typically have microsecond precision; MySQL can declare `DATETIME(6)` or `TIMESTAMP(6)`; SQL Server `datetime2(7)` supports another precision.

If the clock produces `2026-11-13T02:00:00.123456789Z` but the database only stores microseconds, the value read back may be `2026-11-13T02:00:00.123457Z` or be rounded/truncated by the driver and database. Do not write tests requiring exact nanosecond equality if the column does not support that precision.

You should:

- Choose precision matching requirements and database capabilities.
- Verify round-trip behavior with the production JDBC driver.
- Compare values at the precision guaranteed by the database.
- Do not use timestamps as a unique key when two operations can share the same timestamp; use a separate ID/version.
- Do not truncate precision inconsistently across layers without an agreed rounding rule.

Audit timestamps rarely need nanoseconds. Milliseconds or microseconds are usually sufficient, though the decision depends on traceability needs and DBMS capabilities.

## 14. Testing DateTimeProvider with a Fixed Clock

`Clock.fixed(...)` keeps tests independent of execution time. You can expose a test clock as a `@Primary` bean so the production provider automatically injects it:

```java
@TestConfiguration
static class FixedAuditClockConfiguration {

    @Bean
    @Primary
    Clock fixedAuditClock() {
        return Clock.fixed(
            Instant.parse("2026-11-13T02:00:00Z"),
            ZoneOffset.UTC
        );
    }
}
```

Illustrative integration test:

```java
@Test
void auditingUsesConfiguredClock() {
    PurchaseOrder saved = repository.save(
        new PurchaseOrder(null, "CREATED", new BigDecimal("125.00"),
            null, null)
    );

    Instant expected = Instant.parse("2026-11-13T02:00:00Z");

    assertThat(saved.createdAt()).isEqualTo(expected);
    assertThat(saved.lastModifiedAt()).isEqualTo(expected);
}
```

The test must load the JDBC auditing configuration and test clock into the application context. Constructor signatures, repositories, and fixtures must match your real domain.

`Clock.fixed` always returns the same instant. To test that `@LastModifiedDate` changes after an update, use a controllable test clock or initialize contexts with different fixed timestamps. Do not use `Thread.sleep(...)` to wait for the clock to advance; tests become slow and flaky.

### Testing Timezone Conversions

You can test displaying the same instant across different zones:

```java
Instant instant = Instant.parse("2026-11-13T02:00:00Z");

ZonedDateTime hcm =
    instant.atZone(ZoneId.of("Asia/Ho_Chi_Minh"));

ZonedDateTime tokyo =
    instant.atZone(ZoneId.of("Asia/Tokyo"));

assertThat(hcm.toInstant()).isEqualTo(instant);
assertThat(tokyo.toInstant()).isEqualTo(instant);
assertThat(hcm.getHour()).isEqualTo(9);
assertThat(tokyo.getHour()).isEqualTo(11);
```

The two representations have different local hours yet share the exact same instant. This test verifies display conventions without relying on the JVM's default timezone.

## 15. Schema Migrations and Legacy Data

When adding auditing to an existing table, decide how to handle existing rows:

- Add nullable `created_at`/`last_modified_at` first, backfill using migration time or reliable historical data, and only then alter to `NOT NULL`.
- If the true creation time is unknown, do not assign a fabricated date and treat it as accurate history. You can store `legacy_imported_at` or flag the data source.
- Align timezone and column types before deploying code that writes new Java types.
- Verify precision and converters against a real database.
- On large tables, backfill in batches to limit locks and write load.

Two-phase migration example:

```sql
ALTER TABLE purchase_order
    ADD COLUMN created_at TIMESTAMP WITH TIME ZONE NULL,
    ADD COLUMN last_modified_at TIMESTAMP WITH TIME ZONE NULL;
```

Only after backfilling and confirming no nulls remain should you apply `NOT NULL` constraints in a subsequent migration. The SQL type in the example is PostgreSQL; substitute the equivalent type for your database.

## 16. Common Mistakes

| Mistake | Consequence | Remedy |
| --- | --- | --- |
| Using `LocalDateTime.now()` for system-wide auditing | Results depend on JVM timezone and fail to identify an instant without a zone. | Use `Instant` from a UTC clock. |
| Configuring `Clock.systemUTC()` and assuming the DB is in UTC | Sessions/column mappings may still convert or display in another timezone. | Check column type, driver, and session timezone. |
| Mixing app auditing clock with SQL `CURRENT_TIMESTAMP` on the same field | Timestamps can diverge due to clock skew or transaction semantics. | Choose one authoritative time source. |
| Storing `OffsetDateTime` expecting to preserve zone ID | Offsets do not contain timezone rules. | Store zone ID separately if business logic requires it. |
| Using `LocalDateTime` for international appointments without saving zone | Cannot interpret the correct instant across regions. | Store local time alongside `ZoneId` or a resolved instant. |
| Adding 24 hours to cover a full local day | Incorrect on 23- or 25-hour DST transition days. | Compute start of next day in the `ZoneId`. |
| Using `Thread.sleep` in timestamp tests | Tests are slow and flaky. | Inject `Clock.fixed` or a controllable clock. |
| Comparing nanoseconds after a database round-trip | Tests fail due to lower column/driver precision. | Compare at the supported precision. |
| Testing only on developer machines | Production may use a different timezone/session/driver. | Run integration tests on the same database type and production-like settings. |

## 17. Workflow for Designing Time Conventions

Before enabling auditing, align on:

1. Which fields are audit instants, and which are local business dates/times?
2. Do audit properties use `Instant` or another type? Why?
3. Does `DateTimeProvider` read from the app clock or database clock?
4. Which `Clock` bean is the canonical source? Is `Clock.systemUTC()` used?
5. Does `@EnableJdbcAuditing` reference the right provider?
6. Do the database column type and JDBC driver round-trip instants properly?
7. How are session timezone and connection pools managed?
8. Do APIs transfer timestamps with explicit `Z` or offsets?
9. How are local calendar dates converted into instant ranges?
10. Are DST gaps/overlaps handled for appointments?
11. Does database precision meet requirements?
12. Are tests using fixed clocks and the corresponding real database?

## 18. Self-Check Questions

- What value does `DateTimeProvider` supply to the auditing infrastructure?
- Why should `Clock` be injected instead of scattering `Instant.now()` calls?
- How do `@CreatedDate` and `@LastModifiedDate` differ in meaning?
- How does `modifyOnCreate` affect modified fields on insert?
- Why is `Instant` better suited for audit timestamps than `LocalDateTime`?
- Does `OffsetDateTime` store timezone region names like `Asia/Ho_Chi_Minh`?
- Does `Clock.systemUTC()` automatically configure the database session timezone?
- Does PostgreSQL `timestamptz` preserve the original zone ID?
- Why should you avoid mixing the app clock with SQL `CURRENT_TIMESTAMP` for the same field?
- How do you query all records for a local calendar day accurately across DST transitions?
- Why is it necessary to verify precision after a JDBC round-trip?
- How do you test auditing without calling `Thread.sleep`?

A clear time convention begins by distinguishing **the instant of an event** from **its representation on a local clock**. Use a `Clock`-backed `DateTimeProvider` to control the audit time source, prefer `Instant` for creation/modification timestamps, align column types and session timezones, and convert to a `ZoneId` in the presentation layer or when interpreting business dates. Test with fixed clocks and round-trips on a real database to eliminate runtime environment dependencies.
