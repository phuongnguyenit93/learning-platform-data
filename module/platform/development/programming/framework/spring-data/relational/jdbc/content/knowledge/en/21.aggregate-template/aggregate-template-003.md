# Distinguishing save, Explicit insert, and Explicit update

In **Spring Data Relational JDBC**, an aggregate root can be persisted using a repository or `JdbcAggregateTemplate`. The most common APIs are `save`, `insert`, and `update`. All three persist the aggregate—including its owned child entities—but differ in how they decide which SQL operation to execute.

- **`save`** determines whether the aggregate is new or existing, then chooses insert or update.
- **`insert`** requests a create operation without checking the entity's newness state.
- **`update`** requests an update operation on an existing aggregate without checking the entity's newness state.

Repositories normally expose `save`. When you need to state insert or update intent explicitly, Spring Data JDBC provides `JdbcAggregateTemplate` with all three methods. Picking the right API avoids duplicate-key inserts, accidental updates on new aggregates, or incorrect reliance on how Spring detects IDs.

## 1. Three Aggregate-Level Operations

Suppose an application manages orders:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── status
  └── lines (owned child collection)
        ├── OrderLine
        └── OrderLine
```

A Java model used throughout this lesson:

```java
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_no")
        List<OrderLine> lines
) {
    public static PurchaseOrder draft(String orderNumber) {
        return new PurchaseOrder(
                null, null, orderNumber, "DRAFT", List.of());
    }

    public PurchaseOrder withStatus(String newStatus) {
        return new PurchaseOrder(
                id, version, orderNumber, newStatus, lines);
    }

    public PurchaseOrder withLines(List<OrderLine> newLines) {
        return new PurchaseOrder(
                id, version, orderNumber, status, newLines);
    }
}

public record OrderLine(String sku, int quantity) {}
```

Corresponding PostgreSQL schema:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_line (
    purchase_order_id BIGINT NOT NULL
        REFERENCES purchase_order(id),
    line_no INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (purchase_order_id, line_no)
);
```

`PurchaseOrder` is the aggregate root; `OrderLine` instances are child entities belonging to the order's lifecycle. When saving the root, Spring Data JDBC persists all aggregate members according to the mapping.

| API | Meaning | How Operation Is Chosen |
| --- | --- | --- |
| `CrudRepository.save(aggregate)` | Persist aggregate | Spring Data checks whether the aggregate is new or existing |
| `JdbcAggregateTemplate.save(aggregate)` | Persist aggregate | Same semantics as repository `save` |
| `JdbcAggregateTemplate.insert(aggregate)` | Create new aggregate | Always takes the insert path |
| `JdbcAggregateTemplate.update(aggregate)` | Update existing aggregate | Always takes the update path |

Key point: `JdbcAggregateTemplate` methods do not merely insert or update a single root row. They process the aggregate together with its referenced members.

## 2. save: Automatically Deciding Between insert and update

`save` is the standard choice when the application wants to persist an aggregate without explicitly deciding beforehand whether it is new or already exists.

Example with a repository:

```java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

Creating a new order:

```java
PurchaseOrder order = new PurchaseOrder(
        null,
        null,
        "PO-2026-211",
        "DRAFT",
        List.of(new OrderLine("SKU-CHAIR", 2))
);

PurchaseOrder saved = repository.save(order);
```

If Spring Data determines the object is new, the repository inserts the root row and then inserts the child entities belonging to the aggregate. If the object is determined to already exist, the repository updates the existing aggregate.

`save` is not a SQL `MERGE` or `INSERT ... ON CONFLICT` statement. Choosing insert or update is based on the **object's newness state according to Spring Data's rules**, not an atomic database existence check before every save.

### 2.1. How Does Spring Data Determine Whether an Entity Is New?

Spring Data uses an entity state detection strategy. Common rules:

1. If the entity has an `@Version` property, Spring Data checks the version first. A `null` version (or `0` for primitive integer types) indicates a new entity; any other version value indicates an existing entity.
2. If there is no version property, Spring Data checks `@Id`. A `null` ID (or `0` for primitive types) is treated as new; a populated ID is treated as already existing.
3. If the entity implements `Persistable`, Spring Data uses the `isNew()` result provided by the entity to decide.

Detailed behavior depends on the ID type, version, and Spring Data version. When using assigned IDs, do not assume a non-null ID implies the row exists in the database if your application uses `@Version` or `Persistable` to control state.

Example:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_no")
        List<OrderLine> lines
) {}
```

For an entity with `@Version Long version`, a new instance typically has `version == null`. After insertion, Spring Data initializes the version; subsequent saves treat the instance as existing based on the version.

### 2.2. Why Must the Newness State Be Accurate?

Suppose the application creates a new entity with an assigned ID:

```java
PurchaseOrder order = new PurchaseOrder(
        9001L,
        null,
        "PO-9001",
        "DRAFT"
);

repository.save(order);
```

Without `@Version` and without overriding `Persistable.isNew()`, the populated ID can cause Spring Data to treat the entity as existing. Then `save` chooses update even though row `9001` does not exist yet. This is why an explicit `insert` API is valuable when the application assigns IDs before writing.

Conversely, if an existing entity is mistakenly marked as new, `save` may take the insert path and fail with a primary key or unique constraint error.

### 2.3. Using the Return Value from save

When IDs are database-generated, Spring Data receives that value after insertion. For immutable objects such as Java records, the framework can return an instance holding the new ID and version. Therefore, always keep the returned result:

```java
PurchaseOrder saved = repository.save(order);

Long generatedId = saved.id();
Long currentVersion = saved.version();
```

Do not assume every input object is mutated in place. Using the return value ensures code works properly with both mutable and immutable entities.

## 3. insert: Explicitly Creating a New Aggregate

`JdbcAggregateTemplate.insert(aggregate)` bypasses the new/existing entity check and goes straight down the insert path. This is the right choice when the application **knows for sure** the aggregate does not exist yet and wants to state creation intent explicitly.

`JdbcAggregateTemplate` is configured as a Spring bean when Spring Data JDBC is enabled. It can be injected into a service:

```java
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderWriter {

    private final JdbcAggregateTemplate template;

    public PurchaseOrderWriter(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional
    public PurchaseOrder create(PurchaseOrder order) {
        return template.insert(order);
    }
}
```

`insert` is suitable when:

- The application assigns the ID before inserting and the ID is known to be new.
- A data import has a clear workflow where every aggregate in the batch must be newly created.
- You want the API to make clear that a key collision is an error, not an update intent.
- You want to bypass ID/version/`Persistable`-based newness detection.

If the database already has a row violating the primary key or a unique constraint, `insert` fails according to the database constraint. `insert` does not fall back to an update when a duplicate is detected.

### 3.1. Insert Includes Child Entities

Suppose the aggregate has a `lines` collection. When inserting the root:

```text
template.insert(order)
        │
        ├── INSERT purchase_order
        │       └── obtain root ID
        │
        └── INSERT order_line rows
                └── attach purchase_order_id
```

Illustrative PostgreSQL SQL:

```sql
INSERT INTO purchase_order (order_number, status, version)
VALUES ('PO-211', 'DRAFT', 0)
RETURNING id;

INSERT INTO order_line (purchase_order_id, line_no, sku, quantity)
VALUES (211, 0, 'SKU-CHAIR', 2);
```

This SQL illustrates the semantics, not an exact statement generated across every dialect. The ID-retrieval syntax, statement order, and version value are determined by Spring Data JDBC, the dialect, and the schema.

### 3.2. Insert with an Application-Assigned ID

If the ID is pre-assigned, you can use:

```java
PurchaseOrder order = new PurchaseOrder(
        9001L,
        null,
        "PO-9001",
        "DRAFT",
        List.of()
);

PurchaseOrder inserted = template.insert(order);
```

In this case, `insert` explicitly declares that ID `9001` belongs to a new aggregate. The database still checks the primary key and other constraints. If the ID already exists, the operation must be handled as a creation conflict.

## 4. update: Explicitly Updating an Existing Aggregate

`JdbcAggregateTemplate.update(aggregate)` skips newness detection and goes straight down the update path. Use it only when the application knows the aggregate root already exists.

Example:

```java
@Service
public class PurchaseOrderWriter {

    private final JdbcAggregateTemplate template;
    private final PurchaseOrderRepository repository;

    public PurchaseOrderWriter(
            JdbcAggregateTemplate template,
            PurchaseOrderRepository repository) {
        this.template = template;
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long id, String newStatus) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = new PurchaseOrder(
                current.id(),
                current.version(),
                current.orderNumber(),
                newStatus,
                current.lines()
        );

        return template.update(changed);
    }
}
```

In the example, the service loads the current aggregate first, preserves the ID/version and required members, and sends the complete state to `update`. For entities with domain methods, prefer calling the business method instead of constructing a new object manually as shown in the illustration.

`update` is suitable when:

- The aggregate root already exists and needs updating.
- An import or synchronization workflow has verified that incoming records are existing records.
- You want a missing aggregate or mismatched version to be treated as an error rather than falling back to insert.

Do not use `update` for a new aggregate. This method does not check newness to switch to insert. If the root does not exist, an update cannot create a root in place of an insert; the exact outcome follows the framework/database update and version-check semantics.

## 5. Updating an Aggregate Does Not Mean Running UPDATE on a Single Row

In Spring Data JDBC, updating is an operation that synchronizes the state of the **entire aggregate**. For an aggregate with referenced child entities, the typical update workflow consists of:

1. Updating the aggregate root row.
2. Deleting child entities currently stored inside the aggregate.
3. Re-inserting the child entities present in the submitted object.

Because Spring Data JDBC does not retain a persistence context to know the previous state of each child, it brings the database into the state represented by the current aggregate. Consequently, even when changing only the root's status, child rows may still be deleted and re-inserted.

Example:

```text
Before update:
PurchaseOrder #211
  status = DRAFT
  lines = [A, B]

Object passed to update:
PurchaseOrder #211
  status = CONFIRMED
  lines = [A, B]

After update:
PurchaseOrder #211
  status = CONFIRMED
  lines = [A, B]  (resynchronized to match the aggregate)
```

Do not design aggregate children as resources with IDs stably referenced by other systems if they can be replaced when saving the root. If an object has an independent lifecycle, consider splitting it into a separate aggregate and referencing it by ID/`AggregateReference`.

## 6. Comparing save, insert, and update

| Criterion | `save` | `insert` | `update` |
| --- | --- | --- | --- |
| Checks newness state? | Yes | No | No |
| When entity is new | Insert | Insert | Not appropriate |
| When entity exists | Update | Not appropriate; still takes insert path | Update |
| Must know state beforehand? | No, framework determines | Yes, must be certain it is new | Yes, must be certain it exists |
| Saves child entities in aggregate? | Yes | Yes | Yes |
| Switches to the other operation on constraint error? | No | No | No |
| Common API | Repository or template | Template | Template |

Summary rules of thumb:

- **Unsure of newness state and want Spring to decide:** use `save`.
- **Certain it is a new creation, even with an assigned ID:** use `insert`.
- **Certain it updates an existing aggregate:** use `update`.

`save` is not an atomic database upsert. If multiple processes check an ID concurrently and save, Java-side newness detection does not replace unique constraints, transactions, and concurrency strategies.

## 7. save, insert, and update with @Version

Spring Data JDBC supports optimistic locking via an `@Version` property on the aggregate root:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status
) {}
```

When updating a versioned aggregate, Spring Data checks whether the version in the database matches the version carried by the object. If another transaction updated it first, the current operation fails with `OptimisticLockingFailureException` instead of silently overwriting.

Illustrative SQL:

```sql
UPDATE purchase_order
SET status = ?, version = version + 1
WHERE id = ? AND version = ?;
```

If no row matches the ID/version condition, the framework detects an optimistic locking conflict. The actual SQL may vary by dialect and aggregate structure.

For `insert`, the version is initialized according to Spring Data rules. For `update`, the version is checked and incremented. Use the value returned from `save`/`insert`/`update` to obtain the instance with the new version, especially for immutable entities.

If an entity lacks `@Version`, the application has no automatic optimistic locking for the aggregate under this mechanism. An explicit `update` does not create concurrency protection on its own just because the method name states update intent.

## 8. Using save or Explicit insert/update in Services?

Example service using repository `save` for typical flows:

```java
@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder create(String orderNumber) {
        PurchaseOrder newOrder = PurchaseOrder.draft(orderNumber);
        return repository.save(newOrder);
    }

    @Transactional
    public PurchaseOrder confirm(Long id) {
        PurchaseOrder order = repository.findById(id)
                .orElseThrow();
        order.confirm();
        return repository.save(order);
    }
}
```

This is simple and appropriate when new-state detection accurately reflects the entity's state. When a use case needs to force creation or update, use the template:

```java
@Service
public class ExplicitPurchaseOrderService {

    private final JdbcAggregateTemplate template;
    private final PurchaseOrderRepository repository;

    public ExplicitPurchaseOrderService(
            JdbcAggregateTemplate template,
            PurchaseOrderRepository repository) {
        this.template = template;
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder insertNew(PurchaseOrder newOrder) {
        return template.insert(newOrder);
    }

    @Transactional
    public PurchaseOrder updateExisting(Long id, String status) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = current.withStatus(status);
        return template.update(changed);
    }
}
```

`draft` and `withStatus` in the example are illustrative factory/domain methods on the application class. Replace them with your entity's actual API. What matters is that the service only calls `insert` when the data is definitely new, and only calls `update` when the aggregate is confirmed to exist.

## 9. Transactions and Errors When Choosing the Wrong Operation

Persisting an aggregate can involve multiple SQL statements: inserting/updating the root, deleting old children, inserting new children, and updating related members. When business logic requires these steps to succeed or fail together, place the transaction boundary on the service:

```java
@Transactional
public PurchaseOrder replaceOrderLines(
        Long orderId,
        List<OrderLine> newLines) {

    PurchaseOrder current = repository.findById(orderId)
            .orElseThrow();

    PurchaseOrder changed = current.withLines(newLines);
    return template.update(changed);
}
```

A transaction ensures statements within the same transaction commit or roll back together. It does not replace newness checks, primary keys, versions, or domain validation.

| Error / Scenario | Cause | Resolution |
| --- | --- | --- |
| Duplicate key on `insert` | ID or unique value already exists | Check ID source and constraints; do not blindly switch to update |
| `update` does not apply as expected | Aggregate does not exist yet or object carries wrong ID | Check existence and load root before updating |
| Repository `save` chooses update for new object with assigned ID | Default new-state detection treats non-null ID as existing (when no version/`Persistable` override) | Use template `insert` or configure `Persistable.isNew()` properly |
| Repository `save` chooses insert for existing object | Version/ID/`isNew()` reports incorrect newness state | Fix new-state detection strategy |
| Optimistic locking failure | Object version is stale | Reload, handle conflict, and reapply business changes |
| Children lost after `update` | Submitted object lacks children to retain or collection is empty/null | Load full aggregate and modify only the intended children |
| Partial aggregate written on failure | Multiple statements not enclosed in an appropriate transaction | Place `@Transactional` on the service and use the proper transaction manager |

In particular, never construct an aggregate object containing only an ID and a couple of fields and pass it to `update` when other properties were never loaded or restored. With Spring Data JDBC, the submitted aggregate state serves as the source of truth for synchronizing aggregate members.

## 10. save Is Not Equivalent to upsert

In SQL, **upsert** typically means a single database statement that inserts if the key does not exist or updates if it does. Repository `save` does not necessarily carry this semantics:

- `save` relies on the newness state Spring Data determines from the object.
- `save` may choose `insert` even if the database already has the same ID when the object is marked new; constraints will then fail.
- `save` may choose `update` for an object with an ID even when no row actually exists.

Some versions of `JdbcAggregateTemplate` offer an `upsert` API backed by database native upsert. This is a distinct API requiring an assigned ID and dialect support; current documentation also notes that upsert does not yet support optimistic locking. Check your Spring Data Relational version and project dialect before using it. Do not replace `save` with `upsert` just because the names sound similar.

## 11. Batch Variants

`JdbcAggregateTemplate` provides methods that accept an `Iterable`:

| Method | Meaning |
| --- | --- |
| `saveAll(aggregates)` | Saves multiple aggregates, detecting newness per instance |
| `insertAll(aggregates)` | Inserts multiple aggregates known to be new |
| `updateAll(aggregates)` | Updates multiple aggregates known to exist |

Example:

```java
List<PurchaseOrder> inserted =
        template.insertAll(newOrders);

List<PurchaseOrder> updated =
        template.updateAll(existingOrders);
```

These methods do not alter the rules for choosing operations: `insertAll` does not turn into update on a duplicate ID; `updateAll` does not turn into insert when an aggregate does not exist. Classify input data before calling them.

Do not assume the `All` suffix guarantees a single SQL statement or that every element is written in a single JDBC batch across all versions and dialects. Inspect the SQL and batch behavior when performance is critical.

## 12. API Selection Workflow

When writing a use case that persists an aggregate, decide in order:

1. **Is the aggregate known to be new?** If unsure, use `save` and make sure ID/version/`Persistable` accurately reflects state.
2. **Is the aggregate known to exist?** When an explicit update is desired, load the root and use `update`; do not submit partial objects.
3. **Does the application assign IDs for new aggregates?** Use `insert` once the ID is confirmed new; enforce unique constraints.
4. **Are there children/collections?** Submit the complete aggregate state and remember that `update` may resynchronize child rows.
5. **Are concurrent updates possible?** Consider `@Version` and conflict handling.
6. **Must multiple operations be atomic?** Place `@Transactional` on the service.
7. **Need database-level upsert?** Verify API/dialect support and concurrency/optimistic locking limitations.

## 13. Hands-On Exercises

**Exercise 1 — Repository save.** Create an aggregate with an auto-generated ID and call `repository.save` for the first time. Verify the generated ID and that the subsequent `save` takes the update path.

**Exercise 2 — Pre-assigned ID.** Create a new aggregate with an application-assigned ID. Observe how `save` detects state without `@Version`; then try `template.insert` and explain why explicit insert fits.

**Exercise 3 — Duplicate insert.** Insert two aggregates with the same ID. Verify the database reports a constraint error and `insert` does not switch to update.

**Exercise 4 — Existing update.** Load an aggregate using a repository, change its status, and call `template.update`. Test with a nonexistent ID to observe the behavior of your current version and dialect.

**Exercise 5 — Child collection.** Create an aggregate with two children, change the root while keeping the children, and call `update`. Observe the root/child SQL and confirm child rows are synchronized to the aggregate state.

**Exercise 6 — Optimistic locking.** Add `@Version`. Have two transactions read the same version, update in the first transaction, and then attempt to update the stale object in the second. Observe `OptimisticLockingFailureException`.

**Exercise 7 — Batch APIs.** Compare `saveAll`, `insertAll`, and `updateAll` on a clearly classified dataset. Inspect constraints and SQL logs.
