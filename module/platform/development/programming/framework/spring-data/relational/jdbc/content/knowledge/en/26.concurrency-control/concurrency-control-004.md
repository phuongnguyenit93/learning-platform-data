# Handling OptimisticLockingFailureException and retry policies

In Spring Data JDBC, multiple requests can read the same aggregate concurrently and then modify it. If two requests both use stale state, the later write risks overwriting the earlier write's changes. **Optimistic locking** detects this situation using a `@Version` field.

When Spring Data JDBC detects that the version in the database no longer matches the version the application read, the save or delete operation fails and throws `OptimisticLockingFailureException`. This signals that the aggregate was modified by another operation; the application must decide whether it can safely retry or must return a conflict to the caller.

A sound retry policy should ensure:

- Retry only recoverable conflict errors.
- Each retry starts a new transaction.
- Reload the latest aggregate and reapply the business intent.
- Bound the number of attempts, with backoff and jitter.
- Re-evaluate business invariants after reading the new state.
- Do not unintentionally repeat side effects outside the database.

This lesson explains how `@Version` works, how to recognize and handle `OptimisticLockingFailureException`, how to implement retries using `TransactionTemplate` or Spring Retry, and when to return a conflict error instead of automatically retrying.

## 1. Why is optimistic locking necessary?

Suppose a product has 10 units in stock. Two requests both want to reserve 7 units:

1. Request A reads quantity 10.
2. Request B also reads quantity 10.
3. A computes remaining quantity 3 and saves.
4. B, based on stale data, also computes remaining quantity 3 and saves.

Without a mechanism to detect concurrent updates, both operations can succeed. The system records only a single decrement from 10 to 3, even though it confirmed reservations totaling 14 units. This is a *lost update*.

Optimistic locking assumes conflicts are infrequent, so it does not lock rows while the application processes them. Instead, it checks at write time whether the data has changed since it was read.

~~~text
Request A                         Request B
---------                         ---------
Read quantity = 10                Read quantity = 10
Read version = 5                  Read version = 5
Compute quantity = 3              Compute quantity = 3
UPDATE with version = 5
Succeeds, version becomes 6
                                  UPDATE with version = 5
                                  No rows match
                                  OptimisticLockingFailureException
~~~

Request B learns that the state it relied on is stale. It can reload the aggregate and determine whether it can still proceed.

## 2. Enabling optimistic locking with @Version

Spring Data JDBC supports optimistic locking through a property annotated with `@Version` on the aggregate root.

Example:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("inventory_items")
public record InventoryItem(
        @Id Long id,
        String sku,
        int availableQuantity,
        @Version Long version
) {
    public InventoryItem reserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "Quantity must be positive"
            );
        }

        if (availableQuantity < quantity) {
            throw new InsufficientStockException(sku);
        }

        return new InventoryItem(
                id,
                sku,
                availableQuantity - quantity,
                version
        );
    }
}
~~~

Corresponding schema:

~~~sql
CREATE TABLE inventory_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL UNIQUE,
    available_quantity INTEGER NOT NULL
        CHECK (available_quantity >= 0),
    version BIGINT NOT NULL
);
~~~

When creating a new aggregate, Spring Data JDBC initializes the version using the framework's mechanism. When updating an existing aggregate, the framework uses the read version to verify the record is still at that version, then increments the version after a successful write.

Do not manually increment `version` inside ordinary domain methods. The version is concurrency metadata managed by the persistence layer.

### 2.1. What SQL is conceptually executed?

Suppose the aggregate currently has `id = 42` and `version = 5`. When saving, the statement conceptually corresponds to:

~~~sql
UPDATE inventory_items
SET available_quantity = 3,
    version = 6
WHERE id = 42
  AND version = 5;
~~~

If one row is updated, the operation succeeds. If no rows match the condition, it may be because:

- Another transaction updated the aggregate and incremented the version.
- The aggregate was deleted.
- The ID no longer exists.
- The persistence state is stale compared to the database.

In the case of a version mismatch, Spring Data JDBC reports an optimistic locking error rather than silently overwriting newer data.

The SQL above only illustrates the principle of checking `id` and `version`; the exact SQL is generated by Spring Data JDBC and the dialect.

### 2.2. What if @Version is absent?

If an aggregate has no `@Version` property, Spring Data JDBC cannot use this optimistic locking mechanism for that aggregate. Write operations may overwrite another request's changes depending on isolation and how updates are issued.

If an aggregate experiences concurrent updates from multiple requests, consider versioning and enforcing critical invariants in the database with `CHECK`, `UNIQUE`, foreign keys, or an appropriate locking mechanism.

### 2.3. Optimistic locking applies to updates and deletes

For a versioned aggregate, delete operations also verify that the aggregate's version is still the one the caller read. If the aggregate was modified after the read, deleting with stale state can fail with an optimistic locking exception.

This prevents a request from deleting an aggregate based on stale state without knowing another request just updated it.

## 3. What is OptimisticLockingFailureException?

`OptimisticLockingFailureException` belongs to Spring's DAO exception hierarchy under `DataAccessException`. It is a runtime exception indicating that a write operation could not complete because an optimistic lock failed.

Import:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
~~~

You may encounter this exception when:

- Saving a versioned aggregate that another transaction has updated.
- Deleting a versioned aggregate based on a stale version.
- Two requests edit the same aggregate concurrently and the later request uses a version that is no longer current.

Example:

~~~java
@Transactional
public InventoryItem reserve(
        String sku,
        int quantity
) {
    InventoryItem item = repository.findBySku(sku)
            .orElseThrow();

    InventoryItem changed = item.reserve(quantity);

    return repository.save(changed);
}
~~~

If another transaction updates `item` after the read but before the save finishes, the save operation can throw `OptimisticLockingFailureException`.

### 3.1. This is a concurrency error, not a validation error

Distinguish optimistic locking from other errors:

| Error type | Example | Should you retry automatically? |
| --- | --- | --- |
| Optimistic locking | Database version differs from read version | Possibly, if the use case can safely reload and reapply |
| Business validation | Requested quantity is less than or equal to 0 | No |
| Business rule | Insufficient stock after reloading | Do not retry blindly; return a business error |
| Unique constraint | SKU or email already exists | Usually no; handle the data conflict |
| Foreign key | References a nonexistent row | Usually no |
| Database connection error | Database temporarily unreachable | Use a dedicated policy for transient infrastructure failures |
| Deadlock/serialization failure | Database aborts transaction due to lock or isolation conflict | Can have a separate retry policy if the operation is safe |

Do not catch every `DataAccessException` and retry it. A constraint or validation error will not disappear just by running the same statement again.

## 4. How does a conflict happen?

Suppose two transactions both read inventory:

~~~text
Initial database state:
  sku = SKU-01
  available_quantity = 10
  version = 5
~~~

Timeline:

| Time | Transaction A | Transaction B |
| --- | --- | --- |
| T1 | Read quantity 10, version 5 | |
| T2 | | Read quantity 10, version 5 |
| T3 | Compute remaining 3 | Compute remaining 4 |
| T4 | Save with version 5 succeeds, version increments to 6 | |
| T5 | | Save with version 5 fails |
| T6 | | Receives `OptimisticLockingFailureException` |

After T4, the current state in the database is quantity 3, version 6. Transaction B is no longer allowed to write a result calculated from quantity 10.

If business rules allow retrying, B needs to:

1. End the failed transaction.
2. Open a new transaction.
3. Reload the aggregate, now seeing quantity 3 and version 6.
4. Reapply the command "reserve 6 units".
5. Re-check inventory.
6. Save if invariants still hold.

In this example, `reserve(6)` throws `InsufficientStockException` because only 3 remain. That is the right outcome after refreshing to the latest state.

## 5. Why not retry inside the failed transaction?

This is the most important principle of a retry policy.

When a persistence operation throws an exception inside a transaction, the transaction may already be marked rollback-only. Even if the code catches the exception and calls `save` again, that transaction is no longer a safe environment to continue.

Example to avoid:

~~~java
@Transactional
public InventoryItem reserveWithBadRetry(
        String sku,
        int quantity
) {
    InventoryItem item = repository.findBySku(sku)
            .orElseThrow();

    InventoryItem changed = item.reserve(quantity);

    try {
        return repository.save(changed);
    } catch (OptimisticLockingFailureException ex) {
        // Do not save the stale object again inside this transaction.
        return repository.save(changed);
    }
}
~~~

There are two problems:

- The `changed` object still contains the stale version.
- The transaction may already be marked rollback-only; subsequent operations cannot restore it to a committable state.

Even if you reload the aggregate inside the same method, the current transaction may already be rollback-only and unable to commit successfully.

**Retries must wrap the transaction, not sit inside the failed transaction.** Each attempt needs a fresh transaction, reads fresh state, and reapplies the command.

~~~text
Retry coordinator
   |
   +-- Attempt 1
   |      BEGIN transaction 1
   |      Load aggregate
   |      Apply command
   |      Save -> optimistic conflict
   |      ROLLBACK transaction 1
   |
   +-- Backoff
   |
   +-- Attempt 2
          BEGIN transaction 2
          Load fresh aggregate
          Re-apply command
          Save
          COMMIT or ROLLBACK
~~~

## 6. What should a retry policy contain?

A good retry policy should be clearly bounded.

### 6.1. Retry only the appropriate exception

Catch only `OptimisticLockingFailureException` for this policy. Do not catch `Exception` or all `DataAccessException` subclasses and retry every error.

If the system has retries for deadlocks or connection errors, define a separate policy because their causes, recoverability, and safety conditions differ.

### 6.2. Bound the number of attempts

Do not retry indefinitely. For example:

- Maximum 3 attempts total, including the initial attempt.
- If all 3 attempts conflict, return the error to the caller.
- Record metrics for retry counts and final failures.

Bounding ensures requests do not hold threads and resources indefinitely when an aggregate experiences high contention.

### 6.3. Backoff and jitter

If multiple requests conflict and retry immediately, they can collide again. This causes a retry storm or thundering herd.

Use increasing wait intervals:

| Next attempt | Example base delay |
| --- | ---: |
| After attempt 1 | 50 ms |
| After attempt 2 | 100 ms |
| After attempt 3 | Stop if max attempts reached |

**Jitter** adds a small random interval so requests do not all retry at the exact same instant.

Exponential backoff example:

\[
delay_n = \min(initialDelay \times multiplier^{n-1}, maxDelay)
\]

Jitter can be added or multiplied randomly according to your application's policy. Specific values should be tuned based on latency, throughput, and contention levels.

### 6.4. Reload data on every attempt

Do not reuse the stale aggregate:

~~~java
// Wrong retry semantics:
InventoryItem stale = repository.findBySku(sku).orElseThrow();

for (int attempt = 0; attempt < 3; attempt++) {
    try {
        return repository.save(stale.reserve(quantity));
    } catch (OptimisticLockingFailureException ex) {
        // stale is still the old object
    }
}
~~~

Reload on each attempt:

~~~java
for (int attempt = 0; attempt < maxAttempts; attempt++) {
    try {
        return transactionTemplate.execute(status -> {
            InventoryItem current =
                    repository.findBySku(sku).orElseThrow();

            InventoryItem changed = current.reserve(quantity);

            return repository.save(changed);
        });
    } catch (OptimisticLockingFailureException ex) {
        // Next attempt will reload the aggregate in a new transaction.
    }
}
~~~

The snippet above is safe only when each `execute` actually starts and ends its own transaction; the next section presents the complete configuration.

### 6.5. Revalidate business rules

After reading the fresh aggregate, domain rules must run again.

For example:

- Stock may have decreased.
- The order may have been confirmed or cancelled.
- The account may have been locked.
- Credit limits may have changed.
- The user may have lost permission to perform the action.

If the new state no longer allows the command, return a business error. Never bypass checks just to make a retry succeed.

## 7. Retrying with TransactionTemplate

A clear way to retry an entire operation is to use `TransactionTemplate` inside a non-transactional facade.

Each `execute(...)` call opens a transaction, runs the callback, and ends the transaction before returning or throwing an exception. The retry coordinator catches exceptions outside the callback; the next attempt reads data in a fresh transaction.

### 7.1. Configuring TransactionTemplate

Spring Boot typically provides a JDBC transaction manager. You can inject the corresponding transaction manager and create the template:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.support.TransactionTemplate;

@Configuration
public class TransactionConfiguration {

    @Bean
    TransactionTemplate transactionTemplate(
            PlatformTransactionManager transactionManager
    ) {
        return new TransactionTemplate(transactionManager);
    }
}
~~~

If the application has multiple transaction managers, inject the specific bean managing the DataSource used by your repositories, using `@Qualifier` if needed.

### 7.2. Retry coordinator

~~~java
import java.util.concurrent.ThreadLocalRandom;

import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionTemplate;

@Service
public class RetryingInventoryService {

    private static final int MAX_ATTEMPTS = 3;

    private final InventoryRepository repository;
    private final TransactionTemplate transactionTemplate;

    public RetryingInventoryService(
            InventoryRepository repository,
            TransactionTemplate transactionTemplate
    ) {
        this.repository = repository;
        this.transactionTemplate = transactionTemplate;
    }

    // This method has no outer @Transactional.
    public InventoryItem reserve(
            String sku,
            int quantity
    ) {
        for (int attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
            try {
                return transactionTemplate.execute(status -> {
                    InventoryItem current =
                            repository.findBySku(sku)
                                    .orElseThrow();

                    InventoryItem changed =
                            current.reserve(quantity);

                    return repository.save(changed);
                });
            } catch (OptimisticLockingFailureException ex) {
                if (attempt == MAX_ATTEMPTS) {
                    throw ex;
                }

                pauseBeforeRetry(attempt);
            }
        }

        throw new IllegalStateException("Unreachable retry state");
    }

    private void pauseBeforeRetry(int attempt) {
        long baseDelay = Math.min(
                50L * (1L << (attempt - 1)),
                500L
        );

        long jitter = ThreadLocalRandom.current()
                .nextLong(0, 50);

        try {
            Thread.sleep(baseDelay + jitter);
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(
                    "Interrupted while waiting to retry",
                    ex
            );
        }
    }
}
~~~

Key aspects of this example:

1. The `reserve` method coordinates retries and has no outer `@Transactional`.
2. Each attempt calls `transactionTemplate.execute(...)`.
3. The aggregate is reloaded inside each attempt's callback.
4. The command is applied to the fresh state.
5. If saving fails due to an optimistic lock, the callback exits with an exception and that transaction rolls back.
6. The exception is caught outside `execute`, after the transaction attempt has ended.
7. The next attempt opens a fresh transaction.
8. When attempts are exhausted, the exception is thrown to the caller.

`TransactionTemplate` defaults to `REQUIRED` propagation. Because the facade has no active transaction, each `execute` creates a new transaction. If this facade is called from inside an outer transaction, the template may join that outer transaction; in that case, attempts are no longer independent as intended. Keep the retry coordinator at a non-transactional boundary or design propagation/bean boundaries explicitly.

### 7.3. Do not retry every RuntimeException

In the example, only `OptimisticLockingFailureException` is caught. The following errors propagate immediately:

- `InsufficientStockException`.
- `IllegalArgumentException`.
- `DataIntegrityViolationException`.
- Mapping or programming errors.

This is intentional. When fresh data shows insufficient stock, trying a fourth time will not make inventory magically increase.

### 7.4. Backoff must not hold a transaction open

In the example, waiting occurs after `TransactionTemplate.execute` has failed and the transaction attempt has ended. Do not hold connections or row locks while sleeping to wait for a retry.

For high-throughput systems, consider a retry framework with backoff or appropriate scheduling mechanisms instead of blocking HTTP threads with `Thread.sleep`.

## 8. Retrying with Spring Retry

If the project already uses Spring Retry, you can place retry logic on a facade bean and transactions on a separate bean. Splitting beans ensures each retry invokes the transactional method through the Spring proxy.

Example facade:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;

@Service
public class PlaceOrderRetryFacade {

    private final TransactionalOrderService transactionalService;

    public PlaceOrderRetryFacade(
            TransactionalOrderService transactionalService
    ) {
        this.transactionalService = transactionalService;
    }

    @Retryable(
            retryFor = OptimisticLockingFailureException.class,
            maxAttempts = 3,
            backoff = @Backoff(
                    delay = 50,
                    multiplier = 2,
                    maxDelay = 500
            )
    )
    public PurchaseOrder placeOrder(PlaceOrderCommand command) {
        return transactionalService.placeOrderOnce(command);
    }
}
~~~

Bean executing a single attempt in a transaction:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TransactionalOrderService {

    private final InventoryRepository inventoryRepository;
    private final PurchaseOrderRepository orderRepository;

    public TransactionalOrderService(
            InventoryRepository inventoryRepository,
            PurchaseOrderRepository orderRepository
    ) {
        this.inventoryRepository = inventoryRepository;
        this.orderRepository = orderRepository;
    }

    @Transactional
    public PurchaseOrder placeOrderOnce(PlaceOrderCommand command) {
        InventoryItem current = inventoryRepository
                .findBySku(command.sku())
                .orElseThrow();

        InventoryItem changed = current.reserve(command.quantity());
        inventoryRepository.save(changed);

        return orderRepository.save(
                new PurchaseOrder(
                        null,
                        command.sku(),
                        command.quantity(),
                        "PLACED"
                )
        );
    }
}
~~~

Configure Spring Retry annotation support in the application:

~~~java
@Configuration
@EnableRetry
public class RetryConfiguration {
}
~~~

Spring Retry is a separate library; add the dependency matching your project version. `@Retryable` is not provided by Spring Data JDBC itself.

This organization makes sense because:

- The retry proxy wraps the facade.
- Each attempt calls the `TransactionalOrderService` bean through its transaction proxy.
- The transactional method starts a new transaction when no outer transaction exists.
- If the method throws an optimistic locking exception, the transaction rolls back before the exception reaches the retry interceptor.
- The retry interceptor invokes the transactional method again for the next attempt.

Avoid placing retry and transaction annotations on the same method without understanding interceptor/proxy ordering. If the transaction proxy wraps outside the retry interceptor, multiple attempts may execute within the same transaction. Separating the retry facade and transactional service keeps the boundary explicit.

## 9. Retrying an entire multi-repository use case

A use case may write through multiple repositories in the same transaction:

~~~java
@Transactional
public PurchaseOrder placeOrderOnce(PlaceOrderCommand command) {
    InventoryItem inventory = inventoryRepository
            .findBySku(command.sku())
            .orElseThrow();

    inventoryRepository.save(
            inventory.reserve(command.quantity())
    );

    PurchaseOrder order = createOrder(command);

    return orderRepository.save(order);
}
~~~

If saving inventory or saving the order hits an optimistic lock exception, the entire transaction must roll back. Never retry only the failed repository call while keeping changes made earlier in the failed transaction.

The retry coordinator must re-invoke the **entire use case**:

~~~text
Attempt 1 — Transaction 1
  Load inventory
  Reserve quantity
  Save inventory
  Save order -> optimistic conflict
  Rollback both inventory and order

Attempt 2 — Transaction 2
  Load fresh inventory
  Load any required related aggregates
  Revalidate command
  Reserve quantity
  Save inventory
  Save order
  Commit if all operations succeed
~~~

If the first transaction decremented inventory and then failed to save the order due to another aggregate's version, rollback must revert the inventory change too. The new attempt must reload every aggregate the use case depends on.

## 10. When should you retry vs. return a conflict?

Not every optimistic locking exception should be handled with automatic retries.

| Scenario | Appropriate policy |
| --- | --- |
| Background/internal task updating a counter or stock that can reload and re-check invariants | Bounded retry is possible |
| Two requests updating independent fields on an aggregate root sharing a version | Retry is possible if the command can be reapplied without losing the other intent |
| User editing a form based on stale data | Usually return a conflict so the user can review and resolve |
| Command based on an absolute client-supplied value, e.g. "set balance to 100" | Do not automatically reapply if it risks overwriting newer changes |
| Aggregate has been deleted | Usually return not found or conflict per API contract |
| After reloading, business rules are no longer valid | Return a business error; do not keep retrying |
| Persistent conflicts after maximum attempts | Return a conflict or retryable error to the caller layer |

### 10.1. Retry the command, do not replay a stale snapshot

A command expresses business intent:

~~~java
public record ReserveStockCommand(
        String sku,
        int quantity
) {
}
~~~

On each retry, the service reads the latest state and applies the `reserve(quantity)` command.

Do not resend the stale aggregate object or a snapshot constructed by the client from a previous read. The stale snapshot is the source of the conflict.

### 10.2. Reapplying a command may produce a different result

Suppose a user wants to reserve 4 units. The first read saw 10 in stock, but another request reserved 8. After retrying and reloading, only 2 remain.

When reapplying the command, the domain must report insufficient stock. Do not bypass validation to force a retry to succeed.

Similarly, if a user wants to transition an order from `DRAFT` to `CONFIRMED`, but another request moved it to `CANCELLED`, the retry must re-check the state transition. Never overwrite newer state with older state.

## 11. Idempotency and external side effects

Database operation retries can run the service body multiple times. Therefore, distinguish repeatable database operations from external side effects.

Unsafe example:

~~~java
public PurchaseOrder placeOrder(PlaceOrderCommand command) {
    paymentClient.charge(command.paymentToken());

    return transactionTemplate.execute(status -> {
        // Update inventory and create order
        return ...;
    });
}
~~~

If the database transaction fails due to an optimistic lock and the facade retries, the payment provider could be charged multiple times.

Do not execute non-rollbackable side effects outside the transaction and expect database retries to undo them.

Common options:

- Write an outbox event in the same transaction as database changes, then have a worker publish events after commit.
- Use an idempotency key when calling the payment provider or external APIs.
- Publish events after transaction commit using an appropriate mechanism.
- Design consumers to handle duplicate event deliveries safely.
- Keep the retried transaction restricted to rollbackable database operations.

Idempotency also matters at the API layer. If a client misses a response due to a timeout and resends the request, the server must recognize the same business request to avoid creating two orders. Optimistic locking does not by itself provide request idempotency.

## 12. Returning conflict errors to the API

When attempts are exhausted, do not mask the failure by returning fake success. You can map the error to HTTP `409 Conflict` when the API contract models state conflicts.

Example:

~~~java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OptimisticLockingFailureException.class)
    public ResponseEntity<ApiError> handleOptimisticLock(
            OptimisticLockingFailureException exception
    ) {
        ApiError body = new ApiError(
                "RESOURCE_MODIFIED",
                "The resource was modified by another request. "
                        + "Please reload and try again."
        );

        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(body);
    }
}
~~~

Error DTO:

~~~java
public record ApiError(
        String code,
        String message
) {
}
~~~

The message to the caller should explain that the data changed and the caller needs to reload. You do not necessarily need to expose version details or internal database metadata in the API.

If the service already retried automatically a few times and still failed, the response should still reflect the final conflict. Log/record metrics so operations teams know which aggregates experience high contention.

## 13. Monitoring and bounding retries

A retry policy should be observable:

- Total optimistic locking conflicts.
- Average attempts per use case.
- Request success rate after retry.
- Exhausted-attempt rate.
- Aggregates or business operations that conflict frequently.
- Wait time caused by backoff.
- Business error rate after reloading fresh state.

Do not log full sensitive aggregate payloads. Log the aggregate type, permitted internal IDs, attempt number, and correlation/request ID.

If an aggregate continuously experiences high contention, retries are not the only way to improve things. Consider:

- Can the aggregate be split or can fewer use cases update the same root?
- Can updates be batched into a single command?
- Is pessimistic locking needed for a specific critical section?
- Can a conditional atomic SQL update replace read-modify-write?
- Should a hot counter move to a different storage model?

Retry is a recovery mechanism when conflicts are rare, not a solution for continuous contention.

## 14. Testing optimistic locking

An integration test can create two copies of an aggregate with the same version:

1. Save an `InventoryItem`.
2. Read the same aggregate twice into `firstRead` and `secondRead`.
3. Update and save `firstRead`.
4. Attempt to save `secondRead` based on the stale version.
5. Verify that an optimistic locking exception is thrown.

Test skeleton example:

~~~java
@SpringBootTest
class InventoryOptimisticLockingTest {

    @Autowired
    InventoryRepository repository;

    @Test
    void rejectsSaveUsingStaleVersion() {
        InventoryItem created = repository.save(
                new InventoryItem(
                        null,
                        "SKU-01",
                        10,
                        null
                )
        );

        InventoryItem firstRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem secondRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem firstChange =
                firstRead.reserve(2);

        repository.save(firstChange);

        InventoryItem staleChange =
                secondRead.reserve(3);

        assertThrows(
                OptimisticLockingFailureException.class,
                () -> repository.save(staleChange)
        );
    }
}
~~~

The test must run with an appropriate database and transaction configuration. If the test method itself opens a transaction wrapping the entire test, pay attention to how the test transaction affects observing updates between reads.

### 14.1. Testing reload-and-retry

A test for retries should verify:

- The first attempt encounters an optimistic locking exception.
- The first transaction rolls back.
- The next attempt reads the new version.
- The command is reapplied to the new data.
- If business rules are no longer valid, the business error is returned.
- No external side effect executes twice.

Do not merely mock the repository to throw an exception once and succeed; integration tests should verify transaction boundaries and final database state.

## 15. Common mistakes

**"OptimisticLockingFailureException means the database is corrupted."** No. It is a signal that an operation based on a stale version is no longer valid.

**"Just adding @Version makes Spring retry automatically."** No. `@Version` detects conflicts; retry policies are designed by the application.

**"You can catch the exception and call save again immediately."** Unsafe. The transaction may already be rollback-only and the object still holds the stale version.

**"Retrying with the same aggregate object is enough."** No. Each attempt must reload the latest state and reapply the command.

**"Only retry the failed repository method."** That can break atomicity when the use case has already written through multiple repositories. Retry the entire use case in a fresh transaction.

**"More retries make success more likely."** No. Unlimited retries increase load and stall requests. Use bounded attempts and backoff.

**"You can retry every DataAccessException."** No. Constraint, validation, and reference errors are rarely fixed by retrying.

**"After reloading, just apply the command without re-checking."** No. Business rules must be re-evaluated against the new state.

**"TransactionTemplate guarantees each attempt is a new transaction even inside an outer transaction."** No. With default `REQUIRED` propagation, the template joins an existing transaction. The retry coordinator must sit outside any outer transaction or use an explicit bean boundary.

**"Putting @Retryable and @Transactional on the same method always orders them correctly."** Do not assume so. Advisor/proxy ordering affects whether each attempt gets a fresh transaction. Separating the retry facade and transactional service makes ordering explicit.

**"You can call a payment API inside the transaction and retry the whole thing."** Unsafe. Database rollback does not undo external system side effects. Use idempotency and outbox or compensation workflows.

**"All optimistic conflicts should be resolved automatically."** No. For user edits on stale data, returning `409 Conflict` for the caller to review and decide is often more appropriate.

## 16. Workflow for handling OptimisticLockingFailureException

When a write operation fails due to optimistic locking, follow these steps:

1. **Identify the right exception:** catch `OptimisticLockingFailureException` or an appropriate subclass.
2. **Let the failed transaction finish:** do not continue saving inside a rollback-only transaction.
3. **Check whether the command is retryable:** can the command be reapplied to new state without losing other intent?
4. **Bound attempts:** e.g., maximum 3 attempts including the first.
5. **Backoff with jitter:** prevent multiple requests from retrying at the same instant.
6. **Open a fresh transaction:** each attempt must run in an independent transaction.
7. **Reload the aggregate:** do not reuse the stale object/version.
8. **Reapply the command:** re-run validation and invariants.
9. **Retry the entire use case:** if multiple repositories participate in one transaction, roll back and re-execute all required steps.
10. **Stop when attempts are exhausted:** return conflict or throw an exception for the caller to handle.
11. **Protect side effects:** use outbox/idempotency for external calls.
12. **Monitor contention:** if retries happen frequently, revisit the aggregate model and workload.

~~~mermaid

    A["Start use case"] --> B["Open transaction"]
    B --> C["Load latest aggregate"]
    C --> D["Apply command and check invariants"]
    D --> E["Save via repository"]
    E --> F{"Optimistic conflict?"}
    F -->|No| G["Commit transaction"]
    F -->|Yes| H["Rollback transaction"]
    H --> I{"Attempts left and safe to retry?"}
    I -->|No| J["Return conflict to caller"]
    I -->|Yes| K["Backoff + jitter"]
    K --> B
    G --> L["Return result"]
~~~

## 18. Key takeaways

- `@Version` enables Spring Data JDBC to detect updates/deletes based on stale aggregate state.
- When the database version does not match the read version, the operation can fail with `OptimisticLockingFailureException`.
- Optimistic locking detects conflicts; it does not retry automatically.
- Do not retry inside a failed transaction or reuse a stale aggregate.
- Retries must wrap the transaction so each attempt runs in a fresh transaction.
- Each attempt must reload the aggregate, reapply the command, and re-evaluate business invariants.
- If a use case writes across multiple repositories in one transaction, roll back and retry the entire use case.
- Retry only appropriate exceptions, bound attempts, and use backoff/jitter.
- Never blindly retry validation, business rule, or constraint violations.
- `TransactionTemplate` with `REQUIRED` propagation starts a new transaction only when no active transaction exists; design retry boundaries carefully.
- You can use Spring Retry on a separate facade calling a transactional service through its bean proxy so each attempt has its own transaction.
- Do not repeat external side effects outside the database; use idempotency keys, transactional outbox, or compensating workflows.
- For conflicts caused by users editing stale data, returning HTTP `409 Conflict` may be better than automatic merging.
- If conflicts happen frequently, review contention, aggregate boundaries, query/update strategies, and locking.

**Optimistic locking detects when the state an application relied on has become stale. Retrying is safe only when starting from a fresh transaction, reloading data, and re-evaluating business intent.** A sound policy does not try to force every operation to succeed; it ensures newer changes are not overwritten and callers receive honest feedback when a conflict cannot be resolved automatically.
