# Designing Soft Deletes with Custom SQL and Consistent Read Predicates

Soft delete marks a record as deleted while keeping the data row in the database. This approach is useful when data may need to be restored, audit trails must be kept, or historical references must remain intact. With Spring Data JDBC, soft delete is typically implemented with a custom SQL `UPDATE` instead of a physical delete.

The hardest part is not the statement that sets the deletion flag. It is ensuring **every read query applies the same predicate to exclude deleted records**. If one screen filters with `deleted_at IS NULL`, but another report, count query, or repository method forgets that predicate, deleted data can still surface in the application.

This lesson uses a `Customer` example to present the schema, delete/restore SQL statements, repository design, consistent read rules, impact on relationships and indexes, and testing strategies.

## 1. Physical Delete vs. Soft Delete

Physical deletion removes the row from the table:

```sql
DELETE FROM customer
WHERE id = :id;
```

Soft delete keeps the row and updates its status:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NULL;
```

Convention used in this lesson:

- `deleted_at IS NULL`: active record.
- `deleted_at IS NOT NULL`: soft-deleted record.
- The timestamp is recorded when the deletion occurs.

| Criterion | Physical delete | Soft delete |
| --- | --- | --- |
| Row remains in table | No | Yes |
| Can restore directly | No; requires backup or separate copy | Can reset state |
| Foreign keys | Can trigger `ON DELETE` | Not triggered because row still exists |
| Read queries | Do not see deleted rows | Must actively filter |
| Auditing | Needs separate mechanism for history | Can keep timestamp/actor, though full audit still needs dedicated design |

Soft delete is not an automatic feature that makes Spring Data JDBC hide records. If a repository runs an unfiltered SELECT, rows marked deleted are still returned normally.

## 2. Choosing a Deletion State Model

There are two common representations.

### Using a `deleted_at` Timestamp Column

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    deleted_at TIMESTAMP NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

The advantage is that one column represents both state and timestamp. The read predicate is easy to standardize: `deleted_at IS NULL`.

### Using a Boolean Flag

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(150) NOT NULL,
    deleted BOOLEAN NOT NULL DEFAULT FALSE
);
```

This is simple if only status is needed, though it does not record when deletion occurred. If timestamp and actor are needed, `deleted_at` and `deleted_by` can be added.

Throughout this lesson, examples use `deleted_at`. Pick a single convention per table and apply it consistently across schema, domain, and queries.

## 3. Mapping Deletion State into the Aggregate

A simple entity:

```java
package com.example.customer.domain;

import java.time.LocalDateTime;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
    @Id Long id,
    String email,
    String displayName,
    LocalDateTime deletedAt,
    LocalDateTime createdAt
) {
    public boolean isDeleted() {
        return deletedAt != null;
    }

    public Customer markDeleted(LocalDateTime deletedTime) {
        if (deletedAt != null) {
            return this;
        }
        return new Customer(
            id, email, displayName, deletedTime, createdAt
        );
    }

    public Customer restore() {
        if (deletedAt == null) {
            return this;
        }
        return new Customer(
            id, email, displayName, null, createdAt
        );
    }
}
```

Domain methods only produce new object states. Updating the database is still performed by the repository/service. If deletion needs concurrency handling or auditing, conditional SQL and transactions remain essential.

Do not let controllers assign `deletedAt` directly while bypassing authorization and business rules.

## 4. Soft Deleting with Custom SQL

A soft delete statement is usually a conditional UPDATE:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :id
  AND deleted_at IS NULL;
```

The `AND deleted_at IS NULL` condition means:

- Only active records are deleted.
- Repeated calls do not overwrite the original deletion timestamp.
- The updated row count tells whether the operation changed state.

Custom repository using `JdbcTemplate`:

```java
package com.example.customer.repository;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class CustomerWriteRepository {

    private final JdbcTemplate jdbc;

    public CustomerWriteRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public int softDelete(long customerId) {
        return jdbc.update("""
            UPDATE customer
            SET deleted_at = CURRENT_TIMESTAMP
            WHERE id = ?
              AND deleted_at IS NULL
            """, customerId);
    }
}
```

The `customerId` value is bound via JDBC. Table names, columns, and SQL structure are literals defined by the application.

The returned `int` is the number of updated rows:

- `1`: the record existed and just transitioned to deleted state.
- `0`: no matching row; either the ID does not exist or the record was already deleted earlier.

If the API must distinguish `not found` from `already deleted`, the service can read the state or use database-appropriate `RETURNING` SQL. Do not interpret every `0` result as "not found" without checking.
## 5. Do Not Use Default `deleteById` for Soft Delete

`CrudRepository`'s `deleteById` performs a delete according to the repository contract. Spring Data JDBC does not automatically translate it into `UPDATE deleted_at`. Therefore, if a service calls `deleteById`, the row can be physically deleted unintentionally.

You can narrow the repository API using the marker `Repository` interface and declare only allowed operations:

```java
public interface ActiveCustomerRepository
        extends Repository<Customer, Long> {

    Customer save(Customer customer);

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNull();
}
```

A separate write repository provides `softDelete` via `JdbcTemplate`. This avoids inheriting `deleteById`/`deleteAll` in regular business flows.

## 6. Consistent Read Conditions

Every query intended solely for active records must include the predicate:

```sql
deleted_at IS NULL
```

This predicate must be applied to lookup by ID, search, listings, counts, exists checks, joins, pagination, reports, exports, batch jobs, and custom SQL. One properly filtered screen does not protect other read paths.
## 7. Putting the Active Condition in Derived Queries

If the aggregate has a `deletedAt` property, you can declare derived methods:

```java
public interface ActiveCustomerRepository
        extends Repository<Customer, Long> {

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNull();

    Optional<Customer> findByEmailAndDeletedAtIsNull(String email);

    boolean existsByEmailAndDeletedAtIsNull(String email);

    long countByDeletedAtIsNull();
}
```

These methods express the active condition in their names. Semantically in SQL:

```sql
SELECT ...
FROM customer
WHERE id = ?
  AND deleted_at IS NULL;
```

Inherited methods such as `findById(id)` or `findAll()` do not automatically get `deleted_at IS NULL` appended. If you still use `CrudRepository`, default CRUD read methods can return deleted rows as well. Decide clearly which methods have active-only semantics and avoid calling unfiltered methods from normal business logic.

## 8. Reading with `@Query` or Custom Repositories

For complex queries, write the active condition directly in SQL:

```java
public interface CustomerQueryRepository
        extends Repository<Customer, Long> {

    @Query("""
        SELECT id, email, display_name, deleted_at, created_at
        FROM customer
        WHERE deleted_at IS NULL
          AND email = :email
        """)
    Optional<Customer> findActiveByEmail(String email);
}
```

The `:email` parameter binds the value. The `deleted_at IS NULL` condition is written explicitly in SQL.

With a custom repository, you can create shared read methods:

```java
public List<CustomerSummary> findActiveCustomers(String namePart) {
    return jdbc.query("""
        SELECT id, email, display_name
        FROM customer
        WHERE deleted_at IS NULL
          AND display_name LIKE ?
        ORDER BY display_name, id
        """,
        summaryMapper,
        "%" + namePart + "%"
    );
}
```

The search value is still bound. If percent signs and underscores in the input should be treated as literal characters, escape wildcards according to `LIKE` semantics; that is separate from the soft-delete filter.

For custom SQL, include `Active` in method names or organize dedicated classes/queries for active data. This helps readers recognize that the filter predicate is mandatory.

## 9. Soft-Delete Conditions in JOINs

Suppose orders reference customers. A query fetching orders along with customer details:

```sql
SELECT o.id,
       o.status,
       c.email,
       c.display_name
FROM purchase_order o
JOIN customer c ON c.id = o.customer_id
WHERE o.deleted_at IS NULL
  AND c.deleted_at IS NULL;
```

Clearly define what the business wants to filter:

- `o.deleted_at IS NULL`: include only active orders.
- `c.deleted_at IS NULL`: show only orders whose customer is active.

Some systems still need to display historical orders of deleted customers (such as past invoices). In that case, filtering customers in every query is not necessarily right; you may filter only active orders and retain a snapshot of name/email from purchase time. Read predicates must match business semantics.

With `LEFT JOIN`, predicate placement also matters:

```sql
SELECT o.id, c.display_name
FROM purchase_order o
LEFT JOIN customer c
  ON c.id = o.customer_id
 AND c.deleted_at IS NULL
WHERE o.deleted_at IS NULL;
```

Placing `c.deleted_at IS NULL` in `ON` keeps the order in the result even if the corresponding customer is deleted; customer columns will be null. Putting that condition in `WHERE` can alter outer-join behavior due to SQL null logic. Choose placement according to display requirements.

## 10. Counts, Pagination, and Exports Must Also Filter Active Rows

A common bug is filtering the list query while forgetting the count query.

List query:

```sql
SELECT id, email, display_name
FROM customer
WHERE deleted_at IS NULL
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
```

Corresponding count:

```sql
SELECT COUNT(*)
FROM customer
WHERE deleted_at IS NULL;
```

If the count lacks the active filter, the UI can report a total higher than the records actually viewable. Page counts, last pages, and totals will also be wrong.

Similarly, reports/exports need the same semantics:

```sql
SELECT status, COUNT(*) AS order_count
FROM purchase_order
WHERE deleted_at IS NULL
GROUP BY status;
```

Do not inspect only listing endpoints. Search for every query reading the table across repositories, custom adapters, jobs, reports, and exports.
## 15. Transactions and Concurrency in Soft Deletes

A soft-delete operation may include:

1. Checking that the user has permission to delete the record.
2. Confirming the record exists and is active.
3. Updating `deleted_at`.
4. Updating child rows if the domain requires a soft cascade.
5. Writing an audit record or outbox event.
6. Committing the transaction.

If these operations target the same database and must succeed or fail together, place the transaction boundary on the service:

```java
@Service
public class CustomerService {

    private final CustomerWriteRepository writes;

    public CustomerService(CustomerWriteRepository writes) {
        this.writes = writes;
    }

    @Transactional
    public void delete(long customerId) {
        int changed = writes.softDelete(customerId);

        if (changed == 0) {
            throw new CustomerNotActiveException(customerId);
        }

        // Write audit/outbox in the same transaction if needed.
    }
}
```

The `WHERE deleted_at IS NULL` condition makes the operation conditional: only the first request transitions from active to deleted; a subsequent request receives 0. If you need to distinguish nonexistent from already deleted, the service can query further or use database-specific `RETURNING`.

If optimistic locking is used, you can add a `version` column and include the expected version in the update condition:

```sql
UPDATE customer
SET deleted_at = CURRENT_TIMESTAMP,
    version = version + 1
WHERE id = :id
  AND deleted_at IS NULL
  AND version = :expectedVersion;
```

The updated row count is 0 when the ID does not match, the row is already deleted, or the version has changed. The service must classify errors according to the business contract. When using custom SQL, the application itself is responsible for incrementing the version and checking the row count.

Transactions alone do not prevent all race conditions. Conditions inside the UPDATE, database constraints, and concurrency policies must work together.

## 16. Structuring Code So Every Read Path Uses the Same Rule

You can reduce the chance of forgetting filters by:

- Using explicit method names like `findActiveById`, `findAllActive`, `countActive`.
- Placing active queries in a dedicated repository/adapter.
- Not exposing physical `findAll` or `deleteById` to business flows unless needed.
- Auditing every query method, custom SQL, report, export, and job.
- Writing integration tests confirming deleted rows never appear in any active read endpoint.

A marker repository can explicitly define allowed operations:

```java
public interface CustomerRepository
        extends Repository<Customer, Long> {

    Optional<Customer> findByIdAndDeletedAtIsNull(Long id);

    List<Customer> findByDeletedAtIsNullOrderByCreatedAtDescIdDesc();

    Optional<Customer> findByEmailAndDeletedAtIsNull(String email);

    long countByDeletedAtIsNull();

    Customer save(Customer customer);
}
```

For other queries, include `Active` in the method name or write explicit SQL predicates. Avoid generic method names like `search` that hide whether deleted rows are filtered out.

If the system has an administrative need to view deleted records as well, create a separate read path clearly named such as `findIncludingDeletedById`, guard it with administrative permissions, and prevent accidental reuse in regular APIs.

## 17. Common Pitfalls

| Pitfall | Consequence | Resolution |
| --- | --- | --- |
| Calling `CrudRepository.deleteById` intending soft delete | Row is physically deleted per repository mechanism. | Use a custom `UPDATE`. |
| Filtering deleted rows on only one screen | Other queries still return deleted records. | Standardize active conditions across all read paths. |
| Using default `findById` | Can return deleted records too. | Use `findByIdAndDeletedAtIsNull`. |
| Count query missing condition | Total count/last page disagrees with listing. | Apply the same predicate to `SELECT` and `COUNT`. |
| Forgetting filter in `JOIN` | Deleted related data appears or outer-joined rows disappear. | Define semantics and place predicates properly in `ON`/`WHERE`. |
| Assuming FK cascade soft-deletes children | Child rows remain active when root is updated. | Write explicit soft cascades if the domain requires them. |
| Table-wide unique email blocks reuse | Cannot re-register an email belonging to a deleted customer. | Decide between active-only uniqueness vs. full-history uniqueness. |
| Restore ignores constraints | Restoration fails due to conflict with active data. | Handle business conflicts on restore. |
| Forgetting batches/reports/exports | Deleted records still show up in files or statistics. | Audit every data-reading consumer. |
| Allowing clients to pass column names/SQL fragments | Risk of SQL injection or out-of-contract queries. | Bind values and allowlist dynamic structure. |

## 18. Testing Soft Deletes and Read Predicates

Integration tests should verify both database state and repository behavior.

A basic scenario:

1. Create an active customer.
2. Read using `findByIdAndDeletedAtIsNull` and confirm it is found.
3. Call the soft-delete service.
4. Check the row still exists in the table and `deleted_at` is non-null.
5. Read using active methods and confirm it is no longer visible.
6. Verify count/list/search all exclude the deleted row.
7. Call delete a second time and verify the idempotency/row-count policy.
8. Restore, then verify active queries find it again.
9. Check unique constraint behavior when an active record uses the same email.
10. Verify join queries, exports, and count queries if the system has those read paths.

Illustrative test example:

```java
@Test
void softDeletedCustomerIsExcludedFromActiveQueries() {
    Customer saved = customers.save(
        new Customer(null, "a@example.test", "An", null, now)
    );

    assertThat(customers.findByIdAndDeletedAtIsNull(saved.id()))
        .isPresent();

    assertThat(writes.softDelete(saved.id())).isEqualTo(1);

    assertThat(customers.findByIdAndDeletedAtIsNull(saved.id()))
        .isEmpty();

    assertThat(jdbc.queryForObject(
        "SELECT COUNT(*) FROM customer WHERE id = ?",
        Integer.class,
        saved.id()
    )).isEqualTo(1);

    assertThat(jdbc.queryForObject(
        "SELECT deleted_at IS NOT NULL FROM customer WHERE id = ?",
        Boolean.class,
        saved.id()
    )).isTrue();
}
```

This is an illustrative example; repository names, fixtures, date/time types, and boolean assertion SQL must match your project's database/test setup.

Dedicated tests are needed for custom queries because one working active method does not prove every query is right. Create one active record and one deleted record, run each read path, and confirm only the active record appears.

## 19. Process for Implementing Soft Delete

When adding soft delete to a live table, proceed in order:

1. Define semantics: which records count as active, whether restore is allowed, whether unique keys can be reused.
2. Add a nullable `deleted_at` column via migration. Existing rows with `NULL` are treated as active.
3. Map the property onto the aggregate and update active repository queries.
4. Create custom SQL `UPDATE` statements for soft delete/restore.
5. Guard write flows so default hard deletes are not called.
6. Audit `SELECT`, `JOIN`, `COUNT`, pagination, reports, exports, and jobs.
7. Adjust unique constraints/indexes to match active semantics.
8. Write integration tests against the target database/dialect.
9. Deploy code and migrations in compatible order; monitor logs and row counts after release.

There is no need to backfill `deleted_at` for existing rows if `NULL` is defined as active. If using a boolean, the migration should set default `FALSE` for existing data according to database capabilities.

## 20. Self-Check Questions

- How does soft delete differ from physical delete?
- Why does `CrudRepository.deleteById` not automatically turn into updating `deleted_at`?
- What state does `deleted_at IS NULL` represent?
- Why must every active read query include the same predicate?
- Why must count queries and exports also filter out deleted records?
- In a `LEFT JOIN`, when should the right-hand table's deleted condition be placed in `ON`?
- Does soft-deleting a root automatically trigger `ON DELETE CASCADE`?
- When is a soft cascade down to child rows needed?
- How does a partial unique index help when emails only need to be unique among active records?
- What conflicts can happen during restoration?
- How can you restrict services from accidentally calling hard delete?
- Which integration tests prove read predicates are applied consistently?

A complete soft-delete design has two halves: **writing the deleted state with conditional SQL** and **reading active data with a consistent predicate**. Clearly define the state in the schema, prevent business flows from calling default hard deletes, apply filters to listings/counts/joins/exports alike, and test every read path. That way, data is retained for restoration or auditing without accidentally appearing in normal business workflows.
## 11. Soft Delete and Aggregate Children

Suppose `PurchaseOrder` has an `OrderLine` collection in the `order_line` table. When soft-deleting the root:

```sql
UPDATE purchase_order
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :orderId
  AND deleted_at IS NULL;
```

The `order_line` rows remain because there is no physical root deletion and foreign key `ON DELETE CASCADE` is not triggered by an `UPDATE`.

This is usually the desired behavior if child rows belong to the root's lifecycle and must be kept for restoration or auditing. When reading active aggregates, the application queries only roots with `deleted_at IS NULL`; child rows are loaded through that aggregate.

If the child table can be queried independently, or children have their own deletion state, corresponding conditions must be designed as well. Do not assume hiding the root automatically hides direct queries on the child table.

| Policy | Implementation | When appropriate |
| --- | --- | --- |
| Root controls visibility | Keep child rows; access children only through active roots. | Children only make sense inside the aggregate root. |
| Root and child have separate states | Add `deleted_at` to child and filter both as needed. | Children can be deleted/restored independently. |
| Business-cascade soft delete | Service updates root and children in the same transaction. | Domain requires all children to transition together with the root. |

Do not use physical cascades as a substitute for soft cascades. If business rules require a soft cascade, write explicit `UPDATE` statements inside a single transaction.

## 12. Restoring Records

Restoration typically sets `deleted_at` back to null:

```sql
UPDATE customer
SET deleted_at = NULL
WHERE id = :id
  AND deleted_at IS NOT NULL;
```

Custom repository:

```java
public int restore(long customerId) {
    return jdbc.update("""
        UPDATE customer
        SET deleted_at = NULL
        WHERE id = ?
          AND deleted_at IS NOT NULL
        """, customerId);
}
```

Like soft delete, the updated row count tells whether the state changed. Define clearly who is authorized to restore and whether there are time limits or restoration preconditions.

Restoration can encounter business conflicts. For example, email must be unique among active customers; while a customer was deleted, someone else registered with the same email. On restore, the unique constraint may reject the operation. This is a domain error to handle explicitly—do not bypass constraints to force a restore.

If soft delete cascaded across multiple tables, restoration must follow consistent rules as well: does restoring the root restore all children deleted in the same batch? Distinguish children previously deleted independently from those deleted by a soft cascade.

## 13. Unique Constraints and Active Data

If email must be unique among active customers, the constraint:

```sql
UNIQUE (email)
```

still blocks creating a new customer with the email of a soft-deleted customer, because the old row remains.

In PostgreSQL, you can use a partial unique index:

```sql
CREATE UNIQUE INDEX uq_customer_active_email
ON customer (email)
WHERE deleted_at IS NULL;
```

The index applies only to active rows. Deleted customers no longer occupy that email within the scope of that constraint.

Partial indexes are a database-specific feature; there is no completely portable equivalent syntax across every DBMS. On other databases, you can use generated/computed columns, conditional unique key columns, or a different email-reuse rule. Check syntax and semantics on your target engine.

If email reuse after deletion is not desired, keeping a table-wide unique constraint may be the right choice. That is a business rule, not a mandatory consequence of soft delete.

## 14. Indexing for Active Queries

If most queries fetch non-deleted rows, the `deleted_at IS NULL` predicate can affect index design.

Frequently used query example:

```sql
SELECT id, email, display_name
FROM customer
WHERE deleted_at IS NULL
  AND email = :email;
```

A composite index may be suitable:

```sql
CREATE INDEX idx_customer_deleted_email
ON customer (deleted_at, email);
```

In PostgreSQL, if active rows make up the primary dataset, consider a partial index:

```sql
CREATE INDEX idx_customer_active_email
ON customer (email)
WHERE deleted_at IS NULL;
```

Do not add indexes mechanically from examples. If `deleted_at` has low selectivity, an index on that column alone may help little. Inspect execution plans, active/deleted row ratios, query frequency, and write overhead.

For active listings ordered by creation date:

```sql
CREATE INDEX idx_customer_active_created_id
ON customer (created_at DESC, id DESC)
WHERE deleted_at IS NULL;
```

This is a PostgreSQL partial index example. Other dialects may need a composite index or a different strategy.
