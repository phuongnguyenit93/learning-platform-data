# @ReadOnlyProperty for Read-Only Database-Managed Data

In **Spring Data Relational JDBC (Spring Data JDBC)**, there are properties that must be read from the database yet should never be written directly by the application. Examples include values computed by a generated column, timestamps updated by a trigger, or fields managed by an external process. The **`@ReadOnlyProperty`** annotation marks a property for exactly that purpose: Spring Data JDBC still maps the property when reading the entity, while excluding it from write operations when persisting the entity.

This annotation is useful when the database owns the final value. It prevents the application from accidentally overwriting database-generated values while allowing the entity to expose those values once reloaded.

## 1. Meaning of @ReadOnlyProperty

`@ReadOnlyProperty` belongs to the `org.springframework.data.annotation` package:

~~~java
import org.springframework.data.annotation.ReadOnlyProperty;
~~~

Understand the annotation's contract from both directions:

| Operation | Behavior for a property with `@ReadOnlyProperty` |
|---|---|
| Reading entity from database | Property is still mapped from the corresponding column |
| Inserting entity | Property is excluded from the INSERT statement |
| Updating entity | Property is excluded from the UPDATE statement |
| Re-reading after database computes/updates | New value is fetched from the database when the entity is read |

For example, the `products` table has a `stock_value` column computed by the database from `unit_price * stock_quantity`. The Java entity needs to expose `stockValue`, yet must not send that value in INSERT/UPDATE statements.

~~~mermaid
flowchart TB
    App["Application<br/>Product fields"]
    Repo["ProductRepository.save(product)"]
    Write["INSERT / UPDATE<br/>excludes stock_value"]
    DB[("Database")]
    Calc["Generated column / trigger<br/>computes stock_value"]
    Read["SELECT product"]
    Entity["Product.stockValue<br/>mapped on read"]

    App --> Repo --> Write --> DB
    DB --> Calc
    Calc --> DB
    DB --> Read --> Entity
~~~

`@ReadOnlyProperty` is a **mapping instruction at the Spring Data layer**. It does not create a generated column, does not create a trigger, does not grant read-only database permissions, and does not stop Java code from mutating the field in memory.

## 2. Appropriate use cases

Several kinds of data are typically managed by the database:

| Data | Where created/updated | Why mark read-only |
|---|---|---|
| Total value from unit price × quantity | Generated column | Application should not write back a derived value |
| Record creation timestamp | Default `CURRENT_TIMESTAMP` or trigger | Database supplies the authoritative timestamp |
| Last update timestamp | Trigger on UPDATE | All writers follow the exact same rule |
| Normalized value from other columns | Generated column/view | Prevent application from sending inconsistent values |
| Aggregated metrics from a view | View or database query | Entity needs to read results without owning writes |

Not every field forbidden from user editing needs `@ReadOnlyProperty`. If the application remains the party writing the value, use domain rules, input DTOs, validation, or appropriate authorization. This annotation is specifically for cases where **Spring Data JDBC must not write that property**.

## 3. Example: database-computed stock_value column

Suppose a product has a unit price `unit_price` and stock quantity `stock_quantity`. The inventory stock value `stock_value` always equals the product of those two source columns:

\[
\text{stockValue} = \text{unitPrice} \times \text{stockQuantity}
\]

The application only modifies unit price or stock quantity; the database computes the total automatically.

### PostgreSQL

~~~sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(40) NOT NULL UNIQUE,
    unit_price NUMERIC(12, 2) NOT NULL
        CHECK (unit_price >= 0),
    stock_quantity INTEGER NOT NULL
        CHECK (stock_quantity >= 0),
    stock_value NUMERIC(14, 2)
        GENERATED ALWAYS AS (unit_price * stock_quantity) STORED
);
~~~

### MySQL 8.4

~~~sql
CREATE TABLE products (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    sku VARCHAR(40) NOT NULL UNIQUE,
    unit_price DECIMAL(12, 2) NOT NULL,
    stock_quantity INTEGER NOT NULL,
    stock_value DECIMAL(14, 2)
        GENERATED ALWAYS AS (unit_price * stock_quantity) STORED,
    CONSTRAINT ck_product_price CHECK (unit_price >= 0),
    CONSTRAINT ck_product_stock CHECK (stock_quantity >= 0)
) ENGINE=InnoDB;
~~~

These two DDL snippets are mutually exclusive alternatives; do not execute both on the same database. PostgreSQL and MySQL have different generated-column syntax and details; this example uses **STORED** so the result is stored and recomputed whenever source columns change.

Because `stock_value` is a generated column, INSERT/UPDATE statements must not supply values for it. If the application passes a value to this column, the database can reject the operation. This is where `@ReadOnlyProperty` keeps the mapping from attempting to write the column.

## 4. Mapping Product with Spring Data JDBC

~~~java
package com.example.inventory;

import java.math.BigDecimal;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("products")
public class Product {

    @Id
    private Long id;

    private String sku;

    @Column("unit_price")
    private BigDecimal unitPrice;

    @Column("stock_quantity")
    private int stockQuantity;

    @ReadOnlyProperty
    @Column("stock_value")
    private BigDecimal stockValue;

    protected Product() {
        // For Spring Data JDBC.
    }

    public Product(String sku, BigDecimal unitPrice, int stockQuantity) {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("SKU is required");
        }
        if (unitPrice == null || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("Invalid unit price");
        }
        if (stockQuantity < 0) {
            throw new IllegalArgumentException("Invalid stock quantity");
        }
        this.sku = sku;
        this.unitPrice = unitPrice;
        this.stockQuantity = stockQuantity;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }

    public int getStockQuantity() {
        return stockQuantity;
    }

    public BigDecimal getStockValue() {
        return stockValue;
    }

    public void changeStockQuantity(int quantity) {
        if (quantity < 0) {
            throw new IllegalArgumentException("Quantity must be non-negative");
        }
        this.stockQuantity = quantity;
    }
}
~~~

Repository:

~~~java
package com.example.inventory;

import org.springframework.data.repository.CrudRepository;

public interface ProductRepository
        extends CrudRepository<Product, Long> {
}
~~~

`@ReadOnlyProperty` is placed on `stockValue`. The properties `sku`, `unitPrice`, and `stockQuantity` are still written normally. This means the annotation affects **a single property**, rather than making the entire `Product` entity read-only.

### Saving a new entity

~~~java
Product product = new Product(
    "BOOK-01",
    new BigDecimal("150000.00"),
    4
);

Product saved = productRepository.save(product);
Long productId = saved.getId();
~~~

On insert, Spring Data JDBC writes writable fields such as `sku`, `unit_price`, and `stock_quantity`. `stock_value` is excluded from the write; the database computes its value from the two source columns.

### Reading back the database-computed value

~~~java
Product loaded = productRepository.findById(productId)
    .orElseThrow();

System.out.println(loaded.getStockValue()); // 600000.00
~~~

On read, `stock_value` is still mapped into `Product.stockValue`. The annotation does not omit the property from SELECT or read mapping.

**Note on the return value of save:** `@ReadOnlyProperty` specifies that the property is not written. Do not infer that every value produced by a trigger or generated column will automatically be reloaded into the instance returned from `save`. If a use case needs the newly computed database value immediately after insert/update, reload the entity via the repository or run an explicit read query after the write within an appropriate transaction.

## 5. Updating source columns

Suppose stock quantity changes from 4 to 7:

~~~java
Product current = productRepository.findById(productId)
    .orElseThrow();

current.changeStockQuantity(7);
Product saved = productRepository.save(current);

// When the latest stock_value is needed, reload from the DB.
Product refreshed = productRepository.findById(productId)
    .orElseThrow();

System.out.println(refreshed.getStockValue()); // 1050000.00
~~~

Spring Data JDBC writes the change to `stockQuantity`. The `stock_value` column is recomputed by the database according to the generated-column expression. Upon reloading, the framework maps the new value.

Do not add a public setter for `stockValue` just to let controllers pass values in. The domain only needs to expose modifications to source components; the derived value is owned by the database.

## 6. Database defaults and triggers can also produce read-only data

Generated columns are a clear example, yet the annotation also suits values managed by defaults or triggers.

### created_at assigned by the database on insert

PostgreSQL:

~~~sql
CREATE TABLE audit_records (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    event_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
        DEFAULT CURRENT_TIMESTAMP
);
~~~

Entity:

~~~java
import java.time.OffsetDateTime;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("audit_records")
public class AuditRecord {

    @Id
    private Long id;

    private String eventName;

    @ReadOnlyProperty
    @Column("created_at")
    private OffsetDateTime createdAt;
}
~~~

The application does not send `created_at`; the database applies the default on insert. When reading the record, `createdAt` is mapped from the column.

### updated_at updated by a trigger

Some systems require every writer to update `updated_at`. A database trigger can enforce this. PostgreSQL example:

~~~sql
CREATE TABLE inventory_notes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    note TEXT NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL
        DEFAULT CURRENT_TIMESTAMP
);

CREATE FUNCTION set_inventory_note_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_inventory_note_updated_at
BEFORE UPDATE ON inventory_notes
FOR EACH ROW
EXECUTE FUNCTION set_inventory_note_updated_at();
~~~

In the entity, `updatedAt` can be marked `@ReadOnlyProperty` so Spring Data JDBC does not overwrite the trigger-managed value. When the latest update timestamp is needed immediately in a response, reload the record after the update operation.

**Defaults and triggers have different semantics:** defaults usually apply when an insert omits a column; triggers can intervene on every update. If an application explicitly sends `NULL`, defaults do not necessarily apply. With a trigger, the database can change the value even when the UPDATE statement does not write the `updated_at` column.

## 7. How does @ReadOnlyProperty differ from @Transient, @Id, and @Column?

Each annotation serves a distinct purpose:

| Annotation | Role | Is property read from DB? | Is property written? |
|---|---|---|---|
| `@ReadOnlyProperty` | Mapped on read, excluded from writes | Yes | No |
| `@Transient` (Spring Data) | Excludes property from persistence mapping | Not via standard mapping | No |
| `@Id` | Marks primary key | Yes | Depends on ID/newness mechanism and generated IDs |
| `@Column` | Declares column name | Yes | Yes, unless another write exclusion applies |
| `@Version` | Manages optimistic locking | Yes | Framework manages version |

For example, if `stockValue` is marked `@Transient`, Spring Data JDBC does not treat it as a normal column to read or write. When marked `@ReadOnlyProperty`, the framework still reads `stock_value` while skipping writes for that property.

Do not confuse `@ReadOnlyProperty` with JPA's `@Column(insertable = false, updatable = false)`. Spring Data JDBC uses Spring Data Relational's own annotations; do not carry JPA configuration attributes over here.

## 8. @ReadOnlyProperty is not database write protection

The annotation only affects how Spring Data JDBC builds write operations for the annotated property. Other write paths can still modify the column:

- SQL executed directly from an administration tool.
- Another application using JDBC.
- Stored procedures or triggers.
- Another repository or custom SQL not using the same mapping.

If the security requirement is that **the application must not have permission to UPDATE a column or table**, you must use database privileges, views, stored procedures, or an appropriate permission architecture. Never rely on an annotation as a security boundary.

Likewise, the Java field can still be mutated in memory if setters or internal code exist. Spring Data JDBC skipping a property on write does not make the Java object immutable.

## 9. Using entities with database views

A view can expose aggregated data for reading:

~~~sql
CREATE VIEW product_stock_summary AS
SELECT
    id,
    sku,
    stock_quantity,
    unit_price * stock_quantity AS stock_value
FROM products;
~~~

An entity reading from the view can map computed columns with `@ReadOnlyProperty`:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("product_stock_summary")
public class ProductStockSummary {

    @Id
    private Long id;

    private String sku;

    @Column("stock_quantity")
    private Integer stockQuantity;

    @ReadOnlyProperty
    @Column("stock_value")
    private BigDecimal stockValue;
}
~~~

In practice, views may be non-updatable or updatable only under specific conditions depending on the database. Marking one property read-only **does not make the remaining properties of the entity read-only**. If a view is intended solely for reading, do not expose `save`/`delete` operations via a standard CRUD repository; use a dedicated read-only repository, projection, or read-only database permissions.

## 10. Impact on aggregates and child objects

`@ReadOnlyProperty` can be applied to properties on entities/aggregates mapped by Spring Data JDBC. When a computed field on the aggregate root is annotated, other fields on the root are still written. If an aggregate has a child collection, placing the annotation on a root property does not turn the entire collection read-only.

Example:

~~~java
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    private String status;

    @ReadOnlyProperty
    @Column("item_count")
    private Integer itemCount;

    @MappedCollection(idColumn = "order_id")
    private List<OrderItem> items;
}
~~~

If `item_count` is managed by a trigger or generated column, Spring Data JDBC does not write that property. However, the `items` list is still persisted under normal aggregate mapping. Consider how the database computes `item_count` and how it is reloaded after modifying the collection.

Do not use `@ReadOnlyProperty` to mask an unclear aggregate model. If a value is part of a business invariant and must be computed in the domain prior to writing, let the domain compute it and persist it as a normal writable property. Delegate value generation to the database only when the database genuinely owns that calculation or rule.

## 11. Verifying actual SQL

When working with `@ReadOnlyProperty`, verify both write statements and read data:

1. Create a new entity with the source columns.
2. Save via the repository.
3. Check that the generated column has a value in the database.
4. Reload the entity and check that the read-only property is mapped.
5. Update a source column, save again, and verify the database recomputes the value.

SQL example:

~~~sql
SELECT
    id,
    sku,
    unit_price,
    stock_quantity,
    stock_value
FROM products
ORDER BY id;
~~~

If you need to observe SQL executed by Spring Data JDBC, enable appropriate logging for Spring JDBC/Relational packages in development environments. Logger names and statement details may vary by version; avoid relying on logging in production if it could expose sensitive data.

## 12. Common mistakes

| Mistake | Consequence | Resolution |
|---|---|---|
| Marking `@ReadOnlyProperty` without a generated column/default/trigger | Read value may remain null or stale | Ensure the database actually populates/updates the value |
| Failing to annotate a generated property | Spring Data JDBC tries to write a DB-managed column and may be rejected | Annotate the property with `@ReadOnlyProperty` |
| Thinking a read-only property is not read back | Entity does not receive value from SELECT | Remember the annotation only excludes writes, not reads |
| Expecting `save()` to always return fresh computed values | Returned instance may not be refreshed from DB | Reload the entity or run a read query after writing |
| Using the annotation as a security mechanism | Other write paths can still modify the column | Configure database/view permissions and control all writers |
| Trying to make an entire entity read-only via one field annotation | Other properties can still be written | Annotation applies per property; design query-only repositories if the whole entity is read-only |
| Using `@Transient` instead of `@ReadOnlyProperty` | Property is not mapped from DB | Use the right annotation for the purpose |
| Using a Java primitive type for a nullable generated column | Cannot represent SQL NULL | Use wrapper/reference types when columns can be null |
| Recomputing the property in Java and also writing to DB | Two sources of truth that can drift | Pick one owner for the computation and keep it consistent |

## 13. Hands-on exercises

1. Create a `products` table with `stock_value` as a generated column on PostgreSQL or MySQL.
2. Create the `Product` entity with `@ReadOnlyProperty` on `stockValue` and a CRUD repository.
3. Insert a product with price 150,000 and quantity 4. Read it back and confirm stock value is 600,000.
4. Change quantity to 7, save, and read back. Confirm stock value is 1,050,000.
5. Remove `@ReadOnlyProperty` in a practice environment and try saving an entity. Observe how the database reacts when Spring Data JDBC attempts to write the generated column.
6. Create a `createdAt` field with default `CURRENT_TIMESTAMP`. Mark it read-only and compare the database value with the entity after reloading.
7. Create the `product_stock_summary` view and an entity reading it. Explain why a standard CRUD repository should not be used to update a read-only view.
8. Discuss: which fields should be computed in domain services and which should be delegated to the database? State the benefits and risks of having two computation sources.

## 14. Key takeaways

`@ReadOnlyProperty` tells Spring Data JDBC that a property **must still be read from the database yet excluded from inserts and updates performed through that mapping**. It is an appropriate choice for generated columns, trigger/default-managed data, and certain values read from views.

The annotation does not generate values in the database, does not refresh every computed value immediately on `save`, does not make entities immutable, and does not replace read-only database permissions. Design DDL so the database truly produces the value, annotate the property in the entity, and reload whenever the use case needs the latest value after a write.
