# Testing Derived Queries, @Query, Projections, and Pagination

In **Spring Data Relational JDBC**, a repository can supply data through several mechanisms: derived queries from method names, SQL declared with `@Query`, projections/read models mapped with `RowMapper`, and pagination with `Pageable`, `Page`, or `Slice`.

Each mechanism has a different contract. Derived queries are limited to aggregate root properties and do not automatically `JOIN`. String-based `@Query` enables explicit SQL, yet does not automatically apply `Pageable`/`Sort`/`Limit` like derived queries. Projection DTOs require proper `ResultSet` mapping and typically fit read-only views. `Page` provides total counts and can trigger a count query; `Slice` only checks whether a next page exists.

Tests must verify both returned data and how the query behaves: filter conditions, sorting, counts, page bounds, SQL aliases, DTO mapping, and empty/non-unique cases. This lesson uses an order example to demonstrate each mechanism inside a Spring Data JDBC test context.

## 1. Data Model Used in Examples

Aggregate root:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String status;

    @Column("created_at")
    private LocalDateTime createdAt;

    protected PurchaseOrder() {}

    public PurchaseOrder(Long customerId, String status, LocalDateTime createdAt) {
        this.customerId = customerId;
        this.status = status;
        this.createdAt = createdAt;
    }

    public Long getId() { return id; }
    public Long getCustomerId() { return customerId; }
    public String getStatus() { return status; }
    public LocalDateTime getCreatedAt() { return createdAt; }
}
~~~

Example table:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
~~~

DTO for a list view:

~~~java
public record OrderSummary(
        Long orderId,
        String status,
        String customerName,
        Long lineCount
) {}
~~~

The repository will contain derived queries, annotated queries, and projection queries. In this example, `OrderSummary` is a read model, not an aggregate root for persistence.

## 2. Testing Queries Derived from Method Names

Spring Data JDBC parses method names to generate SQL. Common keywords include `And`, `Or`, `Is`, `Between`, `LessThan`, `GreaterThan`, `Before`, `After`, `IsNull`, `Like`, `StartingWith`, `EndingWith`, `Containing`, `In`, `NotIn`, `True`, `False`, `IgnoreCase`, and `OrderBy`.

Example repository:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long>,
                PagingAndSortingRepository<PurchaseOrder, Long> {

    List<PurchaseOrder> findByStatus(String status);

    List<PurchaseOrder> findByCustomerIdAndStatus(
            Long customerId,
            String status
    );

    List<PurchaseOrder> findByCreatedAtAfter(LocalDateTime createdAt);

    List<PurchaseOrder> findTop5ByStatusOrderByCreatedAtDesc(String status);

    Page<PurchaseOrder> findByStatus(String status, Pageable pageable);

    Slice<PurchaseOrder> findByCustomerId(Long customerId, Pageable pageable);
}
~~~

Derived queries only support properties usable in `WHERE` without a `JOIN`; Spring Data JDBC documentation limits derivation to direct properties of the aggregate root. Derived queries currently support `SELECT`, not auto-derived `INSERT`/`UPDATE`/`DELETE` statements.

### Testing Simple Conditions

~~~java
@DataJdbcTest
class PurchaseOrderDerivedQueryTest {

    @Autowired PurchaseOrderRepository repository;
    @Autowired JdbcTemplate jdbcTemplate;

    @BeforeEach
    void setUp() {
        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 10L, "PAID", Timestamp.valueOf("2026-01-10 09:00:00"));

        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 10L, "OPEN", Timestamp.valueOf("2026-01-11 09:00:00"));

        jdbcTemplate.update("""
                INSERT INTO purchase_order(customer_id, status, created_at)
                VALUES (?, ?, ?)
                """, 20L, "PAID", Timestamp.valueOf("2026-01-12 09:00:00"));
    }

    @Test
    void filtersByStatus() {
        List<PurchaseOrder> result = repository.findByStatus("PAID");

        assertThat(result).hasSize(2);
        assertThat(result).allSatisfy(order ->
                assertThat(order.getStatus()).isEqualTo("PAID"));
    }

    @Test
    void combinesRootPropertiesWithAnd() {
        List<PurchaseOrder> result =
                repository.findByCustomerIdAndStatus(10L, "OPEN");

        assertThat(result).hasSize(1);
        assertThat(result.getFirst().getCustomerId()).isEqualTo(10L);
    }

    @Test
    void supportsTopAndOrderBy() {
        List<PurchaseOrder> result =
                repository.findTop5ByStatusOrderByCreatedAtDesc("PAID");

        assertThat(result).hasSize(2);
        assertThat(result.getFirst().getCreatedAt())
                .isAfter(result.getLast().getCreatedAt());
    }
}
~~~

This is an illustrative example; schema and entity constructors/accessors must match real migrations. If using Java 17 rather than Java 21, replace `getFirst()` with `get(0)`.

### Testing Boundary Conditions

For each important derived query, test:

- Zero matching rows: returns an empty collection or `Optional.empty` per return type.
- One matching row: property values are accurate.
- Multiple matching rows: all results are accurate.
- Null values with `IsNull`/`IsNotNull`: SQL semantics are accurate.
- `In` with an empty collection: confirm behavior for your version/database and handle empty inputs in the service if needed.
- Combining `And`/`Or`: predicates group as indicated by the method name.
- `OrderBy`: deterministic ordering, with a tie-breaker when rows share sort values.

Do not assert only element count. Assert IDs and properties to catch queries that filter wrongly or return the wrong order.

## 3. Limitations of Query Derivation

Spring Data JDBC query derivation is not a general-purpose query builder. It is restricted to properties filterable without a `JOIN`.

For example, a method like:

~~~java
List<PurchaseOrder> findByCustomerName(String customerName);
~~~

does not automatically `JOIN` the `customer` table if `customer` is a separate aggregate root referenced by `customerId`. To filter by customer name, use `@Query` with a `JOIN` or a custom repository fragment using `NamedParameterJdbcTemplate`.

Derived queries also support `SELECT` only. When SQL updates or deletes are needed, use `@Modifying` + `@Query` or an appropriate persistence API.

Tests should verify that derived queries stay within supported scope; do not try to cram multi-table joins into method names. When business conditions exceed root properties, switch to an explicit query so SQL stays readable and controllable.

## 4. Testing Page, Slice, and List with Pageable

Spring Data JDBC supports `Pageable` for derived query methods. You can return:

- **`Page<T>`**: the page's data, total element count, and total page count. The framework may run an extra count query.
- **`Slice<T>`**: the page's data and whether a next page exists. The framework fetches `pageSize + 1` rows to determine `hasNext`.
- **`List<T>`**: fetches only rows within the `Pageable` range, creating no `Page` metadata and needing no count query.

Example:

~~~java
Page<PurchaseOrder> findByStatus(String status, Pageable pageable);

Slice<PurchaseOrder> findByCustomerId(Long customerId, Pageable pageable);

List<PurchaseOrder> findByStatus(String status, Pageable pageable);
~~~

These methods need distinct names or parameter signatures to avoid conflicting declarations in the same interface. The repository example earlier declared `Page` and `Slice`; if you also want `List` with `Pageable`, give the query method a distinct name or use a separate repository for the example.

### Testing Page

~~~java
@Test
void returnsPageContentAndTotalCount() {
    PageRequest pageRequest = PageRequest.of(
            0,
            2,
            Sort.by(
                    Sort.Order.desc("createdAt"),
                    Sort.Order.desc("id")
            )
    );

    Page<PurchaseOrder> page =
            repository.findByStatus("PAID", pageRequest);

    assertThat(page.getContent()).hasSize(2);
    assertThat(page.getTotalElements()).isEqualTo(3);
    assertThat(page.getTotalPages()).isEqualTo(2);
    assertThat(page.getNumber()).isZero();
    assertThat(page.hasNext()).isTrue();
}
~~~

This test needs at least three `PAID` rows. `Page` can generate a count query to calculate `totalElements`/`totalPages`. Do not assume the count query always runs if the framework can infer the total from page contents in special cases; observe SQL when verifying query counts.

### Testing Slice

~~~java
@Test
void returnsSliceAndDetectsNextPage() {
    Pageable request = PageRequest.of(
            0,
            2,
            Sort.by(Sort.Order.asc("id"))
    );

    Slice<PurchaseOrder> slice =
            repository.findByCustomerId(10L, request);

    assertThat(slice.getContent()).hasSize(2);
    assertThat(slice.hasNext()).isTrue();
    assertThat(slice.getNumberOfElements()).isEqualTo(2);
}
~~~

`Slice` does not provide `totalElements`/`totalPages`. It only knows whether more data follows. When callers only need Next/Previous buttons or infinite scrolling, `Slice` avoids potentially expensive count queries.

### Testing Last Page and Empty Page

~~~java
@Test
void returnsLastSliceWithoutNextPage() {
    Pageable request = PageRequest.of(
            1,
            2,
            Sort.by(Sort.Order.asc("id"))
    );

    Slice<PurchaseOrder> slice =
            repository.findByCustomerId(10L, request);

    assertThat(slice.hasNext()).isFalse();
}

@Test
void returnsEmptyPageWhenOffsetIsBeyondResults() {
    Pageable request = PageRequest.of(20, 10);

    Page<PurchaseOrder> page =
            repository.findByStatus("MISSING", request);

    assertThat(page.getContent()).isEmpty();
    assertThat(page.getTotalElements()).isZero();
}
~~~

### Stable Sorting

If sorting only by `createdAt` when multiple orders share the same timestamp, the database can return tied rows in non-deterministic order. When a user paginates, rows can repeat or be skipped across requests.

Add a unique key as a tie-breaker:

~~~java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
);
~~~

Test ordering on data with duplicate timestamps to confirm the tie-breaker is actually applied.

### Offset Pagination at Deep Pages

Large offsets can force the database to read and discard many rows before returning the requested page. If tables are large and callers paginate deeply, measure offset cost. Consider keyset/seek pagination using conditions on the last page's boundary values, such as `created_at` and `id`. This usually requires custom queries or repository fragments instead of simply incrementing page numbers.

## 5. Testing @Query with Explicit SQL

`@Query` fits when writing SQL that query derivation cannot express: `JOIN`, subqueries, CTEs, functions, database-specific syntax, or custom filters.

Example query returning an aggregate root:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    @Query("""
        SELECT *
        FROM purchase_order
        WHERE status = :status
        ORDER BY created_at DESC, id DESC
        """)
    List<PurchaseOrder> findByStatusUsingSql(
            @Param("status") String status
    );
}
~~~

Test:

~~~java
@Test
void executesAnnotatedQueryAndMapsAggregateRoot() {
    List<PurchaseOrder> result =
            repository.findByStatusUsingSql("PAID");

    assertThat(result).hasSize(2);
    assertThat(result)
            .extracting(PurchaseOrder::getStatus)
            .containsOnly("PAID");
}
~~~

With the default `RowMapper`, the query must return all columns required by the entity constructor. Properties populated via setters, withers, or field access might not error if absent; missing columns simply leave those properties unset. One-to-one/embedded properties follow specific alias prefix rules. Collection entities such as `List`, `Set`, and `Map` are still loaded via separate queries.

### Testing Named Parameters

Spring Data JDBC supports named parameters. Test values with special characters to confirm inputs bind as values:

~~~java
@Query("""
    SELECT *
    FROM purchase_order
    WHERE status = :status
    """)
List<PurchaseOrder> findByStatusSql(@Param("status") String status);
~~~

Never concatenate user input into SQL strings. Parameter binding protects value inputs; table/column names and SQL keywords cannot be bound as values. If dynamic sorting is needed, map properties through an allowed identifier whitelist.

### Testing @Query Returning Empty and Non-Unique Results

- Unmatched condition: empty `List` or `Optional.empty` per return type.
- Query returning a single entity when data has multiple rows: verify the result-size exception when the method expects a single unique result.
- Query returning an entity: ensure every constructor property appears in the `ResultSet`.
- Query with one-to-one relationships: verify alias prefixes.
- Aggregate with collections: verify generated collection queries and proper hydration of child data.

## 6. Pagination Limitations of String-Based @Query

This is an important distinction: current Spring Data JDBC documentation specifies that string-based `@Query` **does not automatically accept `Pageable`, `PageRequest`, `Sort`, or `Limit` as special parameters** because the framework does not rewrite the SQL string to apply them.

When pagination is needed for `@Query`, write explicit SQL and bind limit/offset:

~~~java
@Query("""
    SELECT *
    FROM purchase_order
    WHERE status = :status
    ORDER BY created_at DESC, id DESC
    LIMIT :limit OFFSET :offset
    """)
List<PurchaseOrder> findPageUsingSql(
        @Param("status") String status,
        @Param("limit") int limit,
        @Param("offset") long offset
);
~~~

The `LIMIT`/`OFFSET` example uses PostgreSQL/MySQL syntax. Adjust for other dialects. If `Page` metadata is needed, write a separate count query:

~~~java
@Query("""
    SELECT COUNT(*)
    FROM purchase_order
    WHERE status = :status
    """)
long countByStatusUsingSql(@Param("status") String status);
~~~

The service can combine content and count into `PageImpl`:

~~~java
public Page<PurchaseOrder> findPage(String status, Pageable pageable) {
    List<PurchaseOrder> content = repository.findPageUsingSql(
            status,
            pageable.getPageSize(),
            pageable.getOffset()
    );

    long total = repository.countByStatusUsingSql(status);

    return new PageImpl<>(content, pageable, total);
}
~~~

In this example, the service must ensure the count query uses the same predicate as the content query. When filters are complex, reuse SQL conditions or build a query fragment so the two queries do not diverge.

If only page data is needed without a total, return a `List` or build a `Slice` using the `pageSize + 1` rule. Avoid running `COUNT(*)` if the caller does not use the total count.

## 7. Testing Projections with RowMapper

Projection DTOs require verifying both SQL aliases and Java mapping. Example DTO:

~~~java
public record OrderSummary(
        Long orderId,
        String status,
        String customerName,
        Long lineCount
) {}
~~~

Repository query:

~~~java
@Query(
    value = """
        SELECT
            po.id AS order_id,
            po.status AS status,
            c.name AS customer_name,
            COUNT(ol.id) AS line_count
        FROM purchase_order po
        JOIN customer c ON c.id = po.customer_id
        LEFT JOIN order_line ol ON ol.order_id = po.id
        WHERE po.status = :status
        GROUP BY po.id, po.status, c.name
        ORDER BY po.id
        """,
    rowMapperRef = "orderSummaryRowMapper"
)
List<OrderSummary> findSummaries(@Param("status") String status);
~~~

Mapper bean:

~~~java
@Configuration
public class OrderSummaryMappingConfiguration {

    @Bean
    RowMapper<OrderSummary> orderSummaryRowMapper() {
        return (rs, rowNum) -> new OrderSummary(
                rs.getLong("order_id"),
                rs.getString("status"),
                rs.getString("customer_name"),
                rs.getLong("line_count")
        );
    }
}
~~~

In a test slice, import the mapping configuration if the bean is not automatically scanned:

~~~java
@DataJdbcTest
@Import(OrderSummaryMappingConfiguration.class)
class OrderSummaryQueryTest {
    // ...
}
~~~

Mapping test:

~~~java
@Test
void mapsJoinedRowsIntoProjection() {
    List<OrderSummary> summaries =
            repository.findSummaries("PAID");

    assertThat(summaries).hasSize(1);

    OrderSummary summary = summaries.getFirst();
    assertThat(summary.orderId()).isEqualTo(100L);
    assertThat(summary.customerName()).isEqualTo("Lan");
    assertThat(summary.lineCount()).isEqualTo(2L);
}
~~~

Fixture data must include the customer and two `order_line` rows for order 100. Also test an order with zero children to verify `LEFT JOIN` and `COUNT(child.id)` returning `0`.

### When Is ResultSetExtractor Needed?

`RowMapper` maps a single `ResultSet` row into a single object. If a one-to-many `JOIN` SQL query returns multiple rows for the same root and you want to group them into one DTO containing a collection, `ResultSetExtractor` fits better because it processes the entire `ResultSet`.

Conceptual example:

~~~java
ResultSetExtractor<List<OrderWithLines>> extractor = rs -> {
    Map<Long, OrderWithLinesBuilder> orders = new LinkedHashMap<>();

    while (rs.next()) {
        Long orderId = rs.getLong("order_id");

        OrderWithLinesBuilder builder = orders.computeIfAbsent(
                orderId,
                id -> new OrderWithLinesBuilder(
                        id,
                        rsValue(rs, "status")
                )
        );

        Long lineId = rs.getObject("line_id", Long.class);
        if (lineId != null) {
            builder.addLine(
                    lineId,
                    rs.getLong("product_id"),
                    rs.getInt("quantity")
            );
        }
    }

    return orders.values().stream()
            .map(OrderWithLinesBuilder::build)
            .toList();
};
~~~

This is illustrative pseudocode because the lambda must handle `SQLException` and the application's concrete builder. When using `ResultSetExtractor`, verify null children, duplicate rows, and ordering. Custom `RowMapper`/`ResultSetExtractor` in Spring Data JDBC also means entity callbacks and lifecycle events are not automatically invoked for custom-mapped results.

## 8. Testing Queries with JOINs and Cardinality

A one-to-many `JOIN` query needs more than a single trivial fixture:

- Root with no children.
- Root with exactly one child.
- Root with multiple children.
- Two roots having children for the same product.
- Joining an additional table without multiplying totals.
- Filtering by the joined table.
- Sorting and paginating by root, not by joined rows.

For example, summary SQL should use `LEFT JOIN` if roots with zero children must still appear:

~~~sql
SELECT
    po.id,
    COUNT(ol.id) AS line_count,
    COALESCE(SUM(ol.quantity * ol.unit_price), 0) AS total_amount
FROM purchase_order po
LEFT JOIN order_line ol ON ol.order_id = po.id
GROUP BY po.id;
~~~

If adding a `JOIN` to a `payment` table, do not recompute line `SUM` on rows multiplied by payment rows. Aggregate lines and payments in separate subqueries before joining results by `order_id`.

Tests must assert aggregated totals, not just DTO count. Cardinality bugs can return the right row count while inflating monetary sums.

## 9. Testing @Query with Custom RowMapper and Lifecycle

Spring Data JDBC lets you specify a custom `RowMapper` or `ResultSetExtractor` via `@Query`. However, custom mapping is designed to give the application control over constructing results; entity callbacks and lifecycle events do not run automatically for results mapped by these custom mappers/extractors.

Therefore:

- Using custom mappers for DTOs/read models is natural.
- If a query returns entities and relies on callbacks, auditing, or lifecycle behavior, check carefully whether a custom mapper alters expectations.
- Do not use a custom query projection as an aggregate loading path while assuming the full aggregate lifecycle runs just like default repository finds.
- Test callbacks/events separately if the use case depends on them.

## 10. Test Slice with @DataJdbcTest

`@DataJdbcTest` is the test slice for Spring Data JDBC. It typically configures:

- A DataSource and embedded database if present on the classpath.
- Spring Data JDBC repositories.
- `JdbcTemplate`.
- A transaction per test that rolls back when the test finishes.

Regular components are not necessarily scanned as in a full application context. If a custom `RowMapper`/configuration is not loaded, use `@Import` to bring the required configuration into the test context.

Example:

~~~java
@DataJdbcTest
@Import(OrderSummaryMappingConfiguration.class)
class PurchaseOrderQueryTest {

    @Autowired PurchaseOrderRepository repository;
    @Autowired JdbcTemplate jdbcTemplate;

    @BeforeEach
    void setUp() {
        // Insert fixtures using JdbcTemplate.
    }
}
~~~

Default test transaction notes:

- Fixture data inserted in the test transaction rolls back when the test finishes.
- Repository queries inside the test see the fixtures because they share the same transaction.
- If testing transaction commit/rollback of an application service through its proxy, structure the test so the outer test transaction does not mask the outcome.
- `@DataJdbcTest` does not test HTTP/controller behavior; use `@SpringBootTest` or an appropriate web slice for that layer.

## 11. Testing Against a Production-Compatible Database

Embedded databases help with basic mapping and query tests, yet SQL dialects, paging, type conversions, and execution plans can differ from production.

If production uses PostgreSQL, MySQL, SQL Server, or Oracle, add integration tests on the exact engine/driver. Testcontainers can spin up temporary databases and supply JDBC URLs to the Spring context.

PostgreSQL example with `DynamicPropertySource`:

~~~java
@Testcontainers
@DataJdbcTest
class PurchaseOrderPostgresQueryTest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("sales")
                    .withUsername("app")
                    .withPassword("secret");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        registry.add(
                "spring.datasource.driver-class-name",
                postgres::getDriverClassName
        );
    }
}
~~~

Ensure migrations/schema SQL execute on the container before tests run. Container configuration and Testcontainers annotations can vary across Spring Boot/Testcontainers versions; adjust dependencies and package imports to match your project.

For projections/SQL JOINs, testing on the real engine catches alias/type mismatches. For paging, test sorting, limit/offset, and counts on the target dialect. For Single Query Loading, use a supporting database/dialect and inspect the actual SQL.

## 12. Measuring Query Counts Instead of Only Checking Results

A query test can return accurate data while silently generating unwanted SQL statements. When controlling N+1 queries or count queries is the goal, measure actual executed statements.

You can use `datasource-proxy`, P6Spy, or test instrumentation to count statements. Avoid brittle assertions on every internal SQL string if the framework might alter SQL across minor versions; instead check key behaviors such as:

- Derived `Page` queries issue a data query and a count query when needed.
- `Slice` fetches `pageSize + 1` rows to determine `hasNext`.
- `List` + `Pageable` returns page-range content without needing count metadata.
- String `@Query` does not automatically apply `Pageable`; SQL must include limit/offset if needed.
- Custom projections fetch only columns needed by the read model.
- Aggregate queries do not issue extra unexpected statements for collections.

When asserting exact statement counts, isolate fixtures and exclude migration/setup queries from the measurement. Reset the query counter right before the method under test.

## 13. Streaming Queries and Closing Resources

Spring Data JDBC lets query methods return a `Stream` to consume results incrementally. Streams keep a connection open; callers must close the stream to prevent connection leaks.

~~~java
@Query("SELECT * FROM purchase_order WHERE status = :status")
Stream<PurchaseOrder> streamByStatus(@Param("status") String status);
~~~

Usage:

~~~java
try (Stream<PurchaseOrder> orders =
             repository.streamByStatus("ARCHIVED")) {

    orders.forEach(this::process);
}
~~~

Do not return a stream outside a service and let callers hold it open arbitrarily. The connection remains checked out while the stream is active. If per-element processing involves network calls or long durations, consider batch/chunk processing rather than holding a database connection open for the entire workflow.

Streaming tests should confirm results are read and the stream is closed. Do not attempt to read further after closing the stream.

## 14. Common Mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Derived query cannot find property | Method name uses a property absent from aggregate root | Check property names and mapping |
| Derived query needs JOIN but does not generate JOIN | JDBC derivation is restricted to properties usable without JOIN | Use `@Query` or a custom fragment |
| Page content is right yet `totalElements` is wrong | Count query or fixture/filter mismatch | Verify predicates and count query |
| Slice has no `totalPages` | `Slice` only provides `hasNext` | Use `Page` when totals are truly needed |
| `@Query` ignores `Pageable` | String-based JDBC queries do not rewrite SQL automatically | Bind limit/offset in SQL |
| `@Query` entity mapping constructor error | Missing constructor property columns | `SELECT` all required columns with proper aliases |
| `@Query` JOIN misses collections | Default `RowMapper` loads collections via separate queries | Check mapping or use DTO/custom extractor |
| Projection DTO alias error | `RowMapper` reads nonexistent column name | Align SQL aliases and mapper |
| Custom projection skips callbacks | Custom `RowMapper`/`ResultSetExtractor` does not invoke lifecycle callbacks/events | Do not rely on callbacks for custom read mappings |
| Pages duplicate/skip rows across calls | Unstable sort when sort values tie | Add ID as tie-breaker |
| Test passes on H2 but fails in production | Dialect or SQL type differences | Run Testcontainers with production engine |
| `@DataJdbcTest` misses custom mapper bean | Test slice does not scan regular configurations | Use `@Import` |
| Stream exhausts connection pool | Stream left unclosed | Use `try-with-resources` |
| JOIN produces wrong count/sum | Multiple collections cause Cartesian multiplication | Aggregate each collection before joining |

## 15. Workflow for Testing a New Repository Query

1. **Identify query kind:** derived query, annotated SQL, or custom fragment.
2. **Check derivation scope:** does the property live directly on the aggregate root without needing a JOIN?
3. **Identify return type:** entity, DTO, `List`, `Slice`, `Page`, or `Stream`.
4. **Prepare fixtures with varied cardinality:** 0, 1, many results, and tied sort keys.
5. **Test filter conditions:** exact results by ID/property, including null and collection parameters if applicable.
6. **Test sorting:** accurate and deterministic order.
7. **Test pagination:** content, offset, limit, `hasNext`, `totalElements`, and count semantics.
8. **Test `@Query` mapping:** constructor fields, aliases, one-to-one prefixes, and collection behavior.
9. **Test projections:** `RowMapper`/`ResultSetExtractor` produces accurate DTOs; verify aggregate count/sum and `LEFT JOIN`.
10. **Test target database:** run migrations and integration tests with the exact dialect/driver.
11. **Measure SQL when needed:** query count, execution plan, result rows, and latency.
12. **Close resources:** verify streams and JDBC resources are properly released.

### Quick Decision Table

| Testing Goal | Mechanism |
|---|---|
| Filter by aggregate root property | Derived query |
| Conditions with JOIN/CTE/functions | `@Query` or repository fragment |
| Need full aggregate | Return aggregate root and verify owned entities |
| Need only a few columns for a read model | DTO + custom `RowMapper`/`ResultSetExtractor` |
| Need total result/page count | `Page` |
| Need only to know if more data follows | `Slice` |
| Need only one page's content | `List` + `Pageable` on a derived query |
| Custom SQL needs bounded results | Bind `LIMIT`/`OFFSET` in SQL |
| Large datasets consumed incrementally | `Stream` and `try-with-resources` |
| Need to verify real SQL dialect | Integration test with production-compatible database |

**Core takeaway:** derived queries suit simple conditions on the aggregate root; `@Query` handles explicit SQL, yet string-based queries do not automatically apply `Pageable`/`Sort`/`Limit`; projection DTOs need `RowMapper`/`ResultSetExtractor` with matching aliases and types; `Page` needs totals, whereas `Slice` only checks if more data follows. Test results, counts, sorting, mapping, query bounds, and the real database engine.
