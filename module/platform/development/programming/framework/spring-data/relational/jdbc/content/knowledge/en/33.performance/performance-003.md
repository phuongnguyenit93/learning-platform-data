# Measuring Delete–Reinsert Costs for Child Entities in Large Aggregates

Spring Data JDBC manages data around aggregate roots. When saving a new aggregate, the framework inserts the root and then inserts referenced entities. When saving an existing aggregate, Spring Data JDBC deletes referenced entities, updates the aggregate root, and reinserts child entities according to the current state of the object passed in.

This approach allows the framework to translate the in-memory aggregate state into the corresponding database state without tracking every granular change. However, for large aggregates, the cost can be high: modifying just one root property or a single child row can cause the entire set of child entities to be deleted and reinserted.

To decide whether a design change is needed, you must understand the exact scope of the operation, estimate write amplification, measure on representative datasets, and compare alternatives that still preserve business invariants.

## 1. Current Aggregate Save Behavior

Suppose a `PurchaseOrder` has an `OrderLine` collection. When creating a new order, Spring Data JDBC inserts the aggregate root and then inserts the order lines.

When the aggregate already exists, the conceptual save flow is:

1. Delete the referenced entities belonging to the aggregate.
2. Update the aggregate root row.
3. Reinsert the referenced entities according to the current collection state.

This happens because Spring Data JDBC does not retain a previous snapshot of the aggregate to diff each child row. The framework receives the new object and must bring the database to the state described by that object.

~~~mermaid
flowchart TD
    A[repository.save(existingAggregate)] --> B[Identify existing aggregate]
    B --> C[Delete referenced entities]
    C --> D[Update aggregate root]
    D --> E[Reinsert all child entities]
    E --> F[Transaction commit]
~~~

This is the behavior described in the Spring Data Relational documentation under Persisting Entities. For a new aggregate, the framework inserts the root and then inserts referenced entities; for an existing aggregate, referenced entities are deleted and reinserted after the root is updated.

A key point is that this applies to **referenced entities belonging to the aggregate**, such as collections mapped with `@MappedCollection`. `@Embedded` properties are stored as columns in the same table as their owning entity, so they do not create separate child rows to be deleted and reinserted this way.

## 2. Example of an Aggregate with a Large Collection

Suppose a sales system has this aggregate:

~~~java
import java.math.BigDecimal;
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        BigDecimal total,
        @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
        List<OrderLine> lines
) {}

public record OrderLine(
        String sku,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

The root and child tables can be designed as follows:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    total DECIMAL(18, 2) NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Suppose an order has 2,000 lines. When a service reads the order, changes `status`, and calls `repository.save(order)`, Spring Data JDBC does not only update `status` on the `purchase_orders` row. The referenced `order_lines` rows are also deleted and reinserted according to the collection passed in.

Even when only a single line changes `quantity`, the framework does not automatically deduce that only that single row needs an update. It does not track prior state to compute a diff.

## 3. Estimating Write Amplification

Let:

- N be the total number of directly and indirectly referenced child entities in the aggregate.
- K be the number of child entities that actually changed between the old and new state.
- K can be much smaller than N.

For a save on an existing aggregate, row-level child work is approximately:

- N rows deleted.
- N rows reinserted.
- Root updated.

Thus, the number of child rows written can be close to 2N, even if only K rows actually changed.

For example:

| Total child rows N | Child rows actually changed K | Child rows deleted | Child rows inserted | Total child row changes |
|---:|---:|---:|---:|---:|
| 10 | 1 | 10 | 10 | 20 |
| 100 | 1 | 100 | 100 | 200 |
| 1,000 | 1 | 1,000 | 1,000 | 2,000 |
| 5,000 | 1 | 5,000 | 5,000 | 10,000 |
| 10,000 | 10 | 10,000 | 10,000 | 20,000 |

This table models estimated affected rows, not a guarantee of exact SQL statement counts or network round trips. Drivers, dialects, batching, mapping strategies, and aggregate structure can change the actual statement count.

Child write amplification can be expressed as a ratio:

\[
WA = \frac{\text{Child rows deleted + inserted}}{\text{Child rows actually changed}}
\]

If only one line changes in a 5,000-line aggregate, the simple model shows 10,000 child row changes for one logical change. This ratio is not a standard Spring Data metric; it is a way to quantify redundant writes in a use case.

If an aggregate has multiple nested collections, N must count all referenced entities across the entire aggregate tree, not just collections directly visible on the root.

## 4. Costs Extend Beyond SQL Statement Counts

Deleting and reinserting child rows can generate multiple kinds of cost:

- **Database CPU**: evaluating delete predicates, inserts, constraint checks, and type conversions.
- **I/O**: reading/writing data pages, indexes, and transaction logs.
- **Index maintenance**: removing old entries and inserting new entries for every relevant index.
- **Foreign key checks**: validating references on insert; deletes can be blocked if another table references a child.
- **Triggers**: DELETE/INSERT triggers can fire again even when the final data is unchanged.
- **Audit tables**: triggers or audit logic can write additional history rows for every delete/insert.
- **Locking**: transactions hold locks longer, increasing wait times and contention.
- **Transaction log/WAL**: increased log volume, potentially affecting replication and backups.
- **Network and driver overhead**: repeated parameter binds/executions or batches can raise communication costs.
- **Connection pool usage**: longer transactions hold connections longer.

An aggregate with 5,000 child rows and three indexes on the child table does not only generate 10,000 row changes. It also generates work across indexes, constraints, triggers, and transaction logs.

## 5. Delete and Reinsert Can Affect External Foreign Keys

In the aggregate model, referenced entities belong to the lifecycle of the root. Spring Data JDBC assumes these entities are managed through the aggregate root. If another independent table directly references a child row, deleting children can cause issues:

- A foreign key with `ON DELETE RESTRICT` can cause the save operation to fail.
- `ON DELETE CASCADE` can delete additional dependent data.
- If a child is reinserted with a new key, old references may no longer be valid.
- Audit triggers may record deletes/inserts even when the user only edited a single property.

This is usually a sign to revisit aggregate boundaries. If a child entity must be referenced and managed independently, it should probably be its own aggregate root, with other aggregates storing its ID or an `AggregateReference` to it.

Do not rely on a child's ID as a stable independent identifier if the child's persistence design belongs to an aggregate collection and may be replaced during a save.

## 6. When Does This Cost Matter?

Not every aggregate needs optimization. For small collections, simple persistence and short transactions can be better than manually managing individual child rows.

The cost becomes worth investigating when one or more of these signs appear:

- Aggregates commonly have hundreds or thousands of child entities.
- Use cases frequently modify only root scalars yet save aggregates with large collections.
- Requests change just one child yet rewrite the entire collection.
- The child table has many indexes, triggers, or foreign keys.
- Saving the aggregate sits on a latency-sensitive request path.
- Many concurrent transactions update large aggregates.
- Transaction log volume, replication lag, or database write IOPS spike unusually.
- Connection pools are held for long periods due to large saves.
- Batch jobs save many aggregates containing large collections.

Start with real measurements. An aggregate with 1,000 child rows might still meet requirements on a fast database under low load; an aggregate with 100 child rows under heavy triggers, indexes, and high concurrency might already cause problems.

## 7. Measuring the True Cost of a Save

To evaluate the impact, separate three questions:

1. How many persistence operations does Spring Data JDBC generate and execute?
2. How many rows does the database actually delete/insert/update, and how long does it take?
3. What are the latency and throughput of the entire use case, including transaction commit?

Do not measure only a `repository.save` call inside a `@Transactional` method and treat that as total time. Inside the method, the transaction may not have committed yet. Measure from a caller outside the Spring proxy to include commit/rollback duration.

### Designing Representative Datasets

Create aggregates with varying cardinalities:

| Tier | Child rows per aggregate | Purpose |
|---|---:|---|
| Small | 10 | Baseline |
| Medium | 100 | Common load |
| Large | 1,000 | Identify where costs begin rising |
| Very large | 5,000 | Observe pronounced write amplification |
| Extreme | 10,000 or more | Determine operational limits if business data reaches this scale |

Do not test only an average-sized aggregate. Real distributions often have many small aggregates and some very large ones; check tail sizes as well.

### Scenarios to Measure

Using the same aggregate and cardinality, measure separately:

1. **Save without changing children**: modify one property on the root, keeping the collection unchanged.
2. **Save changing one child**: change only `quantity` on one `OrderLine`.
3. **Save changing a small fraction**: change 1% of child rows.
4. **Save replacing the entire collection**: change all children.
5. **Targeted SQL**: update just that one child row directly, if this option is under consideration with concurrency/invariants handled.
6. **Split aggregate**: save the root separately and update the child aggregate independently, if the domain model permits.

Scenarios 1 and 2 are especially revealing: if child persistence uses delete/reinsert, child row changes can be nearly identical even though one case changes no children and the other changes only one line.

### Metrics to Collect

- Total use case duration, including transaction commit.
- p50, p95, and p99 latency.
- Throughput in requests/second.
- SQL statement count.
- Batch execution counts and batch sizes, if applicable.
- Child rows deleted and inserted.
- Database CPU and I/O.
- Transaction log/WAL volume.
- Lock waits, deadlocks, and transaction duration.
- Connection pool active/pending connections.
- Optimistic locking or constraint error counts.

SQL statement count does not equal row count. A single DELETE can remove 5,000 rows; a batch insert can insert hundreds of rows in one execute call. Measure both statements and affected rows.

## 8. Tools for Observing SQL and Database Activity

In development or test environments, you can use:

- Spring JDBC/Spring Data SQL logs to inspect statement shapes.
- A DataSource proxy to count queries, batches, and elapsed times.
- P6Spy to observe executed SQL during debugging.
- Micrometer and connection pool metrics to track latency, active connections, and pending requests.
- Native DBMS tools to inspect query statistics, lock waits, I/O, and transaction logs.
- EXPLAIN or execution plans to see how the database executes DELETE/INSERT.

Do not leave full SQL/parameter logging enabled during formal benchmarks because logging adds overhead and skews measurements. Run a separate pass to verify SQL, then disable verbose logging during performance runs.

For a DELETE such as:

~~~sql
DELETE FROM order_lines
WHERE order_id = ?;
~~~

check the index on `order_id`. Without a suitable index, the database may have to scan many rows to find child rows. For INSERTs, check indexes on the primary key, unique keys, and any other indexed columns.

## 9. Repeatable Benchmark Procedure

A valid benchmark should hold conditions steady:

1. Use the same DBMS and a version close to deployment.
2. Use the actual JDBC driver and connection pool settings.
3. Use production-like schemas, indexes, triggers, and foreign keys.
4. Load datasets with realistic cardinality and distribution.
5. Warm up the application and database before collecting metrics.
6. Run each scenario many times rather than taking a single run.
7. Separate aggregate read time from save time if analyzing individual phases.
8. Measure the entire service call from outside the transaction proxy to include commit.
9. Run both single-threaded and concurrent loads.
10. Record p50/p95/p99, affected rows, SQL/batch counts, and database metrics.
11. Re-run benchmarks after schema/index or code changes.
12. Compare alternatives under the same dataset and load conditions.

Do not benchmark on a production database with live data unless an approved procedure allows it. Use a test database with equivalent sizing to avoid disrupting live user workloads.

## 10. Example Benchmark Setup

You can write a dedicated benchmark service to exercise aggregate variants. Timing must sit in a caller outside the transactional service:

~~~java
@Service
public class OrderSaveService {

    private final PurchaseOrderRepository repository;

    public OrderSaveService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long orderId, String status) {
        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow();

        PurchaseOrder changed = new PurchaseOrder(
                current.id(),
                current.version(),
                current.orderNumber(),
                status,
                current.total(),
                current.lines()
        );

        return repository.save(changed);
    }
}
~~~

Benchmark caller:

~~~java
long started = System.nanoTime();

PurchaseOrder saved = orderSaveService.changeStatus(orderId, "PROCESSING");

long elapsedNanos = System.nanoTime() - started;
~~~

When `orderSaveService` is a Spring bean invoked via a proxy, the call returns after the transaction interceptor finishes commit/rollback. This snippet illustrates the measurement boundary only; a real benchmark needs warmup, multiple iterations, data distributions, and percentile statistics. Do not treat a simple loop as a final microbenchmark, because JIT, connection pool, database cache, and garbage collection can distort results.

## 11. Comparing Aggregate Save with Targeted Child Update

Suppose you only need to change the `quantity` of a single order line. Saving the aggregate can delete and reinsert the entire collection. A direct SQL statement can update just one row:

~~~sql
UPDATE order_lines
SET quantity = :quantity
WHERE order_id = :orderId
  AND line_no = :lineNo;
~~~

In terms of row count, a targeted update touches one child row instead of deleting and reinserting N child rows. However, the two approaches are not equivalent in semantics.

When using direct SQL, the application must manually ensure:

- The line belongs to the right order.
- The quantity is valid according to domain invariants.
- The order total is recalculated or updated properly.
- The aggregate root version is checked/incremented if the version protects the whole aggregate.
- Auditing and domain events are handled.
- A transaction wraps all related changes.
- Any `PurchaseOrder` object already loaded in memory is not reused with stale state.

Example update that checks the root version:

~~~sql
UPDATE purchase_orders
SET version = version + 1
WHERE id = :orderId
  AND version = :expectedVersion;
~~~

Then update the child only when the version check succeeds, within the same transaction. If any step fails, roll back everything. The exact order and statements must match domain invariants; do not copy this example as a complete solution for every aggregate.

If you skip the version check or update the child without locking/checking the root, two transactions can modify different parts of the same aggregate without detecting a conflict.

## 12. Option 1: Keep the Aggregate and Accept Delete/Reinsert

This is the simplest option when:

- Collections are small or medium-sized.
- Save frequency is low.
- Transactions are short.
- No external tables depend on child IDs.
- Indexes, triggers, and constraints do not create significant overhead.
- Whole-aggregate consistency matters more than per-row optimization.

Pros:

- Simple domain code.
- Spring Data JDBC manages the entire aggregate.
- Minimal custom SQL.
- Root optimistic locking is built into the save path.
- No need to implement a diff algorithm between old and new states.

Cons:

- Write amplification grows with aggregate size.
- Triggers/audits may re-run for unchanged rows.
- Many child rows lengthen transactions.
- Can cause lock contention and increased transaction logs.

Do not optimize prematurely if metrics show the current save path meets SLOs and expected load.

## 13. Option 2: Reduce Aggregate Size

If a collection can grow unboundedly, re-examine aggregate boundaries. An aggregate should group data that must be protected by the same invariants and the same transaction, not necessarily every piece of data with a foreign key relationship.

For example, a `PurchaseOrder` can keep core attributes and a reference to an independently managed `OrderLine` collection if the business rules allow.

Instead of storing child objects inside the aggregate, the root can hold IDs or an `AggregateReference` to another aggregate. Updating one child aggregate then no longer requires resaving the entire root.

Evaluate:

- Does the child have an independent lifecycle?
- Can the child be updated without loading the root?
- Which invariants must be enforced atomically between root and child?
- Are cross-aggregate transactions required?
- Should deleting the root still automatically delete children, or is a separate process required?
- Does the child aggregate need its own lock/version?

Splitting an aggregate lowers root save costs but shifts consistency responsibilities to an application service or different transaction boundaries. Do not split solely because row counts are large if the domain still requires all children to change atomically with the root.

## 14. Option 3: Use Custom SQL for Small Updates

When the aggregate boundary still makes sense yet certain use cases update a single child row, you can use a custom repository fragment, `JdbcTemplate`, or MyBatis to write targeted SQL.

Example:

~~~java
public interface OrderLineOperations {
    int updateQuantity(
            Long orderId,
            Integer lineNo,
            int quantity
    );
}
~~~

The implementation uses `NamedParameterJdbcTemplate` or an appropriate mapper. The service must declare `@Transactional` and coordinate version, totals, auditing, and invariants.

Pros:

- Writes only the rows that actually need changing.
- Can reduce index maintenance and transaction logs.
- Can use atomic SQL predicates.
- Fits well-designed bulk operations.

Costs:

- Must maintain SQL alongside schema and dialect changes.
- Must manually enforce optimistic locking when changing the aggregate.
- Callbacks/auditing from aggregate save do not run automatically.
- Must reload or synchronize in-memory objects.
- Must test concurrency, rollbacks, and all other write paths.

This is a targeted optimization for specific use cases. Do not rewrite all CRUD into custom SQL just because one collection is large.

## 15. Option 4: Use Bounded Bulk Operations

If business logic updates many child rows under the same condition, a single UPDATE can be more efficient than loading the whole aggregate and saving it:

~~~sql
UPDATE order_lines
SET unit_price = :newPrice
WHERE order_id = :orderId
  AND sku = :sku;
~~~

Or updating multiple rows by a list of IDs. However, bulk SQL usually bypasses entity callbacks and the aggregate lifecycle. Check:

- Does the root version need incrementing?
- Do root totals or status need updating?
- Does auditing need to record every child or just a single bulk event?
- Is row-level optimistic locking required?
- Could the ID list exceed database bind parameter limits?
- Should updates be chunked to avoid overly large transactions?

Bulk operations can cut round trips but raise consistency complexity. Define the contract clearly before implementing.

## 16. Distinguishing Child Entities, Embedded Objects, and AggregateReference

Not every nested property incurs delete/reinsert overhead like referenced entities.

| Mapping | Storage | Impact on root save |
|---|---|---|
| `@Embedded` | Columns on the same table as the root | Embedded values are saved with the root row |
| `@MappedCollection` | Child entity in a separate table, owned by the aggregate | Referenced entities are deleted and reinserted when saving an existing aggregate |
| `AggregateReference` | ID reference to another aggregate | Does not pull the referenced aggregate into the root's save |
| Simple ID property | ID value stored in a column | Does not turn the referenced entity into a child of the aggregate |

If a large collection truly consists of aggregate-owned children, delete/reinsert is a behavior you must account for in your design. If it is a relationship between two independent aggregates, using IDs/`AggregateReference` better matches domain boundaries.

## 17. Impact of Optimistic Locking

When an aggregate root uses `@Version`, Spring Data JDBC checks the version when updating the root. This detects two transactions modifying the same aggregate based on a stale version.

However, do not assume every child row has an independent version or can be updated directly without protecting the root. The root's version protects the aggregate according to the framework's save rules.

When replacing aggregate save with custom SQL:

- Check the expected version in the WHERE clause.
- Increment the version consistently.
- Check the update count.
- Perform child changes within the same transaction.
- Roll back if the root version no longer matches.
- Do not continue saving an old object with a stale version after direct SQL.

If two transactions modify two different children of the same root, the domain might require rejecting one because the whole aggregate is one consistency unit. If independent updates should be allowed, that may signal that the child should be split into a separate aggregate.

## 18. Indexes and Schema for Child Tables

When Spring Data JDBC deletes children by the root's foreign key, the delete predicate typically filters on the parent reference column, such as `order_id`.

The child table should have an index/primary key aligned with queries and constraints:

~~~sql
CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

A composite primary key leading with `order_id` can support querying/deleting by `order_id` in many DBMSs. Still, execution plans and index strategies must be verified on the actual database engine.

If the child table has extra indexes on `sku`, `status`, or `created_at`, every delete/reinsert incurs maintenance on those indexes. Do not drop indexes arbitrarily just to speed up saves; weigh the read queries and constraints they support.

## 19. Considering Triggers, Audits, and Dependent Data

Delete/reinsert can fire row-level triggers. If triggers write audit logs, update counters, or emit signals, a single save can produce many auxiliary records even for unchanged child content.

Check:

- `BEFORE`/`AFTER` DELETE and INSERT triggers.
- `ON DELETE CASCADE` on foreign keys.
- Audit tables and CDC/change data capture.
- Logical replication or binlog volume.
- Materialized views or summary tables maintained by triggers.
- External processes reading change streams.

If one root save causes CDC to emit thousands of delete/insert events, downstream systems can bear higher costs than the original database transaction.

Determine whether consumers care about final state or individual row events. If you need a semantic event like "order changed", do not infer business events from technical row deletes/inserts.

## 20. Evaluating with SLOs and Operational Costs

Lower numbers on every metric do not automatically mean a better architecture. Compare options against concrete objectives:

| Criterion | Question to answer |
|---|---|
| Latency | Do save p95/p99 stay within SLOs? |
| Throughput | Can the database handle expected concurrent saves? |
| Write volume | How many child rows are written per logical change? |
| Locking | Do lock waits or deadlocks increase? |
| Transaction log | How much does WAL/binlog grow when saving large aggregates? |
| Connection pool | Do transactions hold connections too long? |
| Correctness | Are invariants, versions, audits, and rollbacks still sound? |
| Complexity | How much custom SQL and manual coordination must be maintained? |
| Portability | Does it lock into a specific DBMS or driver? |
| Operations | Is it easy to observe, alert on, and recover from failures? |

A targeted SQL solution can lower latency while significantly increasing maintenance overhead. Choose it only when measured improvements solve a real problem and tests protect semantics.

## 21. Decision Table

| Situation | Reasonable starting direction |
|---|---|
| Aggregate has 5–20 child rows, infrequent saves | Keep `repository.save` simple |
| Aggregate has 100–500 child rows, frequent changes | Measure SQL/latency and identify hot paths |
| Aggregate has thousands of child rows, only root scalars change | Consider separating read/write use cases or shrinking the aggregate |
| Frequently updating a single child row | Consider targeted SQL with version/invariants |
| Child has independent lifecycle and separate updates | Consider making the child its own aggregate root |
| Child must be atomically consistent with root | Keep in aggregate; measure costs and optimize deliberately |
| Child table has heavy triggers/audits/CDC | Measure side effects and downstream load too |
| Custom SQL cuts time but bypasses domain rules | Do not adopt until semantics are protected |

## 22. Pre-Optimization Measurement Checklist

Before changing persistence strategies, record:

- Typical and maximum child row counts of the aggregate.
- Save frequency by use case.
- Share of saves modifying only the root, one child, or many children.
- Actual deleted/inserted row counts.
- SQL statement and batch execution counts.
- Transaction and commit durations.
- p50/p95/p99 latency.
- Indexes, triggers, foreign keys, and audit/CDC hooks.
- Concurrency levels and lock waits.
- Version/optimistic locking behavior.
- Handling of caches and already-loaded objects.
- Benchmark results of alternative approaches.
- Code/test/maintenance cost of custom SQL.

Do not keep full SQL logging permanently enabled in production as your primary measurement tool. Use proper instrumentation and enable verbose logs only during controlled debugging windows.

## 24. Key Principles to Remember

- When saving a new aggregate, Spring Data JDBC inserts the root and then inserts referenced entities.
- When saving an existing aggregate, Spring Data JDBC deletes referenced entities, updates the root, and reinserts referenced entities.
- The framework does not keep old aggregate state to diff individual child rows; changing a single child can still rewrite the entire collection.
- With N child rows, you can estimate roughly N deletes and N inserts at the row level; actual SQL statement/batch counts depend on the driver, mapping, and database.
- Costs include index maintenance, foreign key checks, triggers, audits, transaction logs, locks, and connection pool occupancy.
- `@Embedded` lives in the same table as the root, unlike `@MappedCollection`, which uses a child table.
- `AggregateReference` represents a reference to another aggregate and does not pull that aggregate into the root's save.
- Measure on realistic cardinalities and data distributions; collect row counts, statement/batch counts, p50/p95/p99, and database metrics.
- Measure the full service call from outside the transaction proxy to include commit.
- Targeted SQL can reduce row changes but requires manually preserving versions, invariants, audits, callbacks, and transactions.
- If a child has an independent lifecycle, consider splitting aggregates; if atomic consistency with the root is required, keep the aggregate boundary and measure the cost.
- Optimize only after benchmarks prove that write amplification impacts latency, throughput, or operational costs.

Spring Data JDBC chooses to persist aggregates based on the complete state of the object, so saving a large aggregate can delete and reinsert many child entities even when only a small part changes. Quantify written rows and database costs before choosing another approach. Whenever using targeted updates or splitting aggregates, preserve the invariants, optimistic locking, and transaction semantics that the standard save path provides.
