# Combining `And`, `Or`, and Understanding Condition Precedence

In **Spring Data JDBC**, repository method names can combine multiple conditions using the `And` and `Or` keywords. Spring Data parses the method name, identifies the entity properties, and generates the corresponding SQL query. When a method uses both keywords, how the conditions are grouped determines which records are returned.

The key rule to remember is: **conditions joined by `And` are grouped into clauses, and those clauses are joined together by `Or`**. Therefore, a method like `findByStatusAndPriorityOrAssignedTeam` means:

```text
(status = ? AND priority = ?) OR assignedTeam = ?
```

This also matches standard SQL operator precedence: `AND` is evaluated before `OR`. However, when business logic requires a different grouping, method names do not offer arbitrary parenthesis syntax. In that case, use `@Query` with explicit parentheses.

## 1. Running Example: Searching Support Tickets

Suppose a system tracks support tickets (`SupportTicket`). Each ticket has a status, priority level, and assigned team.

Illustrative DDL:

```sql
CREATE TABLE support_tickets (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(180) NOT NULL,
    status VARCHAR(30) NOT NULL,
    priority VARCHAR(20) NOT NULL,
    assigned_team VARCHAR(60) NOT NULL
);
```

Entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("support_tickets")
public record SupportTicket(
        @Id Long id,
        String title,
        String status,
        String priority,
        String assignedTeam
) {}
```

With the default naming strategy, `assignedTeam` maps to the `assigned_team` column. In derived query method names, we use the **Java property** `assignedTeam`; in hand-written SQL, we use the **physical column name** `assigned_team`.

Repository:

```java
import java.util.List;
import org.springframework.data.repository.ListCrudRepository;

public interface SupportTicketRepository
        extends ListCrudRepository<SupportTicket, Long> {

    List<SupportTicket> findByStatusAndPriorityOrAssignedTeam(
            String status,
            String priority,
            String assignedTeam
    );
}
```

Spring Data does not require you to write an implementation for this method manually. When initializing the repository, the framework parses the method name and builds a query matching `SupportTicket`'s metadata.

## 2. `And`: All Conditions in the Group Must Be True

Method:

```java
List<SupportTicket> findByStatusAndPriority(
        String status,
        String priority
);
```

Logical meaning:

```text
status = :status AND priority = :priority
```

Equivalent SQL meaning:

```sql
SELECT id, title, status, priority, assigned_team
FROM support_tickets
WHERE status = ?
  AND priority = ?;
```

If you call:

```java
repository.findByStatusAndPriority("OPEN", "HIGH");
```

a ticket is selected only if it **simultaneously** has `status = 'OPEN'` and `priority = 'HIGH'`. If either condition is false, the ticket is excluded from the results.

`And` is appropriate when a use case requires multiple criteria to be satisfied at once, such as "tickets that are open and have high priority."

## 3. `Or`: Only One Branch Needs to Be True

Method:

```java
List<SupportTicket> findByStatusOrAssignedTeam(
        String status,
        String assignedTeam
);
```

Meaning:

```text
status = :status OR assignedTeam = :assignedTeam
```

Equivalent SQL:

```sql
SELECT id, title, status, priority, assigned_team
FROM support_tickets
WHERE status = ?
   OR assigned_team = ?;
```

With the call:

```java
repository.findByStatusOrAssignedTeam("OPEN", "OPS");
```

a ticket is returned if it is open **or** belongs to the `OPS` team, even if only one of the two conditions is true. If both are true, a row still appears only once in a normal SQL result set.

## 4. Combining Both `And` and `Or`

This is the most common source of confusion. Spring Data parses a derived query into `OrPart` groups; each group contains one or more `Part` conditions joined by `And`.

Example:

```java
List<SupportTicket> findByStatusAndPriorityOrAssignedTeam(
        String status,
        String priority,
        String assignedTeam
);
```

The expression is grouped as:

```text
(status = :status AND priority = :priority)
OR
(assignedTeam = :assignedTeam)
```

Written concisely:

```text
A AND B OR C
```

is interpreted as:

```text
(A AND B) OR C
```

Equivalent SQL meaning:

```sql
SELECT id, title, status, priority, assigned_team
FROM support_tickets
WHERE (status = ? AND priority = ?)
   OR assigned_team = ?;
```

In the actual SQL generated by the framework, parentheses may be formatted differently; what matters is the **condition-grouping semantics**. Standard SQL evaluates `AND` before `OR`, so the unparenthesized expression `status = ? AND priority = ? OR assigned_team = ?` produces the same result.

## 5. Precedence: `And` Groups Before `Or`

You can remember the rule with this table:

| Method name | Grouping | Meaning |
|---|---|---|
| `findByAAndBOrC` | `(A AND B) OR C` | Both A and B are true, or C is true |
| `findByAOrBAndC` | `A OR (B AND C)` | A is true, or both B and C are true |
| `findByAAndBOrCAndD` | `(A AND B) OR (C AND D)` | Either pair of conditions is true |
| `findByAOrBOrC` | `A OR B OR C` | At least one condition is true |
| `findByAAndBAndC` | `A AND B AND C` | All conditions are true |

This matches the parsing structure of method names: each `And` cluster forms a group, and those groups are joined by `Or`. It also aligns with standard SQL precedence rules: `AND` binds tighter than `OR`.

### A counterintuitive reverse example

Method:

```java
List<SupportTicket> findByStatusOrPriorityAndAssignedTeam(
        String status,
        String priority,
        String assignedTeam
);
```

It is **not** interpreted as:

```text
(status = :status OR priority = :priority)
AND assignedTeam = :assignedTeam
```

It is interpreted as:

```text
status = :status
OR
(priority = :priority AND assignedTeam = :assignedTeam)
```

Equivalent SQL:

```sql
WHERE status = ?
   OR (priority = ? AND assigned_team = ?)
```

Therefore, when reading a method that contains both keywords, do not read left-to-right as if all operators had equal precedence. Split it into `And` groups first, then see how those groups are joined by `Or`.

## 6. Illustration with Data and Results

Suppose the table contains the following rows:

| id | status | priority | assigned_team |
|---:|---|---|---|
| 1 | OPEN | HIGH | APP |
| 2 | OPEN | LOW | OPS |
| 3 | CLOSED | HIGH | OPS |
| 4 | CLOSED | LOW | APP |
| 5 | OPEN | HIGH | OPS |

With conditions `status = 'OPEN'`, `priority = 'HIGH'`, `assignedTeam = 'OPS'`:

```text
(status = OPEN AND priority = HIGH) OR assignedTeam = OPS
```

The results include:

- ID 1: `OPEN AND HIGH` is true.
- ID 2: the first branch is false, but `assignedTeam = OPS` is true.
- ID 3: the first branch is false, but `assignedTeam = OPS` is true.
- ID 5: both branches are true; the row still appears only once.

ID 4 satisfies neither branch and is not returned.

If a different grouping is used:

```text
(status = OPEN OR priority = HIGH) AND assignedTeam = OPS
```

the results only include ID 2, ID 3, and ID 5. ID 1 is excluded because it does not belong to `OPS`, even though it satisfies `status = OPEN OR priority = HIGH`. That is a significant business difference caused solely by parenthesis placement.

## 7. Property Names in Methods and Parameter Order

Method names are parsed according to **entity properties**, not SQL column names. Given the entity:

```java
public record SupportTicket(
        @Id Long id,
        String title,
        String status,
        String priority,
        String assignedTeam
) {}
```

the method uses `findByAssignedTeam`, not `findByAssigned_team`. Because the Java property is `assignedTeam`, metadata maps it to `assigned_team` via the naming strategy.

Parameter order follows the order in which properties appear in the method name:

```java
findByStatusAndPriorityOrAssignedTeam(status, priority, assignedTeam)
```

The parameters correspond in order to `status`, `priority`, and `assignedTeam`. When a method has multiple conditions, use clear parameter names and wrap the signature across lines so readers can verify them easily.

If a property name could be parsed ambiguously as a property path, you can use an underscore `_` according to Spring Data's property traversal rules to delimit the path. For basic `And`/`Or` queries, prefer clear property names and avoid overly long method names with segments that might cause confusion.

## 8. When the Method Name Cannot Express the Desired Grouping

Derived query names support combining `And` and `Or`, but they are not a full Boolean expression language. They have no arbitrary parenthesis syntax like:

```text
(A OR B) AND (C OR D)
```

If you write:

```java
findByStatusOrPriorityAndAssignedTeam(...)
```

the result is `A OR (B AND C)`, not `(A OR B) AND C`. You cannot insert parentheses into a method name to alter the grouping.

When business requirements call for explicit grouping, use `@Query` to write SQL and place parentheses directly.

For example, to find tickets whose **status is OPEN or priority is HIGH, while also belonging to team OPS**:

```java
import java.util.List;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.query.Param;

public interface SupportTicketRepository
        extends ListCrudRepository<SupportTicket, Long> {

    @Query("""
        SELECT id, title, status, priority, assigned_team
        FROM support_tickets
        WHERE (status = :status OR priority = :priority)
          AND assigned_team = :team
        """)
    List<SupportTicket> findByStatusOrPriorityWithinTeam(
            @Param("status") String status,
            @Param("priority") String priority,
            @Param("team") String team
    );
}
```

Here `@Query` contains actual SQL, so it must use physical table/column names like `support_tickets` and `assigned_team`. `:status`, `:priority`, and `:team` are bound parameters—user data is never concatenated into the SQL.

The parentheses in SQL express `(A OR B) AND C` accurately, regardless of default precedence. For more complex conditions, explicit parentheses make maintenance easier than a very long method name.

## 9. When Should You Split into Multiple Methods?

If an expression only has a couple of clear clauses, a derived query remains readable. However, when a method name grows long with many branches, consider:

- Splitting into smaller query methods if they represent operations with distinct meanings.
- Using `@Query` with parentheses if you need exact control over the SQL expression.
- Using a repository fragment/`JdbcTemplate` if the query requires dynamic conditions, multiple joins, projections, or specialized optimizations.
- Placing filter-selection logic into an appropriate query builder if conditions depend on many optional parameters.

Do not arbitrarily split a query into multiple repository calls and merge lists in Java. That approach can cause redundant queries, duplicate results, difficult pagination, and reads of data at different points in time. If an expression can run in a single clear SQL statement, it is usually best to let the database apply the conditions and return the needed rows.

## 10. Combining `And`/`Or` with Property Operators

Spring Data query derivation supports many keywords beyond `And` and `Or`, depending on module and version. Common operator examples include:

```java
List<SupportTicket> findByPriorityAndStatusIn(
        String priority,
        Collection<String> statuses
);

List<SupportTicket> findByTitleContainingIgnoreCaseOrAssignedTeam(
        String keyword,
        String team
);
```

The first method means priority equals the passed value **and** status belongs to the passed collection. The second finds titles containing the keyword case-insensitively **or** belonging to the specified team. Operators such as `In`, `Containing`, and `IgnoreCase` apply to their respective properties; `And`/`Or` still combine the predicates.

When adding multiple keywords, parse the method into individual predicates and verify the logical grouping before using it. Do not assume a suffix like `IgnoreCase` changes the precedence of `And`/`Or`; it only changes how that property is compared.

## 11. `NULL` Values and SQL Three-Valued Logic

SQL has three logical states: `TRUE`, `FALSE`, and `UNKNOWN`. Comparing `column = NULL` does not yield `TRUE`; you must use `IS NULL` to check for null. This matters when combining `And` and `Or`.

For instance, if `assigned_team` can be `NULL`, the condition:

```sql
status = 'OPEN' AND assigned_team = 'OPS'
```

will not hold for a row where `assigned_team IS NULL`; the comparison evaluates to `UNKNOWN`. When you need rows without an assigned team, declare a method with the null keyword:

```java
List<SupportTicket> findByAssignedTeamIsNull();
```

Or combine it:

```java
List<SupportTicket> findByStatusAndAssignedTeamIsNullOrPriority(
        String status,
        String priority
);
```

This method means:

```text
(status = :status AND assignedTeam IS NULL)
OR priority = :priority
```

If a property is required, as in the example DDL `assigned_team NOT NULL`, the `IS NULL` branch will yield no rows in valid data. Only use null conditions when the model and schema actually allow that value.

## 12. Common Mistakes When Reading Multi-Condition Methods

| Confusion/Symptom | Cause | Resolution |
|---|---|---|
| `AOrBAndC` is read as `(A OR B) AND C` | Reading left-to-right and ignoring `And` grouping | Read as `A OR (B AND C)` |
| Results include extra rows matching only the last branch | `OR` allows an independent branch to satisfy the query | Check whether that matches the business requirement |
| Using column names in derived query methods | Derived queries reference Java properties | Use entity property names |
| Trying to add parentheses to a method name | Derived queries do not provide arbitrary parenthesis syntax | Write `@Query` with SQL parentheses |
| Parameters passed in wrong order | Method has many predicates; signature is hard to read | Match property order and parameter names |
| Query returns wrong results when nulls exist | SQL uses three-valued logic | Use `IsNull`/`IsNotNull` and check nullability |
| Method too long, hard to maintain | Too many `And`/`Or` and operators | Split queries or use `@Query`/fragment |
| `@Query` reports missing column | Using property name instead of physical column, or missing mapped column | Check DDL, `@Column`, and `SELECT` list |

When debugging, you can enable Spring JDBC logging in development to inspect the executed SQL. Verify the `WHERE` conditions, parentheses, column names, and bound parameters. Avoid relying solely on the method name to guess results if an expression has multiple branches.

## 13. Process for Reading a Complex Method

Given a method:

```java
findByStatusAndPriorityOrAssignedTeamAndTitleContaining(...)
```

read it in sequence:

1. Split at `Or` to form groups.
2. Within each group, split predicates at `And`.
3. Join predicates within each group with `AND`.
4. Join the groups with `OR`.
5. Match each property against the entity, identifying the exact operator and parameter order.
6. Write out the parenthesized Boolean expression on paper before using it in a use case.
7. If the expression does not match the business requirement, switch to `@Query` and write explicit SQL parentheses.

The example above is read as:

```text
(status = ? AND priority = ?)
OR
(assignedTeam = ? AND title CONTAINS ?)
```

This reading method makes the grouping structure immediately visible and reduces mistakes when method names are long.

## 14. Practice Exercise: Checking Condition Precedence

Using the `support_tickets` table and sample data from Section 6, declare two methods:

```java
List<SupportTicket> findByStatusAndPriorityOrAssignedTeam(
        String status, String priority, String assignedTeam);

List<SupportTicket> findByStatusOrPriorityAndAssignedTeam(
        String status, String priority, String assignedTeam);
```

Call both with values `OPEN`, `HIGH`, `OPS`. Record the returned IDs and explain them using the two expressions:

```text
Method 1: (status = OPEN AND priority = HIGH) OR assignedTeam = OPS
Method 2: status = OPEN OR (priority = HIGH AND assignedTeam = OPS)
```

Next, write a `@Query` with the condition:

```text
(status = OPEN OR priority = HIGH) AND assignedTeam = OPS
```

Compare the three result sets. Finally, change one row to have `assigned_team = NULL` if the schema permits, then test an `IsNull` condition to observe SQL three-valued logic.

## 15. Principles to Remember

- `And` combines conditions within the same group; every condition in the group must be true.
- `Or` joins groups; if just one group is true, the row can be selected.
- `findByAAndBOrC` is interpreted as `(A AND B) OR C`.
- `findByAOrBAndC` is interpreted as `A OR (B AND C)`.
- Derived queries use Java properties; SQL in `@Query` uses physical table and column names.
- Method names have no arbitrary parenthesis syntax. Use `@Query` when you need groupings like `(A OR B) AND C`.
- `NULL` values must be handled with `IsNull`/`IsNotNull`; SQL uses three-valued logic.
- For long methods, extract the condition groups into a parenthesized Boolean expression before using them.

In Spring Data JDBC, `And` and `Or` let you describe common filters directly in repository method names. To avoid business-logic discrepancies, always read methods as `And` groups joined by `Or`, verify properties and parameter order, and use `@Query` with explicit parentheses when more complex expressions are needed. Doing so keeps queries clear, verifiable, and free of surprises when real data spans many condition combinations.
