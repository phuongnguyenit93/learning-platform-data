# Trade-offs Between SQL Customizability and Maintenance Cost

When integrating **MyBatis** into a **Spring Data JDBC** application, the development team can pick the right tool for each kind of query: Spring Data JDBC manages aggregates and mapping-driven CRUD operations, while MyBatis provides fine-grained SQL control for complex queries, reporting, or specialized operations.

That customizability comes at a price. Explicitly written SQL must be maintained alongside schemas, dialects, mappings, transactions, caches, and business rules. If both Spring Data JDBC and MyBatis write to the same aggregate without clear boundaries, the application easily ends up with two competing sets of persistence rules.

Therefore, the integration decision is not just about MyBatis offering more flexible SQL. You must weigh **the value of SQL control against the maintenance cost that control introduces**. This lesson explains how to divide responsibilities, identify hidden costs, pick the right scenarios for MyBatis, and keep the system testable when both technologies coexist.

## 1. Why Combine Spring Data JDBC with MyBatis?

Spring Data JDBC focuses on aggregate persistence. The framework reads aggregate root metadata, generates SQL for insert/update/delete, manages IDs, and supports optimistic locking via `@Version`. This approach works well when business logic is modeled around aggregates and saves commonly persist an entire aggregate root.

MyBatis focuses on developer-controlled SQL. Mappers can declare SQL via annotations or XML, use dynamic SQL, join multiple tables, build custom projections, and map results into DTOs. It is helpful when queries need database-specific features or produce result shapes that do not correspond to an aggregate.

An application can use both:

- Spring Data JDBC for standard domain operations such as creating orders, changing status via aggregate behavior, and saving child collections.
- MyBatis for reports, complex searches, multi-table joins, projections, legacy queries, or individually tuned SQL.
- Application services coordinate use cases and transactions, avoiding controllers mixing multiple persistence APIs.

~~~mermaid
flowchart TD
    A[Controller / Job / Message Handler] --> B[Application Service]
    B --> C[Spring Data JDBC Repository]
    B --> D[MyBatis Mapper]
    C --> E[Aggregate Mapping]
    D --> F[Explicit SQL and Result Mapping]
    E --> G[Shared DataSource and Transaction Manager]
    F --> G
    G --> H[(Database)]
~~~

Both tools can access the same database, yet they serve different purposes. Spring Data JDBC manages aggregates based on metadata; MyBatis executes mapper statements defined by the application.

## 2. Benefits of Customizable SQL

MyBatis adds value when SQL statements need to be directly visible and controlled.

### Join and Projection Queries

An admin screen may need data from orders, customers, and payments. The result is a display row, not an aggregate root to save:

~~~sql
SELECT
    o.id AS order_id,
    o.order_number,
    o.status,
    c.display_name AS customer_name,
    p.payment_status,
    o.total
FROM purchase_orders o
JOIN customers c ON c.id = o.customer_id
LEFT JOIN payments p ON p.order_id = o.id
WHERE o.created_at >= #{from}
  AND o.created_at < #{to}
ORDER BY o.created_at DESC, o.id ASC
~~~

MyBatis can map the result directly into a DTO. There is no need to construct an entire aggregate just to render a reporting table.

### Specialized Query Optimization

MyBatis allows the team to explicitly write:

- CTEs and recursive queries.
- Window functions.
- Database-specific JSON operators.
- Complex structured joins and subqueries.
- Conditional bulk updates.
- DBMS-specific hints or syntax when clearly justified.
- Projections selecting only required columns.

This is a genuine benefit once a query has been profiled and explicit SQL helps control the execution plan. However, being able to write complex SQL does not mean you should write complex SQL. An unreadable or untested query rapidly drives up maintenance costs.

## 3. Maintenance Costs Introduced by Explicit SQL

With Spring Data JDBC, part of the SQL is generated from mapping metadata. With MyBatis, the team is directly responsible for more decisions.

| Aspect | Spring Data JDBC | MyBatis |
|---|---|---|
| Basic CRUD SQL | Generated by framework from mapping | Must usually write mapper statements if used for CRUD |
| Property/column mapping | Based on annotations and naming strategies | Based on SQL aliases, `resultMap`, and mapper config |
| Aggregate insert/update | Follows aggregate persistence rules | Mapper simply runs the declared SQL |
| Optimistic locking | Supported in the save path with `@Version` | Must include version in WHERE and increment explicitly |
| Child collections | Managed by framework per aggregate mapping | Must write SQL and operation order manually |
| Generated IDs | Repository returns saved aggregate | Must configure `useGeneratedKeys`/`keyProperty` or database equivalent |
| Dynamic SQL | `Query`/`Criteria` supported within scope | Rich dynamic SQL constructs available |
| Custom joins/projections | May require custom queries or JDBC | Core strength of mapper SQL |
| Portability | Dialect handles framework-generated SQL | Hand-written SQL must be managed per DBMS |
| Maintenance cost | Centralized mapping, little manual CRUD SQL | Many mappers, `resultMap`s, statements, and tests to keep in sync |

MyBatis does not automatically create high cost in every project. Cost depends on statement count, mapping complexity, number of supported DBMS engines, and how much persistence logic is duplicated.

## 4. Establishing Responsibility Boundaries Before Adding Mappers

A useful rule is to designate which tool owns each use case.

Example with the `PurchaseOrder` aggregate:

- Creating an order: Spring Data JDBC.
- Changing status per domain rules: Spring Data JDBC.
- Saving the `OrderLine` list: Spring Data JDBC.
- Search screen combining customer/payment details: MyBatis read mapper.
- Monthly total revenue report: MyBatis read mapper.
- Bulk updating thousands of rows: consider MyBatis if direct SQL is a controlled choice, while handling versioning/auditing/invariants.

This boundary prevents an aggregate from being owned by multiple write paths. If MyBatis must update a column on an aggregate managed by Spring Data JDBC, clearly define who handles versioning, auditing, callbacks, child collections, and synchronizing in-memory objects.

One package organization style:

~~~text
com.example.orders
  domain/
    PurchaseOrder.java
    OrderLine.java
  application/
    PurchaseOrderService.java
    PurchaseOrderSearchService.java
  persistence/
    jdbc/
      PurchaseOrderRepository.java
    mybatis/
      PurchaseOrderReadMapper.java
      PurchaseOrderReadMapper.xml
      PurchaseOrderSummary.java
~~~

Package names are not mandatory. What matters is that the code shows whether a mapper serves reads/reports or a business write path. Names like `ReadMapper` or `ReportMapper` can communicate intent.

## 5. Example: Spring Data JDBC Saves Aggregate, MyBatis Reads DTO

Aggregate root:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        Long customerId,
        String status,
        BigDecimal total
) {}
~~~

Repository:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

DTO for the admin screen:

~~~java
import java.math.BigDecimal;

public record PurchaseOrderSummary(
        Long orderId,
        String orderNumber,
        String customerName,
        String status,
        BigDecimal total
) {}
~~~

Mapper interface:

~~~java
import java.util.List;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

@Mapper
public interface PurchaseOrderReadMapper {
    List<PurchaseOrderSummary> search(
            @Param("status") String status,
            @Param("customerName") String customerName
    );
}
~~~

XML mapper:

~~~xml
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper
  PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
  "https://mybatis.org/mybatis-3-mapper.dtd">

<mapper namespace="com.example.orders.persistence.mybatis.PurchaseOrderReadMapper">

  <select id="search"
          resultType="com.example.orders.persistence.mybatis.PurchaseOrderSummary">
    SELECT
      o.id AS orderId,
      o.order_number AS orderNumber,
      c.display_name AS customerName,
      o.status AS status,
      o.total AS total
    FROM purchase_orders o
    JOIN customers c ON c.id = o.customer_id
    <where>
      <if test="status != null and status != ''">
        AND o.status = #{status}
      </if>
      <if test="customerName != null and customerName != ''">
        AND c.display_name LIKE CONCAT('%', #{customerName}, '%')
      </if>
    </where>
    ORDER BY o.id DESC
  </select>

</mapper>
~~~

Application service:

~~~java
@Service
public class PurchaseOrderService {
    private final PurchaseOrderRepository repository;
    private final PurchaseOrderReadMapper readMapper;

    public PurchaseOrderService(
            PurchaseOrderRepository repository,
            PurchaseOrderReadMapper readMapper
    ) {
        this.repository = repository;
        this.readMapper = readMapper;
    }

    @Transactional
    public PurchaseOrder create(PurchaseOrder order) {
        return repository.save(order);
    }

    @Transactional(readOnly = true)
    public List<PurchaseOrderSummary> search(
            String status,
            String customerName
    ) {
        return readMapper.search(status, customerName);
    }
}
~~~

The example illustrates the split: the repository owns saving the aggregate; MyBatis owns the multi-table read query. The DTO keeps UI screens decoupled from the internal aggregate structure.

`CONCAT` syntax can vary across DBMS engines. If the application supports multiple databases, pick portable syntax or separate mapper statements per database. MyBatis does not automatically translate hand-written SQL into equivalent syntax for other databases.

## 6. Annotation SQL or XML Mappers?

MyBatis lets you declare SQL directly on interfaces or place it in XML.

### Annotations Fit Well When

- Statements are short.
- Queries have few dynamic branches.
- SQL fits comfortably on one screen.
- Mappers are small and do not need complex `resultMap` definitions.

Example:

~~~java
@Mapper
public interface CustomerReadMapper {

    @Select("""
        SELECT id, display_name AS name, email
        FROM customers
        WHERE id = #{id}
        """)
    CustomerSummary findSummaryById(@Param("id") Long id);
}
~~~

### XML Fits Well When

- SQL is long or has many dynamic conditions.
- Complex `resultMap` definitions are needed.
- SQL fragments need reuse.
- You want to separate SQL from Java interfaces.
- Queries need to be read, reviewed, or tuned independently.

~~~xml
<mapper namespace="com.example.CustomerReadMapper">
  <resultMap id="customerSummary"
             type="com.example.CustomerSummary">
    <id property="id" column="id"/>
    <result property="name" column="display_name"/>
    <result property="email" column="email"/>
  </resultMap>

  <select id="findSummaryById" resultMap="customerSummary">
    SELECT id, display_name, email
    FROM customers
    WHERE id = #{id}
  </select>
</mapper>
~~~

There is no rule that annotations are always better than XML or vice versa. Choose the representation that keeps statements readable and maintainable in your codebase. Avoid mixing both styles on the same mapper unless there is a clear convention.

## 7. Dynamic SQL: Flexible, Yet Inputs Must Be Constrained

Dynamic SQL is a standout benefit of MyBatis. Elements like `if`, `choose`, `trim`, `where`, `set`, and `foreach` build statements dynamically from parameters.

Example filtering orders:

~~~xml
<select id="search" resultType="PurchaseOrderSummary">
  SELECT id, order_number, status, total
  FROM purchase_orders
  <where>
    <if test="status != null and status != ''">
      AND status = #{status}
    </if>
    <if test="minimumTotal != null">
      AND total >= #{minimumTotal}
    </if>
    <if test="createdFrom != null">
      AND created_at >= #{createdFrom}
    </if>
    <if test="createdTo != null">
      AND created_at < #{createdTo}
    </if>
  </where>
  ORDER BY created_at DESC, id ASC
</select>
~~~

Values passed via `#{...}` are bound as parameters. Do not use direct string substitution syntax in SQL for untrusted user data, as it can introduce SQL injection.

If dynamic sorting is needed, map the client's selection to an allowlisted set of identifiers in code or use `choose` with fixed branches:

~~~xml
<choose>
  <when test="sortBy == 'amount'">
    ORDER BY total
  </when>
  <when test="sortBy == 'created'">
    ORDER BY created_at
  </when>
  <otherwise>
    ORDER BY id
  </otherwise>
</choose>
~~~

Direction (`ASC`/`DESC`) must also be constrained via fixed branches. Parameter binding protects values; it does not turn identifiers or keywords into valid bind parameters.

The more branches dynamic SQL has, the larger the number of SQL shapes that must be tested. Limit filter counts, write tests for key combinations, and avoid building a single mapper statement that tries to do everything.

## 8. Mapping and resultMap Costs

Spring Data JDBC relies on entity metadata to map aggregates. MyBatis has its own mapping model: `resultType`, `resultMap`, constructor mapping, `association`, and `collection` mapping.

A flat DTO is usually easy to map:

~~~xml
<select id="findSummary" resultType="PurchaseOrderSummary">
  SELECT
    id AS orderId,
    order_number AS orderNumber,
    status,
    total
  FROM purchase_orders
  WHERE id = #{id}
</select>
~~~

When column names do not match properties, use aliases or a `resultMap`. For nested mappings, `resultMap` must explicitly define column-to-property relationships.

Maintenance cost increases when:

- Multiple mappers redeclare the same result mapping independently.
- Column aliases are inconsistent.
- `SELECT *` queries cause schema changes to silently break mappings.
- One DTO is shared across multiple queries with differing column shapes.
- Collection joins generate duplicate rows while `resultMap` fails to handle identity properly.
- Nullability/constructor mappings mismatch Java types.

To reduce cost:

- Use dedicated DTOs for well-defined read models.
- Select only the required columns.
- Name aliases consistently after properties.
- Use `resultMap` for structured mappings instead of forcing `resultType` everywhere.
- Avoid using MyBatis to reconstruct entire Spring Data JDBC aggregates unless genuinely needed.

## 9. Do Not Create Two Owners for One Aggregate

A major risk is having both Spring Data JDBC and MyBatis update the aggregate root table.

Suppose `PurchaseOrder` has `@Version`. When calling `repository.save`, Spring Data JDBC checks the current version and increments it per optimistic locking.

If MyBatis executes:

~~~sql
UPDATE purchase_orders
SET status = #{status}
WHERE id = #{id}
~~~

then the statement neither checks nor increments the version. An outdated request can overwrite a newer status without Spring Data JDBC detecting it.

If updating via MyBatis is unavoidable, include the version check manually:

~~~sql
UPDATE purchase_orders
SET status = #{status},
    version = version + 1
WHERE id = #{id}
  AND version = #{expectedVersion}
~~~

Then inspect the affected row count:

- `1`: update succeeded.
- `0`: ID does not exist or version no longer matches.
- Greater than `1`: anomalous if `id` is the primary key.

Also reload the aggregate before continuing operations with the repository. Old in-memory objects still hold the previous version and will be rejected by optimistic locking on `save`.

A safer pattern for most domain use cases is letting the repository own all aggregate writes, while MyBatis only reads projections or reporting tables. If MyBatis must write, treat it as a write path with its own explicit contract and test concurrency.

## 10. Aggregate Children and Data Relationships

Spring Data JDBC manages children belonging to an aggregate via mappings like `@MappedCollection`. When saving the root, the framework may generate multiple insert/delete/update operations to synchronize the collection.

MyBatis does not automatically know that the collection belongs to an aggregate root. Mapper SQL simply executes the declared statement.

For example, MyBatis deletes an `order_lines` row:

~~~sql
DELETE FROM order_lines
WHERE order_id = #{orderId}
  AND line_no = #{lineNo}
~~~

If the in-memory `PurchaseOrder` object still holds that line, the next `repository.save(order)` may recreate the row or sync the collection to the stale state. Conversely, direct SQL may bypass invariants such as requiring the order total to equal the sum of its lines.

Before writing child rows with MyBatis, determine:

- Does the child belong to the aggregate root's lifecycle?
- Might a repository re-save the root after the mapper operation?
- Are child IDs/keys preserved accurately?
- Does the root version need incrementing?
- Do domain invariants need checking and totals updated?

If a child genuinely has an independent lifecycle, reconsider the aggregate model. Do not use MyBatis to bypass aggregate ownership rules without redesigning the domain.

## 11. Shared Transactions Between Spring Data JDBC and MyBatis

A benefit of Spring integration is that JDBC repositories and MyBatis can participate in the same transaction when configured properly.

MyBatis-Spring provides `SqlSessionTemplate` and integrates mappers with Spring transactions. When Spring Data JDBC and MyBatis share the same DataSource and transaction manager, SQL statements can commit or roll back together.

Service example:

~~~java
@Service
public class OrderWorkflowService {
    private final PurchaseOrderRepository orders;
    private final OrderAuditMapper auditMapper;

    public OrderWorkflowService(
            PurchaseOrderRepository orders,
            OrderAuditMapper auditMapper
    ) {
        this.orders = orders;
        this.auditMapper = auditMapper;
    }

    @Transactional
    public PurchaseOrder approve(Long id) {
        PurchaseOrder current = orders.findById(id).orElseThrow();

        PurchaseOrder approved = new PurchaseOrder(
                current.id(),
                current.version(),
                current.orderNumber(),
                current.customerId(),
                "APPROVED",
                current.total()
        );

        PurchaseOrder saved = orders.save(approved);

        auditMapper.insertApproval(
                saved.id(),
                saved.version(),
                "APPROVED"
        );

        return saved;
    }
}
~~~

In this example, Spring Data JDBC updates the aggregate; MyBatis writes the audit row. If inserting the audit fails and an exception rolls back the transaction, the aggregate update also rolls back when both technologies share the same physical transaction.

### Required Conditions

1. MyBatis `SqlSessionFactory` and Spring Data JDBC repositories use the same DataSource.
2. The transaction manager manages that DataSource.
3. MyBatis is integrated via MyBatis-Spring, typically using `SqlSessionTemplate` or integration-created mapper proxies.
4. Service methods execute through Spring's transaction proxy.
5. Do not open separate JDBC connections and commit independently.
6. Do not assign a mapper to a different transaction manager unintentionally.

If multiple DataSources exist, simply annotating with `@Transactional` does not automatically create an atomic transaction across all databases. You need an appropriate transaction manager or a distributed consistency architecture.

## 12. MyBatis Caches May Not Know Spring Data JDBC Just Wrote

This is an easily overlooked cost when using two persistence frameworks.

MyBatis has a per-`SqlSession` local cache. Mapper statements in the same session can reuse results based on cache configuration. MyBatis also supports a per-mapper-namespace second-level cache when enabled.

When Spring Data JDBC updates a table, MyBatis does not automatically know that another mapper namespace's cache needs invalidation. For example:

1. MyBatis reads `PurchaseOrder` and caches the result.
2. Spring Data JDBC updates `PurchaseOrder`'s status.
3. MyBatis reads again while the cache is still valid.
4. Stale results may be returned if the cache is not cleared appropriately.

Similarly, a MyBatis update does not automatically synchronize another application cache if one exists.

Ways to reduce risk:

- Keep MyBatis caching minimal when tables have multiple writers.
- Do not enable second-level caching for data frequently modified by another framework without an invalidation strategy.
- Consider `flushCache` on MyBatis write statements in the relevant namespace, while noting it does not automatically clear caches in other namespaces.
- Use application-layer caching with explicit invalidation.
- Verify read-after-update behavior in integration tests.
- If distributed caching is needed, design events/invalidation with proper transaction semantics.

Do not enable caching merely because a query looks read-heavy. Measure performance first and clearly define who has permission to write cached data.

## 13. Transactions and Caches Are Not the Same Thing

Transactions ensure atomicity and isolation of database operations within the transaction manager. A cache is a copy of data living outside or inside a persistence framework.

A successful transaction commit does not mean every cache in the application updates automatically. MyBatis caches, application caches, distributed caches, and read replicas each have separate lifecycles.

If a use case updates via Spring Data JDBC and then reads via MyBatis, verify:

- Is the mapper using the local cache in the same `SqlSession`?
- Is second-level caching enabled?
- Does the mapper statement have a separate cache namespace?
- Is the cache flushed when another mapper writes?
- Is there a read replica or routing datasource surfacing un-updated data?

Keeping caching simple is usually cheaper than maintaining a complex invalidation system.

## 14. Generated Keys When Using MyBatis

Spring Data JDBC can return saved aggregates along with database-generated IDs. With MyBatis, mappers must declare how to fetch generated keys in a way compatible with the driver/database.

Annotation example:

~~~java
@Mapper
public interface CustomerMapper {

    @Insert("""
        INSERT INTO customers(display_name, email)
        VALUES(#{name}, #{email})
        """)
    @Options(
        useGeneratedKeys = true,
        keyProperty = "id",
        keyColumn = "id"
    )
    int insert(CustomerInsertCommand command);
}
~~~

The command has an `id` property for MyBatis to populate with the generated value:

~~~java
public class CustomerInsertCommand {
    private Long id;
    private String name;
    private String email;

    // constructors, getters and setters
}
~~~

Generated-key behavior depends on the JDBC driver/database. Some DBMS engines need sequences or `RETURNING`/`OUTPUT` with dedicated statements. Verify key retrieval on the target database.

Do not use `MAX(id)` to get the newly inserted ID, as concurrent inserts can return another transaction's ID.

Distinguish clearly:

- A mapper method's `int` return value is typically the affected row count.
- The `id` value in the command can be assigned by MyBatis via generated keys.
- These two pieces of information are not the same.

## 15. TypeHandlers and Converters: Avoiding Two Representations of Data

Spring Data JDBC has custom converters; MyBatis has `TypeHandler`. The two mechanisms are not shared automatically.

Example domain enum:

~~~java
public enum OrderStatus {
    NEW, PAID, SHIPPED
}
~~~

Spring Data JDBC may use a converter to store codes `N`/`P`/`S`. MyBatis, if defaulting to enum names, writes `NEW`/`PAID`/`SHIPPED`. When both read the same column, one side may fail to understand the other's data.

Agree on a single storage convention:

| Domain value | Physical value |
|---|---|
| NEW | N |
| PAID | P |
| SHIPPED | S |

In MyBatis, a `TypeHandler` converts the enum to and from codes:

~~~java
@MappedTypes(OrderStatus.class)
@MappedJdbcTypes(JdbcType.VARCHAR)
public class OrderStatusTypeHandler
        extends BaseTypeHandler<OrderStatus> {

    @Override
    public void setNonNullParameter(
            PreparedStatement ps,
            int index,
            OrderStatus value,
            JdbcType jdbcType
    ) throws SQLException {
        ps.setString(index, switch (value) {
            case NEW -> "N";
            case PAID -> "P";
            case SHIPPED -> "S";
        });
    }

    @Override
    public OrderStatus getNullableResult(ResultSet rs, String column)
            throws SQLException {
        return fromCode(rs.getString(column));
    }

    @Override
    public OrderStatus getNullableResult(ResultSet rs, int column)
            throws SQLException {
        return fromCode(rs.getString(column));
    }

    @Override
    public OrderStatus getNullableResult(CallableStatement cs, int column)
            throws SQLException {
        return fromCode(cs.getString(column));
    }

    private OrderStatus fromCode(String code) {
        if (code == null) return null;
        return switch (code) {
            case "N" -> OrderStatus.NEW;
            case "P" -> OrderStatus.PAID;
            case "S" -> OrderStatus.SHIPPED;
            default -> throw new IllegalArgumentException(
                    "Unknown order status code: " + code);
        };
    }
}
~~~

This is an illustrative `TypeHandler` example; register the `TypeHandler` in the MyBatis configuration or specify it on mappers/`resultMap`s. Spring Data JDBC converters must also convert to and from the exact same physical codes.

Types to align include enums, UUIDs, JSON, timestamps, timezones, decimals, and value objects. A converter working for repositories does not guarantee MyBatis automatically uses the same conversion.

## 16. Dialect Differences and SQL Portability

Spring Data JDBC uses dialects to generate certain SQL syntax such as pagination and generated keys per database. MyBatis executes SQL declared in mappers; if SQL contains vendor-specific syntax, the team must manage those differences.

Pagination example:

~~~sql
-- PostgreSQL / MySQL
SELECT id, status
FROM purchase_orders
ORDER BY id
LIMIT #{limit} OFFSET #{offset}
~~~

SQL Server typically uses a form like:

~~~sql
SELECT id, status
FROM purchase_orders
ORDER BY id
OFFSET #{offset} ROWS FETCH NEXT #{limit} ROWS ONLY
~~~

If the application only supports one DBMS, vendor-specific SQL may be acceptable when assumptions are documented. If supporting multiple DBMS engines, you can use `databaseId` in MyBatis mappers or separate mapper statements per database:

~~~xml
<select id="search" databaseId="postgresql"
        resultType="PurchaseOrderSummary">
  SELECT id, status
  FROM purchase_orders
  ORDER BY id
  LIMIT #{limit} OFFSET #{offset}
</select>

<select id="search" databaseId="sqlserver"
        resultType="PurchaseOrderSummary">
  SELECT id, status
  FROM purchase_orders
  ORDER BY id
  OFFSET #{offset} ROWS FETCH NEXT #{limit} ROWS ONLY
</select>
~~~

Database IDs must be configured consistently with vendor identification in MyBatis. Separating statements this way increases the number of statements to test, but keeps SQL differences isolated in the right place.

Do not claim multi-database support if mappers are only tested on a single engine.

## 17. Schema Evolution and Migration Costs

When the schema changes, both Spring Data JDBC mappings and MyBatis mappers must be updated.

For example, renaming column `display_name` to `full_name`:

- The entity needs `@Column` or naming convention updates.
- Derived queries may need property updates.
- MyBatis XML/annotations need column name and alias updates.
- `ResultMap`s need updates if mappings depend on the old column.
- `TypeHandler`s may need changes if the physical type changes.
- Migrations must preserve data and constraints.
- Test fixtures and integration tests need updates.

When many mappers repeat the same column names or `resultMap`s, modification costs grow proportionally to the number of copies.

Ways to reduce this:

- Use stable naming conventions.
- Avoid `SELECT *`.
- Use SQL fragments for meaningful repeated snippets.
- Keep DTOs and `resultMap`s focused on clear purposes.
- Search mapper references whenever changing the schema.
- Run migrations from prior versions in test databases rather than only creating fresh schemas.

## 18. Dynamic SQL and Branch Maintenance Count

A mapper with 8 optional filters can produce many distinct SQL shapes. You do not necessarily have to test every mathematical combination, but pick representative tests:

- No filters.
- Each key filter individually.
- Combinations of AND/OR conditions.
- Null values and empty strings.
- Empty and non-empty `IN` lists.
- Valid and invalid sorts.
- First page, deep page, and empty page.

In particular, `foreach` with an empty list must be handled explicitly. An empty `IN` condition can be invalid on databases. Use `choose`/`if` to decide behavior for empty lists: omit the predicate, return no results, or reject the request per business contract.

Do not put all filtering, sorting, pagination, joins, permissions, and update logic into a single mapper statement. Split statements by use case to keep SQL comprehensible.

## 19. Controlling SQL Injection

MyBatis offers two commonly discussed parameter substitution forms:

- `#{value}`: binds the value via `PreparedStatement`.
- Direct string substitution syntax using dollar sign and curly braces: injects text directly into the SQL statement.

Use `#{...}` for values:

~~~xml
WHERE customer_id = #{customerId}
~~~

Do not use direct string substitution syntax for user data:

~~~xml
ORDER BY sortColumn direction
~~~

When identifiers must vary, use an allowlist mapping validated choices to fixed column names. Do not rely on simple regexes like alphanumeric-only checks as the sole defense if arbitrary identifiers are still allowed; an explicit allowlist is much easier to control.

SQL injection is not solely a MyBatis concern. Any hand-written SQL through `JdbcTemplate` or repository queries must separate parameter values from SQL structure.

## 20. Operational and Observability Costs

Adding MyBatis introduces several operational considerations:

- Knowing which mapper statement is running when a query is slow.
- Monitoring SQL and bound parameters without exposing sensitive data.
- Aligning logging between Spring Data JDBC and MyBatis.
- Managing separate caches.
- Monitoring connection pools and transaction durations when one service invokes multiple mappers.
- Handling timeouts and exception translation appropriately.

SQL logging is helpful during debugging, but parameters may include emails, tokens, addresses, or payment details. Do not enable sensitive parameter logging in production without appropriate protection policies.

Use metrics/tracing to observe query durations, returned row counts, errors, and pool usage. Name mapper statements clearly so slow queries can be traced back to use cases.

## 21. Integration Testing Between Both Technologies

Mapper unit tests only verify part of the logic. When integrating Spring Data JDBC with MyBatis, test under the shared DataSource and transaction manager configuration.

Important scenarios:

1. Save an aggregate via repository, then read a DTO via MyBatis.
2. MyBatis writes an audit row in the same transaction as repository save.
3. Intentionally fail the mapper insert and verify the aggregate update rolls back.
4. Verify versioning when MyBatis updates a versioned aggregate.
5. Verify converters/`TypeHandler`s read and write identical values.
6. Verify generated keys with the real JDBC driver.
7. Verify caches do not return stale data after the other framework writes.
8. Verify pagination and sorting on the target DBMS.
9. Run migrations from previous schema versions.
10. Test SQL injection defenses on dynamic parameters.

Conceptual rollback test example:

~~~java
@SpringBootTest
class OrderWorkflowIntegrationTest {

    @Autowired
    PurchaseOrderRepository orders;

    @Autowired
    OrderWorkflowService service;

    @Test
    void rollsBackRepositoryWriteWhenMapperFails() {
        PurchaseOrder order = orders.save(newOrder());

        assertThrows(RuntimeException.class, () ->
                service.approveAndFailAudit(order.id())
        );

        PurchaseOrder reloaded = orders.findById(order.id()).orElseThrow();
        assertEquals("NEW", reloaded.status());
    }
}
~~~

This test needs a real database or Testcontainers, along with properly configured transaction management and mapper integration. If a test method opens an outer transaction wrapping the entire test, understand how that test transaction interacts with the service transaction to avoid false conclusions.

## 22. Measure Performance Before Choosing MyBatis for Speed

MyBatis is not inherently faster than Spring Data JDBC. Both tools ultimately use the JDBC driver and database. Performance depends on SQL, execution plans, indexes, round trips, selected columns, mapping, and transactions.

MyBatis can improve a use case when:

- Current queries load entire aggregates while screens only need a few columns.
- N+1 queries occur due to an unsuitable data-reading approach.
- Joins/projections are needed in a single query.
- Bulk updates are needed instead of saving aggregates one by one.
- SQL is tuned based on actual execution plans.

However, MyBatis can be slower or consume more resources if:

- SQL returns too many columns/rows.
- `ResultMap` constructs large object graphs.
- Dynamic SQL produces query plans that are hard to optimize.
- Caching causes stale reads or consumes excessive memory.
- Mappers run many sequential queries.
- Transactions hold connections for too long.

Measure queries before and after with production-like data, matching databases, indexes, drivers, and concurrency. Do not add another framework solely on assumptions about speed.

## 23. When Should You Use MyBatis?

MyBatis is usually worth considering when one or more of these apply:

- Read queries involve complex joins/projections.
- Database-specific SQL is required and locking into that DBMS is acceptable.
- Proven legacy SQL needs to be preserved.
- Exact control over statements and result mappings is needed.
- Bulk operations bring clear value and versioning/auditing/invariants are designed.
- The team is skilled at reading, reviewing, tuning, and testing SQL.
- Mapper count can be governed via package, naming, and ownership conventions.

Do not add MyBatis just because a derived query feels slightly long or out of a desire to write all CRUD in SQL. Consider Spring Data JDBC `Criteria`/`Query`, derived queries, or `@Query` first if they express the use case cleanly and meet requirements.

## 24. When Does Maintenance Cost Outweigh Benefits?

Consider avoiding or limiting MyBatis if:

- Most queries are just `findById`, `findByStatus`, or simple CRUD.
- Mappers duplicate significant logic already in repositories.
- There are no integration tests on the target database.
- The team lacks a SQL review process.
- The same aggregate is written from multiple places without versioning rules.
- Multiple DBMS engines are supported while mappers contain vendor-specific syntax without variants.
- Caches lack an invalidation strategy.
- `TypeHandler`s and Spring Data converters represent the same property differently.
- Every schema change requires manually editing numerous mappers and `resultMap`s.
- Nobody owns maintaining the mappers.

A warning sign is when the same query or business rule appears in repositories, XML mappers, and services. At that point, change costs climb and code paths tend to drift apart over time.

## 25. Use-Case Decision Matrix

| Use case | Recommended starting tool | Reason |
|---|---|---|
| Create/update aggregate roots and children | Spring Data JDBC repository | Framework manages aggregate mapping and versioning |
| Find by a few properties | Derived query | Minimal manual SQL, easy to read |
| Moderate dynamic filtering on aggregates | `Criteria` + `JdbcAggregateTemplate` | Reuses Spring Data mappings |
| Join/projection queries for screens | MyBatis read mapper | Clear SQL and DTOs |
| Multi-table summary reports | MyBatis or SQL/reporting layer | Can use window functions/grouping/CTEs |
| Well-defined bulk updates | Controlled MyBatis/`JdbcTemplate` | Customizable SQL, though versioning/auditing must be handled |
| Write audit in the same transaction | Repository or MyBatis mapper | Both can join the transaction if configured together |
| Update children belonging to an aggregate | Spring Data JDBC | Preserves ownership and collection synchronization |
| DBMS-specific queries | MyBatis | Accepts dialect-dependent SQL |
| Simple CRUD on non-aggregate legacy tables | MyBatis can fit well | Explicit mapper SQL can be a simpler model |

Not every application needs both tools. If Spring Data JDBC satisfies all use cases, adding MyBatis only increases the concepts and rules to maintain.

## 26. Controlled MyBatis Integration Process

When deciding to add MyBatis, follow these steps:

1. **Identify specific use cases**: state clearly which queries or operations do not fit repositories/templates.
2. **Define ownership**: decide whether mappers are read-only or allowed to write; specify who owns each aggregate.
3. **Configure a shared DataSource**: use a Spring-managed DataSource and transaction manager when shared transactions are needed.
4. **Organize mappers**: keep packages, namespaces, statement names, and XML/annotations consistent.
5. **Design DTOs/resultMaps**: select only needed columns, use clear aliases, and avoid `SELECT *`.
6. **Standardize type mappings**: align MyBatis `TypeHandler`s with Spring Data converters.
7. **Control dynamic SQL**: bind values with `#{...}`, allowlist identifiers, and handle empty lists.
8. **Design versioning/auditing**: if mappers write to aggregates, implement optimistic locking and auditing manually.
9. **Control caching**: enable caches only when there is an invalidation strategy across all writers.
10. **Test thoroughly**: transaction rollbacks, generated keys, type mappings, pagination, and migrations.
11. **Measure performance**: validate gains with real data and execution plans.
12. **Document DBMS assumptions**: if SQL is vendor-specific, state supported databases/drivers/versions explicitly.

## 27. Common Mistakes When Combining Spring Data JDBC and MyBatis

| Symptom | Common Cause | Resolution |
|---|---|---|
| Mapper reads stale data after repository save | MyBatis cache was not invalidated by Spring Data JDBC | Reduce caching or design explicit invalidation |
| Repository misses concurrent mapper updates | MyBatis did not check/increment `@Version` | Add version to WHERE and increment version |
| Children lost after saving root | MyBatis modified child table while aggregate object was stale | Keep root as writer or reload and sync aggregate |
| Audit does not roll back with aggregate | Two technologies use different DataSources/transaction managers | Use the same Spring transaction infrastructure |
| Mapper insert lacks ID | Generated keys not configured or unsupported in that way by driver | Configure `useGeneratedKeys`/`keyProperty` or DB-specific strategy |
| Enum read incorrectly | `TypeHandler` and converter use different conventions | Share physical codes and test bidirectionally |
| SQL runs on one DB but fails on another | Mapper contains vendor-specific syntax | Separate by `databaseId` or dedicated strategies, test each DB |
| Dynamic sort risks SQL injection | Using direct string substitution with untrusted input | Allowlist identifiers, bind values with `#{...}` |
| DTO missing data or unexpected nulls | Alias/`resultMap` mismatch | Check columns, constructors, and nullability |
| Multiple mappers edit the same logic | Lack of ownership and conventions | Separate reads/writes, consolidate shared logic |
| Query fast locally but slow in production | Differences in data, indexes, drivers, or execution plans | Measure on production-like DBMS and data |

## 28. Key Principles to Remember

- Spring Data JDBC fits aggregate-oriented persistence; MyBatis fits explicit SQL control and result mapping.
- Use MyBatis when concrete benefits of joins, projections, bulk SQL, or database-specific queries outweigh mapper and testing costs.
- Prefer one canonical write path per aggregate; avoid letting both repositories and mappers write without versioning/auditing/child rules.
- MyBatis `TypeHandler` and Spring Data custom converters are separate mechanisms; physical representations must agree.
- Mapper SQL does not automatically apply Spring Data JDBC optimistic locking, aggregate lifecycles, callbacks, or auditing.
- Share a DataSource and transaction manager so both technologies participate in the same Spring transaction.
- MyBatis caches do not automatically detect data changes made by Spring Data JDBC; caches require explicit invalidation.
- Use `#{...}` to bind values; allowlist identifiers and avoid direct string substitution with untrusted data.
- SQL inside mappers can be DBMS-dependent; use `databaseId` or separate strategies when supporting multiple engines.
- Test transaction rollbacks, generated keys, mappings, caching, and pagination against the target database.
- Measure performance before concluding MyBatis is faster.
- Keep mappers small and use-case focused, and document SQL assumptions to keep maintenance costs down.

MyBatis complements Spring Data JDBC applications with SQL control, particularly for joins, projections, reports, and specialized statements. That value remains sustainable only when the team maintains clear boundaries between aggregate persistence and SQL mappers, aligns type mappings, manages transactions/caches, and tests database-specific differences. Add MyBatis for use cases where SQL control solves a concrete need; every new mapper should have an owner, a contract, and verification commensurate with the maintenance cost it introduces.
