# Tìm, đếm, kiểm tra tồn tại và xóa aggregate bằng template

Trong **Spring Data Relational JDBC (Spring Data JDBC)**, ngoài repository, ứng dụng có thể thao tác trực tiếp với aggregate thông qua **JdbcAggregateTemplate**. Template cung cấp các thao tác tìm theo ID, tìm theo điều kiện, đếm aggregate, kiểm tra tồn tại và xóa aggregate. Cách này hữu ích khi một service cần điều phối nhiều thao tác persistence hoặc muốn dùng API template thay cho repository trong một phần của ứng dụng.

Các thao tác vẫn tuân theo mô hình aggregate của Spring Data JDBC: template làm việc với **aggregate root**, còn các đối tượng con thuộc aggregate được ánh xạ theo cấu hình quan hệ. Khi xóa một aggregate, ứng dụng cần hiểu phạm vi sở hữu của root, ràng buộc khóa ngoại và transaction để tránh ảnh hưởng ngoài ý muốn.

## 1. JdbcAggregateTemplate là gì?

`JdbcAggregateTemplate` là API thao tác aggregate ở mức template của Spring Data JDBC. Nó sử dụng mapping metadata, dialect và cơ chế truy cập dữ liệu của Spring Data JDBC để lưu và tải aggregate, thay vì yêu cầu ứng dụng tự viết toàn bộ SQL cho các thao tác chuẩn.

Các nhóm thao tác thường dùng:

| Nhu cầu | API template |
|---|---|
| Tìm một aggregate theo ID | `findById(id, DomainType.class)` |
| Tìm nhiều aggregate theo điều kiện | `findAll(query, DomainType.class)` |
| Kiểm tra root có tồn tại | `existsById(id, DomainType.class)` |
| Đếm aggregate root | `count(DomainType.class)` |
| Xóa theo ID | `deleteById(id, DomainType.class)` |
| Xóa từ instance aggregate | `delete(aggregate)` |
| Xóa toàn bộ aggregate của một kiểu | `deleteAll(DomainType.class)` |

Tên API cụ thể cần đối chiếu với phiên bản Spring Data JDBC mà dự án đang sử dụng. Trong các ví dụ dưới đây, ta dùng `JdbcAggregateTemplate` và các method công khai phổ biến của nó.

### Template khác repository ở điểm nào?

Repository đóng gói thao tác theo một interface gắn với aggregate type:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long> {
}
~~~

Template là một collaborator được inject trực tiếp và nhận kiểu aggregate ở tham số:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();
~~~

Hai cách đều dùng Spring Data JDBC mapping và cùng làm việc với aggregate. Chọn template khi cần gọi API tổng quát, phối hợp thao tác trong một service hoặc muốn sử dụng `Query` trực tiếp. Repository thường phù hợp khi muốn interface rõ ràng theo từng aggregate và có derived query methods.

## 2. Chuẩn bị aggregate Order

Giả sử một đơn hàng có thông tin root và nhiều dòng hàng:

~~~java
package com.example.sales.order;

import java.util.ArrayList;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_position")
    private List<OrderItem> items = new ArrayList<>();

    protected Order() {
        // Dành cho Spring Data JDBC.
    }

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public List<OrderItem> getItems() {
        return List.copyOf(items);
    }
}
~~~

Đối tượng con:

~~~java
package com.example.sales.order;

import org.springframework.data.relational.core.mapping.Table;

@Table("order_items")
public class OrderItem {

    private String sku;
    private int quantity;

    protected OrderItem() {
    }

    public OrderItem(String sku, int quantity) {
        this.sku = sku;
        this.quantity = quantity;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }
}
~~~

Schema PostgreSQL minh họa:

~~~sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_items (
    order_id BIGINT NOT NULL REFERENCES sales_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, line_position)
);
~~~

Trong ví dụ, `Order` là aggregate root; `OrderItem` là thành phần được root sở hữu. Các thao tác template bên dưới nhận `Order.class`, không nhận `OrderItem.class` để thao tác độc lập với dòng hàng.

## 3. Inject JdbcAggregateTemplate

Trong ứng dụng Spring Boot có cấu hình Spring Data JDBC và `DataSource`, template được Spring tạo và quản lý. Có thể inject qua constructor:

~~~java
package com.example.sales.order;

import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderAggregateService {

    private final JdbcAggregateTemplate template;

    public OrderAggregateService(JdbcAggregateTemplate template) {
        this.template = template;
    }
}
~~~

Không cần tự tạo `JdbcAggregateTemplate` bằng `new` trong service. Spring cần cung cấp mapping context, dialect, converter, data access strategy và các thành phần hạ tầng liên quan. Inject bean đã được cấu hình giúp template dùng đúng metadata và transaction infrastructure của ứng dụng.

## 4. Tìm aggregate theo ID bằng findById

Method `findById` nhận ID và class của aggregate root:

~~~java
Optional<Order> result =
    template.findById(orderId, Order.class);
~~~

Vì có thể không tồn tại đơn hàng, kết quả được biểu diễn bằng `Optional<Order>`. Xử lý hai trường hợp:

~~~java
public Order getOrder(Long orderId) {
    return template.findById(orderId, Order.class)
        .orElseThrow(() -> new IllegalArgumentException(
            "Order not found: " + orderId
        ));
}
~~~

Khi tìm được Order, Spring Data JDBC dựng aggregate theo mapping đã khai báo. Các thành phần con thuộc aggregate, chẳng hạn danh sách `items`, được tải theo quy tắc mapping của Spring Data JDBC.

`findById` không tự tải những aggregate độc lập được tham chiếu bằng ID. Ví dụ, nếu Order giữ `customerId`, template không tự dựng object Customer. Muốn hiển thị thông tin Customer, hãy truy vấn Customer riêng hoặc dùng read query phù hợp.

### So sánh với existsById

Nếu chỉ cần biết Order có tồn tại không, không cần tải cả aggregate:

~~~java
boolean exists = template.existsById(orderId, Order.class);
~~~

Nếu tiếp theo cần sửa Order, gọi `findById` trực tiếp thường tránh được một lần truy vấn dư thừa:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();

// Thực hiện thay đổi trên aggregate root.
~~~

Không nên gọi `existsById` rồi `findById` chỉ để kiểm tra trước khi tải; `findById` đã cho biết có tìm thấy aggregate hay không.

## 5. Tìm nhiều aggregate theo điều kiện bằng Query

Template hỗ trợ truy vấn dựa trên `Query` và `Criteria` của Spring Data Relational. Ví dụ tìm các đơn ở trạng thái `OPEN`:

~~~java
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Iterable<Order> orders = template.findAll(
    Query.query(Criteria.where("status").is("OPEN")),
    Order.class
);
~~~

`Criteria.where("status")` tham chiếu đến property của entity; Spring Data JDBC ánh xạ property đó tới cột theo metadata. Nếu tên Java là `createdAt` còn cột SQL là `created_at`, query criteria nên dùng property `createdAt`.

Có thể kết hợp điều kiện:

~~~java
Query query = Query.query(
    Criteria.where("status").is("OPEN")
        .and("customerId").is(customerId)
);

Iterable<Order> orders =
    template.findAll(query, Order.class);
~~~

Ví dụ này lấy các Order có status OPEN của một Customer. Điều kiện Customer là một scalar reference trong Order; template không cần tải Customer để lọc theo `customerId`.

### Kết hợp sắp xếp, giới hạn và offset

~~~java
import org.springframework.data.domain.Sort;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Query query = Query.query(
        Criteria.where("status").is("OPEN")
    )
    .sort(Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
    ))
    .limit(20)
    .offset(0);

Iterable<Order> firstBatch =
    template.findAll(query, Order.class);
~~~

Thứ tự sort có khóa `id` làm tiêu chí phụ để giảm sự không xác định khi nhiều đơn có cùng thời điểm tạo. `limit` giới hạn số aggregate trả về; `offset` xác định số kết quả bỏ qua trước khi lấy batch.

Các tên property trong Sort/Criteria phải tương thích với mapping của domain type. Không đưa trực tiếp tên cột hoặc biểu thức SQL tùy ý từ request vào Criteria/Sort; hãy kiểm tra và giới hạn lựa chọn sort ở tầng API.

## 6. Đếm aggregate bằng count

Template có thể đếm số aggregate root của một kiểu:

~~~java
long totalOrders = template.count(Order.class);
~~~

Kết quả là `long`, phù hợp với số lượng có thể vượt phạm vi `int`. Trong ví dụ, `count(Order.class)` đếm các hàng root trong bảng `sales_orders`, không cộng số hàng `order_items`.

Muốn đếm theo điều kiện, truyền `Query`:

~~~java
Query openOrders = Query.query(
    Criteria.where("status").is("OPEN")
);

long openOrderCount = template.count(openOrders, Order.class);
~~~

Một ví dụ đếm đơn của Customer:

~~~java
Query customerOrders = Query.query(
    Criteria.where("customerId").is(customerId)
);

long customerOrderCount =
    template.count(customerOrders, Order.class);
~~~

Phép đếm được thực hiện ở database và chỉ trả về một con số. Không nên gọi `findAll(query, Order.class)`, chuyển thành danh sách rồi lấy `size()` nếu mục tiêu chỉ là đếm.

### Đếm root khác đếm thành phần con

Nếu một Order có 5 OrderItem, nó vẫn là **một aggregate Order**. Vì vậy:

~~~java
long orderCount = template.count(Order.class);
~~~

không trả tổng số item. Muốn đếm dòng hàng, cần truy vấn vào bảng `order_items` bằng Spring JDBC/custom query hoặc một query chuyên biệt phù hợp. Không dùng `OrderItem.class` như một aggregate root nếu OrderItem chỉ là thành phần được sở hữu bên trong Order.

## 7. Kiểm tra tồn tại bằng existsById

Để kiểm tra một aggregate root có tồn tại theo ID:

~~~java
boolean exists = template.existsById(orderId, Order.class);
~~~

Ví dụ trong service:

~~~java
public void ensureOrderExists(Long orderId) {
    if (!template.existsById(orderId, Order.class)) {
        throw new IllegalArgumentException(
            "Order not found: " + orderId
        );
    }
}
~~~

`existsById` trả boolean và không trả nội dung Order. Đây là lựa chọn phù hợp cho use case chỉ cần kiểm tra sự tồn tại, chẳng hạn trước khi trả một kết quả trạng thái hoặc xác nhận một tham chiếu.

### Kiểm tra tồn tại theo điều kiện

Với một điều kiện phức tạp hơn, có thể truy vấn một lát nhỏ và kiểm tra kết quả, nhưng nếu chỉ cần existence, nên dùng API tồn tại có điều kiện nếu phiên bản template cung cấp hoặc dùng một truy vấn SQL `EXISTS` chuyên biệt. Không tải toàn bộ tập dữ liệu chỉ để kiểm tra danh sách có rỗng hay không.

Ví dụ SQL tương đương cho điều kiện:

~~~sql
SELECT EXISTS (
    SELECT 1
    FROM sales_orders
    WHERE customer_id = :customerId
      AND status = :status
);
~~~

Đây là SQL minh họa khi cần một truy vấn existence theo nhiều điều kiện. `JdbcAggregateTemplate.existsById` dành cho kiểm tra theo ID root; nó không thay thế mọi truy vấn EXISTS theo nghiệp vụ.

### Exists không phải khóa bảo đảm dữ liệu còn tồn tại

Một request có thể kiểm tra Order tồn tại, sau đó một transaction khác xóa Order trước khi request đầu ghi dữ liệu liên quan. Vì vậy:

- `existsById` cho biết trạng thái tại thời điểm truy vấn.
- Khóa ngoại và constraint bảo vệ tính toàn vẹn tại thời điểm ghi.
- Transaction/locking cần được thiết kế theo yêu cầu đồng thời.
- Luôn xử lý lỗi khi thao tác ghi có thể xung đột với thay đổi của request khác.

Không dùng kết quả exists như một bảo đảm rằng bản ghi sẽ tồn tại mãi trong các bước sau.

## 8. Xóa aggregate theo ID bằng deleteById

Khi cần xóa một Order theo ID:

~~~java
template.deleteById(orderId, Order.class);
~~~

Lệnh nhận cả ID và aggregate root type để template xác định bảng root cùng mapping của aggregate. Với aggregate có các thành phần con được sở hữu, Spring Data JDBC xử lý các hàng thuộc aggregate theo mapping khi xóa root.

Ví dụ service:

~~~java
public void deleteOrder(Long orderId) {
    if (!template.existsById(orderId, Order.class)) {
        throw new IllegalArgumentException(
            "Order not found: " + orderId
        );
    }

    template.deleteById(orderId, Order.class);
}
~~~

Đoạn code trên giúp đưa ra lỗi nghiệp vụ rõ ràng, nhưng có hai truy vấn và vẫn có race condition giữa exists và delete. Nếu use case chỉ cần xóa theo ID, có thể gọi `deleteById` trực tiếp rồi xử lý kết quả/ngoại lệ theo hợp đồng API và constraint của phiên bản đang dùng.

### Xóa từ aggregate instance

Nếu service đã tải Order và muốn xóa chính aggregate đó:

~~~java
Order order = template.findById(orderId, Order.class)
    .orElseThrow();

template.delete(order);
~~~

Cách này phù hợp khi trước đó use case đã cần tải aggregate để kiểm tra trạng thái hoặc quyền xóa. Không tải aggregate chỉ để xóa nếu `deleteById` đã đáp ứng yêu cầu.

## 9. Xóa toàn bộ aggregate bằng deleteAll

Template có thao tác xóa tất cả aggregate của một kiểu:

~~~java
template.deleteAll(Order.class);
~~~

Đây là thao tác ảnh hưởng rộng: nó xóa toàn bộ Order thuộc kiểu đó theo phạm vi database/schema mà ứng dụng đang kết nối. Nếu Order sở hữu OrderItem, dữ liệu con cũng được xử lý theo mapping aggregate.

Chỉ sử dụng trong tác vụ quản trị, reset dữ liệu kiểm thử hoặc use case có yêu cầu rõ ràng. Không gọi từ endpoint công khai chỉ vì client gửi một tham số thiếu điều kiện lọc.

Nếu muốn xóa theo điều kiện, hãy xác định tập ID phù hợp rồi xóa có kiểm soát trong transaction, hoặc dùng một thao tác SQL chuyên biệt nếu nghiệp vụ cho phép. Đừng nhầm `deleteAll(Order.class)` với xóa các Order thỏa một Criteria.

## 10. Transaction khi tìm, đếm và xóa

Các thao tác template có thể tham gia transaction Spring khi dùng chung `DataSource` và transaction manager được cấu hình. Đối với use case cần nhiều bước liên quan, đặt ranh giới transaction ở application service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderMaintenanceService {

    private final JdbcAggregateTemplate template;

    public OrderMaintenanceService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional
    public void removeDraftOrder(Long orderId) {
        Order order = template.findById(orderId, Order.class)
            .orElseThrow(() -> new IllegalArgumentException(
                "Order not found: " + orderId
            ));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Only draft orders can be removed"
            );
        }

        template.delete(order);
    }
}
~~~

Ví dụ thể hiện quy trình tải aggregate, kiểm tra trạng thái rồi xóa trong cùng transaction. Nếu một bước phát sinh lỗi và transaction bị rollback, các thao tác database thuộc transaction được hoàn tác theo transaction manager.

Không nên cho rằng `@Transactional` tự giải quyết mọi race condition. Nếu hai request cùng kiểm tra một trạng thái rồi xóa/cập nhật, cần cân nhắc optimistic locking, locking hoặc isolation phù hợp với yêu cầu.

### Read-only transaction cho truy vấn

~~~java
@Transactional(readOnly = true)
public long countOpenOrders() {
    Query query = Query.query(
        Criteria.where("status").is("OPEN")
    );
    return template.count(query, Order.class);
}
~~~

`readOnly = true` là metadata/hint cho transaction manager và hạ tầng persistence. Nó không thay thế quyền chỉ đọc của database và không phải cơ chế bảo mật.

## 11. Khóa ngoại và chính sách xóa

Giả sử bảng OrderItem có FK tới Order:

~~~sql
ALTER TABLE order_items
ADD CONSTRAINT fk_order_items_order
FOREIGN KEY (order_id)
REFERENCES sales_orders(id);
~~~

Spring Data JDBC quản lý các hàng con thuộc aggregate khi xóa root. Tuy nhiên, nếu có bảng khác tham chiếu đến `sales_orders` hoặc `order_items`, constraint của database vẫn có thể ngăn xóa.

Ví dụ, bảng `shipments` tham chiếu Order:

~~~sql
CREATE TABLE shipments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES sales_orders(id),
    tracking_code VARCHAR(80) NOT NULL
);
~~~

Nếu shipment là dữ liệu độc lập cần giữ lại, xóa Order có thể bị FK từ chối. Ứng dụng cần xác định chính sách nghiệp vụ: chặn xóa, hủy/ẩn Order, xử lý shipment trước hoặc dùng mô hình lưu trữ phù hợp. Không dùng cascade delete một cách tùy tiện để vượt qua ràng buộc lịch sử.

**Xóa aggregate không đồng nghĩa xóa mọi dữ liệu có liên quan trong toàn hệ thống.** Template chỉ hiểu quan hệ ownership trong mapping; các aggregate khác vẫn có vòng đời riêng và database constraint bảo vệ tham chiếu giữa chúng.

## 12. Phân biệt xóa vật lý và soft delete

Các method `delete`, `deleteById` và `deleteAll` là thao tác xóa theo persistence mapping, thường tương ứng với xóa vật lý. Chúng không tự chuyển một trường `deleted` thành true hoặc điền `deleted_at`.

Nếu nghiệp vụ cần giữ lịch sử:

~~~java
public void cancel() {
    if (!"DRAFT".equals(status)) {
        throw new IllegalStateException("Order cannot be cancelled");
    }
    status = "CANCELLED";
}
~~~

Lưu lại aggregate bằng `update` hoặc `save` qua cơ chế phù hợp để biểu diễn trạng thái hủy. Các truy vấn đọc sau đó phải lọc theo trạng thái/soft-delete policy nếu không muốn hiển thị bản ghi đã hủy.

Soft delete là quy tắc domain và query; không tự xuất hiện chỉ vì dùng template.

## 13. Template và repository: chọn công cụ phù hợp

| Nhu cầu | Repository | JdbcAggregateTemplate |
|---|---|---|
| Tìm theo ID | `findById(id)` | `findById(id, Order.class)` |
| Kiểm tra ID | `existsById(id)` | `existsById(id, Order.class)` |
| Đếm tất cả | `count()` | `count(Order.class)` |
| Xóa theo ID | `deleteById(id)` | `deleteById(id, Order.class)` |
| Tìm theo property | Derived query method | `findAll(Query, Order.class)` |
| Đếm theo Criteria | Derived/custom query | `count(Query, Order.class)` |
| Xóa một root đã tải | `delete(order)` | `delete(order)` |
| Interface theo aggregate | Rất phù hợp | Cần truyền type trong lời gọi |

Repository phù hợp khi API cần dễ khám phá và có các query method theo nghiệp vụ. Template hữu ích khi service muốn xây dựng Criteria động, thao tác nhiều aggregate type hoặc dùng API persistence tổng quát.

Không cần tạo repository và template cho cùng một thao tác nếu không có lý do. Dùng một cách nhất quán trong từng use case giúp code dễ đọc và giảm việc truy vấn trùng.

## 14. Hiệu năng và phạm vi truy vấn

Một số nguyên tắc khi dùng template:

1. Dùng `existsById` khi chỉ cần boolean; không tải aggregate để kiểm tra sự tồn tại.
2. Dùng `count` với Query khi chỉ cần số lượng; không tải danh sách rồi gọi `size()`.
3. Dùng `findById` khi thực sự cần dữ liệu aggregate để xử lý.
4. Dùng Criteria có điều kiện rõ ràng, tránh `findAll` không giới hạn trên bảng lớn.
5. Dùng sort có khóa duy nhất làm tiêu chí cuối nếu phân trang theo offset.
6. Tạo index phù hợp với điều kiện lọc và thứ tự truy vấn thực tế.
7. Với báo cáo JOIN nhiều aggregate, cân nhắc Spring JDBC và DTO thay vì tải từng aggregate rồi ghép trong vòng lặp.

Ví dụ index:

~~~sql
CREATE INDEX idx_sales_orders_status
    ON sales_orders(status);

CREATE INDEX idx_sales_orders_customer_id
    ON sales_orders(customer_id);
~~~

Index cụ thể phải dựa trên workload và execution plan. Index tăng tốc một số truy vấn nhưng làm tăng chi phí insert/update và dung lượng lưu trữ.

## 15. Các lỗi thường gặp

| Lỗi | Hệ quả | Cách xử lý |
|---|---|---|
| Gọi `findById` chỉ để kiểm tra tồn tại | Tải object graph không cần thiết | Dùng `existsById` |
| Gọi `findAll` rồi lấy `size()` | Tải nhiều aggregate chỉ để đếm | Dùng `count` hoặc `count(Query, type)` |
| Nghĩ `count(Order.class)` đếm cả OrderItem | Số liệu báo cáo sai | Phân biệt root với bảng con |
| Gọi deleteById với class của entity con | Nhầm thành phần con với aggregate root | Truyền kiểu root được quản lý |
| Nghĩ deleteAll(Query, type) luôn là API có sẵn | Dùng nhầm method không có trong API | Dùng API công khai của phiên bản; lọc ID hoặc custom SQL nếu cần |
| Nghĩ delete root luôn xóa mọi bảng có FK tới root | Vi phạm constraint hoặc mất dữ liệu ngoài ý muốn | Xác định ownership và chính sách tham chiếu |
| Gọi exists rồi delete trong hai bước như một bảo đảm | Có race condition | Dựa vào transaction/constraint và xử lý xung đột |
| Dùng delete vật lý cho dữ liệu cần lịch sử | Mất dấu vết nghiệp vụ | Dùng trạng thái hủy/soft delete theo domain |
| Dùng `findAll(Query, type)` không có giới hạn | Tải quá nhiều aggregate | Thêm filter, limit/offset hoặc xử lý theo batch |
| Trộn template và repository cho cùng thao tác không cần thiết | Luồng persistence khó theo dõi | Chọn API theo nhu cầu và nhất quán |

## 16. Bài thực hành

1. Tạo `Order` aggregate có danh sách `OrderItem` bằng `@MappedCollection`.
2. Inject `JdbcAggregateTemplate` qua constructor vào một service.
3. Gọi `findById(orderId, Order.class)`; xử lý trường hợp `Optional.empty()`.
4. Gọi `existsById(orderId, Order.class)` và so sánh với `findById`.
5. Gọi `count(Order.class)`; đối chiếu với số hàng trong bảng `sales_orders`.
6. Dùng `Query` và `Criteria` tìm Order theo status và customerId.
7. Thêm sort, limit và offset; kiểm tra kết quả theo thứ tự ổn định.
8. Gọi `count(query, Order.class)` và so sánh với số phần tử nếu tải cùng điều kiện.
9. Xóa một Order theo ID; xác minh các OrderItem thuộc aggregate được xử lý theo mapping.
10. Tạo một bảng Shipment tham chiếu Order và thử xóa Order đang được Shipment tham chiếu. Quan sát FK và xác định chính sách nghiệp vụ cần áp dụng.
11. Viết use case chỉ cho phép xóa Order ở trạng thái DRAFT trong một transaction.
12. Thay xóa vật lý bằng trạng thái CANCELLED và điều chỉnh truy vấn để không hiển thị đơn đã hủy.

## 17. Ghi nhớ

`JdbcAggregateTemplate` cung cấp các thao tác trực tiếp trên aggregate root: `findById` để tải một aggregate, `findAll(Query, type)` để tìm theo điều kiện, `count` để đếm root, `existsById` để kiểm tra ID và `delete`/`deleteById` để xóa aggregate.

Template sử dụng mapping của Spring Data JDBC nên hiểu các thành phần con thuộc aggregate; nó không tự tải hoặc sở hữu aggregate khác chỉ vì có khóa ngoại tham chiếu. Hãy dùng exists khi chỉ cần boolean, count khi chỉ cần số lượng, find khi cần dữ liệu và delete khi nghiệp vụ cho phép xóa. Với thao tác nhiều bước, đặt transaction ở service, giữ ràng buộc FK và xác định rõ xóa vật lý hay soft delete.
