# Querying Entities with Child Components and Checking Additional Loading SQL

In Spring Data JDBC, an aggregate typically consists of an aggregate root and child entities stored in separate tables. When declaring a repository method with **@Query**, the custom SQL is used to find and map the **aggregate root**. Spring Data JDBC still has to construct the complete aggregate, so collections such as **List**, **Set**, or **Map** may be loaded using additional SQL statements.

This is easy to overlook when reading code: a single repository call can execute multiple statements. SQL inside **@Query** does not automatically become a JOIN query that builds every collection. If the method returns multiple roots, the child-loading queries may repeat per aggregate and create an N+1 pattern.

This lesson uses an order with order lines as an example to explain:

1. How **@Query** maps SQL results into the root.
2. Why child collections are still loaded with separate SQL.
3. How to estimate and identify additional query counts.
4. How to read SQL logs and inspect behavior on a real database.
5. When to use a custom **RowMapper**, **ResultSetExtractor**, or DTO/read model.
6. The limitations of string-based queries and Single Query Loading.

## 1. Aggregates with child components

Suppose an order has multiple order lines:

~~~text
PurchaseOrder (aggregate root)
    |
    +-- OrderLine
    +-- OrderLine
    +-- OrderLine
~~~

The root table is **purchase_orders**; the child table is **order_lines**. Each order line has an **order_id** column referencing the order's primary key.

Java mapping:

~~~java
package com.example.shop.order.domain;

import java.math.BigDecimal;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_lines")
public class OrderLine {

    private String sku;
    private int quantity;
    private BigDecimal unitPrice;

    private OrderLine() {
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }
}
~~~

Aggregate root:

~~~java
package com.example.shop.order.domain;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @Column("order_code")
    private String orderCode;

    private String status;

    @Column("created_at")
    private LocalDateTime createdAt;

    @MappedCollection(
            idColumn = "order_id",
            keyColumn = "line_no"
    )
    private List<OrderLine> lines = new ArrayList<>();

    private PurchaseOrder() {
    }

    public Long getId() {
        return id;
    }

    public String getOrderCode() {
        return orderCode;
    }

    public String getStatus() {
        return status;
    }

    public LocalDateTime getCreatedAt() {
        return createdAt;
    }

    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }
}
~~~

**@MappedCollection** tells Spring Data JDBC that the lines collection is stored in a child table, with order_id linking back to the root and line_no acting as the key column for List elements.

Illustrative DDL:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(15, 2) NOT NULL,

    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id)
        REFERENCES purchase_orders(id)
        ON DELETE CASCADE,
    CONSTRAINT ck_order_line_quantity
        CHECK (quantity > 0),
    CONSTRAINT ck_order_line_price
        CHECK (unit_price >= 0)
);
~~~

This is a two-table aggregate. Returning a PurchaseOrder means the framework must obtain both the root data and the order lines belonging to it.

## 2. How does a custom @Query find roots?

Repository declaration:

~~~java
package com.example.shop.order.repository;

import com.example.shop.order.domain.PurchaseOrder;
import java.util.List;

import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    @Query("""
        SELECT
            o.id,
            o.order_code,
            o.status,
            o.created_at
        FROM purchase_orders o
        WHERE o.status = :status
        ORDER BY o.created_at DESC
        """)
    List<PurchaseOrder> findCustomByStatus(
            @Param("status") String status
    );
}
~~~

When calling:

~~~java
List<PurchaseOrder> orders =
        repository.findCustomByStatus("OPEN");
~~~

Spring Data JDBC executes the SQL you declared to fetch rows from the root table. The result is mapped using the default **RowMapper**, just like queries auto-generated by Spring Data JDBC.

Once the roots are retrieved, the framework proceeds to load mapped collections within the aggregate. For lines, SQL similar to the following is needed:

~~~sql
SELECT
    order_id,
    line_no,
    sku,
    quantity,
    unit_price
FROM order_lines
WHERE order_id = :orderId;
~~~

Therefore, the SQL in **@Query** is not the entire aggregate-reading operation.

**Key point:** @Query determines how roots are found. The aggregate's mapping structure still determines what related data must be loaded additionally.

## 3. Why are child collections loaded with additional SQL?

Spring Data JDBC reads aggregates according to their ownership structure. For custom queries, the default RowMapper uses the SQL result to populate:

- The aggregate root.
- Embedded entities.
- One-to-one relationships.
- Primitive arrays stored using SQL array types.

For entity collections such as **Map**, **List**, **Set**, and entity arrays, Spring Data JDBC issues separate queries to load them.

For example, a root has the field:

~~~java
@MappedCollection(idColumn = "order_id")
private List<OrderLine> lines;
~~~

A **@Query** selecting purchase_orders does not automatically build the OrderLine list just because the SQL includes a JOIN. The default RowMapper expects columns in a format it understands for the root and supported relationships; entity collections are loaded via a separate mechanism.

This lets the framework manage the whole aggregate without requiring every custom SQL query to manually implement child-row grouping logic.

### 3.1. One root: counting SQL statements

Suppose a query returns a single order, and the aggregate has one lines collection.

Traditional loading pattern:

~~~text
1. @Query:
   SELECT ... FROM purchase_orders WHERE ...

2. Collection query:
   SELECT ... FROM order_lines WHERE order_id = ?

Illustrative total: 2 SELECTs
~~~

If the aggregate has an additional independent collection, such as notes, another query is needed to load that collection.

~~~text
1. SELECT purchase_orders
2. SELECT order_lines
3. SELECT order_notes

Illustrative total: 3 SELECTs
~~~

This query count scales with the number of loaded collection paths. Exact statement counts also depend on mapping, relationship types, and the Spring Data JDBC version.

### 3.2. List of multiple roots: N+1 risk

Suppose the custom query returns 50 orders and each order has a lines collection. The root SQL executes once, while the collection must be loaded for each root.

Observable query pattern:

~~~text
1. SELECT ... FROM purchase_orders WHERE status = 'OPEN'

2. SELECT ... FROM order_lines WHERE order_id = 101
3. SELECT ... FROM order_lines WHERE order_id = 102
4. SELECT ... FROM order_lines WHERE order_id = 103
...
51. SELECT ... FROM order_lines WHERE order_id = 150
~~~

Illustrative formula:

\[
Q = 1 + N
\]

Where:

- Q is the number of SELECTs.
- N is the number of aggregate roots returned.
- 1 is the custom query finding the roots.
- N is the additional queries loading one collection per root.

With 50 roots:

\[
Q = 1 + 50 = 51
\]

If each root has two separately loaded collections:

\[
Q = 1 + 2N
\]

With 50 roots:

\[
Q = 1 + 2 \times 50 = 101
\]

This is a form of **N+1 queries**. Never look at a single @Query annotation and assume the repository method executes only one SQL statement.

### 3.3. A large collection does not mean many queries

If you load one root with 100 order lines, the collection query can return 100 rows in a single ResultSet:

~~~text
SELECT root             -> 1 statement
SELECT 100 child rows   -> 1 statement

Total: 2 statements
~~~

Distinguish between:

- **Query count:** number of SQL statements.
- **Row count:** number of result rows.
- **Payload size:** amount of data transferred from the database.
- **Materialization cost:** cost of constructing Java objects.

A query returning thousands of rows is still one statement, yet can consume significant time and memory.

## 4. @Query with JOIN still loads collections separately

A common misconception is thinking that adding a JOIN to custom SQL causes Spring Data JDBC to automatically group child rows into the collection.

Example:

~~~java
@Query("""
    SELECT
        o.id,
        o.order_code,
        o.status,
        l.line_no,
        l.sku,
        l.quantity,
        l.unit_price
    FROM purchase_orders o
    LEFT JOIN order_lines l ON l.order_id = o.id
    WHERE o.status = :status
    """)
List<PurchaseOrder> findOrdersWithLines(
        @Param("status") String status
);
~~~

The SQL above produces a ResultSet that repeats root columns for each order line. However, the aggregate's default RowMapper does not automatically interpret arbitrary JOIN column pairs as a collection to group.

Result columns must conform to the format expected by the default RowMapper. For entity collections, Spring Data JDBC still issues separate queries to load them. Hence, a JOIN in the root SQL does not guarantee eliminating extra queries.

If you want to map a JOIN ResultSet into a root with its collections in one read, you must control row grouping yourself using a **ResultSetExtractor** or an appropriate custom mapping mechanism. When doing so, you take responsibility for grouping roots properly, avoiding duplicates, and constructing child components accurately.

### 4.1. Filtering roots by child does not mean loading only matching children

Suppose you want to find orders containing product SKU BOOK-01:

~~~java
@Query("""
    SELECT o.id, o.order_code, o.status, o.created_at
    FROM purchase_orders o
    WHERE EXISTS (
        SELECT 1
        FROM order_lines l
        WHERE l.order_id = o.id
          AND l.sku = :sku
    )
    """)
List<PurchaseOrder> findOrdersContainingSku(
        @Param("sku") String sku
);
~~~

EXISTS filters the list of **orders** matching the condition of having at least one qualifying line.

When Spring Data JDBC builds the aggregate, each order's lines collection is still loaded according to the mapping. Normally the collection contains **all lines of the order**, not just the lines with SKU BOOK-01.

These are two different requirements:

- Finding orders that contain a given SKU.
- Fetching only the order lines with that SKU.

If the screen only needs matching lines, use a dedicated DTO/read query. Do not try to turn an aggregate collection into a filtered sub-projection by putting a condition in the root query.

## 5. Which columns must be in a @Query?

When using the default RowMapper, the SQL statement must return data in the format the RowMapper expects.

Key rules:

- Columns needed for properties passed to the entity constructor must be present.
- Properties assigned via setters, withers, or field access may not be mandatory in the result.
- Properties without a matching column will not be populated.
- Embedded entities and one-to-one relationships require column names matching mapping conventions.
- Entity collections are loaded by separate queries.

Example root with constructor:

~~~java
public PurchaseOrder(
        String orderCode,
        String status
) {
    this.orderCode = orderCode;
    this.status = status;
}
~~~

SQL must supply the columns used in the constructor:

~~~sql
SELECT
    id,
    order_code,
    status
FROM purchase_orders
WHERE status = :status;
~~~

If a column required by the constructor is missing, mapping may fail.

### 5.1. Embedded and one-to-one require proper aliases

Suppose the root has an address property with a city field:

~~~java
class PurchaseOrder {
    private Address address;
}
~~~

The query must return columns prefixed with the relationship property name and an underscore:

~~~sql
SELECT
    o.id,
    o.order_code,
    o.address_city
FROM purchase_orders o
WHERE o.id = :id;
~~~

The alias rule is the relationship property name plus an underscore followed by the nested property name. For property address.city, the column needs the label address_city.

This differs from the lines collection: a collection is not populated by adding aliases like lines_sku to the root query; it is loaded by a separate statement.

## 6. @Query and Single Query Loading

Spring Data JDBC 3.2 introduced Single Query Loading to load multiple aggregates in one SQL statement when the aggregate and database qualify.

However, according to limitations documented in the current Spring Data Relational reference, Single Query Loading applies only to CrudRepository find methods, not to:

- Derived query methods.
- Annotated query methods using @Query.

Therefore, enabling the flag:

~~~java
context.setSingleQueryLoadingEnabled(true);
~~~

does not mean a @Query method will automatically load the root and all collections in one SQL statement. That method still uses the default loading mechanism for collections.

In addition, Single Query Loading has other limitations such as nested collections, AggregateReference, embedded entities, and dialect support. Check the documentation for your exact Spring Data JDBC version before relying on this strategy.

### 6.1. Comparison table

| Query approach | Loading root | Entity collections | Single Query Loading |
|---|---|---|---|
| CrudRepository.findById | Repository query | Separate queries in traditional mode | Can apply if eligible |
| CrudRepository.findAll | Repository query | Separate queries in traditional mode | Can apply if eligible |
| Derived query | Query derived from method name | Separate queries | Does not apply under current limitations |
| Annotated @Query | Custom SQL | Separate queries | Does not apply under current limitations |
| DTO/read query | SQL designed for read data | Returns only data requested by query | No aggregate loading needed |

## 7. What are the limitations of string-based @Query?

Custom queries written as SQL strings have several limitations to keep in mind.

### 7.1. Named parameters only

Spring Data JDBC supports named parameters:

~~~java
@Query("""
    SELECT id, order_code, status
    FROM purchase_orders
    WHERE status = :status
      AND created_at >= :fromDate
    """)
List<PurchaseOrder> findByStatusAndDate(
        @Param("status") String status,
        @Param("fromDate") LocalDateTime fromDate
);
~~~

Do not use positional placeholders like ?1 as in some other Spring Data modules. Using explicit parameter names keeps SQL readable and avoids ordering mistakes.

If the compiler has the -parameters flag enabled, Spring can discover Java parameter names without @Param. In documentation and examples, using @Param makes intent explicit.

### 7.2. Does not accept Pageable, Sort, or Limit as query parameters

String-based queries do not support pagination or Sort, PageRequest, and Limit parameters via automatic SQL rewriting. To limit results, express it directly in SQL and bind appropriate parameters.

Example for PostgreSQL:

~~~java
@Query("""
    SELECT id, order_code, status, created_at
    FROM purchase_orders
    WHERE status = :status
    ORDER BY created_at DESC
    LIMIT :maxRows
    """)
List<PurchaseOrder> findLatestByStatus(
        @Param("status") String status,
        @Param("maxRows") int maxRows
);
~~~

LIMIT is syntax supported by PostgreSQL and several other databases; row-limiting syntax depends on the database. Write according to your actual dialect.

Note that limiting roots does not eliminate collection-loading queries. If the query returns 20 roots, the collections of those 20 aggregates still need to be loaded per the mapping strategy.

### 7.3. Named queries behave the same way

Spring Data JDBC supports named queries in the file:

~~~text
META-INF/jdbc-named-queries.properties
~~~

The default name is usually derived from the domain class name and repository method name, or can be set via the name attribute of @Query.

Named queries are processed similarly to queries declared directly via annotations. Moving SQL from an annotation into a properties file does not eliminate collection loading.

## 8. Checking additional loading SQL with logs

The most reliable way to see how many SQL statements a method actually runs is to observe JDBC statements.

You can enable logging in application.yml:

~~~yaml
logging:
  level:
    org.springframework.jdbc.core.JdbcTemplate: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
~~~

Or enable more broadly:

~~~yaml
logging:
  level:
    org.springframework.jdbc: DEBUG
~~~

Logs can show:

- The custom SQL statement in @Query.
- The SELECT statements loading collections.
- Bound parameter values and bind types when verbose logging is enabled.
- Other SQL statements executed by the service or transaction.

Be cautious with TRACE in environments containing real data: bound parameter logs can contain sensitive information. Only enable during investigation and use test data whenever possible.

### 8.1. What does one repository call look like in logs?

For an order with one collection, logs might show a pattern like:

~~~text
Executing SQL:
SELECT id, order_code, status, created_at
FROM purchase_orders
WHERE status = ?

Executing SQL:
SELECT order_id, line_no, sku, quantity, unit_price
FROM order_lines
WHERE order_id = ?
~~~

If the query returns multiple orders, observe how many times the second statement executes and which order_id values are bound.

Do not just count log lines. One statement can be logged at multiple layers, so distinguish SQL preparation logs, parameter-binding logs, and statement-execution logs.

### 8.2. Counting per use case

When measuring query count:

1. Prepare fixed test data.
2. Reset/start the counter right before the repository call.
3. Call exactly one method.
4. Record SQL statements executed during that interval.
5. Separate the root query from collection-loading queries.
6. Check the actual number of roots returned.
7. Repeat with 1 root, 10 roots, and 100 roots.
8. Compare query count and duration.

Do not include startup SQL, migrations, or health-check queries in the same measurement.

You can use a datasource proxy or JDBC instrumentation library in integration tests to count statements instead of parsing logs by eye. The goal is to measure a single operation while keeping test data stable.

## 9. Integration tests for custom queries and collections

A valuable integration test should verify both domain results and generated queries.

Example testing results:

~~~java
@DataJdbcTest
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void customQueryReturnsOrdersWithTheirLines() {
        List<PurchaseOrder> orders =
                repository.findCustomByStatus("OPEN");

        assertThat(orders).hasSize(2);
        assertThat(orders)
                .allSatisfy(order ->
                        assertThat(order.getLines()).isNotNull()
                );
    }
}
~~~

This test needs a fixture that pre-populates two orders with order lines in the test database. It confirms the results are constructed as aggregates, though it does not by itself prove the query count.

To measure statement counts, integrate a datasource proxy or statement counter and reset the counter before the repository call. Then verify root SELECTs and collection SELECTs separately.

A useful test matrix:

| Fixture | Roots returned | Collections | What to observe |
|---|---:|---|---|
| A | 1 | 1 collection | Root query and child query |
| B | 10 | 1 collection | Whether collection queries repeat per root |
| C | 10 | 2 collections | How many statements run per collection |
| D | 10 | Nested collection | How query count scales across levels |

Do not mock the repository or mock RowMapper and draw conclusions about SQL. Query count is a JDBC/database-layer behavior and should be verified with integration tests using a real datasource or suitable test database.

## 10. When to use a custom RowMapper or ResultSetExtractor?

If the query only needs to filter roots and you still want Spring Data JDBC to build collections automatically, using the default RowMapper is simplest. The framework loads collections via its own mechanism.

If you need control over how the ResultSet is read, @Query allows configuring:

- rowMapperClass
- rowMapperRef
- resultSetExtractorClass
- resultSetExtractorRef

### 10.1. RowMapper fits one result row to one object

RowMapper receives one ResultSet row and converts it into one object. It fits:

- Scalar/primitive results.
- Single-row DTOs.
- A root mapped from a specific column layout.

Example defining a read model:

~~~java
public record PurchaseOrderSummary(
        Long id,
        String orderCode,
        String status
) {
}
~~~

You can write a dedicated RowMapper to map those three columns. When using a custom RowMapper for a @Query, register the class or bean via the corresponding annotation attribute.

### 10.2. ResultSetExtractor fits grouping multiple rows

A JOIN query can return multiple rows for the same root:

~~~text
order_id | order_code | line_no | sku
---------+------------+---------+---------
100      | SO-100     | 0       | BOOK-01
100      | SO-100     | 1       | PEN-02
101      | SO-101     | 0       | BAG-03
~~~

If you want to build a DTO containing a list of order lines from such a ResultSet, you need to group by order_id:

~~~text
ResultSet
    |
    +-- order_id = 100
    |      +-- OrderSummary #100
    |      +-- Line BOOK-01
    |      +-- Line PEN-02
    |
    +-- order_id = 101
           +-- OrderSummary #101
           +-- Line BAG-03
~~~

ResultSetExtractor lets you iterate over the entire ResultSet and build the grouped structure yourself. This is a better fit than a simple RowMapper when a single root spans multiple rows.

However, when grouping results manually, you are responsible for handling:

- Repeated root columns across multiple rows.
- Empty collections when LEFT JOIN has no child rows.
- Element ordering.
- Nulls and data types.
- Duplicate children caused by multiple JOINs.
- Nested relationships.
- Memory usage when the ResultSet is large.

### 10.3. Custom mappers affect lifecycle events

According to Spring Data JDBC documentation, using a custom RowMapper or ResultSetExtractor via QueryMappingConfiguration, rowMapperClass, or resultSetExtractorClass disables Entity Callbacks and Lifecycle Events for that mapping process. Custom mapping code can invoke callbacks/events itself if needed.

If the application relies on auditing or post-load callbacks, understand this impact before switching to custom mappers.

## 11. When only read data is needed, use a DTO/read model

A search screen may only need order code, status, and matching SKU. It does not necessarily need a full PurchaseOrder with every collection.

Example with NamedParameterJdbcTemplate:

~~~java
public record OrderLineSearchResult(
        Long orderId,
        String orderCode,
        String status,
        String sku,
        int quantity
) {
}
~~~

~~~java
@Repository
public class OrderSearchQuery {

    private final NamedParameterJdbcTemplate jdbc;

    public OrderSearchQuery(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<OrderLineSearchResult> findBySku(String sku) {
        String sql = """
            SELECT
                o.id AS order_id,
                o.order_code,
                o.status,
                l.sku,
                l.quantity
            FROM purchase_orders o
            JOIN order_lines l ON l.order_id = o.id
            WHERE l.sku = :sku
            ORDER BY o.id DESC
            """;

        return jdbc.query(
                sql,
                Map.of("sku", sku),
                (rs, rowNum) -> new OrderLineSearchResult(
                        rs.getLong("order_id"),
                        rs.getString("order_code"),
                        rs.getString("status"),
                        rs.getString("sku"),
                        rs.getInt("quantity")
                )
        );
    }
}
~~~

This query returns only matching lines. It does not need to load the entire aggregate and other collections.

Distinguishing purposes:

| Need | Approach |
|---|---|
| Change order status and protect invariants | Load aggregate root, call domain method, save via repository |
| Find orders by custom SQL condition while still needing full aggregate | @Query returning root; accept additional collection loading |
| Display a list with a few columns | DTO/read query |
| Multi-table JOIN report | SQL projection, RowMapper, or ResultSetExtractor |
| Optimize loading aggregates in one SQL statement | Check Single Query Loading if method and aggregate qualify |

DTO/read models do not replace aggregates in write use cases. They prevent read queries from constructing data the screen does not use.

## 12. @Modifying and directly updating child tables

@Query can also be used with @Modifying to perform direct UPDATE/DELETE statements:

~~~java
@Modifying
@Query("""
    UPDATE order_lines
    SET quantity = :quantity
    WHERE order_id = :orderId
      AND line_no = :lineNo
    """)
int updateLineQuantity(
        @Param("orderId") Long orderId,
        @Param("lineNo") Integer lineNo,
        @Param("quantity") Integer quantity
);
~~~

This statement updates the child table directly without loading the aggregate root. It can be useful for a well-designed technical operation, but keep in mind:

- It does not trigger entity lifecycle callbacks/events.
- Auditing fields are not updated automatically unless the SQL updates them itself.
- It does not execute root domain methods.
- It can bypass invariants such as "only edit lines when the order is in OPEN status".
- It does not automatically apply the root's optimistic locking.
- You must check the updated row count and handle cases where no row is found.

If you need to update a child table directly, the SQL must enforce critical business conditions, for example:

~~~sql
UPDATE order_lines l
SET quantity = :quantity
WHERE l.order_id = :orderId
  AND l.line_no = :lineNo
  AND EXISTS (
      SELECT 1
      FROM purchase_orders o
      WHERE o.id = l.order_id
        AND o.status = 'OPEN'
  );
~~~

Even with a status condition, the operation still requires evaluating concurrency and versioning. A custom UPDATE is not automatically equivalent to loading the aggregate, checking invariants in Java, and saving the root.

For frequent business operations, if you keep repeating logic to recreate aggregate safeguards, revisit the domain boundary or design an appropriate command service.

## 13. Common mistakes when reading custom queries with collections

| Symptom/assumption | Cause or reality | How to fix |
|---|---|---|
| Seeing one @Query yet logs show multiple SELECTs | Entity collections are loaded by separate queries | Count statements per aggregate and collection |
| JOINed child table but collection is still empty or queries again | Default RowMapper does not group arbitrary JOINs into collections | Use ResultSetExtractor or let the framework load collections separately |
| List of 100 roots runs many SQL queries | N+1 pattern in collection loading | Measure query count; consider DTOs or an appropriate loading strategy |
| Filtered root by SKU expecting collection to contain only that SKU | Root query condition does not filter collection mapping | Use a DTO/read query tailored for child results |
| Missing columns cause mapping error | Constructor needs columns missing from SELECT | Return all constructor columns with proper aliases |
| One-to-one relationship is not populated | Column alias does not follow relationship name + underscore | Use aliases such as address_city |
| Enabled Single Query Loading yet @Query still runs extra SQL | Annotated queries are not within its supported scope | Use eligible CrudRepository find methods or read queries |
| @Query does not accept Pageable/Sort | String-based queries do not rewrite SQL automatically | Put ORDER BY/LIMIT/OFFSET in SQL and bind parameters |
| Custom RowMapper prevents callbacks from running | Custom result mapping disables lifecycle callbacks/events | Handle callbacks manually if required by business logic |
| @Modifying updates data without updating audit/version | SQL runs directly, bypassing lifecycle and domain flow | Update required fields manually and enforce invariants/concurrency |

## 14. Workflow for investigating a @Query method

When a method returning an aggregate with collections executes multiple SQL statements, investigate in this order:

**Step 1 — Read the domain mapping.** Identify how many collections, embedded entities, and one-to-one relationships the root has.

**Step 2 — Read the custom SQL.** See whether the query selects the root or JOINs child tables, which columns are returned, and how they are aliased.

**Step 3 — Identify the return type.** Does the method return a root, list of roots, DTO, stream, or scalar?

**Step 4 — Predict mapping behavior.** Default RowMapper populates root/embedded/one-to-one; entity collections will be loaded separately.

**Step 5 — Check loading strategy.** Annotated @Query does not use Single Query Loading under current limitations.

**Step 6 — Enable SQL logging.** Record the root query and collection-loading statements.

**Step 7 — Increase test root count.** Compare 1 root with 10 or 100 roots to see whether query count scales linearly.

**Step 8 — Choose the read approach.** If a full aggregate is needed, keep the mapping and consider find methods eligible for Single Query Loading. If only screen results are needed, use a DTO/read model. If manual JOIN grouping is needed, use ResultSetExtractor and own the mapping.

**Step 9 — Re-measure.** Verify query count, row count, duration, and payload size on the target database.

~~~text
Repository method @Query
        |
        v
Custom SQL finds roots
        |
        v
Default RowMapper maps root
        |
        +---- Embedded / one-to-one
        |         -> mapped from query result if aliases match
~~~

## 15. Self-check scenarios

**Scenario A — One order with 20 lines**

A @Query returns exactly one PurchaseOrder with a lines collection. Can we conclude 21 SQL statements run?

**Hint:** No. One root and one collection typically produce a root query and a collection query; 20 is the result row count, not the statement count.

**Scenario B — A query returns 100 orders**

Each order has a lines collection. What query count pattern can traditional loading create?

**Hint:** One root query plus collection-loading queries per root; an N+1 pattern of 1 + N.

**Scenario C — Query uses JOIN to filter by SKU**

The query selects only orders having at least one line with SKU BOOK-01. Will the order's lines collection contain only lines with that SKU?

**Hint:** Not by default. The root query filters orders; the aggregate collection is loaded by its own mapping query and normally contains all lines of the order.

**Scenario D — Returning root and collection from one JOIN ResultSet**

Is adding a JOIN to @Query enough?

**Hint:** No. The default RowMapper does not automatically group arbitrary JOIN rows into collections. A ResultSetExtractor or custom mapping responsible for grouping roots and children is needed.

**Scenario E — Enabling Single Query Loading**

Does a @Query method automatically switch to Single Query Loading?

**Hint:** Not under current limitations; this strategy applies only to eligible CrudRepository find methods.

**Scenario F — Updating a child table with @Modifying**

Does a direct UPDATE on the order_lines table automatically verify root status, trigger callbacks, and update version?

**Hint:** No. It is a directly executed modifying query; you must express the necessary business conditions, auditing, and concurrency checks yourself.

## 16. Key takeaways

| Component | Role |
|---|---|
| @Query | Declares custom SQL to find roots |
| Default RowMapper | Maps root, embedded, and one-to-one from ResultSet |
| Entity collections | List, Set, Map, entity arrays; loaded via separate SQL |
| @MappedCollection | Identifies child table and linking columns to the root |
| N+1 | Root query plus additional queries per root |
| @Query + JOIN | Does not automatically group ResultSet rows into collections |
| ResultSetExtractor | Manually groups multiple rows into a read structure |
| DTO/read model | Loads only data needed for screens/reports |
| Single Query Loading | Does not apply to annotated @Query under current limitations |
| @Modifying | Executes SQL directly without running lifecycle callbacks/events |
| SQL logging | Way to verify actual additional queries |

**One custom SQL statement does not mean reading an aggregate runs only one statement.** @Query fetches roots and the default RowMapper maps supported properties; entity collections are still loaded via separate SQL. When returning multiple roots, this can create N+1 queries. Check SQL logs, distinguish aggregate loading from DTO/read queries, and only JOIN/group a ResultSet manually when you are ready to take responsibility for mapping and the associated lifecycle behavior.
