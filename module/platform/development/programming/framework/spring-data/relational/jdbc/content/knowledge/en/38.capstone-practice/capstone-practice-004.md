# Building Order Filters, Pagination, and Report Projections in Spring Data JDBC

## 1. The real-world problem

An order management screen typically needs several capabilities:

- Filtering by order status.
- Filtering by creation time range.
- Searching by order number or customer information.
- Sorting by creation time, total amount, or status.
- Dividing results into pages.
- Displaying a report showing customer name, line count, and total amount.

Not every data read request needs to load the full `Order` aggregate. A list screen might only need a few columns from `orders`, `customers`, and `order_lines`. Loading the full aggregate for every row and then computing report totals in Java can read far more data than necessary.

In Spring Data JDBC, you should distinguish two kinds of queries:

1. **Aggregate queries:** load the full `Order` via a repository when business operations must be performed on the aggregate.
2. **Read/report queries:** retrieve a projection or DTO containing only the columns needed for display, typically using custom queries with `JOIN` and aggregations.

This lesson builds both types to show when to use repository methods, when to use `JdbcAggregateTemplate`, and when to use a custom repository fragment with `NamedParameterJdbcTemplate`.

## 2. Sample data model

Suppose the application manages `Order`, `Customer`, and `OrderLine`:

~~~text
customers
  id
  name

orders
  id
  order_number
  customer_id
  status
  created_at

order_lines
  id
  order_id
  sku
  quantity
  unit_price
~~~

`Order` is the aggregate root. `OrderLine` belongs to the `Order` aggregate. `Customer` is another aggregate and is referenced by `Order` via `customer_id`.

Order entity:

~~~java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.jdbc.core.mapping.AggregateReference;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("order_number")
    private String orderNumber;

    private OrderStatus status;

    @Column("created_at")
    private Instant createdAt;

    @Column("customer_id")
    private AggregateReference<Customer, Long> customer;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // Constructors, getters and domain methods.
}
~~~

Status enum:

~~~java
public enum OrderStatus {
    PENDING,
    CONFIRMED,
    PAID,
    SHIPPED,
    CANCELLED
}
~~~

Illustrative schema migration:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL
);

CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(id)
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(18, 2) NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES orders(id)
);

CREATE INDEX ix_orders_status_created_at
    ON orders(status, created_at DESC);

CREATE INDEX ix_orders_customer_id
    ON orders(customer_id);

CREATE INDEX ix_order_lines_order_id
    ON order_lines(order_id);
~~~

Timestamp types, identity syntax, and index syntax may need to be adjusted for your database. Indexes should be based on actual queries and execution plans; you should not add every index imaginable.

## 3. Filtering orders with derived queries

For simple conditions based on properties of the aggregate root, Spring Data JDBC can derive SQL from the method name.

Repository:

~~~java
import java.time.Instant;
import java.util.List;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.domain.Sort;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.PagingAndSortingRepository;

public interface OrderRepository
        extends CrudRepository<Order, Long>,
                PagingAndSortingRepository<Order, Long> {

    List<Order> findByStatus(OrderStatus status);

    Page<Order> findByStatusAndCreatedAtBetween(
            OrderStatus status,
            Instant from,
            Instant to,
            Pageable pageable
    );

    Slice<Order> findByStatus(
            OrderStatus status,
            Pageable pageable
    );

    List<Order> findByStatus(
            OrderStatus status,
            Sort sort
    );

    List<Order> findByOrderNumberStartingWith(
            String prefix,
            Pageable pageable
    );
}
~~~

In modern Spring Data versions, `CrudRepository` and `PagingAndSortingRepository` are two separate interfaces. If a repository needs both CRUD and paging/sorting, declare both as shown in the example.

Some commonly used keywords:

| Keyword | Method example | SQL condition |
|---|---|---|
| And | findByStatusAndCustomerId | Two AND conditions |
| Or | findByStatusOrPriority | Two OR conditions |
| Between | findByCreatedAtBetween | Value range |
| GreaterThanEqual | findByCreatedAtGreaterThanEqual | >= |
| LessThan | findByCreatedAtLessThan | < |
| In | findByStatusIn | IN |
| IsNull | findByCancelledAtIsNull | IS NULL |
| StartingWith | findByOrderNumberStartingWith | LIKE prefix% |
| Containing | findByOrderNumberContaining | LIKE %value% |
| OrderBy | findByStatusOrderByCreatedAtDesc | ORDER BY |

Query derivation in Spring Data JDBC has limitations: it primarily supports simple properties directly on the aggregate root and does not automatically create arbitrary JOINs to filter by related tables.

For instance, `findByStatusAndCreatedAtBetween` works well because both `status` and `createdAt` are properties of `Order`. If you want to filter by `customer.name` or total amount calculated from `order_lines`, use a custom query or read model.

## 4. Dynamic filtering when parameters are optional

A search API often lets users supply only a subset of criteria. For example:

~~~text
GET /orders?status=PAID&from=2026-01-01&to=2026-02-01
~~~

Writing a repository method for every combination of status/from/to/customer would result in too many methods.

You can use `Criteria` and `JdbcAggregateTemplate` to construct dynamic conditions.

Filter object:

~~~java
public record OrderFilter(
        OrderStatus status,
        Instant createdFrom,
        Instant createdBefore
) {}
~~~

Custom service:

~~~java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

public class OrderSearchService {

    private final JdbcAggregateTemplate template;

    public OrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    public Page<Order> search(
            OrderFilter filter,
            Pageable pageable
    ) {
        Criteria criteria = Criteria.empty();

        if (filter.status() != null) {
            criteria = criteria.and("status").is(filter.status());
        }

        if (filter.createdFrom() != null) {
            criteria = criteria.and("createdAt")
                    .greaterThanOrEquals(filter.createdFrom());
        }

        if (filter.createdBefore() != null) {
            criteria = criteria.and("createdAt")
                    .lessThan(filter.createdBefore());
        }

        Query baseQuery = Query.query(criteria);

        Query pageQuery = baseQuery.with(pageable);

        List<Order> content = template.findAll(
                pageQuery,
                Order.class
        );

        long total = template.count(baseQuery, Order.class);

        return new PageImpl<>(content, pageable, total);
    }
}
~~~

`Criteria` and `Query` are immutable value objects. Every time you call `and` or `with`, you must assign the returned value to a variable to retain the new condition.

`Query.with(pageable)` applies the offset, limit, and sort from `Pageable`. Use the base query without page limits to count the total number of matching aggregates.

`JdbcAggregateTemplate.count(query, Order.class)` returns the number of aggregate roots matching the criteria. The resulting `PageImpl` contains the page content, `Pageable` metadata, and total count.

### 4.1. Note on property names vs. column names

`Criteria` uses the entity's property mapping. For example, the Java property `createdAt` is mapped to `created_at` according to the `NamingStrategy` or `@Column`.

When writing raw SQL in `@Query` or `JdbcTemplate`, you must use actual database column names, such as `created_at`. Do not mix Java property names with SQL column names.

### 4.2. Never pass input values as column names

Filter values must be bound as parameters. Never concatenate user input directly into SQL.

The Criteria API handles parameter binding. With `NamedParameterJdbcTemplate`, use named parameters. If dynamic sorting is needed in custom SQL, map the sort option through a whitelist of allowed columns rather than concatenating raw strings from the request.

## 5. Pagination: Page, Slice, and List

Spring Data supports multiple return types for query methods:

| Return type | Information | Query cost |
|---|---|---|
| Page<T> | Page content, page number, page size, total elements, and total pages | May run an additional count query |
| Slice<T> | Current content and whether a next page exists | Usually fetches one extra row to determine `hasNext` |
| List<T> + Pageable | Only the content within the page range | No `Page` metadata and no count query needed |
| List<T> + Sort | All matching results, sorted | No page limit |
| Stream<T> | Streams results incrementally | May keep the connection open until the stream is closed |

### 5.1. When to use Page?

Use `Page` when the UI needs to display:

- Total number of orders matching the filter.
- Total number of pages.
- A button to jump to the last page.
- Information like "viewing 21–40 of 537 orders".

Example:

~~~java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.desc("id")
        )
);

Page<Order> page = orders.findByStatusAndCreatedAtBetween(
        OrderStatus.PAID,
        from,
        to,
        pageable
);
~~~

`Page` typically requires a count query to determine total elements. Counting can be expensive if conditions are complex or tables are large.

### 5.2. When to use Slice?

If the UI only needs a "Load more" or "Next page" button, the total page count may not be necessary.

~~~java
Slice<Order> slice = orders.findByStatus(
        OrderStatus.PENDING,
        PageRequest.of(
                0,
                30,
                Sort.by(Sort.Order.desc("createdAt"))
        )
);
~~~

`Slice` only needs to know whether more data follows. Spring Data JDBC may fetch one extra row beyond the page size to determine `hasNext`.

### 5.3. When to use List with Pageable?

If the caller only needs a bounded result set and no `Page` metadata:

~~~java
List<Order> recentOrders = orders.findByOrderNumberStartingWith(
        "ORD-",
        PageRequest.of(
                0,
                50,
                Sort.by(Sort.Order.desc("createdAt"))
        )
);
~~~

This avoids the count query used to construct a `Page`. The caller manages pagination state itself if needed.

### 5.4. Stable sorting

Do not paginate by a column that can have duplicate values without a tie-breaker.

For example, many orders may share the same `createdAt`. If you sort only by `createdAt`, the ordering among rows with identical timestamps can be non-deterministic as the database executes queries for different pages.

Include a unique key as well:

~~~java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
);
~~~

This ordering makes results more stable across pages. With continuously changing data, offset pagination can still cause rows to shift between pages; consider keyset/seek pagination if the workload requires deep, stable navigation.

## 6. Limitations of @Query with pagination

Spring Data JDBC lets you write explicit SQL using `@Query`, but string-based queries do not support passing `Pageable`, `PageRequest`, `Sort`, or `Limit` like query derivation does.

This example is not a valid way to ask the framework to rewrite SQL automatically:

~~~java
@Query("SELECT * FROM orders WHERE status = :status")
Page<Order> findByStatus(
        OrderStatus status,
        Pageable pageable
);
~~~

With string-based `@Query`, if you need to limit results, you must write `LIMIT`/`OFFSET` or your database's equivalent syntax and bind the parameters explicitly.

Furthermore, a query returning an aggregate entity must supply columns matching the mapping/`RowMapper`. A report query returning a DTO should use a dedicated `RowMapper` or `ResultSetExtractor` when the result does not match an aggregate structure.

This is why you should choose derived queries for simple root filters and use custom repository fragments for complex report SQL.

## 7. Report projections: fetching only what is needed for display

A projection represents a subset of data needed for a read use case. It is not necessarily an aggregate root and should not be saved back using a repository `save`.

For example, an order list report needs:

- Order ID.
- Order number.
- Status.
- Customer name.
- Creation date.
- Total amount.
- Line count.

Create a DTO:

~~~java
import java.math.BigDecimal;
import java.time.Instant;

public record OrderReportRow(
        Long orderId,
        String orderNumber,
        String status,
        String customerName,
        Instant createdAt,
        BigDecimal totalAmount,
        long lineCount
) {}
~~~

SQL:

~~~sql
SELECT
    o.id AS order_id,
    o.order_number,
    o.status,
    c.name AS customer_name,
    o.created_at,
    COALESCE(
        SUM(ol.quantity * ol.unit_price),
        0
    ) AS total_amount,
    COUNT(ol.id) AS line_count
FROM orders o
JOIN customers c ON c.id = o.customer_id
LEFT JOIN order_lines ol ON ol.order_id = o.id
WHERE o.status = :status
GROUP BY
    o.id,
    o.order_number,
    o.status,
    c.name,
    o.created_at
ORDER BY o.created_at DESC, o.id DESC;
~~~

This SQL returns only one row per `Order` thanks to `GROUP BY`. `LEFT JOIN` retains orders that do not yet have lines. `COALESCE` turns the total amount of an order with no lines into `0`.

If joining multiple one-to-many collections simultaneously, watch out for cross products multiplying `SUM` and `COUNT`. In those cases, aggregate each collection in a separate subquery/CTE or use an appropriate query strategy.

## 8. Creating a custom repository fragment for reports

When a report requires `JOIN`, `GROUP BY`, a separate count query, and DTO mapping, a custom repository fragment is usually much cleaner than cramming everything into a method name.

Fragment interface:

~~~java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;

public interface OrderReportQuery {

    Page<OrderReportRow> findReport(
            OrderReportFilter filter,
            Pageable pageable
    );
}
~~~

Filter:

~~~java
public record OrderReportFilter(
        OrderStatus status,
        Instant createdFrom,
        Instant createdBefore
) {}
~~~

Main repository:

~~~java
public interface OrderRepository
        extends CrudRepository<Order, Long>,
                PagingAndSortingRepository<Order, Long>,
                OrderReportQuery {
}
~~~

Implementation:

~~~java
@Repository
public class OrderReportQueryImpl implements OrderReportQuery {

    private final NamedParameterJdbcTemplate jdbc;

    public OrderReportQueryImpl(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public Page<OrderReportRow> findReport(
            OrderReportFilter filter,
            Pageable pageable
    ) {
        StringBuilder where = new StringBuilder(" WHERE 1 = 1 ");
        MapSqlParameterSource params = new MapSqlParameterSource();

        if (filter.status() != null) {
            where.append(" AND o.status = :status ");
            params.addValue("status", filter.status().name());
        }

        if (filter.createdFrom() != null) {
            where.append(" AND o.created_at >= :createdFrom ");
            params.addValue("createdFrom", filter.createdFrom());
        }

        if (filter.createdBefore() != null) {
            where.append(" AND o.created_at < :createdBefore ");
            params.addValue("createdBefore", filter.createdBefore());
        }

        String joins = """
                FROM orders o
                JOIN customers c ON c.id = o.customer_id
                LEFT JOIN order_lines ol ON ol.order_id = o.id
                """;

        String countSql = """
                SELECT COUNT(DISTINCT o.id)
                """ + joins + where;

        long total = jdbc.queryForObject(
                countSql,
                params,
                Long.class
        );

        String dataSql = """
                SELECT
                    o.id AS order_id,
                    o.order_number,
                    o.status,
                    c.name AS customer_name,
                    o.created_at,
                    COALESCE(
                        SUM(ol.quantity * ol.unit_price),
                        0
                    ) AS total_amount,
                    COUNT(ol.id) AS line_count
                """ + joins + where + """
                GROUP BY
                    o.id,
                    o.order_number,
                    o.status,
                    c.name,
                    o.created_at
                ORDER BY o.created_at DESC, o.id DESC
                LIMIT :limit OFFSET :offset
                """;

        params.addValue("limit", pageable.getPageSize());
        params.addValue("offset", pageable.getOffset());

        List<OrderReportRow> content = jdbc.query(
                dataSql,
                params,
                (rs, rowNum) -> new OrderReportRow(
                        rs.getLong("order_id"),
                        rs.getString("order_number"),
                        rs.getString("status"),
                        rs.getString("customer_name"),
                        rs.getTimestamp("created_at").toInstant(),
                        rs.getBigDecimal("total_amount"),
                        rs.getLong("line_count")
                )
        );

        return new PageImpl<>(content, pageable, total);
    }
}
~~~

This example targets databases supporting `LIMIT`/`OFFSET` and timestamp types readable via JDBC `Timestamp`. For other databases, adjust pagination syntax and temporal reading to match the dialect/driver.

In this implementation, `ORDER BY` is fixed to `created_at DESC` and `id DESC`. `Pageable` only provides page size and offset; sorting in `Pageable` is not automatically applied to the custom fragment's SQL. If the API needs dynamic sorting, map the sort key through a whitelist and construct `ORDER BY` from application-approved columns.

The count query uses `COUNT(DISTINCT o.id)` because joining `order_lines` can produce multiple rows for a single order. Counting `COUNT(*)` directly would multiply the order count by the number of order lines.

### 8.1. Why does a report need a separate count query?

`Page<OrderReportRow>` needs the total number of orders matching the filter. Because the report query uses `GROUP BY` and `JOIN`, the count query must count distinct order roots under the exact same filter conditions.

The count query must use the same predicates as the data query. If a filter is added to the data query but forgotten in the count query, `totalElements` and `totalPages` will be wrong.

### 8.2. Protecting dynamic SQL

In the example, all filter values are bound using named parameters. Column names, `JOIN`s, and `ORDER BY` are SQL structures controlled by the application.

Do not write:

~~~java
String sql = "SELECT * FROM orders WHERE status = '" + status + "'";
~~~

Also, do not concatenate column names or sort directions directly from the request:

~~~java
sql += " ORDER BY " + request.getSortField();
~~~

If you want to let users choose a sort field, map the request value through a whitelist:

~~~java
String sortColumn = switch (sortKey) {
    case "createdAt" -> "o.created_at";
    case "orderNumber" -> "o.order_number";
    case "status" -> "o.status";
    default -> "o.created_at";
};
~~~

Direction must also be restricted to `ASC` or `DESC`. Parameter binding protects values; it cannot bind column names or SQL keywords.

## 9. How does a projection differ from an aggregate entity?

| Characteristic | Order aggregate | OrderReportRow |
|---|---|---|
| Purpose | Business processing | Display/reporting |
| Data | Full aggregate per mapping | Only needed columns |
| Has OrderLine collection | Possibly | Only aggregated metrics |
| Repository save | Yes | No |
| Multi-table JOIN | Not the primary goal of aggregate mapping | Well-suited |
| Mapping | Spring Data JDBC aggregate converter | RowMapper/custom mapping |
| Used for commands | Yes | Should not be |
| Used for dashboards | May fetch too much data | Well-suited |

Do not call `repository.save(reportRow)` or try to turn a report DTO into an aggregate. Projections are read models.

If you need to update an `Order`, load the aggregate via `OrderRepository`, invoke domain methods, and save. If you only need to display a report table, read the projection directly from the database.

## 10. Deep pagination and keyset pagination

Offset pagination is simple:

~~~sql
SELECT id, order_number, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT :limit OFFSET :offset;
~~~

However, when the offset is large, the database may have to scan many rows before returning results. When data changes between requests, rows can also shift across pages.

Keyset pagination uses the last values from the previous page to fetch the next page.

Suppose the previous page ended at:

~~~text
created_at = 2026-10-10T10:00:00Z
id         = 150
~~~

Next page query:

~~~sql
SELECT id, order_number, created_at
FROM orders
WHERE
    created_at < :lastCreatedAt
    OR (
        created_at = :lastCreatedAt
        AND id < :lastId
    )
ORDER BY created_at DESC, id DESC
LIMIT :limit;
~~~

The condition uses both `created_at` and `id` to establish a unique total ordering. An index matching the column pair used for sorting and filtering is needed.

Keyset pagination fits feeds, transaction histories, and large lists requiring continuous forward navigation. It does not directly provide total page counts like offset-based `Page`.

## 11. Validating filters and pageable inputs

Input filters must be validated before querying:

- `from` must not be after `to`.
- Page number must be non-negative.
- Page size must be greater than 0.
- Page size should have a maximum limit.
- Sort key must be in the whitelist.
- Status enums must belong to valid values.
- Search strings should have a length limit.

Example:

~~~java
public Pageable normalize(Pageable requested) {
    int page = Math.max(requested.getPageNumber(), 0);

    int size = Math.min(
            Math.max(requested.getPageSize(), 1),
            100
    );

    Sort sort = Sort.by(
            Sort.Order.desc("createdAt"),
            Sort.Order.desc("id")
    );

    return PageRequest.of(page, size, sort);
}
~~~

In a real API, you might return a 400 error when page or size is invalid instead of silently clamping values. The example illustrates one normalization policy; choose the contract suited to your API.

Do not allow users to sort by unsupported properties or sensitive columns that the query/report does not intend to expose.

## 12. Indexes and query plans for order filters

Filtering by `status` + `created_at` typically aligns with a composite index:

~~~sql
CREATE INDEX ix_orders_status_created_at
ON orders(status, created_at DESC);
~~~

If queries always sort by `created_at` and `id`, evaluate this index:

~~~sql
CREATE INDEX ix_orders_status_created_id
ON orders(status, created_at DESC, id DESC);
~~~

For filtering by customer:

~~~sql
CREATE INDEX ix_orders_customer_created
ON orders(customer_id, created_at DESC);
~~~

For `order_lines`, an index on `order_id` helps JOINs and per-order aggregations:

~~~sql
CREATE INDEX ix_order_lines_order
ON order_lines(order_id);
~~~

Indexes carry write and storage costs. Use `EXPLAIN`/`EXPLAIN ANALYZE` on your target database to determine which indexes help. Do not create an index merely because a column appears in a rarely used filter.

## 13. Transactions and report consistency

A report query joins multiple tables. If data changes during the query, results depend on isolation level and the database.

For example, one transaction updates `OrderLine` while a report is computing total amounts. Depending on the isolation level, the report may see a consistent snapshot or database-specific semantics.

If the report only displays recent summary data, an ordinary read transaction may suffice. If financial reporting needs a consistent snapshot across multiple queries, explicitly define the isolation level, transaction boundary, and data retrieval strategy.

When `Page` runs separate data and count queries, those two queries might observe different points in time if not inside an appropriate transaction. This can cause content size and total count to diverge slightly under concurrent writes.

If the business requires total and content to share the exact same snapshot, run both queries in a transaction with an appropriate isolation level for your database. Do not raise isolation levels arbitrarily, as that can affect concurrency.

## 14. Testing filters, pagination, and projections

Test each condition individually and in combination:

| Test case | What to verify |
|---|---|
| No filter passed | Returns all orders in query scope |
| Filter by status | Returns only the requested status |
| Filter `from` | Excludes rows before start timestamp |
| Filter `to` | Excludes rows at/after exclusive upper bound |
| Filter `from` + `to` | Correct time interval |
| First page | Offset 0 and proper limit |
| Next page | No duplicates or omissions on stable data |
| Sort with tie-breaker | Stable order when `createdAt` ties |
| Empty page | Empty content, accurate total |
| Slice | Accurate `hasNext` without needing total |
| Report without lines | Total amount 0 and `lineCount` 0 |
| Report with multiple lines | Accurate SUM and COUNT |
| Count query | Counts distinct orders, not joined rows |
| SQL filters | Binds parameters, does not concatenate input into SQL |
| Target database | Dialect, timestamps, and LIMIT/OFFSET work properly |

Repository test example:

~~~java
@DataJdbcTest
class OrderRepositoryTest {

    @Autowired
    OrderRepository orders;

    @Test
    void returnsOnlyPaidOrdersInRequestedPage() {
        Pageable pageable = PageRequest.of(
                0,
                10,
                Sort.by(
                        Sort.Order.desc("createdAt"),
                        Sort.Order.desc("id")
                )
        );

        Page<Order> result = orders.findByStatusAndCreatedAtBetween(
                OrderStatus.PAID,
                Instant.parse("2026-01-01T00:00:00Z"),
                Instant.parse("2026-02-01T00:00:00Z"),
                pageable
        );

        assertThat(result.getContent())
                .allMatch(order -> order.getStatus() == OrderStatus.PAID);

        assertThat(result.getSize()).isEqualTo(10);
    }
}
~~~

This test illustrates basic assertions. Test data must be prepared to verify boundary timestamps, sorting, and the count query.

### 14.1. Testing the report query

Reports should be tested with data having varying numbers of order lines:

~~~text
Order A: 2 lines, total 150
Order B: 0 lines, total 0
Order C: 3 lines, total 420
~~~

Assertions to check:

- Each order appears only once.
- `lineCount` is correct.
- `totalAmount` is correct.
- Orders without lines still appear when using `LEFT JOIN`.
- Page total counts `Order`s, not `OrderLine`s.

Run tests against the same database type as production if the SQL uses database-specific syntax or types.

## 15. Process for building search and reporting features

1. Determine which data belongs to the `Order` aggregate and which is needed only for the read model.
2. Define `OrderFilter` with optional criteria.
3. Use derived queries for simple filters on aggregate root properties.
4. Use `Criteria` and `JdbcAggregateTemplate` when dynamically combining root conditions.
5. Choose `Page` if total count is needed; choose `Slice` or `List` + `Pageable` if not.
6. Always sort deterministically using a unique key as a tie-breaker.
7. Create a DTO projection for reports, dashboards, or table views.
8. Use a custom repository fragment and `RowMapper` for `JOIN`/`GROUP BY`.
9. Write a separate count query and ensure it counts distinct aggregate roots.
10. Bind all filter values; whitelist all dynamic sort columns and directions.
11. Check indexes and query plans on the target database.
12. Test page boundaries, empty results, aggregations, and concurrent updates.

## 16. Common pitfalls

| Symptom | Possible cause | Resolution |
|---|---|---|
| Repository has too many search methods | Creating a method for every optional filter combination | Use `Criteria`/`Query` to build conditions dynamically |
| Derived query cannot filter `customer.name` | JDBC query derivation is limited to simple properties on the aggregate root | Use `JOIN` in a custom query/report fragment |
| Page query runs slowly | Count query or filter lacks indexes | Measure count separately and inspect execution plan |
| Count exceeds number of orders | Joining child rows produces multiple rows per root | Use `COUNT(DISTINCT order_id)` |
| Orders without lines disappear from report | Using `INNER JOIN` with `order_lines` | Use `LEFT JOIN` if empty orders should appear |
| Total amount is multiplied | Joining multiple collections creates a cross product | Aggregate separately via subqueries/CTEs |
| `@Query` ignores `Pageable` | Spring Data JDBC string-based queries do not support dynamic `Pageable`/`Sort` | Use derived queries or bind `LIMIT`/`OFFSET` manually |
| DTO fails to map | Custom query defaults to entity `RowMapper` | Use a custom `RowMapper`/`ResultSetExtractor` or custom repository |
| Pages have duplicate or missing rows | Unstable sort or data changing between requests | Add ID tie-breaker; consider keyset pagination |
| Page total disagrees with content | Data and count queries use different conditions or run at different snapshots | Share predicates and use appropriate transaction isolation |
| Sort causes SQL injection | Concatenating sort field from request into SQL | Whitelist columns and directions |
| Page size too large | API parameter is uncapped | Validate and enforce a maximum page size |
| List view loads too much data | Loading full aggregates when only a few columns are needed | Use a DTO projection/read model |
| Report query returns too many rows | Incorrect `GROUP BY` or `JOIN` | Check cardinality and query plan |
| H2 passes while production fails | Dialect or data type differences | Test against target database/Testcontainers |

## 18. Key takeaways

- Derived queries fit simple filters on direct properties of the aggregate root.
- Query derivation in Spring Data JDBC does not automatically generate arbitrary `JOIN`s for other aggregates' properties.
- Use `Criteria` and `JdbcAggregateTemplate` when building dynamic conditions.
- `Page` provides total element counts and may require a count query; `Slice` only checks if more data follows.
- `Pageable` supports offset, limit, and sorting for query methods; sorting needs a unique tie-breaker.
- String-based `@Query` in Spring Data JDBC does not automatically accept `Pageable`/`Sort`/`Limit`; if pagination is needed, write SQL limits and bind parameters manually.
- DTO projections fit reports, dashboards, and list views requiring `JOIN`/`aggregation`.
- A custom repository fragment with `NamedParameterJdbcTemplate` and `RowMapper` is a clean choice for complex report SQL.
- Count queries must count distinct aggregate roots when joining one-to-many collections.
- `LEFT JOIN` retains aggregates without children; `COALESCE` handles empty aggregations.
- Never concatenate input into SQL; bind values and whitelist sort fields/directions.
- Query count, execution plans, indexes, and returned row counts should all be measured when optimizing.
