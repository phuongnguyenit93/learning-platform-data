# Controlling isNew with Persistable

## 1. Why does Spring Data JDBC need to know if an entity is new?

In Spring Data JDBC, the `repository.save(entity)` method can execute either `INSERT` or `UPDATE`. The framework must decide which write path is appropriate before generating the SQL statement. That decision is based on the **entity's new state**, typically represented by `isNew`.

With database auto-generated primary keys, detection is straightforward: a new entity has no ID yet, whereas a persisted entity usually has an ID. However, many systems **assign IDs themselves before writing data**:

- The ID is a UUID generated with `UUID.randomUUID()` in the application.
- The ID is a business code or natural key present from the start.
- The data originates from an external source that already supplied the key.

In such cases, the newly created entity already has a non-`null` ID. Relying solely on the ID can lead Spring Data JDBC to mistake the entity as already existing and choose `UPDATE`. We need a clearer way to express state.

`Persistable<ID>` is a Spring Data contract that lets an entity **provide the answer to "am I a new entity?" itself** through the `isNew()` method. This lesson explains how to use that contract, manage an in-memory state flag, and avoid common insert/update bugs.

## 2. Default state detection mechanism

If an entity does not implement `Persistable`, Spring Data uses its default state detection strategy. Essentially:

1. If the entity has an eligible version property, the version is checked first: an unpopulated version indicates the entity is still new; once saved, the version has a value.
2. If there is no version property, Spring Data inspects the ID: a `null` ID usually means a new entity; a non-`null` ID is usually treated as an existing entity.

The exact version rules also depend on property type and Spring Data version; with a reference-type version like `Long`, `null` is a common signal for a new entity. When using `Persistable`, Spring Data delegates the decision to the entity's own `isNew()`.

### Example: UUID already present before insert

```java
UUID id = UUID.randomUUID();
Customer customer = new Customer(id, "Lan");
repository.save(customer);
```

At the time `save` is called, `customer.getId()` already has a value. Without a version property or custom strategy, the default mechanism can recognize this as an existing entity and take the update path. Yet no row with that UUID exists in the database.

**A populated ID does not mean the record has already been saved.** The ID only identifies a record; the new state tells the framework whether to create the record or update it.

## 3. What is `Persistable<ID>`?

`Persistable` resides in the `org.springframework.data.domain` package:

```java
public interface Persistable<ID> {
    ID getId();
    boolean isNew();
}
```

This is a simple contract:

- `getId()` returns the entity's key.
- `isNew()` answers whether the current entity needs to be inserted.

When an entity implements `Persistable`, Spring Data uses `isNew()` to determine the save operation:

| `isNew()` result | Chosen save path | Meaning |
| --- | --- | --- |
| `true` | `INSERT` | Entity is treated as new, even when ID is already assigned. |
| `false` | `UPDATE` | Entity is treated as existing; framework updates by ID. |

`Persistable` is not a SQL command, nor does it query the database to check whether the ID exists. It is **state information supplied by the entity**. Therefore, the implementation must accurately reflect the object's lifecycle.

## 4. When should Persistable be used?

`Persistable` is useful when:

- The application generates a UUID or other key before inserting.
- The primary key is a natural code already present in the input data.
- New/existing detection rules cannot be accurately expressed using null IDs or versions.
- You want explicit control over when an object transitions from new to persisted state.

A typical example is a system receiving an identifier generated by an upstream service. When creating a new aggregate, the code already exists in memory, yet the database has no matching row.

There is no need to implement `Persistable` on every entity. If the database auto-generates IDs and new entities have `null` IDs, the default mechanism is simpler and involves less state to manage. If a version property already expresses new state appropriately, consider using it before adding a custom flag.

## 5. Designing a state flag with @Transient

A common implementation keeps a boolean flag that exists only in memory:

- A new entity created via a business factory/constructor sets `newEntity = true`.
- After a successful insert, the application sets the flag to `false`.
- When the entity is read from the database, the flag is not loaded from the table and defaults to `false`.

To prevent the flag from becoming a SQL column, annotate it with `org.springframework.data.annotation.Transient`.

### Why not use a boolean column in the database?

The `isNew` state serves a technical decision within a persistence lifecycle. It is not business data meant to be stored long-term. Storing that flag as a column would mean:

- The flag can drift out of sync with the actual existence of the row.
- Every read of the entity must handle that flag in the database.
- A persistence-state column gets mixed into the business schema.
- Two systems writing to the same table might interpret the flag differently.

Thus, this flag should remain transient state on the object.

## 6. Complete example: self-assigned UUID and Persistable

Suppose a customer management system. The application generates a UUID as soon as registration starts, before sending the insert statement. We use Spring Data JDBC and H2 for illustration.

### 6.1. Dependencies and database configuration

With Gradle Groovy DSL:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jdbc'
    runtimeOnly 'com.h2database:h2'
}
```

Create `src/main/resources/application.properties`:

```properties
spring.datasource.url=jdbc:h2:mem:persistable_demo;DB_CLOSE_DELAY=-1
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=
spring.sql.init.mode=always

logging.level.org.springframework.jdbc=DEBUG
```

Create `src/main/resources/schema.sql`:

```sql
CREATE TABLE "customers" (
    "id" UUID PRIMARY KEY,
    "name" VARCHAR(120) NOT NULL
);
```

H2 supports the `UUID` type. The schema quotes table/column names consistently with the mapping in the example. When moving to another database, verify the UUID type and identifier quoting conventions for the target dialect.

### 6.2. Entity implementing Persistable

Create `src/main/java/com/example/persistable/Customer.java`:

```java
package com.example.persistable;

import java.util.Objects;
import java.util.UUID;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer implements Persistable<UUID> {

    @Id
    private UUID id;

    private String name;

    // Not mapped to a database column.
    // Defaults to false: objects materialized from the database are existing objects.
    @Transient
    private boolean newEntity;

    // Constructor for Spring Data JDBC when reading data.
    protected Customer() {
    }

    private Customer(UUID id, String name) {
        this.id = Objects.requireNonNull(id, "id is required");
        this.name = requireName(name);
        this.newEntity = true;
    }

    public static Customer register(String name) {
        return new Customer(UUID.randomUUID(), name);
    }

    public static Customer registerWithId(UUID id, String name) {
        return new Customer(id, name);
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    // Call only after repository.save(...) completes successfully.
    void markNotNew() {
        this.newEntity = false;
    }

    public String getName() {
        return name;
    }

    public void rename(String newName) {
        this.name = requireName(newName);
    }

    private static String requireName(String value) {
        Objects.requireNonNull(value, "name is required");
        String normalized = value.trim();
        if (normalized.isEmpty()) {
            throw new IllegalArgumentException("name must not be blank");
        }
        return normalized;
    }
}
```

Analysis:

1. `Customer implements Persistable<UUID>`, so Spring Data calls `isNew()` instead of looking solely at the ID to determine new state.
2. `id` is assigned immediately in the factory using `UUID.randomUUID()`, so it is non-null even before insert.
3. `newEntity` defaults to `false`. When created via `register(...)`, the constructor sets it to `true`.
4. `@Transient` excludes this flag from database mapping. The `customers` table does not need a `new_entity` column.
5. When Spring Data JDBC reads a row and reconstructs `Customer` via the no-arg constructor, the transient flag keeps its default value `false`. The loaded entity is treated as existing.
6. `markNotNew()` is an internal operation to complete the lifecycle after insert.

We use a class rather than a record because the `newEntity` flag must change after saving. An immutable record is unsuitable for holding this mutable lifecycle state directly.

### 6.3. Repository

Create `src/main/java/com/example/persistable/CustomerRepository.java`:

```java
package com.example.persistable;

import java.util.UUID;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, UUID> {
}
```

The repository provides basic operations. No manual implementation is needed for `save`, `findById`, or `deleteById`.

### 6.4. Service managing the isNew flag lifecycle

Create `src/main/java/com/example/persistable/CustomerService.java`:

```java
package com.example.persistable;

import java.util.UUID;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public UUID register(String name) {
        Customer candidate = Customer.register(name);

        // candidate has a non-null UUID, yet isNew() == true.
        Customer saved = customers.save(candidate);

        // Mark as existing only after the save operation succeeds.
        saved.markNotNew();
        return saved.getId();
    }

    @Transactional(readOnly = true)
    public Customer find(UUID id) {
        return customers.findById(id)
                .orElseThrow(() ->
                        new IllegalArgumentException("Customer not found"));
    }

    @Transactional
    public void rename(UUID id, String newName) {
        Customer customer = customers.findById(id)
                .orElseThrow(() ->
                        new IllegalArgumentException("Customer not found"));

        customer.rename(newName);
        customers.save(customer);
    }
}
```

Here, the service ensures the sequence:

1. Create an object with an ID and `isNew() == true`.
2. Call `save`; Spring Data chooses `INSERT`.
3. Once save returns successfully, call `markNotNew()` on the returned object.
4. When read back, the new object is materialized with `newEntity == false`.
5. When renaming and calling `save`, Spring Data chooses `UPDATE`.

Updating the flag right after a successful insert prevents a saved object from still claiming to be new and causing the next `save` call to attempt an insert again.

> This example uses standard transactions for illustration. The `newEntity` flag is in-memory state; if a transaction rolls back after the object has been marked, do not reuse that object as a source of truth. Reload the aggregate in a new transaction or reconstruct the object from business state.

### 6.5. Running the demo

Create `src/main/java/com/example/persistable/PersistableApplication.java`:

```java
package com.example.persistable;

import java.util.UUID;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class PersistableApplication {

    public static void main(String[] args) {
        SpringApplication.run(PersistableApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(CustomerService service) {
        return args -> {
            UUID id = service.register("Lan");
            System.out.println("Registered id = " + id);

            Customer loaded = service.find(id);
            System.out.println("Loaded name = " + loaded.getName());
            System.out.println("Loaded isNew = " + loaded.isNew());

            service.rename(id, "Lan Nguyen");

            Customer changed = service.find(id);
            System.out.println("Updated name = " + changed.getName());
            System.out.println("Updated isNew = " + changed.isNew());
        };
    }
}
```

Run at the project root:

```bash
./gradlew bootRun
```

On Windows PowerShell:

```powershell
.\gradlew.bat bootRun
```

Expected console output:

```text
Registered id = <a generated UUID>
Loaded name = Lan
Loaded isNew = false
Updated name = Lan Nguyen
Updated isNew = false
```

This is an illustrative result. The SQL log will look similar to:

```sql
-- First save: isNew() == true
INSERT INTO "customers" ("id", "name")
VALUES (?, ?);

-- Read
SELECT "customers"."id", "customers"."name"
FROM "customers"
WHERE "customers"."id" = ?;

-- Save after renaming: isNew() == false
UPDATE "customers"
SET "name" = ?
WHERE "id" = ?;
```

Exact column names, quoting, and log formatting depend on the dialect and Spring Data JDBC version. What matters is seeing `INSERT` the first time even though the ID already has a value, and `UPDATE` the next time.

## 7. Why must the flag be updated after save?

Suppose we create a customer:

```java
Customer customer = Customer.register("Lan");
System.out.println(customer.getId()); // non-null UUID
System.out.println(customer.isNew()); // true
```

Spring Data JDBC calls `isNew()` and chooses insert. After inserting, the database has a row with that UUID. If the flag remains `true`:

```java
customers.save(customer); // INSERT
customers.save(customer); // May still go to INSERT again
```

The second save can fail due to a primary key violation. Therefore, the flag must switch to `false` after the insert finishes:

```java
Customer saved = customers.save(customer);
saved.markNotNew();

customers.save(saved); // UPDATE
```

Do not set `newEntity = false` **before** calling `save`. If the insert fails, the object would claim to already exist even though no row is in the database.

### Why not set the flag to false as soon as the ID is created?

An ID assigned before insert only proves the application chose an identifier. It does not prove the database has persisted the entity. This is precisely why `Persistable` exists: persistence state and ID value are two independent pieces of information.

## 8. How does a reloaded entity get isNew() equal to false?

A common question: `newEntity` is transient, so the database does not store this flag. When reading a row back, why doesn't `isNew()` become `true`?

In the example, the field is declared as:

```java
@Transient
private boolean newEntity;
```

The default value of a Java boolean is `false`. The no-arg constructor used for mapping does not set the flag to true. Spring Data JDBC materializes persistent properties from the database row; the `@Transient` field is not read from any column and stays `false`.

The factory for creating new objects is the only place setting the flag to true:

```java
private Customer(UUID id, String name) {
    this.id = id;
    this.name = name;
    this.newEntity = true;
}
```

This is a convention that must be kept consistent: every flow creating a new entity must go through a factory/constructor that sets the flag; do not instantiate the object another way and forget the state.

If using a custom mapping constructor, builder, or copy mechanism, ensure the object's transient state is initialized properly. Do not add `newEntity` to a persistent constructor expecting the framework to read it from the database, because no such column exists.

## 9. Comparing Persistable with @Version and null IDs

There are three common approaches:

| Detection method | When appropriate | Advantages | Cost/risk |
| --- | --- | --- | --- |
| `null` ID | Database generates ID on insert | Simple, no extra flag needed | Unsuitable if IDs are always pre-assigned. |
| Nullable `@Version` property | Entity has a version and wants optimistic locking | Version supports concurrency while helping detect new state | Requires a version column and understanding Spring Data version rules. |
| `Persistable.isNew()` | Pre-assigned IDs or custom state rules | Explicit control over insert/update | Flag lifecycle must be managed accurately; wrong state picks wrong SQL. |

### When @Version is present

For an entity with:

```java
@Id
private UUID id;

@Version
private Long version;
```

For a new entity, `version == null` can be used to detect new state even when the ID is already assigned. On save, the framework updates the version. If versioning fits, this is often a more natural way to detect state and catch concurrent writes.

When an entity implements `Persistable`, remember that the `isNew` decision is delegated to your method. Do not assume that version will override a wrong `isNew()` return value. If choosing `Persistable`, take responsibility for maintaining the flag and still use `@Version` separately for optimistic locking if required by business rules.

### When should Persistable be avoided?

- New IDs are `null` and the database generates IDs normally.
- A version property already satisfies both detection and concurrency control needs.
- The development team lacks a clear convention for object creation and marking persisted.
- Entities are constructed directly from requests or deserialized in multiple places, allowing clients to control the flag.

Avoid adding `Persistable` just to force a particular SQL statement. Use it when the new/existing state model genuinely requires its own decision source.

## 10. Persistable is not upsert

`isNew()` only decides whether the framework takes the insert or update branch; it does not ask the database to check and choose an operation automatically.

| Actual database state | `isNew()` | Expected behavior | Possible outcome |
| --- | --- | --- | --- |
| ID not yet in DB | `true` | `INSERT` | Succeeds if no constraints are violated. |
| ID already in DB | `true` | `INSERT` | Primary key duplicate error. |
| ID already in DB | `false` | `UPDATE` | Updates the row by ID. |
| ID not in DB | `false` | `UPDATE` | Cannot create a new row; update may report zero rows updated. |

Therefore:

- Do not always return `true` just because the entity has a UUID.
- Do not always return `false` just because the entity has an ID.
- Do not use `isNew()` as an existence-check query.
- Do not expect Spring Data JDBC to automatically perform `INSERT ... ON CONFLICT DO UPDATE` or `MERGE` when using `Persistable`.

If business logic requires "create if absent, update if present", that is an upsert use case. Design clear semantics, constraints, and appropriate database-specific SQL, or load the entity and update it within a controlled workflow.

## 11. Common implementation mistakes

### Mistake 1: having a UUID without implementing Persistable

**Symptom:** calling `save` with a new object, yet logs show `UPDATE` or report no row found to update.

**Cause:** ID is already non-null, so the default mechanism treats the object as existing (when no version property overrides the strategy).

**Fix:** use `Persistable` with an accurate `isNew()`, or use a nullable `@Version` if it fits the model.

### Mistake 2: isNew() always returns true

**Symptom:** every `save` call attempts to insert; the second call violates the primary key.

**Cause:** flag was not flipped to false after insert, or the object was recreated from a factory when it should have been loaded from the repository.

**Fix:** update the flag after a successful save; entities read from the database must have new=false state.

### Mistake 3: isNew() always returns false

**Symptom:** an entity that has never been persisted takes the update branch.

**Cause:** factory did not set the flag to true or the field was initialized incorrectly.

**Fix:** centralize new-entity creation in factories/constructors; test `isNew()` before calling the repository.

### Mistake 4: persisting the flag as a database column

**Symptom:** Spring Data looks for a non-existent `new_entity` column or the schema gains a technical state column.

**Cause:** forgot `@Transient` or imported the wrong annotation.

**Fix:** use `org.springframework.data.annotation.Transient`, not an annotation of the same name from another library; verify SQL mapping and schema.

### Mistake 5: setting the flag to false before insert

**Symptom:** insert fails yet the object reports it already exists; the next retry enters update.

**Cause:** state was mutated before the persistence operation succeeded.

**Fix:** only switch the flag after `save` returns successfully; do not reuse an object after a transaction rollback as if it reflected DB state.

### Mistake 6: client requests directly controlling isNew

**Symptom:** JSON payloads cause the application to choose insert/update unexpectedly.

**Cause:** using the persistence entity as a request DTO or allowing binding onto the state field.

**Fix:** accept separate DTOs/commands, validate permissions and identity in the service, and then create entities via factories. The `isNew` flag must be managed by the backend.

### Mistake 7: thinking Persistable checks row existence

**Symptom:** `isNew()` returns false, yet the ID is not in the DB and update fails.

**Cause:** confusing state detection with existence checks.

**Fix:** understand `isNew` as an operation-selection hint. If an existence check is needed, use a repository query or design constraints/upserts as required.

## 12. Managing the flag via callbacks: when is it needed?

The example above updates the flag explicitly in the service:

```java
Customer saved = repository.save(candidate);
saved.markNotNew();
```

This is readable and makes responsibility clear. In applications that save the same aggregate type in many places, you can consider Spring Data Relational's lifecycle callback mechanism to centralize marking after save. However, callbacks must be registered using the right API for your project's Spring Data version; ensure that:

- The callback only marks the object after a successful save operation.
- Objects materialized from the database are not mistakenly marked as new.
- The field remains excluded from mapping with `@Transient`.
- Insert/update tests verify the callback is invoked on the expected path.

Do not add callbacks merely to avoid a single `markNotNew()` line if the application only has one entity creation use case. Callbacks are a shared lifecycle mechanism, but they can make state transitions harder to see when a team is unfamiliar with them.

Another option is using a factory combined with a dedicated repository adapter so all insert/update commands pass through one place. Whichever option you choose, there must be **a single place responsible for transitioning state**, avoiding having controllers, services, and repositories each mutate the flag in their own way.

## 13. Testing isNew behavior and actual SQL

Tests should verify both in-object state and persistence results.

### Unit testing the factory

```java
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertTrue;

import org.junit.jupiter.api.Test;

class CustomerTest {

    @Test
    void newCustomerHasAssignedIdAndIsNew() {
        Customer customer = Customer.register("Lan");

        assertNotNull(customer.getId());
        assertTrue(customer.isNew());
    }

    @Test
    void markNotNewChangesPersistenceState() {
        Customer customer = Customer.register("Lan");

        customer.markNotNew();

        assertFalse(customer.isNew());
    }
}
```

In a real project, if `markNotNew()` is package-private, the test can reside in the same package. This test only verifies in-memory state rules; it does not prove SQL insert/update behavior.

### Integration testing with a database

A persistence test should verify:

1. Create `Customer` via factory: non-null ID, `isNew() == true`.
2. Call `repository.save`: a row with that UUID appears in the table.
3. Mark as persisted using the chosen mechanism.
4. Reload via `findById`: name matches and `isNew() == false`.
5. Rename and call `save`: still only one row with the same ID, name updated.
6. No `newEntity` column in the schema and no flag data in SQL.

When verifying SQL paths, enable `org.springframework.jdbc` logging or use your project's datasource proxy/SQL instrumentation. Do not merely assert that `save` throws no exception; a zero-row update and a successful insert are two different business outcomes.

## 15. Takeaways

Spring Data JDBC must know whether an entity is new or existing to choose `INSERT` or `UPDATE`. The default mechanism checks the version property first and then the ID. When the application assigns IDs before inserting, a non-null ID is no longer a reliable indicator of new state.

`Persistable<ID>` lets an entity supply that state itself via `isNew()`. A common implementation keeps a `@Transient` flag in memory: the factory creating new entities sets it to true, the service sets it to false after a successful save, and entities read from the database default to false. This flag must be managed consistently because it determines the SQL write path.

Use `Persistable` when you genuinely need control over new/existing state, keep flag-update rules in one clear place, and test both inserts and updates. **`Persistable` does not check existence automatically, does not replace constraints, and is not an upsert mechanism.**
