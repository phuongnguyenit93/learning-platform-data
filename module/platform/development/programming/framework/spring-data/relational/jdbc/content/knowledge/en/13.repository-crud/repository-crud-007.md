# `delete`, `deleteById`, `deleteAllById`, and `deleteAll` in Spring Data JDBC

In **Spring Data JDBC**, repositories extending `CrudRepository` provide several ways to delete aggregates: passing an object, passing an ID, passing a set of IDs, or requesting deletion of all aggregates in the repository. Four commonly used APIs are `delete`, `deleteById`, `deleteAllById`, and `deleteAll`.

These methods differ in **input and selection scope**, yet all must be understood within Spring Data JDBC's aggregate model. If `PurchaseOrder` is an aggregate root owning `OrderLine` items, deleting an order means deleting that aggregate, including its mapped child elements. Therefore, you cannot assume each method deletes only a single row in the root table.

This lesson explains the API signatures, how to choose the appropriate method, effects on foreign key relationships, transactions, performance, bulk deletion, and common mistakes.

## 1. The four delete methods in `CrudRepository`

A Spring Data JDBC CRUD repository is typically declared as:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

`CrudRepository<T, ID>` provides the primary delete methods:

~~~java
void delete(T entity);

void deleteById(ID id);

void deleteAllById(Iterable<? extends ID> ids);

void deleteAll(Iterable<? extends T> entities);

void deleteAll();
~~~

Where:

- `T` is the aggregate root type managed by the repository.
- `ID` is the type of the property marked with `@Id`.
- These methods return `void`; to verify business outcomes, the application must check conditions and load needed data itself.

### 1.1. Quick comparison table

| Method | Input | Deletion Scope | Typical Usage |
|---|---|---|---|
| `delete(entity)` | One aggregate object | Aggregate with matching identifier | Already loaded the aggregate and decided to delete that object |
| `deleteById(id)` | One ID | Aggregate with the specified ID | Only have the ID; no need to hold the object in calling code |
| `deleteAllById(ids)` | Iterable of IDs | Aggregates whose IDs are in the list | Have a list of identifiers to delete |
| `deleteAll(entities)` | Iterable of aggregates | Aggregates in the collection | Already have the specific objects to delete |
| `deleteAll()` | No input | All aggregates belonging to the repository | Clearing all data in a controlled environment |

**Note:** the name `deleteAll` can lead learners to think it corresponds to SQL `TRUNCATE TABLE`. Do not assume that. The API carries aggregate-deletion semantics for the repository; Spring Data JDBC must handle aggregate components and related constraints.

## 2. Example model: an order with multiple order lines

To understand aggregate deletion, use two tables:

~~~text
purchase_orders
├── id (PK)
├── order_number
└── status

order_lines
├── id (PK)
├── order_id (FK -> purchase_orders.id)
├── product_id
└── quantity
~~~

An order can contain multiple order lines. `PurchaseOrder` is the aggregate root, and `OrderLine` belongs to the order's lifecycle:

~~~java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;
    private String status;

    @MappedCollection(idColumn = "order_id")
    private Set<OrderLine> lines = new LinkedHashSet<>();

    // Constructors, getters, and business methods omitted.
}
~~~

Child table with foreign key:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_lines (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

When saving the aggregate, `@MappedCollection(idColumn = "order_id")` tells Spring Data JDBC that `order_id` links child rows to the root. When deleting the root through the repository, the framework handles aggregate components according to the mapping so child rows are not left behind as orphaned data.

This differs from another table that merely **references** the order. For example, a `Shipment` with an independent lifecycle and a `purchase_order_id` pointing to the order is not automatically a child entity deleted along with the aggregate. Distinguish aggregate ownership from an arbitrary foreign key.

## 3. `delete(entity)`: deleting one aggregate object

`delete(entity)` accepts an object of the aggregate root type:

~~~java
PurchaseOrder order = repository.findById(1001L)
    .orElseThrow();

repository.delete(order);
~~~

Usage flow:

1. The application loads the order to be deleted.
2. Status and deletion permissions can be checked at the service layer.
3. Call `delete(order)` to instruct the repository to delete the corresponding aggregate.

This method fits when business logic already needs the object to validate preconditions before deletion, such as only permitting deletion of orders in `DRAFT` status.

### 3.1. Deletes by identifier, not by all object fields

Do not interpret `delete(order)` as “find a row matching all columns of this object and delete it.” This operation deletes the entity identified by its identifier. Fields such as `orderNumber` or `status` do not become deletion filter predicates merely because they are present on the object.

Accordingly, do not construct a dummy object with only a few fields and pass it to `delete(entity)` like an arbitrary SQL predicate. If you only have the ID, `deleteById(id)` expresses the intent more clearly.

### 3.2. Object no longer in the database

Per the CRUD repository contract, deleting an entity not found in the persistence store is usually silently ignored. Therefore, do not rely on `delete(order)` to prove that a record definitely existed and was deleted exactly once.

If a use case needs to return results like “deleted,” “not found,” or “not eligible for deletion,” design those checks and return values at the service layer. When concurrent updates or optimistic locking are involved, handle the corresponding exceptions.

## 4. `deleteById(id)`: deleting when only the ID is available

When calling code only knows the primary key, it can use:

~~~java
repository.deleteById(1001L);
~~~

Service example:

~~~java
@Service
public class OrderDeletionService {

    private final PurchaseOrderRepository orders;

    public OrderDeletionService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void deleteDraft(long orderId) {
        PurchaseOrder order = orders.findById(orderId)
            .orElseThrow(() ->
                new NoSuchElementException("Order not found"));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Only DRAFT orders can be deleted");
        }

        orders.deleteById(orderId);
    }
}
~~~

Here the service loads the aggregate first to enforce business rules. Once preconditions pass, the service uses `deleteById` because the final deletion target is already identified by ID.

### 4.1. Non-existent ID

Per the `CrudRepository` contract, if the ID does not exist in the persistence store, `deleteById` is ignored. The method does not return a boolean indicating how many rows were actually deleted.

If an external API needs to return HTTP `404` when absent, check beforehand or use a statement/mechanism that determines affected row counts. However, a “check-then-delete” pattern can encounter race conditions if data changes between the two operations. When strict guarantees are needed, design concurrency handling and transactions appropriately.

### 4.2. Do not use `deleteById` to bypass domain rules

A controller calling directly:

~~~java
repository.deleteById(orderId);
~~~

can bypass checks such as order status, ownership, or audit-history requirements. Have the controller invoke an application service; the service loads the aggregate, applies rules, and instructs the repository to delete.

## 5. `deleteAllById(ids)`: deleting by a set of IDs

When you have a list of IDs:

~~~java
List<Long> ids = List.of(1001L, 1002L, 1003L);
repository.deleteAllById(ids);
~~~

The method accepts `Iterable<? extends ID>`, so the input does not have to be a `List`. You can pass a `Set`, collection, or another suitable iterable.

Example:

~~~java
Set<Long> selectedIds = Set.of(1001L, 1005L, 1010L);
repository.deleteAllById(selectedIds);
~~~

### 5.1. How does it differ from looping `deleteById`?

Semantically, `deleteAllById(ids)` expresses a request to delete multiple aggregates by ID. Do not assume this API always turns into **a single SQL statement** or an optimal database-level bulk delete. Actual execution depends on the Spring Data JDBC implementation and version; aggregate deletion must also account for mapped child elements.

If performance is critical, measure the actual SQL emitted, round-trip count, ID set size, and how the framework processes aggregates. Do not assume that having `All` in the name guarantees the database only receives one `DELETE ... WHERE id IN (...)`.

### 5.2. Missing IDs and duplicate IDs

If the iterable contains non-existent IDs, a CRUD repository normally ignores them per delete semantics. If the iterable contains duplicate IDs, do not rely on how many times the framework processes that ID; normalize the input list with a `Set` when the intent is deleting each identifier once.

Never pass `null` as the iterable or as an ID element. Validate input before calling the repository, especially when IDs arrive from HTTP requests or imported files.

### 5.3. Example service deleting a batch of draft orders

~~~java
@Service
public class BulkOrderService {

    private final PurchaseOrderRepository orders;

    public BulkOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void deleteDraftOrders(Collection<Long> ids) {
        if (ids == null || ids.isEmpty()) {
            return;
        }

        Set<Long> uniqueIds = new LinkedHashSet<>(ids);

        // This example assumes the use case has already verified eligible IDs.
        orders.deleteAllById(uniqueIds);
    }
}
~~~

This snippet only illustrates normalizing the list and setting a transaction boundary. In a real system, if only `DRAFT` orders may be deleted, the service must load/check the corresponding aggregates or use an appropriate query mechanism to verify the condition before deletion. You cannot rely solely on the method name `deleteAllById` to protect status rules.

## 6. `deleteAll(entities)`: deleting a set of aggregate objects

When you already hold the aggregate objects to delete, use:

~~~java
List<PurchaseOrder> ordersToDelete = List.of(orderA, orderB);
repository.deleteAll(ordersToDelete);
~~~

This method fits when calling code has already loaded the objects and performed business checks on them. Example:

~~~java
List<PurchaseOrder> selected = new ArrayList<>();

for (Long id : requestedIds) {
    PurchaseOrder order = repository.findById(id)
        .orElseThrow(() ->
            new NoSuchElementException("Order not found: " + id));

    if (!"DRAFT".equals(order.getStatus())) {
        throw new IllegalStateException(
            "An order is not in DRAFT status");
    }
    selected.add(order);
}

repository.deleteAll(selected);
~~~

This expresses the intent clearly when each aggregate must be validated before deletion. For large datasets, loading all objects and child collections can consume significant memory and issue many queries; reconsider the approach instead of defaulting to this method for millions of aggregates.

### 6.1. Difference from `deleteAllById`

| Difference | `deleteAllById(ids)` | `deleteAll(entities)` |
|---|---|---|
| Input | IDs | Aggregate objects |
| Requires objects in calling code? | No | Yes |
| Fits best when | Only have identifiers to delete | Already loaded objects and need domain checks |
| Target | Delete by ID | Delete the supplied aggregates |
| Guaranteed bulk SQL? | No | No |

Do not construct dummy entities from IDs and pass them into `deleteAll(entities)` merely to match parameter types. Using `deleteAllById` directly expresses the intent and avoids incomplete objects.

## 7. `deleteAll()`: deleting all aggregates in the repository

The parameterless method:

~~~java
repository.deleteAll();
~~~

has the broadest scope: it requests deletion of **all aggregate roots managed by the repository**. If the repository manages `PurchaseOrder`, it can delete all orders along with their owned `OrderLine` items according to the mapping.

This operation is useful for:

- Cleaning up test data in test environments.
- Resetting an aggregate table's data in development environments.
- Intentional administrative procedures with strict permission and environment controls.

Never invoke `deleteAll()` from public endpoints or regular business flows. Calling it on the wrong repository or environment can wipe out all data for that aggregate type.

### 7.1. Not synonymous with `TRUNCATE`

`deleteAll()` is a repository API. It does not guarantee:

- Executing a single `TRUNCATE TABLE` SQL statement.
- Resetting identity/sequences.
- Bypassing foreign keys or triggers.
- Deleting data in independent aggregates merely because they reference the root.
- Matching the performance of a database-specific truncate command.

Spring Data JDBC must respect aggregate mapping and relational constraints. If you need to truncate tables in tests or migrations, that is a separate SQL operation requiring awareness of all related tables and schema management mechanisms.

### 7.2. Caution with multi-tenant repositories

If an application shares tables across multiple tenants, `deleteAll()` has no automatic awareness of the current user's tenant scope. A standard CRUD repository will not turn this operation into “delete all aggregates for the current tenant.” Design queries and services with explicit tenant predicates; never use `deleteAll()` for tenant-scoped deletion.

## 8. What happens to child tables and foreign keys?

This is particularly important in Spring Data JDBC. Suppose:

~~~text
purchase_orders
id = 1001

order_lines
id = 1, order_id = 1001
id = 2, order_id = 1001
id = 3, order_id = 1002
~~~

When deleting the `PurchaseOrder` aggregate with ID `1001`, the `OrderLine` items belonging to that aggregate must be handled along with the root. Expected result:

~~~text
Before:
  purchase_orders: 1001, 1002
  order_lines:     (1,1001), (2,1001), (3,1002)

After deleting aggregate 1001:
  purchase_orders: 1002
  order_lines:     (3,1002)
~~~

Spring Data JDBC learns the ownership relationship from `@MappedCollection` and manages aggregate components when deleting the root. Exact SQL statement ordering depends on the implementation; from a constraint standpoint, child rows must be handled so deleting the parent row does not violate foreign keys.

### 8.1. Foreign keys from other aggregates

Suppose there is a `shipments` table:

~~~sql
CREATE TABLE shipments (
    id BIGINT PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL,
    tracking_number VARCHAR(80) NOT NULL,
    FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_orders(id)
);
~~~

If `Shipment` is an independent aggregate, deleting `PurchaseOrder` does not automatically mean deleting `Shipment`. The foreign key may block deleting the root, or the database may apply a configured `ON DELETE` action. The application must make a business decision:

- Disallow order deletion if a shipment already exists.
- Cancel the shipment in a separate use case before deleting the order.
- Use soft delete or store a canceled status instead of physical deletion.
- Choose a database cascade action if it aligns with the lifecycle and impacts have been evaluated.

Do not confuse **a child entity owned by the aggregate** with **another aggregate holding a referencing foreign key**.

### 8.2. Should `ON DELETE CASCADE` be added?

`ON DELETE CASCADE` can be used at the database level in some models, though it is not required just for Spring Data JDBC to understand `@MappedCollection`. Aggregate mapping and database constraints are two separate layers.

If database cascading runs alongside the framework explicitly deleting child elements, verify actual behavior, triggers, and auditing. Pick one consistent design and test migrations on the target database.

## 9. Transactions when deleting one or more aggregates

Deleting an aggregate often requires multiple database operations, especially with child tables. If the use case also includes checks or updates to related data, place a transaction at the service layer so steps succeed or roll back together as required.

~~~java
@Service
public class OrderService {

    private final PurchaseOrderRepository orders;

    public OrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public void cancelAndDeleteDraft(long id) {
        PurchaseOrder order = orders.findById(id)
            .orElseThrow(() ->
                new NoSuchElementException("Order not found"));

        if (!"DRAFT".equals(order.getStatus())) {
            throw new IllegalStateException(
                "Only draft orders can be deleted");
        }

        // Audit logging or related business operations can happen here.
        orders.delete(order);
    }
}
~~~

Spring manages the transaction for the service method when calls go through the proxy. By default, unchecked exceptions trigger rollback; if checked exceptions or custom rollback rules apply, configure them appropriately.

### 9.1. Does deleting multiple aggregates need one transaction?

That depends on business requirements:

- If the requirement is “delete the whole group or nothing,” place the entire operation inside one transaction.
- If each order can be deleted independently and the set is very large, process in small batches, each with its own transaction and progress tracking.
- If external service calls are involved, do not hold a database transaction open while waiting on slow network I/O. Consider asynchronous workflows, outbox, or sagas where appropriate.

`deleteAllById` and `deleteAll(entities)` do not return the count of deleted records for building progress metrics. If audit counts are needed, design your own measurement and recording mechanism.

### 9.2. Optimistic locking and delete operations

If an aggregate has `@Version`, the version participates in Spring Data JDBC's optimistic locking mechanism. When data changes concurrently, the application must handle optimistic locking exceptions according to the framework version and deletion path used. Use freshly loaded aggregates from the database and avoid holding stale objects too long before deletion.

Do not catch and ignore every exception. A conflict may indicate that state has changed and deletion conditions are no longer valid.

## 10. Physical deletion vs soft delete

`CrudRepository`'s `delete...` methods express **removing aggregates from the persistence store**. They do not automatically become soft deletes.

Soft delete means the row remains present but is marked, for example:

~~~sql
ALTER TABLE purchase_orders
ADD COLUMN deleted_at TIMESTAMP NULL;
~~~

Instead of calling `deleteById`, the application updates the column:

~~~java
@Modifying
@Query("""
    UPDATE purchase_orders
    SET deleted_at = CURRENT_TIMESTAMP
    WHERE id = :id AND deleted_at IS NULL
    """)
int markDeleted(@Param("id") Long id);
~~~

This is an illustrative custom SQL example; exact annotations and query signatures must match the Spring Data JDBC version in use. Another option is loading the aggregate, updating `deletedAt` state, and calling `save()` on the root.

When using soft delete, you must define:

- Do regular queries exclude deleted rows?
- Is restoration allowed?
- Do unique constraints include deleted rows?
- Are child tables marked as well?
- Do reports and audits need to see deleted data?

Simply adding `deleted_at` is not enough for the entire application to automatically skip deleted data. Consistent filtering must be applied across queries, repositories, and services.

## 11. Performance and large-scale deletion

Not every method with “All” in its name is bulk SQL. For multi-table aggregates, Spring Data JDBC must preserve ownership relationships and delete related components. Thus, cost depends on:

- Number of aggregates to delete.
- Number of child entities in each aggregate.
- Number of database round-trips.
- Indexes on primary keys and foreign keys.
- Triggers, foreign keys, and constraints.
- Transaction size and contention with concurrent transactions.

### 11.1. Deleting by individual ID

~~~java
for (Long id : ids) {
    repository.deleteById(id);
}
~~~

This gives fine-grained control per ID but can generate many repository calls. Use it when counts are small or per-item error handling is needed.

### 11.2. Using `deleteAllById`

~~~java
repository.deleteAllById(ids);
~~~

This API expresses the intent to delete multiple aggregates by ID. Still measure actual SQL behavior in the version you use, especially when aggregates contain child collections.

### 11.3. Using direct bulk SQL

When very large data cleanups are required, you can consider custom SQL via Spring JDBC. However, direct bulk SQL **bypasses the repository's lifecycle and aggregate rules**. You must handle child/parent deletion order, auditing, constraints, events, and business invariants yourself.

For example, relationally, when explicitly deleting orders for a set of IDs:

~~~sql
DELETE FROM order_lines
WHERE order_id IN (1001, 1002, 1003);

DELETE FROM purchase_orders
WHERE id IN (1001, 1002, 1003);
~~~

Both statements must execute inside an appropriate transaction. This only illustrates relational ordering; do not copy it straight into production without verifying other child aggregates, auditing, foreign keys, and deletion permissions.

### 11.4. Batch deletion

For large datasets, small batches keep transaction duration and memory bounded. A batch process should:

1. Fetch a group of IDs by a stable criterion.
2. Confirm deletion conditions.
3. Delete within the batch's transaction.
4. Record results and errors.
5. Continue from a safe checkpoint.

If you use offset pagination while deleting rows matched by that same query, you can skip data as row positions shift. Use keyset pagination or a stable snapshot/ID range fitting the data model.

## 12. Common errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Deleting root fails due to foreign key | Another table references the root or child mapping is incorrect | Distinguish owned children from referencing aggregates; handle per business rules |
| Child rows remain after deletion | Child relation is not mapped into the aggregate or data was written outside the repository | Check `@MappedCollection`, schema, and write paths |
| Called `deleteAll()` intending to delete only one tenant | Chose an unconditional API | Write tenant-scoped queries/services; never call delete-all |
| `delete(entity)` does not filter by status | Method deletes by identifier, not by all fields as predicates | Use conditional queries or check business rules in the service |
| Assumed `deleteAllById` runs a single SQL statement | Confused API name with a bulk statement | Inspect SQL and benchmark on your version |
| Deleting multiple aggregates fails midway | Transaction boundary does not match atomicity needs | Decide between group transaction vs batch transactions |
| Called delete while needing to retain history | Using physical deletion | Design appropriate soft delete/auditing |
| Batch deletion skips records | Offset pagination over a changing dataset | Use keyset pagination or stable ID sets |
| Deleting an order unexpectedly affects shipments | Confused referencing foreign key with ownership | Separate aggregates and define explicit deletion workflows |

## 13. Which API to choose in real scenarios?

| Scenario | Usually Suitable API | Reason |
|---|---|---|
| Already loaded the aggregate and need to delete that object | `delete(entity)` | Intent is tied to the validated object |
| Only received an ID from a request and don't need the object in calling code | `deleteById(id)` | Minimal input, explicit identifier |
| Have a list of IDs to delete | `deleteAllById(ids)` | Expresses a set of identifiers |
| Already loaded and validated multiple aggregates | `deleteAll(entities)` | Deletes the exact selected objects |
| Resetting all repository data in a controlled environment | `deleteAll()` | Scoped to all aggregates of the repository |
| Deleting with business conditions or tenant scope | Dedicated service/query | Basic delete APIs do not accept predicates |
| Massive deletion needing custom SQL optimization | Controlled bulk SQL | Must manually manage aggregates, FKs, and audits |
| Need to keep history | Soft delete or canceled status | `delete...` removes from the persistence store |

## 15. Conclusion

`delete(entity)` deletes the aggregate specified by object; `deleteById(id)` deletes by one identifier; `deleteAllById(ids)` takes a set of IDs; `deleteAll(entities)` takes a collection of aggregate objects; and `deleteAll()` requests deletion of all aggregates in the repository. The primary differences lie in inputs and selection scope.

In **Spring Data JDBC**, delete operations must be understood through aggregate boundaries. If the root owns child entities via `@MappedCollection`, deleting the root handles the aggregate's components as well. Another table merely referencing the root via a foreign key is not automatically deleted alongside it; that rule depends on ownership, constraints, and business logic.

Place deletion conditions, authorization, and transactions in the application service; pick the repository API matching the data you hold; measure performance when deleting many aggregates; and use soft delete if the system must preserve history. Above all, never treat `deleteAll()` as `TRUNCATE` or treat `deleteAllById()` as a guarantee of a single bulk SQL statement.
