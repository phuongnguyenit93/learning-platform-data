# Đánh giá thiết kế, xử lý lỗi và tiêu chí sẵn sàng triển khai

Một ứng dụng Spring Data JDBC chỉ sẵn sàng triển khai khi mô hình aggregate, schema, transaction, xử lý lỗi và vận hành phối hợp đúng trong môi trường thật. Repository test thành công là bằng chứng cần thiết, nhưng chưa đủ để kết luận hệ thống có thể chịu tải, phục hồi sau lỗi hoặc triển khai an toàn.

Bài thực hành tổng hợp này đưa ra cách đánh giá một ứng dụng Spring Data JDBC trước khi phát hành. Nội dung đi từ ranh giới aggregate và mapping đến concurrency, transaction, exception handling, observability, bảo mật, migration và rollback. Mục tiêu là biến các quyết định thiết kế thành những điều có thể kiểm chứng bằng test, metrics, migration rehearsal và runbook.

## 1. Đánh giá toàn hệ thống theo use case

Bắt đầu bằng cách chọn một số use case quan trọng nhất, ví dụ:

- Tạo đơn hàng cùng các dòng hàng.
- Thanh toán hoặc đổi trạng thái đơn hàng.
- Cập nhật thông tin khách hàng.
- Tìm kiếm đơn hàng theo nhiều bộ lọc.
- Chạy batch import.
- Xử lý message hoặc tác vụ theo lịch.

Với mỗi use case, ghi lại:

1. Aggregate root nào được đọc và ghi?
2. Repository hoặc query adapter nào được gọi?
3. Transaction bắt đầu và kết thúc ở đâu?
4. Các invariant nghiệp vụ nào phải luôn đúng?
5. Có thể xảy ra lỗi database hoặc lỗi hệ thống ngoài nào?
6. Khi retry, thao tác có an toàn và idempotent không?
7. Metrics/logs nào chứng minh use case đang hoạt động bình thường?

Một bảng use case giúp thấy các khoảng trống:

| Use case | Aggregate/adapter | Transaction | Rủi ro chính | Bằng chứng cần có |
|---|---|---|---|---|
| Tạo đơn hàng | PurchaseOrderRepository | Một transaction ghi | FK, generated ID, duplicate request | Integration test và idempotency test |
| Duyệt đơn hàng | PurchaseOrderRepository | Một transaction ghi | Stale version, transition không hợp lệ | Optimistic locking test |
| Tìm kiếm đơn hàng | Read query adapter | Read-only nếu phù hợp | Pagination, query latency | Query contract và execution plan |
| Import batch | Application service + JDBC | Theo chunk hoặc từng item | Retry, dữ liệu lỗi, transaction dài | Batch recovery test |
| Gửi thông báo | Outbox + worker | Ghi outbox cùng aggregate | Gửi lặp hoặc mất message | Outbox delivery/retry test |

Không đánh giá hệ thống chỉ theo số lượng repository. Hãy đánh giá theo đường đi của dữ liệu và các điểm có thể thất bại trong một use case thực tế.

## 2. Kiểm tra ranh giới aggregate

Spring Data JDBC lưu dữ liệu theo aggregate root. Một aggregate nên chứa những entity cần được thay đổi và bảo vệ cùng nhau theo invariant nghiệp vụ.

Khi review aggregate, hãy hỏi:

- Có một root rõ ràng không?
- Child có thực sự thuộc vòng đời root không?
- Có child collection tăng không giới hạn không?
- Có use case thường xuyên cập nhật child độc lập không?
- Có bảng ngoài tham chiếu trực tiếp đến child row không?
- Có transaction nào phải cập nhật nhiều aggregate cùng lúc không?
- Có invariant nào chỉ có thể kiểm tra khi giữ toàn bộ aggregate trong một transaction không?

Ví dụ:

~~~java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        BigDecimal total,
        @MappedCollection(idColumn = "order_id", keyColumn = "line_no")
        List<OrderLine> lines
) {}
~~~

Nếu OrderLine là thành phần của đơn hàng, thay đổi line có thể cần kiểm tra tổng tiền, số lượng và trạng thái đơn. Giữ line trong aggregate giúp domain rule tập trung.

Nếu một collection có hàng chục nghìn phần tử và được cập nhật độc lập, cần xem lại ranh giới. Tách child thành aggregate riêng có thể giảm tải save root, nhưng chuyển consistency sang application service hoặc transaction coordination.

Không tách aggregate chỉ để giảm số câu SQL. Quyết định phải dựa trên invariant và vòng đời domain.

## 3. Đánh giá mapping và schema

Mọi property persistent cần có mapping và schema tương thích.

Review các điểm:

- @Table và @Column khớp tên bảng/cột.
- @Id phù hợp chiến lược generated hoặc assigned ID.
- @Version có cột tương ứng và được kiểm thử.
- @MappedCollection dùng đúng idColumn/keyColumn.
- @Embedded có prefix và semantics null phù hợp.
- Custom converters có cả chiều đọc và ghi khi cần.
- Java type khớp JDBC/database type.
- Nullability trong entity khớp NOT NULL và default.
- Primary key, unique constraint, foreign key và index phản ánh invariant.
- Migration thực tế tạo ra schema giống integration test.

Ví dụ schema:

~~~sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    total DECIMAL(18, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE order_lines (
    order_id BIGINT NOT NULL,
    line_no INTEGER NOT NULL,
    sku VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    unit_price DECIMAL(18, 2) NOT NULL,
    PRIMARY KEY (order_id, line_no),
    CONSTRAINT fk_order_lines_order
        FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
);
~~~

Database constraint là lớp bảo vệ cuối cùng cho dữ liệu. Validation ở Java giúp trả lỗi dễ hiểu, nhưng không thay thế unique/FK/check constraint vì có thể có nhiều request hoặc ứng dụng cùng ghi database.

## 4. Kiểm tra aggregate save và chi phí child collection

Khi save một aggregate đã tồn tại, Spring Data JDBC có thể xóa các referenced entities, cập nhật root rồi chèn lại referenced entities theo trạng thái collection hiện tại. Framework không giữ snapshot trước đó để diff từng child row.

Điều này cần được đưa vào đánh giá hiệu năng nếu aggregate có collection lớn.

Với N child rows, số hàng child bị delete và insert có thể gần 2N dù chỉ một child thay đổi. Đây là ước lượng row changes; số SQL statements/batches thực tế phụ thuộc dialect, driver và mapping.

Đo riêng:

- Save chỉ đổi property của root.
- Save đổi một child.
- Save đổi một phần collection.
- Save thay toàn bộ collection.
- Custom targeted update nếu nghiệp vụ cho phép.

Theo dõi p50/p95/p99, rows affected, transaction duration, database CPU/I/O, lock wait và transaction log. Không thay đổi thiết kế chỉ dựa trên cảm giác query chậm; hãy xác định use case và cardinality gây ra chi phí.

Nếu dùng custom SQL để cập nhật child, phải giữ version, invariant, audit, transaction và trạng thái object trong bộ nhớ nhất quán.

## 5. Transaction boundary phải rõ ràng

Transaction thường nên được đặt ở application service bao quanh một use case nghiệp vụ:

~~~java
@Service
public class OrderCommandService {

    private final PurchaseOrderRepository orders;

    public OrderCommandService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder approve(Long id) {
        PurchaseOrder current = orders.findById(id).orElseThrow();
        PurchaseOrder approved = current.approve();
        return orders.save(approved);
    }
}
~~~

Điểm cần kiểm tra:

- Method được gọi qua Spring proxy.
- Repository và JdbcTemplate dùng cùng DataSource nếu cần cùng transaction.
- Transaction manager quản lý đúng DataSource.
- Không tự mở connection độc lập rồi commit riêng.
- Không giữ transaction mở trong lúc gọi HTTP hoặc thao tác chờ lâu.
- Isolation và timeout phù hợp với use case.
- Các thao tác cần atomicity nằm trong cùng transaction vật lý.

Không đặt @Transactional ở mọi method chỉ để “an toàn”. Transaction quá rộng giữ connection và lock lâu, làm tăng contention và giảm throughput.

## 6. Kiểm tra rollback và exception rules

Mặc định Spring transaction thường rollback khi RuntimeException hoặc Error thoát khỏi transaction boundary. Checked exception không tự động rollback trong mọi cấu hình mặc định.

Nếu nghiệp vụ yêu cầu rollback với checked exception, khai báo rõ:

~~~java
@Transactional(rollbackFor = ImportValidationException.class)
public void importOrder(ImportCommand command)
        throws ImportValidationException {
    // Thay đổi dữ liệu trong transaction.
}
~~~

Nếu exception bị bắt và không được ném ra khỏi method transactional, transaction interceptor có thể không biết use case đã thất bại. Khi bắt exception, cần quyết định rõ:

- Có thể phục hồi và tiếp tục không?
- Có nên ném lại để rollback không?
- Có cần đánh dấu rollback-only không?
- Có cần trả kết quả lỗi một phần cho batch không?

Không nuốt exception database rồi trả success. Nếu lỗi được xử lý tại chỗ, phải có trạng thái kết quả rõ ràng và bảo đảm transaction semantics phù hợp.

## 7. Phân loại lỗi persistence

Spring chuyển nhiều lỗi JDBC thành hệ thống exception thuộc DataAccessException. Phân loại giúp application layer quyết định retry, trả lỗi client hoặc báo lỗi vận hành.

| Nhóm lỗi | Ví dụ | Hướng xử lý |
|---|---|---|
| Dữ liệu không hợp lệ | Vi phạm NOT NULL, CHECK | Trả lỗi validation/domain phù hợp |
| Trùng dữ liệu | Unique constraint violation | Xác định conflict hoặc idempotent duplicate |
| Không tìm thấy | Repository findById trả Optional.empty | Xử lý not-found theo use case |
| Optimistic locking | Version không còn khớp | Báo conflict hoặc yêu cầu đọc lại |
| Deadlock/serialization | Database hủy transaction do xung đột | Chỉ retry có giới hạn nếu thao tác an toàn |
| Connection failure | Database mất kết nối | Fail fast, circuit/health signal và phục hồi connection |
| Timeout | Query hoặc transaction vượt thời hạn | Điều tra query, lock và cấu hình timeout |
| Mapping/conversion | Không chuyển được JDBC type | Sửa mapping/converter và dữ liệu |

Không nên trả stack trace hoặc SQL nội bộ cho client. Log exception ở server với correlation ID và trả lỗi API theo contract.

## 8. Optimistic locking và xung đột đồng thời

Với aggregate có @Version, Spring Data JDBC sử dụng version để phát hiện cập nhật dựa trên trạng thái cũ.

Ví dụ hai request cùng đọc version 4:

1. Request A cập nhật và commit, version thành 5.
2. Request B vẫn giữ object version 4.
3. Request B save; update không khớp version hiện tại.
4. Spring Data JDBC báo optimistic locking failure.

Đây là xung đột nghiệp vụ/concurrency, không phải lỗi hệ thống luôn cần retry tự động.

Cách xử lý:

- Trả HTTP 409 Conflict nếu client cần tải lại dữ liệu.
- Đọc lại aggregate và yêu cầu người dùng xác nhận thay đổi.
- Tự hợp nhất chỉ khi domain rule cho phép.
- Retry có giới hạn chỉ khi thao tác có thể được tính lại an toàn.

Không bắt mọi exception rồi retry. Nếu nghiệp vụ phụ thuộc giá trị người dùng đã xem, retry tự động có thể ghi đè quyết định dựa trên dữ liệu cũ.

## 9. Deadlock, lock wait và retry

Deadlock thường xảy ra khi các transaction giữ khóa theo thứ tự khác nhau. Database sẽ chọn một transaction làm nạn nhân và rollback nó.

Biện pháp giảm:

- Giữ transaction ngắn.
- Truy cập bảng/hàng theo thứ tự nhất quán.
- Có index cho điều kiện UPDATE/DELETE.
- Tránh xử lý ngoài database trong transaction.
- Giảm batch/chunk size nếu transaction quá lớn.
- Đo lock wait và deadlock trên DBMS.

Nếu retry lỗi transient, cần:

- Chỉ retry exception đã xác định là retryable.
- Giới hạn số lần thử.
- Dùng exponential backoff có jitter.
- Có timeout tổng.
- Bảo đảm command idempotent hoặc có idempotency key.
- Không lặp side effect ngoài database.

Ví dụ pseudocode:

~~~java
for (int attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
        return transactionTemplate.execute(status ->
                orderWriter.apply(command)
        );
    } catch (TransientDataAccessException ex) {
        if (attempt == maxAttempts) {
            throw ex;
        }
        backoff(attempt);
    }
}
~~~

Đây là khung ý tưởng. Trong ứng dụng thật, transaction phải được tạo mới cho mỗi lần thử; không retry bên trong một transaction đã bị đánh dấu rollback-only. Cần dùng retry abstraction hoặc transaction template đúng cách.

## 10. Idempotency cho request và message

Một request có thể được gửi lại vì timeout ở client dù database đã commit. Message broker cũng có thể giao lại message. Nếu xử lý lại không an toàn, ứng dụng có thể tạo đơn hàng hoặc charge thanh toán nhiều lần.

Có thể dùng idempotency key:

~~~sql
CREATE TABLE processed_commands (
    command_id VARCHAR(80) PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL
);
~~~

Trong cùng transaction:

1. Thử ghi command ID.
2. Nếu ID đã tồn tại, xác định command đã xử lý và trả kết quả đã lưu hoặc kết quả tương ứng.
3. Nếu ghi thành công, thực hiện thay đổi aggregate.
4. Lưu kết quả xử lý nếu API cần trả lại response ổn định.
5. Commit cả marker và aggregate cùng nhau.

Idempotency key cần gắn với phạm vi người dùng/tenant và loại command phù hợp. Không dùng một key toàn cục không giới hạn nếu các request khác nhau có thể vô tình trùng giá trị.

## 11. Side effect ngoài database và transactional outbox

Gửi email, gọi HTTP, publish message hoặc charge dịch vụ thanh toán không tự rollback cùng transaction JDBC.

Ví dụ nguy hiểm:

~~~java
@Transactional
public void approve(Long id) {
    PurchaseOrder order = orders.findById(id).orElseThrow();
    orders.save(order.approve());
    emailClient.sendApproval(order);
}
~~~

Nếu email gửi thành công nhưng transaction database rollback, hệ thống ngoài đã nhận thông báo trong khi database không ghi nhận trạng thái duyệt.

Transactional outbox giải quyết bằng cách ghi sự kiện vào bảng outbox cùng transaction với aggregate:

~~~sql
CREATE TABLE outbox_events (
    id UUID PRIMARY KEY,
    aggregate_type VARCHAR(80) NOT NULL,
    aggregate_id VARCHAR(80) NOT NULL,
    event_type VARCHAR(120) NOT NULL,
    payload TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL,
    published_at TIMESTAMP
);
~~~

Transaction ghi aggregate và outbox row. Worker riêng đọc event chưa publish, gửi tới broker rồi đánh dấu đã gửi. Worker phải xử lý delivery lặp bằng event ID/idempotency.

Outbox không tạo exactly-once delivery tự động; nó cung cấp cách tin cậy hơn để không mất sự kiện giữa commit database và publish. Consumer vẫn cần idempotent.

## 12. Batch và transaction dài

Import hàng nghìn bản ghi trong một transaction có thể:

- Giữ connection lâu.
- Tăng lock duration.
- Tạo transaction log lớn.
- Khó retry nếu lỗi ở cuối batch.
- Tăng thời gian rollback.
- Gây ảnh hưởng tới workload trực tuyến.

Có thể chia batch thành chunk:

~~~java
for (List<ImportRow> chunk : chunks(rows, chunkSize)) {
    importChunkService.persist(chunk);
}
~~~

Nếu importChunkService là Spring bean với @Transactional, mỗi chunk có transaction riêng. Điều đó cho phép retry hoặc báo lỗi theo chunk, nhưng thay đổi semantics: các chunk trước có thể đã commit khi chunk sau thất bại.

Chọn chiến lược theo nghiệp vụ:

- All-or-nothing: một transaction lớn nếu dữ liệu và thời gian cho phép.
- Chunk commit: chấp nhận kết quả một phần và lưu tiến độ.
- Staging table: nạp dữ liệu trước, validate rồi chuyển vào bảng chính.
- Asynchronous job: trả job ID, theo dõi tiến độ và lỗi.

Không dùng @Transactional trên method tự gọi nội bộ cùng object rồi kỳ vọng proxy tạo transaction mới cho mỗi chunk; self-invocation không đi qua proxy mặc định.

## 13. Migration schema và triển khai tương thích

Schema migration là một phần của readiness. Một thay đổi entity mà không có migration tương ứng sẽ làm ứng dụng lỗi khi triển khai.

Với thay đổi không tương thích, dùng chiến lược expand-and-contract:

1. **Expand**: thêm cột/bảng/index mới theo cách code cũ vẫn chạy.
2. Deploy code có thể đọc/ghi tương thích cả schema cũ và mới khi cần.
3. Backfill dữ liệu theo batch có thể theo dõi và retry.
4. Chuyển read/write sang cấu trúc mới.
5. Xác nhận dữ liệu và metrics ổn định.
6. **Contract**: xóa cột hoặc cấu trúc cũ ở release sau.

Không xóa/rename cột ngay trong cùng release nếu nhiều instance cũ vẫn đang chạy và còn truy cập cột đó.

Migration cần được chạy thử trên bản sao schema/dữ liệu đại diện, đo thời gian, lock và dung lượng. Index creation trên bảng lớn có thể có cách thực hiện online/concurrent riêng theo DBMS.

## 14. Rollback ứng dụng và rollback dữ liệu

Rollback binary không tự động rollback schema hoặc dữ liệu đã chuyển đổi.

Trước deploy, xác định:

- Có thể chạy code cũ với schema mới không?
- Migration có destructive không?
- Backfill có thể chạy lại không?
- Có thể đảo ngược dữ liệu không?
- Nếu không thể reverse, có forward-fix migration không?
- Cần backup/snapshot trước bước nào?
- Ai quyết định rollback và điều kiện kích hoạt là gì?

Với migration destructive, có thể cần giữ cột cũ trong một hoặc nhiều release. Rollback an toàn thường là deploy code tương thích schema mới, hoặc forward-fix thay vì cố khôi phục schema cũ sau khi dữ liệu đã thay đổi.

## 15. Observability: log, metrics và tracing

Production readiness cần trả lời được:

- Request nào gây lỗi?
- Repository/query nào chậm?
- Database có đang bão hòa connection pool không?
- Deadlock, timeout hoặc optimistic conflict có tăng không?
- Migration hoặc batch job đang ở trạng thái nào?

### Logging

Log có cấu trúc nên chứa:

- Correlation ID/trace ID.
- Use case hoặc operation name.
- Aggregate ID khi phù hợp và không nhạy cảm.
- Kết quả thành công/thất bại.
- Exception class và mã lỗi nội bộ.
- Thời gian thực thi.

Không log password, token, session secret hoặc toàn bộ dữ liệu cá nhân. SQL bind parameters có thể chứa thông tin nhạy cảm; chỉ bật log chi tiết trong môi trường có kiểm soát.

### Metrics

Các metric hữu ích:

| Metric | Ý nghĩa |
|---|---|
| Request latency p50/p95/p99 | Chất lượng phản hồi |
| Repository/query duration | Query hoặc use case chậm |
| DataSource active connections | Connection đang sử dụng |
| DataSource pending threads | Request đang chờ connection |
| Transaction duration | Transaction kéo dài |
| Optimistic locking failures | Xung đột cập nhật |
| Deadlocks/lock waits | Contention database |
| Query timeout/error count | Lỗi persistence |
| Batch processed/failed rows | Tiến độ import |
| Outbox backlog/age | Sự kiện chưa publish |

Đặt alert theo SLO và baseline thực tế. Một metric đơn lẻ tăng chưa chắc là sự cố; cần kết hợp latency, error rate và saturation.

### Tracing

Distributed tracing giúp theo dõi request qua controller, application service, repository, query adapter và external service. Cần tránh tạo span quá chi tiết cho từng row trong batch lớn; ưu tiên operation có ý nghĩa.

## 16. Connection pool và timeout

Một ứng dụng có thể có query đúng nhưng vẫn lỗi khi tải tăng vì connection pool không đủ hoặc transaction giữ connection quá lâu.

Cần cấu hình và quan sát:

- Maximum pool size.
- Connection acquisition timeout.
- Idle/minimum connections.
- Connection lifetime/max lifetime.
- Validation/keepalive theo driver/database.
- Transaction timeout.
- Query/statement timeout.
- Network/socket timeout.

Không tăng pool size vô hạn để xử lý pending threads. Database có giới hạn concurrency; quá nhiều connection có thể làm tăng context switching, lock contention và memory usage.

Đo active/pending connection cùng database CPU và latency để tìm điểm cân bằng. Transaction nên kết thúc sớm trước khi thực hiện tác vụ ngoài database.

## 17. Health check và khả năng phục hồi

Readiness probe nên xác định instance có thể nhận traffic hay không. Liveness probe nên xác định process có còn sống và có thể tự phục hồi không.

Không để một dependency chập chờn khiến liveness probe liên tục restart toàn bộ instance nếu restart không giúp phục hồi. Tách health indicator theo dependency và dùng timeout hợp lý.

Các tình huống cần diễn tập:

- Database tạm mất kết nối.
- Connection pool cạn.
- Query timeout.
- Database failover.
- Message broker mất kết nối.
- Replica lag.
- Migration thất bại.
- Outbox backlog tăng.

Ứng dụng nên fail rõ ràng, phát metrics và phục hồi khi dependency hoạt động lại. Không tiếp tục nhận write nếu không thể bảo đảm transaction hoặc consistency cần thiết.

## 18. Bảo mật và quyền truy cập database

Dùng tài khoản database với quyền tối thiểu:

- Runtime user chỉ có quyền cần thiết trên schema/table.
- Migration user có quyền DDL riêng nếu quy trình triển khai yêu cầu.
- Không dùng tài khoản DBA cho ứng dụng.
- Secret lấy từ secret manager/environment được bảo vệ, không commit vào source.
- TLS khi kết nối qua network theo yêu cầu hạ tầng.
- Giới hạn quyền đọc dữ liệu nhạy cảm.
- Kiểm tra tenant isolation và authorization ở application/query layer.
- Bind mọi value và whitelist SQL structure động.

Tách quyền migration và runtime giúp giảm tác động nếu ứng dụng bị xâm nhập. Runtime thường không cần quyền tạo/drop table trong production.

## 19. Backup, restore và dữ liệu

Backup chỉ có giá trị khi đã thử restore. Trước khi phát hành thay đổi dữ liệu quan trọng:

- Xác nhận backup gần nhất thành công.
- Xác định RPO/RTO.
- Thử restore vào môi trường độc lập.
- Kiểm tra tính toàn vẹn sau restore.
- Xác định cách phục hồi sequence/identity, index và constraint.
- Kiểm tra dữ liệu outbox/batch/import.
- Có quy trình xử lý dữ liệu phát sinh sau thời điểm backup.

Không xem snapshot tạo ra là bằng chứng hệ thống có thể phục hồi. Restore rehearsal là bước xác nhận thực tế.

## 20. Kiểm thử trước khi triển khai

Một bộ kiểm thử phù hợp thường có nhiều tầng:

| Tầng | Mục tiêu |
|---|---|
| Unit test domain | Invariant và state transition |
| Unit test converter | Chuyển đổi kiểu domain |
| Repository integration test | Mapping, SQL, generated ID, version |
| Database integration test | Dialect, driver, constraint và migration |
| Transaction test | Commit, rollback, isolation và concurrency |
| API/service test | Authorization, error mapping, idempotency |
| Performance test | Latency, throughput và database saturation |
| Migration rehearsal | Thời gian, lock, backfill và rollback |
| Recovery test | Retry, reconnect, outbox và restore |

H2 có thể hữu ích cho test nhanh, nhưng test phụ thuộc dialect, generated keys, JSON, timezone hoặc locking cần chạy trên DBMS production-like. Testcontainers là một lựa chọn để chạy database thật trong CI.

## 21. Test concurrency bằng hai transaction độc lập

Để xác nhận optimistic locking, cần hai lần đọc cùng version và hai transaction độc lập. Mô hình:

~~~text
Transaction A: đọc aggregate version 3
Transaction B: đọc aggregate version 3
Transaction A: cập nhật và commit version 4
Transaction B: thử cập nhật object version 3
Kỳ vọng: B nhận optimistic locking failure
~~~

Không mô phỏng concurrency bằng hai object trong cùng một transaction. Cần hai connection/transaction độc lập và đồng bộ thời điểm để tạo race condition.

Với deadlock hoặc lock wait, dùng database test và câu lệnh kiểm soát để tái hiện. Test không nên phụ thuộc timing ngẫu nhiên; dùng barrier/latch và timeout có giới hạn để điều phối hai transaction.

## 22. Test transaction rollback qua nhiều thao tác

Một use case có thể lưu aggregate rồi ghi thêm audit/outbox. Cần kiểm tra lỗi ở bước sau làm toàn bộ thao tác database rollback nếu cùng transaction:

~~~java
@Test
void rollsBackAggregateWhenOutboxInsertFails() {
    assertThrows(RuntimeException.class, () ->
            orderCommandService.createAndFailOutbox(command)
    );

    assertFalse(orderRepository.existsByOrderNumber(command.orderNumber()));
    assertEquals(
            0,
            jdbcTemplate.queryForObject(
                    "SELECT COUNT(*) FROM outbox_events WHERE aggregate_id = ?",
                    Integer.class,
                    command.orderNumber()
            )
    );
}
~~~

Test cần chạy qua Spring proxy và database thật/test container. Nếu test framework bọc test method trong transaction riêng, cần hiểu transaction đó ảnh hưởng tới việc quan sát dữ liệu sau rollback như thế nào.

## 23. Xử lý lỗi ở API boundary

Không để persistence exception rò rỉ trực tiếp thành HTTP 500 với stack trace. Map lỗi theo contract:

| Lỗi nội bộ | Response có thể phù hợp |
|---|---|
| Entity không tồn tại | 404 Not Found |
| Validation/domain rule thất bại | 400 hoặc 422 |
| Optimistic locking conflict | 409 Conflict |
| Unique constraint conflict | 409 Conflict hoặc validation response |
| Rate/size limit | 429 hoặc 413 tùy contract |
| Database unavailable | 503 Service Unavailable |
| Lỗi không xác định | 500 Internal Server Error |

Không map mọi DataIntegrityViolationException thành 400 nếu có thể đó là lỗi schema/programming. Cần phân biệt constraint nghiệp vụ dự kiến với lỗi dữ liệu bất thường.

Response nên có error code ổn định, message phù hợp và correlation ID. Chi tiết SQL/constraint nội bộ chỉ nên ở log bảo vệ.

## 24. Runbook cho sự cố persistence

Runbook nên giúp on-call xác định bước đầu tiên mà không cần đọc toàn bộ source.

Ví dụ:

### Database unavailable

1. Kiểm tra database health và network.
2. Kiểm tra connection pool active/pending và acquisition timeout.
3. Xem lỗi driver và thời điểm bắt đầu.
4. Xác định read/write impact.
5. Không retry vô hạn.
6. Khi database phục hồi, kiểm tra request/message có thể được gửi lại an toàn không.

### Optimistic locking failure tăng

1. Xác định aggregate/use case có conflict.
2. Kiểm tra số request đồng thời và transaction duration.
3. Kiểm tra có writer nào bỏ qua version qua SQL trực tiếp không.
4. Xác định conflict có phải hành vi nghiệp vụ bình thường hay bug.
5. Chỉ thay đổi retry/aggregate boundary sau khi hiểu invariant.

### Query latency tăng

1. Xác định query/mapper bằng trace hoặc metrics.
2. Kiểm tra execution plan và index.
3. Kiểm tra row count, cardinality và lock wait.
4. Kiểm tra connection pool và DB saturation.
5. So sánh với deploy/migration gần nhất.
6. Rollback hoặc forward-fix theo runbook nếu SLO bị vi phạm.

Runbook phải có owner, dashboard, alert, command/URL nội bộ được bảo vệ và tiêu chí escalation. Không ghi secret hoặc thông tin truy cập nhạy cảm vào runbook.

## 25. Triển khai theo chiến lược giảm rủi ro

Với thay đổi lớn, cân nhắc:

- Canary: triển khai một phần instance/traffic trước.
- Blue-green: chuẩn bị môi trường mới rồi chuyển traffic.
- Feature flag: bật use case mới theo nhóm người dùng.
- Shadow read: chạy query mới song song để so sánh kết quả, nhưng không tạo side effect.
- Gradual rollout: tăng traffic theo bước và theo dõi SLO.

Shadow read chỉ phù hợp khi query mới không ghi dữ liệu và có thể giới hạn tải. Không chạy query nặng gấp đôi trên production nếu chưa đánh giá tác động.

Mỗi giai đoạn cần có điều kiện dừng rõ: error rate, p95 latency, database saturation, mismatch rate hoặc backlog vượt ngưỡng.

## 26. Tiêu chí sẵn sàng triển khai

Một release Spring Data JDBC có thể được xem là sẵn sàng khi có bằng chứng cho các nhóm sau:

| Nhóm | Tiêu chí |
|---|---|
| Domain | Aggregate boundary và invariant được xác định, có unit test |
| Mapping | Entity, converter, embedded, collection và ID được kiểm thử |
| Schema | Migration chạy thành công, constraint/index đúng |
| Transaction | Boundary, rollback rules, isolation và timeout được xác nhận |
| Concurrency | @Version hoặc cơ chế khóa được test bằng transaction độc lập |
| Failure handling | Lỗi dữ liệu, conflict, transient và connection failure được phân loại |
| Idempotency | Request/message retry không tạo side effect trùng |
| External effects | Outbox/after-commit strategy có test khi cần |
| Performance | p95/p99, throughput và DB resource nằm trong SLO |

Không có một con số chung áp dụng cho mọi ứng dụng. SLO, tải, RPO/RTO và mức rủi ro phải được xác định theo sản phẩm. Tiêu chí quan trọng là mỗi yêu cầu có cách xác minh và người chịu trách nhiệm.

## 27. Checklist go-live

Trước khi bật traffic production, có thể dùng checklist:

- [ ] Repository và query adapter dùng đúng DataSource/transaction manager.
- [ ] Mọi aggregate có root và invariant rõ ràng.
- [ ] Generated ID, assigned ID và @Version đã được test.
- [ ] Embedded/collection/converter mapping đã được test trên DBMS mục tiêu.
- [ ] Migration được chạy thử với dữ liệu đại diện.
- [ ] Unique/FK/check constraint và index đã được xác nhận.
- [ ] Transaction rollback và checked-exception policy rõ ràng.
- [ ] Optimistic locking và concurrency test đã chạy.
- [ ] Retry có giới hạn và chỉ áp dụng với lỗi transient phù hợp.
- [ ] Command/message quan trọng có idempotency strategy.
- [ ] Side effect ngoài DB có after-commit/outbox strategy phù hợp.
- [ ] Query timeout, transaction timeout và pool timeout được cấu hình.
- [ ] Dashboard/alert cho latency, error, pool, lock và backlog sẵn sàng.
- [ ] Secret và database privileges được kiểm tra.
- [ ] Backup và restore đã được diễn tập.
- [ ] Runbook, owner và escalation path được xác định.
- [ ] Rollout, stop condition và rollback/forward-fix được thống nhất.

Checklist chỉ hữu ích nếu mỗi mục được xác nhận bằng test, log, cấu hình hoặc tài liệu có owner. Không đánh dấu hoàn tất chỉ dựa trên việc một class đã được viết.

## 28. Ví dụ tổng hợp một use case sẵn sàng triển khai

Một use case duyệt đơn hàng có thể được tổ chức như sau:

~~~java
@Service
public class OrderApprovalService {

    private final PurchaseOrderRepository orders;
    private final OutboxRepository outbox;

    public OrderApprovalService(
            PurchaseOrderRepository orders,
            OutboxRepository outbox
    ) {
        this.orders = orders;
        this.outbox = outbox;
    }

    @Transactional
    public PurchaseOrder approve(Long orderId, String commandId) {
        if (outbox.wasCommandProcessed(commandId)) {
            return orders.findById(orderId).orElseThrow();
        }

        PurchaseOrder current = orders.findById(orderId).orElseThrow();
        PurchaseOrder approved = current.approve();

        PurchaseOrder saved = orders.save(approved);

        outbox.record(
                commandId,
                "PurchaseOrderApproved",
                saved.id(),
                saved.version()
        );

        return saved;
    }
}
~~~

Đây là ví dụ minh họa ranh giới. Implementation thực tế cần bảo vệ idempotency key bằng unique constraint và thực hiện kiểm tra/ghi command marker trong cùng transaction để tránh race condition. OutboxRepository phải dùng cùng DataSource và transaction manager.

Khi review use case này, xác nhận:

- approve() kiểm tra trạng thái hợp lệ.
- @Version phát hiện cập nhật đồng thời.
- Lưu aggregate và outbox atomic.
- Duplicate command không tạo event mới.
- Worker gửi event idempotently.
- Nếu outbox insert thất bại, aggregate update rollback.
- Metrics thể hiện outbox backlog và delivery failure.
- Test dùng hai transaction độc lập cho concurrency/idempotency.

Một use case chỉ sẵn sàng khi các thuộc tính này được xác nhận bằng test và vận hành, không chỉ vì method có @Transactional.

## 29. Bài thực hành tổng hợp

Chọn một aggregate thực tế của dự án, ví dụ PurchaseOrder, rồi thực hiện theo trình tự:

1. Vẽ aggregate root, child và các tham chiếu sang aggregate khác.
2. Liệt kê invariant và state transition.
3. Đối chiếu entity mapping với DDL/migration.
4. Viết unit test cho domain behavior.
5. Viết repository integration test trên DBMS production-like.
6. Test generated ID, assigned ID, converter, embedded và collection.
7. Test optimistic locking bằng hai transaction độc lập.
8. Test rollback khi bước ghi audit/outbox thất bại.
9. Test duplicate command/message.
10. Đo save aggregate lớn và query đọc chính.
11. Cấu hình pool/query/transaction timeout.
12. Thêm logs, metrics, tracing và alert.
13. Thử database unavailable, deadlock hoặc query timeout trong môi trường test.
14. Chạy migration rehearsal và kiểm tra thời gian/lock.
15. Diễn tập restore và xác nhận RPO/RTO.
16. Viết runbook và xác định điều kiện dừng rollout.
17. Hoàn thành go-live checklist với bằng chứng và owner.

Ghi lại các giả định còn tồn tại, ví dụ database version, driver, mức tải dự kiến và giới hạn aggregate size. Những giả định này cần được xem xét lại khi hạ tầng hoặc nghiệp vụ thay đổi.

## 30. Nguyên tắc ghi nhớ

- Readiness là thuộc tính của toàn use case và môi trường vận hành, không chỉ của repository test.
- Aggregate root phải phản ánh invariant và vòng đời domain; collection lớn cần được đo trước khi tối ưu.
- Entity mapping, converter, ID strategy và migration phải tương thích với database thật.
- Đặt transaction ở application service quanh use case và giữ transaction ngắn.
- Hiểu rollback rules, DataAccessException, optimistic locking, deadlock và timeout.
- Retry chỉ lỗi transient phù hợp, có giới hạn, backoff và idempotency.
- Side effect ngoài database cần after-commit hoặc transactional outbox khi cần độ tin cậy.
- Batch nên có chunk/recovery strategy phù hợp với semantics nghiệp vụ.
- Schema migration cần tương thích trong rollout và có rollback/forward-fix plan.
- Observability phải bao gồm latency, errors, connection pool, lock, query và backlog.
- Security gồm least privilege, secret handling, authorization và parameter binding.
- Backup cần được xác minh bằng restore rehearsal.
- Runbook, owner, alert và escalation phải sẵn sàng trước khi tăng traffic.
- Mỗi tiêu chí go-live cần có bằng chứng kiểm chứng được.

Đánh giá thiết kế và readiness giúp nhóm phát hiện rủi ro trước khi chúng xuất hiện dưới tải production. Hãy đi từ aggregate và schema đến transaction, lỗi, concurrency, bảo mật và vận hành; sau đó xác nhận từng quyết định bằng integration test, benchmark, migration rehearsal và runbook. Khi có bằng chứng cho các tiêu chí này, việc triển khai Spring Data JDBC sẽ có cơ sở rõ ràng hơn và đội vận hành biết cách phát hiện, xử lý và phục hồi khi sự cố xảy ra.
