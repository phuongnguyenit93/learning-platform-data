# Distinguishing `List`, `Iterable`, `Optional`, and Single Results

In **Spring Data JDBC**, the return type of a repository method indicates whether the application expects **zero, one, or many results** and how the caller will use that result set. Common types include `Optional<T>`, a direct `T` object, `Iterable<T>`, and `List<T>`.

Key distinctions:

- **`Optional<T>`** represents a result that may not exist: if there is one object, `Optional` contains it; if not, `Optional.empty()`.
- **`T` (a direct object)** represents a single result; if there is no row, the result is typically `null`. If the query returns more than one row while the method expects a single result, Spring Data reports a result-size error.
- **`Iterable<T>`** represents a multi-result collection that can be traversed with `for-each` or an iterator, without index-based access.
- **`List<T>`** represents a multi-result collection with index-based access, `size()`, and `List` operations.

The return type should match the query's **cardinality** and business meaning. Use `Optional` for a customer looked up by a unique email; use `List` or `Iterable` for a query that can return multiple customers; use `T` directly when the contract allows the caller to handle a missing value as `null`.

## 1. Running Example: Querying Customers

Suppose the database has the following table:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    city VARCHAR(100) NOT NULL,
    active BOOLEAN NOT NULL
);
```

Entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,
        String email,
        String city,
        boolean active
) {}
```

The repository can declare multiple return types depending on the purpose:

```java
import java.util.List;
import java.util.Optional;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findByEmail(String email);

    Customer findCustomerById(Long id);

    List<Customer> findByCity(String city);

    Iterable<Customer> findByActiveTrue();
}
```

These methods all query the `customers` table, but their result contracts differ. `findByEmail` expects at most one row because email has a `UNIQUE` constraint; `findByCity` can return multiple customers; `findByActiveTrue` can also return a set of results.

## 2. `Optional<T>`: A Single Result That May Be Absent

`Optional<T>` is suitable for queries expecting at most one object where the record might not exist.

Example:

```java
Optional<Customer> findByEmail(String email);
```

When calling it:

```java
Optional<Customer> result = customers.findByEmail("lan@example.com");

if (result.isPresent()) {
    Customer customer = result.get();
    System.out.println(customer.name());
} else {
    System.out.println("Customer not found");
}
```

Convenience methods can be used:

```java
Customer customer = customers.findByEmail("lan@example.com")
        .orElseThrow(() -> new IllegalArgumentException("Customer not found"));
```

Or provide a fallback value:

```java
Optional<Customer> result = customers.findByEmail("lan@example.com");
Customer customer = result.orElse(defaultCustomer);
```

Behavior:

| Matching rows | Result |
|---:|---|
| 0 | `Optional.empty()` |
| 1 | `Optional.of(customer)` |
| More than 1 | Result-size error, because the method requires a single result |

`Optional` helps callers handle the not-found case explicitly and avoid checking for `null` everywhere. However, it **does not mean** the query is allowed to return multiple rows and let Spring Data pick one arbitrarily.

## 3. Returning `T` Directly: A Single Result That Can Be `null`

A repository method can also declare the entity type directly:

```java
Customer findCustomerById(Long id);
```

For a single-result query:

- Exactly one row: returns `Customer`.
- No rows: the result can be `null`.
- Multiple rows: Spring Data reports a result-size error instead of merging multiple objects into one.

Example:

```java
Customer customer = customers.findCustomerById(42L);

if (customer == null) {
    // Handle not-found case.
} else {
    System.out.println(customer.name());
}
```

For newer repository APIs, `Optional<Customer>` usually expresses the potentially-missing case more clearly. Returning `Customer` directly can still be useful when the application contract or convention accepts null and callers handle it properly.

### Avoiding `null` Propagation

If a method returns `Customer`, callers must remember to check for null before calling `customer.name()`. If skipped, the application can hit a `NullPointerException`.

With `Optional`, callers can be forced to handle absence right at the call site:

```java
Customer customer = customers.findByEmail(email)
        .orElseThrow(() -> new CustomerNotFoundException(email));
```

This makes the method contract easier to read: the query might find nothing, and the caller must choose how to handle it.

## 4. Cardinality: A Single-Result Query Must Truly Have at Most One Row

A method returning `Optional<Customer>` or `Customer` expresses an expectation of **at most one result**. This expectation should be protected by the data model or query conditions.

For example, if email must be unique:

```sql
ALTER TABLE customers
ADD CONSTRAINT uq_customers_email UNIQUE (email);
```

Then:

```java
Optional<Customer> findByEmail(String email);
```

is backed by the database ensuring no two customers share the same email (according to the database's comparison/collation rules).

Without a unique constraint, `findByEmail` could still return multiple rows. Spring Data does not randomly pick one record to wrap in `Optional`; the single-result query will fail with a result-size error, typically represented by `IncorrectResultSizeDataAccessException` or the corresponding data-access exception.

If the business logic wants to retrieve **the first record** among many, express it explicitly with `First`/`Top` and an ordering:

```java
Optional<Customer> findFirstByCityOrderByNameAsc(String city);
```

This method requests the first result sorted by ascending name, rather than assuming city is unique. Omitting `OrderBy` can make picking “the first” unstable because the database does not guarantee row order without `ORDER BY`.

## 5. `Iterable<T>`: A Traversable Result Set

`CrudRepository<T, ID>` uses `Iterable` for multi-object read methods:

```java
Iterable<T> findAll();
Iterable<T> findAllById(Iterable<ID> ids);
```

A repository query method can also return `Iterable<Customer>`:

```java
Iterable<Customer> findByActiveTrue();
```

The caller iterates using `for-each`:

```java
for (Customer customer : customers.findByActiveTrue()) {
    System.out.println(customer.name());
}
```

Or using an iterator:

```java
Iterable<Customer> result = customers.findByActiveTrue();
var iterator = result.iterator();

while (iterator.hasNext()) {
    Customer customer = iterator.next();
    System.out.println(customer.email());
}
```

Characteristics of `Iterable`:

- Can traverse elements sequentially.
- Has no direct `get(index)` or `size()`.
- Does not guarantee ordering if the query has no `ORDER BY`.
- Is a more general contract than `List`, useful when the caller only needs to iterate.

**Do not infer that `Iterable` means streaming or a lazy cursor.** The return type only promises traversability. In Spring Data JDBC, regular query results are read and mapped during repository execution; `Iterable` should not be treated as a guarantee that all results will be loaded row by row on caller demand.

If you need to handle large volumes of data, consider limiting results, pagination/batching, or an explicitly designed JDBC streaming mechanism. Changing `List` to `Iterable` does not solve memory issues on its own.

## 6. `List<T>`: An Index-Accessible Result Set

`List<T>` fits when the caller needs Java `List` operations:

```java
List<Customer> findByCity(String city);
```

Example:

```java
List<Customer> hcmCustomers = customers.findByCity("Ho Chi Minh City");

System.out.println("Customer count: " + hcmCustomers.size());

if (!hcmCustomers.isEmpty()) {
    Customer first = hcmCustomers.get(0);
    System.out.println(first.name());
}
```

With `List<T>`:

- Has `size()` to know the element count.
- Has `get(index)` for positional access.
- Has operations such as `isEmpty`, `stream`, `forEach`.
- When there are no rows, the result is an empty list (`[]`), not `null`.
- Element order is only guaranteed by the query's ordering; if stability is needed, an `ORDER BY` must be present.

Example of a result-limiting method:

```java
List<Customer> findTop20ByCityOrderByNameAsc(String city);
```

The method returns up to 20 customers ordered by ascending name. `Top`/`First` limits the row count, while `List` expresses the returned collection type.

## 7. How Do `CrudRepository` and `ListCrudRepository` Affect Return Types?

The two CRUD interfaces differ primarily in the collection types of several methods:

```java
public interface CustomerCrudRepository
        extends CrudRepository<Customer, Long> {
}
```

With `CrudRepository`:

```java
Iterable<Customer> all = customerCrudRepository.findAll();
Iterable<Customer> saved = customerCrudRepository.saveAll(batch);
Iterable<Customer> selected = customerCrudRepository.findAllById(ids);
```

If `List` is needed, you can use:

```java
public interface CustomerListRepository
        extends ListCrudRepository<Customer, Long> {
}
```

With `ListCrudRepository`:

```java
List<Customer> all = customerListRepository.findAll();
List<Customer> saved = customerListRepository.saveAll(batch);
List<Customer> selected = customerListRepository.findAllById(ids);
```

`ListCrudRepository` extends `CrudRepository` and redeclares several methods to return `List`. `findById` still returns `Optional<T>`; `existsById` still returns `boolean`; `count` still returns `long`. Choose the interface according to the application's collection usage needs.

| Method | `CrudRepository` | `ListCrudRepository` |
|---|---|---|
| `findById(ID)` | `Optional<T>` | `Optional<T>` |
| `findAll()` | `Iterable<T>` | `List<T>` |
| `findAllById(Iterable<ID>)` | `Iterable<T>` | `List<T>` |
| `save(S)` | `S` | `S` |
| `saveAll(Iterable<S>)` | `Iterable<S>` | `List<S>` |
| `existsById(ID)` | `boolean` | `boolean` |
| `count()` | `long` | `long` |

The two interfaces do not change the nature of SQL queries or aggregate boundaries; the key difference here is the return type of multi-result operations.

## 8. An Empty List Differs from `Optional.empty()`

The two types represent the absence of data in two different ways:

```java
Optional<Customer> one = customers.findByEmail("missing@example.com");
List<Customer> many = customers.findByCity("No Such City");
```

Result:

```text
one  -> Optional.empty()
many -> []
```

Meaning:

- `Optional.empty()` states that **no matching single object** exists.
- `[]` states that **the result set has zero elements**.

Do not declare `Optional<List<Customer>>` for an ordinary multi-row query. If there are no rows, an empty `List<Customer>` already fully represents that case. Wrapping it in `Optional` typically creates two layers of “no data” without adding useful meaning.

Similarly, do not return `null` instead of a collection when a query has no results. A collection contract should return an empty collection so callers can iterate safely.

## 9. Single Results and Limiting with `First`/`Top`

If the query condition is not unique but business logic only needs one result, `First` or `Top` can be used:

```java
Optional<Customer> findFirstByCityOrderByNameAsc(String city);

List<Customer> findTop5ByActiveTrueOrderByNameAsc();
```

The first method returns at most one customer in the city ordered by ascending name. The second method returns up to five active customers ordered by ascending name.

Comparison:

| Requirement | Appropriate method |
|---|---|
| Unique email, may not exist | `Optional<Customer> findByEmail(String email)` |
| Unique ID, want to handle null directly | `Customer findCustomerById(Long id)` or use built-in `findById` |
| All customers in a city | `List<Customer> findByCity(String city)` |
| Iterate over active customers | `Iterable<Customer> findByActiveTrue()` |
| First customer in an explicit order | `Optional<Customer> findFirstByCityOrderByNameAsc(String city)` |
| Up to five active customers | `List<Customer> findTop5ByActiveTrueOrderByNameAsc()` |

`First`/`Top` controls how many rows are returned; `Optional`, `List`, or `Iterable` continues to express the shape of the result. Without `OrderBy`, “first” has no stable business meaning.

## 10. Single Results with `Optional` and Multi-Row Errors

Suppose a method is:

```java
Optional<Customer> findByCity(String city);
```

but `city` can appear on multiple customers. When called:

```java
customers.findByCity("Ho Chi Minh City");
```

the method expects at most one row while the database can return many. Spring Data does not automatically convert it to a `List`; it reports a result-size error. The return type is part of the query contract, so the query conditions must be designed accordingly.

If city is not unique, change it to:

```java
List<Customer> findByCity(String city);
```

If business logic only needs one specific customer, add a unique condition (such as email) or apply an explicit limit and sort:

```java
Optional<Customer> findFirstByCityOrderByIdAsc(String city);
```

Do not change `Optional` to `List` merely to hide duplicate data bugs if email really must be unique. In that case, a `UNIQUE` constraint is needed to protect the invariant in the database.

## 11. Result Ordering: `List` Does Not Guarantee Business Order on Its Own

A `List` has positional order, but that does not mean the database returns rows in the order the application wants. If a query has no `ORDER BY`, result ordering is not guaranteed.

Example:

```java
List<Customer> findByCityOrderByNameAsc(String city);
```

is semantically equivalent to:

```sql
SELECT id, name, email, city, active
FROM customers
WHERE city = ?
ORDER BY name ASC;
```

In this case, the `List` reflects the order specified by SQL. If stable ordering is needed when names tie, add a secondary criterion:

```java
List<Customer> findByCityOrderByNameAscIdAsc(String city);
```

Similarly, `Iterable` promises no ordering. If order matters, declare `OrderBy` in the derived query or use `Sort`/a query with supported sorting.

## 12. `Iterable` and `List` Do Not Mean Pagination

`Iterable<T>` only allows traversal, and `List<T>` allows index-based access. Neither inherently carries information about:

- Current page (`page number`).
- Page size (`page size`).
- Total element count or total page count.
- A cursor to continue reading from the database.

Therefore, replacing `Iterable<T>` with `List<T>` is not a pagination strategy. A `List` may contain all matching rows and consume substantial memory. An `Iterable` also does not automatically read data incrementally.

If pagination is needed, use the `Pageable`/`Sort` capabilities and result types supported by **the Spring Data JDBC version in use**, or implement batch-limited queries with a stable sort order. For very large datasets, design an appropriate read strategy rather than relying on the collection type name.

## 13. Query Results and Aggregate Mapping

In Spring Data JDBC, repositories work with aggregate roots. A `Customer` result is an aggregate mapped according to the root's metadata; if the root has child elements belonging to the aggregate, the standard read path may need to query and construct those elements.

Consequently, `List<Customer>` can cost more than just the columns of the `customers` table if each aggregate has child collections. Be mindful when calling `findAll()` or queries returning many aggregates.

If a screen only needs a few columns, you can return a DTO/projection instead of building full aggregates:

```java
public record CustomerSummary(Long id, String name, String city) {}
```

```java
@Query("""
    SELECT id, name, city
    FROM customers
    WHERE active = TRUE
    ORDER BY name
    """)
List<CustomerSummary> findActiveSummaries();
```

This is a display-oriented read query; it does not replace the aggregate repository used for business updates. The result type should reflect the exact data needed for the use case.

## 14. Other Result Types to Recognize

Besides the types in this lesson, repository methods can return scalar or specialized result types:

```java
long countByCity(String city);

boolean existsByEmail(String email);
```

- `long` expresses a count.
- `boolean` expresses an existence-check result.

These are not entity results. Do not return `Customer` just to check whether a record exists if an `existsBy...` method expresses the need directly and is supported by the module.

Types such as `Page<T>`, `Slice<T>`, `Stream<T>`, or cursors have their own rules, and their support depends on the module/version. Do not assume that every return type in Spring Data JPA works identically in Spring Data JDBC.

## 15. Common Mistakes When Choosing Return Types

| Symptom | Common cause | Solution |
|---|---|---|
| `Optional` throws an error on multiple rows | Query is not truly unique | Add a unique constraint, refine conditions, or switch to a collection |
| Caller hits `NullPointerException` | Method returns `T` directly when no row exists | Use `Optional<T>` or check for null |
| Cannot call `get(index)` | Return type is `Iterable` | Use `ListCrudRepository` or declare the query to return `List` if `List` is needed |
| No results, yet caller checks for null | Returned collection is empty, not null | Use `isEmpty()` |
| `List` holds too much data | Unbounded query | Add filters, `Top`/`First`, or an appropriate paging mechanism |
| Element order changes | SQL has no `ORDER BY` | Declare an explicit ordering |
| `findAllById` is missing IDs | Some IDs have no matching row; result order is not guaranteed | Check the returned ID set and do not assume all IDs are present or in input order |
| `Iterable` mistaken for a lazy stream | Confusing traversability with how data is fetched | Design separate streaming/batching if needed |
| Returned DTO is missing fields | SQL does not select enough columns/aliases | Align the result type and selected columns |
| Unnecessary complexity with `Optional<List<T>>` | Wrapping a collection in `Optional` | Return an empty `List<T>` when no rows exist |

## 16. Application Service Example Handling Each Result Type

```java
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class CustomerService {
    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    public Customer getRequiredCustomer(Long id) {
        return customers.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Customer not found"));
    }

    public List<Customer> getCustomersInCity(String city) {
        return customers.findByCity(city);
    }

    public void printActiveCustomers() {
        for (Customer customer : customers.findByActiveTrue()) {
            System.out.println(customer.name());
        }
    }
}
```

The example illustrates three result types:

- `findById` returns `Optional<Customer>` because the ID may not exist.
- `findByCity` returns `List<Customer>` because a city can have many customers.
- `findByActiveTrue` returns `Iterable<Customer>` because the caller only needs to iterate over the result set.

In a real repository, these methods can coexist; choose the type based on cardinality and how the caller needs to work with it, not merely out of habit.

## 17. Practice Exercise: Observing 0, 1, and Many Results

Using the `customers` table from the beginning, insert sample data:

```sql
INSERT INTO customers (name, email, city, active) VALUES
    ('Lan', 'lan@example.com', 'Ho Chi Minh City', TRUE),
    ('Minh', 'minh@example.com', 'Ho Chi Minh City', TRUE),
    ('Hoa', 'hoa@example.com', 'Da Nang', FALSE);
```

Try the methods:

```java
Optional<Customer> byEmail = customers.findByEmail("lan@example.com");
Optional<Customer> missing = customers.findByEmail("missing@example.com");
List<Customer> hcm = customers.findByCity("Ho Chi Minh City");
Iterable<Customer> active = customers.findByActiveTrue();
```

Observe:

1. `byEmail` contains one `Customer`.
2. `missing` is `Optional.empty()`.
3. `hcm` has two elements.
4. `active` can be iterated over for active customers.
5. Change `findByEmail` to a non-unique condition (e.g., `findByCity`) while still returning `Optional<Customer>`; observe the result-size error when multiple rows match.
6. Change that method to `List<Customer>` to represent multiple results properly.
7. Try `findFirstByCityOrderByNameAsc` and observe why `ORDER BY` is needed to pick the first result deterministically.

## 18. Key Takeaways

- Use `Optional<T>` for **0 or 1** result; do not use it to mask a query that can return multiple rows.
- Use `T` directly for a single result when the caller accepts handling `null` if no row exists.
- Use `Iterable<T>` when the caller only needs to iterate over the result set.
- Use `List<T>` when the caller needs a collection with `size()` and index-based access.
- Collections with no results should return an empty collection; `Optional.empty()` is for an absent single result.
- A single-result query returning multiple rows causes a result-size error; use a unique constraint, explicit conditions, or an ordered `First`/`Top`.
- `CrudRepository` uses `Iterable` for certain multi-row methods; `ListCrudRepository` returns `List` for the corresponding methods.
- `List` and `Iterable` do not automatically mean pagination, streaming, or lazy loading.
- Ordering is only guaranteed when the query has `ORDER BY`.
- Return types should reflect the cardinality and actual needs of the use case.

In Spring Data JDBC, choosing `List`, `Iterable`, `Optional`, or a single object is part of the repository contract. Determine upfront how many rows the query can return, where uniqueness rules live, and how the caller needs to use the results. When the return type matches cardinality, empty-result handling becomes clearer, multi-row errors are avoided, and you do not accidentally load a larger result set than needed.
