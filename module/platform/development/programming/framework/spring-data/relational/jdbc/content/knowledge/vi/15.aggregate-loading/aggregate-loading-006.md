# Trường hợp quay về cách tải thông thường và cách xác minh bằng SQL

Trong **Spring Data Relational JDBC**, một aggregate được tải thông qua aggregate root cùng các thành phần thuộc vòng đời của nó. Framework có thể sử dụng chiến lược tải thông thường với nhiều câu SQL, hoặc một chiến lược tối ưu như **Single Query Loading** khi phiên bản, dialect và cấu trúc aggregate đáp ứng điều kiện hỗ trợ.

Khi chiến lược tối ưu không được bật hoặc aggregate không đủ điều kiện, Spring Data JDBC sử dụng cách tải thông thường. Đây thường là hành vi hợp lệ, không phải lỗi mapping. Muốn hiểu ứng dụng đang thực hiện điều gì, cần quan sát SQL thực tế, đối chiếu các hàng trong database và phân biệt số câu SQL với số aggregate được trả về.

Bài học này tập trung vào ba việc:

- Hiểu cách tải aggregate thông thường và vì sao có thể phát sinh nhiều câu SQL.
- Nhận diện những trường hợp chiến lược tải một câu không áp dụng được và cách diễn giải việc quay về chiến lược thông thường.
- Xác minh bằng SQL/log để biết dữ liệu nào được đọc, khóa ngoại nào liên kết các bảng và chi phí truy vấn nằm ở đâu.

## 1. Aggregate được tải như thế nào?

Một aggregate có một root và có thể chứa value object, entity con hoặc collection entity con. Ví dụ:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── orderNumber
  ├── status
  └── lines (owned collection)
        ├── OrderLine
        ├── OrderLine
        └── OrderLine
```

Giả sử database có hai bảng:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL
        REFERENCES purchase_order(id),
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12, 2) NOT NULL
);
```

Mapping Java:

```java
import java.math.BigDecimal;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        String status,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines
) {}

public record OrderLine(
        Long id,
        String sku,
        Integer quantity,
        BigDecimal unitPrice
) {}
```

`PurchaseOrder` là aggregate root. `OrderLine` thuộc aggregate và được liên kết qua cột `purchase_order_id`. Repository được khai báo cho root:

```java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

Khi gọi `findById`, mục tiêu là trả về một `PurchaseOrder` đã được materialize cùng các dòng hàng thuộc nó. Điều này không có nghĩa mọi dữ liệu phải được đọc bằng một câu SQL duy nhất.

## 2. Cách tải thông thường: root và các thành phần liên quan

Với chiến lược tải thông thường, Spring Data JDBC tải aggregate theo các bước khái niệm:

1. Truy vấn hàng aggregate root theo ID hoặc điều kiện tìm kiếm.
2. Đọc các property thuộc root và xác định những entity/collection cần nạp.
3. Thực hiện các truy vấn cần thiết để lấy entity con và liên kết chúng với root.
4. Tạo object graph trong bộ nhớ và trả aggregate cho ứng dụng.

Ví dụ khi gọi:

```java
PurchaseOrder order = repository.findById(orderId)
        .orElseThrow();
```

Các câu SQL minh họa có thể có dạng:

```sql
-- Lấy aggregate root.
SELECT id, order_number, status
FROM purchase_order
WHERE id = ?;

-- Lấy các dòng hàng thuộc root đó.
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = ?;
```

Đây là **SQL minh họa cho chiến lược tải nhiều câu**, không phải bản sao nguyên văn SQL mà mọi phiên bản Spring Data JDBC đều sinh ra. SQL thực tế còn phụ thuộc dialect, naming strategy, mapping, các quan hệ trong aggregate và phiên bản framework.

Điểm cần nhớ: nhiều câu SQL không đồng nghĩa với nhiều aggregate. Hai câu trên có thể cùng tạo nên **một** object `PurchaseOrder` trong bộ nhớ.

### 2.1. Vì sao không dùng JOIN cho mọi trường hợp?

Nếu tự viết một câu JOIN:

```sql
SELECT
    o.id,
    o.order_number,
    o.status,
    l.id AS line_id,
    l.sku,
    l.quantity,
    l.unit_price
FROM purchase_order o
LEFT JOIN order_line l
    ON l.purchase_order_id = o.id
WHERE o.id = ?;
```

database trả một hàng cho mỗi dòng hàng. Nếu một đơn hàng có ba dòng, thông tin của root sẽ lặp lại ba lần trong result set. Mapper phải nhóm các hàng theo root ID, nhận diện child, xử lý trường hợp không có child và tái tạo collection.

Một chiến lược tải nhiều câu có thể đọc root một lần rồi đọc tập child riêng. Điều này tránh phải xử lý một result set phẳng lặp thông tin root, đồng thời giúp mapping rõ ràng. Đổi lại, nó có thể cần thêm round trip tới database.

Vì vậy, số câu SQL chỉ là một phần của chi phí. Cần xem cả số hàng trả về, kích thước result set, dữ liệu lặp, index, latency và số aggregate được tải.

## 3. Single Query Loading và mục tiêu tối ưu

**Single Query Loading** là chiến lược tối ưu của Spring Data JDBC được giới thiệu trong dòng Spring Data Relational 3.2. Ý tưởng là đọc root và một collection được hỗ trợ trong một câu SQL thay vì tải chúng qua nhiều round trip. Chiến lược này dùng các khả năng SQL của database/dialect, bao gồm kỹ thuật cửa sổ (window functions), để biểu diễn các phần tử collection trong result set và tái tạo aggregate.

Đây là tối ưu cho một số hình dạng aggregate, không phải quy tắc bắt buộc cho mọi entity. Khả năng áp dụng phụ thuộc phiên bản Spring Data Relational, dialect và cấu trúc aggregate. Các giới hạn thường gặp gồm:

- Chiến lược phải được bật trong cấu hình của phiên bản đang sử dụng; không nên giả định mọi dự án tự động dùng nó.
- Dialect/database phải hỗ trợ các tính năng SQL cần thiết.
- Cấu trúc aggregate phải nằm trong phạm vi mà Single Query Loading hỗ trợ. Ví dụ, các aggregate có nhiều collection hoặc collection lồng nhau có thể không đủ điều kiện trong các phiên bản/implementation tương ứng.
- Những mapping đặc biệt hoặc kiểu quan hệ không được hỗ trợ bởi chiến lược tối ưu có thể cần đường tải thông thường.

Không lấy các điều kiện trên làm danh sách hỗ trợ cố định cho mọi phiên bản. Khi triển khai, hãy đối chiếu tài liệu của **đúng phiên bản Spring Data Relational và dialect** trong dự án. Khả năng hỗ trợ được mở rộng theo phiên bản.

### 3.1. Khi nào quay về cách tải thông thường?

Có thể phân thành các trường hợp:

| Tình huống | Điều xảy ra | Cách hiểu |
| --- | --- | --- |
| Single Query Loading không được bật | Framework dùng chiến lược tải mặc định | Nhiều câu SQL là kết quả dự kiến |
| Database/dialect không hỗ trợ tính năng cần thiết | Chiến lược tối ưu không được áp dụng | Đường tải thông thường vẫn cần đảm bảo aggregate được đọc |
| Aggregate không phù hợp với giới hạn của chiến lược tối ưu | Framework dùng cách tải thông thường theo khả năng hỗ trợ của phiên bản | Không phải mọi aggregate đều có thể dùng một câu |
| Đang dùng API/repository hoặc cấu hình không kích hoạt chiến lược tối ưu | Lệnh tải đi qua đường thông thường | Kiểm tra đúng bean/cấu hình thực tế |

**Quay về cách tải thông thường không có nghĩa framework đã phát hiện lỗi dữ liệu.** Đây là lựa chọn chiến lược tải dựa trên khả năng và cấu hình.

Cũng cần phân biệt fallback với lỗi thực thi SQL. Nếu một câu SQL tối ưu đã được chọn, gửi tới database rồi gặp lỗi cú pháp, thiếu cột, thiếu quyền hoặc lỗi driver, không nên mặc định Spring Data JDBC sẽ tự động thử lại bằng chiến lược thông thường. Lỗi SQL runtime thường phải được xử lý như lỗi truy vấn; hãy đọc exception gốc và log để xác định đường đi thực tế.

### 3.2. Vì sao một aggregate không đủ điều kiện?

Ví dụ một aggregate có hai collection:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderNote> notes
) {}
```

Đây là một root với hai tập con độc lập. Khi JOIN cả hai collection, nếu đơn hàng có 3 dòng hàng và 4 ghi chú, result set phẳng có thể có tới 12 tổ hợp hàng do phép nhân giữa hai collection. Mapper phải phân biệt các bản sao của từng child. Một chiến lược Single Query Loading có giới hạn về hình dạng aggregate có thể không xử lý trường hợp này; đường tải thông thường đọc các collection riêng sẽ đơn giản và tránh tích Descartes của result set.

Tương tự, collection lồng nhau tạo thêm một cấp nhóm dữ liệu. Không nên suy luận rằng chỉ cần database hỗ trợ window function thì mọi object graph đều có thể tải bằng một câu.

## 4. Xác minh bằng SQL: xem database thực sự lưu gì

Trước khi kết luận cách tải, hãy xác minh dữ liệu và quan hệ trong database. Có thể bắt đầu bằng cách đọc root:

```sql
SELECT id, order_number, status
FROM purchase_order
WHERE id = 42;
```

Sau đó đọc các child:

```sql
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = 42
ORDER BY id;
```

Hai truy vấn giúp xác nhận:

- Root ID có tồn tại hay không.
- Có bao nhiêu child gắn với root.
- Back-reference có chứa đúng root ID không.
- Giá trị các cột trong database có khớp object mong đợi không.

Nếu root tồn tại nhưng truy vấn child không trả hàng, collection trong aggregate có thể rỗng. Nếu child tồn tại nhưng back-reference trỏ tới ID khác, lỗi nằm ở dữ liệu liên kết hoặc mapping/ghi dữ liệu.

### 4.1. Kiểm tra các root và số lượng child

Truy vấn tổng hợp:

```sql
SELECT
    o.id,
    o.order_number,
    COUNT(l.id) AS line_count
FROM purchase_order o
LEFT JOIN order_line l
    ON l.purchase_order_id = o.id
GROUP BY o.id, o.order_number
ORDER BY o.id;
```

`LEFT JOIN` giữ lại cả đơn hàng chưa có dòng hàng; `COUNT(l.id)` trả 0 cho root không có child. Không dùng `COUNT(*)` ở đây nếu muốn đếm child, vì với một root không có child, LEFT JOIN vẫn tạo một hàng kết quả và `COUNT(*)` sẽ là 1.

Kiểm tra child không có root hợp lệ:

```sql
SELECT l.*
FROM order_line l
LEFT JOIN purchase_order o
    ON o.id = l.purchase_order_id
WHERE o.id IS NULL;
```

Nếu cột `purchase_order_id` có foreign key được database thực thi, truy vấn này thường không trả hàng. Nếu có kết quả, kiểm tra lại constraint, dữ liệu import hoặc việc constraint có thực sự được bật/validate hay không.

### 4.2. Xác minh tính duy nhất nếu quan hệ phải là một-một

Với collection one-to-many, nhiều child cùng root là hợp lệ. Nếu quan hệ là one-to-one, hãy kiểm tra số lượng và ràng buộc UNIQUE:

```sql
SELECT purchase_order_id, COUNT(*) AS child_count
FROM shipping_details
GROUP BY purchase_order_id
HAVING COUNT(*) > 1;
```

Nếu đây là quan hệ một-một, database nên có `UNIQUE(purchase_order_id)` hoặc dùng cột này làm khóa chính. Việc truy vấn hiện tại không thấy duplicate không thay thế được constraint; hai transaction vẫn có thể tạo duplicate trong tương lai nếu schema không khóa quy tắc.

## 5. Xác minh chiến lược bằng SQL log

SQL trực tiếp trong database console cho biết dữ liệu đang lưu, nhưng **không chứng minh ứng dụng đã gửi bao nhiêu câu SQL**. Để biết Spring Data JDBC thực thi câu nào, quan sát log JDBC hoặc dùng công cụ proxy datasource trong môi trường phát triển.

Ví dụ cấu hình log tạm thời trong `application-dev.yml`:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
```

Tùy phiên bản Spring Framework và cách truy vấn được thực thi, log có thể cho biết câu SQL được chuẩn bị/thực thi. Nếu cần quan sát sâu hơn về binding parameter, một số logger ở mức TRACE hoặc datasource proxy có thể hữu ích. Tên logger và mức log cụ thể nên được xác nhận theo phiên bản dự án.

Các lựa chọn thường dùng:

- **Log Spring JDBC:** tiện để kiểm tra nhanh trong local/dev.
- **Datasource proxy:** bọc `DataSource` để ghi nhận câu SQL, thời gian và số lần gọi.
- **P6Spy:** công cụ quan sát SQL qua JDBC, hữu ích khi cần nhìn câu lệnh cùng thông tin thực thi.
- **Database query log/statistics:** giúp kiểm tra truy vấn đến database, nhưng cấu hình cần phù hợp hệ quản trị và môi trường.

Không bật log tham số nhạy cảm ở production. Giá trị bind có thể chứa email, số điện thoại, token hoặc dữ liệu cá nhân. SQL logging cũng làm tăng lượng log và có thể ảnh hưởng hiệu năng; bật có mục tiêu rồi tắt khi không còn cần.

### 5.1. Dấu hiệu của chiến lược tải nhiều câu

Khi gọi `findById` cho một aggregate root có một collection, log có thể cho thấy mẫu tương tự:

```text
1. SELECT ... FROM purchase_order WHERE id = ?
2. SELECT ... FROM order_line WHERE purchase_order_id = ?
```

Với nhiều aggregate roots hoặc nhiều quan hệ, có thể thấy thêm các câu truy vấn theo từng root/property. Số lượng thực tế phụ thuộc đường tải, batch behavior, mapping và phiên bản. Đừng chỉ đếm dòng log mà không nhóm theo request hoặc operation.

### 5.2. Dấu hiệu của Single Query Loading

Khi chiến lược tối ưu được bật và aggregate đủ điều kiện, log có thể cho thấy một câu SQL lớn hơn, dùng join/window function hoặc cấu trúc SQL đặc thù của dialect để biểu diễn root và collection trong cùng result set.

Không nên tìm một chuỗi SQL cố định để nhận diện trên mọi database. Hãy xác định:

1. Có một câu truy vấn aggregate thay vì chuỗi truy vấn root/child riêng hay không?
2. SQL có sử dụng cấu trúc mà dialect cần cho Single Query Loading không?
3. Kết quả trả về có đủ dữ liệu root và các phần tử child không?
4. Object graph sau mapping có số child và giá trị đúng không?

Một câu SQL dài không tự động chứng minh Single Query Loading đã hoạt động. Custom query có JOIN cũng có thể là một câu nhưng không đi qua cơ chế aggregate mapping tương tự. Cần kết hợp log, cấu hình thực tế và kết quả object.

## 6. So sánh hai đường tải

| Tiêu chí | Tải thông thường | Single Query Loading khi đủ điều kiện |
| --- | --- | --- |
| Số round trip | Có thể nhiều câu cho root và các phần liên quan | Mục tiêu là một câu cho aggregate được hỗ trợ |
| Cấu trúc SQL | Các câu root/child riêng, tương đối dễ đọc | Câu SQL phức tạp hơn, phụ thuộc dialect |
| Phạm vi hỗ trợ | Đường tải tổng quát của mapping | Chỉ các aggregate/dialect được hỗ trợ |
| Cách xác minh | Quan sát các truy vấn root và child | Quan sát câu truy vấn tối ưu và object graph |
| Chi phí có thể phát sinh | Nhiều round trip; có thể N+1 khi tải nhiều roots | SQL/result set phức tạp, dữ liệu root có thể lặp theo child |
| Khi tối ưu không áp dụng | Đây là đường tải mặc định | Framework sử dụng đường tải thông thường theo khả năng của phiên bản |

Single Query Loading giảm số round trip nhưng không đảm bảo mọi truy vấn nhanh hơn. Với collection rất lớn, result set vẫn lớn; database vẫn phải đọc và gửi toàn bộ dữ liệu cần thiết. Cần đo thực tế thay vì chỉ tối ưu số câu SQL.

## 7. Kiểm tra hiệu năng của SQL

Khi đã lấy được SQL thực tế từ log, kiểm tra execution plan trên database mục tiêu. Với PostgreSQL, có thể dùng `EXPLAIN`:

```sql
EXPLAIN
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = 42;
```

Nếu truy vấn child thường lọc theo `purchase_order_id`, index trên cột này có thể hữu ích:

```sql
CREATE INDEX idx_order_line_purchase_order_id
    ON order_line(purchase_order_id);
```

Với quan hệ một-một, PK/UNIQUE trên back-reference thường đã tạo index thích hợp theo database. Đừng tạo index trùng lặp mà không xem constraint và execution plan hiện có.

Một số điểm cần xem:

- Database có dùng index trên khóa ngoại hay đang sequential scan bảng child rất lớn?
- Số hàng ước lượng có gần với số hàng thực tế trong workload không?
- Join/window function có tạo sort hoặc memory spill đáng kể không?
- Result set có lặp nhiều dữ liệu root do collection có nhiều phần tử không?
- Count/query bổ sung hoặc các quan hệ khác có chiếm phần lớn thời gian không?

`EXPLAIN ANALYZE` trên PostgreSQL thực thi câu lệnh để đo thời gian thực tế. Chỉ dùng với truy vấn đọc an toàn trong môi trường phù hợp; với câu DML, nó thực sự chạy câu lệnh và có thể tạo side effect. Không chạy thử tùy tiện trên production.

## 8. Phân biệt fallback với lỗi dữ liệu hoặc lỗi SQL

Không phải mọi trường hợp nhiều SQL đều là fallback do Single Query Loading:

| Quan sát | Có thể giải thích | Cần xác minh thêm |
| --- | --- | --- |
| Root query và child query riêng | Đường tải thông thường | Feature có được bật không; aggregate có đủ điều kiện không |
| Chỉ có root query, collection rỗng | Root không có child hoặc query child không được chạy/không map | Kiểm tra bảng child, FK và mapping |
| SQL tối ưu phát sinh lỗi cú pháp | Dialect/cấu hình/version không phù hợp hoặc SQL/schema lỗi | Đọc exception gốc; không mặc định có fallback tự động |
| SQL chạy thành công nhưng thiếu child | Dữ liệu, predicate, back-reference hoặc mapping không khớp | Query trực tiếp bảng child theo root ID |
| Một câu JOIN trả nhiều dòng | Có thể là query tùy chỉnh hoặc chiến lược tải tối ưu | Kiểm tra nguồn SQL và cách mapper tạo aggregate |
| Nhiều câu khi gọi findAll | Có thể là tải root và quan hệ theo từng aggregate | Nhóm log theo operation và số root thực tế |

Để kết luận đúng, hãy trả lời lần lượt:

1. Repository method nào đã được gọi?
2. Aggregate root có bao nhiêu collection/reference cần tải?
3. Single Query Loading có được bật trong cấu hình runtime không?
4. Phiên bản Spring Data Relational và dialect đang sử dụng là gì?
5. SQL nào thực sự được gửi tới database?
6. Dữ liệu root/child trong database có đúng và liên kết bằng khóa nào?

## 9. Ví dụ kiểm chứng từ repository tới database

Giả sử repository:

```java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

Service:

```java
import org.springframework.stereotype.Service;

@Service
public class PurchaseOrderQueryService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderQueryService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    public PurchaseOrder get(Long id) {
        return repository.findById(id)
                .orElseThrow();
    }
}
```

Thực hiện kiểm chứng theo trình tự:

1. Chọn một ID đã biết, ví dụ `42`.
2. Chạy truy vấn SQL trực tiếp để xác nhận root `purchase_order.id = 42` tồn tại.
3. Chạy truy vấn `order_line WHERE purchase_order_id = 42` để biết tập child dự kiến.
4. Bật SQL logging trong profile dev.
5. Gọi `get(42)` một lần và nhóm các câu SQL phát sinh từ request đó.
6. So sánh các child trong object trả về với các hàng tìm được bằng SQL.
7. Lặp lại với một root không có child và một root có nhiều child.
8. Nếu đang thử Single Query Loading, xác nhận cấu hình bật, aggregate/dialect nằm trong phạm vi hỗ trợ rồi so sánh log.

Bảng kết quả kiểm chứng có thể ghi:

| Root ID | Số hàng child theo SQL | Số child trong object | Số câu SQL đọc aggregate | Nhận xét |
| ---: | ---: | ---: | ---: | --- |
| 42 | 3 | 3 | 2 | Ví dụ tải thông thường |
| 43 | 0 | 0 | 2 | Root không có child |
| 44 | 12 | 12 | 1 hoặc nhiều hơn | Phải đối chiếu chiến lược và log thực tế |

Các số trong bảng chỉ là dữ liệu ví dụ để minh họa cách ghi nhận, không phải kết quả đo của một dự án cụ thể. Với root 44, số câu SQL không thể suy ra chỉ từ số child.

## 10. Các lỗi thường gặp

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
| --- | --- | --- |
| Mong đợi một câu nhưng thấy nhiều câu | Feature chưa bật hoặc aggregate/dialect không được hỗ trợ | Kiểm tra cấu hình, phiên bản, dialect và hình dạng aggregate |
| Cho rằng nhiều câu SQL là bug | Nhầm chiến lược tải mặc định với tối ưu một câu | Đối chiếu semantics và dữ liệu trả về trước khi kết luận |
| Bật feature nhưng không thấy SQL tối ưu | Cấu hình không được áp dụng vào bean/repository thực tế hoặc aggregate không đủ điều kiện | Kiểm tra cấu hình runtime và SQL log theo đúng request |
| SQL tối ưu lỗi nhưng không thấy fallback | Lỗi runtime không nhất thiết kích hoạt đường tải khác | Đọc root cause, kiểm tra dialect/schema và cấu hình |
| Collection bị rỗng | Không có hàng child, FK sai hoặc mapping column sai | Truy vấn trực tiếp bảng child theo root ID |
| Số child trong object khác SQL | Query/mapping, dữ liệu thay đổi đồng thời hoặc log không cùng request | Dùng transaction/test fixture ổn định và đối chiếu ID cụ thể |
| Tải danh sách nhiều root rất chậm | Nhiều truy vấn liên quan, thiếu index hoặc aggregate lớn | Đo số truy vấn, execution plan, index và ranh giới aggregate |
| SQL log lộ dữ liệu cá nhân | Bật trace/binding log không kiểm soát | Che dữ liệu, giới hạn môi trường và tắt log sau điều tra |

## 11. Quy trình điều tra ngắn gọn

Khi một aggregate được tải theo cách thông thường dù bạn mong đợi chiến lược tối ưu:

1. **Xác định phiên bản:** kiểm tra phiên bản Spring Data Relational thực tế, không chỉ phiên bản starter trong file build.
2. **Kiểm tra cấu hình:** xác nhận Single Query Loading có được bật trên hạ tầng repository/aggregate template mà ứng dụng đang dùng hay không.
3. **Kiểm tra hình dạng aggregate:** số collection, collection lồng nhau và các mapping đặc biệt có thuộc phạm vi hỗ trợ không?
4. **Kiểm tra dialect:** database đang chạy có hỗ trợ các tính năng SQL mà chiến lược yêu cầu không?
5. **Quan sát SQL:** bật logging hoặc datasource proxy trong môi trường dev/test.
6. **Xác minh dữ liệu:** query root và child trực tiếp theo khóa ngoại.
7. **Đo hiệu năng:** dùng execution plan, index và số hàng trả về để tìm bottleneck.

Đừng chỉnh schema hoặc thêm JOIN tùy tiện chỉ để làm log có ít câu SQL hơn. Mục tiêu là tải đúng aggregate với chi phí phù hợp, giữ nguyên ranh giới aggregate và bảo đảm dữ liệu nhất quán.

## 12. Bài tập thực hành

**Bài 1 — Quan sát đường tải mặc định.** Tạo `PurchaseOrder` có collection `lines`. Gọi `findById` và bật SQL log trong profile dev. Ghi nhận truy vấn root và truy vấn child.

**Bài 2 — Xác minh bằng SQL.** Chọn một root ID. Chạy hai truy vấn riêng để đọc root và child. So sánh số hàng child với số phần tử trong collection của object Java.

**Bài 3 — Root không có child.** Tạo một đơn hàng chưa có dòng hàng. Xác nhận root vẫn được tải và collection rỗng; phân biệt trường hợp hợp lệ này với lỗi mapping.

**Bài 4 — Aggregate có nhiều collection.** Thêm collection `notes` vào root. Kiểm tra xem cấu trúc này có còn thuộc phạm vi Single Query Loading của phiên bản đang dùng không; quan sát đường tải thực tế.

**Bài 5 — Đọc execution plan.** Chạy `EXPLAIN` cho truy vấn child theo `purchase_order_id`. Kiểm tra index, số hàng ước lượng và ảnh hưởng của bảng child lớn.

**Bài 6 — Đọc SQL tối ưu.** Nếu dự án hỗ trợ và đã bật Single Query Loading, chọn aggregate đủ điều kiện, quan sát SQL được sinh và so sánh với đường tải thông thường. Không suy luận chỉ từ số câu; kiểm tra cả dữ liệu object graph.
