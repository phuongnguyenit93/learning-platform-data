# The Role of JdbcTemplate and NamedParameterJdbcTemplate in Spring Data Relational JDBC

## 1. Why Do We Need These Two Classes?

When working with relational databases from Java, JDBC provides foundational components such as `Connection`, `PreparedStatement`, and `ResultSet`. They allow running SQL directly, but application code must manually manage acquiring/releasing connections, binding parameters, iterating results, and handling errors.

**`JdbcTemplate`** and **`NamedParameterJdbcTemplate`** belong to **Spring JDBC**. They eliminate JDBC boilerplate so developers can focus on the SQL statement, input data, and how to map results. In an application using **Spring Data JDBC**, these two classes remain useful whenever you need to query or update directly using SQL.

~~~mermaid
flowchart TD
    A["Service / business logic"] --> B["Spring Data JDBC Repository"]
    A --> C["JdbcTemplate"]
    A --> D["NamedParameterJdbcTemplate"]
    B --> E["Spring JDBC infrastructure"]
    C --> E
    D --> E
    E --> F["DataSource / JDBC Driver"]
    F --> G[("Relational Database")]
~~~

It is important to distinguish three layers:

- **Standard JDBC:** Java's API for sending SQL to a database through a JDBC driver.
- **Spring JDBC:** provides `JdbcTemplate`, `NamedParameterJdbcTemplate`, resource management, exception translation, and transaction integration.
- **Spring Data JDBC:** a higher-level abstraction for saving, loading, and managing *aggregates* via repositories and object mapping. Spring Data JDBC uses Spring JDBC infrastructure underneath, but does not replace every need to write SQL by hand.

`JdbcTemplate` and `NamedParameterJdbcTemplate` are **not an ORM like JPA/Hibernate**: they do not track managed objects (*persistence context*), do not automatically detect property changes to write back to the database, and do not provide lazy loading of object relationships.

## 2. What Does JdbcTemplate Do?

`JdbcTemplate` is the central class of Spring JDBC; it takes a `DataSource` and executes the JDBC workflow on behalf of the application:

1. Acquires an appropriate `Connection` from `DataSource`, participating in an active Spring transaction if one exists.
2. Prepares and executes the SQL statement; binds parameters to `PreparedStatement`.
3. Passes `ResultSet` to a `RowMapper` or callback to convert data rows into Java objects.
4. Releases JDBC resources according to context; connections belonging to a transaction are managed by the transaction lifecycle.
5. Translates `SQLException` into Spring's `DataAccessException` hierarchy.

As a result, developers usually only write **SQL + parameters + result-reading logic**, without writing `try/finally` blocks to close `ResultSet` and `Statement` for every query.

### Common Operations

| Need | Typical API | Result |
|---|---|---|
| Query multiple rows | `query(sql, rowMapper, args...)` | `List<T>` |
| Query a single value | `queryForObject(sql, Long.class, args...)` | A single value, or an exception if row count is wrong |
| Execute INSERT/UPDATE/DELETE | `update(sql, args...)` | Number of affected rows |
| Batch updates | `batchUpdate(...)` | Update results per command/batch |
| Execute special SQL or JDBC callbacks | `execute(...)` | Depends on callback type |

`JdbcTemplate` supports **positional parameters** with the `?` character. Each value must be passed in the exact order of the `?` placeholders in the SQL.

## 3. Example: Reading and Updating the `books` Table with JdbcTemplate

Suppose the application has a table:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    author VARCHAR(120) NOT NULL,
    price DECIMAL(12, 2) NOT NULL
);
~~~

Example using Spring Boot and Spring Data JDBC with Gradle configuration:

~~~groovy
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-jdbc")
    runtimeOnly("com.h2database:h2") // H2 used only for local runnable example
}
~~~

In Spring Boot, when a `DataSource` and matching dependencies are present, Boot auto-configures a `JdbcTemplate` bean ready for constructor injection. In real applications, the driver and connection details depend on the database management system in use.

Define the result object:

~~~java
import java.math.BigDecimal;

public record Book(
        long id,
        String title,
        String author,
        BigDecimal price
) {}
~~~

Create the data access class:

~~~java
import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.stereotype.Repository;

@Repository
public class BookJdbcDao {

    private static final RowMapper<Book> BOOK_MAPPER = (rs, rowNum) ->
            new Book(
                    rs.getLong("id"),
                    rs.getString("title"),
                    rs.getString("author"),
                    rs.getBigDecimal("price")
            );

    private final JdbcTemplate jdbc;

    public BookJdbcDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public List<Book> findByAuthor(String author) {
        String sql = """
                SELECT id, title, author, price
                FROM books
                WHERE author = ?
                ORDER BY id
                """;
        return jdbc.query(sql, BOOK_MAPPER, author);
    }

    public Optional<Book> findById(long id) {
        String sql = """
                SELECT id, title, author, price
                FROM books
                WHERE id = ?
                """;
        return jdbc.query(sql, BOOK_MAPPER, id).stream().findFirst();
    }

    public long countBooks() {
        Long count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM books", Long.class);
        return count.longValue();
    }

    public int changePrice(long id, BigDecimal newPrice) {
        return jdbc.update(
                "UPDATE books SET price = ? WHERE id = ?",
                newPrice, id
        );
    }

    public int deleteById(long id) {
        return jdbc.update("DELETE FROM books WHERE id = ?", id);
    }
}
~~~

**Key points to understand in this example:**

- `BOOK_MAPPER` receives each `ResultSet` row and constructs a `Book`; this is explicit, manual mapping and does not automatically load object graphs.
- In `findByAuthor`, there is only one `?`, so the `author` parameter is at the first position.
- In `changePrice`, the first `?` corresponds to `newPrice`; the second corresponds to `id`. Swapping their order can lead to data corruption or type errors.
- `update(...)` returns the **number of affected rows**. With a primary key, `0` usually means no record was found; `1` means one row was updated.
- `query(...)` returns an empty list if no rows match. Building an `Optional` above relies on the uniqueness of `id` guaranteed by the primary key.
- `queryForObject(...)` requires the result row count to match a single-value/single-row query. For zero rows or multiple rows when expecting one, Spring may throw `IncorrectResultSizeDataAccessException` (the empty case is typically `EmptyResultDataAccessException`). Do not automatically treat every `DataAccessException` as "not found."

### RowMapper, ResultSetExtractor, and RowCallbackHandler

`RowMapper<T>` is best suited when **each row maps to one object**. When results must be aggregated across multiple rows (for example, an invoice with many line items), you can use `ResultSetExtractor<T>` to iterate through the entire `ResultSet` yourself. `RowCallbackHandler` is appropriate when processing rows sequentially without building a result `List`.

In queries with `JOIN`s that repeat parent entity data, do not assume a simple `RowMapper` can reconstruct a one-to-many relationship accurately; design explicit grouping logic or let Spring Data JDBC manage appropriate aggregates.

## 4. How Is NamedParameterJdbcTemplate Different?

`NamedParameterJdbcTemplate` provides **named parameters** using `:paramName` syntax instead of forcing readers to count `?` placeholders. It uses `JdbcTemplate` infrastructure underneath: Spring parses the named SQL, converts it to positional JDBC parameters, and binds the corresponding values.

Example with the same condition:

~~~sql
-- JdbcTemplate: positional parameters
SELECT id, title, author, price
FROM books
WHERE author = ? AND price >= ?;

-- NamedParameterJdbcTemplate: named parameters
SELECT id, title, author, price
FROM books
WHERE author = :author AND price >= :minPrice;
~~~

For SQL statements with many conditions, where the same value appears in multiple places, or where queries are edited frequently, named parameters reduce ordering mistakes.

### Practical Queries with MapSqlParameterSource

~~~java
import java.math.BigDecimal;
import java.util.List;

import org.springframework.jdbc.core.RowMapper;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.stereotype.Repository;

@Repository
public class NamedBookJdbcDao {

    private static final RowMapper<Book> BOOK_MAPPER = (rs, rowNum) ->
            new Book(
                    rs.getLong("id"),
                    rs.getString("title"),
                    rs.getString("author"),
                    rs.getBigDecimal("price")
            );

    private final NamedParameterJdbcTemplate namedJdbc;

    public NamedBookJdbcDao(NamedParameterJdbcTemplate namedJdbc) {
        this.namedJdbc = namedJdbc;
    }

    public List<Book> findByAuthorAndMinPrice(
            String author, BigDecimal minPrice) {

        String sql = """
                SELECT id, title, author, price
                FROM books
                WHERE author = :author AND price >= :minPrice
                ORDER BY id
                """;

        var params = new MapSqlParameterSource()
                .addValue("author", author)
                .addValue("minPrice", minPrice);

        return namedJdbc.query(sql, params, BOOK_MAPPER);
    }

    public List<Book> findByIds(List<Long> ids) {
        if (ids.isEmpty()) {
            return List.of();
        }

        String sql = """
                SELECT id, title, author, price
                FROM books
                WHERE id IN (:ids)
                ORDER BY id
                """;

        return namedJdbc.query(
                sql,
                new MapSqlParameterSource("ids", ids),
                BOOK_MAPPER
        );
    }
}
~~~

In the `findByIds` example, Spring expands the `ids` collection into the matching number of `?` placeholders and binds each value. **An empty list must be handled upfront**, because SQL like `IN ()` does not have consistent syntax or semantics across databases. For very large lists, consider driver/database parameter limits, batching, or an alternative query strategy.

### Ways to Pass Named Parameters

- `Map<String, ?>`: concise for a small number of parameters.
- `MapSqlParameterSource`: convenient for adding parameters and specifying `SQL type` when needed, especially for `null` values.
- `BeanPropertySqlParameterSource`: reads JavaBean properties from an object; suitable when property names match SQL parameter names.

Example when the driver needs to know the type of a `null` value:

~~~java
import java.sql.Types;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;

var params = new MapSqlParameterSource()
        .addValue("author", null, Types.VARCHAR)
        .addValue("minPrice", new BigDecimal("100.00"));
~~~

Key detail: `:author` **only substitutes for a data value**. It cannot be a table name, column name, or arbitrary SQL syntax.

## 5. INSERT Retrieving Auto-Generated Keys and Batch Updates

For tables using an identity `id` column, you can retrieve the database-generated key via `KeyHolder`. Below is a method you can add to `NamedBookJdbcDao` from the previous section:

~~~java
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public long insert(String title, String author, BigDecimal price) {
    String sql = """
            INSERT INTO books (title, author, price)
            VALUES (:title, :author, :price)
            """;

    var params = new MapSqlParameterSource()
            .addValue("title", title)
            .addValue("author", author)
            .addValue("price", price);

    KeyHolder keys = new GeneratedKeyHolder();
    int rows = namedJdbc.update(sql, params, keys, new String[] {"id"});

    Number key = keys.getKey();
    if (rows != 1 || key == null) {
        throw new IllegalStateException("Insert did not return an id key");
    }
    return key.longValue();
}
~~~

Generated key support depends on the JDBC driver and database. The `new String[] {"id"}` array specifies which column to return. For some databases or configurations, dialect-specific SQL or a different retrieval mechanism may be needed.

When updating many records of the same shape, `batchUpdate` usually avoids the overhead of sending individual statements one by one:

~~~java
import org.springframework.jdbc.core.namedparam.SqlParameterSource;

public record PriceChange(long id, BigDecimal price) {}

public int[] updatePrices(List<PriceChange> changes) {
    SqlParameterSource[] batch = changes.stream()
            .map(change -> new MapSqlParameterSource()
                    .addValue("id", change.id())
                    .addValue("price", change.price()))
            .toArray(SqlParameterSource[]::new);

    return namedJdbc.batchUpdate(
            "UPDATE books SET price = :price WHERE id = :id",
            batch
    );
}
~~~

`batchUpdate` returns update results per element; how the driver reports row counts can include special JDBC status codes. **Batching does not automatically guarantee atomicity**: when all statements must succeed or roll back together, place the operation inside an appropriate transaction.

## 6. Transactions: Templates Execute SQL, Spring Manages the Transaction Boundary

`JdbcTemplate` and `NamedParameterJdbcTemplate` can participate in a transaction opened with `@Transactional`. In practice, the transaction manager acquires and binds a connection to the thread in Spring's context; templates using the matching `DataSource` participate in that transaction.

Example updating the price of two books as a single business operation:

~~~java
import java.math.BigDecimal;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class BookPricingService {

    private final JdbcTemplate jdbc;

    public BookPricingService(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void setPairPrice(
            long firstBookId, long secondBookId, BigDecimal price) {

        int first = jdbc.update(
                "UPDATE books SET price = ? WHERE id = ?",
                price, firstBookId
        );
        if (first != 1) {
            throw new IllegalArgumentException("First book not found");
        }

        int second = jdbc.update(
                "UPDATE books SET price = ? WHERE id = ?",
                price, secondBookId
        );
        if (second != 1) {
            throw new IllegalArgumentException("Second book not found");
        }
    }
}
~~~

When the transaction manager is properly configured and the method is called through the Spring proxy, if the second update fails and throws a runtime exception, the first update rolls back with the transaction. By default, Spring rolls back on `RuntimeException` and `Error`; checked exceptions require configuring `rollbackFor` if business rules demand it.

Key points to remember:

- Place `@Transactional` boundaries on **services/use cases**, where the code knows how many SQL operations constitute a single business task.
- A transactional connection is shared only when the templates and transaction manager operate on the matching `DataSource`.
- Calling another `@Transactional` method within the same object usually bypasses the proxy; do not assume the annotation always starts a transaction.
- Transactions ensure consistency across multiple statements, but you must still consider isolation, locking, and update conflicts according to database characteristics.

## 7. SQL Injection and Parameter Safety

**Both templates support binding values via prepared statements.** Never concatenate user input directly into SQL:

~~~java
// Unsafe: user input becomes part of the SQL syntax.
String unsafeSql =
        "SELECT * FROM books WHERE author = '" + authorInput + "'";

// Safe: the driver binds authorInput as a value.
jdbc.query(
        "SELECT id, title, author, price FROM books WHERE author = ?",
        BOOK_MAPPER,
        authorInput
);

// Equivalent with named parameters:
namedJdbc.query(
        "SELECT id, title, author, price FROM books WHERE author = :author",
        new MapSqlParameterSource("author", authorInput),
        BOOK_MAPPER
);
~~~

Prepared parameters **cannot replace SQL identifiers** such as column names in `ORDER BY`. If users can select sort criteria, map them strictly from a fixed allowlist controlled by the application:

~~~java
String orderBy = switch (sortKey) {
    case "title" -> "title";
    case "price" -> "price";
    default -> "id";
};

String sql = """
        SELECT id, title, author, price
        FROM books
        ORDER BY %s
        """.formatted(orderBy);
~~~

Here `orderBy` is always a string from an allowlist and never directly contains arbitrary request input. `ASC`/`DESC` can be handled the same way.

## 8. Interpreting Errors and Observing Performance

Spring translates most `SQLException` instances into `DataAccessException` subtypes so upper layers do not have to handle vendor-specific JDBC error codes individually. Common types include:

| Exception | Typical Situation |
|---|---|
| `EmptyResultDataAccessException` | API expects one row, but the query returns zero rows |
| `DuplicateKeyException` | INSERT/UPDATE violates a unique or primary key constraint |
| `DataIntegrityViolationException` | Data constraint violation, such as foreign key or NOT NULL |
| `BadSqlGrammarException` | SQL syntax is invalid for the database |
| `CannotGetJdbcConnectionException` | Unable to acquire a JDBC connection |

The exact exception class depends on the driver-returned error and Spring's error translator. Do not assume "every SQL error is a duplicate key," and do not use `catch (Exception)` to silently return an empty list by default. Technical errors must be handled and logged at the appropriate layer.

Regarding performance:

- Only SELECT needed columns, index frequent search conditions, and paginate large result sets.
- `RowMapper` allocates an object per row; returning a huge list can exhaust memory. For large streams, consider callbacks or chunked processing mechanisms.
- `batchUpdate` reduces database round-trips, but batch sizes and transaction scope still need tuning.
- `JdbcTemplate` is safe to use as a singleton bean once configured; JDBC resources for each call are managed per invocation. Never store a `ResultSet` or `Connection` as shared state across requests.
- `DataSource` typically uses a connection pool in real applications. Configure pool size and timeouts based on load rather than opening a new connection per statement.
- Do not confuse a template's ability to run SQL with optimized SQL: performance still depends on indexes, query plans, isolation, and schema design.

## 9. Choosing JdbcTemplate, NamedParameterJdbcTemplate, or Spring Data JDBC Repository?

| Criterion | `JdbcTemplate` | `NamedParameterJdbcTemplate` | Spring Data JDBC Repository |
|---|---|---|---|
| Approach | Write SQL directly | Write SQL directly | Work with aggregates/repositories |
| Binding | Positional `?` | Named `:name` | Framework handles standard operations |
| SQL control | Very high | Very high | Repositories for standard CRUD; customizable queries available |
| Result mapping | Supply `RowMapper`/callback | Supply `RowMapper`/callback | Maps aggregates via metadata and conventions |
| Best fit | Simple SQL with few parameters, short statements, special callbacks | Complex SQL with many filters/parameters, `IN` lists, batches | Saving/loading aggregates per the Spring Data JDBC model |

**When to use each:**

1. Choose `JdbcTemplate` when SQL is simple, parameter count is small, ordering is easy to track, or direct JDBC callbacks are needed.
2. Choose `NamedParameterJdbcTemplate` when SQL is more complex, has many filters, reuses parameters, or queries by a collection of IDs.
3. Choose a Spring Data JDBC repository when modeling aggregate save/load operations in domain terms and leveraging Spring Data JDBC lifecycle rules.

They can **coexist in the same application**. For example, a repository can handle saving the `Order` aggregate while `NamedParameterJdbcTemplate` executes a reporting query needing `JOIN`s, aggregations, and a custom projection.

### Note When Combining Spring Data JDBC and Direct SQL

SQL written via a template updates the database directly according to the submitted statement and **does not automatically trigger repository lifecycle steps** such as aggregate callbacks or `@Version`-based optimistic locking checks. If you modify the same aggregate through both a repository and direct SQL, you must explicitly protect invariants and concurrency rules.

For example, if a repository uses a `version` column to detect concurrent updates, direct SQL must explicitly enforce `WHERE id = :id AND version = :expectedVersion` and increment `version` accordingly to maintain the same lost-update protection. Simply running `UPDATE ... WHERE id = :id` bypasses that check.

## 10. Common Mistakes and How to Avoid Them

| Mistake | How to Avoid It |
|---|---|
| Concatenating user variables into SQL strings | Use `?` or `:name` to bind values |
| Mixing up the order of many `?` placeholders | Use named parameters for complex SQL |
| Using `queryForObject` and assuming missing data returns `null` | Handle the "no rows" exception properly, or use `query(...).stream().findFirst()` for guaranteed-unique queries |
| Passing an empty list to `IN (:ids)` | Define business behavior and handle empty lists upfront |
| Using parameter names for table/column names | Use an allowlist of SQL identifiers |
| Assuming `batchUpdate` is automatically an atomic transaction | Wrap multi-update business operations in `@Transactional` |
| Using a one-row-per-object `RowMapper` for every one-to-many `JOIN` | Explicitly group results or use appropriate aggregate mapping |
| Updating an aggregate directly while expecting repository callbacks/`@Version` | Explicitly enforce invariants, version checks, and lifecycle logic |

## 11. Practice Exercises

Using the `books` table above, try:

1. Writing a query to find books where `author` matches a parameter and `price` falls within a range using `JdbcTemplate`. Observe the order of the three `?` placeholders.
2. Converting that query to `NamedParameterJdbcTemplate` with `:author`, `:minPrice`, and `:maxPrice`, then adding a condition that reuses `:author`.
3. Writing `findByIds(List<Long> ids)` and testing both a non-empty list and an empty list.
4. Writing a service that updates the prices of two books inside `@Transactional`; intentionally pass a nonexistent ID for the second update and observe whether the first price change rolls back.
5. Querying a nonexistent book with `queryForObject`, comparing it against returning `Optional<Book>` and distinguishing "no rows found" from a connection error.

**Key takeaway:** `JdbcTemplate` removes JDBC boilerplate with **positional** parameters; `NamedParameterJdbcTemplate` keeps those benefits while making complex SQL much more readable with **named** parameters. Spring Data JDBC repositories add an **aggregate** persistence layer on top. Understanding each layer's responsibilities lets you pick the right tool and keep transactions, data integrity, and SQL under control.
