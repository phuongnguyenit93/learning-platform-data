# `@InsertOnlyProperty` and Support Scope on Aggregate Roots

In **Spring Data JDBC**, `@InsertOnlyProperty` marks a property to be written only when the aggregate is newly created (`INSERT`); that property is excluded from `UPDATE` statements when saving an existing aggregate. The annotation is useful for values established once, such as an external reference code, creation timestamp, or origin source of a record.

The crucial point of this lesson is the **support scope**: `@InsertOnlyProperty` is supported on properties of the **aggregate root**. Do not extrapolate that placing the annotation on arbitrary child entities or properties throughout the object graph will make Spring Data JDBC apply the same rule. If a value on a child entity must remain immutable after insert, design dedicated write paths and protection mechanisms suited to that model.

## 1. Problem: some properties only have meaning at creation time

Suppose an application stores documents (`Document`). Each document has:

- `externalReference`: a code assigned by an external system when the document is created.
- `title`: a title that may change throughout the document's lifecycle.
- `createdAt`: creation timestamp, which should not be altered by subsequent edits.
- `version`: technical version used to detect concurrent updates.

If you use a regular entity and call `save` every time the title changes, Spring Data JDBC can include the root's persistent properties in the update statement. However, `externalReference` and `createdAt` belong strictly to creation time. We want the database to preserve the initial values of these two columns across later updates.

`@InsertOnlyProperty` expresses this write rule right in the property's metadata: **include in insert operations, exclude from update operations**.

## 2. Declaring `@InsertOnlyProperty` on the aggregate root

Entity example using a Java `record`:

```java
import java.time.LocalDateTime;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.InsertOnlyProperty;
import org.springframework.data.relational.core.mapping.Table;

@Table("documents")
public record Document(
        @Id Long id,
        @Version Long version,
        @InsertOnlyProperty String externalReference,
        String title,
        @InsertOnlyProperty LocalDateTime createdAt
) {}
```

Each annotation has a distinct role:

- `@Table("documents")` identifies the table for the aggregate root.
- `@Id` identifies the ID.
- `@Version` instructs Spring Data JDBC to manage the version for optimistic locking.
- `@InsertOnlyProperty` marks a property to be written only when inserting the root.

`@InsertOnlyProperty` resides in the `org.springframework.data.relational.core.mapping` package. Do not confuse it with custom application annotations of a similar meaning or JPA annotations. `@Id` and `@Version` in this example belong to `org.springframework.data.annotation`.

Illustrative DDL:

```sql
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    external_reference VARCHAR(80) NOT NULL,
    title VARCHAR(200) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

The Java names `externalReference` and `createdAt` map under common naming strategies to `external_reference` and `created_at`. The DDL must contain the corresponding columns; the annotation does not create tables or columns.

## 3. On insert: insert-only properties are still written

Creating a new document:

```java
Document draft = new Document(
        null,
        null,
        "EXT-2026-0042",
        "System Design",
        LocalDateTime.of(2026, 11, 13, 9, 0)
);

Document saved = documentRepository.save(draft);
```

Because the new aggregate has no ID/version according to the applicable detection rules, Spring Data JDBC executes an `INSERT`. The `externalReference` and `createdAt` properties are included in the insert alongside `title`:

```sql
INSERT INTO documents (
    version,
    external_reference,
    title,
    created_at
)
VALUES (?, ?, ?, ?);
```

The SQL above illustrates the semantics without guaranteeing identical column order or generated-key syntax across all dialects. The database generates `id`; Spring Data JDBC retrieves the generated key and returns the persisted aggregate. With a `record`, use the returned object:

```java
Long documentId = saved.id();
Long currentVersion = saved.version();
```

`@InsertOnlyProperty` **does not mean skipping the value on creation**. On the contrary, the property is saved during insert. If the column is `NOT NULL`, the application must supply a valid value or design a database default mechanism compatible with the actual SQL statement.

## 4. On update: insert-only properties are not written again

Suppose the document has been saved with ID `42` and version `0`. A user changes the title:

```java
Document changed = new Document(
        saved.id(),
        saved.version(),
        saved.externalReference(),
        "System Design - updated edition",
        saved.createdAt()
);

Document updated = documentRepository.save(changed);
```

When updating an existing root, Spring Data JDBC excludes properties annotated with `@InsertOnlyProperty` from the `SET` clause. The logical SQL is equivalent to:

```sql
UPDATE documents
SET title = ?,
    version = ?
WHERE id = ?
  AND version = ?;
```

Neither `external_reference` nor `created_at` appears in `SET`. Consequently, the database preserves the initially inserted values, even if the input object passed to `save` held different values in those two properties.

Flow:

```mermaid
flowchart TD
    A[Load Document root] --> B[Change title]
    B --> C[repository.save(changed)]
    C --> D[Detect existing root]
    D --> E[Generate UPDATE]
    E --> F[Exclude externalReference and createdAt from SET]
    F --> G[Update title and version]
    G --> H[Database preserves insert-only values]
```

This is the difference between `@InsertOnlyProperty` and a normal persistent property: normal properties may be written during updates, whereas insert-only properties are preserved in the database after creation.

## 5. Java object after `save` vs. values stored in the database

One subtlety with immutable entities: `@InsertOnlyProperty` controls **which columns are written in SQL**, rather than turning the input object into a fresh snapshot re-read from the database.

Example:

```java
Document changed = new Document(
        saved.id(),
        saved.version(),
        "EXT-CHANGED-BY-MISTAKE",
        "New Title",
        LocalDateTime.now()
);

Document result = documentRepository.save(changed);
```

The update SQL does not write `external_reference` or `created_at`, so the database still holds `EXT-2026-0042` and the original creation timestamp. However, do not assume the `result` object was re-read from the database to restore those two values; it may still carry the values passed in. If the application needs a snapshot guaranteed to match the database after the operation, reload the aggregate within an appropriate transaction/scope:

```java
Document persisted = documentRepository.findById(result.id())
        .orElseThrow();
```

In practice, it is still best not to alter insert-only properties in objects during update use cases. Setting them at creation and preserving them when constructing subsequent object versions keeps the Java model faithful to the meaning of the data.

## 6. Support scope: aggregate root

Spring Data JDBC organizes data around aggregates. Repositories save and load aggregates through their root; child entities/collections are data owned by the root. `@InsertOnlyProperty` is supported on the **aggregate root**, so do not assume the annotation behaves identically on child entities mapped with `@MappedCollection`.

Example of a root with children:

```java
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.InsertOnlyProperty;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        @InsertOnlyProperty String sourceSystem,
        @MappedCollection(idColumn = "order_id")
        List<OrderLine> lines
) {}

@Table("order_lines")
public record OrderLine(
        String productCode,
        int quantity
) {}
```

In this model, `sourceSystem` is a property of the aggregate root `PurchaseOrder`; this is where the annotation is supported. `OrderLine` is a child entity in a collection. Do not place `@InsertOnlyProperty` on `OrderLine.productCode` or `OrderLine.quantity` assuming the framework will keep them unchanged across aggregate saves.

If you need insert-only semantics for child data, choose an intentional design:

- Move the immutable value up to the aggregate root if it genuinely belongs to the root from a business perspective.
- Use callbacks or domain logic to preserve child values when updating the collection, if appropriate for the aggregate lifecycle.
- Use custom SQL or database mechanisms such as triggers/permissions if guarantees are required at the storage layer; when doing so, explicitly manage transactions, affected row counts, and related optimistic locking.
- Extract the child into an independent aggregate only if it has its own lifecycle and consistency rules; do not split aggregates merely to work around annotation boundaries.

## 7. Distinguishing properties on the root from embedded objects

`@Embedded` objects are flattened into columns of the root table. If an embedded object is a property of the aggregate root, examine that property's metadata in the context of the root and your Spring Data Relational version. Do not assume insert-only support extends automatically to every property inside arbitrary nested objects.

Example of a root with embedded origin metadata:

```java
public record Origin(
        String system,
        String reference
) {}

@Table("documents")
public record Document(
        @Id Long id,
        @Embedded(prefix = "origin_")
        @InsertOnlyProperty Origin origin,
        String title
) {}
```

This illustrates annotating the root's `origin` property as insert-only. The DDL needs `origin_system` and `origin_reference`. On update, the intent is not to rewrite the columns belonging to the annotated property. However, if you require precise control over how the annotation interacts with embedded mappings in a specific version, check the API/reference documentation for your exact Spring Data Relational version and runtime SQL; do not assume the annotation applies recursively to all nested properties of `Origin`.

For child entities inside `@MappedCollection`, the support scope does not expand merely because the child has `@Table` or lives in a separate table. Ownership still places the child inside the aggregate root.

## 8. Comparison with related annotations and mechanisms

| Mechanism | Write semantics | Difference from `@InsertOnlyProperty` |
|---|---|---|
| `@InsertOnlyProperty` | Written on insert; omitted from update | Mechanism to use for aggregate root properties written only at creation time |
| `@ReadOnlyProperty` | Read from database, never written via standard mapping | Excluded from inserts as well |
| `@Transient` | Does not participate in persistence mapping | Not treated as a readable/writable entity column |
| `@Version` | Spring Data manages version on insert/update to detect concurrent writes | Version changes across updates; not an immutable value |
| `@CreatedDate` | Auditing annotation marking creation time for auditing infrastructure to populate | By itself does not mean omitting the property from updates |
| `DEFAULT` in DDL | Database supplies a default value when insert conditions match | Database behavior, not insert-only mapping metadata |

For instance, if `createdAt` should be populated automatically by auditing, use `@CreatedDate` and enable JDBC auditing per application configuration. If you also need to prevent subsequent updates from rewriting that value, `@InsertOnlyProperty` expresses the insert-only write rule. These two annotations address two distinct concerns: **who populates the value** and **when the property is written**.

## 9. `@InsertOnlyProperty` is not a database immutability constraint

The annotation affects SQL generated by Spring Data JDBC along supported aggregate persistence paths. It does not create an `IMMUTABLE` constraint, does not forbid other SQL statements from updating the column, and does not protect against another application writing directly to the database.

For example, the following SQL can still alter the column if the database user has privileges:

```sql
UPDATE documents
SET external_reference = 'MANUAL-CHANGE'
WHERE id = 42;
```

`@InsertOnlyProperty` does not block that statement. If business rules or compliance controls mandate that a column must never be modified after creation, consider adding database-level enforcement (triggers, column privileges, stored procedures, or controlled migration processes) and ensure all application write paths abide by the same rule.

Similarly, a custom `@Query` containing an `UPDATE` or a `JdbcTemplate` call can update an insert-only column if its SQL specifies that column. The annotation does not parse or rewrite arbitrary custom SQL in the application.

## 10. Effects on `save`, transactions, and optimistic locking

`@InsertOnlyProperty` does not replace the new/existing entity detection mechanism:

- A new root still follows the `INSERT` branch per Spring Data's `isNew` rules.
- An existing root still follows the `UPDATE` branch.
- Insert-only properties are included in inserts and excluded from updates.

If the root has `@Version`, the update statement still checks the previous version and increments it upon successful write. Insert-only properties are omitted from `SET`, while the version column remains managed by the framework under optimistic locking.

Transactional service example:

```java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class DocumentService {
    private final DocumentRepository documents;

    public DocumentService(DocumentRepository documents) {
        this.documents = documents;
    }

    @Transactional
    public Document rename(Long id, String title) {
        Document current = documents.findById(id)
                .orElseThrow(() -> new IllegalArgumentException("Document not found"));

        Document changed = new Document(
                current.id(),
                current.version(),
                current.externalReference(),
                title,
                current.createdAt()
        );

        return documents.save(changed);
    }
}
```

The transaction ensures related SQL statements for the use case commit or roll back within the chosen boundary. `@InsertOnlyProperty` only affects the column list written in the update statement; it does not define transaction boundaries.

If two requests update the root concurrently, `@Version` still detects conflicts. Insert-only properties neither disable nor replace optimistic locking.

## 11. Verifying actual SQL

To observe the difference between insert and update, enable logging in development environments:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
    org.springframework.jdbc.core.StatementCreatorUtils: TRACE
```

Perform two operations:

1. Create a new `Document` and call `save`.
2. Load the document, change `title`, and call `save` again.

When reading logs, compare the column lists:

| Operation | Columns expected | Insert-only columns |
|---|---|---|
| `INSERT` | `external_reference`, `title`, `created_at`, and other required columns | Present |
| `UPDATE` | `title`, `version` (if used), ID/version predicates | Absent from `SET` |

Exact SQL depends on the dialect and framework version; verify whether `external_reference` and `created_at` are omitted from the update clause. Do not inspect only the Java object after `save`, since the in-memory object is not necessarily re-read from the database.

Do not enable detailed bind-parameter logging in production if values may contain sensitive data.

## 12. Common errors and misconceptions

| Symptom | Possible cause | Resolution |
|---|---|---|
| Property not written even on first save | Entity not recognized as new or property not persistent | Check `@Id`, `isNew`, metadata, and insert SQL |
| Property still changes in DB after update | Write did not go through supported root path, custom SQL, or different mapping | Check runtime SQL and all update paths |
| Child property still gets rewritten | Annotation placed on child entity outside supported scope | Redesign owner/invariant or apply dedicated protection |
| Returned object differs from DB | Save does not necessarily reload the entire row after update | Preserve existing insert-only values on root; reload if snapshot is required |
| `NOT NULL` column fails on insert | Insert-only value not provided or bound as null | Provide valid value or design compatible default |
| Annotation has no effect on custom SQL | Annotation does not rewrite `@Query`/`JdbcTemplate` SQL | Specify columns carefully in SQL and enforce manually |
| Version does not increment or updates conflict | DDL missing `@Version`, or custom update skips version | Check DDL and optimistic locking paths |
| Insert-only column altered by another app | Annotation is not a database constraint | Use triggers/DB privileges if strict enforcement is required |

When debugging, record: (1) whether the property is on the root or a child; (2) insert SQL; (3) update SQL; (4) database values after reload. These four facts clarify whether the annotation is used within its supported scope or another write path is bypassing it.

## 13. Hands-on exercise: verifying insert-only on the root

Using the `documents` table and entity above, practice on H2 or a test database:

1. Create a new `Document` with `externalReference = "EXT-001"` and a fixed `createdAt`; call `save`.
2. Read back by ID and record the two values persisted in the database.
3. Construct a new object with the same ID/version, intentionally change `externalReference` and `createdAt`, and change `title`; call `save`.
4. Read back from the database. Verify `title` changed while the two insert-only columns kept their initial values.
5. Inspect runtime SQL to verify both columns appear in `INSERT` but not in `SET` of `UPDATE`.
6. Try placing the same annotation on a child entity property in a separate example to observe your framework version's boundaries; do not rely on behavior outside the supported scope as a stable contract.
7. Try updating the column via direct SQL in the test database to confirm the annotation does not replace database-level constraints.

Never run data-modification experiments on a production database. When inspecting objects after `save`, distinguish values in the Java object from values stored in the database.

## 14. Key takeaways

- `@InsertOnlyProperty` marks a property written on insert and excluded from updates generated by Spring Data JDBC within its supported scope.
- The supported scope is **properties on the aggregate root**; do not extrapolate to child entities in `@MappedCollection`.
- `@Id` still governs identity and new/existing entity detection; `@Version` still manages optimistic locking.
- The annotation does not create schemas, generate default values, auto-reload the database, or block custom SQL.
- With immutable entities, use the object returned from `save` to obtain ID/version; reload when you need a database-verified snapshot of insert-only properties.
- If absolute immutability across all write paths is required, add database constraints or privileges.

In Spring Data JDBC, use `@InsertOnlyProperty` for **aggregate root** values established at creation that must remain unchanged across routine updates. Verify the annotation against DDL and runtime SQL while keeping root/child boundaries clear. That way, metadata accurately reflects the data lifecycle the application intends to protect, while database-wide immutability requirements are handled by appropriate mechanisms at the storage layer.
