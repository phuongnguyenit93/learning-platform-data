# How Does Spring Data Create Objects from Data Rows?

## 1. From a SQL Row to a Java Object

When calling a repository:

~~~java
Optional<Book> result = bookRepository.findById(42L);
~~~

the application receives a `Book` object, even though the database only stores a row in the `books` table. Spring Data JDBC performs a process of **reading values from JDBC results, matching mapping metadata, converting types, and instantiating Java objects**.

General flow:

~~~mermaid
flowchart TD
    A["Repository method<br/>findById / query"] --> B["Spring Data JDBC data access"]
    B --> C["JDBC PreparedStatement"]
    C --> D["Database executes SQL"]
    D --> E["ResultSet"]
    E --> F["Row mapping / JdbcConverter"]
    F --> G["Relational mapping metadata"]
    G --> H["Convert JDBC values to Java types"]
    H --> I["Select persistence constructor"]
    I --> J["Create object"]
    J --> K["Populate remaining properties"]
    K --> L["Return entity / aggregate"]
~~~

Important point: **Spring Data JDBC does not simply take the first column and assign it to the first field, or the second column to the second field**. The framework uses metadata about entities, properties, constructors, table/column names, and converters to determine how to create the object. Therefore, column order in a SQL statement is usually not the constructor parameter order; column names and mapping metadata are what decide.

This article focuses on Spring Data JDBC in the Spring Data Relational JDBC module. Internal implementations may change across versions, but the concepts of mapping metadata, persistence constructors, conversion, and property population are foundational to understanding this process.

## 2. Components Involved in the Mapping Process

At a conceptual level, the main components include:

| Component | Role |
|---|---|
| Repository / data access strategy | Receives data read requests and executes appropriate JDBC operations |
| JDBC ResultSet | Provides values for each result row from the database |
| Spring Data JDBC row mapper | Reads each row and converts it into an object through the converter |
| JdbcConverter / mapping converter | Coordinates metadata, conversion, and object creation |
| RelationalMappingContext | Holds mapping metadata for relational entities and properties |
| RelationalPersistentEntity | Describes an entity: table, identifier, constructor, and properties |
| RelationalPersistentProperty | Describes a property: column name, Java type, annotations, and mapping rules |
| EntityInstantiator / persistence constructor | Creates an instance using the constructor selected by Spring Data |
| PersistentPropertyAccessor | Sets properties not passed to the constructor or creates a new instance for immutable objects |
| Custom conversions | Application-defined conversions between SQL/JDBC types and Java types |

Internal class names and how components collaborate may change across Spring Data versions. You do not need to memorize the entire implementation to use repositories; you need to understand the role of each step when debugging mapping.

### Flow for Reading a Row

1. A repository or custom query requests data.
2. JDBC executes SQL and returns a `ResultSet`.
3. The row mapper reads one row at the current position.
4. The converter uses metadata to determine which properties correspond to the columns.
5. JDBC values are converted to target Java types if needed.
6. Spring Data selects the persistence constructor and passes the corresponding values.
7. Remaining properties are populated after object creation, according to property accessibility.
8. For aggregates with relationships, Spring Data JDBC continues loading the aggregate's parts according to their mapping.

## 3. Source Data Example

Suppose the database has the following table:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn_code VARCHAR(20) NOT NULL,
    title VARCHAR(200) NOT NULL,
    price DECIMAL(12, 2) NOT NULL,
    published_on DATE
);

INSERT INTO books (isbn_code, title, price, published_on)
VALUES
    ('978-0000000001', 'Spring Data JDBC', 199000.00, DATE '2025-01-15'),
    ('978-0000000002', 'Relational Mapping', 159000.00, NULL);
~~~

Java entity:

~~~java
import java.math.BigDecimal;
import java.time.LocalDate;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public class Book {

    @Id
    private Long id;

    @Column("isbn_code")
    private String isbn;

    private String title;

    private BigDecimal price;

    @Column("published_on")
    private LocalDate publishedOn;

    // constructors, getters...
}
~~~

Rules:

- `id` is the identifier designated by `@Id`.
- `isbn` is mapped to the `isbn_code` column.
- `title` and `price` use column names based on default metadata/conventions.
- `publishedOn` is mapped to `published_on`.
- SQL `NULL` for `published_on` can be represented by `null` in the `LocalDate` reference property.

Query:

~~~sql
SELECT id, isbn_code, title, price, published_on
FROM books
WHERE id = ?;
~~~

A result row contains the values of five columns. Spring Data does not need to know which column comes first in the class; it uses column names and mapping metadata to place values into the right properties.

## 4. Step 1: Reading ResultSet and Identifying Columns

`ResultSet` is the JDBC API representing a query result set. On each row, the driver allows reading values by column name or index:

~~~java
long id = rs.getLong("id");
String title = rs.getString("title");
BigDecimal price = rs.getBigDecimal("price");
~~~

Spring Data JDBC uses row mapping to translate a result row into a data structure that the converter can read. Instead of requiring the entity to know how to call `rs.getString(...)`, the converter retrieves column names, data types, and property metadata to perform the mapping.

### 4.1. Mapping Based on Column Name

The Java property `isbn` is mapped using:

~~~java
@Column("isbn_code")
private String isbn;
~~~

The value to read comes from the `isbn_code` column. If the SQL returns a column named `isbn` while the metadata expects `isbn_code`, mapping may fail to find the value as expected. With custom queries, return column names or aliases compatible with the metadata and projection required by the method.

**Do not rely on column position in SELECT** to infer field order or constructor parameter order. Changing column order in SQL should not change mapping semantics as long as column names remain correct.

### 4.2. Column Names and Naming Conventions

Spring Data Relational uses a naming strategy to relate property names to physical column names. For example, `publishedOn` typically corresponds to `published_on`. `@Column` allows explicit specification when the schema differs from the convention.

For databases with quoted identifiers, case sensitivity, or special names, verify how the driver reports column labels and how the dialect/naming strategy handles them. Custom queries should choose intentional aliases rather than arbitrary aliases expecting the converter to guess.

## 5. Step 2: Converting JDBC Data Types to Java

Database data types and Java types are not always identical. The JDBC driver returns values according to the JDBC API; Spring Data JDBC uses the conversion infrastructure to convert them to the target property types.

| Common SQL Type | Common Java Type | Notes |
|---|---|---|
| `BIGINT` | `Long` | Suitable for numeric identifiers |
| `INTEGER` | `Integer` | Use wrapper if the column allows NULL |
| `VARCHAR` | `String` | Length and charset are determined by schema |
| `DECIMAL`, `NUMERIC` | `BigDecimal` | Suitable for monetary and exact decimal data |
| `DATE` | `LocalDate` | Represents date only |
| `TIMESTAMP` | `LocalDateTime` | Carries no time zone information |
| `BOOLEAN` | `Boolean` | Exact mapping depends on driver/database |
| `UUID` | `UUID` | Support depends on database and driver |

For example, column `price DECIMAL(12, 2)` is read into `BigDecimal`, rather than using `double` for monetary amounts requiring decimal precision.

### 5.1. NULL and Java Types

If the database returns `NULL` for a nullable column, the Java property should be able to represent the absence of data:

~~~java
private LocalDate publishedOn;
private Integer pageCount;
~~~

Use the wrapper `Integer` instead of the primitive `int` when a column can be null. Primitives cannot represent `null`; when mapping passes a null value to a primitive property or primitive constructor parameter, the application may encounter conversion/instantiation errors or default values that do not accurately reflect business semantics, depending on the mapping path.

Do not interpret SQL NULL as `0`, an empty string, or the current date unless business rules specify so.

### 5.2. Custom Conversion for Domain Types

Suppose the domain uses an `Isbn` type instead of `String`:

~~~java
public record Isbn(String value) {
    public Isbn {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("ISBN must not be blank");
        }
    }
}
~~~

The application can register reading and writing converters to map `VARCHAR` with `Isbn`.

Reading converter:

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToIsbnConverter implements Converter<String, Isbn> {
    @Override
    public Isbn convert(String source) {
        return new Isbn(source);
    }
}
~~~

Writing converter:

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class IsbnToStringConverter implements Converter<Isbn, String> {
    @Override
    public String convert(Isbn source) {
        return source.value();
    }
}
~~~

Converters must be registered in Spring Data JDBC configuration (for example via the user converters list of the relational JDBC configuration corresponding to the version in use). Placing annotations on converter classes alone does not guarantee every application automatically discovers those converters.

Custom converters should clearly define the conversion direction:

- **Reading converter:** value from JDBC/database to domain type.
- **Writing converter:** domain type to JDBC/database type.

## 6. Step 3: How Spring Data Selects a Constructor to Create Objects

After obtaining the appropriate values, Spring Data must create an instance. This is crucial for understanding why entities can use constructors, records, or immutable classes.

Spring Data looks up the **persistence constructor** based on metadata. Common cases:

1. **Java record:** the record's canonical constructor is used to create the instance.
2. **Single constructor:** that constructor is typically selected.
3. **Multiple constructors:** the appropriate constructor can be marked with `@PersistenceCreator`.
4. **No-arg constructor:** can be used when consistent with selection rules and other constructors.
5. **Factory method or supported instantiation style:** can be selected according to corresponding metadata.

If there are multiple constructors without a clear choice according to Spring Data's rules, entity creation may fail. Design constructors clearly and use `@PersistenceCreator` when explicit designation is needed.

### 6.1. Constructors Selected by Property Name

Example immutable entity:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public class Book {

    @Id
    private final Long id;

    @Column("isbn_code")
    private final String isbn;

    private final String title;

    private final BigDecimal price;

    @PersistenceCreator
    public Book(Long id, String isbn, String title, BigDecimal price) {
        this.id = id;
        this.isbn = isbn;
        this.title = title;
        this.price = price;
    }

    public Long getId() {
        return id;
    }

    public String getIsbn() {
        return isbn;
    }

    public String getTitle() {
        return title;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

Constructor parameter names must correspond to Java property names: `id`, `isbn`, `title`, `price`. The physical column name `isbn_code` is mapped by `@Column` metadata to the `isbn` property; the constructor does not need a parameter named `isbn_code`.

This separates two concepts:

- **Column name:** the column name in the database.
- **Property/parameter name:** the Java property name accepted by the constructor.

If regular classes are compiled without preserving parameter names, the framework may lack the information needed to associate constructor parameters with properties. In Java builds, ensure configuration preserves parameter names (for example compiler option `-parameters`) when mapping relies on parameter names. Records have clearer component/constructor metadata.

### 6.2. Records and Canonical Constructors

With a Java record:

~~~java
import java.math.BigDecimal;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("books")
public record Book(
        @Id Long id,
        @Column("isbn_code") String isbn,
        String title,
        BigDecimal price
) {}
~~~

A record is an immutable type: after instantiation, components cannot be reassigned. Spring Data uses the canonical constructor to create the record with the read values.

When calling `repository.save(new Book(null, ...))`, the repository may return a new record carrying the database-generated ID. Therefore, always use the **return value of `save`** to obtain the entity version with the updated identifier.

### 6.3. When to Use `@PersistenceCreator`?

If a class has multiple constructors:

~~~java
public class Book {

    private final Long id;
    private final String title;
    private final String isbn;

    public Book(String title) {
        this(null, title, null);
    }

    @PersistenceCreator
    public Book(Long id, String title, String isbn) {
        this.id = id;
        this.title = title;
        this.isbn = isbn;
    }

    // getters...
}
~~~

`@PersistenceCreator` indicates which constructor Spring Data should use when reading data. The annotation belongs to `org.springframework.data.annotation.PersistenceCreator`.

The selected constructor must be able to receive the values needed to construct a valid entity; parameter names must match the corresponding Java properties.

## 7. Step 4: Populating Properties After the Constructor Runs

Not every property necessarily has to be passed into the constructor. After creating the instance, Spring Data can populate the remaining properties through property access mechanisms.

Example mutable class:

~~~java
@Table("books")
public class Book {

    @Id
    private Long id;

    private String title;

    private BigDecimal price;

    public Book() {
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public void setPrice(BigDecimal price) {
        this.price = price;
    }
}
~~~

With this model, Spring Data can create an instance using the no-arg constructor and then populate the missing properties according to metadata and the appropriate access mechanism.

Common ways to access properties include:

- **Field access:** writes directly to the field when mapping selects field access.
- **Property/setter access:** uses the corresponding setter.
- **Wither/copy method:** for immutable objects, creates a new instance containing the updated property.
- **Constructor:** passes the property directly at instantiation, avoiding subsequent assignment.

Do not put important business logic inside setters expecting setters to always be called when Spring Data reads an entity. The exact access path depends on metadata and the entity model.

### 7.1. Immutable Objects and Withers

Suppose an immutable class has a `createdAt` property populated during the lifecycle that is not in the persistence constructor. A wither returning a new object can be used:

~~~java
public Book withCreatedAt(Instant createdAt) {
    return new Book(id, title, price, createdAt);
}
~~~

Spring Data can use a conventional wither method to create a copy with the new property instead of modifying a final field. For immutable entities, it is usually best to include all needed values in the persistence constructor, especially when they are required to build a valid object.

## 8. Comparing Three Ways to Create Objects

| Design Approach | Creation Process | Best Suited For |
|---|---|---|
| Mutable class, no-arg constructor | Create instance then populate properties | Simple models with setter/field access |
| Immutable class, persistence constructor | Read values then pass into constructor | Preserving invariants, avoiding incomplete object states |
| Java record | Use canonical constructor with component values | Simple DTOs/domain values, immutable data |

**Mutable object:**

~~~java
Book book = new Book();
book.setId(42L);
book.setTitle("Spring Data JDBC");
~~~

**Immutable object:**

~~~java
Book book = new Book(42L, "Spring Data JDBC");
~~~

Both can represent the same data. The difference is that mutable objects allow intermediate states and post-initialization mutation; immutable objects require necessary data to be provided via constructors or copy mechanisms.

## 9. Does One SQL Row Correspond to a Complete Aggregate?

This is a particularly important point in **Spring Data JDBC**.

A row mapper can create the aggregate root from a row in the main table. However, an aggregate may contain child objects/collections stored in other tables. Spring Data JDBC uses mapping metadata to load parts belonging to the aggregate according to the relational mapping model; do not assume every child object is already present in a single result row.

Example:

~~~text
orders
+----+------------+
| id | order_date |
+----+------------+
| 10 | 2026-01-15 |
+----+------------+

order_lines
+----+----------+------------+-----+
| id | order_id | product_id | qty |
+----+----------+------------+-----+
|  1 |       10 |        101 |   2 |
|  2 |       10 |        205 |   1 |
+----+----------+------------+-----+
~~~

The aggregate root `Order` may contain a `lines` collection:

~~~java
@Table("orders")
public class Order {

    @Id
    private Long id;

    @Column("order_date")
    private LocalDate orderDate;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // constructor, getters...
}
~~~

Spring Data JDBC knows `order_lines.order_id` links the line items to the corresponding order. When loading an aggregate, the framework must read the root data and the data of components belonging to the aggregate according to the mapping. Query details depend on the aggregate structure and implementation; do not equate it with a single `JOIN` statement returning all columns.

### 9.1. Embedded Objects vs. Collections

With `@Embedded`, properties of a value object can reside directly in the row of the containing table. For example, an `Address` created from address columns in the same `customers` row. Prefixes or embedded mapping rules help avoid column name collisions.

In this case, the converter reads multiple columns from **the same row** to create the `Address` value object. For a collection mapped to a child table, the framework must locate related rows using a reference key.

- Embedded: reads multiple columns from the parent row.
- Collection within an aggregate: loads data from related tables according to mapping relationships.

## 10. Mapping Data from Custom Queries

Spring Data JDBC can map custom query results into an entity or an appropriate projection. Example:

~~~java
public interface BookRepository extends CrudRepository<Book, Long> {

    @Query("""
        SELECT id, isbn_code, title, price, published_on
        FROM books
        WHERE price >= :minPrice
        ORDER BY title
        """)
    List<Book> findExpensiveBooks(BigDecimal minPrice);
}
~~~

With return type `Book`, the result must supply the columns required by `Book`'s mapping. Column names must match `@Column` and the naming strategy. If only a few columns are returned while the method declares the full entity as its return type, properties without data may not be initialized as business logic expects.

If only a subset of data is needed, define a projection/DTO:

~~~java
public record BookSummary(
        String title,
        BigDecimal price
) {}
~~~

Query:

~~~java
@Query("""
    SELECT title, price
    FROM books
    WHERE price >= :minPrice
    ORDER BY title
    """)
List<BookSummary> findSummaries(BigDecimal minPrice);
~~~

The projection has a constructor corresponding to the returned values; column names/aliases must be compatible with how the framework maps the projection. For complex projections or queries with joins, define the result type explicitly instead of forcing an incomplete set of columns into an aggregate root.

## 11. Distinguishing Spring Data JDBC Mapping from a Hand-Written RowMapper

When using Spring JDBC directly, an application typically writes its own `RowMapper`:

~~~java
RowMapper<BookSummary> mapper = (rs, rowNum) ->
        new BookSummary(
                rs.getString("title"),
                rs.getBigDecimal("price")
        );

List<BookSummary> summaries = jdbcTemplate.query(
        "SELECT title, price FROM books",
        mapper
);
~~~

Here **the application decides everything itself**:

- Which columns are read.
- Whether to read by name or by index.
- Which values are passed to the constructor.
- How nulls and type conversions are handled.

With a Spring Data JDBC repository, the framework relies on the mapping context, metadata, and converters to perform those steps based on conventions and annotations.

| Criterion | Spring Data JDBC Repository | Hand-Written Spring JDBC RowMapper |
|---|---|---|
| Selecting columns/metadata | Based on entity/projection mapping | Decided by the mapper author |
| Creating objects | Converters and persistence constructor | Hand-written mapper lambda/class |
| Renaming columns | `@Column`, naming strategy, and metadata | SQL aliases or mapper logic |
| Type conversion | Conversion infrastructure and custom conversions | JDBC getters or hand-written converters |
| Aggregates | Has aggregate mapping rules | Author queries and assembles objects manually |
| CRUD | Repository supports standard operations | Hand-written SQL and mappers |

Do not think `@Column` automatically alters SQL written manually for `JdbcTemplate`. Annotations belong to Spring Data mapping metadata; manual SQL/`RowMapper` remain under application control.

## 12. Customizing Object Creation and Mapping

### 12.1. Using `@PersistenceCreator`

When an entity has multiple constructors, mark the constructor used to create the entity:

~~~java
@PersistenceCreator
public Book(Long id, String title, BigDecimal price) {
    this.id = id;
    this.title = title;
    this.price = price;
}
~~~

Keep parameter names identical to Java properties and ensure parameter name metadata can be discovered.

### 12.2. Using Converters for Special Types

When the database stores a simple type but the domain uses a custom type, create reading/writing converters and register them in Spring Data JDBC configuration. Do not stuff complex data parsing logic into getters or setters.

### 12.3. Using Lifecycle Callbacks for Additional Steps

Spring Data Relational provides callbacks such as `AfterConvertCallback` to perform processing after an entity has been converted from read data. For example, you can normalize or enrich derived information, but callbacks should have a clear purpose and not replace standard conversion/mapping.

Callback skeleton:

~~~java
import org.springframework.data.relational.core.mapping.event.AfterConvertCallback;
import org.springframework.stereotype.Component;

@Component
public class BookAfterConvertCallback
        implements AfterConvertCallback<Book> {

    @Override
    public Book onAfterConvert(Book book) {
        // Perform only appropriate post-mapping processing.
        return book;
    }
}
~~~

The entity returned by the callback is used going forward. For immutable objects, create and return a new instance if data changes are needed. Do not use callbacks to silently issue many extra queries or create unnecessary side effects when reading each entity.

## 13. Common Errors When Spring Data Creates Objects

| Symptom | Possible Cause | What to Check |
|---|---|---|
| Cannot find value for property | Column name/alias does not match metadata | Check DDL, `@Column`, naming strategy, and SELECT |
| Unexpected constructor selected | Multiple constructors without designating persistence constructor | Use `@PersistenceCreator` and check constructor rules |
| Cannot initialize constructor parameter | Parameter names not retained or do not match properties | Enable `-parameters`, check parameter names and records |
| Type conversion error | SQL and Java types incompatible or converter missing | Check driver, Java type, and reading converter |
| Null value causes error | Primitive property or constructor rejects null | Use wrapper/nullable type or clear data constraints |
| Record returns null ID after save | Using old instance instead of `save` return value, or generated keys unsupported/unconfigured | Use return value and check identity/driver |
| Property not updated | Unsuitable mapping access strategy, immutable field without wither/constructor | Include property in constructor or provide copy mechanism |
| Aggregate missing child collection | Relationship not declared properly or join column mismatch | Check `@MappedCollection`, foreign key, and schema |
| Embedded object always null | Incorrect columns/prefix or empty-object detection rules | Check `@Embedded`, prefix, and column values |
| Custom query returns entity with missing data | SELECT does not return all columns the entity needs | Return all required columns or use a dedicated projection |

### Debugging Order

1. Verify the SQL statement and the actual columns/aliases returned.
2. Check `@Table`, `@Column`, `@Id`, and the naming strategy.
3. Check Java types, SQL types, nullability, and custom conversions.
4. Check the constructor selected by Spring Data, parameter names, and property access.
5. If it is an aggregate, check relationship mappings and child table data.
6. If the error occurs only in a custom query, compare the query's returned column list against the entity/projection.

## 15. Key Takeaways

- Spring Data JDBC reads rows through JDBC result mapping and then uses **mapping metadata and converters** to create Java objects.
- Mapping relies on **column names, property metadata, and conversion**, not simply on column order in a SELECT statement.
- Spring Data selects a **persistence constructor**; records use the canonical constructor, and classes with multiple constructors should designate one explicitly with `@PersistenceCreator` when needed.
- Properties not passed to the constructor can be populated afterward via field/setter access or a wither/copy method.
- Database data types must be compatible with Java types; custom reading/writing converters handle specialized domain types.
- One row of the root table can create the aggregate root; collections within the aggregate may require additional reads from related tables. Embedded objects are constructed from columns of the same row.
- `JdbcTemplate` with a hand-written `RowMapper` is a different mechanism: the application directly decides how to read columns and instantiate objects.
- When debugging, check in order: **SQL result → column mapping → type conversion → constructor → property population → aggregate mapping**.
