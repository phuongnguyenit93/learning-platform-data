# When Do You Need a Converter Instead of an Embedded Object?

In Spring Data JDBC, a value object can be mapped in two common ways: an **embedded object** using §@Embedded§ or a **custom converter** using Spring's §Converter§. Both let the domain model use meaningful Java types, but they produce different storage structures.

- Use **§@Embedded§** when the properties of a value object should become separate columns in the same table as the parent entity.
- Use a **converter** when an entire domain property should be converted into a single database value and restored from that value.
- If the object has its own identity, lifecycle, or independent business rules, consider modeling a separate entity/aggregate. Converters and embedded objects do not replace aggregate boundaries.

For example, a shipping address with street, city, and postal code usually fits §@Embedded§ because the application can filter, sort, and create indexes on individual parts. An §EmailAddress§ type can fit a converter because the entire email value is stored in a single §VARCHAR§ column.

The deciding factor is not whether the Java class has many or few properties, but whether **the database needs to see the value object as multiple columns or as a single value**.

## 1. Two Mapping Approaches, Two Storage Structures

Suppose the §Customer§ aggregate has two values:

- §Address§ containing street, city, and postal code.
- §EmailAddress§, a dedicated domain type wrapping an email address.

A Java model:

§§§java
@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address,

        EmailAddress email
) {
}

public record Address(
        String street,
        String city,
        String postalCode
) {
}

public record EmailAddress(String value) {
}
§§§

Both §address§ and §email§ properties are value objects, but the appropriate storage approach for each can differ.

§§§text
Customer
  |
  +-- Address
  |     +-- street
  |     +-- city
  |     +-- postalCode
  |          |
  |          +----> multiple columns in the customers table
  |
  +-- EmailAddress
        +-- value
             |
             +----> a single email column in the customers table
                       via a custom Converter
§§§

The database table could look like:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,

    address_street VARCHAR(250),
    address_city VARCHAR(100),
    address_postal_code VARCHAR(20),

    email VARCHAR(320) NOT NULL
);
§§§

§Address§ is flattened into three columns. §EmailAddress§ is converted into a string value and stored in a single column.

## 2. Embedded Objects with @Embedded

§@Embedded§ is used to map the properties of an object into **the same table as its containing entity**. An embedded object does not need its own ID and does not have its own repository just because it is declared as a Java class.

For example:

§§§java
import org.springframework.data.relational.core.mapping.Embedded;

public record Address(
        String street,
        String city,
        String postalCode
) {
}

@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address
) {
}
§§§

The mapped columns:

| Java Property | Database Column |
| --- | --- |
| §id§ | §id§ |
| §name§ | §name§ |
| §address.street§ | §address_street§ |
| §address.city§ | §address_city§ |
| §address.postalCode§ | §address_postal_code§ |

The prefix helps avoid column name collisions when an aggregate has multiple value objects of the same type.

### 2.1. When Is Embedded Appropriate?

Use embedded when:

- The object's fields have individual meaning and should be stored in separate columns.
- The application frequently filters by one or more properties inside the object.
- You need to create indexes, unique constraints, check constraints, or sort by individual properties.
- Properties need to be updated or validated independently at the SQL level.
- The object has no independent identity or lifecycle; it belongs to its containing entity/aggregate.

For example, a shipping address might require filtering all customers in a given city:

§§§sql
SELECT id, name, address_street, address_city, address_postal_code
FROM customers
WHERE address_city = 'Hà Nội';
§§§

Because §city§ is a separate column, the database can use an index on that column:

§§§sql
CREATE INDEX idx_customers_address_city
    ON customers(address_city);
§§§

If the entire address were serialized into an opaque string, filtering by city would be harder and might require database-specific string/JSON functions.

### 2.2. Using Multiple Embedded Objects of the Same Type

An entity can contain two addresses of the same type, such as a billing address and a shipping address:

§§§java
@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,

        @Embedded(prefix = "shipping_")
        Address shippingAddress,

        @Embedded(prefix = "billing_")
        Address billingAddress
) {
}
§§§

The schema can contain two groups of columns:

§§§sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    shipping_street VARCHAR(250),
    shipping_city VARCHAR(100),
    shipping_postal_code VARCHAR(20),

    billing_street VARCHAR(250),
    billing_city VARCHAR(100),
    billing_postal_code VARCHAR(20)
);
§§§

Two objects of the same Java type are mapped to different columns thanks to the prefixes.

### 2.3. Handling Empty Embedded Objects with onEmpty

§@Embedded§ has an §onEmpty§ attribute to decide how to restore the object when all columns mapped from it are SQL NULL.

Two main options:

- §USE_NULL§: the embedded property becomes §null§ when all of its columns are null.
- §USE_EMPTY§: the framework attempts to create an instance with null properties.

For example:

§§§java
@Embedded(onEmpty = Embedded.OnEmpty.USE_NULL)
Address address
§§§

Or use the shortcut §@Embedded.Nullable§ corresponding to §USE_NULL§ behavior; §@Embedded.Empty§ corresponds to §USE_EMPTY§.

This matters when the domain distinguishes between:

- No address: §address == null§.
- An address object exists, but its fields currently have no values: a non-null object whose properties can be null.

If an embedded object contains a §Collection§ or §Map§, Spring Data Relational always considers it non-empty because the collection/map can at least exist in an empty state. Therefore, an embedded object with a collection/map will not become null simply because its scalar columns are all null.

## 3. What Is a Custom Converter?

A custom converter is a Spring §Converter<S, T>§ used to convert between a domain type and a type that the JDBC layer can store or read.

In Spring Data Relational, converters are applied at the **property level**: a single domain value is converted to a single database value and vice versa. A converter does not flatten a complex object into multiple columns.

For example, the domain has a dedicated §EmailAddress§ type:

§§§java
public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(
                    "Email address is required"
            );
        }

        value = value.trim().toLowerCase(Locale.ROOT);
    }
}
§§§

The database only needs a single §VARCHAR§ column:

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    email VARCHAR(320) NOT NULL
);
§§§

The writing converter turns §EmailAddress§ into §String§:

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public enum EmailAddressWriteConverter
        implements Converter<EmailAddress, String> {

    INSTANCE;

    @Override
    public String convert(EmailAddress source) {
        return source.value();
    }
}
§§§

The reading converter turns §String§ from the database into §EmailAddress§:

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public enum StringToEmailAddressConverter
        implements Converter<String, EmailAddress> {

    INSTANCE;

    @Override
    public EmailAddress convert(String source) {
        return new EmailAddress(source);
    }
}
§§§

When saving §Customer§, the §EmailAddress§ value is written as a string. When reading it back, the string is converted into an §EmailAddress§ object.

### 3.1. Converters Do Not Create Extra Tables or Multiple Columns

Suppose:

§§§java
public record Money(
        BigDecimal amount,
        String currency
) {
}
§§§

A converter could serialize the entire object into a single string value, such as §"USD|125.50"§, and read it back from a §VARCHAR§ column. In that case, the database sees only a single value.

A converter does not automatically create two columns §amount§ and §currency§. If you need two columns that can be filtered and indexed independently, using §@Embedded§ is more appropriate.

A converter can convert to a database-specific type supported by the JDBC driver, or use §JdbcValue§ if you need to specify the JDBC type explicitly. Even so, the result is still a single value for a single property, not a mechanism for mapping an object to multiple columns.

### 3.2. Why Must You Provide Both Reading and Writing Converters?

For a complete round-trip:

§§§text
Java domain value
      |
      | EmailAddressWriteConverter
      v
Database value (VARCHAR)
      |
      | StringToEmailAddressConverter
      v
Java domain value
§§§

If you only register a writing converter, Spring Data can write the value but will not have a matching converter to restore the domain type when reading. Conversely, with only a reading converter, data can be read, but the domain type may not be writable.

When designing a bidirectional custom type, provide both the corresponding reading and writing converters.

## 4. Registering Converters in Spring Data JDBC

A converter is not automatically registered just because the class is in component scan or has a Spring annotation. Spring Data requires explicit converter registration through custom conversions.

In Spring Data Relational 4.1.2, the standard way to configure this with §AbstractJdbcConfiguration§ is to override §userConverters()§:

§§§java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class DataJdbcConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
                EmailAddressWriteConverter.INSTANCE,
                StringToEmailAddressConverter.INSTANCE
        );
    }
}
§§§

The framework combines user converters with default converters and JDBC dialect converters.

**Do not arbitrarily override §jdbcCustomConversions()§ following examples from older versions.** In the current documentation, this method assembles shared conversions, dialect-registered conversions, and application conversions. If you replace the whole thing with a new list, you may lose default converters or dialect-specific converters.

If the application uses Spring Boot to configure Spring Data JDBC, you can provide a §JdbcCustomConversions§ bean according to the Boot configuration guide. Choose an approach that fits your current infrastructure and ensure the converters are registered into the exact conversion service used by §JdbcConverter§.

### 4.1. Distinguishing Reading and Writing Directions

Two converters may use source/target types that are both simple types. For example, §String§ and §Long§ are both types that JDBC handles directly. In such cases, the framework cannot always infer whether a converter is for reading or writing.

§@ReadingConverter§ and §@WritingConverter§ clarify the direction:

| Annotation | Direction |
| --- | --- |
| §@WritingConverter§ | From domain type to database type when writing. |
| §@ReadingConverter§ | From database type to domain type when reading. |

With §EmailAddress§ and §String§, even though one side is a custom type, declaring the annotation explicitly makes the code easier to understand and prevents registering the converter for an unintended direction.

### 4.2. Converters Need a Stable Format

If a converter serializes an object into a string or JSON, that format becomes a contract between the application and the stored data.

Considerations include:

- How null is represented.
- Data normalization rules.
- Delimiters and escaping.
- Locale, timezone, and numeric precision.
- Ability to read data from older application versions.
- How to handle malformed strings or invalid historical data.

Do not change a converter's format arbitrarily once the database already contains data written in the old format. A migration or backward-compatible reading converter may be required.

## 5. Direct Comparison of @Embedded and Converter

| Criterion | §@Embedded§ | Custom converter |
| --- | --- | --- |
| Database structure | Multiple columns in the parent table | One database value for one property |
| Mapping approach | Flattens object properties | Converts object to a scalar/native database value |
| Querying sub-fields | Easy with SQL on each column | Depends on storage type; usually harder if value is opaque |
| Indexing individual fields | Separate indexes can be created | Usually only indexes the whole value or uses DB-specific features |
| Field-level constraints | Can use NOT NULL, CHECK, UNIQUE on columns | Harder if the entire object resides in a single column |
| Conversion code | Usually no converter needed | Requires reading/writing converters and registration |
| Own identity | No | No |
| Own lifecycle | No | No |
| Stores multiple properties as multiple columns | Yes | No |
| Serializes into a single column | Not the goal of embedded | Possible |

Both can preserve a rich domain model. The difference lies in the relational data shape they produce.

## 6. Choose Embedded When You Need to Query by Individual Properties

Address is a classic example:

§§§java
public record Address(
        String street,
        String city,
        String postalCode
) {
}
§§§

If you use §@Embedded§, you can write SQL:

§§§sql
SELECT id, name
FROM customers
WHERE address_city = 'Đà Nẵng'
ORDER BY address_postal_code;
§§§

The database can create dedicated indexes:

§§§sql
CREATE INDEX idx_customers_city_postal
    ON customers(address_city, address_postal_code);
§§§

If a converter turns the entire §Address§ into a string such as §"street|city|postalCode"§, querying by city must parse the string or use database-specific functions. This makes queries harder to read, harder to optimize, and tightly coupled to the serialization format.

Therefore, when fields are meaningful in SQL, **embedded is usually the better choice**.

Suitable use cases:

- Addresses with street/city/postal code.
- Time ranges with start/end.
- Coordinates with latitude/longitude when filtering by each dimension is needed.
- Contact information with name/phone/email.
- Monetary information with amount/currency when querying or constraining each part is needed.

If an object has very many fields or has collections/relationships, further evaluate aggregate boundaries and collection mapping; not every nested object should simply be embedded.

## 7. Choose a Converter When a Value Needs to Be Stored as a Single Unit

A converter fits when the domain wants a dedicated type, but the database only needs a single value.

Examples:

### 7.1. EmailAddress

The domain wants to validate and normalize emails in the constructor:

§§§java
public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException("Email is required");
        }
        value = value.trim().toLowerCase(Locale.ROOT);
    }
}
§§§

The database only needs §email VARCHAR(320)§. There is no need to query domain, username, or host separately across distinct columns.

### 7.2. Domain Identifiers

For example, §CustomerCode§ with a standardized format:

§§§java
public record CustomerCode(String value) {

    public CustomerCode {
        if (value == null || !value.matches("[A-Z]{2}-[0-9]{6}")) {
            throw new IllegalArgumentException(
                    "Invalid customer code"
            );
        }
    }
}
§§§

The converter turns §CustomerCode§ into §String§. The database stores a single §customer_code§ column with a unique constraint.

### 7.3. Serialized Values

A small configuration object can be stored as JSON in a single column if:

- The database and driver support an appropriate column type.
- The application usually reads/writes the entire object as a single unit.
- No joins or relational constraints are needed on individual properties.
- A JSON versioning and data migration strategy has been established.

A converter can serialize the object into a JSON value. However, if using PostgreSQL §jsonb§ or a similar native type, check how the driver binds the SQL type; you may need to return §JdbcValue§ with the appropriate §JDBCType§ instead of just returning a plain §String§.

Do not assume a JSON string bound to a native JSON/JSONB column will always be interpreted with the right type by the database across all dialects.

## 8. When Should You Avoid a Converter?

Do not use a converter just to avoid declaring multiple columns if the database still needs to operate on individual fields.

Avoid converters when:

- You need to search by individual properties inside the object.
- You need to sort by a sub-field.
- You need a unique constraint or foreign key on part of the data.
- You need independent indexes on properties.
- You need to update one sub-field without rewriting the entire object.
- The object contains an entity collection or relationships with other aggregates.
- The data has an independent identity and lifecycle.

For example, §OrderAddress§ could be stored as a single string using a converter, but if reports frequently aggregate by province/city, embedded with a separate §city§ column is usually easier to optimize.

If the object needs its own table or is referenced from multiple places, consider a separate entity/aggregate instead of a converter. A converter only handles property type conversion; it does not create relationships between aggregates.

## 9. When Should You Avoid @Embedded?

Embedded is not the default choice for every value object class either.

Avoid §@Embedded§ if:

- The entire object needs to be stored as an opaque value in a single column.
- The storage format needs to be serialized/deserialized using custom rules.
- The database driver has a suitable native type for the domain value and requires custom mapping.
- The properties do not need to be queried individually and flattening them into multiple columns provides no benefit.
- The object actually has an independent identity and lifecycle.

For example, §EmailAddress§ has only a single string value. You could use §String§ directly, but a dedicated domain type keeps validation and normalization in one place. A converter is how you keep that domain type in Java while the database still uses a single string column.

Using §@Embedded§ for a class that only contains §value§ creates a prefixed column without necessarily offering benefits over a converter. Choose the representation that reflects the intended storage semantics.

## 10. Complete Example: Combining Embedded and Converter in the Same Aggregate

An aggregate can use both approaches on different properties.

### 10.1. Domain Model

§§§java
import java.util.Locale;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Embedded;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public record Customer(
        @Id Long id,
        String name,

        @Embedded(prefix = "address_")
        Address address,

        EmailAddress email
) {
}

public record Address(
        String street,
        String city,
        String postalCode
) {
}

public record EmailAddress(String value) {

    public EmailAddress {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(
                    "Email address is required"
            );
        }

        value = value.trim().toLowerCase(Locale.ROOT);
    }
}
§§§

### 10.2. Writing Converter

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public enum EmailAddressWriteConverter
        implements Converter<EmailAddress, String> {

    INSTANCE;

    @Override
    public String convert(EmailAddress source) {
        return source.value();
    }
}
§§§

### 10.3. Reading Converter

§§§java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public enum StringToEmailAddressConverter
        implements Converter<String, EmailAddress> {

    INSTANCE;

    @Override
    public EmailAddress convert(String source) {
        return new EmailAddress(source);
    }
}
§§§

### 10.4. Registering the Converters

§§§java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class DataJdbcConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
                EmailAddressWriteConverter.INSTANCE,
                StringToEmailAddressConverter.INSTANCE
        );
    }
}
§§§

If the application already has a class extending §AbstractJdbcConfiguration§, add the converters to the existing configuration rather than creating a second configuration with competing infrastructure.

### 10.5. Repository

§§§

### 10.6. Schema

§§§sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    address_city VARCHAR(100),
    address_postal_code VARCHAR(20),

### 10.7. Saving and Reading

§§§java
Customer customer = new Customer(
        null,
        "Nguyễn An",
        new Address(
                "12 Nguyễn Trãi",
                "Hà Nội",
                "100000"
        ),
        new EmailAddress("AN@example.com")
);

Customer saved = customerRepository.save(customer);

Customer loaded = customerRepository.findById(saved.id())
        .orElseThrow();

System.out.println(loaded.address().city());
System.out.println(loaded.email().value());
§§§

When saving:

- §Address§ is flattened into §address_street§, §address_city§, and §address_postal_code§.
- §EmailAddress§ is converted into a string and stored in the §email§ column.

When reading:

- The address columns are reconstructed into an §Address§ object.
- The email string is converted back into §EmailAddress§.

Both mechanisms work together within a single aggregate because each property has its own appropriate mapping strategy.

## 11. Impact on Queries and Updates

The mapping choice affects how SQL is written and how data is updated.

### 11.1. Querying Embedded Fields

Because embedded properties become separate columns, you can filter by them:

§§§sql
SELECT id, name
FROM customers
WHERE address_city = 'Hà Nội';
§§§

Dedicated indexes and constraints can be created for address columns.

### 11.2. Querying Converted Properties

With §EmailAddress§ converted to §String§, the database stores a single email value. You can filter using a comparison on the email column:

§§§sql
SELECT id, name
FROM customers
WHERE email = 'an@example.com';
§§§

When using a Spring Data query method or Criteria with a property type that has a registered converter, verify that conversion is applied to the parameter according to the mapping of the version and query path in use. With custom SQL, you can pass the normalized value from §EmailAddress.value()§ or use appropriate JDBC conversion.

A converter does not automatically create extra columns to query individual components inside an object.

### 11.3. Updating Value Objects

With an immutable embedded object, you can replace the entire value object:

§§§java
Address newAddress = new Address(
        "25 Lê Lợi",
        "Đà Nẵng",
        "550000"
);
§§§

With a converted property, replace the domain value:

§§§java
EmailAddress newEmail =
        new EmailAddress("new@example.com");
§§§

In both cases, mutate the aggregate through domain behavior and save the aggregate root according to Spring Data JDBC persistence rules. A converter is not a partial update mechanism; it only converts property values during reads and writes.

## 12. Converters with Specific SQL Types and JdbcValue

Normally, a writing converter can return a type supported by the JDBC driver, such as §String§, §BigDecimal§, §byte[]§, or a suitable native type.

In some cases, returning a Java value alone is not enough to specify the SQL type. For example, the application wants to bind a value using a specific JDBC type. Spring Data JDBC provides §JdbcValue§ to carry both the value and a §JDBCType§.

Idea:

§§§java
@WritingConverter
public class DomainValueWriteConverter
        implements Converter<DomainValue, JdbcValue> {

    @Override
    public JdbcValue convert(DomainValue source) {
        return JdbcValue.of(
                source.value(),
                JDBCType.VARCHAR
        );
    }
}
§§§

This example illustrates the role of §JdbcValue§; the specific JDBC type must match the column and driver in use. For native types like JSON/JSONB, check the dialect and how the driver expects parameters to be bound. Do not assume §VARCHAR§ can always substitute for a native database type.

§JdbcValue§ still represents a single value for a single property. It does not turn a converter into a multi-column object mapping mechanism.

## 13. Testing Converters and Mapping

Custom converters should be tested both in isolation and through integration tests with a database.

### 13.1. Unit Testing the Converter

§§§java
class EmailAddressConverterTest {

    @Test
    void writesEmailAsString() {
        EmailAddress email =
                new EmailAddress("AN@example.com");

        String stored =
                EmailAddressWriteConverter.INSTANCE.convert(email);

        assertEquals("an@example.com", stored);
    }

    @Test
    void readsStringAsEmailAddress() {
        EmailAddress email =
                StringToEmailAddressConverter.INSTANCE
                        .convert("AN@example.com");

        assertEquals("an@example.com", email.value());
    }
}
§§§

Unit tests verify normalization and conversion format.

### 13.2. Round-Trip Integration Test

§§§java
@Test
void savesAndLoadsCustomerWithEmbeddedAddressAndConvertedEmail() {
    Customer customer = new Customer(
            null,
            "Nguyễn An",
            new Address(
                    "12 Nguyễn Trãi",
                    "Hà Nội",
                    "100000"
            ),
            new EmailAddress("AN@example.com")
    );

    Customer saved = repository.save(customer);

    Customer loaded = repository.findById(saved.id())
            .orElseThrow();

    assertEquals("Hà Nội", loaded.address().city());
    assertEquals("an@example.com", loaded.email().value());
}
§§§

This test confirms two different mapping paths working together in one aggregate:

- The embedded object is reconstructed from multiple columns.
- The converted value is reconstructed from a single column.

### 13.3. Inspecting Data in the Database

In addition to checking the object after reading, verify the data shape:

§§§sql
SELECT
    id,
    address_street,
    address_city,
    address_postal_code,
    email
FROM customers;
§§§

The expected result has separate address columns and a single normalized email value. This helps detect cases where a converter was not registered or an embedded prefix does not match the schema.

### 13.4. Checking Legacy Data and Conversion Errors

If a converter is added to a column that already contains data, check:

- Does existing data match the format the reading converter expects?
- Are there null values or empty strings?
- Are there records written by an older version of the application?
- Is a migration needed to normalize data?
- Does the reading converter handle legacy formats?

A reading converter that throws an exception on invalid historical data can cause the entire aggregate load operation to fail. Have an appropriate migration or error-handling strategy in place.

## 14. Common Misconceptions

**"A converter can map an object to multiple columns."** No. Spring Data Relational custom converters apply at the property level and convert a single domain value into a single database value. Use §@Embedded§ when multiple columns are needed.

**"@Embedded creates a separate table."** No. Embedded properties are mapped into the parent entity's table.

**"Using a converter automatically creates a new database type."** No. A converter converts to a type that JDBC/the database can handle; if a specific SQL type is needed, consider §JdbcValue§ and the dialect.

**"Only a writing converter is needed."** Not if the application needs to read the custom type back. Register the corresponding reading converter.

**"Annotating a converter with @Component makes Spring Data use it automatically."** Do not assume so. Converters must be explicitly registered via custom conversions.

**"@ReadingConverter/@WritingConverter are unnecessary."** For converters whose source and target are both simple types, the framework may not determine the direction properly. Use the annotations to disambiguate.

**"You can override jdbcCustomConversions with your own list of converters."** Not recommended under the current guidance. That method also gathers default converters and dialect converters; use §userConverters()§ in §AbstractJdbcConfiguration§ per the current API.

**"An object with multiple properties must always use @Embedded."** Not necessarily. If the entire object is stored as an opaque value in a single column, a converter may be appropriate. Consider how the data is queried and constrained.

**"Converters are suitable for entities with identity."** No. Converters do not create relationships, foreign keys, repositories, or independent lifecycles.

**"A JSON converter always works with a JSONB column."** Do not assume so. You must bind the right JDBC/database type according to the dialect and driver, potentially using §JdbcValue§.

**"Embedded and a converter can be applied simultaneously to the same property."** Do not design it that way. Choose one clear mapping strategy per property; use embedded for a group of columns or a converter for a single value.

**"Converters replace domain validation."** No. Converters are responsible for representation conversion; validation and invariants still belong in the domain type or appropriate service.

## 15. Decision Process

When you have a value object in your domain, ask yourself:

1. **Does the object have its own identity?** If yes, consider a separate entity/aggregate; converters and embedded objects are not suitable for representing independent lifecycles.
2. **Do the properties need to become separate columns?** If yes, choose §@Embedded§.
3. **Does the application need to filter, sort, index, or constrain individual properties?** If yes, embedded is usually more convenient.
4. **Can the entire object be represented as a single database value?** If yes, a converter may be appropriate.
5. **Does the database driver support the target type?** If a specific SQL type is needed, check the dialect and §JdbcValue§.
6. **Is bidirectional reading and writing required?** Register the corresponding reading and writing converters.
7. **Does the converter have a clear direction?** Use §@ReadingConverter§ and §@WritingConverter§ when disambiguation is needed.
8. **Is the storage format stable across versions?** Define serialization and migration rules.
9. **Does the object need partial queries or per-property updates?** If yes, avoid serializing the whole object into an opaque value.
10. **Has round-trip behavior been tested against a real database?** Verify both the Java object and the stored column shape.

## 17. Key Takeaways

- §@Embedded§ flattens the properties of a value object into multiple columns in the same table as the parent entity.
- Spring Data Relational custom converters operate at the property level: one domain value is converted into one database value and vice versa.
- Converters do not map a complex object to multiple columns; use embedded when a multi-column structure is needed.
- Choose embedded when you need to query, sort, index, or constrain individual properties.
- Choose a converter when the entire object is stored as a single value, such as §EmailAddress§ to §VARCHAR§.
- Converters must be registered explicitly; provide both reading and writing converters when round-trip support is needed.
- Use §@ReadingConverter§ and §@WritingConverter§ to distinguish direction, especially when both source and target are simple types.
- With Spring Data Relational 4.1.2, use §userConverters()§ in §AbstractJdbcConfiguration§ per current guidance; avoid overriding §jdbcCustomConversions()§ as in older examples, which can drop dialect converters.
- §JdbcValue§ lets you specify an explicit JDBC type when a written value requires SQL type metadata.
- Converters and embedded objects do not create aggregate roots or independent lifecycles; if an object has its own identity, model it as an entity/aggregate.
- Test converters in isolation, test round-trips, and inspect the actual data in the database.
- Serialization formats must be stable and have a compatibility/migration plan once data is stored.

**Decide based on the shape of data the database needs to store:** if you need multiple individually queryable columns, use embedded; if you need a single value with a clear domain type, use a converter. The right choice lets the Java model preserve business meaning while the schema continues to support reading, filtering, and updating data effectively.
