# Optimistic locking with @Version on the aggregate root

In **Spring Data Relational JDBC (Spring Data JDBC)**, multiple requests can read and update the same aggregate concurrently. If two requests load the same version of an Order and then save their changes one after the other, the later operation risks overwriting data that the earlier operation just updated. This is a **lost update**.

Spring Data JDBC supports **optimistic locking** via the `@Version` annotation on the aggregate root. The framework uses the read version value as a condition during updates. If the row in the database already has a different version, the save operation does not update the expected row and Spring reports a conflict error. This mechanism detects conflicts without locking rows while users read and edit data.

## 1. The lost update problem

Suppose an Order has status `DRAFT` and version 4. Two requests A and B both load that Order:

~~~text
Database: Order #501, status = DRAFT, version = 4

Request A                         Request B
---------                         ---------
Read version 4                    Read version 4
Change status to CONFIRMED        Change status to CANCELLED
Save changes                      Save changes
Write CONFIRMED                   Write CANCELLED
~~~

If the UPDATE statement relies solely on the ID, request B can overwrite A's result. The application does not realize that the data B relied on was stale.

Optimistic locking adds a version condition to the write operation:

~~~sql
UPDATE sales_orders
SET status = :newStatus,
    version = :nextVersion
WHERE id = :id
  AND version = :expectedVersion;
~~~

If request A has already changed the version from 4 to 5, request B's UPDATE with `expectedVersion = 4` matches zero rows. Spring Data JDBC sees that no row was updated and reports an optimistic locking conflict.

## 2. Meaning of @Version

`@Version` belongs to the `org.springframework.data.annotation` package:

~~~java
import org.springframework.data.annotation.Version;
~~~

Place the annotation on a version property of the **aggregate root**:

~~~java
@Version
private Long version;
~~~

This property serves as a token identifying the aggregate version that the application read. Spring Data JDBC manages the version value during inserts and updates. The application should not manually increment or assign the version inside business logic.

Key points to remember:

- The version is stored in a column on the aggregate root table.
- When creating a new aggregate, the framework initializes the version according to Spring Data JDBC rules (typically starting at 0).
- After each successful update, the version is incremented.
- When updating a previously read aggregate, the framework writes only if the database version still matches.
- If no row matches both the ID and the expected version, the operation fails with an optimistic locking error.

The default column name is usually `version`. You can use `@Column` if the schema uses a different name.

## 3. Placing @Version on the aggregate root

Example Order entity:

~~~java
package com.example.sales.order;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String status;

    @Version
    private Long version;

    protected Order() {
        // Required for Spring Data JDBC.
    }

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public Long getVersion() {
        return version;
    }

    public void confirm() {
        if (!"DRAFT".equals(status)) {
            throw new IllegalStateException(
                "Only a draft order can be confirmed"
            );
        }
        this.status = "CONFIRMED";
    }

    public void cancel() {
        if ("CONFIRMED".equals(status)) {
            throw new IllegalStateException(
                "A confirmed order cannot be cancelled here"
            );
        }
        this.status = "CANCELLED";
    }
}
~~~

`version` is persistence metadata used by Spring Data JDBC for concurrency control. Domain methods `confirm()` and `cancel()` do not alter the version; they only change business state.

### Database schema

~~~sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    version BIGINT NOT NULL
);
~~~

If the table already contains data, add the column via migration with an initial value:

~~~sql
ALTER TABLE sales_orders
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
~~~

The column type must be compatible with the chosen Java type. For large schemas or specific databases, choose a safe migration strategy to add the column.

## 4. How does the version change?

### When inserting a new aggregate

~~~java
Order order = new Order(101L);
Order saved = orderRepository.save(order);

System.out.println(saved.getId());
System.out.println(saved.getVersion());
~~~

For a new entity, Spring Data JDBC initializes the version according to the framework's optimistic locking mechanism. Typically, the first version is 0. Do not manually set an arbitrary version number in a constructor or controller.

### When updating an existing aggregate

~~~java
Order order = orderRepository.findById(501L)
    .orElseThrow();

System.out.println(order.getVersion()); // e.g.: 4

order.confirm();
Order saved = orderRepository.save(order);

System.out.println(saved.getVersion()); // e.g.: 5
~~~

On a successful save, the framework checks the old version and writes the next version. The value of `saved.getVersion()` reflects the new version produced by the save operation.

Logically, the update operation corresponds to:

~~~sql
UPDATE sales_orders
SET status = 'CONFIRMED',
    version = 5
WHERE id = 501
  AND version = 4;
~~~

This SQL illustrates the compare-and-set mechanism; the actual SQL is generated by Spring Data JDBC and may differ in placeholders, column lists, or how the version is bound depending on the framework version and dialect.

## 5. Two transactions updating the same aggregate concurrently

Suppose two transactions both read Order #501 at version 4:

~~~mermaid
sequenceDiagram
    participant A as Transaction A
    participant B as Transaction B
    participant DB as Database
    A->>DB: SELECT Order #501, version 4
    B->>DB: SELECT Order #501, version 4
    A->>DB: UPDATE ... WHERE id=501 AND version=4
    DB-->>A: 1 row updated, version becomes 5
    B->>DB: UPDATE ... WHERE id=501 AND version=4
    DB-->>B: 0 rows updated
    B-->>B: Optimistic locking failure
~~~

Outcome:

1. A reads version 4 and saves successfully. The database transitions the version to 5.
2. B still holds an object with version 4.
3. B saves with the condition version 4.
4. The database finds no row having both ID 501 and version 4.
5. Spring Data JDBC throws an optimistic locking error instead of silently overwriting A's change.

Optimistic locking does not prevent A and B from reading concurrently. It detects conflicts at write time.

## 6. Repository and application service

The repository remains a standard CRUD interface:

~~~java
package com.example.sales.order;

import org.springframework.data.repository.CrudRepository;

public interface OrderRepository
        extends CrudRepository<Order, Long> {
}
~~~

The service loads the aggregate, applies domain behavior, and saves:

~~~java
package com.example.sales.order;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final OrderRepository orders;

    public OrderService(OrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public Order confirm(Long orderId) {
        Order order = orders.findById(orderId)
            .orElseThrow(() -> new IllegalArgumentException(
                "Order not found: " + orderId
            ));

        order.confirm();
        return orders.save(order);
    }
}
~~~

There is no need to read the version manually, build the UPDATE statement manually, or increment the version in Java. When a property is annotated with `@Version`, Spring Data JDBC integrates version checking into the aggregate persistence workflow.

`@Transactional` defines the boundary for the read–modify–save use case. Optimistic locking still relies on the version condition in the write operation; the transaction ensures that database changes belonging to the same use case commit or roll back consistently.

## 7. How are optimistic locking errors represented?

When the version no longer matches, Spring Data JDBC raises an error from Spring's data access exception hierarchy, typically `OptimisticLockingFailureException` (`org.springframework.dao`).

It can be handled at the application/API boundary:

~~~java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(OptimisticLockingFailureException.class)
    @ResponseStatus(HttpStatus.CONFLICT)
    public ApiError handleOptimisticLocking(
            OptimisticLockingFailureException exception) {
        return new ApiError(
            "ORDER_CHANGED",
            "Order was changed by another request. Reload and try again."
        );
    }
}

public record ApiError(String code, String message) {}
~~~

HTTP 409 Conflict is appropriate when the client needs to reload the data and reconsider its action. Do not return stack traces or internal SQL details to the client.

The specific exception type may be wrapped in a higher-level exception depending on the call path and framework version; API-level handling should catch the appropriate Spring DAO abstraction.

## 8. What should the client do on a conflict?

Upon receiving a conflict, the client can:

1. Reload the latest aggregate.
2. Display the new data and notify the user that changes occurred elsewhere.
3. Let the user review the operation they intended to perform.
4. Resubmit the command after the user confirms, if the operation is still valid.

Do not automatically resend the stale object with the same version. Doing so only repeats the conflict because the underlying data has not changed.

If the server wants to retry, it must reload the aggregate, re-evaluate business rules, and reapply the **command** onto the new state. Automatically retry only when the operation is safe, bounded in attempts, and guaranteed not to duplicate side effects.

Example:

~~~java
// Avoid: keeping the stale object and retrying save.
orders.save(staleOrder);

// When retry is allowed by business rules:
Order latest = orders.findById(orderId).orElseThrow();
latest.confirm(); // re-check current state
Order saved = orders.save(latest);
~~~

The second snippet only illustrates reloading and reapplying behavior. If the new state no longer allows confirming, the domain method must reject it.

## 9. What scope does @Version on the aggregate root protect?

Spring Data JDBC manages data by aggregate root. Therefore, the version is placed on the root to protect updating the aggregate as a unit.

Suppose an Order consists of:

~~~text
Order (root, version = 4)
├── OrderItem #1
├── OrderItem #2
└── OrderItem #3
~~~

When two requests both load the Order and modify components belonging to it, the version on the root detects that one request saved the aggregate earlier. This matters even when the change is in a child collection.

There is no need to place a separate `@Version` on each `OrderItem` merely to protect changes within the Order aggregate. Spring Data JDBC does not treat each child component as an independent aggregate root simply because it is stored in a separate table.

### Other aggregates do not automatically share a version

If Order only stores `customerId` to reference another Customer aggregate, modifying Customer does not automatically increment Order's version. The two aggregates have separate lifecycles and concurrency tokens.

~~~text
Order (version = 4) ---- customerId ----> Customer (version = 9)
~~~

Saving Order does not imply checking Customer's version. If a use case needs to keep data from two aggregates consistent with each other, design dedicated transaction and coordination rules; do not assume a single `@Version` protects all tables linked by foreign keys.

## 10. Optimistic locking and child collection changes

Spring Data JDBC persists an aggregate according to the mapping of the root and its child components. A single save may update the root row and modify collection rows. The version on the root helps detect two concurrent saves on the same aggregate.

For example, two requests both load Order at version 2:

- Request A adds an OrderItem and saves successfully; the root version becomes 3.
- Request B removes an OrderItem on the version 2 snapshot and saves.
- The root version check detects that the version is already 3; B receives a conflict.

Without a version on the root, two collection writes can lead to lost changes depending on the persistence strategy and execution order.

Transactions are critical: if part of the aggregate write already executed before the conflict is detected, the transaction must roll back so no partial write state remains. Use the transaction manager matching Spring Data JDBC's `DataSource`.

## 11. @Version is not pessimistic locking

The two mechanisms handle contention differently:

| Criterion | Optimistic locking (`@Version`) | Pessimistic locking |
|---|---|---|
| On read | Does not lock rows to reserve update rights | Can acquire a database lock immediately on read |
| On conflict | Detected at write time and raises an error | Other requests may have to wait for the lock |
| Best suited for | Low contention, read-heavy workloads | Frequent conflicts or required serialization |
| Impact | Holds no locks while the user edits | Can hold locks during the transaction |
| Mechanism | Version comparison | Database-managed locks |

Optimistic locking generally fits short web requests: load data, user edits, submit update later. Pessimistic locking can fit workflows that must hold a resource within a short transaction with high contention risk.

`@Version` does not automatically issue `SELECT ... FOR UPDATE`. If business requirements call for a pessimistic lock, design appropriate queries/transactions and locking mechanisms for your database rather than expecting the version annotation to lock rows.

## 12. Other write paths must respect the version

Spring Data JDBC optimistic locking can only detect changes when writers update the version according to the same convention.

Suppose another task uses `JdbcTemplate` to update directly:

~~~sql
UPDATE sales_orders
SET status = :status
WHERE id = :id;
~~~

If the statement does not increment the version, a stale entity in the Spring Data JDBC application can still carry the current database version and overwrite the other task's data without detecting a conflict.

A custom update statement must perform compare-and-set itself:

~~~sql
UPDATE sales_orders
SET status = :newStatus,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
~~~

The application checks the affected row count:

- 1 row: update succeeded.
- 0 rows: version mismatch or row does not exist; determine the appropriate business outcome.

Any batch job, script, external application, or custom SQL writing to the aggregate must obey the version rule to share optimistic locking guarantees. If any writer bypasses the version, the mechanism no longer provides full protection against that writer.

## 13. Version differs from updatedAt and audit history

Do not use version in place of an update timestamp or change history:

| Property | Purpose |
|---|---|
| `version` with `@Version` | Detects updates based on a stale snapshot |
| `updatedAt` | Records the time of the most recent update |
| Audit log | Stores who changed what and when |
| Event history | Stores business events over time |

A version is usually an incrementing number, not a timestamp. It does not tell you who changed the aggregate, which field changed, or what the previous state was.

You can combine `@Version` with auditing metadata such as `@LastModifiedDate` if the application needs both. The two mechanisms solve different needs.

## 14. Common mistakes

| Mistake | Consequence | Fix |
|---|---|---|
| Forgetting `@Version` on the root | Concurrent updates can overwrite each other | Add a version property and schema column |
| Placing version on a child expecting it to protect the whole aggregate | Does not reflect the right concurrency boundary | Place version on the aggregate root |
| Manually incrementing version in a domain method | Framework may compare the wrong snapshot or increment incorrectly | Let Spring Data JDBC manage it |
| Not migrating the version column for existing data | Inserts/updates fail due to missing column or NULL | Add a compatible column and initialize versions |
| Catching the exception and ignoring it | Client believes update succeeded | Return conflict or perform controlled retry |
| Repeatedly retrying the same stale object | Repeats the conflict | Reload the aggregate and re-evaluate the command |
| Assuming `@Transactional` prevents all race conditions | Lost updates can still occur without a version check | Use `@Version` or an appropriate lock |
| Thinking `@Version` locks rows on read | Misunderstands the mechanism and lock duration | It is an optimistic check at write time |
| Custom SQL not incrementing version | Other writers can break the guarantee | Include the version predicate and increment the version |
| Confusing version with audit timestamp | Missing business history | Use dedicated auditing/audit logs |
| Thinking Order's version protects Customer | Cross-aggregate conflicts go undetected | Each aggregate has its own concurrency policy |

4. Load the Order, change its status, save it again, and verify that the version increments after a successful update.

12. Compare optimistic locking with a transaction using a pessimistic row lock; note wait times and behavior when two requests access the row concurrently.

## 16. Key takeaways

`@Version` on the aggregate root provides optimistic locking for Spring Data JDBC. The framework stores a version token, increments it after each successful update, and writes only when the version in the database still matches the version the aggregate read. When another request has updated earlier, the later operation receives an optimistic locking error instead of silently overwriting newer data.

Place the version on the root to protect changes belonging to the aggregate, let the framework manage the value, and handle conflicts at the application/API boundary. Optimistic locking does not lock rows during reads, does not automatically protect other aggregates referenced by ID, and cannot detect writers that bypass the version. Every write path must follow compare-and-increment if you want to preserve protection against lost updates.
