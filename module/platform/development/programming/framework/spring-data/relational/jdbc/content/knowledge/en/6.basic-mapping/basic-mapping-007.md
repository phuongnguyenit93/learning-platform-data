# Quoting, Case Sensitivity, and SQL Keyword Collisions

In **Spring Data Relational JDBC**, a Java entity maps to database tables and columns. Mapping seems straightforward until errors arise from uppercase table names, columns created with double quotes, or names colliding with SQL keywords such as `order` or `select`. These failures can occur even when the table exists and all entity field types are completely valid.

To handle them, you need to understand three related but distinct concepts:

1. **Identifier:** the name of a table, column, schema, sequence, or alias; for example, `customer_order`, `created_at`.
2. **Identifier quoting:** wrapping an identifier in the quote syntax understood by the database engine, such as PostgreSQL using `"Order"` to refer specifically to the table named `Order`.
3. **Case sensitivity and keywords:** databases may normalize unquoted names; when quoted, they usually preserve exact casing. A name that collides with a keyword may require quoting to be accepted.

Quoting here means **quoting SQL identifiers**, which is different from single quotes wrapping string literals, and different from binding parameters with `PreparedStatement`.

## 1. Distinguishing Identifiers, String Literals, and Parameters

Consider a PostgreSQL query:

```sql
SELECT id, customer_name
FROM customer_order
WHERE customer_name = 'An';
```

| Element | Meaning | Related Rule |
| --- | --- | --- |
| `customer_order` | Table identifier | May be case-folded according to database rules if unquoted |
| `id`, `customer_name` | Column identifiers | Must match the names stored/resolved by the database |
| `'An'` | String literal | Single quotes denote a **value**, not a column name |
| `?` in JDBC | Parameter binding placeholder | Cannot stand in for a table name or column name |
| `"Order"` in PostgreSQL | Quoted identifier | Preserves exact casing and allows certain special names |

With JDBC, the safe way to pass values is:

```java
String sql = "SELECT id FROM customer_order WHERE customer_name = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, customerName);
    try (ResultSet result = statement.executeQuery()) {
        // Read results here.
    }
}
```

Never write `WHERE customer_name = "An"` to compare strings in PostgreSQL: `"An"` is a *column name*, not the value `'An'`. If a column name is a keyword, you quote the **identifier** in SQL; if data comes from user input, you **bind the value** as a parameter. The two techniques solve two different problems.

## 2. Case Sensitivity: Why Does SQL Report a Table Missing When It Exists?

Not every database engine handles identifiers the same way:

- **PostgreSQL** folds **unquoted** identifiers to lowercase. Unquoted `CustomerOrder`, `CUSTOMERORDER`, and `customerorder` all resolve to the same name `customerorder`. **Quoted** identifiers are preserved verbatim; for example, `"CustomerOrder"` differs from `"customerorder"`.
- **Oracle Database** typically normalizes **unquoted** identifiers to uppercase. Once quoted, the name is stored and referenced with exact casing.
- **MySQL/MariaDB** has different rules for table names vs. column names. Case sensitivity for database/table names also depends on the operating system, `lower_case_table_names`, and storage engine; you cannot apply PostgreSQL rules to every MySQL installation.
- **H2** has compatibility modes and identifier-normalization settings. Passing tests on H2 does not prove table/column names will behave identically on PostgreSQL.

### 2.1. Experimenting with PostgreSQL

When creating an unquoted table:

```sql
CREATE TABLE customer_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

-- All reference the same customer_order table:
SELECT id FROM customer_order;
SELECT id FROM CUSTOMER_ORDER;
SELECT id FROM "customer_order";

-- Different name: PostgreSQL looks for the exact uppercase table.
SELECT id FROM "CUSTOMER_ORDER";
```

If the schema only contains `customer_order`, the last query fails with an error like `relation "CUSTOMER_ORDER" does not exist`. Double quotes prevent PostgreSQL from folding the name to lowercase.

Conversely, when creating a table with quoted uppercase letters:

```sql
CREATE TABLE "CustomerOrder" (
    "Id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "CustomerName" VARCHAR(100) NOT NULL
);

-- Correct: matches the exact quoted names.
SELECT "Id", "CustomerName" FROM "CustomerOrder";

-- Wrong for the table just created: unquoted identifiers fold to lowercase.
SELECT Id, CustomerName FROM CustomerOrder;
```

Two tables `customer_order` and `"CustomerOrder"` can coexist because their actual stored names differ. When designing a new schema, using uniform names like `customer_order` and `customer_name` significantly reduces confusion across hand-written SQL, migrations, and database tools.

### 2.2. Quote Syntax Also Depends on Dialect

| Database Engine | Common Quoted Identifier Syntax | Example |
| --- | --- | --- |
| PostgreSQL | Double quotes `"..."` | `"Order"`, `"CustomerName"` |
| Oracle Database | Double quotes `"..."` | `"Order"` |
| H2 (standard SQL mode) | Double quotes `"..."` | `"Order"` |
| MySQL/MariaDB | Backticks | `` `order` `` |
| SQL Server | Square brackets; also supports double quotes when configured | `[Order]` |

Do not assume every driver and database uses `"..."`. MySQL can support double quotes for identifiers when `ANSI_QUOTES` is enabled, but by default uses backticks. SQL Server has the `QUOTED_IDENTIFIER` setting governing double quotes. When writing native SQL, follow your actual dialect.

**Quoting is not a SQL injection defense for the whole query.** Dynamic table/column names still require strict validation; `?` placeholders only bind **values**.

## 3. Names Colliding with SQL Keywords

SQL reserves words used as language syntax, such as `SELECT`, `ORDER`, `GROUP`, and `FROM`. When used as table or column names, the parser may fail to recognize them as identifiers unless quoted.

The following PostgreSQL example **intentionally** creates inconveniently named tables and columns:

```sql
CREATE TABLE "order" (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "select" VARCHAR(100) NOT NULL
);

INSERT INTO "order" ("select") VALUES ('draft');

SELECT id, "select"
FROM "order"
WHERE "select" = 'draft';
```

Statements like `FROM order` and `SELECT select FROM ...` can cause syntax errors because `order` and `select` are parsed as keywords. Quoting is required consistently across DDL, native queries, migrations, and any SQL-generating tools.

However, **keyword lists are not identical across database engines or versions**. A name that is valid in one database may need quoting in another. The most reliable safeguard for new schemas is:

- Name tables with clear descriptive nouns: `customer_order` instead of `order`, `application_user` instead of `user` where collision risks exist.
- Name columns specifically: `selected_option` instead of `select`, `sort_order` instead of `order`.
- Use lowercase + underscores (`snake_case`), avoiding spaces or special characters in SQL names unless legacy schema compatibility requires them.
- Keep naming conventions aligned across migrations, entities, manual queries, and reporting/export tools.

## 4. How Does Spring Data JDBC Choose Table and Column Names?

Spring Data JDBC maps entities using metadata. It can derive or read names from:

1. Framework naming conventions, via `NamingStrategy`.
2. `@Table` on the entity type and `@Column` on properties.
3. Special relationship configurations, such as `@MappedCollection(idColumn = ..., keyColumn = ...)`.

The default `NamingStrategy` converts camel-case class/property names into underscore-separated names. The Spring Data Relational documentation illustrates `SavingsAccount` → `SAVINGS_ACCOUNT` and `firstName` → `FIRST_NAME`. When the schema uses different names, do not guess from Java names: declare SQL names explicitly.

PostgreSQL example with keyword-safe names:

```sql
CREATE TABLE customer_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    placed_on DATE NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL
);
```

Mapping with Spring Data JDBC:

```java
import java.math.BigDecimal;
import java.time.LocalDate;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer_order")
public record CustomerOrder(
        @Id Long id,
        @Column("placed_on") LocalDate placedOn,
        @Column("total_amount") BigDecimal totalAmount
) {}
```

Repository:

```java
import org.springframework.data.repository.CrudRepository;

public interface CustomerOrderRepository
        extends CrudRepository<CustomerOrder, Long> {}
```

Here `@Table("customer_order")` specifies the real table name, and `@Column("placed_on")` and `@Column("total_amount")` specify the column names. When the framework generates SQL, it uses this metadata to choose identifiers. `@Id` identifies the primary key; it **does not** rename tables. The schema must already exist (e.g., via Flyway/Liquibase or an appropriate script); Spring Data JDBC does not auto-create tables from entities.

### 4.1. Default Quoting in Spring Data JDBC

In modern Spring Data JDBC versions in the Spring Data Relational 3.x line, **table and column names in generated SQL are typically quoted by default**. The framework uses the **mapping context** and **SQL dialect** configuration to render identifiers. This has two consequences:

- Quoted names handle identifiers that collide with keywords or need exact casing, provided the metadata names match the database names.
- Because quoted names can be case-sensitive, metadata `CUSTOMER_ORDER` may **not** match an unquoted `customer_order` table in PostgreSQL.

In the 3.x line, `RelationalMappingContext.setForceQuote(false)` allows adjusting quoting globally. Do not disable quoting just to make one table happen to query cleanly: that change also affects other tables and columns, especially keyword names or mixed-case schemas. When customizing, check your Spring Data version, actual mapping context, and generated SQL.

In the Spring Data Relational 4.x API, `JdbcMappingContext` provides factory/configuration options for quoted vs. plain identifiers such as `forQuotedIdentifiers()` and `forPlainIdentifiers()`. Configuration API names can vary across versions; do not copy configuration snippets from one major line's docs into an older project without verifying.

> Important rule: **`@Table` and `@Column` declare logical names, while which quote characters are emitted is decided by mapping/dialect.** When quoting is enabled, write `@Table("Order")`, not manual SQL quotes inside the annotation string like `@Table("\"Order\"")`; the latter can cause the quote characters to be treated as part of the identifier name itself.

### 4.2. Mapping a Legacy Schema with Uppercase and Keyword Names

Suppose an existing PostgreSQL schema cannot be altered:

```sql
CREATE TABLE "Order" (
    "Id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Select" VARCHAR(100) NOT NULL
);
```

Corresponding entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("Order")
public record LegacyOrder(
        @Id @Column("Id") Long id,
        @Column("Select") String selectedValue
) {}
```

With a quoting-enabled mapping context and the PostgreSQL dialect, identifiers are rendered similarly to `"Order"`, `"Id"`, and `"Select"` to match the schema. Inside the annotation, `"Order"` is a **Java string containing Order**, not pre-quoted SQL.

If the database actually stores `"ORDER"`, `"order"`, or unquoted `order`, those can all be **distinct names**. Always map to the exact name in the database catalog, not what looks equivalent to the human eye ignoring case.

### 4.3. Relationship Column Names Can Also Be Affected

If an aggregate contains collections or references managed by Spring Data JDBC, the framework may require foreign-key and ordering/map-key columns. Their names are governed by conventions, `NamingStrategy`, and `@MappedCollection`.

Example:

```java
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer_order")
public record OrderAggregate(
        @Id Long id,
        @MappedCollection(
                idColumn = "order_id",
                keyColumn = "position_index")
        List<OrderLine> lines
) {}

@Table("order_line")
public record OrderLine(String sku, int quantity) {}
```

In Spring Data JDBC's `List` model, the child table requires the back-reference column `order_id` and the index column `position_index`; actual names must match both the mapping declarations and the DDL. This is an example of **relationship column naming**, not per-collection quote configuration. Adjusting only the aggregate's `@Table` while leaving back-reference columns with mismatched names can still cause missing-column errors.

## 5. Generated SQL and Hand-Written SQL Are Not the Same

Repositories such as `CrudRepository.save` and `findById` generate SQL from Spring Data JDBC metadata. When writing `@Query`, `JdbcTemplate`, or `NamedParameterJdbcTemplate`, **you are responsible for identifier syntax in the SQL you write**.

Spring Data JDBC repository example on PostgreSQL:

```java
import java.util.Optional;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

interface LegacyOrderRepository extends CrudRepository<LegacyOrder, Long> {

    @Query("""
        SELECT "Id", "Select"
        FROM "Order"
        WHERE "Id" = :id
        """)
    Optional<LegacyOrder> findManually(@Param("id") Long id);
}
```

Here:

- `"Id"`, `"Select"`, and `"Order"` are PostgreSQL identifiers that must be quoted to match the table and columns.
- `:id` is a **named parameter** processed by Spring Data, not an identifier and not usable in place of a column name.
- Double quotes inside the Java text block are SQL characters that must be preserved, not stripped.
- This query relies on PostgreSQL syntax; when switching to another database, native SQL must be reviewed for that dialect.

With `JdbcTemplate`, the same idea applies:

```java
String sql = "SELECT \"Select\" FROM \"Order\" WHERE \"Id\" = ?";
String selected = jdbcTemplate.queryForObject(
        sql, String.class, orderId);
```

`queryForObject` expects **exactly one row and one column** to map directly to `String`. If zero rows, multiple rows, or multiple `SELECT` columns are returned, it can throw an exception. For optional results, use `query(...)` or a repository returning `Optional` as designed.

## 6. Do Not Confuse Aliases, Real Column Names, and Java Property Names

In hand-written SQL, an alias changes **the column label in the query result**:

```sql
SELECT "Select" AS selected_value
FROM "Order";
```

The alias `selected_value` does not rename the real `"Select"` column in the table. With a hand-written `RowMapper`, read the matching label from `ResultSet`:

```java
String sql = "SELECT \"Select\" AS selected_value FROM \"Order\"";
List<String> values = jdbcTemplate.query(
        sql, (rs, rowNum) -> rs.getString("selected_value"));
```

When using Spring Data JDBC `@Query` to map into an entity, column labels need to match what the mapper expects from metadata. With custom SQL using aliases that differ from mapped column names, values may not populate properties as intended. Do not assume arbitrary aliases automatically match Java property names.

When writing SQL with `JOIN`s across multiple tables sharing an `id` column, give explicit aliases when mapping DTOs manually. Distinguish:

- `@Column("Select")`: the entity's SQL column name.
- `String selectedValue`: the Java property name.
- `AS selected_value`: the returned column label of a specific SQL query.

These three names are connected via mapping, not freely interchangeable.

## 7. Quoting and Security When Building Dynamic SQL

`PreparedStatement` protects **value** passing; `?` cannot be used in place of table names, column names, schema names, or sort directions.

Example of an **incorrect** attempt to parameterize a sort column:

```java
// Does not turn ? into a SQL column name.
String sql = "SELECT * FROM customer_order ORDER BY ?";
```

Even if you bind `"placed_on"`, the database receives it as a **string value**, not the identifier `placed_on`. Nor may you concatenate user-supplied column names directly:

```java
// Unsafe: userInputSortColumn comes from external input.
String sql = "SELECT * FROM customer_order ORDER BY " + userInputSortColumn;
```

If users may choose a sort column, **map valid choices onto a fixed set of application-owned identifiers**:

```java
String sortColumn = switch (sortKey) {
    case "date" -> "placed_on";
    case "total" -> "total_amount";
    default -> throw new IllegalArgumentException("Unsupported sort key");
};

String sql = """
    SELECT id, placed_on, total_amount
    FROM customer_order
    ORDER BY """ + sortColumn;
```

If `ASC`/`DESC` selection is allowed, whitelist that as well. In Spring Data JDBC, you can leverage repository sorting APIs where appropriate, while still validating which properties external callers are permitted to request. **Quoting does not make arbitrary concatenated SQL safe.**

## 8. When Migrating Databases or Existing Schemas

For new schemas, keep conventions simple: `lower_snake_case` for tables and columns, no spaces, no SQL keywords, and uniform rules across DDL and `@Table`/`@Column`. For legacy schemas that already use quoted/camel-case names, pick one of two clear paths:

| Approach | When Suitable | Trade-offs |
| --- | --- | --- |
| Keep the schema and configure exact mapping/quoting | Other consumers share the DB; tables/columns cannot be renamed yet | Must maintain exact casing and quoting in every manual SQL query |
| Migration to standardized names | You own the schema and have deployment runway | Must update queries, views, stored procedures, reports, other services, and entity mappings |

**Illustrative** PostgreSQL migration from quoted names:

```sql
-- Assuming impact on dependent objects has been verified.
ALTER TABLE "Order" RENAME TO customer_order;
ALTER TABLE customer_order RENAME COLUMN "Id" TO id;
ALTER TABLE customer_order RENAME COLUMN "Select" TO selected_value;
```

After migrating, update the entity from `@Table("Order")` to `@Table("customer_order")` and from `@Column("Select")` to `@Column("selected_value")`. Migrations must be version-controlled and coordinated with clients and schema dependencies; the snippet only shows syntax, not a safe rollout plan for a live production dataset.

When switching databases from PostgreSQL to MySQL, test **real schema DDL, migrations, and repositories** on the target database. H2 tests with compatibility modes are useful during development, not a substitute for integration tests against the production database engine.

## 9. How to Investigate Table or Column Name Errors

Common errors:

| Symptom | Possible Cause | How to Verify |
| --- | --- | --- |
| PostgreSQL: `relation "CUSTOMER_ORDER" does not exist` | Mapping uses quoted uppercase identifier while real table is `customer_order` | Compare catalog table names with `@Table`/`NamingStrategy` |
| PostgreSQL: `column "Select" does not exist` | Real column has different casing or query alias differs | Check column names in schema, `@Column`, and rendered SQL |
| `syntax error at or near "order"` | `order` used unquoted as a table name | Rename the table or apply dialect-appropriate quoting |
| `BadSqlGrammarException` | Generated or hand-written SQL fails DB name/syntax checks | Inspect SQL, underlying `SQLException`, SQLState, and dialect |
| Query works in `psql` but fails in repository | `psql` query is unquoted while repository uses quoting or a different `NamingStrategy` | Compare verbatim SQL and actual catalog identifiers |
| H2 tests pass but prod PostgreSQL fails | Different case-folding, quoting, or reserved keyword rules | Reproduce on PostgreSQL with the same schema |
| Custom `@Query` returns unexpected data | Alias mismatches mapping or single/double quotes confused | Check returned column labels and mapper/DTO |

### 9.1. Inspecting Real Names in PostgreSQL Metadata

To inspect tables and columns in the `public` schema:

```sql
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name ILIKE '%order%';

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'Order'
ORDER BY ordinal_position;
```

The filter `table_name = 'Order'` in the metadata query is a **string value comparison**, so it uses single quotes. That differs from `SELECT ... FROM "Order"`, where `"Order"` is an identifier. When the real table name is `customer_order`, adjust the string literal in the metadata query accordingly.

In the PostgreSQL CLI, `\dt` and `\d "Order"` are also handy for inspection, though they are `psql` meta-commands, **not standard SQL to run via JDBC**.

### 9.2. Reading Failing SQL Character by Character

When debugging, determine:

1. What table/column names are defined in migrations/DDL, and are they quoted or unquoted?
2. What names are mapped via `@Table`, `@Column`, and `NamingStrategy`?
3. Does Spring Data JDBC render quoted identifiers? What dialect/version is active?
4. Did the SQL come from an auto-generated repository operation or hand-written `@Query`/`JdbcTemplate`?
5. Does a `SELECT` use an alias that differs from the column label the mapper expects?

You can enable SQL logging in development in a controlled manner to inspect the exact table and column names the application sends. Avoid logging sensitive parameter values or leaving overly verbose logging on in production. When a SQL error occurs, read the underlying cause exception and SQLState rather than only Spring's wrapper message.

## 11. Technical Conclusion

For reliable Spring Data JDBC mapping, cross-check **actual database identifiers**, **names declared in mapping metadata**, **database dialect quoting/case rules**, and **the SQL actually executed**. For new schemas, `lower_snake_case` without SQL keywords is the easiest convention to maintain. For legacy schemas, preserving exact casing and configuring quoting properly ensures repositories hit the right tables and columns. Quoting identifiers and binding parameter values are two distinct tools; using both correctly prevents mapping errors and unsafe SQL concatenation.
