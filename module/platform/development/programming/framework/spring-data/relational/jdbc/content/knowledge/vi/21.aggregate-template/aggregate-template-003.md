# Phân biệt save, insert và update tường minh

Trong **Spring Data Relational JDBC**, một aggregate root có thể được lưu bằng repository hoặc bằng `JdbcAggregateTemplate`. Các API thường gặp là `save`, `insert` và `update`. Chúng đều lưu aggregate, bao gồm các entity con thuộc aggregate, nhưng khác nhau ở cách quyết định thao tác SQL.

- **`save`** tự xác định aggregate đang mới hay đã tồn tại, sau đó chọn insert hoặc update.
- **`insert`** yêu cầu thực hiện thao tác tạo mới, không kiểm tra trạng thái new của entity.
- **`update`** yêu cầu thực hiện thao tác cập nhật aggregate đã tồn tại, không kiểm tra trạng thái new của entity.

Repository thường cung cấp `save`. Khi cần nói rõ ý định insert/update, Spring Data JDBC cung cấp `JdbcAggregateTemplate` với cả ba phương thức. Chọn đúng API giúp tránh insert trùng khóa, update nhầm một aggregate mới hoặc phụ thuộc sai vào cách Spring nhận diện ID.

## 1. Ba thao tác ở mức aggregate

Giả sử ứng dụng quản lý đơn hàng:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── status
  └── lines (owned child collection)
        ├── OrderLine
        └── OrderLine
```

Một model Java dùng xuyên suốt bài:

```java
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_no")
        List<OrderLine> lines
) {
    public static PurchaseOrder draft(String orderNumber) {
        return new PurchaseOrder(
                null, null, orderNumber, "DRAFT", List.of());
    }

    public PurchaseOrder withStatus(String newStatus) {
        return new PurchaseOrder(
                id, version, orderNumber, newStatus, lines);
    }

    public PurchaseOrder withLines(List<OrderLine> newLines) {
        return new PurchaseOrder(
                id, version, orderNumber, status, newLines);
    }
}

public record OrderLine(String sku, int quantity) {}
```

Schema PostgreSQL tương ứng:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_line (
    purchase_order_id BIGINT NOT NULL
        REFERENCES purchase_order(id),
    line_no INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (purchase_order_id, line_no)
);
```

`PurchaseOrder` là aggregate root; `OrderLine` là các entity con thuộc vòng đời của đơn hàng. Khi lưu root, Spring Data JDBC lưu cả các thành phần thuộc aggregate theo mapping.

| API | Ý nghĩa | Cách chọn thao tác |
| --- | --- | --- |
| `CrudRepository.save(aggregate)` | Lưu aggregate | Spring Data kiểm tra aggregate mới hay cũ |
| `JdbcAggregateTemplate.save(aggregate)` | Lưu aggregate | Cùng semantics với repository `save` |
| `JdbcAggregateTemplate.insert(aggregate)` | Tạo aggregate mới | Luôn đi theo đường insert |
| `JdbcAggregateTemplate.update(aggregate)` | Cập nhật aggregate đã có | Luôn đi theo đường update |

Điểm quan trọng: các phương thức của `JdbcAggregateTemplate` không chỉ insert/update một hàng root. Chúng xử lý aggregate cùng các thành phần được tham chiếu bên trong nó.

## 2. save: tự quyết định insert hay update

`save` là lựa chọn thông thường khi ứng dụng muốn lưu một aggregate mà không tự quyết định trước nó là mới hay đã tồn tại.

Ví dụ với repository:

```java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

Tạo một đơn hàng mới:

```java
PurchaseOrder order = new PurchaseOrder(
        null,
        null,
        "PO-2026-211",
        "DRAFT",
        List.of(new OrderLine("SKU-CHAIR", 2))
);

PurchaseOrder saved = repository.save(order);
```

Nếu Spring Data xác định object là mới, repository insert hàng root rồi insert các entity con thuộc aggregate. Nếu object được xác định là đã tồn tại, repository cập nhật aggregate hiện hữu.

`save` không phải câu lệnh SQL kiểu `MERGE` hoặc `INSERT ... ON CONFLICT`. Việc chọn insert/update dựa trên **trạng thái new của object theo quy tắc Spring Data**, không phải một thao tác kiểm tra tồn tại nguyên tử ở database trước mỗi lần lưu.

### 2.1. Spring Data xác định entity mới như thế nào?

Spring Data sử dụng chiến lược nhận diện trạng thái new (entity state detection). Các quy tắc phổ biến:

1. Nếu entity có property `@Version`, Spring Data kiểm tra version trước. Version `null` (hoặc `0` với kiểu số nguyên primitive) cho biết entity mới; version đã có giá trị khác biểu thị entity hiện hữu.
2. Nếu không có version property, Spring Data kiểm tra `@Id`. ID `null` (hoặc `0` với kiểu primitive) được xem là mới; ID có giá trị được xem là đã tồn tại.
3. Nếu entity implement `Persistable`, Spring Data dùng kết quả `isNew()` do entity cung cấp để quyết định.

Quy tắc chi tiết phụ thuộc kiểu ID, version và phiên bản Spring Data. Khi dùng ID tự gán, không nên mặc định rằng ID có giá trị đồng nghĩa hàng đã có trong database nếu ứng dụng đang sử dụng version hoặc `Persistable` để kiểm soát trạng thái.

Ví dụ:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_no")
        List<OrderLine> lines
) {}
```

Với entity có `@Version Long version`, instance mới thường có `version == null`. Sau insert, Spring Data khởi tạo version; các lần lưu tiếp theo xem instance là đã tồn tại dựa trên version.

### 2.2. Vì sao trạng thái new phải đúng?

Giả sử ứng dụng tạo entity mới nhưng tự gán ID:

```java
PurchaseOrder order = new PurchaseOrder(
        9001L,
        null,
        "PO-9001",
        "DRAFT"
);

repository.save(order);
```

Nếu không có `@Version` và entity không tự điều khiển `Persistable.isNew()`, ID đã có thể khiến Spring Data xem entity là hiện hữu. Khi đó `save` chọn update, dù hàng `9001` chưa tồn tại. Đây là lý do API explicit insert hữu ích khi ứng dụng cấp ID trước khi ghi.

Ngược lại, nếu một entity đã tồn tại bị đánh dấu new không chính xác, `save` có thể đi theo đường insert và gặp lỗi khóa chính/unique constraint.

### 2.3. Dùng giá trị trả về từ save

Khi ID được database sinh, Spring Data nhận giá trị đó sau insert. Với object bất biến như Java record, framework có thể trả về instance chứa ID/version mới. Vì vậy hãy giữ kết quả:

```java
PurchaseOrder saved = repository.save(order);

Long generatedId = saved.id();
Long currentVersion = saved.version();
```

Không nên giả định mọi object đầu vào đều được thay đổi tại chỗ. Dùng giá trị trả về giúp code hoạt động đúng với cả entity mutable và immutable.

## 3. insert: chủ động tạo aggregate mới

`JdbcAggregateTemplate.insert(aggregate)` bỏ qua bước kiểm tra entity mới hay cũ và đi thẳng theo đường insert. Đây là lựa chọn phù hợp khi ứng dụng **biết chắc** aggregate chưa tồn tại và muốn thể hiện ý định tạo mới rõ ràng.

`JdbcAggregateTemplate` được Spring cấu hình như một bean khi ứng dụng bật Spring Data JDBC. Có thể inject nó vào service:

```java
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderWriter {

    private final JdbcAggregateTemplate template;

    public PurchaseOrderWriter(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional
    public PurchaseOrder create(PurchaseOrder order) {
        return template.insert(order);
    }
}
```

`insert` phù hợp trong các trường hợp:

- Ứng dụng cấp ID trước khi insert và ID đã được xác định là mới.
- Import dữ liệu có quy trình rõ ràng, mỗi aggregate trong lô phải được tạo mới.
- Muốn API thể hiện rõ rằng trùng khóa là lỗi, không phải ý định cập nhật.
- Muốn bỏ qua cơ chế nhận diện new dựa trên ID/version/`Persistable`.

Nếu database đã có hàng trùng primary key hoặc unique constraint, insert sẽ thất bại theo constraint của database. `insert` không tự chuyển thành update khi phát hiện trùng.

### 3.1. Insert bao gồm các entity con

Giả sử aggregate có collection `lines`. Khi insert root:

```text
template.insert(order)
        │
        ├── INSERT purchase_order
        │       └── nhận ID root
        │
        └── INSERT các order_line
                └── gắn purchase_order_id
```

SQL PostgreSQL minh họa:

```sql
INSERT INTO purchase_order (order_number, status, version)
VALUES ('PO-211', 'DRAFT', 0)
RETURNING id;

INSERT INTO order_line (purchase_order_id, line_no, sku, quantity)
VALUES (211, 0, 'SKU-CHAIR', 2);
```

Đây là SQL minh họa về ý nghĩa, không phải câu lệnh cố định được sinh trên mọi dialect. Cú pháp lấy ID, thứ tự câu lệnh và giá trị version do Spring Data JDBC, dialect và schema quyết định.

### 3.2. Insert với ID do ứng dụng cấp

Nếu ID được cấp trước, có thể dùng:

```java
PurchaseOrder order = new PurchaseOrder(
        9001L,
        null,
        "PO-9001",
        "DRAFT",
        List.of()
);

PurchaseOrder inserted = template.insert(order);
```

Trong trường hợp này, `insert` nói rõ rằng ID `9001` là của aggregate mới. Database vẫn kiểm tra primary key và các constraint khác. Nếu ID đã tồn tại, thao tác phải được xử lý như xung đột tạo mới.

## 4. update: chủ động cập nhật aggregate đã tồn tại

`JdbcAggregateTemplate.update(aggregate)` bỏ qua bước nhận diện new và đi thẳng theo đường update. Chỉ dùng khi ứng dụng biết aggregate root đã tồn tại.

Ví dụ:

```java
@Service
public class PurchaseOrderWriter {

    private final JdbcAggregateTemplate template;
    private final PurchaseOrderRepository repository;

    public PurchaseOrderWriter(
            JdbcAggregateTemplate template,
            PurchaseOrderRepository repository) {
        this.template = template;
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long id, String newStatus) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = new PurchaseOrder(
                current.id(),
                current.version(),
                current.orderNumber(),
                newStatus,
                current.lines()
        );

        return template.update(changed);
    }
}
```

Trong ví dụ, service tải aggregate hiện tại trước, giữ ID/version và các thành phần cần thiết, rồi gửi trạng thái đầy đủ cho `update`. Với entity có domain method, nên gọi method nghiệp vụ thay vì dựng object mới như ví dụ minh họa.

`update` phù hợp khi:

- Aggregate root đã tồn tại và cần được cập nhật.
- Quy trình import/synchronization đã xác định rõ các bản ghi đầu vào là bản ghi hiện hữu.
- Muốn coi trường hợp aggregate không tồn tại hoặc version không khớp là lỗi, thay vì tự chuyển sang insert.

Không dùng `update` cho một aggregate mới. Phương thức này không kiểm tra newness để tự đổi sang insert. Nếu root không tồn tại, thao tác update không thể tạo root thay cho insert; kết quả cụ thể được thể hiện qua semantics cập nhật và kiểm tra version của framework/database.

## 5. Update aggregate không đồng nghĩa chỉ chạy UPDATE cho một hàng

Trong Spring Data JDBC, update là thao tác đồng bộ trạng thái của **toàn aggregate**. Với aggregate có entity con được tham chiếu, quy trình cập nhật thông thường gồm:

1. Cập nhật hàng aggregate root.
2. Xóa các entity con đang được lưu bên trong aggregate.
3. Insert lại các entity con hiện có trong object được gửi vào.

Vì Spring Data JDBC không giữ persistence context để biết trạng thái trước đó của từng child, nó cần đưa database về trạng thái được biểu diễn bởi aggregate hiện tại. Do đó, ngay cả khi chỉ thay đổi status của root, các hàng child vẫn có thể bị xóa/chèn lại.

Ví dụ:

```text
Trước update:
PurchaseOrder #211
  status = DRAFT
  lines = [A, B]

Object gửi vào update:
PurchaseOrder #211
  status = CONFIRMED
  lines = [A, B]

Sau update:
PurchaseOrder #211
  status = CONFIRMED
  lines = [A, B]  (được đồng bộ lại theo aggregate)
```

Không nên thiết kế child thuộc aggregate như tài nguyên có ID được hệ thống khác tham chiếu ổn định nếu chúng có thể bị thay thế trong quá trình lưu root. Nếu một đối tượng có vòng đời độc lập, hãy xem xét tách nó thành aggregate riêng và tham chiếu bằng ID/`AggregateReference`.

## 6. So sánh save, insert và update

| Tiêu chí | `save` | `insert` | `update` |
| --- | --- | --- | --- |
| Có kiểm tra trạng thái new? | Có | Không | Không |
| Khi entity mới | Insert | Insert | Không phù hợp |
| Khi entity hiện hữu | Update | Không phù hợp; vẫn đi đường insert | Update |
| Cần biết trước trạng thái? | Không, framework xác định | Có, phải chắc chắn là mới | Có, phải chắc chắn đã tồn tại |
| Có lưu entity con thuộc aggregate? | Có | Có | Có |
| Có tự chuyển sang thao tác còn lại khi lỗi constraint? | Không | Không | Không |
| API thường dùng | Repository hoặc template | Template | Template |

Có thể ghi nhớ:

- **Không chắc trạng thái new và muốn Spring quyết định:** dùng `save`.
- **Chắc chắn tạo mới, kể cả ID đã được gán:** dùng `insert`.
- **Chắc chắn cập nhật aggregate hiện hữu:** dùng `update`.

`save` không phải một upsert nguyên tử ở database. Nếu nhiều tiến trình cùng kiểm tra một ID rồi lưu, việc nhận diện new trong Java không thay thế unique constraint, transaction và chiến lược xử lý cạnh tranh.

## 7. save, insert và update với @Version

Spring Data JDBC hỗ trợ optimistic locking qua property `@Version` trên aggregate root:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status
) {}
```

Khi cập nhật một aggregate có version, Spring Data kiểm tra version trong database có khớp version mà object mang theo không. Nếu một transaction khác đã cập nhật trước, thao tác hiện tại thất bại với `OptimisticLockingFailureException` thay vì âm thầm ghi đè.

SQL minh họa:

```sql
UPDATE purchase_order
SET status = ?, version = version + 1
WHERE id = ? AND version = ?;
```

Nếu không hàng nào khớp điều kiện ID/version, framework nhận diện xung đột optimistic locking. Câu SQL thực tế có thể khác theo dialect và cấu trúc aggregate.

Với insert, version được khởi tạo theo quy tắc Spring Data. Với update, version được kiểm tra và tăng. Dùng giá trị trả về từ `save`/`insert`/`update` để nhận instance với version mới, nhất là khi entity bất biến.

Nếu entity không có `@Version`, ứng dụng không có optimistic locking tự động cho aggregate theo cơ chế này. Explicit `update` không tự tạo bảo vệ cạnh tranh chỉ vì tên phương thức nói rõ ý định update.

## 8. Dùng save hay explicit insert/update trong service?

Ví dụ service dùng repository `save` cho luồng thông thường:

```java
@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder create(String orderNumber) {
        PurchaseOrder newOrder = PurchaseOrder.draft(orderNumber);
        return repository.save(newOrder);
    }

    @Transactional
    public PurchaseOrder confirm(Long id) {
        PurchaseOrder order = repository.findById(id)
                .orElseThrow();
        order.confirm();
        return repository.save(order);
    }
}
```

Đây là cách đơn giản và phù hợp khi new-state detection phản ánh đúng trạng thái của entity. Nếu use case cần ép buộc thao tác tạo mới hoặc cập nhật, dùng template:

```java
@Service
public class ExplicitPurchaseOrderService {

    private final JdbcAggregateTemplate template;
    private final PurchaseOrderRepository repository;

    public ExplicitPurchaseOrderService(
            JdbcAggregateTemplate template,
            PurchaseOrderRepository repository) {
        this.template = template;
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder insertNew(PurchaseOrder newOrder) {
        return template.insert(newOrder);
    }

    @Transactional
    public PurchaseOrder updateExisting(Long id, String status) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = current.withStatus(status);
        return template.update(changed);
    }
}
```

`draft` và `withStatus` trong ví dụ là factory/domain method giả định của class ứng dụng. Hãy thay bằng API thực tế của entity. Điều quan trọng là service chỉ gọi `insert` khi chắc chắn dữ liệu mới, và chỉ gọi `update` khi đã xác định aggregate hiện hữu.

## 9. Transaction và lỗi khi chọn sai thao tác

Lưu một aggregate có thể gồm nhiều câu SQL: insert/update root, xóa child cũ, insert child mới và cập nhật các thành phần liên quan. Khi nghiệp vụ cần các bước này thành công hoặc thất bại cùng nhau, hãy đặt transaction boundary ở service:

```java
@Transactional
public PurchaseOrder replaceOrderLines(
        Long orderId,
        List<OrderLine> newLines) {

    PurchaseOrder current = repository.findById(orderId)
            .orElseThrow();

    PurchaseOrder changed = current.withLines(newLines);
    return template.update(changed);
}
```

Transaction giúp các câu lệnh thuộc cùng transaction được commit/rollback cùng nhau. Nó không thay thế kiểm tra newness, khóa chính, version hoặc validation domain.

| Lỗi/tình huống | Nguyên nhân | Hướng xử lý |
| --- | --- | --- |
| Insert gặp duplicate key | ID hoặc giá trị unique đã tồn tại | Kiểm tra nguồn cấp ID và constraint; không đổi sang update một cách mù quáng |
| Update không áp dụng như mong đợi | Aggregate chưa tồn tại hoặc object không mang đúng ID | Kiểm tra tồn tại và đọc root trước khi update |
| Repository save chọn update cho object mới có ID gán sẵn | New-state detection mặc định xem ID đã có là hiện hữu (nếu không có version/Persistable override) | Dùng template insert hoặc cấu hình `Persistable.isNew()` đúng |
| Repository save chọn insert cho object đã tồn tại | Version/ID/`isNew()` báo trạng thái new sai | Sửa chiến lược new-state detection |
| Optimistic locking failure | Version của object đã cũ | Tải lại, xử lý xung đột và áp dụng lại thay đổi theo nghiệp vụ |
| Child bị mất sau update | Object gửi vào không chứa child cần giữ hoặc collection rỗng/null | Đọc aggregate đầy đủ và chỉ thay đổi child theo yêu cầu |
| Một phần aggregate được ghi khi thao tác thất bại | Nhiều lệnh không nằm trong transaction phù hợp | Đặt `@Transactional` ở service và dùng transaction manager đúng |

Đặc biệt, không tạo một aggregate object chỉ có ID và vài field rồi gọi `update` nếu các property khác chưa được tải/khôi phục. Với Spring Data JDBC, trạng thái aggregate được gửi vào là cơ sở để đồng bộ các thành phần thuộc aggregate.

## 10. save không đồng nghĩa với upsert

Trong SQL, **upsert** thường có nghĩa một câu lệnh database sẽ insert nếu khóa chưa tồn tại hoặc update nếu khóa đã tồn tại. `save` của repository không nhất thiết có semantics này:

- `save` dựa trên trạng thái new mà Spring Data xác định từ object.
- `save` có thể chọn insert dù database đã có cùng ID nếu object được đánh dấu new; khi đó constraint sẽ báo lỗi.
- `save` có thể chọn update cho một object có ID nhưng hàng thực tế không tồn tại.

Một số phiên bản `JdbcAggregateTemplate` cung cấp API `upsert` dựa trên native upsert của database. Đây là API riêng, yêu cầu ID được gán và dialect hỗ trợ; tài liệu hiện hành cũng nêu upsert chưa hỗ trợ optimistic locking. Hãy kiểm tra phiên bản Spring Data Relational và dialect của dự án trước khi sử dụng. Không thay `save` bằng `upsert` chỉ vì hai tên nghe gần giống nhau.

## 11. Các biến thể hàng loạt

`JdbcAggregateTemplate` cung cấp các phương thức xử lý `Iterable`:

| Phương thức | Ý nghĩa |
| --- | --- |
| `saveAll(aggregates)` | Lưu nhiều aggregate, nhận diện trạng thái new cho từng instance |
| `insertAll(aggregates)` | Insert nhiều aggregate đã xác định là mới |
| `updateAll(aggregates)` | Update nhiều aggregate đã xác định là hiện hữu |

Ví dụ:

```java
List<PurchaseOrder> inserted =
        template.insertAll(newOrders);

List<PurchaseOrder> updated =
        template.updateAll(existingOrders);
```

Các phương thức này không làm thay đổi nguyên tắc chọn thao tác: `insertAll` không biến thành update khi gặp ID trùng; `updateAll` không biến thành insert khi aggregate chưa tồn tại. Cần phân loại dữ liệu đầu vào trước khi gọi.

Đừng mặc định tên `All` đồng nghĩa với một câu SQL duy nhất hoặc bảo đảm mọi phần tử được ghi bằng cùng một batch JDBC trong mọi phiên bản/dialect. Hãy kiểm tra SQL và hành vi batch nếu hiệu năng là yêu cầu quan trọng.

## 12. Quy trình chọn API

Khi viết một use case lưu aggregate, có thể quyết định theo trình tự:

1. **Đã biết chắc aggregate mới chưa?** Nếu chưa, dùng `save` và bảo đảm ID/version/`Persistable` phản ánh đúng trạng thái.
2. **Đã biết chắc aggregate hiện hữu chưa?** Nếu cần update tường minh, tải root và dùng `update`; không gửi object partial.
3. **Ứng dụng tự cấp ID cho aggregate mới?** Dùng `insert` khi ID mới đã được xác nhận; kiểm tra unique constraint.
4. **Có child/collection?** Gửi trạng thái aggregate đầy đủ và hiểu rằng update có thể đồng bộ lại các hàng child.
5. **Có cập nhật đồng thời?** Cân nhắc `@Version` và xử lý xung đột.
6. **Nhiều thao tác phải nguyên tử?** Đặt `@Transactional` ở service.
7. **Cần upsert ở database?** Xác nhận API/dialect hỗ trợ và các giới hạn concurrency/optimistic locking.

## 13. Bài tập thực hành

**Bài 1 — Repository save.** Tạo một aggregate có ID tự sinh và gọi `repository.save` lần đầu. Kiểm tra ID được sinh và lần save tiếp theo đi theo đường update.

**Bài 2 — ID gán sẵn.** Tạo aggregate mới với ID do ứng dụng cấp. Quan sát cách `save` nhận diện trạng thái khi không có `@Version`; sau đó thử `template.insert` và giải thích vì sao explicit insert phù hợp.

**Bài 3 — Insert trùng.** Insert hai aggregate cùng ID. Xác nhận database báo lỗi constraint và `insert` không tự chuyển thành update.

**Bài 4 — Update hiện hữu.** Tải aggregate bằng repository, thay đổi status và gọi `template.update`. Thử với ID không tồn tại để quan sát hành vi của phiên bản/dialect đang dùng.

**Bài 5 — Child collection.** Tạo aggregate có hai child, thay đổi root nhưng giữ nguyên child rồi gọi update. Quan sát SQL root/child và xác nhận các hàng child được đồng bộ theo aggregate state.

**Bài 6 — Optimistic locking.** Thêm `@Version`. Cho hai transaction cùng đọc một version, update transaction đầu rồi thử update object cũ ở transaction sau. Quan sát `OptimisticLockingFailureException`.

**Bài 7 — Batch API.** So sánh `saveAll`, `insertAll` và `updateAll` trên tập dữ liệu được phân loại rõ ràng. Kiểm tra constraint và SQL log.
