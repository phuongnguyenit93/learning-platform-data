# Lựa chọn constructor và factory bằng @PersistenceCreator

Khi Spring Data JDBC đọc một hàng dữ liệu và dựng lại domain object, framework cần biết **nên gọi constructor nào hoặc static factory method nào**. Một class Java có thể có constructor không tham số, constructor đầy đủ tham số, constructor phục vụ tạo mới từ nghiệp vụ và nhiều factory method. Nếu không xác định rõ đường khởi tạo, object mapping có thể chọn đường không phù hợp hoặc không thể ánh xạ dữ liệu vào object.

Spring Data cung cấp annotation **`@PersistenceCreator`** để đánh dấu constructor hoặc static factory method được dùng cho mục đích persistence mapping. Annotation này đặc biệt hữu ích khi domain model có nhiều cách tạo object, cần giữ object bất biến hoặc phải tương thích với schema database hiện có.

Bài học tập trung vào cách Spring Data Relational/JDBC lựa chọn constructor, cách sử dụng `@PersistenceCreator` với constructor và factory, quy tắc ánh xạ tham số, cùng các lỗi thường gặp khi materialize entity.

## 1. Vì sao object mapping cần lựa chọn constructor?

Giả sử database có bảng khách hàng:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(160) NOT NULL,
    status VARCHAR(24) NOT NULL
);
```

Domain model có thể được thiết kế bất biến:

```java
@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;
    private final CustomerStatus status;

    public Customer(
        Long id,
        String email,
        String displayName,
        CustomerStatus status
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
        this.status = status;
    }

    // Getter được lược bớt.
}
```

Khi repository chạy:

```java
Customer customer = customerRepository.findById(10L)
    .orElseThrow();
```

Spring Data JDBC cần tạo một instance `Customer` từ các giá trị của hàng database. Framework phải xác định:

- Constructor nào nhận dữ liệu từ database?
- Tham số constructor nào tương ứng với property nào?
- Kiểu dữ liệu SQL được chuyển thành kiểu Java nào?
- Các property không được truyền vào constructor sẽ được gán như thế nào?

Đây là bước **object materialization** (khôi phục đối tượng từ dữ liệu lưu trữ). `@PersistenceCreator` cho mapping framework biết đường khởi tạo được ưu tiên khi class có nhiều lựa chọn.

## 2. @PersistenceCreator thuộc thành phần nào?

Annotation được định nghĩa trong Spring Data Commons:

```java
import org.springframework.data.annotation.PersistenceCreator;
```

Spring Data Relational/JDBC sử dụng cơ chế object mapping của hệ sinh thái Spring Data. Vì vậy `@PersistenceCreator` không phải annotation riêng của JDBC, và không phải annotation của JPA.

Vai trò các thành phần:

| Thành phần | Trách nhiệm |
| --- | --- |
| Spring Data Commons | Cung cấp annotation `@PersistenceCreator` và hạ tầng chung để nhận diện constructor/factory dùng cho persistence. |
| Spring Data Relational | Cung cấp metadata ánh xạ domain object và property quan hệ. |
| Spring Data JDBC | Sử dụng mapping metadata để dựng aggregate/entity khi đọc dữ liệu qua JDBC. |
| Spring JDBC | Thực thi thao tác SQL và cung cấp dữ liệu hàng cho tầng mapping. |

Annotation đánh dấu **đường khởi tạo object khi Spring Data đọc dữ liệu**. Nó không thay thế `@Autowired` trong dependency injection, không cấu hình repository và cũng không thay đổi cách database sinh khóa chính.

## 3. Quy tắc lựa chọn constructor

Spring Data có thể dùng constructor để tạo object rồi gán các property còn lại sau khi khởi tạo. Các nguyên tắc thực tế cần nhớ:

1. Nếu class chỉ có **một constructor**, constructor đó có thể được dùng làm persistence constructor mà không cần annotation.
2. Nếu class có nhiều constructor, hãy đánh dấu constructor muốn mapping framework sử dụng bằng `@PersistenceCreator`.
3. Nếu không có persistence creator được chỉ định và class có constructor không tham số phù hợp, framework có thể dùng constructor không tham số rồi gán property qua cơ chế property population.
4. Nếu class có nhiều lựa chọn khởi tạo hoặc cấu trúc constructor khó suy luận, khai báo rõ `@PersistenceCreator` để tránh phụ thuộc vào lựa chọn ngầm định.
5. Có thể dùng một static factory method được đánh dấu `@PersistenceCreator` thay cho constructor.

Không nên thiết kế class với nhiều constructor cùng có thể dùng để mapping rồi kỳ vọng framework tự suy ra ý định nghiệp vụ.

### 3.1. Class chỉ có một constructor

Ví dụ:

```java
@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    public Customer(Long id, String email, String displayName) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

Class chỉ có một constructor. Spring Data có thể sử dụng constructor đó để truyền giá trị của các property tương ứng. Không cần thêm `@PersistenceCreator` chỉ để đánh dấu một constructor duy nhất.

### 3.2. Nhiều constructor và chọn một constructor cho persistence

Giả sử ứng dụng có constructor ngắn phục vụ tạo khách hàng mới và constructor đầy đủ để khôi phục khách hàng từ database:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    public Customer(String email, String displayName) {
        this(null, email, displayName);
    }

    @PersistenceCreator
    public Customer(
        Long id,
        String email,
        String displayName
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

Hai constructor có mục đích khác nhau:

- `Customer(String, String)` phục vụ use case tạo khách hàng mới, chưa có ID.
- `Customer(Long, String, String)` nhận đầy đủ dữ liệu, bao gồm ID đã được database lưu.

`@PersistenceCreator` giúp Spring Data chọn constructor thứ hai khi materialize dữ liệu. Code nghiệp vụ vẫn có thể gọi constructor ngắn để tạo khách hàng mới.

### 3.3. Constructor không tham số và constructor đầy đủ

Một số entity cũ có constructor không tham số do framework hoặc thư viện khác yêu cầu:

```java
@Table("customers")
public class Customer {

    @Id
    private Long id;

    private String email;
    private String displayName;

    protected Customer() {
        // Phục vụ cơ chế khởi tạo không tham số khi cần.
    }

    @PersistenceCreator
    public Customer(
        Long id,
        String email,
        String displayName
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }
}
```

Khi có nhiều constructor, annotation xác định rõ constructor persistence. Nếu không đánh dấu, một đường khởi tạo không tham số có thể được sử dụng và framework sẽ phải gán các thuộc tính sau đó. Điều này có thể không phù hợp nếu entity cần giữ invariant ngay khi được tạo.

Với domain model bất biến, constructor đầy đủ thường dễ kiểm soát hơn: object được tạo với toàn bộ trạng thái cần thiết ngay từ đầu.

## 4. Ánh xạ tham số constructor với property

Khi Spring Data gọi persistence constructor, framework phải nối từng tham số với property của domain object. Vì thế, **tên tham số constructor cần tương ứng với tên property** và kiểu dữ liệu phải có thể chuyển đổi từ giá trị lưu trữ.

Ví dụ:

```java
@PersistenceCreator
public Customer(Long id, String email, String displayName) {
    this.id = id;
    this.email = email;
    this.displayName = displayName;
}
```

Các tham số `id`, `email` và `displayName` tương ứng với các property cùng tên. Tên cột vật lý trong database có thể khác tên property nếu dùng `@Column`; việc binding constructor dựa trên **property của domain model**, không yêu cầu tên tham số phải bằng tên cột SQL.

### 4.1. Bảo đảm Java giữ tên tham số

Với class Java thông thường, tên tham số có thể không được giữ trong bytecode nếu compiler không được cấu hình để lưu metadata parameter names. Khi đó mapping framework có thể không xác định được tên property tương ứng.

Với Gradle Groovy, có thể bật tùy chọn `-parameters`:

```groovy
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs.add('-parameters')
}
```

Với Maven Compiler Plugin, cấu hình tương ứng là:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
    </configuration>
</plugin>
```

Một số phiên bản plugin/framework hoặc cấu hình build đã bật tùy chọn này. Nếu dự án phụ thuộc vào parameter name discovery, hãy kiểm tra cấu hình compiler thực tế thay vì mặc định rằng tên biến trong source luôn tồn tại ở runtime.

### 4.2. Java record

Java `record` là lựa chọn tự nhiên cho object bất biến. Record có canonical constructor tương ứng với các record component:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String email,
    String displayName
) {}
```

Nếu record chỉ có canonical constructor, Spring Data có thể sử dụng constructor đó mà không cần `@PersistenceCreator`.

Khi thêm constructor phụ hoặc static factory, hãy xác định rõ đường khởi tạo mà mapping cần dùng. Record component name có metadata riêng của record, nhưng quy tắc đặt tên property vẫn phải nhất quán với domain model.

### 4.3. Tên tham số không khớp property

Ví dụ không nên dùng:

```java
@PersistenceCreator
public Customer(Long customerId, String emailAddress) {
    this.id = customerId;
    this.email = emailAddress;
}
```

Nếu property thực tế là `id` và `email`, tham số `customerId` và `emailAddress` không tự động trở thành tên property tương ứng chỉ vì phần thân constructor gán chúng vào đúng field.

Hãy đổi tên tham số để khớp:

```java
@PersistenceCreator
public Customer(Long id, String email) {
    this.id = id;
    this.email = email;
}
```

Nếu cần chuyển đổi dữ liệu phức tạp hoặc property có tên đặc biệt, hãy sử dụng cơ chế mapping/conversion phù hợp thay vì dựa vào tên tham số tùy ý.

## 5. Sử dụng static factory method với @PersistenceCreator

Constructor không phải con đường duy nhất để tạo object. Một class có thể cung cấp **static factory method** được đánh dấu `@PersistenceCreator`. Spring Data sử dụng factory đó làm persistence creator.

Cách này hữu ích khi:

- Constructor cần được giữ private/protected để bảo vệ cách tạo object.
- Domain model có tên factory biểu đạt rõ mục đích, ví dụ `rehydrate` hoặc `restore`.
- Muốn gom logic tạo object vào một điểm duy nhất.
- Có nhiều constructor/factory phục vụ các use case khác nhau.

Ví dụ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    private Customer(
        Long id,
        String email,
        String displayName
    ) {
        if (email == null || email.isBlank()) {
            throw new IllegalArgumentException("Email bắt buộc");
        }

        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public static Customer register(
        String email,
        String displayName
    ) {
        return new Customer(null, email, displayName);
    }

    @PersistenceCreator
    public static Customer rehydrate(
        Long id,
        String email,
        String displayName
    ) {
        return new Customer(id, email, displayName);
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

Hai đường tạo object mang ngữ nghĩa khác nhau:

| Đường khởi tạo | Mục đích | Cách gọi |
| --- | --- | --- |
| `Customer.register(email, name)` | Tạo khách hàng mới theo use case nghiệp vụ. | Code ứng dụng gọi trực tiếp. |
| `Customer.rehydrate(id, email, name)` | Dựng lại khách hàng từ dữ liệu persistence. | Spring Data gọi khi mapping dữ liệu. |

Tên factory `rehydrate` giúp người đọc nhận ra mục đích khôi phục trạng thái đã lưu. Đây là lựa chọn thiết kế, không phải tên phương thức bắt buộc của framework.

### 5.1. Điều kiện thiết kế factory method

Một factory method dùng cho persistence nên:

- Là phương thức **static** trên kiểu domain được materialize.
- Được đánh dấu `@PersistenceCreator`.
- Trả về đúng kiểu domain tương ứng.
- Có tham số phù hợp với các persistent property và có thể được mapping framework chuyển đổi.
- Có khả năng được gọi bởi mapping infrastructure; dùng public static method là cách rõ ràng, dễ tương thích.
- Không phụ thuộc vào request hiện tại, HTTP session hoặc một Spring service cần injection.

Factory persistence được gọi trong quá trình đọc dữ liệu, có thể xảy ra rất thường xuyên. Vì vậy nên giữ logic tạo object gọn, xác định và không gây side effect như gửi email, gọi API ngoài hoặc ghi thêm bản ghi database.

### 5.2. Factory method không phải Spring bean factory

Cần phân biệt hai khái niệm:

- `@PersistenceCreator`: hướng dẫn **Spring Data mapping** chọn factory/constructor khi tạo domain object từ dữ liệu.
- `@Bean` hoặc `@Component`: đăng ký đối tượng do Spring IoC container quản lý.
- `@Autowired`: hướng dẫn Spring dependency injection giải quyết dependency của bean.

Không nên thêm `@Autowired` vào factory chỉ để Spring Data JDBC sử dụng nó. Persistence factory không phải một service bean và không được dùng như cơ chế injection dependency.

## 6. Constructor và factory trong entity bất biến

Entity bất biến giữ trạng thái sau khi được tạo; không có setter công khai để thay đổi tùy ý. Đây là lựa chọn hữu ích khi muốn bảo vệ invariant và giảm trạng thái không hợp lệ.

Ví dụ với Java record:

```java
@Table("orders")
public record PurchaseOrder(
    @Id Long id,
    Long customerId,
    OrderStatus status
) {
    public PurchaseOrder {
        if (customerId == null) {
            throw new IllegalArgumentException("customerId bắt buộc");
        }
        if (status == null) {
            throw new IllegalArgumentException("status bắt buộc");
        }
    }
}
```

Vì record có canonical constructor, Spring Data có thể sử dụng nó để dựng object. Compact constructor cho phép kiểm tra dữ liệu ngay khi object được tạo.

Nếu database có giá trị NULL cho một cột được ánh xạ vào primitive như `int`, Java không thể biểu diễn NULL trong primitive. Hãy dùng kiểu wrapper như `Integer` khi NULL là trạng thái hợp lệ hoặc điều chỉnh schema/constraint để dữ liệu luôn có giá trị.

### 6.1. Property không nằm trong constructor

Một class có thể đưa một số property vào persistence constructor và gán các property còn lại sau đó qua setter hoặc field access. Tuy nhiên, nếu property là final và không có cơ chế thay đổi phù hợp, nó cần được truyền qua constructor/factory.

Với object bất biến, hãy ưu tiên đưa toàn bộ persistent state cần thiết vào constructor. Điều này giúp tránh object được tạo trong trạng thái thiếu dữ liệu rồi mới được hoàn thiện bằng các phép gán sau đó.

Spring Data cũng hỗ trợ một số cơ chế property population như setter, field access và wither method tùy loại property. Không nên dựa vào setter ẩn hoặc field reflection khi một constructor đầy đủ có thể thể hiện trạng thái object rõ ràng hơn.

### 6.2. ID do database sinh và object bất biến

Khi lưu entity mới, database có thể tạo ID. Với object bất biến, giá trị ID không thể được gán trực tiếp vào field final sau khi insert. Có thể thiết kế kiểu domain với một phương thức wither trả về instance mới:

```java
public Customer withId(Long newId) {
    return new Customer(newId, email, displayName);
}
```

Spring Data hỗ trợ cơ chế tạo instance mới khi cần gán property bất biến theo mapping metadata. Khi dùng record, framework cũng có thể sử dụng constructor để tạo bản ghi mới chứa giá trị ID được sinh.

Trong code ứng dụng, luôn ưu tiên sử dụng object được trả về từ `repository.save(entity)` để nhận trạng thái sau persistence:

```java
Customer created = Customer.register(
    "an@example.test",
    "Nguyen An"
);

Customer saved = customerRepository.save(created);

Long generatedId = saved.getId();
```

Không giả định rằng biến `created` ban đầu luôn được thay đổi tại chỗ.

## 7. Constructor mapping với @Column và tên cột khác property

Schema có thể sử dụng tên cột khác tên property:

```sql
CREATE TABLE customers (
    customer_no BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    contact_email VARCHAR(255) NOT NULL,
    display_label VARCHAR(160) NOT NULL
);
```

Domain model:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    @Column("customer_no")
    private final Long id;

    @Column("contact_email")
    private final String email;

    @Column("display_label")
    private final String displayName;

    @PersistenceCreator
    public Customer(Long id, String email, String displayName) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }
}
```

Tên property/constructor parameter vẫn là `id`, `email`, `displayName`. Annotation `@Column` chịu trách nhiệm ánh xạ property tới cột vật lý `customer_no`, `contact_email` và `display_label`.

| Constructor parameter | Domain property | Database column |
| --- | --- | --- |
| `id` | `id` | `customer_no` |
| `email` | `email` | `contact_email` |
| `displayName` | `displayName` | `display_label` |

Đừng đặt tên tham số constructor là `contact_email` chỉ vì cột database dùng tên đó. Constructor mapping hoạt động ở mức property domain.

## 8. @PersistenceCreator trong aggregate Spring Data JDBC

Spring Data JDBC đọc và dựng **aggregate root** cùng các đối tượng thuộc aggregate theo mapping metadata. Cơ chế lựa chọn constructor không chỉ áp dụng cho root mà còn có thể áp dụng cho các kiểu object con/value object được materialize.

Ví dụ aggregate đơn hàng:

```java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private final Long id;

    private final String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private final List<OrderLine> lines;

    @PersistenceCreator
    public PurchaseOrder(
        Long id,
        String orderNumber,
        List<OrderLine> lines
    ) {
        this.id = id;
        this.orderNumber = orderNumber;
        this.lines = List.copyOf(lines);
    }
}
```

Đối tượng con:

```java
@Table("order_lines")
public class OrderLine {

    @Id
    private final Long id;

    private final String sku;
    private final int quantity;

    @PersistenceCreator
    public OrderLine(Long id, String sku, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity phải dương");
        }
        this.id = id;
        this.sku = sku;
        this.quantity = quantity;
    }
}
```

Đây là minh họa cấu trúc object mapping; schema thực tế cần có khóa ngoại `order_id` và các cột tương ứng. `@MappedCollection` xác định quan hệ collection thuộc aggregate. Khi Spring Data JDBC materialize root, nó cần tạo cả các phần tử con theo mapping tương ứng.

Một điểm cần lưu ý: constructor của root có thể được gọi với các đối tượng con đã được mapping. Không nên giả định thứ tự các thao tác SQL hoặc số lần constructor được gọi là API nghiệp vụ ổn định; hãy giữ constructor/factory không phụ thuộc side effect.

## 9. Phân biệt @PersistenceCreator với các annotation khác

| Annotation | Mục đích | Phạm vi |
| --- | --- | --- |
| `@PersistenceCreator` | Chọn constructor/static factory cho Spring Data object mapping. | Spring Data Commons. |
| `@Autowired` | Chỉ định injection dependency cho Spring bean. | Spring Framework IoC. |
| `@Bean` | Đăng ký đối tượng do phương thức cấu hình trả về vào Spring context. | Spring Framework IoC. |
| `@Table` | Chỉ định bảng quan hệ cho domain type. | Spring Data Relational. |
| `@Column` | Chỉ định cột quan hệ cho property. | Spring Data Relational. |
| `@Id` | Đánh dấu property định danh. | Spring Data Commons. |
| `@Version` | Đánh dấu property version cho optimistic locking. | Spring Data Commons. |

`@PersistenceCreator` cũng không phải annotation JPA `@ConstructorResult` dùng trong một số mapping native query. Hai annotation phục vụ những cơ chế persistence khác nhau.

## 10. Tích hợp với Lombok và code được sinh tự động

Lombok có thể sinh nhiều constructor:

```java
@NoArgsConstructor
@AllArgsConstructor
@RequiredArgsConstructor
public class Customer {
    // fields
}
```

Nếu kết hợp các annotation này, class có thể có nhiều constructor mà source code không thể hiện trực tiếp từng constructor sau khi compile. Spring Data mapping vẫn phải chọn được một đường khởi tạo rõ ràng.

Cách xử lý:

- Xem constructor thực tế được Lombok sinh ra.
- Nếu có nhiều constructor, đánh dấu constructor phù hợp bằng `@PersistenceCreator` (có thể dùng annotation trên constructor được khai báo tường minh khi cần).
- Đảm bảo tham số constructor có tên phù hợp với persistent property.
- Bật parameter name metadata nếu cấu hình build chưa có.
- Tránh tạo constructor rỗng chỉ để “cho framework chạy” nếu domain model cần invariant được kiểm tra ngay khi materialize.

Với Lombok builder, `@Builder` chủ yếu phục vụ tạo object từ code ứng dụng. Không nên giả định Spring Data tự dùng builder để dựng entity khi đọc database. Nếu muốn persistence dùng static factory, hãy đánh dấu factory bằng `@PersistenceCreator` và thiết kế tham số rõ ràng.

## 11. Kiểm thử constructor/factory mapping

Một test repository giúp xác nhận Spring Data JDBC thực sự dùng đường khởi tạo và giá trị được gán đúng:

```java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;

@DataJdbcTest
class CustomerRepositoryTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void materializesCustomerFromPersistenceCreator() {
        Customer saved = customers.save(
            Customer.register(
                "an@example.test",
                "Nguyen An"
            )
        );

        Customer loaded = customers.findById(saved.getId())
            .orElseThrow();

        assertThat(loaded.getEmail()).isEqualTo("an@example.test");
        assertThat(loaded.getDisplayName()).isEqualTo("Nguyen An");
    }
}
```

Bài test này cần có schema tương ứng và cấu hình datasource test. Nó xác nhận dữ liệu có thể đi từ object vào database và quay lại object. Để kiểm tra rõ một factory được gọi, có thể thiết kế test ở mức mapping phù hợp hoặc dùng một trạng thái được tạo ra bởi factory; tránh thêm side effect chỉ để đếm số lần gọi trong production code.

Một kiểm thử tích hợp hữu ích nên xác nhận:

- Database row được đọc vào đúng property.
- Constructor/factory có thể nhận các kiểu dữ liệu đã convert.
- Property không được truyền vào constructor vẫn có đường population hợp lệ nếu thiết kế cần.
- Giá trị NULL/enum/date/time được xử lý đúng theo schema và conversion.
- Generated ID được phản ánh trong object trả về từ `save`.
- Constructor/factory không ném exception với dữ liệu hợp lệ đang có trong database.

## 12. Lỗi thường gặp khi sử dụng @PersistenceCreator

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
| --- | --- | --- |
| Mapping không xác định được constructor | Nhiều constructor nhưng không có persistence creator rõ ràng. | Đánh dấu constructor/factory mong muốn bằng `@PersistenceCreator`. |
| Tham số constructor không được gán đúng | Tên tham số không khớp property hoặc thiếu metadata tên tham số. | Đặt tên trùng property, bật `-parameters` khi cần. |
| Factory method không được dùng | Method không phải static, không được đánh dấu hoặc không có signature mapping phù hợp. | Dùng static factory và đánh dấu `@PersistenceCreator`. |
| Constructor ném exception khi đọc dữ liệu | Dữ liệu cũ trong database vi phạm invariant mới hoặc NULL không phù hợp kiểu Java. | Kiểm tra schema/dữ liệu, chuyển đổi hoặc migration trước khi áp dụng domain rule mới. |
| Field bất biến vẫn thiếu giá trị | Property không nằm trong constructor và không có setter/field/wither phù hợp. | Đưa property vào persistence constructor hoặc cung cấp cơ chế immutable population phù hợp. |
| Dùng nhầm annotation | Import sai package hoặc nhầm với annotation DI/JPA. | Import `org.springframework.data.annotation.PersistenceCreator`. |
| Factory gọi API ngoài khi đọc dữ liệu | Trộn persistence reconstitution với side effect nghiệp vụ. | Giữ factory thuần, nhanh và không phụ thuộc service bên ngoài. |
| Test chạy được nhưng production lỗi | Schema, kiểu dữ liệu hoặc parameter metadata giữa hai môi trường khác nhau. | Kiểm thử trên database/dialect và artifact build tương ứng. |

### 12.1. Dữ liệu cũ có thể không thỏa invariant mới

Một constructor có thể kiểm tra email không rỗng hoặc trạng thái phải hợp lệ. Nhưng nếu database đã chứa hàng cũ có email NULL hoặc giá trị enum không còn tồn tại, constructor có thể ném exception ngay khi repository đọc hàng đó.

Đây không nhất thiết là lỗi của `@PersistenceCreator`. Đó có thể là dấu hiệu domain rule mới chưa được đối chiếu với dữ liệu hiện hữu. Trước khi triển khai, cần xác định dữ liệu nào hợp lệ, migration/backfill nào cần chạy và ứng dụng sẽ xử lý bản ghi không hợp lệ ra sao.

## 13. Khi nào nên dùng constructor, khi nào nên dùng factory?

| Tiêu chí | Constructor được đánh dấu | Static factory được đánh dấu |
| --- | --- | --- |
| Mô hình đơn giản, một đường khởi tạo | Rất phù hợp; thường không cần annotation nếu chỉ có một constructor. | Có thể dùng nhưng không bắt buộc. |
| Có nhiều constructor | Dùng `@PersistenceCreator` để chọn constructor persistence. | Có thể đánh dấu factory nếu muốn tách đường reconstitution. |
| Muốn constructor private/protected | Có thể tùy khả năng truy cập và mapping setup. | Factory public/static thường thể hiện ý định rõ. |
| Muốn đặt tên cho thao tác khôi phục | Tên constructor không thể đặt theo ý nghĩa nghiệp vụ. | Tên như `rehydrate`, `restore` làm ý định rõ hơn. |
| Logic tạo object cần biểu đạt nhiều bước | Constructor có thể trở nên dài và khó hiểu. | Factory giúp gom và đặt tên logic, nhưng không nên gọi dịch vụ bên ngoài. |
| Java record | Canonical constructor thường đủ. | Có thể dùng factory nếu cần đường tạo riêng và được mapping hỗ trợ. |

Không có quy tắc rằng factory luôn tốt hơn constructor. Hãy chọn cách giúp domain model rõ ràng, giữ invariant và cho mapping framework một đường khởi tạo xác định.

## 14. Quy trình áp dụng trong codebase Spring Data JDBC

Khi một entity cần nhiều constructor hoặc factory:

1. Xác định những property nào là persistence state cần có khi dựng object từ database.
2. Kiểm tra số lượng constructor và static factory hiện tại.
3. Chọn một persistence creator duy nhất và đánh dấu `@PersistenceCreator` nếu cần phân biệt.
4. Đặt tên tham số theo property của domain model; bảo đảm compiler giữ metadata tên tham số nếu dùng class Java thông thường.
5. Kiểm tra kiểu dữ liệu, nullability, enum/conversion và các invariant mà constructor/factory áp dụng.
6. Xác nhận các property còn lại có thể được gán bằng cơ chế population phù hợp, đặc biệt khi entity bất biến.
7. Chạy repository test trên schema/database tương thích và sử dụng object trả về từ `save` khi cần generated ID.

> **`@PersistenceCreator` cho Spring Data biết nên dùng constructor hoặc static factory nào để dựng domain object từ dữ liệu lưu trữ.** Tên tham số phải gắn đúng với property, còn các invariant nên được bảo vệ ngay tại đường khởi tạo. Khi domain model có nhiều cách tạo object, một persistence creator được chọn rõ ràng giúp mapping ổn định và dễ hiểu.
