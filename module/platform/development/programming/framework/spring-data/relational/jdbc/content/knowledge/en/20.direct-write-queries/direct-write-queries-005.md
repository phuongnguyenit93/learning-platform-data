# Callbacks, Auditing, and Optimistic Locking When Bypassing the Aggregate Save Flow

In **Spring Data Relational JDBC**, calling `repository.save(aggregate)` or using `JdbcAggregateTemplate` goes through Spring Data's aggregate save mechanism. This mechanism understands the aggregate root's mapping, handles child entities, and applies entity callbacks, auditing, and optimistic locking as configured.

When a narrow write operation is needed, an application may use `@Modifying @Query`, `JdbcTemplate`, `NamedParameterJdbcTemplate`, or raw JDBC. These write paths execute DML at the SQL level and **do not automatically run the aggregate save process**. As a result, callbacks may not be invoked, audit fields are not updated automatically, and `@Version` is not automatically checked or verified.

This is a critical distinction when optimizing small updates. A direct `UPDATE` statement can be efficient, but the author of the statement must proactively maintain the rules that aggregate save previously handled: updating audit columns, checking versions, preserving invariants, managing transactions, and triggering necessary side effects.

## 1. Two Different Data Write Paths

Suppose an order has a code, status, update timestamp, and version. The application can write via the repository:

```java
PurchaseOrder order = orders.findById(orderId)
        .orElseThrow();

order.markAsPaid();

orders.save(order);
```

Or update a single column directly:

```java
jdbcTemplate.update(
        "UPDATE orders SET status = ? WHERE id = ?",
        "PAID",
        orderId
);
```

Both snippets can change the `status` column, but their internal paths differ.

```mermaid
flowchart TD
    A[Application service]
    A --> B[repository.save / JdbcAggregateTemplate]
    A --> C[@Modifying @Query / JdbcTemplate / JDBC]

    B --> D[Aggregate mapping]
    D --> E[Entity callbacks]
    E --> F[Auditing callback]
    F --> G[Optimistic version check]
    G --> H[SQL for root and dependent entities]
    H --> I[(Database)]

    C --> J[Execute explicit SQL]
    J --> I

    C -. no automatic aggregate lifecycle .-> K[Caller owns audit, version and invariants]
```

| Capability | Aggregate-aware save | Direct DML |
|---|---|---|
| Aggregate root mapping | Yes | Not automatic |
| Handling `@MappedCollection` | Per aggregate mapping | Only if SQL/FKs are written to do so |
| Entity callbacks | Yes, in the corresponding lifecycle operation | Not automatic |
| Auditing annotations | Handled by auditing infrastructure when callbacks run | Not automatic |
| `@Version` optimistic locking | Managed by Spring Data JDBC | Must add version predicate and increment version manually |
| Domain methods/invariants | Can be applied before save | Do not run automatically |
| Specific SQL | Generated by framework per mapping | Controlled directly by the author |

Direct DML is not always wrong. It fits simple updates, batches, counters, or well-scoped state changes. What to avoid is assuming that conveniences of aggregate save still work automatically after switching to a direct SQL path.

## 2. Entity Callbacks in Spring Data JDBC

Entity callbacks are extension points that let logic run at specific stages of the mapping/persistence lifecycle. They are useful for normalizing data, adding metadata, or reacting before/after saving and loading aggregates.

Common callbacks in Spring Data Relational include:

| Callback | General timing | Typical purpose |
|---|---|---|
| `BeforeConvertCallback` | Before the aggregate is converted into relational form | Normalize or populate values before conversion |
| `BeforeSaveCallback` | Before the aggregate change is written to the database | Adjust data or observe the aggregate change |
| `AfterSaveCallback` | After the aggregate is saved | Perform post-save processing |
| `AfterConvertCallback` | After relational data is converted into an object | Finalize the object after conversion |

Exact callback names and signatures must match the Spring Data Relational version in your project. Callbacks are managed by Spring Data when the application uses the corresponding mapping/persistence path, such as an aggregate repository or `JdbcAggregateTemplate`.

### 2.1. `BeforeConvertCallback` Example

Suppose an order code must be normalized before saving. This technical logic can live in a callback:

```java
@Component
public class OrderCodeCallback
        implements BeforeConvertCallback<PurchaseOrder> {

    @Override
    public PurchaseOrder onBeforeConvert(PurchaseOrder aggregate) {
        String normalized = aggregate.getOrderCode()
                .trim()
                .toUpperCase(Locale.ROOT);

        return aggregate.withOrderCode(normalized);
    }
}
```

The example assumes `PurchaseOrder` is immutable and has a `withOrderCode(...)` method. For a mutable class, the callback can modify the object and return that instance.

When saving through the repository, the callback can run in the pre-conversion lifecycle. However, if the service replaces it with:

```java
jdbcTemplate.update(
        "UPDATE orders SET order_code = ? WHERE id = ?",
        rawOrderCode,
        orderId
);
```

then `BeforeConvertCallback` is not invoked. The SQL writes the exact `rawOrderCode` passed in. If normalization is still required, the direct-write path must normalize before binding the parameter or use an intentional database mechanism.

### 2.2. `BeforeSaveCallback` Example

`BeforeSaveCallback` is used when you need to intervene right before writing the aggregate change. This callback can receive the aggregate and relational change information depending on the API version.

Illustrative callback structure:

```java
@Component
public class OrderBeforeSaveCallback
        implements BeforeSaveCallback<PurchaseOrder> {

    @Override
    public PurchaseOrder onBeforeSave(
            PurchaseOrder aggregate,
            AggregateChange<PurchaseOrder> change
    ) {
        // Can inspect or supplement data as appropriate for persistence.
        return aggregate;
    }
}
```

An actual callback must import the interface and `AggregateChange` type from the Spring Data Relational package matching your version. Check the dependency API in your project before copying examples verbatim into source.

The key point of this lesson: callbacks only have an opportunity to run when the command goes through the Spring Data–managed lifecycle. An `UPDATE` via `JdbcTemplate` does not build an `AggregateChange` and does not invoke callbacks merely because it uses the same `DataSource`.

### 2.3. Callbacks Do Not Replace Domain Methods

Callbacks suit technical or cross-cutting logic such as normalization, attaching metadata, and lifecycle observation. Core business rules should live in domain methods or application services so every write path can use them intentionally.

For example, the rule "only orders in `NEW` status may transition to `PAID`" belongs in domain behavior:

```java
public void markAsPaid() {
    if (status != OrderStatus.NEW) {
        throw new IllegalStateException(
                "Only NEW orders can be paid"
        );
    }

    this.status = OrderStatus.PAID;
}
```

If direct SQL updates `status` without checking the current status, it can bypass this invariant. When writing directly, include the business condition in the statement or invoke a service check before writing.

### 2.4. Callbacks Differ from Database Triggers

Callbacks run inside the Spring Data application. Database triggers run inside the database when matching DML occurs.

| Aspect | Entity callback | Database trigger |
|---|---|---|
| Where it runs | Application process | Database server |
| Requires Spring Data lifecycle | Yes | No |
| Triggered by `JdbcTemplate` | Not automatically | Yes, if DML matches trigger |
| Aware of domain objects | Can receive aggregate/object | Sees only rows/columns and DB context |
| Best suited for | Logic tied to application mapping/domain | DB-level data rules, multi-application auditing |

A trigger can guarantee auditing for both Spring Data and direct SQL, but it must be designed not to conflict with the application's auditing callbacks. Avoid having both layers write the same field under different rules.

## 3. Auditing in Spring Data JDBC

Auditing automatically records who created/modified data and when. Spring Data Relational provides common annotations:

- `@CreatedBy`: creator.
- `@CreatedDate`: creation timestamp.
- `@LastModifiedBy`: last modifier.
- `@LastModifiedDate`: last modification timestamp.

To enable auditing for Spring Data JDBC, configure `@EnableJdbcAuditing` and provide an `AuditorAware` if you need to store the actor.

### 3.1. Declaring Audit Fields on an Aggregate

Example:

```java
import java.time.Instant;

import org.springframework.data.annotation.CreatedBy;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedBy;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.annotation.Version;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @CreatedBy
    private String createdBy;

    @CreatedDate
    private Instant createdAt;

    @LastModifiedBy
    private String lastModifiedBy;

    @LastModifiedDate
    private Instant lastModifiedAt;

    @Version
    private Long version;
}
```

These annotations belong to `org.springframework.data.annotation`. They mark metadata for auditing and optimistic locking; database column names must match the naming strategy or be configured via `@Column`.

Illustrative schema:

```sql
CREATE TABLE orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    status VARCHAR(30) NOT NULL,
    created_by VARCHAR(120),
    created_at TIMESTAMP,
    last_modified_by VARCHAR(120),
    last_modified_at TIMESTAMP,
    version BIGINT NOT NULL
);
```

### 3.2. Enabling Auditing and Providing `AuditorAware`

Illustrative configuration:

```java
@Configuration
@EnableJdbcAuditing
public class JdbcAuditingConfiguration {

    @Bean
    AuditorAware<String> auditorAware(CurrentActor currentActor) {
        return () -> Optional.ofNullable(currentActor.username());
    }
}
```

`CurrentActor` represents an application component that obtains the current user from the authentication context. This is an illustrative example; in a real application, retrieve the actor from a trusted server source such as the security context or service identity, rather than accepting an arbitrary username sent by the client.

The auditing infrastructure uses `AuditorAware` to populate creator/modifier fields when lifecycle auditing is triggered.

If you do not need to store the actor, you can enable only date auditing and omit the auditor provider as supported by your version. If `@CreatedBy` or `@LastModifiedBy` is needed, provide an appropriate auditor source.

### 3.3. Auditing Works on Aggregate Save

When an aggregate is saved via Spring Data JDBC, the auditing callback can populate values:

- On insert, `createdAt`/`createdBy` record creation metadata.
- On update, `lastModifiedAt`/`lastModifiedBy` record the latest modification.
- Created fields are normally preserved across subsequent updates.

Exact population rules depend on auditing configuration, `modifyOnCreate`, date/time types, and entity mapping. Check your project's configuration if you need exact rules for initial creation.

### 3.4. Direct SQL Does Not Populate Audit Fields Automatically

Suppose code changes from:

```java
orders.save(order);
```

to:

```java
jdbcTemplate.update(
        "UPDATE orders SET status = ? WHERE id = ?",
        "PAID",
        orderId
);
```

The SQL statement updates only `status`. It knows nothing about `@LastModifiedDate`, `@LastModifiedBy`, or `AuditorAware`. Audit values remain unchanged unless SQL, a trigger, or another mechanism updates them.

If direct write is an intentionally designed path, bind audit information explicitly:

```sql
UPDATE orders
SET status = :status,
    last_modified_at = :modifiedAt,
    last_modified_by = :modifiedBy
WHERE id = :id;
```

Here `modifiedAt` should come from a `Clock` or the application's time provider; `modifiedBy` should come from a trusted actor. Do not update `created_at` and `created_by` in regular update operations.

### 3.5. Choosing One Authoritative Source for Auditing

There are two common approaches:

**Application-managed auditing:** aggregate save uses auditing callbacks; direct DML must bind audit fields explicitly. This keeps audit logic in code, but requires every write path to follow the same rules.

**Database-managed auditing:** triggers or stored procedures update audit columns. This covers multiple clients accessing the database, though actor/time must be passed via session settings or parameters using a safe convention.

Do not let auditing callbacks write one value while a trigger overwrites another without clear rules. Designate one authoritative source for each audit field.

## 4. Optimistic Locking with `@Version`

Optimistic locking detects when two transactions concurrently modify the same aggregate based on its version. It prevents a stale object from overwriting newer data committed by someone else.

In Spring Data JDBC, mark a property with `@Version`:

```java
import org.springframework.data.annotation.Version;

@Table("orders")
public class PurchaseOrder {

    @Id
    private Long id;

    private String status;

    @Version
    private Long version;
}
```

The schema has a version column:

```sql
ALTER TABLE orders
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
```

Spring Data JDBC uses the current version in the update condition and increments the version upon a successful write.

### 4.1. How Version Protects Updates

Suppose an order has:

| id | status | version |
|---:|---|---:|
| 101 | NEW | 4 |

Two requests A and B both read version 4.

- Request A changes the status and saves successfully; version becomes 5.
- Request B still holds the object at version 4.
- When B saves, the version 4 predicate no longer matches.
- Spring Data JDBC detects that no row was updated for the expected version and reports an optimistic locking failure.

Semantic SQL illustration:

```sql
UPDATE orders
SET status = ?,
    version = 5
WHERE id = 101
  AND version = 4;
```

The statement updates the row only if both ID and version match. Once the version is 5, the statement updates zero rows.

### 4.2. Exception on Conflict

When optimistic locking detects that data was changed by another transaction, Spring Data JDBC raises an error from Spring DAO's `OptimisticLockingFailureException` hierarchy.

The application can handle it according to the use case:

- Inform the client that the data changed and ask them to reload.
- Load the latest aggregate and ask the user to reapply changes.
- Perform a controlled retry if the operation can be safely recomputed.
- Log/emit metrics to track conflict frequency.

Do not blindly auto-retry business operations with side effects. Payments, sending notifications, or deducting stock require idempotency and explicit business rules.

### 4.3. Version Also Applies to Delete

When deleting a versioned aggregate, Spring Data JDBC can use the version to check whether the object is still the current version. If the application deletes with direct SQL, the database does not read `@Version` annotations on its own.

If a direct delete needs optimistic locking, the statement must check the version:

```sql
DELETE FROM orders
WHERE id = :id
  AND version = :expectedVersion;
```

With dependent tables, you must also decide how to delete children and preserve foreign keys in the same transaction. If using an `ON DELETE CASCADE` FK, the database can clean up dependent rows; otherwise, delete children in the proper order. Do not assume `@Version` applies automatically to direct DELETE statements.

## 5. Why Does Direct DML Bypass Optimistic Locking?

A SQL statement such as:

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 101;
```

checks only the ID. It does not check the version that the object previously read. If another request just modified the same order, the statement can still overwrite the new state.

`@Version` is metadata used by Spring Data JDBC inside aggregate-aware persistence. The database does not automatically know that a Java class carries this annotation. When bypassing repository save, you must bring the version protocol into the SQL statement.

### 5.1. Lost Update Example

Suppose:

| Time | Request A | Request B | Database |
|---|---|---|---|
| T1 | Reads version 7 | | version 7 |
| T2 | | Reads version 7 | version 7 |
| T3 | Updates address, saves | | version 8 |
| T4 | | Direct UPDATE status by ID only | B writes over version 8 data without checking version 7 |
| T5 | | | A's changes may be overwritten or combined unexpectedly |

If B uses `WHERE id = ? AND version = 7`, B's UPDATE statement affects zero rows after A increments the version to 8. B can detect the conflict via an update count of 0.

### 5.2. Direct Updates Must Check and Increment Version

A safer update command:

```sql
UPDATE orders
SET status = :status,
    last_modified_at = :modifiedAt,
    last_modified_by = :modifiedBy,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

Three things happen in one statement:

1. Updates only if the version still matches what the caller read.
2. Writes the new status.
3. Increments the version so subsequent writers know the data changed.

Without incrementing the version, a stale aggregate could continue to save with the old version and fail to notice the direct update that just happened.

### 5.3. Checking the Update Count

With `JdbcTemplate`, the return value is the number of updated rows:

```java
int updated = jdbcTemplate.update(sql, parameters);

if (updated == 0) {
    throw new OptimisticLockingFailureException(
            "Order was changed or no longer exists"
    );
}
```

If `updated == 1`, the operation updated exactly one row. If 0, either the order does not exist or the version mismatched. If you need to distinguish the two cases, run an additional check query in an appropriate transaction.

Do not rely on automatic Spring Data JDBC exceptions for `JdbcTemplate.update(...)`; direct DML must interpret the update count itself and throw an appropriate application error.

## 6. A Complete Direct Update with Auditing and Version

Example service using `NamedParameterJdbcTemplate`:

```java
@Service
public class OrderCommandService {

    private final NamedParameterJdbcTemplate jdbc;
    private final Clock clock;
    private final CurrentActor currentActor;

    public OrderCommandService(
            NamedParameterJdbcTemplate jdbc,
            Clock clock,
            CurrentActor currentActor
    ) {
        this.jdbc = jdbc;
        this.clock = clock;
        this.currentActor = currentActor;
    }

    @Transactional
    public void changeStatus(
            long orderId,
            long expectedVersion,
            String newStatus
    ) {
        Instant now = clock.instant();
        String actor = currentActor.username();

        String sql = """
            UPDATE orders
            SET status = :status,
                last_modified_at = :modifiedAt,
                last_modified_by = :modifiedBy,
                version = version + 1
            WHERE id = :id
              AND version = :expectedVersion
            """;

        var parameters = new MapSqlParameterSource()
                .addValue("status", newStatus)
                .addValue("modifiedAt", Timestamp.from(now))
                .addValue("modifiedBy", actor)
                .addValue("id", orderId)
                .addValue("expectedVersion", expectedVersion);

        int updated = jdbc.update(sql, parameters);

        if (updated != 1) {
            throw new OptimisticLockingFailureException(
                    "Order changed or does not exist: " + orderId
            );
        }
    }
}
```

This example illustrates three responsibilities of a direct-write path:

- Obtain timestamp and actor from trusted application components.
- Update audit columns.
- Use a version predicate and increment the version atomically.

`Clock`, `CurrentActor`, exception handling, and timestamp types should be adapted to your application. `@Transactional` ensures the statement joins a Spring transaction when the template and transaction manager share the same `DataSource`.

If the statement modifies a child table instead of the root table, you must also protect the aggregate root's version. One approach is to increment the root version with `WHERE id = :id AND version = :expectedVersion` before updating the child, in the same transaction. If the child update fails, the transaction rolls back the version bump as well. Every writer mutating the aggregate must obey the same version protocol.

## 7. Direct Updates on a Child Collection: Protecting the Root Version

Suppose `OrderLine` is managed by `PurchaseOrder` via `@MappedCollection`. If a command directly updates the `order_lines` table, incrementing only a child version or ignoring the root version may fail to protect an aggregate snapshot loaded earlier.

For example, another transaction read the aggregate at version 10. Direct SQL updates an order line without incrementing `orders.version`. Then the old transaction saves the aggregate with version 10; Spring Data JDBC may still consider the root version valid and synchronize the collection back to the stale state.

To avoid this, direct child writes must coordinate the version on the root:

```sql
BEGIN;

UPDATE orders
SET version = version + 1,
    last_modified_at = :modifiedAt,
    last_modified_by = :modifiedBy
WHERE id = :orderId
  AND version = :expectedVersion;

-- Only proceed if the root UPDATE affected exactly one row.

UPDATE order_lines
SET quantity = :quantity
WHERE id = :lineId
  AND order_id = :orderId;

COMMIT;
```

This illustrates SQL for a transaction checking each statement's result. If the root update does not affect exactly one row, stop and roll back. If the child update does not affect exactly one row, handle the business error and roll back the version bump.

However, if children are frequently updated independently, that may be a sign `OrderLine` needs its own aggregate boundary. Do not maintain multiple write paths into children of the same aggregate without a unified version rule.

## 8. `@Modifying @Query` Is Also Direct DML

Direct writes are not limited to `JdbcTemplate`. Spring Data JDBC can use `@Modifying` with `@Query` to perform explicit UPDATE/DELETE operations.

Example:

```java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    @Modifying
    @Query("""
        UPDATE orders
        SET status = :status
        WHERE id = :id
        """)
    int updateStatusDirectly(
            @Param("id") Long id,
            @Param("status") String status
    );
}
```

This method instructs the database to execute SQL directly. It is not equivalent to loading `PurchaseOrder`, calling a domain method, and calling `save(...)`.

If you use this type of query in production applications, carefully evaluate:

- Must audit columns be updated?
- Must the version be checked and incremented?
- Is a current-status condition needed to protect invariants?
- Are there child rows or auxiliary tables that must be updated in the same transaction?
- Must a domain event or outbox record be written?
- How is the return count handled if no matching row exists?

You can add version and auditing directly in the SQL:

```sql
UPDATE orders
SET status = :status,
    last_modified_at = :modifiedAt,
    last_modified_by = :modifiedBy,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
```

Annotation names and parameter declarations must match your Spring Data JDBC version. The key point is that DML is still governed by the SQL statement; annotations do not automatically inject auditing or version protocols into the SQL content.

## 9. When to Use Aggregate Save vs. Direct Write?

| Situation | Usually appropriate choice | Reason |
|---|---|---|
| Status change requiring domain invariant checks | Load aggregate, call domain method, save | Preserves domain behavior and lifecycle |
| Updating a simple, independent counter | Direct SQL with appropriate version/audit | Avoids loading/saving the entire aggregate |
| Batch updating many rows by condition | Intentional SQL/batch operation | Reduces round trips and controls performance |
| Modifying one child in a small aggregate | Aggregate save | Keeps operation inside the aggregate boundary |
| Very large child collection frequently updated piecemeal | Revisit aggregate boundary; consider extracting child as its own root | Avoids rewriting large collections |
| Auditing callbacks and callback logic are required | Aggregate-aware save | Callbacks are invoked during lifecycle |
| Custom query command needed while keeping version | `@Modifying`/`JdbcTemplate` with handwritten version predicate | Direct DML can be safe if protocol is followed |
| Deleting root together with children | Repository aggregate delete or explicit SQL/FK policy | Direct DELETE does not read `@MappedCollection` automatically |

There is no rule to "always use repository" or "always use direct SQL". Choose based on business boundaries, aggregate size, and the guarantees the use case requires.

## 10. Domain Events, Outbox, and Side Effects

Entity callbacks, auditing, and optimistic locking are not all the side effects of a business operation.

For example, when an order transitions to `PAID`, the application may need to:

- Persist the order status.
- Record the audit actor/timestamp.
- Increment the version.
- Write a domain event or outbox message.
- Send a notification after the transaction commits.

If you only execute a direct UPDATE, the remaining steps do not happen automatically. If they are business requirements, organize an application service to coordinate all of them within an appropriate transaction.

### 10.1. Transactional Outbox

If you need to publish an event reliably alongside a database change, write an outbox row in the same transaction:

```sql
UPDATE orders
SET status = :status,
    version = version + 1,
    last_modified_at = :modifiedAt,
    last_modified_by = :modifiedBy
WHERE id = :id
  AND version = :expectedVersion;

INSERT INTO outbox_events (
    aggregate_type,
    aggregate_id,
    event_type,
    payload,
    created_at
)
VALUES (
    'PurchaseOrder',
    :id,
    'OrderStatusChanged',
    :payload,
    :modifiedAt
);
```

In code, insert the outbox record only when the order update succeeded on exactly one row. Both operations must share the same transaction. A separate publisher sends the outbox later and marks it processed under a retry/idempotency strategy.

Do not send a message to a broker before the transaction commits and assume a database rollback can retract the message. A database transaction does not roll back external side effects.

### 10.2. Callbacks Are Not an Event Bus for Every Write Path

If the application relies on `AfterSaveCallback` or application events emitted from aggregate persistence, direct SQL bypasses that emission path. If an event must be published for all writers, use a shared mechanism invoked by every writer, or place audit/outbox logic at the appropriate database/service boundary.

## 11. Risks of Mixing Multiple Write Paths

When the same table is written via both repositories and direct SQL, all writers must share one contract.

| Risk | Example | Mitigation |
|---|---|---|
| Missing audit data | `JdbcTemplate` updates only status | Write audit fields or use a consistent DB trigger |
| Lost update | Direct UPDATE filters only by ID | Use `WHERE id = ? AND version = ?` and increment version |
| Stale aggregate overwrites data | Direct child update does not bump root version | Bump root version in the same transaction |
| Bypassed domain invariants | SQL makes an invalid state transition | Validate via domain service or SQL predicate |
| Unsynchronized children | Direct root delete skips collection | Repository aggregate delete or FK/SQL cleanup |
| Callbacks do not run | Direct DML skips mapping lifecycle | Put necessary logic explicitly in service/SQL |
| Double-written audit | Both callback and trigger update it | Designate one authoritative source |
| Lost events | Direct update does not write outbox | Write outbox in the same transaction |
| Inconsistent timestamps | Callback uses `Clock`, SQL uses DB time | Choose one time source or clear conversion rules |
| Out-of-sync versions | One writer bumps version, another skips it | Require every write path to obey the version protocol |

In particular, optimistic locking is only meaningful when **every write path capable of conflict participates in the same version protocol**. Merely putting `@Version` on a class does not protect SQL statements that ignore the version column.

## 12. Testing Callbacks, Auditing, and Optimistic Locking

Test with database integration tests because these behaviors depend on real mapping, transactions, and SQL.

### 12.1. Verifying Auditing Through the Repository

Create a new aggregate and save it. Verify:

- `createdAt` and `createdBy` are populated.
- `lastModifiedAt` and `lastModifiedBy` hold expected configured values.
- On subsequent saves, created fields remain unchanged.
- Modified fields update to the new timestamp/actor.

In tests, you can supply a fixed `AuditorAware` for deterministic results instead of depending on a logged-in user.

### 12.2. Verifying Direct DML Does Not Invoke Callbacks Automatically

You can create a callback that counts invocations in tests:

```java
@Component
public class CallbackCounter
        implements BeforeConvertCallback<PurchaseOrder> {

    private final AtomicInteger calls = new AtomicInteger();

    @Override
    public PurchaseOrder onBeforeConvert(PurchaseOrder aggregate) {
        calls.incrementAndGet();
        return aggregate;
    }

    public int count() {
        return calls.get();
    }

    public void reset() {
        calls.set(0);
    }
}
```

After resetting the counter:

- Call repository `save(...)` and confirm the callback is invoked per lifecycle.
- Call `JdbcTemplate.update(...)` and confirm the callback counter does not increase.
- Inspect audit columns after direct DML; if the SQL did not update them, values do not change automatically.

This counter example is test instrumentation. Do not use a singleton counter in production to drive business logic.

### 12.3. Verifying Optimistic Locking

Scenario:

1. Load the same aggregate twice so you have two objects with the same version.
2. Save the first object.
3. Save the second object.
4. Confirm the second save throws an optimistic locking failure.

### 12.4. Verifying Direct Updates with a Version Predicate

Create a row at version 5 and run a direct UPDATE with expected version 5:

- The update count must equal 1.
- The new version must be 6.
- Running again with expected version 5 must return an update count of 0.
- An aggregate previously loaded at version 5 must fail to save after the direct update if saving goes through `@Version`.

Also verify audit fields and transaction rollback when the update count is unexpected.

## 13. Checklist Before Taking Direct Writes to Production

Before replacing an aggregate save with direct DML, answer these questions clearly:

1. **Invariants:** Does the SQL enforce domain conditions before modifying data?
2. **Callbacks:** Is there any callback logic the new path must replicate?
3. **Auditing:** Who writes `last_modified_at` and `last_modified_by`?
4. **Version:** Does the SQL filter by the old version and increment the new version?
5. **Children:** Are there dependent rows that must be updated or deleted with the root?
6. **Transaction:** Are related statements in the same transaction?
7. **Events/outbox:** Are there side effects that must be written in the same transaction?
8. **Concurrency:** Do all other writers obey the same version protocol?
9. **Return value:** How are update counts of 0 or greater than 1 handled?
10. **Testing:** Are there integration tests for stale versions, auditing, and rollback?

## 14. Key Principles to Remember

- Repository aggregate `save` and `JdbcAggregateTemplate` go through the Spring Data JDBC lifecycle; direct SQL via `@Modifying`, `JdbcTemplate`, or JDBC does not automatically run that lifecycle.
- Entity callbacks such as `BeforeConvertCallback` and `BeforeSaveCallback` are invoked only in the corresponding mapping/persistence operations.
- Auditing annotations `@CreatedBy`, `@CreatedDate`, `@LastModifiedBy`, and `@LastModifiedDate` require the auditing infrastructure; direct DML must write audit fields explicitly or rely on an agreed database mechanism.
- `@Version` is not automatically recognized by the database. Spring Data JDBC uses it in aggregate-aware save/delete; direct DML must check the old version and increment the new version in SQL.
- For direct child updates, coordinate the aggregate root's version so stale aggregate snapshots cannot overwrite changes.
- Domain invariants, callback side effects, outbox writes, and transactions do not appear automatically when running a standalone UPDATE statement.
- When multiple write paths coexist, all of them must follow the same auditing, versioning, and ownership contract.

Direct SQL is a useful tool for narrow writes and performance optimization. Keep the boundary clear: Spring Data JDBC can automatically apply callbacks, auditing, and optimistic locking only when operations go through the lifecycle it manages. When bypassing aggregate save, put the necessary guarantees explicitly into your service and SQL statements, then test concurrency and auditing against a real database.
