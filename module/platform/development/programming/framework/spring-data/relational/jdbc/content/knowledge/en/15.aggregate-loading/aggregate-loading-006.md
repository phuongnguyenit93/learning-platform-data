# Falling Back to Traditional Loading and Verifying with SQL

In **Spring Data Relational JDBC**, an aggregate is loaded through its aggregate root together with the components belonging to its lifecycle. The framework may use traditional multi-SQL loading, or an optimization strategy such as **Single Query Loading** when the version, dialect, and aggregate structure satisfy supported conditions.

When the optimization strategy is disabled or the aggregate is ineligible, Spring Data JDBC uses traditional loading. This is normally valid behavior, not a mapping error. To understand what the application is actually doing, inspect the real SQL, cross-check database rows, and distinguish the number of SQL statements from the number of returned aggregates.

This lesson focuses on three things:

- Understanding traditional aggregate loading and why multiple SQL statements may be generated.
- Recognizing scenarios where single-query loading does not apply and interpreting the fallback to traditional loading.
- Verifying with SQL/logs to see what data is read, which foreign keys link tables, and where query costs lie.

## 1. How is an aggregate loaded?

An aggregate has a root and may contain value objects, child entities, or collections of child entities. Example:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── orderNumber
  ├── status
  └── lines (owned collection)
        ├── OrderLine
        ├── OrderLine
        └── OrderLine
```

Suppose the database has two tables:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL,
    status VARCHAR(30) NOT NULL
);

CREATE TABLE order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    purchase_order_id BIGINT NOT NULL
        REFERENCES purchase_order(id),
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12, 2) NOT NULL
);
```

Java mapping:

```java
import java.math.BigDecimal;
import java.util.List;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        String status,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines
) {}

public record OrderLine(
        Long id,
        String sku,
        Integer quantity,
        BigDecimal unitPrice
) {}
```

`PurchaseOrder` is the aggregate root. `OrderLine` belongs to the aggregate and is linked via the `purchase_order_id` column. The repository is declared for the root:

```java
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

When calling `findById`, the goal is to return a materialized `PurchaseOrder` along with its order lines. This does not mean all data must be read in a single SQL statement.

## 2. Traditional loading: root and related components

Under the traditional loading strategy, Spring Data JDBC loads an aggregate in conceptual steps:

1. Query the aggregate root row by ID or search criteria.
2. Read properties belonging to the root and identify which entities/collections need to be loaded.
3. Execute the necessary queries to retrieve child entities and associate them with the root.
4. Build the object graph in memory and return the aggregate to the application.

For example, when calling:

```java
PurchaseOrder order = repository.findById(orderId)
        .orElseThrow();
```

Illustrative SQL statements can look like:

```sql
-- Fetch the aggregate root.
SELECT id, order_number, status
FROM purchase_order
WHERE id = ?;

-- Fetch the order lines belonging to that root.
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = ?;
```

This is **illustrative SQL for a multi-statement loading strategy**, not a verbatim copy of the SQL generated by every Spring Data JDBC version. Actual SQL depends on the dialect, naming strategy, mapping, relationships within the aggregate, and framework version.

A point to remember: multiple SQL statements do not mean multiple aggregates. The two statements above can together construct **one** `PurchaseOrder` object in memory.

### 2.1. Why not use JOIN for every case?

If you hand-write a JOIN query:

```sql
SELECT
    o.id,
    o.order_number,
    o.status,
    l.id AS line_id,
    l.sku,
    l.quantity,
    l.unit_price
FROM purchase_order o
LEFT JOIN order_line l
    ON l.purchase_order_id = o.id
WHERE o.id = ?;
```

the database returns one row per order line. If an order has three lines, the root's information repeats three times in the result set. The mapper must group rows by root ID, identify children, handle the no-child case, and reconstruct the collection.

A multi-statement loading strategy can read the root once and then read the child set separately. This avoids processing a flat result set that repeats root data, while keeping mapping straightforward. In return, it can require extra round-trips to the database.

Therefore, SQL count is only part of the cost. You must also consider returned row count, result set size, duplicate data, indexes, latency, and the number of aggregates loaded.

## 3. Single Query Loading and its optimization goal

**Single Query Loading** is a Spring Data JDBC optimization strategy introduced in the Spring Data Relational 3.2 line. The idea is to read the root and a supported collection in one SQL statement instead of loading them across multiple round-trips. This strategy uses database/dialect SQL capabilities, including window functions, to represent collection elements in the result set and reconstruct the aggregate.

This is an optimization for certain aggregate shapes, not a mandatory rule for every entity. Applicability depends on the Spring Data Relational version, dialect, and aggregate structure. Common limitations include:

- The strategy must be enabled in the configuration of the version in use; do not assume every project uses it automatically.
- The dialect/database must support the required SQL features.
- The aggregate structure must fall within the scope supported by Single Query Loading. For example, aggregates with multiple collections or nested collections may not qualify in corresponding versions/implementations.
- Special mappings or relationship types not supported by the optimization strategy may require the traditional loading path.

Do not treat the conditions above as a fixed support list for all versions. When implementing, consult the documentation for the **exact Spring Data Relational version and dialect** in your project. Support capabilities evolve across versions.

### 3.1. When does it fall back to traditional loading?

Cases can be categorized as:

| Scenario | What happens | How to interpret |
|---|---|---|
| Single Query Loading is not enabled | Framework uses the default loading strategy | Multiple SQL statements are expected |
| Database/dialect does not support required features | Optimization strategy is not applied | Traditional path still ensures the aggregate is read |
| Aggregate does not fit the optimization strategy's limits | Framework uses traditional loading per version support | Not every aggregate can use a single statement |
| Using an API/repository or config that does not trigger the optimization | Load command goes through the traditional path | Verify the actual bean/configuration in use |

**Falling back to traditional loading does not mean the framework detected a data error.** It is a loading strategy choice based on capabilities and configuration.

Also distinguish fallback from SQL execution errors. If an optimized SQL statement was selected, sent to the database, and hit a syntax error, missing column, permission error, or driver error, do not assume Spring Data JDBC will automatically retry using the traditional strategy. Runtime SQL errors must generally be handled as query errors; inspect the underlying exception and logs to determine the actual execution path.

### 3.2. Why might an aggregate be ineligible?

Example of an aggregate with two collections:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderNote> notes
) {}
```

This is a root with two independent child sets. When joining both collections, if an order has 3 order lines and 4 notes, a flat result set can produce up to 12 row combinations from multiplying the two collections. The mapper must deduplicate copies of each child. A Single Query Loading strategy with aggregate shape limits may not handle this case; the traditional path reading each collection separately stays simple and avoids a Cartesian product in the result set.

Similarly, nested collections add another grouping level. Do not infer that simply because the database supports window functions, any arbitrary object graph can be loaded in a single query.

## 4. Verifying with SQL: checking what the database actually stores

Before drawing conclusions about how loading behaves, verify the data and relationships in the database. You can start by reading the root:

```sql
SELECT id, order_number, status
FROM purchase_order
WHERE id = 42;
```

Then read the children:

```sql
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = 42
ORDER BY id;
```

These two queries help confirm:

- Whether the root ID exists.
- How many children are attached to the root.
- Whether the back-reference holds the right root ID.
- Whether database column values match the expected object.

If the root exists but the child query returns no rows, the aggregate's collection can legitimately be empty. If children exist but their back-reference points to a different ID, the issue lies in the linked data or mapping/write logic.

### 4.1. Checking roots and child counts

Aggregate summary query:

```sql
SELECT
    o.id,
    o.order_number,
    COUNT(l.id) AS line_count
FROM purchase_order o
LEFT JOIN order_line l
    ON l.purchase_order_id = o.id
GROUP BY o.id, o.order_number
ORDER BY o.id;
```

`LEFT JOIN` retains orders that do not yet have order lines; `COUNT(l.id)` returns 0 for roots without children. Do not use `COUNT(*)` here if you want to count children, because for a root without children, `LEFT JOIN` still yields one row and `COUNT(*)` will return 1.

Check for orphan children without a valid root:

```sql
SELECT l.*
FROM order_line l
LEFT JOIN purchase_order o
    ON o.id = l.purchase_order_id
WHERE o.id IS NULL;
```

If `purchase_order_id` has an enforced database foreign key, this query normally returns no rows. If rows appear, check constraints, imported data, or whether the constraint is actually enabled/validated.

### 4.2. Verifying uniqueness when the relationship must be one-to-one

For one-to-many collections, multiple children per root are valid. If the relationship is one-to-one, check counts and `UNIQUE` constraints:

```sql
SELECT purchase_order_id, COUNT(*) AS child_count
FROM shipping_details
GROUP BY purchase_order_id
HAVING COUNT(*) > 1;
```

If this is a one-to-one relationship, the database should have `UNIQUE(purchase_order_id)` or use that column as the primary key. Seeing no duplicates in a current query does not substitute for a constraint; two transactions can still create duplicates in the future if the schema does not enforce the rule.

## 5. Verifying the strategy via SQL logs

Running direct SQL in a database console shows what data is stored, but **does not prove how many SQL statements the application sent**. To know which statements Spring Data JDBC executes, inspect JDBC logs or use a datasource proxy tool in a development environment.

Example temporary logging configuration in `application-dev.yml`:

```yaml
logging:
  level:
    org.springframework.jdbc.core: DEBUG
```

Depending on the Spring Framework version and how queries are executed, logs can show prepared/executed SQL statements. If you need deeper insight into parameter binding, TRACE-level loggers or a datasource proxy can help. Specific logger names and log levels should be confirmed against your project's version.

Common options:

- **Spring JDBC logging:** convenient for quick checks in local/dev.
- **Datasource proxy:** wraps `DataSource` to record SQL statements, timings, and call counts.
- **P6Spy:** a JDBC SQL-tracing tool useful when you want to see statements together with execution details.
- **Database query logs/statistics:** help inspect queries hitting the database, though configuration depends on the DBMS and environment.

Do not enable sensitive parameter logging in production. Bound values can contain emails, phone numbers, tokens, or personal data. SQL logging also increases log volume and can impact performance; enable it purposefully and turn it off when no longer needed.

### 5.1. Signs of the multi-statement loading strategy

When calling `findById` for an aggregate root with one collection, logs may show a pattern similar to:

```text
1. SELECT ... FROM purchase_order WHERE id = ?
2. SELECT ... FROM order_line WHERE purchase_order_id = ?
```

With multiple aggregate roots or multiple relationships, additional queries per root/property may appear. Actual counts depend on the loading path, batching behavior, mapping, and version. Do not simply count log lines without grouping by request or operation.

### 5.2. Signs of Single Query Loading

When the optimization strategy is enabled and the aggregate is eligible, logs may show a larger SQL query using joins/window functions or dialect-specific SQL constructs to represent the root and collections in the same result set.

Do not look for one fixed SQL string across all databases. Instead check:

1. Is there one aggregate query instead of separate root/child query sequences?
2. Does the SQL use the structures the dialect requires for Single Query Loading?
3. Does the returned result contain full root data and child elements?
4. Does the mapped object graph have the right child count and values?

A single long SQL statement does not automatically prove Single Query Loading is active. A custom query with a JOIN can also be one statement without going through the same aggregate mapping mechanism. Combine logs, actual configuration, and object results.

## 6. Comparing the two loading paths

| Criterion | Traditional loading | Single Query Loading when eligible |
|---|---|---|
| Number of round-trips | Can issue multiple statements for root and related parts | Aims for a single statement for supported aggregates |
| SQL structure | Separate root/child statements, relatively easy to read | More complex SQL, dialect-dependent |
| Support scope | General mapping loading path | Only supported aggregates/dialects |
| How to verify | Observe root and child queries | Observe the optimized query and object graph |
| Potential costs | Multiple round-trips; possible N+1 when loading many roots | Complex SQL/result set; root data may repeat per child |
| When optimization does not apply | This is the default loading path | Framework uses the traditional path per version capability |

Single Query Loading reduces round-trips but does not guarantee every query is faster. With very large collections, the result set remains large; the database still must read and send all required data. Measure in practice rather than optimizing statement count alone.

## 7. Checking SQL performance

Once you capture actual SQL from logs, inspect the execution plan on the target database. On PostgreSQL, you can use `EXPLAIN`:

```sql
EXPLAIN
SELECT id, purchase_order_id, sku, quantity, unit_price
FROM order_line
WHERE purchase_order_id = 42;
```

If child queries frequently filter by `purchase_order_id`, an index on this column can help:

```sql
CREATE INDEX idx_order_line_purchase_order_id
    ON order_line(purchase_order_id);
```

For one-to-one relationships, a PK/UNIQUE constraint on the back-reference usually creates an appropriate index depending on the database. Do not add duplicate indexes without reviewing existing constraints and execution plans.

Key things to check:

- Does the database use the foreign key index, or is it sequentially scanning a huge child table?
- Are estimated row counts close to actual workload row counts?
- Do joins/window functions cause significant sorting or memory spills?
- Does the result set repeat too much root data due to large collections?
- Do count/extra queries or other relationships account for most of the time?

`EXPLAIN ANALYZE` on PostgreSQL executes the statement to measure actual runtime. Use it only with safe read queries in suitable environments; for DML statements, it actually runs the statement and can cause side effects. Do not run ad-hoc tests recklessly in production.

## 8. Distinguishing fallback from data or SQL errors

Not every multi-SQL case is a fallback from Single Query Loading:

| Observation | Possible explanation | Further verification needed |
|---|---|---|
| Separate root query and child queries | Traditional loading path | Is the feature enabled; is the aggregate eligible? |
| Only root query, empty collection | Root has no children, or child query did not run/map | Check child table, FK, and mapping |
| Optimized SQL throws a syntax error | Mismatched dialect/config/version or broken SQL/schema | Read the root cause exception; do not assume automatic fallback |
| SQL succeeds but children are missing | Data, predicate, back-reference, or mapping mismatch | Query the child table directly by root ID |
| One JOIN query returns multiple rows | Could be a custom query or optimized loading strategy | Check SQL origin and how the mapper builds the aggregate |
| Many statements when calling `findAll` | Likely loading roots and relationships per aggregate | Group logs by operation and actual root count |

To reach the right conclusion, answer these in order:

1. Which repository method was called?
2. How many collections/references does the aggregate root need to load?
3. Is Single Query Loading enabled in the runtime configuration?
4. What Spring Data Relational version and dialect are in use?
5. What SQL is actually sent to the database?
6. Are root/child data in the database valid, and which keys link them?

## 9. Verification example from repository to database

Suppose we have a repository:

```java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
```

Service:

```java
import org.springframework.stereotype.Service;

@Service
public class PurchaseOrderQueryService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderQueryService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    public PurchaseOrder get(Long id) {
        return repository.findById(id)
                .orElseThrow();
    }
}
```

Perform verification in sequence:

1. Pick a known ID, such as `42`.
2. Run a direct SQL query to confirm root `purchase_order.id = 42` exists.
3. Run `order_line WHERE purchase_order_id = 42` to determine the expected child set.
4. Enable SQL logging in the dev profile.
5. Call `get(42)` once and group the SQL statements generated by that request.
6. Compare children in the returned object against the rows found via SQL.
7. Repeat with a root having no children and a root having many children.
8. If testing Single Query Loading, confirm the flag is enabled and the aggregate/dialect are within supported scope, then compare logs.

A verification result table can record:

| Root ID | Child rows in SQL | Children in object | SQL statements to read aggregate | Notes |
| ---: | ---: | ---: | ---: | --- |
| 42 | 3 | 3 | 2 | Example traditional loading |
| 43 | 0 | 0 | 2 | Root without children |
| 44 | 12 | 12 | 1 or more | Must cross-check strategy and actual logs |

Numbers in this table are illustrative sample data showing how to record findings, not benchmark results from a specific project. For root 44, SQL statement count cannot be deduced from child count alone.

## 10. Common pitfalls

| Symptom | Possible cause | How to address |
|---|---|---|
| Expected one query, saw multiple | Feature not enabled or aggregate/dialect unsupported | Check configuration, version, dialect, and aggregate shape |
| Assuming multiple SQL queries is a bug | Confusing default loading with single-query optimization | Check semantics and returned data before concluding |
| Enabled feature, no optimized SQL seen | Config not applied to active bean/repository or aggregate ineligible | Check runtime configuration and SQL logs for the exact request |
| Optimized SQL fails without fallback | Runtime errors do not necessarily trigger another loading path | Read the root cause; check dialect/schema and config |
| Collection is empty | No child rows, wrong FK, or wrong mapping column | Query the child table directly by root ID |
| Child count in object differs from SQL | Query/mapping, concurrent data change, or logs from another request | Use stable transactions/test fixtures and match specific IDs |
| Loading a list of many roots is very slow | Many related queries, missing indexes, or huge aggregates | Measure query counts, execution plans, indexes, and aggregate boundaries |
| SQL logs expose personal data | Uncontrolled trace/binding logging | Mask data, restrict environments, and disable logs after investigation |

## 11. Concise investigation workflow

When an aggregate loads traditionally despite expecting an optimization strategy:

1. **Identify versions:** check the actual Spring Data Relational version, not just the starter version in build files.
2. **Check configuration:** verify Single Query Loading is enabled on the repository/aggregate template infrastructure the application actually uses.
3. **Check aggregate shape:** are collection counts, nested collections, and special mappings within supported scope?
4. **Check dialect:** does the running database support the SQL features required by the strategy?
5. **Observe SQL:** enable logging or a datasource proxy in dev/test.
6. **Verify data:** query root and child tables directly by foreign key.
7. **Measure performance:** use execution plans, indexes, and returned row counts to find bottlenecks.

Do not alter schemas or add arbitrary JOINs just to make logs show fewer SQL statements. The goal is loading the right aggregate at an appropriate cost while preserving aggregate boundaries and data consistency.

## 12. Practice exercises

**Exercise 1 — Observing the default loading path.** Create a `PurchaseOrder` with a `lines` collection. Call `findById` with SQL logging enabled in the dev profile. Record the root query and child query.

**Exercise 2 — Verifying with SQL.** Choose a root ID. Run two separate queries to read the root and children. Compare the child row count with the number of elements in the Java object's collection.

**Exercise 3 — Root without children.** Create an order with no order lines. Confirm the root still loads and the collection is empty; distinguish this valid case from a mapping error.

**Exercise 4 — Aggregate with multiple collections.** Add a `notes` collection to the root. Check whether this structure still falls within Single Query Loading scope for your version; observe the actual loading path.

**Exercise 5 — Reading execution plans.** Run `EXPLAIN` for the child query by `purchase_order_id`. Check indexes, estimated row counts, and the impact of a large child table.
