# Reusing Fragments Across Multiple Repositories

## 1. When Multiple Repositories Need the Same Capability

In Spring Data JDBC, each aggregate typically has its own repository. For example:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID> {
}

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {
}
~~~

As an application grows, multiple repositories may need the same additional capability:

- Writing an audit record for an operation performed.
- Providing a shared group of search methods.
- Performing a custom persistence operation following the same rules.
- Adding a technical API used by multiple aggregates.

Copying the same methods and implementations into each repository creates code duplication and makes them prone to drifting over time. Putting everything into one large base repository forces repositories to inherit methods unrelated to their aggregates.

**Repository fragments** are how Spring Data lets you compose additional capabilities into repositories. A fragment typically consists of an interface describing the contract and an implementation providing the behavior. Multiple repositories can inherit the same fragment interface; if the implementation is registered as a shared Spring bean, those repositories can share the same implementation.

This lesson explains how to design reusable fragments, how Spring Data composes fragments into repositories, conventions for locating implementations, how to share an implementation across multiple repositories, and what to watch out for when a fragment uses JDBC directly.

## 2. Repository Composition and Fragments

A Spring Data repository does not have to consist of only a single CRUD interface. A repository can be built by composing:

1. **Repository base interface:** such as **CrudRepository<T, ID>**, providing basic operations.
2. **Repository fragment interface:** describing a set of additional capabilities.
3. **Fragment implementation:** implementing the fragment's methods.
4. **Repository base implementation:** the foundational implementation provided by the Spring Data module.

This can be visualized as:

~~~text
                   CustomerRepository
                           |
              +------------+------------+
              |            |            |
              v            v            v
        CrudRepository  AuditFragment  SearchFragment
              |            |            |
              v            v            v
        CRUD support   AuditFragmentImpl SearchFragmentImpl
              \            |            /
               \           |           /
                +----------+----------+
                           |
                           v
                 Repository proxy
                           |
                           v
                        Service
~~~

When a service injects CustomerRepository, it receives a repository proxy containing both the CRUD methods and the methods from the composed fragments.

### 2.1. A Fragment Is a Composable Contract

A fragment interface simply describes a capability that a repository needs to add. It does not necessarily represent an aggregate, a table, or a standalone repository.

For example:

~~~java
public interface AuditFragment {

    void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    );
}
~~~

This is a capability that can be used across multiple repositories. The implementation decides how the audit entry is recorded.

### 2.2. A Repository Can Use Multiple Fragments

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID>,
                AuditFragment,
                CustomerSearchFragment {
}
~~~

The repository above combines CRUD, auditing, and customer search. Another repository can use AuditFragment without needing CustomerSearchFragment.

A fragment should only group methods with a single clear responsibility. Do not turn one fragment into a dumping ground for every custom method in the application.

## 3. Creating a Shared Fragment for Multiple Repositories

We will build an audit-writing fragment usable by both CustomerRepository and PurchaseOrderRepository. Audit rows are stored in a separate table, not as part of the Customer or PurchaseOrder aggregate.

### 3.1. Creating the Audit Table

Example schema:

~~~sql
CREATE TABLE repository_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    action VARCHAR(80) NOT NULL,
    occurred_at TIMESTAMP NOT NULL
);
~~~

Identity and timestamp types may need to be adjusted for your target database. This table stores the aggregate type, the ID as a string, the action, and the recorded timestamp.

### 3.2. Declaring the Fragment Interface

Create AuditFragment.java in a shared package:

~~~java
package com.example.shared.repository;

public interface AuditFragment {

    void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    );
}
~~~

The fragment accepts aggregateType and aggregateId explicitly. Because the two repositories may manage different ID types (UUID and Long), using a string in the audit contract gives the log table a single uniform format. The service is responsible for converting the ID to a string.

### 3.3. Writing the Implementation Once

Create AuditFragmentImpl.java:

~~~java
package com.example.shared.repository;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;

@Component
public class AuditFragmentImpl implements AuditFragment {

    private final JdbcTemplate jdbc;

    public AuditFragmentImpl(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Override
    public void appendAudit(
            String aggregateType,
            String aggregateId,
            String action
    ) {
        jdbc.update("""
                INSERT INTO repository_audit (
                    aggregate_type,
                    aggregate_id,
                    action,
                    occurred_at
                )
                VALUES (?, ?, ?, CURRENT_TIMESTAMP)
                """,
                aggregateType,
                aggregateId,
                action
        );
    }
}
~~~

By default, the implementation name follows the convention of fragment interface name plus the Impl postfix: AuditFragment → AuditFragmentImpl. @Component registers the implementation as a Spring bean so it can be reused. Constructor injection provides JdbcTemplate.

This implementation does not hold per-request state in fields; it only holds shared dependencies and builds the statement per call. Because Spring beans are singletons by default, a shared implementation must be safe under concurrent calls from multiple requests.

### 3.4. Extending the Fragment in the First Repository

~~~java
package com.example.customer;

import java.util.UUID;

import com.example.shared.repository.AuditFragment;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, UUID>, AuditFragment {
}
~~~

### 3.5. Extending the Same Fragment in the Second Repository

~~~java
package com.example.orders;

import com.example.shared.repository.AuditFragment;
import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long>, AuditFragment {
}
~~~

Both repositories gain the appendAudit(...) method. There is no need to create CustomerAuditFragment and PurchaseOrderAuditFragment if the contract and behavior are genuinely identical.

## 4. Using the Fragment from Repositories

Services can invoke fragment methods just like regular repository methods:

~~~java
@Service
public class CustomerService {

    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer register(Customer customer) {
        Customer saved = customers.save(customer);

        customers.appendAudit(
                "Customer",
                saved.id().toString(),
                "CREATED"
        );

        return saved;
    }
}
~~~

Another service using the same fragment:

~~~java
@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository orders;

    public PurchaseOrderService(PurchaseOrderRepository orders) {
        this.orders = orders;
    }

    @Transactional
    public PurchaseOrder create(PurchaseOrder order) {
        PurchaseOrder saved = orders.save(order);

        orders.appendAudit(
                "PurchaseOrder",
                saved.id().toString(),
                "CREATED"
        );

        return saved;
    }
}
~~~

The two services use two different repositories, yet the audit-writing logic is implemented once in AuditFragmentImpl.

### 4.1. Does the Fragment Need to Know the Specific Repository?

Not necessarily. This example passes aggregateType and aggregateId into the method, so the implementation does not need to know whether it is composed into CustomerRepository or PurchaseOrderRepository.

Advantages:

- No dependency on specific domain classes.
- Reusable across multiple ID types.
- No separate implementation needed per repository.
- Can be tested independently by verifying the audit insert statement.

The trade-off is that callers must pass the right aggregateType. If the aggregate type name is critical data, an enum or value object can be used instead of a free-form string to reduce typos.

## 5. Reusing a Fragment Implementation Across Multiple Repositories

There are two aspects to distinguish:

- **Contract reuse:** multiple repositories extend the same fragment interface.
- **Implementation reuse:** multiple repositories share the same implementation bean.

In the example, CustomerRepository and PurchaseOrderRepository both extend AuditFragment. AuditFragmentImpl is registered as a shared Spring bean. Spring Data repository composition weaves that capability into both repositories.

### 5.1. Why Register the Implementation as a Bean?

A fragment implementation is a regular Spring bean. When managed by Spring:

- Dependencies such as JdbcTemplate, services, or publishers can be injected.
- It can be injected into other beans if needed.
- It can be reused by multiple repositories sharing the same fragment interface.
- Spring-managed bean configuration, proxies, and lifecycle apply.

In a project, @Component is one way to register it. You can also declare it via @Bean in configuration if special constructor or dependency setup is needed. When declaring manually, ensure the bean is named and discovered by Spring Data according to the fragment conventions of the version in use.

### 5.2. Package and Naming Conventions

Spring Data typically locates fragment implementations by naming convention and repository configuration scope. By default, the implementation postfix is Impl:

| Fragment Interface | Default Implementation |
| --- | --- |
| AuditFragment | AuditFragmentImpl |
| CustomerSearchFragment | CustomerSearchFragmentImpl |
| SoftDeleteFragment | SoftDeleteFragmentImpl |

The implementation is placed in a package recognized by component scanning and repository configuration. If the fragment lives in a shared package, make sure that package is scanned or register the implementation explicitly as a bean.

If the project changes the repository implementation postfix, the fragment implementation class name must match the configured postfix. Do not change the postfix arbitrarily and expect Spring Data to find it automatically.

### 5.3. A Shared Implementation Must Be Stateless or Thread-Safe

Because a single singleton bean may serve multiple repositories and concurrent requests, do not store per-call data in mutable fields:

~~~java
// Avoid: state from one request can be overwritten by another request.
private String currentAggregateId;
~~~

Instead:

- Pass data through method parameters.
- Keep dependencies immutable in final fields.
- Let transactions/context be managed at the appropriate layer.
- If repository-specific configuration is needed, use dedicated implementations/fragments or pass configuration explicitly.

## 6. Sharing a Fragment While Still Allowing Custom Behavior

Not every repository has to use the exact same implementation. There are three common scenarios.

### Scenario A — Identical Contract and Implementation

For example AuditFragment: every repository writes audit rows with the same schema and rules. Use one fragment interface and one shared implementation bean.

### Scenario B — Shared Contract, Different Implementations

Two repositories need the same capability, but how it is carried out depends on the domain or database schema. You can define a shared contract and then provide appropriate implementations per repository configuration, or create specialized fragments extending the shared contract.

For example:

~~~java
public interface SearchFragment<T> {
    List<T> search(String term);
}

public interface CustomerSearchFragment
        extends SearchFragment<Customer> {
}

public interface ProductSearchFragment
        extends SearchFragment<Product> {
}
~~~

Then each specialized fragment has its own implementation. This avoids forcing a generic implementation to guess the domain type or table name at runtime.

### Scenario C — Shared Logic Belongs in a Service, Not a Repository

If a capability is not part of a data access contract, do not force it into a repository fragment. For example, name normalization, authorization checks, sending emails, or orchestrating business workflows usually fit better in an application/domain service.

A fragment should represent a capability that callers reasonably expect to invoke through a repository. If a method is purely a Java utility unrelated to persistence, a separate component/service makes the API clearer.

## 7. Shared Fragments with Generic Types

A fragment can declare generic parameters when the contract genuinely applies to multiple domain types:

~~~java
public interface ValidationFragment<T> {

    void validateBeforeWrite(T aggregate);
}
~~~

Implementation:

~~~java
public class ValidationFragmentImpl<T>
        implements ValidationFragment<T> {

    private final AggregateValidator<T> validator;

    public ValidationFragmentImpl(AggregateValidator<T> validator) {
        this.validator = validator;
    }

    @Override
    public void validateBeforeWrite(T aggregate) {
        validator.validate(aggregate);
    }
}
~~~

This is an example of a generic contract and shared dependency. In practice, picking the right validator for each aggregate requires an explicit resolution mechanism, such as a domain-type registry or specialized implementations. Do not assume Spring Data automatically injects the concrete domain type into a generic fragment implementation's constructor.

If each aggregate has its own validator, a cleaner design is using specialized fragments or calling the validator in an application service before saving. Do not create a generic fragment just to save a few lines of code if type resolution makes the implementation hard to follow.

## 8. Combining Multiple Fragments in the Same Repository

A repository can combine multiple independent fragments:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, UUID>,
                AuditFragment,
                CustomerSearchFragment,
                CustomerExportFragment {
}
~~~

Each fragment should have one responsibility:

| Fragment | Responsibility |
| --- | --- |
| AuditFragment | Recording audit operations |
| CustomerSearchFragment | Searching customers with specialized search rules |
| CustomerExportFragment | Querying data for export |

There is no need to create a single interface with dozens of custom methods. Splitting capabilities lets each repository compose only the parts it actually needs.

### 8.1. Duplicate Method Signatures Across Fragments

If multiple fragments provide methods with identical signatures, composition can become confusing because fragment order affects which implementation gets selected. Avoid designing two unrelated fragments that declare the same method signature expecting Spring Data to infer intent.

If you truly need to override a method, define precedence clearly and test the repository composition. In most cases, renaming the method or consolidating the contract is easier to maintain.

## 9. How Do Fragments Differ from @NoRepositoryBean?

Both mechanisms use interfaces, but they serve different purposes:

| Mechanism | Purpose | Example |
| --- | --- | --- |
| Generic base repository + @NoRepositoryBean | Share a foundational contract across child repositories | BaseRepository<T, ID> |
| Repository fragment | Compose an optional capability into a repository | AuditFragment |
| Repository fragment implementation | Provide behavior for the capability | AuditFragmentImpl |
| Custom repository base class | Change the foundational implementation used by repository proxies | A custom base class extending the module's appropriate implementation |

A base repository is typically a common parent of repositories. A fragment is a modular piece that can be attached or omitted as needed. A fragment interface does not need to be treated as a standalone repository; do not add @NoRepositoryBean just because its name ends with Repository or because multiple repositories extend it.

For example:

~~~java
@NoRepositoryBean
public interface BaseRepository<T, ID>
        extends CrudRepository<T, ID> {
    // Shared contract for all child repositories.
}

public interface AuditFragment {
    void appendAudit(String type, String id, String action);
}

public interface CustomerRepository
        extends BaseRepository<Customer, UUID>, AuditFragment {
}
~~~

Here, the base repository provides the general CRUD contract; the audit fragment provides an additional capability.

## 10. Fragments and Default Methods

Some logic can be written directly as Java default methods:

~~~java
public interface FindRequiredById<T, ID> {

    Optional<T> findById(ID id);

    default T findRequiredById(ID id) {
        return findById(id).orElseThrow();
    }
}
~~~

Default methods fit when logic is simple and can be built from other methods. Fragment implementations fit when dependencies, SQL, services, or dedicated algorithms are needed.

There is no need to create an implementation class for a method that just calls findById and throws an exception if a default method already conveys the intent clearly. Conversely, a fragment using JdbcTemplate or a publisher needs an implementation to supply the behavior.

## 11. Using JDBC Directly in a Fragment: Transactions and Aggregate Boundaries

The AuditFragmentImpl example uses JdbcTemplate to write to the audit table. If a service calls save and appendAudit in the same @Transactional method, both operations can participate in the same transaction when:

- The repository and JdbcTemplate use the same DataSource.
- They use the corresponding transaction manager.
- The calls execute within an active transaction boundary.

Then, if the audit insert fails and the exception triggers a rollback, the aggregate save operation also rolls back.

However, JdbcTemplate does not perform aggregate mapping. It does not invoke domain behavior, synchronize child collections, or apply the optimistic locking of the aggregate save path. Therefore:

- Only use direct JDBC in a fragment when the capability genuinely operates on tables outside the aggregate or when write rules have been explicitly designed.
- If a fragment needs to modify an aggregate, consider JdbcAggregateTemplate or delegating to the responsible application/domain service.
- Do not use a fragment as a shortcut to update child tables while bypassing aggregate root invariants.
- Do not assume @Transactional on a fragment method automatically solves all transaction concerns; define boundaries at the use case level with the same transaction manager.

## 12. When Is a Fragment Not the Right Choice?

Not all shared code should be a repository fragment.

| Need | Typically Better Option |
| --- | --- |
| Sharing a generic CRUD contract | Base repository interface |
| Adding a repository capability with an implementation | Repository fragment |
| Changing how every repository implements core methods | Custom repository base class |
| Coordinating multiple repositories or aggregates | Application service |
| Enforcing invariants of a single aggregate | Domain model / domain service |
| Sending email, calling HTTP, or publishing messages | Application service / event publisher / outbox |
| Complex reporting queries outside an aggregate | DAO using JdbcTemplate or dedicated query |
| Pure Java utility functions | Appropriate component / service / helper |

A fragment should not become a place that orchestrates an entire use case. For example, approveOrderAndNotifyCustomer() usually belongs in an application service because it coordinates order changes, auditing, and notifications; do not push that entire workflow into a repository just for reuse.

## 13. Testing Shared Fragments

Test both the implementation and the composition of the fragment into each repository.

### 13.1. Testing the Implementation

For AuditFragmentImpl, an integration test with a database can verify that one call creates exactly one audit row:

~~~java
@DataJdbcTest
class AuditFragmentImplTest {

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void writesAuditEntry() {
        AuditFragment fragment = new AuditFragmentImpl(jdbc);

        fragment.appendAudit("Customer", "customer-42", "CREATED");

        Integer count = jdbc.queryForObject("""
                SELECT COUNT(*)
                FROM repository_audit
                WHERE aggregate_type = ?
                  AND aggregate_id = ?
                  AND action = ?
                """,
                Integer.class,
                "Customer",
                "customer-42",
                "CREATED"
        );

        assertThat(count).isEqualTo(1);
    }
}
~~~

This is an illustrative skeleton; the test requires appropriate schema and assertion dependencies in your project. If the implementation is injected via Spring, you can use a context test to verify wiring rather than instantiating it directly as shown.

### 13.2. Testing Repository Composition

Verify that both repositories can invoke the fragment method:

~~~java
@SpringBootTest
class SharedAuditFragmentIntegrationTest {

    @Autowired
    CustomerRepository customers;

    @Autowired
    PurchaseOrderRepository orders;

    @Test
    void fragmentIsAvailableOnBothRepositories() {
        customers.appendAudit("Customer", "c-1", "CREATED");
        orders.appendAudit("PurchaseOrder", "42", "CREATED");

        // Read the audit table and verify both entries exist.
    }
}
~~~

This test verifies that Spring Data composed the fragment into both repositories. It also catches package scanning, implementation naming, or bean wiring errors.

### 13.3. Testing Shared Transactions

Add a service integration test to verify:

1. The service saves the aggregate.
2. The fragment writes the audit record.
3. Deliberately force the audit insert to fail.
4. The transaction rolls back both operations if they share the same DataSource/transaction manager.

Do not only test the fragment method in isolation; testing the use case proves the designed transaction boundary.

## 14. Common Errors

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Repository lacks the fragment method | Repository does not extend the fragment interface or composition could not find the implementation | Check extends, implementation name, package scan, and bean registration. |
| Spring cannot find the fragment implementation | Class name does not follow postfix or class is outside scan scope | Use FragmentNameImpl naming, configure the right postfix, or register the bean by convention. |
| Two repositories share the fragment but one fails | Fragment implementation is only scanned in one package scope | Place implementation in a commonly scanned package or register a shared bean. |
| Implementation does not receive injected dependencies | Class was instantiated outside the Spring context or miswired | Register implementation as a Spring bean and use constructor injection. |
| Request data leaks across repositories | Singleton implementation stores mutable per-call state | Keep implementation stateless/thread-safe; pass state via parameters. |
| Method is overridden by another implementation | Multiple fragments share the same method signature | Avoid duplicate signatures or define explicit composition order and test it. |
| Fragment uses JDBC and aggregate becomes inconsistent | Direct SQL bypasses invariants or versioning | Switch to aggregate operations or explicitly guard conditions/version. |
| Audit commits even though aggregate rolls back | Both operations use different transaction managers/resources or independent propagation | Use the same DataSource/transaction manager and appropriate propagation. |
| Fragment contains too much business logic | Repository is being used like an application service | Move orchestration to a service; keep the fragment as a clear data access capability. |

## 15. Workflow for Designing a Reusable Fragment

When you notice multiple repositories duplicating code, follow this sequence:

1. **Identify the capability:** do the repositories genuinely need the same behavior, or do they just happen to have similarly named methods?
2. **Create a small interface:** describe the contract independently of a specific aggregate if possible.
3. **Choose the implementation:** share one implementation if semantics match; otherwise, create specialized fragments.
4. **Manage the bean:** register the implementation via component scanning or appropriate Spring configuration.
5. **Compose into repositories:** have each repository needing the capability extend the fragment interface.
6. **Verify composition:** confirm the method appears on the repository proxy and does not collide with other methods.
7. **Define transactions:** if the fragment writes to the database, ensure it participates in the use case's transaction when needed.
8. **Protect aggregates:** do not let direct SQL violate invariants or bypass versioning.
9. **Test reuse:** test all repositories using the fragment, not just the standalone implementation.

## 16. Practice Exercises

**Exercise 1 — Create a shared fragment.** Create AuditFragment and AuditFragmentImpl, then have both CustomerRepository and PurchaseOrderRepository extend the fragment.

**Exercise 2 — Verify composition.** Inject both repositories and call appendAudit. Verify that the repository proxies expose the method from the fragment.

**Exercise 3 — Shared bean.** Register the implementation as a Spring bean, inject JdbcTemplate via constructor, and verify the implementation can be used by both repositories.

**Exercise 4 — Second fragment.** Create SearchFragment for a genuinely shared search capability. Explicitly decide whether the implementation can be shared or needs domain-specific implementations.

**Exercise 5 — Colliding method signatures.** Create two fragments declaring the same method signature, observe the composition, and explain why this design should be avoided or how to establish explicit precedence.

**Exercise 6 — Transactions.** Call aggregate save and appendAudit in the same @Transactional service. Force the audit insert to fail and verify the aggregate rolls back on the same database.

**Exercise 7 — Choosing the right abstraction.** Given a convenience method, a reporting query, a shared repository capability, and a use case coordinating multiple aggregates, decide whether to use a default method, DAO, fragment, or application service.

## 17. Key Takeaways

Repository fragments let you compose a custom capability into repositories without dumping every method into one large base interface. Multiple repositories can extend the same fragment interface; if the implementation has identical semantics and is registered as a Spring bean, they can share a single implementation.

Keep fragment interfaces small, name implementations according to convention, ensure packages/beans are discovered by Spring Data, and keep shared implementations safe under concurrency. Use fragments for behavior that truly belongs to the repository contract; let application services orchestrate use cases and let aggregate roots protect invariants. If a fragment uses JDBC directly, proactively manage transactions, versioning, and the rules normally handled by the aggregate persistence path.
