# Kiểm thử optimistic locking, khóa bi quan và xung đột đồng thời

Spring Data JDBC hỗ trợ hai chiến lược chính để bảo vệ dữ liệu khi nhiều transaction cùng truy cập một aggregate:

- **Optimistic locking** dùng thuộc tính version để phát hiện một transaction đang ghi dựa trên trạng thái cũ.
- **Pessimistic locking** yêu cầu database khóa hàng khi đọc để transaction khác phải chờ hoặc không thể lấy khóa tương ứng.

Hai cơ chế này có hành vi khác nhau. Optimistic locking cho phép nhiều transaction cùng đọc, sau đó phát hiện xung đột ở thời điểm ghi. Pessimistic locking giữ khóa trong transaction để hạn chế các transaction khác sửa dữ liệu đang được xử lý.

Kiểm thử concurrency phải tạo được các transaction và JDBC connection độc lập. Một unit test gọi hai lần repository tuần tự hoặc mock exception không chứng minh database thực sự phát hiện xung đột hay giữ khóa đúng cách.

Bài học trình bày cách kiểm thử stale update, kiểm thử hai transaction cập nhật cùng aggregate, kiểm thử khóa bi quan bằng Spring Data JDBC, và cách tổ chức integration test để kết quả có thể lặp lại.

## 1. Phân biệt optimistic locking và pessimistic locking

Giả sử tồn kho một sản phẩm đang là 10.

Hai request đồng thời muốn giữ 7 đơn vị. Nếu cả hai cùng đọc 10 rồi cùng ghi kết quả 3 mà không có concurrency control, hệ thống có thể chỉ ghi nhận một lần giảm. Kết quả database không phản ánh tổng số hàng đã giữ.

### 1.1. Optimistic locking

Optimistic locking giả định xung đột không thường xuyên. Transaction đọc aggregate mà không giữ khóa dài hạn. Khi ghi, Spring Data JDBC kiểm tra version:

~~~text
Transaction A                 Transaction B
-------------                 -------------
Read quantity = 10            Read quantity = 10
Read version = 5              Read version = 5
Save with version = 5
Success, version = 6
                              Save with version = 5
                              No row matches
                              OptimisticLockingFailureException
~~~

Một transaction thành công. Transaction còn lại nhận lỗi optimistic locking và phải tải lại dữ liệu nếu use case có thể retry.

### 1.2. Pessimistic locking

Pessimistic locking yêu cầu database khóa hàng khi transaction đọc dữ liệu cần sửa:

~~~text
Transaction A                 Transaction B
-------------                 -------------
BEGIN
SELECT ... FOR UPDATE
Lock acquired
                              BEGIN
                              SELECT ... FOR UPDATE
                              Wait for lock
Update quantity
COMMIT
                              Lock acquired
                              Read current row
                              Continue or revalidate
                              COMMIT
~~~

Transaction B phải chờ cho đến khi A commit/rollback hoặc hết thời gian chờ khóa. Hành vi cụ thể phụ thuộc database, dialect, isolation level và loại khóa.

### 1.3. So sánh

| Tiêu chí | Optimistic locking | Pessimistic locking |
| --- | --- | --- |
| Thời điểm phát hiện/giải quyết | Kiểm tra version lúc ghi | Lấy khóa trước khi xử lý |
| Khóa hàng trong lúc đọc | Không cần khóa dài hạn | Có |
| Khi có xung đột | Một thao tác ghi thất bại | Transaction khác chờ hoặc timeout |
| Phù hợp | Xung đột ít, đọc nhiều | Contention cao hoặc critical section ngắn |
| Chi phí chính | Retry/reload khi conflict | Lock wait, deadlock, giữ connection |
| Cách kiểm thử | Hai bản sao cùng version | Hai transaction giữ/yêu cầu cùng lock |

Không có chiến lược tốt nhất cho mọi use case. Cần chọn theo tần suất xung đột, thời gian xử lý, mức độ quan trọng của invariant và khả năng retry.

## 2. Bật optimistic locking với @Version

Spring Data JDBC hỗ trợ optimistic locking bằng thuộc tính số được đánh dấu @Version trên aggregate root.

Ví dụ aggregate:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("inventory_items")
public record InventoryItem(
        @Id Long id,
        String sku,
        int availableQuantity,
        @Version Long version
) {

    public InventoryItem reserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "Quantity must be positive"
            );
        }

        if (availableQuantity < quantity) {
            throw new InsufficientStockException(sku);
        }

        return new InventoryItem(
                id,
                sku,
                availableQuantity - quantity,
                version
        );
    }
}
~~~

Schema:

~~~sql
CREATE TABLE inventory_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    sku VARCHAR(80) NOT NULL UNIQUE,
    available_quantity INTEGER NOT NULL
        CHECK (available_quantity >= 0),
    version BIGINT NOT NULL
);
~~~

Khi lưu aggregate mới, Spring Data JDBC khởi tạo version theo cơ chế new-entity. Khi cập nhật aggregate đã tồn tại, câu UPDATE kiểm tra version hiện tại trong database và tăng version khi thành công.

Không tự tăng version trong domain method. Version là metadata persistence phục vụ kiểm soát cạnh tranh.

### 2.1. Version check áp dụng cho update và delete

Spring Data JDBC kiểm tra version khi update aggregate root. Nếu version trong database khác version của object được lưu, thao tác thất bại với OptimisticLockingFailureException.

Version check cũng áp dụng khi delete aggregate versioned. Khi xóa, version được kiểm tra nhưng không tăng vì bản ghi bị xóa.

Vì vậy, test cần bao gồm cả:

- Hai object cùng version cập nhật cùng aggregate.
- Một object cũ cập nhật sau khi object khác đã save.
- Một object cũ xóa aggregate sau khi aggregate đã được cập nhật.

### 2.2. Version là thuộc tính của aggregate root

Đặt @Version trên aggregate root mà Spring Data JDBC dùng để xác định optimistic locking cho aggregate. Không coi version của một child object là cơ chế khóa độc lập cho toàn bộ aggregate.

Nếu nghiệp vụ cần kiểm soát đồng thời ở mức một bảng con hoặc một tài nguyên riêng, hãy xác định rõ ranh giới aggregate và cách cập nhật dữ liệu đó.

## 3. Kiểm thử stale update theo cách tuần tự

Đây là bài test cơ bản, có tính xác định cao. Nó tạo hai bản sao cùng version, lưu bản thứ nhất rồi thử lưu bản thứ hai đã cũ.

Repository:

~~~java
import java.util.Optional;

import org.springframework.data.repository.CrudRepository;

public interface InventoryRepository
        extends CrudRepository<InventoryItem, Long> {

    Optional<InventoryItem> findBySku(String sku);
}
~~~

Integration test:

~~~java
@SpringBootTest
class InventoryOptimisticLockingTest {

    @Autowired
    InventoryRepository repository;

    @Test
    void rejectsSaveUsingStaleVersion() {
        InventoryItem created = repository.save(
                new InventoryItem(
                        null,
                        "SKU-01",
                        10,
                        null
                )
        );

        InventoryItem firstRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem secondRead =
                repository.findById(created.id()).orElseThrow();

        InventoryItem firstChange = firstRead.reserve(2);
        repository.save(firstChange);

        InventoryItem staleChange = secondRead.reserve(3);

        assertThrows(
                OptimisticLockingFailureException.class,
                () -> repository.save(staleChange)
        );

        InventoryItem current =
                repository.findById(created.id()).orElseThrow();

        assertEquals(8, current.availableQuantity());
    }
}
~~~

Test xác nhận:

1. Hai object được tải từ cùng một trạng thái.
2. Lần save đầu tăng version.
3. Lần save thứ hai dùng version cũ và bị từ chối.
4. Dữ liệu database giữ kết quả của lần save đầu.

Test này chứng minh optimistic locking hoạt động với object stale. Nó chưa mô phỏng hai transaction chạy cùng thời điểm.

### 3.1. Không đặt toàn bộ test trong một transaction ngoài

Đối với integration test concurrency, tránh đánh dấu test method hoặc class bằng @Transactional nếu điều đó khiến dữ liệu setup chưa commit trước khi worker thread khác đọc.

Spring transaction JDBC thường gắn với thread hiện tại. Transaction mở bởi test thread không tự truyền sang thread executor. Các transaction cần kiểm thử phải được mở độc lập trên từng thread hoặc bằng TransactionTemplate.

Có thể dùng repository để chuẩn bị dữ liệu trước khi khởi chạy các transaction thử nghiệm. Repository CRUD method tự hoàn tất transaction khi lời gọi kết thúc nếu không có transaction ngoài.

## 4. Kiểm thử optimistic locking với hai transaction đồng thời

Muốn kiểm tra concurrency thực sự, cần bảo đảm hai transaction đều đọc cùng version trước khi một trong hai ghi.

Một cách kiểm soát thứ tự là dùng:

- Hai worker thread.
- Một TransactionTemplate dùng chung.
- CountDownLatch hoặc CyclicBarrier để đồng bộ sau khi đọc.
- Một JDBC connection/transaction riêng cho mỗi worker thread.

### 4.1. Mô hình kiểm thử

~~~text
Test thread
   |
   +-- Worker A
   |     BEGIN transaction A
   |     Read quantity = 10, version = 5
   |     Wait at barrier
   |
   +-- Worker B
         BEGIN transaction B
         Read quantity = 10, version = 5
         Wait at barrier

Barrier releases both
   |
   +-- A saves with version 5 -> COMMIT
   |
   +-- B saves with version 5 -> optimistic conflict -> ROLLBACK
~~~

Barrier bảo đảm cả hai transaction đã đọc trước khi cho phép ghi. Nhờ đó test không phụ thuộc tốc độ scheduler để tạo xung đột.

### 4.2. Helper chạy một attempt

~~~java
enum AttemptResult {
    COMMITTED,
    OPTIMISTIC_CONFLICT
}
~~~

~~~java
private AttemptResult reserveInTransaction(
        String sku,
        int quantity,
        TransactionTemplate transactionTemplate,
        InventoryRepository repository,
        CyclicBarrier barrier
) {
    try {
        transactionTemplate.execute(status -> {
            InventoryItem current = repository.findBySku(sku)
                    .orElseThrow();

            awaitBarrier(barrier);

            repository.save(current.reserve(quantity));
            return null;
        });

        return AttemptResult.COMMITTED;
    } catch (OptimisticLockingFailureException exception) {
        return AttemptResult.OPTIMISTIC_CONFLICT;
    }
}

private void awaitBarrier(CyclicBarrier barrier) {
    try {
        barrier.await(5, TimeUnit.SECONDS);
    } catch (Exception exception) {
        throw new IllegalStateException(
                "Could not synchronize concurrent transactions",
                exception
        );
    }
}
~~~

Trong code thực tế, helper này có thể nằm trong test class. Các dependency cần import gồm CyclicBarrier, TimeUnit và Spring TransactionTemplate.

### 4.3. Test điều phối hai worker

~~~java
@SpringBootTest
class InventoryConcurrentUpdateTest {

    @Autowired
    InventoryRepository repository;

    @Autowired
    TransactionTemplate transactionTemplate;

    @Test
    void onlyOneConcurrentReservationCommits() throws Exception {
        InventoryItem created = repository.save(
                new InventoryItem(
                        null,
                        "SKU-CONCURRENT",
                        10,
                        null
                )
        );

        CyclicBarrier barrier = new CyclicBarrier(2);
        ExecutorService executor = Executors.newFixedThreadPool(2);

        try {
            Future<AttemptResult> first = executor.submit(
                    () -> reserveInTransaction(
                            "SKU-CONCURRENT",
                            1,
                            transactionTemplate,
                            repository,
                            barrier
                    )
            );

            Future<AttemptResult> second = executor.submit(
                    () -> reserveInTransaction(
                            "SKU-CONCURRENT",
                            1,
                            transactionTemplate,
                            repository,
                            barrier
                    )
            );

            AttemptResult firstResult =
                    first.get(10, TimeUnit.SECONDS);

            AttemptResult secondResult =
                    second.get(10, TimeUnit.SECONDS);

            long committed = Stream.of(firstResult, secondResult)
                    .filter(result -> result == AttemptResult.COMMITTED)
                    .count();

            long conflicts = Stream.of(firstResult, secondResult)
                    .filter(result ->
                            result == AttemptResult.OPTIMISTIC_CONFLICT)
                    .count();

            assertEquals(1, committed);
            assertEquals(1, conflicts);

            InventoryItem current =
                    repository.findById(created.id()).orElseThrow();

            assertEquals(9, current.availableQuantity());
        } finally {
            executor.shutdownNow();
        }
    }
}
~~~

Ví dụ này giả định transaction manager dùng cùng DataSource với repository và test không có transaction ngoài. Mỗi lần gọi TransactionTemplate trên worker thread tạo transaction riêng.

Trong test thật, hãy đặt helper và import đầy đủ trong test class. Có thể thay CyclicBarrier bằng CountDownLatch nếu muốn kiểm soát riêng số transaction đã đọc và thời điểm thả chúng.

### 4.4. Vì sao phải dùng timeout?

Không để test chờ vô hạn khi một worker không đến barrier hoặc database giữ lock quá lâu.

Dùng timeout cho:

- Chờ worker đọc dữ liệu.
- Chờ barrier.
- Future.get.
- Lock wait của database.
- Kết thúc executor.

Nếu timeout xảy ra, cần giải phóng latch/barrier trong finally để không giữ thread hoặc connection của test suite.

### 4.5. Khác biệt theo isolation level và database

Trong một số database hoặc isolation level, xung đột có thể được báo bằng lỗi serialization/deadlock thay vì cùng một kiểu exception optimistic locking. Test stale update tuần tự thường phù hợp để xác nhận chính xác OptimisticLockingFailureException.

Test concurrency nên xác nhận invariant cuối cùng và phân loại lỗi concurrency theo database/transaction configuration. Không nên dựa vào thông báo lỗi vendor cụ thể.

## 5. Kiểm thử optimistic locking khi delete

Spring Data JDBC cũng kiểm tra version khi xóa aggregate versioned.

Test:

~~~java
@Test
void rejectsDeleteUsingStaleVersion() {
    InventoryItem created = repository.save(
            new InventoryItem(
                    null,
                    "SKU-DELETE",
                    10,
                    null
            )
    );

    InventoryItem stale = repository.findById(created.id())
            .orElseThrow();

    InventoryItem current = repository.findById(created.id())
            .orElseThrow();

    repository.save(current.reserve(1));

    assertThrows(
            OptimisticLockingFailureException.class,
            () -> repository.delete(stale)
    );

    assertTrue(repository.existsById(created.id()));
}
~~~

Object stale không được phép xóa aggregate đã thay đổi sau khi object đó được tải.

Nếu database đã xóa bản ghi bởi một transaction khác, thao tác delete bằng version cũ cũng có thể thất bại do không còn hàng phù hợp.

## 6. Pessimistic locking trong Spring Data JDBC

Spring Data JDBC hỗ trợ pessimistic locking trên **derived query methods** thông qua annotation @Lock.

Hai mode chính:

- **PESSIMISTIC_READ:** khóa đọc, bảo đảm dữ liệu đang đọc không bị transaction khác sửa theo semantics mà database hỗ trợ.
- **PESSIMISTIC_WRITE:** lấy khóa để thực hiện thay đổi.

Một số database không phân biệt hai mode; cả hai có thể tương đương PESSIMISTIC_WRITE.

### 6.1. Khai báo repository method

~~~java
import java.util.Optional;

import org.springframework.data.relational.repository.Lock;
import org.springframework.data.relational.core.sql.LockMode;
import org.springframework.data.repository.CrudRepository;

public interface InventoryLockRepository
        extends CrudRepository<InventoryItem, Long> {

    @Lock(LockMode.PESSIMISTIC_WRITE)
    Optional<InventoryItem> findLockedBySku(String sku);
}
~~~

Tên method có phần mô tả Locked trước By; thuộc tính lọc thực tế là sku.

Spring Data JDBC tạo câu SELECT có lock clause theo dialect. Không cần tự hard-code cú pháp khóa của một database khi dùng derived query cùng @Lock.

### 6.2. @Lock chỉ hỗ trợ derived query methods

Tài liệu Spring Data Relational 4.1.2 quy định @Lock hiện không được hỗ trợ trên string-based query methods.

Ví dụ:

~~~java
@Lock(LockMode.PESSIMISTIC_WRITE)
@Query("SELECT * FROM inventory_items WHERE sku = :sku")
Optional<InventoryItem> findLocked(String sku);
~~~

Không nên kỳ vọng khóa được áp dụng cho query này. Spring Data JDBC sẽ bỏ qua locking information và ghi warning trong log. Nếu cần SQL tùy chỉnh, phải tự triển khai cơ chế khóa phù hợp và kiểm thử theo dialect.

### 6.3. Khóa phải nằm trong transaction

Pessimistic lock được giữ trong phạm vi transaction database. Vì vậy, đặt truy vấn khóa và thao tác cập nhật trong cùng transaction:

~~~java
@Service
public class InventoryLockingService {

    private final InventoryLockRepository repository;

    public InventoryLockingService(
            InventoryLockRepository repository
    ) {
        this.repository = repository;
    }

    @Transactional
    public InventoryItem reserve(
            String sku,
            int quantity
    ) {
        InventoryItem item = repository.findLockedBySku(sku)
                .orElseThrow();

        return repository.save(item.reserve(quantity));
    }
}
~~~

Nếu truy vấn khóa chạy trong một transaction ngắn đã commit trước khi service thực hiện cập nhật, lock có thể được giải phóng quá sớm. Ranh giới transaction cần bao trùm toàn bộ critical section.

Với query methods, Spring Data JDBC khuyến nghị cấu hình transaction rõ ràng. Đặt @Transactional ở service điều phối giúp khóa được giữ trong toàn bộ thao tác nghiệp vụ.

## 7. Kiểm thử pessimistic lock bằng hai transaction

Một test khóa bi quan nên chứng minh:

1. Transaction A lấy khóa.
2. Transaction B yêu cầu cùng khóa và phải chờ.
3. A commit hoặc rollback.
4. B tiếp tục sau khi khóa được giải phóng.
5. Cả hai transaction kết thúc trong thời gian giới hạn.

### 7.1. Test giữ khóa và xác nhận transaction khác bị chặn

Có thể dùng CountDownLatch để giữ transaction A sau khi khóa được lấy:

~~~java
CountDownLatch lockAcquired = new CountDownLatch(1);
CountDownLatch releaseLock = new CountDownLatch(1);

Future<?> holder = executor.submit(() ->
        transactionTemplate.execute(status -> {
            repository.findLockedBySku("SKU-LOCK")
                    .orElseThrow();

            lockAcquired.countDown();
            awaitRelease(releaseLock);

            return null;
        })
);
~~~

Sau khi A lấy khóa, chạy transaction B:

~~~java
assertTrue(lockAcquired.await(5, TimeUnit.SECONDS));

Future<?> waiter = executor.submit(() ->
        transactionTemplate.execute(status ->
                repository.findLockedBySku("SKU-LOCK")
                        .orElseThrow()
        )
);
~~~

Xác nhận B chưa hoàn tất khi A còn giữ khóa:

~~~java
assertThrows(
        TimeoutException.class,
        () -> waiter.get(200, TimeUnit.MILLISECONDS)
);
~~~

Sau đó giải phóng transaction A:

~~~java
releaseLock.countDown();

holder.get(5, TimeUnit.SECONDS);
waiter.get(5, TimeUnit.SECONDS);
~~~

Trong test hoàn chỉnh, đặt releaseLock.countDown() trong finally để bảo đảm transaction A không bị giữ vô hạn nếu assertion thất bại.

Thời gian 200 ms chỉ là khoảng quan sát ngắn để xác nhận B đang chờ, không phải timeout nghiệp vụ. Hãy chọn thời gian phù hợp với môi trường CI và database container.

### 7.2. Dùng hai connection độc lập

Hai transaction phải thực sự dùng hai connection khác nhau. Một transaction JDBC imperative gắn với thread hiện tại; cùng thread và cùng transaction context không mô phỏng được hai client cạnh tranh.

Đảm bảo:

- Executor có ít nhất hai worker thread.
- Connection pool có thể cấp ít nhất hai connection.
- Mỗi worker gọi TransactionTemplate độc lập.
- Không có transaction ngoài bao quanh test.
- Dữ liệu setup đã commit trước khi bắt đầu test.

### 7.3. Kiểm tra giải phóng lock khi rollback

Có thể thay transaction A bằng transaction kết thúc bằng exception:

~~~java
transactionTemplate.execute(status -> {
    repository.findLockedBySku("SKU-LOCK")
            .orElseThrow();

    throw new IllegalStateException("Force rollback");
});
~~~

Sau rollback, transaction B phải có thể lấy khóa. Điều này xác nhận lock được database giải phóng khi transaction kết thúc, kể cả khi kết thúc bằng rollback.

Không dùng exception giả lập ngoài transaction boundary nếu mục tiêu là kiểm tra rollback thật của database.

## 8. Kiểm thử lock timeout và deadlock

Khóa bi quan có thể khiến transaction chờ. Nếu transaction khác giữ khóa quá lâu, database có thể kết thúc request do lock timeout.

Các exception có thể được Spring dịch sang nhóm concurrency/data-access exception như:

- CannotAcquireLockException.
- PessimisticLockingFailureException.
- Một exception thuộc DataAccessException tùy driver và transaction manager.

Không phụ thuộc vào nội dung message do database trả về. Hãy kiểm tra loại exception theo abstraction của Spring và trạng thái cuối cùng của dữ liệu.

### 8.1. Lock timeout

Test timeout cần:

1. Transaction A lấy khóa và giữ khóa.
2. Transaction B yêu cầu khóa.
3. Cấu hình lock wait timeout phù hợp với database test.
4. Xác nhận B thất bại trong thời gian dự kiến.
5. Xác nhận A vẫn có thể commit/rollback.
6. Kiểm tra dữ liệu không bị thay đổi một phần.

Cách cấu hình lock timeout khác nhau theo vendor. Không đưa câu lệnh cấu hình timeout của PostgreSQL hoặc MySQL vào test dùng chung mà không phân nhánh theo database.

### 8.2. Deadlock

Deadlock có thể xảy ra khi hai transaction lấy nhiều khóa theo thứ tự ngược nhau:

~~~text
Transaction A                 Transaction B
-------------                 -------------
Lock row 1                    Lock row 2
Request row 2                 Request row 1
Wait for B                    Wait for A
       \                      /
        \---- DEADLOCK ------/
~~~

Một cách giảm rủi ro là luôn lấy khóa theo thứ tự nhất quán, ví dụ sắp xếp ID tăng dần trước khi lock nhiều aggregate.

Test deadlock có thể khó ổn định vì phụ thuộc scheduler, optimizer và database. Nếu cần kiểm tra, hãy tạo kịch bản có barrier để hai transaction chắc chắn giữ khóa đầu tiên trước khi yêu cầu khóa thứ hai, đồng thời đặt timeout cho test.

Không nên viết test chỉ chờ một khoảng sleep ngẫu nhiên rồi hy vọng deadlock xuất hiện.

## 9. Chọn optimistic hay pessimistic cho từng use case

| Tình huống | Chiến lược thường phù hợp |
| --- | --- |
| Người dùng sửa hồ sơ, xung đột hiếm | Optimistic locking |
| Nhiều request cùng cập nhật bộ đếm nóng | Cân nhắc pessimistic lock hoặc atomic SQL |
| Đặt chỗ/tồn kho có contention cao | Đánh giá pessimistic write hoặc cập nhật có điều kiện |
| Đọc nhiều, ghi ít | Optimistic locking |
| Critical section ngắn, cần tuần tự hóa thao tác | Pessimistic locking |
| Tác vụ dài hoặc gọi HTTP | Tránh giữ pessimistic lock trong toàn bộ thời gian |
| Cập nhật nhiều aggregate cùng lúc | Thiết kế thứ tự lock và transaction boundary rõ ràng |

### 9.1. Optimistic locking không tự giải quyết nghiệp vụ

Khi nhận OptimisticLockingFailureException, ứng dụng cần quyết định:

- Retry trong transaction mới sau khi tải lại aggregate.
- Trả HTTP 409 Conflict để caller tải lại dữ liệu.
- Yêu cầu người dùng giải quyết xung đột thủ công.
- Ghi metric để theo dõi contention.

Không retry mù quáng các lỗi validation hoặc constraint.

### 9.2. Pessimistic locking không thay thế validation

Có lock không có nghĩa thao tác chắc chắn hợp lệ. Sau khi lấy khóa, vẫn phải kiểm tra:

- Số lượng còn đủ hay không.
- Trạng thái aggregate có cho phép chuyển tiếp không.
- Hạn mức có bị vượt không.
- Người dùng còn quyền thực hiện hành động không.

Lock chỉ điều phối quyền truy cập đồng thời; domain rule vẫn phải được thực thi.

## 10. Kiểm thử trên database thật

H2 hữu ích cho test nhanh, nhưng concurrency và lock behavior cần được kiểm chứng trên database thực tế mà ứng dụng triển khai.

Khác biệt có thể đến từ:

- Lock mode được database hỗ trợ.
- Cách diễn giải PESSIMISTIC_READ và PESSIMISTIC_WRITE.
- Isolation level mặc định.
- Lock timeout.
- Deadlock detection.
- Row lock và range/gap lock.
- Transaction engine và JDBC driver.

Nếu production dùng PostgreSQL, chạy concurrency tests trên PostgreSQL Testcontainer. Nếu production dùng MySQL/InnoDB, chạy trên MySQL container cùng major version. Nếu hỗ trợ cả hai, chạy test riêng cho từng database.

### 10.1. PostgreSQL Testcontainers

Ví dụ cấu hình container:

~~~java
@Testcontainers
@SpringBootTest
class PostgreSqlLockingTest {

    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("shop")
                    .withUsername("shop")
                    .withPassword("shop");

    @DynamicPropertySource
    static void databaseProperties(
            DynamicPropertyRegistry registry
    ) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }
}
~~~

Test class này có thể chứa stale-update test, concurrent update test và pessimistic lock test. Dùng phiên bản container gần với production để kiểm tra đúng driver và server behavior.

### 10.2. MySQL Testcontainers

~~~java
@Testcontainers
@SpringBootTest
class MySqlLockingTest {

    @Container
    static final MySQLContainer<?> mysql =
            new MySQLContainer<>("mysql:8.4")
                    .withDatabaseName("shop")
                    .withUsername("shop")
                    .withPassword("shop");

    @DynamicPropertySource
    static void databaseProperties(
            DynamicPropertyRegistry registry
    ) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
    }
}
~~~

Kiểm tra engine của bảng là InnoDB nếu test dựa vào row-level transaction locks. MySQL có thể có semantics khác nếu bảng dùng storage engine khác.

Không coi MySQL và MariaDB là cùng một target test. Nếu production dùng MariaDB, kiểm thử MariaDB riêng.

### 10.3. Không để test context hoặc connection pool làm sai kết quả

Với test chạy song song:

- Dùng dữ liệu test có SKU/ID riêng.
- Đảm bảo connection pool đủ connection cho số transaction đồng thời.
- Đóng ExecutorService trong finally.
- Dùng timeout cho Future và latch.
- Đảm bảo container sống trong toàn bộ vòng đời ApplicationContext.
- Không để transaction test ngoài giữ lock hoặc connection.
- Không chạy các test dùng chung một hàng dữ liệu song song nếu chúng có thể gây nhiễu nhau.

## 11. Kiểm thử nhiều repository trong cùng transaction

Một use case có thể cập nhật tồn kho và tạo đơn hàng. Khi bước thứ hai thất bại, bước thứ nhất phải rollback.

~~~java
@Transactional
public PurchaseOrder placeOrder(String sku, int quantity) {
    InventoryItem inventory = inventoryRepository
            .findBySku(sku)
            .orElseThrow();

    inventoryRepository.save(inventory.reserve(quantity));

    return orderRepository.save(
            new PurchaseOrder(
                    null,
                    sku,
                    quantity,
                    "PLACED"
            )
    );
}
~~~

Test cần xác nhận:

1. Transaction đọc tồn kho.
2. Cập nhật tồn kho thành công trong transaction.
3. Một lỗi được tạo ra ở bước lưu đơn hàng.
4. Transaction rollback.
5. Tồn kho trở về giá trị trước đó.
6. Không có đơn hàng được tạo.

Nếu có optimistic locking conflict ở một aggregate, cả transaction phải rollback. Không chỉ retry repository method cuối cùng trong transaction cũ.

Với pessimistic locking, test cần xác nhận lock được giữ đến khi toàn bộ use case commit/rollback, không chỉ đến khi repository method trả về.

## 12. Kiểm thử optimistic locking và retry

Nếu ứng dụng có retry policy, kiểm thử cả việc phát hiện conflict và cách xử lý sau conflict.

Một test retry cần xác nhận:

- Attempt đầu đọc version cũ.
- Transaction khác cập nhật aggregate.
- Attempt đầu thất bại và rollback.
- Attempt tiếp theo mở transaction mới.
- Aggregate được tải lại với version mới.
- Domain rule được đánh giá lại.
- Chỉ một thay đổi hợp lệ được commit.

Không mock repository để ném OptimisticLockingFailureException rồi coi đó là bằng chứng transaction rollback. Mock chỉ xác nhận nhánh xử lý exception; integration test mới xác nhận database và transaction manager hoạt động đúng.

Nếu retry toàn bộ use case có nhiều repository, xác nhận tất cả thay đổi của attempt thất bại đều được rollback trước khi attempt mới bắt đầu.

## 13. Kiểm thử các tình huống biên

Một bộ concurrency test hữu ích nên bao gồm:

| Tình huống | Điều cần xác nhận |
| --- | --- |
| Hai object cùng version update | Một update thành công, update stale thất bại |
| Hai transaction cùng đọc rồi save | Không mất cập nhật |
| Update và delete cạnh tranh | Delete stale không xóa thay đổi mới |
| Hai transaction cùng lấy pessimistic write lock | Transaction sau chờ hoặc timeout |
| Transaction giữ lock rollback | Lock được giải phóng |
| Deadlock | Transaction bị chọn làm nạn nhân thất bại; dữ liệu không ở trạng thái dở dang |
| Lock timeout | Lỗi được truyền/translate phù hợp; transaction kết thúc |
| Nhiều repository trong một transaction | Rollback toàn bộ khi một bước thất bại |
| Retry sau conflict | Đọc lại version và revalidate business rules |
| Connection pool nhỏ | Test phát hiện timeout do cạn connection, không treo vô hạn |

Không cần đưa tất cả kịch bản vào mọi dự án. Ưu tiên những đường ghi và invariant có tác động trực tiếp đến dữ liệu quan trọng.

## 14. Những sai lầm thường gặp

**“@Version tự khóa hàng khi đọc.”** Không. Optimistic locking kiểm tra version lúc ghi, không giữ pessimistic row lock trong suốt quá trình đọc.

**“Test stale update tuần tự là test concurrency đầy đủ.”** Không. Nó xác nhận version check với object cũ. Muốn kiểm tra transaction cạnh tranh, cần hai transaction/connection độc lập.

**“Hai thread là đủ để chứng minh concurrency.”** Không. Phải đồng bộ để bảo đảm cả hai transaction đọc cùng trạng thái trước khi ghi.

**“Có thể đặt @Transactional trên test rồi dùng executor để test hai transaction.”** Không nên. Transaction test gắn với test thread; worker thread phải có transaction riêng và dữ liệu setup cần commit trước.

**“Pessimistic lock vẫn được giữ sau khi repository method trả về.”** Chỉ khi transaction chứa lời gọi đó vẫn mở. Khi transaction kết thúc, database giải phóng lock.

**“@Lock hoạt động với mọi @Query.”** Không. Spring Data JDBC 4.1.2 hỗ trợ @Lock trên derived query methods; string-based @Query hiện bỏ qua locking metadata và ghi warning.

**“PESSIMISTIC_READ luôn khác PESSIMISTIC_WRITE.”** Không. Một số database triển khai hai mode tương đương.

**“Dùng SELECT FOR UPDATE mà không có transaction là đủ.”** Không. Lock cần được giữ trong transaction bao quanh thao tác nghiệp vụ.

**“Có pessimistic lock thì không cần kiểm tra business rule.”** Không. Sau khi lấy khóa, vẫn phải kiểm tra invariant trên dữ liệu hiện tại.

**“H2 pass là đủ chứng minh lock behavior production.”** Không. Hãy kiểm thử trên database vendor và storage engine thực tế.

**“Lock timeout luôn có cùng exception message.”** Không. Driver và database khác nhau; kiểm tra exception abstraction và trạng thái dữ liệu.

**“Deadlock test có thể dùng Thread.sleep ngẫu nhiên.”** Không ổn định. Dùng barrier/latch để điều khiển thứ tự lấy khóa.

**“Tăng connection pool là giải pháp cho mọi lock wait.”** Không. Có thể chỉ che giấu transaction dài hoặc thứ tự khóa không nhất quán.

**“Có thể giữ lock trong khi gọi HTTP.”** Không nên. Gọi dịch vụ ngoài khi đang giữ lock có thể kéo dài transaction và làm tăng contention.

## 15. Quy trình xây dựng concurrency test

1. **Xác định invariant:** ví dụ tồn kho không âm hoặc chỉ một transaction được xác nhận một lần.
2. **Chọn chiến lược:** optimistic version hay pessimistic lock.
3. **Chuẩn bị aggregate versioned:** đặt @Version trên aggregate root nếu dùng optimistic locking.
4. **Chuẩn bị repository lock method:** dùng @Lock trên derived query method nếu dùng pessimistic locking.
5. **Commit dữ liệu setup:** để các transaction thử nghiệm nhìn thấy dữ liệu.
6. **Mở transaction độc lập:** dùng TransactionTemplate trong các worker thread hoặc service bean được gọi qua proxy.
7. **Điều khiển thứ tự:** dùng CyclicBarrier/CountDownLatch thay vì sleep tùy ý.
8. **Chạy các thao tác cạnh tranh:** update, delete hoặc lấy lock.
9. **Chờ với timeout:** tránh treo CI.
10. **Xác nhận kết quả:** kiểm tra exception, số transaction thành công và trạng thái database cuối cùng.
11. **Giải phóng tài nguyên:** release latch, shutdown executor và kết thúc transaction.
12. **Chạy trên database thật:** dùng Testcontainers với phiên bản server gần production.
13. **Theo dõi độ ổn định:** lặp lại test nhiều lần và kiểm tra không có phụ thuộc thứ tự giữa test cases.

~~~mermaid
flowchart TD
    A["Chuẩn bị dữ liệu đã commit"] --> B["Mở transaction A và B"]
    B --> C["Đồng bộ sau khi đọc"]
    C --> D{"Chiến lược khóa?"}
    D -->|Optimistic| E["Cả hai save cùng version"]
    D -->|Pessimistic| F["A giữ lock, B yêu cầu lock"]
    E --> G["Một transaction thành công, transaction stale thất bại"]
    F --> H["B chờ hoặc timeout"]
    G --> I["Kiểm tra trạng thái cuối"]
    H --> I
    I --> J["Giải phóng executor và connection"]
~~~

## 17. Ghi nhớ

- Spring Data JDBC hỗ trợ optimistic locking bằng thuộc tính số được đánh dấu @Version trên aggregate root.
- Update và delete đều kiểm tra version; delete không tăng version.
- Test stale update tuần tự giúp xác nhận object có version cũ bị từ chối.
- Test concurrency thật cần hai transaction và connection độc lập.
- Dùng barrier/latch để bảo đảm hai transaction đọc cùng trạng thái trước khi ghi.
- TransactionTemplate trên worker thread tạo transaction riêng khi không có transaction ngoài.
- Pessimistic locking trong Spring Data JDBC hỗ trợ @Lock với PESSIMISTIC_READ và PESSIMISTIC_WRITE trên derived query methods.
- @Lock không được hỗ trợ trên string-based @Query trong Spring Data Relational 4.1.2.
- Pessimistic lock phải được giữ trong transaction bao trùm cả thao tác nghiệp vụ.
- Lock behavior phụ thuộc dialect, database, storage engine và isolation level.
- Kiểm thử lock cần timeout, hai connection, dữ liệu setup đã commit và cleanup chắc chắn.
- Không dùng sleep ngẫu nhiên để điều khiển concurrency; dùng barrier/latch.
- H2 hữu ích cho test nhanh nhưng không thay integration test trên database production.
- Kiểm tra trạng thái dữ liệu cuối cùng, không chỉ kiểm tra exception.
- Khi có retry, mỗi attempt phải chạy trong transaction mới và tải lại aggregate.
- Giữ critical section ngắn, tránh gọi HTTP hoặc xử lý lâu khi đang giữ lock.

**Kiểm thử concurrency phải chứng minh database thực sự xử lý hai transaction độc lập theo đúng chiến lược khóa đã chọn.** Với optimistic locking, hãy tạo stale version và xác nhận update bị từ chối. Với pessimistic locking, hãy giữ khóa trong một transaction và quan sát transaction khác chờ hoặc timeout. Chạy các test này trên database production target để phát hiện khác biệt về lock, isolation và driver trước khi triển khai.
