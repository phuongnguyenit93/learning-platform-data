# Differences Between Derived Delete, CRUD Delete, and Direct SQL DELETE in Spring Data JDBC

## 1. Three Ways to Delete Data, Three Levels of Abstraction

Spring Data JDBC lets you delete data in several ways. All of them delete rows in the database, but how you call the repository, how the framework understands aggregates, and who is responsible for handling relationships can differ.

Three common categories:

1. **Derived delete:** declaring a method like `deleteByStatus(...)` or `removeByCreatedAtBefore(...)`. Spring Data derives the condition from the method name and Java properties.
2. **CRUD repository delete:** calling standard methods such as `delete(entity)`, `deleteById(id)`, `deleteAll(...)`. These are repository operations on an entity/aggregate root.
3. **Direct SQL DELETE:** writing `DELETE FROM ...` explicitly using `@Modifying @Query` or `JdbcTemplate`. The application controls the SQL and delete conditions.

What matters is not just whether the syntax is short or long. You must consider **the unit being deleted, how aggregate child rows are handled, lifecycle callbacks, foreign keys, transactions, and affected row counts**.

## 2. Derived Delete with `deleteBy` and `removeBy`

A derived delete is a query method derived from the method name. The part after `By` describes a predicate based on the entity's Java properties.

Example entity:

~~~java
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private Long id;

    @Column("customer_code")
    private String customerCode;

    private String status;

    @Column("created_at")
    private Instant createdAt;

    // constructors, getters...
}
~~~

The repository can declare:

~~~java
import java.time.Instant;

import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    void deleteByStatus(String status);

    void removeByCreatedAtBefore(Instant cutoff);

    void deleteByCustomerCode(String customerCode);
}
~~~

The method names are interpreted as follows:

| Method | Derived condition |
|---|---|
| `deleteByStatus(status)` | Property `status` equals parameter |
| `removeByCreatedAtBefore(cutoff)` | Property `createdAt` is before timestamp |
| `deleteByCustomerCode(code)` | Property `customerCode` equals parameter |

`delete...By` and `remove...By` are two naming forms for derived deletes. Method names use **Java properties**, not physical column names. In the example, `createdAt` is mapped to the `created_at` column via `@Column`.

### 2.1. When to Use Derived Delete?

Use derived delete when:

- The condition is simple and based on an entity's properties.
- The method name stays short and readable.
- Custom SQL is not needed.
- The deletion scope is clearly defined by the predicate.
- The application has verified that derived delete behavior fits the aggregate and schema in use.

Example deleting expired sessions:

~~~java
void deleteByExpiresAtBefore(Instant cutoff);
~~~

This is a concise declaration. However, do not take the method name as proof that the framework will delete all aggregate child tables with the exact same semantics as CRUD delete. A derived delete is a conditional query; you must understand the SQL generated by your Spring Data JDBC version and how your schema handles foreign keys.

### 2.2. Return Type and Deleted Row Count

A derived delete can be declared with no return value, such as `void`. Some query forms/versions allow returning the number of affected rows. Confirm the contract of the Spring Data JDBC version your project uses before choosing a numeric return type.

Simple example:

~~~java
void deleteByStatus(String status);
~~~

If business logic needs to report how many rows were deleted, do not assume every method supports the same return types. You can use a modifying query returning an update count or an explicit SQL API when precise control is required.

### 2.3. Derived Delete Does Not Mean Check-First-Then-Delete

The method:

~~~java
void deleteByCustomerCode(String customerCode);
~~~

is a conditional delete operation. It does not mean the repository checks that the business key is unique. If multiple rows share the same code, the condition can match multiple rows.

If the requirement is to delete exactly one customer by code, protect the code with a unique constraint in the database. Do not rely on an assumption that data "usually has only one row".

## 3. Deleting Through CRUD Repository

A CRUD repository provides delete methods based on identifier or entity:

~~~java
public interface CustomerRepository
        extends CrudRepository<Customer, Long> {
}
~~~

Commonly used methods:

| Method | Meaning |
|---|---|
| `delete(entity)` | Deletes the passed entity |
| `deleteById(id)` | Deletes the entity by identifier |
| `deleteAll(entities)` | Deletes the entities in the passed collection |
| `deleteAllById(ids)` | Deletes the entities whose identifiers are in the collection |
| `deleteAll()` | Deletes all data belonging to the repository |

Exact method names and contracts depend on the repository interface your application extends. The example above uses `CrudRepository`.

### 3.1. `delete(entity)`

Used when the application already has the aggregate root and wants to delete that entity:

~~~java
Customer customer = customerRepository
        .findById(customerId)
        .orElseThrow();

customerRepository.delete(customer);
~~~

This makes it explicit which entity is deleted. It is useful when permissions, state, or business rules must be checked prior to deletion:

~~~java
@Transactional
public void closeCustomer(Long id) {
    Customer customer = customers.findById(id)
            .orElseThrow(CustomerNotFoundException::new);

    if ("ACTIVE".equals(customer.getStatus())) {
        throw new IllegalStateException(
                "Cannot delete an active customer"
        );
    }

    customers.delete(customer);
}
~~~

Loading the entity before deleting is not always necessary. If you only have the ID and do not need an application-level state check, `deleteById` can be simpler.

### 3.2. `deleteById(id)`

~~~java
customerRepository.deleteById(customerId);
~~~

This method targets the aggregate root's identifier. It fits when the caller already knows the ID and wants to use the CRUD repository to perform the delete.

Under standard CRUD repository contracts, requesting deletion of a nonexistent ID is typically not treated as a mandatory "not found" error. If business logic needs to distinguish "deleted" from "did not exist", verify the outcome explicitly or use a query that returns the affected row count.

### 3.3. `deleteAll` and `deleteAllById`

These methods are useful for operating on an explicit set:

~~~java
customerRepository.deleteAll(customersToRemove);

customerRepository.deleteAllById(customerIds);
~~~

Be careful with:

~~~java
customerRepository.deleteAll();
~~~

This method has a very broad scope: it deletes all data belonging to the repository. Only use it when that is genuinely a business requirement or a controlled administrative operation. For large datasets, consider transaction duration, locks, constraints, and transaction log volume.

### 3.4. CRUD Delete and Aggregates

Spring Data JDBC manages data around aggregates. Repositories are defined for aggregate roots; child components are stored in related tables according to mappings such as `@MappedCollection`.

When deleting an aggregate root via a CRUD repository, Spring Data JDBC handles the rows belonging to the aggregate according to the mapping and ordering needed to preserve referential integrity. This differs from sending a single direct DELETE to the root table.

For example:

~~~java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private Long id;

    @MappedCollection(idColumn = "order_id")
    private List<OrderLine> lines;

    // constructors, getters...
}
~~~

If you delete `PurchaseOrder` through the repository, the `OrderLine` rows belonging to the aggregate must be handled according to Spring Data JDBC's persistence strategy. The application should not assume deleting only the row in `purchase_orders` is enough.

The exact SQL executed depends on the version and mapping, but when aggregate semantics are needed, the CRUD repository is a better abstraction than a single-table DELETE command.

## 4. Direct SQL DELETE Using `@Modifying` and `@Query`

When exact control over SQL is required, you can declare a modifying query:

~~~java
import java.time.Instant;

import org.springframework.data.jdbc.repository.query.Modifying;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

public interface AuditEventRepository
        extends CrudRepository<AuditEvent, Long> {

    @Modifying
    @Query("""
        DELETE FROM audit_events
        WHERE created_at < :cutoff
        """)
    int deleteOlderThan(@Param("cutoff") Instant cutoff);
}
~~~

`@Query` provides explicit SQL; `@Modifying` marks the method as modifying data rather than only reading. The SQL is sent to the database according to the application's dialect/schema.

With this approach, the application controls:

- Which table is deleted from.
- Predicates and tenant conditions.
- Whether subqueries or database-specific SQL expressions are used.
- Whether the affected row count is returned, if supported by the method contract.
- How child tables, foreign keys, and cascades are handled.

### 4.1. Direct DELETE Does Not Understand Aggregates Automatically

For example:

~~~sql
DELETE FROM purchase_orders
WHERE id = :orderId;
~~~

This SQL targets only the `purchase_orders` table. It does not inspect `@MappedCollection` metadata to delete `order_lines`.

If the child table has a foreign key:

~~~sql
FOREIGN KEY (order_id) REFERENCES purchase_orders(id)
~~~

the database may reject deleting the root because child rows still exist. If the foreign key is configured with `ON DELETE CASCADE`, the database may delete child rows automatically. If there is no foreign key or cascade, there is a risk of leaving orphan data.

When writing a direct DELETE for an aggregate, proactively choose a strategy:

1. Delete child tables first and then delete the root, in the same transaction.
2. Use a foreign key cascade if that is an explicitly designed and tested policy.
3. Use the CRUD repository so the framework handles the aggregate according to mapping.

Do not rely on a DELETE on the root table automatically handling object relationships.

### 4.2. Direct DELETE Bypasses Entity Mapping

Direct SQL does not instantiate Java entities and invoke CRUD deletion on each aggregate. Therefore, do not expect it to automatically apply steps tied to object mapping such as:

- Business rule checks in the service.
- Verifying entity state before deletion.
- Handling child collections from aggregate metadata.
- Executing lifecycle callbacks attached to entity deletion.
- Creating application-layer audit records.

If the system needs auditing, write audit records explicitly in the same transaction or use an appropriate database mechanism such as a trigger, depending on requirements. Triggers have their own semantics and observability; they do not replace business design.

## 5. Direct SQL DELETE Using `JdbcTemplate`

For dynamic SQL or operations outside a repository, you can use `JdbcTemplate`:

~~~java
@Repository
public class AuditEventDao {

    private final JdbcTemplate jdbc;

    public AuditEventDao(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public int deleteBefore(Instant cutoff) {
        return jdbc.update(
                "DELETE FROM audit_events WHERE created_at < ?",
                Timestamp.from(cutoff)
        );
    }
}
~~~

`JdbcTemplate.update` returns the affected row count for standard DML. Parameters are bound via `PreparedStatement`, separating data values from the SQL statement.

If using `NamedParameterJdbcTemplate`, you can use named parameters:

~~~java
public int deleteForTenantBefore(UUID tenantId, Instant cutoff) {
    String sql = """
            DELETE FROM audit_events
            WHERE tenant_id = :tenantId
              AND created_at < :cutoff
            """;

    var params = new MapSqlParameterSource()
            .addValue("tenantId", tenantId)
            .addValue("cutoff", cutoff);

    return namedParameterJdbcTemplate.update(sql, params);
}
~~~

Do not concatenate user input into SQL strings. Parameter binding is only for values; table names, column names, and keywords must be controlled using fixed SQL or an allowlist.

## 6. Comparing the Three Delete Approaches

| Criterion | Derived delete | CRUD delete | Direct SQL DELETE |
|---|---|---|---|
| Declaration | Method name like `deleteByStatus` | CRUD method like `deleteById` | SQL written in `@Query` or DAO |
| Condition | Derived from Java properties | By entity or identifier | SQL predicate defined by application |
| Entity mapping | Uses metadata to derive query | Repository operation on entity/root | Does not map entities automatically |
| Aggregate children | Do not assume CRUD semantics; verify SQL and version | Suitable when deleting an aggregate via repository | Application/DB must handle explicitly |
| Entity lifecycle | Is a query delete; do not assume it invokes `delete(entity)` per object | Follows CRUD/entity persistence path | Does not run repository lifecycle automatically |
| SQL control | Limited to derived predicates | Framework determines SQL from CRUD | Direct control |
| Deleted row count | Per supported return contract | CRUD API typically does not return count | Can retrieve update count |
| Portability | Depends on parser and dialect | Higher at repository layer | Depends on SQL/dialect |
| Use when | Simple conditions with verified semantics | Deleting an entity/aggregate by ID or object | Bulk delete, complex SQL predicates, technical tables |

An important note: derived delete is a conditional query, whereas CRUD delete is an operation on an entity/identifier. Do not treat both as having identical behavior merely because both end up deleting some rows. For derived deletes on aggregates with children, verify the generated SQL and test your database's foreign keys/cascades.

## 7. Transactions and Multi-Table Deletion

Deleting a root and children often involves multiple SQL statements. If one statement succeeds and the next fails, data can be left in an inconsistent state without a shared transaction.

Example service deleting with explicit SQL:

~~~java
@Service
public class PurchaseOrderDeletionService {

    private final JdbcTemplate jdbc;

    public PurchaseOrderDeletionService(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void deleteOrder(Long orderId) {
        jdbc.update(
                "DELETE FROM order_lines WHERE order_id = ?",
                orderId
        );

        jdbc.update(
                "DELETE FROM purchase_orders WHERE id = ?",
                orderId
        );
    }
}
~~~

Both commands participate in the same transaction if they share the same `DataSource` and transaction manager. If deleting the root fails and an exception escapes the method, the transaction can roll back earlier changes per the rollback policy.

For use cases that need to delete an entire aggregate, using the CRUD repository is often easier to maintain because it expresses the aggregate boundary directly. For example:

~~~java
@Transactional
public void deleteOrder(Long orderId) {
    purchaseOrderRepository.deleteById(orderId);
}
~~~

Distinguish **transaction** from **cascade**:

- A transaction ensures operations within scope commit or roll back together.
- A cascade is a rule for handling related rows when a referenced row is deleted.
- CRUD aggregate deletion is Spring Data JDBC persistence behavior based on mapping.
- Direct SQL DELETE performs only the SQL operations written or database behaviors configured.

Having no transaction does not make a cascade disappear; having a transaction does not automatically create a cascade.

## 8. Is Conditional Deletion Safe?

Deleting by predicate can affect many rows. Before deploying, check:

- Does the predicate restrict properly to the tenant or owner?
- Could it accidentally delete active data?
- Is the business key unique?
- What foreign keys or cascades do child tables have?
- Does audit/history need to be saved before deletion?
- Is soft delete needed instead of hard delete?
- Could the row count be too large for a single transaction?

Example missing a tenant condition:

~~~sql
DELETE FROM sessions
WHERE expires_at < :cutoff;
~~~

If sessions belong to multiple tenants and the deletion policy only allows deleting within one tenant, the SQL needs an added condition:

~~~sql
DELETE FROM sessions
WHERE tenant_id = :tenantId
  AND expires_at < :cutoff;
~~~

The tenant condition should come from the server's authenticated context; do not trust a tenant ID supplied arbitrarily by the caller without authorization checks.

### 8.1. Previewing Before Deletion

You can inspect scope with a count:

~~~sql
SELECT COUNT(*)
FROM audit_events
WHERE created_at < :cutoff;
~~~

Or fetch a sample set of IDs to inspect. However, preview and delete are two separate queries; data can change between runs. If exact scope is required, design transaction isolation/locking or use a strategy that marks rows to delete.

### 8.2. Bulk Deletion and Chunking

Deleting millions of rows in one transaction can create large transaction logs, hold locks long, and hurt other workloads. You can break it into chunks by ID or time range:

~~~sql
DELETE FROM audit_events
WHERE created_at < :cutoff
  AND id IN (
      SELECT id
      FROM audit_events
      WHERE created_at < :cutoff
      ORDER BY id
      LIMIT 1000
  );
~~~

Subquery/limit syntax depends on the database. Some engines require a CTE or different syntax. When chunking, define transaction boundaries, checkpoints, retries, and how to avoid missing rows.

Do not add `LIMIT` to DELETE without checking your dialect. Also do not assume chunking inside a single `@Transactional` method commits each chunk separately; the whole method can still be in one transaction.

## 9. Hard Delete, Soft Delete, and Auditing

SQL DELETE is a **hard delete**: rows are removed from the table per database semantics. If the business requires keeping history, you can use soft delete:

~~~sql
UPDATE customers
SET deleted_at = CURRENT_TIMESTAMP
WHERE id = :id;
~~~

The entity has a `deletedAt` property, and the repository provides an appropriate update method or uses a modifying query. With soft delete:

- Read queries must filter out deleted records.
- Unique constraints may need redesigning if business keys can be reused.
- Foreign keys still point to an existing row.
- A restoration policy must be defined.
- Auditing can retain state-change history.

Soft delete is not a DELETE operation. Do not name a method `delete...` if it really only updates a status flag, unless the application's abstraction explicitly defines that semantics.

## 10. When to Choose Which Approach?

### Choose CRUD Delete When

- Deleting one aggregate root by ID or entity.
- You want Spring Data JDBC to handle aggregate relationships from mapping.
- You want to keep the repository abstraction and avoid writing multi-table SQL manually.
- There is business validation before deleting.
- You want code to clearly show which entity is being deleted.

For example:

~~~java
@Transactional
public void removeCustomer(Long id) {
    Customer customer = customers.findById(id)
            .orElseThrow(CustomerNotFoundException::new);

    customerDeletionPolicy.checkCanDelete(customer);
    customers.delete(customer);
}
~~~

### Choose Derived Delete When

- The predicate is simple and property-based.
- Custom SQL is not needed.
- You have verified the delete behavior of the Spring Data JDBC version in use.
- Schema and aggregate do not require special child handling.
- Deleting by condition clearly expresses the business intent.

For example:

~~~java
void deleteByExpiresAtBefore(Instant cutoff);
~~~

### Choose Direct SQL DELETE When

- You need to delete by a complex SQL predicate.
- You need a bulk delete with an explicit update count.
- You are operating on a technical table rather than an aggregate.
- You need CTEs/subqueries or database-specific syntax.
- The application actively manages child rows, constraints, auditing, and transactions.

For example:

~~~java
@Modifying
@Query("""
    DELETE FROM audit_events
    WHERE tenant_id = :tenantId
      AND created_at < :cutoff
    """)
int purgeTenantEvents(UUID tenantId, Instant cutoff);
~~~

## 11. Common Pitfalls

| Symptom | Possible cause | Resolution |
|---|---|---|
| Derived delete removes many rows | Predicate is non-unique or missing tenant condition | Add appropriate predicates and constraints |
| Deleting root rejected by foreign key | Child table still references root | Use CRUD aggregate delete, delete children first, or design cascade |
| Direct DELETE leaves orphan children | No FK/cascade and SQL only deletes root table | Delete children explicitly or fix schema |
| Assuming `deleteBy...` behaves like `delete(entity)` | Confusing query delete with CRUD entity operation | Verify generated SQL and version semantics |
| Cannot get deleted row count | Method return type is not supported by query contract | Use a supported return type or JDBC update count |
| Missing audit event after deletion | Direct SQL does not run service/callback audit logic | Write audit explicitly or use an intentional DB mechanism |
| Partial data deleted when later step fails | No shared transaction | Place `@Transactional` on the service |
| Wrong tenant's data deleted | Predicate missing tenant/security scope | Get tenant from authenticated context and add condition |
| Slow DELETE query | Predicate lacks suitable index or deletes too many rows | Inspect query plan, chunking, and indexes |
| Soft-deleted records still appear | Read query does not filter deleted state | Standardize repository/query policy |
| Child data unexpectedly cascaded | FK has `ON DELETE CASCADE` | Inspect DDL and cascade policy before deleting |

## 13. Takeaways

- **Derived delete** uses method names like `deleteBy...` or `removeBy...` to derive predicates from Java properties.
- **CRUD delete** uses an entity or identifier to delete through the repository; suitable when operating on an aggregate root per Spring Data JDBC mapping.
- **Direct SQL DELETE** via `@Modifying @Query` or `JdbcTemplate` gives control over SQL and update counts, but the application must proactively handle related tables and business rules.
- Do not assume derived delete shares identical semantics with CRUD delete on aggregates with children; verify actual SQL, version behavior, and foreign keys.
- `@MappedCollection` describes aggregate child data; a DELETE targeting only the root table does not automatically understand this mapping.
- A transaction groups operations to commit/roll back together; a cascade is a database rule for deleting related rows. These two concepts are distinct.
- Before deleting by condition, verify tenant scope, predicates, unique constraints, child rows, auditing, and data volume.
- For large bulk operations, evaluate chunking, checkpointing, indexes, and transaction logs; do not assume one giant delete statement is always suitable.
