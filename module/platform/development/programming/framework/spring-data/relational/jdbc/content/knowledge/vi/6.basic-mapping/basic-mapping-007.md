# Quoting, chữ hoa chữ thường và tên trùng từ khóa SQL

Trong **Spring Data Relational JDBC**, một entity Java được ánh xạ tới bảng và cột của cơ sở dữ liệu. Việc ánh xạ tưởng đơn giản nhưng dễ xảy ra lỗi khi tên bảng có chữ hoa, cột được tạo với dấu nháy kép, hoặc một tên trùng với từ khóa SQL như `order` hay `select`. Các lỗi này có thể xuất hiện ngay cả khi bảng tồn tại và kiểu dữ liệu của entity hoàn toàn đúng.

Để xử lý, cần hiểu ba khái niệm liên quan nhưng khác nhau:

1. **Tên định danh (identifier):** tên của bảng, cột, schema, sequence, alias; ví dụ `customer_order`, `created_at`.
2. **Quoting identifier:** đặt tên định danh trong ký hiệu trích dẫn mà hệ quản trị hiểu, ví dụ PostgreSQL dùng `"Order"` để chỉ đúng bảng có tên `Order`.
3. **Quy tắc chữ hoa/chữ thường và từ khóa:** database có thể chuẩn hóa tên không quote; khi quote, nó thường phân biệt chính xác chữ hoa/chữ thường. Một tên trùng từ khóa có thể cần quote để được chấp nhận.

Quoting ở đây là **trích dẫn tên SQL**, khác với dấu nháy đơn bao quanh giá trị chuỗi, và khác với việc bind tham số bằng `PreparedStatement`.

## 1. Phân biệt identifier, chuỗi ký tự và tham số

Xét truy vấn PostgreSQL:

```sql
SELECT id, customer_name
FROM customer_order
WHERE customer_name = 'An';
```

| Thành phần | Ý nghĩa | Quy tắc liên quan |
| --- | --- | --- |
| `customer_order` | Identifier của bảng | Có thể bị chuyển kiểu chữ theo quy tắc database nếu không quote |
| `id`, `customer_name` | Identifier của cột | Phải khớp tên mà database lưu/truy xuất |
| `'An'` | Literal kiểu chuỗi | Nháy đơn biểu thị **giá trị**, không phải tên cột |
| `?` trong JDBC | Vị trí bind giá trị | Không thể thay cho tên bảng hoặc tên cột |
| `"Order"` trong PostgreSQL | Identifier được quote | Giữ nguyên cách viết và cho phép sử dụng một số tên đặc biệt |

Với JDBC, cách gửi giá trị an toàn là:

```java
String sql = "SELECT id FROM customer_order WHERE customer_name = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setString(1, customerName);
    try (ResultSet result = statement.executeQuery()) {
        // Đọc kết quả ở đây.
    }
}
```

Không viết `WHERE customer_name = "An"` để so sánh chuỗi trên PostgreSQL: `"An"` là *tên cột*, không phải giá trị `'An'`. Nếu tên cột là từ khóa, bạn cần quote **identifier** trong SQL; nếu dữ liệu đến từ người dùng, bạn cần **bind value** bằng tham số. Hai kỹ thuật giải quyết hai vấn đề khác nhau.

## 2. Chữ hoa/chữ thường: tại sao có bảng mà SQL báo không tìm thấy?

Không phải hệ quản trị nào cũng xử lý identifier giống nhau:

- **PostgreSQL** chuyển identifier **không quote** thành chữ thường. `CustomerOrder`, `CUSTOMERORDER` và `customerorder` không quote được hiểu là cùng một tên `customerorder`. Identifier **có quote** được giữ nguyên, ví dụ `"CustomerOrder"` khác `"customerorder"`.
- **Oracle Database** thường chuẩn hóa identifier **không quote** thành chữ hoa. Khi đã quote, tên được lưu và tham chiếu theo đúng chữ hoa/chữ thường.
- **MySQL/MariaDB** có quy tắc khác biệt giữa tên bảng và tên cột. Tính phân biệt chữ hoa/chữ thường của tên database/bảng còn phụ thuộc hệ điều hành, cấu hình `lower_case_table_names` và hệ thống lưu trữ; không thể áp một quy tắc PostgreSQL cho mọi bản cài đặt MySQL.
- **H2** có các chế độ tương thích và cấu hình chuẩn hóa identifier. Kết quả test với H2 không tự chứng minh rằng tên bảng/cột sẽ hoạt động hệt như PostgreSQL.

### 2.1. Thực nghiệm với PostgreSQL

Khi tạo bảng không quote:

```sql
CREATE TABLE customer_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_name VARCHAR(100) NOT NULL
);

-- Cùng tham chiếu tới bảng customer_order:
SELECT id FROM customer_order;
SELECT id FROM CUSTOMER_ORDER;
SELECT id FROM "customer_order";

-- Khác tên: PostgreSQL sẽ tìm bảng có chữ hoa chính xác.
SELECT id FROM "CUSTOMER_ORDER";
```

Nếu trong schema chỉ có bảng `customer_order`, câu truy vấn cuối cùng sẽ báo lỗi kiểu `relation "CUSTOMER_ORDER" does not exist`. Dấu nháy kép khiến PostgreSQL **không** chuyển tên về chữ thường nữa.

Ngược lại, khi tạo bảng với chữ hoa có quote:

```sql
CREATE TABLE "CustomerOrder" (
    "Id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "CustomerName" VARCHAR(100) NOT NULL
);

-- Đúng: khớp chính xác tên có quote.
SELECT "Id", "CustomerName" FROM "CustomerOrder";

-- Sai với bảng vừa tạo: identifier không quote bị đổi thành chữ thường.
SELECT Id, CustomerName FROM CustomerOrder;
```

Hai bảng `customer_order` và `"CustomerOrder"` có thể cùng tồn tại vì tên thực tế khác nhau. Nếu thiết kế schema mới, dùng tên thống nhất như `customer_order` và `customer_name` sẽ giảm đáng kể sự nhầm lẫn giữa SQL thủ công, migration và công cụ quản lý database.

### 2.2. Dấu quote cũng phụ thuộc dialect

| Hệ quản trị | Cú pháp identifier được trích dẫn thường gặp | Ví dụ |
| --- | --- | --- |
| PostgreSQL | Dấu nháy kép `"..."` | `"Order"`, `"CustomerName"` |
| Oracle Database | Dấu nháy kép `"..."` | `"Order"` |
| H2 (chế độ SQL thông thường) | Dấu nháy kép `"..."` | `"Order"` |
| MySQL/MariaDB | Backtick | `` `order` `` |
| SQL Server | Ngoặc vuông; cũng hỗ trợ dấu nháy kép khi cấu hình thích hợp | `[Order]` |

Không được giả định mọi driver và database đều dùng dấu `"..."`. MySQL có thể hỗ trợ dấu nháy kép cho identifier khi bật `ANSI_QUOTES`, nhưng trong chế độ mặc định thường dùng backtick. SQL Server có thiết lập `QUOTED_IDENTIFIER` liên quan đến nháy kép. Khi viết SQL native, cần theo dialect thực tế.

**Quoting không phải một cơ chế thoát SQL injection cho toàn bộ câu truy vấn.** Tên bảng/cột động vẫn cần được kiểm soát chặt chẽ; tham số `?` chỉ bind **giá trị**.

## 3. Tên trùng từ khóa SQL

SQL có các từ được ngôn ngữ sử dụng làm cú pháp, ví dụ `SELECT`, `ORDER`, `GROUP`, `FROM`. Khi dùng những từ này làm tên bảng hoặc cột, parser có thể không hiểu chúng là identifier nếu không có quote.

Ví dụ sau dùng PostgreSQL và **chủ ý** tạo bảng/cột có tên khó dùng:

```sql
CREATE TABLE "order" (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "select" VARCHAR(100) NOT NULL
);

INSERT INTO "order" ("select") VALUES ('draft');

SELECT id, "select"
FROM "order"
WHERE "select" = 'draft';
```

Hai câu `FROM order` và `SELECT select FROM ...` có thể gây lỗi cú pháp vì `order` và `select` được nhận diện như từ khóa. Việc quote yêu cầu xuyên suốt trong DDL, query native, migration và mọi công cụ có tạo SQL.

Nhưng **danh sách từ khóa không hoàn toàn giống nhau giữa các hệ quản trị hoặc phiên bản**. Một tên hợp lệ trong một database có thể cần quote ở database khác. Cách phòng tránh ổn định nhất cho schema mới là:

- Đặt tên bảng theo danh từ có nghĩa rõ ràng: `customer_order` thay cho `order`, `application_user` thay cho `user` khi có rủi ro xung đột.
- Đặt tên cột cụ thể: `selected_option` thay cho `select`, `sort_order` thay cho `order`.
- Dùng chữ thường + dấu gạch dưới (`snake_case`), không dùng khoảng trắng hay ký tự đặc biệt trong tên SQL nếu không có yêu cầu tương thích schema cũ.
- Đồng bộ quy ước đặt tên giữa migration, entity, truy vấn thủ công và công cụ xuất dữ liệu.

## 4. Spring Data JDBC chọn tên bảng và cột ra sao?

Spring Data JDBC ánh xạ entity bằng metadata. Nó có thể lấy tên từ:

1. Quy ước đặt tên của framework, thông qua `NamingStrategy`.
2. Annotation `@Table` trên kiểu entity và `@Column` trên thuộc tính.
3. Tên/thiết lập đặc biệt của quan hệ, chẳng hạn `@MappedCollection(idColumn = ..., keyColumn = ...)`.

`NamingStrategy` mặc định chuyển tên kiểu camel case của class/property thành dạng tách từ bằng dấu gạch dưới. Tài liệu Spring Data Relational minh họa `SavingsAccount` → `SAVINGS_ACCOUNT` và `firstName` → `FIRST_NAME`. Khi schema dùng tên khác, đừng đoán từ tên Java: hãy khai báo tên SQL rõ ràng.

Ví dụ PostgreSQL với tên tránh từ khóa:

```sql
CREATE TABLE customer_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    placed_on DATE NOT NULL,
    total_amount NUMERIC(12, 2) NOT NULL
);
```

Ánh xạ bằng Spring Data JDBC:

```java
import java.math.BigDecimal;
import java.time.LocalDate;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer_order")
public record CustomerOrder(
        @Id Long id,
        @Column("placed_on") LocalDate placedOn,
        @Column("total_amount") BigDecimal totalAmount
) {}
```

Repository:

```java
import org.springframework.data.repository.CrudRepository;

public interface CustomerOrderRepository
        extends CrudRepository<CustomerOrder, Long> {}
```

Ở đây `@Table("customer_order")` chỉ định tên bảng thật và `@Column("placed_on")`, `@Column("total_amount")` chỉ định tên cột. Khi framework tạo SQL, nó dùng metadata này để chọn identifier. `@Id` xác định khóa chính; nó **không** có chức năng đổi tên bảng. Schema phải được tạo sẵn (ví dụ qua Flyway/Liquibase hoặc script phù hợp); Spring Data JDBC không tự tạo bảng chỉ từ entity.

### 4.1. Quoting mặc định trong Spring Data JDBC

Trong các phiên bản Spring Data JDBC hiện đại thuộc dòng Spring Data Relational 3.x, **tên bảng/cột dùng trong SQL sinh ra thường được quote theo mặc định**. Framework dùng cấu hình **mapping context** và **SQL dialect** để xử lý identifier. Điều này có hai hệ quả:

- Tên được quote giúp xử lý identifier trùng từ khóa hoặc cần giữ chữ hoa/chữ thường, miễn là tên trong metadata khớp tên database.
- Vì tên quote có thể phân biệt chữ hoa/chữ thường, metadata `CUSTOMER_ORDER` có thể **không** khớp bảng `customer_order` được tạo không quote trên PostgreSQL.

Trong dòng 3.x, `RelationalMappingContext.setForceQuote(false)` cho phép điều chỉnh việc quote toàn cục. Không tắt quoting chỉ để làm cho một bảng tình cờ truy vấn được: thay đổi này còn tác động đến bảng/cột khác, nhất là những tên trùng từ khóa hoặc schema có chữ hoa. Khi tùy chỉnh, nên kiểm tra phiên bản Spring Data đang chạy, mapping context thực tế và SQL được tạo.

Trong API Spring Data Relational 4.x, `JdbcMappingContext` có các cách khởi tạo cho quoted/plain identifiers như `forQuotedIdentifiers()` và `forPlainIdentifiers()`. Tên API dành cho việc cấu hình mapping có thể khác nhau giữa các phiên bản; không nên sao chép đoạn cấu hình từ tài liệu một dòng phiên bản sang dự án cũ mà không kiểm tra.

> Quy tắc quan trọng: **`@Table` và `@Column` khai báo tên logic, còn việc dùng dấu quote nào do mapping/dialect quyết định.** Khi quoting đang bật, hãy khai báo `@Table("Order")`, không tự nhét dấu nháy SQL vào chuỗi annotation kiểu `@Table("\"Order\"")`; cách làm sau có thể khiến ký tự quote bị coi là một phần của tên.

### 4.2. Ánh xạ một schema cũ có tên chữ hoa và từ khóa

Giả sử không được đổi schema PostgreSQL đang tồn tại:

```sql
CREATE TABLE "Order" (
    "Id" BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    "Select" VARCHAR(100) NOT NULL
);
```

Entity tương ứng:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("Order")
public record LegacyOrder(
        @Id @Column("Id") Long id,
        @Column("Select") String selectedValue
) {}
```

Với mapping context có quoting và PostgreSQL dialect, các identifier cần được render tương tự `"Order"`, `"Id"`, `"Select"` để khớp schema. Trong annotation, `"Order"` là một **Java string có nội dung Order**, không phải câu SQL đã chứa quote.

Nếu database thực tế dùng `"ORDER"`, `"order"` hoặc `order` được tạo không quote, đó có thể là các tên **khác nhau**. Bạn phải ánh xạ theo tên thật trong catalog, không theo cách mắt người đọc bỏ qua hoa/thường.

### 4.3. Tên cột của quan hệ cũng có thể bị ảnh hưởng

Nếu aggregate có collection hoặc tham chiếu được Spring Data JDBC quản lý, framework có thể cần các cột khóa ngoại và cột lưu thứ tự/map key. Tên của những cột này chịu ảnh hưởng của convention, `NamingStrategy` và `@MappedCollection`.

Ví dụ:

```java
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer_order")
public record OrderAggregate(
        @Id Long id,
        @MappedCollection(
                idColumn = "order_id",
                keyColumn = "position_index")
        List<OrderLine> lines
) {}

@Table("order_line")
public record OrderLine(String sku, int quantity) {}
```

Trong mô hình `List` theo quy ước Spring Data JDBC, bảng con cần cột liên kết `order_id` và cột chỉ vị trí `position_index`; tên thật phải nhất quán với các khai báo mapping và DDL. Đây là ví dụ về **tên cột phục vụ quan hệ**, không phải cấu hình quote riêng cho collection. Nếu chỉ chỉnh `@Table` của aggregate mà để cột back reference theo tên cũ, repository vẫn có thể lỗi vì thiếu cột.

## 5. Generated SQL và SQL tự viết không phải một thứ

Repository như `CrudRepository.save`, `findById` thường tạo SQL dựa trên metadata của Spring Data JDBC. Khi khai báo `@Query`, `JdbcTemplate` hoặc `NamedParameterJdbcTemplate`, **SQL bạn viết là SQL bạn phải chịu trách nhiệm về cú pháp identifier**.

Ví dụ Spring Data JDBC repository trên PostgreSQL:

```java
import java.util.Optional;
import org.springframework.data.jdbc.repository.query.Query;
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.query.Param;

interface LegacyOrderRepository extends CrudRepository<LegacyOrder, Long> {

    @Query("""
        SELECT "Id", "Select"
        FROM "Order"
        WHERE "Id" = :id
        """)
    Optional<LegacyOrder> findManually(@Param("id") Long id);
}
```

Ở đây:

- `"Id"`, `"Select"` và `"Order"` là identifier PostgreSQL phải quote để khớp bảng/cột.
- `:id` là **named parameter** do Spring Data xử lý, không phải identifier và không thể thay cho tên cột.
- Dấu nháy kép trong Java text block là ký tự SQL cần giữ, không nên loại bỏ.
- Truy vấn này phụ thuộc cú pháp PostgreSQL; khi chuyển database khác, SQL native phải được kiểm tra lại theo dialect.

Với `JdbcTemplate`, cùng ý tưởng:

```java
String sql = "SELECT \"Select\" FROM \"Order\" WHERE \"Id\" = ?";
String selected = jdbcTemplate.queryForObject(
        sql, String.class, orderId);
```

`queryForObject` yêu cầu kết quả đúng **một hàng và một cột** để ánh xạ trực tiếp sang `String`. Nếu không có hàng, có nhiều hơn một hàng hoặc câu `SELECT` trả nhiều cột, phương thức có thể ném exception. Với kết quả tùy chọn, dùng `query(...)` hoặc repository trả `Optional` theo thiết kế.

## 6. Đừng nhầm alias, tên cột thực và tên property Java

Trong SQL viết tay, alias thay đổi **nhãn cột trong kết quả truy vấn**:

```sql
SELECT "Select" AS selected_value
FROM "Order";
```

Alias `selected_value` không đổi tên cột thật `"Select"` trong bảng. Nếu dùng `RowMapper` tự viết, phải đọc đúng label trong `ResultSet`:

```java
String sql = "SELECT \"Select\" AS selected_value FROM \"Order\"";
List<String> values = jdbcTemplate.query(
        sql, (rs, rowNum) -> rs.getString("selected_value"));
```

Khi dùng Spring Data JDBC `@Query` để ánh xạ entity, các column label cần phù hợp với metadata mà mapper mong đợi. Với câu SQL custom có alias khác tên cột mapping, kết quả có thể không được gán vào property như ý. Đừng giả định alias tùy ý sẽ tự khớp với tên property Java.

Nếu phải dùng SQL có `JOIN` và nhiều bảng có cùng tên cột `id`, nên đặt alias rõ ràng khi tự map DTO. Phân biệt:

- `@Column("Select")`: tên cột SQL của entity.
- `String selectedValue`: tên thuộc tính Java.
- `AS selected_value`: nhãn cột trả về của một truy vấn SQL cụ thể.

Ba tên này liên quan qua mapping, nhưng không thể hoán đổi tùy ý.

## 7. Quoting và bảo mật khi tạo SQL động

`PreparedStatement` bảo vệ việc truyền **giá trị**; dấu `?` không thể được sử dụng để thay cho tên bảng, cột, schema hoặc hướng sắp xếp.

Ví dụ cách **không đúng** khi muốn thay cột sắp xếp:

```java
// Không biến dấu ? thành tên cột SQL.
String sql = "SELECT * FROM customer_order ORDER BY ?";
```

Ngay cả khi bind chuỗi `"placed_on"`, database nhận đó như một **giá trị**, không phải cú pháp identifier `placed_on`. Cũng không được ghép trực tiếp tên cột do người dùng cung cấp:

```java
// Không an toàn: userInputSortColumn đến từ bên ngoài.
String sql = "SELECT * FROM customer_order ORDER BY " + userInputSortColumn;
```

Nếu cần cho phép chọn cột, hãy **ánh xạ lựa chọn hợp lệ sang một tập identifier cố định do ứng dụng sở hữu**:

```java
String sortColumn = switch (sortKey) {
    case "date" -> "placed_on";
    case "total" -> "total_amount";
    default -> throw new IllegalArgumentException("Unsupported sort key");
};

String sql = """
    SELECT id, placed_on, total_amount
    FROM customer_order
    ORDER BY """ + sortColumn;
```

Nếu cho phép chọn `ASC`/`DESC`, cũng phải ánh xạ bằng whitelist. Với Spring Data JDBC, có thể tận dụng API sắp xếp của repository khi phù hợp, nhưng vẫn cần kiểm soát các thuộc tính được phép đưa vào yêu cầu từ người dùng. **Quoting không biến SQL ghép từ chuỗi tùy ý thành an toàn.**

## 8. Khi chuyển đổi database hoặc schema hiện hữu

Với schema mới, nên có quy ước đơn giản: bảng/cột dùng `lower_snake_case`, không có khoảng trắng, không trùng từ khóa SQL và giữ quy tắc thống nhất giữa DDL với `@Table`/`@Column`. Đối với schema cũ đã có tên quoted/camel-case, cần chọn một trong hai hướng rõ ràng.

| Hướng xử lý | Khi phù hợp | Đánh đổi |
| --- | --- | --- |
| Giữ nguyên schema và cấu hình mapping/quoting chính xác | DB đang có người dùng khác, chưa thể đổi bảng/cột | Phải duy trì chữ hoa/chữ thường và quote trong mọi SQL thủ công |
| Migration đổi về tên chuẩn | Có quyền quản lý schema và đủ thời gian triển khai | Phải cập nhật query, views, stored procedures, báo cáo, service khác và mapping entity |

Ví dụ migration PostgreSQL **minh họa** từ schema có tên quoted:

```sql
-- Giả sử đã kiểm tra ảnh hưởng đến các đối tượng phụ thuộc.
ALTER TABLE "Order" RENAME TO customer_order;
ALTER TABLE customer_order RENAME COLUMN "Id" TO id;
ALTER TABLE customer_order RENAME COLUMN "Select" TO selected_value;
```

Sau migration, entity cần sửa từ `@Table("Order")` thành `@Table("customer_order")`, từ `@Column("Select")` thành `@Column("selected_value")`. Migration phải được version control và phối hợp với các client/schema dependency; ví dụ chỉ mô tả cú pháp, không đại diện một kế hoạch deploy an toàn cho hệ thống đang có dữ liệu thật.

Nếu đổi database từ PostgreSQL sang MySQL, nên thử **schema DDL, migration và repository thật** trên database đích. Test H2 với compatibility mode có ích để phát triển nhưng không thay thế được integration test trên database đang vận hành.

## 9. Cách điều tra lỗi tên bảng hoặc cột

Các lỗi thường gặp:

| Triệu chứng | Nguyên nhân có thể | Cách xác định |
| --- | --- | --- |
| PostgreSQL: `relation "CUSTOMER_ORDER" does not exist` | Mapping dùng identifier quoted chữ hoa, bảng thật là `customer_order` | So sánh tên thật trong catalog với `@Table`/`NamingStrategy` |
| PostgreSQL: `column "Select" does not exist` | Cột thật khác hoa/thường hoặc alias query khác tên | Xem tên cột trong schema, `@Column` và câu SQL đã render |
| `syntax error at or near "order"` | `order` bị dùng như tên bảng không quote | Đổi tên bảng hoặc sử dụng quoting đúng dialect |
| `BadSqlGrammarException` | SQL sinh ra/tự viết không khớp tên hoặc cú pháp database | Xem SQL, cause `SQLException`, SQLState và dialect |
| Query hoạt động bằng psql nhưng repository lỗi | psql query không quote, repository có quoting hoặc NamingStrategy khác | So sánh nguyên văn SQL và identifier thực tế |
| Test H2 qua nhưng prod PostgreSQL lỗi | Quy tắc case folding, quote hoặc reserved keywords khác | Tái hiện trên PostgreSQL cùng schema |
| Custom `@Query` trả dữ liệu không như mong đợi | Alias không tương ứng với mapping hoặc nhầm nháy đơn/nháy kép | Kiểm tra tên cột trả về và mapper/DTO |

### 9.1. Kiểm tra tên thật từ metadata PostgreSQL

Để kiểm tra bảng và cột trong schema `public`:

```sql
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_name ILIKE '%order%';

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'Order'
ORDER BY ordinal_position;
```

Điều kiện `table_name = 'Order'` ở truy vấn metadata là **so sánh giá trị chuỗi**, nên dùng dấu nháy đơn. Nó khác `SELECT ... FROM "Order"`, trong đó `"Order"` là identifier. Khi tên bảng thực tế là `customer_order`, thay literal trong truy vấn metadata tương ứng.

Với PostgreSQL CLI, `\dt` và `\d "Order"` cũng có thể hỗ trợ kiểm tra, nhưng đó là lệnh của `psql`, **không phải SQL chuẩn để gọi bằng JDBC**.

### 9.2. Đọc SQL lỗi theo đúng ký tự

Khi debug, cần biết:

1. Tên bảng/cột được định nghĩa trong migration/DDL là gì, có quote hay không?
2. Tên được ánh xạ trong `@Table`, `@Column` và `NamingStrategy` là gì?
3. Spring Data JDBC đang render identifier có quote không? Dialect/phiên bản thực tế là gì?
4. SQL có xuất phát từ repository được sinh tự động hay từ `@Query`/`JdbcTemplate` tự viết?
5. Có dùng alias trong `SELECT` khác với column label mà mapper mong đợi không?

Có thể bật log SQL trong môi trường phát triển một cách có kiểm soát để quan sát tên bảng/cột mà ứng dụng gửi đi. Cần tránh log giá trị tham số nhạy cảm hoặc bật log quá chi tiết ở production. Nếu có lỗi SQL, hãy đọc cả exception gốc và SQLState thay vì chỉ nhìn thông báo tổng quát của Spring.

## 10. Bài tập vận dụng

**Bài 1 — Case folding trên PostgreSQL.** Tạo bảng `customer_order` không quote. Chạy lần lượt `SELECT ... FROM CUSTOMER_ORDER`, `SELECT ... FROM "customer_order"` và `SELECT ... FROM "CUSTOMER_ORDER"`. Giải thích vì sao câu cuối khác hai câu đầu.

**Bài 2 — Tên trùng từ khóa.** Tạo bảng `"order"` có cột `"select"`. Viết `@Table`, `@Column` tương ứng, thử thao tác `save`/`findById` với Spring Data JDBC có quoting. Sau đó thử một query thủ công không quote để quan sát lỗi parser.

**Bài 3 — Mismatch của annotation.** Với bảng `"CustomerOrder"` có cột `"CustomerName"`, thử ánh xạ sai thành `@Table("customerorder")` hoặc `@Column("customer_name")`. Quan sát SQL lỗi và sửa metadata cho khớp tên thật.

**Bài 4 — SQL động an toàn.** Cho người dùng chọn sắp xếp theo `placed_on` hoặc `total_amount`. Viết whitelist từ input đến identifier cố định và bind các giá trị trong mệnh đề `WHERE` bằng parameter.

## 11. Kết luận kỹ thuật

Để ánh xạ Spring Data JDBC ổn định, cần đối chiếu **tên identifier thực tế trong database**, **tên được khai báo qua mapping metadata**, **quy tắc quote/case của database dialect** và **SQL thực sự được thực thi**. Khi thiết kế schema mới, `lower_snake_case` và tránh từ khóa SQL là lựa chọn dễ duy trì. Với schema legacy, giữ đúng chữ hoa/chữ thường và cấu hình quoting giúp repository truy cập đúng bảng/cột. Dấu quote cho identifier và parameter binding cho value là hai công cụ khác nhau; sử dụng đúng cả hai sẽ tránh lỗi ánh xạ và nguy cơ ghép SQL không an toàn.
