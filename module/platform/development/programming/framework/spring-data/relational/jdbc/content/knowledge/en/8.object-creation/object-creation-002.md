# Selecting Constructors and Factories with `@PersistenceCreator`

When Spring Data JDBC reads a data row and reconstructs a domain object, the framework needs to know **which constructor or static factory method to call**. A Java class may have a no-arg constructor, a full-argument constructor, a constructor for creating new business instances, and multiple factory methods. If the instantiation path is not clearly identified, object mapping may pick an unsuitable path or fail to map data into the object.

Spring Data provides the **`@PersistenceCreator`** annotation to mark the constructor or static factory method used for persistence mapping. This annotation is especially useful when a domain model has multiple ways to create objects, needs to keep objects immutable, or must remain compatible with an existing database schema.

This lesson focuses on how Spring Data Relational/JDBC selects constructors, how to use `@PersistenceCreator` with constructors and factories, parameter mapping rules, and common errors when materializing entities.

## 1. Why Does Object Mapping Need Constructor Selection?

Suppose the database has a customers table:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    display_name VARCHAR(160) NOT NULL,
    status VARCHAR(24) NOT NULL
);
```

The domain model can be designed to be immutable:

```java
@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;
    private final CustomerStatus status;

    public Customer(
        Long id,
        String email,
        String displayName,
        CustomerStatus status
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
        this.status = status;
    }

    // Getters omitted.
}
```

When the repository runs:

```java
Customer customer = customerRepository.findById(10L)
    .orElseThrow();
```

Spring Data JDBC needs to create a `Customer` instance from the values of the database row. The framework must determine:

- Which constructor receives data from the database?
- Which constructor parameter corresponds to which property?
- Which Java type is each SQL data type converted into?
- How will properties not passed to the constructor be assigned?

This is the **object materialization** step (reconstructing an object from stored data). `@PersistenceCreator` tells the mapping framework the preferred creation path when a class offers multiple options.

## 2. What Component Does `@PersistenceCreator` Belong To?

The annotation is defined in Spring Data Commons:

```java
import org.springframework.data.annotation.PersistenceCreator;
```

Spring Data Relational/JDBC uses the object mapping mechanism of the Spring Data ecosystem. Thus `@PersistenceCreator` is not a JDBC-specific annotation, nor is it a JPA annotation.

Component responsibilities:

| Component | Responsibility |
| --- | --- |
| Spring Data Commons | Provides the `@PersistenceCreator` annotation and shared infrastructure to identify constructors/factories used for persistence. |
| Spring Data Relational | Provides mapping metadata for domain objects and relational properties. |
| Spring Data JDBC | Uses mapping metadata to construct aggregates/entities when reading data via JDBC. |
| Spring JDBC | Executes SQL operations and supplies row data to the mapping layer. |

The annotation marks **the object instantiation path when Spring Data reads data**. It does not replace `@Autowired` in dependency injection, does not configure repositories, and does not change how the database generates primary keys.

## 3. Constructor Selection Rules

Spring Data can use a constructor to create an object and then populate the remaining properties afterward. Practical principles to keep in mind:

1. If a class has only **one constructor**, that constructor can be used as the persistence constructor without an annotation.
2. If a class has multiple constructors, mark the constructor you want the mapping framework to use with `@PersistenceCreator`.
3. If no persistence creator is specified and the class has an appropriate no-arg constructor, the framework may use the no-arg constructor and then populate properties via the property population mechanism.
4. If a class has multiple instantiation options or a constructor structure that is hard to infer, declare `@PersistenceCreator` explicitly to avoid relying on implicit selection.
5. A static factory method annotated with `@PersistenceCreator` can be used instead of a constructor.

Do not design a class with multiple constructors that could all plausibly be used for mapping and expect the framework to guess your business intent.

### 3.1. Class with a Single Constructor

Example:

```java
@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    public Customer(Long id, String email, String displayName) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

The class has only one constructor. Spring Data can use that constructor to pass the values of the corresponding properties. There is no need to add `@PersistenceCreator` solely to mark a single constructor.

### 3.2. Multiple Constructors and Selecting One for Persistence

Suppose the application has a short constructor for creating a new customer and a full constructor for restoring a customer from the database:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    public Customer(String email, String displayName) {
        this(null, email, displayName);
    }

    @PersistenceCreator
    public Customer(
        Long id,
        String email,
        String displayName
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

The two constructors serve different purposes:

- `Customer(String, String)` serves the use case of creating a new customer without an ID yet.
- `Customer(Long, String, String)` receives complete data, including the ID already stored by the database.

`@PersistenceCreator` helps Spring Data choose the second constructor when materializing data. Business code can still call the short constructor to create a new customer.

### 3.3. No-Arg Constructor and Full Constructor

Some legacy entities have a no-arg constructor required by another framework or library:

```java
@Table("customers")
public class Customer {

    @Id
    private Long id;

    private String email;
    private String displayName;

    protected Customer() {
        // Supports no-arg instantiation when needed.
    }

    @PersistenceCreator
    public Customer(
        Long id,
        String email,
        String displayName
    ) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }
}
```

When there are multiple constructors, the annotation clearly identifies the persistence constructor. Without marking it, a no-arg instantiation path might be used and the framework would have to populate fields afterward. That may be undesirable if the entity needs to enforce invariants immediately upon creation.

For immutable domain models, a full constructor is usually easier to control: the object is created with all necessary state from the very start.

## 4. Mapping Constructor Parameters to Properties

When Spring Data invokes the persistence constructor, the framework must match each parameter to a property of the domain object. Therefore, **constructor parameter names must correspond to property names**, and data types must be convertible from stored values.

Example:

```java
@PersistenceCreator
public Customer(Long id, String email, String displayName) {
    this.id = id;
    this.email = email;
    this.displayName = displayName;
}
```

Parameters `id`, `email`, and `displayName` correspond to properties of the same names. Physical column names in the database may differ from property names when using `@Column`; constructor binding operates on **domain model properties**, without requiring parameter names to match SQL column names.

### 4.1. Ensuring Java Retains Parameter Names

For regular Java classes, parameter names may not be preserved in bytecode unless the compiler is configured to store parameter name metadata. In that case, the mapping framework may be unable to determine the corresponding property names.

In Gradle Groovy, you can enable the `-parameters` option:

```groovy
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs.add('-parameters')
}
```

With the Maven Compiler Plugin, the corresponding configuration is:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <parameters>true</parameters>
    </configuration>
</plugin>
```

Some plugin/framework versions or build setups already enable this option. If your project relies on parameter name discovery, check the actual compiler configuration instead of assuming variable names in source always exist at runtime.

### 4.2. Java Records

Java `record` is a natural choice for immutable objects. A record has a canonical constructor corresponding to the record components:

```java
@Table("customers")
public record Customer(
    @Id Long id,
    String email,
    String displayName
) {}
```

If a record only has its canonical constructor, Spring Data can use that constructor without needing `@PersistenceCreator`.

When adding secondary constructors or static factories, clearly specify which instantiation path mapping should use. Record component names have dedicated record metadata, yet property naming rules must still remain consistent with the domain model.

### 4.3. Constructor Parameter Names Not Matching Properties

Example to avoid:

```java
@PersistenceCreator
public Customer(Long customerId, String emailAddress) {
    this.id = customerId;
    this.email = emailAddress;
}
```

If the actual properties are `id` and `email`, parameters `customerId` and `emailAddress` do not automatically become the corresponding property names just because the constructor body assigns them to the right fields.

Rename the parameters to match:

```java
@PersistenceCreator
public Customer(Long id, String email) {
    this.id = id;
    this.email = email;
}
```

If complex data conversion is needed or a property has a special name, use appropriate mapping/conversion mechanisms instead of relying on arbitrary parameter names.

## 5. Using Static Factory Methods with `@PersistenceCreator`

Constructors are not the only way to create objects. A class can provide a **static factory method** annotated with `@PersistenceCreator`. Spring Data uses that factory as the persistence creator.

This approach is useful when:

- Constructors need to stay private/protected to guard object creation.
- The domain model uses expressive factory names such as `rehydrate` or `restore`.
- You want to centralize object creation logic in one place.
- There are multiple constructors/factories serving different use cases.

Example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.PersistenceCreator;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private final Long id;

    private final String email;
    private final String displayName;

    private Customer(
        Long id,
        String email,
        String displayName
    ) {
        if (email == null || email.isBlank()) {
            throw new IllegalArgumentException("Email is required");
        }

        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }

    public static Customer register(
        String email,
        String displayName
    ) {
        return new Customer(null, email, displayName);
    }

    @PersistenceCreator
    public static Customer rehydrate(
        Long id,
        String email,
        String displayName
    ) {
        return new Customer(id, email, displayName);
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getDisplayName() {
        return displayName;
    }
}
```

The two creation paths carry different semantics:

| Creation Path | Purpose | How Called |
| --- | --- | --- |
| `Customer.register(email, name)` | Creates a new customer per business use case. | Called directly by application code. |
| `Customer.rehydrate(id, email, name)` | Reconstructs a customer from persistence data. | Called by Spring Data when mapping data. |

The factory name `rehydrate` helps readers recognize the intent of restoring saved state. This is a design choice, not a method name mandated by the framework.

### 5.1. Factory Method Design Requirements

A factory method used for persistence should:

- Be a **static** method on the domain type being materialized.
- Be annotated with `@PersistenceCreator`.
- Return the corresponding domain type.
- Have parameters matching persistent properties that can be converted by the mapping framework.
- Be callable by the mapping infrastructure; using a `public static` method is clear and broadly compatible.
- Not depend on the current request, HTTP session, or a Spring service requiring injection.

A persistence factory is invoked while reading data, which may happen very frequently. Keep object creation logic concise, deterministic, and free of side effects such as sending emails, calling external APIs, or writing extra database records.

### 5.2. Factory Methods Are Not Spring Bean Factories

Distinguish two concepts:

- `@PersistenceCreator`: instructs **Spring Data mapping** which factory/constructor to choose when creating a domain object from data.
- `@Bean` or `@Component`: registers an object managed by the Spring IoC container.
- `@Autowired`: instructs Spring dependency injection to resolve bean dependencies.

Do not add `@Autowired` to a factory just so Spring Data JDBC will use it. A persistence factory is not a service bean and is not used as a dependency injection mechanism.

## 6. Constructors and Factories in Immutable Entities

An immutable entity preserves its state after creation; it exposes no public setters for arbitrary modification. This is a useful choice for protecting invariants and reducing invalid states.

Example with a Java record:

```java
@Table("orders")
public record PurchaseOrder(
    @Id Long id,
    Long customerId,
    OrderStatus status
) {
    public PurchaseOrder {
        if (customerId == null) {
            throw new IllegalArgumentException("customerId is required");
        }
        if (status == null) {
            throw new IllegalArgumentException("status is required");
        }
    }
}
```

Because a record has a canonical constructor, Spring Data can use it to construct the object. The compact constructor lets you validate data as soon as the object is created.

If the database contains a NULL value for a column mapped to a primitive such as `int`, Java cannot represent NULL in a primitive. Use a wrapper type such as `Integer` when NULL is a valid state, or adjust schema/constraints so the data always has a value.

### 6.1. Properties Not Included in the Constructor

A class may place some properties in the persistence constructor and populate remaining properties afterward via setters or field access. However, if a property is `final` and has no suitable mutation mechanism, it should be passed via the constructor/factory.

For immutable objects, prefer placing all required persistent state in the constructor. This avoids creating an object in an incomplete state and finishing it with subsequent assignments.

Spring Data also supports property population mechanisms such as setters, field access, and wither methods depending on the property type. Do not rely on hidden setters or field reflection when a full constructor can express object state more clearly.

### 6.2. Database-Generated IDs and Immutable Objects

When saving a new entity, the database may generate the ID. With immutable objects, the ID value cannot be assigned directly to a final field after insert. You can design the domain type with a wither method that returns a new instance:

```java
public Customer withId(Long newId) {
    return new Customer(newId, email, displayName);
}
```

Spring Data supports mechanisms for creating a new instance when an immutable property needs to be populated according to mapping metadata. When using a record, the framework can also use the constructor to create a new record containing the generated ID value.

In application code, always prefer using the object returned from `repository.save(entity)` to receive the post-persistence state:

```java
Customer created = Customer.register(
    "an@example.test",
    "Nguyen An"
);

Customer saved = customerRepository.save(created);

Long generatedId = saved.getId();
```

Do not assume the original `created` variable is always mutated in place.

## 7. Constructor Mapping with `@Column` and Column Names Different from Properties

A schema may use column names different from property names:

```sql
CREATE TABLE customers (
    customer_no BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    contact_email VARCHAR(255) NOT NULL,
    display_label VARCHAR(160) NOT NULL
);
```

Domain model:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    @Column("customer_no")
    private final Long id;

    @Column("contact_email")
    private final String email;

    @Column("display_label")
    private final String displayName;

    @PersistenceCreator
    public Customer(Long id, String email, String displayName) {
        this.id = id;
        this.email = email;
        this.displayName = displayName;
    }
}
```

Property/constructor parameter names remain `id`, `email`, `displayName`. The `@Column` annotation maps properties to the physical columns `customer_no`, `contact_email`, and `display_label`.

| Constructor Parameter | Domain Property | Database Column |
| --- | --- | --- |
| `id` | `id` | `customer_no` |
| `email` | `email` | `contact_email` |
| `displayName` | `displayName` | `display_label` |

Do not name the constructor parameter `contact_email` just because the database column uses that name. Constructor mapping operates at the domain property level.

## 8. `@PersistenceCreator` in Spring Data JDBC Aggregates

Spring Data JDBC reads and builds the **aggregate root** together with objects belonging to the aggregate according to mapping metadata. Constructor selection applies not only to the root, but can also apply to child objects/value objects being materialized.

Order aggregate example:

```java
@Table("purchase_orders")
public class PurchaseOrder {

    @Id
    private final Long id;

    private final String orderNumber;

    @MappedCollection(idColumn = "order_id")
    private final List<OrderLine> lines;

    @PersistenceCreator
    public PurchaseOrder(
        Long id,
        String orderNumber,
        List<OrderLine> lines
    ) {
        this.id = id;
        this.orderNumber = orderNumber;
        this.lines = List.copyOf(lines);
    }
}
```

Child object:

```java
@Table("order_lines")
public class OrderLine {

    @Id
    private final Long id;

    private final String sku;
    private final int quantity;

    @PersistenceCreator
    public OrderLine(Long id, String sku, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }
        this.id = id;
        this.sku = sku;
        this.quantity = quantity;
    }
}
```

This illustrates object mapping structure; an actual schema requires the `order_id` foreign key and corresponding columns. `@MappedCollection` defines a collection relationship belonging to the aggregate. When Spring Data JDBC materializes the root, it must also construct child elements according to their respective mapping.

Note: the root constructor may be invoked with already-mapped child objects. Do not assume the order of SQL operations or how many times a constructor is called is a stable business API; keep constructors/factories free of side effects.

## 9. Distinguishing `@PersistenceCreator` from Other Annotations

| Annotation | Purpose | Scope |
| --- | --- | --- |
| `@PersistenceCreator` | Selects constructor/static factory for Spring Data object mapping. | Spring Data Commons. |
| `@Autowired` | Specifies dependency injection for a Spring bean. | Spring Framework IoC. |
| `@Bean` | Registers an object returned by a configuration method into the Spring context. | Spring Framework IoC. |
| `@Table` | Specifies the relational table for a domain type. | Spring Data Relational. |
| `@Column` | Specifies the relational column for a property. | Spring Data Relational. |
| `@Id` | Marks the identifier property. | Spring Data Commons. |
| `@Version` | Marks the version property for optimistic locking. | Spring Data Commons. |

`@PersistenceCreator` is also not the JPA `@ConstructorResult` annotation used in some native query mappings. The two annotations serve different persistence mechanisms.

## 10. Integration with Lombok and Generated Code

Lombok can generate multiple constructors:

```java
@NoArgsConstructor
@AllArgsConstructor
@RequiredArgsConstructor
public class Customer {
    // fields
}
```

When combining these annotations, a class may end up with multiple constructors after compilation that do not appear directly in source code. Spring Data mapping still has to choose an unambiguous creation path.

How to handle it:

- Inspect the actual constructors generated by Lombok.
- If multiple constructors exist, mark the desired one with `@PersistenceCreator` (using the annotation on an explicitly declared constructor when needed).
- Ensure constructor parameters have names matching persistent properties.
- Enable parameter name metadata if the build setup does not already include it.
- Avoid creating an empty constructor just to "make the framework run" if the domain model requires invariants to be checked immediately upon materialization.

With Lombok builders, `@Builder` primarily serves object creation from application code. Do not assume Spring Data automatically uses the builder to construct entities when reading from the database. If you want persistence to use a static factory, mark the factory with `@PersistenceCreator` and design clear parameters.

## 11. Testing Constructor/Factory Mapping

A repository test verifies that Spring Data JDBC actually uses the creation path and assigns values properly:

```java
import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;

@DataJdbcTest
class CustomerRepositoryTest {

    @Autowired
    CustomerRepository customers;

    @Test
    void materializesCustomerFromPersistenceCreator() {
        Customer saved = customers.save(
            Customer.register(
                "an@example.test",
                "Nguyen An"
            )
        );

        Customer loaded = customers.findById(saved.getId())
            .orElseThrow();

        assertThat(loaded.getEmail()).isEqualTo("an@example.test");
        assertThat(loaded.getDisplayName()).isEqualTo("Nguyen An");
    }
}
```

This test requires a corresponding schema and test datasource configuration. It confirms data can flow from object to database and back into an object. To explicitly verify that a factory was called, design a test at the appropriate mapping level or inspect state produced by the factory; avoid adding side effects solely to count invocations in production code.

A useful integration test should verify:

- Database rows are read into the right properties.
- The constructor/factory can accept converted data types.
- Properties not passed to the constructor still have a valid population path if required by design.
- NULL/enum/date/time values are handled properly according to schema and conversions.
- Generated IDs are reflected in the object returned from `save`.
- The constructor/factory does not throw exceptions on valid existing database data.

## 12. Common Errors When Using `@PersistenceCreator`

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Mapping cannot determine constructor | Multiple constructors without a clear persistence creator. | Mark the desired constructor/factory with `@PersistenceCreator`. |
| Constructor parameter not assigned properly | Parameter name does not match property or parameter name metadata is missing. | Name parameters to match properties, enable `-parameters` when needed. |
| Factory method not used | Method is not static, not annotated, or lacks a matching mapping signature. | Use a static factory and annotate with `@PersistenceCreator`. |
| Constructor throws exception when reading data | Legacy data in the database violates new invariants or NULL does not fit the Java type. | Check schema/data, convert or migrate before enforcing new domain rules. |
| Immutable field still lacks a value | Property is not in the constructor and has no suitable setter/field/wither. | Add the property to the persistence constructor or provide an appropriate immutable population mechanism. |
| Wrong annotation used | Imported wrong package or confused with DI/JPA annotations. | Import `org.springframework.data.annotation.PersistenceCreator`. |
| Factory calls external API when reading data | Mixing persistence reconstitution with business side effects. | Keep factory pure, fast, and independent of external services. |
| Tests pass but production fails | Schema, data types, or parameter metadata differ between environments. | Test against the target database/dialect and corresponding build artifact. |

### 12.1. Legacy Data May Violate New Invariants

A constructor might validate that email is non-blank or status is valid. However, if the database already contains old rows with NULL email or deprecated enum values, the constructor may throw an exception as soon as the repository reads that row.

This is not necessarily a bug in `@PersistenceCreator`. It can be a sign that new domain rules have not been reconciled with existing data. Before deploying, determine what data is valid, what migrations/backfills need to run, and how the application will handle invalid records.

## 13. When to Use a Constructor vs. a Factory?

| Criterion | Annotated Constructor | Annotated Static Factory |
| --- | --- | --- |
| Simple model, single creation path | Very suitable; usually no annotation needed if there is only one constructor. | Can be used, though not required. |
| Multiple constructors | Use `@PersistenceCreator` to select the persistence constructor. | Can annotate a factory to separate the reconstitution path. |
| Want private/protected constructors | Depends on visibility and mapping setup. | Public/static factory expresses intent clearly. |
| Want to name the restoration operation | Constructor names cannot carry business meaning. | Names like `rehydrate`, `restore` clarify intent. |
| Creation logic needs multiple steps | Constructor can become long and hard to read. | Factory groups and names logic, though it should not call external services. |
| Java record | Canonical constructor is usually sufficient. | Can use a factory if a separate creation path is needed and supported by mapping. |

There is no rule that factories are always better than constructors. Choose the approach that keeps the domain model clear, preserves invariants, and gives the mapping framework a deterministic creation path.

## 14. Workflow for Applying in a Spring Data JDBC Codebase

When an entity needs multiple constructors or factories:

1. Identify which properties constitute the persistent state needed to construct the object from the database.
2. Check the number of existing constructors and static factories.
3. Choose a single persistence creator and mark it with `@PersistenceCreator` if disambiguation is needed.
4. Name parameters after domain model properties; ensure the compiler preserves parameter name metadata when using regular Java classes.
5. Check data types, nullability, enums/conversions, and invariants enforced by the constructor/factory.
6. Verify remaining properties can be assigned via an appropriate population mechanism, especially for immutable entities.
7. Run repository tests against a compatible schema/database and use the object returned from `save` when a generated ID is needed.

> **`@PersistenceCreator` tells Spring Data which constructor or static factory to use to build a domain object from stored data.** Parameter names must bind accurately to properties, and invariants should be protected right at the creation path. When a domain model has multiple ways to create objects, an explicitly chosen persistence creator keeps mapping stable and easy to understand.
