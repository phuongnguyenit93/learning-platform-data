# What Is Spring Data JDBC and What Data Persistence Problems Does It Solve?

When building a Java application, data usually has to outlive the runtime of the program. Customer accounts, orders, inventory, or payment history cannot simply live in variables or an in-memory `List`: when the application restarts, that memory is lost. The application needs to **persist data durably**, read back saved data, update the exact right record, and coordinate multiple write operations safely.

**Spring Data JDBC** is a member of the Spring Data ecosystem that supports mapping Java objects to tables in a relational database and provides **repositories** to perform common data access operations. It uses JDBC as its foundation, while allowing developers to focus on the data model and business rules rather than writing the same connection, query, and mapping boilerplate in many places.

> **Key takeaway:** Spring Data JDBC handles most of the repetitive work of persisting and retrieving **aggregates** in a Java application on a relational database. It is not a database itself, does not guarantee durable storage if you use an in-memory-only database, and does not replace table design, data constraints, or transactions.

## 1. Where Does the Data Persistence Problem Come From?

Suppose a store has a customer registration feature. When a user submits a name and email, the system needs to:

1. Validate the input data and business rules.
2. Write the customer into the database's `customers` table.
3. Retrieve the identifier generated by the database.
4. Allow finding the customer by ID or email on subsequent visits.
5. Prevent creating two customers with duplicate emails if the database specifies that email is unique.

Even a very small model has to answer the following technical questions:

| Application need | What the database and data access layer must handle |
| --- | --- |
| Durable storage | Translate data into an `INSERT` statement into a table on a database with durable storage. |
| Reading data | Run `SELECT`, receive result rows, and reconstruct Java objects. |
| Updating, deleting | Identify the right record and execute `UPDATE`/`DELETE`. |
| Data consistency | Apply primary keys, `UNIQUE` constraints, `NOT NULL`, foreign keys, and appropriate business rules. |
| Multiple related operations | Use transactions so that a group of changes either succeeds together or is rolled back together. |
| Concurrent access | Design constraints, isolation levels, or locking/version-checking mechanisms depending on the problem. |

A **relational database** (such as PostgreSQL, MySQL, or H2) is responsible for managing tables, records, constraints, and actual storage. **JDBC** is Java's standard API for sending SQL commands to a database through a driver. **Spring Data JDBC** sits in the application layer, organizing JDBC usage around an object and repository model. These three components have distinct roles.

```text
Java business code
       |
       v
Repository / data access layer
       |
       v
JDBC + database driver
       |
       v
PostgreSQL / MySQL / other relational database
       |
       v
Tables, data rows, keys, and transactions
```

## 2. If You Only Use Plain JDBC, What Must a Developer Do?

JDBC gives full control over writing SQL, but the surrounding code for a query is often repetitive: acquiring a `Connection`, creating a `PreparedStatement`, binding parameters, executing, iterating over a `ResultSet`, converting data types, handling errors, and closing resources.

For example, a method to find a customer by ID using plain JDBC might look like this:

```java
public Optional<Customer> findById(DataSource dataSource, long id)
        throws SQLException {
    String sql = "SELECT id, full_name, email FROM customers WHERE id = ?";

    try (Connection connection = dataSource.getConnection();
         PreparedStatement statement = connection.prepareStatement(sql)) {
        statement.setLong(1, id);

        try (ResultSet result = statement.executeQuery()) {
            if (!result.next()) {
                return Optional.empty();
            }
            Customer customer = new Customer(
                    result.getString("full_name"),
                    result.getString("email")
            );
            customer.setId(result.getLong("id"));
            return Optional.of(customer);
        }
    }
}
```

`PreparedStatement` is the right way to pass parameters, rather than concatenating user input directly into the SQL string. Even so, the snippet still spends many lines managing resources and converting results. When there are dozens of tables and CRUD operations, this repetition makes the data access layer verbose and hard to maintain.

**Spring JDBC** already reduces that work via `JdbcTemplate`: the framework manages resources, executes SQL, standardizes errors, and lets the developer provide a row-mapping function. **Spring Data JDBC** goes a step further: it can provide repository implementations and generate statements for many common operations based on the object model.

```text
Plain JDBC       → Write SQL yourself + manage JDBC yourself + map yourself
Spring JDBC      → Write SQL yourself + JdbcTemplate assists with execution/mapping
Spring Data JDBC → Repository + aggregate mapping + common CRUD
```

These are abstraction layers that can **work together**. Using Spring Data JDBC does not mean giving up the ability to write SQL when you have specialized queries.

## 3. What Actually Is Spring Data JDBC?

Spring Data JDBC provides **object mapping** and a **repository abstraction** for relational data:

- **Java objects:** classes representing business data, such as `Customer`, `Order`, or `OrderLine`.
- **Mapping:** metadata from classes, fields, and annotations such as `@Table`, `@Id`, `@Column`, and `@MappedCollection` tells the framework where data is stored.
- **Repository:** interfaces such as `CrudRepository<T, ID>` allow calling `save`, `findById`, `findAll`, and `deleteById` without building a DAO class for every basic operation.
- **Derived queries by method name:** some simple queries can be derived from method names, such as `findByEmail(String email)`.
- **Spring integration:** manages dependency injection, data access exception translation, and integrates with transactions through Spring.

A repository is declared as follows:

```java
public interface CustomerRepository extends CrudRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);
}
```

When the application configures Spring Data JDBC properly, Spring creates the repository implementation at runtime. Business code only needs to inject `CustomerRepository` and call its methods. For standard CRUD operations, Spring Data JDBC generates SQL and maps results based on the `Customer` type.

**Key distinction:** Spring Data JDBC does not use a JPA `EntityManager`, has no Hibernate persistence context, does not automatically track every change on an object, and has no JPA-style ORM lazy loading. Persistence behavior is explicitly determined through repository operations and aggregate boundaries.

## 4. Example: Saving a Customer to PostgreSQL

The example below uses Spring Boot, Spring Data JDBC, and PostgreSQL. PostgreSQL is the database that stores the actual data; the application needs a `shopdb` database and an account with appropriate privileges before running.

### 4.1. Add Dependencies

For a Spring Boot project using Gradle with dependency versions managed by Spring Boot, the minimal configuration is:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jdbc'
    runtimeOnly 'org.postgresql:postgresql'
}
```

The starter provides the necessary Spring Data JDBC / Spring JDBC components; the PostgreSQL driver allows JDBC to connect to PostgreSQL. The project does not need `spring-boot-starter-data-jpa` for this example.

### 4.2. Create the Table

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE
);
```

Here:

- `id` is the primary key, generated by the database when inserting a record.
- `full_name` and `email` are required columns.
- `UNIQUE (email)` prevents two records from having the same email value according to the database's comparison rules.

Spring Data JDBC **does not automatically create or update the schema like JPA/Hibernate's `hibernate.ddl-auto` mechanism**. In a real project, DDL should be managed through migrations such as Flyway or Liquibase; you can run the table creation SQL manually to follow along with the example.

### 4.3. Configure the Connection

In `src/main/resources/application.yml`:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/shopdb
    username: ${DB_USER}
    password: ${DB_PASSWORD}
```

The environment variables `DB_USER` and `DB_PASSWORD` hold the corresponding credentials. The URL, database name, and account values are only examples and must be adjusted to match your running PostgreSQL instance. A successful connection does not mean the table already exists: the table must be created before calling the repository.

### 4.4. Declare the Table-Mapped Class

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private Long id;
    private String fullName;
    private String email;

    public Customer() {
    }

    public Customer(String fullName, String email) {
        this.fullName = fullName;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getFullName() {
        return fullName;
    }

    public void setFullName(String fullName) {
        this.fullName = fullName;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }
}
```

`@Table("customers")` specifies the table. `@Id` specifies the primary key property. Under the default naming convention, the `fullName` property maps to the `full_name` column; when the convention differs from the schema, you can use `@Column("column_name")`. Using `Long` for `id` allows a `null` value before the object is saved for the first time.

### 4.5. Declare the Repository

```java
import java.util.Optional;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository extends CrudRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);
}
```

`CrudRepository<Customer, Long>` expresses two pieces of information: the repository manages `Customer` objects, and the primary key has type `Long`. Spring Data JDBC provides implementations for standard operations such as `save`, `findById`, `findAll`, `count`, and `deleteById`.

### 4.6. Use the Repository in Business Logic

```java
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository customers;

    public CustomerService(CustomerRepository customers) {
        this.customers = customers;
    }

    @Transactional
    public Customer register(String fullName, String email) {
        Customer customer = new Customer(fullName, email);
        return customers.save(customer);
    }

    @Transactional(readOnly = true)
    public Optional<Customer> find(long customerId) {
        return customers.findById(customerId);
    }

    @Transactional(readOnly = true)
    public Optional<Customer> findByEmail(String email) {
        return customers.findByEmail(email);
    }
}
```

When called:

```java
Customer saved = customerService.register("Nguyễn Minh An", "an@example.com");
System.out.println(saved.getId()); // ID generated by PostgreSQL

Optional<Customer> loaded = customerService.find(saved.getId());
```

Conceptually, the processing flow is:

```text
CustomerService.register(...)
       |
       v
CustomerRepository.save(customer)
       |
       v
Spring Data JDBC identifies a new object (id == null)
       |
       v
SQL INSERT is sent via JDBC to PostgreSQL
       |
       v
PostgreSQL writes the row and assigns id
       |
       v
Returned object has id; can be queried again with findById(...)
```

A semantically equivalent SQL example for saving and reading (the actual SQL generated by the framework/driver may differ):

```sql
INSERT INTO customers (full_name, email)
VALUES ('Nguyễn Minh An', 'an@example.com');

SELECT id, full_name, email
FROM customers
WHERE id = 1;
```

The value `1` is for illustration only; the actual ID depends on the data in the table. When application code runs, dynamic values are passed as SQL parameters rather than building statements by concatenating user input as in the static SQL example above.

**Result:** business code does not have to open connections, create `PreparedStatement` objects, or map `ResultSet` rows manually for these operations. Data is persisted in PostgreSQL and can be read back after the application restarts, as long as the database and its data are preserved.

## 5. Core Concept: Aggregate and Aggregate Root

Spring Data JDBC adopts the mindset of **Domain-Driven Design (DDD)** for persisting objects: an **aggregate** is a group of objects treated as a single consistent unit; the **aggregate root** is the object that external code is allowed to interact with directly through a repository.

For example, an order has multiple order lines:

```text
Order (aggregate root)
  ├── OrderLine: Book A, quantity 2
  └── OrderLine: Book B, quantity 1
```

The order lines belong to this order and participate together in rules such as "order total equals the sum of line totals." You can design an `OrderRepository` that manages `Order` and the `OrderLine` items inside the aggregate. The `@MappedCollection` annotation is commonly used to map a collection of child objects belonging to an aggregate.

Conversely, `Customer` and `Order` should usually be **two independent aggregates**. An order can store `customerId` (or represent an ID reference via `AggregateReference`) to reference the customer, rather than loading and managing the entire customer by default on every order save.

```text
Customer aggregate                   Order aggregate
┌─────────────────┐                  ┌────────────────────────┐
│ Customer        │                  │ Order                  │
│ id = 10         │◄──customerId─────│ customerId = 10        │
└─────────────────┘                  │ ├─ OrderLine A         │
                                   │ └─ OrderLine B         │
                                   └────────────────────────┘
```

Aggregate boundaries directly affect performance and persistence semantics:

- `save(root)` is an operation that saves the **aggregate state**, not simply an automatic detection of which fields changed across all objects in memory.
- For a collection of child objects belonging to an aggregate, when updating the root, Spring Data JDBC may **delete and re-insert** child rows to synchronize state. Therefore, you should not group a huge relational graph into a single aggregate.
- References between **two aggregates** are not automatically lazy-loaded like JPA ORM associations; the application typically queries the other aggregate's repository when needed.
- Choosing small aggregates with clear consistency rules makes persistence behavior and transaction boundaries easier to predict.

This is a foundational difference between Spring Data JDBC and organizing object relationships with JPA/Hibernate. When starting out, begin with a simple aggregate root like `Customer`, and then practice with `Order` and `OrderLine`.

## 6. What Does Spring Data JDBC Solve, and What Does It Not Solve?

| Concern | What Spring Data JDBC handles | What the developer remains responsible for |
| --- | --- | --- |
| Repetitive CRUD code | Built-in repositories, object mapping, and SQL generation for common operations. | Designing data types, repositories, and aggregate boundaries. |
| Low-level JDBC code | Integrates Spring JDBC to execute SQL and process results. | Configuring `DataSource`, driver, and connections properly. |
| Simple queries | CRUD methods and some query derivation like `findByEmail`. | Writing `@Query`, custom repositories, or using `JdbcTemplate`/`JdbcClient` for complex SQL. |
| Durable data storage | Sends write operations to the relational database. | Choosing and operating a database with durable storage, backups, and appropriate recovery. |
| Integrity | Can leverage Spring transactions and data mapping. | Designing keys, `UNIQUE`, `NOT NULL`, foreign keys; handling concurrency conflicts. |
| Schema | Maps to an existing schema. | Creating and versioning tables with SQL migrations. |
| Data relationships | Aggregate model and inter-aggregate references. | Choosing aggregate boundaries; weighing collection read/write costs. |

### 6.1. Transactions Alone Do Not Solve Every Concurrency Problem

Suppose a reward-points transfer feature needs to deduct points from account A and add points to account B. If one operation succeeds and the other fails, the data becomes unbalanced. A service method using `@Transactional` can place both writes in the **same transaction** so they roll back when an appropriate error occurs.

However, a transaction alone does not replace conflict handling when two requests update the same record concurrently. For scenarios that require detecting overlapping updates, Spring Data JDBC supports **optimistic locking** via a `@Version` field; which mechanism to use depends on business rules and transaction isolation levels. A `UNIQUE` constraint in the database remains the safeguard against two concurrent requests registering the same email at the same time.

### 6.2. Not Every Query Should Be Forced into Derived Method Names

Querying customers by email is a simple case. But for a quarterly revenue report involving multiple `JOIN`s, grouping, aggregations, or specially tuned queries, writing explicit SQL is usually easier to control. Spring Data JDBC lets you use `@Query` for suitable queries, or combine it with Spring JDBC / custom implementations. Spring Data JDBC's query derivation capabilities are also not equivalent to JPA's relational/object-graph querying system.

## 7. Comparison with Common Alternatives

| Technology | Primary approach | Best suited when |
| --- | --- | --- |
| **Plain JDBC** | Manage connection/statement/result manually and write SQL. | You need to understand JDBC fundamentals or build a very small, specialized integration. |
| **Spring JDBC** (`JdbcTemplate`, `JdbcClient`) | Full SQL control; Spring handles JDBC mechanics and result mapping. | Applications heavy on custom SQL, reporting, and hand-tuned queries. |
| **Spring Data JDBC** | Repositories for aggregates, simple mapping, assisted CRUD SQL. | Domains with clear aggregates, wanting to reduce CRUD boilerplate while keeping data access predictable. |
| **Spring Data JPA** (usually Hibernate) | JPA-based ORM with persistence context and rich association mechanisms. | Complex interconnected object models requiring appropriate ORM/JPA features. |
| **Spring Data R2DBC** | Relational database access via reactive APIs, not based on blocking JDBC. | Reactive applications requiring a non-blocking data access path across the whole stack. |

**Spring Data JDBC is not a "lightweight JPA" in the sense of retaining all JPA behaviors.** The two technologies choose different ways to manage objects: JDBC focuses on aggregates and explicit save operations; JPA provides a persistence context, dirty checking, and richer association/lazy-loading mechanisms. Choose Spring Data JDBC for its simplicity and fit with your model, not just because the name "JDBC" sounds familiar.

## 8. Common Misconceptions

**"With a repository, there is no more SQL."** False. A repository abstracts data access, while JDBC still sends SQL to the database. For specialized queries, you still need to read and write SQL, inspect execution plans, and design indexes.

**"Just adding the starter automatically creates tables."** False. Spring Data JDBC maps to a schema; you must manage the schema with SQL or migrations. The `spring.jpa.hibernate.ddl-auto` setting is not a schema-creation mechanism for Spring Data JDBC.

**"`save` always runs only one `UPDATE` statement."** False. The framework checks whether the object is new or existing and inspects the aggregate state. For an aggregate with child collections, saving can execute multiple SQL statements and recreate child rows.

**"Declaring a field that references another object automatically loads all relationships."** False. Spring Data JDBC does not provide JPA-style lazy loading; relationships must be modeled around aggregate ownership and ID references across separate aggregates.

**"Using an H2 in-memory database means data always survives restarts."** False. H2 `jdbc:h2:mem:...` is only suitable for demos/tests where persistence across the database lifecycle is not required. For real applications, use an appropriate database and durable storage configuration.

**"Having `@Transactional` makes every data rule safe."** False. Transactions provide configured atomicity boundaries, while constraints, isolation levels, locks, and conflict-handling rules must be designed explicitly.
