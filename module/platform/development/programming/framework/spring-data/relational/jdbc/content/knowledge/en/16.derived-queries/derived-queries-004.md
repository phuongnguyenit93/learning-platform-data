# Comparing Equals, Not, LessThan, GreaterThan, and Between

Spring Data Relational JDBC supports **derived queries**: developers name repository methods by convention, and Spring Data parses the name to build an appropriate query. The keywords `Equals`, `Not`, `LessThan`, `GreaterThan`, and `Between` describe comparison conditions on entity properties.

For example, `findByPriceLessThan(...)` expresses a request to find products priced below a given value. `findByPriceBetween(min, max)` finds products whose price falls within the range from min to max. Understanding the exact mathematical and SQL semantics of each keyword helps you write readable repository names, avoid boundary mistakes, and handle null data accurately.

This lesson uses a products table as a running example to explain method name syntax, compare operators, examine edge cases, combine conditions, and identify when to choose explicit queries.

## 1. What Are Derived Queries?

In Spring Data JDBC, a repository can declare query methods without writing SQL manually for each method. Spring Data parses the method name, identifies the target property and accompanying operator, and builds a query based on mapping metadata.

~~~java
List<Product> findByPriceLessThan(BigDecimal maxPrice);
~~~

The method above is parsed into:

- `findBy`: prefix indicating a lookup query.
- `Price`: the `price` property of the `Product` entity.
- `LessThan`: the less-than comparison operator.
- `maxPrice`: the value bound to the condition.

Logically, the query is equivalent to:

~~~sql
SELECT *
FROM products
WHERE price < ?;
~~~

The `?` placeholder simply represents a bound parameter; the exact SQL, column names, quoting, and row-limiting syntax depend on the database dialect and framework version.

### Why use derived queries?

Derived queries are suitable when conditions can be expressed concisely in a method name:

- Finding products by exact name.
- Finding products priced below a threshold.
- Finding orders with total amount above a value.
- Finding transactions within a time range.
- Combining a few simple conditions with `And` or `Or`.

The method name also documents the query intent. Readers can understand the basic condition without opening a long SQL string.

However, derived queries do not replace SQL in every situation. Queries with complex joins, specialized calculations, CTEs, window functions, or database-specific constructs may be better suited to explicitly declared queries.

## 2. Example Model

Suppose an application manages products with the following table:

~~~sql
CREATE TABLE products (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL,
    category VARCHAR(80) NOT NULL,
    price NUMERIC(19, 4) NOT NULL,
    stock INTEGER NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);
~~~

Spring Data JDBC entity:

~~~java
import java.math.BigDecimal;
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("products")
public class Product {

    @Id
    private Long id;

    private String name;
    private String category;
    private BigDecimal price;
    private Integer stock;

    @Column("created_at")
    private Instant createdAt;

    protected Product() {
    }

    public Product(
            String name,
            String category,
            BigDecimal price,
            Integer stock,
            Instant createdAt) {
        this.name = name;
        this.category = category;
        this.price = price;
        this.stock = stock;
        this.createdAt = createdAt;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public BigDecimal getPrice() { return price; }
}
~~~

Repository:

~~~java
import org.springframework.data.repository.CrudRepository;

public interface ProductRepository
        extends CrudRepository<Product, Long> {
}
~~~

Subsequent examples add query methods to `ProductRepository`. The property name in the method name is the Java property name, such as `price`, not the SQL column name when the two differ. The `@Column("created_at")` mapping links the `createdAt` property to the physical `created_at` column.

## 3. Equals: Equality Comparison

`Equals` expresses an equality comparison between the property's value and the passed parameter. In derived queries, if no operator is specified after a property, equality is usually the default.

Common ways to write equality:

~~~java
List<Product> findByName(String name);

List<Product> findByNameEquals(String name);

List<Product> findByNameIs(String name);
~~~

Conceptual SQL:

~~~sql
SELECT *
FROM products
WHERE name = ?;
~~~

When called:

~~~java
List<Product> products =
    repository.findByNameEquals("Mechanical Keyboard");
~~~

Spring Data binds the string `Mechanical Keyboard` as a query parameter. The value is not concatenated directly into the SQL.

### Equals does not mean approximate string matching

Equality compares values according to the semantics of the data type and database. It does not automatically perform:

- Substring matching.
- Leading/trailing whitespace trimming.
- Case normalization.
- Prefix or suffix matching.

For example, `findByNameEquals("Keyboard")` is different from finding names containing `Keyboard`. For string queries, database collation can affect case sensitivity and diacritic comparison. Do not assume all databases handle equality identically.

### When to use explicit Equals?

`findByName("...")` is shorter and usually clear enough. `findByNameEquals("...")` is helpful when a repository has multiple methods with different operators on the same property or when you want the method name to state the comparison explicitly.

~~~java
List<Product> findByCategoryEquals(String category);

List<Product> findByCategoryNot(String category);
~~~

The two method names express two opposing conditions clearly.

## 4. Not: Different from the Passed Value

`Not` expresses an inequality comparison. It generally corresponds to the SQL `<>` operator:

~~~java
List<Product> findByCategoryNot(String category);
~~~

Conceptual SQL:

~~~sql
SELECT *
FROM products
WHERE category <> ?;
~~~

If the parameter is `"BOOKS"`, the results include products whose category differs from BOOKS according to the database's comparison rules.

### Not is not synonymous with NotNull

These two requirements are different:

- `findByCategoryNot("BOOKS")`: category is not equal to BOOKS.
- `findByCategoryIsNotNull()`: category has a value and is not null.

~~~java
List<Product> findByCategoryNot(String category);

List<Product> findByCategoryIsNotNull();
~~~

In SQL:

~~~sql
WHERE category <> ?;
~~~

and:

~~~sql
WHERE category IS NOT NULL;
~~~

are two distinct conditions.

### Why must NULL be handled separately?

SQL uses three-valued logic: TRUE, FALSE, and UNKNOWN. Ordinary comparisons with NULL do not yield TRUE or FALSE the way comparisons between two regular values do.

For example:

~~~sql
SELECT *
FROM products
WHERE category <> 'BOOKS';
~~~

A row with `category IS NULL` is not selected by `category <> 'BOOKS'`. If the business goal is to fetch all rows not in BOOKS **including rows without a category**, you need to express the null condition as well:

~~~sql
WHERE category <> 'BOOKS'
   OR category IS NULL;
~~~

For derived queries, use `IsNull` or `IsNotNull` when you want to express null checks explicitly. Do not use `Not` as a substitute for `IsNotNull`. If passing a null parameter into a `Not` method, verify the null semantics of your Spring Data version; method names and business goals should state intent clearly rather than relying on an accidental null argument.

### Not and NotIn

`Not` compares one property against a single value. It is not the negation of a set of values.

- `findByCategoryNot("BOOKS")`: differs from a single value.
- `findByCategoryNotIn(categories)`: does not belong to the passed set of values.

When excluding multiple statuses, use the appropriate set keyword rather than chaining multiple `Not` conditions.

## 5. LessThan: Strictly Less Than

`LessThan` corresponds to the SQL `<` operator. Values equal to the threshold are excluded.

~~~java
List<Product> findByPriceLessThan(BigDecimal maxPrice);
~~~

Conceptual SQL:

~~~sql
SELECT *
FROM products
WHERE price < ?;
~~~

Sample data:

| Product | Price |
| --- | ---: |
| A | 50.00 |
| B | 99.99 |
| C | 100.00 |
| D | 120.00 |

Calling `findByPriceLessThan(new BigDecimal("100.00"))` returns A and B. Product C is priced at exactly 100.00 and does not satisfy the condition.

### Comparing with LessThanEqual

`LessThanEqual` corresponds to `<=`:

~~~java
List<Product> findByPriceLessThanEqual(BigDecimal maxPrice);
~~~

| Keyword | Operator | Value at threshold |
| --- | --- | --- |
| `LessThan` | `<` | Excluded |
| `LessThanEqual` | `<=` | Included |

The method name should accurately reflect the business rule. If the requirement is "price at most 100," you usually need `LessThanEqual` because a price of 100 is still valid. If the requirement is "less than 100," use `LessThan`.

### Using with timestamps

~~~java
List<Product> findByCreatedAtLessThan(Instant cutoff);
~~~

This query fetches products created before `cutoff`, excluding the exact `cutoff` instant. With timestamps, pay attention to the timestamp type, time zone, and precision supported by the database.

## 6. GreaterThan: Strictly Greater Than

`GreaterThan` corresponds to the SQL `>` operator. Values equal to the threshold are excluded.

~~~java
List<Product> findByPriceGreaterThan(BigDecimal minPrice);
~~~

Conceptual SQL:

~~~sql
SELECT *
FROM products
WHERE price > ?;
~~~

Given the data:

| Product | Price |
| --- | ---: |
| A | 50.00 |
| B | 99.99 |
| C | 100.00 |
| D | 120.00 |

Calling `findByPriceGreaterThan(new BigDecimal("100.00"))` returns only D. C is priced at exactly 100.00 and is not selected.

### Comparing with GreaterThanEqual

`GreaterThanEqual` corresponds to `>=`:

~~~java
List<Product> findByPriceGreaterThanEqual(BigDecimal minPrice);
~~~

| Keyword | Operator | Value at threshold |
| --- | --- | --- |
| `GreaterThan` | `>` | Excluded |
| `GreaterThanEqual` | `>=` | Included |

For example, "price from 100 upward" should use `GreaterThanEqual`. "Price higher than 100" should use `GreaterThan`.

### Comparing with LessThan

The two operators are symmetric:

~~~java
findByPriceLessThan(limit);       // price < limit
findByPriceGreaterThan(limit);    // price > limit
~~~

Neither includes values equal to `limit`. When the requirement includes the boundary, use `LessThanEqual` or `GreaterThanEqual`.

## 7. Between: Within a Range

`Between` expresses that a value falls within the range between two parameters. In SQL, `BETWEEN` includes **both endpoints**:

~~~java
List<Product> findByPriceBetween(
    BigDecimal minPrice,
    BigDecimal maxPrice
);
~~~

Conceptual SQL:

~~~sql
SELECT *
FROM products
WHERE price BETWEEN ? AND ?;
~~~

Logically:

~~~sql
price >= minPrice AND price <= maxPrice
~~~

### Example with prices

~~~java
List<Product> products = repository.findByPriceBetween(
    new BigDecimal("50.00"),
    new BigDecimal("100.00")
);
~~~

| Product | Price | Included |
| --- | ---: | --- |
| A | 49.99 | No |
| B | 50.00 | Yes |
| C | 75.00 | Yes |
| D | 100.00 | Yes |
| E | 100.01 | No |

Both the minimum and maximum prices are included. This is the single most important detail when choosing `Between`.

### Between is not a half-open interval

If business rules require `min <= value < max`, `Between` is inaccurate because it includes `max`.

You can use two conditions instead:

~~~java
List<Product> findByPriceGreaterThanEqualAndPriceLessThan(
    BigDecimal minInclusive,
    BigDecimal maxExclusive
);
~~~

Conceptual SQL:

~~~sql
WHERE price >= ?
  AND price < ?;
~~~

A half-open interval `[min, max)` is very useful when partitioning data into contiguous windows. For example, grouping transactions by day:

- Day 1: from 00:00 on day 1, inclusive, to 00:00 on day 2, exclusive.
- Day 2: from 00:00 on day 2, inclusive, to 00:00 on day 3, exclusive.

Adjacent windows never overlap at the boundary, and you do not have to guess millisecond or nanosecond precision at the end of a day.

### Parameter order

`Between` does not automatically sort the two values. The first parameter is the lower bound, and the second is the upper bound. Passing a min greater than max normally matches no rows.

Validate before calling the repository:

~~~java
if (minPrice.compareTo(maxPrice) > 0) {
    throw new IllegalArgumentException(
        "minPrice must be less than or equal to maxPrice"
    );
}
~~~

For `BigDecimal`, use `compareTo` to compare numeric values; `equals` also checks scale, so `new BigDecimal("10.0").equals(new BigDecimal("10.00"))` returns false even though the numeric values are equal.

## 8. Operator Comparison Table

| Keyword | Meaning | Conceptual SQL | Includes boundary value? |
| --- | --- | --- | --- |
| `Equals` | Equal to | `= ?` | Yes, on exact match |
| No suffix | Default equality | `= ?` | Yes, on exact match |
| `Not` | Not equal to | `<> ?` | No |
| `LessThan` | Less than | `< ?` | No |
| `GreaterThan` | Greater than | `> ?` | No |
| `LessThanEqual` | Less than or equal | `<= ?` | Yes |
| `GreaterThanEqual` | Greater than or equal | `>= ?` | Yes |
| `Between` | Within inclusive range | `BETWEEN ? AND ?` | Yes, both ends |

A quick mnemonic:

~~~text
Equals           x = a
Not              x <> a
LessThan         x < a
GreaterThan      x > a
LessThanEqual    x <= a
GreaterThanEqual x >= a
Between          min <= x <= max
~~~

When writing a method name, start from the business requirement, determine whether boundaries are inclusive or exclusive, and then pick the matching keyword.

## 9. Declaring Methods in the Repository

Complete example:

~~~java
import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.springframework.data.repository.CrudRepository;

public interface ProductRepository
        extends CrudRepository<Product, Long> {

    List<Product> findByNameEquals(String name);

    List<Product> findByCategoryNot(String category);

    List<Product> findByPriceLessThan(BigDecimal maxPrice);

    List<Product> findByPriceGreaterThan(BigDecimal minPrice);

    List<Product> findByPriceBetween(
        BigDecimal minPrice,
        BigDecimal maxPrice
    );

    List<Product> findByCreatedAtLessThan(Instant cutoff);

    List<Product> findByCreatedAtGreaterThanEqual(Instant start);
}
~~~

These methods do not require hand-written SQL. Spring Data parses the method names when constructing repository queries.

### Choosing a return type

The return type depends on the number of results and application needs:

| Return type | Meaning |
| --- | --- |
| `List<Product>` | List of results, possibly empty |
| `Optional<Product>` | Zero or one result; suitable when the condition is guaranteed unique |
| `Product` | Single result; consider zero or multiple results according to framework semantics |
| `long` | Commonly used with count methods such as `countBy...` |
| `boolean` | Commonly used with existence methods such as `existsBy...` |

When querying by a non-unique value such as category, use a list. Do not declare `Optional<Product>` just because you hope for a single object if the database can return multiple rows.

~~~java
long countByPriceGreaterThan(BigDecimal threshold);

boolean existsByPriceBetween(
    BigDecimal minPrice,
    BigDecimal maxPrice
);
~~~

The `countBy` and `existsBy` prefixes change the result type and query intent, while the predicate section still uses comparison keywords.

## 10. Combining Conditions with And and Or

You can combine multiple conditions in a single derived query:

~~~java
List<Product> findByCategoryEqualsAndPriceLessThan(
    String category,
    BigDecimal maxPrice
);
~~~

Meaning:

~~~sql
WHERE category = ?
  AND price < ?;
~~~

Example fetching products in BOOKS priced under 100:

~~~java
List<Product> booksUnder100 =
    repository.findByCategoryEqualsAndPriceLessThan(
        "BOOKS",
        new BigDecimal("100.00")
    );
~~~

You can combine two range conditions:

~~~java
List<Product> findByPriceGreaterThanEqualAndPriceLessThan(
    BigDecimal minInclusive,
    BigDecimal maxExclusive
);
~~~

This expresses a half-open interval `[min, max)` without writing a custom query.

### Using Or carefully

~~~java
List<Product> findByPriceLessThanOrPriceGreaterThan(
    BigDecimal lower,
    BigDecimal upper
);
~~~

Conceptual SQL:

~~~sql
WHERE price < ?
   OR price > ?;
~~~

This condition fetches products outside the range, not inside it. With long method names containing multiple `And` and `Or` keywords, check how the parser groups conditions; prefer shorter methods or `@Query` once expressions become hard to read.

## 11. Comparisons Across Different Data Types

These operators are not restricted to `BigDecimal`. They apply to any property with an appropriate type mapped to a comparable SQL type.

### 11.1. Integers and decimals

~~~java
List<Product> findByStockLessThan(Integer quantity);

List<Product> findByPriceGreaterThan(BigDecimal price);
~~~

Quantities are usually integers; monetary prices should use `BigDecimal` to avoid floating-point precision errors. Parameter types should be compatible with the property type.

### 11.2. Dates and times

~~~java
List<Product> findByCreatedAtBetween(
    Instant startInclusive,
    Instant endInclusive
);
~~~

With `Between`, both timestamps are included under SQL semantics. When querying a specific day, a half-open interval is usually clearer:

~~~java
List<Product> findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(
    Instant startInclusive,
    Instant nextDayStartExclusive
);
~~~

Do not assume "end of day" is always 23:59:59.999. Timestamp precision can differ across databases and drivers; using an exclusive upper bound at the start of the next day avoids missing boundary data.

For time-zone-sensitive data, standardize storage conventions (e.g., `Instant`/UTC) and how start/end bounds are computed in the business time zone. The start of one local day is not always exactly 24 hours before the start of the next day due to time-zone rules.

### 11.3. Strings

`Equals` and `Not` work with strings. `LessThan`, `GreaterThan`, or `Between` on strings depend on database collation/sort order, which is usually lexicographical rather than a domain ordering users always expect.

If you need to sort structured codes by custom rules, normalize them or store an explicit ordering value instead of relying on default string comparison.

### 11.4. Enums

Enums can be compared for equality or inequality if mapped consistently. Ordering enums with `GreaterThan`/`LessThan` usually has poor business semantics: the declaration order of an enum in Java should not become a business ordering in the database.

If statuses have an order, store a dedicated rank or ordering field and define its mapping explicitly.

## 12. NULL and Edge Cases

Null is an important topic when using comparison operators.

### 12.1. Equality with null

In SQL, to find null values, use `IS NULL` rather than `= NULL`:

~~~sql
WHERE category IS NULL;
~~~

In derived queries, state the intent explicitly:

~~~java
List<Product> findByCategoryIsNull();

List<Product> findByCategoryIsNotNull();
~~~

The `IsNull` and `IsNotNull` keywords are preferable to passing a null argument to express the check.

### 12.2. Not and null

SQL `category <> 'BOOKS'` excludes rows where `category` is null. If you want to include nulls as well, combine a null condition or write a query expressing the exact logic.

Do not read `Not` as "every value not equal, including unset values." Null represents unknown/absent, so it cannot be implicitly treated as a distinct value.

### 12.3. LessThan/GreaterThan with null

Ordering comparisons against null do not evaluate to TRUE in SQL either. If a property is nullable, null rows will not match the comparison. If you want to include them, add an `IsNull` condition appropriately or write an explicit query.

### 12.4. Between with null

If either bound is null, a range comparison can no longer express the desired value domain. Validate both bounds before calling the repository. If one end of a range is optional, use two separate methods or build a query dynamically according to active filters.

## 13. Common Design Mistakes

| Mistake | Why it is wrong | How to fix |
| --- | --- | --- |
| Using `LessThan` for "at most" | Values equal to the threshold are excluded | Use `LessThanEqual` |
| Using `GreaterThan` for "X and above" | Values equal to X are excluded | Use `GreaterThanEqual` |
| Using `Between` expecting an exclusive upper bound | SQL BETWEEN includes both ends | Combine `GreaterThanEqual` and `LessThan` |
| Using `Not` instead of `IsNotNull` | They are different conditions | Use `IsNotNull` |
| Assuming `Not` includes null values | SQL uses three-valued logic | Add a null condition if business logic requires it |
| Passing min greater than max | The range does not match as intended | Validate bound ordering |
| Using `double` for prices | Binary floating-point rounding errors | Use `BigDecimal` |
| Using `Between` for consecutive time windows | Adjacent windows share the boundary instant | Use a half-open interval |
| Using strings for business order comparisons | Collation may not match domain order | Normalize or store a sort key |
| Overly long method names | Hard to understand and maintain | Split methods or use an explicit query |

## 14. When Should You Use @Query Instead of a Derived Query?

Derived queries are handy for simple conditions. When method names grow long or SQL logic needs to be explicit, you can use `@Query`.

~~~java
import org.springframework.data.jdbc.repository.query.Query;

@Query("""
    SELECT id, name, category, price, stock, created_at
    FROM products
    WHERE price >= :minPrice
      AND price < :maxPrice
      AND (category = :category OR category IS NULL)
    """)
List<Product> findInPriceWindowIncludingUncategorized(
    BigDecimal minPrice,
    BigDecimal maxPrice,
    String category
);
~~~

This is developer-written SQL. Table and column names must match the physical schema; Spring Data JDBC does not rewrite SQL identifiers inside the query string from property mappings. Parameters are still bound, avoiding concatenation of user input into SQL.

Consider `@Query` when:

- Complex combined null conditions are needed.
- Database-specific expressions are needed.
- The method name becomes too long to read comfortably.
- Projections or specific column selections are needed.
- Direct control over the SQL statement is needed for query tuning.

There is no need to use `@Query` for every condition. If `findByPriceBetween` already captures the business rule accurately, a derived query is usually more concise.

## 15. Testing Comparison Operators

Tests should verify behavior both inside the range and right on the boundaries. Example:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;

@DataJdbcTest
class ProductRepositoryTest {

    @Autowired
    ProductRepository repository;

    @Test
    void betweenIncludesBothEndpoints() {
        repository.save(product("A", "50.00"));
        repository.save(product("B", "75.00"));
        repository.save(product("C", "100.00"));
        repository.save(product("D", "100.01"));

        List<Product> result = repository.findByPriceBetween(
            new BigDecimal("50.00"),
            new BigDecimal("100.00")
        );

        assertThat(result)
            .extracting(Product::getName)
            .containsExactlyInAnyOrder("A", "B", "C");
    }

    private Product product(String name, String price) {
        return new Product(
            name,
            "TEST",
            new BigDecimal(price),
            10,
            Instant.parse("2025-01-01T00:00:00Z")
        );
    }
}
~~~

This is a skeleton example; you need the corresponding test schema/migrations and repository. Method names, constructors, and fields must match your project's entity.

### Boundary test dataset

With threshold 100:

| Price | LessThan 100 | LessThanEqual 100 | GreaterThan 100 | GreaterThanEqual 100 |
| ---: | --- | --- | --- | --- |
| 99.99 | Yes | Yes | No | No |
| 100.00 | No | Yes | No | Yes |
| 100.01 | No | No | Yes | Yes |

With Between 50 and 100:

| Price | Included |
| ---: | --- |
| 49.99 | No |
| 50.00 | Yes |
| 75.00 | Yes |
| 100.00 | Yes |
| 100.01 | No |

Boundary tests catch off-by-one confusion between `<` and `<=`, `>` and `>=`, as well as wrong assumptions about `Between`.

### Testing NULL

If a property is nullable, add rows with null values and verify:

- `IsNull` returns the null rows.
- `IsNotNull` excludes the null rows.
- Equality/inequality and range comparisons have the intended semantics.
- Combined null logic matches the business requirement.

If tests run on H2 while production uses PostgreSQL or MySQL, write integration tests on a production-compatible database for queries sensitive to collation, data types, time zones, or SQL dialect.

## 16. Process for Choosing Keywords from Business Requirements

When given a requirement, translate it into an operator before writing the method name:

| Business statement | Condition | Suggested method name |
| --- | --- | --- |
| Name equals X exactly | `name = X` | `findByNameEquals(X)` |
| Category differs from X | `category <> X` | `findByCategoryNot(X)` |
| Price lower than X | `price < X` | `findByPriceLessThan(X)` |
| Price at most X, including X | `price <= X` | `findByPriceLessThanEqual(X)` |
| Price higher than X | `price > X` | `findByPriceGreaterThan(X)` |
| Price X and above | `price >= X` | `findByPriceGreaterThanEqual(X)` |
| Price from X to Y, inclusive | `X <= price <= Y` | `findByPriceBetween(X, Y)` |
| Price from X, below Y | `X <= price < Y` | `findByPriceGreaterThanEqualAndPriceLessThan(X, Y)` |
| Category not yet assigned | `category IS NULL` | `findByCategoryIsNull()` |
| Category already assigned | `category IS NOT NULL` | `findByCategoryIsNotNull()` |

This approach reduces semantic mistakes: decide whether boundaries are inclusive or exclusive before picking the keyword.

## 17. Practice Exercises

### Exercise 1 — Equals and Not

Create a repository with `findByCategoryEquals` and `findByCategoryNot`. Prepare products in BOOKS, ELECTRONICS, and one row with a null category. Record the results of each query and explain why the null row is not treated as a different category under SQL logic.

### Exercise 2 — LessThan and LessThanEqual

Create products priced at 99.99, 100.00, and 100.01. Call both methods with threshold 100.00. Explain why the product priced at exactly 100.00 appears only in the `LessThanEqual` result.

### Exercise 3 — GreaterThan and GreaterThanEqual

Repeat the dataset above with the two greater-than operators. Confirm that the boundary price is returned by `GreaterThanEqual` but not by `GreaterThan`.

### Exercise 4 — Between

Create products at endpoints 50 and 100 along with one product in between. Use `findByPriceBetween`. Confirm both endpoints are included. Then try passing a lower bound greater than the upper bound and observe the result.

### Exercise 5 — Half-open interval

Write `findByCreatedAtGreaterThanEqualAndCreatedAtLessThan`. Create two adjacent time windows. Place one row right on the boundary between them and verify that it belongs only to the second window.

### Exercise 6 — Combining And/Or

Write a query fetching products in category BOOKS priced under 100, or products in category CLEARANCE. Rewrite it with `@Query` if the method name becomes hard to read. Compare readability and SQL control.

### Exercise 7 — Testing on a production-like database

Run tests comparing strings, `BigDecimal`, and timestamps against the same database engine used in production. Observe any differences in collation, precision, and time zones.
