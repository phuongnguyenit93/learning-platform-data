# Why Do Multi-Table Operations of an Aggregate Need a Transaction?

In **Spring Data Relational JDBC**, an aggregate is a consistency unit in the domain model, but its data may be stored across multiple relational tables. For example, a purchase order has general information in the `purchase_order` table and order lines in the `order_line` table. When creating or modifying an order, the application may need to execute multiple SQL statements to persist that entire state.

If only part of the SQL statements succeed, the database can end up in a state where the root and child components no longer match. The order might have its status updated while the order lines were not saved; or the old lines were deleted while the new lines were only partially written. **A transaction ensures that the entire multi-step operation is committed as a single unit or rolled back on failure**, so an aggregate is never saved in a half-finished state.

Spring Data JDBC already provides transactions for CRUD write operations inherited from a repository. When a use case needs to coordinate multiple repository calls or custom JDBC operations, the application service is typically where the transaction boundary is placed so that all operations participate in the same transaction. This lesson explains why this is necessary, how it works, how to configure it, and how to test it.

## 1. An Aggregate Is a Consistency Boundary

An aggregate is a group of domain objects managed through an aggregate root. The root controls the changes needed to protect the invariants of the group.

Order example:

~~~text
PurchaseOrder aggregate
  PurchaseOrder (root)
    id
    orderNumber
    status
    totalAmount
    lines
      OrderLine
        lineNumber
        productCode
        quantity
        unitPrice
~~~

The rules may include:

- An order must have at least one line when confirmed.
- The quantity of each line must be greater than 0.
- The order total amount must equal the sum of the order lines.
- A cancelled order must not transition to a delivered status.
- The number of order lines and the order status must be persisted consistently.

The root is the entry point for changing state. A use case that modifies an order should load the root, invoke domain behavior on the root, and then save the aggregate through the repository.

### 1.1. An Aggregate Is a Domain Concept, Not a Single Table

An aggregate can be mapped to:

| Domain component | Common storage location |
| --- | --- |
| Root attributes | Columns in the root table |
| Embedded value objects | Multiple columns in the same root table |
| Child entity collection | A separate child table with a foreign key pointing to the root |
| Referenced other aggregate | Reference ID column, not an owned child object |

Example:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(24) NOT NULL,
    total_amount DECIMAL(19, 2) NOT NULL
);

CREATE TABLE order_line (
    purchase_order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    product_code VARCHAR(80) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(19, 2) NOT NULL,
    PRIMARY KEY (purchase_order_id, line_number),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_order(id),
    CONSTRAINT ck_order_line_quantity
        CHECK (quantity > 0)
);
~~~

An order is stored across both tables. The foreign key ensures that an order line points to an existing order; the composite primary key ensures that line numbers do not duplicate within the same order; the CHECK constraint enforces positive quantities.

### 1.2. One Aggregate Can Require Multiple SQL Statements

When saving a new order, the framework may have to:

1. Insert the root row into `purchase_order`.
2. Retrieve the generated ID for the root.
3. Insert each order line into `order_line` with the corresponding root ID.

When updating an aggregate, the framework may need to update the root and synchronize the child collections. Spring Data JDBC's aggregate saving mechanism can execute multiple SQL statements for owned tables. You should not depend on a specific internal SQL execution order; what must be ensured is that the entire aggregate save operation runs inside the same transaction.

## 2. Why Must Multiple SQL Statements Execute as One Unit?

Consider creating an order with one root and three order lines:

~~~text
INSERT purchase_order
        |
        v
INSERT order_line #1
        |
        v
INSERT order_line #2
        |
        v
INSERT order_line #3
~~~

Suppose the third line violates the CHECK constraint because of an invalid quantity. If the preceding statements had already committed individually, the database could still contain:

- One order row in the root table.
- Two order lines in the child table.
- A missing third order line.
- A root total amount or status that no longer reflects the actual data.

The application would have created an incomplete aggregate. Subsequent reads would see half-finished data, and business rules might no longer hold.

A transaction changes the outcome:

~~~text
BEGIN
  INSERT purchase_order
  INSERT order_line #1
  INSERT order_line #2
  INSERT order_line #3  --> constraint error
ROLLBACK

Result: no new root and no order lines from that operation.
~~~

If all statements succeed:

~~~text
BEGIN
  INSERT purchase_order
  INSERT order_line #1
  INSERT order_line #2
  INSERT order_line #3
COMMIT

Result: the root and all order lines are saved together.
~~~

That is **atomicity**: the database treats the group of operations as a single unit. If all succeed, it commits; if an operation fails according to rollback rules, no partial write is retained.

## 3. The Four ACID Properties Related to Aggregates

Database transactions are commonly described by the four ACID properties:

| Property | Meaning | Relation to aggregates |
| --- | --- | --- |
| Atomicity | All operations in a transaction commit or roll back together | Root and child rows are never saved partially |
| Consistency | A transaction moves the database from one valid state to another, respecting constraints and protected rules | Foreign keys, unique constraints, CHECK constraints, and invariants are maintained |
| Isolation | Concurrent transactions do not observe or overwrite data in ways beyond the chosen isolation level | Two requests updating the same aggregate need appropriate conflict handling |
| Durability | Committed data is guaranteed by the database to persist according to the DBMS configuration | After a successful commit, changes are retained per the database's guarantees |

Transactions do not write missing invariants by themselves. Database constraints protect rules expressible in the schema; the domain model protects business rules when operations go through domain behavior. Transactions group those changes together so they are never partially committed.

### 3.1. Atomicity Does Not Mean Every Error Rolls Back Automatically

Rollback depends on the error type, the transaction manager, and Spring's rollback rules. By default in Spring, unchecked exceptions (such as `RuntimeException`) and `Error` cause a transaction to roll back; checked exceptions usually do not roll back automatically unless `rollbackFor` is declared.

If code catches an exception and ignores it, the transaction can continue and commit if it has not been marked rollback-only. Therefore, you should not swallow an error from one SQL statement and let subsequent statements commit an incomplete aggregate.

## 4. How Does Spring Data JDBC Save an Aggregate?

A simple model:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    private String orderNumber;
    private String status;
    private BigDecimal totalAmount;

    @MappedCollection(
            idColumn = "purchase_order_id",
            keyColumn = "line_number"
    )
    private List<OrderLine> lines;
}
~~~

Child entity:

~~~java
public class OrderLine {
    private String productCode;
    private int quantity;
    private BigDecimal unitPrice;
}
~~~

The `@MappedCollection` declaration describes a collection owned by the aggregate root and the linking column in the child table. Spring Data JDBC uses this metadata to read and write child components along with the root.

When calling:

~~~java
PurchaseOrder saved = orderRepository.save(order);
~~~

the repository saves the aggregate according to the mapping. Depending on the entity state and aggregate structure, the framework executes the necessary SQL commands on the root table and child tables. Some collection update operations may involve deleting existing child rows and re-inserting rows based on the object state; you should not rely on a fixed internal SQL order.

### 4.1. Transactions Cover Aggregate Saving

Inherited CRUD methods from Spring Data repositories have a default transaction configuration: read operations are typically read-only, while write operations such as `save` execute within a transaction. Thus, a single `save` call through a standard CRUD repository is already protected by a transaction under Spring Data JDBC's default configuration.

This is important because a single `save` may consist of multiple SQL statements. Callers do not need to manually open a transaction just to protect a single standard CRUD repository call in typical cases.

However, if a use case involves multiple independent calls — for example, saving an aggregate, writing an audit record, and updating an auxiliary table — a transaction at the service layer is required to cover all operations that must succeed or fail together.

## 5. What Happens Without a Transaction?

Consider a use case that updates an order:

1. Change the root status from DRAFT to CONFIRMED.
2. Synchronize the order lines.
3. Insert a change history record.

If each SQL statement runs and commits separately:

~~~text
UPDATE purchase_order  --> committed successfully
DELETE old order_line  --> committed successfully
INSERT new order_line  --> constraint error
INSERT order_history  --> did not run
~~~

The database could be left with a CONFIRMED order that is missing its new lines and has no confirmation history. The system cannot treat that as a complete update.

With a transaction wrapping the use case:

~~~text
BEGIN
  UPDATE purchase_order
  DELETE/INSERT order_line
  INSERT order_history
  |
  +-- if every step succeeds --> COMMIT
  |
  +-- if one step fails ------> ROLLBACK
~~~

After rollback, the database state returns to the pre-transaction state according to the database's guarantees. This preserves consistency across tables belonging to the same business operation.

## 6. Where Should the Transaction Boundary Be Placed?

A practical rule:

- Repositories are responsible for aggregate persistence operations.
- Application services coordinate a use case that may involve multiple persistence operations.
- The transaction boundary is placed at the layer representing the unit of work that must commit or roll back together.

### 6.1. A Single Aggregate Save

Example:

~~~java
public PurchaseOrder createOrder(CreateOrderCommand command) {
    PurchaseOrder order = PurchaseOrder.create(
            command.orderNumber(),
            command.lines()
    );
    return orderRepository.save(order);
}
~~~

If `save` is a standard inherited CRUD method, the repository's default transaction covers the aggregate save operation. The service is not strictly required to add `@Transactional` solely to wrap this single call, though you may still place a transaction on the service to clearly express the use case or coordinate additional steps.

### 6.2. Multiple Operations That Must Succeed Together

Example use case saving an order and recording an audit in the same database:

~~~java
@Service
public class OrderApplicationService {

    private final PurchaseOrderRepository orderRepository;
    private final OrderAuditRepository auditRepository;

    public OrderApplicationService(
            PurchaseOrderRepository orderRepository,
            OrderAuditRepository auditRepository
    ) {
        this.orderRepository = orderRepository;
        this.auditRepository = auditRepository;
    }

    @Transactional
    public PurchaseOrder createOrder(CreateOrderCommand command) {
        PurchaseOrder order = PurchaseOrder.create(
                command.orderNumber(),
                command.lines()
        );

        PurchaseOrder saved = orderRepository.save(order);
        auditRepository.recordCreated(saved.getId());

        return saved;
    }
}
~~~

`@Transactional` on the service creates a transaction for the use case. When `orderRepository.save` and `auditRepository.recordCreated` use the same datasource and transaction manager, they participate in the same transaction. If recording the audit fails with an exception that triggers rollback, saving the order is rolled back as well.

### 6.3. Multiple Repository Methods in the Same Use Case

~~~java
@Transactional
public void confirmOrder(Long orderId) {
    PurchaseOrder order = orderRepository.findById(orderId)
            .orElseThrow(() -> new OrderNotFoundException(orderId));

    order.confirm();
    orderRepository.save(order);

    auditRepository.recordConfirmed(orderId);
}
~~~

The transaction covers reading, mutating the root, saving the aggregate, and writing the audit. The repository methods join the existing transaction instead of committing independently, provided they use the same appropriate transaction manager.

## 7. Configuring Transactions in Spring

In a Spring Boot application using Spring Data JDBC, a transaction manager is typically auto-configured when a datasource and the appropriate dependencies are present. For JDBC, the common transaction manager is `JdbcTransactionManager` or `DataSourceTransactionManager`.

You can explicitly declare the bean when the application needs custom configuration:

~~~java
@Configuration
public class JdbcTransactionConfiguration {

    @Bean
    PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new JdbcTransactionManager(dataSource);
    }
}
~~~

`JdbcTransactionManager` is available in Spring Framework 5.3 and later. For older versions, `DataSourceTransactionManager` is the corresponding choice. In typical Boot applications, you do not need to declare the bean manually if auto-configuration already provides an appropriate transaction manager.

### 7.1. Using @Transactional

Import:

~~~java
import org.springframework.transaction.annotation.Transactional;
~~~

Read-only:

~~~java
@Transactional(readOnly = true)
public PurchaseOrder getOrder(Long id) {
    return orderRepository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
}
~~~

Write:

~~~java
@Transactional
public PurchaseOrder updateOrder(UpdateOrderCommand command) {
    // load, modify aggregate, save, and coordinate related operations
}
~~~

`readOnly = true` expresses read intent and can serve as a hint to the transaction manager/database. It is not an authorization mechanism and does not guarantee that every database will reject write statements.

### 7.2. Default Propagation REQUIRED

The default propagation of `@Transactional` is `REQUIRED`:

- If a transaction already exists, the method joins that transaction.
- If no transaction exists, Spring creates a new transaction.

Because of this, a single service transaction can cover multiple repository calls. There is no need to create separate transactions for each child method if they must commit or roll back together.

### 7.3. Proxies and Self-Invocation

Spring typically applies `@Transactional` through a proxy. A call from another bean goes through the proxy and is handled by the transaction interceptor.

For example, calling a transactional method from another method in the same instance (self-invocation) usually bypasses the proxy:

~~~java
public void process() {
    saveAllSteps(); // internal call on this
}

@Transactional
public void saveAllSteps() {
    // ...
}
~~~

In proxy-based transaction management, the annotation on `saveAllSteps` may not be triggered through such an internal call. Place `@Transactional` on the public method called from outside the bean, or extract the use case into an appropriate separate bean.

## 8. Rolling Back on Errors

Spring rolls back a transaction by default when a transactional method exits with an unchecked exception or `Error`.

Example:

~~~java
@Transactional
public void createOrder(CreateOrderCommand command) {
    PurchaseOrder order = orderRepository.save(
            PurchaseOrder.create(command.orderNumber(), command.lines())
    );

    auditRepository.recordCreated(order.getId());

    if (command.forceFailure()) {
        throw new IllegalStateException("Simulated failure");
    }
}
~~~

If an unchecked exception escapes the method, the write operations inside the transaction are rolled back.

### 8.1. Checked Exceptions

If a method throws a checked exception and you want it to roll back:

~~~java
@Transactional(rollbackFor = Exception.class)
public void importOrder(ImportOrderCommand command) throws Exception {
    // multiple write operations
}
~~~

You do not need `rollbackFor` on every method. Declare it only when the business contract requires rollback for checked exceptions as well.

### 8.2. Do Not Swallow Exceptions

What to avoid:

~~~java
@Transactional
public void updateOrder() {
    orderRepository.save(...);

    try {
        auditRepository.record(...);
    } catch (DataAccessException ex) {
        log.warn("Failed to record audit", ex);
        // continue normally
    }
}
~~~

If the exception is caught and neither rethrown nor marked rollback-only, the transaction may commit saving the order even though the audit failed. If the audit is a mandatory part of the use case, let the error trigger a rollback or explicitly mark the transaction rollback-only according to the designed policy.

### 8.3. Translated Exceptions

Spring JDBC normally translates JDBC errors into `DataAccessException`, which is an unchecked exception. This aligns with default rollback behavior. If the application wraps errors into checked exceptions, review the rollback rules so you do not accidentally commit partial data.

## 9. What Do Transactions Protect and What Do They Not Protect?

Transactions address the atomicity of operations within the same transaction. They do not replace all consistency mechanisms on their own.

| Need | Appropriate mechanism |
| --- | --- |
| Root and child rows commit/roll back together | Transaction |
| Prevent child rows from pointing to a nonexistent root | Foreign key |
| Prevent negative quantities | CHECK constraint |
| Prevent duplicate business codes | Unique constraint |
| Detect two requests modifying the same aggregate version | Optimistic locking with `@Version` |
| Read consistent data under contention | Appropriate isolation level |
| Keep data synchronized between two independent services | Outbox, saga, or eventual consistency mechanism |

### 9.1. Transactions Do Not Automatically Prevent Lost Updates

Two requests might both read an aggregate at version 5. Then both modify it and try to save. A transaction ensures each save is atomic, but without concurrency control, the later request may overwrite the earlier request's data depending on the update approach and isolation level.

Spring Data JDBC supports optimistic locking with `@Version`:

~~~java
@Table("purchase_order")
public class PurchaseOrder {

    @Id
    private Long id;

    @Version
    private Long version;

    private String status;
}
~~~

When saving a versioned entity, Spring Data JDBC checks the current version and increments it. If the row was already modified by another transaction, the operation can throw `OptimisticLockingFailureException`.

`@Version` and transactions complement each other:

- A transaction keeps multiple SQL statements of a single save committing/rolling back together.
- Optimistic locking detects a stale aggregate version.

### 9.2. Custom SQL Must Handle Version Manually

A `jdbc.update` statement in a custom fragment does not automatically apply repository optimistic locking. If a custom update needs a concurrency check, the SQL must include the version condition and increment the version:

~~~sql
UPDATE purchase_order
SET status = :newStatus,
    version = version + 1
WHERE id = :id
  AND version = :expectedVersion;
~~~

Check the affected row count. If it is 0, the ID may not exist or the version has already changed. Do not assume `@Version` on the entity automatically applies to handwritten SQL statements.

## 10. Isolation and Multi-Table Reads

Loading an aggregate may read the root and then read child collections via multiple SQL statements. When another transaction concurrently updates those tables, the isolation level determines which states a reading transaction can observe.

Example:

~~~text
Transaction A                    Transaction B
-------------                    -------------
SELECT purchase_order
                                 UPDATE order_line
                                 COMMIT
SELECT order_line
~~~

At an isolation level that allows reading newly committed data between statements, transaction A may observe the root and children from different points in time. Higher isolation levels can restrict certain inconsistent reads, but the cost and semantics depend on the database.

### 10.1. Choose Isolation Based on Requirements

Not every use case needs `SERIALIZABLE`. Determine:

- Is a consistent snapshot between root and children needed within a single read?
- Are there concurrent operations on the same aggregate?
- Does the database support snapshot/repeatable read with the desired semantics?
- Can optimistic locking be used instead of long-held locks?
- Is the transaction duration short and narrow enough?

`@Transactional` uses the datasource/database default isolation unless specified otherwise. You can specify isolation for use cases that need it:

~~~java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public PurchaseOrder loadConsistentOrder(Long id) {
    // read aggregate and data that need the same snapshot
}
~~~

Isolation names and semantics must be verified against the target database. Some databases implement REPEATABLE_READ via snapshots, while others may behave differently.

### 10.2. Short Transactions Reduce Contention

Do not keep a transaction open while:

- Waiting for user confirmation.
- Calling a slow external API.
- Sending email synchronously.
- Processing large files.
- Waiting on an operation unrelated to the database.

Perform reads/writes in a short transaction, then carry out external work using an appropriate pattern. For events that must be emitted after commit, consider an outbox to avoid succeeding on the database write while failing to send the message or vice versa.

## 11. How Do Single-Aggregate and Multi-Aggregate Operations Differ?

Transactions are usually placed to protect a use case. However, aggregate boundaries in domain design remain important.

Example:

~~~text
PurchaseOrder aggregate
  PurchaseOrder
    OrderLine[]

Customer aggregate
  Customer

Inventory aggregate
  InventoryItem
~~~

An order owns its order lines. Customer and Inventory are independent aggregates referenced by ID.

When saving a PurchaseOrder, Spring Data JDBC persists the root and its owned children. It does not automatically load or save the entire Customer and Inventory just because the order holds reference IDs.

A use case may need to coordinate multiple aggregates:

- Verify the customer is active.
- Reserve inventory.
- Create the order.

If the aggregates live in the same database and the business truly requires all-or-nothing, a database transaction can span multiple repository operations. However, using transactions across multiple aggregates increases coupling and contention; clearly identify which invariants genuinely require synchronous guarantees.

If aggregates belong to different services/databases, a local JDBC transaction cannot guarantee cross-system atomicity. You need an outbox, saga, or eventual consistency rather than assuming a single `@Transactional` wraps every service.

## 12. Custom JDBC Operations Must Participate Properly in Transactions

A fragment using `NamedParameterJdbcTemplate`, `JdbcTemplate`, or `JdbcClient` can participate in a Spring transaction if it uses the same `DataSource` and transaction manager.

Example:

~~~java
@Repository
public class OrderAuditRepository {

    private final NamedParameterJdbcTemplate jdbc;

    public OrderAuditRepository(NamedParameterJdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    public int recordCreated(Long orderId) {
        return jdbc.update(
                """
                INSERT INTO order_audit(order_id, event_type)
                VALUES (:orderId, :eventType)
                """,
                new MapSqlParameterSource()
                        .addValue("orderId", orderId)
                        .addValue("eventType", "CREATED")
        );
    }
}
~~~

If the service calls `orderRepository.save` and then `auditRepository.recordCreated` inside a `@Transactional` method, both can commit/roll back together because the template uses the Spring-managed datasource.

Do not open connections manually with `DriverManager.getConnection` inside a fragment. A manually created connection will not participate in the current transaction and may commit independently.

### 12.1. Multiple Datasources

If a repository and a custom fragment use two different datasources, a single JDBC transaction manager does not automatically guarantee atomicity across both databases. You must specify the appropriate transaction manager for each part or design separate distributed consistency. Do not claim two databases roll back together just because both methods carry `@Transactional`.

## 13. Why Not Commit Each Table Separately?

One might think each table having its own repository and each method committing on its own is enough. That breaks the meaning of an aggregate when tables represent a unified business state.

Order creation example:

| Step | Table | If committed separately |
| --- | --- | --- |
| 1 | `purchase_order` | Order exists without order lines |
| 2 | `order_line` | Partial order lines exist |
| 3 | `order_line` | Fails due to constraint |
| 4 | `order_history` | Not written |

If each step commits separately, the system has to build compensating logic to delete the already-written order and children. Compensation logic is error-prone, especially when other requests read or modify data between steps.

A database transaction is typically simpler and more reliable for operations in the same database, within the same use case, that require all-or-nothing semantics.

## 14. Testing Aggregate Transactions

Do not just verify that the repository returns the expected object. Confirm that rollback actually removes all partial writes made before the error.

### 14.1. Testing Rollback When Child Insert Fails

Set up the database with a CHECK constraint:

~~~sql
ALTER TABLE order_line
    ADD CONSTRAINT ck_order_line_quantity
    CHECK (quantity > 0);
~~~

An integration test can:

1. Call the service to create an order inside a transaction.
2. Allow the root to be inserted.
3. When inserting a child with an invalid quantity, the database throws a constraint error.
4. Assert that the exception escapes the transaction.
5. Read back in a new transaction and verify that neither the root nor any child from that creation exists.

Pseudocode:

~~~java
@Test
void rollsBackRootWhenSavingChildFails() {
    assertThatThrownBy(() -> orderService.createOrder(
            commandWithInvalidChildQuantity()
    )).isInstanceOf(DataAccessException.class);

    // Read after the service transaction has ended.
    assertThat(orderRepository.findByOrderNumber("ORD-ROLLBACK"))
            .isEmpty();
    assertThat(countLinesForOrderNumber("ORD-ROLLBACK"))
            .isZero();
}
~~~

This is an illustrative outline; the specific exception may be translated by Spring depending on the database/driver. Use a fixture that triggers the error at the database level to test rollback after the root has been written. If the test method itself is wrapped in a test transaction, design the assertion step so the outcome after the service transaction is observable, such as using an appropriate test transaction setup or verifying in a new transaction.

### 14.2. Testing Commit When Everything Succeeds

With valid data:

- The root exists after commit.
- All child rows exist.
- Child foreign keys point to the right root.
- Total amount and status match the data.

Verify both the count and content of the children, not just that `save` returns an object.

### 14.3. Testing Optimistic Locking

A concurrency test can:

1. Have two transactions read the aggregate at version N.
2. Transaction A saves changes successfully, advancing version to N+1.
3. Transaction B attempts to save the entity with version N.
4. Verify transaction B receives an optimistic locking failure.
5. Verify A's data remains intact.

This test verifies concurrent overwrite protection, which is distinct from multi-table rollback tests.

### 14.4. Testing Custom JDBC in the Same Transaction

In a use case that saves an order and writes an audit:

- Let the aggregate save succeed.
- Force the audit insert to fail.
- Verify that root, children, and audit leave no partial writes behind.

The test must use the same datasource/transaction manager as production. If a fragment accidentally uses its own connection, the test can catch data being committed outside the transaction.

## 15. Common Mistakes

| Mistake | Consequence | Fix |
| --- | --- | --- |
| Assuming an aggregate always lives in one table | Overlooking SQL statements on child tables | Identify the schema for the root and owned collections |
| Saving root and children in separate transactions | Partial data may remain | Use a single transaction for the aggregate operation |
| Thinking `@Transactional` on each repository method is enough | Methods may commit separately if there is no outer transaction | Place the transaction on the service when multiple steps must succeed together |
| Assuming every `save` must be wrapped manually | Unnecessary configuration duplication | Inherited standard CRUD write methods already have a default transaction |
| Catching an exception and continuing to commit | Aggregate may remain in an incomplete state | Rethrow the error or mark rollback-only |
| Thinking transactions automatically prevent lost updates | Data can be overwritten during concurrent updates | Use `@Version` or appropriate concurrency control |
| Using custom `jdbc.update` and expecting `@Version` to run automatically | Optimistic locking is bypassed | Include version in `WHERE` and increment version manually |
| Using two datasources with a single transaction manager | No atomicity across both databases | Design distributed consistency or appropriate transaction managers |
| Holding a transaction while making HTTP/email calls | Holds connections and snapshots for too long | Narrow the transaction; use an outbox when emitting events |
| Using `ON DELETE CASCADE` indiscriminately | May delete child history unintentionally | Define delete policies per business rules |
| Tests only check that `save` does not throw | Does not prove rollback on mid-flight failure | Integration test constraint failure and read back after rollback |
| Assuming `@Transactional` always runs on internal method calls | Self-invocation may bypass the proxy | Call through a proxy or extract a bean / annotate the entry point |

## 16. Transaction Design Workflow for an Aggregate

When implementing an aggregate write use case:

1. **Identify the aggregate root and children:** list every table written in the operation.
2. **Identify invariants:** what data must hold true together after commit?
3. **Use the root repository:** load and mutate the aggregate through the root; do not update children outside ownership rules without reason.
4. **Define the transaction boundary:** a single standard save already has a default transaction; multiple repository/custom operations require a service-level transaction.
5. **Use the same datasource:** ensure repositories and JDBC templates participate in the same transaction manager when all-or-nothing is required.
6. **Define rollback rules:** know which exceptions trigger rollback; do not swallow errors that must abort the use case.
7. **Handle concurrency:** use `@Version`, SQL conditions, or appropriate isolation.
8. **Keep transactions short:** do not call external systems while holding a transaction.
9. **Test rollback:** induce an error at a step after earlier writes have run and verify no partial writes remain.
10. **Consider system boundaries:** JDBC transactions do not automatically span independent databases or services.

## Key Takeaways

An aggregate may be stored across a root table and multiple child tables. A single save or update can therefore involve multiple SQL statements. If statements commit individually, a failure in the middle can leave the root and children mismatched. **Transactions protect atomicity: all changes to the aggregate commit or roll back together.**

Spring Data JDBC already configures default transactions for inherited CRUD write operations such as `save`. When a use case coordinates multiple repository methods or custom JDBC commands, place `@Transactional` on the application service so they participate in a single transaction on the appropriate datasource/transaction manager. Transactions protect atomicity, while foreign keys, CHECK constraints, unique constraints, `@Version`, and isolation handle other aspects of consistency. Test by triggering a constraint failure mid-save and verifying that both root and children are rolled back.
