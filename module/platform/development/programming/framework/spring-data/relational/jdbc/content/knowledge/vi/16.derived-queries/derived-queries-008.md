# OrderBy, First, Top và giới hạn kết quả theo phiên bản

Trong **Spring Data Relational JDBC**, derived query cho phép mô tả điều kiện truy vấn ngay trong tên method repository. Ngoài điều kiện như `findByStatus("ACTIVE")`, tên method còn có thể quy định thứ tự và số lượng kết quả. Ba thành phần thường dùng là:

- **`OrderBy`**: khai báo thứ tự sắp xếp trong tên method.
- **`First`** và **`Top`**: giới hạn số kết quả tối đa; hai từ khóa này có ý nghĩa tương đương trong query derivation.
- **`Limit`**: tham số giới hạn động có trong các phiên bản Spring Data mới hơn.

Kết hợp đúng các thành phần này giúp repository lấy đúng tập dữ liệu cần dùng mà không phải tải toàn bộ bảng về Java rồi mới sắp xếp hoặc cắt danh sách. Cú pháp method, kiểu trả về và khả năng hỗ trợ của phiên bản Spring Data phải được hiểu chính xác.

## 1. Derived query là gì?

Spring Data phân tích tên method repository theo quy ước. Phần trước `By` mô tả loại truy vấn; phần sau `By` mô tả điều kiện lọc. Các từ khóa như `OrderBy`, `First` và `Top` bổ sung cách sắp xếp và giới hạn kết quả.

Ví dụ:

```java
List<Customer> findByStatus(String status);
List<Customer> findByStatusOrderByCreatedAtDesc(String status);
Optional<Customer> findFirstByEmail(String email);
List<Customer> findTop10ByStatusOrderByCreatedAtDesc(String status);
```

Spring Data đọc tên method, xác định property trong entity và tạo truy vấn theo dialect database.

Giả sử entity:

```java
import java.time.Instant;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        String fullName,
        String email,
        String status,
        @Column("created_at") Instant createdAt
) {}
```

Schema PostgreSQL minh họa:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Repository:

```java
import java.util.List;
import java.util.Optional;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    List<Customer> findByStatus(String status);

    List<Customer> findByStatusOrderByCreatedAtDesc(String status);

    Optional<Customer> findFirstByEmail(String email);

    List<Customer> findTop10ByStatusOrderByCreatedAtDescIdAsc(
            String status);
}
```

Trong method name, `CreatedAt` là property Java của entity. Nó được ánh xạ sang cột SQL `created_at` theo annotation/naming strategy. Derived query thường dùng tên property của domain model, không dùng tên cột vật lý thay cho property.

## 2. OrderBy: khai báo thứ tự trong tên method

`OrderBy` được đặt sau phần điều kiện và trước property dùng để sắp xếp:

```java
List<Customer> findByStatusOrderByCreatedAtDesc(String status);
List<Customer> findByStatusOrderByFullNameAsc(String status);
```

- `Asc`: thứ tự tăng dần.
- `Desc`: thứ tự giảm dần.
- Nếu không ghi hướng, thứ tự mặc định là tăng dần.

Có thể sắp xếp theo nhiều property:

```java
List<Customer> findByStatusOrderByCreatedAtDescIdAsc(String status);
```

Method trên lọc khách hàng theo `status`, sắp xếp `createdAt` giảm dần, sau đó `id` tăng dần.

### 2.1. Vì sao nên có tiêu chí sắp xếp phụ?

Nếu nhiều hàng có cùng `createdAt`, database không bảo đảm thứ tự tương đối giữa chúng nếu truy vấn không quy định thêm tiêu chí. Khi dùng giới hạn `Top`, thứ tự không xác định có thể làm bản ghi nằm trong tập kết quả thay đổi giữa các lần chạy.

SQL PostgreSQL minh họa:

```sql
SELECT id, full_name, created_at
FROM customer
WHERE status = 'ACTIVE'
ORDER BY created_at DESC, id ASC
LIMIT 10;
```

Khóa chính `id` làm tiêu chí phân định phụ. Điều này giúp thứ tự ổn định hơn khi nhiều khách hàng có cùng timestamp. Tuy vậy, nếu dữ liệu thay đổi giữa hai request, kết quả vẫn có thể khác.

### 2.2. OrderBy dùng tên property Java

Nếu entity khai báo `@Column("created_at") Instant createdAt`, method dùng `OrderByCreatedAtDesc`. Không dùng `OrderByCreated_At` chỉ vì cột vật lý có dấu gạch dưới. Framework ánh xạ property Java sang identifier SQL qua metadata.

## 3. First và Top: giới hạn số kết quả tĩnh

`First` và `Top` là hai từ khóa tương đương:

```java
Optional<Customer> findFirstByStatusOrderByCreatedAtDescIdAsc(
        String status);

List<Customer> findTop5ByStatusOrderByCreatedAtDescIdAsc(
        String status);

List<Customer> findFirst10ByStatusOrderByCreatedAtDescIdAsc(
        String status);
```

Quy tắc:

- `First` hoặc `Top` không kèm số có nghĩa giới hạn tối đa **một** kết quả.
- Có thể thêm số ngay sau từ khóa, ví dụ `Top5` hoặc `First10`.
- `First` và `Top` có ý nghĩa tương đương; nên chọn một cách đặt tên nhất quán.
- Giới hạn được áp dụng trong truy vấn database, không phải sau khi tải toàn bộ danh sách vào bộ nhớ.

Ví dụ lấy khách hàng mới nhất:

```java
Optional<Customer> latest = repository
        .findFirstByStatusOrderByCreatedAtDescIdAsc("ACTIVE");
```

Ví dụ lấy 5 khách hàng mới nhất:

```java
List<Customer> latestFive =
        repository.findTop5ByStatusOrderByCreatedAtDescIdAsc("ACTIVE");
```

### 3.1. Chọn kiểu trả về phù hợp

| Kiểu trả về | Phù hợp khi | Khi không có kết quả |
| --- | --- | --- |
| `Optional<T>` | Tối đa một kết quả, muốn biểu diễn khả năng không có | `Optional.empty()` |
| `T` | Tối đa một kết quả và chấp nhận contract null/exception của API | Thường là null nếu không có |
| `List<T>` | Có thể có nhiều kết quả | Danh sách rỗng |
| `Collection<T>` / `Iterable<T>` | Cần tập kết quả tổng quát | Tập rỗng |

Không khai báo `Optional<Customer>` cho method `Top10` vì method có thể trả nhiều kết quả. Ngược lại, nếu chỉ cần một kết quả, `Optional` giúp code gọi thể hiện rõ việc không tìm thấy.

### 3.2. First/Top không thay thế constraint duy nhất

`findFirstByEmail(email)` trả tối đa một hàng, nhưng không chứng minh email là duy nhất. Nếu nghiệp vụ yêu cầu duy nhất, cần unique constraint trên database và validation phù hợp. Giới hạn một hàng chỉ chọn một kết quả trong các hàng phù hợp; nó không sửa dữ liệu trùng và không bảo đảm hàng được chọn có ý nghĩa nếu thiếu `OrderBy`.

## 4. Kết hợp First/Top với điều kiện lọc

Các điều kiện được mô tả trước phần `OrderBy`:

```java
List<Customer> findTop20ByStatusAndFullNameContainingIgnoreCaseOrderByCreatedAtDescIdAsc(
        String status,
        String keyword
);
```

Method trên lọc theo `status`, tìm `fullName` có chứa keyword không phân biệt hoa/thường theo khả năng query derivation/database, sắp xếp theo thời gian giảm dần rồi ID tăng dần và trả tối đa 20 hàng.

Không nên nhồi quá nhiều logic vào tên method. Khi tên quá dài hoặc query phức tạp, cân nhắc `@Query` với SQL rõ ràng hoặc một query service chuyên biệt; cần kiểm tra dialect và mapping kết quả.

## 5. SQL nào được tạo ra?

Với method:

```java
List<Customer> findTop10ByStatusOrderByCreatedAtDescIdAsc(String status);
```

SQL PostgreSQL tương đương về ý nghĩa:

```sql
SELECT id, full_name, email, status, created_at
FROM customer
WHERE status = ?
ORDER BY created_at DESC, id ASC
LIMIT 10;
```

Đây là SQL minh họa; SQL thực tế do Spring Data JDBC và dialect tạo ra có thể khác về quoting, danh sách cột hoặc cú pháp giới hạn. Driver nhận giá trị `status` qua bind parameter.

Thứ tự xử lý logic là lọc bằng `WHERE`, sắp xếp bằng `ORDER BY` rồi giới hạn bằng cú pháp database. Database khác PostgreSQL có thể dùng `FETCH FIRST ... ROWS ONLY`, `TOP (...)` hoặc cú pháp riêng. Spring Data dùng dialect để tạo SQL tương ứng.

## 6. Giới hạn động bằng Sort và Limit

Giới hạn tĩnh phù hợp khi method luôn có cùng giới hạn. Nếu số lượng hoặc thứ tự thay đổi theo lần gọi, dùng tham số động khi phiên bản hỗ trợ.

### 6.1. Sort động

Repository có thể nhận `Sort`:

```java
import org.springframework.data.domain.Sort;

List<Customer> findTop10ByStatus(String status, Sort sort);
```

Gọi:

```java
List<Customer> customers = repository.findTop10ByStatus(
        "ACTIVE",
        Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.asc("id")
        )
);
```

`Top10` giữ giới hạn tối đa 10; `Sort` thay đổi thứ tự theo từng lần gọi. Sort property là tên persistent property Java, ví dụ `createdAt`, không phải tên cột vật lý `created_at`.

### 6.2. Limit động từ Spring Data Commons 3.2

Từ **Spring Data Commons 3.2**, có thể dùng kiểu `Limit` làm tham số repository để truyền giới hạn động:

```java
import org.springframework.data.domain.Limit;

List<Customer> findByStatusOrderByCreatedAtDescIdAsc(
        String status,
        Limit limit
);
```

Gọi:

```java
List<Customer> latestFive = repository
        .findByStatusOrderByCreatedAtDescIdAsc(
                "ACTIVE",
                Limit.of(5)
        );

List<Customer> allMatching = repository
        .findByStatusOrderByCreatedAtDescIdAsc(
                "ACTIVE",
                Limit.unlimited()
        );
```

`Limit.of(5)` giới hạn tối đa năm hàng; `Limit.unlimited()` không thêm giới hạn từ tham số này. Khả năng kết hợp `Limit` với các tham số khác phụ thuộc phiên bản module và loại query; hãy xác nhận method signature được hỗ trợ trong dự án.

**Giới hạn phiên bản:** `Limit` là API mới hơn các keyword `First`/`Top`. Với Spring Data Commons trước 3.2, class này không có sẵn; dùng `FirstN`/`TopN` cho giới hạn cố định hoặc `Pageable` khi cần phân trang. Không nâng riêng Spring Data Commons để lấy class mới nếu điều đó làm lệch bộ phiên bản do Spring Boot quản lý.

### 6.3. Chọn giữa First/Top, Limit và Pageable

| Nhu cầu | Cách khai báo |
| --- | --- |
| Luôn lấy tối đa một hàng | `findFirstBy...` hoặc `findTopBy...` |
| Luôn lấy tối đa 10 hàng | `findTop10By...` |
| Giới hạn thay đổi theo lần gọi, Spring Data 3.2+ | Tham số `Limit` |
| Số hàng thay đổi và cần page/offset | `Pageable` |
| Số hàng cố định nhưng thứ tự thay đổi | `TopN` cùng tham số `Sort` |

Không dùng `Limit` thay thế `Pageable` khi giao diện cần số trang, offset hoặc metadata trang. Limit chỉ mô tả số hàng tối đa.

## 7. Kết hợp với Pageable và Page

`Pageable` mô tả số trang, kích thước trang và thứ tự. `Page<T>` ngoài nội dung còn có metadata như tổng số phần tử và tổng số trang.

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;

Page<Customer> findByStatus(String status, Pageable pageable);
```

Gọi:

```java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);
Page<Customer> page = repository.findByStatus("ACTIVE", pageable);
```

Khác biệt:

- `Top10` giới hạn tổng số kết quả tối đa của method.
- `PageRequest.of(0, 10)` yêu cầu trang đầu tiên với kích thước 10.
- `Page<T>` có metadata tổng số phần tử/trang; framework có thể cần count query để cung cấp tổng số.
- `Slice<T>` tập trung vào nội dung và việc có trang tiếp theo, không yêu cầu tổng số trang như `Page<T>`.

Một số query derivation cho phép kết hợp limiting keyword với `Pageable`; khi đó phân trang được áp dụng trong phạm vi giới hạn của query. Vì semantics dễ gây nhầm, chỉ kết hợp khi đã xác nhận tài liệu của phiên bản đang dùng. Với phân trang thông thường, dùng query method nhận `Pageable` mà không thêm `TopN`.

## 8. Phiên bản và dependency

Các khả năng phụ thuộc Spring Data Commons và Spring Data JDBC thực tế trên classpath:

| Khả năng | Ghi chú |
| --- | --- |
| `First` / `Top` trong derived query | Có từ các thế hệ Spring Data trước; tương thích rộng |
| `OrderBy` và hướng `Asc`/`Desc` | Cú pháp derived query nền tảng |
| `Limit` làm tham số động | Có từ Spring Data Commons 3.2 |
| `Pageable` / `Sort` | API nền tảng Spring Data Commons; hỗ trợ cụ thể tùy repository module/query type |

Spring Boot quản lý các phiên bản Spring Data thông qua dependency management. Nên khai báo starter phù hợp và để BOM chọn phiên bản tương thích. Có thể kiểm tra dependency thực tế bằng:

```bash
./gradlew dependencyInsight --dependency spring-data-commons --configuration runtimeClasspath
```

Kết quả xác nhận phiên bản classpath. Không chỉ dựa vào phiên bản Spring Boot trong build file nếu dependency bị override bởi BOM khác, version catalog hoặc constraint.

Nếu `Limit` không biên dịch:

1. Kiểm tra import `org.springframework.data.domain.Limit` có tồn tại không.
2. Kiểm tra phiên bản `spring-data-commons` trên compile classpath.
3. Nếu cũ hơn 3.2, dùng `findTop5By...`/`findFirstBy...` cho giới hạn cố định.
4. Nếu giới hạn cần thay đổi, cân nhắc `Pageable` và giới hạn page size ở service.
5. Chỉ nâng Spring Boot/Spring Data như một thay đổi dependency có chủ đích.

## 9. Lưu ý về semantics và hiệu năng

### 9.1. Không tải danh sách lớn rồi mới cắt

Không nên:

```java
List<Customer> all = repository.findByStatus("ACTIVE");
List<Customer> firstTen = all.stream().limit(10).toList();
```

Cách này tải toàn bộ khách hàng ACTIVE về ứng dụng trước khi cắt. Nếu có hàng trăm nghìn bản ghi, ứng dụng vẫn nhận và tạo object cho tập dữ liệu lớn.

Nên:

```java
List<Customer> firstTen =
        repository.findTop10ByStatusOrderByCreatedAtDescIdAsc("ACTIVE");
```

Database lọc, sắp xếp và giới hạn ngay trong truy vấn.

### 9.2. Index phù hợp với điều kiện và thứ tự

Với query lọc `status` và sắp xếp theo thời gian:

```sql
SELECT id, full_name, created_at
FROM customer
WHERE status = ?
ORDER BY created_at DESC, id ASC
LIMIT 10;
```

Một index kết hợp có thể hữu ích trên PostgreSQL:

```sql
CREATE INDEX idx_customer_status_created_id
ON customer (status, created_at DESC, id ASC);
```

Đây chỉ là một phương án cần đo bằng execution plan. Hiệu quả phụ thuộc phân bố dữ liệu, độ chọn lọc của status, kích thước bảng và workload ghi. Không tạo index cho mọi tổ hợp property mà không đo.

### 9.3. Limit không thay thế validation

Nếu API cho client truyền số lượng:

- Từ chối số âm hoặc 0 nếu hợp đồng yêu cầu số dương.
- Đặt giới hạn tối đa hợp lý.
- Không để client yêu cầu số lượng rất lớn.
- Whitelist property được phép sort.
- Nếu yêu cầu "mới nhất", định nghĩa rõ thứ tự và tie-breaker.

`Limit.of(n)` truyền giới hạn tới repository, không tự quyết định mức tối đa mà hệ thống cho phép.

## 10. Lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Method name không parse được | `OrderBy`/property/hướng sai cú pháp hoặc property không tồn tại | Đối chiếu tên property và grammar derived query |
| Sort không đúng | Dùng tên cột SQL thay cho property Java | Dùng persistent property và `Asc`/`Desc` |
| Top 10 thay đổi giữa các lần gọi | Thứ tự không xác định khi giá trị sort trùng | Thêm khóa duy nhất làm tie-breaker |
| Dùng `Optional<T>` nhưng query có thể trả nhiều hàng | Method thiếu giới hạn một hàng | Dùng `List<T>` hoặc giới hạn tối đa một kết quả |
| `Limit` không biên dịch | Spring Data Commons cũ hơn 3.2 hoặc dependency lệch | Kiểm tra classpath; dùng `TopN`/`Pageable` |
| Dùng `Top` nhưng vẫn tải nhiều dữ liệu | Gọi method khác, custom query không áp dụng limit hoặc cắt danh sách ở Java | Quan sát SQL thực tế |
| Query chậm dù chỉ lấy 10 hàng | Thiếu index hoặc sort tốn kém | Xem execution plan và index |
| Nhầm page size với tổng giới hạn | Lẫn phân trang với limiting | Chọn `TopN`/`Limit` hoặc `Pageable` đúng nhu cầu |
| Tên cột có underscore không được nhận diện | Dùng tên cột SQL trong derived method | Dùng tên property Java |

## 11. Ví dụ repository tổng hợp

```java
import java.util.List;
import java.util.Optional;
import org.springframework.data.domain.Limit;
import org.springframework.data.domain.Sort;
import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {

    Optional<Customer> findFirstByEmail(String email);

    List<Customer> findTop5ByStatusOrderByCreatedAtDescIdAsc(
            String status);

    List<Customer> findTop10ByStatus(String status, Sort sort);

    // Yêu cầu Spring Data Commons 3.2+.
    List<Customer> findByStatusOrderByCreatedAtDescIdAsc(
            String status, Limit limit);
}
```

Service:

```java
import java.util.List;
import org.springframework.data.domain.Limit;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;

@Service
public class CustomerQueryService {

    private final CustomerRepository repository;

    public CustomerQueryService(CustomerRepository repository) {
        this.repository = repository;
    }

    public List<Customer> latestActiveCustomers() {
        return repository.findTop5ByStatusOrderByCreatedAtDescIdAsc(
                "ACTIVE");
    }

    public List<Customer> latestCustomers(int requestedSize) {
        int size = Math.max(1, Math.min(requestedSize, 50));
        return repository.findByStatusOrderByCreatedAtDescIdAsc(
                "ACTIVE", Limit.of(size));
    }

    public List<Customer> activeCustomersByName() {
        return repository.findTop10ByStatus(
                "ACTIVE",
                Sort.by(Sort.Order.asc("fullName"), Sort.Order.asc("id")));
    }
}
```

`Math.max/Math.min` trong ví dụ giới hạn request trong khoảng 1..50. Đây là chính sách minh họa; ứng dụng thực tế có thể trả validation error thay vì tự điều chỉnh. Nếu dự án dùng Spring Data trước 3.2, bỏ method có `Limit` và dùng `TopN` cố định hoặc `Pageable`.

## 12. Bài tập thực hành

**Bài 1 — OrderBy.** Tạo method lọc khách hàng ACTIVE, sắp xếp theo `createdAt` giảm dần và `id` tăng dần. Chèn nhiều khách hàng có cùng timestamp để quan sát tác dụng của tiêu chí phụ.

**Bài 2 — First và Top.** Viết `findFirstByStatusOrderByCreatedAtDescIdAsc` và `findTop5ByStatusOrderByCreatedAtDescIdAsc`. So sánh `Optional` và `List` khi không có dữ liệu.

**Bài 3 — SQL giới hạn.** Bật SQL logging trong môi trường dev và xác nhận truy vấn Top 5 được giới hạn ở database, thay vì tải toàn bộ kết quả rồi cắt trong Java.

**Bài 4 — Sort động.** Thêm tham số `Sort` cho method `findTop10ByStatus`. Tạo whitelist các property sort hợp lệ và từ chối tên property không được phép.

**Bài 5 — Limit theo phiên bản.** Xác định phiên bản `spring-data-commons`. Nếu từ 3.2, thử `Limit.of(3)` và `Limit.unlimited()`; nếu cũ hơn, thay bằng `Top3` hoặc `Pageable` phù hợp.

**Bài 6 — Hiệu năng.** Dùng `EXPLAIN` trên truy vấn lọc status và sort theo thời gian. Thử index kết hợp, so sánh execution plan và đo lại với dữ liệu có phân bố khác nhau.
