# ID tự tăng, generated keys và giá trị trả về sau insert

Khi lưu một bản ghi mới bằng **Spring Data Relational JDBC (Spring Data JDBC)**, ứng dụng thường chưa biết khóa chính do cơ sở dữ liệu cấp. Ví dụ, khi tạo đơn hàng mới, đối tượng Java có thể có `id = null`; database sinh ID khi thực hiện `INSERT`; Spring Data JDBC lấy khóa vừa sinh và trả lại entity đã có ID để ứng dụng sử dụng ở các bước tiếp theo.

Luồng này liên quan đến ba khái niệm:

- **ID tự tăng (generated identity):** cơ chế của database tạo khóa chính khi insert.
- **Generated key:** giá trị khóa mà JDBC driver/framework lấy lại từ database sau insert.
- **Giá trị trả về của save:** entity mà repository trả lại sau khi ghi; đây là đối tượng ứng dụng nên tiếp tục sử dụng.

## 1. Vì sao cần ID tự tăng và generated keys?

Giả sử ứng dụng tạo một đơn hàng có nhiều dòng hàng. Khi bắt đầu, ứng dụng biết khách hàng, trạng thái và danh sách item, nhưng chưa có `order_id`. Database cấp khóa cho bản ghi đơn; các dòng hàng sau đó cần dùng chính khóa này làm khóa ngoại.

~~~mermaid
sequenceDiagram
    participant App as Application Service
    participant Repo as OrderRepository
    participant JDBC as Spring Data JDBC / JDBC Driver
    participant DB as Database

    App->>Repo: save(new Order(id = null))
    Repo->>JDBC: INSERT root (không truyền id)
    JDBC->>DB: INSERT INTO shop_orders (...)
    DB-->>JDBC: generated key = 501
    JDBC-->>Repo: entity có id = 501
    Repo-->>App: savedOrder(id = 501)
    App->>Repo: dùng savedOrder hoặc lưu các tham chiếu tiếp theo
~~~

ID được sinh là **danh tính lưu trữ** của bản ghi. Nó thường khác với mã nghiệp vụ mà người dùng nhìn thấy, ví dụ `orderNumber = "ORD-2026-00051"`. Không nên buộc mã đơn hàng hiển thị phải chính là số tự tăng trong database.

## 2. Phân biệt khóa chính, ID tự tăng và mã nghiệp vụ

| Khái niệm | Ví dụ | Mục đích |
|---|---|---|
| Primary key | `shop_orders.id = 501` | Định danh duy nhất một hàng trong bảng |
| Generated ID | Database tự cấp `501` khi insert | Tránh ứng dụng tự tính ID và tránh xung đột giữa nhiều request |
| Business key | `order_number = "ORD-2026-00051"` | Mã có ý nghĩa nghiệp vụ, có thể hiển thị hoặc tra cứu |
| Foreign key | `order_items.order_id = 501` | Liên kết dòng hàng với đơn hàng sở hữu nó |

Một bảng có thể lưu cả ID kỹ thuật và mã nghiệp vụ:

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);
~~~

`id` phục vụ liên kết và truy cập dữ liệu; `order_number` tuân theo quy tắc tạo mã của nghiệp vụ. ID tự tăng không nhất thiết liên tục, không phải số thứ tự đơn hàng có ý nghĩa, và không nên dùng để suy ra thời điểm hoặc số lượng đơn đã tạo.

## 3. Khai báo cột tự tăng trong PostgreSQL và MySQL

Spring Data JDBC không tự biến mọi cột `@Id` thành cột tự tăng. **Database schema phải khai báo cơ chế sinh ID tương ứng.** Ví dụ sau sử dụng bảng `shop_orders` cho cả hai hệ quản trị; hãy chọn đúng một DDL.

### PostgreSQL: IDENTITY

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);
~~~

`GENERATED BY DEFAULT AS IDENTITY` yêu cầu PostgreSQL tự sinh giá trị khi lệnh insert không cung cấp `id`. Cú pháp `GENERATED ALWAYS AS IDENTITY` cũng có thể dùng khi muốn database từ chối giá trị do người dùng truyền trực tiếp, trừ trường hợp dùng cú pháp override có chủ đích.

Trong các schema PostgreSQL cũ, bạn có thể gặp:

~~~sql
id BIGSERIAL PRIMARY KEY
~~~

`BIGSERIAL` là cú pháp tiện ích lịch sử tạo cột số lớn gắn với sequence. Với schema mới, `IDENTITY` diễn đạt rõ đây là cột định danh được sinh tự động.

### MySQL: AUTO_INCREMENT

~~~sql
CREATE TABLE shop_orders (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
) ENGINE=InnoDB;
~~~

MySQL dùng `AUTO_INCREMENT` để sinh giá trị khi insert bỏ qua cột `id` hoặc yêu cầu giá trị tự sinh theo cú pháp thích hợp. Bảng InnoDB hỗ trợ transaction và khóa ngoại cho các ví dụ aggregate ở những bài liên quan.

### Kiểu Java nên tương ứng với kiểu SQL

| Cột SQL | Kiểu Java thường dùng | Ghi chú |
|---|---|---|
| `INTEGER GENERATED ...` / `INT AUTO_INCREMENT` | `Integer` | Số nguyên 32 bit |
| `BIGINT GENERATED ...` / `BIGINT AUTO_INCREMENT` | `Long` | Số nguyên 64 bit |
| UUID được ứng dụng cấp | `UUID` | Ứng dụng tạo trước insert, không phải identity số tự tăng |

Với khóa `BIGINT`, dùng `Long`. Đối với entity mới, **wrapper type** có thể biểu diễn `null` trước insert. Kiểu primitive `long` luôn có một giá trị số mặc định (0), không thể biểu diễn trạng thái “chưa có ID” rõ ràng như `Long null`.

## 4. Ánh xạ ID trong entity Spring Data JDBC

Spring Data JDBC sử dụng annotation `@Id` thuộc `org.springframework.data.annotation.Id` để xác định thuộc tính khóa chính. Entity ví dụ:

~~~java
package com.example.sales.order;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    protected Order() {
        // Dành cho cơ chế ánh xạ của Spring Data JDBC.
    }

    public Order(Long customerId) {
        if (customerId == null || customerId <= 0) {
            throw new IllegalArgumentException("Invalid customer ID");
        }
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }
}
~~~

Các điểm quan trọng:

- `@Table("shop_orders")` chỉ định bảng lưu root.
- `@Id` xác định cột ID theo mapping của entity; tên cột mặc định được suy ra từ thuộc tính `id`, hoặc có thể cấu hình rõ nếu schema dùng tên khác.
- Entity mới được tạo mà không đặt `id`, nên `id == null`.
- `Order` là một entity thuộc aggregate; khi có danh sách đối tượng con, ID được sinh cho root còn được dùng để liên kết các hàng con.

Annotation `@Id` **không phải** annotation `@GeneratedValue` của JPA. Không cần thêm `@GeneratedValue(strategy = GenerationType.IDENTITY)` để Spring Data JDBC lấy ID. Cơ chế sinh khóa nằm trong schema và Spring Data JDBC dùng chiến lược của dialect/JDBC để nhận khóa do database tạo.

## 5. Repository và giá trị trả về sau insert

Repository tối thiểu:

~~~java
package com.example.sales.order;

import org.springframework.data.repository.CrudRepository;

public interface OrderRepository extends CrudRepository<Order, Long> {
}
~~~

Khi tạo đơn hàng:

~~~java
Order draft = new Order(101L);

System.out.println(draft.getId()); // null

Order saved = orderRepository.save(draft);

System.out.println(saved.getId()); // ID do database cấp, ví dụ 501
~~~

**Hãy sử dụng đối tượng được trả về từ `save`.** Spring Data JDBC có thể cần tạo một instance mới khi gán giá trị ID, nhất là với entity bất biến hoặc record. Do đó, không dựa vào giả định rằng instance truyền vào luôn được thay đổi tại chỗ.

Đây là cách viết nên dùng:

~~~java
Order saved = orderRepository.save(draft);
Long orderId = saved.getId();
~~~

Tránh viết:

~~~java
orderRepository.save(draft);
Long orderId = draft.getId(); // Không nên giả định draft đã được gán ID.
~~~

Đối với class mutable, một số đường ánh xạ có thể cập nhật instance truyền vào; nhưng **hợp đồng sử dụng an toàn là lấy entity trả về**. Điều này cũng đúng khi làm việc với entity bất biến.

### Entity bất biến hoặc Java record

Nếu dùng record, giá trị ID không thể thay đổi sau khi khởi tạo. Spring Data JDBC tạo instance phù hợp với ID được sinh và trả instance đó:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public record Order(
    @Id Long id,
    Long customerId,
    String status
) {}
~~~

Tạo và lưu:

~~~java
Order draft = new Order(null, 101L, "DRAFT");
Order saved = orderRepository.save(draft);

Long generatedId = saved.id();
~~~

`draft.id()` vẫn là `null`; `saved.id()` là ID đã được sinh. Việc giữ lại đối tượng trả về rất quan trọng với record và các aggregate bất biến.

## 6. Generated key được lấy về như thế nào?

Ở mức khái niệm, quá trình có các bước:

1. Spring Data JDBC xác định entity mới cần insert.
2. Nó tạo lệnh insert dựa trên mapping; cột ID do database sinh được xử lý theo chiến lược của dialect.
3. JDBC driver thực thi câu lệnh và cung cấp generated key (hoặc kết quả tương đương theo khả năng database).
4. Spring Data JDBC tạo/cập nhật entity trả về với giá trị ID vừa nhận.
5. Repository trả entity đã lưu cho application service.

Ứng dụng **không phải tự chạy một câu SELECT để đoán ID kế tiếp**. Việc tự đọc `MAX(id) + 1` là sai khi có nhiều request đồng thời và có thể gây trùng khóa.

### PostgreSQL và RETURNING

PostgreSQL hỗ trợ lấy ID trực tiếp trong kết quả insert:

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT')
RETURNING id;
~~~

Kết quả trả về chứa ID của hàng vừa insert. Đây là cú pháp SQL minh họa; khi dùng Spring Data JDBC, hãy để framework và dialect xử lý việc lấy generated key, không cần tự viết `RETURNING` vào repository cơ bản.

### MySQL và generated key

MySQL JDBC driver hỗ trợ lấy generated key sau insert. Ở mức SQL client, có thể quan sát ID vừa cấp bằng:

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT');

SELECT LAST_INSERT_ID();
~~~

`LAST_INSERT_ID()` có ý nghĩa theo **connection/session**. Nếu tự dùng trong JDBC, lệnh truy vấn phải chạy trên cùng connection với lệnh insert. Không mở một connection khác rồi gọi `LAST_INSERT_ID()` để lấy ID của connection trước.

Với Spring Data JDBC, không cần ghép thủ công hai câu SQL trên. Framework gọi cơ chế generated keys của JDBC driver/dialect và trả ID trong entity kết quả.

### Generated key không phải là giá trị có thể dự đoán

Ví dụ hai transaction cùng insert:

~~~text
Transaction A          Database identity          Transaction B
INSERT ---------------------> cấp 501
                                                   INSERT
                              cấp 502 <------------
~~~

Thứ tự request, thứ tự commit và thứ tự ID có thể không trùng nhau. Database quản lý việc cấp khóa an toàn; ứng dụng không được tự suy luận ID kế tiếp.

## 7. Lưu aggregate có đối tượng con: ID root được dùng ra sao?

Một Order có thể sở hữu nhiều OrderItem. Spring Data JDBC ánh xạ collection bằng `@MappedCollection`:

~~~java
import java.util.ArrayList;
import java.util.List;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("shop_orders")
public class Order {

    @Id
    private Long id;

    private Long customerId;
    private String status;

    @MappedCollection(idColumn = "order_id", keyColumn = "line_position")
    private List<OrderItem> items = new ArrayList<>();

    protected Order() {}

    public Order(Long customerId) {
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public void addItem(String sku, int quantity) {
        if (sku == null || sku.isBlank() || quantity <= 0) {
            throw new IllegalArgumentException("Invalid item");
        }
        items.add(new OrderItem(sku, quantity));
    }

    public Long getId() {
        return id;
    }
}
~~~

Đối tượng con:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("order_items")
public class OrderItem {

    @Id
    private Long id;

    private String sku;
    private int quantity;

    protected OrderItem() {}

    OrderItem(String sku, int quantity) {
        this.sku = sku;
        this.quantity = quantity;
    }
}
~~~

Schema tương ứng (PostgreSQL):

~~~sql
CREATE TABLE shop_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL
);

CREATE TABLE order_items (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES shop_orders(id),
    line_position INTEGER NOT NULL,
    sku VARCHAR(60) NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    UNIQUE (order_id, line_position)
);
~~~

Khi gọi `save` cho một Order mới:

1. Framework insert hàng root vào `shop_orders`.
2. Database sinh `shop_orders.id` và Spring Data JDBC nhận generated key.
3. Framework dùng ID root vừa nhận để ghi `order_items.order_id` cho các item.
4. Repository trả về Order đã lưu; ID root có thể được đọc từ entity trả về.

~~~java
Order draft = new Order(101L);
draft.addItem("BOOK-01", 2);
draft.addItem("PEN-02", 1);

Order saved = orderRepository.save(draft);
Long orderId = saved.getId();
~~~

Vì vậy, khi dùng aggregate, bạn không cần tự đặt `order_id` cho từng item trước khi lưu. Mapping `@MappedCollection(idColumn = "order_id")` thể hiện quyền sở hữu và cột FK để Spring Data JDBC gắn item với root.

## 8. ID tự tăng không phải ID ứng dụng tự gán

Có hai chiến lược thường gặp:

| Chiến lược | Khi nào có ID? | Ví dụ |
|---|---|---|
| Database-generated | Sau insert | PostgreSQL IDENTITY, MySQL AUTO_INCREMENT |
| Application-assigned | Trước insert | UUID tạo trong Java, mã định danh do hệ thống cấp |

Với ID tự tăng, entity mới thường có `id = null`. Đây là dấu hiệu để Spring Data JDBC nhận diện entity mới và thực hiện insert.

Với ID tự gán, entity đã có ID trước khi gọi `save`. Theo chiến lược nhận diện mặc định dựa trên trạng thái mới/cũ, một ID không null có thể khiến Spring Data JDBC xem entity là đã tồn tại và đi theo đường cập nhật. Nếu muốn dùng ID tự gán cho entity mới, cần khai báo chiến lược nhận diện newness phù hợp, thường bằng cách triển khai `Persistable<ID>` và cung cấp `isNew()` (hoặc dùng cơ chế version/newness phù hợp).

Ví dụ khung cho entity dùng UUID tự cấp:

~~~java
import java.util.UUID;
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.domain.Persistable;
import org.springframework.data.relational.core.mapping.Table;

@Table("external_orders")
public class ExternalOrder implements Persistable<UUID> {

    @Id
    private UUID id;

    private String status;

    @Transient
    private boolean newEntity = true;

    protected ExternalOrder() {}

    public ExternalOrder(String status) {
        this.id = UUID.randomUUID();
        this.status = status;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public void markPersisted() {
        this.newEntity = false;
    }
}
~~~

Đây là khung minh họa cho **ID do ứng dụng tạo**; sau khi lần save đầu thành công, vòng đời đối tượng phải chuyển sang trạng thái không còn mới (ví dụ qua logic application/callback phù hợp). Nếu dùng entity bất biến hoặc nhiều đường tạo đối tượng, hãy thiết kế chiến lược newness nhất quán thay vì giữ cờ `newEntity` luôn true. Khi ID do database tự tăng, không cần cơ chế này: để ID null và dùng generated key.

## 9. Điều gì xảy ra nếu không giữ giá trị trả về của save?

Giả sử code tạo mới:

~~~java
Order order = new Order(101L);
orderRepository.save(order);

// Dùng order.getId() ở đây là không an toàn.
~~~

Nếu implementation trả về một instance mới để gắn generated ID, biến `order` vẫn trỏ tới object ban đầu có `id = null`. Khi cần dùng ID để:

- trả response HTTP chứa ID tài nguyên vừa tạo;
- ghi log hoặc tạo URL truy cập đơn hàng;
- tạo quan hệ từ một thao tác khác;
- gửi ID tới bước xử lý tiếp theo trong cùng use case;

hãy lấy từ entity được trả về:

~~~java
Order saved = orderRepository.save(order);
return saved.getId();
~~~

Với controller REST, có thể trả `201 Created` cùng URI hoặc response body chứa ID vừa được sinh:

~~~java
@PostMapping("/orders")
public ResponseEntity<OrderCreatedResponse> create(
        @RequestBody CreateOrderRequest request) {
    Order order = new Order(request.customerId());
    Order saved = orderRepository.save(order);

    URI location = URI.create("/orders/" + saved.getId());
    return ResponseEntity.created(location)
        .body(new OrderCreatedResponse(saved.getId()));
}
~~~

Đoạn controller giả định các DTO và import tương ứng đã được định nghĩa. Điểm chính là dùng `saved.getId()` cho cả URI lẫn response.

## 10. Transaction, rollback và khoảng trống trong dãy ID

Generated ID thường được cấp trong quá trình insert, trước khi transaction commit. Nếu transaction rollback sau đó, hàng dữ liệu không tồn tại nhưng **giá trị ID đã cấp có thể không được dùng lại**.

Ví dụ:

~~~text
INSERT Order -> database cấp ID 501
INSERT OrderItem -> lỗi ràng buộc
ROLLBACK transaction

Kết quả:
- Order 501 không được commit
- ID 501 có thể bị bỏ trống
- Lần insert tiếp theo có thể nhận ID 502 hoặc cao hơn
~~~

Đây là hành vi bình thường của cơ chế identity/sequence; không phải dữ liệu bị mất hay lỗi tăng ID. Không nên:

- yêu cầu ID liên tục không có khoảng trống;
- dùng `MAX(id) + 1` để tự cấp ID;
- giả định ID lớn hơn luôn đồng nghĩa commit trước trong mọi tình huống;
- coi ID tự tăng là số hóa đơn/biên lai phải liên tục theo quy định nghiệp vụ.

Nếu nghiệp vụ cần **số chứng từ liên tục** với quy tắc cấp số riêng, phải thiết kế một cơ chế đánh số có kiểm soát transaction và quy định nghiệp vụ phù hợp. Không thay thế bằng cột identity.

Khi một application service dùng `@Transactional`, ID có thể đã xuất hiện trong bộ nhớ trước khi transaction commit. Nếu transaction sau đó rollback, không được coi ID đó là tài nguyên đã lưu bền vững hoặc phát thông báo bên ngoài như thể đơn đã tạo thành công. Với tích hợp sự kiện, cân nhắc phát sự kiện sau commit hoặc dùng transactional outbox.

## 11. Kiểm tra ID bằng SQL

Có thể thử trực tiếp trên database để hiểu cơ chế sinh ID. Chạy từng nhóm lệnh theo hệ quản trị đang dùng.

### PostgreSQL

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT')
RETURNING id;
~~~

Kết quả trả về ID của hàng vừa insert. Sau đó dùng ID đó để đọc:

~~~sql
SELECT id, customer_id, status
FROM shop_orders
ORDER BY id DESC
LIMIT 5;
~~~

### MySQL

~~~sql
INSERT INTO shop_orders (customer_id, status)
VALUES (101, 'DRAFT');

SELECT LAST_INSERT_ID() AS generated_id;
~~~

Hai lệnh MySQL phải chạy trên cùng session/connection. Không lấy `LAST_INSERT_ID()` từ một cửa sổ SQL khác nếu công cụ tạo connection mới cho mỗi câu lệnh.

### Quan sát ID được lưu trong bảng

~~~sql
SELECT id, customer_id, status
FROM shop_orders
WHERE id = :generated_id;
~~~

`:generated_id` là placeholder minh họa; thay bằng giá trị vừa nhận hoặc bind parameter từ ứng dụng.

## 12. Các lỗi thường gặp và cách xử lý

| Hiện tượng | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Entity trả về vẫn không có ID | Code bỏ qua giá trị trả về hoặc entity không được cấu hình đúng | Gán kết quả `save` vào biến mới và kiểm tra `@Id` |
| Insert lỗi thiếu ID | Cột DB không có default/identity nhưng ứng dụng không truyền ID | Sửa schema hoặc chọn chiến lược ID do ứng dụng cấp |
| Lệnh insert cố truyền ID null không đúng ý | Mapping/schema hoặc SQL tùy biến không dùng generated-key strategy đúng | Kiểm tra DDL, dialect, câu lệnh thực tế và driver |
| Save đi theo update thay vì insert | ID đã có giá trị nên entity được xem là đã tồn tại | Với generated ID, để ID null; với ID tự gán, cấu hình `Persistable.isNew()` hoặc chiến lược newness |
| Kiểu ID không tương thích | Cột `BIGINT` nhưng code dùng kiểu quá nhỏ hoặc không phù hợp | Dùng `Long` tương ứng `BIGINT` |
| Bản ghi cha có ID nhưng item không được liên kết | Mapping collection/FK không đúng hoặc item không thuộc aggregate mapping | Kiểm tra `@MappedCollection(idColumn = ...)` và tên cột FK |
| ID có khoảng trống | Rollback, xóa hàng, cấp ID đồng thời | Đây là hành vi bình thường; không dùng identity làm số liên tục |
| ID trả về có nhưng query ngay sau đó không thấy | Transaction rollback, đang đọc nhầm database/schema hoặc sai transaction context | Kiểm tra commit, URL, schema và transaction |
| Trùng mã nghiệp vụ dù ID khác nhau | Chưa có unique constraint trên business key | Thêm unique constraint và quy tắc tạo mã riêng |

Đối với lỗi generated key, thứ tự điều tra hữu ích là **schema → mapping entity → newness detection → JDBC driver/dialect → giá trị trả về của repository**. Đừng sửa code bằng cách tự lấy `MAX(id) + 1`.

## 13. Bài thực hành

1. Tạo bảng `shop_orders` với ID tự tăng bằng PostgreSQL hoặc MySQL.
2. Viết entity có `@Id Long id` và repository kế thừa `CrudRepository<Order, Long>`.
3. Tạo một Order mới, xác nhận ID trước khi save là `null`.
4. Gọi `save`, giữ entity trả về và in ID. Xác minh ID tồn tại trong bảng bằng SQL.
5. Dùng một Java record thay cho class mutable; chứng minh đối tượng đầu vào và đối tượng trả về có thể khác nhau về giá trị ID.
6. Tạo một Order có hai OrderItem; lưu aggregate và kiểm tra các item có chung FK `order_id` với ID root được sinh.
7. Thử rollback transaction sau khi insert root; quan sát khoảng trống ID và giải thích vì sao không phải lỗi.
8. Tạo một entity dùng UUID do ứng dụng sinh. So sánh cách xác định entity mới với entity dùng IDENTITY.

Ví dụ kiểm tra nhanh trong service:

~~~java
@Transactional
public Long createOrder(long customerId) {
    Order draft = new Order(customerId);

    if (draft.getId() != null) {
        throw new IllegalStateException("New order should not have an ID");
    }

    Order saved = orderRepository.save(draft);
    if (saved.getId() == null) {
        throw new IllegalStateException("Database did not return an ID");
    }

    return saved.getId();
}
~~~

Đây là ví dụ minh họa luồng; ứng dụng thực tế có thể dùng exception nghiệp vụ riêng và xử lý lỗi database ở tầng phù hợp.

## 14. Ghi nhớ khi làm việc với generated ID

Chuỗi thao tác chuẩn với ID tự tăng trong Spring Data JDBC là:

~~~text
Database schema:
  id = IDENTITY / AUTO_INCREMENT

Java entity mới:
  @Id Long id = null

Repository:
  Order saved = repository.save(newOrder)

Kết quả:
  saved.getId() = generated key
~~~

**Database sinh ID; JDBC driver/dialect giúp lấy generated key; Spring Data JDBC gắn ID vào entity kết quả; application service dùng entity được trả về.** Giữ rõ bốn trách nhiệm này sẽ tránh lỗi ID null sau insert, tránh tự tính khóa cạnh tranh và giúp các đối tượng con dùng đúng khóa ngoại của aggregate root.
