# Implementing Repositories, Converters, and Business Rules

In **Spring Data Relational JDBC**, a complete use case needs to connect three parts: a repository to access the aggregate, converters to map domain types to JDBC types, and business rules to protect valid state. If you only create a repository interface while the domain model lacks invariants, the application can still persist invalid data. If you have value objects without converters, the mapping layer may not know how to write or read those types. If the service lacks a transaction boundary, multiple repository operations may no longer be atomic.

This lesson builds an order aggregate from schema to tests. The example uses:

- **PurchaseOrder** as the aggregate root.
- **OrderLine** as a child entity belonging to the order's lifecycle.
- **OrderNumber** and **Sku** as value objects stored as strings.
- Custom converters to convert value objects to and from JDBC.
- A repository to read and save the aggregate.
- Domain methods to enforce rules for adding lines and confirming orders.
- An application service with **@Transactional**.
- Migrations and tests to verify mapping, business rules, and persistence.

Spring Data JDBC focuses on aggregate roots and explicit transactions. There is no need to create a repository for every child table when those rows belong to the same aggregate.

## 1. Defining the use case and business rules

Suppose the sales system needs to support:

1. Creating an order in **DRAFT** status.
2. Adding one or more order lines.
3. Each line has a SKU, quantity, and unit price.
4. Duplicate SKUs within the same order are not allowed.
5. Negative or invalid quantities or unit prices are not allowed.
6. Modifying lines after the order has been confirmed is not allowed.
7. Only orders with at least one line can be confirmed.
8. Total amount must equal the sum of quantity multiplied by unit price across all lines.

These rules belong to the domain model. The repository is responsible for saving/finding aggregates; the service coordinates use cases and transactions.

### 1.1. Aggregate boundary

~~~text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── customerId
  ├── status
  ├── currencyCode
  ├── totalAmount
  └── lines
        ├── OrderLine (sku, quantity, unitPrice)
        └── OrderLine (sku, quantity, unitPrice)
~~~

**OrderLine** does not have its own repository because it is only created, modified, or deleted through the order. **PurchaseOrderRepository** is the single persistence gateway for this aggregate.

If later an order line gains an independent lifecycle, is managed by a different use case, and can be modified without loading the order, re-evaluate the aggregate boundary. Do not split out a separate repository merely because a child table has a primary key.

## 2. Designing the schema before writing mappings

Example PostgreSQL schema:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(32) NOT NULL,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    currency_code CHAR(3) NOT NULL,
    total_amount NUMERIC(19, 2) NOT NULL,
    CONSTRAINT uk_purchase_order_number UNIQUE (order_number)
);

CREATE TABLE order_line (
    purchase_order_id BIGINT NOT NULL,
    line_number INTEGER NOT NULL,
    sku VARCHAR(50) NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(19, 2) NOT NULL,
    CONSTRAINT pk_order_line
        PRIMARY KEY (purchase_order_id, line_number),
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (purchase_order_id)
        REFERENCES purchase_order(id)
);
~~~

This design expresses:

- Each order has a database-generated ID.
- **version** is used for optimistic locking.
- **order_number** is unique.
- **order_line** belongs to an order via **purchase_order_id**.
- **line_number** stores the position of the line within the collection.
- **sku** is stored as a string.
- Monetary values are stored as **NUMERIC**, avoiding floating-point types.

**customer_id** is a reference key to a customer in this example. If a foreign key is needed, add the corresponding constraint according to your actual schema. This lesson does not include `Customer` inside the order aggregate because customers have an independent lifecycle.

Put DDL into the project's Flyway/Liquibase migrations. Do not merely create tables manually on a developer machine, as the schema must be reproducibly created in CI and production.

## 3. Creating value objects for business data

Value objects help represent domain concepts that have their own validation rules. Example `OrderNumber`:

~~~java
import java.util.Objects;
import java.util.regex.Pattern;

public record OrderNumber(String value) {

    private static final Pattern FORMAT =
            Pattern.compile("PO-[0-9]{4}-[0-9]{4,}");

    public OrderNumber {
        Objects.requireNonNull(value, "order number is required");
        value = value.trim().toUpperCase();

        if (!FORMAT.matcher(value).matches()) {
            throw new IllegalArgumentException(
                    "Invalid order number: " + value);
        }
    }
}
~~~

**OrderNumber** is more than just a String. It ensures every instantiated value has a valid format. When reading existing data from the database, the converter also goes through this constructor; malformed data will be detected rather than silently leaking into the domain.

Similarly, create a value object for SKU:

~~~java
import java.util.Objects;
import java.util.regex.Pattern;

public record Sku(String value) {

    private static final Pattern FORMAT =
            Pattern.compile("[A-Z0-9][A-Z0-9_-]{1,49}");

    public Sku {
        Objects.requireNonNull(value, "sku is required");
        value = value.trim().toUpperCase();

        if (!FORMAT.matcher(value).matches()) {
            throw new IllegalArgumentException("Invalid SKU: " + value);
        }
    }
}
~~~

Validation in a value object should reflect stable rules of that concept. Use-case-dependent rules, such as "only allow adding lines while the order is DRAFT," belong in the aggregate root.

## 4. Writing custom converters for Spring Data JDBC

Spring Data JDBC needs to know how to convert custom types to JDBC values and vice versa. For **OrderNumber** and **Sku**, the database stores strings, while the domain uses value objects.

### 4.1. Converter writing OrderNumber as String

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class OrderNumberToStringConverter
        implements Converter<OrderNumber, String> {

    @Override
    public String convert(OrderNumber source) {
        return source.value();
    }
}
~~~

### 4.2. Converter reading String into OrderNumber

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToOrderNumberConverter
        implements Converter<String, OrderNumber> {

    @Override
    public OrderNumber convert(String source) {
        return new OrderNumber(source);
    }
}
~~~

### 4.3. Converters for SKU

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.WritingConverter;

@WritingConverter
public class SkuToStringConverter implements Converter<Sku, String> {

    @Override
    public String convert(Sku source) {
        return source.value();
    }
}
~~~

~~~java
import org.springframework.core.convert.converter.Converter;
import org.springframework.data.convert.ReadingConverter;

@ReadingConverter
public class StringToSkuConverter implements Converter<String, Sku> {

    @Override
    public Sku convert(String source) {
        return new Sku(source);
    }
}
~~~

The **@WritingConverter** and **@ReadingConverter** annotations specify the conversion direction. This is helpful when the source or target is a simple type like `String` and Spring has many default converters.

### 4.4. Registering converters

With Java configuration, converters can be registered via **AbstractJdbcConfiguration**:

~~~java
import java.util.List;

import org.springframework.context.annotation.Configuration;
import org.springframework.data.jdbc.repository.config.AbstractJdbcConfiguration;

@Configuration
public class JdbcMappingConfiguration
        extends AbstractJdbcConfiguration {

    @Override
    protected List<?> userConverters() {
        return List.of(
                new OrderNumberToStringConverter(),
                new StringToOrderNumberConverter(),
                new SkuToStringConverter(),
                new StringToSkuConverter()
        );
    }
}
~~~

When using Spring Boot, inspect the existing JDBC configuration before adding custom configuration. Ensure custom converters are included in the **JdbcCustomConversions** used by Spring Data JDBC; do not accidentally create an independent **DataAccessStrategy** or mapping context.

Do not register the same converter multiple times across multiple configuration classes. Keep the converter list centralized and write tests to verify both reading and writing directions.

### 4.5. What should a converter do?

Converters should focus on data representation:

- Convert a value object to a simple JDBC type.
- Parse a JDBC type into a value object.
- Normalize a stable storage format.
- Report an error when stored data is invalid.

Do not place use-case business rules such as checking inventory or order status inside converters. Converters are invoked by mapping infrastructure; they are not the place to coordinate repositories or transactions.

## 5. Creating the domain model for the aggregate

Order status:

~~~java
public enum OrderStatus {
    DRAFT,
    CONFIRMED,
    CANCELLED
}
~~~

Child entity:

~~~java
import java.math.BigDecimal;
import java.util.Objects;

public record OrderLine(
        Sku sku,
        int quantity,
        BigDecimal unitPrice
) {

    public OrderLine {
        Objects.requireNonNull(sku, "sku is required");
        Objects.requireNonNull(unitPrice, "unit price is required");

        if (quantity <= 0) {
            throw new IllegalArgumentException(
                    "Quantity must be greater than zero");
        }
        if (unitPrice.signum() < 0) {
            throw new IllegalArgumentException(
                    "Unit price cannot be negative");
        }
    }

    public BigDecimal lineTotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }
}
~~~

**OrderLine** enforces local invariants for a single order line. The rule "SKUs cannot repeat within the same order" must be checked in the aggregate root because it depends on other lines.

### 5.1. Aggregate root with business methods

~~~java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.MappedCollection;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        @Column("order_number") OrderNumber orderNumber,
        @Column("customer_id") Long customerId,
        OrderStatus status,
        @Column("currency_code") String currencyCode,
        @Column("total_amount") BigDecimal totalAmount,
        @MappedCollection(
                idColumn = "purchase_order_id",
                keyColumn = "line_number"
        )
        List<OrderLine> lines
) {

    public PurchaseOrder {
        Objects.requireNonNull(orderNumber, "order number is required");
        Objects.requireNonNull(customerId, "customer is required");
        Objects.requireNonNull(status, "status is required");
        Objects.requireNonNull(currencyCode, "currency is required");
        Objects.requireNonNull(totalAmount, "total amount is required");
        lines = List.copyOf(lines == null ? List.of() : lines);

        if (totalAmount.signum() < 0) {
            throw new IllegalArgumentException(
                    "Total amount cannot be negative");
        }
    }

    public static PurchaseOrder draft(
            OrderNumber orderNumber,
            Long customerId,
            String currencyCode) {

        return new PurchaseOrder(
                null,
                null,
                orderNumber,
                customerId,
                OrderStatus.DRAFT,
                currencyCode,
                BigDecimal.ZERO,
                List.of()
        );
    }

    public PurchaseOrder addLine(
            Sku sku,
            int quantity,
            BigDecimal unitPrice) {

        ensureDraft();
        OrderLine newLine = new OrderLine(sku, quantity, unitPrice);

        boolean skuAlreadyExists = lines.stream()
                .anyMatch(line -> line.sku().equals(sku));

        if (skuAlreadyExists) {
            throw new IllegalStateException(
                    "SKU already exists in this order: " + sku.value());
        }

        List<OrderLine> updatedLines = new ArrayList<>(lines);
        updatedLines.add(newLine);

        BigDecimal updatedTotal = totalAmount.add(newLine.lineTotal());

        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                customerId,
                status,
                currencyCode,
                updatedTotal,
                updatedLines
        );
    }

    public PurchaseOrder confirm() {
        ensureDraft();

        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "An order must contain at least one line");
        }

        BigDecimal calculatedTotal = lines.stream()
                .map(OrderLine::lineTotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        if (calculatedTotal.compareTo(totalAmount) != 0) {
            throw new IllegalStateException(
                    "Order total does not match its lines");
        }

        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                customerId,
                OrderStatus.CONFIRMED,
                currencyCode,
                totalAmount,
                lines
        );
    }

    private void ensureDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                    "Only draft orders can be changed");
        }
    }
}
~~~

The aggregate root preserves these invariants:

- Only DRAFT orders can have lines added.
- Each SKU appears at most once in an order.
- Quantities and unit prices are valid.
- The total amount is recalculated from the order lines.
- Only orders with at least one line can be confirmed.
- Confirmed orders cannot be modified via the existing methods.

The canonical constructor also checks basic constraints to prevent creating invalid instances through other instantiation paths. Domain methods return a new instance while retaining the read ID and version; the repository manages the new version upon save.

This example uses a single currency for the entire order. If the business supports multiple currencies within one order, model currency per line and define explicit conversion and totaling rules.

## 6. Creating a repository for the aggregate root

~~~java
import java.util.Optional;

import org.springframework.data.repository.CrudRepository;

public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    Optional<PurchaseOrder> findByOrderNumber(OrderNumber orderNumber);
}
~~~

The repository is created only for **PurchaseOrder**, the aggregate root. Do not create **OrderLineRepository** when lines are managed exclusively through the order.

The **findByOrderNumber** method uses a custom value object. The converter writes `OrderNumber` as a `String` when binding the parameter and reads `String` back into `OrderNumber` when mapping results. The database unique constraint enforces the assumption that an order number belongs to at most one order.

If the finder by order number finds nothing, the result is **Optional.empty()**. If the data has multiple duplicate rows, the repository will not silently pick one; that is an invariant violation that must be addressed.

## 7. Application service coordinating repository and transactions

Use-case commands:

~~~java
import java.math.BigDecimal;

public record CreateOrderCommand(
        String orderNumber,
        Long customerId,
        String currencyCode
) {}

public record AddOrderLineCommand(
        String sku,
        int quantity,
        BigDecimal unitPrice
) {}
~~~

Business exception:

~~~java
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long id) {
        super("Order not found: " + id);
    }
}
~~~

Service:

~~~java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder createDraft(CreateOrderCommand command) {
        PurchaseOrder draft = PurchaseOrder.draft(
                new OrderNumber(command.orderNumber()),
                command.customerId(),
                command.currencyCode()
        );

        return repository.save(draft);
    }

    @Transactional
    public PurchaseOrder addLine(
            Long orderId,
            AddOrderLineCommand command) {

        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

        PurchaseOrder changed = current.addLine(
                new Sku(command.sku()),
                command.quantity(),
                command.unitPrice()
        );

        return repository.save(changed);
    }

    @Transactional
    public PurchaseOrder confirm(Long orderId) {
        PurchaseOrder current = repository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

        return repository.save(current.confirm());
    }
}
~~~

Each method represents one use case. The service loads the aggregate, calls a domain method, and then saves. **@Transactional** sets a boundary covering both the read and write, ensuring the operations in the use case complete together.

Do not put business rules in repository methods or converters. The repository is a persistence abstraction; the domain model decides which states are valid.

### 7.1. Why call save after a domain method?

Spring Data JDBC does not have JPA-style dirty checking. After calling **current.addLine(...)**, the application has a new instance **changed**; it must call **repository.save(changed)** to persist changes to the database.

With immutable aggregates, keep the instance returned from **save** because it may hold the ID/version managed by Spring Data JDBC. Do not keep using the input object with its stale version for subsequent writes.

### 7.2. Optimistic locking

**@Version** on the root helps detect when two transactions concurrently update an order starting from the same version. When the first transaction saves successfully, the version increments. The second transaction, using the old version, fails to update and receives an optimistic locking exception.

This is why version belongs on the aggregate root. Order lines change through the root, so concurrency is detected at the aggregate boundary.

## 9. Schema migration and existing data

If the application already has order data, ensure the new schema is compatible with existing data:

1. Verify actual table/column names and data types.
2. Ensure every row has a valid **version** before enabling optimistic locking.
3. Normalize **order_number** and **sku** according to value object formats.
4. Resolve duplicate data before adding unique constraints.
5. Verify that order lines have unique **line_number** values per order.
6. Reconcile stored total amounts against the sum of order lines.
7. Run migrations on a data copy or staging environment.

If adding a version column to an existing table:

~~~sql
ALTER TABLE purchase_order
ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
~~~

This is a PostgreSQL example. Check lock duration and backfill strategy according to table size and database version. For large tables, migrations may need to be phased to minimize locking.

Do not turn on overly strict converter validation before old data is normalized. For example, if the database has lowercase SKUs or whitespace, the new converter can normalize to uppercase; however, check collation/uniqueness and potential duplicates resulting from normalization.

## 10. Testing business rules independently of the database

Important invariants should be verified with domain unit tests:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;

class PurchaseOrderTest {

    private PurchaseOrder draft() {
        return PurchaseOrder.draft(
                new OrderNumber("PO-2026-0001"),
                42L,
                "USD"
        );
    }

    @Test
    void addsLineAndRecalculatesTotal() {
        PurchaseOrder updated = draft().addLine(
                new Sku("CHAIR-01"),
                2,
                new BigDecimal("19.50")
        );

        assertThat(updated.lines()).hasSize(1);
        assertThat(updated.totalAmount())
                .isEqualByComparingTo("39.00");
    }

    @Test
    void rejectsDuplicateSku() {
        PurchaseOrder withLine = draft().addLine(
                new Sku("CHAIR-01"),
                1,
                new BigDecimal("19.50")
        );

        assertThatThrownBy(() -> withLine.addLine(
                new Sku("CHAIR-01"),
                1,
                new BigDecimal("19.50")
        )).isInstanceOf(IllegalStateException.class);
    }

    @Test
    void cannotConfirmAnEmptyOrder() {
        assertThatThrownBy(() -> draft().confirm())
                .isInstanceOf(IllegalStateException.class);
    }

    @Test
    void cannotAddLineAfterConfirmation() {
        PurchaseOrder confirmed = draft()
                .addLine(
                        new Sku("CHAIR-01"),
                        1,
                        new BigDecimal("19.50")
                )
                .confirm();

        assertThatThrownBy(() -> confirmed.addLine(
                new Sku("DESK-01"),
                1,
                new BigDecimal("50.00")
        )).isInstanceOf(IllegalStateException.class);
    }
}
~~~

Unit tests do not need a Spring context or database. They test domain rules quickly and deterministically.

## 11. Testing converters

Converters should be tested in isolation:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import org.junit.jupiter.api.Test;

class OrderNumberConverterTest {

    private final OrderNumberToStringConverter writer =
            new OrderNumberToStringConverter();
    private final StringToOrderNumberConverter reader =
            new StringToOrderNumberConverter();

    @Test
    void convertsOrderNumberToDatabaseStringAndBack() {
        OrderNumber orderNumber = new OrderNumber("po-2026-0001");

        String stored = writer.convert(orderNumber);
        OrderNumber restored = reader.convert(stored);

        assertThat(stored).isEqualTo("PO-2026-0001");
        assertThat(restored).isEqualTo(orderNumber);
    }

    @Test
    void rejectsInvalidStoredValue() {
        assertThatThrownBy(() -> reader.convert("INVALID"))
                .isInstanceOf(IllegalArgumentException.class);
    }
}
~~~

This test verifies that the writing converter outputs the right format, the reading converter restores the value object accurately, and invalid stored values are rejected.

If a converter needs to support legacy data in multiple formats, write a parser with explicit compatibility rules and test each format. Never silently return a default value when parsing fails.

## 12. Testing mappings and repositories with the database

**@DataJdbcTest** can be used to test repositories, mappings, and converters. Import the converter configuration into the test slice:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;
import org.springframework.context.annotation.Import;

@DataJdbcTest
@Import(JdbcMappingConfiguration.class)
class PurchaseOrderRepositoryTest {

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void savesAndReloadsAggregateUsingCustomConverters() {
        PurchaseOrder draft = PurchaseOrder.draft(
                new OrderNumber("PO-2026-0002"),
                42L,
                "USD"
        ).addLine(
                new Sku("CHAIR-02"),
                2,
                new BigDecimal("25.00")
        );

        PurchaseOrder saved = repository.save(draft);

        PurchaseOrder loaded = repository
                .findByOrderNumber(new OrderNumber("PO-2026-0002"))
                .orElseThrow();

        assertThat(loaded.id()).isEqualTo(saved.id());
        assertThat(loaded.orderNumber())
                .isEqualTo(new OrderNumber("PO-2026-0002"));
        assertThat(loaded.lines()).hasSize(1);
        assertThat(loaded.lines().get(0).sku())
                .isEqualTo(new Sku("CHAIR-02"));
        assertThat(loaded.totalAmount())
                .isEqualByComparingTo("50.00");
    }
}
~~~

The test demonstrates that converters work for both writing and reading through the repository, not only when called directly.

If production uses PostgreSQL, run integration tests against PostgreSQL via Testcontainers or an equivalent test database. Embedded databases can differ in identity generation, type mapping, precision, constraints, and SQL dialect.

## 13. Testing service transactions and optimistic locking

Service tests should invoke the Spring bean from the `ApplicationContext` so the transaction proxy is active:

~~~java
@SpringBootTest
class PurchaseOrderServiceIntegrationTest {

    @Autowired
    PurchaseOrderService service;

    @Autowired
    PurchaseOrderRepository repository;

    @Test
    void createsAddsLineAndConfirmsOrder() {
        PurchaseOrder created = service.createDraft(
                new CreateOrderCommand(
                        "PO-2026-0003",
                        42L,
                        "USD"
                )
        );

        PurchaseOrder withLine = service.addLine(
                created.id(),
                new AddOrderLineCommand(
                        "DESK-01",
                        1,
                        new BigDecimal("120.00")
                )
        );

        PurchaseOrder confirmed = service.confirm(withLine.id());

        assertThat(confirmed.status()).isEqualTo(OrderStatus.CONFIRMED);
        assertThat(confirmed.totalAmount())
                .isEqualByComparingTo("120.00");
        assertThat(repository.findById(created.id())).isPresent();
    }
}
~~~

In real tests, seed/cleanup data, handle unique order numbers, and use an appropriate database engine. Do not put **@Transactional** on the test if the goal is to observe each service call's independent transaction after the method finishes.

To test optimistic locking, create two copies of the aggregate with the same version:

1. Read the same order twice in two independent transactions.
2. Save the first copy's changes.
3. Attempt to save the second copy with the stale version.
4. Confirm the second save fails with an optimistic locking exception.

Concurrency tests require independent transactions and connections; do not simulate two transactions using two objects within the same persistence operation.

## 14. Adding custom queries when the repository needs search

Not every query requires a basic CRUD method. For example, finding orders by customer and status:

~~~java
public interface PurchaseOrderRepository
        extends CrudRepository<PurchaseOrder, Long> {

    Optional<PurchaseOrder> findByOrderNumber(OrderNumber orderNumber);

    List<PurchaseOrder> findByCustomerIdAndStatusOrderByIdDesc(
            Long customerId,
            OrderStatus status
    );
}
~~~

If a derived query cannot express the needed SQL, use **@Query**:

~~~java
@Query("""
    SELECT id, version, order_number, customer_id, status,
           currency_code, total_amount
    FROM purchase_order
    WHERE customer_id = :customerId
      AND status = :status
    ORDER BY id DESC
    """)
List<PurchaseOrder> findByCustomerAndStatus(
        @Param("customerId") Long customerId,
        @Param("status") OrderStatus status
);
~~~

A custom query must return the columns needed to map the return type. For aggregates with child collections, querying the root does not automatically guarantee all children are loaded in the same way as repository `findById`; verify the query mapping behavior for your version of Spring Data JDBC. If the query only needs a projection, return an appropriate DTO/projection instead of trying to map into an incomplete aggregate.

## 15. Placing business rules in the right layer

Division of responsibilities:

| Component | Responsibility |
| --- | --- |
| Value object | Validation and normalization of a single value |
| Child entity | Local invariants of an order line |
| Aggregate root | Cross-line invariants and overall order state |
| Repository | Finding/saving aggregates, persistence queries |
| Converter | Converting domain types to/from JDBC types |
| Application service | Coordinating use cases, repositories, and transactions |
| Controller/API | Translating requests/responses and protocol error codes |
| Database constraint | Protecting data invariants at the database level |

Examples:

- SKU format validation: **Sku**.
- Quantity greater than 0: **OrderLine**.
- No duplicate SKUs within the same order: **PurchaseOrder**.
- Order only confirmed when it has lines: **PurchaseOrder.confirm()**.
- Unique order number across transactions: unique constraint.
- Finding an order by code: **PurchaseOrderRepository**.
- Converting `OrderNumber` to VARCHAR: converter.
- Creating and saving an order: **PurchaseOrderService** with **@Transactional**.

Do not place all validation only in the controller. Use cases may be invoked from REST, message consumers, schedulers, or batches; domain invariants must always be protected.

## 16. Common pitfalls

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Cannot map custom type | Converter not registered or wrong direction | Check `userConverters`, `@ReadingConverter`, `@WritingConverter` |
| Writes succeed but reads fail | Missing reading converter or invalid legacy data | Write reading converter and test round-trip |
| Converter invoked in wrong direction | Simple source/target types cause ambiguity | Annotate reading/writing converters explicitly |
| Value object is not normalized | Normalized only in writing converter | Place invariant in value object constructor |
| Invalid data slips through on read | Converter skips validation | Parse and validate stored values |
| Repository does not save child | Wrong aggregate boundary or collection mapping | Check `@MappedCollection`, foreign key, and key column |
| Order lines lose ordering | Collection index/key not stored | Use a key column and verify mapping |
| Total amount does not match lines | Separate path updating total independently | Compute total inside aggregate and enforce invariant |
| Two requests overwrite each other | Missing version or unhandled optimistic lock | Use `@Version` and handle conflicts |
| Rule enforced only in controller | Other use cases bypass validation | Move invariants into value objects/aggregates |
| Repository test cannot find converters | Test slice does not import custom configuration | Import mapping configuration into the test |
| Legacy schema incompatible | Mapping assumes different column names/types | Align annotations with schema and test migrations |

## 17. Implementation workflow in a real project

1. Pick a use case and describe its business contract.
2. Identify aggregate roots, child entities, and value objects.
3. Inspect current schema, keys, nullability, and legacy data.
4. Write necessary migrations and clean up duplicate/invalid data.
5. Create value objects with stable validation.
6. Write reading/writing converters and register them centrally.
7. Build the aggregate root with business methods protecting invariants.
8. Create the repository for the root and appropriate finders.
9. Write service methods with clear transaction boundaries.
10. Write unit tests for business rules and converters.
11. Write repository integration tests against the target database.
12. Write service transaction and optimistic locking tests.
13. Measure query count, latency, and write behavior.
14. Roll out in phases and monitor mapping/runtime errors.

If a use case involves reporting queries or bulk SQL, keep them in `JdbcTemplate` when that is the right abstraction. Do not force every query through a repository just to have one uniform code style.

## 18. Practice exercises

**Exercise 1 — Value objects.** Create `OrderNumber` and `Sku` with validation. Write tests for valid values, lowercase, whitespace, empty strings, and invalid formats.

**Exercise 2 — Custom converters.** Write reading and writing converters for both value objects. Verify round-trip conversion and that invalid stored data is rejected.

**Exercise 3 — Aggregate mapping.** Create the `purchase_order` and `order_line` schemas. Map the root and child collection using `@MappedCollection`.

**Exercise 4 — Repository.** Create `PurchaseOrderRepository`, an `OrderNumber` finder, and test the unique constraint.

**Exercise 5 — Business rules.** Implement adding lines, rejecting duplicate SKUs, validating quantity/price, and computing the total.

**Exercise 6 — State transitions.** Implement `DRAFT → CONFIRMED`. Verify that empty orders cannot be confirmed and confirmed orders cannot be modified.

**Exercise 7 — Service transactions.** Write create/add/confirm service methods with `@Transactional`. Make a step fail and verify prior changes roll back.

**Exercise 8 — Optimistic locking.** Add `@Version`, have two transactions read the same order, and confirm the transaction with the stale version is rejected.

**Exercise 9 — Database migration.** Add `version` to an existing table, normalize order numbers/SKUs, and add unique constraints after resolving duplicates.

**Exercise 10 — Repository queries.** Add a finder by customer/status. Check cardinality, sorting, and query plans on representative data.

**Exercise 11 — Integration testing.** Run repository/converter tests against PostgreSQL or your target production database; compare behavior with an embedded database if used in the project.

**Exercise 12 — Extending the use case.** Add a customer existence check or inventory check using another repository within the same service transaction. Verify the entire use case rolls back if the final step fails.
