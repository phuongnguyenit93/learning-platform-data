# Combining CRUD Interfaces with PagingAndSortingRepository

In **Spring Data Relational JDBC**, a repository is the data access gateway for an aggregate. `CrudRepository` provides basic create, read, update, and delete operations; `PagingAndSortingRepository` adds the ability to read data by page and sort order. Combining the two interfaces gives a single repository both a CRUD API and support for querying large lists in slices.

When using modern Spring Data, note an important change introduced in **Spring Data 3.0**: `PagingAndSortingRepository` no longer extends `CrudRepository`. Therefore, if both groups of methods are needed, declare both interfaces on your repository. Many older examples only extend `PagingAndSortingRepository` because they were written for versions prior to 3.0.

This lesson covers the interface structure, how to call CRUD methods, `Pageable`, `PageRequest`, `Sort`, how to create paginated queries, and practical considerations when using them in a Spring Data JDBC application.

## 1. Two interfaces solve two sets of needs

`CrudRepository` defines common CRUD operations:

| Method | Purpose |
| --- | --- |
| `save(entity)` | Save an entity |
| `saveAll(entities)` | Save multiple entities |
| `findById(id)` | Find by ID, returning `Optional` |
| `existsById(id)` | Check whether an ID exists |
| `findAll()` | Read all entities |
| `findAllById(ids)` | Read by a set of IDs |
| `count()` | Count entities |
| `deleteById(id)` | Delete by ID |
| `delete(entity)` | Delete an entity |
| `deleteAll()` | Delete all entities |

`PagingAndSortingRepository` adds two list-reading forms:

| Method | Purpose |
| --- | --- |
| `findAll(Sort sort)` | Read a list in sorted order |
| `findAll(Pageable pageable)` | Read a page of data, optionally with sorting information |

CRUD answers the question **what operation to perform on the aggregate?** Paging/sorting answers **in what order and range to read the result set?** Both groups can coexist in one repository.

### 1.1. Hierarchy change since Spring Data 3.0

In Spring Data versions prior to 3.0, `PagingAndSortingRepository` extended `CrudRepository`. Thus, older code often only needed:

```java
// Example following the hierarchy of older Spring Data versions.
interface CustomerRepository
        extends PagingAndSortingRepository<Customer, Long> {
}
```

Since Spring Data 3.0, the two interfaces are separated and both extend the `Repository` marker interface:

```text
                 Repository<T, ID>
                    /       \
                   /         \
          CrudRepository   PagingAndSortingRepository
              (CRUD)          (Page / Sort)
                   \           /
                    \         /
                 CustomerRepository
```

Therefore, if an application uses Spring Data 3.x and needs both API groups, declare:

```java
interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {
}
```

This is standard Java multiple-interface composition. Spring Data creates a repository proxy implementing the appropriate operations; there is no need to manually write an implementation class for each method. Generic types must be consistent: `Customer` is the domain type and `Long` must match the type of the `@Id` property.

## 2. Declaring a complete entity and repository

Example customer entity:

```java
import java.time.Instant;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customer")
public record Customer(
        @Id Long id,
        String fullName,
        String email,
        String status,
        Instant createdAt
) {}
```

Illustrative PostgreSQL schema:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Repository declaration:

```java
import org.springframework.data.repository.CrudRepository;
import org.springframework.data.repository.PagingAndSortingRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {
}
```

Once Spring Boot configures Spring Data JDBC and repository scanning, Spring creates a `CustomerRepository` bean to inject into services. When configuring manually outside Spring Boot, you must enable the appropriate repository infrastructure, such as `@EnableJdbcRepositories` and a `DataSource`/transaction manager.

Service example:

```java
import java.util.Optional;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {

    private final CustomerRepository repository;

    public CustomerService(CustomerRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Customer create(Customer customer) {
        return repository.save(customer);
    }

    public Optional<Customer> findById(Long id) {
        return repository.findById(id);
    }

    @Transactional
    public void delete(Long id) {
        repository.deleteById(id);
    }
}
```

`@Transactional` on write methods expresses the transaction boundary for business operations. Even for a simple CRUD call, repositories have transaction behavior according to Spring Data configuration; placing transactions at the service level is useful when a business operation coordinates multiple calls within the same transaction.

## 3. How do reading all, sorting, and paging differ?

Three common call patterns:

```java
// 1. Read all data, no order specified.
Iterable<Customer> all = repository.findAll();

// 2. Read all data in order.
Iterable<Customer> sorted = repository.findAll(
        Sort.by(Sort.Direction.ASC, "fullName"));

// 3. Read one page, ordered.
Page<Customer> page = repository.findAll(
        PageRequest.of(0, 20, Sort.by("createdAt").descending()));
```

| API | Data Scope | Result Type |
| --- | --- | --- |
| `CrudRepository.findAll()` | All matching rows | `Iterable<T>` |
| `PagingAndSortingRepository.findAll(Sort)` | All rows, sorted | `Iterable<T>` |
| `PagingAndSortingRepository.findAll(Pageable)` | One page by page number/size/sort | `Page<T>` |

`findAll(Sort)` only changes the order; it does not limit the number of rows. If a table has millions of records, calling this method can still load a huge result set. When you need to limit returned rows, use `Pageable`.

## 4. Pageable and PageRequest

`Pageable` describes a pagination request: page number, page size, and sort order. `PageRequest` is a commonly used implementation to construct this request.

Example:

```java
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

Pageable pageable = PageRequest.of(0, 20);
Pageable secondPage = PageRequest.of(1, 20);

Pageable newestFirst = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Direction.DESC, "createdAt")
);
```

Important rules:

- **Page numbers are 0-based.** `PageRequest.of(0, 20)` is the first page, `PageRequest.of(1, 20)` is the second page.
- Page size must be greater than 0.
- Offset is calculated from page number and size: `offset = pageNumber × pageSize`.
- You can pass `Sort` into `PageRequest` so a single request carries both pagination and sorting.
- Use `Pageable.unpaged()` only when you genuinely want unpaged results; in public endpoints, do not allow clients to arbitrarily request all data.

### 4.1. Sorting by multiple criteria

Multiple `Sort.Order` entries can be combined:

```java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("fullName"),
        Sort.Order.asc("id")
);

Pageable pageable = PageRequest.of(0, 20, sort);
Page<Customer> page = repository.findAll(pageable);
```

Meaning:

1. More recently created customers appear first.
2. If created at the same timestamp, sort by name ascending.
3. If still tied, use ID ascending as a tie-breaker.

Having a unique final criterion (usually the primary key) ensures a more stable order when multiple rows share the same sort values. If you only sort by `createdAt` and multiple records share the same timestamp, the relative order between them is not guaranteed.

### 4.2. Sort uses Java property names

In Spring Data repositories, `Sort.by("createdAt")` generally references a **persistent property** of the entity, not a physical SQL column name. With the default `NamingStrategy`, `createdAt` may map to column `created_at`.

```java
// Java property name.
Sort.by("createdAt");

// If the Java property is named createdAt while the SQL column is created_at,
// do not pass the SQL column name into Sort by default.
Sort.by("created_at");
```

The second line may fail to resolve in mapping because `created_at` is not a Java property. Even when `@Column("created_at")` is present, sort by the property declared on the entity, such as `createdAt`.

Do not sort by transient properties, arbitrary names, or nested properties not supported as a persistent path. For custom queries, verify alias/column rules and how sorting is applied to that query.

## 5. Receiving Page<T> and reading metadata

`Page<T>` contains the current page's content along with navigation metadata:

```java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Direction.DESC, "createdAt")
);

Page<Customer> page = repository.findAll(pageable);

List<Customer> content = page.getContent();
int currentPage = page.getNumber();
int pageSize = page.getSize();
long totalElements = page.getTotalElements();
int totalPages = page.getTotalPages();
boolean hasNext = page.hasNext();
boolean hasPrevious = page.hasPrevious();
```

Values:

| Method | Meaning |
| --- | --- |
| `getContent()` | List of entities in the current page |
| `getNumber()` | Current page number, starting from 0 |
| `getSize()` | Requested page size |
| `getNumberOfElements()` | Actual number of elements in the current page |
| `getTotalElements()` | Total number of elements matching the query |
| `getTotalPages()` | Total number of pages based on total elements and page size |
| `hasNext()` | Whether there is a next page |
| `hasPrevious()` | Whether there is a previous page |
| `isFirst()` / `isLast()` | Whether the current page is the first/last page |

For example, if the total number of matching customers is 47 and the page size is 20:

| Page (0-based) | Elements | Content |
| --- | ---: | --- |
| 0 | 20 | Elements 1–20 |
| 1 | 20 | Elements 21–40 |
| 2 | 7 | Elements 41–47 |

`getTotalPages()` returns `3`. The last page has `getNumberOfElements()` equal to `7` even though `getSize()` remains `20`.

### 5.1. Why can Page cost an extra query?

To build accurate metadata for `Page<T>`, Spring Data typically needs to know the total number of matching rows. Alongside the query fetching the page's data, the framework may execute an additional **count query**. For large tables or complex filter conditions, counting can carry significant cost.

If the UI only needs to know "whether there is more data to load," displaying the total page count is not strictly necessary. For query methods that support it, consider returning `Slice<T>` or a list with `Pageable` to reduce the need to compute totals. Specific capabilities depend on the query type and Spring Data JDBC version; check the APIs supported in your project version.

## 6. Combining CRUD with query methods taking Pageable

Repositories do not just paginate `findAll()`. You can declare derived query methods by name:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;

public interface CustomerRepository
        extends CrudRepository<Customer, Long>,
                PagingAndSortingRepository<Customer, Long> {

    Page<Customer> findByStatus(String status, Pageable pageable);
}
```

Invocation:

```java
Pageable pageable = PageRequest.of(
        0,
        10,
        Sort.by(Sort.Direction.ASC, "fullName")
);

Page<Customer> activeCustomers =
        repository.findByStatus("ACTIVE", pageable);
```

Spring Data parses the method name `findByStatus` to create a filter on property `status`; `Pageable` supplies limit, offset, and sort. You do not manually concatenate `LIMIT`/`OFFSET` in the query method.

You can declare a query method taking only `Sort` when you want all matching results in a specific order:

```java
Iterable<Customer> findByStatus(String status, Sort sort);
```

`Pageable` already includes sort information. Normally pass a single `Pageable` rather than passing both a `Pageable` and a separate `Sort` for the same purpose.

### 6.1. Filter parameters and pagination parameters

Example of a method with multiple parameters:

```java
Page<Customer> findByStatusAndFullNameContainingIgnoreCase(
        String status,
        String keyword,
        Pageable pageable
);
```

`status` and `keyword` are business conditions; `pageable` is query control information. In Spring Data query methods, `Pageable`/`Sort` parameters are recognized specially and do not become ordinary bind predicates. Placing `Pageable` at the end of the method signature keeps the API readable and avoids confusion.

## 7. Using the repository in services and REST APIs

Services should accept pagination requests and return appropriate results:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.stereotype.Service;

@Service
public class CustomerQueryService {

    private final CustomerRepository repository;

    public CustomerQueryService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Page<Customer> findByStatus(
            String status,
            Pageable pageable) {
        return repository.findByStatus(status, pageable);
    }
}
```

A Spring MVC controller can accept `Pageable` directly when Spring Data web support is enabled:

```java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.web.PageableDefault;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
class CustomerController {

    private final CustomerQueryService service;

    CustomerController(CustomerQueryService service) {
        this.service = service;
    }

    @GetMapping("/customers")
    Page<Customer> list(
            @RequestParam(defaultValue = "ACTIVE") String status,
            @PageableDefault(size = 20, sort = "createdAt")
            Pageable pageable) {
        return service.findByStatus(status, pageable);
    }
}
```

Example request:

```http
GET /customers?status=ACTIVE&page=0&size=20&sort=createdAt,desc
```

Common parameters:

- `page`: page number, default 0.
- `size`: number of elements per page.
- `sort`: property and sort direction; the parameter can be repeated for multiple criteria, e.g. `sort=createdAt,desc&sort=id,asc`.

`@PageableDefault` supplies default values for the endpoint; it does not replace input validation. For public APIs, cap the maximum page size and only allow sorting on valid properties. Avoid letting users request `size=1000000` or pass arbitrary column names.

You do not necessarily return the entity directly to clients in every application. You can map `Page<Customer>` to a DTO while preserving pagination metadata:

```java
public record CustomerItem(
        Long id,
        String fullName,
        String email
) {}

Page<CustomerItem> response = page.map(customer ->
        new CustomerItem(
                customer.id(),
                customer.fullName(),
                customer.email()
        )
);
```

`Page.map` transforms the content while retaining the page metadata.

## 8. Safe and stable dynamic sorting

Sort parameters often arrive from query strings. Never pass raw client strings directly into SQL. Instead, whitelist the allowed properties:

```java
Sort.Direction direction = "desc".equalsIgnoreCase(requestDirection)
        ? Sort.Direction.DESC
        : Sort.Direction.ASC;

String property = switch (sortKey) {
    case "name" -> "fullName";
    case "created" -> "createdAt";
    case "email" -> "email";
    default -> throw new IllegalArgumentException("Unsupported sort key");
};

Sort sort = Sort.by(direction, property)
        .and(Sort.by(Sort.Order.asc("id")));

Pageable pageable = PageRequest.of(pageNumber, pageSize, sort);
```

In this example, the external key `name` is mapped to the Java property `fullName`. Adding `id` as a secondary criterion keeps the order stable when primary values are equal.

Principles:

- Accept only known, persistent properties.
- Allow only `ASC` or `DESC` as sort directions.
- Cap page number and page size according to application capacity.
- Add a unique tie-breaker key if the primary order can contain duplicates.
- Never concatenate column names from user input directly into SQL.

Spring Data generates SQL from mapping metadata and dialect, yet a whitelist is still essential to control the API, avoid non-existent properties, and prevent clients from querying by unauthorized fields.

## 9. Limitations and performance impact of offset pagination

Standard pagination uses page number/size, corresponding to `OFFSET` and `LIMIT` in SQL. For the first page:

```sql
SELECT id, full_name, email, status, created_at
FROM customer
ORDER BY created_at DESC, id ASC
LIMIT 20 OFFSET 0;
```

Next page:

```sql
SELECT id, full_name, email, status, created_at
FROM customer
ORDER BY created_at DESC, id ASC
LIMIT 20 OFFSET 20;
```

This is illustrative PostgreSQL SQL; Spring Data JDBC renders pagination syntax according to the dialect. When the offset is large, the database may have to scan and skip many rows before returning results. Consequently, very large page numbers can be slow even with a small page size.

Beyond performance, data can change between two requests:

1. Client reads page 0.
2. A new record is inserted at the top of the ordering.
3. Client reads page 1 using the old offset.
4. Some records may be duplicated or skipped because row positions shifted.

Adding a stable sort handles rows with equal sort values, but **it does not create a consistent snapshot across multiple HTTP requests**. If you need to traverse large, continuously changing datasets or iterate in key order, consider keyset/scrolling pagination supported by your version and repository type, or design a cursor based on the sort values plus a unique key. Do not treat `PageRequest` itself as cursor pagination.

## 10. Common errors

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| Cannot call `save` after extending only `PagingAndSortingRepository` | Spring Data 3.x no longer has P&S extend CRUD | Also extend `CrudRepository` or use an appropriate repository hierarchy |
| `findAll(Pageable)` not found | Repository does not extend P&S or wrong package imported | Check `org.springframework.data.repository.PagingAndSortingRepository` |
| Unexpected results on the first page | Mistakenly assuming 1-based page index | Use page 0 for the first page |
| Last page has fewer elements than page size | Normal behavior when total rows are not divisible by page size | Use `getNumberOfElements()` for the actual count |
| Order changes between requests | Sort lacks a unique tie-breaker or data was updated | Add primary key as tie-breaker; consider cursor if needed |
| Sort reports non-existent property | Passing SQL column name instead of Java property or non-persistent property | Check entity, `@Column`, and mapping metadata |
| Query is slow despite small page size | Very large offset, missing index, or expensive count query | Inspect execution plan, indexes, count, and pagination strategy |
| Total page count is unexpected | Filter/count condition or data changed between queries | Check query conditions and read timing |
| Client can request huge pages | Endpoint does not cap `size` | Set default/maximum page size and validate requests |

## 11. Workflow for choosing the right API

| Need | API to consider |
| --- | --- |
| Save an aggregate | `CrudRepository.save` |
| Find an aggregate by ID | `CrudRepository.findById` |
| Delete by ID | `CrudRepository.deleteById` |
| Fetch a small, clearly bounded set without page metadata | Bounded query or appropriate list-fetching mechanism |
| Fetch all rows in a given order | `PagingAndSortingRepository.findAll(Sort)` |
| Fetch one page and need total elements/pages | `PagingAndSortingRepository.findAll(Pageable)` |
| Filter by condition and paginate | Derived query method taking `Pageable` |
| Traverse very large datasets | Consider appropriate scrolling/keyset/cursor instead of huge offsets |

Never call `findAll()` and slice the list with `subList` to simulate pagination. That approach loads the entire result set into memory and fails to leverage database-level limits.

## 12. Practice exercises

**Exercise 1 — Combining interfaces.** Create `CustomerRepository` extending both `CrudRepository<Customer, Long>` and `PagingAndSortingRepository<Customer, Long>`. Call `save`, `findById`, `deleteById`, and `findAll(Pageable)` to observe both API groups working together.

**Exercise 2 — Sorting.** Fetch the first 20 customers ordered by `createdAt` descending, then add `fullName` ascending and `id` ascending as tie-breakers. Try creating multiple rows with the same timestamp.

**Exercise 3 — Paginating a query method.** Add `findByStatus(String status, Pageable pageable)`. Seed enough data for at least three pages, read pages 0, 1, and 2, and compare `getTotalElements()`, `getTotalPages()`, and `getNumberOfElements()`.

**Exercise 4 — REST API.** Create an endpoint accepting `page`, `size`, and `sort`. Set default page size to 20, cap maximum at 100, and whitelist allowed sort properties.

**Exercise 5 — Evaluating count and offset.** Observe the SQL/plan of a `Page` query; compare the cost of reading the first page versus a page with a large offset. Identify cases where the UI genuinely needs the total page count.
