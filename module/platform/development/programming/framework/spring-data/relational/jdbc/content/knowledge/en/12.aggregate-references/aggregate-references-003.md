# Modeling a Many-to-One Relationship Between Order and Customer

In **Spring Data Relational JDBC (Spring Data JDBC)**, a **many-to-one** relationship between `Order` and `Customer` is typically modeled with a foreign key `customer_id` on the orders table. Multiple orders can reference the same customer, while each order belongs to only one customer according to the example's rules.

Crucially, `Order` and `Customer` can be **two independent aggregates**. `Order` holds the Customer's ID to know who placed the order; it does not need to contain the entire Customer object or own Customer's lifecycle. Spring Data JDBC does not automatically load Customer like an ORM lazy-loading mechanism. When customer details are needed, the application queries the Customer aggregate separately or uses an appropriate read query.

## 1. Understanding Many-to-One Cardinality Correctly

In the sales example:

- One `Customer` can create **0..N Orders**.
- Each `Order` is associated with **exactly one Customer**.
- An Order can have its own items, but those items do not change how the reference to Customer is modeled.


The `||--o{` notation read from Customer to Order means **one Customer can have zero or many Orders**, while each Order must link to exactly one Customer. If the domain allows an order not yet linked to a customer, the cardinality on the Order side changes and the FK column must be nullable; decide that before creating the schema.

### Why Is the Foreign Key Placed on the Order Side?

In the relational model, each row in `sales_orders` only needs to store a single `customer_id` value. Multiple order rows can store that same value:

~~~text
customers
+----+---------------+----------------+
| id | customer_code | display_name   |
+----+---------------+----------------+
| 10 | CUS-010       | Nguyen An      |
| 20 | CUS-020       | Tran Binh      |
+----+---------------+----------------+

sales_orders
+-----+-------------+-----------+
| id  | customer_id | status    |
+-----+-------------+-----------+
| 501 | 10          | CONFIRMED |
| 502 | 10          | DRAFT     |
| 503 | 20          | CONFIRMED |
+-----+-------------+-----------+
~~~

Orders `501` and `502` both belong to customer `10`; order `503` belongs to customer `20`. There is no need for a Customer row to hold a list of order IDs to represent this relationship in the database.

## 2. Distinguishing Data Relationships and Aggregate Boundaries

A foreign key indicates that two rows are linked at the data level. It does **not automatically decide** that two objects must live inside the same aggregate.

With this design:

- `Customer` is a separate aggregate root with independent identity and lifecycle.
- `Order` is a separate aggregate root with order status and business rules.
- `Order.customerId` is a reference to Customer's identity.
- Changing a Customer's name, email, or profile status does not imply loading and re-saving every Order.


Two Orders can reference the same Customer while remaining independent aggregates. Operations updating Order go through `OrderRepository`; operations updating the Customer profile go through `CustomerRepository`.

**Do not assume "has an FK means child object".** If you place Customer directly inside Order's owned object graph, you risk blurring aggregate boundaries and causing Spring Data JDBC to interpret mapping as a different object structure than intended.

## 3. SQL Schema for Customer and Order

The following example uses PostgreSQL. The `customers` table is created first, and then `sales_orders` references it:

~~~sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(40) NOT NULL UNIQUE,
    display_name VARCHAR(120) NOT NULL
);

CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_sales_orders_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
        ON DELETE RESTRICT
);

CREATE INDEX idx_sales_orders_customer_id
    ON sales_orders(customer_id);
~~~

Key details to note:

- `customers.id` and `sales_orders.id` are database-generated primary keys.
- `sales_orders.customer_id` is a foreign key pointing to `customers.id`.
- `NOT NULL` expresses the rule that every Order must have a Customer.
- `ON DELETE RESTRICT` prevents deleting a Customer while orders still reference them. The delete policy must match the business lifecycle.
- The index on `customer_id` makes filtering orders by customer more efficient; not every DBMS automatically creates an index on the referencing foreign key column.

If using MySQL, declare the auto-increment primary key as `BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY`, choose `ENGINE=InnoDB`, and keep the same foreign key structure. The timestamp type can use `TIMESTAMP` or `DATETIME` according to your UTC storage convention and application precision.

### Sample Data

~~~sql
INSERT INTO customers (customer_code, display_name) VALUES
    ('CUS-010', 'Nguyen An'),
    ('CUS-020', 'Tran Binh');

INSERT INTO sales_orders (customer_id, status) VALUES
    ((SELECT id FROM customers WHERE customer_code = 'CUS-010'), 'CONFIRMED'),
    ((SELECT id FROM customers WHERE customer_code = 'CUS-010'), 'DRAFT'),
    ((SELECT id FROM customers WHERE customer_code = 'CUS-020'), 'CONFIRMED');
~~~

The business code `customer_code` is used to look up the actual ID rather than assuming auto-increment IDs always start at a specific value. The first two orders both reference Customer `CUS-010`, illustrating the "many" side of the relationship.

Verification:

~~~sql
SELECT
    c.id AS customer_id,
    c.customer_code,
    c.display_name,
    o.id AS order_id,
    o.status,
    o.created_at
FROM customers c
JOIN sales_orders o ON o.customer_id = c.id
ORDER BY c.customer_code, o.id;
~~~

## 4. Java Model: Storing customerId in Order

The simplest and clearest approach is storing the foreign key as a scalar property `Long customerId`. Spring Data JDBC maps this property to the `customer_id` column via its camelCase-to-snake_case naming strategy; `@Column` can be used to declare the column name explicitly.

### Customer.java

~~~java
package com.example.sales.customer;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("customers")
public class Customer {

    @Id
    private Long id;

    private String customerCode;
    private String displayName;

    protected Customer() {
        // For Spring Data JDBC.
    }

    public Customer(String customerCode, String displayName) {
        this.customerCode = customerCode;
        this.displayName = displayName;
    }

    public Long getId() {
        return id;
    }

    public String getCustomerCode() {
        return customerCode;
    }

    public String getDisplayName() {
        return displayName;
    }
}
~~~

### Order.java

~~~java
package com.example.sales.order;

import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private Long customerId;

    private String status;

    protected Order() {
        // For Spring Data JDBC.
    }

    public Order(Long customerId) {
        if (customerId == null || customerId <= 0) {
            throw new IllegalArgumentException("Customer ID is required");
        }
        this.customerId = customerId;
        this.status = "DRAFT";
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }
}
~~~

Here `Order` only holds the Customer ID. When Spring Data JDBC saves an Order, it writes the numeric ID into `sales_orders.customer_id`. When loading an Order, the framework reads the column value and assigns it to `customerId`; it **does not automatically load Customer**.

### Why Not Declare Customer Directly?

A misleading way to write this is:

~~~java
private Customer customer;
~~~

In Spring Data JDBC, object fields do not carry JPA's `@ManyToOne` semantics. Mapping nested objects can cause Customer to be treated as part of the aggregate being saved, or produce a mapping model that does not match aggregate-reference intent. For another aggregate, use an **ID reference** or `AggregateReference`.

Do not add JPA's `@ManyToOne`, `@JoinColumn`, or `@OneToMany` to Spring Data JDBC examples. Those annotations belong to the JPA ORM model.

## 5. AggregateReference: Representing a Typed Reference

Spring Data JDBC provides `AggregateReference<T, ID>` to express that an aggregate references another aggregate root by ID. It makes the code explicitly state "this is a reference to Customer", while the persisted value remains a scalar foreign key.

Example replacing `Long customerId`:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;
import org.springframework.data.jdbc.core.mapping.AggregateReference;

@Table("sales_orders")
public class Order {

    @Id
    private Long id;

    @Column("customer_id")
    private AggregateReference<Customer, Long> customer;

    private String status;

    protected Order() {}

    public Order(Long customerId) {
        this.customer = AggregateReference.to(customerId);
        this.status = "DRAFT";
    }

    public Long getCustomerId() {
        return customer == null ? null : customer.getId();
    }
}
~~~

In this example, `Customer` is the referenced aggregate type and `Long` is the ID type. `AggregateReference.to(customerId)` creates a reference carrying the ID; it does not query Customer and does not hold a Customer instance.

| Representation | Meaning | When suitable |
|---|---|---|
| `Long customerId` | A plain ID value | Simple model, easy to read and query |
| `AggregateReference<Customer, Long> customer` | Typed reference ID | When you want to clearly indicate a reference to the Customer aggregate |
| `Customer customer` | Customer object | Not suitable for representing an independent aggregate reference in this simple way |

The first two options are **alternatives to each other** for the same `customer_id` column; do not declare both properties writing to the same column.

`AggregateReference` is not a proxy, does not support lazy loading, and does not automatically call `CustomerRepository` on access. If the customer name is needed, Customer must still be read through its repository or a read model query.

## 6. Two Independent Repositories

### CustomerRepository

~~~java
package com.example.sales.customer;

import org.springframework.data.repository.CrudRepository;

public interface CustomerRepository
        extends CrudRepository<Customer, Long> {
}
~~~

### OrderRepository

~~~java
package com.example.sales.order;

import java.util.List;
import org.springframework.data.repository.CrudRepository;

public interface OrderRepository
        extends CrudRepository<Order, Long> {

    List<Order> findAllByCustomerIdOrderByIdAsc(Long customerId);
}
~~~

The `findAllByCustomerIdOrderByIdAsc` method fits the Java model using the scalar `customerId` property. Spring Data JDBC derives the filter condition from the property and maps it to the `customer_id` column.

If `AggregateReference` is chosen, you can still build queries by referenced ID, though how query methods are declared depends on property representation and Spring Data version. You can use an explicit `@Query` when needed:

~~~java
@Query("""
    SELECT id, customer_id, status, created_at
    FROM sales_orders
    WHERE customer_id = :customerId
    ORDER BY id
    """)
List<Order> findOrdersForCustomer(long customerId);
~~~

This is an example query for an entity with matching columns in the schema. When using `@Query`, ensure column names and aliases are compatible with the mapping; SQL syntax and parameter types should be tested against the actual database.

## 7. Creating an Order with a Valid Customer

The application service coordinates both aggregates. Before creating an Order, the use case can verify that the Customer exists and is permitted to place orders:

~~~java
package com.example.sales.order;

import com.example.sales.customer.Customer;
import com.example.sales.customer.CustomerRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderApplicationService {

    private final CustomerRepository customers;
    private final OrderRepository orders;

    public OrderApplicationService(
            CustomerRepository customers,
            OrderRepository orders) {
        this.customers = customers;
        this.orders = orders;
    }

    @Transactional
    public Long createDraft(Long customerId) {
        Customer customer = customers.findById(customerId)
            .orElseThrow(() -> new IllegalArgumentException(
                "Customer not found: " + customerId
            ));

        // Business rules/status checks for the customer can be performed here.
        Order order = new Order(customer.getId());
        Order saved = orders.save(order);
        return saved.getId();
    }
}
~~~

Sequence:

1. The application service receives `customerId` from the use case.
2. `CustomerRepository` loads the independent Customer root.
3. The service checks required business conditions.
4. Create an Order containing only `customerId`.
5. `OrderRepository` saves the Order aggregate and the database checks the FK.
6. The service returns the generated Order ID.

Do not place the entire Customer inside Order just for convenience in reading the name. If the response needs the customer's name as well, the service can construct a DTO from both results or use a join read query.

### Why Is an FK Still Needed When the Service Already Checks Customer?

Between the time the service reads Customer and inserts Order, another transaction might try to delete the Customer. Application-service checks improve business error messages, but **do not replace FK constraints**. The database is the final guarantee that no Order references a deleted Customer.

If Customer is deleted after the check, inserting the Order will fail due to the FK. The transaction rolls back and the application must translate the error into a result appropriate for the use case.

## 8. Reading Order and Customer When Display Is Needed

Because Order only holds the ID, retrieving customer details requires an explicit extra step:

~~~java
Order order = orders.findById(orderId)
    .orElseThrow();

Customer customer = customers.findById(order.getCustomerId())
    .orElseThrow();

OrderDetailResponse response = new OrderDetailResponse(
    order.getId(),
    order.getStatus(),
    customer.getCustomerCode(),
    customer.getDisplayName()
);
~~~

Illustrative DTO:

~~~java
public record OrderDetailResponse(
    Long orderId,
    String status,
    String customerCode,
    String customerName
) {}
~~~

This approach is easy to understand, but it can cause **N+1 queries** if iterating over many Orders and querying Customer separately for each one. When building a list screen, options include:

- Fetch the list of Orders matching the criteria, collect unique customer IDs, batch-load Customers, and assemble DTOs in the service.
- Write a read query joining `sales_orders` and `customers` to return projections/DTOs.
- Use a read model suited to display and performance requirements.

Example SQL reading a list of orders along with customer names:

~~~sql
SELECT
    o.id AS order_id,
    o.status,
    o.created_at,
    c.id AS customer_id,
    c.customer_code,
    c.display_name AS customer_name
FROM sales_orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.id = :customer_id
ORDER BY o.created_at DESC, o.id DESC;
~~~

`:customer_id` is an illustrative named parameter; when running in a SQL client, replace it with a value or bind parameter. A join query used for **reading data** does not require turning Customer into a child object of Order.

## 9. Do Not Add an Order List to Customer Just for Bidirectional Navigation

A tempting model:

~~~java
public class Customer {
    private Long id;
    private List<Order> orders;
}
~~~

In Spring Data JDBC, placing a list of Orders inside Customer can change how the framework understands aggregate ownership: Orders may be treated as child objects belonging to the Customer aggregate. That contradicts the chosen design where each Order has its own lifecycle, state, and repository.

Keep the model as:

~~~text
Customer aggregate
  CustomerRepository

Order aggregate
  OrderRepository
  customerId -> references Customer
~~~

If you need to view a customer's orders, use `findAllByCustomerId` or a read query. There is no need to store a reverse collection in the Customer entity.

## 10. Customer Deletion Rules and Impact on Order

Because Order has an independent lifecycle and needs to retain transaction history, deleting a Customer requires an explicit policy:

| Policy | Configuration/meaning | When suitable |
|---|---|---|
| Prevent deletion if Orders exist | FK `ON DELETE RESTRICT` or equivalent default behavior | Need to keep Customer to preserve history |
| Mark Customer inactive | Update status without deleting the row | Profile is no longer used for new orders, but history still references it |
| Allow unlinking | Nullable FK with `ON DELETE SET NULL` or manual update | Only when an order still makes sense without a Customer |
| Delete Orders along with Customer | `ON DELETE CASCADE` | Only when the domain truly defines a dependent lifecycle and accepts losing orders |

For orders, `ON DELETE CASCADE` is usually a dangerous choice because deleting a customer profile can wipe out order history. Prefer archiving/deactivating Customer or blocking deletion per policy. The FK constraint protects data integrity, while the keep/delete decision is a business policy.

## 11. Customer Reference and Order Snapshots

Storing `customer_id` tells us **which customer the order belongs to**. However, Customer profile data can change over time—for instance, the customer changes their name or address after placing an order.

Distinguish two needs:

- **Current information:** an admin screen wants to show the latest Customer name. Read via `CustomerRepository` or a join.
- **Information at transaction time:** an invoice must preserve the billing name, billing address, and tax code exactly as they were when the order was created. Store a snapshot of the needed values inside the Order aggregate (often as an embedded value object) alongside `customer_id` so the original subject can still be traced.

For example:

~~~text
Order
  id
  customer_id              -> current Customer
  billing_snapshot
    recipient_name         -> name at placement time
    street
    city
    tax_code
~~~

A snapshot is not a copy of the entire Customer. Store only data with legal/business significance for the order. That way, Customer profile updates do not rewrite transaction history.

## 12. Transactions and Invariants Between Two Aggregates

An application service can use a shared database transaction to read Customer and then insert Order. This fits the simple rule "the customer must exist when creating an order."

However, distinguish carefully:

- **Invariants inside Order:** order status and item list must be consistent. Protected inside the Order aggregate.
- **Invariants inside Customer:** profile status and customer-specific rules. Protected inside the Customer aggregate.
- **Coordination rules:** only active customers can create orders. The application service coordinates this; depending on concurrency needs, transactions, locks, or re-checks may be required.

Do not merge Customer and all Orders into a single aggregate just because one use case involves both. When the two aggregates live in different systems/databases, a local transaction cannot guarantee cross-system atomicity; you must design events, retries, outbox/saga, or eventual consistency workflows as required.

## 13. Common Design Mistakes

| Mistake | Consequence | Resolution |
|---|---|---|
| Putting `Customer customer` directly in Order like an ORM relation | Ambiguity in ownership and how Spring Data JDBC maps it | Use `Long customerId` or `AggregateReference<Customer, Long>` |
| Using JPA's `@ManyToOne` annotation | Wrong persistence model | Use ID references and FKs in the schema |
| Adding `List<Order>` to Customer | Can turn Order into a child object inside the Customer aggregate | Keep two separate roots; query orders by customer ID |
| Assuming FK auto-loads Customer when reading Order | Calling getter has no Customer object to access | Use CustomerRepository or a read query |
| Omitting FK because the service already checked existence | Orphan Orders can arise from race conditions or writes from other sources | Add a database FK |
| Using `ON DELETE CASCADE` without careful thought | Deleting Customer can wipe out order history | Choose RESTRICT, soft-delete, or an intentional delete policy |
| Relying on current Customer name as the sole historical record | Name changes corrupt past transaction details | Store required snapshots on Order |
| Querying Customer in a loop for each Order | N+1 queries and higher latency | Batch fetch or join/projection |
| Treating Customer existence as sufficient to place an order | Ignores customer status/business conditions | Validate conditions in the application service |

## 15. Key Takeaways

A many-to-one relationship between Order and Customer means **many Orders reference one Customer**. In the database, the foreign key sits on the "many" side: `sales_orders.customer_id` points to `customers.id`. In the domain model, Customer and Order can still remain two independent aggregates.

With Spring Data JDBC, represent the reference as a scalar ID or `AggregateReference`; both keep the foreign key value without automatically loading the Customer object. Each aggregate has its own repository, while application services and read queries coordinate data when use cases need it. Keeping this boundary clear avoids confusing foreign keys with ownership, prevents unintended cascades, and preserves order history when customer profiles change.
