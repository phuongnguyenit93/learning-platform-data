# Giá trị version lúc thêm mới, cập nhật và xóa

Trong **Spring Data Relational JDBC**, optimistic locking dùng một thuộc tính số được đánh dấu **@Version** trên **aggregate root**. Giá trị version đại diện cho phiên bản của aggregate trong database. Khi cập nhật hoặc xóa aggregate, Spring Data JDBC dùng ID cùng version để xác nhận dữ liệu chưa bị một transaction khác thay đổi kể từ lần đọc trước.

Vòng đời version có ba mốc:

- **Insert:** aggregate mới có version chưa được thiết lập. Spring Data JDBC khởi tạo version khi ghi thành công. Với thuộc tính wrapper **Long** bắt đầu bằng **null**, giá trị ban đầu được lưu là **0**.
- **Update:** câu lệnh cập nhật chỉ thành công nếu version trong database vẫn bằng version của object. Sau khi cập nhật thành công, version tăng một đơn vị trong database và trong object được trả về.
- **Delete:** câu lệnh xóa cũng kiểm tra version. Nếu version đã thay đổi, thao tác xóa thất bại với lỗi **OptimisticLockingFailureException**. Khi xóa thành công, version không tăng vì hàng dữ liệu đã bị xóa.

Hiểu đúng giá trị version ở từng thời điểm giúp tránh dùng object cũ, ghi đè thay đổi mới, xóa nhầm dữ liệu và xử lý sai lỗi cạnh tranh.

## 1. Version đại diện cho điều gì?

Giả sử ứng dụng quản lý đơn hàng:

```text
PurchaseOrder (aggregate root)
  ├── id
  ├── version
  ├── orderNumber
  ├── status
  └── lines
        ├── OrderLine
        └── OrderLine
```

**version** là số thứ tự phiên bản của toàn aggregate. Khi một thao tác lưu aggregate thành công, version mới cho biết trạng thái được ghi sau version trước đó.

Version không phải ID của aggregate, số thứ tự toàn cục, timestamp cập nhật hoặc số lần người dùng mở màn hình. Version chỉ có ý nghĩa trong phạm vi một aggregate root. Hai đơn hàng khác nhau có thể cùng có version 3.

## 2. Khai báo @Version trên aggregate root

Spring Data JDBC hỗ trợ optimistic locking với thuộc tính số được đánh dấu **@Version**. Ví dụ:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String orderNumber,
        String status
) {
    public PurchaseOrder withStatus(String newStatus) {
        return new PurchaseOrder(
                id,
                version,
                orderNumber,
                newStatus
        );
    }
}
```

Trong ví dụ, **@Id** xác định aggregate root, **@Version** đánh dấu thuộc tính dùng cho optimistic locking, còn **Long** cho phép biểu diễn trạng thái chưa có version bằng null. Method withStatus tạo instance mới nhưng giữ version đã đọc; Spring Data dùng version đó để kiểm tra cập nhật.

Version nên nằm trên aggregate root. Các entity con thuộc aggregate được bảo vệ thông qua version của root khi ứng dụng lưu aggregate. Nếu một đối tượng có vòng đời độc lập và được quản lý như aggregate root riêng, nó có thể có version riêng.

### 2.1. Kiểu dữ liệu và schema

Dùng kiểu số như Long hoặc Integer và kiểu cột tương thích. Không dùng String, UUID hoặc timestamp làm thuộc tính @Version cho optimistic locking của Spring Data JDBC.

DDL PostgreSQL minh họa:

```sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version BIGINT NOT NULL,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL
);
```

Cột version phải tồn tại và có kiểu tương thích với thuộc tính Java. Spring Data JDBC quản lý giá trị version khi insert/update; ứng dụng không nên tự tăng version trong domain method.

Nếu database có trigger tự tăng version hoặc một service khác tự cập nhật cột này, phải thiết kế đồng bộ với cơ chế Spring Data. Hai cơ chế cùng thay đổi version có thể làm những lần save tiếp theo bị optimistic locking failure.

## 3. Giá trị version khi thêm mới (INSERT)

Một aggregate mới với thuộc tính wrapper Long thường bắt đầu như sau:

```java
PurchaseOrder draft = new PurchaseOrder(
        null,
        null,
        "PO-261",
        "DRAFT"
);
```

Ở thời điểm này, id là null và version là null. Khi gọi repository:

```java
PurchaseOrder saved = repository.save(draft);
```

Vì version chưa được thiết lập, Spring Data JDBC nhận diện aggregate là mới và thực hiện insert. Version được khởi tạo trong quá trình ghi. Với Long wrapper, giá trị ban đầu thường là 0.

Sau khi lưu:

| Thuộc tính | Trước insert | Sau insert |
| --- | --- | --- |
| id | null | ID do database sinh |
| version | null | 0 |
| orderNumber | PO-261 | PO-261 |
| status | DRAFT | DRAFT |

Dùng instance trả về từ save:

```java
PurchaseOrder saved = repository.save(draft);

Long id = saved.id();
Long version = saved.version(); // 0 sau insert
```

Đặc biệt với entity immutable như record, đừng giả định object đầu vào sẽ được thay đổi tại chỗ để nhận ID hoặc version. Giá trị trả về là trạng thái nên được dùng cho thao tác tiếp theo.

### 3.1. SQL minh họa khi insert

Với schema ở trên, câu lệnh có ý nghĩa tương đương:

```sql
INSERT INTO purchase_order (
    order_number,
    status,
    version
)
VALUES (
    'PO-261',
    'DRAFT',
    0
);
```

Đây là SQL minh họa, không phải cam kết về câu lệnh nguyên văn trên mọi dialect. Spring Data JDBC và dialect quyết định cách tạo ID, bind version và nhận ID do database sinh.

### 3.2. Version cũng tham gia nhận diện entity mới

Khi aggregate có thuộc tính @Version, Spring Data dùng thuộc tính này trong chiến lược xác định entity mới. Một version wrapper null biểu thị instance mới; version đã có giá trị biểu thị instance hiện hữu. Với kiểu số nguyên primitive, giá trị 0 được dùng làm giá trị khởi đầu để nhận diện mới.

Điều này hữu ích khi ứng dụng cấp ID trước khi insert. Ví dụ một aggregate có UUID ID nhưng version vẫn null có thể được nhận diện là mới nhờ version property.

Không tự đặt version thành một số bất kỳ cho object mới. Nếu version đã có giá trị, Spring Data có thể xem aggregate là hiện hữu và đi theo đường update. Khi hàng chưa tồn tại, update không thể thay thế insert.

## 4. Giá trị version khi cập nhật (UPDATE)

Sau insert, giả sử aggregate có:

```text
id      = 261
version = 0
status  = DRAFT
```

Ứng dụng tải aggregate:

```java
PurchaseOrder current = repository.findById(261L)
        .orElseThrow();
```

Thay đổi trạng thái rồi lưu:

```java
PurchaseOrder changed = current.withStatus("CONFIRMED");
PurchaseOrder updated = repository.save(changed);
```

Spring Data JDBC tạo update có điều kiện theo ID và version đang có. Về ý nghĩa:

```sql
UPDATE purchase_order
SET status = 'CONFIRMED',
    version = 1
WHERE id = 261
  AND version = 0;
```

Nếu hàng trong database vẫn có version 0, update thành công. Spring Data tăng version lên 1 cả trong database và instance được trả về.

| Thuộc tính | Trước update | Sau update thành công |
| --- | --- | --- |
| id | 261 | 261 |
| version | 0 | 1 |
| status | DRAFT | CONFIRMED |

SQL trên chỉ mô tả nguyên tắc compare-and-set. Câu lệnh thật có thể khác về bind parameter, danh sách cột và cú pháp theo dialect.

### 4.1. Mỗi lần update thành công tăng version

Giả sử một lần lưu tiếp theo bắt đầu từ version 1:

```java
PurchaseOrder current = repository.findById(261L)
        .orElseThrow();

PurchaseOrder changed = current.withStatus("SHIPPED");
PurchaseOrder updated = repository.save(changed);
```

Database kiểm tra version 1, rồi lưu version 2. Version tiếp tục tăng theo từng lần cập nhật aggregate thành công.

Trong Spring Data JDBC, không có dirty checking kiểu JPA để chỉ cập nhật khi một field thực sự thay đổi. Khi ứng dụng gọi save cho aggregate hiện hữu, thao tác lưu vẫn đi qua cơ chế update và version được tăng khi update thành công. Vì vậy, không gọi save lặp lại không cần thiết chỉ để lấy dữ liệu.

### 4.2. Thay đổi entity con cũng làm version root thay đổi

Nếu PurchaseOrder sở hữu collection lines, thao tác thêm/sửa/xóa line rồi lưu aggregate root cũng thuộc lần cập nhật aggregate:

1. Tải PurchaseOrder hiện tại qua repository.
2. Gọi domain method của aggregate để thêm, sửa hoặc bỏ OrderLine.
3. Gọi repository.save với aggregate đã thay đổi.

Method nghiệp vụ có thể mang tên addLine, changeQuantity hoặc removeLine tùy domain model. Điểm quan trọng là thao tác lưu vẫn đi qua root; Spring Data kiểm tra version của root và tăng version sau khi cập nhật aggregate thành công.

Version của root được kiểm tra và tăng. Nhờ đó, hai transaction cùng sửa các phần khác nhau của một aggregate vẫn có thể phát hiện xung đột ở ranh giới aggregate.

Nếu child thực sự cần được cập nhật độc lập và có concurrency riêng, hãy xem lại ranh giới aggregate thay vì cố dùng version root như version độc lập cho từng child.

## 5. Điều gì xảy ra khi hai transaction cập nhật cùng một version?

Giả sử database đang có:

```text
PurchaseOrder #261
version = 4
status  = DRAFT
```

Hai transaction A và B cùng đọc đơn hàng. Cả hai đều giữ object có version 4.

```text
Database: version 4
       /             \
      ▼               ▼
Transaction A     Transaction B
đọc version 4     đọc version 4
      │               │
      ▼               │
save thành công       │
version thành 5       │
      │               ▼
      │          save với version 4
      │               │
      └──────► WHERE version = 4
                      │
                      ▼
              0 hàng được cập nhật
                      │
                      ▼
          OptimisticLockingFailureException
```

A cập nhật trước, nên version trong database thành 5. B vẫn gửi object version 4; điều kiện WHERE id = 261 AND version = 4 không còn khớp. Spring Data JDBC ném OptimisticLockingFailureException.

Lỗi này có nghĩa object đang được lưu không còn dựa trên phiên bản hiện tại. Nó không nhất thiết có nghĩa database hỏng hoặc SQL sai.

### 5.1. Xử lý OptimisticLockingFailureException

Service có thể bắt lỗi để chuyển thành phản hồi nghiệp vụ/API:

```java
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderService {

    private final PurchaseOrderRepository repository;

    public PurchaseOrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public PurchaseOrder changeStatus(Long id, String status) {
        PurchaseOrder current = repository.findById(id)
                .orElseThrow();

        PurchaseOrder changed = current.withStatus(status);

        try {
            return repository.save(changed);
        } catch (OptimisticLockingFailureException ex) {
            throw new OrderConflictException(
                    "The order changed while this request was being processed",
                    ex
            );
        }
    }
}
```

OrderConflictException là exception nghiệp vụ do ứng dụng định nghĩa. Tùy API, ứng dụng có thể trả HTTP 409 Conflict để client biết cần tải trạng thái mới.

Không nên bắt lỗi rồi tự động gọi save lại trên chính object cũ. Object đó vẫn mang version cũ và có thể chứa quyết định nghiệp vụ dựa trên trạng thái đã lỗi thời. Cách xử lý an toàn là tải aggregate mới, so sánh thay đổi và quyết định có thể áp dụng lại command hay yêu cầu người dùng xác nhận.

### 5.2. Không phải mọi xung đột đều có thể retry mù quáng

Retry có thể hợp lý với một command idempotent và có quy tắc hợp nhất rõ ràng. Nhưng nếu hai người cùng thay đổi giá, trạng thái phê duyệt hoặc số lượng hàng, việc tự áp dụng lại command có thể làm sai ý định của một bên.

Trước khi retry, xác định command có thể thực hiện nhiều lần mà không tạo side effect lặp không, có thể áp dụng thay đổi lên trạng thái mới mà không vi phạm invariant không, người dùng có cần thấy thay đổi của bên kia trước khi quyết định không, và transaction cũ đã rollback đầy đủ chưa.

## 6. Giá trị version khi xóa (DELETE)

Optimistic locking cũng áp dụng cho thao tác xóa aggregate. Khi xóa một aggregate có @Version, Spring Data JDBC kiểm tra version trước khi xóa.

Giả sử object đang có:

```text
id      = 261
version = 5
```

SQL có ý nghĩa tương đương:

```sql
DELETE FROM purchase_order
WHERE id = 261
  AND version = 5;
```

Nếu database vẫn có version 5, xóa thành công. Nếu một transaction khác đã cập nhật aggregate thành version 6, điều kiện không khớp và Spring Data JDBC ném OptimisticLockingFailureException.

**Version không tăng khi delete.** Khi xóa thành công, hàng bị loại khỏi database; không có version kế tiếp được lưu cho hàng đó.

### 6.1. So sánh version trước và sau delete

| Trạng thái | Version |
| --- | ---: |
| Aggregate vừa insert | 0 |
| Sau update thành công lần 1 | 1 |
| Sau update thành công lần 2 | 2 |
| Đọc aggregate trước khi xóa | 2 |
| Xóa thành công | Hàng không còn tồn tại; không tăng version |

Không diễn giải delete như một lần update cuối cùng có version 3. Spring Data dùng version để kiểm tra quyền xóa trên phiên bản đã đọc, sau đó xóa hàng.

### 6.2. Xóa object đã cũ

Giả sử transaction A đọc version 2. Transaction B cập nhật trước và lưu version 3. Sau đó A gọi:

```java
repository.delete(oldOrder);
```

Vì oldOrder vẫn mang version 2, thao tác xóa không được phép xóa phiên bản 3 mà A chưa đọc. Spring Data JDBC báo optimistic locking failure.

Đây là hành vi quan trọng: một yêu cầu xóa dựa trên trạng thái cũ không tự động xóa thay đổi mới của người khác.

### 6.3. delete(entity) và deleteById(id)

Hai cách gọi có thông tin đầu vào khác nhau:

```java
repository.delete(order);
repository.deleteById(orderId);
```

- delete(entity) nhận object có cả ID và version. Version trên object được dùng để kiểm tra trạng thái mà caller đã đọc.
- deleteById(id) chỉ nhận ID. Repository có thể tải entity hiện tại rồi thực hiện xóa theo version của entity được tải. Vì caller không truyền version đã quan sát, phương thức này không thể biểu diễn trực tiếp điều kiện “chỉ xóa nếu vẫn đúng version mà client đã xem”.

Nếu API cần bảo vệ thao tác xóa dựa trên version client đã đọc, hãy truyền version đó trong command/ETag và so sánh với aggregate hiện tại trước khi xóa; hoặc tải entity đã được kiểm soát theo đúng quy trình ứng dụng. Không bỏ qua kiểm tra version chỉ vì request chỉ có ID.

Các phương thức xóa hàng loạt như deleteAll() và SQL tùy chỉnh có thể có semantics khác với xóa từng aggregate. Không mặc định mọi bulk delete đều thực hiện version check trên từng hàng; hãy xem contract của phương thức và phiên bản Spring Data đang dùng.

## 7. Bảng tổng hợp vòng đời version

| Thao tác | Version đầu vào | Điều kiện database | Kết quả version | Nếu version không khớp |
| --- | --- | --- | --- | --- |
| Insert aggregate mới | null với Long wrapper | Hàng chưa được tạo | Khởi tạo thành 0 | Lỗi insert/constraint nếu dữ liệu xung đột |
| Update lần đầu | 0 | id khớp và version là 0 | Tăng thành 1 | OptimisticLockingFailureException |
| Update tiếp theo | 1 | id khớp và version là 1 | Tăng thành 2 | OptimisticLockingFailureException |
| Delete | Version hiện tại, ví dụ 2 | id khớp và version là 2 | Không tăng; hàng bị xóa | OptimisticLockingFailureException |

Minh họa chuỗi SQL:

```sql
-- Tạo mới.
INSERT INTO purchase_order (order_number, status, version)
VALUES ('PO-261', 'DRAFT', 0);

-- Cập nhật version 0 thành 1.
UPDATE purchase_order
SET status = 'CONFIRMED', version = 1
WHERE id = 261 AND version = 0;

-- Cập nhật version 1 thành 2.
UPDATE purchase_order
SET status = 'SHIPPED', version = 2
WHERE id = 261 AND version = 1;

-- Xóa khi version vẫn là 2.
DELETE FROM purchase_order
WHERE id = 261 AND version = 2;
```

Đây là chuỗi SQL mô phỏng semantics. Spring Data JDBC tạo SQL thực tế qua mapping metadata và dialect, đồng thời xử lý giá trị version trên object.

## 8. Version và trạng thái entity mới

Version không chỉ phục vụ concurrency; nó còn tham gia chiến lược nhận diện entity mới.

| Cấu hình entity | Giá trị ban đầu | Ý nghĩa thông thường |
| --- | --- | --- |
| @Version Long version | null | Entity mới |
| @Version Long version | 0 sau insert | Entity đã được insert |
| @Version Long version | 1, 2, ... | Entity hiện hữu |
| @Version long version | 0 | Giá trị primitive khởi đầu, được xem là mới |

Nếu entity có @Version, Spring Data dùng version để xác định trạng thái mới; nếu không có version, chiến lược mặc định thường dựa trên ID. Persistable.isNew() là một cơ chế tùy chỉnh khác và cần được cấu hình nhất quán nếu entity dùng nó.

Một lỗi thường gặp là tự tạo entity có ID và version đã được đặt thành một số dương dù hàng chưa tồn tại. Spring Data có thể coi đó là entity hiện hữu và thử update. Nếu hàng không có, update không tạo mới thay cho insert.

Ngược lại, không đặt lại version của entity đã tồn tại về null để ép insert. Việc đó có thể khiến Spring Data chọn insert và database báo duplicate key.

## 9. Version của aggregate root và các entity con

Spring Data JDBC đặt version ở aggregate root. Khi lưu aggregate:

- Update root được bảo vệ bằng điều kiện ID/version.
- Thay đổi entity con thuộc aggregate đi cùng thao tác lưu root.
- Version root tăng sau update aggregate thành công.
- Delete aggregate kiểm tra version root trước khi xóa.

Ví dụ root có collection:

```java
@Table("purchase_order")
public record PurchaseOrder(
        @Id Long id,
        @Version Long version,
        String status,
        @MappedCollection(idColumn = "purchase_order_id")
        List<OrderLine> lines
) {}
```

Không cần thêm một @Version độc lập vào từng OrderLine chỉ để bảo vệ thay đổi thuộc aggregate này. Nếu một line thực sự cần được chỉnh sửa và lưu độc lập, đó là dấu hiệu cần đánh giá lại mô hình ownership và aggregate boundary.

Vì Spring Data JDBC không giữ persistence context như JPA, một lần save aggregate hiện hữu có thể đồng bộ lại các entity con theo trạng thái object. Optimistic locking trên root giúp phát hiện một transaction khác đã cập nhật aggregate trước khi transaction hiện tại ghi trạng thái của nó.

## 10. Transaction và tính nguyên tử của update/delete

Một lần cập nhật aggregate có thể thực hiện nhiều câu SQL: kiểm tra/cập nhật root, xóa các hàng child cũ và insert lại child theo trạng thái hiện tại. Khi có @Version, câu update root là điểm kiểm tra cạnh tranh.

Nếu update root thất bại vì version không khớp, thao tác lưu aggregate không được để lại các thay đổi child một phần. Hãy bảo đảm các câu SQL của use case nằm trong transaction phù hợp:

```java
@Transactional
public PurchaseOrder replaceLines(
        Long orderId,
        List<OrderLine> newLines) {

    PurchaseOrder current = repository.findById(orderId)
            .orElseThrow();

    PurchaseOrder changed = current.withLines(newLines);
    return repository.save(changed);
}
```

Transaction cũng quan trọng khi xóa aggregate có child: các câu lệnh xóa liên quan phải hoàn thành cùng một đơn vị công việc. Cấu hình transaction manager phải dùng cùng DataSource với Spring Data JDBC.

@Version không thay thế transaction. Nó phát hiện xung đột giữa các lần ghi; transaction bảo đảm các câu SQL trong một thao tác được commit hoặc rollback cùng nhau.

## 11. Khi custom SQL hoặc service khác cập nhật dữ liệu

Optimistic locking chỉ hiệu quả nếu mọi đường ghi đều tôn trọng version. Một câu SQL tùy chỉnh như:

```sql
UPDATE purchase_order
SET status = 'CANCELLED'
WHERE id = 261;
```

không kiểm tra version và cũng không tăng version. Nếu câu lệnh này chạy trong khi một ứng dụng khác đang giữ object version 2, lần save sau của ứng dụng có thể vẫn khớp version 2 và không phát hiện thay đổi ngoài luồng.

Nếu custom SQL cần cập nhật aggregate có version, hãy đưa cả điều kiện version và bước tăng version vào câu lệnh:

```sql
UPDATE purchase_order
SET status = 'CANCELLED',
    version = version + 1
WHERE id = 261
  AND version = 2;
```

Ứng dụng cần kiểm tra số hàng bị ảnh hưởng:

- 1 hàng: cập nhật thành công và version đã tăng.
- 0 hàng: aggregate không tồn tại hoặc version không khớp; phân biệt hai trường hợp nếu nghiệp vụ cần.

Nếu custom SQL thay đổi child nhưng không cập nhật version root, các transaction khác có thể không phát hiện aggregate đã thay đổi. Hãy đồng bộ version root trong cùng transaction hoặc chuyển thao tác về repository/template để Spring Data quản lý.

## 12. Phân biệt optimistic locking với pessimistic locking

@Version là cơ chế **optimistic locking**:

- Không khóa hàng suốt thời gian người dùng chỉnh sửa trên màn hình.
- Cho phép nhiều transaction cùng đọc một version.
- Kiểm tra version tại thời điểm ghi.
- Từ chối thao tác dựa trên snapshot cũ.

Pessimistic locking dùng database lock để hạn chế transaction khác cập nhật trong thời gian khóa. Nó phù hợp với một số quy trình cần tuần tự hóa ngay từ lúc đọc, nhưng phải quản lý thời gian giữ lock và nguy cơ deadlock.

Không nên dùng @Version như một cơ chế khóa giữ chỗ. Nó không ngăn transaction khác đọc hoặc bắt đầu thay đổi object; nó chỉ phát hiện xung đột khi ghi/xóa.

## 13. Version trong REST API và giao diện người dùng

Nếu client đọc một đơn hàng và sau đó gửi lệnh cập nhật, có thể đưa version đã đọc vào response:

```json
{
  "id": 261,
  "version": 4,
  "orderNumber": "PO-261",
  "status": "DRAFT"
}
```

Client gửi command kèm version:

```json
{
  "status": "CONFIRMED",
  "expectedVersion": 4
}
```

Service tải aggregate hiện tại, so sánh version client gửi với version hiện tại và thực hiện domain command. Spring Data JDBC vẫn kiểm tra version ở thời điểm save; kiểm tra ở service giúp phản hồi rõ hơn nhưng không thay thế điều kiện version trong câu SQL vì một transaction khác vẫn có thể ghi giữa bước kiểm tra và save.

Một lựa chọn HTTP là dùng ETag cho version và yêu cầu client gửi If-Match. Nếu ETag không còn khớp, API có thể trả 412 Precondition Failed theo contract HTTP. Nếu ứng dụng biểu diễn xung đột nghiệp vụ bằng 409 Conflict, hãy dùng nhất quán với API của mình.

Không nhận version từ client rồi gán trực tiếp vào entity để tăng nó. Client chỉ cung cấp expected version; Spring Data JDBC và database thực hiện kiểm tra/increment.

## 14. Lỗi thường gặp

| Triệu chứng | Nguyên nhân có thể | Cách xử lý |
| --- | --- | --- |
| Insert mới thất bại vì version null hoặc schema không cho phép | Cột version chưa được cấu hình phù hợp hoặc custom mapping sai | Khai báo @Version đúng kiểu số và cột version tương thích |
| Aggregate mới bị update thay vì insert | Version đã được gán giá trị hiện hữu hoặc Persistable.isNew() báo sai | Để version wrapper ở null cho instance mới và kiểm tra state detection |
| Save lần đầu thành công nhưng object cũ vẫn có version null | Caller tiếp tục dùng instance đầu vào thay vì giá trị trả về | Dùng instance trả về từ save |
| Update thất bại với OptimisticLockingFailureException | Một transaction khác đã tăng version hoặc hàng không còn tồn tại | Tải lại aggregate và xử lý xung đột |
| Version không tăng sau custom update | SQL tùy chỉnh không cập nhật cột version | So sánh version và tăng version trong cùng câu SQL/transaction |
| Xóa object cũ thất bại | Database đã có version mới hơn object | Tải trạng thái hiện tại và yêu cầu quyết định xóa lại |
| Xóa thành công nhưng version không tăng | Đây là hành vi đúng của delete | Không chờ một version kế tiếp cho hàng đã bị xóa |
| Hai service ghi đè nhau mà không phát hiện | Một đường ghi bỏ qua version check | Bảo đảm mọi đường ghi cập nhật version root |
| deleteAll() không thể hiện kiểm tra version như xóa từng object | Bulk operation có contract khác | Dùng thao tác theo entity khi cần kiểm tra từng version; xác nhận API cụ thể |
| Tự retry làm thay đổi dữ liệu sai | Retry dùng object/command cũ mà không hợp nhất trạng thái mới | Tải lại và áp dụng quy tắc nghiệp vụ trước khi retry |

## 15. Bài tập thực hành

**Bài 1 — Insert version.** Thêm @Version Long version vào PurchaseOrder. Tạo aggregate mới với version null, gọi save và quan sát version trong object trả về cùng giá trị ở database.

**Bài 2 — Update version.** Đọc aggregate version 0, đổi status và lưu. Xác nhận version tăng lên 1. Tiếp tục lưu một thay đổi khác và xác nhận version tăng lên 2.

**Bài 3 — Cập nhật đồng thời.** Trong hai transaction, đọc cùng một aggregate version 2. Lưu transaction thứ nhất, sau đó lưu object cũ của transaction thứ hai. Xác nhận lỗi OptimisticLockingFailureException.

**Bài 4 — Xóa đúng version.** Đọc aggregate version hiện tại và gọi repository.delete(entity). Xác nhận hàng bị xóa và không có version mới được tạo.

**Bài 5 — Xóa object cũ.** Đọc aggregate version 3, cập nhật nó qua transaction khác thành version 4, rồi gọi delete với object version 3. Xác nhận thao tác xóa bị từ chối.

**Bài 6 — Entity con.** Thêm collection lines. Cập nhật một line qua aggregate root, lưu và xác nhận version của root tăng. Thử hai transaction sửa hai line khác nhau nhưng cùng root để quan sát xung đột ở aggregate boundary.

**Bài 7 — Custom SQL.** Viết câu update có WHERE id = ? AND version = ?, tăng version và kiểm tra số hàng bị ảnh hưởng. Thử lại với version cũ và xác nhận không có hàng nào được cập nhật.

**Bài 8 — REST expected version.** Trả version trong response, yêu cầu client gửi expectedVersion khi cập nhật. Kiểm tra trường hợp version cũ và chuyển lỗi optimistic locking thành phản hồi API phù hợp.
