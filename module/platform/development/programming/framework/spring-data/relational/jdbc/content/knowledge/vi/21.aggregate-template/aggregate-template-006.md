# Kết hợp `Query`, `Sort` và `Pageable` với template

Trong **Spring Data JDBC**, `JdbcAggregateTemplate` cung cấp API mức thấp hơn repository để làm việc trực tiếp với aggregate root. Khi cần tạo điều kiện tìm kiếm theo tham số lúc chạy, sắp xếp theo nhiều tiêu chí và giới hạn kết quả theo trang, có thể kết hợp ba abstraction của Spring Data:

- **`Query`** mô tả điều kiện lọc, các cột cần đọc, thứ tự sắp xếp và giới hạn/độ lệch của truy vấn.
- **`Sort`** mô tả thứ tự tăng/giảm theo một hoặc nhiều property.
- **`Pageable`** mô tả trang cần lấy, kích thước trang và `Sort` đi kèm.

`JdbcAggregateTemplate` nhận `Query` để đọc aggregate. `Query.with(pageable)` chuyển thông tin trang thành `offset`, `limit` và thứ tự sắp xếp. Với API Spring Data Relational hiện hành, template trả `List` cho `findAll(Query, Class)`; để tạo `Page<T>` có tổng số phần tử, ứng dụng gọi thêm `count(Query, Class)` rồi dựng `PageImpl`.

## 1. Vai trò của `JdbcAggregateTemplate`

Repository thường phù hợp với các thao tác được mô tả bằng method như `findByStatus(...)`, `findByCreatedAtAfter(...)` hoặc `findAll(Pageable)`. `JdbcAggregateTemplate` hữu ích khi điều kiện truy vấn được xây dựng động, chẳng hạn màn hình tìm kiếm có nhiều bộ lọc tùy chọn, hoặc khi một service cần phối hợp các thao tác aggregate mà không muốn khai báo nhiều method repository.

Template làm việc ở **ranh giới aggregate root**. Khi truy vấn và ánh xạ một `PurchaseOrder`, Spring Data JDBC sử dụng metadata của root và các thành phần thuộc aggregate để dựng đối tượng. `Query` ở đây là mô hình truy vấn có cấu trúc, không phải chuỗi SQL tùy ý như `@Query`.

Trong ứng dụng Spring Boot có Spring Data JDBC được cấu hình thông thường, có thể inject `JdbcAggregateTemplate`:

```java
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.stereotype.Service;

@Service
public class PurchaseOrderSearchService {
    private final JdbcAggregateTemplate template;

    public PurchaseOrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }
}
```

Không cần tự gọi constructor của template trong service. Spring Boot/Spring Data JDBC tạo và cấu hình hạ tầng JDBC, mapping context, converter và data access strategy để template sử dụng.

## 2. Mô hình dữ liệu dùng trong ví dụ

Giả sử hệ thống quản lý đơn hàng với các thuộc tính:

- `orderNumber`: mã đơn hàng.
- `status`: trạng thái hiện tại.
- `total`: tổng giá trị đơn.
- `createdAt`: thời điểm tạo.

Entity aggregate root:

```java
import java.math.BigDecimal;
import java.time.LocalDateTime;
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_orders")
public record PurchaseOrder(
        @Id Long id,
        String orderNumber,
        String status,
        BigDecimal total,
        LocalDateTime createdAt
) {}
```

DDL minh họa cho H2:

```sql
CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_number VARCHAR(40) NOT NULL UNIQUE,
    status VARCHAR(30) NOT NULL,
    total DECIMAL(18, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL
);
```

Tên property trong Java được Spring Data Relational ánh xạ theo metadata/naming strategy, ví dụ `orderNumber` thành `order_number`, `createdAt` thành `created_at`. Trong các ví dụ `Criteria` và `Sort` bên dưới, dùng tên property của aggregate như `status`, `total`, `createdAt` và `id`.

## 3. `Query`: mô tả điều kiện lọc

`Query` thuộc package `org.springframework.data.relational.core.query`. Có thể tạo query từ `Criteria`:

```java
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;

Query query = Query.query(
        Criteria.where("status").is("OPEN")
);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Ý nghĩa SQL tương đương:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?;
```

Giá trị `OPEN` được truyền như giá trị điều kiện; API query không yêu cầu nối giá trị người dùng vào một chuỗi SQL.

### Kết hợp nhiều điều kiện

`Criteria` hỗ trợ các toán tử như `is`, `greaterThan`, `greaterThanOrEquals`, `lessThan`, `between`, `in`, `like`, `isNull`, `isNotNull` và các phép kết hợp `and`/`or`.

Ví dụ tìm đơn đang mở có tổng tiền từ 1.000 trở lên:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .and("total").greaterThanOrEquals(new BigDecimal("1000.00"));

Query query = Query.query(criteria);
List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

SQL có ý nghĩa tương đương:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
  AND total >= ?;
```

Có thể thêm điều kiện thời gian:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .and("createdAt").greaterThanOrEquals(from)
        .and("createdAt").lessThan(to);
```

### Kết hợp `OR`

Ví dụ tìm đơn đang mở hoặc đã được đánh dấu ưu tiên:

```java
Criteria criteria = Criteria.where("status").is("OPEN")
        .or("priority").is("URGENT");
```

Khi điều kiện có nhiều nhóm `AND`/`OR`, hãy tạo nhóm `Criteria` tường minh để thể hiện đúng ngoặc logic. Đừng dựa vào việc nối các lời gọi dài mà không kiểm tra biểu thức SQL mong muốn.

### Query không có điều kiện

Khi muốn truy vấn mọi aggregate nhưng vẫn áp dụng `Sort`, `limit` hoặc `offset`, có thể dùng:

```java
Query query = Query.empty();
```

Hoặc dùng overload `template.findAll(PurchaseOrder.class, sort)` nếu chỉ cần tải tất cả đơn hàng theo thứ tự. `Query.empty()` hữu ích khi muốn tiếp tục xây dựng một truy vấn có cấu trúc chung mà không bắt buộc có `WHERE`.

## 4. `Sort`: sắp xếp theo một hoặc nhiều property

`Sort` thuộc `org.springframework.data.domain`. Một `Sort` có thể chứa một hoặc nhiều `Sort.Order`.

Sắp xếp theo thời điểm tạo giảm dần:

```java
import org.springframework.data.domain.Sort;

Sort sort = Sort.by(Sort.Order.desc("createdAt"));

List<PurchaseOrder> orders = template.findAll(
        PurchaseOrder.class,
        sort
);
```

Sắp xếp theo tổng tiền giảm dần, sau đó theo ID tăng dần:

```java
Sort sort = Sort.by(
        Sort.Order.desc("total"),
        Sort.Order.asc("id")
);

Query query = Query.query(Criteria.where("status").is("OPEN"))
        .sort(sort);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

SQL có ý nghĩa tương đương:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
ORDER BY total DESC, id ASC;
```

Thứ tự phụ `id ASC` làm cho thứ tự ổn định hơn khi nhiều đơn có cùng tổng tiền. Điều này đặc biệt quan trọng khi kết hợp phân trang: nếu các hàng có cùng giá trị sắp xếp chính và không có tiêu chí phụ duy nhất, một hàng có thể chuyển vị trí giữa các lần đọc.

### Sắp xếp tăng/giảm và nhiều tiêu chí

```java
Sort sort = Sort.by(
        Sort.Order.asc("status"),
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("id")
);
```

Các order được áp dụng theo đúng thứ tự khai báo. Database sắp xếp theo `status` trước, nếu bằng nhau thì theo `createdAt` giảm dần, nếu vẫn bằng nhau thì theo `id` tăng dần.

`Sort` sử dụng property/đường dẫn thuộc tính mà mapping có thể phân giải, không phải nơi để truyền một đoạn SQL tùy ý. Nếu giá trị `sortBy` đến từ request HTTP, hãy kiểm tra nó qua whitelist các property được phép; không đưa trực tiếp chuỗi tùy ý từ client vào cấu hình truy vấn.

## 5. Kết hợp `Query` và `Sort`

`Query.sort(sort)` trả về một `Query` mới có thêm thông tin sắp xếp:

```java
Query query = Query.query(
        Criteria.where("status").is("OPEN")
                .and("total").greaterThan(new BigDecimal("500.00"))
).sort(Sort.by(Sort.Order.desc("createdAt")));

List<PurchaseOrder> result = template.findAll(query, PurchaseOrder.class);
```

`JdbcAggregateTemplate.findAll(Query, Class)` thực thi truy vấn, dựng các aggregate phù hợp và trả về `List`. Nếu `Query` có `Sort`, danh sách được sắp xếp theo thông tin đó.

Lưu ý rằng `Query` là **immutable**. Các phương thức như `sort`, `limit`, `offset`, `columns` và `with` tạo ra một object mới. Phải giữ kết quả trả về:

```java
Query query = Query.query(Criteria.where("status").is("OPEN"));
query = query.sort(Sort.by("createdAt").descending());
```

Đoạn sau không thay đổi biến `query` vì kết quả mới bị bỏ đi:

```java
query.sort(Sort.by("createdAt").descending()); // Không giữ Query mới
```

## 6. `Pageable`: trang, kích thước trang và thứ tự

`Pageable` thuộc `org.springframework.data.domain`. Cách tạo thông dụng là `PageRequest.of(pageNumber, pageSize, sort)`:

```java
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);
```

Các tham số:

- `pageNumber`: số trang bắt đầu từ `0`, vì vậy `0` là trang đầu tiên.
- `pageSize`: số hàng tối đa của một trang.
- `sort`: thứ tự áp dụng cho dữ liệu của trang.

Với trang số `2` và kích thước `20`, offset là `2 × 20 = 40`. Truy vấn bỏ qua 40 hàng đầu tiên theo thứ tự đã sắp xếp, sau đó lấy tối đa 20 hàng.

`Pageable` không trực tiếp thực thi SQL. Nó chỉ mang thông tin phân trang và sắp xếp; template cần nhận thông tin đó qua `Query.with(pageable)` hoặc qua overload API phù hợp với phiên bản Spring Data JDBC.

## 7. Áp dụng `Pageable` lên `Query` bằng `with`

`Query.with(pageable)` kết hợp thông tin trang vào query. Theo API của Spring Data Relational, phương thức này thiết lập `offset`, `limit` và áp dụng `Sort` nằm trong `Pageable`.

```java
Criteria criteria = Criteria.where("status").is("OPEN");
Query baseQuery = Query.query(criteria);

Pageable pageable = PageRequest.of(
        1,
        10,
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);

Query pageQuery = baseQuery.with(pageable);
List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
```

Ở ví dụ này:

- `baseQuery` chỉ chứa điều kiện `status = OPEN`.
- `pageable` yêu cầu trang thứ hai (page number `1`), mỗi trang 10 hàng.
- `pageQuery` chứa điều kiện, sort, offset `10` và limit `10`.
- `findAll(pageQuery, PurchaseOrder.class)` trả danh sách tối đa 10 aggregate.

SQL có ý nghĩa tương đương:

```sql
SELECT ...
FROM purchase_orders
WHERE status = ?
ORDER BY created_at DESC, id ASC
OFFSET 10 ROWS FETCH NEXT 10 ROWS ONLY;
```

Cú pháp giới hạn hàng thực tế phụ thuộc dialect. Một số database dùng `LIMIT ... OFFSET ...`, một số dùng `OFFSET ... FETCH NEXT ...` hoặc cú pháp khác. `JdbcAggregateTemplate` và dialect chịu trách nhiệm tạo SQL tương ứng.

Khi dùng `Pageable` có `Sort`, không cần gọi thêm `query.sort(...)` với một thứ tự khác nếu không có chủ đích. Hãy đặt sort tại một nơi để tránh khó hiểu khi hai nguồn sắp xếp cùng xuất hiện.

## 8. Tạo `Page<T>` từ template trong API hiện hành

Một điểm cần chú ý về phiên bản: API `JdbcAggregateTemplate.findAll(Query, Class, Pageable)` từng trả về `Page<T>`, nhưng trong Spring Data Relational từ **4.0** đã bị đánh dấu deprecated để loại bỏ trong phiên bản tương lai. Lý do là việc kết hợp truy vấn dữ liệu với thông tin tổng số phần tử tạo ra trách nhiệm phân trang không phù hợp với template; phân trang là khả năng thường thuộc repository hơn.

API hiện hành cung cấp các thao tác:

- `findAll(Query, Class<T>)`: trả `List<T>` cho query đã có điều kiện/sort/limit/offset.
- `count(Query, Class<T>)`: đếm tổng số aggregate thỏa query.
- `Query.with(Pageable)`: chuyển page, size và sort thành thông tin truy vấn.

Vì vậy, để trả `Page<T>`, hãy chạy truy vấn lấy nội dung trang, chạy truy vấn đếm trên **query chưa áp dụng phân trang**, rồi tạo `PageImpl`:

```java
import java.util.List;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jdbc.core.JdbcAggregateTemplate;
import org.springframework.data.relational.core.query.Criteria;
import org.springframework.data.relational.core.query.Query;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PurchaseOrderSearchService {
    private final JdbcAggregateTemplate template;

    public PurchaseOrderSearchService(JdbcAggregateTemplate template) {
        this.template = template;
    }

    @Transactional(readOnly = true)
    public Page<PurchaseOrder> findOpenOrders(Pageable pageable) {
        Query baseQuery = Query.query(
                Criteria.where("status").is("OPEN")
        );

        Query pageQuery = baseQuery.with(pageable);
        List<PurchaseOrder> content = template.findAll(
                pageQuery,
                PurchaseOrder.class
        );

        long total = template.count(baseQuery, PurchaseOrder.class);

        return new PageImpl<>(content, pageable, total);
    }
}
```

`PageImpl` thuộc `org.springframework.data.domain`. Nó nhận nội dung trang, thông tin `Pageable` và tổng số phần tử. Kết quả có các thông tin như `getContent()`, `getNumber()`, `getSize()`, `getTotalElements()`, `getTotalPages()`, `hasNext()` và `hasPrevious()`.

### Vì sao phải giữ `baseQuery` riêng?

`baseQuery` đại diện tập dữ liệu cần tìm, ví dụ tất cả đơn `OPEN`. `pageQuery` chỉ là phiên bản của query đó có thêm offset, limit và sort cho trang hiện tại.

```java
Query baseQuery = Query.query(Criteria.where("status").is("OPEN"));
Query pageQuery = baseQuery.with(pageable);

List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
long total = template.count(baseQuery, PurchaseOrder.class);
```

Không nên dùng query đã phân trang cho phép đếm tổng:

```java
long total = template.count(pageQuery, PurchaseOrder.class); // Không phải tổng toàn bộ tập lọc
```

Mục tiêu của `Page.getTotalElements()` là tổng số đơn thỏa bộ lọc, không phải số hàng trong riêng trang hiện tại. Vì vậy, câu đếm dùng cùng điều kiện lọc nhưng không dùng giới hạn trang.

### Transaction và tính nhất quán giữa hai truy vấn

Tạo `Page` theo cách này thực hiện ít nhất hai truy vấn: một truy vấn lấy content và một truy vấn `COUNT`. Nếu dữ liệu thay đổi giữa hai lần thực thi, `content` và `total` có thể phản ánh hai thời điểm khác nhau. `@Transactional(readOnly = true)` gom các thao tác vào cùng transaction, nhưng mức độ nhìn thấy snapshot nhất quán còn phụ thuộc isolation level và database. Nếu nghiệp vụ cần snapshot nghiêm ngặt, hãy chọn isolation level phù hợp và đánh giá chi phí khóa/đồng thời.

## 9. Kết hợp bộ lọc động, sort và pageable

Một màn hình tìm kiếm thực tế thường có bộ lọc tùy chọn. Có thể xây dựng `Criteria` trước, sau đó kết hợp `Sort`/`Pageable`.

Ví dụ service nhận trạng thái và mức tổng tiền tối thiểu:

```java
@Transactional(readOnly = true)
public Page<PurchaseOrder> search(
        String status,
        BigDecimal minimumTotal,
        Pageable pageable
) {
    Criteria criteria = Criteria.where("status").is(status)
            .and("total").greaterThanOrEquals(minimumTotal);

    Query baseQuery = Query.query(criteria);
    List<PurchaseOrder> content = template.findAll(
            baseQuery.with(pageable),
            PurchaseOrder.class
    );
    long total = template.count(baseQuery, PurchaseOrder.class);

    return new PageImpl<>(content, pageable, total);
}
```

Nếu một bộ lọc thực sự tùy chọn, chỉ thêm predicate khi tham số có giá trị. Ví dụ:

```java
Criteria criteria = Criteria.empty();

if (status != null && !status.isBlank()) {
    criteria = criteria.and("status").is(status);
}

if (minimumTotal != null) {
    criteria = criteria.and("total").greaterThanOrEquals(minimumTotal);
}

Query baseQuery = Query.query(criteria);
```

`Criteria` và `Query` đều có phong cách API immutable. Mỗi lần gọi `and`, `or`, `sort`, `limit`, `offset` hoặc `with`, hãy gán kết quả mới trở lại biến. Với các phiên bản/API có giới hạn cụ thể cho `Criteria.empty()` khi ghép predicate đầu tiên, có thể xây dựng danh sách điều kiện rồi kết hợp bằng `Criteria.from(...)`; luôn đối chiếu chữ ký của phiên bản Spring Data Relational trong dự án.

Không nên tạo một query mới bằng cách nối tên cột hoặc giá trị request thành chuỗi SQL. `Criteria` giữ điều kiện ở dạng cấu trúc và giúp giá trị được bind qua JDBC.

## 10. Dùng `Sort` riêng khi không cần `Page`

Nếu use case chỉ cần một danh sách đã lọc và sắp xếp, không cần dựng `Page`:

```java
Query query = Query.query(
        Criteria.where("status").is("OPEN")
).sort(
        Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))
);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Hoặc nếu chỉ tải mọi aggregate theo thứ tự:

```java
List<PurchaseOrder> orders = template.findAll(
        PurchaseOrder.class,
        Sort.by(Sort.Order.asc("orderNumber"))
);
```

Không cần chạy `count` nếu caller không cần tổng số phần tử. Tránh thực hiện câu đếm tốn kém chỉ để trả một danh sách.

## 11. Dùng `limit` và `offset` trực tiếp trên `Query`

`Query` cũng cho phép thiết lập giới hạn và độ lệch mà không cần tạo `Pageable`:

```java
Sort sort = Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.asc("id")
);

Query query = Query.query(Criteria.where("status").is("OPEN"))
        .sort(sort)
        .limit(20)
        .offset(40);

List<PurchaseOrder> orders = template.findAll(query, PurchaseOrder.class);
```

Đây là cách lấy tối đa 20 hàng sau khi bỏ qua 40 hàng đầu theo thứ tự đã chọn. Nó hữu ích cho tác vụ nội bộ cần lấy theo lô hoặc khi caller chỉ cần một cửa sổ dữ liệu mà không cần đối tượng `Page`.

Khác biệt:

| API | Thông tin được biểu diễn | Kết quả |
|---|---|---|
| `Query.sort(sort)` | Thứ tự | Query được sắp xếp |
| `Query.limit(n)` | Số hàng tối đa | Query bị giới hạn |
| `Query.offset(n)` | Số hàng bỏ qua | Query bắt đầu từ vị trí sau offset |
| `Query.with(pageable)` | Sort + page size + page offset | Query có đầy đủ thông tin trang |
| `template.findAll(query, type)` | Thực thi query | `List<T>` |
| `template.count(query, type)` | Đếm tập hợp thỏa điều kiện | `long` |

## 12. Phân biệt `Page`, `Slice` và `List`

Khi thiết kế API tìm kiếm, cần xác định caller có thực sự cần tổng số phần tử hay không.

| Kiểu kết quả | Thông tin cung cấp | Chi phí thường gặp |
|---|---|---|
| `List<T>` | Nội dung các hàng đã đọc | Một truy vấn lấy dữ liệu |
| `Page<T>` | Nội dung, trang hiện tại, tổng số phần tử và tổng số trang | Thường cần truy vấn dữ liệu và thêm truy vấn count |
| `Slice<T>` | Nội dung và thông tin còn trang tiếp theo hay không | Có thể lấy thêm một hàng để xác định `hasNext`, không cần tổng count |

`JdbcAggregateTemplate.findAll(Query, Class)` trả `List`, không tự trả `Page` hoặc `Slice`. Nếu cần `Page`, hãy ghép `findAll` với `count` như phần trên. Nếu chỉ cần biết còn dữ liệu hay không, có thể lấy `pageSize + 1` hàng bằng `limit`, kiểm tra hàng thừa rồi trả một DTO/Slice được tạo ở tầng ứng dụng. Không cần chạy count nếu tổng số không được sử dụng.

Với repository method, Spring Data JDBC có hỗ trợ các kiểu phân trang phù hợp như `Pageable` và `Page` theo query method. Nếu use case chỉ là truy vấn repository thông thường, dùng khả năng phân trang của repository có thể ngắn gọn hơn việc tự ghép hai truy vấn ở template.

## 13. Vì sao overload nhận `Pageable` của template cần chú ý phiên bản?

Trong API hiện hành, các overload sau được đánh dấu deprecated từ Spring Data Relational 4.0 và dự kiến loại bỏ:

```java
template.findAll(PurchaseOrder.class, pageable);

template.findAll(query, PurchaseOrder.class, pageable);
```

Chúng từng trả `Page<T>` trực tiếp. Tài liệu API hiện hành khuyến nghị dùng:

```java
Query pageQuery = query.with(pageable);
List<PurchaseOrder> content = template.findAll(pageQuery, PurchaseOrder.class);
long total = template.count(query, PurchaseOrder.class);
Page<PurchaseOrder> page = new PageImpl<>(content, pageable, total);
```

Đoạn code trên tách rõ trách nhiệm: `Query` xác định dữ liệu trang, `count` xác định tổng số kết quả, còn `PageImpl` đóng gói metadata trang. Nếu dự án đang dùng Spring Data JDBC phiên bản cũ, chữ ký và trạng thái deprecated có thể khác; hãy xem Javadoc đúng phiên bản được khai báo trong build file trước khi áp dụng.

## 14. Giới hạn khi truy vấn theo aggregate

`JdbcAggregateTemplate` đọc aggregate root cùng các thành phần thuộc aggregate theo mapping của Spring Data JDBC. Một truy vấn trả nhiều root có thể kéo theo chi phí đọc collection/entity con, tùy mô hình.

Vì vậy:

- Không phân trang bằng cách lấy toàn bộ `findAll()` rồi dùng `subList`; hãy đẩy `limit`/`offset` xuống database qua `Query`.
- Đặt điều kiện trên property phù hợp với mapping; không giả định `Criteria` là công cụ viết JOIN tùy ý giữa các aggregate độc lập.
- Nếu cần báo cáo JOIN hoặc projection không phải aggregate đầy đủ, cân nhắc repository query, custom repository fragment, `JdbcTemplate` và DTO/RowMapper.
- Nếu collection con của một root rất lớn, phân trang root không đồng nghĩa phân trang từng child bên trong root.
- Nếu cần đọc một tập dữ liệu lớn theo luồng, xem xét `streamAll(Query, Class)` và quản lý vòng đời stream/transaction/resource phù hợp; không giữ stream mở lâu ngoài phạm vi transaction cần thiết.

`Query.columns(...)` có thể giới hạn các cột được chọn, nhưng khi mục tiêu là dựng một aggregate đầy đủ, cần bảo đảm các cột bắt buộc cho mapping được trả về. Projection một phần thường phù hợp hơn với DTO/read model chuyên biệt.

## 15. Hiệu năng của `Pageable`: offset pagination và thứ tự ổn định

Phân trang bằng `Pageable` thường được thực hiện bằng offset/limit. Cách này dễ hiểu và phù hợp với giao diện có số trang, nhưng offset lớn có thể khiến database phải bỏ qua nhiều hàng trước khi trả trang cần thiết.

Ví dụ trang 500 với kích thước 50 cần offset 24.950. Trên bảng lớn, việc bỏ qua hàng chục nghìn hàng có thể tốn chi phí tùy execution plan và index.

Để phân trang ổn định:

1. Luôn có `Sort` khi thứ tự hiển thị quan trọng.
2. Thêm khóa duy nhất làm tiêu chí cuối, ví dụ `id ASC`, để phá hòa khi các giá trị sort bằng nhau.
3. Tạo index phù hợp với điều kiện lọc và thứ tự sắp xếp nếu execution plan cho thấy cần thiết.
4. Giới hạn page size ở tầng API để tránh request kích thước quá lớn.
5. Với tập dữ liệu rất lớn hoặc trang sâu, cân nhắc keyset/seek pagination thay vì offset pagination.

Keyset pagination thường dùng giá trị cuối của trang trước làm điểm bắt đầu cho trang kế tiếp, ví dụ `(created_at, id) < (:lastCreatedAt, :lastId)` theo chiều sort giảm dần. Nó cần query và điều kiện cursor riêng; không nên giả định `PageRequest` tự chuyển thành keyset pagination.

## 16. Sắp xếp động an toàn

Một API có thể nhận `sortBy` và `direction` từ client. Không nên đưa trực tiếp tên property tùy ý vào query. Hãy ánh xạ các lựa chọn được cho phép:

```java
private Sort resolveSort(String sortBy, boolean descending) {
    String property = switch (sortBy) {
        case "created" -> "createdAt";
        case "amount" -> "total";
        case "number" -> "orderNumber";
        default -> "createdAt";
    };

    Sort.Direction direction = descending
            ? Sort.Direction.DESC
            : Sort.Direction.ASC;

    return Sort.by(
            new Sort.Order(direction, property),
            Sort.Order.asc("id")
    );
}
```

Sau đó:

```java
Pageable pageable = PageRequest.of(
        pageNumber,
        pageSize,
        resolveSort(sortBy, descending)
);
```

Đoạn code chỉ cho phép ba trường sort đã biết. Trong API thực tế, cũng cần kiểm tra `pageNumber >= 0`, giới hạn `pageSize` và xử lý tên sort không hợp lệ theo contract của ứng dụng.

## 17. Các lỗi thường gặp

| Triệu chứng | Nguyên nhân thường gặp | Hướng xử lý |
|---|---|---|
| `findAll(query, type)` trả quá nhiều hàng | Query chưa có limit/offset hoặc chưa áp dụng Pageable | Dùng `query.with(pageable)` hoặc `.limit().offset()` |
| Sort không có tác dụng | Không gán Query mới trả về từ `.sort()` hoặc Pageable không chứa Sort | Giữ kết quả fluent call và kiểm tra `pageable.getSort()` |
| Trang có hàng trùng hoặc đổi vị trí | Sort không có tiêu chí duy nhất khi nhiều giá trị bằng nhau | Thêm `id` làm tiêu chí phụ |
| `Page.getTotalElements()` chỉ bằng số hàng trong trang | Dùng query đã phân trang cho `count` | Đếm bằng `baseQuery` chưa có offset/limit |
| `Page` có content nhưng total không khớp | Hai truy vấn chạy ở thời điểm khác nhau khi dữ liệu đồng thời thay đổi | Xem xét transaction và isolation level |
| API báo trang rỗng dù tổng lớn | Page number vượt phạm vi hoặc offset tính sai | Nhớ page number bắt đầu từ 0 và kiểm tra size |
| Sort theo tên cột gây lỗi | Dùng identifier không được mapping phân giải | Dùng property hợp lệ của aggregate và kiểm tra metadata |
| Client có thể sort theo cột tùy ý | Truyền sort property không qua whitelist | Ánh xạ lựa chọn client sang danh sách property cho phép |
| Overload `findAll(..., Pageable)` có cảnh báo deprecated | Dự án dùng Spring Data Relational 4.0+ | Dùng `Query.with(pageable)`, `findAll(Query, Class)`, `count` và `PageImpl` |
| Query động có điều kiện sai | Nhóm Criteria `and`/`or` không đúng ý định | Viết rõ các nhóm và kiểm tra SQL tương đương |
| Phân trang sâu chậm | Offset lớn hoặc index không phù hợp | Đo execution plan, xem keyset pagination |

## 18. Bài thực hành: lọc, sắp xếp và phân trang đơn hàng

Với entity `PurchaseOrder` và bảng `purchase_orders` ở phần 2, hãy nạp dữ liệu có nhiều trạng thái và tổng tiền khác nhau. Sau đó thực hiện:

1. Dùng `Query.query(Criteria.where("status").is("OPEN"))` để chỉ lấy đơn đang mở.
2. Dùng `Sort.by(Sort.Order.desc("createdAt"), Sort.Order.asc("id"))` để sắp xếp theo thời điểm tạo mới nhất, sau đó theo ID.
3. Dùng `PageRequest.of(0, 10, sort)` để tạo trang đầu gồm tối đa 10 đơn.
4. Áp dụng `baseQuery.with(pageable)` và gọi `template.findAll(pageQuery, PurchaseOrder.class)`.
5. Gọi `template.count(baseQuery, PurchaseOrder.class)` để lấy tổng số đơn đang mở; dựng `PageImpl`.
6. Chuyển sang trang thứ hai (`PageRequest.of(1, 10, sort)`) và xác nhận offset là 10.
7. Thêm điều kiện `total >= 1000` vào Criteria và kiểm tra cả truy vấn nội dung lẫn truy vấn count cùng dùng điều kiện này.
8. Bỏ tiêu chí sort `id` phụ, tạo nhiều đơn có cùng `createdAt` và quan sát vì sao thứ tự trang có thể không ổn định.
9. Dùng `Query.limit(10).offset(20)` trực tiếp và so sánh với `Query.with(Pageable)`.
10. Bật log SQL trong môi trường phát triển để xem điều kiện `WHERE`, `ORDER BY`, `LIMIT/OFFSET` hoặc cú pháp phân trang mà dialect tạo ra.

Mục tiêu là hiểu sự phối hợp giữa điều kiện lọc, sort và page window, đồng thời thấy rõ `Page` cần thêm thông tin tổng số phần tử ngoài danh sách content.

## 19. Nguyên tắc ghi nhớ

- `Query` mô tả Criteria, cột, sort, limit và offset; nó là object immutable.
- `Criteria` xây dựng điều kiện `WHERE` bằng các predicate như `is`, `greaterThanOrEquals`, `between`, `in`, `isNull` và kết hợp `and`/`or`.
- `Sort` mô tả thứ tự theo một hoặc nhiều property; thêm tiêu chí duy nhất như `id` để có thứ tự ổn định.
- `Pageable` chứa page number (bắt đầu từ 0), page size và Sort.
- `Query.with(pageable)` áp dụng offset, limit và Sort lên một Query mới.
- `template.findAll(Query, Class)` trả `List<T>`; `template.count(Query, Class)` đếm các aggregate thỏa điều kiện.
- Để dựng `Page<T>` theo API hiện hành, giữ query gốc, lấy content bằng query đã áp dụng Pageable, đếm bằng query chưa phân trang và tạo `PageImpl`.
- Overload `JdbcAggregateTemplate.findAll(..., Pageable)` bị deprecated từ Spring Data Relational 4.0; kiểm tra Javadoc đúng phiên bản dự án.
- Nếu chỉ cần List, không cần chạy count; nếu cần Page metadata, phải tính total.
- Offset pagination có thể chậm ở trang sâu; xem xét keyset pagination khi quy mô dữ liệu yêu cầu.

Khi kết hợp `Query`, `Sort` và `Pageable` với `JdbcAggregateTemplate`, hãy tách rõ **điều kiện lọc**, **thứ tự**, **cửa sổ dữ liệu** và **tổng số kết quả**. `Query` mô tả truy vấn, `Sort` quyết định thứ tự, `Pageable` chuyển trang thành limit/offset, còn `count` cung cấp tổng để dựng `Page`. Cách phân chia này giúp truy vấn động dễ kiểm soát và tránh phụ thuộc vào overload phân trang đã deprecated trong các phiên bản Spring Data Relational mới.
