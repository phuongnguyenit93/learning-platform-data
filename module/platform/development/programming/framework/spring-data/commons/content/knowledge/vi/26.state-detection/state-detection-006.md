# ID tự gán, ID do cơ sở dữ liệu sinh và thứ tự gán giá trị

## 1. Có ID chưa chắc đã có bản ghi

Một object có thể được gán UUID ngay khi tạo trong ứng dụng nhưng chưa từng được ghi xuống database. Ngược lại, một object sau lần lưu thất bại có thể vẫn giữ ID mà database đã cấp trước khi transaction rollback.

Vì vậy, phải phân biệt ba câu hỏi:

1. Object đang có giá trị định danh nào?
2. Hạ tầng Spring Data đánh giá object là mới hay đã tồn tại bằng chiến lược nào?
3. Bản ghi tương ứng có thực sự tồn tại và đã được commit trong store hay chưa?

Ba câu trả lời không luôn giống nhau.

Trong Spring Data Commons, ID là metadata định danh. Chiến lược phát hiện trạng thái mới có thể xem ID, version hoặc `Persistable.isNew()`. Module store dùng kết quả đó trong đường thực thi của nó.

Mục tiêu của bài là thiết kế đúng thời điểm gán ID, tránh để việc cấp định danh vô tình làm thay đổi nhánh persistence.

## 2. Hai nhóm chiến lược cấp ID

| Chiến lược | Ai cấp ID? | Thời điểm thường gặp | Trạng thái object trước lần lưu |
| --- | --- | --- | --- |
| ID tự gán | Ứng dụng, client nội bộ hoặc dịch vụ cấp ID | Trước khi gọi repository | Có thể đã có ID |
| ID do store sinh | Database hoặc hạ tầng tích hợp với store | Khi cấp sequence, insert hoặc xử lý lưu theo cơ chế cụ thể | Thường chưa có ID tại thời điểm ban đầu |

Ví dụ ID tự gán:

```java
UUID id = UUID.randomUUID();
```

Ví dụ ID do database sinh:

```sql
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Đây là hai mô hình vòng đời khác nhau. Không nên chỉ đổi kiểu field từ `Long` sang `UUID` mà giữ nguyên mọi giả định về phát hiện trạng thái mới.

### @Id không tự tạo một cơ chế cấp ID chung

`org.springframework.data.annotation.Id` đánh dấu thuộc tính định danh trong mô hình mapping dùng annotation Commons.

Annotation đó không tự:

- Tạo sequence hoặc identity column.
- Sinh UUID trong constructor.
- Chọn cơ chế sinh khóa của mọi database.
- Biến mọi giá trị không null thành bằng chứng bản ghi đã tồn tại.

Trong JPA, annotation ID và cơ chế sinh khóa thuộc mô hình JPA, chẳng hạn `jakarta.persistence.Id` và `jakarta.persistence.GeneratedValue` trong môi trường Jakarta Persistence. Không thay import tùy ý bằng annotation Commons.

## 3. Chiến lược phát hiện trạng thái cần được xác định trước

Khi store sử dụng chiến lược metadata tương ứng của Commons, trạng thái mới thường được quyết định từ metadata của entity; không phải bằng một truy vấn tồn tại tự động cho mọi lần `save`.

Các cơ chế quan trọng gồm:

- Kiểm tra thuộc tính version khi chiến lược có sử dụng nó.
- Kiểm tra thuộc tính ID khi không có version phù hợp.
- Giao quyết định cho `Persistable.isNew()` khi entity và hạ tầng hỗ trợ cơ chế đó.
- Chiến lược tùy biến của module hoặc cấu hình repository.

### 3.1. Bảng ID khi đang dùng chiến lược chỉ xét ID

| Khai báo và giá trị | Kết luận dự kiến của chiến lược ID mặc định tương ứng |
| --- | --- |
| `Long id = null` | Mới |
| `Long id = 0L` | Không mới, vì wrapper đã có giá trị |
| `long id = 0` | Mới theo quy tắc numeric primitive bằng 0 |
| `long id = 12` | Không mới |
| `String id = null` | Mới |
| `String id = ""` | Không mới; chuỗi rỗng vẫn khác null |
| `UUID id = UUID.randomUUID()` | Không mới theo kiểm tra ID đơn thuần |

Bảng không có nghĩa chuỗi rỗng hoặc ID bằng 0 đều là khóa hợp lệ với database. Nó chỉ mô tả dấu hiệu mà chiến lược có thể sử dụng.

Một lỗi phổ biến là đổi `long` sang `Long` nhưng vẫn khởi tạo `0L`. Với kiểm tra ID dựa trên null, điều đó khác việc để ID chưa có giá trị.

### 3.2. Khi version được ưu tiên

Với chiến lược metadata dùng version dạng wrapper:

```java
@Version
private Long version;
```

có thể có các trường hợp:

| ID | Version | Kết luận theo chiến lược boxed-version đang xét |
| --- | --- | --- |
| UUID đã gán | null | Mới |
| UUID đã gán | 0L | Không mới |
| UUID đã gán | 5L | Không mới |
| null | 0L | Không mới theo version, nhưng model có thể không hợp lệ cho thao tác tiếp theo |

Version null có thể giúp biểu diễn object chưa được lưu dù ID đã được ứng dụng cấp.

Không khởi tạo version bằng `0L` chỉ vì cho rằng “phiên bản đầu tiên là 0”. Hạ tầng store có thể chịu trách nhiệm thiết lập giá trị ban đầu khi ghi. Giá trị đó phải được phân biệt với trạng thái chưa được lưu.

### 3.3. Không áp dụng nguyên xi quy tắc primitive version cho mọi module

Trong một số chiến lược Commons, numeric primitive bằng 0 có thể được dùng để nhận diện trạng thái mới.

Spring Data JPA lại không sử dụng primitive version giống boxed version cho mục đích này, vì giá trị 0 có thể là phiên bản hợp lệ của entity đã được ghi. Khi không có version phù hợp, chiến lược mặc định của JPA sẽ dựa vào ID.

Do đó, nếu mục tiêu là dùng version để phân biệt “chưa được lưu” và “đã được lưu”, cần chọn kiểu và annotation đúng theo module, đồng thời kiểm tra hành vi của phiên bản thực tế.

Không thêm version chỉ như một mẹo tránh nhánh update. Version còn thể hiện hợp đồng optimistic locking mà ứng dụng phải duy trì.

## 4. ID tự gán: gán trước save làm thay đổi đầu vào của isNew

Xét model đơn giản:

```java
import org.springframework.data.annotation.Id;

import java.util.UUID;

public record AssignedOrder(
        @Id UUID id,
        String reference) {
}
```

Ứng dụng tạo:

```java
AssignedOrder order =
        new AssignedOrder(
                UUID.randomUUID(),
                "PO-2026-001");
```

Object này mới về mặt nghiệp vụ. Nhưng nếu hạ tầng chỉ kiểm tra ID, ID đã khác null nên kết luận có thể là không mới.

Điều đó không nhất thiết gây cùng một lỗi ở mọi store:

- JPA có thể đi qua `merge`, rồi provider vẫn có khả năng thực hiện insert tùy tình huống.
- JDBC/R2DBC có thể chọn nhánh update và không tìm thấy bản ghi để cập nhật.
- MongoDB có thể đi qua đường save có hành vi upsert hoặc replacement trong trường hợp phù hợp.

Thiết kế đúng phải dựa trên hành vi mong muốn của store, không dựa vào việc thử một lần thấy `save` “vẫn chạy”.

### Các lựa chọn xử lý

| Nhu cầu | Lựa chọn có thể phù hợp |
| --- | --- |
| ID do ứng dụng cấp và cần optimistic locking | Version nullable được module hỗ trợ |
| Cần tự biểu diễn trạng thái mới | `Persistable` với vòng đời cờ trạng thái rõ ràng |
| Nghiệp vụ là tạo mới, phải lỗi nếu đã tồn tại | API insert tường minh của store khi có |
| Cần upsert theo khóa xác định | API hoặc câu lệnh có hợp đồng upsert cụ thể |
| Muốn database tự cấp ID | Giữ ID chưa có giá trị đến đúng bước cấp khóa |

`CrudRepository` không có một method `insert` chung cho mọi store. Nếu cần thao tác này, phải dùng API module phù hợp hoặc thiết kế repository fragment có hợp đồng rõ ràng.

## 5. ID tự gán kết hợp nullable version

Ví dụ metadata Commons cho module hỗ trợ mô hình này:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;

import java.util.UUID;

public record VersionedOrder(
        @Id UUID id,
        @Version Long version,
        String reference) {

    public static VersionedOrder create(String reference) {
        return new VersionedOrder(
                UUID.randomUUID(),
                null,
                reference);
    }

    public VersionedOrder withId(UUID newId) {
        return new VersionedOrder(
                newId,
                version,
                reference);
    }

    public VersionedOrder withVersion(Long newVersion) {
        return new VersionedOrder(
                id,
                newVersion,
                reference);
    }

    public VersionedOrder rename(String newReference) {
        return new VersionedOrder(
                id,
                version,
                newReference);
    }
}
```

Trình tự mong muốn khi module hỗ trợ version-based state detection và cập nhật immutable:

```text
Tạo UUID
    → tạo object có version null
    → phát hiện mới dựa trên version
    → thực hiện ghi mới
    → nhận version khởi tạo
    → sử dụng object trả về sau lưu
```

Lần sửa tiếp theo phải giữ version hiện tại:

```java
VersionedOrder changed = saved.rename("PO-2026-001-REV1");
VersionedOrder updated = repository.save(changed);
```

Đoạn sử dụng giả định repository đã được cấu hình với module hỗ trợ model và kiểu UUID tương ứng.

### Lỗi làm mất version

Một implementation sai có thể làm như sau:

```java
public VersionedOrder rename(String newReference) {
    return new VersionedOrder(
            id,
            null,
            newReference);
}
```

Bản sao vẫn có cùng ID nhưng version trở về null. Hạ tầng có thể nhận nhầm đây là object mới và thử insert.

Cũng cần kiểm tra khi nhận request cập nhật: không dựng entity mới chỉ từ ID và dữ liệu request rồi bỏ qua version hoặc trạng thái đã được đọc.

Việc nạp entity hiện tại, áp dụng thay đổi và giữ metadata là một lựa chọn phù hợp trong nhiều nghiệp vụ. Nếu dùng API cập nhật với version do client gửi, phải định nghĩa rõ hợp đồng kiểm tra xung đột.

## 6. Persistable: tách trạng thái mới khỏi giá trị ID

`Persistable<ID>` cho phép entity cung cấp:

```java
ID getId();
boolean isNew();
```

Điểm chính là ID đã có không bắt buộc kéo theo `isNew() == false`.

Tuy nhiên, cờ trạng thái phải chuyển đúng khi nạp hoặc persist. Một cờ luôn trả true sẽ làm các lần lưu sau tiếp tục bị xem là tạo mới.

### 6.1. Ví dụ vòng đời riêng cho JPA

Đây là ví dụ JPA với ID UUID tự gán; không phải mẫu callback dùng chung cho JDBC hoặc MongoDB:

```java
package com.example.order;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.PostLoad;
import jakarta.persistence.PostPersist;
import jakarta.persistence.Table;
import jakarta.persistence.Transient;

import org.springframework.data.domain.Persistable;

import java.util.Objects;
import java.util.UUID;

@Entity
@Table(name = "assigned_order")
public class AssignedJpaOrder implements Persistable<UUID> {

    @Id
    private UUID id;

    private String reference;

    @Transient
    private boolean newEntity = true;

    protected AssignedJpaOrder() {
    }

    public AssignedJpaOrder(UUID id, String reference) {
        this.id = Objects.requireNonNull(id, "id");
        this.reference = Objects.requireNonNull(
                reference,
                "reference");
    }

    public static AssignedJpaOrder create(String reference) {
        return new AssignedJpaOrder(
                UUID.randomUUID(),
                reference);
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public String getReference() {
        return reference;
    }

    public void rename(String reference) {
        this.reference = Objects.requireNonNull(
                reference,
                "reference");
    }

    @PostLoad
    @PostPersist
    void markNotNew() {
        this.newEntity = false;
    }
}
```

Trong ví dụ:

- ID được cấp trước `save`.
- Entity mới vẫn báo `isNew() == true`.
- Sau callback persist hoặc load, entity báo không mới.
- Cờ là transient của JPA, không phải một cột nghiệp vụ.
- Không dùng `@GeneratedValue` cho trường ID tự gán này.

Ứng dụng dùng namespace JPA cũ cần chọn import tương ứng với dependency của nó.

### 6.2. Callback không phải commit thành công

`@PostPersist` không đồng nghĩa transaction đã commit. Sau khi callback chạy, transaction vẫn có thể rollback.

Object Java có thể còn:

- ID đã gán.
- `newEntity == false`.
- Trạng thái không phản ánh dữ liệu đã commit.

Không tái sử dụng mù quáng instance từ transaction thất bại cho một lần retry. Cần tái tạo hoặc nạp lại trạng thái theo chính sách retry của ứng dụng.

Tương tự, nếu object được deserialize từ request, không nên coi một cờ `isNew` do request cung cấp là nguồn sự thật. Trạng thái persistence phải do luồng ứng dụng và store quản lý.

### 6.3. Với module khác

Callback JPA không tự chạy trong Spring Data JDBC hoặc MongoDB.

Khi dùng `Persistable` với module khác, cần kiểm tra:

- Repository có giao quyết định cho `isNew` không?
- Làm sao đánh dấu instance đọc từ store là không mới?
- Làm sao chuyển trạng thái sau khi ghi?
- Nếu model immutable, callback có thể trả instance mới theo cơ chế nào?
- Cờ kỹ thuật có bị mapping thành dữ liệu ngoài ý muốn không?

Không sao chép `@PostLoad` sang một model không do JPA quản lý rồi kỳ vọng cờ tự thay đổi.

## 7. ID do database sinh: để trống đến bước cấp khóa phù hợp

Ví dụ Spring Data JDBC với PostgreSQL:

```sql
CREATE TABLE purchase_order (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    reference varchar(100) NOT NULL
);
```

Model minh họa cho phiên bản hỗ trợ record mapping:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.relational.core.mapping.Table;

@Table("purchase_order")
public record GeneratedOrder(
        @Id Long id,
        String reference) {

    public GeneratedOrder {
        if (reference == null || reference.isBlank()) {
            throw new IllegalArgumentException(
                    "reference must not be blank");
        }
    }

    public GeneratedOrder withId(Long newId) {
        return new GeneratedOrder(newId, reference);
    }
}
```

Repository:

```java
import org.springframework.data.repository.CrudRepository;

public interface GeneratedOrderRepository
        extends CrudRepository<GeneratedOrder, Long> {
}
```

Sử dụng:

```java
GeneratedOrder draft =
        new GeneratedOrder(null, "PO-2026-002");

GeneratedOrder saved = repository.save(draft);

Long generatedId = saved.id();
```

Trình tự JDBC điển hình trong cấu hình này:

```text
ID null
    → hạ tầng chọn nhánh tạo mới
    → INSERT không gán ID chưa có
    → database sinh ID
    → hạ tầng nhận generated key
    → cập nhật hoặc tạo bản sao entity có ID
    → trả kết quả save
```

Không thay ID null bằng `0L` để biểu diễn “chưa có”, nếu chiến lược đang xét wrapper khác null là không mới.

### Dùng instance trả về

Với model immutable, đừng kỳ vọng object `draft` nhận ID tại chỗ:

```java
// Không dùng làm cách lấy ID sau lưu.
repository.save(draft);
Long id = draft.id();
```

Hãy giữ object trả về. Quy tắc này cũng hữu ích với JPA merge, nơi instance trả về có thể khác instance đầu vào.

### Không tự tính ID tiếp theo

Không lấy `max(id) + 1` trong ứng dụng để mô phỏng identity hoặc sequence. Hai transaction có thể tính cùng một giá trị.

Nếu cần ID tự gán, dùng cơ chế cấp định danh được thiết kế cho đồng thời. Nếu chọn database-generated ID, để database thực hiện đúng cơ chế đã cấu hình.

## 8. Generated ID có thể xuất hiện trước khi bản ghi được commit

Không có một thời điểm cấp ID chung cho mọi công nghệ.

| Cơ chế | Điều cần hiểu |
| --- | --- |
| Sequence | Giá trị có thể được cấp trước câu insert tương ứng |
| Identity | Thường gắn với việc thực hiện insert để nhận khóa, theo database/provider |
| UUID phía ứng dụng hoặc provider | Có thể có trước khi gửi câu ghi |
| Khóa trả về sau insert | Cần đường nhận generated key tương thích driver và module |

Với JPA:

```text
save
    → persist hoặc merge theo trạng thái
    → provider quản lý thao tác và cấp ID theo strategy
    → flush khi phù hợp
    → commit transaction
```

Không suy ra rằng mọi `save` đều gửi SQL ngay. Cũng không coi `flush` là commit.

Một object có ID sau `save` có thể vẫn nằm trong transaction chưa commit. Nếu transaction rollback, ID trong bộ nhớ không trở về null một cách bảo đảm.

Khoảng trống trong sequence hoặc identity sau rollback thường không phải lỗi phát hiện trạng thái. Không dùng tính liên tiếp của ID làm bằng chứng không có transaction thất bại.

### Khi nào có thể dùng ID?

ID có thể được dùng làm định danh trong luồng xử lý sau khi được cấp. Nhưng việc công bố một sự kiện “đã tạo thành công” còn phải gắn với quy tắc transaction của ứng dụng.

Đừng để sự hiện diện của ID thay thế kiểm tra kết quả ghi hoặc commit.

## 9. Thứ tự gán ID so với điểm quyết định isNew

Gọi **D** là thời điểm hạ tầng ra quyết định mới/không mới.

Hai trình tự sau khác nhau:

```text
A. Gán ID → D → ghi
B. D → gán ID → ghi
```

Với chiến lược chỉ xét ID:

- Ở A, ID tự gán có thể khiến object bị xem là không mới.
- Ở B, quyết định có thể đã là mới trước khi ID được gán.
- Gán ID sau D không có nghĩa framework chắc chắn tính lại quyết định.

### 9.1. Callback nằm ở đâu?

Tên callback như `BeforeConvert` mô tả quan hệ với bước conversion, không tự mô tả quan hệ với mọi quyết định của repository.

Tùy module và API:

- Repository có thể đã chọn insert/update trước khi đi vào callback.
- Template có thể có pipeline khác.
- Đường save có version có thể khác đường không version.
- Custom fragment có thể chủ động chọn thao tác.

Vì vậy, không đưa ra quy tắc chung “cứ gán UUID trong BeforeConvert là luôn đúng”.

Phải xác định thứ tự của đúng module, phiên bản và đường API đang gọi. Một integration test quan sát số lần insert/update hoặc dữ liệu cuối cùng là cách xác nhận quan trọng.

### 9.2. Cần kiểm tra cả lần lưu thứ hai

Một thiết kế có thể tạo mới thành công nhưng thất bại ở lần cập nhật:

```text
Lần đầu:
isNew true → cấp ID → insert thành công

Lần sau:
Cờ chưa đổi hoặc version bị mất → isNew vẫn true
    → tiếp tục insert
    → trùng khóa hoặc sai hành vi
```

Do đó, test gán ID không được dừng ở việc “ID đã khác null”. Cần lưu lại và đọc lại đối tượng theo vòng đời dự kiến.

### 9.3. Cách tránh phụ thuộc thứ tự ngầm

Có thể ưu tiên:

- Một factory tạo mới cấp ID và để version null trong mô hình có version phù hợp.
- `Persistable` với trạng thái được quản lý rõ.
- API insert tường minh cho lệnh tạo mới.
- Một điểm cấp ID được module hỗ trợ và đã kiểm chứng.

Không tạo nhiều lớp cùng sinh ID: constructor, callback và service đều sinh UUID có thể khiến định danh thay đổi qua từng giai đoạn.

## 10. Ý nghĩa của save khác nhau giữa các module

| Module | Khi được xem là mới | Khi được xem là không mới | Điểm cần tránh suy rộng |
| --- | --- | --- | --- |
| Spring Data JPA | Repository dùng `persist` | Repository dùng `merge` | Merge không có nghĩa chắc chắn chỉ phát sinh SQL update |
| Spring Data JDBC | Đường lưu aggregate mới thực hiện insert | Đường lưu aggregate đã tồn tại thực hiện update | Không coi update thiếu bản ghi là upsert mặc định |
| Spring Data R2DBC | Đường repository tương ứng chọn insert | Đường repository tương ứng chọn update | Không suy cơ chế upsert từ tên save |
| Spring Data MongoDB | Repository có thể chọn insert | Đi qua đường save của template | Save không version có thể upsert/replacement; versioned save có kiểm tra riêng |

Bảng trình bày hướng hành vi của các đường repository thông thường. Custom repository, native query hoặc cấu hình đặc biệt cần được đánh giá riêng.

### JPA merge có thể che việc nhận diện sai

Một entity có ID tự gán và bị xem là không mới có thể vẫn được insert qua merge sau khi provider xác định chưa có dữ liệu phù hợp.

Điều đó không chứng minh chiến lược trạng thái đã đúng với chủ đích. Có thể xuất hiện thêm truy vấn, khác biệt về instance managed hoặc khác biệt vòng đời.

Nếu nghiệp vụ là “chỉ tạo mới”, phải kiểm tra rõ kết quả khi ID đã tồn tại thay vì chỉ quan sát lần chạy đầu.

### MongoDB upsert không phải bằng chứng ID mới

Một thao tác save có thể tạo document dù object bị xem là không mới, nhưng cùng đường đó có thể thay thế dữ liệu khi ID đã tồn tại.

Nếu yêu cầu là phát hiện trùng ID, chọn thao tác có hợp đồng phù hợp và kiểm chứng duplicate key. Không dùng upsert như một cách ngầm che mọi vấn đề state detection.

## 11. Retry, rollback và idempotency

### 11.1. Retry sau lỗi không chỉ là gọi lại save

Sau lỗi, cần phân biệt:

- Ghi chắc chắn chưa xảy ra.
- Ghi đã commit nhưng client không nhận được kết quả.
- Transaction đã rollback.
- Kết quả chưa xác định do lỗi mạng hoặc timeout.

Object giữ ID không đủ để phân biệt các trường hợp này.

Một lần retry insert với cùng ID có thể gặp trùng khóa. Một lần retry update với version cũ có thể gặp xung đột. Đổi sang UUID mới có thể tạo hai bản ghi cho cùng một yêu cầu nghiệp vụ.

### 11.2. ID tự gán hỗ trợ tương quan, không tự bảo đảm idempotency

Một ID ổn định có thể giúp nhận diện yêu cầu lặp, nhưng vẫn cần quy tắc:

- ID hoặc idempotency key có unique constraint phù hợp.
- Payload lặp có được yêu cầu giống lần đầu không?
- Khi đã tồn tại, trả kết quả cũ hay báo xung đột?
- Nếu ID tự gán trùng với nghiệp vụ khác, xử lý thế nào?

Không coi `isNew` là cơ chế chống race condition. Hai request có thể cùng đánh giá mới trước khi một request ghi thành công.

### 11.3. Không reset ID để che mọi lỗi

Xóa ID hoặc version rồi gọi lại `save` có thể chuyển từ cập nhật sang tạo mới và làm phát sinh bản ghi ngoài ý muốn.

Khi transaction thất bại, lựa chọn thường cần dựa trên command nghiệp vụ và dữ liệu authoritative: tái tạo object mới đúng nghĩa hoặc đọc lại trạng thái cần cập nhật.

Không duy trì một instance qua nhiều lần retry nếu metadata trong bộ nhớ đã không còn đáng tin.

## 12. Kịch bản kiểm chứng thiết kế ID

### 12.1. ID do database sinh

1. Tạo object có ID null.
2. Lưu và giữ instance trả về.
3. Kiểm tra ID được cấp theo hợp đồng module.
4. Đọc lại bản ghi.
5. Thay đổi dữ liệu và lưu lần hai.
6. Xác nhận vẫn là cùng định danh và không tạo thêm bản ghi ngoài ý muốn.
7. Kiểm tra tình huống rollback theo chiến lược transaction thực tế.

Không chỉ assert object đã có ID.

### 12.2. ID tự gán với version nullable

1. Cấp ID trước khi lưu.
2. Giữ version null khi tạo mới.
3. Xác nhận lần đầu thực hiện đường tạo mới phù hợp.
4. Giữ version do persistence trả về.
5. Tạo bản sao thay đổi nghiệp vụ mà không làm mất ID/version.
6. Lưu lần hai và xác nhận cập nhật đúng bản ghi.
7. Thử hai instance cùng version để kiểm tra optimistic locking.

Thêm một fixture có ID nhưng thiếu version nếu dữ liệu lịch sử có tình trạng này. Không mặc định dữ liệu đó sẽ được nhận diện là đã tồn tại.

### 12.3. Persistable

1. Factory tạo mới trả `isNew() == true`.
2. Lưu lần đầu có hành vi tạo mới.
3. Callback hoặc đường chuyển trạng thái đưa object sang không mới.
4. Object đọc lại báo không mới.
5. Lần lưu sau không tiếp tục đi vào insert.
6. Kiểm tra rollback và việc tái sử dụng instance.

Cần xác minh callback của đúng module, không chỉ gọi method đánh dấu bằng tay rồi kết luận lifecycle đã hoạt động.

### 12.4. Gán ID trong callback

Ghi nhận tại các điểm có thể quan sát:

```text
Object trước repository
Trạng thái được xác định
Object trước conversion/ghi theo pipeline
Dữ liệu thực thi
Object trả về
Object sau khi đọc lại
```

Test phải chứng minh callback không bị chạy theo cách làm đổi ID đã ổn định và không vô tình thay nhánh ghi. Không chỉ đếm số lần callback được gọi.

## 13. Lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Cách kiểm tra |
| --- | --- | --- |
| Lần save đầu chọn update dù object mới | ID đã được gán, không có chiến lược mới phù hợp | Xác định input của isNew tại điểm quyết định |
| Entity mới dùng version wrapper nhưng vẫn không được xem là mới | Version bị khởi tạo bằng 0L | Kiểm tra factory, builder và giá trị mặc định |
| Cập nhật lại thành insert | Bản sao mất version hoặc Persistable luôn true | Kiểm tra method copy và chuyển trạng thái |
| ID null trong biến đầu vào sau lưu | Model immutable hoặc persistence trả instance khác | Dùng kết quả save |
| JPA phát sinh select trước insert | Entity có ID đi qua merge trong tình huống cụ thể | Kiểm tra state detection và SQL/provider |
| MongoDB tạo mới được nhưng ghi đè khi trùng ID | Đang dựa vào save/upsert thay vì insert-only | Kiểm tra hợp đồng thao tác |
| Callback cấp UUID nhưng vẫn chọn sai nhánh | Thứ tự callback và quyết định khác giả định | Kiểm tra pipeline thực tế |
| Cờ kỹ thuật xuất hiện trong dữ liệu | Thuộc tính isNew chưa được loại khỏi mapping phù hợp | Kiểm tra annotation đúng store và access strategy |
| Sau rollback object vẫn có ID | ID được cấp trước commit và bộ nhớ không được reset | Tái tạo hoặc nạp lại theo chính sách retry |
| Hai request cùng tạo dẫn tới trùng khóa | isNew không phải kiểm tra tồn tại nguyên tử | Dùng ràng buộc store và xử lý xung đột |
| ID tự gán bị thay bằng giá trị khác | Nhiều điểm sinh ID hoặc cấu hình generator không thống nhất | Chọn một chính sách cấp ID rõ ràng |

## 14. Bài thực hành

Thiết kế hai model đơn hàng cho một module store đã chọn:

- Model A dùng ID do database cấp.
- Model B dùng UUID tự gán và cơ chế trạng thái mới phù hợp.

Với mỗi model, mô tả:

1. Ai cấp ID?
2. Giá trị ID trước lần save đầu?
3. Chiến lược nào quyết định mới/không mới?
4. ID được gán trước hay sau điểm quyết định?
5. Metadata nào thay đổi sau ghi?
6. Code lấy instance mới từ đâu?
7. Lần lưu thứ hai đi qua hành vi nào?
8. Khi rollback hoặc timeout, retry dựa trên thông tin gì?

Sau đó thực hiện các kịch bản tạo mới, cập nhật, ID trùng, version cũ nếu có và đọc lại.

Tiêu chí hoàn thành là giải thích được toàn bộ vòng đời, không chỉ tạo ra một giá trị ID. ID định danh object; chiến lược trạng thái quyết định cách repository xử lý; database và transaction xác định dữ liệu đã thực sự tồn tại hay chưa.
