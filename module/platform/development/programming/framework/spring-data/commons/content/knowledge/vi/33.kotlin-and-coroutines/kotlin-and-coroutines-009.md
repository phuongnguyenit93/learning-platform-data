# Kiểm thử tương thích khi cùng dùng entity Java và Kotlin

## 1. Cùng chạy trên JVM chưa đủ để bảo đảm tương thích dữ liệu

Trong chương **Kotlin và coroutine** của module **SPRING_DATA_COMMONS**, một ứng dụng có thể đồng thời chứa entity Java, entity Kotlin, repository reactive và các service coroutine. Những thành phần này có thể dùng chung các abstraction của Spring Data, nhưng không tự có cùng cách khởi tạo object, biểu diễn null hoặc so sánh giá trị.

Ví dụ, một Java entity có constructor không đối số và setter có thể đọc dữ liệu theo đường khác với một Kotlin data class dùng primary constructor và các property `val`.

Kiểm thử tương thích cần trả lời các câu hỏi cụ thể:

- Dữ liệu Java ghi có được Kotlin đọc đúng không?
- Dữ liệu Kotlin ghi có được Java đọc đúng không?
- Cả hai phía có nhận cùng ID, version và trạng thái nghiệp vụ không?
- Query, sort, count và projection có giữ cùng ý nghĩa không?
- Null, field thiếu và dữ liệu cũ được xử lý có đúng hợp đồng không?
- Khi chuyển đường gọi sang coroutine, lỗi và transaction có còn được hiểu đúng không?

Mục tiêu không phải làm hai class giống nhau về mọi chi tiết. Mục tiêu là chứng minh các đường đọc/ghi đang cùng tuân thủ hợp đồng dữ liệu mà ứng dụng cần.

## 2. Xác định dạng “cùng dùng” trước khi viết test

| Tình huống | Điều cần kiểm chứng |
| --- | --- |
| Các entity Java và Kotlin thuộc các bảng hoặc collection khác nhau | Mỗi mapping chạy đúng và các quan hệ/tham chiếu liên quan tương thích |
| Hai model Java và Kotlin cùng biểu diễn một schema | Đọc/ghi chéo không làm sai hoặc mất dữ liệu |
| Chuyển một entity Java sang Kotlin | Dữ liệu cũ vẫn đọc được, dữ liệu mới vẫn phù hợp với các phiên bản ứng dụng còn hoạt động |
| Java repository được gọi từ Kotlin | Nullability, getter/setter và kiểu generic được hiểu đúng tại điểm gọi |
| Entity Kotlin đi qua repository reactive/coroutine | Materialization, kết quả lưu, lỗi và vòng đời thực thi phù hợp |

Hai class cùng tồn tại trong một application context chưa chứng minh được khả năng đọc/ghi chéo. Một test chỉ lưu rồi đọc lại bằng chính repository vừa ghi cũng chưa bao phủ phía ngôn ngữ còn lại.

### 2.1. So sánh hợp đồng dữ liệu, không so trực tiếp hai entity khác kiểu

Không nên dùng:

~~~kotlin
// Không phải tiêu chí tương thích hợp lý giữa hai kiểu entity.
assertEquals(javaEntity, kotlinEntity)
~~~

Java class có thể dùng identity equality; Kotlin data class thường có equality dựa trên property của primary constructor. Hai object còn có thể khác class dù biểu diễn cùng một row.

Hãy so sánh một snapshot có chủ đích gồm ID, dữ liệu nghiệp vụ và metadata persistence cần thiết. Khi cần kiểm chứng mapping, đối chiếu thêm dữ liệu nguồn trong store.

## 3. Giữ persistence stack ổn định khi đánh giá khác biệt ngôn ngữ

Nếu Java dùng JPA còn Kotlin dùng R2DBC, một khác biệt quan sát được có thể đến từ provider, transaction, converter hoặc driver, không chỉ từ ngôn ngữ.

Để kiểm tra việc đổi model Java sang Kotlin, nên có một bộ test giữ nguyên:

- Loại store và schema.
- Module Spring Data và đường mapping.
- Các converter liên quan.
- Quy tắc ID, version và auditing.
- Bộ dữ liệu đầu vào.

Sau đó mới mở rộng sang các stack khác nếu ứng dụng thực sự sử dụng chúng.

Ví dụ chính trong bài chọn **Spring Data R2DBC** với hai kiểu entity cùng map một bảng SQL. Đây không phải một hướng dẫn khai báo hai JPA entity trùng mapping và cũng không phải một lời bảo đảm cho mọi module.

## 4. Ví dụ schema dùng chung

Một schema test theo dialect có cú pháp tương ứng:

~~~sql
CREATE TABLE catalog_product (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(120) NOT NULL,
    stock INTEGER NOT NULL,
    version BIGINT
);
~~~

Cú pháp tạo ID phải được điều chỉnh cho database được chọn. Không suy rằng cùng một DDL chạy nguyên vẹn trên mọi backend.

Trong ví dụ:

- ID chưa được cấp được biểu diễn bằng null ở cả hai model.
- Stock là dữ liệu bắt buộc, không dựa vào fallback để che dữ liệu thiếu.
- Version dùng kiểu số nullable ở cả hai phía.
- Tên column `display_name` được khai báo rõ để tránh phụ thuộc một giả định về tên property.

Schema cần được khởi tạo trong database test cô lập trước khi chạy các đoạn kiểm thử phía sau.

## 5. Model Java và Kotlin cùng một hợp đồng

### 5.1. Java entity dùng constructor rỗng và accessor

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Column;
import org.springframework.data.relational.core.mapping.Table;

@Table("catalog_product")
public class JavaProduct {

    @Id
    private Long id;

    @Column("display_name")
    private String displayName;

    private int stock;

    @Version
    private Long version;

    public JavaProduct() {
    }

    public JavaProduct(String displayName, int stock) {
        this.displayName = displayName;
        this.stock = stock;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getDisplayName() {
        return displayName;
    }

    public void setDisplayName(String displayName) {
        this.displayName = displayName;
    }

    public int getStock() {
        return stock;
    }

    public void setStock(int stock) {
        this.stock = stock;
    }

    public Long getVersion() {
        return version;
    }

    public void setVersion(Long version) {
        this.version = version;
    }
}
~~~

### 5.2. Kotlin entity dùng primary constructor

~~~kotlin
import org.springframework.data.annotation.Id
import org.springframework.data.annotation.Version
import org.springframework.data.relational.core.mapping.Column
import org.springframework.data.relational.core.mapping.Table

@Table("catalog_product")
data class KotlinProduct(
    @field:Id val id: Long? = null,
    @field:Column("display_name") val displayName: String,
    val stock: Int,
    @field:Version val version: Long? = null
)
~~~

Các annotation ở đây thuộc Spring Data và relational mapping, không phải annotation JPA từ `jakarta.persistence`.

`@field:` chỉ rõ use-site của annotation trên Kotlin property. Việc chỉ rõ vị trí giúp người đọc thấy annotation dự định áp vào field nào; không nên cho rằng mọi annotation đều có cùng target hoặc cùng quy tắc nhận diện.

`displayName` và `stock` không có default trong Kotlin model. Nếu query không cung cấp đủ dữ liệu bắt buộc để tạo entity, test cần phát hiện thay vì để một giá trị giả làm kết quả trông hợp lệ.

### 5.3. Repository của hai model

~~~java
import org.springframework.data.domain.Sort;
import org.springframework.data.r2dbc.repository.R2dbcRepository;

import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

public interface JavaProductRepository
        extends R2dbcRepository<JavaProduct, Long> {

    Flux<JavaProduct> findByDisplayName(
            String displayName, Sort sort);

    Mono<Long> countByDisplayName(String displayName);

~~~

~~~kotlin
import org.springframework.data.domain.Sort
import org.springframework.data.r2dbc.repository.R2dbcRepository
import reactor.core.publisher.Flux

interface KotlinProductRepository :
~~~

Hai repository cố ý dùng cùng mô hình reactive để trước hết tập trung kiểm tra entity mapping. Việc chuyển một API sang `CoroutineCrudRepository` có thể được kiểm chứng ở một lớp test khác, trong module hỗ trợ.

## 6. Kiểm thử tích hợp đọc/ghi chéo

Ví dụ sau dùng JUnit 5, Kotlin test assertion, `runTest` và các adapter Reactor/coroutine. Import test slice minh họa theo Spring Boot 3; dự án dùng cấu trúc package khác cần chọn annotation tương ứng.

Các class/entity/repository được đặt đúng vị trí quét của ứng dụng test. Database test phải được cấu hình và có bảng như trên. Đoạn code là tài liệu kiểm thử minh họa, không phải báo cáo đã chạy test.

### 6.1. Snapshot chung và fixture

~~~kotlin
import kotlinx.coroutines.reactor.awaitSingle
import kotlinx.coroutines.test.runTest
import org.junit.jupiter.api.BeforeEach
import org.junit.jupiter.api.Test
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.boot.test.autoconfigure.data.r2dbc.DataR2dbcTest
import org.springframework.dao.OptimisticLockingFailureException
import org.springframework.r2dbc.core.DatabaseClient
import kotlin.test.assertEquals
import kotlin.test.assertFailsWith
import kotlin.test.assertNotNull

data class ProductSnapshot(
    val id: Long,
    val displayName: String,
    val stock: Int,
    val version: Long?
)

@DataR2dbcTest
class ProductCompatibilityTest @Autowired constructor(
    private val javaProducts: JavaProductRepository,
    private val kotlinProducts: KotlinProductRepository,
    private val databaseClient: DatabaseClient
) {

    @BeforeEach
    fun clearTestData() = runTest {
        databaseClient.sql("DELETE FROM catalog_product")
            .fetch()
            .rowsUpdated()
            .awaitSingle()
    }

    private fun JavaProduct.snapshot() = ProductSnapshot(
        id = requireNotNull(id),
        displayName = requireNotNull(displayName),
        stock = stock,
        version = version
    )

    private fun KotlinProduct.snapshot() = ProductSnapshot(
        id = requireNotNull(id),
        displayName = displayName,
        stock = stock,
        version = version
    )

    private suspend fun storedSnapshot(id: Long): ProductSnapshot =
        databaseClient.sql(
            """
            SELECT id, display_name, stock, version
            FROM catalog_product
            WHERE id = :id
            """.trimIndent()
        )
            .bind("id", id)
            .map { row, _ ->
                ProductSnapshot(
                    id = (row.get("id") as Number).toLong(),
                    displayName = requireNotNull(
                        row.get("display_name", String::class.java)
                    ),
                    stock = (row.get("stock") as Number).toInt(),
                    version = (row.get("version") as? Number)?.toLong()
                )
            }
            .one()
            .awaitSingle()

    @Test
    fun javaWriteCanBeReadByKotlin() = runTest {
        val saved = javaProducts.save(
            JavaProduct("Sổ tay", 7)
        ).awaitSingle()

        val id = requireNotNull(saved.id)
        val loaded = kotlinProducts.findById(id).awaitSingle()

        assertNotNull(saved.version)
        assertEquals(saved.snapshot(), loaded.snapshot())
        assertEquals(saved.snapshot(), storedSnapshot(id))
    }

    @Test
    fun kotlinWriteCanBeReadAndUpdatedByJava() = runTest {
        val saved = kotlinProducts.save(
            KotlinProduct(displayName = "Bút chì", stock = 5)
        ).awaitSingle()

        val id = requireNotNull(saved.id)
        val loadedByJava = javaProducts.findById(id).awaitSingle()

        assertEquals(saved.snapshot(), loadedByJava.snapshot())
        assertEquals(saved.snapshot(), storedSnapshot(id))

        loadedByJava.stock = 6
        val updatedByJava = javaProducts.save(loadedByJava)
            .awaitSingle()

        val loadedAgain = kotlinProducts.findById(id).awaitSingle()

        assertEquals(6, loadedAgain.stock)
        assertEquals(updatedByJava.snapshot(), loadedAgain.snapshot())
        assertEquals(updatedByJava.snapshot(), storedSnapshot(id))
    }

    @Test
    fun staleKotlinVersionCannotOverwriteJavaUpdate() = runTest {
        val initial = javaProducts.save(
            JavaProduct("Hộp bút", 10)
        ).awaitSingle()

        val id = requireNotNull(initial.id)
        val staleKotlin = kotlinProducts.findById(id).awaitSingle()

        initial.stock = 9
        val updatedByJava = javaProducts.save(initial).awaitSingle()

        assertFailsWith<OptimisticLockingFailureException> {
            kotlinProducts.save(staleKotlin.copy(stock = 8))
                .awaitSingle()
        }

        val afterConflict = kotlinProducts.findById(id).awaitSingle()
        assertEquals(updatedByJava.snapshot(), afterConflict.snapshot())
        assertEquals(updatedByJava.snapshot(), storedSnapshot(id))
    }
}
~~~

Fixture xóa dữ liệu chỉ dành cho database test cô lập. Nếu các test chạy song song và cùng dùng một bảng, thao tác dọn chung có thể gây nhiễu; cần tách database/schema hoặc điều phối thực thi phù hợp.

Không mặc định test slice sẽ tự rollback mọi reactive transaction. Cách tạo và dọn dữ liệu phải phù hợp với hạ tầng transaction thực tế của test.

### 6.2. Các kiểm chứng trong ví dụ có ý nghĩa gì?

Test thứ nhất kiểm tra Java ghi, Kotlin materialize và dữ liệu lưu có cùng snapshot.

Test thứ hai kiểm tra chiều ngược lại, rồi tiếp tục cập nhật bằng Java và đọc lại bằng Kotlin. Nó không chỉ chứng minh hai model đọc được dữ liệu ban đầu.

Test thứ ba kiểm tra version không bị mất khi đi qua model Kotlin và `copy()`. Một cập nhật bằng version cũ không được ghi đè thay đổi đã thành công ở phía Java theo hợp đồng optimistic locking của ví dụ.

Không cần hard-code version đầu tiên phải bằng một giá trị chung cho mọi store. Điều quan trọng là version được cấp, được đọc đúng và thực sự tham gia kiểm soát cập nhật.

## 7. Query, sort và count cũng cần được so sánh

Đọc đúng một entity theo ID chưa bao phủ query derivation và mapping property.

Với hai repository trên, có thể thêm một tình huống vào fixture test:

~~~kotlin
javaProducts.save(JavaProduct("Nhóm A", 2)).awaitSingle()
kotlinProducts.save(
    KotlinProduct(displayName = "Nhóm A", stock = 1)
).awaitSingle()

val sort = Sort.by(Sort.Direction.ASC, "stock")
    .and(Sort.by(Sort.Direction.ASC, "id"))

val javaResult = javaProducts.findByDisplayName("Nhóm A", sort)
    .map { it.snapshot() }
    .collectList()
    .awaitSingle()

val kotlinResult = kotlinProducts.findByDisplayName("Nhóm A", sort)
    .map { it.snapshot() }
    .collectList()
    .awaitSingle()

assertEquals(javaResult, kotlinResult)
assertEquals(listOf(1, 2), kotlinResult.map { it.stock })
assertEquals(
    javaProducts.countByDisplayName("Nhóm A").awaitSingle(),
    kotlinProducts.countByDisplayName("Nhóm A").awaitSingle()
)
~~~

Đoạn này dùng thêm import `org.springframework.data.domain.Sort` và đặt trong ngữ cảnh test có các helper phía trước.

Khóa `id` giúp phân biệt thứ tự khi stock bằng nhau. Cần kiểm chứng kết quả theo hợp đồng sort của backend, không dựa vào thứ tự insert ngẫu nhiên.

Nếu ứng dụng có derived query dùng nested property, projection, Query by Example hoặc phân trang, hãy chọn các đường thực sự được sử dụng để đưa vào ma trận tương thích. Không cần kiểm thử mọi tên method có thể tưởng tượng.

### 7.1. Projection không phải entity đầy đủ

Java projection và Kotlin DTO có thể có tên property, nullability hoặc constructor khác nhau. Kiểm thử cần xác nhận query cung cấp đủ dữ liệu cho kiểu kết quả đó.

Không dùng default của Kotlin để che một projection thiếu field rồi xem object đó như toàn bộ state có thể lưu lại. Với API ghi thay thế, cách hiểu sai này có thể làm mất dữ liệu chưa được đọc.

## 8. Nullability và field thiếu là các trục kiểm thử riêng

Java `String` không có annotation nullability được Kotlin nhìn nhận theo hợp đồng interop khác với một property Kotlin khai báo `String` rõ ràng.

Kiểm thử cần xét cả metadata nullability của dự án và dữ liệu thực tế:

| Trường hợp | Rủi ro cần phát hiện |
| --- | --- |
| Java field có thể null, Kotlin property không nullable | Java đọc được nhưng Kotlin creator không tạo được object hợp lệ |
| Java primitive có giá trị khởi tạo 0 | Dữ liệu chưa được gán có thể trông giống một giá trị nghiệp vụ thật |
| Kotlin property có default | Dữ liệu thiếu có thể bị fallback che đi |
| Kotlin nullable property có default khác null | Không nên mặc định null nguồn luôn được giữ nguyên qua mọi mapper |
| Query không chọn một column | Khác biệt giữa dữ liệu không được lấy và dữ liệu thực sự null |
| Dữ liệu cũ thiếu field mới | Hai phiên bản model có thể diễn giải khác nhau |

Với Kotlin, nullable nói về miền giá trị; default argument nói về việc có thể bỏ đối số khi tạo object. Hai khái niệm không thay nhau.

### 8.1. Không trộn lỗi database với lỗi materialization

Trong schema ví dụ, `display_name` và `stock` là `NOT NULL`. Một thao tác ghi null có thể bị database từ chối trước khi có cơ hội đọc vào Kotlin model.

Muốn đánh giá hành vi mapper với nguồn null hoặc thiếu field, cần một fixture/query/schema test thực sự tạo ra trường hợp đó theo mục tiêu kiểm thử. Không tuyên bố đã kiểm tra constructor null chỉ vì database chặn null ở bước insert.

Ngược lại, việc constructor từ chối dữ liệu null không tự chứng minh database đã có ràng buộc tương ứng.

### 8.2. Annotation và compiler mode có tác động tại điểm gọi

Nullability của API Java còn phụ thuộc bộ annotation và chế độ kiểm tra mà dự án đang sử dụng. Cần giữ chúng trong cấu hình kiểm thử tương thích và đánh giá lại khi nâng cấp toolchain.

Không dùng `!!` ở mọi điểm gọi chỉ để làm code biên dịch; nó có thể chuyển một hợp đồng chưa rõ thành lỗi runtime. Trong test, `requireNotNull` hoặc assertion nên thể hiện rõ field nào bắt buộc phải có sau khi lưu.

## 9. Constructor, accessor và vị trí annotation

Hai entity có thể có cùng tên property nhưng khác đường materialize:

- Java bean có thể được tạo bằng constructor không đối số rồi population field hoặc setter.
- Kotlin data class thường dùng primary constructor trong mapper hỗ trợ Kotlin.
- Một creator được chỉ định hoặc một custom converter có thể thay đổi đường đi này.
- JPA provider có cơ chế riêng, không đồng nhất với relational/document object mapping của Commons.

Các trường hợp cần có dữ liệu test phù hợp:

1. Creator nhận được đầy đủ field bắt buộc.
2. Tên property và tên column/document field được ánh xạ giống nhau.
3. Annotation được đặt ở target mà mapper nhận diện.
4. Getter/setter Java không làm thay đổi ý nghĩa dữ liệu ngoài dự kiến.
5. Default hoặc initializer không che việc mapper bỏ sót một field.

### 9.1. Boolean accessor và tên property

Một field Java có accessor dạng `isActive`, một Kotlin property tên `active` và một Kotlin property tên `isActive` không nên được xem là ba cách đặt tên luôn tương đương với mọi cơ chế introspection.

Nếu model sử dụng các dạng này, hãy kiểm chứng mapping và derived query bằng tên property thực tế. Khi cần, dùng mapping tường minh thay vì suy từ cách gọi getter trên JVM.

### 9.2. Không thêm no-arg chỉ để mọi test hết lỗi

Một lỗi constructor có thể đến từ dữ liệu thiếu, creator sai hoặc metadata không phù hợp. Thêm constructor rỗng có thể làm thay đổi đường mapping và che nguyên nhân bằng giá trị khởi tạo của field.

Nếu stack yêu cầu no-arg hoặc khả năng proxy, hãy đáp ứng đúng yêu cầu đó. Nếu mapper hỗ trợ constructor binding, hãy kiểm chứng constructor dự định dùng thay vì loại bỏ mọi invariant.

## 10. ID và version phải có cùng ngữ nghĩa

Các khác biệt nhỏ ở kiểu dữ liệu có thể ảnh hưởng nhận diện entity mới:

| Java | Kotlin | Điều cần kiểm tra |
| --- | --- | --- |
| `Long id` nullable | `Long? = null` | Có biểu diễn cùng trạng thái chưa cấp ID không? |
| `long id` mặc định 0 | `Long = 0` | Module có diễn giải 0 khác null không? |
| `Long version` nullable | `Long? = null` | Version có tham gia đúng chiến lược is-new và optimistic locking không? |
| ID được ứng dụng gán | ID được sinh trong constructor default | Có vô tình sinh ID mới khi đọc dữ liệu thiếu không? |

Không áp dụng một quy tắc is-new tự suy cho mọi module. Nếu dùng `Persistable` hoặc chiến lược tùy biến, cần kiểm thử chính chiến lược đó ở cả hai model.

### 10.1. Dùng kết quả save của model bất biến

Với Kotlin data class có `val`, kết quả `save` có thể là instance mang ID hoặc version mới. Không chỉ kiểm tra object đầu vào rồi kết luận persistence không hoạt động.

Luồng nên được kiểm chứng là:

~~~text
Object trước save
    → kết quả save
    → dữ liệu store
    → object đọc lại bằng ngôn ngữ còn lại
~~~

Test phải so các mốc đúng ý nghĩa. Một property không đổi trên object đầu vào chưa tự là lỗi nếu hợp đồng module trả instance kết quả đã được cập nhật.

### 10.2. copy không tự làm entity thành mới

`copy()` thường giữ ID và version từ instance nguồn nếu không truyền giá trị khác. Nó không tự đặt lại vòng đời persistence.

Ngược lại, đặt ID/version về null để tạo bản ghi khác là một quyết định nghiệp vụ, không phải kỹ thuật sửa mọi lỗi lưu data class.

## 11. So sánh dữ liệu có chủ đích

Các field khác stock hoặc String cũng cần quy tắc so sánh phù hợp:

| Nhóm dữ liệu | Ví dụ cần kiểm chứng |
| --- | --- |
| Thời gian | Cùng ý nghĩa thời điểm, zone và độ chính xác được store bảo toàn |
| Số thập phân | Giá trị, scale và quy tắc làm tròn theo nghiệp vụ |
| Enum | Lưu tên hay mã riêng; không phụ thuộc nhầm ordinal |
| Collection | Thứ tự có ý nghĩa không, null khác rỗng không, phần tử có bị mất không |
| Embedded/value object | Creator, tên field và converter có tương thích không |
| ID đặc thù | UUID, document ID hoặc kiểu wrapper có cùng representation không |

Không chuẩn hóa mọi thứ quá rộng chỉ để assertion qua. Ví dụ, thêm sai số thời gian lớn có thể che việc mất zone hoặc dùng sai nguồn thời gian.

Với `BigDecimal`, equality và so sánh giá trị số có thể có ý nghĩa khác nhau khi scale khác nhau. Test nên chọn quy tắc đúng nghiệp vụ, đồng thời đối chiếu representation nếu schema yêu cầu scale cụ thể.

### 11.1. Equality và hashCode không phải giao thức persistence

Kotlin data class sinh equality/hashCode từ các property trong primary constructor. Java entity có thể triển khai theo ID hoặc giữ behavior mặc định.

Nếu ID/version thay đổi sau khi lưu, một model có equality dựa trên các field đó còn có thể ảnh hưởng cách object được dùng trong hash-based collection. Cần kiểm soát cách dùng entity trong ứng dụng, không dùng tập hợp như một bằng chứng duy nhất rằng hai ngôn ngữ đã tương thích.

Snapshot chung giúp test tránh phụ thuộc ngẫu nhiên vào các khác biệt này.

## 12. Coroutine và reactive adapter cần được kiểm chứng riêng

Các test trước dùng `awaitSingle()` để chờ publisher trong coroutine. Điều này không thay đổi schema hoặc quy tắc constructor của entity.

Cần phân biệt:

- Publisher được tạo.
- Publisher được subscribe khi adapter thực thi.
- Query thành công và entity được materialize.
- Query hoàn tất rỗng.
- Query hoặc mapping phát sinh lỗi.

`awaitSingle()` phù hợp khi test kỳ vọng đúng một kết quả. Nếu hợp đồng cho phép không tìm thấy, cần dùng adapter phù hợp như `awaitSingleOrNull()` và kiểm tra null một cách tường minh.

### 12.1. Không đổi mọi lỗi thành “không tìm thấy”

Một lỗi tạo Kotlin entity vì thiếu field không phải là kết quả repository rỗng. Lỗi kết nối cũng không phải một bản ghi không tồn tại.

Tránh một catch quá rộng rồi trả null hoặc danh sách rỗng. Cách đó có thể làm test tương thích đi qua mà dữ liệu thực tế chưa bao giờ được materialize.

Cancellation cũng cần được truyền đúng theo hợp đồng coroutine, không bị nuốt như một lỗi business thông thường.

### 12.2. runTest không làm thời gian database trở thành thời gian ảo

`runTest` hỗ trợ kiểm thử coroutine, nhưng một driver kết nối database thật vẫn có I/O và scheduling thực tế. Virtual time của coroutine test không tự điều khiển database, `Instant.now()` hoặc mọi executor ngoài test scheduler.

Không dùng `delay` để “đợi chắc dữ liệu đã lưu” nếu đã có publisher biểu diễn completion. Hãy chờ đúng kết quả hoàn tất của thao tác và thiết kế timeout phù hợp ở ranh giới test.

Với `Flow`, cần collect để quan sát cả dữ liệu lẫn lỗi mapping; chỉ gọi một method trả Flow chưa chứng minh truy vấn đã chạy.

## 13. Transaction và auditing trong luồng hỗn hợp

Java hay Kotlin không tự quyết định loại transaction. Module, transaction manager và đường thực thi mới quyết định tài nguyên nào cùng tham gia.

Nếu ứng dụng có cả blocking repository và reactive repository, không nên giả định một annotation transaction ở ngoài sẽ tự bao trùm mọi tài nguyên của cả hai phía.

Kiểm thử cần xác định:

- Transaction manager nào được dùng.
- Các thao tác có nằm trong cùng pipeline/ngữ cảnh cần thiết không.
- Khi một lần ghi lỗi, dữ liệu nào rollback và dữ liệu nào đã commit.
- Có subscription hoặc coroutine tách rời làm thoát khỏi phạm vi cần kiểm soát không.

### 13.1. Auditing phải được so bằng hành vi

Nếu cả hai entity có created/modified date hoặc auditor, nên dùng nguồn thời gian và actor xác định để kiểm tra:

- Java tạo, Kotlin đọc: metadata tương ứng có được giữ đúng không?
- Kotlin sửa, Java đọc: created metadata có giữ nguyên và modified metadata có đổi đúng không?
- Mọi field có được mapper/provider nhận diện ở đúng annotation target không?

Không thay thời gian tạo bằng một default `Instant.now()` khi đọc chỉ để non-null assertion không lỗi. Giá trị như vậy có thể là thời gian materialize, không phải metadata lịch sử.

## 14. Ma trận dữ liệu nên phản ánh rủi ro thật

Một bộ fixture hữu ích có thể gồm:

- Dữ liệu bình thường với đầy đủ field.
- Chuỗi Unicode và chuỗi rỗng nếu hợp đồng cho phép.
- Giá trị số biên nằm trong miền nghiệp vụ.
- Field nullable thực sự null.
- Dữ liệu cũ thiếu field mới nếu store hoặc query có thể tạo tình huống đó.
- Nhiều bản ghi có cùng khóa sort chính.
- Entity mới chưa có ID và entity đã có ID/version.
- Hai bản sao cùng version để kiểm tra xung đột.

Không cần tổ hợp mọi giá trị của mọi field. Chọn các trường hợp có thể làm hai đường mapping diễn giải khác nhau hoặc phá invariant quan trọng.

### 14.1. Tách các lớp kiểm thử

| Lớp kiểm thử | Chứng minh điều gì? |
| --- | --- |
| Unit test model | Constructor, validation, copy hoặc conversion thuần của ứng dụng |
| Mapping test theo module | Dữ liệu nguồn được chuyển thành model đúng theo mapper |
| Repository integration test | Query và ghi dữ liệu thực tế qua driver/module |
| Compatibility test đọc/ghi chéo | Hai model hoặc hai phiên bản ứng dụng cùng giữ hợp đồng dữ liệu |
| Migration test | Fixture của schema cũ đi qua bước chuyển đổi rồi được code mới đọc đúng |

Một mock repository trả sẵn object Kotlin không chứng minh Java đã ghi đúng representation trong store. Ngược lại, test database không nhất thiết phải lặp lại mọi phép `copy()` thuần nếu chúng không tạo thêm bằng chứng cần thiết.

## 15. Khi chuyển dần từ Java sang Kotlin

Nếu hai phiên bản ứng dụng có thể hoạt động đồng thời, ma trận cần xét cả producer và consumer dữ liệu:

| Writer | Reader | Câu hỏi |
| --- | --- | --- |
| Java cũ | Kotlin mới | Code mới có đọc được dữ liệu đã tồn tại không? |
| Kotlin mới | Java cũ | Field/representation mới có làm code cũ lỗi hoặc hiểu sai không? |
| Java cũ | Java cũ | Các ràng buộc schema mới có phá đường ghi còn hoạt động không? |
| Kotlin mới | Kotlin mới | Model mới có làm việc đúng trong schema đích không? |

Với document hoặc thao tác ghi thay thế, cần kiểm tra writer cũ có làm mất field mới mà nó không biết hay không. Không chỉ kiểm tra khả năng reader bỏ qua field lạ.

Việc đổi nullability, tên field, enum representation, ID hoặc default cần được xem là thay đổi hợp đồng dữ liệu. Chỉ đổi phần mở rộng file từ Java sang Kotlin không làm các thay đổi đó an toàn tự động.

Khi nâng cấp Kotlin, compiler plugin, Spring Data hoặc provider, dùng lại các fixture đọc/ghi chéo quan trọng để phát hiện thay đổi ở constructor binding, annotation và conversion.

## 16. Chẩn đoán các lỗi thường gặp

| Biểu hiện | Khả năng cần xem xét | Hướng kiểm chứng |
| --- | --- | --- |
| Java đọc được nhưng Kotlin lỗi khởi tạo | Field nguồn null/thiếu so với tham số bắt buộc | Xem dữ liệu nguồn và creator được chọn |
| Kotlin đọc được nhưng dữ liệu hiển thị thành default | Query thiếu field hoặc defaulting che dữ liệu cũ | Đối chiếu row/document thực tế |
| Hai query cùng tên trả khác tập dữ liệu | Property mapping, predicate hoặc converter khác nhau | So query shape và fixture chung |
| ID/version không xuất hiện trên object đầu vào Kotlin | Model bất biến, kết quả save là instance cần dùng | Kiểm tra kết quả save và dữ liệu đọc lại |
| Cập nhật ghi đè thay đổi từ phía còn lại | Version không được map hoặc không đi qua đường kiểm soát đồng thời | Dùng hai bản sao cùng version để tái hiện |
| Equals khác dù field giống nhau | Hai entity có equality khác hoặc khác class | So snapshot hợp đồng thay vì entity trực tiếp |
| Test coroutine trả null khi dữ liệu hỏng | Lỗi mapping bị catch và đổi thành không tìm thấy | Giữ lỗi đúng loại, kiểm tra đường completion/error |
| Test chạy riêng đúng, chạy chung sai | Fixture hoặc database test dùng chung, dọn dữ liệu chồng chéo | Cô lập state và ranh giới thực thi |
| Chỉ khác sau khi đổi persistence stack | Provider, driver hoặc transaction khác nhau | Giữ cố định stack rồi đánh giá từng trục |

Đừng sửa tất cả lỗi bằng constructor rỗng, nullable trên mọi field hoặc default tùy ý. Mỗi thay đổi như vậy đều có thể làm yếu hợp đồng mà test cần bảo vệ.

## 17. Điều kiện chấp nhận tương thích

Một bộ bằng chứng đủ dùng cho phạm vi đã chọn nên thể hiện:

1. Hai chiều đọc/ghi giữ đúng dữ liệu nghiệp vụ và representation quan trọng.
2. ID, version và nhận diện entity mới có cùng ý nghĩa.
3. Null, missing và default được xử lý theo hợp đồng đã công bố.
4. Query, sort, count và projection đang dùng có kết quả đúng.
5. Lỗi mapping không bị nhầm với không tìm thấy hoặc completion thành công.
6. Transaction/auditing được kiểm chứng tại đúng module và đường thực thi.
7. Dữ liệu của phiên bản cũ và mới tương thích trong giai đoạn cùng hoạt động nếu có yêu cầu đó.

Không nên dùng một con số “tất cả test xanh” mà thiếu phạm vi để tuyên bố tương thích với mọi store. Kết luận cần gắn với schema, module, cấu hình và những đường đọc/ghi đã thực sự được kiểm chứng.

Các đoạn code và ma trận trong bài là tài liệu minh họa cho việc thiết kế kiểm thử. Chúng không xác nhận một môi trường cụ thể đã chạy thành công hoặc đã hoàn tất migration.

## 18. Tự kiểm tra kiến thức

1. Vì sao không nên so trực tiếp một Java entity với một Kotlin data class để kết luận tương thích persistence?
2. Một test Java lưu rồi Java đọc lại bỏ sót bằng chứng nào khi ứng dụng còn có Kotlin model?
3. Tại sao cần so thêm row/document thực tế bên cạnh hai object đã materialize?
4. Khi nào một default trong Kotlin làm dữ liệu cũ trông hợp lệ nhưng che sự khác biệt schema?
5. Vì sao phải sử dụng và kiểm tra kết quả save của entity bất biến?
6. Test optimistic locking đọc/ghi chéo phát hiện được lỗi nào mà một test findById đơn giản không phát hiện?
7. Vì sao runTest hoặc suspend không làm một lỗi constructor trở thành kết quả không tìm thấy?
8. Khi chuyển Java sang Kotlin cùng lúc với chuyển JPA sang R2DBC, cần tách những trục kiểm chứng nào để tìm đúng nguyên nhân khác biệt?

Tương thích Java–Kotlin trong Spring Data cần được chứng minh tại ranh giới dữ liệu và hành vi repository. Một snapshot nghiệp vụ rõ ràng, fixture đúng schema và các phép đọc/ghi chéo giúp phân biệt khác biệt ngôn ngữ với khác biệt mapping, transaction và khả năng của từng store.
