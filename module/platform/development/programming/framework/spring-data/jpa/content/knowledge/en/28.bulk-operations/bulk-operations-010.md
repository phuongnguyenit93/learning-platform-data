# Chunking, Flushing, and Clearing When Importing Large Datasets

## 1. Why does importing large datasets require chunking?

When importing tens of thousands or millions of records with Spring Data JPA, the straightforward approach is reading each row and calling `repository.save()`. That may be functionally correct, yet performance and memory usage are often poor if the entire job runs inside one giant persistence context.

JPA maintains a persistence context (first-level cache) to track managed entities. When importing many entities in the same transaction, the number of retained objects grows steadily. Hibernate must also inspect entity state to detect changes and prepare SQL statements. Without control, the application can consume excessive heap, slow down from dirty checking, or encounter out-of-memory errors.

Three ideas should be combined:

- **JDBC batching:** groups multiple executions of statements of the same kind into batches sent to the JDBC driver, reducing round-trips to the database.
- **Data chunking:** processes a group of records per iteration to bound the amount of data held in memory and the unit of work size.
- **`flush()` and `clear()`:** synchronizes pending changes to the database, then evicts entities from the persistence context to avoid holding all objects in memory.

The three mechanisms are related but do not replace one another. Enabling JDBC batching does not automatically evict entities from the persistence context; calling `clear()` does not automatically create JDBC batches or commit the transaction.

After this lesson, you will be able to select appropriate batch sizes, configure Hibernate, write an import loop with properly ordered flush/clear calls, and determine when to commit per chunk.

## 2. Distinguishing JDBC batch, chunk, and transaction

A data import pipeline can have three different sizes:

| Concept | Meaning | Example |
|---|---|---|
| JDBC batch size | Number of JDBC statements of the same group bundled into one batch | 50 INSERT statements |
| Flush/clear interval | Number of entities processed before syncing and clearing the persistence context | 50 or 100 entities |
| Transaction chunk size | Number of records committed in a single transaction | 500 or 1,000 records |

The three values do not have to match. For instance, one transaction can process 1,000 records, flush/clear every 50 records, while Hibernate groups up to 50 INSERT statements into one JDBC batch. In that case, a single transaction can emit multiple JDBC batches.

Start with small values, measure duration, heap, round-trips, and database load, then tune. A JDBC batch size around 25–50 is a common starting point, though the optimal value depends on driver, database, record width, and table relationships. Transaction chunk size is usually larger than JDBC batch size and should be chosen based on rollback requirements, processing time, and database resources.

## 3. Enabling JDBC batching in Hibernate

With Spring Boot, configure Hibernate in `application.properties`:

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
```

Meaning:

- `hibernate.jdbc.batch_size`: limits the number of JDBC statements grouped into a single batch.
- `hibernate.order_inserts`: sorts INSERT operations so statements of the same kind are more easily batched.
- `hibernate.order_updates`: sorts UPDATE operations to improve batching and potentially reduce certain lock conflicts.

The two ordering options can increase in-memory processing overhead. Measure performance before and after enabling them on representative data.

### Key generation strategy affects batching

Hibernate cannot batch INSERTs in the usual way when an entity uses primary keys generated by `GenerationType.IDENTITY`, because the database must execute the INSERT immediately to return the generated ID. This negates the benefit of JDBC insert batching in Hibernate.

If the database supports sequences, the `SEQUENCE` strategy is generally more suitable for batch inserts. Example:

```java
@Entity
@SequenceGenerator(
    name = "product_seq_generator",
    sequenceName = "product_seq",
    allocationSize = 50
)
public class Product {

    @Id
    @GeneratedValue(
        strategy = GenerationType.SEQUENCE,
        generator = "product_seq_generator"
    )
    private Long id;

    private String sku;
    private String name;

    protected Product() {
    }

    public Product(String sku, String name) {
        this.sku = sku;
        this.name = name;
    }
}
```

This is an illustrative entity. The sequence `product_seq` must exist or be created properly according to schema configuration; `allocationSize` must align with how the database and Hibernate allocate sequence values. UUIDs or application-assigned keys can also avoid waiting for the database to return an ID after every INSERT. Do not change the key strategy solely for batching if doing so conflicts with existing data design.

## 4. Understanding flush() and clear() properly

### flush(): synchronizing the persistence context to the database

`EntityManager.flush()` instructs the JPA provider to synchronize pending changes in the persistence context into SQL statements. With Hibernate, this is when the required INSERT, UPDATE, or DELETE statements are emitted to the database; when JDBC batching is configured, eligible statements can be grouped into batches.

`flush()` does not commit the transaction. The transaction stays open and can still roll back. Flushed changes still belong to the active transaction; they have not become committed data visible to other transactions under normal isolation.

Flushing can occur automatically before commit and, depending on flush mode, before certain queries. Calling flush explicitly controls synchronization timing and prevents the persistence context from accumulating too many pending changes.

Flushing can also surface errors early, such as unique constraint violations or data errors. However, commit can still fail due to constraints or errors checked at commit time.

### clear(): detaching all entities from the persistence context

`EntityManager.clear()` removes all managed entities from the persistence context. Those entities become detached. The persistence context no longer tracks changes on these objects; subsequent modifications to a detached object are not saved automatically.

`clear()` does not delete data in the database, does not roll back the transaction, and does not commit pending changes. Therefore, flush before clearing if you want to preserve changes already made:

```java
entityManager.flush();
entityManager.clear();
```

After `clear()`, entities held in Java variables are no longer managed. If further updates are required, re-query or use `merge` intentionally within an appropriate transaction. Do not assume lazy relationships on detached entities can still load data.

### Why call both?

If you only call `flush()`, SQL is synchronized, yet entities remain in the persistence context. Memory continues to grow as more data is imported.

If you only call `clear()`, entities are detached before pending changes are synchronized; unflushed changes may not be saved.

The safe pattern when processing in batches is:

1. Create or update a group of entities.
2. Call `flush()` to synchronize that group.
3. Call `clear()` to evict entities from the persistence context.
4. Continue with the next group in the current transaction or a new transaction according to design.

## 5. Pattern for batch-persisting in one transaction

If business requirements dictate that the entire import must succeed or roll back together, you can keep a single transaction for the entire job while periodically flushing/clearing to bound the number of managed entities.

```java
@Service
public class ProductImportService {

    private static final int BATCH_SIZE = 50;

    @PersistenceContext
    private EntityManager entityManager;

    @Transactional
    public void importAll(Iterator<ProductImportRow> rows) {
        int count = 0;

        while (rows.hasNext()) {
            ProductImportRow row = rows.next();
            entityManager.persist(
                new Product(row.sku(), row.name())
            );

            count++;
            if (count % BATCH_SIZE == 0) {
                entityManager.flush();
                entityManager.clear();
            }
        }

        entityManager.flush();
    }
}

public record ProductImportRow(String sku, String name) {}
```

This is an integration example requiring the `Product` entity, a Spring context, and a data source providing an `Iterator`. The `importAll` method opens a single transaction for the entire import. Flush calls send SQL to the database, while clear frees the persistence context. When the method finishes, Spring commits the transaction; if an error causes the transaction to roll back, groups already flushed within that transaction roll back as well.

The advantage is guaranteeing atomicity for the whole import at the transaction level. The drawback is that the transaction stays open throughout the import: the connection is held for a long time, transaction logs grow, locks may persist, and the database must maintain large transaction state. Flushing/clearing reduces persistence context heap pressure, not transaction duration.

If the data source is a large file, read and parse data in a streaming fashion instead of loading the entire file into a list before calling the service. Clearly determine whether reading the file, validating data, and writing to the database belong in the same transaction.

## 6. Each chunk in a separate transaction

If committing each group of records is acceptable, separate the import coordinator and the single-chunk writer into two Spring beans. Each writer invocation runs in its own transaction:

```java
@Service
public class ProductChunkWriter {

    @PersistenceContext
    private EntityManager entityManager;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void insertChunk(List<ProductImportRow> rows) {
        for (ProductImportRow row : rows) {
            entityManager.persist(
                new Product(row.sku(), row.name())
            );
        }

        entityManager.flush();
        entityManager.clear();
    }
}
```

```java
@Service
public class ProductImportCoordinator {

    private static final int CHUNK_SIZE = 500;

    private final ProductChunkWriter writer;

    public ProductImportCoordinator(ProductChunkWriter writer) {
        this.writer = writer;
    }

    public int importAll(Iterator<ProductImportRow> rows) {
        List<ProductImportRow> chunk = new ArrayList<>(CHUNK_SIZE);
        int imported = 0;

        while (rows.hasNext()) {
            chunk.add(rows.next());

            if (chunk.size() == CHUNK_SIZE) {
                writer.insertChunk(List.copyOf(chunk));
                imported += chunk.size();
                chunk.clear();
            }
        }

        if (!chunk.isEmpty()) {
            writer.insertChunk(List.copyOf(chunk));
            imported += chunk.size();
        }

        return imported;
    }
}
```

The example uses Java 17 with `record`; corresponding imports, entities, data sources, and Spring configuration are required. The two classes must be separate Spring beans so calls to `writer.insertChunk()` pass through the transaction proxy. If both methods are placed in the same bean and called via `this.insertChunk()`, proxy-based transaction interception will not activate for that internal call.

With `REQUIRES_NEW`, each chunk has its own transaction. When the writer method returns normally, the chunk's transaction commits before the coordinator continues. If the fourth chunk fails, previously committed chunks remain persisted; the failed chunk rolls back. Thus, the import must be resumable or safely re-runnable, using unique business keys, progress state, batch IDs, and idempotent operations.

If the coordinator is invoked inside an outer transaction, `REQUIRES_NEW` suspends the outer transaction while writing the chunk. A subsequent rollback of the outer transaction cannot undo independently committed chunks. Therefore, the coordinator should usually be called outside an enclosing transaction when the goal is per-chunk commits.

The size 500 in the example is the business chunk size, not the JDBC batch size. With `hibernate.jdbc.batch_size=50`, a 500-entity chunk can emit multiple JDBC batches. Tune both values independently based on measurements.

## 7. Using Spring Data repositories properly

`JpaRepository.saveAll()` is convenient for saving a collection, yet the method itself does not guarantee a single JDBC batch. In the common implementation, Spring Data JPA iterates over elements and calls `save()` for each entity. Whether Hibernate batches INSERT/UPDATE statements into JDBC batches still depends on configuration, ID strategy, entity state, and SQL shape.

`saveAllAndFlush()` saves the collection and then flushes the persistence context. This method does not automatically split the collection into chunks and does not automatically clear the persistence context. If passed a huge list, all entities can remain in the persistence context until cleared or the transaction ends.

If you need to keep using the repository, split the data into chunks, call `saveAll(chunk)`, then call `flush()` and clear via EntityManager or call `JpaRepository.flush()` followed by clear. Keep in mind that clearing detaches all entities in the current persistence context, including entities loaded earlier for other logic.

For objects guaranteed to be new entities, `EntityManager.persist()` expresses creation intent clearly. `save()` must determine whether an entity is new or existing; depending on state detection, Spring Data may call `persist` or `merge`. `merge` can generate extra read/write work and return a different managed instance than the passed object. Check new-entity detection and actual SQL when optimizing imports.

## 8. Entity relationships and considerations when importing

### Entities with relationships

If an entity has `cascade = PERSIST` or `cascade = ALL`, calling `persist` on the root entity can pull in many related entities. This rapidly increases SQL statements and objects in the persistence context. Clearly determine which relationships genuinely need cascading during import.

When referencing an existing entity, `EntityManager.getReference()` can create a proxy reference by ID without immediately loading the entire entity. This is useful when assigning foreign keys on new records, though accessing proxy properties may trigger a query; inspect actual SQL and handle invalid reference IDs.

### Updating entities instead of inserting

For imports containing both inserts and updates, classify records by business key. Looking up each entity with a separate query before updating can create N+1 read queries. You can fetch existing IDs in batches, use projection queries, or use a staging table for matching. After batch updates, continue periodic flush/clear cycles.

If you only need bulk updates matching a condition, JPQL bulk update or native SQL may be more suitable than loading individual entities. However, bulk DML acts directly on the database and does not synchronize managed entities in the persistence context; it also bypasses the full entity lifecycle of individual updates. After bulk DML, consider flushing beforehand and clearing or refreshing affected entities to avoid reading stale state.

### Constraints and validation

Unique, foreign key, not-null, and check constraints in the database remain the final line of defense. Application-side validation provides user-friendly messages, yet does not replace database constraints when multiple imports run concurrently. On a mid-chunk failure, record the row number, business key, and cause so data can be fixed and re-run.

## 9. Verifying whether batching actually works

Do not conclude JDBC batching works merely because `hibernate.jdbc.batch_size` is configured. Verify with production-like data and environments:

- Enable Hibernate statistics in an appropriate test environment using `spring.jpa.properties.hibernate.generate_statistics=true`.
- Use SQL logs or JDBC observation tools to inspect `executeBatch` calls, statement counts, and round-trip times.
- Compare records per second, completion time, heap used, and database load with batching on/off.
- Test specifically with the actual ID strategy, especially if using `IDENTITY`.
- Test inserts, updates, and entities with relationships/cascades resembling production data.

SQL logs often print many identical INSERT statements. That alone does not prove whether each was sent in a separate round-trip or grouped into a batch; use statistics or JDBC tracing tools to confirm actual behavior.

## 10. Choosing a transaction strategy based on business requirements

| Requirement | Suitable strategy | Trade-off |
|---|---|---|
| Entire import must succeed together | Single transaction, periodic flush/clear | Longer transaction and connection hold duration |
| Very large dataset, partial commits acceptable | Separate transaction per chunk | Requires progress tracking, retries, and duplicate prevention |
| High speed for simple data | JDBC batching and potentially bulk SQL/staging | Requires managing entity lifecycles and persistence context state |
| Need to update entities with relationships and callbacks | Chunked JPA persist/update | Incurs dirty checking and cascade overhead |

Do not choose per-chunk transactions merely to reduce memory. If business logic requires whole-file atomicity, committing per chunk changes the outcome when failures occur. Conversely, one massive transaction can strain the connection pool and database. Clarify rollback requirements before choosing how to split transactions.

## 11. Checklist before running large imports

- [ ] Data source is read via streaming or paging, not holding the entire file in heap.
- [ ] `hibernate.jdbc.batch_size` is configured and measured.
- [ ] Checked whether the ID generation strategy supports insert batching.
- [ ] Chosen JDBC batch size, flush/clear interval, and transaction chunk size separately.
- [ ] Each group is `flush()`ed before `clear()`.
- [ ] Understood that `clear()` detaches every entity in the current persistence context.
- [ ] Decided whether the import is a single transaction or commits per chunk.
- [ ] If committing per chunk, progress tracking, idempotency, and retries are in place.
- [ ] Verified cascades, foreign keys, unique constraints, and data errors.
- [ ] Measured SQL batching, heap, throughput, and transaction duration on representative data.

## 12. Key takeaways

JDBC batching reduces database round-trips; chunking bounds the data processed per iteration; `flush()` synchronizes pending changes and `clear()` evicts entities from the persistence context. The standard JPA pattern is `persist` in batches, `flush()`, then `clear()`. If per-group commits are needed, place each chunk in its own transaction and design the import to resume after failures. Always distinguish flush from commit and choose transaction boundaries according to data integrity requirements.
