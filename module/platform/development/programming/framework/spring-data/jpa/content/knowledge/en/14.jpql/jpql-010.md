# CASE, COALESCE, NULLIF Expressions and Standard Functions in JPQL

JPQL allows expressing conditional logic, handling null values, and transforming data directly inside a query. Three expressions—`CASE`, `COALESCE`, and `NULLIF`—are especially useful when classifying results, choosing fallback values, or preventing invalid calculations. JPQL also provides standard functions for working with strings, numbers, dates/times, collections, and aggregates.

Spring Data JPA supports these expressions in `@Query`, derived queries, or projections. This lesson explains syntax, semantics, practical examples, null and data-type constraints, and testing practices so queries behave reliably on the target database.

## 1. JPQL Works with Entities and Java Attributes

JPQL is JPA's object-oriented query language. Queries reference entity names and Java attributes rather than physical table or column names directly.

For example, suppose an `Employee` entity has these attributes:

| Attribute | Java Type | Meaning |
|---|---|---|
| `id` | `Long` | Primary key |
| `name` | `String` | Employee name |
| `nickname` | `String`, nullable | Short display name |
| `code` | `String`, nullable | Employee code |
| `salary` | `BigDecimal` | Salary |
| `bonus` | `BigDecimal`, nullable | Bonus |
| `active` | `Boolean`, nullable | Active status |
| `hiredAt` | `LocalDateTime` | Hire timestamp |
| `department` | `Department` | Relationship to department |
| `tasks` | `Collection<Task>` | Employee's tasks |

A simple JPQL query:

~~~java
@Query("select e from Employee e where e.active = true")
List<Employee> findActiveEmployees();
~~~

`Employee` is the entity name; `e.active` is a Java attribute. Hibernate translates JPQL into SQL tailored to the database dialect. If the entity uses `@Entity(name = "StaffMember")`, JPQL must use `StaffMember` instead of the class name `Employee`.

JPQL expressions and functions can appear in `SELECT`, `WHERE`, `ORDER BY`, or wherever JPQL grammar permits. They are evaluated by the database via SQL generated by the provider.

## 2. What is a CASE Expression?

`CASE` computes a result value based on conditions. It resembles `if/else` in Java, evaluated row-by-row in the database.

JPQL supports two forms:

- Simple CASE: compares one expression against `WHEN` values.
- Searched CASE: evaluates individual Boolean conditions in `WHEN`.

Both forms may include `ELSE`. If `ELSE` is omitted and no `WHEN` branch matches, the result is null.

### Searched CASE

Syntax:

~~~sql
CASE
    WHEN condition1 THEN result1
    WHEN condition2 THEN result2
    ELSE defaultResult
END
~~~

Example classifying employees by salary:

~~~java
@Query("""
       select e.name,
              case
                  when e.salary >= :highSalary then 'HIGH'
                  when e.salary >= :mediumSalary then 'MEDIUM'
                  else 'STANDARD'
              end
       from Employee e
       """)
List<Object[]> classifySalary(
        @Param("highSalary") BigDecimal highSalary,
        @Param("mediumSalary") BigDecimal mediumSalary);
~~~

Each `Object[]` element contains the employee name and classification label. `WHEN` conditions are evaluated in order; the first branch evaluating to TRUE determines the result. Conditions evaluating to FALSE or UNKNOWN are skipped.

### Simple CASE

Syntax:

~~~sql
CASE expression
    WHEN value1 THEN result1
    WHEN value2 THEN result2
    ELSE defaultResult
END
~~~

Example mapping status labels:

~~~java
@Query("""
       select e.name,
              case e.status
                  when 'NEW' then 'New'
                  when 'ACTIVE' then 'Active'
                  when 'LEFT' then 'Left'
                  else 'Unknown'
              end
       from Employee e
       """)
List<Object[]> describeStatus();
~~~

Simple CASE works well when comparing a single attribute against specific values. When you need greater-than, less-than, `AND`/`OR`, or null checks, use searched CASE.

## 3. CASE in SELECT, WHERE, and ORDER BY

CASE can produce display values in `SELECT`:

~~~java
@Query("""
       select e.name,
              case when e.active = true
                   then 'Active'
                   else 'Inactive or unknown'
              end
       from Employee e
       """)
List<Object[]> employeeLabels();
~~~

CASE can be used in `WHERE` to express conditional selection:

~~~java
@Query("""
       select e
       from Employee e
       where case
                 when :includeInactive = true then 1
                 when e.active = true then 1
                 else 0
             end = 1
       """)
List<Employee> searchByActivity(
        @Param("includeInactive") boolean includeInactive);
~~~

However, for simple optional filters, an `OR` expression is usually easier to read:

~~~java
@Query("""
       select e
       from Employee e
       where (:includeInactive = true or e.active = true)
       """)
List<Employee> searchByActivity(
        @Param("includeInactive") boolean includeInactive);
~~~

CASE is also useful for business-specific sorting:

~~~java
@Query("""
       select e
       from Employee e
       order by
           case
               when e.active = true then 0
               when e.active = false then 1
               else 2
           end,
           e.name asc
       """)
List<Employee> findOrderedByActivity();
~~~

Active employees come first, inactive ones next, and nulls last; within each group, results are sorted by name. Default null ordering in `ORDER BY` can vary across databases, so CASE makes the rule explicit.

## 4. CASE and Result Data Types

`THEN` and `ELSE` branches should return compatible types. For example, if one branch returns a `String`, all other branches should return `String`; if returning numbers, use compatible numeric types.

Reasonable example:

~~~sql
CASE
    WHEN e.active = true THEN 'YES'
    ELSE 'NO'
END
~~~

Example to avoid:

~~~sql
CASE
    WHEN e.active = true THEN 'YES'
    ELSE 0
END
~~~

Mixing a string branch with a numeric branch can cause type-conversion errors or database-dependent behavior. For Boolean outcomes, return `true`/`false` consistently; for labels, return strings consistently.

If `ELSE` is omitted, CASE returns null when no condition matches. Decide explicitly whether null makes sense.

## 5. Combining CASE with Aggregate Functions

CASE is frequently combined with `SUM` or `COUNT` for conditional counts.

Example counting active and inactive employees:

~~~java
@Query("""
       select
           sum(case when e.active = true then 1 else 0 end),
           sum(case when e.active = false then 1 else 0 end)
       from Employee e
       """)
Object[] countActivityGroups();
~~~

This computes two counts in a single query. You can use a DTO projection to avoid returning `Object[]`.

Example categorizing orders by total amount:

~~~java
@Query("""
       select
           case
               when o.total >= :largeAmount then 'LARGE'
               when o.total >= :normalAmount then 'NORMAL'
               else 'SMALL'
           end,
           count(o)
       from Order o
       group by
           case
               when o.total >= :largeAmount then 'LARGE'
               when o.total >= :normalAmount then 'NORMAL'
               else 'SMALL'
           end
       """)
List<Object[]> countOrdersByBand(
        @Param("largeAmount") BigDecimal largeAmount,
        @Param("normalAmount") BigDecimal normalAmount);
~~~

This query groups orders by the label computed via CASE. When using CASE inside `GROUP BY`, verify syntax support with your JPQL/provider version; if portability is a priority, you can compute labels in Java or use an appropriate projection and database-tested query.

## 6. COALESCE: Picking the First Non-Null Value

`COALESCE` accepts two or more expressions and returns the first one that is not null. If all are null, it returns null.

Syntax:

~~~sql
COALESCE(expression1, expression2, ...)
~~~

Example picking a display name:

~~~java
@Query("""
       select coalesce(e.nickname, e.name, 'Unnamed')
       from Employee e
       """)
List<String> findDisplayNames();
~~~

Rules:

1. If `nickname` is non-null, use `nickname`.
2. If `nickname` is null, use `name`.
3. If both are null, use `'Unnamed'`.

COALESCE is helpful when data has fallback sources or nullable columns.

### COALESCE in Calculations

Example adding salary and bonus where null bonus is treated as 0:

~~~java
@Query("""
       select e.name,
              e.salary + coalesce(e.bonus, 0)
       from Employee e
       """)
List<Object[]> findTotalCompensation();
~~~

Ensure the literal `0` is compatible with the numeric type of `bonus` and `salary`. For `BigDecimal`, Hibernate/databases generally handle matching numeric arithmetic; if type issues arise, pass a `BigDecimal` zero parameter or use an explicitly typed expression.

COALESCE does not modify stored database values. It only produces a result value for the query. If `bonus` was never entered, the column remains null.

## 7. COALESCE and Optional Search Parameters

A common way to write an optional filter is:

~~~java
@Query("""
       select e
       from Employee e
       where (:departmentName is null
              or e.department.name = :departmentName)
       """)
List<Employee> searchByDepartment(
        @Param("departmentName") String departmentName);
~~~

If `departmentName` is null, the first condition is true and the filter is bypassed. If a value is provided, the query filters by department.

You may encounter a `COALESCE` variant:

~~~sql
e.department.name = COALESCE(:departmentName, e.department.name)
~~~

However, this differs semantically when `e.department.name` is null: if both the parameter and attribute are null, the comparison still evaluates to UNKNOWN. It can also hinder index usage depending on the database. Therefore, an explicit `OR` condition is usually clearer and safer for optional filters.

Define the meaning of null explicitly: skip filter, match null values, or reject input. Do not use COALESCE to paper over an undefined business rule.

## 8. NULLIF: Turning Two Equal Values into Null

`NULLIF` takes two expressions. If they are equal, it returns null; otherwise it returns the first expression.

Syntax:

~~~sql
NULLIF(expression1, expression2)
~~~

Example:

~~~sql
NULLIF(e.discountCode, '')
~~~

If `discountCode` is an empty string, the result is null; otherwise the code is returned unchanged.

Example in JPQL:

~~~java
@Query("""
       select nullif(trim(e.code), '')
       from Employee e
       """)
List<String> findNormalizedCodes();
~~~

`TRIM` strips leading and trailing whitespace first. `NULLIF` then converts empty strings to null. This transforms query output only; it does not update the `code` column.

### NULLIF to Guard Against Division by Zero

Suppose entity `Metric` has `numerator` and `denominator`:

~~~java
@Query("""
       select m.numerator / nullif(m.denominator, 0)
       from Metric m
       """)
List<BigDecimal> findSafeRatios();
~~~

When `denominator` is 0, `NULLIF` returns null. Dividing by null yields null instead of a division-by-zero error. When `denominator` is non-zero, normal division executes.

Verify numeric types and division precision on the target database. If business rules require `0` instead of null, wrap with `COALESCE`:

~~~sql
COALESCE(m.numerator / NULLIF(m.denominator, 0), 0)
~~~

Then a null result caused by a zero denominator becomes `0`. Use this only when `0` is genuinely the business convention; sometimes null more accurately represents "cannot be computed."

## 9. Combining CASE, COALESCE, and NULLIF

These three expressions can be combined to express clear rules.

Example generating a label for employee codes:

~~~java
@Query("""
       select
           case
               when e.active = true then
                   coalesce(nullif(trim(e.code), ''), 'NO-CODE')
               when e.active = false then 'INACTIVE'
               else 'UNKNOWN'
           end
       from Employee e
       """)
List<String> findEmployeeLabels();
~~~

Evaluation order:

1. `CASE` chooses the branch based on status.
2. If active, `TRIM` strips leading/trailing spaces from `code`.
3. `NULLIF` converts an empty string to null.
4. `COALESCE` falls back to `'NO-CODE'` when `code` has no value.
5. If inactive or `active` is null, `CASE` returns the corresponding label.

Nesting multiple expressions can reduce query readability. When rules grow complex, consider DTO projections, service-layer logic, or controlled database views.

## 10. Standard String Functions in JPQL

JPQL provides common string functions:

| Function | Meaning | Example |
|---|---|---|
| `CONCAT(s1, s2)` | Concatenate two strings | `concat(e.firstName, e.lastName)` |
| `SUBSTRING(s, start, length)` | Extract substring | `substring(e.code, 1, 3)` |
| `TRIM(s)` | Strip leading/trailing whitespace | `trim(e.name)` |
| `LOWER(s)` | Convert to lowercase | `lower(e.name)` |
| `UPPER(s)` | Convert to uppercase | `upper(e.name)` |
| `LENGTH(s)` | String length | `length(e.name)` |
| `LOCATE(search, s[, start])` | Substring position | `locate('an', e.name)` |

Example case-insensitive name search:

~~~java
@Query("""
       select e
       from Employee e
       where lower(e.name) = lower(:name)
       """)
List<Employee> findByNameIgnoreCase(@Param("name") String name);
~~~

Find codes by prefix:

~~~java
@Query("""
       select e
       from Employee e
       where substring(e.code, 1, 3) = :prefix
       """)
List<Employee> findByCodePrefix(@Param("prefix") String prefix);
~~~

`LOCATE` returns a 1-based position, or 0 if not found. Example:

~~~java
@Query("select locate(:part, e.name) from Employee e")
List<Integer> locatePart(@Param("part") String part);
~~~

Notes:

- `SUBSTRING` uses 1-based indexing in JPQL.
- `LENGTH` returns length according to the database's string handling; Unicode character counting may differ across engines.
- `LOWER`/`UPPER` depend on database collation and locale rules.
- `CONCAT` in standard JPQL accepts two string expressions; nest `CONCAT` calls to join more parts.
- `TRIM` has extended syntax to specify `LEADING`, `TRAILING`, `BOTH`, and the trim character; verify provider/database support for advanced forms.

## 11. Standard Numeric Functions in JPQL

| Function | Meaning | Example |
|---|---|---|
| `ABS(x)` | Absolute value | `abs(e.balance)` |
| `SQRT(x)` | Square root | `sqrt(e.score)` |
| `MOD(x, y)` | Remainder of division | `mod(e.id, 2)` |

Example retrieving employees with even IDs:

~~~java
@Query("select e from Employee e where mod(e.id, 2) = 0")
List<Employee> findEvenIds();
~~~

Example filtering by absolute value:

~~~java
@Query("select e from Employee e where abs(e.balance) > :limit")
List<Employee> findOutsideBalanceLimit(
        @Param("limit") BigDecimal limit);
~~~

Result types and limits of numeric functions depend on the attribute type and database. `SQRT` generally returns a floating-point result; do not assume it always returns `BigDecimal`. For division, rounding, and precision, test against a real database.

## 12. Standard Date and Time Functions

JPQL provides current-time functions:

| Function | Meaning |
|---|---|
| `CURRENT_DATE` | Current date of the database/session |
| `CURRENT_TIME` | Current time of the database/session |
| `CURRENT_TIMESTAMP` | Current timestamp of the database/session |

Example finding employees hired up to now:

~~~java
@Query("""
       select e
       from Employee e
       where e.hiredAt <= current_timestamp
       """)
List<Employee> findAlreadyHired();
~~~

Example comparing dates:

~~~java
@Query("""
       select e
       from Employee e
       where e.contractEndDate < current_date
       """)
List<Employee> findExpiredContracts();
~~~

These functions are evaluated by the database, so values depend on session timezone and the database clock. If business logic requires an application-controlled UTC timestamp, pass an `Instant` or explicit time parameter rather than relying on `CURRENT_TIMESTAMP`.

## 13. Collection and Map Functions

JPQL has standard expressions for working with collection-valued associations.

**SIZE(collection)** returns the number of elements in a collection:

~~~java
@Query("""
       select e
       from Employee e
       where size(e.tasks) >= :minimumTasks
       """)
List<Employee> findBusyEmployees(
        @Param("minimumTasks") int minimumTasks);
~~~

`SIZE` works only on collection attributes. Depending on the provider, it may translate into a subquery or equivalent SQL expression. For large collections and frequent queries, inspect generated SQL and indexes.

**INDEX(alias)** retrieves an element's position in an association mapped with `@OrderColumn` or a suitably indexed list. Example in a query over a list association:

~~~java
@Query("""
       select t
       from Employee e join e.orderedTasks t
       where index(t) = :position
       """)
List<Task> findTaskAtPosition(@Param("position") int position);
~~~

`INDEX` requires an ordered list mapping and association alias syntax. It is not an index for arbitrary collection types.

For map-valued associations, JPQL provides:

- `KEY(mapAlias)`: entry key.
- `VALUE(mapAlias)`: entry value.
- `ENTRY(mapAlias)`: map entry; typically used in `SELECT`.

Example:

~~~java
@Query("""
       select key(m), value(m)
       from Employee e join e.attributes m
       where key(m) = :attributeName
       """)
List<Object[]> findEmployeeAttribute(
        @Param("attributeName") String attributeName);
~~~

Collection/map functions apply only to properly mapped associations of those kinds; do not use them as general-purpose string or table functions.

## 14. Aggregate Functions Combined with CASE/COALESCE

Standard aggregate functions include:

| Function | Meaning | Typical Result Type |
|---|---|---|
| `COUNT(x)` | Count non-null values or entities | `Long` |
| `COUNT(DISTINCT x)` | Count distinct values | `Long` |
| `SUM(x)` | Sum | Depends on numeric type |
| `AVG(x)` | Average | `Double` |
| `MIN(x)` | Minimum value | Same as attribute type |
| `MAX(x)` | Maximum value | Same as attribute type |

Key rules:

- `COUNT` ignores null values; `COUNT(entity)` counts matching entities.
- `SUM`, `AVG`, `MIN`, and `MAX` ignore null values.
- If there are no values to aggregate, `SUM`/`AVG`/`MIN`/`MAX` typically return null; `COUNT` returns 0.
- `SUM` returns a type depending on input type: `Long` for standard integers, `Double` for floating-point numbers, `BigInteger` for `BigInteger`, and `BigDecimal` for `BigDecimal`.
- `AVG` returns `Double` under standard JPQL rules.

Example calculating total salary:

~~~java
@Query("select sum(e.salary) from Employee e")
BigDecimal totalSalary();
~~~

Example calculating average salary:

~~~java
@Query("select avg(e.salary) from Employee e")
Double averageSalary();
~~~

Example replacing null when no records exist:

~~~java
@Query("select coalesce(sum(e.bonus), 0) from Employee e")
BigDecimal totalBonusOrZero();
~~~

Ensure the fallback value is type-compatible with the `SUM` expression. In strictly typed systems, pass a `BigDecimal` zero parameter or handle null in the service layer.

Combining CASE to count active employees:

~~~java
@Query("""
       select sum(case when e.active = true then 1 else 0 end)
       from Employee e
       """)
Long countActiveEmployees();
~~~

## 15. Using DTO Projections Instead of Object[]

When a query returns multiple expressions, `Object[]` forces positional casting. DTO projections are much clearer.

DTO:

~~~java
package com.example.employee;

public record EmployeeStatusView(
        Long id,
        String name,
        String statusLabel,
        String displayName
) {
}
~~~

Repository:

~~~java
@Query("""
       select new com.example.employee.EmployeeStatusView(
           e.id,
           e.name,
           case
               when e.active = true then 'ACTIVE'
               when e.active = false then 'INACTIVE'
               else 'UNKNOWN'
           end,
           coalesce(e.nickname, e.name, 'Unknown')
       )
       from Employee e
       order by e.name
       """)
List<EmployeeStatusView> findEmployeeStatusViews();
~~~

JPQL constructor expressions require the fully qualified class name, and parameter order and types must match the constructor. Java records provide a canonical constructor suited to this style. If using a regular DTO class, provide a matching public constructor.

DTO projections avoid loading the full entity when only a few columns are needed, while giving APIs/queries an explicit return type.

## 16. Using Expressions in a Spring Data Repository

Example repository combining `CASE`, `COALESCE`, `NULLIF`, and standard functions:

~~~java
package com.example.employee;

import java.math.BigDecimal;
import java.util.List;

import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {

    @Query("""
           select e.name,
                  case
                      when e.salary >= :threshold then 'HIGH'
                      else 'STANDARD'
                  end
           from Employee e
           """)
    List<Object[]> classify(
            @Param("threshold") BigDecimal threshold);

    @Query("""
           select coalesce(e.nickname, e.name, 'Unknown')
           from Employee e
           """)
    List<String> findDisplayNames();

    @Query("""
           select nullif(trim(e.code), '')
           from Employee e
           """)
    List<String> findNormalizedCodes();

    @Query("""
           select e
           from Employee e
           where lower(e.name) like lower(concat('%', :keyword, '%'))
           """)
    List<Employee> searchName(
            @Param("keyword") String keyword);

    @Query("""
           select e
           from Employee e
           order by
               case when e.active = true then 0 else 1 end,
               upper(e.name)
           """)
    List<Employee> findSortedByActivityAndName();

    @Query("select count(e) from Employee e where mod(e.id, 2) = 0")
    Long countEvenIds();
}
~~~

These methods illustrate an `Employee` entity with matching attributes. When adding them to a project, verify that entity names, attributes, return types, and DTO packages match your actual model. Do not write `@Query` when a derived query already expresses simple conditions cleanly.

## 17. Null Semantics to Remember

SQL and JPQL use three-valued logic: TRUE, FALSE, and UNKNOWN. Comparing against null using `=` or `<>` produces UNKNOWN. Use `IS NULL` or `IS NOT NULL` when testing for null.

| Expression | Meaning |
|---|---|
| `e.nickname = null` | Not a valid null check |
| `e.nickname is null` | Attribute has no value |
| `e.nickname is not null` | Attribute has a value |
| `coalesce(e.nickname, e.name)` | Pick the first non-null value |
| `nullif(e.code, '')` | Return null if `code` is empty string |
| `case when e.active = true then ... else ... end` | An UNKNOWN condition does not match the `WHEN` branch |

COALESCE and NULLIF do not alter stored data. They only compute values in the query output. For permanent data cleanup, update records through controlled business logic or migrations.

## 18. Standard Functions vs. Database-Specific FUNCTION()

JPQL provides standard functions to improve portability across databases. However, each database offers many proprietary functions. JPA provides `FUNCTION()` to invoke a specific database/provider function:

~~~java
@Query("""
       select function('some_db_function', e.name)
       from Employee e
       """)
List<String> callDatabaseFunction();
~~~

`some_db_function` is only an illustrative placeholder; replace it with a function that actually exists on the target database.

`FUNCTION()` is an escape hatch and does not guarantee portable queries. Points to note:

- Syntax and parameter types depend on the database.
- The function may need to be registered in the Hibernate dialect.
- Tests running on H2 may fail if H2 lacks the corresponding function.
- Switching databases may require rewriting the query.
- Never allow user-supplied function names or arbitrary SQL fragments into queries.

When standard functionality like `LOWER`, `CONCAT`, `ABS`, or `CURRENT_DATE` suffices, prefer standard JPQL functions.

## 19. Performance and Portability

Expressions in `SELECT` mostly affect result formatting, whereas expressions in `WHERE` or `ORDER BY` can affect index usage.

For example:

~~~sql
WHERE LOWER(name) = LOWER(?)
~~~

If the database lacks a matching functional index, a regular index on `name` may not be usable. Similarly, filtering via `CASE` or functions on columns can prevent the optimizer from using indexes effectively.

Guidelines:

- Use plain column predicates whenever possible.
- Create functional indexes if supported by the database and justified by workload.
- Avoid overusing `CASE` in `WHERE` when explicit `AND`/`OR` predicates express the logic clearly.
- Check execution plans against production-scale data.
- Use projections to fetch only required fields.
- Paginate large result sets.
- Verify database collation and timezone behavior for string and date/time functions.
- Use `FUNCTION()` only when accepting database coupling.
- Verify return types of `CASE`/`COALESCE`/`NULLIF` on your JPA provider.

Standard JPQL improves portability, though it does not guarantee identical SQL or performance across all databases.

## 20. Testing JPQL Expressions

Use `@DataJpaTest` to test queries at the persistence layer. Tests should populate data covering null and non-null values, true/false conditions, empty strings, and boundary values.

Example testing `COALESCE` and `NULLIF`:

~~~java
package com.example.employee;

import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;

@DataJpaTest
class EmployeeRepositoryTest {

    @Autowired
    private EmployeeRepository repository;

    @Test
    void coalesceUsesFirstNonNullValue() {
        repository.save(EmployeeFixture.employee(
                "An", null, "E001", new BigDecimal("1000.00"), true));
        repository.save(EmployeeFixture.employee(
                "Binh", "Bee", "E002", new BigDecimal("1200.00"), true));

        var names = repository.findDisplayNames();

        assertThat(names).contains("An", "Bee");
    }

    @Test
    void nullifTurnsBlankCodeIntoNull() {
        repository.save(EmployeeFixture.employee(
                "An", null, "   ", new BigDecimal("1000.00"), true));

        var codes = repository.findNormalizedCodes();

        assertThat(codes).containsNull();
    }
}
~~~

`EmployeeFixture` in this example is a project test factory creating `Employee` entities with the listed attributes. If no fixture exists, instantiate the entity directly with a matching constructor. Tests focus on query outputs rather than Hibernate internals.

Additional tests to consider:

- `CASE` with TRUE, FALSE, and UNKNOWN conditions.
- `CASE` without `ELSE`.
- `NULLIF` when two values are equal and when they differ.
- `COALESCE` when all arguments are null.
- `LOCATE` when found and when not found.
- `SUBSTRING` with 1-based indexing.
- `MOD` with negative values or valid divisors.
- `CURRENT_DATE`/`CURRENT_TIMESTAMP` under database timezones.
- `SUM`/`AVG` on empty sets or null values.
- `SIZE` on empty and non-empty collections.

H2 is great for fast tests but differs from PostgreSQL/MySQL in functions, collations, numeric types, and date/time handling. If a query relies on database-specific behavior, run integration tests against the actual deployment database.

## 21. Common Errors

| Error | Cause | Fix |
|---|---|---|
| `CASE` returns incompatible types | `THEN`/`ELSE` branches have different types | Use compatible result types |
| `CASE` returns unexpected null | Missing `ELSE` and no `WHEN` branch matches | Add `ELSE` when a default value is needed |
| `COALESCE` fails to replace missing text | Earlier expression is non-null but empty string | Combine `TRIM`/`NULLIF` as needed |
| `NULLIF` misses whitespace-only strings | Only compares raw string | Use `NULLIF(TRIM(value), '')` |
| Division by zero | Unprotected denominator | Use `NULLIF` or `CASE` |
| JPQL rejects table name | Using SQL table/column names instead of entity/attributes | Use entity names and Java attributes |
| Function not found | Using DB-specific function as if standard JPQL | Use `FUNCTION()` intentionally or switch to a standard function |
| Wrong return type | Aggregate or `CASE` returns unexpected type | Verify JPQL type rules and DTO types |
| Query slows down after `LOWER`/`CASE` | Function on column inhibits regular index use | Inspect execution plan and consider functional indexes |
| H2 test passes but production fails | Function or behavior differs between databases | Test on the actual target DBMS |

## 23. Conclusion

`CASE` computes conditional values inside a query; `COALESCE` selects the first non-null value; `NULLIF` turns two equal values into null, which is especially handy for normalizing blanks or preventing division by zero. String, numeric, date/time, collection, and aggregate functions expand JPQL's data-processing capabilities.

When using these expressions in Spring Data JPA, understand result types, SQL three-valued logic, database null handling, and the impact of column functions on indexes. Prefer standard JPQL functions for portability, use DTOs when returning multiple expressions, and test on the actual database whenever queries depend on dialect or collation.
