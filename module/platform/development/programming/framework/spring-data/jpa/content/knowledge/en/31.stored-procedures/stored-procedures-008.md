# Testing Procedures on the Exact Target DBMS

## 1. Why test on the exact DBMS?

A stored procedure is a program stored and executed inside a database management system (DBMS). Spring Data JPA can invoke procedures via the **@Procedure** annotation or the **StoredProcedureQuery** API; JDBC can also invoke them via **CallableStatement**. However, SQL syntax, data types, parameters, execution privileges, how results are returned, and transaction behavior depend on the specific DBMS and version.

A test passing on H2 does not prove the procedure will run properly on PostgreSQL, MySQL, SQL Server, Oracle, or DB2. H2 has its own parser, data types, functions, transaction rules, and procedure support. Certain statements may succeed in H2 but fail on the target DBMS; a feature specific to the target DBMS may also not exist in H2.

Testing principles:

- Run integration tests against the same DBMS family used in production.
- Match the version, image, extensions, and key configuration settings as closely as possible.
- Use the exact JDBC driver and SQL migrations deployed to production.
- Verify both the Java invocation and the actual state in the database.
- Verify application account privileges, transactions, errors, and boundary cases.

**Examples in this lesson:** the illustrative code uses PostgreSQL 16 and Testcontainers. This is a concrete example for hands-on practice; if your system runs MySQL, SQL Server, Oracle, or another PostgreSQL version, substitute the image, driver, DDL, and configuration to match your production environment. The prompt does not prescribe a project DBMS, so PostgreSQL in the examples is not an assumption about your actual database.

## 2. Identify the exact environment to simulate

Before writing tests, gather details from deployment configs and DBAs/DevOps:

| Attribute | What to identify |
|---|---|
| DBMS | PostgreSQL, MySQL, MariaDB, SQL Server, Oracle, DB2... |
| Version | Running production version |
| JDBC driver | Driver and version used by the application |
| Schema/catalog | Schema containing procedures, tables, sequences, and types |
| Extensions/plugins | Required database extensions or features |
| Charset/collation | Comparison, sorting, and character encoding rules |
| Time zone | Server, session, and application time zones |
| Isolation | Isolation level and transaction settings |
| User/privileges | `EXECUTE` privileges and data permissions granted to the application account |
| SQL mode/settings | Compatibility modes and settings affecting syntax/behavior |

Verify the database version inside tests via JDBC metadata to avoid accidentally connecting to H2 or another database:

```java
try (Connection connection = dataSource.getConnection()) {
    DatabaseMetaData metadata = connection.getMetaData();

    assertEquals("PostgreSQL", metadata.getDatabaseProductName());
    System.out.println(metadata.getDatabaseProductVersion());
}
```

Adjust expected values for the actual DBMS. You can also check the server version using vendor-specific SQL, such as `SELECT version()` or `SHOW server_version` in PostgreSQL. Do not rely solely on the JDBC URL string: verify the metadata of the connection Spring actually uses.

## 3. Keep procedures in repeatable migrations

A stored procedure is a database schema object. Manage procedure DDL alongside table and type migrations, typically with Flyway or Liquibase. Tests must run these exact migrations before invoking procedures.

The example below is a PostgreSQL migration:

File: `src/main/resources/db/migration/V1__payment_audit.sql`

```sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE app.payment_audit (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    invoice_id VARCHAR(40) NOT NULL,
    amount NUMERIC(12, 2) NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE OR REPLACE PROCEDURE app.record_payment(
    IN p_invoice_id VARCHAR(40),
    IN p_amount NUMERIC(12, 2)
)
LANGUAGE plpgsql
AS $$
BEGIN
    IF p_invoice_id IS NULL OR p_amount IS NULL OR p_amount <= 0 THEN
        RAISE EXCEPTION 'amount must be positive';
    END IF;

    INSERT INTO app.payment_audit(invoice_id, amount)
    VALUES (p_invoice_id, p_amount);
END;
$$;
```

The procedure accepts an invoice ID and an amount, rejects null or non-positive amounts, and inserts a row into the audit table. The procedure does not self-commit the transaction; the caller's transaction determines when data is committed or rolled back.

In real projects:

- Place procedure migrations alongside the schema migrations they depend on.
- Use explicit schemas and object names; avoid implicit reliance on `search_path` or default schemas.
- If a procedure invokes functions, sequences, views, or other procedures, create those dependencies in migrations before creating the procedure.
- Verify `EXECUTE` privileges and permissions on tables used by the procedure.
- Do not use Hibernate `ddl-auto=create` as a replacement for procedure migrations. Hibernate generates entity schemas and is not a full DDL management tool for routines.
- When modifying a procedure signature, ensure migrations handle parameter types, overloads, grants, and active callers.

For MySQL, SQL Server, Oracle, and other DBMSs, write migrations in the corresponding syntax. For instance, PostgreSQL uses `CALL` to invoke procedures while functions are invoked with `SELECT`; SQL Server typically uses `EXEC`; MySQL uses `CALL`. You cannot merely swap the DBMS in the JDBC URL and expect the same SQL file to work everywhere.

## 4. Provision a real database with Testcontainers

Testcontainers spins up an ephemeral database inside a container, provides the JDBC URL, username, and password to tests, and cleans up the container after tests finish. This lets developers and CI run the same database type without sharing a fixed test database.

With Testcontainers 2.x and Gradle, you can declare test dependencies as follows:

```groovy
dependencies {
    testImplementation platform("org.testcontainers:testcontainers-bom:2.0.5")
    testImplementation "org.testcontainers:testcontainers-junit-jupiter"
    testImplementation "org.testcontainers:testcontainers-postgresql"
}
```

The application still needs the corresponding PostgreSQL JDBC driver, usually already present at runtime if production uses PostgreSQL. Testcontainers modules do not bring the JDBC driver onto the classpath automatically. Use the BOM so Testcontainers modules share the same version. If the project uses Testcontainers 1.x, dependencies and class packages differ from 2.x; upgrade together or stick consistently to the current version's API without mixing 1.x and 2.x artifacts.

Testcontainers 2.x uses the PostgreSQL container package **org.testcontainers.postgresql.PostgreSQLContainer**. The complete test later in this lesson uses JUnit Jupiter and Spring TestContext.

The `postgres:16.4-alpine` image is a reproducible example version. Replace it with the image and version matching production; in critical pipelines, you can pin a digest rather than a mutable tag. If production uses extensions such as PostGIS, pgvector, or a vendor-provided image, use a compatible image with the same extensions installed. If production runs on a managed database service with specific features a local image cannot replicate, supplement with integration tests on a test environment provided by the vendor or operations team.

**@DynamicPropertySource** registers dynamic URLs and connection credentials before Spring creates the `ApplicationContext`. If the application configures Flyway with separate URL/user/password properties (`spring.flyway.url`, `spring.flyway.user`, `spring.flyway.password`), also point Flyway to the same container database. Otherwise, the application may run migrations against a different database than the one the test calls.

Place migrations in the location production uses, such as `src/main/resources/db/migration`, so tests run the exact same migration set. If using Flyway, add the Flyway dependency and configure the datasource accordingly. You can set `spring.jpa.hibernate.ddl-auto=validate` to verify entity mappings against the schema created by migrations.

## 5. Calling procedures via Spring Data JPA with @Procedure

Spring Data JPA supports declaring procedures with **@Procedure** on repository methods. Procedure metadata can be declared directly on the method or via **@NamedStoredProcedureQuery** on an entity.

Example mapping the PostgreSQL procedure created above:

```java
import java.math.BigDecimal;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.NamedStoredProcedureQuery;
import jakarta.persistence.ParameterMode;
import jakarta.persistence.StoredProcedureParameter;
import jakarta.persistence.Table;

@Entity
@Table(name = "payment_audit", schema = "app")
@NamedStoredProcedureQuery(
    name = "PaymentAudit.recordPayment",
    procedureName = "app.record_payment",
    parameters = {
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_invoice_id",
            type = String.class
        ),
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_amount",
            type = BigDecimal.class
        )
    }
)
public class PaymentAudit {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    protected PaymentAudit() {
    }
}
```

Repository references the declared JPA name:

```java
import java.math.BigDecimal;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.query.Procedure;
import org.springframework.data.repository.query.Param;

public interface PaymentAuditRepository
        extends JpaRepository<PaymentAudit, Long> {

    @Procedure(name = "PaymentAudit.recordPayment")
    void recordPayment(
            @Param("p_invoice_id") String invoiceId,
            @Param("p_amount") BigDecimal amount
    );
}
```

The **@NamedStoredProcedureQuery** annotation has two distinct names:

- **name** is the JPA name used to reference the query in `EntityManager`/repositories.
- **procedureName** is the actual name of the procedure in the database.

Thus, `@Procedure(name = "PaymentAudit.recordPayment")` references the JPA metadata name, while `procedureName = "app.record_payment"` points to the database object. Using `@Procedure(procedureName = "...")` directly on a method references the database procedure directly and bypasses `@NamedStoredProcedureQuery` metadata.

Call the procedure in a service with explicit transactions:

```java
import java.math.BigDecimal;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class PaymentProcedureService {

    private final PaymentAuditRepository repository;

    public PaymentProcedureService(PaymentAuditRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void recordPayment(String invoiceId, BigDecimal amount) {
        repository.recordPayment(invoiceId, amount);
    }

    @Transactional
    public void recordThenFail(String invoiceId, BigDecimal amount) {
        repository.recordPayment(invoiceId, amount);
        throw new IllegalStateException("Force rollback for integration test");
    }
}
```

Placing transactions in the service makes it easy to verify that the procedure participates in the use case's transaction. Custom-declared repository query methods should not be assumed transactional merely because they sit on `JpaRepository`; transaction boundaries at the service layer clarify intent and allow coordinating multiple operations.

## 6. Verifying actual results in the database

A good test invokes the procedure through the exact path the application uses, then queries the database to confirm side effects or return values. Do not merely verify method invocations with Mockito.

Complete integration test example:

```java
import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.DatabaseMetaData;
import java.sql.SQLException;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.postgresql.PostgreSQLContainer;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;

@Testcontainers
@SpringBootTest
class PaymentProcedureIntegrationTest {

    @Container
    static final PostgreSQLContainer postgres =
            new PostgreSQLContainer("postgres:16.4-alpine")
                    .withDatabaseName("app")
                    .withUsername("app_user")
                    .withPassword("app_password");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private PaymentProcedureService service;

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @BeforeEach
    void cleanRows() {
        jdbcTemplate.update("DELETE FROM app.payment_audit");
    }

    @Test
    void connectsToTheExpectedDatabaseProduct() throws SQLException {
        try (Connection connection =
                     jdbcTemplate.getDataSource().getConnection()) {
            DatabaseMetaData metadata = connection.getMetaData();
            assertEquals("PostgreSQL", metadata.getDatabaseProductName());
        }
    }

    @Test
    void procedureInsertsAuditRow() {
        service.recordPayment("INV-100", new BigDecimal("25.50"));

        Integer count = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM app.payment_audit WHERE invoice_id = ?",
                Integer.class,
                "INV-100"
        );

        assertEquals(1, count);
    }

    @Test
    void procedureParticipatesInCallerTransaction() {
        assertThrows(
                IllegalStateException.class,
                () -> service.recordThenFail(
                        "INV-ROLLBACK", new BigDecimal("12.00"))
        );

        Integer count = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM app.payment_audit WHERE invoice_id = ?",
                Integer.class,
                "INV-ROLLBACK"
        );

        assertEquals(0, count);
    }
}
```

This test uses a static container for the class, injects datasource properties dynamically, cleans data before each test, confirms the DBMS, invokes the procedure, and verifies saved data. It requires the migrations creating the schema/procedure and the beans/entity/repository/service from the previous section. The test is not annotated with `@Transactional` so queries executed after the service returns observe committed results. The rollback test verifies that the insert performed by the procedure rolls back along with the service's transaction when an exception escapes.

If using `@DataJpaTest`, Spring Boot may replace the datasource with an embedded database depending on test configuration. When using Testcontainers, configure it to preserve the container datasource (for example `@AutoConfigureTestDatabase(replace = Replace.NONE)` if appropriate for your Boot version) and load migrations/procedure definitions. With `@SpringBootTest`, the datasource is normally picked up from application config and `DynamicPropertySource` can override URL/credentials.

## 7. Testing with JDBC when lower-level call control is needed

Not every procedure maps cleanly via `@Procedure`. When you need control over parameter types, `OUT`/`INOUT`, cursors, or driver-specific features, you can use JDBC `CallableStatement` or `JdbcTemplate`.

Example invoking a PostgreSQL procedure with only `IN` parameters via JDBC:

```java
import java.math.BigDecimal;
import java.sql.PreparedStatement;
import org.springframework.jdbc.core.ConnectionCallback;
import org.springframework.jdbc.core.JdbcTemplate;

public class PaymentProcedureJdbcClient {

    private final JdbcTemplate jdbcTemplate;

    public PaymentProcedureJdbcClient(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public void record(String invoiceId, BigDecimal amount) {
        jdbcTemplate.execute((ConnectionCallback<Void>) connection -> {
            try (PreparedStatement statement = connection.prepareStatement(
                    "CALL app.record_payment(?, ?)")) {
                statement.setString(1, invoiceId);
                statement.setBigDecimal(2, amount);
                statement.execute();
            }
            return null;
        });
    }
}
```

This is a PostgreSQL example using `CALL` for a procedure; do not use this syntax to call a PostgreSQL function, which is called in a `SELECT` expression. With other DBMSs, you may need `CallableStatement` with `{call ...}` escape syntax, `EXEC`, or driver-specific APIs. Always verify the invocation style in the documentation for the driver in use.

If a procedure has `OUT` parameters, `CallableStatement` generally requires registering data types before execution and reading values afterward. Syntax, registration order, and how `ResultSet`s are retrieved depend on the driver. Write tests for both return values and database side effects.

## 8. IN, OUT, INOUT, ResultSet, and cursors

A procedure can have multiple parameter types:

- **IN**: application passes a value in.
- **OUT**: procedure returns a value out.
- **INOUT**: accepts an initial value and returns a modified value.
- **REF_CURSOR/cursor**: returns a result set via the mechanism supported by the DBMS/driver.
- **ResultSet**: a procedure can return one or more result sets depending on the database and API.

With Spring Data JPA:

- If a procedure has a single `OUT` parameter, that value can be returned directly from the repository method.
- If multiple `OUT` parameters are declared in `@NamedStoredProcedureQuery`, Spring Data JPA can return a `Map` keyed by parameter name.
- If a procedure returns a `ResultSet`, `OUT` parameters may be ignored because a method has only one return value; when multiple `OUT` parameters are needed, a `Map` can be used with appropriate metadata.
- `REF_CURSOR` and cursor types have specific requirements from the JPA provider, dialect, and database. Do not assume one vendor's mapping works on another vendor.

Example metadata with `IN` and `OUT`:

```java
@NamedStoredProcedureQuery(
    name = "Invoice.calculateTotal",
    procedureName = "app.calculate_total",
    parameters = {
        @StoredProcedureParameter(
            mode = ParameterMode.IN,
            name = "p_invoice_id",
            type = Long.class
        ),
        @StoredProcedureParameter(
            mode = ParameterMode.OUT,
            name = "p_total",
            type = BigDecimal.class
        )
    }
)
@Entity
public class Invoice {
    @Id
    private Long id;
}
```

The repository can return the single `OUT` parameter:

```java
@Procedure(name = "Invoice.calculateTotal")
BigDecimal calculateTotal(@Param("p_invoice_id") Long invoiceId);
```

This is an illustrative JPA mapping example; procedure DDL and `OUT` parameter support must be written properly for the target DBMS. In PostgreSQL, `CALL` rules for `OUT` arguments depend on version: modern versions require providing the `OUT` parameter position in the `CALL` list (typically passing `NULL` in direct SQL); older versions have different restrictions. Verify syntax against the production version rather than relying on a generic SQL example.

## 9. DBMS differences to test

| Area | Example issues | How to test |
|---|---|---|
| Invocation syntax | `CALL`, `EXEC`, `SELECT` function, JDBC escape syntax | Call via the actual DBMS driver |
| Data types | `NUMBER`/`DECIMAL`, `UUID`, `JSON`, `ARRAY`, enum, date/time | Test round-trips and boundary values |
| Parameters | `IN`, `OUT`, `INOUT`, cursors, null | Check count, order, names, types, and values |
| Result sets | Single or multiple result sets, cursors | Check row count, column order, and returned types |
| Object names | Schema, catalog, case sensitivity, overloads | Call with qualified names, check search path |
| Privileges | `EXECUTE`, table privileges, definer/invoker | Run tests using an account matching the application |
| Transactions | Commit, rollback, savepoints, procedure-managed transactions | Check results after commit/rollback |
| Locking | Deadlocks, lock timeouts, isolation | Run multi-transaction scenarios where meaningful |
| Time | Time zone, timestamp precision, daylight saving | Test boundary time values |
| Collation | String comparison, accents, Unicode, sort order | Test Vietnamese data and special characters |
| Error handling | SQLState, vendor error codes, exception mapping | Trigger errors intentionally and verify Java exceptions |
| Migrations | DDL, overloads, grants, dependencies | Initialize an empty database solely via migrations |

PostgreSQL-specific examples:

- Procedures are created with `CREATE PROCEDURE` and invoked with `CALL`; functions are invoked with `SELECT`.
- `CALL` supports `OUT` parameters and returns a single result row containing `OUT` values according to PostgreSQL rules.
- Users require `EXECUTE` privilege on the procedure.
- If `CALL` executes inside an explicit transaction block, the procedure cannot execute transaction control commands such as `COMMIT` or `ROLLBACK` internally. A Spring service with `@Transactional` typically invokes the procedure within that transaction, so procedures with self-commit logic must be designed and invoked differently.
- Check schema qualification, `search_path`, and privileges of the executing user; a procedure existing does not mean the application user can invoke it.

These points vary across PostgreSQL versions and differ even more across DBMS families. Do not copy SQL or transaction assumptions verbatim from PostgreSQL to Oracle, SQL Server, or MySQL.

## 10. Designing a valuable test suite

An integration test suite for procedures should include the following groups:

| Test group | Example data/scenario | What to assert |
|---|---|---|
| Happy path | Valid parameters | Procedure runs, data/results are accurate |
| Boundary | Zero, negative, max amounts, max-length strings | Business rules and data types hold |
| Null/optional | Null parameters, parameters with defaults | Proper behavior with SQL `NULL` and defaults |
| OUT/INOUT | Input values and output results | Java receives exact expected types and values |
| Result set | 0 rows, 1 row, multiple rows | Mapping, ordering, and column types match |
| Constraints | Foreign key, unique, not-null | Database errors are handled appropriately |
| Transactions | Success, mid-way exception, rollback | Side effects follow transaction boundaries |
| Permissions | User lacking `EXECUTE` or table permissions | Permission errors surface as expected |
| Concurrency | Two calls updating the same record | Locking and isolation do not corrupt data |
| Version compatibility | Running on production version | SQL and procedure APIs are actually compatible |

You do not need to write every data combination for every procedure. Select test cases based on logic branches, data constraints, and procedure risks. For procedures updating balances, inventory, or payment statuses, include repeated calls, concurrent updates, and rollbacks to verify correctness.

If a procedure processes a batch, test empty batches, batches with failing items, processing order, idempotency, and partial error reporting. Do not assume the procedure rolls back the entire batch if it catches exceptions internally and continues.

## 11. Managing test data and repeatability

Testcontainers creates a fresh database for the container's lifecycle, but tests sharing a container can still share data. Prepare clean state explicitly:

- Run migrations from an empty database to confirm schemas and procedures can be created from scratch.
- Have each test create its own fixtures with unique identifiers or clean data in `@BeforeEach`.
- Clean tables in foreign-key dependency order; consider `TRUNCATE`/sequence resets per DBMS syntax.
- Do not rely on test execution order.
- Do not use production data or production secrets as fixtures.
- If tests run in parallel, avoid shared data keys; use separate schemas/databases or unique identifiers.
- If a procedure has side effects outside the database (sending email, calling APIs, publishing messages), control those dependencies in the test environment and verify side effects within proper boundaries.

You can use `@Sql` to load fixtures or clean up, provided scripts are compatible with the target DBMS. For procedures, migrations are generally better than `@Sql` because procedures are part of schema versioning and must be deployed identically to production.

If a procedure self-commits, writes to another database, or uses autonomous transactions, test-rollback cleanup is insufficient. Create identifiable test data and clean it up explicitly after tests, and verify external side effects outside the main transaction separately.

## 12. Running on CI

To make integration tests useful in pipelines:

1. Install a Docker-compatible runtime or configure Testcontainers Cloud/a supported runtime.
2. Pin the DB image, Testcontainers BOM, and JDBC driver.
3. Run migrations on an empty database.
4. Run integration tests with a dedicated test profile.
5. Collect container logs and SQLState/vendor codes when tests fail.
6. Ensure tests never accidentally point to production or shared databases.
7. If custom extensions or server configurations are required, version-control test images/configs.
8. Run a smaller subset on pull requests and the full suite on the main pipeline if database startup time is large.

Testcontainers requires a Docker API-compatible runtime or compatible container environment. If CI lacks Docker, use a pipeline-provisioned test database or a dedicated version-controlled integration environment. Never substitute H2 for the target database and mark procedure tests as verified on the production DBMS.

## 13. Distinguishing unit tests, repository tests, and integration tests

| Test type | Uses target database? | What does it catch? |
|---|---|---|
| Service unit test with mocked repository | No | Control flow, exception handling, service orchestration |
| Repository test with H2 | Not the production DBMS | Partial JPA mappings and portable SQL queries |
| Integration test with Testcontainers | Yes, if using the right image | Procedure syntax, driver, mappings, permissions, transactions, and real results |
| Test on managed DB environment matching production | Yes, close to deployment environment | Extensions, managed service settings, and differences hard to replicate in containers |

Test layers complement one another. Unit tests run fast and suit testing Java logic; integration tests against the right database type provide essential proof for vendor-dependent procedures. You do not need to move every unit test to Testcontainers, but do not use mocks or H2 as proof for stored procedures.

## 14. Common errors and fixes

| Error | Cause | Resolution |
|---|---|---|
| Procedure does not exist | Migration did not run, wrong schema, or wrong name | Check migration history, schema, and full procedure name |
| Function/procedure mismatch | Used `SELECT` for procedure or `CALL` for function | Identify the right routine type and DBMS syntax |
| Test passes on H2 but fails in production | Different SQL/dialect/data types | Run integration tests on the target DBMS |
| Insufficient execute privileges | Test runs as owner while application uses restricted user | Create a test role matching application permissions and check `GRANT`s |
| Wrong parameter count/order | JPA or JDBC mapping does not match procedure signature | Cross-check `IN`/`OUT`/`INOUT` metadata and JDBC types |
| OUT parameter returns null or wrong type | Provider/driver handles differently, wrong name or order | Write dedicated tests for each `OUT` parameter on the target driver |
| Data remains after test rollback | Procedure self-committed or side effect outside transaction | Check transaction control and design explicit cleanup |
| Procedure timeout or deadlock | Long locks, overlapping transactions, or missing indexes | Inspect execution plans, lock waits, and isolation on real DBMS |
| Flaky tests | Shared data, parallel tests, unpinned images | Isolate fixtures and pin environments |
| Flyway runs on wrong database | Datasource and Flyway have separate URLs | Point both to the same container |

When tests fail, record useful diagnostics: DBMS product/version, JDBC driver version, procedure name and schema, parameters (with sensitive data scrubbed), SQLState, vendor error code, migration version, and transaction context. Do not log passwords, tokens, or sensitive personal data.

## 15. Checklist before considering a procedure tested

- [ ] Test connects to the exact chosen DBMS and version.
- [ ] JDBC driver is the actual driver used by the application.
- [ ] Migrations create the schema, tables, and procedures from an empty database.
- [ ] Tests invoke the procedure via the exact API the application uses: `@Procedure`, `EntityManager`, or JDBC.
- [ ] Tests verify side effects/results by querying the database.
- [ ] `IN`, `OUT`, `INOUT`, nulls, data types, and `ResultSet`s are tested when used by the procedure.
- [ ] Test user has permissions matching the application account.
- [ ] Commit, rollback, and business errors are tested.
- [ ] Vendor dependencies like extensions, collation, time zones, and SQL modes are simulated when needed.
- [ ] CI has a compatible runtime and cannot accidentally connect to the production database.

## 16. Takeaways

- Stored procedures are DBMS-dependent; testing with H2 does not replace integration testing on the target database.
- Testcontainers lets you run a real database in a container, but you must pin the right image/version and configuration.
- Use production migrations to create procedures in tests; do not maintain two different SQL definitions for test and production.
- Verify Java calls, actual data, parameters, privileges, errors, and transactions.
- `@Procedure` is convenient for Spring Data JPA mapping; JDBC fits when granular control over drivers and parameters is needed.
- If the DBMS is a managed service or uses specific extensions, supplement with tests on a production-equivalent environment.
