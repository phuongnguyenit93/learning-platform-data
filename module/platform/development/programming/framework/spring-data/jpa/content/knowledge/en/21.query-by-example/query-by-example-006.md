# Searching, Counting, Checking Existence, and Paginating with Example

**Query by Example (QBE)** is a way to build dynamic queries from a sample object (probe). Instead of writing a repository method for each filter combination or manually assembling JPQL, the application creates an entity with the desired fields, configures matching rules with `ExampleMatcher`, and wraps them in an `Example<T>`.

Spring Data JPA provides searching, counting, existence checks, and pagination based on Example. QBE fits search screens with many optional filters where conditions are primarily value comparisons. When you need complex expressions, grouped OR conditions, value ranges, or collection queries, consider Specification, Criteria API, Querydsl, or JPQL.

## 1. What components make up QBE?

QBE has four main components:

1. **Probe**: domain object holding the values to search for. Populated fields become criteria according to nullability rules and the matcher.
2. **ExampleMatcher**: describes how to match, such as AND/OR, ignored fields, string matching, case-insensitivity, and null handling.
3. **Example**: combines the probe with the matcher into a query object.
4. **FetchableFluentQuery**: fluent API for customizing projections, sorting, limits, Page, Slice, Stream, or other result-fetching operations.

General flow:

```text
Search request
      |
      v
Create probe from valid filters
      |
      v
Configure ExampleMatcher
      |
      v
Example.of(probe, matcher)
      |
      +----------+-----------+------------+
      |          |           |            |
    findAll     count      exists      findOne
      |
      v
  Pageable / Sort
```

QBE does not require writing field names inside JPQL/SQL strings for basic conditions. However, when configuring matchers per property, you still use Java property paths such as `firstName` or `address.city`.

## 2. Repository must support QueryByExampleExecutor

`JpaRepository<T, ID>` extends `QueryByExampleExecutor<T>`, so standard Spring Data JPA repositories already have QBE methods:

```java
import org.springframework.data.jpa.repository.JpaRepository;

public interface PersonRepository
        extends JpaRepository<Person, Long> {
}
```

You do not need to redeclare `findAll(Example)`, `count(Example)`, `exists(Example)`, or `findOne(Example)`.

Core methods:

```java
<S extends T> Optional<S> findOne(Example<S> example);

<S extends T> Iterable<S> findAll(Example<S> example);

<S extends T> Iterable<S> findAll(Example<S> example, Sort sort);

<S extends T> Page<S> findAll(
    Example<S> example,
    Pageable pageable
);

<S extends T> long count(Example<S> example);

<S extends T> boolean exists(Example<S> example);
```

In the `QueryByExampleExecutor` contract, `findAll(Example)` and `findAll(Example, Sort)` return `Iterable`. Use the exact types matching the interface and Spring Data version in use; if a List is needed, you can convert the result or declare an appropriate return type in the application layer.

## 3. Creating an entity as a probe

Example Person entity:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "people")
public class Person {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "first_name")
    private String firstName;

    @Column(name = "last_name")
    private String lastName;

    private String city;

    private Integer age;

    private Boolean active;

    protected Person() {
    }

    public Long getId() {
        return id;
    }

    public String getFirstName() {
        return firstName;
    }

    public void setFirstName(String firstName) {
        this.firstName = firstName;
    }

    public String getLastName() {
        return lastName;
    }

    public void setLastName(String lastName) {
        this.lastName = lastName;
    }

    public String getCity() {
        return city;
    }

    public void setCity(String city) {
        this.city = city;
    }

    public Integer getAge() {
        return age;
    }

    public void setAge(Integer age) {
        this.age = age;
    }

    public Boolean getActive() {
        return active;
    }

    public void setActive(Boolean active) {
        this.active = active;
    }
}
```

To create a search example, construct a probe with only the needed criteria populated:

```java
Person probe = new Person();
probe.setFirstName("An");
probe.setCity("Da Nang");
probe.setActive(true);
```

Properties `lastName`, `age`, and `id` remain null. By default, QBE ignores properties with null values, so they do not become search conditions.

The expected logical result is:

```sql
WHERE first_name = 'An'
  AND city = 'Da Nang'
  AND active = TRUE
```

This is a logical illustration. Actual SQL generated by the provider may use bind parameters, aliases, and database-specific syntax.

### 3.1. Be careful with primitive types

QBE determines whether a field is included in conditions based on nullability. Reference fields with null values are typically ignored. Primitive fields like `int`, `long`, and `boolean` always have default values and are therefore always considered populated, unless ignored in the matcher.

Example:

```java
private boolean active;
private int age;
```

A newly created probe has `active = false` and `age = 0`. QBE can treat these as real search conditions even though the user never selected them.

For optional filters, use wrapper types:

```java
private Boolean active;
private Integer age;
```

When active or age is not selected, leave it null. When the user chooses false or 0, that value is accurately represented and can become a search criterion.

Also pay attention to technical fields such as id, version, or creation timestamp. If the probe holds values in those fields, exclude them from the matcher with `withIgnorePaths(...)` when they are not business criteria.

## 4. Example.of() with the default matcher

Creating a simple Example:

```java
Person probe = new Person();
probe.setFirstName("An");

Example<Person> example = Example.of(probe);
```

`Example.of(probe)` uses the default matcher:

- Null fields are ignored.
- Non-null fields are used as conditions.
- Conditions are combined with AND by default.
- Strings use the store/provider default matching mode; in typical setups this is exact match and case-sensitive.
- Non-string types are matched by exact equality.

Because string behavior can depend on the store and database, configure the matcher explicitly when business requirements need starts-with, contains, or case-insensitivity.

You can create an Example with an explicit matcher:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll();

Example<Person> example = Example.of(probe, matcher);
```

`matchingAll()` clearly expresses that every populated condition in the probe must hold true together. `matching()` is also commonly used for the default AND mode.

## 5. ExampleMatcher: configuring matching behavior

`ExampleMatcher` lets you set global rules and per-property-path rules.

Example:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIgnorePaths("id", "age")
    .withIgnoreCase()
    .withStringMatcher(
        ExampleMatcher.StringMatcher.CONTAINING
    );
```

Meaning:

- `matchingAll()`: conditions are combined with AND.
- `withIgnorePaths("id", "age")`: do not use id and age as conditions.
- `withIgnoreCase()`: match strings case-insensitively.
- `CONTAINING`: the string in the probe must appear anywhere within the stored value.

If the probe has `firstName = "an"` and `city = "da"`, the conceptual string conditions are:

```sql
LOWER(first_name) LIKE '%an%'
AND LOWER(city) LIKE '%da%'
```

Exact SQL syntax depends on the database/provider. Case-insensitive matching can affect regular index usage; if the query is critical, inspect the execution plan and consider an appropriate collation or functional index.

### 5.1. StringMatcher modes

Commonly used modes:

| StringMatcher | Meaning | Example with probe "An" |
|---|---|---|
| EXACT | Match the whole string | "An" |
| STARTING | String starts with probe value | "An Nguyen" |
| ENDING | String ends with probe value | "Tran An" |
| CONTAINING | String contains probe value | "Nguyen An Binh" |
| DEFAULT | Uses store default behavior | Depends on store/provider |
| REGEX | Regular expression in some stores | Not supported by Spring Data JPA for QBE |

JPA does not support regex matching in QBE. Do not configure `REGEX` expecting Hibernate to generate portable regex queries.

### 5.2. Configuring per-field matchers

Not every string should share the same rule. For example, firstName needs starts-with, lastName needs contains, and city needs exact:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIgnorePaths("id", "age")
    .withMatcher(
        "firstName",
        property -> property.startsWith().ignoreCase()
    )
    .withMatcher(
        "lastName",
        property -> property.contains().ignoreCase()
    )
    .withMatcher(
        "city",
        property -> property.exact().ignoreCase()
    );
```

Property-path-specific configurations take precedence over matcher-level defaults. That allows setting a global rule while overriding only fields that need different behavior.

Property names must be Java property names, not database column names. In the example, `firstName` is used even though the physical column is `first_name`.

### 5.3. Ignoring specific properties

Use `withIgnorePaths` when the probe contains fields that must not become conditions:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIgnorePaths("id", "createdAt", "updatedAt", "version");
```

This is useful when probes come from entities with many technical fields. Even though null fields are usually ignored, ignoring paths ensures they never accidentally become criteria if populated.

### 5.4. Case-insensitivity

Can be applied to all strings:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIgnoreCase();
```

Or only specific properties:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withMatcher(
        "firstName",
        property -> property.exact().ignoreCase()
    );
```

Case-insensitivity is usually implemented by normalizing comparison expressions in the database, such as using LOWER. Behavior depends on collation and the database; test with Unicode/Vietnamese data if your application has language-specific search requirements.

## 6. matchingAll() and matchingAny()

By default, QBE combines criteria with AND. Example:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll();
```

If the probe has firstName = "An" and city = "Da Nang", results must satisfy both:

```sql
WHERE first_name = 'An'
  AND city = 'Da Nang'
```

Use `matchingAny()` to combine populated predicates with OR:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAny()
    .withIgnorePaths("id");
```

With probe firstName = "An", city = "Da Nang", the logic becomes:

```sql
WHERE first_name = 'An'
   OR city = 'Da Nang'
```

matchingAny is useful for broad searches, such as finding people whose name or city matches a value.

**Important limitation:** QBE cannot express arbitrary nested AND/OR condition groups, such as:

```sql
WHERE first_name = 'An'
   OR (city = 'Da Nang' AND active = TRUE)
```

`matchingAny()` only changes how predicates generated from the probe are combined; it does not provide a boolean expression tree for arbitrary grouping. For complex logic like this, use Specification, Criteria API, Querydsl, or JPQL.

## 7. Null handling: ignore null or search for NULL values?

By default, QBE ignores null fields. Example:

```java
Person probe = new Person();
probe.setCity("Da Nang");
// active remains null

Example<Person> example = Example.of(probe);
```

Only city is used as a condition. QBE does not automatically generate `active IS NULL` for the active field.

If you want null fields to become conditions matching NULL columns, configure:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIncludeNullValues()
    .withIgnorePaths("id");

Example<Person> example = Example.of(probe, matcher);
```

Then null properties are included in criteria according to the matcher's null handling. Use this very carefully: entities often have many nullable fields, and including null values can generate many unintended IS NULL conditions.

If the requirement is to find people with a NULL city while still filtering active = true, consider creating a dedicated probe/matcher with suitable ignore paths or using Specification/JPQL to express the condition clearly. Do not enable includeNullValues on a large entity without controlling which fields enter the query.

A null parameter also does not mean "skip filter" in every context. QBE ignores null by default because of ExampleMatcher's null handling; that is a QBE rule, not a universal rule across all Spring Data queries.

## 8. Searching with findAll(Example)

Repository example:

```java
public interface PersonRepository
        extends JpaRepository<Person, Long> {
}
```

Service creates the probe and retrieves all results:

```java
@Service
public class PersonSearchService {

    private final PersonRepository repository;

    public PersonSearchService(PersonRepository repository) {
        this.repository = repository;
    }

    @Transactional(readOnly = true)
    public Iterable<Person> search(String firstName, String city) {
        Person probe = new Person();
        probe.setFirstName(firstName);
        probe.setCity(city);

        ExampleMatcher matcher = ExampleMatcher.matchingAll()
            .withIgnorePaths("id", "age");

        Example<Person> example = Example.of(probe, matcher);

        return repository.findAll(example);
    }
}
```

If no records match, `findAll(example)` returns an empty Iterable. There is no need to check for a null result.

Do not use `findAll(example)` on tables that could return huge numbers of rows without limits. This is an unpaginated query; consider Page or Slice for large datasets.

## 9. Counting with count(Example)

You can count entities matching the same probe/matcher:

```java
long count = repository.count(example);
```

Example:

```java
@Transactional(readOnly = true)
public long countActivePeopleInCity(String city) {
    Person probe = new Person();
    probe.setCity(city);
    probe.setActive(true);

    ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnorePaths("id", "age");

    return repository.count(Example.of(probe, matcher));
}
```

`count(example)` returns a `long` without loading full entities just to count them. The database still must run a count query for the corresponding conditions; performance depends on row count, indexes, selectivity, and joins produced by mappings.

If you only need to know whether at least one result exists, use `exists(example)` instead of counting everything and comparing against 0.

## 10. Checking existence with exists(Example)

Method:

```java
boolean exists = repository.exists(example);
```

returns true if at least one entity matches and false otherwise.

Example checking if there is an active person in a city:

```java
@Transactional(readOnly = true)
public boolean hasActivePerson(String city) {
    Person probe = new Person();
    probe.setCity(city);
    probe.setActive(true);

    Example<Person> example = Example.of(
        probe,
        ExampleMatcher.matchingAll().withIgnorePaths("id", "age")
    );

    return repository.exists(example);
}
```

Do not use `count(example) > 0` when the goal is only existence. exists states the intent clearly and gives the provider/database a chance to optimize the query for a boolean check.

A QBE existence check also does not replace unique constraints. If you need to guarantee a property is unique, place a constraint/index in the database and handle concurrency conflicts in the service.

## 11. Finding one result with findOne(Example)

`findOne(example)` returns `Optional<T>`:

```java
Optional<Person> person = repository.findOne(example);
```

- No result: Optional.empty().
- Exactly one result: Optional containing the entity.
- More than one result: throws `IncorrectResultSizeDataAccessException`.

Therefore, only use findOne when the probe conditions guarantee uniqueness via business rules or database constraints. Do not use it as an arbitrary way to grab the first record out of many matches.

If you want to fetch the first ordered result, use the fluent API with `first()` and sort:

```java
Optional<Person> first = repository.findBy(
    example,
    query -> query
        .sortBy(Sort.by(Sort.Order.asc("lastName"), Sort.Order.asc("id")))
        .first()
);
```

The sort includes id as a tie-breaker so results have a deterministic order when lastName values collide.

## 12. Paginating with findAll(Example, Pageable)

QBE supports Page directly:

```java
Pageable pageable = PageRequest.of(
    0,
    20,
    Sort.by(
        Sort.Order.asc("lastName"),
        Sort.Order.asc("id")
    )
);

Page<Person> page = repository.findAll(example, pageable);
```

Commonly used information:

```java
List<Person> content = page.getContent();
int pageNumber = page.getNumber();
int pageSize = page.getSize();
long totalElements = page.getTotalElements();
int totalPages = page.getTotalPages();
boolean hasNext = page.hasNext();
```

`Page` provides both content and total element/page metadata. To calculate totals, the provider may need to run a count query in addition to the page content query. If the UI only needs to know whether a next page exists, consider the fluent QBE API with Slice to avoid requiring a total count.

An endpoint can accept Pageable:

```java
@GetMapping("/people")
public Page<PersonResponse> search(
        @PageableDefault(size = 20, sort = "id") Pageable pageable,
        PersonSearchRequest request
) {
    return personSearchService.search(request, pageable);
}
```

In the service, map the request DTO to a probe and matcher, then call `findAll(example, pageable)`. Do not bind the entire entity directly from the request if the entity has internal fields like id, version, tenant, or administrative status. Map only filters allowed by the API.

Page size and sorting still need to be bounded in the web/service layer according to API policy. QBE does not automatically protect the application from overly large page sizes or disallowed sort fields.

## 13. Sorting with findAll(Example, Sort)

If pagination is not needed but sorting is:

```java
Iterable<Person> people = repository.findAll(
    example,
    Sort.by(
        Sort.Order.asc("lastName"),
        Sort.Order.asc("id")
    )
);
```

Sort uses Java properties, such as `lastName`, not column names like `last_name`. Restrict sort fields using an allowlist if Sort comes from an HTTP request. A stable sort should have a unique key as the final criterion.

`findAll(example, sort)` still returns all matching results; Sort does not limit row count. For large datasets, use Pageable or the fluent API with a limit.

## 14. Fluent QBE API with findBy()

Since Spring Data 2.6, `QueryByExampleExecutor` provides `findBy(example, queryFunction)`. This API allows configuring projection, sort, limit, Page, Slice, Window, Stream, count, and exists within one callback.

Example fetching a projected Page:

```java
public interface PersonSummary {
    String getFirstName();
    String getLastName();
    String getCity();
}
```

Execution:

```java
Page<PersonSummary> page = repository.findBy(
    example,
    query -> query
        .as(PersonSummary.class)
        .page(PageRequest.of(
            0,
            20,
            Sort.by("lastName")
        ))
);
```

`as(PersonSummary.class)` selects the projection result type. This is useful when a screen only needs a few fields and does not need to hydrate the entire entity graph.

You can limit results:

```java
List<PersonSummary> topTen = repository.findBy(
    example,
    query -> query
        .as(PersonSummary.class)
        .sortBy(Sort.by("lastName").ascending())
        .limit(10)
        .all()
);
```

You can use Slice:

```java
Slice<Person> slice = repository.findBy(
    example,
    query -> query.slice(
        PageRequest.of(0, 50, Sort.by("id").ascending())
    )
);
```

Or count/check existence using fluent query:

```java
long total = repository.findBy(example, query -> query.count());

boolean any = repository.findBy(example, query -> query.exists());
```

The fluent query object is only valid inside the `findBy` callback. The callback must return a terminal result such as Page, Slice, List, Optional, count, or exists; do not return the query object itself for use after the callback finishes.

For simple needs, calling `count(example)`, `exists(example)`, and `findAll(example, pageable)` directly is often easier to read. Use the fluent API when you need projections, limits, sorting, or flexible result types.

## 15. Nested property paths

QBE can configure nested property paths using dot notation, such as `address.city`. For an entity with an embedded value:

```java
@Embeddable
public class Address {

    private String city;

    protected Address() {
    }

    public String getCity() {
        return city;
    }

    public void setCity(String city) {
        this.city = city;
    }
}

@Entity
public class Person {

    @Id
    @GeneratedValue
    private Long id;

    @Embedded
    private Address address;

    // Other fields and accessors
}
```

Creating the probe:

```java
Person probe = new Person();
Address address = new Address();
address.setCity("Da Nang");
probe.setAddress(address);

ExampleMatcher matcher = ExampleMatcher.matchingAll()
    .withIgnorePaths("id")
    .withMatcher(
        "address.city",
        property -> property.exact().ignoreCase()
    );

Example<Person> example = Example.of(probe, matcher);
```

The matcher name is the Java property path `address.city`. This is a condition on a simple nested property. QBE does not support arbitrary grouped expressions or matching on collections/maps; for complex relationships, verify your specific provider and mapping.

## 16. Mapping search requests to probes safely

In real APIs, use a dedicated DTO for search criteria:

```java
public record PersonSearchRequest(
    String firstName,
    String lastName,
    String city,
    Boolean active,
    Integer age
) {
}
```

Service creates the probe from allowed fields:

```java
@Transactional(readOnly = true)
public Page<Person> search(
        PersonSearchRequest request,
        Pageable pageable
) {
    Person probe = new Person();

    if (request.firstName() != null
            && !request.firstName().isBlank()) {
        probe.setFirstName(request.firstName().trim());
    }

    if (request.lastName() != null
            && !request.lastName().isBlank()) {
        probe.setLastName(request.lastName().trim());
    }

    if (request.city() != null && !request.city().isBlank()) {
        probe.setCity(request.city().trim());
    }

    probe.setActive(request.active());
    probe.setAge(request.age());

    ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnorePaths("id")
        .withMatcher(
            "firstName",
            property -> property.startsWith().ignoreCase()
        )
        .withMatcher(
            "lastName",
            property -> property.contains().ignoreCase()
        )
        .withMatcher(
            "city",
            property -> property.exact().ignoreCase()
        );

    Example<Person> example = Example.of(probe, matcher);

    return repository.findAll(example, pageable);
}
```

The example assumes the repository has the corresponding entity fields and accessors. In real projects, validate page size/sort before calling the repository, and populate only fields exposed by the public API into the probe.

Empty strings are not the same as null. Because QBE ignores null by default rather than ignoring blank strings by default, normalize the request before setting the probe. Otherwise, an empty string can become an unintended search condition.

Do not let clients submit arbitrary property matcher names directly. Property paths and matching rules should be controlled by the application to avoid overly expensive queries or accidental filtering by internal fields.

## 17. What does QBE not support?

QBE intentionally keeps its API simple. Important limitations:

| Requirement | QBE | Alternative |
|---|---|---|
| Field equals value | Yes | QBE |
| String exact/starts/ends/contains | Yes, depends on database/provider | QBE or JPQL |
| Case-insensitive matching | Yes | QBE, test collation/index |
| AND between fields | Yes by default | QBE |
| OR across top-level predicates | Yes with matchingAny | QBE |
| Arbitrary nested AND/OR groups | No | Specification, Criteria, Querydsl, JPQL |
| Greater-than/less-than/between conditions | Not directly | Specification, Querydsl, JPQL |
| Collection or Map matching | No | Join query, Specification, Querydsl |
| Regex in Spring Data JPA QBE | Not supported | Database-specific query if truly needed |
| Aggregate/group by/having | Not suitable | JPQL/native SQL |
| Complex subqueries and EXISTS | Not suitable | Specification, JPQL, Querydsl |

QBE is very handy when conditions are just sample values. It is not a language for constructing every kind of SQL expression.

## 18. When to choose Specification instead of QBE?

Suppose a search screen needs these conditions:

- status belongs to a set of statuses.
- totalAmount is within a min/max range.
- createdAt falls within a date range.
- customer name contains a string.
- there must be at least one OrderItem matching a condition.
- conditions grouped as `A AND (B OR C)`.

QBE does not express these operators, joins, and boolean groups well. Spring Data JPA Specification lets you build predicates with Criteria API:

```java
public static Specification<Person> cityIs(String city) {
    return (root, query, cb) ->
        city == null
            ? cb.conjunction()
            : cb.equal(root.get("city"), city);
}
```

Specifications can be combined with `and()` and `or()`. Querydsl is also a good fit when you want compile-time type-checked expressions. For fixed, readable queries, JPQL `@Query` remains a solid choice.

Choose QBE when a probe naturally represents the filters. Switch to Specification/Querydsl/JPQL when you have to write logic that a probe cannot express.

## 19. Performance and indexes

QBE is a way to construct queries, not a mechanism that makes queries automatically faster. Performance depends on generated SQL, the number of conditioned fields, string matching type, indexes, matching row counts, and execution plans.

Key notes:

- Exact matches on indexed fields are usually easier to optimize than contains.
- `CONTAINING` typically produces patterns with wildcards on both sides, so standard B-tree indexes may not help effectively.
- Ignore case can cause queries to use LOWER expressions; standard indexes may not be used unless the database has a matching functional index or collation.
- Page requires total metadata and can trigger a count query.
- Projections reduce fetched columns and loaded object graphs.
- Do not call `findAll(example)` on large tables without a limit.
- Inspect SQL and execution plans on the real production database.

Example index for exact search by city and active:

```sql
CREATE INDEX idx_people_city_active
    ON people (city, active);
```

This is only an example. Index column order and index creation depend on workload, selectivity, database, and other queries. Do not create an index solely because a field appears in a probe.

## 20. Testing QBE

Important behaviors should be tested:

1. Probe with only one field: only that field is used as a condition.
2. Probe with multiple fields: matchingAll requires all conditions to hold together.
3. matchingAny: one of the conditions is enough to match.
4. Null fields are ignored by default.
5. withIncludeNullValues creates conditions for null fields according to the matcher.
6. Primitive fields with default values can still be included in the query.
7. IgnorePaths excludes technical fields such as id/version.
8. StringMatcher EXACT, STARTING, ENDING, and CONTAINING work as expected.
9. IgnoreCase works properly against real data and collations.
10. count/exists return consistent results for the same Example.
11. findOne returns Optional.empty or the entity, and errors when multiple results exist.
12. Page returns accurate content, sorting, and metadata.
13. Fluent projections return only required fields.
14. Requests with blank strings are normalized per API policy.

Repository test example:

```java
@DataJpaTest
class PersonRepositoryQbeTest {

    @Autowired
    PersonRepository repository;

    @Test
    void searchesCountsAndChecksExistenceUsingSameExample() {
        Person first = new Person();
        first.setFirstName("An");
        first.setCity("Da Nang");
        first.setActive(true);

        Person second = new Person();
        second.setFirstName("Binh");
        second.setCity("Da Nang");
        second.setActive(true);

        Person third = new Person();
        third.setFirstName("An");
        third.setCity("Hue");
        third.setActive(false);

        repository.saveAll(List.of(first, second, third));
        repository.flush();

        Person probe = new Person();
        probe.setCity("Da Nang");
        probe.setActive(true);

        Example<Person> example = Example.of(
            probe,
            ExampleMatcher.matchingAll().withIgnorePaths("id", "age")
        );

        assertThat(repository.count(example)).isEqualTo(2);
        assertThat(repository.exists(example)).isTrue();
        assertThat(repository.findAll(example)).hasSize(2);
    }
}
```

This is an illustrative test skeleton; the entity needs constructors/accessors matching your project. The test reuses the same Example across three operations to confirm predicates are applied consistently.

Pagination tests can verify:

```java
Page<Person> page = repository.findAll(
    example,
    PageRequest.of(0, 1, Sort.by("id").ascending())
);

assertThat(page.getContent()).hasSize(1);
assertThat(page.getTotalElements()).isEqualTo(2);
assertThat(page.hasNext()).isTrue();
```

If using database-specific collations or string functions, add integration tests against the same database engine used in production.

## 21. Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| No records found even though probe only sets name | Another primitive field holds its default value and enters the condition | Use wrappers or ignore the field |
| Empty results when probe has multiple fields | matchingAll requires all fields to match by default | Inspect the probe and use matchingAny if business logic is OR |
| Case-insensitive string search behaves unexpectedly | ignoreCase not enabled or collation differs from expectations | Configure the matcher explicitly and test the database |
| Empty string becomes a condition | Only null is ignored by default | Trim/normalize requests and do not set blank strings |
| Searching for NULL fields yields no results | Null is ignored by default | Use includeNullValues with control or write a separate query |
| findOne throws IncorrectResultSizeDataAccessException | Multiple rows match the probe | Use List/Page or guarantee unique conditions |
| QBE cannot filter age ranges | QBE uses exact matching for non-string types | Use Specification/Querydsl/JPQL |
| Cannot write A AND (B OR C) | QBE does not support arbitrary grouped predicates | Use Specification or Criteria |
| Regex does not work | JPA QBE does not support regex matching | Use a database-specific query if needed |
| Query slow with CONTAINING | Wildcards on both sides struggle to use B-tree indexes | Measure execution plans and consider a search strategy |
| Page slow due to count | Page requires total count metadata | Use Slice if total is not needed |
| Sorting by internal fields | Passing client Sort straight to the repository | Use a sort allowlist in the API |

**Guiding principle:** create probes from permitted filters, use ExampleMatcher to define null/string/AND-OR behavior, and reuse Example across search, count, exists, and pagination. QBE suits simple matching conditions; when you need ranges, collections, subqueries, or complex AND/OR groups, switch to Specification, Querydsl, or JPQL.
