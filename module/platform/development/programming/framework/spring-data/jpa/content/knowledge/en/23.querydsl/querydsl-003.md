# Building Type-Safe Predicates with Q-Types in Spring Data JPA

Querydsl is a library for building queries with a compile-time type-safe Java API. With Spring Data JPA, Querydsl generates Q-type classes from entities. Instead of writing property names as strings like name or createdAt, query code references the corresponding typed properties directly, such as QCustomer.customer.name and QCustomer.customer.createdAt.

Q-types enable IDE autocomplete and allow the compiler to catch many wrong property names or data type errors before the application runs. A Querydsl Predicate can be passed to Spring Data's QuerydslPredicateExecutor or used with JPAQueryFactory to build custom queries.

This lesson explains Q-type generation, annotation processor configuration for Jakarta Persistence, typed expressions, combining optional conditions, relationship and collection queries, repository integration, custom queries, web binding, pagination, testing, and limitations to keep in mind.

## 1. Querydsl and Type-Safe Predicates

Querydsl provides a DSL for expressing query conditions using Java objects. A Predicate is a Boolean expression that can be used in a WHERE clause.

Example with the Customer entity:

~~~java
QCustomer customer = QCustomer.customer;

Predicate predicate = customer.name.eq("Linh")
    .and(customer.enabled.isTrue());
~~~

The predicate means:

- name equals Linh.
- enabled equals true.

There is no need to manually concatenate JPQL or SQL strings. Querydsl uses Q-type metadata to know property names and data types; Querydsl JPA translates the expression into a query suitable for the JPA provider.

An expression can be stored in a variable, combined with other expressions, passed to a repository, or used inside JPAQueryFactory.

## 2. How Are Q-Types Generated from Entities?

A Q-type is a Java class generated by Querydsl's annotation processor during compilation. For the Customer entity, the processor generates the QCustomer class.

Entity:

~~~java
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private String email;

    private Integer age;

    private Boolean enabled;

    @Enumerated(EnumType.STRING)
    private CustomerStatus status;

    private LocalDate birthDate;

    private LocalDateTime createdAt;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "address_id")
    private Address address;

    @OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
    private List<Order> orders = new ArrayList<>();

    private Long tenantId;

    protected Customer() {
    }

    public Customer(
            String name,
            String email,
            Integer age,
            Boolean enabled,
            CustomerStatus status) {
        this.name = name;
        this.email = email;
        this.age = age;
        this.enabled = enabled;
        this.status = status;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }

    public Integer getAge() {
        return age;
    }

    public Boolean getEnabled() {
        return enabled;
    }

    public CustomerStatus getStatus() {
        return status;
    }

    public LocalDate getBirthDate() {
        return birthDate;
    }

    public LocalDateTime getCreatedAt() {
        return createdAt;
    }

    public Address getAddress() {
        return address;
    }

    public List<Order> getOrders() {
        return orders;
    }

    public Long getTenantId() {
        return tenantId;
    }
}
~~~

Enum:

~~~java
public enum CustomerStatus {
    NEW,
    ACTIVE,
    SUSPENDED
}
~~~

The later Q-type examples also use two related entity types. Their property declarations are part of the same model: Address exposes city and countryCode; Order exposes status and its customer association. Keep each public type in its own Java source file.

~~~java
@Entity
@Table(name = "addresses")
public class Address {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String city;

    private String countryCode;

    protected Address() {
    }
}
~~~

~~~java
@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "customer_id")
    private Customer customer;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    protected Order() {
    }
}
~~~

~~~java
public enum OrderStatus {
    NEW,
    PAID,
    CANCELLED
}
~~~

After annotation processing runs, Querydsl generates the QCustomer class with corresponding paths:

- id is NumberPath<Long>.
- name and email are StringPath.
- age is NumberPath<Integer>.
- enabled is BooleanPath.
- status is EnumPath<CustomerStatus>.

Generated class names and details are managed by the processor. Do not write or edit QCustomer by hand. If the entity changes, run compile to regenerate the Q-type.

## 3. How Q-Types Differ from the JPA Static Metamodel

The JPA Criteria API often uses static metamodel classes with an underscore suffix, such as Customer_. Querydsl uses Q-types, such as QCustomer.

| Characteristic | JPA static metamodel | Querydsl Q-type |
|---|---|---|
| Example | Customer_.name | QCustomer.customer.name |
| Query API | CriteriaBuilder/CriteriaQuery | Querydsl Predicate and query DSL |
| Representation | SingularAttribute/SetAttribute | StringPath, NumberPath, EntityPath, CollectionPath |
| Combining conditions | CriteriaBuilder.and/or | BooleanExpression, BooleanBuilder |
| Code generation | JPA metamodel processor | Querydsl annotation processor |

Both help avoid using arbitrary property names as strings in queries. Querydsl provides its own DSL, while the JPA static metamodel works directly with the standard Criteria API.

Do not confuse QCustomer with the Customer entity. QCustomer is metadata for building queries; it is not an entity persisted in the persistence context.

## 4. Adding Dependencies for Spring Boot 3 and Jakarta Persistence

Spring Boot 3 / Spring Data JPA 3 uses the jakarta.persistence namespace. Querydsl needs artifacts with the jakarta classifier so the annotation processor recognizes Jakarta annotations properly.

Maven example using Querydsl 5.1.0:

~~~xml
<dependencies>
    <dependency>
        <groupId>com.querydsl</groupId>
        <artifactId>querydsl-jpa</artifactId>
        <version>5.1.0</version>
        <classifier>jakarta</classifier>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>com.querydsl</groupId>
                        <artifactId>querydsl-apt</artifactId>
                        <version>5.1.0</version>
                        <classifier>jakarta</classifier>
                    </path>
                    <path>
                        <groupId>jakarta.persistence</groupId>
                        <artifactId>jakarta.persistence-api</artifactId>
                        <version>3.1.0</version>
                    </path>
                    <path>
                        <groupId>jakarta.annotation</groupId>
                        <artifactId>jakarta.annotation-api</artifactId>
                        <version>2.1.1</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

Gradle example:

~~~groovy
dependencies {
    implementation("com.querydsl:querydsl-jpa:5.1.0:jakarta")

    annotationProcessor("com.querydsl:querydsl-apt:5.1.0:jakarta")
    annotationProcessor("jakarta.persistence:jakarta.persistence-api")
    annotationProcessor("jakarta.annotation:jakarta.annotation-api")
}
~~~

The versions in the examples illustrate one Jakarta configuration; use versions compatible with the Spring Boot, Spring Data JPA, and Hibernate ORM managed by your project. If your project's dependency management already provides the Jakarta APIs, avoid declaring conflicting versions.

For Spring Boot 2 / Spring Data JPA using javax.persistence, the Querydsl configuration must use the artifacts and annotation processor matching javax. Do not mix Q-types generated for javax with a Jakarta application or vice versa.

## 5. Running the Annotation Processor and Checking Q-Types

After adding the dependencies and annotation processor, run compile:

~~~bash
mvn clean compile
~~~

With Gradle:

~~~bash
./gradlew clean compileJava
~~~

Maven typically places generated sources in target/generated-sources/annotations; Gradle places them under build/generated/sources/annotationProcessor/java/main.

Verify:

- Whether QCustomer.java was generated.
- Whether the IDE recognizes the generated sources directory.
- Whether the Q-type accurately reflects the entity's properties.
- Whether the annotation processor recognizes Jakarta annotations.
- Whether the build uses the same Querydsl version at runtime and compile time.

Do not commit generated files unless your project convention requires it. Many projects commit only entities and processor configuration, generating Q-types on each build. Follow your repository's build policy.

When renaming or deleting an entity property, run a clean compile to remove stale Q-types and regenerate accurate metadata.

## 6. Reading Q-Types and Common Path Types

Q-types expose paths matching the Java type of each property:

| Entity property | Common Querydsl path | Example |
|---|---|---|
| String | StringPath | customer.name |
| Long/Integer | NumberPath | customer.id, customer.age |
| Boolean | BooleanPath | customer.enabled |
| Enum | EnumPath | customer.status |
| LocalDate | DatePath | customer.birthDate |
| LocalDateTime | DateTimePath | customer.createdAt |
| Entity association | EntityPath/Q-type | customer.address.city |
| Collection | ListPath/SetPath/CollectionPath | customer.orders |

Example:

~~~java
QCustomer customer = QCustomer.customer;

BooleanExpression nameMatches =
    customer.name.containsIgnoreCase("linh");

BooleanExpression ageMatches =
    customer.age.goe(18);

BooleanExpression active =
    customer.enabled.isTrue();

BooleanExpression statusMatches =
    customer.status.eq(CustomerStatus.ACTIVE);
~~~

Path types enable the compiler to verify valid methods. For instance, StringPath provides string comparison operations; NumberPath provides numeric comparisons; DateTimePath provides temporal comparisons.

Method names can vary by path type. Use IDE autocomplete or the API documentation for your project's Querydsl version to pick the right operation.

## 7. Basic Comparisons

Querydsl provides commonly used comparison expressions:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression exactName = c.name.eq("Linh");
BooleanExpression differentName = c.name.ne("Linh");

BooleanExpression ageAtLeast = c.age.goe(18);
BooleanExpression ageBelow = c.age.lt(65);

BooleanExpression createdAfter =
    c.createdAt.goe(startTime);

BooleanExpression createdBefore =
    c.createdAt.lt(endTime);
~~~

Common operations:

| Method | Meaning |
|---|---|
| eq(value) | Equal |
| ne(value) | Not equal |
| gt(value) | Greater than |
| goe(value) | Greater than or equal |
| lt(value) | Less than |
| loe(value) | Less than or equal |
| between(a, b) | Within range |
| in(values) | In value set |
| notIn(values) | Not in value set |

Some methods exist only on paths of compatible types. For example, gt/goe are typically available on Comparable or Number types and do not apply to every path.

## 8. String Conditions

StringPath provides string operations:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression exact = c.name.eq("Linh");
BooleanExpression contains = c.name.contains("linh");
BooleanExpression containsIgnoreCase =
    c.name.containsIgnoreCase("linh");

BooleanExpression starts =
    c.email.startsWithIgnoreCase("support");

BooleanExpression ends =
    c.email.endsWithIgnoreCase("@example.com");
~~~

Meaning:

- contains: substring search.
- containsIgnoreCase: case-insensitive substring search according to Querydsl/provider/database semantics.
- startsWith: prefix search.
- endsWith: suffix search.
- eq: exact comparison per database semantics.

Do not infer that IgnoreCase also means accent-insensitive (removing diacritics). Diacritic sensitivity, case folding, and Unicode behavior also depend on database collation and string handling. Test on the target database with realistic data.

contains operations typically generate LIKE patterns with wildcards at both ends; they may not effectively use standard B-tree indexes on large tables. Check the execution plan before using them for large-scale search.

## 9. NULL Must Use isNull and isNotNull

Querydsl should not use eq(null) or ne(null) to check for missing values. Use the dedicated methods:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression emailMissing = c.email.isNull();

BooleanExpression emailPresent = c.email.isNotNull();
~~~

Do not write:

~~~java
c.email.eq(null);
~~~

Querydsl typically rejects eq(null) and requires using isNull(). Additionally, SQL NULL logic is three-valued logic; standard equality comparisons with NULL do not evaluate to TRUE.

If a filter parameter is null and means "skip this condition," do not add a predicate. If null means "find records where the column is NULL," add isNull().

These two requirements must be clearly distinguished in the filter DTO or API contract.

## 10. Combining BooleanExpression with AND and OR

BooleanExpression instances can be combined directly:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression predicate =
    c.name.containsIgnoreCase("linh")
        .and(c.enabled.isTrue())
        .and(c.age.goe(18));
~~~

OR grouping:

~~~java
BooleanExpression textMatches =
    c.name.containsIgnoreCase("linh")
        .or(c.email.containsIgnoreCase("linh"));

BooleanExpression finalPredicate =
    textMatches.and(c.enabled.isTrue());
~~~

Meaning:

~~~text
(name contains "linh" OR email contains "linh")
AND enabled = true
~~~

Assign OR groups to a separate variable when a query has multiple conditions. This avoids logic bugs caused by misreading operator precedence.

BooleanExpression is a good representation for conditions whose values are already known. With many optional filters, BooleanBuilder is often more convenient.

## 11. BooleanBuilder for Dynamic Conditions

BooleanBuilder is a predicate to which conditions can be appended incrementally:

~~~java
QCustomer c = QCustomer.customer;

BooleanBuilder builder = new BooleanBuilder();

builder.and(c.enabled.isTrue());
builder.and(c.age.goe(18));

if (keyword != null && !keyword.isBlank()) {
    builder.and(c.name.containsIgnoreCase(keyword.strip()));
}

if (status != null) {
    builder.and(c.status.eq(status));
}
~~~

Each call to and or or updates the composite expression.

BooleanBuilder is useful when the number of conditions varies per request. Create a new builder for each query construction; do not hold a shared mutable builder across requests or store it in a singleton.

You can use immutable BooleanExpression composition if the number of branches is small and clear. You do not need BooleanBuilder for every query.

## 12. Filter DTO and Building Predicates Only for Valid Filters

Use wrapper types to distinguish an omitted filter from false or 0:

~~~java
public record CustomerFilter(
    String keyword,
    CustomerStatus status,
    Boolean enabled,
    Integer minAge,
    Integer maxAge,
    String email,
    NullMode emailMode
) {
    public enum NullMode {
        ANY,
        IS_NULL,
        IS_NOT_NULL
    }
}
~~~

Builder:

~~~java
public final class CustomerPredicates {

    private CustomerPredicates() {
    }

    public static Optional<Predicate> from(CustomerFilter filter) {
        QCustomer c = QCustomer.customer;
        BooleanBuilder builder = new BooleanBuilder();

        if (filter.keyword() != null
                && !filter.keyword().isBlank()) {
            String keyword = filter.keyword().strip();

            builder.and(
                c.name.containsIgnoreCase(keyword)
                    .or(c.email.containsIgnoreCase(keyword))
            );
        }

        if (filter.status() != null) {
            builder.and(c.status.eq(filter.status()));
        }

        if (filter.enabled() != null) {
            builder.and(c.enabled.eq(filter.enabled()));
        }

        if (filter.minAge() != null) {
            builder.and(c.age.goe(filter.minAge()));
        }

        if (filter.maxAge() != null) {
            builder.and(c.age.loe(filter.maxAge()));
        }

        if (filter.email() != null && !filter.email().isBlank()) {
            builder.and(c.email.eq(filter.email().strip()));
        }

        if (filter.emailMode() == CustomerFilter.NullMode.IS_NULL) {
            builder.and(c.email.isNull());
        } else if (filter.emailMode()
                == CustomerFilter.NullMode.IS_NOT_NULL) {
            builder.and(c.email.isNotNull());
        }

        return builder.hasValue()
            ? Optional.of(builder.getValue())
            : Optional.empty();
    }
}
~~~

Filter contract semantics:

- keyword null or blank: do not add name/email condition.
- status null: do not filter status.
- enabled null: do not filter; false remains a valid filter value.
- minAge/maxAge null: skip the corresponding bound.
- emailMode ANY: do not filter email nullness.
- emailMode IS_NULL: only match NULL emails.
- emailMode IS_NOT_NULL: only match non-NULL emails.

Optional.empty() here represents "no predicate," not an empty query result. The caller must handle the absent-predicate case by calling the corresponding unpredicated repository method or applying the application's default scope.

If a filter has an empty collection, clearly define its semantics: skip the condition, return no results, or reject the request. Do not rely on how a provider handles IN with an empty collection.

## 13. QuerydslPredicateExecutor in Spring Data JPA

Spring Data JPA provides QuerydslPredicateExecutor so repositories can accept a Querydsl Predicate:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                QuerydslPredicateExecutor<Customer> {
}
~~~

Commonly used methods:

| Method | Return type |
|---|---|
| findOne(predicate) | Optional<T> |
| findAll(predicate) | Iterable<T> |
| findAll(predicate, sort) | Iterable<T> |
| findAll(predicate, pageable) | Page<T> |
| count(predicate) | long |
| exists(predicate) | boolean |

Example finding customers:

~~~java
QCustomer c = QCustomer.customer;

Predicate predicate = c.name.containsIgnoreCase("linh")
    .and(c.enabled.isTrue());

Iterable<Customer> customers =
    customerRepository.findAll(predicate);
~~~

Pagination:

~~~java
Pageable pageable = PageRequest.of(
    0,
    20,
    Sort.by(
        Sort.Order.asc("name"),
        Sort.Order.asc("id")
    )
);

Page<Customer> page =
    customerRepository.findAll(predicate, pageable);
~~~

QuerydslPredicateExecutor helps implement simple entity queries quickly. It does not completely replace JPAQueryFactory when projections, group by, multiple joins, fetch joins, or complex queries are needed.

## 14. Handling the Absence of a Predicate

Do not call QuerydslPredicateExecutor with a null argument simply because all filters were omitted. Some implementations require a non-null Predicate.

You can handle this explicitly in the service:

~~~java
public Page<Customer> search(
        CustomerFilter filter,
        Pageable pageable) {

    Optional<Predicate> predicate =
        CustomerPredicates.from(filter);

    if (predicate.isPresent()) {
        return repository.findAll(predicate.get(), pageable);
    }

    return repository.findAll(pageable);
}
~~~

This example treats a filter with no predicate as fetching all Customers within the repository scope. In a real application, mandatory tenant, authorization, or soft-delete scopes must still be applied at the appropriate layer.

If business logic requires returning an empty result when no filter is supplied, create an always-false predicate instead of calling findAll(pageable).

Do not use null to simultaneously mean "no filter" and "not allowed to return results."

## 15. Querydsl with Entity Associations

Q-types let you traverse mapped property paths:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression cityMatches =
    c.address.city.eq("Da Nang");

BooleanExpression customerMatches =
    c.address.countryCode.eq("VN")
        .and(c.enabled.isTrue());
~~~

In this example, Customer has an address association and Address has city/countryCode properties. The processor generates the corresponding paths when the entity mapping is valid.

For to-one associations, traversing nested paths is typically translated by Querydsl into the necessary join in the query. Inspect the generated SQL if the query has multiple relationship paths or optional associations.

If you need control over join type, alias, or join conditions, use JPAQueryFactory and declare joins explicitly.

## 16. Collections and any()

For collection associations, Querydsl can use any() to express a condition on a related element:

~~~java
QCustomer c = QCustomer.customer;

BooleanExpression hasPaidOrder =
    c.orders.any().status.eq(OrderStatus.PAID);
~~~

Meaning: find Customers who have at least one Order with status PAID.

This is an expression on a collection path. How the provider translates it into SQL can depend on the query and mapping; check the SQL when performance or row counts matter.

If the query needs multiple conditions on the same Order, make sure the conditions apply to the same alias/order row. For complex queries, declare an aliased join in JPAQueryFactory for clearer control.

## 17. Controlling Joins Manually with JPAQueryFactory

Create a JPAQueryFactory bean:

~~~java
@Configuration
public class QuerydslConfiguration {

    @Bean
    public JPAQueryFactory jpaQueryFactory(EntityManager entityManager) {
        return new JPAQueryFactory(entityManager);
    }
}
~~~

Custom query:

~~~java
QCustomer customer = QCustomer.customer;
QOrder order = QOrder.order;

List<Customer> results = queryFactory
    .selectFrom(customer)
    .join(customer.orders, order)
    .where(
        order.status.eq(OrderStatus.PAID),
        customer.enabled.isTrue()
    )
    .distinct()
    .fetch();
~~~

JPAQueryFactory produces typed query results. join takes a path and a Q-type alias, so the compiler checks the referenced association and properties.

Use distinct when joining a collection can produce multiple rows for the same root entity and business logic requires each Customer to appear only once. DISTINCT has a cost and is not a substitute for proper join design.

Do not arbitrarily fetch join collections in paginated queries. Collection joins can multiply rows, complicating pagination and counts. Consider querying a page of IDs first and then loading details, or using a DTO projection.

## 18. Projections with Querydsl

Querydsl does not only return entities. JPAQueryFactory can select a subset of data and map it to a DTO.

DTO:

~~~java
public record CustomerSummary(
    Long id,
    String name,
    String email
) {
}
~~~

Query:

~~~java
QCustomer c = QCustomer.customer;

List<CustomerSummary> summaries = queryFactory
    .select(Projections.constructor(
        CustomerSummary.class,
        c.id,
        c.name,
        c.email
    ))
    .from(c)
    .where(c.enabled.isTrue())
    .orderBy(c.name.asc(), c.id.asc())
    .fetch();
~~~

Projections.constructor uses a constructor whose parameter order matches the selected expressions. Data types and order must match the DTO.

Other projection options include Projections.bean and Projections.fields, each with its own requirements for setters, constructors, or fields. Choose constructor projection when you want an immutable DTO and an explicit constructor contract.

When complex projections, group by, or aggregates are needed, JPAQueryFactory is usually a better fit than QuerydslPredicateExecutor.

## 19. Custom Repository Fragment for Querydsl

Custom Querydsl queries can be placed in a repository fragment:

~~~java
public interface CustomerSearchRepository {
    List<CustomerSummary> searchSummaries(CustomerFilter filter);
}
~~~

Main repository:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                QuerydslPredicateExecutor<Customer>,
                CustomerSearchRepository {
}
~~~

Implementation following the fragment convention:

~~~java
public class CustomerSearchRepositoryImpl
        implements CustomerSearchRepository {

    private final JPAQueryFactory queryFactory;

    public CustomerSearchRepositoryImpl(
            JPAQueryFactory queryFactory) {
        this.queryFactory = queryFactory;
    }

    @Override
    public List<CustomerSummary> searchSummaries(
            CustomerFilter filter) {

        QCustomer c = QCustomer.customer;
        BooleanBuilder where = new BooleanBuilder();

        if (filter.keyword() != null
                && !filter.keyword().isBlank()) {
            String keyword = filter.keyword().strip();

            where.and(
                c.name.containsIgnoreCase(keyword)
                    .or(c.email.containsIgnoreCase(keyword))
            );
        }

        if (filter.enabled() != null) {
            where.and(c.enabled.eq(filter.enabled()));
        }

        JPAQuery<CustomerSummary> query = queryFactory
            .select(Projections.constructor(
                CustomerSummary.class,
                c.id,
                c.name,
                c.email
            ))
            .from(c);

        if (where.hasValue()) {
            query.where(where);
        }

        return query
            .orderBy(c.name.asc(), c.id.asc())
            .fetch();
    }
}
~~~

Fragments work well when combining Querydsl with projections, joins, grouping, or custom query logic. The implementation name must match the interface name plus the Impl suffix per repository configuration.

Extract predicate building into a shared class if multiple fragments or repositories need the same filter rules. Avoid letting a single fragment manage every query in the system and accumulate too many responsibilities.

## 20. Combining Predicates from Multiple Sources

Predicates are objects that can be passed between layers. For example, a service can combine security conditions with search conditions:

~~~java
QCustomer c = QCustomer.customer;

Predicate tenantScope =
    c.tenantId.eq(currentTenantId);

Optional<Predicate> search =
    CustomerPredicates.from(filter);

BooleanBuilder finalPredicate =
    new BooleanBuilder(tenantScope);

search.ifPresent(finalPredicate::and);

Page<Customer> page =
    repository.findAll(finalPredicate, pageable);
~~~

The tenantScope condition is always applied, even when the user enters no filters. This keeps mandatory data scoping separate from optional filters.

Do not let clients construct or pass arbitrary Predicates over HTTP. Predicates are internal application expressions; APIs should accept DTOs with whitelisted fields and have the service construct the predicate.

## 21. Querydsl Web Binding and QuerydslBinderCustomizer

Spring Data can bind HTTP query parameters into a Querydsl Predicate via @QuerydslPredicate and Querydsl web support.

Example repository customizing binding:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                QuerydslPredicateExecutor<Customer>,
                QuerydslBinderCustomizer<QCustomer> {

    @Override
    default void customize(
            QuerydslBindings bindings,
            QCustomer root) {

        bindings.excludeUnlistedProperties(true);

        bindings.including(
            root.name,
            root.status
        );

        bindings.bind(root.name)
            .first((path, value) -> path.containsIgnoreCase(value));

        bindings.bind(root.status)
            .first((path, value) -> path.eq(value));
    }
}
~~~

Controller:

~~~java
@RestController
@RequestMapping("/customers")
public class CustomerController {

    private final CustomerRepository repository;

    public CustomerController(CustomerRepository repository) {
        this.repository = repository;
    }

    @GetMapping
    public Iterable<Customer> search(
            @QuerydslPredicate(root = Customer.class)
            Predicate predicate) {
        return repository.findAll(predicate);
    }
}
~~~

With web binding, you must enable appropriate Spring Data web support in the application and verify the Spring Data version in use. Spring Boot web auto-configuration normally provides the web infrastructure, but you should not assume every custom configuration has enabled the Querydsl argument resolver.

Only expose properties needed for searching. excludeUnlistedProperties(true) prevents clients from arbitrarily querying internal fields like tenantId, deletedAt, or sensitive data.

## 22. Whitelisting Sort and Filters from the API

Querydsl helps build type-safe predicates, but that does not mean every field should be exposed to clients.

Do not accept raw property names and arbitrarily use reflection or PathBuilder to construct queries without validation.

Sort whitelist example:

~~~java
public Sort resolveSort(String key, String direction) {
    Sort.Direction order =
        Sort.Direction.fromString(direction);

    return switch (key) {
        case "name" -> Sort.by(order, "name");
        case "created" -> Sort.by(order, "createdAt");
        case "age" -> Sort.by(order, "age");
        default -> throw new IllegalArgumentException(
            "Unsupported sort field"
        );
    };
}
~~~

If using JPAQueryFactory, map keys to the corresponding Q-type expressions:

~~~java
OrderSpecifier<?> order = switch (key) {
    case "name" -> orderDirection == Direction.ASC
        ? c.name.asc()
        : c.name.desc();
    case "age" -> orderDirection == Direction.ASC
        ? c.age.asc()
        : c.age.desc();
    default -> throw new IllegalArgumentException(
        "Unsupported sort field"
    );
};
~~~

Whitelisting protects query structure and limits which fields the API allows sorting on. Also validate page size, number of filters, and input string lengths.

## 23. Pagination with QuerydslPredicateExecutor

QuerydslPredicateExecutor supports Pageable:

~~~java
Predicate predicate = QCustomer.customer.enabled.isTrue();

Pageable pageable = PageRequest.of(
    0,
    25,
    Sort.by(
        Sort.Order.desc("createdAt"),
        Sort.Order.desc("id")
    )
);

Page<Customer> result =
    repository.findAll(predicate, pageable);
~~~

Page contains content, totalElements, and totalPages. To compute the total, Spring Data may execute a count query.

Add a unique tie-breaker like id to guarantee deterministic ordering when multiple records share the same createdAt. This helps pagination, though data changes between requests can still cause offset pages to shift.

If you only need to know whether a next page exists, consider Slice or a dedicated query to avoid the cost of a full count.

## 24. Pagination in JPAQueryFactory

For custom queries, you can use offset and limit:

~~~java
List<CustomerSummary> content = queryFactory
    .select(Projections.constructor(
        CustomerSummary.class,
        c.id,
        c.name,
        c.email
    ))
    .from(c)
    .where(predicate)
    .orderBy(c.createdAt.desc(), c.id.desc())
    .offset(pageable.getOffset())
    .limit(pageable.getPageSize())
    .fetch();
~~~

If a Page is needed, build a separate count query with the same predicate:

~~~java
Long totalValue = queryFactory
    .select(c.count())
    .from(c)
    .where(predicate)
    .fetchOne();

long total = totalValue == null ? 0L : totalValue;
~~~

Then construct PageImpl from content, pageable, and total.

Do not assume an automatic count API is always accurate for queries with multiple group by clauses, distinct, or collection joins. Write a count query matching the semantics of the content query and test totalElements.

## 25. Data Types and Domain Operations

Q-types preserve property type information:

- Integers and decimals: use NumberPath with gt, goe, between.
- Strings: use StringPath with eq, contains, startsWith.
- Booleans: use isTrue, isFalse, or eq.
- Enums: use EnumPath with eq/in.
- Dates: use DatePath/DateTimePath with before, after, between, or goe/lt.
- Associations: use nested Q-types.
- Collections: use CollectionPath/ListPath/SetPath and corresponding operations.

Half-open date range example:

~~~java
BooleanExpression createdInRange =
    c.createdAt.goe(from)
        .and(c.createdAt.lt(to));
~~~

The interval [from, to) includes the start instant and excludes the end instant. This pattern is useful for contiguous date ranges without overlapping boundaries.

Use BigDecimal for currency instead of double. Q-types reflect entity property types, but they do not replace domain validation such as non-negative minPrice or ensuring from is not after to.

## 26. Handling Empty Collections and NULL Data

Querydsl provides isNull, isNotNull, in, and notIn. Define semantics before building the predicate:

~~~java
if (filter.statuses() != null
        && !filter.statuses().isEmpty()) {
    builder.and(c.status.in(filter.statuses()));
}
~~~

The example above treats both null and empty sets as not applying the status filter.

If an empty set means no records should be returned, add an always-false predicate:

~~~java
if (filter.statuses() != null
        && filter.statuses().isEmpty()) {
    builder.and(Expressions.asBoolean(false));
}
~~~

If you want to find null fields:

~~~java
builder.and(c.email.isNull());
~~~

If you want to skip the email filter when input is null, do not add a predicate. Do not call eq(null).

SQL NULL logic is three-valued: TRUE/FALSE/UNKNOWN. Consequently, ne(value) does not automatically include rows with NULL fields. If you need rows that are either not equal to value or NULL, explicitly combine ne(value).or(isNull()).

## 27. Testing Predicates Against a Database

You can test predicates with @DataJpaTest to verify that Querydsl expressions translate into correct queries and return expected results.

Example:

~~~java
@DataJpaTest
class CustomerQuerydslTest {

    @Autowired
    private CustomerRepository repository;

    @Test
    void combinesTypedPredicates() {
        repository.saveAndFlush(
            new Customer(
                "Linh Nguyen",
                "linh@example.com",
                25,
                true,
                CustomerStatus.ACTIVE
            )
        );

        repository.saveAndFlush(
            new Customer(
                "An Tran",
                "an@example.com",
                17,
                false,
                CustomerStatus.NEW
            )
        );

        QCustomer c = QCustomer.customer;

        Predicate predicate = c.name.containsIgnoreCase("linh")
            .and(c.age.goe(18))
            .and(c.enabled.isTrue());

        Iterable<Customer> result = repository.findAll(predicate);

        List<String> names = StreamSupport
            .stream(result.spliterator(), false)
            .map(Customer::getName)
            .toList();

        assertThat(names).containsExactly("Linh Nguyen");
    }
}
~~~

The example assumes the test fixture can save two independent Customers and the repository is configured with Querydsl. Add test framework, StreamSupport, and entity/repository imports matching your project's packages.

You should test:

1. Exact match and substring match.
2. Case-insensitive matching against the real database.
3. Numeric/date ranges.
4. Enums and Boolean false.
5. NULL with isNull/isNotNull.
6. Collection in and empty collection.
7. AND/OR grouping.
8. To-one associations and collection any/join.
9. Absence of filters.
10. Pageable, Sort, and count queries.
11. Web binding exposing only whitelisted properties.
12. Queries with projections and custom fragments.

## 28. Debugging SQL and Performance

Querydsl builds typed expressions, but it does not automatically guarantee optimal queries. Enable SQL logging or a datasource query counter to inspect the real SQL.

Points to check:

- Does the query add unnecessary joins?
- Does contains/containsIgnoreCase produce leading-wildcard patterns?
- Does calling LOWER on a column affect index usage?
- Does a collection join multiply root rows?
- Is DISTINCT necessary and is it expensive?
- Does the count query have the same semantics as the content query?
- Does the Sort have a suitable index?
- Is offset pagination going too deep?

For substring searches on large tables, B-tree indexes usually struggle with leading-wildcard patterns. Consider full-text or database-specific indexes if the workload requires them.

Use EXPLAIN/EXPLAIN ANALYZE or your database's equivalent tool. Compare execution plans with production-like data instead of drawing conclusions from Querydsl code.

## 29. Limitations and Choosing Between Querydsl and Other Query Approaches

| Need | Choice |
|---|---|
| Simple, static queries | Derived queries or @Query |
| Dynamic conditions needing Q-types | Querydsl Predicate/BooleanBuilder |
| Simple entity predicates via repository | QuerydslPredicateExecutor |
| DTO projections, grouping, or complex joins | JPAQueryFactory/custom fragment |
| Queries requiring standard JPA API without extra libraries | Criteria API |
| Database-specific SQL | Native query |
| Only specific columns needed for read screens | DTO projection |

Querydsl is an additional library, not part of the Jakarta Persistence specification. You must manage versions, the annotation processor, and compatibility with the JPA provider.

QuerydslPredicateExecutor is convenient, but it limits projection customization and query structure. When you need control over SQL/JPQL shape, use JPAQueryFactory in a custom repository fragment.

## 30. Common Errors and Troubleshooting

**1. QCustomer fails to generate**

Check querydsl-apt, annotation processor path, Jakarta/Javax classifier, and entity annotations. Run clean compile.

**2. IDE reports Q-type not found, but Maven build succeeds**

Mark generated sources as a source root or refresh the project model. Do not create QCustomer manually.

**3. Mixing up javax and jakarta**

Spring Boot 3 requires the Jakarta classifier. Do not use a javax annotation processor to process jakarta.persistence entities.

**4. Calling eq(null)**

Use isNull(). If null means skip the filter, do not add a predicate.

**5. Boolean false filter gets ignored**

Check value != null rather than if (value). Use the Boolean wrapper for optional filters.

**6. BooleanBuilder shared across requests**

Create a new builder for each query build. The builder is a mutable object.

**7. Query returns too many rows after a collection join**

Check cardinality and consider distinct or EXISTS. Do not use distinct to hide an incorrect join.

**8. Slow pagination or wrong total**

Check the count query, collection joins, and offset. Write a separate count query for complex queries.

**9. Clients can filter internal fields**

Use QuerydslBinderCustomizer, excludeUnlistedProperties, and whitelist filter/sort keys.

**10. containsIgnoreCase does not ignore accents**

IgnoreCase is not accent-insensitive. Check collation or use a separate search strategy.

**11. Empty predicate passed to repository**

Distinguish Optional.empty() from an always-false predicate. When there is no predicate, call the unpredicated repository method; if an empty result is needed, build a false expression.

**12. Querydsl query does not use indexes**

Inspect the SQL, wildcards, column functions, and execution plan. Optimize indexes for the real workload.

## 33. Review Questions

**1. What is a Q-type?**

A Java class generated by Querydsl's annotation processor from an entity, containing typed paths for building predicates and queries.

**2. Why are Q-types type-safe?**

Each property is represented by a path matching its data type. The compiler and IDE can detect many wrong property names or incompatible operations before runtime.

**3. How does QCustomer differ from Customer?**

Customer is the entity managed by JPA; QCustomer is a metadata/query type used to build expressions, not an entity instance.

**4. Why does Spring Boot 3 require the Querydsl Jakarta classifier?**

Entities use jakarta.persistence. Both the processor and Querydsl JPA runtime must match that namespace to recognize annotations and execute queries.

**5. How does BooleanExpression differ from BooleanBuilder?**

BooleanExpression represents a condition; BooleanBuilder is a mutable builder for adding dynamic conditions step by step.

**6. When should you use QuerydslPredicateExecutor?**

When you need to filter entities by Predicate with findAll, findOne, count, exists, and Pageable/Sort without complex query projections.

**7. When should you use JPAQueryFactory?**

When you need controlled joins, DTO projections, grouping, aggregates, or query structures beyond the convenience of QuerydslPredicateExecutor.

**8. How do you handle a null filter?**

If null means skip, do not add a predicate. If you need to match NULL columns, use isNull(). Do not use eq(null).

**9. Is Boolean false treated as no filter?**

No. With the Boolean wrapper, null represents skipping the filter; false is a valid filter value.

**10. Does Querydsl guarantee fast queries?**

No. It helps build typed queries; SQL and execution plans still depend on query shape, database, indexes, cardinality, and provider.

Q-types move many query errors from runtime to compile time and make search conditions easier to read. When combining the annotation processor, Predicate, BooleanBuilder, and repository executor properly, applications can build type-safe dynamic filters; for more complex queries, JPAQueryFactory expands control while keeping Q-types as the foundation.
