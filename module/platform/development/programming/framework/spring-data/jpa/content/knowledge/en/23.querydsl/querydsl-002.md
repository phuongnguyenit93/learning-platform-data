# Configuring Jakarta Persistence-Compatible Q-Type Generation with Querydsl

## 1. What Is a Q-Type?

Querydsl is a Java query-building library with a fluent API and compile-time type checking. Instead of writing property names as strings like in JPQL or plain Criteria API, Querydsl generates a metamodel class for each domain type. These classes are typically prefixed with `Q`, for example:

- Entity `Customer` generates `QCustomer`.
- Entity `PurchaseOrder` generates `QPurchaseOrder`.
- Embedded type `Address` can generate `QAddress`.

A Q-type describes the source type's properties using typed paths. For example, `QCustomer.customer.email` is a `StringPath`, `QCustomer.customer.id` is a path of the ID type, and `QCustomer.customer.createdAt` is a path corresponding to the date/time type.

As a result, the IDE can autocomplete properties and the compiler catches many field-name or data-type errors before running the application. When an entity property is renamed, code using the Q-type must also be recompiled; if the Q-type has not been generated or is stale, the build will report an error.

Q-types are source code automatically generated by an annotation processor. Normally, `Q...` classes are not written or edited by hand.

## 2. Why Does Jakarta Persistence Require Special Configuration?

Starting with Spring Boot 3 and Spring Framework 6, the JPA ecosystem migrated from the Java EE namespace `javax.persistence.*` to the Jakarta EE namespace `jakarta.persistence.*`.

These two namespaces differ at the package and binary name level. For example:

| Legacy API | Jakarta API |
|---|---|
| `javax.persistence.Entity` | `jakarta.persistence.Entity` |
| `javax.persistence.Id` | `jakarta.persistence.Id` |
| `javax.persistence.EntityManager` | `jakarta.persistence.EntityManager` |
| `javax.persistence.MappedSuperclass` | `jakarta.persistence.MappedSuperclass` |

An annotation processor that only recognizes `javax.persistence.Entity` may fail to detect entities annotated with `jakarta.persistence.Entity`. The usual outcome is that the build still compiles the entity but does not generate `QCustomer`, or generates code based on a namespace incompatible with the application.

Therefore, Querydsl configuration must stay aligned in three places:

1. The Querydsl JPA library used at compile/runtime.
2. The Querydsl annotation processor used to generate Q-types.
3. The Jakarta Persistence API that the annotation processor needs to recognize entities.

Do not mix artifacts built for `javax.persistence` with entities and providers using `jakarta.persistence`.

## 3. Choosing the Right Querydsl Line

There are two common options in Jakarta projects today:

| Option | Group ID | How to Enable Jakarta | Notes |
|---|---|---|---|
| Upstream Querydsl 5.1.x | `com.querydsl` | Use classifier `jakarta` for `querydsl-jpa` and `querydsl-apt` | Illustrated in the Spring Data reference |
| OpenFeign Querydsl fork 6.x and later | `io.github.openfeign.querydsl` | Fork uses the `jakarta.*` namespace directly; annotation processor uses classifier `jpa` | Community-maintained fork after upstream slowed down; Spring Data supports it on a best-effort basis |

Current Spring Data documentation notes that maintenance activity on upstream Querydsl has slowed and the community forked the project under group ID `io.github.openfeign.querydsl`. Spring Data supports this fork on a best-effort basis. Check the Spring Data, Spring Boot, JDK, and JPA provider versions in your project before choosing. Do not mix modules from both group IDs in the same configuration.

The examples below illustrate the two separate configurations. Choose a single configuration for your project.

## 4. Maven Configuration with Querydsl 5.1.x Jakarta Classifier

If the project uses upstream Querydsl 5.1.x, add the JPA dependency with the `jakarta` classifier:

~~~xml
<dependencies>
    <dependency>
        <groupId>com.querydsl</groupId>
        <artifactId>querydsl-jpa</artifactId>
        <version>5.1.0</version>
        <classifier>jakarta</classifier>
    </dependency>
</dependencies>
~~~

Next, declare the annotation processor in `maven-compiler-plugin`:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.13.0</version>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>com.querydsl</groupId>
                        <artifactId>querydsl-apt</artifactId>
                        <version>5.1.0</version>
                        <classifier>jakarta</classifier>
                    </path>
                    <path>
                        <groupId>jakarta.persistence</groupId>
                        <artifactId>jakarta.persistence-api</artifactId>
                        <version>3.1.0</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

`querydsl-jpa` provides Querydsl's JPA query API. `querydsl-apt` provides the annotation processor. The Jakarta Persistence API is included on the processor path so the processor recognizes annotations such as `@Entity`, `@Embeddable`, and `@MappedSuperclass`.

The versions in the example are an illustrative set. Choose the Jakarta Persistence API version managed by your project's Spring Boot BOM or JPA provider; do not individually downgrade or upgrade the API if doing so causes drift from the current stack.

### Annotation processing on newer JDKs

Starting with JDK 22, annotation processors should be explicitly configured via `annotationProcessorPaths` or the corresponding opt-in mechanism. Do not rely on `javac` implicitly discovering processors on the compile classpath.

On JDK 23 and later, implicit annotation processing is disabled by default. If the build uses the Maven Compiler Plugin and does not run the processor even though the dependency is declared, check the explicit processor configuration; OpenFeign documentation further illustrates:

~~~xml
<configuration>
    <proc>full</proc>
    <annotationProcessorPaths>
        <!-- Querydsl APT and Jakarta Persistence API paths -->
    </annotationProcessorPaths>
</configuration>
~~~

`<proc>full</proc>` enables annotation processing in the compiler. You must still declare the proper processor and API on `annotationProcessorPaths`; adding `proc` alone without the processor will not generate Q-types.

## 5. Gradle Configuration with Querydsl 5.1.x Jakarta Classifier

With Gradle, the annotation processor must be placed in the `annotationProcessor` configuration, not just `implementation`.

Example `build.gradle` using Groovy DSL:

~~~groovy
dependencies {
    implementation 'com.querydsl:querydsl-jpa:5.1.0:jakarta'

    annotationProcessor 'com.querydsl:querydsl-apt:5.1.0:jakarta'
    annotationProcessor 'jakarta.persistence:jakarta.persistence-api:3.1.0'

    testAnnotationProcessor 'com.querydsl:querydsl-apt:5.1.0:jakarta'
    testAnnotationProcessor 'jakarta.persistence:jakarta.persistence-api:3.1.0'
}
~~~

If using Kotlin DSL (`build.gradle.kts`):

~~~kotlin
dependencies {
    implementation("com.querydsl:querydsl-jpa:5.1.0:jakarta")

    annotationProcessor("com.querydsl:querydsl-apt:5.1.0:jakarta")
    annotationProcessor("jakarta.persistence:jakarta.persistence-api:3.1.0")

    testAnnotationProcessor("com.querydsl:querydsl-apt:5.1.0:jakarta")
    testAnnotationProcessor("jakarta.persistence:jakarta.persistence-api:3.1.0")
}
~~~

`annotationProcessor` applies to main sources; `testAnnotationProcessor` is needed if the test source set contains entities or models requiring Q-type generation. The Jakarta Persistence API version must be compatible with the Spring Boot/JPA provider in use.

Do not place `querydsl-apt` in `implementation` instead of `annotationProcessor`. The processor is a build tool, not a runtime application library.

## 6. Using the OpenFeign Querydsl Fork

For new projects or projects choosing the OpenFeign fork, artifacts use group ID `io.github.openfeign.querydsl`. The fork from version 6 onward uses `jakarta.*` directly, so the `jakarta` classifier is not used for `querydsl-jpa`.

Gradle Groovy DSL example per Querydsl OpenFeign documentation:

~~~groovy
dependencies {
    implementation 'io.github.openfeign.querydsl:querydsl-jpa:7.1'

    annotationProcessor 'io.github.openfeign.querydsl:querydsl-apt:7.1:jpa'
    annotationProcessor 'jakarta.persistence:jakarta.persistence-api'

    testAnnotationProcessor 'io.github.openfeign.querydsl:querydsl-apt:7.1:jpa'
    testAnnotationProcessor 'jakarta.persistence:jakarta.persistence-api'
}
~~~

Maven example:

~~~xml
<dependencies>
    <dependency>
        <groupId>io.github.openfeign.querydsl</groupId>
        <artifactId>querydsl-jpa</artifactId>
        <version>7.1</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.15.0</version>
            <configuration>
                <proc>full</proc>
                <annotationProcessorPaths>
                    <path>
                        <groupId>io.github.openfeign.querydsl</groupId>
                        <artifactId>querydsl-apt</artifactId>
                        <version>7.1</version>
                        <classifier>jpa</classifier>
                    </path>
                    <path>
                        <groupId>jakarta.persistence</groupId>
                        <artifactId>jakarta.persistence-api</artifactId>
                        <version>3.2.0</version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

Here, the `jpa` classifier selects the fork's JPA annotation processor. It is not the `jakarta` classifier of the upstream artifact. Choose the Jakarta Persistence API version matching your project platform; `3.2.0` in the Maven example fits a Jakarta Persistence 3.2 stack, while older Spring Boot/JPA projects may require a different API version according to the BOM.

Current Spring Data documentation also includes Maven and Gradle examples for the OpenFeign fork. If using the fork, keep all Querydsl modules under the same group ID `io.github.openfeign.querydsl`; do not mix upstream `com.querydsl` `querydsl-core` or `querydsl-apt` into that configuration.

## 7. Ensuring Entities Use Jakarta Annotations

Entities must import from `jakarta.persistence`:

~~~java
package com.example.customer;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "customer")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String fullName;
    private String email;

    protected Customer() {
    }

    public Customer(String fullName, String email) {
        this.fullName = fullName;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }

    public String getEmail() {
        return email;
    }
}
~~~

When the annotation processor runs, it reads entity metadata and generates `QCustomer` in the corresponding package. No extra annotations are needed for ordinary properties.

If the entity still imports `javax.persistence.Entity`, the Jakarta processor may not recognize it properly. Align all entities, the JPA provider, the API dependency, and the Querydsl processor to the same namespace.

## 8. Where Are Q-Types Generated?

The annotation processor runs during the compile phase and creates source files in the generated sources directory. The default location is usually under the build directory, for example:

- Maven: `target/generated-sources/annotations`
- Gradle: `build/generated/sources/annotationProcessor/java/main`

Directory names may vary depending on compiler or plugin configuration. Do not assume a single fixed path if the project has customized the build.

For example, the `Customer` entity can generate:

~~~java
package com.example.customer;

import static com.querydsl.core.types.PathMetadataFactory.*;

public class QCustomer extends EntityPathBase<Customer> {
    public static final QCustomer customer = new QCustomer("customer");

    public final StringPath email = createString("email");
    public final NumberPath<Long> id = createNumber("id", Long.class);
    public final StringPath fullName = createString("fullName");

    // Generated constructors and metadata omitted.
}
~~~

This snippet illustrates the Q-type structure, not a complete file to write manually. Real Q-types are generated by the processor with imports, metadata, constructors, and paths matching the entity.

Do not edit files in the generated directory directly. Change the entity or processor configuration and run the build to regenerate them.

## 9. Verifying That Q-Types Were Generated

After configuring, run a clean build to eliminate stale generated code:

~~~bash
# Maven
mvn clean compile

# Gradle
./gradlew clean compileJava
~~~

Check the generated source directory for `QCustomer.java` or the Q-type of the entity you need. You can run tests after compiling:

~~~bash
# Maven
mvn clean test

# Gradle
./gradlew clean test
~~~

If the project has entities in the test source set, make sure `testAnnotationProcessor` is configured in Gradle or the corresponding processor configuration is set for test compilation in Maven.

In your IDE, enable annotation processing if the IDE does not automatically pick up the build configuration, then mark the generated sources directory as a Generated Sources Root if needed. Prefer letting Maven/Gradle serve as the primary configuration source to avoid local developer builds differing from CI.

## 10. Using Q-Types with Querydsl JPA

Once `QCustomer` has been generated, it can be used in queries:

~~~java
QCustomer customer = QCustomer.customer;

List<Customer> activeCustomers = queryFactory
    .selectFrom(customer)
    .where(
        customer.status.eq(CustomerStatus.ACTIVE)
            .and(customer.email.endsWithIgnoreCase("@example.com"))
    )
    .orderBy(
        customer.createdDate.desc(),
        customer.id.asc()
    )
    .fetch();
~~~

The example assumes the entity has `status`, `email`, `createdDate`, and `id`. Paths are generated according to each property's actual type. If the entity only has `fullName` and `email`, you cannot call `customer.status` or `customer.createdDate`; use the actual properties present in your model.

`JPAQueryFactory` is typically initialized from `EntityManager`:

~~~java
@Configuration
public class QuerydslConfiguration {

    @Bean
    JPAQueryFactory jpaQueryFactory(EntityManager entityManager) {
        return new JPAQueryFactory(entityManager);
    }
}
~~~

Import `jakarta.persistence.EntityManager` and the corresponding Spring/JPA classes. The factory bean uses the container-managed EntityManager; do not manually create an independent EntityManager outside the transaction lifecycle.

## 11. Integrating QuerydslPredicateExecutor with a Spring Data Repository

If you only need to execute predicates through the repository abstraction, you can extend `QuerydslPredicateExecutor`:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                QuerydslPredicateExecutor<Customer> {
}
~~~

Then build a predicate from the Q-type:

~~~java
QCustomer customer = QCustomer.customer;

Predicate predicate = customer.status.eq(CustomerStatus.ACTIVE)
    .and(customer.fullName.containsIgnoreCase("an"));

Iterable<Customer> result = customerRepository.findAll(predicate);
~~~

`QuerydslPredicateExecutor` provides operations such as `findAll(predicate)`, `findOne(predicate)`, `count(predicate)`, and `exists(predicate)`. Overloads supporting `Sort` and `Pageable` enable pagination and sorting through the repository API.

Example:

~~~java
Page<Customer> page = customerRepository.findAll(
    predicate,
    PageRequest.of(
        0,
        20,
        Sort.by("id").ascending()
    )
);
~~~

Use `JPAQueryFactory` when you need fine-grained control over select, join, group, projection, or query expressions. Use `QuerydslPredicateExecutor` when you want to reuse predicates with standard repository operations.

## 12. Configuring Test Sources and Multi-Module Entities

If entities are declared in `src/test/java`, the processor must run on the test source set to generate Q-types used in tests. In Gradle, add `testAnnotationProcessor` as shown in the earlier example.

In a multi-module build:

- The module containing the entities is responsible for running the annotation processor and generating Q-types for those entities.
- Other modules needing the Q-types must depend on the artifact containing the compiled/packaged generated classes according to how the project is structured.
- Do not configure two modules to generate the same Q-type for the same entity if that produces duplicate classes.
- Ensure generated sources are included in compilation and artifacts when modules need to share them.

If the project separates out a model module, inspect that module's output and dependency graph before configuring an additional processor in consuming modules.

## 13. Common Errors and Troubleshooting

### 13.1. Build succeeds but no Q-types are generated

Common causes:

- `querydsl-apt` is not on the annotation processor path.
- Newer JDKs do not run annotation processors automatically without opt-in.
- The processor uses the wrong classifier.
- The entity is not processed by the compiler in that source set.
- Entities use `jakarta.persistence`, but the processor uses the `javax` line.
- The generated source directory is not recognized by the compiler/IDE.

How to check:

1. Verify the processor is in `annotationProcessorPaths` or `annotationProcessor`.
2. Verify the artifact has the correct group ID and classifier.
3. Verify `jakarta.persistence-api` is on the processor path.
4. Run `clean compile` to regenerate.
5. Check the generated source output and compiler logs.

### 13.2. Error: javax.persistence not found

Errors like `ClassNotFoundException: javax.persistence.Entity` or `NoClassDefFoundError` usually indicate an old dependency/processor using the Java EE namespace while the application uses Jakarta.

Check the dependency tree and remove incompatible legacy Querydsl configurations. Do not add both `javax.persistence-api` and `jakarta.persistence-api` to mask namespace errors; choose one consistent stack.

### 13.3. Using the wrong classifier

The two configurations are not interchangeable:

- Upstream `com.querydsl`: uses classifier `jakarta` for `querydsl-jpa` and `querydsl-apt`.
- OpenFeign `io.github.openfeign.querydsl`: uses the standard JPA artifact and classifier `jpa` for `querydsl-apt`.

Do not change classifier `jakarta` to `jpa` on upstream artifacts, and do not add classifier `jakarta` to the fork simply because the application uses Jakarta.

### 13.4. Q-type exists, but IDE reports it cannot be found

Check whether the IDE has annotation processing enabled and recognizes the generated source directory. Run the build from the terminal to distinguish IDE issues from Maven/Gradle configuration errors. If the terminal build succeeds while the IDE shows red errors, resync the project and mark the generated directory appropriately.

### 13.5. Duplicate class or stale Q-type errors

This can happen because a Q-type was created manually, stale generated sources remained, or multiple modules generate the same class. Use `clean`, remove unnecessary hand-written Q-type files, and designate a single place responsible for code generation.

### 13.6. Local build works, but CI does not generate Q-types

CI may use a different JDK or run with annotation processing disabled. Explicitly record the JDK, Maven/Gradle wrapper, and processor configuration in the repository. Do not rely on IDE-specific settings.

## 14. Configuration Selection and Verification Workflow

When adding Querydsl to a Jakarta Persistence project:

1. Identify which Spring Boot/Spring Data JPA and JDK versions the project uses.
2. Confirm entities import `jakarta.persistence.*`.
3. Choose one Querydsl line: upstream with classifier `jakarta`, or the OpenFeign fork with processor classifier `jpa`.
4. Declare `querydsl-jpa` in the appropriate compile/runtime dependencies.
5. Declare `querydsl-apt` in the annotation processor configuration, not just in implementation.
6. Put the Jakarta Persistence API on the processor path.
7. Ensure annotation processing is explicitly enabled on newer JDKs.
8. Run a clean build and confirm Q-types appear in generated sources.
9. Use a Q-type in a real query or repository test.
10. Run tests on the same JDK and build tool as CI.

## 15. Key Takeaways

- Q-types are Java metamodels generated by Querydsl from entities/domain models, e.g., `Customer` becomes `QCustomer`.
- Spring Boot 3 / Spring Data JPA 3 uses Jakarta Persistence; entities must import `jakarta.persistence.*`.
- The `javax.persistence` and `jakarta.persistence` namespaces are not binary compatible.
- Upstream Querydsl 5.1.x requires the `jakarta` classifier on `querydsl-jpa` and `querydsl-apt`.
- The OpenFeign Querydsl fork uses group ID `io.github.openfeign.querydsl`; fork versions 6.x+ use Jakarta directly and the JPA processor takes classifier `jpa`.
- Do not mix group IDs or classifiers between the two Querydsl lines.
- `querydsl-apt` must be configured in the annotation processor path/configuration; it is not an ordinary runtime dependency.
- Include the Jakarta Persistence API on the processor path so the processor recognizes annotations.
- On JDK 22+, configure annotation processors explicitly; on JDK 23+, check opt-in/`proc` according to the Maven Compiler Plugin and build tool documentation.
- Q-types are generated in generated sources; do not edit them directly.
- After modifying entities or dependencies, run a clean build and confirm generated Q-types are updated.
- Test the configuration on the exact JDK and build tool used in CI.
