# Managing Changes with Flyway or Liquibase

## 1. Why Do We Need Schema Change Management?

A Spring Data JPA application evolves over time: adding Entity properties, creating new tables, changing column types, adding indexes, normalizing data, or splitting a large table. These changes must be applied consistently across local, test, staging, and production environments.

If each environment modifies the database manually or relies on Hibernate to automatically create/update the schema, database structures can drift apart. An application version might work on a developer's machine but fail upon deployment because production is missing a column, index, or constraint.

Database migrations solve this problem by storing changes as versioned files or changelogs managed in source control. The migration tool reads the applied history, identifies missing changes, and executes them in order.

Both Flyway and Liquibase help:

- Track schema changes in an auditable history.
- Automatically apply migrations during deployment or pipeline execution.
- Detect certain cases where migration files were modified after being applied.
- Keep schemas across environments following the same process.
- Support reviewing database changes alongside code changes.

Migrations are part of a release. They must be designed, reviewed, tested, and deployed with a plan just like application code.

## 2. How Do Flyway and Liquibase Differ?

Flyway typically organizes migrations using versioned files, most commonly SQL. Filenames indicate execution order and describe the change. Flyway records executed migrations in the `flyway_schema_history` table.

Liquibase organizes changes using a changelog. A changelog contains changesets with an `id`, `author`, and file/path identifier. Changesets can be declared in XML, YAML, JSON, or SQL formatted changelogs. Liquibase stores history in `DATABASECHANGELOG` and uses `DATABASECHANGELOGLOCK` to coordinate updates.

| Criterion | Flyway | Liquibase |
| --- | --- | --- |
| Primary model | Sequence of versioned, ordered migrations | Changelog consisting of identified changesets |
| Common authoring style | Plain SQL; also supports Java migrations | XML, YAML, JSON, SQL formatted changelogs, and custom changes |
| History | `flyway_schema_history` | `DATABASECHANGELOG` |
| Repeatable changes | Repeatable migration `R__...` | `runOnChange` or `runAlways` on changesets |
| Conditional application | By version, target, locations, and Flyway configuration | Preconditions, contexts, labels, and Liquibase configuration |
| Rollback | Capability depends on edition/migration type; usually prepares forward migrations | Rollback can be declared per changeset; auto-generation depends on change type |

Neither tool is universally better. Flyway is often easier to adopt when a team wants to manage changes using plain, clearly ordered SQL. Liquibase is useful when you need structured changelogs, preconditions, contexts/labels, and change descriptions across multiple formats.

Choose one tool as the single source of truth for a database's schema. Do not let both Flyway and Liquibase manage the same schema in production because their two history tables do not understand each other's state.

## 3. Integrating Flyway into Spring Boot

Add the Flyway dependency and the database JDBC driver. With newer Flyway versions, some databases require a separate database module alongside `flyway-core`; choose the module matching your database and the version supported by Spring Boot dependency management.

Maven example for a PostgreSQL application; dependency versions should be managed via the Spring Boot BOM or the project's version catalog:

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

Spring Boot automatically configures Flyway when the dependency and a suitable DataSource are present. The default migration directory is usually `classpath:db/migration`.

Directory structure:

```text
src/main/resources/
  db/
    migration/
      V1__create_customer.sql
      V2__add_customer_status.sql
      V3__create_order_table.sql
```

Example `V1__create_customer.sql` file:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);

ALTER TABLE customer
    ADD CONSTRAINT uk_customer_email UNIQUE (email);
```

Identity syntax and timestamp types depend on the database. When using PostgreSQL, `TIMESTAMP WITH TIME ZONE` is suitable for storing an instant in time; the database does not store the user's original ZoneId in this column.

## 4. Flyway Migration Naming Conventions

Versioned migrations follow the common naming convention:

```text
V<version>__<description>.sql
```

Examples:

- `V1__create_customer.sql`
- `V2__add_customer_status.sql`
- `V2_1__add_customer_index.sql`
- `V3__create_purchase_order.sql`

Where:

- `V` is the versioned migration prefix.
- The version determines execution order.
- A double underscore `__` separates the version from the description.
- The description helps reviewers understand the purpose.
- The file extension is typically `.sql`.

Flyway compares migration versions against applied history and runs unexecuted migrations in order. Each versioned migration is treated as a historical step; do not edit the contents of a migration already applied in shared environments.

Do not create two migrations with the same version. Do not rename or delete already-applied files without understanding the impact on history and checksums. When a new schema change is needed, create a migration with the next version.

## 5. Flyway Versioned and Repeatable Migrations

**Versioned migrations** run once per version. Use them for ordered schema/data changes:

```text
V1__create_customer.sql
V2__add_status_column.sql
V3__backfill_customer_status.sql
```

**Repeatable migrations** use the `R__` prefix and re-run whenever their checksum changes. They are typically used for objects whose definitions need to stay synchronized, such as views or stored procedures:

```text
R__customer_summary_view.sql
R__refresh_customer_procedure.sql
```

Repeatable migrations do not have numeric versions like versioned migrations. Flyway checks their checksums and re-executes them when their content changes; repeatable migrations are applied after pending versioned migrations during a migrate run.

Do not place one-time data operations such as "add 10 to balance" in a repeatable migration, because the file may re-run when edited. Repeatable content should have definition-replacement semantics, such as `CREATE OR REPLACE VIEW` if supported by the database.

## 6. Flyway History Table and Checksums

Flyway stores information about executed migrations in `flyway_schema_history`, including version, description, script, checksum, status, execution timestamp, and related metadata.

Checksums help detect when an applied migration has been edited afterward. If you modify the contents of a versioned file that already ran, the `validate` command or the migrate process may fail with a checksum mismatch error.

Working rules:

- A migration not yet deployed to any shared environment may still be edited during development.
- A migration already applied in staging/production should be treated as immutable.
- If a schema fix is needed, create a new migration file.
- Do not edit checksums directly in the history table to mask a mismatch.

`flyway repair` can adjust history metadata, such as syncing checksums or removing certain failed migration records depending on status. It does not automatically undo or repair database structures. Only use it after verifying the actual schema state and having a clear recovery plan.

## 7. Common Flyway Configuration

Example `application.yml`:

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    validate-on-migrate: true
    clean-disabled: true
  jpa:
    hibernate:
      ddl-auto: validate
```

Meaning:

- `enabled`: enables/disables Flyway integration.
- `locations`: where migrations are located.
- `validate-on-migrate`: verifies history/checksums before applying new changes.
- `clean-disabled`: blocks the clean command via Flyway configuration.
- `ddl-auto: validate`: instructs Hibernate to validate mappings against the existing schema.

In production, never enable `clean` as a regular deployment step. The clean command can wipe objects in managed schemas. `clean-disabled: true` is an extra safeguard; database privileges must still be restricted.

Flyway also offers settings such as `schemas`, `default-schema`, `baseline-on-migrate`, `out-of-order`, `target`, and placeholders. Only enable baseline or out-of-order when following an explicit procedure; do not use them to hide missing or out-of-order migrations.

## 8. Baselining When Introducing Flyway to an Existing Database

If a database already has an existing schema before being managed by Flyway, you cannot simply run all `V1`, `V2`, ... migrations against it by default. You may need a baseline to mark a current version as the starting point, then run only newer migrations.

A typical process includes:

1. Back up and inventory the current schema.
2. Identify the version representing the existing schema state.
3. Create a baseline migration or configure baselining according to the project's management strategy.
4. Test on a copy of the production database.
5. Verify which versions Flyway considers applied and which migrations remain pending.
6. Only after confirming the state, deploy to the real database.

`baselineOnMigrate` can automatically baseline when Flyway encounters a non-empty schema without a history table. This is a convenient option, but it reduces your ability to catch connections to the wrong database or an unprepared schema. In production, prefer controlled baselining rather than enabling it blindly.

## 9. Integrating Liquibase into Spring Boot

Add the `liquibase-core` dependency and the database JDBC driver. Spring Boot automatically configures Liquibase when the dependency and a suitable DataSource are present.

Maven example:

```xml
<dependency>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-core</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

The master changelog can be placed at:

```text
src/main/resources/
  db/
    changelog/
      db.changelog-master.yaml
      changes/
        001-create-customer.yaml
        002-add-customer-status.yaml
```

Spring Boot configuration:

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.yaml
  jpa:
    hibernate:
      ddl-auto: validate
```

Example `db.changelog-master.yaml`:

```yaml
databaseChangeLog:
  - include:
      file: db/changelog/changes/001-create-customer.yaml
  - include:
      file: db/changelog/changes/002-add-customer-status.yaml
```

The master changelog is the entry point; included files run in the declared order. You can use `includeAll` for a directory, but you must control file sorting rules and prevent unrelated files from being picked up automatically.

## 10. Liquibase Changesets

A changeset is the unit of change tracked by Liquibase. Each changeset has an `id` and `author`; its historical identity is also tied to the changelog path. Never reuse the same identifier for a different change.

Example `001-create-customer.yaml`:

```yaml
databaseChangeLog:
  - changeSet:
      id: 001
      author: team-platform
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(320)
                  constraints:
                    nullable: false
        - addUniqueConstraint:
            tableName: customer
            columnNames: email
            constraintName: uk_customer_email
```

Liquibase records executed changesets in `DATABASECHANGELOG`, including ID, author, filename, checksum, and metadata. `DATABASECHANGELOGLOCK` helps prevent multiple Liquibase processes from executing updates on the same database simultaneously.

Like Flyway, applied changesets should be treated as immutable. If you edit an old changeset's contents, Liquibase may raise a checksum validation error. Create a new changeset to describe the next change.

## 11. Liquibase Preconditions

Preconditions check database state before running a changeset. For example, adding a column only if the table exists:

```yaml
databaseChangeLog:
  - changeSet:
      id: 003-add-phone
      author: team-platform
      preConditions:
        - onFail: HALT
        - tableExists:
            tableName: customer
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: phone
                  type: VARCHAR(30)
```

Common `onFail` options include `HALT`, `CONTINUE`, `MARK_RAN`, and `WARN`. Choose based on business semantics:

- `HALT`: stops the update when the condition is not met.
- `CONTINUE`: skips the changeset this time and continues processing.
- `MARK_RAN`: marks the changeset as executed even though its contents did not run.
- `WARN`: logs a warning and continues according to Liquibase semantics.

`MARK_RAN` and `CONTINUE` can mask schema drift if misused. For required changes such as creating columns/constraints, `HALT` is generally safer when a precondition fails. Preconditions are state checks, not a substitute for migration testing.

## 12. runOnChange, runAlways, Contexts, and Labels

Liquibase supports controlling when a changeset is applied:

- `runOnChange: true`: re-runs the changeset when its content checksum changes. Typically used for redefined views/procedures.
- `runAlways: true`: runs the changeset every time Liquibase update is invoked.
- `context`: associates a changeset with an environment group or purpose.
- `labels`: categorizes changesets to filter which group should execute.

Example:

```yaml
databaseChangeLog:
  - changeSet:
      id: 010-refresh-view
      author: team-platform
      runOnChange: true
      changes:
        - sqlFile:
            path: db/changelog/sql/customer-summary-view.sql
            relativeToChangelogFile: false
```

Do not put cumulative INSERTs or non-idempotent operations into `runOnChange`/`runAlways` if re-running would mutate data again. Use these attributes for objects whose definitions can be replaced or tasks designed to re-run safely.

Contexts and labels are deployment filters, not a security mechanism. Do not rely on contexts to skip mandatory migrations in production without an explicit process.

## 13. Rollback and Forward Fix

Rollback is part of migration planning, but not every change can be safely reversed.

For example, adding an empty column can be rolled back by dropping the column, but deleted data cannot be restored without a backup or copy. Changing a column type can lose precision; merging data may have no unique inverse.

Liquibase allows declaring rollback logic for a changeset:

```yaml
databaseChangeLog:
  - changeSet:
      id: 004-add-phone
      author: team-platform
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: phone
                  type: VARCHAR(30)
      rollback:
        - dropColumn:
            tableName: customer
            columnName: phone
```

This example rollback is only safe if data written to `phone` does not need to be retained. Many change types do not have suitable auto-generated rollbacks; declare them explicitly and test against a database copy.

Flyway primarily encourages moving forward with new versioned migrations. Undo capability depends on the edition and migration type; with SQL migrations, teams typically prepare a new migration to fix or reverse logic when possible.

In production, a forward fix is often safer than hastily rolling back the application/database. You can deploy a new migration that restores a compatible state, preserves data, and allows running application instances to continue operating.

## 14. How Should Hibernate ddl-auto Coordinate?

When Flyway or Liquibase manages the schema, Hibernate should verify mappings rather than altering database structures on its own:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

Common values:

| Value | Behavior | Recommendation |
| --- | --- | --- |
| `none` | Does not automatically create/update the schema | Can be used when migrations and schema checks are managed separately |
| `validate` | Validates mappings against the existing schema | Suitable for many deployment environments |
| `update` | Attempts to update the schema based on Entities | Avoid using as a production migration mechanism |
| `create` / `create-drop` | Creates a new schema; `create-drop` also drops it when the context closes | Only use in controlled test environments |

`ddl-auto=update` does not create reviewable migration history, does not express data backfills well, and can cause differences across environments. Never let Hibernate DDL generation and Flyway/Liquibase modify the same schema in the same release.

## 15. Migration Execution Order in Spring Boot

With standard auto-configuration, Spring Boot integrates Flyway/Liquibase so migrations run during application startup and before JPA uses the schema. This ensures Hibernate `validate` sees the updated schema.

In multi-replica production systems, consider running migrations as a dedicated deployment step/job before rolling out application instances. While tools use locks to coordinate when all instances start and attempt migrations simultaneously, running them separately avoids startup contention and makes rollback/recovery easier to control.

A typical deployment sequence is:

1. Build an artifact containing reviewed migrations.
2. Back up/snapshot or confirm the database recovery mechanism.
3. Run migrations using credentials with DDL privileges.
4. Verify migration status and schema.
5. Roll out the application version compatible with the new schema.
6. Monitor SQL errors, latency, locks, and connections.

Migrations and application code must remain compatible during rolling deployments, when old and new versions may run concurrently.

## 16. Expand-Contract for Zero-Downtime Deployments

When changing a schema actively used by an application, do not drop or rename columns immediately if older versions are still running. Use the expand-contract strategy:

**Expand:** add the new structure in a backward-compatible way, such as adding a nullable `display_name` column.

**Migrate data:** backfill legacy data into the new column in batches, optionally using a separate job with progress tracking.

**Transition:** deploy new code able to read/write compatibly with both old and new structures; then gradually switch reads to the new column.

**Contract:** once all old instances have stopped and no clients/jobs use the old column, drop the old column in a separate migration.

Example replacing `full_name` with `display_name`:

1. Release A adds nullable `display_name`, keeping `full_name`.
2. Backfill `display_name` from `full_name`.
3. Release B dual-writes both columns during the transition period.
4. Switch reads to `display_name` and verify data.
5. A later release removes logic writing `full_name`.
6. The final migration drops `full_name`.

Do not combine all six steps into a single migration if multiple application versions must coexist. Each step must be independently deployable and verifiable.

## 17. Schema Migration and Data Migration

Schema migrations change structure: creating tables, adding columns, constraints, indexes, views, or sequences. Data migrations transform existing values to fit the new model.

Example adding a status column with a default:

```sql
ALTER TABLE customer
    ADD COLUMN status VARCHAR(20);

UPDATE customer
SET status = 'ACTIVE'
WHERE status IS NULL;

ALTER TABLE customer
    ALTER COLUMN status SET NOT NULL;
```

This example may work for small tables. For large tables, a single UPDATE statement can hold locks for a long time, generate excessive WAL/redo logs, increase replication lag, and bloat transactions.

For large datasets, consider:

- Adding a nullable column first.
- Backfilling in batches with row limits and checkpoints.
- Monitoring locks, transaction duration, replication lag, and write throughput.
- Ensuring the job is resumable/idempotent.
- Verifying no NULLs remain before adding the NOT NULL constraint.
- Separating the backfill from the DDL release if needed.

Do not assume a SQL migration can safely re-run just because it uses `IF NOT EXISTS`. That clause can mask schema drift. Explicitly define the desired state and how to handle partially executed migrations.

## 18. Indexes and Constraints on Large Tables

Adding indexes or constraints can cause locks and impact live traffic. Syntax for online/concurrent index creation varies across databases:

```sql
-- PostgreSQL: creates an index while avoiding normal write blocking.
CREATE INDEX CONCURRENTLY idx_customer_status
    ON customer(status);
```

In PostgreSQL, `CREATE INDEX CONCURRENTLY` has specific limitations and cannot run inside a normal transaction block. When using Flyway/Liquibase, configure the migration/changeset to accommodate the statement's non-transactional requirement and understand how the tool records state if it fails mid-way.

Do not copy this syntax to MySQL, SQL Server, or Oracle; each engine has its own syntax and locking behavior. Test on the exact production database version.

Before adding a unique constraint, check for duplicate data and normalize business keys. Before adding a foreign key or NOT NULL, verify that existing data satisfies the condition.

## 19. Transactions, Locks, and Failed Migrations

Not all databases handle DDL transactions the same way. Some databases implicitly commit certain DDL statements, some statements cannot run inside a transaction block, and multi-step migrations may partially complete before failing.

Flyway and Liquibase have history/locking mechanisms, but they cannot make every DDL statement across every database atomic. When a migration fails:

1. Halt application rollout if the schema is in an incompatible state.
2. Read logs and identify which statements succeeded.
3. Inspect the actual schema and history table.
4. Do not manually edit/delete history records to force the tool to continue.
5. Determine whether it can be re-run, requires metadata repair, or needs a recovery migration.
6. Test the fix procedure on a database copy first.

In Liquibase, `runInTransaction` defaults to true; only set it to false when required by a database statement and after understanding the risk of a partially applied changeset. In Flyway, transactional capability depends on the database and statement types; verify the specific engine's behavior.

## 20. Multiple DataSources and Multiple Schemas

If an application uses multiple databases, each database needs a clear migration lifecycle. Do not let a single migration runner accidentally execute against the wrong DataSource.

With Flyway, you can configure separate Flyway beans per DataSource, specifying appropriate locations, schemas, and history tables. With Liquibase, configure separate beans specifying the DataSource, changelog, and schema history table.

If there are multiple schemas within the same database, a single migration tool can manage multiple schemas when configured properly; you must still specify the default schema, DDL privileges, and object scope.

Do not assume a single `@EnableJpaRepositories` or default `spring.flyway.*` automatically understands every custom persistence unit. Verify the specific Spring Boot configuration and test migrations on each database.

## 21. Credentials and Database Privileges

The runtime application usually only needs SELECT/INSERT/UPDATE/DELETE privileges on business tables. Migrations require DDL privileges such as CREATE/ALTER/DROP and potentially privileges to create indexes/sequences.

When architecture permits, use separate credentials:

- The migration user is granted schema-change privileges during the deployment window.
- The application user has only minimal runtime privileges.
- Never commit passwords or URLs containing secrets into the repository.
- Fetch credentials from a secret manager or managed environment.
- Log migration progress without printing authentication details.

Separating privileges limits the blast radius if the runtime application is compromised and clarifies which identity/tool is permitted to modify the schema.

## 22. CI/CD and Migration Review

Every pull request with Entity/schema changes should include the corresponding migration. The pipeline can:

1. Validate migration naming/versions or changeset identifiers.
2. Spin up a test database using the exact engine via Testcontainers.
3. Run all migrations from an empty schema.
4. Test upgrading from the previous version's schema.
5. Start the application with `ddl-auto=validate`.
6. Run integration tests for critical repositories and queries.
7. Test the migration against a representative copy of data when the change carries risk.

Migration reviews should examine locks, runtime, data loss, nullability, indexes, foreign keys, table size, rolling deployment compatibility, and recovery procedures.

Do not test only from an empty database. Production already has data and a schema at the previous version; the real upgrade path is what must be verified.

## 23. Flyway or Liquibase: Choosing by Need

| Need | Usually Suitable Choice |
| --- | --- |
| Team wants plain SQL, sequential versions, and simple history | Flyway |
| Need multiple changelog formats and structured changesets | Liquibase |
| Need preconditions, contexts, and labels to control changesets | Liquibase |
| Views/procedures need updating based on file definitions | Flyway repeatable or Liquibase `runOnChange` |
| Need declarative rollbacks per changeset | Liquibase can be more convenient, though each change type still needs verification |
| Database has extensive vendor-specific DDL and team wants explicit SQL control | Flyway or Liquibase with SQL changesets |

Decision factors that matter more than syntax include the team's operational familiarity, database engine, release strategy, rollback needs, review workflow, and existing CI/CD tooling.

## 24. Example Testing Migrations with Testcontainers

With Spring Boot, integration tests should run migrations on the same database type as production. Example test structure with PostgreSQL Testcontainers:

```java
@Testcontainers
@SpringBootTest
class DatabaseMigrationIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    JdbcTemplate jdbcTemplate;

    @Test
    void migrationCreatesCustomerTable() {
        Integer count = jdbcTemplate.queryForObject(
            "select count(*) from information_schema.tables " +
            "where table_name = 'customer'",
            Integer.class
        );

        assertEquals(1, count);
    }
}
```

This example assumes Testcontainers PostgreSQL/JUnit dependencies, the driver, and Spring Boot configuration are already in place. Spring Boot runs Flyway or Liquibase during context initialization. If the project has multiple DataSources, provide dynamic properties and migration config for the specific datasource under test.

Add upgrade tests from old schemas by initializing the database at the previous version, inserting representative data, and running the new migration. Verify both schema and data after backfilling.

## 25. Common Errors and Troubleshooting

**Application reports missing table/column at startup.** Check the migration dependency, locations/changelog, selected DataSource, and migration order relative to JPA `validate`.

**Flyway reports checksum mismatch.** An applied file was modified or line endings/contents changed. Restore the historical file or create a new migration; only use `repair` once you understand the database state and history.

**Flyway does not find migrations.** Check the `V` prefix, version, `__` separator, file extension, location, and whether resources are packaged into the artifact.

**Liquibase reports checksum validation failed.** An applied changeset was modified. Keep the old changeset and create a new changeset; do not delete history records to bypass validation.

**Liquibase does not run a changeset.** Check whether the master changelog includes the file, preconditions, contexts/labels, and `DATABASECHANGELOG` state.

**Migration succeeds locally but fails in production.** Causes may include differences in database engine/version, DDL privileges, collation, existing data, locking behavior, or transaction semantics. Test on a production-compatible engine and representative data.

**Two application instances start simultaneously and run migrations.** Check the tool's locking/history mechanism and consider separating migrations into a single deploy job before rollout.

**Hibernate unexpectedly creates/updates the schema.** Set `ddl-auto=validate` or `none` when a migration tool manages the schema; remove competing DDL generation.

**Large migration causes downtime or long locks.** Break into expand/backfill/contract phases, create indexes using database-appropriate methods, and run backfills in batches.

**Rollback causes data loss.** Define rollbacks before release; for hard-to-reverse data transformations, prefer backups and forward fixes.

## 26. Pre-Deployment Migration Checklist

- Choose a single tool as the source of truth for the database schema.
- Assign unique version numbers or changeset IDs with clear descriptions.
- Never edit migrations/changesets already applied in shared environments.
- Verify checksums and migration history.
- Use Hibernate `ddl-auto=validate` when a migration tool manages the schema.
- Test from an empty schema and upgrade from the currently running version.
- Use a production-compatible database engine, preferring Testcontainers.
- Evaluate locks, transactional DDL, execution duration, and data volume.
- Design expand-contract steps for rolling deployments.
- Separate large backfills from DDL if needed; ensure jobs are resumable/idempotent.
- Define backups, rollback, or forward-fix plans before release.
- Run migrations with appropriately privileged credentials and protect secrets.
- For multiple DataSources, explicitly configure the migration runner and schema for each database.
- Monitor history tables, logs, locks, and application health after deployment.

Flyway and Liquibase turn database changes into reviewable, repeatably deployable history. Flyway organizes migrations as versioned or repeatable files; Liquibase manages changesets in changelogs with preconditions and flexible filtering. Whichever tool you choose, keep applied migrations immutable, test on a production-compatible database, coordinate Hibernate with `validate`, and roll out changes in compatible steps to protect data and avoid downtime.
