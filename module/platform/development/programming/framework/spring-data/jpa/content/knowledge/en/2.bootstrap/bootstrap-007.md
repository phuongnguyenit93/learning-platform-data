# Configuring SQL and Query Parameter Logging by Environment

## 1. Objectives and Scope

When Spring Data JPA executes a query, Hibernate typically sends SQL to the database as parameterized statements, such as `WHERE status = ?`. To investigate a query, you need to observe two separate parts: the SQL statement generated by Hibernate and the values bound to each question mark. These two parts have different loggers and log levels.

This lesson applies to Spring Boot applications using Hibernate as the JPA provider, specifically Hibernate 6 in the Spring Boot 3.x lines. Profile-based configuration lets you enable detailed logs in development while keeping logs safe and low-noise in production.

## 2. Two Loggers to Distinguish

| Content | Logger | Typical Log Level |
| --- | --- | --- |
| SQL statements generated by Hibernate | `org.hibernate.SQL` | `DEBUG` |
| Values bound to JDBC parameters | `org.hibernate.orm.jdbc.bind` | `TRACE` |

- `org.hibernate.SQL` displays the SQL statement. Input values usually still appear as `?` placeholders because Hibernate uses prepared statements.
- `org.hibernate.orm.jdbc.bind` displays the data type and actual value bound to each parameter position. This logger requires the `TRACE` level; setting `DEBUG` is usually not enough.
- `spring.jpa.properties.hibernate.format_sql` only formats SQL across multiple lines for readability. It does not enable the logger and does not change the query semantics.

Do not confuse these two loggers with `spring.jpa.show-sql`. The `show-sql` property instructs Hibernate to print SQL directly to the console, making control via the logging framework, profiles, and appenders inconsistent. Leave it as `false` and manage logging via `logging.level`.

## 3. Default Configuration in application.yml

Place a safe baseline configuration in `src/main/resources/application.yml`. In the shared configuration, SQL is logged only at warning level and bind value logging is disabled:

```yaml
spring:
  jpa:
    show-sql: false
    properties:
      hibernate:
        format_sql: true

logging:
  level:
    org.hibernate.SQL: WARN
    org.hibernate.orm.jdbc.bind: 'OFF'
```

`format_sql: true` makes SQL statements easier to read when the logger is enabled. If the application needs more compact logs, you can set it to `false`; this change only affects formatting.

## 4. Enabling Detailed Logging in Development

Create `src/main/resources/application-dev.yml`:

```yaml
logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE
```

When running with the `dev` profile, Hibernate logs SQL statements at `DEBUG` level and parameter values at `TRACE` level. Illustrative example of a query finding users by status:

```text
DEBUG org.hibernate.SQL - select u.id, u.email, u.status from users u where u.status = ?
TRACE org.hibernate.orm.jdbc.bind - binding parameter (1:VARCHAR) <- [ACTIVE]
```

The exact format of the log lines depends on the Hibernate version and logging backend. What to verify is that SQL statements appear under the `org.hibernate.SQL` logger, while parameter values appear under the `org.hibernate.orm.jdbc.bind` logger.

## 5. Keeping Logs Safe in Production

Create `src/main/resources/application-prod.yml` or keep the default values in `application.yml`. If you want to state the production policy explicitly, use:

```yaml
logging:
  level:
    org.hibernate.SQL: WARN
    org.hibernate.orm.jdbc.bind: 'OFF'
```

Do not leave `TRACE` enabled for bind parameters permanently in production. Bound values can contain email addresses, phone numbers, identifiers, business data, or secrets. Verbose logging also increases log volume and can affect performance. When investigating a production incident, use a short time window, a narrow logger scope, controlled data, and appropriate log access/retention policies.

## 6. Selecting a Profile When Running the Application

Spring Boot loads `application.yml` as the shared configuration and additionally loads the file for the active profile. Values in `application-dev.yml` or `application-prod.yml` override corresponding settings in the shared file.

The recommended approach is to choose the profile from the deployment environment, rather than hardcoding a profile in a packaged configuration file:

```bash
export SPRING_PROFILES_ACTIVE=dev
./gradlew bootRun
```

On PowerShell:

```powershell
$env:SPRING_PROFILES_ACTIVE = 'dev'
.\gradlew.bat bootRun
```

When running a JAR, you can pass the profile as an argument:

```bash
java -jar app.jar --spring.profiles.active=prod
```

In Docker or deployment environments, set the `SPRING_PROFILES_ACTIVE` environment variable according to that environment's configuration. Avoid putting secrets or real environment data into committed configuration files.

## 7. Enabling Temporarily via Environment Variables

If you only need a quick investigation without modifying profile files, Spring Boot lets you set log levels via environment variables:

```bash
LOGGING_LEVEL_ORG_HIBERNATE_SQL=DEBUG
LOGGING_LEVEL_ORG_HIBERNATE_ORM_JDBC_BIND=TRACE
```

Set these variables in the process/container being inspected and remove them once finished. When configuration comes simultaneously from files, environment variables, and command-line arguments, Spring Boot applies the precedence order of its externalized configuration system; check the effective deployment configuration if log levels behave unexpectedly.

## 8. Verification Steps

1. Run the application with the `dev` profile and verify that the profile is active.
2. Perform an action that actually invokes a Spring Data JPA repository, such as finding records by a property.
3. Check the logs for SQL statements from `org.hibernate.SQL` at `DEBUG` level.
4. Check the logs for bind lines from `org.hibernate.orm.jdbc.bind` at `TRACE` level; match parameter positions with the `?` placeholders in the SQL statement.
5. Re-run with the `prod` profile and verify that bind values do not appear.
6. After the investigation finishes, remove temporary overrides and maintain the per-environment configuration policy.

Not every repository operation generates SQL immediately at the line calling the method. Hibernate may defer sending statements until transaction flush or commit. Therefore, when verifying, observe the entire operation within the transaction and ensure the query actually needs to access the database.

## 9. Common Configuration Mistakes

**SQL appears but parameter values do not.** Check whether the `org.hibernate.orm.jdbc.bind` logger is set to `TRACE`. Setting the SQL logger to `DEBUG` does not automatically display bind values.

**Set to `TRACE` but bind values still do not appear.** Verify the application uses Hibernate 6 and the logger category is correct. If the project uses Hibernate 5, the typical bind category is `org.hibernate.type.descriptor.sql.BasicBinder`; do not enable multiple old/new categories simultaneously without identifying the provider version.

**SQL is not formatted.** Check `spring.jpa.properties.hibernate.format_sql: true`. This property only formats the SQL statement; it does not replace `logging.level.org.hibernate.SQL`.

**Using `spring.jpa.show-sql: true` and unable to control logs.** Switch it back to `false` and configure Hibernate's loggers so logs flow through the application's logging system.

**No SQL appears when calling a repository.** Check whether the operation actually hits the database, whether it is served from cache, whether the transaction has flushed, and whether the application is using the intended profile/configuration.

**Logs show `?` instead of values.** This is normal prepared statement behavior. Bind values are logged under a separate logger, by parameter position.

## 10. Security and Operational Notes

- Only enable bind parameter logging in development or during controlled investigations.
- Do not record passwords, tokens, access keys, personal data, or sensitive payloads into shared logs.
- Use fake/anonymized test data when observing parameters is necessary.
- Limit how long `TRACE` is enabled, who can read logs, and log retention; disable temporary settings immediately after the investigation.
- For production, prefer metrics, tracing, slow query logs, and database observability tools. Only enable SQL/bind logging when there is a specific operational reason.

## 11. Quick Reference Table

| Need | Configuration |
| --- | --- |
| Disable printing SQL directly to console | `spring.jpa.show-sql: false` |
| Format SQL | `spring.jpa.properties.hibernate.format_sql: true` |
| Log SQL statements in development | `logging.level.org.hibernate.SQL: DEBUG` |
| Log bind values in development | `logging.level.org.hibernate.orm.jdbc.bind: TRACE` |
| Disable bind values in production | `logging.level.org.hibernate.orm.jdbc.bind: 'OFF'` |

This design gives each environment an appropriate level of observability: development gets full SQL and parameters to diagnose query issues; production keeps logs concise and reduces data exposure risk.
