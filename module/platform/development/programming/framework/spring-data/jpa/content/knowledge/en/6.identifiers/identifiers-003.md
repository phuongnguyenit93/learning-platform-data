# Comparing ID Generation Strategies: AUTO, IDENTITY, SEQUENCE, and TABLE

JPA provides four common primary key generation strategies via the **@GeneratedValue** annotation: **AUTO**, **IDENTITY**, **SEQUENCE**, and **TABLE**. They all help the application obtain key values for new entities, but how values are fetched, database requirements, insert batching capability, and concurrency costs differ significantly.

There is no single best strategy for every database system. The choice should be based on the actual database, JPA provider, write load, performance requirements, and schema control. This lesson uses Spring Data JPA, Jakarta Persistence, and Hibernate in Spring Boot 3.x for comparison.

## 1. What Problem Does @GeneratedValue Solve?

An entity usually needs a primary key so the database can distinguish each record. If the application assigns IDs manually, every place creating an entity must guarantee non-duplicate IDs, even when multiple instances run concurrently. Key generation mechanisms at the database/provider level help distribute values more safely.

Example of an entity with an auto-generated Long key:

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Customer() {
    }
}
```

**@Id** marks the primary key property. **@GeneratedValue** specifies the key generation mechanism. The **strategy** attribute selects the strategy; the **generator** attribute references the generator name declared with SequenceGenerator or TableGenerator when the strategy requires generator configuration.

These strategies apply to simple primary keys. Do not rely on @GeneratedValue to auto-generate part of a composite key. For composite keys, design an @EmbeddedId or @IdClass and an appropriate key assignment mechanism.

A technical ID should remain stable throughout the entity's lifecycle. Do not use auto-generated IDs in place of business numbers such as order numbers, invoice numbers, or transaction codes that have their own rules. Those numbers have specific formatting, scope, uniqueness, and sometimes continuity requirements.

## 2. Quick Comparison of the Four Strategies

| Strategy | ID Source | Database Requirement | Key Characteristics |
|---|---|---|---|
| AUTO | Provider automatically chooses a suitable strategy | Depends on provider and dialect | Minimal configuration; exact behavior depends on environment |
| IDENTITY | Table identity/auto-increment column | Database supports identity columns | ID is available after insert; Hibernate typically does not batch insert such entities |
| SEQUENCE | Database sequence | Database/provider supports sequences | Can pre-allocate one or more IDs; favorable for batching |
| TABLE | A table used to issue numbers | Only requires a table and suitable locking/updating mechanism | Relatively portable, but incurs extra operations and contention on the generator table |

### 2.1. AUTO

**AUTO** delegates the decision to the JPA provider. For a Long key, Hibernate chooses a strategy based on the dialect, version, and configuration. A database with sequences may use a sequence; another database may use identity or another appropriate mechanism.

```java
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

Advantages:

- Code depends less directly on a specific strategy.
- The provider can pick an approach suited to the database in use.
- Convenient for simple applications or when accepting provider-determined behavior.

Limitations:

- You cannot tell purely by reading the annotation whether the database will use a sequence, identity, or another mechanism.
- Switching databases or Hibernate dialects may change DDL and ID generation behavior.
- Harder to predict batching capability, ID allocation behavior, and database round trips without checking the actual configuration.

**AUTO does not mean always using auto-increment.** It means the provider has the authority to choose the strategy. If schema and performance behavior need to be predictable, consider specifying the strategy explicitly.

### 2.2. IDENTITY

**IDENTITY** uses an identity/auto-increment column where the database assigns the value on insert. Examples include PostgreSQL identity columns or MySQL AUTO_INCREMENT.

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Customer() {
    }
}
```

Illustrative DDL example for PostgreSQL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);
```

General flow:

1. The application creates a new entity with no ID yet.
2. The provider executes an INSERT into the database.
3. The database generates the ID.
4. The provider retrieves the generated ID and assigns it to the entity.

Because the ID is needed from the database after insert, Hibernate often has to execute the insert earlier than with some other strategies. With Hibernate, identity-generated entities typically cannot use standard JDBC insert batching because the provider needs the ID result of each insert. This is an important consideration for write-heavy systems.

Advantages:

- Easy-to-understand and widespread mapping.
- Many databases support identity/auto-increment directly.
- No need to declare a separate sequence or generator table.

Limitations:

- Inserts must rely on the database to obtain the ID.
- Hibernate typically does not batch insert IDENTITY entities, reducing throughput when writing many records.
- Difficult to allocate IDs before insert, making some entity graph flows or batching less flexible than sequences.

IDENTITY fits typical CRUD applications with moderate insert volume and a database that supports identity columns. If you have batch imports or bulk writes, benchmark with realistic workloads before choosing it.

### 2.3. SEQUENCE

**SEQUENCE** uses a database sequence to issue IDs. A sequence is a database object capable of generating an increasing numeric series independent of any specific table. The provider can fetch an ID in advance or allocate a block of IDs based on the allocation size.

```java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(
        strategy = GenerationType.SEQUENCE,
        generator = "purchaseOrderSequence"
    )
    @SequenceGenerator(
        name = "purchaseOrderSequence",
        sequenceName = "purchase_order_seq",
        initialValue = 1,
        allocationSize = 50
    )
    private Long id;

    @Column(name = "order_number", nullable = false, length = 40)
    private String orderNumber;

    protected PurchaseOrder() {
    }
}
```

There are three names to distinguish:

- **purchaseOrderSequence** in the name attribute is the generator name in JPA metadata.
- **purchase_order_seq** in sequenceName is the physical sequence name in the database.
- **generator = "purchaseOrderSequence"** in GeneratedValue references the generator name, not sequenceName directly.

Example migration for PostgreSQL when using Hibernate with a pooled allocation size of 50:

```sql
CREATE SEQUENCE purchase_order_seq
    START WITH 1
    INCREMENT BY 50;
```

**Note:** allocationSize describes how many IDs the provider may allocate from a single sequence fetch. With Hibernate and a pooled optimizer, the database sequence increment must be compatible with allocationSize; the example above illustrates Hibernate using a block size of 50. Optimization mechanisms and increment validation rules depend on the provider and version. When using a different provider or optimizer, follow the provider's documentation and verify via schema validation. If you want a simpler configuration, allocationSize = 1 with sequence increment 1 is easier to reason about, though it makes less use of block allocation.

Advantages:

- Can obtain the ID before inserting the entity.
- The provider can allocate a block of IDs and consume them gradually, reducing database round trips.
- Hibernate can batch inserts more favorably than with IDENTITY.
- The sequence is independent of the data table and can be intentionally reused via configuration.

Limitations:

- The database must support sequences and the dialect/provider must support them properly.
- Requires keeping sequence configuration, allocationSize, and optimizer aligned.
- Sequences can produce gaps when transactions roll back, the application restarts, or a pre-allocated block is not fully consumed.

Sequence is often a good choice for write-heavy systems on databases that support sequences, such as PostgreSQL and Oracle. With Hibernate, it is frequently worth considering when high insert throughput is needed.

### 2.4. TABLE

**TABLE** uses a database table to store ID counters. The provider reads/updates the value in the generator table and issues IDs for entities. This approach does not rely on specialized sequence or identity features, but it requires the database to support transactions and appropriate row locking.

```java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(
        strategy = GenerationType.TABLE,
        generator = "purchaseOrderTableGenerator"
    )
    @TableGenerator(
        name = "purchaseOrderTableGenerator",
        table = "id_generator",
        pkColumnName = "generator_key",
        valueColumnName = "next_value",
        pkColumnValue = "purchase_order",
        allocationSize = 50
    )
    private Long id;

    @Column(name = "order_number", nullable = false, length = 40)
    private String orderNumber;

    protected PurchaseOrder() {
    }
}
```

In the example:

- **purchaseOrderTableGenerator** is the generator name in JPA metadata.
- **id_generator** is the physical generator table name.
- **generator_key** is the column distinguishing counters.
- **next_value** is the column storing the counter value.
- **purchase_order** is the key value of the generator row for this entity.
- **allocationSize = 50** allows the provider to pre-allocate a block of IDs according to the generator configuration.

The generator table must be created and initialized to match the rules used by the provider. An illustrative structure:

```sql
CREATE TABLE id_generator (
    generator_key VARCHAR(100) PRIMARY KEY,
    next_value BIGINT NOT NULL
);
```

You must create the generator row with key **purchase_order** and an initial value compatible with the provider/DDL strategy. Do not guess the initial counter value or update it manually while the application is running. Check the DDL/schema export of your exact JPA provider and use migrations to manage both the structure and seed data.

If multiple entities share a generator table, each generator should have its own row key, such as purchase_order and customer. Do not configure two entities to use the same counter row unless you intentionally want them to share an ID sequence.

Advantages:

- Does not require the database to have sequences or identity columns.
- ID issuance mechanism relies on standard tables.
- Can pre-allocate blocks of IDs if allocation size is greater than 1.

Limitations:

- Each time an ID block is needed, the generator table must be read/updated.
- Concurrent transactions requesting IDs can contend for locks on the generator row.
- Introduces an extra table and migrations to manage.
- Throughput is usually worse than native sequences on databases with strong sequence support.

TABLE can be useful in database environments lacking sequences/identity or when broad compatibility is required. However, do not choose it simply assuming a generator table is simpler; locking and update overhead can be significant under high write load.

## 3. allocationSize and Block ID Allocation

Both SequenceGenerator and TableGenerator have an allocationSize attribute. This value indicates how many IDs the provider can allocate from a single generator fetch. The default value on the annotation is 50.

Example with allocationSize = 1:

- The provider fetches one generator value per ID.
- Simple configuration, easy to reconcile.
- Can cause more database round trips.

Example with allocationSize = 50:

- The provider fetches a block of IDs and consumes them in memory.
- Fewer generator accesses when inserting many entities.
- Gaps can appear when the application restarts or an allocated block is not fully used.

With Hibernate, optimizers can consume blocks in different ways. Some optimizers require the database sequence increment to match the allocation size; other configurations have different rules. Therefore, do not change allocationSize in the annotation while forgetting the sequence migration.

For example, if Hibernate uses a pooled allocation size of 50, a PostgreSQL sequence is typically configured with increment 50 as shown earlier. If Hibernate reports a sequence increment mismatch, check:

1. allocationSize in @SequenceGenerator.
2. The sequence increment in the database.
3. The Hibernate optimizer and dialect in use.
4. Hibernate's mismatch validation configuration.
5. Whether the migration has actually run on the target database.

Do not manually edit a sequence counter in production to silence a mismatch error without understanding already-issued IDs and existing data. Changing a generator requires a plan to avoid key collisions.

## 4. Why Are Auto-Generated IDs Not Continuous?

A common misconception is thinking IDs must increase sequentially without any gaps. ID generation strategies do not guarantee gap-free continuity.

Gaps can occur because:

- An insert transaction rolls back after an ID was allocated.
- A sequence pre-allocated a block, and the application only used part of it.
- The application restarts and discards unused IDs in the current block.
- A database sequence or identity increments, but the insert fails.
- Multiple application instances obtain independent ID blocks.

For example, a sequence issues block 1–50 to instance A and 51–100 to instance B. If A uses up to 5 and restarts, the remaining IDs in the block may be discarded. This is normal behavior for performance-optimized generators.

Do not use technical IDs as invoice numbers, order numbers, or document numbers that require continuity under legal or accounting rules. If you need a business number with specific rules, design a dedicated business number issuer with appropriate locking, transactions, and retry/rollback handling.

## 5. Batching Capability and Performance

A critical difference between strategies lies in when the provider obtains the ID:

| Strategy | When ID Is Obtained | Batch Insert with Hibernate | Generator Cost |
|---|---|---|---|
| AUTO | Depends on strategy chosen by provider | Depends on actual strategy | Depends on strategy |
| IDENTITY | After database insert | Usually does not batch insert identity-generated entities normally | Insert obtains ID directly from the table |
| SEQUENCE | Can be fetched before insert | Can batch insert favorably | Can be reduced via allocationSize |
| TABLE | Fetched from generator table before insert | Can batch insert after ID allocation | Reads/updates generator table; possible contention |

Do not rely solely on a comparison table to draw performance conclusions. JDBC driver, database, Hibernate version, batch size, number of entities in a transaction, and relationship mappings all affect the outcome.

If you need to insert thousands or millions of records:

- Measure execution time and SQL statement counts with representative data.
- Inspect Hibernate SQL logs or datasource metrics.
- Test appropriate sequence allocation sizes and JDBC batch sizes.
- For large batches, consider flushing/clearing in chunks to bound the persistence context.
- Measure the impact of cascades and entity relationships.
- Verify whether the ID generation strategy allows the provider to batch inserts.

Example Hibernate batch configuration:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
```

This configuration is a starting point for testing, not a guarantee that every insert will be batched. IDENTITY typically prevents Hibernate from grouping inserts of identity-keyed entities via standard batching. Sequence or Table can be more favorable because IDs are known beforehand, though you still must verify the driver, provider, and actual SQL executed.

## 6. Which Strategy Should You Choose?

### Choose IDENTITY When

- The database supports identity/auto-increment.
- The application is primarily standard CRUD.
- Bulk insert speed is not a bottleneck.
- You want simple configuration and want the database to assign IDs at insert time.

### Choose SEQUENCE When

- The database supports native sequences.
- There are many inserts or batch insert operations.
- You want the provider to allocate IDs before insert.
- You can manage sequences and allocationSize cleanly through migrations.

This is often a strong choice for Hibernate applications on PostgreSQL/Oracle with heavy write workloads.

### Choose TABLE When

- The database lacks suitable sequences.
- You need a table-based numbering mechanism that can be deployed broadly.
- Write load is not excessive or generator overhead has been measured.
- You can manage the generator table, counter rows, and concurrent locking.

### Choose AUTO When

- You want the provider to decide the strategy based on database/dialect.
- There are no strict requirements on physical generator type.
- You have verified the actual strategy chosen by the provider in each environment.

If predictable performance and schema behavior are required, specify the strategy explicitly instead of relying on AUTO.

## 7. Example of the Same Entity with All Four Strategies

Do not declare four annotations on the same field. These are four mutually exclusive alternatives; each option uses a separate entity mapping/version in practice.

**AUTO:**

```java
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

**IDENTITY:**

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

**SEQUENCE:**

```java
@Id
@GeneratedValue(
    strategy = GenerationType.SEQUENCE,
    generator = "purchaseOrderSeq"
)
@SequenceGenerator(
    name = "purchaseOrderSeq",
    sequenceName = "purchase_order_seq",
    allocationSize = 50
)
private Long id;
```

**TABLE:**

```java
@Id
@GeneratedValue(
    strategy = GenerationType.TABLE,
    generator = "purchaseOrderTable"
)
@TableGenerator(
    name = "purchaseOrderTable",
    table = "id_generator",
    pkColumnName = "generator_key",
    valueColumnName = "next_value",
    pkColumnValue = "purchase_order",
    allocationSize = 50
)
private Long id;
```

The generator name in the generator attribute must match the name of SequenceGenerator or TableGenerator exactly. The generator name is a JPA identifier, not the physical sequence or table name.

## 8. Testing and Schema Management

When schemas are managed with migrations, confirm the following elements:

- The ID column has a type compatible with the Java property.
- The identity column is created properly for IDENTITY.
- The sequence exists, has the exact name, and has an increment compatible with provider configuration for SEQUENCE.
- The generator table and counter rows are created properly for TABLE.
- Primary key and unique constraints are present.
- Two generators are not accidentally issuing IDs from the same range.
- Existing data does not conflict with the next value the generator will issue.

In test environments, you can use Testcontainers with the same database engine as production to verify real behavior. H2 does not fully represent PostgreSQL, MySQL, Oracle, or SQL Server; pay special attention to testing identity, sequences, locking, and native SQL.

With Hibernate, schema validation can detect certain mapping/schema mismatches at startup. Validation does not replace migrations and does not prove that all ID generation behavior under concurrent load is correct.

## 9. Common Errors

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Sequence does not exist | Migration did not create the sequence or sequenceName is wrong | Check migrations, schema, and sequence name |
| Sequence increment mismatch | allocationSize does not match Hibernate optimizer/sequence increment | Check provider, optimizer, allocationSize, and DDL |
| Duplicate key | Generator shared improperly, counter reset, or sequence behind existing data | Check generator state and existing data; plan a safe synchronization |
| IDENTITY inserts slow during bulk writes | Inserts must retrieve ID immediately, limiting batching | Benchmark SEQUENCE if supported by the database |
| TABLE generator contention | Multiple transactions update the same counter row | Increase allocationSize carefully or use native sequences |
| AUTO picks different strategy when switching databases | Provider/dialect determines the generator | Check DDL and behavior in target environment; specify strategy explicitly if needed |
| IDs have gaps | Rollback, block allocation, restart, or failed inserts | Accept gaps for technical IDs; use a dedicated business number issuer if required |
| Generator name not recognized | generator name in GeneratedValue differs from name in generator annotation | Match exact names and persistence unit scope |

## 10. Practice Exercises

1. Create a Customer entity using IDENTITY and observe the ID after save.
2. Create a PurchaseOrder entity using SEQUENCE with a dedicated sequenceName.
3. Change allocationSize from 1 to 50; inspect the sequence DDL and number of generator calls.
4. Create an entity using a TABLE generator with a dedicated counter row.
5. Run batch inserts with IDENTITY and SEQUENCE; enable SQL logging to compare insert/batch counts.
6. Try rolling back after the generator has issued an ID; observe the gap.
7. Change the database dialect in a test environment and inspect which strategy AUTO chooses.
8. Write migrations for sequence/table generators and enable schema validation.
9. Run multiple concurrent transactions to verify IDs do not collide.
10. Explain why auto-generated IDs are unsuitable for continuous invoice numbering.

**Guiding principle:** AUTO leaves the decision to the provider; IDENTITY gets IDs from an identity column on insert; SEQUENCE gets IDs from a sequence and can allocate blocks; TABLE gets IDs from a generator table. Choose based on database, provider, and write load; manage generators with migrations; accept gaps in technical IDs and keep business numbers in a separate mechanism.
