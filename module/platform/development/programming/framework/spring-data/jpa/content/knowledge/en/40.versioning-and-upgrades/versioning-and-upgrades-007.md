# Updating Annotation Processors for Metamodel and Querydsl

An annotation processor runs during Java compilation to analyze annotations on entities and generate supporting source code. In Spring Data JPA applications, two commonly generated code groups are:

- **JPA static metamodel:** classes with the `_` suffix, such as `Customer_`, used with the Criteria API to reference entity attributes with type checking.
- **Querydsl Q-types:** classes with the `Q` prefix, such as `QCustomer`, used to build statically typed predicates and queries with Querydsl.

These classes are generated from entities, so the processor configuration must match the versions of Java, Jakarta Persistence, Hibernate, Querydsl, and the build system. When upgrading Spring Boot or Hibernate, upgrading runtime dependencies alone is not enough; you must also update the processor path and verify that code is regenerated.

## 1. What does an annotation processor do?

During compilation, the Java compiler discovers annotation processors declared on the processor path, passes type/annotation metadata to the processor, and receives additional generated source files. The compiler then compiles those files alongside application source code.

Simplified workflow:

```text
Entity Java source
       |
       v
Java compiler + annotation processors
       |
       +--------------------------+
       |                          |
       v                          v
JPA metamodel generator      Querydsl APT
       |                          |
       v                          v
Customer_.java              QCustomer.java
       |                          |
       +-------------+------------+
                     |
                     v
             Compile generated code
                     |
                     v
               Application classes
```

Processors run at build time, not at application startup. Processor dependencies are typically placed in Gradle's `annotationProcessor` configuration or Maven's `annotationProcessorPaths`. There is no need to bundle processors into runtime solely to generate `Customer_` or `QCustomer`.

The two types of generated code serve different purposes:

| Generated code | Example | Purpose |
|---|---|---|
| JPA static metamodel | `Customer_` | Use typed attributes in JPA Criteria API, EntityGraph, and related JPA APIs |
| Querydsl Q-type | `QCustomer` | Use fluent API to build Querydsl predicates/queries |
| Hibernate Processor output | Static metamodel and some compile-time checks | Generates metamodel; newer versions can also validate HQL/JPQL at compile time |

Enabling one processor does not automatically generate the code of another processor. If a project uses both Criteria API typed metamodels and Querydsl, configure both processors appropriately.

## 2. JPA static metamodel and Criteria API

The JPA static metamodel represents entity attributes using typed fields. Example entity:

```java
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String email;

    private CustomerStatus status;

    protected Customer() {
    }
}
```

The processor can generate a `Customer_` class similar to:

```java
// Code generated by annotation processor; do not edit manually.
@StaticMetamodel(Customer.class)
public abstract class Customer_ {
    public static volatile SingularAttribute<Customer, Long> id;
    public static volatile SingularAttribute<Customer, String> email;
    public static volatile SingularAttribute<Customer, CustomerStatus> status;
}
```

Generated field names and details depend on mapping, access strategy, and the processor. Do not write or modify generated classes by hand.

Using the metamodel in the Criteria API:

```java
CriteriaBuilder builder = entityManager.getCriteriaBuilder();
CriteriaQuery<Customer> query = builder.createQuery(Customer.class);
Root<Customer> customer = query.from(Customer.class);

query.select(customer)
     .where(builder.equal(
             customer.get(Customer_.status),
             CustomerStatus.ACTIVE
     ));

List<Customer> result = entityManager
        .createQuery(query)
        .getResultList();
```

Compared to writing attribute names as strings like `customer.get("status")`, `Customer_.status` lets the compiler check types and catch attribute renames earlier.

The static metamodel is also useful when building joins, orders, dynamic predicates, or EntityGraphs. It does not replace the Criteria API; it adds type-safe attribute references.

## 3. Choosing the right Hibernate metamodel processor by version

Hibernate's artifact name has changed across version lines:

| Hibernate ORM | Annotation processor | Notes |
|---|---|---|
| Hibernate 5.x | `org.hibernate:hibernate-jpamodelgen` | Coordinates from the older line |
| Hibernate 6.x | `org.hibernate.orm:hibernate-jpamodelgen` | Use the same version as the running Hibernate ORM |
| Hibernate 7.x | `org.hibernate.orm:hibernate-processor` | Module renamed from `hibernate-jpamodelgen` |

In Hibernate 7, `Hibernate Processor` continues generating the Jakarta Persistence static metamodel and adds the ability to validate annotation-declared HQL/JPQL at compile time. Therefore, when upgrading Hibernate from 6 to 7, switch to the exact new processor artifact rather than blindly keeping the old configuration.

Gradle example for Hibernate 6:

```groovy
dependencies {
    implementation "org.hibernate.orm:hibernate-core:$hibernateVersion"
    annotationProcessor "org.hibernate.orm:hibernate-jpamodelgen:$hibernateVersion"
}
```

Gradle example for Hibernate 7:

```groovy
dependencies {
    implementation "org.hibernate.orm:hibernate-core:$hibernateVersion"
    annotationProcessor "org.hibernate.orm:hibernate-processor:$hibernateVersion"
}
```

`hibernateVersion` must match the Hibernate ORM version selected by Spring Boot dependency management. If the project uses the Spring Boot BOM, prefer letting the BOM manage Hibernate instead of manually upgrading `hibernate-core` or the processor to an incompatible version.

Select only one Hibernate metamodel processor matching the Hibernate line in use. Do not declare both `hibernate-jpamodelgen` and `hibernate-processor` for the same source set, as both can generate metamodel classes and cause duplicate generated sources.

## 4. How does Querydsl generate Q-types?

Querydsl is a library for constructing statically typed queries. The annotation processor reads entities and generates a corresponding Q class.

For `Customer`, the processor generates `QCustomer`, typically with attributes such as `id`, `email`, and `status`:

```java
// Auto-generated code; illustrative structure example.
public class QCustomer extends EntityPathBase<Customer> {

    public static final QCustomer customer =
            new QCustomer("customer");

    public final NumberPath<Long> id = createNumber("id", Long.class);
    public final StringPath email = createString("email");
    public final EnumPath<CustomerStatus> status =
            createEnum("status", CustomerStatus.class);
}
```

Using the Q-type to build a predicate:

```java
QCustomer customer = QCustomer.customer;

Predicate predicate = customer.status.eq(CustomerStatus.ACTIVE)
        .and(customer.email.containsIgnoreCase("example"));

Iterable<Customer> customers = customerRepository.findAll(predicate);
```

There is no need to write JPQL strings for each condition. The compiler checks attribute names and data types of Querydsl expressions. For instance, comparing `status` to a value of the wrong type is caught during compilation.

### 4.1. Integration with Spring Data JPA

Spring Data JPA provides `QuerydslPredicateExecutor` so repositories can accept a Querydsl `Predicate`:

```java
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.querydsl.QuerydslPredicateExecutor;

public interface CustomerRepository
        extends JpaRepository<Customer, Long>,
                QuerydslPredicateExecutor<Customer> {
}
```

Services can construct predicates from input criteria:

```java
@Service
public class CustomerSearchService {

    private final CustomerRepository repository;

    public CustomerSearchService(CustomerRepository repository) {
        this.repository = repository;
    }

    public Iterable<Customer> findActiveCustomers(String keyword) {
        QCustomer customer = QCustomer.customer;

        Predicate predicate = customer.status.eq(CustomerStatus.ACTIVE)
                .and(customer.email.containsIgnoreCase(keyword));

        return repository.findAll(predicate);
    }
}
```

The example assumes `CustomerStatus` is an enum and `CustomerRepository` resides in a package scanned by Spring Data. For pagination, `QuerydslPredicateExecutor` also provides methods accepting `Predicate` and `Pageable`.

Querydsl is not mandatory for every repository. Derived queries, JPQL, Criteria API, or Specifications may be a better fit depending on complexity. Use Querydsl when you need to assemble many statically typed dynamic conditions and want to reuse expressions.

## 5. Choosing Querydsl artifacts for Jakarta vs. javax

This is an easy place to make mistakes when upgrading an application from Spring Boot 2 to Spring Boot 3 or newer.

- Spring Boot 2 / JPA 2.x typically uses the `javax.persistence.*` namespace.
- Spring Boot 3+ / Jakarta Persistence 3+ uses the `jakarta.persistence.*` namespace.

The Querydsl processor and runtime library must be compatible with the entity namespace in use. If an entity imports `jakarta.persistence.Entity` while the processor only recognizes `javax.persistence.Entity`, Q-types may fail to generate or the build may fail with incompatible type errors.

There are two common options:

1. The original Querydsl artifacts under group `com.querydsl`, using the `jakarta` classifier for Jakarta Persistence.
2. The fork maintained by OpenFeign under group `io.github.openfeign.querydsl`; Spring Data JPA currently provides dedicated configuration examples for this fork and supports it on a best-effort basis.

Do not mix the runtime artifact from one fork with the annotation processor from the other fork. Pick one line and use the exact same version for `querydsl-jpa` and `querydsl-apt`.

### 5.1. Original Querydsl with the jakarta classifier

Example Maven coordinates for a Jakarta project:

```xml
<dependency>
    <groupId>com.querydsl</groupId>
    <artifactId>querydsl-jpa</artifactId>
    <version>${querydsl.version}</version>
    <classifier>jakarta</classifier>
</dependency>
```

The corresponding annotation processor also needs the `jakarta` classifier:

```xml
<path>
    <groupId>com.querydsl</groupId>
    <artifactId>querydsl-apt</artifactId>
    <version>${querydsl.version}</version>
    <classifier>jakarta</classifier>
</path>
```

Do not use this configuration in a project still using `javax.persistence` if the chosen artifact/version only supports Jakarta.

### 5.2. OpenFeign Querydsl fork

For the OpenFeign fork, the runtime dependency uses no classifier, while the processor uses the `jpa` classifier:

```xml
<dependency>
    <groupId>io.github.openfeign.querydsl</groupId>
    <artifactId>querydsl-jpa</artifactId>
    <version>${querydsl.version}</version>
</dependency>
```

Processor:

```xml
<path>
    <groupId>io.github.openfeign.querydsl</groupId>
    <artifactId>querydsl-apt</artifactId>
    <version>${querydsl.version}</version>
    <classifier>jpa</classifier>
</path>
```

Spring Data notes that maintenance of the original Querydsl slowed down and the community created the OpenFeign fork. Spring Data supports this fork on a best-effort basis, so check releases, issues, and compatibility with your Spring Data JPA version before upgrading.

## 6. Configuring Maven for Hibernate metamodel and Querydsl

The Maven Compiler Plugin lets you declare a dedicated processor path. This is where processors that run during compilation belong; there is no need to place them on the runtime classpath.

Example for a Jakarta application using Hibernate 7 and OpenFeign Querydsl. Version properties should be managed by the Spring Boot BOM or project dependency management:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <maven.compiler.plugin.version>3.15.0</maven.compiler.plugin.version>
    <hibernate.version>VERSION_FROM_BOOT_BOM</hibernate.version>
    <querydsl.version>QUERYDSL_VERSION</querydsl.version>
    <jakarta.persistence.version>JPA_API_VERSION</jakarta.persistence.version>
</properties>

<dependencies>
    <!-- Runtime Querydsl API -->
    <dependency>
        <groupId>io.github.openfeign.querydsl</groupId>
        <artifactId>querydsl-jpa</artifactId>
        <version>${querydsl.version}</version>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>${maven.compiler.plugin.version}</version>
            <configuration>
                <release>${maven.compiler.release}</release>
                <annotationProcessorPaths>
                    <!-- Hibernate 7: use hibernate-processor.
                         For Hibernate 6, change to hibernate-jpamodelgen. -->
                    <path>
                        <groupId>org.hibernate.orm</groupId>
                        <artifactId>hibernate-processor</artifactId>
                        <version>${hibernate.version}</version>
                    </path>

                    <!-- Querydsl OpenFeign fork -->
                    <path>
                        <groupId>io.github.openfeign.querydsl</groupId>
                        <artifactId>querydsl-apt</artifactId>
                        <version>${querydsl.version}</version>
                        <classifier>jpa</classifier>
                    </path>

                    <!-- Jakarta Persistence API for the processor -->
                    <path>
                        <groupId>jakarta.persistence</groupId>
                        <artifactId>jakarta.persistence-api</artifactId>
                        <version>${jakarta.persistence.version}</version>
                    </path>
                </annotationProcessorPaths>
                <generatedSourcesDirectory>
                    ${project.build.directory}/generated-sources/annotations
                </generatedSourcesDirectory>
            </configuration>
        </plugin>
    </plugins>
</build>
```

`VERSION_FROM_BOOT_BOM`, `QUERYDSL_VERSION`, and `JPA_API_VERSION` are placeholders to be replaced with your project's actual versions. Do not copy placeholders literally into your build. If the Spring Boot BOM already manages Hibernate/Jakarta API versions, keep them synchronized with runtime dependencies. Maven Compiler Plugin offers the `annotationProcessorPathsUseDepMgmt` option to apply dependency management to processor paths in appropriate setups; the simplest way to avoid ambiguity is to declare processor versions explicitly.

If using Hibernate 6, replace:

```xml
<artifactId>hibernate-processor</artifactId>
```

with:

```xml
<artifactId>hibernate-jpamodelgen</artifactId>
```

and continue using the version matching `hibernate-core`.

With JDK 23 and above, do not rely on the compiler automatically discovering processors on the compile classpath. Declare `annotationProcessorPaths` or an explicit processor list, and add `<proc>full</proc>` in `<configuration>` for Maven Compiler Plugin versions supporting that option. On older JDKs, only use `proc=full` if the compiler version supports it; otherwise omit that setting. Explicit declaration ensures builds do not rely on implicit processor discovery, which is disabled by default on newer JDKs.

## 7. Configuring Gradle

Gradle uses dedicated configurations for processors:

- `annotationProcessor`: processors for the main source set.
- `testAnnotationProcessor`: processors for the test source set.
- `implementation`: the Querydsl library called by application code.

Groovy DSL example with Hibernate 7 and OpenFeign Querydsl:

```groovy
dependencies {
    implementation "io.github.openfeign.querydsl:querydsl-jpa:$querydslVersion"

    // Hibernate 7 static metamodel + compile-time processor
    annotationProcessor "org.hibernate.orm:hibernate-processor:$hibernateVersion"

    // Querydsl Q-type generator for Jakarta Persistence
    annotationProcessor "io.github.openfeign.querydsl:querydsl-apt:$querydslVersion:jpa"
    annotationProcessor "jakarta.persistence:jakarta.persistence-api:$jakartaPersistenceVersion"

    // Only needed if test sources also declare entities needing Q-types/metamodel
    testAnnotationProcessor "org.hibernate.orm:hibernate-processor:$hibernateVersion"
    testAnnotationProcessor "io.github.openfeign.querydsl:querydsl-apt:$querydslVersion:jpa"
    testAnnotationProcessor "jakarta.persistence:jakarta.persistence-api:$jakartaPersistenceVersion"
}
```

For Hibernate 6, replace `hibernate-processor` with `hibernate-jpamodelgen`. If not using Querydsl, remove `querydsl-jpa` and `querydsl-apt`; if not using static metamodel/Hibernate compile-time processing, remove the corresponding Hibernate processor.

Kotlin DSL example:

```kotlin
dependencies {
    implementation("io.github.openfeign.querydsl:querydsl-jpa:$querydslVersion")

    annotationProcessor("org.hibernate.orm:hibernate-processor:$hibernateVersion")
    annotationProcessor("io.github.openfeign.querydsl:querydsl-apt:$querydslVersion:jpa")
    annotationProcessor("jakarta.persistence:jakarta.persistence-api:$jakartaPersistenceVersion")

    testAnnotationProcessor("org.hibernate.orm:hibernate-processor:$hibernateVersion")
    testAnnotationProcessor("io.github.openfeign.querydsl:querydsl-apt:$querydslVersion:jpa")
    testAnnotationProcessor("jakarta.persistence:jakarta.persistence-api:$jakartaPersistenceVersion")
}
```

Put versions in `gradle.properties`, version catalogs, or dependency constraints. Never let the Hibernate processor version differ from Hibernate ORM runtime. If the project uses Kotlin entities, annotation processing may require KAPT or KSP depending on plugins and processors; Java's `annotationProcessor` configuration does not automatically process all Kotlin sources.

## 8. Using both metamodel and Querydsl in the same project

Both processors can be configured together because they generate different class types:

- Hibernate/JPA processor generates `Customer_`.
- Querydsl APT generates `QCustomer`.

Side-by-side usage example:

```java
// JPA Criteria API
Root<Customer> root = criteriaQuery.from(Customer.class);
criteriaQuery.where(
        criteriaBuilder.equal(
                root.get(Customer_.status),
                CustomerStatus.ACTIVE
        )
);

// Querydsl
QCustomer qCustomer = QCustomer.customer;
Predicate predicate = qCustomer.status.eq(CustomerStatus.ACTIVE);
```

Do not declare two different generators that both produce the same static metamodel type. For example, if you already use Hibernate Processor to generate `Customer_`, do not add a second JPA metamodel generator producing the same class. By contrast, Querydsl APT generates `QCustomer`, so it can coexist with Hibernate Processor.

When using multiple processors, declare all of them in the same processor path and ensure each processor receives the proper annotation namespace. If the build reports duplicate generated types, check whether an old processor remains in dependencies, IDE settings, or another module.

## 9. Verifying generated code after an upgrade

After updating dependencies/configurations, run a clean build to purge old generated sources:

Maven:

```bash
mvn clean compile
```

Gradle:

```bash
./gradlew clean compileJava
```

With Gradle Kotlin or test entities, you may also need `compileTestJava`. With Maven, run `mvn clean test` to verify both test compilation and test runtime.

Inspect the generated source directories:

- Maven typically uses `target/generated-sources/annotations`.
- Gradle Java main typically uses `build/generated/sources/annotationProcessor/java/main`.
- Gradle test typically uses `build/generated/sources/annotationProcessor/java/test`.

Verify at a minimum:

1. The `Customer` entity produces `Customer_` if the Hibernate/JPA metamodel processor is enabled.
2. The `Customer` entity produces `QCustomer` if Querydsl APT is enabled.
3. Generated classes import `jakarta.persistence` or `javax.persistence` matching the project.
4. Application code can import and compile against the generated classes.
5. One sample Criteria query and one sample Querydsl predicate run against the test database.
6. The build has no warnings/errors about processor versions or duplicate classes.

Do not edit files inside the generated directory directly. Update the entity, annotations, or processor configuration and rebuild. Generated sources generally do not need to be committed to Git if the project can regenerate them on every build.

## 10. IDE configuration

IDEs may use their own build system to compile and sometimes do not sync processor configurations immediately after editing Maven/Gradle.

In IntelliJ IDEA:

1. Reload the Maven or Gradle project after updating dependencies.
2. Enable annotation processing in compiler settings if the IDE uses its internal compiler.
3. Verify the generated source directory is recognized as a Generated Sources Root.
4. Run a clean build from the terminal to compare with the IDE result.

In Eclipse, check Java Compiler > Annotation Processing and configure the factory path if the workspace does not pick up processors automatically from Maven/Gradle.

If the terminal build succeeds while the IDE reports `QCustomer` or `Customer_` cannot be found, the issue is usually that the IDE has not synced generated sources or annotation processing. If the terminal build also lacks the files, inspect the processor path and namespace.

## 11. Common errors when updating processors

| Symptom | Common cause | Resolution |
|---|---|---|
| `Customer_` is not generated | Missing Hibernate processor or wrong artifact for version | Hibernate 6 uses `hibernate-jpamodelgen`; Hibernate 7 uses `hibernate-processor` |
| `QCustomer` is not generated | Querydsl APT is not on the processor path | Declare `querydsl-apt` in Maven/Gradle annotation processor configuration |
| Q-types do not recognize Jakarta entities | Wrongly using `javax` processor variant | Choose the appropriate Jakarta classifier/variant |
| Build runs without generated code on newer JDK | Relying on implicit annotation processing | Declare processor paths explicitly |
| `javax.persistence` and `jakarta.persistence` incompatible | Mixing dependencies or processors from two namespaces | Align Spring Boot, JPA API, Hibernate, and Querydsl variants |
| Duplicate class `Customer_` | Two metamodel generators running or stale generated sources | Keep only one metamodel generator, run a clean build |
| Duplicate class `QCustomer` | Multiple Querydsl processors/forks configured | Choose one Querydsl fork and one APT path |
| `NoClassDefFoundError` during annotation processing | Processor missing required API or version skew | Add the API to the processor path and synchronize versions |
| IDE does not see Q-types while CLI build succeeds | IDE annotation processing not enabled/synced | Reload the build project and mark generated sources |
| Generated classes fail after changing entity package | Stale generated files left in output | Run a clean build and check source sets |
| Hibernate processor incompatible with Hibernate runtime | Using a version independent of dependency management | Use the same Hibernate ORM version or a BOM-supported version |

A common namespace error occurs when migrating a project from Spring Boot 2 to 3: entities changed imports to `jakarta.persistence`, but Querydsl still uses the `javax` artifact. You must update both the runtime library and the annotation processor, not just entity imports.

## 12. Annotation processor upgrade workflow

Follow this sequence for easier troubleshooting:

1. **Record current versions:** Java, Spring Boot, Spring Data JPA, Hibernate ORM, Jakarta Persistence, and Querydsl.
2. **Identify the namespace:** check whether entities import `javax.persistence` or `jakarta.persistence`.
3. **Select matching processors:** Hibernate 6 uses `hibernate-jpamodelgen`; Hibernate 7 uses `hibernate-processor`; Querydsl uses the matching Jakarta variant/fork.
4. **Update the build:** place processors in Maven `annotationProcessorPaths` or Gradle `annotationProcessor`; declare Querydsl runtime dependency separately.
5. **Align versions:** use the BOM or version properties consistent with ORM/runtime.
6. **Enable processing explicitly:** especially with JDK 23+ and the Maven Compiler Plugin.
7. **Remove old generated output:** run `clean` to avoid using classes generated from previous entities/versions.
8. **Inspect generated sources:** verify both `Customer_` and `QCustomer` are generated if the project uses both.
9. **Test queries:** compile Criteria API and Querydsl predicates, then run integration tests.
10. **Synchronize IDE and CI:** the same JDK, build tool, and processor config must be used locally and in pipelines.

Do not upgrade Querydsl/Hibernate processors independently beyond the compatibility range of your Spring Boot/Spring Data release. If framework dependency management does not yet support a newer version, inspect the compatibility matrix and migration guide before overriding.

## 13. Completion checklist

- [ ] Identified Java, Spring Boot, Spring Data JPA, Hibernate, and JPA API versions.
- [ ] Selected the right `javax` or `jakarta` namespace.
- [ ] Hibernate 6 uses `hibernate-jpamodelgen`; Hibernate 7 uses `hibernate-processor`.
- [ ] Only one processor generates the JPA static metamodel.
- [ ] Querydsl runtime and APT use the same fork/version.
- [ ] Querydsl Jakarta classifier/variant matches the entity namespace.
- [ ] Processors are declared on the compile-time path, not relying on runtime classpath.
- [ ] JDK 23+ has explicit annotation processing configuration.
- [ ] Generated sources are regenerated from a clean build.
- [ ] Criteria API can use `Customer_` and Querydsl can use `QCustomer`.
- [ ] Test sources have dedicated processors if tests declare entities needing generation.
- [ ] IDE and CI use the same build configuration.
- [ ] No committing or manual editing of generated sources against project conventions.

Updating annotation processors is part of upgrading the persistence stack. Align processors with your Hibernate version and Jakarta/Javax namespace, configure Querydsl APT separately from the runtime library, and verify generated sources with a clean build. Once `Customer_` and `QCustomer` generate cleanly and sample queries compile and pass tests, the project has a solid foundation to proceed with the upgrade.
