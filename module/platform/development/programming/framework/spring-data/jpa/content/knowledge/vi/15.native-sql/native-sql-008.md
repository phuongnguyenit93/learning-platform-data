# Truy vấn CTE, hàm cửa sổ và cú pháp riêng của cơ sở dữ liệu

## 1. Mục tiêu

SQL thuần là lựa chọn cần thiết khi truy vấn cần cấu trúc hoặc tính năng vượt ngoài JPQL chuẩn. Trong Spring Data JPA, bạn có thể khai báo native SQL bằng `@Query(nativeQuery = true)` hoặc dùng custom repository với `EntityManager`, `JdbcTemplate` hay `JdbcClient`.

Bài học tập trung vào ba nhóm kỹ thuật:
- **CTE (Common Table Expression):** đặt một truy vấn con có tên ở đầu câu lệnh bằng `WITH`; CTE đệ quy dùng để duyệt cây hoặc quan hệ phân cấp.
- **Window function:** tính thứ hạng, tổng lũy kế, giá trị trước/sau và thống kê trên một nhóm dòng mà vẫn giữ từng dòng kết quả.
- **Cú pháp riêng database:** dùng các tính năng như `ILIKE`, `DISTINCT ON`, `JSONB`, `FILTER`, `ON CONFLICT` của PostgreSQL và hiểu giới hạn khả chuyển.

Sau bài học, bạn có thể viết CTE và window function trong native query, ánh xạ kết quả vào projection, phân trang đúng cách, kiểm thử bằng chính database đích và quyết định khi nào nên chuyển truy vấn sang custom repository.

## 2. Khi nào cần native SQL?

JPQL làm việc với Entity và thuộc tính Java. Native SQL làm việc trực tiếp với schema database: bảng, cột, kiểu dữ liệu, CTE, window function và cú pháp của engine.

Chọn native SQL khi:
- Truy vấn cần CTE hoặc CTE đệ quy mà JPQL chuẩn của phiên bản đang dùng không biểu đạt được.
- Cần window function như `row_number()`, `rank()`, `lag()` hoặc `sum() over (...)`.
- Cần toán tử, kiểu dữ liệu hoặc hàm riêng của database.
- Cần tối ưu một truy vấn đã đo đạc và xác nhận kế hoạch thực thi của database.

Ưu tiên JPQL hoặc derived query khi chúng diễn đạt rõ ràng use case. Native SQL gắn chặt với tên bảng/cột và dialect nên cần kiểm thử, bảo trì cùng schema database.

Ví dụ trong bài dùng PostgreSQL 16 và Spring Boot 3.5.0. Cú pháp PostgreSQL được ghi rõ; không mặc định rằng cùng câu SQL chạy nguyên trạng trên MySQL, SQL Server, Oracle hoặc H2.

## 4. Mô hình dữ liệu ví dụ

Ta dùng bảng `sales_orders` để lưu đơn hàng. Mỗi đơn có khách hàng, trạng thái, tổng tiền và thời điểm tạo.

```sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    total_amount NUMERIC(14, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_sales_orders_customer_created
    ON sales_orders (customer_id, created_at DESC, id DESC);
```

Index hỗ trợ các truy vấn lọc theo khách hàng và sắp xếp đơn mới nhất. Chỉ tạo index sau khi xem workload và execution plan thực tế; mỗi index cũng làm tăng chi phí ghi và dung lượng lưu trữ.

### Entity SalesOrder

`src/main/java/com/example/orders/SalesOrder.java`:

```java
package com.example.orders;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "sales_orders")
public class SalesOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Column(nullable = false, length = 20)
    private String status;

    @Column(name = "total_amount", nullable = false, precision = 14, scale = 2)
    private BigDecimal totalAmount;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    protected SalesOrder() {
        // JPA cần constructor không tham số.
    }

    public SalesOrder(Long customerId, String status, BigDecimal totalAmount, Instant createdAt) {
        if (customerId == null || customerId <= 0) {
            throw new IllegalArgumentException("Customer ID must be positive");
        }
        if (status == null || status.isBlank() || status.length() > 20) {
            throw new IllegalArgumentException("Status is required");
        }
        if (totalAmount == null || totalAmount.signum() < 0) {
            throw new IllegalArgumentException("Total amount cannot be negative");
        }
        if (createdAt == null) {
            throw new IllegalArgumentException("Created time is required");
        }
        this.customerId = customerId;
        this.status = status;
        this.totalAmount = totalAmount;
        this.createdAt = createdAt;
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public BigDecimal getTotalAmount() {
        return totalAmount;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}
```

Entity ánh xạ cột database qua `@Column`. Tuy nhiên, native SQL bên dưới sẽ dùng tên bảng và tên cột trực tiếp, ví dụ `sales_orders`, `customer_id`, `total_amount` và `created_at`.

## 5. CTE không đệ quy với WITH

CTE đặt một truy vấn có tên ở đầu câu SQL. Truy vấn chính có thể tham chiếu CTE như một nguồn dữ liệu tạm thời trong phạm vi câu lệnh.

Cú pháp khái quát:

```sql
WITH cte_name AS (
    SELECT ...
)
SELECT ...
FROM cte_name;
```

CTE hữu ích để chia một truy vấn phức tạp thành các bước có tên. Ví dụ, lấy các đơn hàng đã thanh toán rồi tính tổng tiền theo khách hàng:

```sql
WITH paid_orders AS (
    SELECT customer_id, total_amount
    FROM sales_orders
    WHERE status = 'PAID'
),
customer_totals AS (
    SELECT customer_id, SUM(total_amount) AS total_spent
    FROM paid_orders
    GROUP BY customer_id
)
SELECT customer_id, total_spent
FROM customer_totals
WHERE total_spent >= 1000
ORDER BY total_spent DESC;
```

Ở đây:
- `paid_orders` lọc các đơn đã thanh toán.
- `customer_totals` tổng hợp doanh thu theo khách hàng từ CTE đầu tiên.
- Truy vấn cuối lọc các khách có tổng chi tiêu từ 1000 trở lên.

CTE không mặc nhiên là bảng vật lý hoặc bảng tạm tồn tại sau câu lệnh. Nó là tên của một tập kết quả trong phạm vi câu SQL. Database có thể inline hoặc materialize CTE tùy engine, phiên bản và cấu trúc truy vấn.

### Nhiều CTE và phụ thuộc giữa các bước

Một câu SQL có thể khai báo nhiều CTE, phân tách bằng dấu phẩy. CTE phía sau có thể tham chiếu CTE đứng trước:

```sql
WITH recent_orders AS (
    SELECT id, customer_id, total_amount, created_at
    FROM sales_orders
    WHERE created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+00'
),
large_orders AS (
    SELECT *
    FROM recent_orders
    WHERE total_amount >= 500
)
SELECT customer_id, COUNT(*) AS order_count, SUM(total_amount) AS revenue
FROM large_orders
GROUP BY customer_id
ORDER BY revenue DESC;
```

Việc đặt tên từng bước giúp đọc, kiểm tra và tối ưu truy vấn dễ hơn. Tránh tách quá nhiều CTE nhỏ nếu chúng không làm rõ logic.

## 6. CTE đệ quy với WITH RECURSIVE

CTE đệ quy phù hợp với dữ liệu phân cấp như danh mục cha-con, cây tổ chức, thư mục hoặc sơ đồ phụ thuộc.

Giả sử bảng `categories` có cấu trúc:

```sql
CREATE TABLE categories (
    id BIGINT PRIMARY KEY,
    parent_id BIGINT NULL REFERENCES categories(id),
    name VARCHAR(120) NOT NULL
);
```

Truy vấn sau tìm một danh mục gốc và toàn bộ hậu duệ của nó:

```sql
WITH RECURSIVE category_tree AS (
    SELECT id, parent_id, name, 0 AS depth, ARRAY[id] AS path
    FROM categories
    WHERE id = :root_id

    UNION ALL

    SELECT child.id, child.parent_id, child.name,
           parent.depth + 1, parent.path || child.id
    FROM categories child
    JOIN category_tree parent ON child.parent_id = parent.id
    WHERE NOT child.id = ANY(parent.path)
)
SELECT id, parent_id, name, depth
FROM category_tree
ORDER BY path;
```

CTE đệ quy có hai phần:
1. **Anchor member:** truy vấn đầu tiên lấy nút gốc, với depth bằng 0.
2. **Recursive member:** truy vấn sau join bảng gốc với kết quả của vòng trước để lấy các nút con.

`UNION ALL` nối các tầng kết quả. Trong ví dụ PostgreSQL, `ARRAY[id]`, phép nối mảng `||` và `ANY(path)` lưu đường đi đã thăm để chặn chu trình. Đây là cú pháp PostgreSQL; database khác có thể dùng kiểu dữ liệu và cách phát hiện cycle khác.

Điều kiện chống cycle đặc biệt quan trọng nếu dữ liệu có thể bị lỗi hoặc có quan hệ vòng. Cũng nên giới hạn độ sâu hoặc số nút trong use case có nguy cơ duyệt cây quá lớn.

## 7. Window function là gì?

Window function tính giá trị trên một tập dòng liên quan tới dòng hiện tại, được xác định bởi mệnh đề `OVER`. Khác với `GROUP BY`, window function không gộp nhiều dòng thành một dòng kết quả; mỗi dòng vẫn được giữ lại.

Cấu trúc:

```sql
some_function(expression) OVER (
    PARTITION BY group_column
    ORDER BY sort_column
    ROWS BETWEEN ...
)
```

- `PARTITION BY` chia kết quả thành các nhóm độc lập. Bỏ `PARTITION BY` thì toàn bộ tập kết quả là một partition.
- `ORDER BY` xác định thứ tự xử lý bên trong mỗi partition.
- Window frame như `ROWS BETWEEN ...` xác định phạm vi dòng được tính đối với những hàm hỗ trợ frame.

### 7.1. ROW_NUMBER, RANK và DENSE_RANK

Ba hàm này gán thứ hạng theo thứ tự trong mỗi partition:

| Hàm | Cách đánh số khi có giá trị bằng nhau |
| --- | --- |
| `ROW_NUMBER()` | Luôn là số thứ tự duy nhất 1, 2, 3, ... |
| `RANK()` | Các dòng đồng hạng nhận cùng hạng và hạng tiếp theo bị bỏ qua. |
| `DENSE_RANK()` | Các dòng đồng hạng nhận cùng hạng, hạng tiếp theo không bị bỏ qua. |

Ví dụ:

```sql
SELECT customer_id, id, total_amount,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total_amount DESC, id) AS row_no,
       RANK() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS amount_rank,
       DENSE_RANK() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS dense_rank
FROM sales_orders
WHERE status = 'PAID';
```

Nếu một khách có tổng tiền các đơn là 900, 900, 700 thì `RANK` trả 1, 1, 3; `DENSE_RANK` trả 1, 1, 2. `ROW_NUMBER` trả 1, 2, 3 theo thứ tự phụ `id`.

Luôn thêm tiêu chí phụ duy nhất như `id` khi cần thứ tự xác định cho `ROW_NUMBER`, phân trang hoặc chọn một dòng duy nhất. Nếu không, hai dòng bằng nhau có thể đổi thứ tự giữa các lần chạy.

### 7.2. LAG và LEAD

`LAG` đọc giá trị của dòng trước, `LEAD` đọc giá trị của dòng sau trong thứ tự của partition. Chúng hữu ích khi so sánh doanh thu hoặc trạng thái giữa các kỳ:

```sql
SELECT customer_id, created_at, total_amount,
       LAG(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
       ) AS previous_order_amount,
       LEAD(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
       ) AS next_order_amount
FROM sales_orders
WHERE status = 'PAID';
```

Ở dòng đầu tiên của mỗi khách hàng, `LAG` trả NULL nếu không có giá trị mặc định được chỉ định. Có thể dùng `LAG(total_amount, 1, 0)` để chỉ định giá trị thay thế khi không có dòng trước.

### 7.3. Tổng lũy kế với SUM OVER

```sql
SELECT customer_id, created_at, total_amount,
       SUM(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at, id;
```

`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` yêu cầu tổng từ dòng đầu partition tới dòng hiện tại. Khai báo frame tường minh giúp tránh khác biệt do default frame và các giá trị sort trùng nhau.

### 7.4. FIRST_VALUE, LAST_VALUE và frame

`FIRST_VALUE` và `LAST_VALUE` trả giá trị đầu/cuối trong window frame. Với `LAST_VALUE`, nếu frame mặc định kết thúc tại dòng hiện tại thì kết quả thường là giá trị của dòng hiện tại, không phải giá trị cuối cùng của cả partition.

Để lấy giá trị cuối cùng của partition:

```sql
SELECT customer_id, created_at, total_amount,
       LAST_VALUE(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS latest_partition_amount
FROM sales_orders
WHERE status = 'PAID';
```

Chọn frame đúng theo ý nghĩa nghiệp vụ. `ROWS` đếm dòng vật lý; `RANGE` dựa trên giá trị sort và có quy tắc xử lý peer rows khác nhau.

## 8. Kết hợp CTE và window function: lấy N đơn mới nhất mỗi khách

Đây là một mẫu truy vấn rất phổ biến: dùng `ROW_NUMBER()` đánh số đơn hàng trong từng khách hàng, sau đó lọc thứ hạng ở truy vấn ngoài.

```sql
WITH ranked_orders AS (
    SELECT o.id, o.customer_id, o.total_amount, o.created_at,
           ROW_NUMBER() OVER (
               PARTITION BY o.customer_id
               ORDER BY o.created_at DESC, o.id DESC
           ) AS row_number
    FROM sales_orders o
    WHERE o.status = :status
)
SELECT id, customer_id, total_amount, created_at, row_number
FROM ranked_orders
WHERE row_number <= :limit_per_customer
ORDER BY customer_id, row_number;
```

Không thể dùng alias `row_number` trong `WHERE` của cùng một SELECT ở nhiều hệ database vì WHERE được xử lý trước window expression. CTE tạo một tầng truy vấn bên ngoài để có thể lọc kết quả window.

Thêm `id DESC` vào thứ tự giúp phân định khi hai đơn có cùng `created_at`. Nếu bỏ tiêu chí phụ, kết quả thứ hạng giữa các đơn cùng thời điểm có thể không ổn định.

## 9. Ánh xạ kết quả native query vào projection

Native query có thể trả Entity nếu các cột được chọn khớp mapping Entity. Với kết quả tổng hợp hoặc window function, interface projection thường gọn hơn.

`src/main/java/com/example/orders/RankedOrderView.java`:

```java
package com.example.orders;

import java.math.BigDecimal;

public interface RankedOrderView {
    Long getId();
    Long getCustomerId();
    BigDecimal getTotalAmount();
    Long getRowNumber();
}
```

`src/main/java/com/example/orders/SalesOrderRepository.java`:

```java
package com.example.orders;

import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface SalesOrderRepository extends JpaRepository<SalesOrder, Long> {
    @Query(value = """
            WITH ranked_orders AS (
                SELECT o.id, o.customer_id, o.total_amount,
                       ROW_NUMBER() OVER (
                           PARTITION BY o.customer_id
                           ORDER BY o.created_at DESC, o.id DESC
                       ) AS row_number
                FROM sales_orders o
                WHERE o.status = :status
            )
            SELECT id AS "id",
                   customer_id AS "customerId",
                   total_amount AS "totalAmount",
                   row_number AS "rowNumber"
            FROM ranked_orders
            WHERE row_number <= :limitPerCustomer
            ORDER BY "customerId", "rowNumber"
            """, nativeQuery = true)
    List<RankedOrderView> findTopOrdersPerCustomer(
            @Param("status") String status,
            @Param("limitPerCustomer") int limitPerCustomer);
}
```

Trong native interface projection, alias cột nên khớp tên property của projection. PostgreSQL chuyển identifier không đặt trong dấu nháy kép thành chữ thường; dùng alias có dấu nháy kép như `"customerId"` và `"rowNumber"` để giữ đúng chữ hoa trong tên alias.

Named parameter trong native query hoạt động với Spring Data JPA và Hibernate như ví dụ. Theo mức khả chuyển JPA thuần, hỗ trợ named parameter cho native SQL không được bảo đảm đồng nhất giữa mọi provider; nếu cần portability cao, cân nhắc positional parameter hoặc custom repository kiểm soát việc bind.

## 10. Phân trang native query và countQuery

Với native query trả `Page<T>`, nên khai báo `countQuery` riêng để Spring Data biết cách đếm tổng số dòng. Ví dụ lọc đơn theo trạng thái:

```java
@Query(
        value = "select * from sales_orders o where o.status = :status order by o.created_at desc, o.id desc",
        countQuery = "select count(*) from sales_orders o where o.status = :status",
        nativeQuery = true)
Page<SalesOrder> findPageByStatus(
        @Param("status") String status, Pageable pageable);
```

Count query phải đếm cùng tập kết quả logic với query chính, nhưng không cần giữ `ORDER BY`. Nếu query chính có CTE, group by hoặc window function, count query có thể cần một CTE tương tự rồi `SELECT COUNT(*)` ở ngoài.

Với query phức tạp, không dựa vào việc framework tự suy ra count query. Hãy viết và kiểm thử `countQuery` rõ ràng.

Native SQL động và Sort cần cẩn thận. Không nối tên cột hoặc chiều sort trực tiếp từ request vào SQL. Hãy whitelist các lựa chọn được phép, hoặc khai báo thứ tự cố định trong query. Khi dùng native query có `Pageable`, truyền page/size riêng và kiểm tra SQL được sinh ra theo phiên bản Spring Data đang dùng.

Nếu chỉ cần biết có trang tiếp theo mà không cần tổng số dòng, cân nhắc `Slice` hoặc truy vấn giới hạn số dòng cộng thêm một bản ghi để xác định còn dữ liệu.

## 11. Cú pháp riêng của PostgreSQL

Native SQL cho phép dùng tính năng riêng của engine. Các ví dụ dưới đây là PostgreSQL, không phải JPQL chuẩn.

### 11.1. ILIKE

`ILIKE` so sánh chuỗi không phân biệt hoa/thường theo quy tắc collation của PostgreSQL:

```sql
SELECT id, customer_id, status
FROM sales_orders
WHERE status ILIKE 'paid';
```

Database khác có thể dùng `LOWER(column) = LOWER(?)`, collation riêng hoặc toán tử khác.

### 11.2. DISTINCT ON

`DISTINCT ON` giữ một dòng cho mỗi nhóm key theo thứ tự `ORDER BY`. Nó là cú pháp PostgreSQL:

```sql
SELECT DISTINCT ON (customer_id)
       id, customer_id, total_amount, created_at
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at DESC, id DESC;
```

Để xác định dòng nào được giữ, biểu thức `DISTINCT ON` phải khớp phần đầu của `ORDER BY`. Nếu cần portability, dùng CTE cộng `ROW_NUMBER()` thay thế.

### 11.3. Aggregate FILTER

PostgreSQL hỗ trợ `FILTER (WHERE ...)` trên aggregate:

```sql
SELECT customer_id,
       COUNT(*) AS all_orders,
       COUNT(*) FILTER (WHERE status = 'PAID') AS paid_orders,
       SUM(total_amount) FILTER (WHERE status = 'PAID') AS paid_total
FROM sales_orders
GROUP BY customer_id;
```

Đây là cách viết gọn hơn một số biểu thức `CASE WHEN`, nhưng cần kiểm tra hỗ trợ của database mục tiêu.

### 11.4. JSONB

PostgreSQL có kiểu `jsonb` và các toán tử như `->>`, `@>`:

```sql
SELECT id, metadata ->> 'source' AS source
FROM audit_events
WHERE metadata @> '{"channel":"web"}'::jsonb;
```

`->>` lấy giá trị JSON dưới dạng text; `@>` kiểm tra containment. Có thể tạo GIN index cho một số workload JSONB, nhưng cần chọn operator class và index dựa trên toán tử truy vấn thực tế.

### 11.5. ON CONFLICT

`ON CONFLICT` hỗ trợ upsert theo unique constraint hoặc unique index:

```sql
INSERT INTO customer_preferences (customer_id, preference_key, preference_value)
VALUES (101, 'language', 'vi')
ON CONFLICT (customer_id, preference_key)
DO UPDATE SET preference_value = EXCLUDED.preference_value;
```

Đây là cú pháp PostgreSQL. Khi cần trả về các dòng bị insert/update bằng `RETURNING`, có thể dùng JDBC/custom repository để kiểm soát result set; không giả định một phương thức `@Modifying` thông thường sẽ ánh xạ mọi dạng `RETURNING` thành Entity một cách portable.

## 12. CTE materialization và tối ưu truy vấn PostgreSQL

Trong PostgreSQL, CTE không phải lúc nào cũng là optimization fence. Từ PostgreSQL 12, planner có thể inline một số CTE không đệ quy được tham chiếu một lần, cho phép tối ưu xuyên qua ranh giới CTE.

Có thể chỉ định:

- `MATERIALIZED`: yêu cầu tính CTE thành kết quả trung gian.
- `NOT MATERIALIZED`: cho phép inline CTE đủ điều kiện.

Ví dụ:

```sql
WITH filtered_orders AS NOT MATERIALIZED (
    SELECT *
    FROM sales_orders
    WHERE status = 'PAID'
)
SELECT customer_id, SUM(total_amount)
FROM filtered_orders
GROUP BY customer_id;
```

Không thêm `MATERIALIZED` hoặc `NOT MATERIALIZED` theo cảm tính. Chúng có thể ảnh hưởng tới việc tính lại CTE, pushdown predicate và lượng dữ liệu trung gian. Đo bằng dữ liệu thực tế.

### EXPLAIN và EXPLAIN ANALYZE

Dùng execution plan để kiểm tra database thực sự thực thi truy vấn như thế nào:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, id, created_at
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at DESC, id DESC;
```

`EXPLAIN` cho biết kế hoạch ước tính. `EXPLAIN ANALYZE` thực thi câu lệnh và báo số liệu thực tế như thời gian, số dòng và số lần lặp. Khi dùng với `UPDATE` hoặc `DELETE`, câu lệnh sẽ thật sự chạy; chỉ thực hiện trong môi trường an toàn hoặc transaction có thể rollback phù hợp.

Đọc các điểm chính:
- `Seq Scan`: quét tuần tự; không mặc nhiên là xấu nếu bảng nhỏ hoặc phần lớn dòng cần đọc.
- `Index Scan` / `Bitmap Index Scan`: sử dụng index.
- `Sort`: sắp xếp; kiểm tra lượng dòng và bộ nhớ/sort spill.
- Estimated rows so với actual rows: chênh lệch lớn có thể cho thấy statistics hoặc cardinality estimate chưa tốt.
- `Buffers`: lượng block đọc từ cache hoặc storage.

## 13. Bulk DML và transaction

Native update/delete trong Spring Data JPA cần `@Modifying` và transaction:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Transactional
@Query(value = "update sales_orders set status = :newStatus where status = :oldStatus",
       nativeQuery = true)
int changeStatus(
        @Param("oldStatus") String oldStatus,
        @Param("newStatus") String newStatus);
```

Giá trị trả về là số dòng bị ảnh hưởng. `flushAutomatically` đồng bộ thay đổi đang chờ trước bulk query; `clearAutomatically` xóa persistence context sau đó để tránh tiếp tục dùng Entity managed có dữ liệu cũ.

Native bulk DML đi thẳng tới database:
- Không tải từng Entity để chạy dirty checking.
- Không gọi lifecycle callback của từng Entity như `@PreUpdate` hoặc `@PreRemove`.
- Không áp dụng cascade Entity lifecycle như khi gọi thao tác trên từng Entity.
- Có thể khiến Entity đang managed trong persistence context không còn đồng bộ với database.

Nếu nghiệp vụ yêu cầu validation hoặc side effect cho từng Entity, hãy tải Entity và xử lý trong Service. Nếu bulk statement là lựa chọn đúng, cập nhật mọi cột audit cần thiết ngay trong SQL hoặc dùng trigger database đã được thiết kế rõ ràng.

## 14. Kiểm thử native SQL với đúng database engine

CTE, window function và cú pháp riêng của PostgreSQL không nên chỉ kiểm thử trên H2 rồi suy ra sẽ chạy giống PostgreSQL. H2 có compatibility mode nhưng không thay thế hoàn toàn engine thật.

Với integration test, dùng Testcontainers để khởi chạy PostgreSQL giống môi trường mục tiêu. Dependency test:

```xml
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>1.20.6</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <version>1.20.6</version>
    <scope>test</scope>
</dependency>
```

Test minh họa:

```java
package com.example.orders;

import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class SalesOrderNativeQueryTest {
    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("orderdb")
                    .withUsername("test")
                    .withPassword("test");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        registry.add("spring.datasource.driver-class-name", postgres::getDriverClassName);
        registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
    }

    @Autowired
    private SalesOrderRepository repository;

    @Autowired
    private TestEntityManager entityManager;

    @Test
    void returnsLatestPaidOrderPerCustomer() {
        entityManager.persist(new SalesOrder(
                10L, "PAID", new BigDecimal("10.00"), Instant.parse("2026-01-01T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                10L, "PAID", new BigDecimal("20.00"), Instant.parse("2026-01-02T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                20L, "PAID", new BigDecimal("30.00"), Instant.parse("2026-01-03T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                10L, "CANCELLED", new BigDecimal("99.00"), Instant.parse("2026-01-04T10:00:00Z")));
        entityManager.flush();

        List<RankedOrderView> result = repository.findTopOrdersPerCustomer("PAID", 1);

        assertThat(result).hasSize(2);
        assertThat(result).extracting(RankedOrderView::getCustomerId)
                .containsExactly(10L, 20L);
        assertThat(result).extracting(RankedOrderView::getTotalAmount)
                .containsExactly(new BigDecimal("20.00"), new BigDecimal("30.00"));
        assertThat(result).extracting(RankedOrderView::getRowNumber)
                .containsOnly(1L);
    }
}
```

Test này kiểm tra CTE, `ROW_NUMBER()`, partition theo khách hàng, thứ tự mới nhất và ánh xạ alias vào interface projection. Chạy bằng:

```bash
mvn test
```

Kết quả mong đợi là `BUILD SUCCESS` và test PostgreSQL hoàn thành. Testcontainers cần Docker hoạt động; đây là kết quả kỳ vọng của ví dụ, không phải log build đã chạy trong môi trường này.

## 15. Chọn cách ánh xạ kết quả native query

| Dạng kết quả | Cách dùng |
| --- | --- |
| Toàn bộ Entity | Chọn các cột cần thiết theo mapping Entity; thường dùng `select *` chỉ khi schema/result phù hợp và ổn định. |
| Interface projection | Alias cột khớp property getter của projection. |
| DTO class/record | Dùng `@SqlResultSetMapping`, constructor mapping phù hợp hoặc custom repository để tự ánh xạ. |
| Scalar/aggregate | Dùng kiểu đơn giản hoặc projection có tên field; tránh `Object[]` khi kết quả cần bảo trì lâu dài. |

Với native query trả nhiều cột không khớp Entity, đừng giả định Spring Data luôn suy ra DTO constructor theo thứ tự cột. Hãy dùng interface projection với alias rõ ràng hoặc khai báo result set mapping tường minh.

## 16. Lỗi thường gặp

| Hiện tượng | Nguyên nhân | Cách xử lý |
| --- | --- | --- |
| Native query báo không tìm thấy bảng/cột | Dùng tên Entity/property thay vì tên schema thật hoặc mapping không khớp. | Kiểm tra DDL, schema, table và column name của database. |
| CTE chạy trên PostgreSQL nhưng lỗi trên H2/MySQL | Cú pháp hoặc khả năng hỗ trợ khác nhau giữa engine. | Kiểm thử trên đúng database mục tiêu và phân loại rõ SQL theo dialect. |
| Window alias không dùng được trong WHERE | Window expression được tính sau WHERE của cùng SELECT. | Đặt window query trong CTE/subquery rồi lọc ở lớp ngoài. |
| Kết quả ROW_NUMBER không ổn định | ORDER BY không phân định được các dòng bằng nhau. | Thêm tiêu chí phụ duy nhất như primary key. |
| `Page` có tổng số sai | Count query không cùng điều kiện với query chính. | Khai báo `countQuery` tương ứng và kiểm thử cả nội dung lẫn tổng số. |
| Projection trả null cho một thuộc tính | Alias không khớp getter hoặc driver/provider trả kiểu khác dự kiến. | Alias rõ ràng, kiểm tra kiểu JDBC và dùng projection phù hợp. |
| Entity managed có dữ liệu cũ sau native DML | Bulk SQL bỏ qua persistence context. | Flush trước nếu cần và clear/refresh sau khi cập nhật. |
| Truy vấn chậm dù đã dùng CTE | CTE không bảo đảm tự động nhanh hơn; plan hoặc index chưa phù hợp. | Dùng `EXPLAIN (ANALYZE, BUFFERS)` và tối ưu dựa trên số liệu. |
| SQL injection qua ORDER BY động | Nối trực tiếp tên cột hoặc chiều sort từ request. | Whitelist identifier/sort direction; bind parameter chỉ dành cho giá trị. |

## 17. Nguyên tắc thiết kế và vận hành

1. Dùng JPQL khi truy vấn có thể biểu đạt rõ ràng bằng mô hình Entity; dùng native SQL khi cần CTE, window function hoặc tính năng database.
2. Viết rõ database và phiên bản mục tiêu cho truy vấn phụ thuộc dialect.
3. Chia truy vấn phức tạp thành CTE có tên phản ánh ý nghĩa từng bước.
4. Dùng window function thay vì self-join nhiều lần khi cần xếp hạng, so sánh dòng trước/sau hoặc tổng lũy kế.
5. Luôn tạo thứ tự xác định khi dùng `ROW_NUMBER`, pagination hoặc chọn bản ghi mới nhất.
6. Khai báo `countQuery` chính xác cho native Page query.
7. Dùng projection hoặc DTO để chỉ lấy dữ liệu cần thiết và tránh hydrate toàn bộ Entity.
8. Không nối chuỗi đầu vào người dùng vào SQL identifier hoặc biểu thức; whitelist sort field và bind mọi giá trị.
9. Xử lý persistence context sau bulk native DML và nhớ rằng lifecycle callback không chạy cho từng Entity.
10. Đo hiệu năng bằng execution plan và dữ liệu gần thực tế; không giả định CTE, index hoặc window function luôn nhanh hơn.
11. Kiểm thử native SQL trên cùng engine và phiên bản với môi trường triển khai; Testcontainers giúp giảm khác biệt giữa dev và CI.
12. Quản lý thay đổi schema bằng migration có phiên bản, kiểm tra index và constraint cùng truy vấn phụ thuộc.
