# Quan hệ một-một dùng khóa chính chung với @MapsId

Trong quan hệ một-một dùng khóa chính chung, entity con sử dụng **chính khóa chính của entity cha làm khóa chính của mình**, đồng thời khóa đó cũng là khóa ngoại tham chiếu về bảng cha. JPA biểu diễn kiểu quan hệ này bằng **@OneToOne + @MapsId**.

Ví dụ, một Customer có thể có một CustomerProfile. Bảng customer_profiles không cần một cột id riêng và cũng không cần sequence riêng. Cột customer_id vừa là primary key của customer_profiles, vừa là foreign key tới customers.id. Cách thiết kế này phù hợp khi hồ sơ phụ thuộc chặt vào danh tính và vòng đời của khách hàng.

## 1. Shared primary key là gì?

Với quan hệ một-một thông thường, bảng con có thể có khóa chính riêng và một cột foreign key unique:

```text
customers
+----+-----------+
| id | name      |
+----+-----------+
| 10 | An        |
+----+-----------+

customer_profiles
+----+-------------+----------------+
| id | customer_id | display_name   |
+----+-------------+----------------+
| 55 | 10          | An Nguyen      |
+----+-------------+----------------+
```

Trong ví dụ trên, profile có ID 55 riêng và customer_id = 10 tham chiếu khách hàng.

Với shared primary key, child dùng cùng giá trị khóa của parent:

```text
customers
+----+-----------+
| id | name      |
+----+-----------+
| 10 | An        |
+----+-----------+

customer_profiles
+-------------+----------------+
| customer_id | display_name   |
+-------------+----------------+
| 10          | An Nguyen      |
+-------------+----------------+
```

Cột customer_id trong customer_profiles đồng thời là:

- Primary key của customer_profiles.
- Foreign key tham chiếu customers.id.
- Giá trị định danh của CustomerProfile.
- Giá trị bằng với Customer.id.

Vì primary key của bảng con là duy nhất, một Customer không thể có hai CustomerProfile. Tuy nhiên, một Customer vẫn có thể chưa có profile. Ràng buộc một-một ở phía child bảo đảm mỗi profile phải thuộc về đúng một customer và tối đa một profile được gắn với một customer.

## 2. Khi nào nên dùng khóa chính chung?

Shared primary key phù hợp khi entity con phụ thuộc về mặt danh tính vào entity cha:

- Customer và CustomerProfile.
- User và UserSettings.
- Employee và EmployeePrivateDetails.
- Product và ProductSpecification riêng biệt theo từng sản phẩm.
- Account và AccountPreferences.

Đặc điểm chung là entity con không có ý nghĩa định danh độc lập ngoài entity cha. Khi parent không tồn tại thì child cũng không nên tồn tại.

Không nên dùng shared primary key chỉ vì hai bảng có quan hệ một-một. Nếu entity con có vòng đời độc lập, cần được tạo trước parent, có thể được tham chiếu từ nơi khác hoặc cần ID riêng để tích hợp hệ thống, một khóa chính riêng cộng với unique foreign key có thể phù hợp hơn.

## 3. Cấu trúc database

Ví dụ schema PostgreSQL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);

CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120),
    bio VARCHAR(1000),
    CONSTRAINT fk_customer_profiles_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

Không có cột profile_id riêng. customer_id là primary key nên đã tự bảo đảm tính duy nhất; không cần thêm một unique constraint thứ hai trên cùng cột.

Foreign key bảo đảm không thể tạo profile trỏ tới customer không tồn tại. Primary key của child bảo đảm mỗi customer có tối đa một profile.

Lưu ý: schema này không bắt buộc mọi customer phải có profile. Nó chỉ bảo đảm mỗi profile phải có một customer. Nếu nghiệp vụ yêu cầu mọi customer đều phải có profile, cần kiểm soát ở tầng nghiệp vụ/transaction hoặc thiết kế schema khác; một foreign key từ child tới parent không tự áp đặt chiều bắt buộc ngược lại.

## 4. Ánh xạ bằng @MapsId

JPA cung cấp **@MapsId** để biểu diễn derived identity: khóa của entity được suy ra từ một quan hệ tới entity khác.

Entity cha:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 160)
    private String name;

    @OneToOne(
        mappedBy = "customer",
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private CustomerProfile profile;

    protected Customer() {
    }

    public Customer(String name) {
        this.name = name;
    }

    public void attachProfile(CustomerProfile profile) {
        this.profile = profile;
        profile.attachTo(this);
    }

    public Long getId() {
        return id;
    }
}
```

Entity con:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "customer_profiles")
public class CustomerProfile {

    @Id
    private Long id;

    @MapsId
    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @Column(name = "display_name", length = 120)
    private String displayName;

    @Column(length = 1000)
    private String bio;

    protected CustomerProfile() {
    }

    public CustomerProfile(String displayName, String bio) {
        this.displayName = displayName;
        this.bio = bio;
    }

    void attachTo(Customer customer) {
        this.customer = customer;
    }

    public Long getId() {
        return id;
    }
}
```

Các điểm quan trọng:

1. Customer.id là khóa chính được database sinh bằng IDENTITY.
2. CustomerProfile.id được đánh dấu @Id nhưng **không có @GeneratedValue**.
3. @MapsId cho biết ID của CustomerProfile được lấy từ khóa của Customer được tham chiếu.
4. @JoinColumn(name = "customer_id") xác định cột vừa làm khóa chính vừa làm khóa ngoại ở bảng customer_profiles.
5. @OneToOne(mappedBy = "customer") ở Customer là phía inverse; field customer trong CustomerProfile là phía owning side vì nó ánh xạ cột khóa ngoại.
6. Cascade từ Customer sang CustomerProfile cho phép lưu/xóa profile cùng vòng đời của customer trong ví dụ này.

Không khai báo thêm @Column(name = "customer_id") trên field id trong ví dụ trên. Quan hệ được đánh dấu @MapsId đã ánh xạ association vào chính cột khóa chính của child. Nếu cùng khai báo một mapping cột riêng không đúng cách, có thể gặp lỗi duplicate column mapping.

## 5. @MapsId đồng bộ ID như thế nào?

Giả sử tạo Customer mới và gắn profile:

```java
@Transactional
public Long createCustomer() {
    Customer customer = new Customer("An");

    CustomerProfile profile =
            new CustomerProfile("An Nguyen", "Customer profile");

    customer.attachProfile(profile);

    Customer saved = customerRepository.save(customer);

    return saved.getId();
}
```

Luồng xử lý:

1. Customer mới chưa có ID.
2. CustomerProfile được gắn với Customer qua association customer.
3. CustomerRepository.save lưu Customer.
4. Cascade PERSIST từ Customer sang CustomerProfile được áp dụng.
5. Database sinh Customer.id.
6. JPA/provider đồng bộ khóa của association vào CustomerProfile.id theo @MapsId.
7. Khi insert profile, customer_id được dùng làm cả PK và FK.

Với IDENTITY, provider cần insert parent để lấy khóa trước khi có thể insert child. Thời điểm ID xuất hiện trong object có thể phụ thuộc provider và thao tác flush. Nếu cần kiểm tra giá trị sau khi lưu, hãy đọc sau khi save/flush phù hợp hoặc sau khi transaction hoàn tất.

**Không tự gán CustomerProfile.id bằng một số tùy ý.** @MapsId yêu cầu ID child được suy ra từ association. Gán hai ID khác nhau sẽ vi phạm ý nghĩa derived identity và có thể gây lỗi mapping hoặc persistence.

## 6. Tại sao child không có @GeneratedValue?

Trong mô hình này, CustomerProfile không sở hữu một dãy ID độc lập. Identity của profile chính là identity của Customer.

Không khai báo @GeneratedValue trên ID child. Nếu vừa yêu cầu database sinh một ID độc lập, vừa khai báo @MapsId để ID lấy từ parent, hai ý định đó xung đột về mặt thiết kế.

Cột customer_id được cấp giá trị thông qua association. Khi parent có ID, child dùng chính giá trị đó. Không cần sequence riêng, identity column riêng hoặc table generator cho child.

Kiểu dữ liệu ID của hai entity phải tương thích. Nếu Customer.id là Long thì CustomerProfile.id cũng nên là Long. Nếu parent dùng UUID thì child dùng UUID tương ứng.

## 7. Đồng bộ hai phía của quan hệ

Trong quan hệ hai chiều, Customer.profile là inverse side và CustomerProfile.customer là owning side. Chỉ cập nhật inverse side không đủ để ghi khóa ngoại. Phương thức attachProfile trong Customer gọi profile.attachTo(this), nhờ đó cả hai phía cùng được cập nhật.

Nếu chỉ làm:

```java
customer.setProfile(profile);
```

mà không gán profile.customer, owning side vẫn null. Database không thể biết customer_id cần lưu là gì.

Nên đóng gói thao tác này trong helper method hoặc domain method để caller không quên đồng bộ. Không để controller tự sửa hai field riêng lẻ.

Nếu child có thể được gỡ khỏi parent, cần xác định rõ quy tắc vòng đời. Với orphanRemoval = true, loại child khỏi quan hệ parent sẽ yêu cầu provider xóa child khi đồng bộ persistence context. Nếu giữ tham chiếu child ở nơi khác trong cùng luồng, hãy cập nhật object graph nhất quán và không tiếp tục dùng child đã bị orphaned.

## 8. Cascade và orphanRemoval

Trong ví dụ, Customer có:

```java
@OneToOne(
    mappedBy = "customer",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private CustomerProfile profile;
```

Cascade ALL bao gồm PERSIST, MERGE, REMOVE, REFRESH và DETACH. Khi persist customer, profile được persist theo. Khi xóa customer qua JPA, profile cũng được xóa theo. orphanRemoval = true giúp xóa profile khi nó bị tách khỏi quan hệ.

Chỉ dùng cascade ALL nếu profile thực sự phụ thuộc vòng đời vào customer. Nếu profile có thể được quản lý độc lập hoặc có quy tắc xóa khác, hãy chọn cascade cụ thể thay vì ALL.

Không cascade REMOVE từ CustomerProfile ngược về Customer. Xóa profile không nên tự động xóa customer. Chiều cascade cần phản ánh quyền sở hữu nghiệp vụ, không chỉ chiều quan hệ database.

Cascade JPA là hành vi của persistence provider. Nó khác với ON DELETE CASCADE ở database. Nếu migration tạo ON DELETE CASCADE, database có thể tự xóa child khi parent bị xóa trực tiếp bằng SQL; điều này cần được phối hợp với persistence context và cache của ứng dụng.

## 9. Optionality và fetch strategy

Ở child, association khai báo:

```java
@OneToOne(fetch = FetchType.LAZY, optional = false)
@MapsId
@JoinColumn(name = "customer_id", nullable = false)
private Customer customer;
```

**optional = false** thể hiện một CustomerProfile luôn phải tham chiếu một Customer. Nó không có nghĩa mọi Customer bắt buộc phải có CustomerProfile.

Phía parent có thể không có profile, vì vậy quan hệ inverse thường là optional. Một Customer có thể có profile hoặc chưa có.

OneToOne mặc định là EAGER theo JPA. Khai báo LAZY thể hiện mong muốn tải chậm, nhưng LAZY ở OneToOne là một hint và khả năng thực hiện phụ thuộc provider, chiều quan hệ và bytecode enhancement. Đặc biệt inverse OneToOne có thể cần provider biết child có tồn tại hay không trước khi tạo proxy. Không giả định LAZY luôn đồng nghĩa không có query phụ; hãy kiểm tra SQL thực tế.

Nếu màn hình luôn cần profile, có thể dùng fetch join hoặc EntityGraph tại repository method cụ thể thay vì đặt EAGER toàn cục.

## 10. Repository và truy vấn

Repository của child dùng ID cùng kiểu với parent:

```java
public interface CustomerProfileRepository
        extends JpaRepository<CustomerProfile, Long> {
}
```

Vì CustomerProfile.id chính là Customer.id, có thể tìm profile bằng ID khách hàng:

```java
Optional<CustomerProfile> profile =
        customerProfileRepository.findById(customerId);
```

JPQL có thể truy vấn profile theo parent:

```java
@Query("""
    select p
    from CustomerProfile p
    join fetch p.customer
    where p.id = :customerId
    """)
Optional<CustomerProfile> findWithCustomer(
    @Param("customerId") Long customerId
);
```

JPQL dùng entity name và property Java. Native SQL sẽ dùng customer_profiles và customer_id. Không nhầm tên field id trong Java với tên cột vật lý customer_id.

## 11. Biến thể với @EmbeddedId

Nếu khóa của entity con là khóa ghép và chỉ một phần khóa được lấy từ parent, @MapsId nhận tên thuộc tính trong embedded ID:

```java
@Embeddable
public class CustomerDocumentId implements Serializable {

    private Long customerId;
    private String documentType;

    // equals() và hashCode()
}

@Entity
@Table(name = "customer_documents")
public class CustomerDocument {

    @EmbeddedId
    private CustomerDocumentId id;

    @MapsId("customerId")
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
```

Trong ví dụ này, customerId trong khóa ghép được lấy từ Customer.id; documentType là phần còn lại do ứng dụng cung cấp. @MapsId("customerId") tham chiếu tên thuộc tính Java trong CustomerDocumentId, không phải tên cột.

Với shared primary key một-một đơn giản, dùng @Id + @MapsId không có value là đủ. Không cần tạo EmbeddedId nếu child chỉ có đúng một thành phần ID giống parent.

## 12. So sánh @MapsId và @PrimaryKeyJoinColumn

Cả hai annotation đều có thể xuất hiện trong mapping một-một có khóa chính liên kết, nhưng chúng nhấn mạnh những điều khác nhau:

- **@MapsId** biểu diễn derived identity: ID của entity được suy ra từ association. Đây là cách rõ ràng khi child dùng khóa của parent.
- **@PrimaryKeyJoinColumn** mô tả cột PK của entity hiện tại được dùng làm join column tới entity liên quan, thường thấy trong mapping one-to-one hoặc inheritance.
- Với mô hình child ID chính là parent ID, @MapsId thể hiện trực tiếp quan hệ giữa ID và association, đồng thời giúp provider biết cách đồng bộ khóa.

Không kết hợp tùy tiện cả hai annotation cho cùng một mapping. Chọn cách diễn đạt phù hợp và kiểm tra DDL/schema thực tế.

## 13. Ràng buộc database và tính nhất quán

Shared primary key tạo ra các ràng buộc quan trọng:

1. customer_profiles.customer_id phải là NOT NULL.
2. customer_profiles.customer_id phải là PRIMARY KEY.
3. customer_profiles.customer_id phải là FOREIGN KEY tới customers.id.
4. Kiểu dữ liệu của hai cột phải tương thích.
5. Không cần thêm UNIQUE riêng trên customer_id vì primary key đã duy nhất.

Migration có thể khai báo:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);

CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120),
    bio VARCHAR(1000),
    CONSTRAINT fk_customer_profiles_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

Nếu database dùng cú pháp identity khác, điều chỉnh migration theo hệ quản trị. Entity mapping không thay thế foreign key hoặc primary key constraint. Dù JPA kiểm tra association trong code, database vẫn cần constraint để bảo vệ dữ liệu khi có nhiều instance, SQL trực tiếp hoặc lỗi ứng dụng.

## 14. Lỗi thường gặp

| Biểu hiện | Nguyên nhân | Cách xử lý |
|---|---|---|
| Child insert với ID null | Parent chưa có ID hoặc association chưa được gán | Persist parent, gán association và dùng @MapsId |
| Duplicate key khi tạo hai profile | Đã tồn tại profile cho customer đó | Kiểm tra PK/FK và xử lý nghiệp vụ trùng |
| Child có ID khác parent | Gán ID thủ công hoặc dùng generator riêng | Bỏ @GeneratedValue và để @MapsId suy ra ID |
| FK customer_id không được ghi | Chỉ cập nhật inverse side ở parent | Gán owning side CustomerProfile.customer |
| EntityNotFound/foreign key violation | Parent chưa tồn tại hoặc bị xóa | Kiểm tra thứ tự persist và vòng đời |
| Mọi Customer bắt buộc có profile ngoài ý muốn | Hiểu sai optionality | optional=false ở child chỉ yêu cầu mỗi child có parent |
| Lazy loading vẫn phát sinh query | OneToOne LAZY là hint, nhất là inverse side | Kiểm tra provider, enhancement và fetch plan |
| Xóa parent bị lỗi FK | Thiếu cascade remove hoặc xóa sai thứ tự | Xóa child trước hoặc cấu hình cascade phù hợp |
| Hai entity có ID type không tương thích | Mapping parent và child không thống nhất | Dùng cùng kiểu khóa và kiểm tra schema |

## 15. Kiểm thử mapping

Nên kiểm thử các hành vi sau trên database cùng loại với môi trường triển khai:

- Tạo Customer và CustomerProfile trong một transaction; xác nhận profile.customer_id bằng customers.id.
- Đọc profile bằng ID khách hàng và xác nhận ID hai entity bằng nhau.
- Thử tạo profile thứ hai cho cùng customer; xác nhận database từ chối vì primary key trùng.
- Tạo profile tham chiếu customer không tồn tại; xác nhận foreign key bảo vệ dữ liệu.
- Xóa profile theo orphanRemoval; xác nhận customer vẫn còn.
- Xóa customer qua JPA với cascade phù hợp; xác nhận profile bị xóa trước hoặc cùng transaction.
- Kiểm tra fetch plan để tránh truy vấn thừa khi tải parent/child.
- Kiểm tra rollback nếu thao tác tạo profile thất bại giữa transaction.

Ví dụ test khung:

```java
@DataJpaTest
class CustomerProfileRepositoryTest {

    @Autowired
    CustomerRepository customerRepository;

    @Autowired
    CustomerProfileRepository profileRepository;

    @Test
    void profileUsesTheCustomerId() {
        Customer customer = new Customer("An");
        customer.attachProfile(
            new CustomerProfile("An Nguyen", "Profile")
        );

        Customer saved = customerRepository.saveAndFlush(customer);

        CustomerProfile profile =
            profileRepository.findById(saved.getId()).orElseThrow();

        assertThat(profile.getId()).isEqualTo(saved.getId());
    }
}
```

Đây là khung minh họa; constructor, getter và các field bắt buộc cần được bổ sung theo entity thực tế. Nếu dùng IDENTITY, saveAndFlush bảo đảm insert parent được thực thi để database cấp ID trước khi test đọc profile.

## 16. Bài tập thực hành

1. Tạo Customer có IDENTITY và CustomerProfile dùng @MapsId.
2. Kiểm tra DDL để xác nhận customer_id vừa là PK vừa là FK.
3. Persist Customer kèm profile qua cascade và xác nhận hai ID bằng nhau.
4. Thử lưu profile mà không gán customer; quan sát lỗi validation hoặc constraint.
5. Thử lưu hai profile cho cùng customer; xác nhận PK ngăn bản ghi thứ hai.
6. Thử xóa profile bằng orphanRemoval và xác nhận customer vẫn còn.
7. Thử tải Customer và profile với LAZY; quan sát SQL để hiểu provider xử lý inverse OneToOne thế nào.
8. Tạo biến thể khóa ghép dùng @EmbeddedId và @MapsId("customerId").
9. Viết integration test trên database thật qua Testcontainers.
10. Giải thích khi nào nên dùng shared primary key và khi nào child cần ID riêng.

**Nguyên tắc xuyên suốt:** @MapsId không tạo một ID độc lập cho child; nó lấy identity từ association tới parent. Child giữ một cột vừa là primary key vừa là foreign key. Hãy gán owning side, để parent có ID trước khi insert child, không dùng @GeneratedValue cho ID child và bảo vệ quan hệ bằng PK/FK trong database.
