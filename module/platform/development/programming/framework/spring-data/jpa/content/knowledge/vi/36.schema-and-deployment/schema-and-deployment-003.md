# Quản lý thay đổi bằng Flyway hoặc Liquibase

## 1. Vì sao cần quản lý thay đổi schema?

Ứng dụng Spring Data JPA thay đổi theo thời gian: thêm thuộc tính Entity, tạo bảng mới, đổi kiểu cột, thêm index, chuẩn hóa dữ liệu hoặc tách một bảng lớn. Những thay đổi này phải được áp dụng nhất quán ở môi trường local, test, staging và production.

Nếu mỗi môi trường tự sửa database hoặc để Hibernate tự tạo/cập nhật schema, cấu trúc database có thể lệch nhau. Một phiên bản ứng dụng có thể chạy ở máy lập trình nhưng lỗi khi triển khai vì production thiếu cột, index hoặc constraint.

Database migration giải quyết vấn đề bằng cách lưu các thay đổi thành các tệp có version hoặc changelog được quản lý trong source control. Công cụ migration đọc lịch sử đã áp dụng, xác định thay đổi còn thiếu và thực thi theo thứ tự.

Flyway và Liquibase đều giúp:

- Theo dõi thay đổi schema theo lịch sử có thể kiểm tra.
- Tự động áp dụng migration khi triển khai hoặc chạy pipeline.
- Phát hiện một số trường hợp file migration đã bị sửa sau khi áp dụng.
- Giữ schema giữa các môi trường đi theo cùng một quy trình.
- Hỗ trợ review thay đổi database cùng với thay đổi code.

Migration là một phần của release. Nó cần được thiết kế, review, kiểm thử và triển khai có kế hoạch giống như code ứng dụng.

## 2. Flyway và Liquibase khác nhau thế nào?

Flyway thường tổ chức migration bằng các file được đánh version, phổ biến nhất là SQL. Tên file biểu thị thứ tự và mô tả thay đổi. Flyway ghi nhận migration đã chạy trong bảng lịch sử `flyway_schema_history`.

Liquibase tổ chức thay đổi bằng changelog. Changelog chứa các changeset có `id`, `author` và định danh theo file/path. Changeset có thể khai báo bằng XML, YAML, JSON hoặc SQL formatted changelog. Liquibase lưu lịch sử trong `DATABASECHANGELOG` và dùng `DATABASECHANGELOGLOCK` để điều phối việc cập nhật.

| Tiêu chí | Flyway | Liquibase |
| --- | --- | --- |
| Mô hình chính | Chuỗi migration có version và thứ tự | Changelog gồm các changeset có định danh |
| Cách viết phổ biến | SQL thuần; cũng hỗ trợ Java migration | XML, YAML, JSON, SQL formatted changelog và custom change |
| Lịch sử | `flyway_schema_history` | `DATABASECHANGELOG` |
| Thay đổi lặp lại | Repeatable migration `R__...` | `runOnChange` hoặc `runAlways` trên changeset |
| Điều kiện áp dụng | Theo version, target, location và cấu hình Flyway | Preconditions, contexts, labels và cấu hình Liquibase |
| Rollback | Khả năng phụ thuộc edition/loại migration; thường chuẩn bị migration tiến về phía trước | Có thể khai báo rollback cho changeset; mức tự sinh rollback phụ thuộc loại change |

Không có công cụ nào luôn tốt hơn. Flyway thường dễ tiếp cận khi nhóm muốn quản lý thay đổi bằng SQL có thứ tự rõ ràng. Liquibase hữu ích khi cần changelog có cấu trúc, preconditions, contexts/labels và mô tả thay đổi theo nhiều định dạng.

Chọn một công cụ làm nguồn sự thật cho schema của một database. Không để Flyway và Liquibase cùng quản lý một schema trong môi trường production vì hai bảng lịch sử không hiểu trạng thái của nhau.

## 3. Tích hợp Flyway vào Spring Boot

Thêm dependency Flyway và JDBC driver của database. Với các phiên bản Flyway mới, một số database cần module database riêng bên cạnh `flyway-core`; chọn module tương ứng với database và phiên bản được Spring Boot dependency management hỗ trợ.

Ví dụ Maven cho một ứng dụng PostgreSQL; phiên bản dependency nên được quản lý qua Spring Boot BOM hoặc version catalog của dự án:

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

Spring Boot tự cấu hình Flyway khi dependency và DataSource phù hợp có mặt. Thư mục migration mặc định thường là `classpath:db/migration`.

Cấu trúc thư mục:

```text
src/main/resources/
  db/
    migration/
      V1__create_customer.sql
      V2__add_customer_status.sql
      V3__create_order_table.sql
```

Ví dụ file `V1__create_customer.sql`:

```sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL
);

ALTER TABLE customer
    ADD CONSTRAINT uk_customer_email UNIQUE (email);
```

Cú pháp identity và kiểu timestamp phụ thuộc database. Khi dùng PostgreSQL, `TIMESTAMP WITH TIME ZONE` phù hợp để lưu một thời điểm; database không lưu nguyên ZoneId của người dùng trong cột này.

## 4. Quy tắc đặt tên Flyway migration

Versioned migration theo naming convention phổ biến:

```text
V<version>__<description>.sql
```

Ví dụ:

- `V1__create_customer.sql`
- `V2__add_customer_status.sql`
- `V2_1__add_customer_index.sql`
- `V3__create_purchase_order.sql`

Trong đó:

- `V` là prefix versioned migration.
- Version xác định thứ tự thực thi.
- Hai dấu gạch dưới `__` phân cách version và description.
- Description giúp người review hiểu mục đích.
- Extension thường là `.sql`.

Flyway so sánh version migration với lịch sử đã chạy và áp dụng migration chưa được thực thi theo thứ tự. Mỗi versioned migration được xem là một bước lịch sử; không sửa nội dung migration đã áp dụng ở môi trường dùng chung.

Không đặt hai migration có cùng version. Không đổi tên hoặc xóa file đã áp dụng nếu chưa hiểu tác động tới lịch sử và checksum. Khi cần thay đổi schema mới, tạo migration version tiếp theo.

## 5. Flyway versioned và repeatable migration

**Versioned migration** chạy một lần theo version. Dùng cho thay đổi schema/data có thứ tự:

```text
V1__create_customer.sql
V2__add_status_column.sql
V3__backfill_customer_status.sql
```

**Repeatable migration** dùng prefix `R__` và chạy lại khi checksum thay đổi. Thường dùng cho object cần đồng bộ định nghĩa, như view hoặc stored procedure:

```text
R__customer_summary_view.sql
R__refresh_customer_procedure.sql
```

Repeatable migration không có version số như versioned migration. Flyway kiểm tra checksum và thực thi lại khi nội dung thay đổi; repeatable migrations được áp dụng sau các pending versioned migrations trong một lần migrate.

Không đặt thao tác dữ liệu một lần như “cộng số dư thêm 10” vào repeatable migration, vì file có thể chạy lại khi thay đổi. Nội dung repeatable nên có semantics thay thế định nghĩa, ví dụ `CREATE OR REPLACE VIEW` nếu database hỗ trợ.

## 6. Bảng lịch sử và checksum của Flyway

Flyway lưu thông tin migration đã thực thi trong `flyway_schema_history`, gồm version, description, script, checksum, trạng thái và thời điểm chạy cùng các metadata liên quan.

Checksum giúp phát hiện migration đã áp dụng bị sửa sau đó. Nếu thay đổi nội dung một file versioned đã chạy, lệnh `validate` hoặc quá trình migrate có thể báo lỗi checksum mismatch.

Quy tắc làm việc:

- Migration chưa được triển khai ở bất kỳ môi trường dùng chung nào có thể còn được chỉnh trong quá trình phát triển.
- Migration đã áp dụng ở staging/production nên được coi là bất biến.
- Nếu cần sửa schema, tạo file migration mới.
- Không sửa trực tiếp checksum trong bảng lịch sử để che mismatch.

`flyway repair` có thể điều chỉnh metadata lịch sử, chẳng hạn đồng bộ checksum hoặc loại bỏ một số failed migration record theo trạng thái. Nó không tự hoàn tác hay sửa cấu trúc database. Chỉ dùng sau khi xác định trạng thái schema thực tế và có kế hoạch khôi phục rõ ràng.

## 7. Cấu hình Flyway thường dùng

Ví dụ `application.yml`:

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    validate-on-migrate: true
    clean-disabled: true
  jpa:
    hibernate:
      ddl-auto: validate
```

Ý nghĩa:

- `enabled`: bật/tắt tích hợp Flyway.
- `locations`: nơi chứa migration.
- `validate-on-migrate`: xác minh lịch sử/checksum trước khi áp dụng thay đổi mới.
- `clean-disabled`: chặn lệnh clean qua cấu hình Flyway.
- `ddl-auto: validate`: yêu cầu Hibernate kiểm tra mapping với schema có sẵn.

Trong production, không bật `clean` như một bước triển khai thông thường. Lệnh clean có thể xóa object trong schema được quản lý. `clean-disabled: true` là lớp bảo vệ bổ sung; quyền database vẫn cần được giới hạn.

Flyway còn có các cấu hình như `schemas`, `default-schema`, `baseline-on-migrate`, `out-of-order`, `target` và placeholders. Chỉ bật baseline hoặc out-of-order khi có quy trình cụ thể; không dùng chúng để che việc migration bị thiếu hoặc chạy sai thứ tự.

## 8. Baseline khi đưa Flyway vào database đã tồn tại

Nếu database đã có schema từ trước nhưng chưa được Flyway quản lý, không thể mặc định chạy toàn bộ `V1`, `V2`, ... lên schema đó. Có thể cần baseline để đánh dấu một version hiện tại như điểm bắt đầu, sau đó chỉ chạy các migration mới hơn.

Quy trình thường gồm:

1. Backup và kiểm kê schema hiện tại.
2. Xác định version đại diện cho trạng thái schema đang có.
3. Tạo migration baseline hoặc cấu hình baseline phù hợp với cách quản lý dự án.
4. Chạy thử trên bản sao database production.
5. Kiểm tra Flyway coi những version nào đã được áp dụng và migration nào còn pending.
6. Chỉ sau khi xác nhận trạng thái mới triển khai lên database thật.

`baselineOnMigrate` có thể tự baseline khi Flyway gặp schema không rỗng chưa có history table. Đây là tùy chọn tiện lợi nhưng làm giảm khả năng phát hiện kết nối nhầm database hoặc schema chưa được chuẩn bị. Trong production, nên dùng baseline có kiểm soát thay vì bật mù quáng.

## 9. Tích hợp Liquibase vào Spring Boot

Thêm dependency `liquibase-core` và JDBC driver của database. Spring Boot tự cấu hình Liquibase khi dependency và DataSource phù hợp có mặt.

Ví dụ Maven:

```xml
<dependency>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-core</artifactId>
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

Changelog master có thể đặt tại:

```text
src/main/resources/
  db/
    changelog/
      db.changelog-master.yaml
      changes/
        001-create-customer.yaml
        002-add-customer-status.yaml
```

Cấu hình Spring Boot:

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.yaml
  jpa:
    hibernate:
      ddl-auto: validate
```

Ví dụ `db.changelog-master.yaml`:

```yaml
databaseChangeLog:
  - include:
      file: db/changelog/changes/001-create-customer.yaml
  - include:
      file: db/changelog/changes/002-add-customer-status.yaml
```

Master changelog là entry point; các file được include theo thứ tự khai báo. Có thể dùng `includeAll` cho một thư mục, nhưng cần kiểm soát quy tắc sắp xếp file và tránh để file không liên quan bị tự động đưa vào.

## 10. Changeset của Liquibase

Changeset là đơn vị thay đổi được Liquibase theo dõi. Mỗi changeset có `id` và `author`; định danh lịch sử còn gắn với đường dẫn changelog. Không tái sử dụng cùng một định danh cho thay đổi khác.

Ví dụ `001-create-customer.yaml`:

```yaml
databaseChangeLog:
  - changeSet:
      id: 001
      author: team-platform
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: email
                  type: VARCHAR(320)
                  constraints:
                    nullable: false
        - addUniqueConstraint:
            tableName: customer
            columnNames: email
            constraintName: uk_customer_email
```

Liquibase ghi changeset đã chạy trong `DATABASECHANGELOG`, gồm ID, author, filename, checksum và metadata. `DATABASECHANGELOGLOCK` giúp tránh nhiều tiến trình Liquibase cùng thực thi update trên cùng database tại một thời điểm.

Giống Flyway, changeset đã áp dụng nên được coi là bất biến. Nếu sửa nội dung changeset cũ, Liquibase có thể báo checksum validation error. Tạo changeset mới để mô tả thay đổi tiếp theo.

## 11. Liquibase preconditions

Preconditions kiểm tra trạng thái database trước khi chạy changeset. Ví dụ chỉ thêm cột nếu bảng tồn tại:

```yaml
databaseChangeLog:
  - changeSet:
      id: 003-add-phone
      author: team-platform
      preConditions:
        - onFail: HALT
        - tableExists:
            tableName: customer
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: phone
                  type: VARCHAR(30)
```

Các lựa chọn `onFail` thường dùng gồm `HALT`, `CONTINUE`, `MARK_RAN` và `WARN`. Chọn theo ý nghĩa nghiệp vụ:

- `HALT`: dừng update khi điều kiện không đạt.
- `CONTINUE`: bỏ qua changeset lần này và tiếp tục xử lý.
- `MARK_RAN`: đánh dấu changeset như đã chạy dù nội dung không được thực thi.
- `WARN`: cảnh báo và tiếp tục theo semantics của Liquibase.

`MARK_RAN` và `CONTINUE` có thể che schema drift nếu dùng không đúng. Với thay đổi bắt buộc như tạo cột/constraint, `HALT` thường an toàn hơn khi precondition không đạt. Preconditions là kiểm tra trạng thái, không thay thế test migration.

## 12. runOnChange, runAlways, contexts và labels

Liquibase hỗ trợ điều khiển thời điểm changeset được áp dụng:

- `runOnChange: true`: chạy lại changeset khi checksum của nội dung thay đổi. Thường dùng cho view/procedure được định nghĩa lại.
- `runAlways: true`: chạy changeset mỗi lần Liquibase update được gọi.
- `context`: gắn changeset với một nhóm môi trường hoặc mục đích.
- `labels`: phân loại changeset để chọn nhóm cần thực thi.

Ví dụ:

```yaml
databaseChangeLog:
  - changeSet:
      id: 010-refresh-view
      author: team-platform
      runOnChange: true
      changes:
        - sqlFile:
            path: db/changelog/sql/customer-summary-view.sql
            relativeToChangelogFile: false
```

Không đặt INSERT cộng dồn hoặc thao tác không idempotent vào `runOnChange`/`runAlways` nếu chạy lại sẽ làm thay đổi dữ liệu thêm lần nữa. Dùng các thuộc tính này cho object có thể thay thế định nghĩa hoặc tác vụ được thiết kế chạy lặp an toàn.

Contexts và labels là bộ lọc triển khai, không phải cơ chế bảo mật. Không dựa vào context để bỏ qua migration bắt buộc ở production mà không có quy trình rõ.

## 13. Rollback và forward fix

Rollback là một phần của kế hoạch migration, nhưng không phải mọi thay đổi đều có thể đảo ngược an toàn.

Ví dụ có thể rollback việc thêm một cột rỗng bằng cách drop cột, nhưng không thể khôi phục dữ liệu đã bị xóa nếu không có backup hoặc bản sao. Đổi kiểu cột có thể làm mất độ chính xác; merge dữ liệu có thể không có phép đảo ngược duy nhất.

Liquibase cho phép khai báo rollback cho changeset:

```yaml
databaseChangeLog:
  - changeSet:
      id: 004-add-phone
      author: team-platform
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column:
                  name: phone
                  type: VARCHAR(30)
      rollback:
        - dropColumn:
            tableName: customer
            columnName: phone
```

Rollback ví dụ này chỉ an toàn nếu không cần giữ dữ liệu đã ghi vào `phone`. Nhiều loại change không có rollback tự sinh phù hợp; cần khai báo tường minh và thử trên bản sao database.

Flyway chủ yếu khuyến khích tiến về phía trước bằng versioned migration mới. Khả năng undo phụ thuộc edition và loại migration; với SQL migration, nhóm thường chuẩn bị một migration mới để sửa hoặc đảo ngược logic khi có thể.

Trong production, forward fix thường an toàn hơn rollback ứng dụng/database một cách vội vàng. Có thể triển khai migration mới khôi phục trạng thái tương thích, giữ dữ liệu và cho phép phiên bản ứng dụng đang chạy tiếp tục hoạt động.

## 14. Hibernate ddl-auto nên phối hợp thế nào?

Khi Flyway hoặc Liquibase quản lý schema, Hibernate nên xác minh mapping thay vì tự ý thay đổi cấu trúc database:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

Ý nghĩa thường dùng:

| Giá trị | Hành vi | Khuyến nghị |
| --- | --- | --- |
| `none` | Không tự tạo/cập nhật schema | Có thể dùng khi migration và kiểm tra schema được quản lý riêng |
| `validate` | Kiểm tra mapping với schema hiện có | Phù hợp cho nhiều môi trường triển khai |
| `update` | Cố gắng cập nhật schema theo Entity | Tránh dùng làm cơ chế migration production |
| `create` / `create-drop` | Tạo schema mới; `create-drop` còn xóa khi context đóng | Chỉ dùng trong môi trường thử nghiệm được kiểm soát |

`ddl-auto=update` không tạo ra lịch sử migration có thể review, không diễn tả tốt data backfill và có thể tạo khác biệt giữa môi trường. Không chạy Hibernate DDL generation và Flyway/Liquibase cùng sửa một schema trong cùng release.

## 15. Thứ tự chạy migration trong Spring Boot

Với auto-configuration tiêu chuẩn, Spring Boot tích hợp Flyway/Liquibase để migration chạy trong quá trình khởi tạo ứng dụng và trước khi JPA sử dụng schema. Điều này giúp Hibernate `validate` nhìn thấy schema đã được cập nhật.

Trong hệ thống production nhiều replica, cân nhắc chạy migration như một bước deploy/job riêng trước khi rollout application instances. Nếu mọi instance cùng khởi động và cố chạy migration, công cụ có lock để điều phối, nhưng vẫn tạo thêm cạnh tranh startup và làm rollback/recovery khó kiểm soát hơn.

Một quy trình triển khai thường có thứ tự:

1. Build artifact chứa migration đã review.
2. Backup/snapshot hoặc xác nhận cơ chế khôi phục database.
3. Chạy migration bằng credentials có quyền DDL.
4. Kiểm tra trạng thái migration và schema.
5. Rollout phiên bản ứng dụng tương thích với schema mới.
6. Theo dõi lỗi SQL, latency, lock và connection.

Migration và ứng dụng cần tương thích trong giai đoạn rolling deployment, khi phiên bản cũ và mới có thể chạy đồng thời.

## 16. Expand-contract để triển khai không downtime

Khi đổi schema đang được ứng dụng sử dụng, không nên xóa hoặc đổi tên cột ngay nếu phiên bản cũ vẫn đang chạy. Dùng chiến lược expand-contract:

**Expand:** thêm cấu trúc mới theo cách tương thích ngược, ví dụ thêm cột `display_name` nullable.

**Migrate data:** backfill dữ liệu cũ sang cột mới theo batch, có thể chạy bằng job riêng và theo dõi tiến độ.

**Transition:** triển khai code mới có thể đọc/ghi tương thích cả cấu trúc cũ và mới; sau đó chuyển dần nguồn đọc sang cột mới.

**Contract:** khi tất cả instance cũ đã dừng và không còn client/job dùng cột cũ, mới xóa cột cũ trong một migration riêng.

Ví dụ thay `full_name` bằng `display_name`:

1. Release A thêm `display_name` nullable, giữ `full_name`.
2. Backfill `display_name` từ `full_name`.
3. Release B ghi đồng bộ cả hai cột trong giai đoạn chuyển tiếp.
4. Chuyển đọc sang `display_name` và xác minh dữ liệu.
5. Release sau xóa logic ghi `full_name`.
6. Migration cuối mới drop `full_name`.

Không gộp cả sáu bước vào một migration nếu application versions cần cùng tồn tại. Mỗi bước phải có thể triển khai và kiểm chứng độc lập.

## 17. Migration schema và data migration

Schema migration thay đổi cấu trúc: tạo bảng, thêm cột, constraint, index, view hoặc sequence. Data migration chuyển đổi giá trị hiện có để phù hợp mô hình mới.

Ví dụ thêm cột status có default:

```sql
ALTER TABLE customer
    ADD COLUMN status VARCHAR(20);

UPDATE customer
SET status = 'ACTIVE'
WHERE status IS NULL;

ALTER TABLE customer
    ALTER COLUMN status SET NOT NULL;
```

Ví dụ này có thể phù hợp với bảng nhỏ. Với bảng lớn, một câu UPDATE duy nhất có thể giữ lock lâu, tạo nhiều WAL/redo log, tăng replication lag và làm transaction phình to.

Với dữ liệu lớn, cân nhắc:

- Thêm cột nullable trước.
- Backfill theo batch với giới hạn số hàng và checkpoint.
- Theo dõi lock, transaction duration, replication lag và tốc độ ghi.
- Đảm bảo job có thể resume/idempotent.
- Xác minh không còn NULL trước khi thêm NOT NULL constraint.
- Tách backfill khỏi DDL release nếu cần.

Không giả định migration SQL có thể chạy lại an toàn chỉ vì có `IF NOT EXISTS`. Điều kiện đó có thể che schema sai khác. Hãy xác định trạng thái mong muốn và cách xử lý khi một phần migration đã thực thi.

## 18. Index và constraint trên bảng lớn

Thêm index hoặc constraint có thể gây lock và ảnh hưởng traffic. Cú pháp tạo index online/concurrently khác nhau giữa database:

```sql
-- PostgreSQL: tạo index mà hạn chế chặn ghi thông thường.
CREATE INDEX CONCURRENTLY idx_customer_status
    ON customer(status);
```

Trong PostgreSQL, `CREATE INDEX CONCURRENTLY` có giới hạn riêng và không được chạy trong transaction block thông thường. Nếu dùng Flyway/Liquibase, cần cấu hình migration/changeset phù hợp với yêu cầu non-transactional của câu lệnh và hiểu cách công cụ ghi nhận trạng thái khi có lỗi giữa chừng.

Đừng copy cú pháp này sang MySQL, SQL Server hoặc Oracle; mỗi engine có cú pháp và lock behavior riêng. Kiểm thử trên đúng phiên bản database production.

Trước khi thêm unique constraint, kiểm tra dữ liệu trùng và chuẩn hóa business key. Trước khi thêm foreign key hoặc NOT NULL, xác minh dữ liệu hiện tại thỏa điều kiện.

## 19. Transaction, lock và migration thất bại

Không phải database nào cũng hỗ trợ DDL transaction giống nhau. Có database tự commit một số DDL, có câu lệnh không được chạy trong transaction block, và có migration gồm nhiều bước chỉ hoàn tất một phần trước khi lỗi.

Flyway và Liquibase có cơ chế ghi lịch sử/lock, nhưng không thể làm cho mọi DDL của mọi database trở nên atomic. Khi migration thất bại:

1. Dừng rollout ứng dụng nếu schema ở trạng thái không tương thích.
2. Đọc log và xác định câu lệnh nào đã chạy thành công.
3. Kiểm tra schema và history table thực tế.
4. Không sửa/xóa history record bằng tay để ép công cụ chạy tiếp.
5. Xác định có thể chạy lại, cần repair metadata, hay cần migration khôi phục.
6. Thử quy trình sửa trên bản sao database trước.

Với Liquibase, `runInTransaction` mặc định thường là true; chỉ đặt false khi database statement yêu cầu và đã hiểu rủi ro trạng thái changeset nếu thực thi dở dang. Với Flyway, khả năng transactional phụ thuộc database và loại statement; kiểm tra behavior cụ thể của engine.

## 20. Nhiều DataSource và nhiều schema

Nếu ứng dụng có nhiều database, mỗi database cần một migration lifecycle rõ ràng. Không để cùng một migration runner vô tình chạy trên nhầm DataSource.

Với Flyway, có thể tạo cấu hình/bean Flyway riêng cho từng DataSource, chỉ rõ locations, schemas và history table phù hợp. Với Liquibase, cấu hình bean riêng, chỉ rõ DataSource, changelog và schema history table.

Nếu chỉ có nhiều schema trong cùng database, một migration tool có thể quản lý nhiều schema khi được cấu hình phù hợp; vẫn cần xác định schema mặc định, quyền DDL và phạm vi object.

Không giả định một `@EnableJpaRepositories` hoặc một `spring.flyway.*` mặc định sẽ tự hiểu mọi persistence unit tùy chỉnh. Kiểm tra cấu hình Spring Boot cụ thể và test migration trên từng database.

## 21. Credentials và quyền database

Ứng dụng runtime thường chỉ cần quyền SELECT/INSERT/UPDATE/DELETE trên các bảng nghiệp vụ. Migration cần quyền DDL như CREATE/ALTER/DROP và có thể cần quyền tạo index/sequence.

Nếu kiến trúc cho phép, dùng credentials riêng:

- Migration user được cấp quyền schema change trong cửa sổ triển khai.
- Application user chỉ có quyền runtime tối thiểu.
- Không commit password hoặc URL chứa secret vào repository.
- Lấy credentials từ secret manager hoặc environment được quản lý.
- Ghi log migration nhưng không in thông tin xác thực.

Tách quyền giúp giảm tác động nếu ứng dụng runtime bị xâm nhập và làm rõ ai/công cụ nào được phép thay đổi schema.

## 22. CI/CD và review migration

Mỗi pull request có thay đổi Entity/schema nên chứa migration tương ứng. Pipeline có thể:

1. Kiểm tra tên/version migration hoặc định danh changeset.
2. Khởi tạo database test bằng đúng engine qua Testcontainers.
3. Chạy toàn bộ migration từ schema rỗng.
4. Kiểm tra nâng cấp từ schema của phiên bản trước.
5. Khởi động ứng dụng với `ddl-auto=validate`.
6. Chạy integration tests cho repository và query quan trọng.
7. Kiểm tra migration trên bản sao dữ liệu đại diện khi thay đổi có rủi ro.

Review migration cần xem lock, thời gian chạy, data loss, nullability, index, foreign key, dung lượng bảng, tương thích rolling deployment và cách khôi phục.

Không chỉ kiểm thử từ database rỗng. Production thường đã có dữ liệu và schema ở version trước; đường nâng cấp thực tế mới là điều cần xác minh.

## 23. Flyway hay Liquibase: chọn theo nhu cầu

| Nhu cầu | Lựa chọn thường phù hợp |
| --- | --- |
| Nhóm muốn quản lý SQL thuần, version tuần tự và lịch sử đơn giản | Flyway |
| Cần nhiều định dạng changelog và changeset có cấu trúc | Liquibase |
| Cần preconditions, contexts và labels để điều khiển changeset | Liquibase |
| View/procedure cần cập nhật theo định nghĩa file | Flyway repeatable hoặc Liquibase `runOnChange` |
| Cần rollback khai báo theo changeset | Liquibase có thể thuận tiện hơn, nhưng vẫn phải kiểm tra từng loại change |
| Database có nhiều DDL đặc thù và nhóm muốn kiểm soát SQL tường minh | Flyway hoặc Liquibase với SQL changeset |

Tiêu chí quyết định quan trọng hơn cú pháp: năng lực vận hành của nhóm, database engine, chiến lược release, nhu cầu rollback, review và công cụ đã có trong CI/CD.

## 24. Ví dụ kiểm tra migration bằng Testcontainers

Với Spring Boot, integration test nên chạy migration trên database cùng loại với production. Ví dụ cấu trúc test với PostgreSQL Testcontainers:

```java
@Testcontainers
@SpringBootTest
class DatabaseMigrationIntegrationTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    JdbcTemplate jdbcTemplate;

    @Test
    void migrationCreatesCustomerTable() {
        Integer count = jdbcTemplate.queryForObject(
            "select count(*) from information_schema.tables " +
            "where table_name = 'customer'",
            Integer.class
        );

        assertEquals(1, count);
    }
}
```

Ví dụ giả định dependency Testcontainers PostgreSQL/JUnit, driver và cấu hình Spring Boot đã có. Spring Boot chạy Flyway hoặc Liquibase trong lúc khởi tạo context. Nếu dự án có nhiều DataSource, cung cấp dynamic properties và migration config cho đúng datasource đang kiểm thử.

Thêm test nâng cấp từ schema cũ bằng cách khởi tạo database ở version trước, nạp dữ liệu đại diện rồi chạy migration mới. Kiểm tra cả schema lẫn dữ liệu sau backfill.

## 25. Lỗi thường gặp và cách xử lý

**Ứng dụng báo thiếu table/column khi khởi động.** Kiểm tra migration dependency, location/changelog, DataSource được chọn và thứ tự migration so với JPA `validate`.

**Flyway báo checksum mismatch.** File đã áp dụng bị sửa hoặc line ending/nội dung thay đổi. Khôi phục file lịch sử hoặc tạo migration mới; chỉ dùng `repair` khi đã hiểu trạng thái database và history.

**Flyway không tìm thấy migration.** Kiểm tra prefix `V`, version, dấu `__`, extension, location và resource có được đóng gói vào artifact không.

**Liquibase báo checksum validation failed.** Changeset đã áp dụng bị sửa. Giữ changeset cũ và tạo changeset mới; không xóa record history để né kiểm tra.

**Liquibase không chạy changeset.** Kiểm tra master changelog có include file, preconditions, contexts/labels và trạng thái `DATABASECHANGELOG`.

**Migration chạy ở local nhưng production lỗi.** Có thể khác database engine/version, quyền DDL, collation, dữ liệu hiện tại, lock behavior hoặc transaction semantics. Test trên engine tương thích production và dữ liệu đại diện.

**Hai application instance cùng khởi động và chạy migration.** Kiểm tra lock/history của công cụ và cân nhắc tách migration thành deploy job duy nhất trước rollout.

**Hibernate tự tạo/cập nhật schema ngoài dự kiến.** Đặt `ddl-auto=validate` hoặc `none` khi migration tool quản lý schema; loại bỏ DDL generation cạnh tranh.

**Migration lớn làm downtime hoặc lock lâu.** Chia nhỏ expand/backfill/contract, tạo index theo cách phù hợp database và chạy backfill theo batch.

**Rollback làm mất dữ liệu.** Định nghĩa rollback trước khi release; với chuyển đổi dữ liệu khó đảo ngược, ưu tiên backup và forward fix.

## 26. Checklist trước khi triển khai migration

- Chọn một công cụ làm nguồn sự thật cho schema của database.
- Đặt version hoặc changeset ID duy nhất, mô tả rõ mục đích.
- Không sửa migration/changeset đã áp dụng ở môi trường dùng chung.
- Kiểm tra checksum và lịch sử migration.
- Dùng Hibernate `ddl-auto=validate` khi migration tool quản lý schema.
- Kiểm thử từ schema rỗng và nâng cấp từ version đang chạy.
- Dùng database engine tương thích production, ưu tiên Testcontainers.
- Đánh giá lock, transaction DDL, thời gian chạy và dung lượng dữ liệu.
- Thiết kế expand-contract cho rolling deployment.
- Tách backfill lớn khỏi DDL nếu cần; bảo đảm job resume/idempotent.
- Xác định backup, rollback hoặc forward-fix trước khi release.
- Chạy migration với credentials có quyền phù hợp và bảo vệ secret.
- Với nhiều DataSource, chỉ rõ migration runner và schema của từng database.
- Theo dõi history table, logs, lock và trạng thái ứng dụng sau triển khai.

Flyway và Liquibase giúp biến thay đổi database thành lịch sử có thể review và triển khai lặp lại. Flyway tổ chức migration theo version hoặc repeatable file; Liquibase quản lý changeset trong changelog với preconditions và bộ lọc linh hoạt. Dù chọn công cụ nào, hãy giữ migration đã áp dụng bất biến, kiểm thử trên database tương thích production, phối hợp Hibernate bằng `validate`, và triển khai thay đổi theo từng bước tương thích để bảo vệ dữ liệu và tránh downtime.
