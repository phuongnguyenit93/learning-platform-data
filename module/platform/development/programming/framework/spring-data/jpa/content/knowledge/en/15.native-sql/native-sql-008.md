# Querying With CTEs, Window Functions, and Database-Specific Syntax

## 1. Objectives

Native SQL becomes necessary when a query requires constructs or capabilities beyond standard JPQL. In Spring Data JPA, you can declare native SQL using `@Query(nativeQuery = true)` or use a custom repository with `EntityManager`, `JdbcTemplate`, or `JdbcClient`.

This lesson focuses on three sets of techniques:
- **CTE (Common Table Expression):** defines a named subquery at the top of a statement with `WITH`; recursive CTEs traverse trees or hierarchical relationships.
- **Window functions:** compute rankings, running totals, previous/next values, and group-level metrics while retaining individual rows.
- **Database-specific syntax:** use PostgreSQL features such as `ILIKE`, `DISTINCT ON`, `JSONB`, `FILTER`, and `ON CONFLICT`, while understanding portability boundaries.

After this lesson, you will be able to write CTEs and window functions in native queries, map results into projections, paginate properly, test against the actual target database, and decide when to move a query into a custom repository.

## 2. When Do You Need Native SQL?

JPQL operates on Entities and Java properties. Native SQL operates directly on the database schema: tables, columns, data types, CTEs, window functions, and engine-specific syntax.

Choose native SQL when:
- A query needs a CTE or recursive CTE that standard JPQL in your active version cannot express.
- Window functions such as `row_number()`, `rank()`, `lag()`, or `sum() over (...)` are required.
- Database-specific operators, data types, or functions are needed.
- You need to tune a query after measuring and reviewing the database execution plan.

Prefer JPQL or derived queries whenever they express the use case clearly. Native SQL couples tightly to table/column names and dialects, so it must be tested and maintained alongside the database schema.

Examples in this lesson use PostgreSQL 16 and Spring Boot 3.5.0. PostgreSQL-specific syntax is called out explicitly; do not assume the same SQL runs unmodified on MySQL, SQL Server, Oracle, or H2.

## 4. Sample Data Model

Let us use a `sales_orders` table to store orders. Each order has a customer, status, total amount, and creation timestamp.

```sql
CREATE TABLE sales_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    total_amount NUMERIC(14, 2) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_sales_orders_customer_created
    ON sales_orders (customer_id, created_at DESC, id DESC);
```

This index supports queries filtering by customer and sorting by newest orders. Only create indexes after examining real workloads and execution plans; each index also adds write overhead and storage cost.

### SalesOrder Entity

`src/main/java/com/example/orders/SalesOrder.java`:

```java
package com.example.orders;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.math.BigDecimal;
import java.time.Instant;

@Entity
@Table(name = "sales_orders")
public class SalesOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "customer_id", nullable = false)
    private Long customerId;

    @Column(nullable = false, length = 20)
    private String status;

    @Column(name = "total_amount", nullable = false, precision = 14, scale = 2)
    private BigDecimal totalAmount;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    protected SalesOrder() {
        // JPA requires a no-argument constructor.
    }

    public SalesOrder(Long customerId, String status, BigDecimal totalAmount, Instant createdAt) {
        if (customerId == null || customerId <= 0) {
            throw new IllegalArgumentException("Customer ID must be positive");
        }
        if (status == null || status.isBlank() || status.length() > 20) {
            throw new IllegalArgumentException("Status is required");
        }
        if (totalAmount == null || totalAmount.signum() < 0) {
            throw new IllegalArgumentException("Total amount cannot be negative");
        }
        if (createdAt == null) {
            throw new IllegalArgumentException("Created time is required");
        }
        this.customerId = customerId;
        this.status = status;
        this.totalAmount = totalAmount;
        this.createdAt = createdAt;
    }

    public Long getId() {
        return id;
    }

    public Long getCustomerId() {
        return customerId;
    }

    public String getStatus() {
        return status;
    }

    public BigDecimal getTotalAmount() {
        return totalAmount;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}
```

The Entity maps database columns via `@Column`. However, the native SQL below will reference table and column names directly, such as `sales_orders`, `customer_id`, `total_amount`, and `created_at`.

## 5. Non-Recursive CTEs With WITH

A CTE defines a named subquery at the beginning of an SQL statement. The main query can reference the CTE as a temporary data source scoped to that statement.

General syntax:

```sql
WITH cte_name AS (
    SELECT ...
)
SELECT ...
FROM cte_name;
```

CTEs help break complex queries into named steps. For example, selecting paid orders and then summing totals per customer:

```sql
WITH paid_orders AS (
    SELECT customer_id, total_amount
    FROM sales_orders
    WHERE status = 'PAID'
),
customer_totals AS (
    SELECT customer_id, SUM(total_amount) AS total_spent
    FROM paid_orders
    GROUP BY customer_id
)
SELECT customer_id, total_spent
FROM customer_totals
WHERE total_spent >= 1000
ORDER BY total_spent DESC;
```

Here:
- `paid_orders` filters paid orders.
- `customer_totals` aggregates spending per customer from the first CTE.
- The outer query filters customers with total spend of 1000 or more.

A CTE is not inherently a physical table or temporary table persisting after the statement. It is a named result set scoped to the SQL statement. The database may inline or materialize a CTE depending on the engine, version, and query structure.

### Multiple CTEs and Step Dependencies

An SQL statement can declare multiple CTEs separated by commas. Later CTEs can reference earlier CTEs:

```sql
WITH recent_orders AS (
    SELECT id, customer_id, total_amount, created_at
    FROM sales_orders
    WHERE created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+00'
),
large_orders AS (
    SELECT *
    FROM recent_orders
    WHERE total_amount >= 500
)
SELECT customer_id, COUNT(*) AS order_count, SUM(total_amount) AS revenue
FROM large_orders
GROUP BY customer_id
ORDER BY revenue DESC;
```

Naming each step makes queries easier to read, inspect, and tune. Avoid splitting into overly tiny CTEs if doing so does not clarify logic.

## 6. Recursive CTEs With WITH RECURSIVE

Recursive CTEs suit hierarchical data such as category trees, organizational charts, folders, or dependency graphs.

Suppose a `categories` table has this structure:

```sql
CREATE TABLE categories (
    id BIGINT PRIMARY KEY,
    parent_id BIGINT NULL REFERENCES categories(id),
    name VARCHAR(120) NOT NULL
);
```

The following query finds a root category and all of its descendants:

```sql
WITH RECURSIVE category_tree AS (
    SELECT id, parent_id, name, 0 AS depth, ARRAY[id] AS path
    FROM categories
    WHERE id = :root_id

    UNION ALL

    SELECT child.id, child.parent_id, child.name,
           parent.depth + 1, parent.path || child.id
    FROM categories child
    JOIN category_tree parent ON child.parent_id = parent.id
    WHERE NOT child.id = ANY(parent.path)
)
SELECT id, parent_id, name, depth
FROM category_tree
ORDER BY path;
```

A recursive CTE has two parts:
1. **Anchor member:** the first query selects the root node with depth `0`.
2. **Recursive member:** the second query joins the base table against the previous iteration's results to retrieve child nodes.

`UNION ALL` combines rows across levels. In the PostgreSQL example, `ARRAY[id]`, array concatenation `||`, and `ANY(path)` track visited paths to prevent cycles. This is PostgreSQL syntax; other databases may use different data types and cycle-detection techniques.

Cycle prevention is especially critical if data could be corrupted or contain circular references. You should also cap depth or node counts in use cases at risk of traversing huge trees.

## 7. What Is a Window Function?

A window function computes a value across a set of rows related to the current row, defined by an `OVER` clause. Unlike `GROUP BY`, window functions do not collapse multiple rows into a single output row; every row is preserved.

Structure:

```sql
some_function(expression) OVER (
    PARTITION BY group_column
    ORDER BY sort_column
    ROWS BETWEEN ...
)
```

- `PARTITION BY` divides results into independent groups. Omitting `PARTITION BY` treats the entire result set as one partition.
- `ORDER BY` establishes processing order within each partition.
- Window frames like `ROWS BETWEEN ...` define the row scope evaluated by frame-aware functions.

### 7.1. ROW_NUMBER, RANK, and DENSE_RANK

These three functions assign rankings within each partition:

| Function | Behavior on Tied Values |
| --- | --- |
| `ROW_NUMBER()` | Always assigns unique sequential numbers 1, 2, 3, ... |
| `RANK()` | Tied rows receive the same rank, leaving gaps in subsequent ranks. |
| `DENSE_RANK()` | Tied rows receive the same rank with no gaps in subsequent ranks. |

Example:

```sql
SELECT customer_id, id, total_amount,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total_amount DESC, id) AS row_no,
       RANK() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS amount_rank,
       DENSE_RANK() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS dense_rank
FROM sales_orders
WHERE status = 'PAID';
```

If a customer has orders totaling `900`, `900`, and `700`, `RANK` yields `1, 1, 3`; `DENSE_RANK` yields `1, 1, 2`. `ROW_NUMBER` yields `1, 2, 3` using the secondary `id` tie-breaker.

Always include a unique tie-breaker like `id` when deterministic ordering is needed for `ROW_NUMBER`, pagination, or picking a single top row. Otherwise, tied rows may swap order across runs.

### 7.2. LAG and LEAD

`LAG` reads a value from a preceding row, while `LEAD` reads from a following row within the partition's order. They are useful for comparing revenue or state across periods:

```sql
SELECT customer_id, created_at, total_amount,
       LAG(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
       ) AS previous_order_amount,
       LEAD(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
       ) AS next_order_amount
FROM sales_orders
WHERE status = 'PAID';
```

On each customer's first row, `LAG` returns `NULL` unless a default value is given. You can use `LAG(total_amount, 1, 0)` to provide a fallback value when no preceding row exists.

### 7.3. Running Totals With SUM OVER

```sql
SELECT customer_id, created_at, total_amount,
       SUM(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at, id;
```

`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` computes the sum from the start of the partition through the current row. Specifying the frame explicitly avoids differences caused by default frames and duplicate sort values.

### 7.4. FIRST_VALUE, LAST_VALUE, and Frames

`FIRST_VALUE` and `LAST_VALUE` return the first or last value within the window frame. With `LAST_VALUE`, if the default frame ends at the current row, the result is usually the current row's value rather than the partition's final value.

To get the last value of the entire partition:

```sql
SELECT customer_id, created_at, total_amount,
       LAST_VALUE(total_amount) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
       ) AS latest_partition_amount
FROM sales_orders
WHERE status = 'PAID';
```

Choose the right frame for your business semantics. `ROWS` counts physical rows; `RANGE` operates on sort values and handles peer rows differently.

## 8. Combining CTEs and Window Functions: Top N Latest Orders per Customer

This is a very common query pattern: number orders per customer with `ROW_NUMBER()`, then filter by rank in an outer query.

```sql
WITH ranked_orders AS (
    SELECT o.id, o.customer_id, o.total_amount, o.created_at,
           ROW_NUMBER() OVER (
               PARTITION BY o.customer_id
               ORDER BY o.created_at DESC, o.id DESC
           ) AS row_number
    FROM sales_orders o
    WHERE o.status = :status
)
SELECT id, customer_id, total_amount, created_at, row_number
FROM ranked_orders
WHERE row_number <= :limit_per_customer
ORDER BY customer_id, row_number;
```

You cannot reference the `row_number` alias inside the `WHERE` clause of the same `SELECT` in most databases because `WHERE` is evaluated before window expressions. A CTE introduces an outer query layer where window results can be filtered.

Adding `id DESC` breaks ties when two orders share the same `created_at`. Without a secondary criterion, ranking among simultaneous orders can be non-deterministic.

## 9. Mapping Native Query Results to Projections

Native queries can return an Entity if selected columns match the Entity mapping. For aggregated or window function results, interface projections are usually cleaner.

`src/main/java/com/example/orders/RankedOrderView.java`:

```java
package com.example.orders;

import java.math.BigDecimal;

public interface RankedOrderView {
    Long getId();
    Long getCustomerId();
    BigDecimal getTotalAmount();
    Long getRowNumber();
}
```

`src/main/java/com/example/orders/SalesOrderRepository.java`:

```java
package com.example.orders;

import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface SalesOrderRepository extends JpaRepository<SalesOrder, Long> {
    @Query(value = """
            WITH ranked_orders AS (
                SELECT o.id, o.customer_id, o.total_amount,
                       ROW_NUMBER() OVER (
                           PARTITION BY o.customer_id
                           ORDER BY o.created_at DESC, o.id DESC
                       ) AS row_number
                FROM sales_orders o
                WHERE o.status = :status
            )
            SELECT id AS "id",
                   customer_id AS "customerId",
                   total_amount AS "totalAmount",
                   row_number AS "rowNumber"
            FROM ranked_orders
            WHERE row_number <= :limitPerCustomer
            ORDER BY "customerId", "rowNumber"
            """, nativeQuery = true)
    List<RankedOrderView> findTopOrdersPerCustomer(
            @Param("status") String status,
            @Param("limitPerCustomer") int limitPerCustomer);
}
```

In native interface projections, column aliases should match the projection's property names. PostgreSQL folds unquoted identifiers to lowercase; use double-quoted aliases such as `"customerId"` and `"rowNumber"` to preserve uppercase letters in alias names.

Named parameters in native queries work with Spring Data JPA and Hibernate as shown. Under pure JPA portability rules, named parameter support in native SQL is not guaranteed uniformly across every provider; if high portability is required, consider positional parameters or a custom repository controlling parameter binding.

## 10. Paginating Native Queries and countQuery

For native queries returning `Page<T>`, declare an explicit `countQuery` so Spring Data knows how to count total rows. Example filtering orders by status:

```java
@Query(
        value = "select * from sales_orders o where o.status = :status order by o.created_at desc, o.id desc",
        countQuery = "select count(*) from sales_orders o where o.status = :status",
        nativeQuery = true)
Page<SalesOrder> findPageByStatus(
        @Param("status") String status, Pageable pageable);
```

The count query must count the same logical result set as the main query, without needing `ORDER BY`. If the main query uses CTEs, `GROUP BY`, or window functions, the count query may need a matching CTE followed by an outer `SELECT COUNT(*)`.

For complex queries, do not rely on the framework to derive the count query automatically. Write and test an explicit `countQuery`.

Be careful with dynamic native SQL and `Sort`. Never concatenate column names or sort directions directly from requests into SQL. Whitelist permitted choices, or declare fixed ordering in the query. When using native queries with `Pageable`, pass page/size separately and inspect the generated SQL for your Spring Data version.

If you only need to know whether a next page exists without needing total rows, consider `Slice` or querying `limit + 1` rows to detect remaining data.

## 11. PostgreSQL-Specific Syntax

Native SQL lets you leverage engine-specific features. The examples below are PostgreSQL-specific, not standard JPQL.

### 11.1. ILIKE

`ILIKE` performs case-insensitive string matching using PostgreSQL collation rules:

```sql
SELECT id, customer_id, status
FROM sales_orders
WHERE status ILIKE 'paid';
```

Other databases may use `LOWER(column) = LOWER(?)`, specific collations, or different operators.

### 11.2. DISTINCT ON

`DISTINCT ON` keeps one row per key group according to `ORDER BY`. It is PostgreSQL-specific syntax:

```sql
SELECT DISTINCT ON (customer_id)
       id, customer_id, total_amount, created_at
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at DESC, id DESC;
```

To make which row is kept deterministic, the `DISTINCT ON` expression must match the leading expressions in `ORDER BY`. For portability, replace it with a CTE plus `ROW_NUMBER()`.

### 11.3. Aggregate FILTER

PostgreSQL supports `FILTER (WHERE ...)` on aggregates:

```sql
SELECT customer_id,
       COUNT(*) AS all_orders,
       COUNT(*) FILTER (WHERE status = 'PAID') AS paid_orders,
       SUM(total_amount) FILTER (WHERE status = 'PAID') AS paid_total
FROM sales_orders
GROUP BY customer_id;
```

This is cleaner than some `CASE WHEN` expressions, though you must check support on your target database.

### 11.4. JSONB

PostgreSQL provides the `jsonb` type and operators like `->>` and `@>`:

```sql
SELECT id, metadata ->> 'source' AS source
FROM audit_events
WHERE metadata @> '{"channel":"web"}'::jsonb;
```

`->>` extracts a JSON value as text; `@>` checks containment. You can create GIN indexes for some JSONB workloads, choosing operator classes and indexes based on actual query operators.

### 11.5. ON CONFLICT

`ON CONFLICT` supports upserts against unique constraints or unique indexes:

```sql
INSERT INTO customer_preferences (customer_id, preference_key, preference_value)
VALUES (101, 'language', 'vi')
ON CONFLICT (customer_id, preference_key)
DO UPDATE SET preference_value = EXCLUDED.preference_value;
```

This is PostgreSQL syntax. When you need inserted/updated rows back via `RETURNING`, use JDBC or a custom repository to control the result set; do not assume a typical `@Modifying` method maps every form of `RETURNING` to an Entity portably.

## 12. CTE Materialization and Query Tuning in PostgreSQL

In PostgreSQL, a CTE is not always an optimization fence. Since PostgreSQL 12, the planner can inline non-recursive CTEs referenced once, enabling optimizations across the CTE boundary.

You can specify:

- `MATERIALIZED`: forces the CTE to be evaluated into an intermediate result.
- `NOT MATERIALIZED`: allows inlining eligible CTEs.

Example:

```sql
WITH filtered_orders AS NOT MATERIALIZED (
    SELECT *
    FROM sales_orders
    WHERE status = 'PAID'
)
SELECT customer_id, SUM(total_amount)
FROM filtered_orders
GROUP BY customer_id;
```

Do not add `MATERIALIZED` or `NOT MATERIALIZED` by guesswork. They affect CTE re-evaluation, predicate pushdown, and intermediate data volume. Measure against realistic data.

### EXPLAIN and EXPLAIN ANALYZE

Use execution plans to see how the database actually runs a query:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, id, created_at
FROM sales_orders
WHERE status = 'PAID'
ORDER BY customer_id, created_at DESC, id DESC;
```

`EXPLAIN` shows the estimated plan. `EXPLAIN ANALYZE` executes the statement and reports actual metrics such as timing, row counts, and loops. When used with `UPDATE` or `DELETE`, the statement actually modifies data; only run it in a safe environment or inside a rolled-back transaction.

Key things to read:
- `Seq Scan`: sequential scan; not automatically bad if the table is small or most rows must be read.
- `Index Scan` / `Bitmap Index Scan`: index usage.
- `Sort`: sorting step; check row counts and memory/disk spill.
- Estimated rows vs. actual rows: large gaps indicate stale statistics or poor cardinality estimates.
- `Buffers`: blocks read from cache or storage.

## 13. Bulk DML and Transactions

Native updates/deletes in Spring Data JPA require `@Modifying` and a transaction:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Transactional
@Query(value = "update sales_orders set status = :newStatus where status = :oldStatus",
       nativeQuery = true)
int changeStatus(
        @Param("oldStatus") String oldStatus,
        @Param("newStatus") String newStatus);
```

The return value is the number of affected rows. `flushAutomatically` synchronizes pending changes before the bulk query; `clearAutomatically` clears the persistence context afterward to avoid continuing to use managed Entities with stale data.

Native bulk DML goes straight to the database:
- Does not load individual Entities for dirty checking.
- Does not invoke per-Entity lifecycle callbacks such as `@PreUpdate` or `@PreRemove`.
- Does not apply Entity lifecycle cascades as per-Entity operations do.
- Can leave managed Entities in the persistence context out of sync with the database.

If business rules require per-Entity validation or side effects, load the Entities and process them in a Service. If a bulk statement is the right choice, update any required audit columns directly in SQL or via well-designed database triggers.

## 14. Testing Native SQL With the Real Database Engine

CTEs, window functions, and PostgreSQL-specific syntax should not be tested only on H2 and assumed to behave identically on PostgreSQL. H2 offers compatibility modes, but they do not fully replace the real engine.

For integration tests, use Testcontainers to spin up PostgreSQL matching your target environment. Test dependencies:

```xml
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>1.20.6</version>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <version>1.20.6</version>
    <scope>test</scope>
</dependency>
```

Illustrative test:

```java
package com.example.orders;

import static org.assertj.core.api.Assertions.assertThat;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class SalesOrderNativeQueryTest {
    @Container
    static final PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("orderdb")
                    .withUsername("test")
                    .withPassword("test");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
        registry.add("spring.datasource.driver-class-name", postgres::getDriverClassName);
        registry.add("spring.jpa.hibernate.ddl-auto", () -> "create-drop");
    }

    @Autowired
    private SalesOrderRepository repository;

    @Autowired
    private TestEntityManager entityManager;

    @Test
    void returnsLatestPaidOrderPerCustomer() {
        entityManager.persist(new SalesOrder(
                10L, "PAID", new BigDecimal("10.00"), Instant.parse("2026-01-01T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                10L, "PAID", new BigDecimal("20.00"), Instant.parse("2026-01-02T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                20L, "PAID", new BigDecimal("30.00"), Instant.parse("2026-01-03T10:00:00Z")));
        entityManager.persist(new SalesOrder(
                10L, "CANCELLED", new BigDecimal("99.00"), Instant.parse("2026-01-04T10:00:00Z")));
        entityManager.flush();

        List<RankedOrderView> result = repository.findTopOrdersPerCustomer("PAID", 1);

        assertThat(result).hasSize(2);
        assertThat(result).extracting(RankedOrderView::getCustomerId)
                .containsExactly(10L, 20L);
        assertThat(result).extracting(RankedOrderView::getTotalAmount)
                .containsExactly(new BigDecimal("20.00"), new BigDecimal("30.00"));
        assertThat(result).extracting(RankedOrderView::getRowNumber)
                .containsOnly(1L);
    }
}
```

This test verifies the CTE, `ROW_NUMBER()`, partitioning by customer, newest-first ordering, and alias mapping into an interface projection. Run with:

```bash
mvn test
```

The expected result is `BUILD SUCCESS` with the PostgreSQL test passing. Testcontainers requires a working Docker environment; this describes the expected outcome of the example, not a build log run in this environment.

## 15. Choosing Native Query Result Mappings

| Result Type | Usage |
| --- | --- |
| Full Entity | Select all columns required by the Entity mapping; typically use `select *` only when the schema/result shape is suitable and stable. |
| Interface projection | Column aliases match the projection's property getters. |
| DTO class/record | Use `@SqlResultSetMapping`, compatible constructor mapping, or a custom repository for explicit mapping. |
| Scalar/aggregate | Use simple types or a projection with named fields; avoid `Object[]` when results need long-term maintenance. |

For native queries returning multiple columns that do not match an Entity, do not assume Spring Data always infers DTO constructors by column order. Use an interface projection with explicit aliases or declare an explicit result set mapping.

## 16. Common Pitfalls

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Native query reports missing table/column | Using Entity/property names instead of real schema names, or mapping mismatch | Check DDL, schema, table, and column names in the database. |
| CTE passes on PostgreSQL but fails on H2/MySQL | Syntax or feature support differs across engines | Test on the exact target database and categorize dialect-specific SQL clearly. |
| Window alias rejected in WHERE | Window expressions are evaluated after `WHERE` in the same `SELECT` | Wrap the window query in a CTE/subquery and filter in the outer query. |
| Non-deterministic `ROW_NUMBER` results | `ORDER BY` cannot break ties between equal rows | Add a unique secondary tie-breaker such as primary key. |
| `Page` has wrong total count | Count query does not share the main query's conditions | Declare a matching `countQuery` and test both content and totals. |
| Projection returns `null` for a property | Alias mismatches getter or driver/provider returns an unexpected type | Use explicit aliases, check JDBC types, and use a matching projection. |
| Managed entity holds stale data after native DML | Bulk SQL bypasses the persistence context | Flush before if needed and clear/refresh after updating. |
| Query is slow despite using a CTE | CTEs do not automatically make queries faster; plan or indexes may be suboptimal | Use `EXPLAIN (ANALYZE, BUFFERS)` and tune from real metrics. |
| SQL injection via dynamic `ORDER BY` | Concatenating raw column names or sort directions from requests | Whitelist identifiers and sort directions; bind parameters only for values. |

## 17. Design and Operational Principles

1. Use JPQL when the query can be expressed cleanly over the Entity model; use native SQL when CTEs, window functions, or database features are needed.
2. Document the target database and version for dialect-dependent queries.
3. Break complex queries into named CTEs reflecting the meaning of each step.
4. Use window functions instead of repeated self-joins for rankings, row-to-row comparisons, or running totals.
5. Always define deterministic ordering when using `ROW_NUMBER`, pagination, or selecting the latest record.
6. Declare an accurate `countQuery` for native `Page` queries.
7. Use projections or DTOs to fetch only required data and avoid hydrating full Entities.
8. Never concatenate user input into SQL identifiers or expressions; whitelist sort fields and bind all values.
9. Manage persistence context state after bulk native DML and remember per-Entity lifecycle callbacks do not run.
10. Measure performance using execution plans and production-like data; never assume CTEs, indexes, or window functions are automatically faster.
11. Test native SQL on the same engine and version as production; Testcontainers helps eliminate drift between dev and CI.
12. Manage schema changes with versioned migrations, reviewing indexes and constraints alongside dependent queries.
