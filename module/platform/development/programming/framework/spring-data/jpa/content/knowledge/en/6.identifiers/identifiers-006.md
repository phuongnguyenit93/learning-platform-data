# Application-Assigned Keys and How Spring Data Detects New Entities

## Objectives

In JPA, an entity's primary key can be generated by the database/provider or supplied by the application. When the application assigns the ID itself, Spring Data JPA needs to determine whether the object being saved is a new entity or an existing one in order to choose the right JPA call.

This lesson explains:

- The difference between database-generated IDs and application-assigned IDs.
- How Spring Data JPA determines whether an entity is new.
- Why a non-null ID can cause a new entity to be treated as an existing entity.
- How to use a `@Version` property or the `Persistable` interface to control detection.
- The impact of `persist`, `merge`, transactions, and optimistic locking.
- How to test, handle duplicate key errors, and select an appropriate strategy.

Examples use Java 17+, Spring Boot 3.x, Jakarta Persistence, and Spring Data JPA.

## 1. Primary Keys and ID Allocation

Every JPA entity requires an identifier marked with `@Id`. The ID uniquely identifies an entity record in both the persistence context and the database.

There are two common ways to supply IDs.

### 1.1. IDs Generated by the Database or JPA Provider

The application lets the provider/database generate the ID. For example, with an auto-incrementing numeric key:

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String email;

    protected Customer() {
    }

    public Customer(String email) {
        this.email = email;
    }

    public Long getId() {
        return id;
    }
}
```

When a new object is created, `id` is normally null. After persist/flush, the database assigns the ID and JPA populates the value on the entity.

With this pattern, Spring Data JPA can use the null ID state to detect a new entity when no higher-priority strategy applies.

JPA also supports strategies like `SEQUENCE` or `TABLE`. The exact strategy depends on the database and provider. The `@GeneratedValue` annotation indicates that the ID is produced by a provider/database strategy; the application does not manually assign the ID in normal flows.

### 1.2. Application-Assigned IDs

In some cases, the application already has the ID before saving:

- A UUID generated inside the application.
- An order number or customer code issued by another system.
- An ID synchronized from an external service.
- A natural key determined prior to writing to the database.

Example:

```java
@Entity
@Table(name = "external_orders")
public class ExternalOrder {

    @Id
    @Column(nullable = false, updatable = false)
    private UUID id;

    @Column(nullable = false)
    private String status;

    protected ExternalOrder() {
    }

    public ExternalOrder(UUID id, String status) {
        this.id = Objects.requireNonNull(id);
        this.status = status;
    }

    public UUID getId() {
        return id;
    }
}
```

The ID is already non-null as soon as the object is created. This is the crucial difference: Spring Data cannot rely solely on the presence of an ID value to conclude that the object has already been persisted.

If an entity uses an application-assigned ID and declares no other newness detection strategy, Spring Data JPA by default may classify the object as an existing entity. The next section explains the consequences.

Do not add `@GeneratedValue` to an ID that the application actively assigns in normal flows. Choose one consistent ID source and reflect it accurately in the mapping.

## 2. How Does Spring Data JPA Determine a New Entity?

When `repository.save(entity)` is called, Spring Data JPA must decide whether to invoke `EntityManager.persist` or `EntityManager.merge`. This decision relies on entity state, not a direct check of "whether the database already has a row with this ID" in every case.

With the default strategy, Spring Data JPA follows this detection order:

1. If the entity implements `Persistable`, Spring Data calls `isNew()` on the entity and uses that result.
2. If the entity does not implement `Persistable` but has a non-primitive `@Version` property, Spring Data checks the version. A null version means a new entity; a non-null version means an existing entity.
3. If neither case applies, Spring Data checks the ID. A null ID means a new entity; a non-null ID means an existing entity.

You can picture it as:

| Entity | Default Detection Rule |
|---|---|
| Null ID, no version | New |
| Non-null ID, no version | Existing |
| Wrapper `@Version`, null version | New |
| Wrapper `@Version`, non-null version | Existing |
| Implements `Persistable` | Uses `isNew()` result |

This order matters greatly. If an entity implements `Persistable`, `isNew()` overrides inference from version/ID. If it does not implement `Persistable`, a wrapper version property is checked before the ID.

### Why Do Pre-Assigned IDs Cause Issues?

Example:

```java
@Entity
public class ExternalOrder {

    @Id
    private UUID id;

    private String status;

    protected ExternalOrder() {
    }

    public ExternalOrder(UUID id, String status) {
        this.id = id;
        this.status = status;
    }
}
```

When creating the object:

```java
ExternalOrder order = new ExternalOrder(
        UUID.randomUUID(),
        "NEW"
);

repository.save(order);
```

The ID already has a value. If the entity lacks an appropriate version property and does not implement `Persistable`, the default strategy classifies the object as existing. Spring Data JPA chooses `merge` instead of `persist`.

This does not mean `merge` always issues an UPDATE statement. Under JPA, merge copies the state of the input object into a managed instance; the provider determines the actual state and may execute an INSERT if the entity does not exist yet. However, going through merge can require state checks or extra reads and fails to express the clear intent that "this is definitely a new entity."

If the application needs to distinguish clearly between new and persisted entities, provide an explicit newness signal.

## 3. How Do persist and merge Differ?

These are the two key JPA operations Spring Data JPA chooses between when saving an entity.

### 3.1. EntityManager.persist

`persist(entity)` introduces a new entity into the persistence context. The entity becomes managed and is scheduled for INSERT upon flush/commit.

- Used for new entities.
- The ID may already be assigned by the application before calling persist.
- If the database already contains a row with the same primary key, the write fails due to primary key uniqueness violation.
- The method does not return a different entity; the passed-in object itself becomes managed.

### 3.2. EntityManager.merge

`merge(entity)` copies the state of the input object into a managed instance and returns that managed instance.

- Typically used for detached entities or entities Spring Data classifies as existing.
- The input object does not necessarily become managed.
- You must use the object returned by `merge` or `repository.save` if you need to continue working with the managed instance.
- The provider may need to query the database to determine entity state and decide the write operation.

Example:

```java
ExternalOrder detached = loadOrderOutsideCurrentContext();

ExternalOrder managed = entityManager.merge(detached);

// Continue using managed in the current persistence context.
managed.setStatus("CONFIRMED");
```

With Spring Data JPA:

```java
ExternalOrder saved = repository.save(order);
```

Use `saved` if you continue modifying the entity after `save`, because in the merge case the returned instance may differ from the input instance.

### 3.3. save Is Not Equivalent to an Atomic Upsert

`repository.save(entity)` is Spring Data's save API. Do not mistake it for an atomic database upsert command, meaning "insert if absent, update if present" safely under all concurrent access.

`save` selects persist or merge based on the entity detection strategy. Atomicity, concurrency conflicts, and overwrite semantics depend on transactions, the provider, and the database.

If you need an upsert by business key under concurrent load, design explicitly:

- A unique constraint on the business key.
- Conflict handling when two transactions create the same key simultaneously.
- Appropriate transactions and retry policies.
- Native database upserts such as PostgreSQL `INSERT ... ON CONFLICT` if the business genuinely requires that behavior and accepts database coupling.

## 4. Approach 1: Using a @Version Property to Detect New Entities

JPA supports optimistic locking via `@Version`. When an entity has a non-primitive version property, Spring Data JPA can use a null version value to recognize a new entity.

This is often a clean option if the entity already needs optimistic locking.

Example of an entity with an application-assigned UUID:

```java
package com.example.demo.order;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

import java.util.UUID;

@Entity
@Table(name = "external_orders")
public class ExternalOrder {

    @Id
    @Column(nullable = false, updatable = false)
    private UUID id;

    @Version
    private Long version;

    @Column(nullable = false)
    private String status;

    protected ExternalOrder() {
    }

    public ExternalOrder(UUID id, String status) {
        this.id = id;
        this.status = status;
    }

    public UUID getId() {
        return id;
    }

    public Long getVersion() {
        return version;
    }

    public String getStatus() {
        return status;
    }

    public void setStatus(String status) {
        this.status = status;
    }
}
```

Repository:

```java
package com.example.demo.order;

import java.util.UUID;

import org.springframework.data.jpa.repository.JpaRepository;

public interface ExternalOrderRepository
        extends JpaRepository<ExternalOrder, UUID> {
}
```

Service creating a new entity:

```java
@Service
public class ExternalOrderService {

    private final ExternalOrderRepository repository;

    public ExternalOrderService(ExternalOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public ExternalOrder create(UUID externalId) {
        ExternalOrder order =
                new ExternalOrder(externalId, "NEW");

        return repository.save(order);
    }
}
```

When a new object is created:

- The ID already has a UUID value.
- The version starts as null.
- Spring Data JPA sees the `Long` version property is null.
- The entity is detected as new and Spring Data chooses persist.
- The JPA provider manages the version on save and updates it under optimistic locking rules.

When the entity is loaded from the database, the version has a value. Spring Data classifies it as existing and chooses merge if `save` is called on that instance.

### Why Use Long Instead of long?

`Long` is a wrapper type and can hold null. `long` is a primitive type and always defaults to 0.

Spring Data JPA only uses version as a newness signal when the version property is non-primitive. If you write:

```java
@Version
private long version;
```

then null cannot be used to represent a new entity. The default strategy falls back to checking the ID. With a non-null application-assigned ID, the entity may once again be classified as existing.

Let the JPA provider manage the version. Do not arbitrarily set version values in services or requests. Version supports optimistic locking, detecting when two transactions concurrently update the same data version.

### When Should You Choose @Version?

Use a version property when the entity needs optimistic locking or when the application wants to leverage Spring Data JPA's default null/non-null version detection.

Do not add `@Version` merely as a dummy flag if the application neither understands nor wants optimistic locking. Version becomes part of persistence mapping and affects UPDATE/DELETE statements as well as update conflict detection.

## 5. Approach 2: Implementing Persistable

If the entity does not need optimistic locking and its ID is application-assigned, it can implement `org.springframework.data.domain.Persistable<ID>`.

This interface defines two methods:

```java
public interface Persistable<ID> {
    ID getId();
    boolean isNew();
}
```

Spring Data JPA checks `isNew()` to decide whether the entity is new. You can maintain a transient state flag inside the entity.

Example:

```java
package com.example.demo.order;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.PostLoad;
import jakarta.persistence.PostPersist;
import jakarta.persistence.Table;
import jakarta.persistence.Transient;

import org.springframework.data.domain.Persistable;

import java.util.UUID;

@Entity
@Table(name = "external_orders")
public class ExternalOrder implements Persistable<UUID> {

    @Id
    @Column(nullable = false, updatable = false)
    private UUID id;

    @Column(nullable = false)
    private String status;

    @Transient
    private boolean newEntity = true;

    protected ExternalOrder() {
    }

    public ExternalOrder(UUID id, String status) {
        this.id = id;
        this.status = status;
    }

    @Override
    public UUID getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    public String getStatus() {
        return status;
    }

    public void setStatus(String status) {
        this.status = status;
    }

    @PostPersist
    @PostLoad
    void markNotNew() {
        this.newEntity = false;
    }
}
```

Role of each element:

- `implements Persistable<UUID>`: the entity provides its own identifier and newness state.
- `@Transient`: the `newEntity` flag is not persisted as a database column.
- `newEntity = true`: a freshly instantiated object in the application is treated as a new entity.
- `@PostPersist`: after the entity is persisted, the callback sets the flag to false.
- `@PostLoad`: when the entity is loaded from the database, the callback sets the flag to false.
- `isNew()`: returns the state used by Spring Data to choose persist or merge.

When calling:

```java
ExternalOrder order =
        new ExternalOrder(UUID.randomUUID(), "NEW");

ExternalOrder saved = repository.save(order);
```

Spring Data calls `isNew()`. Returning true causes it to pick `persist`. After JPA persists the entity, the `@PostPersist` callback marks the object as no longer new.

When the repository loads an entity from the database, `@PostLoad` also marks the object as existing. If `save` is called on a loaded entity, `isNew()` returns false and Spring Data picks merge.

### Watch Out for Objects Reconstructed from Requests

The transient flag strategy assumes new objects come from creation flows and existing objects are loaded from the database. If you take an already-existing ID from a request and construct a new object via a constructor that sets `newEntity = true`, `save` will choose persist. The database may reject it due to a duplicate primary key.

For update operations, you should:

1. Load the existing entity via the repository.
2. Check permissions and business preconditions.
3. Update the allowed properties.
4. Let the transaction commit synchronize the changes.

Never accept a JPA entity directly from a client and trust its state flag.

### Watch Out for Transaction Rollbacks

The `@PostPersist` callback can execute when the persistence context flushes, before the transaction actually commits. If the transaction subsequently rolls back, the in-memory object may already have flipped `newEntity` to false even though no row was committed to the database.

Therefore, do not reuse that instance as a new entity after a rollback. Create a new object or reload state from the database in a fresh transaction. The transient flag is only a signal for the repository's detection strategy, not a substitute for database transaction state.

### When Should You Choose Persistable?

Use `Persistable` when the ID is application-assigned and no suitable version property exists, or when new/existing detection rules need explicit control. It is flexible, though maintaining the state flag becomes the entity's responsibility and must be tested.

## 6. Comparing Detection Strategies

| Strategy | New Entity Condition | Advantages | Notes |
|---|---|---|---|
| Null ID | ID has no value yet | Simple; fits IDs generated on persist | Unsuitable for pre-assigned application IDs |
| Wrapper `@Version` | Null version | Leverages optimistic locking | Version must be managed by the provider |
| `Persistable.isNew()` | Per entity-supplied flag/logic | Accurate control for pre-assigned IDs | Must maintain state accurately across lifecycle |
| Custom `EntityInformation` | Per custom implementation | Flexible for specialized rules | Complex; usually unnecessary |

### Practical Selection Guide

- Database/provider-generated ID left null before saving: use the default strategy.
- Application-assigned UUID or external ID, and the entity needs optimistic locking: use a wrapper `@Version` property such as `Long`.
- Application-assigned ID, no optimistic locking needed, and explicit state control desired: implement `Persistable`.
- Highly specialized detection rules across the repository factory: consider custom `EntityInformation` only when the options above fall short.

Do not combine `Persistable` and `@Version` simultaneously just "to be safe." When an entity implements `Persistable`, `isNew()` is the signal used. Maintain one clear strategy and one source of truth for newness state.

## 7. Testing Example with Application-Assigned IDs

The following example uses the `Persistable<UUID>` entity from section 5. The test verifies that an object with a pre-assigned ID is saved and reloaded successfully.

```java
package com.example.demo.order;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.UUID;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;

@DataJpaTest
class ExternalOrderRepositoryTest {

    @Autowired
    private ExternalOrderRepository repository;

    @Test
    void savesAndLoadsOrderWithApplicationAssignedId() {
        UUID id = UUID.fromString(
                "d9428888-122b-11e1-b85c-61cd3cbb3210"
        );

        ExternalOrder order = new ExternalOrder(id, "NEW");

        ExternalOrder saved = repository.save(order);

        assertThat(saved.getId()).isEqualTo(id);
        assertThat(saved.isNew()).isFalse();

        repository.flush();

        ExternalOrder loaded = repository.findById(id).orElseThrow();

        assertThat(loaded.getId()).isEqualTo(id);
        assertThat(loaded.getStatus()).isEqualTo("NEW");
        assertThat(loaded.isNew()).isFalse();
    }
}
```

The test requires AssertJ/JUnit/Spring Boot test imports and appropriate JPA configuration. `@DataJpaTest` normally runs tests inside a transaction and rolls back after each test finishes. For entities implementing `Persistable`, lifecycle callbacks must behave as expected on the active provider.

If using the `@Version` strategy, also test:

- A new entity with an assigned ID and null version is inserted.
- A loaded entity has a non-null version.
- Two transactions updating the same version detect an optimistic locking conflict.
- Clients cannot overwrite version values to bypass concurrency checks.

To confirm actual SQL or PostgreSQL-specific behavior, run integration tests against the real target database. Embedded databases can differ in data types, constraints, and SQL syntax.

## 8. Common Errors

### New Entity with Non-Null ID Treated as Existing

Cause: the entity lacks a null wrapper version and does not implement `Persistable`. Spring Data checks the ID by default, sees a non-null ID, and chooses merge.

Solution: add a wrapper `@Version` if appropriate, or implement `Persistable` with a state flag managed via lifecycle callbacks.

### New Entity Inserted with Duplicate ID

Cause: `Persistable.isNew()` returns true for an object whose ID already exists in the database. Spring Data selects persist and the database rejects the duplicate primary key.

Solution: do not instantiate a new object with an existing ID to perform an update. Load the entity and modify it; if using `Persistable`, ensure the newness flag reflects the true lifecycle.

### Existing Entity Merged Like a New Entity

Cause: `isNew()` returns true for an already-existing object, or the transient flag was not updated on load.

Solution: check `@PostLoad`, `@PostPersist`, and all constructors/factories. Ensure existing objects are loaded via JPA or marked with the appropriate state.

### @Version Fails to Detect Newness

Common causes:

- Using primitive `long` instead of wrapper `Long`.
- Version is assigned a non-null value before the first save.
- The entity implements `Persistable` and `isNew()` takes precedence.
- Version mapping is not recognized properly by JPA.

Solution: check the mapping, let the provider manage the version, and confirm the active detection strategy.

### save Does Not Return the Same Input Instance

Cause: `save` may call merge; merge returns the managed instance.

Solution: always use the object returned from `save` if continuing operations on the entity.

### Assuming save Is a Safe Upsert

Cause: confusing the persist/merge strategy with an atomic database upsert statement.

Solution: design unique constraints, transactions, and concurrent conflict handling. If database-specific upsert semantics are needed, use an appropriate statement and test concurrency.

### Persistable Flag Wrong After Rollback

Cause: `@PostPersist` ran on flush, but the transaction rolled back afterward.

Solution: do not reuse the instance after a rollback; create a new object or re-read from the database in a new transaction.

## 9. Notes on UUIDs and Business Keys

UUIDs are a popular choice for application-assigned IDs because they can be created before database writes and work conveniently when multiple systems create data independently. Example:

```java
UUID orderId = UUID.randomUUID();
ExternalOrder order = new ExternalOrder(orderId, "NEW");
```

There is no `@GeneratedValue` in this mapping because the application is responsible for supplying the UUID.

JPA 3.1 also offers `GenerationType.UUID` for provider-generated UUIDs. That is a persistence-provider-generated ID, distinct from the application calling `UUID.randomUUID()` itself and assigning it to the entity before saving.

If using a business key as the primary key, evaluate stability and mutability. A primary key should be immutable throughout the entity's lifecycle. If business values can change, it is usually better to use a surrogate key as the primary key and place a unique constraint on the business key.

## 10. Pre-Production Checklist

- [ ] Clearly defined whether IDs are generated by database/provider or assigned by the application.
- [ ] Application-assigned IDs are not arbitrarily combined with `@GeneratedValue`.
- [ ] Understood Spring Data JPA's `isNew` detection strategy.
- [ ] For pre-assigned IDs, selected wrapper version or `Persistable` where needed.
- [ ] Never manually set version to control insert/update behavior.
- [ ] Never accept entities from clients and trust their newness flags.
- [ ] Always use the instance returned by `save`.
- [ ] Use unique constraints to protect IDs/business keys.
- [ ] Tested initial insert, reload, update, and key collision cases.
- [ ] Tested optimistic locking if the entity has `@Version`.
- [ ] Never reuse an entity instance after transaction rollback if lifecycle flags have changed.

## Conclusion

With application-assigned IDs, the ID is already non-null as soon as the entity is created. By default, Spring Data JPA may treat the entity as existing and choose `merge`. Understanding newness detection avoids unintended persistence paths.

There are two standard solutions: use a wrapper `@Version` property if the entity needs optimistic locking, or implement `Persistable` to provide `isNew()` explicitly. Pick one consistent strategy, test the lifecycle, and let the database enforce uniqueness. That way, saving entities with application-assigned IDs stays clear, safe, and maintainable.
