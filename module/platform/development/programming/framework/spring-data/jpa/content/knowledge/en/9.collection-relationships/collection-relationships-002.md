# Comparing One-to-Many with a Foreign Key vs. a Join Table

## 1. The One-to-Many Relationship Problem

A one-to-many (1:N) relationship describes a scenario where one parent object can be associated with many child objects, while each child object belongs to at most one parent object within that relationship.

For example, a department has many employees:

- A Department can have 0, 1, or many Employees.
- An Employee belongs to at most one Department.
- A department can exist before it has any employees.
- An employee may be allowed to belong to no department yet, depending on business rules.

In a relational database, there are two common ways to represent this:

1. Place a foreign key on the many-side table—that is, the Employee table has a `department_id` column pointing to Department.
2. Create a separate join table, such as `department_employee`, storing pairs of `department_id` and `employee_id`.

Both approaches can represent a one-to-many relationship, but they differ in data constraints, JPA mapping, relationship ownership, SQL queries, and maintenance cost.

## 2. Approach 1: Foreign Key on the Many-Side Table

### 2.1. Database Design

This is the most natural approach when each employee belongs to at most one department. The foreign key is placed in the Employee table:

```sql
create table department (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table employee (
    id bigint generated by default as identity primary key,
    name varchar(150) not null,
    department_id bigint,
    constraint fk_employee_department
        foreign key (department_id) references department(id)
);

create index idx_employee_department_id
    on employee(department_id);
```

The `department_id` column resides in the Employee table because Employee is the many side. An Employee row holds only a single `department_id` value, so it cannot point to multiple departments simultaneously.

If the business rule requires every employee to belong to a department, `department_id` can be declared NOT NULL. If employees are allowed to be unassigned, leave the column nullable. The foreign key ensures any non-null value references an existing department.

The foreign key constraint ensures an employee cannot reference a nonexistent department. It does not ensure every department has at least one employee; a department with zero employees remains valid data.

### 2.2. Bidirectional JPA Mapping

The common pattern places ManyToOne on Employee and OneToMany on Department:

```java
@Entity
@Table(name = "department")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany(
        mappedBy = "department",
        cascade = CascadeType.PERSIST,
        orphanRemoval = true
    )
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
    }

    public Department(String name) {
        this.name = name;
    }

    public void addEmployee(Employee employee) {
        employees.add(employee);
        employee.setDepartment(this);
    }

    public void removeEmployee(Employee employee) {
        employees.remove(employee);
        employee.setDepartment(null);
    }

    public Long getId() {
        return id;
    }

    public List<Employee> getEmployees() {
        return Collections.unmodifiableList(employees);
    }
}
```

```java
@Entity
@Table(name = "employee")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    protected Employee() {
    }

    public Employee(String name) {
        this.name = name;
    }

    void setDepartment(Department department) {
        this.department = department;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public Department getDepartment() {
        return department;
    }
}
```

In this example:

- `Employee.department` is the owning side of the relationship because the foreign key mapping is on ManyToOne.
- `Department.employees` uses `mappedBy = "department"`, making it the inverse side. The `mappedBy` value is the Java property name in Employee, not the column name `department_id`.
- When modifying the relationship, you must update the `department` property on Employee so JPA writes the foreign key properly.
- The `addEmployee` and `removeEmployee` helpers update both sides so the in-memory object graph stays consistent.

If you only call `department.getEmployees().add(employee)` without setting `employee.department`, the owning side has not changed. JPA may not write `department_id` as intended. This is a common mistake with bidirectional relationships.

### 2.3. Why Is ManyToOne Usually the Owning Side?

The foreign key lives in the Employee table. When assigning an employee to a department, the database needs to update `employee.department_id`. Therefore, the property corresponding to the foreign key column resides on Employee, making it the owning side of the mapping.

Department only represents navigation from parent to child. `mappedBy` informs the provider that Department does not own a separate foreign key or join table.

Making ManyToOne the owning side is usually simpler in SQL and aligns with the relational structure: each child row directly stores its parent's foreign key.

### 2.4. Unidirectional Relationship Using a Foreign Key

If the application only needs to navigate from Department to Employee and does not need a `department` field on Employee, you can map a unidirectional OneToMany with JoinColumn:

```java
@Entity
public class Department {

    @Id
    @GeneratedValue
    private Long id;

    @OneToMany
    @JoinColumn(name = "department_id")
    private List<Employee> employees = new ArrayList<>();

    protected Department() {
    }
}
```

JoinColumn indicates that the foreign key lives in the target Employee table. In this mapping, the collection on Department controls the association; Employee does not need a back-reference property.

Note: A unidirectional OneToMany without JoinColumn normally uses a join table per JPA defaults. If you want the foreign key on the child table, you must declare JoinColumn as shown above.

The exact SQL emitted by the provider can vary. Some unidirectional mappings with a foreign key can cause the provider to execute an extra UPDATE statement to set the foreign key after inserting. Always check the SQL and NOT NULL constraints with your provider. If you need a bidirectional relationship and want explicit foreign key handling, ManyToOne on the child side is usually more predictable.

## 3. Approach 2: Separate Join Table

### 3.1. Database Design

Instead of putting `department_id` in Employee, create a `department_employee` table to store the links:

```sql
create table department (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table employee (
    id bigint generated by default as identity primary key,
    name varchar(150) not null
);

create table department_employee (
    department_id bigint not null,
    employee_id bigint not null,
    constraint pk_department_employee
        primary key (department_id, employee_id),
    constraint uk_department_employee_employee
        unique (employee_id),
    constraint fk_department_employee_department
        foreign key (department_id) references department(id),
    constraint fk_department_employee_employee
        foreign key (employee_id) references employee(id)
);
```

The crucial detail that makes this truly one-to-many is the `UNIQUE(employee_id)` constraint. It guarantees an Employee appears at most once in the join table, meaning it cannot belong to multiple Departments at the same time.

If you omit this unique constraint, the same `employee_id` can appear with multiple `department_id`s. The structure then permits many-to-many, regardless of table or annotation naming.

A join table has an important difference from a direct foreign key: an Employee can exist with no row in `department_employee`. The foreign keys and unique constraint only guarantee valid links and at most one parent; they do not enforce that every Employee has a link. If business rules require every employee to belong to a department, additional database or application rules are needed.

### 3.2. Unidirectional OneToMany Mapping with JoinTable

Example where Department manages the Employee collection through a join table:

```java
@Entity
@Table(name = "department")
public class Department {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @OneToMany
    @JoinTable(
        name = "department_employee",
        joinColumns = @JoinColumn(name = "department_id"),
        inverseJoinColumns = @JoinColumn(name = "employee_id"),
        uniqueConstraints = @UniqueConstraint(
            name = "uk_department_employee_employee",
            columnNames = "employee_id"
        )
    )
    private Set<Employee> employees = new HashSet<>();

    protected Department() {
    }

    public Department(String name) {
        this.name = name;
    }

    public void addEmployee(Employee employee) {
        employees.add(employee);
    }

    public void removeEmployee(Employee employee) {
        employees.remove(employee);
    }
}
```

```java
@Entity
@Table(name = "employee")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Employee() {
    }

    public Employee(String name) {
        this.name = name;
    }
}
```

In JoinTable:

- `joinColumns` describes the column referencing the source entity Department.
- `inverseJoinColumns` describes the column referencing the target entity Employee.
- `uniqueConstraints` places a unique constraint on `employee_id` to preserve one-to-many cardinality.

JPA mappings express intent at the object layer; the actual schema still needs the corresponding constraint. If the schema is managed with Flyway or Liquibase, create the unique constraint in a migration and let Hibernate validate the schema.

If using `Set`, design Employee's `equals`/`hashCode` safely for entities and pre-/post-persist ID states. If uniqueness at the Java level is not required, `List` can also be used; when order needs to be persisted, consider `@OrderColumn`. Do not choose `Set` hoping the database will automatically guarantee uniqueness.

### 3.3. When Does a Join Table Make Sense?

A join table can be useful when:

- You cannot or do not want to add a foreign key column to the Employee table due to a legacy schema or because the child table is shared by multiple systems.
- Links are managed independently of Employee data.
- Assignment/linking needs to be decoupled from the base entity table.
- There are plans to evolve the link into a separate business entity.
- The existing database already uses an association table and the application must stay compatible with that schema.

However, a join table introduces an extra table and an extra join step when querying the relationship. For a straightforward model where each Employee belongs to at most one Department, a foreign key on Employee is usually less complex.

## 4. Comparing the Two Representations

| Criterion | Foreign key on child table | Join table |
|---|---|---|
| Relationship location | employee.department_id | department_employee |
| Table count | No separate join table needed | Adds one table |
| 1:N cardinality | One FK column per Employee | UNIQUE(employee_id) in join table |
| Each child has at most one parent | Enforced directly by FK structure | Enforced by unique constraint |
| Mandatory parent for child | Can use FK NOT NULL | Needs additional rules; a child may have no link row |
| Query by parent | Filter directly on employee.department_id | Join through join table |
| Assign/transfer parent | Update Employee's FK | Update link row |
| Schema change | Add FK to child table | No need to add FK to child entity table |
| Complexity | Usually lower | Higher due to managing an extra association table |
| Extending link attributes | Requires switching to an association entity if relationship attributes are added | Can evolve into an association entity |

For new schemas and simple relationships, foreign key mapping is usually the first choice. A join table should be chosen when justified by schema constraints, ownership, or the lifecycle of the association itself.

## 5. Owning Side and mappedBy

In JPA, the owning side is the side that determines what association changes are written to the database. This concept is not synonymous with the parent object in the business domain.

### 5.1. With a Direct Foreign Key

In a bidirectional mapping:

- `Employee.department` is the owning side because it contains `@JoinColumn`.
- `Department.employees` is the inverse side because it has `mappedBy = "department"`.

When adding an employee:

```java
Department department = ...;
Employee employee = new Employee("An");

department.addEmployee(employee);

entityManager.persist(department);
entityManager.flush();
```

If persist cascade is configured from Department to Employee, the new entity can be persisted along with the parent. Importantly, the `addEmployee` helper must set `Employee.department` so the owning side is updated.

If not using a helper, you must set both sides manually:

```java
department.getEmployees().add(employee);
employee.setDepartment(department);
```

Avoid exposing a widely mutable collection if multiple layers might update only one side and leave the object graph inconsistent.

### 5.2. With a Join Table

In the unidirectional OneToMany + JoinTable example, the `Department.employees` collection manages the association table. Adding or removing elements from the collection modifies rows in `department_employee`.

There is no `Employee.department` to synchronize, making the object graph code simpler. In return, any query from Employee back to Department must go through the association table or be modeled separately.

### 5.3. Why Is mappedBy Not a Column Name?

In the example:

```java
@OneToMany(mappedBy = "department")
private List<Employee> employees;
```

`department` is the Java property name in Employee:

```java
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
```

`department_id` is the column name in the database. Writing `mappedBy = "department_id"` is wrong because `mappedBy` references the mapped property on the owning-side entity, not the SQL column name.

## 6. Cascade and orphanRemoval Do Not Determine How Relationships Are Stored

Cascade and orphanRemoval are entity lifecycle rules. They do not replace the owning side, nor do they decide whether a relationship is stored via a foreign key or a join table.

### 6.1. Cascade

Example:

```java
@OneToMany(
    mappedBy = "department",
    cascade = {CascadeType.PERSIST, CascadeType.MERGE}
)
private List<Employee> employees = new ArrayList<>();
```

PERSIST cascade means persisting a Department can propagate to associated Employees; MERGE cascade applies similarly to merge. REMOVE cascade propagates parent removal to children; `CascadeType.ALL` includes all cascade types.

Do not use ALL mechanically. If an Employee can be used independently or referenced elsewhere, REMOVE cascade can delete data unexpectedly.

### 6.2. orphanRemoval

For a one-to-many relationship where children belong to the parent's lifecycle ownership, `orphanRemoval` can delete a child when it is removed from the association:

```java
@OneToMany(
    mappedBy = "department",
    cascade = CascadeType.PERSIST,
    orphanRemoval = true
)
private List<Employee> employees = new ArrayList<>();
```

When an Employee is removed from the collection and the persistence context is synchronized, the provider deletes the child entity according to orphan removal semantics. This fits when Employee is genuinely a private child of Department.

If you only want to transfer an Employee from Department A to Department B, understand the orphanRemoval rules and update the relationship within the same transaction. Do not use orphanRemoval when children can be shared or need to exist independently after unlinking.

### 6.3. Deleting a Link Row vs. Deleting a Child Entity

With a join table, deleting an association row only removes the link. It does not necessarily delete the Employee. If `orphanRemoval` is configured, the provider may also delete the child entity when it becomes an orphan in the relationship. These two behaviors are distinct and must be designed according to business requirements.

Similarly, `ON DELETE CASCADE` in the database is a database referential action; remove cascade in JPA is a rule for propagating operations through the persistence context. Do not confuse the two mechanisms.

## 7. Queries and Performance

### 7.1. Fetching Children by Parent

With a foreign key:

```sql
select e.*
from employee e
where e.department_id = ?;
```

With a join table:

```sql
select e.*
from employee e
join department_employee de on de.employee_id = e.id
where de.department_id = ?;
```

Foreign key mapping involves fewer steps. A join table requires an additional join, though with proper indexes and suitable data volumes, the database can still execute it efficiently.

### 7.2. Required Indexes

With a foreign key, an index is typically created on `employee.department_id` because queries commonly filter by department.

With a join table, the primary key `(department_id, employee_id)` supports finding employees by department. A unique index on `employee_id` supports reverse queries and ensures each employee has at most one link.

Not every database automatically creates indexes for foreign keys. Inspect your schema and execution plans rather than assuming an index already exists.

### 7.3. N+1 and Fetch Strategy

Whether using a foreign key or a join table, lazy loading can still cause N+1 queries if you load a list of Departments and then iterate over `employees` for each department.

The solution should fit the use case:
- Fetch join when both parent and children must be loaded in the same query.
- EntityGraph to specify a fetch plan.
- DTO projection when the screen only needs specific fields.
- Batch fetching when loading relationships for multiple parents without joining everything.

Do not switch every relationship to EAGER to avoid N+1. Doing so can over-fetch data and make queries harder to control. With collection fetch joins combined with pagination, carefully check the results because the join can multiply parent rows by the number of children.

### 7.4. Modifying Large Collections

When a collection is very large, avoid always loading the entire list just to add or remove one link. Design the use case to update by ID or an appropriate statement, and check the SQL generated by the provider.

With a unidirectional OneToMany using a join table, the way the provider synchronizes the collection can produce extra delete/re-insert operations on link rows. For large collections, this can be expensive. Inspect the actual Hibernate SQL and consider an association entity or specialized SQL operations if the workload requires it.

## 8. When a Join Table Should Become a Separate Entity

If the relationship has its own attributes—such as assignment timestamp, the employee's role in the department, approver, or effective status—the association is no longer just a pair of keys.

In that case, model the join table as an entity:

```java
@Entity
@Table(name = "department_assignment")
public class DepartmentAssignment {

    @Id
    @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "employee_id", nullable = false)
    private Employee employee;

    @Column(nullable = false)
    private LocalDate assignedAt;

    @Column(nullable = false)
    private String role;

    protected DepartmentAssignment() {
    }
}
```

This model turns the association into a business object with its own lifecycle and data. You can place a unique constraint on `employee_id` if an employee has only one active assignment, or use a more complex key/constraint if historical assignments need to be stored.

When an association has attributes, do not force it into `@ManyToMany` or a hidden JoinTable. An explicit association entity makes validation, auditing, querying, and transactions much clearer.

## 9. Decisions to Check Before Choosing

Answer the following questions:

1. Can a child belong to multiple parents at the same time? If not, a direct foreign key is the natural representation; a join table must have a unique constraint on the child key.
2. Must a child always have a parent? A NOT NULL foreign key can enforce this directly; a join table requires additional rules.
3. Does the child have an independent lifecycle? If so, be careful with REMOVE cascade and orphanRemoval.
4. Is navigation from child to parent needed? If so, a bidirectional mapping with ManyToOne is usually appropriate.
5. Is there a schema reason not to add a foreign key to the child table? If so, a join table may fit.
6. Does the association have its own attributes? If so, consider an association entity.
7. Do queries more frequently filter by parent or by child? Design indexes to match query directions.
8. Can the collection become very large? If so, avoid loading the entire collection for simple operations.
9. Is the schema managed by Hibernate or migrations? Cardinality constraints must be created and verified in the database.

## 10. Conclusion

For simple one-to-many relationships, a foreign key on the many-side table is usually the clearest and most efficient choice. It directly expresses that each child has at most one parent; NOT NULL can enforce that a child has a parent, while an index supports querying by parent.

A join table is useful when the schema cannot or should not place a foreign key directly in the child table, when the association is managed independently, or when it may evolve into a separate entity. To preserve one-to-many cardinality, a unique constraint on the child key in the join table is required; without this constraint, the database effectively allows many-to-many.

In JPA, understanding the owning side, `mappedBy`, JoinColumn, JoinTable, cascade, and orphanRemoval is essential. Synchronize the owning side properly, enforce constraints in the database, inspect the SQL generated by the provider, and choose a fetch plan based on actual use cases.
