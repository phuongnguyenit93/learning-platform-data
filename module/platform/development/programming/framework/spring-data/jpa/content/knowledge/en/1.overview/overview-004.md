# Entities, Tables, Identifiers, Repositories, and Transactions in a Single Model

Spring Data JPA connects the Java object model with relational data in a database. To understand how the components work together, we use one running example: managing books. A book is represented by the **Book** entity, stored as a row in the **books** table. The **id** field is the primary key; **BookRepository** provides query and storage operations; **BookService** defines a business transaction that may span multiple repository operations.

After this lesson, you will be able to explain and implement the relationship between an entity, table, primary key, repository, and transaction; know where to place transaction boundaries; and understand why modifying a managed entity can be persisted to the database without calling **save()** again.

## 1. Viewing the Whole Model

| Component | Role in the example |
|---|---|
| Entity **Book** | Java object representing a persistently stored book |
| Table **books** | Where the database stores book rows |
| Primary key **id** | Uniquely identifies a row and an entity |
| Repository **BookRepository** | Data access gateway: find, insert, update, delete |
| Service **BookService** | Enforces business rules and defines transaction boundaries |
| Transaction | Ensures a group of data changes commits or rolls back as a unit |

Flow for writing a new book:

~~~text
BookService.register(...)
        |
        | @Transactional
        v
BookRepository.save(book)
        |
        v
JPA EntityManager / Hibernate
        |
        v
INSERT INTO books (...)
        |
        v
COMMIT transaction
~~~

Flow for updating the price:

~~~text
BookService.changePrice(...)
        |
        | begin transaction
        v
BookRepository.findByIsbn(...)
        |
        v
Book managed by JPA (managed)
        |
        | book.changePrice(...)
        v
Dirty checking detects change
        |
        v
UPDATE books SET price = ... WHERE id = ...
        |
        v
COMMIT transaction
~~~

An entity is a Java-side concept; tables and rows are database-side structures. JPA maps between the two sides. A repository works with entities, while a transaction wraps a unit of work so data operations coordinate consistently.

**Prerequisites for the example:** the code blocks below are separate source files in a Spring Boot 3.x application running on Java 17 or later, with the **spring-boot-starter-data-jpa** dependency, a configured DataSource, and a corresponding schema in the database. They are not a standalone program that can be compiled with **javac** alone. Exact SQL output depends on Hibernate, dialect, database, and application configuration.

## 2. How Does an Entity Map to a Table?

An entity is a Java class managed by JPA and mapped to stored data. The class is typically annotated with **@Entity**. **@Table** specifies the table name and can declare table-level constraints.

We use a book model with four properties:

- **id**: primary key generated by the database.
- **title**: book title, required.
- **isbn**: ISBN code, required and unique in the example.
- **price**: book price, using **BigDecimal** to avoid binary floating-point rounding errors common when using **float** or **double** for money.

~~~java
package com.example.book.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;

import java.math.BigDecimal;

@Entity
@Table(
    name = "books",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_books_isbn",
        columnNames = "isbn"
    )
)
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String title;

    @Column(nullable = false, length = 20)
    private String isbn;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal price;

    // JPA requires a no-argument constructor; protected is sufficient.
    protected Book() {
    }

    public Book(String title, String isbn, BigDecimal price) {
        this.title = requireText(title, "title");
        this.isbn = requireText(isbn, "isbn");
        this.price = requirePrice(price);
    }

    public void changePrice(BigDecimal newPrice) {
        this.price = requirePrice(newPrice);
    }

    private static String requireText(String value, String fieldName) {
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(fieldName + " must not be blank");
        }
        return value.trim();
    }

    private static BigDecimal requirePrice(BigDecimal value) {
        if (value == null || value.signum() < 0) {
            throw new IllegalArgumentException("price must be greater than or equal to zero");
        }
        return value;
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public String getIsbn() {
        return isbn;
    }

    public BigDecimal getPrice() {
        return price;
    }
}
~~~

### Meaning of the Annotations

- **@Entity**: marks the class as an entity. JPA manages the lifecycle of objects of this class.
- **@Table(name = "books")**: maps the class to the **books** table. If omitted, the table name is derived using the provider's naming rules and application configuration.
- **@Id**: marks the entity's primary identifier property. Every entity must have an identifier.
- **@GeneratedValue**: specifies how primary key values are generated. **IDENTITY** is commonly used with identity/auto-increment columns; the appropriate strategy depends on the database management system and actual schema.
- **@Column**: describes column mapping, such as **nullable**, string length, precision, and scale.
- **@UniqueConstraint**: declares a table-level unique constraint. In the example, two rows cannot have the same ISBN.

Annotations describe the mapping and can be used by Hibernate during schema generation. They do not automatically ensure an existing schema is updated properly in every environment. The database still needs the corresponding table, columns, and constraints.

### Important Rules When Writing Entities

1. An entity needs a **public** or **protected** no-argument constructor so JPA can instantiate it.
2. Do not declare the entity as **final** and avoid making persistent properties **final**, because the provider needs to manage the entity.
3. Placing annotations on fields as in the example means JPA uses field access. If annotations are placed on getters, JPA uses property access. Do not mix both styles arbitrarily within the same entity.
4. Do not allow the primary key to change after the entity has been created. The primary key is the row's stable identifier.
5. Do not base **equals()** and **hashCode()** on all mutable fields. Doing so can cause entities to behave unpredictably in a **Set**, **Map**, or when changing state.
6. Use **BigDecimal** for money and decimal data requiring exactness. Do not initialize monetary values from **double** calculations and convert to **BigDecimal** afterward.

## 3. Primary Key and Business Key

In the example, **id** is the primary key. Each row in the **books** table has a unique, non-null **id** value. JPA uses this key to recognize whether two reads refer to the same entity.

**isbn** is the business key: it has meaning in the business domain and is used to look up books. We add a unique constraint so the database protects ISBN uniqueness.

The two key types serve different purposes:

| Characteristic | **id** (technical primary key) | **isbn** (business key) |
|---|---|---|
| Purpose | Stably identifies a record | Identifies a book according to business rules |
| Value | Usually system-generated | Comes from book data |
| Mutable? | Should be treated as immutable | May have a business process to edit |
| Use in JPA | Marked with **@Id** | Not the JPA identifier in the example |
| Constraint | Primary key | Unique constraint |

Do not use a business attribute as the primary key simply because it currently appears unique. Business codes can change by policy, whereas a primary key should remain stable throughout the data lifecycle. Conversely, a technical primary key does not replace a unique constraint on business data.

### Choosing a Key Generation Strategy

JPA provides common strategies:

- **GenerationType.IDENTITY**: the database generates the key on insert, typically fitting identity or auto-increment columns.
- **GenerationType.SEQUENCE**: uses a database sequence; typically suited to PostgreSQL and Oracle.
- **GenerationType.TABLE**: uses a separate table to manage generated values.
- **GenerationType.AUTO**: lets the provider choose a strategy appropriate for the dialect.

No single strategy is always best for every database. Choose based on the database, feature support, and how the schema is managed. When using **IDENTITY**, Hibernate may need to perform inserts early to obtain the ID; therefore, SQL emission timing can differ from other strategies.

## 4. A Repository Is the Data Access Gateway

Spring Data JPA lets you declare a repository interface without writing a basic CRUD implementation class yourself. For the **Book** entity with a primary key of type **Long**, the repository can be written as:

~~~java
package com.example.book.repository;

import com.example.book.domain.Book;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.List;
import java.util.Optional;

public interface BookRepository extends JpaRepository<Book, Long> {

    Optional<Book> findByIsbn(String isbn);

    boolean existsByIsbn(String isbn);

    List<Book> findByTitleContainingIgnoreCase(String keyword);
}
~~~

Declaring **JpaRepository<Book, Long>** means the repository manages the **Book** entity and the primary key type is **Long**.

Some built-in operations:

| Method | Meaning |
|---|---|
| **save(book)** | Saves a new entity or synchronizes entity changes |
| **findById(id)** | Finds by primary key, returning **Optional<Book>** |
| **findAll()** | Retrieves a list of entities |
| **existsById(id)** | Checks whether an entity exists by ID |
| **deleteById(id)** | Deletes by ID |
| **flush()** | Asks the persistence context to push changes to the database |

Spring Data JPA also supports deriving queries from method names:

- **findByIsbn** creates a query to find a book by ISBN.
- **existsByIsbn** creates a query to check whether an ISBN exists.
- **findByTitleContainingIgnoreCase** searches for titles containing a keyword, case-insensitively.

When query rules become more complex, **@Query**, JPQL, native SQL, or Specifications can be used. Only add custom queries when derived methods no longer express the requirement clearly.

A repository is neither a table nor the place that should hold all business rules. It focuses on data access. Whether an ISBN is allowed to be registered or whether a book's price can be changed belongs to the business logic of the service/domain.

## 5. Transactions Belong at the Service Layer

A business operation may require multiple data accesses. For example, registering a book requires checking the ISBN, creating the entity, and saving it. Changing a price requires finding the book and updating its price. If each repository call ran in an independent transaction, it would be difficult to guarantee the entire business operation is a consistent unit.

Placing **@Transactional** on the service groups repository operations into the same transaction:

~~~java
package com.example.book.service;

import com.example.book.domain.Book;
import com.example.book.repository.BookRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.math.BigDecimal;
import java.util.NoSuchElementException;

@Service
public class BookService {

    private final BookRepository bookRepository;

    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    @Transactional
    public Long register(String title, String isbn, BigDecimal price) {
        if (bookRepository.existsByIsbn(isbn)) {
            throw new IllegalStateException("ISBN already exists: " + isbn);
        }

        Book book = new Book(title, isbn, price);
        Book savedBook = bookRepository.save(book);
        return savedBook.getId();
    }

    @Transactional(readOnly = true)
    public BookView getByIsbn(String isbn) {
        Book book = bookRepository.findByIsbn(isbn)
            .orElseThrow(() -> new NoSuchElementException("Book not found: " + isbn));

        return BookView.from(book);
    }

    @Transactional
    public void changePrice(String isbn, BigDecimal newPrice) {
        Book book = bookRepository.findByIsbn(isbn)
            .orElseThrow(() -> new NoSuchElementException("Book not found: " + isbn));

        book.changePrice(newPrice);
        // book is managed; JPA will detect changes on flush.
    }
}
~~~

DTO used to return data outside the service:

~~~java
package com.example.book.service;

import com.example.book.domain.Book;

import java.math.BigDecimal;

public record BookView(Long id, String title, String isbn, BigDecimal price) {

    public static BookView from(Book book) {
        return new BookView(
            book.getId(),
            book.getTitle(),
            book.getIsbn(),
            book.getPrice()
        );
    }
}
~~~

### Why Is the Service the Right Transaction Boundary?

A service represents a complete business action. In **register**, checking the ISBN and saving the book are in the same transaction. In **changePrice**, loading the entity and updating the price are in the same transaction.

**@Transactional** is typically applied through a Spring proxy. Therefore:

- A method needing a transaction must be called through a Spring bean/proxy.
- Calling another transactional method on the same instance (self-invocation) typically bypasses the proxy, so the called method's annotation may not take effect as expected.
- Place transactions on service methods with clear business meaning and invoke the service through a Spring-managed dependency.

CRUD methods inherited from **JpaRepository** have Spring Data JPA's default transaction configuration. However, placing transactions on the service is still useful because it wraps multiple repository operations and clarifies the unit of work. Custom-declared query methods should not be assumed to always have their own transaction; the service transaction wraps them in this flow.

### What Does **readOnly = true** Mean?

**@Transactional(readOnly = true)** indicates that the method primarily reads data. It is a hint to the transaction manager/provider to optimize certain operations; it is not an authorization mechanism and should not be treated as a security barrier blocking all writes.

Do not use **readOnly = true** on methods intended to modify entities.

## 6. JPA Manages Entities and Automatically Persists Changes

JPA tracks entities through the persistence context. An entity typically goes through these states:

| State | Meaning |
|---|---|
| Transient / New | Newly created Java object, not yet managed by a persistence context |
| Managed | Managed by a persistence context; changes can be synchronized automatically |
| Detached | Previously managed but no longer attached to a persistence context |
| Removed | Marked for deletion upon synchronization |

When calling **findByIsbn** inside an active transaction, JPA returns a managed entity. If you call:

~~~java
Book book = bookRepository.findByIsbn(isbn)
    .orElseThrow();
book.changePrice(newPrice);
~~~

then the change to the **price** property is tracked by the persistence context. On flush, Hibernate compares entity state and issues the necessary **UPDATE** statement. Because the entity remains managed in the current transaction, there is no need to call **bookRepository.save(book)** again.

This is called dirty checking. It is a core feature of JPA.

Conversely, if an object is detached, modifying its fields is not automatically synchronized. When you need to persist detached state, use **save**/**merge** properly and use the returned object. **save()** does not always issue an **UPDATE** statement; Spring Data JPA checks whether the entity is new or existing and coordinates with JPA to persist or merge.

## 7. Flush, Commit, and Rollback

These three concepts are related but not the same:

- **Flush**: synchronizes pending changes in the persistence context to the database via SQL. Flush does not end the transaction.
- **Commit**: confirms the transaction succeeded. Changes become committed data according to the database's transaction mechanism.
- **Rollback**: cancels uncommitted changes of a transaction when the transaction fails.

A service method called through a proxy typically follows this sequence:

1. Spring opens a transaction before running the method body.
2. Repository operations join the current transaction via the default **REQUIRED** propagation.
3. JPA tracks entities and changes in the persistence context.
4. When needed, JPA flushes SQL to the database; flushing can also happen automatically before a query or when the transaction ends.
5. If the method completes normally, Spring commits the transaction.
6. If an error matching rollback rules occurs, Spring rolls back the transaction.

By default, Spring rolls back on unchecked exceptions (**RuntimeException** and **Error**) but does not automatically roll back on all checked exceptions. If the business logic needs rollback for checked exceptions, an appropriate **rollbackFor** can be declared, such as **@Transactional(rollbackFor = Exception.class)**. Use this setting only when the business error policy is clearly defined.

For example, if **register** saves a book and then throws an unchecked exception before the transaction finishes, the write operation in that transaction is rolled back. This prevents half-completed business state.

## 8. Data Constraints Must Be Protected at the Database Level

In the service there is:

~~~java
if (bookRepository.existsByIsbn(isbn)) {
    throw new IllegalStateException("ISBN already exists");
}
~~~

This check helps return a clear error when an ISBN already exists. However, it is not enough to protect uniqueness under concurrency:

1. Request A checks the ISBN and gets the result that it does not exist.
2. Request B also checks the same ISBN and gets the result that it does not exist.
3. Both proceed to insert.

If you rely solely on the Java check, two requests can pass the check together. A unique constraint in the database is the final line of defense. When two inserts race, the database rejects one insert that violates the constraint.

Therefore, you should combine:

- A check in the service to produce clear business feedback.
- A unique constraint in the schema to protect integrity under concurrent access.
- Appropriate constraint error handling in the application layer to translate it into a meaningful response.

Similarly, **nullable = false** in a mapping needs to correspond to **NOT NULL** in the actual schema. Do not assume an annotation automatically fixes an already-deployed database without checking the schema configuration.

## 9. Schema Configuration in Development and Production

Hibernate can be configured to generate or validate a schema. In a learning environment, **spring.jpa.hibernate.ddl-auto=create-drop** or **update** can be convenient for experimentation. However, **update** should not be used by default as a production schema management strategy.

For applications with long-lived data, schema changes should be managed using versioned migrations such as Flyway or Liquibase. The application can use **spring.jpa.hibernate.ddl-auto=validate** to check mappings against the schema created by migrations.

The values **create**, **create-drop**, **update**, and **validate** behave differently. Choose according to the environment lifecycle and data strategy; do not copy development settings to production without evaluating their impact.

## 10. Common Errors

| Error | Cause | How to fix |
|---|---|---|
| Cannot save entity | Class missing **@Entity**, missing ID, or wrong mapping | Check annotations, constructor, and schema |
| Missing constructor error | Entity lacks an appropriate no-argument constructor | Add a **protected** or **public** no-arg constructor |
| ID is always null in code | Not yet inserted/flushed or unsuitable ID strategy | Check transaction and **@GeneratedValue** strategy |
| Duplicate ISBN | Checked only in service, missing unique constraint | Create a unique constraint and handle violation errors |
| Entity changed but database did not | Entity is detached or changed outside a managed transaction | Load the entity inside a transaction and modify it while managed |
| Calling **save()** repeatedly unnecessarily | Not understanding dirty checking | For a managed entity, modifying fields inside a transaction is enough |
| Transaction has no effect | Self-invocation within the same bean or bean not managed by Spring | Call through a Spring proxy and put annotations on the appropriate service |
| Data only partially written | Multiple operations not in the same transaction | Wrap related business operations in a single transaction |
| **@Column** mismatches database | Mapping and schema migration differ | Synchronize migrations with entities and use validate when appropriate |
| Using **double** for money | Binary floating-point representation error | Use **BigDecimal** with appropriate precision/scale |

## 11. Checklist When Designing a New Entity

- [ ] Identify which classes truly need persistent storage and mark them with **@Entity**.
- [ ] Specify the table with **@Table** when explicit names or constraints are needed.
- [ ] Define a stable primary key with **@Id**.
- [ ] Choose a **@GeneratedValue** strategy suited to the database.
- [ ] Declare appropriate nullability, length, precision, scale, and unique constraints.
- [ ] Enforce important invariants in constructors or domain methods.
- [ ] Create a repository with the correct entity type and primary key type.
- [ ] Place transactions in the service according to business boundaries.
- [ ] Use DTOs when transferring data across API boundaries.
- [ ] Keep entity mappings synchronized with actual migrations/schema.

## 12. Summary Through the Book Model

In this model, **Book** is the Java entity; **books** is the storage table; **id** is the primary key; **isbn** is the business key with a unique constraint; **BookRepository** provides data operations; and **BookService** defines the transaction for each business action.

When creating a book, the service calls the repository to save the entity. When changing the price, the service loads the entity inside a transaction and updates its property; JPA dirty checking detects the change and synchronizes it to the database on flush. The transaction determines whether all operations are committed or rolled back. Understanding this relationship helps you design a clear persistence layer and avoid confusion between Java objects, database tables, repositories, and units of work.
