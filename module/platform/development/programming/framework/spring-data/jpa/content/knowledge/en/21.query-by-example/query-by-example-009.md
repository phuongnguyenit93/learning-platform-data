# Choosing Query by Example for Simple Search Forms

## Objective

Query by Example (QBE) is a way to build queries from a sample object (probe). The application populates the properties to search for in the probe, then uses `Example` and `ExampleMatcher` to specify how matching works. Spring Data JPA translates the values in the probe into query conditions without requiring JPQL to be written for every filter combination.

QBE is especially well suited for simple search forms where users can fill in one or more optional fields such as name, email, status, or department. Unfilled values are typically ignored.

After this lesson, you will be able to:

- Understand probe, Example, and ExampleMatcher.
- Build search queries from optional form fields.
- Choose matchingAll or matchingAny.
- Configure string matching, case sensitivity, and ignored properties.
- Combine QBE with Sort and Pageable.
- Recognize QBE's limitations and when to switch to Specification, Querydsl, or @Query.
- Avoid bugs caused by primitive default values, null, associations, and untrusted form data.

The examples use Java 17+, Spring Boot 3.x, Jakarta Persistence, and Spring Data JPA.

## 1. What is Query by Example?

QBE builds search conditions from a sample object. Populated properties in the probe become matching criteria; null properties are usually ignored by default.

For example, a user fills out a form:

- Name: `An`
- Email: left blank
- Active status: `true`

The application creates an Employee probe with fullName set to `An`, email set to null, and active set to true. QBE generates a query semantically equivalent to:

```sql
WHERE full_name = 'An'
  AND active = true
```

If the matcher for name is configured for substring matching, the condition can be equivalent to:

```sql
WHERE full_name LIKE '%An%'
  AND active = true
```

Actual SQL is generated by the JPA provider and uses bind parameters; there is no need to concatenate SQL strings manually.

Three main components:

| Component | Role |
|---|---|
| Probe | Sample object holding the values to search for |
| ExampleMatcher | Defines how to match, ignore fields, and handle strings |
| Example | Combines the probe with the matcher into query criteria |

QBE lives in Spring Data Commons and is supported by Spring Data JPA via `QueryByExampleExecutor`.

## 2. Probe, Example, and repository

Suppose an Employee entity:

```java
package com.example.demo.employee;

import jakarta.persistence.*;

@Entity
@Table(name = "employees")
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String fullName;

    @Column(nullable = false, unique = true, length = 320)
    private String email;

    @Column(nullable = false)
    private Boolean active;

    protected Employee() {
    }

    public Employee(String fullName, String email, Boolean active) {
        this.fullName = fullName;
        this.email = email;
        this.active = active;
    }

    public Long getId() {
        return id;
    }

    public String getFullName() {
        return fullName;
    }

    public String getEmail() {
        return email;
    }

    public Boolean getActive() {
        return active;
    }

    public void setFullName(String fullName) {
        this.fullName = fullName;
    }

    public void setEmail(String email) {
        this.email = email;
    }

    public void setActive(Boolean active) {
        this.active = active;
    }
}
```

Repository:

```java
package com.example.demo.employee;

import org.springframework.data.jpa.repository.JpaRepository;

public interface EmployeeRepository
        extends JpaRepository<Employee, Long> {
}
```

`JpaRepository` inherits Query by Example capabilities, so the repository can use methods such as `findAll(Example<S>)`, `findOne(Example<S>)`, `count(Example<S>)`, `exists(Example<S>)`, and overloads accepting Sort or Pageable.

Creating a probe and Example:

```java
Employee probe = new Employee();
probe.setFullName("An");
probe.setActive(true);

Example<Employee> example = Example.of(probe);
```

Here email is not set, so it is null and ignored by default. The query will search for Employees whose fullName matches `An` and active matches `true` under the default matcher.

Note: a probe is just an object describing search criteria. Do not call `save(probe)` and do not persist the probe to the database.

## 3. ExampleMatcher and matching modes

`ExampleMatcher` specifies how properties in the probe are processed. You can create a matcher with:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll();
```

Or:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAny();
```

### 3.1. matchingAll: all conditions must match

`matchingAll()` applies AND between properties included in the probe.

Example probe with fullName and active:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll();

Example<Employee> example = Example.of(probe, matcher);
```

Meaning:

```sql
WHERE full_name = ?
  AND active = ?
```

This is usually the right choice for search forms with multiple filters: every field the user fills in narrows down the result set.

### 3.2. matchingAny: only one condition needs to match

`matchingAny()` creates OR logic across properties included in the probe:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAny();

Example<Employee> example = Example.of(probe, matcher);
```

Meaning:

```sql
WHERE full_name = ?
   OR email = ?
   OR active = ?
```

Only properties considered populated according to matcher settings participate. Use matchingAny when business logic genuinely wants to return records if any one criterion matches.

Do not confuse matchingAny with building complex condition groups. QBE cannot freely express patterns like:

```sql
WHERE active = true
  AND (full_name LIKE ? OR email LIKE ?)
```

`matchingAny()` ORs all criteria included in the probe; it does not let you group a few OR conditions inside another AND group. For logic like that, use Specification, Querydsl, or JPQL.

### 3.3. Default behavior

If you use `Example.of(probe)` without passing a matcher:

- Null values are ignored by default.
- Strings are matched exactly (exact).
- Strings are case-sensitive by default.
- Other non-null properties are compared according to their respective types.

To make code express intent clearly, you can write `matchingAll().withIgnoreNullValues()` instead of relying on implicit defaults.

## 4. Creating matchers for string fields

Search forms often need to find names by partial string rather than whole exact match. `ExampleMatcher` supports several string matching modes:

| Mode | Meaning | Example probe |
|---|---|---|
| `EXACT` | Exact equality | `An` |
| `STARTING` | Starts with | `An` |
| `ENDING` | Ends with | `An` |
| `CONTAINING` | Contains substring | `An` |

Example:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreNullValues()
        .withStringMatcher(ExampleMatcher.StringMatcher.CONTAINING)
        .withIgnoreCase();
```

This configuration applies substring containment and case-insensitivity to all String properties included in the probe. If only some fields need substring search, configure each property individually to avoid changing semantics for email or identifier codes.

### 4.1. Per-property matchers

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreNullValues()
        .withMatcher(
                "fullName",
                match -> match.contains().ignoreCase()
        )
        .withMatcher(
                "email",
                match -> match.exact().ignoreCase()
        );
```

In the example:

- `fullName` searches by substring and ignores case.
- `email` searches by exact match and ignores case.
- Other properties keep the default rules.
- Null values are ignored.

The name in `withMatcher` is the entity property path, not the SQL column name. For example, if the entity has `fullName` mapped to column `full_name`, the matcher still uses `fullName`.

### 4.2. Case sensitivity

You can set case-insensitivity for all Strings:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreCase();
```

Or only a few properties:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreCase("fullName", "email");
```

The provider/database may translate conditions into uppercase or lowercase normalization expressions. Unicode comparison and collation depend on the database. If the application has specific requirements around Vietnamese diacritics, collation, or locale, test against the target database.

### 4.3. Do not apply one string mode to all fields mechanically

If you apply `CONTAINING` globally, email, employee codes, and other strings will also be searched via substring containment. This may violate business expectations and prevent queries from using regular indexes effectively.

Set matchers per property:

- Name: CONTAINING or STARTING.
- Email: EXACT, optionally ignoreCase.
- Employee code: EXACT.
- Description keywords: CONTAINING if business rules allow.

Choose semantics first, then choose the matcher.

## 5. Building QBE from a search form

Do not accept an entire entity directly from a request as a probe. Create a dedicated DTO containing only the fields the form is allowed to search on:

```java
package com.example.demo.employee;

public record EmployeeSearchForm(
        String name,
        String email,
        Boolean active
) {
}
```

Use the `Boolean` wrapper to distinguish three states:

- `true`: find only active employees.
- `false`: find only inactive employees.
- `null`: do not apply a status condition.

If you use primitive `boolean`, the default value is false; QBE may interpret false as a matching criterion even when the user did not select a status. This is a common bug with probes that have primitive fields.

Building the probe:

```java
private Employee toProbe(EmployeeSearchForm form) {
    Employee probe = new Employee();

    probe.setFullName(blankToNull(form.name()));
    probe.setEmail(blankToNull(form.email()));
    probe.setActive(form.active());

    return probe;
}

private String blankToNull(String value) {
    if (value == null || value.isBlank()) {
        return null;
    }

    return value.trim();
}
```

Converting blank strings to null ensures those fields are ignored under default null handling. If an empty string is left as-is, QBE may generate a condition searching for an empty string instead of skipping the filter.

Creating the Example:

```java
private Example<Employee> toExample(EmployeeSearchForm form) {
    Employee probe = toProbe(form);

    ExampleMatcher matcher = ExampleMatcher.matchingAll()
            .withIgnoreNullValues()
            .withMatcher(
                    "fullName",
                    match -> match.contains().ignoreCase()
            )
            .withMatcher(
                    "email",
                    match -> match.exact().ignoreCase()
            );

    return Example.of(probe, matcher);
}
```

## 6. Repository methods with QBE

The service can use Example to fetch a list:

```java
@Service
public class EmployeeSearchService {

    private final EmployeeRepository repository;

    public EmployeeSearchService(EmployeeRepository repository) {
        this.repository = repository;
    }

    public List<Employee> search(EmployeeSearchForm form) {
        Example<Employee> example = toExample(form);
        return repository.findAll(example);
    }

    private Example<Employee> toExample(EmployeeSearchForm form) {
        Employee probe = new Employee();
        probe.setFullName(blankToNull(form.name()));
        probe.setEmail(blankToNull(form.email()));
        probe.setActive(form.active());

        ExampleMatcher matcher = ExampleMatcher.matchingAll()
                .withIgnoreNullValues()
                .withMatcher(
                        "fullName",
                        match -> match.contains().ignoreCase()
                )
                .withMatcher(
                        "email",
                        match -> match.exact().ignoreCase()
                );

        return Example.of(probe, matcher);
    }

    private String blankToNull(String value) {
        if (value == null || value.isBlank()) {
            return null;
        }
        return value.trim();
    }
}
```

Available QBE methods:

```java
repository.findAll(example);
repository.findAll(example, Sort.by("fullName"));
repository.findAll(example, pageable);
repository.findOne(example);
repository.count(example);
repository.exists(example);
```

`findOne` is appropriate when at most one result is expected. If multiple rows match, Spring Data can throw `IncorrectResultSizeDataAccessException`; do not use it as an arbitrary way to fetch a single first row.

## 7. Combining QBE with pagination and sorting

For search forms that can return many results, bound data using `Pageable`:

```java
public Page<Employee> search(
        EmployeeSearchForm form,
        Pageable pageable
) {
    Example<Employee> example = toExample(form);
    return repository.findAll(example, pageable);
}
```

Calling the service:

```java
Pageable pageable = PageRequest.of(
        0,
        20,
        Sort.by(
                Sort.Order.asc("fullName"),
                Sort.Order.asc("id")
        )
);

Page<Employee> page = searchService.search(form, pageable);
```

Sort uses Java properties of the entity. Adding ID as the final criterion makes ordering deterministic when multiple employees share the same name.

You can use `Slice` or window/scrolling queries in suitable designs, though check the specific API/version. For standard QBE, overloads accepting Pageable and Sort are straightforward and easy to use.

### 7.1. Page and count queries

`Page<T>` provides total elements and total pages. Therefore, Spring Data may need to execute an additional count query.

If the UI only needs to know whether more data follows, consider Slice or an appropriate scrolling mechanism to avoid the cost of total counting. Choose based on UX requirements; Page is not always necessary.

## 8. Ignoring properties that do not participate in search

Probes are usually created from entities and may hold more fields than the form. Ignore properties that are not search criteria:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreNullValues()
        .withIgnorePaths(
                "id",
                "createdAt",
                "updatedAt",
                "version"
        );
```

Null fields are already ignored normally, but `withIgnorePaths` makes explicit which properties must never be used as conditions. This helps when probes have default values or when entities have technical fields.

### 8.1. Primitive fields with default values

Primitives such as `boolean`, `int`, and `long` cannot be null. A newly created probe will have default values like false or 0. QBE may treat those values as search conditions.

Example entity:

```java
private boolean active;
private int level;
```

A new probe will have active as false and level as 0. Even if the form lacks these two filters, the query can still accidentally add corresponding conditions.

How to handle:

- Use wrappers `Boolean`, `Integer`, `Long` for properties that may be omitted from the probe.
- Or add primitive fields to `withIgnorePaths` when the filter is not selected.
- You can build matchers dynamically from form state, but make sure to test cases where false/0 is a value the user genuinely wants to search for.

Do not convert false to null if false is a valid search criterion.

## 9. Nested properties and associations

QBE can work with certain nested property paths through the probe's object graph. For example, Employee has a to-one relationship to Department:

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;
```

If the form has departmentName, you can create a Department probe:

```java
Department departmentProbe = new Department();
departmentProbe.setName(blankToNull(form.departmentName()));

Employee employeeProbe = new Employee();
employeeProbe.setDepartment(departmentProbe);
```

The matcher can reference the path:

```java
ExampleMatcher matcher = ExampleMatcher.matchingAll()
        .withIgnoreNullValues()
        .withMatcher(
                "department.name",
                match -> match.contains().ignoreCase()
        );
```

Association paths can cause the JPA provider to generate a JOIN. Inspect the actual SQL and query count; do not assume nested properties are always cheap or avoid joins.

QBE does not support matching collections/maps as regular probe criteria. If you need to find Employees having at least one Order matching a condition, or need conditions on collection associations, use JPQL, Specification, or Querydsl.

## 10. Null handling and form semantics

By default, null values are ignored. If you want to change semantics, define the business meaning clearly:

| Form value | Common handling |
|---|---|
| Null | Ignore filter |
| Empty string | Normalize to null if the form treats it as unentered |
| Whitespace string | Trim before creating the probe |
| Boolean false | Keep false if the user selected "inactive" |
| Number 0 | Keep 0 if it is a valid criterion |
| Null date | Ignore date filter; QBE does not create date ranges automatically |

QBE normally ignores nulls in probes. If you need to find rows with null columns, QBE can be configured to include null values via the matcher, but including nulls in the probe applies to selected properties per matcher rules and may not suit a multi-filter form. Use this intentionally and test it.

If a form needs to distinguish "not entered" from "search for null field", represent that state separately in the DTO; a single null value cannot express both meanings.

## 11. Limitations of Query by Example

QBE has a simple interface, but it is not a general-purpose query builder.

Important limitations:

- Does not support arbitrary condition groups such as `(A AND B) OR (C AND D)`.
- `matchingAny()` only ORs selected properties; it cannot build nested logic groups.
- Not suitable for comparison conditions like greater-than, less-than, BETWEEN, or date range calculations.
- Does not support matching collections/maps in the usual probe style.
- Does not replace complex JOIN, subquery, or aggregate queries.
- StringMatcher modes and store behavior have their own limits; do not assume every mode like regex is portably supported by JPA.
- Not the best fit when queries require complex security/tenant conditions combined with server-controlled filters.

For example, a requirement to find employees created within a date range:

```sql
WHERE created_at >= :from
  AND created_at < :to
```

QBE has no standard matcher to express this range. Use Specification or JPQL:

```java
@Query("""
       select e
       from Employee e
       where e.createdAt >= :from
         and e.createdAt < :to
       """)
List<Employee> findCreatedBetween(
        @Param("from") Instant from,
        @Param("to") Instant to
);
```

## 12. When to choose QBE, Specification, Querydsl, or @Query?

| Tool | Best suited when | Limitations/considerations |
|---|---|---|
| Query by Example | Simple search form, many optional fields, mainly exact/LIKE conditions | Cannot express complex logic groups and ranges |
| Specification | Dynamic filters, AND/OR, ranges, joins, and conditional predicates | Requires writing predicates using Criteria API |
| Querydsl | Typed dynamic queries with many conditions and expressions | Requires annotation processing/dependency setup |
| @Query | Clear, fixed queries with specific JPQL/native SQL | Query must be maintained alongside the method |
| Derived query | Simple conditions clearly expressed by method name | Method names get long with many conditions |

A quick selection rule:

- Form with optional name, email, active and simple matching conditions: QBE.
- Form with date ranges, greater-than/less-than values, or separate OR groups: Specification/Querydsl.
- Reports with clear JOIN, GROUP BY, aggregates: @Query or custom repository.
- Fixed query easily expressed as a method name: derived query.

Do not use QBE just because the repository supports it. Choose the tool that expresses the business logic most accurately and is easiest to test.

## 13. Security and access control when building probes

Do not bind an entire request directly into an entity probe. An entity can contain fields like tenantId, role, salary, internalStatus, or audit data that users must not be allowed to control in queries.

You should:

1. Create a search DTO containing only publicly allowed filters.
2. Manually map permitted fields from the DTO to the probe.
3. Add tenant/authorization conditions from server-side authentication context.
4. Never let clients dictate the tenant or accessible data scope.
5. Cap page size and restrict sort fields.

For example, if every query must be scoped to the current tenant, never take tenantId directly from the form. Obtain tenantId from the security context and ensure that condition is always enforced. Plain QBE may not suffice to combine a mandatory complex condition with optional filters; in that case, use Specification or a query service with dedicated security predicates.

QBE uses bind parameters through Spring Data/JPA's query mechanism, but that does not replace authorization and validation.

## 14. Performance and generated SQL

QBE reduces query-building boilerplate, but performance still depends on the final SQL.

Points to check:

- `CONTAINING` typically generates LIKE conditions with a leading wildcard; standard B-tree indexes may not help effectively.
- Ignore case can cause the database to apply LOWER/UPPER or collation mechanisms; functional indexes or matching collations may be necessary.
- Nested associations can generate JOINs.
- matchingAny can create multiple OR branches, making index usage harder.
- Page can trigger a count query.
- Probes with unnecessary populated fields can add unintended filter conditions.

Enable SQL logging in development or use datasource metrics to inspect SQL statements and bind parameters. Run EXPLAIN/EXPLAIN ANALYZE on the target database to confirm indexes and execution plans. Do not conclude QBE is faster than Specification or @Query merely from line count.

## 15. Testing Query by Example

Example repository test:

```java
@DataJpaTest
class EmployeeQueryByExampleTest {

    @Autowired
    private EmployeeRepository repository;

    @Test
    void findsEmployeesByPartialNameAndStatus() {
        repository.save(new Employee(
                "An Nguyen",
                "an@example.com",
                true
        ));

        repository.save(new Employee(
                "Binh Tran",
                "binh@example.com",
                true
        ));

        repository.save(new Employee(
                "An inactive",
                "inactive@example.com",
                false
        ));

        Employee probe = new Employee();
        probe.setFullName("an");
        probe.setActive(true);

        ExampleMatcher matcher = ExampleMatcher.matchingAll()
                .withIgnoreNullValues()
                .withMatcher(
                        "fullName",
                        match -> match.contains().ignoreCase()
                );

        Example<Employee> example = Example.of(probe, matcher);

        List<Employee> result = repository.findAll(example);

        assertThat(result)
                .extracting(Employee::getEmail)
                .containsExactlyInAnyOrder(
                        "an@example.com"
                );
    }
}
```

The test assumes Employee has the constructors/getters/setters from the example and that JUnit 5, AssertJ, and Spring Boot JPA test support dependencies are configured. `@DataJpaTest` normally runs inside a transaction and rolls back after each test.

Also test:

- Probe with all fields null.
- Empty strings and whitespace-only strings.
- exact, startsWith, and contains.
- ignoreCase with mixed-case data.
- Boolean false preserved as a condition.
- Primitive fields not accidentally entering the query.
- matchingAll and matchingAny.
- Nested associations if used by the application.
- Page/Sort and ordering when values collide.
- Server-enforced tenant/authorization filters.

If the probe is empty, Example may generate no useful filter criteria and return the entire dataset. For search forms, decide explicitly whether unconditional search is allowed or at least one filter is required before calling the repository.

## 16. Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| Form left empty but query searches for empty strings | Blank strings not normalized to null | Trim and convert blank strings to null |
| Wanted active=true only but got no results | Probe has primitive default false | Use Boolean wrapper or ignorePaths |
| Case-insensitive name search misses results | ignoreCase not configured or collation differs | Configure matcher and test on target database |
| matchingAny returns too many rows | All fields are ORed together | Use matchingAll or Specification to group conditions |
| Cannot create date range | QBE does not support range operators | Use Specification or @Query |
| Collection association is not matched | QBE does not support collection/map probe matching | Use JOIN with Specification/Querydsl/JPQL |
| findOne throws exception | Multiple rows match the Example | Use List/Page or ensure unique conditions |
| Query slow with contains | LIKE has leading wildcard | Inspect execution plan and pick a suitable search strategy |
| User can filter on internal fields | Bound entity directly from request | Use search DTO and allowlist mapping |
| Empty probe returns all data | Did not check filter count before querying | Define empty-form behavior explicitly |

## 17. Checklist for choosing Query by Example

- [ ] Form has optional filters with simple semantics.
- [ ] Dedicated search DTO used; entity is not bound directly from the request.
- [ ] Probe contains only permitted searchable fields.
- [ ] Choose matchingAll or matchingAny according to the exact logic.
- [ ] Configure per-property matchers for strings where needed.
- [ ] Trim and normalize empty strings.
- [ ] Use wrappers for optional filters instead of primitive defaults.
- [ ] Ignore ID, audit, and technical fields that do not participate in search.
- [ ] Check nested associations and avoid collection matching.
- [ ] Use Pageable/Sort and cap page sizes.
- [ ] Do not use QBE for ranges, logic groups, or complex queries.
- [ ] Enforce tenant/authorization filters from the server.
- [ ] Test empty probes, nulls, false, special strings, and the target database.
- [ ] Inspect SQL and execution plans when queries have performance requirements.

## Conclusion

Query by Example fits simple search forms with many optional fields. The application builds a probe from a DTO, chooses `ExampleMatcher` to specify exact/contains/case-insensitive rules, and creates an `Example` for the repository to execute. Nulls are normally ignored; matchingAll produces AND and matchingAny produces OR across selected criteria.

QBE cuts down query code for basic filters, though it does not replace a general-purpose query tool. For ranges, complex condition groups, collection associations, or mandatory security filters, use Specification, Querydsl, or JPQL. Populate probes from permitted fields, handle primitive defaults carefully, and inspect generated SQL so search forms remain accurate and maintainable.
