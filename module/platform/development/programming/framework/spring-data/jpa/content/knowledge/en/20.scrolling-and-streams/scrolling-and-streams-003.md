# Comparing Offset Scrolling and Keyset Scrolling

## Objectives

After this lesson, you will be able to:

- Explain how offset scrolling and keyset scrolling differ in determining the next position.
- Choose the appropriate strategy for UI pagination, large dataset traversal, and exports.
- Use `Window<T>`, `ScrollPosition`, and `WindowIterator` in Spring Data.
- Design stable sort orders and indexes supporting keyset scrolling.
- Recognize the impact of large offsets, concurrently changing data, and nullable sort properties.
- Test multi-window traversal without unexpectedly skipping or duplicating records.

## 1. What Problem Does Scrolling Solve?

A query may return hundreds of thousands or millions of records. Loading everything into a single `List` can consume excessive memory, increase response times, and put pressure on the database.

Scrolling divides results into small windows. The application processes one window and then requests the next window using a continuation position (scroll position).

In Spring Data, the Scroll API uses these core types:

- `Window<T>`: a bounded group of results, along with the ability to indicate whether more data follows.
- `ScrollPosition`: the position used to continue querying.
- `WindowIterator<T>`: an iterator that automatically calls the repository method with the next position to traverse windows.

The two common positioning strategies are:

- **Offset scrolling**: skip a number of records counted from the start of the result set.
- **Keyset scrolling**: continue after the sort key values of the last-read record.

Both help process data in chunks. The difference lies in how the database locates the next portion and which workloads each approach suits best.

## 2. Offset Scrolling

Offset scrolling specifies the position by the number of records to skip. For example, fetching 100 rows after the first 50,000 rows:

~~~sql
SELECT id, created_at, status
FROM orders
WHERE status = 'PAID'
ORDER BY created_at ASC, id ASC
LIMIT 100 OFFSET 50000;
~~~

The actual SQL syntax may vary by database and dialect. The general behavior is that the database must determine the result order, skip the first 50,000 rows, and then return the next 100 rows.

### Advantages

- Easy to understand because the position is a number.
- Can jump to a specific offset or page.
- Suitable for screens requiring navigation to page numbers 1, 2, 3...
- Does not require storing the sort column values of the last record.
- Usable with many sort styles, provided the query has a suitable ordering.

### Limitations

When the offset is large, the database typically has to traverse or identify many rows before returning the desired slice. Cost can increase with page depth, especially when the query must sort or join across a large dataset.

Offset is also sensitive to data changes between calls. Suppose the first page returned 100 rows. Before fetching offset 100, a new record is inserted before that position. Rows shift; the next call may repeat an already-seen row. If a record is deleted, the application may skip a row.

Therefore, offset pagination does not automatically guarantee a consistent single-pass traversal when data changes continuously.

## 3. Keyset Scrolling

Keyset scrolling uses the values of the sort columns from the last-read record to determine the next position. Instead of saying "skip 50,000 rows", the application says "fetch rows that come after these sort keys".

Suppose the order is:

~~~sql
ORDER BY created_at ASC, id ASC
~~~

After reading the last record with:

~~~text
created_at = 2026-10-01T10:30:00Z
id = 850
~~~

The next query can be logically expressed as follows:

~~~sql
SELECT id, created_at, status
FROM orders
WHERE status = 'PAID'
  AND (
       created_at > :lastCreatedAt
       OR (created_at = :lastCreatedAt AND id > :lastId)
  )
ORDER BY created_at ASC, id ASC
LIMIT 100;
~~~

This expresses the keyset condition for ascending order; the SQL generated by the provider may use different structures depending on the database. For descending order or mixed ASC/DESC sorting, comparison operators must match each direction.

### Advantages

- Avoids skipping a large number of records before the cursor.
- Performance is typically more stable during deep traversal when proper indexes exist.
- Less prone to position drift from inserts/deletes ahead of the cursor.
- Well suited for exports, batch processing, feeds, and ordered traversal of large datasets.

### Limitations

- Cannot jump directly to an arbitrary page number without already having the keyset position for that page.
- Requires a stable and uniquely deterministic sort order.
- Sort properties must be selected in projections and must satisfy keyset requirements.
- Nullable sort properties make comparison order hard to define; Spring Data keyset scrolling requires non-null keyset properties.
- If a sort value changes during traversal, a record can move across the cursor position.
- Does not automatically create a consistent snapshot of the entire dataset.

## 4. Why Must There Be a Unique Ordering?

If sorting only by `createdAt`, multiple orders may share the same timestamp. In that case, the position after the last timestamp is insufficient to pinpoint the next record accurately.

Add a unique property as a tie-breaker, usually the primary key:

~~~sql
ORDER BY created_at ASC, id ASC
~~~

This ordering establishes a total order if `id` is unique. The keyset position will hold the required sort values, such as `createdAt` and `id`.

Practical rules:

1. Choose sort properties suited to the use case.
2. Add a unique key at the end to distinguish rows sharing the same sort value.
3. Keep the sort order fixed throughout the scrolling process.
4. Ensure keyset properties are non-null.
5. If using projections, return all sort properties and the unique key.

If you change the sort between two calls, the old keyset position may no longer correspond to the new query. Never use a cursor created from one sort order to continue a query with a different order.

## 5. Direct Comparison

| Criterion | Offset scrolling | Keyset scrolling |
|---|---|---|
| Continuation position | Number of skipped rows | Sort column values of the last row |
| Deep querying | Can incur high cost from traversing many rows | Usually more efficient with suitable indexes |
| Jump to arbitrary page | Convenient | Inconvenient without an existing cursor |
| Sort order | Needs stable sort to avoid unpredictable results | Must be stable with a unique tie-breaker |
| Nullable properties | Usable depending on query/database | Keyset properties must be non-null |
| Data changes between calls | Inserts/deletes before offset easily cause duplicates or skips | Less shifted by changes before cursor, but not a snapshot |
| Projection | More flexible regarding sort keys | Must include keyset/sort properties |
| Suitable use cases | Numbered-page UI, moderately sized datasets | Exports, feeds, batches, and large dataset traversal |

Neither strategy is superior in every case. Choose based on how users navigate, data size, concurrent write rate, and indexing possibilities.

## 6. Using the Scroll API in Spring Data

Spring Data provides `Window<T>` and `ScrollPosition` in the Scroll API. This API has been available since Spring Data 3.1; verify the Spring Data version managed by your Spring Boot BOM before adopting it.

A repository method can return a window:

~~~java
import org.springframework.data.domain.ScrollPosition;
import org.springframework.data.domain.Window;
import org.springframework.data.jpa.repository.JpaRepository;

public interface OrderRepository
        extends JpaRepository<Order, Long> {

    Window<Order> findFirst100ByStatusOrderByCreatedAtAscIdAsc(
        OrderStatus status,
        ScrollPosition position
    );
}
~~~

The method above:

- Filters by `status`.
- Fetches up to 100 results in a single window.
- Sorts by `createdAt` ascending then `id` ascending.
- Accepts `ScrollPosition` to determine the starting position.

`Window` differs from `Page`: it does not provide total row counts or total page counts. It focuses on continuing result traversal. You can check `window.hasNext()` to know whether a subsequent window exists.

## 7. Starting Offset Scrolling

Use the initial offset position:

~~~java
ScrollPosition position = ScrollPosition.offset();

Window<Order> window =
    orderRepository.findFirst100ByStatusOrderByCreatedAtAscIdAsc(
        OrderStatus.PAID,
        position
    );
~~~

`ScrollPosition.offset()` represents the initial position before the first element. Because scroll positions have exclusive semantics, do not confuse it with `ScrollPosition.offset(0)`, which represents the position of the element at offset 0.

After processing the window, you can obtain the position at the last element to continue:

~~~java
if (window.hasNext() && !window.isEmpty()) {
    ScrollPosition nextPosition =
        window.positionAt(window.size() - 1);

    Window<Order> nextWindow =
        orderRepository.findFirst100ByStatusOrderByCreatedAtAscIdAsc(
            OrderStatus.PAID,
            nextPosition
        );
}
~~~

The position obtained from the last element lets the query resume after that element. In real code, you must keep the same predicate and sort across calls.

## 8. Starting Keyset Scrolling

Use the initial keyset position:

~~~java
ScrollPosition position = ScrollPosition.keyset();

Window<Order> firstWindow =
    orderRepository.findFirst100ByStatusOrderByCreatedAtAscIdAsc(
        OrderStatus.PAID,
        position
    );
~~~

On the first call, there are no cursor values yet, so Spring Data fetches from the beginning of the result set. Subsequent windows use keyset positions based on the sort values of the last element in the previous window.

Do not manually create an offset and pass it to the query expecting it to become a keyset position. The ScrollPosition type determines which scrolling strategy is used.

## 9. Continuous Traversal with WindowIterator

If you need to process the entire result set, `WindowIterator` avoids writing manual position-management loops.

Keyset scrolling example:

~~~java
import org.springframework.data.domain.ScrollPosition;
import org.springframework.data.support.WindowIterator;

WindowIterator<Order> iterator = WindowIterator
    .of(position ->
        orderRepository.findFirst100ByStatusOrderByCreatedAtAscIdAsc(
            OrderStatus.PAID,
            position
        )
    )
    .startingAt(ScrollPosition.keyset());

while (iterator.hasNext()) {
    Order order = iterator.next();
    process(order);
}
~~~

To use offset scrolling, change the starting position:

~~~java
WindowIterator<Order> iterator = WindowIterator
    .of(position ->
        orderRepository.findFirst100ByStatusOrderByCreatedAtAscIdAsc(
            OrderStatus.PAID,
            position
        )
    )
    .startingAt(ScrollPosition.offset());
~~~

The iterator automatically requests the next window as needed. The application processes one element at a time instead of loading all results into memory.

If the goal is exporting a large file, do not collect all entities into a List before writing to the file. Process element by element or window by window, release unneeded references, and monitor query duration.

The example above is a fragment to be placed in a service/repository with corresponding dependencies; `process(order)` is an application business operation, not a Spring Data API.

## 10. Index Design for Keyset

Keyset is effective when the database has an index matching the filter conditions and sort order.

For the query:

~~~sql
WHERE status = ?
ORDER BY created_at ASC, id ASC
~~~

A suitable index might be:

~~~sql
CREATE INDEX idx_orders_status_created_id
    ON orders(status, created_at, id);
~~~

Column order in the index matters:

- `status` comes first because it is an equality predicate.
- `created_at` and `id` follow the sort and cursor order.
- The index helps the database locate elements after the keyset faster without scanning/skipping tens of thousands of rows.

The specific index must be verified using the target database's execution plan. If the predicate has additional conditions, different sorting, or skewed data distribution, this index may not yet be optimal.

Do not create indexes for arbitrary sort combinations. Indexes increase insert/update costs and storage footprint. Base index decisions on real queries and workloads.

## 11. Projections When Using Keyset

If the repository returns entities, sort properties are usually available. If using DTO or interface projections, the result must contain all properties required to construct the keyset position.

Projection example:

~~~java
public interface OrderScrollView {
    Long getId();
    Instant getCreatedAt();
    BigDecimal getTotalAmount();
}
~~~

Repository:

~~~java
Window<OrderScrollView> findFirst100ByStatusOrderByCreatedAtAscIdAsc(
    OrderStatus status,
    ScrollPosition position
);
~~~

The projection must include `id` and `createdAt` because both participate in sorting. If it only returns `totalAmount` and omits the sort properties, Spring Data will not have enough values to construct the keyset position.

With custom projections, verify both property names and data types. Do not only inspect displayed data; keyset also needs the sort key metadata.

## 12. Data Changing During Scrolling

Scrolling across multiple calls does not typically equate to a single snapshot transaction.

### Offset and Data Changes

Suppose the first window fetches rows 1–100. A new row is inserted at a position before row 100. When calling offset 100, the boundary has shifted; you may receive the old row 100 again or skip a row depending on order and commit timing.

Deleting a row before the offset likewise shifts subsequent rows in the opposite direction.

### Keyset and Data Changes

Keyset continues after the last sort value. A new record with a sort key less than or equal to the cursor generally sits ahead of the current position and will not appear in the remainder. A new record with a sort key greater than the cursor may appear in a later window.

If an existing record has its `createdAt` updated so it moves from behind the cursor to ahead of it or vice versa, it may be skipped or appear at a different position. Therefore, sort properties should be immutable during traversal if predictable results are needed.

Keyset reduces the impact of offset drift, but does not guarantee snapshot consistency.

### When Consistent Exports Are Needed

If the business requirement is to export an exact dataset at a point in time:

- Define snapshot semantics and the isolation level supported by the database.
- Consider an appropriate snapshot transaction, or lock in a data cutoff such as `createdAt <= exportStartedAt`.
- Use fixed filter predicates and immutable sort keys.
- If necessary, persist the list of dataset IDs prior to processing.
- Evaluate transaction duration and its impact on the connection pool, MVCC/version store, and database vacuuming.

Do not keep transactions open for hours solely to maintain a snapshot if the database is not designed for that workload. You may need a batch export workflow with a data cutoff or staging table.

## 13. When to Use Page, Slice, Window, or Stream?

| Type | Purpose | Total count | Continuation mechanism |
|---|---|---:|---|
| `Page<T>` | UI needs total pages and page-based navigation | Yes, usually needs count query | Pageable/page number |
| `Slice<T>` | UI only needs to know if there is a next page | No total count needed | Pageable |
| `Window<T>` | Sequential traversal by scroll position | No | ScrollPosition |
| `Stream<T>` | Stream-based result processing if provider/driver supports it | No | Stream/cursor depending on implementation |

`Page` is convenient for numbered-page UIs, though the count query can be expensive. `Slice` avoids the total count when only a "load more" button is needed. `Window` fits offset or keyset scrolling. `Stream` can hold database resources while open; streams must be closed and transactions managed properly.

Do not mistake WindowIterator for a JDBC server cursor. It traverses windows via multiple queries, each using a continuation position.

## 14. Limitations and Compatibility Requirements

The Scroll API belongs to Spring Data Commons and is integrated into corresponding Spring Data releases. Before using it:

- Check the Spring Data JPA version managed by your Spring Boot BOM.
- Confirm repository methods support the `Window<T>` return type and `ScrollPosition` parameter.
- Check the query type. Scrolling support for derived queries, Specifications, Querydsl, and string-based `@Query` can vary by release; the documentation for your exact version is the authoritative source.
- For native queries, explicitly verify provider and Spring Data JPA support; do not assume all native queries support keyset.
- Verify database dialects and generated SQL in test environments.

If your project version does not yet support the Scroll API, you can use `Pageable`/`Slice` for offset pagination or write custom keyset queries with explicit seek predicates, sorting, and limits. When writing queries manually, handle tie-breakers and sort directions carefully.

## 15. Common Pitfalls

| Symptom | Cause | Resolution |
|---|---|---|
| Deep pages progressively slow down | Large offset forces database to skip many rows | Use keyset if the use case is sequential traversal |
| Duplicates or missing results on inserts/deletes | Offset shifts with row positions | Use keyset and define concurrent data semantics |
| Keyset fails to build cursor | Projection missing sort key or keyset property is null | Return all sort properties and ensure non-null |
| Records with same timestamp skipped/unstable | Sort lacks a unique tie-breaker | Add primary key at the end of sort |
| Next window at wrong position | Wrong ScrollPosition used or sort changed mid-way | Keep same predicate/sort and use position from previous window |
| Cannot jump to arbitrary page | Keyset only knows current cursor | Use offset/Pageable if random page navigation is required |
| Total pages unavailable | Window does not perform total count like Page | Use Page if total count is needed; weigh count cost |
| Export data changes across windows | Multiple queries are not a single snapshot | Choose appropriate isolation or data cutoff |
| Keyset query not utilizing index | Index does not match filters and sort | Inspect execution plan, design index around predicate/sort |
| @Query does not support scrolling in current version | API limitation of the Spring Data JPA release | Use derived query method or verify support for exact version |

## 16. Strategy Selection Process

1. Determine whether users need to jump to arbitrary page numbers or only traverse forward.
2. If total pages are needed, consider `Page`; if only knowing whether more data remains is needed, consider `Slice`.
3. If sequentially traversing a large dataset, evaluate keyset scrolling.
4. Choose a stable sort and add a unique key as a tie-breaker.
5. For keyset, ensure sort keys are non-null and projections include all those keys.
6. Design indexes with filter prefixes followed by sort keys; verify with execution plans.
7. Define how data is allowed to change during scrolling.
8. Verify Scroll API support in your Spring Data JPA version and database dialect.
9. Measure performance at production-like scale and verify no unexpected duplicates/skips outside chosen semantics.

- [ ] Page/Slice/Window chosen appropriately for total count and continuation needs.
- [ ] Repository method uses version-compatible Window and ScrollPosition.
- [ ] Sort has a deterministic order and a unique tie-breaker.
- [ ] Keyset sort properties are non-null.
- [ ] Projections contain all sort/keyset properties.
- [ ] Indexes matching filters and sorting have been evaluated.

- [ ] Execution plans and performance verified on the target database.

## Conclusion

Offset scrolling determines positions by the number of rows to skip; this is simple and supports jumping to pages, but can be slow at deep offsets and sensitive to inserts/deletes. Keyset scrolling continues after the sort values of the last row, typically proving more efficient when traversing large datasets with proper indexes. In exchange, keyset requires stable sorting, a unique key, non-null sort properties, and projections containing all keyset fields; it also does not automatically create a consistent snapshot. In Spring Data, use `Window<T>`, `ScrollPosition`, and `WindowIterator`, and choose offset or keyset based on user navigation patterns and data consistency requirements.
