# So sánh chiến lược sinh khóa AUTO, IDENTITY, SEQUENCE và TABLE

JPA cung cấp bốn chiến lược sinh khóa chính phổ biến qua annotation **@GeneratedValue**: **AUTO**, **IDENTITY**, **SEQUENCE** và **TABLE**. Chúng đều giúp ứng dụng nhận giá trị khóa cho entity mới, nhưng cách lấy giá trị, yêu cầu đối với database, khả năng batch insert và chi phí đồng thời rất khác nhau.

Không có chiến lược nào tốt nhất cho mọi hệ quản trị. Lựa chọn nên dựa trên database thực tế, JPA provider, tải ghi, yêu cầu hiệu năng và khả năng kiểm soát schema. Bài này dùng Spring Data JPA, Jakarta Persistence và Hibernate trong Spring Boot 3.x để so sánh.

## 1. @GeneratedValue giải quyết việc gì?

Một entity thường cần primary key để database phân biệt từng bản ghi. Nếu ứng dụng tự gán ID, mọi nơi tạo entity phải tự bảo đảm ID không trùng, kể cả khi nhiều instance chạy đồng thời. Cơ chế sinh khóa ở database/provider giúp phân phối giá trị an toàn hơn.

Ví dụ entity có khóa Long được sinh tự động:

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Customer() {
    }
}
```

**@Id** đánh dấu thuộc tính khóa chính. **@GeneratedValue** chỉ định cơ chế tạo giá trị khóa. Thuộc tính **strategy** chọn chiến lược; thuộc tính **generator** tham chiếu tên generator được khai báo bằng SequenceGenerator hoặc TableGenerator khi chiến lược cần cấu hình generator.

Các chiến lược áp dụng cho khóa chính đơn giản. Không nên dựa vào @GeneratedValue để tự sinh một phần của khóa ghép. Với khóa ghép, hãy thiết kế @EmbeddedId hoặc @IdClass và cơ chế gán khóa phù hợp.

ID kỹ thuật nên ổn định trong suốt vòng đời entity. Không dùng ID sinh tự động thay cho mã nghiệp vụ như số đơn hàng, số hóa đơn hoặc mã giao dịch có quy tắc riêng. Những mã đó có yêu cầu định dạng, phạm vi, tính duy nhất và đôi khi tính liên tục riêng.

## 2. So sánh nhanh bốn chiến lược

| Chiến lược | Nguồn cấp ID | Yêu cầu database | Đặc điểm chính |
|---|---|---|---|
| AUTO | Provider tự chọn chiến lược phù hợp | Tùy provider và dialect | Ít cấu hình, hành vi cụ thể phụ thuộc môi trường |
| IDENTITY | Cột identity/auto-increment của bảng | Database hỗ trợ identity column | ID có sau khi insert; Hibernate thường không batch insert các entity kiểu này |
| SEQUENCE | Database sequence | Database/provider hỗ trợ sequence | Có thể cấp trước một hoặc nhiều ID; thuận lợi cho batching |
| TABLE | Một bảng dùng để cấp số | Chỉ cần bảng và cơ chế khóa/cập nhật phù hợp | Tương đối portable nhưng có thêm thao tác và tranh chấp trên bảng generator |

### 2.1. AUTO

**AUTO** giao quyết định cho JPA provider. Với khóa kiểu Long, Hibernate chọn chiến lược theo dialect, phiên bản và cấu hình. Một database có sequence có thể được dùng sequence; database khác có thể dùng identity hoặc cơ chế phù hợp khác.

```java
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

Ưu điểm:

- Code ít phụ thuộc trực tiếp vào một chiến lược cụ thể.
- Provider có thể chọn cách phù hợp với database đang sử dụng.
- Thuận tiện cho ứng dụng đơn giản hoặc khi chấp nhận hành vi do provider quyết định.

Hạn chế:

- Không thể chỉ nhìn annotation để biết chính xác database sẽ dùng sequence, identity hay cơ chế nào.
- Khi đổi database hoặc Hibernate dialect, DDL và hành vi sinh ID có thể thay đổi.
- Khó dự đoán khả năng batching, cách cấp ID và số lần truy cập database nếu không kiểm tra cấu hình thực tế.

**AUTO không có nghĩa là luôn dùng auto-increment.** Nó có nghĩa là provider được quyền lựa chọn chiến lược. Nếu yêu cầu schema và hiệu năng cần dự đoán rõ, hãy cân nhắc chỉ định chiến lược tường minh.

### 2.2. IDENTITY

**IDENTITY** dùng cột identity/auto-increment do database cấp giá trị khi insert. Ví dụ PostgreSQL identity column hoặc MySQL AUTO_INCREMENT.

```java
@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    protected Customer() {
    }
}
```

Ví dụ DDL minh họa cho PostgreSQL:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);
```

Luồng tổng quát:

1. Ứng dụng tạo entity mới với ID chưa có.
2. Provider thực hiện INSERT vào database.
3. Database sinh ID.
4. Provider lấy ID được sinh và gán vào entity.

Do cần ID từ database sau insert, Hibernate thường phải thực thi insert sớm hơn so với một số chiến lược khác. Với Hibernate, identity-generated entity thường không thể dùng JDBC insert batching theo cách thông thường vì provider cần kết quả ID của từng insert. Đây là điểm cần cân nhắc ở hệ thống có lượng ghi lớn.

Ưu điểm:

- Mapping dễ hiểu và phổ biến.
- Nhiều database hỗ trợ identity/auto-increment trực tiếp.
- Không cần khai báo sequence hoặc bảng generator riêng.

Hạn chế:

- Insert phải dựa vào database để lấy ID.
- Hibernate thường không batch insert entity dùng IDENTITY, làm giảm throughput khi ghi nhiều bản ghi.
- Khó cấp ID trước khi insert, nên một số luồng xử lý graph entity hoặc batching không linh hoạt bằng sequence.

IDENTITY phù hợp với ứng dụng CRUD thông thường, số lượng insert vừa phải và database có identity column. Nếu có batch import hoặc ghi hàng loạt, hãy benchmark với workload thật trước khi chọn.

### 2.3. SEQUENCE

**SEQUENCE** sử dụng database sequence để cấp ID. Sequence là đối tượng database có khả năng tạo dãy số độc lập với một bảng cụ thể. Provider có thể lấy trước ID hoặc cấp cả một block ID theo allocation size.

```java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(
        strategy = GenerationType.SEQUENCE,
        generator = "purchaseOrderSequence"
    )
    @SequenceGenerator(
        name = "purchaseOrderSequence",
        sequenceName = "purchase_order_seq",
        initialValue = 1,
        allocationSize = 50
    )
    private Long id;

    @Column(name = "order_number", nullable = false, length = 40)
    private String orderNumber;

    protected PurchaseOrder() {
    }
}
```

Có ba tên cần phân biệt:

- **purchaseOrderSequence** trong thuộc tính name là tên generator trong metadata JPA.
- **purchase_order_seq** trong sequenceName là tên sequence vật lý trong database.
- **generator = "purchaseOrderSequence"** trong GeneratedValue tham chiếu tên generator, không tham chiếu trực tiếp sequenceName.

Ví dụ migration cho PostgreSQL khi sử dụng Hibernate với pooled allocation size 50:

```sql
CREATE SEQUENCE purchase_order_seq
    START WITH 1
    INCREMENT BY 50;
```

**Lưu ý:** allocationSize mô tả số ID provider có thể phân bổ trong một lần lấy sequence. Với Hibernate và pooled optimizer, cấu hình increment của database sequence cần tương thích với allocationSize; ví dụ trên minh họa trường hợp Hibernate dùng block size 50. Cơ chế tối ưu và quy tắc kiểm tra increment phụ thuộc provider/phiên bản. Khi dùng provider khác hoặc optimizer khác, hãy theo hướng dẫn của provider và xác minh bằng schema validation. Nếu muốn cấu hình đơn giản, allocationSize = 1 cùng sequence increment 1 dễ kiểm soát hơn nhưng ít tận dụng việc cấp block.

Ưu điểm:

- Có thể lấy ID trước khi insert entity.
- Provider có thể cấp một block ID rồi dùng dần, giảm số lần round trip tới database.
- Hibernate có thể batch insert thuận lợi hơn so với IDENTITY.
- Sequence độc lập với bảng dữ liệu, dễ tái sử dụng theo cấu hình có chủ đích.

Hạn chế:

- Database phải hỗ trợ sequence và dialect/provider phải hỗ trợ đúng.
- Cần đồng bộ cấu hình sequence, allocationSize và optimizer.
- Sequence có thể tạo khoảng trống khi transaction rollback, ứng dụng khởi động lại hoặc block ID đã cấp nhưng chưa dùng hết.

Sequence thường là lựa chọn tốt cho hệ thống ghi nhiều trên database hỗ trợ sequence, chẳng hạn PostgreSQL và Oracle. Với Hibernate, đây thường là lựa chọn đáng cân nhắc khi cần throughput insert tốt.

### 2.4. TABLE

**TABLE** dùng một bảng database để lưu bộ đếm ID. Provider đọc/cập nhật giá trị trong bảng generator rồi cấp ID cho entity. Cách này không phụ thuộc tính năng sequence hoặc identity chuyên biệt, nhưng cần database hỗ trợ transaction và khóa hàng phù hợp.

```java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(
        strategy = GenerationType.TABLE,
        generator = "purchaseOrderTableGenerator"
    )
    @TableGenerator(
        name = "purchaseOrderTableGenerator",
        table = "id_generator",
        pkColumnName = "generator_key",
        valueColumnName = "next_value",
        pkColumnValue = "purchase_order",
        allocationSize = 50
    )
    private Long id;

    @Column(name = "order_number", nullable = false, length = 40)
    private String orderNumber;

    protected PurchaseOrder() {
    }
}
```

Trong ví dụ:

- **purchaseOrderTableGenerator** là tên generator trong metadata JPA.
- **id_generator** là tên bảng generator vật lý.
- **generator_key** là cột phân biệt bộ đếm.
- **next_value** là cột lưu giá trị bộ đếm.
- **purchase_order** là giá trị khóa của dòng generator dành cho entity này.
- **allocationSize = 50** cho phép provider cấp trước một block ID theo cấu hình generator.

Bảng generator phải được tạo và khởi tạo đúng với quy tắc mà provider sử dụng. Một cấu trúc minh họa:

```sql
CREATE TABLE id_generator (
    generator_key VARCHAR(100) PRIMARY KEY,
    next_value BIGINT NOT NULL
);
```

Cần tạo dòng generator có khóa **purchase_order** và giá trị khởi tạo phù hợp với provider/DDL strategy. Không đoán giá trị counter ban đầu hoặc cập nhật nó thủ công khi ứng dụng đang chạy. Hãy kiểm tra DDL/schema export của đúng JPA provider và dùng migration để quản lý cấu trúc cùng dữ liệu seed.

Nếu nhiều entity dùng chung bảng generator, mỗi generator nên có khóa dòng riêng, ví dụ purchase_order và customer. Không cấu hình hai entity dùng cùng một dòng counter trừ khi chủ đích muốn chia sẻ một dãy ID.

Ưu điểm:

- Không yêu cầu database có sequence hoặc identity column.
- Cơ chế cấp ID dựa trên bảng thông thường.
- Có thể cấp trước block ID nếu allocation size lớn hơn 1.

Hạn chế:

- Mỗi lần cần cấp block ID phải đọc/cập nhật bảng generator.
- Các transaction cùng lấy ID có thể tranh chấp khóa trên dòng generator.
- Có thêm bảng và migration phải quản lý.
- Throughput thường kém sequence native trên database hỗ trợ sequence tốt.

TABLE có thể hữu ích trong môi trường database thiếu sequence/identity hoặc khi cần một cơ chế tương thích rộng. Tuy nhiên, không nên chọn nó chỉ vì nghĩ rằng bảng generator đơn giản hơn; chi phí khóa và cập nhật có thể đáng kể khi tải ghi cao.

## 3. allocationSize và việc cấp ID theo block

SequenceGenerator và TableGenerator đều có thuộc tính allocationSize. Giá trị này cho biết số ID mà provider có thể phân bổ từ một lần lấy giá trị generator. Giá trị mặc định của annotation là 50.

Ví dụ allocationSize = 1:

- Provider lấy một giá trị generator cho mỗi ID.
- Cấu hình đơn giản, dễ đối chiếu.
- Có thể tạo nhiều round trip hơn.

Ví dụ allocationSize = 50:

- Provider lấy một block ID và sử dụng dần trong bộ nhớ.
- Ít truy cập generator hơn khi insert nhiều entity.
- Khi ứng dụng restart hoặc block đã cấp chưa dùng hết, có thể xuất hiện khoảng trống.

Với Hibernate, optimizer có thể dùng block theo cách khác nhau. Một số optimizer yêu cầu database sequence increment tương ứng allocation size; một số cấu hình có quy tắc khác. Vì vậy, không chỉ chỉnh allocationSize trong annotation mà quên migration sequence.

Ví dụ nếu Hibernate dùng pooled allocation size 50, sequence PostgreSQL thường được cấu hình increment 50 theo ví dụ trước. Nếu Hibernate báo sequence increment mismatch, hãy kiểm tra:

1. allocationSize trong @SequenceGenerator.
2. Increment của sequence trong database.
3. Hibernate optimizer và dialect đang được dùng.
4. Cấu hình kiểm tra mismatch của Hibernate.
5. Migration đã chạy trên database thực tế hay chưa.

Không tự sửa sequence counter trong production để chữa lỗi mismatch nếu chưa hiểu ID đã được cấp và dữ liệu hiện có. Thay đổi generator cần kế hoạch tránh trùng khóa.

## 4. Vì sao ID sinh tự động không liên tục?

Một sai lầm phổ biến là nghĩ ID phải tăng liên tục và không được có khoảng trống. Các chiến lược sinh ID không cam kết tính liên tục không có gap.

Khoảng trống có thể xuất hiện vì:

- Transaction insert bị rollback sau khi ID đã được cấp.
- Sequence cấp trước một block nhưng ứng dụng chỉ dùng một phần.
- Ứng dụng restart và bỏ phần ID chưa dùng trong block.
- Database sequence hoặc identity tăng nhưng insert thất bại.
- Nhiều instance ứng dụng lấy các block ID độc lập.

Ví dụ, sequence cấp block 1–50 cho instance A và 51–100 cho instance B. Nếu A mới dùng tới 5 rồi restart, các ID còn lại trong block có thể bị bỏ. Đây là hành vi bình thường của generator tối ưu hiệu năng.

Không dùng ID kỹ thuật làm số hóa đơn, số đơn hàng hoặc số chứng từ có yêu cầu liên tục theo luật/quy trình kế toán. Nếu cần business number có quy tắc riêng, phải thiết kế bộ cấp số nghiệp vụ riêng, có khóa và transaction phù hợp, cùng cách xử lý retry/rollback.

## 5. Khả năng batching và hiệu năng

Khác biệt quan trọng giữa các chiến lược nằm ở thời điểm provider có được ID:

| Chiến lược | Thời điểm có ID | Batch insert với Hibernate | Chi phí generator |
|---|---|---|---|
| AUTO | Phụ thuộc chiến lược provider chọn | Phụ thuộc chiến lược thực tế | Phụ thuộc chiến lược |
| IDENTITY | Sau khi database insert | Thường không batch insert entity identity-generated theo cách thông thường | Insert lấy ID trực tiếp từ bảng |
| SEQUENCE | Có thể lấy trước insert | Có thể batch insert thuận lợi | Có thể giảm bằng allocationSize |
| TABLE | Lấy từ bảng generator trước insert | Có thể batch insert sau khi cấp ID | Đọc/cập nhật bảng generator; có thể tranh chấp |

Không nên chỉ dựa vào bảng so sánh để kết luận hiệu năng. Driver JDBC, database, Hibernate version, batch size, số entity trong transaction và mapping quan hệ đều ảnh hưởng kết quả.

Nếu cần insert hàng nghìn hoặc hàng triệu bản ghi:

- Đo thời gian và số câu SQL với dữ liệu đại diện.
- Kiểm tra Hibernate SQL log hoặc datasource metrics.
- Thử cấu hình sequence allocation size và JDBC batch size phù hợp.
- Với batch lớn, cân nhắc flush/clear theo lô để giới hạn persistence context.
- Đo tác động của cascade và quan hệ entity.
- Kiểm tra chiến lược sinh ID có cho phép provider batch insert không.

Ví dụ cấu hình batch cho Hibernate:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
```

Cấu hình này là gợi ý để thử nghiệm, không bảo đảm mọi insert đều được batch. IDENTITY thường ngăn Hibernate gom insert entity cần identity ID theo cơ chế batching thông thường. Sequence hoặc Table có thể thuận lợi hơn vì ID được biết trước, nhưng vẫn phải kiểm tra driver, provider và SQL thực tế.

## 6. Chọn chiến lược nào?

### Chọn IDENTITY khi

- Database hỗ trợ identity/auto-increment.
- Ứng dụng chủ yếu CRUD thông thường.
- Tốc độ insert hàng loạt không phải nút thắt.
- Muốn cấu hình đơn giản và để database cấp ID tại thời điểm insert.

### Chọn SEQUENCE khi

- Database hỗ trợ sequence native.
- Có nhiều thao tác insert hoặc batch insert.
- Muốn provider cấp ID trước khi insert.
- Có thể quản lý sequence và allocationSize rõ ràng qua migration.

Đây thường là lựa chọn tốt cho ứng dụng Hibernate trên PostgreSQL/Oracle có nhu cầu ghi nhiều.

### Chọn TABLE khi

- Database không có sequence phù hợp.
- Cần cơ chế cấp số dựa trên bảng có thể triển khai rộng.
- Tải ghi không quá cao hoặc đã đo được chi phí generator.
- Có thể quản lý bảng generator, dòng counter và khóa đồng thời.

### Chọn AUTO khi

- Muốn provider quyết định chiến lược theo database/dialect.
- Không có yêu cầu chặt về loại generator vật lý.
- Đã kiểm tra chiến lược thực tế mà provider chọn ở từng môi trường.

Nếu cần hiệu năng và schema dự đoán được, nên chỉ định chiến lược tường minh thay vì dựa vào AUTO.

## 7. Ví dụ cùng một entity với bốn chiến lược

Không khai báo bốn annotation trên cùng một field. Đây là bốn phương án thay thế cho nhau; mỗi phương án dùng một mapping/phiên bản entity riêng trong ví dụ.

**AUTO:**

```java
@Id
@GeneratedValue(strategy = GenerationType.AUTO)
private Long id;
```

**IDENTITY:**

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

**SEQUENCE:**

```java
@Id
@GeneratedValue(
    strategy = GenerationType.SEQUENCE,
    generator = "purchaseOrderSeq"
)
@SequenceGenerator(
    name = "purchaseOrderSeq",
    sequenceName = "purchase_order_seq",
    allocationSize = 50
)
private Long id;
```

**TABLE:**

```java
@Id
@GeneratedValue(
    strategy = GenerationType.TABLE,
    generator = "purchaseOrderTable"
)
@TableGenerator(
    name = "purchaseOrderTable",
    table = "id_generator",
    pkColumnName = "generator_key",
    valueColumnName = "next_value",
    pkColumnValue = "purchase_order",
    allocationSize = 50
)
private Long id;
```

Tên generator trong thuộc tính generator phải khớp chính xác với name của SequenceGenerator hoặc TableGenerator. Tên generator là định danh JPA, không phải tên sequence hoặc table vật lý.

## 8. Kiểm thử và quản lý schema

Với schema được quản lý bằng migration, hãy xác nhận các thành phần sau:

- ID column có kiểu tương thích với thuộc tính Java.
- Identity column được tạo đúng cho IDENTITY.
- Sequence tồn tại, đúng tên và increment tương thích với cấu hình provider cho SEQUENCE.
- Bảng generator và các dòng counter được tạo đúng cho TABLE.
- Primary key và unique constraint có mặt.
- Không có hai generator cùng cấp ID theo một dãy ngoài chủ đích.
- Dữ liệu hiện hữu không xung đột với giá trị tiếp theo mà generator sẽ cấp.

Trong môi trường kiểm thử, có thể dùng Testcontainers với database cùng loại production để xác nhận hành vi thực tế. H2 không đại diện hoàn toàn cho PostgreSQL, MySQL, Oracle hoặc SQL Server; đặc biệt cần kiểm tra identity, sequence, locking và native SQL.

Với Hibernate, có thể dùng schema validation để phát hiện một số sai lệch mapping/schema khi khởi tạo. Validation không thay thế migration và không chứng minh rằng mọi hành vi sinh ID dưới tải đồng thời đều đúng.

## 9. Các lỗi thường gặp

| Biểu hiện | Nguyên nhân có thể | Hướng xử lý |
|---|---|---|
| Sequence không tồn tại | Migration chưa tạo sequence hoặc sai sequenceName | Kiểm tra migration, schema và tên sequence |
| Sequence increment mismatch | allocationSize không khớp optimizer/sequence increment của Hibernate | Kiểm tra provider, optimizer, allocationSize và DDL |
| Duplicate key | Generator bị dùng chung sai cách, counter bị reset hoặc sequence nằm sau dữ liệu hiện có | Kiểm tra trạng thái generator và dữ liệu hiện tại; lập kế hoạch đồng bộ an toàn |
| IDENTITY insert chậm khi ghi hàng loạt | Insert cần lấy ID ngay, hạn chế batching | Benchmark SEQUENCE nếu database hỗ trợ |
| TABLE generator tranh chấp | Nhiều transaction cập nhật cùng dòng counter | Tăng allocationSize có kiểm soát hoặc dùng native sequence |
| AUTO chọn chiến lược khác khi đổi database | Provider/dialect quyết định generator | Kiểm tra DDL và hành vi ở môi trường đích; chỉ định strategy nếu cần |
| ID có khoảng trống | Rollback, block allocation, restart hoặc insert lỗi | Chấp nhận gap cho ID kỹ thuật; dùng bộ cấp business number riêng nếu cần |
| Generator name không được nhận diện | Tên generator trong GeneratedValue khác name của annotation generator | Đối chiếu chính xác tên và phạm vi persistence unit |

## 10. Bài tập thực hành

1. Tạo entity Customer dùng IDENTITY và quan sát ID sau khi save.
2. Tạo entity PurchaseOrder dùng SEQUENCE với sequenceName riêng.
3. Thay allocationSize từ 1 thành 50; kiểm tra DDL sequence và số lần truy cập generator.
4. Tạo entity dùng TABLE generator với một dòng counter riêng.
5. Chạy insert batch với IDENTITY và SEQUENCE; bật SQL log để so sánh số lần insert/batch.
6. Thử rollback sau khi generator đã cấp ID; quan sát khoảng trống.
7. Đổi database dialect trong môi trường test và kiểm tra AUTO chọn chiến lược nào.
8. Viết migration cho sequence/table generator và bật schema validation.
9. Chạy nhiều transaction đồng thời để kiểm tra ID không trùng.
10. Giải thích vì sao ID sinh tự động không phù hợp làm số hóa đơn liên tục.

**Nguyên tắc xuyên suốt:** AUTO giao quyết định cho provider; IDENTITY lấy ID từ cột identity khi insert; SEQUENCE lấy ID từ sequence và có thể cấp block; TABLE lấy ID từ bảng generator. Hãy chọn theo database, provider và tải ghi; quản lý generator bằng migration; chấp nhận khoảng trống của ID kỹ thuật và giữ mã nghiệp vụ ở một cơ chế riêng.
