# Scoping Delete Operations with Specifications and the Impact of Bulk Deletes in Spring Data JPA

Spring Data JPA lets you use Specifications to construct dynamic delete conditions without writing a dedicated repository method for every filter combination. The `delete(spec)` method uses JPA `CriteriaDelete` to perform a bulk delete directly in the database.

Bulk deletion is very efficient when removing many rows matching the same criteria, yet its semantics differ from calling `EntityManager.remove(entity)` per entity. It does not synchronize the persistence context, does not invoke entity lifecycle callbacks, and does not perform JPA `REMOVE` cascades or orphan removal. Therefore, choosing a delete API must account for both performance and the business behaviors that must be preserved.

This lesson explains how to scope deletes with Specifications, API differences between Spring Data JPA 3.5 and 4.x, `CriteriaDelete` limitations, bulk delete side effects, and how to test delete operations safely.

## 1. Specification in Delete Operations

A Specification expresses a predicate on an entity using the JPA Criteria API. The repository must extend `JpaSpecificationExecutor` to execute those conditions:

~~~java
public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long>,
                JpaSpecificationExecutor<PurchaseOrder> {
}
~~~

For read queries, we typically call:

~~~java
List<PurchaseOrder> orders = repository.findAll(specification);
~~~

For conditional deletes, Spring Data JPA provides:

~~~java
long deleted = repository.delete(specification);
~~~

This method builds a `CriteriaDelete` and translates the Specification condition into the DELETE statement's WHERE clause. It returns the count of deleted entity rows matching the criteria. Matching entities do not have to be loaded as Java objects before the database deletes them.

Business example: delete only cancelled orders belonging to the specified tenant and created before a cutoff timestamp. All three conditions must be present in the predicate:

~~~sql
DELETE FROM purchase_orders
WHERE tenant_id = ?
  AND status = 'CANCELLED'
  AND created_at < ?
~~~

This SQL illustrates the semantics; the exact SQL is generated by the JPA provider and database dialect.

## 2. API Differences Between Spring Data JPA 3.5 and 4.x

Check which Spring Data JPA version your project uses. Naming and Specification types for delete operations change in the 4.x line.

### 2.1. Spring Data JPA 3.5: delete(Specification<T>)

In Spring Data JPA 3.5, `JpaSpecificationExecutor` defines:

~~~java
long delete(Specification<T> spec);
~~~

Example:

~~~java
Specification<PurchaseOrder> belongsToTenant(UUID tenantId) {
    return (root, query, cb) ->
            cb.equal(root.get("tenantId"), tenantId);
}

Specification<PurchaseOrder> hasStatus(OrderStatus status) {
    return (root, query, cb) ->
            cb.equal(root.get("status"), status);
}

Specification<PurchaseOrder> createdBefore(Instant cutoff) {
    return (root, query, cb) ->
            cb.lessThan(root.get("createdAt"), cutoff);
}
~~~

Combining conditions:

~~~java
Specification<PurchaseOrder> target =
        Specification.allOf(
                belongsToTenant(tenantId),
                hasStatus(OrderStatus.CANCELLED),
                createdBefore(cutoff)
        );

long deleted = repository.delete(target);
~~~

A key detail of the 3.5 API is that `Specification.toPredicate` takes `CriteriaQuery<?> query`, yet when called from `delete(spec)`, the `query` parameter is null. Spring Data builds a `CriteriaDelete`; `CriteriaDelete` is not a `CriteriaQuery`.

Therefore, Specifications used for deletes should only create predicates from `root` and `CriteriaBuilder`. Never invoke SELECT-specific query operations such as:

- `query.distinct(true)`.
- `query.orderBy(...)`.
- `query.groupBy(...)` or `query.having(...)`.
- `root.fetch(...)` to load associations.
- `query.subquery(...)`, since the `query` argument is null here.

A Specification originally written for `findAll` can work with `delete` if it only builds simple predicates. If it modifies `CriteriaQuery` structure or adds fetch joins, reusing it for delete can cause a `NullPointerException` or Criteria API error.

### 2.2. Spring Data JPA 4.x: PredicateSpecification and DeleteSpecification

Spring Data JPA 4.0 introduces Specification types tied to the query kind:

- `PredicateSpecification<T>`: query-type-independent predicate.
- `Specification<T>`: predicate for read queries.
- `UpdateSpecification<T>`: conditions and updates for CriteriaUpdate.
- `DeleteSpecification<T>`: predicate for CriteriaDelete.

For simple conditions, `PredicateSpecification` can be used directly:

~~~java
PredicateSpecification<PurchaseOrder> belongsToTenant =
        (from, cb) ->
                cb.equal(from.get("tenantId"), tenantId);

PredicateSpecification<PurchaseOrder> isCancelled =
        (from, cb) ->
                cb.equal(from.get("status"), OrderStatus.CANCELLED);

PredicateSpecification<PurchaseOrder> createdBefore =
        (from, cb) ->
                cb.lessThan(from.get("createdAt"), cutoff);

long deleted = repository.delete(
        belongsToTenant.and(isCancelled).and(createdBefore)
);
~~~

To state explicitly that this is a delete condition, convert `PredicateSpecification` into `DeleteSpecification`:

~~~java
DeleteSpecification<PurchaseOrder> deleteSpec =
        DeleteSpecification.where(belongsToTenant)
                .and(isCancelled)
                .and(createdBefore);

long deleted = repository.delete(deleteSpec);
~~~

`DeleteSpecification.toPredicate` directly receives `Root<T>`, `CriteriaDelete<T>`, and `CriteriaBuilder`. Thus, code never assumes a `CriteriaQuery` argument exists.

`PredicateSpecification` suits predicates that only read root attributes and build expressions. `DeleteSpecification` suits cases needing access to the `CriteriaDelete` API, such as creating a subquery for a related condition. Both perform bulk deletes when passed to `JpaSpecificationExecutor.delete`.

### 2.3. Comparison Table

| Version | Delete API | Predicate Parameters | Notes |
|---|---|---|---|
| Spring Data JPA 3.5 | `delete(Specification<T>)` | `Root`, `CriteriaQuery` (null in delete path), `CriteriaBuilder` | Only build predicates; do not access CriteriaQuery |
| Spring Data JPA 4.x | `delete(PredicateSpecification<T>)` | `From`, `CriteriaBuilder` | Query-type-independent predicate |
| Spring Data JPA 4.x | `delete(DeleteSpecification<T>)` | `Root`, `CriteriaDelete`, `CriteriaBuilder` | Dedicated API for CriteriaDelete |

Do not copy `DeleteSpecification` code into projects still running Spring Data JPA 3.5. Verify actual dependencies in Maven/Gradle before choosing an example.

## 3. Designing Delete Specifications with Mandatory Conditions

Deletion is destructive. Mandatory constraints such as tenant, owner, or time scope must always be included in the predicate. Never let optional request filters alone determine the entire delete scope.

Example purchase order entity:

~~~java
@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private UUID tenantId;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private OrderStatus status;

    @Column(nullable = false)
    private Instant createdAt;

    @Version
    private long version;

    protected PurchaseOrder() {
    }

    public PurchaseOrder(
            UUID tenantId,
            OrderStatus status,
            Instant createdAt) {
        this.tenantId = tenantId;
        this.status = status;
        this.createdAt = createdAt;
    }

    public Long getId() {
        return id;
    }

    public UUID getTenantId() {
        return tenantId;
    }

    public OrderStatus getStatus() {
        return status;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}
~~~

Enum:

~~~java
public enum OrderStatus {
    NEW,
    PAID,
    CANCELLED,
    COMPLETED
}
~~~

Predicate-only Specifications:

~~~java
public final class PurchaseOrderSpecs {

    private PurchaseOrderSpecs() {
    }

    public static Specification<PurchaseOrder> belongsToTenant(
            UUID tenantId) {
        return (root, query, cb) ->
                cb.equal(root.get("tenantId"), tenantId);
    }

    public static Specification<PurchaseOrder> hasStatus(
            OrderStatus status) {
        return (root, query, cb) ->
                cb.equal(root.get("status"), status);
    }

    public static Specification<PurchaseOrder> createdBefore(
            Instant cutoff) {
        return (root, query, cb) ->
                cb.lessThan(root.get("createdAt"), cutoff);
    }
}
~~~

Service validating mandatory parameters and executing within a transaction:

~~~java
@Service
public class PurchaseOrderCleanupService {

    private final PurchaseOrderRepository orders;
    private final EntityManager entityManager;

    public PurchaseOrderCleanupService(
            PurchaseOrderRepository orders,
            EntityManager entityManager) {
        this.orders = orders;
        this.entityManager = entityManager;
    }

    @Transactional
    public long deleteOldCancelledOrders(
            UUID tenantId,
            Instant cutoff) {

        Objects.requireNonNull(tenantId, "tenantId is required");
        Objects.requireNonNull(cutoff, "cutoff is required");

        Specification<PurchaseOrder> target =
                Specification.allOf(
                        PurchaseOrderSpecs.belongsToTenant(tenantId),
                        PurchaseOrderSpecs.hasStatus(
                                OrderStatus.CANCELLED),
                        PurchaseOrderSpecs.createdBefore(cutoff)
                );

        entityManager.flush();

        long deleted = orders.delete(target);

        entityManager.clear();

        return deleted;
    }
}
~~~

This example uses the Spring Data JPA 3.5 API. `EntityManager.flush()` pushes pending changes to the database before running the bulk delete. `clear()` detaches all entities from the persistence context afterward so callers do not continue using potentially stale objects.

`clear()` affects every managed entity in the persistence context, not only PurchaseOrder. Therefore, place bulk delete operations in a dedicated service or transaction. If the active transaction holds other entities that still need updates, do not call `clear()` arbitrarily; consider a separate persistence context or reloading needed entities.

If your project uses Spring Data JPA 4.x, substitute `PredicateSpecification`/`DeleteSpecification` as shown earlier; the transaction and persistence context rules remain identical.

## 4. Limitations of CriteriaDelete

`CriteriaDelete` represents a direct database DELETE statement. It is not a `CriteriaQuery` for fetching entities.

Key limitations:

1. A `CriteriaDelete` targets one root entity.
2. There is no SELECT list to select DTOs or entity graphs.
3. There is no fetch plan to load associations.
4. There is no pagination mechanism for deletes such as `Pageable`.
5. `ORDER BY`, `GROUP BY`, and `HAVING` cannot be used like in a regular SELECT query.
6. The result is an affected row count, not a list of deleted entities.
7. The persistence context is not automatically synchronized with the delete result.

Conditions normally inspect root properties such as tenant, status, creation timestamp, or primary key. When conditions involve complex relationships with other entities, path expressions or subqueries may be needed. In Spring Data JPA 4.x, `DeleteSpecification` provides the `CriteriaDelete` object to construct subqueries. In 3.5, the `CriteriaQuery` argument in `Specification` is null on the delete path; if you need a complex `CriteriaDelete`, write a custom repository method using `CriteriaDelete` directly instead of forcing SELECT logic into it.

Skeleton custom repository example for a `CriteriaDelete` operation:

~~~java
@Transactional
public long deleteByCustomCriteria(
        UUID tenantId,
        Instant cutoff) {

    CriteriaBuilder cb = entityManager.getCriteriaBuilder();
    CriteriaDelete<PurchaseOrder> delete =
            cb.createCriteriaDelete(PurchaseOrder.class);

    Root<PurchaseOrder> root = delete.from(PurchaseOrder.class);

    delete.where(
            cb.equal(root.get("tenantId"), tenantId),
            cb.equal(root.get("status"), OrderStatus.CANCELLED),
            cb.lessThan(root.get("createdAt"), cutoff)
    );

    return entityManager.createQuery(delete).executeUpdate();
}
~~~

This illustrates the custom repository part. Production code still requires mandatory parameter validation, tenant scoping, transaction boundaries, persistence context control, and testing on the real provider.

## 5. No Condition Must Never Mean Delete Everything

This is the most dangerous mistake when building dynamic filters.

In Spring Data JPA 3.5, `delete(null)` can be interpreted as deleting every entity of that repository's type. In newer versions, `Specification.unrestricted()`, `PredicateSpecification.unrestricted()`, or `DeleteSpecification.unrestricted()` contributes nothing to the WHERE clause. With no predicate remaining, the delete operation can apply to the entire target table.

In particular, `DeleteSpecification.allOf(...)` and `anyOf(...)` return an unrestricted specification when passed an empty list. An empty filter list does not mean "delete nothing"; in this context, it can mean "unrestricted".

Safety rules:

- Never pass a null Specification into a delete operation.
- Never use `unrestricted` as a fallback when request parameters are missing.
- Never call `allOf`/`anyOf` with a potentially empty filter list without checking first.
- Always enforce mandatory predicates such as tenant ID or owner ID.
- Reject requests if required cutoff/status/scope parameters are missing.
- Never let optional filters collapse into unrestricted and pass that into delete.
- Write tests proving records belonging to other tenants or statuses remain untouched.

Fail-closed validation example:

~~~java
if (tenantId == null) {
    throw new IllegalArgumentException("Tenant is required");
}

if (cutoff == null) {
    throw new IllegalArgumentException("Cutoff is required");
}
~~~

Never substitute an empty Specification for the two mandatory conditions above.

### 5.1. Be Careful When Combining AND and OR

Suppose the requirement is to delete orders that are cancelled or expired, but only within the current tenant. The correct predicate has the form:

~~~text
tenantId = currentTenant
AND
(status = CANCELLED OR createdAt < cutoff)
~~~

Do not write the logic as:

~~~text
(tenantId = currentTenant AND status = CANCELLED)
OR
createdAt < cutoff
~~~

The second expression can delete expired orders belonging to other tenants. Always nest OR conditions inside the mandatory tenant condition and inspect the generated SQL.

## 6. How Bulk Deletes Affect the Persistence Context

The persistence context tracks managed entities and their states. When `EntityManager.remove(entity)` is called, the entity is marked removed. The provider executes DELETE upon flush or at the appropriate time.

Bulk deletes work differently: the database deletes rows directly via a set-based statement. The JPA provider does not load each entity and does not update individual objects residing in the persistence context.

Example:

~~~java
PurchaseOrder managed =
        entityManager.find(PurchaseOrder.class, orderId);

long deleted = repository.delete(specification);
~~~

After the bulk delete statement, `managed` remains a Java object loaded earlier. Its state does not automatically become "deleted" to match the database. If code continues reading or modifying this object, it may operate on stale data.

How to handle it:

- Execute bulk deletes in a dedicated transaction or a persistence context that does not hold entities needed afterward.
- Call `flush()` before deleting if pending changes must be persisted first.
- Call `clear()` after deleting when detaching all entities in the context is acceptable.
- If a single affected entity must still be used after state updates, refresh or reload an existing entity appropriately; never refresh an entity that has been deleted from the database.
- Do not retain references to affected entities for subsequent business logic.

Bulk deletes do not call `EntityManager.clear()` automatically. That is the responsibility of calling code or transaction architecture.

### 6.1. Why Flush Before Clear?

`clear()` detaches every entity and discards tracked changes in the persistence context. Any unflushed modifications may fail to be written as intended.

Common sequence inside a dedicated transaction:

~~~java
entityManager.flush();
long deleted = repository.delete(specification);
entityManager.clear();
~~~

Never call `clear()` before `flush()` if pending changes must be saved. If the persistence context holds many other aggregates, consider using a separate transaction/context instead of detaching everything.

## 7. Bulk Deletes Do Not Run Lifecycle Callbacks or JPA Cascades

Calling `EntityManager.remove(entity)` runs the entity removal lifecycle. It can trigger:

- `@PreRemove`.
- `@PostRemove`.
- Corresponding entity listeners.
- Relationships with `CascadeType.REMOVE` or `CascadeType.ALL`.
- `orphanRemoval = true` rules on association operations.

Bulk deletion via Specification does not call `remove()` per entity. Consequently, there are no per-row `@PreRemove`/`@PostRemove` callbacks and no JPA `REMOVE`/orphan cascades.

Callback example:

~~~java
@Entity
public class PurchaseOrder {

    @PreRemove
    void beforeRemove() {
        // Not invoked per entity during a bulk delete.
    }
}
~~~

If critical business logic lives in callbacks—such as writing audit logs, revoking resources, or publishing domain events—bulk delete skips that logic.

### 7.1. JPA Cascades vs. Database Cascades

Two mechanisms must be distinguished:

| Mechanism | Executed by Bulk Delete? |
|---|---|
| `CascadeType.REMOVE` | No |
| `CascadeType.ALL` (including REMOVE) | No |
| `orphanRemoval = true` | Not triggered by bulk delete |
| Foreign key `ON DELETE CASCADE` | Still executed by the database |
| Database triggers | Triggers still fire per database config |
| `@PreRemove` / `@PostRemove` | No |
| Entity listeners tied to remove lifecycle | No |

If a child table has a foreign key pointing to the orders table without `ON DELETE CASCADE`, the database may reject deleting parent orders due to a foreign key violation. In that case, the application must delete child rows first, use an intentionally designed database cascade, or switch to per-entity removal so JPA cascades execute.

Do not confuse `CascadeType.REMOVE` with `ON DELETE CASCADE`: one belongs to the JPA lifecycle, while the other is a database constraint.

### 7.2. Auditing and Soft Deletes

If auditing relies on `@PreRemove`, entity listeners, or domain events emitted on entity removal, bulk delete bypasses those steps.

If a system needs an audit trail for a purge job, record a summary audit entry in the same transaction capturing tenant, criteria, actor, timestamp, and deleted row count. If per-entity auditing is required, choose a lifecycle-aware deletion method or a database-level audit mechanism.

If soft deletion is implemented via a pre-remove callback toggling a deleted flag, a bulk DELETE will not run that callback; the database will receive a physical delete. You can use a bulk UPDATE to set the soft-delete flag, or invoke per-entity `remove` according to your provider's soft-delete design. Verify the soft-delete mechanism in place before changing APIs.

## 8. Optimistic Locking, Versions, and Consistency

An entity may declare `@Version` to detect conflicts during managed updates or deletes. Bulk delete does not load and process entities individually through that lifecycle. Therefore, do not rely on per-entity delete locking for concurrency protection when using `CriteriaDelete`.

If business rules require constraining by state/version, include that condition in the predicate:

~~~java
Specification<PurchaseOrder> expectedVersion =
        (root, query, cb) ->
                cb.equal(root.get("version"), expectedVersionValue);
~~~

After deleting, check the returned row count:

~~~java
long deleted = repository.delete(target);

if (deleted != expectedCount) {
    throw new ConcurrentModificationException(
            "The matching rows changed before deletion");
}
~~~

This checks affected row counts, though an `expectedCount` queried earlier does not provide atomicity by itself. Between counting and deleting, another transaction could modify rows. If strict concurrency guarantees are required, design appropriate isolation/locking or embed version predicates directly in the DELETE and handle the affected row count.

Never treat `count(spec)` followed by `delete(spec)` as an atomic operation without an appropriate concurrency strategy.

## 9. How Bulk Delete Differs from Derived Delete and Per-Entity Delete

Delete mechanisms that look similar behave quite differently:

| Delete Method | Execution | JPA Callbacks / Cascades | Memory and Performance |
|---|---|---|---|
| `repository.delete(spec)` | Direct database CriteriaDelete | No | Usually efficient for large sets |
| `@Modifying @Query("delete ...")` | Single bulk JPQL DELETE | No | Usually efficient for large sets |
| `deleteAllInBatch()` | Bulk delete via repository API | No | Does not load each entity |
| Derived `deleteByStatus(...)` | Queries matching entities, then deletes each entity | Yes | May load many entities into memory |
| `repository.delete(entity)` | `EntityManager.remove` for the entity | Yes | Fits when lifecycle behavior is needed |
| Looping `findAll(spec)` and deleting each entity | Loads entities and removes each object | Yes | Costs more queries, memory, and time |

Spring Data JPA distinguishes derived deletes from bulk deletes. A derived delete such as `deleteByRoleId(...)` queries matching entities and removes them one by one so the provider can invoke lifecycle callbacks. In contrast, a JPQL DELETE or `delete(spec)` issues a single bulk operation directly against the database.

If callbacks/cascades are needed, choose entity deletion. If high-volume bulk deletion is needed and lifecycle impacts are accounted for, choose bulk deletion.

## 10. Deleting Large Datasets: Single Statement or Batched?

`delete(spec)` does not take a `Pageable` to delete page by page. `CriteriaDelete` is designed for a set-based operation; do not assume portable LIMIT/OFFSET can be attached to it.

A single bulk delete can work when row counts are moderate and the database handles it well. On very large datasets, a single transaction can:

- Hold locks for a long time.
- Generate massive transaction logs / WAL / undo records.
- Put pressure on replication and vacuum/cleanup.
- Increase rollback duration if an error occurs.
- Slow down concurrent requests on the same table.

You can batch by ID or time range:

1. Query a batch of matching IDs in deterministic order.
2. Delete that batch of IDs in a transaction.
3. Commit to release resources.
4. Repeat until no matching data remains.
5. Record checkpoints so jobs can resume after failures.

Repository example fetching IDs via keyset:

~~~java
@Query("""
       select p.id
       from PurchaseOrder p
       where p.tenantId = :tenantId
         and p.status = :status
         and p.createdAt < :cutoff
         and p.id > :afterId
       order by p.id
       """)
List<Long> findNextIds(
        @Param("tenantId") UUID tenantId,
        @Param("status") OrderStatus status,
        @Param("cutoff") Instant cutoff,
        @Param("afterId") Long afterId,
        Pageable pageable);
~~~

Then you can call `deleteAllByIdInBatch(ids)` to bulk-delete by ID batch. Batch methods still carry bulk semantics: no JPA callbacks/cascades are invoked, and the persistence context is not auto-synchronized.

If per-entity lifecycle execution is required, load each batch of entities and call `EntityManager.remove()` on each object. After each batch, flush and clear according to your transaction strategy. This consumes more resources while preserving entity lifecycle semantics.

When batching, decide how to handle data changing while the job runs. Keyset pagination by ID avoids large OFFSET costs, yet does not provide a single snapshot across the entire job.

## 11. Testing Specification-Scoped Deletes

Tests should verify both the deleted row count and which rows remain intact.

Example with Spring Data JPA 3.5 and `@DataJpaTest`:

~~~java
@DataJpaTest
class PurchaseOrderDeleteSpecificationTest {

    @Autowired
    private TestEntityManager entityManager;

    @Autowired
    private PurchaseOrderRepository orders;

    @Test
    void deletesOnlyCancelledOrdersInsideTenantAndBeforeCutoff() {
        UUID tenantA = UUID.randomUUID();
        UUID tenantB = UUID.randomUUID();
        Instant cutoff = Instant.parse("2026-01-01T00:00:00Z");

        entityManager.persist(new PurchaseOrder(
                tenantA,
                OrderStatus.CANCELLED,
                Instant.parse("2025-10-01T00:00:00Z")
        ));

        entityManager.persist(new PurchaseOrder(
                tenantA,
                OrderStatus.PAID,
                Instant.parse("2025-10-01T00:00:00Z")
        ));

        entityManager.persist(new PurchaseOrder(
                tenantB,
                OrderStatus.CANCELLED,
                Instant.parse("2025-10-01T00:00:00Z")
        ));

        entityManager.persist(new PurchaseOrder(
                tenantA,
                OrderStatus.CANCELLED,
                Instant.parse("2026-02-01T00:00:00Z")
        ));

        entityManager.flush();
        entityManager.clear();

        Specification<PurchaseOrder> target =
                Specification.allOf(
                        PurchaseOrderSpecs.belongsToTenant(tenantA),
                        PurchaseOrderSpecs.hasStatus(
                                OrderStatus.CANCELLED),
                        PurchaseOrderSpecs.createdBefore(cutoff)
                );

        long deleted = orders.delete(target);

        entityManager.clear();

        assertThat(deleted).isEqualTo(1);
        assertThat(orders.count()).isEqualTo(3);
    }
}
~~~

This test sets up four cases: matching tenant and status; wrong status; wrong tenant; and matching tenant/status but after cutoff. Only the first row is deleted.

`flush()` writes fixtures to the database before running the bulk DELETE. `clear()` afterward ensures verification queries read fresh state from the database rather than stale entity instances in the persistence context.

### 11.1. Testing Lifecycle Callbacks

If an entity has `@PreRemove`, write a dedicated test proving `delete(spec)` does not invoke the callback. You can use an entity listener with a counter in the test or an appropriate test double.

Do not test callbacks merely by observing that the row vanished. The database can delete the row successfully even though the callback never fired.

### 11.2. Testing Stale Persistence Contexts

Create a managed entity before the bulk delete, perform the delete, then inspect state using a fresh persistence context after clearing. This test exposes code that accidentally continues using stale entity objects after bulk operations.

### 11.3. Testing Foreign Keys and Cascades

Create parent/child data with a foreign key relationship and run a bulk delete:

- If the FK lacks `ON DELETE CASCADE`, assert the database rejects deleting when child rows remain.
- If the database defines `ON DELETE CASCADE`, assert child rows are deleted by the database.
- Do not use that test to claim JPA `CascadeType.REMOVE` executed; that is a separate mechanism.

## 12. Common Pitfalls and Fixes

| Symptom | Cause | Solution |
|---|---|---|
| Deletes entire table | Null or unrestricted Specification | Require tenant/scope filters and fail closed |
| `NullPointerException` inside `toPredicate` | Code accesses `CriteriaQuery` on 3.5 delete path | Avoid `query` param; switch to `DeleteSpecification`/custom `CriteriaDelete` if needed |
| Entity still readable after delete | Persistence context not synchronized | Clear or query in a new context |
| `@PreRemove` never runs | Bulk delete skips entity lifecycle | Delete entities individually if callbacks are mandatory |
| Child entities remain or FK violation occurs | Bulk delete does not run JPA cascades | Delete children explicitly or use designed FK cascades |
| Soft-delete becomes a physical delete | Soft-delete logic lives in callbacks/entity remove | Use bulk UPDATE or appropriate per-entity remove |
| Missing per-row domain events/audits | No per-entity lifecycle events | Record summary audit/outbox entries or use per-entity remove |
| Pre-delete count differs from deleted count | Concurrent data changes between operations | Check affected rows and design concurrency handling |
| Deleting too much in one transaction | Large dataset causes expensive locks/logs/rollbacks | Batch deletes and commit per chunk |
| Test sees old entity after delete | Reading stale object/persistence context | Clear and requery database |

## 13. Pre-Bulk-Delete Checklist

- [ ] Confirmed exact Spring Data JPA version and matching API.
- [ ] Specification includes mandatory conditions such as tenant or owner.
- [ ] Never passing null or unrestricted as a delete condition.
- [ ] Never passing an unchecked potentially empty Specification list.
- [ ] AND/OR conditions are grouped accurately per business rules.
- [ ] With Spring Data JPA 3.5, `toPredicate` does not touch `CriteriaQuery` because `query` is null on the delete path.
- [ ] No fetch joins, ordering, grouping, or select-specific logic inside Specifications used for delete.
- [ ] Operation is wrapped in a transaction.
- [ ] Strategy decided for handling the persistence context after bulk delete.
- [ ] Evaluated whether callbacks, audits, domain events, and soft-deletes need to execute.
- [ ] Checked `CascadeType.REMOVE`, `orphanRemoval`, and database FK cascades.
- [ ] Considered version/concurrency and checked affected row count.
- [ ] Evaluated dataset size and whether batching is required.
- [ ] Tests prove matching rows are deleted and out-of-scope rows remain intact.
- [ ] Dedicated tests cover callbacks, FKs, and persistence context state when relevant.

Specifications let you reuse delete criteria, and CriteriaDelete lets the database remove many rows in a single operation. In exchange, bulk deletes bypass per-entity removal lifecycles and do not automatically synchronize the persistence context. Always enforce mandatory scoping criteria, verify API versions, decide explicitly on cascades/audits/soft-deletes, and test remaining data after deletion.
