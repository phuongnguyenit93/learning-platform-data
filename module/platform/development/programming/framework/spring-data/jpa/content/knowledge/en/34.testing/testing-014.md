# Managing Fixtures With @Sql, Migrations, and Deterministic Data

A reliable Spring Data JPA test must know the exact schema and data it runs against. Three common concepts play distinct roles:

- **Migrations** manage versioned database structure changes: creating tables, adding columns, indexes, constraints, or schema transformations.
- **Fixtures** are the data prepared for a specific test scenario: customers, orders, statuses, relationships, and values needed to verify outcomes.
- **@Sql** from Spring TestContext executes SQL scripts before or after tests to set up and clean up fixtures.

Migrations ensure environments share the same database structure. Fixtures ensure every test begins from a known data state. Never turn structural migrations into test sample datasets re-executed for individual test methods.

## 1. Distinguishing Migrations and Fixtures

| Criterion | Migration | Fixture |
|---|---|---|
| Purpose | Evolve schema and migrate application data | Prepare data for one test or test group |
| Lifecycle | Versioned/checksum-tracked and applied in order | Created, used, and cleaned within test scope |
| Tools | Flyway, Liquibase | `@Sql`, builders/factories, repositories, or Test Data Builders |
| Example | Create `purchase_order` table, add `status` column, add `UNIQUE` constraint | Create one customer and one `PENDING` order |
| Re-run per test? | Normally no | Can run before every test method |

Typical flow:

1. Tests boot the application context and database.
2. Flyway or Liquibase applies migrations to construct the schema.
3. Fixture scripts or factories seed data for the scenario.
4. Tests run repositories/services and verify behavior.
5. Fixtures roll back or are cleaned up per the chosen strategy.

Migrations should not hold sample rows meant solely for a single test. When adding a new test, you should not have to author a new migration version just to insert one test order.

## 2. Managing Schemas With Flyway or Liquibase

### 2.1. Flyway

Flyway commonly uses versioned migrations named like:

~~~text
src/main/resources/
  db/
    migration/
      V1__create_customer.sql
      V2__create_purchase_order.sql
      V3__add_order_status_index.sql
~~~

Example table-creation migration:

~~~sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(50) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_purchase_order_customer
        FOREIGN KEY (customer_id) REFERENCES customer(id)
);
~~~

Flyway records migration history in a schema history table, tracking versions and checksums. Versioned migrations execute sequentially and must not be edited once applied to shared environments. When schema changes are needed, create a new migration instead of rewriting old ones.

In Spring Boot, Flyway normally runs automatically during application context startup if dependencies and datasource settings are present. Tests should run the same schema migration chain required by the application.

### 2.2. Liquibase

Liquibase manages database changes via changelogs. Changelogs can be written in XML, YAML, JSON, or SQL. Each `changeSet` has an identifier and is recorded in the `DATABASECHANGELOG` table.

Example in YAML:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 1-create-customer
      author: team
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
              - column:
                  name: customer_code
                  type: VARCHAR(50)
                  constraints:
                    nullable: false
                    unique: true
              - column:
                  name: name
                  type: VARCHAR(150)
                  constraints:
                    nullable: false
~~~

Liquibase offers `contexts` and `labels` to control which `changeSet`s run in specific environments or scenarios. Use them deliberately; avoid letting test data leak into production via an accidentally enabled context.

### 2.3. Migrations in Tests

Tests should run real migrations to catch early:

- Missing columns or indexes.
- Wrong data types or constraints.
- Invalid migration ordering.
- Entity mappings mismatched with the schema.
- Database-specific SQL that only works on a different DBMS.

For engine-dependent SQL or behavior, Testcontainers runs the exact database type close to production. H2 works well for fast checks, yet does not emulate all dialect, sequence, locking, timestamp, and constraint differences of PostgreSQL, MySQL, or SQL Server.

## 3. Using @Sql to Create Fixtures

Spring TestContext provides **`org.springframework.test.context.jdbc.Sql`** to execute SQL scripts before or after test classes/methods.

Place scripts in test resources:

~~~text
src/test/resources/
  sql/
    fixtures/
      order-before.sql
      order-after.sql
~~~

Example:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.test.context.jdbc.Sql;

class PurchaseOrderRepositoryTest {

    @Test
    @Sql("/sql/fixtures/order-before.sql")
    void findsFixtureOrder() {
        // Execute test
    }
}
~~~

Paths starting with a slash are absolute classpath paths. Without a leading slash, Spring resolves the path relative to the test class's package. Using absolute paths makes script locations in test resources explicit.

By default, scripts execute in the **`BEFORE_TEST_METHOD`** phase. You can run cleanup after tests:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-after.sql",
    executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
~~~

Class-level `@Sql` normally applies before each test method in the class. To combine class-level and method-level scripts, use **`@SqlMergeMode(SqlMergeMode.MergeMode.MERGE)`**. By default, method-level `@Sql` overrides class-level `@Sql`; specify merge/override behavior explicitly to avoid accidentally skipping shared setup scripts.

## 4. Choosing Transaction Modes for @Sql

A common reason fixtures vanish or leak across tests is misunderstanding script transaction modes. Spring offers two primary modes via **`@SqlConfig(transactionMode = ...)`**:

- **`INFERRED`**: the default. Spring uses an existing transaction if active; otherwise, it infers transaction execution from the transaction manager and configuration.
- **`ISOLATED`**: runs the script in its own transaction, independent of the test transaction; the script transaction commits before the test continues.

### 4.1. INFERRED With Test Transactions

Test slices such as **`@DataJpaTest`** run test methods inside a transaction by default and roll back afterward. With `@Sql` set to `INFERRED`, the script normally joins the active test transaction.

Explicitly declaring the default mode:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-before.sql",
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.INFERRED
    )
)
~~~

Typical flow:

~~~text
Start test transaction
        |
        v
@Sql BEFORE_TEST_METHOD (INFERRED)
        |
        v
Test reads/writes data
        |
        v
Roll back test transaction
        |
        v
Fixtures in that transaction also roll back
~~~

This is usually the cleanest option for repository tests: fixtures and test modifications roll back together. Separate cleanup is unnecessary as long as all fixtures stay inside the test transaction with no independent commits.

Verify whether the test truly runs inside a transaction. Non-transactional test methods, or scripts configured to run independently, have a different data lifecycle.

### 4.2. ISOLATED With Separately Committed Fixtures

If fixtures must exist outside the test transaction, or scripts always need an isolated transaction, use `ISOLATED`:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-before.sql",
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.ISOLATED
    )
)
~~~

The script executes and commits in its own transaction. `@DataJpaTest`'s rollback does not delete committed fixtures. Therefore, provide a post-test cleanup script, also running isolated:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-after.sql",
    executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD,
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.ISOLATED
    )
)
~~~

`ISOLATED` requires an appropriate transaction manager. Use it only when a distinct transaction boundary is genuinely needed, and always include a cleanup plan.

### 4.3. Complete Test Example

The example below uses `@DataJpaTest`. Both scripts run in isolated transactions with post-test cleanup:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.test.context.jdbc.Sql;
import org.springframework.test.context.jdbc.SqlConfig;

@DataJpaTest
class PurchaseOrderRepositoryTest {

    @Autowired
    private PurchaseOrderRepository orders;

    @Test
    @Sql(
        scripts = "/sql/fixtures/order-before.sql",
        config = @SqlConfig(
            transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
    )
    @Sql(
        scripts = "/sql/fixtures/order-after.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD,
        config = @SqlConfig(
            transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
    )
    void findsKnownPendingOrder() {
        PurchaseOrder order = orders
            .findByOrderCode("fixture-order-01")
            .orElseThrow();

        assertEquals("PENDING", order.getStatus().name());
    }
}
~~~

Entity/repository imports and status enums depend on your application. The example assumes `PurchaseOrderRepository` has a derived query **`findByOrderCode`** and the `PENDING` status exists in the domain.

### 4.4. Fixture Script Contents

Seed script:

~~~sql
-- order-before.sql
DELETE FROM purchase_order
WHERE order_code = 'fixture-order-01';

DELETE FROM customer
WHERE customer_code = 'fixture-customer-01';

INSERT INTO customer (customer_code, name)
VALUES ('fixture-customer-01', 'Fixture Customer');

INSERT INTO purchase_order (order_code, customer_id, status)
SELECT
    'fixture-order-01',
    id,
    'PENDING'
FROM customer
WHERE customer_code = 'fixture-customer-01';
~~~

Cleanup script:

~~~sql
-- order-after.sql
DELETE FROM purchase_order
WHERE order_code = 'fixture-order-01';

DELETE FROM customer
WHERE customer_code = 'fixture-customer-01';
~~~

The example uses fixed business codes to locate and clean up data instead of assuming identity IDs always equal a specific number. `DELETE` statements clear child tables before parent tables to respect foreign keys. The `customer_code` and `order_code` columns must have `UNIQUE` constraints per the schema migration.

This is illustrative SQL targeting a compatible schema. If your database requires distinct identity, sequence, timestamp, or quoting syntax, adapt the script and test against that database.

## 5. Creating Deterministic Data

Deterministic test data means the same test with the same fixtures and settings runs on known inputs, independent of run time, test execution order, leftover data, or environment state.

Good fixtures should have:

- Distinct, recognizable business keys.
- Explicit statuses, amounts, timestamps, and associations.
- Insert/delete ordering respecting foreign keys.
- Required constraints created by migrations.
- Clear cleanup criteria.
- Zero reliance on data created by other tests.

### 5.1. Avoiding Time-Varying or Random Values

Values like these make tests unstable:

~~~sql
INSERT INTO event_log (event_name, created_at)
VALUES ('order-created', CURRENT_TIMESTAMP);
~~~

Or in Java:

~~~java
LocalDateTime createdAt = LocalDateTime.now();
UUID id = UUID.randomUUID();
~~~

These values fit production, yet make tests hard to reproduce. Tests can fail across midnight boundaries, timezone shifts, or when asserting random values whose results cannot be predicted beforehand.

In tests, use fixed values:

~~~java
Instant createdAt = Instant.parse("2026-01-15T10:30:00Z");
UUID id = UUID.fromString(
    "00000000-0000-0000-0000-000000000101"
);
~~~

For timestamps generated by Spring Data Auditing or services, inject a **`Clock`** and supply **`Clock.fixed(...)`** in tests. That lets tests control time rather than depending on the system clock.

You do not need to hard-code every ID if the application uses generated IDs. When testing business flows, look up records by stable business keys or capture the ID returned by creation. Only assign IDs manually when mappings and the database allow it safely.

### 5.2. Avoiding Assumptions About Data Order

SQL does not guarantee row order if a query omits **`ORDER BY`**. Never write tests expecting the first item to always be record A just because the script inserted A before B.

If order is a business requirement, repository queries must sort explicitly:

~~~java
List<PurchaseOrder> findByCustomerIdOrderByCreatedAtAsc(Long customerId);
~~~

When using `Pageable` or `Sort`, tests should verify the exact sort columns and directions rather than relying on physical storage order in the database.

### 5.3. Avoiding IDs Tied to Sequences or Identities

Do not write tests assuming the first insert always receives `ID = 1`. Sequences might not reset after rollbacks, databases can keep identity counters advancing across deletes, and parallel tests consume IDs in varying order.

Better practices:

- Read the ID from the persisted entity.
- Query using unique business keys.
- Only reset sequences/identities if a test specifically checks ID generation and reset scripts match the database.
- Never generate keys with `SELECT MAX(id) + 1`; two concurrent transactions can pick the same value.

## 6. Choosing Fixture Creation Tools: @Sql, Builders, or Repositories

Not every test needs SQL scripts.

| Data Creation Approach | Best Fit When | Points to Watch |
|---|---|---|
| **`@Sql`** | Needing exact database state, multiple tables, constraints, legacy data, or complex queries | Schema and dialect dependent; requires explicit transaction mode and cleanup |
| Test Data Builder / Object Mother | Testing domain or service logic with readable objects | Can bypass real mapping/constraint behavior if never persisted |
| Repository / `EntityManager` | Creating entities through JPA lifecycle and testing mappings, cascades, auditing | Must manage transactions, flush, clear, and relationship creation order |
| Migrations | Versioned schema changes or data migrations | Do not use as per-test fixtures |
| Testcontainers | Needing a production-like database engine | Must manage container startup time and resources |

A service test can use builders for domain objects, while a repository test can use `@Sql` to establish exact database state. Pick the tool matching what the test aims to prove.

## 7. Organizing Fixtures to Prevent Cross-Test Leakage

### 7.1. Using Distinct Data per Scenario

Avoid having multiple tests mutate the same shared record unnecessarily. Give each fixture its own key, for example:

- `fixture-customer-order-read`
- `fixture-customer-order-update`
- `fixture-customer-order-delete`

If a script reuses a fixed key and runs before each test, it must reset the database to a clean state before inserting. Still, cleaning by fixed keys is unsafe when multiple tests run in parallel against the same schema.

### 7.2. Parallel Test Execution

Suppose two tests concurrently run a script creating `order_code = fixture-order-01`. One test may delete or read data the other test is actively using; `UNIQUE` constraints can also fail one test.

Three ways to handle this:

1. Disable parallel execution for test groups sharing fixed fixtures.
2. Provision separate databases/schemas per test worker or test class.
3. Generate per-run fixture keys and pass them into scripts or fixture factories.

Do not assume tests run sequentially if JUnit, build tools, or CI have parallel execution enabled.

### 7.3. Cleaning Up in Relationship Order

When child tables reference parent tables via foreign keys, cleanup must delete children before parents. For example:

1. Delete `purchase_order_line`.
2. Delete `purchase_order_tag`.
3. Delete `purchase_order`.
4. Delete `customer`.

Do not disable foreign key constraints merely to simplify cleanup; constraints ensure fixtures reflect real database integrity.

## 8. SQL Fixtures and the JPA Persistence Context

`@Sql` executes SQL directly via JDBC. JPA does not automatically know rows changed via SQL if the persistence context already holds corresponding entities.

Example:

1. `Customer` entity was loaded and managed by `EntityManager`.
2. An SQL script updates `Customer`'s name.
3. Code continues reading the managed instance.
4. The persistence context can return the stale in-memory state.

When synchronization is needed after native SQL or bulk updates, consider:

~~~java
entityManager.flush();
entityManager.clear();
~~~

- **`flush()`** pushes pending JPA changes to the database before non-JPA SQL runs.
- **`clear()`** evicts managed entities so subsequent reads fetch fresh state from the database.

Do not call `clear` arbitrarily if you still need managed entities or have unflushed changes. With `@Sql` running before a test method, the test usually has not loaded entities into the persistence context yet; however, if a script runs mid-test, watch out for the first-level cache.

## 9. Testing Migrations and Fixtures

### 9.1. Testing Schema From Migrations

- Start an empty database.
- Apply all migrations from the initial version.
- Boot the application context and repositories.
- Verify required tables, columns, indexes, foreign keys, and unique constraints exist.
- Run basic JPA queries to expose mapping mismatches.

### 9.2. Testing Fixtures

- Execute seed scripts.
- Read data through repositories.
- Verify statuses, relationships, and query results.
- Run cleanup or rollback according to transaction mode.
- Re-run tests independently to confirm fixtures do not depend on prior runs.

### 9.3. Testing on the Appropriate Database

Testcontainers spins up a real database inside tests:

~~~java
@Testcontainers
@SpringBootTest
class PurchaseOrderIntegrationTest {
    // Configure datasource pointing to the container database.
}
~~~

Container and datasource declarations depend on the specific database. The goal is running the same or compatible engine as production to test migrations, constraints, timestamp types, identity/sequence behavior, and SQL syntax.

Tests running solely on H2 can miss dialect-related failures. You can keep a fast suite on a lightweight database, while validating critical flows on a real database.

## 10. Common Pitfalls

| Symptom | Cause | Fix |
|---|---|---|
| SQL script not found | Wrong classpath or relative path | Place files in `src/test/resources` and start paths with `/` |
| Fixture vanishes during test | Script joined test transaction and rolled back | Check `INFERRED`/`ISOLATED` and the test's transaction |
| Fixture persists after test | Script committed in an isolated transaction | Add `AFTER_TEST_METHOD` cleanup with matching transaction mode |
| Duplicate key on re-run | Seed did not clear old data or shared fixture key | Reset fixtures cleanly or use distinct keys |
| Foreign key violation during cleanup | Deleted parent table before child table | Delete in dependency order |
| Test passes on H2 but fails in production | SQL, type, or constraint differs across dialects | Run integration tests on matching production database |
| Timestamp values shift across runs | Used `now`/`current_timestamp` or system timezone | Use fixed timestamps and an injected `Clock` |
| Tests depend on execution order | Shared fixtures or incomplete cleanup | Make tests independent, use dedicated schemas or unique fixture keys |
| JPA returns stale data after `@Sql` | Persistence context holds old entity state | Flush as needed and clear before reading back |
| IDs change across runs | Identity/sequence does not reset on rollback | Never hard-code generated IDs; use returned IDs or business keys |

## 11. Fixture Management Checklist

- [ ] Migrations only describe schema changes or versioned data migrations.
- [ ] Test databases run the same migration chain required by the application.
- [ ] Fixtures reside in `src/test/resources` or dedicated test data factories.
- [ ] `@Sql` uses explicit classpath paths.
- [ ] Selected `INFERRED` or `ISOLATED` intentionally based on test transactions.
- [ ] Separately committed fixtures have matching cleanup scripts.
- [ ] Inserts run parent-before-child; deletes run child-before-parent.
- [ ] Data uses deterministic business keys, statuses, and timestamps.
- [ ] Tests do not rely on auto-generated IDs or unordered query output without `ORDER BY`.
- [ ] Parallel tests do not share conflicting fixture keys.
- [ ] SQL fixtures and migrations are tested on an appropriate database.
- [ ] After direct SQL operations, the persistence context is cleared when needed.

## 12. Key Takeaways

Migrations manage versioned schemas; fixtures prepare data for test scenarios. **`@Sql`** is a convenient way to run scripts before and after tests, provided you understand transaction modes: **`INFERRED`** can join the test transaction and roll back with the test; **`ISOLATED`** executes and commits in its own transaction, requiring explicit cleanup.

Deterministic data keeps tests repeatable. Fix business values and timestamps, avoid assuming IDs or row ordering, isolate fixtures across parallel tests, and verify against a database matching production.
