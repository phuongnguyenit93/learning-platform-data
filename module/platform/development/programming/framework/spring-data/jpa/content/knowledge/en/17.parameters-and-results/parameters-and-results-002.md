# Value Expressions in @Query and the Spring Data JPA entityName Variable

Spring Data JPA lets you use **SpEL (Spring Expression Language)** inside `@Query` to reference method parameters, access properties of input objects, and use special variables provided by Spring Data. One such variable is `#{#entityName}`, which allows a JPQL query in a generic repository to reference the exact entity managed by each concrete repository.

Distinguish between two forms of expressions:

- **Template expressions** such as `#{#entityName}` are substituted into the JPQL string to resolve the entity name.
- **Value expressions** such as `:#{#filter.status}` or `?#{[0]}` are evaluated to values and bound to query parameter positions.

SpEL is not a mechanism for arbitrarily concatenating user-supplied table names, column names, or SQL fragments. Use it to express values and entity metadata cleanly and safely.

This document uses Spring Data JPA with Jakarta Persistence in Spring Boot 3 or later. The examples are repository/service components requiring a Spring project configured with JPA, entities, and a database; they are not standalone programs run directly with `javac`.

## 1. JPQL in @Query and entity names

JPQL queries entity names and Java properties, not physical table or column names directly.

Example:

```java
@Entity
@Table(name = "purchase_order")
public class PurchaseOrder {
    @Id
    private Long id;

    private String status;
}
```

The default entity name is the class name `PurchaseOrder`. JPQL query:

```java
@Query("select p from PurchaseOrder p where p.status = :status")
List<PurchaseOrder> findByStatus(@Param("status") String status);
```

The SQL generated by the provider will use the `purchase_order` table according to the mapping, while JPQL uses `PurchaseOrder`.

You can customize the entity name:

```java
@Entity(name = "Purchase")
@Table(name = "purchase_order")
public class PurchaseOrder {
    // fields
}
```

Then JPQL uses `Purchase`:

```jpql
select p from Purchase p
```

`@Entity(name = ...)` defines the entity name in the persistence model. `@Table(name = ...)` defines the physical table name. These two values serve different layers.

## 2. What is the #{#entityName} variable?

Spring Data JPA provides the SpEL variable `entityName` in repository query expressions. The syntax used inside `@Query` strings is:

```java
@Query("select e from #{#entityName} e")
List<T> findAllEntities();
```

Spring Data replaces `#{#entityName}` with the entity name of the domain type managed by the repository.

Entity name resolution rules:

1. If the entity declares `@Entity(name = "SomeName")`, use `SomeName`.
2. If `@Entity` does not specify a name, use the simple class name of the entity.
3. This is the JPQL entity name, not the table name in `@Table`.

Example:

```java
@Entity(name = "Purchase")
@Table(name = "purchase_order")
public class PurchaseOrder {
    @Id
    private Long id;
}
```

Query:

```java
@Query("select p from #{#entityName} p")
List<PurchaseOrder> findAllDynamicEntityName();
```

When the repository manages PurchaseOrder, the expression resolves to the equivalent JPQL:

```jpql
select p from Purchase p
```

There is no need to hard-code the class name or entity name in a generic repository.

## 3. Why is entityName useful with generic repositories?

Suppose several entities share a `status` property. We want to write one reusable query across multiple repositories without repeating the entity name.

We can create a mapped superclass:

```java
@MappedSuperclass
public abstract class AuditedRecord {
    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private RecordStatus status;

    public RecordStatus getStatus() {
        return status;
    }

    public void setStatus(RecordStatus status) {
        this.status = status;
    }
}
```

Inheriting entities:

```java
@Entity
public class PurchaseOrder extends AuditedRecord {
    @Id
    @GeneratedValue
    private Long id;
}

@Entity
public class Shipment extends AuditedRecord {
    @Id
    @GeneratedValue
    private Long id;
}
```

Define the base repository:

```java
@NoRepositoryBean
public interface StatusRepository<T extends AuditedRecord, ID>
        extends JpaRepository<T, ID> {

    @Query("""
        select e
        from #{#entityName} e
        where e.status = :status
        """)
    List<T> findAllByStatus(
        @Param("status") RecordStatus status
    );
}
```

Concrete repositories:

```java
public interface PurchaseOrderRepository
        extends StatusRepository<PurchaseOrder, Long> {
}

public interface ShipmentRepository
        extends StatusRepository<Shipment, Long> {
}
```

When Spring Data creates PurchaseOrderRepository, `#{#entityName}` resolves to the entity name of PurchaseOrder. For ShipmentRepository, it resolves to the entity name of Shipment.

`@NoRepositoryBean` marks the generic interface as a base repository so no repository bean is created directly for the unresolved type. Concrete repositories extending it will have beans created by Spring Data.

Important requirement: the `status` property must exist in the persistence model of every entity using the base repository. A mapped superclass is a common way to share this property mapping. If an entity lacks that property, the query will be invalid when created or executed.

## 4. entityName is not a table name or column name

This is the most common misconception.

| Declaration | Purpose | Example |
|---|---|---|
| `@Entity(name = "Purchase")` | Entity name used in JPQL | `from Purchase p` |
| `@Table(name = "purchase_order")` | Physical table name | SQL `from purchase_order` |
| `@Column(name = "order_status")` | Physical column name | SQL `p.order_status` |
| `#{#entityName}` | Inserts entity name into JPQL template | `from #{#entityName} p` |

Do not use `#{#entityName}` expecting to get the table name `purchase_order`. When writing native SQL, use the physical table and column names matching the schema.

Correct example with JPQL:

```java
@Query("select p from #{#entityName} p where p.status = :status")
List<T> findByStatus(@Param("status") String status);
```

Native SQL example requiring the actual table name:

```java
@Query(
    value = "select * from purchase_order where order_status = ?1",
    nativeQuery = true
)
List<PurchaseOrder> findByPhysicalStatus(String status);
```

The `entityName` variable is not designed to substitute table names in native queries. Do not rely on it to generate dynamic SQL table identifiers.

## 5. SpEL value expressions in @Query

Beyond the entity name template, Spring Data JPA supports SpEL expressions to extract parameter values.

Named expression:

```java
@Query("""
    select u
    from User u
    where u.firstname = :#{#firstName}
    """)
List<User> findByFirstNameExpression(
    @Param("firstName") String firstName
);
```

`:{#firstName}` is evaluated from the method parameter named `firstName`, and the value is then bound to the query parameter.

Compare with a standard named parameter:

```java
@Query("""
    select u
    from User u
    where u.firstname = :firstName
    """)
List<User> findByFirstName(
    @Param("firstName") String firstName
);
```

If no expression is needed, the `:firstName` syntax is usually simpler. SpEL is useful when you need to access nested properties, compute values from parameters, or use special query variables.

## 6. Accessing parameters by name and by position

### 6.1. Named parameter expressions

Use `@Param` for explicit naming:

```java
@Query("""
    select p
    from Product p
    where p.category = :#{#category}
      and p.price >= :#{#minimumPrice}
    """)
List<Product> search(
    @Param("category") String category,
    @Param("minimumPrice") BigDecimal minimumPrice
);
```

This approach is easy to read when a method has multiple parameters. The name in SpEL must match the name declared in `@Param`.

If you rely on Java parameter names without declaring `@Param`, ensure compilation preserves parameter names (e.g., the `-parameters` compiler option) and that your Spring Data version can read them. To avoid build configuration dependencies, `@Param` is the explicit choice.

### 6.2. Positional parameter expressions

You can access arguments by 0-based index:

```java
@Query("""
    select u
    from User u
    where u.firstname = ?#{[0]}
      and u.lastname = ?#{[1]}
    """)
List<User> findByNames(String firstName, String lastName);
```

- `[0]` is the first parameter.
- `[1]` is the second parameter.

Do not confuse SpEL indices with JPQL positional parameters `?1`, which start at 1. For example, `?#{[0]}` accesses the first argument and binds its value to the query parameter position.

When a method has many parameters or frequently changing signatures, named expressions/`@Param` are easier to maintain.

## 7. Accessing nested properties of a parameter object

SpEL can read properties from a filter object:

```java
public record ProductFilter(
    String category,
    BigDecimal minimumPrice,
    Boolean active
) {}
```

Repository:

```java
@Query("""
    select p
    from Product p
    where p.category = :#{#filter.category}
      and p.price >= :#{#filter.minimumPrice}
      and p.active = :#{#filter.active}
    """)
List<Product> search(
    @Param("filter") ProductFilter filter
);
```

`#filter` references the method parameter, while `.category`, `.minimumPrice`, and `.active` access the corresponding properties.

If properties can be null, design appropriate predicates instead of assuming comparisons with NULL will return expected results.

Optional filter example:

```java
@Query("""
    select p
    from Product p
    where (:#{#filter.category} is null
           or p.category = :#{#filter.category})
      and (:#{#filter.active} is null
           or p.active = :#{#filter.active})
    """)
List<Product> searchOptionalFilters(
    @Param("filter") ProductFilter filter
);
```

When category or active is null, the corresponding first branch is true and that filter is skipped. For large queries with many optional filters, OR expressions can impair index usage. Consider Specification or dynamic queries when there are many condition combinations.

Also define the semantics of a null filter object. If `filter` itself is null, accessing `filter.category` may fail; validate input or handle that case in the service layer before calling the repository.

## 8. Using entityName together with SpEL parameters

Both expression forms can appear in the same query:

```java
@NoRepositoryBean
public interface SearchableRepository<T extends SearchableRecord, ID>
        extends JpaRepository<T, ID> {

    @Query("""
        select e
        from #{#entityName} e
        where e.code = :#{#code}
        """)
    Optional<T> findByCodeExpression(
        @Param("code") String code
    );
}
```

Here:

- `#{#entityName}` is a template expression to resolve the entity name.
- `:#{#code}` is a value expression to extract the parameter and bind it to the query.
- Alias `e` is the JPQL identification variable.
- `e.code` is an entity property, not an SQL column name.

This pattern is useful for generic repositories when multiple entities share a common property mapping.

## 9. Using SpEL with LIKE and wildcard escaping

String searching with LIKE requires attention to two wildcards:

- `%` matches zero or more characters.
- `_` matches exactly one character.

If the user enters `50%_off`, typically we want to search for the literal string containing percent/underscore characters, rather than treating them as wildcards.

Spring Data JPA provides the SpEL function `escape(String)` to escape standard SQL/JPQL wildcards `%` and `_` using the configured escape character:

```java
@Query("""
    select u
    from User u
    where u.firstname like %?#{escape([0])}%
    """)
List<User> findContainingLiteral(String input);
```

`escape([0])` escapes wildcard characters in the first argument before adding search wildcards on both ends.

You can retrieve the configured escape character via `escapeCharacter()`. If writing an explicit ESCAPE clause, verify the syntax against JPQL and your provider:

```java
@Query("""
    select u
    from User u
    where u.firstname like %?#{escape([0])}%
      escape ?#{escapeCharacter()}
    """)
List<User> findContainingLiteralWithEscape(String input);
```

Support for escape parameter syntax can depend on the provider/version; test the query against the target database. The `escape` function only handles standard `%` and `_` wildcards and does not guarantee escaping every database-specific character.

LIKE escaping does not replace parameter binding. Always bind input as a value; never concatenate input directly into the query string.

## 10. Value expressions cannot replace column names or keywords

Parameters and SpEL value expressions are used to pass values, for example:

```java
@Query("select p from Product p where p.price >= :#{#minimum}")
List<Product> findAtLeast(@Param("minimum") BigDecimal minimum);
```

You cannot use parameters to replace identifiers:

```java
// Does not work as expected:
@Query("select p from Product p order by :#{#sortProperty}")
List<Product> search(@Param("sortProperty") String sortProperty);
```

`:sortProperty` is bound as a value, not turned into a property name in ORDER BY. The database may treat it as a constant for every row, causing results not to be sorted by the desired column.

Likewise, you cannot bind table names, entity names, column names, or keywords such as `ASC`/`DESC` using value parameters.

If you need dynamic sorting, use Spring Data `Sort`/`Pageable` with allowed properties, or build a custom query with a whitelist:

```java
String orderExpression = switch (sortKey) {
    case "name" -> "p.name";
    case "price" -> "p.price";
    case "createdAt" -> "p.createdAt";
    default -> "p.id";
};
```

Only concatenate application-controlled identifiers from a whitelist. All data values must still use parameter binding. Never pass user-supplied sort strings or JPQL fragments directly into a query.

## 11. entityName and nativeQuery

`#{#entityName}` is for JPQL entity names. Native SQL uses physical tables and columns:

```java
@Query(
    value = "select * from purchase_order where order_status = ?1",
    nativeQuery = true
)
List<PurchaseOrder> findByStatusNative(String status);
```

Do not assume `#{#entityName}` turns into `purchase_order`. Entity names and table names are distinct; native SQL requires valid database schema identifiers.

Some versions of Spring Data JPA support SpEL value expressions in native queries for parameters, but that does not turn entityName into a table-name resolver. When using native SQL, check your version's documentation, syntax, and provider binding capabilities. If a query needs to be portable across databases, prefer JPQL when it meets the requirements.

## 12. Expressions in countQuery and pagination

Repositories can use `entityName` in both the data query and the count query:

```java
@Query(
    value = """
        select e
        from #{#entityName} e
        where e.status = :status
        """,
    countQuery = """
        select count(e)
        from #{#entityName} e
        where e.status = :status
        """
)
Page<T> findPageByStatus(
    @Param("status") RecordStatus status,
    Pageable pageable
);
```

The data query returns entities; the count query returns the total number of matching entities. The WHERE conditions of both queries must be equivalent, otherwise `totalElements` will be wrong.

If a query has collection JOINs, DISTINCT, GROUP BY, or complex subqueries, the count query may need to be written explicitly and tested. Do not assume Spring Data can always derive an accurate count query from every JPQL/native SQL query.

With Page, Spring Data may execute an additional count query. If you do not need the total page count, consider Slice to avoid the total-count cost.

## 13. Common errors

| Symptom | Cause | Solution |
|---|---|---|
| JPQL reports entity does not exist | Using table name or wrong class name instead of entity name | Check `@Entity(name)`; use entity name or `#{#entityName}` |
| Generic repository query fails on property | Concrete entity lacks property referenced by query | Use an appropriate mapped superclass/interface mapping or split repositories |
| `#{#entityName}` does not produce native table name | Confusing entity name with table name | Native SQL uses physical table/column names |
| SpEL cannot find parameter | `@Param` name and expression name do not match | Align names or use positional expressions |
| `?#{[0]}` picks wrong parameter | Confusing 0-based SpEL index with 1-based JPQL positional parameter | Recheck argument order |
| Expression reads null property | Filter object or nested property is null | Validate input, handle null, or use appropriate predicates |
| ORDER BY does not change with parameter | Parameter is bound as a value, not an identifier | Use Sort/Pageable or a whitelisted dynamic query |
| LIKE matches wildcards as special characters | Input was not escaped | Use `escape([0])` and check the ESCAPE clause |
| Native query does not recognize entityName | Entity name is not an SQL table name | Use physical table names in native SQL |
| Page count is wrong | Count query is not equivalent to data query | Write an explicit countQuery and test it |
| Query works on one provider but fails on another | Provider-dependent SpEL/native binding or functions | Use portable syntax when needed and test on the target provider/database |

## 14. Testing repositories with SpEL

Do not just verify that the query boots cleanly. Test actual results and edge cases:

- Generic repository inherited by at least two entities with different entity names.
- Entity with a custom `@Entity(name = "...")` still resolves properly.
- Named expression parameters receive the right values.
- Positional expressions `[0]` and `[1]` map in the right order.
- Nested filter properties handle nulls as required.
- LIKE escaping handles strings containing `%` and `_`.
- Native queries use physical table names and do not rely on entityName.
- Dynamic sorting only accepts whitelisted identifiers.
- Page content and countQuery return consistent results.
- Inputs containing quotes, special characters, and SQL-like strings cannot alter query structure.

Use `@DataJpaTest` with a production-compatible database or Testcontainers when queries depend on the dialect. Mocking repositories does not execute SpEL, the JPQL parser, or SQL and is therefore insufficient to verify mappings.

## 15. Guide to choosing syntax

| Need | Recommended syntax |
|---|---|
| JPQL query in a generic repository | `#{#entityName}` |
| Bind a named parameter | `:status` |
| Extract parameter value with SpEL | `:#{#status}` |
| Access nested object property | `:#{#filter.minimumPrice}` |
| Access argument by index | `?#{[0]}` |
| Escape LIKE wildcards | `escape([0])` |
| Sort by dynamic property | `Sort`/`Pageable` or whitelist |
| Query physical tables | Native SQL with actual table/column names |

If a query only needs a simple parameter, `:status` is clearer than `:#{#status}`. Use SpEL when you genuinely need expressions, nested objects, or the entityName variable.

## 16. Pre-production checklist for @Query with SpEL

- [ ] Are you writing JPQL or native SQL?
- [ ] Is the entity name customized with `@Entity(name)`?
- [ ] Are you confusing the entity name with `@Table(name)`?
- [ ] Does the generic repository have `@NoRepositoryBean`?
- [ ] Do all inheriting entities have the properties used by the query?
- [ ] Do `@Param` names match the expressions?
- [ ] Are positional SpEL indices properly 0-based?
- [ ] Can the object/nested properties be null?
- [ ] Are user values always bound rather than concatenated?
- [ ] Do dynamic sort/identifiers use a whitelist?
- [ ] Are LIKE wildcards properly escaped?
- [ ] Does the count query share the same predicates as the data query?
- [ ] Do integration tests run on the target provider and database?

## 17. Conclusion

`#{#entityName}` lets you write generic JPQL based on the repository's domain type and automatically resolves each concrete entity's name. It is most useful in generic repositories where the same query can serve multiple entities with shared mappings.

Expressions like `:#{#parameter}` and `?#{[0]}` extract values from method parameters or nested properties and bind them to the query. They do not replace table names, column names, or keywords. For native SQL, use physical table/column names; for dynamic sorting, use Sort/Pageable or whitelisted identifiers.

Keep queries readable by preferring regular named parameters when sufficient, limiting SpEL to cases that actually need it, and running integration tests on the real provider/database. That gives you reusability without making queries obscure or introducing input-handling vulnerabilities.
