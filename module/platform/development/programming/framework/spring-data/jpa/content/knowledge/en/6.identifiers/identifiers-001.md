# Natural Keys, Surrogate Keys, and Selection Criteria

## Objectives

After this lesson, you will be able to:

- Distinguish between a natural key and a surrogate key.
- Identify a candidate key, primary key, and alternate key in a data model.
- Map keys in JPA using `@Id`, `@GeneratedValue`, `@Column`, `@UniqueConstraint`, `@EmbeddedId`, and `@IdClass`.
- Choose an appropriate key based on stability, uniqueness, business scope, integration capability, and operational cost.
- Design `equals()` and `hashCode()` for an entity without causing bugs when the entity transitions from transient to persistent.
- Handle key changes, duplicate data, and migrations when a system already has data.

## 1. Identifier Keys in a Data Model

A record needs a way to be uniquely identified so that the database management system and the application can reference it. In relational data, a key is an attribute or set of attributes used to identify a row.

Several concepts need to be distinguished:

- **Candidate key**: a minimal set of attributes that can uniquely identify a row. A table may have multiple candidate keys.
- **Primary key (PK)**: the candidate key chosen as the main key of the table. Each relational table has only one primary key definition, even if that key consists of multiple columns.
- **Alternate key**: another candidate key that was not chosen as the primary key. It is usually protected by a unique constraint.
- **Foreign key (FK)**: a column or group of columns that references a uniquely guaranteed key of another table.
- **Natural key**: a key that has meaning in the business domain or the external world, such as a book's ISBN or an ISO country code.
- **Surrogate key**: a key created primarily to identify a record within the system, carrying no business meaning, such as an auto-incrementing number or a UUID.

Natural key and surrogate key describe the origin/meaning of a key. Primary key and alternate key describe the role of a key in the table structure. Therefore, a natural key can be chosen as the primary key or simply placed as an alternate key; a surrogate key is usually chosen as the primary key.

## 2. Natural Keys

A natural key is taken from business data that already has meaning independent of the database. Examples:

- An ISBN code identifying a book edition.
- A two-letter ISO country code identifying a country according to the corresponding standard.
- A product SKU code in a retail system, if the business guarantees this code is unique and does not change.
- A registration code or contract code, if business rules clearly define the scope and lifecycle of the code.

A good natural key typically has the following characteristics:

1. **Unique**: two different objects must not share the same key within the defined scope.
2. **Stable**: the value rarely or never changes during the object's lifecycle.
3. **Non-null**: the system can determine the key as soon as the object is created.
4. **Well-defined rules**: normalization rules, case sensitivity, whitespace handling, and uniqueness scope are clearly defined.
5. **Compact**: not overly long or spanning too many columns, which would make indexes and foreign keys heavy.

### Mutable Natural Keys

A name, email address, phone number, street address, or username may be unique at a given point in time, but it is not necessarily stable throughout the object's lifecycle.

For example, an email address can change when a user changes companies or updates their contact information. If the email is the primary key, changing the email requires updating every referencing foreign key, and can also affect caches, URLs, logs, integration events, and historical data.

You should not choose an attribute as a natural key just because it currently has a unique constraint. You need to ask whether the business guarantees that the value is immutable, and if it does change, how far the impact spreads.

### Uniqueness Scope

A code may be unique within each organization but not unique across the entire system. For example, employee code `E001` might appear in multiple companies.

In that case, the actual business key is the pair `(tenant_id, employee_code)`, not `employee_code` alone. This rule must be expressed with a unique constraint in the database and validation logic in the application.

## 3. Surrogate Keys

A surrogate key is generated by the system to identify a record. It carries no business meaning and is usually kept stable even when business attributes change.

Common forms:

- Auto-incrementing integers: `BIGINT`, identity column, or sequence.
- UUID: a 128-bit identifier that can be generated independently across multiple nodes.
- A technical code generated by the system via a custom mechanism, as long as it is unique and does not depend on mutable business data.

Example:

| id | sku | name |
|---:|---|---|
| 101 | BK-001 | Java Fundamentals |
| 102 | BK-002 | Spring Data JPA |

Here `id` is the surrogate primary key. `sku` is the product's natural key and is protected by a unique constraint. If the SKU changes through an allowed business process, foreign keys still reference `id` and do not need to be updated.

### Advantages

- Short, stable key that is convenient for foreign keys.
- Independent of business code naming rules.
- Easy to reference across tables when business data changes.
- Can be created before business data is finalized.
- UUIDs allow generating IDs across multiple services without requesting numbers from a central sequence.

### Costs and Limitations

- Requires a separate unique constraint to protect the natural key if required by the business.
- Sequential numeric IDs can reveal the relative order of records if exposed directly in an API; IDs must never be treated as an authorization mechanism or secret.
- UUIDs are larger than numeric keys, increasing index and foreign key sizes. Random UUIDs can cause index fragmentation depending on the database and storage format.
- For distributed systems, you must choose a UUID format and key generation strategy suited to the database, API, and sorting requirements.

A surrogate key does not eliminate the requirement to check for business duplicates. For example, two products still must not have the same SKU just because they have two different IDs.

## 4. Mapping Surrogate Keys and Natural Keys in JPA

A commonly suitable option for business entities is to use a surrogate key as `@Id` while placing the natural key in a separate column with a unique constraint.

The example below uses Java 17+, Jakarta Persistence, and Hibernate:

~~~java
package com.example.catalog;

import java.util.Locale;
import java.util.Objects;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;

@Entity
@Table(
    name = "products",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_products_sku",
        columnNames = "sku"
    )
)
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "sku", nullable = false, updatable = false, length = 40)
    private String sku;

    @Column(name = "name", nullable = false, length = 160)
    private String name;

    protected Product() {
        // Required by JPA
    }

    public Product(String sku, String name) {
        this.sku = normalizeSku(sku);
        this.name = Objects.requireNonNull(name, "name must not be null");
    }

    private static String normalizeSku(String value) {
        Objects.requireNonNull(value, "sku must not be null");
        String normalized = value.strip().toUpperCase(Locale.ROOT);
        if (normalized.isEmpty()) {
            throw new IllegalArgumentException("sku must not be blank");
        }
        return normalized;
    }

    public Long getId() {
        return id;
    }

    public String getSku() {
        return sku;
    }

    public String getName() {
        return name;
    }

    public void rename(String name) {
        this.name = Objects.requireNonNull(name, "name must not be null");
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) {
            return true;
        }
        if (!(other instanceof Product that)) {
            return false;
        }
        return sku != null && sku.equals(that.getSku());
    }

    @Override
    public int hashCode() {
        return Objects.hashCode(sku);
    }
}
~~~

In the example:

- `id` is the surrogate primary key, generated by the database on insert.
- `sku` is the natural key, normalized upon creation with no setter.
- `updatable = false` prevents Hibernate from including the SKU column in regular UPDATE statements.
- `uniqueConstraints` describes the table-level uniqueness constraint.
- `equals()` and `hashCode()` are based on SKU because the example assumes SKU is immutable and present as soon as the entity is created.

`updatable = false` is not a security constraint or a database-level immutability guarantee. Native SQL, migrations, or another application can still modify the column. Unique constraints and immutability rules need to be enforced at the database level along with business workflows.

A repository can look up by both ID and natural key:

~~~java
package com.example.catalog;

import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;

public interface ProductRepository extends JpaRepository<Product, Long> {

    Optional<Product> findBySku(String sku);
}
~~~

When saving, if the SKU is duplicated, the database rejects the insert or update according to the unique constraint. You can check beforehand using the repository to provide a friendly error message, but pre-checking does not replace the unique constraint because two concurrent transactions can still pass the check at the same time.

## 5. Entity equals() and hashCode()

This is a common source of bugs when choosing a natural key or a surrogate key.

A JPA entity has a lifecycle:

- **Transient**: a new object, not yet managed by a persistence context; an auto-generated ID is usually still null.
- **Managed/Persistent**: the entity is currently managed by an EntityManager; the ID may already be assigned.
- **Detached**: the entity has left the persistence context but still exists in memory.
- **Removed**: the entity is marked for deletion in the persistence context.

If `hashCode()` depends on an auto-generated ID, the hash value can change after persisting. If the entity was already placed in a `HashSet` before the ID was generated, finding or removing the element can fail because the element resides in the old bucket.

### When Using a Natural Key

Only use a natural key for `equals()` and `hashCode()` if that key is:

- Non-null as soon as the entity is created.
- Unique within the entity's scope.
- Immutable throughout the entire lifecycle.
- Normalized consistently across every code path that creates the entity.

The Product example above fits the assumption that SKU is immutable. If SKU can change, that implementation is no longer safe for hash-based collections.

### When Using a Generated Surrogate ID

Do not write `equals()` simply as `id == other.id` without considering the case where two new entities both have a null ID. Two transient objects without an ID are not the same entity.

A common strategy is:

- Two identical references are equal.
- Compare IDs only when both IDs are non-null.
- Use a hash code that remains stable throughout the entity's lifecycle.
- Handle provider proxies consistently.

Hibernate proxies can require careful consideration between `getClass()` and `instanceof`. If using APIs like `Hibernate.getClass()`, you must accept a dependency on Hibernate. There is no single `equals/hashCode` pattern that fits every entity; choose based on the domain's identity contract and test with proxies, transient, managed, and detached entities.

If an entity does not need value-based equality in collections or the domain, you can keep `Object`'s default identity equality. Do not auto-generate equals/hashCode for all fields using an IDE or Lombok `@Data`: doing so can pull lazy associations, collections, or mutable fields into the comparison, leading to unintended data loading, recursion, or unstable hashes.

## 6. Natural Key as Primary Key

There are cases where a natural key is genuinely stable, short, and standardized by a reliable standard or business rule. In those cases, it can be mapped directly with `@Id`.

For example, a countries table using the two-letter ISO code as the key:

~~~java
@Entity
@Table(name = "countries")
public class Country {

    @Id
    @Column(name = "country_code", length = 2, nullable = false)
    private String code;

    @Column(name = "name", nullable = false)
    private String name;

    protected Country() {
    }

    public Country(String code, String name) {
        this.code = code.strip().toUpperCase(Locale.ROOT);
        this.name = name;
    }

    public String getCode() {
        return code;
    }
}
~~~

A country code can be a good choice if the system adheres strictly to the ISO standard and has rules for handling deprecated codes, changes, or historical data. If a code can be reused or multiple versions over time need to be stored, you must model status/validity periods rather than assuming the code always represents an immutable object.

Do not use a natural key as a primary key simply because it is human-readable. A primary key is referenced by many tables and can become very expensive to change if business rules evolve.

## 7. Multi-Column Composite Natural Keys

A natural key can be a combination of multiple attributes. For example, an employee code that is only unique within each tenant:

`(tenant_id, employee_code)`

If the table still has a surrogate ID, you can keep the technical primary key and create a unique constraint for the natural key pair:

~~~java
@Entity
@Table(
    name = "employees",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_employee_tenant_code",
        columnNames = {"tenant_id", "employee_code"}
    )
)
public class Employee {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "tenant_id", nullable = false, updatable = false)
    private Long tenantId;

    @Column(name = "employee_code", nullable = false, updatable = false)
    private String employeeCode;

    protected Employee() {
    }
}
~~~

The unique constraint ensures that one tenant cannot have two employees with the same code. Two different tenants can still use the same employee_code.

### When to Use a Composite Primary Key?

If the combination of natural attributes is a stable identifier and fits all referencing relationships, JPA supports two main approaches:

- `@EmbeddedId`: encapsulates the key components into an `@Embeddable` class.
- `@IdClass`: declares a separate key class and marks the key fields directly on the entity with `@Id`.

Example with `@EmbeddedId`:

~~~java
@Embeddable
public class EmployeeKey implements java.io.Serializable {

    @Column(name = "tenant_id")
    private Long tenantId;

    @Column(name = "employee_code")
    private String employeeCode;

    protected EmployeeKey() {
    }

    public EmployeeKey(Long tenantId, String employeeCode) {
        this.tenantId = tenantId;
        this.employeeCode = employeeCode;
    }

    public Long getTenantId() {
        return tenantId;
    }

    public String getEmployeeCode() {
        return employeeCode;
    }

    @Override
    public boolean equals(Object other) {
        if (this == other) return true;
        if (!(other instanceof EmployeeKey that)) return false;
        return java.util.Objects.equals(tenantId, that.tenantId)
                && java.util.Objects.equals(employeeCode, that.employeeCode);
    }

    @Override
    public int hashCode() {
        return java.util.Objects.hash(tenantId, employeeCode);
    }
}

@Entity
@Table(name = "employees")
public class EmployeeWithCompositeId {

    @EmbeddedId
    private EmployeeKey id;

    @Column(name = "full_name", nullable = false)
    private String fullName;

    protected EmployeeWithCompositeId() {
    }
}
~~~

The key class must meet Jakarta Persistence requirements for a primary key class, including being serializable and implementing equals/hashCode based on the key values. The key fields must be fully assigned before persisting and must not change afterward.

A composite primary key makes referencing foreign keys more complex because child tables must store all key components. When the combination is long, has many relationships, or may change, a surrogate primary key plus a unique constraint is usually easier to operate.

## 8. Choosing a Surrogate Key Type: Long, Sequence, or UUID

JPA provides common ID generation strategies:

| Strategy | How It Works | Considerations |
|---|---|---|
| IDENTITY | Database generates ID on insert using identity/auto-increment | Simple; can limit JDBC insert batching because ID is only available after insert |
| SEQUENCE | Fetches ID from a database sequence before insert | Useful with PostgreSQL and databases supporting sequences; can allocate by allocation size |
| TABLE | Uses a table to allocate IDs | Has coordination overhead and is generally less preferred if the DB supports identity/sequence |
| UUID | Generates UUID via provider/JPA mechanism | Suitable when IDs need to be generated across multiple nodes; evaluate size and index characteristics |
| AUTO | Lets the provider choose the strategy | Convenient, but exact behavior depends on the provider and database |

Example using identity:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
~~~

Example using sequence:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "product_seq")
@SequenceGenerator(
    name = "product_seq",
    sequenceName = "product_id_seq",
    allocationSize = 50
)
private Long id;
~~~

`allocationSize` must be designed to be compatible with how the provider allocates numbers and the sequence configuration in the database. Hibernate can pre-allocate a block of IDs to reduce round trips; do not arbitrarily set mismatched values without checking the sequence configuration and generator strategy of your provider version.

Example using UUID with Jakarta Persistence 3.1 or later:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
private java.util.UUID id;
~~~

UUIDs can generate IDs without a central sequence. However, a UUID is not a security token and does not replace authorization. If index efficiency is needed, consider a native UUID storage type or an ordering format suited to your database.

## 9. Hibernate @NaturalId

Hibernate has a dedicated annotation `org.hibernate.annotations.NaturalId` to mark an attribute or group of attributes that serve as an entity's natural identifier.

Example:

~~~java
import org.hibernate.annotations.NaturalId;

@Entity
@Table(
    name = "products",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_products_sku",
        columnNames = "sku"
    )
)
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NaturalId
    @Column(nullable = false, updatable = false, length = 40)
    private String sku;

    protected Product() {
    }
}
~~~

`@NaturalId` is a Hibernate-specific feature, not part of Jakarta Persistence. It helps Hibernate understand which attribute is the natural identifier and can support natural-id lookups or natural-id caching when configured.

This annotation does not automatically replace a unique constraint in the database. The database still needs to enforce uniqueness to prevent duplicate data, even when multiple applications or concurrent transactions write to it.

If a natural ID can change, Hibernate has an option to represent a mutable natural ID. However, simply marking it mutable does not solve all business consequences: you must check caches, collections, references, history, and transactions. Prefer immutable natural keys whenever possible.

## 10. Criteria for Choosing Between Natural Key and Surrogate Key

There is no single choice for every table. Evaluate according to these criteria:

| Criterion | Natural key fits when | Surrogate key fits when |
|---|---|---|
| Stability | Business rules guarantee no change | Business attributes may change |
| Uniqueness | Clear standard or uniqueness rule exists | Source data lacks a stable key yet |
| Availability timing | Key already exists when creating the object | Business key is added later |
| Length | Short, simple key | Long key or composed of multiple columns |
| Relationships | Few references or very stable natural key | Many foreign keys need durable references |
| Integration | External code is highly stable | Multiple source systems or source codes may change |
| Distribution | Code is issued uniquely system-wide | UUID or technical ID can be generated independently |
| History | Code is never reused and lifecycle rules are clear | Need to store history when business code changes/is reused |

### Practical Guidelines

- Use a natural key as the primary key when the value is short, immutable, unique under a reliable rule, and all referencing relationships accept depending on it.
- Use a surrogate primary key when the entity has many relationships, business data may change, or the natural key is long/complex.
- Keep the natural key as an alternate key with a unique constraint when lookups or business-level duplicate prevention are needed.
- Use a composite key when the combination of columns is genuinely a stable identifier and referencing tables can cleanly manage the entire combination.
- For data imported from external systems, usually use an internal surrogate ID and a unique constraint on the pair `(source_system, external_id)`.

## 11. Migration When Changing Key Strategy

Changing the primary key on a system that already has data is a high-risk migration. You must review all foreign keys, indexes, sequences, API contracts, batch imports, caches, and integration data.

Example of migrating from natural primary key `employee_code` to surrogate `id`:

1. Add the `id` column to the table and create a value generation mechanism for existing rows.
2. Backfill IDs for all records, checking for no nulls and no duplicates.
3. Add a unique constraint for the ID and create necessary indexes.
4. Add the corresponding ID column to child tables, backfilling by joining on employee_code.
5. Add new foreign keys, verifying every child row has a parent record.
6. Deploy the application capable of reading/writing according to an appropriate transition model.
7. Switch foreign keys and queries to the ID; monitor consumers and reports.
8. Only after no consumers depend on the old key, consider dropping the old primary key/foreign keys.
9. Keep the unique constraint on the natural key if the business still requires non-duplicate codes.

Do not run a simple one-shot ALTER PRIMARY KEY when child tables, consumers, and historical data have not been migrated. For large systems, use an expand-and-contract strategy with rollback capability.

## 12. Verification and Testing

### Database Checks

- Primary key must be non-null and unique.
- Natural key has a unique constraint at the right scope.
- Foreign keys reference a column or combination of columns with guaranteed uniqueness.
- Indexes support lookup queries by natural key.
- Values are normalized consistently.

Example check for duplicate SKUs before adding a constraint:

~~~sql
SELECT sku, COUNT(*) AS total
FROM products
GROUP BY sku
HAVING COUNT(*) > 1;
~~~

For a tenant-scoped key:

~~~sql
SELECT tenant_id, employee_code, COUNT(*) AS total
FROM employees
GROUP BY tenant_id, employee_code
HAVING COUNT(*) > 1;
~~~

If the query returns rows, you must resolve duplicates and decide the canonical record before adding the unique constraint.

### JPA Testing

Integration tests should verify:

- Two entities with the same natural key cannot both be saved successfully.
- Lookup via repository method `findBySku` returns the correct entity.
- An entity saved and reloaded has the same identity according to the chosen rules.
- `equals()` and `hashCode()` are stable when the entity is in transient, managed, and detached states.
- If lazy proxies are used, comparisons do not produce asymmetric results or class cast errors.
- Composite keys have correct equals/hashCode and matching repository ID type.
- Foreign keys still reference correctly after migration.

A unique constraint is the last line of defense against concurrent writes. Checking with `existsBySku()` helps provide early messages, not eliminate race conditions between two transactions.

## 13. Common Design Mistakes

| Mistake | Consequence | Improvement |
|---|---|---|
| Using email as primary key even though email can change | Must update foreign keys and references in many places | Use a surrogate ID; keep email as a unique key if required by business |
| Checking duplicates only in service | Two concurrent transactions can still write duplicates | Create a unique constraint in the database |
| Using a reusable display code as a key | Historical records may be misreferenced | Define code lifecycle or use an internal ID |
| Using many columns as PK despite broad referencing relationships | Complex foreign keys and joins | Consider surrogate PK plus composite unique constraint |
| Relying on null ID for entity equality | Two different transient entities may be treated as equal | Design equals/hashCode around an identity contract |
| hashCode changes after persist | HashSet/HashMap fails to find entity in old bucket | Use an immutable key or a stable hash code |
| Using Lombok @Data on an entity | Lazy associations and collections enter equals/hashCode/toString | Write explicit getters, equals/hashCode, and appropriate toString |
| Assuming UUID is a security mechanism | Hard-to-guess IDs still do not prove access rights | Always enforce authorization at the business layer |
| Assuming unique annotation already created production constraint | Schema migration might not apply annotations | Manage constraints via migrations and verify the database |

## Pre-Merge Checklist

- [ ] Identified the entity's natural key and surrogate key.
- [ ] Uniqueness rules and uniqueness scope are clearly documented.
- [ ] Any natural key chosen as PK is genuinely immutable and stable.
- [ ] If using a surrogate PK, business natural keys have unique constraints where needed.
- [ ] Foreign keys reference a stable key and have appropriate indexes.
- [ ] equals/hashCode align with entity lifecycle and proxies.
- [ ] IDENTITY, SEQUENCE, UUID, or AUTO strategy is intentionally chosen.
- [ ] Migration handles legacy data, foreign keys, and consumers.
- [ ] Integration tests verify duplicates, lookups, identity, and relationships.

## Conclusion

A natural key describes an identifier with business meaning; a surrogate key is a technical identifier generated by the system. A natural key should only be a primary key when it is short, unique, and stable throughout the entire data lifecycle. For many business entities, a surrogate primary key combined with a unique constraint on the natural key makes foreign keys and migrations easier to manage. In JPA, key decisions also affect `equals()`, `hashCode()`, ID generation, and repositories. Protect uniqueness in the database, test the entity lifecycle, and choose keys based on real business rules.
