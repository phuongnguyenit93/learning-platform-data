# Querying by Equality, Comparison, Ranges, and Time in Spring Data JPA

## Learning objectives

After this lesson, you will be able to write derived query methods in `JpaRepository` to:
- Find records whose property **equals / differs from** a value, or is `null`.
- Compare **greater than, less than, with or without equality** on numbers and ordered data types.
- Filter values **within a range** using `Between` or two boundary conditions.
- Filter by **date, timestamp, before / after a point in time**, including querying a full day in a specific time zone.
- Check open / closed bounds, parameter types, and how to read method names to avoid wrong results.

Scope of this lesson: **Spring Data JPA – derived query methods**. Examples are based on entity fields, not SQL column names.

## 1. How does Spring Data JPA derive queries from method names?

Declare an interface extending `JpaRepository<Entity, Id>`; Spring Data JPA reads the keywords after `By` in the method name, resolves entity property paths, and generates the corresponding query. You do not need to write SQL manually for these simple conditions.

```java
public interface PurchaseOrderRepository extends JpaRepository<PurchaseOrder, Long> {
    List<PurchaseOrder> findByStatus(String status);
    List<PurchaseOrder> findByTotalGreaterThan(BigDecimal lowerBound);
}
```

Approximate equivalent meaning:

```sql
SELECT * FROM purchase_orders WHERE status = ?;
SELECT * FROM purchase_orders WHERE total > ?;
```

This is **illustrative SQL showing intent**; actual SQL is generated by the Hibernate/JPA provider and may differ in aliases, syntax, or parameter types. The `?` placeholder represents a bound parameter, not direct string concatenation of user values into SQL.

How to read `findByTotalGreaterThan`: `find...By` (query action) + `Total` (Java property `total`) + `GreaterThan` (`>` operator). Property names must match the entity, including nested property paths. Argument types must be compatible with property types.

## 2. Equality, inequality, and NULL conditions

Suppose an entity has a `String status` property:

| Method | Condition meaning |
| --- | --- |
| `findByStatus("PAID")` | `status = 'PAID'` |
| `findByStatusIs("PAID")` or `findByStatusEquals("PAID")` | Same meaning as `findByStatus` |
| `findByStatusNot("PAID")` | `status <> 'PAID'` |
| `findByStatusIsNull()` | `status IS NULL` |
| `findByStatusIsNotNull()` | `status IS NOT NULL` |
| `findByStatusIgnoreCase("paid")` | Case-insensitive string comparison as supported by Spring Data JPA |
| `findByStatusIn(Collection<String> statuses)` | `status IN (...)`; accepts a collection of allowed values |

Signature examples:

```java
List<PurchaseOrder> findByStatus(String status);
List<PurchaseOrder> findByStatusNot(String status);
List<PurchaseOrder> findByStatusIgnoreCase(String status);
List<PurchaseOrder> findByStatusIn(Collection<String> statuses);
```

**Note on `null`:** With equality operators (`Is` / `Equals` / no operator), Spring Data JPA generates `IS NULL` when the parameter is `null`; with `Not` and a `null` argument, it generates `IS NOT NULL`. However, in business APIs, prefer `IsNull` / `IsNotNull` methods to state intent explicitly. A `null` value **does not mean** “skip the filter”. For comparison operators and `Between`, validate parameters before querying; do not use `null` to arbitrarily disable a bound.

If a column is declared `nullable = false` like the runnable example at the end of this lesson, an `IsNull` query is still syntactically valid but will normally return no records.

## 3. Greater than and less than comparisons: understanding boundaries accurately

For `BigDecimal total`, the key operators are:

| Method | Equivalent condition | Includes boundary value? |
| --- | --- | --- |
| `findByTotalGreaterThan(x)` | `total > x` | No |
| `findByTotalGreaterThanEqual(x)` | `total >= x` | Yes |
| `findByTotalLessThan(x)` | `total < x` | No |
| `findByTotalLessThanEqual(x)` | `total <= x` | Yes |
| `findByTotalBetween(a, b)` | `total BETWEEN a AND b` | Includes both `a` and `b` |

Example with order totals `80, 90, 120, 200`:
- `GreaterThan(120)` returns `200`; `GreaterThanEqual(120)` returns `120, 200`.
- `LessThan(90)` returns `80`; `LessThanEqual(90)` returns `80, 90`.
- `Between(80, 120)` returns `80, 90, 120`. In SQL/JPQL, `BETWEEN` is **inclusive on both ends**.
- `Between(120, 80)` does not automatically swap the bounds. Validate `a <= b` before calling.

Use `BigDecimal` for money or decimal numbers requiring precision; avoid comparing money with `double` if business rules require decimal accuracy. For floating-point numbers, database data types, scale, and rounding can also affect results.

## 4. Range filtering: closed, open, and half-open intervals

There are three common forms:

- **[a, b] – closed on both ends:** `findByTotalBetween(a, b)`.
- **(a, b) – open on both ends:** `findByTotalGreaterThanAndTotalLessThan(a, b)`.
- **[a, b) – start inclusive, end exclusive:** `findByTotalGreaterThanEqualAndTotalLessThan(a, b)`.

```java
List<PurchaseOrder> findByTotalGreaterThanAndTotalLessThan(
        BigDecimal lowerExclusive, BigDecimal upperExclusive);

List<PurchaseOrder> findByTotalGreaterThanEqualAndTotalLessThan(
        BigDecimal lowerInclusive, BigDecimal upperExclusive);
```

`And` joins two conditions with logical AND. Each condition on the same `total` property has its own parameter, in the **exact order of appearance** in the method name. There are no short `Gte` or `Lte` keywords in standard derived query syntax; use `GreaterThanEqual` and `LessThanEqual`.

When filtering by range, standardize input rules: `min <= max`; decide whether the upper bound is included; check negative numbers, zero, and equal-boundary edge cases. A half-open interval `[start, end)` is particularly useful for partitioning data into contiguous ranges without double-counting timestamps on the boundary.

## 5. Date and time conditions

JPA supports mapping common `java.time` types:
- `LocalDate`: **calendar date**, without time-of-day or time zone; suitable for transaction dates, birth dates.
- `LocalDateTime`: date and time **without time zone/offset information**; requires an explicit time zone convention when tied to a real point in time.
- `Instant`: **point on the UTC timeline**; suitable for record creation/update timestamps when systems operate across multiple time zones.
- `OffsetDateTime`: includes an offset; check provider and database column type for exact storage and comparison behavior.

Corresponding query names:

```java
List<PurchaseOrder> findByOrderDate(LocalDate day);
List<PurchaseOrder> findByOrderDateBefore(LocalDate day);
List<PurchaseOrder> findByOrderDateAfter(LocalDate day);
List<PurchaseOrder> findByOrderDateBetween(LocalDate first, LocalDate last);
List<PurchaseOrder> findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(
        Instant startInclusive, Instant endExclusive);
```

`Before(x)` means **less than** `x`, equivalent to `<`; `After(x)` means **greater than** `x`, equivalent to `>`. Neither **includes the exact boundary**. If you need to include the boundary, use `LessThanEqual` or `GreaterThanEqual`. With `LocalDate`, `Between(2026-01-01, 2026-01-31)` includes both January 1 and January 31; parameters must be `LocalDate`, not arbitrary formatted strings.

### Querying *an entire day* when the column stores Instant

A day in Vietnam does not coincide with a UTC day. To find all records created on `2026-01-02` in Vietnam time, convert the two **local day starts** to `Instant` and query `[start, nextStart)`:

```java
ZoneId zone = ZoneId.of("Asia/Ho_Chi_Minh");
LocalDate day = LocalDate.of(2026, 1, 2);

Instant start = day.atStartOfDay(zone).toInstant();
Instant end = day.plusDays(1).atStartOfDay(zone).toInstant();

List<PurchaseOrder> result =
        repository.findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(start, end);
```

Import `java.time.ZoneId`, `LocalDate`, and `Instant` accordingly. The two bounds are `2026-01-01T17:00:00Z` (inclusive) and `2026-01-02T17:00:00Z` (exclusive). Using `day.plusDays(1).atStartOfDay(zone)` also handles time zones with daylight saving transitions where days are longer or shorter than 24 hours. Do not construct the end of day using `23:59:59` or `23:59:59.999`: stored data may have microsecond/nanosecond precision and get missed. Also do not use `Between(start, end)` to represent a half-open day because `Between` would include `end`.

If the business requires a **UTC day** instead of a Vietnam day, use bounds `2026-01-02T00:00:00Z` to `2026-01-03T00:00:00Z`; these are two queries with different result sets. The time zone must be determined from product requirements before conversion.

**`src/main/java/com/example/demo/PurchaseOrder.java`**

```java
package com.example.demo;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import java.math.BigDecimal;
import java.time.Instant;
import java.time.LocalDate;

@Entity
@Table(name = "purchase_orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String status;

    @Column(nullable = false, precision = 12, scale = 2)
    private BigDecimal total;

    @Column(nullable = false)
    private LocalDate orderDate;

    @Column(nullable = false)
    private Instant createdAt;

    protected PurchaseOrder() {
        // JPA requires a no-arg constructor, at least protected.
    }

    public PurchaseOrder(String status, BigDecimal total,
                         LocalDate orderDate, Instant createdAt) {
        this.status = status;
        this.total = total;
        this.orderDate = orderDate;
        this.createdAt = createdAt;
    }

    public Long getId() { return id; }
    public String getStatus() { return status; }
    public BigDecimal getTotal() { return total; }
    public LocalDate getOrderDate() { return orderDate; }
    public Instant getCreatedAt() { return createdAt; }
}
```

**`src/main/java/com/example/demo/PurchaseOrderRepository.java`**

```java
package com.example.demo;

import java.math.BigDecimal;
import java.time.Instant;
import java.time.LocalDate;
import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;

public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {

    List<PurchaseOrder> findByStatus(String status);

    List<PurchaseOrder> findByTotalGreaterThan(BigDecimal value);

    List<PurchaseOrder> findByTotalBetween(BigDecimal min, BigDecimal max);

    List<PurchaseOrder> findByOrderDateBetween(LocalDate from, LocalDate to);

    List<PurchaseOrder> findByCreatedAtAfter(Instant instant);

    List<PurchaseOrder> findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(
            Instant fromInclusive, Instant toExclusive);

    List<PurchaseOrder> findByStatusAndTotalGreaterThanEqual(
            String status, BigDecimal min);
}
```

**`src/main/java/com/example/demo/DemoApplication.java`**

```java
package com.example.demo;

import java.math.BigDecimal;
import java.time.Instant;
import java.time.LocalDate;
import java.util.List;
import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @Bean
    CommandLineRunner demo(PurchaseOrderRepository repository) {
        return args -> {
            repository.saveAll(List.of(
                order("PAID", "120.00", "2026-01-01", "2026-01-01T00:00:00Z"),
                order("PAID", "200.00", "2026-01-02", "2026-01-02T12:00:00Z"),
                order("NEW",  "80.00", "2026-01-02", "2026-01-02T23:59:59Z"),
                order("PAID",  "90.00", "2026-01-03", "2026-01-03T00:00:00Z")
            ));

            Instant start = Instant.parse("2026-01-02T00:00:00Z");
            Instant end = Instant.parse("2026-01-03T00:00:00Z");

            System.out.println("PAID=" +
                    repository.findByStatus("PAID").size());
            System.out.println("TOTAL_GT_100=" +
                    repository.findByTotalGreaterThan(new BigDecimal("100")).size());
            System.out.println("TOTAL_80_TO_120=" +
                    repository.findByTotalBetween(
                            new BigDecimal("80"), new BigDecimal("120")).size());
            System.out.println("ORDER_DATE_JAN_2=" +
                    repository.findByOrderDateBetween(
                            LocalDate.of(2026, 1, 2),
                            LocalDate.of(2026, 1, 2)).size());
            System.out.println("UTC_DAY_JAN_2=" +
                    repository.findByCreatedAtGreaterThanEqualAndCreatedAtLessThan(
                            start, end).size());
            System.out.println("AFTER_UTC_START=" +
                    repository.findByCreatedAtAfter(start).size());
            System.out.println("PAID_MIN_100=" +
                    repository.findByStatusAndTotalGreaterThanEqual(
                            "PAID", new BigDecimal("100")).size());
        };
    }

    private static PurchaseOrder order(
            String status, String total, String day, String timestamp) {
        return new PurchaseOrder(
                status,
                new BigDecimal(total),
                LocalDate.parse(day),
                Instant.parse(timestamp));
    }
}
```

## 7. Combining conditions, sorting, and pagination

You can combine conditions clearly:

```java
List<PurchaseOrder> findByStatusAndTotalGreaterThanEqual(
        String status, BigDecimal min);

List<PurchaseOrder> findByStatusOrTotalLessThan(
        String status, BigDecimal limit);

List<PurchaseOrder> findByOrderDateBetweenOrderByTotalDesc(
        LocalDate start, LocalDate end);
```

`And` and `Or` map to AND/OR; when mixing both, check precedence logic and use `@Query` or `Specification` if complex grouping parentheses are needed so readers do not misunderstand. `OrderByTotalDesc` fixes descending order by `total`.

For large result sets, use pagination and sorting as needed:

```java
Page<PurchaseOrder> findByStatusAndOrderDateBetween(
        String status, LocalDate start, LocalDate end, Pageable pageable);
```

Invocation example (also import `org.springframework.data.domain.Page`, `PageRequest`, `Pageable`):

```java
Pageable firstPage = PageRequest.of(0, 20);
Page<PurchaseOrder> page = repository.findByStatusAndOrderDateBetween(
        "PAID", LocalDate.of(2026, 1, 1),
        LocalDate.of(2026, 1, 31), firstPage);
```

`PageRequest.of(0, 20)` fetches the **first** page with at most 20 elements; page indices start at 0. When stable ordering across pages is needed, add a `Sort` with a tie-breaking column (such as `id`) or an appropriate pagination approach.

## 8. Common mistakes and how to check

1. **Confusing column names with property names:** If the entity has `orderDate`, use `findByOrderDateBetween`, not the SQL name `order_date` in the method name. Mismatched names usually cause Spring Data to fail query creation during repository initialization.
2. **Confusing `>` with `>=` or `Before` with `<=`:** Test with data sitting *right on the boundary*, not only inside the interval.
3. **Using `Between` for a full day of `Instant`:** `Between` includes the end timestamp; prefer `GreaterThanEqualAndLessThan` with the start of the next day.
4. **Wrong time zone:** A day in Vietnam and a UTC day differ. Convert using the `ZoneId` matching business requirements before comparing timestamps.
5. **Passing strings to date parameters:** Methods accepting `LocalDate` / `Instant` should convert inputs using `LocalDate.parse(...)` or `Instant.parse(...)` and handle invalid input at the boundary layer (controller/service).
6. **Reversing start and end of a range:** Validate `start <= end` before calling the repository; do not expect `Between` to fix reversed bounds.
7. **Assuming `null` means no filter:** Clarify whether `IS NULL` is desired or whether dynamic query building is needed. For multiple optional filters, consider `JpaSpecificationExecutor`, Criteria API, or an explicit `@Query`.
8. **Querying too many rows:** Use `Pageable` or an appropriate result limit, select only needed fields, and add indexes for frequently used filter/sort conditions after measuring real queries. Indexes can increase write overhead, so evaluate the trade-off.

## 9. Self-practice

Using the 4 orders in the example, predict the results before running:
- Find `PAID` orders with `total <= 100`: what is the method name? How many orders?
- Find orders with `orderDate < 2026-01-03`: how many orders?
- Filter records created on **2026-01-02 in Vietnam time**: does it match the result set of `UTC_DAY_JAN_2`?

Answers:
- `findByStatusAndTotalLessThanEqual("PAID", new BigDecimal("100"))` → **1** order (`90`).
- `findByOrderDateBefore(LocalDate.of(2026, 1, 3))` → **3** orders (Jan 1 and the two Jan 2 orders).
- Vietnam time range converted to UTC: `[2026-01-01T17:00:00Z, 2026-01-02T17:00:00Z)` → **1** order (`2026-01-02T12:00:00Z`); whereas the UTC day has **2** orders.

**Key takeaways:** Equality/inequality uses `Is`, `Equals`, `Not`; inequalities use `GreaterThan` / `LessThan` and their `Equal` variants; `Between` is a closed interval; `Before` / `After` exclude the boundary; for a full calendar day over timestamps, typically choose a half-open interval after time-zone conversion.
