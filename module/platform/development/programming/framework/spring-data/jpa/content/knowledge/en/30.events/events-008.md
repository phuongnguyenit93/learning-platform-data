# Limitations of In-Memory Event Delivery

Spring Data JPA supports publishing domain events from aggregate roots when appropriate repository operations are invoked. This is convenient for notifying other components within the same application that a business change has occurred. However, the default event publishing mechanism relies on application memory and Spring's application event mechanism. It is neither a durable queue nor a distributed messaging system.

Understanding these boundaries helps you choose the right approach: use in-memory events for lightweight internal coordination, use transaction-bound listeners when waiting for transaction commit, and use a transactional outbox or message broker when losing events is unacceptable.

## 1. What is a domain event in Spring Data?

A domain event is a message representing something meaningful in the business domain that has occurred, such as:

- An order has been confirmed.
- A payment has completed.
- An account has been locked.
- A profile has been approved.

Events typically describe what happened using past-tense names, such as `OrderConfirmed`, rather than commands like `ConfirmOrder`. A command expresses an intent requesting a change; an event represents the resulting business fact.

In Spring Data, an aggregate root can publish events using `@DomainEvents` and clear published events using `@AfterDomainEventPublication`. The utility class `AbstractAggregateRoot` already implements storing events in an internal collection, provides `registerEvent(...)` for aggregates to register events, and clears events automatically after publication.

Spring Data's repository proxy publishes registered domain events when supported repository operations are called, such as `save`, `saveAll`, `delete(entity)`, and `deleteAll(entities)`. This does not mean every database-modifying statement emits events automatically.

## 2. Registering events from an aggregate root

Example of an order that can only be completed once paid:

```java
package com.example.order;

public record OrderCompleted(Long orderId) {
}
```

The aggregate root registers an event upon a valid state transition:

```java
package com.example.order;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;

import org.springframework.data.domain.AbstractAggregateRoot;

@Entity
public class PurchaseOrder
        extends AbstractAggregateRoot<PurchaseOrder> {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    protected PurchaseOrder() {
    }

    public void complete() {
        if (status != OrderStatus.PAID) {
            throw new IllegalStateException(
                    "Only paid orders can be completed");
        }

        status = OrderStatus.COMPLETED;
        registerEvent(new OrderCompleted(id));
    }
}
```

`registerEvent` stores the event in the aggregate root's memory. It does not yet write the event to a table or send it to a message broker. When the repository saves the aggregate, Spring Data retrieves registered events and publishes them through Spring's application event mechanism.

The example above assumes the order was already saved and has an ID before `complete()` is called. If the ID is only generated by the database on INSERT, do not build an event payload with a null ID before persisting; design registration timing or event data so the ID is ready.

Repository:

```java
package com.example.order;

import org.springframework.data.jpa.repository.JpaRepository;

public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {
}
```

Service modifying the aggregate and calling the repository:

```java
package com.example.order;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final PurchaseOrderRepository repository;

    public OrderService(PurchaseOrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void complete(Long orderId) {
        PurchaseOrder order = repository.findById(orderId)
                .orElseThrow();

        order.complete();
        repository.save(order);
    }
}
```

When `save(order)` is called, Spring Data publishes the events registered on the aggregate. The service method wraps both the entity change and repository operation in a transaction. When the event is published and when the transaction commits are two distinct milestones; the next section explains how to bind listeners to the transaction.

## 3. Receiving events in the same application

You can use `@EventListener` to receive Spring application events:

```java
package com.example.notification;

import com.example.order.OrderCompleted;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;

@Component
public class OrderNotificationListener {

    @EventListener
    public void handle(OrderCompleted event) {
        System.out.println(
                "Order completed: " + event.orderId());
    }
}
```

With default configuration, Spring application event listeners run synchronously on the event-publishing thread. This means the repository call may wait for the listener to finish. If the listener throws an exception, that exception can propagate back to the publisher and affect the ongoing flow.

This fits lightweight, fast internal reactions that can run within the same process. Examples include updating an in-memory component, writing application logs, or triggering an internal step that does not need independent delivery durability.

Avoid using a synchronous listener for slow network operations if doing so prolongs transactions or requests. Also do not assume an event was successfully delivered externally simply because publishing returned without error.

## 4. Distinguishing publish time and commit time

A common source of confusion is that the repository publishes domain events right after the repository method is called, while the outer transaction may still be uncommitted. For example, the service above has `@Transactional`; when `repository.save(order)` emits the event, `complete()`'s transaction is still running.

If a listener uses `@EventListener`, it may run before the database commits. When the listener sends an email or calls an external API and the transaction subsequently rolls back, the external system has already received a notification for an unsaved change.

When handling must run only after transaction commit, use `@TransactionalEventListener`:

```java
package com.example.notification;

import com.example.order.OrderCompleted;
import org.springframework.stereotype.Component;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

@Component
public class OrderCompletedListener {

    @TransactionalEventListener(
        phase = TransactionPhase.AFTER_COMMIT
    )
    public void handle(OrderCompleted event) {
        // Process after the event-publishing transaction has committed.
    }
}
```

Main phases include:

- `BEFORE_COMMIT`: runs before the transaction commits.
- `AFTER_COMMIT`: runs after successful commit; this is the default phase.
- `AFTER_ROLLBACK`: runs after the transaction rolls back.
- `AFTER_COMPLETION`: runs after the transaction completes, whether committed or rolled back.

If there is no active transaction, transactional event listeners are not invoked by default. You can enable `fallbackExecution = true` if business rules genuinely require running even without a transaction, though be aware the listener is no longer guaranteed to correspond to a commit.

`@TransactionalEventListener` solves execution timing relative to the transaction. It does not turn in-memory events into durable data.

## 5. Why can in-memory events be lost?

The aggregate root domain event mechanism keeps events in an in-memory collection. The Spring application event publisher delivers events to listeners within the same application context. This mechanism does not automatically persist an independent event record in a database or broker.

Key limitations:

1. **Application stop or crash:** unprocessed events sitting in memory are lost when the process terminates.
2. **No durable queue:** by default there is no table storing pending events, retry state, or replay mechanism after restart.
3. **No automatic cross-instance distribution:** an event published in one process's application context does not automatically appear in another instance's context.
4. **No independent delivery guarantees:** Spring application events do not natively provide acknowledgments, durable retries, or exactly-once delivery.
5. **Listeners can fail:** synchronous listeners can throw exceptions; post-commit listeners can fail after data has committed and cannot roll back the original transaction.
6. **The aggregate's event queue is also in memory:** `AbstractAggregateRoot` clears events after publishing. This clearing happens during the publish flow, before any enclosing transaction has necessarily committed. If the transaction later rolls back, `AFTER_COMMIT` listeners do not run, while events on the aggregate have already been cleared.

Thus, internal events are an in-process notification mechanism, not a recoverable event log. If you must ensure database changes and outbound messages are recorded together, a design with durable storage is needed.

## 6. Operations that do not automatically emit domain events

Spring Data publishes domain events through repository infrastructure when supported methods are called on aggregate roots. Do not generalize this mechanism to every data write operation.

Cases that typically do not trigger the aggregate root domain event flow automatically:

- JPQL bulk `UPDATE` or `DELETE` declared with `@Modifying`.
- Direct native SQL execution.
- Updates using `EntityManager` or JDBC without going through a repository proxy that supports event publishing.
- Custom repository methods not handled by the event publishing infrastructure.
- Deletions passing only an ID, where no aggregate instance exists from which to read registered events.

Bulk operations act directly on the database and skip loading, calling business methods, and running individual aggregate lifecycles. If events are needed for such operations, the application must explicitly create and emit appropriate events or record them in a durable mechanism.

## 7. When to use a Transactional Outbox?

If a business change must result in a message sent to another system—for example, sending order details to a shipping service or publishing a payment notification to a message broker—relying only on in-memory events can leave a gap between the database and the receiving system.

The transactional outbox closes this gap by writing business changes and an event record in the same database transaction:

1. Update the aggregate inside the transaction.
2. Insert a row into the `outbox_event` table with event ID, event type, aggregate ID, payload, and creation timestamp.
3. Commit the transaction. If it rolls back, both business changes and the outbox row roll back.
4. A separate publisher reads unsent rows and forwards them to the broker.
5. Upon successful delivery, the publisher marks the row sent or updates processing status. On failure, it can retry according to policy.

Conceptual schema example:

| Column | Purpose |
|---|---|
| `event_id` | Unique ID for identification and deduplication |
| `aggregate_id` | ID of the aggregate producing the event |
| `event_type` | Event type |
| `payload` | Serialized event data |
| `created_at` | Event creation timestamp |
| `published_at` | Timestamp when publisher confirmed delivery; nullable while pending |

An outbox ensures business changes and event-emission intent are saved atomically in the same database transaction. It does not by itself guarantee the broker receives each message only once: the publisher may send successfully and fail before marking the row sent, resulting in redelivery. Therefore consumers must be idempotent, such as storing processed `event_id` values and ignoring duplicates.

A transactional outbox fits when losing events is unacceptable, crash recovery/retries are needed, or cross-service communication is required. For simple internal needs within a single process, Spring application events are usually simpler.

## 8. Choosing a mechanism by requirement

| Requirement | Approach |
|---|---|
| Fast reaction inside the same application, no event persistence needed | `@EventListener` |
| Run listener only when transaction commits successfully | `@TransactionalEventListener(AFTER_COMMIT)` |
| Run logic when transaction rolls back | `@TransactionalEventListener(AFTER_ROLLBACK)` |
| Send durable messages to a broker or another service | Transactional outbox combined with a message broker |
| Reprocessing, deduplication, and delivery status tracking | Outbox/inbox, event IDs, and idempotent consumers |

Do not adopt an outbox merely because an application uses domain events. Choose based on the business consequences if an event is lost, duplicated, or processed late.

## 9. Common mistakes and how to test

- **Assuming `registerEvent` persisted the event to the database:** this method only registers the event inside the aggregate root. For durability, persist events to a table or broker through a controlled workflow.
- **Using `@EventListener` for external side effects before commit:** the listener can run and then the transaction can roll back. Use `@TransactionalEventListener(AFTER_COMMIT)` when waiting for commit is required.
- **Assuming AFTER_COMMIT has durable retries:** a listener failing after commit does not roll back the original transaction and does not create a retry queue. Use an outbox when reliable delivery is mandatory.
- **Not seeing events on bulk updates:** bulk queries bypass aggregate lifecycles and repository event publication. Emit events explicitly or write to an outbox.
- **Events being replayed multiple times:** design idempotent consumers using event IDs and unique constraints on processing markers.
- **Listeners slowing down requests:** listeners are synchronous by default. If using async, configure an executor and handle errors, security context, transactions, and retries explicitly; async still does not provide durability.
- **Using `@TransactionalEventListener` without a transaction:** listeners do not run by default. Check transaction boundaries or consider `fallbackExecution` when genuinely appropriate.

When testing, verify at least four scenarios: when the transaction commits, the AFTER_COMMIT listener is invoked; when the transaction rolls back, the AFTER_COMMIT listener does not run; events on an aggregate are published when an eligible repository method is called; and bulk updates are not assumed to emit domain events automatically. For an outbox, test the case where the publisher delivers successfully but fails before marking the row sent to confirm the consumer handles duplicate events safely.

## 10. Takeaways

Spring Data domain events are a convenient way for aggregate roots to announce business changes within the same application. Events are stored and published through memory, so they provide no durability, retries, or cross-process distribution by default. Use `@TransactionalEventListener` to align handling timing with commit/rollback; use a transactional outbox and idempotent consumers when the system requires durable event delivery across components or services.
