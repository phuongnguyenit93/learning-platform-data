# Lookup Precedence Among @Query, Named Queries, and Derived Queries

Spring Data JPA offers three common ways to define a query for a Repository method: deriving a query from the method name (derived query), declaring a query with `@Query`, or using a predefined named query. They differ not only in syntax, but also in precedence when Spring Data resolves how to execute a method.

With the default `CREATE_IF_NOT_FOUND` configuration, lookup typically proceeds as follows:

1. If the Repository method has `@Query`, Spring Data uses the query declared there.
2. If `@Query` is absent, Spring Data looks for a named query matching the conventional name.
3. If no named query is found, Spring Data attempts to derive a query from the method name.

You can remember this concisely: **`@Query` takes direct priority; if absent, named queries are checked first; derived queries serve as the method-name fallback when no matching declared query exists.** This fallback order also depends on the `QueryLookupStrategy` configured for the Repository.

## 1. What is a derived query?

A derived query is a query generated by Spring Data from the Repository method name. Developers describe conditions using property names and keywords such as `And`, `Or`, `Between`, `In`, `Like`, `Containing`, `IgnoreCase`, and `OrderBy`.

Example Entity:

~~~java
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    private boolean active;

    protected Customer() {
    }

    public Customer(String name, String email, boolean active) {
        this.name = name;
        this.email = email;
        this.active = active;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public String getEmail() {
        return email;
    }

    public boolean isActive() {
        return active;
    }
}
~~~

Repository:

~~~java
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;
import java.util.Optional;

public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    Optional<Customer> findByEmail(String email);

    List<Customer> findByActiveTrueOrderByNameAsc();

    List<Customer> findByNameContainingIgnoreCase(String keyword);
}
~~~

Spring Data parses the method name and generates the corresponding JPQL/SQL. For example, `findByEmail` maps to a comparison on the `email` property; `findByActiveTrueOrderByNameAsc` filters `active = true` and sorts by `name` ascending.

### When should you use a derived query?

Appropriate when:
- Query conditions are short and easy to read.
- Filtering involves only a few properties or simple `And`/`Or` combinations.
- No calculations or database-specific SQL constructs are required.
- The method name still expresses intent without becoming overly long.

Do not force a complex query into a method name. Excessively long names are hard to read, hard to review, and prone to condition-ordering mistakes.

## 2. What is @Query?

`@Query` allows declaring a query directly on a Repository method. By default, its content is JPQL; it can be switched to native SQL using `nativeQuery = true`.

Example:

~~~java
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    @Query("""
        select c
        from Customer c
        where c.active = true
          and lower(c.name) like lower(concat('%', :keyword, '%'))
        order by c.name
        """)
    List<Customer> searchActiveCustomers(
            @Param("keyword") String keyword
    );
}
~~~

The query uses the `Customer` Entity and Java properties `active` and `name`. JPQL does not use the `customers` table name or SQL column names.

### When should you use @Query?

Appropriate when:
- Conditions involve multiple branches or complex combinations.
- You need `JOIN`, subqueries, `EXISTS`, `GROUP BY`, or `HAVING`.
- You need projections or DTO results.
- You want explicit control over the JPQL used by a method.
- A derived query becomes long and hard to follow.

Aggregate query example:

~~~java
@Query("""
    select c.id as customerId,
           c.name as customerName,
           count(o.id) as orderCount
    from Customer c
    left join PurchaseOrder o on o.customer = c
    group by c.id, c.name
    having count(o.id) >= :minimumOrders
    """)
List<CustomerOrderSummary> findCustomerOrderSummaries(
        @Param("minimumOrders") Long minimumOrders
);
~~~

Projection:

~~~java
public interface CustomerOrderSummary {
    Long getCustomerId();
    String getCustomerName();
    Long getOrderCount();
}
~~~

When using interface projections, aliases in `SELECT` should match accessor names. For complex queries, test mappings and result types against your actual JPA provider.

### @Query can use native SQL

~~~java
@Query(value = """
    SELECT c.*
    FROM customers c
    WHERE c.active = true
      AND lower(c.email) = lower(?1)
    """, nativeQuery = true)
Optional<Customer> findActiveByEmailNative(String email);
~~~

Native SQL uses physical table and column names. Choose this only when you need database syntax, legacy schema integration, or measured SQL control. For routine queries, JPQL is usually more portable and maintainable.

## 3. What is a named query?

A named query is a query given a name and declared beforehand, usually on an Entity with `@NamedQuery` or in an `orm.xml` file. In JPA, standard named queries are JPQL; if direct SQL is needed, `@NamedNativeQuery` can be used.

Example declaration on the `Customer` Entity:

~~~java
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
@NamedQuery(
    name = "Customer.findByEmail",
    query = "select c from Customer c where c.email = ?1"
)
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    protected Customer() {
    }
}
~~~

Repository with a matching method:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    Optional<Customer> findByEmail(String email);
}
~~~

Spring Data JPA locates named queries using the naming convention:

~~~text
Simple Entity name + "." + Repository method name
Customer.findByEmail
~~~

When a named query with a matching name is found, Spring Data executes that query instead of deriving one from the method name.

Named query names are global identifiers within the persistence unit, so name them clearly and avoid collisions. Multiple named queries can be declared with `@NamedQueries` or placed in `orm.xml` to separate mappings from Entity code.

### When should you use a named query?

Appropriate when:
- You want queries defined centrally alongside Entity metadata or in `orm.xml`.
- Static queries follow a clear naming convention.
- You want the provider to recognize and validate named queries during persistence unit initialization.
- You need to invoke the same named query from multiple places via `EntityManager` or corresponding repository methods.

A named query is not automatically better than `@Query`. If a query belongs specifically to a single Repository, `@Query` is often easier to find and read because the query sits right next to the method that uses it.

## 4. Lookup precedence when Spring Data resolves queries

Spring Data JPA uses `QueryLookupStrategy` to determine how to resolve a query for each Repository method.

Three main strategies:

| Strategy | Behavior |
|---|---|
| CREATE | Always attempts to derive the query from the method name |
| USE_DECLARED_QUERY | Requires a declared query; throws an error if not found |
| CREATE_IF_NOT_FOUND | Searches for a declared query first; derives from method name if absent |

`CREATE_IF_NOT_FOUND` is the common default strategy in Spring Data JPA.

During declared query lookup:
- `@Query` on the Repository method takes precedence.
- If `@Query` is absent, Spring Data looks for a named query by naming convention.
- Only when no matching declared query is found and the strategy allows it does Spring Data derive a query from the method name.

Example:

~~~java
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {

    @Query("select c from Customer c where c.email = :email")
    Optional<Customer> findByEmail(@Param("email") String email);
}
~~~

Even if the Entity also declares a named query `Customer.findByEmail`, `@Query` on the Repository method is still the query executed. This allows a Repository to override a named query without renaming the method.

If `@Query` is removed, the named query `Customer.findByEmail` can be selected ahead of a derived query. If no named query exists, `CREATE_IF_NOT_FOUND` attempts to parse `findByEmail` as a derived query.

## 5. Comparison table of the three declaration approaches

| Criterion | Derived query | @Query | Named query |
|---|---|---|---|
| Where logic is declared | Method name | On the Repository method | On the Entity or in orm.xml |
| Readability | Read keywords in the name | Read JPQL/SQL directly | Look up by identifier name |
| Suitable complexity | Simple to moderate | Moderate to complex | Static queries needing centralized declaration |
| SQL customization | Limited | JPQL or native SQL | JPQL or named native query |
| Reusability | Typically tied to method | Typically tied to method | Can be invoked by name from multiple places |
| Maintenance | Long names become hard to read | Long queries may live directly in Repository | Queries separated from Repository method |
| Lookup order | Fallback when no declared query exists per strategy | Prioritized on the method | Checked before derived query when @Query is absent and lookup permits |

No approach is always best. Choose based on complexity, where query logic belongs, and reuse needs.

## 6. Example of the same requirement written three ways

Requirement: find a `Customer` by email.

### Approach A: Derived query

~~~java
Optional<Customer> findByEmail(String email);
~~~

Spring Data infers the condition from the method name.

### Approach B: @Query

~~~java
@Query("select c from Customer c where c.email = :email")
Optional<Customer> findCustomerByEmail(
        @Param("email") String email
);
~~~

The JPQL statement is declared directly on the Repository method. The method name can differ because `@Query` supplies the query body.

### Approach C: Named query

On the Entity:

~~~java
@NamedQuery(
    name = "Customer.findByEmail",
    query = "select c from Customer c where c.email = ?1"
)
~~~

In the Repository:

~~~java
Optional<Customer> findByEmail(String email);
~~~

Spring Data looks up `Customer.findByEmail`. If the named query exists and the lookup strategy permits declared queries, the declared query executes.

All three approaches can produce the same result, but their organization and priority differ. Avoid declaring all three for the same method without a clear reason, as maintainers will struggle to tell which query actually runs.

## 7. Configuring QueryLookupStrategy

You can select the strategy when enabling Spring Data JPA repositories:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;
import org.springframework.data.repository.query.QueryLookupStrategy;

@Configuration
@EnableJpaRepositories(
    queryLookupStrategy = QueryLookupStrategy.Key.CREATE_IF_NOT_FOUND
)
public class JpaRepositoryConfiguration {
}
~~~

Meaning:

- CREATE: creates queries from method names.
- USE_DECLARED_QUERY: requires queries to be predeclared, such as `@Query` or named queries.
- CREATE_IF_NOT_FOUND: prefers declared queries, then falls back to derivation.

`CREATE_IF_NOT_FOUND` suits most applications because it allows using all three styles. `USE_DECLARED_QUERY` is helpful when a project wants to enforce explicit declarations for every query method. `CREATE` is useful when relying on method naming conventions without using declared queries for those methods.

If a project has multiple repository configurations, make sure each configuration applies to the right packages. Do not create overlapping `@EnableJpaRepositories` declarations on the same package unless you understand how Spring registers repository beans.

## 8. How do named native queries and native @Query differ?

Named native queries are declared on the Entity or in `orm.xml` with `@NamedNativeQuery`:

~~~java
@NamedNativeQuery(
    name = "Customer.findActiveCustomers",
    query = """
        SELECT *
        FROM customers
        WHERE active = true
        """,
    resultClass = Customer.class
)
~~~

Repository:

~~~java
List<Customer> findActiveCustomers();
~~~

Spring Data can locate the named query by `Customer.findActiveCustomers`. Results are mapped to `Customer` via `resultClass`.

Compared with `@Query(nativeQuery = true)`:

- `@Query` places SQL directly on the Repository method.
- `@NamedNativeQuery` places SQL in JPA metadata.
- Named native queries can use `resultClass` or `@SqlResultSetMapping` for complex mappings.
- Both depend on database schema and syntax.

If the result only contains a subset of columns, do not declare `resultClass` as the full Entity when the `SELECT` statement does not return all required columns. Use `SqlResultSetMapping`, projections, or an explicit DTO conversion.

## 9. Parameters, return types, and pagination

Whether using `@Query` or named queries, bind parameters safely and keep data types consistent.

With `@Query`, named parameters:

~~~java
@Query("""
    select c
    from Customer c
    where c.active = :active
      and c.name like concat('%', :keyword, '%')
    """)
Page<Customer> search(
        @Param("active") boolean active,
        @Param("keyword") String keyword,
        Pageable pageable
);
~~~

With complex native queries, declare `countQuery` so Spring Data counts total results accurately:

~~~java
@Query(
    value = """
        SELECT c.*
        FROM customers c
        WHERE c.active = true
        """,
    countQuery = """
        SELECT COUNT(*)
        FROM customers c
        WHERE c.active = true
        """,
    nativeQuery = true
)
Page<Customer> findActiveCustomers(Pageable pageable);
~~~

JPA-defined named queries can use positional or named parameters according to valid syntax. Verify provider support and how Spring Data binds parameters for that query type.

Do not concatenate user input into JPQL/SQL. Use bind parameters for values. If dynamic column names or sort directions are needed, validate against a whitelist of allowed choices rather than binding identifiers like ordinary parameters.

## 10. When to choose each approach

### Choose a derived query if

- The query has a few straightforward conditions.
- The method name remains short and clear.
- No complex aggregates or database-specific SQL syntax are needed.
- You want to minimize JPQL written and maintained.

Examples: `findByEmailIgnoreCase`, `findByActiveTrueOrderByCreatedAtDesc`, `findByPriceBetween`.

### Choose @Query if

- The query uses `JOIN`, `EXISTS`, subqueries, `GROUP BY`, or projections.
- You need control over JPQL/native SQL for a specific method.
- You need to declare a `countQuery`.
- Readers benefit from seeing the query right next to the method.

Examples: finding Customers whose total order count exceeds a threshold, reporting queries, or querying Entities across multiple relationships.

### Choose a named query if

- Static queries should live in Entity metadata or `orm.xml`.
- You follow a clear naming convention and need lookup from multiple places.
- You want to decouple query definitions from Repository interfaces.
- The project has a reason to manage queries centrally.

Do not pick a named query solely to "reuse" a simple SQL snippet. You can reuse query logic through a shared repository/service method or custom repository where appropriate.

## 11. Dynamic queries: do not force them into these three approaches

If filters vary with input—for example, users can combine name, status, creation date, price, and category in any combination—derived query names can balloon uncontrollably. A static `@Query` packed with nullable parameter checks can also be hard to optimize and read.

Other options:

- Spring Data JPA `Specification` to compose predicates dynamically.
- Criteria API when building queries via the JPA API.
- Querydsl if the project already uses it and wants type-safe queries.
- Custom repositories with `EntityManager` for specialized logic.

Example `Specification` concept:

~~~java
public static Specification<Customer> isActive(Boolean active) {
    return (root, query, cb) -> {
        if (active == null) {
            return cb.conjunction();
        }
        return cb.equal(root.get("active"), active);
    };
}
~~~

Specifications can be combined using `and()` or `or()`. This fits dynamic filtering much better than creating separate methods for every filter combination.

## 12. Common mistakes when multiple query definitions exist

**Assuming a derived query always runs because the method is named findBy...**

If the method has `@Query`, the annotation's query is used. If `@Query` is absent but a matching named query exists, the named query may be chosen ahead of derivation.

**Misnaming a named query**

Spring Data's convention is simple Entity name, a dot, and Repository method name—for example `Customer.findByEmail`. A wrong name prevents Spring Data from locating the declared query by convention.

**Confusing Entity names with table names**

JPQL and named JPQL use Entity names and Java properties. Native queries use physical table and column names.

**Defining duplicate named query names**

Named query names must be unique in a persistence unit. Duplicates can cause startup errors or ambiguous lookups.

**Adding @Query while expecting a named query to run**

`@Query` on a method takes precedence. If you intend to use the named query, remove the `@Query` or clarify the design.

**Using USE_DECLARED_QUERY and forgetting to declare a query**

If no matching declared query exists, the application may fail when initializing the Repository. Verify every query method before choosing this strategy.

**Overly long derived query names**

Switch to `@Query`, `Specification`, or a custom repository once method names stop being readable.

**Not testing actual queries**

Queries can fail due to wrong property names, parameter types, projection aliases, or database syntax. Boot the context and run integration tests against the target database.

## 13. Process for selecting and verifying a query method

When adding a new method to a Repository, you can follow these steps:

1. Determine whether the requirement is a simple query, a complex static query, or a dynamic query.
2. If simple, try a derived query and keep the method name short and clear.
3. If `JOIN`/subqueries/aggregates or projections are needed, use `@Query` to express the logic explicitly.
4. If the query should be managed in Entity metadata or `orm.xml` under a shared convention, use a named query.
5. Identify the active `QueryLookupStrategy` to understand fallbacks and errors when declared queries are missing.
6. Avoid declaring competing query sources for the same method unnecessarily.
7. Verify Entity names, properties, parameter types, return types, and projection mappings.
8. For native SQL, verify schema, dialect, bind parameters, `countQuery`, and portability.
9. Run integration tests covering non-empty results, empty results, and edge cases.

## 14. Conclusion

In Spring Data JPA, derived queries suit simple conditions, `@Query` suits queries requiring direct control, and named queries suit static queries defined in Entity metadata or `orm.xml`. With the default `QueryLookupStrategy` `CREATE_IF_NOT_FOUND`, `@Query` on the method takes priority; otherwise, Spring Data looks up named queries by convention first before deriving a query from the method name. Understanding this order prevents unexpected query overrides and helps keep Repositories clean and maintainable.
