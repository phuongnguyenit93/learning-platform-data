# Reserved Method Names and Collisions with a Property Named id

Spring Data JPA lets you generate queries from repository method names. However, several method names are reserved for CRUD operations inherited from `Repository`, `CrudRepository`, or `JpaRepository`. These methods always operate on the entity's primary key, even when the entity has another property named `id`.

Confusion arises when an entity uses a field like `pk` as `@Id` while also having another persistent property named `id`, such as an account code from an external system. In that case, `findById(...)` still queries by the primary key. To query the regular `id` property, add a descriptive token before `By`, such as `findAccountById(...)`, or declare explicit JPQL with `@Query`.

This lesson explains how Spring Data distinguishes reserved CRUD methods from derived queries, how to name methods to avoid collisions, how to use `@Query`, and how to write tests ensuring queries target the right property.

## 1. How are derived queries created from method names?

Spring Data parses repository method names to infer query conditions. Example:

~~~java
List<Account> findByEmail(String email);
~~~

Spring interprets this method as querying `Account` entities whose `email` property equals the passed value.

A derived query name typically consists of:

- **Subject**: the part indicating the operation type, such as `find`, `read`, `get`, `query`, `search`, `stream`, `count`, `exists`, or `delete`.
- **Descriptive token**: an optional descriptive part between the subject and `By`; it improves readability without becoming a filter condition.
- **Predicate**: the part starting after `By`, describing properties and query conditions.
- **Modifier**: additional parts such as `Distinct`, `Top`, `First`, or `OrderBy` depending on method syntax.

Example:

~~~java
Optional<Account> findAccountByEmail(String email);
~~~

This can be read as:

- `find`: find entities.
- `Account`: descriptive token, purely to make the method name clearer.
- `ByEmail`: filter condition on the `email` property.

A descriptive token does not require the entity to have an `account` property. Query predicates begin after `By`.

## 2. What are reserved CRUD methods?

Spring Data repositories inherit standard methods. Key methods include:

| Method | Meaning |
|---|---|
| findById(ID id) | Finds an entity by the property mapped with @Id |
| existsById(ID id) | Checks whether an entity exists with the given primary key |
| deleteById(ID id) | Deletes an entity by primary key |
| findAllById(Iterable<ID> ids) | Finds entities matching a collection of primary keys |
| deleteAllById(Iterable<? extends ID> ids) | Deletes entities matching a collection of primary keys |

These are CRUD operations already defined in the repository base interfaces. They are not treated as ordinary derived queries merely because their names contain `ById`.

In particular, `findById` always takes the repository's ID type and queries the `@Id` property. If the entity's primary key field is named `pk`, `findById` still queries `pk`. The name of the primary key field does not change this method's meaning.

Repository example:

~~~java
public interface AccountRepository
        extends JpaRepository<Account, Long> {
}
~~~

The ID type of `AccountRepository` is `Long`. Therefore:

~~~java
repository.findById(42L);
~~~

means finding the `Account` with primary key equal to `42`.

## 3. Collision scenario: entity has both pk and id

Suppose a system needs two identifiers:

- `pk`: internal primary key generated by the database.
- `id`: account code from an external system, e.g. `EXT-1001`.

Entity:

~~~java
package example.domain;

import jakarta.persistence.*;

@Entity
@Table(name = "accounts")
public class Account {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long pk;

    @Column(name = "external_id", nullable = false, unique = true)
    private String id;

    @Column(nullable = false)
    private String email;

    protected Account() {
    }

    public Account(String id, String email) {
        this.id = id;
        this.email = email;
    }

    public Long getPk() {
        return pk;
    }

    public String getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }
}
~~~

In this entity:

| Java property | Mapping | Role |
|---|---|---|
| pk | @Id | Entity primary key |
| id | @Column(name = "external_id") | External account identifier |
| email | @Column | Login email |

The database column name is `external_id`, while the Java property name remains `id`. Derived queries use the entity's Java property names, not SQL column names.

If the repository extends `JpaRepository<Account, Long>`, Spring Data already provides `findById(Long id)`. That method queries by `pk` because `pk` is the `@Id` property.

## 4. Why does findById not query the regular id field?

Suppose you write:

~~~java
Optional<Account> account = repository.findById(42L);
~~~

Spring Data handles this as the reserved CRUD method. It finds the `Account` with primary key `pk = 42`.

It does not assume you meant to search the `String id` field simply because the entity happens to have a property named `id`. That method name is reserved in the repository base API, and its semantics are bound to the repository's primary key type.

If you try to use `findById` with a `String` parameter to query the `id` property in the example above, it conflicts with the inherited CRUD signature and the repository's ID type. Do not declare a method with the same name to alter the meaning of the standard API.

Here is the core rule: **reserved CRUD method names take precedence under the repository base interface contract and always target the primary key**.

## 5. The right approach: add a descriptive token before By

To query the regular `id` property, place a descriptive token between the subject and `By`.

Repository:

~~~java
package example.repository;

import example.domain.Account;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface AccountRepository
        extends JpaRepository<Account, Long> {

    Optional<Account> findAccountById(String id);
}
~~~

The method `findAccountById` is parsed as:

- `find`: subject, requesting entity lookup.
- `Account`: descriptive token, not a condition.
- `By`: starts the predicate.
- `Id`: Java property to compare against.

Therefore:

~~~java
repository.findById(42L);
~~~

queries by primary key `pk`.

Whereas:

~~~java
repository.findAccountById("EXT-1001");
~~~

queries by the `id` property with value `EXT-1001`.

The two methods have different meanings even though both contain the word `Id`.

The descriptive token should help readers understand the domain, such as `Account`, `User`, `Customer`, or `Order`. This token does not have to be an existing property on the entity.

## 6. Comparing naming approaches

For the `Account` entity above:

| Method | How Spring Data interprets it | Queried property |
|---|---|---|
| findById(Long id) | Reserved CRUD method | pk, i.e. @Id |
| existsById(Long id) | Reserved CRUD method | pk, i.e. @Id |
| deleteById(Long id) | Reserved CRUD method | pk, i.e. @Id |
| findAccountById(String id) | Derived query | id |
| findByEmail(String email) | Derived query | email |
| findAccountByEmail(String email) | Derived query | email |

How to read the method names:

~~~text
findById
  |
  +-- Reserved CRUD method name
  +-- Queries by @Id

findAccountById
  |
  +-- find: subject
  +-- Account: descriptive token
  +-- ById: predicate
          |
          +-- Queries by property id
~~~

If the `id` property itself is the primary key annotated with `@Id`, `findById` is completely accurate and has no semantic collision. The issue only arises when `id` is a persistent property distinct from the primary key property.

## 7. Using @Query for explicit clarity

If a method name could be misread or the query has complex conditions, use `@Query` to state the target property explicitly.

JPQL example:

~~~java
package example.repository;

import example.domain.Account;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.Optional;

public interface AccountRepository
        extends JpaRepository<Account, Long> {

    Optional<Account> findAccountById(String id);

    @Query("""
        select a
        from Account a
        where a.id = :externalId
        """)
    Optional<Account> findByExternalId(
        @Param("externalId") String externalId
    );
}
~~~

JPQL uses entity names and Java properties:

- `Account` is the entity.
- `a.id` is the `id` property in Java.
- `externalId` is the query parameter name.
- `:externalId` binds the parameter to the passed value.

JPQL does not use the column name `external_id` inside `a.id`. The JPA provider maps the `id` property to column `external_id` via `@Column`.

With native SQL, you work directly with database tables and columns:

~~~java
@Query(
    value = """
        select *
        from accounts
        where external_id = :externalId
        """,
    nativeQuery = true
)
Optional<Account> findNativeByExternalId(
    @Param("externalId") String externalId
);
~~~

Use native queries when database-specific syntax or features are needed. For simple lookups on a single entity property, derived queries or JPQL are usually easier to maintain.

## 8. Distinguishing Java property names from database column names

Another common cause of errors is confusing property names with column names.

~~~java
@Column(name = "external_id")
private String id;
~~~

In Java, the property is named `id`. In the database, the column is named `external_id`.

Derived queries must use the property name:

~~~java
Optional<Account> findAccountById(String id);
~~~

Do not use the SQL column name in the method name:

~~~java
// Not a valid derived query if the entity does not have property externalId:
Optional<Account> findByExternalId(String externalId);
~~~

`findByExternalId` is only a valid derived query if the entity actually has a property named `externalId`. To query the `external_id` column when the Java field is named `id`, use `findAccountById` or declare `@Query`.

This rule applies to every property, not only `id`. For example:

~~~java
@Column(name = "created_at")
private Instant createdAt;
~~~

Derived queries use `findByCreatedAt(...)`, not `findByCreated_at(...)`.

## 9. When are descriptive tokens helpful?

Descriptive tokens are useful when:

- The method name collides with a reserved CRUD method.
- You want clearer intent in a repository with multiple identifiers.
- A property named `id` exists that is not the primary key.
- You need to distinguish querying by internal ID vs. external code.

Examples:

~~~java
Optional<Account> findAccountById(String externalId);

Optional<Account> findAccountByEmail(String email);

List<Account> findAccountByStatus(AccountStatus status);
~~~

The `Account` token makes the method name easier to read. The predicate still starts after `By` and must match a persistent property of the entity.

You do not need to add a descriptive token to every method. `findByEmail` is completely valid when there is no collision.

## 10. Other CRUD methods to watch out for

Beyond `findById`, the repository base API includes primary-key methods such as `existsById`, `deleteById`, and `findAllById`.

Examples:

~~~java
repository.existsById(42L);
repository.deleteById(42L);
repository.findAllById(List.of(10L, 20L, 30L));
~~~

These operations act on `Account`'s primary key, which is `pk` in this example.

If business logic needs to check existence or delete by the external code, choose a distinct name targeting the right property:

~~~java
boolean existsAccountById(String externalId);

void deleteAccountById(String externalId);
~~~

Derived `exists` or `delete` methods should be checked against your Spring Data JPA version and supported return types. For deletions with business rules or explicit transaction control, a dedicated service method is often clearer.

Example deleting by external ID with `@Query`:

~~~java
@Modifying
@Query("delete from Account a where a.id = :externalId")
int deleteByExternalId(
    @Param("externalId") String externalId
);
~~~

This method must be invoked inside an appropriate transaction. Bulk deletes act directly on the database without synchronizing managed entities in the persistence context. If you need to keep using related entities in the same transaction, consider clearing the persistence context or using regular entity deletion.

## 11. Nested property paths and underscores

Spring Data also supports querying via property paths. Suppose an entity has:

~~~java
class Account {
    private AccountProfile profile;
}

class AccountProfile {
    private String id;
}
~~~

The method:

~~~java
Optional<Account> findAccountByProfileId(String id);
~~~

can resolve to the path `profile.id`. If a property name is ambiguous between a direct property and a nested path, an underscore can explicitly mark the boundary:

~~~java
Optional<Account> findAccountByProfile_Id(String id);
~~~

An underscore in a method name is Spring Data's property path separator. It does not mean the database column name contains an underscore.

For complex entities, `@Query` can be clearer if a derived method becomes too long or hard to read.

## 12. Parameter types must match the queried property

With `AccountRepository extends JpaRepository<Account, Long>`:

- `findById` accepts `Long` because that is the primary key type.
- `findAccountById` accepts `String` because the entity's `id` property is `String`.
- `findByEmail` accepts `String` if `email` is `String`.

Do not infer parameter types from the method name alone. Determine whether a method is a reserved CRUD method or a derived query, then verify the type of the exact target property.

If parameter types are incompatible, errors can appear at compile time, when Spring constructs repository queries, or when the provider executes the query, depending on signature and configuration.

## 13. Testing to ensure the two ID types are not confused

A repository test should create a record with a database-generated primary key and an application-supplied external ID, then query using both methods.

Example with a Spring Boot test slice:

~~~java
package example.repository;

import example.domain.Account;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;

import static org.junit.jupiter.api.Assertions.assertEquals;

@DataJpaTest
class AccountRepositoryTest {

    @Autowired
    private AccountRepository repository;

    @Test
    void distinguishesPrimaryKeyFromPropertyNamedId() {
        Account saved = repository.saveAndFlush(
            new Account("EXT-1001", "an@example.com")
        );

        Account byPrimaryKey = repository
            .findById(saved.getPk())
            .orElseThrow();

        Account byExternalId = repository
            .findAccountById("EXT-1001")
            .orElseThrow();

        assertEquals(saved.getPk(), byPrimaryKey.getPk());
        assertEquals(saved.getPk(), byExternalId.getPk());
    }
}
~~~

This is an illustrative integration test for a project using Spring Boot test. If your application does not use Boot, configure the Spring test context and JPA provider per your setup; the logic to verify remains the same.

The test proves:

- `findById` uses the primary key.
- `findAccountById` uses the `id` property.
- Both queries return the same row via two different identifiers.

You should also add tests for missing IDs, duplicate external IDs, and the unique constraint on the `external_id` column.

## 14. Common errors and fixes

**1. findById queries the wrong column**

Check which property carries `@Id`. The CRUD method `findById` always queries that property. If you need another `id` field, use `findAccountById` or `@Query`.

**2. Derived query fails to be created**

Verify that the property name after `By` exists in the entity with matching casing. Derived queries use Java property names, not SQL column names.

**3. Using the wrong parameter type**

Check the `JpaRepository` ID type and the type of the queried property. In our example, `findById` takes `Long` whereas `findAccountById` takes `String`.

**4. Trying to overload findById to change its meaning**

Do not reuse a reserved CRUD name with a different parameter type to target a regular property. Pick a descriptive token so the method name does not collide with CRUD signatures.

**5. Mistaking the descriptive token for a property**

In `findAccountById`, `Account` is part of the subject description. Spring does not require the entity to have an `account` property. The filter condition is the `id` property after `By`.

**6. Using column names instead of field names**

If the Java field is `id` and `@Column` specifies `external_id`, derived queries must still use `ById`. Only native SQL uses `external_id`.

**7. Using Java property names inside native SQL**

Native SQL must use actual database table and column names. Only JPQL uses entity and Java property names.

**8. Failing to test when an entity has multiple identifiers**

Create test data where the primary key differs from the external ID and test each repository method. A test that only checks `findById` when values happen to match might miss confusion bugs.

## 15. Safe method-naming workflow

When adding an ID-related repository method:

1. Identify which field or property is annotated with `@Id`.
2. Identify the second ID type if the entity carries a business code or external system ID.
3. Check whether the method collides with inherited reserved CRUD names.
4. If querying a non-primary-key property named `id`, add a descriptive token before `By`, e.g. `findAccountById`.
5. Match the parameter type to the exact queried property.
6. Use Java property names, not SQL column names, in derived queries and JPQL.
7. Use `@Query` to make conditions explicit or avoid confusing method names.
8. Write repository tests distinguishing primary-key queries from business-identifier queries.

## 17. Review questions

**1. Which field does findById in JpaRepository query?**

It queries the property mapped with `@Id`, regardless of whether that property is named `id`, `pk`, or `userKey`.

**2. An entity has @Id pk and a String id field. How do you query by String id?**

Use a derived method with a descriptive token, such as `findAccountById(String id)`, or a `@Query` method explicitly specifying `a.id = :id`.

**3. Is Account in findAccountById an entity property?**

No. `Account` is a descriptive token in the subject part. The predicate starts after `By` and queries the `id` property.

**4. Does @Column(name = "external_id") mean the method must be written as findByExternalId?**

No. Derived queries use Java property names. If the field is named `id`, the method querying that field can be `findAccountById`.

**5. Why should you not overload findById to search by an external code?**

Because `findById` is a reserved CRUD method tied to the repository's ID type. Using a descriptive token avoids confusion over contracts and parameter types.

**6. When should you use @Query instead of a derived query?**

When conditions are complex, method names get long, or you want the queried property stated explicitly. JPQL uses entities/properties; native SQL uses database tables/columns.

When you clearly separate reserved CRUD methods from derived queries, you can work with entities that have both an internal primary key and a business `id` property without query confusion.
