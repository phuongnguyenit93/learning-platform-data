# Quản lý fixture bằng @Sql, migration và dữ liệu có tính xác định

Một bài kiểm thử Spring Data JPA đáng tin cậy cần biết chính xác schema và dữ liệu mà nó sử dụng. Ba khái niệm thường gặp có vai trò khác nhau:

- **Migration** quản lý thay đổi cấu trúc database theo phiên bản: tạo bảng, thêm cột, index, constraint hoặc chuyển đổi schema.
- **Fixture** là dữ liệu chuẩn bị cho một kịch bản kiểm thử cụ thể: khách hàng, đơn hàng, trạng thái, quan hệ và các giá trị cần để xác nhận kết quả.
- **@Sql** của Spring TestContext chạy script SQL trước hoặc sau test để tạo và dọn fixture.

Migration giúp các môi trường có cùng cấu trúc database. Fixture giúp mỗi test bắt đầu từ trạng thái dữ liệu đã biết. Không nên biến migration cấu trúc thành tập dữ liệu thử nghiệm được chạy lại cho từng test method.

## 1. Phân biệt migration và fixture

| Tiêu chí | Migration | Fixture |
|---|---|---|
| Mục đích | Tiến hóa schema và chuyển đổi dữ liệu ứng dụng | Chuẩn bị dữ liệu cho một test hoặc nhóm test |
| Vòng đời | Được quản lý theo phiên bản/checksum và áp dụng theo thứ tự | Được tạo, sử dụng và dọn theo phạm vi test |
| Công cụ | Flyway, Liquibase | @Sql, builder/factory, repository hoặc Test Data Builder |
| Ví dụ | Tạo bảng purchase_order, thêm cột status, tạo UNIQUE constraint | Tạo một khách hàng và một đơn hàng PENDING |
| Chạy lại cho mỗi test? | Thông thường không | Có thể chạy trước mỗi test method |

Quy trình điển hình:

1. Test khởi động application context và database.
2. Flyway hoặc Liquibase áp dụng migration để tạo schema.
3. Script fixture hoặc factory tạo dữ liệu cho kịch bản.
4. Test thực thi repository/service và xác nhận hành vi.
5. Fixture được rollback hoặc dọn theo chiến lược đã chọn.

Migration không nên chứa các bản ghi mẫu chỉ phục vụ một test. Khi thêm test mới, ta không muốn tạo migration version mới chỉ để thêm một đơn hàng thử nghiệm.

## 2. Quản lý schema bằng Flyway hoặc Liquibase

### 2.1. Flyway

Flyway thường dùng versioned migration có tên dạng:

~~~text
src/main/resources/
  db/
    migration/
      V1__create_customer.sql
      V2__create_purchase_order.sql
      V3__add_order_status_index.sql
~~~

Ví dụ migration tạo bảng:

~~~sql
CREATE TABLE customer (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(150) NOT NULL
);

CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_code VARCHAR(50) NOT NULL UNIQUE,
    customer_id BIGINT NOT NULL,
    status VARCHAR(30) NOT NULL,
    CONSTRAINT fk_purchase_order_customer
        FOREIGN KEY (customer_id) REFERENCES customer(id)
);
~~~

Flyway lưu lịch sử migration trong bảng schema history, theo dõi phiên bản và checksum. Versioned migration được áp dụng theo thứ tự và không nên sửa nội dung sau khi đã chạy trên môi trường dùng chung. Khi cần thay đổi schema, tạo migration mới thay vì viết lại migration cũ.

Trong Spring Boot, Flyway thường tự chạy khi application context khởi tạo nếu dependency và datasource phù hợp. Test nên sử dụng cùng chuỗi migration schema mà ứng dụng yêu cầu.

### 2.2. Liquibase

Liquibase quản lý thay đổi database bằng changelog. Changelog có thể viết bằng XML, YAML, JSON hoặc SQL. Mỗi changeSet có định danh và được ghi nhận trong bảng DATABASECHANGELOG.

Ví dụ dạng YAML:

~~~yaml
databaseChangeLog:
  - changeSet:
      id: 1-create-customer
      author: team
      changes:
        - createTable:
            tableName: customer
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
              - column:
                  name: customer_code
                  type: VARCHAR(50)
                  constraints:
                    nullable: false
                    unique: true
              - column:
                  name: name
                  type: VARCHAR(150)
                  constraints:
                    nullable: false
~~~

Liquibase có contexts và labels để kiểm soát changeSet nào được áp dụng trong môi trường hoặc kịch bản nhất định. Dùng chúng có chủ đích; tránh để dữ liệu test lọt vào production do bật nhầm context.

### 2.3. Migration trong test

Test nên chạy migration thật để phát hiện sớm:

- Thiếu cột hoặc index.
- Sai kiểu dữ liệu hoặc constraint.
- Thứ tự migration không hợp lệ.
- Mapping entity không khớp schema.
- SQL phụ thuộc database nhưng chỉ chạy được trên một hệ quản trị khác.

Với SQL hoặc hành vi phụ thuộc engine, Testcontainers giúp chạy đúng loại database gần với production. H2 hữu ích cho test nhanh, nhưng không mô phỏng đầy đủ mọi khác biệt về dialect, sequence, locking, timestamp và constraint của PostgreSQL, MySQL hoặc SQL Server.

## 3. Dùng @Sql để tạo fixture

Spring TestContext cung cấp **org.springframework.test.context.jdbc.Sql** để chạy SQL script trước hoặc sau test class/method.

Đặt script trong test resources:

~~~text
src/test/resources/
  sql/
    fixtures/
      order-before.sql
      order-after.sql
~~~

Ví dụ:

~~~java
import org.junit.jupiter.api.Test;
import org.springframework.test.context.jdbc.Sql;

class PurchaseOrderRepositoryTest {

    @Test
    @Sql("/sql/fixtures/order-before.sql")
    void findsFixtureOrder() {
        // Thực thi test
    }
}
~~~

Đường dẫn bắt đầu bằng dấu slash là đường dẫn classpath tuyệt đối. Nếu không có slash, Spring diễn giải đường dẫn tương đối với package của test class. Dùng đường dẫn tuyệt đối giúp xác định rõ script nằm trong test resources.

Mặc định, script chạy ở phase **BEFORE_TEST_METHOD**. Có thể chạy cleanup sau test:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-after.sql",
    executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD
)
~~~

@Sql đặt ở cấp class thường được áp dụng trước mỗi test method trong class. Nếu cần kết hợp script cấp class và method, có thể dùng **@SqlMergeMode(SqlMergeMode.MergeMode.MERGE)**. Mặc định, cấu hình @Sql ở method có thể thay thế cấu hình ở class; hãy chọn hành vi merge/override rõ ràng để tránh vô tình bỏ script chuẩn bị chung.

## 4. Chọn transaction mode cho @Sql

Một nguyên nhân phổ biến làm fixture biến mất hoặc rò rỉ giữa test là không hiểu transaction mode của script. Spring cung cấp hai chế độ thường dùng qua **@SqlConfig(transactionMode = ...)**:

- **INFERRED**: mặc định. Spring sử dụng transaction đang tồn tại nếu có; nếu không, suy luận cách chạy transaction từ transaction manager và cấu hình.
- **ISOLATED**: chạy script trong transaction riêng, độc lập với transaction test; transaction của script được commit trước khi test tiếp tục.

### 4.1. INFERRED với test transaction

Các test slice như **@DataJpaTest** mặc định chạy test method trong transaction và rollback sau test. Với @Sql dùng INFERRED, script thường tham gia transaction test hiện tại.

Khai báo rõ chế độ mặc định:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-before.sql",
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.INFERRED
    )
)
~~~

Luồng thường gặp:

~~~text
Bắt đầu transaction test
        |
        v
@Sql BEFORE_TEST_METHOD (INFERRED)
        |
        v
Test đọc/ghi dữ liệu
        |
        v
Rollback transaction test
        |
        v
Fixture trong transaction đó cũng rollback
~~~

Đây thường là lựa chọn gọn cho test repository: fixture và thay đổi do test tạo cùng được rollback. Không cần cleanup riêng nếu toàn bộ fixture được tạo trong transaction test và không có thao tác commit độc lập.

Hãy xác nhận test có thực sự chạy trong transaction. Test method không có transaction, hoặc script được cấu hình chạy độc lập, sẽ có vòng đời dữ liệu khác.

### 4.2. ISOLATED với fixture được commit riêng

Nếu fixture cần tồn tại ngoài transaction test, hoặc muốn script luôn có transaction độc lập, dùng ISOLATED:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-before.sql",
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.ISOLATED
    )
)
~~~

Script được chạy và commit trong transaction riêng. Rollback của @DataJpaTest không xóa fixture đã commit. Vì vậy, cần có cleanup script sau test, cũng chạy độc lập:

~~~java
@Sql(
    scripts = "/sql/fixtures/order-after.sql",
    executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD,
    config = @SqlConfig(
        transactionMode = SqlConfig.TransactionMode.ISOLATED
    )
)
~~~

ISOLATED cần transaction manager phù hợp. Chỉ dùng khi thật sự cần ranh giới transaction riêng và luôn có kế hoạch dọn dữ liệu.

### 4.3. Ví dụ test hoàn chỉnh

Ví dụ sau dùng @DataJpaTest. Hai script chạy trong transaction riêng và cleanup sau test:

~~~java
import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.test.context.jdbc.Sql;
import org.springframework.test.context.jdbc.SqlConfig;

@DataJpaTest
class PurchaseOrderRepositoryTest {

    @Autowired
    private PurchaseOrderRepository orders;

    @Test
    @Sql(
        scripts = "/sql/fixtures/order-before.sql",
        config = @SqlConfig(
            transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
    )
    @Sql(
        scripts = "/sql/fixtures/order-after.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD,
        config = @SqlConfig(
            transactionMode = SqlConfig.TransactionMode.ISOLATED
        )
    )
    void findsKnownPendingOrder() {
        PurchaseOrder order = orders
            .findByOrderCode("fixture-order-01")
            .orElseThrow();

        assertEquals("PENDING", order.getStatus().name());
    }
}
~~~

Các import entity/repository và enum status phụ thuộc ứng dụng. Ví dụ giả định PurchaseOrderRepository có derived query **findByOrderCode** và trạng thái PENDING tồn tại trong domain.

### 4.4. Nội dung script fixture

Script seed:

~~~sql
-- order-before.sql
DELETE FROM purchase_order
WHERE order_code = 'fixture-order-01';

DELETE FROM customer
WHERE customer_code = 'fixture-customer-01';

INSERT INTO customer (customer_code, name)
VALUES ('fixture-customer-01', 'Fixture Customer');

INSERT INTO purchase_order (order_code, customer_id, status)
SELECT
    'fixture-order-01',
    id,
    'PENDING'
FROM customer
WHERE customer_code = 'fixture-customer-01';
~~~

Script cleanup:

~~~sql
-- order-after.sql
DELETE FROM purchase_order
WHERE order_code = 'fixture-order-01';

DELETE FROM customer
WHERE customer_code = 'fixture-customer-01';
~~~

Ví dụ dùng mã nghiệp vụ cố định để tìm và dọn dữ liệu thay vì giả định ID identity luôn bằng một số cụ thể. Câu lệnh DELETE xóa bảng con trước bảng cha để tôn trọng foreign key. Các cột customer_code và order_code cần có UNIQUE constraint theo schema migration.

Đây là SQL minh họa theo schema tương thích. Nếu database yêu cầu cú pháp identity, sequence, timestamp hoặc quoting riêng, điều chỉnh script và chạy test trên database đó.

## 5. Tạo dữ liệu có tính xác định

Dữ liệu xác định (deterministic test data) nghĩa là cùng một test với cùng fixture và cấu hình sẽ có đầu vào đã biết, không phụ thuộc thời điểm chạy, thứ tự test, dữ liệu tồn dư hoặc trạng thái môi trường.

Fixture tốt nên có:

- Giá trị khóa nghiệp vụ riêng và dễ nhận biết.
- Trạng thái, số tiền, ngày giờ và quan hệ được khai báo tường minh.
- Thứ tự insert/delete phù hợp foreign key.
- Constraint cần thiết được tạo bởi migration.
- Điều kiện cleanup rõ ràng.
- Không phụ thuộc dữ liệu mà test khác tạo ra.

### 5.1. Tránh giá trị biến đổi theo thời gian hoặc ngẫu nhiên

Những giá trị sau dễ làm test không ổn định:

~~~sql
INSERT INTO event_log (event_name, created_at)
VALUES ('order-created', CURRENT_TIMESTAMP);
~~~

Hoặc trong Java:

~~~java
LocalDateTime createdAt = LocalDateTime.now();
UUID id = UUID.randomUUID();
~~~

Các giá trị này có thể hợp lệ cho production nhưng làm test khó tái lập. Test có thể thất bại khi chạy qua nửa đêm, khác timezone hoặc so sánh một giá trị ngẫu nhiên mà không biết trước kết quả.

Trong test, dùng giá trị cố định:

~~~java
Instant createdAt = Instant.parse("2026-01-15T10:30:00Z");
UUID id = UUID.fromString(
    "00000000-0000-0000-0000-000000000101"
);
~~~

Với thời gian do Spring Data Auditing hoặc service tạo, inject **Clock** và dùng **Clock.fixed(...)** trong test. Như vậy test kiểm soát được thời điểm thay vì phụ thuộc đồng hồ hệ thống.

Không cần cố định mọi ID nếu ứng dụng dùng ID tự sinh. Khi kiểm tra nghiệp vụ, hãy tìm bản ghi bằng mã nghiệp vụ ổn định hoặc dùng ID trả về từ thao tác tạo dữ liệu. Chỉ gán ID thủ công khi mapping và database cho phép điều đó an toàn.

### 5.2. Tránh giả định về thứ tự dữ liệu

SQL không bảo đảm thứ tự bản ghi nếu query không có **ORDER BY**. Đừng viết test kỳ vọng phần tử đầu tiên luôn là bản ghi A chỉ vì script insert A trước B.

Nếu thứ tự là yêu cầu nghiệp vụ, repository query phải có sort rõ ràng:

~~~java
List<PurchaseOrder> findByCustomerIdOrderByCreatedAtAsc(Long customerId);
~~~

Nếu dùng Pageable hoặc Sort, test nên xác nhận đúng cột và hướng sắp xếp thay vì dựa vào thứ tự vật lý trong database.

### 5.3. Tránh ID phụ thuộc sequence hoặc identity

Không nên viết test với giả định lần insert đầu tiên luôn có ID = 1. Sequence có thể không reset sau rollback, database có thể giữ bộ đếm identity qua lần xóa dữ liệu và test song song có thể tiêu thụ ID theo thứ tự khác.

Cách tốt hơn:

- Lấy ID từ entity đã persist.
- Dùng mã nghiệp vụ duy nhất để truy vấn.
- Chỉ reset sequence/identity nếu test thật sự kiểm tra hành vi sinh ID và script reset tương thích database.
- Không dùng SELECT MAX(id) + 1 để tự tạo khóa; hai transaction đồng thời có thể chọn cùng giá trị.

## 6. Chọn cách tạo fixture: @Sql, builder hay repository

Không phải test nào cũng cần script SQL.

| Cách tạo dữ liệu | Phù hợp khi | Điểm cần lưu ý |
|---|---|---|
| **@Sql** | Cần trạng thái database cụ thể, nhiều bảng, constraint, dữ liệu legacy hoặc query phức tạp | Phụ thuộc schema và dialect; cần transaction mode và cleanup rõ ràng |
| Test Data Builder / Object Mother | Test logic domain hoặc service với object dễ đọc | Có thể bỏ qua hành vi mapping/constraint thật nếu không persist |
| Repository / EntityManager | Cần tạo entity qua lifecycle JPA và kiểm tra mapping, cascade, auditing | Phải quản lý transaction, flush, clear và thứ tự tạo quan hệ |
| Migration | Cần thay đổi schema hoặc dữ liệu chuyển đổi có phiên bản | Không dùng làm fixture riêng cho từng test |
| Testcontainers | Cần database engine gần production | Cần quản lý thời gian khởi động và tài nguyên container |

Một test service có thể dùng builder để tạo object domain, còn test repository có thể dùng @Sql để đặt chính xác dữ liệu trong database. Chọn công cụ theo điều mà test muốn xác minh.

## 7. Tổ chức fixture để tránh rò rỉ giữa test

### 7.1. Dùng dữ liệu riêng cho từng kịch bản

Không nên để nhiều test cùng sửa một bản ghi chung nếu không cần thiết. Mỗi fixture nên có mã riêng, ví dụ:

- fixture-customer-order-read
- fixture-customer-order-update
- fixture-customer-order-delete

Nếu script dùng một mã cố định và chạy trước mỗi test, script cần đưa database về trạng thái sạch trước khi insert. Tuy nhiên, cleanup bằng khóa cố định không an toàn khi nhiều test chạy song song trên cùng schema.

### 7.2. Test chạy song song

Giả sử hai test cùng chạy script tạo order_code = fixture-order-01. Một test có thể xóa hoặc đọc dữ liệu mà test còn lại đang sử dụng; UNIQUE constraint cũng có thể làm một test thất bại.

Có ba cách xử lý:

1. Tắt parallel execution cho nhóm test dùng chung fixture cố định.
2. Dùng database/schema riêng cho từng test worker hoặc test class.
3. Sinh mã fixture riêng theo test run và truyền mã đó vào script hoặc fixture factory.

Không dựa vào giả định test sẽ chạy tuần tự nếu cấu hình JUnit, build tool hoặc CI có bật parallel execution.

### 7.3. Cleanup theo thứ tự quan hệ

Nếu bảng con tham chiếu bảng cha bằng foreign key, cleanup nên xóa con trước cha. Ví dụ:

1. Xóa purchase_order_line.
2. Xóa purchase_order_tag.
3. Xóa purchase_order.
4. Xóa customer.

Không tắt foreign key constraint chỉ để cleanup dễ hơn; constraint giúp fixture phản ánh đúng tính toàn vẹn database.

## 8. SQL fixture và persistence context JPA

@Sql thực thi SQL trực tiếp qua JDBC. JPA không tự biết các hàng đã bị SQL thay đổi nếu persistence context đang giữ entity tương ứng.

Ví dụ:

1. Entity Customer đã được EntityManager tải và quản lý.
2. Script SQL cập nhật tên Customer.
3. Code tiếp tục đọc instance đã quản lý.
4. Persistence context có thể trả về trạng thái cũ trong bộ nhớ.

Khi cần đồng bộ sau native SQL hoặc bulk update, cân nhắc:

~~~java
entityManager.flush();
entityManager.clear();
~~~

- **flush()** đẩy thay đổi JPA đang chờ xuống database trước khi SQL ngoài JPA chạy.
- **clear()** bỏ các entity đang được quản lý để lần đọc sau lấy trạng thái mới từ database.

Không gọi clear tùy tiện nếu còn cần entity đang quản lý hoặc có thay đổi chưa flush. Với @Sql chạy trước test method, thông thường test chưa tải entity vào persistence context; nhưng nếu script chạy giữa một test đang hoạt động, phải chú ý cache cấp một.

## 9. Kiểm thử migration và fixture

### 9.1. Kiểm thử schema từ migration

- Tạo database trống.
- Chạy toàn bộ migration từ phiên bản đầu.
- Khởi tạo application context và repository.
- Xác nhận bảng, cột, index, foreign key và unique constraint cần thiết tồn tại.
- Chạy truy vấn JPA cơ bản để phát hiện mapping không khớp.

### 9.2. Kiểm thử fixture

- Chạy script seed.
- Đọc dữ liệu bằng repository.
- Kiểm tra trạng thái, quan hệ và kết quả truy vấn.
- Chạy cleanup hoặc rollback theo transaction mode.
- Chạy lại test độc lập để xác nhận fixture không phụ thuộc lần chạy trước.

### 9.3. Kiểm thử trên database phù hợp

Testcontainers giúp khởi chạy database thật trong test:

~~~java
@Testcontainers
~~~

Phần khai báo container và datasource phụ thuộc database cụ thể. Mục tiêu là chạy cùng engine hoặc engine tương thích với production để kiểm tra migration, constraint, kiểu timestamp, identity/sequence và cú pháp SQL.

Một test chỉ chạy qua H2 có thể bỏ sót lỗi do khác biệt dialect. Có thể giữ nhóm test nhanh với database nhẹ, nhưng các luồng quan trọng nên được xác nhận trên database thực tế.

## 10. Lỗi thường gặp

| Triệu chứng | Nguyên nhân | Cách xử lý |
|---|---|---|
| Không tìm thấy SQL script | Sai classpath hoặc đường dẫn tương đối | Đặt file trong src/test/resources và dùng đường dẫn bắt đầu bằng / |
| Fixture biến mất khi test chạy | Script tham gia transaction test rồi bị rollback | Kiểm tra INFERRED/ISOLATED và transaction của test |
| Fixture còn tồn tại sau test | Script đã commit trong transaction riêng | Thêm cleanup AFTER_TEST_METHOD với transaction mode phù hợp |
| Duplicate key khi chạy lại | Seed không xóa dữ liệu cũ hoặc mã fixture dùng chung | Reset fixture có kiểm soát hoặc dùng khóa riêng |
| Foreign key violation khi cleanup | Xóa bảng cha trước bảng con | Xóa theo thứ tự phụ thuộc |
| Test pass trên H2 nhưng fail production | SQL, type hoặc constraint khác dialect | Chạy integration test với database production tương ứng |
| Giá trị thời gian thay đổi giữa lần chạy | Dùng now/current_timestamp hoặc timezone hệ thống | Dùng timestamp cố định và Clock được inject |
| Test phụ thuộc thứ tự chạy | Fixture chia sẻ hoặc cleanup không đầy đủ | Làm test độc lập, dùng schema riêng hoặc fixture key riêng |
| JPA trả về dữ liệu cũ sau @Sql | Persistence context đang giữ entity cũ | Flush khi cần và clear trước khi đọc lại |
| ID thay đổi giữa các lần chạy | Identity/sequence không reset sau rollback | Không hard-code ID tự sinh; dùng ID trả về hoặc business key |

## 11. Checklist quản lý fixture

- [ ] Migration chỉ mô tả thay đổi schema hoặc dữ liệu chuyển đổi có phiên bản.
- [ ] Test database chạy cùng chuỗi migration mà ứng dụng cần.
- [ ] Fixture nằm trong src/test/resources hoặc test data factory phù hợp.
- [ ] @Sql dùng đường dẫn classpath rõ ràng.
- [ ] Đã chọn INFERRED hoặc ISOLATED theo transaction của test.
- [ ] Nếu fixture được commit riêng, có cleanup script tương ứng.
- [ ] Insert theo thứ tự cha trước con; delete theo thứ tự con trước cha.
- [ ] Dữ liệu có business key, trạng thái và timestamp xác định.
- [ ] Test không phụ thuộc ID tự sinh hoặc thứ tự bản ghi không có ORDER BY.
- [ ] Test song song không dùng chung fixture key gây xung đột.
- [ ] SQL fixture và migration được kiểm thử trên database phù hợp.
- [ ] Sau thao tác SQL trực tiếp, persistence context được làm mới khi cần.

## 12. Ghi nhớ

Migration quản lý schema theo phiên bản; fixture chuẩn bị dữ liệu cho kịch bản test. **@Sql** là cách thuận tiện để chạy script trước và sau test, nhưng cần hiểu transaction mode: **INFERRED** có thể tham gia transaction test và rollback cùng test; **ISOLATED** chạy và commit trong transaction riêng nên cần cleanup rõ ràng.

Dữ liệu có tính xác định giúp test lặp lại được. Hãy cố định giá trị nghiệp vụ và thời gian, tránh giả định ID hoặc thứ tự bản ghi, tách fixture giữa các test chạy song song và xác minh trên database phù hợp với production.
