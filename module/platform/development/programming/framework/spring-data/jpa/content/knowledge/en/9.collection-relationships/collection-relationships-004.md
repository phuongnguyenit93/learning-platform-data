# Replacing Many-to-Many with an Association Entity Having Its Own Attributes

In the relational model, a many-to-many relationship is typically stored using a join table containing foreign keys to two main tables. When the join table contains only the two foreign keys, JPA can represent it with `@ManyToMany`. However, when each link carries additional business data—such as enrollment date, status, score, role, quantity, or notes—the link itself becomes a meaningful object. At that point, you should model the join table as a separate entity, commonly called an **association entity** or **association object**.

This lesson uses the example of students enrolling in courses. A student can enroll in many courses, a course has many students, and each enrollment has an enrollment date, status, score, and note. We replace the direct Student–Course relationship with an `Enrollment` entity. This approach makes storing link attributes, managing lifecycles, querying, enforcing constraints, and extending business logic much clearer.

## 1. Why Is @ManyToMany No Longer Suitable?

Suppose there are two entities:

- `Student`: a student.
- `Course`: a course.

A student can join many courses; a course can have many students. If the link only needs two foreign keys, the join table can look like this:

~~~sql
CREATE TABLE student_courses (
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(id),
    FOREIGN KEY (course_id) REFERENCES courses(id)
);
~~~

In JPA, this can be mapped with `@ManyToMany` and `@JoinTable`. However, when business requirements need additional information:

- Enrollment timestamp.
- Enrollment status: ACTIVE, COMPLETED, CANCELLED.
- Final course score.
- Member's role in a group.
- Payment amount, quantity, note, or approver.

then the join table is no longer just a technical detail. Each row represents an enrollment event with its own lifecycle and rules. `@ManyToMany` does not provide an independent entity to hold those attributes and behaviors.

A better model is:

~~~text
Student 1 -------- * Enrollment * -------- 1 Course
                      |
                      +-- enrolledAt
                      +-- status
                      +-- score
                      +-- note
~~~

The original many-to-many relationship is split into two one-to-many and many-to-one relationships:

- One Student has many Enrollments.
- Each Enrollment belongs to one Student.
- One Course has many Enrollments.
- Each Enrollment belongs to one Course.

`Enrollment` is the entity representing the Student–Course link itself.

## 2. Database Table Design

The model consists of three tables:

| Table | Role | Key data |
|---|---|---|
| students | Stores students | id, name |
| courses | Stores courses | id, code, title |
| enrollments | Stores enrollments | id, student_id, course_id, enrolled_at, status, score, note |

Example DDL:

~~~sql
CREATE TABLE students (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL
);

CREATE TABLE courses (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code VARCHAR(40) NOT NULL UNIQUE,
    title VARCHAR(200) NOT NULL
);

CREATE TABLE enrollments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    student_id BIGINT NOT NULL,
    course_id BIGINT NOT NULL,
    enrolled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    status VARCHAR(20) NOT NULL,
    score DECIMAL(5, 2),
    note VARCHAR(500),
    version BIGINT NOT NULL DEFAULT 0,

    CONSTRAINT fk_enrollment_student
        FOREIGN KEY (student_id) REFERENCES students(id),

    CONSTRAINT fk_enrollment_course
        FOREIGN KEY (course_id) REFERENCES courses(id),

    CONSTRAINT uk_enrollment_student_course
        UNIQUE (student_id, course_id),

    CONSTRAINT chk_enrollment_status
        CHECK (status IN ('ACTIVE', 'COMPLETED', 'CANCELLED')),

    CONSTRAINT chk_enrollment_score
        CHECK (score IS NULL OR (score >= 0 AND score <= 100))
);

CREATE INDEX idx_enrollment_course_status
    ON enrollments(course_id, status);
~~~

The DDL above uses identity and timezone-aware timestamp syntax common in PostgreSQL/H2; exact syntax may need adjustment for your database engine. These constraints should be retained even if JPA mappings declare equivalents, because the database must protect data integrity against all write sources.

In this example, a student can only enroll once in a given course, hence `UNIQUE(student_id, course_id)`. If business rules allow re-enrolling by term, add `term_id` or `cohort_id` and change the unique constraint to `UNIQUE(student_id, course_id, term_id)`. Clarify business rules before choosing keys.

## 3. Mapping the Enrollment Entity

`Enrollment` is an independent entity with its own primary key. It holds two `@ManyToOne` relationships to `Student` and `Course`, along with the enrollment attributes.

~~~java
package example.domain;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;
import java.util.Objects;

@Entity
@Table(
    name = "enrollments",
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_enrollment_student_course",
            columnNames = {"student_id", "course_id"}
        )
    },
    indexes = {
        @Index(
            name = "idx_enrollment_course_status",
            columnList = "course_id,status"
        )
    }
)
public class Enrollment {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "student_id", nullable = false)
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "course_id", nullable = false)
    private Course course;

    @Column(name = "enrolled_at", nullable = false, updatable = false)
    private Instant enrolledAt;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private EnrollmentStatus status;

    @Column(precision = 5, scale = 2)
    private BigDecimal score;

    @Column(length = 500)
    private String note;

    @Version
    private long version;

    protected Enrollment() {
        // Constructor required by JPA.
    }

    public Enrollment(Instant enrolledAt) {
        this.enrolledAt = Objects.requireNonNull(enrolledAt);
        this.status = EnrollmentStatus.ACTIVE;
    }

    void assignStudent(Student student) {
        this.student = Objects.requireNonNull(student);
    }

    void assignCourse(Course course) {
        this.course = Objects.requireNonNull(course);
    }

    public void complete(BigDecimal score) {
        if (score == null
                || score.compareTo(BigDecimal.ZERO) < 0
                || score.compareTo(new BigDecimal("100")) > 0) {
            throw new IllegalArgumentException(
                "Score must be between 0 and 100"
            );
        }

        if (status == EnrollmentStatus.CANCELLED) {
            throw new IllegalStateException(
                "A cancelled enrollment cannot be completed"
            );
        }

        this.score = score;
        this.status = EnrollmentStatus.COMPLETED;
    }

    public void cancel() {
        if (status == EnrollmentStatus.COMPLETED) {
            throw new IllegalStateException(
                "A completed enrollment cannot be cancelled"
            );
        }

        this.status = EnrollmentStatus.CANCELLED;
    }

    public Long getId() {
        return id;
    }

    public Student getStudent() {
        return student;
    }

    public Course getCourse() {
        return course;
    }

    public Instant getEnrolledAt() {
        return enrolledAt;
    }

    public EnrollmentStatus getStatus() {
        return status;
    }

    public BigDecimal getScore() {
        return score;
    }

    public String getNote() {
        return note;
    }

    public long getVersion() {
        return version;
    }

    public void changeNote(String note) {
        this.note = note;
    }
}
~~~

Status enum:

~~~java
package example.domain;

public enum EnrollmentStatus {
    ACTIVE,
    COMPLETED,
    CANCELLED
}
~~~

Key points to note:

- `Enrollment` has its own `@Id`, so it can be managed, searched, updated, and deleted independently by a repository.
- Both `student` and `course` fields use `@ManyToOne` because multiple enrollments can reference the same student or the same course.
- `@JoinColumn` specifies that the foreign keys reside in the `enrollments` table.
- `FetchType.LAZY` defers loading `Student` and `Course` until needed; accessing them must occur within an active persistence context.
- `@Enumerated(EnumType.STRING)` stores the enum name. If custom storage codes are needed, an `AttributeConverter` can be used as covered in the data conversion lesson.
- `@Version` enables optimistic locking to detect concurrent updates.
- `complete()` and `cancel()` place state transition rules directly on the entity that owns the business behavior.

Do not add REMOVE cascade from `Enrollment` to `Student` or `Course`. Deleting an enrollment must not delete a student or course still referenced by other enrollments.

## 4. Bidirectional Mapping on Student and Course

If navigation from `Student` to its `Enrollment` list and from `Course` to its `Enrollment` list is needed, bidirectional relationships can be used.

Student:

~~~java
package example.domain;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "students")
public class Student {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @OneToMany(mappedBy = "student", fetch = FetchType.LAZY)
    private List<Enrollment> enrollments = new ArrayList<>();

    protected Student() {
    }

    public Student(String name) {
        this.name = name;
    }

    public void addEnrollment(Enrollment enrollment) {
        if (enrollment.getStudent() != null
                && enrollment.getStudent() != this) {
            throw new IllegalArgumentException(
                "Enrollment already belongs to another student"
            );
        }

        if (!enrollments.contains(enrollment)) {
            enrollments.add(enrollment);
        }

        enrollment.assignStudent(this);
    }

    public List<Enrollment> getEnrollments() {
        return Collections.unmodifiableList(enrollments);
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }
}
~~~

Course:

~~~java
package example.domain;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

@Entity
@Table(name = "courses")
public class Course {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 40)
    private String code;

    @Column(nullable = false, length = 200)
    private String title;

    @OneToMany(mappedBy = "course", fetch = FetchType.LAZY)
    private List<Enrollment> enrollments = new ArrayList<>();

    protected Course() {
    }

    public Course(String code, String title) {
        this.code = code;
        this.title = title;
    }

    public void addEnrollment(Enrollment enrollment) {
        if (enrollment.getCourse() != null
                && enrollment.getCourse() != this) {
            throw new IllegalArgumentException(
                "Enrollment already belongs to another course"
            );
        }

        if (!enrollments.contains(enrollment)) {
            enrollments.add(enrollment);
        }

        enrollment.assignCourse(this);
    }

    public List<Enrollment> getEnrollments() {
        return Collections.unmodifiableList(enrollments);
    }

    public Long getId() {
        return id;
    }

    public String getCode() {
        return code;
    }

    public String getTitle() {
        return title;
    }
}
~~~

In these two classes:

- `@OneToMany(mappedBy = "student")` points to the `student` field in `Enrollment`.
- `@OneToMany(mappedBy = "course")` points to the `course` field in `Enrollment`.
- `mappedBy` indicates that both collections are inverse sides; they do not own the foreign keys.
- `Enrollment` is the owning side because its `@ManyToOne` fields declare `@JoinColumn`.

JPA writes foreign keys based on the owning side. If you only add an `Enrollment` to `Student`'s collection without setting `student` on `Enrollment`, the relationship change may not be persisted as intended. The `addEnrollment()` methods update both sides so the object graph stays consistent in memory.

If the application does not need `Student` → `Enrollment` or `Course` → `Enrollment` navigation, you can omit both `@OneToMany` collections and keep only the two `@ManyToOne` mappings in `Enrollment`. This is often a simpler model and avoids unintended collection loading.

## 5. Creating Enrollment Instead of Adding Directly to @ManyToMany

With the old `@ManyToMany`, code typically looked like:

~~~java
student.getCourses().add(course);
~~~

This only expresses that two objects are linked. There is nowhere clear to set `enrolledAt`, `status`, or `score`.

With an association entity, the workflow becomes:

1. Find the existing Student.
2. Find the existing Course.
3. Validate enrollment rules.
4. Create `Enrollment`.
5. Assign both Student and Course.
6. Save `Enrollment`.

Service example:

~~~java
package example.service;

import example.domain.Course;
import example.domain.Enrollment;
import example.domain.Student;
import example.repository.CourseRepository;
import example.repository.EnrollmentRepository;
import example.repository.StudentRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Instant;

@Service
public class EnrollmentService {

    private final StudentRepository studentRepository;
    private final CourseRepository courseRepository;
    private final EnrollmentRepository enrollmentRepository;

    public EnrollmentService(
            StudentRepository studentRepository,
            CourseRepository courseRepository,
            EnrollmentRepository enrollmentRepository) {
        this.studentRepository = studentRepository;
        this.courseRepository = courseRepository;
        this.enrollmentRepository = enrollmentRepository;
    }

    @Transactional
    public Enrollment enroll(Long studentId, Long courseId) {
        Student student = studentRepository.findById(studentId)
            .orElseThrow(() ->
                new IllegalArgumentException("Student not found"));

        Course course = courseRepository.findById(courseId)
            .orElseThrow(() ->
                new IllegalArgumentException("Course not found"));

        if (enrollmentRepository
                .existsByStudent_IdAndCourse_Id(studentId, courseId)) {
            throw new IllegalStateException(
                "Student is already enrolled in this course"
            );
        }

        Enrollment enrollment = new Enrollment(Instant.now());

        student.addEnrollment(enrollment);
        course.addEnrollment(enrollment);

        return enrollmentRepository.save(enrollment);
    }

    @Transactional
    public void complete(Long enrollmentId,
                         java.math.BigDecimal score) {
        Enrollment enrollment = enrollmentRepository.findById(enrollmentId)
            .orElseThrow(() ->
                new IllegalArgumentException("Enrollment not found"));

        enrollment.complete(score);
    }

    @Transactional
    public void cancel(Long enrollmentId) {
        Enrollment enrollment = enrollmentRepository.findById(enrollmentId)
            .orElseThrow(() ->
                new IllegalArgumentException("Enrollment not found"));

        enrollment.cancel();
    }
}
~~~

`Student` and `Course` are loaded within the transaction and are therefore managed entities. When saving `Enrollment`, JPA writes both foreign keys `student_id` and `course_id` along with the remaining attributes.

PERSIST cascade from `Enrollment` to `Student` and `Course` is unnecessary here because both already exist. Misconfigured cascade could cause saving an enrollment to try re-creating or unexpectedly affecting related entities.

`complete()` and `cancel()` do not call `repository.save()` again. The entity is already managed in the transaction; dirty checking detects changes and the provider synchronizes them on flush or commit.

## 6. Repositories for the Association Entity

Each entity can have its own repository:

~~~java

import example.domain.Student;
import org.springframework.data.jpa.repository.JpaRepository;

public interface StudentRepository
        extends JpaRepository<Student, Long> {
}
~~~

~~~java
package example.repository;

import example.domain.Course;
import org.springframework.data.jpa.repository.JpaRepository;

public interface CourseRepository
        extends JpaRepository<Course, Long> {
}
~~~

~~~java
package example.repository;

import example.domain.Enrollment;
import example.domain.EnrollmentStatus;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;
import java.util.Optional;

public interface EnrollmentRepository
        extends JpaRepository<Enrollment, Long> {

    boolean existsByStudent_IdAndCourse_Id(
        Long studentId,
        Long courseId
    );

    Optional<Enrollment> findByStudent_IdAndCourse_Id(
        Long studentId,
        Long courseId
    );

    List<Enrollment> findAllByStudent_IdOrderByEnrolledAtDesc(
        Long studentId
    );

    @Query("""
        select e
        from Enrollment e
        join fetch e.course
        where e.student.id = :studentId
          and e.status = :status
        """)
    List<Enrollment> findWithCourseByStudentAndStatus(
        @Param("studentId") Long studentId,
        @Param("status") EnrollmentStatus status
    );
}
~~~

Derived query methods use property paths:

- `Student_Id` traverses the `student` relationship and accesses `id`.
- `Course_Id` traverses the `course` relationship and accesses `id`.
- `existsByStudent_IdAndCourse_Id` checks whether a link pair already exists.
- `findByStudent_IdAndCourse_Id` retrieves the association entity by both endpoints.

The underscore helps Spring Data clearly separate the relationship name from the `id` property. If property names are complex or ambiguous, `@Query` can express the query more clearly.

## 7. Querying Data by Link Attributes

Once `Enrollment` exists, you can query directly by status, timestamp, score, or fields of `Student`/`Course`.

Example finding active enrollments for a course:

~~~java
@Query("""
    select e
    from Enrollment e
    where e.course.id = :courseId
      and e.status = :status
    order by e.enrolledAt desc
    """)
List<Enrollment> findByCourseAndStatus(
    @Param("courseId") Long courseId,
    @Param("status") EnrollmentStatus status
);
~~~

Finding students who completed a course with a score of 80 or above:

~~~java
@Query("""
    select e
    from Enrollment e
    where e.course.id = :courseId
      and e.status = example.domain.EnrollmentStatus.COMPLETED
      and e.score >= :minimumScore
    """)
List<Enrollment> findHighScoringEnrollments(
    @Param("courseId") Long courseId,
    @Param("minimumScore") BigDecimal minimumScore
);
~~~

In JPQL, you can pass the enum as a parameter for better reusability:

~~~java
@Query("""
    select e
    from Enrollment e
    where e.course.id = :courseId
      and e.status = :status
      and e.score >= :minimumScore
    """)
List<Enrollment> findByCourseStatusAndMinimumScore(
    @Param("courseId") Long courseId,
    @Param("status") EnrollmentStatus status,
    @Param("minimumScore") BigDecimal minimumScore
);
~~~

An association entity lets you query link-level data directly without loading full `Student` or `Course` graphs and filtering in Java.

## 8. Pagination and DTOs

A course may have thousands of enrollments. Never load the entire list into memory when you only need to display one page at a time.

A repository can return a `Page`:

~~~java
Page<Enrollment> findAllByCourse_Id(
    Long courseId,
    Pageable pageable
);
~~~

The service receives `Pageable` and returns the appropriate result. For APIs, map entities to DTOs inside the transaction or use projections to fetch only the required columns.

Example DTO record:

~~~java
package example.dto;

import example.domain.EnrollmentStatus;
import java.math.BigDecimal;
import java.time.Instant;

public record EnrollmentSummary(
    Long enrollmentId,
    String studentName,
    String courseCode,
    String courseTitle,
    EnrollmentStatus status,
    BigDecimal score,
    Instant enrolledAt
) {
}
~~~

JPQL projection:

~~~java
@Query(
    value = """
        select new example.dto.EnrollmentSummary(
            e.id,
            e.student.name,
            e.course.code,
            e.course.title,
            e.status,
            e.score,
            e.enrolledAt
        )
        from Enrollment e
        where e.course.id = :courseId
        """,
    countQuery = """
        select count(e)
        from Enrollment e
        where e.course.id = :courseId
        """
)
Page<EnrollmentSummary> findSummariesByCourseId(
    @Param("courseId") Long courseId,
    Pageable pageable
);
~~~

Projections avoid exposing entities out of the API and prevent lazy loading errors after the transaction ends. They also reduce the amount of data loaded when the UI only needs a subset of fields.

## 9. Choosing a Primary Key for Enrollment

There are two common design choices.

### 9.1. Surrogate Key

The main example uses:

~~~java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
~~~

The `enrollments` table has its own `id`, while the `(student_id, course_id)` pair is protected by a UNIQUE constraint.

Advantages:

- Repositories operate on a simple single ID.
- DTOs and URLs can reference a specific enrollment cleanly.
- Easy to add more business attributes.
- Less complex JPA mapping.

The drawback is an extra primary key column in the table. If the student/course pair is the natural unique identifier, retain the unique constraint to prevent duplicate records.

### 9.2. Composite Primary Key

If the Student–Course pair itself is the stable identifier of the link, you can use `@EmbeddedId` and `@MapsId`:

~~~java
@Embeddable
public class EnrollmentId implements Serializable {

    private Long studentId;
    private Long courseId;

    protected EnrollmentId() {
    }

    public EnrollmentId(Long studentId, Long courseId) {
        this.studentId = studentId;
        this.courseId = courseId;
    }

    // Implement equals() and hashCode() based on both IDs.
}
~~~

~~~java
@Entity
@Table(name = "enrollments")
public class Enrollment {

    @EmbeddedId
    private EnrollmentId id;

    @MapsId("studentId")
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "student_id")
    private Student student;

    @MapsId("courseId")
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "course_id")
    private Course course;

    // Fields such as enrolledAt, status, score...
}
~~~

This is an illustrative outline; constructors, `equals`/`hashCode`, and key initialization must be completed for your application. `@MapsId` synchronizes the embedded ID's key parts with the IDs of the associated entities.

A composite key can work well when the link exists uniquely for a single pair. If re-enrollment per term is allowed, the term must be added to the key, or you should use a surrogate key with a business unique constraint. Do not pick a composite key just to save one column if it makes repository and API operations harder.

## 10. Cascade, Orphan Removal, and Lifecycle

An association entity has its own lifecycle. Clearly define who owns the data and what happens when a `Student` or `Course` is deleted.

- Do not cascade REMOVE from `Enrollment` to `Student` or `Course`.
- If `Enrollment` represents business history, usually keep the record and change status to `CANCELLED` instead of physically deleting it.
- If a link is purely dependent data inside a parent aggregate, PERSIST cascade or `orphanRemoval` on the `@OneToMany` side may be considered.
- `orphanRemoval=true` means removing the association entity from the collection can delete the corresponding row on flush. Enable this only when business rules truly require it.
- If `Enrollment` has payments, approvals, history, or auditing, physical deletion can destroy business evidence; consider soft deletes or terminal statuses instead.

In this example, `Student` and `Course` do not cascade to `Enrollment`. The service saves `Enrollment` explicitly via `EnrollmentRepository`. This keeps operation boundaries readable and prevents saving a `Student` from unexpectedly pulling in many enrollments.

## 11. Bidirectional Synchronization and Owning Side

In a bidirectional relationship, `Enrollment` is the owning side because it holds `@JoinColumn`. `Student.enrollments` and `Course.enrollments` are inverse sides because they use `mappedBy`.

If you only update an inverse collection, JPA does not receive the new owning-side reference to write the foreign key. Therefore, provide helper methods on entities to update both sides together.

Rules:

1. Relationship changes on `Enrollment` must update its `student`/`course` fields.
2. If an inverse collection is loaded, update the collection so the object graph stays consistent.
3. Do not set a NOT NULL relationship to null while the entity is still retained.
4. Do not base `equals`/`hashCode` on entire relationship collections; this can cause recursion, unintended lazy loading, or hash changes as entity state evolves.

If navigation from `Student`/`Course` is not needed, omit the inverse collections and keep only the unidirectional links from `Enrollment` to the two entities. That reduces the number of helpers to maintain.

## 12. Performance and N+1 Queries

When loading a list of `Enrollment`s and then accessing each `Course`, if the `@ManyToOne` relationship is LAZY, the provider may issue one query for enrollments plus many queries for courses. This is the N+1 problem.

Handle it according to need:

- Use `JOIN FETCH` when `Course` must be loaded alongside `Enrollment` in one query.
- Use `@EntityGraph(attributePaths = "course")` for a repository method.
- Use DTO projections to select only the fields needed for display.
- Paginate in the database when lists are large.
- Create indexes matching common filter conditions such as `course_id`, `student_id`, and `status`.
- Inspect execution plans and actual SQL when performance falls short.

The `JOIN FETCH` example in the repository section loads `Course` for a list of `Enrollment`s. Because `Course` is a `@ManyToOne` relationship, each `Enrollment` references only one `Course`. With collection fetch joins and pagination, be especially careful because SQL row counts can multiply and pagination results become non-trivial.

Do not load the entire `Enrollment` list into Java and filter with Streams when the database can execute `WHERE`, `ORDER BY`, and `LIMIT` far more efficiently.

## 13. Transactions and Concurrent Updates

Creating, completing, or canceling an `Enrollment` is a business operation that should run inside a transaction.

For example, checking if a Student–Course pair already exists and then creating an `Enrollment`. If two concurrent requests register the same pair simultaneously, both can pass the `existsBy...` check before either writes data.

Therefore, the service check provides early feedback, while `UNIQUE(student_id, course_id)` in the database serves as the final safeguard protecting data integrity. The application should catch unique constraint violations and translate them into appropriate business responses.

`@Version` on `Enrollment` detects two transactions modifying the same record concurrently. If one transaction commits first, the other can receive an optimistic locking exception at flush/commit because the version has changed. The application can instruct the user to reload and retry according to business rules.

Not every concurrency error should be retried automatically. Distinguish transient errors suitable for retry from conflicts requiring user or business resolution.

## 14. Migrating from an Existing @ManyToMany Join Table

If the system already uses a `student_courses` table, the migration must preserve existing data.

A migration process can include:

1. Inventory existing columns, primary keys, foreign keys, unique constraints, and indexes.
2. Add an `id` column to the join table if switching to a surrogate key.
3. Add new business columns such as `enrolled_at`, `status`, `score`, and `note`.
4. Backfill values for existing rows. For example, set status to `ACTIVE` and use the migration timestamp or suitable historical data for `enrolled_at`.
5. Create the new primary key and retain the unique constraint on `(student_id, course_id)` if business rules still require it.
6. Update entity mappings to map the join table to `Enrollment`.
7. Update repositories, services, DTOs, and JPQL/native SQL queries that used the `@ManyToMany` relationship.
8. Run integration tests on a copy of the data or a staging migration environment.
9. Deploy in an order compatible with running application versions.
10. Remove old mappings and code only after confirming all flows have moved to `Enrollment`.

Do not add new NOT NULL columns without defaults or backfills for existing records. Also do not change mappings before the production schema is ready.

If multiple applications read the join table concurrently, coordinate deployment timing and ensure older versions can still read data during the transition period.

## 15. When Is an Association Entity the Right Choice?

| Scenario | Modeling approach |
|---|---|
| Link only has two foreign keys, no extra data | `@ManyToMany` may suffice |
| Link has creation date, status, score, role, or quantity | Association entity |
| Link has a workflow, approval, or history | Association entity |
| Link needs its own repository, API, or authorization | Association entity |
| Link must be searched, paginated, or reported independently | Association entity |
| A pair can appear multiple times over time | Association entity with a key/unique constraint adding context |

Do not create an association entity just to have another class. Create one when the link genuinely carries business data or behavior, or when it needs to be managed independently.

## 16. Common Pitfalls

**1. Keeping @ManyToMany while adding business fields to the join table**

JPA does not provide a separate entity to map join table attributes in a standard `@ManyToMany` model. Replace it with an association entity containing two `@ManyToOne` mappings.

**2. Updating only the inverse collection**

If you only add `Enrollment` to `Student.enrollments` without setting `Enrollment.student`, the owning side is not updated. Use helper methods that synchronize both sides.

**3. REMOVE cascade deleting main entities**

Deleting an `Enrollment` must not delete a `Student` or `Course`. Do not put `CascadeType.REMOVE` from `@ManyToOne` associations toward the two main entities.

**4. Forgetting the unique constraint**

Calling `exists` in Java is not enough against two concurrent requests. The database must enforce a unique constraint for the business key.

**5. Using a composite key without implementing equals/hashCode**

Embedded IDs require equality based on all key components. Missing or incorrect implementations break persistence and collection behavior.

**6. Returning entities directly from REST APIs**

Entities may hold lazy relationships and bidirectional reference cycles. Use DTOs or projections to control the returned payload.

**7. Loading large collections at once**

Accessing all `Enrollment`s of a `Student` or `Course` can consume memory and trigger many queries. Use paginated repository queries.

**8. Changing converters or enums while forgetting legacy data**

If `status` is stored as enum strings, renaming enum constants can make old rows unreadable. Use stable codes or compatible migrations.

**9. Enabling orphanRemoval out of habit**

If `Enrollment` is business history, automatically deleting rows when removed from a collection can cause data loss. Choose lifecycle policies according to actual requirements.

## 17. Testing the Association Entity

Include the following test suites:

**Domain unit tests**

- Creating an `Enrollment` initializes with status `ACTIVE`.
- Completing with a valid score succeeds.
- Negative scores or scores above 100 are rejected.
- Completing a cancelled `Enrollment` is disallowed.
- Reassigning an `Enrollment` to a different `Student` or `Course` after it already belongs to one is disallowed.

**Repository integration tests**

- Saving `Enrollment` persists both foreign keys.
- Reading back `Student` and `Course` through relationships works.
- Derived queries by `studentId`/`courseId` work.
- JPQL filtering by `status` and `score` works.
- Unique constraint violation is verified on duplicate pairs.
- Pagination and projections work.

**Service integration tests**

- Enrolling succeeds.
- Nonexistent `studentId` or `courseId` is rejected.
- Duplicate enrollment is rejected.
- Completing and canceling follow status transition rules.
- Transaction rollback is verified when a business step fails.
- Optimistic locking is verified under concurrent updates.

Use a database compatible with production for tests that rely on SQL, constraints, or locking. H2 is useful for fast tests but can differ from PostgreSQL/MySQL in DDL, data types, and transaction behavior.

## 19. Review Questions

**1. When should @ManyToMany be replaced with an association entity?**

When each link row has its own attributes or behavior such as timestamps, status, score, role, quantity, approval, or history.

**2. In the Student–Enrollment–Course model, which entity owns the foreign keys?**

`Enrollment` owns both foreign keys because its `@ManyToOne` fields declare `@JoinColumn`. The `@OneToMany` collections in `Student` and `Course` are inverse sides.

**3. Why is a unique constraint needed when the service already checks exists?**

Because two concurrent transactions can both observe that the row does not exist and both attempt to insert. A database constraint enforces uniqueness atomically.

**4. Should REMOVE cascade from Enrollment to Student and Course?**

No, because `Student` and `Course` are independent entities that may be referenced by many `Enrollment`s. Deleting one link must not delete the two main entities.

**5. Should you choose a surrogate key or a composite key?**

A surrogate key is usually simpler for repositories and APIs; a composite key fits when the natural key pair is truly a stable identifier. The decision depends on business rules and whether pairs can recur over time.

**6. How do you avoid N+1 queries when displaying an enrollment list with course titles?**

Use a fetch join or `EntityGraph` for the relationships that need loading, or use a DTO projection to select only the required display fields. Combine with pagination and inspect the actual SQL.

By modeling the link as a separate entity, `Enrollment` can carry its own data, rules, and lifecycle. This is the right design approach whenever a many-to-many relationship becomes a first-class business concept in the system.
