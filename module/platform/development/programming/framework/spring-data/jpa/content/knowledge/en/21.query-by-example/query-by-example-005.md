# Handling Primitive Default Values in Probes

In Spring Data JPA, **Query by Example (QBE)** builds query conditions from a sample object called a *probe*. Populated properties in the probe are typically used as search criteria; `null` properties are ignored by default. This creates an easily overlooked issue with Java primitive types: `int` defaults to `0`, `boolean` defaults to `false`, and other primitives also have specific default values. They cannot be `null`, so QBE can treat them as filter conditions even when the caller never supplied a value.

For example, a new Product probe has `stock = 0` and `active = false`. If you only want to search by name without ignoring these two properties, QBE may search for products with stock equal to 0 and active=false. The appropriate fix is usually to use wrappers (`Integer`, `Boolean`) for optional criteria, or to actively add properties to `withIgnorePaths` when the corresponding filters are not provided.

## 1. How do probes and Query by Example work?

QBE is a way to build queries using a sample object instead of writing JPQL/SQL for every combination of conditions. The probe holds the values to search for; `ExampleMatcher` decides how properties are matched.

The repository needs to extend `QueryByExampleExecutor<T>`:

```java
public interface ProductRepository
        extends JpaRepository<Product, Long>,
                QueryByExampleExecutor<Product> {
}
```

Example creating a probe:

```java
Product probe = new Product();
probe.setName("Tea");

Example<Product> example = Example.of(probe);
List<Product> products = productRepository.findAll(example);
```

With the default configuration, null properties are typically ignored, while populated properties are used to build conditions. For String, the default is exact matching; non-String properties are also matched by exact value.

Example of query semantics:

```text
Probe:
  name = "Tea"
  category = null

QBE condition:
  name = 'Tea'

category is ignored because it is null.
```

QBE fits simple equality conditions and basic AND/OR combinations. It is not a general-purpose tool for every search expression; range conditions, complex joins, or special business logic usually fit Specification, Criteria API, QueryDSL, or explicit queries better.

## 2. Primitive default values in Java

When an object is created without assigning values to primitive fields, Java initializes those fields with default values:

| Primitive type | Default value |
|---|---|
| `byte` | `0` |
| `short` | `0` |
| `int` | `0` |
| `long` | `0L` |
| `float` | `0.0f` |
| `double` | `0.0d` |
| `char` | `'\u0000'` (NUL character) |
| `boolean` | `false` |

Reference fields such as `Integer`, `Long`, `Boolean`, and `String` default to `null` if unassigned.

Example:

```java
public class ProductProbe {
    private int stock;
    private boolean active;
    private Integer minRating;
    private Boolean featured;
}
```

Right after `new ProductProbe()`:

```text
stock     = 0
active    = false
minRating = null
featured  = null
```

Important difference: primitives always hold a value; wrappers can represent an unprovided state using null. Because QBE ignores null by default, wrappers let you distinguish "do not filter on this property" from "filter by 0/false".

Note: constructors, field initializers, or builders can override Java's default values. QBE uses the actual values present in the probe at the time the Example is created; it does not infer whether the user supplied a property.

## 3. Why do primitives cause unintended filtering?

Suppose an entity:

```java
@Entity
@Table(name = "product")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private int stock;

    private boolean active;

    protected Product() {
    }

    // getters/setters
}
```

Create a new probe and set only the name:

```java
Product probe = new Product();
probe.setName("Tea");

Example<Product> example = Example.of(probe);
List<Product> result = repository.findAll(example);
```

The probe holds these values:

```text
id     = null
name   = "Tea"
stock  = 0
active = false
```

The two primitive fields are non-null by Java's nature. QBE can generate an equivalent condition:

```sql
where name = 'Tea'
  and stock = 0
  and active = false
```

The SQL above only illustrates predicate intent. Actual SQL is generated by the provider and database.

Results may be empty or contain only products named Tea with stock equal to 0 and active=false. The author might think they are filtering only by name, yet the probe carried along the default primitive values.

## 4. Preferred approach: use wrappers for optional criteria

If a property might not be used as a filter, wrappers are usually the natural choice:

```java
@Entity
@Table(name = "product")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;

    private Integer stock;

    private Boolean active;

    protected Product() {
    }

    // getters/setters
}
```

Create a probe:

```java
Product probe = new Product();
probe.setName("Tea");
// stock and active remain null so they are ignored by default.

ExampleMatcher matcher = ExampleMatcher.matching()
    .withIgnoreNullValues();

Example<Product> example = Example.of(probe, matcher);
List<Product> result = repository.findAll(example);
```

When you explicitly want to filter by stock=0 or active=false:

```java
probe.setStock(0);
probe.setActive(false);

Example<Product> example = Example.of(
    probe,
    ExampleMatcher.matching().withIgnoreNullValues()
);
```

Now 0 and false are non-null wrapper values, so they are valid criteria. Wrappers allow expressing three common business states:

- `null`: do not filter on this property.
- `0`: filter for the exact numeric value 0.
- Valid positive/negative number: filter by the specific value.

For Boolean:

- `null`: do not filter by active.
- `true`: fetch only active=true.
- `false`: fetch only active=false.

Do not write checks like `if (filter.getActive())` to decide whether to apply a filter; that drops the intentional false case. Check `filter.getActive() != null` instead.

## 5. Complete example with filter DTO and QBE

In real applications, separate search input from the entity. The DTO uses wrappers to represent filters that may be absent:

```java
public record ProductFilter(
    String name,
    Integer stock,
    Boolean active
) {
}
```

Repository:

```java
public interface ProductRepository
        extends JpaRepository<Product, Long>,
                QueryByExampleExecutor<Product> {
}
```

Service:

```java
@Service
public class ProductSearchService {

    private final ProductRepository repository;

    public ProductSearchService(ProductRepository repository) {
        this.repository = repository;
    }

    public List<Product> search(ProductFilter filter) {
        Product probe = new Product();
        probe.setName(filter.name());
        probe.setStock(filter.stock());
        probe.setActive(filter.active());

        ExampleMatcher matcher = ExampleMatcher.matching()
            .withIgnoreNullValues()
            .withMatcher("name", spec ->
                spec.contains().ignoreCase()
            );

        return repository.findAll(Example.of(probe, matcher));
    }
}
```

Example input:

```json
{
  "name": "tea",
  "stock": 0,
  "active": false
}
```

All three criteria have values and are applied. If the request sends only name, stock and active are null so those two properties are ignored.

If the DTO accepted `active` as a primitive boolean, a request omitting active would still become false after deserialization. The service could then not distinguish "active omitted" from "active=false sent". Use `Boolean` in the request DTO to preserve this distinction.

If an API needs to distinguish both "field omitted" and "field sent with JSON null", plain wrappers alone may not suffice because both usually become null after binding. When those semantics matter, use a field-presence tracking mechanism appropriate for your framework/API contract.

## 6. When the entity must use primitives: withIgnorePaths

Sometimes an entity uses primitives appropriately because the domain/database requires a value to always be present. You do not necessarily have to change entity fields just for QBE. You can use `ExampleMatcher.withIgnorePaths(...)` to exclude primitives that are not filters in the current query.

Example entity keeping primitives:

```java
@Entity
public class Product {
    @Id
    @GeneratedValue
    private Long id;

    private String name;

    private int stock;

    private boolean active;

    protected Product() {
    }

    // getters/setters
}
```

If this search filters only by name, ignoring stock and active:

```java
Product probe = new Product();
probe.setName("Tea");

ExampleMatcher matcher = ExampleMatcher.matching()
    .withIgnorePaths("stock", "active", "id")
    .withMatcher("name", spec ->
        spec.contains().ignoreCase()
    );

List<Product> result = repository.findAll(
    Example.of(probe, matcher)
);
```

Path names in `withIgnorePaths` are Java property names of the domain type, not database column names. Include only the properties that should be ignored in that query.

Do not hardcode `withIgnorePaths("stock", "active")` if some requests need to filter by stock or active. A path ignored in the matcher cannot simultaneously serve as a condition in that Example. Build different matchers depending on the filters.

## 7. Building ignorePaths dynamically for optional filters

If the entity has primitives but the API must allow filtering by 0 and false when explicitly sent by the user, use wrappers in the DTO to know whether the field was supplied; then build ignored paths dynamically.

```java
public record ProductFilter(
    String name,
    Integer stock,
    Boolean active
) {
}
```

Service:

```java
public List<Product> search(ProductFilter filter) {
    Product probe = new Product();
    probe.setName(filter.name());

    List<String> ignoredPaths = new ArrayList<>();

    if (filter.stock() == null) {
        ignoredPaths.add("stock");
    } else {
        probe.setStock(filter.stock());
    }

    if (filter.active() == null) {
        ignoredPaths.add("active");
    } else {
        probe.setActive(filter.active());
    }

    ExampleMatcher matcher = ExampleMatcher.matching()
        .withIgnoreNullValues()
        .withIgnorePaths(ignoredPaths.toArray(String[]::new))
        .withMatcher("name", spec ->
            spec.contains().ignoreCase()
        );

    return repository.findAll(Example.of(probe, matcher));
}
```

This handles both cases:

| Filter input | Probe primitive | Matcher | Result |
|---|---:|---|---|
| stock omitted | default 0 | ignore stock | Does not filter stock |
| stock = 0 | 0 | do not ignore stock | Filters stock=0 |
| active omitted | default false | ignore active | Does not filter active |
| active = false | false | do not ignore active | Filters active=false |
| active = true | true | do not ignore active | Filters active=true |

The key is deciding whether to ignore based on the presence of the filter DTO field (wrapper), not on whether the primitive value differs from 0/false.

## 8. withIgnoreNullValues and withIncludeNullValues

By default, QBE ignores null properties. You can make this explicit with:

```java
ExampleMatcher matcher = ExampleMatcher.matching()
    .withIgnoreNullValues();
```

If you want null to become a search criterion, use:

```java
ExampleMatcher matcher = ExampleMatcher.matching()
    .withIncludeNullValues();
```

With include null values, null properties are used to find rows with corresponding NULL values according to mapping/provider capabilities. This is usually not what you want for optional filter forms.

Distinction:

- **Ignore null:** generates no condition for null properties.
- **Include null:** generates a condition searching for null values.
- **Primitive:** cannot be null, so ignoreNullValues does not skip default 0/false values.
- **Ignore path:** ignores a property regardless of its value.

Therefore, `withIgnoreNullValues()` does not solve the primitive default problem. To skip primitives, you must use wrappers or ignore paths.

## 9. Constructors and field initializers also affect probes

Not every probe starts with raw Java default values. Constructors or field initializers can assign other values:

```java
public class Product {
    private int stock = 10;
    private boolean active = true;
}
```

After `new Product()`, the probe has stock=10 and active=true. QBE may treat both values as criteria if those paths are not ignored.

Builders can also set defaults:

```java
Product probe = Product.builder()
    .active(true)
    .build();
```

Inspect all probe values before creating an Example. Do not look only for uninitialized primitive fields; any non-null property can affect QBE conditions.

## 10. Primitives in JSON requests and distinguishing omitted fields

The same issue appears before the probe is even constructed. Suppose a REST request:

```java
public class ProductSearchRequest {
    private boolean active;
    private int stock;
}
```

If the client sends:

```json
{
  "name": "Tea"
}
```

After deserialization, active is typically false and stock is 0 because those are Java object defaults. The service may accidentally treat them as filters that were sent.

Use wrappers:

```java
public class ProductSearchRequest {
    private Boolean active;
    private Integer stock;
}
```

When fields are absent from JSON, they usually remain null; when false or 0 is sent, the value is preserved. Then convert the request to ProductFilter or build the probe directly.

Do not use false/0 as a sentinel meaning "do not filter" if false/0 is also valid data. API design must clearly separate filter absence from filter values.

## 11. Do not confuse Java default, database DEFAULT, and NULL

These three concepts are distinct:

| Concept | When it happens | Example |
|---|---|---|
| Java primitive default | When instantiating an object without assigning the field | `int stock = 0` |
| SQL DEFAULT | During INSERT when a column is omitted or the DEFAULT keyword is used per database syntax | `stock integer default 0` |
| SQL NULL | Missing/unknown value in a nullable column | `stock is null` |

QBE reads values from the probe object to build WHERE conditions. It does not ask the database to apply DEFAULT and does not automatically turn primitive 0 into NULL.

For example, a database column having `DEFAULT 10` does not turn a primitive probe `stock=0` into 10. DEFAULT is an INSERT rule; a probe is input data for a SELECT query.

Similarly, `@Column(nullable = false)` or database NOT NULL only describes a storage constraint. It does not cause QBE to ignore a primitive field in a probe.

## 12. QBE and matching limitations

QBE is useful for property-based search, but it has limitations:

- Properties are matched by equality by default, except when a string matcher is configured.
- Does not directly express `stock >= 10`, date ranges, or complex calculations.
- Does not support all forms of nested/grouped predicates or collection matching.
- `matchingAll()` is AND between conditions; `matchingAny()` is OR.
- Null properties are ignored by default unless include null is enabled.
- Primitive properties cannot represent an unprovided state using null.

For example, if business rules require stock of 10 or more, QBE is not a natural fit. Use JPQL:

```java
@Query("""
    select p
    from Product p
    where (:minimumStock is null or p.stock >= :minimumStock)
    """)
List<Product> findByMinimumStock(
    @Param("minimumStock") Integer minimumStock
);
```

Or use Specification/Criteria API to build dynamic conditions.

## 13. When to use QBE, Specification, or @Query?

| Requirement | Suitable tool |
|---|---|
| Search across multiple simple equality properties | Query by Example |
| String contains/startsWith/ignoreCase | ExampleMatcher |
| Optional filters with null wrappers | QBE or Specification |
| Filtering on primitives while distinguishing 0/false from omitted | Wrappers in request + wrapper probe or dynamic ignorePaths |
| Greater-than/less-than, BETWEEN comparisons | Specification, Criteria API, or JPQL |
| Complex nested OR/AND | Specification, Criteria API, QueryDSL, or @Query |
| Multi-table joins/reports | JPQL/native SQL or QueryDSL |
| Fixed query needing performance control | @Query JPQL/native SQL |

Do not force QBE to handle every kind of search. Choose the abstraction based on the business expressions actually required.

## 14. Testing primitive default cases

An integration test should verify that a fresh probe does not accidentally filter by 0/false when those filters are not provided.

Example with an entity having wrapper fields:

```java
@DataJpaTest
class ProductExampleTest {

    @Autowired
    private ProductRepository repository;

    @Test
    void ignoresOptionalFiltersWhenTheyAreNull() {
        repository.save(new Product("Tea", 0, false));
        repository.save(new Product("Tea", 8, true));
        repository.flush();

        Product probe = new Product();
        probe.setName("Tea");
        // stock and active are unassigned so they are null.

        Example<Product> example = Example.of(
            probe,
            ExampleMatcher.matching().withIgnoreNullValues()
        );

        List<Product> results = repository.findAll(example);

        assertThat(results).hasSize(2);
    }

    @Test
    void canSearchExplicitZeroAndFalse() {
        Product probe = new Product();
        probe.setName("Tea");
        probe.setStock(0);
        probe.setActive(false);

        Example<Product> example = Example.of(
            probe,
            ExampleMatcher.matching().withIgnoreNullValues()
        );

        List<Product> results = repository.findAll(example);

        assertThat(results).hasSize(1);
    }
}
```

The example assumes the entity has a constructor `Product(String, Integer, Boolean)`, the repository extends QueryByExampleExecutor, and test data is cleaned between tests. The test runs under `@DataJpaTest`; it cannot run standalone using `javac` alone.

For entities with primitives, write dedicated tests for the dynamic matcher:

- Filter omits stock: stock is in ignorePaths.
- Filter sends stock=0: stock is not in ignorePaths and the query filters for 0.
- Filter omits active: active is ignored.
- Filter sends active=false: active is included in the predicate.
- Constructors/field initializers do not accidentally add other properties to the probe.

## 15. Checklist before creating an Example

- [ ] Does the probe have any primitive fields?
- [ ] Which primitives could become unintended filters due to 0/false?
- [ ] Does the filter DTO use wrappers to distinguish omitted from 0/false?
- [ ] Are null probe wrappers ignored as required?
- [ ] If the entity keeps primitives, does the matcher build dynamic ignorePaths for omitted properties?
- [ ] Do field initializers or constructors set non-default values?
- [ ] Was includeNullValues accidentally used, turning nulls into IS NULL conditions?
- [ ] Is the string matcher configured properly for exact/contains/startsWith and ignoreCase?
- [ ] Do range or complex join requirements exceed QBE's capabilities?
- [ ] Do integration tests cover 0, false, null, and omitted filters?
- [ ] Are Java defaults, SQL DEFAULT, and SQL NULL kept clearly distinct?

## 16. Conclusion

QBE builds conditions from current values in the probe. Nulls are normally ignored, but primitives cannot be null: `int` starts at 0, `boolean` starts at false, so those values can become unintended predicates.

For optional search criteria, prefer wrappers such as `Integer` and `Boolean` in probes/request DTOs so null represents "do not filter", while 0/false remain valid values. If an entity must keep primitives, use `ExampleMatcher.withIgnorePaths` built dynamically based on whether each filter was provided. `withIgnoreNullValues()` does not eliminate primitive defaults.

Finally, check probe values before creating an Example and write integration tests for omitted, 0, false, and null cases. If a query needs ranges or complex logic, switch to Specification/Criteria API or JPQL instead of pushing QBE beyond its capabilities.
