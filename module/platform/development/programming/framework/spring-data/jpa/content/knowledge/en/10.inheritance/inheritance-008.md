# Trade-offs Between Data Integrity, Extensibility, and Performance

## Objectives

After this lesson, you can evaluate entity inheritance mapping approaches in JPA across three criteria: data integrity, model extensibility, and read/write performance. You will distinguish `SINGLE_TABLE`, `JOINED`, `TABLE_PER_CLASS`, and `@MappedSuperclass`; understand each option's impact on schemas, foreign keys, constraints, polymorphic queries, and migrations; and choose the strategy that fits your data lifecycle and real application workload.

## 1. The Inheritance Problem in JPA

In Java, inheritance lets a subclass reuse attributes and behavior from a superclass. For example, `CardPayment` and `BankTransfer` are both types of `PaymentMethod`, yet each has its own data.

```java
public abstract class PaymentMethod {
    private Long id;
    private String owner;
}

public class CardPayment extends PaymentMethod {
    private String lastFourDigits;
}

public class BankTransfer extends PaymentMethod {
    private String bankCode;
}
```

The code above only describes object-oriented relationships. For JPA to persist an entity hierarchy, you must decide how superclass and subclass attributes map onto tables. That choice directly shapes the database structure and the SQL generated by the provider.

JPA defines three entity inheritance strategies:

- `InheritanceType.SINGLE_TABLE`: the entire hierarchy resides in one table.
- `InheritanceType.JOINED`: the parent class and each subclass have separate tables linked by primary key/foreign key.
- `InheritanceType.TABLE_PER_CLASS`: each concrete entity class has its own table, including inherited attributes.

Additionally, `@MappedSuperclass` allows sharing mappings from a parent class without creating a dedicated entity or table for the parent class. It is a mapping-reuse mechanism, not an `InheritanceType` value.

## 2. Four Ways to Organize Mappings

### 2.1. SINGLE_TABLE: One Table for the Entire Hierarchy

`SINGLE_TABLE` stores shared attributes and specialized attributes of all subclasses in the same table. A column distinguishing entity types is typically declared with `@DiscriminatorColumn`; each subclass's value is declared with `@DiscriminatorValue`.

Example:

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.DiscriminatorColumn;
import jakarta.persistence.DiscriminatorType;
import jakarta.persistence.DiscriminatorValue;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Inheritance;
import jakarta.persistence.InheritanceType;

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(
    name = "payment_type",
    discriminatorType = DiscriminatorType.STRING
)
public abstract class PaymentMethod {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String owner;

    protected PaymentMethod() {
    }

    protected PaymentMethod(String owner) {
        this.owner = owner;
    }

    public Long getId() {
        return id;
    }

    public String getOwner() {
        return owner;
    }
}
```

Subclasses:

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.DiscriminatorValue;
import jakarta.persistence.Entity;

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends PaymentMethod {
    @Column(name = "last_four_digits", length = 4)
    private String lastFourDigits;

    protected CardPayment() {
    }

    public CardPayment(String owner, String lastFourDigits) {
        super(owner);
        this.lastFourDigits = lastFourDigits;
    }

    public String getLastFourDigits() {
        return lastFourDigits;
    }
}
```

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.DiscriminatorValue;
import jakarta.persistence.Entity;

@Entity
@DiscriminatorValue("BANK")
public class BankTransfer extends PaymentMethod {
    @Column(name = "bank_code", length = 20)
    private String bankCode;

    protected BankTransfer() {
    }

    public BankTransfer(String owner, String bankCode) {
        super(owner);
        this.bankCode = bankCode;
    }

    public String getBankCode() {
        return bankCode;
    }
}
```

With this strategy, the database has one table containing columns like `id`, `owner`, `payment_type`, `last_four_digits`, and `bank_code`. A `CARD` row uses `last_four_digits`; a `BANK` row uses `bank_code`. Columns specific to other types generally must allow `NULL` because they do not apply to every row.

JPA defaults to `SINGLE_TABLE` if an entity hierarchy uses inheritance without declaring `@Inheritance` on the root. Even so, declare it explicitly so readers understand the intent and avoid relying on implicit defaults.

**Advantages:**

- Polymorphic queries on `PaymentMethod` usually read from one table without joining child tables.
- Reading a concrete entity is usually simple with minimal joins.
- Adding a subclass usually does not require creating a new table; typically only a column and discriminator value are added.
- Easy to paginate a list of all payment methods since all data lives in one table.

**Limitations:**

- The table can grow very wide with many `NULL` columns when a hierarchy has many subclasses with specialized data.
- Standard `NOT NULL` constraints are hard to apply to columns required by only one subtype.
- Schema changes for one subclass affect the shared table of the entire hierarchy.
- Some data rules or subtype-specific uniqueness constraints require conditional constraints, depending on database capabilities.

Example conditional constraint on PostgreSQL:

```sql
ALTER TABLE payment_method
    ADD CONSTRAINT ck_card_requires_last_four
    CHECK (payment_type <> 'CARD' OR last_four_digits IS NOT NULL);

ALTER TABLE payment_method
    ADD CONSTRAINT ck_bank_requires_bank_code
    CHECK (payment_type <> 'BANK' OR bank_code IS NOT NULL);
```

This is an illustrative example of preserving data integrity for subtype-specific columns. Syntax, table/column names, and constraints must be adapted to the actual database. If each type requires its own unique key, a conditional/filtered unique index or equivalent DBMS feature may be required.

### 2.2. JOINED: Separating Parent and Child Tables

`JOINED` stores shared attributes in the parent class's table and each subclass's specific attributes in its corresponding table. The child table's primary key simultaneously serves as a foreign key referencing the parent table's primary key.

Root entity example:

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Inheritance;
import jakarta.persistence.InheritanceType;
import jakarta.persistence.Table;

@Entity
@Table(name = "payment_methods")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class PaymentMethod {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String owner;

    protected PaymentMethod() {
    }

    protected PaymentMethod(String owner) {
        this.owner = owner;
    }

    public Long getId() {
        return id;
    }

    public String getOwner() {
        return owner;
    }
}
```

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.PrimaryKeyJoinColumn;
import jakarta.persistence.Table;

@Entity
@Table(name = "card_payments")
@PrimaryKeyJoinColumn(name = "payment_method_id")
public class CardPayment extends PaymentMethod {
    @Column(name = "last_four_digits", nullable = false, length = 4)
    private String lastFourDigits;

    protected CardPayment() {
    }

    public CardPayment(String owner, String lastFourDigits) {
        super(owner);
        this.lastFourDigits = lastFourDigits;
    }
}
```

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.PrimaryKeyJoinColumn;
import jakarta.persistence.Table;

@Entity
@Table(name = "bank_transfers")
@PrimaryKeyJoinColumn(name = "payment_method_id")
public class BankTransfer extends PaymentMethod {
    @Column(name = "bank_code", nullable = false, length = 20)
    private String bankCode;

    protected BankTransfer() {
    }

    public BankTransfer(String owner, String bankCode) {
        super(owner);
        this.bankCode = bankCode;
    }
}
```

Conceptual schema:

```sql
CREATE TABLE payment_methods (
    id BIGINT PRIMARY KEY,
    owner VARCHAR(255) NOT NULL
);

CREATE TABLE card_payments (
    payment_method_id BIGINT PRIMARY KEY
        REFERENCES payment_methods(id),
    last_four_digits VARCHAR(4) NOT NULL
);

CREATE TABLE bank_transfers (
    payment_method_id BIGINT PRIMARY KEY
        REFERENCES payment_methods(id),
    bank_code VARCHAR(20) NOT NULL
);
```

The DDL above describes the primary key/foreign key relationships to explain the model. Exact key creation and identity syntax vary by database and ID generation strategy.

**Advantages:**

- Each table contains only the columns meaningful for its data type.
- Required subtype columns can be declared `NOT NULL` on the child table.
- Shared data is stored once in the parent table, reducing column duplication and aiding normalization.
- Foreign keys from child tables to the parent table ensure each child row has a corresponding parent row.
- Adding a subtype usually means adding a new table with minimal impact on existing subtype tables.

**Limitations:**

- Reading a subtype usually requires joining the parent and child tables.
- Polymorphic queries on the parent class may require joining multiple child tables to assemble complete objects.
- Writing a child entity typically involves inserts/updates across both parent and child tables within the same transaction.
- More subclasses increase join count and query complexity.

`JOINED` is often a balanced choice when subtypes have substantial specialized data and need strong relational constraints. Still, measure polymorphic queries and common read paths before deciding.

### 2.3. TABLE_PER_CLASS: Each Concrete Class Has Its Own Table

`TABLE_PER_CLASS` creates a table for each concrete entity class. Columns inherited from the parent class are repeated in each subclass's table. A shared table for the root is unnecessary for a hierarchy with only an abstract parent class.

Example:

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Inheritance;
import jakarta.persistence.InheritanceType;

@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class PaymentMethod {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    @Column(nullable = false)
    private String owner;

    protected PaymentMethod() {
    }

    protected PaymentMethod(String owner) {
        this.owner = owner;
    }
}
```

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;

@Entity
@Table(name = "card_payments")
public class CardPayment extends PaymentMethod {
    @Column(name = "last_four_digits", nullable = false, length = 4)
    private String lastFourDigits;

    protected CardPayment() {
    }

    public CardPayment(String owner, String lastFourDigits) {
        super(owner);
        this.lastFourDigits = lastFourDigits;
    }
}
```

```java
package com.example.learning.payment;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;

@Entity
@Table(name = "bank_transfers")
public class BankTransfer extends PaymentMethod {
    @Column(name = "bank_code", nullable = false, length = 20)
    private String bankCode;

    protected BankTransfer() {
    }

    public BankTransfer(String owner, String bankCode) {
        super(owner);
        this.bankCode = bankCode;
    }
}
```

In this model, `card_payments` has `id`, `owner`, `last_four_digits`; `bank_transfers` has `id`, `owner`, `bank_code`. Common columns such as `owner` are repeated across multiple tables.

**Advantages:**

- Each table holds one concrete entity type without needing a discriminator or unused subtype columns.
- Querying a subtype can read from one table without joining a parent table.
- New subtypes can be added via separate tables with minimal impact on other tables.

**Limitations:**

- Shared columns are duplicated, so changing the type or rules of a parent attribute may require migrations across multiple tables.
- Polymorphic queries through `PaymentMethod` may require `UNION` across child tables; cost and SQL depend on the provider/database.
- Hard to create a single foreign key from another table to all child tables because the database has no shared parent table holding all IDs.
- Guaranteeing uniqueness across the entire hierarchy is harder since each table's unique constraint only checks within that table.
- ID generation must guarantee no collisions across tables. Use an ID strategy with hierarchy-wide uniqueness, such as a shared sequence or provider-appropriate UUID; do not assume independent identity counters will never collide.

This strategy fits better when queries primarily target individual concrete classes, the set of subtypes is stable, and few relationships or constraints reference the parent class. It fits poorly when the application frequently searches, paginates, or links polymorphically via the root entity.

### 2.4. @MappedSuperclass: Sharing Mappings Without Creating a Parent Entity

`@MappedSuperclass` is used when you want to reuse common persistence attributes such as ID, creation timestamp, or audit fields, without treating the parent class as an independent entity.

```java
package com.example.learning.common;

import java.time.Instant;
import jakarta.persistence.Column;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.MappedSuperclass;

@MappedSuperclass
public abstract class AuditedEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    public Long getId() {
        return id;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}
```

Concrete entity inheriting the mapping:

```java
package com.example.learning.catalog;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Table;
import com.example.learning.common.AuditedEntity;

@Entity
@Table(name = "products")
public class Product extends AuditedEntity {
    @Column(nullable = false, length = 160)
    private String name;

    protected Product() {
    }

    public Product(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
```

Here `AuditedEntity` has no table of its own and cannot be queried directly via `EntityManager.find(AuditedEntity.class, id)`. Columns declared in the mapped superclass become columns in each concrete entity's table. If `Order` also extends `AuditedEntity`, the `orders` table also receives `id` and `created_at` columns.

**Advantages:**

- Shares common mappings and behavior without needing a parent table.
- Incurs no joins just to read audit attributes.
- Each concrete entity has its own table and can place constraints directly on that table.

**Limitations:**

- No parent entity for polymorphic queries or JPA associations targeting the parent type.
- Shared columns are repeated in each entity's table.
- Changing shared mappings may require migrations across multiple tables.

Use `@MappedSuperclass` for technical shared fields such as IDs, audit fields, or metadata. If you need to query all subtypes through a parent type or declare associations to the parent type, use entity inheritance instead of a mapped superclass.

## 3. Comparing Data Integrity, Extensibility, and Performance

| Criterion | SINGLE_TABLE | JOINED | TABLE_PER_CLASS | @MappedSuperclass |
| --- | --- | --- | --- | --- |
| Number of tables for hierarchy | One table | Parent table and one table per subclass | One table per concrete class | Each concrete entity has its own table |
| Shared attributes | Stored once | Stored in parent table | Repeated in each child table | Repeated in concrete entity tables |
| Subtype columns | Many nullable columns | Reside in subtype table | Reside in concrete class table | Depends on child entity |
| Subtype NOT NULL constraint | Harder; usually requires conditional CHECK | Easy to set NOT NULL on child table | Easy to set NOT NULL in each table | Easy to set on each entity table |
| Subtype foreign key | No separate subtype table | FK from child table to parent table | No shared parent table to reference | No parent table |
| Querying one subtype | Usually simple | Usually needs join with parent table | Reads subtype table | Reads entity table |
| Polymorphic query | Usually simple | May need joins | May need UNION | Does not support polymorphic queries via mapped superclass |
| Adding a subtype | Usually add columns and discriminator value | Add child table | Add new table | Add new entity/table |
| Schema risks | Wide table, NULL columns | Many tables and joins | Column duplication, hard hierarchy-wide uniqueness | Shared mapping/column duplication |

No strategy wins on every criterion. Wrong choices typically surface in one of three places: the database cannot enforce desired constraints, common queries perform too many joins/unions, or every domain change forces modifications across too many tables.

## 4. Data Integrity Trade-offs

Data integrity is not just about entities being valid in Java. The database must ensure data stays valid when multiple applications, batch jobs, or direct SQL statements write concurrently.

### 4.1. SINGLE_TABLE

Because all subtypes share one table, primary keys, foreign keys, and shared constraints can be defined centrally. However, subtype-specific columns usually must be nullable. If `last_four_digits` is required for `CARD`, a simple `NOT NULL` constraint would reject `BANK` rows as well.

The solution is a discriminator-based conditional `CHECK`, or database-specific triggers/constraints if rules are complex. Be sure to verify that the `CHECK` handles `NULL` according to the intended logic; write explicit conditions for each subtype.

Subtype-specific unique constraints may also require partial/filtered unique indexes. For example, only `CARD` rows require uniqueness on a certain card identifier. Syntax and support vary across PostgreSQL, SQL Server, MySQL, and other engines.

### 4.2. JOINED

Shared data lives in the parent table, and specialized required data lives in child tables. Child tables can use `NOT NULL` for subtype columns, while foreign keys from child primary keys to the parent table prevent orphaned child records.

The database still needs to prevent a parent ID from appearing simultaneously in two subtypes if business rules dictate each payment method has only one concrete type. Depending on the provider and schema, a discriminator or additional constraints may be needed to enforce this mutual-exclusion rule. Do not assume foreign keys alone express every hierarchy invariant.

### 4.3. TABLE_PER_CLASS

Each table enforces constraints for its own data type. Yet a hierarchy-wide rule—such as globally unique IDs or a business code that cannot repeat between `CardPayment` and `BankTransfer`—is hard to enforce with a simple unique constraint because rows live in separate tables.

If another business table needs to reference `PaymentMethod`, the database cannot create a standard foreign key pointing to a set of child tables. You may need a shared registry table, a mapping strategy change, or a redesigned association.

### 4.4. @MappedSuperclass

There is no parent table to reference. Constraints on inherited attributes reside in each concrete entity's table. If the same rule must be enforced across multiple tables, migrations/constraints must be applied to all of them.

## 5. Extensibility and Domain Evolution Trade-offs

Here, extensibility covers adding new entity types, changing shared attributes, evolving business rules, and evolving schemas when data already exists.

- `SINGLE_TABLE`: adding a subtype may require fewer initial DDL steps, but the shared table grows wider. Changing subtype attributes impacts the same large table and discriminator-based constraints.
- `JOINED`: adding a subtype usually means adding a new table and mapping; existing subtype tables are minimally affected. However, large hierarchies increase polymorphic query and mapping complexity.
- `TABLE_PER_CLASS`: adding a subtype adds an independent table; convenient when types are nearly independent. Changing shared attributes requires synchronizing schemas across multiple tables and checking all polymorphic queries.
- `@MappedSuperclass`: very convenient for shared technical attributes. When changing shared fields, every inheriting entity table must be migrated.

Do not merely count projected subclasses. Consider how rapidly shared attributes change, how much data diverges across subtypes, and what queries/relationships the application will need over several years.

## 6. Read and Write Performance Trade-offs

### Reading a Specific Subtype

- `SINGLE_TABLE` usually reads from one table and filters by discriminator.
- `JOINED` usually joins the parent table with the subtype table to retrieve all attributes.
- `TABLE_PER_CLASS` reads from the concrete class's table.
- `@MappedSuperclass` reads the concrete entity's table, as there is no parent table.

### Reading a Polymorphic List

Example query:

```java
List<PaymentMethod> methods = entityManager
    .createQuery("select p from PaymentMethod p", PaymentMethod.class)
    .getResultList();
```

This is a polymorphic query because the query type is the root entity. With `SINGLE_TABLE`, the provider can read from the shared table. With `JOINED`, the provider must combine parent table data with relevant child tables. With `TABLE_PER_CLASS`, the provider may generate SQL combining child tables using `UNION` or an equivalent mechanism. Actual SQL depends on the provider and database.

### Writing Data

- `SINGLE_TABLE`: inserts/updates usually touch one row in the hierarchy table.
- `JOINED`: inserting a child entity usually requires writing both the parent table and child table; updating shared/specialized attributes may touch multiple tables.
- `TABLE_PER_CLASS`: writes to the concrete table, though shared columns are duplicated there.
- `@MappedSuperclass`: writes one concrete entity table, since parent attributes are placed directly in that table.

Do not assume `SINGLE_TABLE` is always fastest. An overly wide table, many indexes, many NULL columns, or queries needing only one subtype can erode that advantage. Likewise, joins in `JOINED` can perform well with proper indexes and a moderate number of subtypes. Measure key queries at realistic data scale.

## 7. Indexes and Query Design

An inheritance strategy does not replace index design. List your frequent queries:

- Finding an entity by ID.
- Fetching a paginated list of all subtypes.
- Fetching a single subtype by status, timestamp, or owner.
- Joining from another entity to the root entity.
- Aggregated reporting across subtypes.

With `SINGLE_TABLE`, composite indexes combining the discriminator and filter predicates may be needed, such as `(payment_type, owner)` or `(payment_type, created_at)`. With `JOINED`, indexes are needed on child table foreign/primary keys and filter columns. With `TABLE_PER_CLASS`, per-table indexes are needed and `UNION` cost must be evaluated.

Illustrative index example for a single-table layout:

```sql
CREATE INDEX idx_payment_type_owner
    ON payment_method (payment_type, owner);
```

Proper indexing depends on filter order, selectivity, and the database query planner. Do not create indexes simply because columns exist; indexes add write overhead and storage cost.

## 8. Migrations and Schema Evolution

JPA mappings are object-relational descriptions; they do not automatically solve every safe migration step for existing data. When changing inheritance strategies or adding subtypes, prepare a dedicated migration plan.

Example of adding a new subtype:

1. Identify the subtype data to persist and required invariants.
2. Decide where shared and specialized attributes live under the current strategy.
3. Create migrations to add necessary columns, tables, foreign keys, discriminator values, or indexes.
4. Deploy code whose reads/writes remain schema-compatible during the transition phase.
5. Backfill data if needed; verify row counts, NULL values, orphans, and duplicates.
6. Switch the application to the new mapping once the schema is ready.
7. Drop old structures only after no application version still references them.

Switching from `SINGLE_TABLE` to `JOINED` or `TABLE_PER_CLASS` is not just changing an annotation. Existing data must be split/copied into new tables, keys and constraints must be created, and legacy queries must be verified. Use Flyway/Liquibase or versioned migration tools instead of relying on `ddl-auto=update` for major changes.

## 9. Choosing a Strategy by Scenario

| Scenario | Strategy to Consider | Reason |
| --- | --- | --- |
| Few subtypes, small attribute differences, frequent polymorphic queries | `SINGLE_TABLE` | Simple reads, minimal joins, easy root pagination |
| Subtypes have many distinct attributes and need clear NOT NULL constraints | `JOINED` | Specialized columns in separate tables; FKs protect relationships |
| Subtypes are nearly independent, primarily queried individually | `TABLE_PER_CLASS` | Each type has its own table, no parent join when reading subtype |
| Only want to share ID/audit fields without querying via parent class | `@MappedSuperclass` | Shares mappings without creating a parent entity |
| Need associations to parent type and polymorphic queries | `SINGLE_TABLE` or `JOINED` | Root is a real entity in the hierarchy |
| Need database-enforced hierarchy-wide uniqueness/FK | Usually prefer `SINGLE_TABLE` or `JOINED` | Shared structure for constraints/associations; still need explicit invariant design |

This is an initial guide, not a substitute for load testing and verifying real constraints. The same domain model can suit different strategies if query and data integrity requirements differ.

## 10. Example Evaluation of a Business Model

Suppose a system has `PaymentMethod`, `CardPayment`, and `BankTransfer`. Requirements:

- Users view all payment methods by owner.
- Each type has required specialized data.
- The system retains history and may add new methods later.
- Many queries fetch a specific subtype, while an admin screen also needs a polymorphic list.

Analysis:

1. `SINGLE_TABLE` keeps the polymorphic list simple and works well if subtype count is low and specialized columns are modest. Discriminator-based CHECK constraints are needed to protect required fields.
2. `JOINED` works well if each method's specialized data is substantial, subtype constraints matter, and clear FKs are needed. The polymorphic screen should be benchmarked because it may join multiple tables.
3. `TABLE_PER_CLASS` can make single-subtype queries simple, but querying all methods and referencing the root becomes harder; hierarchy-wide uniqueness is also difficult to enforce.
4. `@MappedSuperclass` fits only if `PaymentMethod` does not need to be a queryable or referenceable entity. The polymorphic list requirement rules out this option.

In this case, it is usually best to compare `SINGLE_TABLE` and `JOINED` with realistic data. If subtype count is small and polymorphic queries dominate, `SINGLE_TABLE` can be a starting point. If subtype data diverges heavily and constraints are top priority, `JOINED` warrants serious consideration.

## 11. Testing and Measurement

Do not test only that entities persist successfully. Verify that the database actually enforces invariants:

- Create one entity per subtype and read them back through the root type.
- Verify the discriminator maps to the right subclass when using `SINGLE_TABLE`.
- Verify FKs and NOT NULL on child tables when using `JOINED`.
- Verify IDs do not collide across tables when using `TABLE_PER_CLASS`.
- Attempt invalid writes via direct SQL to confirm database constraints reject them.
- Run polymorphic queries with pagination and sorting on a representative dataset.
- Enable SQL logging in test environments to inspect join/union counts and write statements.
- Use database execution plans to evaluate indexes and sort/join costs.

Example polymorphic check in a test with a Spring-configured `EntityManager`:

```java
entityManager.persist(new CardPayment("An", "1234"));
entityManager.persist(new BankTransfer("Bình", "VCB"));
entityManager.flush();
entityManager.clear();

List<PaymentMethod> methods = entityManager.createQuery(
    "select p from PaymentMethod p",
    PaymentMethod.class
).getResultList();

assertThat(methods).hasSize(2);
assertThat(methods).anyMatch(CardPayment.class::isInstance);
assertThat(methods).anyMatch(BankTransfer.class::isInstance);
```

This is an illustrative test body; it needs to sit inside a test class with an injected `EntityManager` and assertion library. The test must run against a schema/mapping matching the strategy being evaluated.

## 12. Common Design Mistakes

- **Choosing `SINGLE_TABLE` solely for fewer joins.** As subtypes grow, the table can become very wide with many nullable columns; type-specific constraints must be designed explicitly.
- **Choosing `JOINED` without measuring polymorphic queries.** Many subtypes can force queries into many joins and inefficient pagination.
- **Choosing `TABLE_PER_CLASS` and then adding an FK to the root entity.** There is no shared parent table for the database to reference with a standard FK.
- **Using `@MappedSuperclass` while expecting queries via the parent type.** A mapped superclass is not an entity and has no table of its own.
- **Assuming Java inheritance automatically determines the schema.** Strategy and mappings must be declared explicitly.
- **Relying on per-table unique constraints for hierarchy-wide uniqueness.** Those constraints do not check other tables.
- **Using separate IDENTITY generators on multiple TABLE_PER_CLASS tables and assuming global IDs won't collide.** Choose an ID generation strategy that guarantees hierarchy-wide uniqueness.
- **Switching strategies just by editing annotations.** Existing data and schemas require controlled migrations.
- **Benchmarking only one simple query.** Measure subtype reads, polymorphic reads, pagination, inserts, updates, and migrations.

## 13. Checklist Before Finalizing an Inheritance Strategy

- [ ] Does the root need to be an entity for polymorphic queries or as an association target?
- [ ] How many subtypes exist now and are projected in the future?
- [ ] How much of the schema is made up of subtype-specific attributes?
- [ ] Which columns must be NOT NULL, and can the database enforce them directly?
- [ ] Are hierarchy-wide uniqueness constraints or foreign keys required?
- [ ] Are common queries by subtype or through the root?
- [ ] Have read/write frequencies and join/union costs been measured on representative data?
- [ ] Can schema changes be rolled out safely via migrations?
- [ ] Does the ID strategy guarantee uniqueness across the required scope?
- [ ] Do integration tests verify constraints, polymorphic queries, and all subtypes?

## Conclusion

`SINGLE_TABLE` prioritizes simple queries and minimal joins; `JOINED` prioritizes normalized structure and clear constraints on subtype tables; `TABLE_PER_CLASS` separates tables by concrete class at the cost of more complex polymorphic queries, associations, and hierarchy-wide uniqueness; `@MappedSuperclass` only shares mappings when a parent entity is unnecessary. Start from data invariants and real query patterns, then evaluate schema, migration, read, and write costs. A good strategy is one where the database enforces business rules and the application still meets expected load.
