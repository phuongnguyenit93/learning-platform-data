# Mapping Native Query Results to Entities

JPA typically uses JPQL to query by entities and Java properties. However, there are situations where you need to write SQL directly: using database-specific syntax, CTEs, window functions, hints, pre-tuned queries, or leveraging an existing view. In those cases, JPA lets you execute native SQL and map the results back to entities.

Mapping a native query to an entity means each SQL result row is converted into an entity instance according to JPA metadata. If the query executes within an active persistence context, returned entities are managed according to JPA identity rules. As a result, entities returned from a native query can participate in dirty checking and subsequent persistence operations.

A crucial requirement is that the result set must supply enough columns for the provider to build the entity's state according to its mapping. Selecting only a few columns and trying to map them to a full entity leads to incorrect or undefined behavior per the specification. For partial data, use a DTO or projection.

**Example prerequisites:** the code snippets use Spring Boot 3.x, Java 17 or higher, Jakarta Persistence, and Spring Data JPA. The application requires the **spring-boot-starter-data-jpa** dependency, a JDBC driver, a `DataSource`, and a matching schema. The snippets are parts of a Spring Boot application, not standalone programs runnable with **javac** alone.

## 1. How Do Native SQL and JPQL Differ?

| Aspect | JPQL | Native SQL |
|---|---|---|
| Query target | Entities and Java properties | Tables, columns, views, and SQL syntax |
| Portability | Relatively high across JPA providers/databases | More dependent on database and dialect |
| Result mapping | Entities, scalars, or DTOs per JPQL | Entities, scalars, DTOs, or result-set mappings |
| Names used in query | Entity name, field/property | Physical table/column names |
| Database-specific features | Limited by JPQL language/provider extensions | Can use CTEs, window functions, hints, and vendor syntax |

JPQL example:

~~~java
select b
from Book b
where b.status = :status
~~~

Native SQL example:

~~~sql
SELECT b.id, b.title, b.status
FROM books b
WHERE b.status = ?;
~~~

JPQL uses the `Book` entity and the `status` property. Native SQL uses the `books` table and its corresponding physical columns.

Choose a native query when the benefit of direct SQL is clear. If JPQL can express the query and meets performance needs, JPQL is generally easier to maintain and less dependent on the database.

## 2. Sample Entity for Result Mapping

Let us use a simple `Book` entity:

~~~java
package com.example.catalog.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

import java.math.BigDecimal;

@Entity
@Table(name = "books")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "title", nullable = false, length = 150)
    private String title;

    @Column(name = "isbn", nullable = false, length = 20)
    private String isbn;

    @Column(name = "price", nullable = false, precision = 12, scale = 2)
    private BigDecimal price;

    @Version
    @Column(name = "version")
    private Long version;

    protected Book() {
    }

    public Long getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public String getIsbn() {
        return isbn;
    }

    public BigDecimal getPrice() {
        return price;
    }

    public Long getVersion() {
        return version;
    }
}
~~~

Assume the database has this table:

~~~sql
CREATE TABLE books (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(150) NOT NULL,
    isbn VARCHAR(20) NOT NULL,
    price NUMERIC(12, 2) NOT NULL,
    version BIGINT
);
~~~

Table and column names in native SQL must match the actual schema. If the mapping uses **@Column(name = "book_title")**, the SQL query must return a matching column or alias for that mapping.

## 3. Approach 1: EntityManager.createNativeQuery(sql, Entity.class)

Jakarta Persistence lets you pass the entity class as the result type:

~~~java
List<Book> books = entityManager
    .createNativeQuery(
        "SELECT id, title, isbn, price, version FROM books WHERE price >= ?",
        Book.class
    )
    .setParameter(1, minimumPrice)
    .getResultList();
~~~

The second parameter is `Book.class`, so the JPA provider maps each result set row into a `Book` entity.

You can also fetch a single result:

~~~java
Book book = (Book) entityManager
    .createNativeQuery(
        "SELECT id, title, isbn, price, version FROM books WHERE id = ?",
        Book.class
    )
    .setParameter(1, id)
    .getSingleResult();
~~~

If no matching row exists, `getSingleResult` throws **NoResultException**. If more than one row matches, it throws **NonUniqueResultException**. If you want to handle missing results via a collection, use `getResultList` and check for an empty list.

### Result Set Requirements

For entity mapping, the query must return all columns mapped for the entity, including the primary key and columns required for entity state. If the entity has relationships, the provider may also require the corresponding foreign key columns. For entities using secondary tables, inheritance, or complex mappings, result set requirements also depend on those mappings.

The JPA specification warns that behavior is undefined if a native query does not return enough column data for the entity mapping. Do not select only `id` and `title` and ask the provider to construct a full `Book` if the entity also maps `isbn`, `price`, and `version`.

If you only need a few columns, use scalar or DTO projections as shown later.

## 4. Approach 2: Spring Data JPA Repository Returning an Entity

With Spring Data JPA, you can declare a native query directly on a repository using **@Query(nativeQuery = true)**:

~~~java
package com.example.catalog.repository;

import com.example.catalog.domain.Book;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

public interface BookRepository extends JpaRepository<Book, Long> {

    @Query(
        value = """
            SELECT b.id, b.title, b.isbn, b.price, b.version
            FROM books b
            WHERE b.price >= ?1
            ORDER BY b.price DESC
            """,
        nativeQuery = true
    )
    List<Book> findBooksWithMinimumPrice(BigDecimal minimumPrice);

    @Query(
        value = """
            SELECT b.id, b.title, b.isbn, b.price, b.version
            FROM books b
            WHERE b.isbn = :isbn
            """,
        nativeQuery = true
    )
    Optional<Book> findNativeByIsbn(@Param("isbn") String isbn);
}
~~~

When the method declares a return type of `Book` or `List<Book>`, Spring Data JPA instructs the provider to map the result set to the `Book` entity.

Notes:

- **nativeQuery = true** tells Spring Data this is SQL rather than JPQL.
- SQL must use the exact database table and column names.
- You can use positional parameters like **?1** or named parameters with **@Param**, depending on Spring Data/provider support and the version in use.
- Entity results require all mapped columns.
- A native query does not automatically become read-only just because it is a `SELECT`; transaction boundaries and flush mode still need consideration.

## 5. Column Names, Aliases, and Mapping Rules

The simplest mapping returns columns whose names match the physical column names in the entity mapping:

~~~sql
SELECT
    b.id,
    b.title,
    b.isbn,
    b.price,
    b.version
FROM books b
~~~

When the SQL uses aliases, the mapping may need explicit configuration. Example:

~~~sql
SELECT
    b.id AS book_id,
    b.title AS book_title,
    b.isbn AS book_isbn,
    b.price AS book_price,
    b.version AS book_version
FROM books b
~~~

Aliases like `book_id` and `book_title` do not automatically equate to `id` and `title` in every entity mapping. With custom aliases, declare **@SqlResultSetMapping** and **@FieldResult** to specify which result column maps to which entity attribute.

Some databases automatically fold the case of unquoted aliases. If mapping depends on mixed-case aliases or special characters, use simple, consistent aliases and test on the target database. Avoid duplicate aliases when joining multiple tables.

## 6. Approach 3: @SqlResultSetMapping and @EntityResult

**@SqlResultSetMapping** is the standard JPA mechanism for describing how to map a result set. **@EntityResult** specifies the target entity; **@FieldResult** links a returned column name to an entity attribute.

Example declaring the mapping on `Book`:

~~~java
@Entity
@Table(name = "books")
@SqlResultSetMapping(
    name = "BookEntityMapping",
    entities = @EntityResult(
        entityClass = Book.class,
        fields = {
            @FieldResult(name = "id", column = "book_id"),
            @FieldResult(name = "title", column = "book_title"),
            @FieldResult(name = "isbn", column = "book_isbn"),
            @FieldResult(name = "price", column = "book_price"),
            @FieldResult(name = "version", column = "book_version")
        }
    )
)
public class Book {
    // JPA fields and mappings as shown in the example above.
}
~~~

Execution:

~~~java
List<Book> books = entityManager
    .createNativeQuery(
        """
        SELECT
            b.id AS book_id,
            b.title AS book_title,
            b.isbn AS book_isbn,
            b.price AS book_price,
            b.version AS book_version
        FROM books b
        WHERE b.price >= ?
        """,
        "BookEntityMapping"
    )
    .setParameter(1, minimumPrice)
    .getResultList();
~~~

In **@FieldResult**:

- **name** is the name of the entity's persistent property.
- **column** is the column name or alias in the result set.

This approach is useful when SQL joins multiple tables, uses custom aliases, or returns column names different from default mapping names.

If the entity has relationships, the mapping must supply the data required for associations per JPA rules. With complex mappings such as embedded IDs, inheritance, secondary tables, or multi-level associations, check the specification and provider capabilities; do not assume adding a single alias is enough.

## 7. Are Entities Returned by Native Queries Managed?

When a native query uses entity result mapping within an active persistence context, results are handled as entities under JPA management and identity rules. If the entity is already present in the current persistence context, JPA maintains consistent identity rather than creating two separate managed instances for the same entity key.

Example:

~~~java
@Transactional(readOnly = true)
public Book findBook(Long id) {
    return bookRepository.findNativeById(id).orElseThrow();
}
~~~

If the returned entity is managed within a transaction, it can be tracked by dirty checking when modified inside an appropriate write transaction.

However, do not treat a native `SELECT` as a refresh command. If the same entity is already managed in the persistence context, do not assume the query will overwrite every field in the existing Java object with the latest database values. If you need to reload state, use an explicit refresh or a new persistence context as appropriate.

A native `SELECT` also does not automatically call `persist` or `merge`. It only queries and maps results.

## 8. When Should You Not Map a Native Query to an Entity?

Do not map to an entity when the result set contains only partial data or represents an aggregation.

Example:

~~~sql
SELECT status, COUNT(*) AS order_count
FROM purchase_orders
GROUP BY status
~~~

This result is not a full `PurchaseOrder`. Do not declare a method returning **PurchaseOrder**. Use a DTO, scalar mapping, or interface projection instead.

Cases suited for DTOs:

- Aggregate reports.
- Multi-table join results where only a few columns are needed.
- List views needing only ID, name, and status.
- Queries using CTEs/window functions that return a shape not matching an entity.
- Results with computed columns or custom aliases.

Entities represent persistent state; DTOs represent data tailored to a specific use case. Separating the two avoids synthetic entities or incomplete objects mistaken for full persistent state.

## 9. Scalar Mapping With @ColumnResult

If a native query returns a few simple columns, JPA can map scalars via **@ColumnResult**.

Example:

~~~java
@SqlResultSetMapping(
    name = "BookPriceMapping",
    columns = {
        @ColumnResult(name = "book_id", type = Long.class),
        @ColumnResult(name = "book_price", type = BigDecimal.class)
    }
)
~~~

Execution:

~~~java
List<Object[]> rows = entityManager
    .createNativeQuery(
        """
        SELECT id AS book_id, price AS book_price
        FROM books
        WHERE price >= ?
        """,
        "BookPriceMapping"
    )
    .setParameter(1, minimumPrice)
    .getResultList();
~~~

Each row contains scalar values in the order declared in the mapping. With multiple columns, you must cast carefully. If you want results with clear field names, DTO constructor mapping is usually easier to maintain.

## 10. Mapping Native Queries to DTOs With @ConstructorResult

JPA supports **@ConstructorResult** to invoke a DTO constructor using columns from the result set.

DTO:

~~~java
package com.example.catalog.dto;

import java.math.BigDecimal;

public record BookPriceView(
    Long id,
    String title,
    BigDecimal price
) {
}
~~~

Mapping:

~~~java
@SqlResultSetMapping(
    name = "BookPriceViewMapping",
    classes = @ConstructorResult(
        targetClass = BookPriceView.class,
        columns = {
            @ColumnResult(name = "book_id", type = Long.class),
            @ColumnResult(name = "book_title", type = String.class),
            @ColumnResult(name = "book_price", type = BigDecimal.class)
        }
    )
)
~~~

Execution:

~~~java
List<BookPriceView> views = entityManager
    .createNativeQuery(
        """
        SELECT
            id AS book_id,
            title AS book_title,
            price AS book_price
        FROM books
        WHERE price >= ?
        ORDER BY price DESC
        """,
        "BookPriceViewMapping"
    )
    .setParameter(1, minimumPrice)
    .getResultList();
~~~

Columns in **@ConstructorResult** are passed to the constructor in the exact order declared. Data types must be compatible with the constructor parameter types. Using a record keeps the DTO immutable and reduces boilerplate.

With Spring Data JPA, native queries can return interface projections or DTOs depending on version capabilities and declaration style. When complex mapping is required, **@SqlResultSetMapping** is a standard, explicit choice that relies less on framework inference.

## 11. Native Queries Joining Multiple Tables While Returning One Entity

You can join other tables for filtering or sorting while still mapping only the primary entity's columns:

~~~sql
SELECT
    b.id,
    b.title,
    b.isbn,
    b.price,
    b.version
FROM books b
JOIN authors a ON a.id = b.author_id
WHERE a.name = ?
~~~

The result contains only `Book` columns. Joining `authors` is used to filter by author name; it does not mean the `Author` entity is also mapped or that the `author` association has been fetched.

If you need to return both `Book` and `Author`, use a multi-entity result set mapping via **@SqlResultSetMapping** with multiple **@EntityResult** entries, or return a DTO containing the required fields. When mapping multiple entities, give columns distinct aliases to avoid collisions on `id`, `name`, or other shared column names.

If `Book` has an `Author` association and you map only `Book`, accessing **book.getAuthor()** afterward still follows the association's fetch strategy. A native SQL `JOIN` in the query does not automatically make the association fetched across all providers or mappings.

## 12. Paginating Native Queries

Spring Data JPA can paginate native queries using **Pageable**. For complex queries, declare a separate count query:

~~~java
@Query(
    value = """
        SELECT b.id, b.title, b.isbn, b.price, b.version
        FROM books b
        WHERE b.price >= ?1
        ORDER BY b.price DESC
        """,
    countQuery = """
        SELECT COUNT(*)
        FROM books b
        WHERE b.price >= ?1
        """,
    nativeQuery = true
)
Page<Book> findPageByMinimumPrice(
    BigDecimal minimumPrice,
    Pageable pageable
);
~~~

The count query must count the exact number of logical rows returned by the content query. If a `JOIN` produces multiple rows per `Book`, you may need **COUNT(DISTINCT b.id)**. If the query uses `GROUP BY`, the count query needs to count the number of groups rather than total source rows.

SQL pagination behavior can depend on the dialect and Spring Data JPA version. Test both the content query and the count query on a real database.

## 13. Parameters, Transactions, and Flushing With Native SQL

Use parameter binding instead of string concatenation:

~~~java
@Query(
    value = "SELECT id, title, isbn, price, version FROM books WHERE isbn = ?1",
    nativeQuery = true
)
Optional<Book> findByIsbnNative(String isbn);
~~~

Do not do this:

~~~java
String sql = "SELECT * FROM books WHERE isbn = '" + isbn + "'";
~~~

Concatenating input into SQL creates SQL injection risks and escaping bugs. Parameter binding is for values; table names, column names, or sort directions generally cannot be bound as values. If you need dynamic SQL for identifiers, use an allowlist of controlled choices.

For native `SELECT` queries, choose an appropriate transaction boundary and consider **@Transactional(readOnly = true)** for read use cases. For native `UPDATE`/`DELETE`, you need **@Modifying** in a Spring Data repository and a write transaction:

~~~java
@Modifying
@Transactional
@Query(
    value = "UPDATE books SET price = ?1 WHERE id = ?2",
    nativeQuery = true
)
int updatePrice(BigDecimal price, Long id);
~~~

Native `UPDATE`/`DELETE` statements execute directly on the database and bypass the normal entity lifecycle. They do not trigger entity callbacks, JPA cascades, or per-entity dirty checking. The persistence context may still hold stale entities; consider flushing before and clearing/refreshing after execution.

In particular, flush mode and how the provider synchronizes pending changes before a native query can vary by provider and configuration. If a query depends on pending changes in the persistence context, flush explicitly when needed and write tests to verify.

## 14. Common Pitfalls

| Symptom | Cause | Resolution |
|---|---|---|
| Returned entity is missing fields or fails mapping | Native `SELECT` does not supply enough entity columns | Select all required persistent columns |
| Aliases are not mapped properly | Alias names differ from mapped column names | Use stable aliases and **@SqlResultSetMapping/@FieldResult** |
| Native query uses entity name and database throws an error | JPQL syntax written inside native SQL | Use physical table and column names |
| Join result produces duplicate entities | Join creates multiple rows for one entity | Check cardinality and use `DISTINCT` where semantically right |
| Entity association is not loaded | SQL `JOIN` only filters; it is not an entity fetch mapping | Use `EntityGraph`/fetch query or a DTO |
| DTO constructor fails | Mismatched column order or types | Check **@ColumnResult** and constructor signature |
| `Page` total elements is wrong | Count query does not reflect logical row/group count | Declare an accurate `countQuery` |
| Stale managed objects after native `UPDATE` | Native DML bypasses persistence context | Flush before and clear/refresh per use case |
| SQL injection | Concatenating input strings into SQL | Use parameter binding |
| Query runs on one DB but breaks on another | Native syntax depends on dialect | Test and manage SQL per target database |

## 15. Checklist for Mapping Native Queries to Entities

- [ ] Verify whether the query truly needs native SQL or if JPQL suffices.
- [ ] Use exact physical database table and column names.
- [ ] When returning an entity, `SELECT` all columns required by the mapping.
- [ ] Include primary key and any needed version/foreign key columns.
- [ ] Use stable aliases if result column names differ from mapped names.
- [ ] Use **@SqlResultSetMapping** and **@EntityResult** when explicit entity mapping is needed.
- [ ] Do not map partial result sets or aggregate results into a full entity.
- [ ] Use DTO or scalar mappings for reporting data.
- [ ] Use parameter binding; never concatenate input into SQL.
- [ ] Declare an accurate `countQuery` when paginating native queries.
- [ ] Manage the persistence context after native `UPDATE`/`DELETE`.
- [ ] Test against the actual target database and dialect.

## 16. Conclusion

Native queries allow leveraging SQL directly in JPA applications. When the result is a full entity, you can use **EntityManager.createNativeQuery(sql, Entity.class)** or Spring Data's **@Query(nativeQuery = true)**. When column names or aliases are customized, use **@SqlResultSetMapping** with **@EntityResult** and **@FieldResult** for explicit mapping.

Only map to an entity when the result set provides complete data per its mapping. For reports, aggregates, or partial data, use DTOs or scalar projections. Always verify aliases, data types, count queries, transactions, and persistence context state so native SQL works reliably in your application.
