# Checking JPQL, Native Query, and Count Query Parser Changes When Upgrading

When upgrading Spring Data JPA or Hibernate, existing queries can fail even if repository code has not changed. The cause can come from the parser used to analyze and rewrite queries, from the JPA provider's semantic parser, from how Spring Data generates count queries for pagination, or from the SQL executed by the database.

Three layers must be distinguished:

1. **Spring Data query enhancer/parser** reads declared queries to detect projections, aliases, sorting, and generate count queries.
2. **JPA provider parser** validates JPQL/HQL queries and translates them into an internal query model. In Hibernate 6, this model is the Semantic Query Model (SQM).
3. **Database SQL parser/optimizer** parses the final SQL generated by the provider or the native SQL written by the application.

Native SQL also has its own path: Spring Data can use a regex-based enhancer or JSqlParser to support rewriting/sorting/counting, but the database is what validates SQL syntax and schema. JSqlParser does not replace the database parser.

This lesson focuses on identifying changes across Spring Data JPA/Hibernate versions, checking native queries, and ensuring count queries are accurate. Examples use Jakarta Persistence in Spring Boot 3+; when applying them, use the exact versions managed by the Spring Boot/Spring Data BOM.

## 1. Four query types to check when upgrading

Spring Data JPA has multiple ways to create queries, and each is affected differently:

| Query type | How it is created | Components to check |
|---|---|---|
| Derived query | Parsing method names such as findByStatusAndCreatedAtAfter | Spring Data method-name parser, property traversal, query semantics |
| JPQL in @Query | Directly declared JPQL/HQL string | Spring Data query enhancer and JPA provider parser |
| Native SQL | @Query(nativeQuery = true) or @NativeQuery in supported versions | Native query enhancer, JSqlParser/regex, JDBC driver, and database |
| Count query | Auto-generated or declared via countQuery | Query enhancer, counting with proper semantics, result type, and pagination |

An error at the parser layer is not necessarily a SQL error. For example, Spring Data may fail to rewrite a complex native query to append ORDER BY or generate a count query, even though the original SQL runs fine in a database client. Conversely, the parser may accept a query that Hibernate or the database still rejects at execution time due to wrong properties, data types, or dialect syntax.

## 2. Distinguishing Spring Data's parser from Hibernate's parser

### 2.1. Spring Data query enhancer

Spring Data needs to understand the declared query structure to perform tasks such as:

- Identifying the SELECT/projection clause and aliases.
- Rewriting projections for interface/DTO projections in certain cases.
- Appending dynamic Sort to the query.
- Generating a count query for Page.
- Detecting complex queries to choose a handling strategy.

Starting in Spring Data JPA 3.1, Spring Data introduced an ANTLR-based parser for HQL and JPQL. Spring's release announcement describes that JPA queries can use the HQL parser when Hibernate is on the classpath; if Hibernate is absent, the specification-compliant JPQL parser is used. Documentation for newer lines describes dedicated parsers for HQL (Hibernate) and EQL (EclipseLink).

How the enhancer is selected depends on the Spring Data JPA version, provider, and repository configuration. Do not infer solely from the Hibernate version. Check the documentation for your project's exact release train.

### 2.2. Hibernate runtime parser and SQM

Hibernate 6 translates HQL/Criteria into the Semantic Query Model (SQM). High-level pipeline:

```text
HQL / JPQL / Criteria
        |
        v
Tokenizer and parser
        |
        v
Semantic Query Model (SQM)
        |
        v
SQL AST
        |
        v
Dialect SQL translator
        |
        v
SQL sent to database
```

SQM helps Hibernate validate expression semantics and types more strictly before generating SQL. Consequently, a query previously accepted by Hibernate 5 due to looser interpretation may be rejected after upgrading to Hibernate 6.

### 2.3. Database parser

The database receives only the final SQL. When using JPQL, Hibernate/EclipseLink translates JPQL to SQL before the database parses it. When using native queries, the database parses the SQL supplied by the application.

Neither the Spring Data parser nor the Hibernate parser checks all differences in functions, operators, data types, JSON syntax, CTEs, or hints across databases. Integration tests against the exact database engine remain mandatory.

## 3. Checking Spring Data JPA changes by version

When upgrading Spring Boot, do not look only at the Spring Data JPA version. Record the full dependency graph:

- Spring Boot version.
- Spring Data JPA version.
- Spring Data Commons version.
- Hibernate ORM or EclipseLink version.
- JSqlParser version if used.
- JDBC driver and database version.

The Spring Boot BOM typically manages compatible versions. Do not upgrade Hibernate or JSqlParser independently outside dependency management without verifying compatibility.

### 3.1. Spring Data JPA 3.1 milestone and JPQL/HQL parser

Spring Data JPA 3.1 introduced an ANTLR-based JPQL/HQL parser to handle more complex queries when rewriting Sort/projection/count. This improves alias recognition and placement of ORDER BY/count projections compared to simple string-manipulation operations.

That does not mean every JPQL/HQL query is accepted. A query must still be valid according to the selected parser and the JPA provider at execution time. HQL may have Hibernate-specific features not present in portable JPQL; if the project depends on HQL extensions, verify that the parser in use is the HQL parser.

### 3.2. Newer Spring Data JPA lines

Current documentation describes dedicated query parsers for HQL and EQL. For native SQL, Spring Data uses a separate enhancer because SQL varies considerably across databases. The built-in SQL enhancer only supports simple queries for introspection and count derivation.

Newer APIs/configurations can differ across release trains. Before using `@NativeQuery`, `QueryEnhancerSelector`, or native parser configuration, confirm they exist in the exact version in use. If the version does not yet have `@NativeQuery`, use `@Query(nativeQuery = true)`.

## 4. Notable HQL/JPQL changes when upgrading Hibernate 5 to 6

Hibernate 6 changed its parser and query semantic validation. Several older patterns should be reviewed.

### 4.1. Use Java properties instead of SQL column names in HQL

HQL/JPQL queries entities and persistent attributes, not physical column names directly.

Do not write:

```java
// Invalid in HQL/JPQL if order_status is only a SQL column name.
@Query("select o from PurchaseOrder o where o.order_status = :status")
List<PurchaseOrder> findByStatus(String status);
```

Use the Java property:

```java
@Query("""
    select o
    from PurchaseOrder o
    where o.status = :status
    """)
List<PurchaseOrder> findByStatus(
    @Param("status") OrderStatus status
);
```

The `@Column(name = "order_status")` mapping translates the `status` property to the corresponding SQL column. Native SQL is what uses physical column names.

### 4.2. Comparing an association with a scalar foreign key

Older Hibernate versions used to accept some expressions comparing an association directly with a scalar ID. Hibernate 6 requires both sides to have clearly compatible types.

Do not rely on:

```java
// Old pattern that may be rejected.
where o.customer = :customerId
```

If you want to compare the foreign key:

```java
@Query("""
    select o
    from PurchaseOrder o
    where o.customer.id = :customerId
    """)
List<PurchaseOrder> findByCustomerId(
    @Param("customerId") Long customerId
);
```

If you want to compare the association with an entity, bind an entity reference:

```java
Customer customerRef =
    entityManager.getReference(Customer.class, customerId);

// Query can compare o.customer = :customerRef.
```

Use `association.id` when the goal is comparing the foreign key. Use an entity reference when the semantics are genuinely entity comparison.

### 4.3. UPDATE no longer accepts an optional FROM

Hibernate 5 allowed syntax such as:

```sql
update from PurchaseOrder o
set o.status = :status
```

For JPQL and Hibernate 6 compatibility, remove FROM:

```java
@Modifying
@Query("""
    update PurchaseOrder o
    set o.status = :status
    where o.id = :id
    """)
int updateStatus(
    @Param("id") Long id,
    @Param("status") OrderStatus status
);
```

### 4.4. Unknown identifiers are no longer passed straight through to SQL

Hibernate 5 previously allowed certain identifiers not recognized as properties to pass straight through HQL functions and appear in SQL. This was removed because it could generate unpredictable queries.

If you need to pass a supported literal SQL fragment, Hibernate 6 provides the `sql(...)` function for specific cases, for example:

```hql
select substring(e.description, 21, 11, sql('octets'))
from AnEntity e
```

This is Hibernate-specific syntax, not portable JPQL. Only use application-controlled literals; never pass user input into a SQL fragment.

### 4.5. Path comparisons and data types

Hibernate 6 checks expression types more strictly. For example, an entity path should not be compared directly to a scalar ID:

```java
// Incorrect types:
where o.customer = 42

// Compare ID:
where o.customer.id = 42
```

Also check Criteria API usage: both sides of a predicate, subquery selections, and expressions must have compatible types. A Criteria query can compile in Java and still be rejected by Hibernate at query creation time due to invalid expression types.

### 4.6. DISTINCT and join fetch

Hibernate 6 changed how root entities are deduplicated during collection join fetches. Do not keep or remove `DISTINCT` based solely on old assumptions. Inspect the generated SQL, returned results, and actual database cost. `DISTINCT` in JPQL can be passed down to SQL, which can affect the execution plan.

### 4.7. Return type of native COUNT

Hibernate 6 changed the default mapping of SQL BIGINT to Java `Long` in corresponding cases. A native query returning `count(*)` might previously have been received by the application as `BigInteger`, whereas after upgrading it may be `Long`.

Example to review:

```java
// Verify the actual result type after upgrading Hibernate.
Number total = (Number) entityManager
    .createNativeQuery("select count(*) from purchase_order")
    .getSingleResult();

long count = total.longValue();
```

If repository or custom code casts directly to `BigInteger`, check and update the return type per provider/version. Do not assume every database/driver always returns the same Java type for native aggregates.

## 5. Distinguishing JPQL from native SQL in @Query

JPQL:

```java
@Query("""
    select o
    from PurchaseOrder o
    where o.status = :status
    """)
List<PurchaseOrder> findByStatus(
    @Param("status") OrderStatus status
);
```

Native SQL:

```java
@Query(
    value = """
        select *
        from purchase_order
        where order_status = :status
        """,
    nativeQuery = true
)
List<PurchaseOrder> findByStatusNative(
    @Param("status") String status
);
```

Differences:

| Aspect | JPQL | Native SQL |
|---|---|---|
| Entity/table | Entity name | Table name |
| Field/column | Java persistent property | Physical column |
| Association | Path expression / join | SQL JOIN and foreign key |
| Function | JPQL/HQL function | Database SQL function |
| Executing parser | JPA provider | Database |
| Spring Data rewrite | HQL/EQL/JPQL enhancer per version | Regex or JSqlParser per version/config |
| Portability | Higher when using standard JPQL | Tied to database/dialect |

Do not switch to `nativeQuery=true` solely to make the parser accept syntax. Determine whether the query is meant to use entity semantics or physical SQL.

## 6. Native query enhancer: regex and JSqlParser

Spring Data needs to parse native SQL when adding sorting, pagination, or generating a count query. SQL has many dialects and structures; a simple regex cannot handle every query.

Two common options:

- **Built-in regex-based enhancer:** lightweight, requires no external SQL parser, suitable for simple queries.
- **JSqlParser:** a library that parses SQL into a structured AST so Spring Data can introspect/rewrite more complex queries.

Spring Data JPA 3.5 documentation describes the property for selecting the native parser in supported versions:

```properties
spring.data.jpa.query.native.parser=auto
```

Values documented by that version:

| Value | Meaning |
|---|---|
| `auto` | Auto-select based on dependency/configuration; this is the default |
| `regex` | Use the built-in regex-based Query Enhancer |
| `jsqlparser` | Force using JSqlParser |

The 3.5 documentation instructs setting this property in `spring.properties` or as a system property. Do not assume this property is read identically to every key in `application.properties`; check the exact documentation and configuration of the release train in use. Some newer versions have an enhancer selection mechanism via `QueryEnhancerSelector`.

If JSqlParser is on the classpath, documented Spring Data versions can use it automatically for native queries. Therefore, adding or upgrading JSqlParser can change how queries are parsed/rewritten even without changing repository source code.

### 6.1. When is regex sufficient?

The regex enhancer can suffice for simple queries such as:

```sql
select id, name
from product
where active = true
```

However, queries that can cause issues include:

- CTEs starting with WITH.
- UNION/UNION ALL.
- Nested subqueries.
- Window functions.
- GROUP BY/HAVING.
- SELECT DISTINCT with complex projections.
- Comments, hints, or database-specific syntax.
- ORDER BY inside a subquery alongside an outer ORDER BY.

There is no fixed list of limitations applicable to every release. When a query has complex structure, verify the enhancer capabilities for your exact version or declare an explicit countQuery.

### 6.2. JSqlParser is not a database validator

JSqlParser can understand SQL structure and help Spring Data rewrite queries. It does not verify:

- Whether tables/columns exist in the schema.
- Whether functions exist in the database.
- Whether data types are compatible with operators.
- Whether SQL is supported by a specific database version.
- Whether the query has a good execution plan.

A query parsed by JSqlParser can still be rejected by the database. Conversely, valid vendor-specific database SQL may fail to be parsed or rewritten accurately by the current JSqlParser version.

If JSqlParser is added to the classpath, verify version compatibility with the Spring Data JPA version in use and run integration tests. Avoid overriding dependencies just to get a newer parser without consulting dependency management.

## 7. Checking count queries when using Page

When a repository method returns `Page<T>`, Spring Data needs the total element count to compute `totalElements` and `totalPages`. The framework can derive a count query from the main query or use a developer-declared query.

Simple JPQL example:

```java
@Query("""
    select o
    from PurchaseOrder o
    where o.status = :status
    """)
Page<PurchaseOrder> findByStatus(
    @Param("status") OrderStatus status,
    Pageable pageable
);
```

Spring Data can derive the corresponding count query. However, with complex queries, do not assume the transformation always preserves semantics.

You can declare `countQuery`:

```java
@Query(
    value = """
        select o
        from PurchaseOrder o
        join o.customer c
        where c.status = :customerStatus
        """,
    countQuery = """
        select count(o)
        from PurchaseOrder o
        join o.customer c
        where c.status = :customerStatus
        """
)
Page<PurchaseOrder> findPageByCustomerStatus(
    @Param("customerStatus") CustomerStatus customerStatus,
    Pageable pageable
);
```

The data query and count query must share the same business predicates. The count query does not need ORDER BY and usually does not need fetch joins.

## 8. When is an explicit countQuery needed?

Prefer an explicit `countQuery` when:

- The native query is complex or uses database-specific syntax.
- There are CTEs, UNIONs, window functions, or nested subqueries.
- There is GROUP BY/HAVING and the total must count the number of groups.
- The query uses DISTINCT or projections that make count derivation unpredictable.
- There is a collection JOIN that multiplies root rows.
- The query uses multiple aliases or complex SELECT expressions.
- After a parser upgrade, the generated count query differs from expectations.
- The main query runs, but pagination fails in the count query.

Collection join query example:

```java
@Query(
    value = """
        select distinct o
        from PurchaseOrder o
        join o.lines line
        where line.productCode = :code
        """,
    countQuery = """
        select count(distinct o.id)
        from PurchaseOrder o
        join o.lines line
        where line.productCode = :code
        """
)
Page<PurchaseOrder> findByLineProductCode(
    @Param("code") String code,
    Pageable pageable
);
```

If counting `count(o)` in a collection join query, an Order with multiple matching Lines may be counted multiple times. Use `count(distinct o.id)` when the goal is counting distinct Order entities.

### 8.1. Counting groups

If a query returns one row per group, the count must count the number of groups, not the number of source entities.

Native SQL example:

```sql
select category_id, count(*)
from product
group by category_id
having count(*) > 5
```

The correct count for Page must count how many category groups satisfy HAVING. A common SQL pattern is wrapping the grouped query:

```sql
select count(*)
from (
    select category_id
    from product
    group by category_id
    having count(*) > 5
) grouped_categories
```

Derived table and alias syntax may need adjustment per database. Portable JPQL does not support all types of subqueries in FROM the way SQL does; for complex grouped reports, consider native SQL, a custom repository, or a separate query.

## 9. Native queries with countQuery

For native queries, explicitly declare `countQuery` when the query is structurally complex:

```java
@Query(
    value = """
        select p.*
        from product p
        where p.tenant_id = :tenantId
          and p.active = true
        order by p.created_at desc, p.id desc
        """,
    countQuery = """
        select count(*)
        from product p
        where p.tenant_id = :tenantId
          and p.active = true
        """,
    nativeQuery = true
)
Page<Product> findActiveProducts(
    @Param("tenantId") Long tenantId,
    Pageable pageable
);
```

In versions supporting `@NativeQuery`, you can use that annotation instead of `@Query(nativeQuery = true)`. Equivalent example:

```java
@NativeQuery(
    value = """
        select p.*
        from product p
        where p.tenant_id = :tenantId
          and p.active = true
        """,
    countQuery = """
        select count(*)
        from product p
        where p.tenant_id = :tenantId
          and p.active = true
        """
)
Page<Product> findActiveProducts(
    @Param("tenantId") Long tenantId,
    Pageable pageable
);
```

Check whether the annotation exists in the version you are using. `@NativeQuery` is a composed annotation for native queries and can provide additional attributes such as `sqlResultSetMapping` in supported releases.

A count query must:

- Retain all filter conditions that affect the result set.
- Retain JOINs needed to apply filters.
- Count the right result unit: rows, distinct entities, or groups.
- Use parameter names/positions matching the main query.
- Return a count value compatible with the type expected by the provider/repository.
- Omit ORDER BY when unnecessary.

## 10. countProjection does not replace every countQuery

Some Spring Data versions allow declaring `countProjection` to specify the projection expression used when deriving a count query.

This is helpful when the query remains simple and what needs changing is mainly the count expression. However, it does not solve all semantic issues involving JOINs, GROUP BY, UNION, CTEs, or vendor-specific native SQL.

If the count requires a different structure from the main query, declare the full `countQuery`. That is clearer and easier to review than trying to steer a derivation rewrite that no longer fits.

## 11. Page, Slice, and count cost

Not every endpoint needs the total page count.

| Return type | Metadata | Count query |
|---|---|---|
| `Page<T>` | Total elements, total pages, current page | May be needed to determine total |
| `Slice<T>` | Whether a next page exists | Does not need total page count |
| `List<T>` + Pageable | Only the limited list | No Page metadata |

If the UI only has a "Load more" button, using Slice can avoid the count query. If business requirements need totalElements/totalPages, Page remains appropriate and its count query must be verified.

In some cases Spring Data can infer the total from the content without executing a count query. Therefore, count query tests should cover both full pages and the last page; do not assume every Page call always runs two SQL statements.

## 12. Sort and aliases when the parser rewrites queries

Spring Data can append Sort to declared queries. With JPQL, Sort properties must be domain properties or valid aliases in the query.

Example:

```java
@Query("""
    select p.name as productName,
           length(p.name) as nameLength
    from Product p
    where p.active = true
    """)
List<Object[]> findNames(Sort sort);
```

Sorting by alias:

```java
Sort.by("nameLength")
```

The query enhancer must recognize aliases to place ORDER BY at the right query level. With subqueries or set operations, Sort should apply to the outer query according to result semantics. Some rewrite bugs only surface when queries contain parentheses, UNION, or multiple SELECTs.

Do not use `Sort.by("LENGTH(p.name)")` as a normal property path. Spring Data offers `JpaSort.unsafe(...)` for certain expressions, but unsafe expressions must be application-controlled and whitelisted; never concatenate user input into a query.

Native SQL dynamic sorting also depends on the enhancer and dialect. If a query is structurally complex or has specific ORDER BY requirements, writing dedicated SQL/queries per whitelisted sort option is often more reliable.

## 13. QueryRewriter is a separate layer from the query parser

Spring Data provides `QueryRewriter` to modify a query right before it is passed to EntityManager. This is a customization hook, not a JPQL/SQL parser and not a replacement for validation.

QueryRewriter can apply to both the actual query and the count query when appropriate. If a rewriter changes aliases, adds conditions, or alters structure, ensure the count query also preserves correct semantics.

Do not use global string regex replacement to modify queries with multiple aliases or subqueries without understanding the structure. For complex rewrites, consider a custom repository/Criteria or an AST-aware query builder.

## 14. Native query differences to verify after an upgrade

Native queries depend on the database, JDBC driver, parser enhancer, and Hibernate result mapping. Verify:

- Returned columns and aliases still match entity/DTO mappings.
- Aggregate data types have not changed, especially BIGINT/count.
- Parameter bindings use the right JDBC types.
- Pagination appends LIMIT/OFFSET/FETCH properly for the dialect.
- Dynamic Sort is placed on the outer query.
- CTEs, UNIONs, subqueries, and window functions are not misparsed by the enhancer.
- Native countQuery returns the accurate entity/group count.
- ResultSet mappings remain compatible with the provider.
- SQL functions/operators are supported by the database version.

In particular, native SQL is not analyzed by Hibernate the way JPQL is. Spring Data may parse it for rewriting, but the database decides whether the SQL is valid.

## 15. Error matrix and isolation strategy

| Symptom | Layer likely at fault | How to check |
|---|---|---|
| Repository fails at startup when creating query | Spring Data query creation or JPA provider validation | Inspect root cause, query string, and provider version |
| JPQL property does not exist | Hibernate/EclipseLink semantic parser | Use entity property, check mapping |
| Legacy JPQL worked in Hibernate 5 but fails in Hibernate 6 | SQM/semantic validation changes | Review association comparisons, identifiers, UPDATE syntax, path types |
| Main query runs but Page fails | Count query derivation or countQuery | Log count SQL separately and run directly against DB |
| Native query runs in DB client but Pageable fails | Spring Data native enhancer cannot rewrite it | Try JSqlParser if version supports it, or declare countQuery |
| Adding JSqlParser changes query behavior | Native enhancer selection/version | Inspect dependency tree and parser selection |
| Sort injected at wrong subquery level | Query enhancer does not recognize structure/alias | Move Sort to outer query or write separate query |
| Count is multiplied | Collection JOIN duplicates root rows | Use count distinct by ID |
| Group count is wrong | Count counts source rows instead of groups | Count over a derived table of the grouped query |
| Native count returns wrong Java type | Hibernate/JDBC mapping changed | Use Number/Long per contract and test driver |
| Query parses but database rejects it | SQL dialect/schema/function | Run the final SQL against the exact DB version |
| Query runs but is slower after upgrade | SQL generation or execution plan changed | Compare SQL, EXPLAIN, and indexes |

## 16. Pre-upgrade verification workflow

1. Inventory derived queries, JPQL `@Query` methods, native queries, and methods returning `Page`.
2. Record versions of Spring Boot, Spring Data JPA, Hibernate/EclipseLink, JSqlParser, JDBC driver, and database.
3. Identify which queries rely on HQL extensions or vendor-specific native syntax.
4. For Hibernate 5 to 6, review property paths, association comparisons, UPDATE syntax, result types, and native counts.
5. For Spring Data version upgrades, check changes to the query enhancer, alias handling, native parser selection, and count derivation.
6. Run repository tests against a production-compatible database.
7. Enable SQL logging in the test environment to compare main queries and count queries.
8. Inspect queries using DISTINCT, collection JOINs, GROUP BY, CTEs, UNIONs, window functions, and subqueries.
9. Write explicit `countQuery` for complex/native queries where auto-derivation is unclear.
10. Run EXPLAIN/EXPLAIN ANALYZE on critical queries.
11. Inspect the dependency tree to avoid JSqlParser or Hibernate overrides outside the BOM.
12. Roll out incrementally and monitor query/runtime errors after the upgrade.

## 17. Integration tests for query parsers and counts

Unit tests checking only query strings or mock repositories are insufficient to prove the parser, provider, and database agree on the query.

Use `@DataJpaTest` with an appropriate test database; if queries use vendor-specific native syntax, prefer Testcontainers with the exact engine/version close to production.

Recommended tests:

- Derived queries return accurate results after upgrade.
- JPQL `@Query` runs with actual aliases, joins, subqueries, and projections.
- Hibernate 6 has no queries relying on deprecated HQL syntax.
- Native queries execute directly against the database.
- Native queries with Pageable append sort/limit correctly.
- Count queries return accurate totals when filters include JOINs.
- Collection JOINs use count distinct when counting entities.
- GROUP BY/HAVING counts the number of groups accurately.
- CTEs/UNIONs/window functions have explicit `countQuery` and run properly.
- Native aggregates return expected Java types.
- QueryRewriter does not skew the count query.
- Page content and `totalElements` match known fixtures.

Example Page test:

```java
@DataJpaTest
class PurchaseOrderQueryTest {

    @Autowired
    private PurchaseOrderRepository repository;

    @Test
    void pageCountMatchesFilteredOrders() {
        // Arrange: create data with multiple OrderLines
        // and include an Order that does not match the filter.

        Page<PurchaseOrder> page = repository.findByLineProductCode(
            "SKU-1",
            PageRequest.of(0, 10)
        );

        assertThat(page.getContent()).hasSize(2);
        assertThat(page.getTotalElements()).isEqualTo(2);
    }
}
```

Fixtures should include a case where one Order has multiple matching Lines so the test catches multiplied counts. The example illustrates test structure only; data and constructors must match actual entities.

## 18. Query logging and observability

In test/dev environments, you can enable Hibernate SQL logging:

```properties
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE
```

Bind logging can expose sensitive data. Only enable it in secure environments and disable it after debugging.

When diagnosing errors, collect:

- Query declared in the repository.
- Query after Spring Data rewriting if observable.
- Final SQL sent by Hibernate to JDBC.
- Bound parameters and data types.
- Count SQL query.
- Database engine/version and execution plan.
- Full root cause exception.

Do not inspect only JPQL logs or initial SQL. What must be verified is the actual SQL and actual count query received by the database.

## 19. Pre-merge checklist for upgrade PRs

- [ ] Spring Boot, Spring Data JPA, Hibernate/EclipseLink, and driver are in a compatible version set?
- [ ] Derived queries and property traversal remain valid?
- [ ] JPQL uses entity properties rather than physical columns?
- [ ] Do any HQL extensions depend on a specific parser/provider?
- [ ] Any Hibernate 5 queries with `association = scalar ID` patterns fixed?
- [ ] Any UPDATE queries with optional FROM removed?
- [ ] Both sides of Criteria expressions have compatible types?
- [ ] Do native queries depend on the parser enhancer or JSqlParser?
- [ ] Is the native parser selected properly per version/config?
- [ ] Do complex queries have explicit `countQuery`?
- [ ] Do count queries keep filters and count the right entity/group unit?
- [ ] Tested DISTINCT/JOIN/GROUP BY/HAVING?
- [ ] Do native counts/aggregates have the expected Java types?
- [ ] Is dynamic Sort applied at the right query level?
- [ ] Does final SQL run on a production-compatible database?
- [ ] No regression in execution plans and query latency?

## 20. Conclusion

When upgrading Spring Data JPA and Hibernate, check Spring Data's parser, the provider's semantic parser, and the database's SQL parser separately. The Spring Data query enhancer analyzes queries to handle projections, Sort, and counting; Hibernate SQM validates HQL/JPQL and translates it to SQL; native SQL is parsed by the database after Spring Data performs enhancer-supported rewrites.

For JPQL, review Hibernate 6 semantic changes such as property paths, association comparisons, UPDATE syntax, and result types. For native queries, verify regex/JSqlParser behavior and rewrite capabilities for the exact version; complex queries should define an explicit `countQuery`. Count queries must count the proper result unit, especially with collection JOINs, DISTINCT, or GROUP BY.

Finally, run integration tests against the target database, compare actual SQL and count queries, check bind/result types, and inspect execution plans. Parsers help the framework understand query structure; only testing against the real provider and database confirms queries still behave correctly after an upgrade.
