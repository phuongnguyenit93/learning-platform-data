# Impact of Key Generation Strategies on Batch Data Imports

## 1. Why Key Generation Strategies Affect Batch Inserts

When Hibernate saves multiple entities, JDBC batching allows grouping multiple executions of the same `INSERT` statement into a single batch. Rather than sending each statement individually over the network to the database, the application prepares parameters for multiple records and calls `executeBatch()`. This reduces round trips between the application and the database, which is especially helpful when importing large volumes of data.

The ability to batch statements depends on when Hibernate obtains the primary key. If the database only returns the ID after executing `INSERT`, Hibernate may have to send each statement immediately to retrieve the ID. When the ID is already available before inserting, Hibernate can queue many statements into a batch. Consequently, `GenerationType.IDENTITY`, `SEQUENCE`, `TABLE`, UUIDs, and application-assigned keys can deliver vastly different bulk import performance.

## 2. Comparing Key Generation Strategies

| Strategy | When ID Is Available | JDBC Batch Insert Capability with Hibernate | Key Considerations |
| --- | --- | --- | --- |
| `IDENTITY` | After database inserts the row | Hibernate does not batch inserts for IDENTITY entities | Simple, but each insert must retrieve the generated key immediately |
| `SEQUENCE` | Fetched from sequence before insert | Can batch inserts | Efficient when pre-allocating a block of IDs; requires compatible sequence setup |
| `TABLE` | Fetched from a key table before insert | Can batch inserts | Generator table can cause lock contention and extra read/update operations |
| `UUID` | Generated by application/provider before insert | Can batch inserts | No DB round trip to fetch ID; UUID takes more bytes than numeric keys and can affect index locality |
| Self-assigned key | Assigned by application before persist | Can batch inserts | Application must guarantee uniqueness and safe key issuance |

With Hibernate ORM 6, entities using `IDENTITY` do not participate in JDBC insert batching because Hibernate needs to execute the insert to obtain the database-generated key. Strategies where the ID is known before insert, such as sequences or UUIDs, can leverage batching when JDBC and transaction settings are also configured appropriately.

`GenerationType.AUTO` does not guarantee a specific strategy. The JPA provider picks a generator based on dialect, version, and configuration. Inspect the actual mapping and DDL rather than assuming `AUTO` will use a sequence.

## 3. IDENTITY: Convenient but Limits Batching

Example:

```java
@Entity
@Table(name = "customer")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String name;
}
```

With IDENTITY, the database generates the ID when it receives the `INSERT`. Hibernate needs the ID to track the persisted entity and manage dependent relationships, so it must execute the insert early to read the generated key. Hibernate cannot group IDENTITY inserts via standard JDBC batching.

This does not mean IDENTITY is always slow or should be avoided. For low-write applications on databases with good identity support and small imports, simplicity may matter more than batching. However, when importing tens of thousands of records, this is a performance limitation to account for.

Do not expect merely adding `hibernate.jdbc.batch_size` to overcome this limitation. You must change the key generation strategy if your goal is JDBC insert batching with Hibernate.

## 4. SEQUENCE: Common Choice for Batch Inserts

A sequence issues IDs independently of the insert operation. Hibernate can fetch an ID or a range of IDs in advance, then queue multiple insert statements into a JDBC batch.

Example:

```java
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.SequenceGenerator;
import jakarta.persistence.Table;

@Entity
@Table(name = "customer")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "customer_id_generator")
    @SequenceGenerator(
        name = "customer_id_generator",
        sequenceName = "customer_seq",
        allocationSize = 50
    )
    private Long id;

    @Column(nullable = false)
    private String name;
}
```

`name` is the generator name in JPA mapping; `sequenceName` is the sequence name in the database. `allocationSize = 50` tells Hibernate the block allocation size for IDs. Hibernate can use a pooled optimizer to reduce sequence calls during bulk imports.

When managing DDL with Flyway or Liquibase, create the sequence with an increment matching the allocation size and optimizer used by Hibernate. Example for a database supporting sequences:

```sql
CREATE SEQUENCE customer_seq
    START WITH 1
    INCREMENT BY 50;
```

Do not copy `INCREMENT BY 50` mechanically into every configuration. Ensure the sequence increment, `allocationSize`, optimizer, and Hibernate's mismatch validation configuration align. Otherwise, Hibernate may fail on startup or allocate IDs unexpectedly. For schemas generated by Hibernate in development, inspect the generated DDL to understand the effective configuration.

Sequence is generally a strong choice when the database supports sequences and batch imports are needed. Migrating from IDENTITY to SEQUENCE requires schema migrations, checking existing data, current sequence values, and how IDs are issued across all applications writing to the table.

## 5. TABLE and UUID

### TABLE Generator

`GenerationType.TABLE` uses a separate table to store ID generation state. Because the generator must read/update a row in that table, it can introduce extra round trips and lock contention when multiple transactions request IDs concurrently. Allocation size can reduce generator accesses, though the generator table can still become a hotspot.

TABLE still knows the ID before entity insert, so it does not suffer from the same batching restriction as IDENTITY. Nevertheless, for write-heavy systems, sequences or application-generated IDs generally scale better. Choose TABLE only for compatibility reasons or specific requirements.

### UUID

With Jakarta Persistence 3.1 and Hibernate 6, you can use the UUID generator:

```java
@Entity
@Table(name = "customer")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    private String name;
}
```

UUIDs are generated before insert, so Hibernate can batch the statements. No database round trip is needed just to fetch an ID. On the flip side, UUIDs are larger than numeric keys and random UUIDs can give B-tree indexes poorer locality than ascending keys. Evaluate column type, index size, sortability, and multi-node ID generation requirements.

Self-assigned keys such as application-generated UUID/ULID also provide the advantage of knowing the ID beforehand. However, you must ensure the generator is high quality, collision-free, and safe when multiple instances run concurrently.

## 6. Enabling JDBC Batching in Spring Boot

The ID strategy is only part of the equation. You must configure Hibernate to enable JDBC batching:

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
          batch_versioned_data: true
        order_inserts: true
        order_updates: true
```

- `hibernate.jdbc.batch_size` is the maximum number of statements Hibernate groups into a single batch. Start testing with 25 or 50, then tune based on driver, database, record size, and real workload.
- `hibernate.order_inserts` orders inserts by entity/table so statements of the same shape sit adjacent to each other and can be batched.
- `hibernate.order_updates` orders updates, which can improve update batching and reduce certain deadlocks in suitable workloads.
- `hibernate.jdbc.batch_versioned_data` enables batching operations on versioned entities when the driver returns reliable update row counts as required by Hibernate.

A batch size of 50 does not mean the database necessarily receives one single SQL statement containing 50 value tuples. JDBC batching usually sends the same prepared statement multiple times via `addBatch()`/`executeBatch()`. Some drivers offer an option to rewrite batches into multi-row inserts; this is a driver-specific optimization and requires checking your database driver documentation.

`@BatchSize` and `hibernate.default_batch_fetch_size` relate to batch fetching when reading associations; they do not replace `hibernate.jdbc.batch_size` for inserts.

## 7. Batch Importing Data with flush and clear

Example using `EntityManager` and a sequence generator:

```java
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;

@Service
public class CustomerImportService {
    private static final int BATCH_SIZE = 50;

    @PersistenceContext
    private EntityManager entityManager;

    @Transactional
    public void importCustomers(List<Customer> customers) {
        for (int i = 0; i < customers.size(); i++) {
            entityManager.persist(customers.get(i));

            if ((i + 1) % BATCH_SIZE == 0) {
                entityManager.flush();
                entityManager.clear();
            }
        }
    }
}
```

`flush()` synchronizes pending changes with the database; Hibernate has an opportunity to execute the JDBC batch at this point. `clear()` detaches entities from the persistence context, avoiding holding tens of thousands of managed objects in memory. When the loop finishes, committing the transaction flushes any remaining partial batch.

The example above still uses a single transaction for the entire method. For very large imports where partial commits are needed to bound transaction duration, design separate transaction boundaries per chunk and clearly define error/rollback handling. Calling `flush()` alone does not commit the transaction.

Do not continue using entities that have been cleared as if they were still managed. If you need to update an entity after clearing, reload or merge it according to entity lifecycle rules.

## 8. saveAll Is Not Equivalent to a Single INSERT

`JpaRepository.saveAll()` typically iterates over the entities and calls `save()` for each element. It does not automatically construct a single multi-row `INSERT` statement, nor does it guarantee that JDBC batching is enabled. When transactions, generators, and Hibernate config align, statements generated by `saveAll()` can still be batched by Hibernate.

`saveAllAndFlush()` flushes after saving the list, but it does not turn the statements into a single SQL query. For very large imports, a `persist` loop combined with chunked `flush/clear` gives tighter control over the persistence context. Note that new and detached entities may take different persist/merge paths inside `save()`.

## 9. Conditions for Batching to Actually Work

- Entities must be written within a transaction long enough for Hibernate to accumulate statements.
- Use a generator that makes IDs known before insert; with Hibernate 6, IDENTITY blocks JDBC insert batching.
- Inserts must share compatible SQL shapes. Different entity types or inserts with differing column sets are batched separately.
- Enable `hibernate.jdbc.batch_size` with a value greater than 0.
- The JDBC driver and database must support batching properly; check driver limits, errors, and generated key behavior.
- Use chunked `flush/clear` for large imports to bound persistence context memory.
- Check whether triggers, cascades, associations, or callbacks emit extra SQL statements or alter write ordering.

Batching reduces communication overhead, but it does not eliminate the cost of indexes, constraints, triggers, transaction log writes, or database validation. Setting batch size too high can increase memory usage, lock hold times, and transaction sizes.

## 10. How to Measure and Diagnose

Do not conclude batching succeeded merely because `batch_size` was configured. Compare the same dataset against the same database, connection pool configuration, and transaction size.

1. Record import duration, records per second, CPU, memory, and database load.
2. Confirm the actual insert SQL and ID generator Hibernate is using.
3. Use JDBC logging, a datasource proxy, or driver observability tools to confirm `executeBatch()` calls and actual batch sizes.
4. Compare IDENTITY against SEQUENCE/UUID when supported by the database, holding all other factors constant.
5. Test multiple batch sizes such as 25, 50, and 100; pick based on measurements rather than always picking the largest number.
6. Measure sequence fetching, insert, flush, and commit costs separately if imports remain slow.

`org.hibernate.SQL` shows generated SQL statements, yet seeing many insert lines in logs does not prove JDBC batches were sent. Use observability tools at the JDBC/driver layer to confirm batching. You can enable Hibernate statistics in test environments for extra metrics, but avoid keeping verbose logging or statistics enabled permanently if they add overhead.

## 11. Choosing a Strategy by Scenario

| Scenario | Approach to Consider |
| --- | --- |
| Database supports sequences, bulk imports required | `SEQUENCE` with appropriate allocation and JDBC batching |
| Small application, low writes, already using identity | Keep `IDENTITY` if simplicity outweighs batch throughput |
| Need IDs generated independently across nodes | Pre-insert generated UUID/ULID; evaluate size and index locality |
| Integrating with a legacy schema | Use existing generator/schema; measure impact of TABLE or current ID issuer |
| Importing hundreds of thousands of records | Sequence/UUID, JDBC batching, chunked `flush/clear`, properly scoped transactions |

## 12. Pre-Deployment Checklist

- Verify database, JDBC driver, Hibernate version, and effective ID strategy.
- Check whether IDENTITY is preventing JDBC insert batching.
- If using SEQUENCE, align `allocationSize`, optimizer, and sequence DDL.
- Enable `hibernate.jdbc.batch_size` and consider `order_inserts`.
- Use appropriate transactions; for large imports, flush/clear in chunks.
- Measure with JDBC/driver tools and compare throughput on representative data.
- Verify ID correctness, rollbacks, constraints, cascades, and error handling when a chunk fails.

The key generation strategy determines whether Hibernate can prepare IDs before inserting or must wait for the database to return IDs after each insert. For bulk data imports, block-allocated SEQUENCE or UUIDs usually create favorable conditions for JDBC batching; final results should still be verified by benchmarking on the real database and driver.
