# Computed Properties, Database-Generated Fields, and Synchronization Risks

In a JPA entity, not every value is supplied directly by a user or stored as an ordinary column. Some values are computed from Java fields, some are computed by Hibernate using SQL expressions on read, and some are generated by the database via DEFAULT values, generated columns, or triggers.

These mechanisms differ in where computation occurs, writability, portability, and synchronization timing with objects in the persistence context. Choosing the wrong mechanism can leave entities displaying stale data, cause Java objects and the database to diverge, or duplicate calculations across layers with inconsistent results.

This lesson distinguishes derived Java properties, `@Transient`, Hibernate `@Formula`, database defaults, `@Generated`, `@GeneratedColumn`, and triggers; explains flush/refresh/clear, first-level and second-level caches, bulk updates, transactions, migrations, testing, and the risks of multiple write paths.

## 1. Four Places Where a Value Can Originate

Suppose OrderLine has quantity and unitPrice. The application needs lineTotal = quantity × unitPrice.

There are several ways to implement this:

1. Compute it directly in Java when the getter is called.
2. Use Hibernate `@Formula` to compute it from a SQL expression when the entity is read.
3. Declare a generated column in the database so the database computes it automatically when source columns change.
4. Store lineTotal as a regular column and have the service update it alongside quantity/unitPrice.

No single approach is always best. The decision depends on whether the value must be physically stored, queried or sorted in the database, shared as a formula with external systems, or audited.

| Approach | Where Computed | Physical Column? | Who Owns the Value? |
|---|---|---|---|
| Java getter | JVM | No | Application |
| @Transient field/property | JVM | No | Application |
| Hibernate @Formula | Database on SELECT | No stored result column | Hibernate mapping + SQL expression |
| Database DEFAULT | Database when INSERT omits column | Yes | Database |
| Generated column | Database by expression | Yes (generated column) | Database |
| Trigger + @Generated | Database on INSERT/UPDATE | Yes (column) | Database |
| Derived column written by service | Application | Yes | Application |

## 2. Properties Computed in Java

If a value is only needed for display or in-application logic, a computed getter is usually the simplest option:

~~~java
@Entity
@Table(name = "order_line")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "unit_price", nullable = false, precision = 12, scale = 2)
    private BigDecimal unitPrice;

    @Column(nullable = false)
    private int quantity;

    protected OrderLine() {
    }

    public BigDecimal getJavaTotal() {
        if (unitPrice == null) {
            return null;
        }

        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }
}
~~~

With field access as shown above, the getter has no backing persistent field, so no column is created in the database. Every call to getJavaTotal() recomputes the result from the object's current state.

Advantages:

- Results immediately reflect unflushed in-memory changes.
- No database query is required to compute it.
- No derived column needs synchronization.
- Easy to unit-test.

Limitations:

- Cannot use this getter directly as a property in JPQL or SQL.
- The database cannot sort, filter, or index by the Java getter's result.
- If the same calculation is repeated across services, UIs, or batch jobs, rules may be duplicated.
- Handling of null, scale, rounding, and overflow must stay consistent.

If an API needs a computed field for responses, a DTO projection or mapper may fit better than adding a persistent property to the entity.

## 3. @Transient for Non-Persisted Properties

Jakarta Persistence provides @Transient to mark fields or properties that should not be mapped to columns.

Example of a display-only field:

~~~java
@Entity
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private BigDecimal price;

    private int quantity;

    @Transient
    private String displayLabel;

    public String getDisplayLabel() {
        return quantity + " x " + price;
    }
}
~~~

@Transient does not mean the database computes the value. It simply tells JPA that the property is not part of persistent state.

Annotation placement must match the access strategy:

- Field access: place @Transient on the field.
- Property access: place @Transient on the getter.

If using @PostLoad to populate a transient field after loading an entity, remember the callback runs only at load time. When quantity or price changes later, the computed field will not update automatically unless the application recalculates it.

## 4. When to Use a Getter Instead of @Formula?

Use a Java getter when:

- The value is only needed in Java and must reflect in-memory object changes immediately.
- Database filtering or sorting on that value is not required.
- The formula does not need to be shared across external applications.
- The formula is small and inexpensive to compute.

Use @Formula or a generated column when the database must participate in the calculation—for example, queries filtering on the result, multiple clients reading the data, or a formula that must run uniformly inside the database.

If a calculation is needed for just a single query, consider a JPQL projection instead of adding a property to the entity:

~~~java
public record LineTotalView(
    Long id,
    BigDecimal total
) {
}

@Query("""
    select new example.dto.LineTotalView(
        line.id,
        line.unitPrice * line.quantity
    )
    from OrderLine line
    where line.id = :id
    """)
Optional<LineTotalView> findTotal(@Param("id") Long id);
~~~

A projection computes the value only for that query, adds no new column, and keeps managed entities free of extra derived state.

## 5. What Is Hibernate @Formula?

@Formula is a Hibernate-specific annotation that maps a SQL expression to a read-only entity property.

Example:

~~~java
@Entity
@Table(name = "order_line")
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "unit_price", nullable = false)
    private BigDecimal unitPrice;

    @Column(nullable = false)
    private int quantity;

    @Formula("quantity * unit_price")
    private BigDecimal formulaTotal;
}
~~~

When Hibernate loads OrderLine, the expression quantity * unit_price is included in the SELECT clause to compute formulaTotal.

@Formula:

- Does not create a column to store the result.
- Does not allow Hibernate to write formulaTotal back to the database.
- Uses a native SQL fragment, not a JPQL expression.
- Is Hibernate-specific, not part of Jakarta Persistence.
- Can reduce database portability if the expression uses vendor-specific functions or syntax.

Column names inside a formula are database column names, not necessarily Java property names. If a mapping specifies @Column(name = "unit_price"), the formula must reference unit_price.

## 6. @Formula Does Not Automatically Recompute in Managed Objects

A common pitfall is forgetting that formulas are evaluated when Hibernate reads the entity from the database. They are not Java getters recomputed on every access.

Example:

~~~java
OrderLine line = entityManager.find(OrderLine.class, id);

BigDecimal before = line.getFormulaTotal();

line.setQuantity(5);
entityManager.flush();

BigDecimal stillInMemory = line.getFormulaTotal();
~~~

After quantity changes on the object and Hibernate flushes the UPDATE, formulaTotal in the in-memory object can still hold the result from the earlier SELECT. Flushing writes the source field, but does not automatically cause Hibernate to re-read formulas in all cases.

If the updated value is needed, refresh the entity or reload it in an appropriate persistence context:

~~~java
entityManager.flush();
entityManager.refresh(line);

BigDecimal refreshed = line.getFormulaTotal();
~~~

refresh reloads database state and overwrites the entity's current in-memory state. Call it only after changes you want to preserve have been flushed; otherwise refresh can overwrite unflushed changes.

## 7. @Formula Can Be Complex, So Control the SQL

Hibernate allows formulas to contain complex SQL expressions, even subqueries. This can be convenient for derived values pulled from related tables.

However, complex formulas can:

- Trigger repeated subqueries for every entity in a result set.
- Make SELECT statements long and hard to optimize.
- Rely on non-portable functions across databases.
- Complicate filtering or sorting by the formula.
- Increase cost when entities are loaded in bulk.

Avoid turning entities into hosts for dozens of formulas instead of writing proper reporting queries. For heavy reporting, prefer DTO projections, views, materialized views, or dedicated aggregation queries.

## 8. What Is a Database DEFAULT?

DEFAULT is a value the database uses when an INSERT statement omits a column.

DDL example:

~~~sql
CREATE TABLE task (
    id BIGINT PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    status VARCHAR(30) DEFAULT 'PENDING'
);
~~~

If an INSERT omits the status column, the database uses PENDING. If the INSERT passes an explicit value, that passed value is used.

In standard SQL, explicitly passing NULL is not the same as omitting the column. DEFAULT does not replace an explicit NULL with the default value unless the database provides specific syntax such as DEFAULT ON NULL.

This matters in Hibernate: by default, generated INSERT statements may include every mapped column even when a Java field is null. When that happens, the database receives NULL instead of applying DEFAULT.

## 9. @ColumnDefault and @DynamicInsert

Hibernate provides @ColumnDefault to specify a default expression in Hibernate-generated DDL:

~~~java
@Entity
@DynamicInsert
public class Task {

    @Id
    @GeneratedValue
    private Long id;

    private String title;

    @ColumnDefault("'PENDING'")
    private String status;
}
~~~

@DynamicInsert instructs Hibernate to generate INSERT statements containing only fields with non-null values. If status is null, the status column is omitted from the INSERT so the database applies DEFAULT.

Distinguish clearly:

- @ColumnDefault describes the default in DDL.
- @DynamicInsert controls omitting null columns from INSERT.
- @ColumnDefault does not force Hibernate to omit the column from INSERT.
- @ColumnDefault does not read the database-assigned value back into the Java object.

When schemas are managed by Flyway or Liquibase, the migration itself must declare DEFAULT. Annotations do not alter production schemas when Hibernate runs with validate or none.

## 10. Database Defaults Can Cause Entity and Database State to Diverge

In the Task example above:

~~~java
Task task = new Task();
task.setTitle("Prepare report");

entityManager.persist(task);
entityManager.flush();
~~~

If status is null and @DynamicInsert omits the status column, the database may store PENDING. Yet task.status on the Java object can remain null because Hibernate does not automatically read back the default value unless the field is marked as generated.

You can synchronize via refresh:

~~~java
entityManager.refresh(task);
assertEquals("PENDING", task.getStatus());
~~~

If the database always owns this value, map it explicitly with @Generated as shown next so Hibernate retrieves the value automatically after INSERT.

## 11. Hibernate @Generated for Database-Generated Values

@Generated is a Hibernate annotation used when a property's value is generated or modified by the database during INSERT or UPDATE.

Common scenarios:

- Columns with DEFAULT in DDL.
- Triggers populating or modifying values.
- SQL expressions in INSERT/UPDATE generating values.
- Database-side normalization on write.

Example where status always gets its default from the database:

~~~java
@Entity
public class Task {

    @Id
    @GeneratedValue
    private Long id;

    private String title;

    @Generated(event = EventType.INSERT)
    @ColumnDefault("'PENDING'")
    @Column(insertable = false, updatable = false)
    private String status;
}
~~~

When Hibernate INSERTs Task, the status column is omitted from the statement. The database applies its default; Hibernate knows status is generated on INSERT and fetches the new value to synchronize the entity.

For fields fully owned by the database, insertable=false and updatable=false prevent Hibernate from overwriting the value.

## 12. Choosing @Generated Timing

@Generated can declare which events produce the value:

~~~java
@Generated(event = EventType.INSERT)
private String createdCode;
~~~

Reads back only after INSERT.

~~~java
@Generated(event = EventType.UPDATE)
private String recalculatedValue;
~~~

Reads back after UPDATE.

~~~java
@Generated(event = {EventType.INSERT, EventType.UPDATE})
private String normalizedCode;
~~~

Reads back after both INSERT and UPDATE.

EventType belongs to Hibernate, in package org.hibernate.generator. If event is omitted, @Generated defaults to INSERT.

Hibernate may use SQL RETURNING or an additional SELECT depending on dialect and JDBC driver. Therefore, the number of SQL statements issued depends on the database and provider.

## 13. Trigger-Generated Values and @Generated

Triggers are commonly used when the database must normalize data or enforce uniform rules across all clients writing to a table.

PostgreSQL trigger example normalizing a product code:

~~~sql
CREATE OR REPLACE FUNCTION normalize_product_code()
RETURNS trigger AS $$
BEGIN
    NEW.normalized_code := upper(trim(NEW.code));
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_product_normalize_code
BEFORE INSERT OR UPDATE OF code ON product
FOR EACH ROW
EXECUTE FUNCTION normalize_product_code();
~~~

Entity mapping:

~~~java
@Entity
@Table(name = "product")
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private String code;

    @Generated(event = {EventType.INSERT, EventType.UPDATE})
    @Column(name = "normalized_code",
            insertable = false,
            updatable = false)
    private String normalizedCode;
}
~~~

When Hibernate performs an INSERT or UPDATE, the trigger updates normalized_code. @Generated instructs Hibernate to read back the value after those operations.

If the trigger runs only on INSERT, use EventType.INSERT. If it runs on both INSERT and UPDATE, declare both events.

The SQL trigger example above is for PostgreSQL. MySQL, SQL Server, Oracle, and other databases have their own trigger syntax.

## 14. Generated Columns in the Database

A generated column is a column whose value is computed by the database from an expression referencing other columns.

DDL example using PostgreSQL syntax:

~~~sql
CREATE TABLE order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(12, 2) NOT NULL,
    line_total NUMERIC(14, 2)
        GENERATED ALWAYS AS (quantity * unit_price) STORED
);
~~~

The database automatically computes line_total on INSERT or whenever quantity/unit_price changes.

Depending on the database, a generated column can be VIRTUAL or STORED:

- VIRTUAL: the database computes the value on read according to engine semantics.
- STORED: the database stores the computed result at write time.

Support, syntax, and expression restrictions vary by database. Some engines disallow non-deterministic functions, subqueries, or references to columns in other tables.

## 15. Hibernate @GeneratedColumn

Hibernate provides @GeneratedColumn to map generated always as DDL columns:

~~~java
@Entity
@Table(name = "order_line")
public class OrderLine {

    @Id
    @GeneratedValue
    private Long id;

    private int quantity;

    @Column(name = "unit_price", precision = 12, scale = 2)
    private BigDecimal unitPrice;

    @GeneratedColumn("quantity * unit_price")
    @Column(name = "line_total",
            insertable = false,
            updatable = false)
    private BigDecimal lineTotal;
}
~~~

@GeneratedColumn declares the generated-column expression in DDL and instructs Hibernate to retrieve the value after INSERT/UPDATE.

This annotation belongs to Hibernate, not Jakarta Persistence. It was introduced in Hibernate ORM 6.0. Verify that your dialect supports the corresponding generated column expression and that production migrations match the definition.

If the database schema is managed by Flyway or Liquibase, the migration must declare the generated column. Never assume the annotation alters the production schema automatically.

## 16. How Does @Generated Differ from @GeneratedColumn?

Both annotations tell Hibernate that a value comes from the database, but their purposes differ:

| Mechanism | Used For |
|---|---|
| @Generated | Values produced by DEFAULT, triggers, or write-time SQL |
| @GeneratedColumn | Columns defined via generated always as DDL |
| @Formula | Read-only SQL expression without a stored column |
| @ColumnDefault | Declaring a default expression for DDL |
| @CreationTimestamp/@UpdateTimestamp | Timestamps generated by Hibernate per annotation strategy |
| @Transient | Non-persisted Java property |

Do not use @GeneratedColumn simply because the database has a trigger. Trigger-generated values typically pair with @Generated. Do not use @Generated instead of @GeneratedValue for identity/autoincrement identifiers; identifiers continue to use @GeneratedValue per JPA mapping.

## 17. @CreationTimestamp, @UpdateTimestamp, and @CurrentTimestamp

Hibernate provides timestamp-generation annotations, though their time sources differ.

In Hibernate ORM 6.6:

- @CreationTimestamp generates a timestamp when the entity is created, defaulting to JVM time.
- @UpdateTimestamp generates a timestamp when the entity is created or updated, defaulting to JVM time.
- @CurrentTimestamp uses the database's current_timestamp via an in-DB strategy.

Example:

~~~java
@Entity
public class AuditRecord {

    @Id
    @GeneratedValue
    private Long id;

    @CreationTimestamp
    private Instant createdAt;

    @UpdateTimestamp
    private Instant updatedAt;

    @CurrentTimestamp(event = EventType.INSERT)
    private Instant databaseCreatedAt;
}
~~~

If multiple application servers have clock skew, JVM-generated timestamps can be inconsistent. When database time is required, use an appropriate DB strategy and verify precision and time zones.

Do not treat these timestamp annotations as a complete substitute for business auditing. They do not record who performed the action, request IDs, or the reason for the change.

## 18. @ColumnTransformer Is Not a Generated Property

@ColumnTransformer lets Hibernate apply SQL expressions when reading/writing a value stored in one or more columns.

Example storing monetary amounts in cents while the application works in currency units:

~~~java
@Column(name = "amount_cents")
@ColumnTransformer(
    read = "amount_cents / 100.0",
    write = "? * 100"
)
private BigDecimal amount;
~~~

Key differences:

- @Formula is a read-only property computed from SQL.
- @ColumnTransformer still maps one or more columns and supports read/write.
- @Generated is used when the database generates a value and Hibernate must read it back.
- @GeneratedColumn maps a generated always as column.

If the read expression does not cleanly invert the write expression, Java state can fall out of sync with the database. In such cases, use an appropriate refresh strategy or generated-value configuration as documented by Hibernate.

## 19. Persistence Context and First-Level Cache

EntityManager maintains a persistence context. Once an entity is loaded, subsequent finds within the same persistence context typically return the same managed instance instead of re-reading the row from the database.

This preserves identity within a unit of work, yet introduces stale-state risk:

1. Hibernate loads Product with normalizedCode = ABC.
2. A trigger, native SQL, or external application updates normalizedCode to XYZ.
3. The managed Product inside EntityManager may still hold ABC.
4. Calling findById again in the same persistence context may return that same old object.

The database may already be up to date while the Java object remains unsynchronized.

## 20. How Do flush, refresh, and clear Differ?

**flush()** pushes pending changes from the persistence context to the database. Flushing does not commit the transaction.

**refresh(entity)** re-reads database state for a single managed entity and overwrites its in-memory state.

**clear()** detaches all entities from the current persistence context. Subsequent finds will load fresh instances.

Example:

~~~java
entityManager.flush();

entityManager.refresh(product);

String currentCode = product.getNormalizedCode();
~~~

Refresh only after changes you wish to keep have been flushed. refresh can overwrite unsaved Java values.

If only one entity needs reloading, refresh is usually clearer than clearing the entire context. After running bulk operations across many entities, clear may be more appropriate.

## 21. @Generated Reduces Manual Refreshes, But Does Not Cover All Write Paths

When Hibernate executes INSERT or UPDATE and a field is marked @Generated, Hibernate automatically retrieves the database value after the corresponding event.

However, @Generated does not run when:

- Another application writes directly to the database.
- A DBA runs a SQL script.
- JDBC/JdbcTemplate executes an UPDATE outside the entity lifecycle.
- Bulk JPQL mutations bypass entity state synchronization.
- An external job updates the table after Hibernate's transaction ends.

In those scenarios, an open persistence context may still hold stale data. Refresh, clear, or finish the unit of work before re-reading.

## 22. Bulk JPQL Update/Delete and the Persistence Context

Bulk JPQL updates/deletes operate directly on the database without loading and updating managed entity instances.

Spring Data example:

~~~java
@Modifying(
    flushAutomatically = true,
    clearAutomatically = true
)
@Query("""
    update Product p
    set p.code = :code
    where p.id = :id
    """)
int updateCode(
    @Param("id") Long id,
    @Param("code") String code
);
~~~

flushAutomatically pushes pending changes before the bulk query. clearAutomatically clears the persistence context afterward to prevent continued use of stale entity state.

Without clearing or refreshing, a previously loaded Product entity may retain old code/normalizedCode values even though a trigger updated the database.

Bulk queries also skip setters, entity callbacks, and per-entity dirty checking. If business logic depends on those mechanisms, design around them explicitly.

## 23. Native SQL, JDBC, and External Systems

When using JdbcTemplate or native SQL directly:

~~~java
jdbcTemplate.update(
    "update product set code = ? where id = ?",
    newCode,
    productId
);
~~~

Hibernate does not know which rows changed when statements bypass entity management.

If a managed Product exists in the same transaction:

- Flush before running JDBC if pending Hibernate changes must be preserved.
- After the JDBC update, refresh Product or clear the persistence context.
- If second-level/query caches are enabled, evict/invalidate affected caches.
- If a database trigger updates other tables as well, corresponding entities may also become stale.

For external systems outside the application, establish cache invalidation protocols or cache TTLs. @Generated does not replace synchronization across multiple applications.

## 24. Second-Level Cache and Query Cache

The first-level cache lives inside an EntityManager's persistence context. Second-level caches and query caches can outlive a single transaction and be shared across sessions.

If the database changes outside Hibernate, refreshing an entity in one EntityManager does not automatically inform every other cache.

Evaluate:

- Whether the entity enables second-level caching.
- Whether queries use the query cache.
- Whether native SQL declares query spaces/synchronized entities so Hibernate knows which tables are affected.
- Whether Spring or Redis caches exist at the service layer.
- Who is responsible for invalidating caches when external systems write to the database.

For data modified by multiple systems, cache policies must be designed as part of consistency architecture, not merely via an annotation on an entity.

## 25. @Version and Concurrent Updates

@Generated reads back database-generated values; it does not resolve conflicts when two transactions edit the same entity concurrently.

JPA `@Version` supports optimistic locking:

~~~java
@Entity
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private String code;

    @Version
    private long version;
}
~~~

If two transactions read the same version and both try to update, the later write with the stale version can fail with an optimistic locking exception instead of silently overwriting the other transaction's changes.

Distinguish:

- @Version detects concurrent modifications.
- @Generated/@GeneratedColumn synchronizes database-generated values.
- refresh reloads current state.
- cache invalidation refreshes data across persistence contexts.

A trigger updating other columns does not substitute for optimistic locking. If a database trigger also increments the version column, coordinate mapping and provider behavior carefully; never let Hibernate and a trigger both increment version by uncoordinated rules.

## 26. Transactions and Generated Values

Database-generated values within a transaction are visible according to database transaction and isolation rules.

Key points to remember:

- save() may not emit SQL immediately; Hibernate can defer until flush.
- saveAndFlush() or entityManager.flush() forces SQL earlier without committing the transaction.
- @Generated reads values back after Hibernate's INSERT/UPDATE.
- Rolling back a transaction rolls back trigger- or generated-column changes made within that transaction.
- If a transaction rolls back after the Java object received a generated value, the in-memory object may still hold that value even though the row was never committed. Never reuse that detached object as a source of truth.
- Other transactions typically cannot see uncommitted changes.

If a trigger dispatches asynchronous work after commit and the value is updated later, @Generated reading immediately after INSERT cannot wait for that future result. Use polling, an outbox/event pattern, or explicit processing states for asynchronous workflows.

## 27. Multiple Write Sources and Formula Drift Risks

A common architectural bug is persisting a derived value and allowing multiple places to calculate and update it independently:

- A REST service updates lineTotal.
- A batch job also updates lineTotal.
- An import script updates only quantity/unitPrice.
- A trigger additionally updates lineTotal.
- A legacy client is unaware of the new column.

Over time, lineTotal can drift out of equality with quantity × unitPrice.

To reduce risk:

1. Pick a single source of truth for the formula.
2. If the database is the source of truth, prefer generated columns or triggers.
3. If the application is the source of truth, centralize the calculation in domain/service code and route all writes through it.
4. Use check constraints or generated expressions if the database can enforce them.
5. When adding a derived column, backfill historical rows before the application depends on it.
6. Test all write paths: Hibernate, bulk SQL, JDBC, imports, and migrations.

Do not duplicate a value in storage just to avoid a trivial multiplication without a clear, measured performance reason.

## 28. Migrations and Schema Drift

Hibernate annotations do not guarantee that production schemas match local schemas.

For example:

- @ColumnDefault may participate in DDL generation, but migrations must still create DEFAULT.
- @GeneratedColumn requires generated expressions valid in the target database syntax.
- Triggers require function and trigger DDL.
- @Formula creates no physical column.
- @Generated only instructs Hibernate to read values back; it does not create triggers or defaults.

With Flyway or Liquibase, migrations must create:

- Columns and data types.
- DEFAULT or generated expressions.
- Triggers/functions if applicable.
- Indexes if queries filter/sort by generated values.
- Backfills for existing rows if adding a new physical column.

Use ddl-auto=validate in environments that verify mappings against migration-managed schemas. Never rely on ddl-auto=update to deploy generated columns or complex triggers to production.

## 29. Backfills and Formula Changes

When changing a formula from quantity × unitPrice to a new rule with rounding or discounts, decide how historical data should be handled.

With generated columns, the database generally evaluates the current expression on read or write according to engine semantics. With manually persisted derived columns, migrations/backfills must update all existing rows.

Safe steps:

1. Write migrations adding the schema/columns.
2. Backfill existing data.
3. Verify row counts and invariants.
4. Deploy code reading from the new schema.
5. Switch write paths to the new mechanism.
6. Monitor for drift using verification queries.
7. Remove old logic once no client writes using the legacy path.

If formulas involve money, rounding modes and precision must match between Java and the database. BigDecimal and DECIMAL/NUMERIC are far better suited than floating-point types for monetary values.

## 30. Performance of Each Approach

| Approach | Primary Cost | How to Optimize |
|---|---|---|
| Java getter | JVM CPU on call | Compute on demand; avoid repeated evaluation if expression is expensive |
| @Formula | SQL expression in SELECT | Keep formulas simple; inspect execution plans |
| Generated virtual column | Engine computation on read | Check database indexing support |
| Generated stored column | Write-time compute cost and storage | Index if queried frequently |
| Trigger | Trigger overhead per INSERT/UPDATE | Keep triggers short; test locking and recursion |
| Service-written derived column | Extra write payload and consistency logic | Centralize write paths; measure actual gain |

You cannot assume generated columns are always faster than @Formula. Stored generated columns help when values are queried frequently and the database supports indexing them. Formulas can be sufficient when row counts are small or expressions are cheap.

## 31. Testing Against a Real Database

Generated columns, triggers, and DEFAULT values depend on database dialect. H2 may not accurately emulate PostgreSQL, MySQL, SQL Server, or Oracle.

Use Testcontainers with a database matching production for integration tests.

Example configuring a PostgreSQL container with DynamicPropertySource:

~~~java
@DataJpaTest
@Testcontainers
class OrderLineGeneratedColumnTest {

    @Container
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired
    private TestEntityManager entityManager;

    @Test
    void generatedColumnIsReadBackAfterInsert() {
        OrderLine line = new OrderLine(
            3,
            new BigDecimal("12.50")
        );

        entityManager.persist(line);
        entityManager.flush();

        entityManager.refresh(line);

        assertEquals(
            new BigDecimal("37.50"),
            line.getLineTotal()
        );
    }
}
~~~

This test assumes migrations created the generated column line_total and the entity has matching constructors and getters. With Hibernate @GeneratedColumn, Hibernate retrieves the value after INSERT; refresh here makes the re-read explicit during test verification and can be omitted if you have verified automatic generated-state synchronization in your specific Hibernate version/provider.

## 32. Essential Synchronization Test Suite

For entities with database-generated properties, test:

1. INSERT applies DEFAULT when the column is omitted.
2. INSERT passing explicit NULL behaves according to DDL.
3. @DynamicInsert omits only expected null fields.
4. @Generated(event=INSERT) reads trigger/default values.
5. @Generated(event=UPDATE) re-reads values after an update trigger.
6. @GeneratedColumn returns correct results after source columns change.
7. @Formula computes correctly on fresh entity loads.
8. @Formula requires refresh/reload to update after modifying source fields.
9. Bulk JPQL updates do not leave the persistence context using stale state.
10. Native SQL/JDBC updates follow refresh/clear/cache-invalidation procedures.
11. Rollbacks leave no committed generated data behind.
12. Concurrent updates across transactions do not lose data.
13. Migrations create exact defaults, generated expressions, and triggers.
14. All supported database versions accept the generated-column syntax.
15. Precision, scale, rounding, and time zones match.
16. @Version detects concurrent updates at the right transaction boundaries.

Do not inspect only the in-memory object right after save. Read the row back with an independent query or fresh EntityManager to verify what the database actually persisted.

## 33. Common Pitfalls and Fixes

**1. Database has DEFAULT, yet Java field remains null**

Hibernate may have inserted NULL instead of omitting the column. Use @DynamicInsert to omit null columns, or map DB-owned fields with @Generated and insertable=false.

**2. @ColumnDefault does not make the database apply a default**

Inspect actual DDL. @ColumnDefault does not alter production schemas if migrations did not create DEFAULT.

**3. @Formula does not update after setter calls**

Formulas evaluate during SELECT. Flushing does not guarantee formula fields on managed objects are recomputed; refresh or reload when needed.

**4. @Generated fails to read trigger values**

Verify INSERT/UPDATE events, insertable/updatable mapping, trigger timing, actual SQL, and Hibernate version.

**5. Generated column fails to create on the database**

Check dialect and database generated-expression syntax. Not all databases support the same features or expression kinds.

**6. Current entity still holds stale data after a JDBC update**

This is stale persistence-context state. Flush before JDBC if needed, then refresh the entity or clear the context.

**7. Bulk update fails to synchronize already-loaded entities**

Bulk JPQL bypasses managed entity instances. Use flushAutomatically/clearAutomatically or refresh entities you continue to use.

**8. Second-level cache returns stale data**

Evict/invalidate affected caches when updating outside Hibernate. Check query caches and service-layer caches.

**9. Triggers slow down writes**

Measure trigger duration, indexes, locks, and firing frequency. Keep trigger logic concise and avoid repetitive queries.

**10. Java and database values diverge due to rounding**

Align BigDecimal scale, rounding mode, and DECIMAL/NUMERIC types; never use double for money.

**11. Tests pass on H2 but fail in production**

Run Testcontainers on the exact production database engine/version using real migrations.

**12. Multiple write paths produce inconsistent derived values**

Establish a single source of truth, use generated columns/triggers or centralize write paths, and add backfills plus invariant checks.

## 34. Process for Choosing the Right Mechanism

1. Determine whether the value is only for Java or must be queried/sorted in the database.
2. If Java-only, use a getter or @Transient.
3. If a read-only SQL expression on load suffices, consider @Formula.
4. If a database column computed from other columns is needed, consider generated columns and @GeneratedColumn.
5. If the database produces values via DEFAULT or triggers, use @Generated with appropriate events.
6. If only an INSERT default is needed, ensure the column is actually omitted from INSERT.
7. Define the source of truth: Java or database.
8. Verify flush/refresh/clear and caching behavior.
9. Account for bulk JPQL, native SQL, JDBC, and external systems.
10. Write migrations for DEFAULT, generated expressions, and triggers.
11. Test against a production-equivalent database.
12. Measure SQL, trigger overhead, indexes, and query plans.
13. Define backfill and cache invalidation workflows when formulas change.

## 36. Review Questions

**1. When should you use a Java getter instead of @Formula?**

When the value is only needed in Java, must reflect in-memory object changes immediately, and does not need database filtering or sorting.

**2. Does @Transient create a database column?**

No. It marks a property as excluded from JPA table persistence.

**3. Is @Formula part of the Jakarta Persistence standard?**

No. It is a Hibernate annotation using a native SQL fragment and can affect database portability.

**4. Why can @Formula become stale after calling setters?**

Hibernate computes formulas during SELECT. Changing source fields in memory does not re-execute the SQL formula.

**5. Is @ColumnDefault enough to make the database apply DEFAULT?**

No. The actual schema must define DEFAULT, and the INSERT statement must omit the column instead of explicitly passing NULL.

**6. When is @Generated used?**

When the database produces a value via defaults, triggers, or SQL expressions and Hibernate needs to read that value back after INSERT/UPDATE.

**7. How does @GeneratedColumn differ from @Generated?**

@GeneratedColumn is for generated always as DDL columns. @Generated is for values produced by mechanisms such as triggers, defaults, or SQL generation.

**8. Why must you refresh after native SQL?**

Hibernate does not automatically know that an external JDBC statement modified a row. Managed entities can continue holding stale snapshots.

**9. Does flush commit the transaction?**

No. Flush sends SQL to the database within the current transaction; commit completes the transaction.

**10. What problem does @Version solve?**

It detects concurrent updates and prevents a transaction from overwriting a version modified by another transaction. It does not synchronize generated values or caches.

**11. Why is Testcontainers needed?**

Generated columns, triggers, defaults, and SQL expressions vary across database engines. Testcontainers verifies behavior on the same database type used in production.

Computed properties and database-generated values require a clear source of truth. Java getters fit in-memory derived values; @Formula fits read-only SQL expressions; @Generated and @GeneratedColumn keep Hibernate synchronized with database values produced after DML. By understanding the persistence context, caching, bulk SQL, optimistic locking, and transactions, applications avoid stale state and keep data consistent across write paths.
