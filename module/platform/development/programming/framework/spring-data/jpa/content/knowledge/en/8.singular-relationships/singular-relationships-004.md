# One-to-One Relationships Sharing a Primary Key with @MapsId

In a one-to-one relationship sharing a primary key, the child entity uses **the parent entity's primary key as its own primary key**, while that same key also serves as a foreign key referencing the parent table. JPA represents this relationship using **@OneToOne + @MapsId**.

For example, a Customer can have one CustomerProfile. The `customer_profiles` table does not need a separate `id` column or a separate sequence. The `customer_id` column is both the primary key of `customer_profiles` and the foreign key to `customers.id`. This design fits when the profile depends closely on the customer's identity and lifecycle.

## 1. What Is a Shared Primary Key?

In a typical one-to-one relationship, the child table can have its own primary key and a unique foreign key column:

```text
customers
+----+-----------+
| id | name      |
+----+-----------+
| 10 | An        |
+----+-----------+

customer_profiles
+----+-------------+----------------+
| id | customer_id | display_name   |
+----+-------------+----------------+
| 55 | 10          | An Nguyen      |
+----+-------------+----------------+
```

In the example above, the profile has its own ID 55, and `customer_id = 10` references the customer.

With a shared primary key, the child uses the exact same key value as the parent:

```text
customers
+----+-----------+
| id | name      |
+----+-----------+
| 10 | An        |
+----+-----------+

customer_profiles
+-------------+----------------+
| customer_id | display_name   |
+-------------+----------------+
| 10          | An Nguyen      |
+-------------+----------------+
```

The `customer_id` column in `customer_profiles` is simultaneously:

- The primary key of `customer_profiles`.
- The foreign key referencing `customers.id`.
- The identity value of `CustomerProfile`.
- Equal to `Customer.id`.

Because the child table's primary key is unique, one Customer cannot have two CustomerProfiles. However, a Customer may still not have a profile yet. The one-to-one constraint on the child side ensures every profile belongs to exactly one customer and at most one profile is attached to a customer.

## 2. When Should You Use a Shared Primary Key?

A shared primary key is suitable when the child entity is identity-dependent on the parent entity:

- Customer and CustomerProfile.
- User and UserSettings.
- Employee and EmployeePrivateDetails.
- Product and a per-product ProductSpecification.
- Account and AccountPreferences.

The common trait is that the child entity has no independent identity outside the parent entity. When the parent does not exist, the child should not exist either.

Do not use a shared primary key just because two tables have a one-to-one relationship. If the child entity has an independent lifecycle, needs to be created before the parent, may be referenced elsewhere, or needs its own ID for system integration, a separate primary key plus a unique foreign key may be more appropriate.

## 3. Database Structure

PostgreSQL schema example:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);

CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120),
    bio VARCHAR(1000),
    CONSTRAINT fk_customer_profiles_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

There is no separate `profile_id` column. `customer_id` is the primary key, so uniqueness is already guaranteed; there is no need to add a second unique constraint on the same column.

The foreign key ensures a profile cannot be created pointing to a non-existent customer. The child's primary key ensures each customer has at most one profile.

Note: this schema does not require every customer to have a profile. It only guarantees every profile has a customer. If business rules require every customer to have a profile, enforce that at the business/transaction layer or with a different schema design; a foreign key from child to parent does not enforce the reverse requirement automatically.

## 4. Mapping with @MapsId

JPA provides **@MapsId** to express derived identity: an entity's key is derived from a relationship to another entity.

Parent entity:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "customers")
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 160)
    private String name;

    @OneToOne(
        mappedBy = "customer",
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private CustomerProfile profile;

    protected Customer() {
    }

    public Customer(String name) {
        this.name = name;
    }

    public void attachProfile(CustomerProfile profile) {
        this.profile = profile;
        profile.attachTo(this);
    }

    public Long getId() {
        return id;
    }
}
```

Child entity:

```java
import jakarta.persistence.*;

@Entity
@Table(name = "customer_profiles")
public class CustomerProfile {

    @Id
    private Long id;

    @MapsId
    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @Column(name = "display_name", length = 120)
    private String displayName;

    @Column(length = 1000)
    private String bio;

    protected CustomerProfile() {
    }

    public CustomerProfile(String displayName, String bio) {
        this.displayName = displayName;
        this.bio = bio;
    }

    void attachTo(Customer customer) {
        this.customer = customer;
    }

    public Long getId() {
        return id;
    }
}
```

Key points:

1. `Customer.id` is the primary key generated by the database via IDENTITY.
2. `CustomerProfile.id` is annotated with `@Id` but **has no @GeneratedValue**.
3. `@MapsId` indicates that `CustomerProfile`'s ID is derived from the referenced `Customer`'s key.
4. `@JoinColumn(name = "customer_id")` specifies the column serving as both the primary key and the foreign key in `customer_profiles`.
5. `@OneToOne(mappedBy = "customer")` on `Customer` is the inverse side; the `customer` field in `CustomerProfile` is the owning side because it maps the foreign key column.
6. Cascading from `Customer` to `CustomerProfile` allows saving/deleting the profile along with the customer's lifecycle in this example.

Do not also declare `@Column(name = "customer_id")` on the `id` field in the example above. The relationship annotated with `@MapsId` already maps the association onto the child's primary key column. Adding a separate column mapping improperly can cause a duplicate column mapping error.

## 5. How Does @MapsId Synchronize the ID?

Suppose you create a new Customer and attach a profile:

```java
@Transactional
public Long createCustomer() {
    Customer customer = new Customer("An");

    CustomerProfile profile =
            new CustomerProfile("An Nguyen", "Customer profile");

    customer.attachProfile(profile);

    Customer saved = customerRepository.save(customer);

    return saved.getId();
}
```

Processing flow:

1. The new `Customer` has no ID yet.
2. `CustomerProfile` is linked to `Customer` through the `customer` association.
3. `CustomerRepository.save` saves the `Customer`.
4. Cascade PERSIST from `Customer` to `CustomerProfile` is applied.
5. The database generates `Customer.id`.
6. JPA/the provider synchronizes the association's key into `CustomerProfile.id` according to `@MapsId`.
7. When inserting the profile, `customer_id` is used as both PK and FK.

With IDENTITY, the provider needs to insert the parent to obtain the key before inserting the child. When the ID becomes populated on the object can depend on the provider and flush timing. If you need to inspect the value after saving, read it after an appropriate save/flush or after the transaction completes.

**Do not manually assign an arbitrary number to CustomerProfile.id.** `@MapsId` requires the child ID to be derived from the association. Assigning two different IDs violates derived identity semantics and can cause mapping or persistence errors.

## 6. Why Does the Child Not Have @GeneratedValue?

In this model, `CustomerProfile` does not own an independent ID sequence. The profile's identity is the Customer's identity.

Do not declare `@GeneratedValue` on the child ID. Asking the database to generate an independent ID while declaring `@MapsId` to take the ID from the parent creates conflicting intentions in the design.

The `customer_id` column receives its value through the association. Once the parent has an ID, the child uses that exact value. No separate sequence, identity column, or table generator is needed for the child.

The ID data types of both entities must be compatible. If `Customer.id` is `Long`, then `CustomerProfile.id` should also be `Long`. If the parent uses `UUID`, the child should use `UUID` accordingly.

## 7. Synchronizing Both Sides of the Relationship

In a bidirectional relationship, `Customer.profile` is the inverse side and `CustomerProfile.customer` is the owning side. Updating only the inverse side is not enough to write the foreign key. The `attachProfile` method in `Customer` calls `profile.attachTo(this)`, ensuring both sides are updated together.

If you only do:

```java
customer.setProfile(profile);
```

without setting `profile.customer`, the owning side remains null. The database cannot know what `customer_id` value to save.

Encapsulate this operation in a helper method or domain method so callers do not forget to synchronize. Do not let controllers modify the two fields individually.

If the child can be detached from the parent, define clear lifecycle rules. With `orphanRemoval = true`, removing the child from the parent relationship instructs the provider to delete the child when synchronizing the persistence context. If a reference to the child is held elsewhere in the same flow, keep the object graph consistent and do not continue using an orphaned child.

## 8. Cascade and orphanRemoval

In the example, `Customer` has:

```java
@OneToOne(
    mappedBy = "customer",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private CustomerProfile profile;
```

`CascadeType.ALL` includes `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, and `DETACH`. When persisting a customer, the profile is persisted too. When deleting a customer via JPA, the profile is deleted as well. `orphanRemoval = true` deletes the profile when it is detached from the relationship.

Only use `CascadeType.ALL` if the profile truly depends on the customer's lifecycle. If the profile can be managed independently or has different deletion rules, choose specific cascade types instead of `ALL`.

Do not cascade `REMOVE` from `CustomerProfile` back to `Customer`. Deleting a profile should not automatically delete the customer. The cascade direction must reflect business ownership, not just the database relationship direction.

JPA cascade is behavior of the persistence provider. It differs from `ON DELETE CASCADE` in the database. If migrations create `ON DELETE CASCADE`, the database may delete child rows automatically when a parent row is deleted directly with SQL; this must be coordinated with the application's persistence context and cache.

## 9. Optionality and Fetch Strategy

On the child, the association declares:

```java
@OneToOne(fetch = FetchType.LAZY, optional = false)
@MapsId
@JoinColumn(name = "customer_id", nullable = false)
private Customer customer;
```

**optional = false** indicates that a `CustomerProfile` must always reference a `Customer`. It does not mean every `Customer` must have a `CustomerProfile`.

The parent side may not have a profile, so the inverse relationship is typically optional. A `Customer` may already have a profile or not yet have one.

`OneToOne` defaults to `EAGER` in JPA. Declaring `LAZY` expresses a desire for deferred loading, but `LAZY` on `OneToOne` is a hint whose feasibility depends on the provider, relationship direction, and bytecode enhancement. In particular, an inverse `OneToOne` may require the provider to check whether the child exists before creating a proxy. Do not assume `LAZY` always means no extra query; inspect the actual SQL.

If a screen always needs the profile, use a fetch join or `EntityGraph` on the specific repository method instead of setting global `EAGER`.

## 10. Repositories and Queries

The child's repository uses the same ID type as the parent:

```java
public interface CustomerProfileRepository
        extends JpaRepository<CustomerProfile, Long> {
}
```

Because `CustomerProfile.id` is `Customer.id`, you can look up a profile by the customer ID:

```java
Optional<CustomerProfile> profile =
        customerProfileRepository.findById(customerId);
```

JPQL can query the profile along with the parent:

```java
@Query("""
    select p
    from CustomerProfile p
    join fetch p.customer
    where p.id = :customerId
    """)
Optional<CustomerProfile> findWithCustomer(
    @Param("customerId") Long customerId
);
```

JPQL uses entity names and Java properties. Native SQL uses `customer_profiles` and `customer_id`. Do not confuse the Java `id` field name with the physical `customer_id` column name.

## 11. Variant with @EmbeddedId

If the child entity's key is a composite key and only part of it comes from the parent, `@MapsId` takes the property name inside the embedded ID:

```java
@Embeddable
public class CustomerDocumentId implements Serializable {

    private Long customerId;
    private String documentType;

    // equals() and hashCode()
}

@Entity
@Table(name = "customer_documents")
public class CustomerDocument {

    @EmbeddedId
    private CustomerDocumentId id;

    @MapsId("customerId")
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
```

In this example, `customerId` in the composite key is derived from `Customer.id`; `documentType` is the remaining part supplied by the application. `@MapsId("customerId")` references the Java property name inside `CustomerDocumentId`, not the column name.

For a simple one-to-one shared primary key, using `@Id` + `@MapsId` without a value is sufficient. There is no need to create an `@EmbeddedId` if the child only has a single ID component matching the parent.

## 12. Comparing @MapsId and @PrimaryKeyJoinColumn

Both annotations can appear in one-to-one mappings with linked primary keys, but they emphasize different things:

- **@MapsId** expresses derived identity: the entity's ID is derived from the association. This is the clear way when the child uses the parent's key.
- **@PrimaryKeyJoinColumn** describes that the current entity's PK column is used as the join column to the related entity, commonly seen in one-to-one or inheritance mappings.
- For a model where the child ID is the parent ID, `@MapsId` directly expresses the relationship between the ID and the association, while helping the provider know how to synchronize the key.

Do not arbitrarily combine both annotations on the same mapping. Choose the appropriate representation and check the actual DDL/schema.

## 13. Database Constraints and Consistency

A shared primary key creates important constraints:

1. `customer_profiles.customer_id` must be `NOT NULL`.
2. `customer_profiles.customer_id` must be `PRIMARY KEY`.
3. `customer_profiles.customer_id` must be a `FOREIGN KEY` to `customers.id`.
4. The data types of both columns must be compatible.
5. There is no need to add a separate `UNIQUE` constraint on `customer_id` because a primary key is already unique.

A migration can declare:

```sql
CREATE TABLE customers (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(160) NOT NULL
);

CREATE TABLE customer_profiles (
    customer_id BIGINT PRIMARY KEY,
    display_name VARCHAR(120),
    bio VARCHAR(1000),
    CONSTRAINT fk_customer_profiles_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(id)
);
```

If your database uses a different identity syntax, adjust the migration for that database engine. Entity mappings do not replace foreign key or primary key constraints. Even though JPA checks associations in code, the database still needs constraints to protect data under concurrent instances, direct SQL, or application bugs.

## 14. Common Errors

| Symptom | Cause | Solution |
|---|---|---|
| Child inserted with null ID | Parent has no ID yet or association is unset | Persist parent, assign association, and use `@MapsId` |
| Duplicate key when creating two profiles | A profile already exists for that customer | Check PK/FK and handle duplicate business cases |
| Child has a different ID from parent | Manually assigning ID or using a separate generator | Remove `@GeneratedValue` and let `@MapsId` derive the ID |
| FK `customer_id` is not written | Only updated the inverse side on the parent | Assign the owning side `CustomerProfile.customer` |
| EntityNotFound / foreign key violation | Parent does not exist or was deleted | Check persist order and lifecycle |
| Every Customer unexpectedly requires a profile | Misunderstood optionality | `optional = false` on child only requires each child to have a parent |
| Lazy loading still emits queries | `OneToOne` `LAZY` is a hint, especially on inverse side | Check provider, enhancement, and fetch plan |
| Deleting parent fails with FK error | Missing cascade remove or wrong deletion order | Delete child first or configure appropriate cascade |
| Both entities have incompatible ID types | Inconsistent parent and child mappings | Use the same key type and check the schema |

## 15. Testing the Mapping

You should test the following behaviors on the same database type as your deployment environment:

- Create `Customer` and `CustomerProfile` in a single transaction; verify `profile.customer_id` equals `customers.id`.
- Read the profile using the customer ID and verify both entity IDs are equal.
- Attempt to create a second profile for the same customer; verify the database rejects it due to duplicate primary key.
- Create a profile referencing a non-existent customer; verify the foreign key protects data integrity.
- Delete the profile via `orphanRemoval`; verify the customer still remains.
- Delete the customer via JPA with appropriate cascade; verify the profile is deleted before or within the same transaction.
- Check the fetch plan to avoid redundant queries when loading parent/child.
- Test rollback if creating the profile fails mid-transaction.

Test skeleton example:

```java
@DataJpaTest
class CustomerProfileRepositoryTest {

    @Autowired
    CustomerRepository customerRepository;

    @Autowired
    CustomerProfileRepository profileRepository;

    @Test
    void profileUsesTheCustomerId() {
        Customer customer = new Customer("An");
        customer.attachProfile(
            new CustomerProfile("An Nguyen", "Profile")
        );

        Customer saved = customerRepository.saveAndFlush(customer);

        CustomerProfile profile =
            profileRepository.findById(saved.getId()).orElseThrow();

        assertThat(profile.getId()).isEqualTo(saved.getId());
    }
}
```

This is an illustrative skeleton; constructors, getters, and required fields must be added according to your actual entities. When using `IDENTITY`, `saveAndFlush` ensures the parent insert executes so the database assigns the ID before the test reads the profile.

9. Write an integration test on a real database using Testcontainers.
10. Explain when to use a shared primary key and when a child needs its own ID.

**Core principle:** `@MapsId` does not generate an independent ID for the child; it derives identity from the association to the parent. The child holds a single column that is both primary key and foreign key. Always set the owning side, ensure the parent has an ID before inserting the child, do not use `@GeneratedValue` for the child ID, and protect the relationship with PK/FK constraints in the database.
