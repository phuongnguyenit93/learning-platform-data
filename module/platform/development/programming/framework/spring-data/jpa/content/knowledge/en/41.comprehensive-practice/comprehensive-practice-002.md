# Designing Orders, Order Lines, and Aggregate Lifecycles

**Module:** Spring Data JPA  
**Knowledge Group:** Comprehensive Practice

## 1. Objectives

After this lesson, you will be able to:

- Identify the aggregate root and consistency boundaries for an ordering domain.
- Design `PurchaseOrder` and `OrderLine` with clear business invariants.
- Map a bidirectional one-to-many relationship with JPA and update the owning side properly.
- Choose `cascade` and `orphanRemoval` based on the actual lifecycle of child entities.
- Structure service transactions to create, modify, confirm, and cancel orders.
- Store snapshots of product names, SKUs, and prices at order placement time.
- Handle concurrent updates, locking, and database constraints.
- Test aggregate lifecycles, rollbacks, and relationships after reloading from the database.

## 2. Starting from Business Rules and Aggregate Boundaries

In Domain-Driven Design (DDD), an aggregate is a cluster of domain objects modified as a consistent unit. The aggregate root is the primary entry point through which external callers request state changes on that cluster.

For an ordering domain, a common model is:

- `PurchaseOrder` is the aggregate root.
- `OrderLine` is a child entity that only makes sense inside an order.
- `Customer` and `Product` are separate aggregates with independent lifecycles.

An order can have multiple order lines. Order lines cannot exist independently outside an order; they are added, quantity-adjusted, or removed through `PurchaseOrder`. Conversely, `Customer` and `Product` can be referenced by many orders and must not be deleted when an order is deleted.

Aggregate boundaries should protect invariants that must hold immediately after each transaction. For example:

- An order must belong to a valid customer.
- Only an order in the `DRAFT` state can have its lines modified.
- Each line's quantity must be greater than 0.
- An order can only become `SUBMITTED` if it has at least one order line.
- A line's selling price is the price captured at the time it was added to the order.
- The total amount must be calculated from the order lines and defined pricing rules.
- An order line cannot be moved to another order after creation.

Not every operation in the system belongs in the same aggregate. Do not embed all of `Product`, `Customer`, inventory, and payments into `PurchaseOrder` merely because they are business-related. Other aggregates should be referenced by ID and coordinated via services or domain events.

## 3. Proposed Data Model

A simple model can consist of:

**PurchaseOrder**

- `id`: primary key.
- `customer_id`: foreign key to the customer.
- `status`: order status.
- `created_at`: creation timestamp.
- `version`: version for concurrent update control.

**OrderLine**

- `id`: primary key.
- `order_id`: foreign key back to `PurchaseOrder`.
- `product_id`: selected product ID.
- `sku_snapshot`: product SKU at order time.
- `product_name_snapshot`: product name at order time.
- `unit_price`: unit price at order time.
- `quantity`: quantity.

`OrderLine` stores a snapshot of the name, SKU, and price so order history does not change when catalog information changes. `Product` remains a separate aggregate; the order line stores the reference ID and the snapshot data needed for invoices and history.

For money, use `BigDecimal` in Java and `DECIMAL`/`NUMERIC` in the database; do not use `double` or `float`. If the system supports multiple currencies, store the currency code and define rounding rules.

Condensed DDL example:

~~~sql
CREATE TABLE purchase_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    version BIGINT NOT NULL
);

CREATE TABLE order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    sku_snapshot VARCHAR(64) NOT NULL,
    product_name_snapshot VARCHAR(200) NOT NULL,
    unit_price DECIMAL(19, 2) NOT NULL,
    quantity INTEGER NOT NULL,
    CONSTRAINT fk_order_line_order
        FOREIGN KEY (order_id) REFERENCES purchase_order(id),
    CONSTRAINT uq_order_line_product
        UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_line_quantity
        CHECK (quantity > 0),
    CONSTRAINT ck_order_line_price
        CHECK (unit_price >= 0)
);
~~~

Identity syntax and timestamp types may need adjustment for PostgreSQL, MySQL, or your target database. If `product_id` has a foreign key to the `product` table, define a product deletion policy. Many systems that preserve order history archive/soft-delete products instead of hard-deleting them.

The unique constraint on `(order_id, product_id)` fits when business rules merge repeated additions of the same product into a single line. If the same product is allowed on multiple lines with different attributes such as size, color, or batch, the unique key must include those distinguishing attributes or the constraint must be dropped.

## 4. Designing States and Invariants

Do not allow controllers or mappers to assign `status` arbitrarily. Status should change through domain behaviors that enforce preconditions.

Example state machine:

~~~text
DRAFT
  |
  | submit
  v
SUBMITTED
  |
  | confirm payment
  v
PAID
  |
  | start fulfillment
  v
FULFILLING
  |
  | complete
  v
COMPLETED

DRAFT / SUBMITTED
  |
  | cancel (by policy)
  v
CANCELLED
~~~

This is a reference workflow. Actual policy must specify whether paid or shipped orders can be cancelled or must go through a refund/return workflow.

~~~java
public enum OrderStatus {
    DRAFT,
    SUBMITTED,
    PAID,
    FULFILLING,
    COMPLETED,
    CANCELLED
}
~~~

Behaviors on `PurchaseOrder` should check the current status before mutating state. For example, only `DRAFT` allows adding or removing lines; `submit` requires a non-empty list of lines.

## 5. Mapping PurchaseOrder as the Aggregate Root

~~~java
import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.Instant;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "purchase_order")
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false, updatable = false)
    private Customer customer;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Version
    private long version;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.ALL,
        orphanRemoval = true
    )
    @OrderBy("id ASC")
    private List<OrderLine> lines = new ArrayList<>();

    protected PurchaseOrder() {
    }

    private PurchaseOrder(Customer customer) {
        this.customer = Objects.requireNonNull(customer);
        this.status = OrderStatus.DRAFT;
        this.createdAt = Instant.now();
    }

    public static PurchaseOrder draft(Customer customer) {
        return new PurchaseOrder(customer);
    }

    public void addLine(ProductSnapshot product, int quantity) {
        ensureDraft();
        Objects.requireNonNull(product, "product must not be null");

        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be greater than 0");
        }

        OrderLine existing = lines.stream()
                .filter(line -> line.getProductId().equals(product.productId()))
                .findFirst()
                .orElse(null);

        if (existing != null) {
            existing.increaseQuantity(quantity);
            return;
        }

        OrderLine line = new OrderLine(product, quantity);
        line.attachTo(this);
        lines.add(line);
    }

    public void removeLine(Long productId) {
        ensureDraft();

        OrderLine line = lines.stream()
                .filter(item -> item.getProductId().equals(productId))
                .findFirst()
                .orElseThrow(() ->
                        new IllegalArgumentException("Product is not in the order"));

        lines.remove(line);
        line.detachFrom(this);
    }

    public void submit() {
        ensureDraft();

        if (lines.isEmpty()) {
            throw new IllegalStateException(
                    "Cannot submit an order with no lines");
        }

        status = OrderStatus.SUBMITTED;
    }

    public void cancel() {
        if (status != OrderStatus.DRAFT
                && status != OrderStatus.SUBMITTED) {
            throw new IllegalStateException(
                    "Current status does not allow cancelling the order");
        }

        status = OrderStatus.CANCELLED;
    }

    public BigDecimal getTotal() {
        return lines.stream()
                .map(OrderLine::getSubtotal)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);
    }

    public Long getId() {
        return id;
    }

    public Customer getCustomer() {
        return customer;
    }

    public OrderStatus getStatus() {
        return status;
    }

    public long getVersion() {
        return version;
    }

    private void ensureDraft() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException(
                    "Only DRAFT orders can modify order lines");
        }
    }
}
~~~

`PurchaseOrder` keeps its collection private and exposes `addLine`/`removeLine` behaviors. External code cannot arbitrarily call `lines.add` or replace the collection. This ensures every mutation goes through invariant checks.

`getLines` returns an unmodifiable copy so external code cannot mutate the internal collection. Mappers can read this list to build DTOs.

In this example, adding the same `productId` increases the quantity on the existing line. If product variants need to be distinguished, `ProductSnapshot` and the line lookup rule must include `variantId` or the corresponding variant SKU. If price or tax can change between additions, decide whether to merge lines or create separate lines based on pricing policy.

## 6. Designing ProductSnapshot

An order must retain product price and name information as of the time it was placed. Do not recalculate historical orders using the current price on `Product`.

~~~java
import java.math.BigDecimal;

public record ProductSnapshot(
        Long productId,
        String sku,
        String name,
        BigDecimal unitPrice,
        String currency
) {
    public ProductSnapshot {
        if (productId == null) {
            throw new IllegalArgumentException("productId must not be null");
        }
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("sku must not be blank");
        }
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("name must not be blank");
        }
        if (unitPrice == null || unitPrice.signum() < 0) {
            throw new IllegalArgumentException("unitPrice is invalid");
        }
        if (currency == null || currency.isBlank()) {
            throw new IllegalArgumentException("currency must not be blank");
        }
    }
}
~~~

`ProductSnapshot` is an immutable value object. It is not a JPA entity and has no independent lifecycle. When creating an `OrderLine`, snapshot values are copied into the line's columns.

If products have promotions, taxes, discounts, or multiple currencies, specify clearly which price is stored: list price, actual selling price, discount amount, tax, and line total. Any subsequent invoice recalculation must rely on the policies and data locked in at order placement time.

## 7. Mapping OrderLine as a Child Entity

~~~java
import jakarta.persistence.*;
import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(
    name = "order_line",
    uniqueConstraints = @UniqueConstraint(
        name = "uq_order_line_product",
        columnNames = {"order_id", "product_id"}
    )
)
public class OrderLine {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "order_id", nullable = false)
    private PurchaseOrder order;

    @Column(name = "product_id", nullable = false, updatable = false)
    private Long productId;

    @Column(name = "sku_snapshot", nullable = false, length = 64)
    private String skuSnapshot;

    @Column(name = "product_name_snapshot", nullable = false, length = 200)
    private String productNameSnapshot;

    @Column(name = "unit_price", nullable = false, precision = 19, scale = 2)
    private BigDecimal unitPrice;

    @Column(nullable = false)
    private int quantity;

    @Column(nullable = false, length = 3)
    private String currency;

    protected OrderLine() {
    }

    OrderLine(ProductSnapshot product, int quantity) {
        this.productId = product.productId();
        this.skuSnapshot = product.sku();
        this.productNameSnapshot = product.name();
        this.unitPrice = product.unitPrice();
        this.currency = product.currency();
        setQuantity(quantity);
    }

    void attachTo(PurchaseOrder order) {
        this.order = Objects.requireNonNull(order);
    }

    void detachFrom(PurchaseOrder order) {
        if (this.order != order) {
            throw new IllegalArgumentException("Order line does not belong to this order");
        }
        this.order = null;
    }

    void increaseQuantity(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be greater than 0");
        }
        this.quantity = Math.addExact(this.quantity, amount);
    }

    private void setQuantity(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be greater than 0");
        }
        this.quantity = quantity;
    }

    public BigDecimal getSubtotal() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }

    public Long getProductId() {
        return productId;
    }

    public String getSkuSnapshot() {
        return skuSnapshot;
    }

    public String getProductNameSnapshot() {
        return productNameSnapshot;
    }

    public BigDecimal getUnitPrice() {
        return unitPrice;
    }

    public int getQuantity() {
        return quantity;
    }

    public String getCurrency() {
        return currency;
    }
}
~~~

`OrderLine` is a child entity because it belongs to a `PurchaseOrder` and has no independent business operations outside the aggregate. Do not expose public setters for `order`, `quantity`, `productId`, or snapshot prices. All changes must go through `PurchaseOrder`.

In this example, `productId` is the scalar ID of the separate `Product` aggregate. This avoids loading and managing the entire `Product` graph in every order. If you want a foreign key to the `product` table, you can create a database constraint while still keeping the domain reference by ID; an archive policy is needed to preserve order history.

## 8. Owning Side and Bidirectional Relationships

In the mapping above:

- `PurchaseOrder.lines` uses `mappedBy = "order"`, so it is the inverse side.
- `OrderLine.order` has `@ManyToOne` and `@JoinColumn` `order_id`, so it is the owning side.
- The database writes the foreign key based on the owning side.

Therefore, merely calling `lines.add(line)` is not enough. You must assign `line.order = this`. The `addLine` helper performs both operations:

~~~java
OrderLine line = new OrderLine(product, quantity);
line.attachTo(this);
lines.add(line);
~~~

When removing a line, the `removeLine` helper removes it from the collection and updates the back reference. With `orphanRemoval = true`, a child entity removed from the collection is marked for deletion on flush. Test the SQL behavior of your provider, especially when the FK is `NOT NULL`.

Do not allow an `OrderLine` to be attached to two `PurchaseOrder`s simultaneously. A line has only one parent. If you need to move a line, that requires an explicit business operation considering status, foreign keys, and audit trails; typically, lines are not moved between created orders.

## 9. Lifecycle-Driven Cascade and orphanRemoval

The root mapping uses:

~~~java
@OneToMany(
    mappedBy = "order",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<OrderLine> lines = new ArrayList<>();
~~~

This choice means:

- Persisting `PurchaseOrder` cascades persist to new `OrderLine`s.
- Merging the root can cascade merge to associated lines.
- Removing `PurchaseOrder` cascades remove to `OrderLine`s.
- Removing an `OrderLine` from the managed collection triggers orphan removal.

This fits because `OrderLine` shares the lifecycle of `PurchaseOrder`.

Do not cascade `ALL` from `PurchaseOrder` to `Product` or `Customer` if they are independent aggregates shared across many orders. Deleting an order must not delete customers or products.

`orphanRemoval` is not a general deletion mechanism for every one-to-many relationship. Use it only when the child entity's lifecycle is truly owned by the root and it is not shared. If a related record can be referenced by multiple roots, do not use `orphanRemoval`.

## 10. Repositories Focused on the Aggregate Root

~~~java
import jakarta.persistence.LockModeType;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.Optional;

public interface PurchaseOrderRepository
        extends JpaRepository<PurchaseOrder, Long> {

    @EntityGraph(attributePaths = "lines")
    Optional<PurchaseOrder> findWithLinesById(Long id);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("""
        select o
        from PurchaseOrder o
        where o.id = :id
        """)
    Optional<PurchaseOrder> findByIdForUpdate(@Param("id") Long id);
}
~~~

The aggregate root's repository is the primary persistence gateway for `PurchaseOrder` and its `OrderLine`s. There is no need for a public `OrderLineRepository` if all line modifications must go through the root. Specialized queries can be created for reporting or reading data, but controllers must not arbitrarily write child entities outside the aggregate.

`EntityGraph` on the detail read method requests loading `lines` together with the order. For large collections, do not use collection fetch joins directly in paginated queries; paginate root IDs first and then load the collection by the ID list.

## 11. Service Transactions Orchestrating Use Cases

The service performs operations requiring repositories of other aggregates, builds snapshots, and then mutates `PurchaseOrder` through domain behaviors.

Commands:

~~~java
import java.util.List;

public record CreateOrderCommand(
        Long customerId,
        List<OrderItemCommand> items
) {
}

public record OrderItemCommand(
        Long productId,
        int quantity
) {
}
~~~

Illustrative service:

~~~java
@Service
@RequiredArgsConstructor
public class OrderApplicationService {

    private final PurchaseOrderRepository orderRepository;
    private final CustomerRepository customerRepository;
    private final ProductRepository productRepository;

    @Transactional
    public Long createDraft(CreateOrderCommand command) {
        if (command.items() == null || command.items().isEmpty()) {
            throw new IllegalArgumentException("Order must have at least one line");
        }

        Customer customer = customerRepository.findById(command.customerId())
                .orElseThrow(() ->
                        new EntityNotFoundException("Customer not found"));

        List<Long> productIds = command.items().stream()
                .map(OrderItemCommand::productId)
                .distinct()
                .toList();

        Map<Long, Product> products = productRepository.findAllById(productIds)
                .stream()
                .collect(Collectors.toMap(Product::getId, Function.identity()));

        if (products.size() != productIds.size()) {
            throw new EntityNotFoundException("One or more products do not exist");
        }

        PurchaseOrder order = PurchaseOrder.draft(customer);

        for (OrderItemCommand item : command.items()) {
            Product product = products.get(item.productId());

            ProductSnapshot snapshot = new ProductSnapshot(
                    product.getId(),
                    product.getSku(),
                    product.getName(),
                    product.getCurrentPrice(),
                    product.getCurrency()
            );

            order.addLine(snapshot, item.quantity());
        }

        return orderRepository.save(order).getId();
    }
}
~~~

This example combines the domain components and repositories of a Spring Boot application; corresponding `Customer`/`Product` entities, repositories, getters, and dependency injection are required. The service imports include Spring `@Service`, `@Transactional`, `@RequiredArgsConstructor`, `EntityNotFoundException`, `Map`, `List`, `Collectors`, and `Function`.

The `createDraft` method:

1. Checks that the command has order lines.
2. Loads the existing `Customer`.
3. Batch-loads the `Product`s, avoiding one query per line.
4. Verifies every requested `productId` was found.
5. Creates a snapshot for each product.
6. Builds the `PurchaseOrder` and adds lines via the `addLine` domain behavior.
7. Saves the root; cascade persist saves the `OrderLine`s.

The entire operation runs in a single transaction. If a `Product` does not exist or a line has an invalid quantity, the exception rolls back the transaction, leaving no partial order behind.

If price and stock must be validated concurrently with order creation, define a locking policy or re-verify the data at submit time. Batch-loading `Product`s reduces query count but does not itself lock prices or inventory.

## 12. Updating a Managed Aggregate

Example adding a product to a `DRAFT` order:

~~~java
@Transactional
public void addItem(Long orderId, Long productId, int quantity) {
    PurchaseOrder order = orderRepository.findById(orderId)
            .orElseThrow(() ->
                    new EntityNotFoundException("Order not found"));

    Product product = productRepository.findById(productId)
            .orElseThrow(() ->
                    new EntityNotFoundException("Product not found"));

    ProductSnapshot snapshot = new ProductSnapshot(
            product.getId(),
            product.getSku(),
            product.getName(),
            product.getCurrentPrice(),
            product.getCurrency()
    );

    order.addLine(snapshot, quantity);
}
~~~

`PurchaseOrder` is loaded inside the transaction and is therefore a managed entity. When `addLine` adds a new `OrderLine` to the collection, `PERSIST` cascade saves the child on flush. When incrementing the quantity of a managed `OrderLine`, dirty checking detects the change and issues an `UPDATE`.

There is no need to call `orderRepository.save(order)` again for an entity already managed in the same persistence context. Calling `save` may still work, but it is unnecessary for dirty checking to take effect.

If the order is not in `DRAFT`, `addLine` throws an exception and the transaction does not commit the change. Do not let a controller accept an arbitrary `OrderLine` and assign `orderId` directly; that bypasses aggregate invariants.

## 13. Submit and State Transitions

A submit use case:

~~~java
@Transactional
public void submit(Long orderId) {
    PurchaseOrder order = orderRepository.findById(orderId)
            .orElseThrow(() ->
                    new EntityNotFoundException("Order not found"));

    order.submit();
}
~~~

The `submit` domain method verifies:

- The current status is `DRAFT`.
- There is at least one `OrderLine`.
- The lines have valid quantities.
- Other business preconditions such as customer, shipping address, inventory, or credit limit have been verified per the workflow.

Do not let the controller set `status = SUBMITTED` directly. When all status changes go through domain behaviors, state transition rules remain centralized and easy to test.

If inventory reservation or payment belongs to another aggregate/service, do not hold a database transaction open while waiting on slow network calls. You can commit the order in a pending state, publish an event after commit, and use an orchestration/saga workflow to coordinate steps. When events must not be lost after commit, consider the Transactional Outbox pattern.

## 14. Calculating Totals and Storing Snapshots

The order total in the example is calculated as the sum of line subtotals:

~~~java
public BigDecimal getTotal() {
    return lines.stream()
            .map(OrderLine::getSubtotal)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
}
~~~

Subtotal:

~~~java
public BigDecimal getSubtotal() {
    return unitPrice.multiply(BigDecimal.valueOf(quantity));
}
~~~

Do not recalculate historical prices using `Product.currentPrice`. Product prices can change after an order is created. Snapshots ensure older orders still reflect the agreement at the time of placement.

If you need to store `total` for fast querying or sorting, treat it as denormalized derived data. Every addition, removal, or quantity change must update the total within the same aggregate transaction, backed by tests reconciling `total` with the sum of the lines. Do not maintain two sources of truth without clear synchronization rules.

For currencies with different scale rules, specify the rounding mode and when rounding occurs. For example, unit prices or line subtotals may be rounded depending on accounting rules. Do not call `BigDecimal.setScale` with an unclear implicit default.

## 15. Optimistic Locking and Concurrent Updates

Two requests might load the same `DRAFT` order simultaneously and both add lines or change quantities. Without concurrency control, one update can overwrite the other or break invariants.

`@Version` can be placed on `PurchaseOrder`:

~~~java
@Version
private long version;
~~~

When an `UPDATE` has an outdated version that no longer matches, the provider may throw `OptimisticLockException`. The application should return an appropriate conflict error or instruct the client to reload and retry per business rules.

Do not assume that changes made solely to a child collection always increment the root's version in the same way across every mapping/provider. In a bidirectional relationship with `mappedBy`, mutating the collection might not produce an `UPDATE` on the root table. If an invariant requires serializing line additions/removals, choose and test an explicit mechanism:

- Use `EntityManager.lock(root, LockModeType.OPTIMISTIC_FORCE_INCREMENT)` to require incrementing the root version within the transaction.
- Use `PESSIMISTIC_WRITE` to lock the root row while modifying the aggregate.
- Use unique/check constraints so the database enforces expressible invariants.
- Handle `OptimisticLockException` and perform bounded retries only when permitted by business rules.

Example of pessimistically locking the root:

~~~java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select o from PurchaseOrder o where o.id = :id")
Optional<PurchaseOrder> findByIdForUpdate(Long id);
~~~

Locks must be held within a transaction. Do not hold locks while waiting on external APIs or long-running tasks. Pessimistic locks can reduce conflicts but increase wait times and deadlock risk; measure and configure appropriate timeouts.

## 16. Idempotency When Creating Orders

A client might retry an order creation request due to a timeout even though the server already committed. Without an idempotency mechanism, a retry can create two identical orders.

You can accept an idempotency key from an authenticated client and store a request key record with an appropriate unique constraint, such as per customer or tenant. Within the same transaction:

1. Check whether the key has already been processed.
2. If so, return the previously created order result.
3. If not, create the aggregate and save the result associated with the key.
4. The unique constraint prevents two concurrent requests from processing the same key simultaneously.

Idempotency keys need a defined scope, retention period, and rules for handling the same key with a different payload. Do not treat a client-supplied key as proof of authentication or authorization.

## 17. Removing Order Lines and Deleting Orders

While an order is `DRAFT`, `removeLine` can delete a line. With `orphanRemoval = true`, Hibernate deletes the child entity on flush after the line is removed from the collection.

Deleting an entire order is a separate business decision. Once an order is submitted, paid, or shipped, it generally should not be hard-deleted because of audit, invoicing, and history requirements. Instead, transition its status or run a cancellation/refund workflow.

If a `DRAFT` order can be hard-deleted, cascading `REMOVE` from the root to `OrderLine` is appropriate because lines belong to the order's lifecycle. Do not cascade `REMOVE` to `Customer` or `Product`.

## 18. Reading Aggregates and DTO Queries

Not every screen needs to load the full aggregate. Order lists typically only need order number, date, status, and total; use a DTO projection to avoid loading every `OrderLine`.

A detail screen can load the root together with `lines` using `EntityGraph`:

~~~java
@EntityGraph(attributePaths = "lines")
Optional<PurchaseOrder> findWithLinesById(Long id);
~~~

Then the service maps to a DTO inside the transaction:

~~~java
@Transactional(readOnly = true)
public OrderDetailDto getDetail(Long id) {
    PurchaseOrder order = orderRepository.findWithLinesById(id)
            .orElseThrow(() ->
                    new EntityNotFoundException("Order not found"));

    return orderMapper.toDetailDto(order);
}
~~~

The mapper should only use data loaded in the fetch plan. Avoid passing entities directly to a JSON serializer, as serialization can access lazy associations outside the transaction, causing `LazyInitializationException` or N+1 queries.

Do not paginate directly over a `JOIN FETCH` of a large collection. Paginate order IDs first, then query details for the IDs on that page and restore the original order.

## 19. Testing the Aggregate and Its Lifecycle

You should have integration tests using Hibernate and an appropriate database to verify mappings, cascades, orphan removal, constraints, and transactions.

Important test cases:

1. Creating a `DRAFT` order with two lines and confirming both root and children are saved.
2. Reading the order back from the database and verifying each line has the right `order_id`.
3. Adding the same `productId` a second time and verifying quantity is summed according to the rules.
4. Removing a line in `DRAFT` and verifying the child is deleted on flush.
5. Submitting an empty order must fail.
6. Adding a line after submitting must fail.
7. Zero or negative quantities must be rejected.
8. A non-existent `Product` must roll back the order creation transaction.
9. A failure at the final step must not leave a partial root or child behind.
10. Two concurrent update requests are handled according to the chosen optimistic/pessimistic locking strategy.

Example test for creating the aggregate:

~~~java
@Test
void savesOrderAndItsLinesThroughAggregateRoot() {
    Customer customer = customerRepository.saveAndFlush(
            new Customer("An"));

    PurchaseOrder order = PurchaseOrder.draft(customer);

    ProductSnapshot first = new ProductSnapshot(
            100L, "SKU-100", "Keyboard",
            new BigDecimal("850000.00"), "VND");
    ProductSnapshot second = new ProductSnapshot(
            200L, "SKU-200", "Mouse",
            new BigDecimal("250000.00"), "VND");

    order.addLine(first, 2);
    order.addLine(second, 1);
    order.submit();

    PurchaseOrder saved = orderRepository.saveAndFlush(order);

    entityManager.clear();

    PurchaseOrder reloaded = orderRepository.findWithLinesById(saved.getId())
            .orElseThrow();

    assertEquals(OrderStatus.SUBMITTED, reloaded.getStatus());
    assertEquals(2, reloaded.getLines().size());
    assertEquals(new BigDecimal("1950000.00"), reloaded.getTotal());
}
~~~

This test requires configuring `EntityManager`, repositories, and the corresponding database. The total amount in the example is 2 x 850,000 + 1 x 250,000 = 1,950,000 VND.

For testing orphan removal, call `removeLine` inside a transaction, flush, clear the persistence context, and query again to confirm the line is gone. Do not only assert against the in-memory Java collection; verify the database state.

If a test method runs inside a transaction managed by `@DataJpaTest`, the test transaction typically rolls back at the end. That is convenient for repository tests, but if you need to verify real commits of an application service, design dedicated test boundaries and read data after the service transaction has completed.

## 20. Common Design Pitfalls

### 20.1. Allowing Controllers to Modify Collections Directly

Controllers accepting entities or calling setters on collections bypass invariants. Expose only domain behaviors such as `addLine`, `removeLine`, and `submit`.

### 20.2. Cascading ALL to Product or Customer

These entities have independent lifecycles and are referenced by many orders. `CascadeType.REMOVE` could delete shared data. Only cascade to child entities that truly belong to the aggregate.

### 20.3. Forgetting to Update the Owning Side

Adding only to `PurchaseOrder.lines` without setting `OrderLine.order` can prevent `order_id` from being written properly. Helpers must update both sides.

### 20.4. Using orphanRemoval for Shared Entities

`orphanRemoval` is only appropriate for private children of the root. Do not use it if a record can be referenced by multiple aggregates.

### 20.5. Using Current Prices to Display Old Orders

Product prices can change. Capture price snapshots and required information as soon as the order line is created.

### 20.6. Putting the Entire System into One Aggregate

An oversized aggregate forces every transaction to load and lock too much data. Keep `Customer`, `Product`, `Inventory`, and `Payment` within separate boundaries; coordinate via IDs, services, and events.

### 20.7. Ignoring Concurrent Updates

A quantity check in Java may be insufficient when multiple requests modify an order at once. Use version, locks, or constraints according to the invariants being protected.

### 20.8. Deleting Completed Orders

Hard deletion destroys audit trails and history. Use statuses, cancellation workflows, or archiving per business policy.

### 20.9. Creating a Separate Repository to Write OrderLines Everywhere

This allows code outside the aggregate to modify children without checking root state. Only open a direct write path if there is a specially designed and well-guarded use case.

## 21. Implementation Checklist

- [ ] `PurchaseOrder` is the aggregate root and the primary write gateway.
- [ ] `OrderLine` can only be modified through `PurchaseOrder`.
- [ ] `Customer` and `Product` are referenced by entity/ID and necessary snapshots.
- [ ] Invariants for status, quantity, price, and lines are enforced in domain methods.
- [ ] The owning side `OrderLine.order` is updated alongside the inverse collection.
- [ ] Cascade applies only to child entities belonging to the root's lifecycle.
- [ ] `orphanRemoval` is used only for unshared children.
- [ ] Price, name, and currency snapshots are saved at order placement time.
- [ ] Service transactions cover a single aggregate creation/modification use case.
- [ ] A concurrency strategy suitable for concurrent operations is in place.
- [ ] The database enforces FK, unique, and check constraints for appropriate invariants.
- [ ] APIs return DTOs rather than uncontrolled entity graphs.
- [ ] Tests cover persist, update, remove, submit, rollback, and concurrency.
- [ ] Idempotency is implemented for order creation requests that require safe retries.

## 22. Conclusion

Good order design starts with aggregate boundaries: `PurchaseOrder` manages the lifecycle and invariants of `OrderLine`, while `Customer` and `Product` remain independent aggregates referenced by ID and snapshot data. JPA mappings must properly define the owning side, `cascade`, and `orphanRemoval`; service transactions orchestrate creating and modifying the root; and database constraints together with locking protect data under concurrent requests. When all line modifications flow through domain behaviors and are verified by integration tests, the order lifecycle becomes clear, consistent, and maintainable.
