# Explicit Registration via configureValidatingRepositoryEventListener

## Objective

Spring Data REST provides repository events so applications can hook into the create, save, link, and delete lifecycle of resources. One explicit way to register validation is to implement `RepositoryRestConfigurer` and override the `configureValidatingRepositoryEventListener(...)` callback.

This callback receives `ValidatingRepositoryEventListener`. An application can register one or more Spring `Validator` instances for each lifecycle event, for example:

- `beforeCreate`: validate data before creating a new resource.
- `beforeSave`: validate data before saving/updating a resource.
- `beforeLinkSave`: validate association changes before saving a link.

This approach places validation at the right point in the repository REST flow, even when requests go through endpoints automatically generated by Spring Data REST without a custom controller.

## 1. Where Do Repository Events Sit in the Request Flow?

Suppose the Person repository is exposed at `/api/people`. A POST request to create a Person goes through these high-level steps:

1. Spring Data REST identifies the collection resource and HTTP POST method.
2. The request body is converted into a Person domain object.
3. Pre-creation repository events are emitted.
4. `ValidatingRepositoryEventListener` invokes the validators registered for the corresponding event.
5. If there are no validation errors, Spring Data REST proceeds to save the entity through the repository.
6. Post-operation events are emitted and the HTTP response is produced.

For PUT/PATCH on an item, the update flow emits the pre-save event. Validators registered for `beforeSave` can verify the final state before the repository writes data.

This can be visualized as:

~~~text
HTTP POST / PUT / PATCH
          |
          v
Spring Data REST resource handler
          |
          v
Deserialize request -> domain object
          |
          v
Repository lifecycle event
          |
          v
ValidatingRepositoryEventListener
          |
          +----> Validators registered for event
          |
          +----> Errors?
                    |
             yes    |    no
              v     |     v
       Reject request| Repository save
       (4xx response)|       |
                     |       v
                     |   HTTP response
~~~

Validation here is part of the repository event flow. It is not controller validation with `@Valid @RequestBody`, although both can coexist in the same application.

## 2. RepositoryRestConfigurer and the Validator Registration Callback

`RepositoryRestConfigurer` is Spring Data REST's configuration point. You can implement this interface and override the callback:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.data.rest.core.config.RepositoryRestConfigurer;
import org.springframework.data.rest.core.event.ValidatingRepositoryEventListener;

@Configuration
public class RepositoryRestValidationConfig
        implements RepositoryRestConfigurer {

    private final PersonValidator personValidator;

    public RepositoryRestValidationConfig(
            PersonValidator personValidator) {
        this.personValidator = personValidator;
    }

    @Override
    public void configureValidatingRepositoryEventListener(
            ValidatingRepositoryEventListener validatingListener) {

        validatingListener.addValidator("beforeCreate", personValidator);
        validatingListener.addValidator("beforeSave", personValidator);
    }
}
~~~

Key points to note:

- `configureValidatingRepositoryEventListener` is invoked by Spring Data REST when configuring the validating event listener.
- `addValidator(eventName, validator)` attaches a validator to a lifecycle event name.
- A single validator can be registered for multiple events if the same rules apply.
- This callback is the registration point; data validation logic should reside in separate validator classes for readability and reuse.

In the example, the same `PersonValidator` is called before create and before save. If creation and update rules differ, create separate validators for each event or branch explicitly by state/use case.

## 3. Writing a Spring Validator

Spring `Validator` has two main methods:

- `supports(Class<?> clazz)`: indicates whether the validator handles the passed object type.
- `validate(Object target, Errors errors)`: inspects the object and records errors into `Errors`.

Example validator for Person:

~~~java
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.validation.Errors;
import org.springframework.validation.Validator;

@Component
public class PersonValidator implements Validator {

    @Override
    public boolean supports(Class<?> clazz) {
        return Person.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Person person = (Person) target;

        if (!StringUtils.hasText(person.getFirstName())) {
            errors.rejectValue(
                "firstName",
                "person.firstName.required",
                "First name is required"
            );
        }

        if (!StringUtils.hasText(person.getLastName())) {
            errors.rejectValue(
                "lastName",
                "person.lastName.required",
                "Last name is required"
            );
        }

        if (person.getEmail() != null
                && !person.getEmail().contains("@")) {
            errors.rejectValue(
                "email",
                "person.email.invalid",
                "Email address is invalid"
            );
        }
    }
}
~~~

Explanation:

- `supports` ensures the validator only accepts the Person type.
- `StringUtils.hasText` checks that a string is non-null, non-empty, and not whitespace-only.
- `rejectValue` records an error attached to a field.
- Error codes such as `person.firstName.required` can be used to resolve messages from a message bundle.
- A validator does not persist entities itself; it only reports errors or confirms data is valid.

If a validator is shared across multiple domain types, verify types with `supports` and avoid unsafe casts. Each validator should have a clear scope of responsibility.

## 4. Registering per Lifecycle Event

The event name is the string that `ValidatingRepositoryEventListener` uses to select validators. Common pre-operation events:

| Event name | Timing | Example use case |
|---|---|---|
| `beforeCreate` | Before creating a new resource | POST to a collection |
| `beforeSave` | Before saving a resource | PUT/PATCH or save operation |
| `beforeLinkSave` | Before saving a link change | Assigning or changing an association |

Example registering different validators:

~~~java
@Override
public void configureValidatingRepositoryEventListener(
        ValidatingRepositoryEventListener listener) {

    listener.addValidator("beforeCreate", personCreateValidator);
    listener.addValidator("beforeSave", personUpdateValidator);
    listener.addValidator("beforeLinkSave", personLinkValidator);
}
~~~

Choose events according to the rule's purpose:

- Checking required fields on creation: `beforeCreate`.
- Checking valid state before updating: `beforeSave`.
- Checking whether an association is allowed to be attached to an entity: `beforeLinkSave`.

Do not register one validator on every event just to be "safe." A validator must accept the right target type and check the right state at the time of the event. For operations with different semantics, separating validators prevents applying the wrong rules.

The event name must exactly match the event key supported by Spring Data REST. If misspelled, the validator will not run at the desired lifecycle stage. Check the event names in the API/version of Spring Data REST you are using.

## 5. How Are Validation Errors Reflected in HTTP?

If a validator adds errors to `Errors`, Spring Data REST halts the write operation and returns a validation error to the client. A common response is `400 Bad Request`, with a representation describing field/global errors depending on version and configuration.

Example client request:

~~~http
POST /api/people
Content-Type: application/json
Accept: application/hal+json

{
  "firstName": "",
  "lastName": "Nguyen",
  "email": "invalid-email"
}
~~~

Because `firstName` is empty and email is invalid, the validator adds two errors. The repository should not proceed to save the entity when these validation errors are detected.

The error response may contain details similar to:

~~~json
{
  "errors": [
    {
      "entity": "Person",
      "property": "firstName",
      "message": "First name is required"
    },
    {
      "entity": "Person",
      "property": "email",
      "message": "Email address is invalid"
    }
  ]
}
~~~

This is an illustrative example of error structure; actual field names, messages, media types, and response shape depend on the Spring Data REST version, exception handlers, and application configuration.

If validation succeeds, processing proceeds to save the entity and returns a success response matching the operation, such as 201 Created for a POST creating a resource.

## 6. Distinguishing Repository Event Validation from Bean Validation

There are multiple validation layers in a Spring application:

| Mechanism | Where Is It Triggered? | When to Use? |
|---|---|---|
| Spring `Validator` registered via repository events | In the Spring Data REST repository lifecycle | Rules that must run when a resource is created/saved/linked via repository REST |
| Bean Validation (`@NotNull`, `@NotBlank`, `@Email`) | Through a Bean Validation provider and framework integration | Declarative constraints directly on DTO/domain properties |
| Controller validation (`@Valid`) | When Spring MVC binds and validates controller arguments | Custom controller endpoints receiving request DTOs |
| Service/domain validation | In application services or domain methods | Business rules that must apply across multiple interfaces/APIs |

These mechanisms can complement each other. For example, Bean Validation checks email formatting, while a repository event validator checks rules that depend on entity state or existing data.

Do not place all rules in a single layer if the same business operation can be invoked via REST, batch jobs, message consumers, or other services. Critical domain rules must be enforced at the service/domain boundary so they are not bypassed when requests do not go through Spring Data REST.

## 7. Validation Does Not Replace Authorization

A validator answers the question: **is the data valid to proceed with the operation?** Authorization answers the question: **is the current user allowed to perform this operation?**

Examples:

- Is the email properly formatted? This is validation.
- Does the user have permission to change this Person's email? This is authorization.
- Does the current state allow transitioning to APPROVED? This is a business rule/state transition.
- Does the user belong to the tenant owning the Person? This is typically resource-based authorization.

Do not use a validator as the sole access control mechanism. A validator may lack full context about the principal, tenant, policies, or resource ownership. Enforce permissions using Spring Security and appropriate application service/domain policies.

## 8. Structuring Validator Registration for Maintainability

A common layout:

~~~text
config/
  RepositoryRestValidationConfig.java

validation/
  PersonValidator.java
  PersonCreateValidator.java
  PersonUpdateValidator.java
  PersonLinkValidator.java

repository/
  PersonRepository.java

domain/
  Person.java
~~~

Conventions:

- Place validators in a component-scanned package.
- Register explicitly via the configuration callback.
- Use constructor injection instead of instantiating validators with `new` if the validator has dependencies.
- Keep `supports` accurate for the domain type.
- Extract shared rules into a service/helper if multiple validators need them.
- Avoid side effects inside validators, such as saving data, sending emails, or calling external systems.
- Validators should be easy to unit-test independently.

Example of a validator needing a repository to check for duplicate emails:

~~~java
@Component
public class PersonCreateValidator implements Validator {

    private final PersonRepository repository;

    public PersonCreateValidator(PersonRepository repository) {
        this.repository = repository;
    }

    @Override
    public boolean supports(Class<?> clazz) {
        return Person.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Person person = (Person) target;

        if (person.getEmail() != null
                && repository.existsByEmail(person.getEmail())) {
            errors.rejectValue(
                "email",
                "person.email.duplicate",
                "Email address is already in use"
            );
        }
    }
}
~~~

When updating, duplicate checking must exclude the current entity itself. Therefore, a validator for `beforeSave` may need different logic than the creation validator. Avoid using a simple exists query that causes a Person to be flagged as duplicating its own email.

## 9. Verifying with Integration Tests

Test both paths: valid data is saved and invalid data is rejected.

Example with MockMvc:

~~~java
mockMvc.perform(
        post("/api/people")
            .contentType("application/json")
            .accept("application/hal+json")
            .content("""
                {
                  "firstName": "An",
                  "lastName": "Nguyen",
                  "email": "an@example.com"
                }
                """)
    )
    .andExpect(status().isCreated());
~~~

Testing invalid data:

~~~java
mockMvc.perform(
        post("/api/people")
            .contentType("application/json")
            .accept("application/hal+json")
            .content("""
                {
                  "firstName": "",
                  "lastName": "Nguyen",
                  "email": "invalid"
                }
                """)
    )
    .andExpect(status().isBadRequest());
~~~

In addition to HTTP integration tests, test the validator directly:

~~~java
PersonValidator validator = new PersonValidator();
Person person = new Person();
person.setFirstName("");
person.setLastName("Nguyen");

BeanPropertyBindingResult errors =
        new BeanPropertyBindingResult(person, "person");

validator.validate(person, errors);

assertThat(errors.hasErrors()).isTrue();
assertThat(errors.hasFieldErrors("firstName")).isTrue();
~~~

Constructor names, dependencies, and test configurations should be adapted to your project. Integration tests confirm the callback registered the validator on the right events; unit tests confirm validation logic for individual cases.

## 10. Common Issues When a Validator Does Not Run

If a request is not rejected despite invalid data, check:

1. Is the configuration class component-scanned by Spring and recognized by Spring Data REST?
2. Does the class properly implement `RepositoryRestConfigurer`?
3. Did it override the exact signature `configureValidatingRepositoryEventListener(ValidatingRepositoryEventListener)`?
4. Is the event key accurate, e.g., `beforeCreate` or `beforeSave`?
5. Is the validator registered for the exact event of the operation being tested?
6. Does `supports(clazz)` return true for the actual domain type?
7. Does the logic record errors through `Errors` rather than only logging a message?
8. Is the request actually hitting the Spring Data REST repository endpoint rather than a different custom controller?
9. Is there an exception handler configuration altering the error response?
10. Are there tests proving the validator runs on both create and update?

If the validator runs yet the request is still saved, check the registration and whether the validator actually adds errors to Errors. Simply logging an error or emitting a log message does not replace reporting errors via the validation mechanism expected by the listener.

## 11. Takeaways

- `configureValidatingRepositoryEventListener` is the `RepositoryRestConfigurer` callback for registering validators on repository lifecycle events.
- `ValidatingRepositoryEventListener.addValidator(eventName, validator)` attaches a Spring Validator to an event.
- `beforeCreate` is typically used for POST resource creation; `beforeSave` is used for save/update operations; `beforeLinkSave` is used for association changes.
- Spring `Validator` implements `supports` and `validate`, recording errors via `Errors`.
- Validation failures typically cause the operation to be rejected with 400 Bad Request; detailed responses depend on configuration/version.
- Repository event validation differs from controller `@Valid` and Bean Validation, though they can work together.
- Validation does not replace authorization or domain policies.
- Avoid side effects inside validators; keep validation logic easy to test and register it on the proper events.
