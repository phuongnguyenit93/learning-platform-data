# Creating Resources with POST and Defining Writable Properties in Spring Data REST

## Objectives

After this lesson, you will be able to create a repository resource using HTTP POST; understand how Spring Data REST converts a JSON request into a domain object; determine which properties clients are allowed to send; and protect server-managed fields such as ID, status, owner, or audit information.

## 1. Creating a resource with POST at the collection endpoint

For a repository exposed by Spring Data REST, the collection resource typically supports `POST` to create a new entity. For example, if `CustomerRepository` is exported under the path `/customers`, the client sends a request to the collection endpoint:

```http
POST /customers HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Accept: application/hal+json

{
  "name": "Ada Lovelace",
  "email": "ada@example.com"
}
```

Spring Data REST reads the body, converts the accepted properties into a `Customer`, and then invokes the repository's save mechanism. When creation succeeds, the response typically has status `201 Created`, a `Location` header pointing to the newly created resource, and the resource representation if the request/configuration asks to return a body.

Abbreviated response example:

```http
HTTP/1.1 201 Created
Location: http://localhost:8080/customers/42
Content-Type: application/hal+json
```

```json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "_links": {
    "self": { "href": "http://localhost:8080/customers/42" }
  }
}
```

`POST` to a collection creates a new resource. This should be distinguished from `PUT` or `PATCH` on an item resource, which are normally used to replace or update an existing resource. You should not send a client-chosen ID if IDs are generated by the database/server.

## 2. Content-Type and Accept in a resource creation request

The two headers serve different roles:

- `Content-Type` describes the format of the body the client sends. For plain JSON, use `application/json`.
- `Accept` describes the representation the client wants to receive back. If you need a response with HAL links, use `application/hal+json`.

Example:

```http
POST /customers
Content-Type: application/json
Accept: application/hal+json
```

The request body is JSON, while the response can be HAL JSON. If the client does not need hypermedia, it can request `Accept: application/json`, depending on Spring Data REST's media type configuration.

When a request has a `Content-Type` not supported by the endpoint, the server may return `415 Unsupported Media Type`. When the `Accept` value does not match any representation the server can provide, the server may return `406 Not Acceptable`.

## 3. How is a JSON request mapped to a domain object?

Spring Data REST uses Spring's HTTP message conversion mechanism and Jackson to deserialize the request body into the domain object corresponding to the repository. JSON properties can be assigned via a constructor/creator, setter, or field depending on how the domain class and Jackson are configured.

Simple entity example:

```java
@Entity
public class Customer {

    @Id
    @GeneratedValue
    private Long id;

    private String name;
    private String email;

    protected Customer() {
    }

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }

    public Long getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        this.email = email;
    }
}
```

The client can send:

```json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com"
}
```

Jackson maps the matching properties into `Customer`; Spring Data REST then saves the entity via the repository. Actual writability also depends on constructors, setter/field visibility, Jackson annotations, custom deserializers, message converters, and `ObjectMapper` configuration.

Therefore, you should not assume every field in an entity is writable simply because that field exists in the Java class. Nor should you assume that hiding a field in the client UI is enough to prevent a forged request from sending that field.

## 4. Determining which properties clients are allowed to write

Classify properties by data source and ownership responsibility before designing the request contract:

| Property group | Examples | Common policy |
| --- | --- | --- |
| User-entered data | `name`, `email`, `description` | Allow client to send, with validation |
| Server/database-generated data | `id`, `createdAt`, `version` | Server-managed; do not accept write values from client |
| Audit data | `createdBy`, `lastModifiedAt` | Populated from auditing/security context |
| Authorization or ownership data | `role`, `ownerId`, `tenantId` | Determined from authenticated identity or business rules |
| Business state | `approved`, `accountStatus`, `balance` | Changed only through permitted business operations |
| Input secrets | `password`, `inviteCode` | Accepted only when needed; never returned in response |

A Customer creation request might only allow `name` and `email`. The ID, creation timestamp, owner, and initial status are assigned by the server. This classification produces an explicit allowlist for each resource creation operation.

## 5. Controlling serialization and deserialization with Jackson

Jackson provides useful annotations to define how a property is read or written via JSON.

### @JsonProperty(access = READ_ONLY)

The property is included in output JSON but ignored when deserializing input JSON. This is a suitable choice for IDs, server-managed statuses, or auto-generated timestamps:

```java
import com.fasterxml.jackson.annotation.JsonProperty;

public class Customer {

    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private Long id;

    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private String accountStatus;

    // Other properties
}
```

If the client sends `id` or `accountStatus`, Jackson does not use those values to populate the object via the read-only properties. The server can still return these values in the response.

### @JsonProperty(access = WRITE_ONLY)

The property is accepted from input JSON but not serialized to output JSON. Use this for sensitive input data that the API needs to receive, such as an invite code or password:

```java
@JsonProperty(access = JsonProperty.Access.WRITE_ONLY)
private String inviteCode;
```

The server must still verify the invite code, handle it securely, and avoid storing secrets in an inappropriate form. `WRITE_ONLY` only controls JSON output; it does not validate values or encrypt data on its own.

### @JsonIgnore

`@JsonIgnore` excludes a property from JSON mapping according to Jackson configuration, usually meaning the property is neither read from requests nor included in responses:

```java
@JsonIgnore
private String internalNote;
```

Use this when a property does not belong in the API representation at all. If you need to expose a property in responses while forbidding client writes, consider `READ_ONLY` instead of `@JsonIgnore`.

Annotations need to be placed on the right logical property. For classes using getters/setters, constructor binding, or Lombok, verify which member Jackson detects the property from to avoid configuration not taking effect as intended.

## 6. Example: allowing only name and email

Suppose the server must generate the ID, account status, and creation timestamp itself. You can express the policy on the entity as follows:

```java
@Entity
public class Customer {

    @Id
    @GeneratedValue
    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private Long id;

    @NotBlank
    @Size(max = 120)
    private String name;

    @Email
    @NotBlank
    private String email;

    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private String accountStatus;

    @CreatedDate
    @JsonProperty(access = JsonProperty.Access.READ_ONLY)
    private Instant createdAt;

    protected Customer() {
    }

    // Appropriate constructor, getters, and setters
}
```

A valid request might look like:

```http
POST /customers
Content-Type: application/json
Accept: application/hal+json

{
  "name": "Ada Lovelace",
  "email": "ada@example.com"
}
```

A request attempting to set the ID and status itself:

```json
{
  "id": 999,
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "accountStatus": "ADMIN"
}
```

For properties marked `READ_ONLY`, Jackson ignores the input values for those properties. The server needs to assign `accountStatus` according to account creation rules, and the database/provider generates the ID.

The example above illustrates the design approach. To run in a real application, you must add imports, JPA auditing configuration if using `@CreatedDate`, constructors/setters, and the appropriate validation dependency for your Spring Boot version.

## 7. Validation and business rules before saving

Writable property control must go hand in hand with validation. Bean Validation annotations such as `@NotBlank`, `@Email`, `@Size`, `@Min`, and `@Max` describe data constraints. When Bean Validation is integrated into the application, requests violating constraints can be rejected before saving.

Some rules require business logic, for example:

- Is the email already in use?
- Does the current user have permission to create a customer belonging to the specified tenant?
- Is the invite code valid and still active?
- Is the initial status allowed to transition to the status requested by the client?

Do not let clients determine `ownerId`, `tenantId`, `role`, or sensitive statuses merely by sending extra JSON properties. Obtain user information from the security context and perform permission checks on the server.

Spring Data REST supports repository event handlers to apply logic around save time. For example, use `@HandleBeforeCreate` to assign server-managed information or check conditions before creation:

```java
@Component
@RepositoryEventHandler(Customer.class)
public class CustomerEventHandler {

    @HandleBeforeCreate
    public void beforeCreate(Customer customer) {
        // Assign initial status and check business rules
    }
}
```

The handler must be registered as a Spring bean. For complex or multi-step logic, consider moving business logic into a dedicated service and designing a custom controller/application service instead of stuffing all rules into an entity event handler.

## 8. Relationship properties and associations

An entity can contain relationships to other resources, for example a Customer belonging to an Address or an Order belonging to a Customer. Spring Data REST exposes associations through links and association resources.

When creating or updating relationships, clients typically reference the URI of the related resource according to the association endpoint contract. Do not assume that sending an arbitrary nested object will automatically create the entire entity graph in the desired way.

Define clearly:

- Which relationships are clients allowed to choose?
- Does the related resource exist and is it accessible?
- Does the current user have permission to link those two resources?
- Can the relationship be changed during this POST operation, or must it go through a separate association endpoint?

Associations may have specific media types or calling conventions. Check the links in HAL and endpoint documentation to know how to send URI references in the right format. Never trust a URI just because the client sent it; the server must still verify access permissions and the validity of the target resource.

## 9. Distinguishing field writability from endpoint exposure

Several annotations and configurations have similar names but control different layers:

- `@RepositoryRestResource(exported = false)` hides the entire repository from REST export.
- `@RestResource(exported = false)` hides a method or association resource.
- `@JsonProperty(access = READ_ONLY)` controls JSON deserialization/serialization of a property.
- `@JsonIgnore` excludes a property from JSON mapping.
- Spring Security decides who is allowed to call endpoints and perform operations.

Hiding a repository or method does not create a field-level write policy. Conversely, marking a property read-only does not protect an endpoint from unauthenticated users. You need to combine JSON mapping, validation, authorization, and business rules.

Spring Data REST projections primarily control read representations. Do not use a projection as an allowlist for properties that POST is allowed to write. Control input with Jackson/domain binding and appropriate validation instead.

## 10. How to test POST in practice

When implementing or debugging a resource creation endpoint, perform the following checks:

1. Identify the collection path from the HAL API root or `@RepositoryRestResource(path = "...")` configuration.
2. Send `POST` with `Content-Type: application/json` and the allowed fields.
3. Check the status code, `Location` header, and response `Content-Type`.
4. Read the item resource back using the URI in `Location` to verify the saved data.
5. Try sending an additional server-managed field such as `id` or `accountStatus`; confirm the server does not accept the client-supplied value.
6. Try sending invalid data to confirm validation works.
7. Try an unauthorized request or linking to an out-of-scope resource to confirm authorization is checked.

Example using curl:

```bash
curl -i -X POST http://localhost:8080/customers \
  -H "Content-Type: application/json" \
  -H "Accept: application/hal+json" \
  -d '{"name":"Ada Lovelace","email":"ada@example.com"}'
```

If the endpoint returns `400 Bad Request`, read the response to identify which field or validation failed. If it returns `403 Forbidden`, check authorization. If it returns `415 Unsupported Media Type`, check `Content-Type`. If it returns `404 Not Found`, verify the collection path and base path.

## Summary

- `POST` to a collection resource creates a new entity; a successful response typically returns `201 Created` and `Location`.
- `Content-Type` describes the uploaded body; `Accept` selects the response representation.
- JSON requests are mapped by Jackson into domain objects; writability depends on binding configuration and property annotations.
- `READ_ONLY` allows returning a property while ignoring client-sent values; `WRITE_ONLY` accepts input without returning the property; `@JsonIgnore` excludes the property from JSON mapping.
- ID, owner, tenant, role, status, and audit metadata should be managed by the server when they are the server's responsibility.
- Combine field policies with validation, authorization, and server-side association checks.
