# Restricting Filterable Properties with QuerydslBinderCustomizer

## Objectives

When a Querydsl-enabled repository is exported by Spring Data REST, clients can pass filter conditions via query parameters in the URL. For example, GET /people?firstName=An asks for Person entities with a matching firstName.

If bindings are not restricted, many persistent properties can become filter keys that clients are allowed to send. This is especially noteworthy for internal properties or properties hidden from JSON with @JsonIgnore: Jackson serialization rules are not a Querydsl filter allow-list.

QuerydslBinderCustomizer lets you specify exactly which properties are allowed to be filtered and how each value is converted into a Querydsl predicate. For public APIs or sensitive data, use an allow-list with excludeUnlistedProperties(true) combined with including(...), rather than merely excluding a few fields.

## 1. Querydsl filtering in Spring Data REST

Querydsl is a library for building type-safe queries via Predicate expressions. Spring Data provides QuerydslPredicateExecutor<T> so repositories can execute predicates:

~~~java
public interface PersonRepository
        extends JpaRepository<Person, Long>,
                QuerydslPredicateExecutor<Person> {
}
~~~

QuerydslPredicateExecutor provides operations such as:

- findAll(Predicate): finds entities matching the condition.
- findAll(Predicate, Pageable): finds matching entities with pagination.
- count(Predicate): counts matching entities.
- exists(Predicate): checks whether matching entities exist.

When a repository is exported by Spring Data REST, Querydsl can be used to filter the collection resource via query parameters. For example:

~~~http
GET /people?firstName=An&lastName=Nguyen
Accept: application/hal+json
~~~

The parameters are mapped into a predicate corresponding to conditions on the entity's properties. The repository executes the predicate, and Spring Data REST returns the collection representation according to the current configuration.

Querydsl filtering requires Querydsl support compatible with the store and Q-types generated by annotation processing. With Spring Data JPA, the Q-type is typically named something like QPerson and generated from the Person entity.

## 2. QuerydslBindings and default rules

QuerydslBindings is where bindings from request parameters to Querydsl expressions are configured. They can be configured for a specific property or by Java type.

Common default bindings:

- A single value on a simple property is usually compared with eq.
- A single value on a collection property can be mapped to contains.
- Multiple values for a simple property can be mapped to in.

Without changing configuration, excludeUnlistedProperties defaults to false. This means properties without explicit binding rules can still use default bindings based on their data types.

Consequently, calling only excluding(root.password) excludes the password field while leaving all other properties open to default bindings. That approach works for a small deny-list, but does not establish an explicit allow-list.

## 3. Allow-list: opening only selected properties

To permit filtering on only a selected set of properties:

1. Call bindings.excludeUnlistedProperties(true).
2. Call bindings.including(...) with the permitted Querydsl paths.
3. Specify custom bindings for the opened paths if you need to change how matching works.

Example entity:

~~~java
@Entity
public class Person {

    @Id
    @GeneratedValue
    private Long id;

    private String firstName;
    private String lastName;
    private String city;

    private String passwordHash;
    private String internalNote;
}
~~~

Repository using QuerydslBinderCustomizer:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository
        extends JpaRepository<Person, Long>,
                QuerydslPredicateExecutor<Person>,
                QuerydslBinderCustomizer<QPerson> {

    @Override
    default void customize(
            QuerydslBindings bindings,
            QPerson person) {

        bindings.excludeUnlistedProperties(true);

        bindings.including(
            person.firstName,
            person.lastName,
            person.city
        );

        bindings.bind(person.firstName)
            .first((path, value) -> path.containsIgnoreCase(value));

        bindings.bind(person.lastName)
            .first((path, value) -> path.containsIgnoreCase(value));

        bindings.bind(person.city)
            .first((path, value) -> path.equalsIgnoreCase(value));
    }
}
~~~

In this example:

- Clients can filter by firstName, lastName, and city.
- Other unlisted properties are excluded from the binding process.
- firstName and lastName use case-insensitive substring matching.
- city uses case-insensitive equality matching.

Valid requests can be:

~~~http
GET /people?firstName=an
GET /people?lastName=nguyen&city=Hanoi
~~~

Requests using fields not in the allow-list, such as passwordHash or internalNote, will not create bindings for those properties. Specific HTTP behavior for disallowed parameters depends on the version and request-handling layer; do not design clients assuming every disallowed parameter must return the exact same status code. What must be ensured is that excluded properties do not participate in the predicate.

## 4. Deny-list: excluding specific properties

If an internal API requires allowing most fields and only excluding a few, you can use excluding(...):

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository
        extends JpaRepository<Person, Long>,
                QuerydslPredicateExecutor<Person>,
                QuerydslBinderCustomizer<QPerson> {

    @Override
    default void customize(
            QuerydslBindings bindings,
            QPerson person) {

        bindings.excluding(
            person.passwordHash,
            person.internalNote
        );
    }
}
~~~

This prevents the two specified properties from being used as filter keys. Remaining properties can still receive default bindings.

| Configuration | Behavior | When to use |
|---|---|---|
| Default, no exclude | Eligible properties use default bindings | Only after auditing the scope of permitted fields |
| excluding(path...) | Excludes specific fields | Internal APIs with a stable deny-list |
| excludeUnlistedProperties(true) + including(path...) | Allows only listed fields | Public APIs, sensitive data, or when strict control is needed |

For important data, an allow-list is usually easier to govern because a newly added entity property will not automatically become a filter key.

## 5. Per-property and per-type bindings

There are two common ways to customize how Querydsl interprets values.

### 5.1. Binding by specific path

Use bindings.bind(root.property) when a field needs its own filtering rule:

~~~java
bindings.bind(person.firstName)
    .first((path, value) -> path.containsIgnoreCase(value));

bindings.bind(person.age)
    .first((path, value) -> path.goe(value));
~~~

For example:

- firstName=an uses contains-ignore-case.
- age=18 can be defined as age >= 18.

first(...) accepts a single value; if the client sends multiple values for the same parameter, this binding uses the first value. If business rules require handling all values, use all(...) with multi-value binding and build an appropriate predicate.

### 5.2. Binding by data type

You can apply a shared rule across all properties of the same type:

~~~java
bindings.bind(String.class)
    .first((StringPath path, String value) ->
        path.containsIgnoreCase(value));
~~~

Type-level binding reduces boilerplate when many String properties share the same rule. However, if using a strict allow-list, consider global type-level binding carefully: it can open shared handling across many paths of the same type. To keep scope clear, prefer declaring bindings by path and listing only permitted paths.

## 6. Nested properties and relationships

Querydsl paths can point to nested properties. For example, Person has an address:

~~~java
@Embeddable
public class Address {
    private String city;
    private String district;
}
~~~

~~~java
@Entity
public class Person {
    @Id
    private Long id;

    @Embedded
    private Address address;
}
~~~

The Q-type can represent nested paths, such as person.address.city. To allow filtering only by city:

~~~java
@Override
default void customize(
        QuerydslBindings bindings,
        QPerson person) {

    bindings.excludeUnlistedProperties(true);
    bindings.including(person.address.city);

    bindings.bind(person.address.city)
        .first((path, value) -> path.equalsIgnoreCase(value));
}
~~~

Do not open the entire nested object if the client only needs one child field. You can exclude a parent path to exclude all child paths; for instance, excluding address excludes both address.city and address.district. When using an allow-list, include only the exact nested paths required in including(...).

## 7. Using aliases for public filter names

QuerydslBindings also supports path aliases. Aliases prevent the API from having to expose Java property names directly:

~~~java
bindings.bind(person.firstName)
    .as("name")
    .first((path, value) -> path.containsIgnoreCase(value));
~~~

Clients can use the name parameter according to the configured alias:

~~~http
GET /people?name=An
~~~

When using aliases, keep parameter names consistent in API documentation and test that the original property name is not inadvertently left open by another binding. An alias is the public name of the filter; it does not change the field name in the entity or database schema.

## 8. Where is QuerydslBinderCustomizer applied?

You can implement QuerydslBinderCustomizer<QPerson> directly on the repository interface. Spring Data picks up this customizer when building bindings for the repository and uses it instead of the corresponding default bindings.

Common structure:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository
        extends JpaRepository<Person, Long>,
                QuerydslPredicateExecutor<Person>,
                QuerydslBinderCustomizer<QPerson> {

    @Override
    default void customize(
            QuerydslBindings bindings,
            QPerson root) {
        // allow-list and binding rules
    }
}
~~~

A customizer can also be specified on a @QuerydslPredicate(bindings = ...) parameter in a custom Spring MVC Controller. In that case, the customizer applies to that handler's predicate. For filtering integrated into a repository, placing the customizer on the repository itself keeps rules alongside the repository rather than tying them to individual controllers.

If the application has multiple repositories, do not assume an allow-list on Person automatically applies to Order or other domain types. Define and enforce the policy on each repository that has Querydsl filtering. You can use QuerydslBinderCustomizerDefaults to share common rules, but the per-domain-type allow-list still needs to be explicitly defined.

## 9. Security note: CVE-2026-41837

On 2026-06-09, Spring published advisory CVE-2026-41837 regarding Spring Data REST's Querydsl integration. The advisory states that the Querydsl integration accepts persistent property paths as filter keys from request parameters without considering Jackson customizations before passing them to Querydsl.

Affected Spring Data REST versions listed in the advisory:

| Branch | Affected versions |
|---|---|
| 5.0 | 5.0.0 to 5.0.5 |
| 4.5 | 4.5.0 to 4.5.11 |
| 4.4 | 4.4.0 to 4.4.14 |
| 4.3 | 4.3.0 to 4.3.16 |
| 3.7 | 3.7.19 and earlier |

Fixed versions published in the advisory:

| Fixed version | Release status in advisory |
|---|---|
| 5.0.6 | OSS |
| 5.0.5.1 | Enterprise Support Only |
| 4.5.12 | OSS |
| 4.5.11.1 | Enterprise Support Only |
| 4.4.15 | Enterprise Support Only |
| 4.3.17 | Enterprise Support Only |
| 3.7.20 | Enterprise Support Only |

Prefer upgrading to the fixed version for your branch. If upgrading immediately is not possible, the advisory provides mitigation guidance by implementing QuerydslBinderCustomizer on each affected repository and calling:

~~~java
bindings.excludeUnlistedProperties(true);
~~~

followed by declaring an allow-list of property paths genuinely permitted for filtering with bindings.including(...).

Mitigation example:

~~~java
@Override
default void customize(
        QuerydslBindings bindings,
        QPerson person) {

    bindings.excludeUnlistedProperties(true);

    bindings.including(
        person.firstName,
        person.lastName,
        person.city
    );
}
~~~

Do not rely on @JsonIgnore, projections, or hiding fields from responses to protect a filter API. Those mechanisms control the representation; the Querydsl allow-list is what controls which paths are permitted as query parameters. Likewise, do not only add excluding(password) if the requirement is to close off all unapproved filter paths.

## 10. Testing the allow-list

Test both allowed filters and blocked filters. The example below is an integration test skeleton; you must prepare fixtures, repository export configuration, and adjust statuses to your application version:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class PersonQuerydslBindingTests {

    @Autowired
    MockMvc mvc;

    @Test
    void allowsFilteringByFirstName() throws Exception {
        mvc.perform(get("/people")
                .param("firstName", "An")
                .accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk());
    }

    @Test
    void allowsFilteringByCity() throws Exception {
        mvc.perform(get("/people")
                .param("city", "Hanoi")
                .accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk());
    }

    @Test
    void doesNotBindPasswordHash() throws Exception {
        mvc.perform(get("/people")
                .param("passwordHash", "secret-value")
                .accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk());
        // Also assert that the result set is not filtered by passwordHash.
    }

    @Test
    void doesNotBindInternalNote() throws Exception {
        mvc.perform(get("/people")
                .param("internalNote", "confidential")
                .accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk());
        // Also assert that the result set is not filtered by internalNote.
    }
}
~~~

For disallowed parameters, checking only the HTTP status is not enough because the framework may ignore an unbound parameter and still return 200. Prepare distinct test data and assert the response content/result set to verify that disallowed filters do not affect the predicate.

Recommended tests include:

- Every path in the allow-list builds a predicate and filters data accurately.
- Unlisted paths do not alter the result set.
- Sensitive fields or fields hidden from JSON cannot be used as filter keys.
- Nested paths only work when explicitly opened.
- Aliases work under their public names and do not unintentionally expose the original path.
- Binding rules are enforced on every repository that uses Querydsl filtering.

## 11. Common errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| Fields outside the allow-list can still filter | excludeUnlistedProperties(true) is not enabled | Enable excluding unlisted properties |
| Excluded password but other internal fields can still filter | Using a single deny-list | Switch to an allow-list for strictly controlled APIs |
| Valid field fails to filter | Forgot to call including(path) or wrong Q-type | Check paths in the customizer |
| String field filters by equals instead of contains | Using default binding | Define bindings.bind(path).first(...) |
| Multiple values only take the first value | Using first(...) | Use all(...) if multiple values need to be handled |
| Nested fields remain exposed too broadly | Opened the parent object or used a global type binding | Allow-list only the needed nested paths |
| @JsonIgnore applied yet field can still be filtered | Jackson does not govern Querydsl filter binding | Use QuerydslBinderCustomizer and upgrade to a CVE-patched release |
| One repository is secured while another is not | Customizer is tied to only one domain type | Apply allow-lists on every repository with Querydsl |

## 12. Checklist for restricting filterable properties

- Check whether repositories use QuerydslPredicateExecutor and Querydsl web filtering.
- List the filter paths genuinely needed by clients.
- Enable excludeUnlistedProperties(true) when an allow-list is needed.
- Use including(...) for each approved path.
- Prefer per-path bindings for opened fields.
- Use excluding(...) only when a deny-list is intentional and all remaining fields have been audited.
- Check nested properties, collections, and aliases.
- Do not use @JsonIgnore in place of filter authorization.
- Check Spring Data REST version and upgrade to a release patched for CVE-2026-41837.
- Apply customizers to every repository with Querydsl filtering.
- Test both valid filters and disallowed filters by comparing result sets.

## Conclusion

QuerydslBinderCustomizer controls how request parameters are turned into predicates and is the key configuration point for restricting filterable properties. excluding(...) creates a deny-list; excludeUnlistedProperties(true) combined with including(...) creates an explicit allow-list. For protected APIs, open only the domain paths genuinely needed and verify in tests that unlisted fields do not influence results. Specifically, CVE-2026-41837 confirms that fields hidden by Jackson can still appear as filter keys on affected versions; upgrade to a patched release and enforce allow-lists on every repository.
