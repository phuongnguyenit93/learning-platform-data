# Distinguishing Hiding Resources, Hiding Links, and Enforcing Authorization

## 1. Objective

Spring Data REST provides multiple ways to control what part of the API is published. Three concepts are frequently confused:

- **Hiding resources (repository/resource export):** decides whether a repository resource is published by Spring Data REST.
- **Hiding links (association export):** decides whether an association is published as a hypermedia relation and endpoint.
- **Authorization:** decides whether a specific caller is permitted to execute a request.

These three mechanisms answer different questions. A link missing from HAL does not prove the target endpoint is protected. A repository not exported through Spring Data REST does not automatically protect custom controllers or other services accessing the same data. Authorization must be enforced at the request boundary or at the appropriate business layer.

This lesson explains how to hide repositories, hide association links, configure Spring Security, and test direct access paths to prevent data leaks.

## 2. Hiding repository resources

By default, Spring Data REST can discover and export repositories within configured scope. When a repository should not become a REST resource, mark it with @RepositoryRestResource(exported = false):

    @RepositoryRestResource(exported = false)
    public interface InternalProfileRepository
            extends JpaRepository<InternalProfile, Long> {
    }

This repository can still be injected and used inside the Spring application. exported=false prevents Spring Data REST from publishing the corresponding repository resources through the REST exporter.

When a repository is hidden, clients cannot discover its collection resource, item resource, or search resource through the corresponding export mechanism. However, that does not mean the data is protected everywhere:

- A custom controller may still return data from the repository.
- Another service may still read or modify the entity.
- Another API or another application may access the same database.
- An association from another repository must be checked separately to see whether it remains exported.

Hiding a repository is a decision about the API surface generated by Spring Data REST, not a replacement for authorization.

## 3. Hiding an association link

Suppose Customer has a relationship to InternalProfile:

    @Entity
    public class Customer {

        @Id
        @GeneratedValue
        private Long id;

        private String name;

        @ManyToOne
        @RestResource(exported = false)
        private InternalProfile internalProfile;
    }

@RestResource(exported = false) on an association instructs Spring Data REST not to export that association resource. The corresponding relation will not be published as a followable link on the Customer representation.

Distinguish this from hiding the entire InternalProfile repository. If InternalProfileRepository remains exported, clients may still access InternalProfile's collection or item resources via its standalone repository endpoint, depending on configuration and permissions. Hiding the link from Customer does not automatically make the target repository endpoint disappear.

Conversely, if the target repository is hidden while the association remains configured for export, whether association links can be generated and resolved depends on metadata, repository export configuration, and the Spring Data REST version. When removing a relationship from the API, configure association export explicitly and verify the actual representation.

## 4. Hiding query methods from search resources

Repository query methods can be exposed under the search resource. If a finder is only for internal processing, hide that individual method:

    public interface CustomerRepository
            extends JpaRepository<Customer, Long> {

        @Query("select c from Customer c where c.email = :email")
        @RestResource(exported = false)
        Optional<Customer> findInternalByEmail(
            @Param("email") String email
        );
    }

The method remains part of the repository API used inside the application, while Spring Data REST does not publish that finder as a search link.

Also inspect the search resource after configuration. The disappearance of the finder link shows that the finder endpoint is no longer published under that configuration; it does not replace permission checks for other endpoints returning the same data.

## 5. Hiding links is not security

HAL helps clients discover next steps through relations in _links. If a relation does not appear, hypermedia-driven clients will not see that path from the current representation.

However, a user can still attempt to call the URL directly if they know or guess the path. URLs can appear in logs, documentation, browser history, other responses, or be inferred from the application. Therefore:

- Do not use hidden links as an authorization mechanism.
- Do not treat hard-to-guess URLs as a data protection measure.
- Do not assume a client not seeing a link means the server rejects the request.
- Test association and repository resource endpoints directly with standalone requests.

For example, if the Customer response no longer includes the internalProfile link, still test GET on the InternalProfile endpoint using an unprivileged caller. If the target endpoint still returns sensitive data, the gap lies in that endpoint's export or authorization configuration.

## 6. Enforcing authorization with Spring Security

Spring Security checks whether the caller is allowed to access an endpoint. URL-based rules can be configured with SecurityFilterChain.

Illustrative example: only users with the customer:read authority can GET Customer resources; only customer:write can modify Customer:

    @Configuration
    @EnableWebSecurity
    public class SecurityConfig {

        @Bean
        SecurityFilterChain securityFilterChain(
                HttpSecurity http) throws Exception {

            return http
                .authorizeHttpRequests(auth -> auth
                    .requestMatchers(
                        HttpMethod.GET,
                        "/customers/**"
                    ).hasAuthority("customer:read")
                    .requestMatchers(
                        HttpMethod.POST,
                        "/customers/**"
                    ).hasAuthority("customer:write")
                    .requestMatchers(
                        HttpMethod.PUT,
                        "/customers/**"
                    ).hasAuthority("customer:write")
                    .requestMatchers(
                        HttpMethod.PATCH,
                        "/customers/**"
                    ).hasAuthority("customer:write")
                    .requestMatchers(
                        HttpMethod.DELETE,
                        "/customers/**"
                    ).hasAuthority("customer:delete")
                    .anyRequest().authenticated()
                )
                .build();
        }
    }

The URLs and authorities above are examples. Adjust matchers to match your application's base path, repository paths, association endpoints, search endpoints, and custom routes. If the API uses HTTP Basic, form login, OAuth2 Resource Server, or sessions, configure authentication to match that mechanism.

Do not copy CSRF configuration mechanically. Applications using sessions/cookies and stateless APIs have different requirements. Configure CSRF based on the actual authentication mechanism and threat model, and test write operations.

URL rules are an HTTP-boundary control layer. They work well for restricting groups of endpoints by method and path, but may be insufficient when permissions depend on entity owner, tenant, or state.

## 7. Object-level authorization and business rules

Sometimes two users are both allowed to GET /customers, yet may only view Customers belonging to their own tenant. A simple URL matcher cannot decide permissions based on entity contents.

When object-level checks are required:

- Obtain the caller's identity from SecurityContext.
- Determine the entity's owner or tenant.
- Check permissions at the service or repository operation actually invoked.
- Deny the request if the caller lacks permission.
- Apply checks across reads, updates, deletes, and association operations.

You can enable method security and use @PreAuthorize on services:

    @Configuration
    @EnableMethodSecurity
    public class MethodSecurityConfig {
    }

    @Service
    public class CustomerService {

        @PreAuthorize(
            "@customerAccess.canRead(authentication, #customerId)"
        )
        public Customer getCustomer(Long customerId) {
            return customerRepository.findById(customerId)
                .orElseThrow();
        }
    }

customerAccess is a business bean checking whether the caller has permission to read customerId. This example only takes effect if the request actually passes through CustomerService.getCustomer. If Spring Data REST calls the repository directly, an annotation on an uninvoked service will not protect that endpoint.

For directly exported repository resources, place controls in the HTTP authorization layer or on the methods/repositories/services actually invoked by Spring Data REST, and confirm with integration tests. Never assume adding @PreAuthorize to some service automatically blocks all repository access paths.

Check permissions on association resources separately. A caller may be allowed to read Customer while forbidden from reading InternalProfile or Orders. Permission on a parent resource does not equate to permission on every related resource.

## 8. Combining the three mechanisms

The three mechanisms can be viewed by purpose:

| Mechanism | Question answered | Example |
|---|---|---|
| Repository export | Does Spring Data REST publish the repository as a REST resource? | @RepositoryRestResource(exported = false) |
| Association export | Is the relation/association endpoint published? | @RestResource(exported = false) on association |
| Authorization | Is the current caller permitted to invoke the endpoint? | Spring Security request matchers or method security |

A secure configuration often uses all three as needed:

1. Export only repositories needed by the API.
2. Export only associations and finders fitting the API contract.
3. Enforce authentication and authorization on all exported endpoints.
4. Check object/tenant permissions where full business context is available.
5. Test endpoints directly, not just HAL responses.

Hiding resources/links shrinks the API surface and simplifies discovery. Authorization is the layer that decides whether a request is allowed or denied.

## 9. HTTP 401, 403, and 404

When Spring Security rejects a request, the status depends on authentication state and application policy:

- **401 Unauthorized:** the caller is unauthenticated or credentials are invalid; the client must authenticate.
- **403 Forbidden:** the caller is authenticated but lacks permission to perform the operation.
- **404 Not Found:** the resource does not exist, or the application deliberately uses 404 to avoid revealing the existence of a resource the caller may not know about.

Do not turn every authorization failure into 404 if the API contract requires 403. Conversely, some multi-tenant systems choose 404 for another tenant's resources to avoid confirming whether an ID exists. This is a security and API contract decision that must stay consistent.

A 401/403 error does not prove a repository or association is hidden; it proves the current request was denied by security policy. Likewise, 404 alone is not enough to conclude a resource is not exported if it could stem from a wrong ID or path.

## 10. Testing hidden resources, hidden links, and access permissions

Test each mechanism separately to know exactly which layer is taking effect.

**Verifying a hidden repository**

- GET the repository's collection path.
- GET an item path if a URI is known.
- GET the search path.
- Confirm Spring Data REST does not publish those resources under the configuration.
- If a custom controller serves the same data, test that route separately.

**Verifying a hidden association link**

- GET the parent resource with a HAL Accept header.
- Confirm the relation does not appear in _links.
- Attempt to call the association URL directly with a standalone request.
- Attempt to call the target repository endpoint if that repository remains exported.

**Verifying authorization**

- Send a request without credentials.
- Send a request with an authenticated user lacking the required authority.
- Send a request with an authenticated user holding the proper authority.
- Repeat for GET, POST, PUT/PATCH, DELETE, search, and association endpoints.
- Attempt to call the target href directly even when the parent response does not advertise the link.
- Attempt to access resources belonging to another tenant or owner.

Do not verify only that the link vanished. Tests must confirm the server rejects direct requests when the caller lacks permission.

## 11. Example integration test with MockMvc

A test can confirm callers lacking Customer read permission are denied:

    @SpringBootTest
    @AutoConfigureMockMvc
    class CustomerAuthorizationTest {

        @Autowired
        private MockMvc mockMvc;

        @Test
        @WithMockUser(authorities = "customer:write")
        void userWithoutReadAuthorityCannotGetCustomer()
                throws Exception {

            mockMvc.perform(get("/customers/42")
                    .accept("application/hal+json"))
                .andExpect(status().isForbidden());
        }

        @Test
        @WithMockUser(authorities = "customer:read")
        void userWithReadAuthorityCanGetCustomer()
                throws Exception {

            mockMvc.perform(get("/customers/42")
                    .accept("application/hal+json"))
                .andExpect(status().isOk());
        }
    }

This example assumes the security policy above and that Customer 42 exists. If the application uses roles instead of authorities, adjust @WithMockUser and matchers accordingly.

You can test a hidden association link:

    mockMvc.perform(get("/customers/42")
            .accept("application/hal+json"))
        .andExpect(status().isOk())
        .andExpect(jsonPath(
            "$._links.internalProfile"
        ).doesNotExist());

Follow up with a separate test calling the target endpoint directly as an unauthorized user. Asserting the link is absent only verifies representation; it does not verify authorization.

When testing 401, 403, or 404, follow the application's actual authentication setup and policy. In some setups, requests without credentials may redirect to login instead of returning 401; API resource servers usually configure responses differently from form login.

## 12. Common pitfalls

**Using exported=false instead of security**

Export annotations control the Spring Data REST surface. They do not protect custom controllers, other services, or the database.

**Hiding links while leaving the target endpoint open**

Clients who cannot see a link can still call the URL directly. Protect target endpoints with authorization and test directly.

**Hiding a repository while forgetting custom endpoints**

The repository is no longer published by the REST exporter, yet another controller or route may still return the same data. Inventory and protect all access paths.

**Confusing rel with repository path**

Association rel is the relationship name in HAL; repository path is the collection/item URL. Both names can be customized independently.

**Testing only GET**

Read permission does not imply write or delete permission. Test every HTTP method and association mutation endpoint.

**Protecting only the parent resource**

A caller may be permitted to read Customer while forbidden from reading related profiles, payments, or sensitive data. Verify permissions on target resources.

**Relying on client UI**

Hiding buttons or omitting links in the UI does not stop HTTP requests. The server must enforce authorization itself.

**Failing to test tenant/owner**

Role-based permissions may be insufficient. Test callers attempting to access IDs belonging to other tenants or owners.

## 13. Hands-on exercises

With Customer and InternalProfile:

1. Create InternalProfileRepository and mark the repository exported=false.
2. GET the collection path and search path to verify the repository is not published by Spring Data REST.
3. Create the Customer.internalProfile association and mark it @RestResource(exported = false).
4. GET the Customer HAL representation and verify the internalProfile relation does not appear in _links.
5. If InternalProfile still has a custom controller or another endpoint, try accessing that endpoint directly.
6. Configure SecurityFilterChain to require customer:read for GET and customer:write for write operations.
7. Send unauthenticated requests, requests lacking authorities, and requests with appropriate authorities.
8. Test association endpoints and item URLs directly, even when links are hidden.
9. Enable method security on a service checking owner/tenant and confirm requests pass through that service.
10. Write MockMvc tests for 401/403 matching your real security configuration.
11. Confirm a user cannot read or modify resources belonging to another tenant.

Self-check questions:

- Which part of the API does @RepositoryRestResource(exported = false) affect?
- How does @RestResource(exported = false) on an association differ from hiding the target repository?
- Why does a missing link not mean an endpoint is protected?
- When should you use request matchers versus object-level permission checks?
- How do 401, 403, and 404 differ in an authorization flow?
- Why test direct URLs and every HTTP method?

## 14. Key takeaways

- Repository export determines whether Spring Data REST publishes repository resources.
- Association export determines whether relation/association endpoints are published.
- Authorization determines whether the current caller is permitted to execute a request.
- @RepositoryRestResource(exported = false) hides repository resources from the REST exporter.
- @RestResource(exported = false) can hide the corresponding association or query method.
- Hiding links does not protect target endpoints; clients can still call URLs directly.
- Use Spring Security at the HTTP boundary and method/service security for owner or tenant business rules.
- Check permissions separately on parent, association, item, collection, and search endpoints.
- Test requests with no credentials, insufficient permissions, and valid permissions.
- Never rely on UI hiding, hard-to-guess URLs, or hidden links to protect data.
