# Distinguishing POST, PUT, and PATCH When All Rely on save

## Objectives

Spring Data REST maps multiple HTTP methods to the same repository `save(…)` method. On a collection resource, `POST` creates an entity. On an item resource, `PUT` replaces the resource state and `PATCH` partially updates it. Therefore, seeing all three requests call `save()` does not mean they share the same semantics.

Two decision layers must be distinguished:

- **HTTP method and URI** determine client intent: creating a resource in a collection, replacing an item, or modifying part of an item.
- **Spring Data repository** decides how to persist the entity based on its new/existing state and datastore mechanics. With Spring Data JPA, `save()` typically chooses `EntityManager.persist()` or `EntityManager.merge()` based on its entity-newness detection strategy.

This lesson uses `PersonRepository` as an example. The HTTP rules describe default Spring Data REST behavior; export configuration, versions, mappings, and specific datastores can still affect outcomes.

## 1. Calling save with Different HTTP Semantics

Suppose the repository is exported at `/people`:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

Spring Data REST provides the `/people` collection resource and the `/people/{id}` item resource. Common requests:

| HTTP request | Target Resource | Intent | Data Handling |
|---|---|---|---|
| `POST /people` | Collection | Create a new entity | Construct entity from body and call `save()` |
| `PUT /people/42` | Item 42 | Replace item state | Use full representation to replace state and call `save()` |
| `PATCH /people/42` | Item 42 | Partially update item | Apply changes onto current state and call `save()` |

In Spring Data REST, `POST` is supported on collection resources; `PUT` and `PATCH` are supported on item resources. Some association endpoints have separate HTTP rules, so do not apply this table to association URIs.

## 2. POST: Creating an Entity via the Collection Resource

Clients send `POST` to the collection URI:

~~~http
POST /people
Content-Type: application/json
Accept: application/hal+json

{
  "firstName": "An",
  "lastName": "Nguyen",
  "city": "Ho Chi Minh City"
}
~~~

Spring Data REST reads the request body, constructs an entity, and invokes the repository's `save()` method. This is a creation operation according to the endpoint's semantics: the client submits a representation for the collection to accept and produce a new item. If the ID is generated by the database or persistence provider, clients typically omit the ID from the body. For manually assigned IDs, the application needs clear ID and entity-newness rules.

Creation responses typically carry status `201 Created` and a `Location` header pointing to the newly created item URI. Whether the response includes a body depends on the `Accept` header and `RepositoryRestConfiguration.setReturnBodyOnCreate(…)`.

For example, the server may return:

~~~http
HTTP/1.1 201 Created
Location: http://localhost:8080/people/42
Content-Type: application/hal+json
~~~

Key takeaway: `POST` targets the collection so the server accepts data and creates an item. If the client resends the same `POST`, the server may create another item; POST is not idempotent by default.

## 3. PUT: Replacing an Item's State

Clients send `PUT` to the URI identifying the item:

~~~http
PUT /people/42
Content-Type: application/json
Accept: application/hal+json

{
  "firstName": "An",
  "lastName": "Tran",
  "city": "Da Nang"
}
~~~

Spring Data REST uses the body to replace the target resource's state and then calls `save()`. Clients should send a complete representation of all properties to retain. Omitting a property from the body may replace the old value with `null` or a default value depending on entity mapping. For instance, if the body omits `city`, the client should not expect the previous `city` value to always be preserved.

In Spring Data REST, `PUT` on an item resource can also create a resource at the specified URI if it does not yet exist. This is Spring Data REST's PUT-for-creation capability; it can be disabled per domain type via `disablePutForCreation()` in `RepositoryRestConfiguration.getExposureConfiguration()`. Clearly define this behavior in your API contract so clients know when PUT creates vs. only updates.

PUT has idempotent semantics: resending the same representation to the same URI should bring the resource to the same target state, though application events or side effects may execute multiple times. On successful update, the response is typically `200 OK` when returning a representation or `204 No Content` when returning no body. When PUT creates a new item, the response is typically `201 Created`. Options like `setReturnBodyOnUpdate(…)` and `setReturnBodyCreate(…)` can adjust the response.

## 4. PATCH: Partially Updating an Item

Clients send `PATCH` to the item URI and supply only the fields to change:

~~~http
PATCH /people/42
Content-Type: application/merge-patch+json
Accept: application/hal+json

{
  "city": "Can Tho"
}
~~~

Spring Data REST applies the changes in the body onto the current resource state and then calls `save()`. In this example, `city` is updated; properties absent from the patch, such as `firstName` and `lastName`, stay at their current state.

Spring Data REST supports patch media types such as `application/patch+json` and `application/merge-patch+json`, in addition to `application/json`. The media type dictates how the patch document is interpreted. In particular, distinguish an omitted property from one explicitly sent as `null`; the meaning of `null` depends on the patch format and mapping mechanism. Always verify the endpoint's media type and data rules.

PATCH is not guaranteed to be idempotent for every patch document type. For example, an increment operation can produce different outcomes when repeated. If clients must retry requests after timeouts, design safely repeatable patch operations or use version control mechanisms.

## 5. Why Can save() Insert or Update?

The HTTP method does not directly decide whether JPA calls `persist()` or `merge()`. With Spring Data JPA, `SimpleJpaRepository.save(entity)` checks whether the entity is considered new:

- New entity: calls `EntityManager.persist(entity)`.
- Existing entity: calls `EntityManager.merge(entity)`.

By default, Spring Data JPA detects entity state in the following order:

1. If there is a non-primitive `@Version` property, a `null` version value marks the entity as new.
2. If there is no suitable version property, inspect the ID: a `null` ID marks the entity as new; a non-`null` ID marks it as existing.
3. If the entity implements `Persistable<ID>`, Spring Data uses the entity's `isNew()` method to determine state.
4. Applications can customize `EntityInformation` in special cases.

JPA entity example:

~~~java
@Entity
public class Person {

    @Id
    @GeneratedValue
    private Long id;

    @Version
    private Long version;

    private String firstName;
    private String lastName;
    private String city;

    // constructors, getters, setters
}
~~~

With this entity, a `null` version indicates a new entity under Spring Data JPA's detection strategy. Once the entity is saved and the version has a value, it is treated as non-new. Without `@Version`, the ID is typically used to detect state.

This explains why you cannot look solely at the HTTP method or JSON ID to conclude for certain whether the final SQL is INSERT or UPDATE. The endpoint determines how the request is interpreted; the store's entity-newness strategy determines the persistence path. For datastores other than JPA, underlying `save()` details may differ.

### 5.1. Manually Assigned IDs

If the application assigns IDs manually upon entity creation, a non-`null` ID can cause the default strategy to treat the entity as already existing. A new entity might then be routed through the `merge()` branch.

One approach is implementing `Persistable<ID>` and managing an `isNew` flag aligned with the entity lifecycle:

~~~java
@MappedSuperclass
public abstract class BaseEntity implements Persistable<Long> {

    @Id
    private Long id;

    @Transient
    private boolean newEntity = true;

    @Override
    public Long getId() {
        return id;
    }

    @Override
    public boolean isNew() {
        return newEntity;
    }

    @PostPersist
    @PostLoad
    void markNotNew() {
        this.newEntity = false;
    }
}
~~~

This is a strategy example, not code to copy verbatim for every domain. Ensure the flag is updated properly after inserts and when entities are reloaded; if using property access, also verify how JPA detects `Persistable` properties.

### 5.2. Using the Return Value of save()

With JPA, `merge()` may return a different managed instance than the one passed in. Therefore, use the entity returned by `save()`:

~~~java
Person saved = personRepository.save(person);
~~~

Do not assume the original object always gets its ID, version, or persistence state updated after calling `save()`.

## 6. Putting the Three Requests Side by Side

Suppose person 42 currently has data:

~~~json
{
  "id": 42,
  "firstName": "An",
  "lastName": "Nguyen",
  "city": "Ha Noi"
}
~~~

**POST – create a new item**

~~~http
POST /people
Content-Type: application/json

{
  "firstName": "Binh",
  "lastName": "Le",
  "city": "Hue"
}
~~~

The result is a new item. Its URI is provided by the server in the `Location` header.

**PUT – replace item 42**

~~~http
PUT /people/42
Content-Type: application/json

{
  "firstName": "An",
  "lastName": "Tran",
  "city": "Da Nang"
}
~~~

The result is that item 42's full state is replaced with the submitted representation. Fields omitted from the body may lose their previous values.

**PATCH – modify only one field of item 42**

~~~http
PATCH /people/42
Content-Type: application/merge-patch+json

{
  "city": "Can Tho"
}
~~~

The result is that city changes to Can Tho; firstName and lastName retain their previous state.

| Criterion | POST | PUT | PATCH |
|---|---|---|---|
| Typical URI | Collection | Item | Item |
| Goal | Create item | Replace item | Partially modify item |
| Body | Data to create | Full representation | Changes to apply |
| Spring Data REST calls | `save()` | `save()` | `save()` |
| Can create an item? | Yes | Possibly, if PUT-for-creation is enabled | Do not use PATCH to create new items |
| Idempotent per HTTP semantics | Not by default | Yes | Not guaranteed for all patches |
| Creation response | Usually 201 Created | Usually 201 Created if created via PUT | Not a resource creation operation |

## 7. Controlling Export and Update Behavior

Because `save()` backs POST on collections and PUT/PATCH on items, hiding save with `@RestResource(exported = false)` can remove multiple write endpoints simultaneously. If you only want to disable one HTTP method or a specific capability, use `RepositoryRestConfiguration.getExposureConfiguration()` to configure by domain type or item exposure.

Example disabling PUT-for-creation for `Person`:

~~~java
@Configuration
public class RestConfiguration implements RepositoryRestConfigurer {

    @Override
    public void configureRepositoryRestConfiguration(
            RepositoryRestConfiguration config,
            CorsRegistry cors) {

        config.getExposureConfiguration()
            .forDomainType(Person.class)
            .disablePutForCreation();
    }
}
~~~

You can disable PATCH on item resources via item exposure:

~~~java
config.getExposureConfiguration()
    .withItemExposure((metadata, methods) ->
        methods.disable(HttpMethod.PATCH));
~~~

API names and method signatures may differ across Spring Data REST generations. Check your dependency version before applying configuration snippets.

## 8. Validation, Events, and Concurrent Updates

All three requests may traverse the same repository save path, yet their input data and intent differ. Therefore:

- Validation must check the final state of the entity. For PATCH, validate after applying the patch onto the existing entity, because the body may contain only a single field.
- Repository events such as before-save/after-save reflect the entity persistence lifecycle. Do not infer POST, PUT, or PATCH solely from a generic save event if the application needs to branch by HTTP method.
- PUT and PATCH can overwrite another request's changes if two clients read the same stale version. With JPA, use `@Version` to enable optimistic locking; Spring Data REST also supports conditional requests via ETag and `If-Match`.
- When operation-specific business rules are needed, place logic in the service/domain layer with explicit operation context or build a custom endpoint. Do not rely on all of them calling `save()` to deduce business intent.

## 9. Common Issues and How to Check Them

| Symptom | Possible Cause | How to Check |
|---|---|---|
| POST creates unexpected extra records | Client used POST for an update operation | Check collection URI and HTTP method |
| PUT clears values of unsent fields | PUT replaces the representation | Send all fields to retain or switch to PATCH |
| PATCH modifies unintended fields | Unclear media type or null/association semantics | Check Content-Type and patch document |
| PUT to a new URI fails to create item | PUT-for-creation disabled or ID invalid for store | Check ExposureConfiguration and ID strategy |
| POST/PUT calls save with unexpected insert/update | Entity-newness detection mismatches ID/version | Check `@Version`, ID, and `Persistable.isNew()` |
| Data saves properly but existing code object lacks version/ID | Not using instance returned by `save()` | Assign `save()` result to a variable and use it |
| Two clients overwrite each other's data | No concurrency control | Use `@Version` and ETag/If-Match conditional requests |

## 10. Checklist for Choosing an HTTP Method

- Choose POST on a collection when the server should create a new item.
- Choose PUT on an item when the client has a full representation and wants to replace state at that URI.
- Choose PATCH on an item when modifying only part of the state.
- Check whether PUT-for-creation is enabled or disabled in Spring Data REST.
- Check the PATCH media type and how omitted properties or explicit `null` values are handled.
- Check the store's entity-newness detection strategy, especially with manually assigned IDs.
- Always use the instance returned by `save()`.
- Use optimistic locking/ETags when multiple clients can update the same resource.
- Inspect response status, `Location`, and returned representation to verify whether the request created or updated.

## Conclusion

POST, PUT, and PATCH can all invoke `save()` while carrying three distinct intents. POST creates an item via the collection; PUT replaces an item's representation and in Spring Data REST can create an item if PUT-for-creation is enabled; PATCH applies partial changes onto the existing item. After the endpoint prepares the entity, Spring Data JPA detects whether the entity is new or existing to choose persist or merge. To understand the outcome accurately, inspect the HTTP method, URI, body, exposure configuration, and entity-newness strategy rather than looking only at the save method name.
