# Integrating `spring-data-rest-webmvc` into an Existing Spring MVC Application

Spring Data REST can run alongside an existing Spring MVC application. For a manually configured Spring MVC application, the main integration consists of two steps: adding the `spring-data-rest-webmvc` module as a dependency and importing `RepositoryRestMvcConfiguration` into the Spring configuration serving MVC. This configuration registers the components needed for Spring Data REST to receive requests and export eligible Spring Data repositories as REST resources.

After integration, existing MVC controllers and repository resources can serve requests side by side within the same application. The most important detail to watch for is that an exported repository path may be handled by Spring Data REST before your application controller if both share the same URL.

This lesson focuses on Spring MVC applications that do not use Spring Boot auto-configuration. If your application uses Spring Boot, the setup differs and is covered in its own section below.

## 1. How Does Spring Data REST Work Inside an MVC Application?

Spring Data REST is built on top of Spring MVC. It adds handlers and REST resource representations backed by Spring Data repositories. When integrated into an existing MVC application, Spring Data REST does not require a separate web application or a second `DispatcherServlet`.

Overall flow:

~~~mermaid
flowchart TD
    C["HTTP client"] --> DS["Existing DispatcherServlet"]
    DS --> RHM["RepositoryRestHandlerMapping"]
    RHM -->|URL belongs to exported repository| SDR["RepositoryRestController"]
    RHM -->|Does not match a repository| HM["Other HandlerMappings"]
    HM --> MVC["Existing MVC Controllers"]
    SDR --> REPO["Spring Data Repository"]
    REPO --> STORE["Store module: JPA, MongoDB, ..."]
    SDR --> RESP["HAL / REST response"]
    MVC --> RESP2["Application response"]
~~~

Spring Data REST registers a `RepositoryRestHandlerMapping` to recognize URLs belonging to exported repositories. If a path matches a repository resource, the request is dispatched to Spring Data REST. If no matching repository exists, the handler mapping returns `null`, allowing other `HandlerMapping` beans to process the request.

Therefore, both endpoint types can coexist:

- Application endpoints written with `@Controller` or `@RestController`.
- Collection, item, search, and association endpoints generated by Spring Data REST from repositories.

## 2. Inspecting the Existing Spring MVC Application

Before adding dependencies, examine the application's structure and locate where MVC configuration is declared.

A traditional Spring MVC application typically already has:

- Spring Framework and a Servlet container such as Tomcat or Jetty.
- A `DispatcherServlet` registered in the web application.
- MVC configuration via Java Config or XML.
- One or more controllers handling requests.
- Spring Data repositories and the corresponding persistence module, or persistence configuration to be added separately.

Identify which Spring configuration is loaded in the web application. Spring Data REST configuration must reside in an `ApplicationContext` where repositories are visible.

In applications with a root context and a `DispatcherServlet` child context, the child context sees beans in the parent context. A common layout puts repositories and services in the root context, and MVC configuration in the child context. When you import `RepositoryRestMvcConfiguration` into the child context, it can access repositories from the parent context. If repositories live in a context invisible to the context containing Spring Data REST configuration, endpoints will not be created as expected.

Do not add another `DispatcherServlet` just for Spring Data REST. Proper integration places Spring Data REST configuration into the existing MVC application context.

## 3. Adding the `spring-data-rest-webmvc` Dependency

For a Spring MVC application without Spring Boot, add the `spring-data-rest-webmvc` artifact as a compile-time dependency.

### 3.1. Gradle

If the project already imports the Spring Data BOM or uses dependency management for Spring Data versions, declare the modules without individual versions:

~~~groovy
dependencies {
    implementation("org.springframework.data:spring-data-rest-webmvc")
    implementation("org.springframework.data:spring-data-jpa")
}
~~~

In this example, `spring-data-jpa` is needed only when the application uses JPA. If your application uses MongoDB, Redis, or another store, add the corresponding Spring Data module and configure repositories for that store.

If the project does not yet have dependency management, import the Spring Data Release Train BOM as a Gradle platform and then declare the modules:

~~~groovy
dependencies {
    implementation(platform("org.springframework.data:spring-data-bom:REPLACE_WITH_COMPATIBLE_RELEASE_TRAIN_VERSION"))

    implementation("org.springframework.data:spring-data-rest-webmvc")
    implementation("org.springframework.data:spring-data-jpa")
}
~~~

Replace `REPLACE_WITH_COMPATIBLE_RELEASE_TRAIN_VERSION` with the release train chosen by your project. Pick a release train compatible with your Spring Framework and Spring Data modules. Do not mix versions of Spring Data REST, Spring Data Commons, Spring Data JPA, and Spring Framework from different release trains.

### 3.2. Maven

With Maven, you can import the Spring Data BOM inside `dependencyManagement`:

~~~xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.data</groupId>
            <artifactId>spring-data-bom</artifactId>
            <version>REPLACE_WITH_COMPATIBLE_RELEASE_TRAIN_VERSION</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
~~~

Then declare the required modules:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.data</groupId>
        <artifactId>spring-data-rest-webmvc</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.data</groupId>
        <artifactId>spring-data-jpa</artifactId>
    </dependency>
</dependencies>
~~~

Replace the placeholder value with a release train compatible with your current platform. If your project already has a BOM managing Spring Data, do not import a second BOM.

### 3.3. Choosing Compatible Versions

Spring Data REST, Spring Data Commons, and store modules do not necessarily have identical version numbers. The Spring Data Release Train BOM is provided to keep compatible versions aligned.

When adding Spring Data REST to a legacy Spring MVC application, also check the Spring Framework version. You cannot simply pick the newest Spring Data REST release and assume it works with any existing MVC application. If the project is on an older Spring Framework generation, pick a Spring Data release train that supports that generation or plan a tested platform upgrade.

Do not combine `spring-boot-starter-data-rest` with manual configuration merely because the application already uses Spring MVC. The starter is meant for Spring Boot applications; plain MVC applications can use `spring-data-rest-webmvc` directly.

## 4. Importing `RepositoryRestMvcConfiguration`

This is the core configuration step for a traditional Spring MVC application.

Create a configuration class or add `@Import` to an existing configuration:

~~~java
package example.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.data.rest.webmvc.RepositoryRestMvcConfiguration;

@Configuration
@Import(RepositoryRestMvcConfiguration.class)
public class SpringDataRestIntegrationConfiguration {
}
~~~

When Spring creates the `ApplicationContext`, `RepositoryRestMvcConfiguration` registers the MVC infrastructure needed to configure `RepositoryRestController` and export repositories visible to that context and its parent contexts.

You can place `@Import` directly on your existing MVC configuration:

~~~java
package example.config;

import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.data.rest.webmvc.RepositoryRestMvcConfiguration;
import org.springframework.web.servlet.config.annotation.EnableWebMvc;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
@EnableWebMvc
@Import(RepositoryRestMvcConfiguration.class)
@ComponentScan(basePackages = "example.web")
public class WebMvcConfiguration implements WebMvcConfigurer {
    // Existing MVC configuration for the application.
}
~~~

The second example illustrates an application already using Java Config with `@EnableWebMvc`. If your application already has an MVC configuration, simply import Spring Data REST into that configuration or into another configuration class loaded in the same context. Do not create a separate standalone MVC configuration that redeclares components that already exist.

### 4.1. Do Not Enable MVC Twice

`@EnableWebMvc` enables Spring MVC configuration. If your application already has this annotation or configures MVC via XML, do not add it a second time just for integrating Spring Data REST.

`@Import(RepositoryRestMvcConfiguration.class)` adds Spring Data REST configuration. It does not require registering another `DispatcherServlet` or replacing your existing controllers, view resolvers, resource handlers, and interceptors.

### 4.2. XML Configuration Case

Legacy applications may declare Spring beans in XML. In that case, register Spring Data REST's Java configuration in the appropriate `ApplicationContext`, or import the configuration using the Java Config mechanism your application uses. Any class/package FQN in XML must match the exact Spring Data REST artifact in your project; do not copy an FQN from old documentation without checking your active dependency.

## 5. Ensuring Spring Data Repositories Are Configured

Importing `RepositoryRestMvcConfiguration` does not create repositories or replace store configuration. Spring Data REST can only export repositories already registered by Spring Data.

Example with Spring Data JPA:

~~~java
package example.people;

import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.rest.core.annotation.RepositoryRestResource;

@RepositoryRestResource(path = "people")
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

The application must have proper JPA configuration and repository scanning. If the project has not enabled repository scanning yet, declare it in your data configuration:

~~~java
package example.config;

import example.people.PersonRepository;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.jpa.repository.config.EnableJpaRepositories;

@Configuration
@EnableJpaRepositories(basePackageClasses = PersonRepository.class)
public class JpaRepositoryConfiguration {
    // Application EntityManagerFactory and transaction manager.
}
~~~

The snippet above only illustrates enabling scanning; a real JPA application must also configure a `DataSource`, `EntityManagerFactory`, transaction manager, and entity mappings. If these components are already configured, do not declare duplicates.

For other stores, use the corresponding scanning annotation and Spring Data module. For example, MongoDB repositories require Spring Data MongoDB and MongoDB configuration; Spring Data REST does not create database connections on its own.

### 5.1. Controlling Which Repositories Are Exported

Spring Data REST uses a repository detection strategy to decide which repositories become REST resources. The default strategy inspects public repository interfaces and the annotation's `exported` flag. You can use `@RepositoryRestResource` to explicitly declare exported repositories:

~~~java
@RepositoryRestResource(path = "people", exported = true)
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

To prevent exporting a repository:

~~~java
@RepositoryRestResource(exported = false)
public interface InternalPersonRepository extends JpaRepository<Person, Long> {
}
~~~

Having a repository in the Spring context does not mean it should be exposed over HTTP. Decide explicitly which repositories belong in the API.

## 6. Combining Spring MVC Endpoints and Repository Resources

Suppose your application already has a controller:

~~~java
package example.web;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/reports")
public class ReportController {

    @GetMapping
    public List<String> getReports() {
        return List.of("daily", "monthly");
    }
}
~~~

At the same time, the application has `PersonRepository` exported at path `people`.

Both sets of endpoints can coexist:

| Request | Handling Component |
|---|---|
| `GET /reports` | Application's `ReportController` |
| `GET /people` | Spring Data REST |
| `GET /people/{id}` | Spring Data REST |
| `GET /people/search` | Spring Data REST if the repository has exported search methods |

Spring Data REST does not convert existing controllers into repository endpoints. Controllers continue running under standard Spring MVC mappings; repository resources are handled by Spring Data REST's own handler mechanism.

### 6.1. `RepositoryRestHandlerMapping` and URL Conflicts

This is the most critical detail when integrating into an application that already has many controllers.

Spring Data REST registers `RepositoryRestHandlerMapping`. This handler mapping checks whether a URL belongs to an exported repository:

- If a repository is exported under `people`, requests starting with `/people` are routed to Spring Data REST.
- If no exported repository matches the path, the handler mapping returns `null`, letting other application handler mappings attempt to handle the request.
- If an existing controller also maps `/people`, that route may be claimed by Spring Data REST first. Your application controller will not process requests belonging to the repository resource.

For instance, if you have:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

then you should not simultaneously declare a business controller mapping `/people` intending to override the collection/item endpoints provided by the repository.

How to handle this:

1. Place repository resources and business controllers on distinct paths, such as `/people` and `/people-management`.
2. Change the export path with `@RepositoryRestResource(path = "...")` if needed.
3. Set `exported = false` on a repository or method if you do not want that endpoint exposed.
4. If you need a custom handler inside the API namespace that uses Spring Data REST response configuration, consider `@RepositoryRestController`. If you need a custom controller under the base path not tied to a specific repository resource, consider `@BasePathAwareController`.

Controllers annotated with `@RepositoryRestController` or `@BasePathAwareController` can leverage Spring Data REST conventions such as base path and response handling. A regular `@RestController` remains part of the application's standard Spring MVC flow.

Do not register an extra `RepositoryRestHandlerMapping` manually if you already imported `RepositoryRestMvcConfiguration`. The imported configuration already creates the required handler mapping.

## 7. Customizing the Base Path and REST Settings

By default, Spring Data REST serves resources from the root path. You can change the base path to separate repository APIs from existing MVC endpoints.

In a non-Spring Boot application, register a `RepositoryRestConfigurer`:

~~~java
package example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.rest.core.config.RepositoryRestConfiguration;
import org.springframework.data.rest.webmvc.config.RepositoryRestConfigurer;
import org.springframework.web.servlet.config.annotation.CorsRegistry;

@Configuration
public class SpringDataRestSettings {

    @Bean
    RepositoryRestConfigurer repositoryRestConfigurer() {
        return new RepositoryRestConfigurer() {
            @Override
            public void configureRepositoryRestConfiguration(
                    RepositoryRestConfiguration config,
                    CorsRegistry cors) {
                config.setBasePath("/api/data");
            }
        };
    }
}
~~~

With this configuration, the `people` repository is accessed at `/api/data/people`. The base path applies to REST resources managed by Spring Data REST.

`RepositoryRestConfigurer` also offers customization points such as repository detection, page size, media types, and CORS. Override only the methods relevant to your application.

If your application uses Spring Boot, the base path can be configured via `spring.data.rest.basePath`. With plain MVC, use a `RepositoryRestConfigurer` bean as shown above.

## 8. Verifying After Integration

After adding dependencies, importing the configuration, and confirming repository scanning, restart the application on your Servlet container as usual.

Suppose:

- `PersonRepository` is exported with path `people`.
- Spring Data REST base path is `/api/data`.
- The application runs at `http://localhost:8080`.

Call the collection endpoint:

~~~bash
curl -i \
  -H "Accept: application/hal+json" \
  http://localhost:8080/api/data/people
~~~

If the repository is discovered, the response is typically HAL JSON. Even without data, the collection returns a valid response with an empty list and resource links.

Verify the existing MVC endpoint:

~~~bash
curl -i http://localhost:8080/reports
~~~

These two requests confirm that Spring Data REST has been integrated and that existing controllers are still served via MVC.

You can also test search resources if the repository declares exported query methods. Example:

~~~java
public interface PersonRepository extends JpaRepository<Person, Long> {
    List<Person> findByNameContainingIgnoreCase(String name);
}
~~~

When a search method is exported, Spring Data REST exposes a `search` link in resource metadata. Clients should discover that link or use the exact path and parameters configured for the repository.

## 9. CORS, Security, and Exported Data

Spring Data REST generates HTTP endpoints from repositories, so adding this module can expose new read and write operations. Review these points before deploying:

- Audit which repositories are exported and which CRUD/search methods can be invoked.
- Configure Spring Security to protect repository URLs, including collections, items, searches, and associations.
- Do not assume existing CORS settings for MVC controllers automatically cover Spring Data REST policies. Configure CORS for repository REST via `RepositoryRestConfigurer` and verify with live requests.
- Do not expose entities with internal fields or sensitive data without controlling the representation. Use appropriate projections/DTOs and enforce authorization on operations.
- Verify API paths after setting a base path so security rules and reverse proxies still match.

Hiding a repository or method from the REST API is part of API design; it does not replace authorization. Clients must still be authenticated and authorized on the server.

## 10. Common Integration Errors

| Symptom | Common Cause | How to Check |
|---|---|---|
| Repository endpoints return 404 | Repository not scanned, not exported, or not visible from the `ApplicationContext` holding Spring Data REST config | Check store config, detection strategy, and context hierarchy |
| Existing controller stops receiving requests | Controller path collides with an exported repository path | Check `@RepositoryRestResource(path = "...")` and controller mappings |
| App fails to start with class/method errors | Incompatible Spring Data REST, Spring Data Commons, or Spring Framework versions | Check dependency tree and Spring Data BOM |
| No repository resources despite importing config | Repositories live in a context not visible to Spring Data REST configuration | Place repositories in the same context or an appropriate parent context |
| API returns 406 or 415 | Incompatible `Accept`/`Content-Type` headers or misconfigured message converters | Send `Accept: application/hal+json` and `Content-Type: application/json` for JSON payloads |
| Requests rejected by security | Security matchers do not cover new repository REST paths | Check rules for base path, collection, item, and search URLs |
| Browser reports CORS errors | CORS policy for Spring Data REST is not configured accordingly | Check `RepositoryRestConfigurer` and preflight responses |

When debugging, check in order: dependencies and version alignment, `ApplicationContext`, repository scanning/export, URL mapping, and finally media types, CORS, and security. This helps isolate which integration step failed.

## 11. The Spring Boot Case

If your real application uses Spring Boot, you generally do not need to import `RepositoryRestMvcConfiguration` manually. Add the starter:

~~~groovy
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-data-rest")
}
~~~

Spring Boot auto-configuration sets up Spring Data REST when auto-configuration is enabled. Continue declaring your repositories and store modules; customizations can be supplied via a `RepositoryRestConfigurer` bean.

Do not mix both bootstrap approaches without a specific reason. When using the Boot starter and auto-configuration, let Boot manage the MVC integration.

## 12. Practical Integration Workflow

You can follow this sequence:

1. Identify your current Spring Framework and Spring Data versions.
2. Choose a compatible Spring Data Release Train BOM; add `spring-data-rest-webmvc` and the corresponding store module.
3. Confirm Spring Data repositories are scanned and store configuration works.
4. Import `RepositoryRestMvcConfiguration` into the MVC `ApplicationContext` serving the application.
5. Select which repositories to export via annotations or detection strategy.
6. Check whether repository paths conflict with existing controllers.
7. Configure the base path, CORS, and required customizations via `RepositoryRestConfigurer`.
8. Test both repository endpoints and existing controller endpoints.
9. Audit security and exposed data before deploying.

## 13. Key Takeaways

- `spring-data-rest-webmvc` is the module implementing Spring Data REST on Spring MVC.
- `RepositoryRestMvcConfiguration` is the Java configuration to import when integrating manually into an MVC application.
- No second `DispatcherServlet` is required.
- Repositories must be registered by Spring Data and visible from the `ApplicationContext` containing Spring Data REST.
- `RepositoryRestHandlerMapping` routes requests to exported repositories; overlapping paths can prevent existing controllers from receiving requests.
- Use `RepositoryRestConfigurer` to configure the base path and REST customizations.
- With Spring Boot, the starter and auto-configuration typically handle these bootstrap steps automatically.
