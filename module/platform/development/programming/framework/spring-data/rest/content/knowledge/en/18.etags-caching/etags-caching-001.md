# ETag and Its Relationship with the @Version Property

## Objectives

Spring Data REST supports HTTP conditional headers to protect resources from stale updates and reduce the amount of data transmitted over the network. This mechanism combines two needs:

- Optimistic locking: preventing one client from overwriting newer changes made by another client.
- HTTP caching/revalidation: allowing a client to ask whether a resource has changed since the previous read.

For an entity with a property annotated with `@Version`, Spring Data REST uses the version value as the resource's ETag. The client retrieves the ETag from the GET response and sends it back via `If-Match` when issuing PUT, PATCH, or DELETE. If the current version no longer matches, the server rejects the operation with `412 Precondition Failed`.

For GET, the client sends `If-None-Match` with the previously received ETag. If the resource still has that ETag, the server can return `304 Not Modified` and omit the response body.

## 1. What Is an ETag?

An ETag (Entity Tag) is an HTTP response header used as a validator for a representation/resource. The server sends an ETag value in the response, and the client stores it and uses that value in subsequent requests.

Illustrative response example:

    HTTP/1.1 200 OK
    Content-Type: application/hal+json
    ETag: "3"

    {
      "id": 1001,
      "name": "An Nguyen",
      "status": "ACTIVE"
    }

The value `"3"` here is only an example. Use the exact value returned by the server, including quotation marks if present. The client should treat the ETag as an opaque token: do not increment, decrement, parse, or reconstruct the value yourself.

ETags serve two common purposes:

1. Comparing resource versions during writes to avoid lost updates.
2. Revalidating caches during reads to avoid re-downloading unchanged representations.

An ETag does not enable long-term caching on its own. Caching policies such as `Cache-Control`, storage lifetime, and where caching is permitted remain separate configuration concerns.

## 2. Linking ETag with @Version

Spring Data REST identifies an entity's version property through Spring Data metadata. When an entity has a version property, that property's value is used as the ETag for the REST resource.

Example with Spring Data JPA:

    import jakarta.persistence.Entity;
    import jakarta.persistence.GeneratedValue;
    import jakarta.persistence.Id;
    import jakarta.persistence.Version;

    @Entity
    public class Customer {

        @Id
        @GeneratedValue
        private Long id;

        @Version
        private Long version;

        private String name;
        private String status;
    }

With Spring Data JPA, use `jakarta.persistence.Version` (or `javax.persistence.Version` in legacy JPA applications). With other Spring Data store modules, use the `org.springframework.data.annotation.Version` annotation according to that module's guidance.

### 2.1. Meaning of the version property

`@Version` marks the property used for optimistic locking. The persistence provider stores the version value in the database and checks it when updating or deleting the entity.

A typical update flow:

1. The entity is read with its current version, for example 3.
2. The client modifies the entity and sends a save request.
3. The persistence provider only updates the row if the ID still matches and the version in the database is still 3.
4. If the update succeeds, the version is incremented, for example to 4.
5. If another transaction has already updated the row earlier, the version condition no longer matches and the current operation fails.

Conceptual SQL illustration:

    UPDATE customer
       SET name = ?, version = 4
     WHERE id = 1001
       AND version = 3;

This is a conceptual description; the actual SQL statement is generated by the persistence provider and may vary by database.

### 2.2. Version types

With JPA, the version property must use a data type supported by Jakarta Persistence for optimistic locking, such as `int`, `Integer`, `long`, `Long`, `short`, `Short`, or `Timestamp` depending on the specification and provider version.

A numeric type such as `Long` is usually easy to observe and suitable for examples:

    @Version
    private Long version;

Do not manually assign or increment the version in business code. Let the persistence provider manage this value. Manually assigning the version can break optimistic locking or make the entity state out of sync with the database.

### 2.3. How are Version and ETag related?

Spring Data REST uses the version property to generate the ETag. Therefore:

- When getting an item resource, the client receives an ETag reflecting the current version.
- When an update succeeds, the version usually increments and the subsequent response includes the new ETag.
- A client still holding an old ETag will know the representation is stale when sending a conditional write.

ETag is the communication part at the HTTP layer. `@Version` is optimistic locking metadata at the persistence layer. They work together, but handle different stages.

## 3. Reading the ETag from a GET Response

Read the item resource and extract the ETag header:

    curl -i       -H "Accept: application/hal+json"       http://localhost:8080/customers/1001

Illustrative response:

    HTTP/1.1 200 OK
    ETag: "3"
    Content-Type: application/hal+json

    {
      "id": 1001,
      "name": "An Nguyen",
      "status": "ACTIVE"
    }

The client must store the ETag associated with the exact resource URI just read. Do not use Customer 1001's ETag for Customer 1002 or for another collection URL.

If a representation is read via a URI with different query parameters or a different projection, keep the ETag tied to the exact request/resource context per the server's contract. Do not mix ETags across different resources or different queries.

## 4. If-Match to Protect PUT, PATCH, and DELETE

`If-Match` is a request header carrying the ETag that the client previously read. The server performs the conditional write only when the resource's current ETag matches the value sent by the client.

For example, the client reads Customer 1001 and receives:

    ETag: "3"

Then the client sends a PATCH:

    curl -i -X PATCH       -H 'If-Match: "3"'       -H "Content-Type: application/merge-patch+json"       -H "Accept: application/hal+json"       -d '{"status":"INACTIVE"}'       http://localhost:8080/customers/1001

If the current ETag is still `"3"`, the condition can be accepted and the update is executed. A successful response may provide a new ETag, for example `"4"`.

`If-Match` can also be used with PUT or DELETE:

    curl -i -X PUT       -H 'If-Match: "3"'       -H "Content-Type: application/json"       -d '{"name":"An Nguyen","status":"ACTIVE"}'       http://localhost:8080/customers/1001

    curl -i -X DELETE       -H 'If-Match: "3"'       http://localhost:8080/customers/1001

The examples only illustrate the headers and request flow. PUT/PATCH bodies must follow the representation, media type, and mapping supported by the actual application.

### 4.1. When the ETag is stale

Suppose two clients simultaneously read Customer when the version is 3:

1. Client A receives ETag `"3"`.
2. Client B also receives ETag `"3"`.
3. Client A updates successfully; the version transitions to 4.
4. Client B still holds ETag `"3"`.
5. Client B sends PUT/PATCH/DELETE with `If-Match: "3"`.
6. The current ETag does not match, so Spring Data REST rejects the request with `412 Precondition Failed`.

Illustrative response:

    HTTP/1.1 412 Precondition Failed

Client B should not automatically change the header to `"4"` and resend the same body immediately. B needs to GET the resource again, inspect A's changes, merge the data according to business rules, and then send a new request with the current ETag.

### 4.2. Why send If-Match?

If a client reads a stale representation and sends an update without carrying a validator, newer data can be overwritten depending on the request semantics.

`If-Match` makes the intent explicit: perform the change only if the resource is still at the version the client observed.

Conditional writes should be applied to operations where overwriting someone else's changes causes data loss or creates an invalid business state. The client must explicitly handle precondition failure rather than retrying infinitely automatically.

## 5. If-None-Match for Cache Validation on GET

`If-None-Match` is used for conditional reads. The client sends the previously received ETag:

    curl -i       -H 'If-None-Match: "3"'       -H "Accept: application/hal+json"       http://localhost:8080/customers/1001

If the current ETag still matches, Spring Data REST can return:

    HTTP/1.1 304 Not Modified
    ETag: "3"

A 304 response does not resend the representation body. The client keeps its cached copy and continues using it.

If the resource has changed, the server returns the new representation along with the new ETag, for example:

    HTTP/1.1 200 OK
    ETag: "4"
    Content-Type: application/hal+json

    {
      "id": 1001,
      "name": "An Nguyen",
      "status": "INACTIVE"
    }

This flow reduces bandwidth and transfer time when clients frequently read resources whose content changes infrequently.

### 5.1. ETag does not mean Cache-Control

ETag indicates whether a representation matches the validator sent by the client. `Cache-Control` determines how caches are allowed to store and reuse the response.

Examples of common directives:

- `Cache-Control: no-store`: do not store the response in a cache.
- `Cache-Control: no-cache`: may be stored, but must be revalidated before reuse.
- `Cache-Control: private`: only client-private cache, not for shared caches.
- `Cache-Control: max-age=60`: the response may be considered fresh for 60 seconds under HTTP caching rules.

Do not add long cache lifetimes simply because a response has an ETag. Sensitive or access-controlled data may require stricter caching policies.

## 6. If-Modified-Since and Last-Modified

Spring Data REST also supports conditional requests based on modification time:

- `Last-Modified` is a response header indicating when the resource was last modified.
- `If-Modified-Since` is a request header for the client to ask whether the resource has changed since that timestamp.

With Spring Data auditing, you can annotate a property with `@LastModifiedDate` and enable auditing with the appropriate configuration.

Example:

    @Entity
    public class Customer {

        @Id
        private Long id;

        @Version
        private Long version;

        @LastModifiedDate
        private Instant lastModifiedDate;
    }

The following request can receive 304 if the resource has not changed since the sent timestamp:

    curl -i       -H 'If-Modified-Since: Wed, 11 Nov 2026 09:00:00 GMT'       http://localhost:8080/customers/1001

ETag and Last-Modified are two different validators. ETag is usually more suitable when an exact version token is needed; timestamps have resolution and update behavior that depend on the system. Do not fabricate or modify header values; use the values returned by the server.

## 7. ETag, Optimistic Locking, and Transactions

Two situations must be distinguished:

### 7.1. ETag mismatch before executing the operation

Spring Data REST compares the request ETag with the current version. If the `If-Match` condition is not satisfied, the request is rejected with `412 Precondition Failed` before the update/delete is accepted.

This is a check at the HTTP boundary and helps the client recognize that the representation is stale.

### 7.2. Data changes after the ETag check

A race can occur between the time Spring Data REST checks the ETag and the time the persistence provider writes the data. Another transaction may modify the row during that interval.

Optimistic locking in the database/persistence provider continues to check the version in the UPDATE or DELETE statement. If the version no longer matches, the persistence operation can raise an optimistic locking exception and roll back the transaction.

Therefore, ETag does not replace `@Version`; `@Version` still protects persistence when contention occurs at write time. Conversely, `@Version` alone does not give the client an HTTP token to tell that the representation it is editing was already stale before the request began.

### 7.3. Handling optimistic locking exceptions

Depending on the persistence provider, Spring Data module, and exception translation, a conflict may appear as `OptimisticLockingFailureException`, `ObjectOptimisticLockingFailureException`, or the corresponding persistence exception.

When an application uses custom services/controllers, handle the error at the appropriate transaction boundary:

- Let the failing transaction roll back.
- Do not continue using a failed persistence context as if the update succeeded.
- Return an API error with a stable code so the client knows to re-read the resource.
- Do not automatically rewrite the same payload with the new version without merging changes.

With custom exception mapping, distinguish an HTTP precondition failure (412) from an optimistic lock conflict occurring during the write process. The final status must follow the application's API contract and exception handler; do not assume all modules map both situations identically.

## 8. Configuration and Prerequisites

To use version-based ETag in Spring Data REST:

1. The domain type needs a version property annotated appropriately for the persistence module.
2. The repository must be exported as a REST resource.
3. Spring Data REST must recognize the version property via persistent entity metadata.
4. The client must read and store the ETag from the response.
5. The client sends back the exact ETag in `If-Match` when performing conditional writes.
6. The client handles `412 Precondition Failed` by re-reading and merging changes.

Example with Spring Data JPA:

    @Entity
    public class Customer {

        @Id
        @GeneratedValue
        private Long id;

        @Version
        private Long version;

        private String name;
    }

Do not expose the version property in JSON solely so the client can use optimistic locking. Clients should use the HTTP ETag header; this header is the contract intended for conditional requests.

If a resource does not have a version property, you should not assume Spring Data REST can generate a version-based ETag for it. You can design a custom validator in a custom controller or use another suitable conditional request mechanism, but clear configuration and testing are required.

## 9. Common Issues

| Symptom | Cause to check |
|---|---|
| Response lacks expected ETag | Entity is missing a version property or uses the wrong annotation for the module |
| PUT/PATCH/DELETE returns 412 | If-Match is stale or does not match the current version |
| Client overwrites newer changes | Client did not send If-Match or did not handle stale representation |
| GET returns 304 with no body | ETag in If-None-Match matches; use the stored cached copy |
| GET always returns 200 | ETag was not sent, does not match, or endpoint/representation does not support conditional requests as expected |
| Version does not increment | Check persistence mapping and whether the operation actually modified the entity |
| Optimistic locking error occurs at flush/commit | Another transaction modified or deleted the row |
| Client sends a self-constructed ETag and is always rejected | ETag must be copied verbatim from the response |
| Using ETag from another resource | ETag must be tied to the exact URI/representation |
| Cache returns sensitive data or data that is stale for too long | Check Cache-Control, authorization, and cache scope |

## 10. Recommended Client Workflow

A client editing a Customer can implement the following flow:

1. GET `/customers/1001`.
2. Store the body along with the response ETag.
3. Allow the user to edit the data based on the read copy.
4. Send PUT or PATCH with `If-Match` containing the saved ETag.
5. If successful, replace the cached body and ETag with the new response.
6. If receiving 412, GET the resource again and display the conflict for the user to merge.
7. On the next GET, send `If-None-Match` so the server returns 304 if the resource has not changed.

Abbreviated shell flow example:

    # Read and capture the ETag from response headers.
    curl -i http://localhost:8080/customers/1001

    # Update only if the resource still has the observed version.
    curl -i -X PATCH       -H 'If-Match: "3"'       -H "Content-Type: application/merge-patch+json"       -d '{"status":"INACTIVE"}'       http://localhost:8080/customers/1001

    # Revalidate a cached representation.
    curl -i       -H 'If-None-Match: "4"'       http://localhost:8080/customers/1001

The ETags `"3"` and `"4"` are illustrative values only. In a real application, retrieve the value from the corresponding response header.

## 11. Testing ETag and @Version

An integration test should verify both HTTP headers and persistence behavior.

Cases that should be covered:

| Case | What to verify |
|---|---|
| GET resource with @Version | Response includes an ETag reflecting the version |
| PATCH with current ETag | Request executes and a new version/ETag is returned |
| PUT with stale ETag | Server returns 412 and newer data is not overwritten |
| DELETE with stale ETag | Server rejects the delete operation with a precondition failure |
| GET with matching If-None-Match | Server returns 304 without sending the representation body |
| GET with stale If-None-Match | Server returns the new representation and current ETag |
| Two concurrent update transactions | Only one update based on the same version can succeed |
| Omitting If-Match | Verify behavior matches the API contract and persistence layer optimistic locking |
| Resource without @Version | Verify no reliance on version-based ETag |
| Cache-Control configured | Cache behavior matches data sensitivity and access permissions |

Illustrative MockMvc example:

    mockMvc.perform(get("/customers/{id}", customerId))
        .andExpect(status().isOk())
        .andExpect(header().exists("ETag"));

    mockMvc.perform(patch("/customers/{id}", customerId)
            .header("If-Match", currentEtag)
            .contentType("application/merge-patch+json")
            .content("{\"status\":\"INACTIVE\"}"))
        .andExpect(status().isOk());

    mockMvc.perform(get("/customers/{id}", customerId)
            .header("If-None-Match", updatedEtag))
        .andExpect(status().isNotModified());

Assertions on status and media type must match the actual Spring Data REST configuration. Test stale ETags separately by resending the old ETag after a successful update and verifying a 412 response.

## 12. Implementation Checklist

1. Add a version property to the entity and use the correct @Version annotation for the persistence module.
2. Let the persistence provider manage the version; do not manually increment the version in business code.
3. GET the item resource and store the ETag verbatim from the response header.
4. Send If-Match on PUT, PATCH, or DELETE when protection against stale updates is needed.
5. Handle 412 by re-GETting, comparing, and merging changes.
6. Send If-None-Match when revalidating a cached GET representation.
7. Handle 304 by using the cached representation.
8. Distinguish ETag from Last-Modified and Cache-Control.
9. Keep @Version so the persistence layer detects races occurring at write time.
10. Do not mix ETags across different resource URIs or queries.
11. Define API behavior when If-Match is missing and when an optimistic locking exception occurs.
12. Test response headers, stale writes, concurrent transactions, and cache behavior.
