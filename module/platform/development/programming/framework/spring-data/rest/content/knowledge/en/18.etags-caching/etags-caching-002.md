# Distinguishing Between JPA and Spring Data `@Version` Annotations

In Spring applications, the `@Version` annotation is used to support optimistic locking: detecting whether a record has been modified after a client or transaction read it. However, there are two annotations with the same name belonging to two different ecosystems:

- `jakarta.persistence.Version` belongs to Jakarta Persistence (JPA) and is used by persistence providers such as Hibernate.
- `org.springframework.data.annotation.Version` belongs to Spring Data Commons and is used by Spring Data modules such as JDBC and MongoDB according to each module's mapping metadata.

The two annotations express the same versioning concept, but they are not interchangeable names for each other. Choose the annotation according to the persistence technology managing the entity. For Spring Data JPA repositories, use the JPA annotation; for Spring Data JDBC or MongoDB, use the corresponding Spring Data annotation.

## 1. What Problem Does Optimistic Locking Solve?

Suppose two users simultaneously open a product record when the current version is 4. User A changes the name and saves first. Then user B submits a change based on the stale data they read.

If the server writes only by ID, B's operation can overwrite A's newer change without detecting a conflict. This is a lost update.

Optimistic locking attaches a version to the record. When reading, the application receives the current version; when writing, the persistence layer updates only if the version in the database still equals the version the transaction read. If another transaction updated first, the version condition no longer matches and the stale write is rejected.

```text
Initial state: database version = 4

Client A reads version 4
Client B reads version 4

Client A updates:
  UPDATE ... WHERE id = 42 AND version = 4
  Succeeds; version increments to 5

Client B updates:
  UPDATE ... WHERE id = 42 AND version = 4
  No row matches version 4
  => optimistic locking conflict detected
```

This mechanism is suitable when write conflicts do not happen frequently and there is no need to lock the database for the entire duration of user editing. It does not hold a row lock from read time to write time; instead, it detects conflicts at write time.

## 2. JPA @Version: jakarta.persistence.Version

For entities managed by JPA, use the `jakarta.persistence.Version` annotation. In legacy JPA applications prior to Jakarta EE 9, the corresponding package is `javax.persistence.Version`.

JPA entity example:

```java
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import jakarta.persistence.Version;

@Entity
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    @Version
    private Long version;

    // getters and setters
}
```

The JPA persistence provider manages the version property. When the entity is persisted or updated, the provider uses the version to detect conflicts and updates the version according to the persistence provider's rules.

During an update, the SQL generated by the provider typically takes this conceptual form:

```sql
UPDATE product
SET name = ?, version = 5
WHERE id = 42 AND version = 4;
```

If another transaction already changed the version to 5 earlier, the statement with the condition `version = 4` updates zero rows. The provider detects the conflict and raises an optimistic locking error, typically via `OptimisticLockException` or an exception translated by Spring into `OptimisticLockingFailureException`.

A few points to remember:

- The property annotated with `@Version` must belong to a JPA entity managed by the persistence context.
- The JPA provider is responsible for reading, checking, and incrementing the version; the application should not manually increment or assign the version as a business field.
- A JPA entity has a single designated version property according to JPA rules.
- The version property type must be a type supported by JPA, such as `int`, `Integer`, `long`, `Long`, or `Timestamp` depending on the specification version in use.
- If fine-grained lock mode control is needed for a query, JPA also provides `LockModeType.OPTIMISTIC` and related lock modes; these are separate lock configurations and do not replace the version property.

## 3. Spring Data @Version: org.springframework.data.annotation.Version

Spring Data Commons defines the `org.springframework.data.annotation.Version` annotation. Spring Data modules can read this annotation from mapping metadata to perform optimistic locking using the corresponding datastore's mechanism.

Example with Spring Data JDBC:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.relational.core.mapping.Table;

@Table("orders")
public class Order {

    @Id
    private Long id;

    private String reference;

    @Version
    private Long version;

    // getters and setters
}
```

Here, the entity is mapped by Spring Data JDBC, not as a JPA entity. Spring Data JDBC uses the version property to check state when updating or deleting an aggregate. When the current version does not match the version carried by the entity, the operation can fail with `OptimisticLockingFailureException`.

With Spring Data MongoDB, the same Spring Data annotation can be used on a document:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.mongodb.core.mapping.Document;

@Document("customers")
public class Customer {

    @Id
    private String id;

    private String name;

    @Version
    private Long version;

    // getters and setters
}
```

Spring Data MongoDB includes the version in the document update condition and increments the version upon write according to the module's semantics. If the document has already been updated by another operation, a write based on the stale version can be rejected.

The same Spring Data Commons annotation is used by multiple modules, but how it is executed in JDBC, MongoDB, or other datastores depends on that module's implementation. Do not infer that every module generates SQL or has identical persistence behavior.

## 4. Comparing the Two Annotations

| Criterion | JPA @Version | Spring Data @Version |
|---|---|---|
| Package | `jakarta.persistence.Version`; legacy JPA uses `javax.persistence.Version` | `org.springframework.data.annotation.Version` |
| Metadata owner | Jakarta Persistence | Spring Data Commons |
| Persistence technology | Entities managed by a JPA provider | Spring Data mapping modules that support versioning |
| Common examples | Spring Data JPA with Hibernate | Spring Data JDBC, Spring Data MongoDB |
| How version is checked | Performed by the JPA provider during the persistence lifecycle | Performed by the corresponding Spring Data module per datastore |
| Common error | `OptimisticLockException`, which may be translated by Spring | Usually `OptimisticLockingFailureException` |
| Directly interchangeable? | No | No |

Having the same class name does not mean they belong to the same annotation type. Java distinguishes annotations by their fully qualified package name. If you import the wrong one, the persistence module may fail to recognize the version metadata it requires.

## 5. Choosing the Right Annotation by Repository

Start from the persistence technology that actually manages the entity:

| Repository type | Appropriate version annotation |
|---|---|
| `JpaRepository` with a JPA entity | `jakarta.persistence.Version` (or `javax.persistence.Version` for legacy JPA) |
| `CrudRepository` / `Repository` using Spring Data JDBC | `org.springframework.data.annotation.Version` |
| Spring Data MongoDB repository | `org.springframework.data.annotation.Version` |
| Other Spring Data modules | Check whether the module supports version metadata and its specific implementation |

Whether a repository interface extends `CrudRepository` is not enough to determine the annotation. Spring Data JPA also provides repository abstractions built on common Spring Data interfaces. Check which module configures the repository and whether the entity is mapped by JPA, JDBC, or MongoDB.

Do not place both annotations on the same property hoping to increase compatibility. That makes metadata confusing and does not cause persistence providers to automatically share the same versioning mechanism.

## 6. What Does the Application Receive When a Conflict Occurs?

Suppose two requests update the same product:

1. Both read the entity with version 4.
2. Request A saves first; the version is incremented to 5.
3. Request B still carries version 4 and attempts to save.
4. The persistence layer detects the version mismatch and rejects B's operation.

In Spring Data JPA, the error can originate from `jakarta.persistence.OptimisticLockException` and be translated by Spring into an optimistic locking exception. With Spring Data JDBC/MongoDB, the corresponding module typically throws `OptimisticLockingFailureException`.

When exposed through Spring Data REST, the specific HTTP status depends on exception mapping and application configuration. Conflicts are commonly represented as `409 Conflict`; if the API uses conditional requests such as ETag/If-Match, a condition that is no longer true can be represented with `412 Precondition Failed`. Clients should inspect the status and response body according to the API contract.

Clients should not automatically resend the same stale payload immediately upon encountering a conflict. The appropriate handling is usually to read the latest representation, allow the user or business logic to reconcile changes, and then submit a new update based on the current version.

## 7. @Version Does Not Equal ETag or If-Match

A version property is concurrency metadata at the persistence layer. ETag and If-Match are HTTP conditional request mechanisms. They can be combined, but they are not automatically the same thing.

- `@Version` enables the persistence layer to detect a write based on a stale version.
- ETag is a representation validator published by the HTTP server.
- `If-Match` lets the client ask the server to process the request only if the validator still matches.
- Having a version field on an entity does not automatically guarantee that Spring Data REST emits the corresponding ETag or automatically checks If-Match.

If an API wants to use ETags, validator generation, condition comparison, and error mapping at the HTTP layer must be configured and tested. Do not assume a version value in JSON is a valid ETag if the server has not defined that contract.

Similarly, do not treat the version field as data that the client can arbitrarily overwrite. The persistence layer needs to manage the version. If the field is included in the representation for client observation, clearly define deserialization behavior and prevent clients from overwriting the version via appropriate API configuration.

## 8. Transactions and Limitations of Optimistic Locking

Optimistic locking protects write operations where the persistence layer actually checks the version. It does not automatically protect every change outside the database.

Several limitations to keep in mind:

- If the application updates data using native SQL or bulk updates that bypass the ORM's version mechanism, the version may not be checked or incremented as expected.
- If multiple tables or aggregates are related, one entity's version does not necessarily represent the entire related business state.
- If external side effects outside the database already executed before the transaction rolled back due to a version conflict, those side effects may not be automatically rolled back.
- If a client reads a representation long before writing, the probability of conflict increases; the application needs to notify and support reconciliation.
- Optimistic locking does not replace validation, authorization, unique constraints, or foreign keys.

For tasks that send messages, emails, or call payment services, define transaction boundaries and design deduplication/outbox patterns if operations can be retried. Version checking only solves stale write detection at the persistence layer.

## 9. Implementation Checklist

1. Identify whether the repository uses Spring Data JPA, JDBC, or MongoDB.
2. For JPA entities, import `jakarta.persistence.Version`; for Spring Data mapping modules that support versioning, import `org.springframework.data.annotation.Version`.
3. Choose a version type supported by the persistence technology.
4. Let the persistence provider/module manage incrementing the version; do not use the version as a business field.
5. Test two transactions or two clients reading the same version and updating concurrently.
6. Verify optimistic locking exceptions are handled properly at the service and HTTP layers.
7. If ETag/If-Match is needed, configure conditional requests separately and test the responses.
8. Do not let bulk/native updates or external side effects accidentally bypass the concurrency policy.
9. Document for clients how to handle conflicts: re-read, reconcile, and submit new changes.

`jakarta.persistence.Version` and `org.springframework.data.annotation.Version` both support the concept of optimistic locking, yet belong to two different metadata systems. Choose the annotation based on the persistence module managing the entity so that the version is checked and updated in the right place. With Spring Data REST, combine conflict handling at the HTTP layer and guide clients to re-read the latest state when an update based on a stale version is rejected.
