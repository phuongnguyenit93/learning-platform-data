# Deploying Spring Data REST Behind a Reverse Proxy with Context Path and Base Path

## Objective

When Spring Data REST runs behind Nginx, Apache HTTP Server, a load balancer, or an ingress controller, the application often sees requests arriving from an internal address such as `http://127.0.0.1:8080`. External clients, however, access it over HTTPS, a public hostname, and possibly a URL prefix such as `https://api.example.com/api`.

If the proxy forwards the request without Spring receiving information about the original address, URLs generated in responses can be wrong: HAL `href` links pointing to the internal host, using `http` instead of `https`, missing a path prefix, or duplicating the context path. These issues affect `self`, collection, item, association, profile, and pagination links as well as the `Location` header.

This guide explains how to distinguish the three path types, configure a proxy to send forwarded headers, enable forwarded header handling in Spring Boot, and verify the links generated by Spring Data REST.

## 1. Distinguishing Context Path, Spring Data REST Base Path, and Proxy Prefix

The three configurations serve different purposes:

| Component | Configuration | Scope |
|---|---|---|
| Servlet context path | `server.servlet.context-path` | Prefix of the entire Servlet application |
| Spring Data REST base path | `spring.data.rest.base-path` | Prefix specifically for repository resources exported by Spring Data REST |
| Public proxy prefix | `X-Forwarded-Prefix` header or equivalent configuration | Prefix clients use to access the API through the proxy |

Example:

- Internal Servlet context path: `/app`.
- Spring Data REST base path: `/rest`.
- Proxy exposes the API publicly under prefix: `/api`.

When prefixes are composed according to this design, the collection resource can be accessed publicly at `https://api.example.com/api/rest/categories`, while the proxy forwards the request to the internal path `/app/rest/categories`.

Do not configure the same prefix across multiple layers without deciding which layer owns that prefix. If the proxy, servlet context, and Spring Data REST all add `/api`, the URL can become `/api/api/api`. Conversely, if the proxy strips a prefix without the application receiving `X-Forwarded-Prefix`, generated links can miss the public path segment.

### 1.1. Servlet Context Path

In a Spring Boot Servlet application, configure:

```properties
server.servlet.context-path=/app
```

The context path applies to the entire application deployed on the servlet container. It affects Spring MVC controllers, Spring Data REST, and other servlet endpoints alike.

### 1.2. Spring Data REST Base Path

You can separately set the root URI for repository resources:

```properties
spring.data.rest.base-path=/rest
```

Then, if the application has no servlet context path, a repository with collection path `/categories` is exported under `/rest/categories`. This setting does not change the context path of other controllers.

With Spring Boot, `spring.data.rest.base-path` is the property corresponding to Spring Data REST's base path configuration. In older API examples, documentation may show camel case `basePath` in `application.properties`; Spring Boot relaxed binding allows using the current kebab-case form.

### 1.3. Reverse Proxy Public Prefix

Suppose the proxy receives requests at `/api/...` but forwards requests to the application with internal prefix `/app/...`. The proxy can send:

```http
X-Forwarded-Host: api.example.com
X-Forwarded-Proto: https
X-Forwarded-Port: 443
X-Forwarded-Prefix: /api
```

`X-Forwarded-Prefix` describes the public prefix seen by the client. Spring Framework supports standard RFC 7239 `Forwarded` headers and common `X-Forwarded-*` headers. How the proxy adds, replaces, or strips a prefix must match how the proxy rewrites the request path.

## 2. Request Flow Behind a Reverse Proxy

Deployment example:

```text
Client
  https://api.example.com/api/rest/categories
       |
       v
Reverse proxy (Nginx)
  public prefix: /api
  forwards to:   http://127.0.0.1:8080/app/rest/categories
  adds forwarded host/proto/port/prefix headers
       |
       v
Spring Boot application
  servlet context path: /app
  Spring Data REST base path: /rest
  repository collection: /categories
       |
       v
HAL response with public links
  https://api.example.com/api/rest/categories/...
```

Spring Data REST uses HAL by default to represent resources and discover links. The root resource contains relations such as collections and `profile`; item resources can contain links to associations. Therefore, Spring needs to know the public host, scheme, port, and prefix to build URLs directly usable by clients.

## 3. Configuring Spring Boot to Handle Forwarded Headers

Spring Boot provides the property:

```properties
server.forward-headers-strategy=FRAMEWORK
```

On the Servlet stack, the `FRAMEWORK` value uses Spring Framework's `ForwardedHeaderFilter`. The filter wraps the request so the application sees the original details forwarded by the proxy. It must run before filters that need to read the adjusted request.

Two main strategies to distinguish:

- `NATIVE`: delegates forwarded header handling to the web server/container. Choose this when the container fully supports the headers needed in your deployment.
- `FRAMEWORK`: uses Spring Framework's mechanism. For a Spring MVC Servlet application, this mechanism is `ForwardedHeaderFilter`.

Do not assume every container supports the same set of headers. In particular, verify support for `X-Forwarded-Prefix` when the public path and internal context path differ.

Example YAML configuration for an application using both a context path and a Spring Data REST base path:

```yaml
server:
  servlet:
    context-path: /app
  forward-headers-strategy: framework
  tomcat:
    redirect-context-root: false

spring:
  data:
    rest:
      base-path: /rest
```

In this example:

- `context-path` is `/app`.
- repository resources start under `/rest`.
- `forward-headers-strategy` enables processing of information sent by the proxy.
- `server.tomcat.redirect-context-root=false` is a setting to consider when using Tomcat with TLS terminated at the proxy, so `X-Forwarded-Proto` is respected before redirects at the context root.

Do not copy this configuration verbatim into every system. If the proxy preserves the path and the container already handles the required headers properly, the `NATIVE` strategy may fit. If the application uses Jetty or Tomcat, check the header support specifics for your container and Spring Boot version.

## 4. Configuring Nginx as a Reverse Proxy

The following example assumes:

- The client calls `https://api.example.com/api/rest/categories`.
- Nginx receives requests under `/api/`.
- Spring Boot runs at `127.0.0.1:8080` with context path `/app`.
- Nginx replaces the `/api` prefix with `/app` when forwarding requests to the upstream.

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8080/app/;

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port $server_port;
        proxy_set_header X-Forwarded-Prefix /api;
        proxy_set_header X-Forwarded-For $remote_addr;
    }
}
```

The trailing slash in `location /api/` and the `proxy_pass` URI matters because Nginx replaces the URI portion matching the location with the URI declared in `proxy_pass`. Verify actual rewrite rules before applying them to a running configuration.

If the proxy does not replace `/api` with `/app`, adjust `proxy_pass` and the forwarded prefix accordingly. Never send a prefix describing a public URL that does not match the path the proxy actually serves.

Meaning of the example headers:

- `Host` and `X-Forwarded-Host`: the hostname used by the client.
- `X-Forwarded-Proto`: the public scheme, usually `https` when TLS terminates at the proxy.
- `X-Forwarded-Port`: the public port.
- `X-Forwarded-Prefix`: the public path prefix.
- `X-Forwarded-For`: the client address along the trusted proxy chain.

If multiple proxies are chained, explicitly design which proxy is allowed to append and preserve each part of the forwarded chain. Configuration at the edge proxy must overwrite or strip forwarded headers sent by external clients, then regenerate trusted values. Using `$remote_addr` above suits a simple single edge proxy; for multiple hops, adjust according to your topology and trusted proxy list.

## 5. When Is X-Forwarded-Prefix Needed?

Spring Framework describes three common scenarios:

| Scenario | Public URL | Internal URL | X-Forwarded-Prefix |
|---|---|---|---|
| Replace prefix | `/api/{path}` | `/app1/{path}` | `/api` |
| Strip internal prefix | `{path}` | `/app1/{path}` | empty prefix |
| Add public prefix | `/api/app1/{path}` | `/app1/{path}` | `/api/app1` |

Prefix replacement example:

```text
https://example.com/api/categories
             |
             | proxy maps /api to /app1
             v
http://localhost:8080/app1/categories
```

The proxy sends `X-Forwarded-Prefix: /api` so the request is recognized under the public prefix `/api`. The case of stripping an internal prefix can send an empty value to override `/app1`. The case of adding a public prefix can send `/api/app1`.

Do not add `X-Forwarded-Prefix` mechanically. First determine whether the proxy is preserving, replacing, or removing a prefix. If the prefix is misconfigured, requests may still reach the controller while HAL links lead to unreachable URLs.

## 6. Verifying HAL Links After Deployment

After the application starts and the proxy reloads, call the public URL:

```bash
curl -i   -H "Accept: application/hal+json"   https://api.example.com/api/rest
```

Verify the response has `200 OK` and `Content-Type: application/hal+json`. In the JSON, links must use the public hostname, public scheme, and correct path prefix.

Example expected root representation:

```json
{
  "_links": {
    "categories": {
      "href": "https://api.example.com/api/rest/categories"
    },
    "profile": {
      "href": "https://api.example.com/api/rest/profile"
    }
  }
}
```

Actual relation names and links depend on exported repositories. The example only illustrates how to verify generated URLs.

Also verify a collection resource:

```bash
curl -i   -H "Accept: application/hal+json"   "https://api.example.com/api/rest/categories?page=0&size=5"
```

Inspect `self`, `next`, `prev`, and `profile` relations if present. Every `href` must be reachable through the public proxy. Do not check only the initial request URL: a successful GET can still return a HAL document with links pointing to an internal address.

For creation operations, also check the `Location` header:

```bash
curl -i -X POST https://api.example.com/api/rest/categories   -H "Content-Type: application/json"   -H "Accept: application/hal+json"   --data '{"code":"BOOKS","name":"Books"}'
```

If the response returns `201 Created`, `Location` should be a public URI that can be used to GET the newly created resource. Specific status codes and bodies also depend on Spring Data REST and repository configuration.

## 7. Testing and Diagnostics

You should test through two paths:

1. **Direct backend:** confirm the application responds at the expected internal address and path.
2. **Public proxy URL:** confirm routing, forwarded headers, HTTPS, and HAL links are all correct when clients go through the proxy.

Common symptoms:

| Symptom | Likely Cause to Check |
|---|---|
| Public URL request returns 404 | Nginx `location`, `proxy_pass`, context path, or Spring Data REST base path mismatch |
| Response is 200 but links contain `localhost:8080` | Forwarded host/port not handled or proxy not sending headers |
| HAL links use `http` while client uses HTTPS | `X-Forwarded-Proto` missing/wrong or strategy not handling it |
| Links are missing `/api` | `X-Forwarded-Prefix` missing or not processed |
| Links duplicate `/api` or `/app` | Prefix added in multiple layers or incorrect proxy rewrite |
| Redirect from HTTPS to HTTP | Check forwarded proto and container redirect configuration |
| Collection link is correct but association link is wrong | Check association path, forwarded request context, and custom resource mapping |

Specific checks:

- Check proxy logs to see the original path and the path sent to upstream.
- Check `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-Port`, and `X-Forwarded-Prefix` at the upstream.
- Verify Spring Boot is using the intended `server.forward-headers-strategy`.
- If using Tomcat, verify the proxy belongs to the trusted internal proxies set; do not set the internal proxies list to empty in production.
- Check both URLs inside HAL responses and `Location` on POST/PUT.
- Check pagination links when query parameters are present and when following the `next` link to the next page.
- Confirm controller endpoints outside Spring Data REST remain reachable under the expected path.

### 7.1. Testing with Forwarded Headers

You can write an integration test using Spring Boot and MockMvc to send forwarded headers and verify generated links. The test must run with the corresponding forwarded header filter configuration:

```java
@SpringBootTest
@AutoConfigureMockMvc
class ForwardedLinksIntegrationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void rendersLinksUsingPublicRequestInformation() throws Exception {
        mockMvc.perform(get("/app/rest/categories")
                .header("X-Forwarded-Host", "api.example.com")
                .header("X-Forwarded-Proto", "https")
                .header("X-Forwarded-Port", "443")
                .header("X-Forwarded-Prefix", "/api")
                .accept(MediaType.parseMediaType("application/hal+json")))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(
                MediaType.parseMediaType("application/hal+json")));
    }
}
```

The example above illustrates the request context and response media type; to verify exact URLs, parse the JSON response and assert `_links.*.href` values according to your actual topology. MockMvc does not replace testing Nginx or a load balancer: it does not verify rewrite rules, TLS termination, or that the proxy overwrites untrusted headers.

## 8. Securing Forwarded Headers

Forwarded headers are only trustworthy when added by proxies within your managed scope. Clients can send `Forwarded` or `X-Forwarded-*` themselves; if the application trusts those values directly, a client can alter the hostname, scheme, port, or prefix the application uses to build URLs.

Follow these principles:

1. Only allow backend access from trusted proxies/load balancers when the architecture requires going through a proxy.
2. At the edge proxy, strip or overwrite forwarded headers sent by clients from the Internet before creating internal headers.
3. Choose `NATIVE` or `FRAMEWORK` according to the container and the set of headers to support.
4. With Tomcat, properly configure the list of internal proxies. Never trust all proxies in production.
5. If you need to strip forwarded headers without using them, Spring `ForwardedHeaderFilter` has a `removeOnly` mode.
6. Never allow a client to reach the backend directly and self-declare host/proto/prefix if the backend trusts forwarded headers from a proxy.

Spring Framework emphasizes that proxies at the trust boundary must strip untrusted forwarded headers. This is critical to prevent generating absolute links or redirects based on client-spoofed hosts.

## 9. Pre-Production Checklist

- [ ] Public URL and upstream URL are clearly defined.
- [ ] Servlet context path, Spring Data REST base path, and proxy prefix are distinguished.
- [ ] Proxy rewrites the request path exactly once.
- [ ] Proxy sends the correct public host, proto, port, and prefix.
- [ ] Edge proxy overwrites or strips client-supplied forwarded headers.
- [ ] Spring Boot enables the strategy suited to the web server and forwarded headers in use.
- [ ] With Tomcat terminating TLS at the proxy, `server.tomcat.redirect-context-root=false` has been evaluated.
- [ ] Root HAL links point to the public hostname and HTTPS.
- [ ] Collection, item, association, profile, and pagination links are all reachable.
- [ ] The `Location` header after resource creation is a public URL.
- [ ] Requests have been tested through the real proxy, not only MockMvc.
- [ ] Confirmed the backend cannot be accessed directly outside intended paths.
