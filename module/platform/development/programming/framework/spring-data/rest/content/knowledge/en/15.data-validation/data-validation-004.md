# Registering Validators with beforeCreate and beforeSave Bean Prefixes

## Objectives

After this lesson, you can:

- Explain at which points in the resource lifecycle Spring Data REST invokes validators.
- Register a validator using a bean name with the **beforeCreate** or **beforeSave** prefix.
- Write a validator implementing the **org.springframework.validation.Validator** interface.
- Use **supports**, **validate**, and **Errors** to validate data.
- Distinguish creation rules from rules before saving/updating.
- Test validation over HTTP and know when to use manual registration.

## 1. Why Are Validators Needed in Spring Data REST?

Spring Data REST automatically exposes repositories as an HTTP API. Clients can send POST requests to create entities or PUT/PATCH requests to modify an existing entity. Before data is persisted, the application needs to check business rules such as:

- Name is required.
- Email must be provided when creating an account.
- Age or quantity must not be negative.
- The new state must be compatible with the current state.
- A field must not be changed after the resource has been created.

Spring Data REST provides a validation mechanism tied to repository events. You can register a **Validator** for a specific event to check the entity at the appropriate time. This mechanism is useful when you want to control incoming data through REST endpoints generated by Spring Data REST.

## 2. Two Important Bean Prefixes

The simplest way to register a validator is to name the bean according to the pattern:

~~~text
<event><DomainType>Validator
~~~

Where:

- **event** is the event prefix recognized by Spring Data REST.
- **DomainType** is the domain class name, typically the simple class name starting with an uppercase letter.
- **Validator** is an easily recognizable suffix for the bean.

For example, with the **Person** domain class:

| Bean Name | Bound Event | When Used |
|---|---|---|
| **beforeCreatePersonValidator** | **beforeCreate** | Before creating a new Person |
| **beforeSavePersonValidator** | **beforeSave** | Before saving a Person |

The two prefixes represent two different events:

- **beforeCreate** is used for rules that apply only when creating a new resource, typically a POST request to the collection.
- **beforeSave** is used for rules that need to run before saving a resource, commonly encountered when updating an item via PUT or PATCH.

Do not name a bean arbitrarily and expect Spring Data REST to guess the event. The prefix must match the event name exactly; the domain type part must also match the class supported by the validator.

## 3. Which Interface Must a Validator Implement?

Spring Data REST uses Spring Framework's **org.springframework.validation.Validator** interface.

A validator has two main methods:

~~~java
public interface Validator {

    boolean supports(Class<?> clazz);

    void validate(Object target, Errors errors);
}
~~~

Meaning:

- **supports(Class<?> clazz)** indicates whether the validator handles the given object type.
- **validate(Object target, Errors errors)** validates the object and records errors in the Errors object if the data is invalid.

When there is an error, use **errors.rejectValue(...)** to associate the error with a specific property. Spring Data REST reads these errors during event processing and prevents invalid data from continuing to be saved.

You should not build an HTTP response directly from the validator. The validator is only responsible for checking data and recording errors; the Spring Data REST layer handles the validation result.

## 4. Registering a Validator for beforeCreate

Suppose the Person entity has name, email, and age:

~~~java
public class Person {

    private Long id;
    private String name;
    private String email;
    private Integer age;

    // Constructors, getters and setters
}
~~~

Create a validator that runs before creating a new entity:

~~~java
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.validation.Errors;
import org.springframework.validation.Validator;

@Component("beforeCreatePersonValidator")
public class BeforeCreatePersonValidator implements Validator {

    @Override
    public boolean supports(Class<?> clazz) {
        return Person.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Person person = (Person) target;

        if (!StringUtils.hasText(person.getName())) {
            errors.rejectValue(
                "name",
                "person.name.required",
                "Name must not be blank"
            );
        }

        if (!StringUtils.hasText(person.getEmail())) {
            errors.rejectValue(
                "email",
                "person.email.required",
                "Email is required when creating a new record"
            );
        }

        if (person.getAge() == null || person.getAge() < 0) {
            errors.rejectValue(
                "age",
                "person.age.invalid",
                "Age must be a non-negative number"
            );
        }
    }
}
~~~

The key part is the bean name:

~~~java
@Component("beforeCreatePersonValidator")
~~~

Spring Data REST recognizes the **beforeCreate** prefix, determines the event to bind to, and associates the validator with the Person domain type.

This validator focuses on data required upon creation. For example, if an email is required when registering a new Person, that rule can be placed in beforeCreate.

If the bean is created with a **@Bean** method, the method name itself is also the default bean name:

~~~java
@Bean
Validator beforeCreatePersonValidator() {
    return new BeforeCreatePersonValidator();
}
~~~

Choose one registration approach that fits your application structure: **@Component** or **@Bean**. There is no need to create two beans with the same name.

## 5. Registering a Validator for beforeSave

When updating an existing Person, the application may need to check rules before saving. Create a separate validator:

~~~java
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.validation.Errors;
import org.springframework.validation.Validator;

@Component("beforeSavePersonValidator")
public class BeforeSavePersonValidator implements Validator {

    @Override
    public boolean supports(Class<?> clazz) {
        return Person.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Person person = (Person) target;

        if (!StringUtils.hasText(person.getName())) {
            errors.rejectValue(
                "name",
                "person.name.required",
                "Name must not be blank"
            );
        }

        if (person.getAge() != null && person.getAge() < 18) {
            errors.rejectValue(
                "age",
                "person.age.minimum",
                "Age must be 18 or older"
            );
        }
    }
}
~~~

Bean name:

~~~java
@Component("beforeSavePersonValidator")
~~~

The **beforeSave** prefix binds the validator to the BeforeSave event. The rule in the example requires a Person to be at least 18 years old when saved through an update flow.

The two validators can contain different rules:

- beforeCreate checks required data upon registration.
- beforeSave checks conditions that must hold before saving changes.

If a rule must hold at both times, put it in both validators or organize shared logic to avoid code duplication. Do not check only in beforeCreate if that data can still be modified later.

## 6. Naming Convention for Other Domain Types

The event prefix precedes the domain class name. For example, with **PurchaseOrder**:

~~~java
@Component("beforeCreatePurchaseOrderValidator")
public class BeforeCreatePurchaseOrderValidator implements Validator {
    // supports and validate
}
~~~

For the save event:

~~~java
@Component("beforeSavePurchaseOrderValidator")
public class BeforeSavePurchaseOrderValidator implements Validator {
    // supports and validate
}
~~~

Some bean name examples:

| Domain Type | Before Create | Before Save |
|---|---|---|
| Person | **beforeCreatePersonValidator** | **beforeSavePersonValidator** |
| Product | **beforeCreateProductValidator** | **beforeSaveProductValidator** |
| PurchaseOrder | **beforeCreatePurchaseOrderValidator** | **beforeSavePurchaseOrderValidator** |

Use the exact simple class name of the domain type. If the class is named PurchaseOrder, do not name the bean beforeCreateOrderValidator unless the domain type is actually Order.

The **supports** method still needs to check the class. The bean name helps Spring Data REST bind the validator to the event/domain type; supports confirms the validator can handle the received object.

## 7. Manual Registration via RepositoryRestConfigurer

If you do not want to rely on the bean name convention, Spring Data REST allows registering validators directly with **ValidatingRepositoryEventListener**.

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.data.rest.core.event.ValidatingRepositoryEventListener;
import org.springframework.data.rest.webmvc.config.RepositoryRestConfigurer;

@Configuration
public class RestValidationConfiguration
        implements RepositoryRestConfigurer {

    @Override
    public void configureValidatingRepositoryEventListener(
            ValidatingRepositoryEventListener listener) {

        listener.addValidator(
            "beforeCreate",
            new BeforeCreatePersonValidator()
        );

        listener.addValidator(
            "beforeSave",
            new BeforeSavePersonValidator()
        );
    }
}
~~~

The **addValidator(eventName, validator)** method binds the validator to the specified event. The event names here are **beforeCreate** and **beforeSave**.

This is an alternative to bean name registration. If you already use the bean name convention for the same validator, do not manually register the same logic again, as it may cause a rule to run multiple times.

If the application already has a RepositoryRestConfigurer class, add the configuration to the existing class instead of creating multiple competing configurations.

## 8. Bean Name Convention vs. Manual Registration

| Criterion | Bean Name Convention | Manual Registration |
|---|---|---|
| Approach | Name the bean after the event and domain type | Call addValidator in RepositoryRestConfigurer |
| Example | **beforeCreatePersonValidator** | **addValidator("beforeCreate", validator)** |
| Pros | Minimal configuration, easy to find by domain type | Explicit control over how validators are bound |
| Best For | Most standard cases | When centralized registration or conditional configuration is needed |
| Notes | Bean name must follow the convention | Must bind the right event and avoid duplicate registration |

Spring Data REST recommends the bean prefix approach for most scenarios. Manual registration is useful when the application needs centralized validator management or wants to construct validators based on configuration conditions.

## 9. How Does Validation Work in the HTTP Flow?

Suppose PersonRepository is exposed:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository
        extends JpaRepository<Person, Long> {
}
~~~

A client sends a POST request to create a Person:

~~~http
POST /api/people
Content-Type: application/json
Accept: application/hal+json

{
  "name": "",
  "email": "",
  "age": -1
}
~~~

Spring Data REST converts the body into a Person object, publishes the event before creation, and invokes the validator registered for that event. The validator records errors in Errors. When validation errors occur, the save operation is rejected and the response returns error details to the client; the status is typically **400 Bad Request**.

A valid request might look like:

~~~http
POST /api/people
Content-Type: application/json
Accept: application/hal+json

{
  "name": "Lan",
  "email": "lan@example.com",
  "age": 25
}
~~~

For an item update operation:

~~~http
PUT /api/people/42
Content-Type: application/json
Accept: application/hal+json

{
  "name": "Lan Nguyen",
  "email": "lan@example.com",
  "age": 25
}
~~~

The item save flow uses the beforeSave event. The corresponding validator checks the object before changes are persisted.

Error body details may vary depending on the Spring Data REST version, exception handling configuration, and how the application customizes error representations. Clients should check the status code and read the response body instead of relying on a fixed error structure.

## 10. Testing Validators with curl

Try creating invalid data:

~~~bash
curl -i -X POST \
  -H "Accept: application/hal+json" \
  -H "Content-Type: application/json" \
  -d '{"name":"","email":"","age":-1}' \
  http://localhost:8080/api/people
~~~

Observe:

- Whether the status code reports a validation failure.
- Whether the response body indicates which fields are invalid.
- Whether the error messages match what was declared in rejectValue.
- Whether the entity is saved when validation fails.

Then try valid data:

~~~bash
curl -i -X POST \
  -H "Accept: application/hal+json" \
  -H "Content-Type: application/json" \
  -d '{"name":"Lan","email":"lan@example.com","age":25}' \
  http://localhost:8080/api/people
~~~

Read the Location header or self link in the response to determine the URI of the newly created Person. Use that URI to test updating with data that violates the beforeSave rule.

Example of updating with an invalid age:

~~~bash
curl -i -X PATCH \
  -H "Accept: application/hal+json" \
  -H "Content-Type: application/merge-patch+json" \
  -d '{"age":16}' \
  http://localhost:8080/api/people/42
~~~

PATCH media types and semantics depend on the application's Spring Data REST configuration. If the API does not enable merge patch, use an update method and Content-Type supported by the API. The purpose of the test is to confirm that the beforeSave validator is invoked in the item save flow.

## 11. Distinguishing Spring Validator and Bean Validation

Spring has several ways to validate data. Do not confuse **org.springframework.validation.Validator** with **Jakarta Bean Validation**.

| Mechanism | Characteristics | Example |
|---|---|---|
| Spring Validator | Write Java logic in supports/validate and record errors via Errors | **beforeCreatePersonValidator** |
| Jakarta Bean Validation | Declare constraints on fields/properties or classes | **@NotBlank**, **@Email**, **@Min** |
| Repository event handler | Handle events by domain type; may serve logic beyond validation | **@HandleBeforeSave** |

Bean Validation is suitable for declarative constraints that can be reused across multiple layers. Spring Validator is suitable for programmatic logic, cross-field validation, or checks that depend on business state.

Both mechanisms can be combined, but you need to understand how they are triggered and configured in the application. Do not assume that merely placing Bean Validation annotations means all Spring Data REST write flows already execute the desired rules.

## 12. Limitations and Usage Guidelines

### Validators Are Tied to Spring Data REST Events

Validators are registered for REST exporter events. They are suitable for protecting write flows through repository resources managed by Spring Data REST.

If another service calls **repository.save(...)** directly, do not assume that validators tied to Spring Data REST events will also be invoked. If a rule must apply to all write flows, place the logic in the domain/service layer or use a validation mechanism appropriate for all entry points.

### Do Not Place Side Effects in Validators

Validators should check data and record errors. Avoid sending emails, calling external systems, writing audit logs, or modifying other data in the validate method. Those side effects are better suited for dedicated services or event handlers after the operation succeeds.

### Do Not Use Validators Instead of Authorization

A validator checks whether data is valid. It does not determine whether a user has permission to modify an entity or field. Authorization must be enforced separately on the server.

### Update Rules May Need to Compare Old State

In beforeSave, the object may already be bound from the request. If a rule needs the value prior to the update, retrieve the old state through a service/repository in a safe and transaction-controlled way. Do not assume a validator always has a snapshot of the entity before changes.

### Check the Right Event

If a validator does not run, verify the bean name, domain type, supports, and whether the repository is discovered by Spring Data REST. If using manual registration, verify the event name passed to addValidator. Also check whether the request actually goes through a Spring Data REST endpoint or is handled by another controller.

## 13. Common Pitfalls

### Bean Is Created but Validator Does Not Run

The bean name lacks a valid event prefix or has the wrong domain type part. Use a name such as **beforeCreatePersonValidator** and verify component scanning.

### supports Returns False

The validator is bound to the right event, but does not accept the actual class. Check the supports condition and the domain object type.

### Mixing Up beforeCreate and beforeSave

A rule meant only for creation is placed in beforeSave or vice versa. Identify the event matching the HTTP operation and register the right prefix.

### Field Errors Do Not Appear As Expected

The field name in rejectValue must match the object's property. Check binding errors and error response configuration.

### Validator Runs Twice

The same logic is registered both by bean name and via manual addValidator. Choose one registration method per validator/event.

### Validation Only Runs When Calling the REST API

This is the scope of Spring Data REST event integration. If data is also written via services, batch jobs, or message consumers, place shared rules in the appropriate layer.

### Using Validators to Modify Data

A validator can read the object and record errors. Data normalization or state changes should be handled explicitly in the appropriate conversion/service layer to avoid unpredictable side effects.

## 14. Key Takeaways

- Spring Data REST binds a Validator to an event via the bean name prefix.
- **beforeCreatePersonValidator** runs on the event before creating a Person.
- **beforeSavePersonValidator** is bound to the event before saving a Person.
- A Validator implements **supports(Class<?>)** and **validate(Object, Errors)**.
- Use **errors.rejectValue(...)** to record field-level errors.
- Validators can be registered manually using **ValidatingRepositoryEventListener.addValidator(...)** in RepositoryRestConfigurer.
- Choose one registration mechanism per validator/event to avoid duplicate execution.
- Spring Data REST validators protect write flows through the REST exporter; shared rules should be placed in the appropriate layer.
- Validation does not replace authorization, transactions, or side-effect control.
