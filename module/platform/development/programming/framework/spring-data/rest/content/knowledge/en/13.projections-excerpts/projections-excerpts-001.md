# What Is a Projection and When Should You Change the Data View in Spring Data REST?

## Objectives

After this lesson, you can explain projections in Spring Data REST; create a projection interface to select the properties to display; use nested projections for relationships; distinguish between client-requested projections and excerpt projections automatically used in collections; and recognize the limitations of projections regarding performance, data writes, and security.

## 1. What is a projection?

A domain entity typically has many properties for persistence and business logic. However, each screen or client only needs a different subset of data. For example, a `Customer` entity might contain a name, email, phone number, address, internal notes, and transaction history. A customer list page only needs the name and email; a detail page also needs the address and phone number.

A **Projection** is a view of an entity that defines the set of properties included in the representation returned by the API. In Spring Data REST, a projection is usually declared using a Java interface with accessors corresponding to the properties of the domain type.

Projections help the API return data tailored to each client's needs without having to create a separate endpoint or DTO for every simple view. The entity and data stored in the database remain the source of data; the projection only defines how the resource is represented in the response.

For example, the entity:

```java
@Entity
public class Customer {

    @Id
    @GeneratedValue
    private Long id;

    private String firstName;
    private String lastName;
    private String email;
    private String phone;
    private String internalNote;

    @ManyToOne
    private Address address;

    // Constructor, getters, and setters
}
```

A list client may only need the name and email. Another client may also need the phone number and address. Instead of returning all properties in every case, we define corresponding projections.

## 2. Creating a projection interface with @Projection

Use the `@Projection` annotation to name the projection and specify the domain types to which it applies:

```java
import org.springframework.data.rest.core.config.Projection;

@Projection(name = "customerSummary", types = Customer.class)
public interface CustomerSummary {

    String getFirstName();

    String getLastName();

    String getEmail();
}
```

Accessors such as `getFirstName()`, `getLastName()`, and `getEmail()` match the properties of `Customer`. When the projection is applied, the representation contains the properties declared in the interface along with the hypermedia links generated by Spring Data REST.

For the projection to be automatically discovered by Spring Data REST, place the interface in the same package as the domain type or in a subpackage of that package. If the project uses a different package organization, you can register the projection explicitly through the projection configuration of `RepositoryRestConfiguration`.

Repository example:

```java
@RepositoryRestResource(path = "customers")
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {
}
```

After the projection is recognized, clients can request it using the `projection` query parameter:

```http
GET /customers/42?projection=customerSummary
Accept: application/hal+json
```

The value `customerSummary` is the name declared in `@Projection(name = "customerSummary", ...)`. The query parameter name and projection name must match a registered projection.

If the client calls `GET /customers/42` without `projection`, Spring Data REST uses the default resource representation or an excerpt/default projection depending on the context. Selecting a projection via the query parameter allows clients to request a specific view when the endpoint supports it.

## 3. Closed projections: specifying the exact properties to fetch

A projection whose accessors map directly to properties of the domain type is typically called a **closed projection**:

```java
@Projection(name = "customerContact", types = Customer.class)
public interface CustomerContact {

    String getFirstName();

    String getLastName();

    String getEmail();

    String getPhone();
}
```

Spring Data knows exactly which properties are required by the projection because all accessors correspond to entity properties. This is the simplest and most predictable form of projection.

Use a closed projection when the client needs a fixed set of properties, such as:

- A concise list for a search screen.
- Contact details for a customer care workflow.
- Properties displayed in a table or summary card.
- A representation that does not need internal fields of the domain object.

A projection can omit properties that the client does not need. However, the fact that a property does not appear in a projection does not mean that the property is deleted, hidden from all endpoints, or inaccessible via another API.

## 4. Open projections: creating derived properties

A projection can also define values computed from multiple properties of the target object using `@Value` and SpEL. This form is typically called an **open projection**:

```java
import org.springframework.beans.factory.annotation.Value;
import org.springframework.data.rest.core.config.Projection;

@Projection(name = "customerDisplay", types = Customer.class)
public interface CustomerDisplay {

    @Value("#{target.firstName + ' ' + target.lastName}")
    String getDisplayName();

    String getEmail();
}
```

Here, `displayName` is not necessarily a column in the database. Its value is computed from `firstName` and `lastName` when the projection is created.

Open projections are useful when the response needs a simple derived property, such as a display name, label, or combined value. However, SpEL expressions can access multiple properties of the target object, making it hard for Spring Data to determine the exact set of required properties before computing the result. This can reduce query optimization opportunities compared to closed projections.

If the computation logic is complex, depends on many business rules, or needs to call other services, consider placing the logic in a service and creating an appropriate custom representation instead of stuffing all the logic into SpEL.

## 5. Nested projections: changing the view of relationships

An entity can reference another entity. A projection can declare a projection interface for a relationship property to control the data displayed at the nested level.

For example, `Customer` has a relationship to `Address`. Create a projection for the address:

```java
@Projection(name = "addressSummary", types = Address.class)
public interface AddressSummary {

    String getCity();

    String getCountry();
}
```

The Customer projection can return `AddressSummary` instead of the entire Address:

```java
@Projection(name = "customerWithAddress", types = Customer.class)
public interface CustomerWithAddress {

    String getFirstName();

    String getLastName();

    AddressSummary getAddress();
}
```

When calling:

```http
GET /customers/42?projection=customerWithAddress
Accept: application/hal+json
```

the representation can contain the customer's name and the address portion restricted by `AddressSummary`. This approach allows the client to receive a nested data structure suited to the screen without requesting all properties of Address.

For collection relationships, you can declare a collection of the corresponding projection interface, such as `List<OrderSummary> getOrders()`. You should verify the domain mapping, how Jackson/Spring Data creates the projection, and serialization configuration to ensure the response structure matches what the client needs.

Nested projections can trigger access to associations. If an association is lazy-loaded or a collection is large, serializing the representation can lead to additional queries or loading large amounts of data. Projections help control the JSON view, but they do not automatically guarantee optimal database queries.

## 6. What is an excerpt projection?

An **excerpt projection** is a projection used by Spring Data REST as a condensed representation for items in a collection resource. For example, when a client calls:

```http
GET /customers
Accept: application/hal+json
```

the collection response may embed the list of customers inside `_embedded`. If the repository configures an excerpt projection, each embedded item uses that summary view instead of the full entity representation.

Declare an excerpt projection on a repository using the `excerptProjection` attribute of `@RepositoryRestResource`:

```java
@Projection(name = "customerExcerpt", types = Customer.class)
public interface CustomerExcerpt {

    String getFirstName();

    String getLastName();

    String getEmail();
}
```

```java
@RepositoryRestResource(
    path = "customers",
    excerptProjection = CustomerExcerpt.class
)
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {
}
```

In this example, the `/customers` collection resource uses `CustomerExcerpt` for embedded customers. The client receives a summary list and can follow the `self` link to access the item resource.

Excerpt projections are useful when a collection has many entities or entities contain many properties unnecessary for a list. They keep collection representations compact and establish a consistent default view for lists.

## 7. Distinguishing requested projections from excerpt projections

The two mechanisms are related, but their purposes differ:

| Mechanism | How it is selected | Where it typically applies | Purpose |
| --- | --- | --- | --- |
| Regular projection | Client sends `?projection=...` | Resource responses supported by the endpoint | Client selects a specific view |
| Excerpt projection | Repository declares `excerptProjection = ...` | Items embedded in a collection resource | Sets a default summary view for the collection |

For example, a repository uses an excerpt projection for its collection:

```java
@RepositoryRestResource(
    path = "customers",
    excerptProjection = CustomerExcerpt.class
)
public interface CustomerRepository
        extends JpaRepository<Customer, Long> {
}
```

The client calls the collection:

```http
GET /customers
```

The items in `_embedded.customers` use the excerpt projection. When the client follows the `self` link to `/customers/42`, the item response can use the default full representation. If the client wants a specific projection and that projection is exposed, the client requests:

```http
GET /customers/42?projection=customerWithAddress
```

Therefore, an excerpt projection should not be understood as locking every request to an item resource to the same set of properties. It shapes the summary inside collections; the projection query parameter allows selecting a specific view in supported contexts.

## 8. How do projections affect the API and data?

A projection changes the representation that the client sees. It does not change the entity stored in the database, does not automatically alter query methods, does not create a new repository, and does not replace the domain model.

Some consequences to keep in mind:

- Properties not included in a projection do not appear in the representation under that projection.
- Hypermedia links are still generated by Spring Data REST according to the resource and its configuration.
- A projection can include associations or nested projections, making the representation deeper.
- Open projections can compute properties using SpEL.
- Excerpt projections apply to embedded collection items according to the repository configuration.
- A projection is not a request DTO or an allowlist for writable properties in POST/PUT/PATCH.

If a client needs a separate input schema, design an appropriate command/request DTO and custom controller or application service. Do not use read projections to control write data.

## 9. Projections are not a security mechanism

Do not use projections as a security boundary for sensitive data. A projection only determines which representation is returned in a specific context. A client can try requesting the default representation, requesting another registered projection, or accessing the resource through another endpoint if that endpoint permits it.

For example, if `internalNote` is administrator-only data, omitting `getInternalNote()` from `CustomerSummary` is not enough to protect that data. You need to apply server-side authorization, use Spring Security, and design endpoints/representations based on user permissions. For properties that must never appear in any JSON response, configure appropriate serialization such as `@JsonIgnore`, while also checking other access paths.

Similarly, projections do not replace permission checks on associations. If a Customer is linked to an Order belonging to another tenant, the server must still verify permissions before returning or modifying the relationship.

## 10. Choosing a projection based on requirements

- Use a **closed projection** when you need a fixed and explicit set of properties.
- Use an **open projection** when you need a simple derived value from entity properties.
- Use a **nested projection** when the response needs to display part of an association.
- Use an **excerpt projection** when a collection needs a default summary representation for embedded items.
- Use a **custom DTO/controller** when the response needs to combine multiple data sources, complex business logic, or a completely custom output/input schema.

Avoid creating too many nearly identical projections without a concrete client need. Each projection is part of the API contract that clients may depend on; renaming a projection or property can break clients calling it.

## 11. How to verify a projection

After declaring a projection, you can verify it in sequence:

1. Confirm the projection interface has `@Projection`, the correct projection name, and the correct target type.
2. Check the projection's package for automatic discovery by Spring Data REST, or register it explicitly via configuration.
3. Call the API root or resource to retrieve links and confirm the repository is exposed.
4. Call the item resource with `?projection=<name>`.
5. Verify that the response body has the exact declared properties and the necessary hypermedia links.
6. Call the collection resource to confirm the excerpt projection is applied to embedded items.
7. Check nested associations and query counts when the projection accesses large or lazy-loaded relationships.
8. Verify access control separately for sensitive properties; do not infer security from a property's absence in a projection.

Example:

```bash
curl -i "http://localhost:8080/customers/42?projection=customerSummary" \
  -H "Accept: application/hal+json"
```

Verify the excerpt in a collection:

```bash
curl -i "http://localhost:8080/customers" \
  -H "Accept: application/hal+json"
```

If the `projection` query parameter has no effect, check the projection name, target type, package discovery, and projection configuration. If the collection does not use the excerpt as expected, check `excerptProjection` on the right repository interface and the `_embedded` response.

## Summary

- A projection is a view of a domain object, typically declared using an interface and `@Projection`.
- Clients request a projection using the `?projection=<name>` query parameter.
- Closed projections map accessors directly to properties; open projections can compute values using SpEL.
- Nested projections restrict association data in nested representations.
- Excerpt projections are declared with `@RepositoryRestResource(excerptProjection = ...)` to shape embedded items in collection resources.
- Projections change the representation, do not change stored data, and are not allowlists for write requests.
- Do not use projections as a security mechanism; control access with proper authorization and serialization configuration.
