# BeforeCreateEvent and AfterCreateEvent When Creating Resources

## Objectives

When a client sends an HTTP POST to a Spring Data REST collection resource, the framework constructs an entity from the request body and saves the entity through the repository. During this process, Spring Data REST publishes two repository events dedicated to creation:

- `BeforeCreateEvent`: published before a new entity is saved for the first time.
- `AfterCreateEvent`: published after the new entity is saved to the repository.

These two events allow the application to execute logic along the resource creation lifecycle without rewriting the POST endpoint. For example, `BeforeCreateEvent` can normalize data or set default values; `AfterCreateEvent` can write business logs, publish an application event, or initiate follow-up work.

This article explains how to register event handlers, distinguish create events from save events, organize pre/post-save logic, and test the behavior.

## 1. Position of Create Events in the POST Flow

Suppose an exported repository manages Person:

~~~java
@RepositoryRestResource(path = "people")
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

A client creates a resource:

~~~http
POST /people
Content-Type: application/json
Accept: application/hal+json

{
  "firstName": " An ",
  "lastName": "Nguyen",
  "email": " AN@EXAMPLE.COM "
}
~~~

High-level processing flow:

1. Spring MVC receives the POST and Spring Data REST selects the collection resource of the people repository.
2. The HTTP message converter reads the JSON body and constructs a Person entity.
3. Spring Data REST publishes `BeforeCreateEvent` so handlers can process the entity before saving.
4. The repository performs the save operation for the new entity.
5. After the save operation completes, Spring Data REST publishes `AfterCreateEvent`.
6. Spring Data REST builds the HTTP response, typically `201 Created` with a `Location` header pointing to the URI of the new item.

This can be visualized as:

~~~text
POST /people
      |
      v
Deserialize JSON -> Person
      |
      v
BeforeCreateEvent
      |
      v
Repository save(new entity)
      |
      v
AfterCreateEvent
      |
      v
Build HTTP response (201 Created, Location, optional body)
~~~

Create events are used for entities being created for the first time through the REST exporter. When updating an existing item via PUT or PATCH, Spring Data REST uses the standard save event pair `BeforeSaveEvent` and `AfterSaveEvent`.

## 2. BeforeCreateEvent: Processing Before Saving

`BeforeCreateEvent` is published before the entity's first save. The handler receives the entity deserialized from the request body and can adjust data before the repository persists it.

Tasks well-suited for this stage:

- Normalizing input data, such as trimming whitespace or normalizing email addresses.
- Setting default values that the client should not determine itself.
- Generating business codes if that rule belongs to the entity creation lifecycle.
- Checking simple invariants before writing.
- Attaching audit metadata such as creation timestamp or source if the application defines clear rules.

Example entity:

~~~java
@Entity
public class Person {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;
    private String lastName;
    private String email;
    private Instant createdAt;

    // constructors, getters, setters
}
~~~

Handler for Person:

~~~java
@Component
@RepositoryEventHandler(Person.class)
public class PersonCreateEventHandler {

    @HandleBeforeCreate
    public void handleBeforeCreate(Person person) {
        if (person.getFirstName() != null) {
            person.setFirstName(person.getFirstName().trim());
        }

        if (person.getLastName() != null) {
            person.setLastName(person.getLastName().trim());
        }

        if (person.getEmail() != null) {
            person.setEmail(
                person.getEmail().trim().toLowerCase(Locale.ROOT)
            );
        }

        if (person.getCreatedAt() == null) {
            person.setCreatedAt(Instant.now());
        }
    }
}
~~~

In this example, data is normalized right before saving. Because the mutation occurs before repository save, the entity is persisted with the normalized values.

Do not use this handler to call a long chain of external services or perform work unrelated to preparing the entity. Logic in the pre-save stage should be short, deterministic, and have controllable error handling.

## 3. AfterCreateEvent: Processing After Saving

`AfterCreateEvent` is published after the new entity has been saved to the repository. This is the right point to read the identifier generated by the persistence provider and initiate follow-up steps that depend on the newly created entity.

Common use cases:

- Writing logs/audits for resource creation.
- Publishing an application event so other parts of the application can react.
- Creating auxiliary records or requesting a background task.
- Updating caches or search indexes according to the application's consistency strategy.
- Recording the ID and details of the newly created resource.

Extended handler example:

~~~java
@Component
@RepositoryEventHandler(Person.class)
public class PersonCreateEventHandler {

    private static final Logger log =
        LoggerFactory.getLogger(PersonCreateEventHandler.class);

    private final ApplicationEventPublisher eventPublisher;

    public PersonCreateEventHandler(
            ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    @HandleBeforeCreate
    public void handleBeforeCreate(Person person) {
        if (person.getEmail() != null) {
            person.setEmail(
                person.getEmail().trim().toLowerCase(Locale.ROOT)
            );
        }

        if (person.getCreatedAt() == null) {
            person.setCreatedAt(Instant.now());
        }
    }

    @HandleAfterCreate
    public void handleAfterCreate(Person person) {
        log.info("Created Person with id={}", person.getId());

        eventPublisher.publishEvent(
            new PersonCreatedEvent(person.getId(), person.getEmail())
        );
    }
}
~~~

Application event of the application:

~~~java
public record PersonCreatedEvent(Long personId, String email) {
}
~~~

The Spring Data REST event handler receives the Person entity; after saving, the generated ID may already be populated on the entity. A dedicated application event helps decouple downstream integration from the REST handler.

If the application only needs to write a log or update a small internal state, it can be done directly in the handler. If it needs to send emails, call HTTP services, push to a message broker, or run long tasks, offload the work to an appropriate background processing mechanism instead of holding the POST request until everything finishes.

## 4. Registering @RepositoryEventHandler

`@RepositoryEventHandler` marks a bean that contains methods for handling repository events. There are two common ways to register the bean.

### 4.1. Using @Component

The straightforward approach:

~~~java
@Component
@RepositoryEventHandler(Person.class)
public class PersonCreateEventHandler {

    @HandleBeforeCreate
    public void beforeCreate(Person person) {
        // normalize data before saving
    }

    @HandleAfterCreate
    public void afterCreate(Person person) {
        // process after saving
    }
}
~~~

Spring Boot component scanning detects the bean, and Spring Data REST registers the corresponding handler methods.

### 4.2. Declaring a bean with @Bean

If you prefer managing the handler in configuration:

~~~java
@Configuration
public class RepositoryEventConfiguration {

    @Bean
    PersonCreateEventHandler personCreateEventHandler(
            ApplicationEventPublisher publisher) {
        return new PersonCreateEventHandler(publisher);
    }
}
~~~

Do not declare both `@Component` and a second `@Bean` for the same handler, as that can create two beans and cause the same logic to be invoked multiple times.

What matters is that the handler actually exists in the Spring ApplicationContext. Simply adding annotations to a class that is neither component-scanned nor declared as a bean is not enough for Spring Data REST to invoke its methods.

## 5. Distinguishing Handlers by Domain Type

Spring Data REST determines the domain type to handle from the first parameter type of the annotated event handler method. You can also scope it at the class level:

~~~java
@RepositoryEventHandler(Person.class)
public class PersonEventHandler {

    @HandleBeforeCreate
    public void beforeCreate(Person person) {
        // only handles Person
    }

    @HandleAfterCreate
    public void afterCreate(Person person) {
        // only handles Person
    }
}
~~~

Or use one handler for multiple domain types:

~~~java
@RepositoryEventHandler
public class CreateEventHandler {

    @HandleBeforeCreate
    public void beforeCreatePerson(Person person) {
        // handles Person
    }

    @HandleBeforeCreate
    public void beforeCreateOrder(Order order) {
        // handles Order
    }

    @HandleAfterCreate
    public void afterCreatePerson(Person person) {
        // handles Person after saving
    }
}
~~~

For a handler not restricted at the class level, each method's parameter type indicates its corresponding domain type. This approach is useful when multiple entities share a common set of rules. If the logic for different entities diverges significantly, split the handlers so each class has a clear scope and responsibility.

## 6. Create Event Annotations and Other Events

The Spring Data REST exporter publishes multiple events across the entity lifecycle:

| Event | Timing | Purpose |
|---|---|---|
| `BeforeCreateEvent` | Before first save | Prepare new entity |
| `AfterCreateEvent` | After new entity is saved | React after create operation |
| `BeforeSaveEvent` | Before saving existing entity | Prepare updated data |
| `AfterSaveEvent` | After entity save operation | React after update/save |
| `BeforeLinkSaveEvent` | Before saving association link | Handle relationship changes |
| `AfterLinkSaveEvent` | After saving association link | React after relationship changes |
| `BeforeDeleteEvent` | Before deleting entity | Check or prepare deletion |
| `AfterDeleteEvent` | After deleting entity | Record or handle post-deletion |

The corresponding handler annotations are `@HandleBeforeCreate`, `@HandleAfterCreate`, `@HandleBeforeSave`, `@HandleAfterSave`, `@HandleBeforeLinkSave`, `@HandleAfterLinkSave`, `@HandleBeforeDelete`, and `@HandleAfterDelete`.

Distinguishing create and save is very important:

- POST to a collection creates a new entity, so use the BeforeCreate/AfterCreate pair.
- PUT or PATCH to an existing item updates the entity, so use the BeforeSave/AfterSave pair.
- Modifying associations can publish separate link save events.

Do not use `@HandleBeforeSave` to replace all creation logic if the business rule only applies on creation. Separating events properly prevents re-running code generation, overwriting creation timestamps, or sending creation notifications when an entity is merely updated.

## 7. Alternative: AbstractRepositoryEventListener

Beyond annotated handlers, Spring Data REST provides `AbstractRepositoryEventListener<T>`. You can extend this class and override the needed callbacks:

~~~java
@Component
public class PersonRepositoryEventListener
        extends AbstractRepositoryEventListener<Person> {

    @Override
    protected void onBeforeCreate(Person person) {
        if (person.getEmail() != null) {
            person.setEmail(
                person.getEmail().trim().toLowerCase(Locale.ROOT)
            );
        }
    }

    @Override
    protected void onAfterCreate(Person person) {
        // process after creation
    }
}
~~~

This approach works well when you want to handle events through a listener class and override repository lifecycle callbacks. A generic listener can restrict the domain type via its type parameter.

A general listener does not distinguish domain types per callback if it uses Object or is not appropriately constrained; in that case, you must check the entity type manually. Annotated handlers are usually easier to read when handling multiple domain types with separate type-safe methods.

There is no need to use both an annotated handler and AbstractRepositoryEventListener simultaneously for the same business logic. Pick one implementation style to avoid duplicate processing.

## 8. Event Handlers and Transaction Boundaries

The name `AfterCreateEvent` means that the repository save operation has completed and Spring Data REST published the event after that operation. It should not be interpreted by default as a guarantee that the database transaction has committed successfully in every configuration.

Spring Data REST events are Spring application events and are published synchronously by default. Therefore, handlers usually execute on the request thread. If a handler performs slow work, POST response latency increases accordingly.

For tasks that must only run after the transaction commits, design explicit transaction boundaries. You can publish an application event inside the transaction and use `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` when the event is published within an active transaction. This mechanism only makes sense when a suitable transaction exists; if the event is published after the repository transaction has already ended, you cannot assume the listener will automatically have a prior transaction to await commit on.

For critical integrations that must guarantee no message loss if the application crashes between writing to the database and sending a message, consider a transactional outbox: write both the business data and the outbox record in the same transaction, then have a worker publish messages from the outbox. This is an application-level architectural decision, not an automatic guarantee of `AfterCreateEvent`.

For background tasks that do not require commit coupling, you can publish an application event and handle it asynchronously using a listener configured with `@Async` and an appropriate executor. You must clearly define error handling, retries, and observability because errors in the worker are no longer returned directly to the POST request.

## 9. Validation and Error Handling Before Creation

If an entity is invalid, block the operation before the repository persists data. You can check invariants in `@HandleBeforeCreate` or use the validation mechanism of Spring Data REST / Spring Validation.

Example of normalizing and validating business conditions:

~~~java
@Component
@RepositoryEventHandler(Person.class)
public class PersonCreateEventHandler {

    @HandleBeforeCreate
    public void beforeCreate(Person person) {
        if (person.getEmail() == null || person.getEmail().isBlank()) {
            throw new InvalidPersonException("Email is required");
        }

        person.setEmail(
            person.getEmail().trim().toLowerCase(Locale.ROOT)
        );
    }
}
~~~

Example exception:

~~~java
public class InvalidPersonException extends RuntimeException {
    public InvalidPersonException(String message) {
        super(message);
    }
}
~~~

The application needs appropriate exception handling configured to translate business errors into consistent HTTP responses. Never let a handler catch and swallow exceptions, as the request might proceed to save an invalid entity.

For annotation-based validation such as `@NotBlank`, `@Email`, or custom constraints, configure Bean Validation and Spring Data REST validators properly. Event handlers can supplement checks that depend on the creation context, but should not duplicate an entire validation framework inside every handler.

## 10. Testing BeforeCreateEvent and AfterCreateEvent

Test via real HTTP POST requests in integration tests to verify that Spring Data REST receives the request, invokes the right events, and saves the entity.

Example testing pre-save normalization results:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class PersonCreateEventTests {

    @Autowired
    MockMvc mvc;

    @Autowired
    PersonRepository repository;

    @BeforeEach
    void cleanDatabase() {
        repository.deleteAll();
    }

    @Test
    void beforeCreateNormalizesEmailBeforeSaving() throws Exception {
        mvc.perform(post("/people")
                .contentType(MediaType.APPLICATION_JSON)
                .accept(MediaTypes.HAL_JSON)
                .content("""
                    {
                      "firstName": " An ",
                      "lastName": " Nguyen ",
                      "email": " AN@EXAMPLE.COM "
                    }
                    """))
            .andExpect(status().isCreated());

        Person saved = repository.findAll().iterator().next();

        assertThat(saved.getFirstName()).isEqualTo("An");
        assertThat(saved.getLastName()).isEqualTo("Nguyen");
        assertThat(saved.getEmail()).isEqualTo("an@example.com");
        assertThat(saved.getCreatedAt()).isNotNull();
    }
}
~~~

To test AfterCreateEvent, you can spy on the handler or register a test listener that receives the application event. Example using a Mockito spy in the test context:

~~~java
@SpringBootTest
@AutoConfigureMockMvc
class AfterCreateEventTests {

    @Autowired
    MockMvc mvc;

    @SpyBean
    PersonCreateEventHandler handler;

    @Test
    void postInvokesAfterCreateHandler() throws Exception {
        mvc.perform(post("/people")
                .contentType(MediaType.APPLICATION_JSON)
                .accept(MediaTypes.HAL_JSON)
                .content("""
                    {
                      "firstName": "An",
                      "lastName": "Nguyen",
                      "email": "an@example.com"
                    }
                    """))
            .andExpect(status().isCreated());

        verify(handler).handleAfterCreate(any(Person.class));
    }
}
~~~

The spied method name must match the actual method in the handler. Depending on the Spring Boot version, `@SpyBean` may be replaced by the corresponding Mockito bean override mechanism. Each test needs isolated data or cleanup so it does not depend on execution order.

Points to verify:

- POST creates exactly one new entity.
- The BeforeCreate handler runs before data is saved.
- Normalized values appear in the repository after POST.
- The AfterCreate handler receives the entity with a persisted ID.
- PUT/PATCH does not accidentally invoke create handlers.
- If the handler publishes an application event, downstream listeners receive the right payload.
- Pre-save validation failures do not create a new entity.

## 11. Common Pitfalls

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Handler is not called | Bean is not in ApplicationContext | Use @Component or declare @Bean and check component scanning |
| Handler runs for wrong entity | Missing domain type restriction or wrong parameter type | Use @RepositoryEventHandler(Person.class) and Person parameter |
| Creation logic runs on PUT/PATCH | Logic placed in BeforeSave/AfterSave or shared service | Move creation-only logic to BeforeCreate/AfterCreate |
| Email still saved with uppercase/spaces | Normalized after repository save or handler not registered | Put normalization in BeforeCreate and test saved data |
| ID missing in BeforeCreate | Entity not yet saved so database-generated ID does not exist | Use AfterCreate for logic requiring the generated ID |
| Message sent but database rolled back | Confused AfterCreate with transaction after-commit | Identify transaction boundary; use after-commit or outbox when needed |
| POST unusually slow | AfterCreate handler performs long synchronous work | Move suitable tasks to background processing |
| Business logic runs twice | Same logic registered via multiple handlers/listeners | Register only one mechanism per rule and check bean count |
| Handler swallows exceptions | Catching errors without handling or rethrowing | Let errors propagate to appropriate exception handling |
| Flaky tests | Depending on auto-generated IDs or leftover data from prior tests | Create dedicated fixtures, clean up, and read URIs from responses |

## 12. Create Event Implementation Checklist

- Identify which operations are truly creations via POST to a collection resource.
- Use `@HandleBeforeCreate` for logic that must run before the first save.
- Use `@HandleAfterCreate` for logic requiring the entity after save completes.
- Register the handler as a Spring bean using `@Component` or `@Bean`.
- Scope the domain type with `@RepositoryEventHandler(Entity.class)` when appropriate.
- Keep handlers short and avoid synchronous external service calls unless necessary.
- Distinguish create events from before/after save events for PUT/PATCH.
- Do not treat AfterCreateEvent as a guarantee that the transaction has committed.
- Use after-commit or a transactional outbox when tasks depend on durable commits.
- Test pre-save data, post-save data, and error cases.
- Avoid registering multiple handlers simultaneously for the same business logic.

## Conclusion

`BeforeCreateEvent` and `AfterCreateEvent` allow extending the Spring Data REST POST lifecycle. BeforeCreate runs before a new entity is saved, making it suitable for normalizing data, setting defaults, and checking invariants. AfterCreate runs after the save operation, making it suitable for recording the created entity and publishing application events for next steps. Registering a handler with `@RepositoryEventHandler` and `@HandleBeforeCreate`/`@HandleAfterCreate` keeps logic scoped by domain type. Distinguish create events from update save events, manage transaction boundaries explicitly, and test through HTTP POST to verify the exact lifecycle.
