# Testing Spring Data REST: Choosing @SpringBootTest, MockMvc, or Real HTTP

## 1. Purpose and Classification

Spring Data REST exports Spring Data repositories as REST resources through Spring MVC. Therefore, API testing needs to confirm that repositories are published properly, paths and HTTP methods work, JSON/HAL representations are accurate, and application configurations participate in request handling.

The three names often placed side by side actually lie on two different axes:

- **@SpringBootTest** determines the scope of the Spring ApplicationContext loaded. This is how you load the Spring Boot application configuration for integration testing.
- **MockMvc** is a tool for creating requests and inspecting responses through Spring MVC using simulated requests/responses. It does not open an HTTP port and does not start an embedded server.
- **HTTP client + real server** sends requests over a network port to a running embedded server or to a deployed environment. This approach additionally verifies behavior dependent on the servlet container and network.

Consequently, @SpringBootTest and MockMvc are frequently used together. For Spring Data REST, the default combination to start with is **@SpringBootTest + @AutoConfigureMockMvc**: load the application configuration, repositories, exporter, and real MVC configuration, then invoke endpoints using MockMvc. Only switch to a real server when the test question requires verifying container, port, or network behavior.

## 2. Choosing Tools by Verification Scope

| Scope to verify | Appropriate testing approach | What is checked | Main limitations |
|---|---|---|---|
| Business rules in a service | Unit test with JUnit and Mockito | Branches, conditions, errors, and interactions with dependencies | Does not verify Spring wiring or HTTP |
| Entities, repository queries, data mapping | @DataJpaTest or datastore-specific slice | Mapping, queries, constraints, and data access | Does not verify exported Spring Data REST resources |
| Endpoints generated by Spring Data REST, HAL, CRUD, search, paging | @SpringBootTest + @AutoConfigureMockMvc | Application config, Spring MVC, repository exporter, serialization, and response | Does not verify embedded server or real network |
| A custom MVC controller without needing the entire application | @WebMvcTest + MockMvc | Web layer mapping and behavior of the controller with mocked dependencies | Slice does not automatically load all repository/exporter configuration |
| Need to verify embedded servlet container, port, cookies/sessions, or container behavior | @SpringBootTest(webEnvironment = RANDOM_PORT) + HTTP client | Requests go through a real server on a random port | Starts server and takes more time; must manage test data |
| Need to verify gateway, reverse proxy, DNS, TLS, or deployed environment config | External HTTP test, smoke test, or end-to-end test | Full path from client to target environment | Environment-dependent and usually slower, harder to isolate |

### Easily confused choices

**@SpringBootTest does not start a server by default.** The default value of webEnvironment is MOCK. For MVC applications, you can combine it with @AutoConfigureMockMvc to obtain MockMvc. To start a server, set webEnvironment to RANDOM_PORT or DEFINED_PORT.

**MockMvc does not mean unit test.** When configured with WebApplicationContext, MockMvc goes through the Spring MVC infrastructure and real application configuration. This is a web layer integration test. MockMvc in standalone mode only accepts specified controllers and MVC configuration provided by the test; it is closer to a unit test and requires a separate integration test pass to verify real MVC configuration.

**@WebMvcTest is a slice test.** It is useful when testing custom controllers and replacing services with mocks. This slice restricts scanned beans; Spring Data repositories and Spring Data REST resource export configurations may not be loaded. Therefore, you should not choose @WebMvcTest as the primary test for repository-generated endpoints. If you must use the slice, you have to explicitly import the right configuration and understand which parts are being skipped.

## 3. Preparing Dependencies and Data

With a Spring Boot application, you usually only need the testing starter in test scope; versions are managed by Spring Boot dependency management.

Maven:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
~~~

Gradle:

~~~groovy
dependencies {
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}
~~~

The starter provides common testing components such as JUnit Jupiter, AssertJ, Hamcrest, and Spring Boot test support. The application still needs the Spring Data REST dependency and the corresponding datastore dependency in its normal runtime configuration.

If testing database-engine-dependent behavior, use the same type of database as the application environment, often via Testcontainers. In-memory databases are useful for fast tests but cannot replace verification of dialect, constraints, collation, transactions, or database-specific SQL. You can refer to official Spring Data samples; many samples use Testcontainers or embedded datastores.

## 4. Integration Example: Testing Exported Resources with MockMvc

Suppose the application has a Person entity and wants to export its repository at `/people`.

Illustrative entity:

~~~java
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Person {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;
    private String lastName;

    protected Person() {
    }

    public Person(String firstName, String lastName) {
        this.firstName = firstName;
        this.lastName = lastName;
    }

    public Long getId() {
        return id;
    }

    public String getFirstName() {
        return firstName;
    }

    public void setFirstName(String firstName) {
        this.firstName = firstName;
    }

    public String getLastName() {
        return lastName;
    }

    public void setLastName(String lastName) {
        this.lastName = lastName;
    }
}
~~~

Repository:

~~~java
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.rest.core.annotation.RepositoryRestResource;

@RepositoryRestResource(
    path = "people",
    collectionResourceRel = "people"
)
public interface PersonRepository extends JpaRepository<Person, Long> {
}
~~~

Spring Data REST can generate collection resources and item resources from the repository. In this example, the collection is `/people`; items have the form `/people/{id}`. By default responses use HAL, with links placed in the `_links` property.

### Testing with Spring Boot context and MockMvc

The example below uses Spring Boot 3.5.x APIs and JUnit Jupiter. With Spring Boot 3.x, the AutoConfigureMockMvc import is `org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc`. In Spring Boot 4.x, the annotation's package moved to `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc`. Use the package matching the version managed in your project.

~~~java
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpHeaders;
import org.springframework.http.MediaType;
import org.springframework.hateoas.MediaTypes;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class PersonRestApiTests {

    @Autowired
    MockMvc mvc;

    @Autowired
    PersonRepository people;

    @BeforeEach
    void prepareData() {
        people.deleteAll();
        people.save(new Person("Ada", "Lovelace"));
    }

    @Test
    void rootPublishesPeopleLink() throws Exception {
        mvc.perform(get("/").accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$._links.people.href").exists());
    }

    @Test
    void collectionIsReturnedAsHal() throws Exception {
        mvc.perform(get("/people").accept(MediaTypes.HAL_JSON))
            .andExpect(status().isOk())
            .andExpect(content().contentTypeCompatibleWith(MediaTypes.HAL_JSON))
            .andExpect(jsonPath("$._embedded.people[0].firstName").value("Ada"))
            .andExpect(jsonPath("$._links.self.href").exists());
    }

    @Test
    void postCreatesResource() throws Exception {
        mvc.perform(post("/people")
                .contentType(MediaType.APPLICATION_JSON)
                .accept(MediaTypes.HAL_JSON)
                .content("""
                    {
                      "firstName": "Grace",
                      "lastName": "Hopper"
                    }
                    """))
            .andExpect(status().isCreated())
            .andExpect(header().exists(HttpHeaders.LOCATION));
    }
}
~~~

Key points to understand in the example:

1. @SpringBootTest loads the main application configuration. Repositories, the Spring Data REST exporter, mappings, serializers, security, and the application's MVC configuration all participate in the test.
2. @AutoConfigureMockMvc creates MockMvc in a mock web environment. There is no need to run a server on port 8080.
3. Accept: application/hal+json requests a HAL representation. The Content-Type of the POST request is application/json because the sent body is JSON.
4. A HAL collection has an `_embedded.people` structure. Do not assume the collection response is a plain JSON array.
5. The POST test confirms status 201 Created and a Location header. This header points to the new resource; avoid hard-coding auto-generated IDs.
6. Data is deleted and recreated before each test so tests do not depend on execution order. For data with relationships or parallel test execution, use separate fixtures, unique identifier keys, or an isolated database/schema.

If the repository has a custom path or custom collection relation, update the URL and JSONPath according to that exact configuration. If the application sets a base path via Spring Data REST configuration, URLs in tests must include the base path as well.

## 5. When Real HTTP Is Needed: Starting a Server with RANDOM_PORT

Use RANDOM_PORT when the objective includes the embedded server or behavior that MockMvc does not fully simulate. Spring Boot recommends a random port to avoid conflicts with other processes and avoid depending on a fixed port.

Example for Spring Boot 3.5.x using TestRestTemplate:

~~~java
import java.util.List;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.SpringBootTest.WebEnvironment;
import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.http.HttpEntity;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class PersonHttpApiTests {

    @Autowired
    TestRestTemplate client;

    @Test
    void collectionIsReachableOverHttp() {
        HttpHeaders headers = new HttpHeaders();
        headers.setAccept(List.of(
            MediaType.parseMediaType("application/hal+json")
        ));

        ResponseEntity<String> response = client.exchange(
            "/people",
            HttpMethod.GET,
            new HttpEntity<>(headers),
            String.class
        );

        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(response.getHeaders().getContentType())
            .isCompatibleWith(MediaType.parseMediaType("application/hal+json"));
        assertThat(response.getBody()).contains("_embedded");
    }
}
~~~

TestRestTemplate is configured by Spring Boot for tests with a running server. Relative paths like `/people` are sent to the random port used by the test server.

With Spring Boot 4.x, you can use RestTestClient together with @AutoConfigureRestTestClient:

~~~java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
class PersonHttpApiTests {

    @Autowired
    RestTestClient client;

    @Test
    void collectionIsReachableOverHttp() {
        client.get()
            .uri("/people")
            .exchange()
            .expectStatus().isOk()
            .expectHeader().contentTypeCompatibleWith(
                MediaType.parseMediaType("application/hal+json")
            );
    }
}
~~~

RestTestClient is the client choice in Spring Boot 4.x documentation. Check the import packages according to the Boot and Spring Framework versions in use. WebTestClient can also be used with a real server; in some MVC configurations, it requires `spring-webflux` on the classpath. Do not add WebFlux just to have an HTTP client if TestRestTemplate or RestTestClient already meets your requirements.

### Calling directly with curl

When the application is already running in a local or test environment, you can smoke test endpoints over real HTTP:

~~~bash
curl -i \
  -H "Accept: application/hal+json" \
  http://localhost:8080/people
~~~

This is useful for inspecting status, response headers, content type, and HAL body. It works well for quick checks or post-deploy smoke tests. For CI, automate using an HTTP client and explicit base URL configuration rather than relying on manual execution.

## 6. Choosing Between MockMvc Standalone and WebApplicationContext

Spring Framework supports two MockMvc setup styles:

- **webAppContextSetup(WebApplicationContext)**: uses the real loaded Spring MVC configuration. This is the right choice for Spring Data REST integration tests because it requires the repository exporter and real MVC infrastructure.
- **standaloneSetup(controller)**: passes controllers and mocked dependencies directly without loading Spring configuration. Suitable for testing the isolated behavior of a custom controller or quickly reproducing a bug.

Standalone example:

~~~java
MockMvc mvc = MockMvcBuilders
    .standaloneSetup(new GreetingController())
    .build();
~~~

You cannot use standalone setup to assert that Spring Data REST exported repositories correctly. It does not initialize the full Spring Data REST infrastructure. If you use standalone setup to test a custom controller, you still need a separate set of integration tests to verify application configuration.

## 7. Checklist for Repository-Exported REST APIs

Select the necessary cases based on application features. Not every test needs to be written for every repository.

| Area | What should be verified |
|---|---|
| Resource discovery | GET root returns 200; `_links` contains the exported repository relations |
| Collection | GET collection returns the right media type, data, metadata, and links |
| Item | GET item with valid URI returns expected representation; nonexistent URI returns error per contract |
| Create | POST valid body creates resource; check 201 and Location |
| Update | PUT replaces, PATCH partially updates; verify updated data and status per response body configuration |
| Delete | DELETE removes resource; subsequent GET confirms resource is gone |
| Search | Search link appears when repository has exposed query methods; invoke query with valid parameters |
| Pagination and sorting | page, size, sort return accurate results; check page metadata and navigation links |
| Association | Relationship links have the right relation; attaching/removing associations uses appropriate URI and media type |
| Representation | HAL links, embedded relations, projections, and JSON fields serialize correctly |
| Validation | Invalid input is rejected according to the application's validation rules and error contract |
| Security | Endpoints requiring authentication/authorization return accurate results for anonymous, authorized, and unauthorized users |
| Content negotiation | Accept and Content-Type are handled properly; check both JSON requests and HAL responses if supported by the API |

Spring Data REST uses HAL by default to represent links. The root resource allows clients to discover published relations. Collection resources typically support GET and POST; item resources typically support GET, PUT, PATCH, and DELETE, depending on repository methods and export configuration. HTTP methods may not be exported if the repository does not provide the corresponding method or if the method is marked `exported = false`.

Regarding status codes, standard GET returns 200; POST creating a resource returns 201. PUT, PATCH, and DELETE may return 200 or 204 depending on whether returning a response body is configured and on the Accept header. Therefore, pin down the response contract in application configuration before writing assertions for updates/deletes.

## 8. Test Data, Transactions, and Speed

### Transaction rollback differs between the two test types

Spring TestContext can roll back a test's transaction after each test method. This is helpful when tests run on the same thread and share a transaction.

With RANDOM_PORT or DEFINED_PORT, the HTTP client and server run on separate threads and use separate transactions. The transaction in which the server processes the request is not part of the test method's transaction. Hence, placing @Transactional on the test does not automatically roll back data created through HTTP requests.

When testing against a real server, choose a clear data cleanup strategy:

- Use a dedicated database or schema for tests.
- Create fixtures with unique keys and delete them after the test.
- Reset the database before each suite or test group.
- Use Testcontainers to get an isolated datastore aligned with test lifecycle.

Do not rely on test method transaction rollback to clean up data written by HTTP requests to a real server.

### Keeping tests fast and stable

- Use unit tests for pure business rules; there is no need to start a Spring context for every processing branch.
- Use @DataJpaTest for JPA queries and mappings; use MVC integration tests for exported endpoints.
- Share test configurations whenever possible. Spring TestContext caches the ApplicationContext across tests with identical configurations.
- Do not unnecessarily change profiles, properties, or imported configurations between tests because it can create multiple distinct contexts.
- Use RANDOM_PORT instead of a fixed port if a real server is needed.
- Avoid assertions on auto-generated IDs, unguaranteed data ordering, or absolute URLs tied to host/port. Prefer checking relations, paths, and contracts.
- When the database engine affects results, run tests against the same engine type rather than relying solely on H2.

## 9. Common Troubleshooting

| Symptom | Common cause | How to resolve |
|---|---|---|
| GET /people returns 404 | Wrong base path, wrong repository path, repository not scanned, or resource not exported | Call GET root to inspect `_links`; check @RepositoryRestResource, package scanning, and base path config |
| GET /people returns 405 | findAll is not provided or export is disabled | Check repository interface and @RestResource(exported = false) |
| POST /people returns 405 | Repository lacks an exported save method or method is disabled | Check repository has appropriate CrudRepository/JpaRepository and save is exported |
| 406 Not Acceptable | Accept requests a representation not supported by the endpoint | Send Accept: application/hal+json or application/json per API |
| 415 Unsupported Media Type | Content-Type does not match the sent body | For JSON requests, set Content-Type: application/json |
| JSONPath cannot find collection field | Test reads JSON as a plain array while response is HAL | Read data via `_embedded.<collection-rel>`; check collectionResourceRel |
| Link assertion fails | Path or relation was customized, base path changed, or host/port differs | Inspect `_links` and Location; avoid hard-coding absolute URLs |
| MockMvc test returns 401/403 | Security filter chain still participates in request and test provides no authentication | Use Spring Security Test support, e.g. @WithMockUser or request postprocessor; only disable filters if that is truly the test scope |
| @WebMvcTest cannot find repository | Slice only loads supported MVC beans | Use @SpringBootTest for Spring Data REST endpoints or explicitly import required configurations |
| HTTP test leaves data behind | Server processes request in a different thread/transaction from test | Clean up data using separate fixtures/schemas; do not expect test @Transactional to roll back |
| Test context cannot find main configuration | Test package is not under the package with @SpringBootApplication or has special scan config | Place test in the right package or specify appropriate classes/configurations |
| Tests fail when run in parallel | Tests share data, IDs, or database | Use unique identifier data, separate schemas/databases, or serialize dependent test groups |

When encountering an error, check the actual response first: status, Content-Type, Location, body, and HAL `_links`. For Spring Data REST endpoints, GET root is often a quick way to see which resources are actually published.

## 10. Running Tests

Run all tests:

Maven:

~~~bash
./mvnw test
~~~

Gradle:

~~~bash
./gradlew test
~~~

Run a single test class:

Maven:

~~~bash
./mvnw -Dtest=PersonRestApiTests test
~~~

Gradle:

~~~bash
./gradlew test --tests '*PersonRestApiTests'
~~~

If tests require an external database, start Testcontainers or the test service per project configuration before running. Do not use the application run command instead of the test command: the goal is for the test runner to create the context/server, send requests, and evaluate assertions automatically.
