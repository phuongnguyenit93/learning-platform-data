# Generating Q-Types and Building Typed Query Conditions

## 1. Why Do We Need Q-Types When Query and Criteria Already Exist?

A product service has a search screen filtering by tenant, status, price range, keyword, stock, and many optional criteria. A derived repository method for every combination quickly produces very long names:

~~~java
List<ProductDocument> findByTenantIdAndActiveAndPriceMinorBetween(
    String tenantId, boolean active, long minPrice, long maxPrice
);

List<ProductDocument> findByTenantIdAndNameContainingIgnoreCase(
    String tenantId, String name
);
~~~

**MongoTemplate** lets you build dynamic conditions with `Criteria`, but field names are still passed primarily as strings:

~~~java
Criteria.where("tenantId").is(tenantId)
    .and("active").is(true)
    .and("priceMinor").gte(minPrice);
~~~

When renaming the Java property **priceMinor** to **salePriceMinor**, the compiler will not automatically flag the stale `"priceMinor"` string. **Querydsl** offers an alternative: generating a **Q-type** class describing Java properties with strong types. Instead of string field names, the application writes:

~~~java
QProductDocument p = QProductDocument.productDocument;
var predicate = p.tenantId.eq(tenantId)
    .and(p.active.isTrue())
    .and(p.priceMinor.goe(minPrice));
~~~

If the property is renamed, code referencing the old Q-type property fails to compile once Q-types are regenerated, catching refactoring errors early.

The lesson **Generating Q-Types and Building Typed Query Conditions** belongs to the **Extended Repositories** chapter of the **SPRING_DATA_MONGODB** module. It is one technique for connecting, mapping documents, and querying MongoDB via repositories; alongside it, `MongoTemplate` remains well suited for aggregations, indexes, transactions, reactive access, testing, and data performance diagnostics.

Objectives:

1. Understand **Q-type**, **Predicate**, **BooleanExpression**, and **BooleanBuilder**.
2. Generate Q-classes from MongoDB entities via annotation processing.
3. Configure Maven and Gradle to run **MongoAnnotationProcessor** properly.
4. Extend repositories with **QuerydslPredicateExecutor**.
5. Write dynamic AND/OR predicates, string/numeric/boolean conditions, and tenant filters.
6. Paginate, sort, count, and check existence using Predicates.
7. Distinguish Querydsl usage in synchronous vs. reactive repositories.
8. Test BSON field mapping, enforce access control, and evaluate performance.

## 2. Processing Flow from @Document to MongoDB

~~~mermaid
flowchart TD
    A["Entity ProductDocument, @Document"] --> B["MongoAnnotationProcessor at compile time"]
    B --> C["Generated QProductDocument"]
    C --> D["Predicate / BooleanBuilder"]
    D --> E["QuerydslPredicateExecutor"]
    E --> F["Spring Data MongoDB mapping"]
    F --> G["MongoDB collection products"]
~~~

| Concept | Responsibility |
| --- | --- |
| **Entity** | Domain object mapped to a BSON document. |
| **Q-type** | Generated Java code representing typed property paths. |
| **BooleanExpression** | Condition chainable with and/or/not. |
| **BooleanBuilder** | Mutable accumulator for optional conditions when building filters. |
| **Predicate** | Condition expression contract accepted by the Querydsl executor. |
| **QuerydslPredicateExecutor** | Extends synchronous repositories with Predicate-based find, count, exists. |
| **ReactiveQuerydslPredicateExecutor** | Extends reactive repositories returning Mono/Flux. |
| **MongoTemplate** | Complementary tool for Query/Criteria, projections, aggregations, or advanced updates. |

**QProductDocument is not a document stored in the database** and not an API response DTO. It is intermediate Java code generated by an annotation processor during the build.

## 3. Document and Entity Used Throughout the Lesson

The **products** collection holds a document:

~~~javascript
{
  _id: ObjectId("507f1f77bcf86cd799439011"),
  tenant_id: "shop-a",
  sku: "BOOK-101",
  name: "Hands-on Spring Data MongoDB",
  active: true,
  priceMinor: NumberLong("159000"),
  stock: NumberInt(12),
  tags: ["JAVA", "MONGODB"]
}
~~~

The BSON name **tenant_id** differs from Java's **tenantId**, illustrating mapping's role. Entity:

~~~java
package com.example.catalog;

import java.util.ArrayList;
import java.util.List;
import org.bson.types.ObjectId;
import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;

@Document(collection = "products")
public class ProductDocument {

    @Id
    private ObjectId id;

    @Field("tenant_id")
    private String tenantId;

    private String sku;
    private String name;
    private boolean active;
    private long priceMinor;
    private int stock;
    private List<String> tags = new ArrayList<>();

    protected ProductDocument() {}

    public ProductDocument(
            String tenantId, String sku, String name,
            boolean active, long priceMinor, int stock) {
        this.tenantId = tenantId;
        this.sku = sku;
        this.name = name;
        this.active = active;
        this.priceMinor = priceMinor;
        this.stock = stock;
    }

    public ObjectId getId() { return id; }
    public String getTenantId() { return tenantId; }
    public String getSku() { return sku; }
    public String getName() { return name; }
    public boolean isActive() { return active; }
    public long getPriceMinor() { return priceMinor; }
    public int getStock() { return stock; }
    public List<String> getTags() { return tags; }
    public void setTags(List<String> tags) { this.tags = tags; }
}
~~~

**@Document** specifies the collection, **@Id** maps Java `id` to BSON `_id`, and **@Field("tenant_id")** maps Java `tenantId` to BSON `tenant_id`.

In multi-tenant systems, always bind the tenant condition from an authenticated context; never let users pick arbitrary tenants simply by passing a filter parameter.

## 4. How Is QProductDocument Generated?

The annotation processor inspects `ProductDocument`'s metadata and generates a Java class structured like:

~~~java
// ILLUSTRATIVE structure only, not source code to write manually.
public class QProductDocument extends EntityPathBase<ProductDocument> {

    public static final QProductDocument productDocument = ...;

    public final StringPath tenantId = ...;
    public final StringPath sku = ...;
    public final StringPath name = ...;
    public final BooleanPath active = ...;
    public final NumberPath<Long> priceMinor = ...;
    public final NumberPath<Integer> stock = ...;
}
~~~

The **...** placeholders represent expressions and constructors filled in by the annotation processor. **Do not copy this illustrative snippet into your source tree to compile.**

Commonly generated path types include:

| Property | Querydsl path group | Common operations |
| --- | --- | --- |
| name, sku, tenantId | StringPath | eq, contains, startsWithIgnoreCase |
| active | BooleanPath | isTrue, isFalse |
| priceMinor | NumberPath<Long> | goe, loe, between |
| stock | NumberPath<Integer> | gt, lt, in |
| id | Path typed for ObjectId | eq and supported comparisons |
| tags | Appropriate Collection/ListPath | contains when supported by serializer |
| Nested supplier | Nested type path if generated by processor | Accessing embedded fields |

In business code:

~~~java
QProductDocument product = QProductDocument.productDocument;
~~~

The static instance typically takes the camelCase form of the entity name. If the actual instance or path name differs, inspect the generated source instead of editing the Q-class manually.

### 4.1. What Does Type Safety Protect Against?

Suppose you rename `priceMinor` to `salePriceMinor` on the entity and recompile:

~~~java
// Code still referencing the renamed property triggers a compiler error:
product.priceMinor.goe(100_000L);
~~~

Thus, property refactors can be caught at build time. However, Q-types do not automatically verify that indexes exist, business inputs are valid, collection schemas match, or the caller is authorized to view the data.

## 5. The Right Processor for Spring Data MongoDB

**Do not use only the Querydsl JPA annotation processor.** Spring Data MongoDB has its own dedicated processor:

~~~text
org.springframework.data.mongodb.repository.support.MongoAnnotationProcessor
~~~

This processor generates Q-types using MongoDB mapping metadata, including entities annotated with **@Document**. A Querydsl JPA setup targeting only `jakarta.persistence.Entity` may skip generating Q-classes for MongoDB domain types.

Everything that must align:

- Spring Boot and Spring Data MongoDB.
- Querydsl core, mongodb, and apt from the same version family.
- Java compiler, Maven, or Gradle.
- `jakarta`/`javax` namespace matching your library stack.
- MongoDB driver managed by Spring Data.

**There is no single Querydsl version number that fits every project.** The examples below use a build variable for the version and must be adjusted to match your project's BOM and dependency setup.

## 6. Gradle: Configuring Annotation Processing

Example with Gradle Groovy DSL:

~~~groovy
plugins {
    id 'java'
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-mongodb'

    implementation("com.querydsl:querydsl-mongodb:$querydslVersion") {
        exclude group: 'org.mongodb', module: 'mongo-java-driver'
    }

    annotationProcessor "com.querydsl:querydsl-apt:$querydslVersion:jakarta"
    annotationProcessor "org.springframework.data:spring-data-mongodb"

    testAnnotationProcessor "com.querydsl:querydsl-apt:$querydslVersion:jakarta"
    testAnnotationProcessor "org.springframework.data:spring-data-mongodb"
}

tasks.withType(JavaCompile).configureEach {
    options.compilerArgs += [
        '-processor',
        'org.springframework.data.mongodb.repository.support.MongoAnnotationProcessor'
    ]
}
~~~

**querydslVersion** is a property declared in your project configuration. With Spring Boot, Spring Data dependencies should be managed consistently through the project's BOM or plugin.

Explanation:

1. **querydsl-mongodb** provides Querydsl integration for MongoDB.
2. Exclude **mongo-java-driver** pulled transitively by Querydsl to avoid conflicting with the driver managed by Spring Data.
3. **querydsl-apt** provides the Q-class source generation tooling.
4. **annotationProcessor spring-data-mongodb** places `MongoAnnotationProcessor` on the processor classpath.
5. The **-processor** compiler flag activates the MongoDB processor by its fully qualified class name.

### 6.1. Q-Class Output Path in Gradle

With the Java plugin, generated sources usually appear under:

~~~text
build/generated/sources/annotationProcessor/java/main/
    com/example/catalog/QProductDocument.java
~~~

Check that file after compiling. If it is absent, adding `import ... QProductDocument` in the repository will not cause the class to be generated.

### 6.2. Multiple Annotation Processors

When specifying **-processor** explicitly, the Java compiler may stop auto-discovering and running other annotation processors. If your project uses Lombok, MapStruct, or custom processors, configure the complete processor list/path and verify with a clean build.

Errors such as "mapper not generated" or "missing getter" after enabling Querydsl often stem from altering processor settings rather than Querydsl APIs themselves.

## 7. Maven: Configuring MongoAnnotationProcessor

Essential snippets for `pom.xml`:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-mongodb</artifactId>
    </dependency>

    <dependency>
        <groupId>com.querydsl</groupId>
        <artifactId>querydsl-mongodb</artifactId>
        <version>${querydsl.version}</version>
        <exclusions>
            <exclusion>
                <groupId>org.mongodb</groupId>
                <artifactId>mongo-java-driver</artifactId>
            </exclusion>
        </exclusions>
    </dependency>

    <dependency>
        <groupId>com.querydsl</groupId>
        <artifactId>querydsl-apt</artifactId>
        <version>${querydsl.version}</version>
        <classifier>jakarta</classifier>
        <scope>provided</scope>
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <annotationProcessors>
                    <annotationProcessor>
                        org.springframework.data.mongodb.repository.support.MongoAnnotationProcessor
                    </annotationProcessor>
                </annotationProcessors>
                <generatedSourcesDirectory>
                    target/generated-sources/annotations
                </generatedSourcesDirectory>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

This is a **POM snippet** to merge into a project that already defines a parent/BOM, properties, and compiler setup; it is not a standalone runnable `pom.xml`. The project must declare **querydsl.version** compatible with the framework in use.

With newer Maven Compiler Plugin/JDK versions, you may need **annotationProcessorPaths** or processor dependency configuration specific to your compiler plugin version. When configuring an isolated processor path, place both Querydsl APT and Spring Data MongoDB processor (along with required dependencies) onto that path. Never add a JPA processor while omitting `MongoAnnotationProcessor`.

### 7.1. Maven Generated Sources Directory

~~~text
target/generated-sources/annotations/
    com/example/catalog/QProductDocument.java
~~~

IDEs sometimes need a Maven project reload or marking that directory as a generated source root. If CLI compilation succeeds while the IDE reports `QProductDocument` missing, check IDE settings before changing application code.

### 7.2. Generated Code Is Not Handwritten Source

Never copy `QProductDocument` into **src/main/java** to patch around APT errors. That leads to:

- Duplicate Q-type classes once the compiler generates another copy.
- Stale Q-types after renaming properties.
- CI builds diverging from an IDE using outdated generated files.

Keep Q-types in generated sources and maintain an explicit policy if your project ever commits generated code to version control.

## 8. Querydsl Compatibility, Fork, Jakarta, and Driver

Current Spring Data MongoDB documentation notes that Querydsl has an active community fork under **OpenFeign**, groupId **io.github.openfeign.querydsl**, supported on a **best-effort** basis. Some older projects use `com.querydsl`.

The Gradle/Maven examples above use groupId **com.querydsl** per official integration documentation. If switching to the fork, you must choose a **consistent** set of compatible artifacts and versions rather than merely editing the groupId on a single dependency.

### 8.1. javax/jakarta Namespace Errors

If compilation reports missing `jakarta` or `javax` classes:

1. Check Spring Data and Querydsl versions.
2. Check the **querydsl-apt** classifier.
3. Check the compiler annotation processor path.
4. Inspect the dependency tree for incompatible transitive libraries.

Never fix this by throwing multiple versions of `querydsl-core`/`querydsl-apt` or both namespaces into the same project.

### 8.2. MongoDB Driver Conflicts

Some Querydsl artifacts can pull in an older MongoDB driver. In Spring Boot applications, let Spring Data/BOM manage the driver and exclude legacy transitive driver dependencies as guided. Inspect the dependency tree and run integration tests after every upgrade.

## 9. Extending Repositories with QuerydslPredicateExecutor

~~~java
package com.example.catalog;

import org.bson.types.ObjectId;
import org.springframework.data.mongodb.repository.MongoRepository;
import org.springframework.data.querydsl.QuerydslPredicateExecutor;

public interface ProductRepository
        extends MongoRepository<ProductDocument, ObjectId>,
                QuerydslPredicateExecutor<ProductDocument> {
}
~~~

The repository gains operations accepting a `Predicate`:

~~~java
QProductDocument p = QProductDocument.productDocument;
var predicate = p.tenantId.eq("shop-a")
    .and(p.active.isTrue());

Iterable<ProductDocument> products =
    repository.findAll(predicate);

long count = repository.count(predicate);
boolean exists = repository.exists(predicate);
~~~

**Do not inject QProductDocument as a Spring bean**. It is generated code exposing a static path instance for Java usage:

~~~java
QProductDocument p = QProductDocument.productDocument;
~~~

`QuerydslPredicateExecutor` is a repository extension; it does not replace `MongoRepository` and does not require you to write implementations for these standard methods.

## 10. Common Typed Query Conditions

~~~java
QProductDocument p = QProductDocument.productDocument;

var byName = p.name.eq("Hands-on Spring Data MongoDB");
var selling = p.active.isTrue();
var inStock = p.stock.gt(0);

var priceRange = p.priceMinor.between(
    100_000L, 300_000L
);

var minPrice = p.priceMinor.goe(100_000L);
var maxPrice = p.priceMinor.loe(300_000L);

var nameSearch = p.name.containsIgnoreCase("mongodb");
var skuPrefix = p.sku.startsWithIgnoreCase("BOOK");
~~~

Operator names to know:

| Operator | Meaning |
| --- | --- |
| eq(value) | Equal |
| ne(value) | Not equal |
| gt(value) | Greater than |
| goe(value) | Greater than or equal |
| lt(value) | Less than |
| loe(value) | Less than or equal |
| between(a,b) | Within range per type/path semantics |
| isTrue(), isFalse() | Boolean condition |
| containsIgnoreCase(s) | Case-insensitive substring match if supported by serializer |
| startsWithIgnoreCase(s) | Case-insensitive prefix match if supported by serializer |

Combining multiple conditions:

~~~java
import com.querydsl.core.types.Predicate;

Predicate predicate = p.tenantId.eq("shop-a")
    .and(p.active.isTrue())
    .and(p.priceMinor.goe(100_000L))
    .and(p.priceMinor.loe(300_000L))
    .and(p.stock.gt(0));

Iterable<ProductDocument> result =
    repository.findAll(predicate);
~~~

Querydsl enforces type-appropriate operators at compile time. Still, compiling in Java does not prove the MongoDB serializer supports every operator in every combination; verify complex cases at runtime.

## 11. AND/OR: Group Conditions Before Binding Tenant

Requirement: products belonging to `shop-a`, currently active, and **(name contains "mongo" or SKU starts with "BOOK")**.

~~~java
QProductDocument p = QProductDocument.productDocument;

var textSearch = p.name.containsIgnoreCase("mongo")
    .or(p.sku.startsWithIgnoreCase("BOOK"));

var predicate = p.tenantId.eq("shop-a")
    .and(p.active.isTrue())
    .and(textSearch);
~~~

Logical form:

\[
\text{tenant = shop-a}
\land \text{active = true}
\land (\text{name contains mongo}\ \lor\ \text{sku startsWith BOOK})
\]

**It is a security bug** to write `A.and(B).or(C)` and accidentally allow branch `C` to bypass the tenant filter. Group user-supplied optional filters first, then **AND the tenant and policy predicates at the outermost level**.

If queries permit multi-level nested ORs, write unit tests inspecting expression structure and integration tests using data from at least two tenants.

## 12. BooleanBuilder for Dynamic Filters

Search input:

~~~java
public record ProductFilter(
    String keyword,
    Long minPriceMinor,
    Long maxPriceMinor,
    Boolean activeOnly
) {}
~~~

Builder:

~~~java
package com.example.catalog;

import com.querydsl.core.BooleanBuilder;
import com.querydsl.core.types.Predicate;

public final class ProductPredicates {

    private ProductPredicates() {}

    public static Predicate forSearch(
            String authenticatedTenantId,
            ProductFilter filter) {

        if (authenticatedTenantId == null
                || authenticatedTenantId.isBlank()) {
            throw new IllegalArgumentException("Tenant required");
        }
        if (filter == null) {
            throw new IllegalArgumentException("Filter required");
        }
        if (filter.minPriceMinor() != null
                && filter.maxPriceMinor() != null
                && filter.minPriceMinor() > filter.maxPriceMinor()) {
            throw new IllegalArgumentException("Invalid price range");
        }

        QProductDocument p = QProductDocument.productDocument;
        BooleanBuilder builder = new BooleanBuilder();

        // Mandatory predicate, never taken from untrusted client input.
        builder.and(p.tenantId.eq(authenticatedTenantId));

        if (filter.keyword() != null
                && !filter.keyword().isBlank()) {
            String keyword = filter.keyword().trim();
            builder.and(
                p.name.containsIgnoreCase(keyword)
                    .or(p.sku.containsIgnoreCase(keyword))
            );
        }

        if (filter.minPriceMinor() != null) {
            builder.and(p.priceMinor.goe(
                filter.minPriceMinor()
            ));
        }

        if (filter.maxPriceMinor() != null) {
            builder.and(p.priceMinor.loe(
                filter.maxPriceMinor()
            ));
        }

        if (Boolean.TRUE.equals(filter.activeOnly())) {
            builder.and(p.active.isTrue());
        }

        return builder;
    }
}
~~~

`BooleanBuilder` appends conditions only when parameters are present. It is **mutable**, so create a new builder per request; never store a singleton `BooleanBuilder` and mutate it across multiple users.

### 12.1. Null Has Two Very Different Meanings

When `minPriceMinor` is omitted, we **skip the lower bound** rather than searching for products whose price is `null`. Never overload a null input to mean both "do not filter" and "BSON field is null."

If business rules require finding documents with missing or null fields, add a dedicated filter option, document its exact semantics, and test legacy data.

### 12.2. Validate Instead of Relying Only on Type Safety

`BooleanBuilder` does not inherently know:

- Whether negative prices are valid.
- Whether a thousand-character keyword causes an expensive query.
- Whether `activeOnly=false` means "no filter" or "inactive only."
- Whether the client is permitted to filter on all properties.
- Whether regex/`contains` aligns with the application's collation and indexes.

Those rules live at the API/service layer before building the Predicate.

## 13. findAll, findOne, count, and exists

~~~java
QProductDocument p = QProductDocument.productDocument;
var predicate = p.tenantId.eq("shop-a")
    .and(p.active.isTrue());

Iterable<ProductDocument> rows =
    repository.findAll(predicate);

long total = repository.count(predicate);
boolean any = repository.exists(predicate);

var single = repository.findOne(
    p.tenantId.eq("shop-a")
        .and(p.sku.eq("BOOK-101"))
);
~~~

| Method | Meaning | Notes |
| --- | --- | --- |
| findAll(predicate) | Find all matching documents | Never return unbounded sets to APIs |
| findOne(predicate) | Find a single entity if present | Multiple matches may throw an error |
| count(predicate) | Count matching documents | Separate query with its own cost |
| exists(predicate) | Check if any matching document exists | Does not replace authorization |
| findAll(predicate, pageable) | Returns Page in sync executor | Includes metadata, may trigger count |
| findAll(predicate, orders...) | Sort via Q OrderSpecifier | Does not automatically cap result size |

### 13.1. findOne Is Not findFirst

If `name = "Book"` matches ten documents, do not use `findOne` to arbitrarily pick "the first document." Restrict with a unique key or use a list query with sort and limit.

For unique SKUs within a tenant, create:

~~~javascript
db.products.createIndex(
  { tenant_id: 1, sku: 1 },
  { unique: true }
);
~~~

That index enforces real uniqueness; a type-safe Predicate is no substitute for a unique constraint.

### 13.2. Count Is Not Free

If the UI only shows "Load more", you do not need to count total matching documents on every request. Counting can require scanning index keys or many documents. Consider `Slice`, `limit+1`, or keyset pagination where appropriate.

## 14. Typed Sorting and Synchronous Pagination

Q-paths produce **OrderSpecifier**s:

~~~java
Iterable<ProductDocument> ordered =
    repository.findAll(
        predicate,
        p.priceMinor.asc(),
        p.sku.asc()
    );
~~~

Pagination with `Page`:

~~~java
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

Pageable pageable = PageRequest.of(
    0,
    20,
    Sort.by(
        Sort.Order.asc("priceMinor"),
        Sort.Order.asc("id")
    )
);

Page<ProductDocument> page =
    repository.findAll(predicate, pageable);
~~~

`PageRequest` page numbers start at 0. Adding `id` as a secondary sort key ensures deterministic ordering when multiple documents share the same price.

**Note:** `Sort` in `PageRequest` still takes string property names. If accepting sort criteria from HTTP requests, restrict them to an allowlist of permitted fields:

~~~java
Sort sort = switch (requestedSort) {
    case "price-asc" -> Sort.by(
        Sort.Order.asc("priceMinor"),
        Sort.Order.asc("id")
    );
    case "name-asc" -> Sort.by(
        Sort.Order.asc("name"),
        Sort.Order.asc("id")
    );
    default -> Sort.by(Sort.Order.asc("id"));
};
~~~

Never allow callers to sort by internal or unindexed fields unless explicitly permitted by business rules.

### 14.1. Ordering Under Data Mutations

Offset pagination can duplicate or skip items if another writer inserts/deletes products between two reads. The secondary `id` key keeps a fixed snapshot ordered clearly, yet does not create snapshot isolation. At very large scale, consider keyset/seek pagination with matching cursor sort keys.

## 15. Embedded Object and Array Paths

Suppose `ProductDocument` is extended with:

~~~java
public class SupplierInfo {
    private String code;
    private String region;

    public SupplierInfo() {}
    public String getCode() { return code; }
    public String getRegion() { return region; }
}
~~~

and adds a `supplier` field:

~~~java
private SupplierInfo supplier;
~~~

When the processor generates the corresponding nested path, syntax can look like:

~~~java
var bySupplier = QProductDocument.productDocument
    .supplier.code.eq("SUP-01");
~~~

**Do not assume every nested path exists automatically**: how Q-types expand embedded objects depends on metadata, APT capabilities, and path-generation settings. Inspect the actual generated Q-class, especially with collections, maps, polymorphism, or custom converters.

### 15.1. Collection Properties

With `tags` as `List<String>`, a generated path may allow:

~~~java
var tagged = QProductDocument.productDocument
    .tags.contains("MONGODB");
~~~

Just because a method compiles does not guarantee the Spring Data MongoDB serializer translates every collection predicate into expected BSON. For arrays of embedded documents requiring multiple criteria on **the same element**, understanding **$elemMatch** is essential.

### 15.2. Querydsl Is Not SQL JOIN

Do not assume a Q-path referencing another entity enables JPA-style JOINs. Spring Data MongoDB documentation notes limitations on DBRef joins, especially in reactive support. When you need **$lookup**, **$group**, or **$project** to join or transform documents, use aggregation.

## 16. @Field and _id: Compile-Time vs. BSON Runtime

In Java:

~~~java
@Field("tenant_id")
private String tenantId;
~~~

The predicate still uses:

~~~java
var predicate = p.tenantId.eq("shop-a");
~~~

Yet MongoDB stores **tenant_id**. The Spring Data mapping layer translates Java property paths to BSON fields. Therefore, an essential test verifies both raw BSON and repository output:

1. Insert a `ProductDocument` with `tenantId=shop-a`.
2. Read raw BSON to confirm **tenant_id** exists.
3. Call `repository.findAll(p.tenantId.eq("shop-a"))`.
4. Verify the right product is returned.
5. Seed another tenant's product and verify it is never returned.

The Java property **id** maps to BSON **_id**. The raw MongoDB Java Driver knows nothing about the entity's `id` property; direct driver calls must use the BSON field name.

## 17. ReactiveQuerydslPredicateExecutor

With `ReactiveMongoRepository`:

~~~java
package com.example.catalog;

import org.bson.types.ObjectId;
import org.springframework.data.mongodb.repository.ReactiveMongoRepository;
import org.springframework.data.querydsl.ReactiveQuerydslPredicateExecutor;

public interface ReactiveProductRepository
        extends ReactiveMongoRepository<ProductDocument, ObjectId>,
                ReactiveQuerydslPredicateExecutor<ProductDocument> {
}
~~~

Usage:

~~~java
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

QProductDocument p = QProductDocument.productDocument;
var predicate = p.tenantId.eq("shop-a")
    .and(p.active.isTrue());

Flux<ProductDocument> result =
    reactiveRepository.findAll(predicate);

Mono<Long> total =
    reactiveRepository.count(predicate);

Mono<Boolean> exists =
    reactiveRepository.exists(predicate);
~~~

For typed sorting:

~~~java
Flux<ProductDocument> sorted =
    reactiveRepository.findAll(
        predicate,
        p.priceMinor.asc(),
        p.sku.asc()
    );
~~~

### 17.1. Pageable in the Reactive Executor

**Do not assume** the synchronous executor's `Pageable` overload exists with the same signature in the reactive executor:

~~~java
// Do not treat this as a guaranteed API across every ReactiveQuerydslPredicateExecutor:
reactiveRepository.findAll(predicate, pageable);
~~~

Spring Data MongoDB documentation describes the reactive executor with `Flux`/`Mono` and `Sort`/`OrderSpecifier` overloads, `count`, `exists`, and fluent `findBy`. When reactive pagination via limit/skip or keysets is needed, use APIs available in your running version, or **ReactiveMongoTemplate** with `Query`/`Criteria` pushed down to MongoDB.

**Never load an entire Flux via `collectList` just to slice pages in Java.** Limits must be applied at the database.

### 17.2. Do Not Block and Do Not Subscribe Twice

`Mono`/`Flux` from a repository executes only upon subscription. In WebFlux, never call **block()** to wait for `count` or `findAll`. Also never call `subscribe()` yourself and then return the same publisher for the framework to subscribe again.

## 18. Search Service with Tenant Scoping and Page Size Limits

~~~java
package com.example.catalog;

import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Sort;

public class ProductSearchService {

    private final ProductRepository repository;

    public ProductSearchService(ProductRepository repository) {
        this.repository = repository;
    }

    public Page<ProductDocument> search(
            String authenticatedTenantId,
            ProductFilter filter,
            int page,
            int size) {

        if (page < 0 || size < 1 || size > 100) {
            throw new IllegalArgumentException("Invalid page or size");
        }

        var predicate = ProductPredicates.forSearch(
            authenticatedTenantId, filter
        );

        var pageable = PageRequest.of(
            page, size,
            Sort.by(
                Sort.Order.asc("priceMinor"),
                Sort.Order.asc("id")
            )
        );

        return repository.findAll(predicate, pageable);
    }
}
~~~

**authenticatedTenantId** must come from a principal/session/token or trusted authorization context. Never simply accept `tenantId` from a URL parameter and pass it into the filter.

### 18.1. DTOs Are a Separate Response Contract

Querydsl filters **which documents match**; it does not create a projection fetching only a few fields. Public endpoints should use DTOs:

~~~java
public record ProductCardDto(
    String id,
    String sku,
    String name,
    long priceMinor
) {}
~~~

~~~java
public ProductCardDto toCard(ProductDocument p) {
    return new ProductCardDto(
        p.getId().toHexString(),
        p.getSku(),
        p.getName(),
        p.getPriceMinor()
    );
}
~~~

DTOs control what is exposed externally, but if you need to **reduce the BSON fields transferred from MongoDB**, design a projection or fluent query/`Query.fields()` accordingly. Do not confuse Java DTO mapping with database projection.

### 18.2. Avoid Letting Clients Construct Unbounded Predicates

Spring Data supports **@QuerydslPredicate** for certain web binding patterns. If used, whitelist fields/operators and exclude sensitive fields using mechanisms such as **QuerydslBinderCustomizer**. The tenant condition must still be added server-side to the final Predicate regardless of whatever filter the caller sends.

## 19. When to Use Querydsl, Criteria, or Aggregation?

| Problem | Suitable tool |
| --- | --- |
| Fixed filters, few parameters | Derived repository methods |
| Optional multi-field filters, type safety desired | Querydsl BooleanBuilder |
| Queries needing specialized MongoDB operators | MongoTemplate Query/Criteria |
| Partial field reads, DTO projections | Repository projection / MongoTemplate fields |
| `$group`, `$lookup`, `$project`, `$filter` | Aggregation / `@Aggregation` |
| Bulk writes, updates with `arrayFilters` | MongoTemplate |
| Reactive queries with custom paging/cursors | ReactiveMongoTemplate or supported APIs |
| Authorization rules, transactions | Dedicated service/transaction boundaries |

`QuerydslPredicateExecutor` **does not replace `MongoTemplate`**, does not create indexes, does not provide SQL JOINs, and does not manage transactions.

If a query needs Q-type filters combined with projections, collation, hints, aggregations, and complex business rules, consider a **custom repository fragment** with `MongoTemplate` instead of stuffing everything into a single Predicate.

## 20. Performance: Type-Safe Does Not Mean Optimal Query

A predicate:

~~~java
var predicate = p.tenantId.eq(tenantId)
    .and(p.active.isTrue())
    .and(p.priceMinor.between(100_000L, 300_000L));
~~~

corresponds in intent to BSON filter:

~~~javascript
db.products.find({
  tenant_id: "shop-a",
  active: true,
  priceMinor: { $gte: 100000, $lte: 300000 }
});
~~~

A compound index to evaluate:

~~~javascript
db.products.createIndex({
  tenant_id: 1,
  active: 1,
  priceMinor: 1
});
~~~

Putting equality fields before the range field can help this query pattern. However, effectiveness depends on data distribution, selectivity, sorting, projections, and workload.

### 20.1. Watch Out for containsIgnoreCase

~~~java
p.name.containsIgnoreCase("mongodb")
~~~

Case-insensitive substring matching may require pattern matching. **Do not assume a B-tree index on `name` optimizes every `contains` operation**, especially without a fixed prefix.

If requirements call for lexical search, relevance scoring, or linguistic analysis, evaluate text indexes or dedicated search solutions rather than assuming Querydsl replaces a search engine.

### 20.2. Run explain on the Real BSON Filter

~~~javascript
db.products.find({
  tenant_id: "shop-a",
  active: true,
  priceMinor: { $gte: 100000, $lte: 300000 }
}).explain("executionStats");
~~~

| Metric | What to verify |
| --- | --- |
| winningPlan | Is an appropriate index used? |
| totalKeysExamined | How many index keys were scanned? |
| totalDocsExamined | How many source documents were read? |
| nReturned | How many documents matched? |
| SORT and FETCH | Are there expensive sort/fetch stages? |
| executionTimeMillis | What is the actual latency? |

A compiling predicate does not prove MongoDB is using the expected fields, indexes, or collation. With `@Field`/custom converters, inspect the actual BSON filter executed by the framework.

## 21. Integration Testing a Querydsl Repository

Mocking the repository in tests can verify that a service builds a Predicate accurately in Java, yet **cannot prove that the processor generates Q-types or that MongoDB executes the filter properly**. At least one integration test against a dedicated test MongoDB, such as Testcontainers, is required.

~~~java
package com.example.catalog;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.ArrayList;
import java.util.List;
import java.util.UUID;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.mongo.DataMongoTest;

@DataMongoTest
class ProductQuerydslTest {

    @Autowired ProductRepository repository;

    @Test
    void filtersByTenantActiveAndPrice() {
        String tenant = "TEST-" + UUID.randomUUID();
        String otherTenant = "OTHER-" + UUID.randomUUID();

        ProductDocument a = repository.save(
            new ProductDocument(
                tenant, "TEST-BOOK", "MongoDB Book", true, 150_000L, 10
            )
        );
        ProductDocument b = repository.save(
            new ProductDocument(
                tenant, "TEST-PEN", "Pen", false, 20_000L, 5
            )
        );
        ProductDocument other = repository.save(
            new ProductDocument(
                otherTenant, "TEST-OTHER", "Other Book", true, 140_000L, 3
            )
        );

        try {
            QProductDocument p = QProductDocument.productDocument;
            var predicate = p.tenantId.eq(tenant)
                .and(p.active.isTrue())
                .and(p.priceMinor.goe(100_000L));

            List<ProductDocument> found = new ArrayList<>();
            repository.findAll(predicate).forEach(found::add);

            assertThat(found)
                .extracting(ProductDocument::getSku)
                .containsExactly("TEST-BOOK");

            assertThat(repository.count(predicate)).isEqualTo(1L);
            assertThat(repository.exists(predicate)).isTrue();
        } finally {
            repository.deleteAllById(
                List.of(a.getId(), b.getId(), other.getId())
            );
        }
    }
}
~~~

This test verifies:

1. `QProductDocument` was generated and compiles.
2. The repository's `QuerydslPredicateExecutor` works.
3. Java `tenantId` maps to BSON **`tenant_id`**.
4. Active/price filters exclude non-matching products.
5. Products from other tenants are not returned.
6. `count`/`exists` using the same predicate produce matching results.

**Run only on a test database**, never on production.

### 21.1. Verifying Raw BSON Field Names

In a test with `mongoTemplate`, `saved`, and `tenant` available:

~~~java
import org.bson.Document;
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;

Document raw = mongoTemplate.findOne(
    Query.query(Criteria.where("_id").is(saved.getId())),
    Document.class,
    "products"
);

assertThat(raw).isNotNull();
assertThat(raw.getString("tenant_id")).isEqualTo(tenant);
assertThat(raw.containsKey("tenantId")).isFalse();
~~~

This snippet inspects **real MongoDB data**, not just mapped Java objects.

### 21.2. Dynamic Filter Test Matrix

| Input | Expected result |
| --- | --- |
| No optional filters | Applies tenant scope only |
| activeOnly=true | Tenant AND active=true |
| minPrice only | Tenant AND priceMinor >= min |
| minPrice and maxPrice | Tenant AND price within range |
| Keyword | Tenant AND (name OR sku) |
| minPrice > maxPrice | Throws validation error |
| Empty tenant | Rejects query |
| Keyword matches name in another tenant | Does not return other tenant's records |

For nested array/collection paths, add runtime tests verifying real MongoDB semantics rather than only testing `Predicate.toString()`.

## 22. Common Pitfalls and How to Fix Them

| Symptom | Cause | Fix |
| --- | --- | --- |
| Cannot find symbol `QProductDocument` | APT did not run or source path unrecognized | Check `MongoAnnotationProcessor` and generated sources |
| Only JPA Q-types generated | JPA processor active instead of Mongo processor | Use `MongoAnnotationProcessor` |
| jakarta/javax errors | Mismatched classifier or versions | Align Querydsl, Spring Data, compiler |
| Missing Querydsl runtime classes | Incompatible artifacts or missing dependency | Inspect dependency tree |
| Legacy MongoDB driver present | `querydsl-mongodb` pulled older dependency | Exclude it and let Spring Data manage driver |
| IDE shows red errors while build succeeds | IDE has not registered generated folder | Reload Maven/Gradle |
| CI lacks Q-types | Local machine relied on stale generated files | Run clean compile in CI |
| Q-type has old properties | Not regenerated after entity change | Run clean build |
| MapStruct/Lombok skipped | `-processor` specified only `MongoAnnotationProcessor` | Configure all needed processors |
| Predicate compiles yet query matches nothing | `@Field`/BSON mapping differs from assumption | Test raw BSON and query results |
| `findOne` fails with multiple results | Non-unique predicate | Add unique filter/index |
| OR leaks cross-tenant data | Wrong OR/AND grouping | Always AND tenant outside search group |
| Search API slow | Missing index or hard-to-index `contains` | Run `explain` |
| Reactive lacks `findAll(predicate,pageable)` | Assuming sync APIs exist on reactive | Use supported overloads or `ReactiveMongoTemplate` |
| Client filters on sensitive fields | Unwhitelisted web binding | Restrict binding and authorization |

### 22.1. Checklist for Missing Q-Classes

1. Entity sits in a compiled source set with proper `@Document`.
2. `querydsl-mongodb` and `querydsl-apt` have compatible versions.
3. `MongoAnnotationProcessor` is enabled.
4. All processor dependencies are present in the build.
5. Q-class appears under target/build generated sources.
6. IDE project has been reloaded.
7. No other processor was excluded by `-processor`.
8. Error persists or disappears after a clean build.
9. Integration tests execute Predicates cleanly.

**Never edit generated Q-classes by hand**. If properties are missing, fix the entity/processor and regenerate.

## 23. Practice Exercises

### Exercise 1: Are Q-Types Entities?

**Question:** Do we store `QProductDocument` in MongoDB?

**Answer:** No. `QProductDocument` is a generated Java type for Predicates; `ProductDocument` is the entity mapped to the collection.

### Exercise 2: The Right Processor

An entity has `@Document` yet no Q-class is generated; the project only configures `JPAAnnotationProcessor`. How do you fix it?

**Answer:** Enable **org.springframework.data.mongodb.repository.support.MongoAnnotationProcessor**, add the matching processor dependencies, compile, and inspect generated sources.

### Exercise 3: Price Filtering

~~~java
var condition = p.active.isTrue()
    .and(p.priceMinor.goe(100_000L))
    .and(p.priceMinor.loe(200_000L));
~~~

**Meaning:** active products with prices between 100,000 and 200,000.

### Exercise 4: Optional Parameters

Does `minPrice=null` mean querying for `priceMinor = null`?

**Answer:** No; under the search contract in this example, a null `minPrice` means **skip the minimum price condition**.

### Exercise 5: OR and Tenant

~~~java
var search = p.name.containsIgnoreCase("mongo")
    .or(p.sku.containsIgnoreCase("book"));

var secured = p.tenantId.eq("shop-a").and(search);
~~~

**Explanation:** group the OR conditions first, then AND with tenant.

### Exercise 6: findOne

If `p.name.eq("Book")` matches ten documents, can you use `findOne` to grab an arbitrary one?

**Answer:** No. `findOne` expects at most one result; use a unique filter or query a list with sort and limit.

### Exercise 7: Synchronous Pagination

**Question:** An admin API needs `Page` and total count. Which API should you choose?

**Answer:** `QuerydslPredicateExecutor.findAll(predicate, Pageable)`, backed by suitable indexes/sorts and awareness of count overhead.

### Exercise 8: Reactive

~~~java
interface ReactiveProductRepository
        extends ReactiveMongoRepository<ProductDocument, ObjectId>,
                ReactiveQuerydslPredicateExecutor<ProductDocument> {}

Mono<Long> total = reactiveRepository.count(predicate);
~~~

**Note:** do not assume a `Pageable` overload exists on the reactive executor.

### Exercise 9: @Field

Java uses `p.tenantId` while BSON stores `tenant_id`. Why?

**Answer:** Q-types mirror Java properties, while Spring Data mapping translates BSON field names. Integration tests must verify this behavior.

### Exercise 10: Type Safety vs. Indexes

`p.name.containsIgnoreCase("java")` compiles. Is the query guaranteed fast?

**Answer:** No. Type safety does not create indexes or optimize regex/pattern matching. Run `explain` and examine the workload.

### Exercise 11: Malicious Input

A client sends another `tenantId` in a Querydsl web filter. How should the server handle it?

**Answer:** Never treat client-supplied tenant values as authorization. Ignore/reject tenant binding and AND the authenticated tenant into the Predicate.

### Exercise 12: Aggregation

A query needs `$lookup` on suppliers and `$group` by region. Is `QuerydslPredicateExecutor` the best choice?

**Answer:** No. Use Spring Data MongoDB/`MongoTemplate` aggregation; Querydsl is better suited for dynamic entity filtering.

## 24. Production Checklist

- Entity has accurate `@Document`, `@Id`, and `@Field` annotations.
- `MongoAnnotationProcessor` is enabled at compile time.
- Maven/Gradle/IDE/CI all generate Q-classes from a clean build.
- Querydsl core/mongodb/apt belong to the same compatible version line.
- `jakarta`/`javax` aligns with the framework generation.
- Legacy conflicting MongoDB drivers are excluded in the dependency tree.
- Repository extends the appropriate sync/reactive `QuerydslPredicateExecutor`.
- Predicates always enforce tenant and permission predicates from an authenticated context.
- A fresh `BooleanBuilder` is created per request; mutable builders are never shared.
- Keywords, prices, page sizes, and sorts are validated/bounded.
- Querydsl web binding prevents filtering on arbitrary sensitive fields.
- DTOs/projections prevent leaking internal entity fields.
- `@Field`/nested paths/arrays are covered by MongoDB integration tests.
- Indexes and `explain` are evaluated against actual BSON queries.
- Sync Querydsl syntax or overloads are not assumed identical on reactive repositories.

## 25. Summary

1. **Q-types** are Java classes auto-generated from entities to build typed query paths.
2. Spring Data MongoDB integrates via **MongoAnnotationProcessor**, not merely the Querydsl JPA processor.
3. **QuerydslPredicateExecutor** extends `MongoRepository` with Predicate-based `find`, `count`, `exists`, and paging.
4. **BooleanExpression** and **BooleanBuilder** compose AND/OR conditions, especially for optional filters.
5. **Always AND server-side tenant/authorization predicates**, never delegating access control to arbitrary client filters.
6. **@Field/@Id** are still translated to BSON by Spring Data mapping; test at runtime since the compiler does not inspect real database data.
7. **ReactiveQuerydslPredicateExecutor** uses `Mono`/`Flux` and offers a different API surface than the synchronous executor.
8. **Querydsl does not replace aggregations, `MongoTemplate`, transactions, or indexes**.
9. **Generated classes must be rebuilt by the build tool**; never edit Q-types by hand.
10. **Performance requires measuring with `explain` and proper indexes**; Q-types address only compile-time type safety.

Knowing how to **generate Q-types and build typed query conditions** helps **SPRING_DATA_MONGODB** services organize refactor-friendly extended repositories, construct safer dynamic filters, and coordinate properly with `MongoTemplate`, aggregations, reactive access, and real MongoDB testing.
