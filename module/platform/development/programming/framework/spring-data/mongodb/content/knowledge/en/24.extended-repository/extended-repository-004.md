# Querydsl and QuerydslPredicateExecutor in Supported Versions

## 1. The Problem: Dynamic Queries with Type Checking in Java

In the **Extended Repositories** chapter of **Spring Data MongoDB**, repositories often start with simple methods:

~~~java
List<CatalogProduct> findByStatus(String status);
List<CatalogProduct> findByTenantIdAndStatus(
        String tenantId, String status);
~~~

When a catalog screen offers many optional filters—tenant, status, minimum price, stock quantity, creation date—the number of derived methods can explode. One option is `MongoTemplate` with `Query`/`Criteria`. **Querydsl** is another option, letting you express predicates using **Java-typed property paths** generated from the model rather than string field names scattered across the codebase.

Example query semantics:

~~~text
tenantId = "tenant-a"
AND status = "ACTIVE"
AND stock >= 5
~~~

Once `QCatalogProduct` is generated by Querydsl, code can express this as:

~~~java
QCatalogProduct product = QCatalogProduct.catalogProduct;

Predicate predicate = product.tenantId.eq("tenant-a")
        .and(product.status.eq("ACTIVE"))
        .and(product.stock.goe(5));
~~~

`Predicate` comes from `com.querydsl.core.types.Predicate`. `QCatalogProduct` is not another MongoDB entity: it is a **query metamodel class** containing property paths such as `StringPath` and `NumberPath`.

Spring Data Commons provides the `QuerydslPredicateExecutor<T>` interface so repositories can execute Querydsl predicates in **modules and versions that supply a matching adapter**. Specifically for Spring Data MongoDB, you must verify support in your exact library version, Querydsl dependencies, and which query expressions the adapter translates to MongoDB.

**The scope of this lesson is intentionally bounded:** Querydsl is not a promise that every combination of Spring Data MongoDB, Querydsl, and MongoDB driver versions is compatible. This lesson explains how to use it **when supported by your version**, how to verify it yourself, common limitations, and how to fall back to `MongoTemplate` when no suitable adapter exists.

> Example context: Java 17+, Spring Boot 3.x, and Spring Data MongoDB releases that support Querydsl repositories. Never treat a Querydsl JPA example as proof that MongoDB supports the same operator; query translators and library generations differ. Every dependency configuration must lock compatible versions in your project and be verified via build/integration tests.

## 2. How Do Querydsl, Q-Types, Predicates, and Executors Differ?

| Component | Role | Example |
|---|---|---|
| **MongoDB Entity** | Declares data and Java ↔ BSON mapping | `CatalogProduct`, `@Document`, `@Field` |
| **Q-type** | Typed property path representation generated by an annotation processor | `QCatalogProduct` |
| **Predicate** | Conditional expression combinable with `and/or/not` | `product.stock.goe(5)` |
| **BooleanBuilder** | Builds a predicate when input has multiple optional filters | `new BooleanBuilder().and(...)` |
| **QuerydslPredicateExecutor** | Repository interface defining find/count/exists by Querydsl Predicate | `findAll(predicate)`, `count(predicate)` |
| **Spring Data MongoDB Querydsl Adapter** | Translates predicates to MongoDB operations, if supported by the version | Repository implementation path |
| **MongoTemplate/Criteria** | Direct Spring Data MongoDB API without Q-types | `Criteria.where("stock").gte(5)` |

Conceptual execution flow:

~~~mermaid
flowchart TD
    A["Java entity with @QueryEntity"] --> B["Querydsl annotation processor"]
    B --> C["QCatalogProduct generated at build time"]
    C --> D["Predicate / BooleanBuilder"]
    D --> E["QuerydslPredicateExecutor repository"]
    E --> F["MongoDB Querydsl adapter if supported"]
    F --> G["BSON filter / sort / pagination"]
    G --> H["MongoDB server"]
    H --> I["Entity / Page / count / exists"]
~~~

The Q-type tells the compiler that `stock` is numeric and `status` is a string. It **does not automatically** guarantee business correctness, proper indexes, or that every Querydsl operator translates into MongoDB query language.

### 2.1. Type Safety and Its Limits

With Querydsl, mistakes like invoking numeric comparisons on a string property are caught early via path types. Renaming `stock` on the entity and regenerating Q-types causes outdated `product.stock` references to fail compilation.

However:

- A valid Java expression may still **be unsupported by the MongoDB adapter**.
- Null/missing fields, embedded arrays, and regexes have MongoDB-specific semantics.
- Querydsl does not create indexes, transactions, or tenant isolation.
- Q-types reflect metadata at generation time; stale generated code or incomplete mapping metadata requires verification.

Thus **type-safe** does not mean **database-semantics-safe**.

## 3. Prerequisite: Confirm Exact Version Support

Before implementing, answer these questions on your **real project**:

1. Does your **Spring Data MongoDB** version provide a repository implementation for `QuerydslPredicateExecutor<CatalogProduct>`? Do not merely check that the interface exists in Spring Data Commons.
2. Which Querydsl artifacts match that Spring Data generation? `querydsl-core`, `querydsl-apt`, and—if needed by the adapter—`querydsl-mongodb` must have compatible versions.
3. Does Java use the `javax` or `jakarta` namespace? Annotation processors tied to JPA annotations require the matching classifier/APT setup; a project using only `@QueryEntity` may configure differently from a JPA project.
4. Are there transitive conflicts with the MongoDB Java Driver or other dependencies? Older `querydsl-mongodb` generations can pull in an older driver.
5. Does the build actually generate `QCatalogProduct`, and does the repository initialize at runtime/test startup?
6. Do comparisons, sorting, nested fields, and arrays generate accurate BSON?

Avoid simplistic assumptions:

~~~text
"spring-data-commons is on the classpath"
     => "MongoDB definitely has a Querydsl adapter"
~~~

Each Spring Data module chooses its own integration scope. Many online tutorials target **Querydsl JPA** or SQL; they are not guaranteed to work verbatim with MongoDB.

### 3.1. Support Scope Must Be Checked Per Release

| Environment | Approach |
|---|---|
Spring Data MongoDB version with compatible Querydsl adapter | Can use `QuerydslPredicateExecutor` after configuring Q-types and verifying |
New/unverified Spring Data MongoDB branch | **Do not assume support**; check release docs/API and integration tests |
Querydsl JPA configured from another tutorial | Do not copy blindly to MongoDB; verify artifacts and serializer |
Do not want annotation processor/adapter dependency | Use `MongoTemplate` + `Criteria` or a custom repository |
Queries needing aggregation, array-specialized operators, or conditional updates | Use appropriate MongoDB APIs instead of forcing everything into Predicate |

Differences in **version support** are part of architectural decision-making: if an adapter changes or disappears in an upgrade path, you need an alternative rather than coupling all business logic directly to Q-types.

## 4. MongoDB Entity and Sample Data

This example uses the `catalog_products` collection with three commonly filtered fields: tenant, status, and stock. We deliberately give BSON fields different names from Java properties to highlight the boundary between Querydsl and Spring Data mapping.

**CatalogProduct.java**

~~~java
package com.example.catalog;

import com.querydsl.core.annotations.QueryEntity;
import java.time.Instant;
import java.util.List;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;
import org.springframework.data.mongodb.core.mapping.FieldType;
import org.springframework.data.mongodb.core.mapping.MongoId;

@QueryEntity
@Document(collection = "catalog_products")
public class CatalogProduct {
    @MongoId(FieldType.STRING)
    private String id;

    private String tenantId;
    private String sku;

    @Field("display_name")
    private String name;

    @Field("stock_qty")
    private long stock;

    private String status;
    private Instant createdAt;
    private List<String> tags;

    protected CatalogProduct() {
        // For MongoDB converter.
    }

    public CatalogProduct(
            String id, String tenantId, String sku,
            String name, long stock, String status,
            Instant createdAt, List<String> tags) {
        this.id = id;
        this.tenantId = tenantId;
        this.sku = sku;
        this.name = name;
        this.stock = stock;
        this.status = status;
        this.createdAt = createdAt;
        this.tags = tags;
    }

    public String getId() { return id; }
    public String getTenantId() { return tenantId; }
    public String getSku() { return sku; }
    public String getName() { return name; }
    public long getStock() { return stock; }
    public String getStatus() { return status; }
    public Instant getCreatedAt() { return createdAt; }
    public List<String> getTags() { return tags; }
}
~~~

`@QueryEntity` is a **Querydsl** annotation used for query type generation. `@Document`, `@MongoId`, and `@Field` are Spring Data MongoDB metadata. The two annotation layers serve **different phases**:

~~~text
@QueryEntity  -> processor generates QCatalogProduct at compile-time
@Document     -> Spring Data knows collection/mapping at runtime
@Field        -> Spring Data knows the physical BSON field name
~~~

Stored BSON example:

~~~json
{
  "_id": "p-101",
  "tenantId": "tenant-a",
  "sku": "BOTTLE-500",
  "display_name": "Water Bottle 500 ml",
  "stock_qty": 12,
  "status": "ACTIVE",
  "createdAt": { "$date": "2026-11-20T08:00:00Z" },
  "tags": ["outdoor", "premium"]
}
~~~

The `id` field maps to `_id`. For `String` IDs, `@MongoId(FieldType.STRING)` prevents 24-character hex strings from being converted into BSON ObjectId unexpectedly.

## 5. Generating QCatalogProduct via Annotation Processing

`QCatalogProduct` is not handwritten by developers. In a build supporting Querydsl APT, the annotation processor reads `@QueryEntity` and generates the Q class into the generated sources directory. Illustrative layout:

~~~text
src/main/java/com/example/catalog/CatalogProduct.java
build/generated/sources/annotationProcessor/java/main/
    com/example/catalog/QCatalogProduct.java
~~~

The actual generated sources path depends on Gradle/Maven, the IDE, and annotation processing setup. Never edit the generated Q file directly; update the entity and rebuild.

### 5.1. Dependencies Must Be Matched Compatibly

In a Gradle Groovy DSL project, configuration components may look like:

~~~groovy
// Choose a querydslVersion compatible with your Spring Data MongoDB
// and MongoDB Java Driver; do not treat this number as a
// universal recommendation for every project.
def querydslVersion = "5.1.0"

dependencies {
    implementation "com.querydsl:querydsl-core:$querydslVersion"
    annotationProcessor "com.querydsl:querydsl-apt:$querydslVersion"
    annotationProcessor "com.querydsl:querydsl-core:$querydslVersion"

    // Add only when required/permitted by your version's MongoDB adapter:
    // implementation "com.querydsl:querydsl-mongodb:$querydslVersion"
}

tasks.withType(JavaCompile).configureEach {
    options.compilerArgs += [
            "-processor", "com.querydsl.apt.QuerydslAnnotationProcessor"
    ]
}
~~~

**This is an APT configuration example for `@QueryEntity`, not an official BOM.** Real build systems may already manage processors alongside MapStruct/Lombok or use Maven. Never overwrite existing processor lists blindly. Across different Spring Data and Querydsl generations, an example using Querydsl 5.1.0 may **not** be the right match; apply the compatibility matrix for your chosen version.

For projects using `jakarta.persistence.*` in JPA models, Querydsl APT's `jakarta` classifier can be relevant; **do not** add the classifier merely because Spring Boot 3 uses Jakarta if MongoDB entities only carry `@QueryEntity`. Configure according to the exact annotation processor invoked and the annotations it needs to process.

### 5.2. Three-Step APT Verification

1. Confirm `@QueryEntity` compiles and the processor runs.
2. Locate `QCatalogProduct` in generated sources and check package `com.example.catalog`.
3. Write a minimal expression using `QCatalogProduct.catalogProduct.status.eq("ACTIVE")`, compile, and run a repository integration test.

If the IDE cannot see the Q-type while the CLI build generates it cleanly, verify that the IDE has annotation processing enabled and generated sources on its classpath. If CLI also fails to generate Q-types, check dependency scopes, processor class, namespace, and annotation processing logs.

Never copy a Q-type from another project with a different schema as a "quick fix": changed properties can cause wrong queries or leave stale Q classes on the classpath.

## 6. Declaring a Repository with QuerydslPredicateExecutor

When your **Spring Data MongoDB** version supports the Querydsl adapter and compatible dependencies, the repository can extend both interfaces:

**CatalogProductRepository.java**

~~~java
package com.example.catalog;

import org.springframework.data.mongodb.repository.MongoRepository;
import org.springframework.data.querydsl.QuerydslPredicateExecutor;

public interface CatalogProductRepository
        extends MongoRepository<CatalogProduct, String>,
                QuerydslPredicateExecutor<CatalogProduct> {
}
~~~

`MongoRepository` provides standard CRUD; `QuerydslPredicateExecutor` adds execution of Querydsl `Predicate`s. Spring Data creates the implementation via the module's repository factory, provided **the adapter and Querydsl classes are actually available**.

Core methods commonly available:

| Method | Meaning | Return type |
|---|---|---|
`findOne(Predicate)` | Find one result matching predicate | `Optional<T>` |
`findAll(Predicate)` | Find all matching results | `Iterable<T>` |
`findAll(Predicate, Sort)` | Find and sort | `Iterable<T>` |
`findAll(Predicate, Pageable)` | Find paged | `Page<T>` |
`count(Predicate)` | Count matching documents | `long` |
`exists(Predicate)` | Check if at least one document matches | `boolean` |
`findAll(Predicate, OrderSpecifier<?>...)` | Sort using Querydsl order expressions | `Iterable<T>` if adapter supports |

Newer Spring Data Commons releases may offer variants like fluent `findBy`; **do not assume every interface method from one release exists and is implemented identically by the MongoDB adapter across all releases**.

### 6.1. Do Not Mistake findOne for Fetching an Arbitrary First Record

`findOne(predicate)` expresses the expectation of finding **a single result**. If multiple documents match, the contract may throw an error due to non-uniqueness instead of picking an arbitrary document. When a predicate is not unique, use `findAll` with appropriate pagination/sorting.

If business rules allow at most one product per (`tenantId`, `sku`), a MongoDB **unique index** enforces that invariant—not `findOne` or `Optional<T>`.

### 6.2. The Executor Is Primarily a Read API

`QuerydslPredicateExecutor` is not a general DSL for calling `updateMany`/`deleteMany` from any predicate. When modifying fields, incrementing stock, or performing conditional deletes, use dedicated repository methods, `@Update`, `MongoTemplate`, or an appropriate custom repository. Do not force `Page` or `Predicate` to represent writes.

## 7. Simple Predicates: Comparing by Java Property

Example using Querydsl to filter active products with sufficient stock for a tenant:

~~~java
package com.example.catalog;

import com.querydsl.core.types.Predicate;
import java.util.ArrayList;
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class ProductQuerydslService {
    private final CatalogProductRepository products;

    public ProductQuerydslService(CatalogProductRepository products) {
        this.products = products;
    }

    public List<CatalogProduct> available(
            String tenantId, long minimumStock) {
        if (tenantId == null || tenantId.isBlank()
                || minimumStock < 0) {
            throw new IllegalArgumentException("Invalid filter");
        }

        QCatalogProduct p = QCatalogProduct.catalogProduct;
        Predicate where = p.tenantId.eq(tenantId)
                .and(p.status.eq("ACTIVE"))
                .and(p.stock.goe(minimumStock));

        List<CatalogProduct> result = new ArrayList<>();
        products.findAll(where).forEach(result::add);
        return result;
    }
}
~~~

Note that `findAll(Predicate)` returns `Iterable`; the example collects results into a `List` for caller convenience. Never load an unbounded collection via `findAll` if filters can be broad. Production APIs should limit or paginate.

The predicate above has the following BSON meaning:

~~~json
{
  "tenantId": "tenant-a",
  "status": "ACTIVE",
  "stock_qty": { "$gte": 5 }
}
~~~

In Java, the property remains `p.stock`; physical BSON is `stock_qty` because of `@Field("stock_qty")`. **This is a semantically equivalent representation, not a byte-for-byte guarantee of the driver command.** Verifying property-to-BSON mapping is one key thing to test when using the Querydsl MongoDB adapter.

### 7.1. Common Comparisons

| Querydsl expression | Logical meaning | Equivalent BSON in sample schema |
|---|---|---|
`p.status.eq("ACTIVE")` | Equality | `{ "status": "ACTIVE" }` |
`p.status.ne("DELETED")` | Inequality | `{ "status": { "$ne": "DELETED" } }` |
`p.stock.gt(10)` | Greater than | `{ "stock_qty": { "$gt": 10 } }` |
`p.stock.goe(10)` | Greater than or equal | `{ "stock_qty": { "$gte": 10 } }` |
`p.stock.lt(10)` | Less than | `{ "stock_qty": { "$lt": 10 } }` |
`p.stock.loe(10)` | Less than or equal | `{ "stock_qty": { "$lte": 10 } }` |
`p.status.in("ACTIVE", "PENDING")` | In set | `{ "status": { "$in": ["ACTIVE", "PENDING"] } }` |
`p.name.isNotNull()` | Non-null value | Must verify BSON null/missing semantics |
`p.tenantId.eq("tenant-a").and(...)` | Logical AND | Multiple conditions or `$and` |
`p.status.eq("ACTIVE").or(p.status.eq("PENDING"))` | Logical OR | `$or` or equivalent expression |

This table shows **commonly expected operators**; the MongoDB adapter does not necessarily support every Querydsl Core expression, and certain date, string, or null comparisons have semantics that require explicit testing.

With `$ne` on missing fields, MongoDB can match documents lacking the field. Do not confuse `isNotNull`/`ne` with verifying "field is required to exist and be valid" in every scenario.

## 8. BooleanBuilder: Creating Controlled Dynamic Filters

This is where Querydsl shines: an endpoint with multiple optional filters. Avoid creating dozens of `findByStatusAndStockGreaterThan...` methods for every combination.

**ProductSearch.java**

~~~java
package com.example.catalog;

public record ProductSearch(
        String status,
        Long minimumStock,
        Long maximumStock,
        String exactSku) {
}
~~~

**ProductSearchService.java**

~~~java
package com.example.catalog;

import com.querydsl.core.BooleanBuilder;
import com.querydsl.core.types.Predicate;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;

@Service
public class ProductSearchService {
    private final CatalogProductRepository products;

    public ProductSearchService(CatalogProductRepository products) {
        this.products = products;
    }

    public Page<CatalogProduct> search(
            String authenticatedTenantId,
            ProductSearch filter,
            int page,
            int size) {
        if (authenticatedTenantId == null
                || authenticatedTenantId.isBlank()
                || filter == null
                || page < 0 || size < 1 || size > 100) {
            throw new IllegalArgumentException("Invalid filter or page");
        }

        QCatalogProduct p = QCatalogProduct.catalogProduct;
        BooleanBuilder where = new BooleanBuilder();

        // Always include the trusted tenant in the filter.
        where.and(p.tenantId.eq(authenticatedTenantId));

        if (filter.status() != null && !filter.status().isBlank()) {
            where.and(p.status.eq(filter.status()));
        }
        if (filter.minimumStock() != null) {
            if (filter.minimumStock() < 0) {
                throw new IllegalArgumentException("minimumStock must be >= 0");
            }
            where.and(p.stock.goe(filter.minimumStock()));
        }
        if (filter.maximumStock() != null) {
            if (filter.maximumStock() < 0) {
                throw new IllegalArgumentException("maximumStock must be >= 0");
            }
            where.and(p.stock.loe(filter.maximumStock()));
        }
        if (filter.minimumStock() != null
                && filter.maximumStock() != null
                && filter.minimumStock() > filter.maximumStock()) {
            throw new IllegalArgumentException("Invalid stock range");
        }
        if (filter.exactSku() != null && !filter.exactSku().isBlank()) {
            where.and(p.sku.eq(filter.exactSku()));
        }

        Sort sort = Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.asc("id"));

        return products.findAll(
                where,
                PageRequest.of(page, size, sort));
    }
}
~~~

Key points:

1. `BooleanBuilder` builds a predicate from multiple independent criteria.
2. `tenantId` is added **unconditionally from the authenticated context**; clients cannot strip it.
3. Other filters are appended only when validly supplied.
4. `PageRequest` bounds the data and enforces stable sorting on `createdAt DESC, _id ASC`.
5. `Page<CatalogProduct>` returns page content along with total metadata, which may cause the framework to issue an extra count query.

For large datasets, never assume `Page` is cheap. If the UI only needs to know whether a next page exists, consider supported scrolling/cursor APIs or a custom repository with `MongoTemplate`. `QuerydslPredicateExecutor` does not inherently provide all `Slice`/keyset characteristics of other APIs.

### 8.1. Why Not Accept Predicates Directly from Clients?

An HTTP request may send:

~~~json
{
  "status": "ACTIVE",
  "minimumStock": 5,
  "maximumStock": 20,
  "exactSku": null
}
~~~

Parse it into a DTO with **allowed** fields, validate, and build the Predicate server-side. Never allow clients to send Querydsl class names, field paths, or arbitrary expressions for database execution, which can expose internal fields, trigger expensive regex queries, or bypass tenant checks.

If a Spring Data Web version supports `@QuerydslPredicate` to bind query parameters, that is an **optional web binding** feature—it does not replace authorization, field whitelisting, sort/pagination limits, or validation. An automatic predicate resolver can expose more properties than intended if unconfigured.

## 9. Using findOne, findAll, count, and exists

Besides `findAll(predicate)`, the executor offers inspection methods:

~~~java
QCatalogProduct p = QCatalogProduct.catalogProduct;

Predicate specific = p.tenantId.eq("tenant-a")
        .and(p.id.eq("p-101"));

Optional<CatalogProduct> one = products.findOne(specific);
boolean hasItem = products.exists(specific);
long exactMatches = products.count(specific);
~~~

This assumes a `products` variable of type `CatalogProductRepository` and `import java.util.Optional`. The predicate filters by ID and tenant, fitting the expectation of at most one document.

### 9.1. Result Types

- `findOne` returns `Optional<CatalogProduct>` when supported by the adapter. Never dereference without checking when `Optional.empty()`.
- `findAll` returns `Iterable<CatalogProduct>`, not `List` by default.
- `count` returns the number of matching documents at read time; not an updated count from a prior write.
- `exists` returns a boolean, which is only accurate at query time.

**`exists` is not a lock.** Two requests can simultaneously observe `exists == false` and then insert products with a duplicate business key. Use a unique index and handle duplicate-key errors rather than treating `exists` as uniqueness protection.

### 9.2. Do Not Treat findOne as a "Top 1" API

For instance, `p.status.eq("ACTIVE")` may match thousands of documents. Do not call `findOne` to grab "the newest product"; use a predicate with sorting and page size 1 instead:

~~~java
Page<CatalogProduct> newest = products.findAll(
        p.tenantId.eq("tenant-a").and(p.status.eq("ACTIVE")),
        PageRequest.of(0, 1,
                Sort.by(Sort.Order.desc("createdAt"),
                        Sort.Order.asc("id"))));
~~~

This example is easy to read, though `Page` may incur a count for metadata. If you only need the first record without total count, `MongoTemplate.findOne` with `Query` and `Sort` can be more economical; choose based on actual needs.

## 10. AND/OR, Grouping Parentheses, and Logical Correctness

Predicates can combine conditions with `and` and `or`. When requirements involve grouping, express the **parentheses** explicitly:

~~~text
tenant = "tenant-a"
AND status = "ACTIVE"
AND (stock >= 10 OR sku = "SPECIAL")
~~~

Querydsl:

~~~java
QCatalogProduct p = QCatalogProduct.catalogProduct;

Predicate predicate = p.tenantId.eq("tenant-a")
        .and(p.status.eq("ACTIVE"))
        .and(
                p.stock.goe(10)
                        .or(p.sku.eq("SPECIAL")));
~~~

Equivalent MongoDB filter:

~~~json
{
  "tenantId": "tenant-a",
  "status": "ACTIVE",
  "$or": [
    { "stock_qty": { "$gte": 10 } },
    { "sku": "SPECIAL" }
  ]
}
~~~

Never replace the expression above with:

~~~java
Predicate wrong = p.tenantId.eq("tenant-a")
        .and(p.status.eq("ACTIVE"))
        .and(p.stock.goe(10))
        .or(p.sku.eq("SPECIAL"));
~~~

Because in `wrong`, the `sku = "SPECIAL"` branch can satisfy the predicate **without matching tenant**, allowing another tenant's data to leak into results.

**This is a real security bug:** whenever `OR` is present, the tenant filter must wrap outside the entire `OR` group. Test with another tenant's document having `sku = SPECIAL` to prove it is excluded.

If a predicate gets too complex to track parentheses or optimize indexes cleanly, express it with `MongoTemplate`/`Criteria.andOperator`/`orOperator`, accompanied by unit and integration tests.

## 11. Querydsl and BSON Field Name Mapping

In the sample entity:

~~~java
@Field("display_name")
private String name;

@Field("stock_qty")
private long stock;
~~~

The Q-type is generated from **Java properties**, e.g. `p.name` and `p.stock`. At query execution time, the MongoDB adapter must produce BSON matching the real schema:

~~~javascript
db.catalog_products.find({
  tenantId: "tenant-a",
  status: "ACTIVE",
  stock_qty: { $gte: 5 }
});
~~~

Never hardcode `p.stock_qty`: Q-types do not generate Java properties from `@Field` names. In versions with supported Querydsl MongoDB mapping, verify that the adapter properly uses Spring Data metadata when translating properties to BSON.

**A reliable verification routine:**

1. Insert a document via `MongoTemplate.insert(entity)`.
2. Read BSON via raw MongoDB collection and confirm `stock_qty`, `display_name` exist.
3. Call `repository.findAll(p.stock.goe(...))`.
4. Cross-check results with a `MongoTemplate` query or MongoDB shell command using real field names.
5. If needed, capture MongoDB driver `CommandStartedEvent` to inspect the exact `filter`.

An integration test matching expectations verifies the mapper path of that version. If the Querydsl adapter mishandles `@Field` or nested paths, move that specific query to `MongoTemplate` instead of deleting mapping annotations or altering the schema arbitrarily.

## 12. Strings, Nulls, Nested Properties, and Arrays: Do Not Assume Everything Is Supported

Querydsl Core defines many expressions: substring matching, inequalities, null checks, collection access, and nested paths. However, the **Querydsl MongoDB serializer/adapter** must translate those expressions into MongoDB equivalents. Support can **differ** from JPA/SQL.

| Requirement | Example/point to check | Reason |
|---|---|---|
Substring matching | `p.name.contains("water")` | MongoDB may use regex, different from full-text search |
Case-insensitive | `p.name.containsIgnoreCase("WATER")` | Must verify regex/collation, indexes, and Unicode |
Null check | `p.name.isNull()` | MongoDB distinguishes null fields from missing fields per operator |
Nested document path | `p.supplier.countryCode.eq("VN")` if Q-type exposes it | Needs nested `@Field` mapping |
String array | `p.tags.any().eq("outdoor")` if path/operator supported | MongoDB has distinct multikey and array semantics |
Multiple conditions on an array of documents | Requires same element | Must express `$elemMatch`, not just dot-path combinations |
Field existence query | `$exists` semantics | Not synonymous with not-null comparisons |
Geo/text/aggregation | Specialized MongoDB operators | Predicate executor is not a full pipeline DSL |

The expressions in this table are **things to verify**, not a guaranteed list supported by every adapter.

### 12.1. Same-Element Trap with Arrays of Documents

Suppose you have an array:

~~~json
{
  "variants": [
    { "color": "RED", "quantity": 2 },
    { "color": "BLUE", "quantity": 15 }
  ]
}
~~~

MongoDB query:

~~~javascript
{
  "variants.color": "RED",
  "variants.quantity": { $gte: 10 }
}
~~~

matches the document even though **no RED variant has quantity 10**, because the two predicates match two different array elements. To target the same element, you need `$elemMatch`.

If the Querydsl adapter cannot translate an expression into accurate `$elemMatch` semantics, use `MongoTemplate`:

~~~java
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;

Query sameVariant = Query.query(
        Criteria.where("variants").elemMatch(
                Criteria.where("color").is("RED")
                        .and("quantity").gte(10)));
~~~

This `sameVariant` example assumes the actual entity has a `variants` field holding embedded subdocuments; `CatalogProduct` in section 4 does not declare that property yet. When using typed `MongoTemplate`, extend the schema/entity accordingly and verify mapping.

### 12.2. Regex Does Not Automatically Use Indexes Well

Even if the adapter supports `containsIgnoreCase`, the resulting query can emit a regex scanning many documents without using a B-tree index as desired. Never assume a query is fast simply because it was built with a type-safe method. For text searches, evaluate text indexes or dedicated search engines and inspect the query plan.

## 13. Pagination, Sorting, and Querydsl Performance

A query using:

~~~java
Page<CatalogProduct> page = products.findAll(
        p.tenantId.eq("tenant-a")
                .and(p.status.eq("ACTIVE")),
        PageRequest.of(0, 20,
                Sort.by(Sort.Order.desc("createdAt"),
                        Sort.Order.asc("id"))));
~~~

Assumes `p` is `QCatalogProduct.catalogProduct`. `Sort` here uses Java property names; `id` corresponds to BSON `_id`.

### 13.1. Why Is Deterministic Ordering Required?

If you sort only by `createdAt` and multiple documents share the same timestamp, pages can drift even when data does not change. Adding `id` as a tie-breaker enforces deterministic order.

However, stable sorting **does not create a snapshot across requests**. When inserts/deletes occur or sort fields mutate, offset pagination can still duplicate or skip items.

### 13.2. Page May Require a Count

`Page<T>` exposes `getTotalElements()`/`getTotalPages()`. The adapter may have to count matching documents separately to supply metadata; do not assume every call runs exactly two commands, since frameworks can optimize special cases.

If the UI only needs a *Load more* button, do not force every query into `Page` indefinitely. For deep pagination, check whether `Slice`/scrolling APIs are supported by your repository/version, or implement a keyset cursor with `MongoTemplate`.

### 13.3. Indexes and Explain

For a tenant + status filter sorted newest first:

~~~javascript
db.catalog_products.createIndex(
  { tenantId: 1, status: 1, createdAt: -1, _id: 1 },
  { name: "idx_tenant_status_created_id" }
);
~~~

Check the equivalent query in MongoDB shell:

~~~javascript
db.catalog_products.find({
  tenantId: "tenant-a",
  status: "ACTIVE"
})
.sort({ createdAt: -1, _id: 1 })
.limit(20)
.explain("executionStats");
~~~

Inspect `winningPlan`, `totalKeysExamined`, `totalDocsExamined`, and latency. This index is not necessarily optimal if you add a `stock_qty >= 5` range predicate; field order in compound indexes, selectivity, and sorts must match the query workload.

Querydsl does not replace index planning. When queries combine `OR`, regex, or multi-field ranges, execution plans can differ dramatically from simple equality lookups.

## 14. Security: Tenant Predicates Must Never Be Optional Filters

In multi-tenant systems, the predicate:

~~~java
Predicate tenantScope = p.tenantId.eq(authenticatedTenantId);
~~~

must combine with user-chosen filters under an **outer AND**, never allowing an `OR` group to drop the tenant boundary.

Wrong:

~~~java
Predicate unsafe = p.tenantId.eq(authenticatedTenantId)
        .and(p.status.eq("ACTIVE"))
        .or(p.sku.eq("SPECIAL"));
~~~

Right:

~~~java
Predicate safe = p.tenantId.eq(authenticatedTenantId)
        .and(
                p.status.eq("ACTIVE")
                        .or(p.sku.eq("SPECIAL")));
~~~

Users may choose status or SKU filters, yet **cannot bypass the tenant condition**. `authenticatedTenantId` must come from a trusted authentication context, never accepted verbatim from client input.

If a service has many query methods and manual tenant predicates are error-prone, design a custom repository layer or encapsulated queries so every read/write path enforces scope. Querydsl does not provide automatic row-level security.

Beyond tenant, verify:

- Visibility permissions by user group, hidden statuses, and ownership.
- Which properties may be filtered/sorted via HTTP; never expose arbitrary Q-paths.
- Page size limits and query rate limits to prevent overly broad filters.
- Never log predicates/BSON containing sensitive data to unauthorized destinations.
- Never let `exists` results leak information about another tenant's resources.

## 15. Testing Against Real MongoDB

Mocking the repository in tests only proves the service **called** some predicate; it does not prove the Spring Data MongoDB adapter **translates that predicate into valid BSON**. Therefore, integration tests against a real MongoDB in an isolated database/collection are essential. Spring Boot 3.x `@DataMongoTest` does not start MongoDB by itself; provide a server via Testcontainers or a configured test environment.

### 15.1. Testing Conditions, count, exists, Page, and Mapping

**CatalogProductQuerydslTest.java**

~~~java
package com.example.catalog;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Instant;
import java.util.List;
import org.bson.Document;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.mongo.DataMongoTest;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Sort;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.query.Query;

@DataMongoTest
class CatalogProductQuerydslTest {
    @Autowired
    CatalogProductRepository products;

    @Autowired
    MongoTemplate mongo;

    private CatalogProduct product(
            String id, String tenant, String status,
            long stock, String sku, int hour) {
        return new CatalogProduct(
                id, tenant, sku, "Product " + id, stock, status,
                Instant.parse("2026-11-20T00:00:00Z")
                        .plusSeconds(hour * 3600L),
                List.of("outdoor"));
    }

    @BeforeEach
    void seed() {
        // Use only inside an isolated test database.
        mongo.remove(new Query(), CatalogProduct.class);
        mongo.insert(List.of(
                product("p-101", "tenant-a", "ACTIVE", 12, "A", 8),
                product("p-102", "tenant-a", "ACTIVE", 3, "B", 9),
                product("p-103", "tenant-a", "INACTIVE", 20, "C", 10),
                product("p-104", "tenant-b", "ACTIVE", 30, "SPECIAL", 11)),
                CatalogProduct.class);
    }

    @Test
    void predicateSelectsTypedFieldAndTenant() {
        QCatalogProduct p = QCatalogProduct.catalogProduct;

        var predicate = p.tenantId.eq("tenant-a")
                .and(p.status.eq("ACTIVE"))
                .and(p.stock.goe(5L));

        assertThat(products.findAll(predicate))
                .extracting(CatalogProduct::getId)
                .containsExactly("p-101");

        Document bson = mongo.getCollection("catalog_products")
                .find(new Document("_id", "p-101")).first();
        assertThat(bson).isNotNull();
        assertThat(bson.get("stock_qty"))
                .isInstanceOf(Number.class);
        assertThat(bson.containsKey("stock")).isFalse();
        assertThat(bson.containsKey("display_name")).isTrue();
    }

    @Test
    void countExistsAndFindOneReflectFilteredData() {
        QCatalogProduct p = QCatalogProduct.catalogProduct;

        var activeForTenant = p.tenantId.eq("tenant-a")
                .and(p.status.eq("ACTIVE"));

        assertThat(products.count(activeForTenant)).isEqualTo(2);
        assertThat(products.exists(
                activeForTenant.and(p.stock.goe(5L)))).isTrue();
        assertThat(products.exists(
                activeForTenant.and(p.stock.goe(50L)))).isFalse();

        assertThat(products.findOne(p.id.eq("p-101")))
                .isPresent()
                .get()
                .extracting(CatalogProduct::getSku)
                .isEqualTo("A");
    }

    @Test
    void pageablePredicateUsesStableSort() {
        QCatalogProduct p = QCatalogProduct.catalogProduct;

        Page<CatalogProduct> page = products.findAll(
                p.tenantId.eq("tenant-a")
                        .and(p.status.eq("ACTIVE")),
                PageRequest.of(0, 1,
                        Sort.by(Sort.Order.desc("createdAt"),
                                Sort.Order.asc("id"))));

        assertThat(page.getContent()).hasSize(1);
        assertThat(page.getContent().get(0).getId())
                .isEqualTo("p-102");
        assertThat(page.getTotalElements()).isEqualTo(2);
    }

    @Test
    void groupedOrDoesNotLeakOtherTenant() {
        QCatalogProduct p = QCatalogProduct.catalogProduct;

        var safe = p.tenantId.eq("tenant-a")
                .and(p.status.eq("ACTIVE")
                        .or(p.sku.eq("SPECIAL")));

        assertThat(products.findAll(safe))
                .extracting(CatalogProduct::getId)
                .containsExactlyInAnyOrder("p-101", "p-102");
    }
}
~~~

The test uses `QCatalogProduct` generated at build time by the annotation processor. If Q-types fail to generate or the repository factory does not support Querydsl in your version, the test fails to compile or initialize; that is a **compatibility verification signal**, not a bug to hide behind casts or mocks.

### 15.2. Verifying BSON Types

Do not assert only counts: inspect raw documents for `stock_qty`, `display_name`, and compare against an equivalent `MongoTemplate` or shell query. If a test succeeds only because historical documents contain both Java and BSON field names, it does not prove mapping works. Seed according to the **canonical BSON schema** and test documents with missing/wrong fields.

### 15.3. Checking Translators/Operators

Write focused tests for:

1. `eq`/`ne` and numeric comparisons.
2. `and`/`or` with parentheses.
3. `isNull` with null fields and missing fields.
4. String `contains`/`containsIgnoreCase` if supported by your version's adapter.
5. Array path `any()` and nested `@Field` if used by the project.
6. `findAll(Predicate, Pageable)` with stable sort and count command count.
7. `findOne` with non-unique predicates, per version contract.

When an operator is rejected or produces wrong BSON, do not label it "always supported by Querydsl MongoDB" simply because the same operator works in Querydsl JPA.

### 15.4. Command Monitoring

The MongoDB Java Driver supports `CommandListener`, which can be registered in `MongoClientSettings` in test configurations. `CommandStartedEvent` lets you observe `find`/`count` and the exact filter/sort sent to MongoDB.

Illustrative BSON example:

~~~json
{
  "find": "catalog_products",
  "filter": {
    "tenantId": "tenant-a",
    "status": "ACTIVE",
    "stock_qty": { "$gte": 5 }
  }
}
~~~

Do not treat the JSON above as a byte-for-byte real driver command; filter by collection, operation, and driver version. **Never log all production commands** if queries contain sensitive data or lack proper retention/access controls.

## 16. When No Querydsl Adapter Exists: MongoTemplate and Custom Repositories

If your project's Spring Data MongoDB version lacks or is incompatible with a Querydsl adapter, **do not keep a broken `QuerydslPredicateExecutor` interface that fails initialization**. The clean alternative pattern is:

1. Keep `MongoRepository` for CRUD and simple derived queries.
2. Add a **repository fragment** or query service using `MongoTemplate`.
3. Represent input filters with a dedicated DTO constraining allowed fields.
4. Use `Criteria` with Java property names when passing an entity class, and test BSON.

Example of the same product lookup logic:

~~~java
package com.example.catalog;

import java.util.List;
import org.springframework.data.domain.Sort;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;
import org.springframework.stereotype.Service;

@Service
public class ProductCriteriaSearchService {
    private final MongoTemplate mongo;

    public ProductCriteriaSearchService(MongoTemplate mongo) {
        this.mongo = mongo;
    }

    public List<CatalogProduct> available(
            String authenticatedTenantId, long minimumStock) {
        if (authenticatedTenantId == null
                || authenticatedTenantId.isBlank()
                || minimumStock < 0) {
            throw new IllegalArgumentException("Invalid filter");
        }

        Query query = Query.query(
                Criteria.where("tenantId").is(authenticatedTenantId)
                        .and("status").is("ACTIVE")
                        .and("stock").gte(minimumStock));

        query.with(Sort.by(
                Sort.Order.desc("createdAt"),
                Sort.Order.asc("id")));
        query.limit(50);

        return mongo.find(query, CatalogProduct.class);
    }
}
~~~

In a typed query, Spring Data maps `stock` to `stock_qty` via `CatalogProduct.class` metadata. For more complex dynamic filters, combine `Criteria.andOperator/orOperator` or build conditions from DTO fields.

The key when migrating from Querydsl to `MongoTemplate` is **preserving exact semantics**, not merely swapping method names. Use the same integration test suite verifying tenant, null/missing fields, sorts, arrays, and performance to compare both implementations.

### Comparing Options

| Requirement | Querydsl executor when supported | MongoTemplate/Criteria |
|---|---|---|
Type-safe paths via code generation | Yes | Uses string property names |
No annotation processor required | No | Yes |
Simple CRUD repository | Combines with MongoRepository | MongoRepository still useful |
Dynamic multi-condition filters | Convenient with BooleanBuilder | Convenient with Criteria/Query |
Complex array queries / `$elemMatch` | Depends on translator support | More direct |
Aggregation/`$lookup`/`$group` | Not primary API | `Aggregation`/`MongoTemplate` |
Conditional updates/transactions | Not PredicateExecutor's job | Supports Query/Update and transactions |
Upgrading when Querydsl adapter breaks | Requires migrating code | Less dependent on Querydsl |

## 17. Common Pitfalls and Diagnostics

| Symptom | Possible cause | Resolution |
|---|---|---|
`QCatalogProduct` not found | Annotation processing did not run | Check `@QueryEntity`, APT, generated sources |
IDE sees Q-type but CI fails compilation | Generated sources exist only locally; build pipeline lacks APT | Configure build to regenerate Q-types from source |
Repository fails initialization when adding executor | MongoDB version lacks adapter support or dependencies mismatch | Verify release and runtime classpath; consider custom repository |
`NoClassDefFoundError` related to Querydsl | Mismatched core/mongodb/apt versions or transitive driver | Align dependency graph, exclude conflicts properly |
Mistaking Querydsl JPA examples for MongoDB | Incompatible operators/serialization | Use real MongoDB tests, never rely on SQL assumptions |
Filter `p.stock` matches no data | BSON is `stock_qty` or legacy schema differs | Inspect Spring Data mapping and raw BSON |
`findOne` fails with multiple results | Non-unique predicate | Create unique index or switch to pagination |
`containsIgnoreCase` is slow | Regex cannot use index well | Run explain, pick suitable search strategy |
`p.tags.any()` or nested path errors | Mongo serializer does not support that expression | Use Criteria/`$elemMatch` or redesign query |
`and(...).or(...)` leaks other tenant's data | Wrong OR grouping | Place tenant condition outside the entire OR |
Result pages repeat or skip items | Sort lacks unique key, offset shifted | ID tie-breaker; keyset/cursor when needed |
Trusting `exists` to enforce uniqueness | Race between exists and insert | Unique index and duplicate-key handling |
Confusing predicate count with update count | Read API is not a write result | Use `UpdateResult`/`DeleteResult` |
Never inspecting server commands | Query translated differently than expected | `CommandListener` and integration tests |

## 18. Practice Exercises

**Exercise 1 — Generating Q-types.** Define `CatalogProduct` with `@QueryEntity` and `@Document`. Configure the annotation processor, verify `QCatalogProduct` is generated, rename a property, and rebuild to observe the compile error in old code.

**Exercise 2 — Repository executor.** Declare a repository extending `MongoRepository` and `QuerydslPredicateExecutor`. Call `findAll` with `tenantId = tenant-a AND status = ACTIVE` and verify expected IDs against test MongoDB.

**Exercise 3 — BooleanBuilder.** Create an optional filter DTO with `status`, `minimumStock`, `maximumStock`, and `sku`. Compare results with the same filters built using `MongoTemplate`. Test that passing no optional filters still returns only the authenticated tenant.

**Exercise 4 — Count and exists.** With 4 products and two tenants, call `count(predicate)` and `exists(predicate)`. Demonstrate that both methods reflect only the current read snapshot and do not prevent races on insert.

**Exercise 5 — OR logic.** Create a `tenant-b` product with SKU `SPECIAL`. Compare `tenant.and(status).or(skuSpecial)` against `tenant.and(status.or(skuSpecial))`; prove the wrong predicate leaks the other tenant's product.

**Exercise 6 — BSON mapping.** Map `stock` to `stock_qty` and `name` to `display_name`. Save an entity with Spring Data, read raw BSON, run a Querydsl predicate, and cross-check with `MongoTemplate`. If results diverge, document the version, error, and fallback.

**Exercise 7 — Nulls and arrays.** Create documents with missing fields, null fields, scalar arrays, and embedded-document arrays with a cross-element condition. Test which Querydsl expressions the adapter actually supports, rewriting with `Criteria` where `$exists`/`$elemMatch` is needed.

**Exercise 8 — Paging and indexes.** Compare `findAll(predicate, Pageable)` against an equivalent `MongoTemplate` query with sort, filter, and limit. Measure command count, `getTotalElements()`, and `explain("executionStats")`; create a compound index only after verifying the workload.

**Exercise 9 — Version upgrades.** List your current Spring Boot/Spring Data MongoDB/Querydsl/driver dependency matrix. Verify the adapter, build Q-types, and run integration tests. Design a `MongoTemplate` fallback in case a new branch drops support or mis-translates an operator.

## 19. Key Takeaways

**Querydsl** provides **Q-types** and `Predicate`s to express query conditions over typed Java properties. **`QuerydslPredicateExecutor<T>`** is a repository interface executing those predicates for reads, counts, existence checks, and pagination **when supported by your Spring Data MongoDB version's adapter**.

Using it properly requires **an annotation processor generating Q-types**, compatible dependencies, and integration tests verifying **Java → BSON mapping**, how the translator handles operators, null/missing fields, arrays, and sorting. Never treat all of Querydsl Core or Querydsl JPA examples as proof that MongoDB supports every expression.

By design, always bind **trusted tenant/access scope** into predicates, limit returned data, and measure query plans. When no adapter is available or queries require `$elemMatch`, aggregations, or dedicated updates/transactions, **`MongoTemplate` + `Criteria`** is the clearer path. Correctness is proven by **actual BSON and MongoDB results**, not merely by Java expressions compiling cleanly.
