# Spring Boot Auto-configuration for MongoDB

## 1. What Problem Does Auto-configuration Solve?

In a Java application using **Spring Data MongoDB**, developers need to connect to MongoDB, map documents to objects, build queries with `MongoTemplate` or repositories, configure connections, and manage resources. If everything is wired manually, the application must define each connection bean, factory, converter, template, and repository infrastructure.

**Spring Boot auto-configuration** is a mechanism that inspects the libraries on the classpath, the beans already declared by the application, and the configuration properties to **automatically register appropriate beans**. As a result, with a single starter and a few lines of configuration, an application can usually inject:

- `com.mongodb.client.MongoClient` to access MongoDB using the Java Sync Driver;
- `MongoDatabaseFactory`, `MongoTemplate`, and Spring Data MongoDB's mapping infrastructure;
- Implementations of the `MongoRepository` interface generated by Spring Data at runtime.

Auto-configuration **does not install or start a MongoDB server**, does not decide optimal collection/index design on its own, and does not guarantee that every connection or statement will succeed. Beans may be created at startup, while network or authentication errors only surface when the driver actually selects a server and executes an operation.

> **Version scope:** Specific property names and configuration classes in the examples focus on **Spring Boot 3.x / Spring Data MongoDB 4.x** and Java 17 or later. On other major versions (especially when upgrading to Spring Boot 4.x), check the configuration metadata and documentation for your exact project version before copying package names, properties, or annotations.

## 2. How Does Spring Boot Know to Configure MongoDB?

A Spring Boot application typically enables auto-configuration via `@SpringBootApplication` (which includes `@EnableAutoConfiguration`). Boot loads the corresponding set of auto-configuration classes from the present libraries and evaluates their **conditions**.

| Component | Role | Conditions/limits to keep in mind |
|---|---|---|
`spring-boot-starter-data-mongodb` | Pulls in dependencies for synchronous MongoDB, Spring Data repositories, and the appropriate driver | Suitable for blocking (imperative) data access applications |
`spring-boot-starter-data-mongodb-reactive` | Pulls in Spring Data MongoDB reactive and the MongoDB Reactive Streams Driver | Suitable for reactive data streams with `Mono`/`Flux` |
`MongoAutoConfiguration` | Typically provides synchronous `MongoClient` from the driver and Boot's configuration | In Boot 3.x; depends on classpath/existing beans |
`MongoDataAutoConfiguration` | Assembles most of the synchronous Spring Data MongoDB infrastructure | Uses factory, converter, mapping, and template when conditions match |
`MongoRepositoriesAutoConfiguration` | Activates repositories based on package scanning conventions | Requires Spring Data repositories and must not be disabled or overridden by related configuration mechanisms |
Reactive auto-configuration classes | Provide reactive client, factory, template, and repositories | Only take effect when the corresponding reactive driver and libraries are present |

Annotations commonly found in auto-configuration:

- `@ConditionalOnClass`: only configures if the required APIs are on the classpath.
- `@ConditionalOnMissingBean`: creates a default bean when the application has not provided a matching bean.
- `@ConditionalOnBean`: depends on another bean already being present.
- `@ConditionalOnProperty` and related conditions: decide based on properties and configuration state.

Therefore, **"having added the starter" does not mean "every bean is guaranteed to exist."** Application-defined beans, package scanning, or disabled conditions can produce results different from the defaults.

~~~mermaid
flowchart TD
    A["Spring Boot startup"] --> B["Read classpath, Environment, bean definitions"]
    B --> C{"MongoDB Sync Driver present and conditions met?"}
    C -->|"Yes"| D["MongoClient / connection settings"]
    C -->|"No"| X["Do not register default sync stack"]
    D --> E["MongoDatabaseFactory"]
    E --> F["Mapping context + MongoConverter"]
    E --> G["MongoTemplate / MongoOperations"]
    F --> G
    G --> H{"Scanned repository interfaces present?"}
    H -->|"Yes"| I["Spring Data creates MongoRepository proxies"]
    H -->|"No"| J["Can use MongoTemplate directly"]
~~~

The diagram represents **conceptual dependency relationships**, not the exact initialization order of every bean. Repositories are typically built on top of Spring Data's access and mapping infrastructure; the driver is the lower-level connection layer.

## 3. Minimal Setup for Synchronous MongoDB

### 3.1. Add the starter

With Gradle, use the dependency whose version is managed by Spring Boot dependency management:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-mongodb'
}
~~~

Or with Maven:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-mongodb</artifactId>
</dependency>
~~~

In projects using `spring-boot-starter-parent` or the Spring Boot BOM, you normally do not need to specify separate versions for Spring Data MongoDB and the MongoDB Java Driver. Mixing incompatible versions can cause class/method errors at runtime.

### 3.2. Configure the URI and database

Example `application.yml` for running MongoDB locally:

~~~yaml
spring:
  data:
    mongodb:
      uri: mongodb://localhost:27017/book_catalog
~~~

In Spring Boot 3.x, `spring.data.mongodb.uri` is the commonly used URI configuration. The `book_catalog` part is the example database. If there is no database in the URI, you need to specify the appropriate database using the configuration mechanism supported by your Boot version. Avoid specifying the database in multiple places to prevent confusion over which value is actually applied.

A more suitable approach for deployment environments is passing the URI through an environment variable:

~~~yaml
spring:
  data:
    mongodb:
      uri: ${MONGODB_URI}
~~~

For example, the value of `MONGODB_URI` might be `mongodb://localhost:27017/book_catalog` locally or a URI to a MongoDB cluster with authentication and TLS in a real environment. The `SPRING_DATA_MONGODB_URI` environment variable can also be mapped directly by Boot 3.x according to relaxed binding rules.

Notes:

- Keep usernames, passwords, and secret keys in a secret manager or environment configuration; never commit real credentials to Git.
- If the password in the connection URI contains special characters, properly percent-encode the credentials portion according to URI rules.
- Depending on the system, you may need to configure `authSource`, TLS, replica set, authentication mechanism, or SRV URI `mongodb+srv://...`; verify support in your driver and infrastructure.
- Boot may create `MongoClient` before verifying that the server is reachable. Attempt an actual operation (or an appropriate health check) when verifying the connection.

### 3.3. Example application using Boot-created beans

Package structure:

~~~text
com.example.catalog
├── CatalogApplication.java
├── data
│   ├── Book.java
│   └── BookRepository.java
└── service
    └── BookCatalogService.java
~~~

File `CatalogApplication.java`:

~~~java
package com.example.catalog;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CatalogApplication {
    public static void main(String[] args) {
        SpringApplication.run(CatalogApplication.class, args);
    }
}
~~~

File `data/Book.java`:

~~~java
package com.example.catalog.data;

import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;

@Document(collection = "books")
public class Book {
    @Id
    private String id;
    private String title;
    private String author;

    public Book() {}

    public Book(String title, String author) {
        this.title = title;
        this.author = author;
    }

    public String getId() { return id; }
    public void setId(String id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getAuthor() { return author; }
    public void setAuthor(String author) { this.author = author; }
}
~~~

File `data/BookRepository.java`:

~~~java
package com.example.catalog.data;

import java.util.List;
import org.springframework.data.mongodb.repository.MongoRepository;

public interface BookRepository extends MongoRepository<Book, String> {
    List<Book> findByAuthor(String author);
}
~~~

File `service/BookCatalogService.java`:

~~~java
package com.example.catalog.service;

import com.example.catalog.data.Book;
import com.example.catalog.data.BookRepository;
import java.util.List;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;
import org.springframework.stereotype.Service;

@Service
public class BookCatalogService {
    private final BookRepository books;
    private final MongoTemplate mongoTemplate;

    public BookCatalogService(BookRepository books, MongoTemplate mongoTemplate) {
        this.books = books;
        this.mongoTemplate = mongoTemplate;
    }

    public Book add(String title, String author) {
        return books.save(new Book(title, author));
    }

    public List<Book> byAuthor(String author) {
        return books.findByAuthor(author);
    }

    public List<Book> byTitle(String title) {
        Query query = Query.query(Criteria.where("title").is(title));
        return mongoTemplate.find(query, Book.class);
    }
}
~~~

Here, **there is no `@Configuration` class manually creating `MongoClient`, `MongoTemplate`, or the `BookRepository` implementation**. Boot and Spring Data create the required beans when the starter, package scanning, and configuration are valid.

`@Document` specifies the mapped collection name; `@Id` specifies the identifier field. The annotation does not mean MongoDB automatically creates the collection when the application starts. Collections are typically created when data is written or through a separate initialization mechanism.

## 4. Which Beans Are Auto-configured?

### 4.1. MongoClient: connection and connection pool management

The synchronous driver's `MongoClient` is typically a shared, **thread-safe** bean that manages the connection pool. An application should not create a `MongoClient` per HTTP request. The driver is responsible for server selection, connections, pooling, and retries as configured; Spring Boot manages the lifecycle of the bean it creates.

The URI is an important input, but effective connectivity also depends on:

- server selection timeout, connect timeout, socket timeout;
- pool size, connection checkout wait time, and connection ramp-up rate;
- TLS, authentication, topology/replica set, retries, and read/write concern;
- network stability and MongoDB server health.

These parameters **should not be tuned by guesswork**. Observe latency, concurrent request counts, pool status, and server statistics before making changes.

### 4.2. MongoDatabaseFactory, mapping, and MongoTemplate

On top of `MongoClient`, Spring Data uses `MongoDatabaseFactory` to access the database in a way that integrates with Spring's infrastructure. `MongoMappingContext` and `MappingMongoConverter` map `@Document`, `@Id`, `@Field`, and configured conversions. `MongoTemplate`/`MongoOperations` provides APIs for querying, aggregation, updates, bulk writes, and collection operations.

Example of injecting the abstraction to reduce coupling to a concrete implementation:

~~~java
import org.springframework.data.mongodb.core.MongoOperations;
import org.springframework.stereotype.Component;

@Component
public class MongoAccessProbe {
    private final MongoOperations operations;

    public MongoAccessProbe(MongoOperations operations) {
        this.operations = operations;
    }

    public boolean hasCollection(String name) {
        return operations.collectionExists(name);
    }
}
~~~

`MongoTemplate` still applies Spring Data mapping when working with entities; that is an important difference compared to using the driver's `MongoCollection<Document>` directly.

### 4.3. Repository proxies and package scanning scope

With `@SpringBootApplication` placed in `com.example.catalog`, Boot can locate repositories in subpackages such as `com.example.catalog.data`. Spring Data generates runtime implementations for `MongoRepository` interfaces and supported query methods.

If a repository sits **outside the scanned area**, the bean may not be created even though `MongoTemplate` still works. Options include moving the application class up to an appropriate root package or configuring scanning explicitly:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.data.mongodb.repository.config.EnableMongoRepositories;

@Configuration
@EnableMongoRepositories(basePackages = "com.example.externalrepos")
public class MongoRepositoriesConfig {
}
~~~

Only use this configuration if you truly need to scan outside the convention. If you enable repository scanning manually, check the scan scope so you do not create duplicate repositories or accidentally select the wrong `MongoTemplate` when multiple databases exist.

## 5. What Happens When You Declare Beans Manually?

An important part of auto-configuration is **back-off**: for beans conditioned with `@ConditionalOnMissingBean`, Boot avoids creating a default bean when the application has already supplied an equivalent one.

| Scenario | Expected behavior |
|---|---|
No beans declared manually, sync starter present | Boot typically creates the default stack |
`MongoClient` declared manually | The default client configuration may back off; other Spring Data beans can still use the provided client |
`MongoTemplate`/`MongoOperations` declared manually | Auto-configuration for the template may back off; repositories need to reference the right template |
Converter/factory or multiple clients declared manually | Some default beans may no longer be created as expected; boundaries and dependencies must be defined explicitly |
Mongo auto-configuration excluded | Do not expect the corresponding stack to appear automatically |

The exact details of **which beans** back off depend on the version and each conditional annotation. Do not assume that declaring a single bean disables all MongoDB auto-configuration.

### 5.1. Prefer properties before creating MongoClient manually

If you need to change the URI or database, use configuration properties. If you need to adjust driver settings that cannot be expressed via properties in your Boot version, consider **`MongoClientSettingsBuilderCustomizer`** before replacing the entire client.

Example for Spring Boot 3.x:

~~~java
import java.util.concurrent.TimeUnit;
import org.springframework.boot.autoconfigure.mongo.MongoClientSettingsBuilderCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class MongoClientTuning {
    @Bean
    MongoClientSettingsBuilderCustomizer selectionTimeout() {
        return settings -> settings.applyToClusterSettings(
                cluster -> cluster.serverSelectionTimeout(3, TimeUnit.SECONDS));
    }
}
~~~

This example limits the driver's **server selection** time; it is not an overall timeout for every query. The value of `3` seconds is illustrative only. The customizer allows Boot to continue using its supported client creation and management mechanism.

### 5.2. When should you create MongoTemplate or a factory manually?

For example, when you need multiple databases with different access permissions, converters, or configurations. In that case, you may need to:

1. Define the required `MongoClient` or `MongoDatabaseFactory` beans.
2. Define a `MongoTemplate` per database with clear bean names.
3. Bind each repository group to a specific template via `@EnableMongoRepositories(mongoTemplateRef = "...")`.
4. Use `@Qualifier` or `@Primary` deliberately; also check transaction managers and index management.

Conceptual example of repository binding:

~~~java
import org.springframework.context.annotation.Configuration;
import org.springframework.data.mongodb.repository.config.EnableMongoRepositories;

@Configuration
@EnableMongoRepositories(
        basePackages = "com.example.catalog.primaryrepo",
        mongoTemplateRef = "catalogMongoTemplate")
public class CatalogRepositoryBinding {
}
~~~

This snippet **only illustrates the binding**; to run, you must define a bean named `catalogMongoTemplate` and configure the appropriate packages. For single-database applications, using the defaults is usually easier to maintain and test.

## 6. Auto-configuration and Reactive Applications

Applications accessing MongoDB asynchronously can use:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-mongodb-reactive'
}
~~~

With reactive libraries on the classpath and matching conditions, Boot 3.x can configure:

- MongoDB Reactive Streams `MongoClient` (a different type from the synchronous client);
- `ReactiveMongoDatabaseFactory` and `ReactiveMongoTemplate`/`ReactiveMongoOperations`;
- implementations of `ReactiveMongoRepository`.

Example of a reactive repository:

~~~java
import org.springframework.data.mongodb.repository.ReactiveMongoRepository;
import reactor.core.publisher.Flux;

public interface ReactiveBookRepository
        extends ReactiveMongoRepository<Book, String> {
    Flux<Book> findByAuthor(String author);
}
~~~

The example assumes `Book` is in an appropriately imported package; in a real project, organize entities and packages cleanly as in the synchronous example in Section 3.

**Spring WebFlux does not automatically turn a synchronous `MongoTemplate` into a non-blocking one.** You must use the reactive driver and API consistently along the processing path. If an application includes both starters, both the sync and reactive stacks may appear depending on conditions; clearly choose which repository/template type is used and avoid injecting the wrong client type.

Do not call `block()` indiscriminately on a reactive processing thread. If you must integrate with a synchronous system, design an appropriate asynchronous boundary and execution scheduler.

## 7. Are Transactions, Indexes, and Auditing Created Automatically?

**Connectivity and mapping** receive more out-of-the-box support from Boot than **business policies**. The following capabilities usually require separate configuration or decisions:

### 7.1. Multi-document transactions

MongoDB supports transactions with a suitable topology (replica set or sharded cluster). Synchronous applications use `MongoTransactionManager` if they want Spring to manage sessions/transactions for participating operations:

~~~java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.mongodb.MongoDatabaseFactory;
import org.springframework.data.mongodb.MongoTransactionManager;

@Configuration
public class MongoTransactionConfig {
    @Bean
    MongoTransactionManager mongoTransactionManager(MongoDatabaseFactory factory) {
        return new MongoTransactionManager(factory);
    }
}
~~~

`@Transactional` can then be used at appropriate service method boundaries, provided transaction management is enabled and all participating operations use the same infrastructure/session. Do not assume that merely adding the MongoDB starter causes Boot to pre-create a multi-document transaction manager.

In reactive systems, use `ReactiveMongoTransactionManager` and compose publishers that participate in the transaction properly; do not mix synchronous and reactive transaction managers.

### 7.2. Indexes

`@Indexed` and `@CompoundIndex` describe indexes on the model, but **automatic index creation** is not enabled by default in modern Spring Data MongoDB versions. In Boot 3.x, there is a related property `spring.data.mongodb.auto-index-creation`; production policies should clearly define index management/migrations, index creation permissions, and deployment timing.

Indexes must align with the workload: filters, sorts, cardinality, write frequency, uniqueness, and execution plans. Do not enable auto-index expecting every slow query to be fixed automatically.

### 7.3. Auditing and callbacks

Fields like `createdAt`, `lastModifiedAt`, `createdBy`, and `lastModifiedBy` require proper auditing configuration (for example, `@EnableMongoAuditing` and an auditor provider if user info is needed). There is no reason to assume they work automatically simply because the MongoDB dependency is present.

Application-defined entity callbacks/converters must also be registered properly and invoked through the appropriate Spring Data mapping path. Accessing collections directly with the BSON driver does not automatically trigger these callbacks.

## 8. Environment-Based Configuration and Security

Auto-configuration reads properties through Spring's `Environment`. Configuration can come from YAML/properties, environment variables, command-line arguments, profiles, or infrastructure secret management mechanisms. Precedence follows Boot's externalized configuration rules.

Example:

~~~yaml
# application.yml
spring:
  data:
    mongodb:
      uri: ${MONGODB_URI}
~~~

~~~yaml
# application-local.yml (only used when the local profile is active)
spring:
  data:
    mongodb:
      uri: mongodb://localhost:27017/book_catalog
~~~

When the `local` profile is active, profile-specific properties can override base values, though higher-priority configuration sources still exist. Never store production URIs with passwords in profile files inside the repository.

Controls to enforce:

- **MongoDB users and permissions**: grant least-privilege permissions per database/collection and required operations.
- **TLS and authentication**: configure according to topology; never disable authentication or certificate verification to "fix" production connection errors.
- **Timeouts and pools**: size according to demand and application instance count to avoid total connections exceeding MongoDB capacity.
- **Logging**: avoid logging connection strings containing credentials, documents with sensitive data, or full query parameters.
- **Health/readiness**: separate the application's started state from whether the data backend is ready for required operations.

## 9. Inspecting What Auto-configuration Is Actually Doing

### 9.1. Condition evaluation report

When a bean cannot be found or it is unclear why a bean was created, run the Boot 3.x application with `--debug` to print the **conditions evaluation report**, or enable logging for the condition report logger in an appropriate environment.

Items to look for:

- Which MongoDB auto-configurations **matched**, and which conditions were satisfied.
- Which ones **did not match** due to missing classes or existing custom beans.
- Whether reactive or imperative configuration is enabled.
- Whether repository packages fall under the scanned area.

If using Spring Boot Actuator, the `conditions` endpoint can aid diagnostics when configured and permitted. Only enable necessary endpoints and protect internal information.

### 9.2. Test a real operation

When startup succeeds but requests fail, test an actual operation and connection:

~~~java
import org.bson.Document;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.stereotype.Component;

@Component
public class MongoPing {
    private final MongoTemplate mongoTemplate;

    public MongoPing(MongoTemplate mongoTemplate) {
        this.mongoTemplate = mongoTemplate;
    }

    public void verifyConnection() {
        mongoTemplate.executeCommand(new Document("ping", 1));
    }
}
~~~

This snippet only illustrates an intentional ping command; do not call it on every request. A successful ping partially confirms connectivity; it does **not** guarantee read/write permissions on all collections. Error diagnostics must be tied to actual business operations.

### 9.3. Common issues

| Symptom | Causes to check | Remediation |
|---|---|---|
`NoSuchBeanDefinitionException: MongoTemplate` | Missing sync starter, custom bean, excluded auto-config, or reactive stack in use | Check dependencies and the condition report; inject the right API |
`No qualifying bean of type BookRepository` | Repository is outside the scan scope or repository auto-config is inactive | Check the root package and `@EnableMongoRepositories` if needed |
Cannot connect / `server selection timeout` | Wrong host/port, firewall, DNS, TLS, MongoDB not ready | Check effective URI, topology, and network |
Authentication/authorization error | Wrong credentials, incorrect `authSource`/auth mechanism, or missing permissions | Verify authentication settings and user privileges |
Beans exist but queries hit the wrong database | Database in URI/property, collection name, multiple factories/templates | Print non-secret configuration, check injected beans and mapping |
WebFlux program blocks threads | Synchronous driver/`MongoTemplate` used on the reactive processing path | Switch to the reactive stack or design an appropriate boundary |
`@Transactional` does not produce expected behavior | Missing transaction manager, unsupported topology, non-proxied call, or session mismatch | Check transaction manager, topology, and transaction boundaries |
Slow queries despite correct configuration | Indexes/query plan, documents scanned, overloaded pool, or large payloads | Use `explain`, metrics, and inspect actual query behavior |

## 10. Configuration and Integration Testing

In Spring Boot 3.x, `@DataMongoTest` is a test slice focused on Spring Data MongoDB that helps load repositories and necessary mapping without pulling in all services/controllers. Example:

~~~java
import static org.assertj.core.api.Assertions.assertThat;

import com.example.catalog.data.Book;
import com.example.catalog.data.BookRepository;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.mongo.DataMongoTest;

@DataMongoTest
class BookRepositoryTest {
    @Autowired
    BookRepository books;

    @Test
    void savesAndQueriesByAuthor() {
        Book saved = books.save(new Book("MongoDB Basics", "An"));
        assertThat(saved.getId()).isNotBlank();
        assertThat(books.findByAuthor("An"))
                .extracting(Book::getTitle)
                .contains("MongoDB Basics");
    }
}
~~~

This test requires **an actual MongoDB instance available to the test environment**; `@DataMongoTest` does not start a MongoDB server by itself. You can use Testcontainers to start MongoDB and supply a dynamic URI through the mechanism appropriate for your Spring Boot version.

If tests require transactions or change streams, the MongoDB environment must support the corresponding topology. Isolate data between tests to avoid unintended state dependencies.

Test at multiple levels:

1. **Configuration tests**: verify that the synchronous or reactive beans actually exist, and that custom beans back off defaults as expected.
2. **Repository/template integration tests**: verify mapping, queries, sorting, required indexes, and update rules against a real server.
3. **Transaction tests**: verify commit/rollback behavior on a supported topology; test error handling and retries.
4. **Performance**: use representative data volumes and monitor query plans, latency, connection pools, and network round trips. Only change abstraction levels with evidence.

## 11. Practice Exercises

**Exercise 1 — Analyze the condition report.** Create a Boot 3.x application with the sync MongoDB starter and a URI to local MongoDB. Run with `--debug`, locate the selected MongoDB configurations, and identify which beans belong to the driver, Spring Data mapping, and repositories. Then try declaring a custom client bean on a scratch branch to observe changes in the condition report; do not keep unnecessary configuration in the main application.

**Exercise 2 — Repository and template sharing infrastructure.** Create a `Book` entity, a query method in `MongoRepository`, and a query using `MongoTemplate`. Write a document via the repository and read it via the template. Explain the roles of `MongoMappingContext` and `MappingMongoConverter`.

**Exercise 3 — Environment configuration.** Run the same application with a local URI and a test-environment URI provided via an environment variable. Verify the target database, connection, and user permissions without printing credentials to logs.

**Exercise 4 — Error handling.** Remove the configuration or set a wrong port in a test environment, and observe the difference between an `ApplicationContext` creation failure and a server selection failure when running a query. Use the condition report and driver messages to identify which layer failed.

**Exercise 5 — Reactive and transactions.** Compare the types of `MongoTemplate`/`ReactiveMongoTemplate` and `MongoRepository`/`ReactiveMongoRepository`. Explain why multi-document transactions and non-blocking access require dedicated infrastructure beyond automatic bean creation.

## 12. Key Takeaways

**Spring Boot auto-configuration** simplifies connecting to and mapping MongoDB by creating a default stack **when the classpath, properties, and bean conditions match**. With the sync starter, the application typically gets `MongoClient`, `MongoDatabaseFactory`, `MongoTemplate`, and repositories; with the reactive starter, it gets the corresponding stack for asynchronous publishers.

Start with **starter + URI + entity/repository**. When customization is needed, prefer properties and customizers before replacing default beans. Requirements around **multi-document transactions, indexes, auditing, multiple databases, security, performance, and query policies** still require explicit design and testing. The most important tool for understanding which beans Boot created is the **condition evaluation report**, combined with testing against a real MongoDB instance.
