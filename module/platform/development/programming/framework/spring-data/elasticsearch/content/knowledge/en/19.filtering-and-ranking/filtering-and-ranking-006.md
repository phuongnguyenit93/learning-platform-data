# Script Score and Limiting Computation Cost

By default, Elasticsearch ranks search results using the relevance score produced by the query. When business requirements call for incorporating custom signals into result ordering—such as popularity, quality, priority, or recency—`script_score` can be used to calculate scores for each matching document.

Script score is very flexible, yet it carries a cost. Elasticsearch must execute the script over the documents matched by the inner query to compute the new score. If the inner query is overly broad, the script is complex, or data lookups are expensive, a single query can consume substantial CPU. Therefore, designing a `script_score` query should always go hand in hand with narrowing the document set, limiting complexity, and measuring performance.

## 1. Scores in Elasticsearch and the Role of script_score

### 1.1. Default Relevance Score

For full-text queries such as `match`, Elasticsearch computes scores based on how well a document matches the query content. Scores depend on query type, analyzers, term statistics, and search settings.

Example:

~~~json
{
  "query": {
    "match": {
      "name": "wireless keyboard"
    }
  }
}
~~~

Results are typically sorted in descending score order. Documents matching query terms better tend to rank higher, though the score is neither a percentage nor a probability that a document is correct.

### 1.2. When Is a Custom Score Needed?

Some products need to blend text relevance with business signals:

- More popular products are favored when text relevance is comparable.
- Newer articles receive a boost over a specific time window.
- Documents with higher quality ratings rank higher.
- Results belonging to a priority tier receive a score boost.
- Geographic or temporal distance influences result ordering.

Built-in queries and functions such as `function_score`, `field_value_factor`, decay functions, or `rank_feature` can handle many cases. When a formula requires specialized logic that built-in tools cannot express cleanly, `script_score` is the more flexible option.

### 1.3. How Does script_score Change Ordering?

`script_score` takes an inner query to identify candidate documents, then runs a script on each matching document to calculate a new score.

~~~mermaid
flowchart TD
    A[Search request] --> B[Inner query selects candidates]
    B --> C[Documents matching inner query]
    C --> D[Painless script per candidate]
    D --> E[New score]
    E --> F[Sort by score and return top hits]
~~~

The inner query determines which documents may appear. The script scores those documents. Results are then ranked by the new score unless the request specifies another sort.

This is a critical point for cost control: limit candidates before the script runs.

## 2. Structure of a script_score Query

### 2.1. Basic Query DSL

A `script_score` query has two primary parts:

- `query`: the inner query selecting documents.
- `script`: the formula computing the score for each matched document.

Example:

~~~json
{
  "query": {
    "script_score": {
      "query": {
        "match": {
          "name": "wireless keyboard"
        }
      },
      "script": {
        "source": "_score * 1.5"
      }
    }
  }
}
~~~

In this example, the inner query finds documents by name. The script reads the original `_score` and multiplies it by 1.5. Since every candidate is multiplied by the same positive factor, their relative order does not change; this example merely demonstrates how to access the score.

### 2.2. Accessing the Original Score

In a Painless `script_score` context, the `_score` variable holds the score generated by the inner query. You can use it to combine text relevance with other signals.

Conceptual example:

~~~text
finalScore = textScore * businessMultiplier
~~~

If you want relevance to stay the main driver, the multiplier should vary within a controlled range. If the business signal is too strong, poorly matching documents can outrank well-matching ones solely due to popularity or priority.

### 2.3. Accessing Fields via Doc Values

Scripts typically read fields using `doc['field_name']`. This uses doc values when supported by the field, which is far better than reading and parsing the entire `_source` on every scoring evaluation.

Example checking if a field has a value:

~~~painless
if (doc['popularity'].size() == 0) {
    return _score;
}
double popularity = doc['popularity'].value;
return _score + popularity;
~~~

Checking `size() == 0` handles documents missing the field. Never access `.value` before checking whether the field exists; otherwise the script can fail on documents lacking that field.

Doc values are normally available for `numeric`, `keyword`, `date`, and several other types. `text` fields do not have doc values enabled by default; enabling `fielddata` on `text` can consume significant heap. For signals used in scoring, consider storing them in dedicated numeric or keyword fields.

## 3. Example Combining Text Relevance and Popularity

### 3.1. Bounded Formula

Suppose documents have a non-negative numeric field `popularity`. We want to:

- Keep the text score as the foundation.
- Boost popular products.
- Cap the boost so popularity never completely overwhelms relevance.

We can use a saturation function:

\[
normalizedPopularity = \frac{popularity}{popularity + k}
\]

As `popularity` grows, the value approaches 1 without exceeding 1 for non-negative `popularity` and \(k > 0\).

Final score:

\[
finalScore = textScore \times (1 + weight \times normalizedPopularity)
\]

If `weight = 0.5`, the multiplier stays in the range from 1 up to just under 1.5. The popularity signal boosts scores only within a clear boundary.

### 3.2. Query DSL with Painless

~~~json
{
  "query": {
    "script_score": {
      "query": {
        "bool": {
          "must": [
            {
              "match": {
                "name": "wireless keyboard"
              }
            }
          ],
          "filter": [
            {
              "term": {
                "available": true
              }
            }
          ]
        }
      },
      "script": {
        "source": "double p = doc['popularity'].size() == 0 ? 0.0 : Math.max(0.0, doc['popularity'].value); double k = params.k; double normalized = p / (p + k); return _score * (1.0 + params.weight * normalized);",
        "params": {
          "k": 10.0,
          "weight": 0.5
        }
      }
    }
  }
}
~~~

The inner query uses `match` to select candidates by name and `filter` to drop unavailable products. The script runs only on documents meeting those conditions.

`Math.max` guards the formula if popularity data unexpectedly contains negative values. Better yet, validate data at ingestion time and enforce valid value ranges.

### 3.3. Why Normalize Signals?

Business fields can live on vastly different scales:

- Popularity can range from 0 to millions.
- Rating can range from 0 to 5.
- Priority can range from 1 to 10.
- Timestamps can be huge numbers.

Adding these raw values directly to `_score` can let a single signal dominate the entire ranking. Map signals onto a meaningful scale, such as 0–1, and apply bounded weights.

Do not pick `weight` by guesswork. Evaluate results on a query set with relevance labels and compare before/after orderings.

### 3.4. Handling Missing Values and Outliers

A `script_score` should define explicitly how to handle:

- Non-existent fields.
- Null or unindexed field values.
- Negative values outside the valid domain.
- Extremely large values.
- Multi-valued fields.
- Zero input scores.

For example, defaulting missing popularity to 0 allows the document to still be ranked by its text score. If business rules want to exclude documents lacking a field, enforce that with a filter in the inner query instead of letting the script throw an exception.

For multi-valued fields, do not assume `.value` represents the intended business value. Decide whether you need min, max, average, or a specific element, and implement it explicitly. If only a single signal is needed, storing a single-valued field is easier to control.

## 4. Parameterizing Scripts

### 4.1. Using params Instead of Dynamic Source Generation

Never build a new script string per request by interpolating user values into `source`. Keep `source` static and pass varying values via `params`:

~~~json
{
  "script": {
    "source": "return _score * params.boost;",
    "params": {
      "boost": 1.2
    }
  }
}
~~~

Benefits:

- A static `source` can be reused in the script compilation cache.
- Runtime values do not trigger a distinct source string per request.
- Reduces risk of escaping bugs.
- Separates scoring logic from business parameters.
- Makes it easy to test multiple parameter sets against the same script.

Never accept raw Painless source from public clients. Clients should only supply validated business parameters.

### 4.2. Example with a Threshold Parameter

Suppose you only want to boost scores when popularity exceeds a threshold:

~~~json
{
  "script": {
    "source": "double p = doc['popularity'].size() == 0 ? 0.0 : doc['popularity'].value; return p >= params.threshold ? _score * params.boost : _score;",
    "params": {
      "threshold": 100.0,
      "boost": 1.25
    }
  }
}
~~~

The same `source` works across different `threshold` and `boost` values without recompiling the script whenever `params` change.

### 4.3. Stored Scripts

If a script is shared across multiple queries or managed independently, you can save it as a stored script in Elasticsearch and reference it by ID.

Example saving a script:

~~~http
PUT _scripts/product-popularity-score
Content-Type: application/json

{
  "script": {
    "lang": "painless",
    "source": "double p = doc['popularity'].size() == 0 ? 0.0 : Math.max(0.0, doc['popularity'].value); double k = params.k; return _score * (1.0 + params.weight * p / (p + k));"
  }
}
~~~

Then reference it:

~~~json
{
  "query": {
    "script_score": {
      "query": {
        "match": {
          "name": "wireless keyboard"
        }
      },
      "script": {
        "id": "product-popularity-score",
        "params": {
          "k": 10.0,
          "weight": 0.5
        }
      }
    }
  }
}
~~~

Stored scripts centralize source management and can be deployed via pipelines. Version them or roll out changes carefully because modifying a stored script can affect multiple queries sharing that ID.

### 4.4. Script Compilation Cache

Elasticsearch compiles Painless scripts before executing them. Static script sources can be cached to cut compilation overhead. If every request generates a unique source, cache hit rates drop and you can hit compilation rate limits.

Best practices:

- Use static script sources.
- Pass changing values via `params`.
- Avoid generating variable names, expressions, or source from input.
- Monitor compilation errors and cache evictions.
- Adjust cache or compilation-rate settings only with measurements and an understanding of node-level impact.

Settings like `script.max_compilations_rate` and script cache sizes depend on Elasticsearch version and node configuration. Do not alter production defaults just to mask a dynamic-source design.

## 5. Limiting Cost by Narrowing the Candidate Set

### 5.1. Filter First, Script Second

The biggest cost driver is usually the number of documents on which the script executes. Therefore, the inner query should eliminate as many irrelevant documents as early as possible.

Better example than scripting over `match_all`:

~~~json
{
  "query": {
    "script_score": {
      "query": {
        "bool": {
          "must": [
            {
              "match": {
                "description": "wireless keyboard"
              }
            }
          ],
          "filter": [
            {
              "term": {
                "tenantId": "tenant-42"
              }
            },
            {
              "term": {
                "available": true
              }
            },
            {
              "range": {
                "price": {
                  "lte": 200
                }
              }
            }
          ]
        }
      },
      "script": {
        "source": "return _score * params.boost;",
        "params": {
          "boost": 1.1
        }
      }
    }
  }
}
~~~

Tenant, availability, and price-range filters narrow the candidate set. `script_score` only evaluates the remaining documents.

### 5.2. Avoid script_score on match_all Unless Truly Necessary

Using `match_all` as the inner query turns virtually every document in the index scope into a candidate. If the script runs on a huge index, cost can escalate rapidly.

If business logic genuinely needs to rank all documents, consider:

- Filtering by tenant, status, time, or data scope.
- Partitioning data via appropriate indexes/aliases or routing.
- Using built-in scoring signals.
- Precomputing scores or features during ingestion.
- Running the script only in a rerank stage on a smaller top set if the architecture permits.

### 5.3. Filter Context vs. Scoring Context

Conditions that do not need to contribute to relevance should go in `filter` rather than `must` when appropriate.

- `must` requires the query to match and normally contributes to the score.
- `filter` requires the condition to hold without adding relevance points.
- `must_not` excludes documents.
- `should` can boost scores or act as a mandatory condition depending on `minimum_should_match` and `bool` structure.

Filters separate business constraints from scoring. They also give Elasticsearch the opportunity to leverage the filter cache when eligible, though you should not assume every filter is cached.

### 5.4. Limiting Index and Shard Scope

A query spanning many indexes or shards creates extra distribution and result-merging work. Target only required indexes/aliases, use routing when data is partitioned properly, and avoid overly broad wildcard index patterns.

Routing helps only when data partitioning and querying are designed together. Incorrect routing can miss documents or create uneven load across shards.

## 6. Keeping Scripts Short with Predictable Cost

### 6.1. Avoid Loops and Heavy Operations

`script_score` is invoked repeatedly—typically once per candidate document. Thus, even a tiny operation multiplied across hundreds of thousands of documents becomes expensive.

Avoid:

- Iterating over large collections in every document.
- Complex regexes or long string processing.
- Allocating unnecessary temporary objects.
- Recomputing invariant constants repeatedly.
- Reading `_source` or parsing JSON per hit when doc values can be used.
- Complex conditional branches that are unnecessary.

Prefer simple arithmetic, concise field checks, and parameters precalculated in the application.

### 6.2. Prefer Doc Values

Doc values are structured for per-document field access and generally suit script scoring well. `numeric`, `date`, and `keyword` fields are good choices for ranking signals.

Example:

~~~painless
if (doc['rating'].size() == 0) {
    return _score;
}
double rating = doc['rating'].value;
return _score + rating * params.ratingWeight;
~~~

For fields used heavily in scoring, design mappings with doc values. Do not enable `fielddata` on `text` just so a script can read it; instead consider adding a numeric/keyword companion field or normalizing data during ingestion.

### 6.3. Precompute What Can Be Precomputed

If a formula depends only on data that remains unchanged for long periods, consider computing it at document write time.

Examples:

- Composite quality score.
- Normalized conversion rate.
- Priority tier.
- Log-transformed popularity value.
- Business status converted to a numeric rank.

When queries only need to read a precomputed field, cost can be far lower than evaluating a complex formula for every candidate.

Be sure to update the precomputed feature whenever source data changes. Precomputing makes queries cheaper at the expense of shifting some work to ingestion and data synchronization.

### 6.4. Avoid Recomputing Invariant Values in Scripts

If `k`, weights, or normalization coefficients do not vary per document, pass them via `params` or precompute them in the application. Do not run expensive calculations repeatedly when parameters can be normalized before the request.

For formulas using `log`, `exp`, or `distance`, check value domains and prevent overflow/underflow.

## 7. Bounding Scores and Handling Invalid Values

### 7.1. Scores Must Be Non-Negative and Finite

A `script_score` must return a valid, non-negative number. Negative values, `NaN`, or infinity can cause Elasticsearch to reject the query or throw score-conversion errors.

Never use a formula that might return a negative number without checking. For signals that could be negative, shift them into a valid domain or clamp them using `max`/`min` according to business semantics.

Example:

~~~painless
double raw = doc['priority'].size() == 0
    ? 0.0
    : doc['priority'].value;

double safePriority = Math.max(0.0, Math.min(raw, 100.0));
return _score * (1.0 + safePriority / 100.0);
~~~

This script clamps `priority` to 0–100 before using it. Choose bounds based on real data rather than copying illustrative numbers mechanically.

### 7.2. Bounding Multipliers

If using a multiplier, define clear lower and upper bounds. Example:

\[
1 \le multiplier \le 1.5
\]

This keeps secondary signals from boosting scores outside controlled limits. If a signal should be able to demote scores, ensure the multiplier stays non-negative and does not unintentionally destroy relevance discrimination.

### 7.3. Avoid Overly Huge Scores

Elasticsearch uses floating-point scores with finite precision. Very large values can erase distinctions between close scores or introduce numerical issues.

Normalize features before combining, bound inputs, and keep formulas in a stable range. Scores are not a place to store exact business figures; never use them as substitutes for currency amounts or accounting calculations.

### 7.4. Checking Missing Fields and Mapping Types

Scripts reading `doc['field']` depend on index mappings. If a field is unmapped, the script can fail. If a field is mapped yet missing in a document, `size()` can be 0.

When querying across multiple indexes with inconsistent mappings, a field might exist in one index and be missing or differently typed in another. Align mappings or handle unmapped cases explicitly where the query/script context permits.

## 8. script_score, function_score, and Built-in Scoring

### 8.1. When to Use function_score?

`function_score` lets you combine a query score with one or more scoring functions. These functions include:

- `weight`
- `field_value_factor`
- `random_score`
- Decay functions such as `gauss`, `exp`, `linear`
- `script_score` when custom logic is needed

If you only need to scale by a numeric field, `field_value_factor` can be simpler than `script_score`.

Conceptual example:

~~~json
{
  "query": {
    "function_score": {
      "query": {
        "match": {
          "name": "wireless keyboard"
        }
      },
      "field_value_factor": {
        "field": "popularity",
        "modifier": "log1p",
        "factor": 0.5,
        "missing": 0
      },
      "boost_mode": "sum"
    }
  }
}
~~~

Check `score_mode` and `boost_mode` semantics against your desired formula. `function_score` can combine multiple functions in various modes; do not assume the output matches a handwritten script without checking.

### 8.2. Using Decay Functions for Recency or Distance

If results near a timestamp or location should be preferred, decay functions can be a better fit than writing formulas manually.

Conceptual examples:

- Newer articles receive a boost.
- Places near the search location are preferred.
- Events close to the current time score higher.

Decay functions provide parameters such as `origin`, `scale`, `offset`, and `decay`. They describe score drop-off over distance or time without writing all the math in Painless.

### 8.3. Using rank_feature for Suitable Signals

If a numeric field represents a ranking feature, consider the `rank_feature` mapping and corresponding query. Elasticsearch supports feature scoring functions such as `saturation`, `log`, and `sigmoid` depending on field/query type.

This field/query type is purpose-built for ranking features and can outperform custom scripts. Check mapping requirements and `rank_feature` limitations before choosing it.

### 8.4. Selection Table

| Need | Tool to Consider |
|---|---|
| Combine relevance with one numeric field | `field_value_factor` |
| Prefer by recency/distance | Decay function |
| Ranking feature with saturation/log | `rank_feature` |
| Custom formula with multiple arithmetic conditions | `script_score` |
| Multiple scoring functions combined | `function_score` |
| Stable signal that can be precomputed | Precomputed numeric field |

Only reach for `script_score` when built-in tools cannot express the required formula or benchmarks confirm it is the right choice.

## 9. Reducing the Number of Documents Executing Scripts

### 9.1. Rescoring Top Results

In some systems, you can run a cheap initial query to gather candidates and then apply a more expensive reranking step over a top window of results. Elasticsearch offers a `rescore` API with `window_size` to cap how many hits are rescored per shard.

This pattern helps when:

1. The first query uses cheap matching/filtering and inexpensive scoring.
2. It collects a sufficiently broad candidate pool.
3. Advanced scoring runs over that candidate pool.
4. Top results are returned after reranking.

Check query types and `script_score` support within `rescore` for your Elasticsearch version. A `window_size` that is too small can miss documents that would have risen via secondary signals; too large raises cost.

### 9.2. Application-Side Reranking Has Its Own Tradeoffs

You can retrieve a bounded candidate set and compute extra scores in the application. This lets you express algorithms in Java, though it may require fetching many fields and holding data in memory.

Use this only when the candidate set is already small, needed fields can be fetched efficiently, and reranking in the app does not break pagination semantics. Never fetch one small page and rerank it if users expect a global top list; relevant items beyond the first page will never get a chance to be promoted.

### 9.3. Filter with Business Conditions Before Reranking

Conditions such as tenant, access rights, active status, effective dates, and categories should reside in the inner query/filter whenever possible.

In particular, authorization filters must live inside the query executed by Elasticsearch or be enforced by an unbypassable mechanism. Never filter only after application-side script scoring, as that can leak metadata or waste work.

## 10. Cost Limits at Cluster and Request Levels

### 10.1. search.allow_expensive_queries

Elasticsearch has a cluster setting `search.allow_expensive_queries`. When disabled, certain queries classified as expensive—including `script_score`—can be rejected.

This is a cluster-side policy, not an `@Document` or repository property. The application must know whether the production environment permits this query class.

Never flip a cluster-wide setting just to let an unoptimized query run. First evaluate candidate counts, built-in scoring alternatives, or indexing changes.

### 10.2. Script Compilation Rate and Cache

Script sources must be compiled. Elasticsearch enforces compilation rate limits and caches compiled scripts. Generating new sources constantly can trigger rate-limit errors or cache thrashing.

Keep sources static, pass data via `params`, and monitor script-related metrics/logs. Settings like `script.max_compilations_rate` and cache size vary by version; consult documentation for your running cluster before tuning them.

### 10.3. Search Timeouts Are Not Exact CPU Quotas

Search requests can specify a timeout to bound wait time. However, a timeout is not a precise CPU quota for a script and can cause responses to return partial results with `timed_out` set.

Applications must check the timeout flag and avoid presenting incomplete results as complete if business rules prohibit it.

### 10.4. Limiting Page Size Does Not Limit Script Executions

Setting `size: 10` only limits returned hits; it does not mean the script ran on only 10 documents. To rank the top 10, Elasticsearch may still need to score many matching candidates.

This is a key reason to filter the candidate set. A small page size reduces response payload, but does not replace narrowing the inner query.

### 10.5. Restricting Inputs and Query Permissions

Public APIs should never accept Painless source, arbitrary stored script IDs, arbitrary field names, or full DSL from clients. Instead:

- Pick scripts from an application-managed allowlist.
- Accept only strongly typed `params`.
- Validate parameter value ranges.
- Cap page size and query breadth.
- Apply authorization filters.
- Monitor query timeouts and script errors.

Painless has its own sandbox and contexts, yet that does not replace application-layer access control and cost limits.

## 11. Integrating script_score in Spring Data Elasticsearch

### 11.1. Using NativeQuery for Type-Safe DSL

Spring Data Elasticsearch provides `NativeQuery` to construct queries using the Elasticsearch Java API Client. Exact builders for `script_score` depend on the client and Spring Data version. Use the script/query builders supplied by your current dependency rather than copying builder snippets from a different version.

The target Query DSL structure is:

- `script_score` on the outside.
- Inner query containing `match`/`filter`.
- Static script source.
- Separate `params`.

### 11.2. Using StringQuery for Static JSON DSL

When managing query JSON in resources or using pre-tested DSL, you can use `StringQuery`:

~~~java
String queryJson = """
{
  "script_score": {
    "query": {
      "bool": {
        "must": [
          {
            "match": {
              "name": "wireless keyboard"
            }
          }
        ],
        "filter": [
          {
            "term": {
              "available": true
            }
          }
        ]
      }
    },
    "script": {
      "source": "return _score * (1.0 + params.boost);",
      "params": {
        "boost": 0.2
      }
    }
  }
}
""";

Query query = new StringQuery(queryJson);

SearchHits<ProductDocument> hits =
    operations.search(query, ProductDocument.class);
~~~

This is a query clause for Spring Data, not the entire search request body with an outer `query` field. For runtime parameters, build a JSON tree and serialize with Jackson rather than concatenating strings.

### 11.3. Using JSON Resources and Runtime Parameters

You can store the query template on the classpath and populate `params` with Jackson:

~~~json
{
  "script_score": {
    "query": {
      "bool": {
        "must": [
          {
            "match": {
              "name": {
                "query": ""
              }
            }
          }
        ],
        "filter": [
          {
            "term": {
              "available": true
            }
          }
        ]
      }
    },
    "script": {
      "source": "return _score * (1.0 + params.boost);",
      "params": {
        "boost": 0.0
      }
    }
  }
}
~~~

Java updates the typed nodes:

~~~java
ObjectNode root = (ObjectNode) template.deepCopy();

ObjectNode match = (ObjectNode) root.at(
    "/script_score/query/bool/must/0/match/name"
);
match.put("query", keyword);

ObjectNode params = (ObjectNode) root.at(
    "/script_score/script/params"
);
params.put("boost", boost);
~~~

Then serialize to JSON and build `StringQuery`. Each request must use a fresh copy of the template so concurrent requests do not overwrite each other's `params`.

### 11.4. Attaching Sort and Pageable Separately

Sort and pageable can be configured via Spring Data `Query` instead of embedding the entire search request in JSON:

~~~java
query.setPageable(PageRequest.of(0, 20));
~~~

If sorting by score is needed, let query scoring drive the default order or declare an appropriate sort. If sorting by a business field, recognize that field sort order can override the role of the score.

## 12. Testing Formulas and Ranking Behavior

### 12.1. Unit Tests for Normalization Functions

If the formula can be mirrored in a pure Java helper, test boundary cases first:

- Popularity equal to 0.
- Missing popularity.
- Negative popularity.
- Popularity at threshold.
- Extremely large popularity.
- Weight equal to 0.
- Invalid `k` parameter.

Example testing a saturation function:

~~~java
static double normalizePopularity(double popularity, double k) {
    if (k <= 0) {
        throw new IllegalArgumentException("k must be positive");
    }

    double safePopularity = Math.max(0.0, popularity);
    return safePopularity / (safePopularity + k);
}
~~~

Unit tests for a Java helper do not verify that the Painless script behaves identically. They only test the math and validation in the application layer.

### 12.2. Integration Tests with Elasticsearch

Run integration tests against a compatible Elasticsearch instance to verify:

1. Mapping includes numeric fields with appropriate doc values.
2. The script compiles and runs in the Painless context.
3. Documents missing the field do not break the query.
4. Scores are non-negative and finite.
5. `params` alter results as expected.
6. The inner query filter excludes out-of-scope documents.
7. Result ordering follows the formula.
8. Cluster policy permits `script_score`.
9. The query does not time out on a representative dataset.

Mocking `ElasticsearchOperations` cannot verify Painless compilation or how Elasticsearch evaluates scores.

### 12.3. Comparing Rankings Before and After

Create a representative query set, assign relevance labels, and compare:

- Precision@k.
- NDCG@k.
- MRR.
- Rate at which desired business results appear near the top.
- p50, p95, and p99 latency.
- CPU usage and number of candidates evaluated.

If ranking improves while latency rises excessively, consider shrinking the candidate set, using precomputed features, or revising the formula.

### 12.4. Using Explain and Profile Purposefully

Explain helps clarify an individual document's score and scoring components. The Profile API lets you inspect per-shard execution cost across query parts.

Profile carries noticeable overhead and should not be enabled broadly on production requests. Run it on representative queries in test environments or during controlled investigations.

## 13. Monitoring Cost in Operations

### 13.1. Metrics to Observe

Track at least:

- Number of requests using `script_score`.
- p50/p95/p99 latency for that query group.
- Timed-out and rejected requests.
- Number of shards/indexes queried.
- Estimated candidate count or total hits.
- CPU and search thread pool load.
- Script compilation/cache metrics and compilation errors.
- Number of queries rejected due to expensive-query policy.

Compare metrics before and after rolling out a new formula.

### 13.2. Controlled Query Logging

You can log query ID, script version, execution time, page size, and timeout status. Avoid logging sensitive payloads or Painless source generated from inputs.

If multiple queries share a stored script, logging ID/version helps pinpoint which formula was active when investigating ranking shifts.

### 13.3. Rolling Out New Formulas

When changing a `script_score`, roll out incrementally:

1. Create a new script version.
2. Run integration tests and benchmarks.
3. Compare rankings on a labeled query set.
4. Trial on controlled traffic or test datasets.
5. Monitor latency, CPU, timeouts, and result quality.
6. Retain the ability to roll back to the previous version on regressions.

Modifying a shared stored script can impact multiple endpoints simultaneously. Use explicit versioning and controlled rollouts instead of editing source in place.

## 14. Common Mistakes

| Symptom | Possible Cause | Resolution |
|---|---|---|
| Script fails reading a field | Field is missing from mapping or document lacks a value | Check mapping and guard with `doc['field'].size()` before `.value` |
| Query rejected despite valid DSL | `search.allow_expensive_queries` is disabled | Check cluster policy and evaluate alternative scoring |
| Compilation rate limit exceeded | Script source changes continuously across requests | Keep source static and pass values through `params` |
| Ranking dominated by popularity | Feature scale outweighs text score | Normalize features and cap multipliers |
| Script returns invalid score | Formula produces negative numbers, `NaN`, or infinity | Validate data domains and clamp outputs |
| Query is very slow on large indexes | Inner query selects too many candidates | Add filters, appropriate routing, or use reranking |
| Small `size` still consumes high CPU | Script still scores many candidates to find top hits | Narrow the inner query; consider a rescore window |
| Script consumes heavy heap | Reading `text` fields via `fielddata` or large objects | Use doc values and suitable numeric fields |
| Unstable results across indexes | Inconsistent mappings or feature data | Align schemas and handle missing/unmapped fields |
| Unit tests pass yet production fails | Painless was never compiled/run against real Elasticsearch | Add integration tests on the target version |
| Editing a stored script alters multiple screens | Multiple queries share the same script ID | Version scripts and roll out in a controlled manner |

## 15. Decision Checklist for Using script_score

Before writing a script, verify:

1. Does the default relevance score genuinely fail to meet requirements?
2. Can the secondary signal be expressed with `field_value_factor`, decay functions, or `rank_feature`?
3. Do the scoring fields have doc values and proper mappings?
4. Can the inner query filter candidates tightly enough?
5. Are the formula's input domain and output score bounded?
6. Is the source static so it benefits from the compilation cache?
7. Can features be precomputed at ingestion time?
8. Should rescoring run only on top candidates?
9. Do integration tests and a query set exist to evaluate ranking?
10. Does the production cluster allow expensive queries and have sufficient resources?

If a formula is simple, prefer built-in scoring functions. When a script is needed, keep it short, static, parameterized via `params`, and scoped to a filtered candidate set.

## 16. Key Takeaways

- `script_score` computes new scores for documents matching the inner query.
- Painless scripts can combine `_score`, doc values, and `params`.
- `script_score` must return valid, non-negative, finite numbers.
- Always check for missing fields before accessing `.value`.
- Normalize features and bound multipliers so secondary signals do not overwhelm relevance.
- Use `params` instead of dynamic source generation to reduce compilation and leverage caching.
- Filter candidates before running the script; a small page size does not bound how many documents get scored.
- Prefer doc values and precomputing features when formulas can be shifted to ingestion.
- Consider `field_value_factor`, decay functions, `rank_feature`, or rescoring before scripting over all candidates.
- `search.allow_expensive_queries` can block `script_score`; script compilation rates and caches must also be monitored.
- Timeouts are not exact CPU quotas and can yield partial results.
- Test Painless on real Elasticsearch and measure both ranking and latency on representative data.

`script_score` is valuable when business signals must enter ranking via a custom formula. Implementation quality hinges on picking the right candidates, keeping formulas stable, and bounding computation cost. When those pieces are well-designed, applications can improve result ordering while keeping search load predictable.
