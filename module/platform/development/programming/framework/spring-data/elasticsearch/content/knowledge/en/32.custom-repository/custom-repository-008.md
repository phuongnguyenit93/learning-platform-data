# Testing Fragments and Real Repository Configuration

Spring Data Elasticsearch lets you extend repositories with custom fragments. A single repository can combine methods auto-generated by Spring Data with methods implemented by the application—such as finding active products, applying custom search rules, or coordinating multiple Elasticsearch operations.

A fragment only works properly when Spring Data discovers the interface, locates the implementation, and composes them into the repository. Consequently, testing custom methods by instantiating and calling the implementation directly is not enough. The application must also verify that repository scanning, implementation naming, package placement, injected templates, entity mappings, and actual Elasticsearch connectivity are all configured properly.

This lesson explains how to structure fragments, test fragment logic in isolation, test how Spring wires repositories together, spin up real Elasticsearch for integration tests, and troubleshoot common configuration errors.

## 1. What Is a Repository Fragment?

A Spring Data repository can combine several slices of functionality. Part comes from the framework, while other parts are added via fragment interfaces and implementation classes written by the application.

For example, a product repository might need:

- **findById** and **save** provided by ElasticsearchRepository.
- **findByStatus** derived from the method name.
- **findActiveProducts** implemented by the application in a fragment.
- A complex search query using ElasticsearchOperations.

You can visualize the structure as:

~~~text
ProductRepository
       |
       +---- ElasticsearchRepository<Product, String>
       |          |
       |          +---- Spring Data CRUD and query methods
       |
       +---- ProductSearchFragment
                  |
                  +---- ProductSearchFragmentImpl
                             |
                             +---- ElasticsearchOperations
~~~

The main repository simply extends the fragment interface. Spring Data finds the matching implementation and merges it into the repository proxy created when the application context starts.

Fragments separate custom queries from large repository interfaces while allowing the same behavior to be reused across multiple repositories when designed appropriately.

## 2. Creating the Fragment Interface

Example fragment providing methods to find active products:

~~~java
public interface ProductSearchFragment {

    List<Product> findActiveProducts();

    List<Product> searchByNameAndStatus(
        String name,
        String status
    );
}
~~~

The interface describes the behavior the repository will expose. It does not need to extend Repository or ElasticsearchRepository.

The main repository combines the fragment with a Spring Data repository:

~~~java
public interface ProductRepository
        extends ElasticsearchRepository<Product, String>,
                ProductSearchFragment {

    List<Product> findByStatus(String status);
}
~~~

Once Spring Data creates the repository proxy, callers can invoke CRUD, derived queries, and fragment methods on the same bean:

~~~java
@Service
public class ProductService {

    private final ProductRepository repository;

    public ProductService(ProductRepository repository) {
        this.repository = repository;
    }

    public List<Product> getActiveProducts() {
        return repository.findActiveProducts();
    }
}
~~~

There is no need to inject ProductSearchFragmentImpl separately into services. Applications should depend on the composed repository interface.

## 3. Naming and Placing the Implementation

Under the modern fragment composition mechanism, the implementation class normally uses the fragment interface name plus the repository implementation postfix. With the default postfix Impl:

| Fragment interface | Implementation class |
|---|---|
| ProductSearchFragment | ProductSearchFragmentImpl |
| InventoryRepositoryFragment | InventoryRepositoryFragmentImpl |
| ProductStatistics | ProductStatisticsImpl |

Example:

~~~java
public class ProductSearchFragmentImpl
        implements ProductSearchFragment {

    private final ElasticsearchOperations operations;

    public ProductSearchFragmentImpl(
            ElasticsearchOperations operations) {
        this.operations = operations;
    }

    @Override
    public List<Product> findActiveProducts() {
        // Query implementation
        return List.of();
    }

    @Override
    public List<Product> searchByNameAndStatus(
            String name,
            String status) {
        // Query implementation
        return List.of();
    }
}
~~~

The implementation must reside within the package scope discoverable by repository implementation scanning as configured. A simple organization is placing the fragment interface, implementation, and main repository interface in the same package or in a clearly defined package layout.

Wrong class suffixes, wrong packages, or mismatches with the fragment interface are common reasons Spring fails to wire an implementation.

### Fragment Implementations Differ from Legacy Repository Implementations

Older Spring Data guides often instructed creating a class named after the repository itself, such as ProductRepositoryImpl. That mechanism is the legacy custom repository implementation style.

With fragment composition, create a dedicated fragment interface and name the implementation after the fragment. This is clearer when a repository has multiple groups of custom methods and makes fragments reusable.

Do not mix the two naming conventions without a clear reason. When upgrading Spring Data, verify the discovery conventions supported by your version.

## 4. Implementing the Fragment with ElasticsearchOperations

ElasticsearchOperations offers an imperative API for building queries, reading results, indexing, and updating documents. Fragments can inject operations via constructor.

Example entity:

~~~java
@Document(indexName = "products")
public class Product {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String name;

    @Field(type = FieldType.Keyword)
    private String status;

    @Field(type = FieldType.Boolean)
    private boolean active;

    // constructors, getters and setters
}
~~~

Implementation:

~~~java
public class ProductSearchFragmentImpl
        implements ProductSearchFragment {

    private final ElasticsearchOperations operations;

    public ProductSearchFragmentImpl(
            ElasticsearchOperations operations) {
        this.operations = operations;
    }

    @Override
    public List<Product> findActiveProducts() {
        Query query = new CriteriaQuery(
            new Criteria("active").is(true)
        );

        SearchHits<Product> hits =
            operations.search(query, Product.class);

        return hits.getSearchHits().stream()
            .map(SearchHit::getContent)
            .toList();
    }

    @Override
    public List<Product> searchByNameAndStatus(
            String name,
            String status) {

        Criteria criteria = new Criteria("name").matches(name)
            .and("status").is(status);

        Query query = new CriteriaQuery(criteria);

        SearchHits<Product> hits =
            operations.search(query, Product.class);

        return hits.getSearchHits().stream()
            .map(SearchHit::getContent)
            .toList();
    }
}
~~~

This example uses Criteria to illustrate a fragment calling Operations. For complex full-text queries, you can substitute NativeQuery and Java API Client builders. Specific Criteria and NativeQuery APIs must match your project's Spring Data Elasticsearch version.

### Why Should the Implementation Not Create Its Own Client?

When the application already configures ElasticsearchOperations, inject that bean instead of instantiating a new client inside the fragment. Doing so ensures the fragment shares the same:

- Connections and authentication.
- Converters and entity mappings.
- IndexCoordinates.
- Client timeouts and related settings.
- Observability/logging mechanisms configured for the application.

Creating a standalone client inside a fragment can cause production and tests to behave differently while complicating resource lifecycle management.

## 5. Using a Fragment Across Multiple Repositories

A fragment can be shared across multiple repositories if its behavior is not tightly coupled to a single entity or index.

Example status-search fragment:

~~~java
public interface StatusSearchFragment<T> {

    List<T> findByStatus(String status);
}
~~~

However, a generic fragment needs a clear implementation and way to resolve the entity type. If the implementation needs Class<T>, index names, or specific mappings, design constructors/metadata compatible with fragment composition.

In many applications, aggregate-specific fragments are easier to understand and less risky than overly generalized generic fragments.

Do not share a fragment merely because two repositories happen to have a method with the same name. Share only when semantics, mappings, and expected results genuinely match.

## 6. Repository Scanning and Real Configuration

Spring Data needs to know which packages contain repository interfaces and which template executes them.

In Spring Boot applications, auto-configuration usually creates the client, converter, and template from application properties. When using explicit repository configuration, you can declare:

~~~java
@Configuration
@EnableElasticsearchRepositories(
    basePackages = "com.example.catalog.repository",
    repositoryImplementationPostfix = "Impl"
)
public class ElasticsearchRepositoryConfiguration {
}
~~~

basePackages must cover ProductRepository's package. The postfix must match fragment implementation names. If using a dedicated template, the annotation has a template reference attribute; check the exact attribute and bean name for your installed Spring Data version.

Do not declare overlapping repository scan configurations over the same package unintentionally. Duplicate scanning can cause bean definition conflicts or bind repositories to the wrong template.

### When Is `@EnableElasticsearchRepositories` Needed?

Use this annotation when you need explicit control over package scanning or want to configure repositories outside default auto-configuration. In simple Boot applications, you can let auto-configuration discover repositories starting from the application class's root package.

If repositories sit outside the default scan package, expand the scan packages or configure EnableElasticsearchRepositories explicitly.

### Distinguishing Imperative and Reactive Templates

Spring Data Elasticsearch provides both imperative and reactive APIs:

- ElasticsearchRepository follows the imperative model.
- ReactiveElasticsearchRepository follows the reactive model.
- ElasticsearchOperations is the imperative API.
- ReactiveElasticsearchOperations is the reactive API.

Imperative fragments should inject ElasticsearchOperations. Reactive fragments should inject ReactiveElasticsearchOperations and return Mono/Flux.

Never inject reactive operations into an imperative fragment and call block() to make it synchronous. Likewise, never use blocking ElasticsearchOperations on reactive request paths.

## 7. Configuring Clients and Templates for the Application

Repository proxies need an appropriate template to execute queries. In Spring Boot, common endpoint properties sit under the spring.elasticsearch prefix, for example:

~~~yaml
spring:
  elasticsearch:
    uris: http://localhost:9200
~~~

Depending on version and environment, you may also configure username, password, TLS, or other client options. Never commit production secrets into configuration files.

If configuring beans manually instead of relying on Boot auto-configuration, verify that client, converter, template, and repository scanning beans are compatible with the same Spring Data Elasticsearch / Elasticsearch Java API Client version.

Do not put a fake or mock template in production configuration just to get repositories to start. Integration tests should validate configuration resembling the real application.

### Multiple Clusters or Multiple Templates

An application may connect to multiple Elasticsearch clusters or use multiple templates. In that case, each group of repositories must bind to its corresponding template and client.

Choose clear bean names, for example:

- catalogElasticsearchOperations
- analyticsElasticsearchOperations
- catalogElasticsearchClient
- analyticsElasticsearchClient

Repository scan configuration must reference the right template bean. Avoid relying on Primary beans when a repository needs a specific cluster; explicit wiring is far easier to verify.

## 8. Unit Testing Fragments in Isolation

Fragment unit tests focus on implementation logic and how it calls ElasticsearchOperations. You do not need to start a Spring context or real Elasticsearch just to verify query construction and result conversion.

You can use Mockito to mock Operations and SearchHits.

~~~java
@ExtendWith(MockitoExtension.class)
class ProductSearchFragmentImplTest {

    @Mock
    ElasticsearchOperations operations;

    @Mock
    SearchHits<Product> searchHits;

    @Mock
    SearchHit<Product> searchHit;

    @Test
    void returnsActiveProducts() {
        Product product = new Product();
        product.setId("P-100");
        product.setActive(true);

        when(searchHit.getContent()).thenReturn(product);
        when(searchHits.getSearchHits())
            .thenReturn(List.of(searchHit));
        when(operations.search(
            any(Query.class),
            eq(Product.class)
        )).thenReturn(searchHits);

        ProductSearchFragmentImpl fragment =
            new ProductSearchFragmentImpl(operations);

        List<Product> result = fragment.findActiveProducts();

        assertThat(result).containsExactly(product);
        verify(operations).search(
            any(Query.class),
            eq(Product.class)
        );
    }
}
~~~

This is a test skeleton. Entity constructors, Query types, and search overloads must match your installed version.

This unit test proves the implementation turns SearchHits into an entity list and calls Operations. It does not prove Spring Data discovers the fragment or composes the repository proxy correctly.

### Inspecting Query Contents

When query conditions are central to the logic, do not just verify any(Query.class). Use ArgumentCaptor<Query> to capture the submitted query:

~~~java
ArgumentCaptor<Query> queryCaptor =
    ArgumentCaptor.forClass(Query.class);

verify(operations).search(
    queryCaptor.capture(),
    eq(Product.class)
);

Query actualQuery = queryCaptor.getValue();
~~~

Then inspect the query type, Criteria, or constructed query structure using the appropriate API. If query objects are awkward to inspect directly, verify behavior with integration tests against Elasticsearch.

## 9. Testing Spring Repository Composition

An essential integration test boots the Spring context, injects the repository interface, and calls the fragment method through the repository proxy.

This simultaneously verifies that:

- The repository package is scanned.
- The fragment interface is recognized.
- The implementation class is found.
- Constructor dependencies are injected.
- The repository proxy combines CRUD, derived queries, and fragments.
- The right template is used.

Test structure example:

~~~java
@SpringBootTest
class ProductRepositoryCompositionTest {

    @Autowired
    ProductRepository repository;

    @Test
    void repositoryContainsCustomFragment() {
        List<Product> products =
            repository.findActiveProducts();

        assertThat(products).isNotNull();
    }
}
~~~

If the fragment is not discovered, the context may fail to start or fragment methods may lack an implementation. This test catches wiring errors that standalone implementation unit tests cannot see.

To verify business outcomes, tests should index controlled seed data before calling methods rather than merely asserting the returned list is non-null.

## 10. Using Testcontainers to Test Against Real Elasticsearch

Elasticsearch has its own semantics for mappings, analyzers, Query DSL, refresh, and version compatibility. Mocking ElasticsearchOperations cannot validate any of those behaviors.

Testcontainers can start Elasticsearch inside Docker for integration tests. Pick an image version compatible with the Spring Data Elasticsearch and Java API Client versions used by your project. Never use the latest tag, as newer versions can change behavior or break dependency compatibility.

Example structure with JUnit 5 and Testcontainers:

~~~java
@Testcontainers
@SpringBootTest
class ProductRepositoryIntegrationTest {

    @Container
    static final ElasticsearchContainer elasticsearch =
        new ElasticsearchContainer(
            DockerImageName.parse(
                "docker.elastic.co/elasticsearch/elasticsearch:8.17.0"
            )
        ).withEnv("xpack.security.enabled", "false");

    @DynamicPropertySource
    static void elasticsearchProperties(
            DynamicPropertyRegistry registry) {
        registry.add(
            "spring.elasticsearch.uris",
            elasticsearch::getHttpHostAddress
        );
    }

    @Autowired
    ProductRepository repository;

    @Autowired
    ElasticsearchOperations operations;
}
~~~

This is an illustrative structure. Select an image tag matching your project's compatibility matrix; if the image or Testcontainers version enables security by default, configure username/password and TLS to match the container rather than disabling security. Some Testcontainers Elasticsearch releases configure containers differently.

DynamicPropertySource supplies the container address before Spring creates the client and template. Never initialize repositories before the endpoint is registered.

### Do Not Pick Arbitrary Docker Images

The test image should match the Elasticsearch version used by your real runtime environment. If production runs a specific version, integration tests should run the same major version and ideally a compatible minor version.

A passing test with mocks does not guarantee queries work in production Elasticsearch. Conversely, testing against a far-off version can produce unrepresentative results.

## 11. Preparing Indexes and Data for Integration Tests

Tests must create indexes with the right mappings before saving documents. You can use IndexOperations:

~~~java
@BeforeEach
void prepareIndex() {
    IndexOperations indexOperations =
        operations.indexOps(Product.class);

    if (indexOperations.exists()) {
        indexOperations.delete();
    }

    indexOperations.create();
    indexOperations.putMapping(
        indexOperations.createMapping(Product.class)
    );
}
~~~

Method names and mapping creation depend on the Spring Data Elasticsearch version. In projects using aliases or dynamic index names, tests must set up the exact target the repository uses.

Next, save test data:

~~~java
Product first = new Product();
first.setId("P-100");
first.setName("Wireless Keyboard");
first.setStatus("ACTIVE");
first.setActive(true);

Product second = new Product();
second.setId("P-101");
second.setName("Office Mouse");
second.setStatus("ACTIVE");
second.setActive(false);

repository.saveAll(List.of(first, second));
~~~

Elasticsearch has a refresh interval, so newly indexed documents may not appear immediately in searches. In tests, refresh the index before querying:

~~~java
operations.indexOps(Product.class).refresh();
~~~

Never use arbitrary Thread.sleep calls to wait for documents. Use refresh or explicit synchronization mechanisms in tests.

### Verifying Fragment Methods Through the Real Repository

~~~java
@Test
void customFragmentFindsOnlyActiveProducts() {
    List<Product> result =
        repository.findActiveProducts();

    assertThat(result)
        .extracting(Product::getId)
        .containsExactly("P-100");
}
~~~

Results depend on seed data and return order. If a query specifies no sort, do not assert ordering; use containsExactlyInAnyOrder when order is not part of the contract.

## 12. Testing Repository Scanning and Package Boundaries

A common mistake occurs when a test class resides in a package that can scan repositories, while the real application starts from a different root package. Passing a test using a test-only configuration does not guarantee production scanning behaves the same way.

Verify that:

- The application main class sits in an appropriate root package.
- Repository interfaces sit in scanned packages.
- Fragment implementations lie within the discovery scope.
- EnableElasticsearchRepositories does not point to the wrong package.
- Two configurations do not scan the same repositories.
- Tests do not add an `@Import` that masks broken production component scanning.
- Repositories use the right template bean.

You can write a context test solely to confirm the repository bean is created:

~~~java
@SpringBootTest
class RepositoryConfigurationTest {

    @Autowired
    ApplicationContext context;

    @Test
    void productRepositoryBeanExists() {
        assertThat(context.getBean(ProductRepository.class))
            .isNotNull();
    }
}
~~~

This is a basic wiring check. Integration tests that invoke a real fragment method additionally verify the implementation was attached to the repository proxy.

## 13. Testing Multiple Repositories and Multiple Templates

When an application has multiple repository groups, verify each group binds to its intended template.

Example:

~~~java
@Configuration
@EnableElasticsearchRepositories(
    basePackages = "com.example.catalog.repository",
    elasticsearchTemplateRef = "catalogElasticsearchTemplate"
)
class CatalogRepositoryConfiguration {
}
~~~

~~~java
@Configuration
@EnableElasticsearchRepositories(
    basePackages = "com.example.analytics.repository",
    elasticsearchTemplateRef = "analyticsElasticsearchTemplate"
)
class AnalyticsRepositoryConfiguration {
}
~~~

The template reference attribute name and template type must match your installed Spring Data Elasticsearch version.

In integration tests, seed distinct data in each cluster or index. Invoke each repository and confirm data is not accidentally read from the other template. Simply asserting both beans exist is not enough to prove wiring is right.

If two configurations scan the same package, repositories may register multiple times or bind to the wrong template. Separate repository packages by bounded context when working with multiple clusters.

## 14. Testing Reactive Repository Fragments

If the application uses reactive repositories, fragments must also preserve the reactive contract.

Interface:

~~~java
public interface ReactiveProductSearchFragment {

    Flux<Product> findActiveProducts();
}
~~~

Implementation:

~~~java
public class ReactiveProductSearchFragmentImpl
        implements ReactiveProductSearchFragment {

    private final ReactiveElasticsearchOperations operations;

    public ReactiveProductSearchFragmentImpl(
            ReactiveElasticsearchOperations operations) {
        this.operations = operations;
    }

    @Override
    public Flux<Product> findActiveProducts() {
        Query query = new CriteriaQuery(
            new Criteria("active").is(true)
        );

        return operations.search(query, Product.class)
            .map(SearchHit::getContent);
    }
}
~~~

Repository:

~~~java
public interface ProductReactiveRepository
        extends ReactiveElasticsearchRepository<Product, String>,
                ReactiveProductSearchFragment {
}
~~~

Never call block() inside a reactive implementation to fetch results synchronously. Unit tests can use StepVerifier, while integration tests should start a real reactive repository and call fragment methods via the proxy.

Example:

~~~java
StepVerifier.create(repository.findActiveProducts())
    .expectNextMatches(Product::isActive)
    .thenCancel()
    .verify();
~~~

If a test needs to verify every item and Publisher completion, use expectNextCount, expectNextMatches, and verifyComplete matching the seed data.

## 15. Distinguishing Unit, Slice, and Integration Tests

These three testing levels answer different questions:

| Test level | Components executed | What it verifies |
|---|---|---|
| Fragment unit test | Implementation and mocked Operations | Conversion logic, parameters, and dependency interactions |
| Repository/context test | Spring application context and repository proxy | Fragment discovery, package scanning, bean wiring |
| Integration test | Spring Data with real Elasticsearch | Mappings, Query DSL, analyzers, refresh, and real results |

A good test suite does not need to boot Elasticsearch for every single case. Use fast unit tests for focused logic, paired with targeted integration tests to verify framework and cluster behavior.

### `@DataElasticsearchTest`

Spring Boot provides the DataElasticsearchTest slice in supported versions. This slice focuses on Elasticsearch components and can fit when testing repositories/templates without booting the entire application.

However, slice tests may omit application services, configurations, or other beans. If a custom fragment implementation depends on beans outside the slice, import the needed configurations or use SpringBootTest for full application wiring tests.

Do not assume DataElasticsearchTest automatically provides an Elasticsearch server. Tests still need a real Elasticsearch endpoint, such as Testcontainers or a dedicated managed test instance.

## 16. Testing Mappings and Query DSL, Not Just Beans

A repository bean booting cleanly does not prove mappings are right. Integration tests should confirm critical fields have the right types and queries return accurate results.

For example:

- Name fields use text and the expected analyzer.
- Status fields use keyword.
- Boolean fields have boolean mappings.
- Nested collections use nested mappings when preserving object boundaries.
- Multi-fields have a keyword subfield when exact queries or sorts rely on them.
- Aliases point to indexes with compatible mappings.

You can verify generated mappings from entities using IndexOperations or by calling Elasticsearch's mapping API. Exact retrieval methods vary by version.

For analyzers, test data with multiple tokens, mixed case, diacritics, or special characters matching the analyzer your application configures. Do not rely solely on a simple single-word match test.

## 17. Test Data, Isolation, and Parallel Execution

Integration tests need isolated data so outcomes never depend on previously run tests.

Strategies:

- Delete and recreate the index before each test when the suite is small.
- Use dedicated indexes per test class or test run.
- Use test-prefixed IDs to avoid collisions.
- Clean up documents after tests when sharing an index.
- Disable or control parallel execution when multiple tests wipe the same index.
- With aliases, create separate target indexes and bind aliases during setup.

Never let tests share development or production indexes. Test data must be isolated and safe to delete.

Sharing a single Testcontainers instance across multiple test classes reduces startup time, but you still need isolation at the index and document ID level. Starting a fresh container per test class can increase build times significantly.

## 18. Testing Repository Configuration Errors

Include tests—or at least one application context startup check in CI—to catch:

- Fragment implementations missing constructor dependencies.
- Wrong implementation postfix names.
- Unscanned repository packages.
- Two repositories sharing the same bean name.
- Missing or wrong-typed template beans.
- Converters lacking required mapping metadata.
- Clients unable to reach endpoints.
- Incorrect authentication or TLS settings.
- Incompatible Elasticsearch versions.

Some errors surface at startup; others only appear when a repository method is invoked. Thus, both context tests and fragment execution tests are necessary.

### Distinguishing Wiring Errors from Connection Errors

If the context reports a missing ElasticsearchOperations bean, that is a wiring/configuration error. If the repository proxy builds but requests fail with connection refused, that is an endpoint connectivity error.

Do not paper over either failure by adding mock beans in integration tests. Mocks can mask missing production configuration.

## 19. CI and Test Execution Environments

To keep integration tests stable in CI:

- Pin the Elasticsearch container version.
- Ensure CI runners support Docker or compatible container runtimes.
- Wait for container health checks before starting the Spring context.
- Allocate sufficient memory for the Elasticsearch test node.
- Use dynamic endpoints from Testcontainers instead of hardcoding localhost:9200.
- Never commit real passwords or certificates.
- Limit parallel test execution if tests share indexes.
- Save container logs on test failure.
- Separate fast unit tests from container-backed integration tests into appropriate tasks/groups.

If CI does not support Docker, use a separately managed Elasticsearch test service. In that setup, create isolated indexes/namespaces and ensure pipelines clean up data afterward.

## 20. Common Pitfalls When Testing Fragments and Repository Configuration

| Symptom | Possible cause | Resolution |
|---|---|---|
| Fragment implementation not found | Wrong class name or postfix | Check interface name + Impl and postfix configuration |
| Repository fragment method has no implementation | Fragment interface not extended | Add fragment interface to the repository |
| Implementation constructor not injected | Dependency is not a bean or template is missing | Check Spring context and Operations bean |
| Unit tests pass, real repository fails | Unit tests invoke implementation directly | Add tests calling through the repository proxy |
| Repository bean not created | Wrong basePackages or application scan package | Verify repository scanning |
| Two configurations create duplicate beans | Package scanned multiple times | Separate packages and configure scanning once |
| Repository targets wrong cluster | Wrong template reference or reliance on Primary | Bind explicit templates per repository group |
| Tests miss newly saved documents | Index not refreshed yet | Refresh the index before searching |
| Queries run but return empty results | Wrong mapping or analyzer | Inspect actual mappings and Query DSL |
| Testcontainers fails to start | Docker/port/memory issue or incompatible image | Check CI environment and pin a compatible image |
| Tests flaky under parallel runs | Multiple tests delete/share the same index | Use isolated indexes or serialize conflicting tests |
| Slice test missing fragment bean | Slice omits required configuration | Import fragment config or use SpringBootTest |
| Reactive tests hang | Calling block or failing to verify Publisher properly | Use StepVerifier and keep the pipeline reactive |
| Mocks pass, production fails TLS | Mocks bypass client configuration | Integration test with matching endpoint/auth config |

## 21. Complete Testing Scenario Example

A test suite for ProductRepository should validate both composition and behavior.

**Step 1: Start the Elasticsearch test node**

Use Testcontainers with a version matching your dependencies. Supply the container URI to the Spring Environment before clients are created.

**Step 2: Boot the Spring context**

Use SpringBootTest or DataElasticsearchTest as appropriate. Inject ProductRepository and ElasticsearchOperations.

**Step 3: Create the index and mapping**

Create the index from entity metadata or using application-managed index templates. Confirm the index is created at the right target.

**Step 4: Seed data**

Save at least one active product and one inactive product with deterministic IDs.

**Step 5: Refresh the index**

Refresh before searching so tests do not depend on the refresh interval.

**Step 6: Call the repository proxy**

Invoke repository.findActiveProducts() rather than instantiating the implementation directly. Confirm only active products are returned.

**Step 7: Verify CRUD and derived queries**

Invoke findById, save, and findByStatus to confirm standard Spring Data repository features work.

**Step 8: Clean up data**

Delete test-specific indexes or delete documents by ID. Never touch shared indexes outside the test environment.

Assertion example:

~~~java
@Test
void repositoryCombinesCrudDerivedQueryAndFragment() {
    List<Product> active =
        repository.findActiveProducts();

    assertThat(active)
        .extracting(Product::getId)
        .containsExactly("P-100");

    assertThat(repository.findByStatus("ACTIVE"))
        .extracting(Product::getId)
        .contains("P-100");
}
~~~

Exact results depend on seed data and sorting. If a method declares no sort, do not rely on return order.

## 22. Custom Repository Testing Checklist

- [ ] Each custom behavior group has a clear fragment interface.
- [ ] The main repository extends the right fragment interfaces.
- [ ] Implementation classes follow the naming postfix convention.
- [ ] Implementations lie within the discovery scope.
- [ ] Constructors inject the right Operations or ReactiveOperations.
- [ ] Repository scanning covers interface packages.
- [ ] Repositories use the intended template beans.
- [ ] No unintended duplicate package scanning exists.
- [ ] Unit tests verify fragment logic and dependency interactions.
- [ ] Integration tests invoke methods via the repository proxy.
- [ ] Elasticsearch container uses a pinned compatible version.
- [ ] Tests create mappings and indexes matching entities.
- [ ] Tests seed data, refresh, and verify results.
- [ ] Tests cover text, keyword, nested, and required mapping behaviors.
- [ ] Test isolation is safe under parallel runs.
- [ ] Multiple repository/template configurations are tested if using multiple clusters.
- [ ] Reactive fragments are verified using StepVerifier.
- [ ] CI has Docker/test service support and proper cleanup.
- [ ] Mocks are not used to mask wiring or connection errors in integration tests.

Testing fragments needs to confirm two things: the implementation behaves properly and Spring Data actually composes that implementation into the repository proxy under your application configuration. Unit tests with mocks check logic quickly; context tests confirm discovery and dependency injection; integration tests against real Elasticsearch validate mappings, queries, and real results. Combining all three testing levels catches package scanning mistakes, postfix mismatches, template wiring errors, and discrepancies between test setups and the real application.
