# Inspecting Tokens with the Analyze API

In Elasticsearch, text is converted into tokens before being stored in the inverted index or before being used to execute a full-text query. This process is controlled by an **analyzer**. A small change in a tokenizer or token filter can alter the generated tokens, directly affecting search results.

When a query does not return expected documents, do not immediately guess that data is missing or the query is written incorrectly. First, inspect what tokens the input text is analyzed into. Elasticsearch provides the **Analyze API** (`_analyze`) for that exact purpose. The API lets you test built-in analyzers, the analyzer bound to a field, or a combination of character filters, tokenizer, and token filters specified directly in the request.

This lesson explains how to use the Analyze API, how to read token output, how to inspect analyzers from mappings, how to test custom analyzers, and how to use analysis results to diagnose issues in Spring Data Elasticsearch.

## 1. Analyzers and tokens in Elasticsearch

An analyzer takes text and produces a stream of tokens. This token stream is the basis for Elasticsearch to index text or process query strings.

A typical analyzer has three parts in order:

1. **Character filters**: transform the character string before tokenization, such as stripping HTML or replacing a character pattern.
2. **Tokenizer**: splits the string into tokens, such as splitting words on word boundaries.
3. **Token filters**: transform, remove, or expand tokens, such as lowercasing, removing stop words, stemming, or applying synonyms.

```text
Input text
      |
      v
Character filters
      |
      v
Tokenizer
      |
      v
Token filters
      |
      v
Output token stream
```

For example, the text `The QUICK Brown Foxes!` passed through an English analyzer can be converted into lowercase tokens; a stop-word filter can remove `the`, and a stemmer can reduce `foxes` to the root `fox`. Actual output depends on the analyzer, language, and filter ordering.

A token is not just a character string. Elasticsearch/Lucene can also store attributes such as token position, offsets in the original text, token type, and position length. These attributes support phrase queries, highlighting, and token graph processing.

## 2. What is the Analyze API used for?

The Analyze API lets you send text to Elasticsearch and inspect the tokens generated by an analyzer. This API is useful when:

- Determining what rules a tokenizer uses to split text.
- Testing lowercase, stop-word, stemming, synonym, or asciifolding filters.
- Confirming the analyzer mapped to a field.
- Comparing the index-time analyzer and the analyzer intended for search time.
- Testing a custom analyzer before adding it to index settings.
- Diagnosing why a `match` or `match_phrase` query fails to match documents.
- Checking the impact of punctuation, casing, accented characters, HTML, or multilingual strings.

The Analyze API does not search documents and does not return a list of matching documents. It only analyzes the input string and returns tokens. Therefore, `_analyze` results verify one part of the search pipeline, but do not replace checking mappings, indexed data, and actual queries.

## 3. Basic Analyze API calls

The Analyze API can be invoked at the cluster level:

```http
POST _analyze
{
  "analyzer": "standard",
  "text": "The QUICK Brown-Foxes!"
}
```

`analyzer` specifies the analyzer name to use; `text` is the text to analyze. This example uses Elasticsearch's built-in `standard` analyzer.

A typical response looks like:

```json
{
  "tokens": [
    {
      "token": "the",
      "start_offset": 0,
      "end_offset": 3,
      "type": "<ALPHANUM>",
      "position": 0
    },
    {
      "token": "quick",
      "start_offset": 4,
      "end_offset": 9,
      "type": "<ALPHANUM>",
      "position": 1
    }
  ]
}
```

This illustrates the response structure; full output depends on the tokenizer and input text. A response may contain more tokens than shown above.

Attributes you typically inspect:

| Attribute | Meaning |
|---|---|
| `token` | The generated token text |
| `start_offset` | Start character offset of the token in the input text |
| `end_offset` | End character offset of the token in the input text |
| `type` | Token type assigned by the tokenizer |
| `position` | Position of the token in the token stream |
| `positionLength` | Position span of the token in a token graph, when provided |

Offsets link tokens back to substrings of the original text, such as for highlighting. Position indicates the order and relative distance between tokens, which is critical for phrase queries. With graph-based synonym filters, some tokens may share or span positions; do not look solely at the list of token strings and conclude the tokens are adjacent.

## 4. Inspecting the analyzer bound to a field

In real applications, fields may declare their own analyzers in the mapping. Instead of guessing an analyzer name or invoking a generic analyzer, use the `field` parameter to inspect the analyzer configured for that field.

Suppose the `articles` index has the mapping:

```http
PUT articles
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "standard"
      },
      "category": {
        "type": "keyword"
      }
    }
  }
}
```

Inspect the `title` field:

```http
POST articles/_analyze
{
  "field": "title",
  "text": "Spring Data Elasticsearch"
}
```

When using `field`, Elasticsearch looks up the field's mapping and uses the analyzer bound to that field. This verifies the index's actual configuration rather than only testing a known analyzer name.

If the field does not exist in the mapping or has no suitable analyzer, the request may return an error or fall back to default behavior according to API/version rules. Check the mapping before drawing conclusions.

Retrieve the current mapping with:

```http
GET articles/_mapping
```

This command confirms field types, analyzers, search analyzers, and multi-fields created in the live index.

### 4.1. Inspecting multi-fields

A property can be indexed under multiple types using multi-fields:

```http
PUT articles
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "standard",
        "fields": {
          "keyword": {
            "type": "keyword"
          }
        }
      }
    }
  }
}
```

You can inspect the main field:

```http
POST articles/_analyze
{
  "field": "title",
  "text": "Spring Data Elasticsearch"
}
```

And the subfield:

```http
POST articles/_analyze
{
  "field": "title.keyword",
  "text": "Spring Data Elasticsearch"
}
```

The `text` field `title` is analyzed into tokens. The `title.keyword` field keeps the entire value as a single term (possibly with a normalizer if configured). Compare both results to understand why full-text queries and exact queries behave differently.

## 5. Testing analyzers by explicit name

You can invoke built-in analyzers without creating an index:

```http
POST _analyze
{
  "analyzer": "whitespace",
  "text": "Spring-Data Elasticsearch"
}
```

The `whitespace` analyzer splits on whitespace; hyphens can remain inside tokens. Compare with `standard`:

```http
POST _analyze
{
  "analyzer": "standard",
  "text": "Spring-Data Elasticsearch"
}
```

The difference shows how the tokenizer decides token boundaries. Other built-in analyzers can include `simple`, `stop`, `keyword`, `pattern`, and language-specific analyzers. Not every analyzer suits every field; choose based on language and search requirements.

For example, the `keyword` analyzer treats the entire string as one token:

```http
POST _analyze
{
  "analyzer": "keyword",
  "text": "Spring Data Elasticsearch"
}
```

This illustrates the difference between a text field that needs word splitting and a string field needing whole-value matching.

## 6. Testing individual analyzer components

The Analyze API can accept `char_filter`, `tokenizer`, and `filter` individually. This is helpful when experimenting with an analyzer combination before writing it into index settings.

For example, stripping HTML, splitting with the `standard` tokenizer, then lowercasing and folding ASCII characters:

```http
POST _analyze
{
  "char_filter": ["html_strip"],
  "tokenizer": "standard",
  "filter": ["lowercase", "asciifolding"],
  "text": "<p>Café SPRING Data</p>"
}
```

This request defines an ad-hoc analysis pipeline directly in the request. It does not create or modify any analyzer stored in an index. It is a fast way to test components and processing order.

You can swap the tokenizer to observe the effect on word boundaries:

```http
POST _analyze
{
  "tokenizer": "whitespace",
  "filter": ["lowercase"],
  "text": "Spring-Data Elasticsearch"
}
```

Or test only token filters on top of the standard tokenizer:

```http
POST _analyze
{
  "tokenizer": "standard",
  "filter": ["lowercase", "stop"],
  "text": "The quick brown fox jumps over the lazy dog"
}
```

If a filter requires custom configuration, you need to declare that filter in index settings and reference it by name. Not every filter can be fully described solely by a built-in filter name.

## 7. Viewing step-by-step analysis details with `explain`

When you only receive the final token list, it can be hard to tell which component modified the text. The `explain: true` parameter asks Elasticsearch to return detailed step-by-step information across the analysis process.

```http
POST _analyze
{
  "analyzer": "standard",
  "text": "The QUICK Brown-Foxes!",
  "explain": true
}
```

The response with `explain` enabled has a more detailed structure than a regular response. It can show:

- Output after each character filter.
- The tokenizer and tokens generated by the tokenizer.
- Output after each token filter.
- Token attributes at each stage.

To focus on specific token attributes, you can pass `attributes` alongside `explain`:

```http
POST _analyze
{
  "analyzer": "standard",
  "text": "Spring Data Elasticsearch",
  "explain": true,
  "attributes": ["keyword", "positionLength"]
}
```

`attributes` requests adding supported token attributes to the explanation. Specific attributes may depend on the tokenizer/filters and Elasticsearch version. When analyzing synonym graphs or phrase queries, pay attention to token positions and position length rather than checking only token text.

`explain` can produce a significantly larger response than regular mode. Use it on short test strings and disable it when detailed inspection is unnecessary.

## 8. Creating and testing a custom analyzer

In real applications, analyzers are usually defined in index settings so mappings can reference them by name. Example creating the `product_text` analyzer:

```http
PUT products
{
  "settings": {
    "analysis": {
      "char_filter": {
        "replace_ampersand": {
          "type": "mapping",
          "mappings": [
            "& => and"
          ]
        }
      },
      "analyzer": {
        "product_text": {
          "type": "custom",
          "char_filter": ["html_strip", "replace_ampersand"],
          "tokenizer": "standard",
          "filter": ["lowercase", "asciifolding"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "analyzer": "product_text"
      }
    }
  }
}
```

After creating the index, test the analyzer by field name:

```http
POST products/_analyze
{
  "field": "name",
  "text": "Café & Tea"
}
```

Or invoke the analyzer by name:

```http
POST products/_analyze
{
  "analyzer": "product_text",
  "text": "Café & Tea"
}
```

The two approaches serve slightly different purposes. `field` tests the analyzer attached to the field's mapping; `analyzer` tests the analyzer invoked directly by name. If the two configurations differ, the output can differ.

### 8.1. Testing an analyzer before saving it to an index

If you do not want to create an index yet, you can describe components inline in the `_analyze` request. However, once the analyzer is placed into settings, re-test using the index endpoint because that is the live configuration the mapping will use.

Inline testing is convenient for comparing tokenizers/filters, but does not replace verifying index settings after deployment. An analyzer may depend on custom filters, synonym sets, plugins, or configurations that only exist on the cluster.

### 8.2. Analyzers and normalizers

An analyzer can produce multiple tokens from one string. A normalizer is for `keyword` fields, normalizing the value while keeping it as a single token. When inspecting a `keyword` field, check the normalizer declared in the mapping.

Example mapping:

```http
PUT customers
{
  "settings": {
    "analysis": {
      "normalizer": {
        "lowercase_normalizer": {
          "type": "custom",
          "filter": ["lowercase", "asciifolding"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "emailLabel": {
        "type": "keyword",
        "normalizer": "lowercase_normalizer"
      }
    }
  }
}
```

You can inspect field normalization using the Analyze API with `field`:

```http
POST customers/_analyze
{
  "field": "emailLabel",
  "text": "USER@EXAMPLE.COM"
}
```

When using a normalizer, the result remains a single token. Do not use a normalizer if the business requirement is to split strings into multiple words for full-text search.

## 9. Inspecting index-time and search-time analyzers

Elasticsearch can use different analyzers at the two stages:

- **Index-time analyzer** is used when indexing field values.
- **Search-time analyzer** is used when analyzing query strings for that field.

A mapping can declare both `analyzer` and `search_analyzer`:

```http
PUT articles
{
  "settings": {
    "analysis": {
      "analyzer": {
        "title_index": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase", "asciifolding"]
        },
        "title_search": {
          "type": "custom",
          "tokenizer": "standard",
          "filter": ["lowercase"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "title_index",
        "search_analyzer": "title_search"
      }
    }
  }
}
```

Inspect how the field is analyzed:

```http
POST articles/_analyze
{
  "field": "title",
  "text": "Café Spring"
}
```

To test a specific named analyzer from settings, specify its name:

```http
POST articles/_analyze
{
  "analyzer": "title_index",
  "text": "Café Spring"
}
```

```http
POST articles/_analyze
{
  "analyzer": "title_search",
  "text": "Café Spring"
}
```

Compare both token sequences to confirm whether normalization differs as intended. The `field` parameter is useful for inspecting the analyzer bound to the mapping; calling `analyzer` by name is useful for testing each configuration explicitly. When investigating an actual query, also check the query type and the search analyzer that query uses.

Do not change analyzers arbitrarily. If the index-time analyzer changes, already-indexed documents keep old tokens until reindexed. Typically you need to create a new index with the new settings/mapping, run a reindex, and switch the alias or application to the new index.

## 10. Using the Analyze API to diagnose search results

Suppose an application searches titles with `match`:

```http
GET articles/_search
{
  "query": {
    "match": {
      "title": "Spring Data"
    }
  }
}
```

If results do not match expectations, investigate in sequence:

1. Fetch the mapping of the `title` field to inspect field type, analyzer, and search analyzer.
2. Call `_analyze` with `field: "title"` to check tokens under the field configuration.
3. Call `_analyze` with the index-time and search-time analyzer names to compare both pipelines.
4. Check `_source` of documents to confirm the actual stored original values.
5. Check whether documents were indexed after the analyzer change.
6. Check query type: `match`, `match_phrase`, `term`, and other queries have different semantics.
7. Re-run the real query after confirming input tokens and indexed tokens are compatible.

### 10.1. Casing scenarios

If the analyzer uses `lowercase`, `Spring`, `SPRING`, and `spring` can all produce the same token `spring`. If the field is a `keyword` without a normalizer, the whole string may be preserved and remain case-sensitive.

The Analyze API lets you confirm this before altering queries or normalizing data in the application.

### 10.2. Diacritics and Unicode characters

`asciifolding` can convert certain accented characters to ASCII equivalents. For example, `café` can produce the token `cafe` if the filter is configured. Do not assume this filter handles every linguistic rule or every Unicode form. Test with real data, including accented letters, combining marks, and non-Latin characters.

### 10.3. Stop words and stemming

A stop filter can remove common words. A stemmer can reduce multiple word variants to a root form. These transformations can alter token positions and phrase matching. Use `explain: true` to see which filter removed or transformed tokens.

Do not remove stop words just to reduce token counts without considering phrase search needs. Some short words remain crucial in proper nouns, codes, or domain queries.

### 10.4. Synonym scenarios

A synonym filter can expand a token into synonymous variants or replace a token with a group of tokens. With a synonym graph, a single token can create multiple paths in the token graph. This affects phrase queries and query builders.

When inspecting synonyms, use the Analyze API with `explain: true` and examine token positions. If you look only at `token` while ignoring `position` or `positionLength`, you can misinterpret the path structure produced by the analyzer.

## 11. Vietnamese and analyzer selection

In Vietnamese, spaces typically separate syllables, yet a meaningful word can consist of multiple syllables. The `standard` analyzer generally processes boundaries supported by the tokenizer; it does not automatically perform dictionary-based Vietnamese word segmentation.

For example, the phrase `cơ chế tìm kiếm` may be split into tokens corresponding to the syllables `cơ`, `chế`, `tìm`, `kiếm`. If business requirements need to recognize `cơ chế` or `tìm kiếm` as lexical units, relying solely on a standard analyzer may fall short.

The Analyze API is very helpful for inspecting this:

```http
POST _analyze
{
  "analyzer": "standard",
  "text": "Cơ chế tìm kiếm văn bản"
}
```

Then compare with the Vietnamese analyzer or pipeline selected by your organization. If using a Vietnamese analysis plugin, install a compatible plugin on all relevant nodes in the cluster, restart nodes per guidelines, and verify output tokens after installation.

There is no single analyzer suited to every Vietnamese dataset. Build a sample query suite from how users actually search, evaluate precision/recall, and test with proper nouns, punctuation, compound words, abbreviations, and loanwords.

## 12. Integrating analyzer checks into the Spring Data Elasticsearch development workflow

In a Spring Data Elasticsearch application, analyzers are configured in index settings and mappings. Entities can declare analyzers using the `@Field` annotation, but custom analyzers must exist in the index settings before the index is created.

Example entity:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "articles")
public class Article {

    @Id
    private String id;

    @Field(type = FieldType.Text, analyzer = "title_index")
    private String title;

    // Constructors, getters and setters
}
```

The name `title_index` must be declared in the index's analysis settings. The `@Field` annotation describes field metadata; it does not define custom tokenizers and filters on its own.

A useful development workflow:

1. Identify the language, data type, and search requirements for the field.
2. Design the analyzer in index settings.
3. Call `_analyze` directly with the analyzer or field to inspect tokens.
4. Test with representative texts and edge cases.
5. Create the index with the chosen settings/mapping.
6. Index some sample documents.
7. Run real queries and evaluate results.
8. Only after results meet expectations, apply the configuration to large datasets.

Once an analyzer has been used for indexing, changing it may require reindexing. Therefore, incorporate settings/mappings into index versioning and migration workflows.

## 13. Limitations of the Analyze API

The Analyze API answers the question "what tokens does this analyzer turn this text into?" It does not fully answer the following questions:

- Whether a specific document exists in the index.
- Whether a document has been refreshed and made searchable.
- How a query combines tokens with AND, OR, phrase, or bool clauses.
- What relevance score a document receives.
- Whether a field is constrained by routing, alias filters, security, or query filters.
- Whether a token is actually stored in the inverted index of a previously indexed document.

For a complete investigation, combine the Analyze API with `_mapping`, `_settings`, reading documents via `_source`, and running real queries. For scoring or query execution issues, you may also need the Search API's `explain` or the Profile API; these are different APIs from the Analyze API's `explain`.

The Analyze API also consumes cluster resources. Avoid sending massive texts or calling it repeatedly in every user request as a normal search step. Use it primarily for development, testing, and diagnostics; if an application needs runtime text analysis, consider suitable analyzers/queries and limit input size.

## 14. Common errors when using the Analyze API

### Analyzer not found

If a custom analyzer has not been declared in index settings or its name is misspelled, Elasticsearch may return an analyzer-not-found error. Check `_settings` and ensure the analyzer is created before the mapping references it.

### Field does not exist or mapping differs from expectations

When using the `field` parameter, the field name must match the live mapping, including multi-field names like `title.keyword`. Use `GET index/_mapping` to confirm.

### `_analyze` output differs from search results

You may be testing a different analyzer from the one the query actually uses; index-time and search-time analyzers can differ. Inspect the mapping and query, then specify analyzers by name to compare.

### Changing the analyzer still leaves old documents unmatched

Old documents were indexed using tokens from the analyzer active at write time. Changing mappings or settings does not rebuild the inverted index. You need to reindex data into a new index if index-time analysis changes.

### Looking only at token text and ignoring positions

Phrase queries and synonym graphs depend on positions/position length. Enable `explain` and inspect token attributes when diagnosing phrases or synonyms.

### Using a generic analyzer for multilingual data

A single analyzer may handle certain languages or content types poorly. Create appropriate fields/analyzers, test representative data, and evaluate result quality rather than assuming one configuration works well for all content.

## 15. Quick verification workflow

When you need to inspect tokens for a field, follow these steps:

1. View the mapping with `GET index/_mapping`.
2. Call `POST index/_analyze` with `field` and sample text.
3. Inspect `token`, `position`, `start_offset`, `end_offset`, and `type`.
4. Enable `explain: true` if you need to see the effect of each character filter, tokenizer, or token filter.
5. Invoke analyzers by name using `analyzer` to compare configurations.
6. Check real queries and indexed documents if tokens look right but results remain wrong.

The Analyze API is the most direct and accessible tool for observing Elasticsearch's text analysis step. By understanding output tokens, positions, and accompanying attributes, developers can design suitable analyzers, explain `match`/`match_phrase` behavior, and catch discrepancies between index-time and search-time configurations early in Spring Data Elasticsearch applications.
