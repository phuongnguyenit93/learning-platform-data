# Choosing Application-Provided IDs vs. Elasticsearch-Generated IDs

Every document in Elasticsearch has an `_id` identifier scoped to an index. When saving a document via Spring Data Elasticsearch, the application can either provide the ID itself before writing or let Elasticsearch generate an ID upon receiving the request. Both options are valid, but they affect retry safety, duplicate prevention, data linking, and how the application references documents differently.

In Spring Data Elasticsearch, the property marked with `@Id` maps to the document's `_id` metadata. If the property already has a value, Spring Data uses that value as the ID. If no ID is supplied, the index operation can let Elasticsearch generate a new ID; the application then needs to retrieve the ID from the save result for future reads, updates, or deletes.

```text
Application creates entity
        |
        v
    Has @Id value?
       /     \
     Yes      No
      |        |
      v        v
 Use app ID   Send request without ID
      |        |
      |        v
      |    Elasticsearch generates _id
      |        |
      +--------+
           |
           v
     Save document
           |
           v
    Receive saved ID
```

## 1. What Is `_id`?

`_id` is the document identifier managed by Elasticsearch within an index. It is used to fetch, update, or delete a document directly by ID. For example, a document might be returned as follows:

```json
{
  "_index": "products",
  "_id": "P-100",
  "_version": 1,
  "_source": {
    "sku": "SKU-100",
    "name": "Mechanical Keyboard"
  }
}
```

In this example:

- `_index` is the physical index where the document is stored.
- `_id` is the document identifier within that index.
- `_source` is the JSON content of the document.
- `_version` is version metadata managed by Elasticsearch.

`_id` is metadata, not an ordinary field inside `_source`. If the application needs to search, filter, sort, or aggregate on a business code, store that code as a separate field, such as `sku`, alongside `@Id`.

IDs are unique within the scope of a single index. If an alias points to multiple indices, the same `_id` value can appear across multiple indices. Therefore, `_id` should not be treated as a unique key across the entire cluster or across an entire alias.

## 2. Declaring an ID in Spring Data Elasticsearch

Spring Data uses the `@Id` annotation to designate the property used as the document ID:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "products")
public class ProductDocument {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String sku;

    @Field(type = FieldType.Text)
    private String name;

    // constructors, getters, setters
}
```

The `id` property is used as `_id`. The `sku` and `name` properties are fields inside `_source` according to their respective mappings.

For example, if an entity has `id = "P-100"`, the document is written with `_id` equal to `P-100`. If `id` is `null` and the operation is executed via Spring Data Elasticsearch using a mechanism that supports auto-generated IDs, Elasticsearch can generate a new ID.

Usually `String` should be used for the ID property because Elasticsearch represents `_id` as a string. An application can also use another identifier type if the Spring Data version's converter supports it, though you should verify the conversion and the actual value sent to the cluster.

## 3. Option 1: Application-Provided ID

When the application provides the ID, the value is already known before sending the request to Elasticsearch. The ID can be:

- A stable business code, such as `orderId`, `customerCode`, or `sku`.
- A UUID/ULID generated by the application.
- A composite ID formed from the tenant and entity identifier.
- Another identifier created by the source system.

### Using a Business Code as the ID

If each product has a unique SKU that does not change over the product's lifecycle, the SKU can be used as `_id`:

```java
ProductDocument product = new ProductDocument();
product.setId("SKU-100");
product.setSku("SKU-100");
product.setName("Mechanical Keyboard");

ProductDocument saved = productRepository.save(product);
```

The document gets `_id = "SKU-100"`. The next time the application saves another entity with the same ID, a normal index operation writes to that same document.

This works well if the business identifier is genuinely stable and unique within the index. Do not use a product name, email, or mutable attribute as the ID if changing its value would prevent the application from finding the document under its old ID.

### Using an Application-Generated UUID

If there is no suitable business key, the application can generate a UUID before saving:

```java
import java.util.UUID;

ProductDocument product = new ProductDocument();
product.setId(UUID.randomUUID().toString());
product.setSku("SKU-100");
product.setName("Mechanical Keyboard");

ProductDocument saved = productRepository.save(product);
```

The ID is known before the request is sent, so the application can log it, persist it in the source system, or send it to another component right away.

Random UUIDs have an extremely low collision probability, but every call to `UUID.randomUUID()` produces a new value. If a write request times out and the application generates a new UUID to retry, the retry can create a second document. For safe retries, generate the ID once at the business boundary, then persist and reuse that same ID across all attempts for the same operation.

### Using Composite IDs for Multi-Tenant Data

If multiple tenants store entities with local IDs like `42`, you can construct a composite ID:

```java
String documentId = tenantId + ":" + orderId;
```

For example, `tenant-7:42` and `tenant-9:42` become two distinct IDs in the same index. You can apply encoding or a stable hash if ID components contain unsuitable characters or are too long. Choose a consistent rule and apply the exact same rule across writes, reads, updates, and deletes.

## 4. Option 2: Letting Elasticsearch Generate the ID

Elasticsearch can generate an ID automatically when it receives an index operation without a specified `_id`. In the REST API, the common approach is `POST /<index>/_doc`:

```http
POST /products/_doc
Content-Type: application/json

{
  "sku": "SKU-200",
  "name": "Wireless Mouse"
}
```

A successful response contains the generated ID:

```json
{
  "_index": "products",
  "_id": "generated-id-from-elasticsearch",
  "_version": 1,
  "result": "created"
}
```

The `_id` value in the example is only illustrative; the application must capture the real value from the response. In the REST API, an endpoint with an ID such as `PUT /products/_doc/P-200` uses the client-specified ID. Endpoints `PUT /products/_create/P-200` or `PUT /products/_doc/P-200?op_type=create` require creation only and return a conflict if the ID already exists.

### Letting Spring Data Elasticsearch Generate the ID

For an entity with an `@Id` property, you can leave the ID as `null` when creating the entity:

```java
ProductDocument product = new ProductDocument();
product.setId(null);
product.setSku("SKU-200");
product.setName("Wireless Mouse");

ProductDocument saved = productRepository.save(product);
String generatedId = saved.getId();
```

In Spring Data Elasticsearch, the save operation returns the saved entity, which can be populated with the ID returned by Elasticsearch. Always use the entity returned by `save`, especially with immutable entities or records, rather than assuming the input object is always mutated in place. Write an integration test against your project's exact Spring Data and Elasticsearch versions to verify the auto-generated ID behavior of your configuration.

If the application calls the Elasticsearch Java API Client directly, the index response has an `id` field:

```java
IndexResponse response = client.index(request -> request
        .index("products")
        .document(productPayload)
);

String generatedId = response.id();
```

In this example the request does not call `.id(...)`, so Elasticsearch generates the ID. The application must store `generatedId` if it needs to reference the document later.

## 5. Comparing the Two ID Approaches

| Criterion | Application-provided ID | Elasticsearch-generated ID |
|---|---|---|
| When ID is known | Known before sending the request. | Known only after receiving a successful response. |
| Retry after timeout | Can re-write to the same ID to avoid creating a second document. | Resending a request without an ID can create a new document. |
| Idempotency | Easy to design if the ID is generated once and reused. | Not inherently idempotent if every retry creates a new ID. |
| Referencing from other systems | Can pass the ID before writing. | Must wait for the response and store the generated ID. |
| Fit with business keys | Can use stable business keys directly. | Independent of business keys. |
| Duplicate write risk | Same ID writes to the same document; must understand overwrite/create semantics. | Each creation typically gets a different ID, so retries can produce duplicates. |
| Complexity | Application is responsible for generating, managing, and avoiding ID collisions. | Elasticsearch handles ID generation; application manages the ID after receipt. |

There is no single right choice for every system. Decide based on requirements for uniqueness, retries, data linking, and traceability.

## 6. `save` Is Upsert by ID, Not Insert-Only by Default

An important point when using application-provided IDs is understanding the behavior of the save operation. Spring Data Elasticsearch's repository `save(entity)` typically performs an index operation by ID. If the ID does not exist yet, the document is created; if the ID already exists, the document content is overwritten according to index operation semantics.

Example:

```java
ProductDocument first = new ProductDocument();
first.setId("SKU-100");
first.setSku("SKU-100");
first.setName("Keyboard");
productRepository.save(first);

ProductDocument second = new ProductDocument();
second.setId("SKU-100");
second.setSku("SKU-100");
second.setName("Keyboard Pro");
productRepository.save(second);
```

The second save writes to the document with the same `_id`; as a result, the current content carries the name `Keyboard Pro`. This behavior is useful for updates by ID, but unsuitable if business rules require rejecting all duplicate writes.

### When Create-Only Is Needed

If you must guarantee the ID does not already exist, use a create-only operation. REST API example:

```http
PUT /products/_create/SKU-100
Content-Type: application/json

{
  "sku": "SKU-100",
  "name": "Keyboard"
}
```

If the ID already exists, Elasticsearch returns HTTP `409 Conflict`. You can use `op_type=create` with the corresponding Index API. When using the Java API Client, you can configure the operation type to `create` on the index request.

Repository `save` should not be assumed to be an insert-only operation. When create-only semantics are needed, use an API supporting `op_type` `create` or a specific abstraction in your Spring Data version, and handle conflicts explicitly.

## 7. IDs and Safe Retries

A common scenario: the application sends a write request, Elasticsearch writes successfully, but the response is lost due to a network timeout. The application cannot be sure whether the operation succeeded.

### With Elasticsearch-Generated IDs

```text
Application              Elasticsearch
    |                           |
    | POST /products/_doc       |
    |-------------------------->| creates document ID=A
    |                           |
    |       response lost       |
    |< - - - - - - - - - - - - X
    |
    | retry POST without ID     |
    |-------------------------->| creates document ID=B
    |<--------------------------| returns ID=B
```

Two documents can end up representing the same business event. Elasticsearch cannot know on its own that the second request is a retry of the first because neither shares an ID or idempotency key.

### With Application-Provided and Reused IDs

```text
Application              Elasticsearch
    |                           |
    | PUT /products/_doc/P-100  |
    |-------------------------->| creates/updates P-100
    |                           |
    |       response lost       |
    |< - - - - - - - - - - - - X
    |
    | retry same ID P-100       |
    |-------------------------->| re-writes P-100
    |<--------------------------| returns result for P-100
```

Retrying with the same ID avoids creating another document with a different ID. However, if a normal index operation is used, the retry still re-writes the entire document. If the retry payload is older than a newer update, it can overwrite the newer data. For concurrently updated data, versioning or optimistic concurrency control is also needed.

### Ways to Design Idempotency

- Derive a stable ID from a business key or idempotency key.
- Generate a UUID once before the first write, store it in the source system, and reuse it on retries.
- Use create-only when a second request should receive a conflict if the document already exists.
- Store event processing state in the source system/outbox so consumers can replay with the same identifier.
- For ordered updates, store the source version and verify the version before writing.

Simply using random UUIDs does not ensure idempotency if the application generates a fresh UUID on every retry.

## 8. IDs, Concurrent Updates, and Optimistic Concurrency

An ID identifies the target document; it does not resolve conflicts when multiple requests modify that document concurrently. If two requests write to the same `_id`, the later operation can overwrite the earlier one under standard semantics.

Elasticsearch supports optimistic concurrency control using `_seq_no` and `_primary_term`. The application reads the document, retains these two metadata values, and sends them back when updating. If the document has changed since the read, the conditional operation is rejected so the application can handle the conflict.

Example request:

```http
PUT /products/_doc/P-100?if_seq_no=12&if_primary_term=3
Content-Type: application/json

{
  "sku": "SKU-100",
  "name": "Keyboard Pro"
}
```

The sequence number and primary term values here are only examples; the application must obtain them from the previous read response. On conflict, re-read the document and decide whether to recompute the change, retry with a limit, or return an error to the business layer.

An application-provided ID provides a stable target, whereas optimistic concurrency protects updates from overwriting newer changes. The two mechanisms solve different problems.

## 9. IDs Do Not Replace Business Fields

`_id` can be used to fetch a document directly or query via an IDs query, but it is not an ordinary field for aggregations, sorting, or analysis like `keyword`. If the application needs to query by SKU, email, or customer code, store that value as a separate field:

```java
@Document(indexName = "customers")
public class CustomerDocument {

    @Id
    private String id;

    @Field(name = "customer_code", type = FieldType.Keyword)
    private String customerCode;

    @Field(type = FieldType.Keyword)
    private String email;
}
```

You can use `customerCode` as `_id` if it is a stable key while also storing `customer_code` to support queries/aggregations. Duplicating the ID into `_source` is a data modeling choice; Spring Data does not automatically turn `_id` metadata into an ordinary searchable field.

Avoid using sensitive personal data such as email addresses or phone numbers as `_id` when unnecessary. IDs frequently appear in logs, URLs, or traces; using an opaque identifier like a UUID or internal code limits data exposure and allows changing personal details without changing the document identifier.

Elasticsearch enforces a length limit on `_id` (up to 512 bytes in modern versions). Do not stuff full JSON payloads, long user names, or unbounded concatenated strings into an ID. If a composite ID is needed, bound its length and use a stable hash when appropriate.

## 10. Choosing an ID in Common Scenarios

| Scenario | Recommended choice | Reason |
|---|---|---|
| Syncing products from a database with a stable primary key | Use the source key or a stably mapped ID. | Repeated reindexing/syncing targets the same document. |
| Orders with a unique `orderId` | Use `orderId` as the ID if the uniqueness scope fits. | Easy to reference and retry for the same order. |
| Fast log/event writes with no source key | Let Elasticsearch generate the ID. | No need to construct business IDs if back-referencing is unnecessary. |
| Events that must prevent duplicates on consumer retry | Use a stable event ID/idempotency key from the source. | The same event always targets the same document. |
| Internal documents without a natural identifier | Generate a UUID/ULID in the application. | The application knows the ID before writing and can reuse it. |
| Multi-tenant data with local IDs that may collide | Use a composite ID with tenant namespace or a global key. | Prevents overwriting another tenant's document in the same index. |
| One alias reading multiple historical indices | Design IDs and queries with index awareness; do not assume `_id` is unique across the alias. | IDs are unique only within each index. |
| Must reject records whose ID already exists | Use a create-only operation. | Standard `save` has index/upsert semantics. |

## 11. Integrating with Spring Data Repositories

A simple repository:

```java
public interface ProductRepository
        extends ElasticsearchRepository<ProductDocument, String> {
}
```

With an application-provided ID:

```java
public ProductDocument createProduct(String sku, String name) {
    ProductDocument document = new ProductDocument();
    document.setId(sku);
    document.setSku(sku);
    document.setName(name);

    return productRepository.save(document);
}
```

With an Elasticsearch-generated ID:

```java
public ProductDocument createProduct(String sku, String name) {
    ProductDocument document = new ProductDocument();
    document.setId(null);
    document.setSku(sku);
    document.setName(name);

    ProductDocument saved = productRepository.save(document);
    return saved;
}
```

In the second case, the caller must retain `saved.getId()` if it wants to read, update, or delete the document later. In an API service, you can return the ID in the response or save it in the business database. If the ID only lives on a temporary object and is discarded, the application will have difficulty referencing the created document.

### Using ElasticsearchOperations

`ElasticsearchOperations` provides a lower-level document API than repositories while preserving Spring Data's mapping and converters:

```java
@Service
public class ProductDocumentService {

    private final ElasticsearchOperations operations;

    public ProductDocumentService(ElasticsearchOperations operations) {
        this.operations = operations;
    }

    public ProductDocument save(ProductDocument document) {
        return operations.save(document);
    }
}
```

The returned result is the saved entity; use it to obtain the populated ID if the server generates it. If you need create-only semantics, custom routing, concurrency conditions, or specialized Index API parameters, use the corresponding API provided by your Spring Data version or call the Elasticsearch Java API Client directly.

### Using the Java API Client When Request Control Is Needed

Example specifying an application-provided ID:

```java
IndexResponse response = client.index(request -> request
        .index("products")
        .id("P-100")
        .document(productPayload)
);
```

Example letting Elasticsearch generate the ID:

```java
IndexResponse response = client.index(request -> request
        .index("products")
        .document(productPayload)
);

String id = response.id();
```

If using the Java API Client directly, the application is responsible for payload conversion, index/alias selection, response handling, and retaining the ID. Do not create a new client for every operation; inject the client managed by Spring Boot.

## 12. Points to Test

The ID strategy affects critical flows, so integration tests should verify:

1. When an ID is provided, the document is written to that exact `_id`.
2. When the ID is `null`, an operation supporting auto-generated IDs returns a non-blank ID.
3. The entity returned from `save` has an ID usable for `findById` and `deleteById`.
4. Saving the same ID again behaves with overwrite/upsert semantics as designed.
5. Create-only with an existing ID returns a conflict and does not overwrite the old document.
6. Retrying with the same ID does not create another document ID.
7. Retrying with auto-generated IDs can create another record if the application does not use an idempotency key.
8. When an alias points to multiple indices, verify uniqueness scope and query behavior match the design.

Conceptual test example for auto-generated ID behavior:

```java
@Test
void saveWithoutIdShouldReturnGeneratedId() {
    ProductDocument draft = new ProductDocument();
    draft.setId(null);
    draft.setSku("SKU-200");
    draft.setName("Wireless Mouse");

    ProductDocument saved = productRepository.save(draft);

    assertThat(saved.getId()).isNotBlank();
    assertThat(productRepository.findById(saved.getId())).isPresent();
}
```

This is an illustrative example; Elasticsearch integration testing and mappings/indices must be configured before running. If using immutable entities or records, inspect the entity returned by the repository rather than the original draft object.

## 13. Common Errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| Every retry creates a new document | Elasticsearch generates a new ID on each request. | Generate a stable ID or idempotency key in the application and reuse it on retries. |
| Saving a new document overwrites an old one | Both entities share the same `_id` and `save` uses index/upsert semantics. | Check ID generation rules; use create-only if duplicates must be rejected. |
| Cannot read the document after saving | The application did not store the ID returned by Elasticsearch or used the wrong index/alias. | Use the entity returned by `save` and persist `getId()`. |
| Querying/aggregating by `_id` does not work | `_id` is metadata, not an ordinary aggregation field. | Store business IDs in a separate `keyword` field. |
| Two tenants overwrite each other's data | Using the same local ID in the same index. | Prefix IDs with a tenant namespace or generate global keys. |
| Alias read returns duplicate IDs | The same `_id` exists across multiple indices pointed to by the alias. | Review index/alias and identifier strategy, or restrict the queried index. |
| Changing an email prevents finding the document by ID | A mutable email was used as `_id`. | Use a stable ID; store email in a separate field. |
| Input entity still has a null ID after save | Code reads the input object instead of the returned entity, or behavior differs by version/entity type. | Use the returned value and verify with an integration test. |

## 14. Decision Process

Before choosing how IDs are assigned, determine:

1. Does the document have a stable business key?
2. Do other systems need to know the ID before the write occurs?
3. Can requests be retried after timeouts or replayed from a queue?
4. Should retries update the same document or create a new event?
5. Is there a requirement to reject duplicate documents rather than overwriting them?
6. Is the ID unique within an index, a tenant, or the entire system?
7. Do you need to search, sort, or aggregate by the business code?
8. Will the application store the ID generated by Elasticsearch?

If you need safe retries or cross-system data linking, a stable application-provided ID is usually easier to control. If documents are independent, the ID does not need to be known before writing, and duplicates are handled elsewhere, Elasticsearch's auto-generated IDs can be simpler.

## 15. Key Takeaways

- `@Id` maps a Java property to the document's `_id` metadata.
- Application-provided IDs can be stable business keys, UUIDs/ULIDs, or composite IDs.
- When no ID is provided, Elasticsearch can generate one; retrieve the ID from the returned entity or client response.
- Use stable IDs and reuse them on retries to avoid creating a second document for the same operation.
- Generating a new UUID per retry can still create duplicate records; UUIDs only aid idempotency when generated once and persisted.
- `save` typically has index/upsert semantics by ID; it is not insert-only by default.
- Use a create-only operation when existing IDs must be rejected.
- `_id` is unique within each index, not guaranteed unique across an alias pointing to multiple indices.
- Store business codes in separate fields if you need filtering, sorting, or aggregations; `_id` does not replace a `keyword` field.
- ID strategy and optimistic concurrency are separate concerns: one identifies the document, the other protects concurrent updates.

Choosing the right ID strategy enables Spring Data Elasticsearch to handle inserts, updates, and retries according to business requirements. Decide based on identifier stability, referencing needs, and failure recovery, then verify the behavior with integration tests against the exact Spring Data Elasticsearch version and cluster you deploy.
