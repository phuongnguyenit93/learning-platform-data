# `save` and Create-or-Replace Behavior by ID

In Spring Data Elasticsearch, `save()` is the operation for writing a document into Elasticsearch. The outcome depends primarily on the document's identifier (`_id`): if the ID does not yet exist in the index, Elasticsearch creates a new document; if the ID already exists, the index operation replaces the old document content with the new content. Therefore, `save()` is well suited for writing a complete and consistent document state by ID.

An important point to understand is that `save()` does not work like a field-by-field merge the way many people picture `save()` in a relational ORM. When you need to change only a few fields and keep the remaining fields intact, use a partial update operation. When you need to prevent an older record from overwriting a newer one, design an optimistic locking or version control mechanism.

## 1. `save()` in Spring Data Elasticsearch

Spring Data Elasticsearch provides repositories for working with documents. A repository typically extends `ElasticsearchRepository<T, ID>`:

```java
import org.springframework.data.elasticsearch.repository.ElasticsearchRepository;

public interface ProductRepository
        extends ElasticsearchRepository<ProductDocument, String> {
}
```

The document class declares the index and ID:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "products")
public class ProductDocument {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String name;

    @Field(type = FieldType.Keyword)
    private String sku;

    @Field(type = FieldType.Long)
    private Long priceMinorUnits;

    @Field(type = FieldType.Boolean)
    private Boolean available;

    // Constructors, getters and setters
}
```

Saving a document:

```java
ProductDocument product = new ProductDocument();
product.setId("p-1001");
product.setName("Coffee Maker");
product.setSku("COFFEE-001");
product.setPriceMinorUnits(3250000L);
product.setAvailable(true);

ProductDocument saved = productRepository.save(product);
```

`@Id` maps the Java property to the Elasticsearch document ID (`_id`). With `@Document(indexName = "products")`, the save operation targets the `products` index or the logical name configured there, such as an alias.

`save()` returns the saved entity. Always keep the returned result, especially when the ID is auto-generated by Elasticsearch or when the entity has version information updated during the write.

## 2. Create-or-Replace Rules by ID

At the Elasticsearch layer, indexing a document by ID has two fundamental outcomes:

| State before write | Result of `save()`/indexing by ID |
|---|---|
| No document with that ID exists in the target index | Creates a new document |
| A document with that ID already exists in the target index | Replaces the document's source with the new source |

For example, the index currently has the document:

```json
{
  "_id": "p-1001",
  "name": "Coffee Maker",
  "sku": "COFFEE-001",
  "priceMinorUnits": 3250000,
  "available": true,
  "description": "Home coffee maker"
}
```

Then the application saves a document with the same ID but a new source:

```json
{
  "name": "Coffee Maker New Edition",
  "sku": "COFFEE-001",
  "priceMinorUnits": 3490000,
  "available": true
}
```

After the write, the document will have the new source. The `description` field that is absent from the new source will no longer exist in the replaced document. This is why you must send a complete object when using `save()` to replace a document.

### IDs Are Scoped to an Index

An ID is not a cluster-wide unique key. The same `_id` can appear in two different physical indices. For instance, `p-1001` in `products-v1` and `p-1001` in `products-v2` are two separate documents. If the application writes through an alias or multiple indices, you must understand which index the alias routes to in order to avoid reading or writing the wrong generation.

## 3. Application-Provided ID or Auto-Generated ID?

There are two common ways to determine a document ID.

### Using a Stable Application-Provided ID

For business data with a stable identifier, assign the ID before calling `save()`:

```java
ProductDocument product = new ProductDocument();
product.setId("product-1001");
product.setName("Mechanical Keyboard");

ProductDocument saved = productRepository.save(product);
```

Subsequent saves with the same ID and the same index will target the same document. This is useful when syncing data from a transactional database, replaying messages, or retrying after a network error.

### Letting Elasticsearch Generate the ID

If the ID is left blank, Elasticsearch can generate an ID for the document during the index operation. Spring Data returns the saved entity with the identifier assigned according to the mechanism of the version in use.

```java
ProductDocument product = new ProductDocument();
product.setName("Wireless Mouse");

ProductDocument saved = productRepository.save(product);
String generatedId = saved.getId();
```

When using auto-generated IDs, keep the saved entity or retrieve the ID from the returned result. If every `save()` call sends a new object with an empty ID, Elasticsearch may create a new document with a different ID, leading to business-level duplicate records.

### Choosing an ID Strategy

| Scenario | Typically appropriate strategy |
|---|---|
| Syncing a product that has a database ID | Use the stable product ID |
| Re-writing the same event on consumer retry | Use a stable event ID so the operation is idempotent |
| Writing independent logs where each write is a new event | Auto-generated ID can be used |
| Only a string business code exists | Use the string as `_id` if unique within the index |
| Sequential or large numeric IDs | Consider string formatting to avoid integer limits across API layers |

A stable ID makes write operations safer to repeat: re-writing the same state to the same ID does not create another document. However, it does not by itself resolve out-of-order updates; versioning or concurrency control is needed if ordering matters.

## 4. `save()` Differs from Partial Update

This is the most important distinction when working with CRUD.

### `save()` Writes a Complete Document

`save()` corresponds to indexing a document by ID. If the document already exists, the old source is replaced with the new source. Fields not present in the new source are not preserved as in a merge.

### Partial Update Changes Only the Sent Fields

The Elasticsearch Update API lets you send a `doc` section containing only the fields to change. Fields omitted from the update payload remain untouched.

For example, the current document has `name`, `price`, `available`, and `description`. Suppose you only want to update the price:

```http
POST /products/_update/p-1001
Content-Type: application/json

{
  "doc": {
    "priceMinorUnits": 3490000
  }
}
```

After the update, `name`, `available`, and `description` remain unchanged. This behaves differently from calling `save()` with an object containing only the ID and the new price.

### Comparing `save()` and Update

| Criterion | `save()` / index by ID | Partial update |
|---|---|---|
| Payload sent | Full document source | Only the fields or script to change |
| ID does not exist yet | Creates a new document | Usually returns not found unless upsert is enabled |
| ID already exists | Replaces old source with new source | Modifies only the specified part |
| Omitted fields | Removed from the new source | Preserved as-is |
| Best suited for | Syncing a complete document state | Updating a few attributes |
| Main risk | Writing an object missing fields causes data loss | Concurrent updates or incorrect scripts |

In Spring Data Elasticsearch, you can use `ElasticsearchOperations` together with `UpdateQuery` for partial updates. The exact builder structure and `Document` type depend on your project's Spring Data version. To illustrate server-side behavior, the Update REST API above directly demonstrates the operation's semantics.

## 5. Upsert: Update If Present, Create If Absent

Upsert combines update and insert. If the document exists, Elasticsearch applies the update; if it does not exist, it creates the document from the specified content.

Example using the Update API with `doc_as_upsert`:

```http
POST /products/_update/p-1001
Content-Type: application/json

{
  "doc": {
    "priceMinorUnits": 3490000,
    "available": true
  },
  "doc_as_upsert": true
}
```

If `p-1001` exists, the sent fields are updated. If it does not exist, the `doc` section is used to create a new document. Make sure the upsert payload includes all required fields so the newly created document is valid.

Distinguishing the three behaviors:

- `save()` by ID already performs create-or-replace source behavior.
- Partial update without upsert only updates an existing document.
- Partial update with `doc_as_upsert` updates if present and creates if absent.

Upsert does not automatically enforce full business validation rules. For example, if a new document requires `sku`, `name`, and `currency`, sending only `price` in `doc_as_upsert` can create a document missing essential data.

## 6. Distinguishing Index, Create, and Update in Elasticsearch

Elasticsearch provides APIs with distinct semantics:

| API | Behavior when ID is absent | Behavior when ID already exists |
|---|---|---|
| Index API (`PUT /index/_doc/id`) | Creates the document | Replaces the source |
| Create API (`PUT /index/_create/id`) | Creates the document | Returns a `409` conflict error |
| Update API (`POST /index/_update/id`) | Not found, unless upsert is enabled | Partially updates or runs a script |

Example of the Create API:

```http
PUT /products/_create/p-1001
Content-Type: application/json

{
  "name": "Coffee Maker",
  "sku": "COFFEE-001",
  "priceMinorUnits": 3250000
}
```

If ID `p-1001` already exists, the request returns a conflict error instead of overwriting. This is the right choice when the application wants to guarantee creation only and treats an existing ID as a business error.

Repository `save()` is used for saving a document by ID and can replace an old source. If you need create-only semantics, use the corresponding create API or an explicitly designed operation rather than assuming `save()` will reject duplicate IDs.

## 7. `saveAll()` and Bulk Writes

`saveAll()` saves multiple entities:

```java
List<ProductDocument> products = List.of(
    productA,
    productB,
    productC
);

Iterable<ProductDocument> savedProducts =
    productRepository.saveAll(products);
```

Spring Data Elasticsearch typically optimizes batch operations using the Bulk API instead of sending a separate request for each document. The Bulk API combines multiple actions into a single request, reducing network overhead and increasing throughput.

### Each Item in a Bulk Request Retains Its Own ID and Semantics

When `saveAll()` receives a document whose ID already exists, that document's index action replaces the source by ID. When the ID does not exist, the document is created. Thus, a single batch can contain both create and replace operations.

### Bulk Is Not an Atomic Transaction

A bulk request can have some items succeed and other items fail. You must not assume the entire batch is committed or rolled back like a relational database transaction. The application needs to inspect item-level errors, record logs/metrics, retry selectively, and ensure stable IDs so retries do not create duplicate records.

For large batches:

- Split into batch sizes suited to the payload and cluster capacity.
- Avoid sending a huge request that spikes heap pressure, network usage, and processing time.
- Track succeeded/failed item counts instead of checking only the overall HTTP request status.
- Retry transient errors with backoff; do not infinitely retry mapping errors or invalid data.
- Keep IDs stable so a resend does not unintentionally create new documents.

## 8. IDs and Idempotency When Syncing Data

Idempotency means that repeating the same operation does not cause unintended changes to the final outcome. In a database-to-Elasticsearch sync pipeline, stable IDs are a key part of achieving this property.

For example, event `product-updated-1001-v7` is delivered three times. If the consumer always writes to document ID `p-1001`, repeated writes with the same payload converge to the same source instead of creating three new documents.

However, suppose two events arrive out of order:

```text
Version 8: price = 200
Version 7: price = 180
```

If version 8 is written first and version 7 is written later, a `save()` call without version control can let the stale state overwrite the newer state. A stable ID only prevents creating duplicate records; it does not by itself protect update ordering.

To handle this, you can:

- Attach a business version to events and accept only newer versions.
- Use Elasticsearch/Spring Data optimistic concurrency control.
- Ensure processing order by product key within a message partition.
- Read the current state from the authoritative source before building the document, combined with versioning to prevent stale writes.

## 9. Optimistic Locking with `@Version`

When multiple processes can modify the same document concurrently, optimistic locking helps detect when a process is writing based on stale state. Spring Data Elasticsearch supports a version property via the `@Version` annotation.

Example:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.elasticsearch.annotations.Document;

@Document(indexName = "products")
public class ProductDocument {

    @Id
    private String id;

    @Version
    private Long version;

    private String name;
    private Long priceMinorUnits;

    // Constructors, getters and setters
}
```

When an entity is read, the version information is kept on the entity. When saving a versioned entity, Spring Data can send concurrency conditions so Elasticsearch detects whether the document has changed since it was read. If another process wrote first, the stale write can fail with an optimistic locking error instead of silently overwriting.

Conceptual flow:

```text
Client A reads document version 4
Client B reads document version 4

Client A saves changes -> succeeds, new version
Client B saves based on version 4 -> conflict
```

When a conflict occurs, the application should re-read the latest document, reapply the change according to business rules, and retry if appropriate. Do not blindly retry by resending the old entity because it still holds stale state.

The exact versioning mechanism and exception types may vary by Spring Data Elasticsearch/client version. Use the versioning API supported by your running version and test concurrent updates from two writers.

## 10. Does `save()` Make a Document Immediately Visible in Search?

Elasticsearch uses refresh to make indexed changes visible in search. After `save()` returns successfully, the document has been acknowledged by Elasticsearch, though it is not guaranteed to appear immediately in a subsequent search query.

This reflects the difference between:

- Reading a document by ID via the Get API, which can observe completed writes.
- Searching with the Search API, which depends on the index's refresh cycle.

If the application needs search to see the document right after a write, you can configure an appropriate refresh policy, such as `wait_for` on supported APIs. However, avoid forcing a refresh after every request because overly frequent refreshes degrade indexing performance.

For normal flows, design to tolerate a short search delay matching the index's refresh interval. If strong read-after-write is required for a screen, consider taking the result directly from the response or reading by ID rather than immediately executing a search.

## 11. Example Service for Saving and Updating Products

Example service using a repository to save full document state:

```java
import org.springframework.stereotype.Service;

@Service
public class ProductIndexService {

    private final ProductRepository repository;

    public ProductIndexService(ProductRepository repository) {
        this.repository = repository;
    }

    public ProductDocument saveFull(ProductDocument document) {
        return repository.save(document);
    }

    public ProductDocument find(String id) {
        return repository.findById(id).orElse(null);
    }
}
```

In a real service, clearly separate two use cases:

- **Syncing the full product:** read the authoritative state from the business database, build a complete `ProductDocument`, and then call `save()` using a stable ID.
- **Updating a single search field:** use partial update if you genuinely want to preserve all other fields; or read the full document, modify it, and save if logic needs full-state control with appropriate concurrency handling.

Do not accept a request DTO containing only `id` and a few fields, convert it directly into `ProductDocument`, and call `save()` if the intent is a partial update. That approach can replace the document with an incomplete source.

## 12. Common Pitfalls

### Calling `save()` Repeatedly Creates Multiple Documents

The usual cause is that the ID remains empty, so Elasticsearch generates a new ID on every save. Use a stable ID or retain the ID from the returned entity.

### Writing a New Document Loses Old Fields

The cause is that `save()` replaces the entire source. If you only want to change a subset of fields, use the Update API or rebuild the full document from the authoritative data source.

### Two Processes Overwrite Each Other

The cause is last-write-wins without concurrency control. Use versioning/optimistic locking or guarantee event ordering by key.

### `save()` Succeeds but Search Does Not See the Document

The cause may be that the index has not refreshed yet. Wait for the refresh interval, use an appropriate refresh policy when truly needed, or read by ID.

### `saveAll()` Reports Errors Even Though Some Documents Succeeded

The Bulk API is not atomic. Inspect item-level errors, fix data/mapping issues, or selectively retry transient errors.

### Same ID Returns a Different Document

Check which index or alias the read and write operations are using. IDs are only unique within an index; an alias may route to different physical indices.

## 13. Process for Choosing a Write Operation

Before selecting an API, determine the business semantics of the operation:

1. If writing a complete document state and the ID can be determined, use `save()`.
2. If the ID does not exist yet and business rules require rejecting duplicate IDs, use a create-only operation.
3. If changing only a few fields while keeping the remaining fields intact, use partial update.
4. If you need update-when-present or insert-when-absent, use upsert with a complete creation payload.
5. If writing multiple documents, consider `saveAll()`/Bulk API and handle errors per item.
6. If multiple writers exist, use versioning/optimistic locking or an update ordering mechanism.
7. If search visibility is needed immediately after writing, evaluate the refresh policy and performance cost.

## 14. Conclusion

In Spring Data Elasticsearch, `save()` stores a document by ID. If the ID does not exist in the target index, the document is created; if the ID already exists, the old source is replaced with the new source. Stable IDs make syncing and retries safer, whereas auto-generated IDs suit independent records where each write is a new document.

Distinguish `save()` from partial update and upsert. Use `save()` for complete state, the Update API when changing only part of a document, and create-only when a duplicate ID must be an error. With `saveAll()`, remember that the Bulk API is not an atomic transaction. When multiple writers exist, use optimistic locking or business versioning; when search must see writes immediately, account for refresh behavior. Understanding these semantics properly helps prevent lost fields, duplicate documents, and newer data being overwritten by stale state.
