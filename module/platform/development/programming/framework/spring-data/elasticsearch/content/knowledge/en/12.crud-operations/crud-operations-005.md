# Distinguishing Direct Lookup by ID from Index Search

Elasticsearch provides two common ways to read documents:

- **Direct lookup by ID**: specify the document ID and target index to read. Elasticsearch goes directly to the shard containing the document to retrieve it.
- **Searching through the index**: send a query to the Search API to find documents matching criteria using the inverted index and other search structures.

The two approaches serve different purposes and have different characteristics. When you know the exact document ID, direct lookup is usually simpler and faster. When you need to search by name, status, business code, content, or multiple criteria, you must use search.

## 1. Document ID and Index

Every document in Elasticsearch belongs to an index and has an ID metadata field named `_id`. For example:

~~~http
PUT /products/_doc/KB-1001
Content-Type: application/json

{
  "name": "Wireless Mechanical Keyboard",
  "sku": "KB-1001",
  "status": "PUBLISHED",
  "price": 1299000
}
~~~

In this example:

- `products` is the index.
- `KB-1001` is the document ID.
- `name`, `sku`, `status`, and `price` are fields in the document source.
- `_id` is the identifier metadata managed by Elasticsearch.

The document ID can be assigned beforehand by the application or auto-generated by Elasticsearch. When saving with Spring Data Elasticsearch, the Java property annotated with `@Id` maps to the `_id` metadata.

Example entity:

~~~java
import org.springframework.data.annotation.Id;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "products")
public class ProductDocument {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String name;

    @Field(type = FieldType.Keyword)
    private String sku;

    @Field(type = FieldType.Keyword)
    private String status;

    // Constructors, getters and setters
}
~~~

`id` in the entity is the value Spring Data uses as the document ID. It does not automatically become a business field for querying, sorting, or aggregations like `sku` or `status`.

## 2. Direct Document Retrieval by ID

Elasticsearch provides the Get API to retrieve a single document by index and ID:

~~~http
GET /products/_doc/KB-1001
~~~

This is a direct read operation. The request does not send Query DSL and does not look up terms in the inverted index like the Search API does.

When the document exists, the response has the form:

~~~json
{
  "_index": "products",
  "_id": "KB-1001",
  "_version": 3,
  "found": true,
  "_source": {
    "name": "Wireless Mechanical Keyboard",
    "sku": "KB-1001",
    "status": "PUBLISHED",
    "price": 1299000
  }
}
~~~

If the document does not exist, the Get API returns a not-found response (HTTP 404). The application should handle this case as a normal outcome of a read operation.

### Characteristics of the Get API

- Requires knowing the index and document ID.
- Returns at most one document for a given ID in the specified index.
- Does not support search predicates like `name contains...` or `status = ...`.
- Does not compute a relevance score.
- Can return `_source` or selectively return specific parts of the source.
- Realtime by default: a newly indexed or updated document can be read via the Get API even if that change does not yet appear in Search API results before a refresh.

The Get API fits when the application already has the ID from a URL, a reference key, or the result of an earlier write operation.

## 3. Fetching Multiple Documents by ID with Multi Get

If you already know multiple IDs and want to retrieve their documents, you do not need to send a separate Get request for each document. Elasticsearch provides the Multi Get API:

~~~http
POST /products/_mget
Content-Type: application/json

{
  "ids": ["KB-1001", "KB-1002", "KB-1003"]
}
~~~

Or specify the index, ID, and routing individually per document:

~~~http
POST /_mget
Content-Type: application/json

{
  "docs": [
    {
      "_index": "products",
      "_id": "KB-1001"
    },
    {
      "_index": "products",
      "_id": "KB-1002"
    }
  ]
}
~~~

Multi Get returns a per-document result. A missing ID does not cause the entire request to fail; inspect the status of each element in the response.

Use Multi Get when:

- The list of IDs is already available from another source.
- You need to load a group of documents to render a screen or execute business logic.
- You want to reduce round trips compared to sequential Get API calls.

If the ID list is very large, split it into sensible batches to control request size, network load, and memory.

## 4. Searching Documents Through the Index

The Search API finds documents matching conditions using Query DSL:

~~~http
GET /products/_search
Content-Type: application/json

{
  "query": {
    "match": {
      "name": "wireless keyboard"
    }
  }
}
~~~

Elasticsearch analyzes the query text with the field's search analyzer, looks up matching terms in the inverted index, and computes relevance scores when the query uses scoring.

The Search API can return multiple documents along with:

- Total hit counts according to the track total hits configuration.
- Relevance score (`_score`) if the query calculates scores.
- Requested source fields or stored fields.
- Sorting, highlighting, aggregation, and pagination details.

Example filtering by status:

~~~http
GET /products/_search
Content-Type: application/json

{
  "query": {
    "term": {
      "status": "PUBLISHED"
    }
  }
}
~~~

Example searching by SKU:

~~~http
GET /products/_search
Content-Type: application/json

{
  "query": {
    "term": {
      "sku": "KB-1001"
    }
  }
}
~~~

Even when expecting only a single result, searching by a business field such as `sku` still performs an index search. Elasticsearch has to look up the corresponding term in the indexed field.

### Characteristics of the Search API

- Searches by fields and query conditions without requiring the document ID upfront.
- Can return one or many matching documents.
- Supports full-text queries, filters, ranges, sorting, aggregations, highlighting, and pagination.
- Can compute relevance scores for results.
- Results depend on the search index state after refresh, so the Search API is near-real-time.

## 5. Visibility Timing Differences: Realtime vs. Near-Real-Time

A crucial point is that the Get API and Search API have different data visibility mechanisms.

Elasticsearch is a near-real-time search engine. After indexing or updating a document, changes may not appear immediately in the Search API. A document becomes searchable after the index refreshes.

Meanwhile, the Get API reads in realtime by default, so it can return the new version even when the Search API cannot find that version yet.

Example:

1. The application saves product `KB-1001` with the name `Wireless Keyboard`.
2. The save API returns success.
3. The application calls the Get API with ID `KB-1001`: it can read the new data immediately.
4. The application immediately calls the Search API with `name = Wireless Keyboard`: the result might not appear until the next refresh.

~~~mermaid
sequenceDiagram
    participant App as Application
    participant ES as Elasticsearch
    App->>ES: Index document KB-1001
    ES-->>App: Index succeeded
    App->>ES: GET /products/_doc/KB-1001
    ES-->>App: Returns new document (realtime)
    App->>ES: POST /products/_search
    ES-->>App: Results based on current search index
    Note over ES: After refresh, the new document becomes searchable via Search API
~~~

Do not treat the Search API not returning a document right after save as proof that the document was not saved. When you need immediate write verification by ID, the Get API is the appropriate choice.

### Refresh and refresh=wait_for

You can tell Elasticsearch to wait for a refresh so changes become searchable:

- `refresh=false`: does not trigger an immediate refresh; uses default behavior.
- `refresh=wait_for`: waits for a refresh that makes the changes searchable.
- `refresh=true`: triggers an immediate refresh, making changes searchable sooner at a higher system cost.

Example:

~~~http
PUT /products/_doc/KB-1001?refresh=wait_for
Content-Type: application/json

{
  "name": "Wireless Keyboard",
  "sku": "KB-1001",
  "status": "PUBLISHED"
}
~~~

`refresh=wait_for` is useful when a business flow must write and then search immediately within the same process. Do not enable `refresh=true` on every write request in production because frequent refreshes reduce indexing efficiency.

If immediate search is not required, let refreshes follow the index configuration and accept normal near-real-time latency.

## 6. Comparing Get API, Multi Get, and Search API

| Criterion | Get API | Multi Get API | Search API |
|---|---|---|---|
| Input | Single ID | List of IDs | Query DSL |
| Document count | One | Multiple known IDs | One or more matching results |
| Search by business field | No | No | Yes |
| Full-text query | No | No | Yes |
| Relevance score | No | No | Optional |
| Aggregation | No | No | Yes |
| Sort and pagination | No | No | Yes |
| Post-write availability | Realtime by default | Realtime by default per document | Near-real-time after refresh |
| Typical use case | Detail view by ID | Loading multiple documents by ID | Searching and filtering |

## 7. How Querying by ID via Search API Differs from Get API

Elasticsearch also has an `ids` query:

~~~http
GET /products/_search
Content-Type: application/json

{
  "query": {
    "ids": {
      "values": ["KB-1001", "KB-1002"]
    }
  }
}
~~~

This query finds documents whose IDs are in the list. However, it still executes via the Search API and depends on search visibility after refresh.

Compare:

~~~http
GET /products/_doc/KB-1001
~~~

and:

~~~http
GET /products/_search
Content-Type: application/json

{
  "query": {
    "ids": {
      "values": ["KB-1001"]
    }
  }
}
~~~

Both target IDs, but their execution paths differ:

- The Get API directly fetches a single document by index and ID.
- The `ids` query is a search query, returning Search Hits and obeying near-real-time visibility.

Use the Get API when you need one specific document. Use the `ids` query when combining a list of IDs with other search filters, or when you need results as Search Hits along with sorting, aggregations, and other Search API features.

## 8. Using Direct ID Lookup in Spring Data Elasticsearch

Spring Data Elasticsearch provides the Repository abstraction and `ElasticsearchOperations` for ID-based reads.

### Using ElasticsearchRepository.findById

A repository can be declared as:

~~~java
import org.springframework.data.elasticsearch.repository.ElasticsearchRepository;

public interface ProductRepository
        extends ElasticsearchRepository<ProductDocument, String> {
}
~~~

Reading by ID:

~~~java
import java.util.Optional;

Optional<ProductDocument> product =
        productRepository.findById("KB-1001");
~~~

`findById` reads by the entity's identifier. The ID type must match the generic ID type on the repository.

The result is an `Optional`:

- Document present: `Optional.of(product)`.
- Document absent: `Optional.empty()`.

Service example:

~~~java
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository repository;

    public ProductDocument getRequired(String id) {
        return repository.findById(id)
                .orElseThrow(() ->
                        new IllegalArgumentException(
                                "Product not found: " + id
                        )
                );
    }
}
~~~

Do not use `findById` to search by SKU if SKU is not the value mapped to `@Id`. In that case, use a field finder method or the Search API.

### Using ElasticsearchOperations.get

You can read directly through `ElasticsearchOperations`:

~~~java
import org.springframework.data.elasticsearch.core.ElasticsearchOperations;
import org.springframework.stereotype.Service;

@Service
public class ProductLookupService {

    private final ElasticsearchOperations operations;

    public ProductLookupService(ElasticsearchOperations operations) {
        this.operations = operations;
    }

    public ProductDocument getById(String id) {
        return operations.get(id, ProductDocument.class);
    }
}
~~~

`operations.get(id, ProductDocument.class)` retrieves the document by ID and converts it into a `ProductDocument` entity. Not-found outcomes are typically represented as `null`; handle that case before using the result.

Repositories fit standard CRUD well. `ElasticsearchOperations` is useful when a service needs explicit control over entity type, index metadata, or combining with other Spring Data operations.

## 9. Using the Search API in Spring Data Elasticsearch

When searching by name, status, price range, or multiple fields, use a search query.

Example with `NativeQuery` and the Elasticsearch Java API Client:

~~~java
import co.elastic.clients.elasticsearch._types.query_dsl.Query;
import org.springframework.data.elasticsearch.client.elc.NativeQuery;
import org.springframework.data.elasticsearch.core.SearchHits;
import org.springframework.data.elasticsearch.core.ElasticsearchOperations;

public SearchHits<ProductDocument> searchByName(
        ElasticsearchOperations operations,
        String text
) {
    Query query = Query.of(q -> q
            .match(m -> m
                    .field("name")
                    .query(text)
            )
    );

    NativeQuery nativeQuery = NativeQuery.builder()
            .withQuery(query)
            .build();

    return operations.search(nativeQuery, ProductDocument.class);
}
~~~

In this example:

- `Query` represents the Elasticsearch Java API Client Query DSL.
- `match` runs a full-text search on the `name` field.
- `NativeQuery` wraps the query for Spring Data execution.
- `operations.search(...)` returns `SearchHits`, including metadata and matching results.

You can use `term` to filter strictly by status:

~~~java
Query query = Query.of(q -> q
        .term(t -> t
                .field("status")
                .value("PUBLISHED")
        )
);
~~~

In real applications, combine conditions inside a `bool` query, using `filter` for filtering clauses that do not need relevance scoring and `must` for full-text search clauses.

### Searching via Repository Finder Methods

Spring Data also supports query derivation from method names:

~~~java
import java.util.List;
import org.springframework.data.elasticsearch.repository.ElasticsearchRepository;

public interface ProductRepository
        extends ElasticsearchRepository<ProductDocument, String> {

    List<ProductDocument> findByStatus(String status);

    List<ProductDocument> findBySku(String sku);
}
~~~

These finder methods query by entity fields, not directly by `@Id`. When you need full-text queries, multiple criteria, sorting, or complex aggregations, use custom queries or `ElasticsearchOperations.search(...)`.

## 10. When to Choose ID Lookup vs. Field Search?

Base the choice on the input data and the goal of the operation.

| Business requirement | Appropriate approach |
|---|---|
| Open a product detail page using an ID in the URL | Get API / `findById` |
| Check a single document with a known ID | Get API |
| Fetch multiple documents from a list of IDs | Multi Get API |
| Search products by name | Search API with `match` |
| Look up by SKU when SKU is not the document ID | Search API with `term` or repository finder |
| Filter by status and price range | Search API with `bool`, `filter`, `range` |
| Search by multiple conditions and compute relevance | Search API |
| Count products by status | Search API with aggregation |

Practical examples:

- Frontend calls `GET /api/products/KB-1001`: the service typically uses `findById("KB-1001")`.
- Frontend calls `GET /api/products?keyword=keyboard`: the service needs the Search API with a full-text query.
- Frontend calls `GET /api/products?status=PUBLISHED`: the service can use a repository finder or Search API with a filter.
- A job already has a list of IDs from another system: consider Multi Get instead of running a search query for each ID.

## 11. Notes on Routing and Index Aliases

### Custom Routing

Elasticsearch can use routing to determine which shard stores a document. When a document is indexed with custom routing, Get or Multi Get operations must provide the same routing value to hit the right shard.

Example indexing with routing:

~~~http
PUT /products/_doc/KB-1001?routing=tenant-42
Content-Type: application/json

{
  "sku": "KB-1001",
  "name": "Mechanical Keyboard"
}
~~~

Reading it back requires the same routing:

~~~http
GET /products/_doc/KB-1001?routing=tenant-42
~~~

If routing is omitted or incorrect, the Get API may fail to find the document even though it exists on another shard. In multi-tenant applications, ensure routing is passed consistently across write, read, update, and delete operations.

### Index Aliases

An application can use an alias instead of a physical index name:

~~~java
@Document(
    indexName = "products",
    createIndex = false
)
public class ProductDocument {
    // ...
}
~~~

The `products` alias can point to a versioned index like `products-v1`. When using an alias, know which index it targets and whether it points to multiple indices.

The Get API requires a document ID within the scope of the target index. If an alias points to multiple indices, do not treat the Get API as an ID search across all indices. When you need to find documents by ID across multiple indices, use the Search API with an `ids` query or determine the specific index before calling Get.

## 12. Common Pitfalls

### Using findById with a Business Key

If `@Id` maps to the `id` property, calling `findById("KB-1001")` looks up the document with ID `KB-1001`. It does not search the `sku` field unless SKU is the document ID.

Check your entity mapping and clearly distinguish IDs from business keys.

### Searching Immediately After Save Before Refresh

The Get API can read the new document while the Search API does not see it yet. If a business flow requires immediate searchability, consider `refresh=wait_for` on the write operation instead of forcing a refresh on every request.

### Using the Search API to Fetch One Document with a Known ID

If you only need one document by ID, the Search API adds search overhead and incurs refresh latency. Using the Get API is usually more appropriate.

### Using the Get API to Search by Partial Name

The Get API does not support full-text queries. To search by content, use `match` on the Search API.

### Forgetting Routing

A document indexed with custom routing may not be found by a Get call using default routing. Pass the exact routing used during the write.

### Confusing _id with a Field in _source

`_id` is identifier metadata. If you want to query by a business code, store that code as a separate field and map it to the proper data type.

## 13. Selection Workflow in a Service

When building a data-reading service, you can follow these steps:

1. Determine whether the input is a document ID or search criteria.
2. If you have an ID and know the target index, use repository `findById` or `ElasticsearchOperations.get`.
3. If you have multiple known IDs, consider Multi Get.
4. If searching by a business field, use a repository finder or the Search API.
5. If you need full-text search, scoring, sorting, aggregations, or multiple conditions, use the Search API.
6. If writes must be immediately searchable, account for refresh visibility and choose an appropriate refresh policy.
7. If using custom routing or multi-index aliases, resolve the correct index/routing for the read operation.

## Conclusion

Direct lookup by ID and index search serve two distinct needs. The Get API and `findById` retrieve a document with a known identifier in realtime; the Search API finds documents matching a query against the search index and is near-real-time after refresh. Use IDs for detail reads, Multi Get for multiple known IDs, and the Search API for field queries, full-text search, filtering, sorting, or aggregations.
