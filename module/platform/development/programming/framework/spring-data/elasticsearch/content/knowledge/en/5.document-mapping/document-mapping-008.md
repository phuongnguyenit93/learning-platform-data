# `@Transient`, `@ReadOnlyProperty`, and `@WriteOnlyProperty`

Spring Data Elasticsearch maps Java objects into Elasticsearch documents when writing data and converts received documents back into Java objects when reading data. Not every property in an entity needs to travel in both directions. Some properties exist only for display in the application, some are generated by an ingest pipeline or another system, and some only need to be sent during a write.

Spring Data provides three annotations to describe these cases:

- `@Transient`: excludes the property from persistence mapping.
- `@ReadOnlyProperty`: reads the property from the datastore but does not write it from the entity to the datastore.
- `@WriteOnlyProperty`: writes the property from the entity to the datastore but does not read its value from the datastore into the entity.

These three annotations belong to Spring Data Commons (`org.springframework.data.annotation`) and are used within Spring Data's mapping model. They control how Spring Data converts objects and documents. They do not replace Elasticsearch-specific mapping settings such as `@Field`, `index`, `doc_values`, or `_source`.

## 1. Two Conversion Directions Between Entity and Elasticsearch

When saving an entity, Spring Data converts the object into data to send to Elasticsearch. When reading, Spring Data takes the returned document and converts its data fields into object properties.

```text
Writing data

Java entity
    |
    v
Spring Data mapping converter
    |
    v
Elasticsearch document
    |
    v
Index

Reading data

Index
    |
    v
Elasticsearch document / _source
    |
    v
Spring Data mapping converter
    |
    v
Java entity
```

For a regular property without special annotations, Spring Data typically writes the property's value on save and assigns the value from the document on read. The three annotations covered here alter behavior in each direction.

| Annotation | Write from entity to Elasticsearch | Read from Elasticsearch into entity | Use Case |
|---|---:|---:|---|
| No special annotation | Yes | Yes | Regular persistent property |
| `@Transient` | No | No | Value exists only in the application, not part of the document |
| `@ReadOnlyProperty` | No | Yes | Value generated by Elasticsearch or another system |
| `@WriteOnlyProperty` | Yes | No | Value only needs to be sent to the datastore or pipeline |

You can remember the three behaviors as:

```text
@Transient          : no write, no read
@ReadOnlyProperty   : read-only
@WriteOnlyProperty  : write-only
```

## 2. `@Transient`: Property Excluded from Persistence Mapping

`@Transient` marks a property that is not data to be persisted in the datastore. Spring Data skips this property both when converting an entity into a document and when converting a document into an entity.

This annotation is commonly used for:

- Values computed from persisted properties.
- Temporary data used only within a single business operation.
- UI state or display helper values.
- In-memory caches attached to the object that are not part of Elasticsearch data.

For example, a product has a name and price persisted in Elasticsearch, while `displayLabel` is constructed solely for display:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Transient;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "products")
public class Product {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String name;

    @Field(type = FieldType.Long)
    private Long priceInCents;

    @Transient
    private String displayLabel;

    public String getDisplayLabel() {
        return name + " - " + priceInCents + " cents";
    }
}
```

`id`, `name`, and `priceInCents` are persistent data. `displayLabel` is derived from those values, so there is no need to store it redundantly in Elasticsearch. When reading the document, Spring Data also does not try to retrieve a `displayLabel` field to populate the entity.

### 2.1. `@Transient` Is Not the Same as `@Field(index = false)`

The two configurations serve different purposes:

- `@Transient` excludes the property from Spring Data persistence mapping. Its value is neither written into the document by the mapping converter nor read from the document into the property.
- `@Field(index = false)` still allows the property to participate in conversion and store its value in the document, while instructing Elasticsearch not to index the field in the usual way for term searches.

For example, a long description may still need to be stored and returned in `_source` without needing full-text search. In that case, `index = false` can be suitable. If a value is solely for display and should not belong to the document, `@Transient` is more appropriate.

### 2.2. `@Transient` Is Not a JSON Annotation

Spring Data's `@Transient` only controls persistence mapping. It does not automatically exclude the property from JSON returned by Spring MVC/Jackson. If a REST API must not return a property, design a DTO or use an appropriate JSON annotation/configuration, such as `@JsonIgnore` when that matches the API requirement.

Java also has the `transient` keyword, which typically relates to Java serialization. The language keyword and the `org.springframework.data.annotation.Transient` annotation belong to two separate mechanisms. When wanting to express intent clearly for Spring Data mapping, use the Spring Data annotation.

## 3. `@ReadOnlyProperty`: Read-Only from Elasticsearch

`@ReadOnlyProperty` marks a property that Spring Data is allowed to read from a document, but does not write when saving the entity.

This is useful when the value is generated or managed outside the entity's normal write path, for example:

- An ingest pipeline adds the document ingestion timestamp.
- Another synchronization system supplements metadata.
- A processing job updates a result field after the application sends the document.
- Elasticsearch returns a value computed or injected into `_source` by another mechanism.

For example, the application sends an order and an ingest pipeline adds `indexedAt` to the document:

```java
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "orders")
public class Order {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String status;

    @ReadOnlyProperty
    @Field(type = FieldType.Date)
    private Instant indexedAt;

    // Constructors, getters and setters
}
```

When saving `Order`, Spring Data does not send the `indexedAt` value from the object down to Elasticsearch. When reading a document containing the `indexedAt` field, Spring Data can still map that value into the `indexedAt` property.

`@Field(type = FieldType.Date)` describes the field's Elasticsearch data type. `@ReadOnlyProperty` describes Spring Data's conversion direction. Both annotations can appear together because they fulfill two different roles.

### 3.1. Example Ingest Pipeline Adding a Field

An ingest pipeline can set the processing timestamp into the `indexedAt` field:

```http
PUT _ingest/pipeline/add-indexed-time
{
  "processors": [
    {
      "set": {
        "field": "indexedAt",
        "value": "{{{_ingest.timestamp}}}"
      }
    }
  ]
}
```

You can configure the index to use a default pipeline:

```http
PUT orders
{
  "settings": {
    "index.default_pipeline": "add-indexed-time"
  },
  "mappings": {
    "properties": {
      "status": {
        "type": "keyword"
      },
      "indexedAt": {
        "type": "date"
      }
    }
  }
}
```

When the application writes a document to this index, the pipeline can populate `indexedAt` before the document is stored. When Spring Data reads the document, `@ReadOnlyProperty` allows receiving the pipeline-generated value.

The pipeline and mapping examples above are created separately in Elasticsearch. `@Document` and `@Field` do not automatically create ingest pipelines. If the index was created earlier, ensure the mapping and pipeline are properly configured before the application sends data.

### 3.2. Caution When Updating Documents

`@ReadOnlyProperty` only prevents Spring Data from writing the property value from the entity. It does not lock the field at the Elasticsearch level and does not stop another client from updating that field.

Additionally, understand how the application writes documents. An index operation replacing a document may recreate `_source` from the fields the client sends. If the `indexedAt` field is created by a pipeline, ensure the pipeline continues running to regenerate the field on every necessary write, or design an appropriate update flow. Do not assume a field created by another system will always remain intact after every `save`.

## 4. `@WriteOnlyProperty`: Write-Only to Elasticsearch

`@WriteOnlyProperty` marks a property that is written from the entity to the datastore, but not mapped back from the document into the entity on read.

It can be used when:

- An input value only serves an ingest pipeline.
- A command or parameter needs to be sent during a write but is not needed in the object read back.
- A temporary field is processed on the Elasticsearch side or by an intermediary system.
- The application wants to separate the input data model from the read data model while sharing the entity in some flows.

For example, the application sends `ingestCommand` for pipeline processing, yet does not need this property when reading the order back:

```java
import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.WriteOnlyProperty;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "orders")
public class Order {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String status;

    @WriteOnlyProperty
    @Field(type = FieldType.Keyword)
    private String ingestCommand;

    // Constructors, getters and setters
}
```

When saving an entity with `ingestCommand`, Spring Data writes this value into the input document. When reading the document into `Order`, Spring Data does not assign the value from that field into the `ingestCommand` property.

### 4.1. `@WriteOnlyProperty` Does Not Remove the Field from Elasticsearch

The important point is that `@WriteOnlyProperty` controls Spring Data's conversion. It does not automatically remove the field from `_source`, encrypt the value, or create Elasticsearch authorization rules.

If the field remains in `_source`, users with permission to read documents via the Elasticsearch API or another client can still retrieve that value. The annotation only prevents Spring Data's mapping converter from populating this value into the Java property on read.

If the input data is sensitive and must not be stored long-term, address that requirement through proper design, such as:

- Do not send sensitive data if Elasticsearch does not need it.
- Use an ingest pipeline to process and then remove the input field using the `remove` processor.
- Grant appropriate index/document access permissions and restrict APIs allowed to read.
- Use dedicated DTOs to avoid returning internal data in REST APIs.

Do not use `@WriteOnlyProperty` as a security mechanism or a way to hide secrets.

### 4.2. Example Pipeline Removing the Input Field

A pipeline can receive `ingestCommand`, generate necessary metadata, and then remove the command field from the document before storing:

```http
PUT _ingest/pipeline/consume-order-command
{
  "processors": [
    {
      "set": {
        "field": "commandProcessed",
        "value": true
      }
    },
    {
      "remove": {
        "field": "ingestCommand",
        "ignore_missing": true
      }
    }
  ]
}
```

When the index is configured to use this pipeline, `ingestCommand` can be processed during ingestion and then removed from the final document. `@WriteOnlyProperty` keeps the entity read path from trying to map this field. Actually removing it from `_source` is the pipeline's responsibility, not the annotation's.

If the application needs to retain input values for auditing, do not remove fields arbitrarily. Determine retention periods, access permissions, and audit requirements before deciding to keep or remove data.

## 5. Comparing All Three Annotations in the Same Entity

An entity can have properties with different behaviors. The following example combines all three annotations:

```java
import java.time.Instant;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.ReadOnlyProperty;
import org.springframework.data.annotation.Transient;
import org.springframework.data.annotation.WriteOnlyProperty;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "orders")
public class Order {

    @Id
    private String id;

    @Field(type = FieldType.Keyword)
    private String status;

    @ReadOnlyProperty
    @Field(type = FieldType.Date)
    private Instant indexedAt;

    @WriteOnlyProperty
    @Field(type = FieldType.Keyword)
    private String ingestCommand;

    @Transient
    private String displayLabel;

    // Constructors, getters and setters
}
```

Meaning of each property:

| Property | Annotation | When saving entity | When reading document |
|---|---|---|---|
| `id` | `@Id` | Used as document ID | Mapped from ID |
| `status` | No special annotation | Written | Read |
| `indexedAt` | `@ReadOnlyProperty` | Not written from entity | Read if document has field |
| `ingestCommand` | `@WriteOnlyProperty` | Written | Not mapped into entity |
| `displayLabel` | `@Transient` | Skipped | Skipped |

This separation lets the entity clearly express the origin and lifecycle of each property. Values generated by Elasticsearch or pipelines are not accidentally overwritten with empty values from the entity; values serving only write commands do not need to be loaded back into read objects.

## 6. Distinguishing Spring Data Annotations from Other Elasticsearch Configurations

Persistence annotations and Elasticsearch mapping attributes are often confused because they appear on the same field. Distinguish the question each configuration answers.

| Configuration | Primary Question | Typical Effect |
|---|---|---|
| `@Transient` | Does the property belong to Spring Data's persistence model? | Skips both write and read in the mapping converter |
| `@ReadOnlyProperty` | Does Spring Data write the value from the entity? | Reads from datastore only |
| `@WriteOnlyProperty` | Does Spring Data load the value from the datastore into the entity? | Writes to datastore only |
| `@Field(type = ...)` | Which Elasticsearch type does the field have? | Describes mapping such as `text`, `keyword`, `date`, `long` |
| `@Field(index = false)` | Does Elasticsearch index the field for searching? | Controls index/search capability of the field |
| `@Field(docValues = false)` | Does the field generate doc values? | Affects operations relying on doc values |
| `@JsonIgnore` | Does Jackson include the property in JSON? | Controls JSON serialization/deserialization |

Example:

```java
@Field(type = FieldType.Text, index = false)
private String internalDescription;
```

The `internalDescription` field is still a persistent property. Spring Data can write and read it; `index = false` controls Elasticsearch's indexing of the field. This differs from:

```java
@Transient
private String temporaryDescription;
```

`temporaryDescription` is ignored by Spring Data's mapping converter.

Similarly, `@WriteOnlyProperty` does not mean Elasticsearch skips indexing the field. If the field has a mapping and is sent in the index request, Elasticsearch still applies the corresponding mapping configuration. Nor does `@ReadOnlyProperty` mean the field is write-locked on the cluster side.

## 7. Impact on `_source` and Search Results

Elasticsearch typically stores the original JSON of a document in `_source`. In addition to `_source`, Elasticsearch creates structures for searching, sorting, or aggregations depending on field type and mapping.

The three Spring Data annotations act at the entity/document conversion layer:

- `@Transient`: Spring Data neither includes the property in the document built from the entity nor populates the property from the document.
- `@ReadOnlyProperty`: Spring Data excludes the property value from the document when writing; if a document created by a pipeline or another client has the corresponding field, Spring Data can read that field.
- `@WriteOnlyProperty`: Spring Data includes the value in the document when writing, yet skips the field when constructing the entity from the document.

The annotations do not alter how Elasticsearch stores `_source` once it receives the request. Pipelines, mappings, `_source` configuration, and Elasticsearch permissions govern what data is stored, indexed, and returned at the Elasticsearch layer.

If you need to determine whether a field is searchable, inspect the index mapping. If you need to determine whether a field exists in `_source`, inspect the actual document. You cannot infer either of those solely from `@ReadOnlyProperty` or `@WriteOnlyProperty`.

## 8. Impact on Repositories and ElasticsearchOperations

The annotations are applied in the Spring Data mapping layer, so their behavior takes effect when using APIs that convert entities, such as repositories or `ElasticsearchOperations`.

Example:

```java
Order order = new Order();
order.setId("order-100");
order.setStatus("CREATED");
order.setIngestCommand("RECALCULATE_METADATA");

Order saved = orderRepository.save(order);

Order loaded = orderRepository.findById("order-100")
        .orElseThrow();
```

On write, Spring Data applies each property's conversion rules. On read, it applies the reverse rules. For a document with a pipeline, `indexedAt` can be read into `loaded`; `ingestCommand` is not populated into `loaded`; `displayLabel` remains a transient value computed by the application.

Do not assume the object returned from `save` will have the exact same state as an object freshly read back from Elasticsearch. A repository may return the input entity or a processed representation depending on the API and version; the `@WriteOnlyProperty` annotation governs mapping from the datastore, rather than requiring clearing values from a Java object the caller already holds.

If using the Elasticsearch Java Client directly to read or write JSON, Spring Data annotations do not automatically apply to those requests. The low-level client bypasses Spring Data's mapping converter. When mixing repositories, `ElasticsearchOperations`, and the direct client, clearly track which layer performs conversion.

## 9. Notes on Constructors, Getters/Setters, and Property Access

Spring Data determines persistent properties based on entity metadata and the chosen access strategy. In Java, annotations are usually placed on fields as shown in this lesson's examples. If a project uses property access or places annotations on getters, remain consistent with how Spring Data discovers properties.

Some points to watch:

- Place annotations on the exact fields/properties managed by Spring Data; avoid duplicate-named properties or getters/setters with side effects.
- If using Lombok, check where annotations are generated and configure `@Getter`, `@Setter`, or `@Accessors` so annotations are not inadvertently placed in unintended locations.
- Constructors used to instantiate entities when reading documents must be compatible with persistent properties. If using a parameterized constructor, names/order and metadata must match Spring Data's mapping rules.
- For `@Transient` properties, do not expect Spring Data to restore values from the document. If values are needed after reading, recompute them in the application or supply them via a service/DTO.
- For `@ReadOnlyProperty`, another source must write the field into the document. If no pipeline or writer populates the field, the property will typically be `null`/default when read.
- For `@WriteOnlyProperty`, the entity read back lacks that property's value from the document. Use nullable/wrapper types if you need to distinguish an unset state from a default value.

## 10. Verifying Behavior with Real Data

When using these annotations, test both conversion directions instead of looking only at Java declarations.

You can create a sample document and inspect `_source`:

```http
GET orders/_doc/order-100
```

Inspect the index mapping:

```http
GET orders/_mapping
```

Useful questions when verifying:

1. Is the `@Transient` field omitted from the document created by Spring Data?
2. Is the `@ReadOnlyProperty` field populated by an ingest pipeline or another system?
3. Is the `@WriteOnlyProperty` field sent in the write request?
4. Does the pipeline keep or remove the input field in `_source`?
5. When the repository reads the document back, is the read-only property populated and the write-only property skipped?
6. Does the Elasticsearch mapping have the right data types and required index configuration?

When inspecting Elasticsearch requests directly, distinguish the document sent by Spring Data from the document transformed by a pipeline before storage. The final data in `_source` may differ from the initial JSON sent by the application.

In integration tests, you can use a real Elasticsearch instance or Testcontainers to verify the mapping converter alongside ingest pipelines. Mocking a repository only tests application-layer interactions; it does not verify Spring Data document conversion or pipeline execution on Elasticsearch.

## 11. Common Mistakes

### Using `@Transient` for a Field Generated by a Pipeline

`@Transient` causes Spring Data to skip the property on both write and read. If a pipeline generates `indexedAt` and the application wants to receive this value when reading documents, use `@ReadOnlyProperty` instead of `@Transient`.

### Using `@ReadOnlyProperty` When Nothing Writes the Field

The annotation only stops the entity from writing the value to Elasticsearch. It does not generate timestamps or metadata on its own. You must configure an ingest pipeline, another writer, or a corresponding value-generation mechanism.

### Assuming `@WriteOnlyProperty` Protects Sensitive Data

The annotation does not guarantee the field is removed from `_source`. Any user permitted to read the document via the Elasticsearch API can still see the field if it was stored. Use a pipeline `remove` processor, access control, and appropriate data design when information needs protection.

### Confusing `@Field(index = false)` with `@Transient`

`index = false` relates to Elasticsearch's indexing capability. It does not remove the field from Spring Data's read/write conversion. `@Transient` is the annotation that excludes a property from persistence mapping.

### Expecting Annotations to Take Effect When Using a Low-Level Client

Spring Data annotations are not Elasticsearch server mapping rules. When calling the Elasticsearch Java Client directly, build requests and handle responses according to your desired data structure.

### Forgetting the Effect of Document-Replacing Writes

If a read-only field is generated by a pipeline, a subsequent index operation may replace `_source`. Ensure the pipeline continues generating the field or use an appropriate update mechanism so metadata is not accidentally lost.

## 12. How to Choose the Right Annotation

| Requirement | Appropriate Annotation/Configuration | Reason |
|---|---|---|
| Value computed only in the application, not part of document | `@Transient` | No need to write or read via persistence mapping |
| Timestamp generated by ingest pipeline, application needs to read | `@ReadOnlyProperty` combined with `@Field` | Reads field from document without writing value from entity |
| Parameter sent to pipeline, no need to load back into entity | `@WriteOnlyProperty` combined with `@Field` | Writes input but skips on entity read |
| String still stored in `_source` without needing indexing | `@Field(index = false)` | Field remains in document, only indexing behavior changes |
| Property must not appear in JSON API | DTO or Jackson configuration | Controls JSON serialization independently of Spring Data mapping |

## 13. Summary

`@Transient`, `@ReadOnlyProperty`, and `@WriteOnlyProperty` allow Spring Data to clearly express which direction of the persistence process a property participates in. `@Transient` skips both reading and writing; `@ReadOnlyProperty` reads data from Elasticsearch only; `@WriteOnlyProperty` writes data to Elasticsearch only.

In Spring Data Elasticsearch, `@ReadOnlyProperty` or `@WriteOnlyProperty` can be combined with `@Field` both to control conversion direction in Spring Data and to describe the field type in Elasticsearch. Distinguish these annotations from `index = false`, `_source`, and JSON annotations. In particular, `@WriteOnlyProperty` is not a security mechanism and `@ReadOnlyProperty` does not write-lock fields on the cluster side. Understanding the boundary between the mapping converter, ingest pipelines, and Elasticsearch mappings ensures entities accurately reflect data provenance and lifecycle.
