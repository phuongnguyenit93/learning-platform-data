# Reading Highlights from SearchHit and Mapping to DTOs

Elasticsearch can return text segments containing matched keywords, accompanied by tags marking the highlighted parts. Spring Data Elasticsearch keeps these segments in the metadata of SearchHit, separate from the entity converted from _source. Therefore, if an API needs to return both product data and highlight segments, the application should receive SearchHit<T> or SearchHits<T>, read getHighlightField(...), and manually map them to a response DTO.

This lesson walks through the full flow: configuring highlighting on a repository or query, reading the list of fragments from SearchHit, distinguishing original content from highlighted content, converting results into DTOs, handling missing fragments, and delivering data safely to the UI.

## 1. Where Do Highlights Live in a Search Response?

When calling the Search API with a highlight configuration, Elasticsearch returns an extra highlight object inside each search hit. Abbreviated example response:

~~~json
{
  "hits": {
    "hits": [
      {
        "_id": "p-100",
        "_score": 3.82,
        "_source": {
          "title": "Mechanical keyboard",
          "description": "A quiet wireless keyboard for daily work."
        },
        "highlight": {
          "title": [
            "<mark>Mechanical</mark> keyboard"
          ],
          "description": [
            "A quiet <mark>wireless</mark> keyboard for daily work."
          ]
        }
      }
    ]
  }
}
~~~

This response contains two distinct data sections:

- _source holds the original document content, which Spring Data maps to the Product entity.
- highlight holds the fragments generated by the highlighter, including tags marking matched terms.

Spring Data represents a single search result with SearchHit<T>. This object holds the entity via getContent() and hit metadata such as ID, index, score, sort values, inner hits, and highlight fields. Multiple SearchHit<T> instances are grouped in SearchHits<T>, which also holds total hits, total hits relation, max score, aggregations, and suggest results.

~~~text
Search API response
       |
       v
SearchHits<Product>
       |
       +---- SearchHit<Product> #1
       |          |
       |          +-- getContent()        -> Product from _source
       |          +-- getId()             -> document ID
       |          +-- getScore()          -> relevance score
       |          +-- getHighlightFields()-> Map<field, fragments>
       |
       +---- SearchHit<Product> #2
                  |
                  +-- getContent()
                  +-- getHighlightFields()
~~~

Do not expect highlight fragments to automatically become properties of the entity. They are metadata on the search result and must be read from SearchHit.

## 2. Declaring the Entity and Repository

Example using the products index with two text fields title and description:

~~~java
package com.example.catalog.domain;

import org.springframework.data.annotation.Id;
import org.springframework.data.elasticsearch.annotations.Document;
import org.springframework.data.elasticsearch.annotations.Field;
import org.springframework.data.elasticsearch.annotations.FieldType;

@Document(indexName = "products")
public class Product {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String title;

    @Field(type = FieldType.Text)
    private String description;

    @Field(type = FieldType.Keyword)
    private String category;

    public Product() {
    }

    public Product(String id, String title, String description, String category) {
        this.id = id;
        this.title = title;
        this.description = description;
        this.category = category;
    }

    public String getId() {
        return id;
    }

    public String getTitle() {
        return title;
    }

    public String getDescription() {
        return description;
    }

    public String getCategory() {
        return category;
    }
}
~~~

The corresponding mapping can be inspected using the Elasticsearch API:

~~~http
GET products/_mapping
~~~

Highlighting is typically used on fields with text content such as text or keyword. The mapping must exist and data must be indexed with an analyzer compatible with the query. Enabling highlighting does not replace field mappings and does not by itself make a field searchable.

## 3. Enabling Highlighting with @Highlight

Spring Data Elasticsearch provides the @Highlight annotation to declare fields to highlight on a repository method. Each field is specified with @HighlightField.

~~~java
package com.example.catalog.repository;

import org.springframework.data.elasticsearch.annotations.Highlight;
import org.springframework.data.elasticsearch.annotations.HighlightField;
import org.springframework.data.elasticsearch.annotations.HighlightParameters;
import org.springframework.data.elasticsearch.core.SearchHits;
import org.springframework.data.elasticsearch.repository.ElasticsearchRepository;

import com.example.catalog.domain.Product;

public interface ProductRepository
        extends ElasticsearchRepository<Product, String> {

    @Highlight(fields = {
        @HighlightField(
            name = "title",
            parameters = @HighlightParameters(numberOfFragments = 0)
        ),
        @HighlightField(
            name = "description",
            parameters = @HighlightParameters(
                fragmentSize = 140,
                numberOfFragments = 3,
                order = "score"
            )
        )
    }, parameters = @HighlightParameters(
        preTags = {"<mark>"},
        postTags = {"</mark>"},
        encoder = "html"
    ))
    SearchHits<Product> findByTitleOrDescription(String title, String description);
}
~~~

Configuration explanation:

- @Highlight(fields = ...) selects the fields for which fragments should be returned.
- @HighlightField(name = "title") requests highlighting the title property.
- numberOfFragments = 0 returns the entire title field content rather than splitting it into fragments.
- fragmentSize = 140 requests description fragments with a target size of around 140 characters.
- numberOfFragments = 3 limits the number of returned description fragments.
- order = "score" requests ordering fragments by relevance.
- preTags and postTags specify the tags wrapping highlighted terms.
- encoder = "html" requests HTML-encoding fragment content before adding highlight tags.

The name in @HighlightField.name is the entity property name, not a renamed field name in the Elasticsearch mapping. If you use @Field(name = "product_title") on the Java property title, the highlight annotation still references the title property. When reading the map from SearchHit, check the actual keys in the response if the mapping uses custom field names.

The method above returns SearchHits<Product>, allowing the application to read both the entity and highlight metadata. Spring Data also supports forms like List<SearchHit<Product>>; if only List<Product> is returned, the application no longer has SearchHit objects to access each hit's metadata.

### 3.1. Calling the Repository Method

~~~java
SearchHits<Product> hits = repository.findByTitleOrDescription(
        "wireless keyboard",
        "wireless keyboard");
~~~

Spring Data generates the search request from the query method and adds the highlight configuration from the annotations. In this example, the query searches by title or description; the highlighter produces fragments for the declared fields.

To avoid confusion between parameter names and search intent, in real applications you can use @Query to explicitly declare the Query DSL, while still combining @Highlight on the same method:

~~~java
import org.springframework.data.elasticsearch.annotations.Query;

@Query("""
    {
      "multi_match": {
        "query": "?0",
        "fields": ["title", "description"]
      }
    }
    """)
@Highlight(fields = {
    @HighlightField(name = "title"),
    @HighlightField(name = "description")
})
SearchHits<Product> searchHighlighted(String text);
~~~

@Query describes the query clause; @Highlight describes the highlight portion of the search request. The two configurations handle two distinct parts of the request.

## 4. Reading Fragments from SearchHit

After receiving SearchHits<Product>, iterate through the SearchHit<Product> elements:

~~~java
import org.springframework.data.elasticsearch.core.SearchHit;
import org.springframework.data.elasticsearch.core.SearchHits;

SearchHits<Product> hits = repository.searchHighlighted("wireless keyboard");

for (SearchHit<Product> hit : hits) {
    Product product = hit.getContent();

    String id = hit.getId();
    float score = hit.getScore();

    List<String> titleFragments = hit.getHighlightField("title");
    List<String> descriptionFragments = hit.getHighlightField("description");

    System.out.println(id + " / " + score);
    System.out.println("Title: " + titleFragments);
    System.out.println("Description: " + descriptionFragments);
}
~~~

Two key methods:

~~~java
Map<String, List<String>> getHighlightFields();
List<String> getHighlightField(String field);
~~~

getHighlightFields() returns a map from field name to list of fragments. Per the SearchHit API, this map is never null. getHighlightField(field) returns the list of fragments for a single field; the list can be empty, but is never null.

Example reading the entire map:

~~~java
Map<String, List<String>> highlightFields = hit.getHighlightFields();

highlightFields.forEach((field, fragments) -> {
    System.out.println("Field: " + field);
    fragments.forEach(System.out::println);
});
~~~

Example output:

~~~text
Field: title
  <mark>Wireless</mark> Keyboard
Field: description
  A compact <mark>wireless</mark> keyboard for travel.
  The keyboard connects through Bluetooth.
~~~

A field may not appear in the map if there are no matching fragments or the field was not requested for highlighting. Do not directly access map.get("title").get(0) without checking that the list has elements.

## 5. Distinguishing Original Content from Highlight Fragments

hit.getContent() returns the entity mapped from the document source. hit.getHighlightField("title") returns the highlight segments generated by Elasticsearch. These two values can differ in length and structure:

| Value | Source | Content |
|---|---|---|
| hit.getContent().getTitle() | _source | Full original title, without highlight tags |
| hit.getHighlightField("title") | Search response highlight | One or more fragments with highlight tags |
| hit.getScore() | Search metadata | Document relevance score |
| hit.getId() | Search metadata | Document ID |

Fragments do not necessarily contain the entire field. For long fields, Elasticsearch usually cuts segments around matched terms. If you need to display the full content, keep the original field and use fragments separately for preview.

Example:

~~~java
Product source = hit.getContent();
String originalTitle = source.getTitle();
List<String> highlightedTitle = hit.getHighlightField("title");

String displayTitle = highlightedTitle.isEmpty()
        ? originalTitle
        : highlightedTitle.get(0);
~~~

The code uses the original title as a fallback if there are no highlight fragments. This is safer than assuming every hit has highlights for every field.

## 6. Mapping SearchHit to a DTO

In a REST API, do not return SearchHit<Product> directly if the API contract only needs a stable result structure. Create a DTO that clearly describes the original data, highlight fragments, and score.

### 6.1. Defining the DTO

~~~java
package com.example.catalog.api.dto;

import java.util.List;

public record ProductSearchResult(
        String id,
        String title,
        String description,
        List<String> titleHighlights,
        List<String> descriptionHighlights,
        float score) {
}
~~~

The DTO has two content layers:

- title, description: original values taken from the entity.
- titleHighlights, descriptionHighlights: fragments returned by Elasticsearch.

Keeping both types of data separate lets the client decide whether to display the full content, preview fragments, or per-field highlights.

### 6.2. Writing a Mapper from a Single SearchHit

~~~java
import org.springframework.data.elasticsearch.core.SearchHit;

import com.example.catalog.api.dto.ProductSearchResult;
import com.example.catalog.domain.Product;

public final class ProductSearchMapper {

    private ProductSearchMapper() {
    }

    public static ProductSearchResult toDto(SearchHit<Product> hit) {
        Product product = hit.getContent();

        return new ProductSearchResult(
                hit.getId(),
                product.getTitle(),
                product.getDescription(),
                hit.getHighlightField("title"),
                hit.getHighlightField("description"),
                hit.getScore());
    }
}
~~~

The mapper only reads highlights from SearchHit; it does not write fragments onto the entity. If the DTO uses a List, Spring Data already returns an empty list when a field has no fragments, so no manual null check is needed for getHighlightField.

### 6.3. Mapping All SearchHits

~~~java
import java.util.List;

import org.springframework.data.elasticsearch.core.SearchHits;

public List<ProductSearchResult> toDtos(SearchHits<Product> hits) {
    return hits.getSearchHits().stream()
            .map(ProductSearchMapper::toDto)
            .toList();
}
~~~

If the project uses Java 8 through Java 15, replace .toList() with .collect(Collectors.toList()):

~~~java
return hits.getSearchHits().stream()
        .map(ProductSearchMapper::toDto)
        .collect(Collectors.toList());
~~~

If the API needs to return total hits or pagination info, you can create a higher-level response DTO:

~~~java
public record ProductSearchResponse(
        List<ProductSearchResult> items,
        long totalHits,
        float maxScore) {
}
~~~

Mapper:

~~~java
public ProductSearchResponse toResponse(SearchHits<Product> hits) {
    List<ProductSearchResult> items = hits.getSearchHits().stream()
            .map(ProductSearchMapper::toDto)
            .toList();

    return new ProductSearchResponse(
            items,
            hits.getTotalHits(),
            hits.getMaxScore());
}
~~~

SearchHits contains information for the whole search response, while each SearchHit contains the data and metadata of a single document. When building an API, decide which metadata actually needs to be exposed instead of returning Spring Data's internal structures directly.

## 7. Creating a DTO with Display Content Only

Some APIs do not need to return the full original content; they only need an ID, display title, and snippet. A shorter DTO can be created:

~~~java
public record ProductSuggestion(
        String id,
        String displayTitle,
        String snippet,
        float score) {
}
~~~

The mapper picks the first fragment and uses the original content as a fallback:

~~~java
public static ProductSuggestion toSuggestion(SearchHit<Product> hit) {
    Product product = hit.getContent();

    String displayTitle = hit.getHighlightField("title").stream()
            .findFirst()
            .orElse(product.getTitle());

    String snippet = hit.getHighlightField("description").stream()
            .findFirst()
            .orElse(product.getDescription());

    return new ProductSuggestion(
            hit.getId(),
            displayTitle,
            snippet,
            hit.getScore());
}
~~~

If the highlighter returns multiple fragments, do not arbitrarily join them all with a space. Each fragment may come from a different location in the original content. Keep List<String> if the UI needs to display multiple excerpts or let users expand results.

## 8. Mapping When Already Using MapStruct or a Dedicated Entity Mapper

If the project already has a mapper converting Product into ProductDto, you can reuse that mapper and add SearchHit metadata in the search mapper layer:

~~~java
public record ProductSearchDto(
        ProductDto product,
        Map<String, List<String>> highlights,
        float score,
        String documentId) {
}
~~~

~~~java
public ProductSearchDto toSearchDto(SearchHit<Product> hit) {
    ProductDto productDto = productMapper.toDto(hit.getContent());

    return new ProductSearchDto(
            productDto,
            hit.getHighlightFields(),
            hit.getScore(),
            hit.getId());
}
~~~

This keeps the existing entity mapper independent of Elasticsearch search metadata. If the public DTO should not depend on internal field names, convert the highlight map into explicit properties such as titleFragments and descriptionFragments rather than returning a generic map.

## 9. Configuring Highlighting with ElasticsearchOperations

When queries are built dynamically in a service, highlighting can be configured using HighlightQuery instead of annotations on a repository method.

Spring Data Elasticsearch provides classes in the org.springframework.data.elasticsearch.core.query.highlight package:

- Highlight: holds the list of fields to highlight and common parameters.
- HighlightField: identifies a field to highlight.
- HighlightParameters: holds tags, fragment size, fragment count, encoder, and common parameters.
- HighlightQuery: associates the highlight definition with an entity type.

Example:

~~~java
import java.util.List;

import org.springframework.data.elasticsearch.core.ElasticsearchOperations;
import org.springframework.data.elasticsearch.core.SearchHits;
import org.springframework.data.elasticsearch.core.mapping.IndexCoordinates;
import org.springframework.data.elasticsearch.core.query.Criteria;
import org.springframework.data.elasticsearch.core.query.CriteriaQuery;
import org.springframework.data.elasticsearch.core.query.HighlightQuery;
import org.springframework.data.elasticsearch.core.query.highlight.Highlight;
import org.springframework.data.elasticsearch.core.query.highlight.HighlightField;
import org.springframework.data.elasticsearch.core.query.highlight.HighlightParameters;

public SearchHits<Product> searchWithHighlight(
        ElasticsearchOperations operations,
        String text) {

    HighlightParameters parameters = HighlightParameters.builder()
            .withPreTags("<mark>")
            .withPostTags("</mark>")
            .withEncoder("html")
            .withFragmentSize(140)
            .withNumberOfFragments(3)
            .build();

    Highlight highlight = new Highlight(
            parameters,
            List.of(
                    new HighlightField("title"),
                    new HighlightField("description")));

    HighlightQuery highlightQuery = new HighlightQuery(highlight, Product.class);

    CriteriaQuery query = new CriteriaQuery(
            Criteria.where("title").matches(text));
    query.setHighlightQuery(highlightQuery);

    return operations.search(
            query,
            Product.class,
            IndexCoordinates.of("products"));
}
~~~

HighlightParameters.builder() creates the common parameters. Highlight combines the parameters with the list of fields. HighlightQuery binds the configuration to the Product entity, and setHighlightQuery adds it to the query executed through ElasticsearchOperations.

This API is useful when the list of fields or highlight options depends on the request. If there is only a single fixed configuration, @Highlight on a repository method is usually shorter and easier to read.

## 10. Commonly Used Highlight Parameters

Elasticsearch has many options controlling how fragments are built. Spring Data exposes many of these via @HighlightParameters and the HighlightParameters/HighlightFieldParameters builders.

| Parameter | Effect |
|---|---|
| preTags | Tag placed before matched segments, typically `<em>` by default |
| postTags | Tag placed after matched segments, typically `</em>` by default |
| fragmentSize | Target fragment size in characters |
| numberOfFragments | Maximum number of fragments returned for the field |
| numberOfFragments = 0 | Return the entire field content instead of splitting into fragments |
| noMatchSize | Return an opening segment of the field when there are no matching fragments |
| order = "score" | Sort fragments by relevance score |
| requireFieldMatch | Defaults to true, only highlights fields with corresponding matches |
| type | Choose a highlighter such as unified, plain, or fvh |
| encoder | html to encode fragment content before adding highlight tags |
| matchedFields | Combine matches from multiple fields to highlight a target field, depending on highlighter |
| highlightQuery | Use a separate query to decide which content gets highlighted |

Corresponding REST request example:

~~~http
GET products/_search
{
  "query": {
    "multi_match": {
      "query": "wireless keyboard",
      "fields": ["title", "description"]
    }
  },
  "highlight": {
    "pre_tags": ["<mark>"],
    "post_tags": ["</mark>"],
    "encoder": "html",
    "fields": {
      "title": {
        "number_of_fragments": 0
      },
      "description": {
        "fragment_size": 140,
        "number_of_fragments": 3,
        "order": "score"
      }
    }
  }
}
~~~

### 10.1. When to Use number_of_fragments = 0?

For short fields like title, address, or name, splitting into fragments may be unnecessary. number_of_fragments: 0 requests returning the entire highlighted field content; in that case fragment_size is ignored.

For long descriptions, set fragment_size and number_of_fragments to return only a few relevant excerpts. This reduces response size and avoids sending the entire long content to the client.

### 10.2. no_match_size

By default, if there are no matching fragments, Elasticsearch returns no highlight content for that field. no_match_size lets you return a segment from the start of the field as a preview even if no terms are highlighted.

A no_match_size segment does not mean the field matched the query. If the DTO falls back from fragments to source, distinguish truly highlighted fragments from untagged previews.

### 10.3. require_field_match

By default require_field_match = true: a field needs a corresponding match to be highlighted. Setting false can tell the highlighter to look for query terms on the specified fields more broadly.

Do not set false just to “have highlights on every field”. It can generate fragments that do not reflect the field or search logic the application intends to present. Verify results with real queries.

## 11. Highlighter Types

Elasticsearch supports the main highlighters:

| Highlighter | Characteristics | Notes |
|---|---|---|
| unified | Uses Lucene Unified Highlighter; default for text and keyword | Supports phrase and multi-term queries; usually a good default |
| plain | Uses traditional Lucene Highlighter | Suits simple queries; can take extra time when processing many fields/documents |
| fvh | Fast Vector Highlighter | Requires term_vector: with_positions_offsets, increasing index size |
| semantic | For semantic/semantic_text fields | Creates fragments by semantic similarity; differs from traditional term highlighting |

With fvh, the mapping needs term vectors enabled:

~~~json
{
  "mappings": {
    "properties": {
      "description": {
        "type": "text",
        "term_vector": "with_positions_offsets"
      }
    }
  }
}
~~~

The unified highlighter can use offsets from postings if the mapping sets index_options: offsets, or use term vectors if present. For large content, the choice of offset strategy can affect performance and index size. Do not enable term vectors on every field just to try a highlighter; benchmark and choose based on workload.

## 12. Highlighting Does Not Alter Entities or Match Results

Highlighting is presentation data, not data stored back into the index. It does not change _source, does not modify entities, and does not affect whether a document matches the query.

Several consequences:

- The entity in hit.getContent() still holds the original content.
- Highlight fragments exist only in search hit metadata.
- If highlighting is not enabled for a field, getHighlightField(field) may return an empty list.
- Highlighting is not a form of score; scores still come from hit.getScore().
- Do not save tagged fragments into the database as the product's original content.

In particular, the highlighter does not always fully reflect the Boolean logic of a query. For complex queries such as nested bool or minimum_should_match, some terms may be highlighted even if that segment does not correspond to the full Boolean condition that matched the document. If the UI needs to explain exactly why a document matched, use the Explain API; do not rely on highlighting as sole proof of match logic.

## 13. Protecting Highlight Content When Rendering HTML

Highlight fragments often contain tags such as <em>...</em> or custom tags from preTags/postTags. Original content in _source may come from users or external sources. Never assume every fragment string is safe to pass directly into innerHTML or raw HTML rendering mechanisms.

Options:

1. Use encoder = "html" so the highlighter encodes content before inserting highlight tags.
2. If rendering HTML, allow only the defined highlight tags using an allow-list HTML sanitizer.
3. If the UI can handle structured data, convert fragments into plain text segments and matched segments, then render with safe text nodes/components.
4. Do not let users arbitrarily control preTags or postTags.

Example configuring encoder in an annotation:

~~~java
@Highlight(
    fields = @HighlightField(name = "description"),
    parameters = @HighlightParameters(
        preTags = {"<mark>"},
        postTags = {"</mark>"},
        encoder = "html"
    )
)
SearchHits<Product> searchDescription(String text);
~~~

encoder = "html" helps encode fragment content before adding tags. On the frontend, still apply safe HTML rendering rules of the framework and application, especially when content comes from multiple sources.

## 14. Highlighting for Multi-fields and Nested Data

### 14.1. Multi-fields

A property can be indexed into multiple subfields, such as title as text and title.keyword as keyword. When needing to combine matches from multiple analyzed fields to highlight one field, Elasticsearch has the matched_fields option where supported by the highlighter.

Example REST configuration:

~~~json
{
  "highlight": {
    "fields": {
      "title": {
        "matched_fields": ["title", "title.english"]
      }
    }
  }
}
~~~

Combination capabilities and mapping conditions depend on the highlighter. With fvh, combined fields must have suitable term vectors. Spring Data exposes matchedFields via highlight field parameters in current versions; if complex structures are needed, check the Javadoc and actual requests.

### 14.2. Nested Objects and Inner Hits

If a field resides inside an object with a nested mapping, the query typically uses a nested query and highlighting can be configured inside inner_hits. Nested results are returned in the inner hits metadata of the parent document.

Spring Data SearchHit provides getInnerHits() and getInnerHits(name). The return value is SearchHits<?> for the inner hits; if the inner hit is mapped to a nested entity, content may be that entity type, otherwise it may be SearchDocument.

When a DTO needs fragments of a nested field, you must read the SearchHit inside the corresponding inner hits instead of looking for that fragment in the parent document-level highlight map. The inner hit name and content type must match the query configuration.

## 15. Mapping DTOs with Nested Inner Hits

Suppose a document has nested comments and the query returns inner hits named matchingComments:

~~~json
{
  "query": {
    "nested": {
      "path": "comments",
      "query": {
        "match": {
          "comments.text": "wireless"
        }
      },
      "inner_hits": {
        "name": "matchingComments",
        "highlight": {
          "fields": {
            "comments.text": {}
          }
        }
      }
    }
  }
}
~~~

At the Spring Data layer, read inner hits by the declared name:

~~~java
SearchHits<?> innerHits = parentHit.getInnerHits("matchingComments");

if (innerHits != null) {
    for (SearchHit<?> innerHit : innerHits) {
        Map<String, List<String>> highlights = innerHit.getHighlightFields();
        // Map nested content and its highlight fragments to a nested DTO.
    }
}
~~~

This is an advanced case; if only highlighting top-level fields, inner hits handling is not needed. When implementing nested DTOs, check the mapping and actual response because content types depend on entity mapping and query configuration.

## 16. Why Are Highlights Missing?

If getHighlightField("title") returns an empty list, check in order:

1. Is highlighting enabled on the repository method or Query?
2. Is the field included in @HighlightField/Highlight.fields?
3. Does the query actually match that field, especially when require_field_match defaults to true?
4. Is the field name used in the annotation the entity's property name?
5. Is the field mapping a highlighter-supported type with indexed content?
6. Do the query analyzer and index analyzer produce matching tokens?
7. Is there a separate highlight_query changing the match condition?
8. Is the field too long and exceeding index.highlight.max_analyzed_offset?
9. Does the query return inner hits, causing highlights to reside on nested hits?
10. Are you returning SearchHit/SearchHits or only entities and losing metadata?

You can inspect the equivalent REST request/response to determine whether the issue is in Elasticsearch or in Spring Data's mapping step. If Elasticsearch returns highlights but the DTO is empty, inspect the keys in hit.getHighlightFields() and the mapper.

## 17. Testing Highlight Reading and DTO Mapping

An integration test should verify both parts: entity content and highlight metadata.

Illustrative test example:

~~~java
@Test
void returnsProductWithHighlightFragments() {
    repository.save(new Product(
            "p-100",
            "Wireless Keyboard",
            "A compact wireless keyboard for travel.",
            "keyboards"));

    // Ensure the document is visible to search before asserting.
    SearchHits<Product> hits = repository.searchHighlighted("wireless");

    assertThat(hits.getSearchHits()).isNotEmpty();

    SearchHit<Product> hit = hits.getSearchHit(0);
    assertThat(hit.getContent().getTitle()).isEqualTo("Wireless Keyboard");
    assertThat(hit.getHighlightField("title")).isNotEmpty();

    ProductSearchResult dto = ProductSearchMapper.toDto(hit);
    assertThat(dto.title()).isEqualTo("Wireless Keyboard");
    assertThat(dto.titleHighlights()).isNotEmpty();
}
~~~

The test illustrates the verification flow; repository method names, index setup, and refresh handling must match your project configuration. Elasticsearch is a near-real-time system, so newly saved documents may not appear in search immediately until the shard is refreshed.

Scenarios to test:

- A field with one fragment.
- A field with multiple fragments.
- A field with no fragments and the mapper using fallback.
- A title field using number_of_fragments = 0.
- A long field split into segments according to fragment_size.
- Content with Vietnamese diacritics, HTML characters, and quotes.
- A query matching multiple fields while requesting highlight on only one field.
- Mapping with a custom field name.
- Nested query with inner hits and highlights.
- DTO keeping original content separate from highlighted fragments.

Mocking SearchHit can test mapper logic, but only integration tests against real Elasticsearch or Testcontainers can confirm the highlighter produces fragments properly according to mapping, analyzer, and Query DSL.

## 18. Designing a Service Returning Search DTOs

Repository calls and DTO mapping can be combined in a service:

~~~java
import java.util.List;

import org.springframework.data.elasticsearch.core.SearchHits;
import org.springframework.stereotype.Service;

@Service
public class ProductSearchService {

    private final ProductRepository repository;

    public ProductSearchService(ProductRepository repository) {
        this.repository = repository;
    }

    public ProductSearchResponse search(String text) {
        SearchHits<Product> hits = repository.searchHighlighted(text);

        List<ProductSearchResult> items = hits.getSearchHits().stream()
                .map(ProductSearchMapper::toDto)
                .toList();

        return new ProductSearchResponse(
                items,
                hits.getTotalHits(),
                hits.getMaxScore());
    }
}
~~~

The controller only needs to return the DTO:

~~~java
@RestController
@RequestMapping("/products")
public class ProductSearchController {

    private final ProductSearchService service;

    public ProductSearchController(ProductSearchService service) {
        this.service = service;
    }

    @GetMapping("/search")
    public ProductSearchResponse search(@RequestParam String q) {
        return service.search(q);
    }
}
~~~

The service is responsible for translating Elasticsearch metadata into the API contract. The controller does not need to know about SearchHit, SearchHits, or how Elasticsearch represents highlights.

## 19. Common Pitfalls

### Repository Returning Only List<Product>

Entities do not carry highlight metadata. Return SearchHits<Product> or List<SearchHit<Product>> when fragments need to be read.

### Looking for Highlights Inside the Entity

Highlights live on SearchHit, and are not automatically assigned onto Product. Retrieve the entity via hit.getContent() and fragments via hit.getHighlightField(...).

### Assuming getHighlightField Always Has at Least One Element

A field may have no fragments. Check isEmpty() or use stream().findFirst().orElse(fallback).

### Using the Wrong Field Name in @HighlightField

The annotation expects the entity property name, not a renamed field name in the Elasticsearch mapping. If using a custom mapping name, check the actual keys in the highlight map when reading.

### Writing Fragments into the Entity and Saving Back

Fragments are temporary presentation data. If assigned to the entity and saved, the application could persist HTML tags or truncated snippets into _source. Keep fragments in a separate DTO.

### Joining Fragments into a Single Paragraph

Each fragment may come from a different region of the content. Joining them can lose context and produce broken sentences. Keep the list or select appropriate fragments in the UI.

### Not Encoding or Sanitizing HTML Content

Fragments can contain document content and highlight tags. Configure an appropriate encoder and render safely on the frontend.

### Using number_of_fragments = 0 on Very Long Fields

This setting returns the entire field. Use it only for short fields; for long content, limit fragment count and fragment size.

### Highlight Differing from Bool Query Conditions

The highlighter may mark terms without reflecting the full Boolean logic of the query. Do not use highlights as the sole inference for why a document was returned.

### Testing Only the Mapper Without Testing Elasticsearch

Mapper tests do not verify that the highlighter generates fragments. Integration tests are needed to check the highlight request, mapping, analyzer, and actual response.

## 20. Implementation Workflow

When adding highlighting to a search API, follow this sequence:

1. Identify text fields to highlight and verify mappings/analyzers.
2. Enable highlighting with @Highlight for repository methods or HighlightQuery for dynamic queries.
3. Choose preTags, postTags, fragmentSize, numberOfFragments, and encoder according to the UI.
4. Use return type SearchHits<T> or List<SearchHit<T>> to retain metadata.
5. Read fragments with getHighlightField(field) or getHighlightFields().
6. Retrieve original data from getContent() and other metadata from SearchHit.
7. Map each hit to a DTO with separate properties for source content and highlight fragments.
8. Handle empty lists and fallbacks explicitly.
9. Keep fragments separate from the entity so tags/snippets are not written back to _source.
10. Encode/sanitize content before rendering HTML.
11. Test single fragment, multiple fragments, zero fragments, custom field names, and nested inner hits.
12. Measure response size and highlight cost on long fields before rolling out broadly.

## 21. Summary

Spring Data Elasticsearch places highlight fragments in the metadata of SearchHit<T>, readable via getHighlightFields() or getHighlightField(field). SearchHit.getContent() remains the entity mapped from _source; highlight fragments do not automatically become entity properties. Therefore, repository methods must return SearchHits<T> or SearchHit<T> when the application wants to retain highlight information.

To return data via a REST API, map each SearchHit into a DTO: extract ID, score, and original content from the hit/entity, then fetch the fragment list per field. Keep source content and highlight fragments separate, handle empty lists, and use appropriate fallbacks. @Highlight fits fixed repository queries; HighlightQuery with ElasticsearchOperations fits dynamically constructed queries. Configure fragments, highlighter, and encoder according to content, and handle HTML safely in the presentation layer.
