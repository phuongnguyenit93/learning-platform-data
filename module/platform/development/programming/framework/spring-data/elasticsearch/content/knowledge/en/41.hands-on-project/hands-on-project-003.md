# Adding Sorting, Pagination, and Highlighting to Search Results

A useful search feature needs to control result ordering, split results into pages, and highlight the content that matched the query. Spring Data Elasticsearch provides abstractions for building sorts, pageable queries, and reading metadata from search hits. Elasticsearch provides server-side semantics such as field sorting, offset pagination, search_after, and highlighting.

These three capabilities are related but serve distinct purposes:

- **Sorting** determines the order of results. Default search usually sorts by relevance score when the query performs scoring.
- **Pagination** limits the number of returned results and identifies the next position.
- **Highlighting** returns text fragments inside fields that matched the query so the UI can show why a document was found.

This lesson builds a complete search flow: accepting a request DTO, validating sort/page inputs, constructing queries with Spring Data Elasticsearch, retrieving SearchHits, mapping highlights and metadata into a response DTO, and testing edge cases. The final section explains when to switch from offset pagination to cursor pagination with search_after.

## 1. Overall Search Flow

A search endpoint should never let clients send arbitrary Elasticsearch field names or Query DSL. Clients choose business options exposed by the API; the server maps them to the corresponding query, sort, and highlight definitions.

~~~text
HTTP request
     |
     v
ProductSearchRequest
     |
     v
Validation + default values
     |
     v
ProductSearchCriteria
     |
     v
Query factory
     |
     +---- Query filters
     +---- Sort options
     +---- Pageable / cursor
     +---- Highlight fields
     |
     v
ElasticsearchOperations
     |
     v
SearchHits<Product>
     |
     v
Response mapper
     |
     +---- Product DTOs
     +---- Pagination metadata
     +---- Sort metadata
     +---- Highlight fragments
     |
     v
HTTP response
~~~

Separating these steps keeps the controller unaware of Elasticsearch Query DSL. When mappings or pagination strategies change, the API contract can remain stable.

## 2. Entity and Mapping for Sorting and Highlighting

Example product entity:

~~~java
@Document(indexName = "products")
public class Product {

    @Id
    private String id;

    @Field(type = FieldType.Text)
    private String name;

    @Field(type = FieldType.Text)
    private String description;

    @Field(type = FieldType.Keyword)
    private String status;

    @Field(type = FieldType.Keyword)
    private String category;

    @Field(type = FieldType.Double)
    private BigDecimal price;

    @Field(type = FieldType.Date)
    private Instant createdAt;

    // Used as a stable sort tie-breaker.
    @Field(type = FieldType.Keyword)
    private String productIdSort;

    // constructors, getters and setters
}
~~~

The corresponding mapping might include:

~~~json
{
  "properties": {
    "name": {
      "type": "text",
      "fields": {
        "keyword": {
          "type": "keyword"
        }
      }
    },
    "description": {
      "type": "text"
    },
    "status": {
      "type": "keyword"
    },
    "category": {
      "type": "keyword"
    },
    "price": {
      "type": "double"
    },
    "createdAt": {
      "type": "date"
    },
    "productIdSort": {
      "type": "keyword"
    }
  }
}
~~~

The name field is mapped as text for full-text search. The name.keyword subfield is used for exact matching or sorting by the full name. The price and createdAt fields suit numeric/date sorting. productIdSort is a unique keyword field used to guarantee stable ordering when documents share the same price or timestamp.

Do not sort directly on a text field whose tokens were generated by an analyzer. Elasticsearch generally requires fields with doc_values, such as keyword, numeric, or date. If you need to sort by name, use a keyword multi-field mapped from the start.

### Synchronizing the Tie-Breaker

If you use productIdSort, assign its value when creating the document and keep it stable:

~~~java
product.setProductIdSort(product.getId());
~~~

Do not rely on _id as a regular sort field. Elasticsearch has limitations on sorting by _id; use a dedicated keyword field with doc values when stable sorting is required.

Existing index mappings do not change automatically just because annotations were added to the entity. If a new multi-field or tie-breaker is needed, update the index template and create the appropriate index or migration.

## 3. Designing the Request DTO

Requests should use enums for sort fields and directions to restrict the options clients can request.

~~~java
public enum ProductSort {
    RELEVANCE,
    NAME,
    PRICE,
    CREATED_AT
}

public enum SortDirection {
    ASC,
    DESC
}
~~~

Request DTO:

~~~java
public record ProductSearchRequest(
    String query,
    String status,
    Integer page,
    Integer size,
    ProductSort sort,
    SortDirection direction,
    Boolean highlight
) {}
~~~

Normalize and validate inputs before building the query:

~~~java
public record ProductSearchCriteria(
    String query,
    String status,
    int page,
    int size,
    ProductSort sort,
    SortDirection direction,
    boolean highlight
) {}
~~~

~~~java
@Component
public class ProductSearchCriteriaMapper {

    private static final int DEFAULT_SIZE = 20;
    private static final int MAX_SIZE = 100;

    public ProductSearchCriteria toCriteria(
            ProductSearchRequest request) {

        int page = request.page() == null ? 0 : request.page();
        int size = request.size() == null
            ? DEFAULT_SIZE
            : request.size();

        if (page < 0) {
            throw new InvalidSearchRequestException(
                "page must be zero or greater"
            );
        }

        if (size < 1 || size > MAX_SIZE) {
            throw new InvalidSearchRequestException(
                "size must be between 1 and " + MAX_SIZE
            );
        }

        return new ProductSearchCriteria(
            normalize(request.query()),
            request.status(),
            page,
            size,
            request.sort() == null
                ? ProductSort.RELEVANCE
                : request.sort(),
            request.direction() == null
                ? SortDirection.DESC
                : request.direction(),
            Boolean.TRUE.equals(request.highlight())
        );
    }

    private String normalize(String value) {
        if (value == null || value.isBlank()) {
            return null;
        }
        return value.trim();
    }
}
~~~

You can use Bean Validation such as @Min, @Max, and @Size to reject invalid inputs at the controller boundary. Validation inside the criteria mapper remains helpful if criteria are constructed from multiple sources.

Never let clients submit raw sort fields such as internalSupplierCode or arbitrary script sorts. A public enum acts as an allowlist so the server controls fields and query cost.

## 4. Building Sorts from an Allowlist

Sort mapping translates the API enum to Elasticsearch fields:

~~~java
@Component
public class ProductSortMapper {

    public Sort toSpringSort(ProductSort field, SortDirection direction) {
        Sort.Direction order =
            direction == SortDirection.ASC
                ? Sort.Direction.ASC
                : Sort.Direction.DESC;

        return switch (field) {
            case NAME -> Sort.by(order, "name.keyword")
                .and(Sort.by(Sort.Direction.ASC, "productIdSort"));

            case PRICE -> Sort.by(order, "price")
                .and(Sort.by(Sort.Direction.ASC, "productIdSort"));

            case CREATED_AT -> Sort.by(order, "createdAt")
                .and(Sort.by(Sort.Direction.ASC, "productIdSort"));

            case RELEVANCE -> Sort.by(
                Sort.Order.desc("_score"),
                Sort.Order.asc("productIdSort")
            );
        };
    }
}
~~~

This example uses Spring Data Sort. How score sorting is represented and combined with field sorts should be verified on your specific release train. With NativeQuery, you can use Elasticsearch Java API Client SortOptions to specify _score and field sorts explicitly.

### Relevance Sort vs. Field Sort

- When sorting by _score, results prioritize documents that match the query better.
- When sorting by price, results follow price; score is no longer the primary criterion.
- When sorting by createdAt, results follow timestamps.
- A tie-breaker produces deterministic ordering when primary sort fields have equal values.

If the query is match_all or filter-only, scores carry no business meaning. Pick a default sort suited to the endpoint type.

### Missing Values

Documents may omit a field used for sorting. Elasticsearch provides a missing option to place documents lacking a value first or last. Establish an explicit policy for fields like price or createdAt.

If every document must have a price or creation timestamp, enforce it at write time and verify mapping/data quality. Do not let missing-value ordering become undocumented random behavior.

### Nested Sort

If sorting on a field inside a nested object, the query must declare a nested sort path and an appropriate filter. Sorting by a nested field is not equivalent to sorting by a regular object. Use it only when the domain requires ordering by a specific child object and add integration tests for the nested mapping.

## 5. Offset Pagination with Pageable

Spring Data uses Pageable to represent page index, page size, and sort.

~~~java
Pageable pageable = PageRequest.of(
    criteria.page(),
    criteria.size(),
    sortMapper.toSpringSort(
        criteria.sort(),
        criteria.direction()
    )
);
~~~

Page index starts at 0:

- page = 0, size = 20: requests the first 20 results.
- page = 1, size = 20: requests the next 20 results.
- page = 2, size = 20: requests the third page.

If the API exposes 1-based pages, convert them in the request mapper and follow the same convention in the response. Never let frontend and backend disagree on page index semantics.

### Using Pageable with a Repository

A derived query can accept Pageable:

~~~java
public interface ProductRepository
        extends ElasticsearchRepository<Product, String> {

    Page<Product> findByStatus(
        String status,
        Pageable pageable
    );
}
~~~

Caller:

~~~java
Page<Product> page = repository.findByStatus(
    "ACTIVE",
    pageable
);
~~~

Page is convenient when standard pagination abstraction suffices. However, for searches needing highlights, scores, aggregations, or Elasticsearch-specific metadata, use SearchHits/SearchPage or ElasticsearchOperations so metadata is not lost.

### Using Pageable with NativeQuery

~~~java
NativeQuery query = NativeQuery.builder()
    .withQuery(q -> q.bool(b -> b
        .filter(f -> f.term(t -> t
            .field("status")
            .value("ACTIVE")
        ))
    ))
    .withPageable(pageable)
    .build();

SearchHits<Product> hits =
    operations.search(query, Product.class);
~~~

NativeQuery combines Query DSL with pageable and other search options. Builder methods can vary across Spring Data Elasticsearch and Elasticsearch Java API Client versions.

## 6. How Does Elasticsearch Execute Offset Pagination?

Offset pagination uses two parameters:

- from: number of hits to skip before starting the page.
- size: maximum number of hits to return.

For example, the third page with 20 results per page:

~~~http
GET /products/_search
{
  "from": 40,
  "size": 20,
  "query": {
    "term": {
      "status": "ACTIVE"
    }
  },
  "sort": [
    {
      "price": "asc"
    },
    {
      "productIdSort": "asc"
    }
  ]
}
~~~

Elasticsearch must retain and process candidate results from shards to determine which hits fall within from to from + size. As the offset grows, CPU and memory cost rise.

### max_result_window

Elasticsearch normally caps from + size using index.max_result_window, commonly defaulting to 10,000. When a request exceeds this limit, Elasticsearch returns an error instead of allowing unbounded deep reads.

Do not raise the limit to a huge value as a default fix. Very deep pages usually indicate you should use search_after, cursors, or a dedicated export flow.

### When Is Offset Suitable?

- First pages and shallow pages.
- UIs that need to jump directly to a specific page number.
- Moderate dataset sizes and concurrency.
- Total hit counts that need to be displayed to users.

If users regularly browse through thousands of pages, cursor pagination is usually a better fit.

## 7. Total Hits and Pagination Metadata

SearchHits provides total hits and the total-hit relation depending on API/version. Elasticsearch does not always count every matching document exactly if the query configures a tracking limit.

A response DTO might look like:

~~~java
public record ProductSearchResponse(
    List<ProductSearchItem> items,
    PaginationMetadata pagination,
    SortMetadata sort
) {}

public record PaginationMetadata(
    int page,
    int size,
    int returned,
    Long totalHits,
    String totalHitsRelation,
    Boolean hasNext
) {}

public record SortMetadata(
    ProductSort field,
    SortDirection direction
) {}
~~~

Mapping the result:

~~~java
private PaginationMetadata toPagination(
        SearchHits<Product> hits,
        ProductSearchCriteria criteria) {

    long total = hits.getTotalHits();
    int returned = hits.getSearchHits().size();

    String relation = hits.getTotalHitsRelation().name();

    Boolean hasNext = relation.equals("EQUAL_TO")
        ? (long) (criteria.page() + 1) * criteria.size() < total
        : null;

    return new PaginationMetadata(
        criteria.page(),
        criteria.size(),
        returned,
        total,
        relation,
        hasNext
    );
}
~~~

The enum/method name getTotalHitsRelation() and relation values must match your Spring Data version. If the API in your version does not expose the relation, do not assume the total is exact.

### Track Total Hits

If the API requires an exact result count, configure track total hits in the query. Exact counting is more expensive on large datasets. If the UI only needs to know whether more results exist, you can fetch one extra hit or use a cursor instead of always counting everything.

The contract should distinguish:

- Exact total.
- Lower-bound total.
- Total not requested.
- Whether hasNext is exact or only an estimate.

Do not compute total pages from a lower-bound total and present it as an exact page count.

## 8. How Does Highlighting Work?

Highlighting returns text fragments containing parts that matched the query. It helps the UI explain why a document appeared in results.

Example query:

~~~http
GET /products/_search
{
  "query": {
    "multi_match": {
      "query": "mechanical keyboard",
      "fields": ["name", "description"]
    }
  },
  "highlight": {
    "pre_tags": ["<em>"],
    "post_tags": ["</em>"],
    "fields": {
      "name": {
        "number_of_fragments": 0
      },
      "description": {
        "fragment_size": 140,
        "number_of_fragments": 2
      }
    }
  }
}
~~~

The response may contain:

~~~json
{
  "hits": {
    "hits": [
      {
        "_id": "P-100",
        "_source": {
          "name": "Wireless mechanical keyboard"
        },
        "highlight": {
          "name": [
            "Wireless <em>mechanical keyboard</em>"
          ],
          "description": [
            "This <em>mechanical keyboard</em> product is great for work..."
          ]
        }
      }
    ]
  }
}
~~~

Highlighting does not modify _source. It is additional metadata attached to each search hit.

### Highlighting Is Not a General Snippet Generator

The highlighter operates based on the query and requested fields. It does not rewrite paragraphs, summarize documents, or guarantee that every semantic synonym is marked.

With vector-only queries, highlights may be absent or fail to reflect why a semantic match occurred as users expect. If hybrid search needs highlights, you typically need an accompanying lexical query or a separate snippet mechanism.

## 9. Selecting Fields and Fragments for Highlighting

Do not highlight every field in a document. Choose fields meaningful for display:

- name: often returned in full using number_of_fragments = 0.
- description: returns a few length-bounded fragments.
- categoryText: can be highlighted if the UI needs it.
- Internal or sensitive fields: never highlight and never include in the response.

Common options:

| Option | Meaning |
|---|---|
| pre_tags | Marker placed before the match |
| post_tags | Marker placed after the match |
| fragment_size | Target fragment size |
| number_of_fragments | Maximum number of fragments |
| no_match_size | Number of characters returned when no fragment matches, if configured |
| encoder | How fragments are encoded as supported by highlighter/version |

Fragment size is a target for the highlighter, not an absolute character cap in all cases. Short fields may return the entire content.

### Unified, Plain, and Postings Highlighters

Elasticsearch provides multiple highlighter implementations:

- **Unified highlighter:** common default supporting many query types and fields.
- **Plain highlighter:** suitable for simple cases but can be costly when re-analyzing content.
- **Postings highlighter:** can be efficient when mappings store appropriate term vectors or postings.

Select a highlighter based on mapping, query types, field sizes, and benchmarks. There is no need to replace the default highlighter without evidence of performance or fragment-quality issues.

## 10. Using HighlightQuery in Spring Data Elasticsearch

Spring Data Elasticsearch provides the HighlightQuery abstraction and Highlight/HighlightField types in appropriate releases. Illustrative example:

~~~java
HighlightField nameField =
    new HighlightField("name");

HighlightField descriptionField =
    new HighlightField("description");

Highlight highlight = new Highlight(
    List.of(nameField, descriptionField)
);

HighlightQuery highlightQuery =
    new HighlightQuery(highlight, Product.class);
~~~

Constructors and HighlightField builders depend on version, especially when configuring fragment size, tags, and highlighter type. Use the API present in your installed dependency.

With NativeQuery, some releases allow attaching HighlightQuery to the builder; others may require building the query with the Elasticsearch Java API Client or different configuration. When fine-grained options are needed, a direct client request can be clearer.

Example using the Java API Client at the request level:

~~~java
SearchResponse<Product> response = client.search(s -> s
    .index("products")
    .query(q -> q.multiMatch(m -> m
        .query(searchText)
        .fields("name", "description")
    ))
    .highlight(h -> h
        .preTags("<em>")
        .postTags("</em>")
        .fields("name", f -> f
            .numberOfFragments(0)
        )
        .fields("description", f -> f
            .fragmentSize(140)
            .numberOfFragments(2)
        )
    ),
    Product.class
);
~~~

This Java API Client snippet illustrates passing highlight options. Builder methods must match your client version. If the app uses Spring Data Operations, you can isolate the direct client inside a gateway instead of letting controllers call the client directly.

## 11. Reading Highlights from SearchHit

When using Spring Data ElasticsearchOperations, search results preserve highlight metadata inside each SearchHit.

~~~java
SearchHits<Product> hits =
    operations.search(query, Product.class);

for (SearchHit<Product> hit : hits) {
    Product product = hit.getContent();

    Map<String, List<String>> highlights =
        hit.getHighlightFields();

    // Map content and highlights to response DTO.
}
~~~

getHighlightFields() typically returns a map from field name to a list of fragments. If the query did not request highlights or a field has no matching fragments, the map may be empty or omit that field.

Do not read highlights from entity properties. Highlights belong to SearchHit metadata; keeping only hit.getContent() and discarding SearchHit drops them.

### Response DTO

~~~java
public record ProductSearchItem(
    String id,
    String name,
    BigDecimal price,
    Map<String, List<String>> highlights
) {}
~~~

Mapper:

~~~java
private ProductSearchItem toItem(SearchHit<Product> hit) {
    Product product = hit.getContent();

    return new ProductSearchItem(
        product.getId(),
        product.getName(),
        product.getPrice(),
        hit.getHighlightFields()
    );
}
~~~

You can filter to only fields permitted in the response:

~~~java
private Map<String, List<String>> publicHighlights(
        SearchHit<Product> hit) {

    Map<String, List<String>> source =
        hit.getHighlightFields();

    Map<String, List<String>> result = new LinkedHashMap<>();

    for (String field : List.of("name", "description")) {
        List<String> fragments = source.get(field);
        if (fragments != null && !fragments.isEmpty()) {
            result.put(field, fragments);
        }
    }

    return result;
}
~~~

This prevents accidentally leaking highlights from internal fields if the query builder is later expanded.

## 12. Protecting the Frontend When Rendering Highlights

The highlight examples use em as markers. If the frontend inserts fragments directly into innerHTML without controls, the original document text could contain malicious HTML or scripts.

Guidelines:

- Allow only marker tags from an allowlist such as em or strong.
- Escape original content before rendering.
- Use an appropriate sanitizer if HTML must be rendered.
- Or return plain-text fragments alongside offset/token metadata so the frontend highlights safely.
- Never assume the highlighter automatically sanitizes all source content.

Highlights come from indexed document content. If data originates from users or external systems, treat it as untrusted input.

### Custom Markers

You can use non-HTML custom markers such as [[ and ]], then have the frontend parse them into safe text nodes and elements. Ensure markers cannot appear naturally or have an explicit escaping mechanism.

## 13. Combining Sort, Pagination, and Highlighting in NativeQuery

A single query can include all three capabilities. Example REST DSL structure:

~~~http
GET /products/_search
{
  "from": 0,
  "size": 20,
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query": "mechanical keyboard",
            "fields": ["name^3", "description"]
          }
        }
      ],
      "filter": [
        {
          "term": {
            "status": "ACTIVE"
          }
        }
      ]
    }
  },
  "sort": [
    {
      "_score": "desc"
    },
    {
      "productIdSort": "asc"
    }
  ],
  "highlight": {
    "pre_tags": ["<em>"],
    "post_tags": ["</em>"],
    "fields": {
      "name": {
        "number_of_fragments": 0
      },
      "description": {
        "fragment_size": 140,
        "number_of_fragments": 2
      }
    }
  },
  "track_total_hits": true
}
~~~

In Spring Data, you can use NativeQuery with the query, pageable, sort, and highlight options supported by your version:

~~~java
NativeQuery query = NativeQuery.builder()
    .withQuery(q -> q.bool(b -> b
        .must(m -> m.multiMatch(mm -> mm
            .query(criteria.query())
            .fields("name^3", "description")
        ))
        .filter(f -> f.term(t -> t
            .field("status")
            .value("ACTIVE")
        ))
    ))
    .withPageable(pageable)
    .build();

SearchHits<Product> hits =
    operations.search(query, Product.class);
~~~

This is a skeleton for the query and pageable. Sorting can be passed via Pageable or withSort depending on usage; highlighting can attach HighlightQuery if supported by your Spring Data release. Check the API signatures in your dependency and verify the final JSON matches the intended DSL.

If you need exact control over every Elasticsearch option, use the Java API Client directly inside a gateway while still returning a unified application DTO.

## 14. Relevance Sort and Field Sort Have Different Semantics

When a search query contains a full-text clause, _score represents relevance. When sorting by price or date, Elasticsearch orders by that field; do not assume results remain ordered by relevance.

Examples:

- Search "mechanical keyboard" + sort PRICE ASC: cheaper products appear first among matching results.
- Search "mechanical keyboard" + sort RELEVANCE DESC: better-matching products appear first.
- Filter status ACTIVE + sort CREATED_AT DESC: newest products appear first even without a full-text query.

Response metadata should reflect the client's chosen sort, such as PRICE ASC, rather than returning only raw sort field names.

### Combining Score with Field Sort

Elasticsearch allows multiple sort criteria in priority order. If the sort list is _score desc followed by price asc, score decides first; price only breaks ties. If the sort list is price asc followed by _score desc, price decides first.

The order of criteria matters greatly. Write tests to verify tie-breaking and business priority.

## 15. Stable Pagination and Tie-Breakers

If you sort only by price, multiple documents can share the same price. When data is indexed or updated while a user pages through results, the order among equal-priced documents can shift. This causes items to repeat or be skipped across pages.

Add a unique tie-breaker:

~~~json
"sort": [
  { "price": "asc" },
  { "productIdSort": "asc" }
]
~~~

A tie-breaker must:

- Have a value for every document that may be returned.
- Be unique within the index/query scope.
- Have a field type that supports efficient sorting.
- Not change arbitrarily after the document is indexed.

A keyword field with doc values is usually appropriate. Do not use an analyzed text field or a field with duplicate values when total ordering is required.

Stable sorting reduces non-deterministic ordering, though offset pagination can still drift when new documents are inserted before the offset. If you need consistent traversal over changing data, consider Point in Time (PIT) together with search_after.

## 16. Deep Pagination with search_after

search_after uses the sort values of the last hit on the current page as the starting point for the next page. It avoids skipping over huge offsets.

Example first-page request:

~~~http
GET /products/_search
{
  "size": 20,
  "query": {
    "term": {
      "status": "ACTIVE"
    }
  },
  "sort": [
    {
      "price": "asc"
    },
    {
      "productIdSort": "asc"
    }
  ]
}
~~~

The last hit may return sort values:

~~~json
{
  "_id": "P-100",
  "sort": [790000, "P-100"]
}
~~~

The next request passes those exact sort values:

~~~http
GET /products/_search
{
  "size": 20,
  "query": {
    "term": {
      "status": "ACTIVE"
    }
  },
  "sort": [
    {
      "price": "asc"
    },
    {
      "productIdSort": "asc"
    }
  ],
  "search_after": [790000, "P-100"]
}
~~~

Sort values must match the order and types of the sort criteria. Never fabricate a cursor solely from a document ID when the sort involves multiple fields.

### Cursor Response

You do not need to expose raw sort value arrays in the public contract. The server can encode them into an opaque token:

~~~json
{
  "items": [],
  "nextCursor": "eyJ2IjoxLCJzb3J0IjpbNzkwMDAwLCJQLTEwMF19"
}
~~~

A cursor should contain a payload version, sort values, and any context needed to continue the query. You can sign the token to detect client tampering. When receiving a cursor, the server must verify it belongs to the current filter, sort, and tenant context.

A cursor is not authorization. Every subsequent query must still enforce permissions and data filters.

## 17. Using Point in Time for Consistent Results

If data changes while a client pages through multiple pages, search_after pages can observe different snapshots. Point in Time (PIT) keeps a consistent view of the index for a bounded duration.

General flow:

1. Open a PIT on the index/alias.
2. Execute searches with the PIT and a stable sort.
3. Read the sort values of the last hit.
4. Send the next request with the same PIT and search_after.
5. Extend keep_alive while continuing.
6. Close the PIT when finished or expired.

PIT prevents many anomalies caused by concurrent changes between pages. It retains resources on the cluster, so keep_alive should be short enough and the PIT must be closed once no longer needed.

The PIT API and how PIT is passed through Spring Data/Java API Client depend on version. You may need the direct Java API Client inside a cursor gateway if the current abstraction does not expose everything required.

### PIT Is Not a Business Transaction

PIT maintains a read snapshot for search. It does not lock documents, does not guarantee newly inserted data after opening the PIT will appear during that browsing session, and does not replace database transactions.

If the user refreshes the search, open a new PIT to see current state.

## 18. search_after in a Spring Application

A cursor abstraction can hold the required state:

~~~java
public record ProductSearchCursor(
    List<Object> sortValues,
    String pointInTimeId
) {}
~~~

Response:

~~~java
public record CursorSearchResponse(
    List<ProductSearchItem> items,
    String nextCursor,
    boolean hasNext
) {}
~~~

Service flow:

~~~text
Decode and verify cursor
        |
        v
Restore PIT and search_after values
        |
        v
Build query with same filter and sort
        |
        v
Execute search
        |
        v
Map hits and last sort values
        |
        v
Encode next cursor
~~~

Never deserialize arbitrary Java objects or blindly trust client-sent tokens. Cursors should have an explicit schema/version, size bounds, and a signature if tamper protection is needed.

If a cursor embeds index/alias or tenant details, never let the token widen access scope. The server must still resolve the tenant from the authenticated principal and verify it matches the cursor context.

## 19. Sorting, Pagination, and Highlighting with Nested Fields

If a query searches nested objects and the response needs highlights on nested fields, configure the nested path consistently with the mapping and query. Highlighting nested fields has different semantics from root-level fields; inner hits may be required to identify which child object matched.

Example document with variants:

~~~json
{
  "name": "T-Shirt",
  "variants": [
    {
      "color": "black",
      "description": "Black cotton shirt"
    },
    {
      "color": "white",
      "description": "White linen shirt"
    }
  ]
}
~~~

If searching variants.description, the query must be a nested query on path variants. If the UI needs to show the exact matching variant, use inner hits and map the nested metadata appropriately.

Do not assume a highlight fragment on a nested field automatically identifies the entire child object. Preserve the child identifier or inner-hit metadata if the UI must associate the fragment with a specific variant.

Sorting by a nested field also requires a nested sort path and mode such as min/max depending on business logic. Test specifically with multiple children having different values to verify behavior.

## 20. Combining Tenant Filters and Sorting

In multi-tenant applications, every search path must scope by the authenticated tenant. Sorting does not replace filtering, and clients must never choose an arbitrary tenant.

Example query:

~~~http
GET /products/_search
{
  "from": 0,
  "size": 20,
  "query": {
    "bool": {
      "must": [
        {
          "match": {
            "name": "keyboard"
          }
        }
      ],
      "filter": [
        {
          "term": {
            "tenantId": "tenant-A"
          }
        }
      ]
    }
  },
  "sort": [
    {
      "price": "asc"
    },
    {
      "productIdSort": "asc"
    }
  ]
}
~~~

The tenantId in the example must come from the server-side security context. If a client passes a tenant ID in a query parameter, the service must verify authorization before using it.

When using tenant-based routing to reduce shard fan-out, still keep the tenant filter in the query. Routing is shard selection, not authorization or document filtering.

## 21. Handling Highlights When a Query Has Multiple Branches

A query can combine match, filter, synonym, phrase, or hybrid branches. Highlighting usually relies on lexical queries and specified fields.

Cases to consider:

- A field has no highlight even though the document matched via a vector branch.
- A query matches a synonym, while the fragment reflects original or analyzed tokens depending on the highlighter.
- A queried field produces no fragment due to analyzer or highlighter settings.
- A document produces many fragments, requiring a count limit.
- Phrase queries need appropriate phrase highlighting.
- Highlighting can increase response size and CPU cost.

If an API supports hybrid search, do not promise highlights on every vector-only hit. You can run a parallel lexical query to extract snippets or use a separate passage extraction step. Document clearly in the contract that highlights are optional.

## 22. Sample End-to-End Service

A service can coordinate criteria, sort, pageable, query, search, and response mapping:

~~~java
@Service
public class ProductSearchService {

    private final ElasticsearchOperations operations;
    private final ProductSearchCriteriaMapper criteriaMapper;
    private final ProductSortMapper sortMapper;

    public ProductSearchService(
            ElasticsearchOperations operations,
            ProductSearchCriteriaMapper criteriaMapper,
            ProductSortMapper sortMapper) {
        this.operations = operations;
        this.criteriaMapper = criteriaMapper;
        this.sortMapper = sortMapper;
    }

    public ProductSearchResponse search(
            ProductSearchRequest request) {

        ProductSearchCriteria criteria =
            criteriaMapper.toCriteria(request);

        Pageable pageable = PageRequest.of(
            criteria.page(),
            criteria.size(),
            sortMapper.toSpringSort(
                criteria.sort(),
                criteria.direction()
            )
        );

        NativeQuery query = NativeQuery.builder()
            .withQuery(q -> buildProductQuery(q, criteria))
            .withPageable(pageable)
            .build();

        SearchHits<Product> hits =
            operations.search(query, Product.class);

        return mapResponse(hits, criteria);
    }
}
~~~

buildProductQuery and mapResponse represent application-specific helper methods. In an actual implementation, highlight queries are attached via HighlightQuery or the Java API Client builder supported by your version.

Separate responsibilities into small components:

- Criteria mapper: defaults and validation.
- Sort mapper: enum to field allowlist.
- Query factory: full-text and filter conditions.
- Highlight factory: field and fragment options.
- Search gateway: calls Spring Data or Java API Client.
- Response mapper: content and metadata.
- Cursor codec: encodes/decodes cursors for deep pagination.

You do not need a separate class for every method in a small app; the goal is to keep controllers and services from turning into a tangle of query and mapping logic that is hard to test.

## 23. Testing Sorting

Test data should contain multiple documents sharing the same primary sort value to verify the tie-breaker.

Example seed:

| ID | Name | Price |
|---|---|---:|
| P-100 | Keyboard A | 500000 |
| P-200 | Keyboard B | 500000 |
| P-300 | Keyboard C | 700000 |

Testing ascending price:

~~~java
@Test
void sortsByPriceThenStableId() {
    ProductSearchResponse response =
        searchService.search(request(
            ProductSort.PRICE,
            SortDirection.ASC,
            0,
            20
        ));

    assertThat(response.items())
        .extracting(ProductSearchItem::id)
        .containsExactly("P-100", "P-200", "P-300");
}
~~~

The test must ensure productIdSort is seeded accordingly. If a query lacks a tie-breaker, do not assert ordering between two documents with identical prices.

Also test:

- Name sorting uses the keyword subfield.
- Created-date sorting respects direction.
- Relevance sorting prioritizes score.
- Missing values follow policy.
- Invalid sort enums from clients are rejected.
- Internal fields cannot be requested through the API.

## 24. Testing Pagination

Create at least 45 documents with deterministic ordering and page size 20:

- Page 0 returns the first 20 documents.
- Page 1 returns the next 20 documents.
- Page 2 returns the remaining 5 documents.
- No duplicates across pages when the dataset is unchanged.
- returned reflects the actual item count.
- totalHits and relation map accurately according to query configuration.
- hasNext is not miscalculated when total is a lower bound.

Example assertions:

~~~java
assertThat(firstPage.items()).hasSize(20);
assertThat(secondPage.items()).hasSize(20);
assertThat(thirdPage.items()).hasSize(5);

assertThat(firstPage.items())
    .extracting(ProductSearchItem::id)
    .doesNotContainAnyElementsOf(
        secondPage.items().stream()
            .map(ProductSearchItem::id)
            .toList()
    );
~~~

In integration tests, refresh the index after seeding data. If data mutates between requests, offset pages can shift; stable pagination tests should use a fixed dataset or test cursor/PIT separately.

## 25. Testing Highlighting

Seed a document containing the keyword in both name and description. Call search with highlighting enabled and verify:

- SearchHit contains fragments for configured fields.
- Response DTO includes the highlight map.
- Fields not requested for highlighting are absent.
- number_of_fragments limits the fragment count as configured.
- When highlighting is disabled, the response follows consistent semantics: field absent, null, or empty map per contract.
- The entity's original content is not altered by markers.

Avoid asserting an entire fragment string verbatim if analyzers or highlighters can produce minor differences across versions. Check that fragments contain the keyword and expected markers per test contract.

## 26. Testing Cursors and PIT

For search_after:

- The first page returns sort values for the last hit.
- The cursor is encoded from those values.
- The next page starts after the last hit with no duplicates.
- Tampered or wrong-version cursors are rejected.
- Cursors used across different tenants are rejected.
- Changing filters or sorts between requests invalidates the cursor per policy.
- Expired PITs return a clear error.
- PITs are closed when the client finishes or the session ends.

Do not assert that a specific document wins when two hits share identical sort values without a stable tie-breaker.

## 27. Common Pitfalls

| Symptom | Possible cause | Resolution |
|---|---|---|
| Sorting on text errors or behaves wrongly | Field lacks doc values | Use a keyword subfield or sortable field |
| Order changes between two pages | Sort lacks a unique tie-breaker | Add a keyword tie-breaker |
| Deep page rejected | Exceeds max_result_window | Use search_after/PIT |
| Total hits inaccurate | Total tracking limited | Expose total relation or enable controlled exact tracking |
| hasNext wrong | Computed from lower-bound total | Fetch one extra hit or use cursor pagination |
| Highlight map empty | Highlight not enabled in query or field didn't match | Check highlight query, field, and analyzer |
| Highlights contain dangerous HTML | Rendering fragments as unsanitized HTML | Escape/sanitize or use safe markers |
| Highlights lost after mapping | Kept only entity content, dropped SearchHit | Map highlights before discarding metadata |
| Sort enum allows unintended field queries | Client allowed to send raw field names | Use an allowlisted enum |
| Relevance ordering lost | Sorted by a field instead of _score | Define sort semantics explicitly |
| search_after repeats or skips hits | Unstable sort values or mismatched sort order | Use tie-breaker and keep sort consistent |
| Cursor reused across filters/tenants | Token not bound to query context | Sign and verify cursor context |
| Vector-only results lack highlights | Vector similarity has no lexical terms to mark | Use lexical snippets or mark highlights optional |
| Nested highlights not linked to right child | Missing nested path/inner hits | Verify nested query and inner hits |

## 28. Implementation Checklist

- [ ] Request DTO uses enums/allowlists for sort fields and directions.
- [ ] Page index, default size, and maximum size are explicitly defined.
- [ ] Sort fields have sortable mappings, typically keyword/numeric/date.
- [ ] Never sort directly on a text field without doc values.
- [ ] Sorts include a stable tie-breaker when pagination is used.
- [ ] Missing sort values have a defined policy.
- [ ] Pageable is created from validated criteria.
- [ ] Offset pagination is used only within safe depths.
- [ ] Beyond max_result_window, consider search_after.
- [ ] Cursors carry sort values and are validated against context.
- [ ] PITs are managed and closed properly when used.
- [ ] Total hits relation is reflected in the response.
- [ ] Highlighting applies only to displayable fields.
- [ ] Fragment size and fragment count are bounded.
- [ ] Highlights are mapped from SearchHit metadata.
- [ ] Frontend renders fragments safely to prevent XSS.
- [ ] Vector-only results are not guaranteed to include highlights.
- [ ] Tenant filters remain enforced alongside routing if used.
- [ ] Unit tests cover sort mapper and criteria validation.
- [ ] Integration tests cover sorting, pagination, and highlighting with real Elasticsearch.
- [ ] Tests cover page boundaries, duplicates, and cursor tampering.

Sorting, pagination, and highlighting complete the search experience. Sorting must rely on appropriately mapped fields and include a tie-breaker whenever stable ordering is needed. Offset pagination is simple for shallow pages, whereas search_after combined with PIT fits deep traversal over changing datasets. Highlights live in SearchHit metadata, must be mapped cleanly into response DTOs, and must be rendered safely. When these capabilities are governed through request criteria, a query factory, and a response mapper, a Spring Data Elasticsearch application can keep its API stable even as mappings and search strategies evolve.
