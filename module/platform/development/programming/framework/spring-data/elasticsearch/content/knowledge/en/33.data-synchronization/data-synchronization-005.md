# Handling Duplicate, Late, and Out-of-Order Events

In a data synchronization system, events can be delivered multiple times, arrive after a newer event, or arrive out of the order generated by the source. This is normal behavior in pipelines using message brokers, CDC, transactional outboxes, or retrying consumers. If a projector writes every event to Elasticsearch in arrival order, documents can regress to older states, increments can be applied twice, or deleted documents can reappear.

A reliable pipeline must determine which state is newer using metadata provided by the source, design idempotent writes, and establish explicit policies for duplicate, late, out-of-order, missing, and permanently failing events.

Key principles:

- Use event IDs to identify a single business emission.
- Use aggregate versions or monotonic sequences to determine change order for the same entity.
- Preserve per-aggregate event order when events carry interdependent deltas.
- Use full-state events or source version guards to prevent stale events from overwriting newer ones.
- Represent deletes with versioned tombstones when needed to prevent document resurrection.
- Commit offsets/checkpoints only after Elasticsearch has processed the event or the event has been durably moved to an error state.
- Retry with bounds, classify errors, and preserve original metadata during replays.

## 1. Why Can Events Be Duplicate, Late, or Out of Order?

A sync pipeline usually involves multiple components:

~~~text
Application / Database
          |
          v
    Outbox or CDC
          |
          v
    Message broker
          |
          v
       Consumer
          |
          v
    Elasticsearch
~~~

Each stage can introduce situations where events are redelivered or arrive out of order.

### 1.1. Duplicate Events

Duplicate events occur when the same event is processed multiple times. For example:

1. Consumer receives event E-100.
2. Consumer writes the document to Elasticsearch successfully.
3. Process stops before committing the offset.
4. Broker redelivers E-100.
5. Consumer writes E-100 again.

This is a common consequence of at-least-once delivery. The broker guarantees unacknowledged events are redelivered, but does not automatically guarantee Elasticsearch side effects occur only once.

Duplicate events can also occur when:

- A publisher retries after a timeout even though the prior publish succeeded.
- An outbox relay re-reads a row not yet marked published.
- A CDC connector recovers from an older offset.
- A consumer processes successfully but fails to commit its offset.
- The system replays a range of events to recover an index.

### 1.2. Late Events

A late event is an event created before another event that reaches the consumer after the newer event.

Example:

~~~text
Source emits:
  E-10: change price to 100
  E-11: change price to 120

Consumer receives:
  E-11 first
  E-10 second
~~~

If the consumer writes in arrival order, the price can revert from 120 back to 100. Event arrival time cannot be used as the sole basis for determining the latest state.

### 1.3. Out-of-Order Events

Out-of-order delivery commonly occurs when:

- One aggregate is processed by multiple parallel consumers.
- Events for the same aggregate are routed to multiple partitions.
- Consumers process asynchronously and complete Elasticsearch requests out of arrival order.
- Retries of an older event run while a newer event has already been processed.
- Multiple publishers emit events for the same aggregate.
- One event takes longer to retry than subsequent events.

Out-of-order delivery is especially dangerous for delta events, because each event contains only a partial change and depends on state created by prior events.

## 2. Distinguishing Event ID, Aggregate ID, and Version

These three fields solve three distinct problems.

| Field | Role | Example |
| --- | --- | --- |
| eventId | Identifies a specific event for deduplication | evt-90001 |
| aggregateId | Identifies the business object that changed | P-100 |
| aggregateVersion | Identifies the state order of the object | 42 |

Example event:

~~~json
{
  "eventId": "evt-90001",
  "eventType": "ProductPriceChanged",
  "aggregateType": "Product",
  "aggregateId": "P-100",
  "aggregateVersion": 42,
  "occurredAt": "2026-11-13T10:15:00Z",
  "payload": {
    "productId": "P-100",
    "price": 120
  }
}
~~~

Meaning:

- `eventId` detects redelivery of the same event.
- `aggregateId` identifies which document in Elasticsearch to update.
- `aggregateVersion` indicates which state is newer in the history of Product `P-100`.
- `occurredAt` is useful for auditing and observability, but does not replace version when strict ordering is required.

Never use `eventId` in place of `aggregateVersion`. A UUID can distinguish two events, but cannot tell which one is newer.

Never use `aggregateId` in place of `eventId`. One aggregate can emit thousands of events over its lifetime.

## 3. At-Least-Once Delivery and Idempotency

Many message brokers and CDC systems prioritize at-least-once delivery. Consumers can receive an event multiple times, and when configured properly, unacknowledged events are redelivered after failures.

This works well for data sync when projection operations are idempotent.

### 3.1. What Does Idempotent Mean?

An idempotent operation can be executed multiple times while leaving the final state identical to executing it once.

Assignment example:

~~~text
set product.price = 120
~~~

Writing the same price 120 repeatedly does not keep increasing the price.

In contrast, addition:

~~~text
product.viewCount = product.viewCount + 1
~~~

is not idempotent. If the event is delivered twice, `viewCount` increases twice.

### 3.2. Preferring Full-State Projections

Events carrying the full post-change document state are usually easier to reprocess than delta-only events.

Full-state event:

~~~json
{
  "eventId": "evt-90011",
  "aggregateId": "P-100",
  "aggregateVersion": 43,
  "operation": "UPSERT",
  "payload": {
    "id": "P-100",
    "name": "Mechanical Keyboard",
    "price": 120,
    "available": true
  }
}
~~~

The consumer can re-index the same document ID with that state. If the event is redelivered, the write targets the same document with the same data.

Delta event:

~~~json
{
  "eventId": "evt-90012",
  "aggregateId": "P-100",
  "aggregateVersion": 44,
  "operation": "INCREMENT_STOCK",
  "payload": {
    "amount": 5
  }
}
~~~

If the consumer applies the addition multiple times, inventory increases erroneously. Delta events require durable deduplication and strict processing order, or recomputing state from the source of truth.

### 3.3. Using Stable Document IDs

When projecting an aggregate, use the aggregate ID as the Elasticsearch document ID:

~~~text
_index = products
_id    = P-100
~~~

Do not generate a random ID every time an event arrives. If the ID changes, a redelivered event creates an extra duplicate document instead of overwriting the same document.

## 4. Deduplication Using Event ID

Event ID is the key identifying an event. Consumers can store processed event IDs in a deduplication table or store.

Example table:

| event_id | aggregate_id | processed_at | result |
| --- | --- | --- | --- |
| evt-90001 | P-100 | 10:15:01 | APPLIED |
| evt-90002 | P-100 | 10:15:03 | APPLIED |

Upon receiving an event:

1. Check whether `eventId` has already been processed.
2. If processed, skip side effects and acknowledge the event.
3. If not, execute the projection.
4. Mark processed only after the projection succeeds or has been handled under a durable policy.

### 4.1. Deduplication Pseudocode

~~~java
public void handle(ProductEvent event) {
    if (processedEventStore.exists(event.eventId())) {
        acknowledge(event);
        return;
    }

    projector.apply(event);
    processedEventStore.markProcessed(event.eventId());
    acknowledge(event);
}
~~~

This is a conceptual model. It still has an important failure window: Elasticsearch may succeed before the process crashes prior to `markProcessed`. The event will be redelivered. Thus, a deduplication ledger does not replace idempotency in the target write operation.

### 4.2. Why Not Mark Processed Before Writing to Elasticsearch?

If you mark processed first:

1. Consumer saves `eventId` in the dedup store.
2. Process crashes before writing to Elasticsearch.
3. Broker redelivers the event.
4. Consumer sees `eventId` is already processed and skips it.
5. The document is never updated.

This is data loss.

### 4.3. Why Write to Elasticsearch First and Mark Processed After?

If you write to Elasticsearch first:

1. Consumer writes document successfully.
2. Process crashes before `markProcessed`.
3. Event is redelivered.
4. Consumer writes the document again.

With full-state upserts using stable IDs and version guards, rewriting is safe. With non-idempotent delta operations, side effects could be repeated.

There is no shared ACID transaction spanning a database dedup store, message broker, and Elasticsearch in typical architectures. Design around at-least-once delivery with idempotent projections instead of assuming end-to-end exactly-once.

### 4.4. Dedup Stores Need Retention

You cannot keep every event ID forever in a table without a cleanup policy.

Retention must exceed:

- How long the broker can replay events.
- How long consumers can retry.
- Incident recovery windows.
- Projection bootstrap or rebuild durations.
- Operational windows permitting manual replays.

If you use `aggregateVersion` and full-state projections to block stale events, you can reduce reliance on an event ID ledger for final document state. Event IDs remain useful for auditing, duplicate detection, and non-idempotent side effects.

## 5. Using Aggregate Version to Block Stale Events

Aggregate version is a number incremented on every state change of an aggregate.

Example:

~~~text
Product P-100:
  version 40: created product
  version 41: renamed
  version 42: changed price
  version 43: changed stock status
~~~

Consumers can store the latest version inside the document:

~~~json
{
  "id": "P-100",
  "name": "Mechanical Keyboard",
  "price": 120,
  "available": true,
  "sourceVersion": 43
}
~~~

Rules:

- Incoming version greater than stored version: can be applied.
- Incoming version less than stored version: stale event, ignore.
- Incoming version equal to stored version: possible duplicate; inspect event semantics and payload.

### 5.1. Version Comparison

~~~text
Stored version = 43

Incoming version 42 -> STALE, do not write
Incoming version 43 -> DUPLICATE or CONFLICT
Incoming version 44 -> APPLY
~~~

Versions must be issued by the authoritative data source and incremented per aggregate. Never increment versions inside the Elasticsearch consumer, because multiple consumers running concurrently would create inconsistent ordering.

### 5.2. Business Version Differs from Elasticsearch `_version`

Elasticsearch maintains internal metadata such as `_version`, `_seq_no`, and `_primary_term` for managing index concurrency.

These values are not automatically the source data's version:

- `_version` is managed by Elasticsearch for the document in that specific index.
- `_seq_no` and `_primary_term` support optimistic concurrency within a shard.
- `aggregateVersion`/`sourceVersion` is managed by the source system to order business changes.

When rebuilding a new index, Elasticsearch's `_version` can reset. Therefore, if you need stale-event protection across rebuilds, store `sourceVersion` explicitly or pass it via external versioning.

## 6. Elasticsearch External Versioning

Elasticsearch supports client-supplied versioning for the Index API and bulk index operations.

Two modes must be distinguished:

| Version type | Acceptance condition |
| --- | --- |
| external | Incoming version must be strictly greater than stored version |
| external_gte | Incoming version must be greater than or equal to stored version |

### 6.1. Bulk Request Example

Suppose the `sourceVersion` of Product `P-100` is 42:

~~~http
POST /_bulk
Content-Type: application/x-ndjson

{ "index": { "_index": "products", "_id": "P-100", "version": 42, "version_type": "external" } }
{ "id": "P-100", "name": "Mechanical Keyboard", "price": 120, "sourceVersion": 42 }
~~~

If the current document holds external version 43, the version 42 operation is rejected instead of overwriting newer state.

### 6.2. `external` or `external_gte`?

With `external`:

- Version 43 is accepted when stored version is 42.
- Version 43 is rejected if stored version is already 43.
- Duplicates with the same version typically receive a version conflict.

With `external_gte`:

- Version 43 is accepted if stored version is 42.
- Version 43 is also accepted if stored version is already 43.
- Duplicates with the same version can rewrite the same state.

Use `external_gte` only when guaranteed that the same aggregate version always represents the exact same state payload. If two events carry different contents with the same version, the later event can overwrite the earlier one.

### 6.3. Handling 409 from Stale Events

When using external versioning, a stale event can receive a `409` version conflict. This can be the expected outcome when the document already has a newer version.

Do not retry the same stale event infinitely. Classify it:

- Stored version > incoming version: stale event, record as skipped.
- Stored version == incoming version: duplicate or data conflict; determine whether payloads match.
- Stored version < incoming version yet conflict still occurred: check writer races, version type, and index state.

Other `409` errors can come from optimistic concurrency or create conflicts. Inspect the error type and context instead of assuming every `409` is a duplicate.

## 7. Using Optimistic Concurrency When Multiple Writers Update Together

Elasticsearch supports optimistic concurrency control using `_seq_no` and `_primary_term`.

Example:

1. Consumer reads a document with `seq_no` 10 and `primary_term` 3.
2. Consumer computes the new state.
3. Consumer sends an update requiring `if_seq_no=10` and `if_primary_term=3`.
4. If another writer modified the document in the meantime, the request is rejected.
5. Consumer re-reads and decides whether to recompute.

This protects concurrent writes inside Elasticsearch.

### 7.1. Optimistic Concurrency Differs from Source Ordering

`_seq_no` and `_primary_term` prevent lost updates when two writers read the same document version, but they do not inherently know which event is newer in business terms.

For example, event version 10 arrives after event version 11. If a consumer reads the current document and uses optimistic concurrency properly, it could still deliberately write version 10 state over version 11 because that write matches the current `seq_no`.

Therefore:

- Source version solves business ordering.
- Elasticsearch `seq_no`/`primary_term` solves write races based on read state.
- Both mechanisms can be combined if the system needs both.

## 8. Handling Out-of-Order Events

Handling depends on whether events carry full state or deltas.

### 8.1. Full-State Events

Full-state events carry complete state as of a version. If event version 12 arrives before version 11, the consumer can apply version 12 and ignore version 11 when it arrives late.

~~~text
Receive v12 -> apply state v12
Receive v11 -> stale, ignore
~~~

This is a major advantage of full-state projections. However, event version 12 must truly contain the complete state, not just a single changed field.

### 8.2. Delta Events

Delta events contain only changes:

~~~text
v10: stock = 10
v11: decrement stock by 2
v12: increment stock by 5
~~~

If v12 is applied before v11, the state can become incorrect because deltas depend on order.

For delta events:

- Preserve ordering per aggregate.
- Detect sequence gaps.
- Buffer early-arriving events if waiting for missing events is possible.
- Never commit offsets past unprocessed events if broker semantics require ordering.
- If the event chain cannot be recovered, re-read the aggregate state from the source of truth and rebuild the projection.

### 8.3. Detecting Sequence Gaps

Suppose the document is at version 20 and the consumer receives event version 22:

~~~text
storedVersion = 20
incomingVersion = 22
expectedVersion = 21
~~~

Version 21 may be delayed or lost. If event 22 is full state, you may apply version 22 and mark version 21 to be skipped per policy. If event 22 is a delta, do not apply it while version 21 is missing.

A policy:

| Condition | Full-state event | Delta event |
| --- | --- | --- |
| Incoming = stored + 1 | Apply | Apply |
| Incoming <= stored | Ignore stale/duplicate | Ignore if already processed, check duplicate |
| Incoming > stored + 1 | Can apply latest state | Buffer, retry, or rebuild |

### 8.4. Do Not Rely Solely on `occurredAt` for Ordering

Timestamps can be useful for displaying history, but have limitations:

- Application instance clocks can skew.
- Two events can share the same timestamp.
- A transaction started earlier can commit later.
- Events are emitted by multiple services.
- Timestamps do not represent commit order in general.

When strict ordering is required, use aggregate versions, database log sequences, or broker offsets with clear semantics.

## 9. Ordering in Message Brokers

Message brokers can guarantee ordering within a scope, though not always system-wide.

### 9.1. Partition Keys by Aggregate ID

With Kafka, events with the same key are typically routed to the same partition. Using `aggregateId` as the message key ensures events for the same aggregate are read in order within that partition.

~~~text
key = Product:P-100

Partition 2:
  offset 100 -> version 10
  offset 101 -> version 11
  offset 102 -> version 12
~~~

Different aggregates can reside in different partitions and be processed in parallel.

### 9.2. Ordering Is Per Partition Only

Kafka does not provide a total global order across multiple partitions. If Product `P-100` and Product `P-200` sit in different partitions, do not assume a global order across their events.

Normally, an Elasticsearch projection by document ID only requires per-aggregate ordering. If business invariants span multiple aggregates, coordinate transactions/events at the source.

### 9.3. Do Not Process the Same Aggregate in Parallel

Even when the broker delivers events in order, a consumer can break ordering if it dispatches multiple events with the same key to parallel workers:

~~~text
Consumer receives:
  v10
  v11

Worker A handles v10 (slow)
Worker B handles v11 (fast)

Elasticsearch receives:
  v11
  v10
~~~

You can prevent this via:

- Serial processing within each partition.
- A key-based executor ensuring the same aggregate goes to the same lane.
- Source version guards in Elasticsearch.
- Combining ordering with version guards for defense in depth.

## 10. Deletes, Tombstones, and Late Events

Deletes are usually harder to handle than upserts because after physical deletion, the document no longer holds a version to compare against old events.

Timeline:

~~~text
v10: Product P-100 exists
v11: Product P-100 is deleted
v10 event retry arrives late
~~~

If v11 physically deletes the document and then v10 is re-indexed, the product comes back to life.

### 10.1. Tombstone Documents

Instead of immediate physical deletion, write a tombstone:

~~~json
{
  "id": "P-100",
  "sourceVersion": 11,
  "deleted": true,
  "deletedAt": "2026-11-13T10:16:00Z"
}
~~~

Product read queries filter `deleted=false`. The tombstone retains `sourceVersion` 11 so a late upsert event at version 10 is rejected.

### 10.2. Keep Tombstones Long Enough

Tombstones must be kept longer than any stale event can possibly surface:

- Broker retention.
- Consumer retry windows.
- DLQ replay windows.
- Backup restore windows.
- Bootstrap/rebuild durations.
- Outage recovery durations.

If a tombstone is purged while old events can still be replayed, the document can resurrect.

### 10.3. When Can a Tombstone Be Physically Deleted?

Only delete tombstones after:

1. All consumers have passed a watermark guaranteeing no older events remain.
2. The DLQ contains no events with lower versions.
3. Backup/replay processes cannot re-emit old events.
4. Mechanisms exist to block stale upserts if they still appear.

You can maintain a separate version ledger if you do not want tombstones residing in the search index.

### 10.4. Delete Events Need Versions

Delete events must carry an `aggregateVersion` newer than prior states. Never emit unversioned deletes if older events might arrive later.

If using Elasticsearch external versioning, you can index a tombstone as a document with an external version, or maintain a separate version ledger. Physical deletes with bounded version retention do not replace durable tombstones across long replay windows.

## 11. Using Event Stores or Outboxes to Preserve Order

If the application controls business transactions, a transactional outbox persists events durably alongside source changes.

Within a single transaction:

1. Update Product.
2. Increment `aggregateVersion`.
3. Write event to outbox with `eventId`, `aggregateId`, and version.
4. Commit once.

Example outbox table:

| event_id | aggregate_id | aggregate_version | event_type | payload |
| --- | --- | ---: | --- | --- |
| evt-100 | P-100 | 10 | ProductCreated | ... |
| evt-101 | P-100 | 11 | ProductPriceChanged | ... |
| evt-102 | P-100 | 12 | ProductStockChanged | ... |

The outbox relay can republish events if unsure whether the prior publish succeeded. Consumers must still be idempotent.

### 11.1. Unique Constraints for Event Identity

Place a unique constraint on `event_id` so the publisher cannot insert the same event record multiple times due to transaction retries or application bugs.

You can add a unique constraint on `(aggregate_id, aggregate_version)` if each aggregate version maps to exactly one event in your data model. If a single transaction emits multiple events at the same version, include an event sequence or design an appropriate key.

### 11.2. Aggregate Version Must Be Assigned Inside the Transaction

Never increment the version in the publisher after reading data. Two concurrent requests could both read version 10 and emit version 11.

Versions must be updated atomically in the database, such as with optimistic locking or conditional updates:

~~~sql
UPDATE product
SET price = :price,
    version = version + 1
WHERE id = :id
  AND version = :expected_version;
~~~

If 0 rows are updated, the transaction must handle the optimistic lock conflict instead of emitting a duplicate version event.

## 12. Consumer Checkpoints and Acknowledgements

Consumers must track which events have been processed. With offset-based brokers, the checkpoint is usually the committed offset. With CDC connectors, the checkpoint is the log position or connector offset.

Rules:

~~~text
Receive event
     |
     v
Validate event
     |
     v
Apply projection to Elasticsearch
     |
     +---- success / stale event safely ignored
     |             |
     |             v
     |        Commit offset
     |
     +---- transient failure
     |             |
     |             v
     |        Retry without advancing
     |
     +---- permanent failure
                   |
                   v
          Persist to DLQ / error store
                   |
                   v
          Commit according to policy
~~~

Never commit offsets before the projection completes. Committing early risks losing events if the consumer crashes.

### 12.1. Commit After Successful Writes

If Elasticsearch succeeded but the offset commit fails, the event may be redelivered. Thus, projections must be idempotent.

This is the classic trade-off of at-least-once processing: duplicates can occur, but events are never silently dropped due to premature acknowledgement.

### 12.2. Multiple Events in a Batch

If a consumer processes batches, commit only up to the highest contiguous completed offset. Never commit past an earlier pending event if the broker relies on offset ordering.

Example:

~~~text
offset 100 -> success
offset 101 -> pending
offset 102 -> success

Safe committed offset = 100
~~~

If you commit 102 while 101 is not yet durably processed, a restart can skip event 101.

### 12.3. Partition Concurrency

With Kafka, offset commits are per partition. If processing concurrently within a partition, track the highest contiguous completed offset, not merely the highest completed offset.

If per-aggregate ordering is required, the simplest approach is usually preserving processing order per partition or using a key-based serial executor.

## 13. Event Retries and Backoff

Not every error is retryable.

| Error | Common handling |
| --- | --- |
| HTTP 429 / rejected execution | Retry with backoff, reduce concurrency |
| Network errors or timeouts | Retry safely after considering unknown outcome |
| Temporary HTTP 5xx | Bounded retries |
| Mapping/parsing exception | Fix payload or mapping; do not retry as-is |
| Authentication/authorization | Fix credentials/permissions |
| Version conflict from stale event | Ignore after confirming a newer version exists |
| Version gap on delta event | Buffer, retry missing event, or rebuild |
| Index missing | Check lifecycle/bootstrap and target configuration |

### 13.1. Exponential Backoff

Example base delays:

| Retry attempt | Delay |
| --- | ---: |
| 1 | 200 ms |
| 2 | 400 ms |
| 3 | 800 ms |
| 4 | 1,600 ms |
| 5 | 3,200 ms |

Add jitter so multiple consumers do not retry simultaneously. Cap maximum delay and total retry duration.

### 13.2. Preserving Ordering During Retries

For delta events, if version 11 fails while version 12 proceeds, state can be corrupted. Block subsequent events for the same aggregate until version 11 succeeds or the aggregate is rebuilt.

For full-state events, you can allow version 12 to apply and later reject version 11 via the version guard.

Never apply the exact same retry policy to both full-state and delta events without accounting for their semantics.

## 14. Dead-Letter Queues and Poison Events

A poison event is an event that fails repeatedly due to invalid data or schema. If a consumer retries infinitely, one event can block an entire partition or cause an ever-growing backlog.

After exhausting allowed retries, save the event to a dead-letter queue (DLQ).

A DLQ record should include:

~~~json
{
  "eventId": "evt-90021",
  "aggregateId": "P-100",
  "aggregateVersion": 45,
  "sourceTopic": "product-events",
  "sourcePartition": 2,
  "sourceOffset": 1024,
  "attempts": 5,
  "errorType": "mapper_parsing_exception",
  "errorReason": "failed to parse field price",
  "failedAt": "2026-11-13T10:20:00Z",
  "payload": {
    "id": "P-100",
    "price": "unknown"
  }
}
~~~

### 14.1. A DLQ Is Not a Place to Forget Events

Every DLQ needs:

- Metrics on DLQ event count.
- Alerts on event count and age.
- Lookup tooling by ID/aggregate.
- A process to fix schemas or data.
- A controlled replay workflow.
- An owner responsible for handling it.

### 14.2. Replaying the DLQ

When replaying:

1. Confirm the root cause is fixed.
2. Preserve the original `eventId` and `aggregateVersion`.
3. Determine whether the event is still newer than the target state.
4. If the event is stale, mark it skipped per policy.
5. If still needed, resend with appropriate ordering.
6. Record the replay outcome.

Never artificially increment `aggregateVersion` just to bypass a version conflict. Version reflects source history, not consumer retry count.

## 15. Full-State Events vs. Delta Events: Choosing by Need

| Criterion | Full-state event | Delta event |
| --- | --- | --- |
| Payload | Full state | Changed portion |
| Duplicate handling ease | High with ID/version | Lower when additions/side effects exist |
| Out-of-order handling ease | Can skip older versions | Usually requires contiguous ordering |
| Event size | Larger | Smaller |
| Replay | Can re-index state | Needs complete, properly ordered history |
| Index rebuild | Convenient | May need snapshot + all events |

When Elasticsearch serves as a read model/search projection, full-state events are usually easier to operate provided payloads are not overly large. Full-state events can be emitted by the aggregate or constructed by having the consumer re-read the latest state from the source of truth.

### 15.1. When Only Delta Events Exist

If the domain emits only deltas:

- Use `aggregateVersion`.
- Ensure events for the same aggregate are partitioned and processed sequentially.
- Detect gaps.
- Persist events durably for replay.
- If missing events cannot be recovered, re-read the aggregate from the source of truth and write a new full document.

Avoid relying on increment/decrement update scripts in Elasticsearch as the sole source of business state when events can be duplicated or reordered.

## 16. Late Events After an Index Rebuild

When creating a new index, consumers may replay events while a snapshot is being written. Without a version guard, stale events can overwrite newer snapshots or vice versa.

A safe model:

1. Snapshot rows carry `sourceVersion` as of snapshot time.
2. Events carry the change's `aggregateVersion`.
3. Snapshot writer and event projector share the same document ID.
4. All writes use external versioning or conditional updates on `sourceVersion`.
5. The target retains only the highest version state.

Example:

~~~text
Snapshot P-100 version 20
Event P-100 version 21
Event P-100 version 22

Arrival order:
  event 22
  snapshot 20
  event 21

Target:
  version 22
  snapshot 20 rejected as stale
  event 21 rejected as stale
~~~

If version guards are not implemented, force the snapshot to complete before starting replay and ensure the change log retains all events from the snapshot boundary.

## 17. Logging and Observing Event Processing

Logs should show which events were received, how they were processed, and why any were skipped or retried.

Success log example:

~~~text
eventId=evt-90001
aggregateType=Product
aggregateId=P-100
aggregateVersion=42
operation=UPSERT
result=APPLIED
targetIndex=products-v2
sourcePartition=2
sourceOffset=1024
~~~

Stale event example:

~~~text
eventId=evt-89990
aggregateId=P-100
incomingVersion=40
storedVersion=42
result=IGNORED_STALE
~~~

DLQ example:

~~~text
eventId=evt-90021
aggregateId=P-100
aggregateVersion=45
result=DEAD_LETTERED
attempts=5
errorType=mapper_parsing_exception
~~~

### 17.1. Metrics to Monitor

| Metric | Meaning |
| --- | --- |
| events_received_total | Total events received by consumer |
| events_applied_total | Total events applied |
| events_duplicate_total | Duplicate events |
| events_stale_total | Stale events ignored |
| events_out_of_order_total | Out-of-order events |
| events_gap_total | Detected version/sequence gaps |
| events_retried_total | Total retry attempts |
| events_dead_letter_total | Total events sent to DLQ |
| consumer_lag | Distance between consumer and source |
| event_processing_duration | Event processing duration |
| projection_version_lag | Difference between source version and target version |

Rising stale event metrics can signal normal retries, but a sudden spike may indicate broken parallel processing or publishers re-emitting many events.

### 17.2. Avoid Logging Sensitive Payloads

Logging `eventId`, `aggregateId`, version, offset, and error metadata is usually enough for investigation. Do not log full payloads if they contain personal info, secrets, or large blobs. You can log a payload hash to help detect two events with identical versions yet different contents.

## 18. Example Projector with Version Guard

The example below shows how to classify events by version before writing. The check and write must execute atomically in Elasticsearch when multiple writers compete.

~~~java
public enum ProjectionDecision {
    APPLY,
    IGNORE_DUPLICATE,
    IGNORE_STALE,
    VERSION_GAP
}

public ProjectionDecision decide(
        long storedVersion,
        long incomingVersion,
        boolean fullStateEvent) {

    if (incomingVersion < storedVersion) {
        return ProjectionDecision.IGNORE_STALE;
    }

    if (incomingVersion == storedVersion) {
        return ProjectionDecision.IGNORE_DUPLICATE;
    }

    if (!fullStateEvent && incomingVersion > storedVersion + 1) {
        return ProjectionDecision.VERSION_GAP;
    }

    return ProjectionDecision.APPLY;
}
~~~

This illustrates sequential consumer logic. If multiple consumers can write to the same document, do not simply read `storedVersion`, decide in Java, and issue an unconditional write. Another writer could modify the document between the read and write steps.

Use external versioning or an update script/optimistic concurrency to execute the version guard atomically.

### 18.1. External Versioning with the Java API Client

Example bulk index operation with external versioning:

~~~java
import co.elastic.clients.elasticsearch.ElasticsearchClient;
import co.elastic.clients.elasticsearch._types.VersionType;
import co.elastic.clients.elasticsearch.core.BulkRequest;
import co.elastic.clients.elasticsearch.core.BulkResponse;

public BulkResponse writeVersionedBatch(
        ElasticsearchClient client,
        String index,
        List<ProductIndexDocument> documents) throws IOException {

    BulkRequest.Builder request = new BulkRequest.Builder();

    for (ProductIndexDocument document : documents) {
        request.operations(operation -> operation
            .index(indexOperation -> indexOperation
                .index(index)
                .id(document.id())
                .version(document.sourceVersion())
                .versionType(VersionType.External)
                .document(document)
            )
        );
    }

    return client.bulk(request.build());
}
~~~

Enum names and builder methods must match the version of the Elasticsearch Java API Client in use. With strict external versioning, duplicates with the same version may return a conflict; the consumer can classify the conflict as stale/duplicate after verifying target state.

### 18.2. Inspecting Each Item

A bulk response can return HTTP 200 even when some items fail. Iterate through each item:

~~~java
BulkResponse response = writeVersionedBatch(
    client,
    "products-v2",
    documents
);

for (var item : response.items()) {
    if (item.error() == null) {
        recordApplied(item.id(), item.status());
        continue;
    }

    if (item.status() == 409) {
        recordVersionConflict(item.id(), item.error().type());
        continue;
    }

    recordFailure(
        item.id(),
        item.status(),
        item.error().type(),
        item.error().reason()
    );
}
~~~

Do not assume every 409 is a stale event. Inspect the error type, version policy, and stored state to distinguish duplicates, stale versions, create conflicts, or optimistic concurrency conflicts.

## 19. Conditional Update Scripts by `sourceVersion`

When partial document updates are needed, an update script can compare versions and apply updates only when the incoming version is newer.

Painless pseudocode:

~~~text
if (ctx._source.sourceVersion == null ||
    params.sourceVersion > ctx._source.sourceVersion) {
    ctx._source.name = params.name;
    ctx._source.price = params.price;
    ctx._source.sourceVersion = params.sourceVersion;
} else {
    ctx.op = 'noop';
}
~~~

The script runs inside Elasticsearch, so checking the version and updating the document occur within one operation. This avoids races present in client-side read-then-write logic.

If the event is a delta, the script must also verify contiguous versions or `previousVersion`:

~~~text
if (params.previousVersion == ctx._source.sourceVersion) {
    // Apply delta and set new sourceVersion.
} else {
    // Reject or noop; caller must classify the gap/stale event.
}
~~~

Do not use update scripts to silently drop all out-of-order events. The consumer still needs to know whether an event was ignored as stale or rejected due to a missing version.

## 20. Reconciliation and Rebuilding When Event Chains Break

If an unrecoverable version gap is detected, re-read the aggregate state from the source of truth and write a full document.

Workflow:

1. Mark the aggregate as needing reconciliation.
2. Pause or serialize new events for that aggregate if needed.
3. Read current state and version from the source of truth.
4. Build the full-state document.
5. Write using a source version guard.
6. Confirm the target has reached the source version.
7. Resume processing new events.

If a newer event arrives during reconciliation, the version guard prevents the older reconciliation snapshot from overwriting newer state.

### 20.1. Batch Reconciliation

You can periodically compare:

- Aggregate versions at the source.
- `sourceVersion` in Elasticsearch.
- Deleted states.
- Aggregates missing documents.
- Documents no longer existing at the source.

You do not need to scan the entire source for every event. Use audit jobs, change logs, or sampling to detect drift.

### 20.2. Never Modify Source Versions During Index Repairs

When rebuilding a document due to projection errors, preserve the original `sourceVersion` of the read state. Never increment the version just to bypass conflicts, because doing so falsifies business history and can cause subsequent valid events to be treated as stale.

## 21. Testing Duplicate, Late, and Out-of-Order Events

Tests should verify the final state in Elasticsearch rather than merely asserting the consumer throws no exceptions.

### 21.1. Duplicate Events

Scenario:

1. Send event version 10.
2. Resend the exact same event.
3. Refresh the index.
4. Assert only one document exists at version 10.
5. If counters or side effects exist, verify they were not applied twice.

### 21.2. Late Events

Scenario:

1. Send event version 12 with price 120.
2. Send event version 11 with price 100.
3. Assert the document retains price 120 and `sourceVersion` 12.

### 21.3. Out-of-Order Events

With full-state events:

~~~text
Send v12
Send v10
Send v11
Expected stored version = 12
~~~

With delta events:

~~~text
Stored v10
Receive v12 (expects v11 first)
Expected: buffer/retry/reconcile, not apply delta
Receive v11
Apply v11 then v12
~~~

### 21.4. Delete Followed by Stale Upsert

Scenario:

1. Write Product `P-100` version 10.
2. Write tombstone version 11.
3. Resend upsert version 10.
4. Assert the document remains deleted or tombstone version 11.
5. Product queries must not return `P-100`.

### 21.5. Crash Between Elasticsearch Write and Offset Commit

Scenario:

1. Consumer writes event successfully.
2. Simulate crash before offset commit.
3. Redeliver the event.
4. Assert projection is idempotent and `sourceVersion` does not change erroneously.

### 21.6. Version Gap

Scenario:

1. Target is at version 20.
2. Send delta event version 22.
3. Assert consumer does not apply delta while version 21 is missing.
4. Send version 21.
5. Assert version 21 and then 22 are applied in the right order.

## 22. Common Pitfalls

**Using event arrival timestamps for ordering.** Stale events can arrive after newer events. Use `aggregateVersion` or a sequence from the source.

**Assuming the broker never delivers duplicate events.** At-least-once delivery can redeliver. Design idempotent consumers.

**Deduplicating only by `eventId` and ignoring versions.** Event IDs do not indicate which event is newer. Use both event identity and aggregate version.

**Marking events processed before writing to Elasticsearch.** Crashing after marking can lose projections. Write to the target first, then commit checkpoints; use version guards to tolerate duplicates.

**Using addition/subtraction on redeliverable events.** Deltas can be applied multiple times. Use durable event deduplication, ordering, or full-state projections.

**Using Elasticsearch's `_version` as the source version.** Elasticsearch's internal version lacks business history semantics. Store `sourceVersion` separately or use external versioning.

**Reading version on the client and issuing an unconditional write.** Two consumers can race. Use external versioning, script conditions, or optimistic concurrency.

**Using `external_gte` when the same version can have different payloads.** A later event can overwrite same-version state. Ensure versions are unique per state or use strict `external`.

**Treating every HTTP 409 as a duplicate.** It could be a version conflict, create conflict, or optimistic concurrency error. Inspect the error type and stored version.

**Ignoring version gaps on delta events.** Missing prior events can corrupt state. Buffer, retry, or rebuild from the source.

**Processing events for the same aggregate in parallel.** Newer events can write before older ones. Partition by aggregate key and/or use version guards.

**Physically deleting documents without retaining tombstones.** Stale upserts can recreate deleted documents. Retain tombstones or a version ledger long enough.

**Retrying poison events infinitely.** A single event can stall a partition. Use bounded retries and a DLQ.

**Committing offsets before projections finish.** A consumer crash can skip events. Commit after writes or after durably storing errors per policy.

**Committing the highest offset while earlier offsets remain incomplete.** Unprocessed events can be skipped. Commit the highest contiguous completed offset.

**Replaying DLQs with fabricated new versions.** That corrupts source history and marks other valid events stale. Keep original versions.

**Having no reconciliation.** Event chains can drop items or projections can drift undetected. Periodically compare `sourceVersion` and source state.

## 23. Recommended Event Processing Workflow

For each received event:

1. Validate schema, `eventId`, `aggregateId`, `aggregateVersion`, and operation.
2. Determine whether the event is full-state or delta.
3. Check `eventId` if a deduplication ledger is needed.
4. Read or check current `sourceVersion` atomically in Elasticsearch.
5. If the incoming version is older, record as stale and do not apply.
6. If versions are equal, classify as duplicate or payload conflict.
7. If the version is newer with a gap and the event is a delta, buffer/retry or reconcile.
8. If valid, apply upsert/delete/tombstone with a version guard.
9. Inspect each item result when using bulk operations.
10. Only commit offsets/checkpoints once results are durably handled.
11. For transient failures, retry with backoff while preserving required ordering.
12. For permanent failures, persist events to a DLQ and raise alerts.
13. Monitor `sourceVersion`, lag, stale counts, gap counts, and DLQ.

~~~text
Receive event
     |
     v
Validate schema and identity
     |
     v
Classify event type
     |
     v
Compare source version
     |
     +-- stale/duplicate ------> record ignored -> ack
     |
     +-- delta version gap ----> buffer/retry/reconcile
     |
     +-- newer valid event ----> atomic versioned write
                                    |
                                    +-- success/noop stale -> ack
                                    |
                                    +-- transient failure -> retry
                                    |
                                    +-- permanent failure -> DLQ
~~~
