# Inspecting the Registration File in Packaged Library JARs

## 1. Objective and Inspection Model

In Spring Boot, a class annotated with `@AutoConfiguration` is not guaranteed to be discovered by other applications. For a library packaged as a JAR, Spring Boot 3.x relies on a resource at the exact path:

~~~text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

This resource lists the **fully qualified class names** (FQCN) of candidate auto-configurations, one class per line. For example:

~~~text
edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

Spring Boot allows using `#` for comments in the file. Nested class names, if any, use binary names with `$` between the outer class and inner class; to avoid confusion, the main example uses top-level classes.

**Lesson objective:** package the sample library yourself, inspect the imports file inside the **actual JAR** (not just in source), read its contents, cross-check against compiled `.class` files, verify the JAR as a runtime dependency, and observe beans in a consuming application. Then inspect the executable Spring Boot JAR case containing dependencies as nested JARs under `BOOT-INF/lib`.

Three questions must be answered with three different kinds of evidence:

| Question | Evidence |
| --- | --- |
| Did the library publish the candidate class name? | `AutoConfiguration.imports` entry in the JAR and its FQCN content |
| Can Spring Boot load the class on the runtime classpath? | Corresponding class and dependency present in the actual artifact/classpath |
| Is the auto-configured bean created in a specific run? | Condition Evaluation Report and `ApplicationContext` |

Conceptual flow:

~~~text
src/main/resources/META-INF/spring/...AutoConfiguration.imports
    |
    v
Build/publish -> library.jar has resource + corresponding class
    |
    v
Application adds library.jar to runtime classpath
    |
    v
@EnableAutoConfiguration reads candidate lists from JARs
    |
    v
Filters exclusions, conditions on configurations/bean methods
    |
    v
Actual BeanDefinitions and bean instances in ApplicationContext
~~~

**Having an imports file does not mean a bean is guaranteed to appear.** An auto-configuration can still be excluded or fail `@ConditionalOnClass`, `@ConditionalOnProperty`, or `@ConditionalOnMissingBean`. Conversely, a bean appearing may be user-declared, not necessarily from auto-configuration.

## 2. File Name and Location Must Be Exact

In a Maven or Gradle library project following standard layout:

~~~text
greeter-autoconfigure/
├── pom.xml
└── src/main/
    ├── java/
    │   └── edu/example/greeter/autoconfigure/
    │       └── GreeterAutoConfiguration.java
    └── resources/
        └── META-INF/
            └── spring/
                └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

After packaging into a **plain library JAR**, the entry path sits at the **JAR root**:

~~~text
greeter-autoconfigure-1.0.0.jar
├── META-INF/
│   ├── MANIFEST.MF
│   └── spring/
│       └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
└── edu/example/greeter/autoconfigure/
    └── GreeterAutoConfiguration.class
~~~

Do not place the file in `META-INF/` missing the `spring/` directory. Do not add a `.txt` or `.properties` suffix. Do not include a `src/main/resources` prefix inside the archive. Resource names are case-sensitive inside the JAR.

In Boot 3.x, this registration mechanism differs from the legacy `org.springframework.boot.autoconfigure.EnableAutoConfiguration` entry in `META-INF/spring.factories`. `spring.factories` may still be needed for other SPIs; do not delete it wholesale. Also do not confuse:

- `META-INF/spring-autoconfigure-metadata.properties`: metadata generated by the annotation processor so Boot can filter conditions early more efficiently; does not replace the imports file.
- `META-INF/spring-configuration-metadata.json`: configuration properties metadata for IDEs and config tools; does not list auto-configuration candidates.
- `META-INF/services/...`: resources for `ServiceLoader` and other SPIs; not this file.

## 3. Spring Boot 3.3 / Java 17 Library Example

We use two independent Maven projects. The library produces a **plain JAR**; the consuming application produces an **executable Spring Boot JAR**. Requirements: JDK 17+, Maven 3.9+, and ability to download Maven dependencies.

~~~text
inspection-demo/
├── greeter-autoconfigure/
│   ├── pom.xml
│   └── src/main/
│       ├── java/edu/example/greeter/
│       │   ├── api/Greeter.java
│       │   └── autoconfigure/GreeterAutoConfiguration.java
│       └── resources/META-INF/spring/
│           └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
└── greeter-consumer/
    ├── pom.xml
    └── src/main/java/edu/example/app/
        └── DemoApplication.java
~~~

### 3.1. POM for the Library

File `greeter-autoconfigure/pom.xml`:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.13</version>
        <relativePath/>
    </parent>
    <groupId>edu.example</groupId>
    <artifactId>greeter-autoconfigure</artifactId>
    <version>1.0.0</version>
    <packaging>jar</packaging>
    <properties>
        <java.version>17</java.version>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-autoconfigure</artifactId>
        </dependency>
    </dependencies>
</project>
~~~

`spring-boot-autoconfigure` provides the `@AutoConfiguration` annotation and Boot conditions. This library **does not need** `spring-boot-starter-web`, and does not use `spring-boot-maven-plugin` to repackage into an executable JAR. An auto-configuration library should be published as a regular classpath JAR.

### 3.2. Service Type

File `greeter-autoconfigure/src/main/java/edu/example/greeter/api/Greeter.java`:

~~~java
package edu.example.greeter.api;

public interface Greeter {
    String message();
}
~~~

### 3.3. Auto-Configuration Class

File `greeter-autoconfigure/src/main/java/edu/example/greeter/autoconfigure/GreeterAutoConfiguration.java`:

~~~java
package edu.example.greeter.autoconfigure;

import edu.example.greeter.api.Greeter;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.context.annotation.Bean;

@AutoConfiguration
@ConditionalOnProperty(
    prefix = "demo.greeter",
    name = "enabled",
    havingValue = "true",
    matchIfMissing = true
)
public class GreeterAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(Greeter.class)
    public Greeter libraryGreeter() {
        return () -> "library";
    }
}
~~~

The configuration above provides a default `Greeter` bean. If `demo.greeter.enabled` is absent, the configuration still applies due to `matchIfMissing=true`. If the application already has a `Greeter` bean, `@ConditionalOnMissingBean` makes the default bean yield.

The annotation on the Java class **is not enough for Boot to auto-discover the class**. You must still create the imports file.

### 3.4. Candidate Registration File

File `greeter-autoconfigure/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` contains only:

~~~text
edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

Names in imports are FQCNs **without `.class`**, and without `/`. One imports file can list multiple classes, one class per line. Auto-configuration classes should stay outside the package component-scanned by consuming applications, so loading them truly comes from the auto-configuration mechanism.

## 4. Packaging the Library and Inspecting the JAR Contents

In the `greeter-autoconfigure` directory:

~~~bash
java -version
mvn -version
mvn -q clean install
~~~

`mvn install` compiles, packages, and installs the artifact into the Maven local repository so the consumer application can reference it. This is not publishing to Maven Central.

The file will be located at:

~~~text
target/greeter-autoconfigure-1.0.0.jar
~~~

### 4.1. Listing Entries with the JDK `jar` Tool

~~~bash
jar tf target/greeter-autoconfigure-1.0.0.jar
~~~

`jar tf` only **lists entries**; it does not print file contents. In the long output, verify at least two entries:

~~~text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
edu/example/greeter/autoconfigure/GreeterAutoConfiguration.class
~~~

These are **two required lines**, not the entire stdout. The JAR also contains the manifest, Maven metadata, and other classes.

Filter on Linux/macOS:

~~~bash
jar tf target/greeter-autoconfigure-1.0.0.jar |
  grep -F 'META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports'
~~~

Filter on PowerShell (Windows):

~~~powershell
jar tf .\target\greeter-autoconfigure-1.0.0.jar |
  Select-String -SimpleMatch 'META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports'
~~~

If the file is missing, recheck `src/main/resources` and resource-copying rules during the build. Seeing the file in the IDE does not prove it was copied into the published archive.

### 4.2. Reading the Imports Content Inside the JAR

If `unzip` is available on Linux/macOS:

~~~bash
unzip -p target/greeter-autoconfigure-1.0.0.jar \
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

Expected content:

~~~text
edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

JDK-only option, extracting a single entry into a separate directory:

~~~bash
mkdir -p inspect-jar
cd inspect-jar
jar xf ../target/greeter-autoconfigure-1.0.0.jar \
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
cat META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
cd ..
~~~

On PowerShell:

~~~powershell
New-Item -ItemType Directory .\inspect-jar -Force | Out-Null
Push-Location .\inspect-jar
jar xf ..\target\greeter-autoconfigure-1.0.0.jar META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
Get-Content .\META-INF\spring\org.springframework.boot.autoconfigure.AutoConfiguration.imports
Pop-Location
~~~

Do this in a separate directory so you do not extract `META-INF` into your existing source tree.

### 4.3. Cross-Checking FQCN Against the Compiled Class

The FQCN in imports uses dots. The `.class` entry in the JAR uses forward slashes:

~~~text
imports: edu.example.greeter.autoconfigure.GreeterAutoConfiguration
class:   edu/example/greeter/autoconfigure/GreeterAutoConfiguration.class
~~~

Having an imports file without the corresponding class is a sign to check the build, package name, version, or where the class is actually distributed. In this example, the class is contained in the same JAR. In real-world libraries, an imports entry can reference a type in another dependency; ensure the required dependency is distributed properly.

## 5. Inspecting the JAR with a Pure Java Program

If `unzip` is unavailable, you can use `java.util.jar.JarFile`. This is a **standalone program running on JDK 17** requiring no external libraries.

Create `InspectImports.java` in the library project directory:

~~~java
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import java.util.jar.JarEntry;
import java.util.jar.JarFile;

public class InspectImports {
    private static final String PATH =
        "META-INF/spring/" +
        "org.springframework.boot.autoconfigure.AutoConfiguration.imports";

    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            System.err.println("Usage: java InspectImports.java <jar-file>");
            System.exit(1);
        }

        try (JarFile jar = new JarFile(args[0])) {
            JarEntry entry = jar.getJarEntry(PATH);
            if (entry == null) {
                System.err.println("MISSING: " + PATH);
                System.exit(2);
            }
            try (BufferedReader reader = new BufferedReader(
                    new InputStreamReader(
                        jar.getInputStream(entry), StandardCharsets.UTF_8))) {
                System.out.println("FOUND: " + PATH);
                reader.lines().forEach(System.out::println);
            }
        }
    }
}
~~~

Run:

~~~bash
java InspectImports.java target/greeter-autoconfigure-1.0.0.jar
~~~

Result when the JAR is valid:

~~~text
FOUND: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

If the entry is absent, the program prints `MISSING: ...` to stderr and exits with code `2`. This works well in build checks. `JarFile` only opens the specified archive; for an executable JAR with nested dependencies, extract the library first—see section 8.

## 6. Using the Library in a Consumer Application

To prove the imports file works, create a second Spring Boot application.

File `greeter-consumer/pom.xml`:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/xsd/maven-4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.13</version>
        <relativePath/>
    </parent>
    <groupId>edu.example</groupId>
    <artifactId>greeter-consumer</artifactId>
    <version>1.0.0</version>
    <properties>
        <java.version>17</java.version>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter</artifactId>
        </dependency>
        <dependency>
            <groupId>edu.example</groupId>
            <artifactId>greeter-autoconfigure</artifactId>
            <version>1.0.0</version>
        </dependency>
    </dependencies>
    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

Create `greeter-consumer/src/main/java/edu/example/app/DemoApplication.java`:

~~~java
package edu.example.app;

import edu.example.greeter.api.Greeter;
import java.util.Arrays;
import org.springframework.boot.Banner;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class DemoApplication {
    @Bean
    @ConditionalOnProperty(
        name = "demo.override",
        havingValue = "true"
    )
    Greeter userGreeter() {
        return () -> "user";
    }

    public static void main(String[] args) {
        try (ConfigurableApplicationContext context =
                 new SpringApplicationBuilder(DemoApplication.class)
                     .web(WebApplicationType.NONE)
                     .bannerMode(Banner.Mode.OFF)
                     .run(args)) {
            String[] names =
                context.getBeanNamesForType(Greeter.class);
            Arrays.sort(names);

            Greeter greeter =
                context.getBeanProvider(Greeter.class).getIfAvailable();

            System.out.println("greeterBeans=" +
                Arrays.toString(names));
            System.out.println("message=" +
                (greeter == null ? "none" : greeter.message()));
        }
    }
}
~~~

Mechanics in the demo:

- The main class is in `edu.example.app`, and the auto-configuration class is in `edu.example.greeter.autoconfigure`, so it is not scanned by component scan from the main class.
- `WebApplicationType.NONE` disables creating a web application context, avoiding needing an HTTP server; auto-configuration still runs.
- By default, the auto-configuration class provides `libraryGreeter`.
- When `demo.override=true`, the application provides the `userGreeter` bean, causing the default to yield via `@ConditionalOnMissingBean`.
- When `demo.greeter.enabled=false`, the auto-config class condition does not match; the default bean is absent.

### 6.1. Running and Observing Actual Beans

After running `mvn -q clean install` in the library, from the consumer directory run:

~~~bash
mvn -q spring-boot:run
~~~

Two lines printed by the program:

~~~text
greeterBeans=[libraryGreeter]
message=library
~~~

Additional Spring Boot logs may appear; these are the two `System.out.println` lines from main, not the entire stdout/stderr.

Let the user declare a bean:

~~~bash
mvn -q spring-boot:run -Dspring-boot.run.arguments=--demo.override=true
~~~

Result:

~~~text
greeterBeans=[userGreeter]
message=user
~~~

Disable the auto-configuration's property condition:

~~~bash
mvn -q spring-boot:run -Dspring-boot.run.arguments=--demo.greeter.enabled=false
~~~

Result:

~~~text
greeterBeans=[]
message=none
~~~

Exclude the auto-configuration by name:

~~~bash
mvn -q spring-boot:run -Dspring-boot.run.arguments=--spring.autoconfigure.exclude=edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

Result:

~~~text
greeterBeans=[]
message=none
~~~

The last two cases have the same bean set yet **different causes**: one failed a condition; the other was excluded from the set of configurations to process.

### 6.2. Observing Why Conditions Match or Do Not Match

Enable `--debug`:

~~~bash
mvn -q spring-boot:run -Dspring-boot.run.arguments=--debug
~~~

Find `GreeterAutoConfiguration` and `libraryGreeter` in the *Condition Evaluation Report*. If `--demo.override=true` is enabled alongside `--debug`, the class may match at the property level, while the `@ConditionalOnMissingBean` condition on the method fails because the user bean is present.

The condition report answers **why a configuration or method was accepted/skipped**. Inspecting `ApplicationContext` answers **which beans exist**. Neither replaces inspecting the imports file in the artifact.

## 7. Where Does an Executable Spring Boot JAR Store Libraries?

A plain library JAR has the imports file at root `META-INF/spring/...`. However, an application packaged by `spring-boot-maven-plugin` typically looks like:

~~~text
greeter-consumer-1.0.0.jar
├── META-INF/MANIFEST.MF
├── org/springframework/boot/loader/...
└── BOOT-INF/
    ├── classes/edu/example/app/DemoApplication.class
    └── lib/
        ├── greeter-autoconfigure-1.0.0.jar
        ├── spring-boot-....jar
        └── ...
~~~

In that case, the library's imports file **is not required to appear at the root of the outer JAR**. It sits inside a **nested JAR** at `BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar`. The normal `jar tf` tool only lists entries of the opened archive; it does not automatically list every file inside nested JARs.

The Spring Boot Loader supports loading nested JARs when running the executable via `java -jar`. Therefore, **not seeing the imports file at the root of the executable JAR** is not proof that the library lacks registration.

## 8. Inspecting Imports of a Nested JAR in a Packaged Application

In the `greeter-consumer` directory:

~~~bash
mvn -q clean package
jar tf target/greeter-consumer-1.0.0.jar
~~~

On Linux/macOS, locate the dependency JAR:

~~~bash
jar tf target/greeter-consumer-1.0.0.jar |
  grep -F 'BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar'
~~~

On PowerShell:

~~~powershell
jar tf .\target\greeter-consumer-1.0.0.jar |
  Select-String -SimpleMatch 'BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar'
~~~

Expected line:

~~~text
BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar
~~~

Extract the library JAR, then open the **nested JAR**. Linux/macOS:

~~~bash
mkdir -p inspect-executable
cd inspect-executable
jar xf ../target/greeter-consumer-1.0.0.jar \
  BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar
jar tf BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar |
  grep -F 'META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports'
unzip -p BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar \
  META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
cd ..
~~~

PowerShell:

~~~powershell
New-Item -ItemType Directory .\inspect-executable -Force | Out-Null
Push-Location .\inspect-executable
jar xf ..\target\greeter-consumer-1.0.0.jar BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar
jar tf .\BOOT-INF\lib\greeter-autoconfigure-1.0.0.jar |
  Select-String -SimpleMatch 'META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports'
jar xf .\BOOT-INF\lib\greeter-autoconfigure-1.0.0.jar META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
Get-Content .\META-INF\spring\org.springframework.boot.autoconfigure.AutoConfiguration.imports
Pop-Location
~~~

The content read from the nested JAR is still:

~~~text
edu.example.greeter.autoconfigure.GreeterAutoConfiguration
~~~

Finally, from the consumer directory run:

~~~bash
java -jar target/greeter-consumer-1.0.0.jar
~~~

The two lines printed by the application:

~~~text
greeterBeans=[libraryGreeter]
message=library
~~~

If `mvn spring-boot:run` works while `java -jar` does not, check the nested JAR version, how the executable packaging plugin is configured, and runtime dependencies. The two runs may be using different artifacts.

### Do Not Confuse JAR Types

| Type | Where to Look for Library Imports |
| --- | --- |
| Plain library JAR | `META-INF/spring/...AutoConfiguration.imports` right at the JAR root |
| Boot executable JAR | Open the dependency in `BOOT-INF/lib/*.jar`, then look for the entry at the root of that dependency JAR |
| Boot executable WAR | Dependencies are usually in `WEB-INF/lib` or `WEB-INF/lib-provided` |
| Shaded/uber JAR merging multiple libraries | Inspect the imports entry after merging; ensure same-path resources were not overwritten, losing class names |

Do not package an auto-configuration library as an executable Boot JAR with classes in `BOOT-INF/classes` and expect consumers to use it as a regular classpath JAR. The class/resource loading mechanisms have different layouts.

## 9. Common Errors and Resolution Workflow

### 9.1. File Exists in Source Yet Missing from the JAR

Check `src/main/resources`, Maven/Gradle resource configuration, the right source set, packaging plugins, and the final artifact. You can check `target/classes` as intermediate evidence, but conclusions must rest on the **published JAR**.

### 9.2. Imports File Exists, Yet Wrong FQCN

Cross-check each line against the actual class: `edu.example.greeter.autoconfigure.GreeterAutoConfiguration` corresponds to `edu/example/greeter/autoconfigure/GreeterAutoConfiguration.class`. When renaming/moving classes, update imports and rebuild. If the class depends on a type absent from the runtime classpath, the application can still fail when loading or processing the configuration.

### 9.3. Class Is Present Yet Bean Is Missing

Do not rush to change packaging. Check `@ConditionalOnProperty`, `@ConditionalOnClass`, `@ConditionalOnMissingBean`, exclusions, user beans, and bean creation errors. Use `--debug` and `ApplicationContext` to pinpoint which step left the bean absent.

### 9.4. Looking Only in the Outer Executable JAR

`jar tf app.jar` shows `BOOT-INF/lib/greeter-autoconfigure-1.0.0.jar` but does not list individual entries inside the nested JAR. Extract the dependency and inspect the nested JAR as in section 8. Do not conclude the file is missing just because you do not see it at the root of the outer archive.

### 9.5. Reusing an Old Build

Sources changed yet the local Maven repository, Gradle cache, dependency version, or executable JAR is still using an old build. Verify actual names/versions and artifacts. In the exercise, after editing the library re-run `mvn -q clean install`, then rebuild the consumer.

### 9.6. Shading Drops Resources

When merging multiple JARs into one with a shading plugin, libraries may share the `AutoConfiguration.imports` path. If the merge keeps only one entry, class lists from other libraries are lost. Configure an appropriate resource transformer and verify **the post-shade file contents** retain all class names.

### 9.7. Renaming an Already-Published Auto-Configuration

Besides updating imports in the new release, Spring Boot also supports `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.replacements` to represent class renames affecting `before/after` ordering and older exclusions. This is an advanced library compatibility scenario, not required in a single-class experiment.

### 9.8. Confusing Metadata Files

`spring-autoconfigure-metadata.properties` is metadata optimizing condition filtering; `spring-configuration-metadata.json` describes properties; `spring.factories` is still used for some SPIs. None of these replace the primary `AutoConfiguration.imports` path in Boot 3.x.

## 10. Pre-Release Artifact Verification Checklist

| Step | What to Verify | Evidence |
| --- | --- | --- |
| 1 | Right JAR, right version | Artifact name, Maven/Gradle dependency coordinates |
| 2 | Right packaging type | Plain dependency JAR vs. Boot executable JAR |
| 3 | Imports at exact path and inside artifact | `jar tf` or `JarFile.getJarEntry` |
| 4 | FQCN content accurate and complete | `jar xf`, `unzip -p`, or `InspectImports.java` |
| 5 | Class/dependencies loadable | `.class` entry and runtime dependencies |
| 6 | Consumer uses that artifact | Dependency graph, `BOOT-INF/lib` if Boot-packaged |
| 7 | Auto-config class not accidentally scanned | Separate package and component scan scope |
| 8 | Conditions match per scenario | Condition Evaluation Report |
| 9 | Bean present or absent as intended | `getBeanNamesForType`, `containsBean`, actual injection |

In CI, you can perform a minimal post-build check:

~~~bash
mvn -q clean package
jar tf target/greeter-autoconfigure-1.0.0.jar |
  grep -F 'META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports'
~~~

The snippet above is for Unix. On Windows use `Select-String`; to fail with an exit code when the entry is missing on any OS, you can use `InspectImports.java` from section 5 (exit code `2` if the entry is absent).

2. **Change the FQCN in imports:** intentionally misspell the class name and rebuild. Inspect the JAR contents, class entry, and startup error. Distinguish a class-name error from a condition error.
3. **Disable the bean via property:** keep the valid JAR, run `--demo.greeter.enabled=false` with `--debug`. Why does imports still exist yet no bean is created?
4. **User bean precedence:** run `--demo.override=true`; prove the class is still considered, yet `libraryGreeter` does not create a default bean.
5. **Try exclusion:** run with `spring.autoconfigure.exclude` and compare with `demo.greeter.enabled=false`. Both lack the bean, so how do the two processing paths differ?
6. **Open the nested JAR:** build the consumer with `mvn -q clean package`, inspect `BOOT-INF/lib`, extract the library JAR, and read the imports file; compare with the standalone library JAR.
7. **Compare old and new artifacts:** modify imports, rebuild/reinstall the library, without rebuilding the executable consumer yet. Compare version/timestamp and explain why the final artifact must be inspected.
8. **Try two candidates:** add another `@AutoConfiguration` class and an FQCN line to imports. Verify both lines are packaged; inspect conditions in the report.

### Self-Assessment Questions

- What is the exact imports filename in Spring Boot 3.x?
- Why inspect the **packaged JAR** instead of looking only at `src/main/resources`?
- How does `jar tf` differ from `jar xf` and `unzip -p`?
- What do dots in an FQCN become when cross-checking against `.class` paths?
- Why can not seeing imports at the root of an executable JAR still be the expected result?
- What does the imports file prove about candidates, and what does it not prove about beans?
- When should you inspect the Condition Evaluation Report?
- When shading multiple libraries, why can same-path resources be lost?

**Completion criteria:** from a real library JAR, you can locate the `AutoConfiguration.imports` entry yourself, read the FQCN and cross-check it against the class; verify the JAR is present on the runtime classpath; test a consuming application to accurately explain both when a bean exists and when a bean is blocked by conditions.
