# `withBean` to Supply User Beans for Experiments with `ApplicationContextRunner`

When testing a Spring Boot auto-configuration, we often need to simulate a scenario where the application **has already declared a bean itself**. For instance, a starter provides a default `PaymentGateway` via `@ConditionalOnMissingBean`; the test must prove the default bean is registered when no gateway exists yet, yet yields when the user provides their own implementation.

`ApplicationContextRunner` provides the `withBean` method to add a bean to the test context without creating an extra `@Configuration` class just to declare a single `@Bean` method. This method gives clear control over **bean name, bean type, instance creation, and certain bean definition attributes**. It is especially useful when writing many small experiments with different bean combinations.

**Key takeaway:** `withBean` registers a user bean into **the context created by the runner for the test**. It does not alter a running application and does not automatically replace an existing bean. Auto-configuration only backs off when its condition actually recognizes that bean, such as matching the `PaymentGateway.class` type or the exact bean name.

## 1. What problem does `withBean` solve?

Suppose a starter has an auto-configuration:

```java
@AutoConfiguration
public class PaymentGatewayAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(PaymentGateway.class)
    PaymentGateway defaultPaymentGateway() {
        return new DefaultPaymentGateway();
    }
}
```

This is an illustrative snippet: `PaymentGateway` and `DefaultPaymentGateway` are project-defined types. In tests, we want to construct two scenarios:

- No `PaymentGateway` bean exists: the auto-configuration registers `defaultPaymentGateway`.
- An application-provided `PaymentGateway` bean exists: the default method backs off.

Using `withUserConfiguration`, we could create a separate configuration class:

```java
@Configuration(proxyBeanMethods = false)
static class UserConfiguration {

    @Bean
    PaymentGateway customPaymentGateway() {
        return new PartnerPaymentGateway();
    }
}
```

Then pass it to the runner via `withUserConfiguration(UserConfiguration.class)`. This works well when you want to test an entire configuration group, multiple `@Bean` methods, `@Import`, custom conditions, or initialization logic.

However, if you only need to add **one specific bean** to test a back-off condition, `withBean` is shorter and more direct:

```java
new ApplicationContextRunner()
        .withConfiguration(AutoConfigurations.of(
                PaymentGatewayAutoConfiguration.class
        ))
        .withBean(
                "customPaymentGateway",
                PaymentGateway.class,
                () -> new PartnerPaymentGateway()
        )
        .run(context -> {
            // Verify the custom bean and that the default backs off.
        });
```

The runner creates a new context for that run, registers the user bean, loads the auto-configuration, and invokes the callback so the test can inspect the context. After the callback, the context is closed. Each `run` call is an independent experiment, sharing no bean instances from the previous context unless the test intentionally supplies a shared external object inside the supplier.

## 2. Overloads of `withBean`

In Spring Boot 3.3, `withBean` is declared on `AbstractApplicationContextRunner` and inherited by `ApplicationContextRunner`, `WebApplicationContextRunner`, and `ReactiveWebApplicationContextRunner`.

There are four common forms:

| Call signature | Meaning |
| --- | --- |
| `withBean(Class<T> type, Object... constructorArgs)` | Registers a bean by type; Spring performs constructor resolution with the supplied arguments. The bean name is generated by the context's `BeanNameGenerator`. |
| `withBean(String name, Class<T> type, Object... constructorArgs)` | Same as above, but specifies the bean name. You may pass `null` for name to use the auto-generated name. |
| `withBean(Class<T> type, Supplier<T> supplier, BeanDefinitionCustomizer... customizers)` | Registers a bean by type and supplies a supplier to create the instance; the name is auto-generated. |
| `withBean(String name, Class<T> type, Supplier<T> supplier, BeanDefinitionCustomizer... customizers)` | Combines an explicit bean name, a supplier, and bean definition customizers. |

Example using constructor arguments:

```java
runner.withBean(PaymentGateway.class, "sandbox");
```

Example specifying a name and supplier:

```java
runner.withBean(
        "customGateway",
        PaymentGateway.class,
        () -> new PartnerPaymentGateway()
);
```

If a constructor has multiple parameters, the passed arguments are used during Spring's constructor resolution; remaining dependencies can be autowired under standard rules. If you need full control over object creation, use a supplier.

**Builder note:** every call to `withBean` returns **a new customized runner**, without mutating the original runner. Therefore, you must chain calls or capture the returned reference:

```java
ApplicationContextRunner customRunner =
        baseRunner.withBean(
                "customGateway",
                PaymentGateway.class,
                () -> new PartnerPaymentGateway()
        );

customRunner.run(context -> {
    // Experiment with customGateway.
});

baseRunner.run(context -> {
    // The base runner remains an experiment without customGateway.
});
```

If you call `baseRunner.withBean(...)` and ignore the return value, the bean will not be added to runs of the original `baseRunner`.

## 3. Using `withBean` to test `@ConditionalOnMissingBean`

This is the most important scenario when developing a starter. Application-provided beans should typically be recognized by **contract type**, allowing users to freely choose bean names.

Example:

```java
@AutoConfiguration
public class GatewayAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(PaymentGateway.class)
    PaymentGateway defaultGateway() {
        return new PaymentGateway("default");
    }
}
```

In the test, add a bean with a different name but the same type:

```java
runner.withBean(
        "partnerGateway",
        PaymentGateway.class,
        () -> new PaymentGateway("partner")
).run(context -> {
    assertThat(context.getBeansOfType(PaymentGateway.class))
            .containsOnlyKeys("partnerGateway");

    assertThat(context.getBean(PaymentGateway.class).id())
            .isEqualTo("partner");

    assertThat(context).doesNotHaveBean("defaultGateway");
});
```

Expected outcome: `partnerGateway` exists; `defaultGateway` is not registered. No same-name bean definition overriding occurs. The type-based condition sees the user bean and **prevents the default method from registering**.

### 3.1. Must match condition criteria

Suppose the auto-configuration uses a name-based condition:

```java
@Bean
@ConditionalOnMissingBean(name = "defaultGateway")
PaymentGateway defaultGateway() {
    return new PaymentGateway("default");
}
```

If the test supplies `partnerGateway`, that condition can still match because **no bean named `defaultGateway` exists yet**. The result can be two beans of the same type:

```text
partnerGateway : PaymentGateway
defaultGateway : PaymentGateway
```

In that case, looking up a single bean by type may throw `NoUniqueBeanDefinitionException` if no `@Primary` candidate or matching qualifier exists. This is not a bug in `withBean`; the test accurately simulated the name-based condition specified in the source.

Therefore, before writing a test, read the condition annotation at the **exact level**:

- `@ConditionalOnMissingBean(PaymentGateway.class)`: checks for a bean by contract type.
- `@ConditionalOnMissingBean(name = "defaultGateway")`: checks for a bean by name.
- `@ConditionalOnMissingBean` with no attributes specified on a `@Bean` method: Spring Boot can infer the type from the method's declared return type.

A useful test must mirror the auto-configuration's actual contract. Do not keep renaming the test bean until assertions pass; if the condition checks by name, the name itself is part of the input under verification.

## 4. Supplying multiple beans of the same type and testing ambiguity

`withBean` can be called multiple times to register multiple implementations:

```java
runner
    .withBean("bankGateway", PaymentGateway.class,
            () -> new PaymentGateway("bank"))
    .withBean("cardGateway", PaymentGateway.class,
            () -> new PaymentGateway("card"))
    .run(context -> {
        assertThat(context.getBeansOfType(PaymentGateway.class))
                .containsOnlyKeys("bankGateway", "cardGateway");

        assertThatThrownBy(() -> context.getBean(PaymentGateway.class))
                .isInstanceOf(NoUniqueBeanDefinitionException.class);
    });
```

The snippet above assumes a `PaymentGateway` record or class taking an id string. Two differently named beans of the same type can coexist. When injecting a single `PaymentGateway`, Spring does not know which bean to pick without additional rules.

This is a helpful test pattern when a starter allows multiple plugins, strategies, or implementations of the same interface. You can inspect the collection via `getBeansOfType`, `getBeanNamesForType`, or `ObjectProvider<PaymentGateway>.stream()` instead of requiring a single bean.

### 4.1. Setting a preferred bean with `BeanDefinitionCustomizer`

The supplier overloads accept `BeanDefinitionCustomizer` arguments to modify definition metadata before the bean is used. For example, marking a bean as `primary`:

```java
runner
    .withBean(
            "preferredGateway",
            PaymentGateway.class,
            () -> new PaymentGateway("preferred"),
            definition -> definition.setPrimary(true)
    )
    .withBean(
            "secondaryGateway",
            PaymentGateway.class,
            () -> new PaymentGateway("secondary")
    )
    .run(context -> {
        assertThat(context.getBean(PaymentGateway.class).id())
                .isEqualTo("preferred");
    });
```

`@Primary` does not remove the other bean. Both still exist; the primary rule simply helps Spring pick a bean when an injection point requests a single `PaymentGateway`.

### 4.2. Customizing lazy initialization and scope

You can also use a customizer to test bean lifecycle:

```java
// Register a lazy bean:
.withBean(
        "lazyGateway",
        PaymentGateway.class,
        () -> new PaymentGateway("lazy"),
        definition -> definition.setLazyInit(true)
)

// Register a prototype bean:
.withBean(
        "prototypeGateway",
        PaymentGateway.class,
        () -> new PaymentGateway("prototype"),
        definition -> definition.setScope(
                ConfigurableBeanFactory.SCOPE_PROTOTYPE
        )
)
```

- `setLazyInit(true)` defers singleton creation until the bean is requested. The supplier is not invoked merely because the runner was configured.
- `setScope(SCOPE_PROTOTYPE)` makes Spring create a new instance on each prototype lookup.
- Unless another scope is set, beans default to singleton scope.

A supplier does not necessarily execute when `withBean` is called. For non-lazy singletons, Spring normally invokes the supplier during context refresh to create the bean. For lazy singletons, the supplier runs on first access. For prototypes, the supplier can be called on every instance request.

Do not pre-create a single mutable object outside and return it repeatedly from a supplier across multiple contexts. Create a fresh object inside the supplier so each run has an isolated lifecycle.

## 5. Complete example: Java 17, Spring Boot 3.3.5, and JUnit 5

The test suite below verifies six behaviors:

1. Without a user bean, auto-configuration registers the default.
2. Adding a bean with a supplier and explicit name makes a type-based condition back off.
3. The constructor-arguments overload can create a user bean.
4. A name-based condition may still register the default when a user bean has the same type but a different name.
5. Multiple beans of the same type cause ambiguity; a `setPrimary(true)` customizer selects one.
6. A lazy supplier executes only when the bean is requested.

### 5.2. Complete test file

Create `src/test/java/demo/WithBeanExperimentTest.java`:

```java
package demo;

import java.util.concurrent.atomic.AtomicInteger;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.NoUniqueBeanDefinitionException;
import org.springframework.beans.factory.config.ConfigurableBeanFactory;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Bean;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class WithBeanExperimentTest {

    public record PaymentGateway(String id) {
    }

    @AutoConfiguration
    public static class TypeBasedGatewayAutoConfiguration {

        @Bean
        @ConditionalOnMissingBean(PaymentGateway.class)
        PaymentGateway defaultGateway() {
            return new PaymentGateway("default");
        }
    }

    @AutoConfiguration
    public static class NameBasedGatewayAutoConfiguration {

        @Bean
        @ConditionalOnMissingBean(name = "defaultGateway")
        PaymentGateway defaultGateway() {
            return new PaymentGateway("default");
        }
    }

    private final ApplicationContextRunner typeRunner =
            new ApplicationContextRunner()
                    .withConfiguration(AutoConfigurations.of(
                            TypeBasedGatewayAutoConfiguration.class
                    ));

    private final ApplicationContextRunner nameRunner =
            new ApplicationContextRunner()
                    .withConfiguration(AutoConfigurations.of(
                            NameBasedGatewayAutoConfiguration.class
                    ));

    @Test
    void defaultBeanIsRegisteredWhenNoUserBeanExists() {
        typeRunner.run(context -> {
            assertThat(context).hasNotFailed();

            assertThat(context.getBeansOfType(PaymentGateway.class))
                    .containsOnlyKeys("defaultGateway");

            assertThat(context.getBean(PaymentGateway.class).id())
                    .isEqualTo("default");
        });
    }

    @Test
    void namedSupplierBeanMakesTypeBasedConditionBackOff() {
        typeRunner.withBean(
                        "partnerGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("partner")
                )
                .run(context -> {
                    assertThat(context).hasNotFailed();

                    assertThat(context.getBeansOfType(PaymentGateway.class))
                            .containsOnlyKeys("partnerGateway");

                    assertThat(context.getBean(PaymentGateway.class).id())
                            .isEqualTo("partner");

                    assertThat(context).doesNotHaveBean("defaultGateway");
                });
    }

    @Test
    void constructorArgumentsCanCreateUserBean() {
        typeRunner.withBean(PaymentGateway.class, "constructor-user")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context).hasSingleBean(PaymentGateway.class);

                    assertThat(context.getBean(PaymentGateway.class).id())
                            .isEqualTo("constructor-user");

                    assertThat(context).doesNotHaveBean("defaultGateway");
                });
    }

    @Test
    void nameBasedConditionDoesNotBackOffForDifferentBeanName() {
        nameRunner.withBean(
                        "partnerGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("partner")
                )
                .run(context -> {
                    assertThat(context).hasNotFailed();

                    assertThat(context.getBeansOfType(PaymentGateway.class))
                            .containsOnlyKeys(
                                    "partnerGateway",
                                    "defaultGateway"
                            );
                });
    }

    @Test
    void multipleBeansCanBeInspectedAndPrimaryCanSelectOne() {
        typeRunner
                .withBean(
                        "bankGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("bank")
                )
                .withBean(
                        "cardGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("card")
                )
                .run(context -> {
                    assertThat(context).hasNotFailed();

                    assertThat(context.getBeansOfType(PaymentGateway.class))
                            .containsOnlyKeys("bankGateway", "cardGateway");

                    assertThatThrownBy(
                            () -> context.getBean(PaymentGateway.class)
                    ).isInstanceOf(NoUniqueBeanDefinitionException.class);
                });

        typeRunner
                .withBean(
                        "preferredGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("preferred"),
                        definition -> definition.setPrimary(true)
                )
                .withBean(
                        "secondaryGateway",
                        PaymentGateway.class,
                        () -> new PaymentGateway("secondary")
                )
                .run(context -> {
                    assertThat(context).hasNotFailed();

                    assertThat(context.getBeansOfType(PaymentGateway.class))
                            .containsOnlyKeys(
                                    "preferredGateway",
                                    "secondaryGateway"
                            );

                    assertThat(context.getBean(PaymentGateway.class).id())
                            .isEqualTo("preferred");
                });
    }

    @Test
    void lazySupplierRunsOnlyWhenBeanIsRequested() {
        AtomicInteger supplierCalls = new AtomicInteger();

        typeRunner.withBean(
                        "lazyGateway",
                        PaymentGateway.class,
                        () -> {
                            supplierCalls.incrementAndGet();
                            return new PaymentGateway("lazy");
                        },
                        definition -> definition.setLazyInit(true)
                )
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(supplierCalls.get()).isZero();

                    assertThat(context.getBean(
                            "lazyGateway",
                            PaymentGateway.class
                    ).id()).isEqualTo("lazy");

                    assertThat(supplierCalls.get()).isEqualTo(1);
                });
    }
}
```

Run from the `withbean-lab` directory with JDK 17+ and Maven:

```bash
mvn test
```

**Expected result:** six test methods succeed; the fifth test creates two independent contexts to test ambiguity and primary. Maven Surefire typically reports `Tests run: 6, Failures: 0, Errors: 0, Skipped: 0`. The tests do not call `System.out.println`, so there is no fixed business stdout.

### 5.3. Reading results per experiment

| Test | Runner input | Observed result |
| --- | --- | --- |
| `defaultBeanIsRegisteredWhenNoUserBeanExists` | Only type-based auto-configuration loaded | Only `defaultGateway` exists. |
| `namedSupplierBeanMakesTypeBasedConditionBackOff` | `partnerGateway` of type `PaymentGateway` created via supplier | Only `partnerGateway` remains; default is not registered. |
| `constructorArgumentsCanCreateUserBean` | `withBean(PaymentGateway.class, "constructor-user")` | Spring uses `PaymentGateway`'s constructor to create the bean; type condition backs off. |
| `nameBasedConditionDoesNotBackOffForDifferentBeanName` | User bean `partnerGateway`, condition checking name `defaultGateway` | Both `partnerGateway` and `defaultGateway` exist. |
| `multipleBeansCanBeInspectedAndPrimaryCanSelectOne` | Two user beans of the same type; then retried with one primary bean | First case lookup by type is ambiguous; second case selects `preferredGateway`. |
| `lazySupplierRunsOnlyWhenBeanIsRequested` | Supplier with customizer `setLazyInit(true)` | Counter is 0 before lookup and 1 after the first lookup. |

A notable detail in the fifth test: each `run` call creates a separate context. The two gateways from the first experiment do not leak into the subsequent primary experiment. The original `typeRunner` is also unmodified; each `withBean` chain returns a new runner.

## 6. How does `withBean` differ from `withUserConfiguration` and `@Bean`?

| Approach | Best suited when | Example |
| --- | --- | --- |
| `withBean` | Need to add one specific bean to simulate an input for a condition or injection. | Add a custom `PaymentGateway` via supplier. |
| `withUserConfiguration` | Need to test application configuration with multiple beans, `@Import`, conditions, factory methods, or configuration logic. | Load `UserGatewayConfiguration.class`. |
| `withPropertyValues` | Need to alter Environment to test `@ConditionalOnProperty` or binding. | `withPropertyValues("payment.gateway=partner")`. |
| `withInitializer` | Need to run context initialization before refresh or register special components. | Add an `ApplicationContextInitializer`. |
| `withParent` | Need to simulate a context hierarchy and ancestor bean lookup conditions. | Supply a parent ApplicationContext to the runner. |

`withBean` fits simple, explicit inputs. If you want to test how Spring processes a real user configuration class, create a `@Configuration` class and load it with `withUserConfiguration`; that exercises the application's actual configuration path.

For example, to test a user configuration containing a factory method and a property condition:

```java
@Configuration(proxyBeanMethods = false)
static class UserGatewayConfiguration {

    @Bean
    @ConditionalOnProperty(
            prefix = "payment",
            name = "gateway",
            havingValue = "partner"
    )
    PaymentGateway partnerGateway() {
        return new PaymentGateway("partner");
    }
}
```

In that case, use `withUserConfiguration(UserGatewayConfiguration.class)` combined with `withPropertyValues`. Do not fake complex configuration with a supplier when the test target is annotation processing and factory method behavior itself.

## 7. Registration order, name collisions, and common mistakes

### 7.1. Beans are added after regular user configurations

Per Spring Boot's API, beans from `withBean` are registered after regular user configurations and in the order `withBean` is called. Auto-configurations are loaded via deferred imports, making user beans appropriate inputs for testing auto-configuration back-off conditions.

However, do not rely on `withBean` to control ordering between unrelated auto-configurations. If two auto-configurations compete for the same type, declare appropriate `before/after` or ordering and test it separately.

### 7.2. `withBean` is not a bean definition replacement API

If a test registers `withBean("gateway", ...)` while another user configuration already registered a bean with the same name `gateway`, a bean definition conflict can occur. When overriding is disabled, the context can fail with `BeanDefinitionOverrideException`.

The runner provides `withAllowBeanDefinitionOverriding(true)` specifically for testing same-name definition overriding scenarios. However, **do not enable it just to force a back-off test to pass**. Enabling overriding can mask condition bugs: instead of the default yielding naturally, one same-name definition might simply overwrite another.

For `@ConditionalOnMissingBean` tests, use a distinctly named bean and verify the exact type or name that the condition actually checks.

### 7.3. Common issues

| Symptom | Possible cause | Resolution |
| --- | --- | --- |
| Default still appears despite calling `withBean` | Condition checks a different name or type from the test bean; or condition is on another source | Read the exact annotation and inspect bean names/types in the context. |
| Context fails due to duplicate name | Test bean and configuration bean register the same name | Pick a different name when testing back-off; only test overriding when that is the specific goal. |
| Test bean missing from context | Called `withBean` but discarded the returned runner | Chain the builder or store the new runner in a variable. |
| Supplier has not executed | Bean is marked lazy and has not been accessed yet | Call `getBean` or inspect instantiation timing properly. |
| Supplier runs immediately during refresh | Bean is a non-lazy singleton by default | Use customizer `setLazyInit(true)` if testing laziness. |
| `getBean(Type.class)` reports non-unique bean | Multiple beans of the same type without primary/qualifier | Inspect the bean map/names, use `@Primary`/qualifier, or iterate multiple beans. |
| Test passes only when overriding is enabled | Back-off condition may be wrong or two beans share the same name | Remove overriding and re-check conditions; do not mask design bugs. |
| One test affects another | Shared context/mutable object outside supplier or state stored outside runner | Each `run` creates a fresh context; create beans inside the supplier and avoid shared mutable state. |
| Startup fails but assertions hide the cause | `run` still passes a failed context into the callback | Use `hasNotFailed()` or inspect startup failure before looking up beans. |

### 7.4. Distinguishing bean definitions from bean instances

`withBean` registers a **definition** first. The supplier is how an instance is created when Spring needs the bean. Consequently:

- Conditions like `@ConditionalOnMissingBean` typically inspect metadata/bean definitions; they do not need to invoke the supplier to know a bean type is registered.
- `@Lazy` can defer instance creation, while the definition still exists for conditions to see.
- `SCOPE_PROTOTYPE` allows the supplier to be invoked multiple times, once per bean retrieval.
- A supplier with side effects such as opening sockets or connecting to databases should only be used in tests if those side effects are controlled; prefer suppliers creating small, deterministic objects.

## 8. Checklist for writing experiments with `withBean`

1. Read the auto-configuration's conditions: does it check by type, name, annotation, or property?
2. Pick the right overload: constructor args if Spring should resolve the constructor; supplier if you need full instance control.
3. Specify a bean name when assertions or conditions depend on the name; otherwise an auto-generated name works.
4. If primary, lazy, or scope is needed, use `BeanDefinitionCustomizer`.
5. Call `withBean` on the runner and **keep the new runner** returned by the method.
6. Use a separate `run` for each case to ensure an independent context.
7. Assert both bean names/types and the behavior under verification; do not only check that the context starts.
8. For multiple beans of the same type, test ambiguity or explicit `@Primary`/`@Qualifier` rules.
9. Do not enable bean definition overriding to hide an unmatched condition.
10. If the context fails, inspect startup failure before calling `getBean`.

**Takeaway:** `withBean` is a concise way to introduce **simulated user beans** into an `ApplicationContextRunner` experiment. Use the constructor-arguments overload for standard instantiation; use suppliers for direct instance control; use customizers to adjust primary, lazy, or scope. To test auto-configuration back-off, the most important requirement is that the test bean matches **the exact condition criteria**. A bean of the same type with a different name makes a type-based condition back off, while a name-based condition will still register the default.
