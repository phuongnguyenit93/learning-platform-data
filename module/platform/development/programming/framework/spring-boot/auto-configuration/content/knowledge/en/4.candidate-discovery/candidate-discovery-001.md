# Registering Auto-Configuration with META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

## 1. Objective and Problem to Solve

A library can provide an `@AutoConfiguration` class so that a Spring Boot application automatically picks up default configuration when the library is added to the classpath. However, **merely placing the annotation on a class does not make Spring Boot discover that class automatically**. In the modern Spring Boot mechanism, the library author must also register the **fully qualified class name** in a special resource file:

~~~text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

This is a **relative path from the classpath root of the JAR** containing the auto-configuration. In a typical Maven or Gradle project, the resource source file should be placed at:

~~~text
src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

When compiling/packaging, the resource must actually be present in the runtime output. In a standard library JAR, the path inside the JAR is `META-INF/spring/...imports`. In an executable Spring Boot JAR, the application module's resources typically reside under `BOOT-INF/classes/META-INF/spring/...imports`; resources from bundled library JARs reside inside nested JARs under `BOOT-INF/lib`.

After this lesson, you will know why Spring Boot needs this file, how to write each line properly, build a runnable Java 17+ example, observe the results when metadata is present or missing, and troubleshoot when auto-configuration is not activated.

**Scope:** focuses solely on the mechanism of *registering and discovering auto-configuration candidates*. Conditions such as `@ConditionalOnClass`, `@ConditionalOnProperty`, `@ConditionalOnMissingBean`, and configuration ordering are explained only as needed, because **registering a candidate does not guarantee a bean will be created**.

## 2. Role of the AutoConfiguration.imports File

Spring Boot looks for resource files named exactly `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` on the classpath. Each library JAR can contain its own file. Boot aggregates the declared auto-configuration classes, then applies a pipeline of selection, exclusion, ordering, and conditions to decide which configurations participate in the context.

The file content is **plain text**, for example:

~~~text
com.example.invoice.autoconfigure.InvoiceAutoConfiguration
com.example.invoice.autoconfigure.InvoiceWebAutoConfiguration
~~~

Rules:

1. **Each line is a fully qualified class name (FQCN)**, including the package and Java class name. Do not write a short name like `InvoiceAutoConfiguration` if the class is inside a package.
2. **Do not append `.class`**, do not write `import ...;` syntax, and do not use JSON, XML, YAML, or `key=value` like `spring.factories`.
3. Lines starting with the `#` character can be used as comments:

   ~~~text
   # Auto-configuration for the invoice service
   com.example.invoice.autoconfigure.InvoiceAutoConfiguration
   ~~~

4. The filename is case-sensitive on corresponding filesystems: it must be exactly `AutoConfiguration.imports`; do not use `autoconfiguration.imports` or `AutoConfiguration.import`.
5. The `META-INF/spring` path must reside **in the packaged resources**, not just exist in the source tree.
6. If the auto-configuration is a nested class rather than a top-level class, the binary name uses `$` between the enclosing class name and the nested class name, for example `com.example.Outer$NestedAutoConfiguration`. In real-world libraries, prefer top-level classes for easier management.

This mechanism is **not a direct bean registration file**. The file lists **candidate configuration classes**, not `@Bean` method names, service interfaces, or implementation classes to be created.

### Comparison with Commonly Confused Files

| File or Mechanism | Role |
| --- | --- |
| `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` | Registers **candidate auto-configuration classes** in modern Spring Boot. |
| `META-INF/spring.factories` | A properties-style metadata mechanism used for many Spring Boot extensions such as `EnvironmentPostProcessor` and `ApplicationContextInitializer`; older auto-configuration guides used `EnableAutoConfiguration` here. |
| `META-INF/spring-autoconfigure-metadata.properties` | Metadata that optimizes filtering of certain auto-configurations; usually generated by an annotation processor, **does not replace the imports file**. |
| `META-INF/spring-configuration-metadata.json` | Metadata providing hints on `@ConfigurationProperties` names/types/descriptions for IDEs and tools; **does not register auto-configuration**. |
| `@ComponentScan` | Scans application components in specific packages; **not the proper mechanism for discovering library auto-configuration**. |
| `@Import(SomeConfiguration.class)` | Imports a specific configuration at a designated location; not the way to publish all candidates of a starter for Boot. |

Spring Boot 2.7 introduced the imports file mechanism; in Spring Boot 3.x, this is the standard mechanism for declaring auto-configuration. If referencing legacy Spring Boot 2.x projects that use `org.springframework.boot.autoconfigure.EnableAutoConfiguration` in `spring.factories`, verify the exact version and migration path before applying it. **Do not conclude that every use of `spring.factories` is obsolete**: other extensions still use that mechanism in appropriate versions.

## 3. Flow: When Does the Metadata File Participate in Startup?

In an application with `@SpringBootApplication` or `@EnableAutoConfiguration`, the auto-configuration mechanism is enabled. The flow can be pictured as:

~~~text
Application calls SpringApplication.run(...)
       |
       v
@SpringBootApplication
  └── @EnableAutoConfiguration
       |
       v
AutoConfigurationImportSelector (DeferredImportSelector)
       |
       +-- Locate AutoConfiguration.imports resources on the classpath
       +-- Read candidate class names from JARs
       +-- Apply exclusions, filters, and ordering
       |
       v
Spring processes the selected @AutoConfiguration classes
       |
       +-- @ConditionalOnClass, @ConditionalOnProperty, ...
       +-- @Bean + @ConditionalOnMissingBean, ...
       |
       v
Register valid bean definitions
       |
       v
Bean factory creates required beans according to the Spring lifecycle
~~~

Four concepts to separate:

- **JAR on classpath:** this only proves the library has been provided to the application. It does not guarantee imports metadata is present.
- **Imports entry found:** Boot knows the name of a candidate auto-configuration. It does not guarantee the class is selected after filtering and exclusions.
- **Auto-configuration class selected and conditions match:** Spring can register bean definitions declared by that class.
- **Bean actually exists and initializes successfully:** still depends on conditions on `@Bean`, the presence of other beans, dependencies, scope, and runtime errors.

`AutoConfigurationImportSelector` implements `DeferredImportSelector`, so auto-configurations are processed in the deferred import phase, after the application's regular configurations. This gives bean-based conditions, especially `@ConditionalOnMissingBean`, a chance to detect beans provided by the application before registering defaults. “Deferred” here **does not mean loading resources on a background thread, waiting for the first request, or instantiating beans after the application is ready**.

### Why Can a Single JAR Have Multiple Imports Lines?

A library may integrate multiple optional parts. For example, one configuration for the core service and one configuration solely for servlet web. The author can list both classes as **candidates** and then apply appropriate conditions on each class. If the required web library is absent, the web configuration can be skipped. Each line in the imports file is not an “unconditionally on” switch.

## 4. Proper Structure and Package Placement

An illustrative layout:

~~~text
invoice-spring-boot/
├── pom.xml
└── src/main/
    ├── java/
    │   └── com/example/invoice/
    │       ├── api/InvoiceFormatter.java
    │       └── autoconfigure/InvoiceAutoConfiguration.java
    └── resources/
        └── META-INF/spring/
            └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

When an application uses this library, it only needs to add the dependency containing the auto-configuration and have auto-configuration enabled; Boot will see the metadata on the classpath. In large projects, you can split into an `invoice-spring-boot-autoconfigure` module containing code/metadata and an `invoice-spring-boot-starter` module aggregating appropriate dependencies; **splitting modules is not mandatory** if the problem is small.

The configuration class is typically written as:

~~~java
package com.example.invoice.autoconfigure;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.context.annotation.Bean;

@AutoConfiguration
@ConditionalOnClass(name = "com.example.invoice.api.InvoiceFormatter")
public class InvoiceAutoConfiguration {

    // Appropriate optional @Bean methods are defined here.
}
~~~

This is a snippet illustrating the annotation mechanism; the body has no `@Bean` and creates no beans. Having the annotation on the class without an entry in the imports file means external applications are **not guaranteed** to discover this configuration via the auto-configuration mechanism.

**Recommendation from Spring Boot documentation:** place auto-configuration in a dedicated package **outside the area scanned by component scanning**. Do not add `@ComponentScan` to auto-configuration to pick up beans uncontrollably; when you need to import a specific configuration, use `@Import` intentionally. Separating packages helps Boot's conditions and ordering orchestration work as intended.

### Why Not Confuse “File Present” with “File Effective”?

For example, the file might exist at `src/test/resources/META-INF/spring/...` but not in the main runtime artifact; when running the released JAR, Boot will not see it. Similarly, writing valid metadata in module A when the application does not depend on module A at runtime means the metadata is also absent from the classpath. What matters is the **classpath of the running process**, not merely the file status in the IDE.

## 5. Complete Java 17+ Example: One Metadata File, Three Bean Outcomes

We create a small Spring Boot application in which:

- `@AutoConfiguration` is outside the application's component scan package.
- `AutoConfiguration.imports` registers the exact class name.
- The auto-configuration adds a default `MessageService` if no bean of the same type exists yet.
- The application can enable its own bean; the auto-configuration must step back.
- The sample auto-configuration can be disabled via a property to prove that an entry in the imports file **does not mean a bean is always created**.

All code is self-contained in the example project. Uses **Spring Boot 3.5.0, JDK 17+, and Maven**.

### 5.1. Project Structure

~~~text
auto-imports-demo/
├── pom.xml
└── src/main/
    ├── java/com/example/
    │   ├── api/MessageService.java
    │   ├── app/DemoApplication.java
    │   └── autoconfigure/MessageAutoConfiguration.java
    └── resources/
        ├── application.properties
        └── META-INF/spring/
            └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

The application class's package is `com.example.app`; the auto-configuration's package is `com.example.autoconfigure`. Default component scanning from `com.example.app` **does not** scan `com.example.autoconfigure`. The imports file is the exact factor that brings the sample configuration into the application.

### 5.2. pom.xml

~~~xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.0</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>auto-imports-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter</artifactId>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

`spring-boot-starter` provides the core components needed to run Spring Boot without a web server. The example requires no database, HTTP endpoints, or external services.

### 5.3. MessageService.java

File `src/main/java/com/example/api/MessageService.java`:

~~~java
package com.example.api;

public interface MessageService {
    String message();
}
~~~

Having only the interface on the `classpath` does not automatically create a bean. It serves as the common type for the application bean and the default bean.

### 5.4. MessageAutoConfiguration.java

File `src/main/java/com/example/autoconfigure/MessageAutoConfiguration.java`:

~~~java
package com.example.autoconfigure;

import com.example.api.MessageService;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.context.annotation.Bean;

@AutoConfiguration
@ConditionalOnProperty(
        prefix = "demo",
        name = "auto",
        havingValue = "true",
        matchIfMissing = true
)
public class MessageAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(MessageService.class)
    public MessageService defaultMessageService() {
        return () -> "AUTO";
    }
}
~~~

Explanation:

- `@AutoConfiguration` declares this as an auto-configuration class.
- `@ConditionalOnProperty` on the class allows it to apply when `demo.auto=true` or when this key is missing; `--demo.auto=false` causes the condition not to match.
- `@ConditionalOnMissingBean(MessageService.class)` on the `@Bean` method ensures the default bean is registered only when no matching `MessageService` bean exists in the context at the time the condition is evaluated.
- The method returns a Java lambda implementing the `MessageService` interface. The `AUTO` output is data defined by the example, not a special bean built into Boot.

### 5.5. Creating AutoConfiguration.imports Correctly

Create a text file **without any extra extension** at the path:

~~~text
src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

Complete content, a single line:

~~~text
com.example.autoconfigure.MessageAutoConfiguration
~~~

Common mistakes:

- The class name in the file must match `package com.example.autoconfigure;` and `public class MessageAutoConfiguration` exactly.
- Do not append `.java` or `.class`.
- Do not write `org.springframework.boot.autoconfigure.EnableAutoConfiguration=\` at the top of the file; that is the syntax of another legacy mechanism.
- The file must be copied into the main resources output to be present when running the JAR.

### 5.6. DemoApplication.java

File `src/main/java/com/example/app/DemoApplication.java`:

~~~java
package com.example.app;

import com.example.api.MessageService;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    @Bean
    @ConditionalOnProperty(
            prefix = "demo",
            name = "custom",
            havingValue = "true"
    )
    MessageService customMessageService() {
        return () -> "CUSTOM";
    }

    @Bean
    ApplicationRunner report(ObjectProvider<MessageService> services) {
        return args -> {
            MessageService service = services.getIfAvailable();
            System.out.println("MESSAGE_SERVICE="
                    + (service == null ? "NONE" : service.message()));
        };
    }
}
~~~

`customMessageService` is the bean provided by the application when `demo.custom=true`. `ObjectProvider` allows retrieving the bean if present and returns `null` when absent; therefore, a run with no bean still prints `NONE` and does not fail startup due to mandatory injection.

### 5.7. application.properties

File `src/main/resources/application.properties`:

~~~properties
spring.main.banner-mode=off
logging.level.root=ERROR
~~~

Suppress most of the startup banner/logs to observe stdout from the program more clearly. The sample configuration has no `demo.auto` or `demo.custom` value in the file; we pass them via the command line for each scenario.

### 5.8. Packaging and Running

Install JDK 17+ and Maven. From the directory containing `pom.xml`:

~~~bash
mvn -q -DskipTests package
java -jar target/auto-imports-demo-1.0.0.jar
~~~

Stdout line printed by the program itself:

~~~text
MESSAGE_SERVICE=AUTO
~~~

Reason: the imports file makes Boot discover `MessageAutoConfiguration`; `demo.custom` is absent so the application bean is not created; the default auto condition allows it and `@ConditionalOnMissingBean` matches.

Run when the application provides a custom bean:

~~~bash
java -jar target/auto-imports-demo-1.0.0.jar --demo.custom=true
~~~

Stdout line:

~~~text
MESSAGE_SERVICE=CUSTOM
~~~

The auto-configuration can be discovered and applied, but the `defaultMessageService` bean steps back because an application bean of the same type has already been declared.

Run when disabling the default configuration and not enabling custom:

~~~bash
java -jar target/auto-imports-demo-1.0.0.jar --demo.auto=false
~~~

Stdout line:

~~~text
MESSAGE_SERVICE=NONE
~~~

The candidate auto-configuration is named in the imports file but fails the property condition; the context has no `MessageService`.

Run when disabling the default while enabling the application bean:

~~~bash
java -jar target/auto-imports-demo-1.0.0.jar --demo.auto=false --demo.custom=true
~~~

Stdout line:

~~~text
MESSAGE_SERVICE=CUSTOM
~~~

The application bean works independently of whether the sample auto-configuration matches its conditions.

| Scenario | Auto-configuration discovered? | Default bean condition | Final bean |
| --- | --- | --- | --- |
| Default run | Yes, if the imports file is packaged properly | Matches | `AUTO` |
| `--demo.custom=true` | Yes | `@ConditionalOnMissingBean` does not match | `CUSTOM` |
| `--demo.auto=false` | Yes | Configuration excluded by property | None |
| `--demo.auto=false --demo.custom=true` | Yes | Configuration excluded by property | `CUSTOM` |

The key takeaway: **all four runs keep the exact same imports file**. The variation in outcomes proves that “candidate registered” is different from “bean guaranteed to exist”.

### 5.9. Experiment: Testing a Missing Imports File

To contrast the role of the metadata file, in a **separate copy** of the sample project, temporarily remove `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, rebuild from scratch, and run with defaults:

~~~bash
mvn -q clean package -DskipTests
java -jar target/auto-imports-demo-1.0.0.jar
~~~

When `MessageAutoConfiguration` is not scanned by component scan and no longer has registration metadata, the expected output is:

~~~text
MESSAGE_SERVICE=NONE
~~~

The `MessageAutoConfiguration` class is still in the artifact, but Boot does not automatically select it via the imports mechanism. After the experiment, restore the imports file and rebuild to return the project to its normal configuration.

**Safety note when experimenting:** perform this experiment only on an example project or a copy, because removing metadata in a production library will cause applications using the library to lose the published auto-configuration.

## 6. Verifying Resources in Practice After Building

Verify against the **final artifact**, rather than assuming the IDE copied the resource.

For the newly created JAR:

~~~bash
jar tf target/auto-imports-demo-1.0.0.jar
~~~

This command lists many entries, so there is no fixed short stdout. In an executable JAR packaged by `spring-boot-maven-plugin`, look for the path:

~~~text
BOOT-INF/classes/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

For a **regular library JAR** not repackaged as an executable JAR, look for:

~~~text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
~~~

If not found:

1. Confirm the source resides under `src/main/resources`, not `src/test/resources`.
2. Check the filename, folder path, and letter casing.
3. Check the `<resources>` section in Maven or `sourceSets` settings in Gradle to see if metadata was accidentally excluded.
4. Ensure the build command runs in the module containing the auto-configuration; in a multi-module project, do not mistakenly inspect the empty starter module JAR instead of the autoconfigure module.
5. Ensure the right module is on the **runtime classpath** of the real application. A `test` or `provided` dependency may not appear where needed depending on packaging.
6. Check the FQCN in the file and the corresponding class after renaming packages or refactoring.

To inspect the **contents** of the packaged file, one way is to open the JAR with a ZIP/JAR tool or use `jar xf` in a separate inspection directory and read the exact resource. The `jar tf` command only shows entry names, not contents.

### Multi-Module Maven Case

With a two-module architecture:

~~~text
my-feature/
├── feature-autoconfigure/
│   ├── src/main/java/.../FeatureAutoConfiguration.java
│   └── src/main/resources/META-INF/spring/
│       └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
└── feature-spring-boot-starter/
    └── pom.xml  (declares dependency on feature-autoconfigure)
~~~

You must ensure:

- Metadata accompanies the **JAR containing the auto-configuration** or a JAR on the runtime classpath where the class name is also available.
- The starter provides the right dependencies so the application pulls the auto-configuration module onto the runtime classpath.
- Adding the starter to the application makes the dependency's imports resources visible to Boot; not every starter is required to have its own imports file if the file resides properly in the module the starter pulls in.
- If the library has optional dependencies, use conditions such as `@ConditionalOnClass` to avoid referencing absent classes; do not force all optional libraries to be required just for config discovery.

## 7. Discovering a Candidate Does Not Mean Conditions Always Match

The imports file is only **one step in the pipeline**. Reasons a bean does not appear despite correct metadata include:

### Class Excluded

The application can exclude an auto-configuration using `exclude` or `excludeName` on `@SpringBootApplication`/`@EnableAutoConfiguration`, or via `spring.autoconfigure.exclude`. In that case Boot knows the candidate class but does not apply the excluded class. Use exclusions with good reason; do not treat them as a workaround for broken metadata.

Example configuration excluding the **actual class from the sample project**:

~~~properties
spring.autoconfigure.exclude=com.example.autoconfigure.MessageAutoConfiguration
~~~

With `demo.custom` absent, this will also prevent the default `MessageService` from being registered even though the imports file still exists. If you need to run the demo multiple times, do not save the exclude property permanently; pass it via the command line instead.

### Class Condition Does Not Match

`@ConditionalOnClass` or `@ConditionalOnProperty` on the auto-configuration can filter out the class. Proper conditions keep the library safe when dependent technologies are unavailable.

### Condition on @Bean Does Not Match

The auto-configuration class may be processed, yet a `@Bean` method is skipped—for instance, because `@ConditionalOnMissingBean` finds an application bean. In the example, `--demo.custom=true` creates this situation.

### Bean Creation Errors Differ from Metadata Discovery Errors

If a definition was registered but the bean constructor throws an exception or lacks a required dependency, the context may fail to start. That error requires analyzing the exception chain; it does not prove the imports file failed to work.

### Package Name Errors During Import

An incorrect FQCN can lead to an error when Boot tries to read or load configuration information, depending on the processing phase; do not expect Boot to always ignore it silently. Fix the class name in the metadata, and avoid inferring only from the short first message in the stack trace.

## 8. Debugging with the Condition Report and Classpath Inspection

When suspecting “the class is registered yet there is no bean”, follow this order:

1. **Inspect the JAR and runtime classpath** to be sure the imports file is in the executed artifact.
2. **Read the imports file contents** to see if the FQCN is correct, or if a line has a typo or a recent package rename.
3. **Confirm auto-configuration is enabled** via `@SpringBootApplication` or `@EnableAutoConfiguration`.
4. **Check the application's exclusions**.
5. **Inspect the Condition Evaluation Report** to see which condition filtered out the class or bean.
6. **Inspect beans in the context** to distinguish a selected class from a created bean.
7. **If it still fails**, compare the Spring Boot version, dependency graph, and startup trace.

For the example in section 5, you can enable debug logging with:

~~~bash
java -jar target/auto-imports-demo-1.0.0.jar --debug --logging.level.root=INFO
~~~

Search for `MessageAutoConfiguration` or `MessageAutoConfiguration#defaultMessageService` in the condition report. Report contents can vary by version and conditions, so do not assume a fixed log string. “Negative matches” entries are often a normal result of configuration selection.

You can also use `ApplicationContextRunner` in auto-configuration tests to create small contexts with different beans/properties. However, if a test **specifies the auto-configuration class directly** in `AutoConfigurations.of(...)`, that test **does not by itself prove the imports file was packaged/discovered**. You need to add a packaged resource check or a smoke test that starts an application using the real dependency.

Some libraries may use `spring-boot-autoconfigure-processor` to generate `spring-autoconfigure-metadata.properties`, aiding early condition filtering to improve startup. Do not confuse the processor-generated file with the `AutoConfiguration.imports` list that must be published.

## 9. Common Metadata Registration Errors

| Symptom | Common Cause | Resolution |
| --- | --- | --- |
| `@AutoConfiguration` class exists but bean is missing | Imports file not created or missing at runtime | Check `src/main/resources`, JAR, and classpath. |
| Imports file exists but Boot does not read it | Wrong filename, wrong `META-INF/spring` location, file in `src/test/resources` | Fix path and repackage. |
| Metadata line cannot find class | Wrong FQCN, package renamed without updating file | Synchronize package, class name, and metadata contents. |
| Class is loaded but default bean is missing | Class/bean condition did not match | Check condition report, especially `@ConditionalOnMissingBean` and properties. |
| Application still runs despite missing imports file | Class accidentally picked up by component scan/`@Import` directly | Place auto-configuration in a separate package, discovered only via imports. |
| Build succeeds but running another JAR misses configuration | Module containing metadata is not on runtime classpath | Check dependency graph and published artifact. |
| Using legacy `spring.factories` example for Boot 3+ | Applying legacy auto-configuration registration mechanism | Move class list to the `AutoConfiguration.imports` file. |
| Renaming configuration class breaks ordering/excludes | External code still references old name | Consider `AutoConfiguration.replacements` when renaming in an already-published library. |

### Renaming an Already-Published Auto-Configuration

If a library has already published `OldAutoConfiguration` and applications depend on that class in excludes/ordering, renaming the package is not just editing the imports file. Spring Boot supports the resource:

~~~text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.replacements
~~~

In it, you can map the old name to the new name:

~~~properties
com.example.old.OldAutoConfiguration=com.example.newpkg.NewAutoConfiguration
~~~

During the transition, the imports file should only point to the new name. This is a mechanism for **compatibility when replacing an auto-configuration class name** in supported versions; do not use the replacements file to register new candidates. The class names in this snippet illustrate the format, not built-in Spring Boot classes.

## 10. Practical Knowledge Checks

### Scenario A: An Application Uses Two Libraries

Library A has `AConfig` in its imports file and Library B has `BConfig` in its imports file. When both JARs are on the classpath, Boot can collect candidates from **both resources**. You do not need to manually merge the two files into one in the application. However, whether Bean A / Bean B exist still depends on conditions and exclusions.

### Scenario B: Only Adding @AutoConfiguration Without Creating an Imports File

For an application outside the configuration class's package, the class is not discovered from the annotation alone; imports metadata on the runtime classpath or another intentional import mechanism is required. For an auto-configuration library, the standard path is the **imports file**.

### Scenario C: Imports File Content Is Correct Yet the Bean Is Still Skipped

Read `@ConditionalOnProperty`/`@ConditionalOnClass` at the class level and `@ConditionalOnMissingBean` on the method. If the application already has a bean of the same type, the default bean should step back. This may be the intended behavior.

### Scenario D: Placing the Imports File in the Same Directory as Java Sources

`src/main/java/META-INF/spring/...` is not Maven's standard resource location. Use `src/main/resources/META-INF/spring/...` so the build copies it properly.

### Scenario E: Wanting to Add an Auto-Configuration for Web

Add the web configuration's FQCN to the imports file, and use conditions such as classpath/web environment so that configuration applies only when appropriate. Do not create defaults unconditionally just because the library has a new entry.

### Scenario F: Wanting to Test Boot's File Discovery

Tests that only manually invoke `new MessageAutoConfiguration()` or `AutoConfigurations.of(MessageAutoConfiguration.class)` are not sufficient to prove the metadata is in the artifact. Inspect the JAR and run a test application with auto-configuration enabled, without manually scanning the configuration's package.

## 11. Pre-Release Checklist for a Library

- [ ] The auto-configuration class is a valid `@AutoConfiguration` and contains conditions appropriate for consuming applications.
- [ ] The class is placed in a separate package, outside the area scanned by component scan.
- [ ] The file is located at the exact path `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
- [ ] The file content has **one exact FQCN per line**, with no `.class` or wrong properties-style structure.
- [ ] The file is packaged in the JAR and present on the runtime classpath when an application pulls the dependency.
- [ ] Both cases tested: without a user bean and with a user bean; the default bean appears only when conditions allow.
- [ ] Verified that missing optional dependencies or non-matching properties do not cause the library to fail unnecessarily.
- [ ] Auto-configuration imports is not confused with `spring-configuration-metadata.json`, `spring-autoconfigure-metadata.properties`, or other extension registrations.
- [ ] Diagnostics are in place using the condition report, artifact inspection, and version compatibility checks.
- [ ] If renaming a published class, ordering/excludes compatibility is handled via the replacements mechanism when appropriate.

## 12. Self-Check

**1. Does AutoConfiguration.imports register beans or configuration classes?** — It registers **candidate auto-configuration class names**; beans are decided later.

**2. What is the full path in a Maven project?** — `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.

**3. What is the content of each line?** — A fully qualified Java class name, e.g., `com.example.autoconfigure.MessageAutoConfiguration`.

**4. What happens if a class has `@AutoConfiguration` without an imports file?** — The annotation by itself does not make Boot discover the class through the standard auto-configuration mechanism.

**5. Why not place auto-configuration in a component-scanned package?** — So the class is only imported by Boot via metadata and orchestrated properly for conditions/ordering.

**6. What if the file is found but `@ConditionalOnMissingBean` does not match?** — The corresponding default bean is not registered; this can be the right result because the application already provides the bean.

**7. Can there be multiple AutoConfiguration.imports files on the classpath?** — Yes; different JARs can contribute their own candidate lists.

**8. Does `spring-autoconfigure-metadata.properties` replace the imports file?** — No; that metadata serves to optimize condition checking.

**9. Why must you inspect the JAR after building?** — Because having the file in the source tree does not prove it is on the runtime classpath of the actual artifact.

**10. When renaming a published class, what can be affected?** — Exclusions/ordering based on the old name; consider replacements metadata depending on the Spring Boot version.
