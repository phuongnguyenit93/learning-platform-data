# BeanDefinitionOverrideException Due to Duplicate Name Registration Outside the Back-Off Mechanism

`BeanDefinitionOverrideException` occurs when Spring attempts to register a new `BeanDefinition` under a **name already in use in the same BeanFactory** while overriding is disabled. In Spring Boot 3.3, `spring.main.allow-bean-definition-overriding` defaults to `false`, so name collisions typically cause ApplicationContext startup to fail right during the bean definition registration phase.

In custom starters, this error often appears when an auto-configuration's default bean and an application-declared bean claim the same name, yet `@ConditionalOnMissingBean` fails to recognize the application bean. It can also stem from two `@Configuration` classes, two scanned components, or two modules declaring the same bean name.

**Distinguish the two errors:**

- `BeanDefinitionOverrideException`: two bean definitions compete for the same **name**; the error occurs during definition registration.
- `NoUniqueBeanDefinitionException`: multiple beans have the **same type but different names**; the context may start, yet a type-based injection point cannot resolve a unique bean.

`@Primary` and `@Qualifier` solve the second case. They do not resolve collisions between two definitions sharing the same name.

## 1. How Are Bean Names Generated?

Spring tracks beans by an identifier in the registry. This name can be declared explicitly or generated by convention.

| Declaration | Default or assigned name |
| --- | --- |
| `@Bean` on method `paymentGateway()` | `paymentGateway` |
| `@Bean("partnerGateway")` | `partnerGateway` |
| `@Bean(name = {"gateway", "paymentGateway"})` | `gateway` is the primary bean name; `paymentGateway` is an alias |
| `@Component` on class `PaymentGatewayClient` | `paymentGatewayClient` per component-name convention |
| `@Component("gateway")` | `gateway` |
| XML `<bean id="gateway" ...>` | `gateway` |
| Registration via `BeanDefinitionRegistry` | Name passed into the registration call |

`@Bean` method names are an easily overlooked source of collisions. Two methods in separate configuration classes can still generate the same bean name if they share a method name or `@Bean("...")` declaration.

Example:

```java
@Configuration(proxyBeanMethods = false)
class LocalGatewayConfiguration {
    @Bean
    PaymentGateway paymentGateway() {
        return new LocalPaymentGateway();
    }
}

@Configuration(proxyBeanMethods = false)
class PartnerGatewayConfiguration {
    @Bean
    PaymentGateway paymentGateway() {
        return new PartnerPaymentGateway();
    }
}
```

Both methods register a bean named `paymentGateway`. Having two objects of different classes does not make their names unique. If the application needs both implementations, give them distinct names and inject with `@Qualifier`, or inject a collection/map of beans of the same type.

A bean can also have aliases. Aliases also occupy names in the registry; do not reuse an alias as the primary name for another bean.

## 2. What Does `BeanDefinitionOverrideException` Actually Report?

`BeanDefinitionOverrideException` is a subclass of `BeanDefinitionStoreException`. It describes an invalid definition registration, typically a new definition registered with a name already present in the registry while overriding is disabled.

The exception provides helpful details:

- `getBeanName()`: the colliding name.
- `getBeanDefinition()`: the new definition being registered.
- `getExistingDefinition()`: the definition that previously claimed the name.
- `getResourceDescription()`: source description of the new definition.

The message typically looks like:

```text
The bean 'paymentGateway' could not be registered.
A bean with that name has already been defined in ...
and overriding is disabled.
```

Exact wording depends on the version and registration source. Use the bean name in the exception as your starting point, then locate **both the old and new definitions**. Looking only at class names in the stack trace is rarely enough to identify which module registered the bean first.

### 2.1. Spring Boot's Default Policy

In Spring Boot 3.3, the property:

```properties
spring.main.allow-bean-definition-overriding=false
```

defaults to `false`. When `false`, another bean definition registration under the same name is rejected.

It can be enabled:

```properties
spring.main.allow-bean-definition-overriding=true
```

When enabled, a definition registered later can replace an existing one. The outcome depends on registration order and can mask conflicts caused by component scanning, imports, or starters. This is a global application override policy, not a fix for auto-configuration conditions.

**Note on plain Spring Framework:** `DefaultListableBeanFactory` has its own default allowing bean definition overriding. Spring Boot sets the default policy for Boot applications to `false`. Therefore, do not extrapolate plain bean factory defaults to Spring Boot.

## 3. Why Might the Back-Off Mechanism Fail to Prevent the Error?

`@ConditionalOnMissingBean` is the mechanism allowing auto-configuration to register a default bean only when no matching bean exists yet. The annotation can check by type or by name.

### 3.1. Back-Off by Type

Auto-configuration example:

```java
@AutoConfiguration
public class GatewayAutoConfiguration {
    @Bean("paymentGateway")
    @ConditionalOnMissingBean(PaymentGateway.class)
    PaymentGateway defaultGateway() {
        return new DefaultPaymentGateway();
    }
}
```

Application supplies its own implementation:

```java
@Configuration(proxyBeanMethods = false)
class UserGatewayConfiguration {
    @Bean("partnerGateway")
    PaymentGateway partnerGateway() {
        return new PartnerPaymentGateway();
    }
}
```

Even though the user bean is named `partnerGateway`, type `PaymentGateway` already exists. The type condition does not match, so `defaultGateway()` does not register the default bean. Only `partnerGateway` exists.

This is usually the right contract for a starter: the application is free to choose any bean name, provided it supplies an implementation of the extension type published by the starter.

### 3.2. Back-Off by Name

Suppose the auto-configuration declares:

```java
@Bean("paymentGateway")
@ConditionalOnMissingBean(name = "paymentGateway")
PaymentGateway defaultGateway() {
    return new DefaultPaymentGateway();
}
```

If the application declares `partnerGateway` of type `PaymentGateway`, the name condition still matches because no bean named `paymentGateway` exists. The result is two beans of the same type with different names.

The context may start up, yet injecting `PaymentGateway` without a qualifier throws `NoUniqueBeanDefinitionException`. This is not `BeanDefinitionOverrideException`, because the registry does not hold two definitions with the same name.

Use name-based conditions only when **the bean name itself is the contract** required by the starter. If users should be free to pick names, prefer type-based conditions.

### 3.3. A Type Condition Cannot Detect a Name Already Claimed by Another Type

This case easily produces `BeanDefinitionOverrideException` even with `@ConditionalOnMissingBean`:

```java
@Configuration(proxyBeanMethods = false)
class UserConfiguration {
    @Bean("paymentGateway")
    String paymentGatewayAlias() {
        return "reserved-name";
    }
}
```

Meanwhile, the auto-configuration has:

```java
@Bean("paymentGateway")
@ConditionalOnMissingBean(PaymentGateway.class)
PaymentGateway defaultGateway() {
    return new DefaultPaymentGateway();
}
```

The existing bean is named `paymentGateway`, yet its declared type is `String`. The condition checks `PaymentGateway.class`, finds no matching bean, and lets the default method run. When Spring registers the new definition also named `paymentGateway`, the registry detects the name is already taken and throws the exception.

A type condition answers "does a bean of this type already exist?". It is not a lock protecting whatever bean name the `@Bean` method is about to use.

### 3.4. `@Bean` Return Types Affect Type Conditions

Spring Boot recommends declaring `@Bean` return types as specifically as possible. Conditions are evaluated based on type metadata exposed by the method signature.

Example:

```java
@Bean("partnerGateway")
Object partnerGateway() {
    return new PartnerPaymentGateway();
}
```

If auto-configuration checks `@ConditionalOnMissingBean(PaymentGateway.class)`, return type `Object` may not provide enough metadata for the condition to recognize the `PaymentGateway` bean before instantiation.

Declare the proper contract type:

```java
@Bean("partnerGateway")
PaymentGateway partnerGateway() {
    return new PartnerPaymentGateway();
}
```

If the API needs a specific implementation, declare the concrete type. If the starter depends only on the interface, declaring the interface as the return type is sufficient for interface-based conditions to work.

### 3.5. Condition Evaluation Order Also Matters

Bean conditions can evaluate only bean definitions already processed by the time the condition runs. Spring Boot recommends placing `@ConditionalOnBean` and `@ConditionalOnMissingBean` on auto-configurations because auto-configurations apply after user-defined bean definitions.

If placed inside a regular configuration scanned or imported in an unsuitable order, the condition may run before the target bean is registered. As a result, the default is added, and then another definition arrives with the same name.

`@AutoConfiguration(after = ...)` and `before = ...` describe ordering relationships between auto-configurations. They control bean definition registration order; they do not replace conditions and do not by themselves resolve two methods sharing the same name.

## 4. Distinguishing Easily Confused Situations

| Symptom | Typical outcome | Resolution |
| --- | --- | --- |
| Two definitions share a bean name, overriding disabled | `BeanDefinitionOverrideException` | Find both registration sources; fix name or condition. |
| Two beans share a type, different bean names | Context may start; type injection may throw `NoUniqueBeanDefinitionException` | Use `@Qualifier`, `@Primary`, or collection injection. |
| User bean matches default bean type and auto-config has `@ConditionalOnMissingBean(Type.class)` | Auto-config backs off | Expected default-override behavior. |
| User bean matches type, but condition checks a different bean name | Default may still be created; multiple same-type beans can occur | Align condition with the type/name contract. |
| User bean claims the same name with a different type, auto-config checks only type | Condition may still match and register duplicate name | Use a distinct name or a contract-aligned condition. |
| Same bean declared from two configuration classes | Name collision may occur | Check `@Bean` method names, `@Bean(name=...)`, and import/scan sources. |

Do not use `@Primary` to fix `BeanDefinitionOverrideException`. `@Primary` is considered only once Spring already has multiple valid candidates for a dependency; it does not permit the registry to store two definitions under the same name.

## 5. Exception-Driven Diagnostic Workflow

When the application fails to start, follow this sequence:

1. **Extract the bean name from the exception.** For example `paymentGateway`. Search for this exact name across `@Bean`, `@Component`, XML, `@Import`, and programmatic registration code.
2. **Inspect both definitions.** Identify which configuration class, component, or module produced the old definition and the new definition. Use `getResourceDescription()` and `getBeanDefinition()` if inspecting in a debugger.
3. **Check auto-generated bean names.** Two `@Bean` methods can share a method name; two components with the same simple class name can produce identical default names; aliases can also claim names.
4. **Check the condition at the registration site.** Does the condition check by type or by name? Is `@ConditionalOnMissingBean` on an auto-configuration loaded by Boot after user configurations?
5. **Check return types.** If the condition relies on type, the user's `@Bean` method must declare a return type reflecting the checked contract.
6. **Check component scanning and imports.** Auto-configurations should be listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, not included in component scanning like regular configurations. Watch for overly broad scan packages or duplicate import paths.
7. **Check profiles/properties.** Two configurations might both be active in one environment when only one was meant to be enabled. Check `@Profile`, `@ConditionalOnProperty`, and active config sources.
8. **Read the Condition Evaluation Report.** Run with `--debug` or enable the report in tests to see which conditions matched and which did not.

For instance, if the exception names `paymentGateway`, locate every declaration using that name. Do not start by renaming randomly: first determine whether the two beans are two implementations meant to coexist or two candidates competing for the same role.

## 6. Fixes by Root Cause

### 6.1. Two Implementations Genuinely Need to Coexist

Assign distinct names:

```java
@Configuration(proxyBeanMethods = false)
class GatewayConfiguration {
    @Bean("localGateway")
    PaymentGateway localGateway() {
        return new LocalPaymentGateway();
    }

    @Bean("partnerGateway")
    PaymentGateway partnerGateway() {
        return new PartnerPaymentGateway();
    }
}
```

When a specific implementation is needed, inject explicitly:

```java
@Service
class CheckoutService {
    private final PaymentGateway gateway;

    CheckoutService(@Qualifier("partnerGateway") PaymentGateway gateway) {
        this.gateway = gateway;
    }
}
```

If the service needs all implementations, inject `List<PaymentGateway>` or `Map<String, PaymentGateway>`. You can add `@Primary` if there is a default choice for injection points without qualifiers.

### 6.2. User Bean Should Replace the Starter's Default

Place the condition on the auto-configuration's default bean:

```java
@AutoConfiguration
public class GatewayAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(PaymentGateway.class)
    PaymentGateway defaultGateway() {
        return new DefaultPaymentGateway();
    }
}
```

The application supplies a bean following the contract:

```java
@Configuration(proxyBeanMethods = false)
class ApplicationGatewayConfiguration {
    @Bean
    PaymentGateway paymentGateway() {
        return new PartnerPaymentGateway();
    }
}
```

Auto-configuration is processed after user configuration and sees the `PaymentGateway` bean, so it skips registering the default. There is no need to force both beans to share a name to express overriding.

If the contract truly requires a specific bean name, use `@ConditionalOnMissingBean(name = "...")` and require users to supply that exact name. Document this convention clearly in the starter docs.

### 6.3. Two Configurations Should Not Both Be Active

If each configuration represents a mutually exclusive choice, use properties or profiles to pick exactly one:

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(
        prefix = "payment.gateway",
        name = "provider",
        havingValue = "local"
)
class LocalGatewayConfiguration {
    // Register localGateway.
}

@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(
        prefix = "payment.gateway",
        name = "provider",
        havingValue = "partner"
)
class PartnerGatewayConfiguration {
    // Register partnerGateway.
}
```

Configuration:

```properties
payment.gateway.provider=partner
```

Do not allow two configurations to match in the same profile if they register the same bean name. If a default implementation is needed, design a dedicated default branch and test property combinations.

### 6.4. Component Scan Loads the Same Configuration Through Multiple Paths

Narrow `@ComponentScan` to packages the application genuinely needs to scan. Do not component-scan packages containing starter auto-configurations. For starters, register auto-configurations via the imports file and use `@Import` for specific supporting configurations when needed.

Having the same auto-configuration in both imports and component scan is a structural bug to fix. Never rely on scan order to decide which definition wins.

### 6.5. Enable Overriding Only When It Is an Intentional Policy

You can set `spring.main.allow-bean-definition-overriding=true` to support a legacy application intentionally replacing definitions by name. However, later-registered definitions then overwrite earlier ones; configuration order becomes part of runtime behavior.

Before enabling it, confirm:

- Both definitions genuinely represent one role and replacement is intentional.
- Registration order is stable and tested.
- No other module or starter accidentally shares the name.
- Operators understand which bean is kept in each profile.

Do not use `true` as a default workaround for starters. For a library/starter with multiple consumers, distinct names and contract-based back-off yield far more predictable behavior.

## 7. Complete Example: Reproducing and Testing Errors with Spring Boot 3.3.5

The example below tests five scenarios:

1. Without a user bean, the default is created.
2. A user bean of the same type with a different name causes type-based auto-configuration to back off.
3. A name-only condition does not back off when the user bean has another name; the result is multiple beans of the same type.
4. Another bean of a different type claiming the same name evades a type condition and fails registration.
5. An auto-configuration lacking back-off plus a same-named user bean triggers `BeanDefinitionOverrideException`.

### 7.1. POM and Structure

```text
bean-name-lab/
├── pom.xml
└── src/
    └── test/
        └── java/
            └── demo/
                └── BeanNameCollisionTests.java
```

Content of `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>demo</groupId>
    <artifactId>bean-name-lab</artifactId>
    <version>1.0.0</version>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.5</version>
        <relativePath/>
    </parent>

    <properties>
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

### 7.2. Complete Test File

Create `src/test/java/demo/BeanNameCollisionTests.java`:

```java
package demo;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.NoUniqueBeanDefinitionException;
import org.springframework.beans.factory.support.BeanDefinitionOverrideException;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

class BeanNameCollisionTests {

    record Sender(String id) {
    }

    @AutoConfiguration
    static class TypeBasedAutoConfiguration {
        @Bean("sender")
        @ConditionalOnMissingBean(Sender.class)
        Sender defaultSender() {
            return new Sender("default");
        }
    }

    @AutoConfiguration
    static class NameBasedAutoConfiguration {
        @Bean("sender")
        @ConditionalOnMissingBean(name = "sender")
        Sender defaultSender() {
            return new Sender("default");
        }
    }

    @AutoConfiguration
    static class UnconditionalAutoConfiguration {
        @Bean("sender")
        Sender defaultSender() {
            return new Sender("default");
        }
    }

    @Configuration(proxyBeanMethods = false)
    static class UserSenderConfiguration {
        @Bean("partnerSender")
        Sender partnerSender() {
            return new Sender("partner");
        }
    }

    @Configuration(proxyBeanMethods = false)
    static class UserWrongTypeConfiguration {
        @Bean("sender")
        String senderName() {
            return "reserved-name";
        }
    }

    @Configuration(proxyBeanMethods = false)
    static class UserSameNameConfiguration {
        @Bean("sender")
        Sender userSender() {
            return new Sender("user");
        }
    }

    private ApplicationContextRunner runnerFor(Class<?> autoConfiguration) {
        return new ApplicationContextRunner()
                .withAllowBeanDefinitionOverriding(false)
                .withConfiguration(AutoConfigurations.of(autoConfiguration));
    }

    @Test
    void defaultSenderIsCreatedWhenNoUserSenderExists() {
        runnerFor(TypeBasedAutoConfiguration.class)
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context.getBeansOfType(Sender.class))
                            .containsOnlyKeys("sender");
                    assertThat(context.getBean(Sender.class).id())
                            .isEqualTo("default");
                });
    }

    @Test
    void userSenderOfSameTypeMakesDefaultBackOff() {
        runnerFor(TypeBasedAutoConfiguration.class)
                .withUserConfiguration(UserSenderConfiguration.class)
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context.getBeansOfType(Sender.class))
                            .containsOnlyKeys("partnerSender");
                    assertThat(context.getBean(Sender.class).id())
                            .isEqualTo("partner");
                });
    }

    @Test
    void nameConditionDoesNotBackOffForAnotherName() {
        runnerFor(NameBasedAutoConfiguration.class)
                .withUserConfiguration(UserSenderConfiguration.class)
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context.getBeansOfType(Sender.class))
                            .containsOnlyKeys("partnerSender", "sender");
                    assertThat(context.getBeansOfType(Sender.class))
                            .hasSize(2);
                    assertThatThrownBy(() -> context.getBean(Sender.class))
                            .isInstanceOf(NoUniqueBeanDefinitionException.class);
                });
    }

    @Test
    void typeConditionCannotDetectAnotherTypeUsingTheSameName() {
        runnerFor(TypeBasedAutoConfiguration.class)
                .withUserConfiguration(UserWrongTypeConfiguration.class)
                .run(context -> {
                    assertThat(context).hasFailed();
                    assertThat(context.getStartupFailure())
                            .hasRootCauseInstanceOf(
                                    BeanDefinitionOverrideException.class
                            );
                });
    }

    @Test
    void missingBackoffOnDefaultBeanCausesSameNameCollision() {
        runnerFor(UnconditionalAutoConfiguration.class)
                .withUserConfiguration(UserSameNameConfiguration.class)
                .run(context -> {
                    assertThat(context).hasFailed();
                    assertThat(context.getStartupFailure())
                            .hasRootCauseInstanceOf(
                                    BeanDefinitionOverrideException.class
                            );
                });
    }
}
```

Run in the `bean-name-lab` directory with JDK 17+ and Maven:

```bash
mvn test
```

**Expected result:** five tests pass. The last two tests verify the context fails with root cause `BeanDefinitionOverrideException`; the third test confirms two differently named beans of the same type lead to `NoUniqueBeanDefinitionException` on type lookup. Maven Surefire reports `Tests run: 5, Failures: 0, Errors: 0, Skipped: 0` if all tests pass.

## 8. Common Diagnostic Mistakes

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Changed implementation class, yet duplicate-name error persists | Bean name comes from method name or `@Bean(name=...)`, not class name | Check definition names and aliases. |
| Added `@Primary`, yet context still fails | Registry forbids registering two definitions with the same name | Fix bean names or conditions; `@Primary` does not apply at registration time. |
| `@ConditionalOnMissingBean` exists, yet name collision still happens | Condition checks wrong type/name or cannot see user bean metadata | Check annotation attributes, return types, and condition evaluation timing. |
| Context starts, yet type injection fails | Multiple beans share the type with different names | Use qualifiers, primary, or collection injection. |
| Fails only in one profile | Two configurations activate together in that profile | Check `@Profile`, `@ConditionalOnProperty`, and environment config. |
| Fails only after adding a starter | Starter registers colliding bean name or auto-configuration was unexpectedly component-scanned | Locate bean name in dependencies, check imports and scan packages. |
| Enabling overriding lets app start, yet wrong bean is used | Later definition overwrote earlier definition | Fix ordering and eliminate the collision instead of relying on implicit replacement. |
| Condition misses user-declared bean | `@Bean` method declares overly broad return type such as `Object` | Return a specific contract type so the condition can recognize it. |

## 9. Pre-Fix Checklist

- [ ] Read the exact bean name in `BeanDefinitionOverrideException`.
- [ ] Identified both the old definition and new definition, plus the resources/configurations creating them.
- [ ] Checked default `@Bean` names, `@Component` names, explicit names, and aliases.
- [ ] Determined whether the two beans share a name or only a type.
- [ ] Inspected `@ConditionalOnMissingBean`: checking by type or by name?
- [ ] Confirmed `@Bean` method return types expose the type the condition looks for.
- [ ] Confirmed the condition resides in auto-configuration and is processed after user configurations.
- [ ] Checked component scan, `@Import`, `AutoConfiguration.imports`, profiles, and properties.
- [ ] If two implementations coexist, assigned distinct bean names and appropriate qualifiers/primary.
- [ ] If user bean replaces default, tested via `ApplicationContextRunner` with overriding disabled.
- [ ] Enabled `spring.main.allow-bean-definition-overriding=true` only when same-name replacement is an intentionally designed and tested policy.

**Key takeaway:** `BeanDefinitionOverrideException` is a collision on **bean name in the registry**. `@ConditionalOnMissingBean` lets auto-configuration back off only when its type or name criteria actually match. Find both registration sources, inspect the type/name evaluated by the condition, and make the bean contract explicit. If two beans have different names and the same type, solve with qualifier/primary; if two definitions share a name, resolve the registration collision before reaching injection.
