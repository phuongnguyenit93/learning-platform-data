# Role of AutoConfigurationImportFilter and Filtering Metadata

## 1. Where Filters Fit in the Auto-Configuration Discovery Process

In Spring Boot, simply listing a class as an auto-configuration candidate does not mean it is guaranteed to be imported or create beans. Before Spring parses the candidate's full bytecode and `@Bean` methods, Boot can **eliminate candidates early that are definitely unsuitable**.

Two key components in this step:

- **`AutoConfigurationImportFilter`**: the contract allowing a filter to decide which auto-configuration candidates continue to be considered.
- **`AutoConfigurationMetadata`**: the API reading pre-compiled metadata generated from annotations on auto-configuration classes; thanks to this, filters can decide quickly without loading full classes.

In Spring Boot 3.3.x, the process can be visualized as:

```text
@SpringBootApplication
  -> @EnableAutoConfiguration
      -> AutoConfigurationImportSelector (DeferredImportSelector)
          -> find candidate names from *.imports
          -> deduplicate and apply exclusions
          -> load AutoConfigurationImportFilter instances
          -> read AutoConfigurationMetadata if present
          -> invoke filter.match(candidateNames, metadata)
          -> drop candidates evaluated as false
          -> sort and import remaining candidates
              -> Spring parses @Configuration and @Conditional
              -> register matching BeanDefinitions
              -> BeanFactory instantiates beans when needed
```

This diagram abbreviates some group handling, ordering, and `DeferredImportSelector` evaluation rounds. Distinguish **filtering the class name list before import** from **evaluating `@Conditional` when Spring processes configurations**. They complement each other.

A filter keeping a candidate only means the candidate **can proceed** into the configuration processing phase; it does not guarantee every bean inside it will be registered. Conversely, when a filter eliminates a candidate outright, that auto-configuration class is not imported through the evaluated candidate list.

## 2. Distinguishing Three Common Metadata Files

This is a very common point of confusion when learning auto-configuration.

| File | Role | Who Reads or Generates It |
| --- | --- | --- |
| `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` | **List of candidate** auto-configuration class names, one class name per line | Provided by the library author; read by Boot to discover candidates |
| `META-INF/spring-autoconfigure-metadata.properties` | **Early-filtering metadata** based on annotations/conditions and configuration info | Generated at compile time by `spring-boot-autoconfigure-processor`; read by Boot for optimization |
| `META-INF/spring-configuration-metadata.json` | Describes **configuration keys**, types, descriptions, defaults/hints for IDEs/tooling | Usually generated by `spring-boot-configuration-processor`; not an auto-configuration list and not primary input for import filters |

Example `AutoConfiguration.imports` file in a library:

```text
com.acme.boot.autoconfigure.AcmeClientAutoConfiguration
com.acme.boot.autoconfigure.AcmeHealthAutoConfiguration
```

These are only **candidate names**. Boot still evaluates exclusions, filters, and conditions on those classes.

Illustrative example of generated metadata shape:

```properties
com.acme.boot.autoconfigure.AcmeClientAutoConfiguration.ConditionalOnClass=com.acme.client.Client
```

The key/value above only illustrates a simple class condition, not an output guaranteed verbatim from a specific processor version. Inspect the file generated in your library's own build to see actual data.

Do not hand-write this metadata file as a separate source of truth while ignoring annotations. In the auto-configuration module, use the matching version of the annotation processor to keep metadata consistent with source. The metadata file may be absent or not cover every condition; the application must still rely on Spring's official condition evaluation process.

## 3. What Is the AutoConfigurationImportFilter API?

In Spring Boot 3.3.13, the interface belongs to package:

```java
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter
```

Core contract:

```java
boolean[] match(
    String[] autoConfigurationClasses,
    AutoConfigurationMetadata autoConfigurationMetadata
);
```

**This is an API signature for explanation**, not a standalone compilable Java file.

- `autoConfigurationClasses`: array of **fully qualified class names** of candidates currently being evaluated, not an array of already-loaded `Class<?>` objects. The array may contain `null` elements from prior filtering steps.
- `autoConfigurationMetadata`: provides pre-generated metadata from the annotation processor, helping avoid unnecessary parsing.
- The `boolean[]` result **must have the exact same length** as the candidate array. A `true` element allows the candidate at that index to proceed; `false` eliminates that candidate from this import pass.
- Filters **must not modify** elements of the `autoConfigurationClasses` array.
- Multiple filters can exist; a candidate eliminated by one filter is not restored simply because another filter returns `true`. Filters must be written to tolerate `null` elements.
- This is an infrastructure extension API; most ordinary applications do not need to implement it themselves.

Simple logic example:

```text
candidates = [A, B, C]
filter F1 = [true, false, true]
filter F2 = [true, true, false]
remaining result = [A]
```

`false` is an elimination decision. Do not confuse `true` with “the bean is guaranteed to exist”: candidate A can still be evaluated further by `@ConditionalOnProperty` or `@ConditionalOnMissingBean` when Spring parses it.

### Filter Registration Mechanism

In Spring Boot 3.3.x, `AutoConfigurationImportFilter` is registered using `META-INF/spring.factories`, for example:

```properties
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter=\
com.acme.boot.filter.AcmeImportFilter
```

**Note the difference in files:** auto-configuration classes are listed in `AutoConfiguration.imports`, whereas **filter** implementations are declared via the `AutoConfigurationImportFilter` key in `spring.factories`. Moving the filter line into `.imports` does not register a filter. You do not need to mark the filter with `@Component` to register it this way.

Boot can invoke methods of the following `Aware` interfaces before calling `match(...)` if the filter implements them:

- `EnvironmentAware`: receives `Environment` to read properties.
- `BeanFactoryAware`: receives `BeanFactory`.
- `BeanClassLoaderAware`: receives the classloader used by the container.
- `ResourceLoaderAware`: receives the resource loader.

Filters should be fast, side-effect-free, and avoid creating business beans during filtering. They run while the container is still assembling configuration; attempting to use any bean as if the application were already ready can skew the lifecycle or cause premature initialization failures.

## 4. How Does AutoConfigurationMetadata Reduce Work?

`AutoConfigurationMetadata` is an interface for reading metadata collected at build time instead of starting by loading and parsing every candidate at runtime.

Several important methods:

```java
boolean wasProcessed(String className);
String get(String className, String key);
Integer getInteger(String className, String key);
Set<String> getSet(String className, String key);
```

These are abbreviated signatures for understanding the API; overloads with `defaultValue` also exist. When using `getSet`, import `java.util.Set`. Calls to `get...` can return `null` if no matching metadata is found; missing metadata should not be treated as proof that a condition definitely fails.

Suppose an auto-configuration class carries:

```java
@AutoConfiguration
@ConditionalOnClass(name = "com.acme.client.Client")
public class AcmeClientAutoConfiguration {
}
```

The annotation processor can collect this class condition into `spring-autoconfigure-metadata.properties`. An optimizing filter can look up the known condition to detect the absence of `com.acme.client.Client` on the classpath **before having to read the candidate's entire configuration**.

Benefits:

1. **Reduces unnecessary I/O/metadata parsing** when many auto-configurations are on the classpath.
2. **Reduces the chance of reading bytecode** for configurations that are definitely inapplicable.
3. Improves startup when using many starters/libraries with optional features.
4. Keeps decisions grounded in build-time information rather than instantiating beans to “try and see” whether they run.

However, this optimization has limits:

- Metadata only reflects conditions/information the processor supports and can generate at compile time; it cannot express arbitrary custom logic.
- Conditions depending on existing beans, dynamic properties, profiles, or context usually still need evaluation in their proper phase.
- Metadata is not a bean definition list and not a cache of instances.
- **No metadata does not mean the auto-configuration must be eliminated**; Spring must be allowed to check actual conditions if information is insufficient.
- Fast filtering only optimizes candidate selection; it does not replace bean lifecycle, dependency injection, or the framework's `@Conditional` logic.

## 5. An Example of OnClassCondition and Checking Levels

Among built-in filters, classpath-based conditions are well suited for early decisions: required/disallowed class names are information the processor can easily store ahead of time.

Illustrative configuration class example:

```java
@AutoConfiguration
@ConditionalOnClass(name = "com.vendor.sdk.VendorClient")
class VendorClientAutoConfiguration {
    // @Beans related to VendorClient
}
```

When `com.vendor.sdk.VendorClient` is absent from the runtime classpath, Boot has grounds to eliminate or skip this configuration under the class condition. Generated metadata makes filtering faster when available; condition handling must still behave correctly even when metadata was not generated.

Not every `@ConditionalOnClass` is decided in one “universal filter” regardless of annotation placement. A condition placed directly on the auto-configuration class can be processed early; a condition placed on a `@Bean` method inside a nested configuration may require deeper configuration analysis. Do not interpret `AutoConfigurationImportFilter` as replacing the entire `Condition` system.

Three decision layers are helpful to remember:

```text
1. Candidate discovery: is the class name in .imports?
2. Import filtering: is there evidence to eliminate the candidate early?
3. Condition evaluation / bean registration:
   do the configuration class and @Bean methods match conditions?
```

Layer 1 does not prove layer 3 will create a bean. Layer 2 operates to avoid unnecessary work before layer 3.

## 6. Runnable Example: Writing a Custom AutoConfigurationImportFilter

This example uses **Java 17**, **Spring Boot 3.3.13**, and **Maven**. The goal is to compare two runs with and without an auto-configuration imported by using a filter reading the `sample.greeting.enabled` property.

For clarity, the example includes:

- Application `demo.app.FilterDemoApplication` using `@SpringBootApplication`.
- API `demo.api.GreetingApi`, a plain class, not a component.
- Auto-configuration `demo.autoconfigure.GreetingAutoConfiguration`, placed **outside the component scan area** of the main class.
- Filter `demo.filter.GreetingImportFilter`, registered in `spring.factories`.
- `.imports` file listing the auto-configuration class.
- Annotation processor allowing the build to generate filtering metadata.

The application still has an `ApplicationRunner`, but it takes `ObjectProvider<GreetingApi>` so startup does not fail when the filter eliminates the default bean. The example is organized in **a single Maven module for ease of running**; real libraries/starters typically package auto-configuration separately.

### 6.1. Directory Tree

```text
filter-demo/
├── pom.xml
└── src/main/
    ├── java/demo/
    │   ├── app/FilterDemoApplication.java
    │   ├── api/GreetingApi.java
    │   ├── autoconfigure/GreetingAutoConfiguration.java
    │   └── filter/GreetingImportFilter.java
    └── resources/META-INF/
        ├── spring.factories
        └── spring/
            └── org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

Place `FilterDemoApplication` in `demo.app`; packages `demo.api`, `demo.autoconfigure`, and `demo.filter` are **sibling packages**, so default component scanning does not auto-register `GreetingAutoConfiguration`. That class enters solely via `.imports`.

### 6.3. API Class

**`src/main/java/demo/api/GreetingApi.java`:**

```java
package demo.api;

public record GreetingApi(String message) {
}
```

This Java record has no stereotype such as `@Component`. Without registration via auto-configuration or application configuration, Spring does not automatically have a `GreetingApi` bean.

### 6.4. Auto-Configuration Class

**`src/main/java/demo/autoconfigure/GreetingAutoConfiguration.java`:**

```java
package demo.autoconfigure;

import demo.api.GreetingApi;
import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.context.annotation.Bean;

@AutoConfiguration
@ConditionalOnClass(GreetingApi.class)
public class GreetingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(GreetingApi.class)
    GreetingApi greetingApi() {
        return new GreetingApi("hello from auto-configuration");
    }
}
```

`@ConditionalOnClass(GreetingApi.class)` illustrates a class condition that the annotation processor can collect for early optimization. In the example, `GreetingApi` is always present because it is a class in the same project; this condition matches. `@ConditionalOnMissingBean` lets the default bean yield if the application explicitly creates a bean of the same type.

Do not confuse the two conditions: a missing class is a classpath issue; whether a bean already exists is the state of the registry at configuration processing time.

### 6.5. Candidate Listing File

**`src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`:**

```text
demo.autoconfigure.GreetingAutoConfiguration
```

If this file is missing or has the wrong class name, Boot will not discover this auto-configuration candidate via the standard mechanism in Spring Boot 3.3.x. This file does **not** register the filter.

### 6.6. Filter Deciding Whether to Import the Candidate

**`src/main/java/demo/filter/GreetingImportFilter.java`:**

```java
package demo.filter;

import org.springframework.boot.autoconfigure.AutoConfigurationImportFilter;
import org.springframework.boot.autoconfigure.AutoConfigurationMetadata;
import org.springframework.context.EnvironmentAware;
import org.springframework.core.env.Environment;

public final class GreetingImportFilter
        implements AutoConfigurationImportFilter, EnvironmentAware {

    private static final String TARGET =
        "demo.autoconfigure.GreetingAutoConfiguration";

    private Environment environment;

    @Override
    public void setEnvironment(Environment environment) {
        this.environment = environment;
    }

    @Override
    public boolean[] match(
            String[] autoConfigurationClasses,
            AutoConfigurationMetadata autoConfigurationMetadata) {

        boolean enabled = environment.getProperty(
            "sample.greeting.enabled", Boolean.class, true);

        boolean[] result = new boolean[autoConfigurationClasses.length];
        for (int i = 0; i < autoConfigurationClasses.length; i++) {
            String candidate = autoConfigurationClasses[i];

            // null may appear from an earlier filter.
            // Pass through other candidates and decide only TARGET.
            result[i] = !TARGET.equals(candidate) || enabled;
        }
        return result;
    }
}
```

Analysis:

- `EnvironmentAware` gives the filter the `Environment` before `match(...)` is called.
- The `sample.greeting.enabled` property is **defined by this example itself**, not a built-in Spring Boot property.
- If the property is absent, it defaults to `true`; the filter keeps `GreetingAutoConfiguration`.
- If the property is `false`, the corresponding element returns `false`, and Boot eliminates the candidate from the import list.
- The result array has the exact length of the input array.
- `TARGET.equals(candidate)` is safe even when `candidate` is `null`; the filter does not mutate the input array and creates no beans.
- The `autoConfigurationMetadata` parameter is available for the filter to look up generated metadata; the example intentionally does not use it because its decision is property-based. A later section illustrates the metadata reading API and why fallback is needed.

### 6.7. Registering the Filter in spring.factories

**`src/main/resources/META-INF/spring.factories`:**

```properties
org.springframework.boot.autoconfigure.AutoConfigurationImportFilter=\
demo.filter.GreetingImportFilter
```

This point is crucial: the **filter** is loaded by Boot via `spring.factories`, whereas **auto-configuration candidates** come from `.imports`. Using the wrong file causes the experiment not to behave as intended.

This is a valid properties file: a trailing `\` continues the value onto the next line. You can also write the entire key/value pair on a single line.

### 6.8. Application Class and Observed Output

**`src/main/java/demo/app/FilterDemoApplication.java`:**

```java
package demo.app;

import demo.api.GreetingApi;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class FilterDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(FilterDemoApplication.class, args);
    }

    @Bean
    ApplicationRunner report(ObjectProvider<GreetingApi> provider) {
        return args -> {
            GreetingApi greeting = provider.getIfAvailable();
            System.out.println("GREETING_PRESENT: " + (greeting != null));
            if (greeting != null) {
                System.out.println("GREETING: " + greeting.message());
            }
        };
    }
}
```

With `ObjectProvider`, the runner can check bean presence without failing when the filter eliminates the auto-configuration. If we required `GreetingApi` in a constructor, the disabled run would fail startup due to a missing dependency, preventing us from observing the message designed here.

### 6.9. Building and Running Two Scenarios

Requirements: Java 17+, Maven, and access to Maven dependencies. Inside `filter-demo`:

```bash
mvn -q -DskipTests package
java -jar target/filter-demo-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none
```

Ignoring logs and banner, the lines printed by the application:

```text
GREETING_PRESENT: true
GREETING: hello from auto-configuration
```

Reason: by default `sample.greeting.enabled=true`; the filter retains the candidate, `@ConditionalOnClass` matches, no application-declared `GreetingApi` bean exists, so `@Bean greetingApi()` is registered and retrieved via `ObjectProvider`.

Second run:

```bash
java -jar target/filter-demo-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --sample.greeting.enabled=false
```

Line printed by the application:

```text
GREETING_PRESENT: false
```

Reason: the filter returns `false` for candidate `demo.autoconfigure.GreetingAutoConfiguration`, so that configuration is not imported to register the `greetingApi` bean. `ObjectProvider#getIfAvailable()` returns `null`, and the runner still executes.

**Significance of the experiment:** the filter decides the **candidate list to import**. Conditions `@ConditionalOnClass` and `@ConditionalOnMissingBean` are separate checks. In ordinary applications, if you only want to toggle a bean by property, `@ConditionalOnProperty` is usually easier to maintain; writing an `AutoConfigurationImportFilter` is a library/infrastructure technique for when early filtering is genuinely needed.

## 7. Inspecting Metadata Generated by the Annotation Processor

After compiling, in a Maven project, metadata is placed in the build's output resources and included in the JAR if generated successfully:

```text
target/classes/META-INF/spring-autoconfigure-metadata.properties
```

You can inspect it with:

```bash
jar tf target/filter-demo-0.0.1-SNAPSHOT.jar
```

Look for the metadata path in the `jar tf` output. In a Spring Boot executable JAR, repackaged applications place application resources under `BOOT-INF/classes/`; that is their location inside the archive and does not change the resource path Boot reads.

On systems with file inspection tools, you can view the class output contents:

```bash
cat target/classes/META-INF/spring-autoconfigure-metadata.properties
```

The `cat` command works in Unix/macOS/Git Bash shells; on Windows PowerShell you can use `Get-Content` instead.

In the example, the processor can write metadata for `GreetingAutoConfiguration`'s `@ConditionalOnClass` condition. Do not expect to see key/value contents identical to the illustrative snippet in section 2; formatting and handled conditions depend on the processor version.

A filter wanting to read metadata can use the following APIs (illustrative snippet, **not a standalone Java file**):

```java
String configClass = "demo.autoconfigure.GreetingAutoConfiguration";
boolean processed = autoConfigurationMetadata.wasProcessed(configClass);
Set<String> requiredClasses =
    autoConfigurationMetadata.getSet(configClass, "ConditionalOnClass");

// processed may be false and requiredClasses may be null.
// Do not infer "no metadata" = "condition does not match".
```

This is an API reading example, not a request to modify the running filter in section 6. Optimized `ConditionalOnClass` handling is built into Boot; do not implement a second classpath check yourself just to demonstrate it. When another condition is needed, define a clear contract and test both with/without metadata and with an appropriate classloader.

## 8. What When Metadata Is Absent or Stale?

An auto-configuration can still run even if the library does not generate `spring-autoconfigure-metadata.properties`, as long as the candidate list and Spring conditions are validly registered. Metadata is an **acceleration tool**.

Scenarios:

| Scenario | Safe Behavior |
| --- | --- |
| Full metadata present for a supported condition | Can use it to eliminate definitely unsuitable candidates early |
| No metadata for a class | Let the official condition processor evaluate it; do not conclude `false` yourself |
| Metadata contains a key with no value | Check for `null`/defaults before using |
| Metadata built from mismatched source/version | Rebuild with the right processor; do not rely on stale manual metadata |
| Multiple JARs provide metadata | Let Boot's resource loading handle it; do not assume one file across the entire app |
| Condition depends on environment or runtime beans | Check at the phase where that information is reliable |

“Early elimination” must preserve correct behavior. If a filter mistakenly eliminates a candidate, later conditions will **have no chance to restore that candidate**. Therefore, a custom filter should not guess from ambiguous information.

In practice, if you only need to toggle a feature via a property:

```java
@AutoConfiguration
@ConditionalOnProperty(
    prefix = "acme.feature",
    name = "enabled",
    havingValue = "true"
)
class AcmeFeatureAutoConfiguration {
}
```

This snippet illustrates the annotation and requires appropriate imports. Boot already has condition mechanisms; a custom filter is usually unnecessary just to re-read the same property.

## 9. Distinguishing Filters from Other Mechanisms

### 9.1. Filter vs. @ConditionalOnClass

`@ConditionalOnClass` expresses the technical/business condition of a configuration: “apply only when this class exists”. An early filter can exploit this condition's metadata to reduce work, yet **the condition remains the source of truth**. If metadata is absent, class checks during configuration processing must still behave correctly.

### 9.2. Filter vs. @ConditionalOnMissingBean

`@ConditionalOnMissingBean` relies on bean definitions already processed at evaluation time. It is commonly used so defaults yield to application-provided beans. An import filter operates earlier and must not assume the bean registry is in a complete state.

### 9.3. Filter vs. Excludes

You can exclude a specific auto-configuration via:

```java
@SpringBootApplication(
    excludeName = "demo.autoconfigure.GreetingAutoConfiguration"
)
```

Or:

```properties
spring.autoconfigure.exclude=demo.autoconfigure.GreetingAutoConfiguration
```

This tells Boot to drop an auto-configuration completely from startup; it is **different** from writing a custom filter. These snippets are illustrative—do not use them simultaneously with the runnable example in section 6 if you want to observe the filter.

Use exclude when the application explicitly knows a configuration class is unwanted. Use conditions when a configuration depends on classes/properties/beans. Use a custom filter when developing infrastructure that needs to select candidates before the configuration parsing/registration phase.

### 9.4. Filter vs. @Primary and Bean Overriding

- `@Primary` only helps break autowiring ties among multiple beans of the same type.
- Bean overriding allows one bean definition to replace a same-named definition if permitted.
- `@ConditionalOnMissingBean` can prevent a default definition from being registered.
- `AutoConfigurationImportFilter` can eliminate an entire **auto-configuration candidate** before Spring processes the bean definitions inside.

These are four mechanisms at four different decision layers; they cannot be substituted arbitrarily for one another.

## 10. Diagnosing Filters and Conditions at Startup

You can run:

```bash
java -jar target/filter-demo-0.0.1-SNAPSHOT.jar \
  --spring.main.web-application-type=none \
  --sample.greeting.enabled=false \
  --debug
```

`--debug` makes Boot output the **Conditions Evaluation Report** to observe positive/negative matches and exclusions. However, a candidate eliminated early by a filter may not appear as a negative match equivalent to a `@Conditional` evaluated after import. The report is not a complete log of **every** decision in every filter.

To troubleshoot a custom filter:

1. Confirm the filter class is in the JAR.
2. Confirm `META-INF/spring.factories` has the `org.springframework.boot.autoconfigure.AutoConfigurationImportFilter` key and the exact filter class name.
3. Confirm the auto-configuration is in `.imports` and not accidentally picked up by component scan.
4. Confirm `Environment` receives the expected property value.
5. In a test run, observe the `match(...)` result array for the target candidate (selective logging can be used; do not log every candidate in production).
6. Cross-check actual beans via `ApplicationContext`, `ObjectProvider`, or a test context after startup.

Avoid `System.out.println` inside production filters: it can run multiple times, clutter startup logs, and increase I/O. When observation is needed, use a TRACE/DEBUG logger and avoid printing sensitive configuration values.

### Symptoms That Easily Mislead

| Symptom | Possible Cause | How to Check |
| --- | --- | --- |
| Filter does not run | Wrong key/file in `spring.factories`, class missing from JAR | Check resources after build |
| Auto-configuration still applies despite filter | Auto-configuration scanned/imported another way, wrong TARGET name | Check packages and `.imports` |
| Bean missing even though filter returned `true` | A later condition did not match or bean replaced by another configuration | Inspect Conditions Evaluation Report |
| Build lacks `spring-autoconfigure-metadata.properties` | `spring-boot-autoconfigure-processor` not enabled or processor did not run | Check Maven plugin/Gradle annotationProcessor |
| Too many candidates eliminated unexpectedly | Wrong boolean array index/length, `null` handling, or overly broad logic | Unit test `match(...)` on multiple candidates |
| Behavior changes abnormally after adding metadata | Stale metadata or custom filter depending on unreliable data | Clean build and compare runs with/without metadata |

When investigating performance, measure startup time of the real application instead of assuming a custom filter is always faster. Spring Boot already has optimized filters and condition mechanisms for common cases.

## 11. Safe Filter Design Guidelines for Libraries

If writing a library integrating with Spring Boot:

1. **Define auto-configurations with official conditions.** Use `@AutoConfiguration`, `@ConditionalOnClass`, `@ConditionalOnMissingBean`, and appropriate properties. Do not turn a custom filter into the sole source of rules while omitting corresponding conditions.
2. **Declare auto-configurations in `.imports`.** Class names must be exact and outside the application's component scan package.
3. **Add the annotation processor for metadata.** Ensure the build produces the resource; do not hand-edit the generated file or confuse it with IDE JSON metadata.
4. **Write a filter only when the benefit is clear.** For instance, many candidates with static information that can definitely be eliminated before parsing. For simple property toggling, `@ConditionalOnProperty` is usually enough.
5. **Handle all elements safely.** Keep the boolean array the same size, never mutate input, tolerate `null`, avoid relying on incidental order, and never instantiate beans early.
6. **Have a strategy when metadata is missing.** If you cannot be certain a candidate is unsuitable, retain it so `Condition` instances can check it later.
7. **Test both directions.** With full/missing classpath, enabled/disabled properties, user-defined beans, exclusions, and multiple filters working together.
8. **Observe in practice.** You can use `ApplicationContextRunner` in the auto-configuration module to verify which configurations are/aren't registered; use controlled logging when inspecting the import step in detail.

A filter has wide impact because it runs ahead of many steps Spring would normally handle. A mistaken `false` decision not only distorts startup behavior, it silently drops genuinely needed functionality. Thus, early-elimination rules must be **simple, testable, and minimally dependent on runtime state**.

## 12. Self-Check Questions

**Question 1.** What is the role of the `.imports` file and why is it insufficient to say a bean exists?

**Answer:** It only lists auto-configuration candidates. Exclusions, import filters, and conditions inside configurations/`@Bean` methods can still prevent bean registration.

**Question 2.** What does `AutoConfigurationImportFilter.match(...)` receive and what must it return?

**Answer:** It receives an array of candidate class names and `AutoConfigurationMetadata`, and returns a `boolean[]` of the same length; `false` eliminates the corresponding candidate. The input array may contain `null` and must not be modified.

**Question 3.** Is a filter registered in `.imports` or `spring.factories`?

**Answer:** In Spring Boot 3.3.x, `AutoConfigurationImportFilter` implementations are registered under the interface key in `META-INF/spring.factories`. Auto-configuration classes are listed separately in `AutoConfiguration.imports`.

**Question 4.** How does `spring-autoconfigure-metadata.properties` differ from `spring-configuration-metadata.json`?

**Answer:** The properties file supports early filtering of auto-configurations; the JSON file describes configurations/properties so IDEs and tooling can assist users. They are generated for different purposes.

**Question 5.** Does failing to find metadata for a candidate mean that candidate must be filtered out?

**Answer:** No. Missing metadata is missing optimization data; Spring's full condition evaluation path must be preserved.

**Question 6.** Why does the `--sample.greeting.enabled=false` run have no `GreetingApi` in the example?

**Answer:** The filter eliminates `GreetingAutoConfiguration` before import; no other configuration registers that bean in the example project.

**Question 7.** If the filter returns `true` yet the bean is still missing, what should be checked?

**Answer:** Conditions on the configuration and `@Bean` methods, dependencies, context type, properties, exclusions, and initialization errors. Returning `true` from an import filter does not force a bean to be created.

**Question 8.** Should filters be used to resolve every runtime bean-based condition?

**Answer:** No. The registry may be incomplete at filter time; conditions like `@ConditionalOnMissingBean` belong in the configuration processing phase.
