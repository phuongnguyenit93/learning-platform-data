# ConditionEvaluationReportLoggingListener in Configuration Testing

## 1. Goal and Problem to Solve

When testing Spring Boot Auto Configuration, a bean may appear or disappear depending on many conditions: whether a class is on the classpath, what value a property has, whether a user bean is already declared, whether the application runs in a web context, or whether another auto-configuration was applied.

A test that only asserts:

```java
assertThat(context).doesNotHaveBean("paymentClient");
```

tells you **the final outcome** but cannot answer why the bean did not appear. Perhaps `@ConditionalOnClass` did not match, `@ConditionalOnProperty` had the wrong value, `@ConditionalOnMissingBean` backed off, or the configuration itself was never included in the test context.

Spring Boot stores condition evaluation details in `ConditionEvaluationReport`. The `ConditionEvaluationReportLoggingListener` class writes that report to logs when running configuration tests. Combined with `ApplicationContextRunner`, you can both read matched/unmatched reasons and write assertions to prevent regressions.

This lesson focuses on Spring Boot **3.3.x** and JDK 17+:

- Understand the relationship among `ApplicationContextRunner`, `ConditionEvaluationReport`, and `ConditionEvaluationReportLoggingListener`.
- Register the listener properly via `ApplicationContextInitializer`.
- Choose the `INFO` or `DEBUG` log level to avoid the report being hidden.
- Do not use logs as a substitute for assertions; inspect the report via API when needed.
- Write tests for matching and non-matching conditions with a standalone runnable Java/Maven example.

## 2. Three Components and Their Responsibilities

### 2.1. `ApplicationContextRunner`: Creating an Isolated Test Context

`ApplicationContextRunner` is in package:

```java
org.springframework.boot.test.context.runner.ApplicationContextRunner
```

It is a runner for a **standard, non-web ApplicationContext**. Each call to `run(...)` creates a context configured according to the declared scenario, refreshes the context, passes it to the callback for verification, and closes the context after the callback completes.

A basic runner:

```java
new ApplicationContextRunner()
    .withConfiguration(
        AutoConfigurations.of(MyAutoConfiguration.class)
    )
    .withPropertyValues("demo.feature.enabled=true")
    .run(context -> {
        // Inspect beans and context state.
    });
```

Key parts:

- `withConfiguration(AutoConfigurations.of(...))`: specifies which auto-configurations to include in the test scenario.
- `withUserConfiguration(...)`: adds application/user-provided configuration, e.g., a custom `@Bean` to test back-off behavior.
- `withPropertyValues(...)`: modifies the `Environment` for the test without editing a real `application.properties` file.
- `withClassLoader(...)`: simulates a class or package missing from the classpath, commonly paired with `FilteredClassLoader`.
- `withInitializer(...)`: adds an `ApplicationContextInitializer`, where the listener is attached to the context.
- `run(...)`: executes the scenario and allows assertions on the context.

Each test should describe one concrete combination of classpath, properties, and user beans. This keeps tests deterministic and independent of the developer machine's configuration.

### 2.2. `ConditionEvaluationReport`: Data on Condition Evaluation Outcomes

`ConditionEvaluationReport` is in package:

```java
org.springframework.boot.autoconfigure.condition.ConditionEvaluationReport
```

This is the object that records condition evaluation information. Useful data includes:

- `getConditionAndOutcomesBySource()`: returns a `Map` of condition outcomes grouped by source, usually the configuration class name or bean method name.
- `getExclusions()`: list of auto-configuration names excluded from condition evaluation.
- `getUnconditionalClasses()`: classes recorded as having no conditions.
- `getParent()`: the parent bean factory's report, if present.

Each source has a `ConditionEvaluationReport.ConditionAndOutcomes`, an iterable collection. Each `ConditionAndOutcome` element provides:

- `getCondition()`: the condition that was evaluated.
- `getOutcome()`: the `ConditionOutcome` result.
- `ConditionOutcome.isMatch()`: whether the condition matched.
- `ConditionOutcome.getMessage()`: the reason/explanation supplied by the condition; content can vary by condition and version.

Example of what the report means:

```text
FeatureAutoConfiguration
  OnPropertyCondition
    MATCH
    @ConditionalOnProperty (demo.feature.enabled=true) matched

AnotherAutoConfiguration
  OnClassCondition
    NO MATCH
    @ConditionalOnClass did not find required class ...
```

This is an **illustrative reading sample**, not fixed stdout across all versions or applications. Actual messages are generated by each condition and depend on the properties, classpath, beans, and configuration under test.

### 2.3. `ConditionEvaluationReportLoggingListener`: Writing the Report to Logs

This class resides in package:

```java
org.springframework.boot.autoconfigure.logging.ConditionEvaluationReportLoggingListener
```

In Spring Boot 3.3.13, it implements:

```java
ApplicationContextInitializer<ConfigurableApplicationContext>
```

The listener's role is to **write `ConditionEvaluationReport` to the logging system**. It does not select auto-configurations itself, does not make a condition become true/false, and does not alter bean definitions. It only helps observe the outcomes Spring Boot has recorded.

There are two ways to create the listener:

```java
// Default: log the report at DEBUG.
new ConditionEvaluationReportLoggingListener();

// Explicitly choose INFO or DEBUG.
ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO);
ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.DEBUG);
```

In Boot 3.3:

- The no-arg constructor defaults to `DEBUG`.
- `forLogLevel(LogLevel)` has been available since Spring Boot 3.0.0.
- The 3.3.13 implementation accepts `INFO` or `DEBUG` for the report; passing other levels is not a valid configuration.
- The Javadoc clearly states the listener **is not designed to be shared across multiple ApplicationContexts**. When each test creates a new context, create a new listener for that context.

If you want to see the report right in standard test logs, `INFO` is usually more convenient than `DEBUG`:

```java
.withInitializer(
    ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO)
)
```

However, the log level requested by the listener is still subject to the logging backend's filtering. If the logging system suppresses `INFO`, report lines can still be hidden. Check your test logging configuration if no output appears.

## 3. Attaching the Listener to ApplicationContextRunner

The standard approach in Spring Boot 3.3 is adding the initializer to the runner:

```java
new ApplicationContextRunner()
    .withInitializer(
        ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO)
    )
    .run(context -> {
        // Assertions.
    });
```

In a test with a specific auto-configuration, combine with `AutoConfigurations.of(...)`:

```java
new ApplicationContextRunner()
    .withConfiguration(
        AutoConfigurations.of(FeatureAutoConfiguration.class)
    )
    .withInitializer(
        ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO)
    )
    .run(context -> {
        assertThat(context).hasSingleBean(FeatureService.class);
    });
```

This is an **illustrative snippet**; the `FeatureAutoConfiguration` and `FeatureService` classes must be defined in a real project.

### 3.1. Creating a New Listener for Each Context

Do not create one listener in a static field and reuse it across dozens of different contexts:

```java
// Avoid: the same initializer is used across multiple contexts.
private static final ConditionEvaluationReportLoggingListener LISTENER =
    ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO);
```

The listener's Javadoc warns against sharing instances across contexts. The safe practice is to create a new runner (and new listener) per test or per scenario:

```java
private ApplicationContextRunner newRunner() {
    return new ApplicationContextRunner()
        .withConfiguration(
            AutoConfigurations.of(FeatureAutoConfiguration.class)
        )
        .withInitializer(
            ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO)
        );
}
```

Each call to `newRunner()` creates a runner with its own initializer. Do not call `newRunner()` once and reuse the listener inside that runner across multiple contexts if you want to follow the Javadoc recommendation.

### 3.2. The Listener Does Not Replace Declaring Auto-Configurations Under Test

Merely adding `withInitializer(listener)` does not automatically pull every auto-configuration on the classpath into the test. You still need to specify configuration classes via `AutoConfigurations.of(...)` or an equivalent mechanism.

Conversely, `AutoConfigurations.of(...)` selects auto-configurations to run but does not automatically print the report. The two actions serve separate purposes:

| Component | Responsibility |
| --- | --- |
| `AutoConfigurations.of(...)` | Selects auto-configurations participating in the test |
| `withPropertyValues(...)` | Sets properties for the scenario |
| `withUserConfiguration(...)` | Adds beans/configuration from the application side |
| `withInitializer(listener)` | Requests writing the condition report to logs |
| `assertThat(context)` | Verifies actual behavior and beans |
| `ConditionEvaluationReport` API | Reads condition outcomes programmatically |

## 4. Reading the Report Directly to Inspect Causes

The listener only writes the report to logs. If a test needs structured inspection, retrieve the report from the context's bean factory:

```java
ConditionEvaluationReport report =
    ConditionEvaluationReport.get(context.getBeanFactory());

Map<String, ConditionEvaluationReport.ConditionAndOutcomes> outcomesBySource =
    report.getConditionAndOutcomesBySource();
```

Iterate over the outcomes:

```java
outcomesBySource.forEach((source, outcomes) -> {
    for (ConditionEvaluationReport.ConditionAndOutcome item : outcomes) {
        ConditionOutcome outcome = item.getOutcome();

        System.out.printf(
            "%s | %s | %s%n",
            source,
            outcome.isMatch() ? "MATCH" : "NO MATCH",
            outcome.getMessage()
        );
    }
});
```

In the example, each line shows:

1. Source: the configuration class or bean method carrying the condition.
2. Outcome: `MATCH` or `NO MATCH`.
3. Message: the explanation returned by the condition.

If you need to inspect excluded auto-configurations:

```java
report.getExclusions().forEach(System.out::println);
```

If you need to inspect unconditional classes:

```java
report.getUnconditionalClasses().forEach(System.out::println);
```

**Difference between `get` and `find`:** `ConditionEvaluationReport.get(beanFactory)` retrieves the existing report or creates a new one if none exists yet; `ConditionEvaluationReport.find(beanFactory)` only looks up an existing report and can return `null`. When checking whether a context actually recorded a report, `find` avoids creating an empty report during inspection.

**Note:** one source can have multiple condition outcomes, so iterate over every element instead of assuming a class has only one condition. The report stores data by source; source names are typically class names or `com.acme.MyAutoConfiguration#myBean` for bean methods.

## 5. The Report Is a Diagnostic Tool; Assertions Are the Test Contract

This is the most important point when using the listener:

- Log reports explain why conditions matched or did not match.
- Assertions define the behavior the application must guarantee.
- Both support each other, yet neither replaces the other.

For example, if the business requirement is “when `demo.feature.enabled=true`, `FeatureService` must exist”, the test needs an assertion:

```java
assertThat(context).hasSingleBean(FeatureService.class);
```

If the requirement is “when the property is false, do not create the bean”, the test needs:

```java
assertThat(context).doesNotHaveBean(FeatureService.class);
```

The report can show that `OnPropertyCondition` did not match because the property value was not `true`. Yet if you only enable the listener and watch logs, the test can still pass even if behavior changes unintentionally; logs do not fail the build by themselves.

When you need to verify the condition outcome itself, read `ConditionEvaluationReport` and assert `ConditionOutcome.isMatch()`. This helps detect cases where a bean is absent for a reason different from what you expected.

**Do not assert full default message strings unless necessary.** Messages can change across Boot versions, condition implementations, or how properties/classpath are configured. Prefer asserting bean behavior, boolean outcomes, or a meaningful substring that is stable for your test.

## 6. Standalone Runnable Java 17+ Example with Maven and JUnit 5

The example creates a property-conditional auto-configuration. When `demo.feature.enabled=true`, the `FeatureService` bean appears; when false, it does not. Both tests log the report at INFO level and read outcomes directly for assertions.

### 6.1. Project Structure

```text
condition-report-demo/
├── pom.xml
└── src/
    └── test/
        └── java/
            └── demo/
                └── ConditionEvaluationReportingTests.java
```

No `main()` is needed because this is a test project. Maven Surefire/JUnit will execute the `@Test` methods.

### 6.3. The `src/test/java/demo/ConditionEvaluationReportingTests.java` File

```java
package demo;

import java.util.Map;

import org.junit.jupiter.api.Test;

import org.springframework.boot.autoconfigure.AutoConfiguration;
import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.springframework.boot.autoconfigure.condition.ConditionEvaluationReport;
import org.springframework.boot.autoconfigure.condition.ConditionOutcome;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.autoconfigure.logging.ConditionEvaluationReportLoggingListener;
import org.springframework.boot.logging.LogLevel;
import org.springframework.boot.test.context.assertj.AssertableApplicationContext;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Bean;

import static org.assertj.core.api.Assertions.assertThat;

class ConditionEvaluationReportingTests {

    // Create a new runner per test so each context gets its own listener.
    private ApplicationContextRunner newRunner() {
        return new ApplicationContextRunner()
            .withConfiguration(
                AutoConfigurations.of(FeatureAutoConfiguration.class)
            )
            .withInitializer(
                ConditionEvaluationReportLoggingListener.forLogLevel(
                    LogLevel.INFO
                )
            );
    }

    @Test
    void enabledPropertyMatchesAndCreatesBean() {
        newRunner()
            .withPropertyValues("demo.feature.enabled=true")
            .run(context -> {
                assertThat(context).hasSingleBean(FeatureService.class);

                ConditionOutcome outcome = featureConditionOutcome(context);
                assertThat(outcome.isMatch()).isTrue();

                System.out.println(
                    "enabled: bean=true, conditionMatch=" + outcome.isMatch()
                );
            });
    }

    @Test
    void disabledPropertyDoesNotMatchAndDoesNotCreateBean() {
        newRunner()
            .withPropertyValues("demo.feature.enabled=false")
            .run(context -> {
                assertThat(context).doesNotHaveBean(FeatureService.class);

                ConditionOutcome outcome = featureConditionOutcome(context);
                assertThat(outcome.isMatch()).isFalse();

                System.out.println(
                    "disabled: bean=false, conditionMatch=" + outcome.isMatch()
                );
            });
    }

    private ConditionOutcome featureConditionOutcome(
        AssertableApplicationContext context
    ) {
        ConditionEvaluationReport report =
            ConditionEvaluationReport.get(context.getBeanFactory());

        Map.Entry<String, ConditionEvaluationReport.ConditionAndOutcomes> source =
            report.getConditionAndOutcomesBySource()
                .entrySet()
                .stream()
                .filter(entry ->
                    entry.getKey().contains("FeatureAutoConfiguration")
                )
                .findFirst()
                .orElseThrow(() ->
                    new AssertionError("Feature condition was not recorded")
                );

        return source.getValue()
            .iterator()
            .next()
            .getOutcome();
    }

    @AutoConfiguration
    @ConditionalOnProperty(
        prefix = "demo.feature",
        name = "enabled",
        havingValue = "true"
    )
    static class FeatureAutoConfiguration {

        @Bean
        FeatureService featureService() {
            return new FeatureService();
        }
    }

    static class FeatureService {
    }
}
```

### 6.4. Running the Tests

Requirements: JDK 17+, Maven 3.8+, and ability to download dependencies from a Maven repository. From the `condition-report-demo` directory, run:

```bash
mvn test
```

Logical output printed by the `System.out.println` statements in the two tests:

```text
enabled: bean=true, conditionMatch=true
disabled: bean=false, conditionMatch=false
```

Maven Surefire may capture test stdout into separate reports rather than printing it verbatim to the console; that does not change assertions. When both tests pass, Maven reports `BUILD SUCCESS`. In addition to the lines above, the logging listener prints the condition evaluation report at `INFO` level; formatting, ordering, and number of conditions in logs depend on environment and version.

**Interpretation:**

1. Property-enabled test: `FeatureAutoConfiguration` matches the condition, and the `featureService` bean is registered; the outcome is `true`.
2. Property-disabled test: the condition does not match, and the bean is not registered; the outcome is `false`.
3. Each test calls `newRunner()`, so each context receives a fresh `ConditionEvaluationReportLoggingListener`.
4. The listener makes reasons visible in logs; `assertThat(...)` and `outcome.isMatch()` are what make the test fail when behavior is wrong.

## 7. Reading the Report When Conditions Do Not Match as Expected

When a test reports a missing bean, go in order:

1. **Confirm the auto-configuration was added to the runner.** Check `AutoConfigurations.of(...)` or the test configuration in use. The listener does not add candidates automatically.
2. **Check the actual property.** Use `context.getEnvironment().getProperty("demo.feature.enabled")` inside the callback if the condition depends on a property. Pay attention to values, profiles, and property sources.
3. **Check the classpath.** If the condition uses `@ConditionalOnClass`, inspect runtime/test dependencies and try `FilteredClassLoader` to simulate a missing class.
4. **Check user beans.** `@ConditionalOnMissingBean` can back off when a matching bean already exists. Check `withUserConfiguration(...)` and beans registered via `withBean(...)`.
5. **Read the condition message.** Check which source is recorded in the report, which conditions matched/unmatched, and the specific message.
6. **Verify actual beans with assertions.** The report explains conditions; assertions confirm the context result.

For example, if the report states `OnClassCondition` did not find a required class, check dependencies/classpath first. If the report states `OnBeanCondition` did not find a bean, check auto-configuration ordering, bean name/type, and user configuration. If the report states `OnPropertyCondition` did not match, check the full property name and `havingValue`.

### 7.1. Simulating a Missing Class with FilteredClassLoader

Spring Boot provides `FilteredClassLoader` to test auto-configuration when a class or package is absent from the classpath:

```java
new ApplicationContextRunner()
    .withConfiguration(
        AutoConfigurations.of(MyLibraryAutoConfiguration.class)
    )
    .withClassLoader(
        new FilteredClassLoader(MyLibraryClient.class)
    )
    .withInitializer(
        ConditionEvaluationReportLoggingListener.forLogLevel(LogLevel.INFO)
    )
    .run(context -> {
        assertThat(context).doesNotHaveBean("myLibraryClient");
    });
```

This is an illustrative snippet; `MyLibraryClient` and `MyLibraryAutoConfiguration` must exist. This test specifically checks the missing-class scenario, which is useful for starters with optional dependencies. When testing missing classes/packages, consider using string class names in class conditions and isolating bean methods that directly reference optional classes as guided by Spring Boot.

### 7.2. When a Web Context Is Needed

`ApplicationContextRunner` creates a non-web context. If an auto-configuration only operates in a web environment:

- Use `WebApplicationContextRunner` for Servlet/MVC.
- Use `ReactiveWebApplicationContextRunner` for WebFlux/reactive.

The listener can still be added via `withInitializer(...)` because it implements `ApplicationContextInitializer<ConfigurableApplicationContext>`. Always test the exact context type the auto-configuration expects; if you use a non-web runner for a web condition, the condition may not match as it would in a real application.

## 8. Condition Reports in Tests vs. Real Applications

In a full Spring Boot application, you can enable debug mode at startup to view the condition report:

```bash
java -jar app.jar --debug
```

Or set `debug=true` in an appropriate configuration file. Spring Boot will enable additional selected loggers, including the auto-configuration condition report. Do not interpret debug mode as setting every logger across all libraries to DEBUG.

If the application has Spring Boot Actuator and the endpoint is enabled/exposed properly, `/actuator/conditions` provides an HTTP/JSON report of the context's condition evaluation. That is how you observe a running application; `ConditionEvaluationReportLoggingListener` is how you write the report to logs in context tests.

| Observation Method | Suitable Environment | Output |
| --- | --- | --- |
| `ConditionEvaluationReportLoggingListener` | `ApplicationContextRunner` / test contexts | Writes the report to logs at INFO or DEBUG |
| `ConditionEvaluationReport` API | Test callbacks or internal diagnostic code | Reads structured outcomes, sources, and exclusions |
| `--debug` | Spring Boot application at startup | Enables condition report and selected debug loggers |
| Actuator `/actuator/conditions` | Application with Actuator and exposed endpoint | Condition report via HTTP/JSON |

Never enable the conditions endpoint publicly at will in production. The endpoint can reveal class names, configurations, and infrastructure details; expose only in accordance with application governance and security policies.

## 9. Common Limitations and Pitfalls

### 9.1. Report Not Appearing in Logs

Common causes:

- The listener uses the default `DEBUG` level, while the logging backend does not display DEBUG.
- Using `forLogLevel(LogLevel.INFO)`, yet the logger is filtered at WARN/ERROR.
- The test does not run any conditional auto-configuration, or the report has nothing to observe yet.
- The listener was not added to the runner actually executing; you configured a different runner instance.
- The logging backend in tests differs from the logging backend when running the application.

Fix: attach the listener directly to the test's runner, pick `INFO`, and check logger configuration. Do not change conditions just because logs haven't appeared.

### 9.2. Using Logs to Replace Assertions

Logs only provide diagnostic information. Tests need `assertThat(context).hasBean(...)`, `doesNotHaveBean(...)`, `hasSingleBean(...)`, or outcome assertions. If you rely solely on manual log inspection, behavior regressions can slip past CI.

### 9.3. Reusing One Listener Across Multiple Contexts

The Javadoc warns against sharing listener instances. Create a new listener in your runner factory method or directly inside each test. Never store one static instance to attach to multiple contexts.

### 9.4. Passing an Unsupported Log Level

In Boot 3.3, `forLogLevel` is implemented for `INFO` or `DEBUG`. Do not pass `WARN`, `ERROR`, or `TRACE` expecting the listener to log the report at that level. Pick `INFO`/`DEBUG` and configure the backend accordingly.

### 9.5. Confusing the Report with a Full Startup Trace

The report records condition evaluation collected by Spring Boot. It is not a trace of every Java line, not a dependency tree, not a bean instantiation history, and does not replace exception stack traces. For custom conditions that do not record outcomes through Spring Boot's mechanism, the report may not provide detailed messages like built-in conditions do.

### 9.6. Reading the Report After the Runner Closes the Context

The `run(...)` callback is the right place to inspect the report. Read the report inside the callback while the context is still active. Do not retain the `BeanFactory` or report object to use as live data after the context has closed.

### 9.7. Testing Only One Property

Auto-configuration typically depends on multiple axes. For a real starter, build a test matrix:

- Class dependency present/absent.
- Property enabled/disabled/missing.
- User bean present/absent.
- Web/non-web context if web conditions exist.
- Custom configuration or default back-off.

Each test should assert the outcome and use the listener for diagnosis when outcomes differ from expectations.

## 10. Recommended Practical Workflow

1. Create a base `ApplicationContextRunner` containing only the auto-configurations under test.
2. For each scenario, create a fresh runner/context; attach a fresh listener with `forLogLevel(LogLevel.INFO)` when you want the report easily visible.
3. Set properties, user configuration, and classloader for one specific scenario.
4. Inside the callback, assert beans and context state first.
5. When a condition explanation is needed, read `ConditionEvaluationReport` via the bean factory and print/inspect `ConditionOutcome`.
6. Write tests for both matching and non-matching cases; add a back-off test when the application supplies a custom bean.
7. When a test fails, use the report to locate the first unsatisfied condition, fix the root cause, and keep the assertion to prevent regressions.

## 11. Self-Check Questions

**Question 1.** Which interface does `ConditionEvaluationReportLoggingListener` implement, and which API adds it to `ApplicationContextRunner`?  
**Answer:** It implements `ApplicationContextInitializer<ConfigurableApplicationContext>`; add it with `withInitializer(...)`.

**Question 2.** Which log level does the listener's no-arg constructor use in Spring Boot 3.3?  
**Answer:** `DEBUG`. You can use `forLogLevel(LogLevel.INFO)` to log the report at INFO.

**Question 3.** Can you reuse the same listener instance across ten `ApplicationContextRunner.run(...)` calls?  
**Answer:** You should not. The Javadoc states the listener is not designed to be shared across multiple ApplicationContexts; create a new listener for each context.

**Question 4.** Does the listener automatically add auto-configurations to the context?  
**Answer:** No. `AutoConfigurations.of(...)` or the runner configuration decides which classes are tested; the listener only logs the report.

**Question 5.** If `ConditionOutcome.isMatch()` is true, does that guarantee the final bean was instantiated successfully?  
**Answer:** No. It only indicates the corresponding condition matched. You still need bean assertions, and bean initialization can fail due to other dependencies or exceptions.

**Question 6.** Which API should you use to inspect structured report data?  
**Answer:** `ConditionEvaluationReport.get(context.getBeanFactory())`, then read `getConditionAndOutcomesBySource()`, `getExclusions()`, and `getUnconditionalClasses()`. If you only want to look up an existing report, use `find(beanFactory)`.

**Question 7.** Why should you avoid asserting the entire verbatim log report?  
**Answer:** Log formatting and condition messages can change across versions, loggers, and environments. Assert bean behavior and boolean outcomes; only assert messages when they are a deliberate, stable test contract.

**Question 8.** Which runner should you use to test an auto-configuration that only runs in a Servlet context?  
**Answer:** `WebApplicationContextRunner`. For WebFlux, use `ReactiveWebApplicationContextRunner`.

## 12. Key Takeaways and References

- `ConditionEvaluationReport` is the **data** recording condition evaluation.
- `ConditionEvaluationReportLoggingListener` is the **initializer** that writes that data to logs; it does not alter conditions.
- `ApplicationContextRunner` creates isolated contexts and lets you attach the listener via `withInitializer(...)`.
- Spring Boot 3.3: default constructor logs at DEBUG; `forLogLevel` accepts INFO or DEBUG; do not share a listener across multiple contexts.
- Log the report for **diagnostics**, use assertions to **verify behavior**.
- Read the report with `ConditionEvaluationReport.get(beanFactory)` when structured outcomes are needed; do so inside the runner callback.
- Test every case of property, classpath, user bean, and context type that your auto-configuration depends on.
