# Running a Version Matrix to Detect Condition Changes and Back-Off Behavior

**Topic:** Spring Boot Auto Configuration  
**Knowledge Area:** Version Compatibility  
**Objective:** Build a test suite that runs across multiple Spring Boot lines to catch changes early in class conditions, property conditions, bean conditions, registration ordering, and back-off behavior when applications supply their own beans. This lesson runs the same Java 17 test suite sequentially against Spring Boot 2.6, 2.7, and 3.3.

## 1. Why run tests across multiple versions?

An auto-configuration library may be used by applications across multiple Spring Boot versions. Each version brings its own Spring Framework, Spring Boot Autoconfigure, Binder, condition implementations, and test support.

A test passing on Boot 3 does not prove the library still works on Boot 2.6. Likewise, source code compiling successfully does not prove conditions will match identically at runtime. Changes in dependencies, classpath, auto-configuration order, or how applications register beans can alter results.

Example of a library with a default service:

```java
@Bean
@ConditionalOnMissingBean(ReportService.class)
DefaultReportService reportService() {
    return new DefaultReportService();
}
```

Expected behavior:

- When the feature is enabled and no application-supplied `ReportService` exists, Spring creates the default service.
- When the application supplies a `ReportService`, the auto-configuration backs off.
- When the property is disabled or an optional dependency is absent, the auto-configuration branch is not applied.
- When user configuration and auto-configuration both appear, user beans must be evaluated before the auto-configuration's back-off condition.

If a version has a registration ordering bug, classpath difference, or change in condition processing, some of the cases above may stop holding. A version matrix verifies the same behavioral contract against each dependency baseline.

## 2. Distinguishing stable contracts from intentional differences

Do not run a single test suite and assume every version must share the same internal implementation. Before creating a matrix, identify:

1. **Behavior that must stay stable:** when the feature is enabled, the default bean appears; a user bean replaces the default; when an optional dependency is missing, that branch does not activate.
2. **Version-dependent behavior:** annotation APIs may differ, Java baselines may differ, and auto-configuration registration mechanisms may change.
3. **Behavior that must not be assumed:** incidental classpath ordering, bean names accidentally generated by component scanning, or a condition matching only because a bean was declared in an unguaranteed place.

The matrix below uses three representative milestones:

| Matrix | Spring Boot | Purpose |
| --- | --- | --- |
| Legacy baseline | 2.6.15 | Verify source/APIs and conditions on the 2.x line prior to the new registration mechanism |
| Transition baseline | 2.7.18 | Verify the 2.x transition line and new auto-configuration APIs |
| Modern baseline | 3.3.13 | Verify Spring Boot 3, Spring Framework 6, and Java 17 |

These are milestone versions to illustrate the workflow, not statements about the current support status of release lines. In a real project, replace them with the lowest version the library commits to supporting and one or more versions used in production.

### 2.1. Choosing the JDK for the matrix

Spring Boot 3 requires Java 17 or later. Boot 2.6 and 2.7 can also run on Java 17, so the example uses one JDK 17 across all three profiles to isolate the Spring Boot variable.

If the library still commits to running on Java 8 or Java 11, a separate JDK matrix is required for the older Boot lines. You cannot use the same JDK 8 job to test Boot 3.

A complete matrix can have two dimensions:

- Spring Boot version.
- JDK versions that the Boot line supports and the library commits to supporting.

Do not collapse the results of both dimensions into one single conclusion. Errors caused by Java bytecode/APIs differ from errors caused by Spring conditions or auto-configuration ordering.

## 3. Conditions to include in the matrix

A useful auto-configuration test suite should cover the following groups:

| Condition group | What to verify | How to construct the scenario |
| --- | --- | --- |
| Class condition | Matches when class exists; safely no-matches when missing | Normal classpath and `FilteredClassLoader` |
| Property condition | Missing, false, and true properties yield expected results | `withPropertyValues(...)` |
| Bean condition | Default bean appears only when no matching bean exists | User configuration provides a bean for the same contract |
| Ordering | Bean conditions see beans registered before them | `AutoConfigurations.of(...)` and ordering annotations |
| Context type | Servlet/reactive conditions match only the right context type | `WebApplicationContextRunner` or `ReactiveWebApplicationContextRunner` |
| Bean hierarchy | Whether conditions consider parent contexts | Parent/child contexts if the library uses context hierarchies |

Not every library needs every group. Select based on the annotations and extension points that actually appear in your auto-configuration.

### 3.1. Class condition

`@ConditionalOnClass` and `@ConditionalOnMissingClass` control configuration based on class presence on the runtime classpath.

A test that runs only with a full classpath fails to catch optional dependency bugs. `FilteredClassLoader` simulates a consuming application lacking an optional library without needing to create a second Maven project.

When an optional class is absent, verify both:

- The condition does not match and optional beans do not appear.
- The ApplicationContext still starts without `NoClassDefFoundError` or linkage errors.

If an optional class appears in the signature of a configuration class or `@Bean` method that is not properly isolated, the condition may be evaluated too late to guard class loading. For optional APIs, place class conditions at the appropriate configuration level and keep references to optional APIs inside the guarded branch.

### 3.2. Property condition

`@ConditionalOnProperty` matches by default when the property exists and its value is not `false`. To keep contracts clear and testable, explicitly declare `havingValue` and decide on `matchIfMissing`.

Example:

```java
@ConditionalOnProperty(
        prefix = "acme.feature",
        name = "enabled",
        havingValue = "true",
        matchIfMissing = false
)
```

The matrix should include at least:

- Property undeclared.
- Property set to `false`.
- Property set to `true`.

If the implementation uses `matchIfMissing = true`, expected results must be updated to match that contract. Do not write tests relying on implicit defaults without stating what happens when the property is missing.

### 3.3. Bean condition and back-off behavior

`@ConditionalOnMissingBean` lets applications replace the default bean provided by auto-configuration.

This condition is evaluated based on bean definitions processed up to that point. Therefore, Spring Boot recommends using bean conditions on auto-configuration classes: auto-configurations are loaded after user-defined bean definitions, allowing conditions to see application-supplied beans.

A back-off test must simulate that exact order. Use `AutoConfigurations.of(MyAutoConfiguration.class)` for auto-configurations and `withUserConfiguration(...)` for application configuration. Putting both in as regular configurations may fail to represent the processing order in a real application.

Also declare a sufficiently specific `@Bean` return type. Bean conditions need type information available from the method signature to identify bean definitions before instantiating objects.

## 4. `ApplicationContextRunner` as the foundation of the test suite

`ApplicationContextRunner` creates a small ApplicationContext for each test, letting you vary properties, user configurations, and classloaders without booting an entire application.

Initialization pattern:

```java
private final ApplicationContextRunner contextRunner =
        new ApplicationContextRunner()
                .withConfiguration(
                        AutoConfigurations.of(FeatureAutoConfiguration.class)
                );
```

Configuring auto-configuration via `AutoConfigurations.of(...)` matters significantly:

- Auto-configuration is applied through Spring Boot's test support mechanism.
- User configurations are processed in their proper place before auto-configuration.
- Bean conditions such as `@ConditionalOnMissingBean` can be tested for accurate back-off behavior.
- Each `run(...)` call creates an isolated context, so tests do not leak beans or properties into subsequent tests.

A test should set up one clear scenario and assert actual outcomes: did the context fail, is there exactly one bean, which bean is used, and did the default bean back off.

`ApplicationContextRunner` is well suited for condition/bean tests. It does not replace integration tests that verify resource registration or that an application packages and starts from the published artifact.

## 5. Organizing a Maven project to run multiple Boot baselines

You can use a single shared test project and Maven profiles to select the Spring Boot BOM. Activate **only one profile** per run so all Spring Boot, Spring Framework, JUnit, and AssertJ dependencies align to the same baseline.

### 5.1. `pom.xml`

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>demo</groupId>
    <artifactId>condition-version-matrix</artifactId>
    <version>1.0.0</version>

    <properties>
        <java.version>17</java.version>
        <spring-boot.version>3.3.13</spring-boot.version>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-dependencies</artifactId>
                <version>${spring-boot.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-autoconfigure</artifactId>
        </dependency>

        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <profiles>
        <profile>
            <id>boot-2.6</id>
            <properties>
                <spring-boot.version>2.6.15</spring-boot.version>
            </properties>
        </profile>

        <profile>
            <id>boot-2.7</id>
            <properties>
                <spring-boot.version>2.7.18</spring-boot.version>
            </properties>
        </profile>

        <profile>
            <id>boot-3.3</id>
            <properties>
                <spring-boot.version>3.3.13</spring-boot.version>
            </properties>
        </profile>
    </profiles>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
                <configuration>
                    <release>${java.version}</release>
                </configuration>
            </plugin>

            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
                <version>3.2.5</version>
            </plugin>
        </plugins>
    </build>
</project>
```

The POM imports the Spring Boot BOM instead of listing disconnected Spring versions. When a profile changes `spring-boot.version`, Maven resolves Spring Boot and test dependencies from the same line.

The project avoids `@AutoConfiguration` in shared example source because that annotation does not exist in Boot 2.6. Using `@Configuration(proxyBeanMethods = false)` allows the same test source to compile across all three baselines. In production modules supporting only Boot 2.7 and higher, `@AutoConfiguration` can be used per that version's convention.

### 5.2. Running each baseline

From the directory containing `pom.xml`:

```bash
mvn -Pboot-2.6 clean verify
mvn -Pboot-2.7 clean verify
mvn -Pboot-3.3 clean verify
```

Run each command separately. Do not enable multiple profiles at the same time because they overwrite the same `spring-boot.version` property.

`clean` ensures no classes or resources compiled from a prior baseline are reused. `verify` runs preceding phases, including compile and test, then finishes verification steps configured in the Maven lifecycle.

To confirm the dependency graph matches the active profile:

```bash
mvn -Pboot-2.6 dependency:tree
mvn -Pboot-2.7 dependency:tree
mvn -Pboot-3.3 dependency:tree
```

Verify that `spring-boot-autoconfigure`, `spring-boot-test`, and Spring Framework come from the expected baseline. Avoid pinning a standalone Spring Framework version that prevents tests from representing Boot's dependency graph.

## 6. Shared production code example for the matrix

The example tests an optional feature with a default service. The service is registered only when:

1. The optional library's marker class is present.
2. `acme.feature.enabled=true`.
3. The application has not yet provided a `FeatureService`.

### 6.1. API: `FeatureService.java`

```java
package demo.api;

public interface FeatureService {
    String source();
}
```

### 6.2. Default implementation: `DefaultFeatureService.java`

```java
package demo.api;

public final class DefaultFeatureService implements FeatureService {

    @Override
    public String source() {
        return "auto";
    }
}
```

### 6.3. Optional marker class: `OptionalClient.java`

In the demo project, place this class in test sources to simulate an optional library present during normal testing:

```java
package demo.optional;

public final class OptionalClient {
}
```

In a real library, this would be a class belonging to the optional dependency. Production auto-configuration uses only the class name in the condition, without importing or referencing the optional class in method signatures.

### 6.4. Auto-configuration: `FeatureAutoConfiguration.java`

```java
package demo.autoconfigure;

import demo.api.DefaultFeatureService;
import demo.api.FeatureService;

import org.springframework.boot.autoconfigure.condition.ConditionalOnClass;
import org.springframework.boot.autoconfigure.condition.ConditionalOnMissingBean;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(name = "demo.optional.OptionalClient")
@ConditionalOnProperty(
        prefix = "acme.feature",
        name = "enabled",
        havingValue = "true",
        matchIfMissing = false
)
public class FeatureAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(FeatureService.class)
    DefaultFeatureService defaultFeatureService() {
        return new DefaultFeatureService();
    }
}
```

The three conditions are placed at positions with distinct roles:

- `@ConditionalOnClass` checks the feature's classpath.
- `@ConditionalOnProperty` checks the application's intent to enable the feature.
- `@ConditionalOnMissingBean` on the bean method lets the application replace the default implementation.

The method return type is `DefaultFeatureService`, giving Spring concrete type information. Meanwhile, the condition checks the `FeatureService` contract, because any implementation of this contract must make the default bean back off.

If optional APIs are used directly in the implementation, isolate those references inside a configuration branch guarded by a class-level condition. The current example uses only a marker class by name to keep the focus on the condition matrix.

## 7. Test suite: `FeatureAutoConfigurationMatrixTests.java`

```java
package demo;

import demo.api.DefaultFeatureService;
import demo.api.FeatureService;
import demo.autoconfigure.FeatureAutoConfiguration;

import org.junit.jupiter.api.Test;

import org.springframework.boot.autoconfigure.AutoConfigurations;
import org.springframework.boot.test.context.FilteredClassLoader;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import static org.assertj.core.api.Assertions.assertThat;

class FeatureAutoConfigurationMatrixTests {

    private final ApplicationContextRunner contextRunner =
            new ApplicationContextRunner()
                    .withConfiguration(
                            AutoConfigurations.of(FeatureAutoConfiguration.class)
                    );

    @Test
    void createsDefaultWhenOptionalClassAndPropertyArePresent() {
        this.contextRunner
                .withPropertyValues("acme.feature.enabled=true")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context).hasSingleBean(FeatureService.class);
                    assertThat(context.getBean(FeatureService.class).source())
                            .isEqualTo("auto");
                    assertThat(context.getBeansOfType(DefaultFeatureService.class))
                            .hasSize(1);
                });
    }

    @Test
    void missingPropertyLeavesFeatureDisabled() {
        this.contextRunner.run(context -> {
            assertThat(context).hasNotFailed();
            assertThat(context.getBeansOfType(FeatureService.class)).isEmpty();
        });
    }

    @Test
    void explicitFalseLeavesFeatureDisabled() {
        this.contextRunner
                .withPropertyValues("acme.feature.enabled=false")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context.getBeansOfType(FeatureService.class))
                            .isEmpty();
                });
    }

    @Test
    void missingOptionalClassDisablesFeatureWithoutLinkageFailure() {
        this.contextRunner
                .withClassLoader(new FilteredClassLoader("demo.optional"))
                .withPropertyValues("acme.feature.enabled=true")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context.getBeansOfType(FeatureService.class))
                            .isEmpty();
                });
    }

    @Test
    void userServiceMakesAutoConfigurationBackOff() {
        this.contextRunner
                .withPropertyValues("acme.feature.enabled=true")
                .withUserConfiguration(UserFeatureConfiguration.class)
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context).hasSingleBean(FeatureService.class);
                    assertThat(context.getBean(FeatureService.class).source())
                            .isEqualTo("user");
                    assertThat(context.getBeansOfType(DefaultFeatureService.class))
                            .isEmpty();
                });
    }

    @Configuration(proxyBeanMethods = false)
    static class UserFeatureConfiguration {

        @Bean
        CustomFeatureService customFeatureService() {
            return new CustomFeatureService();
        }
    }

    static class CustomFeatureService implements FeatureService {

        @Override
        public String source() {
            return "user";
        }
    }
}
```

Note the `AutoConfigurations` import and how the runner is created. `FeatureAutoConfiguration` is added as an auto-configuration, while `UserFeatureConfiguration` is added via `withUserConfiguration`. This simulates the order in which user beans exist before auto-configuration evaluates `@ConditionalOnMissingBean`.

### 7.1. Expected result matrix

| Test case | Optional class | Property | User `FeatureService` | Result |
| --- | --- | --- | --- | --- |
| Default path | Present | `true` | Absent | Exactly one default service |
| Property missing | Present | Undeclared | Absent | No service |
| Property disabled | Present | `false` | Absent | No service |
| Optional dependency absent | Absent | `true` | Absent | Context still runs, no service |
| User override | Present | `true` | Present | Only user service, default backs off |

The test suite has five methods. When run on each profile, all five cases must maintain the same expected results if the library declares the same contract across those Boot lines.

### 7.2. Expected test output

Maven Surefire will report five tests run with no failures:

```text
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

The report directory is typically:

```text
target/surefire-reports/
```

You can inspect the XML reports to confirm which tests ran under each profile. Do not stop at checking the `BUILD SUCCESS` line: check the test count and ensure no tests were unexpectedly skipped.

## 8. Moving the matrix into CI

Running three commands manually is useful during development. In CI, you can declare a matrix so each profile runs as an independent job.

GitHub Actions example:

```yaml
name: Spring Boot compatibility

on:
  push:
  pull_request:

jobs:
  condition-matrix:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        boot-profile:
          - boot-2.6
          - boot-2.7
          - boot-3.3

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
          cache: maven

      - name: Run condition and back-off tests
        run: mvn -B -P${{ matrix.boot-profile }} clean verify
```

`fail-fast: false` lets the remaining baselines continue running if one job fails. This helps reveal whether a bug occurs only on one Boot line or across all of them.

If the build needs different Java versions per Boot line, add a `java-version` dimension and specify valid pairs. Do not include an unsupported JDK/Boot combination in the matrix and mistake an environment error for a condition bug.

## 9. Verifying auto-configuration order when using bean conditions

Another scenario sensitive to project structure is auto-configuration A depending on a bean created by auto-configuration B:

```java
@Configuration(proxyBeanMethods = false)
class TransportAutoConfiguration {

    @Bean
    Transport transport() {
        return new DefaultTransport();
    }
}
```

Dependent auto-configuration:

```java
@Configuration(proxyBeanMethods = false)
@AutoConfigureAfter(TransportAutoConfiguration.class)
@ConditionalOnBean(Transport.class)
class TransportClientAutoConfiguration {

    @Bean
    TransportClient transportClient(Transport transport) {
        return new TransportClient(transport);
    }
}
```

`@ConditionalOnBean` sees only bean definitions already processed when the condition runs. If the client configuration is applied before the configuration creating `Transport`, the condition may fail to match even though the bean would be created later.

Therefore:

- Use `@AutoConfigureAfter` or `@AutoConfigureBefore` when there is a dependency relationship between auto-configurations.
- Test both when the prerequisite is present and when it is absent.
- Pass both auto-configurations to `AutoConfigurations.of(...)` to test ordering via Spring Boot's mechanism.
- Do not rely on line order in the imports file or incidental declaration order.

Ordering test example:

```java
private final ApplicationContextRunner orderedRunner =
        new ApplicationContextRunner()
                .withConfiguration(AutoConfigurations.of(
                        TransportAutoConfiguration.class,
                        TransportClientAutoConfiguration.class
                ));
```

If ordering is part of the contract, assert whether `TransportClient` is present or absent based on the prerequisite's state. Do not assert only that the context starts successfully.

## 10. Verifying back-off across multiple levels

`@ConditionalOnMissingBean` is commonly used to let users replace the default bean. Pinpoint the exact contract the condition checks:

- By **type**: any bean compatible with the specified type causes the default to back off.
- By **name**: only a bean with the specified name causes the condition not to match.
- By **annotation**: beans carrying a matching annotation participate in the decision.
- By **context hierarchy**: `search` determines whether beans from parent contexts are considered.

If the application uses parent/child contexts, write dedicated tests for the hierarchy rather than inferring from single-context tests. If the condition needs to ignore certain implementations, check whether the `ignored` attribute is appropriate.

Do not check only that the user bean exists. Also check:

1. Is there exactly one bean matching the contract consumers expect?
2. Is the injected bean the user implementation?
3. Was the default bean truly not registered?
4. Do other unrelated beans still exist?
5. Does the context suffer from ambiguity because the application provided multiple candidates?

A good back-off test checks the identity or behavior of the bean, not just its name.

## 11. Distinguishing condition tests from registration tests

The example above uses:

```java
AutoConfigurations.of(FeatureAutoConfiguration.class)
```

It specifies the class under test directly. That is ideal for testing conditions and back-off, yet it does not prove the auto-configuration registration file was placed properly or packaged into the JAR.

For each released module, add a consumer integration test:

- The test application enables `@EnableAutoConfiguration` or `@SpringBootApplication`.
- It does not directly import the auto-configuration class.
- The consumer adds only the dependency of the artifact being tested.
- Assert the default bean appears or backs off depending on configuration.
- Verify the JAR contains the registration resource in the exact format for that Boot line.

Boot 2.6 uses the legacy registration mechanism via `spring.factories`; Boot 2.7 supports the transition period; Boot 3 uses `AutoConfiguration.imports`. This is a separate compatibility dimension from condition semantics. Do not use `AutoConfigurations.of(...)` results to conclude resource discovery is correct.

If the library supports multiple Boot lines using different sources or artifacts, each consumer test must pull the exact artifact and dependency graph of its corresponding baseline.

## 12. Reading the Condition Evaluation Report when a test fails

When a bean does not appear as expected, identify which condition failed to match. Do not immediately edit annotations solely because the bean is missing.

In an application, run with:

```bash
java -jar app.jar --debug
```

Or set:

```properties
debug=true
```

Spring Boot prints the Condition Evaluation Report, showing which auto-configurations matched and why certain conditions did not match.

If the application includes Actuator and exposes the appropriate endpoint, the `conditions` endpoint provides the condition report in JSON format. Secure this endpoint according to the application's operational policy.

In tests, `ConditionEvaluationReportLoggingListener` can be added to the runner to log the report at the desired log level. Use logs solely for diagnosis; test assertions must still verify expected beans and behavior.

Diagnostic questions:

- Is the optional class actually visible through the context's classloader?
- Does the property have the exact key, active profile, and value?
- Is `matchIfMissing` enabling the feature when the property is absent?
- Was the user bean registered before auto-configuration?
- Does the bean method have a sufficiently specific return type for the condition to recognize it?
- Did a prerequisite auto-configuration run before the configuration evaluating `@ConditionalOnBean`?
- Is the condition inspecting a parent context or bean name different from what was assumed?

## 13. When one version in the matrix fails

Do not immediately edit expected results to make CI green. Triage the cause:

| Symptom | Cause to check | Action |
| --- | --- | --- |
| Only Boot 2.6 fails to compile | Source uses APIs introduced in Boot 2.7 or 3 | Use shared APIs, split source/artifacts by baseline, or adjust support scope |
| Only Boot 3 fails on startup | Different Java baseline, Spring Framework 6, dependencies, or reflection | Read root cause and verify dependency alignment |
| Context does not create default bean | Property/class condition no-match | Read Condition Evaluation Report and verify test inputs |
| Default still appears despite user bean | User config not processed before auto-config or condition checks wrong type/name | Use `AutoConfigurations.of`, fix ordering/return type/condition |
| Missing optional class causes linkage error | Optional type referenced outside guarded branch | Isolate class conditions and optional references |
| Only full-classpath tests pass | Absent optional dependency not tested | Use `FilteredClassLoader` or a consumer module missing the dependency |
| One auto-config depends on another bean yet no-matches | Incorrect ordering | Use `@AutoConfigureAfter`/`@AutoConfigureBefore` and test both states |
| Bean appears twice | Auto-config double-imported/scanned or condition fails to back off | Check registration, component scan, and bean condition |

A failure appearing on only one baseline may be a real regression, or it may be due to a profile pulling the wrong version or an unsuitable JDK. Before changing implementation, inspect the dependency tree and Surefire report of the failing job.

## 14. Common mistakes when building a version matrix

**Mistake 1 — Running the same test suite without switching dependencies per profile.**  
If tests still use a fixed Spring Boot version, the matrix merely creates multiple jobs with the same classpath. Use a profile-controlled BOM or dependency management and inspect the dependency tree.

**Mistake 2 — Activating multiple profiles at once.**  
Profiles overwrite the same `spring-boot.version`, making results depend on activation order. Enable only one profile per job.

**Mistake 3 — Using `@AutoConfiguration` in source that must compile on Boot 2.6.**  
This annotation does not exist in Boot 2.6. If shared source is needed across all three baselines, use a common annotation such as `@Configuration(proxyBeanMethods = false)` or split artifacts/sources by version.

**Mistake 4 — Testing user beans and auto-configurations as two ordinary configurations.**  
`@ConditionalOnMissingBean` relies on already processed bean definitions. Use `AutoConfigurations.of(...)` for auto-configurations and `withUserConfiguration(...)` for user configs to test accurate back-off order.

**Mistake 5 — Asserting only that the context did not fail.**  
The context may start while the default bean is missing or the user bean was not selected. Assert bean counts, implementations, and actual behavior.

**Mistake 6 — Not testing absent optional classes.**  
The development classpath contains all dependencies, masking class-loading bugs. Use `FilteredClassLoader` to simulate real consumers.

**Mistake 7 — Using logic tests to conclude registration resources are right.**  
`AutoConfigurations.of(...)` passes classes directly. Add an integration test using `@EnableAutoConfiguration` and inspect the final artifact.

**Mistake 8 — Assuming `@ConditionalOnMissingBean` sees all future beans.**  
The condition considers only bean definitions already processed. Use auto-configuration ordering and verify return types.

**Mistake 9 — Skipping `clean` between baselines.**  
Stale outputs can linger in the build directory. Run `clean verify` for each profile and avoid sharing output directories across parallel builds.

**Mistake 10 — Running only the latest version.**  
That fails to detect regressions on the lowest baseline the library still declares supported. CI must cover at least the lowest supported version and risky transition milestones.

**Mistake 11 — Changing expected test values to match a new implementation without reviewing the contract.**  
A condition no-match might be a bug, not an acceptable change. Change expected results only when the product contract genuinely changes with a clear compatibility rationale.

## 15. Pre-release checklist

- [ ] Clearly publish supported Spring Boot lines.
- [ ] Select compatible JDKs for each baseline.
- [ ] Each job's dependency graph uses exactly one Spring Boot BOM.
- [ ] Run `clean verify` separately for each profile.
- [ ] Test missing, false, and true properties per contract.
- [ ] Test optional class present and absent.
- [ ] Test default bean creation when no user bean exists.
- [ ] Test user bean causing default back-off.
- [ ] Test `@ConditionalOnBean` and ordering if auto-configuration depends on another bean.
- [ ] Test parent/child contexts if conditions use context hierarchies.
- [ ] Assert bean identity/type/behavior, not just context started.
- [ ] Read Condition Evaluation Report on unexpected no-matches.
- [ ] Test registration resources and packaged artifacts separately from condition tests.
- [ ] Archive reports from each baseline to compare when upgrading Boot versions.

## 16. Self-check questions

**Question 1.** Why is a test passing on Boot 3 insufficient to prove a library is compatible with Boot 2.6?  
**Answer:** Each Boot line brings its own dependencies, Spring Framework, and condition processing. Running tests only on Boot 3's dependency graph does not test the bytecode/API and runtime behavior of Boot 2.6.

**Question 2.** Why use one Spring Boot BOM per job?  
**Answer:** The BOM aligns Spring Boot/Spring Framework/test dependencies to the same baseline. Mixing versions yields results that do not represent any real Boot release.

**Question 3.** What does `ApplicationContextRunner` help test?  
**Answer:** Creating lightweight contexts with specified properties, user configurations, classloaders, and auto-configurations to test conditions and bean behavior independently.

**Question 4.** Why do back-off tests use `AutoConfigurations.of(...)`?  
**Answer:** It places the class into the auto-configuration flow, allowing user beans to be processed before `@ConditionalOnMissingBean` in the exact order Spring Boot uses.

**Question 5.** When an optional class is absent, what must be asserted?  
**Answer:** The condition does not match, the optional bean does not exist, and the context does not fail with `NoClassDefFoundError` or linkage errors.

**Question 6.** Which cases should `@ConditionalOnProperty` test?  
**Answer:** Missing property, explicit false, and true; expected results depend on the declared `havingValue` and `matchIfMissing`.

**Question 7.** Why might `@ConditionalOnMissingBean` fail to back off if a test registers configurations in the wrong order?  
**Answer:** The condition sees only processed bean definitions. If the user bean has not been registered when the condition runs, the default may still be created.

**Question 8.** Does testing `AutoConfigurations.of(MyAutoConfiguration.class)` verify resource registration in the JAR?  
**Answer:** No. It passes the class directly. You need an integration test via `@EnableAutoConfiguration` and inspection of the packaged JAR.

**Question 9.** When only Boot 2.6 fails to compile because of `@AutoConfiguration`, how can that be handled?  
**Answer:** Use a common compatible annotation such as `@Configuration(proxyBeanMethods = false)`, or split artifacts/sources for different baselines.

**Question 10.** Why assert the actual bean used instead of asserting only that the context has no errors?  
**Answer:** The context may start yet pick the wrong implementation, create an unintended default, or omit a required bean. Assertions must verify the runtime contract.

## 17. Key principles to remember

- A condition test suite must run on every Spring Boot baseline the library commits to supporting.
- Use one consistent BOM per job; do not mix dependencies across Boot lines.
- `ApplicationContextRunner` tests properties, classpath, user configurations, and bean behavior in a lightweight context.
- `FilteredClassLoader` catches failures when optional dependencies are absent.
- `AutoConfigurations.of(...)` and `withUserConfiguration(...)` properly test user bean back-off behavior.
- `@ConditionalOnMissingBean` checks only already processed bean definitions; ordering and `@Bean` return types are critical.
- Test missing/false/true properties, present/absent classes, and user overrides per contract.
- Condition tests do not replace integration tests for registration and packaged JARs.
- The Condition Evaluation Report explains match/no-match; assertions verify behavior.
- Do not alter expected results merely to turn the matrix green; cross-check the contract and root cause of differences first.
