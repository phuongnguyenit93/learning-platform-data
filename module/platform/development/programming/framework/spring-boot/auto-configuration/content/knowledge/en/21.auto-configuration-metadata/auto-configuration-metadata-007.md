# additional-spring-configuration-metadata.json for Supplemental Descriptions and Hints

## 1. Goal: Helping IDEs Understand Library Configuration

Spring Boot can automatically generate metadata for properties declared with `@ConfigurationProperties`. This metadata helps IDEs display descriptions, data types, default values, and autocomplete suggestions when users edit `application.properties` or `application.yaml`.

Auto-generated metadata is not always enough. A property may be read using `@Value`, a custom binder, or directly from `Environment`; enum/collection defaults may not be inferred by the processor; or a property may need a clearer description, suggested values, or a replacement key after deprecation.

Spring Boot provides the file:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

The annotation processor reads this file and merges it into the standard metadata:

```text
META-INF/spring-configuration-metadata.json
```

**The additional file is metadata for IDEs and tooling.** It does not register beans, does not create properties in `Environment`, does not make a string automatically become a valid value when binding, and does not replace runtime validation. If a property is declared without any code reading it, metadata only helps the IDE suggest it; the library still needs logic to consume that value.

This lesson uses Spring Boot 3.3.x and Java 17+, walking through JSON structure, `groups`/`properties`/`hints`, value providers, deprecation, annotation processor configuration, and a test verifying the metadata was merged into the artifact.

## 2. Standard Metadata and Additional Metadata

The two files share the same JSON format but have different roles:

| File | Who creates/maintains it? | Role |
| --- | --- | --- |
| `META-INF/spring-configuration-metadata.json` | Generated by annotation processor at compile time | Final metadata read by IDEs and tooling |
| `META-INF/additional-spring-configuration-metadata.json` | Written manually by developer | Supplemental or override data merged into the standard file by the processor |

Do not manually edit the generated file in the build directory. The next compile can overwrite changes. Edit the additional file or Java sources with the corresponding annotations/Javadoc instead.

The additional file is optional. If all properties are already completely described by `@ConfigurationProperties` and the annotation processor, there is no need to create an empty file.

### 2.1. When Should Manual Metadata Be Added?

| Need | Where to declare |
| --- | --- |
| Property belongs to `@ConfigurationProperties`, name and type are clear | Let the processor generate automatically |
| Auto-generated description is missing or unclear | Add `description` |
| Static default of enum/collection is not inferred | Add exact `defaultValue` |
| Property is read by custom code, not present in a properties bean | Add entry in `properties` |
| Want to suggest some commonly used values | Add `hints.values` |
| Want IDE to suggest classes, beans, profiles, or resources | Add `hints.providers` |
| Want to mark an old key and replacement key | Add `deprecation` or use `@DeprecatedConfigurationProperty` when code still handles the old key |

If a group of properties can be cleanly represented by a `@ConfigurationProperties` class, do that first. Supplemental metadata is for information that cannot be inferred or needs editorial refinement.

## 3. Top-Level JSON Structure

The metadata file has three main sections:

```json
{
  "groups": [],
  "properties": [],
  "hints": []
}
```

- `groups` describes property namespaces/groups, e.g., `acme.storage`. Groups do not hold configuration values themselves.
- `properties` describes individual keys users can set, such as `acme.storage.mode`.
- `hints` supplements value choices or semantics so IDEs can support autocomplete.

Not every property is required to have a group. A standalone property can still sit in `properties` without creating a group.

### 3.1. Group

A group object has commonly used attributes:

| Attribute | Required? | Meaning |
| --- | :---: | --- |
| `name` | Yes | Full name of the group, lowercase and dot-separated |
| `type` | No | Class name representing the group's data type |
| `description` | No | Short description for IDEs to display |
| `sourceType` | No | Source class contributing the group |
| `sourceMethod` | No | Source method contributing the group, if the group comes from an annotated method |

Example:

```json
{
  "groups": [
    {
      "name": "acme.storage",
      "type": "com.example.storage.StorageProperties",
      "description": "Settings for the Acme storage integration.",
      "sourceType": "com.example.storage.StorageProperties"
    }
  ]
}
```

`type` and `sourceType` can be the same when the group is based on a `@ConfigurationProperties` class. For a group contributed by a `@Bean` method, `sourceType` can be the configuration class containing that method, while `type` is the return type. If type/source are unknown, you can omit the corresponding attributes rather than guessing.

Groups help IDEs display structured namespaces. They do not create nested Java objects and do not automatically make the binder accept properties.

### 3.2. Property

A property object commonly uses these attributes:

| Attribute | Required? | Meaning |
| --- | :---: | --- |
| `name` | Yes | Full key name, lowercase, dot-separated |
| `type` | No | Class name or generic signature of the value |
| `description` | No | Explains purpose and usage context |
| `sourceType` | No | Source class contributing the property |
| `defaultValue` | No | Actual default value when user does not configure it |
| `deprecation` | No | Deprecated status and replacement guidance |

Example:

```json
{
  "name": "acme.storage.region",
  "type": "java.lang.String",
  "description": "Logical region selected by the storage integration.",
  "sourceType": "com.example.storage.StorageProperties",
  "defaultValue": "local"
}
```

For primitives, metadata uses wrapper types for consistency: `boolean` is `java.lang.Boolean`, `int` is `java.lang.Integer`. For generics, full types can be used such as `java.util.Map<java.lang.String,com.example.Mode>`.

**Default value is descriptive information, not a runtime default assignment command.** If actual code defaults to `local`, metadata can record `"defaultValue": "local"`. If metadata records `cloud` while the constructor/binder actually uses `local`, the IDE will mislead users. Only record the value the code truly uses.

If the default is computed from environment, method calls, file reads, or depends on runtime state, do not guess. You can omit `defaultValue` if an accurate static value cannot be given.

### 3.3. Auto-Generated Properties and Manual-Metadata-Only Properties

When a property has already been recognized by the annotation processor, the additional file can add description, default, or deprecation for the same `name`. The processor merges information by property name; supported manual attributes override corresponding information if declared.

If a property has not been recognized in the module, a manual entry can add it to the metadata. In that case, declare `type` and `description` so the IDE has enough information.

This is useful for properties read by custom code:

```java
String mode = environment.getProperty("acme.storage.mode");
```

This is just a snippet illustrating reading from `Environment`. Adding metadata helps the IDE understand the key, but **does not change** how code reads it and does not create validation. If you want type-safe binding, consider `@ConfigurationProperties`.

### 4.1. Why Does the mode Property Only Declare description/default?

Suppose `StorageProperties` already declared:

```java
@ConfigurationProperties("acme.storage")
public class StorageProperties {

    private Mode mode = Mode.SAFE;

    public Mode getMode() {
        return this.mode;
    }

    public void setMode(Mode mode) {
        this.mode = mode;
    }

    public enum Mode {
        SAFE, FAST
    }
}
```

The annotation processor already knows `acme.storage.mode` and its enum type. The additional file only needs to supply the missing description/default. There is no need to repeat `type` if the type was already generated properly.

The processor might not automatically detect enum defaults. Because code initializes `Mode.SAFE`, the supplemental metadata records `"defaultValue": "safe"` so the IDE reflects the actual default value. If code changes to `Mode.FAST`, update the metadata accordingly.

### 4.2. Metadata-Only Properties Are Not Automatically Bound

For example, `acme.storage.client-class` might be read by a custom resolver using `Environment`. Metadata provides type/description and a class-reference hint. However, if no code reads this key, a user entering it will not make Spring automatically create the client.

Similarly, `acme.storage.client-bean` suggests matching bean names in the IDE. Binder still only binds the bean name string; the application must look up the bean from `ApplicationContext` or use an appropriate injection mechanism. The provider does not automatically turn a string into a bean object.

## 5. Hints: Static Value Suggestions and Semantic Autocomplete

Each hint object has:

| Attribute | Required? | Meaning |
| --- | :---: | --- |
| `name` | Yes | Property name or map key/value name to which the hint applies |
| `values` | No | List of suggested values and descriptions |
| `providers` | No | List of providers that can offer suggestions based on project context |

A value hint has a required `value` and an optional `description`:

```json
{
  "name": "acme.storage.mode",
  "values": [
    {
      "value": "safe",
      "description": "Use conservative defaults for compatibility."
    },
    {
      "value": "fast",
      "description": "Prefer throughput when the backend supports it."
    }
  ]
}
```

The IDE can display the two choices when a user types the mode property. Description helps explain the difference.

**Hints are not validation rules.** If the property is `String`, suggesting `local` and `cloud` does not forbid users from entering `staging`. If you want to restrict runtime values, use an enum, Bean Validation, a custom validator, or corresponding binding logic. If the property is an enum, the binder/runtime is what validates that the value belongs to the enum.

### 5.1. Hints for Map Keys and Values

For Map-typed properties, hints apply to keys or values using suffixes:

- `acme.storage.contexts.keys`
- `acme.storage.contexts.values`

Do not place hints directly on the entire map. Example:

```json
{
  "hints": [
    {
      "name": "acme.storage.contexts.keys",
      "values": [
        { "value": "primary" },
        { "value": "archive" }
      ]
    },
    {
      "name": "acme.storage.contexts.values",
      "values": [
        { "value": "fast" },
        { "value": "safe" }
      ]
    }
  ]
}
```

If the set of keys is truly fixed, an enum may be a better design than arbitrary String keys; IDEs can understand enums natively without manual hints.

### 5.2. The any Provider

The `any` provider lets the IDE suggest certain known values while still accepting other values. It suits String properties that have a common set of values but are not closed.

For example, `acme.storage.region` suggests `local` and `cloud`, while allowing organization-defined regions. Do not attach `any` to an enum that only accepts `SAFE`/`FAST` if you want the IDE to show the exact restricted value set; the runtime enum still rejects unknown values.

### 5.3. The class-reference Provider

`class-reference` suggests classes present in the project. Important parameters:

- `target`: FQCN of the type to which the chosen class must be assignable.
- `concrete`: whether to suggest only concrete classes or allow abstract classes too; defaults to true.

Example:

```json
{
  "name": "acme.storage.client-class",
  "providers": [
    {
      "name": "class-reference",
      "parameters": {
        "target": "com.example.storage.StorageClient",
        "concrete": true
      }
    }
  ]
}
```

This fits when the property has type String to avoid direct dependencies on optional implementation classes. The provider helps the IDE suggest class names; application code still must load/instantiate/validate the class per library policy.

### 5.4. The handle-as Provider

`handle-as` instructs the IDE to treat the property as a higher-level semantic type. It is useful when code keeps a property as a String but users actually enter a value convertible to a specific abstraction.

Common targets include:

- Enum.
- `java.nio.charset.Charset`.
- `java.util.Locale`.
- `org.springframework.util.MimeType`.
- `org.springframework.core.io.Resource`.

Example where `acme.storage.change-log` is stored as a String but holds a resource location:

```json
{
  "name": "acme.storage.change-log",
  "providers": [
    {
      "name": "handle-as",
      "parameters": {
        "target": "org.springframework.core.io.Resource"
      }
    }
  ]
}
```

The IDE can help suggest resource locations such as `classpath:/db/changelog.xml`. That does not automatically turn the String field into a Resource or perform file access; code still needs to convert it when using it.

### 5.5. The spring-bean-reference Provider

This provider suggests bean names existing in the project, filterable by type:

```json
{
  "name": "acme.storage.client-bean",
  "providers": [
    {
      "name": "spring-bean-reference",
      "parameters": {
        "target": "com.example.storage.StorageClient"
      }
    }
  ]
}
```

The IDE can suggest bean names assignable to `StorageClient`. This is still a string value in configuration. If the application needs to use that bean, code must look up the bean via the context or design proper injection; metadata does not make Binder resolve beans automatically.

### 5.6. The spring-profile-name Provider

The `spring-profile-name` provider helps suggest profiles defined in the project:

```json
{
  "name": "spring.profiles.active",
  "providers": [
    {
      "name": "spring-profile-name"
    }
  ]
}
```

This provider can be used for Spring's profile properties or custom properties with similar semantics. This is a suggestion based on IDE/project context, not a list of profiles Spring runtime is forced to use.

### 5.7. The logger-name Provider

`logger-name` suggests known logger names and logger groups. The `group` parameter can control whether logger groups are included in suggestions; defaults to true per the provider specification.

This provider fits properties accepting a logger category. Since a logger name can be any package/class name, suggestions should not be treated as a closed list.

### 5.8. Multiple Providers and IDE Support

IDEs are not required to support every provider. If an IDE does not understand a provider, it can ignore that hint without causing runtime application errors.

You can declare multiple providers for the same property if they are all useful. The IDE uses the first provider it supports; therefore put the strongest-semantics provider first. Do not rely on providers to guarantee identical experiences across all IDEs.

## 6. Deprecation Metadata: Guiding Users to the New Key

A deprecated property can have a `deprecation` object:

| Attribute | Meaning |
| --- | --- |
| `level` | `warning` or `error`; defaults to warning |
| `reason` | Reason the old key was deprecated |
| `replacement` | Full name of the replacement property |

The two levels have different meanings:

- `warning`: the property is still managed/bound; the application can maintain compatibility during the transition period.
- `error`: the property is no longer managed and is not bound as a supported property.

If the old key is still supported in code, keep the logic reading/mapping it to the new key. Warning metadata only describes status; it does not write an adapter or migrate values automatically. If the key has been removed, error metadata can continue helping IDEs warn users that the old key is no longer valid and point to the replacement.

### 6.1. Using @DeprecatedConfigurationProperty When Code Still Supports the Old Key

If a `@ConfigurationProperties` class still has compatible getter/setter for the old key, you can use `@Deprecated` and `@DeprecatedConfigurationProperty` on the getter:

```java
@ConfigurationProperties("acme.storage")
public class StorageProperties {

    private String mode;

    public String getMode() {
        return this.mode;
    }

    public void setMode(String mode) {
        this.mode = mode;
    }

    @Deprecated
    @DeprecatedConfigurationProperty(
            replacement = "acme.storage.mode")
    public String getLegacyMode() {
        return this.mode;
    }

    @Deprecated
    public void setLegacyMode(String legacyMode) {
        this.mode = legacyMode;
    }
}
```

This is an illustrative example of a bean retaining the old property as an alias for the new property; real code must ensure both keys map to the same state per the published contract.

This annotation produces deprecation at the warning level because code still handles the old key. It does not offer a way to set the error level. When getters/setters have been removed from the public API yet you still want to keep a reminder for users, manual metadata can declare error deprecation and replacement.

### 6.2. Do Not Confuse Metadata Deprecation with Java's @Deprecated

`@Deprecated` on a Java method/class and configuration property deprecation metadata are related but do not replace each other. A Java getter may be deprecated while the key still binds. A property marked error in metadata may no longer be managed by Boot even if users still type the key in YAML.

Define the contract clearly:

- Still supporting the old key: keep compatibility code and use warning.
- Stopped supporting: remove old binding/logic and use error-level metadata.
- Have a replacement: write the exact full property name, not the Java field name or getter name.

## 7. Annotation Processor: Source of Merged Metadata

Spring Boot provides the `spring-boot-configuration-processor` artifact. The annotation processor scans `@ConfigurationProperties` classes/methods at compile time and generates `META-INF/spring-configuration-metadata.json`.

### 7.1. Maven

Declare the processor as an optional dependency in the module containing configuration properties:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>
```

`optional` keeps the processor dependency from becoming a mandatory runtime dependency of consumers. If the project configures Maven Compiler Plugin with an explicit annotation processor path, add the processor to that configuration.

The standard Maven lifecycle processes resources before compile. If a custom build changes this order, ensure the additional file is present when the processor runs.

### 7.2. Gradle

With Gradle, declare the processor in its own configuration:

```groovy
dependencies {
    annotationProcessor(
        "org.springframework.boot:spring-boot-configuration-processor:3.3.13"
    )
}
```

When using an additional file in `src/main/resources`, ensure `compileJava` takes resources output as an input so the processor sees the file before compile:

```groovy
tasks.named('compileJava') {
    inputs.files(tasks.named('processResources'))
}
```

This is an easily forgotten step. If the processor runs before resources are processed, auto-generated metadata may still appear, while manual descriptions/hints are not merged as expected.

### 7.3. What Can the Annotation Processor Generate?

The processor reads `@ConfigurationProperties` on classes and methods. It can detect group/property names, types, descriptions from Javadoc in supported cases, certain static defaults, and nested/collection/map structures.

Not every default can be auto-detected. Enum/collection defaults and dynamically computed values may need manual metadata. If source Javadoc is copied directly into JSON, use simple plain text; do not expect Markdown or HTML to be rendered as rich-text documentation.

### 8.2. Test Reading the Generated Metadata File

`src/test/java/com/example/storage/AdditionalMetadataTest.java`:

```java
package com.example.storage;

import java.io.IOException;
import java.io.InputStream;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;

import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class AdditionalMetadataTest {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Test
    void generatedMetadataContainsManualDescriptionDefaultAndHints()
            throws IOException {

        InputStream stream = getClass().getResourceAsStream(
                "/META-INF/spring-configuration-metadata.json");

        assertThat(stream)
                .as("Generated Spring configuration metadata must exist")
                .isNotNull();

        try (stream) {
            JsonNode root = objectMapper.readTree(stream);

            JsonNode mode = findByName(
                    root.path("properties"), "acme.storage.mode");

            assertThat(mode).isNotNull();
            assertThat(mode.path("description").asText())
                    .contains("execution strategy");
            assertThat(mode.path("defaultValue").asText())
                    .isEqualTo("safe");

            JsonNode oldMode = findByName(
                    root.path("properties"), "acme.storage.old-mode");

            assertThat(oldMode).isNotNull();
            assertThat(oldMode.path("deprecation")
                    .path("level").asText()).isEqualTo("error");
            assertThat(oldMode.path("deprecation")
                    .path("replacement").asText())
                    .isEqualTo("acme.storage.mode");

            JsonNode modeHint = findByName(
                    root.path("hints"), "acme.storage.mode");

            assertThat(modeHint).isNotNull();
            assertThat(modeHint.path("values")).hasSize(2);
            assertThat(modeHint.path("values").get(0)
                    .path("value").asText()).isEqualTo("safe");

            JsonNode classHint = findByName(
                    root.path("hints"), "acme.storage.client-class");

            assertThat(classHint).isNotNull();
            assertThat(classHint.path("providers").get(0)
                    .path("name").asText()).isEqualTo("class-reference");
        }
    }

    private static JsonNode findByName(JsonNode entries, String name) {
        for (JsonNode entry : entries) {
            if (name.equals(entry.path("name").asText())) {
                return entry;
            }
        }
        return null;
    }
}
```

This test verifies the **output metadata**, not runtime binding of `StorageProperties`. The goal is to prove the processor merged the additional file into the standard resource and the JSON has a parseable structure.

## 9. How to Verify in the IDE

After the project compiles, the IDE can use metadata to:

- Suggest property names when typing `acme.storage.`.
- Show descriptions on hover or when opening the documentation popup.
- Suggest `safe` and `fast` for `acme.storage.mode`.
- Offer class candidates for `acme.storage.client-class`.
- Offer bean candidates for `acme.storage.client-bean`.
- Support resource locations for `acme.storage.change-log`.
- Warn on deprecated properties and offer replacements.

If metadata in the JAR is right but the IDE does not display it:

1. Re-import/reload the Maven or Gradle project.
2. Re-run compile so the annotation processor generates a fresh file.
3. Check the `META-INF/spring-configuration-metadata.json` output in build/classes or the JAR.
4. Check whether the IDE supports the corresponding provider.
5. Ensure the IDE is using the module containing the artifact with metadata.
6. If there are multiple modules, identify which module owns the metadata and whether that module is in the current project model.

Not every IDE implements every provider. Autocomplete for classes/beans/profiles/resources can vary; that does not change Spring Boot's runtime behavior.

## 10. Common Errors

| Symptom | Cause | Fix |
| --- | --- | --- |
| Manual description does not appear | File at wrong path or processor ran before resources were processed | Check additional path and task ordering |
| Generated metadata disappears | Developer edited the standard output file directly | Edit the additional file or Java source, then rebuild |
| JSON is ignored | Invalid comma, bracket, data type, or disallowed comments | Validate JSON before compiling |
| IDE suggests property but application does not use value | Metadata only describes the key; code does not bind/read that key | Add `@ConfigurationProperties` or property-reading logic |
| IDE suggests unknown value but runtime rejects it | Hints are not validators | Use enum/Bean Validation/custom validator |
| Default in IDE differs from runtime | Manual `defaultValue` does not match constructor/field initializer | Synchronize metadata with actual default or omit default if unsure |
| Provider suggests nothing | IDE does not support provider or target class is wrong | Check support and FQCN/parameters |
| Bean-reference hint yet bean is not injected | Provider only suggests bean names | Use ApplicationContext lookup or dependency injection |
| Map hint does not work | Hint attached to map instead of keys/values | Use `.keys` or `.values` suffixes |
| Deprecated key still accepted despite warning metadata | Warning preserves binding capability | Keep alias intentionally or switch to error when support stops |
| Additional file is right but JAR lacks standard metadata | Processor did not run or resource merge failed | Check annotationProcessor/Maven compile and JAR output |

### 10.1. Do Not Use Additional Metadata to Replace Runtime Validation

For example, the metadata file may state that `acme.storage.mode` only accepts `safe` or `fast`. Yet if the code property is `String`, users can still enter `turbo` unless runtime code checks it.

If the value set is truly closed, declare a Java enum:

```java
public enum Mode {
    SAFE, FAST
}
```

If the value set is extensible, keep String and use domain validation. Hints only assist value discovery; they do not enforce contracts.

### 10.2. Do Not Declare Defaults That Do Not Exist in Code

Metadata can record a default for the IDE to display, but the binder does not read the metadata file to assign object values. If the field initializes to `SAFE`, describe `safe`. If the default depends on profiles/environment, do not write a misleading fixed value.

### 10.3. Do Not Confuse Deprecation Warning with Removal

`warning` indicates the old key is still managed. `error` indicates the key is no longer managed/bound as a supported property. If you want to transition an API gradually, keep aliases and compatibility logic during the warning period; only use error after the contract has dropped the old key.

## 11. Version Boundary: Do Not Use Boot 3.5 Metadata in a Boot 3.3 Project

The `groups`, `properties`, `hints`, value hints, providers, and deprecation format are the foundation of configuration metadata in Boot 3.x.

However, not every metadata field in later versions exists in Boot 3.3. Specifically, `ignored.properties` support for excluding properties from generated metadata was introduced in Spring Boot 3.5. If a module targets Boot 3.3, do not copy the `ignored` structure from Boot 3.5+ docs/metadata expecting the 3.3 processor to behave the same way.

For Boot 3.3, focus on `groups`, `properties`, `hints`, and `deprecation`. If you need to hide/exclude a generated property, handle it in the source model or upgrade the processor version intentionally after evaluating compatibility.

## 12. Checklist Before Merging Metadata

- [ ] File is located at `src/main/resources/META-INF/additional-spring-configuration-metadata.json`.
- [ ] Root JSON uses `groups`, `properties`, and `hints` properly.
- [ ] Every group/property/hint has a full `name` and exact canonical property name.
- [ ] Type is an accurate FQCN or generic signature.
- [ ] Description is short, clear, plain text, and ends with a period.
- [ ] Default value matches the actual default in code.
- [ ] Manual properties are not mistaken as automatically bound.
- [ ] Value hints reflect accurate suggested values, not pretending to be runtime validation.
- [ ] Provider target is a valid FQCN and IDE-supported.
- [ ] Map hints use `.keys`/`.values` suffixes.
- [ ] Bean reference hints are not mistaken as automatically resolving beans.
- [ ] Deprecation level/reason/replacement match the compatibility policy.
- [ ] Annotation processor is configured in Maven/Gradle.
- [ ] Gradle compile task depends on processResources when using an additional file.
- [ ] Test can read the merged `META-INF/spring-configuration-metadata.json`.
- [ ] Published JAR contains the standard metadata.
- [ ] Boot 3.5 `ignored.properties` is not used in modules targeting Boot 3.3.
- [ ] The team's actual IDE displays the important suggestions.

**Takeaway:** `additional-spring-configuration-metadata.json` is how you add documentation and hints to auto-generated configuration metadata. Use `properties` to describe keys, `groups` to organize namespaces, `hints.values` for value suggestions, and `hints.providers` for semantic autocomplete. Use deprecation to guide users to new keys. Finally, verify that the processor merged the file into `META-INF/spring-configuration-metadata.json` inside the artifact. Metadata helps IDEs understand configuration; code and validation remain responsible for runtime behavior.
