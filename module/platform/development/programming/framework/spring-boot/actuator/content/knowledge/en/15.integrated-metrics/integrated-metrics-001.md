# Monitoring the JVM: Heap, Non-Heap, GC, Threads, and Loaded Classes

## 1. Starting from the Question: What Is the JVM Using Resources For?

A Java application can be slow for many different reasons: creating too many temporary objects, holding objects alive for too long, lock contention, spawning too many threads, or continuously generating new classes. Looking only at a single "RAM used" curve cannot distinguish among those situations.

When monitoring the JVM, five groups of information need to be connected:

- **Heap:** the region containing Java objects and arrays.
- **Non-heap:** regions managed by the JVM outside the heap, such as class metadata and machine code generated by the JIT.
- **GC:** memory reclamation activity, pause times, and related data.
- **Threads:** the number of live threads, peak level, and state distribution.
- **Loaded classes:** the number of classes currently loaded and the amount of classes unloaded.

Each group answers a distinct question. They should be read over time, alongside application load and JVM version, rather than using a single point value to immediately conclude "there is a leak" or "increase the heap."

In Spring Boot 3.3, Actuator auto-configures Micrometer binders to provide many JVM metrics under names starting with `jvm.`. See [Spring Boot: JVM Metrics](https://docs.spring.io/spring-boot/3.3/reference/actuator/metrics.html#actuator.metrics.supported.jvm).

## 2. Data Sources and Map of Metric Groups

Many measurements obtain data from JVM management interfaces, commonly called MXBeans, together with notifications emitted by the JVM. Micrometer wraps them into meters; Actuator provides diagnostic endpoints and integration with monitoring systems.

```text
JVM: memory regions, GC, threads, class loading
    -> MXBeans and JVM notifications
    -> Micrometer binders
    -> MeterRegistry
    -> Actuator or exporter
    -> monitoring system and time-series analysis
```

Some commonly seen names with Micrometer 1.13.x:

| Group | Meter Name | Primary Reading |
| --- | --- | --- |
| Memory | `jvm.memory.used` | Bytes currently used by the pool |
| Memory | `jvm.memory.committed` | Bytes the JVM is guaranteed to have available for the pool |
| Memory | `jvm.memory.max` | Maximum limit of the pool if determinable |
| Buffer | `jvm.buffer.memory.used`, `jvm.buffer.count` | Memory and count of buffers by JVM-provided pool |
| GC | `jvm.gc.pause` | Count and duration of pause events recorded by the binder |
| GC | `jvm.gc.live.data.size` | Live data size according to GC information available to the binder |
| GC | `jvm.gc.memory.allocated` | Allocation amount tracked/estimated by the binder |
| Threads | `jvm.threads.live`, `jvm.threads.daemon` | Number of live threads and daemon threads |
| Threads | `jvm.threads.peak`, `jvm.threads.states` | Peak thread count and thread count by state |
| Classes | `jvm.classes.loaded`, `jvm.classes.unloaded` | Number of currently loaded classes and amount of unloaded classes |

Do not treat the table as a guarantee that every JVM/collector provides every meter right from startup. Pool names, GC notifications, support capabilities, and some details vary by JVM, JDK, collector, and Micrometer version.

Inspect the actual list of meters/tags before building dashboards. The corresponding binders are described in [Micrometer 1.13: JVM Metrics](https://docs.micrometer.io/micrometer/reference/1.13/reference/jvm.html).

## 3. Heap: Distinguishing used, committed, and max

### 3.1. Three Numbers That Cannot Substitute for One Another

The heap contains objects and arrays allocated while the program runs. Objects that are no longer reachable can be reclaimed by GC, though not necessarily immediately after references disappear.

Three values to distinguish:

| Value | Meaning | What Not to Mistake It For |
| --- | --- | --- |
| `used` | Capacity currently in use | Total physical RAM of the process |
| `committed` | Capacity guaranteed to be available for the memory region | Only the portion holding live objects |
| `max` | Maximum limit if determinable by the JVM | Capacity guaranteed to still be allocatable from the operating system |

For a given `MemoryUsage` snapshot, `used <= committed`. If max is defined, committed is no greater than max. The max value can be `-1` when undefined; that is not a negative capacity. See [Java MemoryUsage](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/MemoryUsage.html).

Conceptual example: used=300 MiB, committed=512 MiB, max=1024 MiB. The application is using 300 MiB within a guaranteed region of 512 MiB; a limit of 1024 MiB does not mean the operating system always has another 512 MiB free for the process.

`1 MiB = 1024 × 1024 bytes`. Check units when comparing tools; do not mix bytes with MiB or decimal MB.

### 3.2. Pool Names Depend on the Collector

With HotSpot/G1 you may see `G1 Eden Space`, `G1 Survivor Space`, and `G1 Old Gen`. Other collectors may use different names or organize memory regions differently.

Commonly used tags are:

- `area=heap` or `area=nonheap`.
- `id` as the actual pool name.

Do not hard-code G1 names into dashboards intended for every JVM. Switching collectors can make a per-pool series disappear even though the application is running normally.

### 3.3. Do Not Mechanically Sum Every Pool's max and Divide

Some pools report max=-1; some pool limits depend on how the collector organizes the heap. Summing max values without understanding the pools can produce a meaningless denominator.

To inspect an overall heap snapshot at the Java layer, you can read:

```java
MemoryUsage heap = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
long used = heap.getUsed();
long max = heap.getMax();
```

This is an illustrative snippet requiring imports for `java.lang.management.MemoryUsage` and `ManagementFactory`; it is not a standalone program.

Only compute `used / max` when max is valid and greater than 0. When max=-1, display "unknown" rather than substituting 0 or showing a negative percentage.

### 3.4. High Heap Alone Is Not Enough to Conclude a Leak

Heap growing and then dropping after GC is normal behavior. What warrants attention is the trend of surviving data across multiple GC cycles under comparable load.

Possibilities to distinguish:

- Increased load causes more objects to coexist simultaneously.
- A cache is warming up or growing toward its expected limit.
- Temporary objects are allocated rapidly but reclaimed promptly.
- A structure holds references longer than expected, raising the post-GC memory baseline.
- A batch job creates a temporary memory spike.

Metrics help recognize patterns; they do not pinpoint which objects are retained or which reference chains cause it. When a conclusion is needed, more detailed evidence is required.

## 4. Non-Heap and the Memory That Heap Does Not Explain

### 4.1. Non-Heap Is Not a Single Region

In HotSpot, you may encounter:

- **Metaspace:** metadata serving loaded classes.
- **Compressed Class Space:** class data under compressed class pointers when configured/used by the JVM.
- **CodeHeap/Code Cache:** machine code and data supporting JIT compilation.

Pool names and counts can differ across environments. Do not call all non-heap Metaspace; Code Cache also serves its own role.

A regular Java object and its class metadata are not the same thing. A rise in instance count mainly changes the heap; a rise in dynamic classes can relate to Metaspace and class loading. Heap and non-heap regions are described by the JVM in [MemoryMXBean](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/MemoryMXBean.html).

### 4.2. Heap used Plus Non-Heap used Does Not Equal Total Process RAM

A process can also use memory for platform thread stacks, direct buffers, native libraries, internal JVM structures, memory-mapped files, and other components. Not all of those items fall into the pools reported under `jvm.memory.*`.

`jvm.buffer.*` helps observe buffer pools exposed by the JVM, but it is still not an inventory of all native memory.

Therefore:

```text
heap used                 != process RSS
heap used + nonheap used  != complete inventory of every process byte
-Xmx                      != limit on total process RAM
```

RSS measures resident memory pages observed by the operating system. It does not share the same definition as used, committed, or reserved address space.

A container can hit its memory limit while the heap is not yet full. JVM data must be read alongside process/container memory and system load, rather than simply increasing `-Xmx`.

### 4.3. Do Not Use One Percentage Threshold for Every Pool

Metaspace can report max=-1 if there is no defined limit according to JVM-provided information. In that case, you cannot construct a "used out of max" percentage by ordinary division.

For Code Cache, Metaspace, and heap, consider absolute scale, trends, practical limits, startup phase, and application characteristics. An arbitrary threshold applied to all pools can trigger false alarms or miss real problems.

## 5. GC: Look at Reclamation Activity, Not Just Counts

### 5.1. GC Is Not Responsible for Reclaiming Still-Referenced Objects

GC looks for memory that can be reclaimed and reused. If the application still holds an object via a cache, list, or other reference, GC cannot decide on its own that the object is "no longer needed by business logic."

Object allocation rate, object lifetime, and retained data size all affect GC activity. Collectors can have both pause phases and concurrent work; "GC time" is not a single number with the same meaning across all measurement methods. See [Java 21: Introduction to Garbage Collection Tuning](https://docs.oracle.com/en/java/javase/21/gctuning/introduction-garbage-collection-tuning.html).

### 5.2. Read Pauses with Both Count and Duration

`jvm.gc.pause` is represented by a Timer. Inspect at least:

- Count: how many pause events have been recorded.
- Total time: total duration of the recorded pause samples.
- Max/distribution if configured: whether unusually long pauses occurred.
- Actual tags: distinguishing action/cause groups provided by the collector and binder.

Conceptual example: 100 short pauses and 2 very long pauses can impact latency differently even though looking only at a total GC count obscures that. Pauses must be correlated with request latency, throughput, and load over the same timeframe.

Do not equate total pause time with CPU consumed by GC, or with the total time of all concurrent phases. Those pieces of information have different scopes.

### 5.3. No Pause Meter Initially Does Not Mean GC Is Unsupported

Some series are created only when the binder receives a matching event. On a newly started JVM, `jvm.gc.pause` may not appear yet or may have no samples.

Likewise, live data from GC may not have been updated by a suitable event yet. An initial value of 0 does not by itself prove the heap has no live objects.

The lab exercise does not call `System.gc()` to force an output. When diagnosing an application, examine the collector, when the binder attached, what load has run, and notification support before drawing conclusions.

### 5.4. Allocated Data and Live Data Answer Two Different Questions

`jvm.gc.memory.allocated` reflects the allocation amount tracked/estimated by the binder. `jvm.gc.live.data.size` reflects live data according to GC information available to the binder, not an exact scan of every object at the moment a user opens the dashboard.

An application can allocate very fast while retaining little data; it can cause GC pressure without a leak. Conversely, steadily rising retained data can warrant investigation even when allocation rate does not spike.

At the MXBean layer, collection count and collection time can have value `-1` if the collector does not provide them. Do not turn an "undefined" value into a conclusion that "no GC occurred." See [GarbageCollectorMXBean](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/GarbageCollectorMXBean.html).

### 5.5. Conclusions to Avoid

- "Many GCs" is not enough to say the application has a leak.
- "Heap dropped after GC" is not enough to prove no objects are held too long.
- "Pause max equals 0" after a quiet period is not proof that the most recent GC took 0 seconds; max statistics can decay/expire.
- "Increasing heap" may change GC frequency but does not fix a structure retaining data erroneously.
- Pool names or GC labels changing after switching collectors does not mean all monitoring data remains directly comparable.

## 6. Threads: Counts, States, and Observation Limits

### 6.1. Live, Daemon, and Peak Differ

- `jvm.threads.live`: number of currently live platform threads observed by the JVM management source.
- `jvm.threads.daemon`: the daemon-thread portion among live threads.
- `jvm.threads.peak`: peak live thread count since JVM startup or since the peak was last reset at the management source.
- `jvm.threads.states`: number of threads by state at the time of observation.

Peak is not the current running thread count and does not have the same expiration mechanism as a Timer's max. A high peak can remain after a load burst ends.

Many threads do not automatically mean much work is using CPU. You must read thread states and functions.

### 6.2. Reading States According to Java Semantics

| State | Primary Meaning | Something You Cannot Conclude From State Alone |
| --- | --- | --- |
| `RUNNABLE` | Thread in a state eligible to execute in the JVM | Using 100% CPU or definitely not waiting on an OS resource |
| `BLOCKED` | Waiting to acquire a monitor lock | Deadlock has occurred |
| `WAITING` | Waiting indefinitely for another action | Thread is broken or leaked |
| `TIMED_WAITING` | Waiting with a timeout | Application is hung |
| `NEW` | Not yet started | Already a live thread doing work |
| `TERMINATED` | Finished execution | Still contributing as a live thread |

`BLOCKED` is tied to acquiring a monitor, typically involving `synchronized`. Do not use that word as a generic label for every kind of I/O wait or lock wait.

A worker waiting on an empty queue can be in WAITING; that can be a normal idle state. To conclude contention or a stall, inspect stack traces, the awaited object, work throughput, and how long the state persists.

These states are JVM states and do not match OS-reported thread states one-to-one. See [Java Thread.State](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.State.html).

### 6.3. Java 21: Do Not Treat This as the Total of All Virtual Threads

`ThreadMXBean` in Java 21 manages platform threads and does not provide virtual thread tracking through those same statistics. Binders built on this source do not automatically become counters for all virtual threads.

Therefore, when an application uses virtual threads, do not interpret `jvm.threads.live` as the number of live virtual tasks. Use measurements/tools appropriate to the thread type and library versions in use. See [ThreadMXBean Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/ThreadMXBean.html).

This is also why you need to know the execution architecture before setting alerts based solely on thread count.

### 6.4. Counting States Does Not Replace a Thread Dump

A total BLOCKED count does not tell you who holds the lock. A total WAITING count does not tell you whether tasks are waiting on a queue, condition, I/O, or another coordination operation.

When signs persist, capture appropriate stack/lock evidence and compare multiple points in time. Deadlock requires evidence of a circular wait relationship or corresponding detection tooling, not merely a BLOCKED thread.

## 7. Loaded Classes: Distinguishing Current from Historical Total

`ClassLoadingMXBean` distinguishes:

| Quantity | Meaning |
| --- | --- |
| Loaded class count | Number of classes currently loaded |
| Total loaded class count | Total number of classes ever loaded since JVM startup |
| Unloaded class count | Total number of classes unloaded since JVM startup |

`jvm.classes.loaded` of the binder in use is a Gauge for the number of classes currently loaded. `jvm.classes.unloaded` tracks cumulative unloading; it is not "the number of classes in an unloaded state." See [ClassLoadingMXBean](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/java/lang/management/ClassLoadingMXBean.html).

A Spring application can load additional classes at startup, when a feature is used for the first time, or when generating proxies/dynamic code. A rising loaded curve during warmup is not enough to prove a classloader leak.

Points to examine together:

- After warmup and under steady load, does the class count keep rising?
- Does Metaspace grow at the same rate, or does it plateau?
- Does the application use plugins, dynamic compilation, proxy generation, or reloading mechanisms?
- Are references still held to classloaders whose lifecycle should have ended?
- Is data being compared from the same process, or did the JVM just restart?

One class name can be loaded by different classloaders as distinct class definitions. The class count metric is not simply the number of distinct `.class` filenames in the repository.

Class unloading depends on reachability/reclaimability and JVM/collector mechanisms. Do not expect every reclaimed object to cause its class to be unloaded as well.

## 8. Reading via Spring Boot Actuator

### 8.1. Expose the Right Endpoints in a Diagnostic Environment

In a Spring Boot application with web and Actuator, an illustrative configuration is:

```properties
management.endpoints.web.exposure.include=health,metrics
```

This is an integration setting for an existing application; the console program later in this lesson does not start HTTP. For applications requiring remote access, configure proper authentication, authorization, and management network restrictions before exposing data.

Spring Boot already auto-configures many JVM binders. Do not manually re-register all binders into the application's registry simply because the console example does so.

### 8.2. Explore Names and Tags Before Filtering

The commands below use `curl.exe` on Windows. On Linux/macOS, substitute `curl`. The example URL assumes the web application is running locally on port 8080:

```powershell
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics"
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics/jvm.memory.used"
```

Read `measurements`, `baseUnit`, and `availableTags`. Without filtering, a metric name may represent multiple aggregated meters/pools; it is not automatically a single memory region.

Filter for heap:

```powershell
curl.exe --silent --show-error --get "http://127.0.0.1:8080/actuator/metrics/jvm.memory.used" --data-urlencode "tag=area:heap"
```

If the actual tag list includes `G1 Old Gen`, you can inspect that pool individually:

```powershell
curl.exe --silent --show-error --get "http://127.0.0.1:8080/actuator/metrics/jvm.memory.used" --data-urlencode "tag=area:heap" --data-urlencode "tag=id:G1 Old Gen"
```

`--data-urlencode` preserves pool names containing spaces. Do not assume G1 names exist when running a different collector.

Similarly, read:

```powershell
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics/jvm.threads.live"
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics/jvm.threads.states"
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics/jvm.classes.loaded"
curl.exe --silent --show-error "http://127.0.0.1:8080/actuator/metrics/jvm.gc.pause"
```

If the GC metric has not been created yet, check collection conditions and events before concluding. For thread state metrics, use the actual tag values returned by the endpoint; do not guess casing from the Java enum.

The `metrics` endpoint is for exploration and diagnostics, not a historical store or an endpoint meant for production scraping. Continuous monitoring requires an appropriate exporter and backend. See [Spring Boot 3.3: Metrics endpoint](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/metrics.html).

## 9. Java Practice: Checking Binders, Undefined Values, and a WAITING Thread

The example uses Java 17+ APIs, compiles targeting Java 17, and is verified on HotSpot JDK 21/G1. Spring Boot parent 3.3.13 manages Micrometer 1.13.15.

The goal is real observation without fabricating fixed heap/GC numbers. Default mode prints verifiable checks and thread lifecycle. `--values` mode prints measurements that vary across runs.

Do not create an infinite allocation loop, do not force GC, and do not try to trigger a deadlock or OutOfMemoryError.

### 9.2. Complete Program

File `src/main/java/demo/JvmSignalsDemo.java`:

```java
package demo;

import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.Timer;
import io.micrometer.core.instrument.binder.jvm.ClassLoaderMetrics;
import io.micrometer.core.instrument.binder.jvm.JvmGcMetrics;
import io.micrometer.core.instrument.binder.jvm.JvmMemoryMetrics;
import io.micrometer.core.instrument.binder.jvm.JvmThreadMetrics;
import io.micrometer.core.instrument.simple.SimpleMeterRegistry;

import java.util.Comparator;
import java.util.Locale;
import java.util.OptionalDouble;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.TimeUnit;

public class JvmSignalsDemo {
    public static void main(String[] args) throws Exception {
        if (args.length > 1
                || (args.length == 1 && !args[0].equals("--values"))) {
            throw new IllegalArgumentException("Use no argument or --values");
        }
        boolean values = args.length == 1;
        SimpleMeterRegistry registry = new SimpleMeterRegistry();
        JvmGcMetrics gc = new JvmGcMetrics();

        try {
            new JvmMemoryMetrics().bindTo(registry);
            new JvmThreadMetrics().bindTo(registry);
            new ClassLoaderMetrics().bindTo(registry);
            gc.bindTo(registry);

            System.out.println("heap.meters="
                    + !registry.find("jvm.memory.used").tag("area", "heap")
                    .gauges().isEmpty());
            System.out.println("nonheap.meters="
                    + !registry.find("jvm.memory.used").tag("area", "nonheap")
                    .gauges().isEmpty());
            System.out.println("threads.live.meter="
                    + (registry.find("jvm.threads.live").gauge() != null));
            System.out.println("classes.loaded.meter="
                    + (registry.find("jvm.classes.loaded").gauge() != null));
            System.out.println("classes.unloaded.meter="
                    + (registry.find("jvm.classes.unloaded").functionCounter() != null));
            System.out.println("gc.liveData.meter="
                    + (registry.find("jvm.gc.live.data.size").gauge() != null));

            System.out.println("ratio.demo.known=" + ratioText(512, 1024));
            System.out.println("ratio.demo.undefined=" + ratioText(512, -1));
            observeWorker(registry, values);
        } finally {
            gc.close();
            registry.close();
        }
    }

    private static void observeWorker(
            SimpleMeterRegistry registry, boolean values) throws Exception {
        CountDownLatch entered = new CountDownLatch(1);
        CountDownLatch release = new CountDownLatch(1);
        Thread worker = new Thread(() -> {
            entered.countDown();
            try {
                release.await();
            } catch (InterruptedException ex) {
                Thread.currentThread().interrupt();
            }
        }, "jvm-lab-worker");

        worker.start();
        try {
            if (!entered.await(2, TimeUnit.SECONDS)) {
                throw new IllegalStateException("Worker did not start");
            }
            long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(2);
            while (worker.getState() != Thread.State.WAITING
                    && System.nanoTime() < deadline) {
                Thread.sleep(1);
            }
            if (worker.getState() != Thread.State.WAITING) {
                throw new IllegalStateException("Worker did not enter WAITING");
            }

            System.out.println("worker.state=" + worker.getState());
            Gauge waiting = registry.find("jvm.threads.states")
                    .tag("state", "waiting").gauge();
            System.out.println("threads.waiting.observed="
                    + (waiting != null && waiting.value() >= 1));
            if (values) {
                printValues(registry);
            }
        } finally {
            release.countDown();
            worker.join(2000);
        }
        if (worker.isAlive()) {
            throw new IllegalStateException("Worker did not stop");
        }
        System.out.println("worker.state.after=" + worker.getState());
    }

    private static void printValues(SimpleMeterRegistry registry) {
        System.out.println("VALUES: numbers depend on this JVM and observation time");
        registry.find("jvm.memory.used").gauges().stream()
                .sorted(Comparator.comparing(g -> g.getId().toString()))
                .forEach(used -> {
                    String area = used.getId().getTag("area");
                    String id = used.getId().getTag("id");
                    Gauge committed = registry.find("jvm.memory.committed")
                            .tags("area", area, "id", id).gauge();
                    Gauge max = registry.find("jvm.memory.max")
                            .tags("area", area, "id", id).gauge();
                    double u = used.value();
                    double c = committed.value();
                    double m = max.value();
                    System.out.printf(Locale.ROOT,
                            "memory area=%s id=%s used=%.0f committed=%.0f max=%.0f ratio=%s%n",
                            area, id, u, c, m, ratioText(u, m));
                });

        System.out.printf(Locale.ROOT,
                "threads live=%.0f daemon=%.0f peak=%.0f%n",
                registry.get("jvm.threads.live").gauge().value(),
                registry.get("jvm.threads.daemon").gauge().value(),
                registry.get("jvm.threads.peak").gauge().value());
        System.out.printf(Locale.ROOT,
                "classes current=%.0f unloadedTotal=%.0f%n",
                registry.get("jvm.classes.loaded").gauge().value(),
                registry.get("jvm.classes.unloaded").functionCounter().count());

        System.out.println("gc.pause.series="
                + registry.find("jvm.gc.pause").timers().size());
        for (Timer pause : registry.find("jvm.gc.pause").timers()) {
            System.out.printf(Locale.ROOT,
                    "gc.pause tags=%s count=%d totalSeconds=%.6f maxSeconds=%.6f%n",
                    pause.getId().getTags(), pause.count(),
                    pause.totalTime(TimeUnit.SECONDS), pause.max(TimeUnit.SECONDS));
        }
    }

    private static String ratioText(double used, double max) {
        OptionalDouble ratio = usageRatio(used, max);
        return ratio.isPresent()
                ? String.format(Locale.ROOT, "%.1f%%", 100 * ratio.getAsDouble())
                : "unknown";
    }

    private static OptionalDouble usageRatio(double used, double max) {
        if (!Double.isFinite(used) || used < 0
                || !Double.isFinite(max) || max <= 0) {
            return OptionalDouble.empty();
        }
        return OptionalDouble.of(used / max);
    }
}
```

Important details:

1. Binders are attached manually because this is a standalone program without Spring Boot auto-configuration.
2. `JvmGcMetrics` is closed to release binder resources/listeners; the registry is also closed in `finally`.
3. The worker uses `new Thread`, so it is a platform thread. It awaits a latch to intentionally enter the WAITING state.
4. The latch is released and the worker is joined upon completion, even if the observation path fails.
5. Checking "at least one waiting thread" does not assume total JVM thread count is always a fixed constant.
6. The two ratio demo calculations use 512/1024 and 512/-1 to verify handling logic; they do not masquerade as measured heap figures.
7. Separate pool reads are not an atomic snapshot transaction across the entire JVM. Numbers can change while printing.

The program does not require the JVM to emit a GC pause during its very short runtime.

### 9.3. Compiling and Running Verification Mode

Select JDK 21 and run inside `jvm-signals-lab`. The first Maven run needs network access to fetch plugins/dependencies.

On PowerShell:

```powershell
mvn -q package dependency:build-classpath "-Dmdep.outputFile=classpath.txt"
$cp = "target/classes;" + (Get-Content -LiteralPath classpath.txt -Raw).Trim()
java -XX:+UseG1GC -Xms32m -Xmx128m -cp $cp demo.JvmSignalsDemo
```

On Linux/macOS, after the same Maven command:

```bash
cp="target/classes:$(cat classpath.txt)"
java -XX:+UseG1GC -Xms32m -Xmx128m -cp "$cp" demo.JvmSignalsDemo
```

G1 and the heap bounds here define the lab context, not a recommended flag set for every production application.

Stdout of default mode in the verified context:

```text
heap.meters=true
nonheap.meters=true
threads.live.meter=true
classes.loaded.meter=true
classes.unloaded.meter=true
gc.liveData.meter=true
ratio.demo.known=50.0%
ratio.demo.undefined=unknown
worker.state=WAITING
threads.waiting.observed=true
worker.state.after=TERMINATED
```

The `meter=true` lines only confirm that meters were registered and found. They do not mean every subsystem is "healthy" or that GC has already occurred.

`worker.state=WAITING` shows a thread intentionally waiting. `worker.state.after=TERMINATED` shows the thread was released and exited; the earlier WAITING state was not a deadlock.

### 9.4. Running Measurement Mode

On PowerShell, continue using the generated classpath:

```powershell
java -XX:+UseG1GC -Xms32m -Xmx128m -cp $cp demo.JvmSignalsDemo --values
```

On Linux/macOS, use `"$cp"` instead of `$cp` in the command above.

The numbers will vary by machine, JDK, process, and timing. Part of an actual output from one JDK 21/G1 run is:

```text
memory area=heap id=G1 Eden Space used=6291456 committed=16777216 max=-1 ratio=unknown
memory area=nonheap id=Metaspace used=2228064 committed=2424832 max=-1 ratio=unknown
gc.pause.series=0
```

Do not treat these values as fixed stdout that must match on every machine. They illustrate three points:

- A heap pool like Eden may not have its own defined max.
- Metaspace can report max=-1; ratio must be unknown.
- `gc.pause.series=0` at read time means the registry had no pause Timer series to print yet; it is not proof that GC is disabled or that the JVM has no heap.

The `threads live=...` and `classes current=...` lines in values mode are actual observed numbers. Do not try to assert that every JVM must have the same thread count or class count.

## 10. Reading Signals Together to Form Sound Hypotheses

| Observed Pattern | Hypothesis to Check | Additional Evidence to Gather |
| --- | --- | --- |
| Heap grows then drops cyclically, latency stable | Normal allocation/reclamation behavior | Load, allocation rate, post-GC baseline across multiple cycles |
| Post-GC memory baseline rises under comparable load | Retained data growing, cache growing, or reference leak | Object types, reference chains, cache bounds |
| Heap not full yet, but process/container RAM is high | Native memory, buffers, stacks, or other non-heap parts | Process/container memory, buffers, thread count, relevant native data |
| Long pauses coincide with higher latency | GC may be contributing to slowdown | GC timeline, request latency, and active collector |
| Many persistent BLOCKED threads, throughput drops | Monitor contention or a path holding a lock too long | Thread dump and lock-holding object/thread |
| Many WAITING threads, empty queue, system responsive | Idle workers may be normal | Worker stack traces and pool configuration |
| Live threads keep rising, not returning to baseline after load | Excessive thread creation or unclosed resources | Thread creation source, thread names, executors, and lifecycle |
| Loaded classes and Metaspace both rise after warmup | Heavy dynamic class generation or retained classloaders | Classloader stats and proxy/plugin/reload mechanisms |
| Peak threads high while current live is low | There was an earlier spike | Timing of load burst and live history, not peak alone |

The rows are hypotheses, not automated diagnoses. For instance, a "rising post-GC baseline" can also come from legitimately higher data load; "many waiting" can also result from resource starvation elsewhere. A causal chain must be established with evidence.

Do not sum data across multiple instances and conclude a specific JVM is out of heap. Preserve the ability to slice by instance, deployment version, collector, and lifecycle stage.

Likewise, do not compare a spike in this minute against an average load from another hour and treat it as a direct relationship. Metrics must be aligned on an appropriate timeline.

## 11. From Metrics to Diagnostic Tools

Metrics tell you **when** and **which group** warrants investigation. They do not contain detailed stacks for every thread or reference paths to individual objects.

On supported HotSpot/JDK builds, `jcmd` provides diagnostic commands. The following PowerShell example lets the operator choose the exact PID to inspect:

```powershell
jcmd -l
$targetJvmPid = Read-Host "Enter the PID of the JVM to inspect"
jcmd $targetJvmPid help
jcmd $targetJvmPid GC.heap_info
jcmd $targetJvmPid Thread.print
jcmd $targetJvmPid VM.classloader_stats
```

These commands target a **currently running** JVM, usually on the same machine and with appropriate user permissions. The console program above exits quickly, so do not assume its PID still exists after it finishes.

Supported commands and overhead can differ by JVM. `Thread.print` captures stack information and `VM.classloader_stats` captures classloader statistics; they do not fix the root cause by themselves. See [The jcmd Command, JDK 21](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html).

When detailed observation over time is needed, JFR can be used; when identifying retained objects is needed, a heap dump and reference analysis may be required. Those operations carry overhead and can contain application data, so choose the right timing, scope, and storage handling. Do not automatically take continuous heap dumps just because of a single high heap point.

This lesson focuses on reading metrics and choosing investigation directions, not on prescribing collector changes or tuning a set of production GC flags without evidence.

## 12. Common Interpretation Mistakes

- Treating unfiltered `jvm.memory.used` as "current heap."
- Summing every pool's max, including max=-1, to calculate a percentage.
- Treating committed as total physical RAM in use or treating `-Xmx` as the limit for the entire process.
- Treating all non-heap as Metaspace.
- Treating increased GC counts as conclusive proof of a leak.
- Treating the absence of `jvm.gc.pause` right after startup as proof that GC does not run.
- Treating RUNNABLE as using maximum CPU.
- Treating WAITING as deadlock or every BLOCKED thread as deadlock.
- Treating peak threads as current live threads.
- Treating platform thread counters as the count of all virtual threads on Java 21.
- Treating `jvm.classes.loaded` as total classes ever loaded over the entire lifetime.
- Treating rising class counts during startup as a classloader leak.
- Expecting heap, class, and thread numbers to stay identical across every run.
- Re-registering JVM binders in a Boot application without checking that auto-configuration already does so.

Good dashboard design makes memory region, unit, pool/instance, statistic type, and time explicit, rather than using vague labels like "memory" or "threads."

## 13. Self-Check

**Exercise 1:** A pool has used=64 MiB and max=-1. How should memory utilization percentage be calculated?

**Answer:** There is no valid maximum denominator for calculation. Display the absolute capacity and an unknown status for the ratio; do not divide by -1 or replace max with 0.

**Exercise 2:** Heap uses only half its limit, yet the container is nearly out of memory. Can a memory issue be ruled out?

**Answer:** No. Check off-heap regions, buffers/native memory, stacks, thread counts, and process/container memory data. Heap is only one part.

**Exercise 3:** Fifty workers are in WAITING, the queue is empty, and requests remain responsive. Can a deadlock be concluded?

**Answer:** No. Workers may be normally waiting for work. Stack traces and lock-wait relationships are needed to conclude contention or deadlock.

**Exercise 4:** `jvm.classes.loaded` increases after invoking a feature for the first time. What should be checked next?

**Answer:** Observe after warmup and under comparable load, correlating with Metaspace and class-loading/generation mechanisms. A single increase is not enough to prove a leak.

**Exercise 5:** Current live threads are 20, and peak is 200. Are there 200 live threads right now?

**Answer:** No. Peak reflects a previous high according to the management source's lifecycle/reset; the current live count is the live metric.

**Exercise 6:** The JVM just started; the GC data meter is registered, but there is no pause Timer yet. What does that tell you?

**Answer:** It only confirms the binder/meter exists in the corresponding scope. Check GC notifications and recorded samples; do not infer the presence or absence of all GC activity from a metric name that has not appeared yet.

Effective JVM monitoring connects memory regions, GC activity, threads, and class loading within the same load context. Metrics help form grounded hypotheses; concluding a root cause requires detailed evidence aligned with those hypotheses.
