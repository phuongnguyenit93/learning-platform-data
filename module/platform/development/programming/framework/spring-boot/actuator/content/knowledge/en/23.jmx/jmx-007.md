# Distinguishing Actuator Endpoints over JMX from Metrics Exported via the JMX Registry

## 1. Two Different Mechanisms Can Appear Together in JConsole

When opening JConsole's MBeans tab, learners may see both objects under the `org.springframework.boot` domain and many objects containing metric names under the `metrics` domain. Both are accessed via JMX, yet they are produced by two distinct mechanisms.

- **Actuator endpoints over JMX** provide a management interface: pick an endpoint and invoke an operation on that endpoint.
- **Metrics exported via the JMX registry** expose Micrometer measurements as MBeans so JMX tools can read them.

For instance, `Health` is an endpoint reporting application health. A counter tracking successful requests is a metric. That counter does not become a separate Actuator endpoint merely by being published into the same MBeanServer.

An even easier case to confuse is the **Metrics** endpoint. This endpoint lets callers query registered meters. It is still an endpoint, not `JmxMeterRegistry` itself. You can have the Metrics endpoint without exporting individual meters to JMX; conversely, you can export meters to JMX without exposing the Metrics endpoint over JMX.

This lesson uses Spring Boot 3.3.x. The example pins Spring Boot 3.3.0, Micrometer 1.13.0 via its dependency management, and JDK 21. Specific MBean names in the experiment were verified on this version set.

## 2. Looking Along the Managed-Object Creation Paths

### 2.1. The Actuator Endpoint Path

```text
Built-in endpoint or application @Endpoint
        ↓ enablement and JMX exposure conditions
Actuator's JMX endpoint export mechanism
        ↓
Endpoint MBean
        ↓
Tool invokes an endpoint operation
```

An endpoint can provide information or management operations. The MBean name is typically tied to the endpoint ID. Under default configuration, an example is:

```text
org.springframework.boot:type=Endpoint,name=Health
```

Spring's JMX support is enabled with `spring.jmx.enabled=true`; the endpoint domain can be changed with `management.endpoints.jmx.domain`. [JMX in Spring Boot 3.3](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html).

### 2.2. The Micrometer Metrics Path

```text
Application / instrumentation component
        ↓ records Counter, Gauge, Timer...
Micrometer MeterRegistry
        ↓ with JmxMeterRegistry
Name mapping and JMX metric export
        ↓
Metric MBean
        ↓
Tool reads the metric's attributes
```

Spring Boot can auto-configure a registry when its implementation is on the classpath. To export metrics to JMX, add `io.micrometer:micrometer-registry-jmx`. The default metrics domain is `metrics` and has its own configuration. [Metrics and the JMX backend in Spring Boot 3.3](https://docs.spring.io/spring-boot/3.3/reference/actuator/metrics.html).

In a simple setup, both paths share the JVM's MBeanServer. Sharing the registration hub and protocol does not give them shared enablement conditions, naming rules, or usage interfaces.

### 2.3. Three Different Meanings of “Registry”

| Term | Meaning |
| --- | --- |
| `MeterRegistry` / `JmxMeterRegistry` | Micrometer component managing or exporting meters |
| `MBeanServer` | Place where MBeans are registered and accessed |
| RMI registry in remote JMX connections | Component helping clients locate the remote connector |

Adding `micrometer-registry-jmx` does not mean opening an RMI port for remote machines to connect. Conversely, an active remote connector does not automatically create meters that have not been registered.

## 3. Comparing by the Contract Tools Use

| Aspect | Actuator Endpoint over JMX | Metrics via JMX Registry |
| --- | --- | --- |
| Source object | Endpoint, such as Health, Metrics, or a custom endpoint | Meter, such as Counter or Gauge |
| Purpose | Query or control a management capability | Observe measurements |
| Publishing component | Actuator JMX endpoint exporter | `JmxMeterRegistry` and its JMX integration |
| Primary identifier | Endpoint ID and MBean ObjectName | Meter ID consisting of name and tags, then mapped to a JMX name |
| Default domain considered | `org.springframework.boot` | `metrics` |
| Domain property | `management.endpoints.jmx.domain` | `management.jmx.metrics.export.domain` |
| Typical access pattern | Invoke an operation | Read attributes of the metric MBean |
| Exposure scope | Endpoints allowed over JMX | Meters exported by the registry |
| Is every meter an endpoint? | No | No |
| Automatically persists metric history? | Not merely by exposing endpoints | Not merely by exporting MBeans |

“Typical” does not replace metadata. When working with a specific MBean, inspect `MBeanInfo` to see which attributes or operations it actually has.

An endpoint MBean with an empty Attributes section can still work via Operations. A metric MBean with `Count` or `Value` attributes does not mean it exposes operations of Health, Loggers, or custom endpoints.

## 4. Which Configuration Controls Which Path?

### 4.1. Switches to Distinguish

| Property or Dependency | Primary Effect |
| --- | --- |
| `spring.jmx.enabled=true` | Enables Spring-managed JMX support, required for the endpoint path in the sample |
| `management.endpoints.jmx.exposure.include` | Selects endpoints exposed over JMX |
| `management.endpoints.jmx.exposure.exclude` | Excludes endpoints from JMX exposure |
| `management.endpoints.jmx.domain` | Changes the endpoint domain |
| `micrometer-registry-jmx` | Provides the registry implementation exporting meters to JMX |
| `management.jmx.metrics.export.enabled` | Enables/disables JMX metrics export when configuration conditions are met |
| `management.jmx.metrics.export.domain` | Changes the domain of metrics exported over JMX |

The `management.jmx.metrics.export.*` properties belong to the metrics backend group; do not use property names from older Boot versions without checking the current version. Spring Boot 3.3 defines dedicated domain and enabled properties for this backend. [Spring Boot 3.3 JMX metrics properties](https://docs.spring.io/spring-boot/3.3/appendix/application-properties/index.html).

Setting `enabled=true` does not conjure up a library missing from the classpath. An application lacking `micrometer-registry-jmx` will not export meters as MBeans just because that property is set.

Similarly, adding `metrics` to the JMX endpoint list requests exposing the endpoint whose ID is `metrics`. It is not syntax for selecting all meters and does not replace JMX metrics export configuration.

### 4.2. Do Not Use One Switch to Draw Conclusions About the Entire JVM

`spring.jmx.enabled=false` does not mean every MBean from every library in the JVM disappears. In the experiment below, the JMX meter path still exists when Spring's JMX support is turned off.

Conversely, `management.jmx.metrics.export.enabled=false` disables the JMX metrics backend, yet JMX endpoints can still work. Meters may also still be held in another registry; do not conclude the application stopped recording metrics.

The HTTP exposure list is also separate from the JMX list. Seeing a metric on an HTTP endpoint, if the application has HTTP, does not prove that meter has been exported as an MBean.

## 5. Complete Example with Both Paths

### 5.1. Experiment Goals

The application uses no HTTP server. It exposes three JMX endpoints:

- `Health`: built-in endpoint.
- `Metrics`: endpoint for querying measurements.
- `Catalog`: sample endpoint returning an identifying string.

`src/main/java/example/jmxmetrics/TwoJmxPipelinesApplication.java`:

```java
package example.jmxmetrics;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.actuate.endpoint.annotation.Endpoint;
import org.springframework.boot.actuate.endpoint.annotation.ReadOperation;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication(proxyBeanMethods = false)
public class TwoJmxPipelinesApplication {
    public static void main(String[] args) throws InterruptedException {
        SpringApplication.run(TwoJmxPipelinesApplication.class, args);
        System.out.println("TARGET_PID=" + ProcessHandle.current().pid());
        new CountDownLatch(1).await();
    }

    @Bean
    AtomicInteger queueDepth() {
        return new AtomicInteger(7);
    }

    @Bean
    ApplicationRunner sampleMeters(MeterRegistry registry, AtomicInteger queueDepth) {
        return args -> {
            Counter.builder("lesson.requests").tag("result", "ok")
                    .register(registry).increment(3);
            Counter.builder("lesson.requests").tag("result", "error")
                    .register(registry).increment();
            Gauge.builder("lesson.queue.depth", queueDepth, AtomicInteger::doubleValue)
                    .register(registry);
        };
    }

    @Bean
    CatalogEndpoint catalogEndpoint() {
        return new CatalogEndpoint();
    }

    @Endpoint(id = "catalog")
    public static class CatalogEndpoint {
        @ReadOperation
        public String status() {
            return "catalog=ready";
        }
    }
}
```

`ApplicationRunner` registers and increments the counters after the context is initialized. It does not generate real network requests; the values 3 and 1 are fixed experiment data.

`AtomicInteger` is kept as a bean so the object observed by the gauge has a clear lifecycle. A gauge reads a current value; a counter accumulates event counts. Do not interpret gauge 7 as “seven total events occurred.” [Counter](https://docs.micrometer.io/micrometer/reference/concepts/counters.html), [Gauge](https://docs.micrometer.io/micrometer/reference/concepts/gauges.html).

`CountDownLatch` keeps the sample process alive so JConsole can attach. It is not a mandatory part of metrics export.

  type=meters,name=lessonRequests.result.ok

The tool may lay out the tree differently, yet ObjectName and metadata are the contract to check. Besides the three sample meters, there may be many system meters registered by Spring Boot; do not take the total MBean count of the entire JVM as the experiment's figure.

On the `Catalog` endpoint, open **Operations** and invoke `status`:

```text

```

```text

```

On `lessonQueueDepth`, read `Value`:

```text
7.0
```

The last two actions read meter attributes, rather than invoking operations on the Catalog or Metrics endpoint.

### 5.4. Why Does a Counter Appear Under type=meters?

In the sample's version set, the registry's JMX integration represents counters via MBeans with `type=meters`. Beyond `Count`, metadata may also expose rate information as supported by that backend.

Do not assume the ObjectName must have `type=counters` merely from Micrometer's `Counter` interface name. Nor should `Count=3` be interpreted as “three requests per second”: count and rate are two different quantities.

The MBean names above are observed results under the sample's default configuration. When a custom naming convention or name mapper is present, look up the actual registered names again.

## 6. Comparing the Metrics Endpoint with JMX Meters in Java

### 6.1. One Side Invokes Operations, the Other Reads Attributes

Create `src/main/java/example/jmxmetrics/CompareJmx.java`:

```java
package example.jmxmetrics;

import java.util.List;
import java.util.Map;
import javax.management.ObjectName;

import org.springframework.boot.SpringApplication;

public class CompareJmx {
    public static void main(String[] args) throws Exception {
        try (var context = SpringApplication.run(TwoJmxPipelinesApplication.class,
                "--logging.level.root=ERROR", "--spring.main.banner-mode=off")) {
            var server = java.lang.management.ManagementFactory.getPlatformMBeanServer();
            var catalog = new ObjectName(
                    "org.springframework.boot:type=Endpoint,name=Catalog");
            var metricsEndpoint = new ObjectName(
                    "org.springframework.boot:type=Endpoint,name=Metrics");
            var counter = new ObjectName(
                    "metrics:type=meters,name=lessonRequests.result.ok");
            var gauge = new ObjectName(
                    "metrics:type=gauges,name=lessonQueueDepth");

            Object status = server.invoke(catalog, "status", new Object[0], new String[0]);
            System.out.println("Catalog.status=" + status);
            Map<?, ?> response = (Map<?, ?>) server.invoke(metricsEndpoint, "metric",
                    new Object[] { "lesson.requests", null },
                    new String[] { "java.lang.String", "java.util.List" });
            System.out.println("Metrics.metric COUNT=" + count(response));
            Map<?, ?> filtered = (Map<?, ?>) server.invoke(metricsEndpoint, "metric",
                    new Object[] { "lesson.requests", java.util.List.of("result:ok") },
                    new String[] { "java.lang.String", "java.util.List" });
            System.out.println("Metrics.metric COUNT[result=ok]=" + count(filtered));
            System.out.println("JMX meter Count[result=ok]=" + server.getAttribute(counter, "Count"));
            System.out.println("JMX meter Value[queueDepth]=" + server.getAttribute(gauge, "Value"));
        }
    }

    private static double count(Map<?, ?> response) {
        for (Object item : (List<?>) response.get("measurements")) {
            Map<?, ?> sample = (Map<?, ?>) item;
            if ("COUNT".equals(String.valueOf(sample.get("statistic")))) {
                return ((Number) sample.get("value")).doubleValue();
            }
        }
        throw new IllegalStateException("COUNT measurement not found");
    }
}
```

The program starts an application context to practice inside that same process, reads the JVM's MBeanServer, and closes the context when done. It does not attach to an application running in another terminal. The `CountDownLatch` in the application's main method does not run when this program calls `SpringApplication.run` directly.

`invoke` is for operations and `getAttribute` is for attributes; the two methods on the JMX interface serve two different kinds of members. [The MBeanServerConnection API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanServerConnection.html).

In PowerShell on Windows:

```powershell
mvn clean package
mvn dependency:build-classpath "-Dmdep.outputFile=classpath.txt"
$lessonClassPath = "target/classes;" + (Get-Content -Raw classpath.txt).Trim()
java -cp $lessonClassPath example.jmxmetrics.CompareJmx
```

Maven builds a classpath containing Spring/Micrometer dependencies. `;` is the classpath separator on Windows; on other operating systems, use the appropriate separator. Do not run a standalone `javac CompareJmx.java` command and expect all required libraries to be present.

Sample stdout:

```text
Catalog.status=catalog=ready
Metrics.metric COUNT=4.0
Metrics.metric COUNT[result=ok]=3.0
JMX meter Count[result=ok]=3
JMX meter Value[queueDepth]=7.0
```

### 6.2. Explaining Each Result

- `Catalog.status`: operation of a custom endpoint.
- `Metrics.metric COUNT=4.0`: the `metric` operation on the Metrics endpoint, reading base meter `lesson.requests` and aggregating across both tag values.
- `COUNT[result=ok]=3.0`: calls the same operation, filtered by `result:ok`.
- `JMX meter Count[result=ok]=3`: reads the attribute on the MBean exported specifically for the meter with that tag.
- `Value[queueDepth]=7.0`: reads the gauge's attribute.

4 and 3 do not contradict each other: one is unfiltered across tags, while the other selects `result=ok`. When selecting the same label, both values in the experiment represent three events, even though numeric types and rendering differ.

The verified JMX signature for `Metrics.metric` in the sample is:

```text
metric(java.lang.String, java.util.List) -> java.util.Map
```

A GUI tool may not support entering every complex parameter type. Do not take difficulty entering a `List` in JConsole as proof that the endpoint does not exist. You can inspect metadata or use a JMX client capable of constructing the right parameters like the Java program above.

### 6.3. The Metrics Endpoint Does Not Become a JMX Registry

The Metrics endpoint queries meters from the application's instrumentation system. The JMX registry publishes meters through its own representation. They may read the same underlying measurements, yet they expose different interfaces:

```text
A Micrometer meter
    ├── queried via the Metrics endpoint
    └── exported as a metric MBean by the JMX registry
```

Do not use the number of endpoints in the management domain to infer the number of meters. Nor should you take the presence of a meter MBean to infer that an endpoint with an ID matching the meter name was created.

Stop the application before each run and start a fresh process. Do not combine flags from multiple experiments if you want to compare against the table below cleanly.

| Configuration Change vs. Sample | Sample Endpoint MBeans | Three Sample Metric MBeans |
| --- | --- | --- |
| Keep original configuration | Present: Health, Metrics, Catalog | Present |
| `spring.jmx.enabled=false` | Absent | Present |
| `management.jmx.metrics.export.enabled=false` | Still present | Absent |

| Change only endpoint domain | Move to new domain | Do not follow domain change |
| Change only metrics export domain | Do not follow domain change | Move to new domain |

The table describes the sample application, auto-configured registry, and default MBeanServer. If an application creates its own custom exporter or registry, inspect that configuration code as well.

### 7.1. Disabling Spring-Managed JMX

```shell
java -jar target/two-jmx-pipelines-1.0.0.jar --spring.jmx.enabled=false
```

After reconnecting to the right PID, the three endpoints do not appear in the endpoint domain. The three sample meters are still published by the JMX registry.

This result shows the boundary of `spring.jmx.enabled`. It is not a command that removes every MBean created by every library in the JVM.

### 7.2. Disabling the JMX Metrics Backend

```shell
java -jar target/two-jmx-pipelines-1.0.0.jar --management.jmx.metrics.export.enabled=false
```

The three JMX endpoints are still present. The three sample meter MBeans are no longer exported by this backend. In the sample configuration, instrumentation still has an in-memory registry recording the counters; disabling one backend does not mean disabling all of Micrometer.

Do not run the comparison program unchanged and expect to read the meter ObjectNames after export has been disabled. An MBean-not-found error in that situation matches the configuration.

### 7.3. Excluding Endpoints from JMX Exposure

```shell
java -jar target/two-jmx-pipelines-1.0.0.jar "--management.endpoints.jmx.exposure.exclude=*"
```

JMX endpoints are excluded from exposure; meters still appear. The `*` in this property refers to endpoints, not a request to remove registry meters.

In an application with no other protocol exposing endpoints, some auto-configured endpoint beans may also not be created because they are unavailable. Even then, that does not mean the application's counters and gauges vanish.

### 7.4. Changing Domains Independently

Endpoint domain:

```properties
management.endpoints.jmx.domain=lesson.endpoints
```

Metrics domain:

```properties
management.jmx.metrics.export.domain=lesson.meters
```

With both settings above, an endpoint name is:

```text
lesson.endpoints:type=Endpoint,name=Catalog
```

A meter name is:

```text
lesson.meters:type=meters,name=lessonRequests.result.ok
```

These are two separate namespaces. Changing the domain only changes where managed objects are looked up; it does not change the logical name `lesson.requests` used when calling the Metrics endpoint.

## 8. Meter Names, Tags, and Measurements Must Not Be Conflated

### 8.1. Logical Names Differ from Mapped Names

In the sample:

```text
Meter ID:
    name = lesson.requests
    tag  = result:ok

JMX-mapped name:
    lessonRequests.result.ok
```

The JMX registry uses hierarchical mapping for meters with tag dimensions. Naming conventions and `HierarchicalNameMapper` can affect exported names; do not build JMX names via arbitrary string concatenation for every application. [Micrometer JMX Name Mapping](https://docs.micrometer.io/micrometer/reference/implementations/jmx.html).

When querying the Metrics endpoint, use the logical name `lesson.requests` and tag parameters. When reading a meter MBean, use the registered ObjectName. Passing `lessonRequests.result.ok` as the endpoint's logical name may fail to find the meter.

### 8.2. One Logical Name Can Represent Multiple Meters with Different Tags

The two counters in the sample share a name but have two different tag sets. They are two separate meters.

When comparing numbers between the endpoint and exported MBeans, verify:

1. Is the logical name right?
2. Is the tag set identical?
3. Are you reading count, rate, instantaneous value, or another statistic?
4. Are the units the same?
5. Were the two readings taken at the same time and from the same process?

A gauge's instantaneous value does not substitute for a counter's event total. For timers or distributions, check both statistic name and unit before comparing.

### 8.3. Tag Cardinality Affects Meter Count

Using a tag with very many distinct values can cause the number of meters and MBeans to grow sharply. User IDs, request IDs, or unbounded strings are usually unsuitable to pass raw into a metric dimension meant for aggregation.

For example, `result=ok/error` is a small, statistically meaningful set. Replacing it with a random ID per request leaves operators with far more than two stable counters to observe.

This is an instrumentation design cost, not a reason to increase management endpoints. Review tag value cardinality before sending measurements to any backend.

## 9. Things the Two Mechanisms Do Not Do for Each Other

### 9.1. A Custom Endpoint Does Not Automatically Create a Meter

An operation returning `"catalog=ready"` does not automatically produce a corresponding Counter or Gauge. If you want to count invocation frequency, record measurements through the appropriate Micrometer mechanism.

Conversely, registering `Counter.builder("lesson.requests")` does not create an `@Endpoint`. It creates or looks up a meter by its registered ID.

### 9.2. Exporting Meters to JMX Is Not Importing Data from Every MBean

`micrometer-registry-jmx` serves to export Micrometer measurements out to JMX. It is not a prerequisite for every case where Micrometer reads data originating from MBeans.

An instrumentation component can read JVM or management data and record it into a MeterRegistry, then export it to another backend. Collection direction and export direction must be kept distinct; do not add a JMX export registry merely because the data source mentions JMX.

### 9.3. Standard JVM MBeans Are Also a Separate Group

Objects such as `java.lang:type=Memory` belong to the JVM's standard management layer. They are neither a Spring Boot Health endpoint nor an MBean created by the JMX registry for a meter with a similar meaning.

Memory can be observed through multiple paths. Before concluding data is duplicated or wrong, identify each path's source, sampling time, unit, and aggregation method.

### 9.4. Exposing Data Does Not Automatically Create Historical Storage

JMX is an interface for management and data access. Having MBeans does not automatically create a time-series database, persist history across restarts, or aggregate multiple application replicas.

A counter in a freshly started JVM has a different lifecycle from a counter in a long-running JVM. Graphing tools also need to account for rate of change and instance scope rather than merely comparing absolute totals.

## 10. Diagnosing the Right Branch and Permissions

| Symptom | What to Check |
| --- | --- |
| Health present yet no meters under metrics domain | JMX registry dependency, export flag, registered meters, and domain |
| Meters present yet no Actuator endpoints | `spring.jmx.enabled`, endpoint conditions, and JMX exposure list |
| Metrics MBean present yet individual meters missing | Do not confuse the Metrics endpoint with the JMX export backend |
| Removed `metrics` from endpoint list yet meters remain | This can be expected behavior; the two branches are independent |
| Disabled JMX export yet Metrics endpoint still reads measurements | Measurements remain in another registry or in-memory registry |
| Comparison shows 4 on endpoint and 3 on MBean | Check tags and aggregation first |
| Meter name differs from expectation | Naming convention, hierarchical mapping, and custom configuration |
| Gauge no longer has expected value | Observed target object, reference lifecycle, and read timing |
| MBean count grows continuously | Tag cardinality, dynamic meter names, and registration lifecycle |
| Tool shows only one group | Right JVM, right MBeanServer, and each group's domain |
| Can read attributes yet invoking endpoint operation is denied | Attribute read permission may differ from operation invoke permission |

With the JDK's default JMX agent, `readonly` and `readwrite` permissions have different scopes; successfully reading a metric attribute does not prove permission to invoke an endpoint operation. Do not raise administrative privileges merely because you categorized every object visible in JConsole as “metrics”. [JMX agent access permissions](https://docs.oracle.com/en/java/javase/21/management/monitoring-and-management-using-jmx-technology.html).

Remote connections, authentication, and TLS form the JMX access layer. Spring's domain or include settings do not replace that protection layer, and HTTP security rules do not automatically apply to a JMX connector.

## 11. Self-Check Practice

Perform on the sample project:

1. Identify the three endpoints and three sample meters in JConsole.
2. Point out where Operations are used and where Attributes are used.
3. Run the comparison program and explain why total count is 4 while `result=ok` is 3.
4. Turn off Spring JMX, JMX metrics export, and JMX endpoint exposure one at a time. Start a fresh process for each case.
5. Change each domain separately and compare which branch moves.
6. Explain why other system meters can make the total MBean count larger than the sample table.

Comprehension check questions:

- **Does seeing the metrics domain mean the Metrics endpoint has been exposed over JMX?** Not yet. The endpoint MBean must be checked separately.
- **Does adding micrometer-registry-jmx create a new endpoint for each meter?** No. It provides a metrics export backend.
- **Does disabling spring.jmx.enabled guarantee no MBeans remain at all?** No. It is not a JVM-wide switch.
