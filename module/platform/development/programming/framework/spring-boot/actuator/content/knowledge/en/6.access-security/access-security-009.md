# Restricting Health and Prometheus Access by Infrastructure Needs

## 1. Starting from Consumers of Operational Signals

Actuator provides signals that help infrastructure make decisions. However, different consumers do not need the same set of information:

- Kubernetes probes need to know whether the process is alive and ready to accept requests.
- Load balancers need a small signal to decide whether to route requests to this application instance.
- Prometheus needs to read metrics periodically to store time series and power alerting.
- Operators may need to read aggregate status when investigating incidents.

**Restricting access** means clearly defining who can connect, which endpoints can be called, by which methods, and how much information is returned. The goal is to supply enough signals for operations while avoiding expanding privileges beyond need.

Examples throughout this article use Java 21 and Spring Boot 3.3.13. Runnable code uses Spring MVC/Servlet to illustrate a concrete policy. For WebFlux, keep the same permission matrix while using the corresponding Reactive API stack; do not mix the two types of security chains.

## 2. Health and Prometheus Answer Different Questions

### 2.1. Health: A Decision at Check Time

`/actuator/health` represents aggregate health. The `liveness` and `readiness` groups focus on two separate decisions:

| Signal | Question | Typical infrastructure action |
| --- | --- | --- |
| Liveness | Has the process entered a state needing a restart? | Restart the container when checks fail past threshold |
| Readiness | Is this application instance ready to accept requests? | Stop routing traffic to the unready instance |
| Startup | Has the application completed its startup phase? | Delay liveness/readiness checks until startup succeeds |

Do not use a single aggregate check for every decision. For example, a shared database going down does not necessarily mean restarting the entire application will fix the failure. Conversely, an instance temporarily refusing traffic for maintenance may still be alive normally.

Probe behaviors are described in [Kubernetes: Liveness, Readiness, and Startup Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/). Default probe groups and external dependency selection must be designed per application, not inferred solely from endpoint names.

### 2.2. Prometheus: Data for Observation Over Time

`/actuator/prometheus` returns metrics in a format Prometheus can scrape. This is typically a **pull (scrape)** process: Prometheus sends GET requests to the application periodically.

This endpoint differs from `/actuator/metrics`. The metrics endpoint is for querying metrics via Actuator's API; Prometheus uses a dedicated export endpoint. Having the Prometheus endpoint requires both the corresponding registry library and HTTP exposure configuration.

Metrics can contain service names, path structures, business tags, or load and resource usage information. Do not put tokens, email addresses, request payloads, or personal data into metric tags and expect security configuration to mask everything.

A single successful scrape does not prove the application is ready to serve business traffic. The `up` metric generated by Prometheus reflects scrape outcome on Prometheus's side; do not equate it with Spring Boot's readiness state.

See [Spring Boot 3.3: Metrics — Prometheus](https://docs.spring.io/spring-boot/3.3/reference/actuator/metrics.html#actuator.metrics.export.prometheus).

## 3. Designing Permissions Across Three Layers

A request should succeed only when it satisfies all three layers:

```text
Network path reaches the server
            |
Endpoint is enabled and exposed over HTTP
            |
Application policy permits the caller to make the request
            |
Receive response with appropriate level of detail
```

### 3.1. Network Reachability

Firewalls, network policies, Services, reverse proxies, and Ingress decide which sources can reach the management port.

A path configured with `permitAll()` cannot distinguish kubelet from an Internet user on its own. If both can reach the same path, both can call it. When probes need no password, infrastructure itself must ensure that path only appears where intentionally allowed.

Do not use `User-Agent: kube-probe` as a trusted identity: anyone can set that header. Do not blindly trust externally supplied `X-Forwarded-For` to grant access. If relying on source addresses, verify the trusted proxy chain, header rewriting, and the actual source address seen by the application.

### 3.2. Enabling and Exposing Endpoints

In Boot 3.3, `management.endpoints.web.exposure.include` is the list of endpoints exposed over HTTP. It is not a list of who is allowed to access them.

Setting `include: health,prometheus` does not mean both endpoints are public. Conversely, declaring a `permitAll()` rule does not create an endpoint that is unexposed or missing a dependency.

### 3.3. Authentication, Authorization, and Data Volume

Authentication answers who the caller is; authorization decides which resources that caller may read. An account dedicated to scraping metrics does not need general administrative privileges.

Hiding health details is an independent decision from permitting endpoint calls. A minimal response can contain only:

```json
{"status":"UP"}
```

Even a minimal response reveals service availability. Expose it only for the chosen probe paths.

## 4. Building an Access Matrix Before Writing Configuration

The example uses three caller groups:

- **Internal probes:** carry no credentials; read only the two minimal probe paths.
- **scraper:** machine account with authority `METRICS_SCRAPE`; reads only Prometheus data.
- **operator:** human operator account with role `OPS`; reads aggregate health, without implicitly having scrape permission.

Application-layer matrix:
    
| GET to resource | Unauthenticated | scraper | operator |
| --- | --- | --- | --- |
| `/actuator/health/liveness` | Permit | Permit | Permit |
| `/actuator/health/readiness` | Permit | Permit | Permit |
| `/actuator/health` | 401 | 403 | Permit |
| `/actuator/prometheus` | 401 | Permit | 403 |
| `/actuator` — discovery links | 401 | 403 | 403 |
| Other endpoints exposed later | No access granted | No access granted | No access granted |

Passwords in the two account columns are assumed valid. When intentionally needing operator to also read metrics, grant that authority explicitly and update tests; do not assume `OPS` implies every permission.

The network matrix adds an important condition: **Internet users must not reach Actuator paths through the public entrypoint**, including the two probe paths permitted at the application layer. This requires separate infrastructure configuration; the Java code below does not create network policies or Ingress rules.

```yaml

  port: 8080

management:
  endpoints:
    web:

        include: health,prometheus
  endpoint:
    health:

demo:

  ops-password: ${OPS_PASSWORD}
```

`probes.enabled: true` enables both probe groups even when running on a personal machine. In Kubernetes, Boot can detect the environment and configure probes; enabling explicitly keeps the lab independent of that detection process.

`show-details: never` and `show-components: never` keep health responses minimal for all callers in the sample. If operators need details, design a `when-authorized` policy and a role allowed to see details; separately test anonymous responses and each health group. Permitting endpoint access does not solve detail visibility.

The two `demo.*` properties take passwords from environment variables. The sample provides no default passwords in application config. Test values will be passed separately in the test classes.

### 5.5. src/main/java/example/AccessPolicy.java

```java
package example;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest;
import org.springframework.boot.actuate.health.HealthEndpoint;
import org.springframework.boot.actuate.metrics.export.prometheus.PrometheusScrapeEndpoint;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

import static org.springframework.security.config.Customizer.withDefaults;

@Configuration(proxyBeanMethods = false)
public class AccessPolicy {
    @Bean
    @Order(1)
    SecurityFilterChain actuator(HttpSecurity http) throws Exception {
        http.securityMatcher(EndpointRequest.toAnyEndpoint());
        http.authorizeHttpRequests(rules -> rules
                .requestMatchers(HttpMethod.GET,
                        "/actuator/health/liveness",
                        "/actuator/health/readiness").permitAll()
                .requestMatchers(EndpointRequest.to(PrometheusScrapeEndpoint.class))
                        .hasAuthority("METRICS_SCRAPE")
                .requestMatchers(EndpointRequest.to(HealthEndpoint.class))
                        .hasRole("OPS")
                .anyRequest().denyAll());
        http.httpBasic(withDefaults());
        return http.build();
    }

    @Bean
    @Order(2)
    SecurityFilterChain remainingRequests(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(rules -> rules.anyRequest().denyAll());
        http.httpBasic(withDefaults());
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    @Bean
    UserDetailsService users(
            PasswordEncoder encoder,
            @Value("${demo.scrape-password}") String scrapePassword,
            @Value("${demo.ops-password}") String opsPassword) {
        var scraper = User.withUsername("scraper")
                .password(encoder.encode(scrapePassword))
                .authorities("METRICS_SCRAPE")
                .build();
        var operator = User.withUsername("operator")
                .password(encoder.encode(opsPassword))
                .roles("OPS")
                .build();
        return new InMemoryUserDetailsManager(scraper, operator);
    }
}
```

Key decisions in this configuration:

1. The `@Order(1)` chain only claims Actuator endpoints. The two specific GET rules sit before the broad HealthEndpoint rule.
2. Only the two exact probe URLs are permitted anonymously. Do not use `"/actuator/health/**"` permitting everything, because other health groups or paths may be added later.
3. The Prometheus endpoint requires a dedicated authority. `hasAuthority("METRICS_SCRAPE")` checks that exact string without adding a role prefix.
4. Aggregate health and subpaths not made public require the OPS role. `roles("OPS")` creates authority `ROLE_OPS`, matching `hasRole("OPS")`.
5. The final `denyAll()` rule prevents accidentally granting access if someone adds another endpoint to the exposure list.
6. The `@Order(2)` chain covers the rest. Do not let paths outside the Actuator matcher fall into a zone with no security policy.

`EndpointRequest.toAnyEndpoint()` also includes the links endpoint at the Actuator root path. It does not mean every URL starting with `/actuator` is necessarily an existing endpoint. See [Boot 3.3 Servlet EndpointRequest](https://docs.spring.io/spring-boot/3.3/api/java/org/springframework/boot/actuate/autoconfigure/security/servlet/EndpointRequest.html).

Passwords are hashed with PasswordEncoder when creating sample users. The in-memory user store serves to illustrate policies, not to represent every organization's identity management system. Basic only Base64-encodes credentials; HTTPS or an appropriate secure transport channel is needed outside local personal-machine practice.

CSRF is kept intact. Probe and scrape jobs only use GET, so disabling CSRF is unnecessary. Opening other state-changing operations is a separate decision.

**Path limitation:** the two probe matchers hardcode default URLs. If you change base-path, path-mapping, or add probe paths on the main port, you must update the matchers accordingly and re-run tests. The endpoint-based matchers for health/Prometheus do not automatically alter these two literal URL strings.

## 6. Run and Observe on a Personal Machine

In the directory containing `pom.xml`, set the two test passwords in the terminal running the application.

Bash:

```bash
export SCRAPE_PASSWORD='lab-scrape-pass'
export OPS_PASSWORD='lab-ops-pass'
mvn spring-boot:run
```

PowerShell:

```powershell
$env:SCRAPE_PASSWORD = 'lab-scrape-pass'
$env:OPS_PASSWORD = 'lab-ops-pass'
mvn spring-boot:run
```

These are public values solely for local personal-machine practice. In real deployments, provision secrets via a secret manager and the system's password rotation workflow; do not put real passwords in repositories or commands saved in shell history.

You can package and run with Java instead of `spring-boot:run`:

```bash
mvn package
java -jar target/actuator-infrastructure-access-1.0.0.jar
```

Keep both environment variables in the terminal running the JAR. Because there are Spring dependencies, use Maven to compile and build the classpath; do not merely run `javac` on one file expecting dependencies to download automatically.

### 6.1. Reading Probes

Once the application has started and is ready:

```bash
curl -s http://localhost:8080/actuator/health/liveness
curl -s http://localhost:8080/actuator/health/readiness
```

Body of each response in normal state:

```json
{"status":"UP"}
```

This is HTTP content, not logs from the main method. Curl does not automatically insert blank lines between responses. When readiness transitions to refusing traffic, that group's default response is 503 with status `OUT_OF_SERVICE`; tests in section 7 illustrate this.

### 6.2. Verifying Permissions

The commands below use Bash; in PowerShell use `curl.exe` and replace `/dev/null` with `NUL`. They use the test passwords above:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/actuator/prometheus
curl -s -o /dev/null -w "%{http_code}\n" -u operator:lab-ops-pass http://localhost:8080/actuator/prometheus
curl -s -o /dev/null -w "%{http_code}\n" -u scraper:lab-scrape-pass http://localhost:8080/actuator/prometheus
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/actuator/health
curl -s -o /dev/null -w "%{http_code}\n" -u scraper:lab-scrape-pass http://localhost:8080/actuator/health
curl -s -o /dev/null -w "%{http_code}\n" -u operator:lab-ops-pass http://localhost:8080/actuator/health
```

Results in order:

```text
401
403
200
401
403
200
```

401 in these commands indicates missing valid authentication; 403 with a valid account indicates lacking the corresponding permission. Do not generalize every 403 as a missing role: CSRF and upstream layers can also reject a request.

Reading scrape output:

```bash
curl -s -u scraper:lab-scrape-pass -H "Accept: text/plain;version=0.0.4" http://localhost:8080/actuator/prometheus
```

The response contains Prometheus export data, including `# HELP` lines, `# TYPE` lines, and metric values. Do not hardcode the entire stdout because metric names, values, order, and set depend on environment and timing.

## 7. Testing Policy and Readiness Behavior

The following test suite uses the full Spring Boot context with MockMvc. Basic credentials pass through real security filters instead of replacing the caller with a pre-authenticated identity. No HTTP port is opened.

`@AutoConfigureObservability` enables the observability configuration required in this test so the registry and Prometheus endpoint are present; if the registry is accidentally disabled in the test environment, results no longer test the intended scrape path.

### 7.1. src/test/java/example/AccessPolicyTest.java

```java
package example;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.availability.AvailabilityChangeEvent;
import org.springframework.boot.availability.ReadinessState;
import org.springframework.boot.test.autoconfigure.actuate.observability.AutoConfigureObservability;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.ApplicationContext;
import org.springframework.test.web.servlet.MockMvc;

import static org.hamcrest.Matchers.containsString;
import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.httpBasic;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest(properties = {
        "demo.scrape-password=test-scrape-pass",
        "demo.ops-password=test-ops-pass"
})
@AutoConfigureMockMvc
@AutoConfigureObservability
class AccessPolicyTest {
    @Autowired
    MockMvc mvc;

    @Autowired
    ApplicationContext context;

    @Test
    void probesAreAnonymousAndMinimal() throws Exception {
        for (String group : new String[]{"liveness", "readiness"}) {
            mvc.perform(get("/actuator/health/" + group))
                    .andExpect(status().isOk())
                    .andExpect(jsonPath("$.status").value("UP"))
                    .andExpect(jsonPath("$.components").doesNotExist());
        }
    }

    @Test
    void aggregateHealthIsOnlyForOperator() throws Exception {
        mvc.perform(get("/actuator/health"))
                .andExpect(status().isUnauthorized());
        mvc.perform(get("/actuator/health")
                        .with(httpBasic("scraper", "test-scrape-pass")))
                .andExpect(status().isForbidden());
        mvc.perform(get("/actuator/health")
                        .with(httpBasic("operator", "test-ops-pass")))
                .andExpect(status().isOk());
    }

    @Test
    void prometheusRequiresItsOwnAuthority() throws Exception {
        mvc.perform(get("/actuator/prometheus"))
                .andExpect(status().isUnauthorized());
        mvc.perform(get("/actuator/prometheus")
                        .with(httpBasic("operator", "test-ops-pass")))
                .andExpect(status().isForbidden());
        mvc.perform(get("/actuator/prometheus")
                        .with(httpBasic("scraper", "test-scrape-pass"))
                        .accept("text/plain;version=0.0.4"))
                .andExpect(status().isOk())
                .andExpect(content().string(containsString("# HELP")));
    }

    @Test
    void wrongScrapePasswordIsRejected() throws Exception {
        mvc.perform(get("/actuator/prometheus")
                        .with(httpBasic("scraper", "wrong-pass")))
                .andExpect(status().isUnauthorized());
    }

    @Test
    void discoveryLinksAreNotGrantedToOperator() throws Exception {
        mvc.perform(get("/actuator")
                        .with(httpBasic("operator", "test-ops-pass")))
                .andExpect(status().isForbidden());
    }

    @Test
    void healthSubtreeIsNotAllPublic() throws Exception {
        mvc.perform(get("/actuator/health/unpublished"))
                .andExpect(status().isUnauthorized());
    }

    @Test
    void otherPathsAreDenied() throws Exception {
        mvc.perform(get("/actuator/env")
                        .with(httpBasic("operator", "test-ops-pass")))
                .andExpect(status().isForbidden());
    }

    @Test
    void postToProbeIsNotMadePublic() throws Exception {
        mvc.perform(post("/actuator/health/liveness")
                        .with(httpBasic("operator", "test-ops-pass")))
                .andExpect(status().isForbidden());
    }

    @Test
    void refusingTrafficDoesNotMeanLivenessFailure() throws Exception {
        AvailabilityChangeEvent.publish(context, ReadinessState.REFUSING_TRAFFIC);
        try {
            mvc.perform(get("/actuator/health/readiness"))
                    .andExpect(status().isServiceUnavailable())
                    .andExpect(jsonPath("$.status").value("OUT_OF_SERVICE"));
            mvc.perform(get("/actuator/health/liveness"))
                    .andExpect(status().isOk());
        }
        finally {
            AvailabilityChangeEvent.publish(context, ReadinessState.ACCEPTING_TRAFFIC);
        }
    }
}
```

The readiness test publishes the `REFUSING_TRAFFIC` event and always restores state in `finally`. It proves that refusing traffic does not automatically cause liveness checks to fail. This is a test-only state simulation, not a public API for changing application state.

The POST test returns 403 in a configuration that keeps CSRF. It does not prove a GET permission automatically applies to POST; HTTP method, CSRF, and endpoint handlers are separate conditions.

## 8. Connecting Probes With Kubernetes

The YAML snippet below is **a container configuration fragment**, not a complete Deployment. It matches port 8080 and the project's default paths:

```yaml
ports:
  - name: http
    containerPort: 8080

startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 24

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3
```

The thresholds only illustrate configuration structure; real values must be based on measured startup time and responsiveness. Startup probe gives time for the startup phase before liveness/readiness start running.

HTTP probes go directly to the Pod's configured address and port, without needing to route through a public login page. Kubernetes treats codes 200–399 as success for HTTP probes; therefore, a redirect to a login page can produce a false-positive signal. The sample uses HTTP Basic for resources requiring authentication and does not enable form login for probes.

Do not insert an admin account into probe headers just to fix a 401. First check URL, method, port, rule order, and network scope. If the organization requires probes to authenticate, pick a mechanism the infrastructure truly supports and can manage secrets for, rather than hardcoding Authorization in manifests.

Do not put every external system into liveness. For readiness, include only components whose unavailability genuinely means this instance should not receive traffic. Avoid creating a setup where an outage in a shared dependency removes every instance from service with no recovery path.

See [Kubernetes: Configure Probes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

## 9. Connecting Prometheus With a Dedicated Machine Identity

The `prometheus.yml` example below assumes Prometheus and the application run directly on the same lab host. The `secrets/scrape-password` file contains the exact test password granted to the application; the path is read by the Prometheus process.

```yaml
global:
  scrape_interval: 15s
  scrape_timeout: 5s

scrape_configs:
  - job_name: actuator-local
    metrics_path: /actuator/prometheus
    scheme: http
    basic_auth:
      username: scraper
      password_file: secrets/scrape-password
    static_configs:
      - targets:
          - localhost:8080
```

If running Prometheus in a container, `localhost` is that container itself; change the target to an application address reachable from Prometheus's network. Do not fix a wrong target by exposing the entire management port publicly.

You can validate syntax with the tool bundled with Prometheus:

```bash
promtool check config prometheus.yml
```

Syntax validation does not prove the target is reachable, the password is right, or the CA is valid. After loading the configuration, check target status, scrape errors, and the `up` metric.

### 9.1. When Deploying With HTTPS

Suppose the system already has an internal Service `orders-management.observability.svc.cluster.local:8443` serving HTTPS with a valid certificate for that name. The job section may look like the following; this is configuration for the described infrastructure, not TLS configuration generated automatically by the Java project:

```yaml
scrape_configs:
  - job_name: orders-internal
    scheme: https
    metrics_path: /actuator/prometheus
    basic_auth:
      username: scraper
      password_file: /etc/prometheus/secrets/orders-scrape-password
    tls_config:
      ca_file: /etc/prometheus/certs/internal-ca.crt
    static_configs:
      - targets:
          - orders-management.observability.svc.cluster.local:8443
```

The secret and CA files must be provisioned to the right Prometheus process/container. Do not disable certificate verification to hide hostname or CA chain errors. If TLS terminates at a proxy, also examine the leg from the proxy to the application according to the system's trust boundaries.

The scraper account does not need to share a password with operator. When rotating passwords, coordinate updating the identity source and Prometheus's secret; monitor for 401 errors after the change. Verify reload mechanisms of the components in use, rather than assuming all secret files reload identically.

If using Prometheus Operator, configure authentication and Secret references via the monitoring resources supported by your Operator version; do not copy raw `scrape_configs` structure into every ServiceMonitor.

The `metrics_path`, `basic_auth`, `password_file`, and `tls_config` fields are described in [Prometheus configuration documentation](https://prometheus.io/docs/prometheus/latest/configuration/configuration/).

## 10. When Should You Separate the Management Port?

A single port is convenient when infrastructure allows only one port and can precisely restrict paths. Separating ports is useful when you want to place a management port on a private network and manage Services, firewalls, or TLS independently.

An illustrative configuration change, to be merged into existing YAML:

```yaml
server:
  port: 8080

management:
  server:
    port: 9090
```

**A different port number is not an authentication mechanism.** If port 9090 is still exposed to the Internet, management data can still be reached. Conversely, setting `management.server.address: 127.0.0.1` only fits when the collector actually has a route to that loopback; Prometheus in another Pod cannot reach the application's loopback.

Per [Boot 3.3: Monitoring and Management Over HTTP](https://docs.spring.io/spring-boot/3.3/reference/actuator/monitoring.html), management port and TLS can be configured separately. When changing ports, update scrape targets and probes accordingly.

### 10.1. Probes on the Main Port When Management Uses a Separate Port

A management port still responding does not prove the business port is accepting connections. Boot 3.3 supports:

```properties
management.endpoint.health.probes.add-additional-paths=true
```

This feature adds `/livez` and `/readyz` on the main port. When applying it, do all of the following together:

1. Point infrastructure probe paths to those two URLs on the application port.
2. Add exact GET permissions for `/livez` and `/readyz` in the chain handling those paths on the main port. In the sample configuration, the fallback chain uses denyAll, so merely setting the property will not succeed.
3. Keep the separate policy for the Prometheus endpoint on the management port.
4. Test both ports, the additional paths, and the original Actuator paths.

This is a deployment variant, not pre-verified by the single-port test suite in section 7. Do not open `/actuator/**` on the main port to fix probe failures.

## 11. Network Controls and Public Entrypoints

Layers must align along actual traffic paths:

- The public entrypoint forwards only intentionally exposed business paths; do not accidentally forward all Actuator paths via a catch-all rule.
- The management Service, if any, serves only the required network and callers; do not casually choose external exposure types just to make scraping convenient.
- Network policies restrict connections by appropriate sources and ports; application authorization continues checking scraper identity.
- Kubelet probe paths must be tested in the real node–Pod network model, especially when default-deny policies exist.

Standard Kubernetes NetworkPolicy controls connectivity at the network/transport layer and cannot filter the specific HTTP path `/actuator/prometheus` on the same port as APIs. To distinguish paths at the network layer, you need an appropriate application-layer component or separate ports. Network policies also only take effect when the cluster's CNI plugin supports them; multiple allow policies can also stack access permissiveness.

Observed source addresses and node-originated traffic handling can depend on network infrastructure. Do not infer “only one namespace can call” from a YAML snippet alone without testing from real sources. See [Kubernetes: Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

A deployment verification matrix should include:

| Request source | What must be verified |
| --- | --- |
| External user machine | Receives no Actuator data through the public entrypoint |
| Kubelet/node checking the Pod | Both probes reach the right port and path, receiving the expected status |
| Prometheus process | Scrapes using the machine identity; wrong or missing password is rejected |
| An unauthorized workload | Cannot reach the management port under the intended network policy |
| Operator via granted management path | Can read only granted resources |

## 12. Diagnosing Without Broadening Permissions Arbitrarily

| Symptom | Check in order |
| --- | --- |
| Probe returns 401 | Are port/URL/method right? Does the matcher match before the aggregate health rule? |
| Probe receives 302 | Is a proxy or login mechanism redirecting instead of returning health status? |
| Prometheus receives 401 | Username, password, secret file source, and config reload |
| Prometheus receives 403 with right password | Is actual authority METRICS_SCRAPE? Is a proxy layer denying it? |
| Scrape receives HTML or health JSON | Wrong path, wrong proxy route, or wrong target |
| Prometheus endpoint missing | Are registry, endpoint availability, and exposure configured? |
| Cannot connect | DNS, bind address, port, Service, firewall, and network policies |
| TLS error | Hostname, CA, certificate expiration, and TLS termination point |
| Health has unexpected details | show-details, show-components, and per-group configuration |
| Scrape succeeds while Pod is unready | These are two distinct signals; inspect readiness and application state |

In the sample, a GET to an unexposed path such as `/actuator/env` may receive 403 from the fallback chain for an authenticated account. That does not prove the env endpoint exists. The security chain can reject before the application searches for a handler.

Do not fix failures with `include: "*"`, granting admin rights to scraper, or `permitAll()` across all of Actuator. Trace a single request through network path, endpoint existence, authentication, and required authorization, then fix the failing layer.

## 13. Practice and Completion Criteria

1. Run the 10 tests and explain why scraper cannot read aggregate health, while operator cannot read Prometheus.
2. Read the readiness test results: why does a 503 on readiness still coexist with a 200 on liveness?
3. Add a new health group in the lab project. Prove that group does not automatically become public just because liveness/readiness are public.
4. Change the base path or separate the management port, then update matchers, probes, and scrape targets. Re-test from the right side of each connection.
5. Build a source-access matrix for a real environment: external callers, kubelet, Prometheus, and operators. Point out which layer enforces each condition.

A policy meets the standard when probes receive minimal signals, collectors have dedicated least-privilege rights, operators have explicit permissions, and public entrypoints do not inadvertently become doors to read management data.
