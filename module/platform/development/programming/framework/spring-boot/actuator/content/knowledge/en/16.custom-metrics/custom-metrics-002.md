# Registering a Counter to Count Monotonically Increasing Events

## 1. What Question Does a Counter Answer?

Suppose an application sends notifications via email and SMS. We want to know how many times the provider was observed confirming acceptance of a send request, and then track confirmations per second.

The quantity to measure is the **number of events that have occurred**, which fits Micrometer's `Counter`. Each time an event is confirmed, we add to the counter:

```text
Initial:                  0
One new confirmation:     1
Three more confirmations: 4
Two more confirmations:   6
```

The counter accumulates monotonically upward: its value may stay flat when no new events arrive, but the application does not actively subtract from it to “undo” an event.

In this lesson, “provider accepted” means only the provider's acknowledgment, not that the end recipient has read or received the notification. The recording point must match the declared meaning exactly.

`Counter` is not an arbitrary state variable. “Total notifications ever accepted” is one quantity; “notifications currently waiting to be sent” is another. A pending count can rise and fall, so it needs a state measurement such as `Gauge`.

The measurement pipeline is:

```text
Event occurs
    → code calls increment
    → Counter updates in MeterRegistry
    → Actuator/exporter exposes the measurement
    → monitoring system computes rate or increase
```

Calling `increment()` does not mean every event immediately triggers an HTTP request to the monitoring system. How and when metrics are exported or scraped is determined by the registry and backend.

## 2. Distinguish Registration, Incrementing, and Reading

Three operations have distinct roles:

| Operation | API example | Meaning |
| --- | --- | --- |
| Register | `registry.counter(...)` or `builder.register(registry)` | Obtain a Counter bound to a registry and specific identity |
| Increment | `counter.increment()`, `counter.increment(amount)` | Record the additional count of events that just occurred |
| Read | `counter.count()` | Observe the current value provided by the Counter |

**Registering is not recording an event.** With `SimpleMeterRegistry` in its default mode in the example, a newly registered Counter starts with a count of 0.

You can register once in the constructor of the measuring component, keep the reference in a field, and reuse it across events. This clarifies the measurement lifecycle and avoids looking up the same Counter repeatedly on hot paths.

There is no `decrement()`, `set(...)`, or `reset()` API on the `Counter` interface. If you need state that goes up and down, choose another meter type; if you want daily event counts, query over a time window instead of resetting the Counter every midnight.

The interface and registration methods are described in [Micrometer 1.13.0 Counter](https://raw.githubusercontent.com/micrometer-metrics/micrometer/v1.13.0/micrometer-core/src/main/java/io/micrometer/core/instrument/Counter.java).

## 3. Two Ways to Register a Counter

### 3.1. Quick Registration via MeterRegistry

The snippet below assumes an existing `registry` variable of type `MeterRegistry`:

```java
Counter accepted = registry.counter(
        "notification.provider.accepted",
        "channel", "email",
        "provider", "primary");
```

The metric name is `notification.provider.accepted`. The strings that follow are tag key–value pairs:

```text
channel  → email
provider → primary
```

The tag list must consist of complete pairs. Never pass an odd number of elements or a null tag value. External input must be normalized before being used as a tag.

This call both looks up and registers: if the corresponding Counter already exists in the registry, it returns that Counter; otherwise, the registry creates and retains the appropriate meter.

### 3.2. Registering with Counter.builder

The builder lets you add a description and base unit when needed:

```java
Counter accepted = Counter.builder("notification.provider.accepted")
        .description("Provider acceptance confirmations observed")
        .tag("channel", "email")
        .tag("provider", "primary")
        .register(registry);
```

Calling `Counter.builder(...)` alone is not enough. The builder is a configuration object; you must call `register(registry)` to obtain a usable Counter.

`description` explains what the measurement means. The `baseUnit(...)` method can attach a unit to the counted quantity, but it does not automatically convert input numbers. For example, on a volume counter, declaring bytes does not automatically turn a value measured in kilobytes into bytes.

In this lesson, each counted unit is one observed confirmation, so we do not add a separate unit to the exported name. If you configure a base unit, verify the resulting series name generated by the backend.

Decide metadata at initial registration time. Re-registering the same identity with a different description or unit is not a reliable mechanism for updating a meter's contract.

### 3.3. Identity Consists of Name and Tag Set

Within the same registry, two registration requests with the same name and the same tag set resolve to the same Counter. Tag pair ordering does not create a new Counter.

Conversely, changing `channel=email` to `channel=sms` creates a separate data group:

```text
notification.provider.accepted{channel=email, provider=primary}
notification.provider.accepted{channel=sms,   provider=primary}
```

Tags are grouping dimensions, not mutable in-place properties of a held Counter reference. To record for SMS, use the SMS Counter; do not try to change a tag on the email Counter and expect previous counts to move across groups.

A different registry has its own data lifecycle. Two Counters with the same name and tags in two independent `SimpleMeterRegistry` instances do not share counts automatically. In Spring Boot, a composite registry coordinates child registries; that does not mean every ad-hoc registry created in the application is automatically wired together.

## 4. Increment the Right Amount at the Right Time

### 4.1. Single Event or Batch of Events

```java
accepted.increment();
accepted.increment(3);
```

The first call increments by one. The second increments by three, appropriate when three events of the same kind have just been confirmed.

Do not use `increment(currentTotal)` to “set” a current total. If a source total is 10 and then 12, calling increment by 10 and then increment by 12 makes the Counter 22. When a source already exposes a cumulative total, a different integration approach is needed, such as reading via `FunctionCounter` when its contract fits, or computing deltas in a controlled manner. Do not turn `Counter` into an assignment operation.

`increment(double amount)` accepts a floating-point number. That allows counting a general positive quantity, though if the quantity is discrete events you should pass meaningful integer values. Do not round an ambiguous value just to make it look like a count.

### 4.2. Do Not Rely on Negative or Invalid Values

The Counter usage contract is to increment by positive amounts. Never pass negative numbers to reduce a count, and do not rely on all registries throwing exceptions or ignoring invalid inputs identically.

For externally supplied data, guard against negative numbers, `NaN`, and infinity before the recording point. When no new events occurred, there is no need to call increment.

For example, an adapter receiving an integer count can specify:

```text
amount < 0 → invalid input
amount = 0 → no increment performed
amount > 0 → increment by exact amount
```

If only three out of five notifications in a batch are accepted by the provider, increment by three; do not increment by five just because five requests were sent.

See [Micrometer — Counters](https://docs.micrometer.io/micrometer/reference/concepts/counters.html).

### 4.3. The Recording Point Determines the Meaning of the Count

If the increment is placed before the provider call, the metric actually counts send attempts. If placed after verifying an acceptance response, the metric counts acceptance confirmations.

```text
Start sending
  → call provider
  → receive response
  → check whether accepted
  → only when accepted: increment Counter accepted
```

An HTTP call that does not throw an exception is not yet proof that the response body indicates acceptance. Confirmation rules must follow the protocol and integration contract.

In asynchronous processing, increment in the branch where the actual result is received. Returning a `CompletableFuture` or enqueuing a request is not yet provider confirmation.

If retries produce an additional acceptance response, a response-counting Counter may increment again. To count unique accepted notifications, handle deduplication at the business layer and place the increment after that uniqueness boundary. A Counter does not automatically recognize message IDs that were already counted.

## 5. Runnable Example: Re-registration, Grouping, and Concurrent Increments

The following program uses Java 17 and Micrometer 1.13.0. There is no need to start Spring Boot or connect to a notification service; the increments are experimental data.

### 5.1. Prepare Dependencies in a Dedicated Experiment Directory

Create `build.gradle`:

```groovy
plugins {
    id 'java'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'io.micrometer:micrometer-core:1.13.0'
}

tasks.register('copyRuntimeDependencies', Copy) {
    from configurations.runtimeClasspath
    into layout.buildDirectory.dir('runtime-libs')
}
```

The task collects only runtime dependencies, including transitive dependencies. The version is pinned so the example is reproducible; in a Spring Boot application, use the Micrometer version managed by the application's BOM.

With Gradle 8.x and JDK 17 available, run:

```bash
gradle -q copyRuntimeDependencies
```

If the directory already has a Gradle Wrapper, use the corresponding wrapper instead of `gradle`. Downloading dependencies the first time requires access to Maven Central.

### 5.2. CounterRegistrationDemo.java Program

Place this Java file in the same directory as `build.gradle`; we will compile with `javac` rather than using Gradle's source layout in this experiment.

```java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.simple.SimpleMeterRegistry;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class CounterRegistrationDemo {
    private static void printCount(String label, Counter counter) {
        System.out.println(label + "=" + Math.round(counter.count()));
    }

    public static void main(String[] args) throws Exception {
        SimpleMeterRegistry registry = new SimpleMeterRegistry();
        try {
            Counter email = Counter.builder("notification.provider.accepted")
                    .description("Provider acceptance confirmations observed")
                    .tags("channel", "email", "provider", "primary")
                    .register(registry);

            printCount("initial.email", email);
            email.increment();
            email.increment(3);
            printCount("afterSingleAndBatch.email", email);

            Counter alias = registry.counter(
                    "notification.provider.accepted",
                    "provider", "primary", "channel", "email");
            System.out.println("sameCounter=" + (email == alias));
            alias.increment(2);
            printCount("afterAlias.email", email);

            Counter sms = registry.counter(
                    "notification.provider.accepted",
                    "channel", "sms", "provider", "primary");
            sms.increment(2);
            printCount("sms", sms);

            ExecutorService workers = Executors.newFixedThreadPool(4);
            try {
                List<Future<?>> futures = new ArrayList<>();
                for (int worker = 0; worker < 4; worker++) {
                    futures.add(workers.submit(() -> {
                        for (int event = 0; event < 250; event++) {
                            email.increment();
                        }
                    }));
                }
                for (Future<?> future : futures) {
                    future.get();
                }
            } finally {
                workers.shutdownNow();
            }

            printCount("parallel.email", email);
            System.out.println("meter.ids=" + registry.getMeters().size());

            SimpleMeterRegistry secondRegistry = new SimpleMeterRegistry();
            try {
                Counter otherEmail = secondRegistry.counter(
                        "notification.provider.accepted",
                        "channel", "email", "provider", "primary");
                printCount("secondRegistry.email", otherEmail);
                printCount("firstRegistry.email", email);
            } finally {
                secondRegistry.close();
            }
        } finally {
            registry.close();
        }
    }
}
```

### 5.3. Compile and Run

Windows PowerShell or Command Prompt:

```powershell
javac --release 17 -cp "build/runtime-libs/*" CounterRegistrationDemo.java
java -cp ".;build/runtime-libs/*" CounterRegistrationDemo
```

Linux/macOS uses a colon to separate classpath entries:

```bash
javac --release 17 -cp "build/runtime-libs/*" CounterRegistrationDemo.java
java -cp ".:build/runtime-libs/*" CounterRegistrationDemo
```

Stdout on a successful run:

```text
initial.email=0
afterSingleAndBatch.email=4
sameCounter=true
afterAlias.email=6
sms=2
parallel.email=1006
meter.ids=2
secondRegistry.email=0
firstRegistry.email=1006
```

### 5.4. Explaining the Output

1. A newly registered email Counter has a value of 0 in the experiment registry.
2. Incrementing by one and then by three yields 4.
3. `alias` has the same name and tags as `email`, even with the tag order reversed. `sameCounter=true` and incrementing via the alias brings the email Counter to 6.
4. The SMS Counter has a different tag so its value of 2 is not added to the email Counter.
5. Four tasks increment concurrently, 250 times each: adding `4 × 250 = 1,000`. The final email result is `6 + 1,000 = 1,006`.
6. Registering the alias does not create an extra meter; the first registry has two IDs corresponding to email and SMS.
7. The second registry has a new email Counter at 0, while the first registry still holds 1,006.

`Future.get()` ensures each task has finished before printing the result. Do not replace it with a `Thread.sleep(...)` and guess that the work is done.

`Math.round(...)` only keeps stdout tidy because all values in the experiment are small integers. The actual `count()` API returns `double`; do not treat rounding as part of the Counter mechanism.

## 6. Using Counter in a Spring Boot Component

The application needs Spring Boot Actuator for the metrics infrastructure. With Boot's dependency management configured, dependencies typically include:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}
```

This starter does not create an HTTP server on its own. The HTTP verification section below assumes the application already has an appropriate web starter. To export Prometheus metrics, `io.micrometer:micrometer-registry-prometheus` is also required on the runtime classpath.

Create `NotificationCounters.java` in a package scanned by Spring. This is a component class used inside a Boot application, not a standalone `main` program:

```java
import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.MeterRegistry;
import java.util.EnumMap;
import java.util.Objects;
import org.springframework.stereotype.Component;

@Component
public final class NotificationCounters {
    public enum Channel {
        EMAIL, SMS
    }

    private final EnumMap<Channel, Counter> acceptedByChannel =
            new EnumMap<>(Channel.class);

    public NotificationCounters(MeterRegistry registry) {
        acceptedByChannel.put(Channel.EMAIL,
                createCounter(registry, "email"));
        acceptedByChannel.put(Channel.SMS,
                createCounter(registry, "sms"));
    }

    private static Counter createCounter(
            MeterRegistry registry, String channel) {
        return Counter.builder("notification.provider.accepted")
                .description("Provider acceptance confirmations observed")
                .tags("channel", channel, "provider", "primary")
                .register(registry);
    }

    public void accepted(Channel channel) {
        acceptedByChannel.get(Objects.requireNonNull(channel)).increment();
    }

    public void acceptedBatch(Channel channel, int amount) {
        Counter counter =
                acceptedByChannel.get(Objects.requireNonNull(channel));
        if (amount < 0) {
            throw new IllegalArgumentException("amount must not be negative");
        }
        if (amount > 0) {
            counter.increment(amount);
        }
    }
}
```

Integration points will call `accepted(Channel.EMAIL)` after a single email confirmation, or `acceptedBatch(Channel.EMAIL, n)` for n confirmations in a batch. Do not call both for the same set of events.

The class pre-registers the exact two tag groups and retains the Counters in a field. This ensures even a group with no events yet appears with an initial count of 0 once the component has been initialized and the meter is not denied by filters.

`EnumMap` is written only in the constructor and read thereafter; increments go into existing Counters. The example does not require creating or mutating maps per request.

### 6.1. Use the Spring-Managed Registry

Injecting `MeterRegistry` ensures meters pass through the application's registry, exporters, common tags, and filters. Do not create a `SimpleMeterRegistry` inside a service and expect Actuator endpoints to aggregate measurements from that private object.

Static methods on `Metrics` operate on the global registry. In a Boot application, prefer the injected registry so lifecycle and configuration are explicit.

If you need to initialize common tags or customize the registry, use Boot's configuration mechanisms before meters are registered. See [Spring Boot 3.3 — Metrics](https://docs.spring.io/spring-boot/3.3/reference/actuator/metrics.html).

### 6.2. Bound Tags at the Recording Point

`channel` in the class only has email and SMS; `provider` in the example is a stable configuration code. Do not replace them with arbitrary request content.

Do not create tags for recipient email, phone number, notification ID, or trace ID. Each new value can create another Counter and time series. Detailed identifiers belong in logs/tracing or business datastores.

Keep the tag key set consistent within a Counter family. Do not register one group with only `channel` and another group of the same name with `recipient` added. Beyond data cost, some backends enforce constraints on the label set of a given metric name.

Re-registering the same name and tags does not increase the meter count; registering the same name with millions of different tag sets does.

### 6.3. No @Counted Needed for Manual Counters

Direct `increment` calls already record the event. `@Counted` is a different instrumentation style that typically requires the corresponding annotation/aspect support; placing the annotation on an arbitrary method alone does not guarantee counting works.

An annotation counting method invocations may also not match “provider accepted.” If a method wraps retries or returns before an asynchronous result is known, you must verify the exact counting scope. Once incrementing manually, avoid adding another counter for the same definition unintentionally.

## 7. Thread-Safe Increments Do Not Make Entire Business Flows Atomic

Standard Micrometer Counters are designed to accept increments from multiple threads; the experiment above verifies the final total after all tasks finish.

Do not try to guard a count yourself by doing:

```text
read current count → add one in a local variable → try to set count back
```

Call `increment()` directly. The Counter is responsible for updating its measurement; the application does not need an external read–modify–write loop.

However, distinguish carefully:

| Property | Does Counter solve this automatically? |
| --- | --- |
| Multiple threads writing to a standard Counter | Has appropriate update mechanisms in the implementation |
| Preventing double-counting the same notification | No |
| Committing/rolling back DB transaction and increment together | No |
| Incrementing two Counters as one atomic transaction | No |
| Reading multiple meters as a consistent snapshot | No |
| Preserving data across process restarts | Not guaranteed on its own |

One thread can increment `accepted` and another thread can scrape metrics before a related metric is updated. Therefore, do not use two read measurements to drive business decisions requiring atomicity.

Reading `count()` while multiple threads are still incrementing is a point-in-time observation, not a guarantee that all in-flight events are reflected. To test final totals, wait for work to complete as shown in the example.

## 8. Verify the Counter via Actuator

### 8.1. Expose Diagnostic Endpoints Locally

For a web application that already has Actuator, an experimental configuration:

```yaml
management:
  server:
    address: 127.0.0.1
    port: 8081
  endpoints:
    web:
      exposure:
        include: health,metrics
```

Access permissions remain subject to Spring Security and the active network configuration. Merge with the existing `management` block rather than creating two duplicate root keys.

After the `NotificationCounters` component has been initialized, call:

```bash
curl "http://127.0.0.1:8081/actuator/metrics"
curl "http://127.0.0.1:8081/actuator/metrics/notification.provider.accepted"
curl "http://127.0.0.1:8081/actuator/metrics/notification.provider.accepted?tag=channel:email&tag=provider:primary"
```

On PowerShell, you can use `curl.exe` to avoid confusion with the alias.

The endpoint uses the Micrometer name `notification.provider.accepted`. With a cumulative registry, the `measurements` section of a Counter contains the `COUNT` statistic. The exact value depends on the events that have occurred; there is no single fixed JSON count valid for every application.

If you omit the channel filter, the metrics endpoint may sum the counts of matching Counters with the same name. In the standalone experiment, email 1,006 and SMS 2 give a total of 1,008; that total does not mean email alone reached 1,008.

### 8.2. Exporting to Prometheus

Add the Prometheus registry to the Boot application's dependencies and expose the endpoint:

```groovy
dependencies {
    runtimeOnly 'io.micrometer:micrometer-registry-prometheus'
}
```

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
```

This is an update to the endpoint configuration from the previous example, not a second `management` key in the same file.

With the naming and configuration without a separate base unit in this lesson, the Counter series typically looks like:

```text
notification_provider_accepted_total{channel="email",provider="primary"} 1006.0
```

The value 1006.0 illustrates the email count from the experiment dataset; a running Boot application will have values matching its actual events and may include additional labels. Inspect the `/actuator/prometheus` endpoint to confirm the exact name, value, and full set of labels.

Do not put the Prometheus-suffixed name into the `/actuator/metrics/...` path. Also do not manually append `_total` to the name in code just to guess the exported name.

## 9. Read Rates and Understand Resets

### 9.1. Raw Totals Are Affected by Process Uptime

An instance running for seven days has a count of 500,000; an instance started five minutes ago has a count of 2,000. You cannot conclude from those two raw totals that the first instance is currently processing faster.

With systems like Prometheus, you typically analyze the rate or increase over a time window:

```promql
sum by (channel) (
  rate(notification_provider_accepted_total{provider="primary"}[5m])
)
```

The query expresses the average rate of confirmations per second over a five-minute window, summing matching series by channel.

If the backend holds multiple applications with the same metric name, add labels identifying the specific service/environment before summing; do not accidentally merge data from different scopes.

To view how many additional confirmations occurred over 15 minutes:

```promql
sum by (channel) (
  increase(notification_provider_accepted_total{provider="primary"}[15m])
)
```

`increase` can return non-integer numbers due to extrapolation over the scrape window. It is a query result over monitoring data, not an exact event-by-event ledger. See [Prometheus — Query functions](https://prometheus.io/docs/prometheus/2.55/querying/functions/).

### 9.2. Process Resets Are Not Decrements in Code

When an instance restarts, the cumulative Counter of the new process usually starts over. A raw graph can drop from a large number down to a small number.

The application does not need to decrement or reset Counters to handle this. The backend uses counter-aware functions, such as `rate` or `increase`, to handle resets per series.

Compute the rate per series first and only sum afterward as shown in the queries above. Summing raw totals across multiple instances before computing increases can obscure individual instance resets.

Resets also do not recover events that occurred before the first scrape or data not yet exported when a process dies. Metrics do not replace the durable storage needed for business reconciliation.

### 9.3. Do Not Assume One Registry's Cumulative Semantics Apply to Every Backend

The default `SimpleMeterRegistry` in the experiment and Prometheus typically represent cumulative counts. Some registries publish over fixed intervals, often called a `step`, so observed counts may reflect the completed interval rather than the full process lifetime.

This is a registry aggregation model, not a requirement for business code to reset Counters manually after each interval. When switching backends, read the registry's documentation and aggregation model instead of treating `count()` as a universal persistent total across all systems.

Refer to [Micrometer — Rate Aggregation](https://docs.micrometer.io/micrometer/reference/concepts/rate-aggregation.html).

### 9.4. No Data Is Different from Zero Events

A Counter that is registered but not yet incremented can have a value of 0. A meter that has not been created, was denied by a filter, or is no longer scraped may not appear in the backend at all.

`rate` requires enough samples. A newly started process without enough data does not prove a rate of 0. When building alerts, define both the missing-metric case and the flat-count case.

## 10. Diagnose When a Counter Does Not Appear or Does Not Increase

| Symptom | What to check |
| --- | --- |
| Metric name not found | Did the builder call register? Was the registering component initialized? |
| Code increments but Actuator does not show it | Is it writing to a private registry instead of Spring's registry? |
| Email appears but SMS does not | Was SMS registered? Does that execution path use the exact tag? |
| Counter exists but count stays 0 | Did execution actually enter that event branch? Was a NOOP meter returned? |
| Count is higher than expected | Are retries, duplicate callbacks, or two recording points incrementing for one event? |
| Count is lower than expected | Is there an uninstrumented path, partial batch failure, filter denial, or restart data loss? |
| Aggregated value differs from single-tag value | Is the endpoint/query summing multiple channels, providers, or instances? |
| Re-registering does not reset count to 0 | Same name and tags return the existing Counter |
| Too many series in backend | Do tags contain recipient IDs, request IDs, or dynamic values? |
| Count changes per interval | Does the registry use step-based reporting? |
| Already have a timer and added a counter too | Are both meters counting the same event, or truly two distinct boundaries? |

`MeterFilter` can deny a meter and return a no-op (NOOP) object. Calling `increment` then does not necessarily throw an exception, yet expected numbers still do not appear. Check filter configuration and tag allow conditions rather than incrementing repeatedly to test.

See [Micrometer — Meter Filters](https://docs.micrometer.io/micrometer/reference/concepts/meter-filters.html).

Some design mistakes to avoid right from the start:

- Do not remove and re-register meters per request to get fresh counts.
- Do not embed recipient IDs or the current date into names to simulate grouping or resets.
- Do not use a monotonically increasing Counter to represent the current queue depth.
- Do not decrement the accepted Counter when a delivery failure to the recipient is reported later; if needed, record a separate failure event with its own definition.
- Do not treat an in-memory registry as the source of truth for unique counting, deduplication, or business history.
- Do not add a counter solely to count the same events already counted by a `Timer` or `DistributionSummary`, unless there is a clearly different measurement boundary.

## 11. Practice

1. In the standalone program, change the batch increment from 3 to 5. Predict the email values after the alias and after the four threads, then run to verify.
2. Change the alias tag from `channel=email` to `channel=sms`. Predict `sameCounter`, the meter ID count, and each group's count.
3. Add a `provider=backup` tag to a new Counter. Explain why it is a distinct identity and which groups a query aggregating by channel will sum.
4. Run eight tasks incrementing 125 times each, still waiting on all `Future`s. Explain why the final increment matches the four-task experiment.
5. For a batch of 20 requests where only 17 confirmations are accepted, determine how much the accepted Counter increases. If you want to track the 20 attempts and three rejections, propose separate measurements.
6. Sketch where to increment the Counter in an asynchronous sending flow with retries. State clearly whether the measurement counts attempts, acceptance responses, or unique notifications.
7. Explain why a Counter at 0, an absent series, and insufficient samples to compute `rate` are three situations that must be distinguished.

After practicing, you should be able to prove that **the right identity → the right Counter → the right recording point → the right increment → the right query scope**. That is the foundation that turns a simple counter into an operationally trustworthy metric.
