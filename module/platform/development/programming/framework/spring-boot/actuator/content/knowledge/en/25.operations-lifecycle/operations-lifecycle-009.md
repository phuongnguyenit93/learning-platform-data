# Checking Readiness and Observability Data During Application Shutdown

When stopping a serving instance, two separate things must be verified: whether the application has signaled that it is no longer ready to receive traffic, and whether already-accepted requests finish within the timeout. A single successful health check or an isolated log line answers only part of the picture.

## Distinguishing In-Application State from Probe Results

Spring Boot stores availability state in `ApplicationAvailability`. Readiness indicates whether the instance is ready to accept traffic. Liveness reflects whether the application is functioning properly according to its lifecycle state. When the web context begins closing, Boot emits `ReadinessState.REFUSING_TRAFFIC`. During graceful shutdown, liveness can remain `CORRECT` while the server finishes in-flight requests. [Probe states across the Spring Boot 3.3 lifecycle](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes.lifecycle)

| Phase | Internal state | External signal |
| --- | --- | --- |
| Started and ready | `ACCEPTING_TRAFFIC`, liveness `CORRECT` | With the default readiness group, `GET /actuator/health/readiness` returns `200` and `UP`. |
| Graceful shutdown started | `REFUSING_TRAFFIC`, liveness may still be `CORRECT` | If probe requests still reach Actuator, the readiness indicator reports `OUT_OF_SERVICE`, mapped to HTTP `503` by default. Once the server blocks new connections, same-port probes may encounter connection errors or timeouts. |
| Shutdown completed | Context and server closed | No live probe remains to read state from that instance. Rely on logs, outcomes of sent requests, and platform events for correlation. |

`REFUSING_TRAFFIC` is an in-memory state. Changing the state does not itself block individual HTTP requests at the application layer. In systems with probe configuration, check results update periodically. An instance may still receive traffic during the window before the result is applied to routing. The embedded server's shutdown mechanism handles direct connections to the instance. With Spring Boot 3.3, Tomcat, Jetty, and Reactor Netty stop accepting new requests at the network layer during graceful shutdown. Undertow may return `503` at the server layer. A `503` generated by the server or a proxy only confirms the request was rejected at that layer. To know which readiness status Actuator returned, inspect the path, response body, and response origin. [Graceful shutdown in Spring Boot 3.3](https://docs.spring.io/spring-boot/3.3/reference/web/graceful-shutdown.html)

## Trying with an In-Flight Request

The example uses Java 17 or later, Gradle, Spring Boot 3.3, and embedded Tomcat. Run locally with port 8080 free. Place the following three files in a separate test directory. The shutdown endpoint in the example listens only via a server bound to the loopback address.

**`build.gradle`**

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.0'
}

repositories {
    mavenCentral()
}

dependencies {
    implementation platform('org.springframework.boot:spring-boot-dependencies:3.3.0')
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}

tasks.named('bootJar') {
    archiveFileName = 'readiness-lab.jar'
}
```

**`src/main/java/demo/readiness/ReadinessLab.java`**

```java
package demo.readiness;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.availability.AvailabilityChangeEvent;
import org.springframework.boot.availability.ReadinessState;
import org.springframework.context.event.EventListener;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class ReadinessLab {
    private static final Logger log = LoggerFactory.getLogger(ReadinessLab.class);

    public static void main(String[] args) {
        SpringApplication.run(ReadinessLab.class, args);
    }

    @EventListener
    public void onAvailability(AvailabilityChangeEvent<?> event) {
        if (event.getState() instanceof ReadinessState state) {
            log.info("readiness={}", state);
        }
    }

    @GetMapping("/slow")
    public String slow() throws InterruptedException {
        log.info("slow: started");
        Thread.sleep(8000);
        log.info("slow: finished");
        return "slow completed";
    }
}
```

**`src/main/resources/application.properties`**

```properties
server.address=127.0.0.1
server.port=8080
server.shutdown=graceful
spring.lifecycle.timeout-per-shutdown-phase=20s
management.endpoint.health.probes.enabled=true
management.endpoint.shutdown.enabled=true
management.endpoints.web.exposure.include=health,shutdown
```

`management.endpoint.health.probes.enabled=true` creates the probe groups even when running outside Kubernetes. Setting `server.shutdown=graceful` enables waiting for in-flight requests. The value `20s` is the limit for each Spring lifecycle shutdown phase. In this exercise, the `/slow` request intentionally sleeps for 8 seconds to leave time to send the shutdown command. [Probe configuration](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes) · [Shutdown timeout configuration](https://docs.spring.io/spring-boot/3.3/reference/web/graceful-shutdown.html)

**Terminal 1.** Build and run the JAR. Keep this terminal open to read logs.

```bash
gradle bootJar
java -jar build/libs/readiness-lab.jar
```

**Terminal 2.** Once the log shows `readiness=ACCEPTING_TRAFFIC`, run the following Bash loop to record probe results over time. Keep the HTTP status code, response body, and errors output by `curl`. Press Ctrl+C to stop the loop after the application exits.

```bash
while true; do
  printf '%s ' "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
  curl -sS --connect-timeout 1 --max-time 2 -w ' http=%{http_code}\n' \
    http://127.0.0.1:8080/actuator/health/readiness
  sleep 0.3
done
```

**Terminal 3.** Send a request that takes time to process.

```bash
curl -i --max-time 25 http://127.0.0.1:8080/slow
```

**Terminal 4.** As soon as Terminal 1 logs `slow: started`, send the shutdown request.

```bash
curl -i --max-time 5 -X POST http://127.0.0.1:8080/actuator/shutdown
```

If shutdown happens while `/slow` is still processing, the application log contains the following messages in this order. Timestamps, thread names, and Tomcat log lines vary by run.

```text
readiness=ACCEPTING_TRAFFIC
slow: started
readiness=REFUSING_TRAFFIC
slow: finished
```

Cross-check three more pieces of evidence:

1. Before the shutdown command, the probe returns `{"status":"UP"}` and `http=200`. During shutdown, the probe may jump straight from `200` to a connection error or timeout. `http=000` is the value `curl` displays when no HTTP status code was received. The `readiness=REFUSING_TRAFFIC` log confirms the state transition even when the probe has lost its path to the application.
2. The `/slow` request started before shutdown and can finish within the timeout. In a successful exercise, Terminal 3 receives `200 OK` and body `slow completed`. If the log shows `slow: finished` while the caller failed, you only have evidence that the handler reached the end. Use the caller's outcome to confirm the response actually arrived.
3. A `200` response from the shutdown command confirms Actuator accepted the operation. Use the shutdown log timestamp and the `java -jar` command exit to confirm the instance stopped. If `slow: finished` appears before `readiness=REFUSING_TRAFFIC`, the exercise did not create a request overlapping with shutdown. Run again and send the shutdown command earlier. [shutdown endpoint HTTP contract](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/shutdown.html)

## Correlating Data in Operations

- **Attach a shared identifier and timestamp.** Correlate shutdown receipt time, readiness transition time, last probe time, the time the router stopped sending traffic, and outcomes of started requests. Use the same instance identifier, such as Pod name, and request ID if available. Normalize timestamps to the same time zone before comparing. Through a load balancer, a `200` may come from a different instance.
- **Measure on the serving port as well.** If Actuator runs on a separate management port, probes on that port only verify the availability of the management port and the state it reads. You can set `management.endpoint.health.probes.add-additional-paths=true` to expose `/readyz` and `/livez` on the main port. When analyzing, record which probe and which port returned the result. [Probes and separate management port](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes)
- **Persist evidence out-of-process.** After the server closes, collection systems can no longer scrape endpoints and may miss the final sample. Correlate shipped logs, the latest metric scrape timestamp, routing events, and client-side errors. Use in-flight request counts and completed or failed request counts during the shutdown window to assess impact, provided those metrics were actually collected by the system.
