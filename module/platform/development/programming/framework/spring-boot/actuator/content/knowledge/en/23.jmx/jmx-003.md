# Accessing Endpoints with JConsole or Compatible JMX Tools

## 1. Understand the Connection Path Before Opening the Tool

JConsole is the JDK's graphical interface tool for observing and managing a JVM over JMX. When connecting to a Spring Boot application, the tool can see both JVM MBeans and MBeans registered by Actuator. Successfully connecting to the JVM does not prove that the desired Actuator endpoint has been exposed.

Four components must be distinguished:

| Component | Role |
| --- | --- |
| Target application/JVM | Running process that the operator wants to observe |
| MBeanServer | Registry of managed objects inside the JVM |
| Endpoint MBean | Managed object exposed by Actuator, with a name and operations |
| JMX client | JConsole or another program that connects, reads metadata, and invokes operations |

A typical path:

```text
JConsole / JMX client
        ↓ local attach or remote connector connection
MBeanServer of the right JVM
        ↓ look up the endpoint ObjectName
Read metadata
        ↓ select the right operation and parameter signature
Invoke operation → view result or error
```

There are two common connection styles:

- **Local attach:** the tool and target JVM are on the same machine environment with appropriate OS permissions. You can select by PID without opening a remote JMX port yourself.
- **Remote connector:** the tool uses a JMX address already configured for the target JVM. Network, authentication, permissions, and TLS must be considered.

Local attach is not an HTTP request to `/actuator`. The application's HTTP port, such as 8080, is not a JMX port by default either.

## 2. Preparing an Endpoint So There Is Something to Access

### 2.1. Three Separate Conditions

Before looking for an endpoint in JConsole, verify:

1. The application has Actuator support and the endpoint exists.
2. Spring JMX is enabled and the endpoint is allowed to be exposed over JMX.
3. The tool connects to the right MBeanServer of the running process.

In Spring Boot 3.3, Spring's JMX support is off by default; enable it with `spring.jmx.enabled=true`. Endpoint MBeans use the `org.springframework.boot` domain by default; the example name for Health is `org.springframework.boot:type=Endpoint,name=Health`. [Spring Boot 3.3: JMX](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html).

Do not use the presence of `java.lang` as proof that Actuator is active. Standard JVM MBeans can exist even when Spring's JMX support is not enabled.

`management.endpoints.web.exposure.include` and `management.endpoints.jmx.exposure.include` are two separate exposure configurations. Adding an endpoint to the HTTP list does not substitute for the JMX list. Moreover, a disabled endpoint does not become available merely by being placed in the exposure list. [Endpoint enablement and exposure rules](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html).

### 2.2. Standalone Hands-On Application

The example uses JDK 21 and Spring Boot 3.3.0 to pin the practice environment. The application does not need an HTTP server. It exposes:

- `Health`, to verify a built-in endpoint.
- `Trainingcontrol`, a sample endpoint with a read operation `status` and a write operation `rename`.

The write operation only changes a label in memory of the sample application itself. Do not use it to modify configuration of another system.

Structure:

```text
jmx-console-demo/
├── pom.xml
└── src/main/
    ├── java/example/jmx/JmxDemoApplication.java
    └── resources/application.properties
```

`pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.0</version>
        <relativePath/>
    </parent>
    <groupId>example</groupId>
    <artifactId>jmx-console-demo</artifactId>
    <version>1.0.0</version>
    <properties>
        <java.version>21</java.version>
    </properties>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-actuator</artifactId>
        </dependency>
    </dependencies>
    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

`src/main/resources/application.properties`:

```properties
spring.main.web-application-type=none
spring.jmx.enabled=true
management.endpoints.jmx.exposure.include=health,trainingcontrol
```

`src/main/java/example/jmx/JmxDemoApplication.java`:

```java
package example.jmx;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicReference;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.actuate.endpoint.annotation.Endpoint;
import org.springframework.boot.actuate.endpoint.annotation.ReadOperation;
import org.springframework.boot.actuate.endpoint.annotation.WriteOperation;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication(proxyBeanMethods = false)
public class JmxDemoApplication {
    public static void main(String[] args) throws InterruptedException {
        SpringApplication.run(JmxDemoApplication.class, args);
        System.out.println("TARGET_PID=" + ProcessHandle.current().pid());
        new CountDownLatch(1).await();
    }

    @Bean
    TrainingControlEndpoint trainingControlEndpoint() {
        return new TrainingControlEndpoint();
    }

    @Endpoint(id = "trainingcontrol")
    public static class TrainingControlEndpoint {
        private final AtomicReference<String> label = new AtomicReference<>("demo");

        @ReadOperation
        public String status() {
            return "label=" + label.get();
        }

        @WriteOperation
        public String rename(String label) {
            if (label == null || label.isBlank() || label.length() > 32) {
                throw new IllegalArgumentException("label must contain 1 to 32 characters");
            }
            this.label.set(label);
            return label;
        }
    }
}
```

`@Endpoint` provides an endpoint that can be exposed according to configured technologies. In this sample, only JMX is used. If replaced with `@WebEndpoint`, that endpoint cannot be found in JMX by default; that annotation is specific to web.

`CountDownLatch` keeps the practice process alive so the learner has time to connect JConsole. It is not a required part of a web application or an application that already has work keeping the process alive.

Compile and run from the directory containing `pom.xml`:

```shell
mvn clean package
java -jar target/jmx-console-demo-1.0.0.jar
```

Maven needs to download dependencies if the machine does not have them yet. In addition to startup logs, the application prints a line like:

```text
TARGET_PID=11372
```

11372 is an illustrative PID; you must use the PID printed by your own current process. Do not reuse the PID from a previous run. Stop the application with `Ctrl+C` after practicing.

## 3. Connecting JConsole to an Application on the Local Machine

### 3.1. Opening the Right JDK Tool

Use a full JDK that has `jconsole` in its `bin` directory and an environment that supports a graphical interface. When that directory is already on PATH:

```shell
jconsole
```

You can use `jps -lv` or a process manager to verify the PID. For packaged applications, the process line may show the JAR name and arguments rather than the full Java class name.

Once the PID is known, JConsole also accepts the PID directly. In PowerShell:

```powershell
$targetPid = Read-Host "Enter TARGET_PID of the sample application"
jconsole $targetPid
```

JConsole also accepts `host:port` or a JMX service URL. Those are different connection forms, not alternative ways to write a local PID. [The jconsole command in JDK 21](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jconsole.html).

### 3.2. Selecting the Right Process

In the connection dialog, select **Local Process**, match the PID against `TARGET_PID`, and click **Connect**. Ensure that JConsole and the target JVM run under the same OS account and have appropriate attach permissions.

If no local management agent is running yet, a JVM supporting attach can be instructed by the tool to start the agent upon connection. No remote port needs to be added just for local experiments. [Local connection with JConsole](https://docs.oracle.com/en/java/javase/21/management/using-jconsole.html).

An existing PID alone is not enough to guarantee it is the right application. Check the process name, launch arguments, and sample MBean after connecting. Avoid picking another JVM merely because it appears first in the list.

If the tool displays an insecure connection warning, distinguish the local connector of a verified process from a remote connection lacking TLS configuration. Do not turn bypassing warnings in a local session into a default habit for every server.

## 4. Finding Endpoints and Invoking Operations in JConsole

### 4.1. Search by MBean, Not by HTTP Path

After connecting, open the **MBeans** tab and find the `org.springframework.boot` domain. With the sample configuration, two endpoints should be found:

```text
org.springframework.boot
└── type=Endpoint
    ├── name=Health
    └── name=Trainingcontrol
```

This represents a tree by ObjectName properties; how a tool renders tree labels may vary. The full name of the sample endpoint is:

```text
org.springframework.boot:type=Endpoint,name=Trainingcontrol
```

The parts have different meanings:

| Component | Meaning in the Example |
| --- | --- |
| `org.springframework.boot` | JMX domain |
| `type=Endpoint` | Property used to classify the MBean |
| `name=Trainingcontrol` | Property identifying the sample endpoint |
| `status`, `rename` | Operation names inside the MBean |

`Trainingcontrol` is the verified name derived from endpoint ID `trainingcontrol` in the sample. Do not infer that every ID follows a capitalization rule the tool guesses automatically; for other endpoints or custom naming, check the actual MBean name.

### 4.2. Empty Attributes Is Not an Error

Select MBean `Trainingcontrol` and the **Operations** section. The sample provides:

| Operation | Parameters | JMX Return Type |
| --- | --- | --- |
| `status` | None | `java.lang.String` |
| `rename` | One `java.lang.String` | `java.lang.String` |

Methods with `@ReadOperation` and `@WriteOperation` here are exposed as JMX operations. They are not required to become attributes simply because they read data. Therefore, an empty **Attributes** section on the sample MBean is a normal result.

JConsole uses metadata to display operations as invokable controls. Select an operation to check its signature before entering parameters. [Browsing and invoking MBeans in JConsole](https://docs.oracle.com/en/java/javase/21/management/using-jconsole.html).

### 4.3. Invoking a Read Operation

Select `status` and invoke the zero-argument operation. On a freshly started application, the return value is:

```text
label=demo
```

This is the return string of the JMX operation. There is no HTTP status 200 and no HTTP response body to look for in this view.

To confirm the state again after a change, invoke `status` once more. Do not assume the operation result screen will automatically re-invoke that operation on the JVM chart refresh interval.

### 4.4. Invoking the Write Operation in the Sample

Select `rename`, enter `practice` in the string parameter field, and invoke the operation. Return value:

```text
practice
```

Invoke `status` again:

```text
label=practice
```

The label exists only in memory; restarting the application resets it to `demo`. If you submit an empty label, whitespace-only text, or a value longer than the limit in code, the operation returns an error. An operation invocation error differs from failing to connect to the JVM.

For real management MBeans, read the description and signature before clicking invoke. Some operations can alter configuration or trigger expensive tasks. Just because the tool shows a button does not mean the operation should be clicked merely to see what happens.

## 5. Reading Metadata and Results Under the JMX Contract

### 5.1. ObjectName Is a Structured Name

The following two strings have the same naming properties:

```text
org.springframework.boot:type=Endpoint,name=Trainingcontrol
org.springframework.boot:name=Trainingcontrol,type=Endpoint
```

The second form may appear when a client prints a canonical name. Do not conclude these are two different MBeans solely because the key order differs.

When programming, use `ObjectName` to represent names and search patterns. The pattern:

```text
org.springframework.boot:type=Endpoint,*
```

finds MBeans in that domain that have property `type=Endpoint` and possibly additional properties. Do not use the path `/actuator/trainingcontrol` as an ObjectName.

### 5.2. Operation Name and Signature Must Match

A JMX invocation must specify:

1. The MBean's ObjectName.
2. The operation name.
3. The parameter values.
4. The parameter type names according to the published signature.

For `rename` in the sample, the parameter type is `java.lang.String`. When encountering primitive types, the JMX signature may use names like `int` instead of `java.lang.Integer`. Do not substitute signatures with what the caller thinks is equivalent; read the metadata.

`MBeanServerConnection.getMBeanInfo` reports attributes and operations. `invoke` executes an operation call; `getAttribute` is used for attributes. Calling the wrong kind of member can fail even when both connection and MBean name are valid. [The MBeanServerConnection API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanServerConnection.html).

### 5.3. Do Not Impose JSON Shapes onto JMX Results

The sample intentionally returns a string for easy comparison. For other endpoints, inspect the published JMX return type and how the tool renders that type. A structured result may be displayed differently from the JSON representation of an HTTP endpoint.

If you need data from a standard JVM MBean, look for the right attribute, such as a memory attribute. If you need to invoke an Actuator operation, look for the right operation. Having both appear in the MBeans tab does not mean they share the same interface.

## 6. Accessing with a JMX-Compatible Java Client

The following example uses the JDK's JMX API, connects locally to the chosen PID, prints names and metadata, and invokes only `status`. It does not call the write operation on its own. This is a way to cross-check results without depending on how JConsole lays out its UI.

The client requires a JDK with the `jdk.attach` module. Run it under an account that has permission to attach to the sample JVM. `VirtualMachine.attach` selects the target process; `startLocalManagementAgent` requests the local agent when no connector address is present yet. [The VirtualMachine API](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.attach/com/sun/tools/attach/VirtualMachine.html).

Create `InspectActuator.java` in a practice directory:

```java
import java.util.Arrays;
import java.util.stream.Collectors;

import com.sun.tools.attach.VirtualMachine;
import javax.management.MBeanOperationInfo;
import javax.management.MBeanServerConnection;
import javax.management.ObjectName;
import javax.management.remote.JMXConnector;
import javax.management.remote.JMXConnectorFactory;
import javax.management.remote.JMXServiceURL;

public class InspectActuator {
    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException("Usage: InspectActuator <target-pid>");
        }
        String address;
        VirtualMachine vm = VirtualMachine.attach(args[0]);
        try {
            address = vm.getAgentProperties()
                    .getProperty("com.sun.management.jmxremote.localConnectorAddress");
            if (address == null) {
                address = vm.startLocalManagementAgent();
            }
        }
        finally {
            vm.detach();
        }

        try (JMXConnector connector = JMXConnectorFactory.connect(new JMXServiceURL(address))) {
            MBeanServerConnection connection = connector.getMBeanServerConnection();
            var names = connection.queryNames(
                    new ObjectName("org.springframework.boot:type=Endpoint,*"), null);
            for (String name : names.stream().map(ObjectName::getCanonicalName).sorted().toList()) {
                System.out.println("MBean: " + name);
            }

            ObjectName target = new ObjectName(
                    "org.springframework.boot:type=Endpoint,name=Trainingcontrol");
            MBeanOperationInfo[] operations = connection.getMBeanInfo(target).getOperations();
            Arrays.sort(operations, java.util.Comparator.comparing(MBeanOperationInfo::getName));
            for (MBeanOperationInfo operation : operations) {
                String signature = Arrays.stream(operation.getSignature())
                        .map(parameter -> parameter.getType())
                        .collect(Collectors.joining(","));
                System.out.println(operation.getName() + "(" + signature + ") -> "
                        + operation.getReturnType());
            }
            Object value = connection.invoke(target, "status", new Object[0], new String[0]);
            System.out.println("status -> " + value);
        }
    }
}
```

Compile and run in PowerShell:

```powershell
javac --add-modules jdk.attach InspectActuator.java
$targetPid = Read-Host "Enter TARGET_PID of the sample application"
java --add-modules jdk.attach InspectActuator $targetPid
```

The sample Spring Boot application must still be running. The client needs only its own class and JDK modules; there is no need to put Spring libraries on the client's classpath.

With a freshly started application and the original configuration, stdout:

```text
MBean: org.springframework.boot:name=Health,type=Endpoint
MBean: org.springframework.boot:name=Trainingcontrol,type=Endpoint
rename(java.lang.String) -> java.lang.String
status() -> java.lang.String
status -> label=demo
```

If the label was changed with JConsole, the last line reflects the current label, for example `status -> label=practice`. The program sorts MBean names and operations before printing so results are easy to compare.

`vm.detach()` releases the attach session. It does not replace closing the JMX connection. The `try-with-resources` block closes `JMXConnector` after reading; the connector address is used only inside the program and need not be printed to logs.

`JMXConnectorFactory.connect` creates a connection from a `JMXServiceURL`; the same `MBeanServerConnection` interface can be used after an appropriate local or remote connection. [The JMXConnectorFactory API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/remote/JMXConnectorFactory.html).

The ObjectName in the client matches the sample's original configuration. If you change the domain, enable unique names, or have custom naming rules, you must locate and select the actual ObjectName before invoking.

## 7. When You Need to Connect from Another Machine

### 7.1. Using a Configured Remote Connector

A PID is not a network address. A PID on a server cannot be entered as a local PID on a personal machine and expected to connect over the network automatically.

In JConsole, choose **Remote Process** and use the connector address provided by the environment. For a typical RMI connector, a JMX service URL has the form:

```text
service:jmx:rmi:///jndi/rmi://app.internal:9010/jmxrmi
```

`app.internal:9010` in the example must be replaced with the actual configured address; it is not an HTTP URL. In this URL structure, the JNDI part points to where the RMI registry is looked up. Connector URLs have their own structure and protocol. [The JMXServiceURL API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/remote/JMXServiceURL.html).

### 7.2. Why Opening One Port Might Still Not Be Enough

With the JDK's built-in RMI agent:

| JVM Property | Role |
| --- | --- |
| `com.sun.management.jmxremote.port` | Registry port where clients look up the connector |
| `com.sun.management.jmxremote.rmi.port` | Fixed port of the RMI connector |
| `java.rmi.server.hostname` | Address advertised in RMI references |

A client may look up the registry successfully and then fail when connecting to the returned connector address/port. NAT, containers, or firewalls must therefore be accounted for on both the lookup path and the subsequent invocation path.

These properties belong to the JVM/agent and are usually passed with `-D` before `-jar`. They are not created merely by `spring.jmx.enabled=true`. Remote connections require authentication and TLS configuration appropriate for the environment, including protecting the registry where applicable. [Remote JMX in JDK 21](https://docs.oracle.com/en/java/javase/21/management/monitoring-and-management-using-jmx-technology.html).

The local practice exercise does not need these ports opened. When going through a tunnel, ensure the address advertised by RMI is also reachable through the tunnel; forwarding only the registry port does not prove the connection path is complete.

### 7.3. “Read-Only” Permission and Read Operations Are Two Concepts

With the JDK agent's default access file, `readonly` permission allows reading attributes and receiving notifications; `readwrite` also allows invoking operations. Therefore, an Actuator operation annotated with `@ReadOperation` can still be rejected by an account that only has `readonly` permission on the connector. Spring's annotation does not alter the connector's permission rules.

Policy must be examined at the JMX layer, not only HTTP endpoint permissions. If a narrow set of operations needs to be allowed, design an appropriate JMX policy instead of granting broad admin privileges to every monitoring account.

Spring Security credentials used for HTTP do not automatically become credentials for the remote JMX agent. Local attach also relies on OS permissions, not a login session on the application's website. This separation explains why HTTP and JMX can yield different authorization outcomes.

## 8. Changing the Domain and Handling MBean Names

In a separate experiment, you can add:

```properties
management.endpoints.jmx.domain=example.training
```

Restart and look in the new domain. The sample name becomes:

```text
example.training:type=Endpoint,name=Trainingcontrol
```

The connection still reaches the same kind of MBeanServer, but a program hardcoding the `org.springframework.boot` domain will no longer find that endpoint.

When one JVM has multiple application contexts causing name collisions, `spring.jmx.unique-names=true` is an option in Spring Boot. Do not enable it and continue assuming an ObjectName has only the two properties `type` and `name`. Inspect registered names and use an appropriate search pattern, then uniquely identify the MBean to invoke. [Customizing MBean names in Spring Boot](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html).

Finding multiple MBeans does not mean you should blindly pick the first element. Cross-check context, domain, and naming properties before sending a write operation.

## 9. Layer-by-Layer Diagnosis

| Symptom | Check First |
| --- | --- |
| Cannot run `jconsole` | Full JDK, PATH, and graphical environment |
| JVM not visible in Local Process | Process still running, matching account, attach permissions, host/namespace environment |
| JVM appears but cannot attach | Attach policy, account, how the process was launched |
| Connected, only JVM MBeans visible | `spring.jmx.enabled`, JMX exposure list, and endpoint existence |
| Endpoint not found in expected domain | Custom domain, unique names, or wrong JVM selected |
| Attributes empty while Operations exist | This may match the contract; read the metadata |
| `InstanceNotFoundException` | ObjectName no longer registered or wrong name used |
| Operation/signature not found | JMX method name, parameter count, and type names in metadata |
| `SecurityException` or operation denied | Connector/JMX permissions, not only HTTP permissions |
| Error from operation body | Input and operation rules; separate from connection errors |
| Remote connects to registry then fails | RMI advertised address, connector port, DNS/NAT/firewall |
| TLS/authentication error | Trust config, certificates, and credentials for the right connector |
| Cannot reconnect after restart | Stale PID/connector; a new connection session is needed |

Notable cases:

- An application running inside a container may have a different PID and permission environment from tools on the host. “Same physical machine” is not enough to assume local attach is available.
- A JVM with attach disabled or a minimal runtime may not support this local workflow.
- Disabling `spring.jmx.enabled` affects only management provided by Spring; it does not mean all standard JVM MBeans vanish.
- Repeatedly guessing wrong parameters does not help distinguish a signature error from a business-rule error. Read metadata first, try one small call, and inspect the result.

When finished, close the tool connection session. If the application has stopped, a disconnected status is normal; it is not evidence that the previous operation failed.

## 10. Practice and Self-Check

Follow in order on the sample application:

1. Start the application and record the current PID.
2. Connect JConsole using that PID and find `Health` and `Trainingcontrol`.
3. Inspect Operations of `Trainingcontrol`, invoke `status`, and receive `label=demo`.
4. Change the label to `practice` via `rename`, then invoke `status` again.
5. Run the Java client; compare canonical names, signatures, and the current label.
6. Restart with domain `example.training` and find the endpoint in the new domain.
7. Restart with `spring.jmx.enabled=false`; distinguish Spring MBeans no longer being exposed from JVM MBeans that may still be present.

Answer for yourself:

- **Is a successful JConsole connection enough to prove an endpoint is exposed?** No. You must locate the exact ObjectName and metadata of the endpoint.
- **Do you need an HTTP controller to learn accessing Actuator over JMX?** No. The sample application has no HTTP server.
- **To call `status`, do you always use getAttribute?** No. In the sample, it is an operation, so `invoke` or the corresponding tool control is used.
- **Are two ObjectNames with different key ordering always two different MBeans?** No. Compare structured names and property values.
- **Can a readonly agent account definitely invoke every ReadOperation?** No. Attribute read permission must be distinguished from operation invoke permission.
- **Can you use the application's port 8080 as the default JMX connection?** No. A configured JMX connector address is required.
- **After changing the domain, does an old client reporting not found necessarily mean a network error?** No. The connection may still be valid while the ObjectName being searched is no longer right.
