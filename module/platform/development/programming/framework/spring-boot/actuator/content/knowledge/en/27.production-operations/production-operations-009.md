# Monitoring Data Collection Capability and Identifying Blind Spots of a Separate Management Port

## 1. Two Questions That Must Not Be Merged into One

When a monitoring board is green, you need to know what it is confirming. "The collector can fetch metrics" differs from "users can call the service". A working management port can supply JVM data while the business port is not accepting connections. Conversely, a broken management port or scrape path can lose data even though the application still handles requests.

**Monitoring data collection capability** means checking the observation path: whether targets to measure are discovered, reachable, parsed in the right format, keeping the right metrics, and delivering data to where queries run. **Blind spots** appear when a good result on that path is used to draw conclusions about a path it never traversed.

In Spring Boot, `server.port` is the application port; `management.server.port` can place Actuator on a different port. Both ports still belong to the same application/JVM, yet do not necessarily pass through the same web infrastructure. The management port can still respond when the main port is not accepting connections. [Spring Boot 3.3: probes on a separate management context](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes).

Mental model to keep:

```text
User path:
  Client → DNS/TLS → proxy or load balancer → business port → business processing

Metrics collection path:
  Prometheus → management network/auth → management port → /actuator/prometheus
             → filter/write data → query backend → dashboards/alerts

External check path:
  HTTP prober → main port or public URL → expected protocol/content result
```

The three paths may share resources yet differ in scope of evidence. No single HTTP 200 proves all three paths are working.

## 2. What Does Each Signal Tell You?

| Signal | Direct evidence | Does not yet prove |
| --- | --- | --- |
| `/actuator/health` returns UP | Configured health components produced that aggregate result | Every business path or public route is healthy |
| Management readiness returns UP | Readiness group on the management port reports ready | Main port is accepting connections |
| `/readyz` on main port returns UP | HTTP passes through main port and readiness group is UP | Every query, transaction, and business path works properly |
| HTTP scrape succeeds | Collector can reach/read the endpoint per configuration | All required metrics remain intact or business data is fresh |
| Prometheus `up=1` | Scrape of that exact target succeeded according to collector | Users can use the service |
| Business probe succeeds | From the prober's location, selected operation meets conditions | All users, network regions, and functions are covered |

`up` is generated by Prometheus per scrape target, not JSON `health.status` automatically converted into a metric by Spring Boot. When a target remains in discovery yet scraping fails, Prometheus records `up=0`. Prometheus also provides `scrape_duration_seconds` and sample counts for diagnostics. [Auto-generated scrape series](https://prometheus.io/docs/concepts/jobs_instances/).

If health is needed as a metric, an explicit conversion or suitable exporter/probe is required. Do not write queries using a metric like `health_status` and assume every Actuator application exports it.

## 3. Analyzing the Collection Path Layer by Layer

### 3.1. Are the Expected Targets Accurate and Complete?

A target missing from the discovery list differs from a target having `up=0`. For example, an instance accidentally dropped by a label filter: Prometheus no longer scrapes it, so a rule checking only `up == 0` may miss it.

Compare the target list against the inventory/deployment source: service, environment, instance, port, and path. Do not use the currently present series count as the sole source for how many instances should exist. When deployments replace instances, which identity counts as stable must also be defined.

### 3.2. Is the Endpoint Reachable and Readable?

Test from the same network location as the collector: hostname, bind address, port, protocol, certificates, authentication, and timeouts. Successful access from a laptop does not prove Prometheus in another network has the same access permissions.

401/403 errors usually require checking credentials/permissions; 404 may come from a wrong base path, wrong port, or an unexposed endpoint. Format errors can come from a login HTML page or proxy response. Do not remove authentication just to make the target turn green.

### 3.3. Does Collected Data Contain the Right Metrics to Monitor?

HTTP 200 and valid metric format are not enough. A name change, label change, or `metric_relabel_configs` can drop the exact series dashboards need while other JVM metrics remain kept.

Compare at least three points: raw endpoint content, post-filter data at the collector, and query results where dashboards read. `scrape_samples_scraped` and `scrape_samples_post_metric_relabeling` help spot sample-count changes, yet do not by themselves prove a specific business metric still exists.

### 3.4. Does Fresh Sample Timestamp Mean Fresh Content?

No. A fixed gauge equal to 1 can be scraped freshly over and over without proving a business job just completed. A sample's timestamp indicates measurement/storage time per collection-path semantics, not by default when source data was last updated successfully.

For periodic jobs, a separate metric representing the last successful completion timestamp may be needed. Update it only after the real work finishes; attempt time or getter invocation time cannot substitute for success time. Clocks, run cadence, and staleness thresholds must be defined together.

If remote write or another storage/query tier exists, metrics present in local Prometheus do not prove downstream dashboards receive fresh data. Verify latency and presence right where alerts evaluate.

## 4. Putting Probes on the Main Port to Close One Blind Spot

For a web application already having Actuator and the Prometheus registry, illustrative `application.yml` configuration:

```yaml
server:
  port: 8080
management:
  server:
    port: 8081
    address: 127.0.0.1
  endpoints:
    web:
      exposure:
        include: health,prometheus
  endpoint:
    health:
      probes:
        enabled: true
        add-additional-paths: true
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState
```

Port 8081 in the example binds to loopback only for lab practice on the same machine. In production, choose a network address/service reachable by the real collector per deployment policy. `127.0.0.1` inside a container is that container's own network namespace; another Prometheus container cannot automatically reach the application container's loopback. [Management port, address, and paths](https://docs.spring.io/spring-boot/3.3/reference/actuator/monitoring.html).

`management.endpoint.health.probes.add-additional-paths=true` exposes liveness/readiness on the main port at `/livez` and `/readyz`. Configure probers to call the main port; enabling the property while continuing to call only 8081 does not change observation scope.

The two groups in the example only read availability state. They do not automatically run every business path. Putting a dependency into readiness must follow the application's serving requirements; do not put external systems into liveness just to increase the number of checked items.

Main port, management port, proxy, and security policies can take different paths. Verify in practice that probers reach `/readyz` and are not redirected to a login page. Expose only needed endpoints; a separate port does not substitute for authentication and network controls.

### 5.2. `src/test/java/example/ManagementPortTest.java`

```java
package example;

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;

import com.fasterxml.jackson.databind.ObjectMapper;
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import org.apache.catalina.connector.Connector;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.parallel.Execution;
import org.junit.jupiter.api.parallel.ExecutionMode;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.SpringBootConfiguration;
import org.springframework.boot.autoconfigure.EnableAutoConfiguration;
import org.springframework.boot.test.autoconfigure.actuate.observability.AutoConfigureObservability;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalManagementPort;
import org.springframework.boot.test.web.server.LocalServerPort;
import org.springframework.boot.web.embedded.tomcat.TomcatWebServer;
import org.springframework.boot.web.context.WebServerInitializedEvent;
import org.springframework.context.ApplicationListener;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Import;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@SpringBootTest(
    classes = ManagementPortTest.TestApplication.class,
    webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT,
    properties = {
        "server.address=127.0.0.1",
        "management.server.address=127.0.0.1",
        "management.server.port=0",
        "management.endpoints.web.exposure.include=health,prometheus",
        "management.endpoint.health.probes.enabled=true",
        "management.endpoint.health.probes.add-additional-paths=true",
        "management.endpoint.health.group.liveness.include=livenessState",
        "management.endpoint.health.group.readiness.include=readinessState"
    }
)
@AutoConfigureObservability
@Execution(ExecutionMode.SAME_THREAD)
class ManagementPortTest {
    static final AtomicBoolean rejectOrders = new AtomicBoolean();
    static final HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(1)).build();

    @SpringBootConfiguration
    @EnableAutoConfiguration
    @Import({OrdersController.class, ServerReferences.class})
    static class TestApplication {
        @Bean
        AtomicInteger collectionMarker(MeterRegistry registry) {
            AtomicInteger marker = new AtomicInteger(1);
            Gauge.builder("lab.collection.marker", marker, AtomicInteger::get)
                .register(registry);
            return marker;
        }
    }

    @RestController
    static class OrdersController {
        @GetMapping("/orders/check")
        ResponseEntity<String> check() {
            return rejectOrders.get()
                ? ResponseEntity.status(503).body("orders-unavailable")
                : ResponseEntity.ok("orders-ok");
        }
    }

    static class ServerReferences
            implements ApplicationListener<WebServerInitializedEvent> {
        final Map<Integer, TomcatWebServer> servers = new ConcurrentHashMap<>();

        @Override
        public void onApplicationEvent(WebServerInitializedEvent event) {
            if (event.getWebServer() instanceof TomcatWebServer server) {
                servers.put(server.getPort(), server);
            }
        }

        Connector connector(int port) {
            TomcatWebServer server = servers.get(port);
            if (server == null) {
                throw new IllegalStateException("No test server at port " + port);
            }
            return server.getTomcat().getConnector();
        }
    }

    @LocalServerPort int applicationPort;
    @LocalManagementPort int managementPort;
    @Autowired ServerReferences references;
    @Autowired ObjectMapper json;

    @AfterEach
    void restoreBusinessMode() {
        rejectOrders.set(false);
    }

    HttpResponse<String> get(int port, String path) throws Exception {
        var request = HttpRequest.newBuilder(
                URI.create("http://127.0.0.1:" + port + path))
            .timeout(Duration.ofSeconds(2)).GET().build();
        return client.send(request, HttpResponse.BodyHandlers.ofString());
    }

    void assertReady(int port, String path) throws Exception {
        var response = get(port, path);
        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(json.readTree(response.body()).path("status").asText())
            .isEqualTo("UP");
    }

    void assertMetricsReadable() throws Exception {
        var response = get(managementPort, "/actuator/prometheus");
        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.body()).contains("lab_collection_marker");
    }

    @Test
    void separatePortsExposeDifferentEvidence() throws Exception {
        assertThat(applicationPort).isNotEqualTo(managementPort);
        assertReady(managementPort, "/actuator/health/readiness");
        assertReady(applicationPort, "/readyz");
        assertMetricsReadable();
        var response = get(applicationPort, "/orders/check");
        assertThat(response.statusCode()).isEqualTo(200);
        assertThat(response.body()).isEqualTo("orders-ok");
    }

    @Test
    void mainConnectorFailureDoesNotImplyManagementFailure() throws Exception {
        Connector connector = references.connector(applicationPort);
        connector.stop();
        try {
            assertThatThrownBy(() -> get(applicationPort, "/readyz"))
                .isInstanceOf(IOException.class);
            assertReady(managementPort, "/actuator/health/readiness");
            assertMetricsReadable();
        } finally {
            connector.setPort(applicationPort);
            connector.start();
        }
        assertReady(applicationPort, "/readyz");
        assertThat(get(applicationPort, "/orders/check").statusCode()).isEqualTo(200);
    }

    @Test
    void managementFailureDoesNotImplyBusinessFailure() throws Exception {
        Connector connector = references.connector(managementPort);
        connector.stop();
        try {
            assertThatThrownBy(() -> get(managementPort, "/actuator/prometheus"))
                .isInstanceOf(IOException.class);
            assertReady(applicationPort, "/readyz");
            assertThat(get(applicationPort, "/orders/check").statusCode()).isEqualTo(200);
        } finally {
            connector.setPort(managementPort);
            connector.start();
        }
        assertMetricsReadable();
    }

    @Test
    void mainPortReadinessDoesNotProveEveryBusinessRouteWorks() throws Exception {
        rejectOrders.set(true);
        var response = get(applicationPort, "/orders/check");
        assertThat(response.statusCode()).isEqualTo(503);
        assertThat(response.body()).isEqualTo("orders-unavailable");
        assertReady(applicationPort, "/readyz");
        assertReady(managementPort, "/actuator/health/readiness");
        assertMetricsReadable();
        rejectOrders.set(false);
        assertThat(get(applicationPort, "/orders/check").statusCode()).isEqualTo(200);
    }
}
```

In the directory containing `pom.xml`:

```shell
mvn test
```

Maven supplies the Spring/JUnit classpath; do not run the test file with standalone `javac`. The report `target/surefire-reports/example.ManagementPortTest.txt` should contain the result:

```text
Tests run: 4, Failures: 0, Errors: 0, Skipped: 0
```

### 5.4. Reading the Evidence Accurately

| Test | Verified result |
| --- | --- |
| Both ports healthy | Different ports; readiness UP on both paths; marker metric present; business endpoint returns expected content |
| Stop main port connector | `/readyz` unreachable; management readiness still UP and metric endpoint still readable; restoring main port works again |
| Stop management connector | Metric endpoint unreachable; main port still serves readiness and business requests; restoring makes metrics readable again |
| A business route returns 503 | Readiness on both ports stays UP and metrics remain present; clearing the failure restores 200 on the business route |

`@AutoConfigureObservability` ensures tests load real metric-exporting registries instead of accidentally using only an in-memory registry. HTTP tests read the Prometheus registry scrape format, yet there is still no Prometheus server confirming data was written to storage. [Metrics in Spring Boot tests](https://docs.spring.io/spring-boot/3.3/reference/testing/spring-boot-applications.html#testing.spring-boot-applications.metrics).

`ServerReferences` collects servers from initialization events and selects connectors by port. When restarting a connector, the test assigns the actual allocated port so a new random port does not break the HTTP target. The connector API is fault-injection support solely for the Tomcat lab, not a control endpoint exposed in production. [Tomcat Connector API](https://tomcat.apache.org/tomcat-10.1-doc/api/org/apache/catalina/connector/Connector.html).

Gauge `lab.collection.marker` is always registered to test whether a known datum appears at the endpoint. It is not a business heartbeat and does not prove business data is fresh. The `rejectOrders` flag intentionally affects only one route, so the last test shows a probe on the main port still has limited coverage.

## 6. Adding External Checks with Blackbox Exporter

In-JVM checks help find causes; external checks help observe a real call path. Blackbox Exporter receives requests at `/probe`, calls the target itself, and returns metrics such as `probe_success`. Prometheus scrapes those results. [Multi-target exporter pattern](https://prometheus.io/docs/guides/multi-target-exporter/).

### 6.1. `blackbox.yml`

Configuration illustrating two checks: readiness accepts HTTP 200; business endpoint must return HTTP 200 and the exact string `orders-ok`.

```yaml
modules:
  http_ready:
    prober: http
    timeout: 3s
    http:
      method: GET
      valid_status_codes: [200]
      follow_redirects: false
  http_orders:
    prober: http
    timeout: 3s
    http:
      method: GET
      valid_status_codes: [200]
      follow_redirects: false
      fail_if_body_not_matches_regexp:
        - '^orders-ok$'
```

`follow_redirects: false` prevents a redirect to another page from being counted as success for this contract. The business module checks body content as well, so an HTML page returning 200 does not satisfy the condition. These are Blackbox Exporter HTTP configuration fields; verify against the version in use. [Blackbox Exporter 0.26.0 configuration](https://github.com/prometheus/blackbox_exporter/blob/v0.26.0/CONFIGURATION.md).

The readiness module here only checks HTTP status code under default health mapping. If an application adjusts HTTP mapping or needs to assert specific content, adjust the check accordingly. A check must not be considered a body check if a new config only constrains status codes.

### 6.2. `prometheus.yml`

The sample below is for an application running statically on 8080/8081 on the same machine, with a business check route matching the lab contract. It does not point directly to JUnit's random ports; the test application exited when `mvn test` finished. When applying to a real service, use the service's own address and representative read operation.

```yaml
global:
  scrape_interval: 15s
  scrape_timeout: 4s
  evaluation_interval: 30s
scrape_configs:
  - job_name: orders-management
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ["127.0.0.1:8081"]
        labels:
          service: orders
          env: lab

  - job_name: orders-readyz
    metrics_path: /probe
    params:
      module: [http_ready]
    static_configs:
      - targets: ["http://127.0.0.1:8080/readyz"]
        labels:
          service: orders
          env: lab
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: 127.0.0.1:9115

  - job_name: orders-business
    metrics_path: /probe
    params:
      module: [http_orders]
    static_configs:
      - targets: ["http://127.0.0.1:8080/orders/check"]
        labels:
          service: orders
          env: lab
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: 127.0.0.1:9115

  - job_name: blackbox-self
    static_configs:
      - targets: ["127.0.0.1:9115"]
        labels:
          env: lab
```

The three relabel steps of each probe job play distinct roles:

1. Move the target URL into the `target` parameter of the `/probe` request.
2. Keep the target URL in the `instance` label to know which target the result belongs to.
3. Rewrite the address Prometheus actually scrapes to Blackbox Exporter at 9115.

If only `__address__` is replaced without passing target, the prober does not automatically know which business URL to call. If `instance` is kept as the exporter's address for every target, tracing alerts becomes confusing.

Run commands once both tools are installed and the lab application is serving the corresponding targets:

```shell
blackbox_exporter --config.file=blackbox.yml --web.listen-address=127.0.0.1:9115
prometheus --config.file=prometheus.yml --web.listen-address=127.0.0.1:9090
```

Run each process in a separate terminal; on Windows use the corresponding `.exe` files. Loopback addresses illustrate running on the same machine. If using containers or other hosts, configure targets according to each process's actual network location. Allow only identified components to access management endpoints and probe control endpoints.

You can validate Prometheus file syntax before running:

```shell
promtool check config prometheus.yml
```

Output with promtool 3.2.1:

```text
Checking prometheus.yml
 SUCCESS: prometheus.yml is valid prometheus config file syntax
```

This command does not validate `blackbox.yml` contents, test the network, or prove targets are serving. Verify both exporter modules and received data when the system actually runs.

### 6.3. Reading `up` and `probe_success` Properly

The two expressions below belong to the same job yet answer two questions:

```promql
up{job="orders-business", env="lab"}
```

```promql
probe_success{job="orders-business", env="lab"}
```

| Probe job `up` | `probe_success` | Interpretation |
| --- | --- | --- |
| 1 | 1 | Prometheus fetched the result and the target check succeeded |
| 1 | 0 | Exporter returned metrics, yet the target failed the check contract |
| 0 | No reliable fresh sample | Probe result collection path is failing; insufficient evidence about the target |
| No series | No series | Check discovery, data history, and inventory source; do not default to "healthy" |

For example, if the main port stops accepting connections: the exporter can still return HTTP 200 containing `probe_success=0`. Then `up` for the probe job can still be 1. This is not a contradiction; the scrape succeeded while the business check failed. [Probe results and exporter's own metrics](https://github.com/prometheus/blackbox_exporter/tree/v0.26.0).

The `blackbox-self` job collects metrics of the exporter itself; it does not replace `orders-business`. Similarly, a green `orders-management` job does not replace `orders-readyz`.

## 7. Monitoring Data Completeness and Freshness

### 7.1. Distinguish Unscrapeable Targets from Disappeared Targets

Target still tracked by Prometheus yet scrape failed:

```promql
up{job="orders-management", env="lab"} == 0
```

No `up` samples for the job in a 5m window:

```promql
absent_over_time(up{job="orders-management", env="lab"}[5m])
```

The two expressions are not equivalent. `absent_over_time` checks sample presence in the window, including samples with value 0. It does not turn a failed scrape into "no data". [absent_over_time semantics](https://prometheus.io/docs/prometheus/latest/querying/functions/#absent_over_time).

The job-wide missing-sample expression does not detect a single missing instance if other instances still have samples. Compare each expected identity against an inventory source. On fresh startup with no prior history, the missing-sample expression can evaluate true immediately; the 5m window is not a mandatory 5-minute wait timer.

### 7.2. Checking a Metric with a Presence Contract

For the gauge always registered in the lab:

```promql
absent_over_time(lab_collection_marker{
  job="orders-management", env="lab"
}[5m])
```

If `up=1` yet this expression returns a result, check whether the right application is being scraped, whether the marker is registered, whether names/labels changed, and whether metric filters dropped it. The marker only confirms a marker series passes through the pipeline; it does not prove all other business metrics are retained.

Do not apply such a presence condition mechanically to an HTTP series that appears only after the first request. First know whether that metric is registered at startup or created only when activity occurs.

A useful experiment is intentionally dropping `lab_collection_marker` via metric relabeling in a test environment. The raw endpoint still has the marker and scrapes can still succeed, yet queries in Prometheus no longer see fresh marker data. The lesson is to verify post-filter data, not merely load the endpoint in a browser.

### 7.3. Reading Sample Age with Boundaries

Age of the marker sample visible to the query:

```promql
time() - timestamp(lab_collection_marker{
  job="orders-management", env="lab"
})
```

The result is the number of seconds between evaluation time and the selected sample's timestamp, not "seconds since the last successful transaction". If the series no longer appears, the expression may also return no element; therefore check missing data separately.

A continuously scraped gauge will have fresh timestamps even if the source value stays frozen. Knowing whether a business source updates successfully requires a metric with matching semantics, plus checking clocks, job cadence, and lag. Do not rename a static marker to heartbeat and treat the problem as solved.

When evaluating collection quality, inspect target status, scrape duration relative to timeout, and sample count together. Scrape duration approaching the 4s budget of the illustrative config is a signal to investigate; real operational thresholds must account for load, history, and system limits.

## 8. Placing Checks at the Right Network Location

Probing from the same Pod to 8080 verifies part of the main port yet can bypass public DNS, TLS, ingress, access policies, and load balancers. Probing via a public URL traverses more components yet does not immediately identify which instance failed.

Define each location's purpose:

| Check location | Useful scope | What remains uncovered |
| --- | --- | --- |
| Same process/host to management | Internal diagnostics and data export | User path and main-port infrastructure |
| Internal network to main port | Connectivity and readiness on main port | May bypass public ingress/TLS |
| From user-adjacent network via service URL | External access path from that location | Other network regions/users and all other operations |
| Synthetic operation with result check | One selected business flow | Functionality not included in the scenario |

A lightweight GET returning availability does not test correctness of write operations or multi-step transactions. Choose checks that are valuable yet have controlled cost. If a write operation must be run, use test data/accounts and mechanisms preventing repeated side effects.

In a multi-instance system, the management port has `instance` like `host:8081` whereas probes may have `instance` as a URL. Do not join them solely on `instance` and expect automatic matching. Choose a common identity such as environment/service/instance, or state clearly that checks operate service-wide. Joining solely by `service` can misattribute evidence from instance A to instance B.

## 9. Action Matrix When Signals Differ

| Management scrape | Main-port/business probe | Investigation direction |
| --- | --- | --- |
| Good | Good | Continue checking completeness, freshness, and coverage; do not assume every function works |
| Good | Main port failing | Check main-port connector, network path, proxy, and serving resources; surviving metrics provide useful diagnostic evidence |
| Good | Readiness good yet business failing | Check route contract, data, and business dependencies; expand check scope as needed |
| Failing | Business good | Investigate collection pipeline: address, port, endpoint, auth, TLS, timeout, and exporter |
| Failing or missing | Business also failing | Prioritize user-impact mitigation, use independent observation paths, and determine shared incident scope |
| Good yet missing selected metrics | Probe may still be good | Check metric registration, label/name changes, relabeling, and downstream storage path |

Short investigation procedure:

1. Record target, environment, instance, path, and start time. Confirm you are viewing data from the actual evaluation point.
2. Check whether targets are still discovered and counts match inventory.
3. From the collector's location, distinguish connection, HTTP, certificate, permission, and data-format errors. Do not test only from the most convenient location.
4. Compare management readiness, main-port probes, and a safe business operation. Do not use one signal to unconditionally negate the other two.
5. Cross-check raw endpoint, post-filter data, and storage/query-backend results. Verify samples are fresh and understand source timestamps accurately.
6. After changes, re-verify each previously failing path, target/metric completeness, and business logic. A dashboard turning green again is insufficient if it turned green because an expression has no data left.

A separate management port separates access paths and preserves diagnostics during certain incidents. It does not create an independent JVM: out-of-memory, CPU saturation, or shared resource failures can still affect both ports. Do not design redundant monitoring paths assuming the two ports are completely independent.

## 10. Testing Blind Spots Before Relying on Dashboards

Plan fault injection in a test environment, with rollback conditions and recovery evidence:

- Stop or block only the main port: confirm management can remain green while main-port probes detect the failure.
- Block only the scrape path: confirm business logic still runs and collection-quality signals report the error.
- Return 503 or wrong body on a business route: confirm probes have a deep enough contract to notice, even while readiness stays UP.
- Drop one target from discovery: check inventory source and missing-target condition.
- Drop one metric after scraping: check data-contract alerts, not just `up`.
- Make a data-updating job stop succeeding while the endpoint still responds: check semantic metric for last successful run.
- Independently check the monitoring system: if the rule-evaluation node stops working, another path must detect the loss of observability.

Tests must state which layer they prove. The four JUnit tests in this article verify two-port HTTP and one sample route; they do not by themselves prove Kubernetes network config, production collectors, remote write, or notification delivery paths.

## 11. Self-Verification Exercises

1. Disable `add-additional-paths` in the experiment and predict which assertions will no longer hold. Explain why calling management readiness cannot replace `/readyz` on the main port.
2. Keep readiness UP while changing the business route's response body. Compare a probe checking only HTTP 200 with a probe checking the body as well.
3. Add multiple instances with stable labels and design an expected-target reconciliation check. Show that the whole-job missing rule does not detect every individually lost instance.
4. Compare data before and after metric relabeling. Give a scenario where `up=1` yet the business dashboard loses data.
5. Design a metric representing the last successful completion of a periodic job. Define update timing, units, lag threshold, and missing-sample condition.

Evaluate serving health and observability health with separate evidence, then combine them within the right scope. In doing so, a separate management port becomes a useful diagnostic source without creating a false sense of security about the path users actually take.
