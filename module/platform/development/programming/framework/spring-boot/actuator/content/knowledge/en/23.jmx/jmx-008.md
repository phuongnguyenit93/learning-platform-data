# Controlling Remote JMX Connections, Authentication, and Protecting Management Data

JMX (Java Management Extensions) enables observing and managing a Java process through managed objects called MBeans. When you open remote JMX, you open an access path into the internals of the JVM: threads, memory, configuration, and management operations registered by the application or libraries. A protection design must answer four questions: who is allowed to connect, where the connection travels, how data is protected, and what the caller is permitted to do after connecting.

This lesson uses Spring Boot 3.3.x and JDK 21 as its baseline. The hands-on part uses APIs built into JDK 21 to separate connection security verification from Spring Boot application startup.

## 1. Distinguishing MBeans, Actuator, and Remote Connections

Picture three components:

- **MBeanServer** is the hub holding MBeans inside a Java process.
- **Actuator JMX** registers Spring Boot's management endpoints as MBeans in the appropriate MBeanServer.
- **JMX remote connector** is the bridge allowing a program in another process or machine to access an MBeanServer; this lesson examines the JDK-provided connector using RMI (Remote Method Invocation).

Having an MBean does not mean a network port is open. Conversely, opening the JVM's connector does not expose only Actuator endpoints: a connector attached to the platform MBeanServer can see both JVM MBeans and any other MBeans registered there.

In Spring Boot 3.3, `spring.jmx.enabled=true` enables Spring's JMX support; this property does not by itself create a secure remote JMX configuration. Managing MBeans provided by other libraries can also be independent of this property. [The Spring Boot 3.3 JMX documentation](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html).

For example, these are two distinct access paths:

```text
Browser or HTTP client
  -> HTTPS /actuator/...
  -> Spring Security filter chain
  -> Actuator HTTP

JMX client
  -> RMI registry
  -> JMX/RMI connector
  -> connector authentication and authorization
  -> MBeanServer
```

A `SecurityFilterChain` requiring login for `/actuator/**` does not protect the JMX/RMI path. Configuring HTTPS via `server.ssl.*` does not configure TLS for the JDK's management agent either. Each access path must be verified using its own protocol.

## 2. Choosing the Connection Path Before Opening Ports

If you only need to inspect the JVM directly on the machine running the application, prefer local process attachment using JDK tools and an appropriate OS account. There is no need to enable a remote management port just to view memory graphs on the same host. Permissions on the account running the JVM form an important part of the security boundary here.

When remote management is genuinely needed, choose a dedicated management network, VPN, or identity-controlled tunnel; restrict connection sources with firewalls. Separate read accounts from control accounts. Placing the service inside an internal network narrows exposure, yet authentication and encryption are still needed for the connector.

### 2.1. Why Does RMI Usually Need Two Ports?

With the common address form:

```text
service:jmx:rmi:///jndi/rmi://jmx.internal.example:9010/jmxrmi
```

the client performs two steps:

1. Connect to the registry on port 9010 to fetch the remote proxy object, called an RMI stub.
2. Use the address and port embedded in the stub to connect to the actual connector.

This address structure uses the registry as a lookup directory; management traffic then follows the returned stub. [The JMX/RMI connector specification in JDK 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.management.rmi/javax/management/remote/rmi/package-summary.html).

Explicitly setting both `com.sun.management.jmxremote.port=9010` and `com.sun.management.jmxremote.rmi.port=9011` gives the deployment a deterministic port pair. Without pinning the connector's RMI port, the JDK may allocate a dynamic port, making firewalls or tunnels harder to control.

Two JVM properties must be distinguished:

| JVM Property | Meaning |
| --- | --- |
| `com.sun.management.jmxremote.host` | Local network interface address on which the management agent listens |
| `java.rmi.server.hostname` | Hostname or address advertised in RMI objects for clients to connect back to |

Setting `java.rmi.server.hostname=127.0.0.1` does not substitute for restricting the listening address. Inside containers, a client also cannot reach an internal IP recorded in the stub merely because the registry port was mapped outward. Registry, connector, and advertised address must all be verified. Listening ports and addresses are handled separately in [OpenJDK 21's management agent](https://github.com/openjdk/jdk21u/blob/master/src/jdk.management.agent/share/classes/sun/management/jmxremote/ConnectorBootstrap.java).

If using an SSH tunnel with two ports, forward both ports and ensure the address inside the stub makes sense from the client side. The loopback example in the hands-on section fits local endpoints of a tunnel; it is not a configuration for every NAT layout. A tunnel also does not remove the need for operation authorization on the MBeanServer.

## 3. Narrowing Actuator Data Registered over JMX

In an application that already includes `spring-boot-starter-actuator`, the following Spring Boot 3.3 configuration selects only the `health` endpoint for JMX:

```yaml
spring:
  jmx:
    enabled: true

management:
  endpoints:
    jmx:
      exposure:
        include: health
  endpoint:
    health:
      show-details: never
```

This is a configuration snippet for a Spring Boot application, not a standalone runnable program. The endpoint must still be enabled and meet its initialization conditions. The `management.endpoints.jmx.exposure.*` properties select Actuator endpoints for the JMX channel; HTTP endpoint selection sits in a separate configuration group.

Include only the endpoints that are genuinely needed. For instance, enabling `env`, `configprops`, `beans`, `mappings`, or `loggers` wholesale can expose configuration, application structure, or control capabilities on the management path. Do not use `include: "*"` as a fix for missing MBeans.

In particular, in Spring Boot 3.3, `show-values=when-authorized` does not establish a JMX role-based barrier as many infer from HTTP: for JMX endpoints, all users are treated as authorized in that check. If raw values are not needed, keep `show-values=never` on endpoints supporting that setting while restricting exposure. [Actuator 3.3 exposure and sensitive value sanitization settings](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html).

If you want no Actuator endpoints registered over JMX, use the alternative configuration:

```yaml
management:
  endpoints:
    jmx:
      exposure:
        exclude: "*"
```

That configuration does not close a remote connector enabled via JVM options. Likewise, setting `spring.jmx.enabled=false` is not proof that every JVM JMX port is closed. To stop remote management, remove or stop the connector itself and verify the process's network state.

## 4. Identity Authentication and Authorization Are Two Separate Tasks

**Authentication** answers who is connecting. **Authorization** decides how that identity may read attributes, invoke operations, or modify MBeans.

With the JDK's standard management agent, a password file and an access file can be used for test environments. An identity must have matching entries on both sides. Example access file:

```properties
monitorRole readonly
```

The name `monitorRole` is a name chosen in this configuration; the word “monitor” itself grants no privilege. Privileges come from the value `readonly` and the connector's access controller.

- `readonly` allows reading attributes and performing observation actions permitted by the access controller, but does not allow invoking arbitrary MBean operations.
- `readwrite` adds permission to write attributes and invoke operations. This is a broad privilege, not “write only one desired setting.” Permissions to create or unregister MBeans have additional syntax; do not add them without a clear need.

The standard access file is not a fine-grained policy per `ObjectName` and per method. If you need to allow one specific operation while denying others, design an appropriate delegation mechanism such as a request filter on the connector or an `MBeanServerForwarder`; do not solve it by switching every account to `readwrite`. A forwarder can inspect and reject requests before forwarding them to the MBeanServer. [Request access control mechanism in OpenJDK](https://github.com/openjdk/jdk21u/blob/master/src/java.management/share/classes/com/sun/jmx/remote/security/MBeanServerAccessController.java).

### 4.1. Business-Level “Read” Is Not Necessarily JMX Attribute Read

An Actuator endpoint with a data-reading operation can still be exposed as a JMX operation and invoked by clients via `MBeanServerConnection.invoke(...)`. In the standard management agent's permission model, invoking an operation can be rejected for a `readonly` account.

Therefore, an account that can read `java.lang:type=Runtime` yet cannot invoke an Actuator operation is not necessarily hitting a password or TLS error. Inspect the MBean's metadata and verify whether the client uses `getAttribute` or `invoke`. These two APIs serve different purposes. [The JDK 21 MBeanServerConnection API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanServerConnection.html).

Do not elevate permissions merely to make a test pass. First verify whether the user genuinely needs that operation or whether a more suitable metrics channel fits better. Operational needs requiring fine-grained permissions call for an intentional management design.

## 5. Protecting Both the Registry and Management Transport with TLS

TLS protects confidentiality and integrity of data in transit. In mutual TLS, also called mTLS, both server and client present certificates for the peer to verify.

- **Keystore** holds the side's own private key and certificate.
- **Truststore** holds certificates or CAs that the side agrees to trust.

The server needs the server's private key; clients do not need a copy of that private key to connect. When mTLS is required, the client has its own private key and certificate; the server is configured to trust the client's certificate or issuing CA. [TLS fundamentals and keystores in JSSE](https://docs.oracle.com/en/java/javase/21/security/java-secure-socket-extension-jsse-reference-guide.html).

With the JDK management agent, check all three options:

```properties
com.sun.management.jmxremote.ssl=true
com.sun.management.jmxremote.registry.ssl=true
com.sun.management.jmxremote.ssl.need.client.auth=true
```

Enabling TLS on the connector while leaving the registry unencrypted leaves the initial lookup exposed. JDK documentation warns that a spoofed registry could redirect clients to an untrusted connector to capture credentials. The configuration in this lesson secures the registry and requires client certificates while keeping account authentication enabled. [JDK 21 remote JMX security guide](https://docs.oracle.com/en/java/javase/21/management/monitoring-and-management-using-jmx-technology.html).

A client looking up a TLS-protected registry must use the appropriate socket factory. Adding a truststore alone while still querying the registry over plain sockets can fail before login even starts. The Java example below configures `com.sun.jndi.rmi.factory.socket` with `SslRMIClientSocketFactory`. This class uses the client JVM's default SSL settings, including truststore and keystore when the server requires a client certificate. [The SslRMIClientSocketFactory API](https://docs.oracle.com/en/java/javase/21/docs/api/java.rmi/javax/rmi/ssl/SslRMIClientSocketFactory.html).

Also distinguish trusting a certificate chain from verifying the exact target server identity. Do not assume every RMI client verifies hostnames like an HTTPS client. The lab trusts only the specific server certificate you generated yourself. When moving to a shared CA, verify the client/tool's identity-verification policy and trusted CA scope; do not disable certificate checks to work around connection errors.

## 6. Practice: mTLS, Passwords, and Readonly Permissions on Loopback

The goal is to prove four things: the protected connection works; reading attributes is allowed; invoking operations is blocked; wrong credentials or certificates cannot connect.

Use JDK 21, a fresh test directory, and two terminals on the same machine. The multi-step commands below use Bash on Linux/macOS; the Java code and `.args` files work on Windows when invoking the corresponding JDK tools. On Windows, replace the `chmod` step with ACLs granting access to the password file only to the account running the JVM; the management agent may refuse to start if other accounts can read this file.

Passwords starting with `LabOnly-` in this lesson are public test data strictly for the local lab. Do not reuse them in real systems. Seven-day self-signed certificates keep the experiment self-contained and do not replace certificate issuance processes in production environments.

### 6.1. Generating Private Keys and Trust Relationships

Create a directory and run all subsequent commands inside it:

```bash
umask 077
mkdir jmx-security-lab
cd jmx-security-lab

keytool -genkeypair -alias server -keyalg RSA -keysize 2048 -validity 7 -dname "CN=localhost" -ext "SAN=dns:localhost,ip:127.0.0.1" -storetype PKCS12 -keystore server.p12 -storepass LabOnly-271-store -keypass LabOnly-271-store
keytool -exportcert -alias server -keystore server.p12 -storepass LabOnly-271-store -rfc -file server.crt

keytool -genkeypair -alias client -keyalg RSA -keysize 2048 -validity 7 -dname "CN=jmx-lab-client" -storetype PKCS12 -keystore client.p12 -storepass LabOnly-271-store -keypass LabOnly-271-store
keytool -exportcert -alias client -keystore client.p12 -storepass LabOnly-271-store -rfc -file client.crt

keytool -importcert -noprompt -alias client -file client.crt -storetype PKCS12 -keystore server-trust.p12 -storepass LabOnly-271-store
keytool -importcert -noprompt -alias server -file server.crt -storetype PKCS12 -keystore client-trust.p12 -storepass LabOnly-271-store
```

As a result, the server has `server.p12` and trusts the client certificate via `server-trust.p12`; the client has `client.p12` and trusts the server via `client-trust.p12`. The `-noprompt` option is appropriate here only because you just created and control the exact certificate files being imported; for externally received certificates, verify source and fingerprint before trusting.

### 6.2. Creating Identity and Permissions

Create `jmxremote.password`:

```properties
monitorRole LabOnly-271-monitor
```

Create `jmxremote.access`:

```properties
monitorRole readonly
```

On Linux/macOS, restrict file permissions:

```bash
chmod 600 jmxremote.password jmxremote.access server.p12 client.p12 server-trust.p12 client-trust.p12
```

Do not commit password files, private keys, or argfiles containing passwords to Git. In JDK 21, the management agent has a mechanism to hash passwords in the file when conditions allow; do not rely on that to relax file permissions or treat initial configuration copies as public data. OpenJDK's configuration template describes the `com.sun.management.jmxremote.password.toHashes` property. [OpenJDK 21 management agent configuration](https://github.com/openjdk/jdk21u/blob/master/src/jdk.management.agent/share/conf/management.properties).

### 6.3. Creating a Program to Keep the JVM Alive

Save as `JmxLab.java`:

```java
import java.util.concurrent.CountDownLatch;

public class JmxLab {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("READY");
        new CountDownLatch(1).await();
    }
}
```

The program does not create a connector in Java code. The management agent is enabled via JVM startup options. `CountDownLatch` keeps the process alive to allow connection tests.

Create `server.args`, one option per line:

```text
-Dcom.sun.management.jmxremote.port=9010
-Dcom.sun.management.jmxremote.rmi.port=9011
-Dcom.sun.management.jmxremote.host=127.0.0.1
-Djava.rmi.server.hostname=127.0.0.1
-Dcom.sun.management.jmxremote.authenticate=true
-Dcom.sun.management.jmxremote.password.file=jmxremote.password
-Dcom.sun.management.jmxremote.access.file=jmxremote.access
-Dcom.sun.management.jmxremote.ssl=true
-Dcom.sun.management.jmxremote.registry.ssl=true
-Dcom.sun.management.jmxremote.ssl.need.client.auth=true
-Djavax.net.ssl.keyStore=server.p12
-Djavax.net.ssl.keyStoreType=PKCS12
-Djavax.net.ssl.keyStorePassword=LabOnly-271-store
-Djavax.net.ssl.trustStore=server-trust.p12
-Djavax.net.ssl.trustStoreType=PKCS12
-Djavax.net.ssl.trustStorePassword=LabOnly-271-store
```

Relative paths are resolved from the working directory when running the command. These are JVM properties, not keys placed directly inside `application.yml`. When running a packaged Spring Boot application, the same group of JVM options can be placed before `-jar`, such as `java @server.args -jar application.jar`, using your actual JAR name.

Restricting to loopback in this example is intentional. When deploying truly remotely, redesign listening address, advertised address, certificates, and network rules together.

### 6.4. Creating the Client and Testing Permissions

Save as `SecureJmxProbe.java`:

```java
import java.util.HashMap;
import java.util.Map;
import javax.management.MBeanServerConnection;
import javax.management.ObjectName;
import javax.management.remote.JMXConnector;
import javax.management.remote.JMXConnectorFactory;
import javax.management.remote.JMXServiceURL;
import javax.rmi.ssl.SslRMIClientSocketFactory;

public class SecureJmxProbe {
    public static void main(String[] args) throws Exception {
        String user = System.getenv("JMX_USER");
        String password = System.getenv("JMX_PASSWORD");
        if (user == null || password == null) {
            throw new IllegalArgumentException("Set JMX_USER and JMX_PASSWORD");
        }
        String url = args.length == 0
                ? "service:jmx:rmi:///jndi/rmi://127.0.0.1:9010/jmxrmi"
                : args[0];
        Map<String, Object> environment = new HashMap<>();
        environment.put(JMXConnector.CREDENTIALS, new String[] {user, password});
        environment.put("com.sun.jndi.rmi.factory.socket",
                new SslRMIClientSocketFactory());

        try (JMXConnector connector = JMXConnectorFactory.connect(
                new JMXServiceURL(url), environment)) {
            MBeanServerConnection connection = connector.getMBeanServerConnection();
            ObjectName runtime = new ObjectName("java.lang:type=Runtime");
            System.out.println("connected=true");
            System.out.println("runtimeMBean=" + connection.isRegistered(runtime));
            Object vmName = connection.getAttribute(runtime, "VmName");
            System.out.println("readAttribute=" + (vmName instanceof String));
            try {
                connection.invoke(new ObjectName("java.lang:type=Threading"),
                        "findDeadlockedThreads", new Object[0], new String[0]);
                System.out.println("invoke=ALLOWED");
            } catch (SecurityException denied) {
                System.out.println("invoke=DENIED");
            }
        }
    }
}
```

The client reads credentials from environment variables instead of hardcoding passwords in source code. This serves the lab; environment variables can also be exposed via diagnostic tools or process inspection privileges, so proper secret management is still needed in real systems.

`JMXConnectorFactory.connect` creates and opens the connection; `try-with-resources` closes it when finished. Credentials are passed in the connection environment under the `JMXConnector.CREDENTIALS` key. [JMXConnectorFactory](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/remote/JMXConnectorFactory.html), [JMXConnector](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/remote/JMXConnector.html).

The `findDeadlockedThreads` call is used solely as an observation operation to demonstrate the `invoke` blocking mechanism; the test does not need to alter application configuration or trigger garbage collection. Even this operation is denied to a `readonly` account in the standard management agent.

Create `client.args`:

```text
-Djavax.net.ssl.keyStore=client.p12
-Djavax.net.ssl.keyStoreType=PKCS12
-Djavax.net.ssl.keyStorePassword=LabOnly-271-store
-Djavax.net.ssl.trustStore=client-trust.p12
-Djavax.net.ssl.trustStoreType=PKCS12
-Djavax.net.ssl.trustStorePassword=LabOnly-271-store
```

Restrict argfile permissions in the lab:

```bash
chmod 600 server.args client.args
```

Use `javac` and `java` from the same JDK 21 installation. In the first terminal:

```bash
javac JmxLab.java SecureJmxProbe.java
java @server.args JmxLab
```

When the management agent initializes successfully, the program's stdout:

```text
READY
```

Keep this terminal running. In the second terminal, navigate to the same directory and run:

```bash
export JMX_USER=monitorRole
export JMX_PASSWORD=LabOnly-271-monitor
java @client.args SecureJmxProbe
```

If using PowerShell, set environment variables with the corresponding syntax and quote the `@`-prefixed string:

```powershell
$env:JMX_USER = 'monitorRole'
$env:JMX_PASSWORD = 'LabOnly-271-monitor'
java '@client.args' SecureJmxProbe
```

Similarly, the server startup command in PowerShell is `java '@server.args' JmxLab`.

With the right certificate files, password, and permissions above, client stdout is:

```text
connected=true
runtimeMBean=true
readAttribute=true
invoke=DENIED
```

Four lines verify distinct facts: the connection opened, the target MBean exists, the attribute is actually readable, and the operation is actually denied. The JVM name value is not printed so the output does not depend on JDK vendor.

If the last line is `invoke=ALLOWED`, treat it as a sign that the effective policy does not match the `readonly` goal; inspect the exact connector, access file, and account in use. Do not adjust the expected output just to make the test look like it passed.

### 6.5. Testing Rejected Cases

Each test below launches a fresh client process. Restore the valid configuration after each test; do not lower the server's security requirements.

| Client Change | Expected Observation | Layer Under Test |
| --- | --- | --- |
| Keep valid certificates, replace `JMX_PASSWORD` with a wrong password | Does not print `connected=true`; account authentication error | JMX authentication |
| Use a copy of `client.args` with `javax.net.ssl.keyStore*` lines removed | Fails to establish management connection due to missing client TLS identity | mTLS |
| Use a valid truststore that does not trust the server certificate | Fails to establish management connection; trust or TLS handshake error | Server trust |
| Reuse full valid configuration with `monitorRole readonly` | Reads attributes successfully yet `invoke=DENIED` | Authorization |

Do not pin verbatim stack traces: errors may be wrapped in different JNDI, RMI, or SSL exceptions depending on JDK and OS. What must be proven is that invalid requests are blocked at the right layer, rather than expecting only one exact error string.

Stop the server program with Ctrl+C when finished testing. Clear test environment variables when no longer needed. If continuing to test with Spring Boot, apply the application's JMX configuration from section 3 and check the exact Actuator MBeans; succeeding in the JDK lab alone does not prove Actuator endpoints are registered or have appropriate policy.

## 7. Diagnosing Errors in Connection Order

Checking from outside in avoids modifying the wrong protection layer:

| Symptom | What to Check First |
| --- | --- |
| `Connection refused` or timeout at registry | Process still running, registry port, listening address, VPN/tunnel, and firewall |
| Registry lookup succeeds yet subsequent connection fails | Host inside stub, connector RMI port, NAT, and forwarding of the second port |
| Cannot retrieve stub when registry uses TLS | Whether client sets the socket factory for TLS registry and has matching certificate config |
| `PKIX`, `SSLHandshakeException`, or certificate trust error | Right truststore, certificate chain, certificate validity, server identity, and client key when using mTLS |
| Account authentication failure after TLS succeeds | Identity, password, authentication config, and exact file read by JVM |
| Connects yet gets `Access denied` invoking operation | Identity permissions, actual JMX method, required permission scope |
| Actuator MBean not found | Spring JMX support, whether endpoint is enabled/exposed, actual MBeanServer and `ObjectName` |
| JVM refuses to start due to password file | Owner, POSIX/ACL permissions, path, and process account |

JConsole itself also needs its own keystore/truststore for the JConsole process when using mTLS. A tool connecting via local attach is not proof that the remote path is properly authenticated and encrypted.

Do not resolve errors by setting `com.sun.management.jmxremote.authenticate=false`, disabling TLS, or opening firewalls to all sources. Those changes destroy the conditions being verified. If TLS handshake details are needed, enable diagnostic logging only for a limited time and protect its output because it can reveal internal system details.

## 8. Protecting Data and Operating Management Permissions

**Read permissions can still leak data.** JVM properties, paths, startup arguments, bean structures, or diagnostic data can contain internal secrets. TLS protects data in transit; authorized users can still view or save results. Therefore, review both the contents of each MBean and where diagnostic exports are stored.

Before bringing remote JMX into production, complete the following concrete decisions:

1. **Need and network scope:** identify who needs to connect, via which path, and from which hosts; block access paths outside that scope.
2. **Identities and permissions:** prefer least privilege, dedicated identities, and clear access lifetimes; do not share one `readwrite` account across all tools. For organizational requirements, evaluate integrated authentication mechanisms such as JAAS and corresponding authorization policies instead of test password files.
3. **Cryptographic material and secrets:** deliver keys, passwords, and certificates via controlled secret management; restrict file permissions, process permissions, and access to startup configuration. An argfile is not a secret store; JVM-wide SSL settings also require review if the application makes other TLS connections.
4. **Revocation and rotation:** test password rotation, certificate replacement, and permission revocation on the exact JDK/connector. Do not assume editing a file takes effect immediately or closes existing sessions; plan restarts or appropriate session management and re-verify.
5. **Exposed data:** review Actuator as well as non-Spring-Boot MBeans; keep sensitive data out of management interfaces when unneeded. Do not assume Actuator's exposure list constrains the entire platform MBeanServer.
6. **Operational evidence:** test both allowed and denied cases, record access via appropriate management-system mechanisms, protect logs, and keep the JDK updated. Do not treat adding Actuator as automatically providing complete audit logs for every JMX call.

A design that meets this lesson's goal must demonstrate the full control chain from network path to final data: only legitimate clients reach the registry and connector, invalid certificates and credentials are blocked, valid users receive only necessary permissions, and management data is exposed intentionally.
