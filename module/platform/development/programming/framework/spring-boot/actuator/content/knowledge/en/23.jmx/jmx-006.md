# Resolving Name Collisions with unique-names Across Multiple ApplicationContexts

Multiple `ApplicationContext` instances in the same JVM can simultaneously publish MBeans into one `MBeanServer`. Each context manages its own beans, yet JMX names must share a single registration namespace. Two distinct beans can therefore still try to claim the same `ObjectName`.

In Spring Boot 3.3, `spring.jmx.unique-names=true` instructs the Boot-configured JMX naming mechanism to produce names with a runtime differentiator. This is one way to resolve collisions when the corresponding resource instances genuinely need to coexist.

This lesson explains the cause, proper configuration, impact on management tools, and how to verify each context's lifecycle. The experiment uses two independent contexts in the same JVM, Spring Boot 3.3.0, and JDK 21.

## 1. Why Can Two Independent Contexts Still Collide on JMX Names?

Two namespaces must be distinguished:

| Namespace | Distinction Scope |
| --- | --- |
| Spring bean name | Within the bean factory/context managing that bean |
| MBean `ObjectName` | Within the MBeanServer receiving registrations |

Two contexts can both define a bean named `adminStatus` without bean-definition conflict. Yet if both expose a bean with the name:

```text
learning.unique:type=Control,name=Shared
```

into the same MBeanServer, the second registration hits the already-taken name.

Relationship in this situation:

```text
ApplicationContext alpha
    adminStatus of alpha -----+
                              |
                              v
                     shared MBeanServer
                              ^
                              |
    adminStatus of beta ------+
ApplicationContext beta

Both attempt to register:
learning.unique:type=Control,name=Shared
```

Applications can hit this scenario when running multiple contexts in one process, using embedded multi-module systems, or creating multiple contexts within the same test run.

The key condition is **the same MBeanServer**, not merely the same class name or same JVM. One JVM can have custom application-created management servers; two JVMs also have separate registries. There is no need to rename merely because two different processes use the same `ObjectName`.

[The Java 21 MBeanServer API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanServer.html) describes the registry and MBean registration inside a server.

## 2. Confirm the Exact Cause Before Enabling the Flag

When context startup fails, the outer error may look like a bean creation error or an MBean exposure error. Trace to the deepest cause. A direct indicator is:

```text
javax.management.InstanceAlreadyExistsException:
learning.unique:type=Control,name=Shared
```

Before choosing a fix, verify:

1. How many contexts are active?
2. Are the contexts using the same MBeanServer?
3. What is the exact colliding `ObjectName`?
4. Which context owns the MBean, and which exporter published it?
5. Do both resource instances need to coexist simultaneously?

If an older context was supposed to have shut down yet remains active or keeps MBeans registered, fix the lifecycle first. Adding a runtime suffix may let registration proceed, but it will not fix an old context or resource retained unintentionally.

Nor should you assume every pair of contexts will inevitably collide when the flag is off. Some endpoint naming mechanisms can append context info when encountering an existing name. The hands-on section intentionally creates a duplicate management name so the failure has an unambiguous cause.

## 3. Configuring spring.jmx.unique-names

Basic configuration in Spring Boot 3.3:

```properties
spring.jmx.enabled=true
spring.jmx.unique-names=true
```

If you need a dedicated domain for Actuator endpoints, you can add:

```properties
management.endpoints.jmx.domain=learning.unique
```

The three properties play distinct roles:

| Property | Role |
| --- | --- |
| `spring.jmx.enabled` | Enables Spring Boot's managed-bean publishing support |
| `spring.jmx.unique-names` | Requests runtime-distinct object names in Boot-configured mechanisms |
| `management.endpoints.jmx.domain` | Selects the domain for Actuator endpoint MBeans |

The default value of `spring.jmx.unique-names` in the 3.3 line is `false`. [The Spring Boot 3.3 properties appendix](https://docs.spring.io/spring-boot/3.3/appendix/application-properties/index.html) documents this configuration key.

[The Spring Boot 3.3 JMX documentation](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html) guides using `spring.jmx.unique-names=true` when multiple `ApplicationContext` instances exist.

The setting must be effective in the contexts participating in MBean publishing. In parent/child setups or multiple root contexts, inspect the actual effective environment of each context instead of assuming every context received the same value.

The flag does not enable JMX if it is disabled, nor does it add endpoints to the exposure list. For an Actuator endpoint, the endpoint must still exist, be enabled, support JMX, and be allowed by exposure.

## 4. What Do Unique Names Change?

When the flag is enabled, generated management names may gain runtime identification properties. In the Boot 3.3.0 experiment below, names carry an `identity` property; an endpoint name from a context may also gain `context`.

These parts serve to distinguish concurrently existing objects. They are not sequence numbers with business meaning and should not be treated as fixed IDs across restarts.

Important consequences for callers:

- A short name that once worked may no longer be the full registered name.
- After restarting the application, do not reuse an old runtime identifier value.
- When multiple MBeans match, tools must select the right resource instance rather than arbitrarily picking the first match.

Changing JMX names does not alter endpoint IDs in the Actuator model and is not a mechanism for changing HTTP paths. It adjusts MBean identification within the management space.

## 5. Practice: Reproducing the Error and Verifying Two Coexisting Contexts

The experiment uses two resources in each context:

1. Actuator endpoint `identity`, with operation `identify()` returning label `alpha` or `beta`.
2. Spring JMX bean `AdminStatus`, declared with the same fixed `ObjectName` in both contexts.

The `AdminStatus` MBean produces a deterministic collision when the flag is off. The Actuator endpoint lets us observe naming and lookup within the module's context.

The program runs two passes: `unique=false`, then `unique=true`. Each pass closes all contexts before moving to the next pass. No web server or remote JMX connection is opened.

### 5.2. Complete Java Code

Save to `src/main/java/example/jmxnames/UniqueNamesDemo.java`:

```java
package example.jmxnames;

import java.lang.management.ManagementFactory;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.Set;
import javax.management.InstanceAlreadyExistsException;
import javax.management.MBeanServer;
import javax.management.ObjectName;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.actuate.endpoint.annotation.ReadOperation;
import org.springframework.boot.actuate.endpoint.jmx.annotation.JmxEndpoint;
import org.springframework.boot.autoconfigure.EnableAutoConfiguration;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.env.Environment;
import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedResource;

public class UniqueNamesDemo {
    public static void main(String[] args) throws Exception {
        MBeanServer server = ManagementFactory.getPlatformMBeanServer();

        for (boolean unique : new boolean[] {false, true}) {
            System.out.println("unique=" + unique);
            try (var alpha = start(unique, "alpha")) {
                try (var beta = start(unique, "beta")) {
                    System.out.println("same server="
                            + (alpha.getBean(MBeanServer.class)
                            == beta.getBean(MBeanServer.class)));
                    System.out.println("endpoints="
                            + names(server, "Endpoint", "Identity").size());
                    System.out.println("controls="
                            + names(server, "Control", "Shared").size());
                    System.out.println("instances=" + instances(server));
                    System.out.println("endpoint identity present="
                            + names(server, "Endpoint", "Identity").stream()
                            .allMatch(name ->
                                    name.getKeyProperty("identity") != null));
                    System.out.println("bare endpoint registered="
                            + server.isRegistered(new ObjectName(
                                    "learning.unique:type=Endpoint,name=Identity")));
                } catch (Exception failure) {
                    Throwable root = failure;
                    while (root.getCause() != null) {
                        root = root.getCause();
                    }
                    if (!(root instanceof InstanceAlreadyExistsException)) {
                        throw failure;
                    }
                    System.out.println("beta=NAME_CONFLICT");
                }

                System.out.println("after beta endpoints="
                        + names(server, "Endpoint", "Identity").size());
                System.out.println("after beta controls="
                        + names(server, "Control", "Shared").size());
                System.out.println("remaining=" + instances(server));
            }

            System.out.println("after all endpoints="
                    + names(server, "Endpoint", "Identity").size());
            System.out.println("after all controls="
                    + names(server, "Control", "Shared").size());
        }
    }

    static ConfigurableApplicationContext start(
            boolean unique, String instance) {
        SpringApplication app = new SpringApplication(ContextConfig.class);
        app.setWebApplicationType(WebApplicationType.NONE);
        return app.run(
                "--spring.jmx.enabled=true",
                "--spring.jmx.unique-names=" + unique,
                "--spring.jmx.registration-policy=fail-on-existing",
                "--management.endpoints.jmx.domain=learning.unique",
                "--management.endpoints.jmx.exposure.include=identity",
                "--lab.instance=" + instance,
                "--spring.main.banner-mode=off",
                "--logging.level.root=OFF");
    }

    static Set<ObjectName> names(
            MBeanServer server, String type, String name) throws Exception {
        return server.queryNames(new ObjectName(
                "learning.unique:type=" + type + ",name=" + name + ",*"), null);
    }

    static String instances(MBeanServer server) throws Exception {
        List<String> values = new ArrayList<>();
        for (ObjectName name : names(server, "Endpoint", "Identity")) {
            values.add((String) server.invoke(
                    name, "identify", new Object[0], new String[0]));
        }
        Collections.sort(values);
        return String.join(",", values);
    }

    @Configuration(proxyBeanMethods = false)
    @EnableAutoConfiguration
    public static class ContextConfig {
        @Bean
        IdentityEndpoint identityEndpoint(Environment environment) {
            return new IdentityEndpoint(
                    environment.getRequiredProperty("lab.instance"));
        }

        @Bean
        AdminStatus adminStatus(Environment environment) {
            return new AdminStatus(
                    environment.getRequiredProperty("lab.instance"));
        }
    }

    @JmxEndpoint(id = "identity")
    public static class IdentityEndpoint {
        private final String instance;

        public IdentityEndpoint(String instance) {
            this.instance = instance;
        }

        @ReadOperation
        public String identify() {
            return instance;
        }
    }

    @ManagedResource(
            objectName = "learning.unique:type=Control,name=Shared")
    public static class AdminStatus {
        private final String instance;

        public AdminStatus(String instance) {
            this.instance = instance;
        }

        @ManagedAttribute
        public String getInstance() {
            return instance;
        }
    }
}
```

Key points when reading the code:

- `ContextConfig` uses the same configuration definition to create two independent contexts.
- Each context creates its own endpoint object and its own `AdminStatus` object.
- The `lab.instance` label helps identify which instance owns the data.
- `AdminStatus`'s name is intentionally identical to reproduce the registration error.
- `spring.jmx.registration-policy=fail-on-existing` preserves failing behavior when a name already exists.
- The `names` helper uses a `,*` pattern to match extra identity keys added to the name.
- The `catch` block catches only the expected duplicate-name error; unrelated errors are rethrown.
- `try-with-resources` closes contexts, allowing verification of proper owner unregistration.

Having the same Spring bean name `adminStatus` in both contexts is not a bean-definition conflict. The error occurs when both bean instances are published into the same JMX registry.

### 5.4. Explaining the Results

In the `unique=false` pass:

- Context `alpha` starts successfully.
- Context `beta` cannot register its managed MBean under the existing name; the program prints `beta=NAME_CONFLICT`.
- `alpha`'s MBean remains present and the `identify` operation still returns `alpha`.
- When `alpha` closes, registrations for both sample resource groups drop to `0`.

In the `unique=true` pass:

- Both contexts run together and share a single MBeanServer.
- There are two endpoint MBeans and two control MBeans.
- Invoking the operation on the endpoints confirms both `alpha` and `beta` exist, not merely that two names are counted.
- Both endpoint names contain the `identity` part.
- The short name without the identifier part is no longer registered.
- Closing `beta` leaves only `alpha`'s resources; closing all leaves zero sample resources.

These counts consider only the name groups managed by the exercise. The JVM still contains other platform MBeans; the program does not unregister them.

## 6. Not Every Endpoint Collides the Same Way

In Boot 3.3.0, a separate check creating only Actuator endpoints in two contexts—without a fixed-name `AdminStatus`—can allow two endpoints to coexist even with `spring.jmx.unique-names=false`. One instance's name gets a `context` property when disambiguation is needed.

Therefore, separate two statements:

| Statement | Accurate Understanding |
| --- | --- |
| Multiple contexts can cause name collisions | True when registering into the same MBeanServer and the naming mechanism cannot disambiguate |
| Every multi-context application fails if unique-names=false | Cannot conclude that |
| Enabling unique-names requests runtime-distinct names in Boot-configured mechanisms | That is the meaning of the configuration option being studied |
| Enabling the flag fixes every MBean registration in the JVM | Cannot assume that |

The main example uses a fixed Spring JMX name so the test does not turn into an assumption about fallback naming behavior for every endpoint. When investigating a real system, check the exact name and exporter causing the error.

## 7. Querying and Selecting the Right MBean After Enabling the Flag

Because full names change, instead of constructing a short name and invoking directly, you can search for matching endpoint names:

```java
Set<ObjectName> candidates = server.queryNames(
        new ObjectName(
                "learning.unique:type=Endpoint,name=Identity,*"),
        null);
```

This snippet assumes `MBeanServer server` already exists, with types from packages `javax.management` and `java.util`.

The `,*` part is a property-list pattern: it accepts names with additional keys alongside `type` and `name`. Writing only the two keys without the pattern suffix is not guaranteed to find names that gained `identity` or `context`.

After searching, instances must be distinguished:

1. Read metadata to confirm the right management interface.
2. Verify the label/resource each MBean represents.
3. Select the exact actual `ObjectName`.
4. Only then invoke the needed operation on the chosen instance.

The prototype uses the `identify()` read operation to cross-check labels. In real systems, you can use exposed business details or pre-designed identifying properties.

Do not use `iterator().next()` as a rule for picking the `alpha` instance when a query returns multiple names. Set iteration order is not a contract for identifying contexts.

## 8. Scope of the Flag and Related Options

### 8.1. Auto-Configuration vs. Manual Registration

`spring.jmx.unique-names` is a Spring Boot configuration property; the JDK's MBeanServer does not read this Spring property on its own.

If code manually calls `server.registerMBean(..., objectName)` with the same fixed name twice, the registering code itself must still handle naming and lifecycle. The flag does not automatically rewrite every `ObjectName` passed by every library or custom Java snippet.

If an application provides its own exporter, `ObjectNamingStrategy`, or endpoint naming factory, check that component's configuration. Do not assume all of Boot's auto-configuration continues to apply unmodified.

### 8.2. Unique Names vs. Stable Names for Management Tools

Runtime names allow objects to coexist, but operations tools sometimes need a more stable way to identify instances across restarts.

In such cases, design domains or name properties per application or deployment instance. For Actuator endpoints, `management.endpoints.jmx.static-names` allows adding static properties to names. Distinguishing values must still be properly assigned per instance; giving both the same value does not create two distinct operational addresses.

The Actuator endpoint domain controls only the endpoint MBean group. It does not automatically alter a fixed `ObjectName` used by another MBean or library.

Do not rename an endpoint ID merely to work around a JMX naming issue if that ID is used in other contracts. Solve it in the proper exposure and naming mechanism.

### 8.3. Registration Policy Does Not Replace Identification

An ignore or replace policy when meeting an existing name can make a startup error disappear, but it does not prove both resource instances are managed properly.

If two instances need to coexist, ignoring the second leaves one instance unmanaged; replacing can switch which object tools control. Therefore, do not use “no more exceptions” as sole proof.

Verification must confirm both instances are reachable, invoke the right instance, and confirm proper unregistration as each context closes.

## 9. Verification Gate for Multi-Context Applications or Tests

A meaningful verification run should include:

| Phase | Required Evidence |
| --- | --- |
| Before initialization | No unexpected leftover registrations within test scope |
| Open first context | First instance's MBean is accessible |
| Open second context | Both instances coexist and their full names differ |
| Read/invoke | Output confirms the exact label of each instance |
| Close second context | First instance remains and is still accessible |
| Close all | Registrations belonging to the test run have been removed |

When using multiple contexts in the same test JVM, closing contexts after each case is part of correctness. Enabling unique names is not an excuse to keep old contexts around or accept unbounded MBean growth.

In parent/child setups, also determine which context owns publishing and unregistration. Do not unregister a name merely because it resides in the same domain without knowing the object and its owner.

## 10. Common Errors and Self-Check

| Attempt / Symptom | What to Re-Examine |
| --- | --- |
| Renamed the Spring bean only yet still hit same ObjectName error | Two different namespaces; check the annotation/factory actually generating the JMX name |
| Enabled for only one context | Check the effective configuration value in every participating context |
| Enabled unique names then tool reports old name not found | Query the new full name instead of keeping old runtime identifiers |
| Two MBeans exist yet tool always picks one at random | Add instance identification and an explicit selection rule |
| MBean count grows after each test run | Check context closing and unregistration |
| Changed allow-bean-definition-overriding to fix a JMX error | Bean-definition conflicts and MBean registration conflicts are two separate issues |
| Disabled JMX or excluded all exposure to stop the error | Management capability changed; does not prove two instances coexist |

Self-check questions:

1. Why do two contexts with identically named beans only collide when published to JMX?
2. Under what condition do two identical `ObjectName` values actually conflict?
3. After enabling `unique-names`, why might a short name no longer work?
4. If closing `beta` also causes `alpha`'s MBean to disappear, which part needs checking?
5. Why must data labels also be verified instead of only checking that two names exist?

Answers should stay grounded in three factors: registry scope, the effective naming mechanism, and the lifecycle of the exact context owning the resource.
