# Estimating Percentile Latency from Histograms and Choosing Buckets

When a chart reports p95 as 416 ms, that can be the result of interpolation inside a wide bucket. With the same traffic and the same actual latencies, adding boundaries around the 300 ms mark can bring the estimate closer to 292 ms. The difference lies in how much detail the histogram retains.

The examples below use Prometheus classic histograms for a `Timer` measuring HTTP duration in Spring Boot.

## What information does a histogram retain?

Each `_bucket` series has an `le` label for the upper bound, inclusive of the boundary point. For example, `le="0.3"` counts requests that completed in at most 0.3 seconds. Buckets are **cumulative across boundaries**. An 80 ms request is counted in both the 100 ms and 300 ms buckets. Taking the difference between these two counters gives the number of observations in the interval (100 ms, 300 ms].

The `le="+Inf"` bucket contains the total number of observations, equal to `_count` for the same label combination. These series are also **cumulative over time** while the application runs. To analyze a window, Prometheus can use `rate()` to estimate the rate of increase of each counter within that window.

## Computing p95 from two enclosing boundaries

With a total observation count `N`, the `histogram_quantile(0.95, …)` function finds the first bucket whose cumulative count reaches the `0.95 × N` mark. Let `L` and `U` be the lower and upper bounds of the finite bucket containing that mark. `C(L)` and `C(U)` are the corresponding cumulative counts. The function performs linear interpolation, equivalent to assuming observations are uniformly distributed within the interval.

```text
p95 ≈ L + (U − L) × (0.95 × N − C(L)) / (C(U) − C(L))
```

For non-negative latencies when the mark falls into the first bucket with a positive bound, Prometheus uses 0 as the lower bound. When p95 falls into the `+Inf` bucket, the function returns the highest finite bound. If charts frequently stop at that exact bound, check the ratio of requests exceeding the bound to see whether the histogram still has enough resolution in the tail.

## Same distribution, two sets of boundaries

Suppose there are 100 requests in the window. Of these, 80 requests take 80 ms, 10 requests take 240 ms, 6 requests take 280 ms, 3 requests take 420 ms, and 1 request takes 900 ms. Sorting the raw data by latency gives the 95th observation as 280 ms. This is the reference value using the nearest-rank method.

| Upper bound | Coarse boundary set | Fine boundary set around 300 ms |
| --- | ---: | ---: |
| 100 ms | 80 | 80 |
| 250 ms | — | 90 |
| 300 ms | — | 96 |
| 500 ms | 99 | 99 |
| 1,000 ms | 100 | 100 |
| `+Inf` | 100 | 100 |

The dash indicates an unconfigured boundary. The columns are cumulative bucket counts of observations in the window, used for manual calculation.

- **Coarse boundary set.** Mark 95 falls in (100 ms, 500 ms]. There are 19 requests in the interval, and we need to move 15 positions beyond the 100 ms mark. Interpolating gives `100 + 400 × 15 / 19 ≈ 415.79 ms`.
- **Fine boundary set.** Mark 95 falls in (250 ms, 300 ms]. There are 6 requests in the interval, and we need to move 5 positions beyond the 250 ms mark. Interpolating gives `250 + 50 × 5 / 6 ≈ 291.67 ms`.

Narrowing the bucket containing p95 narrows the interval that can contain the true percentile, from 400 ms down to 50 ms in this example. The exact error still depends on how observations are distributed within the interval. In the raw data, all 6 requests between the 250 and 300 ms boundaries lie at 280 ms.

For the target "at least 95% of requests complete within 300 ms", the 300 ms bucket also answers the ratio question directly. There are 96 requests meeting the threshold out of 100 total, or 96%. When the target threshold aligns with a bucket boundary, dividing these counts requires no assumption about the distribution inside the bucket.

## Configuring and querying in Spring Boot

In a web application using Actuator and `io.micrometer:micrometer-registry-prometheus`, you can reproduce the example's finite boundary set in `application.properties`. The configuration below selects explicit boundaries for `http.server.requests` and disables auto-generated boundaries for that meter.

```properties
management.endpoints.web.exposure.include=health,prometheus
management.metrics.distribution.percentiles-histogram.http.server.requests=false
management.metrics.distribution.slo.http.server.requests=100ms,250ms,300ms,500ms,1s
```

If you want to use boundaries generated by Micrometer, enable `percentiles-histogram` and use `minimum-expected-value` along with `maximum-expected-value` to constrain the range of auto-generated boundaries. Keep `slo` for business thresholds that need to be exported accurately. Expected values are used to choose histogram boundaries. Observations exceeding the highest finite boundary still contribute to `+Inf` and the total observation count.

After generating traffic and having Prometheus scrape it, check the `le` labels in the actual data. Suppose the `orders` job scrapes instances of the same service and `uri="/orders"` is an exported path label. The following query estimates p95 over 5 minutes.

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_server_requests_seconds_bucket{job="orders", method="GET", uri="/orders"}[5m])
  )
)
```

`rate()` runs on each series first so Prometheus handles each instance's counter resets. `sum by (le)` sums buckets with the same upper bound before computing a single overall p95. Keep `uri` in the `by` clause as well when you need one result per route and have removed the fixed route filter. With counts or rates all proportional to the table above, the p95 result for the fine boundary set is approximately 0.292 seconds.

Querying the completion ratio within 300 ms uses the corresponding bucket divided by the total request count. Use the same label scope and window in both the numerator and denominator so both sides refer to the same set of requests.

```promql
sum(rate(http_server_requests_seconds_bucket{job="orders", method="GET", uri="/orders", le="0.3"}[5m]))
/
sum(rate(http_server_requests_seconds_count{job="orders", method="GET", uri="/orders"}[5m]))
```

The query returns a ratio from 0 to 1 when data is available and the denominator is positive. Check the actual boundary labels in Prometheus before using the `le="0.3"` condition. When there are no observations yet, check request counts and scrape status before interpreting the chart. A classic histogram missing the `+Inf` bucket causes `histogram_quantile()` to return `NaN` for that histogram.

## Choosing buckets for real-world services

1. **Start from the threshold you need to act on.** If the SLO is set at 300 ms, configure an exact 300 ms boundary. If you need to know how far p95 is from the threshold, add boundaries on both sides, such as 250 ms and 350 ms. If you only measure the ratio meeting 300 ms, the 300 ms boundary alone already provides the numerator.
2. **Dedicate resolution to the critical region.** Observe the latency range under representative load. Place denser boundaries around the monitored quantile, and widen spacing in regions that have little impact on decisions. Choose the highest finite boundary high enough to cover the tail that needs analysis. If more than 5% of requests exceed this boundary, p95 falls into `+Inf` and the displayed value is capped at the highest finite boundary.
3. **Account for cost by label combination.** With 5 finite boundaries and `+Inf`, each label combination has 6 `_bucket` series, not counting `_count`, `_sum`, and other statistics. If there are 20 label combinations per target and 4 targets, buckets alone create 480 series. Add boundaries when higher resolution truly changes how metrics are read.
4. **Keep the same boundary set across series being aggregated.** When a boundary only exists on some instances, the sum at that boundary reflects only the instances with the corresponding series. After changing configuration, check targets and query windows before comparing p95 with periods using the old boundary set.
