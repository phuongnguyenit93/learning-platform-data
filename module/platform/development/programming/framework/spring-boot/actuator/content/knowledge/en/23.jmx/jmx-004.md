# Reading Attributes and Invoking Operations on Endpoint MBeans

Once an MBean is found, the next step is to use the exact management interface it exposes: reading attributes or invoking an operation. Both go through `ObjectName`, but they use different APIs and inputs.

In Spring Boot Actuator, an important detail to watch for is that **a read operation is not necessarily a JMX attribute**. An endpoint may provide data entirely through operations. Therefore, inspect metadata before deciding whether to open Attributes in JConsole or call `getAttribute` in Java.

This lesson uses a standard MBean and an Actuator endpoint to contrast the two access styles. The hands-on program uses Spring Boot 3.3.0 and JDK 21, working against an MBeanServer in the same JVM without opening network connections.

## 1. Starting from the Right Name and Metadata

To access an MBean, two pieces of information are needed:

1. Which MBeanServer is being used.
2. Which `ObjectName` identifies the MBean inside that server.

A name like `learning.actuator:type=Endpoint,name=Limitslab` is neither a URL nor a Java class name. It is the management registration name in this lesson's experiment.

Once you have `MBeanServerConnection connection` and `ObjectName name`, the discovery step is:

```java
MBeanInfo info = connection.getMBeanInfo(name);
MBeanAttributeInfo[] attributes = info.getAttributes();
MBeanOperationInfo[] operations = info.getOperations();
```

This snippet assumes a context where `connection` and `name` already exist and is not a standalone program. The types belong to package `javax.management`.

Metadata answers:

| Question | Where to Read |
| --- | --- |
| Which attributes does the MBean have? | `MBeanInfo.getAttributes()` |
| Is an attribute readable? | `MBeanAttributeInfo.isReadable()` |
| What are the attribute's name and type? | `getName()`, `getType()` |
| Which operations exist? | `MBeanInfo.getOperations()` |
| Which parameters does an operation take, and in what order? | `MBeanOperationInfo.getSignature()` |
| What type does the operation return? | `MBeanOperationInfo.getReturnType()` |

[MBeanInfo in Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanInfo.html) describes the published management interface. Rely on this rather than inferring everything from methods in the implementation class.

## 2. How Do Attributes and Operations Differ?

| Need | JMX API | Example |
| --- | --- | --- |
| Read one attribute | `getAttribute(name, attributeName)` | Read `Label` |
| Read multiple attributes | `getAttributes(name, attributeNames)` | Read `Label`, `Active` |
| Invoke an operation | `invoke(name, operationName, params, signature)` | Call `snapshot()` or `configure(...)` |

### With Standard MBeans

By Standard MBean convention, `getLabel()` in the management interface can produce an attribute named `Label`. In that case, the appropriate call is `getAttribute(name, "Label")`.

Do not assume you can call `invoke(name, "getLabel", ...)`: that getter may have been represented as an attribute and omitted from the operations list.

### With Actuator Endpoints

`@ReadOperation` and `@WriteOperation` methods describe Actuator operations. On the hands-on endpoint's MBean, they appear in the operations list while the attributes list is empty.

Consequently:

- `@ReadOperation snapshot()` is called via `invoke(..., "snapshot", ...)`.
- Its “read information” semantics do not automatically create an attribute named `Snapshot`.
- Empty attributes do not prove the endpoint is broken or has no data.

Distinguish the **read/write semantics of an operation** from **how the JMX interface represents that operation**.

## 3. Four Parts of an Operation Invocation

General form:

```java
Object result = connection.invoke(
        objectName,
        operationName,
        params,
        signature);
```

| Part | Content |
| --- | --- |
| `objectName` | Target MBean receiving the call |
| `operationName` | Published operation name |
| `params` | Array of argument values in exact count and order |
| `signature` | Array of parameter type names matching published metadata/signature |

For a Standard MBean operation with signature `repeatLabel(String prefix, int times)`, the example uses:

```java
new Object[] {"x", 2}
new String[] {"java.lang.String", "int"}
```

These are two expressions illustrating the last two arguments of `invoke`.

The value `2` is boxed into an `Integer` when placed in `Object[]`, yet the type name in the Standard MBean signature remains `"int"`. Do not derive every element of `signature` from the runtime class of objects inside the value array.

For an operation with no parameters, two empty arrays can be used:

```java
new Object[0]
new String[0]
```

[The MBeanServerConnection API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanServerConnection.html) defines the attribute-reading and operation-invoking methods. [MBeanOperationInfo](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/MBeanOperationInfo.html) provides signature descriptors.

With Dynamic MBeans or framework-generated exposure layers, the management types may differ from the types seen in Java declarations. The hands-on section shows a concrete case.

## 4. Practice: A Program Comparing Two Kinds of MBeans

The application has two managed objects:

- Standard MBean `WorkerControl`: attributes `Label`, `Active`, and operation `repeatLabel`.
- Actuator endpoint `limitslab`: operation `snapshot` to read test settings and `configure` to modify those settings.

The data is strictly in-memory state of the sample program. The `configure` operation does not alter JVM limits or real system settings.

### 4.3. Complete Java Code

Save to `src/main/java/example/jmxaccess/MBeanAccessApplication.java`:

```java
package example.jmxaccess;

import java.util.Arrays;
import java.util.stream.Collectors;
import javax.management.AttributeList;
import javax.management.MBeanInfo;
import javax.management.MBeanOperationInfo;
import javax.management.MBeanParameterInfo;
import javax.management.MBeanServer;
import javax.management.MBeanServerConnection;
import javax.management.ObjectName;
import javax.management.StandardMBean;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.actuate.endpoint.annotation.ReadOperation;
import org.springframework.boot.actuate.endpoint.annotation.WriteOperation;
import org.springframework.boot.actuate.endpoint.jmx.annotation.JmxEndpoint;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class MBeanAccessApplication {
    public static void main(String[] args) {
        try (var context = SpringApplication.run(
                MBeanAccessApplication.class, args)) {
            // ApplicationRunner has already finished before the context is closed.
        }
    }

    @Bean
    LimitsEndpoint limitsEndpoint() {
        return new LimitsEndpoint();
    }

    @Bean
    ApplicationRunner inspectAndInvoke(MBeanServer server) {
        return args -> {
            MBeanServerConnection connection = server;
            ObjectName control = new ObjectName(
                    "learning.management:type=WorkerControl,name=demo");
            server.registerMBean(new StandardMBean(
                    new WorkerControl(), WorkerControlMBean.class), control);
            try {
                System.out.println("label="
                        + connection.getAttribute(control, "Label"));
                System.out.println("active="
                        + connection.getAttribute(control, "Active"));

                AttributeList attributes = connection.getAttributes(control,
                        new String[] {"Label", "Active", "Missing"});
                System.out.println("batch attributes=" + attributes.size());

                Object repeated = connection.invoke(control, "repeatLabel",
                        new Object[] {"x", 2},
                        new String[] {"java.lang.String", "int"});
                System.out.println("standard result=" + repeated);

                ObjectName endpoint = new ObjectName(
                        "learning.actuator:type=Endpoint,name=Limitslab");
                MBeanInfo info = connection.getMBeanInfo(endpoint);
                System.out.println("actuator attributes="
                        + info.getAttributes().length);

                Arrays.stream(info.getOperations())
                        .sorted((left, right) ->
                                left.getName().compareTo(right.getName()))
                        .forEach(operation -> {
                            String types = Arrays.stream(operation.getSignature())
                                    .map(MBeanParameterInfo::getType)
                                    .collect(Collectors.joining(","));
                            System.out.println("operation="
                                    + operation.getName() + "(" + types + ")");
                        });

                Object before = connection.invoke(endpoint, "snapshot",
                        new Object[0], new String[0]);
                System.out.println("actuator before=" + before);

                MBeanOperationInfo configure = Arrays.stream(info.getOperations())
                        .filter(operation -> operation.getName().equals("configure"))
                        .findFirst().orElseThrow();
                String[] signature = Arrays.stream(configure.getSignature())
                        .map(MBeanParameterInfo::getType)
                        .toArray(String[]::new);

                Object configured = connection.invoke(endpoint, "configure",
                        new Object[] {"batch", 12}, signature);
                System.out.println("actuator configured=" + configured);
                System.out.println("actuator after=" + connection.invoke(
                        endpoint, "snapshot", new Object[0], new String[0]));
            } finally {
                server.unregisterMBean(control);
            }
        };
    }

    public interface WorkerControlMBean {
        String getLabel();
        boolean isActive();
        String repeatLabel(String prefix, int times);
    }

    public static class WorkerControl implements WorkerControlMBean {
        @Override
        public String getLabel() {
            return "worker";
        }

        @Override
        public boolean isActive() {
            return true;
        }

        @Override
        public String repeatLabel(String prefix, int times) {
            if (times < 1 || times > 3) {
                throw new IllegalArgumentException("times must be between 1 and 3");
            }
            return (prefix + getLabel()).repeat(times);
        }
    }

    @JmxEndpoint(id = "limitslab")
    public static class LimitsEndpoint {
        private String label = "default";
        private int limit = 5;

        @ReadOperation
        public synchronized String snapshot() {
            return label + ":" + limit;
        }

        @WriteOperation
        public synchronized String configure(String label, int limit) {
            if (limit < 1) {
                throw new IllegalArgumentException("limit must be positive");
            }
            this.label = label;
            this.limit = limit;
            return snapshot();
        }
    }
}
```

Nested classes keep the entire example in a single file. `StandardMBean` explicitly selects the `WorkerControlMBean` management interface; the Actuator endpoint is registered as a Spring bean via `@Bean`.

`MBeanServerConnection connection = server` shows that the caller uses the connection API to access MBeans. Here the connection is local. When a tool has a valid remote JMX connection, the corresponding read/invoke operations are also performed via `MBeanServerConnection`.

The program closes its context automatically after `ApplicationRunner` finishes. The Standard MBean created by the program is unregistered in `finally`.

## 5. Reading One or Multiple Attributes Correctly

### 5.1. One Attribute

In the example:

```java
Object label = connection.getAttribute(control, "Label");
```

The return type is `Object`, so the caller must know the published type to use it. For instance, `Label` yields a `String`; `Active` returns a `Boolean` when retrieved through the `Object`-returning API.

Attribute names are case-sensitive. `"Label"` and `"label"` are not the same name. Also do not prepend `get` to the attribute name just because the interface has a `getLabel()` getter.

Before reading, you can inspect metadata to verify whether the attribute exists and `isReadable()` is `true`. Metadata helps choose how to call, while runtime errors still need handling.

### 5.2. Multiple Attributes

`getAttributes` returns an `AttributeList`, where each element holds both a name and a value. In the sample program, the request list had three names, but the result contained only two elements.

Because some attributes may fail to read, **do not match results to the request list by position alone**. Use the name of each `Attribute`. Example assuming `attributes` already exists:

```java
for (var attribute : attributes.asList()) {
    String name = attribute.getName();
    Object value = attribute.getValue();
    System.out.println(name + "=" + value);
}
```

If an important attribute is missing from a batch result, report clearly that it could not be read; you can read that attribute individually to obtain the specific error. Do not assume a missing value means `0`, an empty string, or `false`.

Reading a group of attributes also does not guarantee they form a snapshot at the exact same instant. If an application needs a consistent set of values, the resource must provide synchronization or an appropriate aggregate read operation.

## 6. Invoking Operations: By Published Name, Order, and Signature

### 6.1. Zero-Parameter Operations

In the sample endpoint, `snapshot` takes no arguments:

```java
Object snapshot = connection.invoke(
        endpoint, "snapshot", new Object[0], new String[0]);
```

This is an operation even though its purpose is reading. Calling `getAttribute(endpoint, "Snapshot")` does not match the metadata observed in section 4.

### 6.2. Operations with Parameters

Three pieces of information must align:

| Position | Value in Actuator Example | Published Type Retrieved from Metadata |
| --- | --- | --- |
| 0 | `"batch"` | `java.lang.String` |
| 1 | `12` | `java.lang.Object` in Boot 3.3.0 example |

The code builds the signature with:

```java
String[] signature = Arrays.stream(configure.getSignature())
        .map(MBeanParameterInfo::getType)
        .toArray(String[]::new);
```

Here `configure` is the metadata of the operation to invoke. This signature describes the published management interface; the framework may subsequently convert incoming values into the required Java types before running the method.

For the Standard MBean operation `repeatLabel`, the published signature is `java.lang.String,int` instead. Both cases must be evaluated against their respective MBeans.

Parameter names present in metadata can help users understand input fields, but the `params` array in `invoke` is still passed positionally. It is not a map that binds values by name.

### 6.3. Same Name, Different Overloads

If an MBean has multiple operations with the same name, matching by name alone is insufficient. You must select the exact signature, including parameter count and type names at each position.

The sample program uses `findFirst()` after filtering on name `configure` because this endpoint exposes only one operation with that name. Do not apply that selection pattern verbatim to an MBean with overloads without inspecting metadata.

Type names in the signature are not variable names either. Do not pass `"limit"` in place of a type name, and do not shorten types to `"String"` or `"Integer"` without package names.

## 7. Using Results and Understanding Call Impact

An operation may return a value, return nothing, or fail. Check the return type in metadata and the MBean's specific contract. If an operation returns `void`, do not treat a `null` return from the call as if it were always an error.

JVM MBeans or other MBeans may return structured data types such as `CompositeData`; in those cases, read the appropriate structure rather than casting to `String` or treating it as JSON by default. The example in this lesson deliberately returns strings to focus on invocation mechanics.

`configure` mutates the test state. A connection-level `invoke` success does not replace checking the business outcome: after the call, the example invokes `snapshot` to confirm the new value.

If a remote call loses its connection while executing a state-changing operation, the caller may not know whether the operation ran. Before resending, understand idempotency and have a way to check state. Do not blindly retry every operation just because a connection error occurred.

## 8. Reading and Invoking with JConsole

With an application running long enough in an environment allowing JMX connections:

1. Connect to the right JVM process or configured JMX address.
2. Open the MBeans tab.
3. Select the right domain and `ObjectName`.
4. Inspect the MBean's metadata.
5. If attributes exist, read them under Attributes.
6. If operations exist, select one under Operations, check argument order/types, and invoke.
7. Verify the result and re-read state when an operation modifies data.

Do not confuse an attribute in the Attributes tab with a read method in the Operations tab. The example's Actuator endpoint has `snapshot` in Operations and no `Snapshot` attribute.

The sample application in section 4 closes its context right after running, so it is not designed to wait for JConsole to attach after printing results. This section describes working with a live managed application; the Java example uses MBeanServer directly so results are reproducible without UI steps.

Remote connection setup and access rights are environment-specific configurations. Actuator JMX exposure chooses which endpoints are published; it does not automatically supply remote connection details to tools.

## 9. Distinguishing Lookup Errors, Interface Errors, and In-Operation Errors

| Error / Symptom | What to Check |
| --- | --- |
| `InstanceNotFoundException` | Right server, right name, whether the MBean is still registered |
| `AttributeNotFoundException` | Whether the attribute exists, matches case, and is readable |
| `ReflectionException` | Whether operation name/signature matches the published interface |
| `MBeanException` | Inspect the target exception thrown by the call into the MBean |
| `RuntimeMBeanException` | Inspect the target runtime exception from MBean code |
| `SecurityException` | Access permissions enforced at the management layer |
| `IOException` over remote connection | Connection health and transport errors |
| Batch attributes missing items | Do not assume every requested name was read successfully |

Exact wrapper exception classes also depend on MBean kind, framework, and invocation path. Read the target cause rather than simply swapping API names based on the outermost exception line.

In the example's Standard MBean, these cases illustrate different errors:

- Reading `label` instead of `Label`: attribute with that exact name is not found.
- Invoking `getLabel` as an operation: the getter was published as an attribute.
- Using `java.lang.Integer` instead of `int` in `repeatLabel`'s signature: signature mismatch.
- Passing `times=0` with the right signature: reaches the operation code, which rejects the input and throws `IllegalArgumentException` wrapped by the JMX layer.

The final case is a precondition error in the operation, distinct from not finding the operation. Fixing the connection or changing `ObjectName` will not resolve rejected input data.

## 10. Verification Exercises

On the prototype and test data:

1. Compare `WorkerControlMBean` against metadata: point out the two attributes and one operation.
2. Change `"Label"` to `"label"` in the read call and explain the error.
3. Change the Standard MBean signature from `"int"` to `"java.lang.Integer"` while keeping value `2`; compare with the valid call.
4. For `limitslab`, use the operations list to explain why state can still be read via `snapshot` even when Attributes is empty.
5. Invoke `configure` using the signature retrieved from metadata and check state afterward.
6. Request only a nonexistent attribute name with `getAttributes`; handle the missing result instead of treating it as a default value.

When building management tools, keep three layers of information clear: the MBean name identifies the object, metadata defines the callable interface, and the return value confirms execution outcome.
