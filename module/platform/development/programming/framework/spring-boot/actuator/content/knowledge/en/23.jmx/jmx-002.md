# Enabling Spring JMX Support and Determining Exposed Endpoints

## 1. Enabling JMX Is Not Exposing Every Endpoint

When monitoring Spring Boot with JConsole, two separate questions must be answered:

1. Has Spring registered its management components into JMX yet?
2. Which Actuator endpoints are allowed to be exported over JMX?

If you only add `management.endpoints.jmx.exposure.include=info` without enabling Spring JMX support, the endpoint will not appear as expected. Conversely, enabling `spring.jmx.enabled=true` does not mean all endpoints are exposed.

This lesson uses **Spring Boot 3.3.13**, Java 17+ source code, and JDK tools. The example and seven tests below were run on Java 21. Property names and defaults are explained for the Boot 3.3 branch without mixing endpoint management configurations from other versions.

### Components to Recognize

| Component | Meaning |
| --- | --- |
| **JMX** — Java Management Extensions | Standard mechanism for observing and managing components inside a JVM |
| **MBean** — Managed Bean | Component with management data or operations exported to JMX |
| **MBeanServer** | Place where MBeans are registered and looked up within a JVM |
| **ObjectName** | Identifier of an MBean, consisting of a domain and key–value pairs |
| **Spring JMX** | Support for exporting Spring beans with management metadata into an MBeanServer |
| **Actuator JMX endpoint** | Actuator endpoint exported as an MBean over the JMX channel |
| **JMX connector** | Mechanism for management tools to connect to an MBeanServer, especially for remote access |

An `info` endpoint is an Actuator management feature. When exported over JMX, it has a corresponding MBean. That is not an HTTP URL, even though the same endpoint can be exported independently over HTTP.

## 2. Three Configuration Decisions to Separate

### 2.1. Enabling Spring JMX Support

In `application.properties`:

```properties
spring.jmx.enabled=true
```

In Spring Boot 3.3, Spring's JMX support is disabled by default. When appropriate auto-configuration is triggered, Boot provides an `MBeanServer` bean named `mbeanServer` and the mechanism to export managed Spring beans. Official source: [Monitoring and Management over JMX](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html).

This property controls the management support provided by Spring. The JVM can still have platform MBeans such as memory or threading; other libraries may also register MBeans via their own mechanisms. Therefore, seeing the `java.lang` domain in JConsole does not prove that Spring JMX or Actuator JMX is enabled.

### 2.2. Choosing Actuator Endpoints to Export over JMX

Example exposing only `health` and `info`:

```properties
spring.jmx.enabled=true
management.endpoints.jmx.exposure.include=health,info
```

The items `health` and `info` are **endpoint IDs**, not Java class names, bean names, URLs, or ObjectNames.

In Boot 3.3's default configuration, the JMX list includes only `health`. To get `info`, it must be added to the appropriate exposure configuration. Include/exclude rules and enablement are described in [Actuator Endpoints](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.exposing).

### 2.3. Allowing a Tool to Connect to the JVM

`spring.jmx.enabled=true` does not automatically configure a remote JMX port. Registering MBeans and opening a connection path to the MBeanServer are two separate layers.

In this lesson, JConsole connects **locally** to the JVM under the same operating system account. No extra parameters to open a remote RMI port are needed for the experiment. Java supports local monitoring via the attach mechanism; monitoring from another machine requires separate connector and security configuration. See [Monitoring and Management Using JMX Technology for JDK 21](https://docs.oracle.com/en/java/javase/21/management/monitoring-and-management-using-jmx-technology.html).

HTTP ports such as `server.port` or `management.server.port` are not JMX connector ports. HTTP security configuration also does not automatically apply to a remote JMX connection.

## 3. Which Endpoints Are Actually Exposed?

For an endpoint to appear as an Actuator MBean, check the following conditions:

1. Appropriate Spring JMX infrastructure and an MBeanServer are available for registration.
2. The endpoint exists, is enabled, and satisfies its initialization conditions.
3. The endpoint supports JMX export.
4. The endpoint ID is selected by the `include` list.
5. The endpoint ID is not removed by `exclude`.
6. MBean registration completes without errors such as duplicate ObjectName.

You can think of the expected set of endpoints as the intersection of the conditions above. The list of registered MBeans is the final runtime evidence; reading a single configuration line is not enough to confirm every condition.

### 3.1. Include Selects, Exclude Removes

Example:

```properties
spring.jmx.enabled=true
management.endpoints.jmx.exposure.include=health,info,metrics
management.endpoints.jmx.exposure.exclude=metrics
```

If all three endpoints meet the conditions to operate, the configuration above selects `health` and `info`, and excludes `metrics`.

If an ID appears in both lists, **exclude takes precedence**. Therefore:

```properties
management.endpoints.jmx.exposure.include=health,info
management.endpoints.jmx.exposure.exclude=info
```

will not expose `info` over JMX.

To select all endpoints that meet the conditions, you can use `include=*`; it does not create non-existent endpoints and does not automatically enable disabled ones. In YAML, `*` must be enclosed in quotes:

```yaml
spring:
  jmx:
    enabled: true

management:
  endpoints:
    jmx:
      exposure:
        include: "*"
        exclude:
          - env
          - configprops
```

This is an example of syntax and precedence. When choosing the set of management endpoints for an application, explicitly identify which endpoints are needed and what data or operations they provide.

### 3.2. Enablement and Exposure Have Different Roles

In Boot 3.3, enabling or disabling an individual endpoint uses:

```properties
management.endpoint.info.enabled=false
```

Whereas selecting the JMX channel uses:

```properties
management.endpoints.jmx.exposure.include=health,info
```

These two lines do not conflict in precedence: `info` has been disabled, so being present in `include` does not re-enable it.

Pay attention to the property names:

- `management.endpoint.<id>.enabled` uses singular **endpoint**.
- `management.endpoints.jmx.exposure.include` uses plural **endpoints**.

If you want to enable endpoints via an allowlist from the start, you can configure:

```properties
spring.jmx.enabled=true
management.endpoints.enabled-by-default=false
management.endpoint.health.enabled=true
management.endpoint.info.enabled=true
management.endpoints.jmx.exposure.include=health,info
```

In the Boot 3.3 branch, `shutdown` is an example of an endpoint disabled by default; adding that ID to `include` does not automatically enable application shutdown. Similarly, an endpoint that depends on a specific library or bean does not appear simply because it is listed in exposure.

### 3.3. Capabilities per Technology

- `@Endpoint` is for the general endpoint model and can be exported over JMX when eligible.
- `@JmxEndpoint` is for JMX only.
- `@WebEndpoint` is for HTTP only.

A web-only endpoint does not become a JMX endpoint by adding its ID to `management.endpoints.jmx.exposure.include`. Exposure lists filter within the set of endpoints usable by that technology.

### 3.4. HTTP and JMX Have Separate Lists

Example:

```properties
spring.jmx.enabled=true
management.endpoints.jmx.exposure.include=health,info
management.endpoints.web.exposure.include=health
```

In the lesson's sample application, JMX has `Health` and `Info`; HTTP exposes only `health`. Not exposing `info` over HTTP does not prevent it from being exposed over JMX.

Conversely, `management.endpoints.web.exposure.include=info` does not replace JMX configuration. When investigating a missing endpoint, first identify which management channel is being used.

## 4. Distinguishing Three MBean Groups in JConsole

| Group | Example | Related Configuration |
| --- | --- | --- |
| JVM platform MBeans | `java.lang:type=Memory` | JVM management mechanism |
| Spring beans exported with Spring JMX | Bean with `@ManagedResource` | MBeanExporter mechanism and management metadata |
| Actuator endpoints exported over JMX | `org.springframework.boot:type=Endpoint,name=Health` | Spring JMX, endpoint availability, and JMX exposure |

`MBeanExporter` is responsible for registering Spring beans into the MBeanServer. This mechanism is introduced in [Exporting Your Beans to JMX](https://docs.spring.io/spring-framework/reference/integration/jmx/exporting.html).

A practical consequence: the following configuration removes all **Actuator endpoints** from JMX:

```properties
management.endpoints.jmx.exposure.exclude=*
```

However, it is not a switch that deletes all MBeans in the JVM. A Spring bean exported with `@ManagedResource` can still exist while Spring JMX remains enabled. The example and tests below confirm this.

Nor should `spring.jmx.enabled=false` be used as proof that every JVM or third-party library management component has been disabled. The entity that registered the MBean must be properly distinguished.

### 5.3. Registering Sample Data and Printing the Endpoint List

Create `src/main/java/com/example/jmxlesson/JmxApplication.java`:

```java
package com.example.jmxlesson;

import java.util.List;
import java.util.Map;
import javax.management.MBeanServer;
import javax.management.ObjectName;

import org.springframework.beans.factory.ObjectProvider;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.actuate.info.InfoContributor;
import org.springframework.context.annotation.Bean;
import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedResource;

@SpringBootApplication
public class JmxApplication {
    public static void main(String[] args) {
        SpringApplication.run(JmxApplication.class, args);
    }

    @Bean
    InfoContributor lessonInfo() {
        return builder -> builder.withDetail(
                "lesson", Map.of("topic", "Spring JMX", "mode", "local"));
    }

    @Bean
    SampleCounter sampleCounter() {
        return new SampleCounter();
    }

    @Bean
    ApplicationRunner inventory(ObjectProvider<MBeanServer> servers) {
        return args -> {
            MBeanServer server = servers.getIfAvailable();
            if (server == null) {
                System.out.println("Spring MBeanServer bean: absent");
                return;
            }
            List<String> names = server.queryNames(
                    new ObjectName("org.springframework.boot:type=Endpoint,*"), null)
                    .stream()
                    .map(name -> name.getKeyProperty("name"))
                    .sorted()
                    .toList();
            System.out.println("Actuator JMX endpoints: " + String.join(", ", names));
            System.out.println("Custom Spring MBean: " + server.isRegistered(
                    new ObjectName("com.example.jmxlesson:type=Sample,name=Counter")));
        };
    }

    @ManagedResource(objectName = "com.example.jmxlesson:type=Sample,name=Counter")
    public static class SampleCounter {
        @ManagedAttribute(description = "Sample pending work count")
        public int getPending() {
            return 12;
        }
    }
}
```

The inventory code uses `queryNames` to find MBeans with domain `org.springframework.boot` and key `type=Endpoint`. It reads the `name` key, sorts, and prints the result, so it does not depend on the ObjectName set order returned by the MBeanServer.

`ObjectProvider<MBeanServer>` allows the program to handle the case where no MBeanServer bean exists yet. With default auto-configuration and Spring JMX disabled, the program can report that this bean is absent instead of failing immediately due to required injection.

The inventory query looks only for **Actuator endpoints** in the specified domain. It does not list JVM MBeans or the `SampleCounter` bean because they have different names.

`SampleCounter` is a Spring bean registered via `@Bean`, with `@ManagedResource` metadata and a `@ManagedAttribute`. It is not an Actuator endpoint and has no `health` or `info` ID.

In this program, `ApplicationRunner` performs the inventory after the application context has finished starting. Querying too early during bean creation might not reflect the final set of MBeans.

```shell
mvn package
java -jar target/spring-jmx-demo-1.0.0.jar
```

Maven compiles Java along with dependencies and runs the tests if the file in section 7 has been added. The first run downloads libraries. If HTTP port `8080` is already in use, you can change `server.port` for the run.

The startup log includes two lines printed by the lesson's inventory code:

```text
Actuator JMX endpoints: Health, Info

```

These two lines confirm:

- Two Actuator MBeans match the query: `Health` and `Info`.
- The custom MBean `com.example.jmxlesson:type=Sample,name=Counter` has been registered.
- The result comes from the MBeanServer, not merely from echoing the `include` value.

Other logs, timestamps, and host information may differ by environment. Health values also depend on the runtime environment; do not assume every machine produces the same health outcome.

### 6.2. Inspecting in JConsole

1. Keep the application running.
2. Run `jconsole` from a JDK that includes this tool.
3. Select the `JmxApplication` JVM or the corresponding JAR process, under the same operating system account.
4. Go to the **MBeans** tab.
5. Expand the `org.springframework.boot` domain, `Endpoint` branch.
6. Find `Health` and `Info`.

With the default naming configuration, the two ObjectNames are:

```text
org.springframework.boot:type=Endpoint,name=Health
org.springframework.boot:type=Endpoint,name=Info
```

On the `Info` MBean, locate the `info` operation under **Operations** and invoke it. The result contains sample data with `lesson.topic` as `Spring JMX` and `lesson.mode` as `local`. The tool may present composite data as a JSON string; property ordering is not a contract to rely on.

On the `Health` MBean, inspect the `health` operation and the actual status result. Do not look for the URL `/actuator/health` in the ObjectName tree: that URL belongs to the HTTP channel.

Next, expand the `com.example.jmxlesson` domain and find MBean `type=Sample,name=Counter`. Under **Attributes**, the `Pending` attribute has value `12`. Here, an attribute of a custom Spring MBean and an operation of an Actuator endpoint are presented in two different management structures.

### 6.3. Cross-Checking with HTTP

In another terminal:

```shell
curl -i http://127.0.0.1:8080/actuator/info
```

With the sample application and configuration above, HTTP has no mapping for the `info` endpoint and returns `404`. The `Info` endpoint still exists over JMX because the two exposure lists are independent.

`http://127.0.0.1:8080/actuator/health` is the URL of the endpoint selected for HTTP. The health output and status code may depend on the environment, but not exposing `info` over HTTP does not remove the `Info` MBean.

The project does not include Spring Security. If integrated into a secured application, HTTP codes such as `401` or `403` also depend on the filter chain; do not use that code alone to conclude whether an endpoint is exposed over JMX.

### 6.4. Changing One Condition at a Time

Stop the sample application and run it again with the following command-line argument:

The inventory code will print:


The Actuator endpoint list is empty, while the custom MBean remains. The first line prints only the label `Actuator JMX endpoints:` and ends because `String.join` receives an empty list.

## 7. Seven Tests Against a Real MBeanServer in the Same JVM

Create `src/test/java/com/example/jmxlesson/JmxExposureTest.java`:

```java
package com.example.jmxlesson;

import java.util.List;
import javax.management.MBeanServer;
import javax.management.ObjectName;

import org.junit.jupiter.api.Test;
import org.springframework.boot.DefaultApplicationArguments;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;

import static org.assertj.core.api.Assertions.assertThat;

class JmxExposureTest {
    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withUserConfiguration(JmxApplication.class);

    private List<String> endpoints(MBeanServer server) throws Exception {
        return server.queryNames(
                new ObjectName("org.springframework.boot:type=Endpoint,*"), null)
                .stream()
                .map(name -> name.getKeyProperty("name"))
                .sorted()
                .toList();
    }

    @Test
    void springJmxIsOffByDefault() {
        runner.withPropertyValues("management.endpoints.jmx.exposure.include=health,info")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(context).doesNotHaveBean(MBeanServer.class);
                });
    }

    @Test
    void enablingSpringJmxExposesOnlyHealthByDefault() {
        runner.withPropertyValues("spring.jmx.enabled=true")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(endpoints(context.getBean(MBeanServer.class)))
                            .containsExactly("Health");
                });
    }

    @Test
    void explicitIncludeRegistersHealthAndInfo() {
        runner.withPropertyValues("spring.jmx.enabled=true",
                "management.endpoints.jmx.exposure.include=health,info")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    MBeanServer server = context.getBean(MBeanServer.class);
                    assertThat(endpoints(server)).containsExactly("Health", "Info");
                    assertThat(server.invoke(
                            new ObjectName("org.springframework.boot:type=Endpoint,name=Info"),
                            "info", new Object[0], new String[0]).toString())
                            .contains("Spring JMX");
                    context.getBean(org.springframework.boot.ApplicationRunner.class)
                            .run(new DefaultApplicationArguments(new String[0]));
                });
    }

    @Test
    void exclusionWinsOverInclusion() {
        runner.withPropertyValues("spring.jmx.enabled=true",
                "management.endpoints.jmx.exposure.include=health,info",
                "management.endpoints.jmx.exposure.exclude=info")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(endpoints(context.getBean(MBeanServer.class)))
                            .containsExactly("Health");
                });
    }

    @Test
    void includeCannotReactivateADisabledEndpoint() {
        runner.withPropertyValues("spring.jmx.enabled=true",
                "management.endpoints.jmx.exposure.include=health,info",
                "management.endpoint.info.enabled=false")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(endpoints(context.getBean(MBeanServer.class)))
                            .containsExactly("Health");
                });
    }

    @Test
    void excludingActuatorDoesNotRemoveOtherSpringMBeans() {
        runner.withPropertyValues("spring.jmx.enabled=true",
                "management.endpoints.jmx.exposure.exclude=*")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    MBeanServer server = context.getBean(MBeanServer.class);
                    assertThat(endpoints(server)).isEmpty();
                    ObjectName sample = new ObjectName(
                            "com.example.jmxlesson:type=Sample,name=Counter");
                    assertThat(server.isRegistered(sample)).isTrue();
                    assertThat(server.getAttribute(sample, "Pending")).isEqualTo(12);
                });
    }

    @Test
    void webExposureDoesNotChooseJmxEndpoints() {
        runner.withPropertyValues("spring.jmx.enabled=true",
                "management.endpoints.jmx.exposure.include=health,info",
                "management.endpoints.web.exposure.exclude=*")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(endpoints(context.getBean(MBeanServer.class)))
                            .containsExactly("Health", "Info");
                });
    }
}
```

Run:

```shell
mvn test
```

Success summary:

```text
Tests run: 7, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

The tests use `ApplicationContextRunner` to create and close a Spring context for each configuration. They verify MBean registration and invoke `Info.info` within the same JVM; no remote JMX connection is used and no network HTTP requests are tested.

An important detail: `ApplicationContextRunner` in this code **does not load `application.properties` like a normal SpringApplication run**. Properties for each case are supplied via `withPropertyValues`; as a result, the first two cases genuinely test the default values without being skewed by `spring.jmx.enabled=true` in the sample runtime file.

The test cases confirm:

| Case | Condition | Result |
| --- | --- | --- |
| Spring JMX off by default | Only JMX include declared | No auto-configured MBeanServer bean |
| Spring JMX enabled, default exposure kept | `spring.jmx.enabled=true` | Only `Health` in the Actuator set |
| Selecting `health,info` | JMX enabled, explicit include | `Health` and `Info` present, `info` operation callable |
| Both include and exclude contain `info` | Exclude takes precedence | Only `Health` remains |
| `info` endpoint disabled | Include still contains `info` | `Info` is not exposed |
| All Actuator JMX excluded | `exclude=*` | No Actuator endpoints left, custom MBean still has `Pending=12` |
| HTTP exposure disabled | JMX still selects `health,info` | JMX MBean set still contains `Health`, `Info` |

In the `health,info` case, the code explicitly invokes `ApplicationRunner` to verify the inventory output. The runner does not automatically execute `ApplicationRunner` beans as a full `SpringApplication` startup flow does.

Closing the context after each case allows exporters to unregister MBeans managed by that context. If you write tests that create multiple contexts without closing them, MBean names can collide and affect subsequent test results.

## 8. Naming and Avoiding False Conclusions During Inventory

### 8.1. Endpoint ID and ObjectName

Example:

```text
ID:         health
ObjectName: org.springframework.boot:type=Endpoint,name=Health
```

`org.springframework.boot` is the domain. `type=Endpoint` and `name=Health` are properties of the ObjectName. The display order of key pairs may differ while still identifying the same ObjectName.

Do not use URL strings or full ObjectNames in `management.endpoints.jmx.exposure.include`. Exposure configuration uses endpoint IDs.

### 8.2. Custom Domain

You can change the Actuator domain:

```properties
management.endpoints.jmx.domain=com.example.ops
```

When doing so, the example's inventory code must change its query pattern from `org.springframework.boot:type=Endpoint,*` to `com.example.ops:type=Endpoint,*`. If the old query is kept, an empty list does not prove that endpoints were not exposed.

This **Actuator endpoint** domain property also does not automatically change the ObjectName explicitly declared on `SampleCounter`.

### 8.3. Multiple ApplicationContexts

If there are multiple contexts in the same JVM, MBeans with the same name can collide. Spring Boot has an option:

```properties
spring.jmx.unique-names=true
```

When using unique names or a custom `EndpointObjectNameFactory`, actual ObjectNames may differ from the two simple names in this lesson. Query or inspect the registered names instead of continuing to guess from the default configuration.

Do not enable this option as a cure-all for every JMX error. First determine whether there really are multiple contexts, whether any beans register the same name, and whether they are closed with the proper lifecycle.

## 9. Root-Cause Diagnosis Procedure When an Endpoint Is Missing

### Step 1: Confirm the Right JVM and Effective Configuration

Verify that JConsole is connected to the right process. Check active profiles, command-line arguments, and configuration sources that can override file values. A `spring.jmx.enabled=true` line inside an unloaded file has no effect.

Do not infer Spring JMX status solely from seeing `java.lang`. Look for Actuator MBeans or check the corresponding bean and configuration.

### Step 2: Confirm Endpoint Initialization Conditions

Check the Actuator dependency and the endpoint's own conditions. Built-in endpoints may depend on a library, bean, or application type. An ID in include does not substitute for those conditions.

If an endpoint has been disabled via `management.endpoint.<id>.enabled=false`, resolve enablement before investigating the exposure list.

### Step 3: Read Both JMX Include and Exclude

Check the exact `management.endpoints.jmx.exposure` prefix. An exclude from another profile can still remove an endpoint present in include.

Do not confuse it with `management.endpoints.web.exposure`. The two channels are selected independently.

### Step 4: Inspect the Actual MBeanServer and ObjectName

Look up the right domain, MBean type, and query timing after startup. If there are multiple MBeanServers or custom exporter configuration, verify that the tool and exporter use the same server.

If there is a duplicate-name registration error, inspect startup errors and context lifecycle. A live JVM does not mean all application MBeans were registered successfully.

### Step 5: Separate Registration Errors from Connection Errors

If an in-JVM query sees the endpoint but a remote tool cannot connect, the issue may lie in the connector, address, port, network, TLS, or JMX authentication. Editing `include` will not automatically resolve a connection error.

For local experiments, check that JConsole and the application run under the same account with attach permissions. For containers or separate machines, remote JMX access must be designed separately; do not treat opening the HTTP management port as opening the right channel.

## 10. Verification Practice with Reference Criteria

1. **Keep Spring JMX enabled, remove the explicit include configuration.** Verify that the default set contains only `Health`.
2. **Select `health,info` and then exclude `info`.** Confirm that the `Info` MBean is gone while the custom MBean remains.
3. **Select `health,info` and disable `info` enablement.** Confirm that include does not cause a disabled endpoint to reappear.
4. **Set JMX exclude to `*`.** Confirm that the Actuator set is empty while the `Pending` attribute of the custom MBean is still readable.
5. **Change the Actuator domain.** Update the inventory query and verify that the same endpoints are found under the new domain.
6. **Keep `info` in JMX, and continue not exposing `info` over HTTP.** Compare MBean and HTTP to prove the two channels are independent.

For each trial, change only the condition under test, restart, and cross-check against the MBeanServer. The set of exposed endpoints should be confirmed by the ObjectNames that actually exist, together with the configuration and conditions that produced them.
