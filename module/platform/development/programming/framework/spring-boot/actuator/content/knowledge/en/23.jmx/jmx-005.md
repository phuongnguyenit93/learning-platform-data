# Customizing MBean Domains and Names

## 1. What Components Do Domain and ObjectName Help Identify?

When a JVM contains many MBeans, operators need to distinguish Actuator MBeans, application-provided MBeans, and MBeans from other libraries. If names lack consistency or change unexpectedly, monitoring queries may miss a component even while it is still running.

A familiar Actuator name is:

```text
org.springframework.boot:type=Endpoint,name=Health
```

This string is an **ObjectName**, consisting of:

- **Domain:** `org.springframework.boot`, acting as a namespace.
- **Key–value properties:** `type=Endpoint` and `name=Health`.

A JMX domain is a label inside the MBeanServer. It is not a DNS domain name to resolve, a host address, an HTTP URL, or a Spring bean name.

This lesson uses **Spring Boot 3.3.13** and Java 17+ source code. The example and nine tests below were run on Java 21. We will step through changing the domain, adding labels to default names, and replacing the entire Actuator naming rule with a factory.

## 2. Understand ObjectName Structure Before Renaming

### 2.1. ObjectName Is a Structured Identifier

Common form:

```text
domain:key1=value1,key2=value2
```

In the Health example:

| Part | Value | Meaning in Default Name |
| --- | --- | --- |
| Domain | `org.springframework.boot` | Actuator MBean group |
| Key `type` | `Endpoint` | Identifies the MBean category |
| Key `name` | `Health` | Name derived from endpoint ID `health` |

The `name` key is not mandatory in every ObjectName. It is a naming convention, not a special field mandated by JMX. The custom factory in this lesson will use the key `endpoint` instead of `name`.

Names are case-sensitive. Actuator's ID `health` and the value `Health` in the default name serve different roles; do not alter the ID in exposure configuration simply because you see an uppercase letter in JConsole.

### 2.2. Key Order Does Not Create a New Identifier

The following two ObjectNames are equal:

```text
com.example.ops:type=Endpoint,name=Health
com.example.ops:name=Health,type=Endpoint
```

Because the key–value set is the same, changing the display order does not rename the MBean. When comparing in Java, use `ObjectName.equals`; when you need a stable string for inventorying, you can use `getCanonicalName()`.

The canonical form sorts keys lexicographically. That is why the output lines of the program below put `name` before `type`.

### 2.3. Names Used for Registration vs. Patterns Used for Querying

Specific name:

```text
com.example.ops:type=Endpoint,name=Health
```

Query pattern accepting additional keys:

```text
com.example.ops:type=Endpoint,name=Health,*
```

The trailing `,*` is a property-list pattern allowing an MBean to carry extra keys such as `identity` or `application`. If you omit it, a query with a fixed set of keys will not automatically match a name that has extra keys.

The pattern `name=Health*` means something different: it matches values starting with `Health`. It does not replace the role of `,*` for extra keys.

Pattern-form ObjectNames are for querying; do not use a name containing pattern wildcards as the MBean name to register.

### 2.4. Handling Values with Special Characters

Characters such as commas, colons, or equals signs carry syntactic meaning in names. When placing a dynamic value into an ObjectName property, use `ObjectName.quote(value)` rather than arbitrary string concatenation. This method also escapes wildcards so they become literal data.

For example, an instance label `blue,zone=1:*` must be handled as **a single value**, rather than accidentally turning into multiple properties or a query pattern.

Quotation marks are part of the value representation inside ObjectName: `instance=blue` and `instance="blue"` are two distinct values when comparing names. If a factory chooses an always-quoted form, querying clients must follow the same contract; `getKeyProperty("instance")` returns the quoted representation, which can be decoded via `ObjectName.unquote` when you know the value was quoted.

Rules for key order, patterns, quoting, and canonical names are defined in [the JDK 21 ObjectName API](https://docs.oracle.com/en/java/javase/21/docs/api/java.management/javax/management/ObjectName.html).

## 3. Choosing the Right Configuration by MBean Owner

### 3.1. Dedicated Domain for Actuator Endpoints

To move Actuator endpoints to a dedicated domain:

```properties
spring.jmx.enabled=true
management.endpoints.jmx.domain=com.example.ops
management.endpoints.jmx.exposure.include=health,info
```

With the default factory, unique names disabled, and no name collisions, we get:

```text
com.example.ops:type=Endpoint,name=Health
com.example.ops:type=Endpoint,name=Info
```

Configuring the domain does not enable Spring JMX, does not change the exposure list, and does not change endpoint IDs. Conditions for exposing endpoints still need to be satisfied.

The [Boot 3.3 Monitoring and Management over JMX](https://docs.spring.io/spring-boot/3.3/reference/actuator/jmx.html) guide describes the Actuator domain, default names, and the naming extension point.

### 3.2. Default Domain of Spring JMX

For Spring beans exported via management metadata, you can set:

```properties
spring.jmx.default-domain=com.example.beans
```

In the example, bean `generatedCounter` has class `GeneratedCounter` and `@ManagedResource` without specifying an ObjectName. With this setting, the generated name is:

```text
com.example.beans:type=GeneratedCounter,name=generatedCounter
```

Spring's metadata naming can build names from the class, bean name, and default domain. Without an appropriate default domain, the class package is one source for deriving a domain under the metadata strategy. See [Controlling ObjectName Instances for Your Beans](https://docs.spring.io/spring-framework/reference/integration/jmx/naming.html).

**The two domain properties have different scopes yet have a fallback relationship in Boot 3.3.13's default Actuator factory.** The Actuator domain selection order is:

1. `management.endpoints.jmx.domain` when non-empty.
2. If no dedicated domain is set, `spring.jmx.default-domain` when non-empty.
3. If neither is set, `org.springframework.boot`.

Therefore, do not conclude that `spring.jmx.default-domain` can only affect application MBeans and never affects Actuator. The test program below confirms this precedence on this exact version.

The algorithm can be cross-checked in [DefaultEndpointObjectNameFactory in Boot 3.3.13](https://github.com/spring-projects/spring-boot/blob/v3.3.13/spring-boot-project/spring-boot-actuator-autoconfigure/src/main/java/org/springframework/boot/actuate/autoconfigure/endpoint/jmx/DefaultEndpointObjectNameFactory.java).

### 3.3. Explicitly Declared ObjectName on a Spring Bean

You can specify the name directly via:

```java
@ManagedResource(objectName = "com.example.fixed:type=Counter,name=Inventory")
public class FixedCounter {
    @ManagedAttribute
    public int getPending() {
        return 9;
    }
}
```

The snippet above illustrates the class declaration; the complete file with imports is in section 6. Under the sample configuration, the explicit domain `com.example.fixed` is preserved when changing the Actuator domain or the default domain used for auto-generated names.

Do not use `management.endpoints.jmx.domain` as a switch to rename every MBean in the JVM. Other MBeans may be managed by another library or already have their own naming rules.

### 3.4. Selection Table

| Goal | Mechanism to Consider |
| --- | --- |
| Change Actuator's domain while keeping `type=Endpoint,name=...` | `management.endpoints.jmx.domain` |
| Set default domain for Spring MBeans named from metadata | `spring.jmx.default-domain` |
| Add fixed labels to default Actuator names | `management.endpoints.jmx.static-names` |
| Name a specific Spring MBean | `@ManagedResource(objectName=...)` or corresponding naming strategy |
| Replace the ObjectName structure of Actuator endpoints | `EndpointObjectNameFactory` bean |
| Reduce collisions under the default naming scheme | Consider `spring.jmx.unique-names=true` and context lifecycle |

Spring bean name, endpoint ID, HTTP path, and ObjectName are not four spellings of the same identifier. Renaming a Java bean alone does not change the Actuator ObjectName.

## 4. Adding Labels and Handling Name Collisions

### 4.1. Fixed Labels While Still Using the Default Factory

Example:

```properties
management.endpoints.jmx.domain=com.example.ops
management.endpoints.jmx.static-names.application=orders
management.endpoints.jmx.static-names.instance=blue
```

With the default factory in Boot 3.3.13, a name may contain:

```text
com.example.ops:type=Endpoint,name=Health,application=orders,instance=blue
```

Key display order may vary. These labels add properties without changing the `health` ID or JMX operation names.

Choose custom keys that do not collide with keys used by the factory, such as `type`, `name`, `context`, or `identity`. Duplicate keys within the same ObjectName are invalid. The example uses simple ASCII labels; if values come from data with special characters, manage quoting according to contract rather than assuming any string can be concatenated directly.

### 4.2. Unique Names Under the Default Mechanism

Within one MBeanServer, two MBeans cannot concurrently register the same ObjectName. When multiple ApplicationContexts share one server, collisions can occur.

With the default factory in this version:

```properties
spring.jmx.unique-names=true
```

causes Actuator names to gain an `identity` property. Its value is generated per object on that run; do not copy an observed hex value as a stable identifier across restarts.

The default factory also adds `context` information when it detects an already existing endpoint name. Therefore, in a multi-context environment, do not assume the key set always contains only `type` and `name`.

If a client simply needs to find all Health MBeans in a domain, use a pattern with an appropriate `,*` suffix, then inspect the keys that distinguish instances or contexts.

### 4.3. Uniqueness Scope Is the MBeanServer

Two applications in two separate JVMs can use the same ObjectName without registration conflicts because they reside in different MBeanServers. Adding application or instance labels is still helpful for monitoring organization, though it is not a network-wide uniqueness requirement.

If multiple components truly share the same server, choose an appropriate domain or distinguishing keys and close contexts/exporters with the proper lifecycle. Renaming to avoid collisions does not substitute for fixing an accidentally retained context.

## 5. When Do You Need EndpointObjectNameFactory?

If you only want to change the domain or add a few labels, default configuration is usually enough. When you need to change `type`, replace the `name` key, or build a custom naming structure for every Actuator endpoint, provide an `EndpointObjectNameFactory` bean.

The factory receives an `ExposableJmxEndpoint` and returns an `ObjectName` for that endpoint. It determines the name; it does not create extra endpoints, change exposure lists, alter HTTP routes, or modify management operations.

The example in this lesson adopts a custom convention:

```text
domain=com.example.ops
type=Actuator
endpoint=health
instance="blue"
```

For endpoint `health` and instance `blue`, the concrete ObjectName is:

```text
com.example.ops:type=Actuator,endpoint=health,instance="blue"
```

When a custom factory is registered, Boot uses it instead of the default factory for Actuator endpoints. Do not assume the default factory's rules will still be layered on afterward.

The sample factory below explicitly reads `management.endpoints.jmx.domain` and `demo.instance`. It does **not** re-implement all domain fallback, static-names, or identity rules of the default factory. Without a dedicated domain property, the sample picks `org.springframework.boot` via the fallback written in code. That is the sample factory's contract, not a copy of the default algorithm.

Likewise, enabling `spring.jmx.unique-names=true` does not automatically add `identity` to ObjectNames returned by the sample factory. Collision-avoidance policy when using a custom factory is the application's design responsibility.

### 6.2. Bean Named by Metadata

Create `src/main/java/com/example/naming/GeneratedCounter.java`:

```java
package com.example.naming;

import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedResource;

@ManagedResource
public class GeneratedCounter {
    @ManagedAttribute
    public int getPending() {
        return 12;
    }
}
```

The class does not declare an ObjectName. The bean name `generatedCounter` is provided by the `@Bean` method in the main application.

### 6.3. Bean with an Explicit ObjectName

Create `src/main/java/com/example/naming/FixedCounter.java`:

```java
package com.example.naming;

import org.springframework.jmx.export.annotation.ManagedAttribute;
import org.springframework.jmx.export.annotation.ManagedResource;

@ManagedResource(objectName = "com.example.fixed:type=Counter,name=Inventory")
public class FixedCounter {
    @ManagedAttribute
    public int getPending() {
        return 9;
    }
}
```

This MBean has its own namespace `com.example.fixed`. In the sample's default mode, neither domain property alters this explicitly declared domain.

### 6.4. Application and Optional Factory

Create `src/main/java/com/example/naming/NamingApplication.java`:

```java
package com.example.naming;

import java.util.Hashtable;
import javax.management.MBeanServer;
import javax.management.ObjectName;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.actuate.endpoint.jmx.EndpointObjectNameFactory;
import org.springframework.boot.actuate.info.InfoContributor;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;

@SpringBootApplication
public class NamingApplication {
    public static void main(String[] args) {
        SpringApplication.run(NamingApplication.class, args);
    }

    @Bean
    GeneratedCounter generatedCounter() {
        return new GeneratedCounter();
    }

    @Bean
    FixedCounter fixedCounter() {
        return new FixedCounter();
    }

    @Bean
    InfoContributor lessonInfo() {
        return builder -> builder.withDetail("lesson", "JMX naming");
    }

    @Bean
    @ConditionalOnProperty(name = "demo.custom-names", havingValue = "true")
    EndpointObjectNameFactory customEndpointNames(Environment environment) {
        String domain = environment.getProperty(
                "management.endpoints.jmx.domain", "org.springframework.boot");
        String instance = environment.getProperty("demo.instance", "blue");
        return endpoint -> {
            Hashtable<String, String> keys = new Hashtable<>();
            keys.put("type", "Actuator");
            keys.put("endpoint", endpoint.getEndpointId().toString());
            keys.put("instance", ObjectName.quote(instance));
            return new ObjectName(domain, keys);
        };
    }

    @Bean
    ApplicationRunner inventory(MBeanServer server) {
        return args -> {
            System.out.println("JMX ObjectNames:");
            server.queryNames(new ObjectName("com.example.*:*"), null).stream()
                    .map(ObjectName::getCanonicalName)
                    .sorted()
                    .forEach(System.out::println);
        };
    }
}
```

`demo.custom-names` is a **property specific to the sample project**, not a built-in Spring Boot property. When it is `false`, the custom factory bean is not created and Boot uses the default factory. When `true`, the `type=Actuator,endpoint=...` rule takes effect.

Inside the factory:

1. The domain is taken from the chosen configuration.
2. The endpoint ID distinguishes `health` and `info`.
3. Instance is always processed with `ObjectName.quote`.
4. `Hashtable` holds each individual key and is used to construct the ObjectName.

The `Hashtable`-accepting constructor does not automatically escape all input values; calling `ObjectName.quote` remains necessary per the sample's contract. The domain and keys are controlled by the program, not taken arbitrarily from users.

The inventory code queries `com.example.*:*` to observe the three MBean groups created by the lesson. It prints canonical names and sorts them before output, making comparison easy. In a large application, narrow queries to the domains and MBean types actually being observed.

### 6.5. Default Configuration

Create `src/main/resources/application.properties`:

```properties
server.address=127.0.0.1
spring.jmx.enabled=true
spring.jmx.default-domain=com.example.beans
management.endpoints.jmx.domain=com.example.ops
management.endpoints.jmx.exposure.include=health,info
management.endpoints.web.exposure.include=health
demo.custom-names=false
demo.instance=blue
```

By default, the sample separates the Actuator domain `com.example.ops` and the auto-named Spring bean domain `com.example.beans`. The bean with an explicit ObjectName remains in `com.example.fixed`.

HTTP exposes only `health`. Changing JMX domains does not affect this endpoint's HTTP URL.

## 7. Running and Comparing ObjectNames

### 7.1. Compiling and Running in Default Mode

In the directory containing `pom.xml`:

```shell
mvn package
java -jar target/jmx-naming-demo-1.0.0.jar
```

Maven compiles Java and dependencies; the first run downloads libraries. If the test file in section 8 has been added, `package` also runs the tests.

In addition to startup logs, the inventory code prints:

```text
JMX ObjectNames:
com.example.beans:name=generatedCounter,type=GeneratedCounter
com.example.fixed:name=Inventory,type=Counter
com.example.ops:name=Health,type=Endpoint
com.example.ops:name=Info,type=Endpoint
```

These are canonical names. They are equivalent to ObjectNames with different key ordering but the same domain and values.

The output demonstrates three scopes:

- `GeneratedCounter` uses Spring JMX's default domain.
- `FixedCounter` retains its explicit name.
- `Health` and `Info` use the dedicated Actuator domain.

Both Counter classes return constant numbers to keep the focus on naming mechanics; they do not measure a real queue or data store.

### 7.2. Observing with JConsole

Keep the application running, launch `jconsole` from the JDK, and select the right JVM under an account with local attach permission. In the **MBeans** tab:

- Domain `com.example.ops` contains endpoints under type `Endpoint`.
- Domain `com.example.beans` contains `GeneratedCounter`.
- Domain `com.example.fixed` contains MBean `Counter`, named `Inventory`.

You can read `Pending=12` on the auto-named bean and `Pending=9` on the explicitly named bean. On the `Info` MBean, the `info` operation contains `lesson` data set to `JMX naming`.

The lesson does not configure a remote JMX connector. Domain is an identifier part inside the MBeanServer; changing domains does not open ports or alter connection permissions.

### 7.3. Switching to the Custom Factory

Stop the previous run and execute:

```shell
java -jar target/jmx-naming-demo-1.0.0.jar --demo.custom-names=true
```

Both Spring bean names remain as in default mode. Both Actuator names change to the canonical forms:

```text
com.example.ops:endpoint=health,instance="blue",type=Actuator
com.example.ops:endpoint=info,instance="blue",type=Actuator
```

The default-factory name `com.example.ops:type=Endpoint,name=Health` is no longer present in that run. Consequently, a client continuing to query `type=Endpoint` will not find the new MBeans.

Operations such as `info` remain operations of the same endpoint; renaming the MBean does not change that functionality. The test below invokes `info` using the new ObjectName.

### 7.4. Adding Labels via Properties Instead of Replacing the Factory

When using the default factory, run:

```shell
java -jar target/jmx-naming-demo-1.0.0.jar --management.endpoints.jmx.static-names.application=orders
```

Health's canonical name gains an extra key:

```text
com.example.ops:application=orders,name=Health,type=Endpoint
```

This keeps the `type=Endpoint,name=Health` convention and only adds the `application` label. If you simultaneously enable the sample custom factory, the `static-names` property is not read automatically because that factory code does not implement it.

### 7.5. Enabling Unique Names

In default mode, you can run:

```shell
java -jar target/jmx-naming-demo-1.0.0.jar --spring.jmx.unique-names=true
```

Endpoint names gain an `identity` key. The specific value depends on the run, so there is no fixed hex string to copy into instructions.

To find Health regardless of extra keys, the suitable query pattern is:

```text
com.example.ops:type=Endpoint,name=Health,*
```

When using the sample factory, queries must follow the new convention, such as:

```text
com.example.ops:type=Actuator,endpoint=health,*
```

Run only one instance of the sample application at a time to avoid HTTP port collisions. Spring Boot `--...` configuration arguments go after the JAR name; if using JVM system properties `-D...`, place them before `-jar`.

## 8. Nine Tests Verifying Real Registered Names

Create `src/test/java/com/example/naming/NamingTest.java`:

```java
package com.example.naming;

import java.util.Set;
import javax.management.MBeanServer;
import javax.management.ObjectName;

import org.junit.jupiter.api.Test;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.DefaultApplicationArguments;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;

import static org.assertj.core.api.Assertions.assertThat;

class NamingTest {
    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withUserConfiguration(NamingApplication.class)
            .withPropertyValues("spring.jmx.enabled=true",
                    "management.endpoints.jmx.exposure.include=health,info");

    private ApplicationContextRunner configured() {
        return runner.withPropertyValues(
                "spring.jmx.default-domain=com.example.beans",
                "management.endpoints.jmx.domain=com.example.ops");
    }

    private Set<ObjectName> find(MBeanServer server, String pattern) throws Exception {
        return server.queryNames(new ObjectName(pattern), null);
    }

    @Test
    void explicitDomainsAndExplicitBeanNameHaveSeparateScopes() {
        configured().run(context -> {
            assertThat(context).hasNotFailed();
            MBeanServer server = context.getBean(MBeanServer.class);
            assertThat(find(server, "com.example.*:*"))
                    .extracting(ObjectName::getCanonicalName)
                    .containsExactlyInAnyOrder(
                            "com.example.beans:name=generatedCounter,type=GeneratedCounter",
                            "com.example.fixed:name=Inventory,type=Counter",
                            "com.example.ops:name=Health,type=Endpoint",
                            "com.example.ops:name=Info,type=Endpoint");
            context.getBean(ApplicationRunner.class)
                    .run(new DefaultApplicationArguments(new String[0]));
        });
    }

    @Test
    void actuatorFallsBackToSpringDefaultDomainWhenItsDomainIsUnset() {
        runner.withPropertyValues("spring.jmx.default-domain=com.example.fallback")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    MBeanServer server = context.getBean(MBeanServer.class);
                    assertThat(find(server, "com.example.fallback:type=Endpoint,*"))
                            .hasSize(2);
                    assertThat(find(server, "org.springframework.boot:type=Endpoint,*"))
                            .isEmpty();
                });
    }

    @Test
    void actuatorUsesBootDomainWhenBothDomainPropertiesAreUnset() {
        runner.run(context -> {
            assertThat(context).hasNotFailed();
            assertThat(find(context.getBean(MBeanServer.class),
                    "org.springframework.boot:type=Endpoint,*")).hasSize(2);
        });
    }

    @Test
    void staticNamesAddLabelsWithoutReplacingDefaultEndpointNames() {
        configured().withPropertyValues(
                "management.endpoints.jmx.static-names.application=orders")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    Set<ObjectName> names = find(context.getBean(MBeanServer.class),
                            "com.example.ops:type=Endpoint,*");
                    assertThat(names).hasSize(2);
                    assertThat(names).allSatisfy(name ->
                            assertThat(name.getKeyProperty("application"))
                                    .isEqualTo("orders"));
                });
    }

    @Test
    void defaultFactoryAddsIdentityWhenUniqueNamesAreEnabled() {
        configured().withPropertyValues("spring.jmx.unique-names=true")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    Set<ObjectName> names = find(context.getBean(MBeanServer.class),
                            "com.example.ops:type=Endpoint,*");
                    assertThat(names).hasSize(2);
                    assertThat(names).allSatisfy(name ->
                            assertThat(name.getKeyProperty("identity")).isNotBlank());
                });
    }

    @Test
    void customFactoryReplacesTheActuatorNamingScheme() {
        configured().withPropertyValues("demo.custom-names=true", "demo.instance=blue")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    MBeanServer server = context.getBean(MBeanServer.class);
                    assertThat(find(server, "com.example.ops:type=Endpoint,*")).isEmpty();
                    assertThat(find(server, "com.example.ops:type=Actuator,*")).hasSize(2);
                    ObjectName info = new ObjectName(
                            "com.example.ops:type=Actuator,endpoint=info,instance=\"blue\"");
                    assertThat(server.invoke(info, "info",
                            new Object[0], new String[0]).toString()).contains("JMX naming");
                    assertThat(server.isRegistered(new ObjectName(
                            "com.example.fixed:type=Counter,name=Inventory"))).isTrue();
                });
    }

    @Test
    void customFactoryOwnsItsUniquenessPolicy() {
        configured().withPropertyValues("demo.custom-names=true",
                "spring.jmx.unique-names=true")
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    assertThat(find(context.getBean(MBeanServer.class),
                            "com.example.ops:type=Actuator,*"))
                            .hasSize(2)
                            .allSatisfy(name ->
                                    assertThat(name.getKeyProperty("identity")).isNull());
                });
    }

    @Test
    void quotingMakesAnArbitraryInstanceValueLiteral() {
        String instance = "blue,zone=1:*";
        configured().withPropertyValues(
                "demo.custom-names=true", "demo.instance=" + instance)
                .run(context -> {
                    assertThat(context).hasNotFailed();
                    Set<ObjectName> names = find(context.getBean(MBeanServer.class),
                            "com.example.ops:type=Actuator,*");
                    assertThat(names).hasSize(2).allSatisfy(name -> {
                        assertThat(name.isPattern()).isFalse();
                        assertThat(ObjectName.unquote(name.getKeyProperty("instance")))
                                .isEqualTo(instance);
                    });
                });
    }

    @Test
    void objectNameEqualityAndPropertyListPatternsAreStructural() throws Exception {
        ObjectName first = new ObjectName("com.example.ops:type=Endpoint,name=Health");
        ObjectName reordered = new ObjectName("com.example.ops:name=Health,type=Endpoint");
        ObjectName extended = new ObjectName(
                "com.example.ops:type=Endpoint,name=Health,identity=sample");
        assertThat(first).isEqualTo(reordered);
        assertThat(first.apply(extended)).isFalse();
        assertThat(new ObjectName(
                "com.example.ops:type=Endpoint,name=Health,*").apply(extended)).isTrue();
        assertThat(new ObjectName("com.example.ops:instance=blue"))
                .isNotEqualTo(new ObjectName("com.example.ops:instance=\"blue\""));
    }
```

## 9. Common Mistakes When Renaming

### Changing Default Domain Yet Endpoints Stay in the Old Domain

Check whether `management.endpoints.jmx.domain` is explicitly set. In Boot 3.3.13's default factory, this dedicated domain has higher priority than `spring.jmx.default-domain`.

Also check whether a custom factory reads that property. A factory that builds a hardcoded string will not change simply by adding a property unused by code.

### Changing Actuator Domain Yet Custom Spring Beans Do Not Change

Verify whether the bean is an Actuator endpoint. A bean with `@ManagedResource` and an explicit ObjectName is governed by Spring JMX or its corresponding naming strategy. The Actuator domain is not a global namespace for every MBean.

### Displayed Name Has a Different Order Than Expected

Read individual keys or the canonical name instead of comparing raw strings in typed order. `name=Health,type=Endpoint` and `type=Endpoint,name=Health` can still be the same ObjectName.

### Client Fails to Find MBeans After Enabling Unique Names or Static Names

Inspect the actual registered name to see which keys were added. A query pattern without `,*` may require an exact key set and miss extended names.

Do not delete distinguishing keys just to make an old client match. Update queries alongside a policy for picking the right instance, especially when a pattern matches multiple MBeans.

### Encountering MalformedObjectNameException

Check the domain, duplicate keys, delimiters, and value representation. Directly concatenating an instance containing `,` or `:` can produce an invalid name. Use `ObjectName.quote` for values needing quoting and do not use arbitrary data as key names or domains.

Even inside quotes, unescaped wildcards can still produce a pattern. Use the standard quote method instead of manually prepending and appending quote characters.

### Encountering Duplicate-Name Registration Errors

Inspect which name already exists in the MBeanServer and who owns it. Two beans or two contexts sharing a name can collide. When using a custom factory, ensure every endpoint/instance that must coexist simultaneously receives a distinct ObjectName.

In the sample factory, the tuple domain + endpoint ID + instance is the distinguishing contract. Two contexts using all three identically in the same server can still collide. The default factory's unique-names option does not automatically fix the contract created by a custom factory.

### Using Per-Request Varying Labels

An ObjectName identifies a managed component with a clear lifecycle. Do not generate a new name per request, token, user, or transaction ID merely to attach observability data. That causes MBean counts to grow uncontrollably and creates unregistration overhead.

Choose stable domains and labels by application, component kind, and instances that genuinely need distinction. Names can also be read by management tools; do not put secrets into an ObjectName.

### Confusing Renaming with Changing Functionality or Security

Changing the domain and ObjectName properties does not enable disabled endpoints, modify the exposure list, change HTTP URIs, or add authorization checks. Those configuration layers must be verified separately according to operational requirements.

## 10. Practice with Reference Outcomes

1. **Change the Actuator domain to `com.example.monitor`.** Verify Health and Info move to the new domain; both Counters still follow their own naming mechanisms.
2. **Remove the Actuator domain property while keeping Spring's default domain.** Verify the default factory uses Spring's default domain for Actuator per the version's fallback order.
3. **Add label `application=orders` via static names.** Verify endpoint names gain the key and the `info` operation remains callable.
4. **Enable unique names in default mode.** Verify `identity` is present and a query with `,*` still finds the endpoints.
5. **Enable the custom factory and change instance to a string with commas and wildcards.** Verify the ObjectName is not a pattern and unquoting recovers the exact original string.
6. **Update the client to query under the new factory convention.** Verify it no longer depends on `type=Endpoint` or `name=Health` after the contract has changed.

When choosing a naming convention, align both the registering side and querying tools: which domain is used, which keys are stable, which values are quoted, and how multiple instances are distinguished. Final proof is the registered ObjectName and confirming management operations still execute through that name.
