# Collecting and Storing Dumps Safely for Off-App Analysis

## 1. From Symptoms to Portable Evidence for Analysis

When a Spring Boot application responds slowly, many threads are blocked, or memory climbs steadily, logs usually reveal only what was explicitly logged. Diagnostic snapshots (dumps) add JVM state at a point in time. You can collect snapshots, transfer them to a controlled analysis machine, and investigate without forcing the serving app to bear heavy analysis work.

Within the **Logging and Memory** chapter, this lesson's goal is keeping evidence accurate, complete, and secure from dump request time through retention expiry. Creating a dump still affects the running JVM; only reading, indexing, and analysis are offloaded outside the application.

The workflow should be:

```text
Symptom + right JVM + collection permission
  → choose dump type and timing
  → download to private area, not yet treated as a complete file
  → inspect + record source metadata + compute hash
  → encrypt + transfer via controlled channel
  → verify on receiving machine + analyze on working copy
  → revoke permissions + dispose of copies upon expiration
```

There is no need to take both a thread dump and a heap dump for every incident. Select evidence according to the investigation question before picking an endpoint.

## 2. Distinguishing Dump Types and Each Type's Limits

| Evidence type | Appropriate questions | Collection notes |
| --- | --- | --- |
| Thread dump | Where are threads running, which locks are awaited, are many threads blocked together? | A series of samples spaced apart can be taken for comparison. |
| Heap dump | Which objects occupy or retain large amounts of memory? | Files can be large, contain business data, and cause pauses during creation. |
| Concurrent logs and operational metrics | When did the incident happen, on which deployment, and how did load and GC change? | Select relevant slices; avoid grabbing all data merely for convenience. |

A thread dump is a snapshot of threads, not a complete history of every call. A heap dump is a snapshot of the object graph, not a full copy of the process or all OS memory. RSS growth from native memory or direct buffers is not necessarily explained fully by a heap dump.

With Spring Boot 3.3, `GET /actuator/threaddump` returns JSON or plain text when requesting `Accept: text/plain`. `GET /actuator/heapdump` returns binary data; HotSpot uses HPROF, OpenJ9 uses PHD. Choose a reader compatible with the actual JVM and format rather than inferring format solely from the filename extension. References: [Thread Dump API](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/threaddump.html), [Heap Dump API](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/heapdump.html).

## 3. Why Must Dumps Be Protected from Creation Time?

The heap can hold in-flight passwords, tokens, keys, connection strings, request payloads, customer info, or decrypted data. Not every secret is guaranteed to appear, yet a dump must never be treated as harmless data just because it is not a database.

Thread dumps usually omit full local variable values, yet thread names, stack traces, class names, paths, or application-assigned task names can still disclose internal information. Reports generated by analysis tools can also extract sensitive strings.

Masking values in `env`, in logs, or in UI views does not automatically mask those same values inside a heap dump. Renaming files, compressing with ZIP/GZIP, or changing extensions is not encryption either. Do not put raw dumps into Git, static directories, public download folders, broad-visibility tickets, or external analysis services without authorization.

Three properties must be protected simultaneously:

- **Confidentiality:** who is allowed to create, download, read, and decrypt the dump?
- **Integrity:** does the analyzed file contain the exact bytes collected?
- **Traceability:** which JVM, what timestamp, and which investigation request produced the snapshot?

## 4. Preparing a Bounded Collection Window

### 4.1. Choosing the Exact Process and Weighing Cost

Before calling the endpoint, identify the application, environment, deployment, instance/pod, UTC timestamp, and symptom to explain. In multi-instance systems, calling through a load balancer could take a thread dump from instance A and a heap dump from instance B. Use a fixed management route to the exact instance or a verified routing mechanism.

For thread symptoms, you can start with three thread dumps spaced about 5–10 seconds apart. That is an investigative choice, not a mandatory Actuator interval. If the same thread group stays stuck at the same location across multiple snapshots, evidence is stronger than a single snapshot.

For heap dumps, evaluate tolerable latency, disk space, container limits, and service continuity beforehand. A single HTTP `GET` can still trigger resource-intensive diagnostic work. Do not place this endpoint into health checks or monitoring scrape schedules.

Distinguish **the disk of the JVM creating the dump** from **the disk of the machine downloading the dump**. In Spring Boot 3.3's HotSpot implementation, the dump is written to a temporary file on the server side before streaming back. Thus free space on the downloader does not mean the server has free space. Check where the JVM puts temp files; `/tmp` mounted on tmpfs or a memory-backed volume can heighten memory pressure instead of relieving it.

Do not estimate dump size as equal to `-Xmx` and treat that as a hard upper bound. Budget for temp files, downloaded copies, encrypted bundles, and analysis tool index files. Base thresholds and collection windows on the real environment.

### 4.2. Separating Three Actuator Access Conditions

With Spring Boot 3.3, distinguish an endpoint being **enabled**, **exposed over HTTP**, and the caller being **authenticated/authorized**. By default HTTP exposes only `health`. The configuration below is an addition for an app that already has Actuator, not a complete security configuration:

```yaml
management:
  server:
    port: 9091
  endpoints:
    web:
      exposure:
        include: "health,threaddump,heapdump"
  endpoint:
    threaddump:
      enabled: true
    heapdump:
      enabled: true
```

Reference on endpoint configuration and security: [Spring Boot 3.3 — Endpoints](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html).

Port `9091` in the example must be restricted via a management network, firewall, or gateway; separating ports alone creates no protection. Apply dedicated permissions for operators who need to collect dumps and use TLS in transit. When the application has custom Spring Security config, inspect rules for Actuator directly instead of assuming adding a dependency suffices.

Do not open `include: "*"` just to grab one dump. If an endpoint is opened only temporarily for an incident, record when to close it and how to revert the configuration. The YAML above is for the 3.3 line; do not mechanically apply newer versions' `access` settings to this application.

## 5. Verified Downloading Without Mistaking Error Files for Dumps

### 5.1. Prerequisites for the Example

The example below is a **Linux Bash script** run on a collector machine authorized to reach the management network. It requires `curl`, `mktemp`, `date`, `wc`, `grep`, `head`, `mv`, `sleep`, and `sha256sum`. This is not PowerShell code and not commands to run on production machines just for study.

It assumes the HTTPS endpoint routes to **one specific instance**, does not redirect to a login page, and uses HTTP Basic with an account authorized for diagnostics. If your environment uses mTLS or another mechanism, swap authentication settings to match that environment's procedure.

Before running:

- Set `CAPTURE_ROOT` to a private collector directory with mode `700`, on controlled storage with sufficient space.
- Set `ACTUATOR_BASE` to the instance's real HTTPS URL, e.g. `https://ops.example.com:9443/actuator`; omit a trailing `/`.
- Set `ACTUATOR_NETRC` to the absolute path of a securely provisioned netrc file, mode `600`, holding only credentials needed for that host. Do not copy this file into the dump bundle. Do not pass passwords directly on the command line or enable `set -x`.
- Set `INCIDENT_ID`, `INSTANCE_ID`, and `DEPLOYMENT_ID` to internal non-secret identifiers. JVM version details are added to the investigation record from verified operational sources.

There are no sample accounts/passwords in this lesson. The variables above are required inputs; the script aborts immediately if any are missing.

### 5.2. Collection Script

```bash
#!/usr/bin/env bash
set -euo pipefail
umask 077

: "${CAPTURE_ROOT:?Private capture directory required}"
: "${ACTUATOR_BASE:?HTTPS URL of exact instance required}"
: "${ACTUATOR_NETRC:?Securely provisioned netrc file required}"
: "${INCIDENT_ID:?Incident ID required}"
: "${INSTANCE_ID:?Instance ID required}"
: "${DEPLOYMENT_ID:?Deployment ID required}"

[[ -d "$CAPTURE_ROOT" && -w "$CAPTURE_ROOT" ]]
[[ -r "$ACTUATOR_NETRC" ]]
[[ "$ACTUATOR_BASE" == https://* ]]

capture_dir=$(mktemp -d "$CAPTURE_ROOT/capture.XXXXXXXX")
chmod 700 "$capture_dir"

printf 'incident=%s\ninstance=%s\ndeployment=%s\n' \
  "$INCIDENT_ID" "$INSTANCE_ID" "$DEPLOYMENT_ID" \
  > "$capture_dir/metadata.txt"
printf 'collection_started_utc=%s\n' \
  "$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$capture_dir/metadata.txt"

fetch_dump() {
  local endpoint="$1"
  local accept="$2"
  local filename="$3"
  local timeout_seconds="$4"
  local part="$capture_dir/$filename.part"
  local http_code started finished

  started=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  if ! http_code=$(curl --disable \
    --silent --show-error --fail \
    --proto '=https' \
    --connect-timeout 10 --max-time "$timeout_seconds" \
    --netrc-file "$ACTUATOR_NETRC" \
    --header "Accept: $accept" \
    --output "$part" --write-out '%{http_code}' \
    "$ACTUATOR_BASE/$endpoint"); then
    printf 'Download failed; .part file not accepted: %s\n' \
      "$filename" >&2
    return 1
  fi

  if [[ "$http_code" != 200 || ! -s "$part" ]]; then
    printf 'Invalid HTTP status or empty file: %s\n' \
      "$filename" >&2
    return 1
  fi

  case "$filename" in
    thread-*.txt)
      if ! grep -Fq 'java.lang.Thread.State:' "$part"; then
        printf 'Unrecognized text thread dump\n' >&2
        return 1
      fi
      ;;
    heap.hprof)
      if [[ "$(head -c 12 "$part")" != 'JAVA PROFILE' ]]; then
        printf 'Unrecognized HPROF file header\n' >&2
        return 1
      fi
      ;;
  esac

  mv -- "$part" "$capture_dir/$filename"
  finished=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  printf 'file=%s start_utc=%s end_utc=%s bytes=%s\n' \
    "$filename" "$started" "$finished" \
    "$(wc -c < "$capture_dir/$filename")" \
    >> "$capture_dir/metadata.txt"
}

for sample in 1 2 3; do
  fetch_dump 'threaddump' 'text/plain' "thread-$sample.txt" 120
  if [[ "$sample" != 3 ]]; then
    sleep 5
  fi
done

# Enable this branch only after assessing cost and confirming a heap dump is needed.
if [[ "${CAPTURE_HEAP:-no}" == yes ]]; then
  fetch_dump 'heapdump?live=true' \
    'application/octet-stream' 'heap.hprof' 600
fi

printf 'collection_finished_utc=%s\n' \
  "$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$capture_dir/metadata.txt"

(
  cd "$capture_dir"
  files=(metadata.txt thread-1.txt thread-2.txt thread-3.txt)
  if [[ -f heap.hprof ]]; then
    files+=(heap.hprof)
  fi
  sha256sum "${files[@]}" > SHA256SUMS
  sha256sum -c SHA256SUMS
)

printf 'Collection complete: %s\n' "$capture_dir"
```

Run the script with `CAPTURE_HEAP=yes` only when a heap dump is needed and its cost has been accepted. By default the script collects only three thread dumps. `120` and `600` seconds are sample client-side timeout budgets, not completion guarantees from Actuator.

The script uses fixed filenames inside a private randomized directory, writing to `.part` before renaming. It never uses filenames supplied by HTTP headers to decide paths. `curl --disable` comes first among options so default curl config files cannot alter behavior. Redirect following, automatic retries, and TLS certificate skipping are not enabled. Option details: [curl manual](https://curl.se/docs/manpage.html).

Checking HTTP `200`, non-zero size, and format signatures catches common mistakes such as downloading a login page. This is only screening: a file with a valid HPROF header can still be truncated; opening cleanly in a compatible analyzer is needed for further confirmation. A corrupted file still hashes normally.

`sha256sum -c` output when collecting only thread dumps looks like:

```text
metadata.txt: OK
thread-1.txt: OK
thread-2.txt: OK
thread-3.txt: OK
Collection complete: <newly created capture directory>
```

The path line varies per run; when a valid heap dump is included, `heap.hprof: OK` also appears. There is no fixed SHA-256 hash to embed in the lesson because dumps contain time-varying data.

### 5.3. HotSpot Scope and Failure Behavior

The heap branch in the script targets **HotSpot**: `live=true` selects reachable objects; it does not mean streaming live data, masking secrets, or guaranteeing low impact. In Spring Boot 3.3.13's code, HotSpot defaults to `true` if this parameter is omitted; OpenJ9 does not support passing `live`. Thus do not reuse the HotSpot branch verbatim for OpenJ9: omit the parameter, adjust filename/checks for PHD, and verify with a matching reader. Source: [HeapDumpWebEndpoint 3.3.13](https://raw.githubusercontent.com/spring-projects/spring-boot/v3.3.13/spring-boot-project/spring-boot-actuator/src/main/java/org/springframework/boot/actuate/management/HeapDumpWebEndpoint.java).

If an error occurs, the script stops and keeps files in the private directory for deliberate operator handling. `.part` files can still contain real data and must be protected like complete dumps. Do not promote a directory from a failed capture into a finished evidence bundle.

A client timeout or dropped connection **does not prove** the JVM canceled dump creation. Check JVM status, resources, and server-side temp files before requesting again. Automatic retries can create multiple large snapshots right when the system is overloaded.

## 6. When HTTP Is Not the Right Collection Path

If the application cannot serve HTTP yet operators still have access to the right host/container and a compatible JDK, JVM tools can be considered. The commands below are a HotSpot Bash example, with a verified `TARGET_PID` and `SERVER_CAPTURE_DIR` as a private directory writable by the JVM account with enough space:

```bash
: "${TARGET_PID:?Verified PID required}"
: "${SERVER_CAPTURE_DIR:?JVM-side directory required}"
jcmd "$TARGET_PID" Thread.print -l \
  > "$SERVER_CAPTURE_DIR/threads.txt"
jcmd "$TARGET_PID" GC.heap_dump \
  "$SERVER_CAPTURE_DIR/heap.hprof"
```

`jcmd` requires appropriate process access permissions and must run on the same host as the JVM; with containers, account for PID namespaces and attach restrictions. Per JDK 21 docs, `GC.heap_dump` is high-impact and requests a full GC unless `-all` is used. Do not casually add `-all` to "go faster" because it changes the set of objects recorded. Source: [JDK 21 — jcmd](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jcmd.html).

The heap dump path is resolved by the JVM process; the `>` on the thread dump command is redirection by the invoking shell. If the shell and JVM live in different filesystem views, do not assume both files land in the same place. Dumps created with `jcmd` must still go through verification, provenance recording, hashing, and protection just like dumps downloaded via Actuator.

`-XX:+HeapDumpOnOutOfMemoryError` can help capture evidence before manual intervention, provided destination path and disk space are prepared ahead of time. Not every OS OOM-kill of a container passes through Java `OutOfMemoryError` or leaves a dump behind. Do not wait for an incident and treat this flag as an evidence recovery guarantee.

## 7. Recording Provenance and Verifying Integrity

Each collection needs a small manifest stored alongside the dump, including:

- Incident ID, owner, and reason for collection.
- Application, environment, instance/pod, deployment; verified Java version and JVM type.
- UTC start/end timestamps; clock sync status if correlating multiple systems.
- Dump type, collection path, and impactful parameters such as `live=true`.
- Filenames, sizes, SHA-256 hashes; errors or uncaptured data intervals.
- Authorized storage location, authorized reader group, review/deletion date, and decryption key owner.

The script fills in only what it knows directly. Supplement the rest from operational sources rather than guessing JVM version or instance from filenames. If editing `metadata.txt` after hashing, update the manifest before encrypting and note the manifest completion. Never modify the original dump to make its contents match the manifest.

SHA-256 detects whether bytes changed, yet if both the dump file and checksum file can be altered by another party, verification can still report success. When sender authenticity matters, use authenticated channels, trusted access logs, or organizational signatures. A hash does not replace source authentication and does not prove semantic completeness of the dump.

Keep a verified original with restricted write access; analyze on a working copy. Do not overwrite multiple snapshots under the same `heap.hprof` name in one folder and lose earlier baselines.

## 8. Encrypting the Evidence Bundle and Handing Off

### 8.1. Access Control Must Continue After Download

Staging storage should belong to a dedicated account on protected disk, avoiding auto-synced folders and uncontrolled backups. Unix permissions `700/600` do not replace object storage ACLs or permissions on the recipient's machine. Grant access only to people needed for investigation, with an expiration and read/download audit logs.

With object stores, use private buckets/containers, proper encryption, and lifecycle policies. If issuing signed download URLs, treat the URL as a credential: restrict lifetime and recipients, and avoid pasting it into logs or widely visible tickets. Data still needs protection after the URL expires.

### 8.2. Example Encryption Before Transfer

This example uses `age`, `tar`, and `sha256sum` on Linux. This is an illustrative tool choice; organization-approved encryption tools can be used instead. `RECIPIENTS_FILE` must contain the intended recipient's public key, verified over a trusted channel. Decryption private keys are never included in the sent bundle.

Run only after collection succeeds and the manifest is verified. Variables are verified real paths; `HANDOFF_ROOT` is a dedicated mode-`700` handoff directory outside `CAPTURE_DIR`:

```bash
set -euo pipefail
umask 077
: "${CAPTURE_DIR:?Successful capture directory required}"
: "${HANDOFF_ROOT:?Private handoff directory required}"
: "${RECIPIENTS_FILE:?Verified public key list required}"
[[ -d "$HANDOFF_ROOT" && -w "$HANDOFF_ROOT" ]]
[[ -r "$RECIPIENTS_FILE" ]]

(
  cd "$CAPTURE_DIR"
  sha256sum -c SHA256SUMS
)

handoff_dir=$(mktemp -d "$HANDOFF_ROOT/handoff.XXXXXXXX")
archive="$handoff_dir/evidence.tar.gz.age"
items=(metadata.txt SHA256SUMS thread-1.txt thread-2.txt thread-3.txt)
if [[ -f "$CAPTURE_DIR/heap.hprof" ]]; then
  items+=(heap.hprof)
fi

tar -C "$CAPTURE_DIR" -czf - -- "${items[@]}" \
  | age -R "$RECIPIENTS_FILE" -o "$archive.part"
mv -- "$archive.part" "$archive"

(
  cd "$handoff_dir"
  sha256sum evidence.tar.gz.age > evidence.tar.gz.age.sha256
  sha256sum -c evidence.tar.gz.age.sha256
)
printf 'Encrypted bundle: %s\n' "$archive"
```

`set -o pipefail` ensures the packaging step is not treated as successful if `tar` fails even if the downstream command finishes. The file list is explicit so `.part`, credential files, or stray files are not swept in. Compression reduces size; `age` itself performs encryption. Tool syntax: [age](https://github.com/FiloSottile/age).

Send the encrypted bundle and checksum over an authorized internal channel; verify the exact destination before transmitting. After receipt, check the bundle checksum, decrypt on an authorized machine, and verify the inner `SHA256SUMS`. If any step fails, keep the status "unverified" and do not broaden sharing permissions so random people can try opening it.

Extract bundles only from verified sources into an empty private directory. Being able to decrypt does not prove who created the bundle: anyone holding the public key can encrypt to the recipient.

## 9. Analyzing Outside the Application While Respecting Evidence Limits

The analysis machine needs sufficient RAM, disk space for indexes, and restricted access. Use approved tools supporting the exact format; avoid syncing dumps or reports to a tool's default cloud service. Index files, temp files, screenshots, and exported reports all fall within the data-protection scope.

With thread dumps, compare snapshots in chronological order, observing execution points and lock-wait relationships. A `WAITING` thread is not automatically an error; idle workers in a thread pool can be completely normal. Conversely, an identical stack trace across multiple captures must be placed alongside actual load, CPU metrics, and logs to explain.

With HotSpot heap dumps, you can use Eclipse Memory Analyzer (MAT) to find object groups retaining large memory, inspect the Dominator Tree, and trace reference paths to GC roots. **Shallow size** is the object's own size; **retained size** relates to memory kept alive through it. A collection with a small shallow size can still retain an entire large set of objects. Reference: [MAT — Dominator Tree](https://help.eclipse.org/latest/topic/org.eclipse.mat.ui.help/concepts/dominatortree.html).

A large heap dump or a "leak suspect" report is not enough to prove a memory leak. Connect it to data lifecycles, cache bounds, and trends over time. Do not take extra heap dumps on a critically stressed system just for a prettier comparison set; base further captures on risk and unanswered questions.

Investigation reports should reference concrete evidence such as timestamps, files, thread groups, or retention chains. When sharing conclusions, prefer summaries with sensitive data stripped; do not attach the entire dump if recipients only need the conclusion.

## 10. Closing Collection and Disposing of Copies

After handoff, confirm the recipient verified the encrypted bundle, decrypted it, and opened the dump with an appropriate tool. Then close any temporarily opened endpoints or access paths, revoke short-lived accounts/permissions, and record where copies remain.

Do not assume completing a download deleted the dump on the server. Deployment, JVM version, collection path, and failure scenarios can leave server-side files behind. Check the exact file/account/directory used; do not wipe all of `/tmp` or a shared volume just to clean up one incident.

When retention expires, account for originals, `.part` files, encrypted bundles, decrypted copies, working directories, indexes, reports, snapshots, backups, and old versions in object stores. For data under legal/incident hold, apply appropriate preservation policy before deleting. Do not promise that deleting a filename or running an overwrite command guarantees erasing every byte on SSDs, snapshots, or backup systems.

Retain necessary audit logs and conclusions instead of keeping dumps indefinitely. A complete closure policy must answer: who still has read access, which copies still exist, and when each copy was disposed of.

## 11. Common Mistakes and How to Handle Them

| Symptom or habit | Issue | How to handle |
| --- | --- | --- |
| HTTP `401`/`403` | Missing authentication or missing permission. | Check account and policy; do not expose the endpoint publicly to bypass errors. |
| HTTP `404` | Possible wrong port/base path, endpoint disabled, or not exposed. | Verify the management route and effective config of the exact instance. |
| HTTP `200` yet file is HTML | May have downloaded a login page or gateway content. | Check format signatures and routing policy; do not treat as a valid dump. |
| Connection times out, tempted to retry immediately | JVM may still be creating the snapshot; partial files also contain sensitive data. | Check server side, handle `.part`, then decide on another capture. |
| Saving to RAM-backed temp volume or nearly full volume | Creating a dump can worsen resource pressure. | Prepare destination path and quotas beforehand; consider lower-cost evidence. |
| Gzipping and sending over chat | Compression does not protect contents and makes copy tracking hard. | Encrypt, restrict recipients, and use a controlled handoff location. |
| Checksum matches, concluding the file is surely complete | Checksum only confirms bytes against a reference value. | Check provenance, format, and readability with an analyzer. |
| Analyzing directly on the original and editing/recompressing over it | Loses ability to verify against the initial evidence. | Keep the verified original untouched; create a separate working copy. |
| Capturing through a load balancer address | Files may come from different JVMs. | Pin the instance and clearly record each capture's source. |

## 12. Practice in a Test Environment

Use a Spring Boot 3.3 application on HotSpot/JDK 21 with synthetic data. Prepare an authenticated HTTPS management route and a known instance, then:

1. Run the thread dump branch; verify three files exist, distinct capture timestamps are recorded, and the manifest validates cleanly.
2. Observe one thread group across all three snapshots, explaining what is normal waiting and what is a hypothesis needing further checks. Do not draw conclusions from a state name alone.
3. When resources permit, enable the heap branch once. Open the working copy with an HPROF-capable tool and record one object-retaining reference chain; do not use real customer data.
4. Encrypt the bundle, transfer within the test scope, and verify checksums before and after decryption. Only someone holding the corresponding private key may decrypt.
5. On **a test copy**, modify one byte and run checksum verification; confirm verification now fails. Keep the original untouched.
6. Inventory and dispose of test copies, including `.part` files, index files, and temporary permissions granted.

You are done when you can identify the exact source JVM, explain the cost of dump creation, detect corrupted/error downloads, hand off an encrypted bundle, and prove the recipient analyzed the exact snapshot collected.
