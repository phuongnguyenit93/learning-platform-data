# Reading Build Metadata from META-INF/build-info.properties

When two machines run the same application yet produce different results, the first question is usually: "Are both machines actually running the same build?". Information in the source repository cannot answer that: the deployed JAR file may have been created from an earlier build.

Build metadata is a set of data describing the produced artifact, such as its name, artifact coordinates, version, and build timestamp. Spring Boot has a convention of storing this data at `META-INF/build-info.properties` on the classpath, reading it into a `BuildProperties` object, and optionally exposing it via Actuator's application information.

This lesson focuses on the path **resource file → BuildProperties → application code**, while explaining Actuator's place in that path. Examples use Java 21 and Spring Boot 3.3.0; API links below belong to the 3.3 line.

## 1. Understanding the Exact Data You Are Reading

### 1.1. The Build, the Running Process, and the Source Code Are Different Objects

Suppose a `1.2.0` JAR was built at 04:05 UTC and then restarted multiple times. The `build.time` field still describes that build, and does not become the new startup timestamp.

It is also necessary to distinguish:

- The application version set by the project, for example `1.2.0`.
- The commit identifier managed by Git.
- The startup time of a JVM process.
- The packaging timestamp of the build.

A version number can be reused across multiple builds; a commit can be built multiple times. Therefore, do not treat `build.version` alone as proof that two JAR files are identical, or treat application-published metadata as an integrity verification mechanism.

### 1.2. What Does the .properties File Contain?

Here is fixed sample data used for hands-on practice:

```properties
build.group=com.example
build.artifact=build-info-demo
build.name=Build Info Demo
build.version=1.2.0
build.time=2025-02-03T04:05:06Z
build.channel=training
```

| Key in file | Meaning in example | How to read from BuildProperties |
| --- | --- | --- |
| `build.group` | Project group `com.example` | `getGroup()` |
| `build.artifact` | Artifact name `build-info-demo` | `getArtifact()` |
| `build.name` | Display name `Build Info Demo` | `getName()` |
| `build.version` | Version `1.2.0` | `getVersion()` |
| `build.time` | Build timestamp, expressed in UTC | `getTime()` returns `Instant` |
| `build.channel` | Example custom property | `get("channel")` |

The display name and artifact name can differ. `Build Info Demo` is meant for human reading, while `build-info-demo` fits artifact identification in packaging systems.

Standard accessor methods may return `null` when the corresponding field is absent. `getTime()` can also return `null` when the timestamp value cannot be parsed; in that case you can read the raw value with `get("time")` to diagnose. See [BuildProperties 3.3 API](https://docs.spring.io/spring-boot/3.3/api/java/org/springframework/boot/info/BuildProperties.html).

## 2. How Does the File Become a Bean?

### 2.1. Location on the Classpath

Spring Boot's default path is:

```text
classpath:META-INF/build-info.properties
```

If writing a sample file manually for learning, place it at:

```text
src/main/resources/META-INF/build-info.properties
```

If generated by Spring Boot 3.3's Gradle task, the output location is typically:

```text
build/resources/main/META-INF/build-info.properties
```

For an executable JAR using the default `bootJar` layout, application resources reside at:

```text
BOOT-INF/classes/META-INF/build-info.properties
```

`BOOT-INF/classes/` is a packaging detail. Application code still looks up `META-INF/build-info.properties` from the classpath.

Do not concatenate project directory paths to read this resource with `new File(...)`. That approach might work inside an IDE but fails when the resource lives inside a JAR. When reading manually, use a resource stream; in a normal Spring Boot application, use the pre-configured bean.

### 2.2. Stripping the build. Prefix Is Done by Auto-Configuration

In an application with Spring Boot auto-configuration, `ProjectInfoAutoConfiguration`:

1. Checks the resource at the configured location.
2. If the resource exists and no `BuildProperties` bean exists yet, loads the file contents.
3. Selects keys starting with `build.`.
4. Strips that prefix and constructs `BuildProperties`.

Thus, the actual mapping is:

```text
File:                 build.version=1.2.0
Key in object:        version
How to read:          build.getVersion() or build.get("version")
```

Additional properties follow the same rule:

```text
File:                 build.channel=training
Key in object:        channel
How to read:          build.get("channel")
```

`build.get("build.version")` does not look up the key as written in the original file; in this example it returns `null`. Conversely, a line written simply as `version=1.2.0` in the file will not be imported by this mechanism as the version field.

This is the behavior of the loading step in [ProjectInfoAutoConfiguration](https://github.com/spring-projects/spring-boot/blob/v3.3.13/spring-boot-project/spring-boot-autoconfigure/src/main/java/org/springframework/boot/autoconfigure/info/ProjectInfoAutoConfiguration.java). Do not assume the `new BuildProperties(properties)` constructor always strips the prefix itself: if constructing the object manually, the caller must supply normalized keys such as `version`, `artifact`, and `time`.

### 2.3. Having a Bean Does Not Mean Having an HTTP Endpoint

Reading `BuildProperties` can take place in an application that does not run a web server. Actuator is just one consumer of that information.

When appropriate configuration conditions are met, `BuildInfoContributor` puts the information into the `build` group of the `info` endpoint. Accessing it over HTTP additionally requires a web application, the endpoint enabled, web exposure enabled, and caller authorization. The mere presence of the file does not satisfy those HTTP conditions.

## 3. Choosing How to Provide the File for Practice

There are two independent ways to practice. **Pick one approach per run**, avoiding two competing sources for the same resource.

### Approach A: Using a Sample File to Isolate Reading

Put the sample content from section 1.2 directly into `src/main/resources/META-INF/build-info.properties`. Do not enable `springBoot.buildInfo()` yet.

This approach suits observing bean loading and data reading before learning the build task. The timestamp in the file is intentionally mocked data, not the actual compilation time.

In real projects, maintaining the version manually long-term easily causes drift: changing `project.version` while forgetting to update the file causes the application to report an old version.

### Approach B: Letting Gradle Generate the File

With Spring Boot Gradle Plugin 3.3, add `springBoot { buildInfo() }` to provide the `bootBuildInfo` task. When the Java plugin is applied, the `classes` task is wired to this info-generation task. Standard fields are pulled from project information, and custom fields can be added.

That is a resource-generation mechanism, not an API call into a running application. DSL details and output are described in [Spring Boot 3.3 — Integrating with Actuator](https://docs.spring.io/spring-boot/3.3/gradle-plugin/integrating-with-actuator.html).

In a multi-module project, you must configure the specific project that produces the JAR being inspected. A `build-info.properties` generated in another module does not automatically become the right metadata for the current application.

## 4. Complete Example: Reading Information at Application Startup

This is a small standalone practice project that needs no controller or HTTP port. Prepare JDK 21 and Gradle Wrapper 8.5. The first build needs to download plugins and dependencies if they are not already cached.

### 4.1. File Structure

```text
build-info-demo/
├── settings.gradle
├── build.gradle
└── src/main/
    ├── java/example/BuildInfoDemo.java
    └── resources/application.properties
```

For Approach A, add `src/main/resources/META-INF/build-info.properties` and remove the `springBoot` block below. For Approach B, keep that block and do not create the sample file in `src/main/resources`.

### 4.2. settings.gradle

```groovy
rootProject.name = 'build-info-demo'
```

### 4.3. build.gradle

```groovy
import java.time.Instant

plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.0'
    id 'io.spring.dependency-management' version '1.1.5'
}

group = 'com.example'
version = '1.2.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}

springBoot {
    buildInfo {
        properties {
            name = 'Build Info Demo'
            time = Instant.parse('2025-02-03T04:05:06Z')
            additional = ['channel': 'training']
        }
    }
}
```

The example fixes `time` so learners can compare results. When using the default build timestamp, remove the `time` assignment line; stdout for that field will change on each build.

Inside `additional`, write `channel`, not `build.channel`: the generator task is responsible for adding the prefix. Never put passwords, tokens, or personal data into packaged metadata.

### 4.4. application.properties

```properties
spring.main.web-application-type=none
spring.main.banner-mode=off
spring.main.log-startup-info=false
logging.level.root=OFF
```

These settings make the example print only the data being observed. Turning off logging like this is for the practice exercise; when diagnosing startup failures, turn logging back on to read the cause.

### 4.5. BuildInfoDemo.java

```java
package example;

import org.springframework.beans.factory.ObjectProvider;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.info.BuildProperties;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class BuildInfoDemo {
    public static void main(String[] args) {
        SpringApplication.run(BuildInfoDemo.class, args);
    }

    @Bean
    ApplicationRunner printBuild(ObjectProvider<BuildProperties> provider) {
        return args -> {
            BuildProperties build = provider.getIfAvailable();
            if (build == null) {
                System.out.println("build-info=missing");
                return;
            }

            System.out.println("group=" + build.getGroup());
            System.out.println("artifact=" + build.getArtifact());
            System.out.println("name=" + build.getName());
            System.out.println("version=" + build.getVersion());
            System.out.println("time=" + build.getTime());
            System.out.println("channel=" + build.get("channel"));
            System.out.println("prefixedLookup=" + build.get("build.version"));
        };
    }
}
```

`ObjectProvider` handles the case where the bean is not created because the resource is missing, which commonly happens when an IDE does not run the metadata-generation task. It does not hide all configuration errors: if the file exists yet cannot be read, bean creation can still fail.

If build information is mandatory for operation, you can inject `BuildProperties` directly and let the application fail to start when the bean is missing. Whether it is required or optional should be deliberate; do not invent a "valid-looking" version to mask missing data.

### 4.6. Building and Running the JAR

On Windows, run from the project directory:

```powershell
.\gradlew.bat clean bootJar
java -jar build/libs/build-info-demo-1.2.0.jar
```

On Linux/macOS, replace the first command with `./gradlew clean bootJar`.

With the fixed data above, the application's stdout is:

```text
group=com.example
artifact=build-info-demo
name=Build Info Demo
version=1.2.0
time=2025-02-03T04:05:06Z
channel=training
prefixedLookup=null
```

Gradle messages are output from the build tool and are not part of the application stdout shown above.

The last line is an intentional check: it demonstrates the difference between the key name in the file and the key name `BuildProperties` uses. Do not keep that incorrect lookup in production business code.

### 4.7. Observing When the File Is Absent

For Approach A, remove the sample file and perform a clean rebuild. For Approach B, remove the `springBoot { buildInfo { ... } }` block and rerun `clean bootJar`.

Application output:

```text
build-info=missing
```

The `clean` command prevents reusing resources generated from a previous build. If you only delete configuration while an old file remains in previous build outputs, you might mistakenly think Spring Boot generates metadata itself at startup.

Here, the application still runs because the information is treated as optional. That differs from the case where the bean exists yet `build.version` specifically is missing: in that case the program still prints the lines and the version line will be `version=null`.

## 5. Reading the Resource Manually When Truly Needed

If diagnosing raw data, you can read the resource before the prefix-stripping step. The snippet below is **an illustrative method placed inside a Spring application class**, not a standalone program:

```java
import java.io.IOException;
import java.io.InputStreamReader;
import java.io.Reader;
import java.nio.charset.StandardCharsets;
import java.util.Properties;

import org.springframework.core.io.ClassPathResource;

static Properties readRawBuildInfo() throws IOException {
    var resource = new ClassPathResource("META-INF/build-info.properties");
    var raw = new Properties();

    try (Reader reader = new InputStreamReader(
            resource.getInputStream(), StandardCharsets.UTF_8)) {
        raw.load(reader);
    }

    return raw;
}
```

At the raw data layer, you must look up `raw.getProperty("build.version")`. No automatic prefix stripping has taken place yet.

Reading via `getInputStream()` avoids assuming the resource is a file sitting directly on the filesystem. `try-with-resources` closes the stream after reading. If the resource does not exist, this method throws an I/O error; it has no fallback branch like the `ObjectProvider` example.

The illustration explicitly chooses UTF-8. If non-ASCII strings are present, how the file is generated and how it is read must align; do not treat `Properties.load(InputStream)` and `Properties.load(Reader)` as having identical decoding rules. The lesson's metadata sample uses ASCII so it does not depend on this difference.

For standard Spring Boot paths, avoid re-loading the file independently in every place that needs the version. Sharing `BuildProperties` ensures components read the same data model.

## 6. Connection to /actuator/info

The example in section 4 intentionally does not run a web server. To observe the same metadata over HTTP in a test web application:

1. Add `spring-boot-starter-web` to dependencies.
2. Remove `spring.main.web-application-type=none`.
3. Keep providing the file using one of the two chosen approaches.
4. Configure exposure of the `info` endpoint.

Additional configuration:

```properties
management.endpoints.web.exposure.include=health,info
management.info.build.enabled=true
```

With the default management path and port, the request is:

```http
GET /actuator/info HTTP/1.1
Host: localhost:8080
```

The JSON response contains the `build` group; the example below only illustrates a subset of fields and does not guarantee ordering or the entire response:

```json
{
  "build": {
    "artifact": "build-info-demo",
    "name": "Build Info Demo",
    "version": "1.2.0",
    "group": "com.example",
    "time": "2025-02-03T04:05:06Z",
    "channel": "training"
  }
}
```

`BuildInfoContributor` uses full mode, so additional properties can also be exposed. See [BuildInfoContributor source code](https://github.com/spring-projects/spring-boot/blob/v3.3.13/spring-boot-project/spring-boot-actuator/src/main/java/org/springframework/boot/actuate/info/BuildInfoContributor.java) and [contributor creation conditions](https://github.com/spring-projects/spring-boot/blob/v3.3.0/spring-boot-project/spring-boot-actuator-autoconfigure/src/main/java/org/springframework/boot/actuate/autoconfigure/info/InfoContributorAutoConfiguration.java).

Enabling `management.info.build.enabled` does not generate a missing file, create a bean out of thin air, or replace HTTP protection rules. If the application has Spring Security, callers still must satisfy the application's security configuration.

Metadata is data readable from the packaged artifact; blocking an endpoint does not turn a token written into the file into a safe secret. Include only fields suitable to travel with the release.

## 7. Diagnosing in Order from Artifact to Reader

When expected information does not show up, inspect layer by layer rather than changing multiple settings at once.

### 7.1. Checking the Resource Inside the Right JAR

On Windows:

```powershell
jar tf build/libs/build-info-demo-1.2.0.jar |
    Select-String -SimpleMatch 'META-INF/build-info.properties'
```

With the executable JAR in the example, look for the entry:

```text
BOOT-INF/classes/META-INF/build-info.properties
```

Inspect the JAR actually running. Seeing the file in `src/main/resources` does not prove it was packaged into the deployed artifact.

### 7.2. Checking the Bean and Keys

| Symptom | What to distinguish | How to check |
| --- | --- | --- |
| No `BuildProperties` bean | Missing resource, changed location, or missing corresponding auto-configuration | Check the runtime classpath and auto-configuration conditions |
| Bean exists yet `getVersion()` is `null` | Bean existence does not guarantee every field has a value | Check the `build.version` line in the actual resource |
| `get("build.version")` is `null` | Using the pre-normalization key name | Change to `getVersion()` or `get("version")` |
| `getTime()` is `null` | Timestamp field omitted or unparseable | Check `get("time")` and source data |
| Bean reads properly yet HTTP returns 404 | Data-reading path and HTTP-exposure path are two layers | Check web app, endpoint, exposure, and base path |
| HTTP returns 401/403 | Request hit a protection mechanism | Check authentication and authorization; do not edit the file to fix an HTTP error |
| IDE lacks metadata while JAR has it | Two run modes may use different resource outputs | Run the resource-generation task or run through Gradle |
| Version stays old after editing config | May be running an old JAR or stale resource | Perform a clean build and compare the exact artifact |

If intentionally changing the location, you can use configuration like:

```properties
spring.info.build.location=classpath:metadata/build-info.properties
```

You must then provide the resource at the new location. Changing the location property only changes where Spring reads from; it does not move the file or generate content. If you have declared a custom `BuildProperties` bean, auto-configuration backs off in favor of that bean; check the data source of the custom bean as well.

### 7.3. Avoid Confusing with Environment

Spring Boot reading `META-INF/build-info.properties` into `BuildProperties` does not mean every key in the file automatically becomes an `Environment` property.

Therefore, do not replace `build.getVersion()` with `@Value("${build.version}")` assuming the result is equivalent. To read from `Environment`, a separate property-source loading mechanism must exist; that is a different configuration choice that must be managed explicitly.

Likewise, `info.app.version` in environment configuration, `Implementation-Version` in the manifest, and `build.version` in this resource are different sources. When diagnosing, state clearly where you read from.

## 8. Decisions Needed in Real Projects

**Who creates the metadata?** Let the build process generate information from the same configuration that builds the artifact. Do not edit metadata inside a JAR after packaging to make it match a desired version.

**Is build time needed?** A changing timestamp can make outputs differ and affect build caching/reusability. If intentionally omitting this field, Spring Boot Gradle Plugin 3.3 supports the following configuration; this is an alternative to the `buildInfo` block in the example:

```groovy
springBoot {
    buildInfo {
        excludes = ['time']
    }
}
```

When the field is excluded, reading code must accept `getTime() == null`. Omitting the timestamp does not by itself make the entire build reproducible; other inputs must also be controlled.

**Does data update while the application is running?** The standard bean is created when the Spring context starts; there is no built-in mechanism to watch and reload the file whenever it changes. Test with a new artifact and a new startup instead of expecting the endpoint to reflect a file edited externally.

**How much can metadata be trusted?** Use it to identify and diagnose releases. When needing to prove two artifacts are identical or verify release provenance, add checksum/signature verification in the release pipeline; do not assign that responsibility to a version string.

## 9. Verification Exercises

Make each change individually and predict the outcome before running:

1. Change the project version to `1.2.1` using Approach B, perform a clean build, and run the exact new JAR. `getVersion()` must reflect the new version.
2. Change `build.channel=training` to `build.channel=qa` using Approach A. `get("channel")` must return `qa`.
3. With Approach A, change `build.version` specifically to `version`. The bean can still be created because the resource exists, yet `getVersion()` returns `null`.
4. Remove the `build.time` field. The bean still works, and `getTime()` returns `null`.
5. Put `build.time=not-a-time` in the sample file. `getTime()` returns `null`, while `get("time")` preserves the invalid value for diagnosis.
6. Run the case with no resource. Explain why the example using `ObjectProvider` still prints `build-info=missing`.
7. If HTTP is enabled, disable `management.info.build.enabled`. Verify that losing the `build` group provided by this contributor does not mean the bean disappeared.

After these experiments, you should be able to answer three questions: which resource is being loaded, whether keys have been normalized, and which component is consuming that information. These three points help distinguish build-metadata errors from Actuator exposure configuration errors.
