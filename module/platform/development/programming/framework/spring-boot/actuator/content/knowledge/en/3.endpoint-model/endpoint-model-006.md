# Reading Content Types and Response Structures of the Actuator API

## 1. A Response Must Be Read Across Three Layers

When calling a management endpoint, do not start by immediately looking for a property inside JSON. Answer these in order:

1. **HTTP status code:** what outcome did the request produce?
2. **Content type:** did the server actually send JSON, plain text, or binary data?
3. **Body structure and meaning:** for that exact endpoint and representation version, what do the fields mean?

For example, `200` on the status line, `application/vnd.spring-boot.actuator.v3+json` in the header, and `"status": "UP"` in the body belong to three different layers. Collapsing them into a single concept of "API succeeded" loses diagnostic information.

In the endpoint model, the **endpoint** identifies the management capability group; the **operation** identifies reading or changing data; the **representation** is the format of data sent over HTTP. The same address can support multiple representations. Knowing the address is not enough to know how to decode it.

This lesson uses the Actuator contract of **Spring Boot 3.3.x**, referencing the 3.3.13 documentation. Sample commands assume an application already running at `http://localhost:8080` with Actuator and appropriate access permissions; adjust the address for your environment. On Windows use `curl.exe` to avoid confusion with the PowerShell alias; on Linux/macOS use `curl`.

## 2. Observe the Raw Response Before Filtering Data

Call `health` and request the V3 JSON representation:

~~~powershell
curl.exe -sS -i -H "Accept: application/vnd.spring-boot.actuator.v3+json" "http://localhost:8080/actuator/health"
~~~

An illustrative response when the application is healthy and details are not exposed:

~~~http
HTTP/1.1 200 OK
Content-Type: application/vnd.spring-boot.actuator.v3+json

{"status":"UP"}
~~~

This is a simplified example, not a transcript of every environment. Actual responses may include extra headers, use HTTP/2, differ in line endings, or report a different health status.

How to read it:

- `HTTP/1.1 200 OK`: the HTTP status line.
- `Content-Type`: the type of the body being received.
- Blank line: separates headers from the body in HTTP/1.1 presentation.
- `{"status":"UP"}`: the JSON content of `health`.

The `-i` option includes headers in the output. Therefore, **do not pipe the output of a command with `-i` straight into a JSON parser**: the `HTTP/1.1 ...` line is not JSON. To process programmatically, separate headers and body into two streams or two files.

When looking at an unexpected response, keep all three layers. Copying only the body can make you miss a login page, a content-negotiation error, or a response generated by a proxy.

## 3. Properly Understanding `Content-Type` and `Accept`

### 3.1. Which Header Describes Which Data?

| Header | Where does it appear here? | Question it answers |
| --- | --- | --- |
| `Accept` | Request sent to server | Which response types does the caller accept? |
| Response `Content-Type` | Response from server | What type is the body just received? |
| Request `Content-Type` | Request with a body, such as POST | What type is the body being sent? |

Sending `Content-Type: application/json` in a bodyless GET request does not replace `Accept`. If the goal is selecting the response type, use `Accept`. Definitions of both headers are described at [Accept](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Accept) and [Content-Type](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Type).

Example of a standard JSON request:

~~~powershell
curl.exe -sS -i -H "Accept: application/json" "http://localhost:8080/actuator/health"
~~~

For endpoints supporting that type, the response may carry `Content-Type: application/json`. Read the actual received header; do not assume the server always returns the exact media type string you once saw in a screenshot.

### 3.2. Reading Actuator Media Type Names

Consider:

~~~text
application/vnd.spring-boot.actuator.v3+json
~~~

- `application`: the content type group.
- `vnd.spring-boot.actuator.v3`: Actuator's vendor-specific representation name, carrying version info.
- `+json`: representation using JSON syntax.

It is still data that a capable JSON parser can read. However, "parseable as JSON" does not mean "valid health structure" or "valid metrics structure."

**`v3` is the Actuator API version, not shorthand for Spring Boot 3.3.** The V3 API has been supported since Spring Boot 2.2. Boot 3.3's Java API lists both V2 and V3; these are two distinct versioning axes to distinguish. See [ApiVersion in Spring Boot 3.3](https://docs.spring.io/spring-boot/3.3/api/java/org/springframework/boot/actuate/endpoint/ApiVersion.html).

Do not change `v3` to `v3.3` or `v4` based on the library version number. If a legacy system requires V2, request a compatible representation only when the endpoint supports it and read the V2 contract properly. For example, the health documentation describes the V3 structure and specifies how to request V2; you should not change the header and assume all field paths remain unchanged. [Health contract](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/health.html)

### 3.3. Do Not Compare Full Header Strings Mechanically

Headers can include parameters:

~~~text
Content-Type: text/plain;charset=UTF-8
Content-Type: application/openmetrics-text;version=1.0.0;charset=utf-8
~~~

When choosing a decoder, separate the main type from parameters; when handling versioned formats like OpenMetrics, retain the version parameter to choose the right reader.

A generic JSON reader can accept `application/json` and supported `application/*+json` types. After that step, you still need to check the endpoint-specific structure. Do not rely solely on "header contains the word json" to decide a response is valid.

## 4. Actuator JSON Has No Common Wrapper

There is no rule that every endpoint returns:

~~~json
{
  "success": true,
  "data": {},
  "message": "OK"
}
~~~

That is only a wrapper an application might design itself; it is not part of Actuator's common contract.

Recognize the starting point of each structure:

| Illustrative address | Fields to identify first | Shape to read |
| --- | --- | --- |
| `/actuator` | `_links` | Map of discovery links |
| `/actuator/health` | `status`, possibly `components` | Health status, possibly a tree |
| `/actuator/metrics` | `names` | Array of metric names |
| `/actuator/metrics/{name}` | `name`, `measurements`, `availableTags` | Single metric with its measurements |
| `/actuator/info` | Keys contributed by info sources | Application info object |
| `/actuator/beans` | `contexts` | Map of contexts and beans |

The shape of `info` depends on enabled info contributors and actual data; an `{}` object does not by itself prove the endpoint is broken. With `beans`, context names and bean names are data keys, not a fixed list of names to hardcode into a program. See [info](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/info.html) and [beans](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/beans.html).

When encountering new JSON, identify in order: root object or array, required fields, optional fields, value types, and dynamic keys. Property ordering inside an object and indentation are not criteria for recognizing the contract.

## 5. Reading health: Aggregated Status and Component Tree

A minimal response may contain only:

~~~json
{
  "status": "UP"
}
~~~

When components and details are exposed, an illustrative example is:

~~~json
{
  "status": "UP",
  "components": {
    "inventory": {
      "status": "UP",
      "details": {
        "checkedItems": 12
      }
    }
  }
}
~~~

In this fabricated example:

- Root `status` is the aggregated status.
- `components` is an object holding components by name.
- `inventory` is an illustrative component name, not a default Boot component.
- `details.checkedItems` is a detail provided by that component; you cannot apply this path to every health indicator.

A component can also contain nested `components`. Therefore, do not force `health` into a flat table with fixed column names. The official documentation clearly distinguishes the paths `components.*.status`, `components.*.components`, and `components.*.details`. [Health V3 structure](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/health.html)

If `components` or `details` are missing, check the exposure policy and access permissions first. The properties `management.endpoint.health.show-components` and `management.endpoint.health.show-details` affect how much information is visible. Do not infer "there is no database" simply because the response lacks a `db` key.

Distinguish **HTTP status** from the **health `status` field**. Under default mapping, `DOWN` and `OUT_OF_SERVICE` result in HTTP `503`; mappings can be customized. Therefore, a `503` response can still be valid health JSON that should be read for diagnosis. See [Health Information and HTTP mapping](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.health).

A good conclusion preserves all evidence: "HTTP 503; health body reports DOWN" is clearer than "JSON error." With custom statuses, also do not assume every string other than `UP` has the same meaning.

## 6. Reading metrics: Catalog Differs from a Single Metric's Value

### 6.1. Catalog

~~~powershell
curl.exe -sS -i -H "Accept: application/vnd.spring-boot.actuator.v3+json" "http://localhost:8080/actuator/metrics"
~~~

Simplified example:

~~~json
{
  "names": [
    "jvm.memory.used",
    "process.uptime"
  ]
}
~~~

This array shows which names are available to query; it does not yet contain measurements for each metric. The actual list depends on the application and registered meters. [Metrics catalog](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/metrics.html)

### 6.2. A Single Metric

~~~powershell
curl.exe -sS -i -H "Accept: application/vnd.spring-boot.actuator.v3+json" "http://localhost:8080/actuator/metrics/jvm.memory.used"
~~~

Abbreviated illustrative example with chosen numbers:

~~~json
{
  "name": "jvm.memory.used",
  "baseUnit": "bytes",
  "measurements": [
    {
      "statistic": "VALUE",
      "value": 41943040
    }
  ],
  "availableTags": [
    {
      "tag": "area",
      "values": ["heap", "nonheap"]
    }
  ]
}
~~~

Read `value` together with `statistic` and `baseUnit`. In this example, 41,943,040 bytes equals 40 MiB. `availableTags` indicates dimensions available for filtering; it is not a list of independent measurements. Element count and statistic types vary by meter type, so do not always grab the first element and label it "total."

Filter one dimension with the `tag` parameter:

~~~powershell
curl.exe -sS -i -H "Accept: application/vnd.spring-boot.actuator.v3+json" "http://localhost:8080/actuator/metrics/jvm.memory.used?tag=area%3Aheap"
~~~

`%3A` is the URL-encoded colon in `area:heap`. Only use tags and values meaningful for the metric being read. Do not expect runtime numbers to match the example; the JVM keeps running while being observed.

The `metrics` endpoint is for viewing and diagnosing metrics; it is not Prometheus's scrape format. [Metrics contract and filters](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/metrics.html)

## 7. Reading `_links`: Navigation Info, Not Management Data

In a typical configuration, the discovery page is at `/actuator`. Partial content example, keeping only the `health` link:

~~~json
{
  "_links": {
    "health": {
      "href": "http://localhost:8080/actuator/health",
      "templated": false
    }
  }
}
~~~

Here, `health` is the link relation name; `href` is the address; `templated` indicates whether the link is a URI template. To know health, you must call the `health` address and read its response. The presence of a link is not the value `UP`.

When encountering `templated: true`, understand and fill the template variables before using it; do not blindly copy literal template braces into a request URL.

The discovery page may be disabled, and the base address can change. Therefore, missing `_links` at a guessed URL does not prove Actuator is not installed. Likewise, do not require payloads like `health` or `metrics` to contain `_links`. See [Hypermedia for Actuator](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.hypermedia).

## 8. Responses That Must Not Be Read with a JSON Parser

### 8.1. Plain-Text Thread Dump

When the endpoint is exposed and you have permission, you can request:

~~~powershell
curl.exe -sS -i -H "Accept: text/plain" "http://localhost:8080/actuator/threaddump"
~~~

The output is plain text about threads when this representation is chosen; `Content-Type` may be `text/plain;charset=UTF-8`. The same endpoint also has a JSON representation. You must choose how to read it based on the actual response, not the path name. [Thread dump](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/threaddump.html)

### 8.2. Prometheus and OpenMetrics

`/actuator/prometheus` requires the appropriate Prometheus registry library and must be exposed. The default format described in the 3.3 docs is `text/plain;version=0.0.4`; it also supports OpenMetrics via the appropriate `Accept` header.

Example OpenMetrics request:

~~~powershell
curl.exe -sS -i -H "Accept: application/openmetrics-text;version=1.0.0;charset=utf-8" "http://localhost:8080/actuator/prometheus"
~~~

Declaration and metric lines in this format are not JSON, even though the media type starts with `application/`. Do not feed them into a JSON parser. [Prometheus API](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/prometheus.html)

### 8.3. Binary Heap Dump

`heapdump` returns binary data; the format depends on the JVM, such as HPROF on HotSpot. You need to save and open it with an appropriate tool. Do not convert that data into a JSON string, and do not print it as text to guess its contents. This lesson does not require generating a heap dump to practice reading headers. [Heap dump](https://docs.spring.io/spring-boot/3.3/api/rest/actuator/heapdump.html)

The key takeaway is: **an Actuator address does not imply a JSON response**. Choose the reader based on the content type and the operation's contract.

## 9. Reading HTTP Status Codes Without Misassigning Body Structure

| Code or group | What to check before reading payload |
| --- | --- |
| `200` | Read content type and endpoint-specific structure; do not assume every application component is healthy |
| `204` | No body to parse; may be a valid result of a write/delete operation |
| `3xx` | Check `Location`; you may be getting redirected elsewhere |
| `401` / `403` | Check authentication or permissions; do not treat the body as a success payload |
| `404` | Check URL, base path, endpoint exposure, and sub-resource; cannot conclude from a single cause |
| `406` | Check whether the response type in `Accept` can be satisfied |
| `415` | For requests with a body, check the sent content type |
| `503` from health | Read the health status and check the HTTP mapping in use |

For endpoint operations, a write/delete operation returning no value can use `204 No Content`; a read operation returning no value can use `404`. These are default rules and do not override custom behaviors such as `health`'s mapping. [Endpoint response status](https://docs.spring.io/spring-boot/3.3/reference/actuator/endpoints.html#actuator.endpoints.implementing-custom.web.response-status)

`406` relates to response representation failing content negotiation; `415` relates to an unsupported request content format. The two errors cannot be fixed with the same arbitrary header change. [406](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/406), [415](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/415)

Error bodies can be produced by the application's error handler, the security layer, or a proxy. Do not apply `health`'s success structure to all `4xx`/`5xx` responses, and do not assume all errors have `timestamp`, `error`, and `path` fields.

If you receive HTML when expecting JSON, record the HTTP code, `Content-Type`, `Location` if present, and the actual URL called. Do not rush to conclude that Actuator's JSON syntax is invalid. When diagnosing redirects, avoid using `-L` from the start as it can hide intermediate responses you need to inspect.

## 10. Hands-On Workflow: Preserve Evidence Before Extracting Fields

### Step 1: Separate Headers from Body

The following PowerShell commands use GET to read `health` and save files in the learner's working directory:

~~~powershell
curl.exe -sS -D health.headers.txt -o health.json -w "HTTP %{http_code}" -H "Accept: application/vnd.spring-boot.actuator.v3+json" "http://localhost:8080/actuator/health"
Get-Content -LiteralPath "./health.headers.txt"
Get-Content -LiteralPath "./health.json" -Raw
~~~

`-D` saves headers; `-o` saves the body; `-w` prints the final HTTP code of the call. Naming a file `health.json` does not guarantee its content is JSON: you must still check the status and headers first.

If you cannot connect, resolve the connection error before reading the files. Do not use leftover contents from a previous run as evidence for the current call.

### Step 2: Parse Only When the Body and Content Type Match

After confirming you received `health` JSON:

~~~powershell
$health = Get-Content -LiteralPath "./health.json" -Raw | ConvertFrom-Json
$health.status
~~~

With the exact body `{"status":"UP"}` in section 2, the output of the last line is:

~~~text
UP
~~~

This result matches the example data. Real applications may report different values. Reading a valid `health` body is still useful when the HTTP code is `503`; record both values.

### Step 3: Do Not Access Optional Fields as If They Always Exist

If you need to inspect components, check for presence first:

~~~powershell
if ($null -ne $health.components) {
    $health.components.PSObject.Properties |
        ForEach-Object { "{0}: {1}" -f $_.Name, $_.Value.status }
} else {
    "Response does not expose components"
}
~~~

With the illustrative JSON containing `inventory` in section 5, the output is:

~~~text
inventory: UP
~~~

With minimal `health`, the else branch only tells you the response does not expose components; it does not prove all components are absent. This snippet only lists the direct level and does not traverse nested `components` trees.

### Step 4: Record Results with an Evidence-Based Description

A useful observation record might be:

> GET /actuator/health; HTTP 200; Actuator V3 JSON media type; status UP; no components in the received body.

Another record might be:

> GET /actuator/metrics; HTTP 200; has `names` array; individual metric values not yet queried.

These statements separate what was observed from what was not checked. They help others reproduce the observation without guessing which endpoint you called.

## 11. Common Mistakes and Self-Checks

- **Accepting only the exact string `application/json`:** easily rejects Actuator JSON with the `+json` suffix. Check supported media types, then validate the structure.
- **Using one data wrapper class with a `data` field for every endpoint:** fails immediately when the actual root has `status` or `names`.
- **Treating missing fields, `null`, `{}`, and `[]` as identical:** these are different data states. Determine their meaning per specific field and endpoint.
- **Hardcoding component, context, bean, or tag names from examples as constants:** breaks easily when the environment or configuration changes.
- **Parsing headers as JSON:** commonly happens when piping `curl -i` into a JSON reader. Separate the two parts first.
- **Assuming every metrics value is bytes or a percentage:** read the unit and statistic type; do not assign units by guesswork.
- **Expecting JSON from every endpoint:** check plain-text, OpenMetrics, and binary representations.
- **Discarding the body just because health returned 503:** can throw away useful diagnostic evidence.
- **Treating example responses as fixed outputs:** operational data changes; assert exact output only when inputs are fixed.

## 12. Response Reading Exercises

**Scenario 1.** A `health` call returns HTTP 503, `Content-Type` is Actuator V3 JSON, and the body is:

~~~json
{
  "status": "DOWN"
}
~~~

Is the JSON parser broken?

**Suggested answer:** There is no evidence of a JSON error in this data. This is a valid `health` body; record status `DOWN` and code `503`, then investigate the cause using the information permitted to be seen.

**Scenario 2.** `/actuator/metrics` returns `{"names":["process.uptime"]}`. Can you report uptime by counting the elements in `names`?

**Suggested answer:** No. That is a metric name. You must query `/actuator/metrics/process.uptime`, then read the actual measurements and unit returned.

**Scenario 3.** A tool reports "data.status not found", while the body is `{"status":"UP"}`.

**Suggested answer:** The tool is applying the wrong wrapper structure. In this body, `status` sits directly at the root.

**Scenario 4.** Two thread dump responses have types JSON and `text/plain`, respectively. Can they share the same JSON parser?

**Suggested answer:** No. Choose the reader based on the actual received media type; if you need a specific representation, send the corresponding `Accept` header supported by the endpoint.

After the exercises, practice reading a response in order: **URL and operation → HTTP status → content type → specific structure → meaning of the data**. Conclude only within the scope of the evidence just observed.
