# Random Values from random.* and Usage Limits

> **Topic:** Spring Boot Externalized Configuration  
> **Group:** Placeholders and Defaults

## 1. When Are Random Values Needed in Configuration?

In Spring Boot, a value in `application.properties` or `application.yml` does not always have to be hardcoded. Placeholders allow referencing other properties, providing defaults, or requesting a random value through the special **`random.*`** key group.

For instance, when test-running an application, you might want a temporary ID to distinguish startups, an integer for a demo, or a port within an experimental range. Spring Boot provides `RandomValuePropertySource` to generate such values without requiring custom random-generation Java code in every example.

However, "random" does not mean "unique," "secret," "stable," or "safe in every environment." Understanding the boundaries of `random.*` is essential when moving from learning examples to real applications.

After this lesson, you will:

- Recognize `random.value`, `random.int`, `random.long`, and `random.uuid` expressions.
- Use `${random.*}` placeholders in Spring Boot configuration and bind them to appropriate Java types.
- Choose bounded numeric values and understand interval boundary semantics.
- Distinguish values generated by a random placeholder from fixed property values supplied by the environment.
- Understand why you cannot rely on `random.*` for durable identifiers, production secrets, or guaranteed-free ports.
- Control test reproducibility and identify configuration sources across precedence levels.

## 2. What Is `RandomValuePropertySource`?

Spring Boot adds a property source capable of generating random values, commonly called `RandomValuePropertySource`. Keys starting with `random.` are interpreted by this source according to its supported syntax. When a placeholder references a key like `random.int`, property resolution can pull a value from that source.

Example in `src/main/resources/application.properties`:

~~~properties
demo.instance-id=${random.uuid}
demo.seed=${random.long}
demo.sample-number=${random.int}
~~~

In `application.yml`:

~~~yaml
demo:
  instance-id: "${random.uuid}"
  seed: "${random.long}"
  sample-number: "${random.int}"
~~~

Both examples use application properties under the `demo` prefix. The keys `random.uuid`, `random.long`, and `random.int` are **value-generating sources** referenced by those properties.

Distinguish two roles:

- **`random.uuid`**: special key provided by the random source.
- **`demo.instance-id`**: application-defined business configuration key, readable via `Environment` or bound into `@ConfigurationProperties`.

Do not assume a key named `random.my-custom-secret` means "generate a secret" just because you invented the name. Use expression forms supported by Spring Boot and verify their data types.

## 3. Common Random Expressions

| Expression | Value type | Typical use |
| --- | --- | --- |
| `${random.value}` | Random string value | Sample data or temporary name |
| `${random.int}` | Integer of type `int` | Integer examples |
| `${random.long}` | Integer of type `long` | Large integer examples |
| `${random.uuid}` | Random UUID | Temporary identifier for examples or startups |
| `${random.int(10)}` | Integer from 0 up to below 10 | Upper-bounded example |
| `${random.int[1024,65536]}` | Integer within a two-bound range | Selecting a number in a range |

The forms above show syntax commonly used in Spring Boot documentation. `random.value` is a random string-typed value; do not design code around a specific length or character set unless the documentation for your version guarantees that format. `random.uuid` produces a UUID representation when converted to a string.

Parentheses and brackets in the numeric examples belong to **the random expression parser**, not placeholder fallback syntax. It is `:` that separates the default value of a placeholder, such as `${demo.timeout:5s}`.

### 3.1. A Complete Illustrative Configuration File

~~~properties
demo.random-text=${random.value}
demo.random-int=${random.int}
demo.random-long=${random.long}
demo.random-uuid=${random.uuid}
demo.digit=${random.int(10)}
demo.port-candidate=${random.int[10000,20000]}
~~~

When values are queried and resolved from these placeholders, Spring can receive output resembling:

~~~text
demo.random-text   = <random string>
demo.random-int    = <integer>
demo.random-long   = <long integer>
demo.random-uuid   = <UUID>
demo.digit         = <number from 0 to 9>
demo.port-candidate= <number from 10000 to 19999>
~~~

Actual values vary; lines in the output block merely describe types and ranges. Do not put a fixed UUID into an example and assume learners will get that same UUID.

### 3.2. Why Place the Placeholder Inside an Application Property?

When writing:

~~~properties
client.retry-jitter=${random.int[0,1000]}
~~~

the application can read `client.retry-jitter` as its own configuration key. In an environment requiring reproducible behavior, you can supply `CLIENT_RETRY_JITTER=250` or `--client.retry-jitter=250` to replace it. This design keeps configuration control at deployment time.

If every component called `Environment.getProperty("random.int")` directly inside business logic, controlling when the value is generated and sharing one consistent value would be much less clear. For any configuration parameter, define a meaningful property name first and then decide on its fallback.

## 4. Integer Bounds: Single-Bound and Two-Bound Forms

### 4.1. Single-Bound Form

~~~properties
demo.index=${random.int(10)}
~~~

In standard usage, this expression generates an integer **from 0 (inclusive) to 10 (exclusive)**. Possible values are 0, 1, ..., 9.

A few examples:

~~~properties
demo.coin=${random.int(2)}
demo.test-shard=${random.int(8)}
~~~

`random.int(2)` can produce 0 or 1. `random.int(8)` can produce 0 through 7. Do not pass a bound of 0 or a negative bound expecting a meaningful random range; bounds must satisfy the generator's constraints.

### 4.2. Two-Bound Form

~~~properties
demo.batch-size=${random.int[10,20]}
~~~

Typical meaning is an integer in the interval **[10, 20)**: lower bound 10 is inclusive, upper bound 20 is exclusive. Possible results are 10, 11, ..., 19.

Other examples:

~~~properties
demo.ephemeral-port-candidate=${random.int[10000,20000]}
demo.initial-counter=${random.int[1,100]}
~~~

With `[10000,20000]`, the generated value is between 10000 and 19999 under the exclusive upper bound rule. The square brackets here are part of Spring Boot's random expression syntax, **not** a YAML list.

If you want a value in 1–100 including 100, the upper bound in this expression must exceed 100, such as `random.int[1,101]`.

### 4.3. The `long` Type and Bounds

`random.long` fits when an integer of type `long` is needed. When using bounded variants, ensure bounds fit within the type's range and the upper bound exceeds the lower bound. Avoid relying on syntax undocumented for your Spring Boot version.

Basic unbounded example:

~~~properties
demo.session-number=${random.long}
~~~

Bind to `long` or `Long` when needed instead of manually parsing with code that assumes a specific format.

### 4.4. Random Only Generates Candidates, Not Guaranteed-Usable Resources

A random integer in a TCP port range **does not guarantee the port is free**. For example:

~~~properties
server.port=${random.int[10000,20000]}
~~~

could pick a value already occupied by another process. When running a Spring Boot embedded server and wanting the OS to select an available port, you normally use:

~~~properties
server.port=0
~~~

and then retrieve the actual port after the server binds (for example, in integration tests). Likewise, `random.int` does not guarantee a valid resource index, does not promise a number has never been used, and is not a distributed ID allocator.

## 5. Random UUIDs: Useful, Yet Not Durable

### 5.1. Using `random.uuid`

Example:

~~~yaml
demo:
  run-id: "${random.uuid}"
~~~

When this property is resolved, the value has UUID form. It is helpful for distinguishing runs **in examples**, or temporarily labeling an experimental process.

Code can bind to `String`:

~~~java
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "demo")
public record DemoProperties(String runId) {}
~~~

Or you can use `UUID` if the Spring application's conversion path supports it:

~~~java
import java.util.UUID;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "demo")
public record DemoIdProperties(UUID runId) {}
~~~

In either case, it remains **a value generated during configuration resolution**, not an ID persisted and lifecycle-managed by a system.

### 5.2. Do Not Mistake a Random UUID for a Stable ID

Suppose an application uses:

~~~properties
app.node-id=${random.uuid}
~~~

If every startup generates a new ID, a server can change its `node-id` after a restart. This is unsuitable if the system uses the ID to link long-lived data, register in a cluster needing durable identity, or identify an instance across deployments.

Better options depending on the case:

- **ID that must survive restarts:** generated once and stored in a database, durable config file, or identity system.
- **Pod/instance ID in orchestration:** use metadata or an identity mechanism provided by the deployment platform.
- **Per-request ID:** generated while handling the request and attached to a request context; do not use an application-wide random property.
- **Demo run ID:** an initialized value like `random.uuid` may suffice when stable identity is not required.

### 5.3. Random Does Not Mean Guaranteed Collision-Free

Random UUIDs typically have very low collision probability under proper models, yet that does not provide an absolute business-level uniqueness guarantee. For data requiring uniqueness in storage, still enforce a database unique constraint or an appropriate ID allocation/verification mechanism.

Do not rely on low probability as a substitute for a constraint required by data integrity.

## 6. Value Generation Timing: A Key Aspect of `random.*`

`RandomValuePropertySource` is a source that **generates values on demand**, not a persistent immutable table of constants. Therefore, do not assume every read of `random.uuid` returns the exact same UUID, or that two separate placeholders referencing `random.int` share the same number.

Example:

~~~properties
demo.first=${random.uuid}
demo.second=${random.uuid}
~~~

Do not treat `demo.first` and `demo.second` as the same identifier. Even if both resolve during the same startup, there is no reason to design them to be equal. Nor should you assert "every read is guaranteed to differ"; two random numbers can coincide by chance.

### 6.1. Values Bound into a Bean Can Stay Stable for the Bean's Lifecycle

If `@ConfigurationProperties` is bound once at startup, fields in the bean hold the bound values until the bean is changed or recreated by application mechanisms. Example:

~~~java
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "demo")
public record DemoProperties(String runId, int sampleNumber) {}
~~~

Configuration:

~~~properties
demo.run-id=${random.uuid}
demo.sample-number=${random.int(1000)}
~~~

A normal `DemoProperties` bean receives the values at binding time. Subsequent calls to `properties.runId()` read that bean's field, **rather than invoking the random generator on every call**.

Yet two distinct things must be separated:

1. **A field value already stored in a Java object** can remain unchanged.
2. **A fresh placeholder resolution or random property lookup** can generate a new value.

If the application has a special refresh/rebind mechanism, bean lifecycles also depend on that mechanism. Do not treat "random only runs once" as a universal contract for every configuration-reading path.

### 6.2. Want to Share Exactly One Value? Keep It in One Place

A simple approach is binding once into a bean and passing that bean to components that need it. Example:

~~~java
import org.springframework.stereotype.Service;

@Service
public class DemoRunService {
    private final DemoProperties properties;

    public DemoRunService(DemoProperties properties) {
        this.properties = properties;
    }

    public String runIdForLogging() {
        return properties.runId();
    }
}
~~~

Components using the same bean share one bound value for that bean's lifecycle. If it must be **consistent across multiple processes**, sharing one bean in one JVM is not enough: supply the value via deployment configuration, storage, or a shared service.

### 6.3. Do Not Treat Random Properties as a Per-Call Business RNG

If business logic needs a fresh random value per operation—such as generating a temporary token, taking a sample, or choosing per-retry jitter—use an appropriate random API **inside business logic at the time of generation**. `random.*` is an externalized configuration utility, not a general replacement for Java's random libraries or an ID allocation service.

## 7. Placeholders, Defaults, and Proper Syntax

### 7.1. Property with a Random Fallback

A realistic example in a demo environment:

~~~properties
demo.run-id=${APP_RUN_ID:${random.uuid}}
~~~

Idea: if `APP_RUN_ID` exists in the placeholder resolution environment, use it; otherwise fall back to generating a UUID. However, when designing Spring Boot configuration, prefer canonical property names (e.g., `app.run-id`) and supply environment variable `APP_RUN_ID` via relaxed binding:

~~~properties
app.run-id=${app.assigned-run-id:${random.uuid}}
~~~

Here `app.assigned-run-id` is supplied by the environment if available; if absent, a random value is used. Results are still governed by system-wide precedence. If `app.run-id` itself is supplied by a higher source, the expression in the lower-precedence file may not be used.

In all cases, a random fallback should only be chosen if business rules truly permit the ID to change when unconfigured. An ID that must remain stable should not silently fall back to random.

### 7.2. Using in YAML

Because some placeholders contain special characters like `[`, `]`, `{`, or `}`, a safe and readable convention is quoting scalars in YAML:

~~~yaml
demo:
  run-id: "${random.uuid}"
  sample-index: "${random.int(10)}"
  service-port-candidate: "${random.int[10000,20000]}"
~~~

YAML may read those values as strings before Spring resolves placeholders. When binding to `int` or `long`, Spring Boot converts based on the target type. Do not assume that double quotes in YAML force the bean field to be `String`.

### 7.3. Distinguishing Two Uses of Colons

In:

~~~properties
demo.mode=${demo.explicit-mode:local}
~~~

the `:` separates **property name** and **default value** of the placeholder: if `demo.explicit-mode` is absent, use `local`.

In:

~~~properties
demo.mode=${demo.explicit-mode:${random.uuid}}
~~~

the part after `:` is **another placeholder** providing the fallback value.

Meanwhile:

~~~properties
demo.number=${random.int[10,20]}
~~~

asks the random source to generate a number in a range. These forms serve different purposes.

### 7.4. A Property Can Be Overridden by a Higher Source

`application.yml`:

~~~yaml
demo:
  run-id: "${random.uuid}"
~~~

Start with:

~~~bash
java -jar app.jar --demo.run-id=run-fixed-2026
~~~

Under default precedence, the command-line property `demo.run-id` can beat the value from YAML. This is desirable when a deployment needs to pin a specific value.

There is no need to disable `RandomValuePropertySource` to force a fixed value; supply the business property in a higher-precedence source.

## 8. Precedence Compared to Other Sources

Spring Boot orders many property sources. With default configuration and excluding test-specific or custom sources, the **high → low** order relevant to this lesson can be pictured as:

| Relative precedence | Source |
| --- | --- |
| High | Application command-line arguments |
| High | `SPRING_APPLICATION_JSON` and JSON application properties |
| High | Servlet/JNDI environment sources when present |
| Higher than random | Java system properties |
| Higher than random | Operating system environment variables |
| **Random** | `RandomValuePropertySource` |
| Lower than random | Config data: `application.properties`, `application.yml`, imports/profiles |
| Low | `@PropertySource` and default properties |

The core point is: `random.*` is not an "absolute priority" source; it is one property source in the lookup chain. A business property like `demo.run-id` provided via CLI/OS env can override an expression placed in a file.

Also do not confuse **random's position in precedence** with "every file property will always be overridden by random." `RandomValuePropertySource` only supplies keys it supports—typically the `random.*` namespace. It does not invent values for arbitrary `demo.*` keys unless a file declares a placeholder or the app requests them.

### 8.1. Three-Source Example

`application.properties`:

~~~properties
demo.run-id=${random.uuid}
demo.retries=3
~~~

Environment variable:

~~~bash
export DEMO_RETRIES=5
~~~

Run:

~~~bash
java -jar app.jar --demo.retries=8
~~~

With all three sources active under default configuration, `demo.retries` gets `8` from CLI. `demo.run-id` can receive a UUID requested by the placeholder in the file, unless a higher-precedence source sets `demo.run-id`.

If the deployment supplies `DEMO_RUN_ID=deployment-7`, that is an explicitly supplied business property, allowing the fixed value to beat the `random.uuid` fallback in the file.

### 8.2. Test Sources Have Their Own Precedence

In Spring Boot tests, `@TestPropertySource`, `@DynamicPropertySource`, or test slice settings can contribute high-precedence sources. Therefore, when tests require reproducible results, explicitly set `demo.run-id=test-run` or a similar value and verify that property is actually used in the test context.

Do not predict test outcomes solely from the standard runtime table when the test adds multiple property sources.

## 9. Reading and Binding Values in Java

### 9.1. Reading via `Environment`

Example:

~~~java
package com.example.demo;

import org.springframework.core.env.Environment;
import org.springframework.stereotype.Component;

@Component
public class DemoOptions {
    private final Environment environment;

    public DemoOptions(Environment environment) {
        this.environment = environment;
    }

    public String runId() {
        return environment.getProperty("demo.run-id");
    }

    public Integer index() {
        return environment.getProperty(
                "demo.sample-index", Integer.class);
    }
}
~~~

`Environment` looks up properties by `demo.*` names. In the sample application, they are declared via `random.*` placeholders in `application.yml`. If the result needs to stay constant for the lifetime of an object, bind the configuration into a bean appropriately and read that bean's field.

### 9.2. Binding with `@ConfigurationProperties`

`application.yml`:

~~~yaml
demo:
  run-id: "${random.uuid}"
  sample-index: "${random.int[0,100]}"
  enabled: true
~~~

Record for Spring Boot 3, Java 17+:

~~~java
package com.example.demo;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        String runId,
        int sampleIndex,
        boolean enabled
) {}
~~~

Enable scanning from the application:

~~~java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;

@SpringBootApplication
@ConfigurationPropertiesScan
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
~~~

Usage:

~~~java
import org.springframework.stereotype.Service;

@Service
public class DemoService {
    private final DemoProperties properties;

    public DemoService(DemoProperties properties) {
        this.properties = properties;
    }

    public String describe() {
        return properties.runId()
                + " / index=" + properties.sampleIndex();
    }
}
~~~

With no higher override, `runId` receives a String UUID, `sampleIndex` receives a number in 0–99, and `enabled` receives `true`. Normal Java beans retain their fields after creation, making this a clean way to use **one configuration value at a given time**.

### 9.3. Choosing Appropriate Data Types

- `random.int`: bind to `int` or `Integer`.
- `random.long`: bind to `long` or `Long`.
- `random.uuid`: usually retrievable as `String` or bound to `UUID` when conversion supports it.
- `random.value`: use as a string-typed value; do not assume a fixed format unless guaranteed by an API contract.
- With numeric ranges, the field's Java type must still fit the bounds and actual range.

When business constraints apply, enforce dedicated validation. For example, a `sampleIndex` value must be non-negative and less than the number of available items; the configured random range might be valid at startup yet invalid if the actual item count changes.

## 10. Why `random.*` Should Not Be Treated as a Secret Management System

The word "random" easily creates a false sense of security, yet security requirements go far beyond generating an unpredictable-looking string.

### 10.1. Generating a Random Value Does Not Create a Security Process

Example:

~~~properties
security.api-token=${random.value}
~~~

Several risks arise even if the value looks hard to guess:

- There is no guarantee from this usage that format, length, entropy, or algorithm satisfies any specific security standard.
- The value can change when the application restarts, breaking clients using the old token.
- If multiple instances generate their own secrets, they may be unable to validate tokens or sessions issued by another instance.
- There is no workflow to distribute to clients, issue, revoke, rotate, or recover secrets.
- Printing configuration to logs or exposing diagnostic endpoints can leak the value.

Therefore, **never use `random.value` as a default for production passwords, signing keys, encryption keys, API tokens, or cross-instance secrets** just because it contains the word "random."

### 10.2. Obtain Secrets from an Appropriately Managed Source

In production, use an operationally managed secret source:

- A secret manager with access policies and rotation mechanisms.
- A secret volume mounted with restricted read permissions, loadable into Spring Boot via `configtree:` where appropriate.
- Configuration supplied through a deployment pipeline that protects sensitive data.

An application can use `@ConfigurationProperties` to bind secrets like other properties, but the secret source must meet requirements for lifecycle, restricted access, and cross-instance synchronization.

If you genuinely need to **generate new cryptographic secrets**, use an API or system with verified security properties—such as `SecureRandom` used properly in Java code—and persist/distribute the secret as required. `random.*` is a configuration utility, not a full secret-management lifecycle.

### 10.3. UUIDs Are Not Passwords

UUIDs can make fine identifiers, but you should not automatically treat `random.uuid` as a password or signing key. A value being hard to guess does not determine whether it has the right entropy or security properties for your algorithm and threat model.

Moreover, using a UUID as a secret token requires rules around usage, expiration, revocation, storage, and access control; none of those belong to `RandomValuePropertySource`.

## 11. Limitations in Multi-Instance and Production Environments

### 11.1. Each Instance Can Receive a Different Value

With three application pods sharing:

~~~properties
app.instance-id=${random.uuid}
~~~

each pod can generate its own identifier during configuration initialization. This can help if you just want a temporary label in demo logs. But if the application needs a recoverable cluster node identity, the identifier must come from stable infrastructure allocation or storage.

Never expect pods to receive the same "default random secret" for shared authentication. If each pod generates a different one, users will hit errors when requests are load-balanced to another instance.

### 11.2. Restarts Can Change Behavior

A value `demo.random-delay=${random.int[100,500]}` bound at startup can differ on the next deployment. If this is an important tuning parameter, random changes make performance observation, regression detection, and cross-environment comparison harder.

Only use random defaults for configuration where variation is an **intended** part of behavior. For timeouts, quotas, retry counts, or core operational parameters, usually set deliberate, auditable values.

### 11.3. Random Numbers Do Not Prevent Collisions on Their Own

Using a `random.int` as an order ID can cause collisions. Using it to pick a server port can also cause collisions. For problems needing true uniqueness, use database unique constraints, identifier allocators, lock/lease mechanisms, or OS-level selection depending on the resource.

For example, in server port tests, `server.port=0` lets the OS assign a free port at bind time, which is better than guessing with an independent random number. In distributed systems, coordinate at a shared data source rather than hoping two numbers will not collide.

### 11.4. Do Not Use as a Substitute for Controlled Feature Rollouts

A feature toggled via:

~~~properties
feature.new-ui=${random.int(2)}
~~~

causes state to flip arbitrarily across runs. It does not ensure user percentages, test cohorts, cross-request consistency, or rollback control. If you need a 10% rollout, use a proper feature flag system or deterministic bucketing by user ID rather than startup randomness.

## 12. Tests and Reproducibility

### 12.1. Tests Need Deterministic Configuration

Suppose logic depends on `demo.bucket`. With:

~~~properties
demo.bucket=${random.int[0,100]}
~~~

tests can receive different values across context startups. If assertions assume `bucket=12`, tests become flaky.

Better control:

~~~java
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest(properties = {
        "demo.bucket=12",
        "demo.run-id=test-run-001"
})
class DemoApplicationTests {
    // Tests verify behavior based on deterministic configuration.
}
~~~

Or use `application-test.yml` with fixed values and activate the `test` profile. Check precedence if tests also use command-line args, `@DynamicPropertySource`, or other custom configuration.

### 12.2. When Testing Bounded Ranges

If the goal is to verify that the application accepts a value within range, tests should check **range invariants** or value-handling logic rather than predicting a specific random number.

For example, receiving `demo.sample-index` in `@ConfigurationProperties`:

~~~java
int sample = properties.sampleIndex();
if (sample < 0 || sample >= 100) {
    throw new IllegalStateException("sample index out of range");
}
~~~

This illustrates checking invariants. When genuinely repeatable tests are needed, inject fixed values. Sampling many random values and asserting every possible number appeared is not a sustainable test pattern.

### 12.3. Testing Random Logic Should Decouple the Generator

If business rules require picking fresh jitter on every retry, separate a component or interface supplying random numbers from the retry logic. In tests, provide a fake/deterministic generator; in production, provide an appropriate generator. This tests the algorithm without depending on unpredictable `random.*` state.

`random.*` properties are primarily for **initializing random configuration values** in examples or deliberate scenarios.

## 13. Diagnosing Unexpected Results

### 13.1. Reading a Bound Value

A safe way to observe non-sensitive demo keys:

~~~java
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.stereotype.Component;

@Component
public class RandomConfigProbe implements ApplicationRunner {

    private final DemoProperties properties;

    public RandomConfigProbe(DemoProperties properties) {
        this.properties = properties;
    }

    @Override
    public void run(ApplicationArguments args) {
        System.out.println("demo.sample-index = "
                + properties.sampleIndex());
    }
}
~~~

This code reads **the bound field** instead of calling the random source repeatedly. It demonstrates one value captured at startup without requiring learners to predict exact numbers ahead of time.

Only log non-sensitive test values. Never log secrets or the entire `Environment` in real environments.

### 13.2. Distinguishing Value-Generating Sources from Override Sources

Suppose:

~~~properties
demo.run-id=${random.uuid}
~~~

yet the application always receives `fixed-run`. Check higher-precedence sources: is there `DEMO_RUN_ID=fixed-run`, `--demo.run-id=fixed-run`, `-Ddemo.run-id=fixed-run`, or a test property?

If using a `@ConfigurationProperties` bean, also confirm the bean was scanned/registered and bound from the right context. If the application calls `Environment.getProperty("random.uuid")` directly, that behaves differently from reading `demo.run-id` defined via a file placeholder.

### 13.3. Common Errors Table

| Symptom | Cause to check |
| --- | --- |
| `${random.int(10)}` is not in 1–10 | Range starts at 0 and upper bound 10 is exclusive |
| Value changes on every startup | Random property is regenerated; no persistence exists |
| Two components see different values despite referencing random | Placeholders may resolve at different times; bind/share one value if consistency is needed |
| Error binding number or `UUID` type | Check expression, override data, and target Java type |
| Picked random port yet server fails to start | Port may be occupied; use `server.port=0` to let the OS pick a port |
| Flaky tests | Using random placeholders in config while assertions expect fixed results |
| Secret changes after restart | Used random as an unpersisted secret source |
| Result is not random as expected | A higher-precedence source may have supplied a fixed value |
| Logs show multiple different UUIDs | Likely resolving `random.uuid` repeatedly instead of reading one bound field |
| Expression is not resolved | Code reads raw file as text without going through Spring placeholder resolution |

### 13.4. Checklist of Things to Inspect in Order

1. **Placeholder name:** is it valid `${random.int}`, `${random.uuid}`, or supported bounded syntax?
2. **Where the placeholder sits:** in Config Data actually loaded by Spring Boot, or merely in a text file opened with `Files.readString`?
3. **Business property name:** is the app querying `demo.run-id` or directly looking up `random.uuid`?
4. **Higher-precedence sources:** are there env vars, system properties, JSON, or CLI overrides?
5. **Read timing:** binding a bean once at startup or resolving random properties multiple times?
6. **Data type:** does the number fit `int`/`long` and business bounds?
7. **Business requirement:** do you need a temporary random value or a durable ID/secret/port?
8. **Test environment:** are fixed values provided for reproducible tests?

Predict valid ranges: `digit` is in 0–9; `two-digit` is in 10–99. In code, use `Integer` or `int` to bind. Try an invalid upper bound to observe the error when the expression resolves, then restore a valid range.

### Exercise C: Overriding Random with a Supplied Value

`application.properties`:

~~~

Run without overrides and observe the value. Then run:

~~~bash
java -jar lesson.jar --lesson.run-id=known-test-run
~~~

The second run is expected to yield `known-test-run` because CLI supplies the business value with higher precedence. Having a random placeholder in the file does not mean it beats all other sources.

### Exercise E: Choosing a Port in Integration Tests

Try configuring `server.port=${random.int[10000,20000]}`, then compare with `server.port=0`. ### Exercise F: Classifying Requirements

Pick the right mechanism for each scenario:

| Requirement | Recommendation |
| --- | --- |
| Generate a temporary number for startup demo | `random.int` |
| A temporary UUID label for a startup run | `random.uuid`, if changing across runs is acceptable |
| Account ID that must persist long-term | ID allocator / storage with constraints |
| Server port automatically chosen in tests | `server.port=0` or equivalent test mechanism |
| Token signing secret shared across pods | Secret manager or synchronized secret source |
| Fresh jitter for each retry | Runtime random logic, not startup config property |
| Exact value for reproducible tests | Fixed test property |

## 15. Design Principles to Remember

**Random values are a deliberate choice.** Do not put `random.*` as a default fallback for every missing setting, especially values whose variation can cause bugs or complicate diagnostics.

**Think about value lifecycles before picking a source.** A value may need to stay fixed for a request, a JVM, a deployment, or the entire lifetime of data. `random.*` itself does not describe those lifecycles; code and deployment infrastructure must enforce them.

**Distinguish uniqueness from randomness.** An unpredictable number can still collide. When uniqueness is a business constraint, enforce it in storage or an allocation service.

**Distinguish convenience from security.** `RandomValuePropertySource` is handy in configuration and examples, not a secret-management system or a cryptographic quality guarantee.

**Preserve overridability and testability.** Place random placeholders behind a business property name, such as `demo.sample-index`, so tests and deployments can supply explicit values when needed.
