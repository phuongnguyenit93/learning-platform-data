# Using Java Records for Configuration and Nested Objects in Spring Boot

## 1. Goal and Context

Spring Boot allows loading configuration from `application.yaml`, `application.properties`, environment variables, command-line arguments, and other sources into Java objects via `@ConfigurationProperties`. When configuration spans multiple levels such as `demo.api.base-url`, `demo.retry.max-attempts`, and a `demo.regions` list, scattering many `@Value` annotations across services becomes hard to read, hard to test, and hard to maintain when the schema changes.

**Java records** are a concise choice for modeling structured configuration data. A record declares its data components right in its header, with constructor, accessors, `equals`, `hashCode`, and `toString` generated by Java. Spring Boot 3.3 can use **constructor binding** to instantiate a record from properties in `Environment`; if the record contains child records, the Binder continues building the entire nested object graph.

Target example for this lesson:

```yaml
demo:
  application-name: record-lab
  api:
    base-url: https://api.example.test
    connect-timeout: 2s
  retry:
    max-attempts: 3
    backoff: 250ms
```

Represented as:

```java
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        String applicationName,
        Api api,
        Retry retry
) {
    public record Api(URI baseUrl, Duration connectTimeout) {}

    public record Retry(int maxAttempts, Duration backoff) {}
}
```

The goal is to understand **why** nested YAML sections bind to nested `record` types, how to handle missing values, data types, validation, lists/maps, precedence, and bean lifecycle.

After completing this lesson, you will be able to:

1. Describe how `@ConfigurationProperties` maps canonical kebab-case names to camelCase record components.
2. Create records that are immutable at the reference level along with child records representing property groups.
3. Register records properly with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`.
4. Explain how constructor binding differs from JavaBean setter binding and field injection.
5. Use `@DefaultValue` on constructor/record components that have appropriate fallbacks.
6. Apply Bean Validation on root and nested records, including when an entire property group is missing.
7. Bind `Duration`, `URI`, booleans, lists, and maps while understanding the boundaries of immutability.
8. Create a Java 21 / Spring Boot 3.3 / Gradle project to observe the results firsthand.
9. Run repeatable experiments with profiles, CLI arguments, environment variables, and invalid configuration.
10. Choose config record designs suited to real applications while avoiding storing secrets and unnecessary mutable objects.

**Scope:** Spring Boot 3.3.x and Java 21. Domain names, labels, and sample values are not production services.

## 2. Why Choose Records for Configuration Properties?

Before Java records, a configuration class written in the JavaBean style often had many fields, getters, setters, and a default constructor:

```java
@ConfigurationProperties(prefix = "demo")
public class DemoProperties {
    private String applicationName;

    public String getApplicationName() {
        return applicationName;
    }

    public void setApplicationName(String applicationName) {
        this.applicationName = applicationName;
    }
}
```

This is **mutable JavaBean binding**: Spring instantiates the object and sets properties afterward. This style remains valid, especially when a mutable bean is needed, but for configuration that is only read after startup, exposing setters is not always desirable.

A record:

```java
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(String applicationName) {}
```

Has the accessor:

```java
properties.applicationName()
```

rather than the traditional bean accessor `properties.getApplicationName()`.

### 2.1. Constructor Binding Instead of Setter Binding

When binding to a record with a canonical constructor, Spring Boot knows the component names and prepares values for the constructor. The mental model is:

```text
application.yaml + environment + CLI
               |
               v
        Spring Environment
               |
               v
  ConfigurationProperties Binder
               |
               v
   resolves demo.application-name
               |
               v
 new DemoProperties("record-lab")
               |
               v
 Spring bean used by services
```

No setter is needed to populate `applicationName`; values are supplied **when creating the instance**.

This establishes a clear contract: which parameters construct the record, which parameters are required, and which parameters have defaults.

### 2.2. A Record Does Not Make Everything Inside Strictly Immutable

Record components are `private final` fields. You cannot reassign `properties.applicationName()` or replace the entire `properties.api()` once the record is created.

However, if a component holds a `List`, `Map`, array, or mutable class, **its inner contents can still change** without additional defensive measures.

Example:

```java
public record Options(List<String> regions) {}
```

External code could still modify the list if that `List` itself is mutable. To reduce risk, make a copy:

```java
public record Options(List<String> regions) {
    public Options {
        regions = regions == null ? List.of() : List.copyOf(regions);
    }
}
```

`List.copyOf` produces a collection that cannot be modified via standard `List` APIs. Immutability remains **shallow** if the inner elements are mutable objects. In configuration, prefer immutable element types such as `String`, `URI`, `Duration`, enums, or child records.

## 3. How Are YAML Keys and Java Record Components Linked?

Spring Boot recommends **canonical kebab-case** for property names.

| YAML / property key | Record component |
| --- | --- |
| `demo.application-name` | `applicationName` |
| `demo.api.base-url` | `api.baseUrl` |
| `demo.api.connect-timeout` | `api.connectTimeout` |
| `demo.retry.max-attempts` | `retry.maxAttempts` |
| `demo.retry.backoff` | `retry.backoff` |
| `demo.regions` | `regions` |

With YAML:

```yaml
demo:
  api:
    base-url: https://api.example.test
    connect-timeout: 2s
```

The Binder traverses level by level:

```text
demo
  |
  +-- api
        |
        +-- base-url        -> Api.baseUrl
        |
        +-- connect-timeout -> Api.connectTimeout
```

Dots create property hierarchy levels, while hyphens separate words **within a single level**. These two names do not describe the same schema:

```text
demo.api-base-url
demo.api.base-url
```

The first key has no `api` group; the second has a child `api` object. To bind into a nested `Api` record, use the second structure.

### 3.1. Relaxed Binding

The Spring Boot Binder applies **relaxed binding** rules: the same logical key can accept different naming formats across supported configuration sources. For instance, `application-name` in YAML can bind to Java's `applicationName`.

For environment variables, the corresponding canonical forms are:

```text
demo.application-name   -> DEMO_APPLICATIONNAME
demo.api.base-url       -> DEMO_API_BASEURL
demo.retry.max-attempts -> DEMO_RETRY_MAXATTEMPTS
```

When converting from a canonical name to an environment variable: replace dots with `_`, remove hyphens `-`, and convert to uppercase. Do not arbitrarily insert extra `_` between two words within the same name segment.

Stick to canonical notation in YAML, documentation, and CLI flags, while following the corresponding source rules for environment variables.

### 3.2. Record Components Do Not Need Setters

With traditional classes, many frameworks expect setters. Here, the Binder invokes the record's constructor. Therefore, components can remain `final`, and inner configuration groups are still constructed as new nested records.

This also differs from placing `@Value` on multiple instance fields. `@Value` typically resolves a single placeholder, whereas `@ConfigurationProperties` resolves **an entire group of properties**, supporting conversion, collection binding, and structural validation.

## 4. Nested Records: Using an Object Tree Instead of a Flat Class

Suppose an application needs a name, an API client configuration, a retry policy, and region labels.

A flat design might look like:

```java
public record FlatSettings(
        String applicationName,
        URI apiBaseUrl,
        Duration apiConnectTimeout,
        int retryMaxAttempts,
        Duration retryBackoff
) {}
```

It works, but grows long when there are multiple property groups or multiple backends. Replace it with nested records:

```java
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        String applicationName,
        Api api,
        Retry retry
) {
    public record Api(
            URI baseUrl,
            Duration connectTimeout
    ) {}

    public record Retry(
            int maxAttempts,
            Duration backoff
    ) {}
}
```

Usage:

```java
URI apiUrl = demoProperties.api().baseUrl();
int attempts = demoProperties.retry().maxAttempts();
```

`Api` and `Retry` are **nested records**. In Java, a member record declared inside a class or record is a nested type that semantically holds no hidden reference to the enclosing instance. There is no need to write `static` before the `record` keyword.

This **does not contradict** the rule against injecting configuration into a `static field`. A nested record is a **data type**, while each `new Api(...)` or `new Retry(...)` object is still an instance with its own components. Spring Boot is not injecting into a global static variable here.

### 4.1. Must Every Group Use a Nested Record?

Not necessarily. You can extract:

```java
public record ApiSettings(URI baseUrl, Duration connectTimeout) {}
```

into a separate top-level type and use it as a component of the root record. Constructor binding still works when the schema matches.

However, declaring nested records inside the root record makes it immediately clear which groups **belong exclusively** to that configuration. If a type is shared across multiple places or carries complex rules, extracting a separate class or record is often easier to maintain.

## 5. Registering a Record with Spring Boot Properly

`@ConfigurationProperties(prefix = "demo")` defines the binding prefix, but the annotation itself does not necessarily register a bean. In Spring Boot setups, there are two common ways:

### 5.1. Scanning with `@ConfigurationPropertiesScan`

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class RecordBindingApplication {
    public static void main(String[] args) {
        SpringApplication.run(RecordBindingApplication.class, args);
    }
}
```

Spring Boot finds `@ConfigurationProperties` types within the scan scope, registers the beans, and binds them when the context is created. This is convenient when a project has many configuration properties classes.

### 5.2. Explicit Registration with `@EnableConfigurationProperties`

```java
@SpringBootApplication
@EnableConfigurationProperties(DemoProperties.class)
public class RecordBindingApplication {
    public static void main(String[] args) {
        SpringApplication.run(RecordBindingApplication.class, args);
    }
}
```

This fits when you want an explicit list of registered configuration types. **Pick one appropriate method for this lab**; there is no need to use both just to register the same bean.

### 5.3. Avoid `@Component` on Constructor-Bound Configuration Records

You may come across code like:

```java
@Component
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(String applicationName) {}
```

This **is not the recommended approach** for constructor binding. If a bean is created through a regular Spring bean mechanism like `@Component`, constructor parameters may be interpreted as dependencies to autowire rather than properties to bind. Spring Boot requires constructor binding to be registered via a configuration-properties mechanism such as scanning or `@EnableConfigurationProperties`, not by creating a bean via `@Component` or a regular `@Bean` factory method and expecting the Binder to invoke its constructor that way.

**Use `@ConfigurationProperties` + `@ConfigurationPropertiesScan`** for the record in this lesson.

### 5.4. Is `@ConstructorBinding` Needed on a Record?

In Spring Boot 3.3, if a configuration type has one suitable parameterized constructor, constructor binding is inferred automatically. A standard record has its canonical constructor, so you **do not need** to add `@ConstructorBinding` to enable it.

In Spring Boot 3, `@ConstructorBinding` is placed on a **constructor** when you need to designate the binding constructor in cases of multiple constructors or ambiguity. Do not take old Spring Boot 2.x examples that put this annotation on the class and copy them verbatim into a Boot 3.3 project.

If using a regular class instead of a record, parameter names must be present so the Binder knows each parameter's name. Java records already capture component names as part of the language structure. For regular class constructors, build settings to retain parameter names (`-parameters`) may need to be checked depending on the version/framework.

### 6.4. Root Record and Nested Records

`src/main/java/dev/example/recordbinding/DemoProperties.java`:

```java
package dev.example.recordbinding;

import java.net.URI;
import java.time.Duration;
import java.util.List;
import java.util.Map;

import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotEmpty;
import jakarta.validation.constraints.NotNull;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        @NotBlank String applicationName,
        @Valid @NotNull Api api,
        @Valid @NotNull Retry retry,
        @NotEmpty List<String> regions,
        Map<String, String> labels
) {
    // Compact constructor: keep an immutable copy of collections.
    public DemoProperties {
        regions = regions == null ? List.of() : List.copyOf(regions);
        labels = labels == null ? Map.of() : Map.copyOf(labels);
    }

    public record Api(
            @NotNull URI baseUrl,
            @DefaultValue("2s") @NotNull Duration connectTimeout
    ) {}

    public record Retry(
            @DefaultValue("3") @Min(1) @Max(10) int maxAttempts,
            @DefaultValue("250ms") @NotNull Duration backoff
    ) {}
}
```

Explanation of each part:

1. `@ConfigurationProperties(prefix = "demo")` indicates the entire record receives values from the `demo.*` key group.
2. `@Validated` instructs Spring Boot to perform validation with the validator configured in the context.
3. `@NotBlank applicationName` requires a non-blank name.
4. `@Valid @NotNull Api api` both requires the `api` group to exist and cascades validation into the nested record.
5. `@Valid @NotNull Retry retry` does the same for the `retry` group.
6. `@DefaultValue("2s")` on `connectTimeout` takes effect when that child property is omitted while binding an `Api`.
7. `@DefaultValue("3")` on `maxAttempts` supplies 3 when the property does not appear.
8. `@Min(1)` and `@Max(10)` bound valid attempt counts from 1 to 10.
9. `List.copyOf` and `Map.copyOf` avoid storing mutable collections directly in the record.
10. If an entire `api`/`retry` group is unbound and has no default at the **nested component level**, the corresponding root component can be `null`, and `@NotNull` will report missing configuration.

Inside the compact constructor, Java reassigns the `regions` and `labels` parameter variables before the constructor finishes. The record fields receive those copies. This is a simple defensive pattern well suited for collections containing `String`.

Note: `Map.copyOf` and `List.copyOf` do not accept `null` elements or values; for configuration schemas that need to retain `null` values, build a different normalization rule instead of copying as shown.

### 6.5. Main Class and ApplicationRunner

`src/main/java/dev/example/recordbinding/RecordBindingApplication.java`:

```java
package dev.example.recordbinding;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;

@SpringBootApplication
@ConfigurationPropertiesScan
public class RecordBindingApplication {

    public static void main(String[] args) {
        SpringApplication.run(RecordBindingApplication.class, args);
    }

    @Bean
    ApplicationRunner report(DemoProperties properties,
                             Environment environment) {
        return args -> {
            System.out.println("=== RECORD CONFIGURATION ===");
            System.out.println("activeProfiles = "
                    + String.join(",", environment.getActiveProfiles()));
            System.out.println("applicationName = "
                    + properties.applicationName());
            System.out.println("api.baseUrl = "
                    + properties.api().baseUrl());
            System.out.println("api.connectTimeout = "
                    + properties.api().connectTimeout());
            System.out.println("retry.maxAttempts = "
                    + properties.retry().maxAttempts());
            System.out.println("retry.backoff = "
                    + properties.retry().backoff());
            System.out.println("regions = " + properties.regions());
            System.out.println("labels = " + properties.labels());
        };
    }
}
```

The application runs as a console app; because `spring.main.web-application-type=none` is set, it does not start a web server. Values are already bound into the record before the runner is invoked. `ApplicationRunner` prints only illustrative properties, never accessing secrets.

### 7.1. If `api.connect-timeout` Is Removed

Edit `application.yaml`:

```yaml
demo:
  application-name: "record-lab"
  api:
    base-url: "https://api.example.test"
  retry:
    backoff: 400ms
  regions:
    - ap-southeast-1
  labels:
    team: education
```

Run again. `api.connectTimeout()` is expected to be `PT2S` thanks to:

```java
@DefaultValue("2s") Duration connectTimeout
```

Do not think of defaults in a record as a new configuration file. They are values used by the Binder when no specific value exists for the parameter being bound.

### 7.2. If the Entire `api` Group Is Removed

If YAML omits the entire `demo.api` group, the value of the `api` root component can be `null`. With `@NotNull` at the root and validation enabled, the application will refuse to start rather than letting a service call `properties.api().baseUrl()` and hit a `NullPointerException`.

A default on the **child component** `connectTimeout` does not automatically decide that the parent group `Api` must be instantiated when the entire subtree is missing. To make a nested group optional while still providing an instance with defaults, see the section on `@DefaultValue` for nested objects below.

## 10. Validation on Records and Nested Records

A typed record reduces errors from arbitrary setter calls, but does not automatically guarantee every value is **valid in business terms**. For instance, `maxAttempts=-5` is still an `int` and converts successfully; its error lies in business rules.

Bean Validation provides constraints:

```java
@Validated
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        @NotBlank String applicationName,
        @Valid @NotNull Api api,
        @Valid @NotNull Retry retry,
        @NotEmpty List<String> regions
) {
    public record Api(
            @NotNull URI baseUrl,
            @NotNull Duration connectTimeout
    ) {}

    public record Retry(
            @Min(1) @Max(10) int maxAttempts,
            @NotNull Duration backoff
    ) {}
}
```

- `@Validated` on the root type activates configuration-properties validation.
- `@Valid` on nested components instructs the validator to recurse into child objects.
- `@NotNull` on `api` or `retry` prevents losing an entire group.
- `@NotBlank` applies to `String`.
- `@NotEmpty` suits lists that must contain at least one element.
- `@Min` and `@Max` bound numeric values.

In the sample project, constraints on the record are already used together with `spring-boot-starter-validation`.

### 10.1. Testing an Invalid Value

Run:

```bash
./gradlew bootRun --args='--demo.retry.max-attempts=0'
```

The value `0` converts to `int`, but fails `@Min(1)`. When binding and validation execute, Spring Boot reports a configuration error and the context may fail to start. This is the desired behavior for required configuration.

Similarly, try:

```bash
./gradlew bootRun --args='--demo.application-name='
```

An empty string fails `@NotBlank`.

### 10.2. Testing a Type Conversion Error

```bash
./gradlew bootRun --args='--demo.api.connect-timeout=not-a-duration'
```

Here the binder cannot convert the string into a `Duration`, so a binding error occurs before the application runs normally. Distinguish **type conversion errors** from **validation errors**: `not-a-duration` has an invalid type format, whereas `0` for `maxAttempts` has a valid type but violates a constraint.

### 10.3. When a Nested Object Is Completely Absent

Two different cases:

```yaml
demo:
  api:
    base-url: https://api.example.test
```

and:

```yaml
demo:
  # no api group
  retry:
    max-attempts: 3
```

The first case can construct an `Api` with `connectTimeout` taken from `@DefaultValue("2s")`. The second case **does not necessarily create Api**. With `@NotNull` on the root `api` component, the application is required to detect the missing required group.

This is why validation design must examine **whole nested groups**, not only their inner fields.

## 11. `@DefaultValue` and Constructor Binding

In JavaBean binding, a mutable class sometimes sets defaults using field initializers:

```java
private int maxAttempts = 3;
```

With record constructor binding, there are **no setters** to override an already-initialized instance field in that same way. Spring Boot provides `@DefaultValue` for constructor parameters and record components.

Example:

```java
public record Retry(
        @DefaultValue("3") int maxAttempts,
        @DefaultValue("250ms") Duration backoff
) {}
```

When keys are omitted and the Binder creates a `Retry`, `maxAttempts` can receive `3` and `backoff` receives a 250-millisecond `Duration`. The Binder performs conversion based on the target type.

### 11.1. Default for an Entire Nested Object

If a configuration group **can be absent**, yet you still want to construct the nested record from its inner defaults, you can declare `@DefaultValue` with no arguments on **the parent object's component**:

```java
@ConfigurationProperties(prefix = "feature")
public record FeatureProperties(
        @DefaultValue Security security
) {
    public record Security(
            @DefaultValue("false") boolean enabled,
            @DefaultValue("public") String mode
    ) {}
}
```

When the entire `feature.security` group is missing, the argument-less `@DefaultValue` on the `security` component lets the Binder create the nested object using appropriate defaults. If a nested-type component requires mandatory data with no defaults, design validation rather than creating an incomplete object and using it.

Distinguish three scenarios:

| Scenario | Design |
| --- | --- |
| A primitive/string parameter has a clear fallback | `@DefaultValue("3")` |
| A nested object can be absent yet still needs a default instance | `@DefaultValue` on the nested component |
| A configuration group must be declared | `@NotNull` and `@Valid`, do not mask absence with defaults |

Do not turn all required configuration into optional settings just so the application always starts.

### 11.2. Record Defaults vs. Placeholder Fallbacks

The two forms:

```java
@DefaultValue("3") int maxAttempts
```

and:

```java
@Value("${demo.retry.max-attempts:3}") int maxAttempts
```

are not completely equivalent in where they apply.

`@DefaultValue` belongs to the constructor parameter's **binding** contract; placeholder fallback belongs to the `${...}` reference site. For a property group used across multiple services, centralize defaults in the configuration type or baseline file instead of having each service define its own fallback.

## 12. Nested Records and Collections

Real-world configuration often includes lists or maps alongside scalar properties.

### 12.1. Simple Lists

YAML:

```yaml
demo:
  regions:
    - ap-southeast-1
    - eu-west-1
```

Java:

```java
public record DemoProperties(List<String> regions) {}
```

The whole `List<String>` is a single component. Spring Boot can bind list data from YAML or from index notation in `.properties`:

```properties
demo.regions[0]=ap-southeast-1
demo.regions[1]=eu-west-1
```

When list configuration appears in multiple property sources, understand Spring Boot's precedence and list-replacement rules. Do not assume it merges elements from every file into one longer list.

### 12.2. Simple Maps

YAML:

```yaml
demo:
  labels:
    team: education
    tier: sandbox
```

Record component:

```java
Map<String, String> labels
```

Access:

```java
String team = demoProperties.labels().get("team");
```

Maps fit when key names are more dynamic than a rigid record schema, such as operator-defined region names or labels. However, when keys have fixed meanings like `baseUrl` and `connectTimeout`, a nested record is usually clearer because it models the schema and type of each value.

### 12.3. Maps Whose Values Are Child Records

An advanced example:

```yaml
integrations:
  clients:
    billing:
      base-url: https://billing.example.test
      connect-timeout: 1s
    inventory:
      base-url: https://inventory.example.test
      connect-timeout: 2s
```

Java:

```java
@ConfigurationProperties(prefix = "integrations")
public record IntegrationsProperties(
        Map<String, Client> clients
) {
    public record Client(
            URI baseUrl,
            Duration connectTimeout
    ) {}
}
```

The Binder can create a map with keys `billing` and `inventory`, each value being a `Client` record. This pattern fits when the set of client names varies by deployment while every client shares the same structure.

For map keys containing dots, slashes, or special characters, pay attention to Spring Boot's map binding syntax and bracket notation to preserve key names. For basic labs, use simple lowercase alphabetic keys to focus on record binding.

### 12.4. Immutability of Nested Collections

Even when the outer map itself is unmodifiable, its inner values could be mutable classes if you use regular classes. For a configuration graph intended to remain stable after startup, prefer child records and immutable value types.

If you need to add or remove clients at runtime, that is generally no longer a simple "immutable config snapshot" problem; design a dedicated state-management service with concurrency and refresh rules rather than trying to mutate configuration records.

## 13. Record Compact Constructors: How Much Should They Do?

A compact constructor is useful for non-negotiable invariants:

```java
public record Retry(int maxAttempts, Duration backoff) {
    public Retry {
        if (maxAttempts < 1) {
            throw new IllegalArgumentException(
                    "maxAttempts must be positive");
        }
        if (backoff == null || backoff.isNegative()) {
            throw new IllegalArgumentException(
                    "backoff must not be negative");
        }
    }
}
```

This guarantees a `Retry` instance can never be constructed with values violating the constructor's checks. However, for configuration properties, manual exceptions typically provide less structured messages than Bean Validation.

**Suggested separation of responsibilities:**

- Basic type conversion: let the Spring Boot Binder handle it.
- Default constructor parameters: use `@DefaultValue` or a baseline configuration file.
- Declarative constraint checks: use Jakarta Validation.
- Complex invariants that cannot be expressed with annotations: consider a compact constructor, custom validator, or startup validation service.
- Copying collections: a compact constructor is appropriate to protect shallow immutability.

Do not put I/O operations, network calls, or Spring bean lookups inside a configuration record's constructor. A record should represent data; services are where side effects belong.

## 14. `@ConfigurationPropertiesScan` and Package Layout

The main class is located at:

```text
dev.example.recordbinding.RecordBindingApplication
```

and the configuration record is located at:

```text
dev.example.recordbinding.DemoProperties
```

so `@ConfigurationPropertiesScan` on the main class discovers `DemoProperties` within the appropriate package scope.

If you move the record into a package **outside the scan scope**, the bean may not be registered. In that case, pick one valid approach:

```java
@ConfigurationPropertiesScan(
        basePackages = "dev.example.configuration"
)
```

or:

```java
@EnableConfigurationProperties(DemoProperties.class)
```

Do not fix this by casually adding `@Component` to a constructor-bound record.

When the record has no bean in the context, errors usually appear at the service injection point, such as:

```text
No qualifying bean of type DemoProperties
```

This is a **bean registration** issue, distinct from **binding** or **validation** failures. Classifying the error correctly speeds up resolution.

## 15. Reading Records in a Service

A well-designed service does not need to know whether configuration came from YAML, profiles, CLI arguments, or Kubernetes environment variables:

```java
package dev.example.recordbinding;

import java.net.URI;
import java.time.Duration;

import org.springframework.stereotype.Service;

@Service
public class ApiPolicyService {

    private final DemoProperties properties;

    public ApiPolicyService(DemoProperties properties) {
        this.properties = properties;
    }

    public URI baseUrl() {
        return properties.api().baseUrl();
    }

    public Duration timeout() {
        return properties.api().connectTimeout();
    }

    public int maxAttempts() {
        return properties.retry().maxAttempts();
    }
}
```

The service only knows one **typed contract**: `DemoProperties`. This avoids scattered `${...}` strings, stops each service from guessing its own defaults, and keeps unit tests easy to control.

In plain Java unit tests, you can instantiate configuration explicitly:

```java
DemoProperties props = new DemoProperties(
        "unit-test",
        new DemoProperties.Api(
                URI.create("https://api.example.test"),
                Duration.ofSeconds(1)),
        new DemoProperties.Retry(
                2, Duration.ofMillis(100)),
        List.of("local"),
        Map.of("team", "tests"));

ApiPolicyService service = new ApiPolicyService(props);
```

This test **needs no Spring context**, so it is fast and independent of Config Data loading. It tests service logic with a concrete configuration object, not the Binder.

Conversely, an integration test with `@SpringBootTest` is suitable for verifying that Spring Boot reads configuration and instantiates records via constructor binding.

## 16. Testing Binding with Spring Boot Test

`src/test/java/dev/example/recordbinding/DemoPropertiesTest.java`:

```java
package dev.example.recordbinding;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.net.URI;
import java.time.Duration;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest(properties = {
        "demo.application-name=from-test",
        "demo.api.base-url=https://test.example.test",
        "demo.retry.max-attempts=8"
})
class DemoPropertiesTest {

    @Autowired
    DemoProperties properties;

    @Test
    void bindsRootAndNestedRecords() {
        assertEquals("from-test", properties.applicationName());
        assertEquals(URI.create("https://test.example.test"),
                properties.api().baseUrl());
        assertEquals(8, properties.retry().maxAttempts());
        assertEquals(Duration.ofMillis(400),
                properties.retry().backoff());
        assertTrue(properties.regions().contains("ap-southeast-1"));
    }
}
```

Run:

macOS/Linux:

```bash
./gradlew test
```

PowerShell:

```powershell
.\gradlew.bat test
```

In this example, `application.yaml` supplies the non-overridden keys, such as `demo.retry.backoff` and `demo.regions`; the test properties override the three listed keys. Spring Boot still constructs both root and nested records, converts `URI`/`Duration`, and runs validation.

### 16.1. One Test Does Not Cover Every Error Case

Add cases meaningful to your application:

- A required group `demo.api` is missing.
- `demo.retry.max-attempts=0` violates `@Min(1)`.
- Malformed duration string.
- An empty required list.
- Configuration under the `dev` profile produces different record values than baseline configuration.
- Environment variable and CLI names map to expected canonical names.
- Sensitive data is not printed to logs, `toString`, or endpoints.

Testing startup failures requires an appropriate context setup, such as `ApplicationContextRunner`, to assert failure without breaking the entire test suite on context load. For simple keys, `@SpringBootTest` covering the happy path is enough to get started.

## 17. Distinguishing Four Common Error Types

| Symptom | Typical Cause | Starting Point to Fix |
| --- | --- | --- |
| Cannot inject `DemoProperties` | Bean not registered / outside scan scope | Check `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties` |
| Error binding `base-url` to `URI` or `connect-timeout` to `Duration` | Value cannot convert to target type | Check raw value and syntax |
| `@NotBlank`, `@NotNull`, `@Min` error | Value converted yet violates constraint, or nested group missing | Check validation on root and nested records |
| Result differs from newly edited YAML file | Profile, environment, CLI, or another location overrides it | Check `Environment` and source precedence |

Also distinguish **property naming errors** from validation errors. If YAML uses `demo.api-base-url` instead of `demo.api.base-url`, the Binder will not automatically put that flat key into the nested `Api` record. `api.baseUrl` may be missing even though you see a URL string in the file.

### 17.1. Why Is a Nested Record `null`?

Causes to consider:

1. No property at all was declared under that nested prefix.
2. Misspelled group name, e.g., `demo.client` when the record declares `api`.
3. The file is placed in a location that is not loaded.
4. The profile containing the configuration file is not active.
5. `spring.config.location` changed the default search locations.
6. A higher-precedence source altered or cleared the expected configuration.
7. `@DefaultValue` was omitted on the nested component when a default object is desired despite the entire subtree being absent.

For required groups, `@NotNull` paired with `@Valid` enables failing fast rather than failing only when a service calls a nested method.

### 17.2. Why Didn't `@DefaultValue` Apply as Expected?

Check whether the value is truly **absent**. `@DefaultValue` is for when there is no value to bind; it is not a mechanism that replaces empty strings or malformed data.

For example, `demo.retry.max-attempts=garbage` should not silently fall back to 3. The Binder cannot convert the existing input into an `int`, so a conversion error is appropriate.

If an entire nested subtree is missing, defaults on components **inside the nested record** alone may not instantiate the nested record itself. Look at the nested-type component on the parent record.

## 18. Records and Profiles: Same Schema, Multiple Value Sets

One strength of typed configuration records is that **the schema does not have to change** per environment.

Baseline file:

```yaml
demo:
  api:
    base-url: https://api.example.test
```

Dev file:

```yaml
demo:
  api:
    base-url: http://localhost:8089
```

With the dev profile active, both still bind into:

```java
DemoProperties.Api(URI baseUrl, Duration connectTimeout)
```

Which source takes precedence is Externalized Configuration's job; the Java object retains the same types and accessors.

This avoids code like:

```java
if (isDev) {
    return devUrl;
}
return prodUrl;
```

just to pick a configuration value. A service can use `properties.api().baseUrl()` across every profile, while operators supply values from properly ordered and managed configuration sources.

Do not treat profiles as a secret-protection mechanism. A profile file packaged in a JAR can still be read from the artifact; credentials should come from managed secure sources, not embedded in source or record `toString` output.

## 19. Should You Log an Entire Record Using `toString()`?

Java records generate a `toString()` containing the type name and all component values. For example:

```java
System.out.println(properties);
```

can produce readable output, yet poses a **risk if the record contains credentials or tokens**. When a nested record holds a secret, the root's `toString()` can print those values too.

In this lab, only mock keys are printed to the console. In production:

- Do not automatically log entire configuration properties records.
- Do not expose `Environment`, Actuator `env`/`configprops`, or configuration objects on public endpoints.
- Consider separating secrets from displayable groups.
- If a setting must be verified, log only allowlisted keys approved for display.
- Restrict read permissions on files and environment variables holding secrets.
- Never let `String` or `record` types become an excuse to bypass secret management.

Records clarify the data contract; they do not make the data inside them secure.

## 20. Comparison Table: Record, POJO, and `@Value`

| Criterion | Record + `@ConfigurationProperties` | Mutable POJO + `@ConfigurationProperties` | Multiple `@Value` |
| --- | --- | --- | --- |
| Reading structured property groups | Very well suited | Very well suited | Easily scattered |
| Constructor binding | Natural | Possible, depending on constructor | Mostly per parameter |
| Requires setters | No | Usually present in JavaBean binding | Not required |
| Nested objects | Nested record or class | Nested class or object | Must manage multiple strings manually |
| Type conversion | Yes | Yes | Yes, but does not replace the Binder |
| Structured validation | Good fit | Good fit | Hard to centralize |
| Instance state after binding | Record components cannot be reassigned | Can be mutable | Depends on class |
| Collection defense | Consider `List.copyOf` | Consider defensive copying | Depends on object |
| Unit tests without Spring | Instantiate record via constructor | Instantiate POJO | Need appropriate dependency isolation |
| Recommendation | Stable, read-heavy configuration schemas | When mutable beans or framework constraints apply | A few isolated single values |

Records are not always the sole option. When a system requires dynamic refresh with a specific state-transition strategy, consider object lifecycle and how consumers receive updates. Records usually work best as a **configuration snapshot** at binding time.

## 21. Common Misconceptions

### "Records don't have constructors so Spring won't know how to create them"

Records have a canonical constructor provided by Java. That constructor accepts the record components in declaration order. Spring Boot's binder uses record metadata and constructor binding to pass values.

### "You must add `@ConstructorBinding` to every record"

Not in Spring Boot 3.3 for a regular record with one eligible constructor. If reading older guides that put the annotation at the class level, check Boot 3's API before copying.

### "Adding `@Component` helps Spring find the record more easily"

For constructor-bound `@ConfigurationProperties`, that is not the proper registration method. Use `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`.

### "Nested records are implicitly `static` so they cannot be bound"

A nested record is a **type** that can have many instances; it is not a static field for Spring to inject values into. The Binder instantiates nested objects via constructor just like other records.

### "If nested fields have defaults, omitting the entire nested object still works"

Do not assume that. If the entire subtree is absent, the nested component on the root record can be null. Decide whether the object is required or optional and use `@NotNull` or `@DefaultValue` at the nested-component level accordingly.

### "Records make Maps and Lists completely immutable"

The component reference itself is `final`, yet the collection can remain mutable. Use `List.copyOf`/`Map.copyOf` or immutable value types when protecting the snapshot.

### "Adding a dev file automatically loads dev values into the record"

No. `application-dev.yaml` is only used when the `dev` profile is active. Enable the profile through a valid source.

### "Maps and lists from multiple sources are always merged the same way"

No. Collection binding follows distinct rules: lists are typically replaced by the chosen source, while maps can merge by key. Read the rules for each collection type and test with actual files/profiles.

### "A record config bean is a global singleton like static"

A regular Spring singleton is one bean scoped to the **ApplicationContext**. A static field is class/JVM-level state. Registering a configuration record as a bean does not turn it into a global static variable.

### "Editing YAML at runtime automatically updates an active record"

Not by default. Standard Config Data binds configuration at startup. Dynamic refresh, if used, is a separate mechanism that may recreate/swap instances and refresh consumers. Do not treat a record as a live view of a file.

## 22. Checklist for Shipping a Configuration Record

Before introducing a new configuration group into a real application:

1. Choose a clear prefix that does not collide with framework or library groups.
2. Use canonical kebab-case property names in documentation.
3. Use nested records for groups with fixed schemas; use maps when keys are genuinely dynamic.
4. Decide which groups are required and which are optional.
5. Use `@DefaultValue` when defaults make business sense, without hiding missing critical configuration.
6. Add `@Validated` at the root and `@Valid` on nested components when deep checks are needed.
7. Register the record with `@ConfigurationPropertiesScan` or `@EnableConfigurationProperties`.
8. Keep configuration that does not need mutability as a stable snapshot; copy collections if needed.
9. Inject the record into services via constructors; avoid services looking up the same keys via `Environment` in multiple places.
10. Test at least one baseline configuration, one profile override, and one critical validation failure.
11. Never print entire configurations or secrets via `toString` or endpoints.
12. When dynamic refresh is required, design an explicit update lifecycle instead of arbitrarily mutating configuration state.

## 24. Conclusion

`@ConfigurationProperties` combined with Java records is a clean, strongly typed way to represent Spring Boot configuration. A root record describes the **schema**, nested records model **configuration groups**, constructor binding creates a **typed configuration snapshot**, and `@DefaultValue` with Bean Validation express **fallbacks and constraints** directly on the data contract.

What matters most is not reducing Java line count, but separating responsibilities:

```text
Configuration sources / precedence -> Spring Environment
Name and type conversion           -> ConfigurationProperties Binder
Structure and defaults             -> Record + nested records
Input constraints                  -> Bean Validation
Business consumption               -> Service receiving bean via constructor
```

When a value behaves unexpectedly, verify in order: was the property actually loaded, do the canonical name and prefix match, which profile and source precedence are active, was the nested object instantiated, and did conversion and validation succeed. This design keeps configuration clear as an application grows in deployment environments and property groups.
