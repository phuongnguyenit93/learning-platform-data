# What Is Configuration Metadata and How Does IDE Support Work in Spring Boot 3.3?

## 1. Overview

When writing a Spring Boot application, you may encounter the following keys:

```properties
spring.application.name=inventory-service
server.port=8081
management.endpoint.health.show-details=when-authorized
```

In an IDE with Spring support, you often see features such as key name auto-completion, data type display, descriptions, default values, or warnings when using a deprecated configuration key. The tool does not need to start the entire application to understand these details. Instead, it can read **Spring Boot configuration metadata** packaged alongside the libraries.

When creating your own configuration group such as:

```yaml
acme:
  mail:
    enabled: true
    retry-count: 3
    timeout: 5s
    channel: email
```

you can provide metadata for `acme.mail.*` so the IDE suggests properties similarly to `spring.*` or `server.*`.

This lesson belongs to the **Configuration Metadata** group of the **Spring Boot Externalized Configuration** topic, applicable to **Spring Boot 3.3.x** and Java **17+**. The contents include:

- What configuration metadata is, where it resides, and how it is structured.
- Why metadata is not a runtime configuration value source.
- How IDEs use metadata to suggest keys, types, descriptions, and values.
- How to generate metadata using `spring-boot-configuration-processor`.
- Maven and Gradle configuration.
- How to declare `@ConfigurationProperties`, field Javadoc, records, and nested objects.
- How to supplement with `additional-spring-configuration-metadata.json`.
- `groups`, `properties`, `hints`, providers, and deprecation.
- Support limitations by IDE/plugin and how to troubleshoot when metadata is not recognized.
- Methods to inspect build output and distinguish tooling errors from Binder errors.

## 2. What Is Configuration Metadata?

**Configuration metadata** is data that *describes* the configuration properties exposed by a Spring Boot application or library. Metadata is typically stored as JSON at:

```text
META-INF/spring-configuration-metadata.json
```

Inside it, there may be:

```json
{
  "groups": [
    {
      "name": "acme.mail",
      "type": "example.metadata.MailProperties",
      "sourceType": "example.metadata.MailProperties"
    }
  ],
  "properties": [
    {
      "name": "acme.mail.timeout",
      "type": "java.time.Duration",
      "description": "Timeout for one outbound mail request.",
      "defaultValue": "5s"
    }
  ],
  "hints": [
    {
      "name": "acme.mail.channel",
      "values": [
        {"value": "email"},
        {"value": "smtp-api"}
      ]
    }
  ]
}
```

This is an example of the JSON structure, not a byte-for-byte guarantee of a file generated by the annotation processor.

Metadata states: "there is a group `acme.mail`, a property `acme.mail.timeout` of type `Duration`, and suggested values for `acme.mail.channel`."

It **does not state** that the running application is actually using `timeout=5s`.

A mental model:

```text
Java code with @ConfigurationProperties
           |
           v
spring-boot-configuration-processor
           |
           v
META-INF/spring-configuration-metadata.json
           |
           v
IDE / configuration support tools
  - Suggest key names
  - Display descriptions
  - Suggest types and values
  - Warn on deprecated keys
```

The **runtime** path is different:

```text
application.yaml / environment / CLI / import
           |
           v
Config Data + PropertySource precedence
           |
           v
Binder + ConversionService + validation
           |
           v
@ConfigurationProperties bean
           |
           v
Service uses the effective value
```

Do not confuse the two diagrams.

## 3. Distinguishing Metadata, Configuration Files, and Java Models

| Component | Where is it located? | Purpose |
| --- | --- | --- |
| `application.properties` | In the classpath or another config location | Provides actual values |
| `application.yaml` | In the classpath or another config location | Provides actual values |
| Environment variables | Environment of the Java process | A value source with its own precedence order |
| `@ConfigurationProperties` | Java code | Typed configuration group binding model |
| `spring-configuration-metadata.json` | `META-INF` in output/JAR | Describes properties for tooling |
| `additional-spring-configuration-metadata.json` | `src/main/resources/META-INF` | Supplements/adjusts metadata at build time |
| `@Validated` / Bean Validation | Java code | Data constraints during binding/validation |

For example:

```properties
acme.mail.timeout=3s
```

in a shared file, while an environment variable has:

```text
ACME_MAIL_TIMEOUT=10s
```

Metadata may describe a default of `"5s"`. When Spring Boot runs, the effective value can be `10s` from the environment variable. Metadata does not override environment variables and does not automatically add a new `PropertySource`.

**Metadata is a configuration contract description for tooling, not a file containing prioritized values at startup.**

## 4. What Benefits Does the IDE Get?

An IDE or extension that supports Spring Boot metadata can perform the following functions:

1. **Key name auto-completion:** after typing `acme.mail.`, it can suggest `enabled`, `timeout`, `retry-count`, `channel`.
2. **Contextual description:** hovering over `timeout` can show the explanation from metadata.
3. **Data type:** knowing `timeout` is `Duration` and `retry-count` is an integer.
4. **Suggested values:** for enums or `hints`, the IDE can propose choices like `email`, `smtp-api`.
5. **Default value:** the IDE can display the default value described in metadata.
6. **Deprecated warning:** when typing an old key, the IDE can notify about the replacement key.
7. **Navigate to source:** the `sourceType` field can help tools link the property to the Java class.
8. **Unknown key warning:** depending on the plugin, the IDE may detect certain typos.

However, metadata does not force every IDE to display the same features. Support capabilities depend on the editor, extension, version, project configuration, and classpath.

If a plain text editor does not show completion, you cannot conclude that the metadata file is wrong. Conversely, an IDE showing completion does not prove that the runtime application is actually reading the key.

## 5. Three Main Arrays: `groups`, `properties`, `hints`

In Spring Boot 3.3, metadata JSON typically has three sections:

```json
{
  "groups": [],
  "properties": [],
  "hints": []
}
```

### `groups`

A group gathers properties that share a common context. For example:

```json
{
  "name": "acme.mail",
  "type": "example.metadata.MailProperties",
  "sourceType": "example.metadata.MailProperties"
}
```

The `acme.mail` group does not necessarily have a value of its own. It serves as the namespace for `acme.mail.timeout`, `acme.mail.enabled`, etc.

Group entries may contain a name, type, source class, or source method. Some nested groups may be generated when the processor recognizes nested objects in the Java model.

### `properties`

Each element represents a specific property:

```json
{
  "name": "acme.mail.retry-count",
  "type": "java.lang.Integer",
  "description": "Maximum number of retries.",
  "sourceType": "example.metadata.MailProperties",
  "defaultValue": 3
}
```

Meaning of common fields:

| Field | Meaning |
| --- | --- |
| `name` | Full canonical name, for example `acme.mail.retry-count` |
| `type` | Java type that the property corresponds to |
| `description` | Short description for whoever configures the property |
| `sourceType` | Java class that contributes the property declaration |
| `defaultValue` | Described default value if determinable |
| `deprecation` | Information indicating the property is no longer recommended |

Not every property is required to have all fields. If the processor cannot determine a description or defaultValue, that data may be omitted.

### `hints`

Hints help tools assist with value entry:

```json
{
  "name": "acme.mail.channel",
  "values": [
    {
      "value": "email",
      "description": "Send messages using email."
    },
    {
      "value": "smtp-api",
      "description": "Send messages through the SMTP API."
    }
  ]
}
```

`hints.values` proposes values; `hints.providers` can suggest dynamic content sources, such as class names or profiles.

**HINTS DO NOT MEAN VALIDATION.** If the Java field is a `String`, a value outside the list can still be accepted by the Binder if there is no enum, validation, or explicit blocking logic.

## 6. Where Does Metadata Come From?

Official Spring Boot starters already carry metadata for many configuration properties. When an application depends on a starter, the IDE can read metadata from the dependency JAR.

As for application-specific properties, the common approach is:

```java
@ConfigurationProperties(prefix = "acme.mail")
public class MailProperties {
    // ...
}
```

and using the annotation processor:

```text
org.springframework.boot:spring-boot-configuration-processor
```

The processor runs during **Java compilation**. It is not a Spring bean running in the ApplicationContext when the application starts.

```text
Compile
  |
  +-- javac reads classes with @ConfigurationProperties
  +-- Annotation processor analyzes metadata
  |
  v
META-INF/spring-configuration-metadata.json
```

A project can **run normally at runtime without the processor**, though the IDE may not recognize metadata for custom properties. A library can also carry good metadata while lacking auto-configuration or bean registration at runtime, in which case the IDE suggests keys that the application may not actually use.

## 7. Example of `@ConfigurationProperties` with a JavaBean

Let us build the `acme.mail` group for illustration.

Create `src/main/java/example/metadata/MailProperties.java`:

```java
package example.metadata;

import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "acme.mail")
public class MailProperties {

    // Whether outbound mail is enabled.
    private boolean enabled = true;

    // Number of retries after a failed send.
    private int retryCount = 3;

    // Timeout for one outbound mail request.
    private Duration timeout = Duration.ofSeconds(5);

    // Transport name for mail delivery.
    private String channel = "email";

    public boolean isEnabled() {
        return enabled;
    }

    public void setEnabled(boolean enabled) {
        this.enabled = enabled;
    }

    public int getRetryCount() {
        return retryCount;
    }

    public void setRetryCount(int retryCount) {
        this.retryCount = retryCount;
    }

    public Duration getTimeout() {
        return timeout;
    }

    public void setTimeout(Duration timeout) {
        this.timeout = timeout;
    }

    public String getChannel() {
        return channel;
    }

    public void setChannel(String channel) {
        this.channel = channel;
    }
}
```

The example uses single-line comments to keep the code concise. **When you want the processor to extract descriptions automatically, write real Javadoc on the fields**, such as a Javadoc block starting with double asterisks and ending with valid Java syntax. In real projects, descriptions should explain business meaning rather than merely repeating the field name.

Corresponding canonical properties:

```text
acme.mail.enabled
acme.mail.retry-count
acme.mail.timeout
acme.mail.channel
```

YAML data:

```yaml
acme:
  mail:
    enabled: true
    retry-count: 4
    timeout: 3s
    channel: email
```

`retryCount` in Java maps to `retry-count` in configuration thanks to Spring Boot's relaxed binding.

### Registering the Bean at Runtime

```java
package example.metadata;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;

@SpringBootApplication
@ConfigurationPropertiesScan
public class MetadataApplication {

    public static void main(String[] args) {
        SpringApplication.run(MetadataApplication.class, args);
    }
}
```

`@ConfigurationPropertiesScan` registers the `MailProperties` type in the application context. It serves **runtime**; the annotation processor serves **metadata at compile time**.

## 8. Maven Configuration

For a Maven project using Spring Boot 3.3.x and appropriate dependency management:

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter</artifactId>
    </dependency>

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-configuration-processor</artifactId>
        <optional>true</optional>
    </dependency>
</dependencies>
```

`optional=true` indicates that the processor is for compilation and should not automatically become a mandatory transitive dependency for projects consuming the library.

Some builds use `maven-compiler-plugin` with an explicit annotation processor path. In that case, ensure the processor is actually executed by the compiler rather than just appearing as an unprocessed dependency.

Run:

```bash
./mvnw clean compile
```

When compilation succeeds and the annotation processor runs properly, the typical output is:

```text
target/classes/META-INF/spring-configuration-metadata.json
```

Some builds have custom output configurations; check the actual artifact rather than relying strictly on the default path.

### Maven with Multiple Processors

If the project also uses Lombok or MapStruct, you must ensure the annotation processing configuration is compatible. Other processors may affect processing order or the Java sources being processed. If metadata is missing, inspect the compiler configuration and output instead of just adding the dependency multiple times.

## 9. Gradle Configuration

Gradle Groovy DSL:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
}
```

Gradle Kotlin DSL:

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter")
    annotationProcessor("org.springframework.boot:spring-boot-configuration-processor")
}
```

`annotationProcessor` explicitly places the dependency on Java annotation processing. Do not assume that putting the processor in `implementation` is the best configuration for Gradle to run it.

Run:

```bash
./gradlew clean build
```

Metadata can be generated in the `compileJava` output and included in the packaged artifact. The exact path depends on source sets, Gradle version, and build configuration.

### Gradle with Manual Metadata

If you create:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

the processor must pick up this file at compile time. Spring Boot 3.3 guides making the `processResources` task an input of `compileJava`:

```groovy
tasks.named('compileJava') {
    inputs.files(tasks.named('processResources'))
}
```

With Kotlin DSL, the equivalent can be expressed as:

```kotlin
tasks.named<JavaCompile>("compileJava") {
    inputs.files(tasks.named("processResources"))
}
```

If using Kotlin DSL, ensure the `JavaCompile` type is resolved in the script (with an appropriate import if needed). This configuration relates to **when the processor sees the additional file**, and does not alter runtime configuration precedence.

## 10. Generated Files vs. Developer-Managed Files

Distinguish between:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

which is a **source file** that you can create and edit.

Whereas:

```text
target/classes/META-INF/spring-configuration-metadata.json
```

or the corresponding file in Gradle's output is a **generated file** produced by the annotation processor.

An example directory tree:

```text
my-service/
├── pom.xml
├── src/main/java/example/metadata/
│   ├── MetadataApplication.java
│   └── MailProperties.java
└── src/main/resources/
    ├── application.yaml
    └── META-INF/
        └── additional-spring-configuration-metadata.json

After build:
target/classes/
├── application.yaml
└── META-INF/
    ├── additional-spring-configuration-metadata.json
    └── spring-configuration-metadata.json
```

Do not edit the generated file in `target/classes` directly and expect the changes to persist: a `clean` and rebuild will wipe out those edits.

To adjust metadata, modify the **Java source, Javadoc, annotations, or additional file** and recompile.

## 11. Javadoc Makes Tooltips More Useful

A property with only the name `timeout` is often not informative enough for someone configuring it.

A useful description:

> Maximum time allowed for one outbound mail request.

It explains what is being measured, instead of just saying "timeout".

In Java source, you can place Javadoc on the field; for example, the comments below illustrate the idea for Javadoc text:

```java
// Field Javadoc in real source:
// Maximum time allowed for one outbound mail request.
// The value is a Duration, for example 5s or 250ms.
private Duration timeout = Duration.ofSeconds(5);
```

For the annotation processor to extract it into metadata, use a **valid Javadoc block** in a real project, not just `//` comments like the illustration above.

Descriptions should:

- Be concise, have a clear subject, and explain what the value controls.
- State the unit when important.
- State the scope of application, for example per request or per batch.
- Clarify relationships with profiles or feature toggles.
- Avoid pointlessly repeating the property name.
- Not contain secrets or sensitive internal information.

Without a description, the IDE can still suggest key names, but the self-discovery experience via tooltips is limited.

## 12. Records and Constructor Binding

With Java 17, the configuration model can be a record:

```java
package example.metadata;

import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;

@ConfigurationProperties(prefix = "acme.client")
public record ClientProperties(
        String endpoint,
        @DefaultValue("5s") Duration timeout,
        @DefaultValue("3") int retryCount
) {
}
```

Corresponding properties:

```text
acme.client.endpoint
acme.client.timeout
acme.client.retry-count
```

Spring Boot 3.3 can use constructor binding for a record with an appropriate canonical constructor. The metadata processor describes property types based on supported declarations.

`@DefaultValue` on a record component is an explicit source of default information for the Binder. However, **default metadata is not the mechanism that provides runtime values**. Runtime defaults are determined by the Binder, code, and configuration sources; metadata describes them for tooling.

Do not assume the processor can evaluate arbitrary default computation logic, such as:

```java
private Duration timeout = createTimeoutFromEnvironment();
```

The annotation processor analyzes source at compile time; it does not boot the entire application and cannot know dynamically computed values.

## 13. Nested Configuration Properties

Consider the configuration:

```yaml
acme:
  client:
    endpoint: https://api.example.test
    security:
      enabled: true
      mode: strict
```

A JavaBean class with a nested object:

```java
@ConfigurationProperties(prefix = "acme.client")
public class ClientProperties {

    private URI endpoint;
    private final Security security = new Security();

    public URI getEndpoint() {
        return endpoint;
    }

    public void setEndpoint(URI endpoint) {
        this.endpoint = endpoint;
    }

    public Security getSecurity() {
        return security;
    }

    public static class Security {
        private boolean enabled;
        private String mode = "strict";

        public boolean isEnabled() {
            return enabled;
        }

        public void setEnabled(boolean enabled) {
            this.enabled = enabled;
        }

        public String getMode() {
            return mode;
        }

        public void setMode(String mode) {
            this.mode = mode;
        }
    }
}
```

Typical imports:

```java
import java.net.URI;
import org.springframework.boot.context.properties.ConfigurationProperties;
```

The processor can describe the nested prefix `acme.client.security` and the sub-keys `acme.client.security.enabled`, `acme.client.security.mode`.

### `@NestedConfigurationProperty`

When the nested object is a separate class and the processor does not automatically recognize it clearly as a nested property, you can use:

```java
import org.springframework.boot.context.properties.NestedConfigurationProperty;
```

For example:

```java
@ConfigurationProperties(prefix = "acme.client")
public class ClientProperties {

    @NestedConfigurationProperty
    private SecurityOptions security = new SecurityOptions();

    public SecurityOptions getSecurity() {
        return security;
    }

    public void setSecurity(SecurityOptions security) {
        this.security = security;
    }
}
```

Where `SecurityOptions` is a separate type containing child properties.

`@NestedConfigurationProperty` primarily affects **the generated metadata structure**, and is not an annotation that alters runtime binding rules on its own.

### `List` and `Map`

For:

```java
private List<String> recipients;
private Map<String, Integer> quotas;
```

metadata typically describes the **collection property**, rather than generating a fixed property for every index or data key that might be added later.

The IDE can know that `acme.mail.recipients` is a `List<String>`, though it does not necessarily know how many elements will exist at runtime.

## 14. Manual Metadata: When the Annotation Processor Is Not Enough

Place the file at:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

Use it when you need to:

- Describe keys not declared via `@ConfigurationProperties`.
- Add descriptions or defaultValues for cases the processor cannot infer.
- Add a set of suggested values for a `String` property.
- Add providers so the IDE suggests class, bean, resource, or profile names.
- Add deprecation and replacement information.
- Describe a dynamic key or `Map` keys.

For example:

```json
{
  "properties": [
    {
      "name": "acme.mail.channel",
      "type": "java.lang.String",
      "description": "Transport used to send mail notifications.",
      "defaultValue": "email"
    }
  ],
  "hints": [
    {
      "name": "acme.mail.channel",
      "values": [
        {"value": "email", "description": "Send through email."},
        {"value": "smtp-api", "description": "Use the SMTP API gateway."}
      ]
    }
  ]
}
```

If the annotation processor has already discovered the property automatically, additional metadata can override the specified description/default/deprecation details according to Spring Boot's merging rules.

If the additional file declares a property **with no code reading its value**, the IDE may still propose that key; however, this does not mean the application magically gains new functionality. Metadata does not cause runtime to use a key that the code does not support.

## 15. `hints.values` and Enum Types

Suppose notification channels consist only of:

```text
EMAIL
SMS
PUSH
```

A model can use an enum:

```java
public enum Channel {
    EMAIL, SMS, PUSH
}

@ConfigurationProperties(prefix = "acme.notify")
public record NotifyProperties(Channel channel) {}
```

Enums are beneficial because:

- They restrict the state set in Java.
- The Binder can perform enum conversion.
- IDEs can suggest enum constants when metadata and plugins support it.
- There is no need to write manual hints lists just to describe the exact enum values.

If an organization allows external plugins to add dynamic channel names, `String` plus hints may be more appropriate:

```json
{
  "hints": [
    {
      "name": "acme.notify.channel",
      "values": [
        {"value": "email"},
        {"value": "sms"},
        {"value": "push"}
      ]
    }
  ]
}
```

**HINTS ARE SUGGESTIONS** — not a runtime constraint. For a `String` property, another value can still bind successfully unless the application has separate validation.

### The `"any"` Provider

When you want the IDE to suggest common values while still allowing other inputs:

```json
{
  "hints": [
    {
      "name": "acme.notify.channel",
      "values": [
        {"value": "email"},
        {"value": "sms"}
      ],
      "providers": [
        {"name": "any"}
      ]
    }
  ]
}
```

`any` is an official provider allowing values outside the suggested list. It does not change runtime validation.

## 16. Context-Aware Value Providers

In addition to `values`, Spring Boot metadata allows using `providers`.

| Provider | Suggestion direction |
| --- | --- |
| `any` | Not restricted to the listed values |
| `class-reference` | Class names on the classpath, optionally filtered by interface/base type |
| `handle-as` | Treat the input as another Java type |
| `logger-name` | Logger names and logger groups |
| `spring-bean-reference` | Spring bean names |
| `spring-profile-name` | Spring profile names |

Example for suggesting classes:

```json
{
  "hints": [
    {
      "name": "acme.worker.strategy-class",
      "providers": [
        {
          "name": "class-reference",
          "parameters": {
            "target": "example.worker.WorkStrategy"
          }
        }
      ]
    }
  ]
}
```

If supported by the IDE, it can find classes compatible with `WorkStrategy` in the project.

### `handle-as`

A property with Java type `String` whose semantics is a resource path:

```properties
acme.notify.template=classpath:/mail/welcome.txt
```

Metadata:

```json
{
  "hints": [
    {
      "name": "acme.notify.template",
      "providers": [
        {
          "name": "handle-as",
          "parameters": {
            "target": "org.springframework.core.io.Resource"
          }
        }
      ]
    }
  ]
}
```

The IDE can provide assistance as if the property were a `Resource`. This **does not automatically change the real Java field from `String` to `Resource`**.

Provider behavior also depends on IDE support. Do not conclude the JSON is wrong just because a plugin does not display `spring-bean-reference` suggestions.

## 17. Hints for Map Keys and Values

Suppose the configuration is:

```yaml
acme:
  labels:
    team: order
    environment: staging
```

Java:

```java
@ConfigurationProperties(prefix = "acme")
public record AcmeProperties(Map<String, String> labels) {}
```

For `Map`, metadata allows using two special suffixes:

```json
{
  "hints": [
    {
      "name": "acme.labels.keys",
      "values": [
        {"value": "team"},
        {"value": "environment"},
        {"value": "cost-center"}
      ]
    },
    {
      "name": "acme.labels.values",
      "values": [
        {"value": "internal"},
        {"value": "public"}
      ],
      "providers": [
        {"name": "any"}
      ]
    }
  ]
}
```

`.keys` and `.values` refer to Map components, **not two separate runtime properties** that the code must bind.

A `Map<String, String>` can contain many unpredictable entries. Metadata does not automatically scan runtime data to list all keys existing across every environment.

## 18. Deprecated Properties and Migration Hints

An application renames:

```text
acme.notify.sender-name
```

to:

```text
acme.notify.from-name
```

Metadata can provide deprecation information:

```json
{
  "name": "acme.notify.sender-name",
  "type": "java.lang.String",
  "deprecation": {
    "level": "warning",
    "reason": "Use the clearer from-name property.",
    "replacement": "acme.notify.from-name",
    "since": "2.1"
  }
}
```

Fields:

- `level`: `warning` or `error`.
- `reason`: why it is no longer recommended.
- `replacement`: key to migrate to.
- `since`: version where deprecation started.

`warning` is typically used when the old key is still processed but should be replaced. `error` is suitable when the key is no longer managed according to the metadata description.

### `@DeprecatedConfigurationProperty`

Spring Boot 3.3 includes:

```java
import org.springframework.boot.context.properties.DeprecatedConfigurationProperty;
```

On a deprecated JavaBean getter:

```java
@Deprecated
@DeprecatedConfigurationProperty(
        reason = "Use acme.notify.from-name instead.",
        replacement = "acme.notify.from-name"
)
public String getSenderName() {
    return fromName;
}
```

The annotation helps the processor generate deprecation metadata. It **does not automatically create a runtime alias** or convert an old configuration value to the new one. The code still has to decide whether to support the old key and the precedence rule when both appear.

When the old property has been removed from code, you can keep a deprecated entry with `"level": "error"` in manual metadata so the IDE continues warning users that the key is no longer valid.

## 19. `defaultValue` Is Not a Runtime Default

A metadata property having:

```json
{
  "name": "acme.notify.timeout",
  "type": "java.time.Duration",
  "defaultValue": "5s"
}
```

does not mean Spring Boot will automatically supply `5s` just because the JSON file has that field.

Runtime defaults can come from:

- A JavaBean field initializer.
- `@DefaultValue` in constructor binding.
- Shared configuration in a file.
- Another PropertySource.
- Explicitly designed application logic.

In metadata, `defaultValue` is **descriptive data for tooling**. If this description contradicts runtime behavior, the IDE may mislead users.

An annotation processor also cannot infer dynamically computed defaults:

```java
private Duration timeout = determineTimeoutAtRuntime();
```

It does not invoke this method during compilation to find the real value.

### Metadata and `@DefaultValue`

Record:

```java
@ConfigurationProperties(prefix = "acme.retry")
public record RetryProperties(
        @DefaultValue("3") int attempts,
        @DefaultValue("250ms") Duration pause
) {}
```

`@DefaultValue` is the way to express a default for Binder constructor binding. The processor can use this information when describing properties, though you should distinguish the two roles: one creates data during binding, while the other describes it for tooling.

## 20. Metadata Does Not Replace Bean Validation

Having metadata for:

```text
acme.notify.retry-count: Integer
```

does not prove the following value is valid:

```properties
acme.notify.retry-count=-100
```

`-100` is still an integer. If the business logic does not allow negative retries, the model can use:

```java
@Min(0)
private int retryCount;
```

and declare `@Validated` on the configuration class, along with an appropriate Jakarta Bean Validation implementation.

Similarly:

```properties
acme.notify.timeout=-5s
```

can convert to a negative `Duration`. Validation is needed if negative timeouts are disallowed.

Distinction:

| Mechanism | Role |
| --- | --- |
| Metadata | Information for IDEs and tooling |
| Binder | Maps names and converts data into Java types |
| Bean Validation | Checks declared constraints |
| Business logic | Checks relationships, policies, and operational conditions |

The IDE can warn early, but **does not replace runtime checks** and does not guarantee every value entered by a user is valid.

## 21. Metadata for Properties Used Only via `@Value`

For example:

```java
@Service
public class GreetingService {

    private final String text;

    public GreetingService(
            @Value("${acme.greeting.text:Hello}") String text
    ) {
        this.text = text;
    }
}
```

Do not assume `spring-boot-configuration-processor` will automatically generate a complete metadata model for every `@Value` in the application.

If a property has no `@ConfigurationProperties`, it can be described manually:

```json
{
  "properties": [
    {
      "name": "acme.greeting.text",
      "type": "java.lang.String",
      "description": "Greeting shown on the landing screen."
    }
  ]
}
```

If multiple properties share the same prefix, it is usually better to group them into a `@ConfigurationProperties` class rather than maintaining scattered `@Value` annotations and separate JSON entries.

When using `@Value`, Spring Boot recommends writing placeholders in canonical kebab-case to take advantage of existing relaxed lookup support:

```java
@Value("${acme.notify.retry-count:3}")
```

rather than using arbitrary camelCase variants.

## 22. Complete Practice with Maven

### Step 1 — Prepare Dependencies

Create a Spring Boot 3.3.x, Java 17 project with `spring-boot-starter`, and add the processor:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>
```

The project needs appropriate dependency management/parent to align versions.

### Step 2 — Create the Model

`src/main/java/example/metadata/MailProperties.java` as in the JavaBean example in section 7, with prefix `acme.mail`.

### Step 3 — Create the Application

`MetadataApplication.java` with:

```java
@SpringBootApplication
@ConfigurationPropertiesScan
public class MetadataApplication {

    public static void main(String[] args) {
        SpringApplication.run(MetadataApplication.class, args);
    }
}
```

### Step 4 — Create `application.properties`

```properties
spring.application.name=metadata-demo

acme.mail.enabled=true
acme.mail.retry-count=2
acme.mail.timeout=3s
acme.mail.channel=email
```

### Step 5 — Create Hints

At:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

content:

```json
{
  "hints": [
    {
      "name": "acme.mail.channel",
      "values": [
        {
          "value": "email",
          "description": "Use email delivery."
        },
        {
          "value": "smtp-api",
          "description": "Use the configured SMTP API gateway."
        }
      ]
    }
  ]
}
```

### Step 6 — Build

```bash
./mvnw clean compile
```

### Step 7 — Inspect Generated Metadata

Open:

```text
target/classes/META-INF/spring-configuration-metadata.json
```

Some entries that may appear:

```text
group acme.mail
property acme.mail.enabled
property acme.mail.retry-count
property acme.mail.timeout
property acme.mail.channel
hint acme.mail.channel
```

The actual JSON organization may differ in ordering and optional fields.

### Step 8 — Try in the IDE

Open `application.properties` and type:

```text
acme.mail.
```

If the IDE has Spring Boot metadata support and has indexed the project, it can suggest the properties of the group above. When typing `channel`, it can suggest `email` and `smtp-api`.

Open `application.yaml` and type:

```yaml
acme:
  mail:
```

The IDE can suggest child names following YAML structure. The same metadata serves both YAML and `.properties`, so there is no need to create two separate metadata files.

### Step 9 — Start the Application

```bash
./mvnw spring-boot:run
```

The configuration bean is created by the runtime `@ConfigurationPropertiesScan` and Binder mechanisms. Metadata assists the editor, and is not what decides configuration values.

## 23. Inspecting the Output JAR

When publishing a library or starter, metadata should be inside the JAR artifact so that consuming applications' IDEs can also use it.

Using the JDK tool:

```bash
jar tf target/actual-jar-name.jar
```

Look for `spring-configuration-metadata.json`.

A library JAR may store directly:

```text
META-INF/spring-configuration-metadata.json
```

A Spring Boot executable JAR may place application resources in a structure like:

```text
BOOT-INF/classes/META-INF/spring-configuration-metadata.json
```

The location depends on the packaging format. Inspect the actual artifact rather than assuming every Spring JAR has the same internal archive path.

If you publish a starter, inspect the library JAR that consuming projects will depend on, not just the `target/classes` output on your development machine.

## 24. When the IDE Does Not Suggest Properties: Separating Three Layers

### Layer 1 — Annotation Processing

Questions:

- Is the processor dependency present?
- Is Maven/Gradle running annotation processing?
- Does the model have `@ConfigurationProperties`?
- Is there any compiler config causing the processor to be skipped?
- Does the build output contain the metadata file?

If the file does not exist yet, this is a **generation** issue.

### Layer 2 — IDE / Project Index

If the metadata file exists:

- Has the IDE opened the right module and imported dependencies?
- Is the Spring Boot plugin/extension installed and enabled?
- Has the project been reloaded after building?
- Is the IDE using the latest output/annotation processing?
- Does the IDE support `hints.values` or that specific provider?

If only one editor does not show suggestions, do not conclude that the runtime binder is broken.

### Layer 3 — Runtime Configuration

If the IDE suggests the key, yet the bean gets unexpected values:

- Which profile is active?
- Are there external files outside the JAR or `spring.config.import`?
- Are environment variables or CLI arguments overriding it?
- Is there a typo in the actual property?
- Is the `@ConfigurationProperties` bean registered?
- Can the type be converted?
- Did validation reject it?

Do not fix a runtime error by adding a `hint` when the root cause is a configuration source or binding issue.

## 25. Common Issues Table

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| No generated metadata file | Processor did not run | Configure the processor in Maven/Gradle |
| Processor present but missing new property | Class not discovered or structure not analyzed | Check `@ConfigurationProperties`, accessors, source |
| Hints do not appear | Additional file in the wrong location | Check `src/main/resources/META-INF/` |
| Gradle does not merge additional metadata | Processor ran before resources were ready | Configure task input/`processResources` as guided |
| Empty description | Missing Javadoc recognized by processor | Write Javadoc or supplement manually |
| `defaultValue` mismatch | Runtime value computed dynamically or from another source | Do not use metadata as runtime proof |
| Nested JavaBean not described | Nested type not recognized by processor | Check `@NestedConfigurationProperty` |
| IDE does not suggest even though JSON exists | Plugin lacks support or not indexed yet | Reload project, check extension |
| Wrongly suggests removed keys | Stale metadata in cache or old dependency | Rebuild/reload and inspect artifact |
| Values outside hints still bind | Hints are not validators | Use enum/Bean Validation |
| Deprecated key shows no warning | Metadata lacks `deprecation` or IDE unsupported | Add migration information |
| `@Value` property has no metadata | Processor primarily serves typed config properties | Use manual metadata or a `@ConfigurationProperties` model |
| Runtime works but IDE reports unknown | Insufficient metadata; binding is more flexible than tooling | Check metadata file and source |
| IDE suggests but app ignores | Key exists in manual metadata, not read by code | Check runtime consumer |
| Edits in `target` disappear | Generated file overwritten by build | Edit source or additional metadata |
| Need Map key suggestions | Metadata does not know all dynamic keys | Use `.keys` hint |
| Duplicate metadata across modules | Multiple modules share a prefix | Check ownership and dependency versions |

## 26. Metadata in Shared Libraries

For example, a project writing a starter:

```text
acme-notification-spring-boot-starter
```

It exposes the group:

```java
@ConfigurationProperties(prefix = "acme.notifications")
public class NotificationsProperties {
    // ...
}
```

If the starter JAR contains metadata, consuming applications can get `acme.notifications.*` suggestions in the IDE without opening the library's source code.

Flow:

```text
Library source code
  |
  +-- @ConfigurationProperties
  +-- Javadoc
  +-- Additional hints if needed
  |
  v
Build + annotation processor
  |
  v
JAR with metadata
  |
  v
Application depends on the JAR
  |
  v
IDE reads dependency metadata
  |
  v
Code completion for acme.notifications.*
```

However, **metadata does not replace auto-configuration**: the library must still register beans, import necessary components, apply appropriate activation conditions if needed, and use proper Spring Boot runtime mechanisms.

Metadata is part of the user experience **for the configuration API**, not the entire functionality of the library.

## 27. Deprecated Metadata Does Not Automatically Migrate

Suppose the old API used:

```properties
acme.notify.sender-name=Service
```

The new API uses:

```properties
acme.notify.from-name=Service
```

Metadata can inform:

```json
{
  "name": "acme.notify.sender-name",
  "deprecation": {
    "level": "warning",
    "replacement": "acme.notify.from-name"
  }
}
```

However, having `replacement` in JSON does not mean Spring Boot Binder will automatically synchronize the two keys.

If the library wants to keep supporting the old key, code must retain corresponding handling. If it should prioritize the new key when both are present, explicit rules are also needed in runtime code or configuration.

When genuinely removing the old key, metadata can keep a manual `"error"` warning to assist editors, but it **does not resurrect removed runtime behavior**.

## 28. Using Metadata During Spring Boot Upgrades

When upgrading Spring Boot or a starter, metadata may change:

- New keys added.
- Old keys renamed.
- Defaults adjusted.
- Keys becoming deprecated.
- Hints or sourceType changing.

IDEs can leverage metadata from the new dependency version to help users update `application.yaml`. Still, you should read release notes and test the application; metadata is not guaranteed to catch every behavioral change.

With the Spring Boot 3.3 branch, classes and the annotation processor should be version-aligned. Do not arbitrarily mix Spring Boot 3.3 with a processor/auto-configuration from a different branch and expect consistent metadata.

## 29. Self-Check Exercises

### Exercise 1 — Metadata and Final Value

Metadata lists `defaultValue=3` for `acme.mail.retry-count`. The launch command supplies:

```bash
java -jar app.jar --acme.mail.retry-count=9
```

**Question:** Must the value in the bean necessarily be 3?

**Answer:** No. The CLI argument can supply 9 according to runtime precedence order. Metadata only describes defaults.

### Exercise 2 — Processor

Class:

```java
@ConfigurationProperties(prefix = "acme.cache")
public record CacheProperties(int maxSize) {}
```

**Question:** Which component can generate `spring-configuration-metadata.json`?

**Answer:** `spring-boot-configuration-processor` enabled during Java compilation.

### Exercise 3 — Metadata Does Not Replace `@ConfigurationPropertiesScan`

The IDE suggests `acme.cache.max-size`, but Spring Boot has no `CacheProperties` bean.

**Question:** Why?

**Answer:** Metadata does not register runtime beans. Appropriate scanning or enabling of `@ConfigurationProperties` is required.

### Exercise 4 — Is a Hint Validation?

```json
{
  "name": "acme.mail.channel",
  "values": [{"value": "email"}]
}
```

**Question:** Will `channel=sms` definitely be rejected?

**Answer:** No. Hints only assist the editor; runtime depends on types and validation.

### Exercise 5 — `@Value`

A service reads:

```java
@Value("${acme.mail.title}")
String title;
```

**Question:** Will complete metadata be automatically generated for this key?

**Answer:** You should not assume so. You can describe it in additional metadata or use a typed configuration model.

### Exercise 6 — Nested Object

`SecurityOptions` is a standalone class and the IDE does not suggest `acme.client.security.enabled`.

**Question:** Which annotation relates to marking a nested property for the processor?

**Answer:** `@NestedConfigurationProperty`, placed on the appropriate field or declaration.

### Exercise 7 — Gradle

**Question:** Which dependency configuration is for the annotation processor?

**Answer:** `annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'` in Groovy DSL or the equivalent Kotlin DSL syntax.

### Exercise 8 — Additional File

**Question:** Where must the manual source file be placed?

**Answer:**

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

### Exercise 9 — `Map` Keys

You want the IDE to suggest `team`, `environment` for `acme.labels`; which hint name do you use?

**Answer:** `acme.labels.keys`, not a runtime property named `acme.labels.keys`.

### Exercise 10 — IDE Does Not Suggest

The build already has the metadata file, yet the editor lacks key completion.

**Question:** Should you debug Spring Boot runtime first?

**Answer:** No. Check the IDE/plugin, project import, and output indexing. Runtime may be working completely normally.

### Exercise 11 — Deprecated

The old key `acme.mail.sender` is replaced by `acme.mail.from`.

**Question:** What should metadata include?

**Answer:** `deprecation` with `reason`, `replacement`, and optionally `level`, `since`.

### Exercise 12 — defaultValue

You add `"defaultValue": "5s"` to manual metadata for a key that has no default in code or runtime files.

**Question:** Will Spring Boot automatically supply 5s?

**Answer:** No. Metadata does not create runtime defaults.

- [ ] Are prefix names clear and in canonical kebab-case?
- [ ] Do `@ConfigurationProperties` describe supported configuration groups?
- [ ] Are Java types appropriate (`Duration`, enum, `URI`, `DataSize`)?
- [ ] Does Maven/Gradle configure `spring-boot-configuration-processor` properly?
- [ ] Have you built and verified `META-INF/spring-configuration-metadata.json`?
- [ ] Are descriptions for important keys useful to those configuring the app?
- [ ] Do described defaults match runtime behavior?
- [ ] Does `additional-spring-configuration-metadata.json` only supplement what is necessary?
- [ ] Are hints not mistaken for runtime validators?
- [ ] Do deprecated keys have appropriate migration information?
- [ ] Are nested objects and collections expressed reasonably?
- [ ] Does the published JAR carry metadata?
- [ ] Is the IDE or plugin supporting Spring Boot metadata enabled?
- [ ] Are runtime binding/validation tested separately rather than relying on IDE hints?
- [ ] Does metadata avoid containing sensitive secrets that should not be distributed?

## 31. Summary

A formula:

```text
@ConfigurationProperties
        +
spring-boot-configuration-processor
        |
        v
META-INF/spring-configuration-metadata.json
        |
        +-- groups
        +-- properties
        +-- hints
        |
        v
IDE with Spring Boot support
        |
        +-- key name completion
        +-- quick descriptions
        +-- type/default hints
        +-- suggested values
        +-- deprecation warnings
```

Key takeaways:

1. **Configuration metadata describes the configuration API for tooling**; it is not a runtime values file.
2. **`spring-boot-configuration-processor` generates metadata at compile time** from supported configuration types, especially `@ConfigurationProperties`.
3. The standard file is `META-INF/spring-configuration-metadata.json`.
4. The manual supplement file is typically placed at `src/main/resources/META-INF/additional-spring-configuration-metadata.json`.
5. **`groups`, `properties`, and `hints` have distinct responsibilities**. Hints assist the IDE but do not enforce runtime value sets.
6. Support levels vary by IDE/plugin; having metadata does not guarantee every editor displays identical completion.
7. Metadata **does not replace** the Binder, validation, profiles, source precedence, or startup tests.

When building a Spring Boot application or starter with many custom properties, good metadata makes configuration **discoverable, well-documented, and less error-prone during editing**, while keeping a clear boundary from runtime mechanisms.
