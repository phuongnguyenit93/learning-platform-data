# Preserving Special Map Keys Using Bracket Notation

## 1. The Problem: Property Names Are Not Always the Exact Map Keys You Want Preserved

Spring Boot lets you bind externalized configuration to Java objects via `@ConfigurationProperties`. For fields of type `Map<K, V>`, each entry in a YAML or `.properties` file can become an entry in the Map.

This is straightforward when keys contain only letters and digits:

```yaml
routing:
  handlers:
    orders: orders-handler
    payments: payments-handler
```

Java:

```java
@ConfigurationProperties(prefix = "routing")
public record RoutingProperties(Map<String, String> handlers) {}
```

Once registered and bound, `handlers` contains two keys: `orders` and `payments`.

However, many systems need **Map keys containing special characters**: HTTP routes `/api/v1`, partner names `tenant@east`, paths `/public/**`, environment codes `us.east`, or policy names `rate:premium`. These characters carry meaning; dropping even one character breaks lookups completely.

For example:

```yaml
routing:
  handlers:
    /api/v1: orders-handler
```

A YAML author might expect the Map to keep the key `/api/v1`. However, the Spring Boot binder applies **property name** rules. When a Map key is **not** wrapped in bracket notation `[ ]`, characters other than letters, digits, `-`, or `.` can be stripped during binding.

As a result, a key like `/api/v1` can become `apiv1`, causing the following Java call to return `null`:

```java
properties.handlers().get("/api/v1");
```

To preserve the original key, write:

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
```

After binding, the Map preserves the exact key `/api/v1`.

**Main idea:** Spring Boot's `[key]` notation tells the binder that *the bracketed portion is a Map key that must be preserved verbatim*, instead of letting special characters be normalized as property path segments.

## 2. Three Syntax Layers to Distinguish

When reading a YAML file containing a Map, there are actually three processing layers:

1. **YAML syntax:** colons, indentation, and quotes represent data in the document.
2. **Property names generated by Spring Boot from YAML:** nested structure is flattened into property names for the binder to access.
3. **Map binding rules:** the binder interprets the property path to determine field names and Map keys.

For example:

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
```

The `"[/api/v1]"` part is both a **quoted YAML key** and **Spring Boot's Map-key preservation notation**. Quotes tell the YAML parser to read this as a string; square brackets signal preservation to the Spring Boot binder.

Diagram:

```text
YAML:
  "[/api/v1]": orders-handler
            |
            v
YAML parser reads key string: [/api/v1]
            |
            v
Spring Boot binder recognizes [ ... ]
            |
            v
Original Map key: /api/v1
Map value:        orders-handler
```

Do not mistakenly think *just adding quotes* is enough. If you write:

```yaml
routing:
  handlers:
    "/api/v1": orders-handler
```

the quotes ensure YAML reads `/api/v1` cleanly as a string, yet **do not** enable the binder's `[ ]` notation. The key can still be normalized during binding.

Conversely, if you write `[/api/v1]` without quotes in a YAML key position, the parser may interpret `[ ]` using YAML's own collection syntax. Spring Boot documentation requires **wrapping square-bracketed Map keys in quotes in YAML**.

## 3. The Binder's Map Key Normalization Rule

Spring Boot provides *relaxed binding* so property names like `max-attempts`, `maxAttempts`, or `max_attempts` bind to the right Java member. That is helpful for field names, whereas for Maps there are cases where keys must stay verbatim.

Key rule for Map keys:

> If a Map key is not surrounded by `[ ]`, characters outside alphanumeric characters, hyphens `-`, and dots `.` may be stripped while interpreting property names.

Illustration table for a scalar-valued Map such as `Map<String, String>`:

| Desired Map key | YAML key | Outcome to verify |
| --- | --- | --- |
| `orders` | `orders` | `orders` |
| `shipping-fast` | `shipping-fast` | `shipping-fast` |
| `/api/v1` | `"[/api/v1]"` | `/api/v1` |
| `tenant@east` | `"[tenant@east]"` | `tenant@east` |
| `/public/**` | `"[/public/**]"` | `/public/**` |
| `feature.beta` | `"[feature.beta]"` | `feature.beta` |
| `a_b` | `"[a_b]"` | `a_b` |

For special characters such as `/`, `@`, `*`, and `_`, use brackets to keep names unaltered. Dots `.` have an important exception when values are scalars; a later section on dots explains why using brackets is still worthwhile if you want stable config across Map type changes.

Not all property-name transformations are bugs. For example, mapping `max-attempts` to the Java property `maxAttempts` is **intended** by relaxed binding. By contrast, if a Map key is actually a route `/api/v1`, turning it into `apiv1` is **unintended**.

## 4. Syntax in `application.properties`

In a `.properties` file, key-preserving notation is written directly in the property name:

```properties
routing.handlers[/api/v1]=orders-handler
routing.handlers[tenant@east]=tenant-handler
routing.handlers[/public/**]=static-handler
routing.handlers[feature.beta]=beta-handler
routing.handlers[shipping-fast]=fast-handler
```

In this example:

- `routing` is the `@ConfigurationProperties` class prefix.
- `handlers` is the `Map<String, String>` field name in Java.
- `[... ]` marks the bracketed text as a Map key to preserve verbatim.
- `=` separates the property name and value per properties file syntax.

Crucially, this is **not** list-index syntax. Two constructs can both use square brackets yet mean different things depending on the target Java type:

```properties
workers[0].name=first
routing.handlers[/api/v1]=orders-handler
```

- With `List<Worker> workers`, `[0]` denotes element index 0.
- With `Map<String, String> handlers`, `[/api/v1]` denotes string key `/api/v1`.

The binder inspects the declared Java type to handle each appropriately.

### What Happens Without Brackets?

Compare:

```properties
# Not preserved:
routing.handlers./api/v1=orders-handler

# Preserved:
routing.handlers[/api/v1]=orders-handler
```

In the first line, slashes may be removed from the Map key name; in this example, the scalar key becomes `apiv1`. In the second line, the key stays `/api/v1`.

So when your code later calls:

```java
properties.handlers().containsKey("/api/v1")
```

only the bracketed form expresses the intent to preserve the path name.

In `.properties` files, do not needlessly add escapes or wrap the entire `[key]` in quotes out of YAML habit. `.properties` and YAML follow different parsing rules.

## 5. Syntax in `application.yml`

YAML uses indented hierarchy:

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
    "[tenant@east]": tenant-handler
    "[/public/**]": static-handler
    "[feature.beta]": beta-handler
    "[shipping-fast]": fast-handler
```

Keys in the example use double quotes; single quotes also work under YAML syntax. With square brackets, quotes tell the YAML parser to treat the entire key as one string.

Remember to put **quotes outside the brackets**, not brackets outside an already-quoted string by guesswork:

```yaml
# Clear way to write it:
"[/api/v1]": orders-handler
```

Inside a full YAML file, these keys must sit directly under the Map field, such as `routing.handlers`.

### Why Can't You Just Quote the Original Key?

Two lines look similar yet mean different things:

```yaml
routing:
  handlers:
    "/api/v1": might-change
    "[/api/v2]": preserved
```

In the first line, quotes only satisfy YAML syntax. The binder sees no `[... ]` form. In the second line, the binder recognizes preservation notation and can keep `/api/v2` intact.

Do not mix both forms for the same logical key in the same file, because the normalized key could collide with or overwrite the other or yield unpredictable results. Pick one consistent convention: **every Map key containing special characters uses `"[...]"`**.

## 6. Complete Spring Boot Example with `Map<String, String>`

Create a Spring Boot 3.x project with Java 17 or newer and the basic `spring-boot-starter` dependency. We do not need an HTTP server; the program just prints bound Map keys.

### 6.1. Directory Structure

```text
map-key-lab/
└── src/main/
    ├── java/com/example/mapkey/
    │   ├── MapKeyApplication.java
    │   └── RoutingProperties.java
    └── resources/
        └── application.yml
```

### 6.2. `application.yml` File

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
    "[tenant@east]": east-handler
    "[feature.beta]": beta-handler
    normal: default-handler
```

### 6.3. `@ConfigurationProperties` Class

`RoutingProperties.java`:

```java
package com.example.mapkey;

import java.util.Map;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "routing")
public record RoutingProperties(Map<String, String> handlers) {
}
```

`RoutingProperties` is a record that Spring Boot binds from properties starting with `routing`. The `handlers` field is a Map with `String` keys and `String` values.

With a record using Spring Boot 3 constructor binding, you do not need setters for individual entries. You also do not need `@Component` when registering the record through the dedicated configuration-properties mechanism.

### 6.4. Startup and Inspection Class

`MapKeyApplication.java`:

```java
package com.example.mapkey;

import java.util.Map;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
@EnableConfigurationProperties(RoutingProperties.class)
public class MapKeyApplication {

    public static void main(String[] args) {
        SpringApplication.run(MapKeyApplication.class, args);
    }

    @Bean
    ApplicationRunner showMap(RoutingProperties properties) {
        return args -> {
            System.out.println("=== MAP KEY LAB ===");

            for (Map.Entry<String, String> entry
                    : properties.handlers().entrySet()) {
                System.out.println(
                    "[" + entry.getKey() + "] => " + entry.getValue()
                );
            }

            System.out.println(
                "lookup /api/v1 = "
                + properties.handlers().get("/api/v1")
            );

            System.out.println(
                "lookup tenant@east = "
                + properties.handlers().get("tenant@east")
            );
        };
    }
}
```

`@EnableConfigurationProperties(RoutingProperties.class)` registers the configuration bean so the binder builds the Map. `ApplicationRunner` simply reads the constructed bean with no network calls or operational side effects.

After packaging with Maven/Gradle as appropriate, run the executable JAR. In the command below, `app.jar` is an illustrative filename:

```bash
java -jar app.jar
```

Iterated Map entries **should not be relied on to appear in any particular display order**, yet the two lookups produce expected results:

```text
lookup /api/v1 = orders-handler
lookup tenant@east = east-handler
```

In addition, the Map has keys `feature.beta` and `normal`. The goal of this example is to confirm the **original key strings** after binding, not print order or real HTTP routing configuration.

## 7. Experiment A: Remove Square Brackets and Compare

Change YAML to:

```yaml
routing:
  handlers:
    "/api/v1": orders-handler
    "tenant@east": east-handler
    "feature.beta": beta-handler
    normal: default-handler
```

Leave Java unchanged. Repackage and rerun the application.

With `Map<String, String>`, characters `/` and `@` fall outside the set preserved without `[ ]`, so their key names can become:

```text
/api/v1     -> apiv1
tenant@east -> tenanteast
```

The result of:

```java
properties.handlers().get("/api/v1");
properties.handlers().get("tenant@east");
```

can be `null` even though the Map still holds the entries under their **normalized** names. This bug easily tricks readers into thinking "Spring didn't load YAML", when YAML was actually loaded but the **Map key names changed unexpectedly**.

The `feature.beta` key behaves differently: a dot is treated specially depending on value type. For a scalar Map in this experiment, a dotted key can still be preserved even without brackets. That exception is explained in the next section.

### Experiment B: Keep Square Brackets

Switch back to:

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
    "[tenant@east]": east-handler
    "[feature.beta]": beta-handler
    normal: default-handler
```

Expected:

```text
handlers.containsKey("/api/v1")     == true
handlers.containsKey("tenant@east") == true
handlers.containsKey("feature.beta")== true
handlers.containsKey("normal")      == true
```

All four keys are retained exactly as intended. Square brackets are not kept as part of the key string in Java; the binder treats them as preservation syntax.

## 8. Important Exception: Dots in Maps with Scalar Values

Not every `.` requires square brackets. In Spring Boot, how dots behave in Map keys depends on the **Map's value type**.

With a scalar-valued Map such as `Map<String, String>`:

```properties
labels.names.a.b=hello
```

If Java declares:

```java
@ConfigurationProperties(prefix = "labels")
public record LabelProperties(Map<String, String> names) {}
```

the binder can keep `a.b` as **a single key** and bind:

```text
names = { "a.b" : "hello" }
```

Reason: when the target value is a simple `String`, the binder can treat the remainder of the property name as the Map key, including dots.

Scalar value types noted in Spring Boot docs include enums and types in `java.lang` (excluding `Object`). As soon as the value is a complex object or `Object`, dot interpretation can change.

Therefore, for `Map<String,String>`, both forms below can sometimes preserve key `a.b`:

```properties
labels.names.a.b=hello
labels.names[a.b]=hello
```

Do not declare both lines for the same key simultaneously in a real application. They simply demonstrate two ways toward the same goal. If you want exact key preservation across future Map type changes, writing `[a.b]` is the clearer choice.

## 9. `Map<String, Object>`: Dots Can Become Nested Structure

Consider the property:

```properties
feature.flags.a.b=enabled
```

If Java declares:

```java
@ConfigurationProperties(prefix = "feature")
public record FeatureProperties(
        Map<String, Object> flags
) {}
```

the path `a.b` can be interpreted as **two levels**: key `a` holding an object/map with key `b`. The equivalent result is:

```text
flags = {
    "a": {
        "b": "enabled"
    }
}
```

In that case:

```java
properties.flags().get("a.b")
```

is not the right lookup because at the top level of the Map, the key is `a` instead of `a.b`.

To keep `a.b` as **one single key**, use bracket notation:

```properties
feature.flags[a.b]=enabled
```

Or YAML:

```yaml
feature:
  flags:
    "[a.b]": enabled
```

Expected result when binding into `Map<String, Object>`:

```text
flags = { "a.b" : "enabled" }
```

Now:

```java
properties.flags().get("a.b")
```

can return `"enabled"`.

Distinction to remember:

| Declaration | Target type | Effect of the dot |
| --- | --- | --- |
| `feature.flags.a.b=enabled` | `Map<String, String>` | Key `a.b` preserved because value is scalar |
| `feature.flags.a.b=enabled` | `Map<String, Object>` | Usually becomes nested structure `a → b` |
| `feature.flags[a.b]=enabled` | `Map<String, Object>` | Literal key `a.b` preserved |
| YAML `"[a.b]": enabled` | `Map<String, Object>` | Literal key `a.b` preserved |

If the value is a nested Java class such as `RuleProperties`, the path after the Map key continues to address fields of that object. Thus, you must distinguish **dots inside the key name** from **dots traversing nested properties**.

## 10. `Map<String, Rule>`: Separating Key Name from Field Path

Suppose each tenant has its own rule:

```java
public record Rule(
        boolean enabled,
        int limit
) {}

@ConfigurationProperties(prefix = "tenants")
public record TenantProperties(
        Map<String, Rule> rules
) {}
```

We want to preserve a literal tenant name `team.east`. YAML:

```yaml
tenants:
  rules:
    "[team.east]":
      enabled: true
      limit: 20
    "[team@west]":
      enabled: false
      limit: 10
```

The binder can create two entries:

```text
rules["team.east"] = Rule(true, 20)
rules["team@west"] = Rule(false, 10)
```

Structurally equivalent `.properties` syntax:

```properties
tenants.rules[team.east].enabled=true
tenants.rules[team.east].limit=20
tenants.rules[team@west].enabled=false
tenants.rules[team@west].limit=10
```

Here:

- `[team.east]` preserves the literal Map key name.
- `.enabled` and `.limit` sit **outside the brackets**, so they form the path to fields of `Rule`.

If you write:

```properties
tenants.rules.team.east.enabled=true
```

without brackets, the binder may interpret `team` as the key or another path segment instead of literal key `team.east`. When Map values are complex objects, marking key boundaries clearly is even more critical.

### Why Not Put the Whole Path Inside Brackets?

Compare:

```properties
tenants.rules[team.east].enabled=true
tenants.rules[team.east.enabled]=true
```

The first line sets key `team.east`, then accesses field `enabled` of `Rule`. The second puts the whole string `team.east.enabled` into the key, providing no field path as in the first line. For `Map<String, Rule>`, these are not equivalent structures.

Put brackets strictly **around the portion meant to be a Map key**, not around all property names.

## 11. When Special Characters Appear in Route Names

An intuitive use case is a route configuration table:

```yaml
gateway:
  route-to-service:
    "[/api/v1/orders]": orders-service
    "[/api/v1/payments]": payments-service
    "[/assets/**]": static-service
    "[/users/{id}]": user-service
```

If Java uses:

```java
@ConfigurationProperties(prefix = "gateway")
public record GatewayProperties(
        Map<String, String> routeToService
) {}
```

the keys can be preserved verbatim as:

```text
/api/v1/orders
/api/v1/payments
/assets/**
/users/{id}
```

Characters `/`, `*`, `{`, and `}` are meaningful parts of the key string and must be preserved.

**Important:** binding these strings **does not automatically register HTTP routes**. This is purely data inside a Map. The application still needs a component that reads the Map, validates rules, and configures an appropriate router/gateway. The Spring Boot binder does not know whether strings represent URL patterns, regexes, partner codes, or feature names.

Similarly, a key like `/assets/**` may need separate validation to ensure the pattern is valid for the router in use. Brackets only preserve characters; they do not validate pattern syntax.

### A Hard-to-Spot Bug: Two Keys Colliding After Normalization

Suppose you accidentally declare:

```yaml
gateway:
  route-to-service:
    "/api/v1": old-service
    "apiv1": new-service
```

When `/` is stripped from the first key, both can become `apiv1` during binding. Within a single configuration source like this, overriding or subtle ordering behavior not obvious from the YAML text can occur. This is a dangerous configuration bug because the routing map stops distinguishing two routes.

If you intend two separate keys, write:

```yaml
gateway:
  route-to-service:
    "[/api/v1]": old-service
    "apiv1": new-service
```

Then the literal keys differ and both can coexist.

## 12. Interaction with Relaxed Binding

**Relaxed binding** matches property name variations to Java field names. For instance, `route-to-service` in YAML binds to field `routeToService`.

However, do not assume altering Map key names is equally desirable:

```text
gateway.route-to-service
            |
            +-- Java field: routeToService
            |   (relaxed binding helps)
            |
            +-- key in Map: /api/v1
                (must be preserved verbatim)
```

Two distinct roles:

- Field name `route-to-service` can be normalized by the binder to match `routeToService`.
- Key data `/api/v1` must not be altered into another name because business code looks up entries using that exact key.

A good convention is to **use canonical configuration field names while preserving special data keys**.

For example:

```yaml
tenant-routing:
  destination-map:
    "[tenant@north]": https://north.example.invalid
    "[tenant@west]": https://west.example.invalid
```

Class:

```java
@ConfigurationProperties(prefix = "tenant-routing")
public record TenantRoutingProperties(
        Map<String, String> destinationMap
) {}
```

- Prefix `tenant-routing` names the configuration group.
- Field `destination-map` matches `destinationMap`.
- Keys `tenant@north` and `tenant@west` remain intact because they are wrapped in brackets.

Never apply the same normalization mental model to every layer and guess the result.

## 13. A Common YAML Mistake: Confusing Bracketed Keys with Lists

In YAML, `[ ]` has special syntax for flow sequences. That causes unquoted keys to parse differently from what you expect.

Do not write:

```yaml
routing:
  handlers:
    [/api/v1]: orders-handler
```

and expect the parser to always treat `[/api/v1]` as a literal string. Per Spring Boot guidance, when using bracket notation in YAML, **quote the entire bracketed string**:

```yaml
routing:
  handlers:
    "[/api/v1]": orders-handler
```

In addition, `:`, `#`, `*`, `?`, and other special characters have syntactic meaning in YAML in certain contexts. Map key preservation syntax and quotes clarify intent, yet you still must write valid YAML with correct indentation and field structure.

Example key containing `#`:

```yaml
routing:
  handlers:
    "[policy#blue]": blue-handler
```

Here `#` is part of the Map key name, not the start of a YAML comment, because it sits inside a quoted string.

### Single Quotes vs. Double Quotes

Both are generally read by YAML as strings:

```yaml
"[/v1/orders]": orders-handler
'[/v1/orders]': orders-handler
```

Pick one consistent style. For keys containing complex escapes such as backslashes, keep in mind that escape rules differ between YAML's two quote styles; avoid switching quote styles without checking the resulting string.

## 14. Map Bracket Notation Does Not Change the Value Type

Square brackets only apply to the **key**. They do not turn every value into a `String` or disrupt type conversion.

For example:

```yaml
limits:
  per-path:
    "[/api/v1/orders]": 50
    "[/api/v1/payments]": 20
```

Class:

```java
import java.util.Map;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "limits")
public record LimitProperties(
        Map<String, Integer> perPath
) {}
```

After binding, code can read:

```java
Integer maxOrders = properties.perPath().get("/api/v1/orders");
```

and get `50` as an `Integer`.

Likewise, with `Map<String, Duration>`, values `2s` and `500ms` convert to durations through Spring Boot's binding mechanism. If a value fails to convert to the target type, that is a **value binding/conversion error**, not a problem with brackets on the key.

Therefore, when a Map contains wrong data, ask two independent questions:

1. **Is the key preserved?** Inspect `Map.keySet()` and bracket notation.
2. **Did the value convert to the right type?** Inspect type `V`, converters, and property contents.

A properly preserved key can still be paired with an invalid value.

## 15. `Environment` and Map Binding Are Not the Same Lookup

One way to check configuration is:

```java
String value = environment.getProperty(
        "routing.handlers[/api/v1]");
```

Another way is:

```java
String value = routingProperties.handlers().get("/api/v1");
```

These mechanisms are related, but should not be treated as always equivalent in key lookup and normalization:

- `Environment.getProperty(...)` looks up a property name across `PropertySource`s.
- The `@ConfigurationProperties` Binder walks and interprets property names to assemble objects/Maps matching target types.

What matters in this lesson is **the key after binding into the Map**, not merely whether a key string exists in some configuration source.

When diagnosing, print non-sensitive keys:

```java
System.out.println(properties.handlers().keySet());
```

and test the specific lookup:

```java
System.out.println(
    properties.handlers().containsKey("/api/v1")
);
```

Do not just print values and assume the key is right. Two different key names could point to the same value.

## 16. Impact of Profile Files and Precedence Order

`[key]` notation does not introduce a new configuration precedence tier. It only requests preserving the Map key. When the same key appears in multiple sources, Spring Boot still applies its normal source and binding rules.

Example common file:

```yaml
# application.yml
routing:
  handlers:
    "[/api/v1]": local-handler
    "[/health]": health-handler
```

Profile-specific file:

```yaml
# application-prod.yml
routing:
  handlers:
    "[/api/v1]": prod-handler
```

When running:

```bash
java -jar app.jar --spring.profiles.active=prod
```

with no higher-priority source, the Map can receive:

```text
/api/v1 -> prod-handler
/health -> health-handler
```

The value of entry `/api/v1` is overridden by the profile file, while entry `/health` remains from the common source. With Map binding, entries from multiple sources can be combined by rule, unlike wholesale replacement of a list in some scenarios.

This is helpful when only one route differs between development and production. Still, you must consistently write `"[/api/v1]"` in both files. If one file accidentally writes `"/api/v1"` without brackets, the binder can create **two distinct keys** (`/api/v1` and `apiv1`) instead of overriding the same entry.

That mistake tricks deployers into thinking "the prod file didn't override", when the real reason is **the key got mangled**.

## 17. Overriding via Command-Line Arguments

For a special key, you can pass the property via Spring Boot command-line arguments:

```bash
java -jar app.jar '--routing.handlers[/api/v1]=runtime-handler'
```

Use single quotes in Bash/PowerShell so the shell does not interpret special characters such as square brackets, `*`, or other symbols before Java receives the string.

On Windows `cmd.exe`, double quotes around the argument work:

```bat
java -jar app.jar "--routing.handlers[/api/v1]=runtime-handler"
```

This illustrates passing a special-key property on the command line. If running the JAR behind wrappers, Docker, Kubernetes, or CI/CD pipelines, make sure the string reaching the application still retains the square brackets intact.

Whether configured by file or command line, inspect `properties.handlers().get("/api/v1")` after binding to confirm the effective value.

### Why Aren't Environment Variables Always Used?

Operating systems and shells typically restrict characters allowed in **environment variable names**. A variable name like:

```text
ROUTING_HANDLERS[/api/v1]
```

is not valid in many shells and violates standard environment variable conventions. Spring Boot also applies specific rules when binding environment variables to Maps, including lowercasing Map keys.

Thus, for keys containing `/`, `@`, `*`, or needing exact case preservation, **configuration files with bracket notation** or another source supporting structured property names are easier to control. Do not force an invalid environment variable name and conclude the binder lacks special-key support.

If deployment rules mandate environment variables, consider passing a JSON blob or another platform/framework-supported config mechanism and test how it enters Spring Boot. There is no rule guaranteeing that arbitrary Map keys can be encoded directly as standard environment variable names.

## 18. Distinguishing Map Keys and Nested Property Names in YAML

An application can mix Maps and nested objects:

```yaml
integrations:
  vendors:
    "[vendor@north]":
      endpoint: https://north.example.invalid
      timeout: 2s
    "[vendor@west]":
      endpoint: https://west.example.invalid
      timeout: 5s
```

Java classes:

```java
import java.net.URI;
import java.time.Duration;
import java.util.Map;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "integrations")
public record IntegrationProperties(
        Map<String, Vendor> vendors
) {
    public record Vendor(
            URI endpoint,
            Duration timeout
    ) {}
}
```

Each element has a distinct role:

```text
integrations             prefix
  |
  +-- vendors            Map<String, Vendor> field
          |
          +-- vendor@north   Map key (must be preserved)
                 |
                 +-- endpoint   field in Vendor
                 +-- timeout    field in Vendor
```

The Spring binder converts `https://north.example.invalid` to `URI`, `2s` to `Duration`, and places the `Vendor` object under key `vendor@north`. The `endpoint` and `timeout` fields need no brackets because they are ordinary Java property names.

When inspecting values:

```java
IntegrationProperties.Vendor vendor =
    properties.vendors().get("vendor@north");

System.out.println(vendor.timeout());
```

If code passes another key name such as `"vendornorth"`, the Map cannot tell it refers to the same vendor. Bracket notation makes the key contract explicit between config data and lookup code.

## 19. Dedicated Binding Tests for Special Keys

You can verify Map keys without booting the whole application by using `ApplicationContextRunner` from Spring Boot Test.

Suppose the record is:

```java
package com.example.mapkey;

import java.util.Map;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "routing")
public record RoutingProperties(Map<String, String> handlers) {}
```

A simple JUnit 5 test:

```java
package com.example.mapkey;

import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.boot.test.context.runner.ApplicationContextRunner;
import org.springframework.context.annotation.Configuration;

class RoutingPropertiesTest {

    private final ApplicationContextRunner runner =
        new ApplicationContextRunner()
            .withUserConfiguration(TestConfig.class);

    @Test
    void preservesSpecialMapKeys() {
        runner.withPropertyValues(
                "routing.handlers[/api/v1]=orders-handler",
                "routing.handlers[tenant@east]=east-handler",
                "routing.handlers[feature.beta]=beta-handler"
        ).run(context -> {
            RoutingProperties props =
                context.getBean(RoutingProperties.class);

            assertThat(props.handlers())
                .containsEntry("/api/v1", "orders-handler")
                .containsEntry("tenant@east", "east-handler")
                .containsEntry("feature.beta", "beta-handler");
        });
    }

    @Configuration(proxyBeanMethods = false)
    @EnableConfigurationProperties(RoutingProperties.class)
    static class TestConfig {
    }
}
```

This test verifies the **binding contract**:

1. Does the binder construct the right bean type?
2. Does the Map contain the verbatim keys?
3. Does each value match its expected key?

This is not testing the router, HTTP requests, or business services. If the test fails, you can focus immediately on property syntax and binding rather than debugging the entire application.

For YAML files, you can use `@SpringBootTest` loading the real `application.yml` or an appropriate test context, then assert `containsKey("/api/v1")`. Dedicated configuration tests catch Map key bugs early in your build pipeline.

## 20. Testing the Dot Exception by Map Type

To see the difference between a scalar Map and an object Map, use two separate setups.

### Case 1: `Map<String, String>`

```properties
demo.labels.a.b=value-one
```

Java:

```java
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        Map<String, String> labels
) {}
```

In this case you can get:

```text
labels["a.b"] = "value-one"
```

### Case 2: `Map<String, Object>`

```properties
demo.options.a.b=value-two
```

Java:

```java
@ConfigurationProperties(prefix = "demo")
public record DemoProperties(
        Map<String, Object> options
) {}
```

Here the binder can interpret it as:

```text
options["a"] = { "b": "value-two" }
```

If you want:

```text
options["a.b"] = "value-two"
```

then declare:

```properties
demo.options[a.b]=value-two
```

This is why you **cannot simply memorize "dots are always kept"**. The rule depends on the value type. When keys arrive externally and must remain exact, square brackets state the key boundaries explicitly.

## 21. Common Mistakes

### 21.1. Adding Quotes Without Brackets

```yaml
routes:
  names:
    "/v1/orders": orders
```

YAML reads the string key accurately, yet the Spring Boot binder can still strip `/`. Fix:

```yaml
routes:
  names:
    "[/v1/orders]": orders
```

### 21.2. Adding Brackets Without Quotes in YAML

```yaml
routes:
  names:
    [/v1/orders]: orders
```

Does not follow Spring Boot's YAML syntax for bracketed Map keys. Fix to `"[/v1/orders]"` or `'[/v1/orders]'`.

### 21.3. Wrapping the Wrong Part of the Path

```properties
tenants.rules[team.east.enabled]=true
```

If Java expects `Map<String, Rule>` with key `team.east` and field `enabled`, write:

```properties
tenants.rules[team.east].enabled=true
```

### 21.4. Blaming YAML Loading When the Map Looks Wrong

Check `keySet()`. The value may still be present under a normalized key like `apiv1` instead of `/api/v1`.

### 21.5. Treating Dotted Keys as One Universal Rule

With `Map<String, String>`, `a.b` can be kept without `[ ]`. With `Map<String, Object>` or complex values, `a.b` can become a nested path. Check the Java type before explaining the result.

### 21.6. Confusing a Map with a List

`values[0]` with `List` accesses a position; `values[0]` with `Map<String,String>` can be string key `"0"` as interpreted by the binder for the target type. Never deduce syntax from brackets alone; inspect the properties class.

### 21.7. Thinking `[key]` Notation Secures Sensitive Data

This notation does not encrypt keys/values, restrict access, or secure route patterns. For sensitive keys or values, apply proper security controls and never print them to diagnostic logs.

### 21.8. Mixing Up Entry Overriding and Key Renaming

If the common file uses `"[/api/v1]"` while the prod file uses unbracketed `"/api/v1"`, they become two separate identifiers after binding. Use identical notation across all sources when intending to override the same entry.

### 21.9. Using Environment Variable Names with Special Characters as Property Keys

Not all shells allow `/`, `[`, `]`, or `@` in variable names. If exact keys must be preserved, choose a configuration source supporting that syntax instead of assuming environment variable mapping restores every character.

### 21.10. Overusing `Map<String,Object>` for Everything

`Map<String,Object>` is flexible, yet makes dotted keys vs. nested structure hard to read. When data has a stable schema, prefer `Map<String, Rule>` or a typed nested configuration class. When only mapping strings to strings, `Map<String,String>` is a simpler contract.

## 22. When to Use a Map vs. a Fixed Class?

Use a `Map` when the key set is genuinely dynamic data:

- Tenant names added across deployments.
- Extensible sets of route paths.
- Geographic region codes or partner groups not fixed in Java classes.
- Alias lookup tables pointing to endpoints or policies.

Use a class or record with explicit fields when the field set has a fixed schema:

```java
public record RetryPolicy(
        int maxAttempts,
        Duration backoff
) {}
```

Do not replace every field of `RetryPolicy` with `Map<String,Object>` just to avoid declaring types; that throws away type-safe binding benefits and invites runtime bugs.

For "dynamic tenant names, fixed per-tenant policy", a clean choice is usually:

```java
Map<String, RetryPolicy> tenantPolicies
```

Then bracket notation preserves tenant keys verbatim, while the Spring Boot binder binds `RetryPolicy` fields according to a typed schema.

## 23. Step-by-Step Troubleshooting

Suppose code calling:

```java
String handler = props.handlers().get("/api/v1");
```

returns `null`.

**Step 1 — Check the Map type.** Is it truly `Map<String, String>` or a complex Map value? Value type governs how the binder treats dots.

**Step 2 — Print harmless keys.** Inspect `props.handlers().keySet()`. If you see `apiv1`, the issue is key preservation.

**Step 3 — Check key spelling.** Was `"/api/v1"` written as `"[/api/v1]"` in YAML? Are brackets or quotes missing?

**Step 4 — Check prefix and field name.** If Java uses `@ConfigurationProperties(prefix="routing")` and field `handlers`, YAML must sit under `routing.handlers`. Missing entries might stem from a wrong prefix rather than brackets.

**Step 5 — Check active environment sources.** Does `application-prod.yml`, an external config file, or a command-line argument override that entry? Do different files declare the key with matching syntax?

**Step 6 — Check value conversion errors.** If Map values are `Integer`, `Duration`, or a record, do supplied values match expected types and structures?

**Step 7 — Write a minimal binding test.** Use `ApplicationContextRunner` with one property string containing `[key]`. If the minimal test passes while the full app fails, look for overriding sources and other config structures.

**Step 8 — Check Map consumption logic.** If binding succeeds yet routing fails, the bug may lie in router logic, route order, pattern matching, or permissions rather than the binder.

Breaking the problem into steps prevents rewriting half the application over a single `/` stripped from a Map key.

## 25. Summary

Bracket notation is an essential mechanism when binding Spring Boot configuration into a `Map` whose keys contain special characters.

```text
Desired Map key: /api/v1

In .properties:
  routing.handlers[/api/v1]=orders-handler

In YAML:
  routing:
    handlers:
      "[/api/v1]": orders-handler

In Java:
  properties.handlers().get("/api/v1")
```

Core rules:

1. **Use `[key]` to preserve Map key names** containing characters like `/`, `@`, `*`, or others outside the ordinary identifier set.
2. **In YAML, put quotes around the entire `[key]`** so the parser reads the key cleanly.
3. **Quotes alone do not replace square brackets.** `"/api/v1"` and `"[/api/v1]"` do not mean the same thing to the binder.
4. **Dots are an exception worth watching.** With scalar Maps like `Map<String,String>`, `a.b` can be kept without brackets; with `Map<String,Object>` or complex values, it can become a nested path.
5. **Wrap only the Map key portion in brackets.** With `Map<String, Rule>`, write `rules[team.east].enabled` to access a value object's field.
6. **Brackets do not alter source precedence or value validation.** They preserve key names—not type conversion, validation, or security.
7. **Inspect the Map after binding.** Calling `containsKey(...)` and checking `keySet()` in tests catches key mangling early.

Key takeaway: a Map can hold the right values under the wrong keys. When keys represent routes, tenants, partner codes, or policy names, **preserving every character of the key is preserving the configuration contract**.
