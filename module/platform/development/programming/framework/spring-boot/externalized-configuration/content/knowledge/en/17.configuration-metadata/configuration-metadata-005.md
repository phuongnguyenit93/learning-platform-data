# Property Descriptions, Data Types, and Default Values in Spring Boot Configuration Metadata

## 1. Problem: The Application Reads Configuration, but Do Configuration Authors Understand It Correctly?

Suppose a Spring Boot project has a property group controlling a delivery client:

```yaml
delivery:
  endpoint: https://api.example.invalid/v1
  connect-timeout: 2s
  max-attempts: 3
  mode: STANDARD
```

These keys can be bound into a `@ConfigurationProperties` class. However, when opening the YAML file, newcomers to the project will ask:

- Where does `delivery.endpoint` connect to? Is `http://` allowed or must it be `https://`?
- Is `connect-timeout` in seconds, milliseconds, or some default unit?
- Is `max-attempts` the total number of calls or the number of **retries after the first attempt**?
- What values are valid for `mode`?
- If a key is omitted, what default value does the application use?
- Is `delivery.connection-timeout` a valid key name, or just a typo?
- When renaming a key in a new version, how can the IDE warn configuration authors?

Spring Boot has a **Configuration Metadata** mechanism to describe the set of supported configuration keys. In common usage, the `spring-boot-configuration-processor` annotation processor collects information from `@ConfigurationProperties` classes and generates a JSON file on the classpath.

For example, metadata can state that:

```json
{
  "name": "delivery.max-attempts",
  "type": "java.lang.Integer",
  "description": "Maximum number of total delivery attempts.",
  "defaultValue": 3
}
```

IDEs with Spring Boot support can use that information to suggest key names, show descriptions, display value types, and warn when users enter invalid configuration. **Metadata is descriptive data supporting tooling; it is not a prioritized configuration value source or a runtime validator.**

This lesson focuses on three core attributes in metadata:

1. **`description`** — explains the meaning of the property.
2. **`type`** — data type declared for the property.
3. **`defaultValue`** — information about the default value determinable at metadata generation time.

Additionally, we will explore how to generate the file, how to add manual metadata, and how to distinguish metadata from the actual runtime behavior of `@ConfigurationProperties`.

## 2. Where Does Metadata Reside and Who Uses It?

A Spring Boot Configuration Metadata file is generated by convention at:

```text
META-INF/spring-configuration-metadata.json
```

When using Maven or Gradle with the annotation processor configured, the file can appear in the compilation output directory and then be packaged into the JAR alongside the classes.

Diagram:

```text
@ConfigurationProperties classes
         |
         | annotation processor at compile time
         v
META-INF/spring-configuration-metadata.json
         |
         +----> IDE / tooling / automated docs
         |
         +----> May be packaged into JAR
         
At application runtime:
application.yml / ENV / CLI
         |
         v
Spring Environment
         |
         v
Spring Boot Binder
         |
         v
@ConfigurationProperties object
```

These two flows are related but have **different responsibilities**:

- The metadata flow occurs mainly at build time and is read by development tools.
- The binding flow occurs when the application receives actual configuration and constructs Java objects.
- Data in metadata JSON is not directly used by the Spring Boot Binder as a source for deciding application values.
- An IDE suggesting valid values does not guarantee the application has runtime validation for those values.
- An application can still bind keys in YAML without metadata, as long as the configuration properties class is registered and the binder works normally.

Generally, use metadata to **improve the development experience** and reduce key name typos before running the application; to guard startup, add appropriate type conversion, Bean Validation, or business checks.

## 3. Structure of a Metadata File

The `spring-configuration-metadata.json` file is represented as JSON and has three main information groups:

```json
{
  "groups": [],
  "properties": [],
  "hints": []
}
```

### 3.1. `groups` — Configuration Groups

A group typically represents a namespace or configuration object, for example:

```json
{
  "name": "delivery",
  "type": "com.example.delivery.DeliveryProperties",
  "sourceType": "com.example.delivery.DeliveryProperties"
}
```

Groups help tools understand which configuration class `delivery.*` properties belong to. The actual fields present depend on the Spring Boot version, source structure, and how the annotation processor detects classes/beans.

### 3.2. `properties` — Individual Configuration Keys

An entry may contain information such as:

```json
{
  "name": "delivery.connect-timeout",
  "type": "java.time.Duration",
  "description": "Time allowed to establish a network connection.",
  "sourceType": "com.example.delivery.DeliveryProperties",
  "defaultValue": "2s"
}
```

Important fields:

| Field | Meaning | Always present? |
| --- | --- | --- |
| `name` | Canonical property name, usually in kebab-case | Core field of an entry |
| `type` | Java type name of the property | May be absent or formatted differently if uninferable |
| `description` | Text explaining the property | May be absent if source lacks Javadoc/additional metadata |
| `defaultValue` | Default that tools can describe | May be absent if processor cannot infer it |
| `sourceType` | Class declaring or supplying the property | Context-dependent |
| `deprecation` | Info for an outdated property | Present only when declared |

**Do not read an illustrative JSON file as proof that every Spring Boot version generates the exact same fields and formatting.** The actual file is a product of the processor and the source code being built.

### 3.3. `hints` — Value or Input Suggestions

`hints` can help the IDE offer choices for a property, such as:

```json
{
  "name": "delivery.mode",
  "values": [
    {
      "value": "STANDARD",
      "description": "Normal delivery handling."
    },
    {
      "value": "EXPRESS",
      "description": "Prioritize fast delivery."
    }
  ]
}
```

These suggestions do not automatically turn the property into an enum or enforce a runtime restriction. With Java enums, IDEs may already have suggestions from the type; with a `String` accepting a set of conventional values, additional metadata can supply the suggestion list.

## 4. Preparing `spring-boot-configuration-processor`

**Goal:** add the annotation processor to the compilation process without making it a required runtime business dependency.

### 4.1. Maven

For a Spring Boot Maven project using parent/BOM version management, you can declare:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>
```

Some projects configure `maven-compiler-plugin` with `annotationProcessorPaths` or explicit annotation processing policies. In that case, ensure the processor is on the corresponding processor path; merely adding a dependency while the compiler does not run annotation processing will result in no metadata being generated.

With projects using common plugins and wrappers, run:

```bash
./mvnw clean compile
```

On Windows, you can use:

```bat
mvnw.cmd clean compile
```

After building, check the expected path:

```text
target/classes/META-INF/spring-configuration-metadata.json
```

The path above is simply the common Maven output form and may differ if the project reconfigures its build directory.

### 4.2. Gradle Groovy DSL

In `build.gradle`:

```groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
}
```

If Spring Boot tests are needed:

```groovy
dependencies {
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
```

Then:

```bash
./gradlew clean classes
```

On Windows, use `gradlew.bat clean classes`. For Java projects, a common output path is:

```text
build/classes/java/main/META-INF/spring-configuration-metadata.json
```

### 4.3. Gradle Kotlin DSL

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter")
    annotationProcessor(
        "org.springframework.boot:spring-boot-configuration-processor"
    )
}
```

Use `annotationProcessor` rather than putting the processor on the runtime classpath just to generate JSON. For Kotlin code, annotation processing mechanisms may require configuring kapt/KSP or appropriate tooling per build version. Do not assume Java `annotationProcessor` configuration automatically handles all Kotlin classes.

### 4.4. Why Is the Processor a Build-Time Component?

Metadata is extracted from classes and annotations at compile time. There is no need for a runtime bean named `ConfigurationMetadataProcessor` to process YAML when the server runs.

If you delete metadata from the JAR while keeping the compiled classes and binder configuration intact, the application can still start and bind configuration as before; what is affected is mainly the experience of tools reading metadata.

Therefore, when the IDE does not suggest a property, check the build/metadata step first rather than **jumping to conclusions that the runtime binder is broken**.

## 5. First Example: Creating a Well-Described `@ConfigurationProperties` Class

We build a Spring Boot 3.x, Java 17+ project using a delivery client configuration.

Create file:

```text
src/main/java/com/example/delivery/DeliveryProperties.java
```

JavaBean example illustrating how the processor reads field Javadoc:

```java
package com.example.delivery;

import java.net.URI;
import java.time.Duration;

import org.springframework.boot.context.properties.ConfigurationProperties;

/**
 * Settings for the outbound delivery API integration.
 */
@ConfigurationProperties(prefix = "delivery")
public class DeliveryProperties {

    /**
     * Base URI for the delivery API.
     * Configure this for the target deployment environment.
     */
    private URI endpoint;

    /**
     * Maximum time allowed to establish an outbound connection.
     */
    private Duration connectTimeout = Duration.ofSeconds(2);

    /**
     * Total number of attempts including the initial request.
     */
    private int maxAttempts = 3;

    /**
     * Whether the delivery integration is enabled.
     */
    private boolean enabled = false;

    public URI getEndpoint() {
        return endpoint;
    }

    public void setEndpoint(URI endpoint) {
        this.endpoint = endpoint;
    }

    public Duration getConnectTimeout() {
        return connectTimeout;
    }

    public void setConnectTimeout(Duration connectTimeout) {
        this.connectTimeout = connectTimeout;
    }

    public int getMaxAttempts() {
        return maxAttempts;
    }

    public void setMaxAttempts(int maxAttempts) {
        this.maxAttempts = maxAttempts;
    }

    public boolean isEnabled() {
        return enabled;
    }

    public void setEnabled(boolean enabled) {
        this.enabled = enabled;
    }
}
```

The example class has four properties:

| Java field | Canonical key name | Data type | Initializer value |
| --- | --- | --- | --- |
| `endpoint` | `delivery.endpoint` | `URI` | `null` (unset) |
| `connectTimeout` | `delivery.connect-timeout` | `Duration` | 2 seconds |
| `maxAttempts` | `delivery.max-attempts` | `int` | 3 |
| `enabled` | `delivery.enabled` | `boolean` | false |

The `/** ... */` comments are **Javadoc**. This is an important source for the processor to obtain `description` for properties in JavaBean-style classes. Regular comments such as `// max attempts` are not a reliable way to generate the `description` field.

In the example, `getXxx` and `setXxx` form JavaBean accessors for the binder. Spring Boot can use the setters to bind values from external configuration.

## 6. Registering the Bean and Reading Configuration at Runtime

We register `DeliveryProperties` via `@EnableConfigurationProperties`, rather than just writing the annotation and leaving the class unused in source.

```java
package com.example.delivery;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
@EnableConfigurationProperties(DeliveryProperties.class)
public class DeliveryApplication {

    public static void main(String[] args) {
        SpringApplication.run(DeliveryApplication.class, args);
    }

    @Bean
    ApplicationRunner printDeliverySettings(DeliveryProperties properties) {
        return args -> {
            System.out.println("enabled = " + properties.isEnabled());
            System.out.println("endpoint = " + properties.getEndpoint());
            System.out.println(
                "connectTimeout = " + properties.getConnectTimeout());
            System.out.println(
                "maxAttempts = " + properties.getMaxAttempts());
        };
    }
}
```

Example `application.yml`:

```yaml
delivery:
  endpoint: https://api.example.invalid/v1
```

On startup, `enabled`, `connectTimeout`, and `maxAttempts` can still retain the initializer values in the class; `endpoint` receives the URI from YAML.

An illustrative output:

```text
enabled = false
endpoint = https://api.example.invalid/v1
connectTimeout = PT2S
maxAttempts = 3
```

**Core distinction:**

- The Binder creates or updates the `DeliveryProperties` object according to proper registration.
- Java initializer values take effect at runtime because that is the object's initial state.
- Metadata `defaultValue` can describe this state for tools, but it is not the source that produces the runtime default.
- If the environment supplies `--delivery.max-attempts=8`, the bound value is `8` even though metadata describes default `3`.

The `api.example.invalid` URL is strictly for illustration, not a service this program will actually call.

## 7. Descriptions with Javadoc: Writing What Config Authors Actually Need to Know

A good metadata `description` field does not simply repeat the key name.

Do not merely write:

```java
/** Max attempts. */
private int maxAttempts = 3;
```

Because users still do not know what an "attempt" counts as. Instead write:

```java
/**
 * Maximum number of total delivery attempts, including the first request.
 * The value must be greater than zero.
 */
private int maxAttempts = 3;
```

This clarifies two points prone to misunderstanding:

1. This is the **total** number of calls, not the number of extra retries.
2. The value must be positive per the operational contract.

Similarly, for durations:

```java
/**
 * Maximum time allowed to establish an outbound connection.
 * Values such as "500ms" and "2s" are supported.
 */
private Duration connectTimeout = Duration.ofSeconds(2);
```

For endpoints:

```java
/**
 * URI of the delivery API for the active environment.
 * Do not include access tokens in this URI.
 */
private URI endpoint;
```

### Distinguishing Description and Validator

A description stating "must be positive" does not automatically enforce a positive check on a Java `int`. If startup validation is needed, use Bean Validation or an appropriate check mechanism.

Example:

```java
import jakarta.validation.constraints.Min;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "delivery")
public class DeliveryProperties {

    /**
     * Total number of attempts including the initial call.
     */
    @Min(1)
    private int maxAttempts = 3;

    // getters/setters...
}
```

For constraints to be evaluated, the project needs a compatible validation provider, usually via `spring-boot-starter-validation` in Boot applications. Metadata assists the IDE, whereas `@Min(1)` in the validation system is the runtime rule.

An important reason to write sufficiently detailed descriptions is that they typically appear in the IDE right where the user declares the property. This helps developers understand meaning without having to look up the Java class.

## 8. Where Do Data Types in Metadata Come From?

The processor usually determines types through Java declarations.

Example:

```java
private String senderName;
private int maxAttempts;
private boolean enabled;
private Duration connectTimeout;
private URI endpoint;
private List<String> tags;
private Map<String, Integer> limits;
```

In metadata, the `type` field is usually the fully qualified Java type name, such as:

```text
java.lang.String
java.lang.Integer
java.lang.Boolean
java.time.Duration
java.net.URI
java.util.List<java.lang.String>
java.util.Map<java.lang.String,java.lang.Integer>
```

The representation of primitives like `int` may be normalized in metadata to wrapper type `java.lang.Integer`. For generic types, the annotation processor can provide a parameterized type format understood by tools.

**Metadata type is not the same as YAML data types.** In YAML, a value may appear as `2s` or `true`. The Binder is responsible for converting to `Duration`, `Boolean`, or other Java types.

```text
YAML text: connect-timeout: 2s
                  |
                  v
Metadata type: java.time.Duration  (hint for IDE)
                  |
                  v
Spring Boot Binder runtime: Duration.ofSeconds(2)
```

Just because metadata says `Duration` does not mean every duration string format is valid. Conversion capability depends on the binder, conversion service, and library version. For custom types, an appropriate converter may be needed.

### Enums and Type Metadata

Example:

```java
public enum DeliveryMode {
    STANDARD,
    EXPRESS
}
```

A configuration class:

```java
@ConfigurationProperties(prefix = "delivery")
public record DeliveryProperties(
        DeliveryMode mode
) {}
```

The processor can describe `type` using the full name of the enum, helping the IDE suggest the enum constants defined by the project.

Example:

```yaml
delivery:
  mode: EXPRESS
```

The runtime Binder still performs type conversion. If configuration supplies a non-existent name or a value rejected by the converter, the application may fail binding; metadata does not add new enum constants on its own.

## 9. Defaults: Three Distinct Places to Distinguish

The word "default" in Spring Boot configuration is commonly used for **three concepts**:

1. Initializer values in a Java class or values specified via constructor binding.
2. Default values in `application.yml` or a lower-precedence configuration source.
3. The **`defaultValue` field in JSON metadata**, mainly for tooling.

All three values may be identical, yet they are **not the same mechanism**.

### 9.1. Defaults in a JavaBean

```java
@ConfigurationProperties(prefix = "delivery")
public class DeliveryProperties {

    private int maxAttempts = 3;
    private boolean enabled = false;

    // getters/setters...
}
```

When no configuration source overrides these fields, the object can retain the initial values `3` and `false`. The annotation processor can infer certain simple initializers and record them in metadata.

Not every Java expression is fully evaluated by the processor. For example, a default depending on an arbitrary function, runtime variable, or service call should not be expected to appear accurately in JSON metadata automatically.

### 9.2. Defaults in Constructor Binding with `@DefaultValue`

With records or classes using constructor binding, you can declare `@DefaultValue`:

```java
package com.example.delivery;

import java.net.URI;
import java.time.Duration;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;

@ConfigurationProperties(prefix = "delivery")
public record DeliveryProperties(
        URI endpoint,

        @DefaultValue("2s")
        Duration connectTimeout,

        @DefaultValue("3")
        int maxAttempts,

        @DefaultValue("false")
        boolean enabled
) {}
```

Under constructor binding supported by Spring Boot, when a property is absent, the binder can use the value from `@DefaultValue` to instantiate the object. The processor can also use that information to describe defaults in metadata.

With Spring Boot 3 and a record having a single suitable constructor, `@ConstructorBinding` is not needed in this simple example. If using multiple constructors or different bean registration configurations, follow the constructor binding rules for your project's version.

Do not place a Spring bean such as `HttpClient` or `Repository` as a constructor parameter of a `@ConfigurationProperties` record just to inject dependencies. Constructor binding here is **binding configuration data**, not standard service dependency injection.

### 9.3. Defaults in `application.yml`

```yaml
delivery:
  connect-timeout: 2s
  max-attempts: 3
  enabled: false
```

This is a **runtime configuration source**. If no higher-precedence source overrides it, the binder takes these values. If you only change:

```yaml
delivery:
  max-attempts: 5
```

without recompiling the `@ConfigurationProperties` class, the metadata file generated from Java source **does not automatically change to `defaultValue: 5`**. The processor is not tasked with treating every value in every YAML file, profile, or secret store as a compile-time default.

That is why it is important to understand when an IDE shows "default = 3" while the application runs with `5` from YAML or `8` from an environment variable.

### 9.4. Does `defaultValue` in Metadata Have Runtime Effect?

Do not treat the entry:

```json
{
  "name": "delivery.max-attempts",
  "type": "java.lang.Integer",
  "defaultValue": 3
}
```

as an instruction telling the binder to populate `3` into the record. This is **descriptive information**. If the class does not declare a runtime default and real sources provide no value, JSON metadata alone will not cause the property to receive `3`.

To make a default take effect in practice, place it in runtime configuration or express it in the binding class using APIs supported by Spring Boot.

## 10. Defaults for Special Data Types

### 10.1. `Duration`

```java
@DefaultValue("250ms")
Duration retryDelay
```

When no configuration value is present, the binder can convert this default to a `Duration` equivalent to 250 milliseconds.

If you want a 2-second default duration, you can write:

```java
@DefaultValue("2s")
Duration connectTimeout
```

A metadata file may represent `defaultValue` as text such as `"2s"`, though exact output formatting may depend on the version and how the processor processes the source.

When writing descriptions, specify whether the duration is for **connect**, **read**, or the overall request deadline. Two properties of type `Duration` do not necessarily mean the same thing.

### 10.2. `DataSize`

For memory or payload limits, Spring Boot provides `DataSize`:

```java
import org.springframework.util.unit.DataSize;

@DefaultValue("8MB")
DataSize maxPayloadSize
```

Metadata `type` can specify `org.springframework.util.unit.DataSize`. The runtime binder handles appropriate syntax via Spring Boot's converter.

Do not apply `@Min` directly to `DataSize` as with `int` if the validation provider has no corresponding validator. Type metadata and validation constraints are two separate aspects.

### 10.3. Enum

```java
@DefaultValue("STANDARD")
DeliveryMode mode
```

When the property is missing and constructor binding is properly configured, the default can be `DeliveryMode.STANDARD`. Metadata lets the IDE know the enum type and can offer valid values.

### 10.4. Collection

```java
Map<String, String> headers
List<String> regions
```

A collection can have defaults or complex structure. However, do not assume the processor will automatically infer every default value of lists/maps from Java expressions or YAML files. For collections, documentation descriptions should explain add/remove rules, element syntax, and whether dynamic keys are allowed.

For the `DeliveryProperties` class in section 5, illustrative output has a structure roughly like:

```json

    {
      "name": "delivery",
      "type": "com.example.delivery.DeliveryProperties",
      "sourceType": "com.example.delivery.DeliveryProperties"
    }
  ],
  "properties": [
    {
      "name": "delivery.endpoint",
      "type": "java.net.URI",
      "description": "Base URI for the delivery API. Configure this for the target deployment environment.",
      "sourceType": "com.example.delivery.DeliveryProperties"
    },
    {
      "name": "delivery.connect-timeout",
      "type": "java.time.Duration",
      "description": "Maximum time allowed to establish an outbound connection.",
      "sourceType": "com.example.delivery.DeliveryProperties"
    },
    {
      "name": "delivery.max-attempts",
      "type": "java.lang.Integer",
      "description": "Total number of attempts including the initial call.",
      "sourceType": "com.example.delivery.DeliveryProperties",
      "defaultValue": 3
    },
    {
      "name": "delivery.enabled",
      "type": "java.lang.Boolean",
      "description": "Whether the delivery integration is enabled.",
      "sourceType": "com.example.delivery.DeliveryProperties",
      "defaultValue": false
    }
  ],
  "hints": []
}
```

**This is illustrative JSON showing the schema and expected contents, not a file copied from an actual build.** The processor might produce a different description if the source Javadoc differs, format duration defaults differently, or include/omit fields depending on inference capabilities.

What you should inspect in the real output:

- Is there a `delivery` group?
- Are keys in canonical `delivery.*` form?
- Does `type` match the Java declaration?
- Does `description` include the needed Javadoc?
- Which `defaultValue` entries appear and why?
- Is there extra tooling information such as `hints`?

If an optional field is absent in JSON, do not conclude that the runtime application has lost a configuration value. Analyze the metadata generation mechanism first.

## 12. Javadoc for Records and Constructor-Bound Properties

With records, source code is more concise:

```java
package com.example.delivery;

import java.net.URI;
import java.time.Duration;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;

/**
 * Configuration for outbound delivery requests.
 *
 * @param endpoint target service URI
 * @param connectTimeout maximum time allowed to establish a connection
 * @param maxAttempts total attempts including the first call
 */
@ConfigurationProperties(prefix = "delivery")
public record DeliveryProperties(
        URI endpoint,
        @DefaultValue("2s") Duration connectTimeout,
        @DefaultValue("3") int maxAttempts
) {}
```

Javadoc `@param` documents record components according to Java conventions. When using the annotation processor, the ability to collect descriptions from records/constructors and source fields can depend on the processor version.

Therefore, with record classes:

1. Write descriptions for each parameter in the appropriate place instead of writing only one generic Javadoc line.
2. Use `@DefaultValue` to clarify constructor binding defaults.
3. **Inspect the generated JSON file** after building to confirm the expected descriptions actually appear.
4. If a property cannot be fully self-described through source, consider purposeful additional metadata.

The goal is not to force every class style to generate identical JSON; the goal is to produce accurate metadata so tooling and configuration authors understand the contract.

## 13. Supplementing Metadata Manually with `additional-spring-configuration-metadata.json`

The annotation processor does not always capture sufficient information. A property may:

- Be read manually from `Environment`, without a corresponding `@ConfigurationProperties` field.
- Have a longer business description than what the processor extracts.
- Need a list of suggested values for configurators.
- Need a note about a renamed or deprecated key.
- Be created through a structure the processor cannot fully infer.

Spring Boot supports an additional file at the conventional path:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

This is a **project-managed source file**, distinct from `spring-configuration-metadata.json` which is **generated at build time**.

An example:

```json
{
  "properties": [
    {
      "name": "delivery.legacy-region",
      "type": "java.lang.String",
      "description": "Legacy region identifier used by an older integration."
    }
  ],
  "hints": [
    {
      "name": "delivery.mode",
      "values": [
        {
          "value": "STANDARD",
          "description": "Use the normal delivery workflow."
        },
        {
          "value": "EXPRESS",
          "description": "Prefer fast delivery processing."
        }
      ]
    }
  ]
}
```

When the annotation processor and resource processing are properly configured, additional metadata is used to complete the generated information. It can supply properties not discovered by the processor or add information assisting tools.

**Do not confuse the additional file with `application.yml`.** Declaring `delivery.legacy-region` in metadata does not make the application automatically read values or create a Java field named `legacyRegion`.

### When Should Descriptions Be Declared Manually?

For example, a `delivery.mode` property used by an integration adapter whose description in the source class is not clear enough. An additional metadata entry can provide a fuller operational description.

However, if the `@ConfigurationProperties` class already owns the field and you have permission to edit the source, it is usually easier to maintain by writing Javadoc directly on that field. Do not create two conflicting description locations without reason.

### When Should You Watch Build Order?

The additional file sits in `src/main/resources`, while the annotation processor runs during the compile step. In some Gradle/Maven setups, you must ensure the additional resource can be read by the processor at the proper stage so the results merge cleanly.

If additional JSON does not appear in output or does not merge as expected, check:

- Is the processor enabled?
- Is the file at the exact `META-INF` path?
- Is the JSON syntactically valid?
- In what order do compile and process resources run?
- Which metadata files are inside the final artifact?

Do not solve this by directly editing the generated file in `build/` or `target/`, because the next build will overwrite manual changes.

## 14. Value Hints: When a String Has Common Choices

Suppose the class uses:

```java
/**
 * Delivery workflow mode.
 */
private String mode = "STANDARD";
```

Because `String` accepts arbitrary values, having only metadata type `java.lang.String` does not inform the IDE that the team has two common modes.

You can add hints:

```json
{
  "hints": [
    {
      "name": "delivery.mode",
      "values": [
        {
          "value": "STANDARD",
          "description": "Normal priority."
        },
        {
          "value": "EXPRESS",
          "description": "Higher priority."
        }
      ]
    }
  ]
}
```

An IDE supporting metadata can display these two options.

Distinguish:

- **Hint**: suggests options to the config author in the IDE.
- **Java enum**: data type with a fixed set of values.
- **Validation**: mechanism checking input against application rules at runtime.
- **Default**: value chosen when the property is absent.

If requirements only permit two values, consider switching to an enum:

```java
public enum DeliveryMode {
    STANDARD,
    EXPRESS
}
```

And use `DeliveryMode mode` in properties. That way, the data type expresses a stronger contract than an arbitrary string. Metadata hints can add explanations, but do not replace choosing an appropriate Java model.

## 15. Describing Nested Properties and Configuration Groups

Configurations often have multiple levels:

```yaml
delivery:
  retry:
    max-attempts: 3
    backoff: 500ms
  security:
    verify-tls: true
```

A model:

```java
@ConfigurationProperties(prefix = "delivery")
public record DeliveryProperties(
        Retry retry,
        Security security
) {
    public record Retry(
            int maxAttempts,
            Duration backoff
    ) {}

    public record Security(
            boolean verifyTls
    ) {}
}
```

Key names can be represented in metadata as:

```text
delivery.retry.max-attempts
delivery.retry.backoff
delivery.security.verify-tls
```

The processor can discover nested properties based on data types and declarations. For standalone classes that are not obviously nested groups, Spring Boot provides `@NestedConfigurationProperty` to assist nested configuration metadata recognition where appropriate.

**Note:** `@NestedConfigurationProperty` mainly targets the metadata discovery mechanism; it is not a switch forcing the runtime Binder to reject configurations lacking the annotation. For inner classes or types directly supported by the binder, adding the annotation is not necessary just to support nested YAML syntax.

Descriptions should explain **the meaning of each property**, not just the group name:

- `delivery.retry.max-attempts`: total number of sends including the first attempt.
- `delivery.retry.backoff`: wait interval between attempts per policy.
- `delivery.security.verify-tls`: whether to verify TLS for outbound connections.

When a group has many properties, these descriptions also help config authors catch placing a value at the wrong nesting level.

## 16. Metadata and Units of `Duration`/`DataSize`

A `type` field of `java.time.Duration` tells the IDE this is a duration. However, operators need to understand **units and semantics**.

Example:

```java
/**
 * Time allowed to establish the connection.
 * Use values with units, for example "250ms" or "2s".
 */
private Duration connectTimeout = Duration.ofSeconds(2);
```

With Spring Boot, annotations such as `@DurationUnit` and `@DataSizeUnit` can specify the default unit when binding a value without a unit suffix in supported cases.

Example:

```java
import java.time.Duration;
import java.time.temporal.ChronoUnit;
import org.springframework.boot.convert.DurationUnit;

@DurationUnit(ChronoUnit.SECONDS)
private Duration connectTimeout = Duration.ofSeconds(2);
```

Without a suffix, the binder can interpret a plain number as seconds in this context. Even so, metadata descriptions should still encourage using `2s` or `500ms` to avoid ambiguity in configuration files.

Do not treat `description` or `type` as what decides runtime units. Conversion annotations, the conversion service, Java types, and source values are what determine binding results.

### `DataSize` Data

```java
import org.springframework.util.unit.DataSize;

/**
 * Maximum permitted payload size.
 * Example: "8MB".
 */
private DataSize maxPayloadSize = DataSize.ofMegabytes(8);
```

Metadata can inform the IDE of the `DataSize` type and description; the application still needs validation if negative sizes or exceeding business limits are disallowed.

## 17. Deprecation Metadata: Describing Outdated Properties

When a system renames a key, such as from `delivery.retries` to `delivery.max-attempts`, metadata can help the IDE warn configuration authors.

An illustrative additional metadata entry:

```json
{
  "properties": [
    {
      "name": "delivery.retries",
      "type": "java.lang.Integer",
      "description": "Legacy retry setting.",
      "deprecation": {
        "level": "warning",
        "reason": "The name is ambiguous about total attempts.",
        "replacement": "delivery.max-attempts"
      }
    }
  ]
}
```

Meaning:

- `level` expresses the deprecation severity for tooling.
- `reason` explains why the old name should no longer be used.
- `replacement` points to the recommended replacement name.

**Deprecation metadata does not automatically migrate configuration values.** If runtime code no longer accepts `delivery.retries`, the IDE suggesting `delivery.max-attempts` does not ensure older deployments still run properly.

To support a transition period, design an explicit compatibility or migration mechanism. Once the support window ends, remove the old name from code and update deployment configurations.

For JavaBean properties, Spring Boot can leverage dedicated deprecation annotations under appropriate conditions. For metadata exercises, the additional JSON file clearly shows an old name marked and its replacement path described.

## 18. Metadata Is Not Global Schema Validation

When the IDE has the information:

```json
{
  "name": "delivery.max-attempts",
  "type": "java.lang.Integer",
  "defaultValue": 3
}
```

users might expect every invalid declaration to be blocked automatically. Several scenarios must be distinguished.

| Scenario | What does metadata help with? | How does runtime handle it? |
| --- | --- | --- |
| Typing `delivery.max-attemtps` | IDE may not suggest it, may warn unknown name | `ignoreUnknownFields`, binder, and real sources decide |
| Typing `delivery.max-attempts=abc` | IDE knows numeric type, may warn | Conversion to `int` usually fails |
| Typing `delivery.max-attempts=-5` | May show description | `int` still converts; validation like `@Min(1)` is needed |
| Omitting `delivery.max-attempts` | IDE may show metadata default | Runtime default depends on Java/Binder/YAML, not JSON |
| Switching files by profile | Metadata still describes the same property | Runtime reads value from the highest-precedence active source |
| Putting a token in URI | Metadata can state recommendation | Separate security policy needed |

Metadata does not replace:

- `@Validated` and Jakarta Bean Validation.
- The `ignoreUnknownFields` mechanism of `@ConfigurationProperties`.
- Type conversion of Spring Boot Binder.
- Startup tests using real profiles and configuration sources.
- Secret management, authorization, and deployment monitoring practices.

A well-engineered configuration product typically has **clear metadata**, **typed binding**, and **intentional validation**. These three layers complement one another without swapping roles.

## 19. Metadata and Configuration Sources Have Different Priorities

Suppose the Java class has:

```java
private int maxAttempts = 3;
```

Metadata may generate:

```json
{
  "name": "delivery.max-attempts",
  "type": "java.lang.Integer",
  "defaultValue": 3
}
```

`application.yml`:

```yaml
delivery:
  max-attempts: 4
```

`application-prod.yml`:

```yaml
delivery:
  max-attempts: 5
```

Startup:

```bash
java -jar app.jar \
  --spring.profiles.active=prod \
  --delivery.max-attempts=8
```

In a standard Spring Boot setup, command-line arguments have higher precedence than the corresponding Config Data files, so the bean receives `8`.

Even so, metadata can still report **defaultValue = 3** because that is the default recognized at build time. Metadata does not need to change to 4, 5, or 8 whenever the runtime environment varies.

Table:

| Source | Illustrative Value | Role |
| --- | --- | --- |
| Java field initializer | `3` | Runtime default of object when not overridden |
| Metadata `defaultValue` | `3` | Compile-time description for tooling |
| `application.yml` | `4` | Runtime Config Data source |
| `application-prod.yml` | `5` | Profile-specific Config Data source |
| Command-line argument | `8` | Higher-precedence runtime source in example |
| Final bean value | `8` | Runtime result after applying precedence |

Do not call the value in metadata the "actual running value". To observe runtime state, use a safe diagnostic method querying `Environment` or the constructed `@ConfigurationProperties` object.

## 20. Practice: Generating Metadata and Reading Each Field

Let us walk through a repeatable exercise.

### Step 1 — Create Configuration

```yaml
delivery:
  endpoint: https://api.example.invalid/v1
  mode: STANDARD
```

### Step 2 — Create Class with Javadoc and Defaults

```java
package com.example.delivery;

import java.net.URI;
import java.time.Duration;

import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "delivery")
public class DeliveryProperties {

    /**
     * Target URI for outbound delivery requests.
     */
    private URI endpoint;

    /**
     * Timeout for opening the network connection.
     */
    private Duration connectTimeout = Duration.ofSeconds(2);

    /**
     * Total number of requests allowed, including the first attempt.
     */
    private int maxAttempts = 3;

    /**
     * Requested delivery mode.
     */
    private String mode = "STANDARD";

    public URI getEndpoint() {
        return endpoint;
    }
    public void setEndpoint(URI endpoint) {
        this.endpoint = endpoint;
    }

    public Duration getConnectTimeout() {
        return connectTimeout;
    }
    public void setConnectTimeout(Duration connectTimeout) {
        this.connectTimeout = connectTimeout;
    }

    public int getMaxAttempts() {
        return maxAttempts;
    }
    public void setMaxAttempts(int maxAttempts) {
        this.maxAttempts = maxAttempts;
    }

    public String getMode() {
        return mode;
    }
    public void setMode(String mode) {
        this.mode = mode;
    }
}
```

### Step 3 — Register Properties

```java
@SpringBootApplication
@EnableConfigurationProperties(DeliveryProperties.class)
public class DeliveryApplication {
    public static void main(String[] args) {
        SpringApplication.run(DeliveryApplication.class, args);
    }
}
```

Required imports:

```java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
```

### Step 4 — Add the Processor

Gradle:

```groovy
annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
```

Or Maven using the dependency shown in section 4, ensuring annotation processing is enabled.

### Step 5 — Compile

Gradle:

```bash
./gradlew clean classes
```

Maven:

```bash
./mvnw clean compile
```

### Step 6 — Open Generated Metadata

Find `META-INF/spring-configuration-metadata.json` in the build output. In a Gradle Java project, it is usually under:

```text
build/classes/java/main/META-INF/spring-configuration-metadata.json
```

With Maven, usually under:

```text
target/classes/META-INF/spring-configuration-metadata.json
```

Inspect each property `delivery.endpoint`, `delivery.connect-timeout`, `delivery.max-attempts`, and `delivery.mode`. For each property, note:

- `name`
- `type`
- `description`
- `defaultValue` if present

Do not compare JSON against a sample file byte-for-byte. The goal is to understand the meaning and presence of relevant fields.

### Step 7 — Change Javadoc and Rebuild

For example, change the comment on `maxAttempts` from:

```java
/** Total requests allowed. */
```

to:

```java
/**
 * Total delivery attempts including the first request.
 */
```

Rebuild. Check whether `description` of `delivery.max-attempts` updated. If not, confirm whether the processor ran, the compiler recompiled the source, and the IDE is reading the updated output.

### Step 8 — Change Runtime Without Changing Source

Keep Java and metadata unchanged, and launch with:

```bash
java -jar app.jar --delivery.max-attempts=7
```

The bean's runtime result can be 7; metadata still describes the class's compile-time default. This exercise highlights the boundary between **tooling** and **runtime configuration**.

## 21. Adding Hints for a `mode` Property

Suppose configurators must choose `STANDARD` or `EXPRESS` while the Java class temporarily still uses `String`. Create file:

```text
src/main/resources/META-INF/additional-spring-configuration-metadata.json
```

Content:

```json
{
  "hints": [
    {
      "name": "delivery.mode",
      "values": [
        {
          "value": "STANDARD",
          "description": "Normal delivery processing."
        },
        {
          "value": "EXPRESS",
          "description": "Faster processing with higher priority."
        }
      ]
    }
  ]
}
```

After building and letting the IDE update metadata, open `application.yml`, type `delivery.mode`, and see whether the tool displays those choices/hints.

If the IDE does not show the list immediately, you cannot conclude the metadata configuration is wrong. Different IDEs have different metadata support levels and caching behavior; sometimes you need to reload the Gradle/Maven project, rebuild, or refresh indexing.

What matters is that the additional file is in the right place, has valid JSON, and the output metadata contains the required information.

## 22. From Metadata Information to Team Configuration Documentation

Metadata can assist tools, yet the development team still needs a configuration contract table for operations. Example:

| Property | Java Type | Application Default | Description |
| --- | --- | --- | --- |
| `delivery.endpoint` | `URI` | No default | Endpoint of the delivery API |
| `delivery.connect-timeout` | `Duration` | 2 seconds | Maximum time to open connection |
| `delivery.max-attempts` | `int` | 3 | Total calls including initial attempt |
| `delivery.mode` | `String` or enum | `STANDARD` | Request processing mode |

Distinguish "Application Default" in the table from the metadata `defaultValue` field. The table should describe **actual runtime behavior** of the class and shared configuration sources; the JSON file is only one input for generating documentation.

If a value only exists in `application-dev.yml` rather than in the class, deployment docs must clearly state "dev profile value", not mistakenly write "default for all environments".

When writing descriptions for deployers, include:

1. Purpose of the property.
2. Type and unit if needed.
3. When declaring it is required.
4. Valid values or allowed range.
5. Runtime default, if one truly exists.
6. Impact when changed or misconfigured.
7. Security notes if the property involves secrets.

Not all information has to fit inside a short Javadoc comment. However, ensure descriptions help users understand the **property's contract**, rather than merely repeating the field name.

## 23. Common Mistakes When Creating Configuration Metadata

### 23.1. Cannot Find `spring-configuration-metadata.json`

Causes may include not adding the annotation processor, the compiler not running annotation processing, the class not being processed, or build output residing in another directory.

Resolution: check Gradle/Maven configuration, recompile, and look for `META-INF/spring-configuration-metadata.json` in the output.

### 23.2. Added `@ConfigurationProperties` but Forgot the Processor

`@ConfigurationProperties` handles binding; JSON metadata is generated by the processor. An application can read YAML without having the expected metadata file. Add `spring-boot-configuration-processor` if automated tooling metadata is desired.

### 23.3. Confusing `//` Comments with Javadoc

```java
// Maximum attempts
private int maxAttempts;
```

Do not expect this regular comment to appear as `description`. Use:

```java
/**
 * Total delivery attempts including the initial request.
 */
private int maxAttempts;
```

### 23.4. Metadata Type Is Right but Runtime Value Fails

A field `type=java.lang.Integer` only tells tools the expected type. If YAML says `delivery.max-attempts=abc`, the Binder still cannot convert the value to `int`. Do not fix conversion issues merely by changing JSON metadata.

### 23.5. Metadata Default Differs from Running Value

If the class defaults to 3 while deployment passes `--delivery.max-attempts=8`, both metadata `defaultValue=3` and runtime value `8` can be accurate for their respective responsibilities.

### 23.6. Declaring `defaultValue` Manually Without a Runtime Default

A JSON entry declaring `"defaultValue": 3` does not populate 3 into a property missing at runtime. If a real default is needed, add it to the binding class or an effective configuration source.

### 23.7. Overly Vague Description

`"Timeout."` does not tell which timeout, which unit, or which target is affected. Describe specifically "time allowed to establish a connection" and suggest appropriate units.

### 23.8. Overusing `String` Types

Using `String` for timeouts, sizes, endpoints, and modes makes it harder for metadata to express structure and reduces typed conversion/validation capabilities. Prefer `Duration`, `DataSize`, `URI`, enums, and appropriate types supported by the binder.

### 23.9. Mixing Legacy `javax.validation` Annotations

To get runtime validation in Spring Boot 3, use appropriate annotations under `jakarta.validation` and a validation provider. Metadata does not substitute for setting up validation dependencies.

### 23.10. Describing Secrets with Real Values

Do not put real tokens, real passwords, or URLs containing credentials into Javadoc, metadata hints, or `defaultValue`. Metadata JSON may live inside the JAR and be read by IDEs; it is not a secret vault.

### 23.11. Manually Editing Build Output Files

Editing `build/classes/.../spring-configuration-metadata.json` can yield temporary results that get overwritten on the next compile. Edit source, annotations, or `additional-spring-configuration-metadata.json` instead.

### 23.12. Duration Defaults Without Units

If a description only says "default: 3000" without stating milliseconds or seconds, users easily get confused. Describe using `3s` or `3000ms` and use `Duration` so code conveys meaning.

### 23.13. Failing to Check Metadata for Nested Objects

If `delivery.retry.max-attempts` is missing from JSON, the processor may not have recognized the nested type. Inspect the Java structure and nested metadata annotations where appropriate.

### 23.14. Confusing Metadata Hints with Mandatory Values

A `values` list in `hints` is generally meant to assist the IDE; it is not necessarily a check against all runtime inputs. For a fixed set of values, use an enum or validation.

### 23.15. Forgetting to Refresh the IDE After Building

The IDE may cache metadata from a previous build. If JSON output has updated while suggestions remain stale, reload the project and re-index per your tool instead of tweaking YAML arbitrarily.

## 24. How to Inspect Metadata in the Final Artifact

When packaging with the Spring Boot Gradle plugin, create the JAR:

```bash
./gradlew bootJar
```

With Maven and its corresponding plugin, you can use:

```bash
./mvnw package
```

Then inspect metadata in the output or JAR. With a Spring Boot executable JAR, application resources typically live at a location corresponding to `BOOT-INF/classes/META-INF/`.

Example expected path inside the JAR:

```text
BOOT-INF/classes/META-INF/spring-configuration-metadata.json
```

The layout may differ from an ordinary library JAR. In a library module, the metadata resource is usually at `META-INF/spring-configuration-metadata.json` directly in the JAR. What matters is that metadata is available on the classpath so IDEs/tooling can read it when needed.

If a module contains `@ConfigurationProperties` used by other applications, packaging metadata inside the library JAR lets consuming projects also get suggestions when declaring properties belonging to that module.

In a multi-module workspace, check metadata generated **in the exact module declaring the properties**, not only looking at an aggregate application output.

## 25. Compatibility Between Metadata, Source Code, and Spring Boot Versions

Metadata is a format specified by Spring Boot. However, source-code inference capabilities vary by class style and processor version.

Cases to watch out for:

- JavaBean with fields/getters/setters.
- Constructor-bound classes.
- Java records.
- Kotlin data classes.
- Nested properties.
- Collections, Maps, and generic types.
- Properties with defaults from annotations or initializer expressions.
- Properties provided via `@Bean` or a library adapter.

For classes that are hard to infer, do not promise the compiler will figure everything out automatically. **Inspect the actual output** and supply additional metadata if needed.

At the same time, when upgrading Spring Boot, keep the processor and runtime within the same Boot version management system, avoiding attaching a processor version far removed from the annotations or source constructs in use.

Do not try to deduce runtime policy solely from metadata without considering bean registration, binding, conversion, and validation of the application version.

## 27. Practical Workflow Summary

When adding a new configuration group, you can follow this sequence:

1. **Define the prefix and properties:** for example `delivery.*`.
2. **Choose meaningful Java types:** `Duration` for time, `URI` for endpoints, enums for fixed value sets.
3. **Write Javadoc:** clarify purpose, units, scope, and required conditions.
4. **Define intentional runtime defaults:** field initializers, `@DefaultValue`, or shared configuration files per design.
5. **Register `@ConfigurationProperties`:** ensure the runtime binder actually creates the bean.
6. **Configure `spring-boot-configuration-processor`:** so the build generates metadata.
7. **Inspect `spring-configuration-metadata.json`:** verify `name`, `type`, `description`, and `defaultValue` if present.
8. **Add additional metadata when needed:** especially for hints or properties that cannot be inferred automatically.
9. **Test runtime configuration:** test missing properties, wrong types, violated constraints, and profile overrides.
10. **Never put secrets in metadata:** JSON may be distributed with artifacts.

Consolidated flow:

```text
Source code @ConfigurationProperties
       |
       +-- Java type -----------> type
       |
       +-- Javadoc -------------> description
       |
       +-- Runtime default -----> defaultValue (if inferable)
       |
       +-- Additional metadata -> hints / supplementary info
       |
       v
spring-boot-configuration-processor
       |
       v
META-INF/spring-configuration-metadata.json
       |
       v
IDE suggests and assists the config author

Meanwhile:

ENV / YAML / CLI / Profiles
       |
       v
Environment -> Binder -> Validation -> Runtime bean
```

These two flows complement each other: metadata helps **write configuration more accurately**; binding and validation help **run configuration more reliably**.

## 28. Takeaways

Three metadata fields to remember:

- **`description`**: provides text explaining *what the property is used for*; usually taken from Javadoc or additional metadata.
- **`type`**: indicates the *Java type of the configuration value*; usually inferred by the processor from `@ConfigurationProperties` declarations.
- **`defaultValue`**: describes the *default recognized at build time*; may be absent if uninferable. This is **not** an automatic runtime default source.

Spring Boot generates metadata when an appropriate processor is present:

```text
org.springframework.boot:spring-boot-configuration-processor
```

The output file is typically:

```text
META-INF/spring-configuration-metadata.json
```

When extra descriptions or suggestions are needed, you can create:

```text
META-INF/additional-spring-configuration-metadata.json
```

Things not to conflate:

1. Having metadata **does not mean** the application automatically checks all values.
2. Having `defaultValue` in JSON **does not mean** the Binder automatically uses it when the property is missing.
3. Metadata listing type `Integer` **does not mean** a value `abc` becomes valid.
4. The IDE suggesting a key name **does not mean** that property is guaranteed to be supplied in the running environment.
5. Values in production **do not necessarily** match the default described at compile time.

Writing good metadata is part of creating a **discoverable, understandable, and maintainable configuration contract**, especially when a codebase has multiple modules and multiple `@ConfigurationProperties` groups.
