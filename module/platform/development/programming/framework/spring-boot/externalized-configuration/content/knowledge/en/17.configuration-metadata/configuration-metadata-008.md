# Value Hints, Deprecation Marking, and Declaring Replacement Keys

Spring Boot supports **configuration metadata** so development tools (especially IDEs) understand the structure of application configuration properties. In addition to describing a property's name, data type, default value, and meaning, metadata can provide **suggestions for reasonable values**, mark **properties as deprecated**, and clearly indicate **the recommended replacement property**.

This information is very helpful when a project has many custom properties, when packaging a Spring Boot starter for another team to use, or when renaming a configuration key without catching library consumers off guard.

However, it is essential to understand the boundary:

> **Metadata helps tools understand and guide configuration authors. It does not create validation rules, does not rename old keys to new keys automatically, does not migrate values, and does not guarantee Spring Boot prints warnings at runtime.**

This lesson moves from generating metadata for `@ConfigurationProperties` to adding `hints`, declaring `deprecation` with `reason` and `replacement`, using `@DeprecatedConfigurationProperty`, supporting version transitions, and verifying the packaged JSON file.

## 1. What Problem Does Configuration Metadata Solve?

Suppose an internal library allows configuring:

~~~yaml
warehouse:
  client:
    mode: "http"
    endpoint: "https://warehouse.example.invalid"
    timeout: 3s
~~~

Library consumers need to know:

- Which keys exist under `warehouse.client`?
- Which values does `mode` accept, such as `http` or `queue`?
- What type does `timeout` use and is there a default?
- If the old `base-url` name was changed to `endpoint`, will the IDE remind users?
- Is the old key still supported by the software at runtime or has it actually been removed?

Those questions have two kinds of answers.

**First kind: the real runtime contract.** `@ConfigurationProperties` classes, the Binder, validation, and application logic decide how keys are read and which values are valid.

**Second kind: tooling information.** Metadata describes types, descriptions, hints, and deprecation so the IDE can autocomplete, show explanations, or warn users.

The file typically recognized by tools is named:

~~~text
META-INF/spring-configuration-metadata.json
~~~

This is a resource packaged on the classpath. It can be auto-generated by the annotation processor, then supplemented from a hand-written metadata file when needed.

## 2. Four Concepts to Distinguish

| Concept | Purpose | Automatically alters runtime binding? |
| --- | --- | --- |
| `properties` in metadata | Describes name, type, default, description | No |
| `hints` | Proposes values or suggestion providers for the IDE | No |
| `deprecation` | Signals that a key is no longer recommended or has been removed | No |
| `replacement` | Points to the key to use instead of the old key | Does not migrate values |

For example, when metadata declares:

~~~json
{
  "name": "warehouse.client.mode",
  "values": [
    { "value": "http" },
    { "value": "queue" }
  ]
}
~~~

the IDE can suggest these two values. However, if the Java bean still accepts `String mode` and the application does not check the value, users can still configure `mode: "typo"`; metadata does not ensure the application rejects it.

Conversely, if Java uses an `enum`:

~~~java
public enum ClientMode {
    HTTP,
    QUEUE
}
~~~

then the Binder has an enum conversion mechanism and can reject unconvertible values per conversion rules. This is a **type/runtime constraint**, not because metadata values were declared.

## 3. Starting from a `@ConfigurationProperties` Class

Typed configuration example:

~~~java
package example.warehouse;

import java.net.URI;
import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "warehouse.client")
public record WarehouseClientProperties(
        String mode,
        URI endpoint,
        Duration timeout
) {}
~~~

Registration:

~~~java
package example.warehouse;

import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(WarehouseClientProperties.class)
class WarehouseClientConfiguration {
}
~~~

Configuration file:

~~~yaml
warehouse:
  client:
    mode: "http"
    endpoint: "https://warehouse.example.invalid"
    timeout: 3s
~~~

Thus, runtime configuration already has a typed object contract. If the corresponding annotation processor is enabled, Spring Boot can generate metadata for properties under the `warehouse.client` prefix.

Key points to remember:

- `@ConfigurationProperties` binds a prefix name to a Java type.
- `@EnableConfigurationProperties` or `@ConfigurationPropertiesScan` registers that type as a configuration-properties bean.
- The Binder reads PropertySources, converts types, and constructs the object.
- Configuration metadata helps tooling understand those keys.

The annotation processor **is not** a bean registration mechanism. Having JSON metadata does not make the bean automatically appear in the ApplicationContext.

## 4. Enabling `spring-boot-configuration-processor`

The component commonly used to generate metadata is `spring-boot-configuration-processor`.

### 4.1. Maven

Dependency example:

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>
~~~

In standard Maven projects using Spring Boot dependency management, the processor version is managed alongside the project's Boot version. `optional=true` helps avoid accidentally propagating the processor dependency to consumers via ordinary transitive dependency relationships; it **does not** replace configuring annotation processing.

If the project manages annotation processors via `maven-compiler-plugin` or newer JDK mechanisms, ensure the processor **is actually run by javac** in the module containing `@ConfigurationProperties`. Especially in Java/Maven setups with explicit processor lists or JDKs that do not auto-enable annotation processing, simply adding the dependency may not suffice.

Example processor path configuration in a project with an appropriate plugin/compiler setup:

~~~xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <configuration>
                <annotationProcessorPaths>
                    <path>
                        <groupId>org.springframework.boot</groupId>
                        <artifactId>spring-boot-configuration-processor</artifactId>
                        <version><!-- version aligned with Spring Boot --></version>
                    </path>
                </annotationProcessorPaths>
            </configuration>
        </plugin>
    </plugins>
</build>
~~~

The XML snippet illustrates how to declare the processor in the build plugin; in a real POM, the `version` tag needs a **valid version value** or corresponding plugin/processor management mechanism, not a comment left in place of a runnable version.

### 4.2. Gradle Groovy DSL

~~~groovy
dependencies {
    annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
}
~~~

### 4.3. Gradle Kotlin DSL

~~~kotlin
dependencies {
    annotationProcessor(
        "org.springframework.boot:spring-boot-configuration-processor"
    )
}
~~~

Gradle has a dedicated configuration for annotation processors. A library containing only `@ConfigurationProperties` may need the processor in **that module itself**, not only in the consuming application module.

In pure Kotlin projects, annotation processing and metadata have specific guidance for the Kotlin compiler; examples here focus on Java.

## 5. Where Is Generated Metadata Located?

The target filename on the classpath is:

~~~text
META-INF/spring-configuration-metadata.json
~~~

Its location in the build directory depends on Maven, Gradle, the annotation processor, and packaging. Usually it can be found at:

~~~text
target/classes/META-INF/spring-configuration-metadata.json

build/classes/java/main/META-INF/spring-configuration-metadata.json
~~~

These paths are only examples. The file inside the **published JAR** is the final resource that IDEs or consuming tools can use.

You can inspect:

~~~bash
jar tf build/libs/warehouse-client.jar
~~~

or:

~~~bash
jar tf target/warehouse-client.jar
~~~

Then look for:

~~~text
META-INF/spring-configuration-metadata.json
~~~

If the file is missing, do not immediately conclude `@ConfigurationProperties` is broken at runtime. It may simply be that the annotation processor did not run, the compilation task is misconfigured, or the module artifact did not package the metadata file.

## 6. JSON Metadata Structure

A metadata file typically uses three top-level groups:

~~~json
{
  "groups": [
    {
      "name": "warehouse.client",
      "type": "example.warehouse.WarehouseClientProperties",
      "sourceType": "example.warehouse.WarehouseClientProperties"
    }
  ],
  "properties": [
    {
      "name": "warehouse.client.mode",
      "type": "java.lang.String",
      "description": "Protocol used to reach the warehouse service."
    },
    {
      "name": "warehouse.client.endpoint",
      "type": "java.net.URI",
      "description": "Base URI of the warehouse service."
    },
    {
      "name": "warehouse.client.timeout",
      "type": "java.time.Duration",
      "description": "Maximum wait time for one request."
    }
  ],
  "hints": [
    {
      "name": "warehouse.client.mode",
      "values": [
        {
          "value": "http",
          "description": "Direct HTTP integration."
        },
        {
          "value": "queue",
          "description": "Asynchronous message-based integration."
        }
      ]
    }
  ]
}
~~~

This is an **illustration of metadata structure**, not advice to manually write all groups/properties when the processor can already generate them.

- `groups` describes a group of properties, usually tied to a prefix.
- `properties` describes concrete keys along with Java types and supporting information.
- `hints` provides value suggestions or providers for a supported key.

Actual fields also include `defaultValue`, `sourceMethod`, deprecation metadata, and other fields per the Spring Boot schema. Do not add arbitrary custom fields expecting the IDE to understand them.

JSON metadata must follow valid JSON syntax: no comments in the file, no trailing commas, and double quotes must be used for string keys/values.

## 7. Additional File: `additional-spring-configuration-metadata.json`

The annotation processor generates much information from Java types, yet cannot guess every mode value a project wants to suggest.

Spring Boot supports an additional file at the path:

~~~text
src/main/resources/
  META-INF/
    additional-spring-configuration-metadata.json
~~~

Sample content:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.mode",
      "values": [
        {
          "value": "http",
          "description": "Use an HTTP client."
        },
        {
          "value": "queue",
          "description": "Publish messages to a queue."
        }
      ]
    }
  ]
}
~~~

When the annotation processor is properly configured and sees the additional resource, the information can be merged into the generated/packaged `spring-configuration-metadata.json` file.

**Note on build order:** In certain special Maven/Gradle setups, the processor needs to see additional metadata in the compilation classpath/resource pipeline. Inspect the artifact after `clean build` rather than concluding solely from the source file's existence.

Do not create a hand-written `spring-configuration-metadata.json` file that accidentally overwrites processor output if your goal is only to add hints or descriptions. Use the conventional `additional-spring-configuration-metadata.json` path.

## 8. How to Declare Value Suggestions with `hints.values`

Example property:

~~~yaml
warehouse:
  client:
    mode: "http"
~~~

You want the IDE to display two familiar options:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.mode",
      "values": [
        {
          "value": "http",
          "description": "Use the HTTP integration."
        },
        {
          "value": "queue",
          "description": "Use the queue integration."
        }
      ]
    }
  ]
}
~~~

A `values` element contains:

- `value`: value that tools can propose.
- `description`: info helping users choose, typically an optional field.

This is a **suggestion list**, not an access list or mandatory value filter.

Some IDEs can use this metadata to autocomplete values after `:` in YAML or `=` in properties. However, IDE behavior depends on plugins, versions, and metadata support.

If the application must not accept any string other than `http` and `queue`, enforce that **at runtime** using an enum, Bean Validation, or appropriate validation logic.

## 9. Value Suggestions Do Not Mean a Runtime Enum

Compare two Java types.

**String type:**

~~~java
@ConfigurationProperties(prefix = "warehouse.client")
public record WarehouseClientProperties(String mode) {}
~~~

Adding metadata values can help the IDE suggest `http` or `queue`. Yet `String mode` can still receive `"ftp"` if there is no validation.

**Enum type:**

~~~java
public enum ClientMode {
    HTTP,
    QUEUE
}
~~~

~~~java
@ConfigurationProperties(prefix = "warehouse.client")
public record WarehouseClientProperties(ClientMode mode) {}
~~~

Here the Binder applies enum conversion. In many cases, the annotation processor/IDE can also infer choices from the enum. Hand-written hints may be unnecessary if the type already expresses the complete value set.

Choose:

- `String` + hints: when suggested values are common, yet the application permits extensible values or custom rules.
- `enum`: when the value set is closed and controlled by the Java model.
- `String` + `@Pattern`/custom validator: when strings follow a valid pattern or domain but enums are undesirable/impractical.

Metadata does not replace Java type design.

## 10. Hints for Numeric or Boolean Properties

Suppose:

~~~yaml
report:
  level: 2
  enabled: true
~~~

Common reporting levels can be described:

~~~json
{
  "hints": [
    {
      "name": "report.level",
      "values": [
        { "value": 1, "description": "Light reporting." },
        { "value": 2, "description": "Standard reporting." },
        { "value": 3, "description": "Detailed reporting." }
      ]
    }
  ]
}
~~~

However, if Java uses `Integer level`, the value `100` can still bind. To constrain 1..3:

~~~java
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;

@ConfigurationProperties(prefix = "report")
@Validated
public record ReportProperties(
        @Min(1) @Max(3) int level
) {}
~~~

Similarly, for booleans, the Java type already expresses true/false. Adding hints does not automatically implement feature-toggle logic.

A rule of thumb: **do not overuse hints to express what the type system/validation does better**.

## 11. Hint Providers and How They Differ from `values`

Besides static `values`, metadata allows describing a **provider** so the IDE or tool draws suggestions from context.

General example:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.profile",
      "providers": [
        {
          "name": "spring-profile-name"
        }
      ]
    }
  ]
}
~~~

The `spring-profile-name` provider is one of the conventional provider names in Spring Boot metadata. Supporting tools can use project context to propose profile names instead of hardcoding every profile in the values array.

Other conventional providers in Spring Boot metadata include `class-reference`, `spring-bean-reference`, `logger-name`, and `any`. Support for each provider depends on the IDE and situation.

Do not invent an imaginary provider name like `"my-custom-provider"` expecting every IDE to know where to find data. Provider metadata is a **contract with tooling**, not a Java SPI executed automatically by Spring Boot at runtime.

If the value set consists of two or three static strings, `values` is usually sufficient. If the list depends on beans, classes, or profiles existing in the project, a tool-supported provider may be more appropriate.

## 12. Combining `values` and Providers

A property may have a few common values while still permitting user-defined names.

Example:

~~~json
{
  "hints": [
    {
      "name": "routing.strategy",
      "values": [
        {
          "value": "round-robin",
          "description": "Distribute requests in sequence."
        },
        {
          "value": "least-connections",
          "description": "Prefer the backend with fewer connections."
        }
      ],
      "providers": [
        {
          "name": "any"
        }
      ]
    }
  ]
}
~~~

The message to tools is: there are useful suggestions, though other values may also exist per the configuration contract.

**Warning:** the "other values may be entered" signal in metadata must not be treated as a runtime permission. If the application only accepts two strategies, Java logic must restrict to those two strategies and may not need the `any` provider.

Metadata shapes the configuration authoring experience; it does not replace domain structure.

## 13. Hints for Map Keys and Map Values

When a property is a Map, suggestion needs may fall on **keys** or **values**.

Example:

~~~yaml
warehouse:
  channels:
    email: "enabled"
    webhook: "disabled"
~~~

Java:

~~~java
@ConfigurationProperties(prefix = "warehouse")
public record WarehouseProperties(
        java.util.Map<String, String> channels
) {}
~~~

In additional metadata, the `.keys` or `.values` conventions can be used in hint names for map entries.

Example:

~~~json
{
  "hints": [
    {
      "name": "warehouse.channels.keys",
      "values": [
        { "value": "email", "description": "Email channel." },
        { "value": "webhook", "description": "Webhook channel." }
      ]
    },
    {
      "name": "warehouse.channels.values",
      "values": [
        { "value": "enabled", "description": "Channel is active." },
        { "value": "disabled", "description": "Channel is inactive." }
      ]
    }
  ]
}
~~~

This form is useful when keys/values need suggestions from a common set. However, remember:

- Map keys may be normalized or bound under specific rules (especially with special characters).
- Hints do not restrict the entire Map to the two keys above.
- If the value is a complex object, it is usually better to declare structured properties types and validation rather than cramming all rules into hints.
- If Map entry keys require a closed set, design corresponding validation or types.

## 14. Declaring `description` and `defaultValue`: Giving Hints Context

A list of values without explanations can easily mislead. When designing metadata, describe clearly:

~~~json
{
  "properties": [
    {
      "name": "warehouse.client.timeout",
      "type": "java.time.Duration",
      "description": "Request timeout; use a duration such as 3s.",
      "defaultValue": "3s"
    }
  ]
}
~~~

The `description` field helps the IDE show the key's meaning. `defaultValue` describes the **published default**.

Be careful though: **adding `defaultValue` to metadata does not assign a default for the Binder**. If the actual application has no default, metadata can become inaccurate information.

Runtime defaults must come from something that actually takes effect, such as JavaBean field initializers, constructor-binding `@DefaultValue`, or default property sources supplied by the application.

If the processor already generated metadata for the class, it is usually better to edit the type/Javadoc at the source or add metadata intentionally, avoiding two conflicting descriptions.

## 15. What Does a Deprecated Property Mean?

When a key is no longer recommended, it can be marked **deprecated** so users know to migrate to a new key.

Old version example:

~~~yaml
warehouse:
  client:
    base-url: "https://warehouse.example.invalid"
~~~

New version uses:

~~~yaml
warehouse:
  client:
    endpoint: "https://warehouse.example.invalid"
~~~

During the transition period, developers want to communicate:

> `warehouse.client.base-url` is the old key. Please use `warehouse.client.endpoint`.

Configuration metadata allows describing that message. However, "deprecated" can carry several levels of meaning:

- **Deprecated yet still supported at runtime** to give users time to update.
- **Already removed from runtime**, so the IDE should discourage using it.
- **Replaced by another key** with a new structure or meaning.
- **No direct replacement key**, because the old feature was removed.

Do not mark deprecation just because a key has an awkward name. Have a clear compatibility plan and reason.

## 16. Deprecation Structure in Metadata

In JSON metadata, a property can contain a `deprecation` field:

~~~json
{
  "properties": [
    {
      "name": "warehouse.client.base-url",
      "type": "java.net.URI",
      "description": "Legacy base URL for the warehouse client.",
      "deprecation": {
        "level": "warning",
        "reason": "Renamed for consistency with client endpoint settings.",
        "replacement": "warehouse.client.endpoint"
      }
    }
  ]
}
~~~

Field meanings:

| Field | Meaning |
| --- | --- |
| `deprecation.level` | Severity level: `warning` or `error` per metadata schema |
| `deprecation.reason` | Explains why the key is no longer recommended |
| `deprecation.replacement` | Suggested new property name, if any |

`replacement` should use the **full property name with prefix**, such as `warehouse.client.endpoint`. Do not write only `endpoint` if the IDE needs to know the exact new key.

This information serves tooling experience and does not execute logic changes on its own.

## 17. How Do `warning` and `error` Levels Differ?

In Spring Boot configuration metadata, deprecation has two common levels:

**`warning`**: the property is no longer the recommended choice; typically it may still exist for compatibility. The IDE can warn and suggest migrating.

**`error`**: the property is no longer supported per metadata, so tools can display a stricter warning and avoid proposing continued use.

Example:

~~~json
{
  "properties": [
    {
      "name": "warehouse.client.legacy-mode",
      "type": "java.lang.String",
      "deprecation": {
        "level": "warning",
        "reason": "Use a typed mode setting.",
        "replacement": "warehouse.client.mode"
      }
    },
    {
      "name": "warehouse.client.old-debug",
      "type": "java.lang.Boolean",
      "deprecation": {
        "level": "error",
        "reason": "This configuration option was removed."
      }
    }
  ]
}
~~~

**Very common misconception:** `level:"error"` in metadata **does not mean Spring Boot automatically throws an exception when it sees that property**. It is a severity marker for metadata tooling. If the application needs to reject a removed key, it must have explicit runtime checks, or simply cease binding/using the key by design alongside an appropriate unknown-property policy.

Metadata levels must not be described as a security enforcement mechanism.

## 18. `@DeprecatedConfigurationProperty` on Getters

Spring Boot provides the `@DeprecatedConfigurationProperty` annotation in package:

~~~java
org.springframework.boot.context.properties.DeprecatedConfigurationProperty
~~~

This annotation helps the processor recognize that a configuration property is deprecated, along with `reason` and `replacement`.

JavaBean-style example:

~~~java
package example.warehouse;

import java.net.URI;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.DeprecatedConfigurationProperty;

@ConfigurationProperties(prefix = "warehouse.client")
public class WarehouseClientProperties {

    private URI baseUrl;
    private URI endpoint;

    @Deprecated
    @DeprecatedConfigurationProperty(
        reason = "The base-url property was renamed to endpoint.",
        replacement = "warehouse.client.endpoint"
    )
    public URI getBaseUrl() {
        return baseUrl;
    }

    @Deprecated
    public void setBaseUrl(URI baseUrl) {
        this.baseUrl = baseUrl;
    }

    public URI getEndpoint() {
        return endpoint;
    }

    public void setEndpoint(URI endpoint) {
        this.endpoint = endpoint;
    }

    public URI effectiveEndpoint() {
        return endpoint != null ? endpoint : baseUrl;
    }
}
~~~

The snippet illustrates two responsibilities:

1. Getter `getBaseUrl()` is marked as an old property so the processor generates deprecation metadata.
2. Method `effectiveEndpoint()` **actively performs the runtime fallback** from the new endpoint to the old baseUrl.

`@DeprecatedConfigurationProperty` **does not automatically create a fallback**. If you delete `effectiveEndpoint()` or omit equivalent logic, metadata can still suggest migrating, yet runtime will not automatically prefer the new key.

In the example, when both keys are declared, the code picks `endpoint` first. This is an **application compatibility decision**, not built-in Spring Boot precedence between two differently named properties.

## 19. Why Is the Annotation Placed on the Getter?

With JavaBean-style `@ConfigurationProperties`, the metadata processor can locate properties through accessors. To attach deprecation to a property in the standard way, Spring Boot recommends placing `@DeprecatedConfigurationProperty` on the corresponding getter.

Example:

~~~java
@Deprecated
@DeprecatedConfigurationProperty(
    reason = "Use client.request-timeout instead.",
    replacement = "client.request-timeout"
)
public Duration getTimeout() {
    return timeout;
}
~~~

Points to distinguish:

- `@Deprecated` is a standard Java annotation signaling an API member is no longer recommended.
- `@DeprecatedConfigurationProperty` conveys **deprecation info specifically for configuration metadata**.
- This annotation does not rename fields, does not convert bindings, and does not create aliases in `Environment`.
- `@DeprecatedConfigurationProperty` targets methods appropriately; do not assume you can put it directly on any record component or constructor parameter and have the processor reliably recognize it.

For immutable records lacking traditional JavaBean getters, or for properties already deleted from source, **the additional metadata file** is usually the clear choice for describing deprecation and replacement.

## 20. Manually Declaring a Deprecated Property for a Record

Suppose the new type was changed to:

~~~java
import java.net.URI;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "warehouse.client")
public record WarehouseClientProperties(
        URI endpoint
) {}
~~~

However, the project wants tools to keep showing that `warehouse.client.base-url` is an old key.

You can declare deprecation manually in:

~~~text
src/main/resources/META-INF/
  additional-spring-configuration-metadata.json
~~~

Content:

~~~json
{
  "properties": [
    {
      "name": "warehouse.client.base-url",
      "type": "java.net.URI",
      "description": "Legacy configuration key.",
      "deprecation": {
        "level": "warning",
        "reason": "The key was renamed.",
        "replacement": "warehouse.client.endpoint"
      }
    }
  ]
}
~~~

However, it must align with **the actual behavior of the application version**.

If the new code only binds `endpoint`, configuring `base-url` **no longer necessarily has any effect**. Declaring a warning claiming "key was just renamed yet still works" is misleading if runtime has stopped supporting it. When a key is truly removed, consider level `error` and clearly document the migration plan.

To preserve compatibility, code must handle the legacy key, such as supporting both properties in a JavaBean or an appropriate adapter configuration.

## 21. Replacement Is Not an Alias

This is the most important point when declaring a replacement key.

Metadata:

~~~json
{
  "deprecation": {
    "level": "warning",
    "reason": "Renamed to endpoint.",
    "replacement": "warehouse.client.endpoint"
  }
}
~~~

does not mean Spring Boot automatically performs:

~~~text
warehouse.client.base-url
        |
        v
warehouse.client.endpoint
~~~

in `Environment`.

If the user's file only has:

~~~yaml
warehouse:
  client:
    base-url: "https://legacy.example.invalid"
~~~

and the new Java record only accepts `URI endpoint`, the `endpoint` value may be missing. The IDE may suggest editing YAML, yet the Binder does not carry the value of `base-url` over to `endpoint` based on metadata alone.

You must **choose one of the compatibility strategies**:

1. Keep both old and new fields in the properties type and select the effective value in code.
2. Use an explicit migration mechanism provided by the application/library.
3. Accept a breaking change, announce deprecation/removal, and require users to rename the key.
4. When the contract is complex, add validation to catch old/invalid configurations at startup.

Do not rely on metadata as a runtime migration mechanism.

## 22. Precedence Policy When Both Old and New Keys Are Declared

An application may encounter:

~~~yaml
warehouse:
  client:
    base-url: "https://legacy.example.invalid"
    endpoint: "https://new.example.invalid"
~~~

The two keys have different names. **`PropertySource` precedence does not automatically decide which key wins**, because this is not one key declared in two different sources.

A policy must be established:

- Prefer the new key if both exist.
- Fail with an error if both appear to avoid ambiguity.
- Allow the old key as a fallback for a fixed transition window.
- Log a migration notice once, without leaking secrets.

Explicit code example:

~~~java
public URI effectiveEndpoint() {
    if (endpoint != null) {
        return endpoint;
    }
    return baseUrl;
}
~~~

If the new endpoint becomes required in a later version, remove the fallback and update the migration guide/metadata. To prevent both keys from coexisting, write a cross-field validator.

What matters is that code readers can pinpoint **precisely which value takes effect**.

## 23. Two-Phase Migration Strategy

A solid roadmap for library configuration:

| Phase | Runtime | Metadata | User Guidance |
| --- | --- | --- | --- |
| Version A | Uses `base-url` only | Normal key | No migration yet |
| Version B | Supports `base-url` and `endpoint` | Marks `base-url` warning, replacement=endpoint | Recommends switching to endpoint |
| Version C | Drops support for `base-url` | Marks removed/error as appropriate | Requires using endpoint |

This is a policy example, not a mandate that every project use exactly three versions.

Key aspects during Version B:

- Do not break users' running configurations.
- Provide enough information for IDEs or documentation to guide migration.
- Have a clear policy when old and new are declared simultaneously.
- Have tests covering both the old key and the new key.
- Have a specific deprecation message, not just "deprecated".

When moving to Version C, inspect how the application reacts to the old key. Spring Boot may ignore unknown properties depending on binding configuration; merely removing a field from the properties class does not guarantee startup will fail. If the old key must be rejected, design an explicit check.

## 24. How Should `reason` Be Written?

A good `reason` answers **why** the key was deprecated and **what changed**.

Insufficient example:

~~~json
"reason": "Deprecated."
~~~

More helpful examples:

~~~json
"reason": "Renamed to client.endpoint to distinguish the full endpoint from the service root URL."
~~~

Or:

~~~json
"reason": "This option is no longer used because retry behavior is controlled by client.retry-policy."
~~~

Conventions to follow:

- Short, clear, stating the technical reason or meaning of the change.
- Do not claim "the old key still works" if that is untrue.
- Specify the replacement key in `replacement` when an equivalent migration path exists.
- If there is no replacement, state plainly that the feature was removed or configuration must be changed.
- Avoid putting internal URLs, credentials, tokens, or sensitive data into description/reason.

IDE tooltips may display these strings directly, so they should be written clearly for library consumers.

## 25. Metadata Does Not Automatically Generate Startup Warnings

A common misconception: "Marking deprecated means Spring Boot will log a warning whenever anyone uses the old key."

**Do not assume that.** Configuration metadata is primarily used by tools like IDEs; the Spring Boot Binder does not read `deprecation.replacement` to emit migration logs or remap keys.

If you want a runtime warning for an old key, implement it intentionally in code, such as a startup component inspecting configuration sources and detecting legacy keys in use. Be careful though:

- `Environment.containsProperty("warehouse.client.base-url")` only tells whether Environment can resolve that key; it does not automatically indicate the source or intent.
- Never log secret property values.
- Do not spam warnings on every request.
- Do not use runtime warnings as a substitute for official migration documentation.
- If runtime still supports both keys, tests must prove precedence and fallback work properly.

Do not invent a "runtime migration mechanism" merely to solve an IDE suggestion problem unless there is an actual requirement.

## 26. Hints Do Not Guarantee Valid YAML Either

Example:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.mode",
      "values": [
        { "value": "http" },
        { "value": "queue" }
      ]
    }
  ]
}
~~~

The following are two separate concerns:

1. **Autocomplete** can suggest `http`/`queue` while writing YAML.
2. **Validation** decides whether `mode: "ftp"` is allowed when the application runs.

If a strict rule is needed, use an enum:

~~~java
public enum Mode {
    HTTP,
    QUEUE
}
~~~

Or validation:

~~~java
import jakarta.validation.constraints.Pattern;

@Pattern(regexp = "http|queue")
String mode
~~~

An appropriate Bean Validation provider and `@Validated`/registration on the root are needed when using Bean Validation for configuration properties.

Similarly, `hints.values` does not check whether a `URI` is reachable, whether timeouts are positive, or bound List element counts.

## 27. Value Descriptions Should Reflect Only the Real Contract

If `mode=http` works synchronously and `mode=queue` requires message broker configuration, the hint description should reflect that:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.mode",
      "values": [
        {
          "value": "http",
          "description": "Send requests directly to the HTTP endpoint."
        },
        {
          "value": "queue",
          "description": "Publish messages; requires queue configuration."
        }
      ]
    }
  ]
}
~~~

However, descriptions do not replace runtime required conditions. For example, in `queue` mode, the application may require `warehouse.client.queue-name`; conditional validation is needed to catch missing values during bean creation or startup.

When multiple keys have interdependencies, complete configuration documentation or a custom validator is usually clearer than stuffing all logic into a few description sentences.

## 28. Hints for Nested Configuration and Collections

An object may have:

~~~yaml
warehouse:
  client:
    retries:
      attempts: 3
      backoff: 250ms
    modes:
      - "http"
      - "queue"
~~~

Metadata property names are flattened:

~~~text
warehouse.client.retries.attempts
warehouse.client.retries.backoff
warehouse.client.modes
~~~

To suggest collection elements, a hint structure following metadata conventions and IDE support may be required. For instance, Spring Boot metadata permits hinting collection values via the `.values` suffix where applicable:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.modes.values",
      "values": [
        { "value": "http" },
        { "value": "queue" }
      ]
    }
  ]
}
~~~

Do not confuse the metadata hint name with a runtime property named `warehouse.client.modes.values`: the `.values` suffix here is **tooling semantics for suggesting elements**; the application still binds `warehouse.client.modes` into a List.

For complex object collections, prefer describing the typed configuration structure, defaults/validation, and YAML examples rather than trying to represent the entire schema with static value hints.

## 29. Adding Metadata for Properties Not Auto-Generated

Sometimes a property is read manually via `Environment#getProperty` or a library lacks a corresponding `@ConfigurationProperties` class. The processor may not generate metadata for that key.

Example:

~~~java
String region =
    environment.getProperty("warehouse.client.region", "apac");
~~~

To have the IDE suggest the key and values, you can declare it manually:

~~~json
{
  "properties": [
    {
      "name": "warehouse.client.region",
      "type": "java.lang.String",
      "description": "Deployment region for the warehouse integration.",
      "defaultValue": "apac"
    }
  ],
  "hints": [
    {
      "name": "warehouse.client.region",
      "values": [
        { "value": "apac" },
        { "value": "eu" },
        { "value": "us" }
      ]
    }
  ]
}
~~~

This is why `additional-spring-configuration-metadata.json` is not solely for deprecation: it can also supplement keys the processor cannot analyze.

However, note: adding metadata descriptions **does not make runtime automatically read new keys**. If code has no path handling `warehouse.client.region`, the IDE might suggest a useless property. Always keep metadata synchronized with source code and deployment docs.

## 30. Multi-Module Projects: Metadata Must Accompany the Right Artifact

Suppose the project is:

~~~text
root/
  warehouse-client-config/
    src/main/java/.../WarehouseClientProperties.java
  warehouse-client-starter/
    src/main/java/.../WarehouseClientAutoConfiguration.java
  order-service/
    src/main/java/.../OrderApplication.java
~~~

If `WarehouseClientProperties` sits in `warehouse-client-config`, the processor must run in that module (or via an intentional metadata packaging pipeline). Do not add the processor only to `order-service` expecting it to re-analyze Java sources already packaged in a dependency JAR.

Good workflow:

1. The module owning the properties class defines and generates metadata.
2. The appropriate module supplies additional metadata if hints/deprecation are needed.
3. The build packages metadata into a consumable artifact.
4. Downstream application IDEs can read metadata from the dependency.
5. CI tests verify the artifact contains the JSON file and critical entries.

With a starter comprising multiple JARs, metadata may exist in several different artifacts on the classpath. Do not manually merge or overwrite files sharing the same path without controlling packaging.

## 31. Watch Out for Duplicate Metadata Entries

A common maintenance mistake is when the processor already generated a property:

~~~json
{
  "name": "warehouse.client.endpoint",
  "type": "java.net.URI"
}
~~~

and a developer manually declares a full entry with the same name in additional metadata using a different type:

~~~json
{
  "name": "warehouse.client.endpoint",
  "type": "java.lang.String",
  "description": "Endpoint..."
}
~~~

Additional information fields may be processed during metadata merging, yet do not create **contradictory contracts** between source code and the JSON file. If the Java type is `URI`, metadata should not claim `String` just because YAML configuration is written as text.

Recommended:

- Prefer letting the processor generate names and types.
- Write additional metadata for hints, descriptions/deprecation, or properties that cannot be auto-generated.
- Add only the fields actually needed.
- Inspect the final JSON output after building.
- Review changes when renaming properties or Java types to avoid stale deprecations.

No matter how nice the suggestions look, they are pointless if the property does not exist at runtime or describes the wrong type.

## 32. How to Inspect Metadata After Building

A manual check procedure:

**Maven:**

~~~bash
./mvnw clean compile
~~~

**Gradle:**

~~~bash
./gradlew clean classes
~~~

Then locate the output metadata file of the module being built. If a JSON reader is available, check:

- Is there a `properties` entry for `warehouse.client.mode`?
- Are there `hints` for that exact key?
- Do values include `http` and `queue`?
- Does the old property `warehouse.client.base-url` have `deprecation`?
- Does `deprecation.replacement` match `warehouse.client.endpoint`?
- Does the warning/error level reflect actual runtime support status?
- Has metadata been packaged into the JAR?

Python example for checking the generated file (if Python is installed):

~~~python
import json
from pathlib import Path

path = Path(
    "target/classes/META-INF/"
    "spring-configuration-metadata.json"
)
data = json.loads(path.read_text(encoding="utf-8"))

hints = {
    item["name"]: item
    for item in data.get("hints", [])
}
assert "warehouse.client.mode" in hints

properties = {
    item["name"]: item
    for item in data.get("properties", [])
}
assert (
    properties["warehouse.client.base-url"]
    ["deprecation"]["replacement"]
    == "warehouse.client.endpoint"
)
~~~

This is a technical verification of the **metadata artifact**, not a replacement for Binder integration tests. If building with Gradle or if the file sits in another module, adjust the path accordingly.

Do not rely solely on whether the IDE displays autocomplete, because that experience also depends on whether the IDE has indexed the JAR and whether plugins support the metadata schema.

## 33. Unit Tests That Only Read the Object Do Not Prove Hints Work

Example:

~~~java
@Test
void readsMode() {
    var props = new WarehouseClientProperties(
        "http",
        URI.create("https://warehouse.example.invalid"),
        Duration.ofSeconds(3)
    );
    assertEquals("http", props.mode());
}
~~~

This test verifies the record works as a Java object; **it does not check**:

- Whether the annotation processor ran.
- Whether additional metadata was merged.
- Whether metadata contains hint values.
- Whether the IDE can read the JSON.
- Whether deprecation/replacement appears in the artifact.

A metadata test can read `META-INF/spring-configuration-metadata.json` from the classpath and parse JSON to verify required entries. A runtime binding test, meanwhile, needs a Spring Boot context/Binder.

Two separate test suites are needed because they verify **two distinct contracts**.

## 34. Testing Runtime for Old and New Keys

If you actively support a legacy key, you can use `ApplicationContextRunner` or `@SpringBootTest(properties=...)` to verify.

Logic example with two keys:

~~~java
@ConfigurationProperties(prefix = "warehouse.client")
public class WarehouseClientProperties {

    private URI baseUrl;
    private URI endpoint;

    @Deprecated
    @DeprecatedConfigurationProperty(
        reason = "Use endpoint instead.",
        replacement = "warehouse.client.endpoint"
    )
    public URI getBaseUrl() {
        return baseUrl;
    }

    @Deprecated
    public void setBaseUrl(URI baseUrl) {
        this.baseUrl = baseUrl;
    }

    public URI getEndpoint() {
        return endpoint;
    }

    public void setEndpoint(URI endpoint) {
        this.endpoint = endpoint;
    }

    public URI effectiveEndpoint() {
        return endpoint != null ? endpoint : baseUrl;
    }
}
~~~

Test scenarios to cover:

| Input | Expected effective value if preferring new key |
| --- | --- |
| Only `base-url=old` | old |
| Only `endpoint=new` | new |
| Both present | new |
| Neither key present | Missing endpoint; clear policy/validation needed |

Do not allow both properties to be declared without an explicit precedence rule. If the old key is no longer supported, tests should confirm the removed status and the error/migration behavior chosen by the application.

## 35. When Should `deprecation.level=error` Be Used?

A migration period usually starts with `warning` before moving to removed/`error` once runtime drops support. However:

- Do not set `error` merely to pressure users into renaming keys faster while runtime still supports them and the official policy is warning.
- Do not use `error` as a substitute for an actual runtime failure.
- If the old key has been removed, the reason message and upgrade guide must be clear.
- If the new key has a different unit/type, `replacement` may require data-conversion instructions rather than just renaming.

For example, old key `client.timeout-ms=3000` and new key `client.timeout=3s` have different representations. Merely declaring:

~~~json
"replacement": "client.timeout"
~~~

is not enough to guarantee users renaming the key while keeping `3000` will have the right unit. Description/reason and migration guides should clearly state the units or conversion rules of the new version.

**Replacement is a recommended path, not a guarantee that the two properties have completely identical semantics.**

## 36. Do Not Suggest Secrets as Concrete Values

Example property:

~~~yaml
payment:
  api-token: "..."
~~~

Do not create hints:

~~~json
{
  "name": "payment.api-token",
  "values": [
    { "value": "actual-production-token" }
  ]
}
~~~

Doing so can leak secrets in JARs, repositories, IDE indexes, or build logs.

For secrets, metadata can describe the provisioning source (environment/secret manager) and String type if needed, but **never** put real tokens/passwords into `values`/`defaultValue`/`description`.

Similarly, do not put internal URLs containing credentials, customer data, or secret parameters into `deprecation.reason` or `replacement`.

Metadata is a resource distributed with artifacts and must be treated as content readable by many tools.

## 37. Common Misconceptions

### 37.1. "Having `hints.values` means Spring only allows those values"

False. Hints are IDE suggestions. You must use enums/validation or business logic when real restrictions are required.

### 37.2. "Simply adding `spring-boot-configuration-processor` registers the bean"

False. The processor generates metadata at compile time; bean registration still requires `@EnableConfigurationProperties`, `@ConfigurationPropertiesScan`, or an appropriate registration method.

### 37.3. "Adding `replacement` automatically reads the old key into the new field"

False. Replacement is only migration information. Supporting aliases/fallbacks requires code or another runtime migration mechanism.

### 37.4. "`DeprecatedConfigurationProperty` makes startup fail automatically"

False. The annotation mainly serves metadata; fail-fast must come from real logic/runtime constraints.

### 37.5. "Putting `@Deprecated` on everything is enough"

Not quite. `@Deprecated` is a Java annotation. To include clear `deprecation.reason` and `replacement` in Spring Boot metadata, use `@DeprecatedConfigurationProperty` on the appropriate getter or additional metadata.

### 37.6. "Marking `error` means Spring Runtime throws an error"

False. `error` is a level in metadata, not an automatic validation rule.

### 37.7. "Placing the additional metadata file is all it takes"

Not necessarily. The processor must see the additional resource and merge it into output; the build must package the JSON. Inspect the final `spring-configuration-metadata.json` file.

### 37.8. "No IDE autocomplete means runtime cannot read the property"

Not necessarily. The IDE may not have indexed yet, the plugin may not support the provider, or metadata was not published. Runtime Binder and IDE metadata are two separate paths.

### 37.9. "Properties types changed, yet stale JSON metadata is harmless"

Stale metadata can suggest wrong keys, issue false warnings, and lead users to configure ineffective settings. When changing config APIs, update metadata and migration together.

### 37.10. "Put as much detail as possible into `reason` and `description`"

Never include secrets or unnecessary internal details. Short, accurate, actionable descriptions are much more helpful.

## 38. Checklist Before Releasing a New Configuration Key

1. Is the new key actually used by Java code?
2. Are prefixes and kebab-case consistent?
3. Is there a typed `@ConfigurationProperties` or another clear lookup path?
4. Is the bean properly registered?
5. Did the annotation processor run in the module owning the class?
6. Does the artifact contain `META-INF/spring-configuration-metadata.json`?
7. Do property `type`/`defaultValue`/`description` in metadata match runtime?
8. If choices are needed, do `hints.values` reflect real options?
9. If the key is an enum, are hand-written hints really needed?
10. If using `hints.providers`, does the target IDE support that provider?
11. If the old property is deprecated, does `reason` explain enough?
12. Does `replacement` contain the full and semantically accurate property name?
13. If runtime still accepts the old key, are fallback/priority tests present?
14. If the old key is removed, are migration guides and error reporting policies appropriate?
15. Are secrets excluded from metadata JSON?
16. Does CI test the metadata artifact and runtime binding independently?

## 39. Practice Exercise

**Problem:** configuration for an HTTP/queue client has `warehouse.client.transport` accepting `http` or `queue`. Old key `warehouse.client.base-url` was replaced by `warehouse.client.endpoint`. You want the IDE to suggest transport, warn on the old key, and state the replacement.

### Step 1 — Define the Java Type

~~~java
package example.warehouse;

import java.net.URI;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "warehouse.client")
public record WarehouseClientProperties(
        String transport,
        URI endpoint
) {}
~~~

And register:

~~~java
@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(WarehouseClientProperties.class)
class WarehouseClientConfiguration {}
~~~

### Step 2 — Enable the Configuration Processor

Gradle:

~~~groovy
dependencies {
    annotationProcessor 'org.springframework.boot:spring-boot-configuration-processor'
}
~~~

Or appropriate Maven compiler/processor configuration.

### Step 3 — Add Additional Metadata

Create `src/main/resources/META-INF/additional-spring-configuration-metadata.json`:

~~~json
{
  "hints": [
    {
      "name": "warehouse.client.transport",
      "values": [
        {
          "value": "http",
          "description": "Direct HTTP transport."
        },
        {
          "value": "queue",
          "description": "Queue-based transport."
        }
      ]
    }
  ],
  "properties": [
    {
      "name": "warehouse.client.base-url",
      "type": "java.net.URI",
      "description": "Legacy property name.",
      "deprecation": {
        "level": "warning",
        "reason": "Use endpoint instead of base-url.",
        "replacement": "warehouse.client.endpoint"
      }
    }
  ]
}
~~~

### Step 4 — Decide Runtime Compatibility

If the Java record only has `endpoint`, then **the old key is not automatically supported**. You must choose:

- Treat the contract as a breaking change, updating metadata level/reason accurately; or
- Retain legacy binding/fallback logic in a compatible structure.

Do not declare migration complete merely because JSON metadata has `replacement`.

### Step 5 — Clean Build and Verify

~~~bash
./gradlew clean classes
~~~

Or:

~~~bash
./mvnw clean compile
~~~

Inspect the output JSON and the module's JAR. Confirm hints and deprecation display properly. Then test runtime binding separately with configurations using the new key, old key, and both.

### Step 6 — Predict the Outcomes

| Scenario | Expected Outcome |
| --- | --- |
| IDE supports metadata, user types transport | Can suggest http/queue |
| User enters transport=unknown | Metadata does not reject it on its own |
| IDE encounters key base-url | Can display warning and replacement |
| Runtime only has record endpoint, YAML only has base-url | Does not automatically bind into endpoint |
| Runtime has old/new fallback code | Behavior determined by code |
| Metadata marks deprecation error | Does not imply a startup exception |
| No JSON in JAR | Downstream IDEs may lack hints |

## 40. Summary

Spring Boot configuration metadata has three highly useful capabilities for evolving a sustainable configuration API:

1. **Value suggestions** with `hints.values` and, when appropriate, `hints.providers`, helping YAML/properties authors discover choices.
2. **Marking deprecated keys** with deprecation metadata or `@DeprecatedConfigurationProperty` on getters of JavaBean-style properties types.
3. **Indicating replacement keys** via `deprecation.replacement`, accompanied by `reason` explaining the migration path.

Metadata is typically generated by `spring-boot-configuration-processor` and supplemented via `META-INF/additional-spring-configuration-metadata.json`. After building, inspect `META-INF/spring-configuration-metadata.json` in the artifact to ensure consumers receive accurate guidance.

**Most important takeaway:** metadata is **information for IDEs/tooling**, not a migration engine or runtime validation. To forbid bad values, use types/validation; to support old keys, write compatible binding/fallback paths; to remove old keys, announce breaking changes and test runtime behavior explicitly.
