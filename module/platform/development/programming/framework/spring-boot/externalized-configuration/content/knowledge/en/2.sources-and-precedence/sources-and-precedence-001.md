# Configuration Source Groups and How They Participate in Environment

## Learning Objectives

After this lesson, you will be able to identify the configuration source groups that Spring Boot uses, explain why the same key can have multiple values while the application only reads one effective value, and trace a property's path from a configuration file to `Environment`, `@Value`, or `@ConfigurationProperties`.

## 1. The Problem: One Application, Multiple Runtime Environments

Suppose an application runs on a developer's machine, in a testing environment, and in production. The Java code remains the same, but the HTTP port, external service addresses, timeouts, and connection details may differ. If you hardcode those values in the source code, every deployment would require modifying or recompiling the application.

Spring Boot allows you to move these values outside the source code (externalized configuration). A value such as `app.timeout` can appear in `application.yaml`, a file placed next to the application, an operating system environment variable, or a startup argument. Spring Boot organizes them into ordered configuration sources so the application uses a single, unified way to read them.

**Core point:** `Environment` is not a copy of a single `application.yaml` file. It is a unified interface for looking up properties from **multiple `PropertySource` instances in precedence order**. A source earlier in the lookup order can provide a value before those that come after it.

## 2. From Configuration Sources to Environment

A `PropertySource` represents a set of key–value pairs coming from a source: configuration files, environment variables, Java System properties, command-line arguments, and so on. `ConfigurableEnvironment` manages an ordered collection named `PropertySources`; application code usually only needs to depend on the `Environment` interface.

You can picture it as follows:

~~~text
application.yaml inside JAR ----┐
external application-prod.yaml -┤
OS environment variables -------┤
Java System properties ---------┼--> Ordered PropertySources --> Environment
command-line arguments ---------┤                                 |
other sources ------------------┘                                 +--> getProperty(...)
                                                                  +--> @Value(...)
                                                                  +--> @ConfigurationProperties
~~~

When `app.timeout` is needed, the lookup mechanism checks the sources in precedence order. If a higher-precedence source has a matching key, that value takes effect. Otherwise, it continues searching in subsequent sources. A key that only exists in the default file can still be used even when many other keys have been overridden by environment variables.

Therefore, you need to distinguish between two phenomena:

- **Key-level override:** two sources both define `app.timeout`; the value from the higher-precedence source wins.
- **Property supplementation:** source A defines `app.timeout` and source B defines `app.endpoint`; the application reads both through the same `Environment`.

This single-property lookup rule does not mean that every complex object or list has its elements merged together. Binding configuration into `List`, `Map`, and Java objects also follows the rules of the binder (`Binder`).

## 3. Common Configuration Source Groups

| Group | Example | Role |
| --- | --- | --- |
| Application default values | `SpringApplication.setDefaultProperties(...)` | Provides fallback values with low precedence. |
| Additional declarations from configuration code | `@PropertySource("classpath:extra.properties")` | Loads a properties file into `Environment` when the Spring context is initialized. |
| Config Data | `application.properties`, `application.yaml`, `application-prod.yaml`, imported files, configuration trees | Spring Boot's primary configuration source; supports file locations, profiles, and imports. |
| Special values generated by Spring | `random.*` | Generates random values for keys in the `random` namespace. |
| Process environment | `APP_TIMEOUT`, `SERVER_PORT` | Passes configuration from the operating system, container, or deployment platform. |
| Java System properties | `-Dapp.timeout=10s` | JVM-level configuration at startup. |
| Traditional web environment sources | JNDI, Servlet init parameters | Relevant when running in a Servlet container or supported application server. |
| Embedded configuration JSON | `SPRING_APPLICATION_JSON` or `spring.application.json` | Supplies multiple properties via a single JSON value. |
| Command-line arguments | `--app.timeout=5s` | Convenient overrides when running a specific application instance. |
| Testing and development sources | `@SpringBootTest(properties=...)`, `@DynamicPropertySource`, `@TestPropertySource`, Devtools | Serves testing or development scenarios; can change effective values compared to normal runs. |

These are **functional groups**, not files merged into one single file. In practice, one group can create multiple `PropertySource` instances. For example, individual configuration documents loaded from different locations and profiles can become separate sources in `Environment`.

### 3.1. Default Values and @PropertySource

`SpringApplication.setDefaultProperties(...)` is suitable for setting fallback values that other configuration sources can replace.

`@PropertySource` allows adding a properties file on a `@Configuration` class:

~~~java
@Configuration
@PropertySource("classpath:extra.properties")
class ExtraConfiguration {
}
~~~

However, `@PropertySource` is added while the ApplicationContext is refreshing (`refresh`). It may arrive **too late** for properties that Spring Boot reads very early, such as certain `logging.*` and `spring.main.*` settings. For application startup configuration, prefer the standard Config Data mechanism.

### 3.2. Config Data: Files, Profiles, and Imported Sources

`application.properties` or `application.yaml` files are the familiar starting point. Spring Boot automatically searches for these files on the classpath and in several external locations, including the working directory, `./config/`, and direct subdirectories of `./config/`. Configuration packaged inside the JAR is convenient for defaults; external configuration is convenient for deployment without modifying the JAR.

Profiles add configuration layers that only take effect under the appropriate conditions. When the `prod` profile is active, `application-prod.yaml` can override properties from `application.yaml`. When a profile is not activated, the file specific to that profile does not participate as an active configuration source.

In addition to auto-discovered files, `spring.config.import` lets a configuration document import another source:

~~~properties
spring.config.import=optional:file:./local-overrides.properties
~~~

`optional:` allows the file not to exist without causing startup to fail due to that missing location. Under the Config Data mechanism, imported content can override matching keys in the document that declared the import.

When a deployment platform mounts each secret as a file, you can import a configuration tree:

~~~properties
spring.config.import=optional:configtree:/run/secrets/
~~~

For example, the file `/run/secrets/db.password` creates the property `db.password`. You must protect access permissions on these files; placing values into `Environment` does not automatically encrypt or secure secrets.

### 3.3. Process- and Infrastructure-Provided Sources

Environment variables fit Docker, Kubernetes, and CI/CD well because they can change at runtime without repackaging the application. For example:

~~~bash
export SERVER_PORT=9090
export APP_TIMEOUT=15s
~~~

With `@ConfigurationProperties`, relaxed binding rules connect Java configuration names with environment variable names. To convert a canonical property name into an environment variable, replace dots with underscores, remove dashes, and convert to uppercase: `spring.main.log-startup-info` corresponds to `SPRING_MAIN_LOGSTARTUPINFO`. Avoid guessing variable names by personal habit when a property contains dashes.

Java System properties are a different group from operating system environment variables:

~~~bash
java -Dapp.timeout=10s -jar app.jar
~~~

Spring Boot's `--key=value` arguments are a separate source:

~~~bash
java -jar app.jar --app.timeout=5s
~~~

By default, Spring Boot adds these command-line options into `Environment`. A program can disable that mechanism via `SpringApplication.setAddCommandLineProperties(false)`, though most applications keep the default.

`SPRING_APPLICATION_JSON` is used when you need to pass multiple keys in a single variable:

~~~bash
SPRING_APPLICATION_JSON='{"app":{"timeout":"8s","region":"apac"}}' java -jar app.jar
~~~

The JSON values become properties such as `app.timeout` and `app.region`. A JSON `null` value cannot be used to "delete" a value from a lower-precedence source, because the property resolver treats `null` as having no value.

### 3.4. Context-Dependent Sources

`RandomValuePropertySource` primarily serves expressions in the `random.*` group, not as a replacement for securely managed secrets. JNDI and Servlet init parameters may appear in web applications running under a corresponding container; many standalone executable-JAR Spring Boot applications will not use them.

In tests, properties declared directly on test annotations and `@DynamicPropertySource` can add sources with dedicated precedence. Devtools also has global configuration settings when enabled. When inspecting the `PropertySource` list during a test run, do not assume the source order and names must match a production run identically.

## 4. Precedence Order: What Happens When Multiple Sources Have the Same Key?

For **a typical Spring Boot 3.3 application**, you can read the following order from **lowest to highest precedence**:

1. Default properties provided via `SpringApplication.setDefaultProperties`.
2. `@PropertySource` annotations on `@Configuration` classes.
3. Config Data: `application.properties`/YAML, profile-specific files, and related imports.
4. `RandomValuePropertySource` (only relevant to `random.*` keys).
5. OS environment variables.
6. Java System properties.
7. JNDI attributes from `java:comp/env`.
8. `ServletContext` init parameters.
9. `ServletConfig` init parameters.
10. Properties from `SPRING_APPLICATION_JSON`.
11. Command-line arguments `--...`.

Test-specific sources and Devtools can sit at higher precedence levels in their respective contexts. In the list above, items **lower down** can override items **higher up**. Conversely, when iterating over `ConfigurableEnvironment.getPropertySources()` in Java, the source checked first appears first in the iteration list; do not confuse the two directions of presentation.

Even within the Config Data group, there is precedence. In the common case, when the same key is declared in multiple places, the order from lowest to highest is:

1. `application.properties`/YAML packaged **inside the JAR**.
2. `application-{profile}.properties`/YAML packaged **inside the JAR**.
3. `application.properties`/YAML located **outside the JAR**.
4. `application-{profile}.properties`/YAML located **outside the JAR**.

Search locations, location groups, multiple active profiles, and `spring.config.import` have their own detailed rules. The four-level list above helps visualize the common case and does not replace the full Config Data algorithm. If both `.properties` and YAML exist at the same location, Spring Boot prefers `.properties`; choose one format consistently to avoid confusion.

## 5. Walkthrough Example: Five Sources Participating in One Environment

Suppose the application has a default file `src/main/resources/application.yaml`:

~~~yaml
app:
  greeting: "Hello from JAR"
  retries: 2
  endpoint: "https://api.example.test"
  feature-enabled: false
~~~

When deploying to production, place `./config/application-prod.yaml` next to where the application runs:

~~~yaml
app:
  greeting: "Hello from external file"
  retries: 5
  feature-enabled: true
~~~

Then launch it in a Unix-style shell:

~~~bash
APP_GREETING='Hello from env var' java -Dapp.retries=8 -jar app.jar --spring.profiles.active=prod --app.greeting='Hello from CLI'
~~~

Assuming the current working directory contains `./config/application-prod.yaml` and no other sources intervene, the result is:

| Property | Effective Value | Winning Source |
| --- | --- | --- |
| `app.greeting` | `Hello from CLI` | Command-line argument, overriding the environment variable and both files. |
| `app.retries` | `8` | Java System property, overriding the value `5` in the external file. |
| `app.endpoint` | `https://api.example.test` | Default file inside the JAR; no source overrides this key. |
| `app.feature-enabled` | `true` | External `application-prod.yaml` file, because the `prod` profile is active. |

Four values can come from **three different sources in the same run**. Spring Boot does not force picking a single "winning" file; it resolves each property individually according to source precedence.

If you omit the `--app.greeting` argument, the `APP_GREETING` variable wins for `app.greeting`. If you also omit that environment variable, the value in `application-prod.yaml` takes effect. If you remove the `prod` profile, the profile-specific file is no longer loaded in the manner above.

## 6. Java Code Reading Values from Environment

Use `Environment` when you need to query one or a few keys directly:

~~~java
import org.springframework.core.env.Environment;
import org.springframework.stereotype.Service;

@Service
public class GreetingService {
    private final Environment environment;

    public GreetingService(Environment environment) {
        this.environment = environment;
    }

    public String greeting() {
        return environment.getProperty("app.greeting", "Hello");
    }
}
~~~

If your goal is a strongly typed group of configuration settings, `@ConfigurationProperties` is a better fit. With a Java record:

~~~java
import java.net.URI;
import org.springframework.boot.context.properties.ConfigurationProperties;

@ConfigurationProperties(prefix = "app")
public record AppProperties(
        String greeting,
        int retries,
        URI endpoint,
        boolean featureEnabled) {
}
~~~

Register this record using `@ConfigurationPropertiesScan` on the application or `@EnableConfigurationProperties(AppProperties.class)` in configuration. The binder reads effective values from `Environment` and converts them to the appropriate types; for example, `feature-enabled` is bound to `featureEnabled`. `@Value("${app.greeting:Hi}")` can also read a single value, but it is less convenient than `@ConfigurationProperties` for structured groups of properties.

Note: `Environment` resolves configuration when read, but changing `application.yaml` after the application is already running does not mean Spring Boot automatically reloads the configuration or updates all beans. Dynamic refresh requires a dedicated solution.

## 7. Inspecting and Identifying the Winning Source

When a property does not have the expected value, check **the key name, which sources are actually loaded, the active profiles, and the precedence order**.

You can iterate over **source names** during development without printing sensitive values:

~~~java
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.core.env.ConfigurableEnvironment;
import org.springframework.core.env.PropertySource;
import org.springframework.stereotype.Component;

@Component
class PropertySourceNames implements ApplicationRunner {
    private final ConfigurableEnvironment environment;

    PropertySourceNames(ConfigurableEnvironment environment) {
        this.environment = environment;
    }

    @Override
    public void run(ApplicationArguments args) {
        for (PropertySource<?> source : environment.getPropertySources()) {
            System.out.println(source.getName());
        }
    }
}
~~~

Sources are iterated in `Environment`'s lookup order. Source names can contain clues about file locations or source types, helping locate where a configuration is set. For applications needing monitoring, Spring Boot Actuator provides the `env` and `configprops` endpoints if configured/enabled; since they may contain sensitive information, restrict access and use value masking. Never log passwords, tokens, or the entire `Environment`.

To inspect Config Data loading, you can enable TRACE-level logging for `org.springframework.boot.context.config` in a development environment. This is useful when an external file, a profile, or an import is not loaded as expected.

## 8. Common Misconceptions

- **"Spring Boot only reads application.yaml."** False: that file is only one source group; environment variables, System properties, CLI arguments, and other sources also participate.
- **"A higher-precedence source replaces the entire lower-precedence source."** False for single-property lookup: the higher source only wins for keys it provides; missing keys are still looked up in lower sources.
- **"Just having application-prod.yaml exist makes it active."** You must activate the corresponding profile and place the file in a location that Spring Boot loads.
- **"@PropertySource is equivalent to application.properties in load timing."** Not quite: some startup properties are already processed before `@PropertySource` participates.
- **"Environment variable names always replace both dots and dashes with underscores."** Under Spring Boot's binding rules, dashes are **removed**, while dots are converted to underscores and letters are uppercased.
- **"spring.config.location only adds one location."** This property replaces the default search locations; use `spring.config.additional-location` if you want to add locations while keeping the defaults. These location keys must be supplied early enough, such as via environment variables, JVM properties, or CLI arguments.
- **"You can use null in SPRING_APPLICATION_JSON to clear an old value."** `null` does not override a value from a lower-precedence source under standard property resolution.
- **"Changing the config file on disk makes beans immediately receive the new value."** Not automatically; that is configuration refresh, which differs from aggregating sources at startup.

## 9. Hands-On Practice

1. Create `application.yaml` with `app.mode: default` and `app.timeout: 30s`. Run with `APP_MODE=staging`, then add `--app.mode=demo`. Query both keys via `Environment`; explain why `app.mode` changes while `app.timeout` stays the same.
2. Activate the `prod` profile, and create `./config/application-prod.yaml` overriding `app.timeout`. Add `-Dapp.timeout=12s` to observe which source takes effect. Remove each source in turn to see the value fall back to the configuration layer underneath.
3. List `PropertySource` names during a normal run and during a test run. Observe the differences in sources and avoid printing values of sensitive keys.

## 10. Key Takeaways

`Environment` is the unified access point for properties drawn from multiple ordered `PropertySource` instances. Config Data provides file-, location-, profile-, and import-based configuration; the OS environment, JVM, and command-line arguments allow adjustments per deployment. When keys collide, source order determines the effective value; when a source lacks a key, lower sources continue supplying values. Understanding these three ideas will help you explain most cases of "why did the application read this configuration value?".
