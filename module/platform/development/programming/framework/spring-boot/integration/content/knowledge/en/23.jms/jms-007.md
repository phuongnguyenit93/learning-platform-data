# Queues, Topics, and Durable Subscriptions in JMS with Spring Boot

In a Spring Boot system, the same `OrderCreated` event may need to reach multiple capabilities: billing, warehouse, email, and analytics. Conversely, a `GenerateInvoice` request typically needs **only one worker** to execute it. JMS (Java Message Service, using the `jakarta.jms` API in modern Spring Boot) provides two fundamental destination types to model these two needs: **queue** and **topic**. For topics, a **durable subscription** lets a logical processing group receive messages published while that group was temporarily stopped.

This lesson sits within `SPRING_BOOT_INTEGRATION`: organizing system integration in Spring Boot across HTTP clients, databases, caches, message brokers, and Spring Integration adapters. We focus on event publishing/receiving contracts, JMS configuration in Spring Boot, retaining messages during disconnects, duplicate handling, errors, testing, and operational observability. Examples use Apache ActiveMQ Artemis; **queue/topic/durable mechanics are JMS concepts**, whereas address names, queue auto-creation policies, storage, and DLQs depend on the broker.

## 1. Framing the problem: one job or many interested parties?

Suppose `order-service` publishes an event when a customer completes an order:

~~~json
{
  "eventId": "evt-2026-1042",
  "eventType": "OrderCreated",
  "eventVersion": 1,
  "orderId": "ORD-1042",
  "occurredAt": "2026-11-21T03:15:00Z"
}
~~~

Three business flows have distinct needs:

- **Invoicing:** each invoice-generation command should be handled by one of the workers. With four workers, all four can share the pending commands.
- **Order event processing:** both billing service and warehouse service need to know a new order appeared. Each service must receive its own copy of the event.
- **Receiving events after recovery:** warehouse service occasionally undergoes 20-minute maintenance. When it comes back up, it still needs to receive new events emitted during that gap.

Queues solve the first case. Topics solve the second case. **Topics with durable subscriptions** solve the additional requirement in the third case.

Terms to distinguish:

| Term | Meaning |
| --- | --- |
| **Producer** | Application sending messages to the broker |
| **Broker** | System that receives, routes, stores, and delivers messages per policy |
| **Destination** | Logical address for sending/receiving: queue or topic |
| **Consumer** | Currently active message-receiving session/client |
| **Subscription** | Receiving relationship on a topic; can be temporary or durable |
| **Durable subscription** | Subscription remembered by the broker that accumulates matching messages when no consumer is connected |

**A consumer is a running receiver; a subscription is a logical receiving interest/stream on a topic.** These two concepts are not identical. A durable subscription continues to exist when its consumer stops.

## 2. Queue: point-to-point and competing consumers

Queues suit *work distribution*. A producer sends each message to a queue; the broker dispatches one processing attempt to **one consumer** on that queue at a time. When multiple consumers read the same queue, they act as *competing consumers*, sharing work from a single stream.

~~~mermaid
flowchart LR
    P["order-service"] --> Q[("Queue: invoice.commands")]
    Q --> C1["invoice-worker A"]
    Q --> C2["invoice-worker B"]
    Q --> C3["invoice-worker C"]
~~~

If the queue receives 100 commands and has three workers, the goal is **100 total successfully processed commands**, not 100 commands per worker. How many commands each worker gets depends on the broker, consumer state, prefetch/credit mechanics, latency, and load.

Characteristics to remember:

- Queues generally hold pending messages when no consumer is active; capacity limits, lifetimes, and survival across broker restarts depend on delivery mode and storage configuration.
- Adding consumers increases throughput for **the same kind of work**. A typical example is multiple replicas of `invoice-worker` reading `invoice.commands`.
- A message can be **redelivered** if a consumer fails before acknowledgment/commit. "One consumer processes at a time" does not mean "processed only once under all circumstances."
- Do not assume business completion order always matches send order when multiple consumers, message priorities, retries, or redeliveries are involved.
- If both billing and warehouse must receive the same message, having both services read **one queue** is the wrong model: they will compete for messages. Use a topic or fan out to separate queues.

**Good fits:** PDF generation requests, background jobs, sending a specific email, reconciling a transaction, reprocessing a record.

## 3. Topic: publish/subscribe and copies per subscription

Topics suit *event fan-out* (broadcasting an event to multiple interested groups). A single producer publish can deliver a copy of the message to **each eligible subscription**.

~~~mermaid
flowchart LR
    O["order-service"] --> T[("Topic: orders.events")]
    T -->|Billing subscription| B["billing-service"]
    T -->|Warehouse subscription| W["warehouse-service"]
    T -->|Analytics subscription| A["analytics-service"]
~~~

If three subscriptions exist and match any selectors when the message is sent, each subscription has its own delivery stream. Three logical copies do not mean every process inside one subscription gets a copy: distribution **within a subscription** depends on subscription type and consumer count.

### Non-durable subscription

A **non-durable** subscription lives only for the presence of that consumer/subscription. When the consumer stops and the subscription becomes inactive, the broker has no obligation to retain subsequent messages waiting for its return.

Example:

1. Dashboard connects to topic `orders.events` and receives events E1 and E2.
2. Dashboard disconnects; producer emits E3 and E4.
3. Dashboard reconnects; it receives only new messages such as E5 and **does not automatically receive missed E3 and E4**.

This model fits live monitoring dashboards or data that can be reloaded from another source. If missing E3/E4 corrupts business data, use a durable subscription or a separate storage/replay mechanism.

### What if there are multiple consumers on a topic?

Two independent **non-durable** consumers watching a topic each receive a copy of an event. Two consumers belonging to **one shared subscription** share the load across that subscription stream. Scaling replica counts must therefore be designed around *logical subscriptions*, not just TCP connection counts.

## 4. Durable subscription: subscriptions that persist while consumers are offline

A durable subscription binds a stable identity to a subscription on a topic. Once the subscription **has been created**, the broker can retain matching messages published while no consumer is connected and deliver them when a valid consumer reconnects.

~~~mermaid
sequenceDiagram
    participant B as Billing consumer
    participant R as JMS broker
    participant P as order-service
    B->>R: Create durable subscription billing-orders-v1
    B--xR: Disconnect
    P->>R: Publish E1
    P->>R: Publish E2
    Note over R: Retain E1 and E2 for subscription<br/>unless expired by TTL or evicted by policy
    B->>R: Reconnect with matching subscription
    R-->>B: Deliver E1, E2
    B->>R: Commit / acknowledge processing
~~~

In the diagram, retention is not infinite: capacity, expiration, quota eviction, paging policies, and recovery depend on configuration.

### Durable subscription lifecycle

1. **Create subscription:** the application registers a named subscription on a topic; the broker records its identity and attributes (such as selector, `noLocal`).
2. **Connected:** the broker delivers matching events to the consumer and waits for acknowledgment per session/transaction mode.
3. **Temporarily disconnected:** the logical subscription stays intact. Matching messages sent after creation can be retained for later delivery.
4. **Reconnect:** the application reconnects with the same subscription identity; the broker delivers remaining valid backlog.
5. **Unsubscribe:** an explicit `unsubscribe` operation deletes the durable registration and typically discards unprocessed backlog. **Stopping the application is not unsubscribing.**

Important boundaries:

- **Durable is not retroactive.** Messages sent **before the subscription existed** do not automatically appear in a newly created subscription's backlog.
- **Durable differs from persistent delivery.** Durable preserves subscription identity and backlog while consumers are offline; `DeliveryMode.PERSISTENT` expresses the broker storage guarantee to survive broker restarts per JMS and vendor implementation. To expect messages to survive a broker restart, you need both the right delivery mode **and** a properly configured, operated persistent broker store.
- **TTL and broker policies still apply.** Messages that expire, hit quotas, or get moved by admin policies may not be there upon reconnect.
- **Selectors apply per subscription.** If a subscription only matches `eventType = 'OrderCreated'`, other event types never enter its backlog.
- **No exactly-once effect guarantee.** Events can still arrive again after crashes/rollbacks; consumers need deduplication.

### Subscription identity, client ID, and subscription name

With an **unshared durable subscription**, a common configuration uses:

- `clientId`: JMS client/connection identifier, e.g., `billing-service-prod`.
- `subscription`: durable subscription name, e.g., `billing-orders-v1`.
- `destination`: topic watched by the subscription, e.g., `orders.events`.

Keep identifiers stable across restarts. Changing `clientId` or subscription name creates **a brand-new subscription**, stranding old backlog in the previous one. Furthermore, a single `clientId` cannot be used simultaneously by multiple active connections under JMS constraints; two replicas opening connections with the same `clientId` will collide.

Topic, message selector, and other properties tied to a durable subscription must be managed as stateful configuration. Changing them may require closing consumers, unsubscribing/recreating the subscription, and handling the old backlog depending on the broker.

## 5. Comparing queues, non-durable topics, and durable topics

| Criterion | Queue | Topic + non-durable subscription | Topic + durable subscription |
| --- | --- | --- | --- |
| Goal | Share work across workers | Broadcast to currently active consumers | Deliver to each logical subscription, even across offline periods |
| How many groups receive a message? | One shared consumer group on the queue | Each active matching subscription | Each matching durable subscription plus active subscriptions |
| Two workers reading the same stream | Compete for individual messages | Two independent subscriptions receive two copies | Unshared: at most one active consumer/subscription; shared: multiple consumers share load |
| Consumer offline | Queue retains pending per policy | Does not retain messages sent while absent | Broker retains for existing subscription within policy/TTL limits |
| Requires stable subscription name? | No | Usually no | Yes |
| Example | `invoice.commands` | Live event dashboard | `billing-orders-v1`, `warehouse-orders-v1` |

Both a *queue* and a *durable topic subscription* can accumulate backlog, yet their routing differs: a queue has **one shared work stream**; a topic has **an independent delivery stream per subscription**. Never assume the two models are equivalent merely because both hold backlogs.

## 6. Configuring Spring Boot with ActiveMQ Artemis

Examples below use **Spring Boot 3+**, Jakarta JMS, and Artemis in external broker mode. The configuration is concise to highlight destination and subscription choices; in production, add security, retries, observability, and broker policies.

### 6.1. Dependencies and broker connection

In Maven, add the Artemis starter (version managed by Spring Boot dependency management):

~~~xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-artemis</artifactId>
</dependency>
~~~

Example `application.yml`:

~~~yaml
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    user: ${ARTEMIS_USER}
    password: ${ARTEMIS_PASSWORD}
~~~

Ports, credentials, and whether destinations auto-create must match the actual broker. Examples assume the broker is configured to recognize `invoice.commands` as a queue and `orders.events` as a topic under corresponding JMS routing. In Artemis, JMS queues typically map to **anycast** and JMS topics to **multicast**; verify this mapping if reusing an address name.

### 6.2. Separating factories for queues and topics

`@JmsListener` builds consumers via a listener container factory. Do not guess whether destinations default to topics: set `pubSubDomain` explicitly.

~~~java
import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.annotation.EnableJms;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.core.JmsTemplate;

@Configuration
@EnableJms
public class JmsConfig {

    @Bean
    public DefaultJmsListenerContainerFactory queueListenerFactory(
            ConnectionFactory connectionFactory) {

        var factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setPubSubDomain(false);      // Queue
        factory.setSessionTransacted(true);  // Roll back JMS when listener throws
        factory.setConcurrency("2-4");
        return factory;
    }

    @Bean
    public DefaultJmsListenerContainerFactory liveTopicListenerFactory(
            ConnectionFactory connectionFactory) {

        var factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setPubSubDomain(true);       // Topic
        factory.setSessionTransacted(true);
        // subscriptionDurable not enabled: receives only while actively subscribed.
        return factory;
    }

    @Bean
    public DefaultJmsListenerContainerFactory durableTopicListenerFactory(
            ConnectionFactory connectionFactory) {

        var factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setPubSubDomain(true);
        factory.setSubscriptionDurable(true);
        factory.setClientId("billing-service-prod");
        factory.setSessionTransacted(true);
        factory.setConcurrency("1");        // Unshared durable subscription
        return factory;
    }

    @Bean
    public JmsTemplate topicJmsTemplate(ConnectionFactory connectionFactory) {
        var template = new JmsTemplate(connectionFactory);
        template.setPubSubDomain(true);
        template.setExplicitQosEnabled(true);
        template.setDeliveryPersistent(true);
        return template;
    }
}
~~~

Clarifying lines that are easy to misread:

- `setPubSubDomain(false)` selects queues; `true` selects topics on that factory/template.
- `setSubscriptionDurable(true)` makes the topic listener a durable subscriber using the name declared in `@JmsListener(subscription = ...)`.
- `setClientId(...)` sets a stable identifier for this durable listener. Applications with multiple durable subscriptions/connections, connection pooling/caching, or multiple instances must design client IDs carefully to avoid collisions.
- `setConcurrency("1")` keeps one active consumer for an **unshared durable subscription**. On queues, concurrency can scale up because consumers share work.
- `setSessionTransacted(true)` turns processing errors into rollbacks/redeliveries inside the **local JMS transaction**. It does not automatically pull SQL writes into that transaction.
- `setExplicitQosEnabled(true)` instructs `JmsTemplate` to apply our chosen delivery mode; calling `setDeliveryPersistent(true)` without this line can leave the template using provider defaults.

This configuration illustrates **one instance** of billing service. Never launch two instances using the same `clientId = billing-service-prod` in unshared mode; the shared durable section in section 7 shows the valid way to scale.

### 6.3. Publishing events to a topic

The producer injects `topicJmsTemplate`, sends JSON as a `TextMessage` via the default `String` converter, and attaches properties for selector filtering.

~~~java
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderEventPublisher {

    private final JmsTemplate topicJmsTemplate;

    public OrderEventPublisher(
            @Qualifier("topicJmsTemplate") JmsTemplate topicJmsTemplate) {
        this.topicJmsTemplate = topicJmsTemplate;
    }

    public void publishOrderCreated(String jsonPayload) {
        topicJmsTemplate.convertAndSend(
            "orders.events",
            jsonPayload,
            message -> {
                message.setStringProperty("eventType", "OrderCreated");
                message.setStringProperty("eventVersion", "1");
                return message;
            }
        );
    }
}
~~~

Setting `eventType` as a JMS message property lets JMS selectors filter without parsing JSON bodies. The JSON contract still needs `eventId` (deduplication key), `eventVersion` (schema version), and business fields.

**Transaction note:** if an order commits to SQL before calling `publishOrderCreated`, the app can crash in between and lose the event; if published before SQL commits, consumers may receive an event for a rolled-back change. When you need reliable coordination between database and broker, consider a **transactional outbox** or deliberate distributed-transaction architecture. JMS `sessionTransacted` alone does not close this gap.

### 6.4. Receiving from queues, live topics, and durable topics

In production these listeners typically live in separate services. If placing them together in one app for testing, keep their distinct purposes and identities clear.

~~~java
import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class ExampleJmsListeners {

    @JmsListener(
        destination = "invoice.commands",
        containerFactory = "queueListenerFactory"
    )
    public void generateInvoice(String commandJson) {
        // Validate command, persist result, and process idempotently.
        System.out.println("Invoice command: " + commandJson);
    }

    @JmsListener(
        destination = "orders.events",
        containerFactory = "liveTopicListenerFactory"
    )
    public void updateLiveDashboard(String eventJson) {
        // Dashboard tolerates missing events while offline.
        System.out.println("Live event: " + eventJson);
    }

    @JmsListener(
        destination = "orders.events",
        subscription = "billing-orders-v1",
        selector = "eventType = 'OrderCreated'",
        containerFactory = "durableTopicListenerFactory"
    )
    public void updateBilling(String orderEventJson) {
        // In production: parse eventId, insert unique inbox key,
        // update billing, commit DB; on failure, throw an exception.
        System.out.println("Billing event: " + orderEventJson);
    }
}
~~~

`System.out.println` merely illustrates message delivery; real business logic must delegate to a transactional, duplicate-safe service. If `updateBilling` throws an exception in a transacted session, the broker can redeliver per policy. Never catch exceptions, log, and return normally if you expect broker retries: returning normally typically commits the JMS session.

When publishing to a **queue**, use a template configured with `pubSubDomain(false)` or pass an explicit `Queue`. Never use `topicJmsTemplate` above to send commands to `invoice.commands`: it interprets destination names in the topic domain.

## 7. Scaling consumers: unshared vs. shared durable

In multi-replica deployments, a common question is: "Can we scale `billing-service` from one pod to three pods reading the same durable subscription?"

### Unshared durable subscription

With an *unshared durable subscription*, at most one active consumer may exist for that subscription at a time. Two instances sharing `clientId` collide at the JMS connection layer. If each instance uses a distinct `clientId` or subscription name, the broker creates **three independent durable subscriptions**, yielding three copies of every event and triple execution. That is usually wrong when trying to scale **one** logical subscriber.

### Shared durable subscription (JMS 2.0 and above)

A *shared durable subscription* lets multiple consumers share a durable subscription when supported by the broker and driver. Messages in the subscription are load-balanced across participating consumers rather than duplicated per replica.

~~~mermaid
flowchart LR
    P["order-service"] --> T[("Topic: orders.events")]
    T --> SD[("Shared durable: billing-orders-v2")]
    SD --> B1["billing pod A"]
    SD --> B2["billing pod B"]
    SD --> B3["billing pod C"]
    T --> WD[("Durable: warehouse-orders-v1")]
    WD --> W["warehouse-service"]
~~~

To use shared durable instead of the unshared example in section 6, configure the factory as follows:

~~~java
@Bean
public DefaultJmsListenerContainerFactory sharedDurableTopicListenerFactory(
        ConnectionFactory connectionFactory) {

    var factory = new DefaultJmsListenerContainerFactory();
    factory.setConnectionFactory(connectionFactory);
    factory.setPubSubDomain(true);
    factory.setSubscriptionDurable(true);
    factory.setSubscriptionShared(true);
    factory.setSessionTransacted(true);
    factory.setConcurrency("2-4");
    return factory;
}
~~~

Listeners share the same logical subscription name:

~~~java
@JmsListener(
    destination = "orders.events",
    subscription = "billing-orders-v2",
    containerFactory = "sharedDurableTopicListenerFactory"
)
public void handleOrderEvent(String json) {
    // Process event using eventId to guard against redelivery/duplicates.
}
~~~

This is an **alternative**, not something to enable alongside the unshared `billing-orders-v1` listener expecting only one copy; doing both creates two logical subscriptions.

For shared durable subscriptions, verify whether `clientId` should be set or omitted and how your JMS provider resolves subscription identity. Never copy a static `clientId` from an unshared setup across all replicas: JMS still enforces unique client IDs across active connections. Test with your actual driver, connection pool, and broker before scaling replicas.

If your broker/driver lacks the shared durable support you need, you can route from the topic into a **dedicated worker queue** via broker-side routing; note that this depends on broker platform capabilities rather than portable JMS syntax.

## 8. Reliability: delivery mode, transactions, redelivery, and idempotency

JMS supports **PERSISTENT** and **NON_PERSISTENT** delivery modes. Keep these concepts separate:

| Mechanism | Solves | Does NOT solve by itself |
| --- | --- | --- |
| Durable subscription | Retains subscription registration and matching backlog while offline | Infinite retention or messages sent before subscription creation |
| Persistent delivery | Requests broker durable message storage per provider contract | Exactly-once business execution on the consumer |
| JMS local transaction | Commits/rolls back sends/receives within one JMS session | Atomic commits with an external database |
| Redelivery/DLQ | Retries or isolates failing messages per broker policy | Preventing double execution if side effects already occurred |
| Inbox/idempotency | Prevents reapplying the same business event | Replacing brokers and transactions entirely |

### Why can duplicates arrive?

A consumer commits SQL successfully, then dies before committing the JMS session. Without confirmation that JMS delivery completed, the broker **can redeliver**. If the consumer increments revenue a second time, business state corrupts even though the broker behaved correctly.

The pragmatic solution is an **immutable `eventId`** from the producer and an inbox table with a unique key in the database:

~~~sql
CREATE TABLE processed_events (
    subscriber_id VARCHAR(120) NOT NULL,
    event_id      VARCHAR(120) NOT NULL,
    processed_at  TIMESTAMP NOT NULL,
    PRIMARY KEY (subscriber_id, event_id)
);
~~~

Billing service's SQL transaction should execute:

1. Start a database transaction.
2. Insert `(billing-orders-v1, eventId)` into the inbox. If already present, treat as duplicate and return safely.
3. Update billing/invoice state within **the same database transaction**.
4. Commit SQL; once the handler returns normally, the JMS session commits.

If an error happens mid-way, roll back SQL and let JMS roll back/redeliver. JMS commit and SQL commit remain non-atomic with each other, yet redeliveries are blocked by the inbox key. This gives near-"processed once" business effects for protected state; external HTTP calls or downstream systems need their own idempotency keys or compensation.

Persistent poison messages must not spin forever. Configure retry/backoff and a **dead-letter queue (DLQ)** per broker capabilities; retain `eventId`, error code, timestamp, delivery count, and correlation ID for diagnosis, data fixes, and controlled replay.

## 9. Selectors, time to live, and data contract versions

### JMS selectors

Selectors filter messages by **JMS headers/properties**, not arbitrary JSON fields:

~~~java
@JmsListener(
    destination = "orders.events",
    subscription = "billing-created-v1",
    selector = "eventType = 'OrderCreated' AND eventVersion = '1'",
    containerFactory = "durableTopicListenerFactory"
)
public void handleCreated(String json) {
    // ...
}
~~~

Here `eventType` and `eventVersion` must be attached by the producer as matching message properties. If `eventVersion` is set as a `String`, compare against `'1'`; if set as an integer, use a numeric expression. Type or name mismatches prevent matching, and the subscription receives nothing.

Changing the selector on an existing durable subscription with backlog is a **breaking contract change**. Plan for queued messages, choose whether to keep or rename the subscription, and check how your broker handles re-subscription.

### TTL and backlog

TTL (time to live) sets how long a message remains valid before expiration. If an SLA allows two hours of consumer downtime, size TTL, quotas, and storage accordingly. A JMS TTL of zero means **no automatic expiration**, though broker quotas/policies may still evict messages.

Backlog storage scales with subscription count. At 50 events/second, 2 hours of billing downtime builds roughly **360,000 pending events** for that single subscription before factoring in selectors, TTL, compression, and storage overhead. If three durable subscriptions go offline simultaneously, each accumulates its own backlog.

### Schemas and versioning

Successful topic delivery does not guarantee consumers understand the payload. Include `eventType`, `eventVersion`, `eventId`, timestamps, and versioned payload fields. When extending schemas, preserve backward compatibility for older consumers or establish explicit migration flows. Never rename subscriptions merely to "hide" schema-compatibility bugs, as that strands older backlogs.

## 10. Operations and production observability

A Spring Boot JMS system requires visibility across **publishing**, **consuming**, and **broker state**:

| Symptom | Questions to check | Typical resolution |
| --- | --- | --- |
| Producer sends OK, consumer gets nothing | Sending to queue or topic? When was subscription created? Does selector match? | Check `pubSubDomain`, destination, subscription name, and message properties |
| Consumer restarts and missed offline events | Is subscription truly durable? Created before events? TTL/store intact? | Verify durable identity, backlog, broker persistence, and expiration |
| `InvalidClientIDException` or connection error on scale | Do two active connections share a client ID? | Design shared durable or unique connection identities |
| Same event arrives repeatedly | Redelivery after rollback/crash? Multiple logical subscriptions? | Audit `eventId`, inbox unique keys, and broker subscription list |
| Backlog growing continuously | Publish rate exceeds processing? Consumer errors? Selectors/poison messages? | Monitor depth, oldest message age, error rates; scale deliberately |
| DLQ growing | Malformed schema payloads, external dependency errors, or exhausted retries? | Classify causes, record diagnostics, and run controlled replay |
| Wrong business ordering | Multiple consumers, retries, or message priority? | Process by business key, sequence/version, or limit concurrency |

Useful metrics: ready/pending message counts per queue/subscription, oldest message age, connected consumer count, enqueue/dequeue rates, redeliveries, DLQ counts, processing latency, schema parse errors, and downstream dependency failures. Distinguish **topic name**, **subscription name**, and **client ID** in logs, metrics, and traces; logging only `orders.events` obscures which subscriber is lagging.

Security note: omit sensitive payloads and credentials from default logs. Use `eventId`, `orderId` (per data policy), and `JMSCorrelationID` to correlate processing steps. Broker dashboards should alert on backlog thresholds and message age, not message counts alone.

## 11. Minimum test scenarios

Run tests against a real Artemis broker or a test container broker. Verify **observable behavior** instead of trusting code annotations alone.

| Test case | Action | Expected behavior |
| --- | --- | --- |
| Queue and competing consumers | Start 2 consumers on one queue, send 10 uniquely ID'd commands | Total successfully processed commands = 10; each handled once successfully |
| Non-durable topic | Start 2 independent subscribers, send 3 events | Each active subscriber receives all 3 matching events |
| Non-durable offline | Stop subscriber, send 3 events, restart | Missed 3 events are not retroactively delivered |
| Durable offline | Create durable subscription, stop consumer, send 3 events, restart with same identity | Receives the 3 unexpired/un-evicted events |
| Durable non-retroactive | Send E1 before creating durable subscription; create it, then send E2 | New subscription receives E2, not E1 |
| Identity change | Leave backlog on subscription A; start with name B | B is a separate logical subscription; A's backlog does not move to B |
| Broker restart | Send persistent event, stop consumer, restart persistent broker | Backlog survives restart when broker config and policies support it |
| Redelivery and inbox | Force error/rollback, then reprocess the same `eventId` | Message can redeliver; final SQL side effect applies only once |
| Selector | Emit `OrderCreated` and `OrderCancelled` with typed properties | Subscriber filtering `OrderCreated` receives only matching events |
| Shared durable scaling | Start 2 instances sharing one subscription and publish N IDs | Total unique IDs processed by the group = N, not N × instances |

When testing durable offline behavior, **start the listener at least once to register the subscription before stopping it**; otherwise the test creates the subscription after publishing and produces misleading results. If the broker automatically sweeps unused subscriptions, disable or control that policy during tests.

## 12. Common architectural decisions

**"Both billing and warehouse must process `OrderCreated`."** Use one topic with two separate logical subscriptions—typically durable if neither service can afford losing events during maintenance. Each service maintains its own inbox and progress.

**"Four workers should share invoice generation commands."** Use a queue with competing consumers; protect against duplicates via command IDs and idempotency. Adding consumers on that queue scales throughput.

**"The dashboard only shows live real-time state."** A non-durable topic may suffice if the dashboard can hydrate current state from an API/store after reconnecting.

**"Billing runs multiple pods, yet each event should be processed by only one billing pod."** Use a shared durable subscription if supported by the broker/driver and tested for `clientId` rules, or bridge the topic into a billing-specific queue. Never give each pod its own durable subscription expecting them to load-balance.

**"We want to replay every event from six months ago."** JMS durable subscriptions are not inherently long-term offset-replayable historical logs. Use an event store/log or dedicated archive if business requirements demand historical querying and replay.

### Pre-deployment checklist

- Choose queues for **one work-sharing group**, topics for **multiple independent receiving groups**.
- Decide explicitly whether offline message retention is required; create durable subscriptions before events need protection.
- Design stable subscription names and client IDs; validate scaling under unshared vs. shared modes.
- Configure `pubSubDomain`, delivery mode, expiration, broker persistence, retries, and DLQs per SLA.
- Give every event an `eventId` and schema version; persist inbox/idempotency inside consumer business transactions.
- Test reconnects, rollbacks, broker restarts, selectors, and multi-instance scaling; monitor backlog depth and message age in production.

**Key takeaway:** queues distribute a single work stream across competing consumers; topics broadcast an event to each subscription; durable subscriptions let **an existing subscription** accumulate matching messages while consumers are absent. Choosing the right model alongside sound transactions and idempotency determines whether a Spring Boot integration recovers reliably.
