# Caching or Pooling Connections and Sessions in JMS

> **Chapter:** JMS  
> **Module:** SPRING_BOOT_INTEGRATION — integrating Spring Boot with HTTP clients, databases, caches, message brokers, and Spring Integration adapters, emphasizing configuration, data contracts, transactions, error handling, duplicates, testing, and observability.  
> **Objective:** Understand when to cache or pool JMS Connections, Sessions, Producers, and Consumers; configure them safely in Spring Boot; control resources; and recover when the broker fails.

An application receives orders and publishes thousands of events over JMS every minute. Each call to **`JmsTemplate.convertAndSend(...)`** needs a JMS connection and session. Opening a fresh connection, session, and producer and tearing them down completely on every message incurs heavy overhead as traffic grows. **Caching** and **pooling** reuse resources, yet they differ in how they manage and bound them.

Remember up front: **caching/pooling optimizes resource lifecycles**, not delivery guarantees. The broker can still redeliver after errors; a send may succeed even if the client missed the response. Integration design still requires transactions, idempotency, retries, and observability.

## 1. Where do JMS resources sit?

~~~mermaid
flowchart LR
    A["Service / @JmsListener"] --> B["JmsTemplate / Listener Container"]
    B --> C["ConnectionFactory"]
    C --> D["Connection"]
    D --> E["Session"]
    E --> F["MessageProducer / MessageConsumer"]
    F --> G["JMS Broker"]
~~~

| Resource | Role | Key rule |
| --- | --- | --- |
| **ConnectionFactory** | Factory that creates JMS Connections | Can be a native factory, cache wrapper, or pool wrapper |
| **Connection** | Logical/physical transport link to the broker | Expensive to open; may support multiple sessions depending on provider |
| **Session** | Context for send/receive, acks, and local transactions | **Never use a single Session concurrently from multiple threads** |
| **MessageProducer** | Sends messages to destinations | May be cached/reused depending on the wrapper |
| **MessageConsumer** | Receives from queues/topics; may hold selectors/subscriptions | Retaining consumers too long can pin unintended resources/subscriptions |
| **JmsTemplate** | Manages send/receive and closes logical resources per contract | The template itself does not imply `ConnectionFactory` is pooled |
| **DefaultMessageListenerContainer** | Manages background consumers and listener resources | Has its own connection/session/consumer cache levels |

In Spring Boot projects on Spring Framework 6+, the JMS API uses package **`jakarta.jms`**. Older versions use **`javax.jms`**. Broker, cache, and pool dependencies must match the same JMS API family.

### Why shouldn't one Session be shared across all requests?

A Session holds message processing state, acknowledgments, transactions, and its consumers/producers. Two concurrent HTTP requests sharing one singleton Session and invoking commit/rollback would scramble transaction boundaries. One Connection can serve multiple Sessions, yet each concurrent operation needs a Session allocated according to JMS/provider thread-confinement rules.

Never store a **`Session`** or **`MessageProducer`** in a singleton service field shared by multiple threads. In Spring, **`JmsTemplate`** and listener containers allocate, use, and return resources through the configured **`ConnectionFactory`**.

## 2. How do caching and pooling differ?

| Criterion | **Spring CachingConnectionFactory** | **JMS pool** |
| --- | --- | --- |
| How it works | Keeps a shared connection and idle Sessions for reuse | Manages multiple connections/sessions, lending on borrow and reclaiming on logical close |
| Common implementation | **`org.springframework.jms.connection.CachingConnectionFactory`** | **`org.messaginghub.pooled.jms.JmsPoolConnectionFactory`** or provider-specific pool |
| Connection count | Usually one physical Connection per factory | Can bound multiple physical Connections |
| Session count | **`sessionCacheSize`** caps idle sessions retained **per session type**, not concurrent sessions | **`maxSessionsPerConnection`** typically caps sessions per connection |
| When no idle session is left | Can create extra sessions and physically close them on return once cache is full | Can borrow from another connection, wait, time out, or fail per policy |
| Producer/Consumer | Optional producer and consumer caching | Cache/reuse policy depends on pool/provider |
| Typical fit | Steady light-to-moderate load, predictable producers reducing churn | High parallel bursts needing capacity bounds and backpressure |
| Risks | Confusing cache size with concurrency cap; caching dynamic consumers | Slot exhaustion, long borrow waits, session leaks, cluster-wide connection explosion |

Neither option is universally faster: throughput also depends on the broker, message persistence, transactions, acknowledgments, network latency, message size, and concurrency.

### Caching: closing a logical Session returns it to the cache

~~~mermaid
sequenceDiagram
    participant T as JmsTemplate
    participant C as CachingConnectionFactory
    participant B as JMS Broker
    T->>C: Get/create Connection and Session
    C-->>T: Session proxy
    T->>B: Send message via Session
    T->>C: Session.close()
    Note over C: Keep Session idle if cache has room
    T->>C: Next operation
    C-->>T: May reuse cached Session
~~~

### Pooling: bounded capacity

~~~mermaid
flowchart TD
    A["Operation needs Session"] --> B{"Idle Session available?"}
    B -->|Yes| C["Borrow"]
    B -->|No, capacity left| D["Create Session within limit"]
    B -->|No, at max| E["Wait / Timeout / Fail"]
    C --> F["Send / Receive"]
    D --> F
    F --> G["Close logical resource"]
    G --> H["Return Session to pool"]
~~~

If code borrows a resource and forgets to close it, the session remains counted as active; later requests stall once the pool hits capacity. Conversely, closing a **logical connection/session** after an operation does not necessarily close the underlying TCP socket.

## 3. Using CachingConnectionFactory in Spring Boot

**`CachingConnectionFactory`** extends **`SingleConnectionFactory`**: it maintains a target connection, caches sessions, and optionally caches producers/consumers created from them. Common settings:

| Setting | Effect |
| --- | --- |
| **`setSessionCacheSize(n)`** | Retains up to `n` idle Sessions per session/ack-mode type |
| **`setCacheProducers(true/false)`** | Whether to cache producers created through a Session |
| **`setCacheConsumers(true/false)`** | Whether to cache consumers created through a Session |
| **`setReconnectOnException(true/false)`** | Whether to reset/replace the target connection upon a `JMSException` |

Spring's common default for **`sessionCacheSize`** is **1**. **That is not a limit on concurrent Sessions.** If 20 concurrent requests need sessions, the wrapper can create extra sessions beyond the cache size; upon return, only up to the cache size of idle sessions are kept. Thus caching reduces churn rather than acting as a quota enforcer.

### 3.1. Declaring the wrapper around a provider factory

Assuming a **`nativeJmsConnectionFactory`** bean was configured for your provider, this class wraps it with caching:

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.jms.connection.CachingConnectionFactory;

@Configuration
public class JmsCachingConfiguration {
    @Bean
    @Primary
    public CachingConnectionFactory cachedConnectionFactory(
            @Qualifier("nativeJmsConnectionFactory")
            ConnectionFactory nativeFactory) {

        CachingConnectionFactory caching =
                new CachingConnectionFactory(nativeFactory);
        caching.setSessionCacheSize(10);
        caching.setCacheProducers(true);
        caching.setCacheConsumers(false);
        return caching;
    }
}
~~~

This example is for applications **explicitly declaring a native provider bean**. When using Spring Boot auto-configuration, a cache wrapper may already exist; avoid wrapping a second layer without inspecting the effective bean graph.

In Spring Boot versions supporting these properties, you can configure:

~~~yaml
spring:
  jms:
    cache:
      enabled: true
      session-cache-size: 10
~~~

**`spring.jms.cache`** configures Spring's cache wrapper, not **`maxConnections`** on a provider pool. Verify configuration metadata for your exact Boot version.

### 3.2. Sending messages via JmsTemplate

~~~java
package example.integration.jms;

import org.springframework.jms.core.JmsTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderEventPublisher {
    private final JmsTemplate jmsTemplate;

    public OrderEventPublisher(JmsTemplate jmsTemplate) {
        this.jmsTemplate = jmsTemplate;
    }

    public void publish(String orderId, String eventId) {
        jmsTemplate.convertAndSend(
                "orders.created",
                orderId,
                message -> {
                    message.setStringProperty("eventType", "OrderCreated");
                    message.setStringProperty("eventId", eventId);
                    return message;
                }
        );
    }
}
~~~

**`JmsTemplate`** manages the Session, Producer, and operation scope. With a caching wrapper, closing at the end of the operation returns the Session to the cache for reuse. **`eventId`** is a stable ID for a specific event; never mint a new `eventId` when retrying the same message.

### 3.3. Is caching producers the same as caching consumers?

Producers typically send repeatedly to a fairly static set of destinations, so reusing producers cuts overhead. Consumers have more complex lifecycles:

- Consumers can carry **message selectors**, durable/shared subscriptions, or topics.
- Caching consumers created with dynamic selectors can pin unneeded broker resources.
- Listener containers already manage long-lived Sessions/Consumers via their own cache levels.
- Combining multiple cache layers makes it hard to tell who owns a Session/Consumer.

For applications mostly **sending** via `JmsTemplate` and **receiving** via **`@JmsListener`**, setting **`setCacheConsumers(false)`** on the producer-facing wrapper lets listener containers manage consumers directly. When both paths share one wrapper, verify behavior with your provider, transactions, and concurrency.

## 4. Using a JMS pool to cap connections and sessions

A common choice in Jakarta JMS environments is **`pooled-jms`** with **`JmsPoolConnectionFactory`**. Pooling bounds physical connections and sessions per connection, controlling broker resource consumption under high concurrency.

### 4.1. Java example

The snippet below assumes **`org.messaginghub:pooled-jms`** compatible with your Jakarta JMS version, plus an existing **`nativeJmsConnectionFactory`** bean:

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.messaginghub.pooled.jms.JmsPoolConnectionFactory;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;

@Configuration
public class JmsPoolingConfiguration {

    @Bean(destroyMethod = "stop")
    @Primary
    public JmsPoolConnectionFactory pooledConnectionFactory(
            @Qualifier("nativeJmsConnectionFactory")
            ConnectionFactory nativeFactory) {

        JmsPoolConnectionFactory pool = new JmsPoolConnectionFactory();
        pool.setConnectionFactory(nativeFactory);
        pool.setMaxConnections(4);
        pool.setMaxSessionsPerConnection(16);
        pool.setBlockIfSessionPoolIsFull(true);
        return pool;
    }
}
~~~

**Never enable both `JmsCachingConfiguration` and `JmsPoolingConfiguration`** as competing **`@Primary`** beans in one application. They are alternative setups; pick one and verify which bean is injected into `JmsTemplate` and listeners.

With 4 connections × 16 sessions/connection, theoretical per-instance capacity is **64 sessions**. Actual capacity depends on how the pool distributes sessions, active/idle states, transactions, provider limits, and connection borrowing. Across 10 instances, system-wide capacity nears **640 pooled sessions**, so size broker limits for total replicas.

When **`blockIfSessionPoolIsFull`** is enabled, requests wait if no slot is free. Configure a borrow timeout per your exact **`pooled-jms`** version's API aligned with request SLAs; never let HTTP workers hang indefinitely if the broker or consumers stall.

### 4.2. Spring Boot with a provider pool

In Spring Boot releases supporting Artemis pooling integration, configuration looks like:

~~~yaml
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    pool:
      enabled: true
      max-connections: 4
      max-sessions-per-connection: 16
  jms:
    cache:
      enabled: false
~~~

This requires the starter/provider and pool library matching your Spring Boot release. Verify property names and dependencies against your pinned version. **ActiveMQ Classic** and **Artemis** use different config prefixes/providers; never copy **`spring.artemis`** properties verbatim for ActiveMQ Classic.

When enabling a provider pool, disabling Spring's cache wrapper avoids unintentionally stacking two session-management layers. If you intentionally combine layers, test actual resource usage and reconnect behavior, because an outer cache can mask pool saturation.

### 4.3. Sizing the pool

A sizing process:

1. Measure **peak concurrency** across producers, listeners, and background tasks **per instance**.
2. Compute total bounds across **all replicas**.
3. Set **`maxConnections`**, **`maxSessionsPerConnection`**, and borrow timeouts within what the broker can serve.
4. Monitor active/idle/waiting sessions, borrow wait latency, send latency, consumer throughput, and errors.
5. Raise limits only after confirming pool saturation is the bottleneck, while checking broker and database load.

A larger pool improves throughput when connection/session acquisition is the bottleneck; if the real bottleneck is broker disk, persistence, consumer logic, or downstream HTTP, a bigger pool only adds pressure.

## 5. Listener containers have their own caching

Spring's **`DefaultMessageListenerContainer (DMLC)`** manages listener threads, JMS Sessions, `MessageConsumer`s, and error recovery. With **`@JmsListener`**, applications typically configure a **`DefaultJmsListenerContainerFactory`**.

~~~java
package example.integration.jms;

import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;
import org.springframework.jms.listener.DefaultMessageListenerContainer;

@Configuration
public class ListenerConfiguration {
    @Bean
    public DefaultJmsListenerContainerFactory listenerFactory(
            ConnectionFactory connectionFactory) {

        DefaultJmsListenerContainerFactory factory =
                new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setConcurrency("2-6");
        factory.setSessionTransacted(true);
        factory.setCacheLevel(
                DefaultMessageListenerContainer.CACHE_CONSUMER);
        return factory;
    }
}
~~~

~~~java
package example.integration.jms;

import org.springframework.jms.annotation.JmsListener;
import org.springframework.stereotype.Component;

@Component
public class OrderEventListener {
    private final OrderConsumerService orderService;

    public OrderEventListener(OrderConsumerService orderService) {
        this.orderService = orderService;
    }

    @JmsListener(
            destination = "orders.created",
            containerFactory = "listenerFactory")
    public void handle(String orderId) {
        orderService.processIdempotently(orderId);
    }
}
~~~

**`OrderConsumerService`** is a business service you implement. When a transacted listener throws an exception, the container rolls back the JMS session so the broker can redeliver. Business services must be idempotent.

| DMLC cache level | Resources typically retained |
| --- | --- |
| **`CACHE_NONE`** | Does not cache JMS resources across receive cycles |
| **`CACHE_CONNECTION`** | Connection |
| **`CACHE_SESSION`** | Connection and Session |
| **`CACHE_CONSUMER`** | Connection, Session, and `MessageConsumer` |
| **`CACHE_AUTO`** | DMLC chooses based on environment and transaction manager |

**`CACHE_CONSUMER`** fits long-lived listeners on steady queues without special transaction-manager constraints. **When using JTA/XA**, review the cache level and enlistment behavior; some providers/transaction managers require reacquiring sessions per transaction. Never force `CACHE_CONSUMER` purely because local benchmarks look faster.

### Concurrency and session capacity

Setting **`2-6`** lets the listener container scale consumers between min and max based on load and scaling rules. Each active consumer typically requires its own session/consumer. If pool max sessions is smaller than active listeners plus concurrent producers, threads will wait on sessions, time out, or starve.

Especially when an app hosts multiple **`@JmsListener`** endpoints or shares one `ConnectionFactory` across inbound and outbound flows, sum total demand rather than looking at a single listener's concurrency.

### Queues and topics behave differently

- On a **queue**, multiple competing consumers typically raise throughput, though business completion order can vary.
- On a **topic**, distinct subscriptions each receive copies of messages. Adding subscribers does not share load like a queue.
- On **durable/shared subscriptions**, client IDs and subscription names must obey JMS contracts and provider limits, especially across multiple replicas.

When business rules require ordering by order ID or account ID, design explicit routing/partitioning and concurrency limits; raising consumer counts arbitrarily breaks update order.

## 6. Resource reuse does not create distributed transactions

A JMS Session can join a **local JMS transaction** or an **external/JTA transaction** if supported by the provider and transaction manager. Caching/pooling manages resource lifecycles only; it never alters transaction boundaries.

| Case | Guarantee to distinguish |
| --- | --- |
| **JMS Session transacted** | Message commit/rollback scoped to that session transaction |
| **`AUTO_ACKNOWLEDGE`** | Acknowledgment per JMS and listener-container semantics |
| **`CLIENT_ACKNOWLEDGE`** | Application-driven session-scoped ack; understand session scope |
| **JDBC `@Transactional`** | Manages enlisted DB transaction; does not automatically roll back JMS sends |
| **JTA/XA** | Atomically coordinates only XA resources properly enlisted with a compatible transaction manager |

Failure window when a consumer writes to PostgreSQL:

~~~text
1. Broker delivers OrderCreated(eventId=E123).
2. Consumer writes database and COMMITS.
3. Process dies before JMS Session COMMIT/ACK.
4. Broker redelivers E123.
5. Without deduplication, consumer may apply business logic twice.
~~~

Therefore consumers need an **inbox/`processed_message`** table with a unique **`eventId`** in the same DB transaction as business side effects. When publishing events after DB commits, a **transactional outbox** preserves outbound intent for retries. Even a large session pool cannot solve duplicate deliveries or lost events.

### Idempotent inbox example

~~~sql
CREATE TABLE processed_message (
    consumer_name VARCHAR(100) NOT NULL,
    event_id VARCHAR(100) NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (consumer_name, event_id)
);
~~~

~~~java
@Transactional
public void process(String eventId, String orderId) {
    int created = jdbcTemplate.update("""
            INSERT INTO processed_message (consumer_name, event_id)
            VALUES ('order-consumer', ?)
            ON CONFLICT DO NOTHING
            """, eventId);

    if (created == 0) {
        return;
    }

    orderRepository.applyOrderCreated(orderId);
}
~~~

This SQL targets PostgreSQL; **`orderRepository.applyOrderCreated(...)`** represents business writes sharing **the same datasource and transaction manager** as `processed_message`. On rollback, both the marker and business updates roll back so redelivery can retry cleanly. Because the earlier listener snippet received only `orderId`, real systems need a **message contract carrying `eventId`** wired into the service.

### Returning a Session with an unfinished transaction?

When using the raw JMS API directly, developers must commit/roll back, ack, and close in the right order. Pools have cleanup/eviction hooks, yet you should never rely on them to clean up code that leaks open transacted Sessions. Using **`JmsTemplate`** and listener containers lets Spring govern session lifecycles cleanly.

## 7. Broker restarts, reconnects, and uncertain send outcomes

A physical Connection can drop on broker restarts or network partitions. Caches/pools must detect broken resources and rebuild connections/sessions. Still, not every error reveals whether the broker accepted a message.

~~~mermaid
sequenceDiagram
    participant A as Producer
    participant P as Cache / Pool
    participant B as JMS Broker
    A->>P: send(eventId=E123)
    P->>B: Message E123
    Note over B: Broker received/persisted
    B--xP: Disconnect before ACK
    P-->>A: JMSException or timeout
    A->>P: Retry send E123
    P->>B: Message E123
    Note over B: May hold two copies with same eventId
~~~

Mitigations:

1. **Use a stable `eventId`** across retries of the same event so consumers deduplicate by `eventId`.
2. **Bound retries with backoff**, avoiding hammering a freshly restarting broker.
3. **Monitor reconnects and `JMSException`s**, distinguishing configuration bugs from transient blips.
4. **Use an outbox** when DB updates and messages must stay reliably paired.
5. **Configure DLQs and poison-message policies** for unprocessable messages.
6. **Reconcile** when business rules require confirming final state across independent systems.

A wrapper can replace a broken physical Connection on exception, but it cannot roll back side effects committed elsewhere. Pools and consumers also need clean shutdown hooks so rolling deployments do not leave zombie connections.

## 8. Choosing cache vs. pool per scenario

| Scenario | Recommended choice | What to verify |
| --- | --- | --- |
| Steady producer, few threads, same queue | Spring **`CachingConnectionFactory`** | Session/producer reuse rate, send latency |
| High-burst producer, many threads | **JMS pool** with caps and borrow timeout | Pool saturation, cluster-wide connections, broker capacity |
| Long-lived consumer via **`@JmsListener`** | **DMLC** cache level with compatible factory | Listener concurrency, broker consumer count, selectors |
| JMS + DB requiring atomic XA | XA-capable provider factory and JTA transaction manager | Enlistment, recovery, DMLC cache level; generic pools often lack full XA support |
| JMS sender in a Spring Integration adapter | Match factory to adapter/`JmsTemplate` load | Who owns Session and transactions; avoid stacked caches |
| Reliably forwarding DB events to broker | Outbox publisher + matching cache/pool | DB commits, duplicate sends, retries, consumer inbox |

**Standard `JmsPoolConnectionFactory` is not a default XA pooling solution.** If XA is required, verify library/provider versions and JTA integration explicitly. Never wrap an `XAConnectionFactory` in a generic pool assuming distributed transactions automatically work.

## 9. Common configuration mistakes

**Confusing `sessionCacheSize` with max concurrent sessions.** `CachingConnectionFactory` still creates extra sessions outside the cache for concurrent callers. Use a pool for hard bounds.

**Raising `maxConnections` while forgetting replica counts.** Four connections per instance across 30 pods means 120 physical connections before counting other clients.

**Holding a Session in a singleton bean.** Sessions are not thread-safe for concurrent use, especially with acks/transactions.

**Failing to close borrowed pool resources.** Leaked sessions remain active until callers block or time out. Raw JMS code needs `try-with-resources` or `finally`.

**Caching dynamic consumers indefinitely.** Changing selectors or subscriptions can pin stale broker resources. Disable `cacheConsumers` or let listener containers own consumers.

**Stacking a cache wrapper and provider pool together.** Two resource lifecycles obscure borrow/return metrics, reconnects, and capacity limits. Test explicitly if combining them.

**Adding listeners blindly to clear backlogs.** If the real bottleneck is DB locks or downstream APIs, extra consumers only increase retries and contention.

**Assuming `close()` always closes the TCP socket.** With caches/pools, `close()` returns logical handles; sockets close on factory destroy / pool stop at shutdown.

**Assuming caching guarantees exactly-once.** Lost ACKs, process crashes, and redeliveries still create duplicates. Deduplicate via business keys/event IDs.

## 10. Observability and tuning

Track at least:

| Metric | Meaning |
| --- | --- |
| **Active/idle connections** | Sockets/broker resources currently held |
| **Active/idle/waiting sessions** | Whether the pool is saturating or leaking sessions |
| **Session creation rate** | Whether caching is effectively reusing sessions |
| **Borrow wait/timeouts** | Whether operations stall before sending |
| **Send/receive latency** | Separates pool wait, broker latency, and business handler time |
| **Listener concurrency** | Whether active consumers match configured limits |
| **Queue depth / age** | Message backlog and oldest message age |
| **Redelivery / DLQ** | Processing failures, duplicates, or poison messages |
| **Reconnects / `JMSException`** | Connection stability and broker recovery behavior |
| **Outbox/inbox lag** | Sync delay across DB and broker |

Not every pool/provider exposes all metrics through Spring Boot Actuator out of the box. You may need broker exporters, JMX, or custom instrumentation. Never conclude a pool is uncontended merely because app CPU is low: threads may be blocked waiting to borrow.

Measurement workflow:

1. **Baseline** with the real broker, persistent delivery mode, message size, and transaction mode.
2. **Load test** steady and burst traffic, measuring throughput, p95/p99 latency, and active/idle sessions.
3. **Locate the true bottleneck**—pool, broker, consumer, or database—before raising limits.
4. **Adjust one parameter at a time**, accounting for replica multipliers and broker limits.
5. **Inject faults:** broker restarts, brief network cuts, slow consumers, verifying recovery and duplicate safety.

## 11. Required pre-production tests

| Scenario | What to prove |
| --- | --- |
| Sequential high-volume sends | All succeed; caching cuts session/producer churn vs. uncached |
| Burst exceeding `sessionCacheSize` | Concurrent sends succeed without sharing one Session across threads |
| Burst exceeding pool capacity | Waits/times out/fails per policy without hanging every HTTP worker forever |
| Listener scaling from 2 to 6 consumers | Fits resource budgets; queue/topic semantics hold |
| Broker restart mid-send | Connections recover; retries cause zero duplicate side effects |
| Consumer commits DB then dies before ack | Redelivery deduplicated by inbox/business key |
| Repeatedly failing message | Bounded retries, routed to DLQ, observable in metrics |
| Rolling deploy | Listeners stop cleanly and connections/pools close per lifecycle |
| External XA (if used) | Resources enlist and recover properly on mid-commit failures |

When verifying connection/session creation, redelivery, and failover, test against a real broker such as Apache ActiveMQ Artemis via Testcontainers or a dedicated test environment. Mocking `JmsTemplate` only checks service calls, not pool behavior under network faults.

## 12. Implementation checklist

- Verify matching **`jakarta.jms`** / **`javax.jms`** APIs across Spring Boot, Spring Framework, and the provider.
- Know exactly **which `ConnectionFactory` bean** `JmsTemplate`, listeners, and Spring Integration adapters inject.
- Configure one primary caching/pooling layer for producers as needed; justify and test any extra layer.
- Never share a `Session` across threads; close logical handles promptly.
- Size for concurrent operations **times replica counts**, with borrow timeouts and backpressure.
- Explicitly design listener concurrency, cache levels, selectors, and queue/topic semantics.
- Keep session transactions and DB transactions distinct; use XA only when provider/manager support is verified.
- Enforce `eventId`, inbox/outbox, idempotent consumers, and retry/DLQ policies for critical operations.
- Monitor saturation, queue backlogs, redeliveries, latency, and reconnects.
- Test bursts, crashes, broker restarts, DB-commit-before-ack, and clean shutdowns.
