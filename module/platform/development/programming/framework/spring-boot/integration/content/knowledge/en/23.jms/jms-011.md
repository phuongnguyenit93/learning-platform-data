# Database Coordination, JTA, and Atomic Commit Boundaries

## 1. The problem: are receiving a message and writing to the database really one transaction?

In a **Spring Boot** integration system, a JMS message often triggers database changes: receiving a payment event, updating an order, writing audit history, and possibly sending a follow-up message to shipping. These steps touch at least two independent resources: a **JMS broker** and a **database**.

Suppose a consumer receives **`PaymentCaptured`** from queue **`payments.captured`**:

1. Receive the payment event from the broker.
2. Mark the order paid in PostgreSQL.
3. Confirm message processing (acknowledge/commit receipt).
4. Publish **`OrderPaid`** so downstream services continue processing.

If the application crashes mid-way, messages can be redelivered or follow-up events can go missing. Slapping **`@Transactional`** onto a Java method is not enough to make steps across two systems commit atomically.

In the **SPRING_BOOT_INTEGRATION** module, this is the core challenge of coordinating message brokers with databases, HTTP clients, caches, and integration adapters: defining exact **transaction boundaries**, failure recovery, and duplicate-processing guards.

### Concepts to distinguish

| Concept | Guaranteed scope | Does NOT guarantee by itself |
| --- | --- | --- |
| **Local database transaction** | SQL operations on database resources enlisted in that transaction. | Committing/rolling back a JMS session or HTTP call. |
| **JMS session transacted** | JMS send/receive operations within one transacted session per provider rules. | Committing/rolling back SQL in a database. |
| **`JmsTransactionManager`** | Manages local transactions for one matching JMS `ConnectionFactory`. | Distributed transactions with JDBC/JPA merely because both use Spring. |
| **`DataSourceTransactionManager` / `JdbcTransactionManager` / `JpaTransactionManager`** | Manages database/JPA transactions per configuration. | Making the JMS broker join the same atomic commit. |
| **JTA/XA** | Coordinates commits across multiple resources **genuinely supporting and enlisted in XA**, typically via two-phase commit. | Atomicity for HTTP, non-XA caches, email, or external side effects; nor does it eliminate recovery concerns. |
| **Transactional outbox + idempotent consumer** | Commits business state and outbound intent in one database transaction; safely handles duplicate deliveries on the receiver. | Physically single delivery or simultaneous instant commit between database and broker. |

In JMS, **acknowledge** signals receipt from consumer to broker; **database transaction commit** persists database changes. Those two decisions bind into one distributed commit only when matching XA infrastructure and resources are configured.

## 2. What happens with two local transactions?

Trace a flow that receives a message, updates the database, and then confirms JMS:

~~~mermaid
sequenceDiagram
    participant B as JMS broker
    participant L as Spring JMS listener
    participant D as Database
    B->>L: Deliver PaymentCaptured
    L->>D: BEGIN, update order
    D-->>L: COMMIT succeeded
    Note over L: Application can crash right here
    L->>B: COMMIT JMS / acknowledge receipt
    B-->>L: Confirm completed
~~~

If the application stops **after the database commits but before the broker records the JMS commit**, the broker may redeliver the same message. The database changed once; the consumer risks changing it a second time without idempotency.

Reversing the order does not solve it either. Confirming JMS **before** the database commit succeeds risks losing the message on a subsequent database error without completing the business task.

| Failure point | Database | JMS | Consequence to handle |
| --- | --- | --- | --- |
| Mid-processing, before database commit | Open SQL transaction can roll back. | Transacted JMS session rollback lets broker redeliver per policy. | Retryable if data and logic are safe to re-run. |
| Database committed, JMS uncommitted | Change is durable. | Broker may redeliver message. | **Duplicate processing** unless a processed marker is stored and checked inside the same SQL transaction. |
| JMS confirmed, database uncommitted | Database may fail. | Broker considers message processed. | **Lost work** unless separate recovery exists. |
| Database committed, outbound JMS send failed | Data updated. | Follow-up event may not be sent. | **Lost event** without an outbox or tracking/compensation mechanism. |
| Outbound JMS sent, database commit failed | Business data may roll back. | Other consumers may already act on event. | **Phantom event**: external systems react to state never persisted. |

These **failure windows** exist even when each resource individually provides full ACID transactions. Network latency, timeouts, disconnects, or restarts can also leave a caller unsure whether a commit succeeded remotely.

## 3. Spring JMS transaction mechanisms

### 3.1. Transacted sessions and acknowledgment

A **transacted** JMS session commits or rolls back all JMS operations on that session. For consumers, rollback makes the message eligible for redelivery per broker and redelivery settings. For producers, messages sent inside the transaction become visible when the JMS transaction commits.

Do not equate **`AUTO_ACKNOWLEDGE`**, **`CLIENT_ACKNOWLEDGE`**, and **transacted sessions**:

- **`AUTO_ACKNOWLEDGE`** confirms automatically per API/container rules. Exact ack timing depends on receive mode and listener container; never rely on the assumption that "every exception triggers broker retries."
- **`CLIENT_ACKNOWLEDGE`** lets the app acknowledge, yet does not create a SQL or distributed transaction. In JMS, acknowledging can also apply to other messages already consumed in the same session, not solely one business row.
- **Transacted sessions** establish a clear JMS commit/rollback boundary. With Spring listener containers, configure and test redelivery, attempt caps, and dead-letter queues (DLQs) on your actual provider.

Example listener container configured for **local JMS transactions** (Spring Boot with **`jakarta.jms`**):

~~~java
import jakarta.jms.ConnectionFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.jms.config.DefaultJmsListenerContainerFactory;

@Configuration
class PaymentJmsConfig {

    @Bean
    DefaultJmsListenerContainerFactory paymentJmsFactory(
            ConnectionFactory connectionFactory) {
        var factory = new DefaultJmsListenerContainerFactory();
        factory.setConnectionFactory(connectionFactory);
        factory.setSessionTransacted(true);
        factory.setConcurrency("2-4");
        return factory;
    }
}
~~~

This configuration runs the listener container with transacted JMS sessions. It **does not automatically make** database transactions invoked from the listener part of that JMS transaction. When mixing transaction managers or custom containers, verify where transactions start and commit rather than guessing from annotations.

### 3.2. Which transaction manager does @Transactional choose?

Spring delegates **`@Transactional`** to a matching **`PlatformTransactionManager`**. When both JDBC/JPA and JMS are present, keep transaction manager selection explicit:

~~~text
@Transactional + JdbcTransactionManager   -> JDBC transaction
@Transactional + JpaTransactionManager    -> JPA/database transaction
JMS sessionTransacted=true                -> local JMS transaction
@Transactional + JtaTransactionManager    -> JTA transaction,
                                             if resources are properly enlisted
~~~

Spring does not infer that calling both **`JdbcTemplate`** and **`JmsTemplate`** inside one method requires XA. With multiple transaction managers, qualify the intended manager explicitly so methods do not bind to the wrong one. Also, **`@Transactional`** AOP proxies do not intercept self-invocation (one method on a bean calling another method directly on `this`).

## 4. Practical example: JMS consumer updating a database with duplicate protection

Consider a Spring Boot app receiving JSON **`PaymentCaptured`** events and updating orders in **PostgreSQL**. Events must carry a stable **`eventId`** generated by the producer; never mint a new ID when resending the same business event.

Create a tracking table:

~~~sql
CREATE TABLE processed_jms_messages (
    consumer_name VARCHAR(100) NOT NULL,
    event_id      VARCHAR(100) NOT NULL,
    processed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, event_id)
);
~~~

The unique constraint on **`(consumer_name, event_id)`** enforces deduplication directly in the database, holding even when concurrent consumers race. Never rely solely on an in-memory JVM set, Redis TTLs, or a "SELECT then INSERT" check: those suffer races or state loss on restart.

Example event record and listener (common imports omitted):

~~~java
public record PaymentCapturedEvent(
        String eventId,
        long orderId,
        long amountMinor,
        String currency) {}

@Component
class PaymentCapturedListener {
    private final ObjectMapper objectMapper;
    private final PaymentApplicationService paymentService;

    PaymentCapturedListener(ObjectMapper objectMapper,
                            PaymentApplicationService paymentService) {
        this.objectMapper = objectMapper;
        this.paymentService = paymentService;
    }

    @JmsListener(
            destination = "payments.captured",
            containerFactory = "paymentJmsFactory")
    public void onMessage(String json) throws JsonProcessingException {
        var event = objectMapper.readValue(json, PaymentCapturedEvent.class);
        paymentService.applyOnce(event);
    }
}
~~~

When the provider delivers a JMS **`TextMessage`**, the default converter extracts a **`String`** payload. With custom JSON converters, match message types and converters deliberately; never blindly assume every broker maps JSON into Java records automatically.

The service records the marker **and** updates state in **the same PostgreSQL transaction**:

~~~java
@Service
class PaymentApplicationService {
    private final JdbcTemplate jdbc;

    PaymentApplicationService(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void applyOnce(PaymentCapturedEvent event) {
        if (event.eventId() == null || event.eventId().isBlank()) {
            throw new IllegalArgumentException("Missing eventId");
        }

        int inserted = jdbc.update("""
                INSERT INTO processed_jms_messages (consumer_name, event_id)
                VALUES (?, ?)
                ON CONFLICT DO NOTHING
                """, "payment-service", event.eventId());

        if (inserted == 0) {
            return; // Event already processed earlier.
        }

        int updated = jdbc.update("""
                UPDATE orders
                SET payment_status = 'PAID'
                WHERE id = ? AND payment_status = 'PENDING'
                """, event.orderId());

        if (updated != 1) {
            throw new IllegalStateException(
                    "Order missing or not in PENDING state");
        }
    }
}
~~~

This example focuses on database-side atomicity. Production code must also validate **`amountMinor`**, **`currency`**, order IDs, state transitions, and producer authorization—never trust unverified JSON from a broker. **`ON CONFLICT DO NOTHING`** is PostgreSQL syntax; other databases require equivalent unique-insert idioms. With multiple transaction managers, ensure **`@Transactional`** on this service binds to the database transaction manager.

### Commit order analysis

1. Listener container opens a transacted JMS receive session.
2. Listener invokes the Spring service via proxy; service starts a database transaction.
3. Within the same database transaction, `INSERT` the processed marker and `UPDATE` the order.
4. Service returns normally; **database transaction commits**.
5. Listener returns normally; container **commits the JMS session**.

If an error occurs before step 4, the database rolls back and the escaping exception rolls back the JMS session. If the app crashes between step 4 and step 5, the broker may redeliver. On redelivery, the unique key in **`processed_jms_messages`** shows it was already processed, so the service returns normally and lets JMS commit.

This yields **at-most-once business effects per `eventId`** as long as every protected write shares the same transaction as the marker. It **does not prevent broker redelivery**, nor does it protect external API calls or emails outside that DB transaction.

If two events carry **different `eventId`s representing the same payment**, `eventId` uniqueness alone is insufficient. Add a business uniqueness key such as unique **`paymentId`** plus valid state-transition guards. Retain processed-event records longer than any possible replay window, or archive permanently per business policy.

### Handling unprocessable messages

Corrupt JSON payloads, missing order IDs, or invalid states can cause repeated exceptions and endless redeliveries. Configure redelivery counts/backoff and a **DLQ** on the JMS provider, separating transient failures (DB disconnect, timeout) from permanent data errors. Record **`eventId`**, correlation ID, failure reason, and diagnostic data safely; replay only after resolving the root cause.

## 5. The reverse direction: database commits, but JMS send fails

Suppose a REST endpoint confirms an order and emits **`OrderConfirmed`**:

~~~java
@Transactional
public void confirmOrder(long orderId) {
    orderRepository.markConfirmed(orderId);
    jmsTemplate.convertAndSend("orders.confirmed", createPayload(orderId));
}
~~~

This looks "all-or-nothing," yet with a **local database** transaction manager, the JMS send does not commit atomically with SQL. Two failure modes arise:

- Broker accepts the event, then the database rolls back: downstream reacts to an order that was never confirmed.
- Database commits, then sending/completing the send fails: **`CONFIRMED`** exists while downstream never receives the event.

Reordering **`convertAndSend`** only moves the failure window without eliminating it. Registering an **`afterCommit`** callback avoids publishing before DB commit, yet crashes right after commit and before/during send still drop events. It does not guarantee events are never lost.

### Transactional outbox

A **transactional outbox** eliminates the split commit by committing solely within **one database**: updating business state and inserting the outbound event row in one transaction. A separate relay process reads the outbox and sends to JMS:

~~~mermaid
flowchart LR
    A[API / Business service] -->|Same DB transaction| B[(Orders)]
    A -->|Same DB transaction| C[(Outbox)]
    C -->|Read unpublished events| D[Outbox relay]
    D -->|Send with retry| E[JMS broker]
    E --> F[Idempotent JMS consumer]
~~~

PostgreSQL schema example:

~~~sql
CREATE TABLE outbox_events (
    event_id     UUID PRIMARY KEY,
    destination  VARCHAR(120) NOT NULL,
    payload      JSONB NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);
~~~

Within the same database **`@Transactional`**, the service runs both statements:

~~~sql
UPDATE orders
SET status = 'CONFIRMED'
WHERE id = :orderId AND status = 'NEW';

INSERT INTO outbox_events (event_id, destination, payload)
VALUES (:eventId, 'orders.confirmed', CAST(:jsonPayload AS jsonb));
~~~

This SQL uses illustrative named parameters; production code must verify the `UPDATE` row count, generate **`eventId`** once, adhere to the payload contract, and execute both statements on the same connection/transaction manager. If the outbox insert fails, the order update rolls back too; if the transaction commits, the outbound intent is durable.

The relay can poll on a schedule or stream changes via transaction log / CDC. With simple polling:

1. Claim unpublished rows (using leases, locks, or `SKIP LOCKED` so multiple relays do not contend).
2. Send JMS messages with stable **`eventId`** and correlation ID using broker-appropriate persistence.
3. Once broker acceptance is confirmed per guarantees, set **`published_at`**.
4. Retry unmarked rows while monitoring backlog and send errors.

If the relay dies **after broker acceptance but before updating `published_at`**, the event will be sent again. An outbox therefore delivers **at-least-once intent publication**: preventing lost events while requiring idempotent consumers for duplicates.

Watch **event ordering** too. Concurrent relays or multiple partitions/queues can alter delivery order; if contracts require per-order sequence, add **`aggregateId`**, sequence/version numbers, and partitioned claiming or consumer version checks. An outbox does not guarantee global ordering on its own.

## 6. JTA/XA: when can JMS and databases commit atomically?

**Jakarta Transactions (JTA)** defines an API and model for distributed transaction coordination. When both database and JMS provider support **XA** and properly enlist in a global transaction, the transaction manager coordinates **two-phase commit (2PC)**.

### How it works at a high level

~~~mermaid
sequenceDiagram
    participant S as Spring service
    participant T as JTA transaction manager
    participant D as XA database
    participant J as XA JMS broker
    S->>T: Begin global transaction
    S->>D: Write data (enlist XA)
    S->>J: Receive/send JMS (enlist XA)
    S->>T: Commit
    T->>D: Prepare
    T->>J: Prepare
    D-->>T: Prepared
    J-->>T: Prepared
    T->>D: Commit
    T->>J: Commit
    Note over T,J: Coordinator writes logs and recovers incomplete transactions
~~~

In the **prepare** phase, each participant votes whether it can commit cleanly. Only if all participants prepare successfully does the coordinator commit; if any fails prepare, it rolls back all branches. A transaction can enter an **in-doubt** state if connectivity drops or a process crashes during decision/commit propagation. The coordinator relies on durable transaction logs and recovery scans to resolve them.

**Essential prerequisites**:

- Database must use an **`XADataSource`** or equivalent XA driver, not a plain non-XA `DataSource`.
- JMS provider must support XA, and the injected `ConnectionFactory`/wrapper must **enlist JMS sessions into JTA transactions**.
- Spring/Jakarta transaction manager must be wired consistently for **both listener containers and database services**, spanning every operation meant to commit together.
- Transaction coordinator must have **durable transaction logs**, stable resource identifiers, configured recovery, and procedures for in-doubt transactions.
- Spring Boot, Jakarta, transaction manager, JDBC driver, and JMS broker versions must be compatible; seeing a **`JtaTransactionManager`** bean does not prove both resources actually enlist via XA.

Skeleton listener configuration when infrastructure already supplies an XA-aware `ConnectionFactory` and `JtaTransactionManager`:

~~~java
@Bean
DefaultJmsListenerContainerFactory xaPaymentListenerFactory(
        ConnectionFactory jtaEnlistedConnectionFactory,
        JtaTransactionManager jtaTransactionManager) {
    var factory = new DefaultJmsListenerContainerFactory();
    factory.setConnectionFactory(jtaEnlistedConnectionFactory);
    factory.setTransactionManager(jtaTransactionManager);
    return factory;
}
~~~

This code **does not manufacture XA on its own**. The name **`jtaEnlistedConnectionFactory`** indicates a requirement on the bean supplied by your JMS provider/transaction manager. Passing a non-XA `ConnectionFactory` or non-XA database `DataSource` leaves you without atomic commits. Verify transaction manager usage, resource enlistment, and real fault tests in a production-like environment.

### JTA does not equal "system-wide exactly once"

Even with 2PC, recognize its limits:

1. **The coordinator only manages enlisted XA resources.** HTTP calls, email, most caches, and third-party APIs cannot join an XA transaction.
2. **Heuristic outcomes** can occur when a participant unilaterally commits or rolls back under severe faults, requiring manual investigation/reconciliation.
3. Disconnecting mid-commit can leave the caller **unsure of the outcome**, even when the coordinator eventually recovers.
4. JTA/XA adds operational complexity, longer resource/lock hold times, commit latency, and stalling risk if any participant goes down.
5. Even when JMS + database commit atomically, downstream consumers still need idempotency for redeliveries, retries, or duplicate upstream business events.

JTA makes sense when cross-XA atomicity is strictly required and operations can maintain transaction coordinators and recovery logs. Never enable XA by default just to get a shorter annotation.

## 7. Comparing three common coordination patterns

| Criterion | Local JMS tx + local DB tx + idempotency | Transactional outbox + idempotent consumer | JTA/XA (2PC) |
| --- | --- | --- | --- |
| Primary scenario | Consume JMS and update database while tolerating redelivery. | DB updates must reliably emit events via eventual delivery. | JMS and database must commit/roll back as one global transaction. |
| Atomicity | Independent per resource; deduplication preserves business correctness. | **DB state + outbox record** atomic; relay publishes independently. | Across properly enlisted XA resources. |
| Crash between commits | Redelivery possible; DB inbox prevents duplicate writes. | Event stays in outbox; relay retries, may publish duplicates. | Coordinator runs recovery for in-doubt transactions. |
| Duplicate behavior | JMS can redeliver; consumer must prevent double writes. | Relay can republish and broker can redeliver; consumer must be idempotent. | Still needs dedup at non-XA boundaries. |
| Complexity | Low to moderate; focus on business keys and DLQs. | Moderate; needs outbox schema, relay, retries, monitoring, ordering. | High; needs XA drivers/providers, coordinator, logs, recovery, XA monitoring. |
| Outside JMS and DB | Separate compensation/reconciliation. | Separate compensation/reconciliation. | HTTP, caches, email, and non-XA services stay outside. |

For most workflows accepting **eventual consistency**, idempotent JMS consumption paired with an outbox for publishing is easier to observe and recover. When strict atomicity directly between JMS and a database is mandatory, evaluate JTA/XA carefully along with its operational overhead.

## 8. Role of HTTP, caches, and other integration flows

Neither local transactions nor JTA can automatically undo external actions:

**HTTP calls:** if a payment gateway already captured funds, rolling back your orders database does not "cancel" the payment. Design idempotent requests, business keys, and compensating APIs (refund/void). On HTTP timeouts, query external state before retrying.

**Caches:** updating a cache before DB commit exposes uncommitted data; evicting after commit leaves a crash window. Emit invalidation events via outbox, use versions/TTLs, and match cache-aside policies to desired consistency.

**Spring Integration adapters:** inbound JMS adapters, routers, transformers, and outbound gateways still obey the transaction boundaries of each endpoint/channel and enlisted resources. Shifting a message onto an asynchronous channel/executor detaches it from the original transaction thread. Never assume transaction context flows automatically across internal queues, schedulers, threads, or HTTP clients.

**Saga/compensation:** when coordinating multiple non-XA systems, use local steps, events, and idempotent compensating actions. Compensation is a new business action (refunding money, releasing stock), not a database rollback. Sent emails or shipped parcels cannot simply be undone.

## 9. Fault testing to verify actual guarantees

Testing against a **real broker matching production config** and the same database engine/version matters far more than mocking **`JmsTemplate`**. Mocks verify method calls, not commit/ack timing, redelivery, or XA recovery.

| Test scenario | What to observe / verify |
| --- | --- |
| SQL failure before DB commit | No partial SQL changes remain; JMS message retries or enters DLQ per policy. |
| Crash after DB commit, before JMS commit | Broker redelivers; **`processed_jms_messages`** blocks a second business update. |
| Two consumers receive the same `eventId` or duplicate copies | Unique constraint lets only one apply business changes; the other handles duplicate cleanly. |
| Invalid payload or invariant violation | No endless retries; after cap, moves to DLQ with diagnostics and replay path. |
| DB commits while broker is unreachable for new event | Outbox retains unpublished record and relay sends once broker recovers. |
| Broker accepts event, relay crashes before marking outbox | Event republishes; downstream dedup prevents duplicate side effects. |
| Slow broker, slow DB, partial network loss | Retries/backoff, bounded concurrency, timeouts, and alerts prevent total system lockup. |
| JTA coordinator crashes during prepare/commit | Recovery resolves in-doubt transactions; enlistment and durable logs work; no silent heuristic outcomes. |
| HTTP or cache succeeds while remaining transaction rolls back | Verification, repair, compensation, or eventual reconciliation path works. |

With JTA, test 2PC failure points and **transaction recovery** after restarts. Testing only the happy path gives zero assurance that XA protects both database and JMS.

### Key metrics to monitor

- **Consumer:** messages received/processed, redelivery count, duplicate rate, message age, queue depth/consumer lag, DLQ ingress count.
- **Database:** transaction rollbacks, unique constraint conflicts, deadlocks, lock waits, connection pool saturation, commit latency.
- **Outbox:** unpublished row count, oldest unpublished age, publish failure/retry rates, stalled or slow relays.
- **JTA/XA:** active global transactions, timeouts, in-doubt branches, recovery failures, heuristic outcomes, prepare/commit duration.
- **Tracing:** carry **`eventId`**, **`correlationId`**, order ID, and trace context across listeners, services, outboxes, relays, and downstreams while keeping sensitive data out of logs.

Alert on **rising outbox backlog**, **DLQ spikes**, **abnormal redeliveries**, and **unresolved XA transactions**—those directly signal divergence between broker and business data.

## 10. Common misconceptions

**"Using `@Transactional` makes JMS and the database roll back together."** True only when the transaction manager and both resources participate in a distributed atomic commit. With a local DB transaction manager, JMS calls are independent.

**"`sessionTransacted=true` means JTA."** No. It creates a session-local JMS transaction and does not enlist the database.

**"The listener didn't throw, so the data is right."** No. Logic can write wrong state, or swallow failed HTTP calls. Enforce invariants, logging, error propagation, and reconciliation.

**"Enabling persistent delivery means business events can never be lost."** JMS persistence protects messages once inside the broker per configuration; it does not make saving outbound intent atomic with prior database commits.

**"XA eliminates all duplicates and gives exactly once."** XA only coordinates XA resources inside one global transaction. Upstream duplicates, intentional replays, and non-XA side effects still require idempotency.

**"Using an outbox guarantees messages are sent only once."** If the relay crashes right after sending and before marking the outbox row sent, it sends again; **at-least-once + idempotent consumers** is the intentional design.

## 11. Checklist for choosing a JMS–database coordination pattern

1. **Map boundaries:** identify SQL, JMS receive, JMS send, HTTP, and cache steps, plus which transaction wraps each.
2. **Define invariants:** how many times an event may apply side effects, when replays are safe, and which business key is stable.
3. **Select pattern:** local JMS + local DB + dedup for consumers; outbox for producers; XA/JTA only when cross-XA atomicity is truly required.
4. **Design failure handling:** retry/backoff, DLQs, duplicate handling, checkpoints, outbox replay or JTA recovery, and compensation.
5. **Test crashes between commits:** verify data state, broker state, and post-restart recovery instead of only happy paths.
6. **Monitor and operate:** log by `eventId`, track outbox/DLQ/redelivery metrics, alert on in-doubt transactions, and run reconciliation.

## 12. Summary

**Atomic commits hold only across resources actually participating in the same transaction.** In Spring Boot, JDBC/JPA transactions, JMS sessions, and JTA/XA have distinct boundaries. Local transactions paired with **idempotency** handle redeliveries safely; a **transactional outbox** preserves outbound event intent alongside database state; and **JTA/XA** coordinates commits across XA-capable resources at significant configuration and recovery cost. For HTTP calls, caches, and external side effects, you still need eventual consistency, reconciliation, or compensating actions.
