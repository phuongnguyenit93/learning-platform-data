# Testing Declarative Contracts and Real Runtime Behavior of HTTP Interface Proxies in Spring Boot

A Java interface annotated with `@GetExchange`, `@PostExchange`, `@PathVariable`, `@RequestParam`, and `@RequestBody` looks like an **HTTP contract**. Spring Framework can build an **HTTP service client proxy** from that interface via `HttpServiceProxyFactory`, wired to `RestClient`, `WebClient`, or another supported adapter. However, **syntactically valid annotations do not prove that HTTP requests are sent correctly or understood by the server**: a path variable with special characters may encode unexpectedly; a header may be missing; a request body may drop a field; an API may return `204` instead of JSON; or a timeout after the server committed may still make the client think the operation failed.

This lesson belongs to the **HTTP interface** chapter of the **SPRING_BOOT_INTEGRATION** module, which covers Spring Boot integration across HTTP clients, databases, caches, message brokers, and Spring Integration adapters. Its focus is testing at three levels:

1. **Declarative contract**: do the interface's annotations, methods, parameters, and return types express the intended API?
2. **Actual proxy behavior**: do the HTTP method, URL, query encoding, headers, body, codecs, responses, and exceptions emitted by the proxy match the contract?
3. **Cross-service compatibility**: are real requests generated by the proxy accepted by the current provider, and do data semantics, errors, idempotency, and timeouts hold over the network?

We will build an inventory client example, test it with **`MockRestServiceServer`**, an **HTTP stub server**, and **provider contract/compatibility tests**, and wire these checks into CI. Examples target Spring Boot 3.x and Spring Framework 6.1+ with `RestClient`, `HttpServiceProxyFactory`, and Spring Test. Framework 6.0, older Boot releases, or Spring Framework 7 may differ in factory/adapter setup, packages, or supported return types; verify APIs against your project's BOM before copying code.

## 1. The HTTP Interface Is Declarative; the Proxy Creates Network Behavior

Suppose `checkout-service` needs to call `inventory-service` to read available stock and reserve inventory:

~~~mermaid
flowchart LR
    A["CheckoutService"] --> I["InventoryHttpApi (interface)"]
    I --> P["HttpServiceProxyFactory"]
    P --> AD["RestClientAdapter"]
    AD --> R["RestClient"]
    R --> N["HTTP client / serializer / TLS"]
    N --> S["inventory-service"]
    S --> DB[("PostgreSQL")]
~~~

Here:

- `InventoryHttpApi` is the **Java contract** on the caller side, defining paths, HTTP methods, parameters, and response types.
- `HttpServiceProxyFactory` inspects methods/annotations and generates a runtime proxy.
- `RestClientAdapter` connects the proxy to a `RestClient` performing synchronous HTTP calls.
- `RestClient` owns most runtime behavior: base URL, request interceptors, message converters, network request factory, HTTP errors, and timeouts.
- `inventory-service` owns its own server-side contract, typically expressed via controllers, schemas, OpenAPI, or provider specification/tests.

**Successful compilation** only proves Java types and annotations exist. It does not confirm `/v1/inventory/SKU-1` was assembled properly, `X-Correlation-Id` was actually sent, or `409 Conflict` mapped to a domain exception.

### Three Complementary Testing Layers

| Test Layer | What It Sees | What It Cannot Prove |
| --- | --- | --- |
| Reflection/static contract check | Route annotations, parameters, return types | What bytes/headers the proxy emits or how codecs behave |
| Client-proxy HTTP test | Method, URL, headers, JSON, response, exceptions of the real proxy | Whether the real server still honors that contract |
| Provider contract test | Whether the server accepts requests and returns contract-compliant structures/statuses | Whether the real client builds compatible requests |
| End-to-end/integration | Combines client, transport, and server in a production-like environment | Every error permutation and future contract evolution |

To protect the real contract, include **at least one test exercising the real proxy** rather than mocking the interface with Mockito and asserting only that the service called `inventoryApi.reserve(command)`.

## 2. Building a Testable HTTP Interface Contract

A minimal inventory contract:

~~~http
GET /v1/inventory/{sku}?warehouse={warehouse}
Accept: application/json
X-Correlation-Id: <trace-token>

HTTP/1.1 200 OK
Content-Type: application/json

{"sku":"SKU-42","available":5}
~~~

And the side-effecting reservation operation:

~~~http
POST /v1/inventory/reservations
Content-Type: application/json
Accept: application/json
Idempotency-Key: reserve-order-1042
X-Correlation-Id: trace-abc

{"orderId":"ORDER-1042","sku":"SKU-42","quantity":2}
~~~

Success response:

~~~http
HTTP/1.1 201 Created
Content-Type: application/json

{"reservationId":"RES-918","status":"RESERVED"}
~~~

Java DTOs:

~~~java
public record StockDto(String sku, int available) {}

public record ReserveCommand(
        String orderId,
        String sku,
        int quantity
) {}

public record ReservationDto(
        String reservationId,
        String status
) {}
~~~

And the HTTP interface:

~~~java
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.service.annotation.DeleteExchange;
import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.HttpExchange;
import org.springframework.web.service.annotation.PostExchange;

@HttpExchange(url = "/v1/inventory", accept = "application/json")
public interface InventoryHttpApi {

    @GetExchange("/{sku}")
    StockDto getStock(
            @PathVariable("sku") String sku,
            @RequestParam("warehouse") String warehouse,
            @RequestHeader("X-Correlation-Id") String traceId);

    @PostExchange(
            url = "/reservations",
            contentType = "application/json")
    ReservationDto reserve(
            @RequestBody ReserveCommand command,
            @RequestHeader("Idempotency-Key") String key,
            @RequestHeader("X-Correlation-Id") String traceId);

    @DeleteExchange("/reservations/{reservationId}")
    void cancel(
            @PathVariable("reservationId") String reservationId);
}
~~~

**This is a client contract**, not a server controller. Key points to verify:

- `@HttpExchange` on the interface sets the URL prefix and accepted media type.
- `@GetExchange` and `@PostExchange` set the HTTP verb and sub-path.
- `@PathVariable("sku")` binds the argument into the path, directly tied to URI encoding.
- `@RequestParam("warehouse")` controls the query parameter; null values, lists, `+`, spaces, and Unicode characters require explicit contract tests.
- `@RequestHeader` injects the correlation ID and idempotency key into the network request; having a Java parameter alone does not prove the header is emitted correctly.
- `@RequestBody` triggers serialization into the HTTP body via a message converter or encoder.
- `ReservationDto` requires the proxy to receive a status and response body; if the server switches to `204 No Content`, that expectation breaks.

Contracts must be agreed upon with the provider via API specifications, contract tests, or cross-team alignment. Consumer-side annotations **do not verify** server-side choices on their own.

### Name Routes and Versions Deliberately

`/v1/inventory` is part of the API contract. Do not change `v1` to `v2` only on the interface and expect the proxy to stay "compatible" with an older server. Changes to fields, defaults, enums, paths, error codes, or auth policies can break compatibility even when Java compiles cleanly.

## 3. Creating the Proxy Correctly with `HttpServiceProxyFactory`

A Spring Boot application using Spring MVC or blocking clients can register the bean as follows:

~~~java
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

@Configuration(proxyBeanMethods = false)
public class InventoryHttpClientConfiguration {

    @Bean
    InventoryHttpApi inventoryHttpApi(
            RestClient.Builder restClientBuilder,
            @Value("${app.inventory.base-url}") String baseUrl) {

        RestClient restClient = restClientBuilder
                .baseUrl(baseUrl)
                .build();

        var adapter = RestClientAdapter.create(restClient);

        return HttpServiceProxyFactory
                .builderFor(adapter)
                .build()
                .createClient(InventoryHttpApi.class);
    }
}
~~~

`application.yml`:

~~~yaml
app:
  inventory:
    base-url: https://inventory.internal.example
~~~

Important notes:

1. Spring Boot-supplied `RestClient.Builder` (when classpath/auto-config matches) carries converters, observation, and customizers. Calling `RestClient.builder()` manually can bypass customizers the application relies on.
2. `HttpServiceProxyFactory.builderFor(adapter)` is the convenience API in modern Spring Framework versions; do not assume it exists across every older version.
3. When creating multiple proxies for different providers, give each proxy an explicit **base URL, timeouts, auth policy, and bean name** instead of reusing a mutated shared builder.
4. Proxies are usually registered as singletons and used concurrently across threads per the underlying client; do not build a new factory/client per business request.
5. Choose **synchronous** `RestClient` or **reactive** `WebClient` based on return types and execution model; never swap backends while ignoring semantic differences.

**Testing trap:** if a service is tested only with `@MockBean InventoryHttpApi` or a Mockito mock, the `HttpServiceProxyFactory → RestClientAdapter → HTTP` path never runs. Such mocks work for *unit-testing service logic*, but fail the goal of this lesson.

## 4. Defining a Testable Contract Table

Before writing tests, specify expected wire behavior in a table rather than just reading annotations:

| Condition / Input | Required Request | Expected Response / Exception |
| --- | --- | --- |
| Normal SKU read | GET `/v1/inventory/SKU-42?warehouse=HCM`, Accept JSON, correlation | 200 JSON → `StockDto` |
| Warehouse contains spaces | Query is URI-encoded consistently; server decodes original value | Parameter meaning preserved |
| SKU contains `/` or Unicode | Path variable encoded per API policy | Does not misroute or split into two path segments |
| Create reservation | POST, exact JSON fields, `Idempotency-Key` unchanged across retries | 201 JSON → `ReservationDto` |
| Schema-invalid body | JSON missing required field or wrong type | Classified client/provider error |
| SKU does not exist | GET to exact path | 404 mapped to agreed error/domain result |
| Out of stock | POST with valid payload | `409 Conflict` per contract |
| Provider overloaded | HTTP 503, possibly with `Retry-After` | No infinite retries or misclassifying as data error |
| Request exceeds deadline | Configured client timeout | Classified error type; write outcome may be unknown |
| Cancellation succeeds | DELETE with valid id | 204; proxy does not attempt to deserialize absent object |
| Response adds new field | JSON remains valid per versioning policy | Consumer handles or rejects per DTO/codec settings |

This is a **test decision table**, not a promise that Spring handles every case automatically. For path encoding and list queries, test the actual emitted request rather than guessing from annotations.

## 5. `MockRestServiceServer`: Inspecting Real Requests Built by a `RestClient` Proxy

`MockRestServiceServer` from Spring Test binds to a `RestClient.Builder` before `RestClient` is built. It intercepts HTTP exchanges at the client layer for testing: **it exercises the HTTP interface proxy, annotation resolvers, `RestClient`, and codecs**, without opening real network sockets.

Test dependency (typically included via `spring-boot-starter-test`):

~~~xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-test</artifactId>
  <scope>test</scope>
</dependency>
~~~

Complete JUnit 5 example focused on GET:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.*;
import static org.springframework.test.web.client.response.MockRestResponseCreators.*;

import org.junit.jupiter.api.Test;
import org.springframework.http.HttpMethod;
import org.springframework.http.MediaType;
import org.springframework.test.web.client.MockRestServiceServer;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

class InventoryHttpApiContractTest {

    @Test
    void getStockBuildsCorrectMethodUrlHeadersAndDeserializesBody() {
        RestClient.Builder builder = RestClient.builder()
                .baseUrl("https://inventory.test");

        MockRestServiceServer server =
                MockRestServiceServer.bindTo(builder).build();

        InventoryHttpApi client = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(builder.build()))
                .build()
                .createClient(InventoryHttpApi.class);

        server.expect(requestTo(
                    "https://inventory.test/v1/inventory/SKU-42?warehouse=HCM"))
                .andExpect(method(HttpMethod.GET))
                .andExpect(header("X-Correlation-Id", "trace-001"))
                .andExpect(header("Accept", "application/json"))
                .andRespond(withSuccess(
                    """
                    {"sku":"SKU-42","available":5}
                    """,
                    MediaType.APPLICATION_JSON));

        StockDto stock = client.getStock("SKU-42", "HCM", "trace-001");

        assertThat(stock.sku()).isEqualTo("SKU-42");
        assertThat(stock.available()).isEqualTo(5);
        server.verify();
    }
}
~~~

Assumptions in this example:

- `InventoryHttpApi` and `StockDto` are declared as in Section 2.
- The test has appropriate Jackson/JSON message converters; in Boot apps with `spring-boot-starter-web`, JSON converters are already configured.
- `MockRestServiceServer.bindTo(builder)` must run **before `builder.build()`** so requests route through the mock request factory.
- Expected URLs are written **in full** including base URL, catching URL-prefix assembly mistakes.
- `server.verify()` confirms all expected mock server interactions occurred.

Had this test used `Mockito.when(api.getStock(...))`, it would **never** catch a typo in a URL annotation.

### Why Tests Should Verify More Than HTTP 200

A test that merely stubs a 200 response and asserts `StockDto` values can miss wrong headers, wrong query params, or wrong HTTP methods. Assert the **complete request contract**: method, URL/path/query, content-type, accept, auth/correlation, payload, and related timeout/error mappings.

At the same time, avoid asserting default HTTP client headers like `User-Agent`, `Connection`, or `Content-Length` if they are not part of the contract. Over-asserting transport-generated headers makes tests brittle across library upgrades.

## 6. Testing POST: Body Serialization and `Idempotency-Key`

Write-operation tests must verify the **entire payload**, not just that "the proxy invoked the method".

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.*;
import static org.springframework.test.web.client.response.MockRestResponseCreators.*;

import org.junit.jupiter.api.Test;
import org.springframework.http.HttpMethod;
import org.springframework.http.MediaType;
import org.springframework.test.web.client.MockRestServiceServer;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

class ReservationProxyContractTest {

    @Test
    void reserveSendsJsonAndStableIdempotencyKey() {
        RestClient.Builder builder = RestClient.builder()
                .baseUrl("https://inventory.test");
        MockRestServiceServer server =
                MockRestServiceServer.bindTo(builder).build();

        InventoryHttpApi client = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(builder.build()))
                .build()
                .createClient(InventoryHttpApi.class);

        server.expect(requestTo(
                    "https://inventory.test/v1/inventory/reservations"))
                .andExpect(method(HttpMethod.POST))
                .andExpect(content().contentTypeCompatibleWith(
                        MediaType.APPLICATION_JSON))
                .andExpect(header("Idempotency-Key",
                        "reserve-order-1042"))
                .andExpect(header("X-Correlation-Id", "trace-abc"))
                .andExpect(content().json(
                    """
                    {"orderId":"ORDER-1042","sku":"SKU-42","quantity":2}
                    """, true))
                .andRespond(withStatus(
                        org.springframework.http.HttpStatus.CREATED)
                        .contentType(MediaType.APPLICATION_JSON)
                        .body(
                            """
                            {"reservationId":"RES-918","status":"RESERVED"}
                            """));

        ReservationDto reply = client.reserve(
                new ReserveCommand("ORDER-1042", "SKU-42", 2),
                "reserve-order-1042",
                "trace-abc");

        assertThat(reply.reservationId()).isEqualTo("RES-918");
        assertThat(reply.status()).isEqualTo("RESERVED");
        server.verify();
    }
}
~~~

`content().json(expected, true)` compares JSON structurally under Spring Test's strict mode, so JSON object property order does not matter. Depending on the schema, add tests checking:

- `quantity` serializes as a JSON number, not a string.
- No secrets or internal state leak into request DTOs.
- Timestamps follow consistent ISO-8601/timezone formats; monetary fields retain precision.
- Null vs missing fields behave accurately when the server distinguishes them.
- `schemaVersion` and enums obey evolution rules.
- `Idempotency-Key` stays unchanged **for the same logical operation** across retries, never regenerated per attempt.
- Status 201 and body match the contract; a provider switching to `202 Accepted` + job ID is a **semantic breaking change** even though both are 2xx.

### Avoid Hardcoding Tests Coupled to Arbitrary Serializer Formatting

When the provider accepts structural JSON, use semantic JSON matchers instead of exact string comparisons tied to whitespace or key ordering. If HMAC request signing requires byte-for-byte canonicalization, that is a separate **byte-level contract** requiring tests covering charset, newlines, content encoding, and signed header ordering.

## 7. Testing URL Encoding, Queries, Optional Values, and Headers

The riskiest bugs rarely live on `@GetExchange` itself, but in how values travel on the wire.

### Path Variables with Special Characters

Suppose an SKU contains spaces or `/`:

~~~text
SKU input: "ABC/2026"
Expected API semantics: a single object ID, not an extra route segment
Potential network paths:
  /v1/inventory/ABC%2F2026
  /v1/inventory/ABC/2026
~~~

Which path succeeds depends on server/router/proxy contracts, Spring URI encoding configuration, and whether reverse proxies preserve encoded slashes. If `/` is genuinely allowed inside an ID, **test through a real HTTP transport and ingress**; a client-side mock URL test will not detect an intermediary proxy decoding or rejecting encoded slashes.

If the API forbids slashes in SKUs, validate at the boundary rather than relying on encoding. Never use raw string concatenation to build paths from user input.

### Query Strings with Special Values

`@RequestParam` inputs containing spaces, `+`, `&`, commas, diacritics, or lists require dedicated tests. Depending on the contract, a list may serialize as:

~~~http
GET /v1/inventory/search?tag=red&tag=large
~~~

or:

~~~http
GET /v1/inventory/search?tag=red,large
~~~

These two forms are **not equivalent** if the provider supports only one. Declaring a `List<String>` parameter is no substitute for wire testing. Agree on OpenAPI style/explode settings or an explicit schema and assert the emitted request.

### Headers

Cases worth testing:

- `Authorization` attaches to the right provider and never leaks to other hosts on redirects.
- `X-Correlation-Id` propagates across layers from HTTP ingress → client proxy → downstream.
- `Idempotency-Key` stays stable on retries and distinct across unrelated commands.
- `Accept` and `Content-Type` match active codecs, rather than asserting bodies alone.
- User-influenced header values are validated to block header injection/CRLF or oversized headers.
- Cookies or tenant headers originate from trusted identity context rather than raw caller input.

**Security tests** should confirm tokens/secrets never appear in logs; ordinary contract tests must never store real Bearer tokens in fixtures or CI reports.

## 8. Testing HTTP Errors: 4xx, 5xx, Error Bodies, and Exception Mapping

A proxy does more than turn HTTP 200 into DTOs; it must enforce policy when the server rejects or fails.

Suppose the inventory server returns:

~~~http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{"type":"https://errors.example/insufficient-stock",
 "title":"Not enough stock",
 "status":409,
 "detail":"Stock is already reserved"}
~~~

Decide explicitly: should callers receive an **HTTP exception**, a domain exception, or a failure `Result`? In `RestClient` with default `retrieve()` error handling, 4xx/5xx responses surface as `RestClientResponseException` and subclasses such as `HttpClientErrorException`. **An HTTP interface does not automatically know 409 means "out of stock" in your domain.**

Test for default error behavior of a `RestClient`-backed proxy:

~~~java
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.springframework.test.web.client.match.MockRestRequestMatchers.*;
import static org.springframework.test.web.client.response.MockRestResponseCreators.*;

import org.junit.jupiter.api.Test;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.test.web.client.MockRestServiceServer;
import org.springframework.web.client.HttpClientErrorException;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

class ReservationErrorContractTest {

    @Test
    void conflictIsNotSilentlyConvertedToSuccess() {
        RestClient.Builder builder = RestClient.builder()
                .baseUrl("https://inventory.test");
        MockRestServiceServer server =
                MockRestServiceServer.bindTo(builder).build();

        InventoryHttpApi client = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(builder.build()))
                .build()
                .createClient(InventoryHttpApi.class);

        server.expect(requestTo(
                    "https://inventory.test/v1/inventory/reservations"))
                .andExpect(method(HttpMethod.POST))
                .andRespond(withStatus(HttpStatus.CONFLICT)
                        .contentType(MediaType.APPLICATION_PROBLEM_JSON)
                        .body(
                            """
                            {"type":"about:blank","title":"Insufficient stock",
                             "status":409}
                            """));

        assertThatThrownBy(() -> client.reserve(
                new ReserveCommand("ORDER-1042", "SKU-42", 99),
                "reserve-order-1042", "trace-abc"))
                .isInstanceOf(HttpClientErrorException.Conflict.class);

        server.verify();
    }
}
~~~

If the project registers a custom status handler, the outcome may be a custom domain exception; tests should assert the **application-defined client contract**, not preserve default exceptions after deliberately replacing them.

### Error Matrix to Test

| Response / Failure | Question to Answer | Reference Policy |
| --- | --- | --- |
| `400 Bad Request` | Did client send bad data or schema? | No blind retries; fix contract/validation |
| `401 Unauthorized` | Token expired, wrong audience, auth misconfig? | Refresh credentials per provider if supported; avoid infinite retries |
| `403 Forbidden` | Caller lacks permissions or tenant rejected? | Never turn 403 into 404 or 200 arbitrarily |
| `404 Not Found` | Missing ID; can API return 404 for valid states? | Map to NotFound per contract; do not default to null |
| `409 Conflict` | Conditional contention or out-of-stock business rule? | Classify in domain; prevent duplicate side effects |
| `412 Precondition Failed` | ETag/version mismatch? | Enforce optimistic concurrency |
| `422 Unprocessable Entity` | Syntactically valid payload failing business rules? | Return safe field-level validation/domain error |
| `429 Too Many Requests` | `Retry-After`, per-tenant quota? | Backoff, cap attempts and concurrency |
| `500/502/503/504` | Downstream failure/unavailability/timeout? | Bounded retries for safe ops; circuit breaker |
| Connect refused/DNS/TLS | Never reached HTTP server | Distinguish network exceptions; never assume server ran or did not run |
| Read timeout after POST | Server may have committed yet client lost response | Idempotency + status reconciliation |
| Response JSON violates schema | Server deployed breaking change or corrupt data | Fail explicitly; monitor contract drift |
| `204 No Content` | Does caller expect a DTO? | Valid for `void`; test explicitly when DTO declared |

**Never test errors solely by mocking a Java method to throw `RuntimeException`**: that skips status codes, headers, codecs, error bodies, and `RestClient`/`WebClient` handler policies.

## 9. `204`, Empty Bodies, `ResponseEntity`, and Varying Return Types

HTTP 204 carries different implications depending on the method signature:

~~~java
@DeleteExchange("/reservations/{reservationId}")
void cancel(@PathVariable String reservationId);
~~~

With this contract, a successful DELETE needs no response body. However, if you declare:

~~~java
@GetExchange("/{sku}")
StockDto getStock(@PathVariable String sku);
~~~

and the provider returns 204 without a body, callers may get `null` or a conversion/decoding error depending on the HTTP client adapter, response handling, and version. Never assume the mapping **behaves like `Optional.empty()`**; if 204 is a valid outcome, design the return type and tests to express it explicitly.

An interface can also request metadata:

~~~java
@GetExchange("/{sku}")
ResponseEntity<StockDto> getStockWithStatus(
        @PathVariable("sku") String sku);
~~~

`ResponseEntity` helps when consumers inspect statuses or headers like `ETag`, `Cache-Control`, or versions. With reactive return types, distinguish `Mono<ResponseEntity<T>>` from `ResponseEntity<Flux<T>>` per adapter, as header arrival and body streaming timings differ. Never change a return type without updating response/status contract tests.

### JSON Backward Compatibility

A Java record DTO with a required canonical constructor can reject missing fields more strictly than a DTO with defaults. Conversely, new response fields may be ignored or rejected depending on Jackson config. Maintain at least two fixtures:

- **Old provider → new consumer**: response omits new fields or uses older enums.
- **New provider → old consumer**: response adds new fields or new enum values.

Never enable Jackson `FAIL_ON_UNKNOWN_PROPERTIES` off or `@JsonIgnoreProperties(ignoreUnknown=true)` as a blanket fix without assessing data-loss or silent-breakage risks. Design *tolerant readers* aligned with the business contract.

## 10. Testing with a Real HTTP Stub Server: WireMock

`MockRestServiceServer` does not send requests over sockets. It excels at catching mapping/serialization issues, yet **cannot test** DNS, transport connect/read timeouts, redirects, chunking, TLS, or hung server connections.

To exercise the real HTTP transport, use a stub server such as WireMock 3. Example Maven test dependency (pin a project-approved version):

~~~xml
<dependency>
  <groupId>org.wiremock</groupId>
  <artifactId>wiremock</artifactId>
  <version>${wiremock.version}</version>
  <scope>test</scope>
</dependency>
~~~

Testing GET over a real local TCP socket:

~~~java
import static com.github.tomakehurst.wiremock.client.WireMock.*;
import static com.github.tomakehurst.wiremock.core.WireMockConfiguration.*;
import static org.assertj.core.api.Assertions.assertThat;

import com.github.tomakehurst.wiremock.WireMockServer;
import org.junit.jupiter.api.Test;
import org.springframework.web.client.RestClient;
import org.springframework.web.client.support.RestClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

class InventoryWireContractTest {

    @Test
    void proxySendsRequestOverActualHttpTransport() {
        WireMockServer server =
                new WireMockServer(wireMockConfig().dynamicPort());
        server.start();
        try {
            server.stubFor(get(urlEqualTo(
                    "/v1/inventory/SKU-42?warehouse=HCM"))
                    .withHeader("X-Correlation-Id",
                            equalTo("trace-wire"))
                    .willReturn(okJson(
                            """
                            {"sku":"SKU-42","available":5}
                            """)));

            RestClient restClient = RestClient.builder()
                    .baseUrl(server.baseUrl())
                    .build();

            InventoryHttpApi client = HttpServiceProxyFactory
                    .builderFor(RestClientAdapter.create(restClient))
                    .build()
                    .createClient(InventoryHttpApi.class);

            StockDto reply =
                    client.getStock("SKU-42", "HCM", "trace-wire");

            assertThat(reply.available()).isEqualTo(5);
            server.verify(1, getRequestedFor(urlEqualTo(
                    "/v1/inventory/SKU-42?warehouse=HCM")));
        } finally {
            server.stop();
        }
    }
}
~~~

Advantages over `RestClient`-level mocking:

- Opens a real HTTP listener on a dynamic port.
- Client executes through its real request factory/transport and local network stack.
- Exercises serialization, request target, headers, and response decoding end-to-end.
- Simulates HTTP 429, 503, delays, connection resets, or corrupt bodies using WireMock stubs and fault injection.

**Limitations:** a local HTTP stub still does not fully replicate DNS, ingress/reverse proxies, mTLS, service meshes, load-balancer retries, or real providers. Infrastructure-level policies require integration environments or production-like end-to-end tests.

## 11. Timeouts and Retries: Use Transport Tests and Account for Unknown Outcomes

A timed-out request does not prove the server never ran. Especially with `reserve`, the server may have created the reservation before the TCP response dropped.

Example `RestClient` configuration using a request factory with bounded timeouts:

~~~java
import org.springframework.http.client.SimpleClientHttpRequestFactory;
import org.springframework.web.client.RestClient;

SimpleClientHttpRequestFactory requestFactory =
        new SimpleClientHttpRequestFactory();

requestFactory.setConnectTimeout(300); // milliseconds
requestFactory.setReadTimeout(700);    // milliseconds

RestClient restClient = RestClient.builder()
        .baseUrl("https://inventory.internal.example")
        .requestFactory(requestFactory)
        .build();
~~~

These values are illustrative and environment-dependent. `connectTimeout` bounds establishing the connection; `readTimeout` bounds transport reads, which is not necessarily the **entire business deadline**. Other transports such as Apache HttpClient, JDK HttpClient, and Reactor Netty expose distinct APIs and semantics. For strict SLAs, enforce an overall budget at the orchestration layer instead of relying solely on one socket timeout.

### Controlled Timeout Tests

Configure WireMock to delay the response past the read timeout:

~~~java
server.stubFor(get(urlEqualTo(
        "/v1/inventory/SKU-42?warehouse=HCM"))
        .willReturn(aResponse()
                .withStatus(200)
                .withFixedDelay(2000)
                .withHeader("Content-Type", "application/json")
                .withBody(
                    """
                    {"sku":"SKU-42","available":5}
                    """)));
~~~

The test proxy must use a `RestClient` with a **read timeout shorter than 2000 ms**. After invoking and catching the exception, verify both reasonable elapsed duration and the transport error type for your active request factory; avoid asserting OS-specific message strings or overly fragile internal exception messages.

Do not test retries by spinning up 10 `WireMockServer` instances in one test or sleeping endlessly with `Thread.sleep`. Build a scenario with measurable attempt counts, short timeouts, clean server shutdown, and assertions verifying total attempts/backoff stay within budget.

### Reliable Retry Test Suite

Assertions to verify:

1. **Retried errors** occur only for allowlisted exception/status classes.
2. **Retry counts** are bounded (e.g., at most two retries after the first call).
3. **`Idempotency-Key`** stays identical across all attempts of the same business command.
4. **Payload** is never rebuilt with fresh random IDs or timestamps that turn retries into different commands.
5. **Total duration** stays within the caller's SLA even when multiple layers exist.
6. 400/401/403/422 errors are never blindly retried.
7. Server success followed by dropped response **never produces a second side effect** on retry.
8. When the circuit breaker opens, the caller gets the designed fallback/error promptly instead of hanging.

Some stacks configure retries in `RestClient`, the service layer, the API gateway, and messaging listeners. Stacked retries multiply HTTP attempts; tests must count **actual requests hitting the stub server**, not just Java service method invocations.

## 12. `WebClient`-Backed HTTP Interfaces: Testing Reactive Return Types

In WebFlux applications, `HttpServiceProxyFactory` can use `WebClientAdapter`:

~~~java
import org.springframework.web.reactive.function.client.WebClient;
import org.springframework.web.reactive.function.client.support.WebClientAdapter;
import org.springframework.web.service.invoker.HttpServiceProxyFactory;

WebClient webClient = WebClient.builder()
        .baseUrl("https://inventory.internal.example")
        .build();

var reactiveProxy = HttpServiceProxyFactory
        .builderFor(WebClientAdapter.create(webClient))
        .build()
        .createClient(ReactiveInventoryHttpApi.class);
~~~

Reactive interface:

~~~java
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.service.annotation.GetExchange;
import org.springframework.web.service.annotation.HttpExchange;
import reactor.core.publisher.Mono;

@HttpExchange(url = "/v1/inventory", accept = "application/json")
public interface ReactiveInventoryHttpApi {

    @GetExchange("/{sku}")
    Mono<StockDto> getStock(@PathVariable("sku") String sku);
}
~~~

Testing over a real WireMock socket with `StepVerifier`:

~~~java
import static org.assertj.core.api.Assertions.assertThat;
import static reactor.test.StepVerifier.*;

import reactor.core.publisher.Mono;

Mono<StockDto> result = reactiveProxy.getStock("SKU-42");

create(result)
        .assertNext(stock -> {
            assertThat(stock.sku()).isEqualTo("SKU-42");
            assertThat(stock.available()).isEqualTo(5);
        })
        .verifyComplete();
~~~

`reactiveProxy` must be built with a `WebClient` pointing to the test stub server, never production. `StepVerifier` provides **subscription** and sequence verification. If a test creates a `Mono` without subscribing, no HTTP request may be sent at all.

### Completion and Cancellation Differences

For `Mono<T>`, test success, error, and cancellation/timeout behavior. For streaming `Flux<T>`, verify item counts, ordering, completion or long-lived stream behavior, backpressure, and subscription cancellation. Calling `block()` just to "inspect data" cannot replace reactive contract tests.

Cancelling a subscription aborts client-side response reading, yet **does not guarantee** server-side rollback of started work. Idempotency rules still apply to write operations.

### Avoid Blocking on Event Loops

Never call synchronous `RestClient` inside a WebFlux handler on a Netty event loop without proper scheduling/bulkheads. `HttpServiceProxyFactory` proxies do not magically convert blocking code into non-blocking execution; the underlying adapter and return types determine execution behavior.

## 13. Testing from the Provider Side: Is the Contract Still Accurate?

Client tests prove the proxy emits the requests expected by the consumer, yet the provider may have changed:

- `/v1/inventory/{sku}` to `/inventory/{sku}`;
- `warehouse` to `warehouseId`;
- `available` from integer to string;
- `201 Created` to `202 Accepted`;
- `409 Conflict` to `422`;
- adding a new required request field;
- authentication, authorization, ETag, or rate-limit rules.

**Provider contract tests** verify the server implementation complies with the contract. Two useful approaches follow.

### 13.1. Testing Controllers/Servers Against the API Contract

If the provider is Spring MVC:

~~~java
@RestController
@RequestMapping("/v1/inventory")
public class InventoryController {

    @GetMapping("/{sku}")
    public StockDto getStock(
            @PathVariable String sku,
            @RequestParam String warehouse) {
        return stockService.find(sku, warehouse);
    }
}
~~~

MVC tests can use `MockMvc` to verify routes, queries, and JSON responses:

~~~java
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.test.web.servlet.MockMvc;

@WebMvcTest(InventoryController.class)
class InventoryProviderContractTest {

    @Autowired MockMvc mvc;

    @Test
    void servesDocumentedGetStockContract() throws Exception {
        mvc.perform(get("/v1/inventory/SKU-42")
                    .param("warehouse", "HCM"))
                .andExpect(status().isOk())
                .andExpect(content().contentTypeCompatibleWith(
                        org.springframework.http.MediaType.APPLICATION_JSON))
                .andExpect(jsonPath("$.sku").value("SKU-42"))
                .andExpect(jsonPath("$.available").isNumber());
    }
}
~~~

This snippet assumes the provider configures/mocks `stockService` returning a stable fixture along with security/filters; otherwise `@WebMvcTest` requires `@MockBean`/`@MockitoBean` or test fixture wiring per Boot version. This is a provider test sketch, not full production source. If tests mock the controller's service to return ideal JSON while production service mapping diverges, include tests covering real service/database/serialization paths as well.

### 13.2. Consumer-Driven Contracts (CDC)

With Spring Cloud Contract or Pact, consumers specify the exact requests/responses they rely on. Providers run verification to prove the current implementation satisfies those expectations. Typical workflow:

~~~mermaid
flowchart TD
    C["Consumer: defines contract/stub"] --> AR["Versioned contract artifact"]
    AR --> P["Provider: verifies contract"]
    P --> CI["Provider CI gate"]
    AR --> CT["Consumer: proxy tests against stub"]
    CT --> CC["Consumer CI gate"]
    CI --> DEP{"Safe to deploy?"}
    CC --> DEP
~~~

Key considerations:

- **Contract tests do not replace proxy tests** if consumer tests call stubs via a different HTTP client than production. Always keep at least one test driving the real `InventoryHttpApi` proxy.
- Contract artifacts must be **versioned** alongside provider/consumer releases. Pointing blindly to `"latest"` makes CI non-reproducible.
- Provider verification must run with realistic auth, validation, and serializers—not fake stub responses from mocked endpoints.
- For backward compatibility, verify the new provider against all **deployed** consumer versions, not just the latest consumer source branch.
- Never store real secrets or PII in contract examples, stub recordings, or CI logs.

**OpenAPI specifications** also help define and compare HTTP schemas. However, an OpenAPI file and Java `@HttpExchange` interface do not guarantee compatibility automatically without explicit verification or tooling. An updated OpenAPI spec does not prove the server actually deployed matching code.

## 14. Data Contracts: Validate Structure and Semantics, Not Just DTOs

Two JSON payloads can deserialize into the exact same DTO yet represent opposite business meanings:

~~~json
{"sku":"SKU-42","available":0}
~~~

and:

~~~json
{"sku":"SKU-42","available":-1}
~~~

Both fit `int`, yet negative stock violates domain invariants. Layer contract checks accordingly:

| Contract Layer | Examples | What Tests Should Do |
| --- | --- | --- |
| HTTP syntax | Method, path, query, `Content-Type` | Assert wire requests |
| Schema | Required/optional fields, types, enums | Decode and schema validation |
| Semantics | `available >= 0`, `quantity > 0` | Domain validation/fixtures |
| Version compatibility | Adding optional field, evolving enums | Old/new consumer-provider matrix |
| Authorization | Callers cannot inspect another tenant's SKU | Security contract tests |
| Status codes | 201 vs 202, 204 vs 200 | Assert statuses and response semantics |
| Repeatability | `Idempotency-Key` on identical command | Server does not create duplicate reservations |
| Consistency | DB commit vs HTTP response/retry | Fault-inject post-commit drops and verify state |

For numeric data, never use `double` for money; timestamps must agree on timezone/precision and encoding. Where objects distinguish `null` from omitted fields, test both. Consumers tolerant of unknown fields must still enforce validation on **required** fields.

### Contract Evolution Policy

Adding an optional response field is usually **relatively safe** when existing consumers ignore unknown fields, though strict decoders can still fail. Breaking changes such as renaming paths, changing HTTP verbs, removing fields, altering enums, changing status semantics, or requiring new headers typically require migration/versioning.

Test suites should keep **fixtures from production-deployed versions** to catch compatibility drift. During blue-green/canary rollouts when old and new provider versions coexist, ensure all active consumers handle responses from both versions.

## 15. Proxies Do Not Share a Database Transaction with Remote Servers

A Spring service method may be annotated `@Transactional`:

~~~java
@Transactional
public ReservationDto reserveForOrder(ReserveCommand command) {
    orderRepository.markReserving(command.orderId());
    return inventoryHttpApi.reserve(
            command,
            stableIdempotencyKey(command),
            currentTraceId());
}
~~~

**A local Spring JDBC transaction does not span HTTP requests.** Common failure modes:

1. DB transaction opens, HTTP `reserve` succeeds, then DB commit fails → inventory is reserved while the SQL order rolls back.
2. HTTP `reserve` commits on the server, then response times out → client may retry and create a second reservation without idempotency.
3. DB commit succeeds, yet a subsequent HTTP step fails → requires reconciliation or compensation.
4. Holding DB transactions/locks open during slow HTTP calls starves connection pools and raises deadlock risk.

Architectural separation resolves this:

- Persist `PENDING_RESERVATION` state and an outbox row in a short SQL transaction.
- A worker picks up the job and invokes the proxy with a **deterministic idempotency key** bound to the business operation.
- The inventory server persists a receipt keyed by `(callerId, idempotencyKey)` in the same transaction that creates the reservation.
- The worker updates state to `RESERVED` or `RETRY_PENDING`, backed by recovery/reconciliation.
- When recovery cannot proceed, trigger business compensation rather than expecting HTTP rollback.

Thorough integration tests should **deliberately drop the response after the provider commits**, retry with the same key, and assert only one reservation exists. Mocking the method to throw an exception never exercises this failure window.

### Contract for a Retry Attempt

Tests must guarantee:

- No fresh `orderId`, `requestId`, or idempotency key is generated per retry attempt.
- Retries fire only for permitted failure types within the total deadline.
- The provider replays the persisted result of the first command on duplicate retries, even if the first response was lost.
- Concurrent duplicate requests are serialized via unique constraints/locks rather than `SELECT` before `INSERT`.
- If brokers/outboxes also retry, total attempt counts remain bounded and observable.

## 16. Security, Configuration, and Observing Proxies in Production

A functionally compliant proxy can still be unsafe if pointed at the wrong base URL, sending leaked credentials, or dumping sensitive data into logs.

### Environment Configuration

~~~yaml
app:
  inventory:
    base-url: https://inventory.internal.example
    connect-timeout: 500ms
    read-timeout: 2s
~~~

`connect-timeout` and `read-timeout` here are **application-defined properties**; Spring Boot does not automatically wire them to every proxy just because they appear under `app.inventory`. Bind them via `@ConfigurationProperties` and apply them to your request factory/client connector.

To catch misconfigurations early, validate URL schemes/hosts, positive timeouts, and endpoint formats on startup. Prevent user requests from arbitrarily overriding base URLs (SSRF risk). With multiple providers, use distinct bean names/qualifiers and test that the inventory proxy never sends payment `Authorization` headers.

### Logging / Tracing / Metrics

Request flow:

~~~mermaid
sequenceDiagram
    participant U as Checkout API
    participant P as HTTP Interface Proxy
    participant N as RestClient/WebClient
    participant S as Inventory Provider
    U->>P: getStock(SKU-42, HCM, traceId)
    P->>N: GET path + query + headers
    N->>S: HTTP request, trace context
    S-->>N: 200 JSON / 409 / 503
    N-->>P: DTO / exception / reactive signal
    P-->>U: Business result or failure
~~~

Recommended telemetry:

- `client.name`, `peer.service`, operation/route template, HTTP method, status category.
- Latency p50/p95/p99, connect/read timeouts, retry attempts, in-flight calls.
- Error class (HTTP 4xx vs 5xx vs network vs deserialization).
- Circuit breaker state, fallback rate, auth refresh counts.
- Idempotency duplicate hits and count of commands ending in "unknown outcome".
- Consumer/provider versions and CI contract verification failures.

When using Spring Boot Actuator/Micrometer/Observation, verify instrumentation is active on the `RestClient.Builder` or `WebClient.Builder` you inject. Building manual builders without Boot customizers can silently drop metrics and tracing while the proxy appears to function normally.

Never tag metrics with `orderId`, unbounded `sku`, user IDs, or full URLs containing query strings: that blows up cardinality and leaks data. Use route templates, provider names, and status categories. Never log Bearer tokens, API keys, or full customer payloads.

### Essential Security Tests

- Never forward tokens to another host via unauthorized redirects.
- Verify TLS certificates and trust chains; never disable validation just to pass test environments.
- Confirm `Authorization` never appears in error messages, traces, or logs.
- Prevent callers from controlling absolute URLs if the interface allows `URI` overrides or dynamic URL parameters.
- Enforce request size, response size, and read-time bounds per SLA.
- Verify real provider authentication and authorization; correlation IDs and idempotency keys are not identity proofs.

## 17. Comprehensive Test Matrix for HTTP Interface Proxies

A standard review matrix for pull requests:

| Group | Case | Appropriate Test Layer |
| --- | --- | --- |
| Mapping | GET right verb, prefix, path variable | `MockRestServiceServer` |
| Query | Spaces, Unicode, lists, optional, null | Mock + WireMock for special encoding |
| Headers | `Accept`, `Content-Type`, auth, correlation | `MockRestServiceServer` |
| Request body | DTO JSON fields/types, null/unknown | `MockRestServiceServer` |
| Response body | 200/201 decoded accurately into DTO | `MockRestServiceServer` |
| Empty response | 204 with `void`, unexpected empty body | `MockRestServiceServer` |
| Error status | 400/401/403/404/409/422/429/503 | Mock + provider contract |
| Error payload | `application/problem+json`, fields/version | Mock + provider verification |
| Connect/read timeout | Server delay, unreachable port | WireMock / transport test |
| TLS/redirect/proxy | Hostnames, certificates, redirects | Integration environment |
| Retries | Attempt cap, backoff, stable key | WireMock scenario + provider state |
| Auth rotation | Expired/refreshed token, right audience | Integration/security contract |
| Reactive | `Mono`/`Flux` success, error, cancel, demand | WireMock + `StepVerifier` |
| Provider compatibility | Old/new consumer vs new/old response | CDC/OpenAPI + provider tests |
| Data consistency | Remote commit followed by lost response | Full integration/fault injection |
| DB/broker boundary | Transactional outbox, duplicate messages | Integration + real database |
| Observability | Trace propagation, route tags, safe logging | Integration instrumentation test |

Not every cell needs a heavyweight end-to-end test. Balance the pyramid:

- Many fast proxy/mock tests to catch mapping mistakes.
- Targeted real-socket HTTP tests for timeouts, transports, streaming, and retries.
- Provider contract verification on every provider change.
- Focused fault-injected end-to-end tests for critical consistency paths.

## 18. CI Pipeline and Contract Drift Detection

An effective CI pipeline separates fast checks from slower ones and catches contract drift before deployment:

~~~mermaid
flowchart TD
    A["Consumer pull request"] --> B["Compile + static contract review"]
    B --> C["Proxy tests / MockRestServiceServer"]
    C --> D["WireMock transport tests"]
    D --> E["Versioned consumer contract artifact"]
    E --> F["Provider CI contract verification"]
    F --> G{"Compatible with deployed consumers?"}
    G -->|Yes| H["Release/canary + smoke tests"]
    G -->|No| I["Block deploy / version API / expand-contract"]
~~~

Workflow:

1. **Consumer** updates the interface and expected HTTP request/response tests in the same pull request.
2. Version contract artifacts/fixtures with releases or commit hashes rather than pointing tests at a silently mutating `"latest"` stub.
3. **Provider** verifies contracts required by currently running consumers, not only the latest consumer source branch.
4. When evolving provider schemas, follow **expand-contract**: add backward-compatible extensions first, roll out consumers, and only then retire old fields.
5. For major status/route/security changes, release a new API version or maintain parallel endpoints during transition.
6. Run post-deploy canary/smoke checks watching 4xx/5xx rates, deserialization errors, timeouts, retry rates, and compatibility.
7. Keep curated error response fixtures under version control and review updates deliberately; never blindly overwrite snapshots and treat every change as valid.

**Passing proxy tests in consumer CI does not prove the live provider honors the contract.** Connect consumer and provider CI via contract verification, complemented by integration tests against staging or prod-like environments.

## 19. Troubleshooting: Proxy Compiles Yet Calls Wrongly

| Symptom | Common Cause | How to Verify |
| --- | --- | --- |
| 404 even though provider is healthy | Wrong URL prefix, API version, or path variable encoding | Assert request URL in proxy test vs provider route |
| Provider receives wrong query | Mismatched `@RequestParam` name, list/encoding mismatch | WireMock exact query, provider contract |
| `415 Unsupported Media Type` | Wrong `Content-Type` or missing converter | Inspect request header/body and codec config |
| `406 Not Acceptable` | Provider does not support `Accept` type | Compare declared media type with provider |
| 400 from missing body field | DTO serialization, null/default policy mismatch | Strict JSON fixtures and provider validation |
| 401/403 | Missing/wrong token, audience, scope, tenant | Assert auth header reaches right destination; check safe security logs |
| 409 treated as retryable transport failure | Overly broad exception catch | Assert `HttpClientErrorException.Conflict`; map in domain |
| Infinite 503 retries | Multi-layer retries without shared budget | Count real requests in WireMock/metrics |
| Proxy tests pass yet real network times out | Mock tests skip sockets and real timeouts | Add WireMock delays and request factory timeouts |
| `Mono` returned yet no request fires | No subscriber | `StepVerifier`/subscription tests |
| 204 produces null DTO | Return type does not reflect empty response | Assert 204 response contract and mapper |
| New enum value in response breaks decoding | Strict consumer enum/DTO incompatibility | Consumer/provider schema compatibility tests |
| Breaking provider change goes undetected | Unit tests only mocked interface without CDC | Publish contract artifacts and verify on provider |
| HTTP POST runs twice after timeout | Retrying command without stable `Idempotency-Key` | Test post-commit response loss + unique receipts |
| Empty metrics/tracing | Built client without Boot customizer | Test observation via `RestClient.Builder`/`WebClient.Builder` |
| Connection pool exhaustion | Missing concurrency/timeout limits or unclosed response streams | Pool metrics, thread dumps, transport tests |
| Proxy hits wrong backend | Profile/config base URL or wrong bean qualifier | Assert host in tests; validate environment config |

### Ordered Diagnostic Process

1. Read the expected **wire contract**: method, URL, query, headers, body, status, and schema.
2. Confirm tests invoke the **`HttpServiceProxyFactory` proxy**, not a Mockito mock.
3. Inspect emitted requests via `MockRestServiceServer` and WireMock, checking the active adapter/backend.
4. If the client contract is accurate yet the provider rejects requests, inspect live provider routes, validation, auth, and version.
5. If failures occur only outside unit tests, inspect DNS, TLS, ingress, redirects, pooling, timeouts, and instrumentation.
6. For write requests with unknown outcomes, check database/idempotency receipts before retrying or compensating.
7. Lock in a regression test at the **exact layer that failed**, instead of adding arbitrary sleeps or raising timeouts blindly.

## 20. Pre-Production Checklist for HTTP Interface Proxies

- The interface's paths, HTTP methods, media types, parameters, DTOs, and return types match the provider's supported API.
- The proxy is built with `HttpServiceProxyFactory` and the right `RestClientAdapter`/`WebClientAdapter` for your execution model.
- At least one **real proxy test** verifies method + URL + query + headers + body + response/exception handling, rather than mocking only the Java interface.
- Tests cover special characters in URLs, list queries, nullable/optional body fields, and empty responses.
- A 4xx/5xx matrix, error bodies, and exception/domain mappings are explicitly defined without treating all errors as retryable.
- Real transport tests cover connect/read timeouts, redirects/TLS/ingress where applicable, and subscribed reactive publishers.
- An agreed provider contract (OpenAPI/CDC) and provider verification catch schema drift during deployments.
- Retries are bounded by total deadlines with stable idempotency keys; writes never duplicate on lost responses.
- HTTP requests are never treated as part of a local SQL transaction; use outbox, state machines, and reconciliation where needed.
- Auth, base URLs, timeouts, pools, and observation are environment-configured without exposing credentials or PII in logs/metrics.
- CI maintains versioned contract fixtures, verifies consumer/provider compatibility, and runs post-deploy canary/smoke checks.
