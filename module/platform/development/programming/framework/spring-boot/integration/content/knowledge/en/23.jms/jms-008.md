# Session Acknowledgment, Transactions, and Redelivery

## 1. Context and objectives

In the **SPRING_BOOT_INTEGRATION** module, Spring Boot coordinates integration across HTTP clients, databases, caches, message brokers, and Spring Integration adapters. When an application uses **JMS** (Jakarta Messaging) to receive commands or events from a queue/topic, processing reliability does not depend solely on whether the listener method runs. It depends on **when the broker is told delivery succeeded**, **transaction boundaries**, and **redelivery after failures**.

A common scenario: a consumer receives a payment event, updates the order in PostgreSQL, and the process terminates before the broker receives confirmation. The broker may redeliver the same event; without duplicate protection, business logic could execute twice. Conversely, if a message is acknowledged too early and the database update fails, the event disappears from the queue without completing business work.

This lesson belongs to the **JMS** chapter and focuses on three decisions:

1. **Acknowledgment mode:** who acknowledges and at what point?
2. **Session transaction:** which JMS sends/receives commit or roll back together?
3. **Redelivery and dead-lettering:** after a failure, where does the message go and when do retries stop?

After this lesson, you will be able to:

- Distinguish `AUTO_ACKNOWLEDGE`, `CLIENT_ACKNOWLEDGE`, `DUPS_OK_ACKNOWLEDGE`, and transacted sessions.
- Configure Spring Boot / Spring JMS listener containers with intentional transaction boundaries.
- Understand the relationship between JMS transactions, JDBC transactions, and XA/JTA.
- Design retries, redelivery, DLQs, and idempotent consumers without losing or duplicating messages.
- Test state after exceptions, crashes, rollbacks, and concurrent consumers.

## 2. Where do Session, Message, and the listener container sit?

JMS is the standard API for communicating with a message broker. Key types:

| Component | Role |
| --- | --- |
| **ConnectionFactory** | Creates connections to the provider/broker |
| **Connection / JMSContext** | Manages the connection or JMS context depending on API usage |
| **Session** | Sequential boundary for send/receive operations, acks, and JMS transactions |
| **MessageProducer / MessageConsumer** | Sends or receives messages on a destination |
| **Queue** | Typically each message goes to one consumer in a competing group |
| **Topic** | Publish–subscribe; each eligible subscription gets its own message stream |
| **Message** | Body, standard headers, and properties such as `JMSMessageID` and `JMSRedelivered` |
| **DefaultMessageListenerContainer** | Spring manages consumer threads, Sessions, message receipt, handler calls, and commit/rollback |
| **@JmsListener** | Declares a message endpoint executed via the designated listener container |

In Spring Boot 3.x/4.x with Jakarta Messaging, imports use **`jakarta.jms.*`**; legacy Spring Boot 2.x/JMS apps use **`javax.jms.*`**. Never mix both namespaces in the same configuration.

~~~mermaid
flowchart TD
    A["Producer: JmsTemplate / JMS API"] --> B["JMS broker"]
    B --> C["Queue / subscription"]
    C --> D["Spring listener container"]
    D --> E["Session + consumer"]
    E --> F["@JmsListener"]
    F --> G["Service / DB / HTTP / event"]
    G --> H{"Handler completed?"}
    H -->|"Success"| I["ACK or commit JMS"]
    H -->|"Threw error"| J["Rollback / recover per mode"]
    J --> K["Broker decides redelivery / DLQ"]
    I --> B
    K --> B
~~~

**Never create a single Session shared across multiple threads.** Under standard JMS rules, a `Session` is a single-threaded sequential context, not a thread-safe object for arbitrary sharing. With concurrent listeners, the container manages dedicated consumers/Sessions. To raise throughput, configure container concurrency while checking broker, database, and per-key ordering limits.

## 3. What is acknowledgment and why does it matter?

**Acknowledge (ACK)** informs the JMS provider that message receipt is confirmed per session rules. It is not synonymous with "database committed" or "downstream HTTP succeeded" unless the application explicitly coordinates those boundaries.

| Mode | Who/what ACKs? | When listener fails | Fits when |
| --- | --- | --- | --- |
| **AUTO_ACKNOWLEDGE** | JMS provider/container ACKs automatically | In Spring `DefaultMessageListenerContainer`, redelivery is not guaranteed when the handler throws; risk of losing business messages | Work where loss on failure is acceptable or simple non-critical tasks |
| **CLIENT_ACKNOWLEDGE** | Client may call `Message.acknowledge()`; Spring listener containers usually ACK after handler succeeds | Spring container provides best-effort redelivery when handler fails | Flows needing post-handler ack without JMS transactions |
| **DUPS_OK_ACKNOWLEDGE** | Provider may delay / lazily ACK | Allows duplicate delivery; do not rely on listener exceptions for guaranteed retries | Workloads tolerating duplicates to reduce ACK overhead |
| **SESSION_TRANSACTED** | **`Session.commit()/rollback()`**, not standalone ACK | Handler error rolls back the transaction, making the message eligible for redelivery | Flows needing strong recovery or atomic receive+send within one local JMS transaction |

### 3.1. Warning: AUTO_ACKNOWLEDGE differs across containers

With Spring's **`DefaultMessageListenerContainer`**, **`AUTO_ACKNOWLEDGE`** may occur **before invoking the listener**; thus throwing an exception inside the listener will not cause redelivery. With **`SimpleMessageListenerContainer`**, ACK timing differs and still does not guarantee redelivery on listener exceptions. Inferring Spring listener behavior solely from generic JMS spec summaries is unsafe.

When **at-least-once** processing is required, Spring recommends **`sessionTransacted=true`**, or `CLIENT_ACKNOWLEDGE` if you understand its best-effort limits. Actual guarantees still depend on the provider, message persistence, queue/topic semantics, and recovery settings.

### 3.2. CLIENT_ACKNOWLEDGE is not per-message ACK

In standard JMS, calling **`Message.acknowledge()`** under `CLIENT_ACKNOWLEDGE` acknowledges **all messages consumed so far on that Session**, not solely the single message in hand. Some brokers offer proprietary **individual acknowledge** extensions, which are non-portable.

~~~java
// Direct JMS API illustration, NOT running inside a listener container:
try (JMSContext context =
             connectionFactory.createContext(JMSContext.CLIENT_ACKNOWLEDGE)) {

    JMSConsumer consumer = context.createConsumer(
            context.createQueue("orders.paid"));
    Message message = consumer.receive(1_000);

    if (message != null) {
        processBusinessMessage(message);
        message.acknowledge();
    }
}
~~~

This snippet covers application-managed synchronous receives; implement `processBusinessMessage` and error recovery yourself. With **`@JmsListener`**, Spring owns the Session and normally ACKs after the listener completes under `CLIENT_ACKNOWLEDGE`; do not call ACK manually mid-flight without full control over the Session lifecycle. Increasing concurrency makes session-scoped ACK even riskier to manage manually.

### 3.3. What does DUPS_OK_ACKNOWLEDGE mean?

The provider may defer ACKs for efficiency. After a crash, the app may receive messages again even if already processed. The mode name means "duplicates are acceptable," **not** that the framework deduplicates automatically. Listeners updating balances or triggering payments should never choose it purely for throughput.

## 4. Transacted sessions: commit and rollback at the JMS layer

With a **transacted Session**, one JMS unit of work can combine receiving a message and sending another message on **that same Session/transaction**. On **`commit`**, the broker confirms receipt and makes sent messages visible. On **`rollback`**, receipt is undone and the message becomes eligible for redelivery per provider policy.

~~~mermaid
sequenceDiagram
    participant Q as Source JMS Queue
    participant C as Spring Listener Container
    participant S as JMS Session
    participant H as Application Handler
    C->>S: begin local JMS transaction
    S->>Q: receive OrderPaid
    C->>H: invoke listener
    alt Handler succeeds
        H-->>C: return
        C->>S: commit()
        S-->>Q: ACK/commit receive
    else Handler throws
        H--xC: exception
        C->>S: rollback()
        S-->>Q: redelivery eligible
    end
~~~

In Spring's **`DefaultMessageListenerContainer`** with **`sessionTransacted=true`**, the container commits or rolls back after each listener invocation per transaction semantics. Never call **`session.commit()`** manually inside a Spring-managed **`@JmsListener`**. When a Session is transacted, **`sessionAcknowledgeMode`** does not govern ACKs the way non-transacted modes do; keep the two settings distinct.

**Key limitation:** a **local JMS transaction** applies only to JMS resources participating in that Session/ConnectionFactory. It **does not automatically encompass**:

- `INSERT`/`UPDATE` statements against PostgreSQL on a separate `DataSource`.
- Outbound REST or `WebClient` calls to external services.
- Redis/cache writes or Kafka publishes.
- JMS sends on a different Session/ConnectionFactory outside that transaction.

If the DB commits and then the JMS commit fails, the message still redelivers. That is why at-least-once consumers need idempotency.

## 5. Spring Boot: dependencies and listener configuration

### 5.1. Example with ActiveMQ Artemis

Spring Boot supplies starters for JMS brokers. Maven example with **ActiveMQ Artemis**:

~~~xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-artemis</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-jdbc</artifactId>
    </dependency>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>
~~~

Examples target Spring Boot 3.x or compatible Boot releases with BOM/parent version management. For ActiveMQ Classic, IBM MQ, or other JMS providers, switch the starter/client and `ConnectionFactory` configuration accordingly. Never assume every broker shares identical DLQ, retry delay, or XA behavior.

~~~yaml
spring:
  artemis:
    mode: native
    broker-url: tcp://localhost:61616
    user: shop_consumer
    # Provide SPRING_ARTEMIS_PASSWORD via runtime environment.
  jms:
    listener:
      session:
        transacted: true
      min-concurrency: 2
      max-concurrency: 6
~~~

This assumes an Artemis broker is running with the **`orders.paid`** queue and valid credentials. Never store real passwords in YAML or source control. Exact modern Spring Boot property names are **`spring.jms.listener.session.transacted`** and **`spring.jms.listener.session.acknowledge-mode`**; do not place them directly under **`spring.jms.listener`**.

Key points:

- Spring Boot often configures the default listener factory as **transacted** when no JTA transaction manager is present; when JTA is present, it can integrate with that transaction manager. Still, **explicit configuration and runtime verification** are clearer.
- **`min-concurrency / max-concurrency`** control consumer/Session counts, not retry attempt limits.
- Spring Boot may expose a **`CachingConnectionFactory`** for general JMS sends; listener containers need their own connection recovery management. When building a custom listener factory, prefer Boot's **`DefaultJmsListenerContainerFactoryConfigurer`** and unwrap any caching `ConnectionFactory` per your Boot version's guidance.
- Destination names/creation, durability, and DLQ policies belong to broker setup; Spring listeners do not provision full production broker policies.

### 5.2. Listener receiving payloads and letting the container commit

~~~java
public record OrderPaid(
        String eventId, String orderId, long paymentVersion) {}

@Component
public class PaidOrderJmsListener {
    private final ObjectMapper objectMapper;
    private final PaidOrderService service;

    public PaidOrderJmsListener(
            ObjectMapper objectMapper, PaidOrderService service) {
        this.objectMapper = objectMapper;
        this.service = service;
    }

    @JmsListener(destination = "orders.paid")
    public void onMessage(String json) throws JsonProcessingException {
        OrderPaid event = objectMapper.readValue(json, OrderPaid.class);
        service.applyIdempotently(event);
        // Normal return: container commits the JMS transaction afterward.
    }
}
~~~

Spring/Jackson imports are omitted. This assumes the broker sends a JSON **`TextMessage`** and the listener receives a `String` via the active converter. For `ObjectMessage`/`BytesMessage` or custom converters, align conversion contracts. Use a stable business event ID; **`JMSMessageID`** is assigned by the provider per JMS message and is not always the right idempotency key across a whole workflow.

If **`objectMapper.readValue(...)`** or **`service.applyIdempotently(...)`** throws, the exception escapes the listener so the container rolls back the JMS Session. **Never catch exceptions, merely log, and return** if you want the broker to redeliver; Spring may treat normal return as success and commit.

### 5.3. Dedicated factory when different policies are needed

When one flow needs distinct concurrency or transaction settings, define a named factory and reference it via **`containerFactory`**:

~~~java
@Configuration(proxyBeanMethods = false)
public class ReliableJmsConfiguration {

    @Bean
    DefaultJmsListenerContainerFactory reliableJmsFactory(
            ConnectionFactory connectionFactory,
            DefaultJmsListenerContainerFactoryConfigurer bootConfigurer) {

        DefaultJmsListenerContainerFactory factory =
                new DefaultJmsListenerContainerFactory();
        bootConfigurer.configure(factory,
                ConnectionFactoryUnwrapper.unwrapCaching(connectionFactory));
        factory.setSessionTransacted(true);
        factory.setConcurrency("2-6");
        return factory;
    }
}
~~~

~~~java
@JmsListener(
        destination = "orders.paid",
        containerFactory = "reliableJmsFactory")
public void onMessage(String payload) {
    // Parse, validate, and invoke idempotent service;
    // let exceptions propagate when rollback is needed.
}
~~~

This example uses Spring Boot 3.5 APIs:

- **`DefaultJmsListenerContainerFactoryConfigurer`** in package **`org.springframework.boot.autoconfigure.jms`**.
- **`ConnectionFactoryUnwrapper`** in package **`org.springframework.boot.jms`**.
- In Spring Boot 4.x, auto-configuration package paths may differ; use the imports matching your project's version.

**`bootConfigurer.configure(...)`** preserves Boot's customizations (converters, transactions, listener settings) before you override them. Call **`setSessionTransacted(true)`** explicitly afterward if transacted Sessions are required. **`ConnectionFactoryUnwrapper.unwrapCaching(...)`** lets the container use the native factory for connection recovery as recommended by Spring Boot.

## 6. Using CLIENT_ACKNOWLEDGE instead of a transacted Session

For a flow **not using local JMS transactions**, you can configure:

~~~yaml
spring:
  jms:
    listener:
      session:
        transacted: false
        acknowledge-mode: client
~~~

With Spring's default listener container, normal handler return ACKs the message; throwing an exception asks the Session to recover so the message can be redelivered **best-effort**. This differs from application-managed Sessions manually calling **`message.acknowledge()`**.

| Question | CLIENT_ACKNOWLEDGE via Spring container | JMS transacted Session |
| --- | --- | --- |
| Listener returns normally | Container ACKs per mode | Container commits transaction |
| Listener throws error | Best-effort recover/redelivery | Rolls back so message can redeliver |
| Sending JMS response on same Session | Not committed atomically with receive | Can share the same local JMS transaction |
| Call acknowledge manually? | Usually **no** with Spring listener container | **No**; container commits |
| Guarantees DB + JMS atomicity? | No | No, unless coordinated via appropriate transactions |

**Caution:** setting both **`transacted=true`** and **`acknowledge-mode=client`** still lets the transaction govern primary disposition. Treat those two settings as mutually exclusive alternatives rather than expecting `CLIENT_ACKNOWLEDGE` to create an extra checkpoint inside a transacted Session.

## 7. JDBC transactions and JMS: two separate boundaries

Suppose a listener receives **`OrderPaid`** and updates the database:

~~~java
@Service
public class PaidOrderService {
    private final JdbcTemplate jdbc;

    public PaidOrderService(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    @Transactional
    public void applyIdempotently(OrderPaid event) {
        int inserted = jdbc.update("""
            INSERT INTO processed_event (consumer_name, event_id)
            VALUES (?, ?)
            ON CONFLICT DO NOTHING
            """, "paid-orders", event.eventId());

        if (inserted == 0) {
            return; // Event already processed by this consumer.
        }

        int updated = jdbc.update("""
            UPDATE orders
            SET payment_version = ?, paid = TRUE
            WHERE id = ? AND payment_version < ?
            """,
            event.paymentVersion(),
            event.orderId(),
            event.paymentVersion());

        if (updated != 1) {
            throw new IllegalStateException(
                    "Order not found or out-of-order payment version");
        }
    }
}
~~~

This targets **PostgreSQL** with migration-managed tables; **`processed_event`** needs **`PRIMARY KEY (consumer_name, event_id)`**. It assumes **`payment_version`** on `orders` is initialized properly and business rules require strictly increasing versions. If out-of-order events or retries must be handled differently, define explicit version rules.

When **`@Transactional`** uses the database JDBC transaction manager, the marker insert and the `UPDATE` commit or roll back together. If the `UPDATE` fails, the **`RuntimeException`** rolls back the marker too, allowing retries. When the listener rethrows the exception, the container rolls back the **JMS Session**.

Still, **the two commits are independent operations** when using local JDBC and local JMS transactions:

~~~mermaid
sequenceDiagram
    participant B as JMS Broker
    participant L as JMS Listener Container
    participant DB as Database
    B->>L: Deliver evt-7821
    L->>DB: Begin DB transaction
    L->>DB: Insert processed_event + update orders
    DB-->>L: DB commit succeeded
    Note over L: Crash before JMS commit
    B->>L: Redeliver evt-7821
    L->>DB: Attempt insert processed_event
    DB-->>L: Duplicate key → business no-op
    L-->>B: JMS commit/ACK
~~~

**Practical solution:** build an **idempotent consumer/inbox** right where business data commits. A unique-constrained marker inside the same DB transaction as business side effects prevents double updates on redelivery. Never use an in-memory set or write a marker into Redis assuming it commits transactionally with PostgreSQL.

### 7.1. Can DB and JMS be combined into one transaction?

| Transaction type | Participating resources | Scope of guarantee |
| --- | --- | --- |
| **JMS local transaction** | One matching Session/broker resource | Receive/send messages on the same Session |
| **JDBC local transaction** | One DataSource/transaction manager | SQL statements sharing that transaction |
| **JmsTransactionManager** | One ConnectionFactory | Spring-managed local JMS resource |
| **JtaTransactionManager / XA** | XA-capable resources managed by a transaction coordinator | Can coordinate DB + JMS commits via distributed protocol at higher cost and complexity |

**`JmsTransactionManager` does not create an XA transaction with a database.** XA requires an XA-capable broker/`ConnectionFactory`, an XA `DataSource`, a transaction coordinator, and properly tested recovery. Most integration flows are better served by **transactional outbox**, **idempotent consumers**, and reconciliation—especially when external HTTP, caches, or non-XA brokers are also involved.

### 7.2. Sending another message inside a listener

In a transacted JMS Session, **JMS sends** can join the same local JMS transaction if **`JmsTemplate`** and the listener share the same `ConnectionFactory`/Session exposed by Spring on the processing thread. Example:

~~~java
@JmsListener(destination = "orders.commands",
             containerFactory = "reliableJmsFactory")
public void handleCommand(String json) {
    OrderCommand command = parseOrderCommand(json);
    processLocalJmsCommand(command);
    jmsTemplate.convertAndSend("orders.processed", command.orderId());
}
~~~

The business methods/variables here are illustrative and must be implemented in your app. **Never assume a send shares the transaction** if `JmsTemplate` uses another `ConnectionFactory`, opens its own Session, or dispatches onto another thread. Verify via integration tests: if the handler throws after sending, is the outbound `orders.processed` message rolled back alongside the incoming message?

If a DB transaction also runs, sending a JMS response inside the local JMS transaction still is **not** automatically atomic with the DB commit. Use an outbox when you must guarantee "DB updated and event will be published" across process crashes.

## 8. Redelivery after rollback and JMS headers

When a Session rolls back or recovers, the message **can be redelivered by the broker**. Timing, retry counts, delays, and final routing depend on provider and policy:

~~~text
Receive attempt #1 → handler throws → JMS rollback
                          |
                          v
                   Broker redelivery policy
                          |
       +------------------+------------------+
       |                                     |
       v                                     v
Redelivery attempt #2                  Limit exceeded
       |                                     |
       v                                     v
Success → JMS commit                    DLQ / expiry / discard
~~~

Two diagnostic headers:

- **`JMSRedelivered`**: provider flag indicating the message is being redelivered. It is a diagnostic hint, **not proof that side effects already committed or that another delivery is a business duplicate**.
- **`JMSXDeliveryCount`**: delivery attempt counter when exposed by the provider for your version and config. Helpful for monitoring, though never treat its naming or exact value as a broker-independent API for business decisions.

Reading headers from a raw JMS `Message`:

~~~java
public void observeDelivery(jakarta.jms.Message message)
        throws JMSException {

    boolean redelivered = message.getJMSRedelivered();
    String brokerMessageId = message.getJMSMessageID();

    Integer count = null;
    if (message.propertyExists("JMSXDeliveryCount")) {
        count = message.getIntProperty("JMSXDeliveryCount");
    }

    deliveryMetrics.record(redelivered, count);
    // Use brokerMessageId in logs/traces per data policy,
    // never as a high-cardinality metric tag.
}
~~~

**`deliveryMetrics`** is an illustrative application component. A **`@JmsListener`** accepting `String` can read headers via **`@Header`** / Spring Messaging or receive the raw JMS `Message` directly. Test your exact message type, converter, and argument resolvers.

### Why isn't JMSRedelivered enough to skip processing?

A redelivered message after an exception may **never have succeeded**, so skipping whenever **`JMSRedelivered=true`** drops business work. Conversely, a newly published message carrying a duplicate `eventId` has **`JMSRedelivered=false`**, yet is still a business duplicate. Idempotency decisions must rest on **`eventId`/business operation ID and committed state**.

## 9. Application retries vs. broker redelivery

There are two distinct retry layers:

| Layer | Controlled by | When it runs | Consequence |
| --- | --- | --- | --- |
| **In-listener retry** | Spring Retry / Resilience4j or app code | Inside the same delivery / JMS Session | Transient failures can resolve before container rollback |
| **Broker redelivery** | Provider/broker + session rollback/recover | After delivery failure or disconnect | Message redelivered, possibly to another consumer/instance |

Suppose a listener retries **up to three attempts** on HTTP 503 and then throws. The container rolls back the JMS Session, and the broker redelivers for another three attempts. If the broker permits five deliveries, external services could see **15 HTTP calls** for one message. Always budget **total retries across layers**.

Principles:

1. Keep in-listener retries fast, bounded, and backed off with jitter for brief transient glitches; never retry invalid schemas.
2. If recovery succeeds inside the listener and it **returns**, the container commits; ensure recovery truly resolved or handed off the work.
3. If the handler still throws, the container **rolls back** in transacted mode and the broker schedules the next attempt.
4. For `POST`/mutating external calls that may have succeeded despite client timeouts, retries require idempotency keys and reconciliation.
5. Avoid long backoffs inside listeners that pin sessions or DB locks; for multi-minute waits, broker scheduling or retry queues fit better.

## 10. Dead-letter queues and poison messages

A **poison message** cannot succeed through simple retries—e.g., malformed JSON, unsupported schema version, or missing required business fields. Infinite rollbacks stall the queue and flood logs.

Sample policy:

| Error category | Example | Recommended action |
| --- | --- | --- |
| **Transient** | DB/network timeout, downstream 503 | Bounded redelivery + backoff |
| **Throttling** | HTTP 429 | Delay per `Retry-After` / retry budget |
| **Permanent payload** | Malformed JSON, unknown event type | Do not retry infinitely; route to DLQ or remediation workflow |
| **Business rejected** | Order invalid per contract | Persist business rejection; decide ACK/DLQ per policy |
| **Already-processed duplicate** | `eventId` already committed | Idempotent no-op, then commit/ACK |
| **Uncertain outcome** | Timeout after calling payment API | Query status/idempotency; never assume failure |

In **ActiveMQ Artemis**, max attempts, delays, and dead-letter addresses are configured via **broker address settings** (such as **`redelivery-delay`**, **`redelivery-multiplier`**, **`max-delivery-attempts`**, and **`dead-letter-address`**). Other brokers structure policies differently. **`@JmsListener`** does not automatically wire bounded DLQ policies by itself.

Distinguish three milestones:

1. Handler throws and Session rolls back: **does not prove the message reached the DLQ**.
2. Broker dead-letters after exhausting attempts: **verify the route/destination actually exists**.
3. DLQ consumer receives a message: **count DLQ deliveries**, which may differ from unique events or remaining backlog.

If application code republishes a failed message to a quarantine queue and ACKs the source, use publisher confirms or coordinated recovery; failing to send after ACKing loses the message. Use transactions/outbox/inbox or broker-native policies to close that gap.

## 11. Classifying errors and propagating exceptions to the container

Listener with validation and error handling:

~~~java
@JmsListener(destination = "orders.paid")
public void onMessage(String json) {
    final OrderPaid event;
    try {
        event = objectMapper.readValue(json, OrderPaid.class);
    } catch (JsonProcessingException ex) {
        // Do not return normally if policy expects broker poison handling.
        throw new InvalidEventPayloadException("Unsupported JSON", ex);
    }

    paidOrderService.applyIdempotently(event);
}
~~~

~~~java
public final class InvalidEventPayloadException
        extends RuntimeException {
    public InvalidEventPayloadException(
            String message, Throwable cause) {
        super(message, cause);
    }
}
~~~

The container catches the exception to roll back a transacted JMS Session. However, **the broker does not inspect `InvalidEventPayloadException` on its own**; to fast-track permanent errors without burning retries, configure container error policies/recoverers, route to an error branch safely, or cap broker attempts globally.

Common mistakes:

- **Catching Exception, logging, and returning:** container commits/ACKs, losing unprocessed messages.
- **Calling raw `Session.commit()` inside a Spring container:** breaks container-managed transaction boundaries.
- **Throwing under `CLIENT_ACK` expecting XA:** `CLIENT_ACK` never joins JDBC transactions.
- **Skipping unconditionally on `JMSRedelivered`:** drops events that previously failed before commit.
- **Sending every error to the DLQ on attempt 1:** transient network blips can recover; build a clear taxonomy and retry budget.

## 12. Sizing timeouts and concurrency to match infrastructure

Listener containers must balance consumption rate against real processing capacity:

| Parameter | Impact | Risk if misconfigured |
| --- | --- | --- |
| **min/max concurrency** | Parallel consumers/Sessions | Too many consumers overload downstream DB/APIs |
| **receive timeout** | Wait per poll cycle before checking lifecycle | Zero/infinite timeout can stall clean shutdowns in some setups |
| **Broker prefetch / window** | Messages buffered to a client ahead of processing | Uneven distribution and memory bloat with slow consumers |
| **Redelivery delay/backoff** | Pause before next delivery attempt | Zero delay causes retry storms |
| **Max delivery attempts** | When poison messages leave the main queue | Too low prematurely dead-letters transient errors; too high clogs queues |
| **JMS session transacted** | ACK/rollback boundary | Disabling it risks losing messages on listener exceptions |
| **DB/HTTP timeouts** | Bounds on downstream I/O | Long timeouts + high concurrency exhaust resources |

In modern Spring Boot releases, **`spring.jms.listener.receive-timeout`** bounds **the polling container's receive wait**, **not** the maximum execution time of your business handler. If a handler stalls on an HTTP call, configure timeouts directly on the HTTP client/downstream or enforce service deadlines.

If business rules require sequential processing per **`orderId`**, concurrent consumers alter completion order. JMS queues maintain broker delivery order to a degree, **but never guarantee ordered completion across concurrency/retries**. Consider key-based sharding, single-consumer segments where strictly required, or optimistic version checks in the database.

## 13. Logging, metrics, and tracing for ACK and redelivery

One **delivery** is not one **business event**: a broker can redeliver the same message after rollback. Define metric units explicitly:

| Suggested metric | Incremented when | Meaning |
| --- | --- | --- |
| **`jms.delivery.received`** | Listener/container receives a delivery | Includes redeliveries |
| **`jms.delivery.redelivered`** | `JMSRedelivered=true` on receipt | Deliveries flagged as retries |
| **`jms.processing.success`** | Business logic finishes | Does not guarantee JMS commit already succeeded |
| **`jms.processing.failure`** | Handler throws out to container | Eligible for rollback/redelivery |
| **`jms.transaction.rollback`** | Actual observed rollback | Never count purely inside app catches |
| **`jms.deadletter.observed`** | DLQ consumer sees a delivery | Differs from unique event count |
| **`jms.idempotency.duplicate`** | Business ID already processed | Backed by durable idempotency store |

These are **suggested metric names**, not all built into Spring Boot out of the box. With Micrometer/Actuator, collect latency, error categories, consumer counts, queue depths, and DLQ backlogs from appropriate sources; avoid unbounded tags such as `eventId`, `JMSMessageID`, or `orderId`.

Example structured log:

~~~text
flow=paid-order
eventId=evt-7821
jmsRedelivered=true
deliveryCount=3
outcome=retryable_failure
errorKind=database_timeout
traceId=...
~~~

IDs may appear in protected logs/traces per data policy, but **never** in high-cardinality metric labels. Never log credentials or full sensitive payloads. Across HTTP calls, propagate trace correlation via JMS headers/properties per producer–consumer convention rather than assuming the broker forwards HTTP trace context automatically.

## 14. Testing: do not merely mock the listener

Unit-testing that a listener method throws an exception only proves your code throws. It **does not prove** the JMS container rolled back or the broker redelivered. Those guarantees require integration tests against a real JMS broker or test container.

| Scenario | What to verify |
| --- | --- |
| Listener succeeds | DB commits, JMS transaction commits, message leaves queue |
| Handler throws runtime error in transacted session | JMS rolls back; message redelivered per broker policy |
| DB transaction rolls back | Idempotency marker and business update roll back together |
| DB commits but process dies before JMS commit | Redelivery produces zero duplicate side effects |
| `CLIENT_ACK` mode | ACK on success; best-effort redelivery on failure per container/provider |
| `AUTO_ACK` mode | Never assume handler exceptions trigger redelivery |
| Poison message | After attempt limit, message lands in expected DLQ with diagnostic headers/payload |
| Broker reconnects after outage | Listener container recovers without losing committed work |
| Two consumers receive the same business event ID | Unique constraint protects DB state |
| Event version 8 followed by version 7 | Older event does not regress committed state |
| Retry delay/max attempts | Delivery count and timing match broker policy |
| DLQ publish/routing error | Reconciled/alerted; never falsely reported as dead-lettered |

### 14.1. A meaningful transaction-layer test

Using a test database and real JMS broker (such as Testcontainers with ActiveMQ Artemis), execute this sequence:

~~~text
1. Start broker, DB, migrations, and Spring test application.
2. Send OrderPaid(eventId=evt-7821, orderId=O-1).
3. Configure the first attempt to throw intentionally after UPDATE.
4. Assert DB transaction rolled back; processed_event is absent.
5. Wait for redelivery; allow the next attempt to succeed.
6. Assert orders updated once and processed_event has one key.
7. Resend the same business eventId in a new JMS message.
8. Assert idempotent no-op and clean JMS commit.
9. Measure deliveries/retries/rollbacks directly instead of guessing from call counts.
~~~

Tests often need shorter `redelivery-delay` and tuned `max-delivery-attempts` in the test broker config. Assert using bounded timeouts instead of long fixed sleeps. To test competing consumers, run at least two instances or two listener containers against the same queue and database.

### 14.2. Testing atomicity when sending JMS on the same Session

Send a source message where the listener sends to **`orders.processed`** and then throws an exception. With a single transacted Session and properly exposed `ConnectionFactory`, **`orders.processed`** must not appear after rollback; once the listener succeeds on retry, exactly one response message commits.

This test is essential whenever code assumes **`JmsTemplate.convertAndSend`** joins the listener's Session; a misconfigured `ConnectionFactory` can emit the response even while the incoming JMS receipt rolls back.

### 14.3. Inspecting beans and properties at runtime

Spring Boot auto-configuration varies conditionally with the classpath, `ConnectionFactory`, JTA, and custom factories. In startup tests, inject **`JmsListenerEndpointRegistry`** to look up the container by listener ID, inspect its runtime config and startup logs, and verify rollback behavior against the broker. **Never rely solely on a YAML property** when Java configurers override it or multiple factories exist.

## 15. Misconceptions to avoid

**"The listener didn't throw, so the DB committed."** False if side effects run asynchronously via unawaited `Future`s or separate threads. Containers typically commit JMS on return; cross-thread handoffs need their own durable guarantees.

**"`AUTO_ACK` always ACKs after all business logic finishes."** Behavior depends on the listener container. In `DefaultMessageListenerContainer`, `AUTO_ACK` does not provide reliable redelivery after handler exceptions.

**"`CLIENT_ACK` lets `Message.acknowledge()` ACK one exact message."** Standard JMS ACKs at Session scope; individual ACK is a provider-specific extension.

**"Putting `@Transactional` on a listener makes DB + JMS an XA transaction."** `@Transactional` binds to one transaction manager; two local transactions do not automatically fuse into a distributed atomic commit.

**"JMS rollback rolls back all side effects."** Only operations inside that JMS transaction roll back; HTTP calls, Redis, and separate databases need their own handling.

**"A message with `JMSRedelivered=true` was definitely processed earlier."** The flag reflects transport delivery attempts, not business commit outcomes.

**"Requeue every error forever so no message is lost."** Poison messages will loop endlessly; define retry budgets, DLQs, alerts, and controlled replay.

**"The queue has a DLQ configured, so throwing guarantees messages land in the DLQ."** Verify broker policies, max attempts, routing, and destination existence.

**"More concurrency always boosts throughput."** If the DB or downstream is slow, adding consumers increases contention, latency, and rollbacks.

**"Application retry count equals broker delivery count."** Internal retries and broker redeliveries multiply; one delivery can execute multiple internal attempts.

## 16. Checklist for reliable JMS implementations

1. Explicitly define **queue/topic**, durability, provider, and required delivery guarantees.
2. Know which listener factory handles each endpoint and its actual **`sessionTransacted`** or **`acknowledgeMode`** setting.
3. For workflows needing failure recovery, prefer transacted Sessions; never assume `AUTO_ACK` gives at-least-once.
4. Never manually ACK/commit while the Spring container owns the Session lifecycle.
5. Let exceptions propagate at the boundary when rollback is required; never swallow errors and return normally.
6. Distinguish JMS local transactions, DB local transactions, and XA/JTA; verify `DataSource`, `ConnectionFactory`, and transaction manager wiring.
7. Use a stable **`eventId`/business key** with unique constraints or conditional updates to block duplicate side effects.
8. Configure redelivery delay, max attempts, and DLQs on the broker matching its version, permissions, and verified routing.
9. Bound retries at both listener and broker layers; enforce reasonable HTTP/DB timeouts instead of holding Sessions indefinitely.
10. Define strategies for poison messages, duplicates, older schema versions, and ambiguous-outcome timeouts.
11. Monitor ACK/commit, rollbacks, redeliveries, queue depth, DLQs, and handler failure rates with well-defined metrics.
12. Run integration tests against a real broker and DB, including crashes between DB commit and JMS commit plus concurrent consumers.

To ensure a JMS event applies its business effect once as required, combine **properly scoped ACK/transactions**, **idempotency at the business data store**, **bounded redelivery**, and **post-failure observability**. Each mechanism solves a distinct piece of the reliability puzzle.
