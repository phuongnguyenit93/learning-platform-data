# Eliminating Absolute Path, Time Zone, and Locale Effects on Reproducible Spring Boot Builds

## 1. The Problem: Why Can Two JARs from the Same Source Have Different SHA-256 Hashes?

A **reproducible build** is a build where the same source code, same input data, same build instructions, and specified environmental factors produce a **byte-for-byte identical artifact**, not merely equivalent behavior. Two executable Spring Boot JARs can serve the same API yet have different checksums because they embed timestamps, developer machine paths, usernames, locale-formatted values, or ZIP entries in an unstable order.

This lesson focuses on three hidden input categories:

1. **Absolute paths and machine state:** `/home/alice/work/app` differs from `C:\build\app` or `/agent/_work/42`. If a generator writes this path into a resource, manifest, metadata, or JSON packaged in the archive, the JARs will differ.
2. **Time zones and time:** the same `Instant` can format into two different local wall-clock times; ZIP/JAR entry timestamps, `build.time` metadata, or generators calling `Instant.now()` or `new Date()` cause output to drift.
3. **Locale, charset, and regional rules:** Turkish uppercase/lowercase mapping, French decimal separators, date/currency formatting, collation/sorting order, default encoding, and line endings can alter generated file bytes.

```text
Same Git commit + same dependencies
      |
      +-- Machine A: /home/alice/repo, UTC, en_US, Linux
      |       -> build-info, generated.txt, jar entries
      |
      +-- Machine B: C:\agent\repo, Asia/Tokyo, tr_TR, Windows
              -> build-info, generated.txt, jar entries
      |
      v
Goal: SHA-256(artifact A) == SHA-256(artifact B)
```

**Distinguish carefully:**
- *Deterministic code:* a step produces consistent output whenever its inputs are identical.
- *Reproducible artifact:* the entire build chain emits **identical bytes** when repeated under declared conditions.
- *Hermetic build:* a build isolated from undeclared external environmental sources. Hermeticity helps reproducibility, though it does not automatically guarantee matching checksums.
- *Functional equivalence:* two JARs exhibit equivalent runtime behavior; checksums need not match.

Never promise that simply setting `TZ=UTC` or flipping one Maven/Gradle flag automatically makes every project reproducible. You must inspect **generated code/resources, compiler/toolchain, archive metadata, dependency locking, and plugin behavior**.

## 2. Map of Environmental Inputs to Control

| Factor | Common leak form | Consequence | How to eliminate/control |
| --- | --- | --- | --- |
| `project.basedir`, `user.dir`, `projectDir.absolutePath` | Written to generated JSON/manifest/config | Artifact contents embed differing workspace paths | Use relative logical paths or artifact coordinates |
| `user.home`, `user.name`, `HOME` | Builder identity recorded in metadata | Artifacts differ by account | Omit from output unless it is a legitimate input |
| `Instant.now()`, `new Date()` | Build timestamp tracks wall clock | Every build differs | Use a fixed release timestamp or drop time fields |
| ZIP/JAR entry timestamps | Copies timestamps from filesystem | Archive checksum shifts | Maven `project.build.outputTimestamp`; Gradle archive flags |
| `ZoneId.systemDefault()` | Converts Instant to local time | Output varies by host | Use UTC/`ZoneOffset.UTC` for metadata |
| `Locale.getDefault()` | Formats numbers, dates, letter casing | Generated text changes | Use `Locale.ROOT` or explicit business locale |
| `Charset.defaultCharset()` | Reads/writes resources per platform | Different bytes or corrupted Unicode | Explicitly pick `StandardCharsets.UTF_8` and compiler encoding |
| `System.lineSeparator()` / CRLF | Text generated on Windows differs from Unix | File checksum differs | Standardize LF for artifact text, `.gitattributes` |
| Unsorted directory traversal | `Files.list`/`File.listFiles` order varies by FS | File order/JSON keys differ | Sort by normalized logical name before serialization |
| JDK/compiler/vendor/version | Generated bytecode or resources can differ | JARs differ even with matching Java major | Pin exact JDK toolchain for strict gates |
| Version ranges / SNAPSHOTs / mutable plugins | Dependency resolution shifts | Classpath/archive differs | Pin/lock dependencies/plugins; govern repositories |
| Locale-sensitive ZIP metadata | Filename encoding/permissions | Archive varies across OSes | Use UTF-8 and reproducible archive tasks/plugins |
| Immutable files overwritten by generated tasks | Task depends on clock or environment | Wrong build cache hits or perpetual misses | Declare inputs/outputs and avoid implicit state |

**Where to spot leaks:** inspect `jar tf`, `META-INF/MANIFEST.MF`, `META-INF/build-info.properties`, `BOOT-INF/classes`, generated sources/resources, nested JARs, and checksums. Console logs may vary by time zone, yet **do not** alter the artifact unless written back into the packaged product; separate these two layers.

## 3. Absolute Paths: What Is Dangerous and What Is Not?

An absolute path is an **address on the build host**, not an identifier of an application resource. For example:

```text
/home/mai/projects/billing-service
/var/lib/ci/work/7/billing-service
C:\agent\_work\billing-service
```

All three can hold the exact same repository revision, yet if a code generator executes:

```java
String workspace = System.getProperty("user.dir");
String machine = System.getProperty("user.name");
String value = Path.of("src/main/resources").toAbsolutePath().toString();
```

and writes those strings into `build-info.properties`, generated Java sources, or the manifest, artifact bytes will diverge.

### 3.1. Use Classpath-Based Resource Names

For resources shipped with the application:

```java
// Inside Spring Boot code; this is a snippet inside a method, not a standalone .java file.
try (var input = new org.springframework.core.io.ClassPathResource(
        "rules/defaults.txt").getInputStream()) {
    String text = new String(input.readAllBytes(),
            java.nio.charset.StandardCharsets.UTF_8);
    // Use text...
}
```

`rules/defaults.txt` is a **logical** identifier on the classpath. Maven/Gradle packages the resource at `BOOT-INF/classes/rules/defaults.txt`, and the Boot Loader resolves the classpath when running the executable JAR.

**Never use** `/home/mai/.../src/main/resources/rules/defaults.txt` in runtime code, and avoid calling `ClassPathResource.getFile()` by default: resources **inside an executable JAR** may not exist as standalone files on the filesystem.

### 3.2. If a Generator Must Read the Filesystem, Separate Root and Relative Path

A build task generating docs from `src/main/resources/schemas` still needs to read real files on disk. However, the **emitted data** must use relative paths anchored to a meaningful root:

```java
Path root = Path.of(args[0]).toAbsolutePath().normalize();
Path source = root.resolve("src/main/resources/schemas/model.json").normalize();

if (!source.startsWith(root)) {
    throw new IllegalArgumentException("Resource escaped project root");
}

String portable = root.relativize(source)
        .toString()
        .replace('\\', '/');
```

This is a **Java snippet inside a method importing `Path`**, not a standalone runnable program. `portable` evaluates to `src/main/resources/schemas/model.json` on compliant systems, while `root` differs across machines. Converting `\` to `/` keeps emitted logical names independent of Windows/Unix separators. When enforcing a path trust boundary against untrusted path inputs, also check symlinks/real paths; `normalize` alone does not prevent all symlink escapes.

**Never slice absolute paths by fixed character offsets** or string-replace usernames; that breaks with Unicode, junctions/symlinks, different drive letters, and nested modules. Always compute relative paths from an **explicit base directory**.

### 3.3. Paths That Do Not Need Stripping from Build Logs

There remain legitimate absolute paths:
- Maven reporting a compiler error at `/workspace/.../MyClass.java`.
- Gradle logs pointing to `build/tmp/compileJava`.
- Test reports placed in CI-created directories.
- Runtime stack traces containing paths for diagnostics.

These **affect reproducible artifacts only if written into artifact bytes or influencing build inputs**. You do not need to scrub every path from console logs, though you must still avoid logging sensitive data.

## 4. Time Zones, Time, and Reproducibility: Three Distinct Layers

### 4.1. Instants Are Time-Zone-Independent; Their Formatting Is Not

A fixed instant:

```text
2024-01-02T03:04:05Z
```

is a single `Instant`. Converting it with `ZoneId.systemDefault()` makes machines in Tokyo and New York print **different local wall-clock times**. If a generator writes local date/time to a file, artifacts differ despite the same `Instant`.

Use:

```java
Instant fixed = Instant.parse("2024-01-02T03:04:05Z");
String stable = java.time.format.DateTimeFormatter.ISO_INSTANT.format(fixed);
```

`stable` is strictly `2024-01-02T03:04:05Z`. This is a **Java snippet** requiring `java.time.Instant` to be imported, not a standalone program.

If business logic needs a string in a fixed zone:

```java
var formatter = java.time.format.DateTimeFormatter
        .ofPattern("yyyy-MM-dd'T'HH:mm:ssXXX", java.util.Locale.ROOT)
        .withZone(java.time.ZoneOffset.UTC);

String stable = formatter.format(
        java.time.Instant.parse("2024-01-02T03:04:05Z"));
```

Output carries the UTC offset per pattern, e.g., `2024-01-02T03:04:05Z`, without reading the host's default time zone.

**Never use `LocalDateTime.now()` to stamp artifacts** unless build-time stamping is explicitly required; if provenance needs a timestamp, it must be a **pinned, reproducible input**, such as the release commit timestamp, rather than the build's wall clock.

### 4.2. Timestamps on ZIP/JAR Entries

ZIP/JAR files store timestamp metadata per entry. If Maven/Gradle keeps filesystem mtimes or uses “now,” an unchanged source file still gets archived with different timestamps.

This is why:
- Stabilizing `.class` contents alone is not enough.
- Two archives with identical entry lists and functionality can still differ in SHA-256.
- Comparing only `jar tf` (filenames only) is insufficient; inspect ZIP metadata, timestamps, ordering, and bytes.

**Maven:** use `project.build.outputTimestamp` with plugins supporting reproducible archives.

**Gradle:** set `isPreserveFileTimestamps = false` and `isReproducibleFileOrder = true` on archive tasks for older Gradle compatibility; since **Gradle 9.0**, archive tasks use equivalent reproducible defaults. Even with stable archive metadata, generated files **inside** can still hold machine-dependent timestamps.

### 4.3. Spring Boot build-info Embeds build.time

When a project enables Maven goal `spring-boot:build-info` or Gradle `springBoot { buildInfo() }`, `META-INF/build-info.properties` can contain `build.time`.

- With **Spring Boot Maven Plugin**, time defaults to `project.build.outputTimestamp` when set; otherwise it uses the session request start time. You can omit time with `<time>off</time>` or exclude the `time` property.
- With **Spring Boot Gradle Plugin**, `bootBuildInfo` defaults to writing the live build timestamp. Spring Boot documentation notes this makes the task continually out-of-date and impedes repeatable builds; you can exclude the `time` property.

If you only need to trace version/commit, it is usually better to store the **pinned version and CI-supplied commit hash** rather than always recording live build time. If compliance/audits demand actual build execution time, document it as an input that changes the artifact, and do not claim two independent builds are byte-identical when given different timestamps.

## 5. Locale and Charset: Silent Data Drift Without Compiler Errors

### 5.1. Never Default Case Conversion to System Locale for Machine-Readable Keys

In Java:

```java
String key = "IMAGE".toLowerCase();
```

The result depends on the default locale. Under the Turkish locale, `I` turns into `ı` (dotless i), differing from the ASCII `i` expected by configuration/resource keys.

For identifiers, keys, enum-like labels, logical filenames, and canonical machine-readable text:

```java
String key = "IMAGE".toLowerCase(java.util.Locale.ROOT);
```

The result is strictly `image`, regardless of `user.language`/`user.country`. For user-facing text in a specific language, pick an explicit business locale (`Locale.forLanguageTag("vi-VN")`, `Locale.US`, etc.) rather than forcing everything to `ROOT`.

### 5.2. Formatting Numbers and Dates

`String.format("%.2f", 12.5)` uses the default formatting locale. Some locales use a **decimal comma** instead of a decimal point, changing values inside generated SQL/JSON/manifests.

Use:

```java
String number = String.format(java.util.Locale.ROOT, "%.2f", 12.5);
```

The output is consistently `12.50`. Similarly:
- `NumberFormat.getInstance()` and `DateTimeFormatter.ofPattern(...)` can be locale-dependent unless specified.
- `Collator.getInstance()` performs locale-dependent sorting; for machine-readable order, use an explicit comparator and predetermined Unicode normalization.
- Choose `Locale.ROOT` for **internal serialization**, not necessarily for user-facing UI/currency formats.

### 5.3. Text File Formatting, Encoding, and Newlines

On Java 17, APIs that omit an explicit charset can depend on runtime/platform defaults. Avoid relying on:

```java
// Avoid when producing byte-identical artifacts:
new String(bytes);
text.getBytes();
new java.io.FileWriter("generated.txt");
System.lineSeparator();
```

Methods using default encoding/newlines can make generated files diverge. Prefer:

```java
byte[] bytes = text.replace("\r\n", "\n")
        .getBytes(java.nio.charset.StandardCharsets.UTF_8);
java.nio.file.Files.write(
        java.nio.file.Path.of("generated.txt"), bytes);
```

**Note:** `replace("\r\n", "\n")` is only an example normalization. If inputs contain standalone `\r` line endings or binary/signed formats requiring exact bytes, define an explicit policy instead of transforming blindly. For text generated directly by your tool, emit `\n` strings and encode with UTF-8 directly for tighter control.

### 5.4. Git Checkout and CRLF

Configure an appropriate `.gitattributes`:

```gitattributes
*.java        text eol=lf
*.properties  text eol=lf
*.yml         text eol=lf
*.yaml        text eol=lf
*.json        text eol=lf
*.sh          text eol=lf
*.bat         text eol=crlf
*.png         binary
*.jpg         binary
*.jar         binary
```

This is an **example policy**, not the only valid configuration for every repo. For files already committed with mixed line endings, renormalize in a dedicated commit (`git add --renormalize .` after review) to avoid noisy diffs. Never apply text conversion to binaries. Changing line endings can affect generated code/scripts, so test on target environments.

## 6. Runnable Java 17 Demo: Identical Stdout Across Paths, Time Zones, and Locales

This section is a Java program **with no Spring Boot dependency** to isolate all three causes. It requires only JDK 17+ and two files. It outputs a relative resource path, text, lowercase key, timestamp, and number with **exact UTF-8/LF bytes**.

Structure:

```text
portable-report/
├── ReproProbe.java
└── data/
    └── greeting.txt
```

**`data/greeting.txt`:**

```text
hello
```

**`ReproProbe.java`:**

```java
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Instant;
import java.time.format.DateTimeFormatter;
import java.util.Locale;

public class ReproProbe {
    public static void main(String[] args) throws Exception {
        if (args.length != 1) {
            throw new IllegalArgumentException("Expected project root path");
        }

        Path root = Path.of(args[0]).toAbsolutePath().normalize();
        Path resource = root.resolve("data/greeting.txt").normalize();

        if (!resource.startsWith(root)) {
            throw new IllegalArgumentException("Resource outside project");
        }

        String portableName = root.relativize(resource)
                .toString()
                .replace('\\', '/');
        String content = Files.readString(resource, StandardCharsets.UTF_8)
                .strip();
        String key = "IMAGE".toLowerCase(Locale.ROOT);

        Instant fixed = Instant.parse("2024-01-02T03:04:05Z");
        String timestamp = DateTimeFormatter.ISO_INSTANT.format(fixed);
        String decimal = String.format(Locale.ROOT, "%.2f", 12.5);

        String report = "resource=" + portableName + "\n"
                + "content=" + content + "\n"
                + "key=" + key + "\n"
                + "instant=" + timestamp + "\n"
                + "decimal=" + decimal + "\n";

        System.out.write(report.getBytes(StandardCharsets.UTF_8));
    }
}
```

Use `javac`/`java` (Linux/macOS, working directory `portable-report`):

```bash
mkdir -p out
javac -encoding UTF-8 -d out ReproProbe.java

# Run under one locale and timezone:
java -Duser.language=en -Duser.country=US -Duser.timezone=UTC \
  -cp out ReproProbe "$PWD"

# Run under Turkish locale and Japan timezone:
java -Duser.language=tr -Duser.country=TR -Duser.timezone=Asia/Tokyo \
  -cp out ReproProbe "$PWD"
```

**Exact stdout of each run:**

```text
resource=data/greeting.txt
content=hello
key=image
instant=2024-01-02T03:04:05Z
decimal=12.50
```

Outputs match because:
- Absolute `root` is used solely to **read inputs**, never serialized into output.
- `root.relativize(resource)` computes a logical name and `replace('\\', '/')` stabilizes slashes.
- `Files.readString(..., UTF_8)` fixes the charset; `strip()` trims trailing newlines in the sample.
- `Locale.ROOT` governs keys and numbers.
- Timestamp is a fixed `Instant`, formatted as ISO in UTC.
- `System.out.write(... UTF_8)` emits UTF-8 bytes with `\n`, never calling `System.lineSeparator()`.

**Test across two different workspaces:** copy `ReproProbe.java` and `data/greeting.txt` into two separate directories (e.g., `/tmp/probe-a` and `/tmp/probe-b`), compile in each, and pass their respective `"$PWD"`. As long as input files match, stdout remains identical. In Windows PowerShell, pass `(Get-Location).Path` instead of `"$PWD"` and place `-D` JVM options before `-cp`.

Do not use this example to argue every Java project becomes byte-identical automatically: it simply proves a **small generator designed to eliminate the three hidden inputs**.

## 7. Directory Traversal, Map Ordering, and Paths Skewing Generated Resources

A code generator often iterates files from a directory:

```java
Files.list(root.resolve("schemas"))
        .forEach(path -> writeSchema(path));
```

This snippet (assuming a `writeSchema` method exists) must not treat filesystem entry order as stable. If the generator appends items to JSON or a manifest, differing order alters bytes.

Instead:
1. Convert absolute files into **relative logical paths**.
2. Normalize `/` separators.
3. Sort using a deterministic comparator.
4. Serialize in deterministic order using UTF-8/LF.

**Java 17 snippet inside a method** (importing `Path`, `Files`, `Comparator`, `List`, `Stream`) to obtain stable filenames:

```java
try (var paths = Files.walk(root.resolve("schemas"))) {
    List<String> names = paths
        .filter(Files::isRegularFile)
        .map(path -> root.relativize(path).toString().replace('\\', '/'))
        .sorted()
        .toList();

    for (String name : names) {
        System.out.println(name);
    }
}
```

`Stream.sorted()` on strings uses Java String comparison order (not the default `Collator`). For filenames whose Unicode normalization differs across OSes, enforce NFC/NFD normalization and prohibit case-insensitive collisions; byte-identical ordering requires consistency in **both filenames and contents**. `Files.walk` can also hit differing symlinks/permissions; control traversal and error handling.

Similarly, when generated JSON/manifests come from a `HashMap` or database query lacking `ORDER BY`, sort keys/records with a deterministic comparator before serializing. Never rely on accidental iteration order on one machine.

## 8. Maven: Configuring an Executable Spring Boot JAR with Reproducible Timestamps

This is a **standalone** project building a Spring Boot web JAR to demonstrate archive reproducibility. The example fixes **Spring Boot 3.5.0 and Java 17**, with plugin versions managed by the Spring Boot parent; before upgrading, test plugins and runtime on a real branch.

Structure:

```text
repro-app/
├── pom.xml
└── src/main/java/com/example/repro/ReproApplication.java
```

**Complete `pom.xml`:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.0</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>repro-app</artifactId>
    <version>0.1.0</version>
    <name>repro-app</name>
    <packaging>jar</packaging>

    <properties>
        <java.version>17</java.version>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>
        <!-- Illustrative fixed timestamp; in reality an input of the release. -->
        <project.build.outputTimestamp>2024-01-02T03:04:05Z</project.build.outputTimestamp>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

**`src/main/java/com/example/repro/ReproApplication.java`:**

```java
package com.example.repro;

import java.time.Instant;
import java.time.format.DateTimeFormatter;
import java.util.Locale;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class ReproApplication {

    public static void main(String[] args) {
        SpringApplication.run(ReproApplication.class, args);
    }

    @GetMapping("/proof")
    public String proof() {
        String key = "IMAGE".toLowerCase(Locale.ROOT);
        String stamp = DateTimeFormatter.ISO_INSTANT.format(
                Instant.parse("2024-01-02T03:04:05Z"));
        return key + "|" + stamp;
    }
}
```

Run:

```bash
mvn -B -ntp clean package
java -jar target/repro-app-0.1.0.jar
```

Call `curl -fsS http://localhost:8080/proof` in another terminal. **Exact body:** `image|2024-01-02T03:04:05Z`. If port 8080 is in use, launch the JAR with `--server.port=9090` and adjust the URL. Stop the app with Ctrl+C.

**Role of each element:**
- `<java.version>17</java.version>`: configures the compiler target under the Spring Boot starter parent.
- `<project.build.sourceEncoding>UTF-8</...>`: pins encoding for supporting source/resource plugins.
- `<project.build.outputTimestamp>2024-01-02T03:04:05Z</...>`: supplies a **stable timestamp** to Maven plugins supporting reproducible archives, including Maven JAR Plugin and Spring Boot Maven Plugin `repackage`.
- `spring-boot-maven-plugin`: produces the executable JAR from the original JAR; with the starter parent, the `repackage` execution is bound to `package`.

Some newer Maven versions/plugins enable reproducible mode by default, yet **do not skip verification by relying on defaults**; explicitly declaring a release timestamp makes build docs deterministic. The example timestamp is a preselected input; real projects can use the release commit timestamp, keeping it constant across rebuilds of that release.

### 8.1. What Does project.build.outputTimestamp Do and Not Do?

It typically helps:
- Maven archiver write reproducible ZIP/JAR entry timestamps.
- Spring Boot repackaging normalize archive entry times to the chosen input.
- Certain metadata plugins read this timestamp instead of querying the wall clock.

It **does not automatically guarantee**:
- Java code generators avoid `Instant.now()`.
- Absence of absolute paths in generated sources.
- Identical dependency/plugin/JDK binaries.
- That all plugins support reproducible outputs.
- Immutable checksums for container images or signed files.

Official Maven docs recommend upgrading to plugin versions supporting reproducible builds and verifying with `maven-artifact-plugin`. With Maven 3.9.x and older plugins, defaults can differ; verify via effective POM and actual artifacts.

### 8.2. The build-info Plugin Requires Extra Control

**Only if your app actually uses the `spring-boot:build-info` goal**, Spring Boot Maven Plugin can add `META-INF/build-info.properties` containing `build.time`.

Two options:
- Keep build time, anchored to a fixed `project.build.outputTimestamp`; supporting plugins honor this value.
- Omit build time completely with `<time>off</time>` or by excluding `time`.

Example **replacement configuration inside the POM's `spring-boot-maven-plugin` section** if you want to run `build-info` without writing `time`:

```xml
<executions>
    <execution>
        <id>build-info</id>
        <goals>
            <goal>build-info</goal>
        </goals>
        <configuration>
            <time>off</time>
        </configuration>
    </execution>
</executions>
```

This **is not a complete `pom.xml`**. With the starter parent, the `repackage` execution already exists and is not replaced when adding a new execution with ID `build-info`. If the project does not need `build-info`, **do not enable** that goal. Avoid automatically injecting timestamps via Git or build-number plugins if byte identity is your goal.

## 9. Maven: Configuring Tests and Build JVMs to Be Independent of Time Zone/Locale

### 9.1. Do Not Confuse the Build JVM with the Test JVM

Maven runs in one JVM; Maven Surefire/Failsafe may launch a **forked test JVM**. Setting `TZ=UTC` in the shell does not guarantee every test uses the same Java timezone, especially if `user.timezone` is overridden or plugins pick another JVM.

If existing tests rely on APIs using the default timezone/locale, you can **temporarily lock the test environment** to create a baseline:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <configuration>
        <argLine>
            -Duser.timezone=UTC -Duser.language=en -Duser.country=US
        </argLine>
    </configuration>
</plugin>
```

This is a **plugin fragment** to place inside `<build><plugins>` of a valid POM. With the Spring Boot starter parent, the Surefire version is managed automatically; with a custom parent, pin the plugin version and check JUnit Platform support.

**Important:** `argLine` on Surefire affects the test JVM. If the project uses JaCoCo or tooling injecting a JVM agent via `argLine`, a plain override block can drop the agent; merge/resolve the `argLine` property per that plugin's documentation. Surefire's `systemPropertyVariables` works for many properties, though for VM bootstrap properties like locale/encoding, passing them on the **forked JVM** command line is clearer.

Still, the best fix is **updating code** to use `Locale.ROOT` and `ZoneOffset.UTC` wherever semantics are environment-independent. Always forcing UTC/en-US can let tests PASS while hiding bugs when deployed on hosts in other time zones. Maintain a test matrix that intentionally varies those values.

### 9.2. Running Maven Across Multiple Time Zones/Locales

On Linux/macOS, pass JVM options to the **Maven process** via `MAVEN_OPTS`:

```bash
MAVEN_OPTS="-Duser.timezone=UTC -Duser.language=en -Duser.country=US" \
  mvn -B -ntp clean verify

MAVEN_OPTS="-Duser.timezone=Asia/Tokyo -Duser.language=tr -Duser.country=TR" \
  mvn -B -ntp clean verify
```

Run these commands **separately**. `MAVEN_OPTS` affects the Maven JVM itself, while forked test JVMs/other tools may need separate configuration. When comparing artifacts, verify both builds use identical sources/dependencies/plugins/JDK, and no generated resources are driven by live time or locale.

## 10. Gradle Kotlin DSL: Archive Order, Timestamps, and Java Toolchain

Gradle provides reproducible archive task support. **Since Gradle 9.0**, `AbstractArchiveTask` (JAR/ZIP/WAR/EAR/TAR as applicable) defaults to equivalent settings:
- `preserveFileTimestamps = false`;
- `reproducibleFileOrder = true`;
- permissions metadata normalized per archive type.

On older Gradle versions, **set both flags explicitly**. This configuration does not force other generators or tasks in the build to be deterministic.

Spring Boot app equivalent to the Maven section, reusing `src/main/java/com/example/repro/ReproApplication.java` from Section 8 verbatim, while **not keeping `pom.xml` in a Gradle-only demo**.

**`settings.gradle.kts`:**

```kotlin
rootProject.name = "repro-app"
```

**`build.gradle.kts`:**

```kotlin
import org.gradle.api.tasks.bundling.AbstractArchiveTask
import org.gradle.api.tasks.compile.JavaCompile

plugins {
    java
    id("org.springframework.boot") version "3.5.0"
    id("io.spring.dependency-management") version "1.1.7"
}

group = "com.example"
version = "0.1.0"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
}

tasks.withType<JavaCompile>().configureEach {
    options.encoding = "UTF-8"
    options.release.set(17)
}

tasks.withType<AbstractArchiveTask>().configureEach {
    isPreserveFileTimestamps = false
    isReproducibleFileOrder = true
}
```

**Explanation:**
- `java.toolchain` picks the project's compiler/JVM tooling version instead of taking an arbitrary `JAVA_HOME`.
- `options.encoding` prevents default file encoding variance when compiling Java source.
- `options.release=17` enforces Java API/bytecode targets within the selected toolchain.
- `withType<AbstractArchiveTask>()` affects `jar`, `bootJar`, and applicable archive tasks without changing XML/other resource formats.
- `Gradle 9+` enables reproducible archives by default, so both assignments are typically unnecessary if targeting Gradle 9+ exclusively. When supporting Gradle 8.x, declaring them explicitly avoids surprises.
- Use a Gradle Wrapper with a **version compatible with Spring Boot plugin 3.5**; never pull Gradle “latest” untested.

Run:

```bash
./gradlew clean bootJar
java -jar build/libs/repro-app-0.1.0.jar
```

This assumes a Gradle Wrapper exists in the project. On Windows run `gradlew.bat`. If no wrapper exists, generate one with a compatible installed Gradle first; do not assume `./gradlew` exists before project initialization. The `/proof` endpoint matches the Maven demo's response.

### 10.1. Spring Boot Gradle buildInfo: Removing Continuously Changing Timestamps

When a project needs `META-INF/build-info.properties` for Actuator, add:

```kotlin
springBoot {
    buildInfo {
        excludes.set(setOf("time"))
    }
}
```

This is an **add-on snippet for a `build.gradle.kts` with the Spring Boot plugin applied**. It makes `bootBuildInfo` emit the remaining properties without `build.time`. Spring Boot docs note that default `build.time` uses the live build timestamp, causing task output to shift and breaking repeatable builds; excluding `time` stabilizes outputs and improves up-to-date checks.

If audit requirements demand a real build time, use a fixed release input and a supporting API/plugin version; never write `Instant.now()` into a resource expecting `bootJar` to strip it automatically.

### 10.2. Gradle Test JVM: Configuring a Baseline

To give the test suite a clear baseline:

```kotlin
tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    systemProperty("user.timezone", "UTC")
    systemProperty("user.language", "en")
    systemProperty("user.country", "US")
}
```

This is an **add-on snippet**; matching test dependencies/`Test` tasks are required. In Gradle's Java plugin, the test JVM is separate from the Gradle daemon. This controls test runtime defaults, yet does not prove code itself is locale/timezone-independent. Add test runs under `tr_TR`/`Asia/Tokyo` to catch hidden leaks.

### 10.3. Avoiding Path Leaks in Custom Gradle Tasks

**Do not generate artifact text like this:**

```kotlin
// Anti-pattern illustration; do not put this in build.gradle.kts.
val absolute = project.projectDir.absolutePath
val buildDate = java.time.Instant.now().toString()
```

If written into resources, the JAR will vary across CI agents and runs. Instead use:
- `providers.gradleProperty(...)` for explicitly declared build metadata.
- Relative path names anchored to a defined source root.
- Gradle `Property<T>`/`RegularFileProperty` and `@Input`/`@OutputFile` annotations when writing custom tasks needing caching/up-to-date support.
- Stable release metadata from Git commits or CI inputs instead of live time.

**Never treat the Gradle cache as proof of reproducibility:** the cache can return an old output for declared task inputs, yet if a task reads undeclared `System.getenv`/`user.dir`, its fingerprint misses environment variables and serves wrong outputs. Reproducibility requires both **accurate task input modeling** and byte-identical outputs.

## 11. Comparing Two Builds Across Two Workspaces and Two Time Zones

One successful build does not prove reproducibility. Run **two independent clean builds** from the exact same Git commit, in two different paths, with different timezones/locales, then compare SHA-256 or raw bytes.

### 11.1. Maven Bash Demo in Two Directories

This assumes you are in the **Git repository of the Maven project from Section 8**, files are committed at `HEAD`, and `git`, `tar`, Maven/JDK, and `sha256sum`/`cmp` are installed on Linux. Do not run against paths holding important unsaved data, as it creates two new directories.

```bash
mkdir -p /tmp/repro-a /tmp/repro-b

# Export only files committed in HEAD, excluding target/ or local caches.
git archive HEAD | tar -x -C /tmp/repro-a
git archive HEAD | tar -x -C /tmp/repro-b

(
  cd /tmp/repro-a
  MAVEN_OPTS="-Duser.timezone=UTC -Duser.language=en -Duser.country=US" \
    mvn -B -ntp clean package
)

(
  cd /tmp/repro-b
  MAVEN_OPTS="-Duser.timezone=Asia/Tokyo -Duser.language=tr -Duser.country=TR" \
    mvn -B -ntp clean package
)

sha256sum /tmp/repro-a/target/repro-app-0.1.0.jar
sha256sum /tmp/repro-b/target/repro-app-0.1.0.jar

if cmp -s /tmp/repro-a/target/repro-app-0.1.0.jar \
          /tmp/repro-b/target/repro-app-0.1.0.jar; then
  echo "ARCHIVE_EQUAL"
else
  echo "ARCHIVE_DIFFERENT"
fi
```

**Expected result:** both checksums match and the script prints `ARCHIVE_EQUAL` if every factor affecting the artifact is controlled. Do not fabricate a fake SHA-256 here, as real checksums depend on exact dependencies/plugins/JDK/toolchain. **If it prints `ARCHIVE_DIFFERENT`**, that is a valuable test signal: investigate the root cause rather than forcing PASS.

**Test limitation:** it varies path and certain JVM defaults while sharing the same machine/JDK/OS/network/Maven cache; it does not yet prove a third party on a different OS can rebuild byte-for-byte. For stronger validation, run on two independent CI agents/container images with pinned versions and compare artifacts. Also note Maven forked tests may not inherit all `MAVEN_OPTS`; configure Surefire JVM args separately if testing test behavior.

### 11.2. With Gradle

From two separate checkouts of the same commit and Gradle Wrapper:

```bash
(
  cd /tmp/repro-a
  ./gradlew --no-build-cache clean bootJar
)

(
  cd /tmp/repro-b
  ./gradlew --no-build-cache clean bootJar
)

sha256sum /tmp/repro-a/build/libs/repro-app-0.1.0.jar
sha256sum /tmp/repro-b/build/libs/repro-app-0.1.0.jar
```

This is an **illustrative snippet for two directories containing a Gradle project and Wrapper**, not directories exported from a Maven-only POM without Gradle settings/build scripts. `--no-build-cache` ensures each run performs the work instead of pulling from the build cache; Gradle can still use the dependency cache to resolve the **same** versions. Pass JVM options to the Gradle daemon or test JVM intentionally when expanding to a timezone/locale matrix. If tasks report up-to-date within a single workspace, inspect `clean` and input modeling.

### 11.3. Comparing Checksums vs. Functionality

- `SHA-256 A == SHA-256 B`: evidence both files **share the same hash**, providing strong practical assurance of byte equality; `cmp` verifies bytes directly.
- `java -jar A` and `java -jar B` both serve `/proof`: proves sample behavior matches, **not** that bytes are equal.
- Matching `jar tf` listings: only entry names match, **not** timestamps/permissions/compression/layout.
- Equivalent build logs: prove nothing about output bytes.
- Maven/Gradle `BUILD SUCCESS`: unrelated to bit-for-bit equality without actual comparison.

## 12. When Hashes Differ: Where Is the Divergence?

An effective diagnostic workflow:

1. Confirm **identical commit, POM/Gradle config, and JDK/compiler/plugin/dependency versions**.
2. Compare file sizes and SHA-256 hashes.
3. List ZIP entries, timestamps, ordering, and permissions.
4. Unpack into two temporary directories and diff **inner files**.
5. Focus on generated files: `META-INF/build-info.properties`, manifest, generated sources/resources, SBOMs, index files, XML/JSON.
6. If `.class` files differ, inspect toolchains, compiler flags, generated sources, and annotation processors.
7. If entry bytes match yet JAR hashes differ, compare ZIP metadata/order/compression/signatures.
8. Identify **which task/plugin created the difference** and fix it at the source, rather than patching the JAR post-build.

Useful Bash commands:

```bash
jar tf /tmp/repro-a/target/repro-app-0.1.0.jar > /tmp/list-a.txt
jar tf /tmp/repro-b/target/repro-app-0.1.0.jar > /tmp/list-b.txt
diff -u /tmp/list-a.txt /tmp/list-b.txt

unzip -l /tmp/repro-a/target/repro-app-0.1.0.jar
unzip -l /tmp/repro-b/target/repro-app-0.1.0.jar
```

`unzip -l` shows entry sizes/times; because ZIP timestamps and timezone conversions have quirks, never treat display times in one terminal as absolute truth. For deep analysis, use `zipinfo`, unpack-and-diff, or **diffoscope**:

```bash
diffoscope /tmp/repro-a/target/repro-app-0.1.0.jar \
           /tmp/repro-b/target/repro-app-0.1.0.jar
```

`diffoscope` is a separately installed tool, not bundled with JDK/Maven/Gradle. It helps surface differing ZIP metadata, manifests, and generated files; it does not replace reading plugin source/configs.

### 12.1. Maven Artifact Plugin Comparison Support

Apache Maven offers a workflow using `maven-artifact-plugin`:

```bash
mvn clean install
mvn clean verify artifact:compare
```

The first command builds/installs a reference artifact; the second rebuilds and compares via the plugin. Requires a Maven Artifact Plugin version supporting those goals and a valid repository setup; the plugin may download on first run.

**Limitation:** two builds on the same machine do not catch every path/locale/OS leak. It is a good local check, yet still needs independent validation in another workspace, another environment, or formal reproducible build verification.

## 13. Artifact Time Zone Is Not Application Runtime Time Zone

A Spring Boot service must return data to users in their local time zones. Putting all users in UTC is not the goal of this lesson.

**Separate the two scopes:**
- *Build metadata / artifact identity:* normalize timestamps, formats, and inputs so the JAR is reproducible.
- *Business runtime behavior:* store timestamps accurately as `Instant`/UTC, and **format display output using the user's explicit timezone and locale**; this is a **valid request input**, not a hidden environment leak.

Java runtime example:

```java
Instant orderTime = Instant.parse("2024-01-02T03:04:05Z");
ZoneId customerZone = ZoneId.of("Asia/Ho_Chi_Minh");
String visible = DateTimeFormatter
        .ofPattern("dd/MM/yyyy HH:mm", Locale.forLanguageTag("vi-VN"))
        .withZone(customerZone)
        .format(orderTime);
```

This snippet sits inside a method importing `Instant`, `ZoneId`, `DateTimeFormatter`, and `Locale`; output is `02/01/2024 10:04` in `Asia/Ho_Chi_Minh`. It is **deterministic because zone and locale are explicit inputs**, not because every host must be in Vietnam.

For tests:
- Date/time formatting tests must pass explicit `Instant` and `ZoneId` values instead of depending on developer machine settings.
- Multilingual formatting tests should exercise multiple locales via test data.
- DST transition tests must use a DST-observing zone (e.g., `Europe/Berlin`) and test instants around transitions.
- Never use `LocalDateTime.now()` for fixed assertions; inject `Clock.fixed(...)` into services.

If a product tracks local calendar dates, model them with `LocalDate`/`ZonedDateTime` per business rules rather than forcing everything into UTC strings and losing local date semantics.

## 14. Clock Injection: Making Tests and Generators Deterministic

Sometimes code **needs a timestamp** (e.g., generating release metadata or testing expiration). Instead of querying the system clock inside every function, pass `Clock` as a dependency.

Standalone Java 17 example:

**`ClockProbe.java`:**

```java
import java.time.Clock;
import java.time.Instant;
import java.time.ZoneOffset;

public class ClockProbe {
    static String createdAt(Clock clock) {
        return Instant.now(clock).toString();
    }

    public static void main(String[] args) {
        Clock frozen = Clock.fixed(
                Instant.parse("2024-01-02T03:04:05Z"),
                ZoneOffset.UTC);
        System.out.println(createdAt(frozen));
    }
}
```

Run:

```bash
javac -encoding UTF-8 ClockProbe.java
java ClockProbe
```

**Exact stdout:**

```text
2024-01-02T03:04:05Z
```

In enterprise Spring Boot apps, define a `@Bean Clock` and constructor-inject it; production can use `Clock.systemUTC()`, while tests use `Clock.fixed(...)`. In **build-generated resources**, if reproducibility is required, the clock must take a **pinned release timestamp** rather than a live production clock. `Clock.systemUTC()` only fixes the time zone, **not** the instant; consecutive calls still produce different timestamps.

## 15. Things That Must Not Enter the Artifact

### 15.1. Workspace Paths, OS Accounts, and Host Config

Example Maven manifest entries **not** to use:

```xml
<!-- Anti-pattern if writing these values into the artifact -->
<manifestEntries>
    <Workspace>${project.basedir}</Workspace>
    <Builder>${user.name}</Builder>
</manifestEntries>
```

This embeds absolute paths and local usernames into the JAR. For release traceability, prefer groupId/artifactId/version, a **pinned Git commit ID**, and provenance stored in CI attestations. If policy requires recording builder identity, treat it as a formal input and accept that artifacts differ when identity differs; never claim unconditional reproducibility.

In Gradle, the equivalent anti-pattern is reading `project.projectDir.absolutePath`, `System.getProperty("user.home")`, or `System.getenv("WORKSPACE")` into generated metadata.

### 15.2. “Now” Build Timestamps

Calling `LocalDateTime.now()` and `Instant.now()` inside generators makes output files differ on every build. Spring Boot `build.time` must also be removed or pinned if `build-info` is enabled.

Replace with:
- A fixed release timestamp recorded in CI/manifest.
- A UTC-normalized commit timestamp identical across rebuilds of the same commit (if used by release policy).
- Or **omit timestamps** from the artifact when unnecessary.

`SOURCE_DATE_EPOCH` is a common convention representing a stable source timestamp in Unix seconds, yet **do not assume Maven, every Gradle plugin, and every code generator reads it automatically**. Wire it explicitly into relevant plugin configs (`project.build.outputTimestamp`, task properties, metadata generators) and verify the resolved value.

### 15.3. Data Ordered by Locale or Filesystem

Never generate resources from queries lacking `ORDER BY`, unordered map iteration, or `Collator.getInstance()` without an explicit locale. When serialized JSON/CSV requires stable order, sort by a deterministic logical key, normalize Unicode/charsets, and fix serialization options.

### 15.4. Runtime Data/Secrets Embedded at Build Time

Released binaries must never embed:
- Environment-specific database URLs/passwords.
- API tokens, local certificates/private keys.
- Random session IDs.
- Local service endpoints reachable only by CI agents.
- Test outputs containing timings, hostnames, or usernames.

This is both a **security hazard** and a source of **non-determinism**. Supply runtime values via Spring Config Data, environment variables, or secret stores after the artifact has been built and verified.

## 16. Principles for CI/CD and Multi-Module Spring Boot

### 16.1. Pin Toolchains and Dependency Versions

When targeting bit-for-bit reproducibility across environments:
- Record Maven/Gradle Wrapper versions and confirm wrapper files are committed.
- Pin Spring Boot plugin, Maven plugin/JDK toolchains, and dependency versions (no time-varying version ranges in releases).
- With Gradle, consider dependency locking/verification; with Maven, `dependencyManagement`/Enforcer/repository policies.
- Control annotation processors/code generators, native tools, locale/tzdata databases, and any tool versions affecting output.
- Keep build flags identical across compared builds.
- Across Windows/Unix, standardize source line endings and UTF-8; do not assume tools emit identical output across both OSes.
- The same major JDK is insufficient for strict gates; compiler/vendor/patch/OS flags can produce different bytecode/resources. Record exact image digests/toolchains.

### 16.2. Handling Multi-Module Builds

A parent Maven POM setting `project.build.outputTimestamp` helps child modules inherit the property, yet **individual modules** can still run plugins/tasks that emit non-reproducible files. Check every artifact:
- Plain library JAR modules.
- Spring Boot executable JAR module.
- Generated client/source/schema modules.
- Integration test module artifacts if published.
- OCI image/buildpack layers if part of deliverables.

In Gradle multi-project builds, `tasks.withType<AbstractArchiveTask>().configureEach` inside one subproject configures only that subproject's tasks. For repo-wide policy, apply a shared convention plugin deliberately to each project rather than writing ad-hoc cross-project script blocks that break configuration-cache/project isolation. Setting `outputTimestamp` at Maven root alone likewise cannot force unsupported custom plugins to become deterministic.

### 16.3. Release Candidate Reproducibility Gate

A CI workflow might look like:

```text
Pinned Git commit
    |
    +-- Build A: workspace A, UTC/en_US, pinned JDK + deps
    |        -> app-a.jar + sha256
    |
    +-- Build B: workspace B, Asia/Tokyo/tr_TR, pinned JDK + deps
             -> app-b.jar + sha256
    |
    +-- Byte-level comparison & diff analysis
             |
             +-- Equal: reproducibility check PASS
             +-- Different: FAIL, preserve safe diff, fix root cause
```

A CI build may still need secrets to fetch private dependencies; never embed secrets into outputs. Use artifact repositories with checksums/immutable release policies and verify supply-chain provenance separately. **Reproducibility does not guarantee content safety and does not replace SBOM/vulnerability scanning**.

### 16.4. Two Separate Test Levels

1. **Build reproducibility tests:** compare SHA-256/JAR bytes across two clean builds.
2. **Locale/timezone behavior tests:** run unit/integration tests under varied `user.language`, `user.country`, `user.timezone` settings and assert expected behavior.

A project can pass (1) because artifacts contain no locale-dependent bytes yet fail (2) when runtime UI formatting breaks. Conversely, an app may behave properly across locales at runtime while archive hashes differ due to ZIP timestamps. Never collapse both checks into one metric.

## 17. Common Errors Table

| Symptom | Likely cause | Check and remediation |
| --- | --- | --- |
| Two JARs share class/resource names, different SHA | ZIP entry timestamps/order/permissions differ | Inspect archive metadata, Maven `outputTimestamp`, or Gradle archive flags |
| Same source, different path → generated JSON differs | `project.basedir`/`user.dir` serialized | Switch to relative logical paths |
| Build-info keeps changing | `build.time` uses wall clock | Maven pinned timestamp/`time=off`; Gradle exclude `time` |
| String keys differ in `tr_TR` | `toLowerCase()` used default locale | Use `toLowerCase(Locale.ROOT)` for machine identifiers |
| Decimal prints `12,50` instead of `12.50` | `String.format` used default locale | Choose `Locale.ROOT` or explicit business locale |
| Dates shift by a day when CI runs in another region | `ZoneId.systemDefault()` used | Use `Instant` and explicit zone |
| UTF-8 resources corrupt or change | Default charset/compiler encoding differed | Specify UTF-8 explicitly; normalize text resources |
| Generated text on Windows differs from Linux | CRLF/LF and `System.lineSeparator()` | `.gitattributes`; generators emit LF for machine-readable output |
| Manifest/schema listing changes order | Unsorted filesystem/Map iteration | Use stable comparator and relative names |
| Gradle `bootJar` still differs with archive flags on | Generated file embeds live time/path or dependency mismatch | Diff contents; inspect `bootBuildInfo`/custom tasks |
| Maven `outputTimestamp` has no effect | Outdated/unsupported plugin or wrong format | Upgrade plugin, check effective POM, inspect entry times |
| Same-machine check PASSes, other machine FAILs | Uncontrolled JDK/OS/locale/plugin state | Rebuild independently on separate CI agents and run diffoscope |
| Build cache masks non-determinism | Custom task reads undeclared hidden env/time | Declare inputs explicitly; run clean no-cache checks |
| Tests fail only in CI | Different default timezone/locale or Java/JUnit/tool versions | Test with explicit `Clock`/`Locale`/`ZoneId`; use CI matrix |
| Maven Surefire tests differ from Maven JVM | Forked test JVM lacked expected flags | Configure Surefire JVM args in the proper scope |
| Artifact matches, OCI image differs | Image layer metadata/base image/digest/build-time env differs | Pin image/base; configure reproducible image builds separately |
| Runtime still sees stale regional config | Build-time and runtime configs mixed | Separate immutable JAR from external Spring Config Data |
| `.class` files differ despite identical source | Different JDK/compiler/annotation processors/generated sources | Compare toolchains, compiler flags, and generator outputs |

## 18. Progressive QA Exercises

### Exercise A — Demonstrating a Locale Leak

Try this small Java program:

```java
import java.util.Locale;

public class LocaleLeak {
    public static void main(String[] args) {
        System.out.println("IMAGE".toLowerCase());
        System.out.println("IMAGE".toLowerCase(Locale.ROOT));
    }
}
```

Run:

```bash
javac -encoding UTF-8 LocaleLeak.java
java -Duser.language=tr -Duser.country=TR LocaleLeak
```

Expect **`ımage`** (dotless `ı`) and **`image`** respectively. On modern JDKs with standard locale data, this illustrates how the default locale alters string keys. With `Locale.ROOT`, output is always `image` regardless of region.

### Exercise B — Demonstrating a Timezone Leak

```java
import java.time.Instant;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class ZoneLeak {
    public static void main(String[] args) {
        Instant fixed = Instant.parse("2024-01-02T03:04:05Z");
        System.out.println(ZonedDateTime.ofInstant(fixed,
                ZoneId.systemDefault()));
        System.out.println(fixed);
    }
}
```

Run two commands:

```bash
javac ZoneLeak.java
java -Duser.timezone=UTC ZoneLeak
java -Duser.timezone=Asia/Tokyo ZoneLeak
```

The first line shows different local zones/offsets; the second line is **always** `2024-01-02T03:04:05Z`. Do not hardcode exact string expectations for the first line, as `ZonedDateTime.toString()` displays the zone ID/offset supplied by configuration.

### Exercise C — Detecting Absolute Paths Inside an Artifact

Build the same commit in two checkouts at different paths. If hashes differ, check:
- Does `META-INF/MANIFEST.MF` contain `Workspace`, `Builder`, or a path?
- Does `BOOT-INF/classes/META-INF/build-info.properties` contain time or path fields?
- Do generated sources/resources contain `/home/...`, `C:\...`, or usernames?
- Does `BOOT-INF/lib` contain different dependency versions?
- Have archive metadata/ordering been normalized?

**Never run scanners that dump all secrets** into CI logs. Extract only files/structures needed for diagnosis into a protected workspace. Do not conclude an absolute path leaked into the artifact purely from build logs unless the path actually entered the artifact.

### Exercise D — Setting a Quality Gate

A release candidate meets the chosen reproducibility goal when:
1. Two independent checkouts use the same source revision and dependency set.
2. Toolchains/plugins/configurations are explicitly defined.
3. Paths, time zones, and locales are intentionally varied between the two runs.
4. Both executable JARs are byte-identical (verified by `cmp` or equivalent).
5. Runtime tests also pass across multiple timezones/locales without relying on defaults unless required.
6. Release metadata (version/commit) is stable, containing no secrets or host-specific data.

If step 4 fails, preserve evidence and locate the source of divergence; never alter hashes by overwriting binaries or disabling checks.

## 19. Production Project Implementation Checklist

- [ ] Define which artifacts must be reproducible: plain JAR, Boot JAR, WAR, container image, or all.
- [ ] Pin source revision, Maven/Gradle Wrapper, plugin/dependency versions, and JDK toolchain.
- [ ] Never write absolute workspace paths, usernames, hostnames, or home directories into generated resources/manifests.
- [ ] Use classpath resource identifiers or relative paths with normalized separators.
- [ ] Sort generated files built from directories/maps/databases before serialization.
- [ ] Never write `Instant.now()`/`LocalDateTime.now()` into artifacts; pin release timestamps or omit the field.
- [ ] Maven uses `project.build.outputTimestamp` and archive plugins supporting reproducibility.
- [ ] Gradle archive tasks use `preserveFileTimestamps=false`, `reproducibleFileOrder=true` (default from Gradle 9).
- [ ] If Spring Boot `build-info` is enabled, handle `build.time` in Maven/Gradle.
- [ ] Generated text uses UTF-8 and defined newline conventions; `.gitattributes` reviewed.
- [ ] Machine-readable data uses `Locale.ROOT`/explicit locale and `Instant`/explicit zone.
- [ ] Tests use `Clock` injection and run across a locale/timezone matrix.
- [ ] Separate build JVM, test JVM, and runtime Spring Boot JVM when applying flags.
- [ ] Declare inputs/outputs on custom tasks so Gradle caching never hides implicit state.
- [ ] Actually compare SHA-256/bytes across two clean builds in two workspaces.
- [ ] On mismatch, inspect ZIP metadata, generated files, toolchains, and dependencies first.
- [ ] Keep runtime secrets/config external to immutable artifacts.
- [ ] CI releases the exact tested artifact with version/digest and archives QA evidence.

- Java 17 – [Instant](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/Instant.html), [Clock](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/Clock.html), [ZoneId](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/ZoneId.html): time handling with explicit inputs.

**Remember:** to eliminate the impact of **absolute paths, time zones, and locales**, convert them from *implicit inputs* into *explicitly controlled inputs or strip them from artifacts*. Use **relative resource names**, **UTC/Instant or explicit timezones**, **Locale.ROOT/explicit business locales**, **UTF-8/LF**, stable archive timestamps, and pinned toolchains/dependencies. Validate with **two clean builds in two workspaces under differing locales/timezones and compare real bytes**; only then do you have proof your Spring Boot build meets its reproducibility criteria.
