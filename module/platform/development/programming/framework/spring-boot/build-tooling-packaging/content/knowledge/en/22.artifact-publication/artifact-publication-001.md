# Distinguishing Maven Repositories, CI Artifact Stores, and OCI Registries When Publishing Spring Boot

## 1. Why Are the Three Storage Destinations Often Confused?

After building a Spring Boot application, a pipeline might produce `target/release-demo-0.1.0.jar`, report `BUILD SUCCESS`, and need to deliver the product to consumers. However, saying "the artifact has already been uploaded" is **not enough**: where is the artifact located, who retrieves it with which tool, for how long, with what metadata/identity, and is it the exact binary that was tested?

Three common destination types:

1. **Maven repository**: distributes Java/Maven components by **coordinates** `groupId:artifactId:version`, along with the corresponding POM, metadata, and JAR/WAR/classifier files. Maven/Gradle consumes them via dependency resolution.
2. **CI artifact store** (*workflow/job artifacts*): stores **the outputs of a single pipeline run**, such as executable JARs, test reports, coverage, logs, checksums, and SBOMs, for passing between jobs or post-build inspection/debugging. Identifiers are typically tied to the workflow run/build number and a retention policy, and **do not provide a Maven repository protocol by default**.
3. **OCI registry**: distributes container images and OCI artifact types by **repository:tag** or **repository@digest**. Docker/Podman/containerd/Kubernetes pull image manifests and layers rather than fetching an executable JAR via standard Maven GAV.

```text
Pinned Git commit
       |
       v
  Maven / Gradle build + tests
       |
       +--> target/release-demo-0.1.0.jar
       |            |
       |            +--> [CI artifact store]
       |            |      build #308 / artifact "app-jar"
       |            |      -> downloaded by another job, QA, investigation
       |            |
       |            +--> [Maven repository]
       |                   com.example:release-demo:0.1.0
       |                   -> downloaded by Maven/Gradle consumer via GAV
       |
       +--> Dockerfile / Spring Boot build-image
                    |
                    v
              OCI image + manifest + layers
                    |
                    v
             [OCI registry]
             registry.example.invalid/team/release-demo:0.1.0
             -> pulled by node/container runtime by tag/digest
```

**The three destinations are not mutually exclusive.** A good pipeline can store test evidence in CI, publish a Java library to a Maven repository, and also release a Spring Boot executable container image to an OCI registry. However, you should not **push everything everywhere** simply because they are all called "artifacts": you must determine the consumer, retention, security, and release policy.

This lesson illustrates with **Java 17 and Spring Boot 3.5.0**, Maven 3.9.x, and common CI/Docker tools. Fixed versions are used for example consistency and do not imply the latest releases. The `example.invalid` domains in configuration snippets are **non-working illustrative addresses**; they must be replaced with an actual repository/registry authorized by your organization before publishing.

## 2. Quick Comparison Table

| Criterion | Maven repository | CI artifact store | OCI registry |
| --- | --- | --- | --- |
| Primary objects | POM, JAR, WAR, sources, javadoc, classifiers, Maven metadata | Files and folders generated by workflows: JAR, test reports, logs, SBOM, checksum | Container image, image index/manifest, layers, OCI artifact types |
| Typical identifier | `com.example:shared-api:1.2.0` | Workflow run `#308` + artifact name `app-jar` | `registry/team/app:1.2.0` or `@sha256:...` |
| Typical upload | `mvn deploy` or Gradle `maven-publish` | CI upload-artifact or job artifact feature | `docker push`, `buildx --push`, `bootBuildImage --publish` |
| Typical download | Maven dependency resolution, `mvn dependency:get` | CI download-artifact / CI provider web API | `docker pull`, `podman pull`, Kubernetes pull |
| Key metadata | POM, GAV, dependency graph, maven-metadata.xml, checksums | Run ID, job, branch/commit, uploader, retention, artifact checksum | OCI manifest/index, config, layer digests, platform, tag, media types |
| Retention period | Release/snapshot policy per repository manager | Usually limited by run/plan, may auto-expire | Registry retention, garbage collection, tag immutability policy |
| Dependency resolution | **Yes, via Maven** | Usually **no** | **Not via Maven GAV** for standard images |
| Running JVM deployment | Consumer fetches JAR and runs it if artifact is executable | Job downloads JAR and uses it as a file | Runtime pulls image, creates container |
| Traceability | Coordinate version + checksum and repository provenance | Run/job/commit + hash + logs | Image digest/index digest + SBOM/provenance |
| Secrets/permissions | Deploy token, read token, repo roles | CI identities/artifact read permissions | Registry credentials, pull/push permissions |

**Note:** a service like Nexus, Artifactory, or GitHub Packages can provide **multiple repository types under the same UI/hostname**. That **does not turn them into a single format**. The Maven endpoint, generic artifact storage, workflow artifacts, and OCI Registry endpoint still have separate APIs, metadata, and access permissions. An OCI registry can also store non-image artifacts (such as Helm charts/SBOMs via OCI artifact media types), but **it is not a Maven repository for Java dependencies by default**.

## 3. What Is a Maven Repository?

A Maven repository is a store with **a layout and metadata understood by Maven clients**. The key identifier is:

```text
groupId    : artifactId   : version        [:packaging] [:classifier]
com.example: shared-api   : 1.2.0          : jar
com.example: release-demo : 0.1.0          : jar
com.example: release-demo : 0.1.0          : jar        : exec
```

Maven uses coordinates to decide which dependency to download, at which version, and with which transitive dependencies described in the POM. Filenames might resemble files in CI, but **GAV and the POM are the Java distribution contract**.

### 3.1. maven2 Layout: Realistic Path Example

For `com.example:shared-api:1.2.0`, the relative path in the repository layout is typically:

```text
com/example/shared-api/1.2.0/
├── shared-api-1.2.0.pom
├── shared-api-1.2.0.jar
└── [checksums / signatures depending on system]

com/example/shared-api/maven-metadata.xml
```

Dots in `groupId` are converted into directories; filenames contain artifactId and version. A repository manager may add other metadata/indexes/checksums. **Do not manually copy a JAR to an object storage path that looks like Maven and assume it becomes a valid Maven repository**: POMs, metadata, release/snapshot policies, checksums, and how the Maven resolver accesses them must also be handled.

### 3.2. Three Maven Repository Types to Distinguish

- **Local repository:** usually located at `~/.m2/repository`, where Maven caches downloaded dependencies/plugins and artifacts installed with `mvn install`. This is **not** automatically visible to colleagues or other CI runners.
- **Remote repository:** an HTTP(S) or filesystem repository accessed by the Maven resolver to download dependencies/plugins, such as Maven Central or an internal Nexus/Artifactory.
- **Hosted deploy repository:** an endpoint with **write** permissions to publish an organization's artifacts, typically separating **releases** and **snapshots**. It may reside on the same repository manager as remote mirrors.

`mvn install` places the artifact into the local Maven repository. `mvn deploy` executes the lifecycle up to the deploy phase and transfers artifacts/metadata to the configured remote deployment repository. **`mvn package` only creates files in `target`; `mvn deploy` is not synonymous with Docker push.**

### 3.3. Releases and SNAPSHOTs

| Maven version | Meaning | Typical publish rule |
| --- | --- | --- |
| `1.2.0` | Release version | Should be immutable, do not overwrite already published builds |
| `1.2.1-SNAPSHOT` | Development snapshot | Can be published multiple times with corresponding timestamp/build number and metadata |
| `1.2.0-RC1` | Release candidate, treated by Maven as a version without the SNAPSHOT suffix | Depends on hosted release repository policy |

A Maven snapshot `1.2.1-SNAPSHOT` can be stored server-side under a timestamped snapshot name and `maven-metadata.xml` metadata. It is neither a Git branch nor an OCI image tag. When consumers download a SNAPSHOT, the `updatePolicy` and local Maven cache affect when Maven checks for newer versions.

**Do not reuse the same release version to write multiple different JARs:** doing so breaks dependency graph reproducibility, even if a repository allows overwrites. When a security fix update is needed, release a new version and record its checksums.

## 4. Distinguishing repositories (for Downloads) from distributionManagement (for Publishing)

In a Maven POM, configuring:

```xml
<repositories>
    <repository>
        <id>company-proxy</id>
        <url>https://repo.example.invalid/repository/maven-public/</url>
    </repository>
</repositories>
```

typically serves **dependency resolution**. It **does not automatically tell the Maven Deploy Plugin to publish to that endpoint**.

To publish the project's own artifacts:

```xml
<distributionManagement>
    <repository>
        <id>internal-releases</id>
        <url>https://repo.example.invalid/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
        <id>internal-snapshots</id>
        <url>https://repo.example.invalid/repository/maven-snapshots/</url>
    </snapshotRepository>
</distributionManagement>
```

`<repository>` above is the **release destination**; `<snapshotRepository>` is the **snapshot destination**. This is a POM snippet, not a complete XML file. `repo.example.invalid` is a placeholder with no live service; replace it with the exact URL from an approved repository manager.

**Very important point:** `<repositories>` (download), `<pluginRepositories>` (plugin download), `<mirrors>` in settings (download redirection), and `<distributionManagement>` (deploy upload) have distinct roles. A `mirrorOf="*"` should not be assumed to automatically alter the deploy URL. Inspect the effective settings/POM when debugging.

### 4.1. Do Not Put Credentials in the POM

Maven matches `distributionManagement.repository.id` with `settings.xml -> servers -> server.id`. Example **`settings.xml` used in CI** (complete file for this section):

```xml
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">
    <servers>
        <server>
            <id>internal-releases</id>
            <username>${env.MAVEN_REPO_USER}</username>
            <password>${env.MAVEN_REPO_TOKEN}</password>
        </server>
        <server>
            <id>internal-snapshots</id>
            <username>${env.MAVEN_REPO_USER}</username>
            <password>${env.MAVEN_REPO_TOKEN}</password>
        </server>
    </servers>
</settings>
```

Maven supports environment variable interpolation in settings using `${env.NAME}` syntax via its settings interpolation mechanism. The `MAVEN_REPO_USER` and `MAVEN_REPO_TOKEN` variables must be supplied from the **CI secret store** when a job actually needs to publish. Do not put real credentials into Git, `pom.xml`, command-line arguments, or logs.

**Warning:** the sample `settings.xml` is sufficient to illustrate server credentials, but your organization may require a proxy, mirror, TLS truststore, certificates, or different usernames per repo. Some CI providers use tokens/OIDC or a maven settings generator instead of a manual file. The `id` **must match exactly**, and the token must have deploy permissions to the right hosted repository.

### 4.2. Distinguishing Build, Install, and Deploy Commands

```bash
# Build and test only:
mvn -B -ntp clean verify

# Build and install artifact into local ~/.m2/repository:
mvn -B -ntp clean install

# Build + test + publish artifacts to distributionManagement:
mvn -B -ntp -s ci/settings.xml clean deploy
```

The last `deploy` command only works when `ci/settings.xml` actually exists, the deploy URLs have been replaced with provisioned endpoints, and environment secrets are configured. **Do not run the publish command with example URLs**, as they are not active repositories.

If a project only has a JAR already built in another pipeline and needs to publish it as a Maven artifact, the Maven Deploy Plugin has the `deploy-file` goal, but it requires **complete coordinates, POM/pomFile, classifier, and policy**. You cannot simply rename a file in CI to `my-app.jar` and HTTP upload it to a Maven repo.

## 5. CI Artifact Store: Not a Maven Dependency Registry

CI artifacts store **files produced by a job** for use by other people or other jobs. Examples:
- `target/release-demo-0.1.0.jar` for deployment/smoke testing;
- `target/surefire-reports/*.xml` for tracking test failures;
- `target/site/jacoco/index.html` or coverage reports;
- `dist/app.jar.sha256` for byte verification;
- SBOMs, provenance/attestations, generated docs, and support bundles.

A CI provider usually identifies artifacts by **run ID + artifact name** and limits retention per repository/organization/plan. GitHub Actions has `actions/upload-artifact` / `actions/download-artifact`. Other CI providers (GitLab CI, Jenkins, Azure Pipelines, etc.) have equivalent features, though their APIs and permissions differ.

### 5.1. Characteristics of Workflow Artifacts

1. **Tied to a run/job:** easily answers "which files did build #308 produce?".
2. **Passed between jobs:** the build job creates the JAR; the container test job can download **that exact JAR**.
3. **Has retention:** for example `retention-days: 7` on GitHub Actions, not exceeding the organization/repository maximum policy.
4. **Not a permanent release storage solution by default:** artifacts may expire or be deleted along with workflow history.
5. **Does not automatically provide POM/transitive dependency metadata:** Maven does not understand `run-id/app-jar.zip` as `com.example:release-demo:0.1.0`.
6. **Not a dependency cache:** CI caching stores dependencies/tool caches for speedup, whereas artifacts store **deliverable or verifiable outputs**.
7. **Artifact name is not content:** `app-jar` may contain one or many files; verify checksums, not just the name.
8. **Artifact upload may archive files when storing:** if byte-for-byte comparison is needed, compute the hash of the **original JAR** and verify after download/extraction rather than comparing the checksum of the outer wrapper ZIP.

### 5.2. GitHub Actions Workflow Artifact: Concise Example

Example of a workflow that **does not publish** to Maven/OCI. It builds the JAR, stages it into a `dist` directory, generates a checksum, uploads the CI artifact in the first job, and downloads/verifies it in the second job.

**`.github/workflows/build-and-check.yml`:**

```yaml
name: Build and check artifact

on:
  workflow_dispatch:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'
          cache: maven

      - name: Package
        run: mvn -B -ntp clean verify

      - name: Stage JAR and checksum
        shell: bash
        run: |
          mkdir -p dist
          cp target/release-demo-0.1.0.jar dist/app.jar
          (cd dist && sha256sum app.jar > app.jar.sha256)

      - name: Upload CI artifact
        uses: actions/upload-artifact@v4
        with:
          name: release-demo-jar
          path: dist/
          if-no-files-found: error
          retention-days: 7

  verify-download:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Download CI artifact
        uses: actions/download-artifact@v4
        with:
          name: release-demo-jar
          path: dist

      - name: Verify checksum
        shell: bash
        run: |
          cd dist
          sha256sum -c app.jar.sha256
          jar tf app.jar | grep 'BOOT-INF/classes/'
```

**Preconditions:** this workflow assumes there is a `pom.xml`/Java application producing `target/release-demo-0.1.0.jar` as in the hands-on section below. `actions/upload-artifact@v4` and `actions/download-artifact@v4` are illustrative action names only; for production CI, pin actions to an approved commit SHA and update versions per policy. `ubuntu-latest` and hosted runner images may change tool versions, so strict reproducibility gates require more precise runner/container toolchain pinning.

`sha256sum -c app.jar.sha256` prints a line equivalent to `app.jar: OK` if the file bytes match. This is **evidence that the file passed between jobs was not modified** relative to the input checksum; it does not prove the artifact is safe, nor does it guarantee the repository/cache was not compromised. The `jar tf` check confirms the JAR has the Spring Boot layout; if test report artifacts also need to be saved, add **another artifact** or an appropriate upload path.

**If a workflow downloads an artifact from another workflow run**, the right run-id/token/permissions must be selected; do not assume `download-artifact` in the current run automatically finds artifacts from any previous workflow.

### 5.3. GitHub Artifacts Differ from GitHub Packages

A **GitHub Actions workflow artifact** is an output belonging to a workflow run. **GitHub Packages** can provide a Maven package registry and container registry (GHCR). They share the GitHub brand, but **their APIs, retention, permissions, and publish commands differ**.

For example:
- `actions/upload-artifact`: stores `dist/app.jar` as a CI workflow artifact.
- `mvn deploy` to the package registry's Maven endpoint: publishes `GAV + POM/JAR`.
- `docker push ghcr.io/org/app:1.2.0`: publishes an OCI image manifest and layers.

A JAR uploaded with `actions/upload-artifact` **does not automatically appear** for dependency consumers to resolve by Maven GAV. And an OCI image push **does not automatically create** a Maven release.

## 6. OCI Registry: Store for Manifests, Configs, and Layers

An OCI image has a content structure different from a Maven artifact:

```text
registry.example.invalid/team/release-demo:0.1.0
                  |
                  v
tag -> OCI image manifest / image index
                  |
                  +--> image config digest
                  +--> filesystem layer digest #1
                  +--> filesystem layer digest #2
                  +--> ...
```

**Image reference**:
- `registry.example.invalid/team/release-demo:0.1.0`: repository + tag.
- `registry.example.invalid/team/release-demo@sha256:<actual-digest>`: repository + manifest/index digest.

`<actual-digest>` is descriptive notation, **not a valid SHA-256** to copy and run. The digest must be obtained from the registry after build/push. Tags can be reassigned if the registry permits; a digest identifies the specific manifest/index content.

### 6.1. One Image Can Support Multiple CPU Architectures

An image tag can point to an OCI index (Docker manifest list):

```text
tag: 0.1.0
   |
   v
OCI index sha256:INDEX...
   |
   +--> linux/amd64 manifest -> AMD64 config/layers
   +--> linux/arm64 manifest -> ARM64 config/layers
```

`INDEX...` is illustrative only. When Kubernetes/a node pulls an image from an **index**, the container runtime selects the variant matching the CPU architecture/OS. Java bytecode JARs may be portable across architectures, but **the JRE and native OS libraries inside the image** are not portable that way. If multi-architecture support is required, the appropriate platform manifests must be built/published and runtime-tested.

### 6.2. Docker Push/Pull Does Not Use Maven GAV

```bash
# After building a local image with a name and tag:
docker push registry.example.invalid/team/release-demo:0.1.0

# On the deployment machine, once authorized:
docker pull registry.example.invalid/team/release-demo:0.1.0
```

These commands are **templates only after replacing the real hostname, running docker login, and building/tagging the image**. The Docker Registry API does not read Maven `pom.xml` to resolve `groupId:artifactId:version` or transitive dependencies. It exchanges manifests/layers using OCI/Docker distribution semantics.

An OCI registry can store **non-image OCI artifacts** (such as SBOMs/Helm charts with supporting tools like ORAS), but that **does not make the Maven Deploy Plugin automatically understand that endpoint**. If you want to distribute a Java library via Maven, use an appropriate Maven repository endpoint.

### 6.3. Image Digest Differs from JAR SHA

| Hash | Hashed object |
| --- | --- |
| `sha256sum target/release-demo-0.1.0.jar` | Bytes of the JAR file |
| `docker image inspect .Id` | Usually the image config digest of the local image |
| `docker buildx imagetools inspect...` `Digest:` line | Manifest or multi-platform index digest on the registry |
| Layer digest in manifest | Compressed filesystem layer |
| Downloaded CI artifact file digest | May be JAR bytes, ZIP container artifact, or separate metadata depending on how it is computed |

Do not take a JAR checksum and use it as `docker pull repository@sha256:...`; those are two addresses for **two different types of objects**.

## 7. Complete Hands-On Example: One Spring Boot JAR, Three Delivery Channels

We will create a simple web application, build the JAR with Maven, and observe:
1. The JAR file on disk after `mvn package`.
2. The JAR file uploaded/downloaded via CI artifacts and verified byte-for-byte.
3. A Docker image containing the JAR pushed to an OCI registry.
4. How to publish the JAR's Maven coordinates when an authorized repository is available.

**Environment:** Java 17+, Maven 3.9.x compatible with Spring Boot 3.5.0, Docker Engine/Buildx when running the OCI section, Linux/macOS Bash or Windows equivalent. Some publish steps require private endpoints/credentials provided by your organization and **cannot be run with placeholders**.

### 7.1. Project Structure

```text
release-demo/
├── pom.xml
├── Dockerfile
├── .dockerignore
├── src/main/java/com/example/release/ReleaseDemoApplication.java
├── dist/                                      # created after build, do not commit
└── target/                                    # generated by Maven
```

### 7.2. Complete Maven/Spring Boot pom.xml

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.0</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>release-demo</artifactId>
    <version>0.1.0</version>
    <name>release-demo</name>
    <packaging>jar</packaging>

    <properties>
        <java.version>17</java.version>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>

    <!-- Only enable after the organization provides the repository URL and deploy credentials.
    <distributionManagement>
        <repository>
            <id>internal-releases</id>
            <url>https://repo.example.invalid/repository/maven-releases/</url>
        </repository>
        <snapshotRepository>
            <id>internal-snapshots</id>
            <url>https://repo.example.invalid/repository/maven-snapshots/</url>
        </snapshotRepository>
    </distributionManagement>
    -->
</project>
```

**Why is distributionManagement commented out?** To demonstrate **building and running locally right away** without needing a publish account; the URLs in `distributionManagement` are `example.invalid` and do not exist. When `mvn deploy` is needed, uncomment it and replace endpoints + server IDs/CI secrets according to your real system. With the Spring Boot starter parent, `spring-boot-maven-plugin` is declared so `repackage` runs during the `package` phase; no duplicate execution needs to be added.

### 7.3. Runnable Java 17 File

**`src/main/java/com/example/release/ReleaseDemoApplication.java`:**

```java
package com.example.release;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class ReleaseDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(ReleaseDemoApplication.class, args);
    }

    @GetMapping("/ready")
    public String ready() {
        return "ready";
    }

    @GetMapping("/version")
    public String version() {
        return "release-demo:0.1.0";
    }
}
```

Both endpoints use literals only so output does not depend on environment. In a real application, the version should come from controlled release metadata (project version or Git commit) rather than hardcoding in source, though this example allows learners to verify output deterministically.

### 7.4. Build, Run, and Inspect Archive

```bash
mvn -B -ntp clean package
jar tf target/release-demo-0.1.0.jar
java -jar target/release-demo-0.1.0.jar
```

Once the web server is running (default port 8080), in another terminal:

```bash
curl -fsS http://localhost:8080/ready
curl -fsS http://localhost:8080/version
```

**Exact response body per request:**

```text
GET /ready   -> ready
GET /version -> release-demo:0.1.0
```

The lines above are **a mapping table of endpoints and bodies**, not verbatim stdout from a single curl command. When executing curl, it prints only the body `ready` or `release-demo:0.1.0`, typically without a trailing newline. Stop the JVM with Ctrl+C before running steps that use the same port.

`jar tf` will contain representative entries:

```text
META-INF/MANIFEST.MF
BOOT-INF/classes/com/example/release/ReleaseDemoApplication.class
BOOT-INF/lib/...
org/springframework/boot/loader/...
```

The `...` indicates placeholder notation, not a literal JAR entry name. This is an **executable Spring Boot archive** created by `repackage`; it is not an OCI image and has not been uploaded to any remote repository.

## 8. Preparing a Single JAR for CI and Docker

After `mvn package`, create a staging directory:

```bash
mkdir -p dist
cp target/release-demo-0.1.0.jar dist/app.jar
(
  cd dist
  sha256sum app.jar > app.jar.sha256
  sha256sum -c app.jar.sha256
)
```

On Linux with `sha256sum`, the verification command prints:

```text
app.jar: OK
```

This point is critical: `dist/app.jar` is a **copy of the built executable JAR**. In CI, **this exact file** should be used to upload the workflow artifact and to build the OCI image; do not rebuild from source in a later job and assign the same version if your goal is to publish the exact binary that was tested.

On Windows PowerShell, you can use `Get-FileHash -Algorithm SHA256` and the corresponding copy command; the example `app.jar.sha256` file uses `sha256sum` format for Linux CI.

**Keep `dist/` and `target/` outside Git.** CI artifacts can store both `app.jar` and the checksum file, but the Git source repository should not unnecessarily store JARs from every build.

## 9. Packaging the JAR into an OCI Image: Dockerfile Without a Maven Repo

**`Dockerfile`:**

```dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY dist/app.jar /app/app.jar

USER 10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

**`.dockerignore`:**

```dockerignore
.git
target/
.gradle/
.idea/
.vscode/
.env
*.pem
*.p12
*.key
```

Do not exclude `dist/` because the Dockerfile needs to copy `dist/app.jar`. If the pipeline uses a Docker build context other than the project root, ensure `dist/app.jar` is inside that context before `docker build`.

Run locally:

```bash
docker build -t release-demo:local .
docker run --rm -p 127.0.0.1:8080:8080 release-demo:local
```

After the container starts, `curl -fsS http://localhost:8080/ready` returns `ready`. `EXPOSE 8080` only documents the intended port, while `-p 127.0.0.1:8080:8080` publishes the port on the loopback host. If a local Java process is still running on port 8080 at the same time, `docker run` may fail to bind; stop the old process.

**What changed:** you created an **OCI container image** containing Linux/JRE layers and the Java archive. Only after `docker push` or `buildx --push` to a remote registry is the image actually published. A successful local `docker build` does not mean the image is present in the registry.

### 9.1. Publishing an OCI Image When a Real Registry Exists

When you have registry access and a confirmed repository name:

```bash
# IMAGE_REF provided by CI/release environment, e.g. hostname/repo:version.
: "${IMAGE_REF:?Set an authorized OCI registry image reference}"

docker tag release-demo:local "$IMAGE_REF"
docker push "$IMAGE_REF"

docker buildx imagetools inspect "$IMAGE_REF"
```

These commands use Bash and **require IMAGE_REF to be a valid image reference**, such as a configured organizational registry; they cannot run with an unprovisioned name. CI must log in using a secret/token per policy; do not write passwords into the Dockerfile or shell history. `imagetools inspect` verifies the published manifest/digest on the remote registry.

If the registry returns an **index digest** (multi-platform), it represents a set of platform manifests; if the image was built for a single platform, the reference may be a single manifest. Do not assume `app.jar`'s digest is the image digest.

### 9.2. Do Not Misuse Docker Push for a Maven Library

When another Java library needs `GreetingService.class` or API classes via a Maven dependency, pushing an executable OCI image to a registry **does not enable Maven to resolve those classes**. A registry serves an image filesystem/runtime, whereas a Maven consumer needs proper **JAR + POM + GAV** from a Maven repository.

An OCI registry may support storing generic/OCI artifacts, but the consumption workflow **is not equivalent** to `<dependency>com.example:shared-lib:1.0.0</dependency>` without specialized Maven tooling/adapters.

## 10. Publishing Maven Artifacts: Right for Which Consumers?

If a Spring Boot app only runs as a **service/container**, an OCI image is usually the direct deployment deliverable. However, a Maven repository can still be useful for storing Java packages, or for releasing an artifact to an environment running `java -jar` without containers.

Before publishing:
- Decide whether this is an **application executable JAR** or a **library JAR** for consumers.
- Choose GAV/version/release policy.
- Configure `distributionManagement` with the right releases/snapshots URLs.
- Supply `settings.xml` credentials for matching server IDs.
- Run tests and deploy only when they pass.

Command from the source tree:

```bash
mvn -B -ntp -s ci/settings.xml clean deploy
```

**Meaning:** builds, tests, packages/repackages, installs locally per lifecycle, and deploys the artifact/POM to the Maven hosted repository. With the example's commented-out `distributionManagement`, this command **has no remote deploy destination**. Do not overlook this precondition.

### 10.1. Why Isn't an Executable Boot JAR an Ideal Library JAR?

A Boot executable JAR puts classes under `BOOT-INF/classes` and nested dependencies under `BOOT-INF/lib`. When another module consumes it as a regular Maven dependency, the Java classpath does **not** automatically treat `BOOT-INF/classes` as the root of a library JAR. Therefore, if code needs to be reused across services, publish a separate **plain library JAR**.

If the same Maven module needs to publish both a **plain JAR for dependencies** and an **executable JAR for operations**, the Spring Boot Maven Plugin can attach the executable JAR with a classifier, such as `exec`, while keeping the main artifact as a plain JAR:

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <classifier>exec</classifier>
    </configuration>
</plugin>
```

This is a **replacement snippet for the plugin configuration in `pom.xml`**; do not paste two plugin declarations with the same group/artifact. With the proper setup, Maven output can include:
- `release-demo-0.1.0.jar`: plain JAR main artifact;
- `release-demo-0.1.0-exec.jar`: executable Spring Boot archive, attached classifier `exec`.

**Warning:** when using classifier `exec`, the Dockerfile must COPY **`release-demo-0.1.0-exec.jar`**, not the plain `release-demo-0.1.0.jar`. If only distributing a service, keep the simple default configuration of the main example with no classifier needed. In a multi-module architecture, separating the library module and the Spring Boot app module is usually clearer.

### 10.2. Maven Repository Consumer: Dependency POM Example

A consumer module adds:

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>shared-api</artifactId>
    <version>1.2.0</version>
</dependency>
```

and configures `<repositories>`/`settings.xml` appropriately so Maven fetches the right hosted artifact. Maven downloads the POM and transitive dependencies according to the dependency graph. **Do not** add a `workflow artifact URL` or `docker.io/repo:tag` to `<dependency>`, as those are not Maven coordinates.

**Downloading a Maven artifact to verify** (assuming remote repository declaration/credentials are configured):

```bash
mvn -B -ntp dependency:get \
  -Dartifact=com.example:shared-api:1.2.0
```

This command uses the Maven Dependency Plugin and requires plugin resolution and an available remote repository. It places the artifact into the local Maven cache; it does not run the service or pull an OCI image.

## 11. Gradle Equivalents: maven-publish and bootBuildImage Are Different

If a project uses Gradle, the three destinations must still be kept distinct:
- `maven-publish` plugin for a **Maven repository**;
- CI provider upload-artifact for **workflow artifacts**;
- `bootBuildImage` or Docker/Buildx for an **OCI image**.

### 11.1. Gradle Kotlin DSL: Maven Publication

Example **snippet added to a Java library's `build.gradle.kts`** that already has the Java plugin:

```kotlin
plugins {
    `java-library`
    `maven-publish`
}

group = "com.example"
version = "1.2.0"

publishing {
    publications {
        create<MavenPublication>("mavenJava") {
            from(components["java"])
        }
    }
    repositories {
        maven {
            name = "internal"
            url = uri("https://repo.example.invalid/repository/maven-releases/")
            credentials {
                username = providers.environmentVariable("MAVEN_REPO_USER").orNull
                password = providers.environmentVariable("MAVEN_REPO_TOKEN").orNull
            }
        }
    }
}
```

**Note on adapting to a real Kotlin DSL file:** the two lines ``java-library`` and ``maven-publish`` inside `plugins` are wrapped in backticks for display; **standard Kotlin DSL plugin syntax** is:

```kotlin
plugins {
    `java-library`
    `maven-publish`
}
```

This section **illustrates publishing a Java library** and does not apply directly to an executable Boot app without selecting the right component/artifact. The `example.invalid` URL is non-functional. With the Gradle plugin DSL, you can also write `id("java-library")` and `id("maven-publish")` (valid) to avoid syntax confusion.

Publish command once endpoint/credentials are in place:

```bash
./gradlew publish
```

Gradle generates the Maven publication containing POM/JAR per the component and uploads it to the declared repository. **`publish` is not Docker push**. For a Spring Boot executable JAR, you need to deliberately configure publication of the `bootJar` artifact if you want to publish it separately; plain `components["java"]` may not be the executable binary you intend to deliver.

### 11.2. Spring Boot Gradle bootBuildImage

With the Spring Boot and Java plugins, the `bootBuildImage` task can build an OCI image using Cloud Native Buildpacks. An illustrative Kotlin DSL snippet:

```kotlin
import org.springframework.boot.gradle.tasks.bundling.BootBuildImage

tasks.named<BootBuildImage>("bootBuildImage") {
    imageName.set("registry.example.invalid/team/release-demo:0.1.0")
    publish.set(false)
}
```

`publish=false` means building the image in the local daemon/builder without sending it to an OCI registry. To publish, `publish=true` and appropriate registry authentication/permissions are required. **This task does not write Maven GAV/POM to a Maven repository and does not create a CI workflow artifact upload**.

## 12. Spring Boot Cloud Native Buildpacks Also Publish OCI Images

Besides a Dockerfile, the Spring Boot Maven Plugin has the goal:

```bash
mvn -B -ntp spring-boot:build-image \
  -Dspring-boot.build-image.imageName=release-demo:local
```

This command can create an OCI image with Buildpacks when a supported Docker daemon/builder is available and the buildpack images can be pulled. Building a local image is **different** from publishing to a registry.

Once the image name is configured as a reference to an authorized registry and proper CI credentials are in place, publishing can be enabled:

```bash
mvn -B -ntp spring-boot:build-image \
  -Dspring-boot.build-image.imageName=registry.example.invalid/team/release-demo:0.1.0 \
  -Dspring-boot.build-image.publish=true
```

**The publish command is illustrative** and not runnable with `example.invalid`. If the repository uses a private registry, `docker.publishRegistry` credentials or a Docker/credential helper may be required depending on the plugin version and environment; check docs for the exact Spring Boot version. Do not put passwords directly on the CLI (which can leak in process lists/logs), and do not use default Docker Hub credentials for a company registry.

**Relationship between goals:** `spring-boot:repackage` builds an executable Java archive; `spring-boot:build-image` uses Buildpacks to build an OCI image. Neither is equivalent to `mvn deploy` (Maven distribution).

## 13. Sketching a Controlled Release Pipeline

A solid release flow separates responsibilities:

```text
(1) Build & test
    mvn clean verify
    |
    +-- app.jar, app.jar.sha256, test reports, SBOM
    |
    v
(2) Store CI artifacts by run/commit, short-to-medium retention
    |
    +-- QA job downloads JAR again, verifies checksum, smoke tests
    |
    v
(3) Release approval / security scanning / provenance
    |
    +-- Maven repository (if Java consumers exist)
    |      Maven GAV + POM + checksum, immutable release version
    |
    +-- OCI registry (if deploying containers)
           image digest + manifests/layers, arch coverage
    |
    v
(4) Deploy
    - Java consumer: locked GAV/version
    - Kubernetes/container: repository@sha256:index-or-manifest-digest
    - VM java -jar: download exact release JAR + verify checksum
```

**Avoid "QA passed on A, but published B":** if the QA job tests a JAR file from one run and the publish job rebuilds from source with a different version/dependency/JDK without checking bytes, the released product may not match the tested artifact. A reliable approach is to **promote the exact bytes already verified**, or rebuild reproducibly and **prove identical checksums** before publishing.

### 13.1. Build Once, Publish Multiple Forms

CI can run `mvn clean deploy` in **a single invocation** when publishing to a Maven repository and QA gate conditions are satisfied before deploy. In the same session, take the executable JAR and use the Dockerfile to build the OCI image.

If jobs must be split:
- upload JAR + checksum;
- the next job downloads and verifies;
- publish the image from that exact downloaded JAR;
- Maven publish uses a mechanism supporting publishing **already-verified files** with full POM/coordinates, or uses a unified build/release job; do not blindly invoke `mvn deploy` from a folder containing only a JAR without a Maven POM.
- preserve provenance linking Git commit, artifact SHA-256, image digest, and build run ID.

No single CI syntax works across every provider; the GitHub Actions YAML above is an example of handoff, while publish commands depend on the real repository.

### 13.2. Where to Store Release Metadata?

A useful release record:

| Field | Example format | Purpose |
| --- | --- | --- |
| Git revision | Approved commit SHA | Build source |
| Maven coordinates | `com.example:release-demo:0.1.0` | Java package identity |
| Executable JAR checksum | `sha256:...` of the actual JAR file | Byte verification |
| CI build | run ID + workflow + job | Locate logs/evidence |
| OCI image ref | `registry/team/release-demo:0.1.0` | Human-readable release name |
| OCI digest | `sha256:...` of the actual manifest/index | Pin image at runtime |
| SBOM/provenance | Verifiable file or OCI artifact reference | Supply-chain trace |
| Test/security status | Gate name, timestamp, tool version | Promotion decision |

Do not infer a digest from a version string. Each digest must be computed/read from the actual binary/registry.

## 14. Retention and Immutability: One Policy Does Not Fit All

### Maven releases

A Maven hosted release repository should **prevent arbitrary overwrites/deletions**, keeping POMs/JARs and metadata long enough for consumers to reproduce builds. Maven SNAPSHOTs have separate retention/cleanup to limit storage, but policy must be clear so CI does not unexpectedly lose a dependency.

### CI artifacts

Artifacts tied to individual runs typically have limited retention, such as 7 or 30 days per organization policy. Set retention intentionally: PR test reports can be kept short-term, whereas release approvals/provenance should be **archived to long-term storage** if legal/audit compliance requires it. Do not use identical artifact names across runs as proof of long-term content immutability.

### OCI images

Container registries have lifecycles for **tags, manifests, layers, and garbage collection**. A tag may be mutable, while a digest is content-addressed. However, a digest may no longer be pullable if the registry deletes manifests/layers via retention and garbage collection; retain release images according to policy, especially for rollbacks.

**A complete release requires balancing all three policies**: deleting old CI artifacts must not break production releases; deleting image layers referenced by digest must not break rollbacks; Maven release artifacts must have appropriate retention and permissions.

## 15. Authentication and Authorization: Three Different Protocols

| Destination | Typical credentials | Permissions to separate |
| --- | --- | --- |
| Maven repository | `settings.xml` server credentials/token, repository manager roles | Read dependencies; deploy releases/snapshots |
| CI artifact store | CI job identity/token, run access, repository permissions | Upload job artifact; download within workflow; admin delete |
| OCI registry | Docker login/credential helper, OCI registry token/OIDC | Pull image; push image; delete/retag per policy |

**Do not share a single admin token** across Maven, CI, and OCI if avoidable. Design with **least privilege**: build jobs only need to read dependencies; publish jobs get write access only to the target repository; deployment runtimes only need pull. Separate release and snapshot credentials, and scope OIDC subject/audience when federation is used.

### 15.1. Avoiding Secret Leaks During Build

- Do not put Maven passwords/tokens in `pom.xml` or a `settings.xml` committed to Git.
- Do not add `ARG SECRET=...` in a Dockerfile and bake secrets into layers/history.
- Do not upload `~/.m2/settings.xml`, `.docker/config.json`, `.env`, or token files as CI artifacts.
- Avoid enabling Maven `-X` or echoing all environment variables in public CI logs when secrets are present.
- Do not run untrusted PR runners with publish credentials that have production access.
- Use the CI secret store, minimal permissions, and review provenance before promotion.

OCI images and Maven JARs can be downloaded/extracted/inspected; "packaged inside an archive" is **not encryption**. If a Maven artifact is internal, configure explicit repository access; if an image contains runtime config secrets, move secrets to a runtime secret store.

## 16. Checksum, Provenance, and Signature: Value of Each Layer

**Checksums** verify that current file bytes match an expected hash. However, there are multiple objects to hash:

```text
Git tree/commit hash
         |
         v
JAR file bytes ----> sha256(JAR)
         |
         v
Docker build -----> OCI manifest/index digest
         |
         +----------> layer digests (multiple layers)
```

`sha256(JAR)` is not the OCI image digest. A Maven repository may store checksums of the JAR/POM; a CI artifact has the checksum of the raw file; an OCI registry has content-addressed manifests/layers. They relate to the same release, yet **their values do not match**.

### 16.1. A Checksum Alone Does Not Prove a Trusted Source

An attacker could replace both the artifact and the checksum if they control both. Therefore, supply-chain assurance also requires:
- trusted build identity;
- repository/registry access controls;
- signed artifacts/attestations/provenance when required by policy;
- SBOMs, vulnerability/license scans;
- immutable version/digest/registry policies;
- reproducible builds or binary promotion.

Do not advertise `sha256sum -c` as a digital signature. It only compares a content hash against data you trust came from a valid source.

### 16.2. Maven GAV Is Not Full Provenance

`com.example:release-demo:0.1.0` helps consumers locate an artifact, but does not prove who built it with which toolchain. You need to store the Git commit, CI run, JAR SHA, repository write identity, and security evidence in the release system. Likewise, OCI tag `:0.1.0` is just an alias; production deployments should pin/record the **actual digest**.

## 17. Multi-Architecture Builds and OCI Index

When publishing an OCI image for `linux/amd64` and `linux/arm64`, Buildx can produce a **multi-platform image index**. Meanwhile, the Java 17 JAR file may remain the exact same portable Java artifact (assuming no native dependencies).

```text
app.jar (Java bytecode)
       |
       +--> JRE/base linux/amd64 -> AMD64 image manifest
       |
       +--> JRE/base linux/arm64 -> ARM64 image manifest
                     |
                     v
            OCI multi-platform index
```

Therefore:
- A Maven repository may distribute **one Java JAR**;
- A CI artifact store may hold **one JAR** and logs;
- An OCI registry may store **multiple manifests/layers** per CPU architecture under **one tag/index**.

Inspect using:

```bash
docker buildx imagetools inspect "$IMAGE_REF"
```

when the image has been pushed and `IMAGE_REF` is real. Do not use `uname -m` on a developer laptop as proof of a multi-platform image; inspect index manifests and smoke-test on target CPUs. If an executable Spring Boot app has JNI/native dependencies or uses native-image (GraalVM), the executable artifact may need to be built separately per architecture.

## 18. CI/CD Safeguards Against Publishing the Wrong Product

### 18.1. Do Not Publish Before Testing

A safe gate sequence:
1. Build with Maven/Gradle, run unit/integration tests.
2. Store JAR/checksum/reports in the CI artifact store.
3. Another job downloads and verifies the checksum, then runs smoke tests on those exact bytes.
4. Security scan/SBOM/provenance and release approval as required.
5. Publish Maven components if Java consumers exist.
6. Build/push the OCI image from the verified JAR, scan the final image, and inspect the index.
7. Deploy using a Maven version with verified checksum or the published OCI digest.
8. Record rollback references and monitor health.

**Trade-off:** `mvn deploy` is a lifecycle covering compile/test/package/install/deploy in a single invocation. If you invoke it directly after all gates are satisfied, Maven runs those phases itself. If you want to separate approval **after QA** but **before publish**, the pipeline must structure jobs/promotion mechanisms carefully so it does not rebuild into a different file.

### 18.2. Difference Between "Upload Succeeded" and "Release Succeeded"

An HTTP 200 from a workflow artifact upload proves the file entered CI storage **per the CI API**. It does not prove that:
- Maven consumers can resolve the `GAV`;
- OCI runtimes can pull the image digest;
- the image has been scanned;
- the JAR has the right version/manifest;
- the production release has been deployed;
- the artifact will be retained long enough.

A `mvn deploy` SUCCESS proves the Maven deployment step completed per the repository response, but does not automatically prove the OCI image was published or runs on Kubernetes.

A `docker push` SUCCESS proves the registry received the image layers/manifests, but does not automatically prove the Maven repository has the POM/JAR or that the artifact has the right checksum in CI.

## 19. Common Errors and Diagnostics

| Symptom | Common cause | Resolution |
| --- | --- | --- |
| `mvn package` succeeds but colleagues cannot fetch the artifact | JAR only exists in `target` or local Maven repository | Publish with `mvn deploy` to a hosted Maven repo with policy |
| `mvn install` succeeds then another CI machine fails | Local `~/.m2/repository` is not shared | Use a remote Maven repository or the same reactor build |
| CI uploads artifact but Maven consumer gets `Could not find artifact` | Workflow artifact lacks GAV/POM/metadata | Publish to a properly formatted Maven repository |
| `mvn deploy` reports repository not specified | Missing `distributionManagement` or alt repo | Configure the exact deploy target |
| Maven deploy reports 401/403 | Wrong server ID/token/permissions | Match `distributionManagement.id` and `settings.xml server.id` |
| Maven deploy reports 404 | URL points to wrong repository endpoint or does not support uploads | Check hosted repo URL/type |
| Maven release overwrite blocked | Version already published and immutability policy is active | Bump version, do not overwrite releases |
| Stale Maven snapshot | Repository metadata/cache `updatePolicy` | Check metadata/policy/version and CI cache |
| `docker pull` fails even though JAR is in Maven repo | Container image was not pushed to OCI | Build/tag/push image to registry |
| `docker push` 401/403 | Wrong OCI registry auth/push permission | Log in with appropriate token, check image reference |
| Docker push succeeds then Kubernetes `ImagePullBackOff` | Wrong registry/image tag, missing pull secret, or platform mismatch | Inspect image reference/index, node architecture, credentials |
| `no match for platform in manifest` | OCI index lacks requested CPU architecture | Build/push the matching target platform |
| Docker image has wrong Java app | Dockerfile COPY picked wrong JAR version or rebuilt after QA | Use checksummed JAR, inspect contents and image provenance |
| `java -jar` fails on JAR from Maven repo | Published plain JAR is not an executable Boot JAR | Pick the right classifier/JAR and manifest |
| Library consumer cannot load classes from Boot JAR | Using executable `BOOT-INF/classes` as a dependency | Publish a plain library JAR or separate library module |
| CI artifact disappeared | Retention expired or workflow run deleted | Store release binaries in long-term storage, do not rely on run artifacts |
| Downloaded artifact archive checksum differs | Comparing ZIP wrapper instead of raw JAR | Hash and verify the raw JAR inside |
| OCI tag points to new build, rollback fails | Mutable tag without digest pin | Record/deploy using `repository@sha256:...` |
| Maven dependency downloads but transitives are missing | Incorrect POM metadata, wrong exclusions/scope | Inspect published POM/dependency graph |
| Jobs building same version yield different checksums | Different toolchain, timestamps, dependencies, or generated resources | Promote exact bytes or compare reproducible builds |
| JAR scan PASSes but image has JRE CVEs | Scan missed base OS/JRE layers | Scan the **final OCI image** and base digest |
| CI job downloads artifact from wrong run | Wrong name/run-id/permissions selected | Pin run ID, verify SHA-256 and provenance |

### 19.1. Quick Diagnostic Workflow from Symptoms

1. **Ask which tool the consumer uses**: Maven/Gradle, CI download, or Kubernetes/docker pull?
2. **Identify the identity**: GAV (Java package), run-id+artifact-name (CI), repo:tag/digest (OCI).
3. **Check where the file actually landed**: `target`/`~/.m2` is not remote Maven deploy; local Docker image is not remote OCI registry.
4. **Verify access permissions and endpoint type**: Maven hosted endpoint, CI artifact API, and OCI Registry API differ.
5. **Compare checksums** of the raw JAR before/after handoff, or the pushed OCI digest.
6. **Inspect metadata**: POM/transitives for Maven, CI retention/run ID, OCI manifest/platform list.
7. **Run a real consumer**: `mvn dependency:get`, CI download/checksum, or `docker pull`/runtime smoke test.
8. **Check release policy**: immutable releases, OCI tag overwrites, CI artifact expiry.
9. **Check security/trust**: publish source, signed attestations, SBOM, and permissions.
10. **Record results**: GAV/JAR SHA/CI run ID/OCI digest and timestamps in the release record.

## 20. Misconceptions to Eliminate

1. **"All three are called artifacts so they are the same."** No: each has its own **identifier/protocol/metadata**.
2. **"`mvn package` is publishing."** No: it only produces outputs in `target`.
3. **"`mvn install` publishes to the whole team."** No: it normally installs only into the local Maven repository.
4. **"`actions/upload-artifact` creates a Maven release."** No: that is a workflow artifact, without GAV/POM under the Maven protocol.
5. **"`docker push` makes a Java module importable by Maven."** No: push only publishes an OCI image/artifact per registry semantics.
6. **"If one Artifactory/Nexus server hosts all three, the APIs are the same."** No: the same system can host multiple repository types/paths.
7. **"OCI tag `:1.0.0` is immutable."** Not by default; a tag immutability policy or digest pin is required.
8. **"Maven GAV alone proves the right source commit."** No: provenance/checksums and a release process are required.
9. **"JAR SHA-256 = image digest."** No: the hashed objects are different.
10. **"CI artifacts can be kept forever without disappearing."** Do not assume that; retention/expiry can delete them.
11. **"An executable Spring Boot JAR is ideal as a library dependency."** Usually not; use a plain JAR for libraries.
12. **"Just HTTP upload a JAR to a URL with the word maven in it."** Does not guarantee valid POM/metadata/layout.
13. **"Pushing an OCI image means it runs on every CPU."** No: matching manifests are required.
14. **"Digest pinning proves the publisher is trustworthy."** No: digest only provides content addressing, while trust requires provenance/signature/policy.
15. **"Rebuilding the same version automatically produces an identical binary."** Not if toolchains/dependencies/timestamps differ.
16. **"Saving an SBOM as a CI artifact automatically attaches it to the image."** No: explicit OCI attestation/attachment or release record linkage is required.
17. **"A Maven snapshot and a mutable Docker tag are the same mechanism."** No: Maven has snapshot metadata/version semantics different from an OCI tag pointer.
18. **"Releasing an app to Kubernetes requires publishing a Maven JAR."** No: you can build/push an OCI image from a verified JAR and deploy the image digest.
19. **"Using an OCI registry for generic artifacts makes Maven understand it automatically."** No, unless tooling/adapters actually supporting the Maven protocol are used.
20. **"CI cache and CI artifacts are the same."** No: caches optimize build inputs, whereas artifacts store build outputs/evidence.

## 21. Decision Table: Where Should You Publish?

| Situation | Appropriate destination | Reason |
| --- | --- | --- |
| Another team declares `<dependency>com.example:api:1.2.0</dependency>` | Maven repository | Needs GAV, POM, transitive dependency resolution |
| Spring Boot service deployed via Kubernetes | OCI registry | Kubelet/container runtime pulls image by digest |
| Test job in another workflow needs the built JAR | CI artifact store or release artifact store | Handoff of exact bytes, tied to run/commit and checksum |
| Store PR test reports for a few days | CI artifact store | Debugging/QA tied to workflow run |
| Release a plain Java library for Gradle/Maven | Maven repository | Standard Java ecosystem |
| Distribute a VM service to run `java -jar` | Maven repository, release storage, or suitable long-term artifact store | Depends on how installer/updater fetches binaries and verifies checksums |
| Distribute a multi-arch container image | OCI registry with image index | Runtime selects OS/architecture variant |
| Store a Helm chart via OCI | OCI registry supporting artifact types | Uses Helm/OCI client rather than Maven GAV |
| Long-term storage of SBOM/provenance | OCI attachments, release archive, or artifact store with suitable retention | Needs linkage to digest/version and policy |
| Store intermediate build outputs only within one run | CI artifact store | Permanent package publishing is unnecessary |

**Rule of thumb:** ask "**what command will the recipient type?**" If they run `mvn dependency:get`, it is a Maven repository; if a job calls `download-artifact`, it is a CI artifact; if a node runs `docker pull`, it is an OCI registry.

## 22. Spring Boot Release Checklist

- [ ] Distinguish a Java **library** from a Spring Boot **executable application**.
- [ ] Define GAV/version/packaging/classifier when a Maven package is needed.
- [ ] Point Maven `distributionManagement` to the right hosted releases/snapshots repo.
- [ ] Match Maven `settings.xml server.id` to repo ID; supply tokens from secret store, never commit.
- [ ] Run tests before publishing; if using `mvn deploy`, understand lifecycle execution through deploy.
- [ ] Do not rely on `mvn install` as a shared store across CI runners.
- [ ] Ensure CI artifacts have clear name/run ID/retention/checksum and contain no secrets.
- [ ] Verify the raw JAR checksum of downloaded CI artifacts before using them in subsequent steps.
- [ ] Build container images from the **verified JAR** rather than uncontrolled rebuilds.
- [ ] Ensure the OCI registry image reference has the right namespace/tag and pushes successfully.
- [ ] Record the **actual image digest** after push; for multi-arch, inspect the index/platforms.
- [ ] Ensure Maven releases and OCI images have immutability/retention policies supporting rollback.
- [ ] Link release metadata across Git commit ↔ JAR SHA ↔ CI run ↔ OCI digest.
- [ ] Scan Java dependencies, image OS/JRE layers, SBOM, and provenance per policy.
- [ ] Separate read/publish/deploy permissions; do not share an admin token.
- [ ] Test from the **real consumer side**: Maven resolve, CI download, docker pull/smoke.
- [ ] Proactively update base images/dependencies even when artifacts are pinned.
- [ ] Do not declare a release complete based on a single upload step succeeding.

**Conclusion:** even though all are called "artifacts," a **Maven repository** serves **Java components by GAV/POM**, a **CI artifact store** holds **workflow run outputs and evidence**, and an **OCI registry** serves **container images by tag/digest/manifests/layers**. A Spring Boot release may need all three, but consumer, version identity, retention, permissions, and checksums must be defined for each destination. Maintain the chain **Git commit → JAR SHA-256 → CI run → Maven GAV (if any) → OCI image digest (if any)** to ensure traceability, verification, and rollback.
