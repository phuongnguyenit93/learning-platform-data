# Selecting the JVM Version in a Buildpack and Checking Compatibility with Compiled Bytecode

## 1. Objectives

With **Cloud Native Buildpacks (CNB)**, Spring Boot can produce an OCI image without requiring learners to write a Dockerfile manually. The Gradle `bootBuildImage` task and Maven `spring-boot:build-image` goal invoke a builder containing buildpacks, such as Paketo Java Buildpacks. Buildpacks detect the application, select a Java runtime, create layers, and export the application image.

Two values must be kept separate:

- **Java compile target**: the Java version of `.class` files generated by `javac` or another compiler. For example, Java 17 corresponds to class-file major version **61**.
- **Container JVM**: the Java runtime selected and contributed to the application image by the buildpack. With Paketo, `BP_JVM_VERSION=17` requests the Java 17 line **during image build**, not when running an already built image.

Rule: the runtime JVM must understand the class-file versions of all classes it will load, and must also meet the minimum Java version required by Spring Boot and its dependencies. A successfully created image **does not prove** the application runs cleanly across features that only load libraries on specific requests.

After this lesson, you will be able to:

1. Understand builder, buildpacks, build-time JDK, launch-time JRE, run image, and app image.
2. Configure Java 17 with Gradle Groovy/Kotlin DSL, Maven, and Paketo `BP_JVM_VERSION`.
3. Inspect bytecode with `javap -verbose` and know that Java 11/17/21 have major versions **55/61/65** respectively.
4. Run a Spring Boot Java 17 example and read the JVM version **actually running inside the container**.
5. Inspect the image SBOM rather than guessing patch versions from the builder name.
6. Diagnose `UnsupportedClassVersionError` and distinguish it from `NoSuchMethodError`, missing native libraries, or image build errors.
7. Choose the right fix: compile validly to a lower target or upgrade the image JVM with full testing.

**Example milestone:** Spring Boot 3.3.13, Java 17. This is a fixed sample version, not a claim about the latest version of any software. Paketo's default JVM and available patch versions vary by specific builder and buildpack.

## 2. How Do Buildpacks Bring the JVM into the Image?

~~~text
Spring Boot source / executable JAR
               │
               ▼
Spring Boot bootBuildImage / build-image
               │
               ▼
CNB Builder
  ├─ lifecycle and buildpacks
  ├─ detect Java application
  ├─ analyze build-time configuration
  ├─ select JDK/JRE version per buildpack policy
  ├─ create application + launch layers
  └─ export OCI image
               │
               ▼
Final application image
  ├─ run-image OS base
  ├─ JVM/JRE launch layer
  ├─ application + dependency layers
  └─ CNB launcher/process metadata
               │
               ▼
docker run / Kubernetes
~~~

The **builder** is the build-environment image containing lifecycle and buildpacks. The **run image** provides OS userspace and does not necessarily include Java itself. Buildpacks can add the JVM launch layer. The **application image** is the final product carrying the runtime and application code.

Paketo Java buildpacks typically use a JDK in the build phase when compilation is needed and a JRE in the runtime phase; `BP_JVM_TYPE=JRE` is a common default. If a JDK is required at runtime, `BP_JVM_TYPE=JDK` may be supported by the JVM provider, though you should not ship a compiler to production merely to run `javap`.

There are two flows:

- **Building an image from a prebuilt JAR**: the Spring Boot plugin prepares the executable JAR/WAR. Bytecode is already compiled before the buildpack selects the JVM. Changing `BP_JVM_VERSION` **does not recompile class files**.
- **Building an image from source**: the Pack CLI can pass an entire Maven/Gradle project to buildpacks, and a buildpack runs the compiler inside the builder. In that case, the build-phase JVM and `--release` configuration must also match.

This lesson uses the **pre-compiled JAR** flow to directly compare bytecode ↔ launch JVM.

## 3. Class-File Major Version and Compatibility

According to the Java Virtual Machine Specification, every `.class` file has a `major_version`. A JVM cannot load a class whose major version exceeds what it supports.

| Java SE | Major | Example Conclusion |
| --- | ---: | --- |
| 8 | 52 | Java 8 classes can be loaded by JVM 17 if APIs are compatible |
| 11 | 55 | Java 11 cannot load Java 17 classes |
| 17 | 61 | Minimum baseline for Spring Boot 3.3 |
| 18 | 62 | JVM 17 cannot load |
| 19 | 63 | JVM 17 cannot load |
| 20 | 64 | JVM 17 cannot load |
| 21 | 65 | JVM 17 cannot load Java 21 classes |
| 22 | 66 | Requires a JVM supporting Java 22 format |
| 23 | 67 | Requires a JVM supporting Java 23 format |

For example, Java 21 bytecode (major 65) running on Java 17 (which only supports up to major 61) may report:

~~~text
java.lang.UnsupportedClassVersionError:
  ... has been compiled by a more recent version of the Java Runtime
  (class file version 65.0), this version of the Java Runtime only
  recognizes class file versions up to 61.0
~~~

Class names/punctuation vary by JVM, but the pair **65.0 and 61.0** is diagnostically definitive. There is no safe JVM flag to force Java 17 to accept Java 21 classes.

A newer Java runtime can run older **class-file formats**. However, Java modules/reflection, TLS/crypto, native JNI, garbage collector flags, or libraries can change behavior. Per the System Requirements documentation for **Spring Boot 3.3.13**, apps on this line require at least **Java 17** and declare compatibility up to **Java 23**. Do not run on Java 11 simply because your main class targets 11: Spring Boot 3.3 dependencies themselves require JVM 17+.

**Do not inspect only the main class:** an executable Boot JAR contains libraries inside `BOOT-INF/lib`. A dependency containing major 65 classes may only fail when a feature triggers loading that class. Check the runtime classpath and run integration tests.

## 4. `BP_JVM_VERSION` Selects the JVM at Build Time

With **Paketo Java buildpacks**, set:

~~~text
BP_JVM_VERSION=17
~~~

to request Java major 17 when creating the image. Paketo accepts majors such as `17` or `17.*` and picks an appropriate patch among supported JVM distributions. Do not guess the exact patch from this variable alone.

| Value | Effect | No Effect |
| --- | --- | --- |
| `BP_JVM_VERSION=17` | Requests JVM major 17 at build time | Does not downgrade Java 21 bytecode to Java 17 |
| `BP_JVM_VERSION=21` | Requests JVM major 21 | Does not upgrade the compiler target of an existing archive |
| `BP_JVM_TYPE=JRE` | Selects JRE launch layer if provider supports it | Does not change `javac --release` |
| `BP_JVM_TYPE=JDK` | Selects JDK launch layer when needed | Does not fix dependency API mismatches |
| `JAVA_TOOL_OPTIONS` | JVM options at runtime | Does not install a different Java major |
| `BPL_*` | Paketo runtime options | Does not alter bytecode |
| `BPE_*` | Customizes launch environment at build time | Not a compiler version selector |
| `JAVA_HOME` on host | Java of the host process when used | Does not guarantee CNB image JVM matches host |

A very common misconception:

~~~bash
docker run -e BP_JVM_VERSION=21 local/jvm-demo:0.1.0
~~~

does **not** turn an already built Java 17 image into Java 21. `BP_JVM_VERSION` is read **when building the image**; you must configure it in Gradle/Maven/Pack and rebuild.

**Default Java major can change:** do not rely on statements like “Paketo always picks Java 17” or “builder:latest always picks 21”. The Spring Boot plugin infers from compile target on the default builder, yet custom builders can behave differently. Configure explicitly, read logs, check SBOMs, and verify at runtime.

If the buildpack reports no matching JVM found, check the builder/buildpack JVM provider, CPU architecture, OS stack, JDK/JRE availability, proxy/network, and registry. Do not edit source code before knowing the issue is **failure to provision a Java distribution**.

## 5. Spring Boot Plugin Can Infer Java Target

The Spring Boot **3.3 Gradle Plugin** documents that `bootBuildImage` detects Java target compatibility via `JavaPlugin.targetCompatibility` and, when using the default Paketo builder, instructs buildpacks to install the matching Java version. The Spring Boot **3.3 Maven Plugin** detects from compiler plugin configuration or `maven.compiler.target`.

Inference is convenient, not a replacement for QA:

- A Java compiler task might set `options.release` differently from another target property.
- An application module and a library module may target different versions.
- A transitive dependency may be compiled with a newer Java version.
- A custom builder may use a different JVM provider or defaults.
- `BP_JVM_VERSION` may have been directly overridden by a user.
- The Gradle daemon may run on a different JDK than the one compiling.

Therefore, the example configures **both** `--release 17` and `BP_JVM_VERSION=17`; even though default inference can handle it, explicit configuration makes intent clear and easy to verify.

| Compile target | Image JVM | Conclusion |
| --- | --- | --- |
| Java 17, major 61 | 17 | Version match, smoke/integration tests still required |
| Java 17, major 61 | 21 | Can run major 61 bytecode; verify full compatibility |
| Java 21, major 65 | 17 | Incompatible; may fail during image build or class loading |
| Spring Boot 3.3 + major 61 | 11 | Unsupported; Spring Boot 3.3 requires Java 17 minimum |
| Main class major 61, dependency class major 65 | 17 | Risk of failure when that dependency is loaded |

A builder might catch the mismatch during build, or the image might build and fail at runtime. Do not assume every error happens at the same stage.

## 6. Java 17 Project to Verify the Exact Runtime JVM

Project `jvm-compat-demo` contains a simple REST API:

~~~text
jvm-compat-demo/
├── settings.gradle             # if using Groovy DSL
├── build.gradle
│   or settings.gradle.kts      # if using Kotlin DSL
│   or build.gradle.kts
├── gradlew                     # Gradle wrapper must be generated/provisioned
├── gradle/wrapper/
└── src/
    ├── main/java/com/example/cnb/
    │   ├── JvmCompatApplication.java
    │   └── VersionController.java
    └── test/java/com/example/cnb/
        └── VersionControllerTest.java
~~~

**Main class** — `src/main/java/com/example/cnb/JvmCompatApplication.java`:

~~~java
package com.example.cnb;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class JvmCompatApplication {

    public static void main(String[] args) {
        SpringApplication.run(JvmCompatApplication.class, args);
    }
}
~~~

**Controller** — `src/main/java/com/example/cnb/VersionController.java`:

~~~java
package com.example.cnb;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class VersionController {

    @GetMapping("/hello")
    public String hello() {
        return "hello-from-java";
    }

    @GetMapping("/runtime-major")
    public String runtimeMajor() {
        return Integer.toString(Runtime.version().feature());
    }

    @GetMapping("/runtime-version")
    public String runtimeVersion() {
        return System.getProperty("java.version");
    }
}
~~~

`Runtime.version().feature()` is a Java SE 9+ API and reads the **major version of the JVM actually serving the request**, not `build.gradle` or host laptop environment variables.

When the app runs inside a Java 17 image, the body of `GET /runtime-major` must be:

~~~text
17
~~~

`/runtime-version` returns the real patch version as a Java system property string; do not hardcode a fixed patch value before inspecting the image.

**JUnit test** — `src/test/java/com/example/cnb/VersionControllerTest.java`:

~~~java
package com.example.cnb;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

class VersionControllerTest {

    @Test
    void helloIsStable() {
        VersionController controller = new VersionController();
        assertEquals("hello-from-java", controller.hello());
    }

    @Test
    void supportedJvmForBoot33() {
        VersionController controller = new VersionController();
        int major = Integer.parseInt(controller.runtimeMajor());
        assertTrue(major >= 17);
    }
}
~~~

This test runs inside the **test task's** JVM and does **not** measure the container's Java runtime. The image runtime must be smoke-tested separately. In production, restrict access to JVM info endpoints or replace them with internal metrics/logging.

## 7. Gradle Groovy DSL: Compile 17 and Buildpack JVM 17

File `settings.gradle`:

~~~groovy
rootProject.name = 'jvm-compat-demo'
~~~

Complete `build.gradle` file:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.13'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.1.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test', Test) {
    useJUnitPlatform()
}

tasks.named('bootBuildImage') {
    imageName = 'local/jvm-compat-demo:0.1.0'
    environment['BP_JVM_VERSION'] = '17'
}
~~~

Explanation:

- `java.toolchain.languageVersion` chooses the Java toolchain for compilation/testing.
- `options.release=17` applies `javac --release 17`, restricting Java APIs and class-file target to major 61.
- `bootBuildImage.environment` sets the **builder's build-time environment** so Paketo picks launch JVM Java 17.
- `imageName` specifies a local Docker image tag for testing, without publishing to a registry.
- `spring-boot-starter-web` provides the embedded server, and the test dependency provides JUnit 5.

Commands from a project with a valid Gradle wrapper:

~~~bash
./gradlew --version
./gradlew clean test bootJar
./gradlew bootBuildImage
~~~

Docker daemon/context must be running, with network access to download builder/run images, JVM distributions, and dependencies. On Windows PowerShell, use `.\gradlew.bat`. Build scripts do not generate a Gradle wrapper automatically.

Per Spring Boot 3.3 docs, environment variables can be set for a single CLI invocation:

~~~bash
./gradlew bootBuildImage --environment BP_JVM_VERSION=17
~~~

Do not confuse this with running:

~~~bash
./gradlew compileJava --environment BP_JVM_VERSION=17
~~~

The latter is not how compiler targets are configured and has no meaning for `compileJava`. To change the bytecode target, modify toolchain/`options.release` on the appropriate task.

**Custom builder fragment**, only for organizations with existing approved images:

~~~groovy
tasks.named('bootBuildImage') {
    builder = 'registry.example/builder/java:approved'
    runImage = 'registry.example/run/base:approved'
}
~~~

`registry.example` is an illustrative placeholder, not a verified registry. Do not pick a run image incompatible with the CNB stack/ABI merely to reduce image size.

## 8. Gradle Kotlin DSL: Equivalent Syntax

File `settings.gradle.kts`:

~~~kotlin
rootProject.name = "jvm-compat-demo"
~~~

File `build.gradle.kts`:

~~~kotlin
import org.gradle.api.tasks.compile.JavaCompile
import org.springframework.boot.gradle.tasks.bundling.BootBuildImage

plugins {
    id("java")
    id("org.springframework.boot") version "3.3.13"
    id("io.spring.dependency-management") version "1.1.7"
}

group = "com.example"
version = "0.1.0"

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

tasks.withType<JavaCompile>().configureEach {
    options.release.set(17)
}

repositories {
    mavenCentral()
}

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}

tasks.named<Test>("test") {
    useJUnitPlatform()
}

tasks.named<BootBuildImage>("bootBuildImage") {
    imageName.set("local/jvm-compat-demo:0.1.0")
    environment.put("BP_JVM_VERSION", "17")
}
~~~

`BootBuildImage` is the type provided by the Spring Boot Gradle Plugin. `environment` is a `MapProperty<String,String>`, so Kotlin uses `environment.put`; this is documented Spring Boot 3.3 syntax. `options.release.set(17)` is a typed property of Gradle `JavaCompile`.

**Choose either Groovy or Kotlin DSL** for a project, using the same Java source/test files from section 6 and the same Gradle commands. Kotlin DSL does not require the main application itself to be written in Kotlin.

If the project actually uses Kotlin application source or has a Kotlin-compiled module, also check the Kotlin compiler's `jvmTarget`; `JavaCompile.options.release` does not ensure Kotlin classes target Java 17.

## 9. Maven: `maven.compiler.release` and `build-image`

A Maven project **as an alternative to Gradle** can use the same Java sources from section 6 and this complete POM:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.13</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>jvm-compat-demo</artifactId>
    <version>0.1.0</version>

    <properties>
        <java.version>17</java.version>
        <maven.compiler.release>17</maven.compiler.release>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
                <configuration>
                    <image>
                        <name>local/jvm-compat-demo:0.1.0</name>
                        <env>
                            <BP_JVM_VERSION>17</BP_JVM_VERSION>
                        </env>
                    </image>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
~~~

`java.version` and `maven.compiler.release` are compiler/build settings. `BP_JVM_VERSION` inside `spring-boot-maven-plugin/image/env` is a buildpack setting. Do not put it into dependencies or treat it as `JAVA_HOME`.

Build:

~~~bash
mvn -version
mvn clean verify
mvn spring-boot:build-image
~~~

Per Spring Boot 3.3 docs, `build-image` suits CLI usage and forks the lifecycle to ensure `package` occurs; `build-image-no-fork` is for binding into a lifecycle execution to avoid re-running the lifecycle. Do not configure two goals that double-build without understanding plugin execution.

Inspect effective POM and compiled classes:

~~~bash
mvn help:effective-pom -Doutput=target/effective-pom.xml
mvn clean compile
javap -verbose -classpath target/classes com.example.cnb.JvmCompatApplication
~~~

Expect to see `major version: 61` when compiler release 17 is active. The Maven Compiler Plugin needs a JDK capable of supporting `--release 17`. If Maven runs under JDK 11 without a newer JDK toolchain, compiling with release 17 fails even if the image builder has Java 17 — that is a **compile toolchain error**, not launch JVM selection.

If using the Maven wrapper, make sure the wrapper is provisioned; use `./mvnw` on Unix or `.\mvnw.cmd` on Windows, depending on the project.

## 10. Toolchain, `release`, `sourceCompatibility`, and `JAVA_HOME`

Multiple JVMs may be involved in a single build:

| Where measured | Meaning |
| --- | --- |
| `./gradlew --version` | Java running the Gradle daemon/launcher |
| `mvn -version` | Java running Maven |
| Gradle `java.toolchain` | JDK used by Java tasks |
| `options.release` / `maven.compiler.release` | Java language/API/bytecode target |
| `sourceCompatibility` | Source language level |
| `targetCompatibility` | Bytecode target without strictly restricting APIs |
| `BP_JVM_VERSION` | JVM the buildpack selects when constructing the OCI image |
| `Runtime.version().feature()` | Java major of the process actually running the application |

Recommended Gradle configuration:

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}
tasks.withType(JavaCompile).configureEach {
    options.release = 17
}
~~~

`--release` constrains the compiler to the public APIs of that Java release, not merely syntax/bytecode target. If you compile with JDK 21 and only set `targetCompatibility=17`, source can still reference APIs introduced only in JDK 21; running on Java 17 can then throw `NoSuchMethodError` or missing class/API errors. `--release 17` reduces this risk by checking APIs at compile time.

An advanced setup might use a JDK 21 toolchain with `options.release=17` to produce major 61; in that case, newer Java 21 language features/APIs cannot be used under the release 17 contract. Conversely, a toolchain 17 cannot compile `--release 21`.

Do not rely on global `JAVA_HOME` or `System.getenv("JAVA_HOME")` to assume what JVM resides inside a Paketo image. Host JDK, build compiler, and launch JRE serve distinct purposes.

## 11. Checking Bytecode Before Building the Image

### 11.1. Gradle

~~~bash
./gradlew clean compileJava
javap -verbose -classpath build/classes/java/main com.example.cnb.JvmCompatApplication
javap -verbose -classpath build/classes/java/main com.example.cnb.VersionController
~~~

In the output, look for:

~~~text
major version: 61
~~~

On Windows PowerShell:

~~~powershell
javap -verbose -classpath build/classes/java/main com.example.cnb.JvmCompatApplication |
    Select-String "major version"
~~~

### 11.2. Maven

~~~bash
mvn clean compile
javap -verbose -classpath target/classes com.example.cnb.JvmCompatApplication
~~~

This must also show major 61 if target 17 is in effect. For multi-module projects, adjust `-classpath` for the relevant module, e.g. `api/target/classes`.

### 11.3. Inspecting the Executable Boot Archive

Gradle:

~~~bash
./gradlew bootJar
jar tf build/libs/jvm-compat-demo-0.1.0.jar
~~~

Look for entries:

~~~text
BOOT-INF/classes/com/example/cnb/JvmCompatApplication.class
BOOT-INF/classes/com/example/cnb/VersionController.class
BOOT-INF/lib/
~~~

`jar tf` only lists archive entries; it **does not print class-file major versions**. Run `javap` on build classes, or extract the archive into a separate safe directory to inspect classes. If a file has a prepended launch script (fully executable JAR), some `jar` tools may not read/extract it properly; produce a standard JAR for inspection.

### 11.4. Checking Dependency Class Files

A major 61 main class **does not prove every runtime dependency is major 61 or lower**. If a transitive library carries Java 21/major 65 classes, an error may only surface when a request activates that library.

Inspect `runtimeClasspath`/dependency trees and supported Java matrices of dependencies. Use an appropriate bytecode scanner to check key runtime libraries. Note that **multi-release JARs** can store version-specific classes under `META-INF/versions`; do not assume every major 65 class inside a multi-release JAR gets loaded on Java 17. Understand runtime entry selection or verify with integration tests.

## 12. Verifying the Actual JVM Inside the Image

After creating the image with Gradle or Maven:

~~~bash
docker image ls local/jvm-compat-demo
docker image inspect local/jvm-compat-demo:0.1.0
~~~

`docker image inspect` reports metadata/architecture/config/labels; there is no guarantee every builder writes a fixed field named `java.version`.

Run the image:

~~~bash
docker run --rm -p 18080:8080 local/jvm-compat-demo:0.1.0
~~~

In another terminal:

~~~bash
curl -fsS http://localhost:18080/hello
curl -fsS http://localhost:18080/runtime-major
curl -fsS http://localhost:18080/runtime-version
~~~

The first two bodies **in order** are:

~~~text
hello-from-java
17
~~~

if the buildpack actually selected Java 17. These are two separate HTTP requests, not a single response. `/runtime-version` contains the real patch version; do not hardcode `17.0.x` before running the image.

If major returns 21 despite the compiled application being major 61, that does not necessarily throw a Java exception: Java 21 normally loads Java 17 classes. However, if release policy requires strictly Java 17, the image violates policy. If runtime returns 11, there is a severe mismatch with Spring Boot 3.3.

### 12.1. Checking the SBOM

Paketo buildpacks generate a Software Bill of Materials for the JVM/JRE and dependencies. With Pack CLI installed:

~~~bash
pack sbom download local/jvm-compat-demo:0.1.0
~~~

Read the SBOM files to identify the exact JRE version, vendor, checksum, packages, and architecture. Output format/directory depends on Pack CLI/SBOM format; run:

~~~bash
pack sbom download --help
~~~

`pack inspect-image local/jvm-compat-demo:0.1.0` helps inspect builder/run-image/buildpacks/process metadata, but does not replace checking the actual JRE version in the SBOM and verifying at runtime.

### 12.2. Do Not Require `javac` or `javap` in the Runtime JRE

Paketo defaults typically use a JRE launch layer; it may omit the compiler or `javap`. Lacking `javac` in a runtime image is not a bug. Check bytecode on the build machine/JDK, and check the image's JVM major via an endpoint/SBOM. Do not switch to `BP_JVM_TYPE=JDK` just to keep an unnecessary debug tool in production.

### 12.3. Running the Exact Deployment Digest

CI might build image tag `local/jvm-compat-demo:0.1.0` while production pulls a different tag. To finalize QA, cross-check the image digest of the published/deployed artifact, not just local results. Manage SBOMs, digests, and approved builder/run-image inputs per organizational policy.

## 13. Experiment: Deliberately Triggering `UnsupportedClassVersionError`

Use a standalone pure Java SE file `VersionProbe.java`, unrelated to Spring Boot:

~~~java
public final class VersionProbe {

    public static void main(String[] args) {
        System.out.println("CLASS_OK");
    }
}
~~~

**Experiment A, JDK 17:**

~~~bash
javac --release 17 VersionProbe.java
javap -verbose VersionProbe
java VersionProbe
~~~

Expect `major version: 61` from `javap` and stdout when running:

~~~text
CLASS_OK
~~~

**Experiment B, with JDK 21 and a separate Java 17 runtime:**

~~~bash
javac --release 21 VersionProbe.java
javap -verbose VersionProbe
/path/to/java17/bin/java VersionProbe
~~~

Expect `major version: 65` and Java 17 **rejecting the class** with `UnsupportedClassVersionError`. The path `/path/to/java17` is a **placeholder to replace with a real JRE 17**. If `java` on PATH is still JDK 21, the program will run and the experiment will not demonstrate the error.

`CLASS_OK` is not printed on the mismatched run: the main class is never loaded. This experiment illustrates bytecode versions; never intentionally put major 65 into a Java 17 production image.

**Fix in one of two ways:**

1. Recompile with `--release 17` once source/APIs are Java 17-compatible; keep Paketo JVM 17.
2. If the application truly needs Java 21, upgrade both the compiler target and `BP_JVM_VERSION` to 21, verify Spring Boot/dependency support, rebuild a new image, and run full tests.

Do not use `--add-opens` or clear Gradle caches as a workaround for a class-file major higher than the JVM.

## 14. When the JVM Is Newer Than the Bytecode

Scenario:

~~~text
Application compiled target 17 → class major 61
BP_JVM_VERSION=21 → runtime major 21
JVM reads class-file major 61 successfully
~~~

This is not enough to declare the application completely compatible. Evaluate framework version, JDK APIs, reflection/modules, serialization/TLS, native libraries, runtime JVM flags, JFR/profilers, and dependency agents. This is a **runtime platform upgrade**, not just changing a single number.

Safe upgrade procedure:

1. Check the compatibility matrix of Spring Boot and libraries in use.
2. Confirm the builder/JVM provider supplies Java 21 on the target OS/architecture.
3. Build a new tag/digest; do not overwrite un-QA'd release artifacts.
4. Run unit, integration, contract, and smoke tests; run security scanning.
5. Read the SBOM JRE patch/vendor and the runtime major/version endpoint.
6. Record provenance/digest and keep a rollback plan.

If you only change `BP_JVM_VERSION` from 17 to 21 on a `--release 17` project, application bytecode stays major 61. To use Java 21 language features/APIs, that is a **separate compile-target change** requiring source and dependency compatibility.

## 15. Distinguishing `BP_`, `BPL_`, `BPE_`, and `JAVA_TOOL_OPTIONS`

| Variable | Common Role |
| --- | --- |
| `BP_JVM_VERSION` | Selects JVM during image creation |
| `BP_JVM_TYPE` | Selects JDK or JRE launch layer |
| `BP_JVM_JLINK_ENABLED` | Creates a trimmed JRE with `jlink` when supported by buildpack |
| `BPL_*` | Runtime features/diagnostics handled by Paketo buildpacks |
| `BPE_*` | Configures launch environment modifications at build time |
| `JAVA_TOOL_OPTIONS` | Flags passed to the JVM process at runtime |
| `SPRING_PROFILES_ACTIVE` | Spring Boot profile, not Java version |

Example runtime flag (does not change Java version):

~~~bash
docker run --rm \
  -e JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70.0" \
  -p 18080:8080 \
  local/jvm-compat-demo:0.1.0
~~~

Paketo may already populate default `JAVA_TOOL_OPTIONS`. Overriding the whole variable from Docker CLI can drop necessary settings; read buildpack/runtime docs and test before using.

**Optional** Gradle fragment illustrating adding launch env flags:

~~~groovy
tasks.named('bootBuildImage') {
    environment['BPE_DELIM_JAVA_TOOL_OPTIONS'] = ' '
    environment['BPE_APPEND_JAVA_TOOL_OPTIONS'] =
        '-XX:+HeapDumpOnOutOfMemoryError'
}
~~~

Do not apply this fragment to fix `UnsupportedClassVersionError`. Heap dumps can contain sensitive data and require storage/permission policies.

## 16. Errors and Practical Diagnostics

| Symptom | Possible Cause | Resolution |
| --- | --- | --- |
| `UnsupportedClassVersionError 65.0 / 61.0` | Java 21 bytecode on Java 17 JVM | Compile `--release 17` or use JVM 21 image and test |
| `UnsupportedClassVersionError 61.0 / 55.0` | Spring Boot Java 17 on Java 11 | Spring Boot 3.3 requires Java 17+, update runtime |
| Buildpack lacks JVM 17 | JVM provider/builder/stack/arch cannot supply it | Check buildpack metadata, approved builder/mirror |
| `docker run -e BP_JVM_VERSION=21` does not change JVM | Build-time variable passed at runtime | Rebuild image with `BP_JVM_VERSION` set properly |
| Host `java -version` is 21, image is 17 | Host and launch JVM are independent | May be intended; verify runtime inside image |
| Gradle `bootBuildImage` does not exist | Spring Boot/Java plugin not applied to module | Check `./gradlew tasks --all`, plugin/module paths |
| Maven `build-image` fails | Maven goal, Docker engine, builder/network error | Check logs and effective POM |
| `javap` app class 61, dependency class 65 | Transitive/generated Java 21 class | Check `runtimeClasspath` and stack trace class name |
| `NoSuchMethodError` or missing JDK API | Compiled without API restriction, binary dependency mismatch | Use `--release`, check library versions |
| `NoClassDefFoundError` yet major matches | Missing dependency or class initialization failure | Check Boot JAR/stack trace; do not blindly change JVM |
| `UnsatisfiedLinkError` | Native ABI/OS/arch/loader mismatch | Check run image/native library and platform |
| Image major 17 yet JRE patch differs from expectation | Buildpack/JVM vendor update | Read SBOM, pin approved inputs |
| Pack CLI missing or SBOM not found | Pack version/image/registry/context | Check `pack --version`, `pack sbom download --help` |
| Container runs yet endpoint unreachable | Wrong port mapping/server config | Check logs, `-p`, and `server.port` |
| CI tests on Java 21 while image runs Java 17 | Test toolchain mismatches release environment | Add image-level tests and align policy |

**Diagnose in order:** record class name + stack trace → identify bytecode major of failing class → measure actual runtime major → compare compile target → check buildpack version/provider → inspect dependencies → rebuild and re-run new image. Do not wipe all caches over a single class major mismatch.

### 16.1. Why One Working Endpoint Does Not Prove All Libraries Are Compatible

Java lazy-loading allows certain classes to be loaded later. For instance, the app starts normally and `/hello` returns HTTP 200, yet a reporting library compiled at major 65 is only loaded on a `/report` request. Write integration tests covering major paths, especially codegen, plugins, agents, JNI, and transitive dependencies.

### 16.2. Multi-Release JARs

Some JARs contain classes under `META-INF/versions/9`, `META-INF/versions/17`, or `META-INF/versions/21`. The JVM selects the appropriate version-specific entry per multi-release JAR rules. Therefore, do not conclude “any JAR containing a major 65 class will fail on Java 17” if that class sits inside the version-specific entry for Java 21. Use multi-release-aware scanners or runtime tests.

### 16.3. Native Image Differs from JVM Image

GraalVM native-image buildpacks produce a native executable; there is no JVM class loader reading `.class` files at runtime in the same way. If switching to native image, study GraalVM/native toolchains and buildpacks separately rather than applying the same JVM runtime matrix as for Java application images.

## 17. CI/CD Pipeline Checking Both Compile Target and Runtime Image

Gates can be organized in steps:

1. **Lock inputs:** Gradle wrapper/Maven, Spring Boot plugin, approved JDK toolchain, dependencies, builder/run-image version/digest.
2. **Compile/test:** Gradle `clean test bootJar` or Maven `clean verify`.
3. **Bytecode check:** `javap -verbose` on main class and key generated/dependency classes; Java 17 must show major 61.
4. **CNB build:** `bootBuildImage`/`spring-boot:build-image` with explicit `BP_JVM_VERSION`.
5. **Image metadata:** record image tag/digest, architecture, buildpacks, selected JVM provider.
6. **Runtime smoke test:** run image, check HTTP responses and runtime major via endpoint/metrics.
7. **SBOM:** archive JRE vendor, patch, and vulnerability scan results.
8. **Integration/security tests:** verify functionality, native libs, Java modules, security policies, and Kubernetes/registry environment.
9. **Publish/deploy:** only after full QA, publish the image and confirm that **exact digest** runs in the target environment.

Gradle example:

~~~bash
./gradlew clean test bootJar
javap -verbose -classpath build/classes/java/main com.example.cnb.JvmCompatApplication
./gradlew bootBuildImage
docker image inspect local/jvm-compat-demo:0.1.0
~~~

Then run the container and test from another terminal:

~~~bash
docker run --rm -p 18080:8080 local/jvm-compat-demo:0.1.0
~~~

~~~bash
curl -fsS http://localhost:18080/hello
curl -fsS http://localhost:18080/runtime-major
~~~

For non-interactive CI, run the container detached, add a readiness probe with timeout, collect logs, and clean up per policy. Do not create a “green image build” check and skip runtime smoke tests.

Evidence that is **insufficient on its own**: seeing only `mvn package BUILD SUCCESS`; seeing only `BP_JVM_VERSION=17` in config; seeing only `major version: 61` on the main class; seeing only that the Docker image exists; or calling only `/hello` without checking runtime Java/dependencies.

## 18. Exercises with Answers

### Exercise 1: Identifying Major Version

**Prompt:** `javap` prints `major version: 65`. Which Java target is that? Can JVM 17 run it?

**Answer:** Java 21. JVM 17 cannot load major 65 classes; you need a lower compile target or a higher runtime, with testing.

### Exercise 2: Spring Boot 3.3 Minimum Version

**Prompt:** application main class targets 11, yet dependencies are Spring Boot 3.3.13. Can the entire app run on JVM 11?

**Answer:** No. Spring Boot 3.3.13 requires Java 17 at minimum.

### Exercise 3: Gradle Groovy Configuration

**Answer:**

~~~groovy
tasks.named('bootBuildImage') {
    environment['BP_JVM_VERSION'] = '17'
}
~~~

This is only a fragment for a project that already applies the Spring Boot and Java plugins.

### Exercise 4: Gradle Kotlin Configuration

**Answer:**

~~~kotlin
import org.springframework.boot.gradle.tasks.bundling.BootBuildImage

tasks.named<BootBuildImage>("bootBuildImage") {
    environment.put("BP_JVM_VERSION", "17")
}
~~~

### Exercise 5: Maven

**Answer:**

~~~xml
<configuration>
    <image>
        <env>
            <BP_JVM_VERSION>17</BP_JVM_VERSION>
        </env>
    </image>
</configuration>
~~~

This is a plugin configuration fragment and does not alter Maven compiler release.

### Exercise 6: Host Java 21, Image Java 17

**Prompt:** `java -version` on the laptop is 21, `/runtime-major` returns 17. Is that an error?

**Answer:** Not necessarily. Build tool JVM and container JVM are independent environments; what matters is that the runtime matches policy and bytecode.

### Exercise 7: Changing Environment Too Late

**Prompt:** a Java 17 image is already built; you run `docker run -e BP_JVM_VERSION=21`. Does the runtime switch to 21?

**Answer:** No. `BP_JVM_VERSION` must be set at image build time and a new image built.

### Exercise 8: Main Class Right, Dependency Wrong

**Prompt:** main class is major 61, a transitive library has a major 65 class, and runtime is Java 17. Might the error only appear when a specific feature is called?

**Answer:** Yes. The JVM may only load the major 65 class when that feature is used; add integration tests and inspect the dependency.

### Exercise 9: Compiler `release` vs `target`

**Prompt:** using JDK 21 to compile `targetCompatibility=17`, while source calls a JDK 21 API. Why can runtime 17 fail?

**Answer:** `-target` restricts bytecode format, not full Java platform APIs. Use `javac --release 17` via Gradle/Maven.

### Exercise 10: Checking Exact JVM Patch

**Prompt:** does `BP_JVM_VERSION=17` guarantee the image uses a fixed `17.0.x` JRE patch?

**Answer:** No. Read the SBOM and runtime version, and manage approved builders/JVM providers/digests and patch update policies.

## 19. Pre-Release Checklist

- [ ] Framework version verified to support selected JVM; Spring Boot 3.3.13 requires Java 17+.
- [ ] Gradle/Maven/JDK build compiler uses an appropriate version rather than relying on an arbitrary host JDK.
- [ ] Compiler target locked with `--release`/toolchain or Maven compiler release.
- [ ] `javap -verbose` confirms compiled class major matches contract.
- [ ] Key runtime/transitive/generated classes checked for compatibility.
- [ ] `BP_JVM_VERSION` set in the build-time environment of the right builder, not just `docker run`.
- [ ] Buildpack/JVM provider/run image support the required version, OS/CPU architecture, and vendor.
- [ ] Image built cleanly with clear tag/digest; no confusion with stale images.
- [ ] Container launched for real and runtime major read from the process inside the image.
- [ ] SBOM shows exact JRE vendor, patch version, and dependencies.
- [ ] Runtime flags/native dependencies/modules/agents verified by integration tests.
- [ ] When Java major changes, regression/performance/security tests and rollback plan are in place.
- [ ] CI/deployment records provenance and verifies the actual deployed digest.
- [ ] Build success, class major, or buildpack env alone is never treated as proof of runtime compatibility.

**Conclusion:** `BP_JVM_VERSION` determines **the JVM Paketo supplies to the image**, while toolchain and `--release` determine **the class files generated by the compiler**. With Spring Boot 3.3 Java 17, the clearest control path is compiling with `--release 17`, verifying major **61**, building the image with `BP_JVM_VERSION=17`, checking the SBOM, and running the real image to confirm JVM major **17**. On any mismatch, fix the appropriate compile or runtime layer and re-verify the full image and dependencies.
