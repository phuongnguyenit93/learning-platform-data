# Controlling build.time and Metadata That Changes on Every Build

## 1. The Problem: Same Source Code, Different JAR Checksums

A **reproducible build** aims to ensure that given the **exact same source code, inputs, tool versions, and locked dependencies**, you can regenerate an artifact whose contents are **byte-for-byte identical**. This is a vital foundation for verifying software provenance, comparing checksums, validating releases, and relying on build caches.

Spring Boot can generate metadata at `META-INF/build-info.properties`. Fields such as `build.artifact`, `build.group`, and `build.version` normally stay unchanged across builds of the same commit. However, `build.time` typically represents the **actual build execution time**, changing on every run, altering the metadata file, and causing **the executable JAR's checksum to change**. Beyond metadata, ZIP/JAR entry timestamps, entry order, build numbers, CI run IDs, manifest timestamps, and other generated files can also introduce discrepancies.

Illustrative scenario:

~~~text
Git commit: abc123  (unchanged)
Project version: 1.0.0
Maven / Gradle / JDK / dependencies: unchanged

Build A, 09:00:
  META-INF/build-info.properties
    build.version=1.0.0
    build.time=2026-11-09T02:00:00Z

Build B, 09:05:
  META-INF/build-info.properties
    build.version=1.0.0
    build.time=2026-11-09T02:05:00Z

=> File contents differ.
=> JAR checksum can differ even with unchanged source.
~~~

**Core principle:** when **reproducibility** is the goal, do not embed CI-execution-time-dependent data inside the artifact—or turn it into an **immutable, predetermined input**. In particular, distinguish **the `build.time` value** from **ZIP entry timestamps**: they are two independent issues and both must be handled.

### Learning Outcomes

After this lesson, you will be able to:

1. Explain how `build.time`, `project.build.outputTimestamp`, archive-entry timestamps, build numbers, and commit IDs differ.
2. Choose a metadata policy: **omit `build.time`**, or **pin it to a known source time** instead of reading the live clock.
3. Configure the Spring Boot Maven Plugin `build-info` goal with `<time>off</time>` alongside `project.build.outputTimestamp` for packaging.
4. Configure Gradle `bootBuildInfo` to exclude `time`, while normalizing archive order and timestamps.
5. Write a runnable Java 17/Spring Boot 4.1.2 example, verifying `META-INF/build-info.properties` via JUnit and the Java runtime.
6. Compare **two clean builds** using SHA-256 and byte comparison, accurately locating any remaining differences.
7. Design external provenance metadata outside the artifact, avoiding embedding CI run IDs, build timestamps, hostnames, workspace paths, or secrets into the JAR.

**Lesson context:** Spring Boot Build Tooling Packaging → *Reproducible Builds*. Examples use Java 17, Spring Boot 4.1.2, Maven, and Gradle Groovy DSL. In production projects, pin exact plugin/Gradle Wrapper/JDK/dependency versions per policy.

## 2. Three Concepts Often Conflated

| Concept | Where does it live? | Meaning | Can it vary per build? |
| --- | --- | --- | --- |
| `build.time` | `META-INF/build-info.properties` | A property generated by Spring Boot build-info; optionally exposed via Actuator | **Yes**, if using wall clock |
| `project.build.outputTimestamp` | Maven configuration | Stable timestamp for **JAR/ZIP entries** of supporting plugins; can also be used by Boot Maven build-info | Should **not** change when inputs do not change |
| ZIP/JAR entry timestamps | Metadata of each entry inside the archive | Timestamp recorded in the ZIP/JAR format | Yes, if plugins preserve live timestamps |
| `build.version` | `build-info.properties` | Project version | Unchanged when version is a fixed input |
| `build.commit` (custom) | Build metadata, manifest, or SBOM by design | Git revision identifying source | Stable for the same commit |
| CI job ID / build number | CI system | Identifier of **one pipeline execution** | **Yes**, even for the same commit |
| Release/deployment timestamp | Release/operations system | Time of publication or deployment | Yes; does not belong inside the artifact |
| Artifact JAR SHA-256 | File/registry/attestation | Fingerprint of artifact bytes | Matches only when bytes match |

**Example:** fixing `project.build.outputTimestamp` does not fix a generated file containing `Instant.now()`. Conversely, removing `build.time` from Spring metadata does not normalize timestamps on archive entries. You must handle both the **content layer** and the **container/archive layer**.

### Reproducibility Levels to Verify

- **Functional correctness:** two builds both run and return identical results — not yet byte reproducibility.
- **Input determinism:** same commit, same dependency versions/checksums, same JDK/toolchain and config — a necessary condition.
- **Metadata reproducibility:** free of arbitrary varying info; build-info, manifest, and generated resources are consistent.
- **Byte-for-byte reproducibility:** both JARs have **identical SHA-256** and `cmp` finds no differing bytes. This is direct evidence for that specific pair of builds, not an automatic guarantee across all machines.

## 3. How Does Spring Boot Generate `build-info.properties`?

Spring Boot supports generating:

~~~text
META-INF/build-info.properties
~~~

Standard keys typically include:

~~~properties
build.group=dev.example
build.artifact=repro-demo
build.name=repro-demo
build.version=1.0.0
build.time=2026-11-09T02:00:00Z
~~~

This is an **example containing dynamic time**, not the output of the reproducible setup below. Key order, escaping, and comments in the file are not an API contract, so in tests parse via `java.util.Properties` rather than asserting raw text order.

- Maven: goal `spring-boot:build-info` reads `MavenProject` details and generates the file at `target/classes/META-INF/build-info.properties` (default output path), which is then packaged into the executable JAR.
- Gradle: `springBoot { buildInfo() }` configures the `bootBuildInfo` task, writing `META-INF/build-info.properties` to the task's output directory. In Spring Boot Gradle Plugin 4.1, the typical output directory is `build/bootBuildInfo`; main source set resources consume this output onto the classpath/JAR. **Do not assume the file only exists at `build/resources/main` in 4.1.**
- Spring Boot Actuator can expose build metadata at `/actuator/info` when starter/endpoint/exposure are configured. Exposing metadata does not force it to carry the live build execution timestamp.
- If application code accesses `BuildProperties`, `getTime()` may be empty/null when `build.time` is omitted; handle absence gracefully instead of assuming non-null.

### Properties Appropriate to Embed in the Artifact

| Property | Good for reproducibility? | Condition |
| --- | --- | --- |
| `build.version=1.0.0` | Yes | Version stays constant across builds of identical inputs |
| `build.group` / `build.artifact` / `build.name` | Yes | Stable project configuration |
| `build.commit=<full Git SHA>` | Yes | Immutable Git revision passed as a controlled input |
| `build.channel=stable` | Yes | Channel derived from release/branch rules, not changed arbitrarily |
| `build.time=Instant.now()` | No | Value changes on every build |
| `build.job-id=CI_RUN_ID` | No | Every CI run has a new ID, even for the same commit |
| `build.hostname` / `build.workspace` | No | Depends on machine/runner |
| `build.random=UUID.randomUUID()` | No | Non-deterministic |
| `build.timestamp=commitDate` | Possibly | Uses clear, immutable commit time formatted deterministically |

**Do not label commit time as “actual build execution time.”** If you need both, record **source/commit time** as a stable provenance input and store **CI execution time** in logs, CI run records, or attestations **outside the artifact**.

## 4. Maven: Which Time Does `build.time` Use?

Per Spring Boot Maven Plugin:

- The `build-info` goal has a `time` parameter.
- If `project.build.outputTimestamp` has a value, `build.time` defaults to it.
- If `project.build.outputTimestamp` is unset, the plugin may use the Maven session start time — which changes between builds.
- To **omit `build.time` completely**, configure `<time>off</time>`. You can also exclude `time` via `excludeInfoProperties`, though `time=off` is concise, explicit, and documented by the plugin.
- To **keep `build.time` with a stable value**, set a fixed `Instant.parse(...)`-compatible timestamp and ensure both builds use it; never use the live clock.

**Distinction:** `spring-boot:build-info` is a **metadata-generation** goal, while `spring-boot:repackage` is an **executable archive packaging** goal. Neither replaces the other.

## 5. Complete Reproducibility-First Maven POM

This exercise adopts **Policy A: do not pack `build.time` into the JAR**, keeping immutable metadata `build.version` and `build.channel`, while pinning JAR entry timestamps to a stable value.

Structure:

~~~text
repro-demo/
├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/dev/example/repro/ReproDemoApplication.java
│   │   └── resources/application.properties
│   └── test/
│       └── java/dev/example/repro/BuildInfoTest.java
~~~

### 5.1. `pom.xml`

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>4.1.2</version>
        <relativePath/>
    </parent>

    <groupId>dev.example</groupId>
    <artifactId>repro-demo</artifactId>
    <version>1.0.0</version>
    <name>repro-demo</name>
    <packaging>jar</packaging>

    <properties>
        <java.version>17</java.version>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <!-- Fixed illustrative value; production should derive from source/release policy -->
        <project.build.outputTimestamp>1704067200</project.build.outputTimestamp>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
                <executions>
                    <execution>
                        <id>generate-build-info</id>
                        <goals>
                            <goal>build-info</goal>
                        </goals>
                        <configuration>
                            <time>off</time>
                            <additionalProperties>
                                <channel>stable</channel>
                            </additionalProperties>
                        </configuration>
                    </execution>
                </executions>
            </plugin>
        </plugins>
    </build>
</project>
~~~

**Explanation and technical notes:**

1. The starter parent manages dependency/plugin versions and configures the `repackage` execution. When Boot Maven Plugin is declared, executable `target/repro-demo-1.0.0.jar` is produced during `package`.
2. Execution `generate-build-info` binds the `build-info` goal to its **default lifecycle phase**; it generates `META-INF/build-info.properties` for subsequent compile/test/package steps. Do not invoke `mvn spring-boot:build-info` in isolation assuming resources are already packaged into the JAR; `mvn clean verify` is safer.
3. `<time>off</time>` ensures the generated file **omits the `build.time` key**. This changes **content**, not merely ISO timestamp formatting.
4. `<additionalProperties><channel>stable</channel></additionalProperties>` emits `build.channel=stable`; use only stable values, never a per-run CI run ID.
5. `project.build.outputTimestamp=1704067200` is **seconds since Unix epoch**, corresponding to `2024-01-01T00:00:00Z`. This is an intentional illustrative anchor, **not live current time**. Maven JAR Plugin and Spring Boot `repackage` honor it for ZIP/JAR entry timestamps.
6. If CI passes a different `project.build.outputTimestamp` value, two builds using different values still produce different archives. To reproduce **the same release**, policy must yield the exact same value whenever inputs are unchanged.
7. `java.version=17` configures Java target per parent. For higher cross-machine reproducibility, also control JDK compiler version, Maven and plugins, dependencies, and environment.

**Caution:** adding custom Maven resource filtering, manifest timestamps, or CI build numbers can still make artifacts diverge even when the POM above omits `build.time`.

## 6. Java 17 and JUnit Example Verifying build-info Has No Dynamic Time

Code objective: run Spring Boot as a command-line app, read the **actual metadata file** from the classpath, print version/channel, and confirm `build.time` is **absent**. The example opens no web server and exits after the runner finishes.

### 6.1. `src/main/resources/application.properties`

~~~properties
spring.application.name=repro-demo
spring.main.web-application-type=none
spring.main.banner-mode=off
spring.main.log-startup-info=false
logging.level.root=OFF
~~~

These settings suppress background noise. **Do not assume** the JVM or libraries will never write anything else to stderr/stdout.

### 6.2. `src/main/java/dev/example/repro/ReproDemoApplication.java`

~~~java
package dev.example.repro;

import java.io.InputStream;
import java.nio.charset.StandardCharsets;
import java.util.Properties;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class ReproDemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(ReproDemoApplication.class, args);
    }

    @Bean
    CommandLineRunner showBuildInfo() {
        return args -> {
            Properties properties = new Properties();

            try (InputStream input = getClass().getClassLoader()
                    .getResourceAsStream("META-INF/build-info.properties")) {
                if (input == null) {
                    throw new IllegalStateException("Missing build-info.properties");
                }
                properties.load(input);
            }

            System.out.println("BUILD_VERSION="
                    + properties.getProperty("build.version"));
            System.out.println("BUILD_CHANNEL="
                    + properties.getProperty("build.channel"));
            System.out.println("BUILD_TIME_PRESENT="
                    + properties.containsKey("build.time"));
        };
    }
}
~~~

This uses only Java 17 APIs. `Properties#load(InputStream)` parses Java Properties syntax; example values are all ASCII, avoiding encoding pitfalls. `InputStream` reads from the classpath, working in both exploded classes directories and executable JARs.

**Three lines printed by code with Section 5's config:**

~~~text
BUILD_VERSION=1.0.0
BUILD_CHANNEL=stable
BUILD_TIME_PRESENT=false
~~~

`BUILD_TIME_PRESENT=false` is the key criterion. If you configured `build-info` to keep a fixed timestamp instead of omitting it, this line becomes `true`; do not treat that as a failure if the policy changed intentionally.

### 6.3. `src/test/java/dev/example/repro/BuildInfoTest.java`

~~~java
package dev.example.repro;

import java.io.InputStream;
import java.util.Properties;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotNull;

class BuildInfoTest {

    @Test
    void buildInfoHasStablePropertiesAndNoBuildTime() throws Exception {
        Properties info = new Properties();

        try (InputStream input = getClass().getClassLoader()
                .getResourceAsStream("META-INF/build-info.properties")) {
            assertNotNull(input, "Build metadata missing from classpath");
            info.load(input);
        }

        assertEquals("repro-demo", info.getProperty("build.artifact"));
        assertEquals("1.0.0", info.getProperty("build.version"));
        assertEquals("stable", info.getProperty("build.channel"));
        assertFalse(info.containsKey("build.time"));
    }
}
~~~

The test reads the **resource generated during the build lifecycle**, not a hand-written file in `src/main/resources/META-INF/...`. This catches if the `build-info` goal/task is skipped, the resource is missing, the version is wrong, or `build.time` reappears.

In production projects, avoid hardcoding `1.0.0` forever if versions change frequently; supply the expected version from an independent build input so the test does not merely verify a value copied from the same faulty variable.

Inside `target/classes/META-INF/build-info.properties`, expect equivalent key/value pairs:

~~~properties

build.name=repro-demo
build.version=1.0.0
build.channel=stable
~~~

**There is no `build.time`.** Line order or comments may vary and should not be used to validate configuration correctness. Additional fixed keys do not by themselves break reproducibility, though every key's value source must be audited.

Run the artifact:

~~~bash
java -jar target/repro-demo-1.0.0.jar
~~~

Three lines printed by the application:

~~~text
BUILD_VERSION=1.0.0
BUILD_CHANNEL=stable
BUILD_TIME_PRESENT=false
~~~

Inspect the archive on Linux/macOS when `unzip` is available:

~~~bash
jar tf target/repro-demo-1.0.0.jar
unzip -p target/repro-demo-1.0.0.jar BOOT-INF/classes/META-INF/build-info.properties
~~~

**Structural note:** inside an executable Boot JAR, this resource lives at `BOOT-INF/classes/META-INF/build-info.properties`, whereas Java `ClassLoader` code loads it at logical path `META-INF/build-info.properties`. Never use `Path.of("src/main/resources/...")` to read it after packaging.

If the project does not bind the `build-info` goal, this file **is not generated by default just by having `spring-boot-starter`**. Configure the corresponding goal/task.

## 8. Maven: Separating `build.time` from JAR Entry Timestamps

Spring Boot Maven Plugin `repackage` supports the `outputTimestamp` parameter, defaulting to `project.build.outputTimestamp`. Maven JAR Plugin also honors this property. With the starter parent and supporting plugin versions, set:

~~~xml
<properties>
    <project.build.outputTimestamp>1704067200</project.build.outputTimestamp>
</properties>
~~~

The equivalent ISO 8601 form is also supported by relevant plugins:

~~~xml
<project.build.outputTimestamp>2024-01-01T00:00:00Z</project.build.outputTimestamp>
~~~

**Choose only one form** in a real POM. `1704067200` in the example is Unix seconds, **not milliseconds**; passing milliseconds uses the wrong unit.

### When Keeping `build.time` Yet Staying Reproducible

If policy requires `build.time` to always exist, replace `<time>off</time>` in the `build-info` execution with:

~~~xml
<time>${project.build.outputTimestamp}</time>
~~~

provided `project.build.outputTimestamp` is fixed. `build-info.properties` then stores `build.time` equal to the chosen anchor, remaining constant across two builds with identical inputs. **However, it no longer necessarily means “the moment CI just ran.”** Document its semantics clearly—for example, a release-source timestamp or pre-approved anchor.

Leaving `project.build.outputTimestamp` unset while letting `build-info` fall back to session time causes `build.time` to vary on every run. Never invoke a fresh `date -u` on each run for `outputTimestamp` when comparing the same commit: that just moves randomness from file metadata into a property.

### `SOURCE_DATE_EPOCH` in Practice

`SOURCE_DATE_EPOCH` is a widespread convention representing a stable source timestamp as **Unix seconds**. CI can derive the anchor from commit/release policy and **pass it explicitly** into Maven:

~~~bash
mvn clean verify -Dproject.build.outputTimestamp=1704067200
~~~

Never assume every Maven plugin automatically reads the `SOURCE_DATE_EPOCH` environment variable: **check documentation for each plugin and how CI passes the value**. Keeping packaging and resource plugins synchronized is a configuration responsibility.

## 9. Gradle: `bootBuildInfo` and Why `time` Breaks Incremental Builds

Spring Boot Gradle Plugin provides the DSL:

~~~groovy
springBoot {
    buildInfo()
}
~~~

This configures the `bootBuildInfo` task, generating `META-INF/build-info.properties`. Per Spring Boot Gradle Plugin docs, `build.time` defaults to the build execution time. Because that value shifts with the wall clock, task output changes on every run; the task **cannot be considered up-to-date**, forcing downstream tasks (resource processing, tests, packaging) to re-execute.

Spring Boot recommends excluding the `time` property when prioritizing performance and repeatability:

~~~groovy
springBoot {
    buildInfo {
        excludes = ['time']
    }
}
~~~

This keeps `build.version`, `build.group`, `build.artifact`, and `build.name`, while **omitting `build.time`**.

### Entry Timestamps and Order in Gradle Archives

Per Gradle guidelines, starting in **Gradle 9.0**, archive tasks use reproducible defaults (stable file ordering, fixed timestamps, normalized permissions). If a project still supports Gradle 8.x, configure explicitly:

~~~groovy
tasks.withType(org.gradle.api.tasks.bundling.AbstractArchiveTask).configureEach {
    preserveFileTimestamps = false
    reproducibleFileOrder = true
}
~~~

This applies to archive tasks including `jar` and `bootJar`. **It does not neutralize dynamic generated content** such as `build.time`, UUIDs, or CI run numbers. Therefore `excludes = ['time']` or an equivalent content fix is still required.

## 10. Complete Gradle Example Equivalent to Maven

Reuse the exact three Java/properties files from Section 6; use **Gradle instead of Maven** as the project's primary build tool. Create:

**`settings.gradle`**

~~~groovy
rootProject.name = 'repro-demo'
~~~

**`build.gradle` (Groovy DSL)**

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '4.1.2'
}

group = 'dev.example'
version = '1.0.0'

repositories {
    mavenCentral()
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

dependencies {
    implementation platform('org.springframework.boot:spring-boot-dependencies:4.1.2')
    testImplementation platform('org.springframework.boot:spring-boot-dependencies:4.1.2')
    implementation 'org.springframework.boot:spring-boot-starter'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}

springBoot {
    buildInfo {
        excludes = ['time']
        properties {
            additional = ['channel': 'stable']
        }
    }
}

tasks.withType(org.gradle.api.tasks.bundling.AbstractArchiveTask).configureEach {
    preserveFileTimestamps = false
    reproducibleFileOrder = true
}
~~~

**Why is each section needed?**

- `java` provides compile/test/resources tasks; `org.springframework.boot` provides `bootJar`.
- `java.toolchain` requests Java 17 for applicable Java tasks. The **Gradle runtime/daemon** JVM must still be compatible with plugin/JDK; use the project's Gradle Wrapper.
- `platform(...)` applies the BOM so Spring Boot starter versions are managed; Boot Gradle Plugin alone should not be treated as complete dependency version management.
- `springBoot.buildInfo` configures `META-INF/build-info.properties`, excluding `build.time` and adding `build.channel=stable`.
- `preserveFileTimestamps=false` and `reproducibleFileOrder=true` normalize archive entries. In Gradle 9+, these are defaults for archive tasks; explicit configuration helps if the project still runs on Gradle 8.
- `test.useJUnitPlatform` enables discovering the JUnit Jupiter test `BuildInfoTest`.

### Running and Verifying

Assuming the project has a Gradle Wrapper:

~~~bash
./gradlew clean build
java -jar build/libs/repro-demo-1.0.0.jar
jar tf build/libs/repro-demo-1.0.0.jar
~~~

**Three lines printed by the app:**

~~~text
BUILD_VERSION=1.0.0
BUILD_CHANNEL=stable
BUILD_TIME_PRESENT=false
~~~

The `bootBuildInfo` task typically writes metadata at:

~~~text
build/bootBuildInfo/META-INF/build-info.properties
~~~

in **Spring Boot Gradle Plugin 4.1.x**. Its contents are included in the main resources classpath and packaged into the executable archive at `BOOT-INF/classes/META-INF/build-info.properties`. When checking projects on other versions, do not assume every Spring Boot Gradle Plugin version uses the exact same generated output directory.

Running `./gradlew bootBuildInfo` only generates metadata, **not** a full build. `./gradlew bootJar` builds the executable without guaranteeing JUnit tests ran; run `./gradlew clean build` to execute attached verification tasks.

## 11. Proving Reproducibility via Two Clean Builds

Hash verification **only makes sense if source and inputs are held constant**. The examples below build twice **without modifying source/config/dependencies/JDK** and compare the exact same artifact:

### 11.1. Linux/macOS — Maven

From project root:

~~~bash
set -eu
CHECK_DIR="$(mktemp -d)"

mvn -q clean verify
cp target/repro-demo-1.0.0.jar "$CHECK_DIR/first.jar"

mvn -q clean verify
cp target/repro-demo-1.0.0.jar "$CHECK_DIR/second.jar"

sha256sum "$CHECK_DIR/first.jar" "$CHECK_DIR/second.jar"

if cmp -s "$CHECK_DIR/first.jar" "$CHECK_DIR/second.jar"; then
    echo "JAR_BYTES_IDENTICAL"
else
    echo "JAR_BYTES_DIFFER"
    exit 1
fi
~~~

**Final output when bytes match:**

~~~text
JAR_BYTES_IDENTICAL
~~~

`sha256sum` is standard on Linux; macOS can use `shasum -a 256`. Actual hash lines are never fabricated in advance: values depend on every artifact byte, and `cmp` directly verifies both files are identical.

**Do not delete the temp directory carelessly.** In real CI, create temp directories scoped to the job and clean up per policy. If JARs differ in bytes, retain both for inspection with `unzip`, `jar tf`, and archive diff tools; never rush to tweak timestamps before locating the differing file first.

### 11.2. Linux/macOS — Gradle

~~~bash
set -eu
CHECK_DIR="$(mktemp -d)"

./gradlew clean build
cp build/libs/repro-demo-1.0.0.jar "$CHECK_DIR/first.jar"

./gradlew clean build
cp build/libs/repro-demo-1.0.0.jar "$CHECK_DIR/second.jar"

sha256sum "$CHECK_DIR/first.jar" "$CHECK_DIR/second.jar"

if cmp -s "$CHECK_DIR/first.jar" "$CHECK_DIR/second.jar"; then
    echo "JAR_BYTES_IDENTICAL"
else
    echo "JAR_BYTES_DIFFER"
    exit 1
fi
~~~

If Gradle's local build cache restores the artifact rather than re-executing tasks under test, matching hashes **do not prove an independent fresh execution**. For strict verification, pass `--no-build-cache` and use independent runners/checkouts per policy. `clean` removes project build outputs without disabling remote/local caches.

### 11.3. Windows PowerShell

After the first build, copy the JAR to a check directory; run the second build and compare SHA-256:

~~~powershell
$checkDir = Join-Path $env:TEMP ("repro-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $checkDir | Out-Null

mvn clean verify
if ($LASTEXITCODE -ne 0) { throw "First build failed" }
Copy-Item .\target\repro-demo-1.0.0.jar (Join-Path $checkDir "first.jar")

mvn clean verify
if ($LASTEXITCODE -ne 0) { throw "Second build failed" }
Copy-Item .\target\repro-demo-1.0.0.jar (Join-Path $checkDir "second.jar")

$first = (Get-FileHash (Join-Path $checkDir "first.jar") -Algorithm SHA256).Hash
$second = (Get-FileHash (Join-Path $checkDir "second.jar") -Algorithm SHA256).Hash

if ($first -eq $second) {
    "SHA256_MATCH=true"
} else {
    throw "SHA256_MATCH=false"
}
~~~

This script targets **Maven** on Windows; for Gradle, replace both build commands with `.\gradlew.bat clean build` and the copy source with `.\build\libs\repro-demo-1.0.0.jar`. `Get-FileHash` computes checksums and `$LASTEXITCODE` checks build success.

### 11.4. Analyzing When Hashes Differ

1. Compare `META-INF/build-info.properties` in both JARs, especially `build.time` and custom keys.
2. Compare `META-INF/MANIFEST.MF` (build numbers, hostnames, timestamps, classpath entries).
3. Inspect ZIP/JAR entry timestamps and entry ordering with ZIP tooling.
4. Compare generated resource files, annotation processor outputs, embedded Git metadata, or resource-filtered `application.properties`.
5. Check source commit, git dirty state, JDK/compiler version, Maven/Gradle/plugin versions, dependency resolution, and network inputs.
6. Check locale/timezone, paths, file permissions, and OS if built on different hosts.
7. If needed, run a tool like `diffoscope` to diff binary archives; **never guess a root cause solely from a hash mismatch**.

**Note:** matching hashes on one runner do not prove reproducibility across Windows/Linux or across JDK vendors/versions. It is a QA checkpoint, not universal proof for every environment.

## 12. Which Metadata Belongs Inside vs. Outside the Artifact?

| Metadata | Recommended source | Where to store |
| --- | --- | --- |
| App version | Release POM/Gradle version | Inside the artifact |
| Group/artifact/name | Stable project configuration | Inside the artifact |
| Commit SHA | Fixed Git revision of source | Inside the artifact or external provenance |
| Commit timestamp | Commit timestamp with clear semantics | Can be a stable input; avoid calling it actual build time |
| Dependency versions/checksums | Lockfiles/SBOM | SBOM, lock, provenance |
| CI run ID/job URL | CI pipeline | CI record or attestation **outside the JAR** |
| Build wall-clock time | CI host/runner | CI logs, artifact registry event, provenance **outside the JAR** |
| Deployment timestamp | Deployment system | Release management/deployment records |
| Machine hostname/workspace | Runner | Avoid embedding; generally should not be published |
| Secrets/tokens | Secret manager | **Never embed into build-info.properties** |

### Build Provenance Satisfies Audit Needs

Removing `build.time` **does not mean losing traceability**. A release pipeline can record:

~~~text
artifact:
  name: repro-demo-1.0.0.jar
  sha256: <computed from the artifact itself>
source:
  git_commit: <full SHA>
toolchain:
  java: <JDK version>
  maven_or_gradle: <version>
execution:
  ci_run_id: <run identifier>
  started_at: <actual UTC timestamp>
~~~

This is an **illustrative field schema**, not a generated file or a complete standard attestation format. CI can emit this as a provenance attestation linked by artifact digest. Thus two rebuilds of the same source still yield **byte-identical JARs**, while every CI execution keeps its own distinct execution record.

### When Commit Hash Is Needed Inside the JAR

If version or commit must be exposed at runtime, use the immutable value from the **checked-out commit itself**, never `CI_PIPELINE_ID` or current time. Ensure CI supplies the exact same Git SHA across two builds of the same commit.

**Never generate a random UUID as a build ID inside packaged resources** when reproducibility is a goal. Identify artifacts via hash or `version + commit` without generating random numbers on every build.

## 13. Other Risks Beyond `build.time`

### 13.1. Snapshots and Dynamic Dependencies

Using `1.2.+`, `latest.release`, or unlocked SNAPSHOTs can resolve different bytes whenever repositories change. Even with `build.time` omitted and archive timestamps pinned, builds with different dependencies will differ.

**Mitigation:** pin versions, use dependency locking/verification, enforce repository policies, and store resolved dependency graphs alongside toolchains.

### 13.2. Changing Build Plugins / Java Vendors

Sharing Java release target `17` does not guarantee identical bytecode across all JDK patches/vendors. Maven/Gradle, annotation processors, compiler flags, and plugin versions are also build inputs.

**Mitigation:** use Maven/Gradle Wrappers where available, manage JDK toolchains/CI images, and pin plugin versions. Verify outputs in independent reproducible environments.

### 13.3. Generated Sources and Environment Leakage

Files emitted using `new Date()`, `System.currentTimeMillis()`, `Instant.now()`, `UUID.randomUUID()`, build numbers, hostnames, absolute paths, or unstable file ordering still cause JARs to differ. Annotation processors can also emit timestamps/comments.

**Mitigation:** avoid wall-clock reads in generated files; enforce deterministic ordering, pass immutable inputs, and audit custom tasks/plugins.

### 13.4. Docker Images and JARs Are Different Artifacts

Even when a JAR is byte-identical, a container image can differ in creation-time metadata, layer ordering, base image digest, or file ownership. A passing `docker build` does not prove the **image** is reproducible.

**Mitigation:** evaluate reproducibility separately at the JAR level and image level, pin base image digests when needed, record provenance, and compare digests of the exact target deliverable.

### 13.5. Reproducibility Differs from Security

Two builds with matching hashes do not guarantee freedom from vulnerabilities, malicious dependencies, or valid source licensing. Reproducibility evidences **process consistency**, and must accompany vulnerability scanning, SBOMs, code reviews, and provenance verification.

## 14. Common Issues and Fixes Table

| Symptom | Likely hypothesis | Check and fix |
| --- | --- | --- |
| Two JARs have different hashes, `build.time` differs | `build-info` used live clock | Maven `<time>off</time>`; Gradle `excludes=['time']` |
| Maven sets `outputTimestamp`, yet metadata still differs | Custom resources/manifest used another clock, or property overridden | Compare `build-info.properties`, effective POM, and CI args |
| Maven `build.time` still present despite trying to omit it | `build-info` execution missed the config | Check Maven goal/execution, exact `time` tag, and generated file |
| Gradle `bootBuildInfo` always re-runs | Default `build.time` reads wall clock | Exclude `time`; inspect task inputs/outputs |
| Gradle `bootJar` differs even with matching `build-info` | Archive timestamps/order, dependencies, generated files | Check `preserveFileTimestamps`, `reproducibleFileOrder`, and resolved graph |
| JAR timestamps differ, yet resource contents match | ZIP entry metadata unnormalized | Maven `outputTimestamp` / Gradle archive settings |
| `BuildProperties.getTime()` returns null | `build.time` was intentionally omitted | Handle optionality in code; do not assume time always exists |
| `META-INF/build-info.properties` missing | Goal/task unbound or output unpackaged | Check Maven `build-info`, Gradle `bootBuildInfo`, and classpath |
| Runtime still prints old timestamp after rebuild | Running stale artifact or stale incremental output | Verify which JAR is executing, run intentional clean build, check classpath |
| Version or commit differs for same source | CI overrode property or checked out different commit/tag | Compare exact inputs, Git SHA, and release policy |
| Same-runner builds match hashes, another host does not | Differing toolchain/OS/locale/permissions | Pin toolchain/environment and verify cross-runner |
| Build cache makes hash checks always match | Both runs restored the same cached artifact | Use clean runners or disable cache when verifying real rebuilds |
| `build-info.properties` embeds hostname/run ID | Custom `additionalProperties` captured dynamic env | Move execution metadata to external provenance outside JAR |
| CI audit lacks execution time after omitting `build.time` | Timestamp was previously stored only inside artifact | Write CI run records and link digests to provenance |
| Test comparing raw text fails due to key order | Java `Properties` does not guarantee key ordering | Parse with `Properties`; assert key/values and key absence |
| Tests pass, yet executable JAR wasn't checked | Tests read `target/classes` or Gradle generated output | Run `jar tf`, `unzip -p`, `java -jar`, and compare artifact hashes |

**Diagnostic sequence:** (1) inspect the generated file → (2) inspect the file inside the packaged JAR → (3) inspect ZIP entry metadata → (4) compare dependency graphs/toolchains → (5) compare two independent clean builds. Fix the **first point introducing divergence** rather than changing every setting at once.

## 15. Pipeline Rollout Checklist

- [ ] Define whether the goal is **functional equivalence** or **byte-for-byte identical JARs**.
- [ ] Pin source commit, dependency graph, plugins, and toolchain versions.
- [ ] Maven: `build-info` goal generates metadata; `<time>off</time>` if prioritizing reproducibility.
- [ ] Maven: set `project.build.outputTimestamp` from a **stable** source, not each CI run's wall clock.
- [ ] Gradle: `springBoot.buildInfo { excludes = ['time'] }`.
- [ ] Gradle: archive tasks set `preserveFileTimestamps=false`, `reproducibleFileOrder=true` (especially pre-Gradle 9).
- [ ] Never embed run IDs, random UUIDs, hostnames, workspace paths, or live timestamps into manifests/resources.
- [ ] Use commit SHA/version as stable metadata when properly governed.
- [ ] Store CI build time, job ID, and provenance **outside the JAR**, linked to its digest.
- [ ] Unit tests confirm `build-info.properties` has expected keys and **no `build.time`** per policy.
- [ ] Inspect generated files and the `BOOT-INF/classes/META-INF/build-info.properties` entry inside the JAR.
- [ ] Run the application and verify expected runtime output.
- [ ] Execute **two clean builds** with fixed inputs; compare SHA-256 and bytes of the exact JAR.
- [ ] On hash mismatch, use diff/ZIP inspection to find the varying file or metadata.
- [ ] Ensure Gradle build cache, Maven local repo, and network inputs do not mask reproducibility checks.
- [ ] Never conflate JAR reproducibility with container image reproducibility.

**Remember:** **`build.time` is file content; `outputTimestamp` and Gradle archive options control ZIP/JAR metadata.** If two builds from the same source must yield identical digests, handle both and move **single-CI-run** metadata outside the artifact.

## 16. Self-Check Questions

**Question 1.** You set a fixed `project.build.outputTimestamp` while keeping a generated file containing `Instant.now()`. Is the JAR guaranteed reproducible?

**Answer:** No. ZIP timestamps are fixed, yet the generated file has dynamic contents, causing archive bytes to differ.

**Question 2.** Where does Maven `spring-boot:build-info` get `build.time` when `project.build.outputTimestamp` is unset?

**Answer:** Typically from the Maven session start time per plugin behavior; the value can differ between two builds.

**Question 3.** How do you turn off `build.time` in Maven without disabling build info entirely?

**Answer:** In the `build-info` goal configuration, set `<time>off</time>`. Keys like `build.version` are still generated.

**Question 4.** How do you omit `build.time` from Gradle `bootBuildInfo`?

**Answer:** `springBoot { buildInfo { excludes = ['time'] } }`.

**Question 5.** Why does `build-info` time hurt Gradle incremental build efficiency?

**Answer:** A value tracking the wall clock changes the task output every run; dependent tasks cannot remain up-to-date.

**Question 6.** What unit is `project.build.outputTimestamp=1704067200`?

**Answer:** **Seconds since the Unix epoch**, equal to `2024-01-01T00:00:00Z`; not milliseconds.

**Question 7.** How do you preserve the real release timestamp without changing JAR checksums?

**Answer:** Record the release/CI run timestamp in external provenance/registry/logs linked to the artifact digest instead of embedding it inside the JAR.

**Question 8.** Do two JARs with matching hashes on one machine prove reproducibility on every machine?

**Answer:** Not yet. Test in independent environments/runners, pin JDK/plugins/dependencies, and audit OS-dependent inputs.

**Question 9.** Does adding `build.commit` break reproducibility?

**Answer:** No, if it is an immutable Git revision identical for the same source. It can break reproducibility if derived from a mutable value like a build number or uncontrolled dirty working-tree metadata.

**Question 10.** Why shouldn't tests assert raw text line order of `java.util.Properties`?

**Answer:** Key output order is not a stable API contract; tests should parse key/values and assert required/prohibited properties.
