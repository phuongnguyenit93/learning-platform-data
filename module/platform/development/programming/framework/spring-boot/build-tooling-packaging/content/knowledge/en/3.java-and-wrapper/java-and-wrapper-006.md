# Managing Wrapper Versions, Distribution URLs, and Checksums

## Goal and Context

Within the **Java and Wrapper** topic of Spring Boot Build Tooling Packaging, the `Wrapper` is a set of scripts and configuration that lets both developers and CI run the **exact build tool version chosen by the project**. With Maven, we typically invoke `./mvnw`; with Gradle, `./gradlew`. This lesson focuses on three items that must be managed in sync: **version**, **distribution URL**, and **SHA-256 checksum**.

After this lesson, you should be able to identify which Maven/Gradle version actually runs, read `distributionUrl` and `distributionSha256Sum`, understand the difference between the build tool ZIP and the Wrapper JAR, change versions in a verifiable way, and diagnose download/checksum failures without confusing them with Java or Spring Boot errors.

**Core point:** The Wrapper manages the **Maven/Gradle** version; `pom.xml` or `build.gradle[.kts]` manages the build; the Java toolchain/JDK manages Java; the Spring Boot parent/plugin manages the Spring Boot version. These four versions relate through compatibility, but they are not one single value.

## 1. How the Wrapper Works: From Script to Distribution

```text
Developer / CI
    |
    +---- ./mvnw or mvnw.cmd
    |              |
    |              +--> .mvn/wrapper/maven-wrapper.properties
    |                         |
    |                         +--> distributionUrl (Maven ZIP)
    |                         +--> distributionSha256Sum (ZIP SHA-256)
    |
    +---- ./gradlew or gradlew.bat
                   |
                   +--> gradle/wrapper/gradle-wrapper.properties
                              |
                              +--> distributionUrl (Gradle ZIP)
                              +--> distributionSha256Sum (ZIP SHA-256)
```

The Wrapper script locates an already-downloaded build tool distribution or downloads it from `distributionUrl` when needed. When checksum verification is enabled/supported, it compares the pinned SHA-256 value against the bytes of the newly downloaded ZIP. Only after preparing the tool does Maven/Gradle perform tasks such as reading dependencies, running tests, compiling, and packaging Spring Boot.

This reduces drift such as **machine A using Maven 3.x while machine B uses a different Maven version**, or **CI using a different Gradle version than a developer machine**. However, the Wrapper **does not install a suitable JDK**, does not make Spring Boot compatible with every Gradle/Maven release, and does not verify all application dependencies.

### Related Files

| Maven Wrapper | Gradle Wrapper | Role |
| --- | --- | --- |
| `mvnw`, `mvnw.cmd` | `gradlew`, `gradlew.bat` | Wrapper launch scripts on Unix/macOS and Windows |
| `.mvn/wrapper/maven-wrapper.properties` | `gradle/wrapper/gradle-wrapper.properties` | URL, checksum, and distribution details |
| `.mvn/wrapper/maven-wrapper.jar`, if present | `gradle/wrapper/gradle-wrapper.jar` | Wrapper program; Maven `only-script` may omit the JAR |
| `pom.xml` | `build.gradle` / `build.gradle.kts` | Declares plugins, dependencies, and build configuration |

Commit the standard Wrapper files to Git so others run the exact same version. Do not commit download cache directories such as `~/.gradle/wrapper/dists` or `~/.m2/wrapper/dists`. Committed JARs and scripts are executable code, so changes to them must be reviewed.

## 2. `distributionUrl` Is Where the Tool Version Is Pinned

`distributionUrl` points to a **specific Maven/Gradle distribution ZIP**. Read all three parts: **host**, **version**, and **ZIP type**.

Maven example:

```properties
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.11/apache-maven-3.9.11-bin.zip
```

This is the ZIP for **Maven 3.9.11** from the official Maven Central host. The version appears in both the path segment and the ZIP filename. This is a **fixed illustrative version**, not a directive to upgrade every project to 3.9.11.

Gradle example:

```properties
distributionUrl=https\://services.gradle.org/distributions/gradle-8.14.3-bin.zip
```

This is the ZIP for **Gradle 8.14.3** of type `bin`. Gradle also has an `-all.zip` type adding sources and documentation; **the `bin` ZIP and `all` ZIP differ** even for the same version, so their checksums are not interchangeable. The `\://` sequence is standard colon escaping in Java properties files generated by Gradle.

**URL reading rules:** use HTTPS, a pinned version, and a concrete ZIP filename; verify the official domain or an organization-controlled mirror. A URL containing `latest`, a frequently changing SNAPSHOT, or an unverified host weakens reproducibility and verification. Internal mirrors must be verified to ensure uploaded artifacts match official releases. HTTPS protects the transport channel, not the content checksum.

### Why Can't You Change Only the Version String?

For example, switching `gradle-8.14.3-bin.zip` to `gradle-8.14.3-all.zip` while keeping the old checksum causes verification to fail when the `all` archive is freshly downloaded. Switching Maven `3.9.11` to another version is the same: **both the URL and the new ZIP's checksum** must be updated together.

Bumping the Spring Boot version in the POM/build script **does not mean** the Wrapper automatically upgrades Maven/Gradle. Conversely, upgrading Gradle/Maven may require updating the JDK, plugins, or build scripts for compatibility.

## 3. SHA-256 and `distributionSha256Sum`

SHA-256 is a hash function producing a **64-character hex string** from a file's bytes. Two ZIPs with different contents almost certainly produce different digests. `distributionSha256Sum` is the expected checksum for **the entire ZIP at `distributionUrl`**, not for the extracted folder, `build.gradle`, `pom.xml`, or Java dependencies.

```text
distributionUrl --> download specific ZIP ----> SHA-256(downloaded ZIP)
                                                       |
distributionSha256Sum -----------------------------> compare
                                                       |
                                  match: continue / mismatch: abort untrusted ZIP
```

A checksum is only useful when obtained from a **trusted source independent of the download being checked**: an official release page, verified checksum/signature files, or a vetted internal artifact repository. Never download a file from an untrusted host, compute SHA-256 on that very file, and pin it into properties: that only confirms it hasn't changed relative to the suspect file.

**Know the limit:** a checksum protects the integrity of the pinned ZIP; it does not guarantee absolute security of the tool's source code, validate application correctness, or replace code/build-script review.

### Where to Get Checksums?

- **Gradle:** https://gradle.org/release-checksums/ publishes the SHA-256 for each `-bin`/`-all` ZIP as well as the Gradle Wrapper JAR. Make sure you select the **exact version and ZIP type**.
- **Maven:** check Apache Maven's official release/signature or checksum info; Maven Wrapper documentation supports `distributionSha256Sum`. Some Apache release sources prioritize SHA-512: verify the artifact using the release checksum/signature first, then **compute the SHA-256 of the verified ZIP yourself** to pin it in the Wrapper.
- For an internal mirror, cross-check the mirrored artifact against upstream via a trusted workflow **before** letting other machines download it.

Never paste a SHA-512 string (128 hex characters) into a SHA-256 field (64 hex characters); and never include a `sha256:` prefix or trailing filename in properties.

## 4. Maven Wrapper: Maven Version and Wrapper Version Are Two Different Things

An illustrative **`script`-type** Maven Wrapper configuration showing the full URL–checksum pairs:

```properties
# .mvn/wrapper/maven-wrapper.properties
wrapperVersion=3.3.4
distributionType=script
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.11/apache-maven-3.9.11-bin.zip
distributionSha256Sum=0d7125e8c91097b36edb990ea5934e6c68b4440eef4ea96510a0f6815e7eeadb
wrapperUrl=https://repo.maven.apache.org/maven2/org/apache/maven/wrapper/maven-wrapper/3.3.4/maven-wrapper-3.3.4.jar
wrapperSha256Sum=4e2fbf6554bc8a4702cdfdd3bef464f423393d784ddbb037216320ce55d5e4e1
```

The specific SHA-256 values here correspond to **Maven 3.9.11 ZIP** and **Maven Wrapper JAR 3.3.4**. They are valid only for those exact two artifacts; never reuse them for other versions. In a real project, the wrapper type may differ and this file might contain only a few properties.

| Property | Purpose |
| --- | --- |
| `distributionUrl` | Selects the ZIP and **actual Maven version to run** |
| `distributionSha256Sum` | Expected SHA-256 of the **Maven ZIP** |
| `wrapperVersion` | Version of the **Maven Wrapper** software, not Maven itself |
| `distributionType` | Wrapper execution mode: `only-script`, `script`, `bin`, `source` |
| `wrapperUrl` | URL to download `maven-wrapper.jar` when the wrapper type uses a JAR |
| `wrapperSha256Sum` | Expected SHA-256 of the **downloaded Maven Wrapper JAR** |

**What sets `only-script` apart:** this is the default in many modern Maven Wrapper versions. The script handles downloading Maven directly without requiring `maven-wrapper.jar`. Thus an absent JAR can be completely normal; `wrapperSha256Sum` has no JAR verification meaning when the wrapper type does not use a JAR. Do not switch types just to force a JAR to exist.

Conversely, in types that download a JAR such as `script`, `wrapperUrl` and `wrapperSha256Sum` can protect the **downloaded Wrapper JAR**. That checksum is **separate** from `distributionSha256Sum`, which protects the Maven ZIP. If the JAR is already committed in Git, verify its integrity against the trusted release source rather than relying solely on properties lines.

### Upgrading the Maven Version Used by the Wrapper

According to Apache Maven Wrapper documentation, in a **trusted environment with Maven installed**, you can set/change the tool version via the plugin:

```bash
mvn -N wrapper:wrapper -Dmaven=3.9.11
```

This is an illustrative command with **target version 3.9.11**, not a requirement to use this version. If the project has custom Wrapper settings, the task/plugin may rewrite scripts and properties differently from this example. Afterward, inspect the diff of `mvnw`, `mvnw.cmd`, and `.mvn/wrapper/`, update the official checksum for the **target Maven ZIP**, and—if the Wrapper JAR changed—the matching checksum for the target JAR. Apache also permits editing `distributionUrl` to switch Maven versions, but you must update the URL–checksum pair together.

Do not confuse `-Dmaven` with `wrapperVersion`: the first selects the **Maven** version; the second refers to the **Maven Wrapper**.

## 5. Gradle Wrapper: Version, ZIP Checksum, and Cache Location

Example Gradle Wrapper file configured for **Gradle 8.14.3 `bin`**:

```properties
# gradle/wrapper/gradle-wrapper.properties
distributionBase=GRADLE_USER_HOME
distributionPath=wrapper/dists
distributionUrl=https\://services.gradle.org/distributions/gradle-8.14.3-bin.zip
distributionSha256Sum=bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists
```

The digest `bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531` matches the checksum **published by Gradle for `gradle-8.14.3-bin.zip`**. Verification URL: https://gradle.org/release-checksums/. For the `all` ZIP of the same version, the digest is a **different** value.

| Gradle Property | Meaning |
| --- | --- |
| `distributionUrl` | Host, Gradle version, ZIP name/type |
| `distributionSha256Sum` | SHA-256 of the ZIP when freshly downloaded and verified |
| `distributionBase`, `distributionPath` | Where the extracted Gradle distribution is stored |
| `zipStoreBase`, `zipStorePath` | Where the downloaded ZIP is stored |
| `networkTimeout` (if present) | Connection timeout when the Wrapper downloads |

`GRADLE_USER_HOME` and `wrapper/dists` are **cache path settings**, not versions or URLs. `gradle/wrapper/gradle-wrapper.jar` is the Wrapper program executed before downloading the ZIP; this JAR's checksum is **not verified by `distributionSha256Sum`**.

### Upgrading Gradle via the `wrapper` Task

Once the current checkout/Wrapper is verified and the project supports the target Gradle version, an example update syntax is:

```bash
./gradlew wrapper --gradle-version 8.14.3 --distribution-type bin --gradle-distribution-sha256-sum bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531
```

In Windows PowerShell, use `.\gradlew.bat wrapper` with the same trailing flags. This is an **invocation example**, not a claim that 8.14.3 suits every project. When changing versions, if Gradle sees an old `distributionSha256Sum` and the task isn't given the new digest, the `wrapper` task may refuse to run; do not delete the checksum to bypass the error.

After updating properties during an upgrade, Gradle recommends **running the `wrapper` task a second time with the new Gradle version** so `gradle-wrapper.jar` and the scripts are fully updated if needed. Inspect the diff of `gradle-wrapper.properties`, `gradle-wrapper.jar`, `gradlew`, and `gradlew.bat`; verify the Wrapper JAR SHA-256 against the official list, check `--version`, and run a build before committing.

A bad practice is editing only `distributionUrl` in the file and assuming all Wrapper files are updated. The URL controls which Gradle version gets downloaded; the Wrapper JAR and scripts belong to another layer and may need updating separately during an upgrade.

## 6. Two Things Must Be Checked: the Tool ZIP and the Wrapper Program

Clearly separate two protection targets:

**A. Build tool distribution (ZIP).** `distributionSha256Sum` detects when a downloaded ZIP does not match the expected bytes. An official URL with a wrong checksum is still an error; a valid checksum for a different ZIP is still an error.

**B. Bootstrap loader/launcher (Wrapper JAR and scripts).** The Gradle JAR is usually committed and executes *before* checking the ZIP checksum; compare the JAR's SHA-256 against official release lists or use a Wrapper JAR validation step in CI. With Maven, `wrapperSha256Sum` covers the Wrapper JAR in applicable types; `only-script` has no JAR to check, though the scripts themselves still require review. A malicious actor could alter both the URL and checksum in the same PR; therefore **code review and independent checksum sources** remain essential.

### Cache Limitations

Gradle documentation explicitly states that `distributionSha256Sum` is checked when the Wrapper needs to **download a new distribution**. If that Gradle distribution already exists validly in cache, subsequent runs may skip downloading and not recompute the ZIP checksum. Thus running `./gradlew --version` successfully right after editing the checksum **does not prove** the checksum was just re-verified. To verify the download/checksum path, test in a fresh environment or an isolated cache directory rather than wiping teammates' shared caches.

Maven Wrapper also has multiple types and implementation versions; exact verification behavior depends on the type in use. Do not assume every older Maven Wrapper script handles checksums identically.

### Computing and Comparing a ZIP Checksum Yourself

After obtaining the exact `gradle-8.14.3-bin.zip` from a trusted source, compute its SHA-256 with:

```bash
# Linux
sha256sum gradle-8.14.3-bin.zip

# macOS
shasum -a 256 gradle-8.14.3-bin.zip
```

```powershell
# Windows PowerShell
(Get-FileHash .\gradle-8.14.3-bin.zip -Algorithm SHA256).Hash.ToLowerInvariant()
```

The SHA-256 result for the exact Gradle ZIP in the example must be:

```text
bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531
```

Compare **all 64 characters**, not just the first few digits. For a Maven ZIP, the hash command is the same—just pass the exact filename. If Apache provides SHA-512, verify/cross-check it per Apache's release instructions before computing SHA-256 yourself to pin; never replace the digest with the hash of a suspicious freshly downloaded file.

## 7. End-to-End Change Management Workflow

1. **Read current settings.** Note `distributionUrl`, `distributionSha256Sum`, wrapper type, and JAR/script files; run `./mvnw -v` or `./gradlew --version` on a trusted checkout to see the current tool version.
2. **Choose the target version and check compatibility.** Spring Boot/plugins, the JDK used by Gradle/Maven, tasks, and CI may impose separate requirements. Do not upgrade just because a newer release exists.
3. **Locate the official release.** Pick a fixed-version ZIP (`bin`/`all` as needed); decide between the official URL or a vetted internal mirror.
4. **Find the independent checksum of that exact ZIP.** For Gradle, use the official release checksums page; for Maven, use Apache's release info/signatures/checksums and the corresponding wrapper mechanism.
5. **Update the Wrapper using trusted tooling.** For Maven, use the Maven Wrapper Plugin or edit the URL per official docs; for Gradle, run the `wrapper` task with the verified version and SHA-256. Update the JAR checksum separately if the Wrapper JAR changed.
6. **Review every change in Git.** Check the exact URL, digest, JAR/script versions, hostname, and generated files; review the scripts too because they execute before the build.
7. **Verify from a fresh environment or isolated cache.** Test downloading + SHA-256 verification, then run `-v`/`--version` to confirm the actual tool version.
8. **Run a test and build command.** For Maven: `./mvnw test`, `./mvnw package`; for Gradle: `./gradlew test`, `./gradlew build`. Run the commands matching the repo's build system—you do not need both.
9. **Document the change clearly in the commit/PR.** State old → new version, URL, checksum source, rationale, tests run, and details of any changed wrapper JAR/scripts. CI must use the repo's Wrapper to honor the pinned version.

Quick commands for a Maven or Gradle project:

```bash
# Run from the root of a trusted Maven project
./mvnw -v
./mvnw test

# Or, if this is a Gradle project
./gradlew --version
./gradlew test
```

In Windows PowerShell, substitute `.\mvnw.cmd -v` / `.\mvnw.cmd test` or `.\gradlew.bat --version` / `.\gradlew.bat test`. If a Unix shell reports `Permission denied` due to missing execute permission on a trusted script, check the executable bit before changing anything.

## 8. Diagnosing Common Problems

| Symptom | Check | Action |
| --- | --- | --- |
| `distributionSha256Sum` mismatch | Did the version or ZIP type change? Did a mirror serve the right file? Is the digest from the official source? | Stop using that ZIP, re-verify URL and digest from the official source; never pin the hash of a suspect file. |
| HTTP 404 when Wrapper downloads | Path/version ZIP does not exist, or mirror is out of sync | Confirm the official release URL and valid version. |
| TLS/certificate/proxy error | Network settings, JDK/machine trust store, corporate proxy | Fix connectivity/certificates properly; never disable TLS verification. |
| `gradlew --version` still works right after setting a bad checksum | The Gradle distribution is already in cache | Use a fresh environment/isolated cache to prove downloading and SHA-256 checking run. |
| Maven lacks `maven-wrapper.jar` | `distributionType=only-script` may intentionally omit the JAR | Read `distributionType`; do not assume a missing file. |
| Gradle Wrapper JAR changed unexpectedly | JAR may have been modified or generated by another version | Compare the JAR hash against https://gradle.org/release-checksums/ and inspect the diff and rationale. |
| `./mvnw -v` differs from `mvn -v` | Wrapper and global Maven are two independent choices | Check `distributionUrl`; use the project's Wrapper. |
| `./gradlew --version` differs from `gradle --version` | Wrapper and global Gradle have different versions | Use the Wrapper to avoid machine environment drift. |
| Build fails on "Java version" even though checksum passes | Java/JDK, Gradle/Maven version, plugins, or Spring Boot are incompatible | Check `java -version`, the JDK picked by IDE/CI, and compatibility matrices. |
| Test/build fails after Wrapper downloads cleanly | Dependency, plugin, application config, or code error | Classify the post-download build error; do not blame the checksum. |

### Reading a Diff to Spot Mistakes

```diff
-distributionUrl=https\://services.gradle.org/distributions/gradle-8.14.3-bin.zip
+distributionUrl=https\://services.gradle.org/distributions/gradle-8.14.3-all.zip
 distributionSha256Sum=bd71102213493060956ec229d946beee57158dbd89d0e62b91bca0fa2c5f3531
```

The untouched checksum line **belongs to `bin.zip`**, whereas the new URL is `all.zip`: you must fetch the official checksum for `all.zip` (or revert to `bin.zip` if switching types wasn't intended). Changing only the URL while keeping the old checksum does not produce a valid Wrapper update.

Even if an unfamiliar URL and a new checksum match the file at that URL, you still must verify the distribution source and the reason for changing hosts. A mathematically valid digest **does not prove by itself** that the artifact came from the official publisher.

## 9. Verification Practice

Take a Spring Boot project generated by Spring Initializr, choose **Maven or Gradle**, and complete these steps:

1. Locate the exact `*wrapper.properties` path and list all Wrapper scripts/JARs in the repo. Identify the tool version from `distributionUrl`.
2. Break down the URL into host, version, filename, and ZIP type. Distinguish this tool version from the project's Java and Spring Boot versions.
3. Check whether `distributionSha256Sum` is present. If missing, find the checksum for that exact ZIP from a trusted release source—**never make up 64 hex characters**.
4. For Maven, identify `distributionType` and see where `wrapperSha256Sum` applies. For Gradle, explain why the ZIP checksum does not verify `gradle-wrapper.jar`.
5. Run `./mvnw -v` or `./gradlew --version` from a trusted checkout; record the exact tool version and JDK used.
6. On a practice branch, pick a **compatible** target version, update the URL and checksum as a pair, inspect the Wrapper diff, test with an isolated cache, and run `test` and `build`.
7. Explain in your own words: why does caching mean checksum verification doesn't necessarily run on every invocation, and why does a checksum supplied by the same person who changed the URL still require independent review?

**Completion criteria:** state the exact running tool version, ZIP URL, and matching SHA-256; show evidence of how the digest was chosen/verified; and clearly separate ZIP checksums from JAR/script checks and post-download build errors.
