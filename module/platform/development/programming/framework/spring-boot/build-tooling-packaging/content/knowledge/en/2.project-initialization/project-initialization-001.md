# Creating a Spring Boot Project with Spring Initializr: Choosing Java, Spring Boot Version, and Build Tool

## 1. Lesson Objectives

After this lesson, you will be able to create a Spring Boot project yourself from https://start.spring.io, explain each important option on the initialization screen, choose a compatible trio of **Java version – Spring Boot version – build tool**, open the project in an IDE, run a quick test, and identify the causes of initial configuration errors.

**Spring Initializr** is a project scaffolding generator. It pre-creates the directory structure, Spring Boot startup class, configuration file, dependency declarations, and build tool Wrapper scripts. Initializr does **not** install the JDK for you, set up the runtime environment, design business logic, or test compatibility for all external libraries.

Three choices that are easily confused:

| Choice | What does it decide? | Example |
| --- | --- | --- |
| **Language** | Application source language: Java, Kotlin, or Groovy | Choose **Java** so source files are `.java` |
| **Java** | Java version level of the project: bytecode/API and compiler configuration generated by the build tool | Choose **21**, use a suitable JDK to build/run |
| **Spring Boot** | Framework release line and corresponding ecosystem of dependencies/plugins | Choose a **stable/GA** release compatible with requirements |
| **Project** | Dependency management and build lifecycle system | **Maven**, **Gradle – Groovy**, or **Gradle – Kotlin** |

Do not confuse the **Java** field (version) with **Language = Java** (language), and do not confuse **Spring Boot version** with **JDK version**.

## 2. Choosing the Right Java and Spring Boot Versions

### 2.1. Distinguishing Between the JDK, Project Java Level, and Running JVM

- The **JDK** is the toolkit containing `javac`, the Java runtime, and development tools. A JDK is required to compile the project.
- **Java** in Initializr lets the scaffold generate the corresponding language-level/toolchain configuration. Selecting Java 21 does not automatically install JDK 21 on your machine.
- The **JDK used by Maven/Gradle** can differ from the JDK shown in the IDE or by the `java -version` command. With Gradle, the toolchain used for compilation can also differ from the JVM running Gradle.

Check before creating/running the project:

~~~bash
java -version
javac -version
~~~

In the IDE, check both **Project SDK/JDK** and **Gradle JVM** or **Maven Runner JRE**. On a machine with multiple JDKs, check `JAVA_HOME` and which `java`/`javac` path is actually invoked.

### 2.2. Checking Compatibility Before Clicking Generate

The **Spring Boot 3.x and 4.x release lines require Java 17 minimum**; Java 21 or 25 are LTS options worth considering if your system, plugins, and libraries support them. Spring Boot 4.x uses Spring Framework 7 and a newer Jakarta EE baseline than the 3.x line, so choosing the framework line also depends on your libraries and deployment environment. Do not assume an older project will upgrade to Boot 4 without checking.

For Spring Boot 4.x, the official documentation states support for Maven 3.6.3+ and Gradle 8.14+ (8.x branch) or 9.x. Limits may change in other branches/releases: **check the system requirements for the exact Boot version before combining a JDK and Gradle**. An older Gradle version may fail to run on a newer JDK, even if Spring Boot itself can run on that JDK.

When selecting Spring Boot in Initializr:

1. Prioritize a **stable (GA/release)** version that is supported and fits project requirements.
2. **SNAPSHOT**, **M** (milestone), or **RC** versions are meant for testing upcoming features and are usually not the starting choice for typical projects.
3. Check compatibility with Java, Spring Cloud (if used), starters, and your system's libraries. Do not pick a version solely because it has the highest number.
4. If the project belongs to an existing codebase/team, use the version line approved by the team; keep development, CI, and production environments synchronized.

**Rule of thumb:** Spring Initializr generates a scaffold with the versions selectable at the time of access, but you still need to confirm that the build machine, JDK, plugins, and dependencies are actually compatible.

## 3. Choosing Maven or Gradle

Maven and Gradle can both download libraries, compile, run tests, package, and produce a runnable Spring Boot application. **Choose only one** build system for a new project, unless there is a specific requirement to maintain multiple builds.

| Criterion | Maven | Gradle |
| --- | --- | --- |
| Primary build file | `pom.xml` (XML) | `build.gradle` (Groovy DSL) or `build.gradle.kts` (Kotlin DSL) |
| Organization style | Fairly clear convention-based build lifecycle, declarative configuration | Flexible task graph, DSL allows diverse configuration/extensions |
| Starting out for learners | Easy to look up XML structure and standard commands | Suitable when wanting to learn Gradle, Kotlin DSL/Groovy, or when the team project already uses it |
| Running Spring Boot | `spring-boot:run` | `bootRun` |
| Packaging executable JAR | `package` with the Spring Boot Maven plugin in an Initializr project | `bootJar` with the Spring Boot Gradle plugin |
| Included Wrapper | `mvnw`, `mvnw.cmd`, `.mvn/wrapper/` | `gradlew`, `gradlew.bat`, `gradle/wrapper/` |

**Gradle – Groovy** and **Gradle – Kotlin** differ in the syntax of the build configuration file, **not** in requiring the application itself to be written in Groovy/Kotlin. You can choose **Language = Java** together with **Gradle – Kotlin**. If you are new and have no team convention, **Maven + Java** is an easy-to-follow choice; if a large project already uses Gradle, pick the exact DSL already in use to reduce maintenance overhead.

The **Wrapper** scripts let you run the build tool at the version locked by the project, without necessarily installing Maven/Gradle globally. On the first run, the Wrapper may need network access to download the distribution and dependencies; **a JDK must still be available**.

## 4. Creating a Project on Spring Initializr

Open **https://start.spring.io**. Labels may change slightly between UI versions, but the meaning of the fields remains similar.

**Step 1 — Project:** Choose **Maven** for the example in this lesson. If you want to use Gradle, choose **Gradle – Groovy** or **Gradle – Kotlin** and use the Gradle command set in the later sections.

**Step 2 — Language:** Choose **Java**. This selects the language for the generated Spring Boot source code.

**Step 3 — Spring Boot:** Choose a stable release compatible with your JDK and deployment environment. When following a course or working in a team, use the exact Boot line specified by the lesson/team, because starters and APIs can change across major versions.

**Step 4 — Project Metadata:** You can configure it as in the example table:

| Field | Example | Meaning |
| --- | --- | --- |
| Group | `com.example` | Group identifier, typically a reversed domain name |
| Artifact | `initializr-demo` | Module/artifact identifier, usually the directory name and JAR file prefix |
| Name | `initializr-demo` | Descriptive project name |
| Description | `Demo creating a Spring Boot project` | Metadata description; does not change runtime behavior |
| Package name | `com.example.initializrdemo` | Root Java package; **no hyphens** |
| Packaging | **Jar** | Packaging for an application that typically runs standalone with an embedded server when a web starter is present |
| Java | **21** | Selected Java level; a compatible JDK/toolchain must be used |

**Group** and **Artifact** typically form the `groupId:artifactId` coordinates (Maven) or the corresponding project/artifact name (Gradle). **Package name** is the namespace of Java classes; it must follow Java package syntax. Do not use a name containing hyphens as a package.

**Step 5 — Dependencies:** Click **Add Dependencies**. For the HTTP test in section 7, select **Spring Web**. Initializr will generate the corresponding starter declaration for the **selected Spring Boot line**; you do not need to memorize exact artifact names across every major version. If you only want to observe the scaffold and initialization lifecycle, you can create a project without Spring Web, though it will not automatically have an HTTP server to call `/ping`. Only add the starters you truly need (e.g., Validation, Spring Data JPA) when the problem requires them; each starter brings in dependencies and auto-configuration.

**Step 6 — Generate:** Click **Generate**, extract the ZIP, and open the **root directory containing `pom.xml` or `build.gradle(.kts)`** in IntelliJ IDEA, VS Code, or an IDE with Java/Spring support. Wait for the IDE to download dependencies and recognize the project. In a team, commit the Wrapper along with the build file to version control so CI and teammates' machines use the same build setup.

**Step 7 — Verify:** Compare your actual UI selections against the generated build file. If you want to change a major parameter (Boot major version, build tool, Java version), it is best to understand the impact or regenerate a clean project to compare, rather than mixing two build setups together.

## 5. What Does the Generated Scaffold Contain?

The example below illustrates a typical **Maven + Java + Jar** structure. Actual file/class names depend on the entered metadata and Initializr version.

~~~text
initializr-demo/
├── .mvn/wrapper/                 # Maven Wrapper configuration
├── mvnw                          # Wrapper for macOS/Linux
├── mvnw.cmd                      # Wrapper for Windows
├── pom.xml                       # Maven build, dependencies, plugins
├── src/
│   ├── main/
│   │   ├── java/com/example/initializrdemo/
│   │   │   └── InitializrDemoApplication.java
│   │   └── resources/
│   │       └── application.properties
│   └── test/java/com/example/initializrdemo/
│       └── InitializrDemoApplicationTests.java
└── .gitignore
~~~

The `InitializrDemoApplication` class typically has `@SpringBootApplication` and a `main` method calling `SpringApplication.run(...)`. This annotation combines Spring Boot configuration, auto-configuration, and component scanning starting from the root package. Therefore, when adding controllers/services, place them in the root package or a subpackage so they are scanned by default.

If you choose **Gradle**, the `src/main` and `src/test` structure is essentially similar, but it will use:

~~~text
build.gradle       # If choosing Gradle - Groovy
# OR build.gradle.kts if choosing Gradle - Kotlin
settings.gradle    # Or settings.gradle.kts, depending on the DSL
gradlew
gradlew.bat
gradle/wrapper/
~~~

In a Maven Initializr project, `pom.xml` typically contains Spring Boot parent/dependency management and the Maven plugin configuration. In a Gradle project, the build file configures the Spring Boot plugin, dependency management, and Java toolchain. **Do not copy Maven XML directly into Gradle or vice versa.** Make edits through the mechanisms of the chosen build tool.

Example snippet setting the Java level for **Maven** (just a snippet within `pom.xml`, not a complete standalone POM):

~~~xml
<properties>
    <java.version>21</java.version>
</properties>
~~~

Example Java toolchain configuration in **Gradle – Groovy** (just a snippet within `build.gradle`):

~~~groovy
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
~~~

Both must be backed by an actual JDK/toolchain that the build tool can use. To change the Spring Boot version, inspect the Boot plugin/parent version configuration generated by Initializr; **do not arbitrarily override individual Spring library versions**, as Boot manages a compatible set of versions via dependency management.

## 6. Running, Testing, and Packaging the Application

Open a terminal at the **project root directory**. Choose **one** command set corresponding to the selected build tool.

### Maven (macOS/Linux)

~~~bash
./mvnw test
./mvnw spring-boot:run
~~~

Open another terminal while the application is running; to package afterward:

~~~bash
./mvnw clean package
~~~

### Maven (Windows PowerShell)

~~~powershell
.\mvnw.cmd test
.\mvnw.cmd spring-boot:run
~~~

The packaging command is `.\mvnw.cmd clean package`. The JAR file usually appears in `target/`. When running manually with `java -jar`, use the **actual generated JAR name**, avoiding `.original` files or other JARs.

### Gradle (macOS/Linux)

~~~bash
./gradlew test
./gradlew bootRun
~~~

To package the Spring Boot executable JAR:

~~~bash
./gradlew clean bootJar
~~~

### Gradle (Windows PowerShell)

~~~powershell
.\gradlew.bat test
.\gradlew.bat bootRun
~~~

The packaging command is `.\gradlew.bat clean bootJar`. Output files usually reside in `build/libs/`. If using Gradle, do not invoke `spring-boot:run`; if using Maven, do not invoke `bootRun`.

**`test`** runs the generated test suite; **`spring-boot:run`/`bootRun`** starts the application via the plugin; **`package`/`bootJar`** creates the application archive. **`java -jar <path-to-boot-jar>`** runs the built executable JAR (replace the path placeholder with the actual file). Whether an HTTP server listens on a port depends on the project's dependencies and configuration.

## 7. Verifying with a Small Endpoint

To see the scaffold in action, in a project with **Spring Web**, create `src/main/java/com/example/initializrdemo/PingController.java`. The following code is **a complete class**, compiled as part of the Spring Boot project generated by Initializr; it is not a standalone Java application.

~~~java
package com.example.initializrdemo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class PingController {

    @GetMapping("/ping")
    public String ping() {
        return "pong";
    }
}
~~~

Explanation: `@RestController` marks a bean that handles HTTP requests and returns a response body; `@GetMapping("/ping")` maps HTTP GET requests at `/ping`; the string `"pong"` is returned as text. Because the controller is in the same package as the main application class (or a subpackage), Spring Boot discovers it via default component scanning.

Start the application with **one of the two** commands shown earlier (Maven or Gradle). With the default HTTP port 8080, call it from another terminal:

~~~bash
curl -s http://localhost:8080/ping
~~~

Expected response body:

~~~text
pong
~~~

If using Windows PowerShell, you can run `curl.exe -s http://localhost:8080/ping`. Do not rely on the exact order of startup log lines as verification criteria, because the banner, versions, and logs may differ. If you changed `server.port` in `application.properties`, use the configured port. If **Spring Web** was not added or the controller is not scanned, this HTTP example will not work as described.

## 8. Three Practical Selection Scenarios

**Scenario A — New to Spring Boot:** Choose **Maven + Java + Java 21 + Spring Boot stable/GA + Jar + Spring Web**. Switch to Java 17 if your learning environment only supports 17 and the chosen Boot line allows it. Use the Wrapper and test `/ping`. What matters is understanding how each choice affects the build file and runtime.

**Scenario B — Team Already Uses Gradle:** Choose **Gradle – Groovy** or **Gradle – Kotlin** matching the repo convention, **Language = Java**, and Java and Boot according to the team's compatibility matrix. Use `gradlew`/`gradlew.bat`; verify the Java toolchain and the JVM running Gradle in CI.

**Scenario C — Project Integrating with Legacy Systems:** Choose the Boot line based on library requirements and support lifecycle first, then select the corresponding JDK and build tool. A library compatible only with Boot 3 will not automatically work on Boot 4 just because both use Java 17/21; in particular, check Spring Framework/Jakarta changes across major versions.

## 9. Common Errors and Troubleshooting

| Symptom | Common Cause | How to Check and Fix |
| --- | --- | --- |
| `invalid target release` / `invalid source release: 21` | The JDK used to compile is older than the selected Java version | Check `javac -version`, `JAVA_HOME`, Maven/Gradle JVM, and toolchain; install/select the matching JDK |
| `Unsupported class file major version` or Gradle fails to start | The JVM running the build tool or the Gradle version does not support the Java level in use | Read the error message; check the Java–Gradle–Boot compatibility matrix and Wrapper |
| `bootRun` does not exist | Using Maven or missing the Spring Boot Gradle plugin | Confirm `pom.xml`/`build.gradle(.kts)`; use the matching build command |
| `spring-boot:run` does not run | Using Gradle, running in the wrong directory, or build failure | Open the project root directory; use `./gradlew bootRun` for Gradle |
| Cannot download dependencies/distribution | Network, DNS, proxy, repository, or certificates | Check connectivity, proxy, and download logs; the Wrapper may need network access on the first run |
| HTTP 404 at `/ping` | Wrong path, controller not scanned, or missing mapping | Check `@GetMapping`, controller package, and Spring Web dependency |
| Cannot connect to `localhost:8080` | Application not running, no web starter, or using a different port | Read startup logs, check dependencies, `server.port`, and running processes |
| `Port 8080 was already in use` | Another application is occupying the port | Stop the process using the port or configure `server.port=8081` |
| Builds locally on personal machine but fails in CI | Different JDK, Gradle/Maven Wrapper, or cache/repository | Align JDK/toolchain, commit Wrapper, pin versions, and run the same command in CI |

When an error occurs, read the **first root error line** in the log and determine which of the three layers it belongs to: **JDK/toolchain**, **build tool + dependencies**, or **Spring Boot runtime**. Changing multiple versions at once usually makes isolating the issue harder.
