# Exploring `BOOT-INF/classes`, `BOOT-INF/lib`, and Spring Boot Loader Classes in an Executable JAR

## 1. Goal: Look Inside the JAR and Understand Exactly How `java -jar` Runs Spring Boot

A Spring Boot application can be packaged into an **executable JAR** containing application code, resources, runtime libraries, and **Spring Boot Loader** code. Instead of merely memorizing `java -jar app.jar`, you should understand **where each piece lives, why it is placed there, and how the JVM locates your application's `main()`**.

This lesson focuses on three areas:

- **`BOOT-INF/classes/`**: the application's **own** classes and resources built from the `main` source set.
- **`BOOT-INF/lib/`**: **runtime dependency** JARs stored as *nested JARs*, preserving their own archive structure.
- **`org/springframework/boot/loader/...`** at the **root of the archive**: Spring Boot Loader classes serving as the entry point and constructing a classloader capable of reading the two areas above.

A typical executable JAR also includes `META-INF/MANIFEST.MF` declaring `Main-Class` and `Start-Class`; it may include `BOOT-INF/classpath.idx` or `BOOT-INF/layers.idx` depending on packaging configuration.

**Key takeaway:** Java does not automatically treat `BOOT-INF/classes` as the classpath, nor does it have a standard mechanism to directly load JARs nested inside another JAR. The Spring Boot Loader is the bootstrap layer solving precisely this problem.

### Three Questions to Answer After This Lesson

1. When opening `jar tf app.jar`, can you identify application classes, config files, runtime libraries, and Boot Loader code?
2. Why does the manifest point `Main-Class` to `JarLauncher` instead of your `@SpringBootApplication` class?
3. Why do a **plain JAR** and a **Spring Boot executable JAR** share the `.jar` extension yet cannot be launched the same way?

Examples use **Java 17** and **Spring Boot 3.3.13** to keep package/class names consistent; these are illustrative versions, **not a claim about the latest release**. Other versions, particularly before Spring Boot 3.2, may use different launcher packages/names. Always inspect the **actual** manifest and JAR contents rather than copying launcher class names from another tutorial.

## 2. What Does a Spring Boot Executable JAR Look Like?

Here is a **conceptual** diagram of an executable JAR after `spring-boot:repackage` (Maven) or `bootJar` (Gradle). Artifact/version names depend on the project:

~~~text
hello-boot-0.0.1-SNAPSHOT.jar
|
+-- META-INF/
|   +-- MANIFEST.MF
|
+-- org/springframework/boot/loader/
|   +-- launch/
|   |   +-- JarLauncher.class
|   |   +-- LaunchedClassLoader.class
|   |   +-- ...
|   +-- jar/
|   |   +-- NestedJarFile.class
|   |   +-- ...
|   +-- ...
|
+-- BOOT-INF/
    +-- classes/
    |   +-- com/example/hello/HelloApplication.class
    |   +-- application.properties
    |   +-- static/...             (if present)
    |   +-- templates/...          (if present)
    |
    +-- lib/
    |   +-- spring-boot-3.3.13.jar
    |   +-- spring-context-<resolved-version>.jar
    |   +-- ...                    (actual runtime JARs)
    |
    +-- classpath.idx             (depends on config)
    +-- layers.idx                (depends on config)
~~~

Library names in the diagram are illustrative; exact files come from the project's dependency resolution. The **directory layout** of the archive is relatively stable, while the dependency set varies by starters, scopes, excluded dependencies, plugins, and modules.

| Location | Role | Where It Comes From | How to Read It |
| --- | --- | --- | --- |
| `META-INF/MANIFEST.MF` | Entry-point metadata, versions, and archive information. | JAR packaging / Spring Boot build plugin. | `unzip -p app.jar META-INF/MANIFEST.MF` or extract this single entry with `jar xf`. |
| `BOOT-INF/classes/` | Project's production `.class` files and resources. | `src/main/java`, `src/main/resources`, built annotation/generated outputs. | `jar tf app.jar` filtered by prefix. |
| `BOOT-INF/lib/` | Dependency JARs packaged inside the outer JAR. | Runtime classpath resolved by the build tool. | `jar tf app.jar` to list nested JAR names; extract an individual nested JAR to inspect inside. |
| `org/springframework/boot/loader/` | Boot loader bootstrap/launcher and loader infrastructure. | Loader code added to the executable archive by the Maven/Gradle Spring Boot plugin. | Filter `jar tf` by this prefix. |
| `BOOT-INF/classpath.idx` | Specifies classpath entry order when the launcher runs via `java -jar`. | May be generated by the packaging plugin. | Read entry if present; not inherently mandatory. |
| `BOOT-INF/layers.idx` | Metadata grouping archive contents into layers for container images/extraction. | Layered archive feature of the build plugin. | Read index if present; do not treat it as an ordinary runtime classpath list. |

**Terminology caution:** "fat JAR", "uber JAR", and "runnable JAR" are often used interchangeably. In Spring Boot, the distinguishing trait here is **nested dependency JARs kept intact**, unlike how a shaded JAR may merge/relocate `.class` files from multiple dependencies into a flat namespace.

## 3. `BOOT-INF/classes`: Where Does Your Application Live?

When Maven or Gradle compiles a project's main code, temporary outputs typically land in:

- Maven: `target/classes/com/example/hello/HelloApplication.class`.
- Gradle: `build/classes/java/main/com/example/hello/HelloApplication.class` and resources in `build/resources/main/`.

When building the executable JAR, these main outputs are placed inside **`BOOT-INF/classes/`**, for example:

~~~text
BOOT-INF/classes/com/example/hello/HelloApplication.class
BOOT-INF/classes/com/example/hello/Greeter.class
BOOT-INF/classes/application.properties
~~~

### 3.1. `BOOT-INF/classes` Is Not an Ordinary Directory on Disk

When looking at `hello-boot.jar` in a file explorer, you see only **one archive file**. The path `BOOT-INF/classes/...` is an **entry inside the ZIP/JAR**, not a folder Java creates alongside the archive.

This matters when writing resource-reading code:

~~~java
// Read a resource from the classpath: compatible with standard packaging.
try (var stream = Thread.currentThread()
        .getContextClassLoader()
        .getResourceAsStream("application.properties")) {
    if (stream == null) {
        throw new IllegalStateException("Resource not found");
    }
    // Process the stream if the application genuinely needs it.
}
~~~

This snippet is only an **illustrative Java fragment for resource loading**, not a standalone program. When launched via the Boot Loader, `BOOT-INF/classes` belongs to the application's runtime classpath so the resource can be found. In application code, normally use Spring's `Environment`/`@ConfigurationProperties` to read configuration rather than opening files manually.

Common anti-pattern:

~~~java
// Incorrect when the resource only exists inside the executable JAR:
new java.io.File("BOOT-INF/classes/application.properties");
~~~

`File` points to a path on the **filesystem**, not an entry inside a JAR. This path may not exist even though the resource is packaged in the archive. Do not force classpath resources to be `File` instances; use `getResourceAsStream`, URL/resource abstractions, or extract to an appropriate location.

### 3.2. Main Code, Test Code, and Generated Output Differ

- `src/main/java` and `src/main/resources` are production inputs, typically going into `BOOT-INF/classes` after compilation/resource processing.
- `src/test/java` and `src/test/resources` are **not** packaged into the runtime executable JAR by default. If test classes appear in the archive, check source sets and custom packaging configurations.
- Dependencies only in `test` scope/`testImplementation` are excluded from `BOOT-INF/lib` in a normal executable JAR.
- Generated classes/resources may appear if the build attaches them to the main output.
- `application.properties`/`application.yml` can sit at `BOOT-INF/classes` if present in sources; **not every project is required to have one**.

To locate the main class by package, filter `jar tf` by the real path rather than just grepping for `Application`: a module may have multiple `@Configuration` classes or different class names.

## 4. `BOOT-INF/lib`: Nested Dependency JARs

A Spring Boot Web app may need Spring Framework, Jackson, an embedded servlet container, and logging. Supplying all dependency classes on an external classpath traditionally requires distributing many JAR files along with a classpath script. A Spring Boot executable JAR typically packages **each dependency JAR as an entry** under `BOOT-INF/lib`:

~~~text
BOOT-INF/lib/spring-boot-3.3.13.jar
BOOT-INF/lib/spring-core-<version>.jar
BOOT-INF/lib/spring-web-<version>.jar
BOOT-INF/lib/<embedded-server>.jar
BOOT-INF/lib/<logging-dependency>.jar
...
~~~

These are **sample names**, not mandatory output. Check exact versions of each dependency from the manifest/dependency tree or actual JAR names inside the archive rather than guessing from the Boot version.

### 4.1. How Does a Nested JAR Differ from an Unpacked Library?

**Nested JAR:**

~~~text
outer-app.jar
  +-- BOOT-INF/lib/library-a-1.0.jar
        (a complete JAR file residing inside outer-app.jar)
~~~

**Shaded/flattened JAR:**

~~~text
outer-app.jar
  +-- com/vendor/a/ClassA.class
  +-- com/vendor/b/ClassB.class
        (dependency classes merged directly into the outer archive)
~~~

The Spring Boot Loader keeps nested JARs separate, allowing dependency lookups per archive and reducing the need to merge duplicate resource/class files during the build. However, nested JARs **do not make dependency conflicts disappear automatically**: if two versions of the same library end up on the runtime classpath, load order/compatibility still needs attention.

### 4.2. Why Isn't the JDK Enough to Load JARs Inside a JAR?

Standard `java -jar outer.jar` syntax tells the JVM to read `META-INF/MANIFEST.MF` and invoke `Main-Class`. The standard Java classpath has no rule to "automatically treat each `BOOT-INF/lib/*.jar` inside a ZIP file as a classpath entry".

Traditional example:

~~~bash
java -cp "lib/*:classes" com.example.hello.HelloApplication
~~~

requires `lib/` and `classes/` to exist on the filesystem (and classpath separators differ between Linux/macOS and Windows). That mechanism **does not apply as-is** to `BOOT-INF/lib` inside an outer JAR.

The Boot Loader adds support for accessing nested JARs without forcing the project to unpack every dependency prior to startup.

### 4.3. ZIP Rule: Nested JAR Entries Need `STORED`

According to the Spring Boot Loader specification, **the ZIP entry of a nested JAR inside the outer archive** must use the `ZipEntry.STORED` method (uncompressed at the outer-entry level). This lets the loader seek directly to the nested archive's byte range. **Inside** the nested JAR, classes and resources can still be compressed per standard JAR rules; other entries in the outer JAR can also be compressed.

Do not confuse "STORED" with "Spring Boot does not compress dependencies". It is only a requirement on the **outer entry wrapping the nested JAR**, enabling efficient data access by the loader. Thus, when building archives with an arbitrary ZIP tool or custom script, repacking the ZIP without preserving this requirement can leave the JAR readable by `jar tf` yet unrunnable by the Spring Boot Loader.

**Recommendation:** let `spring-boot-maven-plugin` or `BootJar` produce the proper layout. Do not manually manipulate the outer ZIP in a production pipeline unless you understand the loader spec and smoke-test `java -jar` afterward.

## 5. Boot Loader Classes: Why Are They at the JAR Root?

When running:

~~~bash
java -jar hello-boot-0.0.1-SNAPSHOT.jar
~~~

the Java launcher reads `Main-Class` from the manifest. In a typical Spring Boot 3.3 executable JAR, the entry point is not the application class, but:

~~~text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.hello.HelloApplication
~~~

**Right mental model:**

- `Main-Class` = the **bootstrap class** the JVM can invoke directly from the JAR. In Spring Boot 3.3, this is normally `org.springframework.boot.loader.launch.JarLauncher`.
- `Start-Class` = the **application main class**, containing `public static void main(String[] args)` and calling `SpringApplication.run(...)`.
- The Boot Loader looks up `Start-Class`, builds the runtime classpath, and calls the application main once the right classloader is ready.

**Why does the Boot Loader live at the root under `org/...`?** The JVM launching the outer JAR must find `Main-Class` **directly on the outer archive's classpath**. If `JarLauncher.class` were placed under `BOOT-INF/classes`, the JVM would lack the extra logic needed to know about that location and could not start. That is why **bootstrap code sits at the root**, while **application code sits in `BOOT-INF/classes`**.

### 5.1. Key Classes / Class Groups to Recognize

| Class / Group | Conceptual Role | What to Remember |
| --- | --- | --- |
| `org.springframework.boot.loader.launch.JarLauncher` | Entry point for executable JARs; initializes the fixed classpath of the JAR layout. | Finds app classes in `BOOT-INF/classes` and dependency JARs in `BOOT-INF/lib`. |
| `org.springframework.boot.loader.launch.Launcher` | Common base class for launchers. | Handles setting up the classloader and calling the app main class. |
| `org.springframework.boot.loader.launch.LaunchedClassLoader` | Classloader used by the launcher for the launched application. | Capable of loading classes/resources from the classpath built by the Boot Loader. |
| `org.springframework.boot.loader.jar.NestedJarFile` | Supports reading data from nested JARs / outer archives. | Not a business dependency of the app; a runtime packaging detail. |
| `org.springframework.boot.loader.launch.WarLauncher` | Launcher for executable WARs. | WARs use `WEB-INF` paths rather than the exact JAR layout. |
| `org.springframework.boot.loader.launch.PropertiesLauncher` | More flexible launcher supporting external path config when used. | Only present and selected when that launch style/layout is configured; not needed by default in every app. |

In **Spring Boot 3.3.13**, the package `...loader.launch.JarLauncher` is established in that version's API. Documentation for Boot 2.x or Boot 3.1 and earlier may show `org.springframework.boot.loader.JarLauncher` (without the `launch` segment), so **do not use those examples to edit a 3.3 JAR's manifest**.

### 5.2. Actual Startup Flow

~~~mermaid
flowchart TD
  CMD["java -jar hello-boot.jar"] --> MF["JVM reads META-INF/MANIFEST.MF"]
  MF --> ML["Main-Class: JarLauncher (Boot Loader root classes)"]
  ML --> CL["Set up runtime classpath / LaunchedClassLoader"]
  CL --> APP["BOOT-INF/classes: application classes/resources"]
  CL --> DEPS["BOOT-INF/lib: nested dependency JARs"]
  CL --> ST["Read Start-Class"]
  ST --> MAIN["Invoke HelloApplication.main(args)"]
  MAIN --> SB["SpringApplication.run: build Spring context"]
  SB --> READY["HTTP app ready / job starts"]
~~~

Note that the diagram simplifies many details around manifest parsing, nested URLs, and loading. The key point is that **the JVM calls the loader first**, rather than jumping straight into the application inside `BOOT-INF/classes`.

### 5.3. Why Does `java -cp app.jar MyApplication` Usually Fail?

~~~bash
# Anti-pattern: do not use for JARs packaged with the Spring Boot layout
java -cp hello-boot-0.0.1-SNAPSHOT.jar com.example.hello.HelloApplication
~~~

Standard classpath handling on an outer JAR does not recognize `BOOT-INF/classes` as the classpath root. Consequently, the JVM may report `ClassNotFoundException` or fail to find the main class, even though `jar tf` shows `BOOT-INF/classes/com/example/hello/HelloApplication.class` exists.

The right command to verify an executable Boot JAR is:

~~~bash
java -jar hello-boot-0.0.1-SNAPSHOT.jar --server.port=18085
~~~

There is no need to manually add `BOOT-INF/lib/*.jar` to `-cp` when the launcher already handles it. Note that certain `PropertiesLauncher` customizations or alternative launch setups have their own rules; this lesson explains the **default `JarLauncher` layout**.

### 5.4. Context ClassLoader and Third-Party Libraries

Some reflection or service-loading code uses the thread's context classloader. The Spring Boot Loader recommends accessing classes/resources via `Thread.currentThread().getContextClassLoader()` or Spring resource abstractions where appropriate. Do not force `ClassLoader.getSystemClassLoader()` to find nested dependencies, because the initial system classloader lacks the full classpath constructed by the Boot Loader.

When a library reports missing resources/classes even though `BOOT-INF/lib` contains the JAR, check which classloader it uses, whether it demands a real filesystem path, and whether it requires native library/temp extraction. Avoid reacting by copying dependency JARs haphazardly into the root archive.

## 6. The Manifest Is the Map Showing How a JAR Can Run

A standard JAR has a manifest at `META-INF/MANIFEST.MF`. In a Spring Boot executable JAR, an illustrative example is:

~~~text
Manifest-Version: 1.0
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.hello.HelloApplication
Spring-Boot-Version: 3.3.13
~~~

Other fields may be added by build plugins and project configuration (such as implementation metadata, Spring Boot paths, build tool versions, and classpath indices). **Not every JAR's manifest is required to have these exact lines**. What is mandatory for `java -jar` is a valid entry point; in a standard Boot JAR layout, `Start-Class` identifies the application main class.

### 6.1. Distinguishing `Main-Class` and `Start-Class`

Question: "I annotated my class with `@SpringBootApplication`; why doesn't the manifest put that class in `Main-Class`?"

Answer: because the launcher must open the classpath from `BOOT-INF/classes` and `BOOT-INF/lib` **before** the JVM can load the app class. `Main-Class` points to the loader class at the root; `Start-Class` points to the application. If you build a **plain JAR** whose `Main-Class` points directly to the app, it runs only if all dependencies are supplied externally in a compatible manner; the `.jar` extension by itself does not make an app self-contained.

### 6.2. Inspecting the Manifest via CLI

If `unzip` is available (common on macOS/Linux, though not guaranteed):

~~~bash
unzip -p target/hello-boot-0.0.1-SNAPSHOT.jar META-INF/MANIFEST.MF
~~~

Or using only JDK `jar`:

~~~bash
# Run in a separate inspection directory to avoid overwriting project files.
mkdir -p jar-inspect
cd jar-inspect
jar xf ../target/hello-boot-0.0.1-SNAPSHOT.jar META-INF/MANIFEST.MF
cat META-INF/MANIFEST.MF
~~~

The command above illustrates Maven: `target/` sits at the root before `cd`. If using Gradle, adjust the path to `build/libs/`. On Windows, use PowerShell `Get-Content META-INF/MANIFEST.MF` after extracting. Use a **new inspection directory** to avoid overwriting files in the working directory when running `jar xf`.

Look up the **actual** `Main-Class` and `Start-Class`. If `Main-Class` is missing, `java -jar` usually reports `no main manifest attribute`. If `Main-Class` contains an old launcher name or a class absent from the archive, revisit the plugin configuration/packaging before manually editing the manifest.

## 7. Runnable Practice: Building a Small Executable JAR

This example uses a Spring Boot Web app returning `pong` so archive inspection connects directly to real runtime behavior. **Use one build tool—Maven or Gradle**—rather than keeping both wrappers in the same project unless the team intentionally maintains both.

Code structure:

~~~text
hello-boot/
  pom.xml                           (if Maven)
  # or settings.gradle/build.gradle (if Gradle)
  src/main/java/com/example/hello/HelloApplication.java
  src/main/resources/application.properties
  src/test/java/com/example/hello/HelloApplicationTest.java
~~~

### 7.1. Java Source: Entry Point and HTTP Endpoint

File `src/main/java/com/example/hello/HelloApplication.java`:

~~~java
package com.example.hello;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@SpringBootApplication
@RestController
public class HelloApplication {

    public static void main(String[] args) {
        SpringApplication.run(HelloApplication.class, args);
    }

    @GetMapping("/ping")
    public String ping() {
        return "pong";
    }
}
~~~

File `src/main/resources/application.properties`:

~~~properties
spring.application.name=hello-boot
server.port=8080
~~~

The class path inside the JAR will be `BOOT-INF/classes/com/example/hello/HelloApplication.class`, and the resource will be `BOOT-INF/classes/application.properties` under standard packaging. The `8080` value in the resource can be overridden with `--server.port=18085` at runtime.

Test `src/test/java/com/example/hello/HelloApplicationTest.java`:

~~~java
package com.example.hello;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class HelloApplicationTest {

    @Test
    void pingReturnsPong() {
        assertEquals("pong", new HelloApplication().ping());
    }
}
~~~

The test above verifies **method logic** without starting a Spring context, so it does not replace an HTTP smoke test of the executable JAR. It is sufficient to distinguish `src/test/java` from `src/main/java` and observe that test classes are **not** packaged into `BOOT-INF/classes`.

### 7.2. Maven: Complete POM for `repackage`

File `pom.xml`:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.3.13</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>hello-boot</artifactId>
    <version>0.0.1-SNAPSHOT</version>

    <properties>
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

With the Boot starter parent, the plugin is managed and the `repackage` execution is already configured in the parent POM. Declaring the plugin as above causes `mvn package` to build the ordinary archive and then let the Spring Boot plugin repackage it into an **executable archive**.

Commands (assuming the project includes the Maven Wrapper):

~~~bash
./mvnw clean package

# Output file per example GAV; confirm exact name in target/
jar tf target/hello-boot-0.0.1-SNAPSHOT.jar
~~~

**Expected outcome:** the package build discovers and passes `HelloApplicationTest`; `target/hello-boot-0.0.1-SNAPSHOT.jar` contains the launcher and `BOOT-INF`. Maven may also leave `*.jar.original`, which is the original plain JAR before repackaging; do not use that file as the executable artifact.

If a project **does not use the Spring Boot starter parent and only imports the BOM**, you must declare the `spring-boot-maven-plugin` **version** and appropriate `repackage` goal binding; the BOM only manages dependency versions and does not add build plugin executions.

### 7.3. Gradle: `bootJar` Produces the Same Layout

`settings.gradle`:

~~~groovy
rootProject.name = 'hello-boot'
~~~

`build.gradle`:

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.13'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
~~~

Commands (assuming a compatible Gradle Wrapper is present):

~~~bash
# Run tests/checks then package, per the actual build graph
./gradlew clean build

# Request only the task that creates the executable JAR
./gradlew bootJar

# Inspect the archive built by bootJar:
jar tf build/libs/hello-boot-0.0.1-SNAPSHOT.jar
~~~

`bootJar` builds an executable JAR using the Boot layout. In a Java plugin project, `jar` may also create a **plain JAR** (often carrying the `plain` classifier), such as `hello-boot-0.0.1-SNAPSHOT-plain.jar`. Do not confuse them: `jar tf` lets you tell them apart by contents, and `java -jar` tests runnability.

### 7.4. Two Packaging Commands, Same Structural Verification

Whether using Maven or Gradle, verify at minimum:

~~~text
META-INF/MANIFEST.MF
org/springframework/boot/loader/launch/JarLauncher.class
BOOT-INF/classes/com/example/hello/HelloApplication.class
BOOT-INF/classes/application.properties
BOOT-INF/lib/<actual-dependencies>.jar
~~~

The entry order does not have to match the diagram; `jar tf` typically prints many lines, and ordering depends on how the archive was built. If the loader version differs, determine the exact launcher path from the actual file's manifest.

## 8. Exploring the JAR from the Outside In with Real Commands

**Rule:** first locate the right JAR file, then read the manifest, classify entries by prefix, and finally extract a nested dependency to inspect it. Do not extract into the workspace root, and do not modify the built artifact before running a smoke test.

### 8.1. Step 1 — List Entries

Maven (example path):

~~~bash
jar tf target/hello-boot-0.0.1-SNAPSHOT.jar
~~~

Gradle:

~~~bash
jar tf build/libs/hello-boot-0.0.1-SNAPSHOT.jar
~~~

`jar tf` **only lists entries at the level of the archive being opened**. When you see `BOOT-INF/lib/spring-core-....jar`, it displays the **nested JAR file as a single entry**, without automatically listing every `.class` inside that nested JAR.

macOS/Linux filter (requires `grep`):

~~~bash
JAR=target/hello-boot-0.0.1-SNAPSHOT.jar

# Grab main entries and skip classes/metadata you don't need immediately
jar tf "$JAR" | grep -E '^(META-INF/MANIFEST.MF|BOOT-INF/classes/|BOOT-INF/lib/|org/springframework/boot/loader/)'
~~~

If the output is too large, filter each layer separately:

~~~bash
jar tf "$JAR" | grep '^BOOT-INF/classes/'
jar tf "$JAR" | grep '^BOOT-INF/lib/'
jar tf "$JAR" | grep '^org/springframework/boot/loader/'
~~~

PowerShell (no `grep` needed):

~~~powershell
$jar = "target/hello-boot-0.0.1-SNAPSHOT.jar"
jar tf $jar | Select-String '^BOOT-INF/classes/'
jar tf $jar | Select-String '^BOOT-INF/lib/'
jar tf $jar | Select-String '^org/springframework/boot/loader/'
~~~

Update `$jar` to the right path if using Gradle. These commands **do not run the application**; they only read the archive.

### 8.2. Step 2 — Read the Manifest and Check the Launcher

If `unzip` is available:

~~~bash
unzip -p "$JAR" META-INF/MANIFEST.MF
~~~

Look for `Main-Class` and `Start-Class`. With Boot 3.3.13 in this example, expect:

~~~text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.hello.HelloApplication
~~~

If `unzip` is not installed, use JDK `jar xf` inside a **new temporary directory**, never extracting over your sources:

~~~bash
mkdir -p jar-inspect
cd jar-inspect
jar xf ../target/hello-boot-0.0.1-SNAPSHOT.jar META-INF/MANIFEST.MF
cat META-INF/MANIFEST.MF
~~~

From `jar-inspect`, return to the root with `cd ..` before running other archive checks. On Windows PowerShell, create an inspection directory and use `jar xf`/`Get-Content` similarly, adjusting path separators.

### 8.3. Step 3 — Inspect a Nested JAR from `BOOT-INF/lib`

Suppose `jar tf` gave the **exact name** `BOOT-INF/lib/spring-core-6.x.y.jar`. Here `6.x.y` is a placeholder; replace it with the real version. Extract only the one dependency you want to inspect:

~~~bash
# Syntax example after replacing <actual-version>
unzip -p "$JAR" "BOOT-INF/lib/spring-core-<actual-version>.jar" > spring-core-inspect.jar
jar tf spring-core-inspect.jar
~~~

In the shell example above, run the commands from the root where `$JAR` is set and extract into a writable inspection directory. **Do not literally pass `<actual-version>` in the shell** because angle brackets can be interpreted as redirection; substitute the real version or a safe path first.

You can replace `unzip -p` with `jar xf` into an inspection directory, though that creates the `BOOT-INF/lib/...` directory structure and you must run a second `jar tf` on the extracted nested JAR. Opening an outer entry and then opening the inner nested archive is **two operations**, not an automatic recursive listing.

### 8.4. Step 4 — Verify Packaged Configuration Files

If `application.properties` exists in main resources:

~~~bash
unzip -p "$JAR" BOOT-INF/classes/application.properties
~~~

Its contents are the resource **after build/packaging**, which may differ from source if Maven filtering or Gradle `processResources` ran. If a resource is generated or relocated by a plugin, check its actual path before concluding it is missing.

Expected evidence in this example:

~~~properties
spring.application.name=hello-boot
server.port=8080
~~~

When running `java -jar ... --server.port=18085`, the CLI overrides `8080` **without modifying the packaged file**. That is the proper practice for runtime configuration.

## 9. `NestedJarFile` and How the Spring Boot Loader Accesses Internal Contents

An outer JAR is actually a ZIP archive containing an index/directory of entries. To load a class from a nested dependency, the loader must resolve:

1. At which byte offset inside the **outer JAR** does `BOOT-INF/lib/spring-core-...jar` reside?
2. Inside the nested JAR, where does `org/springframework/.../SomeClass.class` reside?
3. How does the classloader read resource bytes and define classes when the classpath entry is not a standalone JAR file on the filesystem?

The Spring Boot Loader mechanism uses components like `NestedJarFile` and appropriate URL/protocol handlers to map nested entries to byte ranges in the outer archive, rather than forcing all dependencies to be unpacked to disk before startup.

**It does not mean the JVM "loaded the whole JAR into RAM".** The loader can access archive entries by offset/index and load classes on demand. Exact implementation details may change across Boot versions; ordinary application developers only need to rely on **correct classpath behavior**, without calling internal loader APIs directly.

### 9.1. Classpath URLs and Compatibility Scenarios

The Boot Loader supports accessing nested JAR resources via URLs compatible with Boot's mechanism. Some frameworks use `URLClassLoader`, `ServiceLoader`, reflection, or resource scanning; under supported conditions, they work on the classpath built by the Boot Loader.

If a library assumes resource URLs must use the `file:` scheme or tries converting a JAR resource URL into a `java.io.File`, reading may fail when the resource lives inside a nested archive. The right fix is usually to use stream/resource abstractions, or (if the library truly requires a physical file) **extract that specific resource to a temp directory** via appropriate APIs and clean it up. Do not unpack the entire executable JAR just to mask a faulty assumption in code.

### 9.2. Testing `ClassLoader` — Observational Code Snippet

This is an **illustrative Java snippet**, not a standalone program:

~~~java
ClassLoader loader = Thread.currentThread().getContextClassLoader();

try (var in = loader.getResourceAsStream("application.properties")) {
    if (in == null) {
        throw new IllegalStateException("Missing application.properties");
    }
    // You can read the properties file from InputStream without a physical File.
}
~~~

When the project is started by the Spring Boot Launcher, the context classloader can locate resources on the application classpath. Do not pass `BOOT-INF/classes/application.properties` as the resource name to the classloader: to running code, the classpath root corresponds to `BOOT-INF/classes/`, so the resource name is normally `application.properties`.

### 9.3. Why Might Many Loader Classes Appear Without Showing Up in the Dependency Tree?

The Spring Boot Loader is injected into the outer executable archive by the **packaging plugin**. It is not necessarily listed as a separate project runtime dependency in the same sense as `spring-web` or `jackson-databind`. When comparing the dependency tree with archive contents, distinguish:

- **Build plugin / loader infrastructure** at the root.
- **Resolved runtime dependencies** inside `BOOT-INF/lib`.
- **Application output** inside `BOOT-INF/classes`.

Thus, seeing loader classes at the root that do not appear as direct dependencies in the dependency tree is not an error. Conversely, if `BOOT-INF/lib` is completely empty in a Spring Boot Web app, inspect plugin classpath/repackage settings and actual dependency scopes.

## 10. `classpath.idx` and `layers.idx`: Both Live in `BOOT-INF`, with Different Responsibilities

A Spring Boot executable JAR may contain index files inside `BOOT-INF`. They do **not** replace `BOOT-INF/classes` or `BOOT-INF/lib`.

### 10.1. `BOOT-INF/classpath.idx` — Library Ordering

Example **illustrative format**:

~~~text
- "BOOT-INF/lib/example-a-1.0.jar"
- "BOOT-INF/lib/example-b-2.0.jar"
~~~

The classpath index specifies the order of classpath entries used by the Spring Boot Launcher **when the archive is executed via `java -jar`**. It is not a directive forcing Gradle/Maven to use that order in dev mode, nor does it resolve dependency conflicts by itself.

- `jar tf "$JAR" | grep '^BOOT-INF/classpath.idx$'` checks if the index exists (macOS/Linux).
- `unzip -p "$JAR" BOOT-INF/classpath.idx` reads its contents if present.
- Inspect real entries instead of placeholder names.
- When running from an IDE or `spring-boot:run`/`bootRun`, the build tool's classpath differs; do not assume every dev mode uses this index.

### 10.2. `BOOT-INF/layers.idx` — Layer Separation for Image Building

Illustrative YAML-like example of a layer index:

~~~yaml
- "dependencies":
  - "BOOT-INF/lib/example-a-1.0.jar"
  - "BOOT-INF/lib/example-b-2.0.jar"
- "application":
  - "BOOT-INF/classes/"
  - "META-INF/"
~~~

`layers.idx` groups archive files and directories into layers so image-building tools can reuse caches more effectively. Depending on the plugin, the structure may also contain `spring-boot-loader` and `snapshot-dependencies` layers; the illustration above is **not the full set of required defaults**.

**Do not equate them:**

- `classpath.idx`: metadata regarding **classpath order** for the Boot launcher.
- `layers.idx`: metadata regarding **artifact/container image layering**.
- Neither indicates "this dependency is missing" or "this project passed security scanning".

A layered JAR is still an **executable JAR**. If `layers.idx` is absent in a customized archive, that alone does not mean the archive cannot run; inspect the launcher, classes/lib, and `java -jar`.

### 10.3. When Are Layers Truly Useful?

In multi-layer CI/CD image pipelines, application code changes more often than dependencies. If app classes are placed in a different layer from dependency JARs, image builders can reuse the dependency layer when only business code changes. Actual cache effectiveness still depends on your Dockerfile/Buildpacks/layer ordering.

Spring Boot 3.3 supports archive extraction and the appropriate launcher via documented modes. That is an **optional deployment optimization**; the core lesson remains understanding executable archives and reading `BOOT-INF` properly. Do not blindly run `jarmode` extraction commands from a different version without checking `java -Djarmode=tools -jar app.jar help` or your project's build docs.

## 11. Comparing Three Easily Confused Artifact Types

| Type | Main Structure | Directly Runnable via `java -jar` Without External Classpath? | When to Use? |
| --- | --- | --- | --- |
| **Plain/library JAR** | Classes/resources usually at root package paths; dependencies not embedded. | **Not by default**. May lack `Main-Class` or runtime deps. | Libraries, intermediate outputs, artifacts consumed by other apps. |
| **Spring Boot executable JAR** | Loader at root; app in `BOOT-INF/classes`; runtime JARs in `BOOT-INF/lib`; manifest points to launcher/`Start-Class`. | **Yes**, when archive is valid and JDK/runtime config/external services match. | Standalone Spring Boot deployment. |
| **Shaded/flattened uber JAR** | Many dependency classes merged under shared package paths in one archive. | Depends on manifest/shading config and compatibility. | Alternative distribution approach with conflict/relocation/resource-merging trade-offs. |

**Do not choose an artifact by size alone.** A Boot executable JAR is usually larger than a plain JAR because it contains runtime dependencies, yet size alone does not confirm the right entry point. Always check **`BOOT-INF` + manifest + smoke test**.

### 11.1. Maven `.jar.original` and Gradle `-plain.jar`

- **Maven:** when Boot `repackage` processes an ordinary JAR and replaces the output, it may keep the original with a `.jar.original` suffix.
- **Gradle:** when both `jar` and `bootJar` run, the ordinary JAR may get the `plain` classifier while the executable JAR typically has no classifier, depending on config.
- When deploying, use the **executable Boot JAR** published by the pipeline; never match with a wildcard and grab the first file.

With Gradle:

~~~bash
# Example to view files produced by build, not a safe CI artifact selection command
ls -l build/libs/
~~~

In CI, explicitly verify archive name/metadata or configure a fixed `archiveFileName` to avoid deploying `*-plain.jar` by mistake.

### 11.2. Executable WAR Is a Different Variant

A Spring Boot WAR uses **`WEB-INF/classes`**, `WEB-INF/lib`, and possibly `WEB-INF/lib-provided`, with `WarLauncher` when run as an executable WAR. Therefore, do not use `BOOT-INF/classes` criteria to judge a **WAR** as broken. This lesson evaluates **executable JARs** only; do not apply these criteria verbatim to WARs or native images.

## 12. Running the Exact Artifact You Just Inspected

After building the JAR, stop any `spring-boot:run` or `bootRun` instance using the test port, then run the **actual JAR file**:

~~~bash
# Sample Maven artifact:
java -jar target/hello-boot-0.0.1-SNAPSHOT.jar --server.port=18085

# Or sample Gradle artifact:
# java -jar build/libs/hello-boot-0.0.1-SNAPSHOT.jar --server.port=18085
~~~

Open a second terminal:

~~~bash
curl -i http://localhost:18085/ping
~~~

**Expected:** HTTP status `200`, exact body `pong`. Headers and console logs do not have fixed output across different JDKs/OSes/networks/runtimes. Stop the app with Ctrl+C after testing.

If `java -jar` starts successfully and handles `GET /ping`, you have verified **loader + nested dependency classpath + application classes + HTTP runtime** working together in the artifact. Still, that remains a smoke test and does not prove all business flows, security, throughput, or production readiness.

### 12.1. When Logs Show an Error Before App Ready

- **`no main manifest attribute`**: verify you have the right executable JAR, `repackage`/`bootJar` plugin, and manifest.
- **`Could not find or load main class org.springframework.boot.loader...JarLauncher`**: `Main-Class` does not match the actual loader path, the archive was altered, or an incompatible loader version is used.
- **`ClassNotFoundException: com.example.hello.HelloApplication`**: compare `Start-Class` against `BOOT-INF/classes/com/example/hello/HelloApplication.class`.
- **`NoClassDefFoundError`/`ClassNotFoundException` for framework classes**: check whether the dependency is in `BOOT-INF/lib` and selected in `runtimeClasspath`, and verify scopes/exclusions/configuration.
- **`UnsupportedClassVersionError`**: the runtime JDK does not support the bytecode version the project compiled to.
- Spring context/DB/port errors: these may be **runtime configuration** issues rather than loader bugs. Check the root cause and packaged resources.

Before editing the manifest or repacking manually, check your goal and runtime evidence; many failures stem from confusing a plain JAR with an executable JAR.

## 13. Layer-by-Layer Diagnostic Checklist

| Symptom | Likely Cause | Check You Can Run Immediately |
| --- | --- | --- |
| `jar tf` shows `BOOT-INF/classes` without `org/springframework/boot/loader`. | Custom-built archive or packaging missing Boot Loader layout. | Check `Main-Class`, `bootJar`/`repackage`, and which task ran. |
| `BOOT-INF/lib` exists yet `jar tf` does not list classes inside dependencies. | `jar tf` only opened the **outer JAR**, not the nested JAR. | Extract one nested JAR and run `jar tf` on the extracted file. |
| Loader is present yet `BOOT-INF/classes/...Application.class` is missing. | Wrong main module/source set, or build failed to include class in archive. | Check source path, compile output, `Start-Class`, and packaging task. |
| Manifest lists `Main-Class` as app class instead of loader. | Might be a plain JAR or customized executable layout. | Inspect all entries and run `java -jar` per the matching mechanism. |
| `Start-Class` points to a different FQCN than source. | Wrong `mainClass` config, multiple main methods, or custom manifest. | Compare `Start-Class` with source FQCN and entries in `BOOT-INF/classes`. |
| `application.properties` missing under `BOOT-INF/classes`. | File absent from main resources, filtered/relocated, or wrong source set. | Check `src/main/resources`, `processResources`/`target/classes`. |
| JAR exists yet runtime library is missing. | Dependency in `test`/`provided`/`compileOnly`, excluded, or custom `bootJar` classpath. | Maven `dependency:tree`, Gradle `runtimeClasspath`, archive `BOOT-INF/lib`. |
| Two versions of the same library appear. | Conflict or flawed resolution/custom packaging config. | Dependency tree/`dependencyInsight` and archive listing; do not manually delete a JAR inside the archive. |
| `java -cp outer.jar ...` fails to find app. | JDK classpath does not treat `BOOT-INF/classes` as root. | Use `java -jar` so the Boot Loader builds the classpath. |
| Library fails looking up resources via `new File(resourceUrl.toURI())`. | Resources inside JAR/nested JAR are not physical files. | Switch to stream/resource APIs or extract separately when truly required. |
| `layers.idx` exists yet application fails. | Layer index does not guarantee valid launcher/runtime config. | Check manifest, libs/classes, smoke test; distinguish layers from classpath. |
| Repacking ZIP with another tool breaks launch. | Lost layout/metadata, `STORED` compression mode, or altered manifest. | Compare original plugin output with post-processed archive; prefer rebuilding with Boot plugin. |
| Dev run works, packaged JAR fails. | Development classpath differs from executable archive. | Compare Maven/Gradle dependency scopes, resources, repackage, launcher, and runtime config. |
| Works on Machine A, fails on Machine B. | Different JDK, environment variables, profile, port, external service, or filesystem permissions. | Record JVM version + args + artifact hash + config sources; do not infer from JAR structure alone. |

### 13.1. Which Layer Failed?

1. **Build/compile:** did Maven/Gradle resolve dependencies and generate main classes/resources?
2. **Packaging:** did the Boot plugin run, is the manifest right, and are `BOOT-INF`/loader intact?
3. **Nested dependency loading:** does the JAR hold the right libraries and can the classloader read them?
4. **Application bootstrap:** is `Start-Class` right, and did `SpringApplication.run` initialize the context?
5. **Runtime/environment:** are port/profile/secrets/DB/broker/JDK accurate?
6. **Business behavior:** does the request/job satisfy its minimal contract?

A failure at steps 5–6 should not be "fixed" by randomly moving entries inside `BOOT-INF/lib`; a failure at step 2 will not be solved by changing `server.port`.

## 14. Verifying with Build Tools: Do Not Rely on File Listings Alone

### 14.1. Maven

~~~bash
./mvnw -version
./mvnw clean verify
./mvnw dependency:tree
jar tf target/hello-boot-0.0.1-SNAPSHOT.jar
~~~

From `mvn verify`, ensure real tests are discovered and pass; from `dependency:tree`, inspect resolved versions/scopes. Then inspect `BOOT-INF/lib`: a dependency appearing in the tree yet absent from the executable archive may be due to a valid scope or packaging exclusion, **not automatically a bug**.

### 14.2. Gradle

~~~bash
./gradlew --version
./gradlew clean build
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --configuration runtimeClasspath --dependency spring-core
jar tf build/libs/hello-boot-0.0.1-SNAPSHOT.jar
~~~

`dependencyInsight` shows the selected version and why (BOM/constraint/conflict resolution). `bootJar` typically packages dependencies from `runtimeClasspath` per plugin configuration. Configurations like `testImplementation` are not treated as runtime application dependencies.

### 14.3. Preserving Proper Artifacts and Evidence

A minimal handoff package should record:

- Commit/build number and version of the Spring Boot build plugin.
- JDK versions used for building and running per organizational requirements.
- Build commands and actual test reports executed (not just a generic success line).
- Exact archive name/path; optionally checksum/digest for traceability.
- Key entries: `Main-Class`, `Start-Class`, `BOOT-INF/classes`, `BOOT-INF/lib`, loader.
- `java -jar` outcome and smoke test/job output.
- For security scans/SBOMs, use actual metadata/dependency versions from the artifact rather than guessed versions.

A structurally valid archive is a **necessary condition** for the loader to run, not complete proof of security or production readiness.

1. Why is `HelloApplication.class` in `BOOT-INF/classes` instead of the archive's root directory?
