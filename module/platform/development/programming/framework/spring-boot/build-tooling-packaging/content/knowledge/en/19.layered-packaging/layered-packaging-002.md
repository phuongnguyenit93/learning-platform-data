# Role of layers.idx and Distinction from classpath.idx

## 1. Lesson Objectives

In Spring Boot, an executable JAR can carry two files in the `BOOT-INF` directory: **`classpath.idx`** and **`layers.idx`**. Both use a simple text format and are typically generated by the Spring Boot Maven/Gradle Plugin during packaging, yet they answer **two completely different questions**:

- **`classpath.idx`:** When running an executable archive with `java -jar`, **in what order** must the Spring Boot Loader add **the nested JARs** to the classpath?
- **`layers.idx`:** When an image-building tool extracts archive contents, **which files/directories belong to which layer**, and **in what order should those layers be arranged in a Docker/OCI image**?

One index serves **classloading order**, while the other serves **container image layering and caching strategy**. Sitting together in `BOOT-INF` does not mean they serve the same purpose. In particular, merely having a JAR with `layers.idx` **does not make Docker automatically split four image layers** when the Dockerfile only runs `COPY app.jar`.

After this lesson, you will be able to:

1. Read the structure of a Spring Boot nested executable JAR.
2. Identify the location, syntax, and usage timing of each index.
3. Distinguish classpath ordering from dependency version resolution and image layer ordering.
4. Explain the four default layers: `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, and `application`.
5. Build and run a Spring Boot JAR containing both indices using Maven or Gradle.
6. Inspect contents via `jar tf`, `unzip -p`, JDK tools, `jarmode=tools list-layers`, and `extract --layers`.
7. Use layered extraction in a multi-stage Dockerfile with `COPY` commands in the proper order.
8. Configure enabling/disabling or custom layers via Maven XML or Gradle DSL; do not manually edit raw index files.
9. Diagnose missing files, IDE vs. packaged JAR discrepancies, duplicate dependencies, and unexpected Docker caching behavior.
10. Identify the limitations of both indices for WARs, thin JARs, shaded JARs, and reproducible builds.

**Example context:** Spring Boot **3.5.16**, Java **17+**, compatible Maven/Gradle, executable JAR packaging. Java 17 and Spring Boot 3.5.x simply define a practice scope with explicit API and tool names; they do not mean every project must use this exact version.

## 2. Structure of an Executable Spring Boot JAR

Spring Boot packages dependencies as **nested JARs** (each dependency remains a JAR file inside the outer JAR), rather than unpacking every `.class` file and merging them flat like Maven Shade or Gradle Shadow.

~~~text
layer-index-demo-1.0.0.jar
├── META-INF/
│   └── MANIFEST.MF
├── org/springframework/boot/loader/
│   └── launch/JarLauncher.class
└── BOOT-INF/
    ├── classes/
    │   ├── com/example/indexdemo/
    │   │   └── LayerIndexApplication.class
    │   └── application.properties
    ├── lib/
    │   ├── spring-boot-3.5.16.jar
    │   ├── commons-lang3-3.17.0.jar
    │   └── ... other runtime JARs ...
    ├── classpath.idx
    └── layers.idx
~~~

The tree above is a **model**; dependencies beyond the two illustrative names depend on the resolved graph. To check actual contents, run `jar tf` on the real file. `spring-boot-3.5.16.jar` is a dependency JAR, while `JarLauncher.class` at the root is a Boot Loader class packaged into the executable archive.

| Location | Function |
| --- | --- |
| `META-INF/MANIFEST.MF` | Declares `Main-Class` as Spring Boot's `JarLauncher` and `Start-Class` as the application's `main` class |
| `org/springframework/boot/loader/**` | Loader classes enabling execution with nested libraries |
| `BOOT-INF/classes/` | Project application classes, resources, and configuration files |
| `BOOT-INF/lib/*.jar` | Runtime dependencies preserving JAR boundaries |
| `BOOT-INF/classpath.idx` | Ordered list of paths for loading dependency JARs |
| `BOOT-INF/layers.idx` | Mapping of archive entries into logical image layers |

Because the standard Java JVM launcher does not automatically scan nested JAR files in `BOOT-INF/lib` to add them to the classpath, the Spring Boot Loader is the startup component suited for this layout.

### 2.1. Two Distinct Flows

~~~text
FLOW A: Application startup
java -jar app.jar
  -> META-INF/MANIFEST.MF
  -> Boot JarLauncher
  -> BOOT-INF/classes and BOOT-INF/lib
  -> BOOT-INF/classpath.idx: order of nested dependency JARs
  -> Start-Class.main(args)
  -> SpringApplication.run(...)

FLOW B: Creating a layered Docker/OCI image
mvn package / gradle bootJar
  -> executable app.jar containing BOOT-INF/layers.idx
  -> jarmode tools / image build tooling
  -> extract dependencies, loader, snapshot deps, app
  -> Dockerfile COPY each layer in order
  -> Image filesystem layers + container cache
~~~

**There is no step where “layers.idx decides which class is loaded first”.** Conversely, `classpath.idx` does not dictate whether the Docker `dependencies` layer is copied before or after `application`.

## 3. classpath.idx: Library Order on the Classpath

### 3.1. File and Syntax

`BOOT-INF/classpath.idx` is a list of **JAR paths including their directory**, in the exact order the loader needs to add them to the application classpath.

Valid example when the archive actually contains `alpha-1.0.jar` and `beta-2.0.jar`:

~~~text
- "BOOT-INF/lib/beta-2.0.jar"
- "BOOT-INF/lib/alpha-1.0.jar"
~~~

Each line takes the form `- "BOOT-INF/lib/<dependency>.jar"`, specifically:

- Starts with a **dash + one space** (`- `).
- The internal archive path is enclosed in **double quotes**.
- The list contains only ordered JAR paths; **there are no layer names**.
- Uses `/` for paths inside the ZIP/JAR, even on Windows.
- A file described as residing at `BOOT-INF/lib/foo.jar` must actually have a matching entry in the archive.

This is a **YAML-compatible** syntax, but Boot **does not parse it as an arbitrary YAML document**. Do not add anchors/tags/comments/map keys just because another YAML parser would accept them.

### 3.2. Why Is Ordering Needed?

Classpath order can affect lookups when two JARs contain:

- The same fully-qualified Java class name due to conflicting dependency versions.
- Duplicate resource names, such as `META-INF/services/...`, a properties file, or an XML file.
- A library calling `ClassLoader.getResource(...)` and receiving the first matching resource instead of reading all resources via `getResources(...)`.

Spring Boot build plugins typically generate a classpath index so the launcher knows the dependency JAR order matching the build system. However, **the index is not a tool for fixing dependency conflicts**: if two JARs contain conflicting classes, fix BOMs/constraints/exclusions in Maven/Gradle and rebuild rather than editing the index order to “let the right version win”.

### 3.3. Used Only in Packaged Runs

Spring Boot 3.5 documentation explicitly states that `classpath.idx` is used by Boot when an executable JAR/WAR runs via **`java -jar`**.

| Execution method | Uses packaged classpath.idx? |
| --- | --- |
| `java -jar target/app.jar` | Potentially yes, when the index exists and Boot Loader reads the archive |
| `java -jar build/libs/app.jar` | Potentially yes |
| Clicking Run main class from an IDE | **No** |
| `mvn spring-boot:run` | **No** |
| `./gradlew bootRun` | **No** |
| JUnit running on the project classpath | **No** |
| Plain Java JAR run via `java -cp ...` | **Does not automatically use the Boot index** |

This is why you must test the **actual executable archive** in addition to running in an IDE. If a bug only occurs with `java -jar`, compare both runtime dependencies and the index against the IDE classpath. Do not assume the index is the sole culprit: exclusions, profiles, file locations, and classloader behavior can also differ.

### 3.4. classpath.idx Is Not a Dependency Lockfile

`classpath.idx` only records **the paths of already-packaged JARs**. It does not:

- Download missing dependencies from Maven Central/Gradle repositories.
- Select newer library versions.
- Perform dependency conflict resolution in place of Maven/Gradle.
- Lock the transitive dependency graph like `gradle.lockfile`.
- Pull in extra JARs if there is only an index line without bytes in `BOOT-INF/lib`.

To change dependency versions, edit the source build configuration and rebuild the executable JAR.

### 3.5. Reproducible Builds Affect Ordering

Spring Boot notes that when reproducible build behavior is enabled, entries in `classpath.idx` may be **sorted alphabetically**. Therefore, never promise that the first line of the index always reflects dependency declaration order in `pom.xml` or `build.gradle.kts`.

When you need to verify specific behavior, inspect the file directly in the output and compare against `mvn dependency:tree`/Gradle `dependencyInsight`. Avoid relying on “first JAR wins” behavior for application logic.

## 4. layers.idx: Layer Map Used for Docker/OCI

### 4.1. layers.idx Syntax

`BOOT-INF/layers.idx` consists of **layer names**, each with a list of paths belonging to it. **Illustrative** example, not an exact dump from a build:

~~~yaml
- "dependencies":
  - "BOOT-INF/lib/spring-boot-3.5.16.jar"
  - "BOOT-INF/lib/commons-lang3-3.17.0.jar"
- "spring-boot-loader":
  - "org/springframework/boot/loader/"
- "snapshot-dependencies":
  - "BOOT-INF/lib/my-lib-1.0-SNAPSHOT.jar"
- "application":
  - "BOOT-INF/classes/"
  - "META-INF/"
~~~

Each layer name is written as `- "layer-name":`. Entries for the layer are indented by two spaces and start with `- "path"`. **Directory paths** end with `/`, while file paths do not. When specifying a directory, contents beneath that directory belong to the same layer.

**Do not copy this example verbatim into a real JAR**: when a project has no `my-lib-1.0-SNAPSHOT.jar`, that line does not fit the artifact. The plugin builds the index based on actual dependencies and files.

### 4.2. The Four Default Layers

Spring Boot Maven and Gradle plugins use by default:

| Layer | Main default contents | Change characteristics |
| --- | --- | --- |
| `dependencies` | Standard release libraries | Typically change infrequently |
| `spring-boot-loader` | Boot Loader classes under `org/springframework/boot/loader/**` | Changes when Boot Loader changes |
| `snapshot-dependencies` | External SNAPSHOT libraries | Can change frequently |
| `application` | App classes/resources and local module/project dependencies | Typically changes per commit |

Default order:

~~~text
1. dependencies
2. spring-boot-loader
3. snapshot-dependencies
4. application
~~~

The rationale is **cache locality**: less frequently changing parts go into earlier layers; frequently changing application code goes into later layers. When source changes while dependencies do not, the Docker/OCI builder can reuse earlier layers and only build/push/pull what changed per actual cache mechanics.

**No absolute performance guarantee:** If library versions change on every build, `dependencies` is also invalidated; if the base image digest changes, cache behavior changes too. Simply having layer names does not prove image startup is faster by some fixed percentage.

### 4.3. Local Module Dependencies Differ from External Dependencies

In a Maven multi-module reactor, the Boot plugin can classify dependencies corresponding to modules **belonging to the current build** into `application`, rather than treating them as external release dependencies. If an internal dependency is resolved purely from the local Maven cache because it is not part of the current reactor, it may be classified as a regular dependency.

Gradle automatically recognizes `project(":shared")` dependencies and puts them in `application`. Libraries coming from external repositories are evaluated by release/SNAPSHOT rules.

**Do not guess based on groupId:** Whether a `com.example:shared` dependency lands in `application` or `dependencies` depends on whether it is a module dependency of the current build or a separately published/resolved JAR. To be sure, read `layers.idx` from the actual artifact.

### 4.4. layers.idx Does Not Interfere with the Runtime Classpath

In this index, a library may be in the `dependencies` layer, yet that tells you nothing about whether it precedes or follows another library on the runtime classpath. To check loader order, read **`classpath.idx`**. Adding a “business-libs” layer does not create a new Java classloader, enable/disable Spring profiles, or alter the version selected by the resolver.

## 5. Comparison Table: Two Non-Interchangeable Indices

| Characteristic | classpath.idx | layers.idx |
| --- | --- | --- |
| Question answered | “Which nested JARs are loaded in what order?” | “Which image layer do archive entries belong to?” |
| File in JAR | `BOOT-INF/classpath.idx` | `BOOT-INF/layers.idx` |
| Data structure | A list of JAR paths | List of layer names and nested path lists |
| Kind of order | Classpath loading order | Docker/OCI layer order |
| Consumer | Spring Boot Loader during `java -jar` | Jarmode tools/image tooling/buildpacks |
| Primary job | Supports runtime classloading | Separates image contents for cache reuse |
| Mentions app classes? | No, mainly library paths | Yes, e.g., `BOOT-INF/classes/` |
| Mentions Boot Loader classes? | No | Yes, `spring-boot-loader` layer |
| Used during IDE `main` run? | No | No |
| Locks versions? | No | No |
| Automatically creates Docker image? | No | No |
| Edit manually? | No; rebuild from dependency graph | No; adjust layer policy in plugin |
| When absent? | Packaged app can still run without order hints | App can still run; image layering tools lack metadata |

**Remember:** `classpath.idx = classpath order`; `layers.idx = layer cache grouping`.

## 6. Complete Maven Spring Boot Project for Practice

This Java 17 example uses `spring-boot-starter`, **requiring no web server, database, or Docker to run the initial Maven steps**. A Commons Lang dependency is declared so a nested library is clearly visible.

### 6.1. Project Tree

~~~text
layer-index-demo/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/com/example/indexdemo/LayerIndexApplication.java
    │   └── resources/application.properties
    └── test/
        └── java/com/example/indexdemo/LayerIndexApplicationTest.java
~~~

### 6.2. pom.xml

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.16</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>layer-index-demo</artifactId>
    <version>1.0.0</version>
    <packaging>jar</packaging>

    <properties>
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter</artifactId>
        </dependency>
        <dependency>
            <groupId>org.apache.commons</groupId>
            <artifactId>commons-lang3</artifactId>
            <version>3.17.0</version>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
                <configuration>
                    <layers>
                        <enabled>true</enabled>
                    </layers>
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
~~~

The Spring Boot starter parent already configures the `repackage` execution; declaring the plugin as above makes `mvn package` build an **executable Boot JAR**. In Boot 3.5, layered packaging is already enabled by default, so `enabled=true` is included deliberately to make the lesson easy to verify, not as a mandatory requirement for every project.

Do not add the Maven Shade Plugin to this project. Shade merges libraries into a different layout from Boot nested JARs.

### 6.3. Runnable Java Source

Create `src/main/java/com/example/indexdemo/LayerIndexApplication.java`:

~~~java
package com.example.indexdemo;

import org.apache.commons.lang3.StringUtils;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class LayerIndexApplication {

    public static void main(String[] args) {
        SpringApplication.run(LayerIndexApplication.class, args);
    }

    public static String outputMessage() {
        return "LAYERS_OK " + StringUtils.capitalize("hello");
    }

    @Bean
    ApplicationRunner printMessage() {
        return args -> System.out.println(outputMessage());
    }
}
~~~

`StringUtils.capitalize("hello")` returns `Hello`. The exact line **printed by `ApplicationRunner` after context initialization** is:

~~~text
LAYERS_OK Hello
~~~

Spring Boot also outputs startup logs depending on the environment, so do not assume the entire stdout contains only that single line.

### 6.4. application.properties

Create `src/main/resources/application.properties`:

~~~properties
spring.application.name=layer-index-demo
~~~

After packaging, this resource resides at `BOOT-INF/classes/application.properties`, normally belonging to the `application` layer. This file is not an index file; it is Spring Boot configuration data.

### 6.5. JUnit Test

Create `src/test/java/com/example/indexdemo/LayerIndexApplicationTest.java`:

~~~java
package com.example.indexdemo;

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertEquals;

class LayerIndexApplicationTest {

    @Test

        assertEquals("LAYERS_OK Hello",

    }

~~~

The test runs with JUnit Jupiter from `spring-boot-starter-test`. It **does not print to stdout** and needs no external services, making it suitable for testing logic independently of the Docker pipeline.

## 7. Reading the Contents of Both Indices

### 7.1. Linux/macOS with unzip

~~~bash
unzip -p target/layer-index-demo-1.0.0.jar BOOT-INF/classpath.idx
unzip -p target/layer-index-demo-1.0.0.jar BOOT-INF/layers.idx
~~~

`unzip -p` prints entry contents to stdout without extracting or modifying the JAR. `classpath.idx` will contain lines like `- "BOOT-INF/lib/foo.jar"`; `layers.idx` will contain groups like `- "application":` followed by file paths.

To check only the index locations in the archive:

~~~bash
jar tf target/layer-index-demo-1.0.0.jar |
  grep -E '^BOOT-INF/(classpath|layers)\.idx$'
~~~

If both exist, the output from `grep` may be:

~~~text
BOOT-INF/classpath.idx
BOOT-INF/layers.idx
~~~

### 7.2. Windows PowerShell with the JDK

JDK `jar` can extract **only specified entries**. To avoid colliding with existing files, create a separate inspection directory:

~~~powershell
$archive = (Resolve-Path .\target\layer-index-demo-1.0.0.jar).Path
New-Item -ItemType Directory -Force .\inspect-index | Out-Null
Push-Location .\inspect-index

jar xf $archive BOOT-INF/classpath.idx BOOT-INF/layers.idx
Get-Content .\BOOT-INF\classpath.idx
Get-Content .\BOOT-INF\layers.idx

Pop-Location
~~~

This snippet assumes `inspect-index` is a new inspection directory and you have write permissions. In a shared project, choose an empty directory containing no important data before running `jar xf`. Do not re-zip the production JAR after reading the indices.

### 7.3. Analyzing One Dependency Example

Suppose both files contain information about Commons Lang.

In `classpath.idx`:

~~~text
- "BOOT-INF/lib/commons-lang3-3.17.0.jar"
~~~

It indicates **the position of the Commons Lang JAR in the runtime classpath order** when the archive runs via the launcher.

In `layers.idx`:

~~~yaml
- "dependencies":
  - "BOOT-INF/lib/commons-lang3-3.17.0.jar"
~~~

It indicates **this path is placed in the `dependencies` layer** for image tooling.

**You cannot infer classpath order from layer membership, nor infer layer membership from a classpath index line.**

## 8. Spring Boot 3.5 Jarmode Tools

### 8.1. Correct Command for Boot 3.5

Layered executable Boot 3.5 JARs typically carry the **`spring-boot-jarmode-tools`** dependency. The tool provides `-Djarmode=tools` mode to inspect or extract the archive without **starting application logic**.

~~~bash
java -Djarmode=tools -jar target/layer-index-demo-1.0.0.jar
~~~

The tool prints usage information with subcommands such as `extract`, `list-layers`, and `help`.

List layer names:

~~~bash
java -Djarmode=tools \
  -jar target/layer-index-demo-1.0.0.jar \
  list-layers
~~~

For default layering, you should see the names:

~~~text
dependencies
spring-boot-loader
snapshot-dependencies
application
~~~

This is an **illustrative output of layer names**; exact usage/log formatting is not required to match verbatim. If the project has custom layers, the names will differ.

**Version warning:** some older Spring Boot 2.x/3.x guides use `-Djarmode=layertools` and `spring-boot-jarmode-layertools`. With **Spring Boot 3.5**, use **`-Djarmode=tools`** and `spring-boot-jarmode-tools`. Do not copy commands from documentation for a different major/minor version.

### 8.2. Extracting Layers

~~~bash
java -Djarmode=tools \
  -jar target/layer-index-demo-1.0.0.jar \
  extract --layers --destination extracted
~~~

Windows PowerShell:

~~~powershell
java "-Djarmode=tools" -jar .\target\layer-index-demo-1.0.0.jar extract --layers --destination extracted
~~~

With default layers, the tool generates output separated by layer names, for example:

~~~text
extracted/
├── dependencies/
├── spring-boot-loader/
├── snapshot-dependencies/
└── application/
~~~

A layer may be empty if the project has no dependencies in that group. Use a directory you control; if files remain from an earlier extraction, use a different destination or inspect actively so contents from different builds are not mixed.

View available flags:

~~~bash
java -Djarmode=tools -jar target/layer-index-demo-1.0.0.jar extract --help
~~~

### 8.3. Why Not Just Unzip the Outer JAR?

Tools mode understands **layer metadata and launcher layout**. Simply running `unzip app.jar` unpacks all files into one directory and does not create `dependencies` and `application` directories matching the cache policy.

In particular, the extracted layout can produce an **`application.jar` tailored for launcher mode**, which differs from the outer Uber JAR the builder received prior to extraction. Therefore, when writing a Dockerfile per Spring Boot docs, use `extract --layers` and the corresponding entrypoint rather than arbitrarily copying raw files and guessing the classpath.

### 8.4. When Tools Mode Fails to Run

Check these conditions:

- It is a **Boot executable archive**, not a thin JAR or standard shaded JAR.
- The plugin actually generated a layered archive.
- `spring-boot-jarmode-tools` was not excluded via `includeTools=false`.
- The JDK/JRE is compatible with the Boot release and application classes.
- The archive does not have a prepended **fully executable launch script**, which leaves tools mode unsupported.
- The command actually places `-Djarmode=tools` **before** `-jar`; it is a JVM system property.

If the tool is absent by configuration, extracting layers requires using another tool or adjusting packaging. Never randomly edit the raw JAR index as a workaround.

## 9. From layers.idx to a Layered Docker Image

### 9.1. Simple Dockerfile Not Consuming layers.idx

~~~dockerfile
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY target/layer-index-demo-1.0.0.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]
~~~

This Dockerfile can run the Spring Boot application. However, the `COPY` step places the **entire JAR file** into one image filesystem layer. Changing a single Java class alters the outer JAR bytes and forces the `COPY` layer to update. **Docker does not automatically parse `BOOT-INF/layers.idx`** just because the JAR contains it.

### 9.2. Multi-Stage Dockerfile for Boot 3.5

Place the Dockerfile at the Maven project root after running `mvn clean package`. The example below uses an illustrative Java 17 image:

~~~dockerfile
FROM eclipse-temurin:17-jre AS builder
WORKDIR /builder
COPY target/layer-index-demo-1.0.0.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM eclipse-temurin:17-jre
WORKDIR /application

COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./

ENTRYPOINT ["java", "-jar", "application.jar"]
~~~

**How the steps work:**

1. Builder receives the outer Boot JAR containing tools mode.
2. `extract --layers` unpacks contents into four logical directories according to `layers.idx`.
3. The runtime stage runs `COPY` for the directories in order: dependencies, loader, snapshot-dependencies, application.
4. Each `COPY` establishes a cache boundary/filesystem layer suited to how Docker image builds work.
5. The entry point invokes `application.jar` generated inside the **extracted launcher layout**, **not** the outer `/builder/application.jar` copied initially.

After building the JAR file, run:

~~~bash
docker build -t layer-index-demo:local .
docker run --rm layer-index-demo:local
~~~

The sample application has no HTTP server, so no port mapping is needed. The business output line remains:

~~~text
LAYERS_OK Hello
~~~

### 9.3. Cache Reuse Opportunities

If `LayerIndexApplication.java` source changes while dependencies stay the same, the `application` layer changes while `dependencies` can be reused. If you upgrade a release library, `dependencies` changes; if `spring-boot-loader` changes due to a Boot upgrade, the loader layer changes too.

This is a **mechanism for improving cache efficiency**, not a promise that “every build only uploads the final layer”: caching depends on the Docker builder, registry state, base image, archive metadata, timestamps, and build inputs.

**`COPY` order is a deliberate design choice.** Copying frequently changing app code before dependencies causes many builders to invalidate subsequent steps and forfeit caching benefits.

### 9.4. Supply Chain Note

`eclipse-temurin:17-jre` is a readable tag for examples; tags can point to new bytes when maintainers publish updates. In CI/releases requiring reproducibility, use a **genuinely verified image digest** instead of fabricating hashes. Do not store credentials inside Dockerfiles or `application.properties` files packaged in artifacts.

If using Cloud Native Buildpacks (`spring-boot:build-image` or Gradle `bootBuildImage`), the image builder has its own layering strategy; there is no need to copy the jarmode Dockerfile if buildpacks already satisfy your requirements.

## 10. Configuring Layer Metadata in Maven

### 10.1. Enabling/Disabling Layers

Spring Boot 3.5 Maven Plugin supports layered archives by default. If layer metadata is not needed, configure:

~~~xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <layers>
            <enabled>false</enabled>
        </layers>
    </configuration>
</plugin>
~~~

This is a **snippet inside `<build><plugins>`**, not a standalone POM. When layers are disabled, `layers.idx` may not be created; **`java -jar` does not need this index to start the Spring ApplicationContext**. Do not confuse the layer metadata option with disabling `classpath.idx` or the Boot Loader.

### 10.2. Custom layers.xml Is INPUT, layers.idx Is OUTPUT

To change the policy, point the plugin to a configuration file:

~~~xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
    <configuration>
        <layers>
            <enabled>true</enabled>
            <configuration>${project.basedir}/src/layers.xml</configuration>
        </layers>
    </configuration>
</plugin>
~~~

Create `src/layers.xml` with a complete configuration illustrating Spring Boot 3.5's **default behavior**:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<layers xmlns="http://www.springframework.org/schema/boot/layers"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.springframework.org/schema/boot/layers
            https://www.springframework.org/schema/boot/layers/layers-3.5.xsd">
    <application>
        <into layer="spring-boot-loader">
            <include>org/springframework/boot/loader/**</include>
        </into>
        <into layer="application" />
    </application>
    <dependencies>
        <into layer="application">
            <includeModuleDependencies />
        </into>
        <into layer="snapshot-dependencies">
            <include>*:*:*SNAPSHOT</include>
        </into>
        <into layer="dependencies" />
    </dependencies>
    <layerOrder>
        <layer>dependencies</layer>
        <layer>spring-boot-loader</layer>
        <layer>snapshot-dependencies</layer>
        <layer>application</layer>
    </layerOrder>
</layers>
~~~

**This is XML configuration for the build plugin**, not the contents of `layers.idx`. Maven reads the XML during packaging, decides layer membership, and generates the raw index inside the executable archive.

### 10.3. Claim Mechanics and layerOrder

- `<application>` defines how application classes/resources and Boot Loader entries are classified.
- `<dependencies>` defines how dependency artifacts are classified.
- `<into>` blocks are evaluated **top to bottom**; content claimed by an earlier block is unavailable to later blocks.
- `<includeModuleDependencies />` claims local modules into `application`.
- `<include>*:*:*SNAPSHOT</include>` claims matching SNAPSHOT dependencies.
- `<into layer="dependencies" />` without includes acts as a catch-all for remaining dependencies.
- `<layerOrder>` specifies the **order in which layers are written**, which can differ from the order in which `<into>` rules match files. Every participating layer must be declared.

To split out an extra layer by group/artifact, use include patterns with valid syntax inside `<dependencies>` and add the new layer to `<layerOrder>`. Never edit raw `layers.idx` after packaging.

### 10.4. Example Adding an Internal Layer

Inside `<dependencies>` of the custom XML file, before the catch-all:

~~~xml
<into layer="internal-libraries">
    <include>com.acme:*:*</include>
</into>
~~~

This is a **configuration snippet**, not a complete XML file. You must also add `<layer>internal-libraries</layer>` to `layerOrder` and place the rule where it can claim the desired artifacts. If a local module was already claimed into `application` by `includeModuleDependencies`, a later rule cannot claim it a second time. Only change layer policies when data shows splitting that library improves caching/deployment.

### 11.6. Custom Layers in Gradle

Kotlin DSL example inside `build.gradle.kts` with the Spring Boot plugin:

~~~kotlin
tasks.named<BootJar>("bootJar") {
    layered {
        application {
            intoLayer("spring-boot-loader") {
                include("org/springframework/boot/loader/**")
            }
            intoLayer("application")
        }
        dependencies {
            intoLayer("application") {
                includeProjectDependencies()
            }
            intoLayer("snapshot-dependencies") {
                include("*:*:*SNAPSHOT")
            }
            intoLayer("dependencies")
        }
        layerOrder.set(listOf(
            "dependencies",
            "spring-boot-loader",
            "snapshot-dependencies",
            "application"
        ))
    }
}
~~~

This is an **example illustrating the default policy**. `intoLayer` is evaluated in rule order, whereas `layerOrder` governs layer order when image tools extract/copy. Customize via the DSL and rebuild; do not edit raw `layers.idx`.

## 12. Maven Reactor, Gradle Project Dependencies, and Caching

A multi-module repository has:

~~~text
root
├── shared   (Java library)
└── service  (Spring Boot executable JAR depending on shared)
~~~

In Maven, `service` declares a dependency on `shared` and the parent aggregator includes `<modules>`; in Gradle, `service` uses `implementation(project(":shared"))`. Boot's default layering typically places **current-build module dependencies** in `application`.

Why? Internal modules can change on every commit just like application source, whereas external stable libraries change less often. Separating them from `dependencies` reduces the chance that internal code edits invalidate the layer containing third-party libs.

**Important distinction:** a Maven module is treated as a local module dependency only when it is **part of the current build/reactor**; a library with internal coordinates resolved only from `~/.m2` may be classified as an ordinary dependency. Thus two different build commands can produce different `layers.idx` files even with the same GAV. To verify, run the appropriate reactor build (`mvn -pl service -am package`) and read the index.

Another benefit of `layers.idx` is enabling deployment by **change frequency**, rather than by Java package structure. One layer can hold multiple JARs; the Java classpath still includes all dependencies when the app runs, regardless of which image layers they reside in.

## 13. Common Sources of Confusion

### 13.1. “layers.idx makes the JVM load dependencies before application code”

False. Layer order is the order for image builders to arrange filesystem layers/cache. Java classloading is handled by the Boot Loader and classpath policy. `layers.idx` does not make the JVM create one classloader per Docker layer.

### 13.2. “classpath.idx is a map of Docker layers”

False. That file only gives the order of dependency JAR entries. It does not assign `BOOT-INF/classes` to the `application` layer or `spring-boot-loader` to its corresponding layer.

### 13.3. “If an application has layers.idx, Docker optimizes automatically”

False. A Dockerfile with `COPY app.jar app.jar` still copies a monolithic file. You need jarmode extraction or image tooling that understands layered metadata.

### 13.4. “It ran fine in the IDE, so java -jar will definitely behave the same”

Not guaranteed. The IDE uses a different classpath from the Boot Loader packaged classpath; `classpath.idx` is not used in the IDE/`spring-boot:run`/`bootRun`. Test the executable artifact and container image directly.

### 13.5. “Disabling layers.idx disables the Boot Loader”

False. `layers.idx` serves OCI image distribution. Disabling layered metadata does not convert a Boot executable archive into a plain JAR.

### 13.6. “Editing classpath.idx is a good way to fix dependency collisions”

Not recommended. That only masks conflicts. Fix the source dependency graph, exclusions/BOM/Gradle constraints, and rebuild from a managed toolchain.

### 13.7. “Without classpath.idx, the JAR definitely won't run”

Not necessarily. The index is optional metadata. A Boot Loader-compatible executable archive can run without it, though expected classpath ordering must be verified.

### 13.8. “Having no snapshot-dependencies is an error”

No. A project may simply use no SNAPSHOT dependencies; an empty layer or one with no members is normal. The default name may still appear in the layer list when the plugin generates metadata.

### 13.9. “A JAR with META-INF/MANIFEST.MF must have both indices”

No. Thin JARs, shaded JARs, plain `jar` tasks, and certain configured Boot archives do not include both by default. Inspect the artifact type and packaging plugin.

## 14. Note on WARs and Differences from JARs

An executable Spring Boot WAR has directories:

~~~text
WEB-INF/classes/
WEB-INF/lib/
WEB-INF/lib-provided/
~~~

which differ from an executable JAR (`BOOT-INF/classes` and `BOOT-INF/lib`). Spring Boot 3.5 packaging documentation covers **layered JAR or WAR**, while the `Nested JARs / Layer Index` specification page illustrates `BOOT-INF/layers.idx` syntax for the executable JAR case.

**Do not copy JAR paths from this lesson as assumptions for all WARs.** For a WAR, run `jar tf actual.war` to identify the index location and dependencies produced by the actual plugin version. When deploying a WAR into an **external servlet container**, the container uses its own web application classloader; do not expect it to consume `classpath.idx` the same way Boot `java -jar` does.

For apps primarily running in container images, consider an executable JAR if an external servlet container is not needed. If WAR is required, test both the `java -jar` path and external deployment according to their respective contracts.

## 15. Reproducibility, Correctness, and Security

### 15.1. An Index File Does Not Replace Reproducible Builds

When the Maven/Gradle dependency graph or plugin/JDK versions change, both indices can change. Building the exact same artifact from the same source requires managing:

- JDK, Maven/Gradle Wrapper, and Spring Boot Plugin versions.
- Dependency versions/BOMs/Gradle dependency locks.
- Reproducible archive settings: timestamps, file order, and generated resources.
- Repositories, artifact checksums, and source revisions.
- Container base image digests when comparing OCI image outputs.

Spring Boot documentation notes that `classpath.idx` can be sorted alphabetically when reproducible builds are enabled. Do **not** use this file to enforce a version graph or act as a security scanner.

### 15.2. Image Layering Is Not an Application Security Boundary

A Docker/OCI layer is a filesystem changeset and cache unit, **not a security mechanism to hide secrets**. Even if app/resources are placed in a separate layer, secrets hardcoded in `application.properties` can still be read from the artifact/image.

Do not place secrets into source resources, Dockerfiles, or custom index metadata. Use environment variables/secret managers and proper filesystem permissions. For JARs, scan dependencies/SBOMs based on the build graph and actual artifacts, not just the `dependencies` layer name.

## 16. Troubleshooting: At Which Layer Should You Investigate?

| Symptom | Common possibilities | Recommended action |
| --- | --- | --- |
| Missing `BOOT-INF/layers.idx` | Reading plain JAR, layers disabled, plugin did not repackage | Check output artifact, `spring-boot:repackage`/`bootJar`, plugin config |
| Missing `BOOT-INF/classpath.idx` | Different plugin/packaging, optional file not generated | Check manifest, Boot Loader, runtime graph; do not hand-craft text |
| `java -jar` works but image cache always changes | Dockerfile only `COPY`s the whole JAR | Use tools mode extraction and `COPY` each layer |
| `list-layers` fails to run | Missing tools, wrong `jarmode`, fully executable script | Check Boot 3.5 `-Djarmode=tools`, `includeTools`, logs |
| `extract --layers` errors | Non-layered JAR, tools excluded, or wrong flags | Check `jar tf`, `help`, and plugin configuration |
| Docker cannot find `extracted/snapshot-dependencies/` | Extracted custom layer names or missing output directory | Run `list-layers`, inspect extraction tree, update Dockerfile |
| Runs in IDE, packaged JAR missing class | Dependency scope/exclusion, runtime vs. test classpath differs | `jar tf BOOT-INF/lib`, `classpath.idx`, dependency graph |
| Packaged JAR picks a different resource than IDE | Classpath order/duplicate resources/profiles | Eliminate conflict, compare classpaths; do not use index edits as primary fix |
| Custom layer does not appear | Wrong `intoLayer`/`layerOrder` or content claimed by earlier rule | Fix XML/DSL, rebuild, then inspect index |
| Local module lands in `dependencies` | Not part of current Maven reactor/project dependency | Check `-am`/module graph; add custom layer if needed |
| `layers.idx` contains non-existent path | Artifact edited manually or faulty custom tooling | Rebuild from source and inspect outer archive |
| `jar tf` does not show classes inside commons-lang3 | Classes reside inside nested `BOOT-INF/lib/commons-lang3-...jar` | Inspect nested JAR entries; do not look for classes at root |
| Maven missing Boot loader/index | Forgot Boot plugin `repackage` when using another parent | Declare plugin/execution properly |
| Gradle builds `*-plain.jar` missing indices | Inspecting `jar` task instead of `bootJar` | Run `bootJar` and check the right filename |
| `application` layer changes even without Java source changes | Generated files/timestamps/resources changed | Check reproducible archive inputs and Gradle/Maven plugin flags |
| Container start cannot find `application.jar` | Different extraction method, wrong Dockerfile COPY | Follow Boot 3.5 tools example and inspect actual file tree |

### 16.1. Five-Step Procedure

1. **Pick the right artifact:** do not confuse an executable JAR with a thin/shaded/plain JAR or `.original` file.
2. **Read both indices:** verify syntax and which paths exist in the archive.
3. **Isolate the symptom:** for class/resource loader issues, check `classpath.idx` and dependency resolution; for Docker cache issues, check `layers.idx` and `COPY` order.
4. **Run the tool in the right mode:** `java -jar` for runtime, `-Djarmode=tools` for list/extract; IDE/`bootRun` do not use the packaged classpath index.
5. **Fix build config and rebuild:** never edit raw JAR bytes manually.

## 17. Exercises and Answers

### Exercise 1. Classify the Two Files

~~~text
File A:
- "BOOT-INF/lib/a.jar"
- "BOOT-INF/lib/b.jar"

File B:
- "dependencies":
  - "BOOT-INF/lib/a.jar"
  - "BOOT-INF/lib/b.jar"
- "application":
  - "BOOT-INF/classes/"
~~~

**Answer:** File A is `classpath.idx`; File B is `layers.idx`. Both contain the same JAR names but serve different purposes.

### Exercise 2. Classpath Order vs. Layer

`classpath.idx` lists `b.jar` before `a.jar`; `layers.idx` puts both in `dependencies`.

**Answer:** Runtime classpath order is described by `classpath.idx`, while the Dockerfile copies the **`dependencies` layer** at the position defined by layer order. Docker does not create one layer for `a.jar` and another for `b.jar` if they share the same group.

### Exercise 3. Changing Only Java Source

When modifying `LayerIndexApplication.outputMessage()`, which layer is likely to change?

**Answer:** `application`, because `BOOT-INF/classes` changes. Unchanged dependencies can reuse cache if other inputs remain stable.

### Exercise 4. IDE Does Not See classpath.idx

Running the main class directly in IntelliJ/Eclipse/VS Code. Does it read the packaged index?

**Answer:** No. The IDE uses the module classpath when running. To test packaged behavior, run `java -jar` on the built artifact.

### Exercise 5. Only COPY JAR

The Dockerfile has `COPY target/app.jar app.jar` and the JAR contains `layers.idx`. Has the image automatically separated `dependencies`/`application`?

**Answer:** Not yet. It requires layer-aware extraction and corresponding `COPY` steps, or buildpacks/other image tooling.

### Exercise 6. Java Output Line

When the application in section 6 runs successfully via `java -jar`, which line is printed by `ApplicationRunner`?

**Answer:** `LAYERS_OK Hello`, alongside other Spring Boot startup log lines.

### Exercise 7. Maven Custom Rule

How do you recognize local reactor modules, snapshot libraries, and release libraries?

**Answer:** Use `includeModuleDependencies` in the `application` rule, `*:*:*SNAPSHOT` in `snapshot-dependencies`, and a catch-all `dependencies`. `layerOrder` must cover all layer names.

### Exercise 8. Missing classpath.idx

The JAR still runs but lacks the index. Is that definitely a packaging error?

**Answer:** No. The classpath index is optional. However, if the project requires deterministic runtime classpath ordering, verify plugin behavior and the artifact.

### Exercise 9. Renaming a Layer

The team renames `snapshot-dependencies` to `internal-changing`, but the Dockerfile still copies the old path.

**Answer:** The `COPY` command may fail or the image may miss files. Keep layer names synchronized across custom configuration, extracted output, and the Dockerfile.

### Exercise 10. Dependency Version Change

Changing `commons-lang3` from 3.17.0 to another release. Which index can change?

**Answer:** Both `classpath.idx` (filename/path version changes) and `layers.idx` (entry for the same dependency changes). The `dependencies` layer missing cache is expected; it does not mean loader order or code logic is broken.

## 18. Pre-Release Checklist

- [ ] Artifact is genuinely an executable Boot JAR from Maven `repackage` or Gradle `bootJar`.
- [ ] `BOOT-INF/classes`, `BOOT-INF/lib`, and Boot Loader are packaged properly.
- [ ] `classpath.idx` (if present) has accurate nested JAR paths and is not used to patch over dependency conflicts.
- [ ] Aware that `classpath.idx` only applies to packaged `java -jar` runs, not IDE/`spring-boot:run`/`bootRun`.
- [ ] `layers.idx` (if present) has accurate layer names and assigned archive paths.
- [ ] Understand default order: dependencies → spring-boot-loader → snapshot-dependencies → application.
- [ ] Do not confuse layer order with classpath order, JVM classloaders, or dependency resolution.
- [ ] Ran `jarmode=tools list-layers` and verified the extracted layout when Docker layers are needed.
- [ ] Dockerfile runs `COPY` from each extracted layer with an appropriate entrypoint.
- [ ] Verified Maven/Gradle custom layer config, rule ordering, and `layerOrder`.
- [ ] Never manually modified index files or ZIP entries of a production JAR after packaging.
- [ ] Did not disable jarmode tools while the pipeline still relies on tools mode.
- [ ] Smoke-tested `java -jar` and the deployable image, not just the IDE.
- [ ] Evaluated cache effectiveness via build logs/artifact hashes, not by counting layer names.
- [ ] Did not embed secrets in app resources/container images and maintained proper dependency/SBOM governance.
