# Inspecting Generated Sources and Compiled Resources in Build Output Directories

## 1. Why Inspect Build Output Directories?

A Spring Boot application may have valid Java source code and a build that reports success, yet still fail at runtime because a resource is missing, configuration was filtered incorrectly, or an annotation-processor implementation is absent. Looking only at **src/main/java** and **src/main/resources** cannot tell you what the program actually receives after compilation and packaging.

A Maven or Gradle build produces several **distinct output categories**. Checking the right directory helps distinguish:

1. **Hand-written source code**: Java files tracked in the repository.
2. **Generated source code**: Java files created by annotation processors, code generators, or build plugins.
3. **Compiled bytecode**: **.class** files executed by the JVM, originating from either hand-written or generated sources.
4. **Processed resources**: properties, YAML, JSON, templates, service descriptors, etc. copied or transformed during the build.
5. **Final artifact**: plain JAR, executable Spring Boot JAR/WAR, or image containing selected outputs.
6. **Build reports and caches**: test results, incremental compilation state, metadata, or intermediate files; these are not deployment artifacts by default.

**Lesson goal:** identify default locations for each output type in Maven and Gradle; use build commands, file search tools, **javap**, **jar tf**, and an annotation processing example to inspect actual contents; and explain why a file present in the build directory can still be absent from the JAR.

The hands-on lab uses **Java 17**, Spring Boot **3.5.16**, and MapStruct **1.6.3** as concrete versioned examples. Spring Boot 3.5.16 is the final OSS-supported release of the 3.5 line per release announcements; new production projects should pick an actively maintained line and verify current Java/Gradle/Maven compatibility. The paths and inspection techniques here apply broadly across standard Java builds.

## 2. Pipeline Map: From Source to Artifact

~~~text
src/main/java/                     (application source)
       |
       | compiler + annotation processors
       v
generated *.java ------------------------------+
       |                                       |
       +----> javac ---------------------------+----> compiled *.class
                                                    |
src/main/resources/ -- copy / filtering ------------+----> processed resources
                                                    |
                                  runtime dependencies
                                                    |
                                                    v
                                       plain JAR / Spring Boot JAR
                                                    |
                                                    v
                                          JVM / container runtime
~~~

Key takeaway: **generated `.java`, compiled `.class` bytecode, and resources are three distinct artifacts**. Some generators do not emit Java sources at all, instead generating other languages, metadata files, or bytecode directly. The paths listed below are defaults for common Java/Compiler plugins, **not universal rules for every plugin**. Whenever a project customizes `outputDirectory`, `layout.buildDirectory`, source sets, or code generators, inspect the project's effective configuration.

## 3. Quick Reference: Maven and Gradle Output Locations

| Artifact | Maven (typical path) | Gradle Java plugin (typical path) |
| --- | --- | --- |
| Hand-written Java source | `src/main/java` | `src/main/java` |
| Raw main resources | `src/main/resources` | `src/main/resources` |
| Java generated by annotation processors | `target/generated-sources/annotations` | `build/generated/sources/annotationProcessor/java/main` |
| Main `.class` files (including generated classes) | `target/classes` | `build/classes/java/main` |
| Main resources after copy/filter | `target/classes` | `build/resources/main` |
| Test `.class` files | `target/test-classes` | `build/classes/java/test` |
| Test resources after copy | `target/test-classes` | `build/resources/test` |
| Java generated by test annotation processors | `target/generated-test-sources/test-annotations` (plugin/compiler dependent) | `build/generated/sources/annotationProcessor/java/test` |
| Packaged JAR | `target/<artifactId>-<version>.jar` | `build/libs/<projectName>-<version>.jar` |
| Test reports | `target/surefire-reports` | `build/reports/tests/test` and `build/test-results/test` |

In Maven, both main **classes** and main **resources** commonly share **target/classes**. In Gradle, the Java plugin separates them into **build/classes/java/main** and **build/resources/main**, then combines them in source set outputs, classpaths, and archives.

**Do not expect every directory to always exist.** If a project has no file-generating annotation processors, the generated-sources folder may be empty or absent. If you only compiled `main`, test classes and test reports will not exist yet. Kotlin/Groovy projects, multi-module builds, or custom builds add paths such as **build/classes/kotlin/main** or plugin-specific **build/generated/...** folders.

## 4. Identify the Output Root and Tasks Before Inspecting Files

### 4.1. With Maven

A standard Maven project sets **project.build.directory = target**. The paths below derive from this variable and can be overridden in `pom.xml` or a parent POM. Inspect the effective values:

~~~bash
./mvnw --version
./mvnw help:evaluate -Dexpression=project.build.directory -q -DforceStdout
./mvnw help:evaluate -Dexpression=project.build.outputDirectory -q -DforceStdout
./mvnw help:evaluate -Dexpression=project.build.testOutputDirectory -q -DforceStdout
~~~

In a project using the default layout, these evaluate to **target**, **target/classes**, and **target/test-classes** relative to the project root. Maven Help Plugin may need to be downloaded to the local repository/cache on first run.

Relevant Maven phases/goals:
- **process-resources**: processes/copies main resources.
- **compile**: runs the main compiler; processors may generate `.java` and `javac` emits `.class`.
- **process-test-resources** and **test-compile**: prepare test resources and test bytecode.
- **test**: executes tests via configured plugins.
- **package**: builds the JAR/WAR; with Spring Boot Maven Plugin's **repackage** bound, the archive uses the Boot executable format.

In a project inheriting from **spring-boot-starter-parent** with Spring Boot Maven Plugin declared, **./mvnw package** normally runs compile/resources/test and builds the Boot JAR. Never treat the existence of **target/classes** as proof that **repackage** ran.

### 4.2. With Gradle

With the Gradle Java plugin, the default output root is **build/** for each project. Common commands:

~~~bash
./gradlew --version
./gradlew tasks --all
./gradlew compileJava
./gradlew processResources
./gradlew classes
./gradlew test
./gradlew bootJar
~~~

**compileJava** produces main `.class` files and runs annotation processors. **processResources** processes/copies main resources. **classes** is a lifecycle task depending on `compileJava` and `processResources`. **test** prepares/runs tests; **bootJar** is added by the Spring Boot Gradle Plugin when applied alongside the Java plugin. A task reporting **UP-TO-DATE** or **FROM-CACHE** still retains valid outputs from an earlier build; do not assume missing files just because no actions executed in this invocation.

Java plugin documentation defines these default main outputs:
- **build/classes/java/main** for compiled classes;
- **build/resources/main** for processed resources;
- **build/generated/sources/annotationProcessor/java/main** for Java sources generated by annotation processors.

To check whether your project overrides the **actual** paths, inspect `SourceSet` outputs and `JavaCompile` task options in the build script. Do not hardcode these defaults as universal answers for polyglot or custom-source-set builds.

## 5. Hands-On Lab: Generating a Real Java Class with MapStruct

Annotation processing is the classic example of **generated source**. Here we use **MapStruct**, which generates Java mapping code at **compile time**. Given an interface annotated with **@Mapper**, MapStruct generates a Java implementation typically named **GreetingMapperImpl**, which the compiler then compiles into **GreetingMapperImpl.class**. Both can be inspected independently.

The source files below are shared between the **Maven and Gradle** options. Pick **one** build tool for your practice project. Expected paths may differ if plugin/processor versions or output directories change.

### 5.1. Source Layout

~~~text
inspect-output/
├── pom.xml                       (Maven option)
│   or build.gradle               (Gradle option)
├── settings.gradle               (if using Gradle)
├── mvnw, mvnw.cmd, .mvn/...      (Maven Wrapper, if using Maven)
├── gradlew, gradlew.bat, gradle/wrapper/... (Gradle Wrapper, if using Gradle)
└── src/
    ├── main/
    │   ├── java/com/example/inspect/
    │   │   ├── InspectOutputApplication.java
    │   │   ├── InspectController.java
    │   │   ├── GreetingSource.java
    │   │   ├── GreetingDto.java
    │   │   └── GreetingMapper.java
    │   └── resources/demo.properties
    └── test/
        └── java/com/example/inspect/InspectControllerTests.java
~~~

Wrapper files must be generated via Spring Initializr/Maven Wrapper/Gradle Wrapper for the chosen tool; they do not appear automatically just by writing **pom.xml** or **build.gradle**. Use Maven 3.x or Gradle 8.14 compatible with Spring Boot 3.5.16, and configure JDK 17 for the example.

### 5.2. Input Model

File **src/main/java/com/example/inspect/GreetingSource.java**:

~~~java
package com.example.inspect;

public class GreetingSource {
    private String message;

    public GreetingSource() {}

    public GreetingSource(String message) {
        this.message = message;
    }

    public String getMessage() {
        return message;
    }

    public void setMessage(String message) {
        this.message = message;
    }
}
~~~

### 5.3. Output DTO

File **src/main/java/com/example/inspect/GreetingDto.java**:

~~~java
package com.example.inspect;

public class GreetingDto {
    private String text;

    public String getText() {
        return text;
    }

    public void setText(String text) {
        this.text = text;
    }
}
~~~

### 5.4. Mapping Interface

File **src/main/java/com/example/inspect/GreetingMapper.java**:

~~~java
package com.example.inspect;

import org.mapstruct.Mapper;
import org.mapstruct.Mapping;

@Mapper
public interface GreetingMapper {
    @Mapping(source = "message", target = "text")
    GreetingDto toDto(GreetingSource source);
}
~~~

This is a **hand-written** Java interface committed to source control. The MapStruct annotation processor detects **@Mapper** and generates the matching implementation class, so developers never write **GreetingMapperImpl.java** manually. If the annotation processor is not declared or processing is skipped, the implementation class will be missing even though the **GreetingMapper.class** interface compiles cleanly.

### 5.5. Spring Boot Application Class

File **src/main/java/com/example/inspect/InspectOutputApplication.java**:

~~~java
package com.example.inspect;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class InspectOutputApplication {
    public static void main(String[] args) {
        SpringApplication.run(InspectOutputApplication.class, args);
    }
}
~~~

### 5.6. Controller Using Both Generated Code and a Resource

File **src/main/java/com/example/inspect/InspectController.java**:

~~~java
package com.example.inspect;

import java.io.IOException;
import java.io.InputStream;
import java.util.Properties;

import org.mapstruct.factory.Mappers;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InspectController {
    private final GreetingMapper mapper =
            Mappers.getMapper(GreetingMapper.class);

    @GetMapping("/inspect")
    public String inspect() throws IOException {
        GreetingDto dto =
                mapper.toDto(new GreetingSource("generated-ok"));

        Properties properties = new Properties();
        try (InputStream input =
                     InspectController.class.getResourceAsStream(
                             "/demo.properties")) {
            if (input == null) {
                throw new IOException("demo.properties not found");
            }
            properties.load(input);
        }

        return dto.getText() + " / "
                + properties.getProperty("label", "missing");
    }
}
~~~

Calling **Mappers.getMapper(GreetingMapper.class)** locates the implementation generated by the processor. **getResourceAsStream("/demo.properties")** loads the resource from the **runtime classpath**, not directly from **src/main/resources**. When running the JAR, the resource must exist inside the artifact because the source folder may not be present on the deployment host.

### 5.7. Simple Resource for Byte-for-Byte Verification

File **src/main/resources/demo.properties**:

~~~properties
label=resource-ok
~~~

For this file, Maven/Gradle simply copies its contents as-is to the output. Keeping ASCII characters ensures consistent rendering across environments; when using Unicode in Java properties, verify encoding and loading mechanisms carefully.

### 5.8. Test Verifying Both Mapper Implementation and Resource

File **src/test/java/com/example/inspect/InspectControllerTests.java**:

~~~java
package com.example.inspect;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class InspectControllerTests {
    @Autowired
    private MockMvc mvc;

    @Test
    void generatedMapperAndResourceAreAvailable() throws Exception {
        mvc.perform(get("/inspect"))
                .andExpect(status().isOk())
                .andExpect(content().string(
                        "generated-ok / resource-ok"));
    }
}
~~~

This test verifies that both outputs are usable **on the classpath inside a running application**. That goes beyond seeing files on disk: a file sitting in a build folder is not guaranteed to be packaged into the artifact or loaded by the right classloader.

## 6. Maven Option: Configuring the Annotation Processor and Building

Create **pom.xml** at the project root:

~~~xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.5.16</version>
        <relativePath/>
    </parent>

    <groupId>com.example</groupId>
    <artifactId>inspect-output</artifactId>
    <version>1.0.0</version>

    <properties>
        <java.version>17</java.version>
        <mapstruct.version>1.6.3</mapstruct.version>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>
        <dependency>
            <groupId>org.mapstruct</groupId>
            <artifactId>mapstruct</artifactId>
            <version>${mapstruct.version}</version>
        </dependency>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <configuration>
                    <annotationProcessorPaths>
                        <path>
                            <groupId>org.mapstruct</groupId>
                            <artifactId>mapstruct-processor</artifactId>
                            <version>${mapstruct.version}</version>
                        </path>
                    </annotationProcessorPaths>
                </configuration>
            </plugin>

            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
~~~

**Why two MapStruct artifacts?** **org.mapstruct:mapstruct** provides annotations/APIs and the runtime factory; **mapstruct-processor** generates implementations during compilation. Putting the processor in **annotationProcessorPaths** keeps it out of regular runtime dependencies. On newer JDKs, do not rely on implicit classpath scanning for annotation processing; explicit processor configuration keeps builds verifiable.

### 6.1. Running Phases Step by Step to Generate Outputs

~~~bash
./mvnw --version
./mvnw clean compile
~~~

After **compile** succeeds, expected outputs:

~~~text
target/
├── generated-sources/
│   └── annotations/com/example/inspect/
│       └── GreetingMapperImpl.java
└── classes/
    ├── com/example/inspect/
    │   ├── InspectOutputApplication.class
    │   ├── InspectController.class
    │   ├── GreetingSource.class
    │   ├── GreetingDto.class
    │   ├── GreetingMapper.class
    │   └── GreetingMapperImpl.class
    └── demo.properties
~~~

This is an **expected directory tree**, not a literal machine snapshot. Maven Compiler Plugin's default **generatedSourcesDirectory** is **target/generated-sources/annotations**; its default class output is **target/classes**. Maven Resources Plugin copies main resources during **process-resources**, which runs before `compile`.

Next, run the build with tests and packaging:

~~~bash
./mvnw clean verify
~~~

With the POM above, you will also see **target/test-classes**, **target/surefire-reports**, and **target/inspect-output-1.0.0.jar**. Because **repackage** is configured by the Spring Boot parent when the Boot plugin is declared, the JAR becomes an executable archive. If tests fail, do not assume the packaged JAR was produced.

### 6.2. Inspecting the Generated Java Source

On Linux/macOS:

~~~bash
find target/generated-sources/annotations -type f -name '*MapperImpl.java'
cat target/generated-sources/annotations/com/example/inspect/GreetingMapperImpl.java
~~~

On PowerShell/Windows:

~~~powershell
Get-ChildItem -Path .\target\generated-sources\annotations -Recurse -Filter '*MapperImpl.java'
Get-Content .\target\generated-sources\annotations\com\example\inspect\GreetingMapperImpl.java
~~~

Inside the generated Java code, find the **toDto** method and the mapping **source.getMessage() → dto.setText(...)** or equivalent logic. Generator outputs can vary in imports, annotations, comments, timestamps, and formatting; **never assert against the entire generated file verbatim**. The class name **GreetingMapperImpl** follows MapStruct's naming convention in this example.

### 6.3. Inspecting Compiled Classes and Resources

~~~bash
find target/classes -type f -name '*.class'
cat target/classes/demo.properties
javap -classpath target/classes -public com.example.inspect.GreetingMapperImpl
~~~

Use **javap** to inspect bytecode signatures of the processor-generated class. **javap** does not show original Java source code verbatim; pass **-c** if you want bytecode instructions. Never treat the presence of **GreetingMapperImpl.java** as sufficient proof that **GreetingMapperImpl.class** was compiled.

On Windows PowerShell:

~~~powershell
Get-ChildItem .\target\classes -Recurse -Filter '*.class'
Get-Content .\target\classes\demo.properties
javap -classpath .\target\classes -public com.example.inspect.GreetingMapperImpl
~~~

Reading the resource should show:

~~~properties
label=resource-ok
~~~

If the resource appears in **src/main/resources** but not in **target/classes**, inspect the **process-resources** phase, resource includes/excludes, filtering rules, and paths in the **effective POM**.

## 7. Gradle Option: Configuring the Annotation Processor and Building

Use this section only when choosing Gradle. Create **settings.gradle**:

~~~groovy
rootProject.name = 'inspect-output'
~~~

Create **build.gradle** (Groovy DSL):

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.5.16'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'

    implementation 'org.mapstruct:mapstruct:1.6.3'
    annotationProcessor 'org.mapstruct:mapstruct-processor:1.6.3'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

tasks.named('test') {
    useJUnitPlatform()
}
~~~

- The Spring Boot plugin provides **bootJar** when paired with the Java plugin.
- The Spring dependency-management plugin applies the corresponding Spring Boot BOM, so managed starters omit versions.
- **implementation mapstruct** supplies annotations and the factory API; **annotationProcessor mapstruct-processor** runs the generator during compilation.
- **annotationProcessor** is not a runtime dependency; the generated/compiled `.class` implementation is what loads at runtime.
- **toolchain Java 17** selects the compiler JDK; it does not automatically change the production server's Java runtime.

### 7.1. Building Piece by Piece and Inspecting Outputs

~~~bash
./gradlew --version
./gradlew clean classes
~~~

The **classes** task triggers **compileJava** and **processResources**. On success:

~~~text
build/
├── generated/
│   └── sources/
│       └── annotationProcessor/java/main/com/example/inspect/
│           └── GreetingMapperImpl.java
├── classes/
│   └── java/main/com/example/inspect/
│       ├── InspectOutputApplication.class
│       ├── InspectController.class
│       ├── GreetingSource.class
│       ├── GreetingDto.class
│       ├── GreetingMapper.class
│       └── GreetingMapperImpl.class
└── resources/
    └── main/
        └── demo.properties
~~~

These are **Java plugin default paths**, not folder names imposed by Spring Boot. With the Gradle Kotlin plugin, many outputs sit under **build/classes/kotlin/main**; custom compiler options or `buildDir` settings change paths accordingly.

Continue with:

~~~bash
./gradlew clean test bootJar
~~~

When `test` and `bootJar` succeed, additional outputs appear:
- **build/classes/java/test** — test bytecode;
- **build/test-results/test** — machine-readable test results;
- **build/reports/tests/test** — HTML test reports;
- **build/libs/inspect-output-1.0.0.jar** — default executable Boot JAR.

**Note:** running **./gradlew clean classes** produces neither test reports nor the JAR. Running **./gradlew clean test bootJar** builds those artifacts via task dependencies. Gradle provides caching and incremental builds, so avoid running **clean** on every routine build since it discards incremental outputs. Here `clean` ensures deterministic output inspection.

### 7.2. Inspecting the Exact Generated Source and Compiled Resource

Linux/macOS:

~~~bash
find build/generated/sources/annotationProcessor/java/main -type f -name '*MapperImpl.java'
cat build/generated/sources/annotationProcessor/java/main/com/example/inspect/GreetingMapperImpl.java

find build/classes/java/main -type f -name '*.class'
javap -classpath build/classes/java/main -public com.example.inspect.GreetingMapperImpl

cat build/resources/main/demo.properties
~~~

PowerShell/Windows:

~~~powershell
Get-ChildItem .\build\generated\sources\annotationProcessor\java\main -Recurse -Filter '*MapperImpl.java'
Get-Content .\build\generated\sources\annotationProcessor\java\main\com\example\inspect\GreetingMapperImpl.java
Get-ChildItem .\build\classes\java\main -Recurse -Filter '*.class'
Get-Content .\build\resources\main\demo.properties
javap -classpath .\build\classes\java\main -public com.example.inspect.GreetingMapperImpl
~~~

In Gradle, **build/resources/main/demo.properties** is where processed main resources live in the source set output. Do not look for it in **build/classes/java/main/demo.properties** and wrongly assume the resource was skipped: compiled classes and processed resources live in **two separate output directories**.

## 8. Three Verification Levels: Generated Source, Class, Artifact

To prove an element made it all the way through the pipeline, check in order:

| Question | Evidence | MapStruct example |
| --- | --- | --- |
| Did the processor run? | Java source generated under generated-sources | `GreetingMapperImpl.java` |
| Was the generated Java compiled? | Bytecode appears in output classes | `GreetingMapperImpl.class` |
| Was the resource copied/transformed? | File exists in output resources | `demo.properties` |
| Did the archive package them? | Entry listed in the final JAR/WAR | `BOOT-INF/classes/.../GreetingMapperImpl.class` |
| Does runtime find and use them? | Integration test or running the JAR | `GET /inspect` returns expected string |

In particular, **generated Java source is not normally packaged as `.java` inside a Spring Boot JAR**. JARs carry **compiled `.class` files**. Seeing **GreetingMapperImpl.class** in the archive without **GreetingMapperImpl.java** is normal packaging behavior, not missing generated code.

**Another nuance:** compilers can emit **.class** files without ever writing a generated **.java** file to disk (e.g., certain compilers or bytecode transformers). Conversely, a generator can emit Java source that never enters compilation if task wiring/dependencies are misconfigured. Know which kind of generator you are using before choosing paths to inspect.

## 9. Inspecting the Executable Spring Boot JAR

After `package`/`bootJar`, run the JDK's **jar** tool:

~~~bash
jar tf target/inspect-output-1.0.0.jar
~~~

Or with Gradle:

~~~bash
jar tf build/libs/inspect-output-1.0.0.jar
~~~

Look for representative entries (JAR paths always use `/` on every OS):

~~~text
META-INF/MANIFEST.MF
BOOT-INF/classes/com/example/inspect/InspectOutputApplication.class
BOOT-INF/classes/com/example/inspect/InspectController.class
BOOT-INF/classes/com/example/inspect/GreetingMapper.class
BOOT-INF/classes/com/example/inspect/GreetingMapperImpl.class
BOOT-INF/classes/demo.properties
BOOT-INF/lib/mapstruct-1.6.3.jar
BOOT-INF/lib/...
org/springframework/boot/loader/...
~~~

These are **key entries to check**, not an exhaustive list or guaranteed ordering, since Boot loader, libraries, and metadata vary by version and config. Spring Boot executable JARs normally put application files in **BOOT-INF/classes** and runtime dependencies in **BOOT-INF/lib**, with the launcher specified in the manifest to load nested JARs.

### 9.1. Inspecting the Manifest Instead of Relying on Filenames Alone

In an environment with JDK **jar**:

~~~bash
jar xf target/inspect-output-1.0.0.jar META-INF/MANIFEST.MF
~~~

**jar xf** **extracts the entry into the current working directory**, so only run it inside a **temporary/sandbox folder** when inspecting the manifest; avoid extracting at the project root where files could mix into sources. On PowerShell, use **jar tf** to verify entries, or a ZIP viewer to read the manifest without extracting the archive.

A Spring Boot executable JAR manifest typically defines:
- **Main-Class** pointing to the Spring Boot launcher;
- **Start-Class** pointing to the main application class (here **com.example.inspect.InspectOutputApplication**).

Do not expect **Main-Class** to point directly to your application class in a Spring Boot executable JAR; the Spring Boot launcher is what loads nested libraries.

### 9.2. Verifying the Running Artifact

Maven:

~~~bash
java -jar target/inspect-output-1.0.0.jar
~~~

Gradle:

~~~bash
java -jar build/libs/inspect-output-1.0.0.jar
~~~

In a second terminal, once Spring Boot has started on the default port 8080:

~~~bash
curl http://localhost:8080/inspect
~~~

**Exact expected response body**:

~~~text
generated-ok / resource-ok
~~~

This confirms the MapStruct implementation was generated and compiled, the resource is packaged, and the controller loads both through the runtime classloader. If **/inspect** returns an error, inspect startup logs, exceptions, profiles/ports, and the classpath first; a file existing in the source tree proves nothing about runtime loading.

## 10. Distinguishing Resource Copying from Resource Filtering

**Copying resources** and **filtering resources** are two distinct operations:

- **Copy:** moves contents from **src/main/resources** to output resources without modifying values.
- **Filtering/expansion:** substitutes tokens with build-time values; output files can differ from source files.

In our example, **demo.properties** is only copied. When verifying filtering, identify which component replaces each token: Maven Resources Plugin, Gradle `processResources`, or Spring `Environment` at **runtime**.

### 10.1. Maven Filtering with Spring Boot Parent

In projects inheriting from **spring-boot-starter-parent**, Spring Boot configures resource filtering for production application configs using **`@...@`** tokens so they do not clash with Spring's **`${...}`** placeholders.

For example, add these lines to **src/main/resources/application.properties** in the Maven project:

~~~properties
app.build.version=@project.version@
app.runtime.flag=${RUNTIME_FLAG:off}
~~~

Run:

~~~bash
./mvnw process-resources
~~~

Inspect **target/classes/application.properties**. With the example POM at version `1.0.0`, the logical post-build file contents are:

~~~properties
app.build.version=1.0.0
app.runtime.flag=${RUNTIME_FLAG:off}
~~~

**@project.version@** was substituted by Maven at build time; **${RUNTIME_FLAG:off}** stays intact for Spring at runtime. Avoid enabling filtering with the wrong delimiter across all files, or filtering binary assets like PNGs/JARs/certificates, which can corrupt contents. Never bake environment-specific secrets into artifacts during filtering.

**Note:** the Spring Boot parent filters production configs by default; do not assume files in **src/test/resources** or arbitrary resource types are filtered automatically. If a project overrides the parent or resource plugin settings, inspect **help:effective-pom** and actual outputs.

### 10.2. Gradle Filtering Must Be Configured Explicitly

Gradle's **processResources** copies resources by default; it **does not automatically treat `@project.version@`** as a build token like the Spring Boot Maven parent. If you need build metadata, put it in a dedicated source file **src/main/resources/build-metadata.properties**:

~~~properties
app.build.version=@VERSION@
~~~

And add this task configuration to **build.gradle** (Groovy DSL):

~~~groovy
tasks.named('processResources') {
    inputs.property('appVersion', project.version.toString())

    filesMatching('build-metadata.properties') {
        filter { line ->
            line.replace('@VERSION@', project.version.toString())
        }
    }
}
~~~

This replaces **@VERSION@** with the project version as **processResources** copies the file. After **./gradlew processResources**, inspect **build/resources/main/build-metadata.properties**: with **version = '1.0.0'**, the line reads **app.build.version=1.0.0**.

This is an **incremental snippet for a Gradle project**, not a standalone `build.gradle`. It targets a single text file and registers the version input so Gradle detects changes. In practice you can also use **expand** or template filters when needed, while watching for collisions with Spring's **${...}** placeholders. Keep Spring runtime config separate from build-time metadata whenever possible.

### 10.3. Read Processed Outputs, Not Source Templates

A common point of confusion:

~~~text
src/main/resources/application.properties: app.build.version=@project.version@
target/classes/application.properties:    app.build.version=1.0.0
~~~

The source file still contains the token by design. The **output** is what reflects Maven's processing. In Gradle, that output lives in **build/resources/main** rather than alongside `.class` files. Afterward, also verify **BOOT-INF/classes/application.properties** or **BOOT-INF/classes/build-metadata.properties** inside the JAR if it must be packaged.

## 11. When Generated Java Sources Are Missing: Inspect Annotation Processing

### 11.1. Generators Must Be in the Right Scope

**Gradle:** the MapStruct processor belongs in **annotationProcessor**, not only **implementation**. Inspect the configuration:

~~~bash
./gradlew dependencies --configuration annotationProcessor
./gradlew compileJava --info
~~~

**Maven:** the processor is declared in **maven-compiler-plugin / annotationProcessorPaths** as shown. Check the effective POM and compile logs:

~~~bash
./mvnw help:effective-pom
./mvnw compile
~~~

**MapStruct 1.6.3** is used here for illustration; if using Lombok, Immutables, Hibernate metamodel, or OpenAPI Generator, the classes, paths, and tasks to inspect differ. Seeing no generated sources when an app only uses **@SpringBootApplication** is completely normal: **Spring annotations do not automatically mean generated Java sources must exist**.

### 11.2. Check Package, Class Name, and Source Set

If the interface is in **com.example.inspect.GreetingMapper**, MapStruct's default implementation is **com.example.inspect.GreetingMapperImpl**. The Java package determines the directory path on disk. Do not look under **Gradle `project.group`** or **Maven `groupId`** paths and think the class is missing: build coordinates do not change Java package paths.

For test annotation processors, Gradle uses **testAnnotationProcessor** and writes generated test Java under **build/generated/sources/annotationProcessor/java/test**. Maven likewise uses a generated test-sources directory via test compilation. Configuring a processor only for **main** will not process annotations on test sources that need their own processor.

### 11.3. Never Hand-Edit Generated Sources

**build/** and **target/** are normally excluded from version control and regenerated. Editing **GreetingMapperImpl.java** in the output directory affects only the current build and will be overwritten on the next compile or clean. To change generated code, update the **interface/annotation/source model**, processor version, or processor options and rebuild.

When a generator runs as a separate task (OpenAPI/GraphQL/protobuf), the build script must configure its output directory and wire it into the source set and compile task. A generated file sitting in **build/generated/** that is not wired into compilation produces no `.class` file and will not reach the JAR.

## 12. When a `.class` Exists Without a Generated `.java`

Several valid explanations exist:

1. The class came directly from **hand-written Java source**; having no generated `.java` is expected.
2. The compiler emitted an **inner, anonymous, or synthetic class** (such as **Outer$Inner.class**) from a single source file; there is no 1:1 `.java` file for every `.class`.
3. A bytecode enhancement/weaving tool or plugin generated bytecode directly.
4. IDE/build caches or a previous build left a `.class` behind; run a clean build in the right directory/module to confirm.
5. **MapStruct's implementation `.class`** exists while `.java` is elsewhere because the generated-sources output directory was customized.

To trace where a class came from, check source declarations, compiler task inputs, generated outputs, compiler logs, and if necessary inspect class metadata with **javap -v**. The **SourceFile** attribute (if present) hints at the source filename, though it does not prove where the source file lived on disk or when it was generated.

## 13. When Resources Are Missing from the JAR or Unreadable at Runtime

Check layer by layer:

1. **Source:** is the file actually under **src/main/resources** or a configured resource directory?
2. **Processing:** did Maven **process-resources** or Gradle **processResources** run cleanly without conflicting filters/includes/excludes?
3. **Output:** check **target/classes** in Maven; **build/resources/main** in Gradle.
4. **Packaging:** run **jar tf** to verify the entry under **BOOT-INF/classes** in the exact executable JAR.
5. **Runtime lookup:** does code call **getResourceAsStream("name")** relative to a package or **getResourceAsStream("/name")** from the classpath root? Does Spring `Environment` load that filename automatically?
6. **Config overrides:** do Spring profiles or external configs override values after startup?

For example, with **demo.properties** at the resources root, the classpath lookup path is **/demo.properties**. If moved to **src/main/resources/config/demo.properties**, Java must request **/config/demo.properties**. **application.properties** and **application.yml** have special Spring Boot loading rules; a custom file named **demo.properties** does not become a Spring property source automatically unless loaded or configured explicitly.

Another common mistake: having a file on the classpath yet using **new File("src/main/resources/demo.properties")** at runtime. That works by accident only when the current working directory points to the project root; when running the deployed JAR, the `src` folder may not exist. Use **ClassLoader.getResourceAsStream**, Spring **Resource**, or standard Spring configuration loading for resources inside JARs.

## 14. Never Confuse Test Output Directories with Main Outputs

In Maven:

~~~text
target/classes/            # main classes and main resources
target/test-classes/       # compiled test classes and test resources
target/surefire-reports/   # Surefire unit test reports
~~~

In Gradle:

~~~text
build/classes/java/main/   # main Java bytecode
build/classes/java/test/   # test Java bytecode
build/resources/main/      # main resources
build/resources/test/      # test resources
build/reports/tests/test/  # HTML test reports
build/test-results/test/   # machine-readable test results
~~~

**Test resources and test-only dependencies are not packaged into the production Spring Boot executable JAR by default**. If code works in tests yet fails once deployed, the project may have placed a required config file or dependency inside **src/test/resources**, **testImplementation**, or the test classpath. Move true production requirements to main runtime scope, while keeping secrets and sensitive test fixtures out of artifacts.

A passing test suite can also mask differences between **testRuntimeClasspath** and the Boot JAR runtime. Inspecting the **final artifact** with `jar` and running **java -jar** is essential when suspecting packaging bugs.

## 15. Files Generated by Other Plugins: Trace the Exact Producer Task

Beyond annotation processors, Spring Boot projects often use:

| Tool/mechanism | Example output | Proper way to inspect |
| --- | --- | --- |
| **MapStruct** | Java mapper implementations | Generated `.java`, compiled `.class`, classpath |
| **Lombok** | AST/bytecode modified by `javac`; typically no separate Lombok-generated `.java` for getters | **javap** on compiled classes, `annotationProcessor` config |
| **OpenAPI Generator** | Templated client/server Java sources | Output directory configured on generator task/plugin and wired source set |
| **Protobuf/gRPC** | Java sources and service stubs | Build plugin task output, compiled classes, and dependencies |
| **JPA static metamodel** | `*_` classes or annotation-processor sources | `generated-sources` and compiled classes |
| **Spring Boot build info** | **META-INF/build-info.properties** from buildInfo goal/task when enabled | **build-info / bootBuildInfo** task/goal, processed resources/JAR |
| **Generated resources** | JSON, service metadata, config files | Task outputs, resource source sets, JAR entries |

**Locations vary by plugin and version**; not every generated file lands in **target/generated-sources/annotations** or **build/generated/sources/annotationProcessor/java/main**. For instance, Lombok injects getters/setters into the compiler AST/bytecode, so searching for `UserLombokGenerated.java` is the wrong approach. Always identify **which tool** produced the file or bytecode under inspection.

In Spring Boot, **spring-boot:build-info** (Maven) or **bootBuildInfo** (Gradle) generates **META-INF/build-info.properties** with build metadata if enabled. Simply applying the Spring Boot plugin **does not guarantee** the build-info file is created. Check your config/tasks before treating a missing file as a bug.

## 16. Debugging Unexpected Paths or Results

| Symptom | Diagnostic question | Concrete action |
| --- | --- | --- |
| Missing **target/generated-sources/annotations** | Is there an annotation processor that actually emits Java? Did compile run? | Check `annotationProcessorPaths`, run **./mvnw compile**, inspect compiler logs |
| Missing **build/generated/sources/annotationProcessor/java/main** | Is the processor in `annotationProcessor` rather than `implementation` only? | Run **./gradlew dependencies --configuration annotationProcessor**, `compileJava --info` |
| **GreetingMapperImpl.java** exists, no `.class` | Were generated sources compiled? Were there `javac` errors or a custom outputDir? | Check compile logs, **javap**, and generated source-set configuration |
| `.class` exists without generated Java source | Did `javac` create it directly, as an inner/synthetic class, or via bytecode gen? | Run **javap -v**, inspect plugin/processor behavior |
| Maven lacks resource in **target/classes** | Did `process-resources` run? Was the file excluded? | Run **./mvnw process-resources**, inspect effective POM |
| Gradle lacks resource in **build/resources/main** | Did `processResources` run? Are there `filesMatching`/exclude rules? | Run **./gradlew processResources --info**, inspect `sourceSets` |
| Resource is in output, missing from **BOOT-INF/classes** | Are you inspecting the right JAR? Boot archive vs. plain JAR? | Run **jar tf**, check `bootJar`/`repackage` and exact filename |
| Class exists in build, runtime throws **ClassNotFoundException** | Is the class in the runtime artifact/classpath? Which dependency scope? | Run **jar tf**, Gradle `runtimeClasspath`/Maven dependency tree |
| **NoClassDefFoundError** for MapStruct impl | Did processor generate and compile it? Does JAR contain impl? | Inspect generated `.java`, `.class`, and `BOOT-INF/classes` |
| File filtered wrongly; `@...@` tokens still literal | Was filtering enabled on the right file, delimiter, and phase? | Read resource output, Maven effective POM, or Gradle `processResources` |
| Tests see resource, production does not | Does the file live only in test resources? | Compare test vs. main outputs and JAR entries |
| No JAR after **classes/compile** | Did you run `package`/`bootJar`? | Run Maven `package` or Gradle `bootJar` after tests |
| Checking root module, yet build runs a submodule | Which module owns the build output? | Use Maven `-pl` or Gradle `:module:task`, check module-specific `target`/`build` |
| Generated file is stale from an older build | Is the file current or stale from cache/incremental build? | Check timestamps and task outcomes; clean build when verifying |
| JAR fails while IDE runs fine | Does IDE classpath differ from archive, or runtime config/port? | Compare JAR entries, `java -jar`, and actual logs |

**Debugging rule:** pinpoint where the data disappears along **source → generated source → compiled class/resource → packaged artifact → runtime classpath**. Run the command that inspects that exact link. If a file is already present in build output, do not immediately add another dependency; check packaging and runtime classpath first.

## 17. Be Careful with Build Caches, Stale Files, and Deletions

**Maven `target/`** and **Gradle `build/`** are reproducible output directories; most projects exclude them in Git. When troubleshooting strange bugs, **clean** clears leftover files from earlier runs:

~~~bash
./mvnw clean verify
~~~

Or:

~~~bash
./gradlew clean test bootJar
~~~

However, **clean deletes project outputs**; only run it in environments or dev workspaces where clearing outputs is safe. For everyday builds, avoid unnecessary `clean` runs so you keep incremental compilation and caching benefits. When multiple builds share a workspace, outputs can change mid-inspection; track logs/build IDs and inspect one deterministic build.

**Never hand-edit compiled classes, generated Java, or resources inside `target/` or `build/` as a permanent "fix"**. Those edits vanish on the next build. Fix the original source, build script, processor configuration, or resource template and rebuild the artifact. Never commit secrets, credential files, sensitive reports, or unwanted build outputs.

In a multi-module build, each module usually maintains its own **target/** or **build/** directory. Do not check only the root directory and assume outputs are missing; identify which module actually performs the compilation or task.

## 18. Self-Check Questions

### Question 1. `GreetingMapperImpl.java` is missing after Maven `compile`. What does that prove?

**Answer:** Not enough by itself. The processor may not be declared/invoked, the build may not have reached `compile`, there may be no valid annotated mapper, the generated-source directory may have been customized, or compilation failed earlier. Check **annotationProcessorPaths**, compile logs, and **project.build.directory**. Under the demo config, the file belongs under **target/generated-sources/annotations/com/example/inspect/**.

### Question 2. Why does Gradle place `GreetingMapperImpl.class` in `build/classes/java/main` instead of `build/resources/main`?

**Answer:** Each output directory serves its intended role. **build/classes/java/main** holds Java bytecode; **build/resources/main** holds copied/processed resources. Java `.class` files do not belong in the resources output directory.

### Question 3. Why does the Spring Boot JAR contain `GreetingMapperImpl.class` without `GreetingMapperImpl.java`?

**Answer:** Runtime archives package compiled bytecode rather than Java source code. In the Boot executable JAR layout, compiled application classes live in **BOOT-INF/classes**; generated `.java` files stay in the build workspace for inspection and debugging.

### Question 4. After Maven `process-resources`, `application.properties` still contains `${RUNTIME_FLAG:off}` — did filtering fail?

**Answer:** Not if it is a runtime Spring placeholder. The Spring Boot Maven parent uses **@...@** for Maven filtering to prevent conflicts. Only **@project.version@** was substituted from the POM in the example.

### Question 5. A resource lives in `src/test/resources` and tests pass. Is that resource guaranteed to be in the Boot JAR?

**Answer:** No. Test resources are copied to **target/test-classes** or **build/resources/test**, not packaged into the production JAR by default. If runtime code requires it, place it in main resources or configure packaging properly and verify with **jar tf**.

### Question 6. When should inspecting generated source shift to inspecting bytecode?

**Answer:** When a processor modifies AST/bytecode directly (like Lombok), when `.class` files do not map 1:1 to source files, or when confirming the compiler emitted the class. **javap** reveals signatures and bytecode, though without source info it does not prove which `.java` file was committed or generated.

## 19. Output Inspection Completion Checklist

- [ ] Identified the exact project/module, Maven/Gradle version, JDK, and task/phase executed.
- [ ] Distinguished **src/main/java**, **generated `*.java`**, **compiled `*.class`**, **processed resources**, and the **archive**.
- [ ] Maven: checked **target/generated-sources/annotations**, **target/classes**, and **target/test-classes** by phase.
- [ ] Gradle: checked **build/generated/sources/annotationProcessor/java/main**, **build/classes/java/main**, and **build/resources/main** by source set.
- [ ] For annotation processors, verified processor dependency/scope, generated source, and compiled implementation.
- [ ] Read post-filtering resource outputs rather than only reading templates in `src/main/resources`.
- [ ] Verified **BOOT-INF/classes** and **BOOT-INF/lib** inside the **exact JAR being deployed**.
- [ ] Verified classes and resources load via the classloader when running **java -jar**.
- [ ] Never edited generated outputs directly; updated sources/config and rebuilt instead.
- [ ] When outputs behaved unexpectedly, separated stale files, cache/incremental builds, and module/source-set selection.

**Conclusion:** Inspecting build output directories lets you observe the real journey of code and resources: **Java source → generated Java → bytecode**, alongside **resource processing**, converging into the **executable archive**. Once you know where each stage writes its files, you can explain any Spring Boot build issue with build evidence instead of guessing from an IDE or POM/`build.gradle`.
