# Distinguishing the JDK Running Maven or Gradle from the JDK Used to Compile

## 1. The Problem and Expected Outcomes

In a Java/Spring Boot project, saying "the machine is using Java 21" is **not enough** to conclude that source code is compiled by JDK 21 or that the application can only run on Java 21. Each stage can select a different Java version:

1. **Java running the build tool:** the JVM that launches Maven or Gradle; with modern Gradle you must also distinguish between the **client JVM** and the **daemon JVM**.
2. **Compile JDK (compiler/toolchain):** the JDK installation that supplies `javac` and tools for compilation tasks.
3. **Target Java release:** the language level, APIs, and bytecode version generated by the compiler, such as `--release 17`.
4. **JVM running tests and the application:** the environment that actually loads and executes the generated bytecode. It can differ from the JDK used for building and compiling.
5. **Maven/Gradle Wrapper:** how the project invokes the **selected Maven/Gradle version**; the wrapper is not equivalent to choosing the compile JDK.

**Correct example:** the machine has JDK 21 and JDK 17 installed; Maven runs on Java 21, Maven Toolchains selects `javac` from JDK 17, and the code is built with release 17. Or the Gradle daemon runs Java 21 while Gradle Java Toolchains provides JDK 17 for `compileJava` and `test`. There is no contradiction: these are distinct roles.

## 2. Quick Comparison Table

| Component | Question It Answers | Common Way to Choose | How to Verify |
| --- | --- | --- | --- |
| Maven JVM | Which Java are Maven and its plugins running on? | `JAVA_HOME`, `mvn`/`mvnw` scripts, IDE runner | `mvn -version` or `./mvnw -version` |
| Gradle client JVM | Which Java starts the `gradlew` script? | `JAVA_HOME`, `java` on `PATH`, IDE | `./gradlew --version`, check `Launcher JVM` on supported Gradle versions |
| Gradle daemon JVM | Which JVM executes build scripts and coordinates tasks? | Defaults to client; `org.gradle.java.home`, IDE, daemon JVM criteria | `./gradlew --version`, check `Daemon JVM` or daemon config/logs |
| Compile JDK | Which JDK does the actual `javac` belong to? | Maven Toolchains, Maven Compiler Plugin; Gradle Java Toolchains | Compiler/toolchain logs, `javaToolchains`, resolved compiler path |
| Target release | At which level are bytecode, Java syntax, and Java SE APIs? | `maven.compiler.release`, `options.release` | Build config and `javap -verbose` |
| Test JVM | Which Java runs the tests? | Maven Surefire/Failsafe config, Gradle `Test.javaLauncher` or toolchain | Test/task logs, fork/launcher config |
| Application JVM | When deploying/`java -jar`, which Java runs the app? | JRE/JDK in deployment environment, container base image, service runtime | `java -version` right in the runtime environment, runtime logs |
| Wrapper | Which build tool version does the project use? | `.mvn/wrapper/maven-wrapper.properties`, `gradle/wrapper/gradle-wrapper.properties` | `./mvnw -version`, `./gradlew --version` |

**Rule of inference:** `mvn -version` and `./gradlew --version` show the Java **running the build tool**; they do not by themselves prove the final `javac` version when a toolchain is configured. Conversely, class file version 61 only proves **target Java 17 bytecode**, not that `javac` was JDK 17.

## 3. Why Can the Build JDK and Compile JDK Differ?

```text
Shell / IDE / CI
    |
    +--> JAVA_HOME / PATH / IDE JVM
    |         |
    |         +--> Maven JVM (e.g., JDK 21)
    |         |         |
    |         |         +--> Maven Toolchains --> javac from JDK 17
    |         |
    |         +--> Gradle client JVM (e.g., JDK 21)
    |                   |
    |                   +--> Gradle daemon JVM (e.g., JDK 21)
    |                               |
    |                               +--> Java Toolchains --> javac from JDK 17
    |
    +--> Compiler: --release 17 --> .class major version 61
    |
    +--> JVM at deployment (e.g., JRE 17 or 21) --> runs application
```

Maven is a Java application. Without a separate JDK selection mechanism configured, the Maven Compiler Plugin typically uses the compiler bundled with the JDK running Maven. When **Maven Toolchains** is configured, *toolchain-aware* plugins can obtain tools from a different JDK. Maven itself continues running on the original JVM. Maven Toolchains does not automatically run every plugin on the chosen JDK: plugins must support toolchains or have their own configuration.

Gradle also runs on a JVM, but modern Gradle uses a **client** to accept commands and a long-lived **daemon** to execute builds. They can run on two different Java installations. Java tasks such as `JavaCompile`, `Test`, and `Javadoc` have their own toolchain properties; when using `java.toolchain` in the Java plugin, they are typically configured according to that toolchain. Custom plugins or tasks only use the corresponding JDK if they support it or are explicitly wired to the toolchain.

**Separating two configuration axes:**

- `JDK 17 used to compile` refers to **the toolset being invoked**.
- `--release 17` refers to **the compatibility level of the generated code**.

For example, JDK 21 can still use `javac --release 17` to produce Java 17 bytecode and validate calls against Java SE 17 APIs. Thus "target Java 17" **does not imply** "compiled with JDK 17." Conversely, selecting JDK 17 `javac` does not imply the production JVM is JDK 17.

## 4. `JAVA_HOME`, `PATH`, and Java Versions in the IDE

### Terminal

- `JAVA_HOME` usually points to the **JDK root directory**, e.g., a JDK 21 installation folder; its value is not the path to `bin/java`.
- `PATH` determines which `java`/`javac` executable the shell finds when invoked directly. If `JAVA_HOME` and `PATH` point to two different JDKs, `java -version` can differ from `mvn -version`.
- Maven/Gradle Wrapper scripts usually prefer a valid `JAVA_HOME`, otherwise they locate an available Java installation using script/OS mechanisms. IDE settings can override this selection.
- If a project uses a toolchain, the compiler may come from a JDK that **does not appear first on `PATH`**.

Useful inspection commands:

```bash
java -version
javac -version
mvn -version
./mvnw -version
./gradlew --version
```

Only use `./mvnw` when the project has a Maven Wrapper and `./gradlew` when the project has a Gradle Wrapper. On Windows, use `mvnw.cmd` and `gradlew.bat` respectively. `java -version` may print output to stderr; that is normal behavior.

On Linux/macOS, you can check `echo "$JAVA_HOME"`, `command -v java`, and `command -v javac`. In PowerShell, use `$env:JAVA_HOME`, `Get-Command java`, and `Get-Command javac`. Do not deduce the **build** compiler solely from these commands if the project uses a toolchain.

### IDE

In an IDE there are usually at least three independent settings: Project SDK/JDK (for the editor), **Maven Runner JRE/Gradle JVM** (used to run builds), and the toolchain described in `pom.xml`/`build.gradle`. Compiling via the IDE's Build button may go through an internal compiler or be delegated to Maven/Gradle depending on configuration.

Therefore, when **terminal builds succeed but the IDE fails**, compare the runner JVM, the wrapper being used, how the IDE imports toolchain settings, and the actual compile logs. The editor displaying "Project SDK 17" does not prove the Gradle daemon is running Java 17.

## 5. Maven: Running on JDK 21 While Compiling with JDK 17

### 5.1. Without Maven Toolchains

In a standard Maven project, the configuration:

```xml
<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>
```

tells the Compiler Plugin to generate bytecode and enforce Java 17 language/API compatibility. It **does not force Maven to start on JDK 17** and **does not force the compiler to be JDK 17**. If Maven runs on JDK 21 and no special compiler/toolchain is configured, compilation can use JDK 21's `javac` with `--release 17`.

You can enable `fork` along with `executable` so the Compiler Plugin uses a specific `javac` executable. However, this only affects the configured plugin; if you want multiple plugins (`compiler`, `surefire`, `javadoc`, etc.) to share a JDK choice, use **Maven Toolchains** when those plugins support it.

### 5.2. How Does Maven Toolchains Work?

1. Maven is launched with a JDK suitable for running **Maven and its build plugins**.
2. The Maven Toolchains Plugin locates a JDK matching the requirements, either from installed and discovered JDKs or via `~/.m2/toolchains.xml` in the traditional setup.
3. A toolchain-aware compiler plugin obtains the compiler from the selected JDK. Other supporting plugins can also use that JDK.
4. The compiler applies `--release` to constrain language features, APIs, and target bytecode.

Starting from Maven Toolchains Plugin 3.2.0, the `select-jdk-toolchain` goal automatically discovers JDKs. The approach below uses version 3.3.0 and requests a JDK version in the range `[17,18)` to select Java 17.x without selecting JDK 18 or 21.

### 5.3. Standalone Maven Example

Create the structure:

```text
jdk-separation-demo/
├── pom.xml
└── src/main/java/dev/demo/Hello.java
```

**`pom.xml`** — a simple Maven project, with no Spring Boot dependencies needed, to illustrate JDK selection:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <groupId>dev.demo</groupId>
    <artifactId>jdk-separation-demo</artifactId>
    <version>1.0.0</version>

    <properties>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <maven.compiler.release>17</maven.compiler.release>
        <toolchain.jdk.version>[17,18)</toolchain.jdk.version>
    </properties>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-toolchains-plugin</artifactId>
                <version>3.3.0</version>
                <executions>
                    <execution>
                        <goals>
                            <goal>select-jdk-toolchain</goal>
                        </goals>
                    </execution>
                </executions>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.16.0</version>
            </plugin>
        </plugins>
    </build>
</project>
```

**`src/main/java/dev/demo/Hello.java`**

```java
package dev.demo;

public record Hello(String text) {
    public static void main(String[] args) {
        System.out.println(new Hello("Hello from Java 17").text());
    }
}
```

`record` is modern Java syntax supported by JDK 17. Prerequisites to follow this example: a compatible Maven installation, JDK 21 to run Maven, and JDK 17 installed and discoverable by Maven Toolchains. Set `JAVA_HOME` for the **Maven runner** to JDK 21 according to your operating system before running; installation paths vary by machine.

Run:

```bash
mvn -version
mvn org.apache.maven.plugins:maven-toolchains-plugin:3.3.0:display-discovered-jdk-toolchains
mvn clean compile
java -cp target/classes dev.demo.Hello
javap -verbose target/classes/dev/demo/Hello.class
```

In the desired setup, `mvn -version` shows Maven running Java **21**, the discovery command lists JDK **17**, and the build log shows the Java 17 toolchain being selected. Running `Hello` produces exact stdout:

```text
Hello from Java 17
```

In the `javap -verbose` output, `Hello.class` has **`major version: 61`** (Java 17). This is evidence of the *target bytecode*, not independent proof of which JDK compiled it; proof of the compiler lies in the JDK path selected by Maven Toolchains and the compiler logs.

If JDK 17 is not auto-discovered, install the JDK or declare its location using a method supported by Maven Toolchains. **Do not change `<toolchain.jdk.version>` to 21 just to make the build green** if the requirement is to compile with JDK 17; doing so alters what you are verifying.

### 5.4. Maven Using `toolchains.xml` in Legacy Projects

Some projects use the `toolchains:toolchain` goal and the user file `~/.m2/toolchains.xml`, containing the toolchain type (`jdk`), version/vendor properties, and `jdkHome` pointing to the actual JDK. `pom.xml` declares the requirement, while each machine maps that requirement to its own JDK path. This file lives in the **build machine's** Maven configuration, not something the Maven Wrapper creates by default. You do not need to combine both the legacy mechanism and the new auto-discovery if one already meets your needs.

To debug a legacy build, inspect which toolchains goal is running, which `toolchains.xml` file is being read, and whether the compiler/test plugins truly support that toolchain.

## 6. Gradle: Daemon JDK and Java Toolchain Are Two Separate Layers

### 6.1. Up to Three JVMs/JDKs Can Be Involved

**Gradle client JVM:** the process started when invoking `gradle` or `./gradlew`; picks Java from the script, environment, or IDE.

**Gradle daemon JVM:** the process executing the build. Unless configured otherwise, it usually uses the same JDK as the client. It can differ via `org.gradle.java.home`, the IDE/Tooling API, or **Daemon JVM criteria** (`gradle/gradle-daemon-jvm.properties` in supported Gradle versions). When Daemon JVM criteria are present, they take precedence over `JAVA_HOME` and `org.gradle.java.home`.

**Java compilation toolchain:** the JDK used by the `compileJava` task. Configured in `java { toolchain { ... } }` and not meant to change the Gradle daemon JVM. This is the single most important distinction.

Example:

```text
Gradle client:   Java 21  <- JAVA_HOME
Gradle daemon:   Java 21  <- default or daemon config
compileJava:     JDK 17   <- java.toolchain
Test:            JDK 17   <- default launcher from Java toolchain
Artifact:        class file 61 (Java 17)
Production:      Java 17 or compatible Java 21
```

When Gradle is not run on a JVM supported by **that Gradle version**, the build can fail before the `compileJava` task is even created. The project's Java Toolchains **cannot fix an inability to run Gradle itself**. Consult the [Gradle–Java Compatibility Matrix](https://docs.gradle.org/current/userguide/compatibility.html) for your exact wrapper version, because the JDK supported for **running Gradle** and for **compiling** can have different thresholds.

### 6.2. Standalone Gradle Groovy DSL Example

Reuse `src/main/java/dev/demo/Hello.java` from Section 5; replace `pom.xml` with two files:

**`settings.gradle`**

```groovy
rootProject.name = 'jdk-separation-demo'
```

**`build.gradle`**

```groovy
plugins {
    id 'java'
}

group = 'dev.demo'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

tasks.withType(JavaCompile).configureEach {
    options.release = 17
}

tasks.register('runHello', JavaExec) {
    classpath = sourceSets.main.runtimeClasspath
    mainClass = 'dev.demo.Hello'
    javaLauncher = javaToolchains.launcherFor {
        languageVersion = JavaLanguageVersion.of(17)
    }
}
```

Explanation:

- `id 'java'`: creates the basic compilation, testing, and JAR tasks.
- `java.toolchain.languageVersion = 17`: selects JDK 17 for Java plugin tasks that support toolchains.
- `options.release = 17`: controls the target syntax/API/bytecode level; included to make Java 17 compatibility intent explicit.
- `runHello`: a custom `JavaExec` task using a JDK 17 launcher, because the JVM running the app can be chosen independently of the build JVM.

With a project that already has a **Gradle Wrapper** supporting JDK 21, and JDK 17 available:

```bash
./gradlew --version
./gradlew -q javaToolchains
./gradlew clean compileJava runHello
javap -verbose build/classes/java/main/dev/demo/Hello.class
```

The line printed by the application when `runHello` executes is:

```text
Hello from Java 17
```

Full Gradle output also contains task/build information and varies by version. `javap` should show `major version: 61`. `./gradlew -q javaToolchains` lists the JDKs detected by Gradle along with version/location details; in newer Gradle versions, `--version` also shows launcher/daemon JVMs. Inspect the `compileJava` task with `--info` when you need to confirm which compiler is being used.

If the machine lacks JDK 17 and no toolchain provisioning repository is configured, Gradle may report "No matching toolchains found." Toolchains **do not download JDKs by default in every project**; automatic downloading requires a properly configured repository resolver. Do not arbitrarily lower or raise `languageVersion` to mask a missing JDK error.

### 6.3. Selecting Java for Individual Tasks

Project-level Java Toolchains cause standard `JavaCompile`, `Test`, and `Javadoc` tasks to use the same version by Gradle convention. However, you can intentionally run tests on JDK 21 while compiling with JDK 17 by configuring `Test.javaLauncher`:

```groovy
tasks.withType(Test).configureEach {
    javaLauncher = javaToolchains.launcherFor {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
```

This is an **additional snippet**, not a standalone build script. The result is that `compileJava` uses JDK 17 while the test task is configured to use JDK 21. This scenario is useful when verifying whether an application compiled for Java 17 can run on a newer runtime environment. Do not mistake the **test-running JDK** for the **compile JDK**.

## 7. What Do Maven/Gradle Wrappers Do and Not Do?

`mvnw`/`mvnw.cmd` together with `.mvn/wrapper/` ensure the project uses the **Maven** version it specifies, including downloading the Maven distribution if needed. `gradlew`/`gradlew.bat` together with `gradle/wrapper/gradle-wrapper.properties` ensure the project uses the specified **Gradle** version. Thus using a wrapper reduces cases where machine A runs a different Maven/Gradle version than machine B.

However, the Maven/Gradle version and the JDK version are **two separate decisions**. Wrappers normally do not set `java.toolchain` or select `maven.compiler.release`. Consistent builds require all three: **build tool version**, a compatible **JDK running the build tool**, and an explicitly declared **compile JDK/release**. Gradle Daemon JVM criteria are an additional mechanism for standardizing the JVM running the daemon, distinct from the Gradle Wrapper and distinct from the Java compilation toolchain.

Example on CI:

```text
CI provides JDK 21  -->  runs ./mvnw or ./gradlew
Project pins Maven/Gradle version with Wrapper
Project selects JDK 17 for compiler with Toolchains
Compiler produces major 61 class files for Java 17
CI runs tests with configured JDK
Release runs on Java 17+ if all dependencies/APIs are compatible
```

Do not use `java -version` output from a developer's laptop as proof of the same environment in **CI or containers**. `JAVA_HOME`, JDK paths, daemons, and environments can differ.

## 8. What Else Should You Check in Spring Boot?

With Spring Boot, you must also account for the **Java requirement to run the build tool and plugins**. For instance, a Spring Boot plugin version may require Java 17 or higher just for the plugin itself to work. When Maven/Gradle is running on a lower Java version than the plugin requires, setting the compiler toolchain to Java 17 **will not fix the plugin-loading failure up front**.

Conversely, if the Spring Boot plugin can run on Java 21, you can still choose a JDK 17 toolchain to compile the application targeting Java 17, provided the Spring Boot/dependency versions also support Java 17. Do not assume all Spring Boot lines share the same minimum Java; check [Spring Boot System Requirements](https://docs.spring.io/spring-boot/system-requirements.html) for the **exact version you are using**.

Packaging Spring Boot via `spring-boot-maven-plugin:repackage` or Gradle `bootJar` primarily creates an executable archive. Having the Boot loader and runtime dependencies inside the JAR **does not change** the Java requirements of the compiled classes or the Spring Boot runtime. `java -jar` actually uses the deployment environment's JVM, not a "compile JDK" embedded inside the JAR.

Also watch other plugins such as Kotlin, annotation processors, bytecode enhancement, code generation, and test plugins: some run inside the build JVM, some spawn separate processes, and some use toolchains. If a build has a JDK mismatch, inspect **each plugin/task individually** rather than assuming the `JavaCompile` mechanism applies to every task.

## 9. Distinguishing `source`, `target`, `release`, and Toolchains

| Option | What It Actually Controls | What It Does Not Guarantee |
| --- | --- | --- |
| `maven.compiler.source` or `-source` | Allowed Java syntax | Does not specify which JDK runs the compiler; does not guard against newer Java APIs |
| `maven.compiler.target` or `-target` | Target bytecode version | Does not automatically block calling new APIs when compiling on a newer JDK |
| `maven.compiler.release` or `javac --release` | Syntax, bytecode, and public APIs of the target Java SE release | Does not force the compiler executable to come from the same major JDK |
| Gradle `options.release` | The `--release` flag for `JavaCompile` | Does not change the JVM running the Gradle daemon |
| Gradle `sourceCompatibility`/`targetCompatibility` | Source/bytecode level via legacy mechanism | Does not guarantee public API restriction like `--release` |
| Maven Toolchains / Gradle Java Toolchains | Selects the **actual JDK** supplying Java tools | Does not automatically select the production server's JVM environment |

**API trap example:** code calling an API introduced only in Java 21, configured with `source=17` and `target=17` and compiled with JDK 21 `javac`, can compile into Java 17 classes and then fail when running on Java 17. Configuring `--release 17` checks target Java SE APIs and usually catches this at compile time. Even so, `--release` does not replace compatibility checks for third-party libraries, JNI setups, native images, or other runtime dependencies.

How to read a class file: `javap -verbose ...` prints `major version`. Common milestones: **Java 8 = 52**, **Java 11 = 55**, **Java 17 = 61**, **Java 21 = 65**. Running major 65 classes on Java 17 (which only understands up to major 61) can raise `UnsupportedClassVersionError`. If major 61 classes run on Java 21 and still fail, the cause may lie in APIs, dependencies, plugins, or runtime rather than the class version.

## 10. Ordered Diagnosis

When encountering a "Java version" error in a project, follow this sequence to avoid changing the wrong setting:

1. **Locate the failing layer:** did the error occur before the build script, inside a plugin, at `compileJava`/`maven-compiler-plugin`, during tests, or on `java -jar`?
2. **Check the wrapper:** run `./mvnw -version` or `./gradlew --version`; note the Maven/Gradle version and the Java running the tool. If there is no wrapper, check the global installation.
3. **Check the Gradle coordinating JVMs:** check Launcher JVM and Daemon JVM, `org.gradle.java.home`, or daemon JVM criteria; the IDE may use a different JVM than the terminal.
4. **Check the compiler JDK:** for Maven, check `mvn ...:display-discovered-jdk-toolchains`, `mvn -X compile` logs, and toolchain plugins; for Gradle, check `./gradlew -q javaToolchains` and `./gradlew compileJava --info`.
5. **Check target release:** locate `maven.compiler.release`, `options.release`, and `source`/`target` settings; use `javap -verbose` to confirm post-build bytecode.
6. **Check test and production JVMs:** inspect `Test.javaLauncher`, Surefire/Failsafe, Dockerfile/base image, and the real deployment environment. Do not treat `java -version` on a laptop as proof of a container's JVM.
7. **Fix the right configuration layer:** if a plugin fails to run, change the build JVM or plugin version; if JDK 17 is not found, install/configure the toolchain; if Java 21 APIs fail under target 17, fix the code or adjust the release per product requirements; if runtime fails, verify the deployment JRE/JDK and dependencies.

### Quick Symptom Guide

| Symptom | Likely Cause to Check | Appropriate Action |
| --- | --- | --- |
| `mvn -version` shows Java 21 but a Java 17 artifact is needed | Not necessarily an error; Maven JVM differs from compiler/release | Check toolchain and `maven.compiler.release=17` |
| `./gradlew --version` shows Java 21 daemon but `compileJava` needs JDK 17 | Daemon JVM and compilation toolchain differ | Set `java.toolchain=17`, inspect `javaToolchains` |
| `No matching toolchains found` | No matching JDK available or provisioning not configured | Install JDK, configure installation paths or auto-provisioning |
| `invalid target release: 21` or `release version 21 not supported` | Actual compiler is too old for the requested release | Select a sufficiently new compiler JDK; check plugins/toolchains |
| `UnsupportedClassVersionError` when running the app | Runtime JVM is older than the generated class file version | Use a newer runtime or rebuild with a compatible release |
| IDE fails while terminal builds cleanly | IDE runner JDK, Gradle daemon, or wrapper differs | Align JDK paths and tool versions; inspect the actual task |
| `source=17,target=17` is set yet `NoSuchMethodError` occurs on Java 17 | Newer Java API used at compile time or mismatched runtime dependency | Use `--release 17`, check resolved dependencies and runtime |
| Boot plugin fails before the compile step | JVM running the build does not meet the plugin's requirements | Switch the JVM running Maven/Gradle appropriately, not just the toolchain |

## 11. Self-Check Exercises

**Exercise 1.** `mvn -version` reports Java 21; the POM has `maven.compiler.release=17`. Is `javac` guaranteed to be JDK 17? **No.** Without a dedicated toolchain, the compiler could be from JDK 21 using `--release 17`.

**Exercise 2.** The Gradle daemon runs Java 21, while `java.toolchain.languageVersion=17`. Which JDK will `compileJava` use? **JDK 17**, if the toolchain is found and the task uses the standard toolchain.

**Exercise 3.** `javap` reports `major version: 61`. Does that prove Maven/Gradle ran on Java 17? **No.** It only proves the class file targets Java 17.

**Exercise 4.** Switching `JAVA_HOME` from 17 to 21 automatically switches the Java compiler of a project configured with toolchain 17 to JDK 21? **No.** The compiler still follows the toolchain if configured and working; the JVM running the build may change.

**Exercise 5.** The Maven Wrapper uses the exact required Maven version, but a plugin running on Java throws `UnsupportedClassVersionError` right when Maven loads the plugin. Will editing `maven.compiler.release` help? **No.** You must inspect the JVM running Maven and the plugin's Java requirements.

**Exercise 6.** A Spring Boot JAR is packaged by a JDK 21 Gradle daemon with class major version 61. Must production run JDK 21 because the daemon used 21? **No.** The runtime must satisfy the Java level of the application, Spring Boot, and dependencies; the daemon version does not directly dictate the runtime level.

## 12. Practical Project Checklist

- [ ] Project uses a wrapper to standardize the Maven/Gradle version.
- [ ] The JDK running Maven/Gradle meets the exact requirements of the build tool and build plugins.
- [ ] The compiler JDK is intentionally selected via toolchains, especially when multiple JDKs exist on machines/CI.
- [ ] The target release is declared with `--release` when Java compatibility is required.
- [ ] IDE, terminal, CI, and containers each have a way to verify actual versions.
- [ ] The test JVM is clearly specified if there is a runtime version matrix.
- [ ] The artifact is checked for class major version and tested on the target runtime environment.
- [ ] `JAVA_HOME`, wrapper version, compiler JDK, and runtime JDK are never conflated into a single concept.

**Remember:** **Build-running JDK ≠ compiler JDK ≠ target Java release ≠ application-running JVM.** Maven Toolchains and Gradle Java Toolchains let you pick the compile JDK independently; `--release` controls code compatibility; the wrapper controls the build tool version.
