# Generating Build Information with Gradle springBoot.buildInfo and bootBuildInfo

## Objectives and context

A Spring Boot application has been built and deployed successfully, yet when inspecting logs or management endpoints, the operations team still needs to answer very practical questions:

- Which version of the application is running: `0.0.1-SNAPSHOT`, `1.2.3`, or something else?
- Which module produced the artifact when the repository has multiple modules?
- What are the artifact's group, application name, and release channel?
- What timestamp was recorded as the **build time**, and why can it slow down builds or hinder reproducibility?
- Is the metadata file actually inside the **released JAR/WAR**, or only in the local build directory?
- How does Spring Boot Actuator read and publish metadata? Does the `/actuator/info` endpoint require configuration?
- When CI or a developer runs `bootBuildInfo` on its own, does it generate the right file and get wired into the `bootJar` task?

The Spring Boot Gradle Plugin provides a built-in solution: declaring `springBoot { buildInfo() }` configures the `bootBuildInfo` task, which generates **`META-INF/build-info.properties`**. Spring Boot can read the file into a `BuildProperties` bean; if the application uses Actuator, `BuildInfoContributor` can expose that information on the `/actuator/info` endpoint.

After this lesson, you will be able to:

1. Distinguish the **Gradle DSL `springBoot.buildInfo`** from the **`bootBuildInfo` task**, understanding what registers the task and when it runs.
2. Explain the five default properties `build.artifact`, `build.group`, `build.name`, `build.version`, and `build.time`.
3. Configure metadata file generation in Gradle Groovy DSL and Kotlin DSL, add custom properties, and modify or exclude default properties.
4. Understand the output location in **Spring Boot 3.3**, how it enters the main source set, and its location inside an executable JAR/WAR.
5. Use Java 17+ and Spring Boot Actuator to read `BuildProperties`, and verify `/actuator/info` and a simple application endpoint.
6. Analyze why the default `build.time` keeps `bootBuildInfo` from being `UP-TO-DATE`, along with its impact on `test`, `bootJar`, and build reproducibility.
7. Diagnose missing files, stale metadata, missing `BuildProperties` beans, `/actuator/info` returning empty or 404, or CI releasing the wrong artifact.

**Versions used in examples:** Spring Boot **3.3.13**, Java **17**, and a compatible Gradle **8.x**. Plugin and task configurations change across Spring Boot generations, so always consult the documentation for the **exact version**. The `build/...` paths in this lesson follow **Spring Boot 3.3** conventions and may not match paths documented for Spring Boot 4.x.

## 1. What is build metadata? How does it differ from runtime information?

**Build metadata** is information embedded into the artifact **at build time**, such as the project's name/group/version, creation timestamp, and custom release properties.

An illustrative `build-info.properties`:

```properties
build.artifact=build-meta-demo
build.group=com.example
build.name=build-meta-demo
build.version=0.0.1-SNAPSHOT
build.time=2026-11-09T08:30:00Z
```

**This is simulated content**, not a file generated by a project. The `build.time` value changes with the time of build, so never copy a sample timestamp into real reports.

| Field | Meaning | Default source with Gradle Boot Plugin |
| --- | --- | --- |
| `build.artifact` | Base name of the packaged artifact | Base name of the `bootJar` or `bootWar` task |
| `build.group` | Gradle `project.group` | `group` declared in the build script |
| `build.name` | Gradle project/module name | `project.name` |
| `build.version` | Gradle project version | `project.version` |
| `build.time` | Build timestamp recorded by the plugin | Instant at build time |

**Do not confuse** `build.name` with `spring.application.name`. `build.name` comes from the Gradle project, whereas `spring.application.name` is Spring runtime configuration. The two values can match if you configure them that way, but they do not sync automatically.

**Do not confuse** `build.time` with uptime, deployment time, or app startup time. The build time recorded in the file can be days older than deployment time. During a rollback, you may deploy an older artifact today; its `build.time` remains the metadata of that older artifact.

Build info is also not a **Software Bill of Materials (SBOM)**, CVE list, artifact signature, or provenance attestation. It helps with identification and cross-referencing, but does not by itself verify quality, security, or cryptographic origin.

## 2. Relationship between `springBoot.buildInfo` and `bootBuildInfo`

### 2.1 One DSL declaration registers one task

In Gradle Groovy DSL:

```groovy
springBoot {
    buildInfo()
}
```

This block goes in the `build.gradle` of **the application project applying the Spring Boot Gradle plugin**. It is **not an immediate file-generation call**; during the Gradle configuration phase, the plugin registers and configures a task named **`bootBuildInfo`**.

This task is of type `org.springframework.boot.gradle.tasks.buildinfo.BuildInfo`. When executed, it writes Java properties content to:

```text
META-INF/build-info.properties
```

According to **Spring Boot Gradle Plugin 3.3** documentation, the standard output location is `META-INF` under the **main source set** resources output, typically:

```text
build/resources/main/META-INF/build-info.properties
```

The plugin also wires the Java plugin's `classes` task to depend on this metadata generation task if `classes` exists. Because `bootJar` packages the main source set outputs, the build-info file is carried into the archive as a classpath resource.

Diagram:

```text
build.gradle
  springBoot { buildInfo() }
                |
                v
    Gradle registers task bootBuildInfo
                |
        +-------+--------------------------+
        |                                  |
        v                                  v
 ./gradlew bootBuildInfo          classes depends on task
        |                                  |
        v                                  v
 build/resources/main/                ./gradlew bootJar
 META-INF/build-info.properties            |
                                           v
                              build/libs/build-meta-demo-...
                                  BOOT-INF/classes/
                                      META-INF/build-info.properties
```

The diagram shows the **primary dependencies**, not the entire Gradle task graph. In Spring Boot 3.3, the output location is as shown above. **Do not assume these paths apply to Spring Boot 4.x**: newer plugin docs describe a default output of `build/bootBuildInfo/META-INF/build-info.properties` and wire the source set resources to consume the task output accordingly.

### 2.2 Four conditions for metadata to reach the artifact

1. The `org.springframework.boot` Gradle plugin and `springBoot.buildInfo` configuration are present in the **right module**.
2. The `bootBuildInfo` task runs directly or is triggered via `classes`/`bootJar` per that version's wiring.
3. `META-INF/build-info.properties` is treated as a resource of the **main runtime classpath**.
4. The release stage uses the **exact executable JAR/WAR** containing the resource, not a plain JAR, stale artifact, or different module.

You can **still generate the file** using `bootBuildInfo` without Actuator. Actuator is simply a convenient mechanism to **read and expose build metadata at runtime**.

### 2.3 Difference between `bootBuildInfo` and `build`

`build` is a **Gradle lifecycle task** combining build/assemble/check; `bootBuildInfo` is a **resource-generating task**. It does not replace `compileJava`, `test`, `processResources`, or `bootJar`.

Running standalone:

```bash
./gradlew bootBuildInfo
```

usually only creates or updates the metadata file and related tasks, which is **not enough** to produce an executable Boot JAR.

Running:

```bash
./gradlew bootJar
```

produces the executable JAR for the application module while triggering the steps needed for classes/resources, including `bootBuildInfo` when configured.

If you run `./gradlew bootBuildInfo` and look in `build/libs` to find no JAR, do not conclude the task failed; you only invoked the **metadata-generating task**, not the packaging task.

## 3. Complete Gradle Groovy DSL example

This hands-on exercise uses a simple Spring Boot web application with an endpoint to check the build version, alongside Actuator to inspect the metadata file.

### 3.1 Project structure

```text
build-meta-demo/
├── settings.gradle
├── build.gradle
├── gradlew / gradlew.bat           (if Gradle Wrapper was generated)
├── gradle/wrapper/...
└── src/
    ├── main/
    │   ├── java/com/example/buildmeta/
    │   │   ├── BuildMetaApplication.java
    │   │   └── BuildMetadataController.java
    │   └── resources/
    │       └── application.properties
    └── test/
        └── java/com/example/buildmeta/BuildMetadataTest.java
```

If the project does not have a Gradle Wrapper yet, generate one with an installed Gradle **compatible with Boot 3.3**, e.g. `gradle wrapper --gradle-version 8.5`. Use wrappers generated from trusted sources; do not download arbitrary Gradle scripts from the Internet. In PowerShell, replace `./gradlew` with `.\gradlew.bat`.

### 3.2 `settings.gradle`

```groovy
rootProject.name = 'build-meta-demo'
```

### 3.3 `build.gradle` – complete version prioritizing reproducible builds

```groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.13'
    id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-actuator'

    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

springBoot {
    buildInfo {
        // Avoid changing timestamps on every run.
        excludes = ['time']

        // This entry is added as build.channel.
        properties {
            additional = ['channel': 'training']
        }
    }
}

tasks.named('test') {
    useJUnitPlatform()
}
```

This is a **complete build file** for the demo app using Java 17 and the code in the next section. In Gradle Groovy DSL, `springBoot { buildInfo { ... } }` both registers and customizes the `bootBuildInfo` task; you do not need another `springBoot { buildInfo() }` call in a separate block.

Component breakdown:

- `id 'org.springframework.boot'` registers the Spring Boot Gradle plugin for the current project.
- `id 'java'` sets up source sets and `classes`/`compileJava`/`processResources`/`test` tasks.
- `io.spring.dependency-management` manages dependency versions via Spring Boot dependency management; it is not the plugin that generates build info.
- `spring-boot-starter-web` builds an HTTP application with an embedded Servlet container.
- `spring-boot-starter-actuator` enables Actuator infrastructure, providing `BuildInfoContributor` and `BuildProperties` when a valid resource exists.
- `springBoot.buildInfo` registers the task generating `META-INF/build-info.properties`.
- `excludes = ['time']` suppresses `build.time`, reducing unstable inputs.
- `properties.additional` adds a custom key `channel`, written to the file with the **`build.` prefix**.
- `test.useJUnitPlatform()` runs JUnit Jupiter tests in `src/test/java` under Gradle's Java Test task.

**Do not confuse:** `excludes` on `buildInfo` takes **metadata field names** like `time`; it does **not** exclude dependencies, source code, or other files from the executable JAR. Nor is it Gradle's `configurations.exclude`.

### 3.4 Why exclude `time` right in the example?

Spring Boot Gradle Plugin 3.3 documents `build.time` as defaulting to the build timestamp. Changing on every invocation causes `bootBuildInfo` to **never be up-to-date**, forcing downstream tasks (potentially `test` and `bootJar`) to re-execute and making metadata output non-reproducible.

In this example we prioritize **builds with stable outputs** over knowing "what exact time the build just ran." Thus `time` is excluded right in the sample configuration. If a project needs build time for audit/release reasons, it can keep it, provided the performance and reproducibility costs are understood.

**Note:** excluding `build.time` alone is a **helpful step**, not proof that all JARs will be byte-for-byte identical; the result still depends on the compiler, build inputs, archive metadata, resolved dependencies, and custom tasks.

## 4. Runnable Java 17+ code proving build-info

### 4.1 Spring Boot main class

Create `src/main/java/com/example/buildmeta/BuildMetaApplication.java`:

```java
package com.example.buildmeta;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class BuildMetaApplication {

    public static void main(String[] args) {
        SpringApplication.run(BuildMetaApplication.class, args);
    }
}
```

This is a standard application class and cannot be run with plain `javac BuildMetaApplication.java` because it requires Spring Boot dependencies; use Gradle to compile and package.

### 4.2 Controller reading `BuildProperties` at runtime

Create `src/main/java/com/example/buildmeta/BuildMetadataController.java`:

```java
package com.example.buildmeta;

import org.springframework.boot.info.BuildProperties;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class BuildMetadataController {

    private final BuildProperties build;

    public BuildMetadataController(BuildProperties build) {
        this.build = build;
    }

    @GetMapping("/build/version")
    public String version() {
        return "version=" + build.getVersion()
                + ";channel=" + build.get("channel");
    }
}
```

This is **valid Java 17+ code in a Spring Boot project with Actuator/Web**. When the resource is generated properly and detected by Actuator AutoConfiguration, Spring provides a `BuildProperties` bean for constructor injection. `BuildProperties#getVersion()` returns the version string; `get("channel")` accesses the additional property read from `build-info.properties` (the `build.` prefix is stripped when constructing `BuildProperties`).

With the sample configuration, the expected response body of `GET /build/version` is:

```text
version=0.0.1-SNAPSHOT;channel=training
```

This is the output **of the Java method** for the example configuration, not the entire Spring Boot startup stdout. The server also prints its banner/logs and the port may differ if overridden by the environment.

**Important:** this constructor injection **intentionally requires `BuildProperties`**. If you remove `buildInfo` or Actuator so no bean exists, the application may **fail to start** due to a missing bean. That helps the lab catch errors early; in real projects, if metadata is optional, design an explicit fallback or use `ObjectProvider<BuildProperties>` instead of silently making the app depend on optional metadata.

### 4.3 Configuring `application.properties`

Create `src/main/resources/application.properties`:

```properties
spring.application.name=build-meta-demo

# The info endpoint is NOT exposed over HTTP by default.
management.endpoints.web.exposure.include=health,info

# With a build-info.properties resource, the build contributor is enabled by default
# in Spring Boot 3.3; declare it explicitly if you want readers to notice.
management.info.build.enabled=true
```

**Important distinction:** `BuildProperties` and `build-info.properties` **do not automatically expose `/actuator/info`**. In Spring Boot 3.3, only `health` is exposed over HTTP by default; `management.endpoints.web.exposure.include=health,info` adds `info`. When running in public production, endpoints must be reviewed and secured appropriately.

Do not set `management.endpoints.web.exposure.include=*` across all environments just to check a version, as other endpoints may leak internal information or permit administrative operations.

### 4.4 Test verifying the bean and properties

Create `src/test/java/com/example/buildmeta/BuildMetadataTest.java`:

```java
package com.example.buildmeta;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.info.BuildProperties;
import org.springframework.boot.test.context.SpringBootTest;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNull;

@SpringBootTest
class BuildMetadataTest {

    @Autowired
    private BuildProperties properties;

    @Test
    void exposesExpectedBuildMetadata() {
        assertEquals("build-meta-demo", properties.getArtifact());
        assertEquals("com.example", properties.getGroup());
        assertEquals("build-meta-demo", properties.getName());
        assertEquals("0.0.1-SNAPSHOT", properties.getVersion());
        assertEquals("training", properties.get("channel"));
        assertNull(properties.getTime());
    }
}
```

This test serves two goals: verifying `BuildProperties` exists in the Spring context, and checking that **the values match the sample `build.gradle`**. `assertNull(properties.getTime())` is valid because we excluded `time`; if you remove `excludes`, update the assertion accordingly.

The test alone does not prove the file **inside the executable JAR** is right, since tests can run against the main output classpath before `bootJar` creates the archive. Section 6 inspects the final artifact directly.

## 5. Running `bootBuildInfo` and inspecting the file on disk

### 5.1 Running the metadata task standalone

From the directory containing `build.gradle` and the Wrapper:

```bash
./gradlew bootBuildInfo --console=plain --info
```

Or on Windows PowerShell:

```powershell
.\gradlew.bat bootBuildInfo --console=plain --info
```

This command focuses on running the metadata task; **it is not the command to build the executable JAR**. In **Spring Boot 3.3**, the task output is expected at:

```text
build/resources/main/META-INF/build-info.properties
```

Check in Bash:

```bash
test -f build/resources/main/META-INF/build-info.properties
cat build/resources/main/META-INF/build-info.properties
```

Windows:

```powershell
Test-Path -LiteralPath "build\resources\main\META-INF\build-info.properties"
Get-Content -LiteralPath "build\resources\main\META-INF\build-info.properties"
```

With the sample project, **expected output based on the configured data** looks like:

```properties
build.artifact=build-meta-demo
build.group=com.example
build.name=build-meta-demo
build.version=0.0.1-SNAPSHOT
build.channel=training
```

**Line order may vary**, depending on how the task writes properties and how tools display them. What matters is that the key/value pairs are present. **`build.time` is absent** in the sample because of `excludes = ['time']`.

Do not treat the example as an actual file generated in your environment; always open the `bootBuildInfo` output of the project you are working on.

### 5.2 Running `bootBuildInfo` separately vs. `classes`

Run:

```bash
./gradlew classes --console=plain --info
```

According to Spring Boot Gradle 3.3 docs, when `buildInfo` is configured and the project applies the Java plugin, the `classes` task depends on `bootBuildInfo`. Thus running `classes` triggers generating the required file even if the user does not invoke `bootBuildInfo` directly.

However, do not assume every Gradle task depends on `bootBuildInfo`. For instance, `./gradlew help` mainly prints configuration info and has no reason to run the metadata generation task.

### 5.3 Distinguishing `bootBuildInfo` from `processResources`

`processResources` processes/copies `src/main/resources`. `bootBuildInfo` is a **resource-generating task** writing to the plugin-specified output location.

In Spring Boot 3.3, the plugin wires `classes` to depend on `bootBuildInfo` and the task writes to the resources output area. It does not require developers to manually create `src/main/resources/META-INF/build-info.properties`, nor to call `processResources.expand(...)` to splice version strings.

**Do not maintain two sources generating `META-INF/build-info.properties`**, such as keeping a manual file in `src/main/resources/META-INF` while also enabling `bootBuildInfo`, as that risks overwrites, stale files, or ambiguous task/output ownership.

### 5.4 When does `bootBuildInfo` report `UP-TO-DATE`?

With `time` excluded, if inputs and outputs do not change, subsequent runs **can** report:

```text
> Task :bootBuildInfo UP-TO-DATE
```

This is a **conditional illustrative output**. If group/name/version/additional values change, the file is deleted, the task implementation/plugin version changes, or something else alters the output, the task must re-run. `UP-TO-DATE` is an outcome evaluated by Gradle, not a flag you set on the task.

## 6. Packaging the executable JAR and inspecting ZIP contents

### 6.1 Building the right artifact

Run:

```bash
./gradlew clean test bootJar --console=plain
```

`clean` provides clean build outputs for this initial packaging exercise; **do not use `clean` in the up-to-date experiment** in Section 10. In the example, `bootJar` creates:

```text
build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar
```

This path follows conventions from `rootProject.name` and `version` in the build script; if a project sets a different `archiveBaseName`, `archiveVersion`, `archiveClassifier`, or `destinationDirectory`, use the actual output path.

### 6.2 Why does metadata live inside `BOOT-INF/classes`?

When `bootJar` packages an executable JAR, compiled classes and main resources go into `BOOT-INF/classes`. Since `META-INF/build-info.properties` is a **classpath resource** of the main source set, its path in the archive is typically:

```text
BOOT-INF/classes/META-INF/build-info.properties
```

The filesystem path before packaging and the path inside the archive differ:

| Stage | Location |
| --- | --- |
| `bootBuildInfo` task output, Spring Boot 3.3 default | `build/resources/main/META-INF/build-info.properties` |
| Classpath resource via main source set | `META-INF/build-info.properties` |
| Executable Boot JAR (typical Boot 3.3 layout) | `BOOT-INF/classes/META-INF/build-info.properties` |
| Executable Boot WAR if using `bootWar` | `WEB-INF/classes/META-INF/build-info.properties` |

**Do not look in `BOOT-INF/lib`**: that directory holds dependency JARs nested inside the executable archive. Build metadata is an **application resource**, not a library.

### 6.3 Inspecting with JDK `jar`

```bash
jar tf build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar
```

To verify the exact entry:

```bash
jar tf build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar \
  | grep -Fx 'BOOT-INF/classes/META-INF/build-info.properties'
```

If this outputs:

```text
BOOT-INF/classes/META-INF/build-info.properties
```

then **the ZIP entry exists**. That alone does not prove the values inside are right; you need to read the contents. On macOS/Linux with `unzip`:

```bash
unzip -p build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar \
  BOOT-INF/classes/META-INF/build-info.properties
```

The output should contain `build.version=0.0.1-SNAPSHOT` and `build.channel=training`, and **omit `build.time`**. Watch for Java properties escaping if custom values contain special characters.

If the JAR does not exist or you are inspecting a `-plain.jar`, the result will differ. Do not hardcode a single path for all modules.

### 6.4 Inspecting the archive in PowerShell

```powershell
$jar = "build\libs\build-meta-demo-0.0.1-SNAPSHOT.jar"

if (-not (Test-Path -LiteralPath $jar)) {
    throw "Executable JAR not found"
}

$entries = & jar tf $jar
if ($LASTEXITCODE -ne 0) {
    throw "Cannot list archive"
}

$matches = @($entries | Select-String -SimpleMatch "BOOT-INF/classes/META-INF/build-info.properties")
if ($matches.Count -ne 1) {
    throw "Build info entry not found exactly once"
}

Write-Output "PASS: build-info.properties entry found"
```

This is a **script that only checks ZIP entry presence**. To inspect contents, use a trusted ZIP extraction tool or .NET's ZIP API. Confirming a file exists **is not enough** to verify group/version/time; you must cross-check keys and values.

### 6.5 Distinguishing plain files from executable files

The Gradle Spring Boot plugin can produce **two JARs** if both `jar` and `bootJar` run:

```text
build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar          # executable Boot JAR
build/libs/build-meta-demo-0.0.1-SNAPSHOT-plain.jar    # plain JAR
```

By Boot Gradle 3.3 convention, the plain JAR uses the `plain` classifier to avoid name collisions. The plain file may place the resource at `META-INF/build-info.properties` near the root rather than in `BOOT-INF/classes`. Thus, grepping for `BOOT-INF/classes` on the plain JAR may FAIL even though the resource was packaged.

For this lesson, check the **exact Boot JAR that CI will deploy**, avoiding wildcards like `*.jar` that could match multiple outputs.

## 7. Runtime verification: `BuildProperties` and `/actuator/info`

### 7.1 Running the packaged artifact

In a first terminal:

```bash
java -jar build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar
```

With a compatible JDK and port 8080 free, the web app will start and stay running. Open another terminal:

```bash
curl --fail --silent --show-error http://localhost:8080/build/version
```

Expected response body based on the sample code:

```text
version=0.0.1-SNAPSHOT;channel=training
```

If the response differs, verify that you built the right file, whether the metadata came from another version, or if an environment setting overrode the Gradle project version. Do not assume an endpoint returning 200 proves the archive contains the right build info until you have read the key/value pairs.

### 7.2 Actuator info endpoint

Because the application includes `spring-boot-starter-actuator` and exposes `info`:

```bash
curl --fail --silent --show-error http://localhost:8080/actuator/info
```

Expected JSON **structural shape**:

```json
{
  "build": {
    "artifact": "build-meta-demo",
    "group": "com.example",
    "name": "build-meta-demo",
    "version": "0.0.1-SNAPSHOT",
    "channel": "training"
  }
}
```

This is a **configuration-based example**, not a guarantee of JSON key order or output captured from a real machine. `time` is absent because the task configured `excludes`. The endpoint may contain more fields if other `InfoContributor` beans are enabled or users add metadata.

### 7.3 Why might `/actuator/info` return `{}` or 404?

Different layers are involved:

| Symptom | Causes to check |
| --- | --- |
| HTTP 404 | Missing Actuator, `info` endpoint disabled/not exposed, wrong port, or wrong management base path |
| HTTP 401/403 | Security rules/authorization protecting the endpoint |
| HTTP 200 but `{}` | No `BuildProperties`, build contributor disabled, or no other info contributors |
| `build.version` in file but `/actuator/info` lacks `build` | Resource missing **on runtime classpath**, auto-configuration, or other contributor config |
| `/build/version` fails to start due to missing bean | Constructor requires `BuildProperties` but bean was not created |
| `/build/version` returns stale version | Running old artifact, stale Gradle output, deployed wrong module, or overridden metadata |
| `/actuator/info` has `build` without `time` | The example's `excludes=['time']` setting is working as intended |

In Spring Boot 3.3, only **`health`** is exposed over HTTP by default. To view `info`, set `management.endpoints.web.exposure.include=health,info` as in the example. If the app uses Spring Security, the endpoint is also subject to access controls. Do not fix security issues by exposing all of Actuator to the Internet.

### 7.4 Having the file vs. having the bean are two separate issues

`bootBuildInfo` is a **build plugin feature**, running at Gradle build time. `BuildProperties` is a **runtime bean** created by Spring Boot auto-configuration when the appropriate module and resource exist. `BuildInfoContributor` is an **Actuator component** that consumes that bean to expose info.

```text
Gradle build-time                      Spring runtime
-----------------                      --------------
springBoot { buildInfo() }            classpath:
      |                               META-INF/build-info.properties
      v                                      |
bootBuildInfo writes resource                v
      |                               BuildProperties bean
      v                                      |
bootJar packages resource into JAR           v
                                     BuildInfoContributor
                                             |
                                             v
                                      /actuator/info
```

Without `spring-boot-starter-actuator`, generating the metadata file does not automatically give you an Actuator endpoint. Conversely, adding the Actuator dependency without generating the resource will not make `build-info.properties` appear by itself.

## 8. Customizing default properties

### 8.1 Overriding artifact, group, name, or version

The plugin exposes `properties` on `buildInfo` to override defaults. **Replacement snippet** for the `springBoot` block in `build.gradle`:

```groovy
springBoot {
    buildInfo {
        excludes = ['time']
        properties {
            artifact = 'release-app'
            group = 'com.example.platform'
            name = 'Release Application'
            version = '1.2.3'
        }
    }
}
```

In this case, the metadata output can contain:

```properties
build.artifact=release-app
build.group=com.example.platform
build.name=Release Application
build.version=1.2.3
```

These are **overridden values**; they do not prove that `project.version` or the JAR filename changed along with them. If the actual build script still has `version='0.0.1-SNAPSHOT'`, you can end up with **a JAR file carrying version A while build-info carries version B**. That may be intentional, but is usually a sign of conflicting configuration.

To keep them aligned, prefer managing Gradle `group`/`version` and archive naming from a controlled single source; only override metadata when there is an explicit convention and CI consistency check.

### 8.2 Excluding one or more fields

Example:

```groovy
springBoot {
    buildInfo {
        excludes = ['time']
    }
}
```

`excludes` accepts **field names without the `build.` prefix**. For example use `time`, **not** `build.time`, inside `excludes`.

You can also exclude other fields such as `name` if you truly do not want to record it, though at runtime `BuildProperties#getName()` may return `null`. If a field is a required startup dependency, do not exclude it arbitrarily without updating application/test contracts.

**Do not confuse metadata exclusions with dependency exclusions**. It does not prevent `spring-boot-starter-actuator` or other JARs from being packaged.

### 8.3 Adding custom properties

Example:

```groovy
springBoot {
    buildInfo {
        excludes = ['time']
        properties {
            additional = [
                'channel': 'training',
                'flavor': 'community'
            ]
        }
    }
}
```

In the output file, custom keys are written with the `build.` prefix:

```properties
build.channel=training
build.flavor=community
```

In Java when using `BuildProperties`, access `build.get("channel")` and `build.get("flavor")`, not `build.get("build.channel")`. Actuator can expose them under the corresponding `build` object.

Never put `password`, `privateKey`, `API_TOKEN`, database passwords, sensitive internal URLs, or unnecessary user/machine identities into metadata. The file resides **inside the executable archive** and may be published over the info endpoint if enabled. HTTP security configuration does not remove data already packaged inside the JAR.

### 8.4 Providers for CI-supplied values

A value can be computed **lazily** via the Gradle Provider API to avoid reading the environment too early. The Spring Boot 3.3 Gradle Plugin supports additional property values backed by Providers. **Replacement snippet for the `springBoot` block**, used only if CI defines the corresponding environment variable:

```groovy
def releaseChannel = providers.environmentVariable('RELEASE_CHANNEL')
    .orElse('local')

springBoot {
    buildInfo {
        excludes = ['time']
        properties {
            additional = ['channel': releaseChannel]
        }
    }
}
```

When `RELEASE_CHANNEL=qa`, the expected output is `build.channel=qa`; when the variable is unset, it falls back to `local`.

Advantage of Provider: Gradle tracks inputs/lazy evaluation cleanly compared to ad hoc `System.getenv` calls scattered around that hide impacts on outputs. Still, **whenever the CI variable actually changes, the resource changes too**; having `bootBuildInfo` re-run can be **correct** behavior, not a performance bug.

**Do not use a value that changes on every run, such as a random build number**, if your goal is reproducible artifacts and you do not truly need that value. If build number is part of release identity, accept that it alters output and record provenance accurately.

### 8.5 Commit ID is not automatically included in `buildInfo`

`build-info.properties` and `git.properties` are **two different kinds of metadata**:

- `build-info.properties` comes from the `bootBuildInfo` task.
- `git.properties` typically requires a dedicated Git information plugin/mechanism; `BuildProperties` does not automatically scan a Git repository for commits.
- `GitProperties`/`GitInfoContributor` are how Spring Boot/Actuator read Git metadata when that file is on the classpath.

If an organization wants to record a commit in `buildInfo.properties` via `additional`, it must pass the commit value into task inputs reliably and ensure no sensitive info is exposed. Never fabricate a "commit hash" from the build date or use the version as a placeholder.

## 10. `build.time` and its impact on up-to-date and reproducible builds

### 10.1 Why is the default build time special?

Spring Boot Gradle 3.3 documentation warns that `build.time` defaults to **the instant the project is built**. This value differs across runs, causing:

```text
./gradlew bootJar
    |
    v
bootBuildInfo creates build.time=T1
    |
    v
classes/resource output changes
    |
    v
bootJar/JAR may change

./gradlew bootJar  (no Java changes)
    |
    v
bootBuildInfo creates build.time=T2
    |
    v
metadata file changes even though source is unchanged
    |
    v
dependent tasks must consider re-running
```

This does **not** mean Gradle fails to support up-to-date checks. The task is behaving properly given a **constantly changing time input**; the real question is whether your project genuinely needs a new build timestamp inside the artifact every single time.

If you always generate `build.time=now()`, two builds from identical source code can yield two different `build-info.properties` files, making the executable archives differ byte-for-byte. That harms reproducibility, build caching, and downstream work such as tests and JAR packaging.

### 10.2 Comparing the two configurations

**Experiment A — keeping the default time**:

```groovy
springBoot {
    buildInfo()
}
```

Run twice:

```bash
./gradlew bootBuildInfo --console=plain --info
./gradlew bootBuildInfo --console=plain --info
```

According to Spring Boot 3.3 docs, the build-info task is **never up-to-date** with a changing default time. You can inspect `build.time` in the output after two runs; exact timestamp format/precision depends on how the plugin writes it.

**Experiment B — excluding time**:

```groovy
springBoot {
    buildInfo {
        excludes = ['time']
    }
}
```

Run twice **without `clean`**:

```bash
./gradlew bootBuildInfo --console=plain --info
./gradlew bootBuildInfo --console=plain --info
```

If nothing else changed, the second run **can** report `UP-TO-DATE`. `build-info.properties` will also omit `build.time`. Inspect both the task outcome and file contents rather than merely comparing wall-clock durations.

### 10.3 Why not use `clean` when measuring up-to-date?

`./gradlew clean bootBuildInfo` deletes build outputs before the task runs. After `clean`, the task has no previous output for a local up-to-date check. If the build cache is enabled, a cacheable task may report `FROM-CACHE`, which is a **different mechanism**.

To demonstrate `UP-TO-DATE` behavior, run **the same task twice in a row without `clean` and without editing the build script**. To verify an artifact from a clean state, run `clean bootJar` **as a separate run**, without mixing the two measurements.

### 10.4 Build time can matter for operations

Some systems require packaging/release timestamps for audits. In that case, **do not strip `time` solely to optimize builds** at the expense of business requirements. Consider:

- Distinguishing build timestamps from deployment timestamps in release management systems.
- Using a **fixed release value** if the workflow has a trusted time source and the plugin version supports configuring it appropriately.
- Avoiding undeclared dynamic timestamps in custom tasks.
- Checking `BuildProperties#getTime()` compatibility: it returns `Instant` when parseable, or `null` when absent/unparseable.
- Documenting that if timestamps are intentionally kept, task invalidation and non-reproducible artifacts from identical inputs are expected trade-offs.

An ISO-8601 `build.time` aids lookup, but **does not prove deployment time or Git commit time**. Record timestamps according to a clear convention.

### 10.5 Build cache vs. up-to-date

| Mechanism | Indicator | Main condition |
| --- | --- | --- |
| Up-to-date | `bootBuildInfo UP-TO-DATE` | Current workspace inputs/outputs still match local execution history |
| Build cache | `bootBuildInfo FROM-CACHE` if task is cacheable and key hits | Matching cached outputs exist |
| Normal execution | `bootBuildInfo` with no label | Inputs changed or outputs are ineligible for reuse |
| Clean build | May execute or restore from cache | Local build outputs were deleted; do not assume "everything recompiled" |

Do not assume every version of the `BuildInfo` task is cacheable; verify actual task outcomes and plugin docs. Only enable build caching for tasks with complete input/output tracking and metadata free of sensitive data unsuitable for sharing.

## 11. Multi-module Gradle: which module owns the task?

Suppose:

```text
project/
├── settings.gradle
├── app/
│   ├── build.gradle
│   └── src/main/java/...
└── core/
    ├── build.gradle
    └── src/main/java/...
```

`settings.gradle`:

```groovy
rootProject.name = 'platform'
include 'app', 'core'
```

If `:app` is the Spring Boot **executable application**, normally only **`app/build.gradle`** needs to apply the Spring Boot plugin and `springBoot { buildInfo() }`. `:core` is a Java library consumed by the app and may only need `java-library`.

Run:

```bash
./gradlew :app:bootBuildInfo --console=plain
./gradlew :app:bootJar --console=plain
./gradlew :app:tasks --all
```

If invoking `./gradlew bootBuildInfo` from root fails to find the task at root, that does not mean build-info is broken; the task may live in subproject `:app`. Gradle may also match task names across multiple modules, so use a **qualified task path** when targeting a specific module.

### 11.1 Why avoid buildInfo in every library module?

An executable Spring Boot JAR bundles the **application module's** classes/resources along with dependencies. If an internal library `:core` generates its own `META-INF/build-info.properties` and the app generates one at the same path, the runtime classpath ends up with **multiple resources sharing the same path**. The classloader picks one based on classpath order, leading to unpredictable results.

Therefore, if the goal is **metadata for the released artifact**, generating one canonical build-info file in the **packaged application module** is much easier to govern. If each module needs its own metadata, use distinct resource names/paths and reading contracts rather than letting all modules compete for `META-INF/build-info.properties`.

### 11.2 Artifact name differing from project name

The `bootBuildInfo` task defaults `build.artifact` from the **base name of `bootJar`/`bootWar`**, while `build.name` defaults to `project.name`. If you set `bootJar.archiveBaseName` to `service-runtime` while `project.name` remains `app`, the two fields will differ.

Do not assume that is an error; verify expected artifact and metadata names against your module policy. Before using `build.version` as a release identity, cross-check it against Gradle project version, image tag, and deployment descriptors to prevent drift.

## 12. Common errors with `bootBuildInfo`

| Symptom | Causes to check | Resolution |
| --- | --- | --- |
| `Task 'bootBuildInfo' not found` | Missing `springBoot { buildInfo() }`/`buildInfo { ... }`, Boot plugin not applied, or task is in another module | Check `plugins`, `:app:tasks --all`, target the right project |
| `bootBuildInfo` succeeds but no JAR appears | Task only generates metadata, not packaging | Run `bootJar`/`bootWar` to produce the artifact |
| `build/bootBuildInfo` missing in Boot 3.3 | That output path belongs to newer plugin docs | For Boot 3.3 check `build/resources/main/META-INF/build-info.properties` |
| Local file exists but JAR lacks the entry | Wrong JAR/module selected, custom task graph/classpath, or excluded output | Check `bootJar`, `jar tf`, and main resources |
| `bootJar` has file but `/actuator/info` is `{}` | Missing Actuator/runtime contributor or resource not on classpath | Check starter, `BuildProperties` bean, and runtime classpath |
| `/actuator/info` HTTP 404 | Info endpoint not exposed or wrong port/base path | Expose `health,info` and inspect management server config |
| `/actuator/info` HTTP 401/403 | Security protecting the endpoint | Use proper authentication; do not expose all endpoints |
| Cannot inject `BuildProperties` | Missing resource, missing auto-configuration, or disabled bean | Check `META-INF/build-info.properties` and Actuator |
| `build.time` is absent | `excludes=['time']` | Expected behavior in this example |
| `bootBuildInfo` runs every time | Default `build.time` changes | If time is unneeded, exclude `time` and test two runs |
| Version inside differs from JAR filename | Metadata `properties.version` overridden differently from `project.version` | Align version sources and verify in CI |
| Metadata still shows old version | Running stale build, copied `-plain.jar` by mistake, or misconfigured task I/O | Run an intentional clean build and check the right artifact |
| Changed CI channel but file unchanged | Additional property/Provider not picking up value, or wrong module targeted | Check generated file, Gradle task inputs, and logs |
| Tests re-run constantly without Java edits | Changing time alters resources, triggering downstream tasks | Exclude `time` if appropriate or accept the cost |
| Properties contain `build.buildNumber` key | Additional names are prefixed with `build.` by the plugin | In build DSL name it `buildNumber` without adding the prefix |
| Build info leaks tokens/sensitive addresses | Pulled secret from env/CI into `additional` | Never put secrets in artifacts; change metadata and rotate leaked secrets |
| Two `build-info.properties` on classpath | Module/library or manual file colliding on path | Establish one canonical source and remove duplicates |
| Actuator shows unexpected Git commit | Git properties come from a separate mechanism | Check `git.properties`/Git plugin and the deployed artifact |
| `buildInfo` and Maven build-info mixed up | Confused Gradle DSL with Maven plugin goal | Use the right build tool and matching plugin |
| CI green yet image runs old version | Deploy stage used a different artifact than tested, or Docker cache/copy mistake | Check hash/tag and exact artifact path |
| Config uses Kotlin syntax in Groovy | DSL does not match `.gradle`/`.gradle.kts` file | Use the Groovy/Kotlin comparison table in Section 9 |

### Short diagnostic sequence

1. Identify the **module containing the application** and the correct build system.
2. Verify the Spring Boot Gradle plugin is applied to that module and `springBoot.buildInfo` is configured.
3. Run `:module:bootBuildInfo --info` and open the **output file** matching your Boot version.
4. Run `:module:bootJar` and use `jar tf` to verify the ZIP entry.
5. Inspect the **values** of `build.version`, `build.artifact`, `build.channel`, and the presence/absence of `build.time`.
6. Run `java -jar` on the exact inspected JAR and test `/build/version` and `/actuator/info`.
7. If an endpoint misbehaves, isolate bean, contributor, exposure, security, and config issues.
8. If builds are slow, run twice without `clean` and check `UP-TO-DATE`; do not toggle caches blindly.
9. Compare the artifact CI puts into the image/deploy against the verified artifact.

## 13. CI/CD: verifying metadata before release

### 13.1 Minimum policy

A release pipeline may require:

- `build-info.properties` must exist inside **the exact executable JAR being published**.
- `build.version` must match the release version authorized for deployment.
- `build.artifact` must match the expected module/app name.
- If policy prioritizes reproducible builds, `build.time` must be absent or fixed by convention.
- Additional metadata must contain no secrets/PII and must not be exposed over Actuator if risky.
- Build/release must promote **the exact single artifact file** from the verified stage; avoid rebuilding at deploy time with different inputs.
- HTTP `/actuator/info` is exposed and protected only when genuinely needed.

**Do not treat a timestamp or version string in build-info as a signature guaranteeing origin**. When strict provenance is required, combine checksums, artifact signing/attestation, SBOMs, and release policies.

### 13.2 Example Bash gate verifying an executable JAR

Using the project from Section 3:

```bash
#!/usr/bin/env bash
set -euo pipefail

artifact="build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar"
resource="BOOT-INF/classes/META-INF/build-info.properties"

if [[ ! -f "$artifact" ]]; then
    echo "FAIL: executable artifact missing"
    exit 1
fi

# Catch corrupt ZIP/JAR or wrong file.
entries="$(jar tf "$artifact")"

if ! printf '%s\n' "$entries" | grep -Fxq "$resource"; then
    echo "FAIL: build info resource missing in executable JAR"
    exit 1
fi

# Sample script uses unzip; if unavailable in CI,
# replace with a trusted ZIP/JDK tool.
metadata="$(unzip -p "$artifact" "$resource")"

if ! printf '%s\n' "$metadata" | grep -Fxq 'build.version=0.0.1-SNAPSHOT'; then
    echo "FAIL: unexpected build version"
    exit 1
fi

if ! printf '%s\n' "$metadata" | grep -Fxq 'build.channel=training'; then
    echo "FAIL: missing expected release channel"
    exit 1
fi

if printf '%s\n' "$metadata" | grep -Eq '^build[.]time='; then
    echo "FAIL: build.time should be excluded for this release"
    exit 1
fi

echo "PASS: Spring Boot build metadata verified"
```

Printed output **when all script checks pass**:

```text
PASS: Spring Boot build metadata verified
```

This is **expected output**, not proof the script ran on a real file. If the JAR/resource is missing, version/channel mismatches, or `time` appears when forbidden, the script prints FAIL and exits 1.

This gate fits **sample projects with simple ASCII property values**. For real Java `.properties` files containing escaped characters, line continuations, unicode escapes, or custom metadata, parse with Java `Properties.load` or a compliant parser rather than relying solely on `grep` to interpret the full syntax. In CI with automated version generation, pull the expected version from a controlled release source rather than hardcoding `0.0.1-SNAPSHOT`.

### 13.3 Checking artifact bytes and runtime

After the gate PASSES:

```bash
sha256sum build/libs/build-meta-demo-0.0.1-SNAPSHOT.jar
```

Record the checksum so the deploy stage can verify the exact artifact. When building a Docker image, verify that the Dockerfile/Buildpacks consume the **gate-verified executable JAR**, not a different file or a rebuild using different task/version settings.

Once an image is running, internal metadata at `/actuator/info` (when exposed under access control) helps cross-check the version against release records. However, matching version strings do not guarantee identical artifact bytes; use checksums/digests and provenance when needed.

## 14. Preventing release metadata from becoming a security risk

`META-INF/build-info.properties` inside an artifact is generally readable by anyone who holds the artifact. If Actuator `/info` is exposed, part of that data can also be served over HTTP.

**Safe to include:** group/artifact/name/version, public channel, or non-sensitive commit IDs per policy.

**Never include:** access tokens, private keys, database passwords, AWS credentials, CI bearer tokens, unpublished internal system addresses, or unnecessary personal information.

If the app uses Spring Security, the `info` endpoint can be protected; without Spring Security and with `info` exposed, anyone able to reach the HTTP endpoint can view it. Never assume public metadata is harmless simply because it says "info." Verify firewalls, auth, and exposure per environment.

**Note:** removing `info` from `management.endpoints.web.exposure.include` **does not strip metadata from the JAR**. If a secret was accidentally included, change how the artifact is built and follow secret-incident response rather than merely disabling the endpoint.
