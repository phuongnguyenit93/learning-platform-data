# Nested Library Limitations and How to Read Resources Inside an Archive

A Spring Boot application may run fine from an IDE or with `./gradlew bootRun` yet fail when run via `java -jar app.jar`: a class is not found, a resource cannot be read, or a library demands a `File` path and errors out. The reason is usually that a Spring Boot executable JAR uses **library JARs nested inside an outer archive**, and **classpath resources are not guaranteed to be filesystem files**.

This lesson explains Spring Boot Loader's mechanics, the real limitations of nested JARs, how to read resources portably, and how to verify them inside the packaged artifact.

**Core principle:** If you only need the resource's contents, use an `InputStream` or Spring `Resource`; **do not** convert a classpath URL into a `File` unless you know the resource actually lives on the filesystem. If a library requires a physical JAR, identify that exact library and use the appropriate unpack mechanism rather than extracting all dependencies.

The examples run with **Java 17**, **Spring Boot 3.3.5**, and a compatible Gradle version such as **8.7**. These are fixed versions for learning purposes, not claims about the latest release.

## 1. What Is a Nested Library in a Spring Boot Executable Archive?

An executable Spring Boot JAR generated by `bootJar` (Gradle) or `spring-boot:repackage` (Maven) has a common layout:

~~~text
application.jar
├── META-INF/
│   └── MANIFEST.MF
├── org/springframework/boot/loader/
│   └── ... Boot Loader classes ...
└── BOOT-INF/
    ├── classes/
    │   ├── com/example/app/Application.class
    │   ├── guide/message.txt
    │   └── application.properties
    ├── lib/
    │   ├── spring-boot-<version>.jar
    │   ├── spring-context-<version>.jar
    │   └── library-<version>.jar
    ├── classpath.idx  (may be present)
    └── layers.idx     (may be present)
~~~

This is a **diagram**, not verbatim output from `jar tf`. `<version>` is a placeholder for the real version.

- `BOOT-INF/classes/` contains compiled application classes and processed resources.
- `BOOT-INF/lib/` contains dependency JARs **nested inside the outer archive**.
- The Boot launcher sits where the Java launcher can find it to start up.
- `META-INF/MANIFEST.MF` records the launcher as `Main-Class` and the application main class as `Start-Class` in typical packaging.
- `classpath.idx`, if present, can specify the order in which nested JARs are added to the classpath when running the archive with the launcher.
- `layers.idx` helps split layers for container images; it **does not** turn libraries into ordinary directories at runtime.

For an executable WAR, the layout differs: `WEB-INF/classes/`, `WEB-INF/lib/`, and possibly `WEB-INF/lib-provided/`. Do not hard-code JAR's `BOOT-INF` paths for every WAR.

### Development Classpath vs. Archive Classpath

When running from an IDE/Gradle:

~~~text
build/classes/java/main/
build/resources/main/
~/.gradle/caches/.../spring-boot-3.3.5.jar
~/.gradle/caches/.../other-library.jar
~~~

Each dependency may be a **real JAR file** in the Gradle cache. After packaging, `other-library.jar` becomes **a ZIP entry** at `BOOT-INF/lib/other-library.jar` inside `application.jar`.

This explains an apparent paradox: Boot Loader successfully loads classes in the nested library, yet `new File("BOOT-INF/lib/other-library.jar")` opens nothing. A ZIP entry name **is not** an independent path on the filesystem.

## 2. How Does Boot Loader Start from a JAR?

The standard JVM supports classpaths from directories and ordinary JARs, but does not automatically provide a general classpath for all kinds of JARs inside other JARs. Spring Boot adds a launcher/class loader aware of its archive layout:

~~~text
java -jar application.jar
      |
      v
JVM reads META-INF/MANIFEST.MF
      |
      v
Main-Class = Spring Boot JarLauncher
      |
      +-- prepares BOOT-INF/classes/
      +-- accesses nested JARs in BOOT-INF/lib/
      +-- creates nested-JAR-capable class loader
      +-- reads application Start-Class
      |
      v
Application.main(String[] args)
      |
      v
SpringApplication.run(...)
~~~

In Spring Boot 3.3, the JAR launcher is typically `org.springframework.boot.loader.launch.JarLauncher`. Older Spring Boot generations may use different package names. Do not hard-code a launcher name based solely on a tutorial from a different version.

The loader maps entries of nested JARs to data offsets inside the outer archive, allowing classes/resources to be read without pre-extracting all dependencies. It also provides URL handling for nested archives within the Boot Loader environment. However, the class loader's capability **does not turn** a nested JAR into a `java.io.File` that every library can open.

Therefore, separate two questions:

1. **Can the class loader read the class/resource?** Verify via `getResourceAsStream` or an appropriate loader.
2. **Does a third-party library require a physical file?** Check APIs accepting `File`/`Path`/`JarFile(String)` and dedicated unpack requirements.

### Do Not Infer from `java.class.path`

With `java -jar`, the `java.class.path` property may only reflect the outer JAR path at the Java launcher layer. It **is not** a complete inventory of nested libraries visible to the Spring Boot application class loader. To prove a dependency is missing, inspect `BOOT-INF/lib` and attempt to load the class through the application class loader.

## 3. First Limitation: The Outer Entry of a Nested JAR Must Be `STORED`

In ZIP, `ZipEntry.STORED` means **the entry is uncompressed at the ZIP layer in question**; `ZipEntry.DEFLATED` means the entry is compressed.

According to Spring Boot Loader, **the ZIP entry of a nested JAR inside the outer archive must use `ZipEntry.STORED`**. Reason: the loader must seek directly to the nested archive's data by offset. If another packaging tool recompresses all outer entries as DEFLATED, random access may no longer work properly.

~~~text
application.jar  (outer ZIP)
    BOOT-INF/lib/library.jar   <-- outer entry: STORED
        com/example/X.class    <-- entries inside library.jar can still be DEFLATED
        data/default.json      <-- entries inside library.jar can still be DEFLATED
~~~

**Important:** there is no requirement to uncompress every class/resource inside a nested JAR. The `STORED` constraint applies to **the outer ZIP entry representing the entire nested JAR**; entries inside the library can remain normally compressed.

The Spring Boot Maven and Gradle plugins generate archives meeting this requirement. Risk increases when a CI/CD step, ZIP editor, or custom packaging script **repacks** the file after `bootJar`/`repackage` finishes. The name `BOOT-INF/lib/foo.jar` still appears in `jar tf`, yet the compression method may have changed.

**How to verify:** use Java `JarFile` with `ZipEntry#getMethod()` on the **outer JAR entries**, as in the complete tool in Section 9. Do not merely check the `.jar` extension.

## 4. Second Limitation: The System Class Loader Does Not Necessarily See Nested Libraries

Spring Boot launcher uses an application class loader for classes and nested JARs. In this model, `ClassLoader.getSystemClassLoader()` is not guaranteed to see classes inside `BOOT-INF/lib`.

Anti-pattern inside a Java method:

~~~java
Class<?> plugin = Class.forName(
        "com.example.plugins.Widget",
        true,
        ClassLoader.getSystemClassLoader());
~~~

This line can fail when running the executable archive, even though `Widget` is loaded normally by the application loader. This is an **illustration with a hypothetical class name**, not a standalone runnable program.

When looking up classes or resources belonging to the application context, it is usually best to use:

~~~java
ClassLoader loader = Thread.currentThread().getContextClassLoader();
Class<?> plugin = Class.forName(
        "com.example.plugins.Widget", true, loader);
~~~

Or use the class loader attached to a known application class. `Thread.getContextClassLoader()` is the approach adopted by many frameworks for compatibility with custom loaders. It does not conjure nonexistent classes into existence; `ClassNotFoundException` can still occur if the library is truly missing or excluded.

Some older libraries, SPI integrations, or code relying on the system class loader may require configuration or versions that support Boot Loader. Do not fix it by adding duplicate dependencies if the root cause is **picking the wrong loader**.

## 5. Third Limitation: A Classpath Resource Is Not a `File`

Common mistake:

~~~java
// Only safe when the URL actually points to a physical file.
URL url = getClass().getClassLoader().getResource("guide/message.txt");
File file = new File(url.toURI());
~~~

When running from an IDE, the URL might be `file:/.../build/resources/main/guide/message.txt` and conversion to `File` works. Inside a Boot executable JAR, the URL points to a resource **inside the archive**, with nested-JAR protocol/syntax varying across loader generations. It is not a filesystem URI.

The following approaches are **not** general ways to read classpath resources:

~~~java
new File("src/main/resources/guide/message.txt");
Path.of("BOOT-INF/classes/guide/message.txt");
Paths.get(resourceUrl.toURI());
~~~

- `src/main/resources` is a source directory in the repo and typically does not exist in deployment containers.
- `BOOT-INF/classes` is a path **inside the archive**, not a real process path.
- `Paths.get(resourceUrl.toURI())` depends on the corresponding filesystem provider; nested archive URLs are not necessarily understood by the default provider.

Symptoms can include `URI is not hierarchical`, `FileSystemNotFoundException`, `FileNotFoundException`, or accidentally reading a same-named file outside the archive.

**Solution:** if the application needs the resource's **contents**, read via an `InputStream` from the class loader or Spring `Resource`; do not require a filesystem path.

### Standard Java: `ClassLoader.getResourceAsStream`

If the file sits at `src/main/resources/guide/message.txt`, the resource name from the classpath root is `guide/message.txt`, even though when packaged it resides in `BOOT-INF/classes/guide/message.txt`.

~~~java
import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

static String loadMessage(ClassLoader loader) throws IOException {
    try (InputStream in = loader.getResourceAsStream(
            "guide/message.txt")) {
        if (in == null) {
            throw new IOException("Missing resource: guide/message.txt");
        }
        return new String(in.readAllBytes(), StandardCharsets.UTF_8).trim();
    }
}
~~~

This is an **illustrative method** and must be placed inside a suitable Java class. `readAllBytes()` is valid on Java 17; for large files, stream incrementally to avoid holding the entire file in RAM.

Guidelines:

- Do not prepend `BOOT-INF/classes/` to the classpath resource name.
- `ClassLoader.getResourceAsStream` normally takes a name **without a leading `/`**.
- Check for `null` when the file does not exist.
- Use `try-with-resources` to close the stream, even on errors.
- Specify the charset via `StandardCharsets.UTF_8` if the data is text.
- If multiple copies of a resource exist across JARs, `getResourceAsStream` opens only one per the class loader's logic; understand classpath order when name collisions matter.

### Difference Between `Class.getResourceAsStream` and `ClassLoader.getResourceAsStream`

~~~java
// Absolute from classpath root:
MyApplication.class.getResourceAsStream("/guide/message.txt");

// From classpath root; no leading slash:
MyApplication.class.getClassLoader()
        .getResourceAsStream("guide/message.txt");
~~~

In `Class#getResourceAsStream`, a leading `/` selects an absolute name, whereas without `/` it looks relative to the class's package. In `ClassLoader#getResourceAsStream`, use the resource name relative to the classpath root, normally **without** a leading `/`. Confusing this rule causes the resource to return `null` even when present in the JAR.

## 6. Spring Framework: `ClassPathResource` and `ResourceLoader`

Spring provides the `org.springframework.core.io.Resource` abstraction for reading data from the classpath, URLs, the filesystem, and other sources.

### Reading via `ClassPathResource`

~~~java
import java.io.InputStream;
import java.nio.charset.StandardCharsets;
import org.springframework.core.io.ClassPathResource;

ClassPathResource resource = new ClassPathResource("guide/message.txt");
try (InputStream in = resource.getInputStream()) {
    String message = new String(
            in.readAllBytes(), StandardCharsets.UTF_8).trim();
    System.out.println(message);
}
~~~

This is a **snippet inside a method declaring or handling `IOException`**, not a standalone Java class. It uses a stream without needing to know whether the resource resides in an IDE directory, ordinary JAR, or nested archive.

Avoid:

~~~java
new ClassPathResource("guide/message.txt").getFile();
~~~

`ClassPathResource#getFile()` is only valid when the resource resolves to a physical file (e.g., a built source set in a directory). For a resource in an unpacked JAR, it can fail. `getInputStream()` is more portable.

### Reading via `ResourceLoader`

~~~java
import java.io.IOException;
import java.io.InputStream;
import org.springframework.core.io.Resource;
import org.springframework.core.io.ResourceLoader;

public final class ConfigReader {
    private final ResourceLoader loader;

    public ConfigReader(ResourceLoader loader) {
        this.loader = loader;
    }

    public byte[] read() throws IOException {
        Resource resource = loader.getResource(
                "classpath:guide/message.txt");
        try (InputStream in = resource.getInputStream()) {
            return in.readAllBytes();
        }
    }
}
~~~

`classpath:` denotes a classpath resource, distinct from `file:/...` which points to a filesystem resource. This is a sample class and must be instantiated or injected in a Spring context. Do not use the `file:` prefix merely because the file sits in `src/main/resources` during development; the production archive will not have that source path.

| Need | Preferred API | Limitation |
| --- | --- | --- |
| Plain Java without Spring, known resource name | `ClassLoader.getResourceAsStream` | Returns null if missing |
| Internal Spring resource | `ClassPathResource#getInputStream` | `getFile()` is not always valid |
| Configurable source with explicit prefix | `ResourceLoader#getResource` | Must choose `classpath:`/`file:` properly |
| Need to list multiple resources with same name | `ClassLoader.getResources` | Order/listing depends on loader |
| Third party strictly requires `File` | Controlled copy to temp file or unpack dependency | Requires managing resources and file lifecycle |

## 7. Complete Lab: Reading Classpath Resources in `bootRun` and `java -jar`

The example uses Spring Boot 3.3.5, Java 17, and Gradle Groovy DSL. One resource resides in the application code, while `SpringApplication` comes from a dependency JAR. The program verifies **both are readable** via classpath APIs in both development and archive runs.

Structure:

~~~text
nested-demo/
├── settings.gradle
├── build.gradle
└── src/main/
    ├── java/com/example/demo/NestedDemoApplication.java
    └── resources/guide/message.txt
~~~

### File `settings.gradle`

~~~groovy
rootProject.name = 'nested-demo'
~~~

### File `build.gradle`

~~~groovy
plugins {
    id 'java'
    id 'org.springframework.boot' version '3.3.5'
    id 'io.spring.dependency-management' version '1.1.6'
}

group = 'com.example'
version = '1.0.0'

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(17)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
}

tasks.named('bootJar') {
    archiveFileName.set('nested-demo.jar')
}
~~~

`spring-boot-starter` provides the basic Spring runtime without creating an HTTP server. `bootJar` packages an executable JAR, distinct from the Java plugin's regular `jar`. The sample pins Spring Boot/Gradle versions for learner reproducibility and does not represent a timeless production recommendation.

### File `src/main/resources/guide/message.txt`

~~~text
HELLO_FROM_ARCHIVE
~~~

### File `src/main/java/com/example/demo/NestedDemoApplication.java`

~~~java
package com.example.demo;

import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

import org.springframework.boot.CommandLineRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.core.io.ClassPathResource;

@SpringBootApplication
public class NestedDemoApplication implements CommandLineRunner {

    public static void main(String[] args) {
        SpringApplication.run(NestedDemoApplication.class, args);
    }

    @Override
    public void run(String... args) throws IOException {
        ClassPathResource resource =
                new ClassPathResource("guide/message.txt");

        try (InputStream in = resource.getInputStream()) {
            String message = new String(
                    in.readAllBytes(), StandardCharsets.UTF_8).trim();
            System.out.println("RESOURCE=" + message);
        }

        ClassLoader loader =
                Thread.currentThread().getContextClassLoader();

        try (InputStream bootClass = loader.getResourceAsStream(
                "org/springframework/boot/SpringApplication.class")) {
            System.out.println(
                    "BOOT_DEPENDENCY_VISIBLE=" + (bootClass != null));
        }
    }
}
~~~

Correctness points:

1. Public Java class name matches filename and package.
2. `@SpringBootApplication` makes the application class a Spring component; `CommandLineRunner` executes upon context startup.
3. `ClassPathResource` reads `guide/message.txt` via stream, without converting to `File`.
4. `SpringApplication.class` is provided by the Spring Boot runtime dependency; the context class loader still finds it inside the executable archive.
5. Both streams are closed using `try-with-resources`.
6. Single-line UTF-8 data ensures deterministic stdout independent of machine paths.

### Running in Development

If the project has a Gradle Wrapper:

~~~bash
./gradlew bootRun --args='--spring.main.banner-mode=off --logging.level.root=OFF'
~~~

The two lines printed **by the application itself**:

~~~text
RESOURCE=HELLO_FROM_ARCHIVE
BOOT_DEPENDENCY_VISIBLE=true
~~~

Gradle/Spring logs may differ per machine. The lines above are solely the program's `System.out.println` output.

### Running from the Executable Boot JAR

~~~bash
./gradlew clean bootJar
java -jar build/libs/nested-demo.jar --spring.main.banner-mode=off --logging.level.root=OFF
~~~

The two lines printed by the application remain:

~~~text
RESOURCE=HELLO_FROM_ARCHIVE
BOOT_DEPENDENCY_VISIBLE=true
~~~

Here `guide/message.txt` sits in `BOOT-INF/classes` and `SpringApplication` resides in a JAR under `BOOT-INF/lib`. The class loader mechanism differs from development, yet the stream API still works.

Inspect the outer JAR:

~~~bash
jar tf build/libs/nested-demo.jar
~~~

In the very long list, you should find entries such as:

~~~text
META-INF/MANIFEST.MF
BOOT-INF/classes/com/example/demo/NestedDemoApplication.class
BOOT-INF/classes/guide/message.txt
~~~

The list also contains `BOOT-INF/lib/...jar` entries with real names. `jar tf` lists **outer entries**; it does not recursively display every `.class` inside nested dependencies.

On Windows PowerShell, use `.\gradlew.bat` instead of `./gradlew` and quote arguments per shell rules. If there is no Gradle Wrapper yet, you can use a compatible Gradle version to generate it via `gradle wrapper --gradle-version 8.7` at the project root.

## 8. Standalone Java 17 Inspector: Proving the Compression Method of Nested JARs

To verify the `STORED` rule, use `JarFile` to iterate over **outer JAR entries**. Create a standalone `InspectBootArchive.java` file:

~~~java
import java.io.IOException;
import java.util.Enumeration;
import java.util.jar.JarEntry;
import java.util.jar.JarFile;
import java.util.zip.ZipEntry;

public final class InspectBootArchive {
    private InspectBootArchive() {
    }

    public static void main(String[] args) throws IOException {
        if (args.length != 1) {
            System.err.println("Usage: java InspectBootArchive <boot-jar>");
            System.exit(2);
        }

        try (JarFile jar = new JarFile(args[0])) {
            boolean resourcePresent =
                    jar.getEntry("BOOT-INF/classes/guide/message.txt") != null;

            int nestedCount = 0;
            int storedCount = 0;
            Enumeration<JarEntry> entries = jar.entries();

            while (entries.hasMoreElements()) {
                JarEntry entry = entries.nextElement();
                String name = entry.getName();

                if (!entry.isDirectory()
                        && name.startsWith("BOOT-INF/lib/")
                        && name.endsWith(".jar")) {
                    nestedCount++;

                    if (entry.getMethod() == ZipEntry.STORED) {
                        storedCount++;
                    }
                }
            }

            System.out.println("APP_RESOURCE_PRESENT=" + resourcePresent);
            System.out.println("HAS_NESTED_LIBRARIES=" + (nestedCount > 0));
            System.out.println("ALL_NESTED_STORED=" +
                    (nestedCount > 0 && storedCount == nestedCount));
        }
    }
}
~~~

Compile with JDK 17:

~~~bash
javac InspectBootArchive.java
~~~

After building the JAR from the lab and running the inspector from the right directory:

~~~bash
java InspectBootArchive build/libs/nested-demo.jar
~~~

Output for **this lesson's standard archive**:

~~~text
APP_RESOURCE_PRESENT=true
HAS_NESTED_LIBRARIES=true
ALL_NESTED_STORED=true
~~~

The count of nested libraries is not fixed because it depends on dependency versions and plugins. The program only prints the boolean checks needed for verification.

**Inspector limitation:** `new JarFile("build/libs/nested-demo.jar")` opens the outer archive as a filesystem file. You can use `jar.getInputStream(entry)` to read the bytes of a nested JAR entry, but you cannot just pass `"build/libs/nested-demo.jar!/BOOT-INF/lib/foo.jar"` to `new JarFile(...)` and expect Java to treat it as a normal physical JAR file.

When you need to analyze a nested JAR offline, you can extract the entry to a temp JAR and open it with `JarFile`, or use tooling aware of nested archives. For reading resources inside a Boot runtime application, the simpler way is **reading via a classloader/Resource stream**, without manual extraction.

## 9. Fourth Limitation: Some Libraries Require Receiving the JAR or Resource as a Real File

A legacy library or native integration might:

- call `new File(...)` with a classpath resource path;
- require passing a physical `Path` to an API;
- call `new JarFile(path)` after deriving the path from `ProtectionDomain#getCodeSource()`;
- read nested ZIPs on its own yet only support single-level JARs;
- require shared libraries/native assets to be extracted to a filesystem directory.

A class might be loaded successfully by Spring Boot Loader yet the library still fails due to **filesystem assumptions**. Adding the dependency again is not always the answer: the issue may lie in the library's API.

### `requiresUnpack` — Marking Specific Dependencies for Unpacking

Spring Boot build plugins support marking certain JARs to unpack at runtime. For example, in `build.gradle` Groovy DSL with `bootJar`:

~~~groovy
tasks.named('bootJar') {
    requiresUnpack '**/jruby-complete-*.jar'
}
~~~

`JRuby` is the official example of a dependency whose internal mechanics require the JAR as a real file. The snippet above **only takes effect** when the project actually has the matching dependency; it is not a requirement to add JRuby to every Boot application.

Maven equivalent, snippet inside `spring-boot-maven-plugin`:

~~~xml
<configuration>
    <requiresUnpack>
        <dependency>
            <groupId>org.jruby</groupId>
            <artifactId>jruby-complete</artifactId>
        </dependency>
    </requiresUnpack>
</configuration>
~~~

In supported cases, Boot Loader unpacks the marked dependency to a temporary directory when needed. Do not enable unpacking for every JAR: it costs I/O and introduces operational requirements on the temp directory.

In containers or environments with a read-only root filesystem, ensure `java.io.tmpdir` points to a writable area with adequate disk space and proper permissions, and is not purged by cleanup processes while the app is still using it. Native libraries may also require specific OS/architecture/ABI environments — unpacking does not automatically fix those compatibility issues.

### If Only a Data Resource Needs a `File`

When a third-party API **strictly** requires a `File` and offers no stream overload, you can copy the resource to a temp file in a controlled manner:

~~~java
import java.io.IOException;
import java.io.InputStream;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardCopyOption;

static Path materializeResource(
        ClassLoader loader, String name) throws IOException {

    Path temp = Files.createTempFile("resource-", ".bin");
    try (InputStream in = loader.getResourceAsStream(name)) {
        if (in == null) {
            Files.deleteIfExists(temp);
            throw new IOException("Missing resource: " + name);
        }

        Files.copy(in, temp, StandardCopyOption.REPLACE_EXISTING);
        return temp;
    } catch (IOException | RuntimeException ex) {
        Files.deleteIfExists(temp);
        throw ex;
    }
}
~~~

This is an **illustrative method** inside a Java class, not a standalone file. The caller must delete the file when done, bound data size, avoid writing secrets with overly broad permissions, and ensure the temp location is valid. `deleteOnExit()` is not a sufficient strategy for long-lived services.

If the API already accepts `InputStream`, `byte[]`, or Spring `Resource`, **do not** create a temp file.

## 10. Fifth Limitation: Wildcard Scanning and Multiple Same-Named Resources

Reading a known resource name:

~~~java
loader.getResourceAsStream("guide/message.txt");
~~~

is usually more predictable than **scanning all resources** by pattern across many nested JARs. Spring's `PathMatchingResourcePatternResolver` supports patterns like `classpath*:META-INF/services/*`, but results depend on class loaders, URL handling, directory entries, and library versions.

Illustrative snippet inside a Spring method that may throw `IOException`:

~~~java
import org.springframework.core.io.Resource;
import org.springframework.core.io.support.PathMatchingResourcePatternResolver;

var resolver = new PathMatchingResourcePatternResolver();
Resource[] resources =
        resolver.getResources("classpath*:META-INF/services/*");
~~~

`classpath*:` tries to find multiple matching resources, while `classpath:` normally represents a single classpath location. Per Spring Framework documentation, wildcard scanning at the classpath root can face portability limitations across app servers and JAR/classloader implementations.

Notes:

1. Resources with identical names across multiple dependencies can return multiple results, ordered by classpath order.
2. Manually parsing JAR URLs by splitting strings on `!` or looking for `file:` is unreliable when nested URL formats vary between loader versions.
3. When a library opens URLs with its own `URLClassLoader`/ZIP parser, verify compatibility; Spring Boot loading classes successfully does not guarantee that scanner supports the layout.
4. For critical resources, prefer **exact classpath resource names** over root wildcard scans if business logic does not need broad scanning.
5. If scanning is mandatory, **test on the actual executable archive**, not just `bootRun` or the IDE.

## 11. `classpath.idx` and `layers.idx` Are Not Magic Fixes for the Classpath

Two frequently confused index types:

| Index | What is it used for? | What does it NOT do? |
| --- | --- | --- |
| `BOOT-INF/classpath.idx` | Describes nested JAR ordering when the launcher runs `java -jar` in supported configurations | Does not automatically add a library missing from the JAR |
| `BOOT-INF/layers.idx` | Splits the artifact into layers during image creation | Does not create physical file directories for every nested dependency at runtime |

`classpath.idx` is not necessarily used when running the app from an IDE/`bootRun` or `mvn spring-boot:run`. When hitting "same resource name but wrong copy picked" issues, classpath order and duplicate entries should be examined, yet **do not manually edit the index** before accurately determining the dependency graph and artifact.

## 12. `JarLauncher`, `PropertiesLauncher`, and Running Exploded

`JarLauncher` fits the default executable JAR layout, locating nested libraries in `BOOT-INF/lib`. `WarLauncher` applies to the WAR layout. `PropertiesLauncher` supports configuring additional paths, such as via `loader.path` or `LOADER_PATH` depending on version, and requires the matching manifest/launcher.

Do not assume `-Dloader.path=...` always takes effect with the default `JarLauncher`. If external libraries are needed, check which launcher is set in `Main-Class` and read the Spring Boot documentation for that exact version.

Some environments opt for an **exploded archive**: unpacking the artifact into directories and configuring an appropriate launch command. Dependencies may then be physical files, though simply extracting the JAR does not mean every command behaves identically to `java -jar`. Keep the right main class, classpath, and resources intact.

Choose an exploded layout, shaded JAR, or unpack configuration **only when** a library is genuinely incompatible with the nested format and its resource-reading API cannot be fixed. A one-line fix to `getInputStream()` is usually simpler than changing the entire artifact distribution method.

## 13. Verification Using Gradle and Maven Tools

### Gradle

~~~bash
./gradlew clean bootJar
./gradlew dependencies --configuration runtimeClasspath
./gradlew dependencyInsight --dependency spring-core --configuration runtimeClasspath
jar tf build/libs/nested-demo.jar
~~~

- `runtimeClasspath` shows the resolved dependency graph; whether a library makes it into the archive also depends on packaging config, exclusions, and whether the artifact was built properly.
- `dependencyInsight` helps identify why a version was chosen.
- `jar tf` displays files/entries of the outer archive; it does not recurse deeply into each dependency JAR.
- The inspector in Section 8 verifies the outer compression method.

### Maven

~~~bash
mvn clean package
mvn dependency:tree
mvn help:effective-pom
jar tf target/your-application.jar
~~~

`your-application.jar` is an illustrative placeholder to replace with your actual artifact name. With Maven, `spring-boot-maven-plugin` and the `repackage` goal must be configured/bound properly. Simply importing the Spring Boot BOM or adding `spring-boot-starter` **does not guarantee** producing an executable Boot JAR. A plain JAR does not necessarily contain `BOOT-INF/lib` or the Boot launcher.

Both build systems require **inspecting the exact file to be deployed**, rather than just reading the build script and inferring.

## 14. Symptoms and Remediation

| Symptom | Possible cause | Fix/verification |
| --- | --- | --- |
| `getFile()` works from IDE yet fails in JAR | Resource is inside the archive | Use `getInputStream` |
| `URI is not hierarchical` | Converting `jar:`/nested URL to `File` | Use stream; only create temp file if API mandates |
| `FileSystemNotFoundException` | ZIP/nested URL unsupported by filesystem provider | Read via classloader/Resource |
| `ClassNotFoundException` with system loader | Class resides in application loader | Try TCCL; inspect `BOOT-INF/lib` |
| `jar tf` shows `foo.jar` yet API says file does not exist | JAR is a nested entry, not a physical file | Use `requiresUnpack` for that specific library |
| JAR repacked with ZIP tool then fails at startup | Outer nested JAR entries became `DEFLATED` | Check `ZipEntry.STORED`, fix packaging step |
| Resource only appears during `bootRun` | Not packaged or in dev-only path | Move into proper source set; verify `BOOT-INF/classes` |
| `getResourceAsStream` returns null | Wrong name/case, leading slash, or missing file | Check classpath root, archive listing |
| Class present yet `NoClassDefFoundError` | Missing transitive dependency or initialization failure | Read `Caused by`, check dependency versions |
| `NoSuchMethodError` | Possible binary incompatibility between versions | Compare resolved versions and archive |
| Wildcard `classpath*:` misses files | Scanner/URL/classloader portability | Test in packaged archive, prefer exact names |
| Native library fails with `UnsatisfiedLinkError` | Different OS/ABI/path/extraction | Check native platform, filesystem, temp directory |
| `java.class.path` only shows outer JAR | Boot launcher uses application loader | Do not conclude nested dependencies are lost |
| Cannot see nested class via `jar tf` | Tool only lists outer entries | Extract the specific nested JAR or use suitable tooling |

### 8-Step Diagnostic Process

1. **Confirm the exact artifact**, exact Git revision/build, and compatible JVM runtime.
2. **Read the manifest** to know the launcher, `Main-Class`, and `Start-Class`.
3. **List the outer archive**: do `BOOT-INF/classes` and `BOOT-INF/lib` have the expected contents?
4. **Check the STORED method** if any custom ZIP/repack step exists in the pipeline.
5. **Test resource/class loader**: what does `Thread.currentThread().getContextClassLoader().getResourceAsStream(...)` return?
6. **Hunt for filesystem assumptions**: `getFile()`, `new File(url.toURI())`, `Paths.get(url.toURI())`, `JarFile(codeSource)`.
7. **Fix precisely**: switch to stream/`Resource`, place the resource in the main source set, or configure unpack for **the exact dependency** requiring a file.
8. **Rebuild and run the actual executable archive** in a production-like environment and inspect the exception chain.

## 15. Review Questions

**Question 1.** `BOOT-INF/lib/example.jar` appears in `jar tf application.jar`. Can it immediately be opened with `new File("BOOT-INF/lib/example.jar")`?

**Answer:** Not solely from the entry name being present. That JAR sits inside the outer archive rather than necessarily being an independent filesystem file.

**Question 2.** Why must the outer nested-JAR entry be `STORED` while classes inside the nested JAR can still be `DEFLATED`?

**Answer:** Spring Boot Loader needs to seek directly to the nested archive's position within the outer file, yet can decompress individual class/resource entries inside the nested JAR like a normal JAR.

**Question 3.** `ClassPathResource#getInputStream` reads a file inside an executable JAR, yet `getFile` fails. Is this a packaging bug?

**Answer:** Not necessarily. A resource can exist on the classpath without having a physical file path. A stream is the right API when only the contents are needed.

**Question 4.** Is using `ClassLoader.getSystemClassLoader()` reliable for loading classes from `BOOT-INF/lib`?

**Answer:** Not across all Spring Boot Loader configurations. Prefer the thread context loader or the class loader of an application class where appropriate.

**Question 5.** Should `requiresUnpack` be used for every dependency?

**Answer:** No. Most dependencies are loaded directly by Boot Loader. Only unpack when a library is confirmed to require a physical JAR and a proper temp directory is prepared.

**Question 6.** Why doesn't `jar tf` print all classes inside `BOOT-INF/lib/spring-core-....jar`?

**Answer:** Because it is a nested JAR stored as **a single entry** of the outer archive; `jar tf` does not automatically extract and recursively traverse nested JAR entries.

**Question 7.** Does `classpath.idx` add a dependency not yet present into the executable JAR?

**Answer:** No. The index describes the order of JARs loaded, and does not download or package a new library.

**Question 8.** What proves that a resource is read properly when the application is deployed?

**Answer:** Build the executable JAR, verify `BOOT-INF/classes`/`BOOT-INF/lib`, then **run that exact JAR** and read the resource via stream from the application/context class loader; do not test only from the IDE.
