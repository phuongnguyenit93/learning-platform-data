# Parent-Child Spans in Distributed Tracing with Spring Boot

When an order creation request flows through `order-service`, `inventory-service`, and the database, looking solely at total HTTP response time is not enough to know which step caused a slowdown. **Distributed tracing** represents this path using **spans** linked together in the same **trace**. The **parent-child span** relationship reveals how a larger operation is broken down into smaller operations and where each step's time was spent.

For example, a `POST /orders` request takes 2.4 seconds; the inventory reservation span takes 2.1 seconds, while the database query in `inventory-service` takes 1.9 seconds. Inspecting the span tree gives the operations team a clear basis to prioritize investigating the database or connection pool rather than optimizing the controller in `order-service`.

This lesson belongs to the **Tracing** chapter of the **SPRING_BOOT_OBSERVABILITY** module. It places parent-child spans within the observability picture for Spring Boot using **Micrometer Observation, metrics, logs, and distributed tracing**; explaining propagation across HTTP/threads, tags and cardinality, exporters, sampling, and how to correlate signals to investigate errors, latency, and application behavior in production.

## Learning Objectives

After this lesson, you will be able to:

1. Distinguish **trace ID**, **span ID**, **parent span ID**, root span, and parent–child relationships.
2. Understand how `Observation` and `Scope` in Micrometer define operation boundaries and help tracing handlers build a span tree.
3. Instrument two nested business operations in Spring Boot without creating duplicate spans alongside HTTP instrumentation.
4. Explain **W3C Trace Context** and cross-service span relationships with instrumented HTTP clients/servers.
5. Recognize scenarios where parent–child relationships break across thread switches, `@Async`, Reactor, or messaging.
6. Distinguish **parent-child** relationships from **span links**, and understand the limitations of sampling, exporters, and trace data.
7. Test span hierarchies, handle scope errors, control high/low-cardinality metadata, and use traces alongside metrics/logs when investigating incidents.

## 1. Traces, Spans, and Identifiers

A **trace** describes the path associated with an activity, usually a user request or a background job. Each **span** describes an interval of work with start/end timestamps, an operation name, and related metadata. A trace can have one or many spans.

| Concept | Role | Example |
| --- | --- | --- |
| **Trace ID** | Shared identifier for spans belonging to the same trace | `4bf92f3577b34da6a3ce929d0e0e4736` |
| **Span ID** | Unique identifier for a single span within a trace | `00f067aa0ba902b7` |
| **Parent span ID** | Reference to the direct parent span | `00f067aa0ba902b7` |
| **Root span** | Span with no parent in the recorded trace | Span receiving the request into the system |
| **Child span** | Span with a defined parent | Calling inventory from the checkout step |
| **Span attributes** | Metadata about the span | `dependency.name=inventory` |
| **Span events/status** | Milestones or errors inside the span | Recorded timeout or exception |
| **Span kind** | Role of the span in an interaction | SERVER, CLIENT, INTERNAL, PRODUCER, CONSUMER |

**Parent and child share the same trace ID**, yet have **different span IDs**. On the child, `parentSpanId` references the parent's `spanId`. This is the direct relationship backends use to construct the tree.

An example structure:

~~~text
traceId = 4bf92f3577b34da6a3ce929d0e0e4736

POST /orders                        spanId=1111111111111111  parent=none
└─ orders.checkout                  spanId=2222222222222222  parent=1111111111111111
   └─ inventory.reserve             spanId=3333333333333333  parent=2222222222222222
      └─ HTTP POST inventory        spanId=4444444444444444  parent=3333333333333333
         └─ inventory HTTP server   spanId=5555555555555555  parent=4444444444444444
            └─ DB lookup            spanId=6666666666666666  parent=5555555555555555
~~~

The span IDs in this example are hypothetical numbers for easy comparison. Production data may feature parallel branches, unexported branches, and spans generated by various frameworks/dependencies.

### 1.1. What Does the Parent–Child Relationship Tell Us?

A parent–child relationship indicates that one operation executes within the **context of** another operation, not necessarily "parent calls child function" on a single-process Java call stack. The parent can live in another service; context propagates via HTTP or messages. Children can also **run concurrently** rather than sequentially.

More importantly, **do not sum the durations of all children and treat that as the parent's duration**. Multiple children may overlap in time, and the parent may also perform processing outside any child. A span's "exclusive" time, if shown by a backend, depends on how intervals and trace structure are analyzed.

### 1.2. Parent-Child Does Not Mean Two Spans Share the Same Name

One span can be named `orders.checkout`, its child named `inventory.reserve`, while HTTP client instrumentation generates a third span like `HTTP POST`. Names describe the **operation type**, whereas the parent–child relationship is determined by the **trace/span context at span creation time**.

A business label like `order.id` is not used to establish parent–child links and should not be placed in metric labels. Tracing relies on dedicated trace/span identifiers to build structure.

## 2. Building a Span Tree via Micrometer Observation

In Spring Boot, the standard way to instrument business code is **Micrometer Observation**, rather than calling exporter APIs directly. `ObservationRegistry` manages handlers and lifecycle; with an appropriate tracing bridge/handler, Observations can become spans.

~~~mermaid
flowchart TD
    Root["HTTP server Observation / scope"] --> Business["orders.checkout Observation / scope"]
    Business --> Reserve["inventory.reserve Observation / scope"]
    Reserve --> Client["HTTP client span"]
    Client --> Remote["Remote HTTP server span"]
    Remote --> Database["DB span if instrumented"]
    Business --> Metrics["Metrics handler records duration, count"]
    Reserve --> Trace["Tracing handler creates spans"]
    Root --> Logs["Logging correlation: traceId/spanId"]
~~~

Core components:

| Component | Responsibility |
| --- | --- |
| `Observation.createNotStarted(...)` | Creates an Observation without starting it yet |
| `start()` | Starts the lifecycle, emitting corresponding callbacks |
| `openScope()` | Places the current Observation onto the thread's context so nested operations find their parent |
| `observe(Runnable/Supplier)` | Convenience helper managing start, scope, error, and stop around a callback |
| `error(Throwable)` | Records an exception when managing lifecycle manually |
| `stop()` | Completes the Observation and triggers completion handlers |
| `ObservationRegistry` | Holds Observation handlers, conventions, filters, and tracks the current Observation |
| Tracing handler/bridge | Translates Observation lifecycle and context into tracing-semantic spans |

**Core principle of parent-child:** when Observation B is created and runs inside the `Scope` of Observation A, tracing instrumentation uses the active context to make B's span a **child** of A's span. Simply writing two consecutive `createNotStarted` blocks **does not guarantee** a parent–child link without proper scoping/context.

### 2.1. Using observe(...) for Nested Operations

Here is a Spring Boot application example with two business steps:

~~~java
package com.example.orders.tracing;

import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Service;

@Service
public class CheckoutService {
    private final ObservationRegistry registry;
    private final InventoryGateway inventory;
    private final PaymentGateway payment;

    public CheckoutService(ObservationRegistry registry,
                           InventoryGateway inventory,
                           PaymentGateway payment) {
        this.registry = registry;
        this.inventory = inventory;
        this.payment = payment;
    }

    public void checkout(String sku, int quantity) {
        Observation.createNotStarted("orders.checkout", registry)
                .lowCardinalityKeyValue("orders.channel", "web")
                .observe(() -> {
                    reserveInventory(sku, quantity);
                    chargePayment();
                });
    }

    private void reserveInventory(String sku, int quantity) {
        Observation.createNotStarted("inventory.reserve", registry)
                .lowCardinalityKeyValue("dependency.name", "inventory")
                .observe(() -> inventory.reserve(sku, quantity));
    }

    private void chargePayment() {
        Observation.createNotStarted("payment.charge", registry)
                .lowCardinalityKeyValue("dependency.name", "payment")
                .observe(payment::charge);
    }
}

interface InventoryGateway {
    void reserve(String sku, int quantity);
}

interface PaymentGateway {
    void charge();
}
~~~

With a proper tracing handler and all calls executing synchronously within the same context:

- `orders.checkout` is the **parent** of `inventory.reserve` and `payment.charge`.
- If `checkout(...)` runs inside an instrumented HTTP request, the HTTP server span is typically the parent of `orders.checkout`.
- Inside `inventory.reserve`, if `InventoryGateway` makes an HTTP call via an instrumented client, the HTTP client span is typically a child of the business span.
- If tracing is not configured, the code can still record Observation metrics, but you cannot assume spans were created in the backend.

This snippet assumes `InventoryGateway` and `PaymentGateway` are adapters implemented in the application. Place each public class in its own Java file and handle business errors properly outside this example.

### 2.2. Manual Scope and Lifecycle

`observe(...)` fits most synchronous operations. When you need to hold a scope across multiple code branches, you can manage it manually:

~~~java
Observation parent = Observation.createNotStarted(
        "orders.checkout", observationRegistry);
parent.start();

try (Observation.Scope parentScope = parent.openScope()) {
    Observation child = Observation.createNotStarted(
            "inventory.reserve", observationRegistry);
    child.start();

    try (Observation.Scope childScope = child.openScope()) {
        inventoryGateway.reserve(sku, quantity);
    } catch (RuntimeException exception) {
        child.error(exception);
        throw exception;
    } finally {
        child.stop();
    }
} catch (RuntimeException exception) {
    parent.error(exception);
    throw exception;
} finally {
    parent.stop();
}
~~~

With `try-with-resources`, the child scope closes before the parent scope, and each Observation stops in `finally` even on failure. Key invariants:

1. **`start()` before opening a scope**, and **`stop()` exactly once**.
2. Never leak a scope to another request or a reused thread pool thread.
3. Record errors on the matching Observation; the parent may also record an error when a child error propagates unhandled.
4. Do not call `stop()` prematurely and then add metadata expecting handlers to still pick it up.

**Note:** the snippet illustrates lifecycle handling with `RuntimeException`. In real systems, cover exception types and cancellation appropriately for your application APIs. For simple operations, prefer `observe(...)` to minimize the risk of forgetting to close scopes.

### 2.3. When Should You Avoid Adding a Span?

Spring Boot usually instruments HTTP servers, HTTP clients, and supported libraries automatically. There is no need to add a custom Observation merely to wrap **a single HTTP call** with no additional business meaning if it creates two nearly identical spans.

Add spans for **business boundaries valuable during investigation**, such as `orders.checkout` encompassing inventory reservation, payment charging, and DB persistence; or a retry/validation step truly worth measuring. Too many spans increase CPU overhead, trace size, storage cost, and timeline noise.

## 3. Span Relationships Across HTTP Between Two Services

In distributed tracing, a parent may execute in another process. To connect the tree between `order-service` and `inventory-service`, the system must **propagate trace context** over HTTP.

~~~mermaid
sequenceDiagram
    participant Client as Client
    participant Order as order-service
    participant Inventory as inventory-service
    participant Database as DB
    Client->>Order: POST /orders
    Note over Order: SERVER span A
    Order->>Order: orders.checkout span B, parent A
    Order->>Order: inventory.reserve span C, parent B
    Order->>Inventory: HTTP POST + traceparent, CLIENT span D
    Note over Inventory: SERVER span E, remote parent D
    Inventory->>Database: Query, child span F if instrumented
    Database-->>Inventory: Result
    Inventory-->>Order: HTTP response
    Order-->>Client: Response
~~~

In this model:

- Spans A, B, C, and D in `order-service` belong to the same trace.
- Headers carry context from client span D to the server side of `inventory-service`.
- SERVER span E carries `parentSpanId` matching CLIENT span D's ID when instrumentation/propagation is wired properly.
- Span F, if present, is a child of E or of a business span beneath E.

Do not create a second manual server span if Spring MVC/WebFlux instrumentation already creates a server span for the request.

### 3.1. W3C Trace Context and traceparent

A header following the W3C standard:

~~~http
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
~~~

Components:

| Component | Meaning |
| --- | --- |
| Leading `00` | Version of the `traceparent` format |
| Next 32 hex chars | Trace ID (128-bit) |
| Next 16 hex chars | Parent ID: sender's span ID in the propagated context |
| Trailing `01` | Trace flags; sampled bit is set in this example |

**Parent ID in the header** is the span ID the receiving service should treat as its remote parent, not "the HTTP request ID" or "the inventory reservation ID". When the receiving service creates a SERVER span, it receives a **new span ID** while retaining the **trace ID** if propagation succeeds.

The `tracestate` header can carry vendor-specific tracing data per the standard; its presence depends on the tracing system. Never put passwords, access tokens, or user data into trace context headers.

If using B3 instead of W3C, header names differ. Both services must agree on a format or have compatible context translation; do not look at a trace ID in logs alone and assume propagation succeeded.

### 3.2. Using a Spring Boot-Instrumented HTTP Client

With Spring Boot 3.2+ providing a Spring-configured `RestClient.Builder`, an adapter calling inventory might look like:

~~~java
package com.example.orders.tracing;

import org.springframework.stereotype.Component;
import org.springframework.web.client.RestClient;

@Component
public class HttpInventoryGateway implements InventoryGateway {
    private final RestClient restClient;

    public HttpInventoryGateway(RestClient.Builder builder) {
        this.restClient = builder
                .baseUrl("http://inventory-service:8080")
                .build();
    }

    @Override
    public void reserve(String sku, int quantity) {
        restClient.post()
                .uri("/inventory/reservations")
                .body(new ReserveRequest(sku, quantity))
                .retrieve()
                .toBodilessEntity();
    }
}

record ReserveRequest(String sku, int quantity) {}
~~~

When using the **Spring Boot auto-configured** builder with active Observation/tracing instrumentation, the HTTP client can create a CLIENT observation/span and attach the appropriate context headers. On `inventory-service`, HTTP server instrumentation reads the header to continue the trace.

**Never assume a manually constructed `RestClient.create()`, arbitrary client SDK, or third-party HTTP client is automatically instrumented.** For custom clients, verify integration with `ObservationRegistry` and propagators.

`inventory-service:8080` merely illustrates a service name resolvable in a container environment; use the appropriate endpoint for your running system.

## 4. Spring Boot: Tracing Bridge, Exporter, and Sampling

In a Spring Boot 3.x application using Micrometer Tracing with the OpenTelemetry bridge and OTLP, illustrative dependencies:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
    implementation 'io.micrometer:micrometer-tracing-bridge-otel'
    runtimeOnly 'io.opentelemetry:opentelemetry-exporter-otlp'
}
~~~

Test `application.yml` configuration:

~~~yaml
spring:
  application:
    name: order-service

management:
  tracing:
    sampling:
      probability: 1.0   # For testing only; high sample rate to easily view the span tree
  otlp:
    tracing:
      endpoint: http://localhost:4318/v1/traces
~~~

Meaning:

1. `Actuator` and the tracing bridge participate in Spring Boot's observability/tracing auto-configuration.
2. The OTLP tracing exporter ships recorded spans to a compatible Collector or backend.
3. `probability: 1.0` is for low-traffic lab/test environments; production requires choosing sampling based on traffic, cost, and analysis goals.
4. `http://localhost:4318/v1/traces` is only valid when the OTLP HTTP receiver is reachable at that address from the app process. Inside a container, `localhost` may point to the wrong target.

Property names, modules, and auto-configuration behavior can vary across Spring Boot/Micrometer versions. Keep dependencies aligned with your project's BOM and verify docs for your exact version.

### 4.1. Having a Tracing Bridge Does Not Guarantee a Span Tree in the Backend

A complete data pipeline typically includes:

~~~mermaid
flowchart LR
    Code["Observation in code"] --> Registry["ObservationRegistry"]
    Registry --> Handler["Tracing handler / bridge"]
    Handler --> Sampler["Sampling decision"]
    Sampler --> Exporter["OTLP exporter"]
    Exporter --> Collector["OpenTelemetry Collector"]
    Collector --> Backend["Trace backend"]
    Registry --> Metrics["Metrics handler / MeterRegistry"]
    Code --> Logs["Logging / correlation"]
~~~

A trace can be lost at any stage: Observation has no handler, sampler drops it, exporter fails, Collector rejects data, backend retention expires, or you are querying the wrong service/time range. **A missing span in the UI does not prove the code did not run.**

### 4.2. Parent-Child Under Sampling

With **head-based sampling**, the decision is usually made early at the start of the trace and children can inherit the sampling flag from the parent. Parent context may still be propagated to the next service even when the trace is not recorded. Therefore:

- A trace dropped by sampling may have zero spans stored in the backend.
- Observations can still record metrics through handlers independent of tracing.
- A trace may appear **incomplete** if one service is mis-instrumented, an exporter fails, the pipeline splits, or services use differing policies.
- Do not use the ratio of stored traces as the request success/failure rate unless sampling was specifically designed to support such inference.

**Tail-based sampling** can decide after collecting spans, e.g., prioritizing error or slow traces; however, it requires a Collector/pipeline capable of buffering related spans, incurring higher memory cost and export latency. Do not assume a single `sampling.probability` flag in Spring Boot enables tail sampling.

## 5. Scope and Context Propagation Across Thread Switches

The hardest part of parent-child spans is rarely naming—it is **preserving the right trace context** when execution switches threads. Scope is usually tied to the current thread or execution context. Creating a child Observation on another thread without carrying the parent context across can turn the child into a new root.

### 5.1. Example of Losing the Parent in an Executor

~~~java
// Illustrates an error-prone case:
Observation.createNotStarted("orders.checkout", registry)
        .observe(() -> {
            executor.execute(() ->
                    Observation.createNotStarted("invoice.generate", registry)
                            .observe(this::generateInvoice));
        });
~~~

If `executor` lacks context propagation, the task running on the thread pool may not see `orders.checkout`'s current Observation/span. As a result, `invoice.generate` lacks the expected parent or fails to connect to the original trace.

**Never "fix" this by copying the trace ID into a String and setting it as the span name.** Parent-child linkage depends on trace/span context, not a text string. Setting headers or thread-locals incorrectly can split traces or introduce security flaws.

### 5.2. Using a TaskDecorator with Context Propagation

With Spring Framework 6.1+ and the appropriate context-propagation dependency, you can configure an executor:

~~~java
package com.example.orders.tracing;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.task.support.ContextPropagatingTaskDecorator;
import org.springframework.scheduling.annotation.EnableAsync;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration(proxyBeanMethods = false)
@EnableAsync
public class AsyncTracingConfiguration {

    @Bean("observedExecutor")
    ThreadPoolTaskExecutor observedExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("observed-");
        executor.setTaskDecorator(new ContextPropagatingTaskDecorator());
        return executor;
    }
}
~~~

`ContextPropagatingTaskDecorator` captures and restores contexts registered with Micrometer Context Propagation when tasks are submitted/executed. Service example:

~~~java
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.scheduling.annotation.Async;
import org.springframework.stereotype.Service;

import java.util.concurrent.CompletableFuture;

@Service
public class InvoiceService {
    private final ObservationRegistry registry;

    public InvoiceService(ObservationRegistry registry) {
        this.registry = registry;
    }

    @Async("observedExecutor")
    public CompletableFuture<Void> generateAsync(String reference) {
        Observation.createNotStarted("invoice.generate", registry)
                .observe(() -> generateInvoice(reference));
        return CompletableFuture.completedFuture(null);
    }

    private void generateInvoice(String reference) {
        // Process invoice; do not record sensitive reference in a low-cardinality tag.
    }
}
~~~

**Conditions for this example to work:** `InvoiceService` must be invoked through the Spring `@Async` proxy; the executor must match the configured bean, and appropriate context accessors must be registered. For other executors or scheduling frameworks, apply their corresponding propagation mechanisms. Inspect actual traces rather than assuming the decorator automatically solves every boundary.

Even if the parent scope has closed by the time the async child starts, the child can still reference the parent via previously captured context; the span tree does not strictly require the two spans' execution intervals to overlap. However, this also depends on how the framework preserves/restores context and the tracing backend's recording behavior.

### 5.3. Reactor, Messaging, and Virtual Threads

- **Reactor/WebFlux:** do not naively rely on `ThreadLocal`; execution can switch threads across operators. Use Reactor/Spring context propagation support and verify context in actual pipelines.
- **Messaging/Kafka/RabbitMQ:** instrument producers/consumers or headers to propagate trace context. Delayed consumers or multi-message batches may choose parent-child or span links depending on workflow semantics.
- **Virtual threads:** having the same operation name does not guarantee the parent automatically propagates when spawning new tasks; use framework-supported mechanisms and verify span relationships.

An `Observation` with the right name, tags, and `stop()` call does not automatically guarantee it is a child of the intended span. **Propagation requires its own verification.**

## 6. How Parent-Child Spans Differ from Span Links

Not every relationship between two pieces of work fits a single direct parent.

| Relationship | When to Use | Example |
| --- | --- | --- |
| **Parent-child** | One operation runs inside another operation's context | HTTP client span → HTTP server span from the same request |
| **Sibling spans** | Two operations sharing the same parent | Two independent calls to inventory and payment |
| **Span link** | Need to associate with another span/context without setting a direct parent | Batch job consuming multiple messages from multiple source traces |
| **Same business ID** | Related in business terms, not necessarily the same trace | An order reprocessed days later |

Suppose a batch consumer receives 100 messages, each with a different trace context. The batch process span cannot have **100 direct parent span IDs**: a span has only **one parent** in a tree. In tracing systems that support them, **span links** express relationships to multiple sources.

Do not manually "stitch traces" by copying an arbitrary request's trace ID onto the entire batch. Follow the semantic conventions and instrumentation of the messaging system in use; span link support also depends on the tracer and backend.

## 7. Attributes, Cardinality, and Security in Span Trees

Span attributes help explain why a step was slow or failed. For `inventory.reserve`:

| Key | Value | Classification / Assessment |
| --- | --- | --- |
| `dependency.name` | `inventory` | Low cardinality, useful for metrics/traces |
| `inventory.operation` | `reserve` | Low cardinality |
| `inventory.channel` | `web`, `batch` | Low cardinality if normalized |
| `inventory.attempt.id` | Pseudonymous per-attempt ID | High cardinality, consider storing on trace only |
| `http.route` | `/orders/{id}` | Route template preferred over raw URL |
| `customer.email` | User email | Do not collect by default |
| `authorization` | Bearer token | Never write to attributes |

In Micrometer Observation:

~~~java
Observation.createNotStarted("inventory.reserve", registry)
        .lowCardinalityKeyValue("dependency.name", "inventory")
        .lowCardinalityKeyValue("inventory.operation", "reserve")
        .highCardinalityKeyValue("inventory.attempt.id", attemptId)
        .observe(() -> inventoryGateway.reserve(sku, quantity));
~~~

**Low-cardinality key-values** are typically used for metric labels and can also appear on spans. **High-cardinality key-values** can be turned into span attributes by tracing handlers, yet should never go into metric labels because series counts grow with traffic. Do not assume every handler/exporter retains all attributes: backends may limit string length, attribute counts, or indexing.

A high-cardinality tag **does not automatically become baggage**. Baggage is a mechanism for carrying selected context data downstream when configured, requiring strict allowlists, size limits, and privacy review. Adding `highCardinalityKeyValue` in `order-service` does not automatically deliver that key to `inventory-service`.

### 7.1. Do Parent and Child Automatically Share Attributes?

Not by default. Parent-child typically shares **trace context** (trace ID, sampling state, and propagation data), not all business attributes. A tag on a parent does not automatically appear on a child span. If the same attribute is needed on multiple spans, define the requirement explicitly and attach it appropriately; avoid blindly duplicating data across hundreds of spans.

### 7.2. Managing Costs

Adding a child span for every single item in a 100,000-item batch can generate massive tracing volume. Instrument meaningful boundaries, consider sampling, and cap attributes/events; use metrics to measure traffic and overall distributions, and logs/traces to investigate specific cases.

Similarly, never attach `order.id` or `trace.id` to labels of the `orders.checkout` timer. For example, 5 routes, 4 outcomes, 20 instances, and 30 histogram buckets can produce up to **5 × 4 × 20 × 30 = 12,000** bucket series in a simple model, before even counting other labels. Adding a request ID causes cardinality to scale with request volume.

## 8. Observing Errors and Latency Through a Span Tree

Suppose `POST /orders` becomes slow after deploying a new release. A sampled trace might show:

~~~text
POST /orders (SERVER)                 2.40 s
└─ orders.checkout (INTERNAL)          2.32 s
   ├─ inventory.reserve (INTERNAL)     2.10 s
   │  └─ HTTP POST inventory (CLIENT)  2.07 s
   │     └─ reserve (SERVER)           2.03 s
   │        └─ SELECT stock (DB)       1.87 s
   └─ payment.charge (INTERNAL)        0.12 s
~~~

This is a **hypothetical** timeline; individual child durations can overlap if operations run concurrently. A backend may represent errors via span status, events, or attributes depending on SDK/instrumentation.

Investigation path:

1. **Metrics:** verify request rate, 5xx rate, p95/p99 latency of `POST /orders`, and timeout counts for `inventory-service`.
2. **Traces:** open a slow trace and read the parent-child tree to see that the inventory step dominates total duration.
3. **Logs:** use trace ID/span ID to correlate with timeout logs, slow query logs, or connection pool warnings.
4. **Dependency metrics:** cross-check JDBC pool pending connections, DB latency, CPU/GC, queues, and saturation.
5. **Changes:** review rollouts, concurrency limits, timeouts, retries, and rollback plans.
6. **Re-measure:** after fixing, compare error ratios, p95/SLOs, timeout counts, and sample traces.

**Do not infer system-wide health from a single trace.** Traces show one recorded execution; metrics describe trends and impact scale; logs help interpret errors. Trace visibility also depends on sampling and retention.

### 8.1. Log Correlation and Its Limits

Example log record:

~~~text
2026-11-22T09:10:15Z ERROR service=order-service
traceId=4bf92f3577b34da6a3ce929d0e0e4736 spanId=3333333333333333
event=inventory_timeout dependency=inventory-service duration_ms=2070
~~~

If logging is configured to place trace/span IDs into MDC, you can jump from logs to traces. However:

- Not every log is emitted inside an active scope; background logs may lack a trace ID.
- A trace ID in logs does not guarantee the trace was exported or retained by sampling.
- Never log request bodies, access tokens, or emails just to add context.
- A span can record an error without the parent recording an error if the application catches and handles the exception cleanly; error status rules must be interpreted per actual instrumentation.

## 9. Testing Parent-Child Span Relationships

Layer your tests to avoid overclaiming from a single unit test:

| Layer | Can Verify | Does Not Prove |
| --- | --- | --- |
| **Unit test with TestObservationRegistry** | Observation created/stopped, nested scopes, key-values, errors | Exporter-generated Span ID and parentSpanId |
| **Tracing integration test** | Spans created by tracing handler with correct parentSpanId | Entire production infrastructure |
| **HTTP cross-service test** | Context headers and CLIENT/SERVER spans continuing the trace | Every request is stored |
| **Async/reactive test** | Context crosses thread/pipeline and child keeps parent | Error-free across every executor/framework |
| **Staging backend test** | Collector receives traces, UI renders tree, log correlation works | Absolute completeness when sampling/retention varies |

### 9.1. Testing Nested Scopes with TestObservationRegistry

`micrometer-observation-test` lets you test the Observation runtime without a Collector. JUnit 5 example:

~~~java
import io.micrometer.observation.Observation;
import io.micrometer.observation.tck.TestObservationRegistry;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertSame;

class NestedObservationScopeTest {

    @Test
    void restoresParentScopeAfterChildCompletes() {
        TestObservationRegistry registry = TestObservationRegistry.create();
        Observation.createNotStarted("orders.checkout", registry)
                .observe(() -> {
                    Observation parent = registry.getCurrentObservation();
                    assertNotNull(parent);

                    Observation.createNotStarted("inventory.reserve", registry)
                            .observe(() -> {
                                Observation current = registry.getCurrentObservation();
                                // Inside child scope, current is the child Observation.
                                assertNotNull(current);
                                org.junit.jupiter.api.Assertions.assertNotSame(
                                        parent, current);
                            });

                    assertSame(parent, registry.getCurrentObservation());
                });

        assertNull(registry.getCurrentObservation());
    }
}
~~~

This test checks that scopes are established and restored. **It does not prove `parentSpanId` is accurate in a tracing backend**, because `TestObservationRegistry` can run without a tracing bridge. Verifying real span relationships requires a tracing integration test.

### 9.2. Testing Span IDs with an In-Memory Exporter

At the integration level, you can configure the OpenTelemetry SDK with an in-memory test exporter (e.g., `InMemorySpanExporter` when adding the corresponding SDK test dependency) or use a test span handler if using Brave.

Expected test flow:

1. Initialize real tracing infrastructure, not just `TestObservationRegistry`.
2. Start parent Observation `orders.checkout` and open its scope.
3. Start child Observation `inventory.reserve` inside the parent's scope, then stop both.
4. Collect exported spans in memory.
5. Assert **both spans share the same trace ID**.
6. Assert **child.parentSpanId equals parent.spanId** and **child.spanId differs from parent.spanId**.
7. Assert each span ended, has sensible timing, and records error/status on failure.

In this test, **control sampling** so spans are always recorded and avoid depending on an external OTLP server. Separate cross-service tests must include HTTP client/server instrumentation and header propagation; a local in-memory exporter does not prove context crosses between two processes.

### 9.3. Testing HTTP Propagation

Simple scenario:

- From `order-service`, issue a request under an active span to a test HTTP server or test `inventory-service`.
- On the receiving side, inspect the `traceparent` header (when using the W3C propagator) and the active SERVER span.
- Assert the received span's trace ID equals the sender's trace ID and `parentSpanId` matches the CLIENT span.
- Also run a case with a manually created uninstrumented client to see the contrast and avoid assuming automatic behavior.

Do not hardcode exact span IDs in assertions since IDs are typically randomized; assert the **relationships between IDs** instead.

### 9.4. Testing Errors and Async

For failure paths, have `InventoryGateway` throw a timeout and verify the Observation stops and records the error; in a tracing integration test, verify the span has appropriate error info. For async, compare context/span trees when the executor **has** vs. **lacks** context propagation to see how a child can become a root.

Avoid long sleeps to assert exact durations in unit tests. Use appropriate clocks/test infrastructure and assertions focused on relationships/behavior, verifying real latency in dedicated integration tests.

## 10. Common Pitfalls When Building a Trace Tree

| Symptom | Possible Cause | How to Investigate |
| --- | --- | --- |
| Child becomes a root span | No active scope or context lost across thread switch | Check `observe/openScope`, executor/context propagation |
| Two services have different trace IDs | Uninstrumented HTTP client or mismatched propagator | Inspect `traceparent` and client/server configs |
| Parent exists, child missing | Child not created, no-op, missing tracing handler, or sampling/exporter dropped data | Check Observation runtime, sampler, and collector |
| Cluttered duplicate parent/child names | Same step instrumented twice | Remove redundant span or clarify business boundaries |
| Subsequent request's scope carries previous trace | Forgot to close scope or thread-local leak | Use `try-with-resources` or `observe(...)` |
| Trace has many spans, still unclear which step is slow | Overly fine spans, generic names, missing semantic attributes | Restructure around business steps; keep names/tags stable |
| Parent ends before async child | Async lifecycle not designed/propagated clearly | Check context capture and async task semantics |
| Trace only has spans from one service | Exporter/downstream uninstrumented or Collector misconfigured | Check pipeline per service |
| Logs have trace ID, backend finds no trace | Sampling, exporter error, retention, or wrong time range | Check sampling config and telemetry pipeline |
| High-cardinality metadata appears in metric labels | Confused `highCardinalityKeyValue` with low cardinality | Fix conventions, check MeterRegistry |
| Broken links across Kafka/batch | Incorrect header propagation or span-link semantics | Check producer/consumer and relationship type |

### 10.1. Inside-Out Investigation Procedure

When a parent–child relationship is missing:

1. **In code:** confirm the parent Observation is active at the child creation point and its lifecycle wasn't stopped early.
2. **In-process:** confirm the tracing handler/bridge creates spans and the child has the same trace ID as the parent with a matching `parentSpanId`.
3. **Across network/threads:** confirm context is injected/extracted or captured/restored properly.
4. **At the exporter:** confirm the sampler and exporter record/ship the expected spans.
5. **In the backend:** check service name, trace ID, time range, retention, and indexing limits.

Do not tweak histograms, change metric labels, or raise the Prometheus scrape interval to fix a parent-child tracing issue. Metrics and traces have separate pipelines even when generated from the same Micrometer Observation.

## 11. Pre-Production Checklist

| Criterion | Evidence of Readiness |
| --- | --- |
| Meaningful parent/child boundaries | Request journey diagram and key operation names |
| Scopes closed cleanly | Explicit `observe(...)` or `try-with-resources` |
| No duplicate spans | HTTP auto-instrumentation and business spans don't overlap redundantly |
| W3C propagation verified | CLIENT/SERVER spans share trace ID with valid `parentSpanId` |
| Async/reactive propagation verified | Tested across executor/WebFlux or messaging in use |
| Sampling well understood | Aware of missing-trace expectations and cost impact |
| Exporter/Collector operational | Traces searchable in backend by trace ID |
| Safe span attributes | No tokens, PII, or request bodies; high cardinality bounded |
| Metrics still cover full trends | Request rate, error ratio, p95/p99, and SLIs/SLOs if applicable |
| Logs correlate with traces | Trace/span IDs present whenever context is active |
| Span IDs and error status tested | Tested at the tracing layer, not only Observation runtime |
| Instrumentation change plan | Avoid breaking dashboards or spiking cost on name/tag changes |

## 12. Hands-On Exercise: Tracing Order Creation Across Two Services

**Context:** `order-service` handles `POST /orders`, then calls `inventory-service` to reserve stock and writes to a database. Users report requests occasionally take over 2 seconds. You need a span tree pinpointing the slow step and correlated with metrics/logs.

**Tasks:**

1. Add Actuator, Micrometer Tracing bridge, and an appropriate exporter to both services. Standardize on W3C Trace Context.
2. Let HTTP server instrumentation create the incoming request span in `order-service`.
3. Add a custom Observation `orders.checkout` wrapping the business flow, and a child `inventory.reserve` inside the parent's scope.
4. Use a Spring Boot-instrumented HTTP client to call `inventory-service` and inspect the `traceparent` header.
5. On the receiving service, verify the SERVER span shares the trace ID with the caller's CLIENT span; if DB instrumentation is enabled, confirm the DB span sits beneath the appropriate handler step.
6. Write a unit test with `TestObservationRegistry` verifying nested scopes and lifecycle; write an integration test with an in-memory exporter verifying `parentSpanId`.
7. Simulate a timeout error, inspect the error span, logs with the same trace ID, and HTTP error metrics; do not put order IDs or personal data into metric tags.
8. Offload work to `@Async` without context propagation and observe the broken span tree; configure `ContextPropagatingTaskDecorator` and compare.
9. Lower sampling from 100% in testing to a low rate, and explain why some requests have no trace while metrics still record them.
10. Propose a dashboard with request rate, error ratio, p95/p99, and a workflow moving from an anomalous panel to sample traces and logs.

**Expected deliverables:** span tree diagram with verifiable trace ID and `parentSpanId`, Observation/HTTP client code, scope and tracing integration tests, a metrics/logs correlation table for a simulated error, and notes on sampling, exporter, and context propagation.

## 13. Key Takeaways

**Parent-child spans** represent the relationship between operations within the same trace. A child keeps the shared **trace ID** while receiving its own **span ID** and referencing **parent span ID**. In Spring Boot, Micrometer Observation and proper scoping enable tracing handlers to build nested business spans; HTTP client/server instrumentation with W3C Trace Context stitches relationships across service boundaries.

An accurate span tree depends not only on span-creating code, but also on **context propagation, sampling, tracing bridges, exporters, and backends**. To investigate errors, latency, and application behavior effectively, combine traces with **cardinality-controlled metrics** and **trace-ID-correlated logs**, always distinguishing evidence from a single request from system-wide trends.
