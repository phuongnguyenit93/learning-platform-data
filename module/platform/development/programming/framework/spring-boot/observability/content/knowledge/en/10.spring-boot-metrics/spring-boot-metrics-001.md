# Auto-configured MeterRegistry

In the **Spring Boot metrics** chapter of the **SPRING_BOOT_OBSERVABILITY** module, `MeterRegistry` is the central component for an application to record **metrics**: request counts, processing duration, errors, JVM usage, resource saturation, and business indicators. With the auto-configuration mechanism, Spring Boot can create and configure a registry suited to the dependencies on the classpath. You only need to inject `MeterRegistry` into a service when you need to measure your application's own activities.

The goal of the module is to build observability in Spring Boot using **Micrometer Observation, metrics, logs, and distributed tracing**; including context propagation, tags/cardinality, exporters, sampling, and signal correlation to investigate real-world behavior. `MeterRegistry` belongs to the metrics branch. Tracing and logs have their own pipelines; understanding the exact responsibility of each component helps avoid expecting that adding a Prometheus registry will automatically create distributed traces.

## 1. Learning Objectives

After this lesson, you will be able to:

1. Explain when Spring Boot automatically provides a `MeterRegistry` bean, and the role of the registry implementation on the classpath.
2. Distinguish between **SimpleMeterRegistry**, **CompositeMeterRegistry**, and a registry for Prometheus or another backend.
3. Configure Actuator and Prometheus; verify data at `/actuator/metrics` and `/actuator/prometheus`.
4. Inject `MeterRegistry` to record `Counter`, `Timer`, and several business metrics.
5. Apply common tags and configure latency distributions without creating excessively high cardinality.
6. Distinguish data recorded directly by a meter from metrics generated by Micrometer Observation.
7. Diagnose missing metrics, unexpected metric names, scrape errors, and the relationship with tracing/logs.

## 2. What does `MeterRegistry` manage?

Micrometer Metrics provides meter types to describe numerical data. `MeterRegistry` registers, looks up, and provides meters by **name plus tag set**. When code retrieves a meter with the same identifier from the same registry, it typically receives the already-registered meter.

| Meter type | Measured information | Practical example |
| --- | --- | --- |
| `Counter` | Monotonically increasing event count. | Number of successful or rejected payments. |
| `Timer` | Call count and total duration, optionally with distributions. | Price calculation time, HTTP processing time. |
| `Gauge` | Current value at the time of observation. | Number of elements in a queue. |
| `DistributionSummary` | Distribution of non-time measurements. | Message size in bytes. |
| `LongTaskTimer` | Number of long-running active tasks and their durations. | Long batch job or process that needs tracking while running. |

For example, a `Timer` typically has a count and total duration. With a Prometheus registry, timer data can be exported as time series such as `_seconds_count` and `_seconds_sum`; histogram buckets require appropriate configuration.

**MeterRegistry is not a monitoring data store.** It is the layer for recording and exporting measurements. A Prometheus registry typically lets a Prometheus server **scrape** data; some other registries can push data to an external service.

~~~mermaid
flowchart LR
    A["Spring Boot request / business code"] --> B["Meter or Micrometer Observation"]
    B --> C["Auto-configured MeterRegistry"]
    C --> D["Simple/Composite/Prometheus registry"]
    D --> E["Actuator or exporter"]
    E --> F["Metrics backend and dashboard"]
    B --> G["Tracing handler if configured"]
    G --> H["Trace exporter and backend"]
    A --> I["Logs / MDC if configured by app"]
~~~

The diagram illustrates only the conceptual flow. An observation requires a **metrics observation handler** to produce measurements in `MeterRegistry`; it also requires a separate **tracing handler** and exporter if spans are desired. Logs are usually produced by the logging framework and can be correlated with traces via MDC when appropriate tracing integration is enabled.

## 3. Spring Boot auto-configures the registry based on the classpath

The auto-configuration mechanism relies on beans, libraries, and properties present at startup:

1. Adding `spring-boot-starter-actuator` brings the Actuator and Micrometer infrastructure into a standard Spring Boot application.
2. Spring Boot detects supported registry implementations on the classpath and configures the corresponding registry bean if auto-configuration conditions are met.
3. Spring Boot often configures a **composite meter registry** so measurements can be forwarded to underlying registries.
4. If no specific backend registry is present yet, an in-memory **SimpleMeterRegistry** can act as a fallback when configuration allows.
5. Spring Boot can register supported meter binders/instrumentation for JVM, process, HTTP, connection pools, or other integrations.
6. You inject the `MeterRegistry` bean to record metrics; exporters and external collection systems are responsible for bringing data into dashboards.

You do not need to manually define a `SimpleMeterRegistry` or `PrometheusMeterRegistry` bean in every service if the application already uses proper auto-configuration.

### Three commonly encountered registry types

| Type | Purpose | Limitations |
| --- | --- | --- |
| **Simple** | Stores measurements in memory, suitable for local observation or testing. | Does not automatically send measurements to a centralized backend. |
| **Composite** | Combines multiple registries, allowing application code to record through a single point. | Each child registry may have its own naming/representation rules. |
| **Prometheus** | Provides a data format for Prometheus to collect. | Requires a scrapeable endpoint and corresponding Prometheus server/config. |

Auto-configured **does not mean** Spring Boot automatically installs a Prometheus server, trace collector, or log backend. An application may record metrics accurately yet have no external place storing them.

When an application already defines a custom `MeterRegistry` bean or has multiple registry implementations, the behavior may differ from the simple pattern above; inspect bean definitions and actual endpoints before drawing conclusions.

## 4. Enabling Actuator and the Prometheus registry

Gradle example for a **Spring Boot 3.x** application using Spring MVC:

~~~groovy
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
    implementation 'io.micrometer:micrometer-registry-prometheus'
}
~~~

Spring Boot normally manages compatible Micrometer versions via dependency management/BOM. Avoid arbitrarily pinning a Micrometer version different from the dependency set Spring Boot manages.

Example `application.yml` for a testing environment:

~~~yaml
spring:
  application:
    name: order-api

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    tags:
      application: order-api
      environment: local
~~~

Key points to understand:

- Actuator provides endpoints to inspect metrics and the instrumentation infrastructure.
- `micrometer-registry-prometheus` allows Spring Boot to auto-configure the Prometheus registry when conditions are met.
- `management.endpoints.web.exposure.include` specifies which endpoints are exposed over the web.
- `management.metrics.tags` adds common tags with stable values to meters.

**Security:** do not expose management/metrics endpoints broadly to the Internet. Use appropriate management ports, network policies, and security rules. Only expose endpoints that are actually needed.

### Direct verification

Start the application, send a few requests to a controller, and then verify:

~~~bash
curl -i http://localhost:8080/actuator/health
curl -s http://localhost:8080/actuator/metrics
curl -s http://localhost:8080/actuator/metrics/http.server.requests
curl -s http://localhost:8080/actuator/prometheus
~~~

Expected results:

- `/actuator/metrics` lists the **meter names** that currently have data.
- `/actuator/metrics/http.server.requests` returns HTTP server data if the corresponding instrumentation has recorded requests.
- `/actuator/prometheus` serves data in the Prometheus registry format.
- Actuator meter names such as `http.server.requests` may be converted into Prometheus names such as `http_server_requests_seconds_count`.

If there has been no traffic yet or the metric-recording code path has not executed, a specific meter may not appear yet. Having data at the metrics endpoint also does not prove that the Prometheus server is scraping successfully.

## 5. Injecting `MeterRegistry` instead of instantiating a registry manually

A Spring service can receive the registry provided by Spring Boot via its constructor:

~~~java
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.stereotype.Service;

@Service
public class CheckoutMetrics {
    private final MeterRegistry registry;

    public CheckoutMetrics(MeterRegistry registry) {
        this.registry = registry;
    }

    public void success() {
        registry.counter("checkout.completed", "outcome", "success")
                .increment();
    }

    public void failure() {
        registry.counter("checkout.completed", "outcome", "error")
                .increment();
    }
}
~~~

In this example, the values `success` and `error` form a finite set, making them suitable as **low-cardinality tags**. `MeterRegistry` reuses the counter by name and tags; each `increment()` call increments the event count in that meter.

Because `CheckoutMetrics` is a regular Spring bean, **no new metrics are recorded just because the bean exists**. A controller or service must invoke `success()` or `failure()` in the business flow. If both the controller and the service increment the counter for a single event, the metric will be double-counted.

Check after exercising the business flow:

~~~bash
curl -s http://localhost:8080/actuator/metrics/checkout.completed
~~~

There should be a single responsible place emitting each business metric, with clear definitions of "success", "failure", "retry", and "business rejection".

## 6. Measuring latency with `Timer`

Suppose `PricingService` calculates the price of an order and needs to record the duration of each calculation:

~~~java
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import org.springframework.stereotype.Service;

@Service
public class PricingService {
    private final MeterRegistry registry;
    private final PricingEngine engine;

    public PricingService(MeterRegistry registry, PricingEngine engine) {
        this.registry = registry;
        this.engine = engine;
    }

    public Price calculate(PriceRequest request) {
        Timer timer = Timer.builder("pricing.calculate")
                .description("Time spent calculating prices")
                .tag("operation", "calculate")
                .register(registry);

        return timer.record(() -> engine.calculate(request));
    }

    public interface PricingEngine {
        Price calculate(PriceRequest request);
    }

    public record PriceRequest(String currency, int itemCount) {}
    public record Price(long minorUnits, String currency) {}
}
~~~

`Timer.record(...)` measures the execution time of the lambda. If an exception is thrown, the timer still records the duration, but **does not automatically create a separate "error" outcome label**. When outcomes need to be distinguished, design an error status according to business semantics or use `Timer.Sample`.

### Outcome known only after processing

~~~java
Timer.Sample sample = Timer.start(registry);
String outcome = "success";

try {
    return engine.calculate(request);
} catch (RuntimeException exception) {
    outcome = "error";
    throw exception;
} finally {
    Timer timer = Timer.builder("pricing.calculate")
            .tag("outcome", outcome)
            .register(registry);
    sample.stop(timer);
}
~~~

The snippet above illustrates the logic inside a method with an appropriate return type. `Timer.Sample` starts timing, then selects the timer matching the outcome to stop. If "insufficient funds" is a valid business outcome, it does not necessarily have to be recorded with the same `error` tag as a system failure.

Note: timers are created and registered by **name plus tags**. Never use order ID, request ID, email, or raw URL as a tag because each request can create a new meter identifier.

## 7. Commonly seen automatic metrics

Depending on dependencies, beans, binders, and application type, Spring Boot can automatically record the following metric groups:

| Group | Examples | Investigation questions |
| --- | --- | --- |
| **JVM** | Heap, GC pause, thread count. | Does latency coincide with GC or memory pressure? |
| **Process/system** | CPU, uptime, file descriptors depending on platform. | Is the service saturating resources? |
| **HTTP server** | Count, duration, status, method, and route template. | Which route has an elevated error rate or P95? |
| **HTTP client** | Duration of calls to other services when the client is instrumented. | Which dependency is slow? |
| **Connection pool** | Active, idle, and waiting connections depending on the supported library. | Are requests waiting to acquire a connection? |
| **Cache/message/database** | Metrics from the corresponding integration. | Is there a bottleneck in cache, queue, or data source? |
| **Business** | `checkout.completed`, `pricing.calculate`. | What are the business success rate and processing time? |

This list represents **conditional capabilities**, not a guarantee that every application will expose every meter. For example, an HTTP client instantiated manually outside the builder/instrumentation provided by Spring Boot may not emit the expected metrics.

Always inspect the actual list of meters and labels at the endpoint or backend rather than guessing from library names.

## 8. Relationship with Micrometer Observation

In Spring Boot, many operations are instrumented via **Micrometer Observation**. Distinguish the two registries:

| Component | Responsibility |
| --- | --- |
| `ObservationRegistry` | Manages observations, handlers, conventions, filters, and scopes. |
| `Observation` | Describes an operation with a start–stop lifecycle, key-values, and errors. |
| Metrics observation handler | Records measurements from observations into `MeterRegistry`. |
| `MeterRegistry` | Manages counters/timers/gauges and metric-exporting registries. |
| Tracing observation handler | Converts observations into spans when a tracing bridge is configured. |

Custom observation example:

~~~java
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Service;

@Service
public class InventoryService {
    private final ObservationRegistry observationRegistry;
    private final InventoryGateway gateway;

    public InventoryService(ObservationRegistry observationRegistry,
                            InventoryGateway gateway) {
        this.observationRegistry = observationRegistry;
        this.gateway = gateway;
    }

    public Stock reserve(String sku, int quantity) {
        return Observation.createNotStarted("inventory.reserve", observationRegistry)
                .lowCardinalityKeyValue("operation", "reserve")
                .lowCardinalityKeyValue("dependency", "inventory")
                .observe(() -> gateway.reserve(sku, quantity));
    }

    public interface InventoryGateway {
        Stock reserve(String sku, int quantity);
    }

    public record Stock(int quantity) {}
}
~~~

The `observe(...)` pattern manages the lifecycle when the lambda executes synchronously. When a metrics handler is configured, a timing meter can be created for `inventory.reserve`; if a matching tracing bridge/exporter is also added, a tracing span can be created. **A working MeterRegistry alone does not guarantee spans or traces.**

Avoid wrapping the same processing block with a manual `Timer` just to "make sure there are metrics" if an observation already records the same type of measurement with the same meaning. Duplicate instrumentation causes confusion or double counting when reading dashboards.

## 9. Common tags and cardinality

In many metrics backends, each combination of **metric name + full tag set** creates a separate time series. A tag that varies per request can cause the number of series to grow with the number of requests.

Example to avoid:

~~~java
// Almost every request ID is unique: uncontrolled cardinality.
registry.counter("checkout.attempts",
        "requestId", requestId).increment();
~~~

A more appropriate approach:

~~~java
registry.counter("checkout.attempts",
        "operation", "checkout",
        "outcome", "success").increment();
~~~

Tags such as `operation`, `method`, `status`, templated `uri` routes, and `outcome` are usually useful if their value set is small and controlled. `userId`, `orderId`, UUIDs, emails, and raw URLs containing IDs are generally unsuitable for low-cardinality metrics.

### Setting common tags with properties

~~~yaml
management:
  metrics:
    tags:
      application: order-api
      environment: prod
      region: ap-southeast-1
~~~

Common tags are useful for filtering services or environments in dashboards. However, adding many dimensions multiplies the total number of series combinations. Do not put request IDs or current timestamps into common tags.

### Customizing with `MeterRegistryCustomizer`

When Java configuration is needed instead of YAML, Spring Boot supports customizers:

~~~java
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.boot.actuate.autoconfigure.metrics.MeterRegistryCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
class MetricsConfiguration {

    @Bean
    MeterRegistryCustomizer<MeterRegistry> commonTagsCustomizer() {
        return registry -> registry.config()
                .commonTags("team", "checkout");
    }
}
~~~

The customizer configures the registry during Spring Boot's configuration phase. Avoid declaring overlapping tags across multiple sources without verifying the exported output.

## 10. Histograms and P95/P99

`Timer` records duration measurements; computing aggregated percentiles across multiple instances requires an appropriate measurement mechanism. With the Prometheus registry, histogram buckets enable approximating P95/P99 from aggregated data.

Example enabling histograms for the HTTP server timer in Spring Boot 3.x:

~~~yaml
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
~~~

Do not enable histograms indiscriminately for every timer: each set of buckets and label combinations can generate many additional time series, increasing collection and storage costs.

The PromQL examples below assume the registry exports matching metric names and labels; verify them against `/actuator/prometheus` in the actual application.

**Requests per second by route:**

~~~promql
sum(rate(http_server_requests_seconds_count{
  uri="/orders/{id}",method="GET"
}[5m]))
~~~

**HTTP 5xx error rate:**

~~~promql
100 *
sum(rate(http_server_requests_seconds_count{
  uri="/orders/{id}",method="GET",status=~"5.."
}[5m]))
/
sum(rate(http_server_requests_seconds_count{
  uri="/orders/{id}",method="GET"
}[5m]))
~~~

**P95 latency from histogram buckets:**

~~~promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_server_requests_seconds_bucket{
      uri="/orders/{id}",method="GET"
    }[5m])
  )
)
~~~

Notes:

- Timer metrics exported to Prometheus in these examples use **seconds** as the unit: `0.25` corresponds to 250 ms.
- Histogram P95 is only available when bucket series exist and query label filters are accurate.
- When multiple services/environments write to Prometheus, add appropriate service/namespace/job filter labels.
- **Do not take the arithmetic mean of per-instance P95 values** to get service-wide P95. Aggregate buckets with compatible boundaries first, then apply `histogram_quantile`.
- At very low traffic, error rates or P95 can fluctuate significantly; choose an appropriate time window and traffic threshold.
- When the denominator is zero, the error rate may be undefined; dashboards and alerts must handle that case.

## 11. `MeterFilter` and control rules

`MeterFilter` operates at the metrics registry layer, allowing you to block a category of meters or adjust meter metadata. Example of blocking an unnecessary group of debug metrics:

~~~java
import io.micrometer.core.instrument.config.MeterFilter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
class MetricsPolicyConfiguration {

    @Bean
    MeterFilter denyDebugMeters() {
        return MeterFilter.deny(id ->
                id.getName().startsWith("internal.debug."));
    }
}
~~~

This illustrates how to apply a clearly scoped rule. Avoid accidentally denying metrics related to errors, latency, or SLOs. If high cardinality is caused by poor tag design, the sustainable fix is to **redesign the tags** rather than denying the entire business metric.

`MeterFilter` does not replace `ObservationPredicate` or tracing sampling:

- `MeterFilter` intervenes in **meter registration** at the metrics registry.
- `ObservationPredicate` can exclude observations at the Micrometer Observation layer.
- Tracing sampling decides which fraction of **distributed traces** is recorded/retained based on the stack and pipeline.

Filtering out a meter does not automatically stop a logger from emitting log lines or disable tracing spans for the associated observation.

## 12. MeterRegistry, logs, and distributed tracing

Metrics are **aggregated** signals: "how many requests failed?", "when did P95 increase?", "which route is affected?". They do not directly explain the complete path of an individual request.

When an application has proper Micrometer Tracing configured:

- Tracing can use W3C `traceparent` to propagate trace context over HTTP or other carriers.
- Logs can include `traceId` and `spanId` in MDC, making it easier to locate specific events.
- A retained trace can show parent/child spans, retries, network time, and dependency latency.
- The exporter, collector, backend, and **sampling** determine which traces are stored and queryable.

Example: HTTP server metrics count 10,000 requests, of which 200 failed. The trace backend may store only a subset of requests due to sampling. This **does not mean metrics lost 90% of data**; metrics and traces have separate pipelines.

Conversely, having a tracing exporter does not automatically enable Prometheus metrics; the two exporters do not replace each other. If a trace breaks at a service boundary, check context propagation, client instrumentation, and async boundaries—it cannot be fixed by adding more metric tags.

## 13. Runbook: how metrics help isolate an incident

Suppose after a deployment, the P95 of `POST /checkout` rises from 200 ms to 1.4 seconds, while requests per second stay nearly constant.

1. **Confirm baseline parameters:** service, environment, deployment timestamp, time window, and actual tags from the registry.
2. **Check HTTP metrics:** traffic, error rate, and P95 of `POST /checkout` compared to other routes.
3. **Check JVM and saturation:** CPU, heap/GC, thread pools, connection pools; avoid concluding "CPU is fine so the database is slow" without evidence.
4. **Compare custom metrics:** did `pricing.calculate` increase? How did checkout success/failure counts change?
5. **Open logs in the same time window:** timeouts, retries, exceptions, correlation IDs, and dependency names.
6. **Open several relevant traces:** inspect the critical path and which span consumes the most time, comparing client and server latency.
7. **Confirm with dependency data:** slow queries, queues, pool waits, locks, network, or data from downstream services.
8. **Remediate and re-measure:** monitor P95, error rate, and traffic long enough; a single fast trace is not enough proof that the issue is resolved.

If metrics are missing in steps 2–4, prioritize checking the **data pipeline** (registry, binder, exporter, scrape target) before drawing inferences from an empty dashboard.

## 14. Common issues

| Symptom | Possible cause | How to check |
| --- | --- | --- |
| Cannot inject `MeterRegistry` | Missing dependency or auto-configuration did not create the bean. | Check Actuator/Micrometer on the classpath and bean configuration. |
| `/actuator/metrics` returns 404 | Endpoint not exposed, disabled, or management port/base path changed. | Check properties and security configuration. |
| `/actuator/metrics` works, but `/actuator/prometheus` is missing | Missing Prometheus registry or endpoint not enabled/exposed. | Check dependency and endpoint exposure. |
| App has metrics, but Prometheus does not collect them | Wrong scrape target or network/auth/port issue. | Check target status and raw scrape response. |
| Custom metric not visible | Recording code not invoked; unexpected name/tags or registry. | Trigger the business path and inspect the meter list. |
| P95 query returns empty | Missing histogram buckets or wrong PromQL label filters. | Check `_bucket` and `le` in Prometheus. |
| Latency looks abnormally large/small | Confusing seconds with milliseconds. | Verify the base unit and conversion math. |
| Series count grows with request count | Tag contains request ID, user ID, or raw URL. | Remove high-cardinality tags from metrics. |
| Business counter increments twice | Two layers recording or duplicate instrumentation. | Establish a single authoritative recording source. |
| Metrics exist, but no traces | Misconfigured tracing bridge, sampling, or exporter/collector. | Inspect the tracing pipeline separately. |
| Tracing has spans, but logs lack trace ID | Logging correlation/context inactive or async lost context. | Check MDC pattern, tracing, and propagation. |

## 15. Practice exercises

### Exercise 1: Registry and exporter

An application returns data from `/actuator/metrics/http.server.requests`, but `/actuator/prometheus` returns 404. Does this prove HTTP metrics do not exist?

**Answer:** No. The Actuator metrics endpoint has data, while the Prometheus registry/endpoint may not be configured or exposed yet. Check the `micrometer-registry-prometheus` dependency, endpoint exposure, management port/base path, and security.

### Exercise 2: Which tag is dangerous?

For `checkout.completed`, which options are appropriate tags?

- A. `outcome=success/error`.
- B. `requestId=new-uuid-per-request`.
- C. `paymentProvider=bank-a/bank-b`.
- D. `customerEmail=user@example.com`.

**Answer:** A and C are suitable if their value sets are finite and governed. B and D have high cardinality; D also carries a risk of exposing personal data. Use appropriately authorized logs/traces to investigate an individual request.

### Exercise 3: Composite registry

If an application configures two backend registries, should a service increment the same counter twice to "send to both places"?

**Answer:** No. Code records once through the auto-configured `MeterRegistry` bean; the composite/registries handle forwarding data as configured. Recording twice will corrupt the numbers.

### Exercise 4: Why not average P95s?

Three instances have different traffic levels and latency distributions. A dashboard computes the arithmetic average of each instance's P95. Is this the P95 of the entire service?

**Answer:** No. Percentiles do not aggregate that way. Use histogram buckets with shared boundaries, aggregate `rate(..._bucket[5m])` by `le` and the dimensions to preserve before calling `histogram_quantile`.

### Exercise 5: Metrics present, traces missing

Metrics count 1,000 requests, while the trace backend stores only about 100 traces. Does `MeterRegistry` need to be fixed?

**Answer:** Not without evidence. Tracing may be sampling at 10%, or the exporter/collector may have an issue. Check the tracing pipeline first; metrics and traces have different collection policies.

## 16. Pre-deployment checklist

- [ ] `spring-boot-starter-actuator` and the appropriate registry implementation are on the classpath.
- [ ] The application uses the `MeterRegistry` provided by Spring Boot, avoiding unintended custom registry creation.
- [ ] You know whether the registry is Simple, Composite, or backed by an exporter; and who scrapes/pushes the data.
- [ ] `/actuator/metrics` and `/actuator/prometheus` are exposed only when needed and properly secured.
- [ ] HTTP, JVM, and business metrics actually appear after sending test traffic.
- [ ] Meter names are stable, tags are bounded, and do not contain request IDs or sensitive data.
- [ ] Common tags accurately identify service, environment, or region.
- [ ] Histograms are enabled selectively, and dashboards verify correct units and routes.
- [ ] No duplicate instrumentation causes double counting or conflicting data sources.
- [ ] A procedure exists to check scrape targets, exports, and registries when metrics are missing.
- [ ] Metrics are correlated with logs/traces during investigations; sampling and propagation are well understood.

**Key takeaway:** Spring Boot can **auto-configure MeterRegistry** based on dependencies and environment, enabling applications to measure metrics without manually initializing a registry in every service. To make the data truly useful, choose the right registry/exporter, keep tag cardinality low, verify histograms and pipelines, and combine metrics with logs and distributed tracing to turn anomalous signals into hypotheses and evidence for incident resolution.
