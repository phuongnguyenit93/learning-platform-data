# Registering ApplicationContextInitializer via API or META-INF/spring.factories

**Topic:** Spring Boot Application Runtime → Extension Points. This article explains how to register `ApplicationContextInitializer` using the two mechanisms supported by Spring Boot: calling the `SpringApplication.addInitializers(...)` API when creating the application, and declaring `META-INF/spring.factories` for automatic loading from the classpath. The focus is on **execution timing**, **how to write a valid class**, **configuring for a single application or a shared library**, **ordering**, **packaging**, **runtime evidence**, and **common pitfalls**.

The examples use **Java 17+**, **Spring Boot 3.3.x**, Maven, and Spring MVC. They are designed to compile when generating a project with `Spring Web` from Spring Initializr while keeping the dependencies and plugins generated by Initializr intact. If your project uses a different Spring Boot release line, check the matching version's documentation before copying packages and metadata.

## 1. What is ApplicationContextInitializer?

`ApplicationContextInitializer<C extends ConfigurableApplicationContext>` is a Spring Framework extension point. Its primary method is:

~~~java
void initialize(C applicationContext);
~~~

Spring Boot invokes initializers **after creating and preparing the `ApplicationContext`, but before loading primary bean definitions and before refreshing the context**. When an initializer runs, the context already has an `Environment`; however, many application beans have not been registered yet, and there is no guarantee that `BeanFactory` has finished processing configuration or that singletons have been instantiated.

An initializer is appropriate for:

- Adding or ordering a `PropertySource` that matters for subsequent bean loading and instantiation.
- Configuring context properties within the scope of supported APIs.
- Registering a `BeanFactoryPostProcessor` early via `context.addBeanFactoryPostProcessor(...)` when bean definitions must be processed at the right phase.
- Attaching small bootstrap information that is independent of business beans.
- Providing shared configuration across multiple applications when packaged as a library.

Do not use an initializer to perform regular controller/service work, run long jobs, query created repositories, or call `getBean(...)` to access application singletons. Those tasks belong to the phase after the container has refreshed.

### 1.1. Position of initializers in the startup sequence

~~~text
main()
   |
   v
new SpringApplication(MyApplication.class)
   |        +-- loads initializers declared via spring.factories
   |        +-- accepts additional initializers via addInitializers(...) API
   v
springApplication.run(args)
   |
   +-- prepares Environment, profiles, command-line properties
   +-- creates ConfigurableApplicationContext
   +-- prepares context and attaches Environment
   +-- runs ApplicationContextInitializer.initialize(context)
   +-- ApplicationContextInitializedEvent
   +-- loads bean definitions from primary sources
   +-- ApplicationPreparedEvent
   +-- refreshes ApplicationContext
   |     +-- processes bean definitions and post-processors
   |     +-- creates required singletons
   |     +-- ContextRefreshedEvent
   +-- ApplicationStartedEvent
   +-- ApplicationRunner / CommandLineRunner
   +-- ApplicationReadyEvent
   v
application serves HTTP / processes work
~~~

This is the core sequence for Spring Boot 3.3; internal details may vary between versions. What can be verified reliably is: initializers run **before `ApplicationContextInitializedEvent`**, before `ApplicationPreparedEvent`, and **before `refresh()`**. Therefore, a regular `@Bean` is not a reliable registration mechanism for an initializer that needs to operate during the same startup run: `@Bean` instances are only created when Spring processes the context at a later time.

### 1.2. Two registration approaches

| Criterion | Via `SpringApplication` API | Via `META-INF/spring.factories` |
|---|---|---|
| Registration point | In `main()` or code creating `SpringApplication` | Resource inside a JAR/module on the runtime classpath |
| Core syntax | `app.addInitializers(new MyInitializer())` | `org.springframework.context.ApplicationContextInitializer=...MyInitializer` |
| Scope | The configured `SpringApplication` instance | Any `SpringApplication` that sees the resource on the classpath |
| Instantiation | Code instantiates the object directly | Spring Boot loads the class and creates an instance per the factories contract |
| Best suited for | Single-application setup, runtime-chosen wiring | Shared libraries, self-registering integration modules |
| Verification | Add log markers, inspect `getInitializers()` and outcomes | Check `spring.factories` in the artifact/classpath, logs, and outcomes |
| Common traps | Calling `addInitializers` after `run`, mistakenly using `setInitializers` | Wrong key, wrong FQCN, missing file in JAR, invalid constructor |

Both approaches ultimately cause Spring Boot to invoke `initialize(...)` on an initializer instance. They differ mainly in where configuration lives and how the initializer is discovered.

## 2. Contract and limits of initialize(...)

A valid initializer that can be used while the context is not yet refreshed:

~~~java
package com.example.initializerlab;

import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;

public final class SimpleInitializer
        implements ApplicationContextInitializer<ConfigurableApplicationContext> {

    @Override
    public void initialize(ConfigurableApplicationContext context) {
        System.out.println("LAB_SIMPLE_INITIALIZER");
    }
}
~~~

The generic interface parameter is chosen as `ConfigurableApplicationContext` because it works across servlet, reactive, and non-web contexts. If you use an overly narrow type parameter, such as accepting only a servlet context subclass, running the application with a different context can cause type or startup errors; verify the actual `WebApplicationType` and context class.

**What you can rely on at this moment:**

1. There is a `ConfigurableApplicationContext` created by Spring Boot.
2. You can obtain `context.getEnvironment()` to read or add prepared configuration sources.
3. You can register additional BeanFactory-related hooks before refresh.
4. You must not treat this as a fully initialized container; normally do not call `context.getBean(MyService.class)`.
5. Do not call `context.refresh()` inside an initializer: `SpringApplication` orchestrates refresh; calling it early can cause configuration to be processed out of order.
6. Do not assume all startup events have fired or that the embedded server is already listening on its port.

Clearly distinguish modifying properties **at initializer time** from modifying properties **very early** when Spring Boot is resolving config-data locations. Several configuration decisions (especially locating and loading `application.properties` / `application.yml`) have already occurred before initializers are called. If you must intervene during `Environment` and config-data preparation, study `EnvironmentPostProcessor` or an appropriate bootstrap mechanism; do not use an initializer to change `spring.config.location` late and expect Spring to reload everything automatically.

### 3.1. Main class: registering via API

File `src/main/java/com/example/initializerlab/InitializerLabApplication.java`:

~~~java
package com.example.initializerlab;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.event.ApplicationContextInitializedEvent;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.context.ApplicationListener;
import org.springframework.context.event.EventListener;

@SpringBootApplication
public class InitializerLabApplication {

    public static void main(String[] args) {
        SpringApplication application =
                new SpringApplication(InitializerLabApplication.class);

        // Approach 1: add an initializer specifically for this SpringApplication.
        application.addInitializers(new ApiInitializer());

        // Listener added early to observe the context before refresh.
        application.addListeners(
                (ApplicationListener<ApplicationContextInitializedEvent>) event -> {
                    var env = event.getApplicationContext().getEnvironment();
                    System.out.println("LAB_CONTEXT_INITIALIZED api="
                            + env.getProperty("lab.api.initialized", "false")
                            + " factories="
                            + env.getProperty("lab.factories.initialized", "false"));
                });

        application.run(args);
    }

    @EventListener(ApplicationReadyEvent.class)
    public void onReady() {
        System.out.println("LAB_APPLICATION_READY");
    }
}
~~~

**Important point:** `new SpringApplication(...)` lets you configure the instance before calling `run()`. The shorthand `SpringApplication.run(InitializerLabApplication.class, args)` remains valid for apps needing no extra setup, but in this example we need to hold onto the `SpringApplication` instance to register the initializer.

`ApplicationContextInitializedEvent` is a milestone occurring **after initializers run but before primary bean definitions are loaded**. The listener is registered directly on `SpringApplication` because a listener created via `@Bean` would appear too late for this early event. `ApplicationReadyEvent` is a milestone after refresh and after runners; its log serves as a reference point.

### 3.2. First initializer: registering directly via API

File `src/main/java/com/example/initializerlab/ApiInitializer.java`:

~~~java
package com.example.initializerlab;

import java.util.Map;
import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.Ordered;
import org.springframework.core.env.MapPropertySource;

public final class ApiInitializer
        implements ApplicationContextInitializer<ConfigurableApplicationContext>,
                   Ordered {

    @Override
    public int getOrder() {
        return 0;
    }

    @Override
    public void initialize(ConfigurableApplicationContext context) {
        System.out.println("LAB_API_INITIALIZER");

        context.getEnvironment().getPropertySources().addLast(
                new MapPropertySource(
                        "labApiSource",
                        Map.of("lab.api.initialized", "true")));
    }
}
~~~

`getOrder() == 0` gives this initializer higher priority than the initializer returning `10` in the next example: in `Ordered` ordering, **smaller numbers run first**. Ordering relative to other framework initializers may interleave; only compare the two lab initializers against each other.

`MapPropertySource` is a value source added to `Environment` before the container instantiates application beans. Using `addLast(...)` gives the sample configuration source lower priority than already-prepared property sources. If you intentionally want to override multiple existing sources, `addFirst(...)` has higher priority, though precedence policies should be explicitly designed and documented rather than silently altering operator settings.

The `"true"` value here is a string, and the controller will read that string back. It does not prove every dependency is initialized; it proves the initializer was actually invoked and added a property visible in a later phase.

### 3.3. Second initializer: auto-registering via spring.factories

File `src/main/java/com/example/initializerlab/FactoriesInitializer.java`:

~~~java
package com.example.initializerlab;

import java.util.Map;
import org.springframework.context.ApplicationContextInitializer;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.core.Ordered;
import org.springframework.core.env.MapPropertySource;

public final class FactoriesInitializer
        implements ApplicationContextInitializer<ConfigurableApplicationContext>,
                   Ordered {

    public FactoriesInitializer() {
        // No-arg constructor for the factories loading mechanism.
    }

    @Override
    public int getOrder() {
        return 10;
    }

    @Override
    public void initialize(ConfigurableApplicationContext context) {
        System.out.println("LAB_FACTORIES_INITIALIZER");

        context.getEnvironment().getPropertySources().addLast(
                new MapPropertySource(
                        "labFactoriesSource",
                        Map.of("lab.factories.initialized", "true")));
    }
}
~~~

When loading via `spring.factories`, Spring Boot needs to instantiate the initializer object. In this example, the class is `public`, has a public no-argument constructor, and does not depend on an application bean that has not been created yet. Do not inject `@Autowired SomeService` into the constructor of a factories-loaded initializer expecting the Spring container to supply the service like a bean, because factories instantiation occurs before regular beans are ready.

### 3.4. Declaring META-INF/spring.factories properly

Create **the exact path and filename**:

~~~text
src/main/resources/META-INF/spring.factories
~~~

File contents:

~~~properties
org.springframework.context.ApplicationContextInitializer=com.example.initializerlab.FactoriesInitializer
~~~

This uses Java `.properties` format. The **key** is the fully qualified interface name `org.springframework.context.ApplicationContextInitializer`; the **value** is the fully qualified class name of the implementation. Do not shorten the key to `ApplicationContextInitializer=...`, do not use slashes instead of dots in the FQCN, and do not place the resource beside Java files or inside `src/main/java`.

When declaring multiple initializers under the same key, separate the classes with commas. Syntax example:

~~~properties
org.springframework.context.ApplicationContextInitializer=com.example.initializerlab.FirstInitializer,com.example.initializerlab.SecondInitializer
~~~

The two classes `FirstInitializer` and `SecondInitializer` in the syntax snippet above merely illustrate **list formatting**; they do not belong to the sample project and should not be added to `spring.factories` when running the lab. If splitting across multiple lines using Java properties `\` continuation, ensure line continuations and whitespace are valid; for this exercise, a single line is easiest to inspect.

Multiple JAR libraries can each provide their own `META-INF/spring.factories`. Spring Boot uses classpath factory loading to find matching declarations and instantiate them. This is neither component scanning nor plain Java `ServiceLoader`. If an initializer resides inside a dependency JAR and the `spring.factories` resource resides in that same JAR, an application using that dependency can receive the initializer without modifying `main()`.

### 3.5. Controller verifying the effect of both initializers

File `src/main/java/com/example/initializerlab/InitializerController.java`:

~~~java
package com.example.initializerlab;

import org.springframework.core.env.Environment;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class InitializerController {
    private final Environment environment;

    public InitializerController(Environment environment) {
        this.environment = environment;
    }

    @GetMapping("/initializer-status")
    public InitializerStatus status() {
        return new InitializerStatus(
                environment.getProperty("lab.api.initialized", "false"),
                environment.getProperty("lab.factories.initialized", "false"));
    }

    public record InitializerStatus(String api, String factories) {
    }
}
~~~

`Environment` is injected into the controller bean during refresh. When the endpoint is called, it reads the two values previously set by the initializers. The Java 17 `record` type is serialized to JSON by Jackson in Spring Web. With all files valid and both initializers running, the HTTP body contains:

~~~json
{"api":"true","factories":"true"}
~~~

JSON key order is not an important criterion; only the two keys and correct values matter. If the application is launched with command-line properties of the same names overriding the `addLast` sources, the body will reflect the effective `Environment` values; when testing the registration mechanisms, do not pass such overrides.

## 6. Initializer ordering: Ordered and @Order

Spring Boot sorts the set of initializers using a mechanism compatible with `Ordered`/`@Order`. **Smaller** numeric values have **higher** priority. In the lab:

~~~text
ApiInitializer       order = 0
FactoriesInitializer order = 10

Order between the two initializers: API -> FACTORIES
~~~

You can declare `@Order(5)` on a class when you want to provide ordering metadata instead of implementing `Ordered`. There is no need to use both on a simple class. When two initializers share the same order or declare no order, do not rely on an unguaranteed sequence; if initializer A needs data produced by B, define explicit ordering or merge the logic into one initializer.

**Rule for PropertySource:** multiple initializers calling `addFirst(...)` on the same property name can produce a final precedence different from intuition: the initializer that runs later can push its new source to the front and override the value of an initializer that ran earlier. In the lab, each initializer uses a distinct source name and property key alongside `addLast(...)`, avoiding conflicts. In production systems, document ordering, source names, and override policies clearly for easier diagnosis.

Do not assume the order of initializers you register is determined solely by "API first, factories second". `Ordered` is the explicit tool when both mechanisms coexist.

## 7. addInitializers, setInitializers, and SpringApplicationBuilder

### 7.1. addInitializers(...) appends to the existing set

~~~java
SpringApplication app = new SpringApplication(MyApplication.class);
app.addInitializers(new MyInitializer());
app.run(args);
~~~

This **snippet** assumes `MyApplication` and `MyInitializer` already exist in the project. `addInitializers(...)` adds an initializer to the current `SpringApplication`. If you want an initializer applied across multiple apps, call the method when creating each instance or package it via the factories mechanism.

### 7.2. setInitializers(...) resets the initializer set

`SpringApplication.setInitializers(Collection<? extends ApplicationContextInitializer<?>>)` sets the list of initializers on the instance. It can replace initializers previously supplied by the framework or dependencies; careless use will discard important configuration. When the goal is only to add an initializer, **prefer `addInitializers(...)`**.

`SpringApplication.getInitializers()` lets you inspect the set of initializers registered on the instance at the time of inspection. It is useful for debugging, though a class appearing in the list is not proof that `initialize(...)` ran successfully; you still need markers or observable effects.

### 7.3. Using SpringApplicationBuilder

If the project already uses the builder, equivalent registration can be done as:

~~~java
new SpringApplicationBuilder(MyApplication.class)
        .initializers(new MyInitializer())
        .run(args);
~~~

This is a syntax example placed inside `main()` once the required classes and imports exist. With `SpringApplicationBuilder`, the initializer is added to the application built by the builder. Do not create a separate `SpringApplication` instance just to call `addInitializers` alongside it, as doing so can accidentally run two applications.

## 8. Placing an initializer inside a reusable library JAR

Suppose a `runtime-common` module contains `CommonContextInitializer` and the resource:

~~~text
runtime-common/
  src/main/java/com/example/common/CommonContextInitializer.java
  src/main/resources/META-INF/spring.factories
~~~

Example `spring.factories` in the library:

~~~properties
org.springframework.context.ApplicationContextInitializer=com.example.common.CommonContextInitializer
~~~

After packaging the library, services A and B only need to put the `runtime-common` JAR onto their **runtime classpath**. Spring Boot can discover the resource and load the initializer from the JAR without modifying each service's `main()`. This mechanism is helpful for infrastructure modules, though it also applies globally across any application using the library.

**Library design rules:**

1. The initializer must be independent enough to run before application beans exist.
2. Constructors used for factories should be simple and instantiable by Spring's factories loading mechanism; do not depend on container constructor injection like a `@Component`.
3. Use `Ordered` if a stable order relative to other initializers is needed.
4. Limit side effects: do not open long-lived network connections, write arbitrary files, spawn long-lived threads, or print secrets.
5. Provide an enable/disable toggle via available configuration sources if the initializer has significant impact, while understanding that the initializer itself is already loaded before deciding whether to run its logic.
6. Ensure the JAR preserves `META-INF/spring.factories` when shading/merging or repackaging. Some build configurations may overwrite another dependency's resource instead of merging factory entries.
7. When supporting multiple Spring Boot versions, verify the API and loading process on each version; do not assume auto-configuration metadata is the same as initializer metadata.

**Do not confuse metadata types:** Spring Boot 3.x uses `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` for auto-configuration registration. `ApplicationContextInitializer` still uses `META-INF/spring.factories` per the contract described here. Moving an initializer into `AutoConfiguration.imports` will not register this kind of extension point properly.

## 9. Context initialization failure scenarios

If `initialize(...)` throws an exception, `SpringApplication` may abort startup before context refresh, and you will not see the ready marker. For example, replace the `initialize(...)` method body in a separate test copy with:

~~~java
@Override
public void initialize(ConfigurableApplicationContext context) {
    System.out.println("LAB_INITIALIZER_BEFORE_FAILURE");
    throw new IllegalStateException("LAB_INTENTIONAL_INITIALIZER_FAILURE");
}
~~~

This is a **method-replacement snippet**, not a standalone file. Run the test copy in the lab environment and inspect the `LAB_INTENTIONAL_INITIALIZER_FAILURE` line in the stack trace. Startup failure due to an initializer **differs from** a bean init error (`@PostConstruct`) during refresh and also differs from a runner failure after refresh.

In such an early failure, an `@EventListener` on an application bean may not have been created yet to receive the failure event. If you need to observe `ApplicationFailedEvent`, register an `ApplicationListener` with `SpringApplication.addListeners(...)` before `run(...)` and use a listener with minimal dependencies.

**Do not** solve this by catching every exception and continuing silently, because the context might be missing vital configuration while the application still starts. Only handle errors that truly have a defined fallback path.

## 10. Diagnosing when an initializer does not run

| Symptom | Common cause | Verification step |
|---|---|---|
| API initializer marker missing | Forgot to call `addInitializers` before `run`, or ran the wrong main class | Check the call in the executed main class, compare command and logs |
| Factories marker missing | Wrong `ApplicationContextInitializer` key or wrong resource path | Open `src/main/resources/META-INF/spring.factories`, inspect build output |
| Works via Maven but JAR lacks marker | Resource/class omitted from packaged JAR or running a stale artifact | Run `jar tf` to check for `BOOT-INF/classes/META-INF/spring.factories`; clean build |
| `ClassNotFoundException` / factory instantiation error | Wrong FQCN, class missing on runtime classpath, incompatible constructor | Verify package/class name, dependency scope, root stack trace |
| `ClassCastException` or context type error | Overly specific generic initializer for servlet/reactive/none context differing from actual | Check `WebApplicationType`, context class, and generic bound |
| Marker present but property missing in controller | Wrong PropertySource name/key, modified another Environment, overridden by higher-priority source | Print source names and read `Environment.getProperty(...)` |
| Two initializers run duplicate logic | Registered the same behavior via both API and factories | Check `getInitializers()`, classpath, logs, and side effects |
| Initializer instantiated but fails before final marker | Exception in constructor or `initialize(...)` | Read `Caused by` and the marker immediately before the error |
| Calling `getBean(...)` in initializer reports context not active | BeanFactory/context has not refreshed yet | Move code to a bean, post-processor, runner, or appropriate event |
| Changed `spring.config.location` in initializer but config did not reload | Config data was already processed earlier than initializers | Use an appropriate early environment mechanism |
| Unexpected property override order | `addFirst`, `addLast`, or `Ordered` differs from expectations | Log precedence and initialization order, use distinct source names |
| Initializer missing in tests or non-web mode | Different test bootstrap or initializer only compatible with web contexts | Check how `SpringApplication` is created, test framework, and context type |

If you need to set breakpoints, stop at `SpringApplication.applyInitializers(...)`, `ApiInitializer.initialize(...)`, and `FactoriesInitializer.initialize(...)`; inspect the unrefreshed `ApplicationContext` and verify `Environment` has the added source. There is no need to inspect all runtime beans to confirm an initializer was invoked.

## 11. Distinguishing initializers from neighboring extension points

| Mechanism | Typical timing | Used for | Must not expect |
|---|---|---|---|
| `ApplicationContextInitializer` | Context created, before primary bean definitions and refresh | Modifying context/Environment, registering early hooks | Accessing initialized services/repositories |
| `EnvironmentPostProcessor` | During Environment preparation phase | Adding/adjusting early config sources per Boot contract | Accessing a full ApplicationContext |
| `BeanFactoryPostProcessor` | During refresh, before normal singleton beans are created | Adjusting bean definition metadata | Running request logic |
| `BeanPostProcessor` | As each bean instance is created/initialized | Injection, init hooks, proxies, wrapping beans | Being called before context creation |
| `ApplicationListener<ApplicationContextInitializedEvent>` | After all initializers have been applied | Observing context initialized | Treating it as ready for HTTP |
| `ApplicationRunner` | After refresh, before `ApplicationReadyEvent` | Application-level tasks that must finish before ready | Intervening in already-completed context creation steps |
| `ApplicationReadyEvent` | After runners | Recording final startup milestone | Running long tasks while guaranteeing traffic is blocked |

**Why not replace everything with `@Component`?** Component scanning happens during configuration processing and refresh. A `@Component` class may become a bean afterward, but that does not put it into the set of initializers `SpringApplication` already used before refresh. If the goal is pre-refresh intervention, you must register it properly on `SpringApplication`.

**Why not replace `spring.factories` with `@AutoConfiguration`?** Auto-configuration configures bean definitions conditionally during refresh. Initializers run earlier to customize the context. Both mechanisms solve different phases, even though both can live inside a Spring Boot library.

## 12. Operational notes and proper design

- **Idempotency:** initializers should tolerate multiple contexts being created in tests, restarts, parent/child contexts, or multiple apps in one JVM. If idempotency is needed, check whether the `PropertySource` name already exists before adding it or use an appropriate guard.
- **Multi-context:** the same initializer can be applied multiple times across different context instances; do not use mutable static state as proof that the entire JVM only initialized once.
- **Class dependency:** factories are loaded by fully qualified class name, so renaming a package or class requires updating metadata. A build may still succeed if metadata points to a missing class, surfacing the error only at runtime.
- **Resource merging:** when packaging a fat JAR with tools other than the Boot Maven plugin, preserve all dependencies' `spring.factories`; losing metadata can alter system behavior without changing Java source code.
- **Property precedence:** sources added to `Environment` occupy a priority slot. The example uses `addLast` to avoid overriding pre-existing sources; in production, establish which data source owns each property.
- **Startup time:** do not run database migrations, slow HTTP calls, or unbounded waits inside an initializer because it blocks refresh. Post-refresh tasks belong in runners with proper timeouts and readiness checks.
- **Security:** never dump the entire `Environment` or secrets into logs. When markers are needed, only log source names, non-sensitive booleans, context class names, and timestamps.
- **Testability:** a working initializer should produce stable input/output evidence. The lab's marker logs and HTTP properties allow verification without depending on Spring's internal bean counts.
- **Version upgrades:** Spring Boot 3.3 uses the mechanisms above; after upgrading, review the new version's docs on factory loading, metadata, web contexts, and event ordering.
