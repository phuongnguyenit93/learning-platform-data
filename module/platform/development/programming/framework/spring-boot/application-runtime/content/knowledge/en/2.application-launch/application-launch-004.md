# Return Value ConfigurableApplicationContext and When SpringApplication.run Completes

## 1. What Does SpringApplication.run(...) Return?

In a Spring Boot application, the **SpringApplication.run(...)** call starts a run of the application and, if successful, returns an object of type **org.springframework.context.ConfigurableApplicationContext**. This is the Spring IoC container that has been created, configured, and refreshed for that run. It manages beans, the configuration environment, application events, and the lifecycle of the context.

~~~java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ConfigurableApplicationContext;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        ConfigurableApplicationContext context =
                SpringApplication.run(DemoApplication.class, args);

        System.out.println("Context active: " + context.isActive());
    }
}
~~~

In a normal startup, the line printed after the run call outputs **Context active: true**. Startup logs generated by Spring Boot may appear before this line and vary according to configuration.

The two common ways of calling have the same return value type:

~~~java
// Convenient style using default configuration:
ConfigurableApplicationContext context =
        SpringApplication.run(DemoApplication.class, args);

// Creating SpringApplication directly to customize before running:
SpringApplication app = new SpringApplication(DemoApplication.class);
// app.setAdditionalProfiles("dev"); // Customization example if needed
ConfigurableApplicationContext anotherContext = app.run(args);
~~~

The two statements in the example above illustrate **two independent call styles**; do not place both in a real main flow if you only want to launch one application. The concrete context class depends on the application type and configuration: servlet, reactive, and non-web applications can use different context implementations. Therefore, program against the **ConfigurableApplicationContext** interface and avoid casting to a fixed implementation.

## 2. What Is ConfigurableApplicationContext Used For?

**ApplicationContext** provides access to Spring-managed beans; **ConfigurableApplicationContext** also provides lifecycle management operations such as closing the context. Common capabilities:

| API | Meaning | Notes |
| --- | --- | --- |
| **context.getBean(MyService.class)** | Retrieves a managed bean by type | Fails if none exists or multiple matching beans cannot be disambiguated |
| **context.getEnvironment()** | Reads active properties and profiles | Properties are subject to configuration source precedence order |
| **context.isActive()** | Checks whether the context is in the active state | Not equivalent to all external services being healthy |
| **context.getId()** | Retrieves the identifier of the context | Useful when diagnosing multiple contexts |
| **context.close()** | Closes the context, destroys applicable singletons, and releases resources | Can stop the web server; call only when you genuinely want to end the lifecycle |

Example illustrating accessing a registered bean:

~~~java
ConfigurableApplicationContext context =
        SpringApplication.run(DemoApplication.class, args);

MyService service = context.getBean(MyService.class);
service.doWork();
~~~

This snippet **assumes** the project has a **MyService** bean and a **doWork()** method; it illustrates how to use the context, not a standalone program. In everyday application code, prefer constructor injection to receive dependencies; there is no need to pass the context object across layers solely to look up beans.

Holding a reference to the context is useful in bootstrap code, integration tests, or command-driven applications. For typical web applications, you do not need to call **close()** right after **run(...)**: doing so begins shutting down the application that just started.

## 3. What Exactly Does "run Completes" Mean?

A common misconception is treating **context refresh finished** and **the run method returning** as the same milestone. Spring Boot still executes callbacks and publishes events in between.

Key sequence during a successful startup (Spring Boot 3.x, default event publishing):

1. Prepare Environment, create ApplicationContext, register configuration and bean definitions.
2. **Refresh context**: triggers creation/initialization of non-lazy singletons and processes container lifecycle; for web applications, the web server is typically initialized during this stage.
3. Publish **ApplicationStartedEvent**: context has refreshed, but **ApplicationRunner/CommandLineRunner have not yet been called**.
4. Publish liveness signal **LivenessState.CORRECT**.
5. Invoke **ApplicationRunner** and **CommandLineRunner** beans. If there are multiple runners, use **@Order** or **Ordered** when an explicit order is required.
6. Publish **ApplicationReadyEvent**, then readiness signal **ReadinessState.ACCEPTING_TRAFFIC**.
7. **SpringApplication.run(...) returns ConfigurableApplicationContext** to the caller; subsequent statements in **main** only run after this.

Condensed timeline:

~~~text
main: before run
    |
    v
prepare + refresh ApplicationContext
    |
    v
ApplicationStartedEvent
    |
    v
ApplicationRunner / CommandLineRunner
    |
    v
ApplicationReadyEvent
    |
    v
ReadinessState.ACCEPTING_TRAFFIC
    |
    v
run(...) RETURNS context
    |
    v
main: next statement
~~~

**Consequence:** if code inside a runner executes synchronously and has not finished yet, the **run(...)** call has not returned yet. If a listener handles events via the default synchronous mechanism, listener execution also sits on the startup path before the return point. However, work offloaded to another thread, scheduler, or queue system is not automatically awaited until completion.

**ContextRefreshedEvent** also occurs when the context is refreshed, earlier than **ApplicationStartedEvent**. Do not confuse this event with the "entire application is ready" milestone.

## 4. Runnable Example: Observing the Order Yourself

The example below uses **Java 17+** and a **Spring Boot 3.x** project with the **spring-boot-starter** dependency. Place the file **src/main/java/com/example/runtime/RuntimeDemoApplication.java** in a Boot project with an appropriate build plugin configured. Set the application type to **NONE** so no web server is created, keeping the example focused on the lifecycle.

~~~java
package com.example.runtime;

import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.WebApplicationType;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.boot.context.event.ApplicationStartedEvent;
import org.springframework.context.ApplicationListener;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.Bean;

@SpringBootApplication
public class RuntimeDemoApplication {

    public static void main(String[] args) {
        System.out.println("1 | Before run");

        SpringApplication app =
                new SpringApplication(RuntimeDemoApplication.class);
        app.setWebApplicationType(WebApplicationType.NONE);

        ConfigurableApplicationContext context = app.run(args);

        System.out.println(
                "5 | After run; context active = " + context.isActive());
    }

    @Bean
    ApplicationListener<ApplicationStartedEvent> startedListener() {
        return event ->
                System.out.println("2 | ApplicationStartedEvent");
    }

    @Bean
    ApplicationRunner startupRunner() {
        return arguments ->
                System.out.println("3 | ApplicationRunner");
    }

    @Bean
    ApplicationListener<ApplicationReadyEvent> readyListener() {
        return event ->
                System.out.println("4 | ApplicationReadyEvent");
    }
}
~~~

Run with the Boot project's Gradle Wrapper (first command for Linux/macOS, second command for Windows):

~~~bash
./gradlew bootRun
~~~

~~~powershell
.\gradlew.bat bootRun
~~~

Among the lines printed by the program itself, the **exact expected order** is:

~~~text
1 | Before run
2 | ApplicationStartedEvent
3 | ApplicationRunner
4 | ApplicationReadyEvent
5 | After run; context active = true
~~~

The banner log, startup timing, and Spring Boot messages may appear interleaved between these lines. The example illustrates the exact timeline: **ApplicationStartedEvent** does not mean runners are done; **ApplicationReadyEvent** comes after runners; only after that does code after **app.run(args)** execute.

Note that the example is a **non-web** application. If no non-daemon threads remain to keep the JVM alive, the process may exit after **main** finishes. In servlet/reactive applications, the web server and runtime components typically keep the process running after **run(...)** has returned.

## 5. Distinguishing "started", "ready", and "Process Termination"

| Milestone | What Has Happened | What Cannot Be Inferred Yet |
| --- | --- | --- |
| Context refresh complete | Container has initialized eagerly and refresh steps succeeded | Runners have finished, all lazy beans have been instantiated |
| ApplicationStartedEvent | Context has refreshed, runners have not run yet | Application has completed startup tasks |
| ApplicationReadyEvent | Runners have finished executing successfully | All asynchronous tasks or external systems have finished |
| run(...) returns | Synchronous SpringApplication startup chain succeeded up to return | JVM has exited or web server has stopped |
| JVM process terminates | No threads keep JVM alive or process shutdown was requested | Cannot infer this solely from when run returns |

**For web apps:** the server can bind its port during refresh, meaning **before** runners finish and before **ApplicationReadyEvent** is published. Therefore, "port is open" is not synonymous with "published as ready to accept traffic." On systems with readiness probes, distinguish between when the network listener starts operating and the **ReadinessState.ACCEPTING_TRAFFIC** state. The readiness signal only reflects the state published by the application; it does not by itself guarantee that all external dependencies or background tasks succeeded.

**For batch/CLI apps:** to run one-time logic after the container is ready, place it in a runner. If the program needs to return an exit code and exit cleanly, check the **SpringApplication.exit(context)** contract and appropriate context closing rather than inferring an exit code from **run(...)** returning.

## 6. What Happens When Startup Fails?

If an error occurs during context creation, refresh, runner invocation, or synchronous listeners before the return point, **run(...) does not return a successful context**; Spring Boot handles the startup failure and publishes **ApplicationFailedEvent**. For example, if a runner throws an exception:

~~~java
@Bean
ApplicationRunner failingRunner() {
    return arguments -> {
        throw new IllegalStateException("Data initialization failed");
    };
}
~~~

When this runner is added to the example above, the line **After run; context active = true** will not be printed on the successful startup path as before. You should not write logic assuming "if run returns then initialization errors can be ignored," because errors occurring **before** the return point cut off normal flow.

When bootstrap-level error handling is needed, wrap the **run(...)** call in an appropriate **try/catch** and ensure errors are logged or reported to the operations system. Do not swallow exceptions and declare the application ready.

## 7. Limitations to Keep in Mind

- **Lazy/prototype beans:** an active context does not mean all beans exist as instances. Lazy beans may only be created when actually requested; prototype beans are not instantiated all at once during refresh.
- **Background tasks:** **@Async**, schedulers, custom threads, message consumers, and I/O started asynchronously may still be running after **ApplicationReadyEvent** and after **run(...)** returns. If readiness depends on their results, design explicit state signaling and synchronization.
- **Long-running runners:** a runner doing synchronous work for too long delays **run(...)** from returning and delays the ready milestone. For work that does not need to block readiness, consider an appropriately monitored background mechanism.
- **Closing the context:** do not call **context.close()** immediately after **run(...)** in a long-running web application serving requests. Use intentional shutdown mechanisms so beans and resources close according to lifecycle.
- **Order across multiple runners:** relying solely on the **ApplicationRunner** and **CommandLineRunner** interfaces does not establish a fixed business order; declare **@Order** or **Ordered** when order matters.
- **Milestone names:** in Spring Boot 3.x, **ApplicationStartedEvent** occurs **after refresh, before runners**. Do not infer behavior solely from the name while ignoring the concrete lifecycle order.
- **Reading context state:** **isActive() == true** is the state of the Spring context, different from system-level health checks and readiness. Check service health via appropriate health/readiness mechanisms in operations.

## 8. Self-Check Questions

**Scenario A.** In main, there is **System.out.println("after")** immediately after **SpringApplication.run(...)**. An **ApplicationRunner** runs synchronously for 5 seconds. Will the "after" line be printed while the runner is still running?

**Answer:** No, if the runner belongs to that same startup run and does not offload work to another thread. Spring Boot waits for the runner callback to return before transitioning to the ready milestone and returning from **run(...)**.

**Scenario B.** The web server has started listening on port 8080, but **ApplicationRunner** has not finished yet. Can we assert that the application has already published **ApplicationReadyEvent**?

**Answer:** Not yet. Server port binding can occur during refresh, before runners; **ApplicationReadyEvent** follows runners.

**Scenario C.** **SpringApplication.run(...)** has returned the context. Is it guaranteed that all initialization tasks running via **@Async** have finished and the JVM is about to exit?

**Answer:** No. Asynchronous work has its own lifecycle; the JVM of a web application usually keeps running long after the run call completes.

## 9. Takeaways to Apply

An accurate way to read the bootstrap snippet is: **SpringApplication.run(...)** returns **ConfigurableApplicationContext** after Spring Boot's synchronous startup chain completes successfully, including context refresh, runners, and ready events in the default order. This result allows calling code to continue using the running container; it does **not** mean all background tasks have finished or that the application process has terminated.
