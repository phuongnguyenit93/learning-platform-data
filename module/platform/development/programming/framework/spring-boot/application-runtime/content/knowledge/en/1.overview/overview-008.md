# Learning Path Through a Sample Application and Runtime Evidence

**Scope:** Spring Boot Application Runtime. This lesson guides learning through a small Java application where every change has an execution command, an observable signal, and an explanation. The goal is to understand what happens from the moment a Spring Boot process starts until the application serves HTTP, receives configuration, encounters errors, and shuts down.

## 1. Destination and learning principles

After this hands-on lesson, you should be able to prove five things yourself:

1. A Java process is started from a Spring Boot application, creates an `ApplicationContext`, registers beans, and starts an embedded web server.
2. The application is ready to serve requests based on **HTTP evidence and runtime events**, rather than inferring readiness merely because the launch command has not exited.
3. Configuration values and profiles directly affect the behavior of **the exact same codebase**.
4. You can compare observations when running via Maven versus running the packaged JAR file.
5. You can distinguish startup errors, HTTP routing errors, configuration errors, and health status.

**How to learn:** form a hypothesis → run a single experiment → save the command, logs, and HTTP result → explain via Spring Boot mechanics → change one variable to verify again. A sound conclusion must cite concrete evidence rather than stopping at "it works".

## 2. Map of components in the runtime

A web-based Spring Boot application can be understood along the following observation path:

~~~text
java / Maven
    |
    v
main() -> SpringApplication.run(...)
    |
    +--> create Environment; load configuration, profiles, and CLI arguments
    +--> create and refresh ApplicationContext
    |       +--> scan components, instantiate and wire beans
    |       +--> apply auto-configuration by dependencies and conditions
    |       +--> start embedded web server if it is a web application
    +--> run ApplicationRunner / CommandLineRunner
    +--> publish ApplicationReadyEvent
    |
    v
HTTP request -> servlet container -> DispatcherServlet -> controller -> HTTP response
    |
    +--> Actuator provides operational observability endpoints (if added and configured)
    |
Ctrl+C / stop signal -> close ApplicationContext and resources
~~~

The phases above are a **learning model**, not a guarantee of the order of every log line or every bean. `SpringApplication.run` orchestrates the startup lifecycle; `ApplicationContext` manages beans; auto-configuration configures only what satisfies classpath and environment conditions. With **Spring MVC**, the embedded server (typically Tomcat when using the corresponding web starter) accepts connections, while `DispatcherServlet` dispatches requests to controllers.

`ApplicationReadyEvent` occurs after runners finish. It is a good milestone to **observe the startup process**, yet an actual HTTP request is still needed to prove an endpoint responds properly. Actuator health reports the outcome of configured health indicators; `UP` does not mean every business flow is correct.

## 3. Building a single sample application

### 3.1. Preparing the project

Use **JDK 17 or later**, Maven, and a terminal. For Spring Boot **3.5.x**, generate a project from Spring Initializr with the following choices:

- Project: Maven; Language: Java; Group: `com.example`.
- Artifact: `runtime-lab`; Package: `com.example.runtimelab`; Packaging: Jar; Java: 17.
- Dependencies: **Spring Web** and **Spring Boot Actuator**.

Keep the dependencies and plugin versions generated by Initializr. If you are using another Spring Boot version, select the matching web/MVC starter on Initializr for that version and keep the Java source code below intact. No external Tomcat server installation is needed for this lab.

After extracting, the key file tree is:

~~~text
runtime-lab/
  pom.xml
  mvnw
  mvnw.cmd
  src/main/java/com/example/runtimelab/
    RuntimeLabApplication.java
    GreetingController.java
  src/main/resources/
    application.properties
    application-dev.properties
~~~

### 3.2. Main class and lifecycle milestones

Contents of `RuntimeLabApplication.java`:

~~~java
package com.example.runtimelab;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.ApplicationRunner;
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.context.annotation.Bean;
import org.springframework.context.event.EventListener;

@SpringBootApplication
public class RuntimeLabApplication {
    private static final Logger log =
            LoggerFactory.getLogger(RuntimeLabApplication.class);

    public static void main(String[] args) {
        SpringApplication.run(RuntimeLabApplication.class, args);
    }

    @Bean
    ApplicationRunner startupCheck() {
        return args -> log.info("LAB_RUNNER_DONE");
    }

    @EventListener(ApplicationReadyEvent.class)
    public void onReady() {
        log.info("LAB_APPLICATION_READY");
    }
}
~~~

`@SpringBootApplication` combines application configuration, component scanning, and auto-configuration. The runner performs a simple action after the context has been prepared. The listener logs when Spring Boot publishes the ready event. The two strings `LAB_RUNNER_DONE` and `LAB_APPLICATION_READY` are **self-defined markers**, making them easy to locate in logs; they are not default framework messages. In a successful startup, the runner marker appears before the ready marker.

### 3.3. A controller with measurable behavior

Contents of `GreetingController.java`:

~~~java
package com.example.runtimelab;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api")
public class GreetingController {
    private final String prefix;

    public GreetingController(
            @Value("${demo.greeting-prefix:Greetings}") String prefix) {
        this.prefix = prefix;
    }

    @GetMapping("/hello")
    public Greeting hello(
            @RequestParam(defaultValue = "friend") String name) {
        return new Greeting(prefix + ", " + name + "!");
    }

    public record Greeting(String message) {
    }
}
~~~

`@RestController` returns HTTP response data, `@GetMapping` maps the path, and `@RequestParam` reads query parameters. Java 17's `record` type can be serialized to JSON by Jackson included in the web starter. The `prefix` value comes from the configuration environment when the bean is created; this will help verify profiles and overrides.

Contents of `src/main/resources/application.properties`:

~~~properties
spring.application.name=runtime-lab
server.port=8080
demo.greeting-prefix=Greetings
management.endpoints.web.exposure.include=health,info
management.endpoint.health.show-details=never
~~~

Contents of `src/main/resources/application-dev.properties`:

~~~properties
demo.greeting-prefix=Greetings from dev
~~~

The `application-dev.properties` file is used when the `dev` profile is active. Do not and should not put real passwords, tokens, or connection strings into logs or example configurations.

### 3.4. First run and verifying results

From the project root directory, on Linux/macOS:

~~~bash
java -version
./mvnw spring-boot:run
~~~

On Windows PowerShell you can use `java -version` and `./mvnw.cmd spring-boot:run`. Keep this terminal open. In another terminal, send requests:

~~~bash
curl -i "http://localhost:8080/api/hello?name=Lan"
curl -i "http://localhost:8080/actuator/health"
~~~

On Windows PowerShell, use `curl.exe -i` if `curl` is aliased to a different PowerShell cmdlet.

With the sample application and default configuration, the signals to look for are:

~~~http
HTTP/1.1 200
Content-Type: application/json

{"message":"Greetings, Lan!"}
~~~

At the `/actuator/health` endpoint, in a minimal lab environment with no failing dependencies, it usually returns HTTP 200 with equivalent JSON:

~~~json
{"status":"UP"}
~~~

Other headers, timestamps, PID, the order of some logs, or detail fields from health indicators can vary across machines and versions. Do **not** compare the entire log character-by-character; compare the meaningful parts: HTTP status code, body, application name, port, event markers, and root cause of errors.

## 4. Hands-on path with evidence for each stage

Every stage uses the same sample application. Move to the next stage only after capturing at least one observable piece of evidence and one sentence explaining the mechanism.

### Stage 0 — Lock down the environment before running

**Question:** which runtime and build tool will this process use?

Run `java -version`, `./mvnw -version` (or `./mvnw.cmd -version` on Windows) and verify the JDK that Maven actually uses. Inspect `pom.xml` to verify the project uses Java 17 and includes Spring Web and Actuator.

**Evidence:** Java version line; Java home and Maven version; dependencies in `pom.xml`. **Explanation:** a build failing because the JDK is too old is an environment/build issue, not grounds to conclude the web runtime ran incorrectly.

### Stage 1 — Observe startup along the lifecycle

**Question:** which milestones did the application pass through before accepting requests?

Start with `./mvnw spring-boot:run`. Look for signs that the web server started listening on port 8080, `LAB_RUNNER_DONE`, and `LAB_APPLICATION_READY`. Spring Boot versions may log lines like `Started RuntimeLabApplication`; exact wording and position of that line do not need to match verbatim.

**Evidence:** process is alive; runner and ready markers appear; port 8080 starts accepting requests. **Explanation:** context and server are prepared, the runner executes, and then the ready event is published. If a runner throws an exception, startup can fail even though some components were already created.

**Stage pass criterion:** explain the distinct roles of `main`, `SpringApplication`, `ApplicationContext`, runners, and the ready event.

### Stage 2 — Verify requests entering the application

**Question:** does the server "having opened its port" guarantee the controller returns the right response?

Execute:

~~~bash
curl -i "http://localhost:8080/api/hello?name=Lan"
curl -i "http://localhost:8080/api/hello"
curl -i "http://localhost:8080/api/khong-ton-tai"
~~~

The first two requests return HTTP 200 with bodies `{"message":"Greetings, Lan!"}` and `{"message":"Greetings, friend!"}` respectively. The third request returns HTTP 404 because no matching mapping exists; the exact error body shape depends on Spring Boot configuration.

**Evidence:** status and body of each request. **Explanation:** Tomcat accepts connections, Spring MVC looks up the mapping and invokes the controller; no matching mapping leads to 404. An HTTP 404 proves the server may still be up and running, unlike `Connection refused` when no process is listening on that port.

**Stage pass criterion:** distinguish "cannot connect", "connected but 404", and "200 with valid data".

### Stage 3 — Change behavior with externalized configuration

**Question:** is editing Java required to change the greeting or port?

Stop the previous run with Ctrl+C. Package the JAR, then run with configuration arguments:

~~~bash
./mvnw clean package
java -jar target/runtime-lab-0.0.1-SNAPSHOT.jar --server.port=8081 --demo.greeting-prefix=Hello
~~~

The JAR filename above applies if the artifact/version generated by Initializr is `runtime-lab/0.0.1-SNAPSHOT`; if different, check the actual JAR name in `target/`.

From the second terminal:

~~~bash
curl -i "http://localhost:8081/api/hello?name=Lan"
~~~

**Expected evidence:** HTTP 200, body `{"message":"Hello, Lan!"}` on port 8081 without changing Java code. **Explanation:** `--...` arguments are placed into Spring Boot's command-line configuration source and can override application values in `application.properties`.

**Stage pass criterion:** clearly identify the source of `server.port` and `demo.greeting-prefix` across both runs; understand that restarting creates a new configuration environment.

### Stage 4 — Try profiles and compare configuration precedence

**Question:** can the exact same artifact behave differently across environments?

Stop the previous run, then run:

~~~bash
java -jar target/runtime-lab-0.0.1-SNAPSHOT.jar --spring.profiles.active=dev
curl -i "http://localhost:8080/api/hello?name=Lan"
~~~

**Evidence:** logs show the `dev` profile is active and HTTP 200 returns `{"message":"Greetings from dev, Lan!"}`. Next, run a separate launch with both `--spring.profiles.active=dev` and `--demo.greeting-prefix=Hello`; the response changes to `Hello, Lan!`.

**Explanation:** `application-dev.properties` contributes values when the `dev` profile is active; command-line arguments in this experiment take precedence over values in config files. Other configuration sources such as environment variables also exist; when diagnosing, always determine which source won rather than guessing from filenames.

**Stage pass criterion:** present a table of "launch command → profile → prefix value → HTTP body" to explain the differences.

### Stage 5 — Use Actuator for its intended purpose

**Question:** what does "application is healthy" actually prove?

Against a running session, call:

~~~bash
curl -i "http://localhost:8080/actuator/health"
curl -i "http://localhost:8080/actuator/info"
~~~

Use the actual port if `server.port` was changed. `health` typically reports aggregated status, while `info` may be `{}` if no info contributors are declared. Having `/health` and `/info` comes from Actuator together with the exposure configuration in this lab.

**Evidence:** HTTP status and JSON returned by each endpoint. **Explanation:** health reflects registered indicators, not a replacement for testing business logic on `/api/hello`. Paths like `/actuator/health/readiness` do not automatically exist in every configuration; use them only when health probes are enabled and you have verified the endpoint exists.

**Stage pass criterion:** state at least one case where health is `UP` yet business logic still fails, such as a controller returning wrong data while the server and basic dependencies are working.

### Stage 6 — Compare running during development vs. distribution

**Question:** what is the difference between `spring-boot:run` and `java -jar`?

Run sequentially via the Maven plugin and via the packaged JAR with the same profile/port/prefix; test one request in each session. Do not let two sessions contend for the same port simultaneously.

**Evidence:** same endpoint and same body given identical inputs/configuration; different launch paths. **Explanation:** `spring-boot:run` serves the development loop, whereas the JAR bundles the application and required dependencies according to Spring Boot's packaging format. Editing `application.properties` after building **does not automatically update the contents of an already-built JAR**; you must rebuild or pass external configuration outside the JAR.

**Stage pass criterion:** articulate the difference between "current source code and resources" and "contents of a built artifact".

### Stage 7 — Induce controlled failures and read the right signals

**Experiment A — Port collision:** keep one instance on 8080, then try starting a second instance on the same port. The second instance may fail with `Port 8080 was already in use` or `BindException`; exact wording depends on the stack. Base your conclusion on the cause in the logs and the fact that the new process is not listening on the port.

**Experiment B — Wrong path:** call `/api/hello-wrong` on a healthy instance; typically returns HTTP 404, not a startup error.

**Experiment C — Wrong profile:** run without `--spring.profiles.active=dev`, then compare `/api/hello` with when `dev` is active. If the result differs from expectations, re-check the active profile, the source of `demo.greeting-prefix`, and restart status rather than editing the controller by guesswork.

**Experiment D — Wrong port when testing:** have the app listen on 8081 while calling 8080. If no service is on 8080, the client reports a connection error; this differs from a 404 returned by the application itself.

**Evidence:** command, chosen port, status or error message, cause line. **Stage pass criterion:** from a log/response, identify whether the fault lies in the startup phase, network/port, HTTP mapping, or configuration.

### Stage 8 — Stop the application and inspect the lifecycle

Press Ctrl+C in the launch terminal, observe the process terminate, then try sending a request to the port just used. If no other process is listening on that port, requests can no longer connect. You can experiment with `server.shutdown=graceful` as an advanced exercise and observe shutdown under load, but do not treat Ctrl+C as proof that every in-flight request finished.

**Evidence:** terminal exits, port stops serving, shutdown messages if emitted by the runtime. **Explanation:** stopping the process terminates the server and closes the context; how in-flight requests are handled depends on shutdown configuration and server type. Do not draw conclusions about data preservation merely from the absence of responses.

**Stage pass criterion:** describe the differences among startup, ready, serving, and shutdown, along with one observable signal for each state.

## 5. Experiment log: record evidence instead of conclusions alone

Use the column template `Step | Command and input | Direct observation | Explanatory mechanism | Conclusion`. Example completed record for the lab:

| Step | Command and input | Direct observation | Explanatory mechanism | Conclusion |
|---|---|---|---|---|
| Startup | `./mvnw spring-boot:run` | `LAB_RUNNER_DONE` then `LAB_APPLICATION_READY` | Runner finishes before ready event | Passed startup milestone |
| HTTP | `GET /api/hello?name=Lan` | 200, `{"message":"Greetings, Lan!"}` | MVC invokes controller and serializes record | Endpoint works correctly |
| Profile | `--spring.profiles.active=dev` | 200, `{"message":"Greetings from dev, Lan!"}` | Profile config file supplies prefix | Same code, different config |
| Override | `--demo.greeting-prefix=Hello` | 200, `{"message":"Hello, Lan!"}` | CLI overrides config file | Confirmed config precedence |
| Health | `GET /actuator/health` | 200, status `UP` in healthy lab | Actuator aggregates health indicators | Basic runtime health |
| Wrong mapping | `GET /api/hello-wrong` | 404 | No matching handler | Server running but route wrong |

The observed values in the table are **expected benchmarks when the lab environment works properly**. In real practice, record actual outputs even when they differ from expectations and explain the discrepancy. Save a log snippet with timestamps, the command run, HTTP status, and body rather than terminal screenshots lacking context.

## 6. Framework for reading logs and analyzing errors

Ask in order:

1. **Did the application manage to start?** If `java` or Maven stops before `SpringApplication.run`, check the JDK, build, classpath, and entry point first.
2. **Did the context initialize successfully?** Bean creation errors, missing required properties, or configuration conflicts usually appear in the startup exception; read the entire `Caused by` chain down to the source-nearest cause.
3. **Which port is the web server listening on?** Find the effective port after combining config/profile/CLI; `server.port=0` requests an ephemeral port, so you cannot assume port 8080.
4. **Has it reached the ready phase?** Look for `LAB_APPLICATION_READY` and send a real request; a missing marker warrants checking startup or runner failures.
5. **What kind of error did the client receive?** `Connection refused` suggests no listener on that host/port; 404 suggests an unmatched route; 500 suggests a request-handling exception; a 200 response with the wrong body is a logic or API contract bug.
6. **What does Actuator prove?** `UP` is only the result of registered checks; to verify API correctness you must still call the API and inspect the content.

Do not disable logs completely, leave `--debug` enabled permanently, or expose sensitive Actuator endpoints merely for "easy observation". When you need to inspect the auto-configuration condition report, run once with `--debug`, find the condition report, and turn it off again to return to normal logging.

## 7. Common misunderstandings

- **Confusing process status with readiness status:** a running process is not enough; combine the ready marker, HTTP checks, and health.
- **Reading a startup log line as an API test:** a controller can still have a wrong mapping or faulty logic even when startup succeeds.
- **Thinking `@SpringBootApplication` creates all beans:** component scanning follows package scope; auto-configuration is conditional and does not arbitrarily generate every component.
- **Editing configuration without restarting or rebuilding when needed:** properties inside a packaged JAR do not change just by editing source files; `@Value` values in this lab are resolved when the bean is created.
- **Mistaking `/actuator/health` for overall readiness:** health indicators and readiness probes have different semantics, and endpoint configurations may differ.
- **Calling the wrong port yet editing the controller:** verify the listener and connection status before touching API code.
- **Comparing logs line-by-line:** timestamps, PIDs, and detailed initialization ordering can vary. Focus on meaningful events and outcomes.
- **Exposing `env`, `configprops`, or `heapdump` to public networks:** operational observability must restrict endpoints and access permissions so secrets are not accidentally leaked.

## 8. Self-assessment and completion criteria

Run an independent series of experiments: first with no active profile on 8080; second with profile `dev` on 8080; third with profile `dev` plus CLI overrides for prefix and port 8081; fourth intentionally calling a wrong path; finally stopping the server. For **each run**, record the launch command, effective profile/port, status/body, corresponding marker or error, and explain why the outcome changed.

The exercise is complete when you can independently:

- Build and run a Java 17 application with `@SpringBootApplication`, Spring MVC, and Actuator.
- Point out where the context, web server, runner, and ready event occur on a simple lifecycle diagram.
- Demonstrate two valid HTTP responses; distinguish a 404 response from a connection error.
- Demonstrate that profiles and CLI arguments produce different results without editing Java logic.
- Compare running via the Maven plugin vs. JAR, accompanied by at least one packaging piece of evidence.
- Explain what `/actuator/health` measures without inferring "all business logic is right" from `UP`.
- Correctly diagnose one port collision error, one routing error, and one misconfiguration error.
- Record actual observation data so someone else can reproduce the experiment.

You can extend this exercise with `ApplicationFailedEvent`, `ApplicationStartup`, readiness/liveness probes, and graceful shutdown once the foundational milestones are solid. For each extended feature, continue using the same rule: **every proposed mechanism must have independent, reproducible observational evidence**.
