# @DataJpaTest and Auto-Configured Persistence Components in Spring Boot

## 1. Goal: Test the Real JPA Layer Without Pulling the Entire Application into the Test

A Spring Boot application typically has a dependency chain of `Controller → Service → Repository → EntityManager → DataSource → Database`. If the test's question is **“Are the entity mappings, Spring Data JPA repository, JPQL, and database constraints correct?”**, loading controllers, the HTTP server, security filters, and external clients is usually unnecessary.

`@DataJpaTest` is a Spring Boot **test slice** focused on persistence using **Spring Data JPA**. Instead of starting the entire `ApplicationContext`, it prioritizes loading entities and JPA repositories while enabling the auto-configurations needed for persistence (the JPA provider, `EntityManagerFactory`, `DataSource`, transaction support, test database, `TestEntityManager`, and certain JDBC/schema tools depending on the classpath).

Examples of bugs this slice test should catch:

- `@Column` or `@JoinColumn` declared incorrectly relative to the schema.
- A repository method name that cannot be mapped to a valid query.
- `@Query` using the wrong entity/property name or JPQL parameter.
- `@OneToMany`/`@ManyToOne` relationships, fetch strategies, cascades, or orphan removal producing unexpected results.
- `UNIQUE`, `NOT NULL`, or foreign key constraints failing when SQL is executed.
- Entity state in the persistence context masking real data read/write errors.
- A query on the test database returning results different from business expectations.

**You should not conclude from a green `@DataJpaTest` that the HTTP API, business `@Service`, Spring Security, a service's transaction boundary, or the production system has been verified.** Those layers normally do not belong to the JPA slice context.

## 2. How @DataJpaTest Works and Bean Scope

In **Spring Boot 3.5 / Spring Framework 6.x**, this annotation is imported via:

```java
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
```

Minimal declaration:

```java
@DataJpaTest
class BookRepositoryTest {
    // @Autowired BookRepository repository;
}
```

This is a syntax template; the repository/entity classes will be fully defined in section 5. `@DataJpaTest` already integrates Spring TestContext with JUnit Jupiter, so **adding `@ExtendWith(SpringExtension.class)` is normally not required**.

When creating the context, Spring Boot applies filters to **restrict component scanning** while enabling only the auto-configurations appropriate for Data JPA. Overview:

```text
JUnit Jupiter
    |
    v
Spring TestContext + @DataJpaTest bootstrapper
    |
    +---- @Entity classes
    +---- Spring Data JpaRepository interfaces
    +---- EntityManagerFactory / Hibernate JPA
    +---- DataSource / JDBC driver / connection pool
    +---- JPA transaction manager
    +---- Test database auto-configuration
    +---- TestEntityManager (test helper)
    +---- JdbcTemplate (if appropriate JDBC infrastructure is present)
    +---- SQL initialization / Flyway / Liquibase (if configured)
    |
    +---- TYPICALLY NOT loaded:
             @RestController, business @Service,
             schedulers, message listeners, custom HTTP clients,
             most regular @Component / @ConfigurationProperties
```

This is a diagram of the **kinds of components allowed to be configured**, not a guarantee that every bean appears in every project. The classpath, dependencies, entity scan, application config, additional `@Import`s, and `@AutoConfigure...` annotations still determine the actual context.

### 2.1. Core Persistence Components

| Component | Role | What Can Be Verified |
|---|---|---|
| Jakarta Persistence `@Entity` | Maps class/field/association to tables and columns | DDL, insert/read, relationships, and constraints |
| `JpaRepository<T,ID>` | Repository proxy generated by Spring Data | `save`, `findById`, derived queries, JPQL |
| `EntityManagerFactory` | Creates persistence contexts; configures the provider | JPA metadata and mappings |
| `EntityManager` | Tracks managed entities, `persist`, `flush`, `clear` | Dirty checking, SQL flush, queries |
| `TestEntityManager` | Spring Boot test helper for JPA | Quick fixture creation, `persistAndFlush`, `persistFlushFind` |
| `DataSource` | Provides JDBC connections | Connection to H2/Testcontainers/selected DB |
| `PlatformTransactionManager` | Manages transactions | Test-managed rollback and repository transactions |
| `JdbcTemplate` | Sends raw JDBC SQL when needed | Inspecting real rows/columns without relying on ORM cache |
| `TestDatabaseAutoConfiguration` | Configures the test datasource | Embedded DB or keeping a declared test database |
| Flyway/Liquibase | Migrations per configuration/classpath | Can run schema migrations in the slice if appropriate |

In Boot 3.5, the list of auto-configurations typically includes `JpaRepositoriesAutoConfiguration`, `HibernateJpaAutoConfiguration`, `DataSourceAutoConfiguration`, `TransactionAutoConfiguration`, `TestDatabaseAutoConfiguration`, and `TestEntityManagerAutoConfiguration`, along with several conditional JDBC/SQL/migration configurations.

**`@DataJpaTest` does not spin up a real database server by itself.** If an embedded database library such as H2, HSQLDB, or Derby is on the classpath and selected, Boot can use an in-process database. If you want real PostgreSQL/MySQL, you must connect to a separate test database or container.

### 2.2. Components Typically Excluded from the Slice

A regular `@Service` class, even if its constructor takes `BookRepository`, is normally **not auto-scanned**. Likewise, a `@RestController` needing a service, a scheduler, a custom HTTP client, or a Kafka listener does not automatically appear just because `@DataJpaTest` is present.

This explains `NoSuchBeanDefinitionException` when trying to `@Autowired BookService` inside a JPA slice. If the goal is only to test the repository, inject the real repository directly. If a converter/mapping component is needed to support JPA, you can `@Import` **only the required helper bean**; if you genuinely need to test a business service across multiple layers, write a different test with an appropriate scope.

An important exception: an application class using a custom `@ComponentScan` can disable the default slice filters, unexpectedly scanning many non-persistence beans. In that case, check the scan configuration; do not fix it by endlessly adding mocks for every service in the application.

## 3. Default Transaction and Rollback in the JPA Slice

`@DataJpaTest` is marked transactional: each test method normally runs **inside a test-managed transaction**, and Spring TestContext **rolls it back** when the test finishes. This helps prevent leftover data between tests.

```text
@BeforeEach / test method (inside the test transaction)
    |
    +-- repository.save(entity)
    +-- entityManager.flush()
    +-- repository.findBy...
    +-- assertions
    |
Spring TestContext: roll back the test transaction
    |
    v
Changes participating in that transaction are not committed
```

Key points to remember:

1. `repository.save(...)` **is not equivalent to commit**. JPA may defer SQL until `flush`, or execute INSERT early depending on the ID strategy and provider.
2. `flush()` pushes pending changes from the persistence context to the database within the transaction, but **does not commit**.
3. `clear()` detaches managed entities from the persistence context; reading after `clear` helps reduce false positives caused by the **first-level cache**.
4. A test that already has a transaction can mask a production service missing `@Transactional`; a repository test **does not automatically verify** external transaction boundaries.
5. If a test opens a new `REQUIRES_NEW` transaction, calls an API over another HTTP thread, or emits side effects to an external system, the test's rollback **does not automatically undo** all those outcomes.
6. You can change how the test transaction ends with `@Commit`, `@Rollback(false)`, or `TestTransaction`, but you must understand that committed data can pollute other tests.

Do not apply `@DirtiesContext` to every test just to clean up records: it evicts the context from the cache and increases startup cost, yet **it is not a tool for deleting committed rows in a shared database**.

## 4. A Complete Java 17+ Example: BookRepository, Hibernate, H2

The example uses **Spring Boot 3.5.x**, Java 17+, Spring Data JPA, Hibernate, H2, and Spring Boot Test/JUnit Jupiter. The goal is to test **real SQL/database behavior inside a persistence slice**, without using Mockito to mock the repository.

### 4.4. JPA Entity with a UNIQUE Constraint

File `src/main/java/com/example/jpaslice/Book.java`:

```java
package com.example.jpaslice;

import java.util.Objects;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;

@Entity
@Table(
        name = "library_books",
        uniqueConstraints = @UniqueConstraint(
                name = "uk_library_books_isbn",
                columnNames = "isbn"))
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 40)
    private String isbn;

    @Column(nullable = false, length = 200)
    private String title;

    protected Book() {
        // Constructor for the JPA provider.
    }

    public Book(String isbn, String title) {
        this.isbn = Objects.requireNonNull(isbn, "isbn");
        this.title = Objects.requireNonNull(title, "title");
    }

    public Long getId() {
        return id;
    }

    public String getIsbn() {
        return isbn;
    }

    public String getTitle() {
        return title;
    }

    public void rename(String newTitle) {
        this.title = Objects.requireNonNull(newTitle, "newTitle");
    }
}
```

Significant details:
- `@Entity` includes the class in JPA entity scanning.
- `@Id`, `@GeneratedValue(IDENTITY)` declares a `Long` primary key generated by the database/provider.
- `@Table(name="library_books")` sets the table name explicitly rather than relying solely on implicit naming.
- `UniqueConstraint` requires ISBNs not to duplicate at the schema level (once DDL/migrations have created the constraint).
- `@Column(nullable=false)` declares a mapping/schema constraint; it **does not automatically replace Bean Validation** for HTTP inputs.
- `rename` mutates a **managed** entity, which is a good case for testing dirty checking.

Do not expose this entity directly as an HTTP response in a real application if it has internal fields or lazy associations. The scope here is persistence.

### 4.5. Real Spring Data JPA Repository

File `src/main/java/com/example/jpaslice/BookRepository.java`:

```java
package com.example.jpaslice;

import java.util.List;
import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface BookRepository extends JpaRepository<Book, Long> {

    Optional<Book> findByIsbn(String isbn);

    long countByIsbn(String isbn);

    List<Book> findByTitleContainingIgnoreCaseOrderByTitleAsc(
            String fragment);

    @Query("""
            select b from Book b
            where b.isbn like concat(:prefix, '%')
            order by b.isbn asc
            """)
    List<Book> findIsbnStartingWith(
            @Param("prefix") String prefix);
}
```

Spring Data JPA creates the repository implementation/proxy according to the context configuration; in the test we inject the **real repository**, without creating a Mockito mock. Derived queries are parsed from the method name, and `@Query` uses JPQL (Java entity/property names, not SQL table names).

**Distinction:** `Book` is the entity class name, and `isbn` is the Java property. In JPQL it is `select b from Book b`; when using native SQL, the table name in this example is `library_books`.

### 4.7. Complete JUnit Test Suite

File `src/test/java/com/example/jpaslice/BookRepositoryTest.java`:

```java
package com.example.jpaslice;

import java.sql.Connection;
import java.sql.SQLException;
import java.util.List;

import javax.sql.DataSource;

import org.junit.jupiter.api.Test;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.context.ApplicationContext;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.JdbcTemplate;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

@DataJpaTest(
        showSql = false,
        properties = "spring.jpa.hibernate.ddl-auto=create-drop")
class BookRepositoryTest {

    @Autowired
    BookRepository books;

    @Autowired
    TestEntityManager entities;

    @Autowired
    JdbcTemplate jdbc;

    @Autowired
    DataSource dataSource;

    @Autowired
    ApplicationContext context;

    @Test
    void usesEmbeddedH2DatabaseInThisTestSetup() throws SQLException {
        try (Connection connection = dataSource.getConnection()) {
            assertEquals(
                    "H2",
                    connection.getMetaData().getDatabaseProductName());
        }
    }

    @Test
    void savesAndReadsAfterClearingPersistenceContext() {
        Book saved = books.saveAndFlush(
                new Book("ISBN-100", "JPA Fundamentals"));
        assertNotNull(saved.getId());

        // Avoid getting the managed entity back from the first-level cache.
        entities.clear();

        Book read = books.findById(saved.getId()).orElseThrow();
        assertEquals("ISBN-100", read.getIsbn());
        assertEquals("JPA Fundamentals", read.getTitle());

        Integer rows = jdbc.queryForObject(
                "select count(*) from library_books where isbn = ?",
                Integer.class,
                "ISBN-100");
        assertNotNull(rows);
        assertEquals(1, rows.intValue());
    }

    @Test
    void derivedQueryFiltersAndSorts() {
        entities.persist(new Book("ISBN-101", "Spring Data"));
        entities.persist(new Book("ISBN-102", "Postgres Guide"));
        entities.persist(new Book("ISBN-103", "Spring AOP"));
        entities.flush();
        entities.clear();

        List<String> titles = books
                .findByTitleContainingIgnoreCaseOrderByTitleAsc("SPRING")
                .stream()
                .map(Book::getTitle)
                .toList();

        assertEquals(
                List.of("Spring AOP", "Spring Data"),
                titles);
    }

    @Test
    void explicitJpqlQueryUsesEntityProperties() {
        entities.persist(new Book("ISBN-200", "One"));
        entities.persist(new Book("ISBN-201", "Two"));
        entities.persist(new Book("CODE-999", "Other"));
        entities.flush();
        entities.clear();

        List<String> isbn = books.findIsbnStartingWith("ISBN-")
                .stream()
                .map(Book::getIsbn)
                .toList();

        assertEquals(
                List.of("ISBN-200", "ISBN-201"), isbn);
    }

    @Test
    void dirtyCheckingUpdatesManagedEntityAfterFlush() {
        Book created = entities.persistAndFlush(
                new Book("ISBN-301", "First Title"));
        Long id = created.getId();
        assertNotNull(id);
        entities.clear();

        Book managed = books.findById(id).orElseThrow();
        managed.rename("Updated Title");

        // Do not call books.save(managed):
        // JPA detects changes on a managed entity on flush.
        entities.flush();
        entities.clear();

        Book reloaded = books.findById(id).orElseThrow();
        assertEquals("Updated Title", reloaded.getTitle());
    }

    @Test
    void databaseRejectsDuplicateIsbnOnFlush() {
        books.saveAndFlush(new Book("ISBN-DUP", "First Book"));

        assertThrows(
                DataIntegrityViolationException.class,
                () -> books.saveAndFlush(
                        new Book("ISBN-DUP", "Second Book")));

        // Do not continue querying after a SQL constraint violation:
        // the transaction may already be marked rollback-only.
    }

    @Test
    void ordinaryServiceIsNotAutoScannedByJpaSlice() {
        assertTrue(
                context.getBeansOfType(BookCatalogService.class).isEmpty());
        assertFalse(context.getBeansOfType(
                BookRepository.class).isEmpty());
    }
}
```

### 4.8. Interpreting Results Within the Proper Scope

| Test Method | What It Proves | What It Does Not Prove |
|---|---|---|
| `usesEmbeddedH2DatabaseInThisTestSetup` | DataSource points to H2 in this sample config | Production also runs on H2 |
| `savesAndReadsAfterClearingPersistenceContext` | Real INSERT/query and JDBC sees the row after flush | Transaction committed and readable by an external client |
| `derivedQueryFiltersAndSorts` | Repository derived query, case-insensitive filter, and sort in H2 | PostgreSQL collation matches H2 identically |
| `explicitJpqlQueryUsesEntityProperties` | JPQL parses/runs, prefix filter and ordering match sample data | JPQL tested against all production volumes/plans |
| `dirtyCheckingUpdatesManagedEntityAfterFlush` | Hibernate dirty checking works on a managed entity | Detached entities also update automatically |
| `databaseRejectsDuplicateIsbnOnFlush` | H2 schema has unique constraint and error translates through repository | Every database dialect throws/translates the exact same exception |
| `ordinaryServiceIsNotAutoScannedByJpaSlice` | Context selected repository without scanning regular service | No custom component is ever included in any @DataJpaTest |

**Test 2 uses both `books.findById` after `clear` and SQL via `JdbcTemplate`** to observe flushed data. If you only write `assertEquals(saved, books.findById(id).orElseThrow())` without clearing the persistence context, Hibernate may return the same managed object from the first-level cache, reducing the test's power to catch mapping/SQL bugs.

The example uses `DataIntegrityViolationException` in a Spring Data JPA/Hibernate/H2 environment. On another JPA provider or driver, exception timing or translation can differ; the test here has a **clearly stated scope** of the Boot 3.5/Hibernate/H2 sample configuration.

The class above has seven `@Test` methods, with no `System.out.println` or fixed console output. Only claim cases **actually PASS** after running Gradle/Maven and inspecting the report; the code snippet itself is not a run result.

## 6. How Do TestEntityManager, EntityManager, and JdbcTemplate Differ?

`TestEntityManager` is a helper provided by Spring Boot in JPA tests, **not a new JPA provider**, and it does not replace `EntityManager` in production. It offers several convenient operations:

```java
Book saved = entities.persistAndFlush(
        new Book("ISBN-A", "A"));
Long id = saved.getId();

entities.clear();
Book loaded = entities.find(Book.class, id);
```

This is an illustrative snippet inside a test where `entities` is already injected; in practice you can choose `persistFlushFind` to run persist + flush + find more concisely.

| API | Effect | Watch Out For |
|---|---|---|
| `entities.persist(entity)` | Puts entity into the persistence context | SQL may not be flushed/committed yet |
| `entities.persistAndFlush(entity)` | Persists then flushes | Flush **is not commit** |
| `entities.persistFlushFind(entity)` | Persist + flush + find by ID | Does not guarantee the find is isolated from first-level cache like a prior `clear()` |
| `entities.clear()` | Removes managed entities from the persistence context | Unflushed changes may be lost |
| `entities.getEntityManager()` | Retrieves the real JPA EntityManager | Transaction and lifecycle remain managed by the context |
| `books.saveAndFlush(entity)` | Saves via repository then flushes | Does not guarantee transaction commit |
| `jdbc.queryForObject(sql, ...)` | Reads the database via JDBC | Bypasses the ORM entity cache, though it may still share the **same transaction** |

Do not call `persistFlushFind` and claim it **definitely** forces a physical SELECT from the database after the persistence context was cleared; that API does not inherently perform `clear`. When the goal is to verify SQL readback, use an explicit `flush → clear → find` sequence.

### 6.1. Why Does Early Flushing Matter for Constraints?

In JPA, `save` sometimes does not issue all SQL immediately. If a test uses:

```java
Book saved = books.save(
        new Book("ISBN-EX", "Title"));
assertNotNull(saved);
```

the test might pass while a constraint error only surfaces **after the test method ends** or at another flush point. Especially with unique/foreign key constraints, perform `saveAndFlush` or `EntityManager.flush` at the exact point where you want to assert the failure.

However, with `GenerationType.IDENTITY`, an INSERT may happen **immediately on persist** to obtain the generated ID; do not assert “SQL only appears when flush is called” for every entity/provider. The meaning of `flush` is to request synchronization of pending persistence actions, not a promise that it is the very first SQL statement.

### 6.2. Why Can a Rolling-Back Test Still See Data in the Same Transaction?

Because the Spring test transaction is active, code inside the transaction can read rows it just inserted/flushed, even though they **have not committed for an independent connection**. Therefore:

```java
assertEquals(1L, books.countByIsbn("ISBN-100"));
```

inside the same test proves the repository query sees data belonging to the current transaction; it does not prove an external HTTP request can read it before commit. To test real visibility/isolation/commit, design **a read path in a separate transaction/connection** and explicitly control transaction boundaries.

## 7. Embedded Databases and @AutoConfigureTestDatabase

`@DataJpaTest` typically includes **test database auto-configuration**. In Boot 3.5, the default `AutoConfigureTestDatabase.Replace` is **`NON_TEST`**: a regular DataSource may be replaced by an embedded test database, whereas connections recognized as a **test database** (such as a Testcontainers service connection or `spring.datasource.url` from `@DynamicPropertySource`) can be preserved.

Do not oversimplify this to “`@DataJpaTest` always replaces every DataSource with H2”. Replacement depends on **annotations, connections, classpath, and datasource configuration**; if no embedded driver or valid DB config is available, the context may fail to start.

### 7.1. Common Replace Modes

In Boot 3.5:

```java
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;

@AutoConfigureTestDatabase(
        replace = AutoConfigureTestDatabase.Replace.NONE)
```

This snippet is placed on a test class, **not a standalone Java file**.

| Replace Mode | Meaning |
|---|---|
| `ANY` | Replaces an existing DataSource with a test database when possible, even a user-declared datasource |
| `AUTO_CONFIGURED` | Replaces only a DataSource auto-configured by Boot |
| `NON_TEST` | Boot 3.5 default; does not replace datasources recognized as test databases |
| `NONE` | Keeps the configured datasource without replacing it with an embedded DB via test database auto-config |

**Use `NONE` when you genuinely want to connect to Testcontainers PostgreSQL or a designated test database.** However, `NONE` **does not start containers, create schemas, or make a production URL safe**. Make sure configuration points to an isolated test DB, especially when tests can delete/write data.

### 7.2. What Happens If H2 Is on the Classpath?

In the section 4 example, H2 is on the classpath and no PostgreSQL test URL is provided, so the context uses H2. You can verify the database product name from `DataSource.getConnection().getMetaData()` instead of relying only on a log line saying “embedded”.

**H2 is not PostgreSQL/MySQL/Oracle.** Possible differences include:
- SQL dialect, reserved words, and native query syntax.
- JSON/JSONB, array types, generated columns, upserts, or partial indexes.
- Identity/sequence behavior.
- Collation, `ILIKE`, case sensitivity, and Unicode ordering.
- Transaction isolation, lock timing, deadlocks, and constraint semantics.
- Compatibility of migration SQL from Flyway/Liquibase.

Therefore, JPA slice + H2 is suited for quick checks of **general entity mappings/queries**, but insufficient for dialect-dependent database features.

## 8. When You Need a Production-Like Database: @DataJpaTest with Testcontainers

One way to keep the test slice lean while still testing **real PostgreSQL** is Testcontainers. This approach requires Docker/a compatible container runtime and the PostgreSQL JDBC driver, so it is unsuitable in environments without permission to run containers.

### 8.1. Testcontainers Dependencies

In the same Spring Boot 3.5 project, add lines compatible with the Boot BOM:

```groovy
dependencies {
    runtimeOnly 'org.postgresql:postgresql'
    testImplementation 'org.testcontainers:junit-jupiter'
    testImplementation 'org.testcontainers:postgresql'
}
```

This is an **addition** to the `dependencies` block in section 4, not a replacement build file. To keep the production app using PostgreSQL, put the driver in the appropriate runtime configuration; to keep H2 in tests only, put H2 in `testRuntimeOnly`.

### 8.2. A Test Class Using a PostgreSQL Container

File `src/test/java/com/example/jpaslice/BookRepositoryPostgresTest.java`:

```java
package com.example.jpaslice;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;

import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;

@Testcontainers
@DataJpaTest(
        showSql = false,
        properties = "spring.jpa.hibernate.ddl-auto=create-drop")
@AutoConfigureTestDatabase(
        replace = AutoConfigureTestDatabase.Replace.NONE)
class BookRepositoryPostgresTest {

    @Container
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine")
                    .withDatabaseName("books_test")
                    .withUsername("test")
                    .withPassword("test");

    @DynamicPropertySource
    static void databaseProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url",
                postgres::getJdbcUrl);
        registry.add("spring.datasource.username",
                postgres::getUsername);
        registry.add("spring.datasource.password",
                postgres::getPassword);
    }

    @Autowired
    BookRepository books;

    @Test
    void repositoryStoresDataInRealPostgres() {
        Book persisted = books.saveAndFlush(
                new Book("PG-100", "PostgreSQL Mapping"));

        assertNotNull(persisted.getId());
        assertEquals(
                1L, books.countByIsbn("PG-100"));
    }
}
```

In this configuration:
- The JUnit/Testcontainers extension manages the static container's lifecycle.
- `@DynamicPropertySource` supplies the JDBC URL/username/password from the container when Spring creates the datasource. The actual URL contains the proper host and mapped port; do not hard-code `localhost:5432`.
- `@AutoConfigureTestDatabase(replace=NONE)` prevents Spring from replacing the container datasource with H2.
- `@DataJpaTest` still loads only the JPA slice, without starting an HTTP server or business services.
- `ddl-auto=create-drop` creates the schema from entity mappings for the demonstration test. **Do not use this on shared/production databases**, and do not treat this as a test verifying migration scripts.
- The test still **rolls back under the test-managed transaction**; a count query in that same transaction does not prove data committed outside the test.

In Spring Boot versions supporting `@ServiceConnection` and `spring-boot-testcontainers`, manual JDBC property registration can be replaced by a Boot service connection when the image/connection type is recognized. Choose **one configuration approach** deliberately; do not register the same datasource from multiple sources without checking precedence.

**Context cache and container lifecycle:** if a context is cached while another class's static container has stopped, the datasource may point to an old port. When sharing resources across multiple test classes, design the container lifetime accordingly or explicitly control context cleanup; do not share static mutable URLs carelessly.

## 9. Migrations and Schema: Hibernate DDL Differs from Flyway/Liquibase

The H2 and Testcontainers examples above use:

```properties = "spring.jpa.hibernate.ddl-auto=create-drop"
```

That setting tells Hibernate to **create and drop the schema from entity mappings** during the context's lifecycle. It works when a lesson focuses on JPA mapping, but **does not verify** the SQL migration files used in production.

If the application uses Flyway or Liquibase:
1. Place migrations in the project path loaded by the tool, such as Flyway's `db/migration`.
2. Use the same database dialect as production when migrations contain vendor-specific SQL.
3. Let migrations create the test schema; consider `spring.jpa.hibernate.ddl-auto=validate` so Hibernate checks entity mappings against the migrated schema.
4. Verify that migration auto-configuration is enabled in the JPA slice and the datasource is correct; do not assume migrations always run just because the artifact is present.
5. Assert data/schema after migration, especially indexes, unique constraints, column lengths, and default values.

**Avoid using both Hibernate `create-drop` and expecting migrations to be the sole source of schema truth.** Use one clear schema owner; if migrations have run, Hibernate may need `validate` instead of recreating tables.

### 9.1. @Sql for Fixture Creation and Cleanup

Spring TestContext supports `@Sql` to run SQL before/after tests. Sample snippet:

```java
@Sql(
    scripts = "/sql/books-fixture.sql",
    executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
@Test
void readsMigrationFixture() {
    // repository query...
}
```

This is an **illustrative snippet**, requiring `org.springframework.test.context.jdbc.Sql` and a real script file. If run inside `@DataJpaTest`'s test-managed transaction, SQL fixtures can **be rolled back at the end of the test**. If configured as `ISOLATED` or committed to a shared DB, cleanup must be explicitly designed; do not let shared data make tests order-dependent.

Do not throw `schema.sql`, Flyway scripts, and Hibernate `ddl-auto=create` into tests simultaneously just to “be sure tables exist”; they can conflict over schema creation and make failures hard to diagnose.

## 10. First-Level Cache and False Positives in Persistence Tests

JPA `EntityManager` maintains a **persistence context**; loaded/managed entities can be returned from the first-level cache by identity. Thus:

```java
Book book = books.save(new Book("X-1", "Saved"));
assertEquals("Saved", books.findById(book.getId())
                          .orElseThrow().getTitle());
```

This is an illustrative snippet. It exercises part of the repository path but **may not prove data was read via SQL**: the entity is managed and finding by ID may return the exact same instance.

A stronger approach:

```java
Book book = books.saveAndFlush(
        new Book("X-2", "Saved"));
Long id = book.getId();

entities.clear();

Book fromDatabase = books.findById(id).orElseThrow();
assertEquals("Saved", fromDatabase.getTitle());
```

When combined with a `JdbcTemplate` row check, the test gains an observation that bypasses the JPA entity cache. However, sharing the same transaction still **does not** prove a commit occurred.

### 10.1. N+1 Queries and Lazy Loading

In `@DataJpaTest`, each test usually has an active transaction, so a lazy association can be accessed validly in the test even if production code accessing it outside a transaction hits `LazyInitializationException`. That situation makes tests “all green” while the real API fails.

To test lazy loading/fetch graphs:
- Explicitly declare where fetching is needed via `JOIN FETCH`, `@EntityGraph`, or an appropriate DTO projection.
- `flush`/`clear`, load the entity via the target query, and observe the SQL count or Hibernate statistics if controlling N+1.
- Separate tests measuring query count/transaction boundaries from simple mapping tests.
- Do not access a lazy collection inside a test transaction and then conclude a controller serializing to JSON outside a transaction is guaranteed to be safe.

N+1 is a performance and SQL shape issue, not merely an object equality issue. A test checking only correct data without observing SQL can miss hundreds of queries in production.

## 11. Does @DataJpaTest Test Service Transaction Commit/Rollback?

**Not automatically.** Services are typically filtered out of the JPA slice. When a test needs to protect a use case like “creating an Order and OrderLines must be atomic”, determine **which layer holds the transaction boundary**:

- Repository test: tests JPA mapping, queries, constraints.
- Service transaction test: keeps the real service and real transaction manager, typically using `@SpringBootTest` or a test context configured with all parts under test.
- HTTP integration test: calls through a real server; the server thread normally has a **separate** transaction and does not borrow the client thread's test transaction.

In a service test, if the test method itself is `@Transactional`, an unannotated service can still run inside the transaction created by the test framework. That weakens assertions about “an active transaction”. To test real commit/rollback, the test should start outside a test transaction or explicitly end the transaction and re-read the database in an independent transaction.

`@DataJpaTest` allows overriding:

```java
@DataJpaTest
@Transactional(propagation = Propagation.NOT_SUPPORTED)
class NonTransactionalRepositoryTest {
    // The test manages transactions manually if needed.
}
```

The snippet above illustrates syntax and requires importing `org.springframework.transaction.annotation.Transactional` and `Propagation`; it is not a complete Java file. **When test-managed transactions are disabled, data can be committed and not automatically rolled back**, so proper cleanup or database lifecycle handling is required.

If you need to control an already active test transaction:

```java
TestTransaction.flagForRollback();
TestTransaction.end();
```

This is an illustrative snippet inside a test with a Spring TestContext-managed transaction, not applicable in every context. `TestTransaction` controls **the test thread's transaction**, not a transaction handled by an HTTP request on a separate server thread.

## 12. Comparing @DataJpaTest with Other Test Slices

| Goal | Typically Appropriate Tool | Key Point to Remember |
|---|---|---|
| JPA entity mapping and JpaRepository | `@DataJpaTest` | Persistence slice, rolls back by default |
| Direct JDBC via JdbcTemplate | `@JdbcTest` | Does not require JPA provider/repositories |
| Spring Data JDBC repositories | `@DataJdbcTest` | Differs from JPA entity lifecycle/dirty checking |
| Reactive R2DBC repositories | `@DataR2dbcTest` | Reactive stack, different transaction model |
| MVC controller and JSON response | `@WebMvcTest` | Service/repository usually must be mocked |
| WebFlux annotated controller | `@WebFluxTest` | WebTestClient, Mono/Flux, does not prove JPA |
| Service + Repository + DB + config | `@SpringBootTest` or matching integration context | Heavier; verifies real wiring |
| Real HTTP server + full workflow | `@SpringBootTest(RANDOM_PORT)` | Server thread transaction differs from test thread |
| Pure Java business logic | JUnit + Mockito if needed | No Spring context needed |
| Production-specific migration SQL | Testcontainers + migrate/validate | Prefer production-like database/dialect |

Do not replace `@DataJpaTest` with `@SpringBootTest` simply because a service bean is missing when the test's goal is actually the repository. Conversely, do not take a JPA slice, `@Import` numerous services, controllers, schedulers, and API clients, and still call it a “lightweight slice”; at that point its scope approaches an integration test with higher cost and risk.

## 13. Common Errors and How to Handle Them

| Symptom | Common Cause | Diagnostic Direction |
|---|---|---|
| `Failed to configure a DataSource` | Missing embedded driver, URL, or valid test datasource config | Check H2/HSQL/Derby classpath, Replace mode, and JDBC URL |
| `Unable to find a @SpringBootConfiguration` | Test is outside the application's package hierarchy | Place test in same package/subpackage or declare bootstrap config explicitly |
| `NoSuchBeanDefinitionException: BookService` | Service is not part of the JPA slice | Inject repository, import intentionally, or switch to a service test |
| `Not a managed type: Book` | Entity scan did not pick up `@Entity` or package is outside base | Check `@Entity`, package scan/`@EntityScan` if needed |
| `Table ... not found` | DDL not generated, migrations not run, or wrong datasource/schema | Check DDL/migrations/datasource and `ddl-auto` |
| Derived query fails at context startup | Wrong property name or return type | Verify entity property names and method name |
| `@Query` fails at startup/invocation | Wrong JPQL syntax/param name | Check entity properties and `@Param`; distinguish from native SQL |
| Save/find test green but SQL unverified | First-level cache masked bug or no flush | `flush → clear → reload`; also check via JDBC |
| Unique constraint test shows no error | SQL not executed or schema lacks constraint | `saveAndFlush`, check generated DDL |
| Constraint test throws error but next test fails | Rollback-only transaction / polluted DB state | Do not query after SQL error in same test; rely on rollback and isolate fixtures |
| H2 test green but PostgreSQL fails | Different dialect, collation, locking, migrations | Use Testcontainers PostgreSQL and real migrations |
| Test unexpectedly hits production database | `replace=NONE` and URL points to wrong environment | Guard datasource URLs, isolate profiles/secrets; never run destructive tests on production |
| Flyway `schema history` error | Schema created by both Hibernate and migrations, or checksum mismatch | Choose one schema owner, run migrations as in production |
| `LazyInitializationException` outside tests | Active test transaction masks lifecycle | Review fetch plans and service boundaries |
| N+1 queries go undetected | Only asserting output without checking SQL count | Use query statistics/logging with sufficient fixture size |
| Context loads too many beans | Custom `@ComponentScan`/Import breaks slice filter | Trim scans/imports, keep JPA-only config |
| Test passes alone but fails in suite | Context cache, shared DB, or committed fixture | Use transaction rollback, unique keys, cleanup, container isolation |
| Boot 4 `@DataJpaTest` import not found | Packages/modules changed compared to Boot 3.x | Use the Boot 4 test modules and packages |

**Prioritize reading the root cause** in `Caused by`, rather than fixing an assertion when the application context failed to initialize. `@DataJpaTest` reduces the variety of beans and therefore usually narrows down errors faster than a full context.

## 14. Version Notes: Boot 3.5 and Boot 4.x

The code in sections 4 and 8 targets **Spring Boot 3.5.x / Java 17+**, with imports:

```java
org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest
org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager
org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase
```

This is a package list, not the contents of a Java file.

In **Spring Boot 4.x**, the test auto-configuration module layout is reorganized. The corresponding types now live in new packages/modules, for example:

```java
org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest
org.springframework.boot.jpa.test.autoconfigure.TestEntityManager
org.springframework.boot.jdbc.test.autoconfigure.AutoConfigureTestDatabase
```

You need test dependencies such as `spring-boot-data-jpa-test` and modules matching Boot 4/BOM. **Do not mix `spring-test`/Boot 4.x test jars with a Boot 3.5 runtime just to fix imports.** Keep all dependency versions consistent and follow the code style of your project's Boot line.

Principles that **stay the same** regardless of module renames:
- The persistence slice loads only related components, not the full application.
- Entity/repository tests should run against a real database and transaction.
- Flush differs from commit; the first-level cache can make tests pass too easily.
- H2 does not prove PostgreSQL/MySQL-specific behavior.
- Test database replacement/connection and migrations must be controlled explicitly when reliability depends on them.

## 15. Checklist When Writing @DataJpaTest

- [ ] Confirmed the goal is entity mapping/repository queries/database constraints, not full HTTP/service workflows.
- [ ] `@DataJpaTest` uses the right package for your Boot version; did not add `@SpringBootTest` to the same class just to pull every bean.
- [ ] `@Entity` and `JpaRepository` are within scan scope and not excluded by custom component scan config.
- [ ] JPA infrastructure, `DataSource`, transaction manager, and test database are actually created.
- [ ] Know whether the datasource is H2/embedded, a container, or a configured test database; did not infer only from profile names.
- [ ] If using Testcontainers, used `Replace.NONE` or proper test DB detection and appropriate container lifecycle.
- [ ] Distinguished `persist/save`, `flush`, `clear`, and `commit`.
- [ ] Tests verifying real database state use `flush → clear → reload` or JDBC assertions where appropriate.
- [ ] Fixtures contain representative data; unique/foreign key and query edge cases are tested, not only the happy path.
- [ ] Migrations/Flyway/Liquibase do not conflict with Hibernate `ddl-auto`.
- [ ] H2 is not used as proof for production-specific SQL dialects/locking/indexes without a production-like DB test.
- [ ] No dependency on test execution order or committed data in a shared DB.
- [ ] Considered lazy loading, N+1, and transaction boundaries outside the test thread.
- [ ] If a service is missing from the slice, chose the proper test type instead of pulling in the whole application context.
- [ ] Executed the right test task/class, verified the actual test count run, and read reports before claiming PASS.
