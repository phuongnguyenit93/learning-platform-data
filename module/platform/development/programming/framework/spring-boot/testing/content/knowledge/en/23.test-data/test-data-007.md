# Reproducible Identifiers, Time, Timezones, and Locales

## 1. Goal: A Test Suite That Produces the Same Result Anywhere, Anytime

In the **Spring Boot - testing** module under **Test Data**, a common source of *flaky* tests is environment-dependent data: random IDs, the current wall clock, the OS timezone, or the CI machine's default locale.

For example, code can PASS on a personal laptop yet FAIL near midnight, when CI sets `TZ=UTC`, or when the JVM runs under locale `tr-TR`:

~~~java
// Illustrative anti-example, not a standalone compilable class.
UUID id = UUID.randomUUID();
Instant issuedAt = Instant.now();
LocalDate today = LocalDate.now();
String key = "ID".toLowerCase();
~~~

Because the data comes from ambient environment state, the expected result no longer depends solely on test inputs. The right fix is not adding `Thread.sleep`, hardcoding today's date, or calling `TimeZone.setDefault` for the whole JVM, but **turning sources of variation into controllable dependencies**:

1. Generate IDs through an `IdGenerator`, using fixed fakes or deterministic sequences in tests.
2. Read time through `java.time.Clock`, using `Clock.fixed`/`Clock.offset`.
3. Compute calendar dates using an explicit business `ZoneId`, never the OS default.
4. Pick `Locale` from the input/request; use `Locale.ROOT` for technical keys and `MessageSource` for localized text.
5. Seed and clean up the database with isolated fixtures; never hardcode expectations on uncontrolled database sequences.
6. Protect tests under parallel execution and across differing JDK/CLDR/tzdb versions.

This lesson includes a standalone **Java 17 / Spring Boot 3.5.16** example: an illustrative receipt-issuing REST API, two JUnit test classes verifying ID/time/zone/locale (unit and real HTTP), plus guidance on JPA, DST, JSON, and CI.

## 2. “Reproducible” Does Not Mean “Every ID Is Always Identical”

| Subject | Appropriate Control | What Not to Do |
| --- | --- | --- |
| Output UUID | Inject generator returning a chosen UUID | Assert an arbitrary ID generated by `UUID.randomUUID()` on a previous run |
| Two records needing two IDs | Fake generator returning a sequence of **distinct** fixed IDs | Reuse the same UUID for two database inserts |
| DB-sequence-assigned ID | Use the returned real ID; assert relationships/business keys | Assert the sequence always starts at 1 |
| `createdAt` timestamp | Inject `Clock`, capture a single `Instant` | Call `Instant.now()` twice and assert equality |
| TTL | Compute using `Duration` from a controlled instant | Wait out the TTL with `Thread.sleep` |
| Business date | `instant.atZone(businessZone).toLocalDate()` | Use the machine's default `LocalDate.now()` |
| Localized text | `MessageSource` with an explicit `Locale` | Rely on `Locale.getDefault()` |
| JSON timestamps | Define format/precision, test raw JSON | Rely on differing library defaults |
| Database fixtures | Explicit seed/reset, isolated schema/indexes | Rely on leftover data from an earlier test |

Fixed IDs in unit tests are **not** production IDs. Production generators must still satisfy uniqueness, concurrency, and unpredictability requirements where needed. A UUID used as a public identifier **does not replace authorization**.

Determinism also requires smart assertions. A test can remain completely deterministic even with **random IDs** if it verifies the ID is valid, unique, and foreign keys point to the **actual returned ID**, rather than demanding one hardcoded UUID string.

## 3. Choosing the Right java.time Type

| Java Type | What It Represents | Example Use Case |
| --- | --- | --- |
| `Instant` | An absolute point on the timeline | Created/updated timestamp, audit event, expiry |
| `LocalDate` | A calendar date without zone or time | Business date, birth date |
| `LocalTime` | Time of day on a clock without a date | Opening hours |
| `LocalDateTime` | Local date+time **without zone or offset** | Schedule input requiring regional interpretation |
| `OffsetDateTime` | Date-time with fixed offset `+07:00` or `Z` | APIs requiring an explicit offset |
| `ZonedDateTime` | Date-time with IANA `ZoneId` and DST rules | Appointments in `Europe/Paris` |
| `Duration` | Timeline length in seconds/nanos | Timeout, 60-minute TTL |
| `Period` | Calendar difference in years/months/days | Expires after one calendar month |
| `Clock` | Injected source of current time | Freezing/advancing time in tests |

Given `Instant` = `2025-01-01T00:30:00Z`:

~~~text
UTC:                    2025-01-01 00:30
Asia/Ho_Chi_Minh:       2025-01-01 07:30
America/Los_Angeles:    2024-12-31 16:30
~~~

This is **the exact same instant**, yet it maps to two different calendar dates depending on business zone. If a test verifies “closing business date in Vietnam,” explicitly use `Asia/Ho_Chi_Minh`, never the OS setting.

**Avoid `LocalDateTime` for absolute timestamps**: `2025-01-01T00:30` does not tell you whether it is UTC, Hanoi, or Los Angeles. You need a `ZoneId` or `ZoneOffset` to turn it into an `Instant`.

## 4. Clock: Making Time Testable

Production bean:

~~~java
@Bean
Clock clock() {
    return Clock.systemUTC();
}
~~~

Test setup:

~~~java
Instant base = Instant.parse("2025-01-01T00:30:00Z");
Clock fixed = Clock.fixed(base, ZoneOffset.UTC);
Clock plusTwoHours = Clock.offset(fixed, Duration.ofHours(2));
~~~

These are illustrative Java snippets requiring imports for `java.time.Clock`, `Instant`, `ZoneOffset`, and `Duration`. With a fixed clock, `fixed.instant()` always returns `base`; with an offset clock, time can be simulated **advancing by two hours without sleeping**.

A service with TTL logic should do:

~~~java
Instant createdAt = clock.instant();
Instant expiresAt = createdAt.plus(Duration.ofHours(1));
~~~

Instead of:

~~~java
// Anti-example: two system clock reads can drift apart.
Instant createdAt = Instant.now();
Instant expiresAt = Instant.now().plus(Duration.ofHours(1));
~~~

**Never instantiate `Clock.fixed` in production code** unless the domain intentionally requires a simulated clock. Tests swap `Clock` via `@Primary` or a test bean; production source retains `Clock.systemUTC`.

`Clock` injection **cannot control** timestamps generated by DB `CURRENT_TIMESTAMP`, triggers, Kafka brokers, independent schedulers, or external systems. Those sources must be tested separately rather than assuming a frozen Java `Clock` freezes the entire system.

## 5. Timezones: ZoneId Differs from Offset

- `ZoneOffset.ofHours(7)` is a fixed numeric offset.
- `ZoneId.of("Asia/Ho_Chi_Minh")` is an IANA timezone with its own historical and transition rules.
- `ZoneId.of("America/New_York")` observes DST: `-05:00` in winter, `-04:00` in summer per 2025 rules.

For regional schedules, use **`ZoneId`** instead of hardcoding the current month's offset. Conversely, an `Instant` stored in UTC may not need a local timezone if the app only computes a 60-minute timeline expiry.

### A Day Is Not Always 24 Local Hours

- `instant.plus(Duration.ofDays(1))` adds exactly **24 hours**.
- `zonedDateTime.plusDays(1)` adds **one calendar day**, which can span 23 or 25 hours across a DST transition.

Clarify the contract: “TTL of 24 hours” differs from “at 09:00 tomorrow Paris time.” Tests should include DST transition dates when applications schedule by local time.

### DST Gaps and Overlaps

`ZoneRules.getValidOffsets(localDateTime)` classifies local times:

| New York in 2025 | Valid Offset Count | Consequence |
| --- | --- | --- |
| `2025-03-09T02:30` | 0 | Gap: this wall time does not exist |
| `2025-11-02T01:30` | 2 | Overlap: this wall time occurs twice |
| `2025-01-15T09:00` | 1 | Normal unambiguous case |

The JUnit code in Section 12 verifies both DST boundaries. If a user schedules an appointment during a gap or overlap, the application needs an **explicit policy**: reject it, shift to a valid time, or require choosing an offset—never rely silently on library ambiguity defaults.

Tzdb rules evolve when national laws change. For sensitive future dates, pin CI's JDK/tzdb version or test invariants rather than assuming DST laws never change.

## 6. Locale: Distinct from Timezone, Affecting Language and Formatting

`Locale.forLanguageTag("vi-VN")` represents Vietnamese in Vietnam; `Locale.forLanguageTag("en-US")` is US English; `Locale.ROOT` is the neutral locale for technical data processing.

**Locale does not imply timezone.** An `Accept-Language: vi-VN` header does not prove the user is in Vietnam; a Vietnamese speaker in California can pick a Vietnamese UI while business dates follow a US branch's timezone.

Impacts to test:

1. **Messages:** `MessageSource.getMessage(key, args, locale)` reads resource bundles instead of hardcoding strings in controllers.
2. **Numbers:** `NumberFormat.getNumberInstance(locale)` varies grouping and decimal separators.
3. **Currencies:** require an explicit `Currency` or business currency code rather than inferring from locale alone.
4. **Formatted dates:** `DateTimeFormatter.ofLocalizedDate(...)` is language-sensitive.
5. **Technical normalization:** `toLowerCase(Locale.ROOT)` avoids the Turkish-I trap.

Turkish-I example:

~~~java
assertEquals("id", "ID".toLowerCase(Locale.ROOT));
assertEquals(
        "ıd",
        "ID".toLowerCase(Locale.forLanguageTag("tr-TR"))
);
~~~

This is an illustrative JUnit body, not a standalone file; `ı` is the dotless-i character, distinct from ASCII `i`. **Never** call zero-argument `toLowerCase()` on protocol keys or stable identifiers.

### JDK/CLDR Do Not Guarantee Every Format Character Stays Immutable

A `NumberFormat` string for `fr-FR` may use NBSP or narrow NBSP, looking nearly identical to an ordinary ASCII space. Asserting exact localized text can break across JDK/CLDR upgrades. When the contract only cares about **numeric values**, assert JSON numbers or parse with a specific locale; when the contract mandates **exact formatted strings**, pin the formatter, runtime, and expected separator characters.

Locale fallback must be configured intentionally. Spring Boot auto-configures `MessageSource` only when a base bundle like `messages.properties` is present (unless customized); if only `messages_vi.properties` exists without the base bundle, do not assume Boot created the `MessageSource` you expect.

## 7. Hands-On Exercise: A Deterministic REST Response for ID, Time, and Locale

We build a receipt endpoint **without database writes** so dependencies stay crystal clear. Request:

~~~http
POST /api/receipts
Content-Type: application/json
Accept-Language: vi-VN

{"sku":"SKU-7"}
~~~

Expected response in the test:

~~~json
{
  "id": "00000000-0000-4000-8000-000000000007",
  "sku": "SKU-7",
  "createdAt": "2025-01-01T00:30:00Z",
  "expiresAt": "2025-01-01T01:30:00Z",
  "businessDate": "2025-01-01",
  "languageTag": "vi-VN",
  "message": "Đã tạo"
}
~~~

At the same `Instant`, if the zone is `America/Los_Angeles`, `businessDate` becomes `2024-12-31`. With `Accept-Language: en-US` and the zone still in Vietnam, `message` becomes `Created` while `createdAt` and `businessDate` remain unchanged.

Concrete contract:

- Production IDs come from `UUID.randomUUID()` behind `IdGenerator`; tests fake a known ID.
- Production time comes from `Clock.systemUTC()`; tests inject `Clock.fixed`.
- Business zone comes from `app.business-zone=Asia/Ho_Chi_Minh`, never `systemDefault`.
- Messages come from `MessageSource` using the request's locale.
- JSON dates/times are ISO strings rather than locale-dependent formats.
- Request `sku` must pass `@NotBlank`, rejecting blank inputs with 400.

**`src/main/java/com/example/deterministic/ReceiptService.java`:**

~~~java
package com.example.deterministic;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.time.LocalDate;
import java.time.ZoneId;
import java.util.Locale;
import java.util.Objects;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.MessageSource;
import org.springframework.stereotype.Service;

@Service
public class ReceiptService {
    private final Clock clock;
    private final IdGenerator ids;
    private final MessageSource messages;
    private final ZoneId businessZone;

    public ReceiptService(
            Clock clock,
            IdGenerator ids,
            MessageSource messages,
            @Value("${app.business-zone:Asia/Ho_Chi_Minh}")
            String configuredBusinessZone
    ) {
        this.clock = Objects.requireNonNull(clock, "clock");
        this.ids = Objects.requireNonNull(ids, "ids");
        this.messages = Objects.requireNonNull(messages, "messages");
        this.businessZone = ZoneId.of(configuredBusinessZone);
    }

    public ReceiptResponse issue(String sku, Locale locale) {
        Objects.requireNonNull(sku, "sku");
        Objects.requireNonNull(locale, "locale");

        Instant createdAt = clock.instant();
        LocalDate businessDate = createdAt.atZone(businessZone)
                .toLocalDate();

        String message = messages.getMessage(
                "receipt.created", null, locale
        );

        return new ReceiptResponse(
                ids.next(),
                sku,
                createdAt,
                createdAt.plus(Duration.ofHours(1)),
                businessDate,
                locale.toLanguageTag(),
                message
        );
    }
}
~~~

**Key takeaways:**

- `clock.instant()` is read once, and expiry is derived from that exact same instant.
- `@Value` injects the explicit business zone; `ZoneId.of` fails fast on invalid zone IDs instead of falling back silently to the OS zone.
- `Locale` is passed in by the caller; `Locale.getDefault()` is never called in the service.
- Messages are resolved from bundles rather than hardcoding language branches in business logic.
- IDs come from an injected interface rather than calling random generators directly in the service.

### Translations

**`src/main/resources/messages.properties`:**

~~~properties
receipt.created=Created
~~~

**`src/main/resources/messages_vi.properties`:**

~~~properties
receipt.created=Đã tạo
~~~

With locale `vi-VN`, Spring resolves the Vietnamese bundle; with `en-US` (which has no dedicated English bundle here), the base `messages.properties` returns `Created`. This is **configured fallback**, independent of the machine's `Locale.getDefault`.

## 11. HTTP Controller Using the Request's Locale

**`src/main/java/com/example/deterministic/ReceiptController.java`:**

~~~java
package com.example.deterministic;

import java.util.Locale;

import jakarta.validation.Valid;

import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/receipts")
public class ReceiptController {
    private final ReceiptService service;

    public ReceiptController(ReceiptService service) {
        this.service = service;
    }

    @PostMapping(
            consumes = MediaType.APPLICATION_JSON_VALUE,
            produces = MediaType.APPLICATION_JSON_VALUE
    )
    public ReceiptResponse create(
            @Valid @RequestBody ReceiptRequest request,
            Locale locale
    ) {
        return service.issue(request.sku().trim(), locale);
    }
}
~~~

Spring MVC resolves `Locale` using `LocaleResolver`. By default it inspects `Accept-Language`; the HTTP tests send that header explicitly. This never alters the business `ZoneId`.

The controller returns `200 OK` because this demo builds a response without **persisting to a DB**. In production apps that persist resources, you might choose `201 Created` + `Location` and dedicated transactions. HTTP status codes are a separate contract, unrelated to faking IDs or `Clock`.

`@Valid` and `@NotBlank` let Spring return `400` for empty or whitespace-only SKUs. This requires `starter-validation`, declared in `build.gradle`.

## 12. JUnit Unit Test: Controlling ID, Time, Zone, and Locale

**`src/test/java/com/example/deterministic/ReceiptServiceTimeTest.java`:**

~~~java
package com.example.deterministic;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZoneOffset;
import java.util.Locale;
import java.util.UUID;

import org.junit.jupiter.api.Test;
import org.springframework.context.support.StaticMessageSource;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

class ReceiptServiceTimeTest {
    private static final Instant BASE =
            Instant.parse("2025-01-01T00:30:00Z");
    private static final UUID ID = UUID.fromString(
            "00000000-0000-4000-8000-000000000007"
    );

    private StaticMessageSource messages() {
        StaticMessageSource source = new StaticMessageSource();
        source.addMessage(
                "receipt.created",
                Locale.forLanguageTag("vi-VN"),
                "Đã tạo"
        );
        source.addMessage(
                "receipt.created",
                Locale.forLanguageTag("en-US"),
                "Created"
        );
        return source;
    }

    private Clock fixed() {
        return Clock.fixed(BASE, ZoneOffset.UTC);
    }

    private ReceiptService service(String zone, Clock clock) {
        return new ReceiptService(
                clock, () -> ID, messages(), zone
        );
    }

    @Test
    void fixedClockAndIdGiveExactOutput() {
        ReceiptResponse receipt = service(
                "Asia/Ho_Chi_Minh", fixed()
        ).issue("SKU-7", Locale.forLanguageTag("vi-VN"));

        assertEquals(ID, receipt.id());
        assertEquals("SKU-7", receipt.sku());
        assertEquals(BASE, receipt.createdAt());
        assertEquals(
                Instant.parse("2025-01-01T01:30:00Z"),
                receipt.expiresAt()
        );
        assertEquals(LocalDate.of(2025, 1, 1), receipt.businessDate());
        assertEquals("vi-VN", receipt.languageTag());
        assertEquals("Đã tạo", receipt.message());
    }

    @Test
    void sameInstantCanHaveDifferentCalendarDates() {
        ReceiptResponse hcm = service(
                "Asia/Ho_Chi_Minh", fixed()
        ).issue("SKU-7", Locale.forLanguageTag("en-US"));

        ReceiptResponse la = service(
                "America/Los_Angeles", fixed()
        ).issue("SKU-7", Locale.forLanguageTag("en-US"));

        assertEquals(hcm.createdAt(), la.createdAt());
        assertEquals(LocalDate.of(2025, 1, 1), hcm.businessDate());
        assertEquals(LocalDate.of(2024, 12, 31), la.businessDate());
    }

    @Test
    void offsetClockSimulatesFutureWithoutSleeping() {
        Clock later = Clock.offset(fixed(), Duration.ofHours(2));

        ReceiptResponse receipt = service(
                "Asia/Ho_Chi_Minh", later
        ).issue("SKU-7", Locale.forLanguageTag("en-US"));

        assertEquals(
                Instant.parse("2025-01-01T02:30:00Z"),
                receipt.createdAt()
        );
        assertEquals(
                Instant.parse("2025-01-01T03:30:00Z"),
                receipt.expiresAt()
        );
    }

    @Test
    void newYorkSpringForwardGapHasNoOffset() {
        ZoneId ny = ZoneId.of("America/New_York");
        LocalDateTime gap = LocalDateTime.of(2025, 3, 9, 2, 30);

        assertTrue(ny.getRules().getValidOffsets(gap).isEmpty());
    }

    @Test
    void newYorkFallBackOverlapHasTwoOffsets() {
        ZoneId ny = ZoneId.of("America/New_York");
        LocalDateTime overlap = LocalDateTime.of(2025, 11, 2, 1, 30);

        assertEquals(
                2, ny.getRules().getValidOffsets(overlap).size()
        );
    }

    @Test
    void localeChangesMessageButNotInstant() {
        ReceiptService service = service("Asia/Ho_Chi_Minh", fixed());
        ReceiptResponse vi = service.issue(
                "SKU-7", Locale.forLanguageTag("vi-VN")
        );
        ReceiptResponse en = service.issue(
                "SKU-7", Locale.forLanguageTag("en-US")
        );

        assertEquals("Đã tạo", vi.message());
        assertEquals("Created", en.message());
        assertEquals(vi.createdAt(), en.createdAt());
        assertEquals(vi.businessDate(), en.businessDate());
    }

    @Test
    void technicalKeysMustUseLocaleRoot() {
        assertEquals("id", "ID".toLowerCase(Locale.ROOT));
        assertEquals(
                "ıd",
                "ID".toLowerCase(Locale.forLanguageTag("tr-TR"))
        );
    }

    @Test
    void wrongIanaZoneFailsEarly() {
        assertThrows(
                java.time.DateTimeException.class,
                () -> service("Not/A_Real_Zone", fixed())
        );
    }
}
~~~

There are **8 test methods** requiring no Spring context, server, DB, or sleeps. `StaticMessageSource` supplies translations in Java, isolating the unit test from production resource bundles. Every time assertion checks concrete values, and DST checks inspect `ZoneRules` instead of guessing from the host clock.

Note: when switching to reactive time sources with schedulers (e.g., Reactor `Flux.interval`), `Clock.fixed` does not control every scheduler; use the corresponding virtual scheduler/time API.

            Class<T> responseType
    ) {
        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.setAcceptLanguageAsLocales(
                List.of(Locale.forLanguageTag(languageTag))
        );

        return http.exchange(
                "/api/receipts",
                HttpMethod.POST,
                new HttpEntity<>(new ReceiptRequest(sku), headers),
                responseType
        );
    }

    @Test
    void vietnameseRequestHasFixedValues() {
        ResponseEntity<ReceiptResponse> response =
                post("vi-VN", "SKU-7", ReceiptResponse.class);

        assertEquals(HttpStatus.OK, response.getStatusCode());
        assertNotNull(response.getBody());

        ReceiptResponse result = response.getBody();
        assertEquals(EXPECTED_ID, result.id());
        assertEquals("SKU-7", result.sku());
        assertEquals(BASE, result.createdAt());
        assertEquals(
                Instant.parse("2025-01-01T01:30:00Z"),
                result.expiresAt()
        );
        assertEquals(LocalDate.of(2025, 1, 1), result.businessDate());
        assertEquals("vi-VN", result.languageTag());
        assertEquals("Đã tạo", result.message());
    }

    @Test
    void englishLocaleChangesLanguageButNotBusinessTime() {
        ResponseEntity<ReceiptResponse> response =
                post("en-US", "SKU-7", ReceiptResponse.class);

        assertEquals(HttpStatus.OK, response.getStatusCode());
        assertNotNull(response.getBody());

        ReceiptResponse result = response.getBody();
        assertEquals(EXPECTED_ID, result.id());
        assertEquals(BASE, result.createdAt());
        assertEquals(LocalDate.of(2025, 1, 1), result.businessDate());

        assertEquals("Created", result.message());
    }

    @Test
    void jsonDatesHaveStableIsoRepresentation() {
        ResponseEntity<String> response =

        assertEquals(HttpStatus.OK, response.getStatusCode());

    @Test

        assertEquals(

        );
    }
}
~~~

**Four test methods** run here against a real Spring Boot server on a random port via `TestRestTemplate`, rather than just invoking the service in a unit test. They prove:

- `@Primary Clock` and `@Primary IdGenerator` beans from `@TestConfiguration` are injected into the service.
- Spring MVC resolves `Accept-Language` into `Locale`, and `MessageSource` returns the right translation.
- Jackson outputs `Instant` and `LocalDate` in the ISO contract format rather than epoch timestamps, regardless of JSON key ordering.
- Blank SKU inputs are rejected by Bean Validation before creating a receipt.

**The demo does not persist to a DB**, so reusing the same fixed UUID across requests serves assertions cleanly without triggering duplicate primary keys. When adding a repository, use a fake generator producing a repeatable sequence of unique IDs and seed/reset the database per test.

`@TestConfiguration` lives solely in test sources; production continues using the random generator and `Clock.systemUTC`. Using `@Primary` beans is cleaner than using `@MockBean` and forgetting to stub `Clock.instant()`, which causes services to receive `null`.

## 14. Multiple IDs: Ordered Sequence Fakes Instead of One Constant

When a test creates multiple entities, a single fixed ID is insufficient. Use a sequence-based generator:

~~~java
import java.util.Iterator;
import java.util.List;
import java.util.UUID;

final class SequenceIdGenerator implements IdGenerator {
    private final Iterator<UUID> values;

    SequenceIdGenerator(List<UUID> ids) {
        values = List.copyOf(ids).iterator();
    }

    @Override
    public UUID next() {
        if (!values.hasNext()) {
            throw new AssertionError("Unexpected extra ID request");
        }
        return values.next();
    }
}
~~~

This is an **illustrative class** to place in the appropriate package alongside `IdGenerator` from Section 9; it is not part of the main demo's runnable files. For two distinct IDs:

~~~java
IdGenerator ids = new SequenceIdGenerator(
        List.of(
                UUID.fromString("00000000-0000-4000-8000-000000000001"),
                UUID.fromString("00000000-0000-4000-8000-000000000002")
        )
);
~~~

This is an illustrative setup snippet requiring `List` and `UUID` imports. An `Iterator`-backed fake is **not thread-safe**; never share a mutable singleton generator across parallel tests. Instantiate a dedicated fake per test, or design concurrency-safe ID derivation/namespaces.

When IDs come from DB `@GeneratedValue`/sequences, assert **relationships** using the ID returned by the DB rather than assuming the sequence resets to 1 before every test. Under parallel DB tests, exact sequence numbers are an artifact of DB state, not a business contract.

## 15. Database Timestamps, JDBC Timezones, and Precision

Time sources exist beyond Java:

- `Clock` controls code calling `clock.instant()`.
- DB `CURRENT_TIMESTAMP` and triggers use the **database server's** clock.
- Message brokers may attach their own broker timestamps.
- Hibernate/JDBC converts between `Instant`, `LocalDateTime`, session timezone, and `TIMESTAMP` columns depending on the database.
- Databases may store microsecond or millisecond precision, truncating nanoseconds.

Testing strategy:

1. When the service creates timestamps, **inject a fixed `Clock`**, persist `Instant`, and assert round-trips within the defined precision.
2. When the DB generates timestamps, never claim a fixed Java `Clock` controls the DB. Assert valid bounds or use test DB clock/fixtures if infrastructure supports it.
3. With Hibernate, `spring.jpa.properties.hibernate.jdbc.time_zone=UTC` configures the JDBC timezone depending on version/driver; it **does not replace `Clock`** and does not turn ambiguous DB local datetimes into clear instants.
4. For critical database behavior, use Testcontainers matching the production engine instead of extrapolating from H2.
5. When assertions require ordering events within the same millisecond, use explicit sequence numbers or business ordering rather than relying on timestamps alone to break ties.

### `@DataJpaTest` Still Needs Isolated Fixtures

`@DataJpaTest` normally provides a test-managed transaction with rollback, whereas a `REQUIRES_NEW` service or an HTTP server thread can commit outside the test transaction. Use explicit cleanup or resets for committed fixtures. Never assume every row vanishes automatically after every test regardless of transaction boundaries.

When seeding multiple rows, assign per-case primary/business keys and never rely on `findAll()` ordering without `ORDER BY`. Expected-output reproducibility **cannot be guaranteed** if queries lack a deterministic order contract.

## 16. Number/Date Formatting and Non-Fixed CI Locales

Localized formats can change across JDK/CLDR releases. For example:

~~~java
NumberFormat fr = NumberFormat.getNumberInstance(
        Locale.forLanguageTag("fr-FR")
);
String formatted = fr.format(12345.67);
~~~

This illustrative snippet requires `java.text.NumberFormat` and `java.util.Locale`. The thousands separator may be a non-breaking space or narrow no-break space. When an API returns **numbers**, prefer JSON numbers and format in the UI rather than converting numbers to localized text on the backend under the JVM's default locale.

For currencies, specify `Currency.getInstance("VND")` or an explicit contract currency code; locale never replaces currency units. For locale-formatted display dates, pass `DateTimeFormatter.withLocale(locale)` while applying the right zone before extracting `LocalDate`.

Never call `Locale.setDefault` or `TimeZone.setDefault` in ordinary unit tests. They mutate **JVM-wide global state**, leaking into other tests even when your test passes. If legacy code absolutely forces testing default changes, restore them in `try/finally` and forbid parallel execution; even then, it is a temporary compatibility shim rather than a substitute for dependency injection.

## 17. Reproducibility Under Parallel Execution and in CI

Reasons tests pass individually yet fail in a suite:

- Test A mutates `Locale.setDefault` while Test B formats strings on another thread.
- Two tests share a mutable static fake `Clock`.
- A singleton `IdGenerator` increments counters inside a cached context, making output depend on test order.
- DB tests share primary keys, and one test wipes rows while another reads them.
- An HTTP server runs on another thread and commits DB rows while the test client assumes rollback cleaned them up.
- CI upgrades JDK/tzdb/CLDR, shifting localization or DST rules.
- Tests hardcode environment-dependent hosts, ports, or paths.

Mitigations:

- Use immutable `Clock.fixed` fakes and per-test or stateless generators; never mutate singletons across test methods.
- Scope synthetic data with per-test/per-CI-worker namespaces, explicit cleanup, or separate databases/schemas.
- Never sleep to wait for time or events; use `Clock.offset`, virtual schedulers, or latches/barriers/bounded awaits.
- Pin the JDK toolchain, Spring Boot BOM, and CI TZ/locale **as a defensive guardrail**, without letting business code depend on ambient defaults.
- Run an extra suite pass with `-Duser.language=tr -Duser.country=TR -Duser.timezone=America/Los_Angeles` to expose hidden ambient-state dependencies.
- For future dates in DST zones, manage tzdb updates and avoid promising that local DST laws will never change.

## 18. Common Mistakes and How to Fix Them

| Mistake | Consequence | Proper Fix |
| --- | --- | --- |
| Asserting a literal UUID generated by `UUID.randomUUID()` | Expected value changes randomly | Inject a generator or assert structure |
| Reusing one fixed ID across multiple DB inserts | Duplicate PK error | Use a deterministic sequence of distinct IDs |
| Asserting DB-generated sequences start at 1 | Fails when sequences do not reset | Use returned IDs and assert relationships |
| Calling `Instant.now()` directly in business logic | Tests depend on CI wall clock | Inject `Clock` |
| Reading the clock twice for created/expiry | Drift by milliseconds | Capture one `Instant` and add `Duration` |
| Using `Thread.sleep` to wait for expiration | Slow and flaky | `Clock.offset` or virtual time on the scheduler |
| Calling `LocalDate.now()` without a zone | Returns different dates around midnight | `Instant` + explicit `ZoneId` |
| Using `ZoneId.systemDefault()` | Differs between CI and laptops | Business zone from config or tenant |
| Implicit `Locale.getDefault()` | Varying language/formatting | Explicit `Locale` and message bundles |
| Calling `toLowerCase()` on technical keys | Turkish-I bug | `Locale.ROOT` |
| Inferring timezone from `Accept-Language` | Wrong business date | Separate `ZoneId` from `Locale` |
| Using fixed offsets for DST regions | Wrong hour across seasonal switches | IANA timezone and gap/overlap tests |
| Using `LocalDateTime` as a UTC timestamp | Ambiguous without offset | `Instant` or `OffsetDateTime` |
| Asserting raw localized separators without pinning CLDR | Breaks on JDK upgrades | Assert semantics or pin runtime |
| Using fixed `Clock` while DB uses `CURRENT_TIMESTAMP` | DB still writes real `now` | Test DB-generated timestamps separately |
| Changing `TimeZone.setDefault` across the suite | Pollutes other tests | Inject `Clock` and `ZoneId` |
| Mocking `Clock` without stubbing `instant()` | `NullPointerException` | Use real `Clock.fixed` |
| Sharing a mutable test generator | Order-dependent failures | Fresh fake per test |
| Assuming HTTP tests roll back server writes | Leftover rows remain | Seed/clean up outside the test transaction |
| Never asserting the JSON ISO contract | Clients decode incorrectly | Test raw JSON and precision |

## 19. Code Review and QA Checklist

- [ ] Are IDs controlled via an injected generator or asserted relationally using returned IDs?
- [ ] When creating multiple records, do fake generators avoid returning duplicate IDs?
- [ ] Is business logic free of direct `Instant.now()` and `UUID.randomUUID()` calls outside infrastructure?
- [ ] Is `Clock` injected in production and replaced by a fixed clock in tests?
- [ ] Are related timestamps computed from **one** captured `Instant`?
- [ ] Are TTLs modeled with `Duration` and tested without `sleep`?
- [ ] Do business dates use an explicit IANA `ZoneId` instead of system defaults?
- [ ] Do calendar operations crossing DST include gap/overlap tests where relevant?
- [ ] Does `Locale` for text and formatting come from inputs or explicit configuration?
- [ ] Are technical identifiers normalized with `Locale.ROOT`?
- [ ] Does a default resource bundle exist, with fallback locales tested?
- [ ] Do HTTP tests send `Accept-Language` explicitly?
- [ ] Do JSON timestamps enforce an explicit ISO/offset/precision contract?
- [ ] Are DB-generated timestamps kept distinct from Java `Clock`?
- [ ] Are database fixtures properly seeded, cleaned up, and isolated for parallel runs?
- [ ] Do tests avoid mutating process-global `Locale`/`TimeZone`?
- [ ] Do tests avoid assuming DB query order without `ORDER BY`?
- [ ] Are JDK/tzdb/CLDR versions managed if byte-for-byte localized formatting is part of the contract?
- [ ] Are unit, HTTP integration, and DB integration tests scoped cleanly?
