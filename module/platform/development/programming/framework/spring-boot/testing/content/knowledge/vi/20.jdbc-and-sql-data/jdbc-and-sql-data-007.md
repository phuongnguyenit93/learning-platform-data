# Generated key, batch update và ràng buộc database

Trong ứng dụng Java sử dụng JDBC, viết thành công một câu lệnh `INSERT` chưa có nghĩa workflow ghi dữ liệu đã đúng. Khi database tạo khóa chính tự động, chương trình phải lấy **generated key** một cách đáng tin cậy; khi ghi nhiều hàng, **batch update** phải xử lý row count, lỗi giữa chừng và transaction; khi dữ liệu có quan hệ, các ràng buộc **PRIMARY KEY, UNIQUE, NOT NULL, CHECK, FOREIGN KEY** phải được kiểm bằng database thật, không chỉ dựa vào điều kiện `if` trong service.

Ba chủ đề này liên quan chặt chẽ. Một use case tạo hóa đơn gồm một hàng `invoice` có ID do database sinh, nhiều hàng `invoice_line` trỏ tới ID ấy, và các điều kiện dữ liệu cần giữ đúng ngay cả khi nhiều request đồng thời ghi. Nếu lấy sai key, line có thể gắn nhầm parent. Nếu batch gặp lỗi nhưng phần đã ghi không được rollback, dữ liệu bị dở dang. Nếu chỉ mock `JdbcTemplate`, bạn **không thể chứng minh** database thực thi constraint và transaction chính xác.

Bài Knowledge này đặt trong module **Spring Boot – testing**, nhóm **JDBC và dữ liệu SQL**, hướng tới **Java 17+, Spring Boot 3.5.x, Spring JDBC, JUnit Jupiter 5 và H2**. Có project mẫu đầy đủ với `JdbcTemplate`, `NamedParameterJdbcTemplate`, `GeneratedKeyHolder`, `@JdbcTest`, `@SpringBootTest`, `@Transactional` và SQL fixtures. H2 chỉ là database phục vụ học tập; khi production dùng PostgreSQL/MySQL/SQL Server/Oracle, những hành vi liên quan driver, dialect, identity, constraint và locking cần được kiểm bổ sung **trên đúng hệ quản trị**.

## 1. Sau bài học bạn làm được gì?

- Giải thích ý nghĩa **generated key** và vì sao **không** dự đoán ID bằng `MAX(id)+1` hay giả định ID liên tục.
- Dùng Spring JDBC `GeneratedKeyHolder` để lấy khóa sau `INSERT`, kiểm trường hợp key không được trả và hỗ trợ driver khác nhau.
- Phân biệt `JdbcTemplate.update`, `NamedParameterJdbcTemplate.update` và `batchUpdate`.
- Đọc đúng ý nghĩa các phần tử `int[]`/`int[][]` update counts, kể cả `Statement.SUCCESS_NO_INFO` và `Statement.EXECUTE_FAILED`.
- Thiết kế batch nhỏ có bound parameters; không nối chuỗi SQL bằng dữ liệu đầu vào.
- Thử các constraint `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `FOREIGN KEY` bằng SQL thực.
- Dùng `@Transactional` tại service boundary để **rollback** khi batch lỗi, không coi batch tự động atomic.
- Phân biệt `@JdbcTest` rollback theo test với **rollback thật của service**.
- Soạn regression tests bắt được duplicate key, số tiền không hợp lệ, line trỏ parent không tồn tại, row count bất thường và partial batch failure.
- Biết khi nào H2 đủ, khi nào cần Testcontainers/DB thật để bắt khác biệt dialect, sequence, generated keys và concurrency.

## 2. Tình huống xuyên suốt: hóa đơn và chi tiết hóa đơn

Ta xây mô hình:

```text
invoice
 + id             BIGINT IDENTITY, PRIMARY KEY
 + external_ref   UNIQUE, NOT NULL
 + amount_minor   > 0
 + status         NEW | PAID
           |
           | 1 : n
           v
invoice_line
 + id             BIGINT IDENTITY, PRIMARY KEY
 + invoice_id     FOREIGN KEY -> invoice.id
 + sku            NOT NULL
 + quantity       > 0
 + UNIQUE(invoice_id, sku)
```

Ví dụ flow tạo một hóa đơn có hai dòng:

```text
HTTP/application call
    |
    v
InvoiceRegistrationService.createWithLines(...)
    |
    +-- Transaction BEGIN
    |
    +-- INSERT invoice (external_ref, amount_minor)
    |       -> database sinh invoice.id
    |       -> GeneratedKeyHolder đọc id
    |
    +-- batch INSERT invoice_line
    |       -> mọi line dùng invoice_id vừa sinh
    |
    +-- nếu không lỗi: COMMIT
    +-- nếu constraint/batch error: ROLLBACK
```

Ứng dụng demo lưu **số tiền theo đơn vị nhỏ nhất của tiền tệ** vào `amount_minor` (ví dụ cent), không dùng `double`. Mục tiêu ở đây là JDBC/testing, không triển khai toàn bộ nghiệp vụ accounting hoặc thuế.

## 3. Generated key là gì?

Một bảng có thể để database cấp ID cho mỗi bản ghi:

```sql
CREATE TABLE invoice (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    external_ref VARCHAR(64) NOT NULL UNIQUE,
    amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
    status VARCHAR(12) NOT NULL DEFAULT 'NEW'
);
```

Khi gửi:

```sql
INSERT INTO invoice (external_ref, amount_minor)
VALUES ('INV-A', 10000);
```

SQL không chỉ định `id`. Database dùng identity/sequence hoặc cơ chế tương ứng để sinh nó. Java cần lấy key bằng JDBC API `getGeneratedKeys()` hoặc Spring JDBC wrapper.

Những điều **không được suy luận**:

- ID đầu tiên luôn bằng `1`.
- ID sẽ liên tục, không có khoảng trống; sequence/identity có thể tăng dù transaction rollback.
- ID kế tiếp bằng `MAX(id)+1`; kỹ thuật này có race condition khi concurrent inserts.
- Database nào cũng hỗ trợ generated keys như nhau, hoặc trả key cùng tên/cùng kiểu Java.
- Batch insert luôn trả về danh sách ID theo thứ tự input trên mọi driver.
- Lấy được generated key nghĩa là transaction đã commit; có thể rollback sau đó.

**Key là định danh**, không nhất thiết mang ý nghĩa thời gian, thứ tự hay số thứ tự nghiệp vụ. Nếu cần mã hóa đơn thân thiện người dùng, hãy thiết kế một `external_ref`/business identifier riêng và kiểm uniqueness/idempotency.

## 4. JDBC thuần: `PreparedStatement.RETURN_GENERATED_KEYS`

Với JDBC thuần, pattern điển hình:

```java
// Snippet minh họa trong method có Connection connection.
String sql = """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (?, ?)
        """;

try (PreparedStatement statement = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS)) {
    statement.setString(1, "INV-JDBC");
    statement.setLong(2, 10000L);

    int affected = statement.executeUpdate();
    if (affected != 1) {
        throw new SQLException("Expected one inserted row");
    }

    try (ResultSet keys = statement.getGeneratedKeys()) {
        if (!keys.next()) {
            throw new SQLException("No generated key returned");
        }
        long id = keys.getLong(1);
        // Dùng id để ghi invoice_line, trong cùng transaction.
    }
}
```

Imports cần thiết: `java.sql.PreparedStatement`, `Statement`, `ResultSet`, `SQLException`. Đây là **snippet**, không phải file Java độc lập: `connection` phải được tạo và transaction/cleanup do caller quản lý.

Một số driver thích được chỉ định tên cột:

```java
// Snippet JDBC thuần, nếu driver hỗ trợ tên cột.
connection.prepareStatement(sql, new String[] {"ID"});
```

Đừng dùng `Statement.RETURN_GENERATED_KEYS` như bằng chứng mọi DB chắc chắn trả khóa. JDBC driver có quyền báo không hỗ trợ hoặc trả kiểu/metadata khác. Với PostgreSQL, giải pháp native `INSERT ... RETURNING id` cũng có thể phù hợp nếu bạn chủ động chấp nhận phụ thuộc dialect; với Spring JDBC muốn giữ API khái quát thì bắt đầu bằng `KeyHolder`.

## 5. Spring JDBC: `GeneratedKeyHolder`

`GeneratedKeyHolder` gom kết quả generated keys mà `JdbcTemplate` hoặc `NamedParameterJdbcTemplate` nhận từ driver.

Ví dụ lõi:

```java
KeyHolder holder = new GeneratedKeyHolder();

int affected = named.update(
        """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (:ref, :amount)
        """,
        new MapSqlParameterSource()
                .addValue("ref", externalRef)
                .addValue("amount", amountMinor),
        holder,
        new String[] {"id"});

if (affected != 1) {
    throw new IllegalStateException(
            "Expected exactly one inserted invoice");
}

Number key = holder.getKey();
if (key == null) {
    throw new IllegalStateException(
            "Driver did not return invoice ID");
}
long invoiceId = key.longValue();
```

Đây là **snippet**; phần 14 có class repository runnable với đầy đủ imports.

Chữ `id` trong `keyColumnNames` chỉ rõ column cần lấy. Với H2 của ví dụ, cột `id` được khai báo là identity. Ở hệ DB khác, cần kiểm driver có hiểu tên cột theo case hoặc cần SQL native `RETURNING` không.

### 5.1. Vì sao gọi `getKey()` đôi khi không phù hợp?

`getKey()` thuận tiện khi **chỉ có đúng một generated key** trong holder và value là `Number`. Khi driver trả nhiều cột hoặc nhiều hàng, phải xem `getKeys()`/`getKeyList()` và hiểu map key names/type thay vì ép một kết quả thành `long`.

Ví dụ nếu statement trả `id` **và** `created_at`, `getKey()` có thể không áp dụng; cần truy cập theo tên cột trong map. Nếu driver không trả key, không “sửa” bằng cách đoán `MAX(id)`; hãy điều tra driver/SQL/DDL và đưa lỗi thành failure rõ ràng.

## 6. Tại sao không dùng `SELECT MAX(id)`?

Một anti-pattern:

```java
// PHẢN VÍ DỤ: dễ trả ID của giao dịch khác.
jdbc.update("INSERT INTO invoice (...) VALUES (...)");
Long id = jdbc.queryForObject(
        "SELECT MAX(id) FROM invoice", Long.class);
```

Hai threads cùng ghi:

```text
Thread A INSERT -> ID 101
Thread B INSERT -> ID 102
Thread A SELECT MAX(id) -> 102 (SAI)
```

Sequence/identity là cơ chế DB quản lý. Dùng `getGeneratedKeys()`/`KeyHolder` hoặc `RETURNING` phù hợp. Đừng dùng một global MAX query để tra “ID vừa ghi”.

Cũng đừng tìm dòng vừa insert bằng `external_ref` nếu quy tắc uniqueness/idempotency chưa rõ. Nếu một request bị retry, `external_ref` có thể cố tình trùng và DB trả duplicate key; cần thiết kế hành vi retry riêng (đọc bản ghi cũ, idempotency key hoặc conflict) chứ không mặc nhiên coi duplicate là cùng một insert thành công.

## 7. Batch update là gì?

Thay vì gửi lần lượt 1.000 câu lệnh `INSERT`/`UPDATE` riêng lẻ, JDBC có thể gom nhiều parameter sets thành **một batch** để giảm overhead và round trips:

```text
SQL giống nhau:
INSERT INTO invoice_line (invoice_id, sku, quantity)
VALUES (:invoiceId, :sku, :quantity)

Batch:
  {invoiceId: 10, sku: BOOK, quantity: 2}
  {invoiceId: 10, sku: PEN,  quantity: 1}
  {invoiceId: 10, sku: BAG,  quantity: 1}
```

`NamedParameterJdbcTemplate.batchUpdate(String, SqlParameterSource[])` là một cách rõ ràng, không cần tự quản lý PreparedStatement.

**Không đồng nhất batch với transaction.**

- **Batch:** cách gửi/thi hành nhiều statement hiệu quả hơn.
- **Transaction:** ranh giới **COMMIT/ROLLBACK** để bảo vệ atomicity.
- **Constraint:** quy tắc DB không cho phép trạng thái dữ liệu vi phạm.

Một batch có thể chạy trong auto-commit, có thể một số câu lệnh thành công trước khi phần tử sau lỗi; hành vi phụ thuộc driver/DB và mức transaction. Nếu muốn “tất cả hoặc không gì”, hãy dùng transaction phù hợp và kiểm rollback bằng database thật.

## 8. Spring JDBC batch với named parameters

Ví dụ:

```java
SqlParameterSource[] batch = new SqlParameterSource[] {
    new MapSqlParameterSource()
            .addValue("invoiceId", 10L)
            .addValue("sku", "BOOK")
            .addValue("quantity", 2),
    new MapSqlParameterSource()
            .addValue("invoiceId", 10L)
            .addValue("sku", "PEN")
            .addValue("quantity", 1)
};

int[] counts = named.batchUpdate(
        """
        INSERT INTO invoice_line (invoice_id, sku, quantity)
        VALUES (:invoiceId, :sku, :quantity)
        """,
        batch);
```

Đây là **snippet**; `named` là `NamedParameterJdbcTemplate` đã được inject. Mảng `counts` có một phần tử tương ứng một parameter set trong batch.

Ví dụ H2 bình thường có thể trả `[1, 1]` (mỗi INSERT thêm một dòng). Nhưng JDBC quy định cả **giá trị đặc biệt**:

- `Statement.SUCCESS_NO_INFO` = `-2`: statement thành công nhưng driver không biết số row.
- `Statement.EXECUTE_FAILED` = `-3`: statement thất bại, có thể xuất hiện trong một số kết quả batch xử lý lỗi.
- `0`: statement có thể hợp lệ nhưng không đụng hàng nào, ví dụ `UPDATE ... WHERE id` không tìm thấy.
- Số dương: số row mà driver báo đã tác động.

Khi driver báo lỗi cả batch, API có thể ném `BatchUpdateException` (được Spring chuyển thành một `DataAccessException`), kèm **partial update counts** trong exception gốc tùy driver.

Đừng viết test portable mặc định `assertArrayEquals(new int[]{1,1},counts)` cho **mọi database**. Với H2 cụ thể, đó là kỳ vọng hợp lý; với database khác, nên kiểm cả **trạng thái dữ liệu cuối** và các giá trị driver hỗ trợ.

## 9. Batch update cho UPDATE khác batch INSERT thế nào?

Batch `UPDATE` có thể trả **0** cho một ID không tồn tại:

```java
// Snippet, đặt trong method có NamedParameterJdbcTemplate named.
int[] counts = named.batchUpdate(
        """
        UPDATE invoice
        SET status = :status
        WHERE id = :id
        """,
        new SqlParameterSource[] {
            new MapSqlParameterSource()
                    .addValue("id", 11L)
                    .addValue("status", "PAID"),
            new MapSqlParameterSource()
                    .addValue("id", -1L)
                    .addValue("status", "PAID")
        });
```

Trong database H2 có ID 11 và không có ID -1, bạn có thể nhận `[1,0]`. Một batch “thành công” ở cấp JDBC **không bảo đảm mọi business entity đã tồn tại**. Khi contract yêu cầu mỗi row phải được update, service cần kiểm số lượng và báo conflict/not found với transaction tương ứng.

**Cẩn thận với `SUCCESS_NO_INFO`:** nếu driver không báo row count, không thể kết luận `1 row updated` từ `-2`. Muốn bảo đảm trạng thái của tập ID, có thể kiểm query hậu điều kiện hoặc dùng SQL `RETURNING`/stored procedure phù hợp với DB.

## 10. Batch-generated keys: API có, nhưng phải hiểu driver

Spring Framework 6.2 hỗ trợ overload `NamedParameterJdbcTemplate.batchUpdate(sql, batchArgs, generatedKeyHolder, keyColumnNames)` khi driver hỗ trợ trả keys trong batch.

```java
// Snippet: CHỈ dùng khi driver đã được integration test.
GeneratedKeyHolder holder = new GeneratedKeyHolder();

int[] counts = named.batchUpdate(
        """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (:ref, :amount)
        """,
        parameterSources,
        holder,
        new String[] {"id"});

List<Map<String, Object>> keyRows = holder.getKeyList();
```

`parameterSources` là `SqlParameterSource[]` hợp lệ được tạo trước. Đừng tự mặc định `keyRows.size()==parameterSources.length` và `keyRows[i]` luôn ứng với input `i` nếu chưa có **kiểm thử trên driver/DB/version production**. Một số driver có giới hạn generated keys khi batching, đặc biệt với rewritten batch hoặc multi-row INSERT.

Trong ví dụ runnable, ta **lấy generated key một lần cho parent**, sau đó batch INSERT children có cùng `invoice_id`. Điều này tránh bài toán mapping nhiều generated parent IDs trong batch và làm atomicity dễ kiểm hơn.

## 11. Ràng buộc database là phần của hợp đồng dữ liệu

Bảng cần các ràng buộc:

| Constraint | Đảm bảo | Kịch bản test âm |
|---|---|---|
| `PRIMARY KEY` | Không hai row cùng khóa chính | Insert thủ công trùng ID nếu DDL cho phép |
| `UNIQUE(external_ref)` | Không hai invoice dùng cùng business reference | Ghi lại `external_ref` |
| `NOT NULL` | Field bắt buộc không nhận SQL NULL | INSERT thiếu field bắt buộc hoặc truyền null |
| `CHECK(amount_minor > 0)` | Số tiền phải dương | Amount 0 hoặc âm |
| `CHECK(status IN (...))` | Status thuộc tập hợp hợp lệ | Status `ARCHIVED` khi schema chỉ có NEW/PAID |
| `FOREIGN KEY(invoice_id)` | Line phải trỏ invoice có thật | Line dùng ID không tồn tại |
| `CHECK(quantity > 0)` | Quantity dương | Quantity 0 |
| `UNIQUE(invoice_id,sku)` | Một SKU không lặp trong cùng invoice | Hai line cùng invoice và SKU |

**App-level validation không thay thế constraint.** Hai request đồng thời có thể đều kiểm “reference chưa tồn tại” rồi cùng insert; chỉ UNIQUE ở database mới đảm bảo invariant khi race. Tương tự, service có thể validate quantity nhưng một import job hoặc script SQL khác vẫn cần DB CHECK.

**Constraint không tự thay business logic.** CHECK có thể giữ amount dương nhưng không chứng minh tổng tiền được tính đúng từ các line. Cần domain/service test.

### 11.1. Lưu ý DB dialect

- PostgreSQL, H2, MySQL, SQL Server có khác biệt về CHECK support theo version, exception code, identity/sequence, auto increment, default values và transaction.
- `UNIQUE` trên nullable columns có behavior/phạm vi khác theo DB và thiết kế index; ví dụ đặt `NOT NULL` cho `external_ref` để tránh phụ thuộc semantics NULL.
- Foreign key có thể kiểm ngay hoặc deferred nếu DB hỗ trợ và khai báo như vậy.
- Không coi H2 compatibility mode là bằng chứng toàn bộ migration/chức năng chạy được trên DB production.

## 12. Lỗi constraint chuyển thành exception nào trong Spring?

Spring JDBC dịch `SQLException` của driver sang hệ `DataAccessException`. Một số kiểu thường gặp:

- `DuplicateKeyException`: có thể phát sinh khi trùng UNIQUE/PRIMARY KEY (subclass của `DataIntegrityViolationException`).
- `DataIntegrityViolationException`: lỗi integrity/constraint như CHECK, FK, NOT NULL hoặc duplicate tùy error translation.
- `BadSqlGrammarException`: câu SQL/schema name không hợp lệ.
- `CannotAcquireLockException`/`DeadlockLoserDataAccessException` hoặc các loại concurrency khác tùy dialect và version.

**Không hard-code exception vendor-specific trong business test** nếu bạn muốn test portable; có thể assert `DataIntegrityViolationException` cho constraint case. Nhưng trong test adapter trên DB production, có thể cần kiểm **SQLState/vendor error code** khi contract phải phân biệt duplicate business ref với FK violation để trả HTTP 409/422 phù hợp.

**Lưu ý an toàn:** Không đẩy nguyên error message SQL từ driver vào API response, vì nó có thể chứa tên bảng, field, query hoặc dữ liệu đầu vào. Map sang **public error code** đã định nghĩa, log lỗi chi tiết ở kênh có kiểm soát.

## 13. Transaction và batch: điều gì bảo đảm atomicity?

Spring declarative transaction:

```java
@Service
public class InvoiceRegistrationService {
    private final InvoiceJdbcRepository repository;

    public InvoiceRegistrationService(
            InvoiceJdbcRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long createWithLines(
            String ref,
            long amountMinor,
            List<LineDraft> lines) {
        long id = repository.insertInvoice(ref, amountMinor);
        repository.batchInsertLines(id, lines);
        return id;
    }
}
```

Đây là skeleton; file Java runnable và imports ở mục 17.

Khi method được gọi **qua Spring proxy**, `@Transactional` mở hoặc tham gia transaction theo mặc định `PROPAGATION_REQUIRED`. JDBC operations dùng cùng Spring-managed DataSource/transaction manager, nên nếu batch ném runtime `DataAccessException` và exception thoát ra ngoài boundary, transaction sẽ rollback.

**Những giới hạn cần nhớ:**

1. Spring mặc định rollback với `RuntimeException` và `Error`, **không mặc định rollback với checked Exception**; nếu có checked exception cần `rollbackFor=...` hoặc chiến lược phù hợp.
2. Self-invocation `this.createWithLines(...)` bên trong cùng bean **không đi qua proxy** nên annotation trên method được gọi có thể không hoạt động.
3. Nuốt exception rồi trả success có thể dẫn tới commit không mong muốn nếu transaction chưa bị đánh dấu rollback-only.
4. `@Transactional` không biến các call qua nhiều database hoặc HTTP gateway thành một atomic transaction toàn cục.
5. Generated identity/sequence có thể tiêu thụ một số key dù transaction rollback; **không kiểm contiguous IDs**.
6. Một transaction dài bao nhiều nghìn rows có thể giữ lock và tăng contention; thiết kế batch size và transaction boundary có chủ đích.

## 14. `@JdbcTest` rollback và rollback của service là hai phép kiểm khác nhau

`@JdbcTest` trong Spring Boot 3.5 thường:

- Chỉ dựng JDBC slice, embedded test database, JDBC/SQL init và infrastructure phù hợp.
- Không tự scan mọi `@Service` và `@Repository` ngoài phạm vi; có thể `@Import` repository cần test.
- Chạy test trong **test-managed transaction** và rollback sau mỗi method theo mặc định.

Vì vậy:

```java
@JdbcTest
@Import(InvoiceJdbcRepository.class)
class InvoiceJdbcSliceTest {
    // DataSource + repository thật trên DB test.
}
```

là lựa chọn tốt cho **generated keys, batch counts, DDL constraints**. Nhưng có một cạm bẫy:

> Nếu JUnit method được `@JdbcTest` bọc trong transaction, service được gọi bên trong thường **tham gia transaction test ấy**. Sau method, Spring Test rollback dù service có sai `@Transactional` hay không. Vì vậy “DB trống sau test” **không chứng minh rollback của service**.

Để kiểm **transaction boundary thật của service**, dùng một test `@SpringBootTest` **không gắn `@Transactional` lên JUnit method**, tạo lỗi giữa batch, rồi query DB **sau khi service call ném exception**. Reset fixture bằng `@Sql` trước/sau test để không nhiễm dữ liệu nhau. Code runnable ở mục 20 làm đúng điều này.

**`src/main/java/com/example/invoicejdbc/InvoiceJdbcRepository.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class InvoiceJdbcRepository {

    private final NamedParameterJdbcTemplate named;
    private final JdbcTemplate jdbc;

    public InvoiceJdbcRepository(
            NamedParameterJdbcTemplate named,
            JdbcTemplate jdbc) {
        this.named = named;
        this.jdbc = jdbc;
    }

    public long insertInvoice(
            String externalRef, long amountMinor) {
        String sql = """
                INSERT INTO invoice (external_ref, amount_minor)
                VALUES (:ref, :amount)
                """;

        MapSqlParameterSource parameters =
                new MapSqlParameterSource()
                        .addValue("ref", externalRef)
                        .addValue("amount", amountMinor);

        KeyHolder holder = new GeneratedKeyHolder();

        int count = named.update(
                sql, parameters, holder, new String[] {"id"});

        if (count != 1) {
            throw new IllegalStateException(
                    "Expected one inserted invoice");
        }

        Number key = holder.getKey();
        if (key == null) {
            throw new IllegalStateException(
                    "Generated invoice ID was not returned");
        }
        return key.longValue();
    }

    public int[] batchInsertLines(
            long invoiceId, List<LineDraft> drafts) {

        SqlParameterSource[] args =
                new SqlParameterSource[drafts.size()];

        for (int i = 0; i < drafts.size(); i++) {
            LineDraft line = drafts.get(i);
            args[i] = new MapSqlParameterSource()
                    .addValue("invoiceId", invoiceId)
                    .addValue("sku", line.sku())
                    .addValue("quantity", line.quantity());
        }

        return named.batchUpdate(
                """
                INSERT INTO invoice_line
                    (invoice_id, sku, quantity)
                VALUES (:invoiceId, :sku, :quantity)
                """,
                args);
    }

    public int[] batchMarkPaid(List<Long> ids) {
        SqlParameterSource[] args =
                new SqlParameterSource[ids.size()];

        for (int i = 0; i < ids.size(); i++) {
            args[i] = new MapSqlParameterSource()
                    .addValue("id", ids.get(i))
                    .addValue("status", "PAID");
        }

        return named.batchUpdate(
                """
                UPDATE invoice
                SET status = :status
                WHERE id = :id
                """,
                args);
    }

    public int countInvoices() {
        Integer count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice", Integer.class);
        return count == null ? 0 : count;
    }

    public int countLines() {
        Integer count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line", Integer.class);
        return count == null ? 0 : count;
    }
}
```

**Giải thích mã:**

- Sử dụng **named parameters** thay vì nối chuỗi SQL; các giá trị `ref`, `sku`, `quantity` được bind.
- `new String[]{"id"}` báo driver cần key của cột `id`; `holder.getKey()` kiểm null.
- Batch lines nhận **chính generated invoiceId** từ parent.
- Không đoán ID liên tiếp, không lấy ID từ `MAX(id)`.
- Batch `UPDATE` cho phép quan sát row counts, gồm zero nếu không tìm thấy ID.
- `countInvoices()` và `countLines()` là helper đơn giản cho integration tests; production thường tách query DAO/metrics theo nhu cầu thật.
- Empty list tạo `SqlParameterSource[0]`; ở Spring JDBC 6.2, `NamedParameterJdbcTemplate.batchUpdate` với input rỗng cho mảng đếm rỗng. Trong service production cần quyết định liệu một hóa đơn không có line có hợp lệ hay không; ràng buộc hiện tại **chưa ép số line tối thiểu**.

### 17.1. Bản code không xử lý mọi lỗi sản phẩm

Để giữ bài tập tập trung, repository chưa có validation cho chuỗi SKU rỗng, amount overflow trong domain, duplicate external_ref idempotency, retry deadlock, metrics hay trace. Đó là việc của application service và adapter policy. Database constraint vẫn là tầng chặn cuối cho các invariant đã khai báo.

## 18. Service transaction: parent và children phải cùng commit

**`src/main/java/com/example/invoicejdbc/InvoiceRegistrationService.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class InvoiceRegistrationService {

    private final InvoiceJdbcRepository repository;

    public InvoiceRegistrationService(
            InvoiceJdbcRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long createWithLines(
            String externalRef,
            long amountMinor,
            List<LineDraft> lines) {

        long id = repository.insertInvoice(
                externalRef, amountMinor);
        repository.batchInsertLines(id, lines);
        return id;
    }
}
```

Khi gọi `service.createWithLines(...)` từ bên ngoài bean qua Spring proxy, Spring transaction manager bao cả parent INSERT và child batch INSERT. Nếu constraint của child fail và exception được propagate, cả parent và những child đã insert trước đó sẽ rollback.

Một số **tình huống đáng kiểm thêm ở production**:

- Nếu child list rỗng có được phép không? Schema hiện không cấm hóa đơn không có line; nếu không được, validate trước transaction hoặc có business invariant tương ứng.
- Nếu service gửi event ra Kafka trước commit, JDBC rollback không thu hồi event đã gửi; cần outbox pattern hoặc chiến lược nhất quán.
- Nếu method tự gọi từ chính bean (`this.createWithLines(...)`), proxy `@Transactional` có thể không được áp dụng.
- Khi có nhiều DataSource/transaction managers, phải chọn đúng transaction manager cho repository.
- Duplicate key có thể được dùng để phát triển idempotent create, nhưng không nên mặc định “cứ thấy duplicate là thành công” nếu payload không trùng hợp đồng.

## 19. `@JdbcTest`: generated key, batch counts và constraint thực

**`src/test/java/com/example/invoicejdbc/InvoiceJdbcSliceTest.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.JdbcTest;
import org.springframework.context.annotation.Import;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.JdbcTemplate;

import static org.junit.jupiter.api.Assertions.assertArrayEquals;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

@JdbcTest
@Import(InvoiceJdbcRepository.class)
class InvoiceJdbcSliceTest {

    @Autowired
    InvoiceJdbcRepository repo;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void generatedKeyIdentifiesInsertedParent() {
        long id = repo.insertInvoice("INV-KEY", 10_000L);

        assertTrue(id > 0);
        assertEquals("INV-KEY", jdbc.queryForObject(
                "SELECT external_ref FROM invoice WHERE id = ?",
                String.class, id));
    }

    @Test
    void batchInsertCreatesExpectedLines() {
        long id = repo.insertInvoice("INV-LINES", 50_000L);

        int[] counts = repo.batchInsertLines(
                id,
                List.of(
                        new LineDraft("BOOK", 2),
                        new LineDraft("PEN", 1)));

        // Với H2 của ví dụ, mỗi INSERT ảnh hưởng một row.
        assertArrayEquals(new int[] {1, 1}, counts);

        List<String> skus = jdbc.queryForList(
                """
                SELECT sku FROM invoice_line
                WHERE invoice_id = ?
                ORDER BY id
                """,
                String.class, id);

        assertEquals(List.of("BOOK", "PEN"), skus);
    }

    @Test
    void rejectsDuplicateBusinessReference() {
        repo.insertInvoice("INV-DUP", 100L);

        assertThrows(DataIntegrityViolationException.class,
                () -> repo.insertInvoice("INV-DUP", 200L));
    }

    @Test
    void checkConstraintRejectsNonPositiveAmount() {
        assertThrows(DataIntegrityViolationException.class,
                () -> repo.insertInvoice("INV-ZERO", 0L));
    }

    @Test
    void childConstraintsRejectBadQuantityAndMissingParent() {
        long id = repo.insertInvoice("INV-CHILD", 500L);

        assertThrows(DataIntegrityViolationException.class,
                () -> repo.batchInsertLines(
                        id,
                        List.of(new LineDraft("BOOK", 0))));

        assertThrows(DataIntegrityViolationException.class,
                () -> repo.batchInsertLines(
                        -1L,
                        List.of(new LineDraft("PEN", 1))));
    }

    @Test
    void uniqueLineSkuIsEnforcedPerInvoice() {
        long id = repo.insertInvoice("INV-UNIQUE-LINE", 900L);

        repo.batchInsertLines(
                id, List.of(new LineDraft("BOOK", 1)));

        assertThrows(DataIntegrityViolationException.class,
                () -> repo.batchInsertLines(
                        id, List.of(new LineDraft("BOOK", 2))));
    }

    @Test
    void batchUpdateReportsMatchedAndUnmatchedIds() {
        long a = repo.insertInvoice("INV-A", 100L);
        long b = repo.insertInvoice("INV-B", 200L);

        int[] counts = repo.batchMarkPaid(
                List.of(a, b, -1L));

        // Assertion gắn với H2 trong project mẫu.
        assertArrayEquals(new int[] {1, 1, 0}, counts);

        assertEquals("PAID", jdbc.queryForObject(
                "SELECT status FROM invoice WHERE id = ?",
                String.class, a));
        assertEquals("PAID", jdbc.queryForObject(
                "SELECT status FROM invoice WHERE id = ?",
                String.class, b));
    }
}
```

### 19.1. Bộ test này chứng minh được gì?

- `generatedKeyIdentifiesInsertedParent`: KeyHolder trả key dùng được để query đúng row. Không cần biết ID là `1` hay `157`.
- `batchInsertCreatesExpectedLines`: Hai line được ghi với đúng parent; driver H2 báo hai update counts bằng 1.
- Duplicate `external_ref` bị database thật từ chối.
- `CHECK(amount_minor>0)` được database áp dụng.
- Quantity sai và FK parent không tồn tại đều bị từ chối.
- `UNIQUE(invoice_id,sku)` không cho hai line cùng SKU trong cùng invoice.
- Batch UPDATE áp dụng thay đổi cho hai ID tồn tại và không tác động ID âm không có.

**Có 7 methods `@Test`.** Vì `@JdbcTest` mặc định là test-managed transaction rollback, các test không cần xóa dữ liệu giữa những method này, và **không nên assert identity luôn bắt đầu ở 1**.

### 19.2. Điều test chưa chứng minh

- Rollback của `InvoiceRegistrationService` khi dùng một transaction do **service tự quản**.
- JDBC constraints của PostgreSQL/MySQL production nếu khác H2.
- Interleavings/locking/deadlocks khi nhiều transaction đồng thời.
- Generated key behavior của driver production khi batch nhiều parent cùng lúc.
- Tác dụng phụ qua queue/payment/external service.
- API HTTP 409, GraphQL error hoặc message client; đây là tầng JDBC.

## 20. `@SpringBootTest`: kiểm rollback thật khi batch lỗi giữa chừng

**`src/test/java/com/example/invoicejdbc/InvoiceTransactionIntegrationTest.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.jdbc.Sql;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

@SpringBootTest(classes = InvoiceJdbcApplication.class)
@Sql(scripts = "/cleanup.sql",
        executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
@Sql(scripts = "/cleanup.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD)
class InvoiceTransactionIntegrationTest {

    @Autowired
    InvoiceRegistrationService service;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void createsParentAndAllChildrenInOneTransaction() {
        long id = service.createWithLines(
                "INV-COMPLETE", 60_000L,
                List.of(
                        new LineDraft("BOOK", 2),
                        new LineDraft("PEN", 1)));

        assertTrue(id > 0);
        assertEquals(1, jdbc.queryForObject(

                Integer.class));
        assertEquals(2, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line",
                Integer.class));
    }

    @Test
    void failureInBatchRollsBackParentAndPartialChildren() {
        assertThrows(DataIntegrityViolationException.class,
                () -> service.createWithLines(
                        "INV-ROLLBACK", 60_000L,
                        List.of(
                                new LineDraft("BOOK", 1),
                                new LineDraft("BOOK", 2))));

        // Không gắn @Transactional lên JUnit test method:
        // đọc trạng thái DB sau khi service proxy xử lý lỗi.
        assertEquals(0, jdbc.queryForObject(

                Integer.class));
        assertEquals(0, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line",
                Integer.class));
    }

```

### 20.1. Điểm quan trọng nhất

Class `InvoiceTransactionIntegrationTest` **không dùng `@Transactional` trên test methods**. Nó gọi bean service thật qua Spring container; service có `@Transactional`. Khi batch child thứ hai trùng `(invoice_id,sku)`, database báo constraint error, runtime `DataIntegrityViolationException` thoát khỏi service và transaction manager rollback toàn bộ transaction.

Sau khi exception trở lại JUnit thread, test query DB: **không còn parent, không còn child**. Đây mới là một bài chứng minh thực sự rằng transaction boundary của service hoạt động đối với kịch bản batch failure.

Hai `@Sql` scripts trước/sau đảm bảo fixture sạch giữa hai phương thức và sau test. Identity vẫn có thể tăng qua những lần test rollback/cleanup nên test chỉ kiểm `id>0`.

### 20.2. Vì sao test rollback dùng H2 có giới hạn?

Nó chứng minh Spring transaction + JDBC + H2 hoạt động theo setup demo. PostgreSQL có behavior sau statement error khác H2 (giao dịch có thể ở trạng thái lỗi cho đến rollback); MySQL isolation/engine semantics cũng khác. Trong hệ thống thật cần integration tests trên **đúng database engine/version** để bảo vệ transaction, constraint, locking và migration.

### 20.3. Điều gì xảy ra nếu không có transaction?

Nếu `@Transactional` bị bỏ và JDBC ở auto-commit:

1. Parent `INSERT` có thể commit.
2. Child batch ghi phần tử đầu có thể commit/được chấp nhận.
3. Phần tử thứ hai vi phạm UNIQUE.
4. Dữ liệu có nguy cơ dở dang.

Hành vi partial commit của batch tùy driver/connection/DB; không tự bịa chính xác “một line chắc chắn đã commit” trong mọi database. Test ở mục 20 cố ý xác minh **không có gì còn lại khi service transaction đúng**.

## 21. Batch size, hiệu năng và quản lý tài nguyên

Batch không phải càng lớn càng tốt. Với 100.000 rows, một batch khổng lồ có thể:

- Giữ lock quá lâu và kéo dài transaction.
- Chiếm memory cho parameter arrays, driver buffers hoặc result sets.
- Vượt kích thước packet/statement của database/driver.
- Làm log, retry và xác định input lỗi khó hơn.
- Gây xung đột với những transaction khác.
- Tăng nguy cơ timeout/network disconnect giữa batch.

**Cách tiếp cận thực tế:** thử chunk size như `100`, `500` hoặc `1.000` (chỉ là điểm khởi đầu, không phải thông số tối ưu chung), đo throughput, lock wait, error rate và memory trên workload/driver thật.

Spring JDBC cung cấp overload:

```java
// Snippet có JdbcTemplate jdbc và Collection<Row> rows.
int[][] counts = jdbc.batchUpdate(
        """
        UPDATE invoice
        SET status = ?
        WHERE id = ?
        """,
        rows,
        500,
        (ps, row) -> {
            ps.setString(1, row.status());
            ps.setLong(2, row.id());
        });
```

`Row` ở đây là type minh họa cho `status()`/`id()`, chưa định nghĩa; đây **không phải file runnable độc lập**. Overload này trả `int[][]`, một mảng đếm cho mỗi chunk. Để kiểm toàn bộ kết quả, phải tổng hợp các batch và áp dụng chính sách phù hợp với `SUCCESS_NO_INFO`, `0`, exceptions.

Đừng tách transaction thành hàng trăm commit riêng nếu nghiệp vụ cần all-or-nothing. Ngược lại, không giữ một transaction kéo dài nhiều phút chỉ vì muốn toàn bộ file import hoàn toàn atomic nếu product có thể hỗ trợ resume/checkpoint; hãy thiết kế **idempotent chunks** và quy tắc khôi phục rõ.

## 22. Generated key trong batch và tính đồng thời

Các failure modes quan trọng:

1. **Driver không trả keys trong batch:** số row insert đúng nhưng holder rỗng hoặc thiếu key.
2. **Thứ tự key khác assumption:** mapping input record ↔ generated ID sai.
3. **Identity gaps:** rollback/failed insert vẫn tiêu thụ sequence values.
4. **Concurrent inserts:** hai threads tạo nhiều invoice; ID phát sinh không phản ánh thứ tự request tuyệt đối.
5. **Duplicate external_ref:** client retry có thể nhận unique violation, không nên tự tạo external_ref mới nếu idempotency được yêu cầu.
6. **Transaction isolation:** query sau insert trong cùng transaction thấy row, nhưng transaction khác chưa chắc thấy trước commit.
7. **UUID vs identity:** ứng dụng dùng UUID do client tạo có thể không cần generated key từ DB, nhưng vẫn cần uniqueness/transaction tests.

**Giải pháp kiểm thử:** trên driver production, seed input có reference ổn định, batch insert, đọc lại DB bằng business reference và xác nhận mapping key ↔ row; không chỉ assert `keyList.size()`. Trong code demo, việc insert từng parent để lấy key rồi batch child là lựa chọn dễ review và ít phụ thuộc driver.

## 23. Duplicate key, idempotency và HTTP 409

Một request tạo invoice có `external_ref="ORDER-2026-7"` được client gửi hai lần do retry. Database báo UNIQUE violation ở lần thứ hai.

Bạn cần quyết định business contract:

- **Conflict:** trả `409` với error code ổn định nếu cùng key nhưng payload không khớp hoặc retry không được hỗ trợ.
- **Idempotent replay:** nếu cùng idempotency key và cùng payload, trả kết quả tạo trước đó theo quy định.
- **Upsert:** dùng `INSERT ... ON CONFLICT` hoặc `MERGE` với semantics được review, không dùng bừa để che duplicate.

Không nên chỉ:

```java
try {
    repository.insertInvoice(ref, amount);
} catch (DuplicateKeyException ignored) {
    return 1L; // PHẢN VÍ DỤ: ID tự bịa, mất integrity.
}
```

Đây là snippet **sai có chủ đích**. Nếu idempotency được yêu cầu, phải đọc/kiểm bản ghi cũ bằng key duy nhất, xác nhận payload tương thích, kiểm concurrency và trả đúng ID thật trong transaction phù hợp.

**Vì sao DB UNIQUE không đủ cho idempotency?** Nó ngăn hai row trùng reference, nhưng không xác định client nên được trả kết quả nào, có cần lặp lại side effects hay không, và xử lý request cùng key nhưng nội dung khác ra sao.

## 24. Những bẫy giao dịch thường gặp

### 24.1. Self-invocation bỏ qua proxy

```java
@Service
class ExampleService {

    void outer() {
        createWithLines(); // gọi nội bộ: có thể không qua proxy.
    }

    @Transactional
    public void createWithLines() {
        // JDBC writes
    }
}
```

Đây là snippet minh họa. Nếu không qua proxy, `@Transactional` trên method được gọi có thể không có hiệu lực. Đặt boundary ở public method được bean khác gọi, hoặc cấu trúc lại service.

### 24.2. Swallow exception

```java
@Transactional
public void create() {
    try {
        repository.batchInsertLines(...);
    } catch (DataAccessException error) {
        log.warn("Ignoring DB error"); // PHẢN VÍ DỤ
    }
}
```

Nếu exception không ra khỏi transaction và transaction không được mark rollback-only, kết quả commit có thể trái ý. Đừng dùng ví dụ này như code runnable; nó thiếu repository/context thực. Nếu muốn recover từng row, hãy thiết kế transaction/savepoint/partial-success contract riêng.

### 24.3. Checked exception không mặc định rollback

`@Transactional` mặc định rollback RuntimeException/Error, không mặc định checked exception. Với use case có checked exception cần rollback, có thể thêm `@Transactional(rollbackFor = SomeCheckedException.class)`, hoặc dùng policy khác. Đừng giả định Java Exception nào cũng rollback.

### 24.4. Test-level transaction che mất lỗi

Một test `@JdbcTest` trả DB trống sau method **không** đủ chứng minh service atomic; đó có thể là test rollback. Để bảo vệ service transaction, cần test không bao test method trong transaction rồi assert database state sau lỗi (mục 20).

### 24.5. Mọi side effect không cùng một database

JDBC transaction không tự rollback HTTP request, Kafka event hoặc email đã gửi. Khi vừa ghi DB vừa phát event, dùng outbox/saga hoặc cơ chế nhất quán có chủ đích; bổ sung adapter/end-to-end tests theo rủi ro.

## 25. Đừng chỉ kiểm exception, hãy kiểm hậu điều kiện

Một test yếu:

```java
assertThrows(DataIntegrityViolationException.class,
        () -> service.createWithLines(...));
```

chỉ chứng minh **có exception**, không chứng minh:

- Parent đã rollback.
- Các child được batch trước đó đã rollback.
- Bản ghi có `external_ref` khác vẫn nguyên.
- Không có duplicate event hay side effect ngoài DB.

Test mục 20 mạnh hơn vì kiểm `count(invoice)==0` và `count(invoice_line)==0` **sau exception**. Trong ứng dụng thật còn nên kiểm row unaffected, record version, audit/outbox và isolation theo business invariants. Nếu test có dữ liệu khác trong bảng, đừng assert tổng count = 0; hãy query theo fixture/business key của chính test.

**Trong transaction test, query kiểm hậu điều kiện phải quan sát đúng boundary.** Một select ngay trong transaction test đang chuẩn bị rollback có thể thấy row uncommitted, không chứng minh trạng thái sau rollback. Đó là lý do test rollback thật sử dụng SpringBootTest không gắn test @Transactional.

## 26. SQL fixture, migration và database thật

### 26.1. H2 là test double của database engine

H2 chạy nhanh, phù hợp học SQL cơ bản, generated identity, constraint phổ thông và JDBC API. Nhưng khi production là PostgreSQL/MySQL, khác biệt có thể xuất hiện ở:

- Generated keys và `RETURNING` syntax.
- Constraint behavior và error SQLState.
- Case folding và quoted identifiers.
- Isolation level, locks, deadlocks.
- Index/unique semantics với NULL.
- Datetime/timestamp precision và timezone.
- Batch rewrite/parameter limits.
- Trigger, stored procedure, deferred constraints.
- JSONB, ARRAY, UPSERT syntax, database-specific types.

**Độ tin cậy cao cho database-specific behavior đòi hỏi test trên đúng engine/version**, thường bằng Testcontainers. Không dùng H2 compatibility mode làm bằng chứng đầy đủ cho Postgres-specific syntax/locking.

### 26.2. Giữ migration thật là nguồn chân lý

Nếu project dùng Flyway/Liquibase, nên cho integration test chạy migrations thật thay vì duy trì một `schema.sql` bản sao dễ lệch. Với demo ở đây, `schema.sql` là nguồn DDL vì chưa có migration framework.

Khi thêm constraint mới, test phải kiểm **ràng buộc thật đã có trong schema test**, không chỉ đọc code SQL trong review. Nếu migration production chưa được chạy trên DB test, test có thể xanh giả.

### 26.3. Testcontainers với Spring Boot (mở rộng)

Với PostgreSQL, có thể dùng PostgreSQL Testcontainer và `@ServiceConnection`/`@DynamicPropertySource` theo Spring Boot version và test infrastructure. Cấu hình đó **không nằm trong project H2 runnable của bài này**; cần Docker runtime, image/version, migrations, cleanup và chính sách CI riêng.

Đừng tự dùng một DB production qua test URL hoặc account thông thường. Test phá dữ liệu, constraint và rollback phải chạy trên **database được cấp cho kiểm thử**.

## 27. Test race condition trên UNIQUE và FK

Một test tuần tự trùng `external_ref` chứng minh UNIQUE cơ bản, nhưng không chứng minh đầy đủ correctness khi concurrent inserts. Trong hệ thống nhiều requests:

1. Hai transactions đọc “chưa có external_ref”.
2. Cả hai cùng thử INSERT.
3. Database UNIQUE đảm bảo không thể commit hai row trùng key.
4. Một transaction thành công, transaction còn lại nhận conflict/unique violation (tùy timing/isolation).

Để test concurrency có ý nghĩa:

- Dùng database engine thật với isolation và unique index production.
- Dùng barrier/latch để hai threads cùng bắt đầu sau khi setup.
- Giới hạn timeout để tránh test treo.
- Assert **số row cuối** đúng một và public conflict/idempotency behavior.
- Không assert chắc chắn “thread số 1 thắng” vì scheduler không deterministic.
- Retry khi phù hợp với lock/deadlock/serialization errors, không retry bừa mọi integrity violation.

Một test với `List.of("A","A")` trong cùng batch **không thay thế** concurrency test. Nó là kiểm constraint/transaction khi **cùng một request** đưa dữ liệu trùng.

## 28. Những anti-pattern cần loại bỏ

| Anti-pattern | Hậu quả | Cách đúng |
|---|---|---|
| `SELECT MAX(id)` sau INSERT | Race, lấy key của transaction khác | Generated keys/RETURNING |
| Giả định key luôn bằng 1 | Test fail do identity gaps/parallel tests | Assert key >0 và query row theo key |
| Dùng `batchUpdate` mà không transaction khi cần atomic | Partial writes khi lỗi | Service `@Transactional` + rollback test |
| Giả định mọi `counts[i]==1` mọi driver | Fail/false confidence với `-2` | Driver-specific test + query hậu điều kiện |
| Ghép chuỗi SQL với giá trị client | SQL injection, quote/encoding lỗi | Prepared statements/named params |
| Mock JdbcTemplate rồi bảo constraint đúng | Không chạy DB constraint thật | `@JdbcTest` với DB test |
| Bỏ UNIQUE vì service đã kiểm | Race giữa concurrent requests | DB UNIQUE + business conflict mapping |
| Dùng H2 để khẳng định Postgres-specific locking | Dialect/isolation khác | Testcontainers engine thật |
| Bắt exception rồi trả success | Commit dữ liệu dở dang | Propagate/rollback hoặc explicit recovery |
| Gắn `@Transactional` lên test rồi “chứng minh” service rollback | Test rollback che lỗi service | Full test không có test transaction, assert sau lỗi |
| Cập nhật toàn bộ bảng trong SQL batch | Hậu quả lớn nếu WHERE sai | SQL có WHERE rõ, test matched IDs |
| Duplicate key coi như idempotent không kiểm payload | Trả sai kết quả, che conflict | Unique key + idempotency contract |
| Lấy generated keys của batch rồi zip mù với input | Mapping sai nếu driver không đảm bảo | Integration verify với business ref |
| Lưu password/PII thật trong SQL fixtures | Rò rỉ dữ liệu | Fixtures giả, tối thiểu |
| Cleanup xóa toàn bộ DB dùng chung | Rủi ro mất dữ liệu | DB test riêng, hạn quyền |

## 29. Troubleshooting lỗi JDBC

### 29.1. `KeyHolder.getKey()` là null

Có thể do SQL không phải INSERT có generated key, driver chưa bật return generated keys, tên cột sai hoặc schema không tạo key tự động. Kiểm DDL, `keyColumnNames`, driver metadata, xem `holder.getKeys()`. Không tự thay bằng `MAX(id)`.

### 29.2. `KeyHolder.getKey()` ném lỗi vì nhiều key

Có thể statement trả nhiều cột hoặc nhiều rows. Dùng `getKeys()`/`getKeyList()`; đánh giá mapping chính xác trên driver và SQL thực. Với parent đơn, chỉ định cột `id` giúp giảm mơ hồ.

### 29.3. Batch trả `-2`

Đó có thể là `SUCCESS_NO_INFO`: thành công nhưng không có số row, **không phải đã thất bại**. Kiểm dữ liệu cuối khi business cần chắc chắn số hàng.

### 29.4. Batch ném exception giữa chừng

Kiểm root `SQLException`/SQLState, update counts nếu driver cung cấp, constraint vi phạm và transaction boundary. Trong service transaction đúng, rollback toàn batch/parent, không cố “cứ lỗi thì retry tất cả” nếu external side effect có thể lặp.

### 29.5. `BadSqlGrammarException` trên H2 nhưng production SQL chạy

SQL dialect khác: `RETURNING`, `ON CONFLICT`, identity syntax hoặc reserved word. Test với DB production engine để bảo vệ dialect. Đừng thay schema production cho vừa H2 nếu migration thật không tương thích.

### 29.6. `DataIntegrityViolationException` tại line insert

Kiểm FK parent ID, duplicate `(invoice_id, sku)`, quantity và NOT NULL. Query bản ghi đã ghi (trong transaction test phù hợp), xem SQLState; không log payload nhạy cảm ra CI.

### 29.7. Test pass khi chạy riêng nhưng fail trong suite

Nguyên nhân có thể là shared H2 DB name, `@Sql` cleanup thiếu, context cache, parallel test cùng bảng, identity assumptions hoặc test order. Cô lập database/fixture và tắt shared writes không cần thiết; không giải quyết bằng `@TestMethodOrder` trừ khi thứ tự là yêu cầu thật.

### 29.8. Transaction không rollback như kỳ vọng

Kiểm method có được gọi qua proxy không, `@Transactional` có ở public boundary không, Spring transaction manager nào được dùng, DataSource nào đang cấp connection, exception có bị nuốt không, propagation gì. Đặc biệt, kiểm JUnit test có `@Transactional` riêng khiến kết luận bị nhầm.

## 30. Bài tập tự đánh giá

### Bài A — key sinh tự động

Hai threads insert gần như cùng lúc. Một lập trình viên dùng `SELECT MAX(id)` để tìm ID vừa tạo. Giải thích vì sao sai và sửa bằng KeyHolder. Có được assert ID tăng liên tục không?

**Đáp án:** Không; MAX có thể trả key do transaction khác cấp. Dùng generated key của chính statement. Gaps do rollback/sequence là bình thường.

### Bài B — batch counts

Batch UPDATE ba ID trả `[1, 0, -2]`. Diễn giải. Có được kết luận cả ba rows đã update đúng một lần không?

**Đáp án:** Không. `1` một row affected, `0` không có row affected, `-2` là SUCCESS_NO_INFO; phải có chính sách xử lý unmatched IDs và xác minh hậu điều kiện.

### Bài C — database constraint

Tạo invoice với `amount_minor=0`. Nếu service không validate, DB có từ chối không? Test nào trong ví dụ bảo vệ?

**Đáp án:** `CHECK(amount_minor>0)` từ chối; `checkConstraintRejectsNonPositiveAmount` dùng H2 thật trong `@JdbcTest`.

### Bài D — FK và generated key

Parent có ID do DB sinh, child dùng một ID hard-coded `42`. Test chạy xanh khi H2 tình cờ cấp ID 42. Đây có phải cách đúng không?

**Đáp án:** Không. Đọc KeyHolder, truyền ID thật, rồi assert child `invoice_id` bằng key vừa nhận.

### Bài E — rollback

Service insert parent, batch hai lines cùng SKU, line thứ hai vi phạm UNIQUE. Test `@JdbcTest` cuối cùng rollback khiến DB trống. Có được kết luận service `@Transactional` đúng không?

**Đáp án:** Chưa. Cần test không nằm trong test-managed transaction, gọi service proxy thật và query DB **sau lỗi**. `InvoiceTransactionIntegrationTest` minh họa.

### Bài F — H2 vs PostgreSQL

H2 tests xanh nhưng production dùng `INSERT ... ON CONFLICT RETURNING`. Có nên tin rằng SQL tương thích không? Cần thêm gì?

**Đáp án:** Không. Đó là SQL dialect-specific; bổ sung Testcontainers PostgreSQL với migration, generated keys và transaction tests.

### Bài G — UNIQUE trong concurrency

Hai requests có cùng `external_ref`, cả hai kiểm `SELECT COUNT(*)==0` trước INSERT. Vì sao vẫn cần UNIQUE? Test cuối nên assert gì?

**Đáp án:** Cả hai có thể cùng đọc 0; UNIQUE bảo đảm chỉ một row thành công. Test concurrent assert đúng một row cuối và behavior conflict/idempotency được định nghĩa.

### Bài H — trạng thái batch

Batch trả `[1,1,0]` và service vẫn trả “3 invoices paid”. Đâu là bug? Sửa ở service hoặc assertion thế nào?

**Đáp án:** ID thứ ba không match, nếu contract yêu cầu tất cả phải tồn tại, đó là conflict/not found. Service phải kiểm row counts hoặc trạng thái DB, rồi rollback/báo lỗi phù hợp; chú ý driver có thể trả SUCCESS_NO_INFO.

### Bài I — side effects ngoài DB

Trong transaction tạo invoice, service gửi email trước COMMIT; batch child thất bại và DB rollback. Email có bị thu hồi không?

**Đáp án:** Không. JDBC transaction không rollback email. Dùng outbox/after-commit/cơ chế workflow idempotent và test failure modes.

## 31. Checklist cuối bài

- [ ] Tôi phân biệt generated key thật với business reference và không dùng `MAX(id)+1`.
- [ ] Statement INSERT dùng KeyHolder hoặc RETURNING theo driver.
- [ ] Không giả định ID bắt đầu từ 1, liên tục hoặc tương đương commit order.
- [ ] KeyHolder có thể không trả key hoặc trả nhiều keys; có xử lý rõ.
- [ ] Batch sử dụng prepared/bound parameters, không nối input trực tiếp vào SQL.
- [ ] Tôi biết `int[]` counts có thể chứa `0`, `-2`, `-3` hoặc gây exception.
- [ ] Mỗi batch có quy tắc cho unmatched UPDATE IDs.
- [ ] Nếu nghiệp vụ yêu cầu all-or-nothing, có `@Transactional` đúng service boundary.
- [ ] Tests thực sự xác minh rollback sau lỗi, không bị `@JdbcTest` rollback che mất.
- [ ] DDL có PRIMARY KEY, UNIQUE, NOT NULL, CHECK, FOREIGN KEY theo invariant.
- [ ] Tests kiểm constraints trên database thật, không chỉ mock JDBC interactions.
- [ ] `external_ref` có chính sách duplicate/idempotency rõ.
- [ ] Không để constraint error message của DB lộ ra HTTP API.
- [ ] Test data cô lập, cleanup không chạy lên DB dùng chung.
- [ ] SQL schema test khớp migration thực; khác DB engine được test đúng.
- [ ] Batch size/transaction size được lựa chọn theo workload, không đoán.
- [ ] Concurrency, locking/deadlock được kiểm thêm nếu rủi ro cao.
- [ ] Generated keys của batch nhiều rows đã được xác minh driver-specific trước khi mapping.
- [ ] Không gửi event/email ngoài DB rồi giả định JDBC rollback sẽ hoàn tác.
- [ ] Tests giữ đúng ranh giới: JDBC slice cho repository/constraint, full context cho transaction thật, adapter/HTTP test khi cần.

**Kết luận:** Generated key trả về ID do database cấp cho đúng lệnh INSERT, batch update giúp giảm overhead khi ghi nhiều rows, còn database constraints là hàng rào integrity không thể thay bằng service validation đơn lẻ. Ba phần chỉ thật sự kết hợp an toàn khi có **transaction boundary đúng**, xử lý **row counts và exceptions** có ý nghĩa, đồng thời dùng tests **chạy database thật ở cấp cần thiết**. `@JdbcTest` rất phù hợp để kiểm KeyHolder/batch/constraint, nhưng để chứng minh rollback service phải tránh để transaction của JUnit che kết quả. Với production SQL dialect và concurrency, hãy nâng bài kiểm lên đúng database engine trước khi tin rằng một H2 test xanh đã chứng minh tất cả.
