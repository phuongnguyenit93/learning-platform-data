# Mocking void, final, or static Methods Based on Version Capabilities

## 1. Goal and Nature of the Problem

In Java/Spring Boot unit tests, Mockito often replaces a dependency with a **mock** to control responses and verify interactions. `void`, `final`, and `static` methods require different handling:

- **`void`:** has no return value, so `when(mock.method()).thenReturn(...)` cannot be used. You can verify whether it was called with `verify(...)`, or configure behavior with the `doNothing()`, `doThrow(...)`, `doAnswer(...)`, and `doCallRealMethod()` family.
- **`final`:** methods/classes restrict inheritance or overriding. Mocking capability depends on the **mock maker** and Mockito version. On standard JVMs, Mockito 5 uses the inline mock maker by default and supports many `final` cases.
- **`static`:** methods belong to the class rather than a mock instance. Mockito since **3.4.0** provides `mockStatic(...)` when using the inline mock maker. It returns a `MockedStatic<T>` whose scope must be closed, typically using `try-with-resources`.

**Core point:** before applying a code snippet, know which Mockito version is running, which mock maker is active, the JVM, and the test runner. “Mockito has this API” does not guarantee a particular environment permits it. Likewise, mocks exist to test the **unit under test**, not to erase every piece of real behavior that needs proving.

### 1.1. When to Mock vs. When to Call Real Code?

Consider a service sending order notifications via an external gateway:

- The rule deciding whether to send is **logic to test for real**.
- The email/HTTP/queue port producing side effects is a **good boundary to mock**.
- An identifier generated by a static utility might need control in a special unit test, yet could be redesigned into an interface/instance method if it is an important dependency or reused across many tests.

Even when `void`, `final`, and `static` can be mocked, mocking alone does not make a test valid. Ensure the test still verifies outcomes or critical interactions, avoiding overly specific setup where the test merely “replays” stubs.

## 2. Version Matrix and Limitations to Remember

| Capability | Key version milestones | Conditions / limitations |
|---|---|---|
| Mock interfaces, regular classes; `verify` | Available since early Mockito generations | Requires compatible Mockito dependency and test runtime |
| Stub `void` with `doThrow/doNothing/doAnswer` | Long-standing Mockito API | Cannot use `when(voidCall).thenReturn(...)` because `void` calls produce no value |
| Mock `final` classes/methods | Supported via inline mock maker in Mockito 2.x–4.x; **default in Mockito 5.x** | Pre-5 Mockito requires enabling inline appropriately; some configurations/methods still have limits |
| Mock `static` methods | `mockStatic` since **Mockito 3.4.0** | Requires inline mock maker, `MockedStatic` scope, and compatible instrumentation environment |
| Mockito 5.x | Inline mock maker default on JVM; requires **Java 11+** for Mockito itself | Java 17+ fits the baseline, though JVM/agent environment and dependencies must still be compatible |
| Java 21+ and JVM agent attachment restrictions | Inline instrumentation may warn or fail to attach depending on runtime | Follow official `-javaagent` guidance when needed rather than ignoring warnings |

**Do not infer from dependency name alone.** Even with `mockito-core`, one project might use Mockito 4 with the subclass mock maker while another uses Mockito 5 inline. If a project includes `mockito-extensions/org.mockito.plugins.MockMaker` selecting `mock-maker-subclass`, `final` and `static` still cannot be mocked even on Mockito 5.x.

In Mockito 3.x/4.x, the inline mechanism can be enabled via extension config on the test classpath:

**File `src/test/resources/mockito-extensions/org.mockito.plugins.MockMaker` (single line):**

```text
mock-maker-inline
```

In older releases, the `mockito-inline` artifact also provided preconfigured inline support. **Do not manually add an old `mockito-inline` artifact to Mockito 5**, as Mockito 5 already uses inline by default and that artifact is unnecessary for modern projects. Use a consistently managed Mockito dependency set, avoiding mismatched versions across `mockito-core`, `mockito-junit-jupiter`, Byte Buddy, and the framework.

### 2.1. Limitations That Remain Even with the Inline Mock Maker

- Inline mocking relies on instrumentation/Byte Buddy and a compatible JVM; on newer JDKs or agent-restricted runtimes, initializing the mock maker can fail.
- By default, it cannot mock **native methods**, certain methods in `java.*`, classes/methods tied to JVM intrinsics, or objects with special classloaders.
- `mockStatic` **mocks static method calls**, not turning `static final` fields into values stubbed via `when(...)`. Compile-time constants may already be inlined by the Java compiler.
- Mocking `private` methods or `new` constructors is not the same as mocking `final` or `static`. Mockito has separate APIs for construction mocking in supported versions, though they should not be default choices for every test.
- Avoid broadly mocking core APIs like `System` or `Thread`. Mockito enforces safeguards to protect runtime execution; wrappers or injection are usually better solutions.

**Decision principle:** if you find yourself mocking static calls constantly to test main flows, consider extracting the dependency into an object passed via constructor. Static mocking fits best for legacy APIs or integration points that are hard to change immediately.

## 4. Fundamentals of Mockito Stubbing and Verification

Before covering the three method kinds, distinguish two questions:

- **Stubbing — “if the dependency is called, what will it do?”** Use `when(...).thenReturn(...)` for value-returning methods; use the `do...` family for `void` methods or when avoiding real method execution on a spy.
- **Verification — “was the dependency called properly?”** Use `verify(mock).method(...)`, `verify(mock, times(n))`, `never()`, `verifyNoInteractions(...)`, `ArgumentCaptor`… Verification does not replace assertions on output data or business state.

Example on a value-returning mock:

```java
when(policy.accepts("buyer@example.org")).thenReturn(true);
org.junit.jupiter.api.Assertions.assertTrue(policy.accepts("buyer@example.org"));
verify(policy).accepts("buyer@example.org");
```

This is an **illustrative snippet** in a test that already has a suitable `policy` mock. For `void` methods, `when(channel.send(...))` cannot compile because the call has type `void`.

### 4.1. Matchers and Specific Arguments

Mockito uses matchers like `anyString()`, `eq("...")`, and `argThat(...)` to select calls to stub or verify. Once you use a matcher for one argument in a call, you must normally use matchers for **all** arguments in that call:

**Right:**

```java
doThrow(new IllegalStateException("offline"))
        .when(channel)
        .send(eq("buyer@example.org"), anyString());
```

**Invalid matcher combination:**

```java
doThrow(new IllegalStateException("offline"))
        .when(channel)
        .send("buyer@example.org", anyString());
```

In the invalid snippet, the first argument is a literal and the second is a matcher; Mockito typically throws `InvalidUseOfMatchersException`. Fix it with `eq("buyer@example.org")` or use literals for both arguments as appropriate.

A broad matcher like `anyString()` accepts any matching non-null `String` and does not verify specific payloads when payload content is part of the contract. When outcomes depend on arguments, stub exact conditions so you do not match the wrong call.

## 5. Mocking `void` Methods

### 5.1. Default on a Mock: Does Nothing, Yet Can Still Be Verified

On a plain Mockito mock with normal default answers, calling an unstubbed `void` method **executes no real side effect**. Example:

```java
Channel channel = mock(Channel.class);
channel.send("buyer@example.org", "hello");
verify(channel).send("buyer@example.org", "hello");
```

This is an **illustrative snippet**, assuming a `Channel` interface with `void send(String, String)`. `verify` confirms the invocation; no real email or message is sent by that mock. There is no need to write `doNothing()` before every `void` call just to repeat default behavior.

### 5.2. `doNothing()`: Useful on Spies or When Chaining Behaviors

```java
doNothing().when(channel).send(anyString(), anyString());
```

This is genuinely helpful only when:

1. You are using a **spy** on a real object and want to suppress a specific side effect in the test.
2. You want to configure consecutive calls differently, e.g., succeed first then throw: `doNothing().doThrow(error).when(channel).send(...)`.

If `channel` is an unstubbed plain mock, that line barely strengthens the test. Prefer exact verifications or checking business outcomes.

### 5.3. `doThrow(...)`: Simulating a Failing Side Effect

```java
doThrow(new IllegalStateException("gateway offline"))
        .when(channel)
        .send(eq("buyer@example.org"), anyString());
```

When the dependency is called with matching arguments, Mockito throws the configured exception. This lets you test how the service **propagates, handles, or retries errors** per contract. Distinctions:

- `doThrow(new IOException(...))` with a checked exception is valid only when the method signature permits that checked exception; otherwise Mockito reports an invalid exception configuration.
- `doThrow(IllegalStateException.class)` lets Mockito instantiate the exception internally; if you need to check a specific **message or instance identity**, pass a constructed instance as shown.
- For a `void` method, you cannot write `when(channel.send(...)).thenThrow(...)` because `send(...)` returns no value.

### 5.4. `doAnswer(...)`: Observing Arguments or Simulating Conditional Behavior

```java
List<String> sent = new ArrayList<>();

doAnswer(invocation -> {
    String to = invocation.getArgument(0, String.class);
    String body = invocation.getArgument(1, String.class);
    sent.add(to + ": " + body);
    return null;
}).when(channel).send(anyString(), anyString());
```

**Note:** this is a snippet in a test importing Java Collections and Mockito; an `Answer` for a `void` method normally returns `null`. There is no fake “void value” in Java to return. `doAnswer` helps when responses depend on parameters or to build an in-memory fake, though you should not write complex `Answer` lambdas where `verify`/`ArgumentCaptor` suffices.

### 5.5. `doCallRealMethod()` and Real Side-Effect Risks

`doCallRealMethod().when(spy).someVoidMethod()` specifies running the real method. On a spy, that is already the default; use it when needed in a stub chain. On a **mock of a class**, calling a real method can run on an object whose constructor never initialized its fields, causing NPEs or unpredictable side effects. Prefer a **real instance** for the logic under test or a properly constructed spy.

**Do not overuse spies:** spies run real methods by default unless stubbed. If a method sends email, writes to DB, deletes files, or publishes events, a stubbing oversight can trigger real behavior during tests.

## 6. Complete Java 17+ Example — Production Code

The example below demonstrates all three groups—`void`, `final`, `static`—with a simple service. We do not start a Spring `ApplicationContext` because the focus is Mockito behavior.

Create **`src/main/java/com/example/testing/mockito/ShipmentService.java`**:

```java
package com.example.testing.mockito;

import java.util.Objects;

public final class ShipmentService {

    public interface Channel {
        void send(String destination, String payload);
    }

    public static final class AddressPolicy {
        // final class and final method to test Mockito inline.
        public final boolean accepts(String address) {
            return address != null && address.contains("@");
        }
    }

    public static final class TraceIds {
        private TraceIds() {}

        public static String forOrder(String orderId) {
            return "trace-" + orderId;
        }
    }

    private final Channel channel;
    private final AddressPolicy policy;

    public ShipmentService(Channel channel, AddressPolicy policy) {
        this.channel = Objects.requireNonNull(channel, "channel");
        this.policy = Objects.requireNonNull(policy, "policy");
    }

    public void dispatch(String orderId, String destination) {
        if (orderId == null || orderId.isBlank()) {
            throw new IllegalArgumentException(
                    "orderId must not be blank");
        }
        if (!policy.accepts(destination)) {
            throw new IllegalArgumentException(
                    "destination rejected");
        }

        String payload = "order=" + orderId
                + ";trace=" + TraceIds.forOrder(orderId);
        channel.send(destination, payload);
    }
}
```

Roles:

- `Channel.send(...)` returns `void`, representing a dependency with side effects; can be mocked without sending anything real.
- `AddressPolicy` is a **final class** and `accepts` is a **final method**; Mockito 5 inline can mock it to force the rejection branch. Checking `@` is only a simple illustrative rule, **not a production email validator**.
- `TraceIds.forOrder(...)` is a **static method**; we intercept it within one test scope and then restore real behavior.
- `ShipmentService.dispatch(...)` is the behavior under test. Keeping both conditional checks and dependency calls lets us contrast **asserting exceptions** with **verifying interactions**.

## 7. Complete Java 17+ Example — JUnit Jupiter + Mockito

Create **`src/test/java/com/example/testing/mockito/ShipmentServiceTest.java`**:

```java
package com.example.testing.mockito;

import java.util.ArrayList;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.mockito.ArgumentCaptor;
import org.mockito.MockedStatic;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.anyString;
import static org.mockito.ArgumentMatchers.eq;
import static org.mockito.Mockito.doAnswer;
import static org.mockito.Mockito.doNothing;
import static org.mockito.Mockito.doThrow;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.mockStatic;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.spy;
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.verifyNoMoreInteractions;
import static org.mockito.Mockito.when;

class ShipmentServiceTest {

    private static final String ADDRESS = "buyer@example.org";

    private ShipmentService.Channel newChannel() {
        return mock(ShipmentService.Channel.class);
    }

    private ShipmentService newService(
            ShipmentService.Channel channel) {
        return new ShipmentService(
                channel, new ShipmentService.AddressPolicy());
    }

    @Test
    void verifiesVoidInvocationWithExactArguments() {
        var channel = newChannel();
        var service = newService(channel);

        service.dispatch("R-01", ADDRESS);

        verify(channel).send(
                ADDRESS, "order=R-01;trace=trace-R-01");
        verifyNoMoreInteractions(channel);
    }

    @Test
    void canExplicitlyStubVoidToDoNothing() {
        var channel = newChannel();
        var service = newService(channel);

        doNothing().when(channel)
                .send(eq(ADDRESS), anyString());

        service.dispatch("R-02", ADDRESS);

        verify(channel).send(
                ADDRESS, "order=R-02;trace=trace-R-02");
    }

    @Test
    void doThrowSimulatesFailureOfVoidDependency() {
        var channel = newChannel();
        var service = newService(channel);

        doThrow(new IllegalStateException("gateway offline"))
                .when(channel)
                .send(eq(ADDRESS), anyString());

        assertThatThrownBy(
                () -> service.dispatch("R-03", ADDRESS))
                .isInstanceOf(IllegalStateException.class)
                .hasMessage("gateway offline");

        verify(channel).send(
                ADDRESS, "order=R-03;trace=trace-R-03");
    }

    @Test
    void voidCanHaveDifferentBehaviorsAcrossCalls() {
        var channel = newChannel();
        var service = newService(channel);

        doNothing()
                .doThrow(new IllegalStateException(
                        "second attempt blocked"))
                .when(channel)
                .send(anyString(), anyString());

        service.dispatch("R-04", ADDRESS);

        assertThatThrownBy(
                () -> service.dispatch("R-04", ADDRESS))
                .isInstanceOf(IllegalStateException.class)
                .hasMessage("second attempt blocked");

        verify(channel, times(2)).send(
                ADDRESS, "order=R-04;trace=trace-R-04");
    }

    @Test
    void doAnswerCanRecordVoidArguments() {
        var channel = newChannel();
        var service = newService(channel);
        List<String> events = new ArrayList<>();

        doAnswer(invocation -> {
            String destination =
                    invocation.getArgument(0, String.class);
            String payload =
                    invocation.getArgument(1, String.class);
            events.add(destination + " <- " + payload);
            return null;
        }).when(channel).send(anyString(), anyString());

        service.dispatch("R-05", ADDRESS);

        assertThat(events).containsExactly(
                "buyer@example.org <- order=R-05;trace=trace-R-05");
    }

    @Test
    void canStubFinalClassAndFinalMethodWithInlineMockMaker() {
        var channel = newChannel();
        var policy = mock(ShipmentService.AddressPolicy.class);
        when(policy.accepts(ADDRESS)).thenReturn(false);
        var service = new ShipmentService(channel, policy);

        assertThatThrownBy(
                () -> service.dispatch("R-06", ADDRESS))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessage("destination rejected");

        verify(policy).accepts(ADDRESS);
        verifyNoInteractions(channel);
    }

    @Test
    void staticMockIsRestrictedToTryWithResourcesScope() {
        var channel = newChannel();
        var service = newService(channel);

        assertThat(ShipmentService.TraceIds.forOrder("R-07"))
                .isEqualTo("trace-R-07");

        try (MockedStatic<ShipmentService.TraceIds> traces =
                     mockStatic(ShipmentService.TraceIds.class)) {

            traces.when(() ->
                    ShipmentService.TraceIds.forOrder("R-07"))
                    .thenReturn("fixed-07");

            service.dispatch("R-07", ADDRESS);

            verify(channel).send(
                    ADDRESS, "order=R-07;trace=fixed-07");
            traces.verify(() ->
                    ShipmentService.TraceIds.forOrder("R-07"));
        }

        assertThat(ShipmentService.TraceIds.forOrder("R-07"))
                .isEqualTo("trace-R-07");
    }

    @Test
    void invalidDestinationNeverCallsVoidDependency() {
        var channel = newChannel();
        var service = newService(channel);

        assertThatThrownBy(
                () -> service.dispatch("R-08", "invalid"))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessage("destination rejected");

        verifyNoInteractions(channel);
    }

    @Test
    void capturesVoidPayloadForFurtherAssertions() {
        var channel = newChannel();
        var service = newService(channel);
        ArgumentCaptor<String> payload =
                ArgumentCaptor.forClass(String.class);

        service.dispatch("R-09", ADDRESS);

        verify(channel).send(eq(ADDRESS), payload.capture());
        assertThat(payload.getValue())
                .startsWith("order=R-09;")
                .contains("trace-R-09");
    }

    @Test
    void doNothingOnSpyPreventsRealVoidSideEffect() {
        var counter = spy(new SideEffectCounter());

        doNothing().when(counter).increment();
        counter.increment();

        assertThat(counter.count()).isZero();
        verify(counter).increment();
    }

    static class SideEffectCounter {
        private int calls;

        void increment() {
            calls++;
        }

        int count() {
            return calls;
        }
    }
}
```

This code contains **10 test methods**. Each test creates its own mocks, keeps static mocks strictly inside `try-with-resources`, and requires no Spring context. Place both files with matching names/packages using Java 17+ and Mockito 5.x with the inline mock maker on a compatible JVM; all **10 tests are expected to pass**. The application prints no explicit stdout; exact test count/status log formatting depends on JUnit/Gradle/Maven.

```

```

In a multi-module project, target the module task/goal containing the test class. ### 7.1. Why Is Each Test Trustworthy?

- `verifiesVoidInvocationWithExactArguments`: skips stubbing `void` because mocks do nothing by default. `verify` checks exact destination and payload.
- `canExplicitlyStubVoidToDoNothing`: demonstrates the syntax while explicitly noting `doNothing` on a plain mock is usually redundant.
- `doThrowSimulatesFailureOfVoidDependency`: tests the service branch through the dependency when transport fails, including exception type/message and verifying the call.
- `voidCanHaveDifferentBehaviorsAcrossCalls`: succeeds first, fails second; `times(2)` verifies exactly two calls occurred.
- `doAnswerCanRecordVoidArguments`: simulates an in-memory side effect, letting us assert the passed payload.
- `canStubFinalClassAndFinalMethodWithInlineMockMaker`: proves Mockito can mock a `final` class containing a `final` method when inline is supported.
- `staticMockIsRestrictedToTryWithResourcesScope`: inside the scope, static returns a fixed value; outside the scope, the real method returns its original value again.
- `invalidDestinationNeverCallsVoidDependency`: verifies **zero side effects** when the service rejects input.
- `capturesVoidPayloadForFurtherAssertions`: extracts the argument from the invocation instead of forcing a full-string match when only parts of the payload are contractually fixed.
- `doNothingOnSpyPreventsRealVoidSideEffect`: creates a spy from a real object while disabling `increment`, keeping `count()` at 0.

## 8. Mocking `final`: Right Version and Right Target

### 8.1. Why Was `final` Hard to Mock Before?

A **subclass** mock maker creates a generated subclass to override methods. Java forbids subclassing a `final class` and overriding a `final method`. Therefore, under that mechanism, `mock(FinalType.class)` or stubbing `finalMethod()` could be rejected or fail to intercept.

The **inline mock maker** transforms class bytecode via instrumentation rather than subclassing alone, enabling it to alter behavior of many `final` methods and classes. Mockito 5 enables inline by default on standard JVMs; Mockito 2.x–4.x usually require opting in. This is a change in the **mock maker mechanism**, not a feature specific to JUnit or Spring Boot.

### 8.2. Final Class + Final Method Example

From `ShipmentService.AddressPolicy` in Section 6:

```java
var policy = mock(ShipmentService.AddressPolicy.class);
when(policy.accepts("buyer@example.org")).thenReturn(false);

assertThat(policy.accepts("buyer@example.org")).isFalse();
verify(policy).accepts("buyer@example.org");
```

This excerpt runs inside a test with matching imports. `accepts` is `final`, yet Mockito 5 inline supports stubbing it. With a subclass mock maker, creating the mock may fail or the final method will not be intercepted as expected.

### 8.3. Cases Where You Should Not Mock `final`

- **Records/value objects without side effects:** simply instantiate them for real instead of mocking. Mocking data objects easily yields tests that only verify your own setup.
- **Pure algorithm classes:** run them for real so tests verify actual logic rather than mocking the very answer you should prove.
- **Final beans or classes hard to test due to dependency design:** when you own the design, introducing an interface/adapter yields cleaner tests than mocking `final` classes directly.
- **Final methods calling external dependencies:** if a class comes from an unmodifiable library, inline mocking can be pragmatic—keep mocking scoped strictly to where needed.

Distinguish `final` on a **reference variable** from `final class/method`. `final SomeService service` only prevents variable reassignment; it does not determine whether Mockito can mock `SomeService`.

## 9. Mocking `static`: Scope, Threads, and Controlling Impact

### 9.1. Standard Syntax

```java
try (MockedStatic<ShipmentService.TraceIds> traces =
             mockStatic(ShipmentService.TraceIds.class)) {

    traces.when(() ->
            ShipmentService.TraceIds.forOrder("R-07"))
            .thenReturn("fixed-07");

    assertThat(ShipmentService.TraceIds.forOrder("R-07"))
            .isEqualTo("fixed-07");

    traces.verify(() ->
            ShipmentService.TraceIds.forOrder("R-07"));
}
```

**`MockedStatic<T>` is a scoped controller, not an ordinary mock instance.**

- `mockStatic(MyUtility.class)` enables intercepting static methods of that class for the calling thread.
- `traces.when(() -> MyUtility.staticMethod(...))` configures behavior within the scope.
- `traces.verify(() -> MyUtility.staticMethod(...))` verifies matching static calls within the scope.
- When leaving `try-with-resources`, `close()` runs even if an assertion fails, preventing static mock leaks into subsequent tests.

To prove tests do not leak mocks, the illustrative test compares real method behavior **before and after** the scope—stronger evidence than only seeing assertions pass inside the scope.

### 9.2. Thread-Local Does Not Mean Active on Every Thread

Mockito's `MockedStatic` is scoped to the **thread that created the static mock**. If production code offloads work to `CompletableFuture.supplyAsync(...)`, an `ExecutorService`, or another thread, static calls on the new thread may **not be intercepted** by the test thread's mock.

Therefore:

- Do not rely on a single static mock to control every call in an asynchronous flow unless you can guarantee they execute on the same thread.
- Do not share a `MockedStatic` object across multiple threads; the API documentation states this is not safe.
- Prefer injecting an instance dependency for scheduler/async logic that needs dedicated testing.
- Always close the static scope with `try-with-resources`; never leave it open across multiple test methods.

**Anti-pattern example:** opening a static mock in `@BeforeAll` and leaving it open until the entire suite finishes. Other tests can unexpectedly receive mocked responses, especially when the same thread executes multiple tests. Keep scopes as tight as needed.

### 9.3. Unstubbed Methods While a Static Mock Is Active

A static mock created with default answers **does not automatically forward other static calls to the real methods**. Unstubbed calls return default values (e.g., `null` for references, 0 for numbers, false for booleans) by type. Thus **mocking an entire static class** risks causing unrelated methods in that class to return fake defaults unexpectedly.

If you need certain methods to run for real, Mockito supports default answers like `CALLS_REAL_METHODS` in supported versions. However, that can execute real logic (even during stubbing), so inspect side effects and use it only intentionally. Keeping the static mock narrow or extracting an injectable dependency is usually safer.

### 9.4. Static Mocks and Overloads / Argument Matchers

Inside `traces.when(() -> TraceIds.forOrder("R-07"))`, the method call is recorded for stubbing. For overloads and matchers, make sure you select the right signature and arguments. If code calls `forOrder("R-08")` while you only stubbed `"R-07"`, the stub misses and default values can trigger confusing errors downstream.

Do not script complex sequences like “first static call returns A, second returns B” without knowing how many times production calls it and on which thread. For static time or randomness utilities, **`Clock`**, suppliers, or interface injection are usually cleaner than mocking `Instant.now()`/`UUID.randomUUID()`.

## 10. Spies and `doCallRealMethod()`: Understanding Real Execution

### 10.1. How Mock and Spy Differ

- **Mock:** does not run real methods by default (unless specially configured); unstubbed methods return default values.
- **Spy:** wraps a real initialized object; unstubbed methods call real logic by default. This makes spies handy for partial checks while risking unintended side effects.

`SideEffectCounter` example from the complete test:

```java
var counter = spy(new SideEffectCounter());
doNothing().when(counter).increment();

counter.increment();
assertThat(counter.count()).isZero();
```

Without `doNothing`, `increment()` would increment the counter because it is a spy. This demonstrates isolating **one void method** from its side effect while keeping other methods real.

### 10.2. Why Use the `do...` Family When Stubbing Spies?

For a **value-returning** method, `when(spy.read()).thenReturn(value)` must **evaluate `spy.read()` first** to pass its result to `when`, executing the real method during stubbing. To avoid real execution, use `doReturn(value).when(spy).read()` where appropriate.

For `void`, stubbing must also use the `do...` family because `when(spy.voidMethod())` is invalid Java syntax. Be careful with `doCallRealMethod()` as it lets real side effects run on subsequent calls; never use it just to make a test look “more complete.”

### 10.3. Spying on Spring Beans

In Spring versions supporting `@MockitoSpyBean`, that annotation wraps a Spring bean with a spy inside the test context; older versions use `@SpyBean`. This is **Spring bean management**, distinct from `spy(new SomeClass())` creating a local object. Because spies can call real methods, consider transactions, caches, AOP proxies, and external side effects carefully. Do not add a spy to the Spring context merely to test a pure Java condition.

## 11. Strong, Sufficient, and Meaningful Verification

### 11.1. `verify(...)` with `void`

Most common patterns for testing “did the service call the gateway?”:

```java
verify(channel).send("buyer@example.org", "payload");
verify(channel, times(2)).send(anyString(), anyString());
verify(channel, never()).send(eq("blocked@example.org"), anyString());
verifyNoInteractions(channel);
```

**These lines are independent options**, not four assertions to apply together on a single already-called mock. `verifyNoInteractions(channel)` passes only if the mock received zero interactions; `never()` confirms no call matched that condition without guaranteeing no other calls occurred.

Verify interactions when the interaction itself is a **business contract** (e.g., do not notify a rejected user, log once, send the exact payload). Avoid putting `verifyNoMoreInteractions` on every mock if it makes tests overly sensitive to harmless auxiliary calls.

### 11.2. `ArgumentCaptor` When Payloads Matter

```java
ArgumentCaptor<String> payload =
        ArgumentCaptor.forClass(String.class);

verify(channel).send(eq("buyer@example.org"), payload.capture());
assertThat(payload.getValue()).contains("trace-R-09");
```

This snippet belongs inside a test after `channel.send(...)` was invoked. Captors help when asserting **properties of arguments**, especially DTOs or large messages. Do not misuse captors for stubbing when a simple matcher suffices: `ArgumentCaptor` shines during **verification**.

### 11.3. When Ordering Must Be Verified

If business rules require recording an audit event **before** calling the gateway, use `InOrder` across the relevant mocks. Do not constrain call order when operations may run asynchronously, when order is not part of the contract, or when calls do not affect each other. Over-verifying implementation details makes tests hard to maintain even when business outcomes stay right.

## 12. Common Errors by Symptom

| Symptom | Possible cause | Fix |
|---|---|---|
| Java does not compile at `when(channel.send(...))` | `send` returns `void` | Use `doThrow/doAnswer/doNothing` or just `verify` |
| `Cannot mock/spy class ... final class` | Subclass mock maker or version without inline support | Check Mockito version and mock maker; upgrade/enable inline properly |
| `mockStatic(...)` not found | Mockito too old (pre-3.4) or wrong import/dependency | Check version, classpath, and version-specific API |
| `mockStatic(...)` reports unsupported by mock maker | Using `SUBCLASS`/proxy maker instead of inline | Use inline on a compatible JVM; remove conflicting mock maker config |
| `MockitoInitializationException`/Byte Buddy agent error | Restricted instrumentation/JVM/agent | Check root cause, JDK/test runner; configure `-javaagent` per Mockito docs |
| Static test passes alone, fails in suite | Unclosed scope, thread reuse, static dependency unexpectedly mocked | Use `try-with-resources` per test and minimize static mocking |
| Static stub does not affect async code | Execution moved to a different thread | Use injection/adapters or structure tests around the actual thread |
| Spy sends real email/writes file during setup | Real method ran during stubbing or unstubbed call | Use `do...`, reduce spies, mock boundary dependencies |
| `InvalidUseOfMatchersException` | Mixed literals and matchers or misplaced matcher | Wrap literals in `eq(...)` whenever other arguments use matchers |
| `UnnecessaryStubbingException` | Stub unused by code under test in strict mode | Remove redundant stub; check branch; avoid blanket `lenient` |
| `Wanted but not invoked` | Production did not call that mock; SUT holds another instance or branch | Check injection and inputs; do not arbitrarily adjust `times` |
| Multiple calls matched by overly broad `anyString()` | Matcher does not reflect business rules | Use exact arguments, `eq`, or captor/assertions on payload |
| Trying to mock `static final SOME_CONSTANT` | It is a field, not a static method | Inject configuration via constructor/config rather than stubbing constants |

### 12.1. Errors Commonly Appearing When Moving to Newer JDKs

In Mockito 5, inline mocking can use Java instrumentation. On **Java 21 and later**, dynamic self-attaching of agents may emit warnings or fail in restricted environments due to newer JDK policies on dynamic agent loading. Mockito's documentation explains attaching `mockito-core` via `-javaagent` on the test JVM. Never copy JVM flags blindly from another project because jar paths and Gradle/Maven test-JVM forking must match your build.

If a test fails with “Could not initialize inline Byte Buddy mock maker”, first read the **deepest meaningful cause**: unsupported JDK, prohibited attach, incompatible Byte Buddy version, or conflicting mock maker config. The remedy is usually managed compatible dependencies or an explicit javaagent per docs, never simply disabling assertions.

### 12.2. Misconceptions to Avoid

1. **“Void methods cannot be mocked.”** False. Mockito mocks `void` to do nothing by default; you can `verify` them or use `do...`.
2. **“Final can never be mocked.”** False in Mockito 5 inline on compatible JVMs, though true with subclass mock makers/older setups.
3. **“Static mocks do not need to be closed.”** False. `MockedStatic` must be closed to avoid leaking into other tests.
4. **“Static mocks intercept all threads.”** False; scope is thread-local per the API.
5. **“Verifying a call means business logic is right.”** Insufficient; assert outcomes/semantics too. Calling with malformed data can still pass a weak verification.
6. **“`@MockitoBean` and `mock()` are identical.”** No; the annotation belongs to Spring bean overriding, while `mock()` creates a plain local object.
7. **“If the library supports mocking it, you must mock it.”** False; testing goals decide what stays real and what boundary is isolated.

## 13. Choosing Techniques Based on System Design

| Situation | Usually reasonable choice | Why |
|---|---|---|
| Service calls a `void` email/queue port | Mock port via interface, `verify`/`doThrow` | Separates side effects from logic |
| Need to test error handling from a gateway | `doThrow(error).when(mock).voidMethod(...)` | Forces the exact failure branch |
| Need to collect sent payloads | `ArgumentCaptor` or `doAnswer` | Inspects data without real delivery |
| Legacy SDK has an unmodifiable `final` class | Mockito inline if version/JVM supports it | Isolates SDK without editing source |
| Final value object/DTO | Instantiate real object | Tests real data, avoids pointless mocks |
| Legacy static utility called on a single thread | `mockStatic` with narrow `try-with-resources` | Controls one hard-to-inject point |
| Static utilities for time/randomness or async | `Clock`/`Supplier`/interface injection | Decouples dependency cleanly across threads and versions |
| Testing a Spring bean already in context | `@MockitoBean` or version-appropriate override | Replaces bean inside the exact `TestContext` |
| Need to verify real bean/transaction coordination | Integration test with real beans | Mocking everything misses config/coordination bugs |

Good designs minimize places requiring complex static/final mocking, yet avoid forcing massive refactors just to write one unit test. Weigh refactoring cost against the value of real verification.

## 14. Practice Exercises and Sample Answers

### Exercise 1. Make a `void` Port Throw an Exception

In a test, `channel.send(...)` must throw `IllegalStateException("temporary failure")` for any valid destination and payload. How do you stub it?

**Answer:**

```java
doThrow(new IllegalStateException("temporary failure"))
        .when(channel)
        .send(anyString(), anyString());
```

Then call the service and assert the exception type and message. Check whether the service is expected to propagate or handle the failure before choosing expectations. If the service **retries**, verify total call count per contract rather than assuming one call.

### Exercise 2. Ensure No Real Send Occurs When Input Is Rejected

Given `service.dispatch("R-11", "invalid")`. If the service must reject the destination, how do you verify the side-effect dependency was never called?

**Answer:**

```java
assertThatThrownBy(() ->
        service.dispatch("R-11", "invalid"))
        .isInstanceOf(IllegalArgumentException.class);

verifyNoInteractions(channel);
```

Assumes `service` was constructed with mock `channel` and a real `AddressPolicy`. The test verifies both the input validation error and **no gateway calls**.

### Exercise 3. Verify Static Behavior Is Restored

**Answer:**

```java
assertThat(ShipmentService.TraceIds.forOrder("R-12"))
        .isEqualTo("trace-R-12");

try (MockedStatic<ShipmentService.TraceIds> traces =
             mockStatic(ShipmentService.TraceIds.class)) {
    traces.when(() ->
            ShipmentService.TraceIds.forOrder("R-12"))
            .thenReturn("fixed");

    assertThat(ShipmentService.TraceIds.forOrder("R-12"))
            .isEqualTo("fixed");
}

assertThat(ShipmentService.TraceIds.forOrder("R-12"))
        .isEqualTo("trace-R-12");
```

Observation: once the scope closes, real static logic resumes. This is critical for test isolation.

### Exercise 4. Diagnosing a Version Issue

A project uses Mockito 4.x with the default subclass mock maker. Calling `mockStatic(TraceIds.class)` reports static mocks are not supported. What can you do?

**Suggested answer:** check dependency resolution and mock maker config; with Mockito 4, enable the inline mock maker if runtime-compatible (e.g., via extension config or the version-appropriate artifact). When upgrading to Mockito 5, verify the Java 11+ baseline, agent constraints, and dependency management. You do not need to rewrite business logic over a `void` method, and changing JUnit annotations will not enable static mocking.

## 15. Checklist Before Finalizing Tests Using void/final/static

- [ ] You know the exact **Mockito version** and **mock maker** active in the test runtime.
- [ ] JDK, Byte Buddy/instrumentation, and Gradle/Maven/IDE runner settings are compatible.
- [ ] For `void`, use `verify` when only checking calls; skip redundant stubbing.
- [ ] To force a `void` failure, use `doThrow` with an exception valid for the method signature.
- [ ] `doAnswer` returns `null` for `void` and introduces no dangerous side effects.
- [ ] For spies, you understand real methods can run; use the `do...` family when avoiding side effects.
- [ ] For `final`, do not confuse a `final` variable with a `final` class/method.
- [ ] For `static`, `MockedStatic` sits inside `try-with-resources` and closes after the test.
- [ ] Static mocks are never assumed to apply across other worker threads.
- [ ] Never try to stub a `static final` field as if it were a static method.
- [ ] Matchers are used consistently within a single call; verifications/captors check business-relevant arguments.
- [ ] The test still asserts real SUT behavior rather than mocking away what needs testing.
- [ ] No test depends on state or leaked static mocks from another test.
- [ ] Tests run both individually and in the full suite via the official task/goal, with failure messages clearly stating the cause.
- [ ] If Spring bean overriding is needed, the right annotation is chosen for your Spring version.

## 16. Conclusion

**`void` is a stubbing syntax issue; `final` and `static` are mock maker, version, and JVM mechanism issues.** Mockito provides suitable tools for all three: `verify/doThrow/doAnswer/doNothing`, inline mocking, and `MockedStatic`. Use them when they help test a clear unit's behavior within a tight scope and with verifiable assertions.

With Spring Boot, prefer injectable dependency boundaries to avoid real side effects; reserve final/static mocking for cost-effective situations or legacy code, and always confirm the test suite runs stably on the actual JVM/CI environment.
