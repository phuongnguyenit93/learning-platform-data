# Building a Test Suite for a Feature from Service to HTTP and Database

> **Module:** Spring Boot – testing  
> **Group:** Integration Practice  
> **Topic:** Building a test suite for a feature from service to HTTP and database  
> **Goal:** Design and practice a vertical-slice test suite for order creation and lookup: unit testing business rules, MVC slice testing validation and HTTP mapping, JPA slice testing with real PostgreSQL, full-context MockMvc testing for writing/reading data, and real TCP HTTP testing via a random port. The examples use **Java 17, Spring Boot 3.5.0, JUnit Jupiter, Mockito, Spring Data JPA, Bean Validation, Flyway, and Testcontainers**.

## 1. The problem: testing a complete journey, not just individual classes

We will implement a simple API that still covers realistic scenarios: **creating an order** and **looking up an order by ID**.

```text
HTTP client
   |
   | POST /api/orders or GET /api/orders/{id}
   v
Spring MVC / JSON / Bean Validation
   |
   v
OrderController
   |
   v
OrderService [business logic, transaction, duplicate handling]
   |
   v
OrderRepository [Spring Data JPA]
   |
   v
Hibernate / JDBC / HikariCP
   |
   v
PostgreSQL [Flyway migration, unique constraint]
```

A good test suite does not merely ask “does the controller return 201?”—it needs to detect:

- Whether the controller receives and deserializes JSON properly.
- Whether the DTO rejects requests with missing data, quantity ≤ 0, or out-of-bounds quantities.
- Whether the service protects business invariants even when called outside HTTP.
- Whether the service detects duplicate request IDs and throws the right domain exception.
- Whether the Spring ExceptionHandler maps domain exceptions to HTTP 404/409 instead of returning 500 without reason.
- Whether the repository writes, queries, and enforces the unique constraint on **real PostgreSQL**.
- Whether a full request through Spring MVC calls the real service/repository, commits data, and allows GET to read the newly created record.
- Whether MockMvc tests provide sufficient integration down to the database while **not** opening a TCP server.
- Whether a `RANDOM_PORT` test uses a real HTTP client to prove the embedded server accepts requests over a socket.
- Whether cleanup avoids depending on test order or wiping out other tests' data.

**Two opposite mistakes:** Only writing Mockito unit tests and calling it end-to-end; or only running `@SpringBootTest` for every edge case, making the suite slow and hard to diagnose when something breaks. This lab coordinates multiple layers, each with its own responsibility.

## 2. API contract and acceptance criteria

### 2.1. POST create order

```http
POST /api/orders
Content-Type: application/json

{
  "requestId": "client-2026-001",
  "sku": "BOOK-01",
  "quantity": 2
}
```

Requirements:

- `requestId` is a non-empty/non-whitespace-only string, at most 64 characters long.
- `sku` is a non-empty/non-whitespace-only string, at most 32 characters long.
- `quantity` is an integer from 1 to 20; must not be missing/null.
- One `requestId` may create **only one** order. Lab policy: calling again with the same `requestId` returns **409 Conflict**, not an automatic idempotent replay. If a project wants true idempotency-key semantics, it must add payload checking and response replay; do not call this sample idempotent.
- When creation is valid, return **201 Created** and header `Location: /api/orders/{id}`.
- The body returns the database-generated ID and business details.

Illustrative response example; the actual ID is generated by the database:

```http
HTTP/1.1 201 Created
Location: /api/orders/1
Content-Type: application/json

{
  "id": 1,
  "requestId": "client-2026-001",
  "sku": "BOOK-01",
  "quantity": 2,
  "status": "CREATED"
}
```

Do not hard-code expecting ID `1` in integration tests: sequences/identities can advance due to other tests, and rollbacks do not guarantee sequence resets.

### 2.2. GET read order

```http
GET /api/orders/1
```

- Found: **200 OK** with full JSON.
- ID does not exist: **404 Not Found**, `ProblemDetail`-shaped body containing `status` and `detail`.

### 2.3. Invalid input and duplicate IDs

- POST with missing SKU, blank `requestId`, `quantity=0`, or `quantity=21`: **400 Bad Request**, does not call the service in the MVC slice and does not insert a row in integration tests.
- POST with the same `requestId` when the row already exists: **409 Conflict**, only one row for that requestId.
- Two concurrent requests with the same `requestId`: checking `existsByRequestId` before insert is **not enough to prevent a race**; the database unique constraint is the deciding layer. The service must translate **only** the right unique-constraint violation into a domain conflict. Other constraints must not be indiscriminately mapped to 409.

### 2.4. Acceptance test matrix

| ID | Scenario | Service | HTTP | DB |
| --- | --- | --- | --- | --- |
| AC-01 | Valid creation | Creates entity with CREATED status | 201, Location, body | 1 row, generated ID |
| AC-02 | Lookup created order | Returns view | 200 JSON | GET returns exact row |
| AC-03 | Duplicate request | Throws OrderConflictException | 409 | No second row |
| AC-04 | Invalid payload | Protects invariants if called directly | 400 | No insert |
| AC-05 | Non-existent ID | Throws OrderNotFoundException | 404 | No row created |
| AC-06 | Duplicate insert race | DB constraint detects it | 409 when matching unique key | Unique constraint |
| AC-07 | After POST, GET reads it | Transaction commits | 201 → 200 | Data persists after HTTP request |
| AC-08 | Real TCP HTTP | Bean wiring + server | Real TCP response | Real Postgres |

This is a **concrete contract**, not a promise of a complete production order management feature. The lab does not yet include payment, inventory, authentication, an event broker, pagination, or distributed idempotency.

## 3. Choosing the right test layer

### 3.1. Five test types used in this lab

| Layer | Annotation / mechanism | Real components | Substituted components | Bugs caught |
| --- | --- | --- | --- | --- |
| Unit Service | JUnit + `MockitoExtension` | OrderService | Mock OrderRepository | Business rules, exception branches |
| MVC Slice | `@WebMvcTest`, `@MockitoBean` | Controller, MVC, Jackson, validation/advice | Mock OrderService | Route, DTO, HTTP status/body |
| JPA Slice | `@DataJpaTest` + PostgreSQL Testcontainers | Repository, Hibernate, PostgreSQL, Flyway | No service needed | SQL mapping, unique constraint |
| Full Context MockMvc | `@SpringBootTest` + `@AutoConfigureMockMvc` | Controller → Service → JPA → PostgreSQL | No business mocks | Integration chain, commit/persistence |
| HTTP TCP | `@SpringBootTest(RANDOM_PORT)` + `TestRestTemplate` | Embedded HTTP server + full stack | No business mocks | Port/network serialization and real HTTP |

**Important distinction:** `@WebMvcTest` and `@AutoConfigureMockMvc` do **not** open a TCP server, even though both simulate HTTP requests through the servlet stack. Only `RANDOM_PORT` starts an embedded server on a dynamic port. In the full-context MockMvc test we intentionally do **not** put `@Transactional` on the test method so we verify that the row actually committed after the service call.

### 3.2. Why not use 100% `@SpringBootTest`?

- Service unit tests need neither a database nor a Spring context; they give fast feedback and pinpoint business branches accurately.
- The MVC slice should not depend on Docker just to test request validation or status mapping.
- The JPA slice checks DB mapping/constraints without booting a web server.
- Full integration catches cross-layer wiring bugs that mock-based tests cannot see.
- Real TCP tests only need a few happy/error paths to catch startup/port/codec differences, without repeating all unit assertions.

When an integration test fails, the results of lower-layer tests help narrow it down: service business logic, HTTP mapping, JPA migration, or Spring wiring.

### 4.3. `application.properties`

```properties
# src/main/resources/application.properties

spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
spring.flyway.locations=classpath:db/migration

# Do not put production datasource details/secrets into the sample.
# Integration tests obtain JDBC credentials from Testcontainers @ServiceConnection.
```

`ddl-auto=validate` means Hibernate **does not auto-create** tables in tests; Flyway migrations are the source of truth for the schema. If a migration is missing or entity/schema drift occurs, the Spring context fails early — which is a useful signal.

Running the app standalone in production requires providing a separate datasource URL/credentials via environment/secret manager. This exercise primarily runs the test suite and has no hard-coded production PostgreSQL.

### 4.4. Flyway migration

```sql
-- src/main/resources/db/migration/V1__create_purchase_orders.sql

CREATE TABLE purchase_orders (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    sku VARCHAR(32) NOT NULL,
    quantity INTEGER NOT NULL,
    status VARCHAR(16) NOT NULL,
    CONSTRAINT ck_purchase_orders_quantity
        CHECK (quantity BETWEEN 1 AND 20),
    CONSTRAINT uk_purchase_orders_request_id
        UNIQUE (request_id)
);
```

The migration is named `V1__create_purchase_orders.sql` with **two underscores** between the version and description; Flyway runs when the context connects to PostgreSQL. The DB unique key protects even when two HTTP requests both observe `existsByRequestId=false`. Do not replace the unique constraint with an assertion in a single test.

Uses PostgreSQL 16. H2 can differ in dialect/constraint behavior, so this lab intentionally uses PostgreSQL Testcontainers for repository/full integration tests.

### 5.3. `PurchaseOrder.java`

```java
// src/main/java/com/example/orders/PurchaseOrder.java
package com.example.orders;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;

@Entity
@Table(
        name = "purchase_orders",
        uniqueConstraints = @UniqueConstraint(
                name = "uk_purchase_orders_request_id",
                columnNames = "request_id"))
public class PurchaseOrder {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "request_id", nullable = false, length = 64)
    private String requestId;

    @Column(nullable = false, length = 32)
    private String sku;

    @Column(nullable = false)
    private int quantity;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 16)
    private OrderStatus status;

    protected PurchaseOrder() {
        // Required by JPA.
    }

    public PurchaseOrder(
            String requestId, String sku, int quantity) {
        this.requestId = requestId;
        this.sku = sku;
        this.quantity = quantity;
        this.status = OrderStatus.CREATED;
    }

    public Long getId() {
        return id;
    }

    public String getRequestId() {
        return requestId;
    }

    public String getSku() {
        return sku;
    }

    public int getQuantity() {
        return quantity;
    }

    public OrderStatus getStatus() {
        return status;
    }
}
```

`@GeneratedValue(IDENTITY)` relies on the PostgreSQL identity column; the ID is generated by the DB. `@Enumerated(STRING)` stores the literal `CREATED` rather than a fragile ordinal integer that breaks when enum order changes. The entity has a protected no-arg constructor for JPA.

### 5.9. `OrderService.java`

```java
// src/main/java/com/example/orders/OrderService.java
package com.example.orders;

import org.hibernate.exception.ConstraintViolationException;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

@Service
public class OrderService {

    private static final String REQUEST_ID_CONSTRAINT =
            "uk_purchase_orders_request_id";

    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public OrderView create(
            String requestId, String sku, int quantity) {

        // Defense-in-depth: service can be called outside HTTP.
        if (!StringUtils.hasText(requestId)
                || requestId.length() > 64
                || !StringUtils.hasText(sku)
                || sku.length() > 32
                || quantity < 1 || quantity > 20) {
            throw new IllegalArgumentException(
                    "invalid order input");
        }

        if (repository.existsByRequestId(requestId)) {
            throw new OrderConflictException(requestId);
        }

        try {
            PurchaseOrder saved = repository.saveAndFlush(
                    new PurchaseOrder(requestId, sku, quantity));
            return OrderView.from(saved);
        }
        catch (DataIntegrityViolationException ex) {
            // Handle only the known unique constraint.
            if (isRequestIdUniquenessViolation(ex)) {
                throw new OrderConflictException(requestId, ex);
            }
            throw ex;
        }
    }

    @Transactional(readOnly = true)
    public OrderView get(long id) {
        return repository.findById(id)
                .map(OrderView::from)
                .orElseThrow(
                        () -> new OrderNotFoundException(id));
    }

    private static boolean isRequestIdUniquenessViolation(
            Throwable error) {
        Throwable current = error;

        while (current != null) {
            if (current instanceof ConstraintViolationException
                    constraint
                    && REQUEST_ID_CONSTRAINT.equalsIgnoreCase(
                            constraint.getConstraintName())) {
                return true;
            }
            current = current.getCause();
        }
        return false;
    }
}
```

**Why does the service check both `existsBy...` and the DB constraint?**

- `existsByRequestId` returns a domain error early for ordinary duplicates.
- Two transactions checking `exists=false` concurrently can both attempt to insert; PostgreSQL's unique constraint makes the final decision.
- `saveAndFlush` forces Hibernate to emit SQL so a unique violation occurs inside the method rather than waiting for commit outside the service.
- When the exception hierarchy contains Hibernate's `ConstraintViolationException` with the exact name `uk_purchase_orders_request_id`, the service translates it into `OrderConflictException` → HTTP 409.
- Other constraint errors are rethrown—**never convert every `DataIntegrityViolationException` into 409**.

**Intentional limitation:** Not every database/vendor/JDBC driver reports constraint names consistently. If Hibernate has no constraint name, the service rethrows the DB exception instead of guessing. In production, add PostgreSQL SQLSTATE + exact constraint metadata handling tested against your driver/version and a centralized error policy. Do not parse SQL error messages by relying on unstable English text. Because this is a lab using PostgreSQL 16 and a fixed Flyway constraint name, we can test both the repository unique violation and the service exception mapping.

**Transaction:** The service's `@Transactional` wraps the entire order creation. If the unique insert fails, the runtime exception rolls back the transaction. Full-flow tests must not place `@Transactional` outside the method and assume they tested a real commit.

### 5.10. `OrderController.java`

```java
// src/main/java/com/example/orders/OrderController.java
package com.example.orders;

import java.net.URI;

import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final OrderService service;

    public OrderController(OrderService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<OrderView> create(
            @Valid @RequestBody CreateOrderRequest request) {

        OrderView view = service.create(
                request.requestId(),
                request.sku(),
                request.quantity());

        return ResponseEntity
                .created(URI.create("/api/orders/" + view.id()))
                .body(view);
    }

    @GetMapping("/{id}")
    public OrderView get(@PathVariable long id) {
        return service.get(id);
    }
}
```

`@Valid` ensures invalid payloads receive 400 from Spring MVC before calling the service. The `Location` header uses the ID from the persisted `OrderView`. Do **not** infer a 201 response from a mocked service unit test (where ID may be null): the controller slice must supply a concrete mock response ID; full integration ensures the DB generates a non-null ID.

### 5.11. `OrderExceptionHandler.java`

```java
// src/main/java/com/example/orders/OrderExceptionHandler.java
package com.example.orders;

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class OrderExceptionHandler {

    @ExceptionHandler(OrderConflictException.class)
    public ResponseEntity<ProblemDetail> conflict(
            OrderConflictException ex) {
        return problem(
                HttpStatus.CONFLICT,
                "Order request conflict",
                ex.getMessage());
    }

    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> notFound(
            OrderNotFoundException ex) {
        return problem(
                HttpStatus.NOT_FOUND,
                "Order not found",
                ex.getMessage());
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public ResponseEntity<ProblemDetail> badRequest(
            IllegalArgumentException ex) {
        return problem(
                HttpStatus.BAD_REQUEST,
                "Invalid order request",
                ex.getMessage());
    }

    private static ResponseEntity<ProblemDetail> problem(
            HttpStatus status, String title, String detail) {
        ProblemDetail body =
                ProblemDetail.forStatusAndDetail(status, detail);
        body.setTitle(title);
        return ResponseEntity.status(status).body(body);
    }
}
```

Spring Framework 6 `ProblemDetail` provides HTTP status/detail/title for domain errors. Tests assert **status and stable information**, without depending on Spring Boot's entire error JSON for malformed JSON/validation; default error formats can vary with configuration.

```java
import org.springframework.context.annotation.Bean;
import org.testcontainers.containers.PostgreSQLContainer;

@TestConfiguration(proxyBeanMethods = false)
public class PostgresTestConfig {

    @Bean
    @ServiceConnection
    PostgreSQLContainer<?> postgres() {
        return new PostgreSQLContainer<>("postgres:16-alpine");
    }
}
```

- The container is a **Spring-managed bean** (`@Bean`), not a static `@Container` from the JUnit extension.
- `@ServiceConnection` lets Boot obtain the dynamic host/port/username/password without hard-coding `localhost:5432`.
- The container bean starts **before** dependent beans (Flyway/DataSource/JPA) and stops **after** those beans are destroyed.
- ApplicationContext caching can keep both the container and the JDBC pool alive across compatible classes; their lifetimes stay synchronized.
- `@Import(PostgresTestConfig.class)` goes on test classes that need Postgres; unit/MVC slices do not import it.
- Each distinct context configuration may start its own PostgreSQL container. Because `@DataJpaTest`, full MockMvc, and `RANDOM_PORT` have different context keys, the project typically creates **three separate context/container lifetimes**; that is an intentional trade-off to isolate test scopes.
- Reusable Testcontainers or global Docker cleanup are not used in this lab; if the environment is killed, separate CI resource management is needed.

### 6.2. `@DataJpaTest` and database replacement

`@DataJpaTest` auto-configures JPA repositories/entities, transactions, and Flyway (when the dependency is present), but may automatically replace the datasource with an embedded database if H2/HSQL/Derby is on the classpath. For PostgreSQL Testcontainers, explicitly declare:

```java
@AutoConfigureTestDatabase(
        replace = AutoConfigureTestDatabase.Replace.NONE)
```

Even though the project does not declare H2, this flag states the **intent to test real PostgreSQL**, preventing false-green tests if an H2 dependency is added later.

### 6.3. Flyway vs `ddl-auto=validate`

Desired sequence:

```text
Spring creates PostgreSQLContainer bean
      ↓
Boot obtains JdbcConnectionDetails
      ↓
DataSource/Hikari ready
      ↓
Flyway applies V1 migration
      ↓
Hibernate validates entity/table mapping
      ↓
Repository/Service/Controller tests run
```

If the migration is wrong, tests should fail at startup rather than falling back to H2 or `ddl-auto=create-drop` just to “turn green”. Test schemas must match production migrations within the feature's scope.

**5 `@Test` methods.** The unit-mocked repository returns an entity without a JPA-generated ID, so the service test does **not** assert `id == 1` or a non-null ID. Persisted records and database-assigned IDs are verified in the JPA/full integration tests.

**Mockito strict stubbing note:** Do not stub every method “just in case”. Only stub calls actually needed; unstubbed `existsBy...` methods return boolean `false` by default on mocks, so the happy/race tests do not need `when(...).thenReturn(false)`.

**Why unit test the race?** It proves the branch translating the exact **named unique constraint** into a domain conflict. However, because the repository is mocked, it does **not** prove that real PostgreSQL enforces the unique key — `OrderRepositoryPostgresTest` in Section 9 verifies that.

### 7.2. What unit tests do NOT prove

- They do not run Hibernate, SQL, Flyway, or PostgreSQL.
- They do not prove `@Transactional` creates/commits a DB transaction, because `MockitoExtension` does not start a Spring AOP proxy.
- They do not prove JSON/request validation; `@Valid` belongs to Spring MVC and the validation framework.
- They do not prove 201/404/409 HTTP mapping; that is the controller/advice's responsibility.
- They do not prove the actual `constraintName` reported by PostgreSQL/Hibernate during a race. When upgrading drivers, add a race integration test if that is a critical goal.

```java
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.context.annotation.Import;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.test.annotation.DirtiesContext;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@DataJpaTest
@AutoConfigureTestDatabase(

@Import(PostgresTestConfig.class)
@DirtiesContext(
        classMode = DirtiesContext.ClassMode.AFTER_CLASS)
class OrderRepositoryPostgresTest {

    @Autowired
    OrderRepository repository;

    @Test
    void savesAndReadsRowWithGeneratedIdentity() {
        String requestId =
                "repo-" + UUID.randomUUID();

        PurchaseOrder saved = repository.saveAndFlush(
                new PurchaseOrder(requestId, "BOOK-01", 2));

        assertThat(saved.getId()).isNotNull();
        assertThat(repository.findByRequestId(requestId))
                .isPresent()
                .get()
                .extracting(PurchaseOrder::getQuantity)
                .isEqualTo(2);
    }

    @Test
    void postgresUniqueConstraintRejectsSameRequestId() {
        String requestId =
                "dup-" + UUID.randomUUID();

        repository.saveAndFlush(
                new PurchaseOrder(requestId, "BOOK-01", 1));

        assertThatThrownBy(() ->
                repository.saveAndFlush(
                        new PurchaseOrder(
                                requestId, "BOOK-02", 2)))
                .isInstanceOf(
                        DataIntegrityViolationException.class);
        // After a PostgreSQL constraint error, do not run more queries
        // in the same transaction marked as aborted.
    }
}
```

**2 `@Test` methods.** This test runs Hibernate/real PostgreSQL without loading controllers or services. `@DataJpaTest` normally creates a transaction and rolls it back after each method. Thus fixtures in the first method do not affect the second; PostgreSQL identity sequences do **not** always roll back to 1.

**Warning when testing constraints on PostgreSQL:** When an SQL violation occurs inside a transaction, PostgreSQL marks the transaction as aborted until rollback. Do not issue further queries in the same transaction and conclude the repository API is broken; let the Spring test-managed transaction roll back when the method finishes.

With only H2, unique constraints might still pass without proving that the PostgreSQL driver/dialect/DDL match. `@AutoConfigureTestDatabase(replace=NONE)` is an explicit requirement.

## 10. Full-context MockMvc + PostgreSQL — 4 tests

### 10.1. Why is this class not `@Transactional`?

`@SpringBootTest + @AutoConfigureMockMvc` loads **controller, service, JPA, Flyway, and PostgreSQL**. Although MockMvc does not open a socket, it traverses Spring MVC filters, request mapping, validation, and the controller. The service opens and commits its own transaction.

We omit `@Transactional` on the test methods because we want to confirm that after POST, GET and repository queries **in a new transaction** see the committed row. A test-managed transaction can mask commit issues or roll back data automatically after the method.

To avoid polluting the database, each test uses a random `requestId` and `@AfterEach` deletes only the rows **owned by itself**.

### 10.2. `OrderFlowMockMvcIT.java`

```java

import java.util.HashSet;
import java.util.Set;
import java.util.UUID;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.context.annotation.Import;
import org.springframework.http.MediaType;
import org.springframework.test.annotation.DirtiesContext;
import org.springframework.test.web.servlet.MockMvc;
import org.springframework.test.web.servlet.MvcResult;

import static org.assertj.core.api.Assertions.assertThat;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.post;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.header;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
@Import(PostgresTestConfig.class)
@DirtiesContext(
        classMode = DirtiesContext.ClassMode.AFTER_CLASS)
class OrderFlowMockMvcIT {

    @Autowired
    MockMvc mvc;

    @Autowired
    OrderRepository repository;

    @Autowired
    ObjectMapper mapper;

    private final Set<String> ownedIds = new HashSet<>();

    private String newRequestId() {
        String id = "it-" + UUID.randomUUID();
        ownedIds.add(id);
        return id;
    }

    private static String json(
            String requestId, String sku, int quantity) {
        return """
            {"requestId":"%s","sku":"%s","quantity":%d}
            """.formatted(requestId, sku, quantity);
    }

    @AfterEach
    void deleteOnlyRowsCreatedByThisTest() {
        for (String requestId : ownedIds) {
            repository.findByRequestId(requestId)
                    .ifPresent(repository::delete);
        }
        repository.flush();
    }

    @Test
    void postThenGetReadsCommittedRow()
            throws Exception {
        String requestId = newRequestId();

        MvcResult created = mvc.perform(

                .andExpect(header().exists("Location"))

                        .value(requestId))
                .andExpect(jsonPath("$.status")
                        .value("CREATED"))
                .andReturn();

        long id = mapper.readTree(
                created.getResponse().getContentAsString())
                .get("id").asLong();

        assertThat(id).isPositive();

        mvc.perform(get("/api/orders/{id}", id))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.sku")
                        .value("BOOK-01"))
                .andExpect(jsonPath("$.quantity")
                        .value(2));

        assertThat(repository.countByRequestId(requestId))
                .isEqualTo(1);
    }

    void duplicatePostReturns409AndOnlyOneRow()

        String requestId = newRequestId();

        mvc.perform(post("/api/orders")

                        .content(payload))

                .andExpect(jsonPath("$.status").value(404));
    }
}
```

**4 `@Test` methods** exercise the real path through the application. They do not mock the repository or service. `postThenGetReadsCommittedRow` provides three complementary pieces of evidence: HTTP 201, HTTP GET 200, and the repository observing **one** row for `requestId`. `duplicatePostReturns409AndOnlyOneRow` not only checks status 409 but also asserts the database did not grow to two rows.

**About cleanup:** `@AfterEach` runs after each method and only calls `findByRequestId`/`delete` for IDs owned by the test. It does not run a global `TRUNCATE TABLE purchase_orders`. JUnit's default `PER_METHOD` test instance gives each test object its own `ownedIds`. The class does not enable concurrent methods; if enabling parallelism/forks, database namespace/transaction and context lifecycle must be redesigned.

**Do not confuse:** MockMvc is still a **mock servlet environment**; there is no real listening HTTP server. To test TCP/embedded server behavior, see Section 11.

## 11. Random-port real HTTP + PostgreSQL — 2 tests

### 11.1. Why add a real HTTP layer?

`MockMvc` is strong at the Spring MVC boundary but bypasses real sockets and embedded server startup. `@SpringBootTest(webEnvironment = RANDOM_PORT)` starts Tomcat/embedded server on a random port; `TestRestTemplate` sends HTTP requests across real client/server threads.

Important: a `@Transactional` test method does **not** automatically roll back DB writes executed by the server thread. In this project, we declare no test transaction and clean up rows by `requestId`.

### 11.2. `OrderHttpSocketIT.java`

```java
// src/test/java/com/example/orders/OrderHttpSocketIT.java
package com.example.orders;

import java.util.HashSet;
import java.util.Objects;
import java.util.Set;
import java.util.UUID;

import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.context.annotation.Import;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.test.annotation.DirtiesContext;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(
        webEnvironment =
                SpringBootTest.WebEnvironment.RANDOM_PORT)
@Import(PostgresTestConfig.class)
@DirtiesContext(
        classMode = DirtiesContext.ClassMode.AFTER_CLASS)
class OrderHttpSocketIT {

    @Autowired
    TestRestTemplate http;

    @Autowired
    OrderRepository repository;

    private final Set<String> ownedIds = new HashSet<>();

    private String ownedRequestId() {
        String id = "http-" + UUID.randomUUID();
        ownedIds.add(id);
        return id;
    }

    @AfterEach
    void cleanupOnlyOwnRows() {
        for (String id : ownedIds) {
            repository.findByRequestId(id)
                    .ifPresent(repository::delete);
        }
        repository.flush();
    }

    @Test
    void realTcpPostThenGetPersistsOrder() {
        String requestId = ownedRequestId();

        ResponseEntity<OrderView> created =
                http.postForEntity(
                        "/api/orders",
                        new CreateOrderRequest(
                                requestId, "BOOK-HTTP", 3),
                        OrderView.class);

        assertThat(created.getStatusCode())
                .isEqualTo(HttpStatus.CREATED);
        assertThat(created.getHeaders().getLocation())
                .isNotNull();

        OrderView body = Objects.requireNonNull(
                created.getBody());

        assertThat(body.id()).isNotNull();
        assertThat(body.requestId())
                .isEqualTo(requestId);
        assertThat(body.status())
                .isEqualTo(OrderStatus.CREATED);

        ResponseEntity<OrderView> fetched =
                http.getForEntity(
                        "/api/orders/{id}",
                        OrderView.class,
                        body.id());

        assertThat(fetched.getStatusCode())
                .isEqualTo(HttpStatus.OK);
        assertThat(
                Objects.requireNonNull(fetched.getBody())
                        .requestId())
                .isEqualTo(requestId);

        assertThat(repository.countByRequestId(requestId))
                .isEqualTo(1);
    }

    @Test
    void invalidRealHttpPostYields400WithoutRow() {
        String requestId = ownedRequestId();

        ResponseEntity<String> invalid =
                http.postForEntity(
                        "/api/orders",
                        new CreateOrderRequest(
                                requestId, "", 0),
                        String.class);

        assertThat(invalid.getStatusCode())
                .isEqualTo(HttpStatus.BAD_REQUEST);

        assertThat(repository.countByRequestId(requestId))
                .isZero();
    }
}
```

**2 `@Test` methods.** `TestRestTemplate` is auto-configured when `@SpringBootTest(RANDOM_PORT)` and `spring-web` are present, using relative URLs against the actual server port. Do not hard-code `8080`. `@DirtiesContext(AFTER_CLASS)` makes Spring close the web server, DataSource, and PostgreSQL container bean together with an intentional lifecycle.

**Do not confuse the test server port with the database port:** Spring Testcontainers `@ServiceConnection` provides the mapped PostgreSQL connection; the embedded HTTP server port is randomized by Spring Boot. They are two separate resources.

## 13. What breaks if each layer is omitted?

### 13.1. Omitting Service unit tests

Business logic could change from `quantity >= 1` to `quantity >= 0` without early detection. Unit tests clearly establish invariants and exception mapping when the repository reports duplicates.

### 13.2. Omitting the MVC slice

The controller could mistakenly use `@RequestParam` instead of `@RequestBody`, omit `@Valid`, map `/api/order` without the “s”, or return status `200` instead of `201`. Repository tests are blind to these HTTP contract errors.

### 13.3. Omitting the JPA slice

Entity `@Column(name="request_id")` could be misnamed, migrations could drift, or the unique constraint could be dropped. Service Mockito tests remain green because the repo is mocked, and the MVC slice remains green because the service is mocked.

### 13.4. Omitting full-context MockMvc

The real service and repository might not be wired properly by Spring, the transaction proxy might be inactive, Flyway migrations might fail, or HTTP calls might bypass beans assumed by unit tests. Full context catches wiring and cross-layer behavior.

### 13.5. Omitting real HTTP

MockMvc does not prove the embedded server can start, bind a random port, or pass client/server HTTP headers over a socket. Some serialization/filter/connector behaviors differ in a real HTTP environment.

**However:** Not every API needs 2 real-HTTP tests. In large systems, pick contract-critical journeys as smoke tests and keep most business edge cases in unit/slice tests to keep CI fast.

## 14. Transactions, rollbacks, and test data: the easiest part to get wrong

### 14.1. `@DataJpaTest` rolls back by default

Repository tests wrap each method in a transaction, so rows created in a method normally roll back afterward. Even with rollback, **the PostgreSQL identity sequence is not guaranteed to reset**. Do not assert fixed IDs.

### 14.2. `@SpringBootTest + @AutoConfigureMockMvc` does not roll back automatically

`@SpringBootTest` does not add `@Transactional` by default. The service's `@Transactional` creates and commits a transaction per invocation. This is what we want when asserting that a GET after a POST reads the row. Putting `@Transactional` on the integration test can cause the service to join the test-managed transaction and roll the row back at the end; the test could pass without proving actual commit logic.

### 14.3. `RANDOM_PORT`: HTTP client and server run on different threads

With a real server, the HTTP client test and the application server run on separate threads, so `@Transactional` on the test method does **not** roll back DB writes performed by the server thread. Cleanup must use owned IDs/namespaces instead of relying on test rollback.

### 14.4. Avoid global cleanup

Anti-pattern:

```java
@AfterEach
void resetEverything() {
    repository.deleteAll();
}
```

If two test classes or forks share a database, `deleteAll` wipes out another test's rows and causes flaky failures. Use unique UUID requestIds and delete only the rows you created. If a full schema reset is needed, own a **dedicated database/schema per worker** rather than doing it on a shared DB.

### 14.5. Do not use `@DirtiesContext` to clean up rows

`@DirtiesContext` marks the context dirty, forcing Spring to close/recreate beans, and does **not** automatically delete rows already committed in a shared PostgreSQL instance. In the sample, the annotation closes the context/container at the end of the class; `@AfterEach` cleans up test-owned records.

### 14.6. Exceptions inside a PostgreSQL transaction

When a unique violation occurs, the transaction normally enters an aborted state until rollback. Do not catch it and keep querying inside the **same** transaction as the failed `saveAndFlush`. The service throws `OrderConflictException` so the transaction rolls back. The JPA constraint test stops after the exception assertion; Spring rollback finishes the lifecycle.

## 15. Distinguishing validation, business rules, and database constraints

### 15.1. Bean Validation is the HTTP boundary

`@NotBlank`/`@NotNull`/`@Min`/`@Max` on the DTO are triggered at the controller via `@Valid`. MVC invalid-input tests assert `400` and zero service calls.

### 15.2. Service invariants do not rely solely on HTTP

If a scheduler, message listener, or another service calls `OrderService.create(...)`, those callers do not necessarily pass through MVC Bean Validation. Therefore the service checks core invariants itself. The invalid-quantity unit test proves the repository is not called.

### 15.3. DB constraints are the final boundary

An API that only checks `exists` before inserting is not atomic against concurrent requests. PostgreSQL's unique key guarantees there are never two rows with the same requestId even under application races. The JPA slice test proves the real unique constraint; the service unit test proves the branch mapping the known DB exception.

### 15.4. Do not classify SQL errors using message text

Hibernate's `ConstraintViolationException.getConstraintName()` can provide the constraint name, though DB drivers/vendors do not always report names. If a project supports multiple DBs, inspect the root SQLSTATE and driver-specific constraint metadata. Do not parse `SQLException.getMessage()` for strings like “duplicate key” because localization and versions vary.

### 15.5. 409 is not idempotency

In this lab, a second POST with the same requestId returns 409. If the real requirement is **idempotent retry** (a POST with the same key and same payload must return the same result), you also need to:

- Store a canonical request hash/payload.
- On key collision, compare payloads and decide whether to replay the result or return 409 on differing content.
- Use database locking or an upsert/transaction policy for concurrent request races.
- Test retries, concurrent clients, and failures after commit before the HTTP response is sent.

Do not assume a unique constraint implements full idempotency.

## 16. Troubleshooting failures by layer

| Symptom | First layer to inspect | Tools |
| --- | --- | --- |
| Unit service returns wrong status | Business logic | Mockito, captured entity |
| MVC 400 on valid JSON | Controller/DTO | MockMvc, Bean Validation logs |
| MVC status 200 instead of 201 | Controller | MockMvc status/header |
| MVC 409 returns 500 | ExceptionHandler / mapping | MockMvc ProblemDetail |
| `@WebMvcTest` fails for missing Service bean | Slice dependency | `@MockitoBean` |
| `@DataJpaTest` unexpectedly uses H2 | Test DB replacement | `@AutoConfigureTestDatabase` |
| Flyway “Unsupported Database” | Flyway PostgreSQL module | Maven dependency tree |
| Hibernate `Schema-validation: missing table` | Migration didn't run or wrong DB | Flyway history, connection details |
| JPA mapping error on column `request_id` | Entity/schema drift | PostgreSQL repository test |
| Duplicate rows created | Missing DB unique constraint | Flyway migration/constraint |
| Unit conflict PASSES but full flow returns 500 | Different real constraint name/translation | SQLSTATE, Hibernate cause chain |
| Test passes only when run with another class | Fixture/setup leak | Unique IDs, independent setup |
| Order ID is not 1 | Normal identity/sequence behavior | Assert non-null/positive ID |
| `RANDOM_PORT` connection refused | Server startup/port/runner | Spring logs, TestRestTemplate |
| HTTP client GET doesn't see POST | Transaction commit/persistence | Full flow repo query |
| Test hangs when Docker is missing | Container runtime/CI | Docker preflight; env failure |
| `Connection refused` after another class | Stopped container/context cache mismatch | Spring-managed container lifecycle |
| Maven runs only 10 tests | Surefire `*IT` not included | POM includes, surefire-reports |

### 16.1. When a test fails

1. Capture the **root cause stacktrace**, the test's requestId, and the test class/method.
2. Verify the test actually ran (not SKIPPED).
3. Verify Docker/container readiness when the test needs PostgreSQL.
4. Check Spring profiles/properties and the mapped datasource host/port from `@ServiceConnection`.
5. Check Flyway migrations and schema validation.
6. For HTTP 400, inspect request contentType/JSON field names/Bean Validation before debugging the repository.
7. For 500 on duplicates, inspect the SQL violation root cause/constraint name; do not convert every DataIntegrityViolation into 409.
8. Re-run the failing test standalone, then the whole suite; if it only fails together, check shared state/cleanup.
9. Never fix flaky tests with `Thread.sleep` or infinite timeout increases.
10. Never drop mandatory integration tests just to make the build green.

## 17. CI/CD for this test suite

### 17.1. Fast/slow grouping

- **Fast checks (10 tests):** `OrderServiceTest` (5) + `OrderControllerMvcTest` (5); no Docker, suitable for pre-commit/fast feedback.
- **Database/integration (8 tests):** `OrderRepositoryPostgresTest` (2), `OrderFlowMockMvcIT` (4), `OrderHttpSocketIT` (2); requires Docker and the PostgreSQL image.

In a large repository, split Maven Surefire/Failsafe or CI jobs by test-group profiles to optimize runtime; **never** treat an unexecuted group as PASS. This lab uses one Surefire configuration including all files so `mvn test` runs everything.

### 17.2. Illustrative GitHub Actions workflow

```yaml
name: Orders Vertical Slice Tests

on:
  push:
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 25

      - uses: actions/checkout@v4
```

The Docker daemon must be reachable and permitted to start containers. This is an illustrative workflow, **not a claim that it has been executed**. Never put production database URLs/credentials in tests. Never expose a privileged Docker socket to untrusted builds without an isolation policy.

### 17.3. Resource budget

Three layers with different contexts may start three PostgreSQL containers sequentially. On CI runners with low CPU/RAM, container boot/migrations take time; measure real performance before increasing parallelism. If consolidating containers or using a suite-wide singleton to cut runtime, ensure Spring context cache lifecycles and data isolation so classes never wipe out each other's database state.

### 17.4. Running in parallel

Do not enable parallel methods on the full-context/DB tests in the sample. When enabling it, ensure:

- Every test data row has its own requestId.
- No `deleteAll` or `TRUNCATE` on a shared DB.
- Do not stop a Spring-managed container while another class still uses the cached context.
- Consider `@DirtiesContext` interactions when classes run concurrently.
- Database pool limits fit the fork count.
- JUnit `@ResourceLock` does not lock resources across Surefire JVM forks or CI jobs; if sharing a DB, use external namespace/schema/run isolation.

## 18. Extending to real-world scenarios

### 18.1. Adding GET list/search

When the API expands with `GET /api/orders?sku=...`, test pagination, stable sorting, tenant filtering, empty results, and SQL performance. Do not assert against the whole table if other tests' data may be present.

### 18.2. Adding order update/cancel

Add state transitions like `CREATED -> CANCELLED`, test illegal transitions, optimistic locking (`@Version`), and HTTP 409 on concurrent updates. A state-machine unit test is necessary, but it does not replace PostgreSQL integration for locking/transactions.

### 18.3. Adding payments or event publishing

If the service sends Kafka/Rabbit messages or calls a Payment API, test outbox/rollback/idempotency using a Testcontainers broker and a separate HTTP stub. Do not wire a real payment sandbox into unit tests.

### 18.4. Adding security

If Spring Security is present, `@WebMvcTest` can load security filters; use `spring-security-test` and `@WithMockUser`/MockMvc request post-processors to test 401/403 and authorization boundaries. Never disable filters just to make a 201 test pass when security is part of the production contract.

### 18.5. Adding HTTP contract docs

Use Spring REST Docs/OpenAPI contract tests to protect schemas and headers. Avoid snapshotting full error JSON if it contains unstable timestamps/trace IDs.

### 18.6. Adding real concurrency/idempotency tests

Issue two requests with the same requestId truly **concurrently** (barrier/latch), verify one 201 and one 409, and one row in the database; run bounded iterations without relying on `Thread.sleep`. When testing concurrency, use **two independent transactions/threads** rather than the test-managed transaction, and manage cleanup by ID.

### 18.7. Adding failure/recovery

Simulate DB outages/network errors to ensure the application returns controlled errors. Do not translate every `DataIntegrityViolationException` or `DataAccessException` to 409; that misclassifies failures. With timeouts/retries, inspect committed side effects and duplicate risk.

## 20. Self-check questions

**1.** Does a Mockito unit test prove Postgres's unique constraint works?  
**No.** The repository is mocked; a JPA/PostgreSQL integration test is required.

**2.** Does `@WebMvcTest` start a real TCP server?  
**No.** MockMvc operates on a mock servlet environment.

**3.** Can `@SpringBootTest + @AutoConfigureMockMvc` call the real service and database?  
**Yes**, if those beans are not mocked and the context has a real DataSource.

**4.** How does `RANDOM_PORT` differ from `MOCK`?  
**RANDOM_PORT** starts an embedded server accepting real HTTP; **MOCK** does not.

**5.** Does `@DataJpaTest` roll back by default?  
**Yes**, test-managed transactions normally roll back after each method.

**6.** Does `@Transactional` on a test method roll back the HTTP server thread?  
**Not automatically**; the server thread has its own transaction.

**7.** Why is Flyway needed in integration tests?  
To test the schema/migrations along the same boundary as production, rather than letting Hibernate auto-generate an arbitrary schema.

**8.** Why is `@AutoConfigureTestDatabase(replace=NONE)` needed?  
To prevent the JPA slice from silently replacing the Postgres Testcontainer with an embedded DB.

**9.** Does checking duplicates with `existsByRequestId` prevent every race?  
**No**, a DB unique constraint is required.

**10.** Why use `saveAndFlush` instead of `save` when testing unique violations?  
So SQL/constraints are checked before leaving the service method.

**11.** If the whole table count is greater than 1, does that mean the test must fail?  
No. Other data may exist; assert by test-owned `requestId`.

**12.** Does `@DirtiesContext` automatically delete committed Postgres rows?  
No; context/container lifecycle is separate from data cleanup.

**13.** Does Mockito's `@Mock` replace a bean in `@WebMvcTest`?  
No; use Spring's `@MockitoBean`.

**14.** What should you check on a Flyway “Unsupported Database PostgreSQL” error?  
The PostgreSQL-specific Flyway module dependency/version.

**15.** Why must Surefire include `*IT.java` in the sample?  
So `mvn test` does not skip integration classes based on naming convention.

**16.** How many `@Test` methods are in this codebase?  
**18:** 5 service unit + 5 MVC + 2 JPA + 4 full MockMvc + 2 HTTP TCP.
