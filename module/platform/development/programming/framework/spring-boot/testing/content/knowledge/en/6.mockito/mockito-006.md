# Mockito: verify, Invocation Counts, and Order When Behavior Requires It

## 1. From Checking Return Values to Checking Interactions

For a pure function like adding two numbers, the most direct test calls the function and compares the **return value**:

```java
assertEquals(5, calculator.add(2, 3));
```

However, many operations in a Spring Boot application produce **side effects** through dependencies: issuing a payment charge, writing an audit event, publishing a message, sending an email, or calling an external system. In those cases, a right return value alone may not prove the behavior happened correctly.

Mockito provides **interaction verification** via `verify(...)` to answer questions such as:

- Was the payment gateway called for a valid order?
- Was it called **exactly once**, or did we accidentally double-charge?
- When input is invalid, was the external service **not** called?
- Was authorization checked **before** performing a sensitive operation?
- When retrying transient failures, did attempts stay within the limit and stop as soon as one succeeded?

**Key principle:** verify interactions only when *the interaction, invocation count, or call order* is part of the behavior you must protect. For logic with observable outputs or state, prefer asserting results/state. Overusing `verify` for every internal call makes tests brittle when refactoring even when external behavior is unchanged.

For instance, “Never charge twice” is a critical contract, so `verify(paymentGateway, times(1)).charge(...)` is valuable. By contrast, whether a service calls an internal getter once or twice is rarely a business contract.

### Different Roles

| Component | Role | What does it prove? |
| --- | --- | --- |
| JUnit Jupiter `@Test`, assertions | Runs the test and compares expectations | Outcomes, state, exceptions |
| Mockito `@Mock` and `when(...).thenReturn(...)` | Creates fake collaborators and defines responses | Input conditions for testing the service |
| Mockito `verify(...)` | Inspects calls recorded on a mock | Whether called, with which arguments, how many times |
| Mockito `InOrder` | Checks order across relevant calls | A happened before B per the test contract |
| Spring Boot Test | Starts a Spring context or test slice when needed | Wiring/framework behavior; does not replace Mockito assertions |

Plain Java tests using Mockito **do not need** `@SpringBootTest`. If you need to verify a Spring bean mocked inside a context, use the bean creation/override mechanism appropriate for your Spring Boot version; the end of this lesson distinguishes the two clearly.

## 2. How `verify` Works: Mockito Records Invocations

A mock is an object generated by Mockito. When code under test invokes a method on a mock, Mockito records an **invocation**: the target object, method name, arguments, relative order, and related metadata. After running the service's real behavior, the test uses `verify` to inspect those recorded invocations.

```text
Arrange:
  Create mock PaymentGateway
  Configure responses if needed: when(gateway.charge(...)).thenReturn(...)

Act:
  checkoutService.checkout(orderId)
      └── paymentGateway.charge(orderId, amount)
          Mockito records invocation

Assert / Verify:
  assertTrue(result)
  verify(paymentGateway, times(1)).charge(orderId, amount)
      └── Mockito checks recorded invocations; mismatch → test FAILS
```

`verify(mock).method(...)` **does not invoke the method a second time**. It is syntax telling Mockito to match expectations against previously recorded invocations. Therefore, tests must always run **Act before Verify**.

An invocation can be verified for both **arguments** and **counts**. Stubbing and verification are separate concerns:

- `when(gateway.charge(...)).thenReturn("tx-1")`: specifies what the mock returns if a matching call occurs.
- `verify(gateway).charge(...)`: verifies whether the call actually occurred.
- Stubbing alone does not guarantee the service called the dependency; verification alone does not guarantee the return value or final state is right.
- `assertEquals(...)` is still required whenever the business operation produces an observable outcome.

If you call `verify` on a real object that is not a mock/spy, Mockito reports invalid usage. If the service holds a **different instance** from the mock verified in the test, the test cannot assume calls to the real instance were recorded.

## 3. `verify` Syntax and VerificationMode Options

Basic API:

```java
verify(mock).method(expectedArgument);
verify(mock, times(1)).method(expectedArgument);
```

Both lines are **equivalent** ways to check that the method was called once with matching arguments. In real tests, pick **one** of the two rather than repeating the same verification.

| Syntax | Condition to PASS | When to use |
| --- | --- | --- |
| `verify(mock).send("id")` | Exactly **1** matching invocation | Single call is the contract |
| `verify(mock, times(2)).send("id")` | Exactly **2** matching invocations | Designed retry / 2-step flow |
| `verify(mock, times(0)).send("id")` | Zero matching invocations | Block a side effect |
| `verify(mock, never()).send("id")` | Equivalent to `times(0)` | Express clearly “must not be called” |
| `verify(mock, atLeastOnce()).send("id")` | **At least 1** matching invocation | “Happened at least once” suffices |
| `verify(mock, atLeast(2)).send("id")` | **At least 2** matching invocations | Minimum count matters |
| `verify(mock, atMost(3)).send("id")` | **At most 3** matching invocations, including **0** | Upper bound, paired with checks that work occurred |
| `verify(mock, only()).send("id")` | This invocation is the **only interaction** on the mock | Mock must have zero other interactions |
| `verifyNoInteractions(mock)` | Zero interactions of any kind on the mock | Error path must not touch dependency |
| `verifyNoMoreInteractions(mock)` | No **unverified** invocations remain on the mock | When the test truly requires a no-extra-interactions contract |

The `...` in the table represents actual arguments, not literal Java syntax to copy verbatim. In Java files, add static imports:

```java
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.atLeastOnce;
import static org.mockito.Mockito.atLeast;
import static org.mockito.Mockito.atMost;
import static org.mockito.Mockito.only;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.verifyNoMoreInteractions;
```

### How Does `times(1)` Differ from `atLeastOnce()`?

Suppose a bug causes the payment gateway to be called twice:

- `verify(gateway, times(1)).charge(...)` → **FAILS**, catching the double-charge risk.
- `verify(gateway, atLeastOnce()).charge(...)` → **PASSES**, because two calls is still “at least once.”

When “exactly once” matters, choose `times(1)`. Using `atLeastOnce()` just to make tests pass weakens the business contract.

### `atMost(3)` Does Not Prove Any Call Happened

If the mock was never called, `verify(mock, atMost(3)).send(...)` still PASSES. To express “at least once, at most three times”:

```java
verify(mock, atLeastOnce()).send("event-1");
verify(mock, atMost(3)).send("event-1");
```

This is a **usage pattern** assuming a declared `mock` variable; it is not a standalone Java class. In fixed-count retry contracts, verifying `times(expectedAttempts)` is clearer than a loose range.

### `never()` by Arguments vs. `verifyNoInteractions()` for the Entire Mock

```java
verify(gateway, never()).charge("invalid-order", 2000);
```

This only forbids `charge("invalid-order", 2000)`. It **does not** prove the gateway was not called with other arguments. If an error path must not call the gateway with **any** arguments at all, use:

```java
verifyNoInteractions(gateway);
```

Choose the right assertion strength: “do not charge this order ID” differs from “do not interact with the payment system at all.”

## 5. Complete Example: Verifying Exactly-Once Calls and Business Order

Problem: process an order according to these rules:

1. Validate that the amount is positive.
2. Call the order approval port.
3. Only if approved, call the payment gateway to charge.
4. Only after the gateway returns a transaction ID, send the receipt.
5. For rejected orders or invalid amounts, **never** charge or send a receipt.

This contract genuinely relies on **ordering** and **side effects**. We define three interfaces representing dependencies and a small Java service class. Mockito mocks the three interfaces; the service is a real object.

`src/test/java/com/example/testing/CheckoutWorkflowTest.java`:

```java
package com.example.testing;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InOrder;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.mockito.Mockito.inOrder;
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.verifyNoMoreInteractions;
import static org.mockito.Mockito.when;

@ExtendWith(MockitoExtension.class)
class CheckoutWorkflowTest {

    interface ApprovalService {
        boolean isApproved(String orderId);
    }

    interface PaymentGateway {
        String charge(String orderId, int amountInCents);
    }

    interface ReceiptSender {
        void send(String orderId, String transactionId);
    }

    static final class CheckoutWorkflow {
        private final ApprovalService approval;
        private final PaymentGateway payment;
        private final ReceiptSender receipts;

        CheckoutWorkflow(
                ApprovalService approval,
                PaymentGateway payment,
                ReceiptSender receipts) {
            this.approval = approval;
            this.payment = payment;
            this.receipts = receipts;
        }

        boolean execute(String orderId, int amountInCents) {
            if (amountInCents <= 0) {
                throw new IllegalArgumentException(
                        "amount must be positive");
            }

            if (!approval.isApproved(orderId)) {
                return false;
            }

            String transactionId =
                    payment.charge(orderId, amountInCents);
            receipts.send(orderId, transactionId);
            return true;
        }
    }

    @Mock
    ApprovalService approval;

    @Mock
    PaymentGateway payment;

    @Mock
    ReceiptSender receipts;

    private CheckoutWorkflow workflow() {
        return new CheckoutWorkflow(approval, payment, receipts);
    }

    @Test
    void approvedOrderChargesOnceBeforeSendingReceipt() {
        // Arrange
        when(approval.isApproved("order-1")).thenReturn(true);
        when(payment.charge("order-1", 2500)).thenReturn("tx-99");

        // Act
        boolean accepted = workflow().execute("order-1", 2500);

        // Assert state/output
        assertTrue(accepted);

        // Verify exactly once with exact arguments
        verify(approval, times(1)).isApproved("order-1");
        verify(payment, times(1)).charge("order-1", 2500);
        verify(receipts, times(1)).send("order-1", "tx-99");

        // Verify contract ordering: approve -> charge -> receipt
        InOrder order = inOrder(approval, payment, receipts);
        order.verify(approval).isApproved("order-1");
        order.verify(payment).charge("order-1", 2500);
        order.verify(receipts).send("order-1", "tx-99");

        // Contract also forbids any extra operations.
        verifyNoMoreInteractions(approval, payment, receipts);
    }

    @Test
    void rejectedOrderNeverChargesOrSendsReceipt() {
        when(approval.isApproved("order-2")).thenReturn(false);

        boolean accepted = workflow().execute("order-2", 2500);

        assertFalse(accepted);
        verify(approval).isApproved("order-2");
        verifyNoInteractions(payment, receipts);
    }

    @Test
    void invalidAmountDoesNotCallAnyDependency() {
        assertThrows(
                IllegalArgumentException.class,
                () -> workflow().execute("order-3", 0)
        );

        verifyNoInteractions(approval, payment, receipts);
    }
}
```

Run:

```bash
./gradlew test --tests 'com.example.testing.CheckoutWorkflowTest'
```

**Expected result: 3 tests PASS.** There is no fixed stdout in the tests. Gradle can display passed test names per `testLogging`; the default HTML report is at `build/reports/tests/test/index.html`.

### Why Does the First Test Check Value, Count, and Order?

- `assertTrue(accepted)` confirms the service returned “order accepted.”
- `verify(..., times(1))` confirms each side effect ran **exactly once**.
- `InOrder` confirms approval occurred before charge, and charge before receipt.
- `verifyNoMoreInteractions(...)` checks that no unverified interactions remain on the three mocks. It is used deliberately here because the contract states no other interactions may occur.

In a real service, there might also be logging, metrics, or auxiliary calls outside the test's contract. Checking **every interaction** in that setting is overly strict; keep only meaningful verifications and avoid `verifyNoMoreInteractions` when valid internal changes should not break tests.

### Why Does the Second Test Not Need InOrder?

When approval returns `false`, we only need to prove the result was rejected and **payment/receipt were never called**. Between two mocks with zero interactions, ordering has no meaning. Adding `InOrder` there creates no new evidence.

### Why Does the Third Test Use `verifyNoInteractions`?

Invalid data must be rejected **before touching any external system**. That is an important negative contract, and `verifyNoInteractions(approval, payment, receipts)` expresses it more accurately than verifying individual methods with `never()`.

## 6. `InOrder`: Verifying Order When Order Is Part of the Contract

Mockito does not enforce call order by default when using ordinary `verify`:

```java
verify(payment).charge("order-1", 2500);
verify(receipts).send("order-1", "tx-99");
```

These two `verify` statements **only state that both happened**. Even if the service sent the receipt before charging, both statements would still PASS as long as each ran once.

When you must enforce “charge before sending receipt,” use:

```java
InOrder order = inOrder(payment, receipts);
order.verify(payment).charge("order-1", 2500);
order.verify(receipts).send("order-1", "tx-99");
```

This is an **excerpt** from Section 5's class, not a standalone example. `InOrder` tracks relative invocation order across **the mocks passed to it**. Calls to collaborators outside that list are not automatically checked.

### Relative Order Differs from “No Interleaving Calls”

Two consecutive `InOrder` verifications do not assert that two calls were adjacent in time. An audit or logging call could occur in between while the contract still holds:

```text
approved(order) → audit("approved") → charge(order) → audit("charged")
                → sendReceipt(order)
```

If you only care that `approved < charge < sendReceipt`, do not make tests fail just because the service adds auditing. Select **business-meaningful interactions**.

### `InOrder.verifyNoMoreInteractions()` Has an Important Limitation

On an `InOrder`, `verifyNoMoreInteractions()` primarily checks that no unverified invocations occurred **after the last verified invocation** in that order. It is not fully equivalent to `Mockito.verifyNoMoreInteractions(mock1, mock2)`, which checks all unverified invocations on those mocks.

For instance, if an unverified invocation happened before the first verified call, `InOrder.verifyNoMoreInteractions()` might not catch it. When the requirement is **no other interactions anywhere**, call `verifyNoMoreInteractions(mock1, mock2, ...)` after the required verifications, as in Section 5's checkout example.

Do not mechanically attach both kinds of `verifyNoMoreInteractions` to every test. They enforce different checks and can couple tests tightly to implementations.

### Must `verify` Statements Appear in Execution Order?

Ordinary `verify` statements can be written in whatever order reads best, independent of the order the service called the methods. Only with `InOrder` does verification order become a meaningful expectation.

For example, writing `verify(receipts)` before `verify(payment)` **does not** tell Mockito to require sending receipts before charging. It is simply the order of statements in test code.

## 7. Invocation Counts with Retry: Choosing `times(n)` by Behavior

Suppose the system publishes an event to a message gateway. On transient errors, the service retries up to **3 attempts**; if the first attempt succeeds, it stops without sending again. Here invocation count truly is part of the contract.

The complete example below uses a custom exception to model retryable errors; no real network or broker is needed.

`src/test/java/com/example/testing/RetrySenderTest.java`:

```java
package com.example.testing;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.Mockito.doNothing;
import static org.mockito.Mockito.doThrow;
import static org.mockito.Mockito.times;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoMoreInteractions;

@ExtendWith(MockitoExtension.class)
class RetrySenderTest {

    interface MessageGateway {
        void publish(String eventId);
    }

    static final class TransientFailure extends RuntimeException {
    }

    static final class RetrySender {
        private final MessageGateway gateway;

        RetrySender(MessageGateway gateway) {
            this.gateway = gateway;
        }

        void publishWithRetry(String eventId) {
            for (int attempt = 1; attempt <= 3; attempt++) {
                try {
                    gateway.publish(eventId);
                    return; // Stop immediately on success.
                } catch (TransientFailure ex) {
                    if (attempt == 3) {
                        throw ex;
                    }
                }
            }
        }
    }

    @Mock
    MessageGateway gateway;

    @Test
    void retriesTwiceThenSucceedsOnThirdAttempt() {
        doThrow(new TransientFailure())
                .doThrow(new TransientFailure())
                .doNothing()
                .when(gateway).publish("event-1");

        new RetrySender(gateway).publishWithRetry("event-1");

        verify(gateway, times(3)).publish("event-1");
        verifyNoMoreInteractions(gateway);
    }

    @Test
    void successfulFirstAttemptDoesNotRetry() {
        new RetrySender(gateway).publishWithRetry("event-2");

        verify(gateway, times(1)).publish("event-2");
        verifyNoMoreInteractions(gateway);
    }

    @Test
    void failsAfterAtMostThreeAttempts() {
        doThrow(new TransientFailure())
                .when(gateway).publish("event-3");

        assertThrows(
                TransientFailure.class,
                () -> new RetrySender(gateway)
                        .publishWithRetry("event-3")
        );

        verify(gateway, times(3)).publish("event-3");
    }
}
```

Run:

```bash
./gradlew test --tests 'com.example.testing.RetrySenderTest'
```

**Expected result: 3 tests PASS.** Combined with the three checkout tests, the example suite has **6 tests PASS** when running `./gradlew test`.

Explanation:

- Test 1 uses `doThrow(...).doThrow(...).doNothing().when(gateway).publish(...)` to simulate transient failures on attempts 1 and 2, succeeding on attempt 3. `verify(..., times(3))` proves exactly three attempts occurred.
- Test 2 configures no response: a `void` method on a Mockito mock does nothing and throws nothing by default, so the service stops after **one call**. This protects the “do not retry on success” rule.
- Test 3 makes the mock throw on every call, verifying that the exception propagates when attempts are exhausted and that exactly three attempts occurred.

**Note:** using `times(3)` in test 3 is stronger than `atMost(3)` because it also catches the service giving up too early. If the contract only says “at most three attempts” and allows early termination under some condition, assertions should reflect the approved policy.

### Should You Verify Each Retry Attempt with `InOrder`?

If all three attempts invoke **the same method with the same arguments**, verifying the count with `times(3)` suffices for most retry tests. Ordering of identical attempts is inherent because invocations are recorded chronologically; `InOrder` adds value only when each retry must interleave with other actions per contract, such as auditing “retrying”, advancing backoff, or refreshing a token before the next attempt.

Avoid hard-coding fixed call counts for algorithms using jitter, parallel requests, or caching unless the contract truly guarantees that number. For asynchronous flows, wait for completion before verifying or use timeout verification modes discussed later.

## 8. Verifying Arguments: Not Just Counting Calls

A verification matches both **method and arguments**. Counting one call with the wrong `orderId` or wrong amount can still be a severe bug.

### 8.1. Exact Arguments

```java
verify(payment).charge("order-1", 2500);
```

Fits when the contract specifies exact arguments, such as ID and amount in cents.

### 8.2. Argument Matchers

When only certain properties matter:

```java
verify(payment).charge(
        eq("order-1"),
        intThat(amount -> amount > 0)
);
```

This is an **illustrative snippet** requiring mock `payment` and imports `org.mockito.ArgumentMatchers.eq`, `intThat`. When you use a matcher for one parameter of an invocation, the remaining parameters must also use matchers, such as `eq(...)`; do not mix `eq("order-1")` with literal `2500` in the same call. Mockito throws `InvalidUseOfMatchersException` if mixed improperly.

Do not pass `any()` for every argument just to get tests to PASS. If order IDs, amounts, or recipients carry business meaning, verify them specifically.

### 8.3. ArgumentCaptor to Inspect Actual Data Sent

When messages are complex, inspecting individual properties with a captor can be clearer than matching an entire object. Suppose:

```java
interface NotificationGateway {
    void publish(String destination, String payload);
}
```

The snippet below applies **after the real service has invoked mock `notifications`**, and is not a standalone program:

```java
ArgumentCaptor<String> payload =
        ArgumentCaptor.forClass(String.class);

verify(notifications, times(1))
        .publish(eq("orders"), payload.capture());

assertTrue(payload.getValue().contains("order-1"));
```

Requires importing `org.mockito.ArgumentCaptor`, matcher `eq`, and the JUnit assertion. If the method is called multiple times, `capture()` with `times(n)` and `getAllValues()` lets you check values in recorded order. When comparing complex objects, consider contract-based equality or AssertJ recursive comparison rather than verifying numerous getters.

**Important:** Captors/matchers check the data sent; they do not replace checking counts or order when those are also part of the contract.

## 9. Two Styles of Negative Verification: `never` and No Interactions

Scenarios verifying the absence of side effects are often more important than happy-path checks:

- Unauthorized input → do not call payment gateway.
- Validation error → do not publish event.
- Customer has not opted in → do not send notification.
- Retry already succeeded → do not send again.
- Entity not found → do not invoke next step.

Choose the expression matching your commitment level:

```java
verify(payment, never()).charge("order-9", 1000);
```

Forbids **one specific call**; if the service calls `charge("order-10", 1000)`, this verify still PASSES.

```java
verifyNoInteractions(payment);
```

Forbids **all interactions on the payment mock**. Use when calling any method on this collaborator is forbidden along that path.

```java
verify(payment).charge("order-1", 1000);
verifyNoMoreInteractions(payment);
```

Requires **one verified interaction** and no other unverified interactions. This differs from `verifyNoInteractions`: the mock was called once, so `verifyNoInteractions(payment)` would FAIL.

A test cannot prove “the entire application produces no side effects” solely via `verifyNoInteractions` on one mock: it only observes **the mocks controlled by that test**. Behavior of real objects, external systems, or other dependencies requires appropriate tests.

### Do Not Use `verifyNoMoreInteractions` by Default

This pattern often makes tests brittle:

```java
verify(repository).save(order);
verifyNoMoreInteractions(repository, auditLogger, metrics);
```

If the contract only requires “order was saved properly,” adding a valid metrics counter or extra lookup causes tests to FAIL needlessly. Conversely, if the contract is “never call the billing port a second time,” verify that method with `times(1)` or inspect the relevant mock for only allowed interactions.

Use negative verification intentionally to **prevent harmful behavior** or **protect invariants**.

## 10. Mockito in Spring Boot: Verifying on the Exact Injected Mock

In a Spring Boot application, the core question stays the same: **which mock is the service actually using?**

### 10.1. Plain Tests Without a Spring Context

```java
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock
    PaymentGateway gateway;

    @Test
    void chargesOnce() {
        OrderService service = new OrderService(gateway);

        service.checkout("order-1");

        verify(gateway, times(1)).charge("order-1");
    }
}
```

This is an **illustrative snippet tied to existing `OrderService`/`PaymentGateway`**, not standalone code. Adjust method signatures to match your actual contract. It tests a directly constructed Java object without loading a Spring context, ideal for unit tests.

### 10.2. Testing a Real Spring Bean with a Mock Bean

In **Spring Boot 3.3.x**, you can use `@MockBean` to replace a Spring bean in the test context:

```java
@SpringBootTest
class OrderServiceSpringTest {
    @Autowired
    OrderService orderService;

    @MockBean
    PaymentGateway paymentGateway;

    @Test
    void callsGatewayOnce() {
        orderService.checkout("order-1");

        verify(paymentGateway, times(1)).charge("order-1");
    }
}
```

This is also an **integration snippet for an existing application**. It requires importing `org.springframework.boot.test.context.SpringBootTest`, `org.springframework.beans.factory.annotation.Autowired`, `org.springframework.boot.test.mock.mockito.MockBean`, JUnit `@Test`, and Mockito methods; the gateway signature is illustrative. The test may also need stubbing and configuration so the service reaches the payment branch.

In Boot 3.3.x, `@MockBean` creates/replaces a bean in the Spring context so the real service bean uses the Mockito mock. A plain `@Mock` in a Spring test **does not automatically** replace a bean just because the field shares the type. In Spring Framework 6.2 / Spring Boot 3.4 and later, `@MockitoBean` is the replacement API; choose the annotation matching your project's version.

### 10.3. Controller Slices

`@WebMvcTest` combined with `MockMvc` and a mocked service bean is well suited for checking routing, status codes, JSON, and confirming the controller called the service with the right inputs. Still, avoid overly detailed service verifications when the HTTP response already proves enough; an HTTP test does not need to inspect every internal controller method.

### 10.4. Mockito Strict Stubbing Is Not Invocation Count Verification

`MockitoExtension` detects unused stubs or problematic stubbing under default strictness. That is a **mock configuration hygiene check**, different from `verify(mock, times(...))`. Do not interpret the absence of `UnnecessaryStubbingException` as proof that side effects happened the right number of times.

## 11. Common Mockito Verification Mistakes

### 11.1. Verifying Before Behavior Executes

**Wrong logical order:**

```java
verify(gateway).charge("order-1", 2500);
service.checkout("order-1");
```

Mockito has no recorded invocations yet during `verify`. Correct structure: **Arrange → Act → Assert/Verify**.

### 11.2. Verifying the Wrong Mock or Wrong Instance

```java
PaymentGateway mockGateway = mock(PaymentGateway.class);
OrderService service = new OrderService(new RealPaymentGateway());

service.checkout("order-1");
verify(mockGateway).charge("order-1");
```

This is an **illustrative counter-example** assuming those classes exist. If the service holds a different real instance, verification FAILS and the test may trigger real side effects. Inject the exact mock the test observes, or use a Spring mock bean to replace the dependency in context.

### 11.3. Checking Only That It Was Called, Forgetting Duplicate Calls

`verify(mock, atLeastOnce()).send(...)` permits sending multiple times. When the contract is “send exactly once,” use `verify(mock, times(1))`. This is critical for payments, order creation, duplicate events, and non-repeating emails.

### 11.4. Checking Only Count While Ignoring Arguments

`verify(payment, times(1)).charge(anyString(), anyInt())` can PASS even when called for the wrong order or wrong amount. Relax matchers only on genuinely irrelevant parameters. Verify business-relevant data fields.

### 11.5. Using `InOrder` for Details Outside the Contract

A service might check cache then read repository, or read repository then update cache, returning the right result either way. If order does not affect business semantics, `InOrder` couples the test to implementation. Only verify order for true constraints: authorize before charge, persist before publish when required by consistency, or release resources after use.

### 11.6. Confusing “Same Count” with “Right Order”

`verify(a).first()` and `verify(b).second()` do not prove `first` ran before `second`. To test sequencing, create `InOrder` via `inOrder(a, b)` and verify sequentially.

### 11.7. Misunderstanding `verifyNoMoreInteractions`

After verifying one method, `verifyNoMoreInteractions(mock)` FAILS if the mock had any other unverified call, even a valid call the test does not care about. Do not “fix” it by adding verifications for trivial calls; first decide whether the contract truly forbids extra interactions.

### 11.8. Unused Stubbing Flagged as an Error

`MockitoExtension` can throw `UnnecessaryStubbingException` when a test sets up a stub that the tested branch never uses. This is not a `verify` bug; usually you remove the stub or move it into the test that needs it. Avoid sprinkling `lenient()` everywhere.

### 11.9. Verifying on a Spy Can Trigger Unintended Real Behavior

A spy wraps a real object, so unstubbed methods can run real logic when called. `verify(spy).method(...)` checks recorded invocations, yet the preceding **Act** step may have hit a DB or network if the spy references real collaborators. Furthermore, `when(spy.method()).thenReturn(...)` can invoke the real method during stubbing; for spies, consider `doReturn(...).when(spy).method()`. Unit tests should generally mock collaborators and keep the class under test as a real object.

### 11.10. Static Methods and Constructors Are Not Regular Mocks

`verify(mock)` applies to invocations on mock/spy instances. Mockito also offers scoped APIs for static/construction mocking (`MockedStatic`/`MockedConstruction`) when appropriate, which operate differently and must be closed properly. Do not try to verify a static call on a plain object using `verify(mock)`. Prefer DI for testable dependencies whenever application design permits.

### 11.11. Asynchronous Flows: Verifying Too Early

A service may return before a worker thread sends an event. Calling `verify(mock)` immediately can FAIL even though the event arrives milliseconds later. Mockito offers verification modes like `timeout(millis)`:

```java
verify(events, timeout(1000).times(1)).publish("order-1");
```

This is an **illustrative snippet** requiring mock `events` and importing `org.mockito.Mockito.timeout`. It waits until the condition is satisfied within the time limit, though it does not prove no late call arrives **after** verification succeeds. For async behavior, a more deterministic solution is **waiting for the task's completion signal/`Future`/`CompletableFuture`** before verifying; avoid fixed `Thread.sleep(...)` and flaky tests. If the contract forbids extra calls after the whole process ends, wait for completion before `times(1)`.

### 11.12. Misreading Error Messages

Common Mockito messages:

| Symptom | Common meaning | Where to look |
| --- | --- | --- |
| `Wanted but not invoked` | No matching invocation recorded | Was the mock injected properly? Did execution take that branch? |
| `TooManyActualInvocations` | Actual count exceeds expectation | Is a retry/loop/duplicate call valid or a bug? |
| `TooFewActualInvocations` | Actual count is lower than expectation | Early return/exception, or async work not awaited? |
| `ArgumentsAreDifferent` | Call occurred but arguments did not match | Check IDs, amounts, matchers, input transformations |
| `VerificationInOrderFailure` | Order did not match expectation | Which ordering is contract vs. implementation? |
| `NoInteractionsWanted` | Unexpected interaction occurred | Was `verifyNoMoreInteractions` too strict? |
| `UnnecessaryStubbingException` | Stub was never used | Remove excess stubbing or fix test branch |

Exact exception names/messages vary across Mockito versions and scenarios. Read the **wanted invocation**, **actual invocation**, and stack trace call site to pinpoint the cause rather than blindly loosening `verify` to make it PASS.

## 12. Designing Less Brittle Tests: What Should You Verify?

Compare three ways to test “approved orders charge once and send a receipt”:

**Insufficient check:**

```java
assertTrue(workflow.execute("order-1", 2500));
```

Returning true does not guarantee we didn't charge twice or send the receipt before charging.

**Right contract check:**

```java
assertTrue(workflow.execute("order-1", 2500));
verify(payment, times(1)).charge("order-1", 2500);

InOrder order = inOrder(payment, receipts);
order.verify(payment).charge("order-1", 2500);
order.verify(receipts).send("order-1", "tx-99");
```

This is a **condensed illustrative snippet**: assume mocks and workflow are set up as in the complete example. It checks value, exactly-once execution, and meaningful order.

**Overly detailed check:**

```java
verify(logger).debug("starting");
verify(cache).get("order-1");
verify(orderRepository).findById("order-1");
verify(metrics).increment("approved");
verify(payment).charge("order-1", 2500);
verify(logger).debug("done");
verifyNoMoreInteractions(logger, cache, orderRepository, metrics, payment);
```

This is a **counter-example** illustrating brittle verification; the mocks and service are not part of a standalone runnable project. Adding caching, changing log lines, or improving metrics can break the test without any change in payment behavior. If those interactions are not independent business requirements, do not lock down their exact counts or order.

### Quick Decision Matrix

| Nature of requirement | Preferred assertion/verification |
| --- | --- |
| “Total price is right” | `assertEquals(expected, actual)` |
| “Invalid input must be rejected” | `assertThrows(...)` and if needed `verifyNoInteractions(...)` |
| “Charge only once” | `verify(payment, times(1)).charge(...)` |
| “Do not notify if unapproved” | `verifyNoInteractions(notifier)` or targeted `never()` |
| “Must authorize before charging” | `InOrder(authorizer, payment)` |
| “Retry at most three times then fail” | Assert exception + `times(expectedAttempts)` in specific scenario |
| “Publish message with right orderId” | `verify` exact arguments or `ArgumentCaptor` |
| “Controller returns HTTP 201 with valid JSON” | Assert status/body via MockMvc; verify service only when call contract matters |

Write tests so a FAIL communicates a **behavioral violation**, not a harmless internal change.

## 13. QA Checklist for a Test Using verify

Before accepting a test:

1. **Did the class under test run its real behavior?** Did the test invoke the SUT rather than just stubbing and verifying?
2. **Is the Mockito mock the exact instance used by the SUT?** For Spring beans, was the right bean mocked in the context?
3. **Should output/state be asserted too?** `verify` only checks calls; it does not prove return values.
4. **Which count fits the contract?** `times(1)`, `times(n)`, `never()`, or an `atLeast/atMost` range?
5. **Are arguments precise enough?** Avoid `any()` when wrong ID/amount would be a bug.
6. **Does order genuinely matter?** Use `InOrder` only when business/consistency constraints require it.
7. **Do negative paths forbid side effects?** Use `verifyNoInteractions` on critical collaborators when required.
8. **Is anything over-verified?** Do `verifyNoMoreInteractions` or helper call checks make the test brittle?
9. **Does the test involve asynchronous behavior?** Await completion properly before verifying.
10. **Did you inspect the report and executed test count?** Ensure the test actually ran and was not `@Disabled` or filtered out.

### Suggested Practice

Using the two complete test classes:

```bash
./gradlew test --tests 'com.example.testing.CheckoutWorkflowTest'
./gradlew test --tests 'com.example.testing.RetrySenderTest'
./gradlew test
```

Self-practice exercises:

1. In `CheckoutWorkflow.execute`, intentionally call `payment.charge` **twice** when approved; predict which test FAILS and why.
2. Swap the order of sending the receipt and charging (adjusting illustrative code accordingly); observe how `InOrder` catches the contract violation.
3. For a rejected order, add an accidental call to payment; confirm `verifyNoInteractions(payment, receipts)` FAILS.
4. In `RetrySender`, change `attempt <= 3` to `attempt <= 2`; identify why the 3-attempt test FAILS.
5. Try replacing `times(1)` with `atLeastOnce()` in the “charge once” test; explain why the assertion becomes weaker.
6. Remove `verifyNoMoreInteractions` from the happy path and discuss which internal refactorings should be allowed to add calls without breaking the test.

## 14. Key Takeaways

- **`verify(mock).method(args)` = exactly one matching invocation**, equivalent to `times(1)`.
- **`times(n)`** is for when invocation count is part of the contract; **`never()`** forbids a specific invocation.
- **`verifyNoInteractions(mock)`** forbids all interactions on the mock; **`verifyNoMoreInteractions(mock)`** forbids any remaining unverified invocations.
- **`InOrder`** matters only when call sequence is truly required. Plain `verify` does not check order.
- **Argument matchers/captors** clarify the content sent to collaborators.
- **Mockito verifies observable mock interactions**; it does not prove full business correctness, real external side effects, or Spring dependency injection on its own.
- Verify **required behavior**, keeping tests readable, strong enough to catch bugs, and decoupled from internal implementation details.
