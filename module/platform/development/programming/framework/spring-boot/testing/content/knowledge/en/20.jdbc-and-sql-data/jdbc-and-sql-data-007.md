# Generated Keys, Batch Updates, and Database Constraints

In a Java application using JDBC, executing an `INSERT` statement without error does not mean the write workflow is correct. When the database generates primary keys automatically, the program must retrieve **generated keys** reliably; when writing multiple rows, **batch updates** must handle row counts, mid-batch failures, and transactions; and when data has relationships, **PRIMARY KEY, UNIQUE, NOT NULL, CHECK, and FOREIGN KEY** constraints must be verified against a real database rather than relying solely on `if` checks in services.

These three topics are tightly linked. Creating an invoice involves inserting one `invoice` row whose ID is generated by the database, inserting multiple `invoice_line` rows referencing that ID, and preserving data invariants even under concurrent writes. Capturing the wrong key links lines to the wrong parent. If a batch fails midway without rolling back earlier rows, data is left half-written. If you only mock `JdbcTemplate`, you **cannot prove** that the database enforces constraints and transactions accurately.

This Knowledge article sits in the **Spring Boot – testing** module, **JDBC and SQL data** group, targeting **Java 17+, Spring Boot 3.5.x, Spring JDBC, JUnit Jupiter 5, and H2**. It includes a complete sample project with `JdbcTemplate`, `NamedParameterJdbcTemplate`, `GeneratedKeyHolder`, `@JdbcTest`, `@SpringBootTest`, `@Transactional`, and SQL fixtures. H2 serves as an educational database; when production runs PostgreSQL/MySQL/SQL Server/Oracle, driver, dialect, identity, constraint, and locking behaviors must also be tested **against the target engine**.

## 1. What Will You Be Able to Do After This Lesson?

- Explain what a **generated key** is and why you must **never** predict IDs via `MAX(id)+1` or assume contiguous IDs.
- Use Spring JDBC `GeneratedKeyHolder` to obtain keys after `INSERT`, handle missing keys, and account for driver differences.
- Distinguish `JdbcTemplate.update`, `NamedParameterJdbcTemplate.update`, and `batchUpdate`.
- Interpret `int[]`/`int[][]` update count elements accurately, including `Statement.SUCCESS_NO_INFO` and `Statement.EXECUTE_FAILED`.
- Design small batches with bound parameters instead of concatenating input data into SQL strings.
- Exercise `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, and `FOREIGN KEY` constraints with real SQL.
- Use `@Transactional` at the service boundary to **roll back** when a batch fails, rather than assuming batches are automatically atomic.
- Distinguish `@JdbcTest` per-test rollback from **real service-level rollback**.
- Write regression tests catching duplicate keys, invalid amounts, lines pointing to missing parents, unexpected row counts, and partial batch failures.
- Know when H2 is sufficient and when Testcontainers or a real DB is needed to catch dialect, sequence, generated-key, and concurrency differences.

## 2. Running Scenario: Invoices and Invoice Lines

We model:

```text
invoice
 + id             BIGINT IDENTITY, PRIMARY KEY
 + external_ref   UNIQUE, NOT NULL
 + amount_minor   > 0
 + status         NEW | PAID
           |
           | 1 : n
           v
invoice_line
 + id             BIGINT IDENTITY, PRIMARY KEY
 + invoice_id     FOREIGN KEY -> invoice.id
 + sku            NOT NULL
 + quantity       > 0
 + UNIQUE(invoice_id, sku)
```

Flow for creating an invoice with two lines:

```text
HTTP/application call
    |
    v
InvoiceRegistrationService.createWithLines(...)
    |
    +-- Transaction BEGIN
    |
    +-- INSERT invoice (external_ref, amount_minor)
    |       -> database generates invoice.id
    |       -> GeneratedKeyHolder reads id
    |
    +-- batch INSERT invoice_line
    |       -> all lines use the generated invoice_id
    |
    +-- if no error: COMMIT
    +-- if constraint/batch error: ROLLBACK
```

The demo app stores **money in minor currency units** in `amount_minor` (e.g., cents), never using `double`. The focus here is JDBC and testing, not full accounting or tax rules.

## 3. What Is a Generated Key?

A table can let the database assign an ID to each row:

```sql
CREATE TABLE invoice (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    external_ref VARCHAR(64) NOT NULL UNIQUE,
    amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
    status VARCHAR(12) NOT NULL DEFAULT 'NEW'
);
```

When sending:

```sql
INSERT INTO invoice (external_ref, amount_minor)
VALUES ('INV-A', 10000);
```

the SQL omits `id`. The database uses identity/sequence or a corresponding mechanism to generate it. Java retrieves the key via the JDBC `getGeneratedKeys()` API or a Spring JDBC wrapper.

Things you **must never assume**:

- The first ID is always `1`.
- IDs are contiguous with no gaps; sequences/identities can advance even when transactions roll back.
- The next ID equals `MAX(id)+1`; that technique suffers race conditions under concurrent inserts.
- Every database supports generated keys identically or returns them under the same column name and Java type.
- Batch inserts always return IDs in input order across every driver.
- Obtaining a generated key means the transaction committed; it can still roll back afterward.

**A key is an identifier**, not necessarily a reflection of time, order, or business sequence numbers. If you need user-friendly invoice numbers, design a separate `external_ref`/business identifier with explicit uniqueness and idempotency checks.

## 4. Plain JDBC: `PreparedStatement.RETURN_GENERATED_KEYS`

In plain JDBC, the typical pattern is:

```java
// Illustrative snippet inside a method with Connection connection.
String sql = """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (?, ?)
        """;

try (PreparedStatement statement = connection.prepareStatement(
        sql, Statement.RETURN_GENERATED_KEYS)) {
    statement.setString(1, "INV-JDBC");
    statement.setLong(2, 10000L);

    int affected = statement.executeUpdate();
    if (affected != 1) {
        throw new SQLException("Expected one inserted row");
    }

    try (ResultSet keys = statement.getGeneratedKeys()) {
        if (!keys.next()) {
            throw new SQLException("No generated key returned");
        }
        long id = keys.getLong(1);
        // Use id to write invoice_line within the same transaction.
    }
}
```

Required imports: `java.sql.PreparedStatement`, `Statement`, `ResultSet`, `SQLException`. This is a **snippet**, not a standalone Java file: `connection` must be opened and transactions/cleanup managed by the caller.

Some drivers prefer specifying column names:

```java
// Plain JDBC snippet, if the driver supports column names.
connection.prepareStatement(sql, new String[] {"ID"});
```

Do not treat `Statement.RETURN_GENERATED_KEYS` as a guarantee that every DB returns keys. JDBC drivers may report lack of support or return different types/metadata. With PostgreSQL, native `INSERT ... RETURNING id` can also work well if you deliberately accept dialect coupling; with Spring JDBC, if you want a general API, start with `KeyHolder`.

## 5. Spring JDBC: `GeneratedKeyHolder`

`GeneratedKeyHolder` collects generated keys returned by the driver to `JdbcTemplate` or `NamedParameterJdbcTemplate`.

Core example:

```java
KeyHolder holder = new GeneratedKeyHolder();

int affected = named.update(
        """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (:ref, :amount)
        """,
        new MapSqlParameterSource()
                .addValue("ref", externalRef)
                .addValue("amount", amountMinor),
        holder,
        new String[] {"id"});

if (affected != 1) {
    throw new IllegalStateException(
            "Expected exactly one inserted invoice");
}

Number key = holder.getKey();
if (key == null) {
    throw new IllegalStateException(
            "Driver did not return invoice ID");
}
long invoiceId = key.longValue();
```

This is a **snippet**; section 17 contains the runnable repository class with full imports.

`"id"` in `keyColumnNames` specifies which column to retrieve. In the example's H2 database, column `id` is declared as an identity column. On other databases, verify how the driver handles column name casing or whether native `RETURNING` SQL is needed.

### 5.1. Why Is `getKey()` Sometimes Unsuitable?

`getKey()` is convenient when the holder contains **exactly one generated key** whose value is a `Number`. When a driver returns multiple columns or multiple rows, inspect `getKeys()`/`getKeyList()` and handle map key names/types instead of forcing a single result into `long`.

For instance, if a statement returns both `id` **and** `created_at`, `getKey()` may not apply; access the map by column name instead. If the driver returns no key, never "fix" it by guessing `MAX(id)`; investigate the driver/SQL/DDL and fail explicitly.

## 6. Why Not Use `SELECT MAX(id)`?

An anti-pattern:

```java
// ANTI-EXAMPLE: easily returns another transaction's ID.
jdbc.update("INSERT INTO invoice (...) VALUES (...)");
Long id = jdbc.queryForObject(
        "SELECT MAX(id) FROM invoice", Long.class);
```

Two concurrent writer threads:

```text
Thread A INSERT -> ID 101
Thread B INSERT -> ID 102
Thread A SELECT MAX(id) -> 102 (WRONG)
```

Sequences/identities are managed by the DB. Use `getGeneratedKeys()`/`KeyHolder` or `RETURNING` as appropriate. Never run a global `MAX` query to look up "the ID just inserted".

Similarly, avoid looking up the inserted row by `external_ref` if uniqueness/idempotency rules are unclear. If a request is retried, `external_ref` can intentionally collide and trigger a duplicate-key error; retry behavior must be designed explicitly (reading the existing record, idempotency keys, or returning conflict) rather than blindly treating duplicates as successful inserts.

## 7. What Is a Batch Update?

Instead of sending 1,000 individual `INSERT`/`UPDATE` statements one by one, JDBC can group multiple parameter sets into **one batch** to cut overhead and round trips:

```text
Same SQL:
INSERT INTO invoice_line (invoice_id, sku, quantity)
VALUES (:invoiceId, :sku, :quantity)

Batch:
  {invoiceId: 10, sku: BOOK, quantity: 2}
  {invoiceId: 10, sku: PEN,  quantity: 1}
  {invoiceId: 10, sku: BAG,  quantity: 1}
```

`NamedParameterJdbcTemplate.batchUpdate(String, SqlParameterSource[])` is a clean approach without managing `PreparedStatement` manually.

**Do not equate batches with transactions.**

- **Batch:** a more efficient way to transmit and execute multiple statements.
- **Transaction:** a **COMMIT/ROLLBACK** boundary protecting atomicity.
- **Constraint:** a DB rule disallowing invalid data states.

A batch can run in auto-commit mode, where earlier statements succeed before a later element fails; exact behavior depends on the driver, DB, and transaction setup. When you need "all or nothing", wrap it in a proper transaction and verify rollback against a real database.

## 8. Spring JDBC Batches with Named Parameters

Example:

```java
SqlParameterSource[] batch = new SqlParameterSource[] {
    new MapSqlParameterSource()
            .addValue("invoiceId", 10L)
            .addValue("sku", "BOOK")
            .addValue("quantity", 2),
    new MapSqlParameterSource()
            .addValue("invoiceId", 10L)
            .addValue("sku", "PEN")
            .addValue("quantity", 1)
};

int[] counts = named.batchUpdate(
        """
        INSERT INTO invoice_line (invoice_id, sku, quantity)
        VALUES (:invoiceId, :sku, :quantity)
        """,
        batch);
```

This is a **snippet**; `named` is an injected `NamedParameterJdbcTemplate`. The `counts` array has one element per parameter set in the batch.

H2 in this example normally returns `[1, 1]` (each INSERT adds one row). However, JDBC also defines **special status values**:

- `Statement.SUCCESS_NO_INFO` = `-2`: the statement succeeded, but the driver does not know the row count.
- `Statement.EXECUTE_FAILED` = `-3`: the statement failed, which may appear in some error-handling batch results.
- `0`: the statement may be valid yet affected no rows, e.g., `UPDATE ... WHERE id` matched nothing.
- Positive integer: the row count reported by the driver.

When the driver fails the batch, the API can throw `BatchUpdateException` (translated by Spring into a `DataAccessException`), optionally carrying **partial update counts** in the underlying exception depending on the driver.

Do not write portable tests assuming `assertArrayEquals(new int[]{1,1}, counts)` across **all databases**. Against H2 specifically, that is a valid expectation; across other databases, also verify **final database state** alongside driver-supported count values.

## 9. How Does a Batch UPDATE Differ from a Batch INSERT?

A batch `UPDATE` can return **`0`** for a nonexistent ID:

```java
// Snippet inside a method with NamedParameterJdbcTemplate named.
int[] counts = named.batchUpdate(
        """
        UPDATE invoice
        SET status = :status
        WHERE id = :id
        """,
        new SqlParameterSource[] {
            new MapSqlParameterSource()
                    .addValue("id", 11L)
                    .addValue("status", "PAID"),
            new MapSqlParameterSource()
                    .addValue("id", -1L)
                    .addValue("status", "PAID")
        });
```

In an H2 database containing ID 11 and no ID -1, you can receive `[1,0]`. A JDBC-level "successful" batch **does not guarantee every business entity existed**. When the contract requires every row to be updated, the service must inspect counts and report conflict/not-found within the appropriate transaction.

**Watch out for `SUCCESS_NO_INFO`:** if the driver reports `-2`, you cannot infer `1 row updated`. To confirm state for a set of IDs, run a post-condition query or use DB-appropriate SQL `RETURNING`/stored procedures.

## 10. Batch-Generated Keys: The API Exists, Yet You Must Know the Driver

Spring Framework 6.2 provides an overload `NamedParameterJdbcTemplate.batchUpdate(sql, batchArgs, generatedKeyHolder, keyColumnNames)` when the driver supports returning keys for batches.

```java
// Snippet: ONLY use once verified with integration tests on your driver.
GeneratedKeyHolder holder = new GeneratedKeyHolder();

int[] counts = named.batchUpdate(
        """
        INSERT INTO invoice (external_ref, amount_minor)
        VALUES (:ref, :amount)
        """,
        parameterSources,
        holder,
        new String[] {"id"});

List<Map<String, Object>> keyRows = holder.getKeyList();
```

`parameterSources` is a valid `SqlParameterSource[]` built beforehand. Never assume `keyRows.size() == parameterSources.length` or that `keyRows[i]` always maps to input `i` without **testing on the production driver, DB, and version**. Some drivers have limitations returning generated keys during batching, especially with rewritten batches or multi-row INSERTs.

In our runnable example, we **fetch the generated key once for the parent**, then batch-INSERT children sharing that `invoice_id`. This avoids mapping multiple generated parent IDs in a batch and makes atomicity easier to verify.

## 11. Database Constraints Are Part of the Data Contract

The tables require these constraints:

| Constraint | Guarantees | Negative Test Scenario |
|---|---|---|
| `PRIMARY KEY` | No two rows share a primary key | Manually insert duplicate ID if DDL permits |
| `UNIQUE(external_ref)` | No two invoices share a business reference | Re-insert existing `external_ref` |
| `NOT NULL` | Required field rejects SQL NULL | INSERT omitting required field or passing null |
| `CHECK(amount_minor > 0)` | Amount must be positive | Amount 0 or negative |
| `CHECK(status IN (...))` | Status belongs to valid set | Status `ARCHIVED` when schema allows only NEW/PAID |
| `FOREIGN KEY(invoice_id)` | Line must reference an existing invoice | Line using a nonexistent invoice ID |
| `CHECK(quantity > 0)` | Positive quantity | Quantity 0 |
| `UNIQUE(invoice_id,sku)` | One SKU cannot repeat within the same invoice | Two lines with the same invoice and SKU |

**App-level validation does not replace constraints.** Two concurrent requests can both check "reference does not exist yet" and then both insert; only a database `UNIQUE` constraint enforces the invariant under a race. Likewise, a service may validate quantity, yet another import job or SQL script still needs the DB `CHECK`.

**Constraints do not replace business logic.** A `CHECK` keeps amounts positive, yet it cannot prove the invoice total equals the sum of its lines. Domain/service tests remain necessary.

### 11.1. DB Dialect Notes

- PostgreSQL, H2, MySQL, and SQL Server differ in version-dependent `CHECK` support, error codes, identity/sequences, auto-increment, default values, and transactions.
- `UNIQUE` across nullable columns varies in behavior and scope by DB and index design; e.g., mark `external_ref` `NOT NULL` to avoid NULL uniqueness subtleties.
- Foreign keys may be checked immediately or deferred if the DB supports and declares them as deferrable.
- Do not treat H2 compatibility modes as proof that all production migrations and features work.

## 12. Which Spring Exceptions Do Constraint Errors Translate Into?

Spring JDBC translates driver `SQLException`s into the `DataAccessException` hierarchy. Common types:

- `DuplicateKeyException`: can be thrown on `UNIQUE`/`PRIMARY KEY` violations (subclass of `DataIntegrityViolationException`).
- `DataIntegrityViolationException`: integrity/constraint errors such as `CHECK`, `FK`, `NOT NULL`, or duplicates depending on error translation.
- `BadSqlGrammarException`: invalid SQL syntax or schema/table names.
- `CannotAcquireLockException`/`DeadlockLoserDataAccessException` or other concurrency exceptions depending on dialect and version.

**Avoid hardcoding vendor-specific exception classes in business tests** if you want tests to stay portable; asserting `DataIntegrityViolationException` fits general constraint cases. However, in adapter tests against the production DB, checking **SQLState or vendor error codes** may be needed when the contract must distinguish duplicate business refs from FK violations to return HTTP 409 vs. 422.

**Security note:** never expose raw driver SQL error messages in API responses, as they can leak table names, fields, queries, or input data. Map to **defined public error codes**, and log detailed errors in controlled channels.

## 13. Transactions and Batches: What Guarantees Atomicity?

Spring declarative transactions:

```java
@Service
public class InvoiceRegistrationService {
    private final InvoiceJdbcRepository repository;

    public InvoiceRegistrationService(
            InvoiceJdbcRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long createWithLines(
            String ref,
            long amountMinor,
            List<LineDraft> lines) {
        long id = repository.insertInvoice(ref, amountMinor);
        repository.batchInsertLines(id, lines);
        return id;
    }
}
```

This is a skeleton; the runnable Java file and imports are in section 17.

When called **through the Spring proxy**, `@Transactional` starts or joins a transaction under default `PROPAGATION_REQUIRED`. JDBC operations share the same Spring-managed `DataSource` and transaction manager, so if the batch throws a runtime `DataAccessException` that escapes the boundary, the transaction rolls back.

**Important caveats to remember:**

1. Spring rolls back on `RuntimeException` and `Error` by default, **not on checked exceptions** by default; if checked exceptions occur, configure `rollbackFor=...` or an appropriate policy.
2. Self-invocation `this.createWithLines(...)` inside the same bean **bypasses the proxy**, so annotations on the target method may not take effect.
3. Swallowing the exception and returning success can cause an unintended commit unless the transaction was marked rollback-only.
4. `@Transactional` does not turn calls across multiple databases or HTTP gateways into a single global atomic transaction.
5. Generated identities/sequences may consume key values even when the transaction rolls back; **never test for contiguous IDs**.
6. A long-running transaction spanning thousands of rows can hold locks and increase contention; choose batch sizes and transaction boundaries deliberately.

## 14. `@JdbcTest` Rollback and Service Rollback Are Two Different Checks

In Spring Boot 3.5, `@JdbcTest` typically:

- Builds only the JDBC slice, embedded test database, JDBC/SQL init, and related infrastructure.
- Does not auto-scan all out-of-slice `@Service` and `@Repository` beans; `@Import` the repository under test.
- Runs each test inside a **test-managed transaction** that rolls back after each method by default.

Hence:

```java
@JdbcTest
@Import(InvoiceJdbcRepository.class)
class InvoiceJdbcSliceTest {
    // Real DataSource + repository on test DB.
}
```

is a great fit for **generated keys, batch counts, and DDL constraints**. Still, watch out for this trap:

> Because the JUnit method is wrapped in a transaction by `@JdbcTest`, a service invoked inside it normally **joins that test transaction**. Once the method ends, Spring Test rolls back even if the service's `@Transactional` is broken. Thus, "empty DB after test" **does not prove service-level rollback**.

To verify a **service's real transaction boundary**, use a `@SpringBootTest` **without `@Transactional` on the JUnit method**, trigger an error midway through the batch, and query the DB **after the service call throws**. Reset fixtures with `@Sql` before/after tests so they do not pollute each other. The runnable code in section 20 demonstrates this cleanly.

## 16. SQL Schema and Fixture Cleanup

**`src/main/resources/schema.sql`**

```sql
CREATE TABLE invoice (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    external_ref VARCHAR(64) NOT NULL,
    amount_minor BIGINT NOT NULL,
    status VARCHAR(12) NOT NULL DEFAULT 'NEW',
    CONSTRAINT uq_invoice_external_ref UNIQUE (external_ref),
    CONSTRAINT ck_invoice_amount CHECK (amount_minor > 0),
    CONSTRAINT ck_invoice_status CHECK (status IN ('NEW', 'PAID'))
);

CREATE TABLE invoice_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    invoice_id BIGINT NOT NULL,
    sku VARCHAR(40) NOT NULL,
    quantity INT NOT NULL,
    CONSTRAINT fk_line_invoice
        FOREIGN KEY (invoice_id) REFERENCES invoice(id),
    CONSTRAINT ck_line_quantity CHECK (quantity > 0),
    CONSTRAINT uq_line_invoice_sku UNIQUE (invoice_id, sku)
);
```

With Spring Boot SQL initialization and embedded H2, `schema.sql` on the classpath runs when the test `DataSource` initializes under standard defaults. If a project already uses Flyway/Liquibase, **do not add a parallel `schema.sql`** that causes conflicts; use real migrations or a project-consistent test setup.

**`src/test/resources/cleanup.sql`**

```sql
DELETE FROM invoice_line;
DELETE FROM invoice;
```

**Deletion order matters:** lines before parent because of the foreign key. Cleanup removes rows without **resetting identity/sequences**; tests never rely on fixed IDs.

In real applications, destructive cleanup scripts must **only ever run against a dedicated test database**. Never include this cleanup in shared or production configurations.

**`src/main/java/com/example/invoicejdbc/InvoiceJdbcRepository.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.namedparam.MapSqlParameterSource;
import org.springframework.jdbc.core.namedparam.NamedParameterJdbcTemplate;
import org.springframework.jdbc.core.namedparam.SqlParameterSource;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

@Repository
public class InvoiceJdbcRepository {

    private final NamedParameterJdbcTemplate named;
    private final JdbcTemplate jdbc;

    public InvoiceJdbcRepository(
            NamedParameterJdbcTemplate named,
            JdbcTemplate jdbc) {
        this.named = named;
        this.jdbc = jdbc;
    }

    public long insertInvoice(
            String externalRef, long amountMinor) {
        String sql = """
                INSERT INTO invoice (external_ref, amount_minor)
                VALUES (:ref, :amount)
                """;

        MapSqlParameterSource parameters =
                new MapSqlParameterSource()
                        .addValue("ref", externalRef)
                        .addValue("amount", amountMinor);

        KeyHolder holder = new GeneratedKeyHolder();

        int count = named.update(
                sql, parameters, holder, new String[] {"id"});

        if (count != 1) {
            throw new IllegalStateException(
                    "Expected one inserted invoice");
        }

        Number key = holder.getKey();
        if (key == null) {
            throw new IllegalStateException(
                    "Generated invoice ID was not returned");
        }
        return key.longValue();
    }

    public int[] batchInsertLines(
            long invoiceId, List<LineDraft> drafts) {

        SqlParameterSource[] args =
                new SqlParameterSource[drafts.size()];

        for (int i = 0; i < drafts.size(); i++) {
            LineDraft line = drafts.get(i);
            args[i] = new MapSqlParameterSource()
                    .addValue("invoiceId", invoiceId)
                    .addValue("sku", line.sku())
                    .addValue("quantity", line.quantity());
        }

        return named.batchUpdate(
                """
                INSERT INTO invoice_line
                    (invoice_id, sku, quantity)
                VALUES (:invoiceId, :sku, :quantity)
                """,
                args);
    }

    public int[] batchMarkPaid(List<Long> ids) {
        SqlParameterSource[] args =
                new SqlParameterSource[ids.size()];

        for (int i = 0; i < ids.size(); i++) {
            args[i] = new MapSqlParameterSource()
                    .addValue("id", ids.get(i))
                    .addValue("status", "PAID");
        }

        return named.batchUpdate(
                """
                UPDATE invoice
                SET status = :status
                WHERE id = :id
                """,
                args);
    }

    public int countInvoices() {
        Integer count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice", Integer.class);
        return count == null ? 0 : count;
    }

    public int countLines() {
        Integer count = jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line", Integer.class);
        return count == null ? 0 : count;
    }
}
```

**Code explanation:**

- Uses **named parameters** instead of SQL string concatenation; `ref`, `sku`, and `quantity` values are bound safely.
- `new String[]{"id"}` tells the driver to return the `id` column's key; `holder.getKey()` checks for null.
- Batch lines receive the **exact generated `invoiceId`** from the parent.
- Does not guess sequential IDs or read `MAX(id)`.
- Batch `UPDATE` exposes row counts, including zero for missing IDs.
- `countInvoices()` and `countLines()` are simple helpers for integration tests; production code typically separates query DAOs/metrics as needed.
- An empty list creates `SqlParameterSource[0]`; in Spring JDBC 6.2, `NamedParameterJdbcTemplate.batchUpdate` with empty input returns an empty count array. In production services, decide whether a line-less invoice is valid; the current constraints **do not enforce a minimum line count**.

### 17.1. This Code Does Not Handle Every Production Edge Case

To keep the exercise focused, the repository omits validation for blank SKUs, domain amount overflow, `external_ref` duplicate idempotency, deadlock retries, metrics, and tracing. Those belong to the application service and adapter policies. Database constraints remain the final guardrail for declared invariants.

## 18. Service Transaction: Parent and Children Must Commit Together

**`src/main/java/com/example/invoicejdbc/InvoiceRegistrationService.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class InvoiceRegistrationService {

    private final InvoiceJdbcRepository repository;

    public InvoiceRegistrationService(
            InvoiceJdbcRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public long createWithLines(
            String externalRef,
            long amountMinor,
            List<LineDraft> lines) {

        long id = repository.insertInvoice(
                externalRef, amountMinor);
        repository.batchInsertLines(id, lines);
        return id;
    }
}
```

When `service.createWithLines(...)` is called externally through the Spring proxy, Spring's transaction manager wraps both the parent INSERT and child batch INSERT. If a child constraint fails and the exception propagates, both the parent and any previously inserted children roll back.

Additional **scenarios worth testing in production**:

- Should an empty child list be allowed? The current schema does not forbid zero-line invoices; if disallowed, validate before the transaction or enforce a business invariant.
- If the service publishes an event to Kafka before commit, a JDBC rollback cannot recall the published event; use the outbox pattern or a consistency strategy.
- If the method is self-invoked from the same bean (`this.createWithLines(...)`), `@Transactional` proxy interception may be skipped.
- When multiple DataSources/transaction managers exist, ensure the right transaction manager is selected for the repository.
- Duplicate keys can support idempotent creation, though you must never blindly treat duplicates as success if the payload differs from the contract.

## 19. `@JdbcTest`: Generated Keys, Batch Counts, and Real Constraints

**`src/test/java/com/example/invoicejdbc/InvoiceJdbcSliceTest.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.JdbcTest;
import org.springframework.context.annotation.Import;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.JdbcTemplate;

import static org.junit.jupiter.api.Assertions.assertArrayEquals;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

@JdbcTest
@Import(InvoiceJdbcRepository.class)
class InvoiceJdbcSliceTest {

    @Autowired
    InvoiceJdbcRepository repo;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void generatedKeyIdentifiesInsertedParent() {
        long id = repo.insertInvoice("INV-KEY", 10_000L);

        assertTrue(id > 0);
        assertEquals("INV-KEY", jdbc.queryForObject(
                "SELECT external_ref FROM invoice WHERE id = ?",
                String.class, id));
    }

    @Test
    void batchInsertCreatesExpectedLines() {

                SELECT sku FROM invoice_line
                WHERE invoice_id = ?
                ORDER BY id
                """,
                String.class, id);

        assertEquals(List.of("BOOK", "PEN"), skus);
    }

    @Test
    void rejectsDuplicateBusinessReference() {
        repo.insertInvoice("INV-DUP", 100L);

        assertThrows(DataIntegrityViolationException.class,

    }

    @Test
    void checkConstraintRejectsNonPositiveAmount() {
        assertThrows(DataIntegrityViolationException.class,
                () -> repo.insertInvoice("INV-ZERO", 0L));
    }

    @Test
    void childConstraintsRejectBadQuantityAndMissingParent() {
        long id = repo.insertInvoice("INV-CHILD", 500L);

    }

        long id = repo.insertInvoice("INV-UNIQUE-LINE", 900L);

        repo.batchInsertLines(
                id, List.of(new LineDraft("BOOK", 1)));

        assertThrows(DataIntegrityViolationException.class,
                () -> repo.batchInsertLines(
                        id, List.of(new LineDraft("BOOK", 2))));
    }

    @Test
    void batchUpdateReportsMatchedAndUnmatchedIds() {
        long a = repo.insertInvoice("INV-A", 100L);
        long b = repo.insertInvoice("INV-B", 200L);

        int[] counts = repo.batchMarkPaid(
                List.of(a, b, -1L));

        // Assertion specific to H2 in the sample project.
        assertArrayEquals(new int[] {1, 1, 0}, counts);

        assertEquals("PAID", jdbc.queryForObject(

                String.class, a));
        assertEquals("PAID", jdbc.queryForObject(
                "SELECT status FROM invoice WHERE id = ?",
                String.class, b));
    }

```

### 19.1. What Does This Test Suite Prove?

- `generatedKeyIdentifiesInsertedParent`: `KeyHolder` returns a usable key that queries the exact row, without needing to know whether the ID is `1` or `157`.
- `batchInsertCreatesExpectedLines`: both lines are inserted with the right parent; the H2 driver reports two update counts of `1`.
- Duplicate `external_ref` is rejected by the real database.
- `CHECK(amount_minor>0)` is enforced by the database.
- Invalid quantity and missing FK parent are both rejected.
- `UNIQUE(invoice_id,sku)` blocks two lines with the same SKU in one invoice.
- Batch UPDATE applies changes to the two existing IDs and leaves the nonexistent negative ID unaffected.

**There are 7 `@Test` methods.** Because `@JdbcTest` defaults to test-managed transaction rollback, these tests need no manual cleanup between methods, and **you must never assert that identity always starts at 1**.

### 19.2. What These Tests Do Not Prove Yet

- Rollback of `InvoiceRegistrationService` using a **service-managed transaction**.
- Production PostgreSQL/MySQL JDBC constraints where they differ from H2.
- Interleavings, locking, and deadlocks across concurrent transactions.
- Production driver generated-key behavior when batching multiple parents simultaneously.
- Side effects on queues, payment gateways, or external services.
- HTTP 409 APIs, GraphQL errors, or message clients; this is the JDBC layer.

## 20. `@SpringBootTest`: Verifying Real Rollback on Mid-Batch Failure

**`src/test/java/com/example/invoicejdbc/InvoiceTransactionIntegrationTest.java`**

```java
package com.example.invoicejdbc;

import java.util.List;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.jdbc.Sql;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.junit.jupiter.api.Assertions.assertTrue;

@SpringBootTest(classes = InvoiceJdbcApplication.class)
@Sql(scripts = "/cleanup.sql",
        executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
@Sql(scripts = "/cleanup.sql",
        executionPhase = Sql.ExecutionPhase.AFTER_TEST_METHOD)
class InvoiceTransactionIntegrationTest {

    @Autowired
    InvoiceRegistrationService service;

    @Autowired
    JdbcTemplate jdbc;

    @Test
    void createsParentAndAllChildrenInOneTransaction() {
        long id = service.createWithLines(
                "INV-COMPLETE", 60_000L,
                List.of(
                        new LineDraft("BOOK", 2),
                        new LineDraft("PEN", 1)));

        assertTrue(id > 0);
        assertEquals(1, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice",
                Integer.class));
        assertEquals(2, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line",
                Integer.class));
    }

    @Test
    void failureInBatchRollsBackParentAndPartialChildren() {
        assertThrows(DataIntegrityViolationException.class,
                () -> service.createWithLines(
                        "INV-ROLLBACK", 60_000L,
                        List.of(
                                new LineDraft("BOOK", 1),
                                new LineDraft("BOOK", 2))));

        // Do not attach @Transactional to the JUnit test method:
        // inspect DB state after the service proxy handles the error.
        assertEquals(0, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice",
                Integer.class));
        assertEquals(0, jdbc.queryForObject(
                "SELECT COUNT(*) FROM invoice_line",
                Integer.class));
    }
}
```

### 20.1. The Most Important Point

`InvoiceTransactionIntegrationTest` **does not put `@Transactional` on the test methods**. It invokes the real service bean through the Spring container; the service itself carries `@Transactional`. When the second child in the batch duplicates `(invoice_id,sku)`, the database raises a constraint error, the runtime `DataIntegrityViolationException` escapes the service, and the transaction manager rolls back the entire transaction.

After the exception returns to the JUnit thread, the test queries the DB: **no parent, no children**. This is genuine proof that the service's transaction boundary works for a mid-batch failure scenario.

The two `@Sql` scripts before and after each method keep fixtures clean between methods and after tests. Identity values can still increment across rolled-back/cleaned runs, so the test only checks `id > 0`.

### 20.2. Why Does H2-Based Rollback Testing Have Limits?

It verifies Spring transactions + JDBC + H2 in the demo setup. PostgreSQL handles post-statement errors differently from H2 (a transaction can remain in an error state until rollback); MySQL isolation and engine semantics also differ. In real systems, run integration tests on **the target database engine and version** to protect transactions, constraints, locking, and migrations.

### 20.3. What Happens Without a Transaction?

If `@Transactional` is removed and JDBC runs in auto-commit mode:

1. The parent `INSERT` can commit.
2. The first element of the child batch can commit / be accepted.
3. The second element violates `UNIQUE`.
4. Data is left partially written.

Exact partial-commit behavior for batches depends on the driver, connection, and DB; never invent a guarantee like "one line is always committed" across all databases. Section 20's test intentionally verifies **nothing remains when the service transaction is right**.

## 21. Batch Size, Performance, and Resource Management

Bigger batches are not always better. With 100,000 rows, a huge batch can:

- Hold locks too long and stretch out the transaction.
- Consume excessive memory for parameter arrays, driver buffers, or result sets.
- Exceed database/driver packet or statement size limits.
- Make logging, retries, and pinpointing the failing input harder.
- Contend with concurrent transactions.
- Increase the risk of timeouts or network disconnects mid-batch.

**Practical approach:** start with chunk sizes like `100`, `500`, or `1,000` (merely starting points, not universal optima), and measure throughput, lock waits, error rates, and memory under realistic workloads and drivers.

Spring JDBC offers this overload:

```java
// Snippet assuming JdbcTemplate jdbc and Collection<Row> rows.
int[][] counts = jdbc.batchUpdate(
        """
        UPDATE invoice
        SET status = ?
        WHERE id = ?
        """,
        rows,
        500,
        (ps, row) -> {
            ps.setString(1, row.status());
            ps.setLong(2, row.id());
        });
```

`Row` here is an illustrative type with `status()`/`id()`, undefined here; this is **not a standalone runnable file**. This overload returns `int[][]`, one count array per chunk. To verify the whole result, aggregate across chunks and apply proper handling for `SUCCESS_NO_INFO`, `0`, and exceptions.

Do not split a transaction into hundreds of separate commits when business rules demand all-or-nothing. Conversely, avoid holding a single transaction open for minutes to make a huge file import atomic when the product can support resume/checkpointing; design **idempotent chunks** and clear recovery rules instead.

## 22. Generated Keys in Batches and Concurrency

Key failure modes:

1. **Driver returns no keys in a batch:** the right number of rows insert, yet the holder is empty or missing keys.
2. **Key order differs from assumption:** mapping input records ↔ generated IDs breaks.
3. **Identity gaps:** rollbacks and failed inserts still consume sequence values.
4. **Concurrent inserts:** two threads create invoices; generated IDs do not strictly reflect request arrival order.
5. **Duplicate `external_ref`:** client retries trigger unique violations; do not generate a fresh `external_ref` if idempotency is required.
6. **Transaction isolation:** querying after insert inside the same transaction sees the row, while another transaction may not see it before commit.
7. **UUID vs. identity:** apps using client-generated UUIDs may not need DB-generated keys, yet still require uniqueness and transaction tests.

**Testing solution:** on the production driver, seed inputs with stable business references, batch-insert, query back by business reference, and verify key ↔ row mapping—do not assert only `keyList.size()`. In the demo code, inserting each parent individually to retrieve its key and then batching children is easier to review and far less driver-dependent.

## 23. Duplicate Keys, Idempotency, and HTTP 409

Suppose a client retries an invoice creation request with `external_ref="ORDER-2026-7"`. The database reports a `UNIQUE` violation on the second attempt.

You must decide the business contract:

- **Conflict:** return `409` with a stable error code if the key collides with a different payload or retries are unsupported.
- **Idempotent replay:** if both idempotency key and payload match, return the previously created result per specification.
- **Upsert:** use `INSERT ... ON CONFLICT` or `MERGE` with reviewed semantics, never blindly to mask duplicates.

Never do:

```java
try {
    repository.insertInvoice(ref, amount);
} catch (DuplicateKeyException ignored) {
    return 1L; // ANTI-EXAMPLE: fabricated ID, integrity lost.
}
```

This is an **intentionally wrong snippet**. If idempotency is required, query and inspect the existing record by unique key, verify payload compatibility, test concurrency, and return the real ID within an appropriate transaction.

**Why is DB `UNIQUE` alone not enough for idempotency?** It prevents two rows with the same reference, yet it does not specify what result the client should receive, whether external side effects should repeat, or how to reject identical keys carrying different content.

## 24. Common Transaction Traps

### 24.1. Self-Invocation Bypasses the Proxy

```java
@Service
class ExampleService {

    void outer() {
        createWithLines(); // internal call: may bypass proxy.
    }

    @Transactional
    public void createWithLines() {
        // JDBC writes
    }
}
```

This is an illustrative snippet. When bypassing the proxy, `@Transactional` on the target method may have no effect. Place the boundary on a public method invoked by another bean, or refactor the service structure.

### 24.2. Swallowing Exceptions

```java
@Transactional
public void create() {
    try {
        repository.batchInsertLines(...);
    } catch (DataAccessException error) {
        log.warn("Ignoring DB error"); // ANTI-EXAMPLE
    }
}
```

If the exception does not leave the transaction and the transaction is not marked rollback-only, the resulting commit can violate intent. Do not treat this snippet as runnable code; it lacks a real repository and context. If per-row recovery is needed, design explicit inner transactions, savepoints, or a partial-success contract.

### 24.3. Checked Exceptions Do Not Roll Back by Default

`@Transactional` rolls back on `RuntimeException`/`Error` by default, not checked exceptions by default. When a use case needs a checked exception to roll back, use `@Transactional(rollbackFor = SomeCheckedException.class)` or an equivalent policy. Never assume every Java `Exception` triggers rollback.

### 24.4. Test-Level Transactions Mask Bugs

A `@JdbcTest` leaving an empty DB after the method **does not** prove the service is atomic; that can simply be the test rollback. To guard service transactions, run tests without wrapping the test method in a transaction and assert database state after failure (section 20).

### 24.5. Not All Side Effects Share the Same Database

A JDBC transaction cannot roll back an HTTP call, Kafka event, or email already sent. When writing to a DB and emitting events, use an outbox/saga or intentional consistency strategy, and add adapter/end-to-end tests based on risk.

## 25. Do Not Assert Only the Exception — Verify Post-Conditions

A weak test:

```java
assertThrows(DataIntegrityViolationException.class,
        () -> service.createWithLines(...));
```

proves only **that an exception was thrown**; it does not prove:

- The parent rolled back.
- Earlier children in the batch rolled back.
- Records with other `external_ref` values stayed intact.
- No duplicate events or external side effects escaped.

Section 20's test is stronger because it asserts `count(invoice)==0` and `count(invoice_line)==0` **after the exception**. In real applications, also verify unaffected rows, record versions, audit/outbox tables, and isolation per business invariants. If other test data exists in the table, do not assert total count = 0; query by the test's own fixtures or business keys.

**In transactional tests, post-condition queries must observe from the right boundary.** A select run inside a test transaction about to roll back can still see uncommitted rows and fails to prove post-rollback state. That is why real rollback tests use `@SpringBootTest` without test-level `@Transactional`.

## 26. SQL Fixtures, Migrations, and Real Databases

### 26.1. H2 Is a Test Double for the Database Engine

H2 runs fast and works well for learning basic SQL, generated identities, common constraints, and JDBC APIs. However, when production uses PostgreSQL/MySQL, differences can emerge in:

- Generated keys and `RETURNING` syntax.
- Constraint behavior and SQLState error codes.
- Case folding and quoted identifiers.
- Isolation levels, locks, and deadlocks.
- Index/unique semantics with NULLs.
- Datetime/timestamp precision and timezones.
- Batch rewrites and parameter limits.
- Triggers, stored procedures, and deferred constraints.
- JSONB, ARRAY, UPSERT syntax, and vendor-specific types.

**High confidence for database-specific behavior requires testing on the matching engine and version**, typically via Testcontainers. Do not treat H2 compatibility mode as full proof of Postgres-specific syntax or locking.

### 26.2. Keep Real Migrations as the Source of Truth

If the project uses Flyway/Liquibase, let integration tests run the real migrations rather than maintaining a duplicate `schema.sql` that easily drifts out of sync. In this demo, `schema.sql` is the DDL source because no migration framework is used.

Whenever adding a new constraint, tests must exercise **the real constraint in the test schema**, not rely merely on reading SQL during code review. If a production migration did not run against the test DB, tests can pass falsely.

### 26.3. Testcontainers with Spring Boot (Extension)

For PostgreSQL, you can use a PostgreSQL Testcontainer with `@ServiceConnection`/`@DynamicPropertySource` depending on your Spring Boot version and test infrastructure. That setup is **not included in this article's runnable H2 project**; it requires a Docker runtime, pinned image/version, migrations, cleanup, and CI policy.

Never point test URLs or ordinary test accounts at a production DB. Destructive data, constraint, and rollback tests must run strictly on a **database provisioned for testing**.

## 27. Testing Race Conditions on UNIQUE and FK Constraints

A sequential test with duplicate `external_ref` proves basic `UNIQUE` enforcement, yet does not fully verify correctness under concurrent inserts. Under concurrent requests:

1. Two transactions both read "no `external_ref` exists yet".
2. Both attempt to `INSERT`.
3. Database `UNIQUE` ensures both cannot commit duplicate keys.
4. One transaction succeeds while the other receives a conflict/unique violation (depending on timing/isolation).

To write meaningful concurrency tests:

- Use the real database engine with production isolation and unique indexes.
- Use barriers/latches so two threads start together after setup.
- Set finite timeouts so tests never hang.
- Assert **final row count** is exactly one and verify public conflict/idempotency behavior.
- Never assert "thread 1 always wins" because OS scheduling is non-deterministic.
- Retry appropriately on lock/deadlock/serialization errors, never blindly on all integrity violations.

Testing `List.of("A","A")` in a single batch **does not substitute for** a concurrency test. That checks constraints/transactions when **a single request** supplies duplicate items.

## 28. Anti-Patterns to Eliminate

| Anti-Pattern | Consequence | Right Approach |
|---|---|---|
| `SELECT MAX(id)` after INSERT | Race condition, steals another transaction's ID | Generated keys / `RETURNING` |
| Assuming keys always start at 1 | Tests break from identity gaps or parallel runs | Assert `key > 0` and query row by key |
| Using `batchUpdate` without a transaction when atomicity is needed | Partial writes on failure | Service `@Transactional` + rollback test |
| Assuming `counts[i]==1` across every driver | Fails or misleads on `-2` | Driver-specific tests + post-condition queries |
| Concatenating client values into SQL strings | SQL injection, quoting/encoding bugs | Prepared statements / named params |
| Mocking `JdbcTemplate` and claiming constraints work | Real DB constraints never run | `@JdbcTest` with a test DB |
| Omitting `UNIQUE` because the service checks first | Race between concurrent requests | DB `UNIQUE` + business conflict mapping |
| Using H2 to claim Postgres-specific locking works | Different dialect/isolation | Testcontainers real engine |
| Catching exceptions and returning success | Commits half-written data | Propagate/rollback or explicit recovery |
| Putting `@Transactional` on a test to "prove" service rollback | Test rollback hides broken service boundary | Full test without test transaction, assert after error |
| Updating the whole table in a SQL batch | Huge blast radius if WHERE is wrong | Explicit WHERE in SQL, test matched IDs |
| Treating duplicate key as idempotent without checking payload | Returns wrong result, masks conflict | Unique key + idempotency contract |
| Fetching batch generated keys and blindly zipping with input | Mapping breaks if driver does not guarantee order | Integration test verifying via business ref |
| Storing real passwords/PII in SQL fixtures | Data leak | Minimal synthetic fixtures |
| Running cleanup deletes on a shared DB | Risk of data loss | Isolated test DB, least-privilege roles |

## 29. Troubleshooting JDBC Errors

### 29.1. `KeyHolder.getKey()` Is Null

Possible causes: SQL is not an INSERT with a generated key, driver has not enabled returning generated keys, wrong column name, or schema does not auto-generate keys. Inspect DDL, `keyColumnNames`, driver metadata, and `holder.getKeys()`. Never replace it with `MAX(id)`.

### 29.2. `KeyHolder.getKey()` Throws Because Multiple Keys Returned

The statement may return multiple columns or multiple rows. Use `getKeys()`/`getKeyList()` and verify exact mapping against the real driver and SQL. For single-parent inserts, specifying column `"id"` reduces ambiguity.

### 29.3. Batch Returns `-2`

This may be `Statement.SUCCESS_NO_INFO`: succeeded without a specific row count, **not a failure**. Query final database state whenever business rules require confirming exact row counts.

### 29.4. Batch Throws an Exception Midway

Inspect root `SQLException`/SQLState, update counts if provided by the driver, the violated constraint, and the transaction boundary. Inside a proper service transaction, the entire batch/parent rolls back; do not blindly retry everything if external side effects could duplicate.

### 29.5. `BadSqlGrammarException` on H2 While Production SQL Works

Dialect differences: `RETURNING`, `ON CONFLICT`, identity syntax, or reserved words. Test on the production DB engine to protect dialect syntax. Never rewrite production schemas merely to appease H2 if real migrations become incompatible.

### 29.6. `DataIntegrityViolationException` During Line Insert

Check FK parent ID, duplicate `(invoice_id, sku)`, quantity, and `NOT NULL`. Query already-written records (inside an appropriate test transaction) and inspect SQLState; never log sensitive payloads to CI.

### 29.7. Test Passes Alone but Fails in the Suite

Common causes: shared H2 DB name, missing `@Sql` cleanup, context caching, parallel tests sharing tables, identity assumptions, or test order dependence. Isolate databases/fixtures and remove unneeded shared writes; avoid solving it with `@TestMethodOrder` unless ordering is an actual requirement.

### 29.8. Transaction Does Not Roll Back as Expected

Verify the method is invoked through the proxy, `@Transactional` is on a public boundary, which Spring transaction manager is active, which `DataSource` supplies connections, whether exceptions are swallowed, and the propagation setting. Especially check whether the JUnit test itself has `@Transactional` masking the real behavior.

## 30. Self-Assessment Exercises

### Exercise A — Auto-Generated Keys

Two threads insert nearly simultaneously. A developer runs `SELECT MAX(id)` to find the newly inserted ID. Explain why that is wrong and fix it with `KeyHolder`. Can tests assert IDs increment contiguously?

**Answer:** No; `MAX` can return a key issued by another transaction. Retrieve the statement's own generated key. Gaps caused by rollbacks/sequences are normal.

### Exercise B — Batch Counts

A batch `UPDATE` of three IDs returns `[1, 0, -2]`. Interpret each value. Can you conclude all three rows were updated once?

**Answer:** No. `1` means one row affected, `0` means no row affected, `-2` means `SUCCESS_NO_INFO`; handle unmatched IDs explicitly and verify post-conditions.

### Exercise C — Database Constraints

Create an invoice with `amount_minor=0`. If the service does not validate it, will the DB reject it? Which test in the example guards this?

**Answer:** `CHECK(amount_minor>0)` rejects it; `checkConstraintRejectsNonPositiveAmount` tests it against real H2 in `@JdbcTest`.

### Exercise D — FK and Generated Keys

A parent has a DB-generated ID, and the child hardcodes `42`. The test passes when H2 happens to assign ID 42. Is this valid?

**Answer:** No. Read `KeyHolder`, pass the real ID, and assert the child's `invoice_id` matches the received key.

### Exercise E — Rollback

A service inserts a parent and batches two lines with the same SKU; the second line violates `UNIQUE`. `@JdbcTest`'s final rollback leaves the DB empty. Does that prove the service's `@Transactional` works?

**Answer:** Not yet. Run a test outside any test-managed transaction, invoke the real service proxy, and query the DB **after failure**. `InvoiceTransactionIntegrationTest` demonstrates this.

### Exercise F — H2 vs. PostgreSQL

H2 tests pass while production runs `INSERT ... ON CONFLICT RETURNING`. Should you trust SQL compatibility? What should be added?

**Answer:** No. That is dialect-specific SQL; add PostgreSQL Testcontainers tests covering migrations, generated keys, and transactions.

### Exercise G — UNIQUE Under Concurrency

Two requests carry the same `external_ref`, and both check `SELECT COUNT(*)==0` before `INSERT`. Why is `UNIQUE` still needed? What should the final test assert?

**Answer:** Both can read 0 concurrently; `UNIQUE` ensures only one row succeeds. Concurrency tests should assert strictly one final row and defined conflict/idempotency behavior.

### Exercise H — Batch Status

A batch returns `[1,1,0]` yet the service reports "3 invoices paid". What is the bug? How do you fix the service or assertions?

**Answer:** The third ID did not match; if the contract requires all IDs to exist, that is a conflict/not-found. The service must verify row counts or DB state and roll back/report error appropriately; note that drivers may return `SUCCESS_NO_INFO`.

### Exercise I — External Side Effects

Inside the invoice-creation transaction, the service sends an email before `COMMIT`; the child batch fails and the DB rolls back. Is the email recalled?

**Answer:** No. A JDBC transaction does not roll back emails. Use outbox/after-commit/idempotent workflow patterns and test failure modes.

## 31. Final Checklist

- [ ] I distinguish real generated keys from business references and never use `MAX(id)+1`.
- [ ] `INSERT` statements use `KeyHolder` or `RETURNING` per driver support.
- [ ] Tests never assume IDs start at 1, are contiguous, or match commit order.
- [ ] Handled cases where `KeyHolder` returns no key or multiple keys.
- [ ] Batches use prepared/bound parameters without concatenating input directly into SQL.
- [ ] I know `int[]` counts can contain `0`, `-2`, `-3`, or raise exceptions.
- [ ] Every batch defines rules for unmatched `UPDATE` IDs.
- [ ] When all-or-nothing is required, `@Transactional` sits at the proper service boundary.
- [ ] Tests verify rollback after failure without being masked by `@JdbcTest` rollback.
- [ ] DDL declares `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, and `FOREIGN KEY` per invariants.
- [ ] Tests verify constraints on a real database rather than mocked JDBC calls.
- [ ] `external_ref` has an explicit duplicate/idempotency policy.
- [ ] Raw DB constraint error messages are never leaked to HTTP APIs.
- [ ] Test data is isolated and cleanup never runs against shared DBs.
- [ ] Test SQL schemas match real migrations; different DB engines are tested accurately.
- [ ] Batch size and transaction size are tuned to workload rather than guessed.
- [ ] Concurrency and locking/deadlocks are tested separately where risk is high.
- [ ] Multi-row batch generated keys are verified driver-specifically before mapping.
- [ ] Never emit external events/emails expecting JDBC rollback to undo them.
- [ ] Tests preserve clear boundaries: JDBC slice for repository/constraints, full context for real transactions, adapter/HTTP tests when needed.

**Conclusion:** Generated keys return database-assigned IDs for exact INSERT statements, batch updates reduce round-trip overhead when writing multiple rows, and database constraints form an integrity barrier that service validation alone cannot replace. All three combine safely only with **proper transaction boundaries**, meaningful handling of **row counts and exceptions**, and tests running **against a real database at the right level**. `@JdbcTest` fits KeyHolder/batch/constraint verification well, while proving service rollback requires keeping JUnit transactions from masking results. For production SQL dialects and concurrency, upgrade testing to the real database engine before trusting a green H2 run to prove everything.
