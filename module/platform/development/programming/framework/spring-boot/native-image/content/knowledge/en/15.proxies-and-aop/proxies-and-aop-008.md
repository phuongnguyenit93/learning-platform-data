# Libraries that generate bytecode at runtime and finding compatible integrations

Many Java frameworks create new classes while the application is running to implement proxies, AOP, lazy loading, interception, serialization, or method call optimization. On a standard JVM, a library can generate bytecode and define classes through a class loader. This approach is flexible, but creates challenges for **GraalVM Native Image** because the native executable is analyzed and compiled before running.

With Native Image, distinguish two things:

- **Metadata for dynamic access** describes classes, methods, fields, resources, or proxy interface sets that the program will access dynamically.
- **Runtime bytecode generation** creates a new class file while the program is running.

Reachability metadata can solve the first case. It **does not automatically turn an arbitrary bytecode-generating library into a native-compatible library**. To integrate successfully, use AOT mechanisms supported by the framework, move class generation to build time, change how proxies are implemented, or use a specialized GraalVM feature with known limitations.

## 1. Why do libraries generate bytecode?

Libraries can generate new classes instead of pre-writing every implementation. For example:

- Spring AOP creates proxies to apply transactions, security, caching, or advice.
- CGLIB creates subclasses to intercept methods on a specific class.
- Byte Buddy creates subclasses, interceptors, or classes for instrumentation.
- Javassist and ASM manipulate class files or bytecode directly.
- ORMs can use proxies for lazy loading or enhancement to track entity changes.
- Mocking frameworks can generate fake implementations for testing.
- RPC or serialization libraries can generate adapters/proxies for interfaces and schemas.

The benefit of this approach is generating implementations tailored to data types, annotations, configurations, or interfaces known only at runtime. On the JVM, a class loader can define a new class and the JVM will verify, link, and load it when needed.

General example:

~~~java
Class<?> proxyType = proxyGenerator.createProxyClass(
    PaymentService.class,
    interceptor
);

Object proxy = proxyType.getDeclaredConstructor()
    .newInstance();
~~~

`proxyGenerator` may use Byte Buddy, CGLIB, Javassist, or ASM code to produce the class file. The issue for Native Image is that this new class does not yet exist in the class set analyzed at build time, so the compiler cannot automatically include it in the executable.

## 2. Distinguishing proxies, reflection, and bytecode generation

Three concepts often appear together but are not synonymous:

| Mechanism | What it does | What Native Image needs |
|---|---|---|
| Reflection | Looks up classes/members or invokes constructors/methods/fields | Reachability metadata when analysis cannot infer it |
| JDK dynamic proxy | Creates an implementation of one or more interfaces via `java.lang.reflect.Proxy` | Proxy interface list must be determined at build time or registered |
| Class-based proxy | Creates a subclass of the target class, often with CGLIB or Byte Buddy | Proxy class must be pre-generated by the framework or have suitable support |
| Arbitrary bytecode generation | Generates bytecode from data and defines a new class via a class loader | Must move to build time or use a supported special feature; reflection hints alone are not enough |
| Instrumentation | Modifies loaded classes or attaches an agent to transform bytecode | Depends on runtime capabilities; cannot assume HotSpot-like behavior |

For example, declaring reflection for `PaymentService`'s constructor does not make Byte Buddy generate `PaymentServiceProxy`. Likewise, declaring a proxy hint for an interface does not mean GraalVM supports every subclass generated by CGLIB from an arbitrary class.

## 3. Native Image's default model

Native Image statically analyzes reachable execution paths from entry points and dependencies. Required classes, methods, and metadata must be identified before the executable is built.

~~~mermaid
flowchart TD
    A["Source + dependencies"] --> B["Spring AOT / build plugins"]
    B --> C["Pre-generated class files and proxies"]
    C --> D["GraalVM reachability analysis"]
    E["Runtime hints / proxy metadata"] --> D
    D --> F["Native executable"]
    F --> G["Run prepared classes and proxies"]
    H["Arbitrary runtime bytecode generation"] -. "Not in default flow" .-> I["Class loader / defineClass"]
    I -. "Class missing from image" .-> G
~~~

In the default model, the native executable does not embed a full JVM compiler to accept and define arbitrary bytecode after startup. Therefore, a library calling `ClassLoader.defineClass`, `MethodHandles.Lookup.defineClass`, `Enhancer.create()`, or `ByteBuddy.make().load()` at runtime can fail, even if the same code runs normally on HotSpot.

GraalVM has dedicated mechanisms for dynamic proxies, predefined classes, and certain experimental runtime class loading features. They have specific scopes and conditions; do not treat them as a general-purpose JVM inside the native executable.

## 4. JDK dynamic proxies: the pre-preparable case

JDK proxies create a class implementing a given set of interfaces:

~~~java
public interface PaymentOperations {
    Receipt charge(String orderId);
}

public final class PaymentInvocationHandler
        implements InvocationHandler {

    private final PaymentOperations target;

    public PaymentInvocationHandler(PaymentOperations target) {
        this.target = target;
    }

    @Override
    public Object invoke(
            Object proxy,
            Method method,
            Object[] args) throws Throwable {
        return method.invoke(target, args);
    }
}
~~~

Creating the proxy on the JVM:

~~~java
PaymentOperations proxy = (PaymentOperations) Proxy.newProxyInstance(
    PaymentOperations.class.getClassLoader(),
    new Class<?>[] { PaymentOperations.class },
    new PaymentInvocationHandler(target)
);
~~~

Native Image can detect some `Proxy.newProxyInstance` and `Proxy.getProxyClass` calls when the interface set can be determined at build time. In that case, the proxy class is pre-generated and included in the image.

If the interface set is decided by runtime configuration or an overly dynamic code path, proxy metadata must be declared. Interface order is also part of the proxy definition: the same interfaces in a different order can correspond to different proxy classes.

**JDK proxies fit well when interface contracts are stable.** They are usually much easier to integrate natively than a library that must generate arbitrary subclasses at runtime.

## 5. Spring AOT generates bytecode before native compilation

Spring AOT does not only generate Java sources and runtime hints. AOT output can also include **bytecode, typically used for dynamic proxies needed by Spring**. These classes are generated during the build and become inputs to GraalVM.

Spring Boot documents common output directories:

| Build tool | Common AOT classes directory |
|---|---|
| Maven | `target/spring-aot/main/classes` |
| Gradle | `build/generated/aotClasses` |

Runtime hints are generated in the corresponding AOT resource directories, such as `target/spring-aot/main/resources` for Maven or `build/generated/aotResources` for Gradle.

You can picture the pipeline as:

~~~text
@Configuration, @Bean, @Aspect, @Transactional
                    |
                    v
             Spring AOT processing
                    |
        +-----------+------------+
        |                        |
        v                        v
Generated Java source       Generated bytecode
        |                  (proxy classes, ...)
        |                        |
        +------------+-----------+
                     |
                     v
             GraalVM Native Image
                     |
                     v
              Native executable
~~~

This means proxies recognized and supported by Spring can be prepared at build time. It **does not mean every third-party library calling Byte Buddy or CGLIB at runtime is automatically converted by Spring AOT**. Each library needs its own AOT integration, runtime hints, or corresponding alternative mechanism.

## 6. Spring AOP: JDK proxies and CGLIB proxies

Spring AOP uses two common mechanisms:

| Mechanism | How it is created | Conditions and limitations |
|---|---|---|
| JDK dynamic proxy | Generates an implementation of interfaces | Target needs an interface; callers usually interact via the interface |
| CGLIB proxy | Generates a subclass of the target class | Cannot override `final` methods; cannot extend `final` classes; `private` methods cannot be advised |

On the JVM, Spring can create proxies at startup. In a native build, Spring AOT needs to prepare the proxies identified by the context so GraalVM can include them in the image.

Example of a service with an interface:

~~~java
public interface InvoiceService {
    Invoice create(String customerId);
}

@Service
class DefaultInvoiceService implements InvoiceService {

    @Override
    public Invoice create(String customerId) {
        return new Invoice(customerId);
    }
}
~~~

Spring AOP can be configured to use interface proxies:

~~~java
@Configuration(proxyBeanMethods = false)
@EnableAspectJAutoProxy(proxyTargetClass = false)
class AopConfiguration {
}
~~~

When transactions or other auto-proxy creators are needed, check the unified proxy configuration of Spring and Spring Boot. The `spring.aop.proxy-target-class` property can also affect proxy selection in Spring Boot. Do not assume a single annotation always overrides every other auto-proxy setting.

Design points:

- Inject via interfaces if you want to use JDK proxies.
- Avoid forcing class-based proxies when unnecessary.
- Do not expect CGLIB to advise `final` classes or `final` methods.
- Remember that self-invocation (a method in the same target calling another method via `this`) does not go through Spring AOP proxies under the standard proxy model.
- Use `@Configuration(proxyBeanMethods = false)` when `@Bean` methods do not call each other directly; dependencies should be passed via method parameters to avoid needing a subclass proxy for the configuration class.

## 7. CGLIB, Byte Buddy, Javassist, and ASM

All of these libraries can generate or transform bytecode, though their APIs and goals differ:

| Library/tool | Common capability | Risk when migrating to native |
|---|---|---|
| CGLIB | Generates subclasses and method interceptors | `Enhancer` creates new classes at runtime |
| Byte Buddy | Creates subclasses, interface implementations, advice, instrumentation | `DynamicType.Unloaded.load()` defines classes in a class loader |
| Javassist | Creates/modifies classes using a high-level API | `CtClass.toClass()` or class-defining mechanisms |
| ASM | Low-level bytecode generation and transformation | Writing class bytes manually and calling `defineClass` |
| Java Instrumentation | Agents and class transformers | Requires attach/retransform support and compatible runtime instrumentation |

Byte Buddy example on the JVM:

~~~java
Class<? extends InvoiceService> proxyType =
    new ByteBuddy()
        .subclass(InvoiceService.class)
        .name("com.example.generated.InvoiceServiceProxy")
        .make()
        .load(InvoiceService.class.getClassLoader())
        .getLoaded();
~~~

This snippet defines a new class in the class loader at runtime. Reachability metadata for `InvoiceService` does not automatically generate `InvoiceServiceProxy` in the native image.

**Inspect the library's actual behavior**, not just the dependency name. A library might use Byte Buddy in tests or JVM mode, while selecting a different implementation in native mode. Conversely, a library that never mentions bytecode generation in its public API might still use it internally.

## 8. Compatible integration strategies

| Strategy | When appropriate | Actions required |
|---|---|---|
| Use built-in framework AOT integration | Spring, ORM, or library already supports native/AOT | Pin a supported version, enable the proper plugin, and follow docs |
| Generate classes at build time | Class set and proxy structure known ahead of time | Run generator before AOT/native compilation and include class files in output |
| Use JDK dynamic proxies | Stable interfaces, known interface combinations | Register proxy hints or let static analysis detect them |
| Replace proxies with static decorators/registries | Finite number of implementations | Write static classes, composition, or explicit method dispatch |
| Use library-provided metadata | Issue is reflection, resources, serialization, or JDK proxies | Update dependency/reachability metadata and test |
| Use predefined classes | Legacy system generates classes with stable, exact-matching bytecode | Capture class bytes via GraalVM's experimental feature and assess limits |
| Use experimental runtime class loading | Application truly must define new classes after startup | Apply only after checking GraalVM version, limits, and overhead |
| Split into a separate JVM service | Plugins/classes must change arbitrarily after deployment | Run the dynamic part on a separate JVM and communicate via HTTP/gRPC/messaging |

Do not start by adding sweeping reflection hints. First determine whether the library needs to **access existing classes** or **create new classes**. Those two problems have different solutions.

## 9. Generating bytecode before AOT with a build task

If the proxy set is known at build time, move class generation into a dedicated task:

1. Build generator runs on the JVM in the build environment.
2. Generator uses Byte Buddy, ASM, or a similar library to write `.class` files to an output directory.
3. The output directory is added to the application's main source set/classpath.
4. The `classes` task and Spring AOT task depend on the generator so classes exist before AOT runs.
5. Native compilation receives the generated classes alongside other application classes.
6. Classes selected via reflection still need corresponding metadata if static analysis cannot infer them.

Example of generating a subclass with Byte Buddy during the **build process**:

~~~java
new ByteBuddy()
    .subclass(InvoiceService.class)
    .name("com.example.generated.InvoiceServiceProxy")
    .make()
    .saveIn(generatedClassesDirectory);
~~~

This illustrates the class file writing step. To build a proxy with real advice, the generator must also define method interception/delegation and any helpers the generated bytecode calls. The generator does not need to run inside the native application; it only needs to run during the build.

With Gradle, configure the generator task and declare the generated output directory as a source set output; ensure AOT/native tasks depend on the generator task. With Maven, bind the generator to an appropriate phase before `process-aot` and native compilation, and include the generated classes directory in the build artifact.

**Task ordering is critical.** If AOT runs before the generator, Spring may not see the classes or resolve required beans/proxies. If `.class` files sit in a directory excluded from the build classpath, GraalVM cannot analyze them either.

## 10. Using JDK proxies and registering RuntimeHints

When a library explicitly calls `Proxy.newProxyInstance` with an interface list that cannot be statically inferred, Spring can register a proxy hint:

~~~java
import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.ImportRuntimeHints;

public class PaymentProxyHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(
            RuntimeHints hints,
            ClassLoader classLoader) {

        hints.proxies().registerJdkProxy(PaymentOperations.class);
    }
}

@Configuration(proxyBeanMethods = false)
@ImportRuntimeHints(PaymentProxyHints.class)
class NativeProxyConfiguration {
}
~~~

If the proxy implements multiple interfaces, register the exact interface set in the order the application requires:

~~~java
hints.proxies().registerJdkProxy(
    PaymentOperations.class,
    Serializable.class
);
~~~

This is metadata for a **JDK interface proxy**. It is not metadata for GraalVM to generate an arbitrary CGLIB subclass or run Byte Buddy at runtime.

Spring Boot also allows declaring proxy metadata directly in GraalVM JSON hint files. When using static files, place them in the appropriate `META-INF/native-image` location and avoid overwriting the output directory generated by Spring AOT.

## 11. What must a native-supporting library provide?

A library aiming to support Spring AOT/Native Image should make its dynamic requirements clear:

- Which classes/members does reflection require?
- Does it create JDK proxies, and how can the interface set be determined?
- Does it generate subclasses or new classes via CGLIB/Byte Buddy/Javassist?
- Are classes generated at build time or runtime?
- Are there resources, serialization, JNI, or instrumentation?
- Is there an alternative when running native?

For Spring libraries, extension points may include:

- `RuntimeHintsRegistrar` to contribute reflection, resource, serialization, and JDK proxy hints.
- `BeanFactoryInitializationAotProcessor` to contribute code that restores the bean factory.
- `BeanRegistrationAotProcessor` to contribute how beans are created/registered.
- Framework-specific AOT mechanisms or build plugins.

A library that only provides reflection metadata while still calling `new ByteBuddy().make().load()` at runtime has not solved class generation. If proxies are needed, the library should generate them during AOT/build or provide a native-compatible static implementation.

For third-party libraries, check the reachability metadata repository and native support documentation for the exact version. The metadata repository can provide hints for common dynamic features; it does not replace a runtime code generation mechanism unsupported by Native Image.

## 12. Predefined classes: a transitional option for some legacy systems

GraalVM supports **predefined classes** through the Native Image Tracing Agent in certain versions. The agent can record the bytecode of dynamically defined classes while the application runs on the JVM. During the native build, collected class bytes are pre-prepared; runtime can supply the corresponding class if the name and bytecode match an observed class.

Example of running the JVM with the agent and the experimental option:

~~~bash
java \
  -agentlib:native-image-agent=config-output-dir=target/native-agent,experimental-class-define-support \
  -jar target/application.jar
~~~

After exercising all necessary flows, the configuration directory can contain metadata and a directory of predefined class bytecode. Use this output in the native build according to the documentation for your exact GraalVM version.

This is a **best-effort option for legacy systems**, not a way to make every arbitrary class-generating library native-compatible:

- Classes must be observed during JVM runs.
- When requested at runtime, the class name and bytecode must match the recorded class.
- Class names or bytecode that vary by request, sequence number, timestamp, or random data usually cannot match reliably.
- Class loader and reload count limits may apply depending on version.
- Metadata cannot make a new class appear if its bytecode was not collected beforehand.

The agent does not automatically test every business branch. Insufficient test coverage can leave a required proxy class unrecorded.

## 13. Experimental runtime class loading

Some recent GraalVM releases document an experimental option allowing classes to be defined from bytecode while the native executable runs. The option described in current development documentation is `-H:+RuntimeClassLoading`, unlocked with `-H:+UnlockExperimentalVMOptions`.

Example build configuration form:

~~~text
-H:+UnlockExperimentalVMOptions
-H:+RuntimeClassLoading
-H:-UnlockExperimentalVMOptions
~~~

This is an **experimental** feature, not Native Image's default mode. Documented limitations may include:

- Parallel class loading is not supported.
- Attention must be paid to class loaders and class names because a class loader cannot redefine the same binary name.
- Dynamically loaded classes may reference build-time classes where some methods or fields were stripped from the image; package/type preservation configuration may be required.
- May increase image size and memory usage.
- Cannot be combined with predefined classes in the documented configurations.
- Requires extra verification per API, class loader, and specific library; enabling the flag does not guarantee every dynamic framework will work.

Consider this feature only when the application genuinely must define classes after startup and cannot move to build-time generation or a static architecture. Before using it in production, verify whether the feature exists in your pinned GraalVM release, vendor support policy, limitations, and your library's own test results.

## 14. When to use a decorator instead of a dynamically generated proxy?

If you only need to add logging, metrics, validation, or permission checks before/after a call, a static decorator can fulfill this without generating bytecode:

~~~java
public interface PaymentOperations {
    Receipt charge(String orderId);
}

final class DefaultPaymentOperations implements PaymentOperations {

    @Override
    public Receipt charge(String orderId) {
        return new Receipt(orderId);
    }
}

final class AuditedPaymentOperations implements PaymentOperations {

    private final PaymentOperations delegate;

    AuditedPaymentOperations(PaymentOperations delegate) {
        this.delegate = delegate;
    }

    @Override
    public Receipt charge(String orderId) {
        // Record before calling business logic.
        Receipt receipt = delegate.charge(orderId);
        // Record result after calling business logic.
        return receipt;
    }
}
~~~

Registering via Spring:

~~~java
@Configuration(proxyBeanMethods = false)
class PaymentConfiguration {

    @Bean
    PaymentOperations paymentOperations() {
        PaymentOperations target = new DefaultPaymentOperations();
        return new AuditedPaymentOperations(target);
    }
}
~~~

The example simplifies logging to focus on structure. In real projects, you can use decorators for certain concerns while still using Spring AOP for transactions/security where supported.

Decorators offer several advantages:

- Classes exist from build time; no class loader needs to define new classes.
- Dependencies and behavior can be verified with unit tests.
- No proxy metadata needed unless other reflection/proxies are used.
- Call flow and processing order are easy to see.
- Suitable when the number of wrapper layers is finite and not every method needs automatic interception.

## 15. Libraries/frameworks to inspect carefully

| Category | Examples | Questions to ask |
|---|---|---|
| DI/AOP | Spring AOP, AspectJ, CGLIB | Does the framework have an AOT processor to pre-create proxies? |
| Bytecode toolkits | Byte Buddy, Javassist, ASM | Can the generator run during the build and package the classes? |
| ORM | Hibernate lazy proxies, enhancement | Which native integration and enhancement mode does this ORM version offer? |
| Mocking | Mockito and mock makers | Do tests run on JVM or native? Does the mock maker need inline instrumentation? |
| Serialization/RPC | Jackson, RPC stub generators | Are adapter classes generated at build or runtime? Are DTO/proxy hints complete? |
| Instrumentation/agents | Java agents, attach API, class transformers | Does the native runtime support those APIs and transformation steps? |
| Scripting/plugins | Plugin classloaders, script compilers | Is external bytecode loaded after the image has been built? |

You cannot conclude that all libraries in a category are universally compatible or incompatible. Check the exact version, module, code path, and configuration. An ORM might use proxies in one case while providing build-time bytecode enhancement in another.

In particular, check the scope of native support: a library may support native for production applications while not supporting an optional mocking extension or plugin.

## 16. Inspecting Spring AOT output and generated proxy classes

After running AOT, you can inspect generated classes:

~~~bash
# Gradle
./gradlew processAot
Get-ChildItem -Recurse build/generated/aotClasses

# Maven
./mvnw spring-boot:process-aot
Get-ChildItem -Recurse target/spring-aot/main/classes
~~~

`Get-ChildItem` is a PowerShell command; on Linux/macOS you can use `find`. Output paths depend on Spring Boot version and build configuration.

To inspect a specific class file, use `javap`:

~~~bash
javap -classpath build/generated/aotClasses -p com.example.generated.SomeProxy
~~~

Replace the package/class name with the actual class. `javap` helps inspect the superclass, interfaces, methods, and bytecode signatures; it does not prove every runtime path is included in the image.

You can also check:

- Is the proxy class present in AOT output?
- Does the bean definition reference the right class or supplier?
- Are JDK proxy interfaces registered?
- Does the generated class depend on any unpackaged helper class?
- Does advice/interceptor code use reflection or resources needing separate hints?

## 17. Workflow for diagnosing proxy or bytecode generation errors

| Symptom | Possible cause | Resolution |
|---|---|---|
| `UnsupportedFeatureError` when calling `defineClass` | Library is defining new classes at runtime | Move generator to build time, replace proxy, or evaluate experimental feature |
| `ClassNotFoundException` with dynamically generated proxy name | Class missing from image or predefined class mismatch | Check build output, classpath, bytecode, and metadata |
| `MissingReflectionRegistrationError` inside proxy | Proxy/interceptor uses reflection without hints | Register required members; do not confuse with class generation |
| `IllegalArgumentException` creating JDK proxy | Invalid interface list or mismatched metadata | Check interfaces, order, and class loader |
| CGLIB reports it cannot subclass class | `final` class, constructor/visibility, or non-overridable method | Use interface proxy or refactor target design |
| AOP advice does not run on native | Proxy not created, method bypasses proxy, or self-invocation | Check AOT output, proxy type, and call flow |
| Generated class exists on disk but native misses it | Generated output not on classpath during AOT/native build | Fix task dependencies and source sets |
| Works on JVM but native build fails | Unsupported dynamic generation/instrumentation or missing metadata | Identify class-creating API and choose another integration |
| Native runs but a plugin proxy fails | Tests did not cover that interface set/proxy-creation branch | Expand tests and hints per case |

When debugging, trace the stack trace to the API actually creating the class: `Proxy.newProxyInstance`, `ClassLoader.defineClass`, `Lookup.defineClass`, `Enhancer`, `ByteBuddy`, `CtClass.toClass`, or an instrumentation API. Spring-level error names are sometimes only wrappers around a root cause in a lower-level library.

## 18. Practice: replacing a runtime proxy with a pre-preparable proxy

Suppose a payment application uses a library that generates a `PaymentServiceProxy` subclass at runtime to record metrics.

### Step 1 — Identify requirements

Record:

- Which classes/interfaces are proxied.
- Which methods need interception.
- Whether the target set is fixed in the application.
- Whether the proxy class depends on runtime configuration or tenant data.
- Whether the library provides an AOT plugin or native integration.

### Step 2 — Choose an approach

If the service has interfaces and the interface set is fixed, try JDK proxies. If Spring AOP can manage the proxy, let Spring AOT prepare the proxy from known configuration. If a concrete subclass is needed, move the generator into a build task and package the classes.

### Step 3 — Feed generated output into AOT

Ensure the generator task runs before `processAot`. Verify `.class` files appear in the output and are present on the classpath used by native compilation.

### Step 4 — Verify hints

If the proxy uses reflection, register the exact constructors/methods. If using JDK proxies, register the interface set. Do not add reflection hints as a substitute for ungenerated class files.

### Step 5 — Run native

~~~bash
./gradlew processAot
./gradlew nativeCompile
~~~

Start the executable and invoke every advised method. Compare against JVM results: business logic, metrics, transactions, security, and exception handling must all be preserved.

### Step 6 — Record the trade-offs

| Criterion | Before | After |
|---|---|---|
| Proxy generation time | Runtime | Build time or prepared JDK proxy |
| Class loader dependency | Defines new class at runtime | Class already present in image |
| Metadata | Unclear/missing | Scoped hints |
| Native compatibility | May fail | Tested on executable |
| Configuration changes | Can generate arbitrary proxies | Constrained to known build configuration |

## 19. Checklist for evaluating a bytecode-generating library

Before selecting a library for Spring Boot Native Image, verify:

1. **When does it generate bytecode?** Build time, AOT time, startup runtime, or per request?
2. **Which API does it use to define classes?** JDK Proxy, CGLIB, Byte Buddy, `defineClass`, Javassist, ASM, or instrumentation?
3. **Is the class set deterministic?** Are class names, interfaces, superclasses, and methods known before the build?
4. **Does the library have native/AOT integration?** Check release notes, docs, reachability metadata, and native samples.
5. **Can it pre-generate?** Is there a Maven/Gradle plugin, annotation processor, or AOT extension?
6. **Can it be replaced by interfaces/decorators?** If so, a static design is usually easier to control.
7. **Is the metadata of the right kind?** Reflection hints, JDK proxy hints, and class bytecode are three different things.
8. **Are there GraalVM limitations?** Predefined classes/runtime class loading may be experimental and conditional.
9. **Has the exact path been tested?** A successful build is not enough; invoke the real method/proxy/plugin on the native executable.
10. **Which versions are supported?** Record Spring Boot, Spring Framework, GraalVM, JDK, and bytecode library versions.

## 20. Key takeaways

Native Image can handle many forms of reflection and JDK dynamic proxies when targets are known or have matching metadata. Spring AOT can also generate proxy bytecode at build time for Spring-supported cases. These mechanisms let you keep many benefits of proxies/AOP without defining new classes while the native application runs.

For arbitrary bytecode-generating libraries, prefer AOT integrations or move generation to build time, placing class files on the classpath before AOT/native compilation runs. If the interface set is fixed, JDK proxies with proxy hints can be a good fit. If the implementation set is finite, static decorators or registries reduce complexity.

Predefined classes and runtime class loading are specialized options with constraints; verify them against your exact version and do not treat them as a general replacement for native-friendly design. **Reflection metadata does not create new class files**; always distinguish accessing an existing class from generating a new class.
