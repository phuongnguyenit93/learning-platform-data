# Checking Reachability Metadata Formats and Build Flags by Version

> **Chapter:** Migration and Upgrade  
> **Module:** SPRING_BOOT_NATIVE_IMAGE  
> **Objective:** Identify reachability metadata formats by GraalVM JDK version; migrate legacy JSON configurations to the unified format; manage application and library metadata; inspect build flags, Native Build Tools, and Spring Boot AOT before upgrading the toolchain.

## 1. Why Check Metadata and Build Flags When Upgrading?

Spring Boot Native Image depends on multiple components participating in the build: the Spring Boot plugin, Spring Framework, GraalVM JDK/Native Image, Native Build Tools, and library reachability metadata. Each component has its own release lifecycle. A configuration that previously built cleanly can emit warnings, be ignored, or become invalid when upgrading GraalVM.

Common causes:

- Metadata files generated by an older JDK's Tracing Agent follow a different structure than what the newer JDK recommends.
- Metadata conditions use `typeReachable` while the newer version uses `typeReached`.
- Resource patterns written as regular expressions were copied verbatim into a `glob` field.
- Proxy or serialization metadata remains in separate files even though the newer format folds them into reflection metadata.
- Build scripts retain deprecated or removed flags.
- A valid `native-image` CLI flag is mistakenly passed to the JVM running Maven/Gradle.
- The plugin downloads reachability metadata for dependencies, but the repository release or a library's metadata version is pinned improperly.

An upgrade must inspect **metadata structure**, **the semantics of each entry**, **flags supported by the builder**, and **how the plugin passes flags to the builder**. Simply renaming files or bumping plugin versions does not prove the native executable retains all dynamic behavior.

## 2. Distinguish Versions Participating in the Native Build

There is no single version number representing the entire toolchain. Record these components separately:

| Component | Role | What to record |
|---|---|---|
| Spring Boot | Orchestrates AOT, native packaging, and dependency management | Boot version and Java baseline |
| Spring Framework / Spring Data | Generates AOT contributions and runtime hints | Version managed by Boot BOM |
| GraalVM JDK / Native Image | Static analysis, metadata reading, and executable generation | JDK major, GraalVM distribution, `native-image --version` |
| GraalVM Native Build Tools | Maven/Gradle integration, testing, and metadata repository | Plugin version |
| GraalVM Reachability Metadata Repository | Metadata for third-party libraries | Repository release and per-library metadata version when overridden |
| Buildpacks / builder image | Packaging and selecting the Native Image toolchain | Builder/run image digest and Java version |

Key principles when selecting versions:

1. Choose Spring Boot and the Java baseline first; use the Spring Boot BOM to manage Spring Framework, Spring Data, and related dependencies.
2. Pick a GraalVM distribution whose JDK major matches the Java version supported by Spring Boot and your build pipeline.
3. Pick Native Build Tools compatible with your Gradle/Maven wrapper and GraalVM JDK.
4. Record the reachability metadata repository release used by the plugin; verify metadata matches the exact library versions.
5. Pin versions in CI so two builds do not silently pick different builder images or metadata repositories.

Do not infer compatibility merely because components support the same Java language level. Buildpacks, Native Image, and plugins can have their own requirements. Current Spring Boot documentation also requires checking the Java version used for compilation when building native images with Buildpacks. [Spring Boot — Developing a Native Application](https://docs.spring.io/spring-boot/how-to/native-image/developing-your-first-application.html)

## 3. Legacy Metadata Format: Separate Files per Feature

In older GraalVM JDKs, metadata was split into separate files on the classpath, typically placed under:

```text
src/main/resources/
└── META-INF/
    └── native-image/
        └── com.example/
            └── payment-service/
                ├── reflect-config.json
                ├── resource-config.json
                ├── proxy-config.json
                ├── serialization-config.json
                └── jni-config.json
```

These files have distinct schemas:

| Legacy file | Contents |
|---|---|
| `reflect-config.json` | Classes, constructors, methods, fields needing reflection |
| `resource-config.json` | Resource includes/excludes and resource bundles |
| `proxy-config.json` | Ordered interface lists for creating JDK dynamic proxies |
| `serialization-config.json` | Types used by Java serialization |
| `jni-config.json` | Classes/members accessed by native code via JNI |

Example `reflect-config.json` in the legacy schema:

```json
[
  {
    "condition": {
      "typeReachable": "com.example.payment.PaymentService"
    },
    "name": "com.example.payment.dto.PaymentCommand",
    "allDeclaredConstructors": true,
    "methods": [
      {
        "name": "from",
        "parameterTypes": ["java.lang.String"]
      }
    ]
  }
]
```

Notable characteristics:

- The reflection file is typically a JSON array.
- The class name sits in the `name` field.
- Reachability conditions use `condition.typeReachable`.
- Resource metadata has a `resources` object with `includes`/`excludes`, each entry using `pattern`.
- Proxies and serialization have separate files.

Legacy resource metadata example:

```json
{
  "resources": {
    "includes": [
      {
        "condition": {
          "typeReachable": "com.example.payment.ReportService"
        },
        "pattern": "db/migration/.*\\.sql"
      }
    ]
  },
  "bundles": [
    {
      "name": "com.example.payment.Messages",
      "locales": ["en", "vi"]
    }
  ]
}
```

In this structure, `pattern` is a regular expression. Never rename the field to `glob` while keeping the regex expression verbatim, because the two representations have different semantics.

## 4. Unified Format Starting in GraalVM JDK 23

GraalVM for JDK 23 introduced the unified `reachability-metadata.json` format. Individual files like `reflect-config.json`, `resource-config.json`, `proxy-config.json`, `serialization-config.json`, and `jni-config.json` were marked deprecated, though Native Image still accepts them for backward compatibility. [GraalVM JDK 23 Release Notes](https://www.graalvm.org/release-notes/JDK_23/)

Recommended path:

```text
src/main/resources/
└── META-INF/
    └── native-image/
        └── com.example/
            └── payment-service/
                └── reachability-metadata.json
```

The new format uses a single top-level JSON object. Common metadata sections include:

- `reflection`: reflection, dynamic proxies, and serialization declarations in the newer schema.
- `jni`: types/members accessed by native code.
- `resources`: resources on the classpath/module path.
- `bundles`: resource bundles for localization.

Combined example:

```json
{
  "reflection": [],
  "jni": [],
  "resources": [],
  "bundles": []
}
```

Not every project needs all of the above sections. Declare only the metadata sections that the application or dependencies actually use. In addition, `predefined-classes-config.json` remains a separate configuration for predefined classes; do not merge this file into `reachability-metadata.json`.

Native Image reads metadata from classpath entries under `META-INF/native-image/<groupId>/<artifactId>/`. A dependency can package its own metadata; an application can also provide its own metadata in its artifact. [GraalVM JDK 25 — Reachability Metadata](https://www.graalvm.org/jdk25/reference-manual/native-image/metadata/)

## 5. Structural Changes to Handle During Conversion

### 5.1. Reflection: `name` to `type`

Legacy example:

```json
[
  {
    "name": "com.example.PaymentCommand",
    "allDeclaredConstructors": true
  }
]
```

Unified format:

```json
{
  "reflection": [
    {
      "type": "com.example.PaymentCommand",
      "allDeclaredConstructors": true
    }
  ]
}
```

The `type` field also supports describing proxy or lambda types in the new schema. When converting, verify that attributes such as constructors, methods, fields, query-only access, and unsafe allocation are preserved accurately. Do not mechanically rename the field and drop specific members the application needs.

### 5.2. Conditions: `typeReachable` to `typeReached`

GraalVM JDK 23 replaced `typeReachable` with `typeReached`. The new condition evaluates whether a type is considered reached at runtime; a type is considered reached right before its class initialization starts, or when one of its subtypes is reached. [GraalVM JDK 23 Release Notes](https://www.graalvm.org/release-notes/JDK_23/)

New format example:

```json
{
  "reflection": [
    {
      "condition": {
        "typeReached": "com.example.payment.PaymentService"
      },
      "type": "com.example.payment.dto.PaymentCommand",
      "allDeclaredConstructors": true
    }
  ]
}
```

Do not simply find-and-replace across the entire repository without re-reading condition semantics. Conditional metadata only takes effect when the condition type is reached. Choosing the wrong condition class can cause a syntactically valid entry not to apply at runtime.

### 5.3. Resources: `includes`/`excludes` Object to Entry List

The new format places resource entries into the `resources` array:

```json
{
  "resources": [
    {
      "glob": "db/migration/*.sql"
    },
    {
      "glob": "reports/templates/**"
    }
  ]
}
```

GraalVM JDK 23 added glob support for resource paths, and the Tracing Agent began outputting entries in glob format. Globs support `*` within a single path level and `**` across multiple levels. [GraalVM JDK 23 Release Notes](https://www.graalvm.org/release-notes/JDK_23/)

Conversion examples:

| Legacy regex (`pattern`) | New glob (`glob`) |
|---|---|
| `db/migration/.*\\.sql` | `db/migration/*.sql` |
| `reports/.*` | `reports/**` |
| `config/application\\.ya?ml` | Write two explicit globs: `config/application.yaml`, `config/application.yml` |

The table only illustrates simple patterns. For complex regexes, rewrite them using glob semantics or keep the legacy config during transition if the target Native Image version still supports it. Verify actual resources inside the executable after building.

## 6. Converting Proxy, Serialization, and JNI Metadata

### 6.1. Dynamic Proxies

In the legacy format, proxy interfaces lived in `proxy-config.json`:

```json
[
  {
    "interfaces": [
      "com.example.payment.PaymentGateway",
      "java.io.Serializable"
    ]
  }
]
```

In the unified format, proxy types are declared in the `reflection` section:

```json
{
  "reflection": [
    {
      "type": {
        "proxy": [
          "com.example.payment.PaymentGateway",
          "java.io.Serializable"
        ]
      }
    }
  ]
}
```

Interface order is part of the proxy definition. Do not reorder the list or merge two proxies just because they use the same interfaces in a different order. GraalVM JDK 23 marks `proxy-config.json` deprecated while continuing to support it for backward compatibility. [GraalVM JDK 23 Release Notes](https://www.graalvm.org/release-notes/JDK_23/)

### 6.2. Serialization

In older GraalVM JDKs, serialization had a dedicated `serialization-config.json` file with a `types` list. Starting in GraalVM JDK 24, serialization JSON metadata moves into reflection metadata via the `serializable` attribute.

New format example:

```json
{
  "reflection": [
    {
      "type": "com.example.payment.PaymentEvent",
      "serializable": true
    }
  ]
}
```

When converting, verify both serialized and deserialized types, subclasses that may appear in the object graph, proxy serialization, and custom serialization hooks. Do not register every class in a package just to silence errors. Broad serialization metadata inflates the executable and widens the surface of allowed deserializable types. [GraalVM JDK 24 Release Notes](https://www.graalvm.org/release-notes/JDK_24/)

### 6.3. JNI

Legacy JNI metadata lived in `jni-config.json`; the unified format moves entries into the `jni` array. The `type` field and members are preserved to match lookups from native code.

Example:

```json
{
  "jni": [
    {
      "type": "com.example.payment.NativeBridge",
      "methods": [
        {
          "name": "onPaymentResult",
          "parameterTypes": ["java.lang.String", "int"]
        }
      ]
    }
  ]
}
```

JNI metadata differs from reflection metadata in the caller origin: native code calls into Java via JNI. If a library uses JNI, verify every class, method, and field looked up by the native library. JVM tests alone are insufficient to confirm JNI paths work inside the native executable.

## 7. GraalVM JDK Milestone Changes Table

The table below summarizes milestones that directly affect metadata conversion and build arguments. These are Native Image feature milestones; always check the specific release of the distribution your project installs.

| GraalVM JDK | Metadata and build behavior to note |
|---|---|
| JDK 17 / 21 | Split files are standard: `reflect-config.json`, `resource-config.json`, `proxy-config.json`, `serialization-config.json`, `jni-config.json`. Reflection uses `name`, conditions use `typeReachable`; resources use regex `pattern`. |
| JDK 22 | Split metadata still encountered. Strict image heap is enabled by default; no need to copy historical configs just to re-enable this default. |
| JDK 23 | Introduces `reachability-metadata.json`; replaces `typeReachable` with `typeReached`; moves proxy metadata into reflection types; supports resource globs; introduces `--exact-reachability-metadata`; `--report-unsupported-elements-at-runtime` deprecated and runtime reporting enabled by default. |
| JDK 24 | Serialization metadata folded into reflection entries via `serializable`; some legacy serialization fields like `customTargetConstructorClass` removed. Prefix `-Dgraal.` starts emitting deprecation warnings; switch to `-Djdk.graal.` for corresponding Graal compiler options. |
| JDK 25 | Native Image documentation marks `--enable-http`, `--enable-https`, and `--enable-url-protocols` deprecated; for URL protocol handlers, use reachability metadata. Options may vary between JDK 25.0 and 25.x updates. |

Release notes sources: [JDK 22](https://www.graalvm.org/release-notes/JDK_22/), [JDK 23](https://www.graalvm.org/release-notes/JDK_23/), [JDK 24](https://www.graalvm.org/release-notes/JDK_24/), [JDK 25 Native Image options](https://www.graalvm.org/jdk25/reference-manual/native-image/overview/Options/).

Do not treat this table as a Spring Boot support matrix. It describes GraalVM Native Image changes. Spring Boot releases and the Java baseline remain separate constraints that must be verified.

## 8. Version-Specific Build Flags for Diagnosing Missing Registrations

A major difference when upgrading from JDK 21/22 to JDK 23+ is how exact reachability metadata and missing registration reporting are enabled.

### 8.1. GraalVM JDK 23 and Later

Build-time flag:

```text
--exact-reachability-metadata
```

Can be scoped to specific packages during incremental migration:

```text
--exact-reachability-metadata=com.example.payment,com.example.integration
```

When running the native executable in tests, use:

```bash
./target/payment-service -XX:MissingRegistrationReportingMode=Warn
```

`Warn` helps find missing registrations without forcing the app to exit immediately. In strict tests, use `Exit` to terminate immediately upon hitting a registration error, even when application code catches `Throwable` and accidentally swallows the error:

```bash
./target/payment-service -XX:MissingRegistrationReportingMode=Exit
```

Exact metadata mode makes reflection, resource, JNI, and serialization errors surface earlier and easier to trace. Enable it in CI/native tests before major toolchain upgrades, then fix each missing entry one by one. [GraalVM — Reachability Metadata](https://www.graalvm.org/latest/reference-manual/native-image/metadata/)

### 8.2. GraalVM JDK 22 and Earlier

The newer flags `--exact-reachability-metadata` and `-XX:MissingRegistrationReportingMode` are not compatible choices on all older GraalVM releases. Native Build Tools documents using hosted options at build time:

```text
-H:ThrowMissingRegistrationErrors=
-H:MissingRegistrationReportingMode=Warn
```

Place these options in the native build configuration for older versions. Do not copy JDK 23+ runtime flags onto executables built with JDK 21/22 assuming the runtime understands them.

Native Build Tools documentation notes that `--exact-reachability-metadata` was introduced in GraalVM JDK 23; for older versions, use `-H:ThrowMissingRegistrationErrors=`. For GraalVM older than JDK 23, `-H:MissingRegistrationReportingMode=Warn` is passed at build time. [Native Build Tools — Troubleshoot Missing Configuration](https://graalvm.github.io/native-build-tools/latest/end-to-end-maven-guide.html)

### 8.3. Do Not Confuse Missing Registration with Unsupported Elements

`--report-unsupported-elements-at-runtime` was an older flag to defer certain unsupported element errors from build time to runtime. GraalVM JDK 23 deprecated this flag and enabled runtime reporting by default.

That flag does not replace metadata. If the application uses reflection without registration, supply the exact metadata or refactor the code so static analysis sees the access path. Do not add unsupported-runtime flags as a fix for reflection/resource errors.

## 9. URL Protocol Flags and Metadata in Newer JDKs

Previously, projects might add:

```text
--enable-http
--enable-https
--enable-url-protocols=http,https
```

In GraalVM JDK 25 Native Image documentation, those options are marked deprecated. Instead, if the application genuinely uses `java.net.URL` with HTTP/HTTPS handlers, register the handler constructors in `reachability-metadata.json`:

```json
{
  "reflection": [
    {
      "type": "sun.net.www.protocol.http.Handler",
      "methods": [
        {
          "name": "<init>",
          "parameterTypes": []
        }
      ]
    },
    {
      "type": "sun.net.www.protocol.https.Handler",
      "methods": [
        {
          "name": "<init>",
          "parameterTypes": []
        }
      ]
    }
  ]
}
```

This is metadata for JDK URL protocol handlers. It is not a blanket flag to enable HTTP servers, Spring MVC, WebFlux, or arbitrary HTTP clients. Those stacks have their own reachability mechanisms from their frameworks/dependencies and must be verified per library in use. [GraalVM — URL Protocols in Native Image](https://www.graalvm.org/latest/reference-manual/native-image/dynamic-features/URLProtocols/)

## 10. Classify Build Flags Before Migrating

Not every dashed option is passed at the same stage. GraalVM classifies options by where they take effect:

| Syntax | Meaning | Example |
|---|---|---|
| `--...` | Native Image build option | `--exact-reachability-metadata` |
| `-H:` | Hosted option, configures the build process or runtime defaults baked into the image | `-H:IncludeLocales=vi,en` |
| `-R:` | Sets initial values for runtime options at build time | Depends on option and version |
| `-XX:` | Runtime option when launching the native executable | `-XX:MissingRegistrationReportingMode=Warn` |
| `-Dname=value` | System property set for the Native Image build; certain JDK properties are captured into the executable | `-Duser.language=vi` |
| `-J...` | Passes an option to the JVM running the Native Image builder process | `-J-Xmx8g` |

`-H:` and `-R:` are not interchangeable syntaxes. Check the option category in documentation for your exact JDK before moving flags between build scripts and the command line. `-D` also does not automatically mean a property will be re-read at runtime; properties generally exist only during the build process, except JDK properties retained by Native Image according to that version's rules.

Before upgrading, extract the option list directly from the builder used in CI:

```bash
native-image --version
native-image --help
native-image --help-extra
native-image --expert-options
```

Newer releases may support `--print-options` to output a structured list, such as JSON. Only use this command if `--help` on your installed version confirms it exists. Unrecognized options fail the build; do not rely on option lists from a documentation page for a different JDK. [GraalVM JDK 25 — Command-line Options](https://www.graalvm.org/jdk25/reference-manual/native-image/overview/Options/)

## 11. Build Flags to Review When Upgrading

### 11.1. Class Initialization

The two current options controlling when classes initialize are:

```text
--initialize-at-build-time=com.example.StableMetadata
--initialize-at-run-time=com.example.RuntimeConfiguration
```

Specify only classes or packages that truly need it. Build-time initialization can capture state from the build environment into the executable; runtime initialization defers that decision until application launch. Do not copy a huge package list from a legacy project without inspecting static initializers, files, clocks, random seeds, environment variables, and security providers.

### 11.2. Strict Image Heap and Legacy Class Initialization

GraalVM JDK 22 enabled strict image heap by default. When upgrading to JDK 23, do not carry over the historical `--StrictImageHeap` flag expecting it to keep altering behavior; JDK 23 release notes document that this legacy option has no effect. Use current class initialization options and fix warnings as guided by the builder.

### 11.3. Unsupported Elements

`--report-unsupported-elements-at-runtime` was deprecated in GraalVM JDK 23 because runtime reporting became the default. Remove the old flag after confirming no scripts or profiles rely on older version behavior.

### 11.4. Graal Compiler System Properties

If build scripts contain properties like `-Dgraal.SomeOption=...`, review them. GraalVM JDK 24 began emitting deprecation warnings for the `graal.` prefix and recommends `jdk.graal.` for corresponding Graal compiler options. This change applies to Graal compiler properties; do not rename unrelated Java system properties starting with `-D`.

### 11.5. Optimization Level and Build Report

GraalVM JDK 23 added `-Os` to optimize for executable size. Do not pass `-Os` to older builders that do not support it. Evaluate size, startup, and throughput on real workloads before picking an optimization level.

You can request a build report with `--emit build-report` to inspect image contents and dynamic accesses. According to current documentation, Build Report is unavailable in GraalVM Community Edition; on unsupported distributions, use logs, metadata reports, and other resource inspection tools. [GraalVM — Native Image Build Report](https://www.graalvm.org/latest/reference-manual/native-image/overview/build-report/)

## 12. Setting Default Configuration in `native-image.properties`

If a library or application needs consistent options on every build, place a `native-image.properties` file under the metadata namespace:

```text
src/main/resources/
└── META-INF/
    └── native-image/
        └── com.example/
            └── payment-service/
                ├── native-image.properties
                └── reachability-metadata.json
```

Example:

```properties
Args = --exact-reachability-metadata
ImageName = payment-service
```

`Args` contains options passed to the Native Image builder. `JavaArgs` targets the JVM running the builder; `ImageName` sets the default executable name. You can reference an argument file with `@file` syntax for long configs, provided that file resides in the classpath entry containing `native-image.properties` per Native Image rules.

Options are evaluated left to right. Options passed later on the command line can override file settings. Avoid declaring the same flag in `native-image.properties`, Maven/Gradle, and Buildpacks with conflicting values; doing so makes it very hard to tell which final value the builder receives. [GraalVM — Native Image Build Configuration](https://www.graalvm.org/jdk25.5/reference-manual/native-image/overview/BuildConfiguration/)

## 13. Configuring Flags with Maven and Gradle

### 13.1. Maven Native Build Tools

Pass build arguments via `native-maven-plugin`:

```xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
    <configuration>
        <buildArgs>
            <buildArg>--exact-reachability-metadata</buildArg>
            <buildArg>--emit build-report</buildArg>
        </buildArgs>
    </configuration>
</plugin>
```

Each `buildArg` is a Native Image option expression, not an entire shell command. If an option takes a multi-token value, keep them in the same expression as required by the plugin. If running GraalVM Community Edition without Build Report support, remove the `--emit build-report` line.

When using `spring-boot-starter-parent`, the Spring Boot Maven plugin's `native` profile can configure `process-aot`, native build settings, and downloading third-party reachability metadata. Without this parent, you must configure `process-aot` and required metadata steps manually. [Spring Boot — Maven AOT Processing](https://docs.spring.io/spring-boot/maven-plugin/aot.html)

### 13.2. Gradle Native Build Tools

With Gradle Groovy DSL:

```groovy
graalvmNative {
    binaries {
        main {
            buildArgs.add("--exact-reachability-metadata")
            buildArgs.add("--emit=build-report")
        }
    }
}
```

If using Kotlin DSL, use the corresponding API of the plugin version pinned in your build. Do not copy Groovy syntax into `build.gradle.kts` without converting types and accessors properly.

The Spring Boot Gradle plugin coordinates AOT tasks when the GraalVM Native plugin is applied. Confirm AOT and native compile tasks appear in the task graph; do not see the plugin in the `plugins` block and assume it ran.

### 13.3. Never Mix Build Options and Runtime Arguments

For example:

- `--exact-reachability-metadata` is a build option.
- `-XX:MissingRegistrationReportingMode=Warn` is a runtime option for the native executable on GraalVM JDK 23+.
- `-J-Xmx8g` tunes the JVM running the builder, not the heap of the native application.

Put each option in the right place in the plugin. If a runtime argument is placed in `buildArgs`, or a builder JVM option is passed to the executable, the build may fail or have no intended effect.

## 14. Reachability Metadata Repository for Third-Party Libraries

Native Build Tools can automatically look up dependency metadata from the GraalVM Reachability Metadata Repository. The repository holds configurations contributed by library authors or the community for dependencies that do not yet bundle sufficient metadata themselves.

With Maven, the plugin supports the metadata repository and can fetch configs matching dependencies. The Spring Boot `native` profile also configures downloading third-party reachability metadata. With Gradle, the `org.graalvm.buildtools.native` plugin provides `graalvmNative.metadataRepository`.

Two version concepts must stay separate:

1. **Repository release version:** the version of the metadata repository bundle downloaded by Native Build Tools.
2. **Per-module metadata version:** the metadata version selected for a specific dependency when the repository has multiple variants or lacks metadata for the exact library version.

Maven example overriding a dependency's metadata version:

```xml
<metadataRepository>
    <enabled>true</enabled>
    <dependencies>
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>legacy-client</artifactId>
            <metadataVersion>2</metadataVersion>
        </dependency>
    </dependencies>
</metadataRepository>
```

Gradle override example for a specific module:

```groovy
graalvmNative {
    metadataRepository {
        moduleToConfigVersion.put("com.example:legacy-client", "2")
    }
}
```

The number `2` in the example is the module's metadata version—not the GraalVM JDK major, Spring Boot version, or Native Build Tools plugin version. Only override after verifying that metadata is compatible with the dependency in use. [Native Build Tools — Maven Metadata Repository](https://graalvm.github.io/native-build-tools/latest/maven-plugin.html), [Gradle Metadata Repository](https://graalvm.github.io/native-build-tools/latest/gradle-plugin)

### 14.1. Check Dependencies Missing Metadata

With Maven:

```bash
./mvnw native:list-libraries-missing-metadata
```

With Gradle:

```bash
./gradlew listLibrariesMissingMetadata
```

These goals/tasks scan direct runtime dependencies and report libraries not yet supported by the repository. Check this report before writing custom metadata for a library that already has an official configuration. If metadata is missing, check the library's issues/release notes to see which versions have been tested.

### 14.2. When Should Repository Metadata Be Packaged into the JAR?

By default, Native Build Tools can use the metadata repository during the native build. If a downstream step takes an AOT-processed JAR and converts it into a native image later, repository metadata must be copied into the artifact.

With Maven, use the `add-reachability-metadata` goal in an appropriate execution. With Gradle, use the `collectReachabilityMetadata` task and include its output in the JAR if downstream pipelines expect metadata inside the artifact. You do not need this extra copy step if the native image is built in the same build where the plugin resolves metadata for the builder.

## 15. Collecting Metadata with the Tracing Agent

The Tracing Agent observes dynamic operations while the application runs on the JVM and records metadata for reflection, resources, proxies, serialization, or JNI it sees. This is useful for finding missing entries when a library does not yet provide adequate metadata.

Example running a Spring Boot executable JAR containing AOT assets:

```bash
java -Dspring.aot.enabled=true \
  -agentlib:native-image-agent=config-output-dir=target/native-agent \
  -jar target/payment-service.jar
```

After startup, exercise the business flows to check: deserializing requests, reading mappings/resources, running repository queries, creating proxies, invoking JNI, or serializing messages. Shut down the application gracefully so the Agent flushes output files.

### 15.1. Check Output by GraalVM Version

- On older GraalVM JDKs, the Agent may generate split files such as `reflect-config.json`, `resource-config.json`, and `proxy-config.json`.
- On GraalVM JDK 23+, the Agent can generate `reachability-metadata.json` in the unified format.
- Do not mix outputs generated across different GraalVM major versions without normalizing and validating against the schema.
- Do not overwrite already-reviewed metadata with fresh Agent output without diffing first.

The Agent only records executed code paths. If tests never hit a reflection or resource branch, its metadata will not appear. Use integration tests with thorough coverage and exercise error paths, alternate configs, profiles, and realistic payloads.

### 15.2. Filter Test-Generated Metadata

If running the Agent inside a test process, output may include metadata for JUnit, Maven Surefire, test fixtures, or test frameworks. Do not ship all of that metadata into a production image by default.

Instead:

1. Determine whether each entry belongs to application/runtime dependencies or only test frameworks.
2. Keep constructors/members/resources genuinely accessed dynamically.
3. Add conditions where appropriate so metadata applies only when the related type is reached.
4. Compare Agent output against metadata repository configs already supplied by dependencies.
5. Run native tests after filtering to ensure no needed entry was accidentally deleted.

The Tracing Agent is a runtime evidence-gathering tool; its output must be reviewed like code/configuration before committing.

## 16. Metadata and Build Flag Upgrade Workflow

Perform upgrades step by step so you can tell which change altered build or runtime behavior:

1. **Capture baseline:** record current Spring Boot, Java, GraalVM, Native Build Tools, metadata repository, dependency tree, build arguments, and native test results.
2. **Lock target JDK:** confirm GraalVM JDK major and Spring Boot release support each other; verify `native-image --version`.
3. **Check dependency metadata:** run `native:list-libraries-missing-metadata` or `listLibrariesMissingMetadata`; address unsupported dependencies.
4. **Inventory legacy config:** list all split metadata files, `native-image.properties`, Maven `buildArgs`, Gradle `buildArgs`, Buildpacks arguments, and environment variables used in the build.
5. **Select target schema:** for JDK 23+, migrate to `reachability-metadata.json`; for older targets, retain the schema supported by that builder. Do not validate a project built with JDK 21 against a JDK 25 schema.
6. **Convert entries:** update `name`/`type`, `typeReachable`/`typeReached`, resource regex/glob, proxies, and serialization according to the schema. Check conditions and interface order.
7. **Audit flags:** drop deprecated options, update missing-registration diagnostics per JDK major, and confirm every option still exists in `native-image --help`.
8. **Run Spring AOT:** confirm `process-aot` finishes with the exact profile and build-time environment; inspect generated sources, classes, and JSON hints.
9. **Build native:** run Maven/Gradle/Buildpacks with the pinned toolchain. Save full logs and the native image build report if supported by your distribution.
10. **Verify executable:** run native integration tests for reflection, proxies, resources, serialization, JNI, and actually used URL protocols.
11. **Compare artifacts:** inspect metadata diffs, binary size, startup, memory, and any new warnings; investigate every unexplained change.
12. **Lock configuration:** pin plugin/toolchain/repository versions, record the flag list, and update CI instructions so future builds are reproducible.

### 16.1. Validate Schema and Artifacts

GraalVM publishes JSON Schemas for `reachability-metadata.json`. JDK 25 documentation references schema `reachability-metadata-schema-v1.2.0.json`; to validate an older GraalVM release, use the schema matching that release. Don't just check that JSON parses: it can parse cleanly while still containing invalid fields or missing required metadata. [GraalVM — Reachability Metadata JSON Schema](https://www.graalvm.org/jdk25/reference-manual/native-image/metadata/)

After building, confirm metadata actually made it into build inputs:

```bash
jar tf target/payment-service.jar
```

Look for entries under `META-INF/native-image/`, including metadata contributed by the application, dependencies, and Spring AOT. If using Buildpacks or a pipeline converting the JAR to a native image in a subsequent step, confirm the final JAR still contains the metadata that step needs.

If you need to inspect which resources were embedded, use the Build Report or `-H:+GenerateEmbeddedResourcesFile` on supported versions. A file existing in the JAR does not prove it was included in the native executable.

## 17. Common Errors and Release Checklist

| Symptom | Possible cause | Resolution |
|---|---|---|
| `Unrecognized option` | Build script uses a flag absent in the installed GraalVM | Check `native-image --version`, `--help`, and plugin arguments |
| Metadata JSON parses but build reports invalid entry | Wrong schema, legacy fields, or field unsupported in that version | Validate against the target JDK's schema |
| Missing reflection registration at runtime | Agent missed the code path, or metadata was over-filtered | Enable exact metadata mode, run full tests, and add exact members |
| Resource not found | Wrong glob, file missing from classpath, or stripped from artifact | Check resource path and Build Report/embedded-resources file |
| Dynamic proxy error | Missing interface or interface order differs from metadata | Compare proxy definition against runtime interfaces |
| Serialization error | Unregistered type or custom serialization path | Check serialization metadata for the exact GraalVM release |
| JNI lookup error | Missing class/member accessed by native library | Add JNI metadata and run native integration tests |
| `--enable-https` flag warns deprecated | Old URL handler option used on newer JDK | Use reachability metadata for handlers if the app calls `java.net.URL` |
| Buildpacks and local native build differ | Builder image uses different GraalVM/Java or JAR lacks metadata | Pin builder image and inspect metadata inside the artifact |
| Unusual binary size growth | Overly broad metadata, whole-package includes, or huge resource glob | Narrow entries, add conditions, and inspect the report |

### Pre-Release Checklist

- [ ] Documented exact Spring Boot, Java, GraalVM JDK, Native Build Tools, and metadata repository versions.
- [ ] Metadata format matches the GraalVM JDK used in CI.
- [ ] No `typeReachable` conditions remain in newly converted metadata.
- [ ] Reflection entries use `type` and retain all required constructors/methods/fields.
- [ ] Resource regexes were intentionally converted to globs or kept in a compatible legacy format.
- [ ] Proxy metadata preserves exact interface lists and ordering.
- [ ] Serialization metadata matches the target GraalVM schema.
- [ ] JNI metadata covers lookups from native libraries.
- [ ] Dependency metadata is fetched by Native Build Tools or packaged when required by downstream pipelines.
- [ ] Repository release version is not confused with per-module metadata version.
- [ ] No deprecated build flags remain without documented justification.
- [ ] Exact reachability metadata and missing-registration reporting are configured properly for the JDK major.
- [ ] `native-image.properties`, Maven `buildArgs`, and Gradle `buildArgs` declare no conflicting options.
- [ ] Spring AOT runs with the proper profiles/build-time environment.
- [ ] Native executable has passed integration tests for dynamic access paths.
- [ ] Binary size, resource inclusion, and startup have been compared against the baseline.
- [ ] Toolchain and build arguments are pinned so CI builds are reproducible.

## 18. Key Takeaways

Reachability metadata and build flags are part of the contract between the application, libraries, Spring AOT, and GraalVM Native Image. GraalVM JDK 23 marks the shift to `reachability-metadata.json`, changes conditions to `typeReached`, and folds in proxy metadata; JDK 24 folds serialization metadata into reflection entries; JDK 25 documentation marks legacy URL protocol flags deprecated.

When upgrading, pick the schema and flags matching your target GraalVM JDK, audit the metadata repository for every dependency, and run native tests after conversion. Spring Boot AOT prepares generated assets; Native Build Tools delivers build arguments and metadata to Native Image; the Tracing Agent captures executed dynamic access paths. Only by checking all three pieces and verifying on the final executable does an upgrade have proof that reflection, resources, proxies, serialization, and JNI still work.
