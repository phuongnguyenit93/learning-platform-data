# Avoiding Metadata from Test Frameworks or Unnecessary Development Tools

The Native Image Tracing Agent records dynamic operations that static analysis may not infer on its own, such as reflection, JNI, dynamic proxies, and resource accesses. The agent observes the application while running on the JVM and then generates reachability metadata for use during the native build. If you simply run the full test suite or launch the application in a development environment, the output may contain lots of metadata generated by JUnit, Mockito, test fixtures, Spring Boot DevTools, or diagnostic tools.

Excess metadata makes configuration hard to review, may retain types unnecessary in production, and makes it harder to identify what metadata is genuinely needed. The solution is to **collect along production-like execution flows, filter by caller where appropriate, filter by target deliberately, and then verify the native executable against real business flows**.

This lesson focuses on the official filters of the GraalVM Tracing Agent, how to avoid recording metadata from test frameworks/development tools, and the risks of filtering too broadly.

## 1. Why Can Tracing Metadata Contain Unnecessary Data?

The Tracing Agent runs inside an ordinary JVM. Whenever the application performs a dynamic operation, the agent inspects the caller and target and decides whether to record that operation in metadata.

A Spring Boot application can be run in several contexts:

- A production-like JVM running the packaged JAR, containing only runtime dependencies.
- A test JVM running with JUnit, Mockito, AssertJ, Testcontainers, or other test libraries.
- A development JVM running with DevTools, restart classloaders, debuggers, profilers, or hot reload.
- A JVM running migration tools, code generation, schema checks, or diagnostics.
- A JVM launched by a Maven/Gradle test worker, IDE, or wrapper with extra dependencies.

If you attach the Tracing Agent to a test JVM, the agent can see dynamic accesses performed by the test framework. For example, JUnit may use reflection to discover test methods; Mockito/Byte Buddy may generate proxy classes; assertion libraries may read fields; DevTools may inspect classloaders or resources. These operations can appear in metadata even though the production application does not need them.

### Example of Noisy Data

Suppose the application has a real business path:

~~~text
HTTP request
  -> OrderController
  -> OrderService
  -> PaymentAdapter
  -> reads class metadata of PaymentDetails
~~~

Meanwhile, the test suite also runs:

~~~text
JUnit engine
  -> finds test methods via reflection
  -> Mockito creates mocks
  -> Byte Buddy generates classes
  -> AssertJ reads properties to build failure descriptions
~~~

If both run in the same tracing session, metadata can mix application accesses with test-only accesses. This does not necessarily break the native build, but it makes metadata larger and harder to understand.

## 2. Caller and Target: Two Different Filtering Questions

GraalVM provides two filter types for the Tracing Agent.

**Caller-based filters** answer: *Which class performed the dynamic operation?*

The agent identifies the method performing the access (the caller method), gets the class declaring that method, and matches it against rules. If the caller belongs to `org.junit`, the operation can be excluded from metadata even if the target is an application class.

**Access filters** answer: *Which class is the target of the dynamic operation?*

This filter evaluates the accessed class, not the calling class. If the target belongs to a test fixture package, that target can be excluded from metadata regardless of who called it.

| Criterion | Caller filter | Access filter |
| --- | --- | --- |
| Filters by | Class containing the method performing the dynamic operation | Class that is the accessed target |
| Used to exclude | Operations initiated by test frameworks/devtools | Test-only targets or classes outside runtime scope |
| Agent option | `caller-filter-file` | `access-filter-file` |
| Example | Skip reflection performed by JUnit | Skip targets inside a test fixture package |
| Risk | May drop operations performed by a framework that production also needs via the same call path | May drop application classes that runtime genuinely needs to access dynamically |

**Usually, start with a caller filter when you want to exclude operations initiated by a test framework.** Only use an access filter once you are certain a target class truly lies outside the application's runtime scope.

## 3. How Does a Caller Filter Work?

Create a JSON file, for example `caller-filter.json`:

~~~json
{
  "rules": [
    {
      "excludeClasses": "org.junit.**"
    },
    {
      "excludeClasses": "org.mockito.**"
    },
    {
      "excludeClasses": "org.assertj.**"
    },
    {
      "excludeClasses": "org.springframework.boot.devtools.**"
    },
    {
      "includeClasses": "com.example.billing.**"
    },
    {
      "excludeClasses": "com.example.billing.testsupport.**"
    }
  ]
}
~~~

The rules above illustrate how to exclude operations originating from test/framework/devtools packages while keeping operations originating from application packages. Replace the packages with your project's actual namespaces.

### Pattern Semantics

- `com.example.billing` matches the exact class with that full name.
- `com.example.billing.*` matches classes directly in the `com.example.billing` package, without descending into subpackages.
- `com.example.billing.**` matches classes in that package and all subpackages at every depth.

For applications with subpackages like `com.example.billing.order`, `com.example.billing.payment`, and `com.example.billing.config`, the `.**` pattern is usually more appropriate when you want to cover the entire package tree.

### Rule Ordering Matters

Rules are evaluated in the order they appear. A later rule can partially or completely override the outcome of an earlier rule.

Example:

~~~json
{
  "rules": [
    {
      "excludeClasses": "com.example.**"
    },
    {
      "includeClasses": "com.example.billing.**"
    },
    {
      "excludeClasses": "com.example.billing.testsupport.**"
    }
  ]
}
~~~

Result:

- By default, exclude callers in `com.example` and its subpackages.
- Then re-include callers in `com.example.billing`.
- Finally, specifically exclude callers in `com.example.billing.testsupport`.

This pattern is helpful when you need to exclude broadly and then reopen a specific application area. However, keep rules short and easy to review; if there are many overlapping exceptions, split filters by purpose and check ordering carefully.

## 4. Examples of Filtering Test Frameworks and DevTools

A starter caller filter for Spring Boot might exclude the following common packages:

| Caller Package | Why It Typically Appears | Caveat |
| --- | --- | --- |
| `org.junit.**` | JUnit discovers tests, invokes lifecycle methods, and accesses test metadata | Exclude only when tracing a test JVM; unnecessary in a production-only capture |
| `org.mockito.**` | Mockito creates mocks, inspects classes, and uses instrumentation/code generation | Whether production uses Mockito is a separate question; normally it does not |
| `org.assertj.**` | Assertion framework inspects objects to format comparison messages | Test-only |
| `org.springframework.boot.devtools.**` | Restarts, classloaders, and development support | Exclude only if this package actually appears in the trace |
| `com.example.billing.testsupport.**` | Test-only helpers, fixtures, or factories | Use a dedicated test package so test helpers do not sit inside production packages |
| `org.testcontainers.**` | Container startup and test environment checks | Should not be present in a production runtime capture |

Do not copy this list mechanically. The Tracing Agent may record operations from other packages depending on framework and library versions. Open the trace/metadata to inspect actual callers before adding rules.

### Do Not Exclude All of Byte Buddy or ASM by Default

Mockito and some frameworks use Byte Buddy/ASM internally. However, Byte Buddy can also be used by the application or production libraries to dynamically generate classes/proxies. If you exclude all `net.bytebuddy.**` or `org.objectweb.asm.**` callers, you can accidentally drop metadata needed by a production flow.

Exclude the specific test framework packages first. Only exclude Byte Buddy/ASM once you have verified the corresponding operations serve only tests/devtools and the native application does not need that path.

## 5. Access Filters: Excluding Target Classes Based on Evidence

Caller filters do not solve every case. Sometimes the caller is application code, while the target is a test fixture or a development-only class. In those cases, you can use an access filter.

Example `access-filter.json`:

~~~json
{
  "rules": [
    {
      "excludeClasses": "com.example.billing.testsupport.**"
    },
    {
      "excludeClasses": "com.example.billing.devfixtures.**"
    }
  ]
}
~~~

When a dynamic operation attempts to access a class in those packages, the target will not be added to the agent-generated metadata.

### When Is an Access Filter Dangerous?

Suppose the production application loads an implementation class by name from configuration:

~~~properties
billing.payment-handler=com.example.billing.payment.CardPaymentHandler
~~~

If the access filter excludes `com.example.billing.payment.**`, metadata needed for the handler can be dropped even though that class is genuinely used in production.

Therefore:

- Do not exclude a production package merely because its name looks internal.
- Do not exclude a target solely because it appears during tests.
- Verify whether the target class can be accessed in production.
- If a target appears in tests and is also used in production, you must retain the metadata needed for production.

## 6. Combining Caller Filters and Access Filters When Running the Tracing Agent

The agent accepts filter options in the `-agentlib:native-image-agent=...` string. Example running a packaged JAR:

~~~bash
$JAVA_HOME/bin/java \
  -agentlib:native-image-agent=caller-filter-file=src/native-image/caller-filter.json,access-filter-file=src/native-image/access-filter.json,config-output-dir=target/native-agent-config \
  -jar target/billing-service.jar \
  --spring.profiles.active=native-capture
~~~

Key points to remember:

- Use `java` from a GraalVM JDK with a compatible Native Image Tracing Agent.
- Place `-agentlib` before `-jar` or the main class name.
- Filter paths are resolved relative to the JVM process working directory.
- `config-output-dir` is the output directory; the agent writes metadata when the process exits cleanly.
- The `native-capture` profile is only an example. Use a profile that does not pull in DevTools, test fixtures, or development configuration.
- Never use real production credentials in a tracing workflow; use a test/staging environment with synthetic data and controlled services.

If you want to append results from multiple runs into the same metadata set, use `config-merge-dir`:

~~~bash
$JAVA_HOME/bin/java \
  -agentlib:native-image-agent=caller-filter-file=src/native-image/caller-filter.json,access-filter-file=src/native-image/access-filter.json,config-merge-dir=target/native-agent-config \
  -jar target/billing-service.jar \
  --spring.profiles.active=native-capture
~~~

Run separate scenarios to cover different business flows. If you need to save metadata periodically for a long-running application, the agent supports `config-write-period-secs` and `config-write-initial-delay-secs`; check the documentation for your GraalVM version before adding them to scripts.

## 7. Capturing from the Packaged Application Instead of the Test Classpath

The most effective way to reduce noise is choosing the right process to attach the agent to.

### Recommended Workflow

1. Build the application JAR with a production-like profile.
2. Do not include test dependencies on the runtime classpath.
3. Do not enable Spring Boot DevTools or remote development tooling.
4. Launch the packaged JAR itself using the GraalVM JDK and Tracing Agent.
5. Send requests via HTTP or a message broker just like the operating environment.
6. Exercise business flows involving reflection, serialization, proxies, resources, and JNI.
7. Stop the process cleanly so the agent writes output.
8. Review metadata before placing it under `META-INF/native-image`.

Do not attach the Tracing Agent to the Maven Surefire/Failsafe test JVM and treat the entire output as production metadata. A test JVM may contain the JUnit engine, mock frameworks, assertion libraries, test containers, and numerous test-scope-only helpers.

### When Tests Are Still the Only Way to Trigger a Dynamic Branch

Sometimes only a test triggers a rare business branch, yet that branch still exists in production. Do not discard metadata merely because the operation was observed during a test.

Instead:

- Create a production-like capture scenario calling that exact endpoint or service.
- Use synthetic data to trigger the branch.
- Invoke the flow through the application's real entry point.
- Use a caller filter to remove accesses performed by the test framework itself.
- Keep metadata needed by application code while handling business logic.

The goal is to eliminate **test-tooling activity**, not to remove **capabilities the application needs to serve business logic**.

## 8. Reading the Trace to Find Noisy Callers Before Adding Filters

The Tracing Agent can emit a trace file to inspect individual dynamic accesses rather than only looking at merged metadata files:

~~~bash
$JAVA_HOME/bin/java \
  -agentlib:native-image-agent=trace-output=target/native-agent-trace.json \
  -jar target/billing-service.jar \
  --spring.profiles.active=native-capture
~~~

The trace helps answer:

- Which dynamic access occurred?
- Which caller method/class performed the access?
- Which target class/member/resource was accessed?
- Did that access occur during startup, request handling, or running a test helper?

Afterward, you can use `native-image-utils` to generate metadata from the trace file:

~~~bash
native-image-utils generate \
  --trace-input=target/native-agent-trace.json \
  --output-dir=target/native-agent-config
~~~

Field names and trace structure may depend on the release. Consult `native-image-utils help` and documentation for your exact version.

### Access Classification Workflow

| Question | If Yes | Action |
| --- | --- | --- |
| Caller belongs to JUnit/Mockito/AssertJ? | Operation performed by test framework | Consider a caller filter |
| Caller belongs to DevTools/restart infrastructure? | Development-only operation | Disable DevTools during capture; if still needed, consider a caller filter |
| Caller belongs to an application package? | Likely a business flow | Do not exclude merely because it ran in a test |
| Target belongs to a test fixture? | May not exist in production | Consider an access filter after verifying |
| Target belongs to a production package? | Likely needed in real execution | Keep metadata and test on native |
| Caller is Byte Buddy/ASM? | Could be a mock or runtime code generation | Trace back who requested class generation; do not exclude the whole package immediately |

## 9. Understanding Filter Rules and Exceptions Accurately

Caller/access filters share the same JSON structure with two optional sections:

- `rules`: pattern-based rules matching class names.
- `regexRules`: regular expression rules applied to the entire fully qualified class identifier.

Example:

~~~json
{
  "rules": [
    {
      "excludeClasses": "org.junit.**"
    }
  ],
  "regexRules": [
    {
      "excludeClasses": ".*\\$\\$Generated[0-9]+"
    }
  ]
}
~~~

If `regexRules` is present, a class is considered included only when both `rules` and `regexRules` allow it and neither section excludes it. If `regexRules` is not declared, only `rules` determines the outcome.

Key principles:

- Rules are processed in order; later rules can override earlier ones.
- Multiple `caller-filter-file` options can be specified; rules are concatenated in the order the files are passed.
- The built-in caller filter runs before custom caller filters, and custom rules can override built-in results.
- Built-in filters already exclude certain accesses that Native Image supports without metadata.
- `no-builtin-caller-filter` and `no-builtin-heuristic-filter` are primarily for experimentation; their output is rarely suitable for normal builds.

Do not disable built-in filters just to make metadata look more complete. A metadata set with more entries does not equal a better metadata set.

## 10. Reviewing and Cleaning Metadata After Capture

After tracing finishes, inspect the output before committing. Depending on the GraalVM release, metadata may be emitted as `reachability-metadata.json` or separate files such as `reflect-config.json`, `resource-config.json`, `proxy-config.json`, `jni-config.json`, and `serialization-config.json`.

A review pass can follow these steps:

1. List generated files and compare against the previous capture.
2. Search for test/devtools packages still appearing in metadata.
3. Open the trace to identify callers and targets of suspicious entries.
4. Determine whether the production application needs that entry.
5. Adjust filters or capture scenarios.
6. Re-run the relevant business flows.
7. Build native and run integration tests.
8. Commit only verified metadata.

Do not bulk-delete entries based solely on package name. For instance, `org.springframework.*` may contain framework code that needs metadata for the application. Just because a library is a dependency does not mean all of its dynamic accesses are redundant.

### Inspecting Metadata with Diff

If using Git:

~~~bash
git status --short
git diff -- META-INF/native-image
~~~

You can store capture output in a temporary directory, review it, and then copy only the necessary parts into the module's metadata location. Do not let a local tracing output directory accidentally become production configuration without review.

## 11. Testing to Catch Over-Filtered Metadata

A good filter reduces noise while keeping all metadata needed for production. Therefore, after changing filters, rebuild native and test again.

Minimum scenarios:

| Scenario | Objective |
| --- | --- |
| Start native executable | Verify metadata needed during context bootstrap |
| Core business endpoints | Verify reflection/proxy/resource handling in common flows |
| Error and validation paths | Verify rarely invoked branches |
| Serialization/JSON binding | Verify required DTOs and subtypes |
| Security/login | Verify authentication-related metadata |
| Config-selected plugins/strategies | Verify all valid implementations |
| Resources/templates/message bundles | Verify static files and resource bundles |
| Native integration tests | Confirm behavior on the real executable |

If the native build fails with missing metadata or runtime throws an error on a specific branch:

1. Identify the missing target class/member/resource.
2. Locate the corresponding entry in the initial trace.
3. Check whether the entry's caller was dropped by a filter.
4. If the caller was a test framework but production business flows need that access, create a production-like capture scenario to preserve the entry.
5. Recollect metadata and run native tests.

A passing JVM test is not enough to prove a filter is safe. Final proof must come from the native executable running the production flows you need to support.

## 12. Hands-On Exercise: Excluding JUnit and DevTools Metadata

Suppose the `billing-service` application has:

- Application package `com.example.billing`.
- Test helper `com.example.billing.testsupport`.
- JUnit 5, Mockito, and AssertJ in test scope.
- Spring Boot DevTools used only during development.

Steps:

1. Build the executable JAR with runtime dependencies.
2. Confirm DevTools and test dependencies are not on the runtime classpath for the capture run.
3. Create `caller-filter.json` excluding `org.junit.**`, `org.mockito.**`, `org.assertj.**`, `org.springframework.boot.devtools.**`, and `com.example.billing.testsupport.**`.
4. If the trace contains targets belonging solely to test fixtures, create `access-filter.json` excluding that exact fixture package.
5. Run the JAR with the GraalVM JDK using `caller-filter-file`, `access-filter-file`, and `config-output-dir`.
6. Call endpoints for creating orders, payments, login, and flows involving reflection/serialization.
7. Run supplemental captures using `config-merge-dir` for any remaining branches.
8. Review metadata and verify no unnecessary test/devtools packages remain.
9. Build the native executable using the approved metadata.
10. Run native integration tests for the business flows.
11. Try removing one filter rule on an experimental branch to diff metadata; note which entries change and why.

### Self-Check Questions

1. How do caller filters and access filters differ in what they match?
2. Why is excluding caller `org.junit.**` usually appropriate when tracing a test JVM?
3. If JUnit invokes a test method, and that method triggers application reflection, which class might be the caller of the dynamic access?
4. Why should you not exclude all of `net.bytebuddy.**` by default?
5. How do the `.*` and `.**` patterns differ in package scope?
6. Why can rule order cause a class to be re-included after being excluded?
7. When should an access filter be used to exclude test fixture targets?
8. Why should you capture from the packaged application rather than just running the test suite?
9. How can you detect that a filter dropped metadata needed for a production branch?
10. Why does having more metadata not mean a better native executable?

**Success criteria:** you can explain caller filters and access filters; write JSON filters with clear rule ordering; exclude accesses initiated solely by test frameworks/DevTools without accidentally dropping application dynamic accesses; collect metadata from the packaged application with production-like scenarios; review and merge metadata in a controlled manner; and finally verify business flows on the native executable.
